[Target: SignerDb::create_or_migrate, MIGRATIONS/SchemaVersion (V1..V20)] An attacker who controls a miner slot cannot directly trigger this, but forces a signer's DB into a state where a restart mid-migration between two versions (e.g. crash after SCHEMA_19's MIGRATE_BLOCKS_DROP_SIGNED_OVER_ADD_APPROVED_TIME statement but before 'INSERT INTO db_config (version) VALUES (19)') leaves `blocks` recreated as `new_blocks`/`blocks` with rows whose `approved_time` was backfilled from `signed_self` while `db_config.version` still reads 18. Preconditions: signer has PreCommitted/LocallyAccepted blocks recorded before restart; crash occurs inside `create_or_migrate`'s per-migration loop after `sql_tx.execute_batch` but the process dies before `Self::get_schema_version` check commits. Call sequence: signer restarts, `create_or_migrate` re-reads `current_db_version`, and because SQLite DDL inside `execute_batch` is not atomic across process crash the same block may be replayed through migration 19 twice or seen as still version 18 with a half-renamed table, causing `BlockInfo::approved_time` and `signed_self` to diverge from what was recorded pre-crash. Equality: the `BlockInfo.approved_time`/`state` a signer holds for a given `signer_signature_hash` after restart == what it held immediately before the crash. Impact: Critical — if `approved_time` is lost/reset, `mark_pre_committed`/`mark_locally_accepted`'s `get_or_insert` semantics let the signer re-derive a *different* PreCommitted/LocallyAccepted decision on the same hash and potentially sign a second, conflicting message at the same height. Proof idea: Rust test that runs `SignerDb::new` on a v18 DB fixture with a PreCommitted row, kills the transaction before commit (simulate via manual `execute_batch` without commit), reopens, and asserts `block_lookup` returns identical `BlockInfo` (byte-for-byte state) both before and after.
