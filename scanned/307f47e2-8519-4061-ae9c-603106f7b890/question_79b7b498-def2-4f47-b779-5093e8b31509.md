[Target: create_block_rejection / send_block_response ordering vs signer_db.insert_block] When check_block_against_state returns Some(block_rejection) in handle_block_proposal, the rejection is sent via send_block_response WITHOUT calling signer_db.insert_block (per the 'not stored' comment), meaning a subsequent re-proposal of the identical bytes with no prior BlockInfo record re-runs the full check from scratch rather than short-circuiting via should_reevaluate_block. An attacker exploits this by re-sending the SAME invalid proposal thousands of times, but more critically, by interleaving a validly-different proposal with a hash collision-adjacent scenario is infeasible; the real risk is: if check_block_against_state has ANY nondeterministic branch (e.g. depends on sortition_state fetched fresh each time via SortitionsView::fetch_view, which can race with a legitimate burnchain-tip update), repeated resends of the SAME bytes could get a DIFFERENT verdict on each call since no BlockInfo persists the first (correct) rejection. Preconditions: block never stored because it was 'provably invalid', sortition_state races between calls. Call sequence: handle_block_proposal(X) [attempt 1] -> check_block_against_state -> Err/rejection sent, not stored; handle_block_proposal(X) [attempt 2, resent by attacker within a fork window] -> block_lookup_by_reward_cycle returns None (never stored) -> fresh check_block_against_state -> if sortition_state now reflects a fork that makes X valid, X is accepted and submitted for node validation, then possibly signed. Equality: FAIL-CLOSED - a block once determined invalid for the SAME bytes must never later flip to being submitted-for-validation/signed without an intervening canonical state change that a signer can point to. Impact: Critical - an attacker can retry an invalid proposal across a natural sortition-view refresh race to get it accepted despite no real chain-state justification, given rejections are never persisted for un-stored blocks. Proof idea: Rust test in stacks-signer/src/v0/tests.rs sending an identical BlockProposal twice with a SortitionsView refresh injected between the two calls (simulating a legitimate view change), asserting that if the second call's chainstate view differs, this constitutes a genuine re-evaluation and must be logged/traceable, and that repeated resends with an UNCHANGED view never produce a different verdict.
