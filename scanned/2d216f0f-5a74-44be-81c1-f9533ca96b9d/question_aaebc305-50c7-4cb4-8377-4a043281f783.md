Target: NakamotoBlockVote persisted implicitly via BlockInfo.vote: Option<NakamotoBlockVote>, and its StacksMessageCodec round-trip (rejected flag encoded as presence/absence of a trailing byte). Attacker action: none required beyond normal signing flow; the flaw is that consensus_serialize/consensus_deserialize for NakamotoBlockVote encodes 'rejected=true' as an optional trailing 1u8 byte, so any truncation or partial write during a crash right after voting can leave a persisted vote whose deserialized rejected flag flips to false. Preconditions: signer wrote a NakamotoBlockVote{rejected:true} for H just before an abrupt process kill, and the JSON serialization of BlockInfo (not the codec path) is what's actually stored, but any code path that separately persists/replicates the vote via StacksMessageCodec is subject to truncation. Call sequence: restart -> vote read back with rejected=false due to a truncated write -> BlockInfo.state may still say LocallyRejected while BlockInfo.vote now claims an unrejected (i.e. accepting) vote was cast -> downstream code trusting BlockInfo.vote over BlockInfo.state re-emits or reports an acceptance signature for H. Equality: BlockInfo.vote.rejected read back after restart == the state field's rejection status for the same signer_signature_hash; the two must never disagree. Impact: Critical - a torn write on the optional trailing byte can convert a persisted rejection vote into an apparent acceptance vote, and if any consumer trusts .vote over .state, it can result in a signature over a block the signer meant to reject. Proof idea: Rust test that serializes NakamotoBlockVote{rejected:true}, truncates the last byte of the buffer to simulate a torn write, deserializes it, and asserts the signer's consistency check (vote.rejected == (state == LocallyRejected/GloballyRejected)) rejects/repairs the mismatch rather than trusting the truncated vote.
