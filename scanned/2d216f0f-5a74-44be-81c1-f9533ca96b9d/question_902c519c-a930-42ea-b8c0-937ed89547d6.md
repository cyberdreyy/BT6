Target: db_config table (version INTEGER) gating which SCHEMA_N array runs, combined with SignerDb opening the same sqlite file from two different binary versions in a blue/green signer-restart deployment. Attacker action: none direct; the attacker's leverage is timing a BlockProposal exactly during an operator's blue/green restart where an old-version signer process and a new-version signer process both briefly hold connections to the same signerdb file, with the new one having already bumped db_config.version and altered the blocks table shape mid-migration. Preconditions: old process still has an in-memory decision for H as LocallyRejected but hasn't flushed; new process's migration transaction is applied concurrently. Call sequence: new process's migration (DROP TABLE blocks / ALTER TABLE ... RENAME) commits -> old process's later insert_block(H, LocallyRejected) targets a table that no longer has the pre-migration column set expected by the old binary's SQL text, causing either an error that's swallowed by a retry-and-recreate path, or a write to a freshly recreated 'blocks' table missing the rejection entirely. Equality: the persisted decision for H immediately after the migration window == the decision the old process believed it had already committed, i.e. no committed decision may vanish due to a concurrent schema migration. Impact: Critical - concurrent migration during operator restart can silently drop an already-decided rejection, letting either the same or a re-spawned signer process sign the previously rejected block. Proof idea: Rust test using two SignerDb connections to the same sqlite file, running migrate() on one while the other attempts insert_block, asserting the insert either fails loudly (never silently drops) or is applied strictly after migration completes and is confirmed present via block_lookup.
