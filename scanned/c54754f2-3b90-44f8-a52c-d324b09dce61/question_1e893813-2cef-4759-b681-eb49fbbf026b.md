Target: `stacks-signer/src/v0/signer.rs::Signer.signer_weights: HashMap<StacksAddress, u32>` used implicitly by pre-commit tally logic versus `stacks-signer/src/signerdb.rs::get_block_pre_committers` which returns raw `StacksAddress`es with no embedded weight, requiring a separate lookup at tally time. Attacker action: as a miner/gossip peer, cause two different `StacksAddress`es to be presented for the same `BlockPreCommit` sighash by racing message delivery so `add_block_pre_commit` records an address whose corresponding weight entry in `signer_weights` was already stale-evicted or not yet populated (e.g., during the `refresh_signer_config` gap when `signer_weights` is being swapped for a new cycle), causing the tally routine to either skip that address's weight (undercount, liveness stall) or, if a default/fallback weight is used, overcount it. Preconditions: race window during `refresh_signer_config` where `Signer` struct fields (`signer_weights`, `signer_addresses`) are being replaced. Call sequence: `handle_block_pre_commit`'s weight-tally step (`docs/signer-flows.md` section 5, "tally weight") sums via lookup into `signer_weights`; a missing or defaulted entry produces a tally that doesn't equal `sum(true weight of addresses that pre-committed)`. Equality: the sum of weights the pre-commit tally credits toward the 70% `compute_voting_weight_threshold` gate == the sum of the *current* `RewardSet`'s per-address weights for exactly the addresses that actually pre-committed. Impact: Critical — an undercount can wedge liveness (never reaching 70%, a valid block never gets signed) while an overcount can let an under-supported block cross the signing threshold. Proof idea: `stacks-signer` unit test replacing `signer_weights` mid-flight between two `add_block_pre_commit` calls for the same block, asserting the tally computed by the pre-commit handler matches (or diverges from) a ground-truth sum computed directly from a fixed `RewardSet` snapshot.
