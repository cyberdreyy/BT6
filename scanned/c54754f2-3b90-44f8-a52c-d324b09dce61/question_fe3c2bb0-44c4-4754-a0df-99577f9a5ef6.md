Target: `stackslib/src/chainstate/nakamoto/mod.rs::verify_signer_signatures`'s strict `last_index` ordering check (`if *index >= signer_index { return Err(...) }`), which is keyed by `signer_index` from `reward_set.signers().enumerate()`. Attacker action: as the block-proposing miner, submit a `BlockProposal` at the exact reward-cycle rollover height where the reward set the *validating node* uses (fetched by `block_id`/tip) is one block behind the reward set the *signing signers* believe is active (their `current_reward_cycle_info` from `stacks_client.get_current_reward_cycle_info`), by proposing before all signers have observed the same tip. Preconditions: reward-cycle boundary block just processed by some but not all signers; `first_proposal_burn_block_timing` window ambiguous. Call sequence: some signers sign using their view of the reward-set ordering under cycle N+1's index assignment, others still under N's; when a coordinator/node assembles `signer_signature` for `verify_signer_signatures`, indices computed from the *node's* `reward_set` may not correspond 1:1 to the ordering signers actually signed against. Equality: the `reward_set`/index ordering each signer signs relative to (implicitly, via their own weight computation) == the `reward_set` the node passes into `verify_signer_signatures` for that specific block. Impact: Critical — a legitimately signed-but-index-mismatched set of signatures can be rejected as "out of order" (fail-closed miss, wedging liveness) or, worse, a signature recovered to a public key that collided with a different signer_index across the two orderings can be double counted/misattributed, corrupting `total_weight_signed`.
