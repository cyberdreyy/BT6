`SignerDb::create_or_migrate` executes each `Migration`'s `statements` sequentially outside of a single atomic transaction spanning all of them (each migration's individual `&str` scripts are executed, e.g. `MIGRATE_BLOCKS_DROP_SIGNED_OVER_ADD_APPROVED_TIME`'s multi-statement script). If the process is killed between `CREATE TABLE new_blocks` + `INSERT OR IGNORE INTO new_blocks` completing and the terminal `DROP TABLE blocks; ALTER TABLE new_blocks RENAME TO blocks;` and `INSERT INTO db_config (version) VALUES (19)` running, can a restart re-observe `get_schema_version` still at 18, re-run schema 19's `CREATE TABLE IF NOT EXISTS new_blocks` (now already populated) and error or silently no-op on `INSERT OR IGNORE`, leaving the signer with two divergent tables (`blocks` old, `new_blocks` partially populated) such that `block_lookup` reads a stale pre-migration `blocks` row for a tenure whose true latest decision is only in `new_blocks`? Equality: the row `block_lookup` returns after a crashed-and-retried migration == the last decision actually recorded before the crash. Impact: High, a genuinely-decided block appears `Unprocessed` post-restart, or vice versa, risking a re-sign. Proof idea: manually replicate the intermediate on-disk state (both tables present, version still 18), run `create_or_migrate` again, and assert `block_lookup` matches the pre-crash decision, not a reset one.
