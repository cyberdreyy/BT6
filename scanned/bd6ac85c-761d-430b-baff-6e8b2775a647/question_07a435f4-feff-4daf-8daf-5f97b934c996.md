`get_schema_version` is computed via `SELECT MAX(version) FROM db_config LIMIT 1`; `db_config` has no `UNIQUE`/single-row constraint enforced beyond migration discipline (`DELETE FROM db_config;` only appears in `SCHEMA_5`). If two concurrent migration attempts (e.g. two signer processes briefly racing on the same DB path during a restart/upgrade window) each `INSERT INTO db_config (version) VALUES (N)` for different N without the `DELETE`, can `db_config` end up with multiple rows so `MAX(version)` reports a version higher than what was actually fully applied, causing `create_or_migrate` to skip re-running a migration whose statements never completed, leaving e.g. `superseded_tenures` absent while the signer believes schema 20 is active and blindly trusts absent-table reads (via `table_exists` guards elsewhere) as 'nothing superseded' rather than 'unknown'? Equality: reported schema version == fully-applied schema version. Impact: High, false confidence in migration completeness silently degrades the equivocation/canonicity guard. Proof idea: manually insert two `db_config` rows with different versions after only partially running a migration's statements, restart `SignerDb::new`, and assert whether it detects the inconsistency or proceeds as if fully migrated.
