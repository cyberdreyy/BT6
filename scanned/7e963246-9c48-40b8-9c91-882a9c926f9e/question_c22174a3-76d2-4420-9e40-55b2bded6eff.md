Can two DeployGlobalContractAction receipts for the same GlobalContractIdentifier::CodeHash (impossible since CodeHash is derived from content) or, more relevantly, two AccountId-mode deployments issued back-to-back by the owner before the first's distribution receipt reaches a given shard, cause check_and_update_nonce on that shard to accept the second (newer) nonce first and then accept the first (older, now-stale by content) deployment's receipt as 'fresh' too via the >= rule, so the account ends up with different code cached (precompile_contract_with_warming) than committed to state_update.set(trie_key, ...)? Victim: any account with AccountContract::GlobalByAccount(owner) relying on deterministic code identity across shards. Invariant: determinism -- all shards converge to the same code for a given identifier after both receipts apply, in receipt-arrival order not nonce order. Proof idea: apply two GlobalContractDistributionReceipt for the same AccountId identifier with nonces N and N+1 delivered out of order to the same shard's state_update and assert the final GlobalContractCode trie value equals the higher-nonce code deterministically regardless of delivery order. Scoped impact: Contracts execution flows / Consensus flaws (state-root divergence across shards applying receipts in different order).
