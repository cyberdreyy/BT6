In `conflict_still_blocks` (stacks-signer/src/v0/signer.rs), an attacker who wins tenure T2 can force the node's `/v3/sortitions/burn/:hash` and `get_tenure_tip` RPCs to be unreachable during the exact evaluation window (e.g. by exploiting timing around a burnchain event) so that both branches return 'leaving the conflict in place' -- but if the attacker can instead get the *node itself* to observe a 404 for the conflicting tenure's burn block while its own burnchain tip has NOT yet reached that height, and then race a second signer instance that has already advanced its tip, two signers disagree on `conflict_still_blocks` for the same signed conflict A vs proposal B. Preconditions: signer restarted or slow to sync, block A locally signed in T1, proposal B in T2 at same height. Call sequence: get_burn_block_by_ch -> get_sortition_by_burn_hash returns 404 -> get_peer_info compares burn_block_height on a lagging node -> conflict wrongly treated as blocking on one signer, non-blocking on a resynced one -> only the resynced one signs B while the first already signed A. Equality: UNIQUENESS across signers for (tenure, height) is not the target here; rather the wedge is per-signer FAIL-CLOSED disagreement causing a chain split at 70% weight if enough signers are in the resynced state. Impact: Critical, signer signing a non-canonical/conflicting block due to a race in node sync state, not attacker-controlled bytes but attacker-timed tenure win. Proof idea: unit test in stacks-signer/src/v0/tests.rs mocking StacksClient::get_sortition_by_burn_hash to 404 and get_peer_info at two different burn_block_height values, asserting conflict_still_blocks returns different booleans for the same SignedConflictInfo depending purely on node lag, and that this is exploitable to produce two `signed_self` results for siblings.
