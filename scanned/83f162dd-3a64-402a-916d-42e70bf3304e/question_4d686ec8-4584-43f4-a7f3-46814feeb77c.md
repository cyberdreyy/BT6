Target: `BlockRejection::recover_public_key` vs `BlockAccepted`'s `signer_pubkey.verify` (libsigner/v0/messages.rs, stackerdb_listener.rs Rejected arm). Attacker action: gossip a `BlockRejection` whose `signature` recovers to a pubkey that happens to equal `signer_pubkey` for a *different* slot_id than the one the chunk was posted under. Preconditions: attacker only knows public signer_entries (public reward-set data), not any private key. Call sequence: `rejected_data.recover_public_key()` -> compare to `signer_pubkey` looked up via `slot_id` -> `if rejected_pubkey != signer_pubkey { ignore }`. Equality: the pubkey that authorizes the rejection weight increment must equal the pubkey assigned to that `slot_id` in `signer_entries`; recovery-based auth (not straight `verify`) creates an asymmetric check between the Accepted and Rejected code paths. Impact: Critical if this asymmetry lets a rejection's weight get attributed to the wrong slot_id (double counting or wrong-signer-weight substitution) without the real key. Proof idea: construct a `BlockRejection` signed by an attacker-controlled key, submit it under a slot_id belonging to an honest signer, assert `StackerDBListener` correctly ignores it (rejects, since `rejected_pubkey != signer_pubkey`) — regression-guard test that this cannot be relaxed.
