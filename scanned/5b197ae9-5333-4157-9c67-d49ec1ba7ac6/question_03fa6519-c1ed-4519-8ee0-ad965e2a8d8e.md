Target: SortitionData fields trusted from the sortition (miner_pkh, consensus_hash, parent_tenure_id, burn_block_hash) versus the BlockProposal header's independently signed fields (chainstate/v2.rs check_proposal_miner_pkh_mismatch test). Attacker action: submit a BlockProposal whose header.consensus_hash correctly matches current_sortition but whose header.miner_signature is produced by a different keypair than current_sortition.data.miner_pkh, attempting to have a losing party's block accepted as if the winning miner produced it. Preconditions: attacker is a non-winning party observing the winning miner's consensus_hash publicly. Call sequence: check_proposal -> PubkeyHashMismatch comparison of block.header.miner_signature's recovered pubkey hash against current_sortition.data.miner_pkh. Equality: the pubkey hash recovered from block.header.miner_signature must equal current_sortition.data.miner_pkh (the sortition-determined winner), or the proposal must be rejected. Impact: Critical - if this equality check is ever bypassable (e.g., signature malleability or a code path skipping PubkeyHashMismatch), a party who did not win the sortition gets a block signed as canonical. Proof idea: Rust test extending check_proposal_miner_pkh_mismatch to attempt bypasses (e.g., high-S signature variant, or a tenure-extend path that does not re-verify miner pubkey) and asserting RejectReason::PubkeyHashMismatch still fires in every code path that ends in a signature.
