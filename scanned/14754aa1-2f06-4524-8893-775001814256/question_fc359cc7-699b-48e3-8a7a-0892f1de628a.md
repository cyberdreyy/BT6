`NakamotoBlockHeader::compute_voting_weight_threshold` (stackslib/src/chainstate/nakamoto/mod.rs) is called both by the node (in `verify_signer_signatures`) and independently mirrored by `stacks-signer`/StackerDBListener using each side's own `total_weight` input. Can an attacker force a signer's locally-cached `total_weight` (from a previous `get_reward_set` fetch, stacks-signer/src/client/stacks_client.rs) to diverge from the node's freshly-recomputed `total_weight` for the same `reward_cycle` — e.g. by triggering a PoX reward-set recomputation between the signer's last refresh and a new `BlockProposal` — so `compute_voting_weight_threshold(signer_total_weight) != compute_voting_weight_threshold(node_total_weight)`? Equality: threshold the signer applies to decide 'enough weight has signed' == threshold the node's `verify_signer_signatures` applies for the same reward_cycle. Impact: Critical — a signer's local approval-of-quorum decision (if it independently tallies weight) diverges from consensus's actual threshold, letting an under-weighted block be treated by the signer's bookkeeping as approved. Proof idea: Rust test computing `compute_voting_weight_threshold` twice with two different `total_weight` values derived from stale vs fresh reward sets for the same cycle, asserting the thresholds differ and demonstrating a block could satisfy one but not the other.
