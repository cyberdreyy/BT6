`get_miner_slot` (stackslib/src/chainstate/nakamoto/mod.rs) resolves a miner's StackerDB slot range via `miners_info.get_signer_index(election_sortition)`, keyed by the sortition's `ConsensusHash`, not by the current chain tip's sortition. Can an attacker who wins a miner slot for sortition A, then submits a `BlockProposal` referencing a *different* `election_sortition` value B (one that also maps them to a valid slot range under `make_miners_stackerdb_config`), get a signer to accept a proposal whose declared election-sortition slot mapping doesn't match the miner's actual winning sortition for the current burn tip? Equality: (election_sortition used to resolve the miner's StackerDB slot for the proposal a signer is validating) == (the sortition that actually elected the miner for the current tenure). Impact: Critical — a signer could validate/sign a `BlockProposal` attributed to the wrong tenure's miner, breaking canonicity of which tenure the block belongs to. Proof idea: stacks-signer test building two `BlockProposal`s that reference different `election_sortition` ConsensusHash values for the same miner key, feeding both through the signer's proposal-acceptance path and asserting only the proposal whose sortition matches the current tip's elected miner is signed.
