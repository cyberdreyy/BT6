`SignerConfig.reward_cycle` is fixed at construction time in `get_signer_config` (stacks-signer/src/runloop.rs), and `RunLoop.stacks_signers: HashMap<u64, ConfiguredSigner<Signer, T>>` is keyed by `reward_cycle % 2` (an odd/even bucket), not by the full `reward_cycle` value. Can an attacker who forces two reward cycles N and N+2 (same parity) to overlap in the runloop's transition window cause a `ConfiguredSigner` built for cycle N to remain keyed under the same HashMap slot as a newly-built `ConfiguredSigner` for cycle N+2, so a `BlockProposal`/message tagged for reward_cycle N+2 gets routed to (or evaluated against) the still-resident cycle-N `Signer`'s `reward_cycle`/`signer_weights` state before the runloop replaces the entry? Equality: (reward_cycle the `Signer` instance handling an incoming message believes it is) == (reward_cycle the message/proposal is actually for). Impact: Critical — a signer could evaluate a proposal for cycle N+2 using cycle N's weight/threshold context, or sign a message whose `signer_signature_hash` gets bound as if issued under the wrong cycle's reward set. Proof idea: stacks-signer test driving the runloop through consecutive same-parity reward-cycle transitions with deliberately overlapping timing, asserting the `stacks_signers` HashMap never holds a `Signer` whose `.reward_cycle` mismatches the reward_cycle of a message being dispatched to it via the parity key.
