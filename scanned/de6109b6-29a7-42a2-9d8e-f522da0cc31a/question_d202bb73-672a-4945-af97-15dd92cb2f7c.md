`SignerEntries::parse` (libsigner/src/signer_set.rs) assigns `signer_id` as the enumeration index `i` over the `reward_set` slice with no ordering assertion versus consensus. Can an attacker who wins a miner slot in the burn header submit a `NakamotoBlock` whose `signer_signature` vector's ordering the miner constructs to line up with a different `signer_id` mapping than the node's own `signers_by_pk` HashMap built in `NakamotoBlockHeader::verify_signer_signatures` (stackslib/src/chainstate/nakamoto/mod.rs)? Preconditions: reward set with distinct weights per signer, `strict_order` gated by `epoch_id.enforces_strict_signature_order()`. Call sequence: signer signs `signer_signature_hash`, its signature is later reordered/interleaved by the miner before broadcast, `verify_signer_signatures` recovers `public_key` per signature and finds `(signer, signer_index)` from `signers_by_pk`, enforcing `last_index >= signer_index` fails for out-of-order signatures. Equality: the (signer, weight) pair the signature cryptographically authenticates == the (signer, weight) the node credits via `signer_index`. Impact: Critical if pre-epoch-4.0 non-strict-order path lets a signature be attributed to the wrong weight bucket, mis-tallying `total_weight_signed`. Proof idea: unit test in stackslib constructing a reward set with skewed weights and signatures submitted out of enumeration order, asserting `verify_signer_signatures`' `total_weight_signed` matches only signatures whose recovered pubkey equals the credited signer.
