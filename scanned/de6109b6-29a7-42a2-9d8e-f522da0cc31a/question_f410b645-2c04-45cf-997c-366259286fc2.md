`update_signers` (stackslib/src/chainstate/nakamoto/signer_set.rs) writes `signers_list`/`stackerdb_list` Clarity tuples keyed by `signer` (a `StacksAddress` derived via `Hash160::from_data(&signer.signing_key)`), while `SignerEntries::parse` (libsigner/src/signer_set.rs) derives `stacks_address` via `StacksAddress::p2pkh(is_mainnet, &signer_public_key)`. Can an attacker exploiting any divergence between these two address-derivation paths (e.g. a signing key whose `Hash160::from_data` output byte-for-byte differs from `p2pkh`'s internal hashing due to a version/hash-mode mismatch under a crafted delegate/stacking setup) get a signer's `signer_addr_to_weight` lookup in libsigner to key on an address distinct from the one the on-chain `.signers` contract actually credits weight to via `get-signers`/`get_signers_weights` (stackslib/src/chainstate/nakamoto/signer_set.rs)? Preconditions: attacker controls a delegated stacking configuration influencing `NakamotoSignerEntry.signing_key`. Call sequence: reward-set computed and written on-chain -> signer parses same entries locally -> address mismatch causes a HashMap miss/wrong-weight-key at vote tally time. Equality: signer-derived StacksAddress-to-weight mapping == on-chain `.signers` contract's signer-to-weight mapping (`get_signers_weights`). Impact: Critical - a signer's vote miscredited to the wrong address, causing incorrect weight tallying at finalization. Proof idea: property test in stackslib comparing `Hash160::from_data(&entry.signing_key)`-derived address in `update_signers` against `SignerEntries::parse`'s `StacksAddress::p2pkh` derivation for the same signing_key across many keys, asserting equality holds unconditionally.
