`RunLoop::process_event` (stacks-signer/src/runloop.rs) computes `current_reward_cycle` once per pass and calls `signer.process_event(..., current_reward_cycle)` for every `ConfiguredSigner::RegisteredSigner` in `stacks_signers`, but each `Signer` instance internally stores its own fixed `self.reward_cycle` set at construction via `Signer::new(&self.stacks_client, new_signer_config)`. Can a miner that stalls burn-chain progress right at a reward-cycle boundary (so the node's runloop computes a new `current_reward_cycle` before `refresh_signer_config` has replaced the stale `ConfiguredSigner`) cause `self.reward_cycle <= current_reward_cycle` (v0/signer.rs process_event) to be true for a signer instance whose `signer_entries`/`signer_slot_ids` were parsed from the prior cycle's reward set? Preconditions: exactly at cycle rollover, `refresh_signer_config` not yet called for new cycle. Call sequence: stale `Signer` processes `BlockProposal` for `block_proposal.reward_cycle` matching its own `self.reward_cycle` field but signer_entries stale. Equality: `self.reward_cycle`/`signer_entries` of the acting `Signer` == the `RewardCycleInfo.reward_cycle`/reward set consensus derived for that height. Impact: Critical - block finalized with weight computed from a stale/wrong reward set. Proof idea: Rust test constructing two `SignerConfig`s (old/new reward_cycle) and asserting `process_event` never lets a stale `signer_entries` handle a `BlockProposal` whose `reward_cycle` differs from the entries' origin cycle.
