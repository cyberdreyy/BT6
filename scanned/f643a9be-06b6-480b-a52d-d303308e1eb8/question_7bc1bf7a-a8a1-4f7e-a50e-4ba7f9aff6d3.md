`BlockRejection`'s `recover_public_key()` in libsigner/v0/messages.rs recovers the signer's key from the rejection's own `signature` field, and stackerdb_listener.rs cross-checks it against the StackerDB slot's known `signer_pubkey` before counting weight — but the Accepted arm never calls an equivalent slot-vs-signature cross-check function, relying solely on `signer_pubkey.verify(block_sighash.bits(), &signature)` (does the signature verify under the *slot's* key, not whether the key *recovered* from the signature matches the slot). Since `verify` on a message can accept a signature produced by any key if malformed/ambiguous recovery libraries allow multiple valid (r,s,v) reconstructions, can an attacker (controlling gossip content, not any private key) craft a `BlockAccepted.signature` for a hash H such that it independently verifies under two different signer_entries' pubkeys mapped to two different slot_ids (a shared-signature multi-slot credit), inflating `total_weight_approved` beyond the true number of consenting signers when the *same* forged blob is submitted under two different slot_ids in two separate StackerDB writes? Equality: distinct slot_ids credited toward total_weight_approved == distinct signer keys that each independently produced a signature over H. Impact: Critical, weight inflation without majority collusion could push a bad block over `weight_threshold`. Proof idea: property test enumerating whether a fixed secp256k1 ECDSA signature+message pair can validate under more than one public key (should be false); if so, add signer-vs-signature key-recovery cross check identical to BlockRejection's, and assert it in the Accepted arm.
