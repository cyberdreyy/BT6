In stackerdb_listener.rs, the Accepted arm's guard `let Some(block) = blocks.get_mut(&block_sighash) else { ... continue }` silently drops any Accepted message for a hash not already inserted via `insert_block`, but the Rejected arm has the identical guard. Since `insert_block` is called once per proposal by the miner thread in `propose_block`, and `block_sighash`/`rejected_data.signer_signature_hash` are attacker-visible from a prior gossiped `BlockProposal`, can an attacker pre-seed a flood of Rejected messages for a *predicted future* signer_signature_hash before the corresponding `insert_block` call executes, so they are silently dropped (not a safety bug) — but then race the *opposite*: send Accepted messages for a hash matching a *previous, superseded* proposal that is still present in the `blocks` map (never evicted) because `propose_block`'s loop only inserts new entries and there is no eviction of stale sighash keys — can late-arriving Accepted weight for an abandoned prior proposal linger and be read by `wait_for_block_status` if a *new* proposal at the same height coincidentally regenerates the same `signer_signature_hash` (e.g. re-proposing identical block content after `SignatureTimeout`)? Equality: weight aggregated for hash H at time T == accept responses whose signature verifies over the exact block object live at T. Impact: Critical if reused identical resubmission after timeout lets stale, no-longer-relevant Accepted weight silently satisfy the new attempt's threshold without those signers re-validating current chain tip. Proof idea: test resending an identical block after `SignatureTimeout`, injecting pre-existing gathered_signatures from the earlier round, and asserting the new round requires fresh validation context (e.g. tip check) rather than reusing stale weight.
