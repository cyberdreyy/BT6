`get_block_status` in signer_coordinator.rs treats reaching the staging DB (`chain_state.nakamoto_blocks_db().get_nakamoto_block(block_id)`) as proof of enough signing weight ('a block can only get stored there if it has enough signing weight to clear the threshold') and short-circuits by returning `stored_block.header.signer_signature` without re-verifying those signatures against `block_signer_sighash` locally. Can an attacker relay-race a `NakamotoBlock` into the staging DB via `find_highest_known_block_header_in_tenure` matching `block_id` but whose `header.signer_signature` vector was in fact aggregated over a *different*, sibling `signer_signature_hash` (possible if the block content differs from what this coordinator proposed but shares `block_id`/`parent_block_id`), so the returned signatures are accepted for the local proposal without the coordinator ever confirming `signer_signature_hash()` equality? Equality: block_id used to fetch staged signatures == the signer_signature_hash those signatures were computed over. Impact: Critical, VALIDITY breach - signatures for one block content accepted as if covering the coordinator's own proposal. Proof idea: unit test staging a NakamotoBlock with mismatched header vs coordinator's in-memory `block.header`, and assert `get_block_status` must re-derive and compare `signer_signature_hash()` before trusting `stored_block.header.signer_signature`.
