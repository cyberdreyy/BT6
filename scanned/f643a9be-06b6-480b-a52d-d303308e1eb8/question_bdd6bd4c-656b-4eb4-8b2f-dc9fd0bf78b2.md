`StackerDBListener`'s Accepted arm checks `if !block.gathered_signatures.contains_key(&slot_id) { total_weight_approved += weight }` then unconditionally does `block.gathered_signatures.insert(slot_id, signature)` — a second Accepted message from the same `slot_id` with a *different* signature (still verifying over the same `block_sighash`, e.g. different `s` in a malleated ECDSA sig) silently overwrites the stored signature without incrementing weight again, but also without checking the *first* stored signature is unchanged before final aggregation in `propose_block`. Since gossip order across a StackerDB session is attacker-influenced (attacker controls miner-side proposal cadence and can trigger `wait_for_block_status` reads at any interleaving), can an attacker cause the *last-write-wins* `gathered_signatures` map to hold a signature that was never actually validated in the final read that `get_block_status` uses to build the returned `Vec<MessageSignature>`? Equality: the signature the aggregator returns for a slot == the one whose `signer_pubkey.verify` passed in that same call. Impact: Critical, a signature slot overwritten so an accept could carry an unverified or stale signature value into the final quorum. Proof idea: local test replaying two Accepted messages with same slot_id, different signature bytes both individually validated separately, then asserting the map holds only a signature that verifies against block_sighash at read time.
