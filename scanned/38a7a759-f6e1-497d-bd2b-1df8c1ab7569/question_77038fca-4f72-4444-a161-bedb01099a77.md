`SignerConfig`'s `signer_id`/`signer_slot_id` fields (from `get_signer_config`, `stacks-signer/src/runloop.rs`) are captured once when a `Signer` is constructed for a reward cycle and never revisited for the lifetime of that `Signer` object, even though `cleanup_stale_signers` keeps a `RegisteredSigner` alive as long as `signer.has_unprocessed_blocks()` returns true — potentially spanning into the *next* reward cycle's prepare phase. If a corrective `.signers` contract re-vote (as in the in-cycle re-vote scenario) changes this signer's `signer_id`/weight for the same `reward_cycle` while the old `Signer` object is still alive processing a lingering unprocessed block, does the signer keep signing with its original (now-superseded) `signer_id`/weight rather than the corrected one? Equality: the `signer_id`/weight used by a live `Signer` instance must equal the *current* consensus value for its `reward_cycle`, for every block it processes, not just at construction. Impact: Critical — a superseded index/weight is used to authenticate a signature that consensus now attributes differently. Proof idea: construct a `Signer` with an initial `signer_id`/weight, mutate the underlying `.signers` weight table for the same cycle, and confirm no code path re-fetches or invalidates the live `Signer`'s cached `signer_id`/weight before it signs a pending block.
