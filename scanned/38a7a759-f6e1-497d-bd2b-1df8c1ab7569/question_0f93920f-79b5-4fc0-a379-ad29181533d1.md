`Signer::handle_state_machine_update` (`stacks-signer/src/v0/signer.rs`) unconditionally calls `self.global_state_evaluator.insert_update(address, update.clone())` for any `signer_public_key` that deserializes, without checking that `address` is a member of `self.signer_weights` / `self.global_state_evaluator.address_weights` for the *current* `self.reward_cycle`. Since `StateMachineUpdate` messages are gossiped over StackerDB (a channel the attacker can push chunks into, per scope, as long as they don't need another signer's key to have it accepted at protocol level for *their own* slot), can a miner who is also registered as a low-weight signer in the reward set repeatedly overwrite `insert_update` with a `StateMachineUpdate` whose `current_miner` field claims a non-canonical tenure, and does `insert_update`'s per-address (not per-weight-verified) overwrite semantics allow that single address's late/duplicate updates to flip `determine_global_state()` if `address_weights` still contains a stale/inflated weight for that address from a prior cycle snapshot? Equality: the weight `determine_global_state` credits to `address` must equal that address's weight in the *current* consensus reward set, not a cached one. Impact: Critical — inflated stale weight lets one low-privilege signer's message swing the group's local capitulation to a non-canonical miner view. Proof idea: build `GlobalStateEvaluator` with an intentionally stale `address_weights` entry, call `insert_update` once from that address with a divergent `current_miner`, and show `determine_global_state()` flips despite only one address's message.
