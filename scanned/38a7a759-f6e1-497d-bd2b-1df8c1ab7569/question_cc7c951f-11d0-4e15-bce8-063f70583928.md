`stacks-signer/src/monitor_signers.rs`'s `SignerMonitor::refresh_state` only refreshes `cycle_state` (`signers_slots`, `signers_weights`, `signers_addresses`) when `Some(reward_cycle) != self.cycle_state.reward_cycle`, i.e. it trusts the node's `get_current_reward_cycle_info()` number alone as the staleness signal. Since this same 'trust the cycle number, not the underlying set' pattern also matches how `Signer`/`RunLoop` cache `SignerEntries`, can a `.signers` contract re-vote *within the same reward cycle* (e.g. a corrective `set-signers` call after an earlier bad calculation, permitted because `update-last-round`/`pox_*_compute_and_update_signers` can be invoked more than once before the cycle boundary is fixed) change `cycle-signer-set` weights while `reward_cycle` stays numerically the same, so a signer keeps voting/aggregating against the old weight table because nothing besides the cycle number triggers `refresh_signer_config`? Equality: the weight table the signer's threshold math uses must equal the *latest* consensus `cycle-signer-set` for that `reward_cycle`, not the first one observed. Impact: Critical — an in-cycle correction of the signer set/weights is silently ignored by already-configured signers, so their acceptance threshold is computed against a superseded reward set. Proof idea: unit test `refresh_signer_config`/`SignerMonitor::refresh_state` called twice with the same `reward_cycle` but different underlying `NakamotoSignerEntry` weights and assert the cached config is never updated.
