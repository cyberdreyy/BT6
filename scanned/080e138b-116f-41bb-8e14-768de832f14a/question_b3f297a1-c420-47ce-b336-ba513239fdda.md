Target: `compute_voting_weight_threshold(total_weight)` as computed independently by each signer versus by `verify_signer_signatures`. Attacker action: submit a `BlockProposal` right after a reward-set update transaction that changes `total_weight` mid-tenure (e.g., PoX-5 waterfall recomputation event applied), so a signer that validated before the update computed threshold from the pre-update `total_weight` and one that validated after uses the post-update value. Preconditions: PoX-5 signer-set recomputation event lands within the tenure the block proposal belongs to. Call sequence: signer snapshot at time T1: `total_weight = W1`, threshold = `compute_voting_weight_threshold(W1)`; signer at T2 (post-update): `total_weight = W2`. Both sign the same `signer_signature_hash`. Equality: `total_weight` (and derived `threshold`) each signer used == the `total_weight` the node computes in `verify_signer_signatures` for that exact block. Impact: Critical - aggregated signatures span two different threshold universes, letting the on-chain check pass with a mixture that would fail under either single consistent `total_weight`. Proof idea: Rust test simulating a `RewardSet` weight mutation between two signer validation calls and asserting `verify_signer_signatures` rejects the mixed-threshold signature set.
