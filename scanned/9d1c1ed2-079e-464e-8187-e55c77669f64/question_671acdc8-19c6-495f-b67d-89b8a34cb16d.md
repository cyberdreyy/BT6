[Same file/scope] Target: SignerDb::block_lookup vs BlockInfo::signer_signature_hash(). Attacker action: none required beyond normal proposal; the flaw is structural. Preconditions: a BlockInfo persisted under schema version N is later read back after schema version N+1 changes the `blocks` table's derived columns (state, valid, signed_group) via json_extract migrations (CREATE_INDEXES_4) that could diverge from the JSON blob if the JSON's field names or shapes changed (e.g. old serialized enum variant string for BlockState). Call sequence: block_lookup selects `block_info` JSON and try_deserialize; if an older serialized `state` string doesn't parse into current BlockState enum, deserialization fails silently and the row is dropped from visibility, but the SQL `state` column (used by other queries like get_last_signed_block) may still say GloballyAccepted. Equality: signer_signature_hash recomputed from the deserialized block == the signer_signature_hash used as the row's primary key. Impact: Critical — inconsistency lets a signer both 'not see' a prior acceptance (via block_lookup) yet the row still satisfies state-based conflict queries, or vice versa, causing either a double-sign or a wedge. Proof: Rust test in signerdb.rs seeding a `blocks` row with a JSON blob using a BlockState variant name from an older version and asserting block_lookup and get_last_signed_block agree.
