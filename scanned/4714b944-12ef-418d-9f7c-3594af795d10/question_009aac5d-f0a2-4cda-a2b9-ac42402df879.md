[File: core/primitives/src/action/delegate.rs DelegateAction vs DelegateActionV2 nonce field] DelegateAction.nonce is a bare Nonce (u64), DelegateActionV2.nonce is TransactionNonce (u64 or GasKeyNonce{nonce,nonce_index}). Both feed into get_nep461_hash via SignableMessage. If an attacker constructs a DelegateActionV2 with nonce = TransactionNonce::from_nonce(N) (the plain-nonce variant, no index) intending it to borsh-serialize identically to a DelegateAction with nonce=N, does the differing SignableMessageType tag alone prevent signature reuse, or does TransactionNonce's borsh encoding introduce an extra discriminant byte that could, for some N, produce byte-identical serialized SignableMessage output between the V1 and V2 shapes despite the type-level intent to keep them disjoint, letting a victim's V1-signed delegate action be replayed as a V2 action carrying additional privilege-adjacent fields (max_block_height, receiver_id) unintentionally re-signed? Attacker: relayer holding a victim's SignedDelegateAction(V1). Invariant: authorization exactness / signing-domain disjointness. Proof idea: property test over many (sender_id, receiver_id, actions, nonce, max_block_height, public_key) tuples asserting SignableMessage::new(&v1,..) borsh bytes never equal SignableMessage::new(&VersionedDelegateActionPayload::V2(v2_with_same_fields),..) bytes. Scoped impact: Cryptographic flaws / Unauthorized transaction.
