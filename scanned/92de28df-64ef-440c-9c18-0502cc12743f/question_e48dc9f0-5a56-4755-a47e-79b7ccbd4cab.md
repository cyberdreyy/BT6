Target: block_rejection_signer_addrs table and CREATE_BLOCK_REJECTION_SIGNER_ADDRS_V16 migration (signerdb.rs), which backs the >30% global-rejection tally. Attacker action: attacker's miner re-proposes an identical block (same signer_signature_hash) after the signer restarts, hoping the restart drops the rejection record. Preconditions: pre-restart, the signer locally rejected block H and this address is recorded via a rejection-tracking insert; schema migrates from an older version that used a different PRIMARY KEY layout (DROP_BLOCK_REJECTION_SIGNER_ADDRS then CREATE_BLOCK_REJECTION_SIGNER_ADDRS_V16 with PRIMARY KEY (signer_addr) instead of per-hash). Call sequence: restart -> create_or_migrate applies SCHEMA_16 -> old block_rejection_signer_addrs table is dropped and recreated -> re-proposal of H -> check_proposal path re-evaluates without the old per-hash rejection record since only signer_addr is now the key (so a rejection of a DIFFERENT hash by the same signer_addr overwrites/removes the record for H). Equality: 'this signer already rejected H' known after restart+migration == known before, for every H not yet finalized. Impact: Critical - a rejection recounted as never-having-happened lets the signer be re-solicited and, on a resubmitted or lightly modified BlockProposal for a still-invalid block, sign it (FAIL-CLOSED violation: a rejection must never later count as, or be silently forgotten to become, an accept). Proof idea: insert two rejection rows for the same signer_addr against two different signer_signature_hashes under the pre-V16 schema, run the SCHEMA_16 migration, and assert both hash-specific rejection facts are independently still queryable, not collapsed by the addr-only key.
