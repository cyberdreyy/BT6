In `store_and_process_block_signature` (stacks-signer/src/v0/signer.rs), a peer's `BlockAccepted` for block hash H arrives with a signature recoverable to a public key belonging to a signer address with weight, but this signer never sent a `BlockPreCommit` for H (`self.signer_db.has_committed` is false) so it is rerouted into `handle_block_pre_commit` (per the 'outdated peer' fallback) instead of being tallied directly as a signature -- an attacker gossiping only a single crafted `BlockAccepted` message (not the actual signature over the operating signer's own validated bytes but a spoof of another signer's slot they do NOT control, which is impossible without the key) cannot forge this, BUT can replay a stale genuine `BlockAccepted` for an already-superseded block hash to force `handle_block_pre_commit` re-evaluation, potentially crossing the pre-commit threshold on a block that should be dead. Preconditions: an old but validly-signed `BlockAccepted` from a signer who has since gone offline, replayed by the attacker via StackerDB gossip after the block's freshness window logically should have expired for OTHER purposes but pre-commit weight math doesn't independently re-check staleness the same way. Call sequence: handle_block_response -> handle_block_signature -> block_lookup_by_reward_cycle finds stale H -> has_committed false -> handle_block_pre_commit(H) -> tally weight -> if crosses 70% pre-commit and valid still true, sign. Equality: UNIQUENESS/FAIL-CLOSED - a replayed old acceptance must not be counted as fresh pre-commit weight toward a NEW signature decision if `conflict_still_blocks` for other signed blocks at that height should have voided H. Impact: Critical, replay of a genuine but stale gossip message triggers signing of a block that later conflicts with a fresher signed block. Proof idea: Rust test in stacks-signer/src/v0/tests.rs replaying a captured BlockAccepted message hours after original validity, asserting handle_block_pre_commit's threshold-crossing path still runs conflict_still_blocks/get_signed_conflicts checks before signing, and constructing a case where staleness of the REPLAYED message itself is not checked, only the conflict's staleness is.
