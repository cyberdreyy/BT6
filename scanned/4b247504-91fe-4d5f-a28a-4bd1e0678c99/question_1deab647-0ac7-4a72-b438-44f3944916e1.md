Preconditions: attacker controls one signer's StateMachineUpdate content (per threat model, at most one honest signer's worth) but not its authenticity — it must be validly signed by that one attacker-controlled signer key; still within a single signer's weight, insufficient alone for threshold, but combined with confusion about 'most recent' can bias which state the RESTARTING signer treats as current. Call sequence: restart -> `Signer::new` loads latest chunks -> `insert_state_machine_update` with `received_time=now()` -> `get_signer_state_machine_updates(reward_cycle)` ordered by the re-stamped time -> `capitulate_miner_view` buckets by weight using this ordering to break ties among equal-weight views. Equality: the 'most recent by received_time' StateMachineUpdate selected after restart == the update that was actually most recently authored/sent, not the one that happens to be re-stamped with the largest post-restart timestamp. Impact: High — a restart with re-stamped-loaded-chunk timestamps confuses staleness so the restarting signer can adopt/reject a miner-view differently than it would have pre-crash. Named in-scope: 'a signer acting on a stale reward set/threshold' via wrong tie-break; wedge/liveness on view convergence. Proof: Rust test seeding two StateMachineUpdate chunks with distinct real send times, simulating restart's re-stamping via `insert_state_machine_update(..., &SystemTime::now())`, and asserting `get_signer_state_machine_updates` ordering differs from true send-time ordering, then showing this flips `capitulate_miner_view`'s chosen view.
