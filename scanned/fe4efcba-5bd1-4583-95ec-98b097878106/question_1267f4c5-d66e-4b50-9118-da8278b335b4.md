Target: LockupInformation.lockup_timestamp: Option<Timestamp> defaulting via .unwrap_or(0) inside get_locked_amount, lockup/src/getters.rs. Attacker action: owner obtains a lockup from LockupFactory::create with lockup_timestamp=None and a very small lockup_duration (e.g. 1ns) while transfers are already enabled network-wide at creation time. Preconditions: TransfersEnabled{transfers_timestamp} already in the past relative to creation; lockup_duration=1. Call sequence: lockup_timestamp = max(transfers_timestamp+1, 0) == transfers_timestamp+1, which for an old transfers_timestamp is already <= current block_timestamp at the very next block after creation, so get_locked_amount's `if lockup_timestamp <= block_timestamp` branch triggers on essentially the first callable block. Binding broken: the schedule was supposed to lock tokens for lockup_duration measured from transfers-enablement, but with lockup_duration=1ns the 'locked' period is functionally zero, making get_balance()-get_locked_amount() equal the full lockup_amount almost immediately after contract creation rather than after any meaningful custody period. Scoped impact: Critical, an attacker can create a self-owned lockup that markets itself as time-locked NEAR but is liquid within nanoseconds, letting them extract the full amount essentially at will. Proof idea: near-workspaces test: create lockup with lockup_duration=1, lockup_timestamp=None after transfers are enabled; advance one block; assert get_locked_amount().0 == 0 and transfer(lockup_amount, receiver) succeeds.
