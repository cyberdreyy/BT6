Target: `Signer::should_reevaluate_block` / `should_reevaluate_reject_reason` (v0/signer.rs, referenced in docs/signer-flows.md section 3) governing re-proposal handling for a block already `BlockState::PreCommitted`. Attacker action: propose block B, wait for the signer to reach `PreCommitted` (validated, willing to sign), then re-broadcast the *identical* `BlockProposal` for B in a tight loop before 70% pre-commit is reached network-wide. Preconditions: signer set doesn't yet have 70% pre-commits; attacker miner controls proposal gossip rate. Call sequence: `handle_block_proposal` -> `block_lookup_by_reward_cycle` finds B `PreCommitted` -> `should_reevaluate_block` is documented to route pre-commit-only blocks back through pre-commit evaluation on every re-proposal (deliberately, to prevent shortcutting a signature) -> each re-proposal forces `check_block_against_signer_db_state`/`check_latest_block_in_tenure` to re-run, updating `update_last_activity_time` and consuming CPU/DB cycles but never advancing B past `PreCommitted` if the attacker also never sends the corresponding `BlockPreCommit`/`BlockResponse` messages from a majority. Wedge: the design intends this to be safe (re-evaluation, not signature reuse) but if the repeated re-evaluation itself can flip a *different*, unrelated pending block C's `BlockState` from `Unprocessed` toward `LocallyRejected` via shared `check_block_against_signer_db_state` side effects (e.g., `update_last_activity_time` masking a real inactivity condition for C), C never reaches a terminal state. Impact: High — collateral permanent/temporary liveness loss for block C caused entirely by attacker-controlled reproposal loops on B. Proof idea: Rust test proposing B then C, then flooding re-proposals of B only, asserting C still reaches a terminal `BlockState` within the nominal timeout budget.
