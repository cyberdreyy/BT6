Target: SignerDb::block_lookup and the block_info TEXT column (signerdb.rs). Attacker action: none needed directly - attacker exploits a migration bug; attacker's role is to submit a BlockProposal whose signer_signature_hash collides in string form pre/post migration re-serialization edge cases (e.g. chain_length boundary values). Preconditions: a BlockInfo with an unusual field (e.g. tenure_change_cause=None) stored under schema V17, node restarts and applies SCHEMA_19 (MIGRATE_BLOCKS_DROP_SIGNED_OVER_ADD_APPROVED_TIME) then SCHEMA_20. Call sequence: create_or_migrate -> INSERT OR IGNORE INTO new_blocks ... SELECT ... FROM blocks -> DROP TABLE blocks -> block_lookup recomputes nothing (id is primary key signer_signature_hash, not recomputed) but block.header fields are re-derived from JSON block_info. Equality: signer_signature_hash computed from the round-tripped BlockInfo.block header == the primary-key string stored before migration. Impact: Critical - if any header field used in the hash is mis-copied during the temp_blocks/new_blocks rebuild, block_lookup(H) returns None post-restart even though the block was signed, so the signer treats it as unseen and can resign a genuinely different (equivocating) block at the same height.
