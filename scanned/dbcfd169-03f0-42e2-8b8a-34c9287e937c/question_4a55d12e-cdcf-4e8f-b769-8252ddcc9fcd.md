`NakamotoBlockVote::consensus_deserialize` reads the `rejected` flag via `let rejected_byte: Option<u8> = read_next(fd).ok();` — any read failure or truncated trailing byte is silently treated as `rejected = false` (accept) rather than propagating an error. If a `BlockInfo.vote` is persisted to the `blocks.block_info` JSON, then later re-serialized/copied through a migration path that touches the codec-serialized form (or exported/imported across a restart tool), can truncation of that one byte flip a previously-recorded rejection vote into an accepted vote after restart? Equality: `vote.rejected` decoded after restart == `vote.rejected` as originally recorded. Impact: Critical, a persisted rejection silently becomes an acceptance (FAIL-CLOSED violation). Proof idea: serialize a `NakamotoBlockVote{rejected: true}`, truncate the trailing rejection byte, deserialize, and assert `rejected` incorrectly reads `false`, then trace that this deserialized vote is what a restarted signer would re-broadcast/consult.
