SELECT` copying rows from the old table. Can a signer that collected other signers' `block_signatures` rows before upgrading lose that aggregated-signature record entirely at restart, so post-migration the signer recomputes 'have we reached signing threshold' from zero recorded signatures and re-broadcasts/re-signs a block it previously determined was `GloballyAccepted`, or fails to recognize consensus already reached (an accept miscounted as not-yet-accepted)? Equality: aggregated weight of `block_signatures` rows the signer trusts before restart == aggregated weight it can reconstruct after restart. Impact: High, restart drops accumulated accept evidence risking a duplicate broadcast/sign cycle. Proof idea: Rust test inserting `block_signatures` rows pre-migration, running schema 16 migration, and asserting the new table is empty for that `signer_signature_hash`, then checking that this does not cause the signer to sign a second, different vote at the same height.
