`burn_block_updates_received_times` (schema 16, PK `(signer_addr, burn_block_consensus_hash)`) records when each peer signer's burn-block state-machine update was received, used presumably to compute freshness/staleness of peers' reported views. Can an attacker replay an old, previously-recorded `StateMachineUpdate` for a `burn_block_consensus_hash` right after a victim's restart, so the fresh `received_time` (post-restart wall clock) overwrites the old row and makes a stale burn-view update look current, causing the signer to trust a peer's outdated reward-set/threshold view as if freshly reported and validate a `BlockProposal` against that stale reward set? Equality: the reward-set/threshold view the signer treats as 'current' post-restart == the reward set of the canonical sortition tip at validation time. Impact: High, acting on a stale reward set/threshold after restart. Proof idea: seed an old `StateMachineUpdate` row, restart, replay the identical message from the attacker's gossip channel, and assert `received_time` is refreshed without the underlying data being re-validated against the current tip.
