Target: `NakamotoBlockProposal::validate` (postblock_proposal.rs) computing `BlockValidateOk.signer_signature_hash` from a reconstructed `block.header.signer_signature_hash()` vs `Signer::create_block_acceptance` (v0/signer.rs) signing `block_info.block.header.signer_signature_hash()`. Attacker action: submit a `BlockProposal` whose non-header-hashed fields (e.g. `txs` ordering, a tx that gets dropped/replaced) diverge between the miner's broadcast copy and what the node reconstructs, while `tx_merkle_root` still validates. Preconditions: current reward cycle, signer holds an `Unprocessed` `BlockInfo` for the proposal. Call sequence: `handle_block_proposal` -> `submit_block_for_validation` -> node `validate` -> `BlockValidateOk` keyed by `signer_signature_hash` -> `handle_block_validate_ok` looks up `block_lookup_by_reward_cycle(signer_signature_hash)` and signs the locally stored `block_info.block`, not the node-validated bytes. Equality: the block whose bytes the node actually executed == the block bytes the signer signs under that hash (VALIDITY). Impact: Critical, signer signs a block that was never actually the one the node validated (chain-safety/invalid-block signature). Proof idea: Rust test in stacks-signer driving `handle_block_proposal` then `handle_block_validate_ok` with a `BlockValidateOk` for a hash whose stored `BlockInfo.block` was mutated in signerdb between submission and response; assert the signature target equals the validated block's serialized bytes, not just its hash.
