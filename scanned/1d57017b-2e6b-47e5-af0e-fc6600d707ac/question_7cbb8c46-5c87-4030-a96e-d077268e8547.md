Attacker action: none privileged -- exploit targets any code path that conflates `signer_id` (index into `signer_addr_to_id`/reward-set position) with `signer_slot_id` (StackerDB write slot) when attributing a received `BlockResponse` to a weight in a local tally. Preconditions: a reward set where at least one signer's StackerDB registration slot differs from its reward-set enumeration index (plausible whenever `.signers` list order and StackerDB `num-slots` allocation order diverge). Call sequence: signer receives a `BlockResponse` from `slot_id=k`, looks up the responder's identity/weight using `k` as if it were `signer_id=k` (instead of resolving through `signer_id_to_addr`/`signer_addr_to_id` correctly), attributing the WRONG signer's weight to the vote. Equality: the weight credited for a `BlockResponse` from StackerDB slot `k` == the weight of the reward-set signer whose `signer_addr_to_id` entry is `k`'s corresponding ADDRESS (via `signer_id_to_addr`), not slot index `k` used directly as `signer_id`. Impact: Critical -- one signer's vote is credited with a different (possibly larger) weight than it actually holds, letting an attacker-influenced acceptance/rejection tally cross the threshold incorrectly. Proof idea: unit test constructing a reward set where slot order != signer_id order, feeding a `BlockResponse` from a known slot, and asserting the tally must use the address-resolved weight, not the raw slot/id conflated value.
