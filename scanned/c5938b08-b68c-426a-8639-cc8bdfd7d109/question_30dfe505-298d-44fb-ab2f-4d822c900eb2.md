Target: `NakamotoBlock::signer_signature_hash()` domain and its use as the sole aggregation key across `SignerCoordinator`/`StackerDBListener`. Attacker action: propose a block for reward cycle N whose `signer_signature_hash` (computed only over consensus-relevant header fields per current code) collides with a previously finalized block's hash from reward cycle N-1 due to reuse of `parent_block_id`/`consensus_hash` bytes across a cycle boundary the hash function does not fully bind. Preconditions: cross-cycle boundary just crossed, old block's cached weight/status object still resident in listener's map (not purged). Call sequence: new proposal reuses old hash entry, listener returns already-satisfied `total_weight_approved` from the stale cycle-N-1 entry to the coordinator for the cycle-N block. Equality: a signature's binding to (chain, cycle, tenure, block) must equal the actual cycle/tenure it was produced under; a hash collision or key reuse across cycles must not transfer weight. Impact: Critical - signature valid across cycle boundaries improperly finalizes a new-cycle block. Proof idea: test that forces two BlockProposal objects mapping to the same status-map key across cycle boundary and asserts stale weight is not returned for the new proposal.
