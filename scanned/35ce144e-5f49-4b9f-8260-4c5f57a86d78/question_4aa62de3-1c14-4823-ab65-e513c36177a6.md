Target: `SignerDb::set_block_broadcasted` / the `broadcasted` column preserved across `insert_block` calls per `test_and_set_block_broadcasted`. Attacker action: cause a signer to sign and broadcast a block, then restart the signer immediately after `set_block_broadcasted` but before the node's own block-acceptance event is processed; then resend the identical `BlockProposal` (same `signer_signature_hash`) after restart. Preconditions: prior to restart, `broadcasted` was set (e.g., to a nonce/timestamp) but `state` was still `BlockState::Unprocessed` (as shown by the test, broadcasting does not itself change `state`). Call sequence: restart -> `insert_block` is called again for the resent proposal -> `let broadcasted = self.get_block_broadcasted(hash)?;` correctly re-preserves the broadcasted marker, but the freshly computed `state`/`valid`/`vote` fields from the new `BlockInfo` fully overwrite the previous ones -- if the new `BlockInfo` was built from a validation pass that has not yet incorporated the earlier vote (e.g., a race where the mempool/validation result differs slightly, such as a different `tx_merkle_root` due to mempool reordering that the node fully revalidates), the signer could end up voting differently for what is nominally 'the same' hash while `broadcasted` (implying it already signed) is preserved. Equality: signed-versus-validated - the block a signature authenticates (tracked via `broadcasted`) must equal the block that was actually validated on this pass; preserving `broadcasted` while replacing `valid`/`vote` breaks that pairing if the two do not refer to the same validation outcome. Impact: Critical - a signer could end up with a persisted 'already broadcasted' marker attached to a differing vote/validity outcome after restart, confusing later logic that assumes broadcasted implies a specific vote. Proof idea: Extend `test_and_set_block_broadcasted` to call `insert_block` a second time with a `BlockInfo` differing only in `valid`/`vote` for the same hash after a simulated restart, and assert `broadcasted` from the first insert is preserved alongside the second insert's `valid`/`vote`, showing the two are no longer coupled to a single validation pass.
