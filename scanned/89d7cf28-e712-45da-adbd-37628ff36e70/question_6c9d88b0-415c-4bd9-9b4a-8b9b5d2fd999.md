ReceiptManager::append_action_delete_key (receipt_manager.rs) appends a DeleteKeyAction with an attacker-chosen public_key to a receipt targeting receiver_id chosen by the calling contract. Confirm actions.rs's action_delete_key execution requires receipt.predecessor_id() == receiver_id (i.e., only self-managed keys can be deleted) exactly as it does for a transaction-originated DeleteKey, and that there is no code path where a contract can queue a receipt whose receiver_id is a victim account V and have V's OWN access key deleted by a receipt whose predecessor_id resolves (via any RuntimeExt misthreading) to the attacker's account rather than V's, which would let an attacker permanently revoke a key V never asked to remove.
