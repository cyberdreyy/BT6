Target: `Signer::compute_signature_total_weight` (stacks-signer/src/v0/signer.rs) as a denominator vs. `RewardSet::total_signing_weight` used in `NakamotoBlockHeader::compute_voting_weight_threshold`. Attacker action: none beyond normal participation; exploit a signer whose `signer_weights` HashMap was built from a `SignerEntries::parse` call that silently dropped or deduplicated an entry (e.g., two distinct StacksAddresses colliding under a lossy address-derivation edge case) so `compute_signature_total_weight` sums to a value less than the on-chain `total_signing_weight()`. Preconditions: any discrepancy between the address set libsigner reconstructs and the address set the node's `RewardSet` carries. Call sequence: victim signer computes its own threshold as `ceil(total_own * ratio)` internally for UI/heuristics while node computes threshold from `total_signing_weight`; if signer-side total is lower, the signer's internal accept/idle-timeout heuristics fire early relative to actual on-chain threshold. Equality broken: `compute_signature_total_weight()` (local) == `reward_set.total_signing_weight()` (consensus) for the same reward cycle. Impact: Critical - a signer can locally conclude "consensus reached" (and stop tracking/using its equivocation guard for later heights) before the on-chain threshold is actually met, opening a path to sign a conflicting block at the same height believing the prior one is already final. Proof idea: Rust test constructing a `RewardSet` and an independently-parsed `signer_weights` map that omit one entry, asserting `compute_signature_total_weight` != `total_signing_weight` and that the local "reached consensus" threshold fires at a smaller aggregate than `compute_voting_weight_threshold` requires.
