Target: `SignerConfig::signer_slot_ids`/`signer_id_to_addr` construction in `SignerRunLoop::get_signer_config` (stacks-signer/src/runloop.rs). Attacker action: exploit a race where a signer's `stacks_client.get_parsed_signer_entries`/`get_signer_slots` call returns a signer list from a slightly earlier `.signers` contract read than the one used to compute `signer_slot_ids.get(current_addr)`, so the victim signer's own `signer_slot_id`/`signer_id` is bound to an index that a differently-timed peer no longer agrees with. Preconditions: `.signers` contract updated mid-query window at prepare-phase boundary; no atomic combined read of slots+entries. Call sequence: victim signer signs using `signer_id` X but writes to StackerDB slot Y (from the stale slot mapping); the node's `StackerDBListener::signer_entries` (built from the current reward set) attributes the write to whichever signer key actually owns slot Y in the up-to-date mapping. Equality broken: the `(signer_id, signer_slot_id)` pair a signer believes it holds == the pair consensus (StackerDBListener/get_signers_weights) derives for the same cycle. Impact: Critical - a vote can be attributed to the wrong signer's weight, letting an aggregate tally reach threshold using miscredited weight. Proof idea: Rust test in stacks-signer feeding `get_signer_config` two out-of-sync `(slot_ids, entries)` snapshots and asserting the resulting `SignerConfigMode::Normal{signer_slot_id, signer_id}` is inconsistent with a reference mapping built from the later snapshot alone.
