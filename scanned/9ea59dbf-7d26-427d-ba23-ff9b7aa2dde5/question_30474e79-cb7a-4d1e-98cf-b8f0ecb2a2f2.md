Target: `Signer::is_valid_signer` gate in `handle_block_rejection` (stacks-signer/src/v0/signer.rs) versus the `signer_weights` map it was constructed from. Attacker action: gossip a `BlockRejection` (`RejectReason` arbitrary) signed by a still-valid key from a signer that is registered for cycle N but whose `weight` field the victim signer's `signer_weights` map has memoized from cycle N-1 (weights differ across cycles because PoX-5 re-apportions weight by stake, per `pox_5_make_signer_set`). Preconditions: same signing key retained across two adjacent reward cycles with a materially different weight allocation. Call sequence: `is_valid_signer` passes (key format/address matches), `compute_reject_code_signing_weight`/`compute_signature_signing_weight` then add the *old* weight instead of the cycle-N weight, e.g. via `self.signer_weights.get(stacker_address).unwrap_or(&0)`. Equality broken: the weight credited for a signature == the weight `reward_set.signers()`/`total_signing_weight()` assigns that key for the cycle the block under vote belongs to. Impact: Critical - the aggregate accept/reject weight computed locally diverges from the weight the node would compute via `verify_signer_signatures`, letting a block reach the local "consensus reached" state without reaching the on-chain threshold (or vice versa). Proof idea: Rust test building `signer_weights` from a cycle-(N-1) `RewardSet` and validating a rejection/acceptance for a cycle-N block, asserting the tallied weight differs from a fresh cycle-N weight table for the same key.
