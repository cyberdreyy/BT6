Target: `StackerDBListener::signer_entries` (`HashMap<u32, NakamotoSignerEntry>`, stacks-node/src/nakamoto_node/stackerdb_listener.rs) keyed by enumerated `slot_id` from `reward_set_signers.iter().cloned().enumerate()`. Attacker action: gossip a `SignerMessageV0` chunk into a StackerDB `slot_id` that was legitimately assigned to signer A in the current reward set, timed right after a burnchain reorg re-derives the reward set with a *different* signer at that same numeric `slot_id` (rare but possible reorg across a prepare-phase boundary where reward-set computation input changes). Preconditions: a reorg changes the reward set's signer ordering/membership without changing the total slot count. Call sequence: `StackerDBListener::run` resolves `modified_slots` to `signer_entries.get(&slot_id)` to recover the *expected* pubkey, then verifies the signature against that pubkey; if the reorg has updated `signer_entries` (rebuilt for the new fork) but any queued/duplicated message from the old fork's slot layout is replayed, the response can be validated against the wrong signer identity for weight-crediting purposes. Equality broken: the signer identity/weight credited for a `slot_id`'s message == the identity consensus's current-fork reward set assigns to that `slot_id`. Impact: Critical - weight can be credited to signer B's slot while actually authenticated by signer A's key (or rejected as invalid when it's actually a stale, still-cryptographically-valid but pre-reorg attribution), corrupting the tally used for finalization. Proof idea: Rust test building two `RewardSet`s with the same slot count but a differently-ordered signer list, and replaying a stored chunk from set 1 into a `StackerDBListener` initialized with set 2, asserting the recovered pubkey and the map's expected pubkey diverge but the message is still processed.
