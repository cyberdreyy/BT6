Target: `NakamotoBlockProposal::validate`'s network/chain check (`ValidateRejectCode::NetworkChainMismatch`) comparing `self.chain_id`/`mainnet` against `chainstate.chain_id`/`chainstate.mainnet`. Attacker action: submit a proposal with `chain_id` matching testnet while the block content (signatures, tenure data) is otherwise valid on mainnet's reward set, attempting to get a validation result whose `signer_signature_hash` is reused across chain contexts. Preconditions: signer running in a mixed testnet/mainnet config or a signer that participates in both networks with shared keys (explicitly excluded if it needs privileged config, but the check itself is the target). Call sequence: `validate()` rejects immediately on mismatch, but the question is whether the signer's local chainstate rules ever bind a signature to `chain_id` independent of this node-side check. Equality: LIVENESS/DOMAIN - each signature bound to one (chain, cycle, tenure, block, message-type); the signer must independently verify `chain_id` binding, not rely solely on the node's `NetworkChainMismatch` reject. Impact: Critical if the signer's `v0/signer.rs` message construction fails to embed chain_id in the signed payload leading to cross-chain signature reuse. Proof idea: `stacks-signer` test asserting `signer_signature_hash` / signed message includes chain_id-derived data and that a reject on `NetworkChainMismatch` is never converted into a signable state.
