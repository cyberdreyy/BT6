Target: `BlockValidateResponse::signer_signature_hash` used by `v0/signer.rs` to key `signerdb.rs` state after a validation round trip. Attacker action: submit two distinct `NakamotoBlockProposal`s (`block_A`, `block_B`) at the same `chain_length`/tenure whose bodies differ only in a field that is not part of `signer_signature_hash()` computation. Preconditions: fresh tenure, signer state has not yet recorded either hash in `signerdb.rs`. Call sequence: `validate()` runs to completion for `block_A`, returns `BlockValidateOk{signer_signature_hash: h}`; miner then submits `block_B` with the identical `h` but a different `parent_block_id` or different `chain_id`-mismatched body reused via a stale hex-encoded block payload. Equality: VALIDITY - the block a signer signs (`h`) must equal the exact block bytes the node validated, not merely a hash collision surface. Impact: Critical - a signature bound to `h` could be replayed as if it authenticated `block_B`. Proof idea: `stacks-signer` unit test constructing two `NakamotoBlock`s with identical `signer_signature_hash()` inputs but different `txs`, feeding both through the local validation-result handler, and asserting the signer never accepts the second without a fresh matching validation for the exact bytes.
