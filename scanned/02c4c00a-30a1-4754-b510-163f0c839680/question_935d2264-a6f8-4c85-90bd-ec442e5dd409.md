Attacker action: none directly needed beyond normal proposal traffic during the window; the flaw is exercised purely by the restart/downgrade, but the attacker's in-flight `BlockProposal` at the time of downgrade determines whether the `Ordering::Greater` error path (`sql_tx.rollback()`) discards a just-signed decision. Preconditions: DB at `SCHEMA_VERSION = 20`; binary downgraded to `SCHEMA_VERSION = 19`. Call sequence: restart -> `create_or_migrate` computes `current_db_version.cmp(&Self::SCHEMA_VERSION)` as `Greater` -> returns `Err` and rolls back the *migration* transaction (which only ever contained schema DDL, not the attacker's already-committed `insert_block`/`mark_locally_accepted` row from a prior autocommit) -> signer process fails to start, or if the caller ignores the error and retries with an older binary that never reads V20-only columns like `superseded_tenures`, it silently loses that guard. Equality: whether the process starts or not, the equivocation-relevant guard state (superseded tenures / rejections) available under version 19 code paths must not silently drop what was recorded under version 20 code paths. Impact: High — a downgrade wedges the signer's restart, or (if operators bypass the hard stop) removes a guard, causing a downgraded signer to reprocess a tenure believing it hasn't yet acted. Proof idea: Rust test bumping schema version artificially past `SchemaVersion::V20` then reopening with the real `SCHEMA_VERSION`, asserting the hard `Ordering::Greater` error fires (LIVENESS wedge is explicit, not silent data loss).
