### Title
Dust queue deposit after the prefunding cutoff permanently reverts `stopEpochWithDuration`, freezing the credit vault - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
Analogous to GHSA-23vw-mhv5-grv5 (an edge-case input reaching an unguarded code path and crashing the service), an unprivileged KYC'd lender can deposit a dust amount into the prefunded `IdleCDOEpochQueue` in the final block before `prefundedDepositWindow` cutoff. That dust sits in `epochPendingDeposits[nextEpoch]` and can never be prefunded afterward, yet `prefundedDepositsToProcess()` reverts whenever raw pending deposits remain for the epoch being settled. Since `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration()` calls it unconditionally inside `stopEpochWithDuration`, every subsequent stop attempt reverts, freezing the epoch state machine and all user funds.

### Finding Description
In `IdleCDOEpochQueue.requestDeposit`, deposits made while the epoch runs are booked into `epochPendingDeposits[epochNumber + 1]` (line 126). For an AA queue on the prefunded variant, deposits are blocked only when the epoch is already prefunded or when `block.timestamp + prefundedDepositWindow >= epochEndDate` (lines 111-117). `processDepositsToBorrower` — the only function that clears `epochPendingDeposits` into `epochPrefundedDeposits` — enforces the same cutoff (line 164), so it cannot be called once the window is reached.

In `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration` (lines 72-89), `prefundedDepositsToProcess()` is invoked on every `stopEpochWithDuration`. That view reverts with `NotAllowed` if `epochPendingDeposits[_epoch] != 0` (lines 277-282), where `_epoch` resolves to the epoch id that queue deposits targeted. The revert propagates and undoes the entire stop, including default handling.

Attack sequence (prefunded deployment, running epoch):
1. Attacker (any KYC-passed wallet) waits until the last block where `block.timestamp + prefundedDepositWindow < epochEndDate` still holds and calls `queue.requestDeposit(1)` (or `1 wei` of underlying). This is a griefing-cost dust deposit.
2. The cutoff now passes. `processDepositsToBorrower` permanently reverts for that epoch; `epochPendingDeposits[nextEpoch] == 1` forever.
3. Manager calls `cdoEpoch.stopEpochWithDuration(...)` after `epochEndDate` → `_afterStopEpochWithDuration` → `prefundedDepositsToProcess` → `NotAllowed` revert. The epoch can never be stopped; `startEpoch`, `processWithdrawRequests`, and all claims are blocked behind it.
4. The attacker can repeat the dust deposit every epoch, so even after owner recovery the same griefing is available again.

Existing guards do not stop it: `checkPrefunding` only validates the amount against guarded limits and emergency flags; the attacker is a legitimate `isWalletAllowed` user; the deposit-window check in `requestDeposit` and the identical check in `processDepositsToBorrower` share the same boundary, leaving no residual window for the manager to react after the last permissible deposit block.

### Impact Explanation
Temporary freezing of the entire pool TVL plus all queued withdrawal claims. `stopEpoch` (direct selector) is also bricked because `_beforeStopEpoch` reverts on the direct selector whenever `epochQueue != 0` (line 43), so the only recovery is the owner calling `setEpochQueue(0)` — which the code itself warns against (`"do not change the queue after deposits were already prefunded"`, line 22-23) since prefunded deposits for that epoch would then never be settled into `epochPrice`, permanently stranding those depositors' tranche minting. Cost to the attacker is 1 unit of underlying per epoch frozen.

### Likelihood Explanation
Requirements: a prefunded-variant deployment with `epochQueue` set and a nonzero `prefundedDepositWindow` (the documented configuration), and one KYC'd attacker wallet. The attack needs no privileged collusion and no market conditions; it is a pure transaction-ordering grief that the attacker can execute passively in the last valid block each epoch. If `prefundedDepositWindow == 0` the issue does not trigger, so severity is configuration-dependent.

### Recommendation
Allow the stop flow to tolerate leftover pending deposits instead of reverting — e.g., in `_afterStopEpochWithDuration`, treat `epochPendingDeposits[_epoch] != 0` as "not prefunded" (return 0 / skip settlement) rather than reverting, or add a queue function callable by owner/manager that refunds or re-books un-prefunded pending deposits to the next epoch. Alternatively, decouple the deposit cutoff from the prefunding cutoff so `processDepositsToBorrower` remains callable for some grace period after `requestDeposit` closes.

### Proof of Concept
Foundry fork PoC (prefunded deployment, AA queue enabled, `prefundedDepositWindow = 5 days`, `epochDuration = 30 days`):

```solidity
// setup: prefunded CDO + AA epochQueue wired via setEpochQueue, epoch running
uint256 lastAllowed = cdoEpoch.epochEndDate() - queue.prefundedDepositWindow() - 1;
vm.warp(lastAllowed);

// 1) attacker (KYC'd EOA) dust-deposits into the queue for nextEpoch
deal(address(underlying), attacker, 1);
vm.startPrank(attacker);
underlying.approve(address(queue), 1);
queue.requestDeposit(1); // epochPendingDeposits[nextEpoch] = 1
vm.stopPrank();

// 2) cutoff passes: manager can no longer prefund the dust
vm.warp(lastAllowed + 2);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
queue.processDepositsToBorrower();

// 3) epoch ends; every stopEpochWithDuration reverts -> funds frozen
vm.warp(cdoEpoch.epochEndDate() + 1);
// borrower repays interest as usual (honest borrower)
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpochWithDuration(newApr, 0, duration, 0);

assertTrue(cdoEpoch.isEpochRunning()); // stuck running, withdrawals unclaimable
```

Note: exact `epochNumber` bump semantics inside `IdleCreditVault` were not fully traced (30 matches, file not fully read); the PoC assumes `nextEpoch = epochNumber + 1` during a running epoch equals the `_prefundedEpochToProcess` result at that epoch's stop, which matches the queue's own comments and `processDepositsToBorrower` indexing.
