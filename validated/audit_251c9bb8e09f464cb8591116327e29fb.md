### Title
Instant-withdraw path in `requestWithdraw` omits the upfront management fee, letting withdrawers exit fee-free (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In `IdleCDOEpochVariant.requestWithdraw`, the normal withdrawal branch deducts `_totalWithdrawFees(principal, interest)` — which includes an upfront management fee charged because a withdraw receipt leaves live NAV but still waits outside it (remaining buffer + next epoch, per `_withdrawRequestManagementFeeDuration`). The instant-withdraw branch (taken when `lastEpochApr > currentApr + instantWithdrawAprDelta`) returns early with the gross `_underlyings` amount and never applies that fee. The instant receipt also leaves live NAV immediately — strategy tokens are burned in `IdleCreditVault.requestInstantWithdraw` and `lastNAV` is decreased via `_withdrawOps` — yet it still sits unfunded until `getInstantWithdrawFunds` runs after `instantWithdrawDeadline` inside the next running epoch. The result is a fee bypass directly analogous to the XYK sizing bug: an exit path is priced without the fee term, so the protocol (feeReceiver/owner) under-collects management fees on principal that is economically still unexited.

### Finding Description
Normal path (IdleCDOEpochVariant.sol:772-790): `_underlyings = principal + interest - totalFees`, and `totalFees` includes `_calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration())`, justified at line 786-787 by "The receipt is fixed now and leaves live NAV. Charge management fees upfront for the time it waits outside live NAV."

Instant path (IdleCDOEpochVariant.sol:761-769): `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` followed by `_withdrawOps(_amount, _underlyings, _tranche)` returns the full tranche-price value with no fee subtraction and no `pendingWithdrawFees` accrual.

The instant receipt burns CDO strategy tokens (`IdleCreditVault.requestInstantWithdraw`, IdleCreditVault.sol:356-375) so it no longer accrues management fee through `_accrueManagementFee` on live NAV — exactly the situation the normal-path upfront fee compensates for. Funding is delayed until after `instantWithdrawDeadline` (IdleCDOEpochVariant.sol:558-574) and the claim may be later still; a request made at the start of the buffer can sit outside live NAV for `bufferPeriod + instantWithdrawDelay` or longer. No fee is charged for any of that time.

### Impact Explanation
feeReceiver/owner permanently lose `principal * managementFee * waitDuration / FULL_ALLOC / 365 days` on every instant withdrawal whenever `managementFee > 0`. The loss is unbounded in aggregate: any KYC-passed tranche holder can repeatedly cycle instant withdrawals each time the APR drops. Because NAV is reduced by the full amount and `pendingWithdrawFees` is not incremented, the skipped fee is never recovered — it is a direct leak of expected fee revenue to the withdrawer, matching the "takers fill passive orders without paying the swap fee" pattern.

### Likelihood Explanation
Requires only an unprivileged, KYC-passed tranche holder and a configuration with `managementFee > 0` and instant withdrawals enabled (`!disableInstantWithdraw && !isProgrammableBorrower`). The trigger — manager setting a lower APR at `stopEpoch`, making `lastEpochApr > unscaledApr + instantWithdrawAprDelta` — is a normal, honest operational action, not attacker-controlled or exploitable-only state. Note the counter-argument: the omitted duration for an instant receipt is shorter (up to `instantWithdrawDelay` into the next epoch rather than a full epoch), so the correct charge is a smaller amount than `_withdrawRequestManagementFeeDuration` — but the current code charges exactly zero, which is inconsistent with the stated rationale at line 786.

### Recommendation
Apply an upfront management fee on the instant path before `requestInstantWithdraw`/`_withdrawOps`, sized to the actual expected time outside live NAV, e.g. `_calculateManagementFee(_underlyings, remaining buffer + instantWithdrawDelay)` (or the configured wait period), and add it to `pendingWithdrawFees` so it is distributed via `_transferFeeUnderlyings` at the next `stopEpoch` alongside normal withdraw fees.

### Proof of Concept
Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantWithdrawSkipsManagementFee() external {
    _setManagementFee(1_000); // 1%/yr management fee, feeReceiver set
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    idleCDO.depositBB(amount);

    _startEpochAndCheckPrices(0);
    // stop epoch with APR drop so instant withdrawals are enabled
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Same principal, instant vs normal path
    uint256 instantRequested = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));

    // pendingWithdrawFees is NOT increased for the instant request
    assertEq(cdoEpoch.pendingWithdrawFees(), 0, "instant request bypassed withdraw fees");

    // A normal request of identical size books the upfront management fee
    uint256 normalRequested = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));
    assertGt(cdoEpoch.pendingWithdrawFees(), 0, "normal request booked fees");
    assertEq(instantRequested, normalRequested + cdoEpoch.pendingWithdrawFees(),
        "instant withdrawer received the fee that should go to feeReceiver");
}
```

The instant request pays `principal` in full while an equal-sized normal request pays `principal + interest - _totalWithdrawFees(...)`; the delta accrues to the withdrawer instead of `feeReceiver`/`owner`.
