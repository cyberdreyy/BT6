This confirms the vulnerability. `MessageId` is fully attacker-controlled (client-supplied, embedded in the signed `MessageBody`, and validated only for length/null-suffix in `Message.Validate()` [1](#0-0) ), with no uniqueness check against `Sender`/signer. In `HandleLegacyUserMessage`, the handler unconditionally writes `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` while holding the mutex, without checking for or rejecting a pre-existing entry [2](#0-1) . Later, `handleWebAPITriggerMessage` looks up and deletes by `msg.Body.MessageId` alone and invokes whatever callback is currently stored, again with no sender/requester binding check [3](#0-2) .

### Title
Cross-user callback hijack via attacker-chosen `MessageId` collision in `savedCallbacks` map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores each user's response callback keyed solely by the client-supplied `Body.MessageId`, with no check for an existing entry and no binding to the requester's identity/signer. An unprivileged attacker who submits a validly self-signed message with a `MessageId` that collides with a victim's in-flight request overwrites the victim's saved callback, so the DON's response to the victim's request is delivered to the attacker's callback instead.

### Finding Description
The gateway's legacy HTTP user endpoint accepts a self-signed `api.Message` and routes it to `HandleLegacyUserMessage`. `Message.Validate()` only checks length, null-suffix, and signature well-formedness of `Body.MessageId` [1](#0-0) ; there is no requirement that the ID be unique, random, or bound to the sender. The signature only proves the sender authored *that specific message*, it does not prevent choosing an ID that a different (victim) sender is concurrently using.

Inside `HandleLegacyUserMessage`, after validation, the handler does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [2](#0-1) 
This blindly overwrites any existing map entry for that key — there is no existence check, no compare-and-swap, and no association of the stored callback with `msg.Body.Sender`.

When a DON node later responds with the same `MessageId` (which is echoed back through the request/response cycle, e.g. via `ValidatedRequestFromMessage`/`ValidatedMessageFromResp` which propagate `MessageId` as the JSON-RPC `ID`), `handleWebAPITriggerMessage` does:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    ...
    return savedCb.SendResponse(...)
}
``` [3](#0-2) 
This looks up purely by `MessageId` and delivers to whatever `Callback` currently occupies that slot — there is no cross-check that the responding message's payload/sender corresponds to the original requester who set up the callback. If the attacker's `HandleLegacyUserMessage` call for the same `MessageId` executes after the victim's (overwriting the map entry) but before the DON's response arrives, the victim's original request is still forwarded to DON nodes under the victim's request context, but the eventual node response keyed by that shared `MessageId` will be delivered to the attacker's callback instead of the victim's.

None of the existing checks (signature verification, timestamp freshness, method whitelist, rate limiting) validate MessageId uniqueness or ownership, so this path is fully reachable by any unprivileged, unauthenticated caller of the gateway's HTTP user endpoint holding any ECDSA keypair — no DON membership or special role is required.

### Impact Explanation
This is a cross-user response/callback confusion vulnerability: an attacker can receive another user's capability-execution result (e.g., an HTTP trigger/target response payload intended for the victim) by racing a colliding `MessageId`. Depending on what data the web API trigger/target payload carries (which may include sensitive execution results or data derived from the victim's request), this constitutes unauthorized disclosure of another user's request/response and denial of the legitimate response to the victim (the victim's callback is dropped/never called since the map entry was stolen). This matches the "cross-user response confusion" / "request impersonation" impact classes called out in scope.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs any ECDSA keypair to self-sign a message (no DON membership, no privileged role, no allowlist entry beyond what any user needs to reach the endpoint at all). The attacker needs to guess or observe a victim's in-flight `MessageId` (predictable IDs, e.g., counters or client-reused constants, make this trivial; even for random IDs, the map has no uniqueness enforcement so any collision — accidental or crafted — succeeds), and win a race window between the victim's `HandleLegacyUserMessage` call and the DON's response. This is realistic if the gateway/client convention allows attacker-visible or predictable IDs, or if the same client reuses IDs. The race window is bounded by node processing time (could be sub-second to seconds), which is a modest but real constraint on reliability, not exploitability.

### Recommendation
- Bind saved callbacks to the requester's identity: key `savedCallbacks` by a composite of `MessageId` and `Body.Sender` (the ECDSA-recovered signer address), or store the expected sender in `savedCallback` and verify it matches the responding message's sender/context before overwriting or delivering a callback.
- In `HandleLegacyUserMessage`, check `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { reject/return error }` before insertion, rather than silently overwriting.
- Consider generating `MessageId` server-side (or requiring cryptographically random, sufficiently long IDs) instead of trusting client-supplied values for correlation.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two `api.Message`s with the same `Body.MessageId` but signed by two different ECDSA keys (victim key A, attacker key B), with distinct mock `handlers.Callback` implementations (`victimCallback`, `attackerCallback`) recording whichever `UserCallbackPayload` they receive.
2. Call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)` then `h.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` sequentially (simulating the attacker's request landing after the victim's, before the DON responds) — assert `h.savedCallbacks[messageId].Callback == attackerCallback` (overwrite confirmed).
3. Simulate the DON's response by constructing a `jsonrpc.Response` with `ID == messageId` and calling `h.HandleNodeMessage` (routing to `handleWebAPITriggerMessage`) as if the victim's original node response arrived.
4. Assert that `attackerCallback.SendResponse` was invoked with the victim's response payload, and `victimCallback.SendResponse` was never called — demonstrating cross-user callback hijack.
