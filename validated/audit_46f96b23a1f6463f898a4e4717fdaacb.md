### Title
`VestingSchedule::assert_valid` is dead code — invalid vesting schedules (start ≥ end) can permanently block `terminate_vesting` - ([File: lockup/src/getters.rs], [File: lockup/src/foundation.rs], [File: lockup/src/lib.rs])

### Summary
`VestingSchedule::assert_valid()` is defined but is **never called anywhere in the contract logic**, for either the explicit `VestingScheduleOrHash::VestingSchedule` variant or the `VestingScheduleOrHash::VestingHash` variant, at `LockupContract::new`. Consequently a lockup creator can commit to a `VestingHash` (or even an explicit `VestingSchedule`) whose real schedule has `start_timestamp >= end_timestamp`, and later, when the Foundation calls `terminate_vesting` to reveal and use that schedule, `get_unvested_amount` performs an unchecked `u64` subtraction `end_timestamp.0 - start_timestamp.0` that underflows and panics (overflow-checks are enabled in release), aborting the transaction and permanently preventing termination.

### Finding Description
The claimed binding is: `VestingSchedule::assert_valid()` (`start<=cliff<=end`, `start<end`) is enforced ⟺ every `VestingSchedule` value that ever reaches `get_unvested_amount`/`get_locked_vested_amount` satisfies that invariant. Tracing the code shows this binding never holds, for any code path:

- `VestingSchedule::assert_valid` is defined in `lockup/src/types.rs:110-125` [2](#0-1)  but a repo-wide search for call sites (`.assert_valid()`) finds it invoked only in `staking-pool/src/lib.rs` and `staking-pool-factory/src/lib.rs` — **never** in the lockup contract or lockup-factory. It is genuinely dead code.
- `LockupContract::new` accepts `Option<VestingScheduleOrHash>` and stores it directly into `VestingInformation::VestingHash(hash)` or `VestingInformation::VestingSchedule(vs)` with no call to `assert_valid()` on either branch: [3](#0-2) .
- `LockupFactory::create` forwards whatever `vesting_schedule: Option<VestingScheduleOrHash>` the caller supplies straight into the `new` call of the deployed lockup contract, and automatically attaches the real `foundation_account_id` as the party entitled to terminate, without any validation of the schedule's content: [4](#0-3) .
- Later, `terminate_vesting` (Foundation-only) reveals the hidden schedule via `assert_vesting`, which only checks the hash matches — it does not call `assert_valid()`: [5](#0-4) , then immediately calls `get_unvested_amount(vesting_schedule)`: [6](#0-5) .
- `get_unvested_amount` computes, in the branch `cliff_timestamp <= block_timestamp < end_timestamp`: `total_time = U256::from(vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0)`. This subtraction happens in native `u64` arithmetic **before** the `U256::from` conversion: [7](#0-6) . If `start_timestamp > end_timestamp`, this underflows.
- `lockup/Cargo.toml` sets `overflow-checks = true` in the `[profile.release]` section, so this underflow panics/aborts the transaction rather than wrapping: [1](#0-0) .

Because `terminate_vesting` is the sole path by which the Foundation can lock/forfeit an employee's unvested balance, a lockup creator who deliberately commits an invalid `VestingHash` (e.g. `cliff=0, end=100, start=1000`) can guarantee that any future `terminate_vesting` call — issued once the block timestamp falls in `[cliff, end)` — panics and reverts, permanently preventing the Foundation from ever terminating the vesting and reclaiming unvested tokens. No existing guard (`assert_called_by_foundation`, `assert_eq!` hash check in `assert_vesting`, `saturating_sub`, `is_promise_success`) mitigates this, since none of them validate the numeric relationship between `start_timestamp` and `end_timestamp`.

### Impact Explanation
This breaks a Critical-tier invariant: "locked or unvested tokens released early" / "funds permanently frozen [from the Foundation's perspective, permanently un-terminable]". Concretely, an employee/lockup-owner who is later terminated can, by having pre-committed a malformed hidden vesting schedule at lockup creation time, make the Foundation's `terminate_vesting` call permanently revert. The unvested tokens — which should have been forfeited back to the Foundation — remain in the lockup contract, and since `vesting_information` never transitions out of `VestingInformation::VestingHash`, the owner continues normal lockup operation (subject to `get_locked_amount`'s existing lockup/release schedule) while the tokens intended to be clawed back are never removed. This is repeatable by any lockup creator against the same Foundation account, one lockup per malicious schedule.

### Likelihood Explanation
- The attacker needs only to be the creator of their own lockup contract (unprivileged, permitted by the ruleset) — this is possible via the public `LockupFactory::create` entry point with a self-chosen `VestingScheduleOrHash::VestingHash`.
- No cooperation from the Foundation is needed to *create* the malformed commitment; it is only needed later, when the Foundation calls `terminate_vesting` in good faith (believing it received a valid schedule/salt from the employee/employer relationship).
- The cost is the standard `MIN_ATTACHED_BALANCE` deposit for lockup creation; there is no other precondition.
- The vulnerability is deterministic and 100% reproducible in a unit test since `assert_valid()` is provably never invoked.

### Recommendation
Call `vesting_schedule.assert_valid()`:
1. In `LockupContract::new`, for the `VestingScheduleOrHash::VestingSchedule` branch (this is possible since the schedule is public at creation time).
2. In `assert_vesting` (`lockup/src/internal.rs`), immediately after the hash check succeeds and before returning the revealed `VestingSchedule`, so that a genuinely invalid revealed schedule fails fast with a clear assertion message rather than panicking deep inside a `u64` subtraction.
Additionally, consider using `checked_sub`/`saturating_sub` in `get_unvested_amount`'s `total_time` and `time_left` computations as defense in depth.

### Proof of Concept
```rust
// lockup/src/lib.rs test module (cfg(test))
#[test]
#[should_panic] // subtraction overflow panic due to start_timestamp > end_timestamp
fn test_invalid_vesting_schedule_underflow_on_terminate() {
    let mut context = basic_context();
    testing_env!(context.clone());

    // Malformed schedule: start > end, violates assert_valid() invariants,
    // but assert_valid() is never called anywhere in the contract.
    let invalid_vesting_schedule = VestingSchedule {
        start_timestamp: to_ts(GENESIS_TIME_IN_DAYS + 1000).into(), // start AFTER end
        cliff_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
        end_timestamp: to_ts(GENESIS_TIME_IN_DAYS + 100).into(),
    };

    // Confirm assert_valid would have rejected this (never called by contract code):
    let result = std::panic::catch_unwind(|| invalid_vesting_schedule.assert_valid());
    assert!(result.is_err());

    // Creator commits the invalid schedule as a private hash via LockupContract::new
    // (mirrors LockupFactory::create forwarding an attacker-chosen VestingScheduleOrHash::VestingHash).
    let mut contract = new_contract_with_lockup_duration(
        true,
        Some(invalid_vesting_schedule.clone()),
        None,
        true,
        0,
    );

    // Move block_timestamp into [cliff, end) so get_unvested_amount hits the
    // total_time = end - start branch.
    context.block_timestamp = to_ts(GENESIS_TIME_IN_DAYS + 50);
    context.is_view = true;
    testing_env!(context.clone());

    // Public view call also panics with attacker-chosen schedule (frozen getter):
    let _ = contract.get_locked_vested_amount(invalid_vesting_schedule.clone());
}
```
A second test should directly reproduce the state-changing failure path: have the Foundation call `terminate_vesting(Some(VestingScheduleWithSalt { vesting_schedule: invalid_vesting_schedule, salt }))` at a `block_timestamp` inside `[cliff, end)`, and assert that the call panics (via `#[should_panic]`), demonstrating that `terminate_vesting` — and thus forfeiture of unvested tokens — can never succeed for this lockup once the timestamp enters that window.

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }
        }
    }
