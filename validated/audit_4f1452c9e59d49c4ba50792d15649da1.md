### Title
Per-tenure "one tenure-start block" guard is enforced only at proposal arrival, letting two conflicting tenure-change blocks reach pre-commit and get independently signed - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
The signer's rule that only one tenure-start (tenure-change) block may ever be signed per tenure — the `DuplicateBlockFound` check — is only evaluated once, when a proposal first arrives, against each signer's *local* view of already-globally-accepted blocks. It is never re-run when a block later crosses the pre-commit threshold. The pre-commit-time re-check (`check_block_against_signer_db_state`) only looks for conflicts among blocks that already carry a *signature* (`signed_self`/`signed_group`), not blocks that are merely `PreCommitted`. A single malicious miner can therefore fan out two different tenure-start blocks for the same tenure to different subsets of the signer set before either is signed; each subset's local duplicate check passes (no block has been globally accepted yet), both blocks separately cross the pre-commit weight threshold in their respective subsets, and each subset signs a different, mutually conflicting block at the same tenure/height.

### Finding Description
`SortitionsView::check_proposal` (v1) calls `validate_tenure_change_payload`, which is the only place `RejectReason::DuplicateBlockFound` is produced: [1](#0-0) 

This check queries `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — a *per-signer local* view — and only fires if that signer already sees a globally-accepted block in the tenure. Because this evaluation happens once, at proposal arrival, in the "fresh evaluation" branch of `handle_block_proposal`: [2](#0-1) 

the documentation itself calls this out as a design gap: the duplicate check "never runs again," and the only backstop is the "own-tenure conflict guard" run at pre-commit threshold time: [3](#0-2) 

That backstop, in `handle_block_pre_commit`'s threshold-reached path, only considers conflicts returned by `get_signed_conflicts`, which explicitly excludes anything not yet signed (`PreCommitted` carries no signature and is never returned): [4](#0-3) [5](#0-4) 

So the sequence is:
1. A byzantine miner (one slot) proposes tenure-change block `A` for tenure `T` to signer subset 1, and a different tenure-change block `B` for the same tenure `T`/height to signer subset 2 (e.g. via targeted gossip/network delay).
2. For each subset, at proposal time no signer has yet seen *any* globally-accepted block in tenure `T`, so `validate_tenure_change_payload`'s `DuplicateBlockFound` check passes for both `A` and `B` independently.
3. Both blocks are individually valid according to the node's `/v3/block_proposal` validation (each legitimately extends the same parent, since neither has been processed yet): [6](#0-5) 

4. Each subset moves its block to `PreCommitted` and broadcasts pre-commits; if subset 1's weight for `A` and subset 2's weight for `B` each independently reach the ≥70% pre-commit threshold, `handle_block_pre_commit`'s re-check (`check_block_against_signer_db_state` + `get_signed_conflicts`) finds no conflict for either — because the other side is still only `PreCommitted`, not `signed_self`/`signed_group` — and each subset signs its own block.
5. The result: the signer network produces two distinct, mutually exclusive signed tenure-start blocks for the same tenure — a direct break of the "one tenure-start block per tenure" equality this specific check exists to guarantee, achievable by a single miner without requiring a majority of signers or another signer's key.

This is the direct analog to the reported bug class: a restriction ("no duplicate admin/tenure-start action") is enforced at one entry point (the UI / initial proposal-arrival check) but is not re-enforced at the alternate path that ultimately performs the sensitive action (the direct API call / the pre-commit-threshold signing path), so the restriction can be bypassed via the alternate path.

### Impact Explanation
This breaks a Critical-severity invariant: a signer (in aggregate, the group) signs a conflicting/non-canonical block. Two conflicting tenure-start blocks each gathering a valid group signature threshold is exactly the "aggregated-weight vs verified-accepts" equality violation called out as in-scope, and can be used by a single miner to force a fork or stall recovery at the tenure boundary.

### Likelihood Explanation
Requires only a single miner (the one attacker-controlled slot per the threat model) plus normal gossip-timing asymmetry across signers — no majority of signers, no other signer's key, and no auth token access is required. The race window is bounded by real network/validation latency (time between proposal arrival, node validation round-trip, and pre-commit gossip), which is realistic for a miner deliberately staggering delivery of the two proposals to different signer subsets.

### Recommendation
Re-run (or persist and re-check) the per-tenure "no other tenure-start block already inflight" guard at the pre-commit-threshold re-check, not just at proposal arrival — e.g. extend `get_signed_conflicts`/`check_block_against_signer_db_state` to also treat any other `PreCommitted` tenure-change block for the same tenure as a conflict, or gossip pre-commit decisions early enough that `validate_tenure_change_payload`'s duplicate check considers group-wide `PreCommitted` state, not just each signer's local globally-accepted state.

### Proof of Concept
1. Stand up a signer set and a byzantine miner controlling the single mining slot for tenure `T`.
2. Have the miner construct two distinct, both-individually-valid tenure-change blocks `A` and `B` for tenure `T` (same parent, same height), differing e.g. in included transactions.
3. Deliver `A` to signer subset 1 and `B` to signer subset 2 with enough separation that neither subset observes the other's proposal before completing pre-commit and node validation (`check_block_against_state` → `check_proposal` → `validate_tenure_change_payload`, `stacks-signer/src/chainstate/v1.rs:461-519`).
4. Show each subset's `get_last_globally_accepted_block(T)` returns `None` at proposal time, so `DuplicateBlockFound` is never raised for either block.
5. Let each subset's pre-commit weight for its respective block cross the 70% threshold; observe `handle_block_pre_commit`'s conflict re-check (`stacks-signer/src/v0/signer.rs:1383-1421`) find no conflict (since the counterpart block is not yet `signed_self`/`signed_group`) and both `A` and `B` get signed by their respective subsets, producing two conflicting signed blocks for tenure `T`.

    /// Return every signed block at or above the given Stacks height, in ANY tenure, excluding
    /// the block with the given signer signature hash, ordered by height (highest first). A
    /// block is considered signed if a signature was ever put over it, ours (`signed_self`)
    /// or the observed group's (`signed_group`). Blocks that were only pre-committed carry no
    /// signature and are never returned. Each row carries the most recent endorsement time
    /// (`signed_self`/`signed_group`, whichever is later) so the caller can judge freshness per
    /// conflict.
    ///
    /// The search deliberately spans all tenures: two blocks at the same height are siblings
    /// no matter which tenure they belong to (e.g. a tenure-start block conflicts with the
    /// previous tenure's block at the same height), so a signature over either may conflict
    /// with a fresh signature over the other.

    /// Blocks in tenures whose reorg we sanctioned under the reorg-timing rules (see
    /// [`SignerDb::mark_tenure_superseded`]) are still returned, but annotated with the
    /// permitting tenure's sortition (`superseded_by_*`): the permit only holds while that
    /// sortition is canonical, which the caller derives from the node per evaluation (see
    /// `Signer::reorg_permit_stands`) -- like every other question about whether a conflict is
    /// still *live* (`Signer::conflict_still_blocks`), it is not recorded.
