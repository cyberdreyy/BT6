### Title
Unclaimed loss-adjusted withdraw receipts are paid at par when the user re-requests in a later epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, pending withdraw receipts of that epoch are only partially funded and a haircut is stored in `lossRecoveryPriceByEpoch[epoch]`. The strategy looks up that haircut only through the single `lastWithdrawRequest[_user]` marker. If the user makes a new `requestWithdraw` in a later epoch before claiming, `lastWithdrawRequest` is overwritten, the loss-adjusted path can never fire for the old receipt, and `_claimFundedWithdrawRequest` pays the full aggregate `withdrawsRequests[_user]` — including the haircut receipt — at par.

### Finding Description
- On a lossy stop, `collectWithdrawFunds` is called with `_amount < pendingBasis`; it zeroes `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` (IdleCreditVault.sol:411-430). The shortfall `pendingBasis - _amount` is never funded; users are meant to absorb it.
- `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and applies the haircut only if `lossRecoveryPriceByEpoch[lossEpoch] != 0` (IdleCreditVault.sol:789-801). There is only one marker per user.
- `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (IdleCreditVault.sol:282-294). Nothing forces the user to claim (or forbids re-requesting) while an older receipt is pending — the code comments explicitly support "claim both requests" later.
- After the later epoch is funded, `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` checks the *new* `lastWithdrawRequest` epoch, finds no loss price, and returns 0. Then `_claimFundedWithdrawRequest` pays `amount = withdrawsRequests[_user] + apr0…` at par and burns/clears everything (IdleCreditVault.sol:319-350). The epoch-keyed receipt for the lossy epoch is still in `withdrawsRequests[_user]` — the haircut is bypassed permanently.
- The same ordering hole exists post-default: `_claimDefaultedWithdrawRequest` clears `lastWithdrawRequest` to 0 when it equals `defaultRecoveryEpoch` (IdleCreditVault.sol:832-836), so an older loss-adjusted receipt falls straight through to the funded path at par.

Broken invariant: loss waterfall / one-receipt-one-payout. `_transferFundedClaim` only guards against dipping into `defaultRecoveryReserve` (IdleCreditVault.sol:897-907); there is no per-epoch funding check, so the overpayment is paid out of underlyings funded for *other* users' pending receipts.

### Impact Explanation
Direct theft / insolvency. Attacker over-withdraws `basis * (1 - lossRecoveryPrice) / RECOVERY_FULL` more than entitled. That amount was never collected from the borrower, so it is paid from underlyings funded for other pending receipts; when the attacker claims first, honest users' `claimWithdrawRequest` calls revert on the reserve/balance check or on insufficient balance — permanent freezing of their funded claims. Same drain applies against `defaultRecoveryReserve`-adjacent balances after a default.

### Likelihood Explanation
Fully attacker-driven sequencing with honest privileged roles:
1. Attacker requests a withdraw in epoch N.
2. Manager stops epoch N via `stopEpochWithDuration` with a partial loss (a supported, honest action). `lossRecoveryPriceByEpoch[N]` is set; only the reduced amount is funded.
3. Instead of claiming, attacker requests a new withdraw in epoch N+1 (buffer allowed; request path has no "claim first" check).
4. Epoch N+1 ends normally and is fully funded.
5. Attacker calls `claimWithdrawRequest` via the CDO and receives both receipts at par, taking `basis_N * (1 - price)` extra.

No privileged misbehavior required; only the existence of one lossy epoch and one subsequent normal epoch.

### Recommendation
Track the loss-adjusted epoch per user instead of relying on `lastWithdrawRequest` — e.g., store per-epoch loss prices and iterate/clear `withdrawsRequestsByEpoch` against `lossRecoveryPriceByEpoch` for *every* epoch with a recorded receipt, or record each request epoch's pending haircut at request/finalization time. Minimal fix: in `requestWithdraw`, settle any existing loss-adjusted receipt for the user (or revert if `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`), and in `_clearWithdrawClaimForEpoch`/`_claimFundedWithdrawRequest` verify no uncleared `lossRecoveryPriceByEpoch` entry applies to epochs still present in `withdrawsRequestsByEpoch`.

### Proof of Concept
```solidity
// Foundry fork PoC outline on the repo's own harness (test/foundry/IdleCDOEpochQueue.t.sol style)
// Assumes helpers _depositWithUser/_requestWithdrawWithUser/_stopCurrentEpochWithApr exist.

function testLossReceiptPaidAtParAfterSecondRequest() external {
    uint256 amount = 100e6; // 100 USDC
    uint256 tranchesA = _depositWithUser(FASA, amount);
    uint256 tranchesB = _depositWithUser(VICTIM, amount);

    // Epoch N: both request withdraws
    _requestWithdrawWithUser(FASA, tranchesA);
    _requestWithdrawWithUser(VICTIM, tranchesB);

    // Fund epoch N partially via stopEpochWithDuration with a loss (honest manager),
    // e.g. 50% loss -> lossRecoveryPriceByEpoch[N] = RECOVERY_FULL/2
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 lossAmount = pendingBasis / 2; // ensure previewLossAdjustedWithdrawFunds split
    // borrower approves pendingToFund only
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    // ...warp to epochEndDate, deal+approve borrower for interest+pendingToFund...
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);
    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), 0);

    // Epoch N+1: FASA does NOT claim; makes a new request instead
    vm.prank(manager); cdoEpoch.startEpoch();
    // deposit again or reuse tranches; request again
    uint256 tranchesA2 = _depositWithUser(FASA, amount);
    _requestWithdrawWithUser(FASA, tranchesA2);
    // VICTIM also does not claim

    // Epoch N+1 stops normally and is fully funded
    _stopCurrentEpochWithApr(10e18);

    // FASA claims: funded path pays withdrawsRequests[FASA] (N + N+1 receipts) at par
    uint256 balPre = underlying.balanceOf(FASA);
    vm.prank(address(cdoEpoch));
    strategy.claimWithdrawRequest(FASA);
    uint256 got = underlying.balanceOf(FASA) - balPre;

    uint256 entitled = tranchesA /*≈ basis_N*/ / 2 + tranchesA2 /*≈ basis_N+1*/; // haircut applied
    assertGt(got, entitled); // haircut bypassed: FASA overpaid by basis_N * (1 - price)

    // VICTIM's claim now reverts / underpays: funded balance was drained
    vm.prank(address(cdoEpoch));
    vm.expectRevert(); // NotAllowed or SafeERC20 insufficient balance
    strategy.claimWithdrawRequest(VICTIM);
}
```
Concrete numbers: 100 USDC basis in epoch N at 50% loss (50 funded) + 100 USDC basis in epoch N+1 fully funded. Contract holds 50 + 100 + victim's 50 = 200. Attacker claims 200 (both receipts at par) instead of 150, draining the victim's funded 50; the victim's claim reverts permanently.
