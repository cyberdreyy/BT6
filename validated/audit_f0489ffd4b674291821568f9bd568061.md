### Title
Users can burn tranche tokens for a zero-value withdrawal receipt and deposit underlyings for zero shares — dust funds are permanently lost (contracts/IdleCDOEpochVariant.sol, contracts/IdleCDOCreditVault.sol)

### Summary
`requestWithdraw`, `depositAA`/`depositBB` and `depositDuringEpoch` never check that the computed underlying amount (`_underlyings`) or minted shares (`_minted`) are non-zero after integer rounding. Rounding always favors the vault, so a user with a dust tranche balance can burn real tokens for a 0-underlying receipt, and a user depositing less than one tranche-token unit of value pays underlyings and receives 0 tranche tokens while their NAV is credited to existing holders.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739-791`), `_underlyings = _trancheToUnderlyings(_amount, _tranche)` computes `_amount * _tranchePrice / ONE_TRANCHE_TOKEN` rounded down (`contracts/IdleCDOEpochVariant.sol:815-817`). There is no check that `_underlyings > 0` — the only zero-handling is `_amount == 0` → full balance. `_withdrawOps(_amount, principal, _tranche)` then unconditionally burns the user's tranche tokens (`contracts/IdleCDOCreditVault.sol:369-378`) even when `principal == 0`, leaving the user with a 0-value withdraw receipt in `IdleCreditVault` and no claim on the NAV they just relinquished. The same pattern exists on the instant-withdraw branch (`contracts/IdleCDOEpochVariant.sol:761-769`): `requestInstantWithdraw(_underlyings, ...)` + `_withdrawOps` burn shares for a potentially zero amount.

Symmetrically, `_mintSharesAtCurrPrice` computes `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` rounded down with no `_minted > 0` check (`contracts/IdleCDOCreditVault.sol:344-347`, same shape in `IdleCDO.sol:437-441`). `_deposit` only rejects `_amount == 0` (`contracts/IdleCDOCreditVault.sol:191-194`), so a deposit where `amount < price` in token terms mints 0 shares while `lastNAVAA`/`lastNAVBB` is still incremented by the full `_amount` (`_mintShares`), i.e. the depositor donates their transfer to other holders. `depositDuringEpoch` has the same hole: `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` rounds down and `_mintShares` credits NAV and pulls funds even when `_minted == 0` (`contracts/IdleCDOEpochVariant.sol:724-732`).

This is the direct analog of the Surge `withdraw(0)`/`deposit` finding: calculated amounts can be 0 and the user loses funds while receiving nothing.

### Impact Explanation
Permanent loss of user funds at dust scale: (a) a tranche holder calling `requestWithdraw` with a balance worth less than 1 wei of underlying burns the shares, gets a receipt paying 0, and forfeits a claim that could have aggregated to a redeemable amount later (e.g., dust accumulating after partial withdrawals or transfers); (b) a depositor of `amount < tranchePrice` loses the full deposit while receiving 0 shares. Both violate the fair mint/burn invariant — the exchange is one-directional with no revert.

### Likelihood Explanation
Low-to-medium. Each occurrence loses only sub-wei-value dust, but the conditions occur naturally: tranche prices drift above `oneToken` over time, widening the dust band; users frequently request withdrawals of "full balance" via `_amount == 0`, so leftover dust balances from prior partial requests/claims are common. No existing guard stops it: `_skimDonatedAssets` runs before, `_updateAccounting` doesn't revert on zero deltas, and `requestWithdraw`/`_withdrawOps` contain no zero-value check.

### Recommendation
- In `requestWithdraw`, revert when `_underlyings == 0` (after resolving `_amount == 0` → full balance).
- In `_mintSharesAtCurrPrice` and `depositDuringEpoch`, revert when `_minted == 0`.
- In `IdleCDO._withdraw`/equivalent credit-vault path, revert when `toRedeem == 0` while `_amount > 0`.

### Proof of Concept
Foundry fork sketch (credit-vault epoch variant, buffer phase):

```solidity
// setup: epoch not running, allowAAWithdrawRequest = true, user is KYC-allowed
uint256 price = cdo.virtualPrice(AA);            // e.g. ~1.0001e6 for USDC
uint256 dustShares = (ONE_TRANCHE - 1) / price;  // shares worth < 1 wei underlying
trancheAA.transferFrom(holder, user, dustShares); // user owns only dust

vm.prank(user);
uint256 underlyings = cdo.requestWithdraw(dustShares, AA);
assertEq(underlyings, 0);                        // rounds to 0
assertEq(trancheAA.balanceOf(user), 0);          // but shares were burned
// strategy receipt for `user` pays 0 -> user's claim is permanently gone

// deposit side:
uint256 tiny = price / ONE_TRANCHE;              // deposits value < 1 share unit
token.approve(cdo, tiny);
vm.prank(user2);
uint256 minted = cdo.depositAA(tiny);
assertEq(minted, 0);                             // 0 shares minted
assertEq(token.balanceOf(user2), balBefore - tiny); // funds taken, NAV increased
```

Note: I could not fully verify whether `IdleCreditVault.requestWithdraw`/`requestInstantWithdraw` internally reverts on a 0 amount (grep returned matches without contents). Even if it does revert, the `_mintSharesAtCurrPrice`/`depositDuringEpoch` zero-share minting path and the share burn in `_withdrawOps` stand independently, so the analog holds; confirm the strategy-side behavior when writing the final PoC.
