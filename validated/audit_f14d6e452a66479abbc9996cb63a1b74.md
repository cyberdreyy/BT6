### Title
Builder payment bypasses PTC quorum check when payload settlement is delayed 2+ epochs - (File: specs/gloas/beacon-chain.md)

### Summary
`apply_parent_execution_payload`'s fallback branch for late-settled builder payments unconditionally credits the builder's bid value to `builder_pending_withdrawals`, bypassing the Payload Timeliness Committee (PTC) quorum-weight check that gates payment in every other code path. This mirrors the Autonolas bug class: a value-release condition ("has this been validated/does the actual value support the credit?") is enforced on the common path but silently skipped on an edge-case path, letting a payment escape without the invariant that normally authorizes it.

### Finding Description
Two normal settlement paths exist for a builder's pending payment:

- `settle_builder_payment`, invoked when the very next (or next-epoch) block explicitly commits to the parent (`bid.parent_block_hash == parent_bid.block_hash`), pays unconditionally because the child block's own commitment is proof the payload was received/available. [1](#0-0) 

- `process_builder_pending_payments`, the epoch-boundary fallback for payments whose parent was never immediately built upon, only forwards the withdrawal if PTC-weighted attestations reached quorum, i.e. `payment.weight >= quorum`: [2](#0-1) 

However, `builder_pending_payments` only spans two epochs. If no descendant block settles the payment within that window, the epoch-boundary rotation evicts the entry (see `process_builder_pending_payments` clearing `state.builder_pending_payments[:SLOTS_PER_EPOCH]`). When a block eventually *does* build on that stale parent (2+ epochs late), `apply_parent_execution_payload` no longer finds a live payment index and falls into:

```python
elif parent_bid.value > 0:
    # Parent is older than the previous epoch, its payment entry has been
    # evicted from builder_pending_payments. Append the withdrawal directly.
    state.builder_pending_withdrawals.append(
        BuilderPendingWithdrawal(
            fee_recipient=parent_bid.fee_recipient,
            amount=parent_bid.value,
            builder_index=parent_bid.builder_index,
        )
    )
``` [3](#0-2) 

This branch pays the builder the full bid value from `state.latest_execution_payload_bid` with **no reference to `payment.weight` or the quorum threshold at all**. It does not matter whether the PTC ever attested the payload was available, or whether `process_builder_pending_payments` had already evicted the entry specifically *because* weight never reached quorum (weight stayed at 0 or below `get_builder_payment_quorum_threshold`). The unconditional `elif` simply re-derives the payment from the cached bid and pays it anyway — exactly the "only correct in one direction" pattern from the reference report, where the correction/verification step (`incentives[4] > curMaxBond`) was applied on the expected path but omitted on the path where the actual value diverged from what should be paid.

### Impact Explanation
This breaks the invariant that a builder is paid only when PTC attesters confirm payload availability with sufficient weight (`get_builder_payment_quorum_threshold`). Whenever a chain experiences 2+ epochs without a descendant block settling a given full parent's payment (e.g., during a period of missed/empty slots, common during liveness degradation, not requiring any privileged coalition), the builder is guaranteed to be paid in full regardless of whether the payload was ever verified as available by the PTC. This is a Gwei payment released to a builder that the protocol's stated attestation-quorum invariant did not actually authorize — falling under "a builder payment or withdrawal misdirected, doubled or escaped" and "a payload or payment applied that the block did not commit to."

### Likelihood Explanation
Triggering requires only that a canonical full-payload block does not have a descendant that "settles" it within the 2-epoch `builder_pending_payments` window — i.e., roughly 2 epochs of empty/skipped slots following the block. This is not attacker-privileged; it can occur from ordinary network liveness issues (nobody needs to collude), and the test suite (`test_builder_payment_after_missed_epochs`, `test_process_parent_execution_payload__older_than_previous_epoch`) explicitly exercises and expects this exact unconditional-payment behavior, confirming the code path is reachable and deterministic once slots are missed for 2+ epochs. [4](#0-3) [5](#0-4) 

### Recommendation
In the `elif parent_bid.value > 0` branch of `apply_parent_execution_payload`, do not unconditionally append the withdrawal from `parent_bid`. Instead, before evicting a payment in `process_builder_pending_payments`, either (a) persist enough information (e.g., a per-builder "confirmed" flag or extend retention) to remember whether quorum was reached before the slot is rotated out, or (b) retain the evicted payment's weight/quorum outcome so the late-settlement path can re-apply the same `weight >= quorum` test rather than defaulting to unconditional payment.

### Proof of Concept
1. Builder submits a full-value bid at slot `S`; block `S` is canonical and includes the bid, creating `builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH]` with `weight = 0`.
2. No attestations ever accrue weight for slot `S` (e.g., because no PTC/attesters observed the payload as available) — `payment.weight` stays at `0`, well below `get_builder_payment_quorum_threshold`.
3. Two epoch boundaries pass with no child block explicitly building on `S`'s payload; `process_builder_pending_payments` rotates the entry through and evicts it without adding it to `builder_pending_withdrawals` because `weight (0) < quorum`.
4. A later block finally sets `parent_block_hash` to match the stale bid's `block_hash` and is processed via `apply_parent_execution_payload`; since `parent_epoch` is now older than `get_previous_epoch(state)`, the `elif parent_bid.value > 0` branch fires and unconditionally appends `BuilderPendingWithdrawal(amount=parent_bid.value, ...)` to `state.builder_pending_withdrawals`, paying the builder in full despite quorum never having been met.
5. This exact flow is demonstrated by the existing test `test_builder_payment_after_missed_epochs`, which asserts the builder's balance decreases by the bid `value` after this precise 2-epoch-late scenario, confirming payment occurs with `weight = 0` and no quorum check applied. [6](#0-5)

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

@with_gloas_and_later
@spec_state_test
def test_builder_payment_after_missed_epochs(spec, state):
    """
    Test that a builder is correctly charged when their canonical payload
    is processed after 2+ epochs of missed blocks.
    """
    # Advance to get finalization
    for _ in range(4):
        next_epoch_with_full_participation(spec, state)
    assert state.finalized_checkpoint.epoch == 2

    # Build Block 1 with a non-zero value bid from a builder
    block_1 = build_empty_block_for_next_slot(spec, state)
    builder_index = 0
    value = spec.Gwei(1000000)  # 0.001 ETH
    fee_recipient = b"\xab" * 20
    block_hash = spec.Hash32(b"\x42" * 32)

    bid = block_1.body.signed_execution_payload_bid.message
    bid.block_hash = block_hash
    bid.builder_index = builder_index
    bid.value = value
    bid.fee_recipient = fee_recipient
    bid.execution_requests_root = spec.hash_tree_root(spec.ExecutionRequests())

    # Sign the bid with the builder's private key
    signature = spec.get_execution_payload_bid_signature(
        state, bid, builder_privkeys[builder_index]
    )
    block_1.body.signed_execution_payload_bid = spec.SignedExecutionPayloadBid(
        message=bid,
        signature=signature,
    )

    # Ensure builder can cover the bid
    state.builders[builder_index].balance = spec.MIN_DEPOSIT_AMOUNT + value

    yield "pre", state

    # Process Block 1 — creates a pending payment for the builder
    signed_block_1 = state_transition_and_sign_block(spec, state, block_1)

    # Verify pending payment was created
    payment_idx = spec.SLOTS_PER_EPOCH + block_1.slot % spec.SLOTS_PER_EPOCH
    payment = state.builder_pending_payments[payment_idx]
    assert payment.withdrawal.amount == value
    assert payment.withdrawal.builder_index == builder_index
    assert payment.weight == 0

    pre_builder_balance = state.builders[builder_index].balance

    # Build Block 2 with 2+ epochs of missed slots. During the slot advancement,
    # process_builder_pending_payments runs at each epoch boundary:
    #   1st boundary: shifts payment from second half to first half
    #   2nd boundary: checks quorum on first half — weight 0 < quorum → evicted
    # When Block 2 is processed, parent is FULL so apply_parent_execution_payload
    # runs. Since parent_epoch is older than previous_epoch, payment_index is None.
    # The fix creates the withdrawal directly from the bid in this case.
    block_1_epoch = spec.compute_epoch_at_slot(block_1.slot)
    block_2_slot = spec.compute_start_slot_at_epoch(block_1_epoch + 2) + 1
    block_2 = build_empty_block(spec, state, slot=block_2_slot)
    block_2.body.signed_execution_payload_bid.message.parent_block_hash = block_hash
    signed_block_2 = state_transition_and_sign_block(spec, state, block_2)

    yield "blocks", [signed_block_1, signed_block_2]
    yield "post", state

    # Verify apply_parent_execution_payload actually ran (parent was FULL)
    parent_slot_index = bid.slot % spec.SLOTS_PER_HISTORICAL_ROOT
    assert state.execution_payload_availability[parent_slot_index]

    # Verify the builder was charged — balance decreased by the bid value
    assert state.builders[builder_index].balance == pre_builder_balance - value

@with_gloas_and_later
@spec_state_test
def test_process_parent_execution_payload__older_than_previous_epoch(spec, state):
    """
    Test ``apply_parent_execution_payload`` appends the withdrawal directly when
    the parent's slot is older than the previous epoch.
    """
    builder_index = 0
    value = spec.Gwei(50_000_000)
    fee_recipient = spec.ExecutionAddress(b"\xab" * 20)
    parent_bid = _commit_full_parent_with_payment(spec, state, value, builder_index, fee_recipient)
    previous_epoch_idx = parent_bid.slot % spec.SLOTS_PER_EPOCH

    # Cross two epoch boundaries to evict payments
    spec.process_slots(state, 2 * spec.SLOTS_PER_EPOCH)
    block = build_empty_block_for_next_slot(spec, state)
    spec.process_slots(state, block.slot)

    # Assert payment was evicted from the previous epoch
    assert spec.compute_epoch_at_slot(parent_bid.slot) < spec.get_previous_epoch(state)
    assert state.builder_pending_payments[previous_epoch_idx] == spec.BuilderPendingPayment()

    pre_pending_withdrawals_len = len(state.builder_pending_withdrawals)
    pre_payments = state.builder_pending_payments.copy()

    yield from run_parent_execution_payload_processing(spec, state, block)

    # Check we have a pending withdrawal
    assert len(state.builder_pending_withdrawals) == pre_pending_withdrawals_len + 1
    withdrawal = state.builder_pending_withdrawals[pre_pending_withdrawals_len]
    assert withdrawal.amount == value
    assert withdrawal.builder_index == builder_index
    assert withdrawal.fee_recipient == fee_recipient

    # Assert no payment slot is modified
    assert all(
        post == pre for post, pre in zip(state.builder_pending_payments, pre_payments, strict=True)
    )
