### Title
Stale write-off requests remain fulfillable outside the epoch in which they were priced because `fullfillWriteOffRequest` never re-checks `isEpochRunning()` - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` correctly gates request creation to the running epoch (`if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();`), but `fullfillWriteOffRequest` contains no validity-window check at all. The request's agreed price (`underlyings` per `tranches`) is fixed at creation time inside one epoch's market conditions, yet the order can be executed in any later phase: buffer, a subsequent epoch, after a loss-realizing `stopEpochWithDuration`, or even after default. This is the direct analog of a token verifier that checks issuance parameters but never enforces `exp`/`nbf`: the credential was valid when minted, and is still accepted after its intended lifetime.

### Finding Description [1](#0-0)  shows the creation-side epoch gate. In contrast, [2](#0-1)  only checks that the request exists and that `_underlyings >= currentRequest.underlyings` and `_tranches == currentRequest.tranches`; nothing binds fulfillment to the epoch in which the price was quoted.

Between creation and fulfillment the tranche price moves freely:

- `stopEpochWithDuration(_lossAmount)` burns strategy tokens and lowers `virtualPrice`, so tranches escrowed at a pre-loss quote become worth less than the fixed `underlyings` requested.
- Interest accrual across epochs raises `virtualPrice`, so a stale request may price tranches below market.
- After `_handleBorrowerDefault`, tranche value collapses pending `defaultRecoveryPrice`, yet fulfillment still proceeds at the old quote.

Two exploit directions exist for unprivileged actors:

1. **Attacker = requester (tranche holder).** Create a request quoting N underlyings during a running epoch, wait for a loss epoch or borrower default that slashes the tranche price, then let any third-party wallet fulfill. The fulfiller (explicitly permissionless per the `@dev this function can be called by any wallet` note and `testFullfillWriteOffRequestAllowsThirdPartyBuyer`) pays the stale high price for nearly worthless tranches. Theft equals `underlyings - tranches * currentPrice`.
2. **Attacker = fulfiller.** A request created during a low-price epoch remains live after interest accrual raises the tranche price. The fulfiller buys tranches at the stale discount, extracting value from the seller who did not call `deleteWriteOffRequest` (there is no automatic expiry to protect them).

The broken invariant is fair-price exchange: the escrow assumes the quoted price reflects current `virtualPrice`, but the state machine allows the quote to outlive the conditions that made it fair. None of the existing guards stop this: `nonReentrant` is orthogonal, `EpochNotRunning` is only checked at creation, `pendingUnderlyings` accounting does not gate execution, and no expiry timestamp exists on `WriteOffRequest`.

### Impact Explanation
Direct theft of underlyings. In direction 1 the victim fulfiller pays up to the full `underlyings` for tranches whose redemption value may be near zero after a default; loss magnitude is `underlyings - tranches * virtualPrice / 1e18` (minus the ≤1% exit fee, which goes to `feeReceiver`, not the victim). In direction 2 the seller's tranches are bought below current market price; loss is the price delta. Because tranche prices swing sharply at `stopEpochWithDuration(_lossAmount)` and default finalization, the mispricing can approach 100% of the requested underlyings.

### Likelihood Explanation
Direction 2 requires only that a requester forgets to delete after an epoch transition — no malicious counterparty setup needed; anyone can scan `userRequests` and fulfill profitable stale orders. Direction 1 requires an uninformed third-party fulfiller, which is plausible since fulfillment is deliberately permissionless (tests confirm non-borrower, non-KYC fulfillers are supported). Likelihood is moderate: it needs an epoch transition to move price materially, but epoch boundaries (loss application, APR changes, defaults) are routine events in this design, and the absence of expiry makes every stale quote a standing arbitrage/victim opportunity.

### Recommendation
Bind the request to its validity window the same way creation is bound: store the epoch identifier (e.g., `strategy.epochNumber()` or `idleCDOEpoch` epoch counter) in `WriteOffRequest` at creation, and in `fullfillWriteOffRequest` require `isEpochRunning()` and the same epoch number — or alternatively require `isEpochRunning()` and add an explicit `expiry` timestamp set at creation. Auto-invalidating requests on `stopEpoch`/default finalization would also close the gap.

### Proof of Concept
Reproducible Foundry scenario (fork of `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` harness):

```solidity
function testStaleWriteOffRequestFulfilledAfterLoss() external {
    // LP quotes 10000e6 underlyings for 10000e18 tranches during a running epoch
    vm.prank(LP);
    escrow.createWriteOffRequest(10000e18, 10000e6);

    // Epoch ends with a realized loss; tranche virtualPrice drops, e.g. 50%
    _stopCurrentEpochWithLoss(); // stopEpochWithDuration(apr, interest, duration, lossAmount)
    uint256 priceAfter = cdoEpoch.virtualPrice(address(tranche));
    uint256 trueValue = 10000e18 * priceAfter / 1e18; // << 10000e6

    // Any wallet fulfills the stale, now-overpriced request — no EpochNotRunning check
    address buyer = makeAddr("buyer");
    deal(address(underlying), buyer, 10000e6);
    vm.startPrank(buyer);
    underlying.approve(address(escrow), 10000e6);
    escrow.fullfillWriteOffRequest(LP, 10000e18, 10000e6); // succeeds
    vm.stopPrank();

    // Buyer overpaid: 10000e6 paid for tranches worth trueValue
    assertLt(trueValue, 10000e6);
    assertEq(tranche.balanceOf(buyer), 10000e18);
}
```

The same test inverted (fulfill a request priced before interest accrual) demonstrates the cheap-buy direction.

**Caveat:** I was unable to verify whether the spec for the write-off escrow intends requests to be epoch-scoped; the code comment ("can request write off only when epoch is running") strongly implies epoch-lifetime semantics, which makes the missing fulfillment-side check a genuine validity-window bug, but if the design intentionally treats requests as open orders, this is a design weakness rather than a strict invariant violation.

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);

    // If the fulfiller is the borrower, they can then choose to either keep the tranche tokens or write them off via
    // IdleCDOEpochVariant.writeOffDeposit method.
  }
```
