Confirmed: `WorkflowMetadataHandler.Authorize` is reachable directly from an unprivileged external client through `httpTriggerHandler.authorizeRequest` → `HandleUserTriggerRequest`, which is invoked for every incoming HTTP trigger request to the gateway.

### Title
Unsynchronized read of `authorizedKeys` map in `WorkflowMetadataHandler.Authorize` races with periodic `syncMetadata` writes - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` without holding `h.mu`, while the background `syncMetadata` goroutine periodically replaces `h.authorizedKeys` (and the sibling maps `workflowRefToID`, `workflowIDToRef`, `workflowShards`) under `h.mu.Lock()`. This is the same class of bug as the Prysm `service.head` fix referenced in the report: a hot, request-driven read path accesses mutable shared state guarded by a mutex elsewhere in the codebase, but the read path itself omits the lock.

### Finding Description
`Authorize` is called synchronously for every incoming user HTTP trigger request via `httpTriggerHandler.authorizeRequest`: [1](#0-0) 

Inside `Authorize`, the map is read with a plain index expression, with no `h.mu.RLock()`: [2](#0-1) 

Meanwhile, `syncMetadata` runs on a background ticker (`h.runTicker(..., h.syncMetadata)`) and reassigns `h.authorizedKeys` under `h.mu.Lock()`: [3](#0-2) [4](#0-3) 

Every other accessor of these fields in the same struct is correctly protected with `h.mu.RLock()`/`h.mu.RUnlock()` — e.g. `WorkflowShards` [5](#0-4) , `GetWorkflowID` [6](#0-5) , and `GetWorkflowReference` [7](#0-6) . `Authorize`'s access to `h.authorizedKeys` at line 92 is the sole outlier that bypasses `h.mu`, which is exactly the pattern the Prysm patch fixed by adding `RLock` around every read of shared head state.

Because `syncMetadata` replaces the map variable itself (not just mutating entries in place) while a concurrent goroutine holds a reference from an unsynchronized read, Go's race detector will flag this as a data race, and — since Go maps are not safe for concurrent read/write — a concurrent write from `syncMetadata` while `Authorize` is iterating/reading can trigger `fatal error: concurrent map read and map write`, which is unrecoverable and crashes the entire gateway process.

### Impact Explanation
The gateway node handling workflow HTTP triggers processes external, unprivileged user requests concurrently (goroutine per JSON-RPC request from the workflow DON connection layer) while `syncMetadata` runs on its own ticker in the background. An attacker does not need any special privilege — merely sending trigger requests (with any `workflowID`, valid or not) during the metadata sync window is enough to race the read against the periodic write. A crash here is a fatal, unrecoverable Go runtime panic that takes down the whole gateway service (denial of service for all workflows/users routed through that gateway instance), not just the single request.

### Likelihood Explanation
`syncMetadata` runs continuously per `MetadataAggregationIntervalMs`, and `Authorize` is invoked on the hot path for every single incoming trigger request, so the window for a race is opened repeatedly and continuously in production. No authentication or special access is required to reach `Authorize` — any external caller able to send an HTTP trigger request to the gateway can trigger the racing read.

### Recommendation
Acquire `h.mu.RLock()`/`h.mu.RUnlock()` around the `h.authorizedKeys[workflowID]` read in `Authorize`, consistent with the locking discipline already used by `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`. Since `Authorize` performs multiple operations (JWT verify, replay check, key lookup, replay record), only the map access itself needs the lock; consider snapshotting `keys` under the lock before doing the outside-of-lock signature comparison, mirroring the copy pattern already used in `WorkflowShards`.

### Proof of Concept
Run Go's race detector against a test that concurrently: (1) repeatedly calls `handler.Authorize(workflowID, token, req)` in a loop from multiple goroutines, and (2) repeatedly calls `handler.syncMetadata(ctx)` in another goroutine, both operating against the same `WorkflowMetadataHandler` instance populated as in `TestWorkflowMetadataHandler_Authorize` [8](#0-7) . Running with `go test -race` will report a data race on `h.authorizedKeys`, and under sufficient load can panic with `fatal error: concurrent map read and map write`.

	if !exists {

	}

func (h *WorkflowMetadataHandler) WorkflowShards(workflowID string) []*shardEndpoint {
	h.mu.RLock()
	defer h.mu.RUnlock()
