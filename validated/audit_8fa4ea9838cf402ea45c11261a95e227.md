### Title
Missing fee-sum validation in `createDstEscrow` allows an unprivileged taker to permanently break `EscrowDst.withdraw`/`publicWithdraw` via arithmetic underflow, forcing funds through `cancel()` back to the taker - ([File: contracts/BaseEscrowFactory.sol])

### Summary
`BaseEscrowFactory._postInteraction` (source-side) explicitly guards against `integratorFeeAmount + protocolFeeAmount >= takingAmount` before deploying the source escrow, reverting with `InvalidFeeAmounts()`. [1](#0-0) 
No equivalent check exists on the destination path. `createDstEscrow` accepts `dstImmutables` (including the `parameters` blob that encodes `protocolFeeAmount`/`integratorFeeAmount`) directly from the caller and only validates the native value against `safetyDeposit`/`amount` - it never checks the fee amounts against `immutables.amount`. [2](#0-1) 

### Finding Description
`EscrowDst._withdraw` unconditionally subtracts both fee amounts from the locked amount:
```solidity
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
``` [3](#0-2) 

Because Solidity ≥0.8 reverts on underflow, if `integratorFeeAmount + protocolFeeAmount >= immutables.amount`, both `withdraw()` and `publicWithdraw()` will always revert (they share `_withdraw`). Unlike the source-side escrow creation (`_postInteraction`), which computes and sanity-checks fee amounts on-chain via `FeeTaker._getFeeAmounts` and the `InvalidFeeAmounts` guard, `createDstEscrow` performs no analogous check - the fee fields inside `parameters` are fully attacker-controlled calldata supplied by whoever calls `createDstEscrow` (any unprivileged address can call it; there is no whitelist/caller restriction on this function).

This is the direct analog of the reported bug class: fee/royalty-like values that are not bounded relative to the principal amount, causing the payout ordering to run out of funds and revert (or, in the LSSVM case, drain pair balance). Here the destination escrow's fee subtraction can be made to underflow, permanently disabling the normal withdrawal path for that escrow instance while `cancel()` (which returns the full `immutables.amount` to the **taker**, not the maker) remains a route for the deploying party to reclaim funds. [4](#0-3) 

### Impact Explanation
Because `withdraw`/`publicWithdraw` on the destination escrow can be made permanently unusable by fee values chosen by the escrow-creating (unprivileged) caller, the maker can never successfully claim the destination funds through the intended path; the only functioning exit is `cancel()`, which pays the taker instead of the maker. This matches the Medium bounty category "smart contract unable to operate because required token/native balances can be broken by an unprivileged actor," and, depending on off-chain secret-reveal timing (a maker's failed withdraw transaction exposes the secret in a public/mempool transaction even though it reverts), could escalate to loss of maker funds on the source chain if the leaked secret is used to withdraw there while the destination side reverts and later gets cancelled back to the taker - approaching the High/Critical "theft of user funds" categories. I can only confirm the on-chain DoS/underflow condition with certainty from the code; the secret-leak escalation depends on off-chain client behavior (whether the maker's tooling verifies the CREATE2-derived escrow address/parameters before revealing the secret), which this repository's index does not let me verify.

### Likelihood Explanation
`createDstEscrow` is a public, unauthenticated function; any address can call it and supply a `parameters` payload that sets `integratorFeeAmount + protocolFeeAmount >= amount`. No on-chain validation prevents this, unlike the equivalent source-chain path. The condition to trigger is purely arithmetic and fully within the calling taker's control at escrow-creation time.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`:
```solidity
if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
extracting the fee amounts from `dstImmutables.parameters` before deployment, so both source and destination escrow creation enforce the identical invariant `protocolFeeAmount + integratorFeeAmount < amount`.

### Proof of Concept
1. An unprivileged actor calls `createDstEscrow` supplying `dstImmutables` where `parameters` encodes `protocolFeeAmount + integratorFeeAmount >= immutables.amount` (e.g. `protocolFeeAmount = amount`, `integratorFeeAmount = 1`). [2](#0-1) 
2. The function only checks `msg.value == safetyDeposit (+ amount if native)` and deploys the clone/funds it - no fee-sum check is performed.
3. When the maker later calls `withdraw(secret, immutables)` (or anyone calls `publicWithdraw`), `_withdraw` computes `immutables.amount - integratorFeeAmount - protocolFeeAmount`, which underflows and reverts every time. [5](#0-4) 
4. The maker can never withdraw destination funds through the intended function; only `cancel()` (payable to the taker) succeeds once the cancellation timelock elapses. [4](#0-3)

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
