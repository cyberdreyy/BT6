### Title
Replay of a previously captured, still-valid signed Message within `MaxAllowedMessageAgeSec` causes duplicate capability execution - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` only checks message freshness (`payload.Timestamp` vs `MaxAllowedMessageAgeSec`) and signature validity via `common.ValidatedRequestFromMessage`, but never checks whether the exact `msg.Body.MessageId`/signature pair has already been processed. An attacker who obtains a validly-signed `Message` through any non-network side channel (e.g., a public log, response payload, or monitoring endpoint) can resubmit it verbatim within the allowed age window and the gateway will forward it to all DON members a second time, re-triggering the victim's capability execution.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) performs the following checks on an inbound signed `Message`:
1. Decodes `payload` from `body.Payload` [1](#0-0) 
2. Verifies `payload.Timestamp != 0` [2](#0-1) 
3. Rejects the message only if it is older than `MaxAllowedMessageAgeSec` [3](#0-2) 
4. Confirms the method is `MethodWebAPITrigger` [4](#0-3) 
5. Builds a validated request via `common.ValidatedRequestFromMessage` (signature check) [5](#0-4) 
6. Stores a `savedCallback` keyed by `msg.Body.MessageId` and forwards the request to every DON member [6](#0-5) 

Critically, step 6 unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` and unconditionally calls `don.SendToNode` for every member on every call — there is no check for whether that `MessageId` has already been seen/processed (either currently pending in `savedCallbacks` or already completed and evicted by `pruneCallbacks`). The `savedCallbacks` map's only purpose is to route the DON's asynchronous response back to the correct callback (`handleWebAPITriggerMessage`, lines 148-162); it is not a replay-protection cache, and entries are deleted once a response arrives (line 151) or after `CallbackMaxAgeSec`/`MaxSavedCallbacks` pruning (lines 299-339). This means the same signature-valid message can be resubmitted at any point up to `MaxAllowedMessageAgeSec` seconds after minting (and, if it slips through before the first callback is deleted, its `savedCallback` slot is simply overwritten, silently orphaning the first caller's pending callback), and each resubmission independently triggers a fresh `don.SendToNode` fan-out to all DON members, re-executing the capability with the original signer's identity attached, without needing the private key.

The signature check performed by `common.ValidatedRequestFromMessage`/`ValidatedMessageFromResp` validates that the signature matches the message contents (authenticity/integrity) but does not, and cannot, prevent replay of a captured, still-valid signed blob, since the signature is not bound to a single use.

### Impact Explanation
This allows an unauthenticated or low-privileged attacker who can passively observe a previously-submitted signed trigger message (e.g., via a public log, gateway response, or monitoring/observability endpoint that leaks request bodies) to force duplicate execution of the victim's capability/workflow attributed to the original signer, without any private key access. This maps to the "unauthorized job run" / request-impersonation / duplicate-execution impact class — a paid or rate-limited workflow (e.g., an HTTP trigger action billed per execution) can be double-triggered, consuming the victim's quota or budget and producing duplicate side effects on external systems, all while appearing to originate from the legitimate signer.

### Likelihood Explanation
- Preconditions: attacker needs only the raw signed `Message` bytes (body + signature) of a legitimate prior request — obtainable from any non-network side-channel exposure (logs, telemetry, a leaked/cached HTTP response, etc.), not the private key.
- No additional credential or role is required to call the gateway's message ingestion path that reaches `HandleLegacyUserMessage`.
- The replay window is bounded only by `MaxAllowedMessageAgeSec` (configurable, default not shown here but intended to be short); within that window the exploit is fully repeatable — the attacker can resend the identical payload as many times as desired, each resulting in a fresh `don.SendToNode` broadcast.
- This is a straightforward, deterministic exploit path requiring no timing races, no node compromise, and no network-layer manipulation — purely replaying already-valid data.

### Recommendation
Maintain a replay-protection cache independent of the callback lifecycle: track processed/seen `MessageId`s (or a hash of body+signature) with a TTL of at least `MaxAllowedMessageAgeSec`, and reject `HandleLegacyUserMessage` calls whose `MessageId` has already been seen, regardless of whether the original `savedCallback` entry has since been deleted or overwritten. This should be a de-duplication check performed before checking/inserting into `savedCallbacks`, distinct from and persisted independently of the callback map's prune logic (lines 299-339).

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a short `MaxAllowedMessageAgeSec` (e.g., 120s) and a mock `handlers.DON`/callback.
2. Build one valid signed `api.Message` with `MethodWebAPITrigger`, a fixed `MessageId`, and `payload.Timestamp = time.Now().Unix()`.
3. Call `h.HandleLegacyUserMessage(ctx, msg, callback1)` — assert `don.SendToNode` is invoked once per DON member and `savedCallbacks[msg.Body.MessageId]` is set to `callback1`.
4. Immediately call `h.HandleLegacyUserMessage(ctx, msg, callback2)` a second time with the identical `msg` object (simulating replay) before any response arrives.
5. Assert (currently failing, demonstrating the bug): the second call is forwarded again to `don.SendToNode` (fan-out count doubles) and `savedCallbacks[msg.Body.MessageId]` is overwritten with `callback2`, silently dropping `callback1`.
6. Expected fixed behavior: the second call should be rejected with a duplicate/replay error via `callback.SendResponse(...)`, `don.SendToNode` should not be called again, and the original `callback1` entry should remain untouched.
