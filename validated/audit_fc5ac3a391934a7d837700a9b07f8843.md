## Title
Multisig requests can execute below the configured confirmation threshold because removing a member does not purge that member's existing confirmations on other pending requests - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
The multisig contracts (`multisig` and `multisig2`) let members submit `MultiSigRequest`s and accumulate `confirmations` from members until `num_confirmations` is reached, at which point the request executes. When a member is removed via `DeleteMember` (`multisig2`) or `DeleteKey` (`multisig`), the contract only purges requests that member itself originated - it does **not** scrub that member's confirmation from other pending requests that member had already confirmed. A confirmation recorded by a member who is later removed remains counted toward the threshold forever, so a request can execute with fewer live, current members approving it than `num_confirmations` requires.

### Finding Description
In `multisig2/src/lib.rs`, `confirm` counts entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set and executes the request once the count reaches `num_confirmations`: [1](#0-0) 

Membership removal is handled by `delete_member`, which only removes *requests originated by* the removed member, and clears confirmations only for *those* requests: [2](#0-1) 

It never inspects `self.confirmations` entries belonging to *other* requests (added by different members) that the removed member may have already confirmed. Those stale confirmation strings remain in the `HashSet<String>` for those requests and continue to count toward `num_confirmations` in `confirm`.

The equality that should hold is:
```
confirmations counted for request R == number of *current* members who approved R
```
After a member is deleted, this becomes:
```
confirmations counted for request R > number of current members who approved R
```
because the removed member's confirmation is still present in the set.

The identical pattern exists in the legacy `multisig` contract, where `DeleteKey` only removes requests where `r.signer_pk == pk`, leaving that key's confirmations on other requests untouched: [3](#0-2) 

and `confirm`/`assert_valid_request` similarly just checks set membership/count without re-validating that every confirming key/member is still active: [4](#0-3) 

### Impact Explanation
This breaks the multisig's core security invariant: "N confirmations from currently authorized members are required to move funds/execute an action." A request can be scheduled and executed (including `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, `DeployContract`, etc.) with strictly fewer live approvals than `num_confirmations`, because a stale confirmation from a member who has since been removed (e.g., for being compromised or malicious) still counts. This matches the Critical impact class "a multisig request executed below threshold," since NEAR (or any receiver-controlled action) can move out of the multisig account with less authorization than the contract is supposed to enforce.

### Likelihood Explanation
No special privilege beyond ordinary multisig operation is required to trigger the bug once it exists: any legitimate turnover of a multisig member (a normal, expected lifecycle event - e.g. removing a departing or compromised signer) leaves behind any confirmations that member had already cast on still-open requests. Any subsequent legitimate `confirm` call by a remaining member can then push a stale-inflated count over the threshold and execute the request, silently completing it with fewer live approvals than intended. Since `add_request`/`confirm` are routine calls exposed to every member and `DeleteMember`/`DeleteKey` are a normal governance action, this is easily triggered without any additional attacker capability, and there is no code path today that revalidates confirmations against current live membership before execution.

### Recommendation
When removing a member/key (`delete_member` / `DeleteKey`), iterate over **all** requests' confirmation sets (not just ones the member originated) and remove that member's/key's entry from each. Alternatively, when counting confirmations in `confirm`, filter the stored confirmation set to only those entries that are still contained in `self.members` (or still hold a valid key) before comparing against `num_confirmations`, so removed members can never contribute toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request(R)` for `Transfer { amount }` to some receiver (request id `req_id`, 0 confirmations).
3. `B` calls `confirm(req_id)` → `confirmations[req_id] = {B}` (1 confirmation, below threshold, not executed).
4. The group later removes `B` (e.g. suspected key compromise) via a properly-confirmed `DeleteMember { member: B }` request. `delete_member` only deletes requests where `r.member == B` (i.e., requests B itself created) - `req_id` was created by `A`, so it is untouched, and `confirmations[req_id]` still equals `{B}`.
5. Now members are `[A, C]`, `num_confirmations` still `2`. `A` calls `confirm(req_id)`. Code checks `!confirmations.contains(A)` (true) and `confirmations.len() + 1 (=2) >= num_confirmations (=2)` → executes the `Transfer`.
6. The transfer executes with only one live-member confirmation (`A`), even though `num_confirmations = 2` and `B` is no longer a member - the threshold was bypassed using a stale confirmation from a removed member.

        self.assert_valid_request(request_id);

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
