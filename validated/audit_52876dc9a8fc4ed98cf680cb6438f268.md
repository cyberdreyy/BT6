### Title
Unprivileged front-running of `LockupFactory::create` permanently squats a victim's deterministic lockup address with attacker-chosen `staking_pool_whitelist_account_id` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the lockup account id purely from `owner_account_id` and the factory's own account id, and it never checks that `env::predecessor_account_id()` is the intended grantor/employer for that `owner_account_id`. Because the method is public and payable to anyone who attaches `MIN_ATTACHED_BALANCE`, any unprivileged attacker can race the legitimate creator, deploy the lockup first with attacker-chosen `whitelist_account_id`, and permanently occupy the deterministic address before the real employer's transaction lands.

### Finding Description
The broken binding is:
`LockupArgs.staking_pool_whitelist_account_id stored at sha256(owner_account_id)[..20].<factory>` **==** `staking_pool_whitelist_account_id the rightful/authorized grantor for owner_account_id intended to configure`.

In `lockup-factory/src/lib.rs`, `create()` computes the target account deterministically: [1](#0-0) 

There is no `assert_called_by_foundation`, allow-list, or any check binding `env::predecessor_account_id()` to `owner_account_id`; the only guard is `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)`, which any unprivileged caller can satisfy with 3.5 NEAR. The account id is `format!("{}.{}", hex::encode(&sha256(owner_account_id)[..20]), current_account_id())` — fully determined by `owner_account_id`, not by who calls `create()`.

The promise chain then does `create_account().deploy_contract(CODE).transfer(deposit).function_call("new", LockupArgs{...})`, followed by `.then(ext_self::on_lockup_create(...))`: [2](#0-1) 

`create_account()` on NEAR fails if the account already exists. Whichever `create()` call reaches the runtime first wins the account and locks in its `LockupArgs` (including its own `staking_pool_whitelist_account_id`, `vesting_schedule`, `release_duration`, etc.). The second call's promise chain fails at `create_account`, so `is_promise_success()` returns `false` in `on_lockup_create`, which only refunds the deposit and logs a failure — it does not, and cannot, alter the already-deployed attacker contract: [3](#0-2) 

Exploit flow: attacker observes (or predicts) that `owner_account_id = <victim_employee>` is about to receive a lockup, computes the same deterministic address, and submits `create(<victim_employee>, lockup_duration, None, None, None, Some(<attacker_whitelist>))` with 3.5 NEAR attached, timed/gas-tuned to land before the legitimate employer's transaction. If it lands first, the victim's deterministic lockup address is permanently deployed with the attacker's chosen `staking_pool_whitelist_account_id` (and no vesting schedule, since attacker controls all optional args). The legitimate employer's later `create()` call fails at `create_account`, and `on_lockup_create` merely refunds their deposit to `predecessor_account_id` — it never invalidates or overwrites the attacker's deployed contract.

No existing guard (`assert_self`, `is_promise_success`, `assert_one_yocto`, etc.) prevents this because none of them check *who is entitled* to create a lockup for a given `owner_account_id` — they only guard the callback's self-call and promise-result interpretation.

### Impact Explanation
The victim employee's canonical lockup address is permanently squatted with attacker-chosen parameters, most critically `staking_pool_whitelist_account_id`. This sets up any staking/delegation the victim later performs through that lockup to trust a staking pool whitelist the attacker controls, and denies the legitimate grantor (employer/foundation) any ability to configure the intended vesting/lockup terms at that address, since the account already exists and cannot be redeployed by the legitimate party. This matches the explicitly listed Critical category: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attack is repeatable against any `owner_account_id` for which a lockup has not yet been created, i.e. it can be run pre-emptively against every future employee/grantee of the protocol.

### Likelihood Explanation
The only precondition is knowledge (or prediction) of an `owner_account_id` that will receive a lockup and 3.5 NEAR (`MIN_ATTACHED_BALANCE`) to attach — both are cheap and observable (e.g., watching mempool/pending transactions, or targeting known upcoming hires/grantees). No special privilege, key, or role is required; `create()` is a fully public `#[payable]` method. The attacker only needs their transaction to be included before the legitimate one, which is a standard front-running assumption already treated as in-scope by the question (mempool-level transaction ordering, not node/validator compromise).

### Recommendation
Restrict who may call `create()` for a given `owner_account_id`, e.g. require `assert_eq!(env::predecessor_account_id(), foundation_account_id)` (as already done elsewhere via `assert_called_by_foundation`-style checks) or require a signature/allow-list tying `owner_account_id` to an authorized creator, so that address squatting by arbitrary third parties is impossible regardless of attached deposit.

### Proof of Concept
Using `near-sdk-sim`/`RuntimeStandalone` (not unit `testing_env!`, since the real account-existence race needs an actual runtime):
1. Deploy `LockupFactory` with `whitelist_account_id = legit_whitelist`, `foundation_account_id`.
2. Create two signer accounts: `attacker` and `real_employer`, both funded ≥ 3.5 NEAR.
3. `attacker.call(factory, "create", {owner_account_id: victim, lockup_duration, whitelist_account_id: Some(attacker_whitelist)}, gas, deposit=3.5N)` — execute and let it finish (including the `on_lockup_create` callback) so the lockup account at `sha256(victim)[..20].factory` is deployed with `staking_pool_whitelist_account_id = attacker_whitelist`.
4. `real_employer.call(factory, "create", {owner_account_id: victim, lockup_duration, whitelist_account_id: None}, gas, deposit=3.5N)` — execute and let it finish.
5. Assert:
   - Step 4's `on_lockup_create` returns `false` (execution outcome / return value inspection via `ExecutionResult`).
   - `real_employer`'s balance after step 4 reflects the refund (deposit returned minus gas), confirming `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` fired.
   - Querying the deployed lockup contract's state at `sha256(victim)[..20].factory` (e.g., via a view call reading `staking_pool_whitelist_account_id`) shows `attacker_whitelist`, i.e. `stored_whitelist == attacker_whitelist != legit_whitelist/real_employer's intended value`, proving the binding `stored LockupArgs == rightful grantor's LockupArgs` is broken.     #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
