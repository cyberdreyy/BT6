### Title
`lending_account_liquidate` provides no liquidator-specified price/slippage bound, exposing liquidators to unexpected execution prices - ([File: programs/marginfi/src/instructions/marginfi_account/liquidate.rs])

### Summary
The classic liquidation instruction `lending_account_liquidate` lets the liquidator specify only the quantity of collateral to seize (`asset_amount`), while the exchange rate between the seized asset and the repaid liability is computed entirely from live oracle prices fetched at execution time. There is no parameter allowing the liquidator to cap the liability amount they are willing to pay (or set a minimum acceptable asset price), so a liquidator has no on-chain protection against unfavorable price movement between transaction submission and execution.

### Finding Description
`lending_account_liquidate` accepts `asset_amount`, `liquidatee_accounts`, and `liquidator_accounts` as its only inputs [1](#0-0) . Inside the instruction handler, `asset_price` and `liab_price` are pulled fresh from the oracle feeds at execution time via `fetch_asset_price_for_bank_low_bias` and `OraclePriceFeedAdapter::try_from_bank`, and the liability amount the liquidator must pay (`liab_amount_liquidator`) is derived purely from those live prices and the fixed protocol fee discount, with no liquidator-supplied bound: [2](#0-1) .

The only quantity the liquidator constrains is `asset_amount` (how much collateral to seize); the price paid per unit of collateral (in terms of liability tokens) is entirely determined by whatever the oracle reports when the transaction lands. The project's own documentation acknowledges this: "Most liquidators will set this number conservatively, since prices may change by the time liquidation lands" [3](#0-2) . This is the same missing-safeguard class as in the referenced report: the liquidator has no way to specify a maximum liability price they are willing to pay, so if the transaction is delayed, reordered, or lands later than intended (e.g. due to network congestion, priority-fee competition, or oracle price updates arriving in between), the liquidator can be charged more liability tokens per unit of seized collateral than they anticipated when constructing the transaction.

This contrasts with comparable liquidation designs referenced elsewhere in the same codebase's IDLs (e.g. Drift's `liquidate_spot` / `liquidate_borrow_for_perp_pnl`, which take an explicit `limit_price: Option<u64>` argument) [4](#0-3)  and [5](#0-4) , showing that a limit-price parameter is a recognized mitigation missing from marginfi's classic liquidation path.

By contrast, the newer receivership liquidation flow does enforce a bound protecting the liquidatee from over-extraction (`seized <= repaid * max_fee`), but this protects the liquidatee's health, not the liquidator's price exposure, and does not give the liquidator any way to specify a maximum acceptable liability price either [6](#0-5) .

### Impact Explanation
A liquidator submitting `lending_account_liquidate` sized based on current oracle prices can end up paying a materially worse liability amount than expected if the price moves (or the tx lands later than expected) before execution, since the instruction has no user-supplied ceiling on `liab_amount_liquidator`. This is a direct, unprivileged, permissionless-caller economic exposure with financial effect (overpayment), matching the impact class described in the referenced report. It does not affect protocol solvency, but it exposes any liquidator interacting with the permissionless liquidation instruction to unexpected loss of value.

### Likelihood Explanation
`lending_account_liquidate` is a permissionless instruction callable by any account holder with an existing marginfi account; oracle price movement between transaction construction and landing is a routine occurrence (not a theoretical edge case) given oracle refresh cadence requirements and mempool/priority-fee dynamics, making this readily reachable in normal liquidator operation rather than a purely theoretical scenario.

### Recommendation
Add an optional liquidator-specified bound (e.g. `max_liab_amount` or `min_asset_price`) to `lending_account_liquidate`, and enforce it against the computed `liab_amount_liquidator` (or equivalent effective price) before completing the accounting changes, causing the instruction to fail if the realized price exceeds the liquidator's specified tolerance — mirroring the `limit_price` pattern already used by comparable protocols such as Drift.

### Proof of Concept
1. Liquidator observes an unhealthy account and computes an expected `liab_amount_liquidator` based on current oracle prices for a chosen `asset_amount`.
2. Liquidator submits `lending_account_liquidate(asset_amount, ...)` per [7](#0-6) .
3. Before the transaction executes, the oracle price for the liability token rises (or asset token price falls) due to normal market movement or update timing.
4. The instruction recomputes `liab_amount_liquidator` from the new price at execution time [8](#0-7)  and the liquidator's account is debited more liability than they intended, with no instruction-level check to prevent or bound this, since no max-price argument exists.
