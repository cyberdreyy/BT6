### Title
Unsigned Nonce-Account Front-Running via Missing Authority Binding in `InitializeNonceAccount` - (File: programs/system/src/system_instruction.rs)

### Summary
The System Program's `InitializeNonceAccount` instruction sets a nonce account's authority without requiring any signature or ownership check tied to the account creator, only that the account is writable and in `State::Uninitialized`. If the two-step "create-then-initialize" nonce account setup (`CreateAccount` followed by `InitializeNonceAccount`) is ever split across separate transactions instead of bundled atomically, an attacker can race to submit `InitializeNonceAccount` first, installing themselves as the `nonce_authority`. This is the exact same bug class as the Ramses report: a multi-step deployment/initialization sequence that is not enforced atomically on-chain, allowing a third party to call the "initialize" step with attacker-controlled parameters before the legitimate caller does.

### Finding Description
`initialize_nonce_account` only checks that the target account is writable and currently `State::Uninitialized`; it performs no check that the caller or transaction is authorized by whoever funded/created the account: [1](#0-0) 

By contrast, the earlier `CreateAccount` step does enforce that the new account's own key must sign (`address.is_signer(signers)` inside `assign`/`allocate_and_assign`): [2](#0-1) 

The dispatch code for `SystemInstruction::InitializeNonceAccount` confirms no additional signer requirement is imposed beyond what `initialize_nonce_account` checks — it only requires the RecentBlockhashes and Rent sysvars and the account itself to be writable, not signed: [3](#0-2) 

The standard SDK helper `system_instruction::create_nonce_account` mitigates this by bundling `CreateAccount` and `InitializeNonceAccount` into the same instruction list/transaction, and the CLI follows this same pattern: [4](#0-3) 

However, this atomicity is a convention enforced only by client tooling, not by the runtime. Nothing in `initialize_nonce_account` or the System Program dispatcher prevents `InitializeNonceAccount` from being submitted as an independent transaction against any system-owned, rent-exempt, correctly-sized (`State::size()`), still-`Uninitialized` account — exactly analogous to how Ramses V3's `RamsesV3Factory.initialize` could be called by an attacker with a wrong deployer address before the legitimate atomic sequence completed.

### Impact Explanation
If a caller (wallet, exchange backend, program, or any tooling that does not follow the SDK's atomic `create_nonce_account` helper) creates a nonce account in one transaction and initializes it in a later, separate transaction, an attacker monitoring the mempool/ledger can submit their own `InitializeNonceAccount` instruction for that account address first, setting themselves as `nonce_authority`. Once initialized with an attacker-controlled authority, the attacker can later call `WithdrawNonceAccount`, which requires only `check_signer(&data.authority)` — satisfied by the attacker's own key — to drain the account's lamports: [5](#0-4) 

This results in concrete unsigned/unauthorized fund movement from the perspective of the account's actual creator/funder: the funds only ever needed the attacker's own signature because the authority binding was hijacked during the initialization race.

### Likelihood Explanation
Likelihood is low-to-moderate in practice because the canonical SDK path (`system_instruction::create_nonce_account`, used by `solana-cli`) already bundles both instructions atomically in one transaction, which fully closes the window. The risk only materializes for integrators (custom wallets, multisig/hardware-signing flows, or programs that construct nonce accounts across multiple transactions/CPI boundaries) that deviate from the atomic helper and submit `CreateAccount` and `InitializeNonceAccount` separately — mirroring precisely the "unless these steps are executed atomically" caveat from the Ramses report.

### Recommendation
Since this mirrors a known, accepted design tradeoff of Solana's nonce account model (rather than a regression), the practical mitigation is the same one recommended in the source report: enforce atomicity. Concretely:
- Continue to strongly recommend (and, where possible, enforce in higher-level SDKs/wallet UX) that `CreateAccount` and `InitializeNonceAccount` always be submitted together in a single transaction, never split across transactions.
- Consider whether `initialize_nonce_account` should additionally require a signature from the account's own key (similar to `CreateAccount`'s `assign` check) to bind initialization to the original creator, closing the front-running window at the protocol level rather than relying solely on client convention.

### Proof of Concept
1. Victim submits Transaction A: `SystemInstruction::CreateAccount` creating account `N` (owned by System Program, sized `State::size()`, funded to be rent-exempt), intending to initialize it as a nonce account in a follow-up transaction.
2. Before the victim's follow-up transaction lands, an attacker observes account `N` on-chain (funded, system-owned, `State::Uninitialized`) and submits their own Transaction B containing `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` naming `N` as the writable account (no signature from `N`'s keypair is required per `initialize_nonce_account`/`system_processor.rs` dispatch shown above).
3. Transaction B lands first; `N`'s nonce state becomes `Initialized` with `authority = attacker_pubkey`.
4. The victim's original `InitializeNonceAccount` transaction now fails with `InstructionError::InvalidAccountData` (already `Initialized`), per the `State::Initialized(_) => Err(InvalidAccountData)` branch.
5. After a slot advances (so `durable_nonce` differs), the attacker submits `SystemInstruction::WithdrawNonceAccount(full_balance)` signed only by `attacker_pubkey`, which passes `check_signer(&data.authority)` and transfers all of `N`'s lamports to an account the attacker controls.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

fn assign(
    account: &mut BorrowedInstructionAccount,
    address: &Address,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    // no work to do, just return
    if account.get_owner() == owner {
        return Ok(());
    }

    if !address.is_signer(signers) {
        ic_msg!(invoke_context, "Assign: account {:?} must sign", address);
        return Err(InstructionError::MissingRequiredSignature);
    }

    account.set_owner(&owner.to_bytes())
}

fn allocate_and_assign(
    to: &mut BorrowedInstructionAccount,
    to_address: &Address,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    allocate(to, to_address, space, signers, invoke_context)?;
    assign(to, to_address, owner, signers, invoke_context)
}

#[allow(clippy::too_many_arguments)]
fn create_account(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    to_address: &Address,
    lamports: u64,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(
                invoke_context,
                "Create Account: account {:?} already in use",
                to_address
            );
            return Err(SystemError::AccountAlreadyInUse.into());
        }

        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(
        from_account_index,
        to_account_index,
        lamports,
        invoke_context,
        instruction_context,
    )
}
