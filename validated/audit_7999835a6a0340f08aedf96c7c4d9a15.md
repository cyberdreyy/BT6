### Title
Signer vote-flip (Reject→Accept) permanently inflates a block's rejected-weight tally in the mining coordinator, causing spurious `SignersRejected` on a block that should reach consensus - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The `StackerDBListener::run()` loop tallies per-block signer weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, guarded by two *different* de-duplication keys (`gathered_signatures` for the approve path, `responded_signers` for the reject path). When a signer first rejects and later accepts the *same* block (a normal, doc-sanctioned re-evaluation flow), the accept path only checks `gathered_signatures` before adding weight, and never clears or checks the earlier `total_weight_rejected` contribution recorded from that signer's rejection. The stale rejected weight is never retracted, so it stays counted forever, alongside the now-added approved weight for the same signer.

### Finding Description
`stackerdb_listener.rs` maintains, per block hash, a `BlockStatus { responded_signers, gathered_signatures, total_weight_approved, total_weight_rejected, .. }`.

Accept path ( [1](#0-0) ):
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```
Reject path ( [2](#0-1) ):
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```

The accept branch's guard (`gathered_signatures.contains_key`) is blind to whether this `slot_id` already contributed weight through the *reject* branch's `responded_signers` set. Consequently:

1. Signer S (weight `w`) rejects block B first → `responded_signers += {S}`, `total_weight_rejected += w`.
2. S's local signer later re-evaluates B (e.g. a conflict it was blocking on goes stale, per the `HOLD1 → OWN → SIGN` transition documented in [3](#0-2)  and re-sends its verdict), and sends a legitimate `BlockAccepted` with a valid signature over the same block hash.
3. The accept branch sees `gathered_signatures` does not yet contain S's slot, adds `w` to `total_weight_approved`, and inserts S into `gathered_signatures`/`responded_signers` (no-op on the latter, since already present).
4. `total_weight_rejected` is **never decremented**; S's weight is now counted in both totals simultaneously and permanently.

This breaks the intended invariant that each signer's weight is attributed to exactly one side of the "aggregated-weight vs verified-accepts/-rejects" equality that the mining coordinator relies on to decide a block's fate ( [4](#0-3) , checked against `EzraCole/stacks-core--005`). If enough weight (including S's stale, retracted rejection) crosses the blocking-minority line, `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` fires and the coordinator returns `NakamotoNodeError::SignersRejected`, permanently killing that block proposal, even though the live, current set of signer opinions (after S's flip) may in fact clear the 70% approval bar.

### Impact Explanation
This is a liveness wedge in the node-side mining coordinator/`StackerDBListener` (explicitly in-scope per the rules). A single signer that initially rejects for a transient reason (stale sortition view, in-flight conflict, timing) and then legitimately re-accepts once its local state clears — a flow the signer explicitly supports (`should_reevaluate_block`, `HOLD1`→`SIGN` in the pre-commit conflict logic) — leaves a permanent, uncleared rejection weight in the coordinator's tally. Combined with any other signers' rejections that are also stale/retracted the same way, or simply add up, this can push `total_weight_rejected` over the 30% blocking-minority threshold and cause the coordinator to declare the block dead (`SignersRejected`) even though a live majority (≥70% weight) would currently sign it. This stalls block production for that tenure/proposal without requiring a majority of malicious signers or any signature forgery — a single flip-voting signer (attacker-influenced or simply reacting to normal chain events) is sufficient to trigger the miscount.

### Likelihood Explanation
No majority collusion is required — a single signer's ordinary reject→accept sequence (a supported, documented state transition) triggers the bug. The reject→accept path is explicitly designed for and exercised by the signer's own re-evaluation logic (`check_block_against_signer_db_state`, `HOLD1`/`OWN`/`SIGN` in `handle_block_pre_commit`), so this is a routine, one-slot-triggerable sequence, not a contrived edge case, making it readily reachable in normal or lightly-adversarial network conditions (e.g. a signer intentionally delaying its own re-evaluation, or a byzantine one-slot miner/signer sending a reject then withdrawing it via accept to inflate the stale rejected tally against future proposals for the same block hash).

### Recommendation
Track weight attribution per slot with a single source of truth (e.g. an enum `Approved(Signature) | Rejected(reason)` keyed by `slot_id`) instead of two independently-guarded counters/sets. On receiving an `Accepted` for a slot that is already present with a `Rejected` entry, subtract the previously-added weight from `total_weight_rejected` before adding it to `total_weight_approved` (and vice versa if a later `Rejected` should be allowed to retract an `Accepted`, matching the documented "a rejection is a revocable opinion" semantics in `signer-flows.md`). At minimum, add a check for prior rejection tally in the accept branch and appropriately roll it back.

### Proof of Concept
1. Configure a reward-cycle with signer weights so that no single signer exceeds the 30% blocking-minority threshold alone, but two signers together do (e.g. weights `[25, 20, 55]`, threshold 70).
2. Signer A (weight 25) sends `BlockResponse::Rejected` for block B → `total_weight_rejected = 25`.
3. Signer B (weight 20) sends `BlockResponse::Rejected` for block B → `total_weight_rejected = 45` (still < 30 blocking minority relative to 100 total... adjust weights to be just under threshold so this step alone doesn't yet reject).
4. Signer A's local signer re-evaluates B (conflict clears) and sends a valid `BlockResponse::Accepted` with its real signature over B.
5. Per `stackerdb_listener.rs` accept branch, `total_weight_approved` becomes 25, but `total_weight_rejected` remains 45 (A's earlier rejection is never subtracted).
6. Now Signer C's weight can push `total_weight_rejected` (still counting stale A weight) past `total_weight - weight_threshold`, causing `signer_coordinator.rs`'s wait loop to return `SignersRejected` for a block that, in the *current* signer opinion set (A accepted, only B truly rejects), should not have been globally rejected — demonstrating the stale/duplicated weight tally.
