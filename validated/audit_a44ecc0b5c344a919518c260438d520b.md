## Confirmed: this is the exact analog of the OS-Command-Injection bug class

The report's pattern is "a check that exists is skipped because a *weaker* re-implementation of the same check is consulted instead of the authoritative one." The direct analog is the v1 vs v2 asymmetry between `get_last_signed_block` and `get_last_globally_accepted_block`, combined with the fail-open own-tenure staleness path in `handle_block_pre_commit`.

### Title
A single miner can make a v1-protocol signer equivocate (sign two conflicting tenure-start blocks in the same tenure) — ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (v1 chainstate) rejects a duplicate tenure-change proposal only if a block in the same tenure has already reached `get_last_globally_accepted_block` [1](#0-0) . It never checks `get_last_signed_block`, which also includes `LocallyAccepted` blocks. This is a strictly weaker check than the v2 equivalent (`get_last_signed_block`, covering local+global) [2](#0-1) , and the docs explicitly flag this asymmetry [3](#0-2) .

### Finding Description
A miner proposes tenure-change block **A** for tenure T. A single signer validates it, pre-commits, and — once the pre-commit/signature thresholds are met from its own perspective — signs it (`mark_locally_accepted`, `signed_self` set) [4](#0-3) . Suppose A never reaches the *node* (e.g. the group signature threshold stalls because other signers are slow/partitioned) — a locally-accepted block is not handed to the node until the whole set has signed [5](#0-4) .

The same miner now proposes a **second, different** tenure-change block **B** for the *same* tenure T. At proposal time, v1's duplicate check only looks at `get_last_globally_accepted_block`, which is still `None` (A was only locally accepted) — so `DuplicateBlockFound` never fires [1](#0-0) . `check_block_against_signer_db_state` at validate-ok time only re-checks the *parent* tenure for tenure-change blocks, never the block's own tenure [6](#0-5) , so B is also validated and pre-committed.

The only remaining backstop is the pre-commit-time conflict check (`get_signed_conflicts`) [7](#0-6) . While A is *fresh* (within `tenure_last_block_proposal_timeout`), it blocks signing B. But once that window elapses, A becomes "stale," and the code falls through to the own-tenure stale-conflict check, which asks the **node** whether the tenure's tip is already at/above B's height [8](#0-7) . Since A was never pushed to the node (it stalled below the global signature threshold), `get_tenure_tip` shows nothing at that height, so the check does **not** block, and the signer signs B: `mark_locally_accepted(false)` [9](#0-8) .

The signer has now placed a signature over two mutually-exclusive blocks (A and B) at the same height in the same tenure — a direct equivocation. This breaks the "signed vs validated" / "one-per-height" equality the state machine is built to guarantee, purely through a single miner's proposal timing, using a genuine v1-only gap (`get_last_globally_accepted_block` instead of `get_last_signed_block`) that the v2 code path already closes.

### Impact Explanation
This is a **Critical** finding under the stated impact taxonomy: a signer signing a conflicting block (equivocation) via the loophole in the tenure-duplicate check. If enough v1 signers hit the same stall/timeout independently (each individually delayed, no majority collusion required — just natural asynchrony/partition), the second block B can accumulate its own competing signature set, producing two co-signed, mutually exclusive blocks at the same height.

### Likelihood Explanation
Requires: (1) a v1-protocol-era signer/reward-cycle, (2) the malicious/single miner controlling the winning slot to re-propose a distinct tenure-change block for its own tenure, and (3) A's group signature to stall past `tenure_last_block_proposal_timeout` before reaching the node. All of this is achievable by one miner plus normal network asynchrony — no other signer's key or majority collusion is needed. Likelihood is moderate: it depends on timing (A must go unstale) but is fully attacker-triggerable since the miner controls when to submit B.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace the `get_last_globally_accepted_block` duplicate check with `get_last_signed_block` (as v2 does), so a locally-accepted-but-not-yet-globally-accepted block in the same tenure is treated as a duplicate at proposal time, matching v2 semantics and closing the gap before it ever reaches the pre-commit staleness fallback.

### Proof of Concept
1. Bring up a v1-protocol-era signer set with one signer (S) and a byzantine miner M.
2. M wins the sortition for tenure T and proposes tenure-change block A. S validates, pre-commits, and (assume other signers slow to respond) signs A locally (`signed_self` set), but A never reaches the group signature threshold and is never pushed to S's node.
3. Wait past `tenure_last_block_proposal_timeout`.
4. M proposes a second, different tenure-change block B for the same tenure T (same parent tenure, different content/txs).
5. Observe: `validate_tenure_change_payload` (v1.rs) checks only `get_last_globally_accepted_block(T)` → `None` → no `DuplicateBlockFound`. B is submitted for validation and passes `check_block_against_signer_db_state` (only checks parent tenure). At pre-commit, A is now stale, `get_tenure_tip(T)` on the node returns nothing at B's height (A was never posted) → the own-tenure stale guard does not block → S signs B via `mark_locally_accepted`.
6. S has now signed both A and B — a same-height, same-tenure signature conflict.
