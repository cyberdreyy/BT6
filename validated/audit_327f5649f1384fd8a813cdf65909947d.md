### Title
Missing duplicate-registration check in `savedCallbacks` map allows cross-user response hijacking via MessageId reuse - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` registers a user's callback in `h.savedCallbacks` keyed only by the attacker-controllable `msg.Body.MessageId`, with no check for an existing/pending entry, unlike the sibling `confidentialrelay` handler which explicitly rejects duplicate IDs. Because lookup/delivery in `handleWebAPITriggerMessage` is also keyed purely by `MessageId` with no per-registration token, a second request (attacker's) using the same `MessageId` as a still-outstanding legitimate (victim's) request silently overwrites the map slot, and the DON's later response intended for the victim is delivered to the attacker's callback instead.

### Finding Description
`api.Message.Validate()` (`core/services/gateway/api/message.go:54-88`) only checks length/format of `MessageId`; it enforces no uniqueness across senders. The gateway entrypoint `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) forwards any signed request with a valid-length `MessageId` straight to `h.HandleLegacyUserMessage`, so an attacker fully controls the `MessageId` string for their own signed request.

In `core/services/gateway/handlers/capabilities/handler.go:411-412`:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
```
this unconditionally overwrites any existing entry for that `MessageId` — there is no "already exists" guard (compare with `confidentialrelay`'s handler, which explicitly returns `"request ID already exists"` on duplicate IDs).

Delivery in `handleWebAPITriggerMessage` (`core/services/gateway/handlers/capabilities/handler.go:148-162`) is:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
```
It matches purely on `MessageId`; there is no per-registration token/nonce tying the specific outbound request instance to the specific saved callback, so whichever registration currently occupies the map slot receives the response.

Exploit flow:
1. Victim submits a signed `HandleLegacyUserMessage` request with `MessageId = "X"`; handler registers `savedCallbacks["X"] = victimCallback` and dispatches the trigger to all DON members.
2. Before the DON responds (or, per the question, right as `pruneCallbacks` evicts a stale/expired "X" entry, or simply while "X" is still outstanding since there is no dedup check at all), the attacker submits their own signed request also using `MessageId = "X"`.
3. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with `attackerCallback`.
4. A DON node's legitimate, correctly-signed response to the victim's original trigger later arrives via `HandleNodeMessage` → `handleWebAPITriggerMessage`. The sender/nodeAddr check (`msg.Body.Sender != nodeAddr`) passes because it's a genuine DON node responding to a request that legitimately carries `MessageId = "X"`.
5. The lookup finds `attackerCallback` (the current occupant of slot "X") and delivers the victim's DON response — including any payload the victim expected only to receive — to the attacker.

This is a real cross-user response confusion bug, not merely dependent on the prune-timing race described in the question; the missing duplicate check makes the window exploitable at any time the victim's request is in-flight, and the described `pruneCallbacks()`-adjacent scenario is simply one variant (a slot freed by pruning is equally susceptible to being claimed by an attacker before/while a legitimately late response for the original registration is still in transit from a slow DON node, since `pruneCallbacks` removes the map entry but does not signal in-flight `SendToNode` calls or cancel the pending DON dispatch).

### Impact Explanation
Cross-user response leakage: an unauthenticated (but request-signing) attacker can, by choosing a `MessageId` that collides with a targeted victim's in-flight or recently-expired request, cause the DON's response payload (which may include workflow trigger results tied to the victim's request) to be delivered to the attacker's own callback/HTTP connection instead of the victim's. This maps to Chainlink's "cross-user response confusion" bounty impact class — unauthorized disclosure of another user's response data via the gateway.

### Likelihood Explanation
Requires the attacker to know or predict a targeted victim's exact `MessageId` and to time their own request submission to coincide with the victim's outstanding registration window (bounded by DON response latency, or by `CallbackMaxAgeSec`/`CallbackPruneIntervalSec` around pruning). No privileged credentials are needed beyond the ability to sign and submit a gateway request (any address with a valid ECDSA key can sign per `Message.Sign`). Feasibility is moderate-to-low in practice because it depends on `MessageId` predictability/observability, but the underlying code defect (no duplicate-registration check) removes what should be the primary safeguard, making exploitation only a matter of timing/knowledge rather than a cryptographic or authorization bypass. Repeatable: attacker can retry the race for any known/observed pending `MessageId`.

### Recommendation
- In `HandleLegacyUserMessage`, check for an existing entry in `h.savedCallbacks[msg.Body.MessageId]` before inserting and reject the request (mirroring the `confidentialrelay` handler's `"request ID already exists"` behavior) instead of silently overwriting.
- Replace the map value type or add a monotonically-increasing per-registration token (e.g., store a `registrationSeq`) and verify, in `handleWebAPITriggerMessage`, that the delivered response's originating request matches the same registration token that dispatched it to the DON — not merely the same `MessageId`.
- Ensure `pruneCallbacks()` eviction of a `MessageId` also invalidates/cancels any still in-flight `don.SendToNode` calls tied to that registration so a late DON response cannot be matched to a newer registrant occupying the same key.

### Proof of Concept
Go test plan (handler-level, in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Set up `handler` via `setupHandler(t)` with a mocked `don.SendToNode` that captures the outbound request per call.
2. Register victim: call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCb)` with `MessageId = "X"`, signed by victim's key. Assert `handler.savedCallbacks["X"]` is registered and points at `victimCb` (via reflection or by triggering a response).
3. Before delivering the DON response, call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb)` with the same `MessageId = "X"`, signed by an attacker key. Assert (bug reproduction) that `handler.savedCallbacks["X"]` now points at `attackerCb`.
4. Simulate the DON's legitimate response to the victim's original request: build a valid signed response message with `MessageId = "X"` and a node address from `donConfig.Members`, call `handler.HandleNodeMessage(ctx, resp, nodeAddr)`.
5. Assert that `attackerCb.Wait(ctx)` receives the response payload (proving hijack) while `victimCb.Wait(ctx)` times out / never receives a response — demonstrating the invariant violation ("no cross-user callback delivery across pruning/registration boundaries") is broken.
6. Add a second variant of the test that instead uses `handler.pruneCallbacks()` to evict `"X"` after `CallbackMaxAgeSec`, then has the attacker re-register `"X"` immediately after pruning and before the late DON response for the victim's original send arrives, asserting the same cross-delivery occurs — validating the pruning-adjacent scenario from the question specifically. func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
