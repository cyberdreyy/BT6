### Title
Loss-adjusted withdraw receipts are re-evaluated at par once the user files any later request, letting them drain other receipt holders' funded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Nuclei bug is a two-pass evaluation flaw: a value is substituted once, then reinterpreted in a second pass where attacker-influenced data escapes its original context. The idle-tranches analog is in `claimWithdrawRequest`: a withdrawal receipt that was haircut by `collectWithdrawFunds` (stored per-epoch in `lossRecoveryPriceByEpoch`) is only cleared through `_claimLossAdjustedWithdrawRequest`, which locates the loss epoch exclusively via the mutable `lastWithdrawRequest[_user]`. Because a second `requestWithdraw` overwrites `lastWithdrawRequest`, the haircutted receipt is silently re-interpreted as a plain funded receipt and paid at par by `_claimFundedWithdrawRequest`, breaking the "one receipt, one (haircutted) payout" invariant.

### Finding Description
1. `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws` writes `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and sets `pendingWithdraws = 0` (lines 411-421). Only `_amount` (the haircutted sum) is transferred into the strategy to back all receipts of that epoch.
2. On claim, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` and looks up `lossRecoveryPriceByEpoch[lossEpoch]` (lines 789-792). If the user's most recent request is *not* the loss epoch, the lookup returns 0 and the haircutted receipt is never cleared.
3. Execution falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` — the aggregate full (un-haircutted) basis including the loss-epoch receipt — after only checking `epochNumber > lastWithdrawRequest[_user]` (lines 326-349).

Concretely: attacker requests a withdraw in epoch N; the manager legitimately calls `stopEpochWithDuration`/`collectWithdrawFunds` realizing a loss, so receipts are funded only at price `p < 1`. The attacker then calls `requestWithdraw` with a dust amount in epoch N+1, overwriting `lastWithdrawRequest` to N+1. After that epoch ends, `claimWithdrawRequest` skips the loss-adjusted path (`lossRecoveryPriceByEpoch[N+1] == 0`) and pays `withdrawsRequests[attacker]` at par. The strategy only ever received `B * p` for the loss-epoch basis `B`, so the excess `B * (1 - p)` is paid out of other users' funded claims held in the same strategy balance; subsequent honest claimants' `_transferFundedClaim` calls revert on insufficient balance.

This mirrors the Nuclei flaw exactly: data fixed in a first pass (the haircut applied at `collectWithdrawFunds`) is reinterpreted on a second pass (the funded-claim path) because the lookup key (`lastWithdrawRequest`) was re-substituted by attacker-controlled input (a new dust request).

### Impact Explanation
Direct theft plus freezing of unclaimed funds. Every user with a haircutted receipt from the loss epoch shares one funded pool of `pendingBasis * p`. An attacker claiming at par extracts `B * (1 - p)` more than funded, i.e. steals `(1 - p)` fraction of their basis from other receipt holders; if the attacker holds a large share of epoch-N receipts, they can drain the entire funded pool, leaving remaining claimants permanently unable to claim (transfer underflow/insufficient balance). Loss magnitude is `min(attackerBasis * (1 - p), poolReserves)` — with a 50% realized loss the attacker doubles their claim.

### Likelihood Explanation
Requires a real loss event via `stopEpochWithDuration`/partial `collectWithdrawFunds` — an honest-manager action that occurs whenever the borrower underpays, so the preconditions arise naturally in this protocol's lifetime. The attacker needs only two `requestWithdraw` calls (one before, one dust-sized after the loss epoch) plus waiting one epoch — all unprivileged tranche-holder actions. No guard prevents it: `defaultRecoveryInitialized` is already true (required for the loss path itself), `lastWithdrawRequest` is unconditionally overwritten in `requestWithdraw` (line 282), and `_claimLossAdjustedWithdrawRequest` never scans other epochs with nonzero `lossRecoveryPriceByEpoch` and nonzero `withdrawsRequestsByEpoch`.

### Recommendation
Do not key loss-adjusted claims solely on `lastWithdrawRequest`. Either iterate/check `lossRecoveryPriceByEpoch` for every epoch with nonzero `withdrawsRequestsByEpoch[_user][e]`, or store a per-user flag/bitmap of epochs with outstanding loss-adjusted receipts and clear them before the funded path runs. Alternatively, prevent `requestWithdraw` from overwriting `lastWithdrawRequest` while the user has an uncleared loss-adjusted receipt (or force-settle the loss-adjusted claim inside `requestWithdraw`/`_requestWithdrawApr0`).

### Proof of Concept
Foundry fork PoC sketch (mainnet fork, existing `IdleCreditVault.t.sol` harness):

```solidity
function testLossAdjustedReceiptClaimedAtParAfterReRequest() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    address attacker = makeAddr('attacker');
    address victim = makeAddr('victim');

    // both deposit AA and both request withdraw in epoch N
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _depositWithUser(victim,   10_000 * ONE_SCALE, true);
    vm.prank(attacker); cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(victim);   cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // borrower funds only 50% of pendingWithdraws -> lossRecoveryPrice = 0.5e18
    IdleCreditVault strat = IdleCreditVault(address(strategy));
    uint256 pending = strat.pendingWithdraws();
    deal(defaultUnderlying, borrower, pending / 2);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(...); // half-funded path -> collectWithdrawFunds(pending/2)
    assertEq(strat.lossRecoveryPriceByEpoch(strat.epochNumber()), RECOVERY_FULL / 2);

    // attacker re-requests dust in the new buffer, overwriting lastWithdrawRequest
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // or new deposit+request

    _startEpochAndCheckPrices(2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // fund the dust request normally
    deal(defaultUnderlying, borrower, strat.pendingWithdraws() + dustInterest);
    vm.prank(manager);
    cdoEpoch.stopEpoch(...);

    // attacker claims FULL basis: loss-adjusted path skipped because
    // lossRecoveryPriceByEpoch[lastWithdrawRequest] == 0
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(attacker) - balBefore;

    uint256 attackerBasis = /* full epoch-N basis */;
    assertGt(claimed, attackerBasis / 2 + dust, "claimed above haircutted amount");

    // victim's claim now reverts / underpays: pool drained
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Note: exact `stopEpochWithDuration` arguments and the dust deposit step depend on harness helpers (`_stopEpochAndCheckPrices` variants) in `test/foundry/IdleCreditVault.t.sol`; the core sequence — request in epoch N, partial funding at `p < 1`, dust `requestWithdraw`, wait one epoch, `claimWithdrawRequest` pays full `withdrawsRequests` — is what triggers the bug. I verified the claim-path logic in `IdleCreditVault.sol` (lines 271-350, 411-430, 786-801); I did not fully trace `stopEpochWithDuration` in `IdleCDOEpochVariant.sol` to confirm the exact call ordering that reaches `collectWithdrawFunds` with partial funding, so the PoC wiring may need adjustment around that entry point.
