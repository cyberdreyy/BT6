### Title
Multisig confirmations counted against removed members allow request execution below the live threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in `multisig2/src/lib.rs` removes a member from `self.members` and purges only the outstanding *requests authored by* that member, but it never scans existing `confirmations` sets on other pending requests to strip that member's prior confirmation. As a result, a confirmation cast by a member who is later removed continues to count toward `num_confirmations` on any other request they had already confirmed, letting the remaining live members execute that request with fewer *live* confirmations than the multisig's configured threshold requires.

### Finding Description
`confirm()` counts confirmations purely from the `HashSet<String>` stored in `self.confirmations` keyed by request id, checking only `confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) . It never re-validates that each entry in that set still belongs to a current member of `self.members`.

`delete_member` only cleans up requests where `r.member == member` (i.e., requests the removed member *authored*), and only clears confirmations tied to those specific request ids: [2](#0-1) 
It does not iterate `self.confirmations` to strip the removed member's string from confirmation sets belonging to *other* pending requests that this member had already confirmed but did not author.

Consequently the binding "confirmations counted == confirmations from live members" is broken: once a member is removed, any request they confirmed earlier still holds their confirmation as valid evidence toward `num_confirmations`, even though `current_member()` would now reject that member from confirming anything new [3](#0-2) .

### Impact Explanation
This lets a multisig request (e.g. a `Transfer` moving NEAR, or an `AddKey`/`AddMember` action) execute with fewer than `num_confirmations` *live* signers - the exact "multisig request executed below threshold" Critical impact category. For example, in a 3-of-4 multisig, if a since-removed member had already confirmed a pending `Transfer` request before being removed, only 2 remaining live members need to confirm afterward for it to execute, even though the intent of removing that member (e.g., due to key compromise) was to no longer trust their authorization for pending fund movements.

### Likelihood Explanation
This requires no privileged access beyond being (or having been) a legitimate multisig member/access key at some point — it is triggered by the normal, expected sequence: (1) member A confirms request X (but does not push it over threshold), (2) the multisig later removes member A via a legitimate `DeleteMember` action (e.g., key rotation, offboarding, suspected compromise), and (3) remaining members confirm X to execute it. No malicious deployment or foundation/owner privilege is needed beyond the standard multisig member confirm flow; it's a straightforward oversight in bookkeeping reachable via ordinary usage.

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` (not just requests authored by the removed member) and remove the deleted member's string entry from every confirmation set. Alternatively, validate membership of every entry in a request's confirmation set at `confirm()` time (i.e., recompute `confirmations.len()` counting only entries whose corresponding member is still present in `self.members`) before comparing against `self.num_confirmations`.

### Proof of Concept
1. Initialize a `multisig2` contract with 4 members (A, B, C, D) and `num_confirmations = 3`.
2. Member A calls `add_request` to create a `Transfer` request X to some receiver.
3. Member B calls `confirm(X)` → confirmations = {B}, len=1, request not executed (1 < 3).
4. Members create and confirm a `DeleteMember { member: B }` request (via existing legitimate flow) and it executes: `delete_member` runs, removes B from `self.members`, but since B did not author request X, `self.confirmations` for X is untouched and still contains B's entry — see `delete_member`'s filter `r.member == member` at [4](#0-3) .
5. Now live members are {A, C, D}, requiring 3 live confirmations for threshold 3. But request X already has B's stale confirmation counted.
6. Member C calls `confirm(X)` → `confirmations.len() (1, from B) + 1 = 2`, still below 3, but only 1 live confirmation (C) plus 1 phantom (B) is now recorded.
7. Member D calls `confirm(X)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` runs and the transfer executes, even though only C and D (2 live members) plus the ghost of removed B actually contributed, never reaching 3 genuine live confirmations.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
