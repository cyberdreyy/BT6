## Finding: Missing registration check in `staking_contract::set_beneficiary_for_operator` permanently bricks distribution and traps staker funds

The external report's bug class — a downstream step that fails after already-committed state changes, permanently stranding user funds — has a direct analog in `aptos_move/framework/aptos-framework/sources/staking_contract.move`.

### Root cause
`vesting.move::set_beneficiary` explicitly guards against this exact class of bug: [1](#0-0) 

The comment says this check exists "so `distribute()` wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered."

However, `staking_contract.move`'s own `set_beneficiary_for_operator` — which controls who actually receives operator commission at distribution time — has **no equivalent check**: [2](#0-1) 

### Why this breaks the lockup/distribution invariant
`distribute_internal` pays out every recipient queued in `distribution_pool` in a single atomic loop, resolving the operator's payout address dynamically via `beneficiary_for_operator(operator)` at payout time, and depositing with `aptos_account::deposit_coins`: [3](#0-2) 

If `beneficiary_for_operator(operator)` resolves to an account that cannot accept an un-registered/direct APT deposit (e.g., an account that called `aptos_account::set_allow_direct_coin_transfers(false)` and never registered a `CoinStore<AptosCoin>`), `aptos_account::deposit_coins` aborts. Because the loop is atomic, **that single failing recipient aborts the entire distribution for every other shareholder in the pool, including the staker.**

Crucially, `distribute_internal` is not only invoked from the public `distribute` entry function — it's also called as the first step of `unlock_stake`, `request_commission`, and `switch_operator`: [4](#0-3) [5](#0-4) 

This means once an operator sets a poisoned beneficiary and there is any non-zero pending distribution amount recorded under that operator in `distribution_pool`, **every subsequent call to `unlock_stake`, `request_commission`, `switch_operator`, or `distribute` on that staking contract will revert**, since they all invoke `distribute_internal` first.

### Impact
The staker has no recourse: they cannot withdraw their own already-unlocked/inactive stake (`unlock_stake`/`distribute` revert), and cannot even escape the malicious/misconfigured operator (`switch_operator` also calls `distribute_internal` on the old operator's contract before removal, so it reverts too). This traps the staker's principal and rewards indefinitely — a permanent, non-recoverable loss of withdrawal/claim rights, triggerable entirely by the operator (a role the staker already granted for validation duties, not for controlling fund liquidity), or even accidentally if the operator's beneficiary account happens to have direct transfers disabled.

### Recommendation
Add the same registration/acceptance guard used in `vesting.move::set_beneficiary` to `staking_contract::set_beneficiary_for_operator`, requiring `new_beneficiary` to be registered/able to accept direct AptosCoin deposits before allowing the beneficiary change. Alternatively, make `distribute_internal` resilient to a single failing recipient (e.g., skip/queue that portion rather than aborting the whole loop), similar to how the "dust to staker" fallback path already isolates unrelated logic.

### Caveat
I could not directly view the body of `aptos_account::deposit_coins` in this session (only its declaration and related constants were found), so the exact abort condition (`EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`) is inferred from the constant definitions in `aptos_account.move` and confirmed indirectly by the defensive check already present in `vesting.move`'s `set_beneficiary`, which exists specifically to avoid this failure mode. A background Devin session with full repo access should verify `deposit_coins`' exact abort semantics to fully confirm the PoC before remediation. [6](#0-5)

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
