### Title
APR0 interest claims are committed to `IdleCreditVault` before the fallible borrower pull in `stopEpoch`, so a defaulted epoch persists phantom interest claims that dilute default recovery - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
In `_stopEpoch` the strategy call `prepareStopEpochWithApr0` is executed **before** the only fallible external call (`try this.getFundsFromBorrower`). That call permanently writes `pendingWithdraws += _apr0NetInterest`, `apr0RateByEpoch[epochNumber]`, and clears `apr0TotalPrincipal`. If the borrower subsequently fails to pay, the `catch` path routes to `_handleBorrowerDefault`, but the APR0 bookkeeping committed earlier in the same transaction cannot be rolled back. This mirrors CVE-2021-25836: state produced by a not-yet-successful operation is cached and then persisted by the later (default-finalization) stage.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` ordering (contracts/IdleCDOEpochVariant.sol):

1. Line 362: `(_expectedInterest, _pendingWithdrawFees) = _strategy.prepareStopEpochWithApr0(_interest);` — a **non-view** call.
2. Inside `IdleCreditVault.prepareStopEpochWithApr0` (contracts/strategies/idle/IdleCreditVault.sol:490-541), when `apr0TotalPrincipal > 0` and override `_interest > 1`:
   - `pendingWithdraws += _apr0NetInterest` (line 535)
   - `apr0RateByEpoch[epochNumber] = ...` (line 537)
   - `apr0TotalPrincipal = 0` (line 540)
3. Lines 388-389 persist `expectedEpochInterest` and `pendingWithdrawFees`.
4. Line 408: `try this.getFundsFromBorrower(...)` — if the borrower's `transferFrom` fails, the `catch` block calls `_handleBorrowerDefault(...)` (line 504).

Because `prepareStopEpochWithApr0` is an external call into the strategy contract, its writes are **not** reverted when the outer `try` fails. The epoch then enters the defaulted state carrying:

- `pendingWithdraws` inflated by APR0 "interest" that was computed from an override `_interest` the borrower never paid.
- `apr0RateByEpoch[epochNumber]` set, so `_settleApr0` (IdleCreditVault.sol:545-565) later converts `principal * _rate` into `settledInterest` for every APR0 requester of that epoch.
- `apr0TotalPrincipal` cleared, so the bucket can never be re-settled correctly on retry.

Default recovery distributes the shortfall across the aggregate basis (active + pending). The phantom `settledInterest` and the inflated `pendingWithdraws` give APR0 withdrawal requesters a claim on yield that no one ever funded, directly reducing the recovery multiplier paid to all other LPs and pending receipt holders — the same "failed-transaction state persisted at end-stage" shape as the Ethermint honeypot-bytecode bug.

### Impact Explanation
Unprivileged lenders who requested withdrawals during an APR0 epoch receive recovery payouts for interest that was never transferred by the borrower. The loss is borne pro rata by every other claimant in `finalizeDefault`/`finalizeDefaultRecovery` distribution. Magnitude: `_apr0NetInterest = (overrideInterest - pendingFees) * apr0Principal / (TVL + apr0Principal) * (1 - fee)` — a fraction of the declared epoch interest, i.e. direct theft/dilution of the default recovery pool, not a rounding artifact.

### Likelihood Explanation
Requirements: (a) the vault ran an epoch with `unscaledApr == 0` and at least one `requestWithdraw` during it (creating `apr0TotalPrincipal`), and (b) the manager calls `stopEpoch`/`stopEpochWithDuration` with an override `_interest > pendingWithdrawFees`, and (c) the borrower fails the pull (default). APR0 epochs are a supported mode and borrower default is a supported flow; the attacker is simply a KYC'd lender who filed an APR0 withdrawal request — no privileged role is needed to benefit. The state corruption is deterministic once (a)-(c) hold; there is no guard that defers the APR0 writes until after the pull succeeds.

### Recommendation
Move the APR0 finalization out of the pre-pull section: either make `prepareStopEpochWithApr0` a pure preview and apply `pendingWithdraws`/`apr0RateByEpoch`/`apr0TotalPrincipal` writes inside the `try` success path of `_stopEpoch` (e.g., via a second strategy call after `collectWithdrawFunds`), or have `_handleBorrowerDefault` explicitly roll back the APR0 bucket (`pendingWithdraws -= _apr0NetInterest`, delete `apr0RateByEpoch[epochNumber]`, restore `apr0TotalPrincipal`).

### Proof of Concept
```solidity
// test/foundry/Apr0DefaultPhantomClaim.t.sol
function testApr0ClaimPersistedOnDefault() external {
    // Setup: epoch with unscaledApr == 0 (APR0 mode), lender FASA deposits AA
    idleCDO.depositAA(ONE_TRANCHE);
    _startEpochAndCheckPrices(0); // apr scaled to 0

    // During the running APR0 epoch FASA requests withdraw -> apr0TotalPrincipal > 0
    vm.prank(FASA);
    cdoEpoch.requestWithdraw(ONE_TRANCHE / 2, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Manager stops epoch with override interest, borrower does NOT approve/pay -> default
    uint256 overrideInterest = 100 * ONE_SCALE + cdoEpoch.pendingWithdrawFees();
    // borrower intentionally underfunded: transferFrom inside getFundsFromBorrower reverts
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, overrideInterest);

    assertTrue(cdoEpoch.defaulted());

    // BUG: APR0 writes survived the failed pull
    uint256 reqEpoch = strategy.epochNumber();
    assertGt(strategy.apr0RateByEpoch(reqEpoch), 0, "phantom APR0 rate persisted");
    // pendingWithdraws includes _apr0NetInterest never paid by borrower
    // FASA's _settleApr0 later mints settledInterest, diluting the recovery
    // multiplier for all other claimants in finalizeDefaultRecovery.
}
```

Note: the exact theft magnitude flows through `defaultPendingClaimBasis`/recovery-multiplier accounting in the default claim path (`_claimDefaulted*`, `DefaultDistributor.claim`); the pre-commit of `pendingWithdraws` and `apr0RateByEpoch` is confirmed in code, but I did not fully trace the recovery-basis snapshot to confirm whether it reads `pendingWithdraws` post-inflation — if the basis is snapshotted before `prepareStopEpochWithApr0`, the dilution vector narrows to the `apr0RateByEpoch`/`settledInterest` component only.
