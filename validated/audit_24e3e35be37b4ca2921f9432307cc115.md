### Title
Uncapped builder-pending-withdrawal amount committed to `payload_expected_withdrawals` while the actual balance deduction is capped, minting Gwei that was never backed by builder balance - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` builds `Withdrawal` entries for `state.builder_pending_withdrawals` using the *requested* `withdrawal.amount` with no check against the builder's current `balance`, whereas `get_builders_sweep_withdrawals` (the sibling function for full-balance sweeps) correctly bounds its amount to `builder.balance`. `apply_withdrawals`, in contrast, deducts only `min(withdrawal.amount, builder_balance)` from the builder's on-chain balance. The amount *committed* (and thus minted to the `fee_recipient` by the execution layer) can therefore exceed the amount actually *deducted* from the builder.

### Finding Description
`get_builder_withdrawals` in `specs/gloas/beacon-chain.md` iterates `state.builder_pending_withdrawals` and appends withdrawals with the raw, uncapped amount: [1](#0-0) 

Compare this to `get_builders_sweep_withdrawals`, which correctly uses `builder.balance` (the actual available amount) rather than any externally supplied request: [2](#0-1) 

These withdrawal lists are merged and returned unmodified as `expected.withdrawals`, which is written verbatim into `state.payload_expected_withdrawals` — the value the execution layer is bound to honor as the actual mint/payment to `withdrawal.address`: [3](#0-2) 

However, when the CL applies the corresponding balance deduction, it caps the deduction to the builder's current balance: [4](#0-3) 

So if `withdrawal.amount` (from `builder_pending_withdrawals`) is larger than `builder_balance` at withdrawal time, the CL only removes `builder_balance` (i.e., zeroes it out), but the `Withdrawal` object committed in `state.payload_expected_withdrawals` — which the execution layer is spec-bound to pay out via the withdrawals list in the execution payload — still carries the full, uncapped `withdrawal.amount`. This breaks the equality "Gwei paid out to `fee_recipient` == Gwei removed from builder balance," creating Gwei that is paid to a non-owner (the `fee_recipient`) without being backed by any corresponding balance deduction.

This is the direct structural analog of the reported DeFi bug: `getSendTokenMessage`/`sendTokenToUser` committed to sending a token amount without checking the real, available liquidity at the destination, letting committed obligations exceed backing reserves. Here, the beacon state commits a withdrawal amount to be executed/minted by the EL without checking it against the actual `builder.balance`, while only the *internal* CL bookkeeping (the balance decrement) is capped — the two sides of the ledger silently diverge.

Whether `state.builder_pending_withdrawals` entries can actually contain an `amount` greater than the builder's balance at processing time (e.g., via `withdrawal_amount`/`amount` fields set by `process_builder_withdrawal_request` or similar processing prior to the balance being spent through consecutive withdrawals/slashing) could not be fully confirmed within available tool budget — this needs verification by reading how entries are appended to `state.builder_pending_withdrawals` and whether any invariant elsewhere in `specs/gloas/beacon-chain.md` (outside `get_builder_withdrawals`/`apply_withdrawals`) enforces `amount <= balance` at append time or re-validates it at processing time.

### Impact Explanation
If reachable, this is a Critical-severity, unpermissioned Gwei-creation bug: a fee_recipient address can receive an execution-layer payment/mint larger than the builder ever had, funded from nothing, purely because the commitment path (`get_builder_withdrawals`) and the deduction path (`apply_withdrawals`) use different, inconsistent bounds (uncapped vs. `min(amount, balance)`).

### Likelihood Explanation
Likelihood is uncertain without confirming whether `builder_pending_withdrawals.amount` can ever legitimately exceed the builder's live balance by the time `process_withdrawals` runs (e.g., through balance depletion by an earlier withdrawal/slashing/other builder-balance-reducing event in the same sweep or an intervening event between request creation and processing). Given the existence of the analogous, explicitly-bounded sibling function (`get_builders_sweep_withdrawals` uses `builder.balance`) and the explicit capping in `apply_withdrawals`, the asymmetry strongly suggests the designers were aware balance could be insufficient at processing time but only patched the *deduction* side, not the *commitment* side.

### Recommendation
In `get_builder_withdrawals`, bound the committed withdrawal amount to the builder's current balance the same way `get_builders_sweep_withdrawals` and `apply_withdrawals` do, e.g. `amount=min(withdrawal.amount, state.builders[builder_index].balance)` (and correspondingly re-derive/decrement a running "available balance" across `prior_withdrawals` for the same builder within one call, mirroring how `get_validators_sweep_withdrawals`/`get_balance_after_withdrawals` account for prior withdrawals in the same batch for validators).

### Proof of Concept
Conceptual state transition (values illustrative):
1. Builder `B` has `state.builders[B].balance = 1_000_000_000` (1 ETH).
2. `state.builder_pending_withdrawals` contains an entry `BuilderPendingWithdrawal(builder_index=B, amount=10_000_000_000, fee_recipient=F)` (10 ETH), created/queued at a time when `B` legitimately had ≥10 ETH balance backing it, but `B`'s balance has since been reduced (e.g., by other withdrawals processed earlier in the same or prior slot, or slashing) to 1 ETH.
3. `process_withdrawals(state)` → `get_expected_withdrawals` → `get_builder_withdrawals` emits `Withdrawal(validator_index=convert(B), address=F, amount=10_000_000_000)` — uncapped.
4. `apply_withdrawals(state, [that withdrawal])` executes `state.builders[B].balance -= min(10_000_000_000, 1_000_000_000)` → `state.builders[B].balance = 0`.
5. `state.payload_expected_withdrawals` (committed to the execution payload) still records `amount=10_000_000_000` paid to `F`.
6. The execution layer, bound to honor `payload_expected_withdrawals` exactly, mints/pays `F` the full 10 ETH, while only 1 ETH was ever removed from any CL balance — 9 ETH of Gwei materialized with no corresponding deduction, i.e. created and paid to `F`.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
