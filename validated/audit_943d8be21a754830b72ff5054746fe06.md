### Title
Unfunded instant-withdraw receipts can drain funded claim cash pooled in IdleCreditVault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The instant-withdraw flow mirrors the reported bug class: a request that was *not* funded (the "TLS-required" leg of the curl CVE, i.e., the leg that must satisfy the funding requirement) is paid by "reusing" whatever underlying cash the strategy contract already holds — cash that belongs to other users' already-funded claims or to the default recovery reserve — because `claimInstantWithdrawRequest` never verifies that *this* receipt's share of `pendingInstantWithdraws` was actually collected before paying out.

### Finding Description
`requestInstantWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:356-375) mints receipt strategy tokens to the user, increments `instantWithdrawsRequests[_user]` and the global unfunded counter `pendingInstantWithdraws`. Funding arrives later via `collectInstantWithdrawFunds` (line 398-403), which decrements `pendingInstantWithdraws` and pulls underlying from the IdleCDO.

On the claim side, `claimInstantWithdrawRequest` (line 380-393):
```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```
burns the receipt and pays the full amount through `_transferFundedClaim` (line 897-907), whose only guard is `balance - defaultRecoveryReserve >= _amount`. It never checks `pendingInstantWithdraws` — the unfunded remainder — nor any per-epoch funding status (`instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` are only used for default recovery). So a receipt that was never funded can be paid out of pooled underlying that was collected for *other* instant-withdraw claimants.

### Impact Explanation
Direct theft / insolvency. When the strategy holds underlying collected for a subset of instant requests (partial funding — `instantWithdrawClaimsByEpoch[epoch] > pendingInstantWithdraws` per `_defaultPrefundedInstantReserve`, line 716-723, which explicitly acknowledges this mixed state), an attacker whose receipt is part of the unfunded remainder claims first and walks away with cash earmarked for other users' funded receipts. Those honest users' subsequent claims then revert on insufficient balance — permanent freezing of their claims — while the attacker keeps the difference. Quantified loss: up to the strategy's entire funded instant balance, i.e., `instantWithdrawClaimsByEpoch[epoch] - pendingInstantWithdraws` at claim time.

### Likelihood Explanation
The attacker needs only to be a KYC'd tranche holder (`isWalletAllowed` is checked on `requestWithdraw`, IdleCDOEpochVariant.sol:741-744). Preconditions: instant-withdraw mode is active (APR dropped below `lastEpochApr - instantWithdrawAprDelta`, line 761-770), and the IdleCDO funds instant requests in tranches so a mixed funded/unfunded state exists — the codebase itself treats partially funded instant buckets as a normal state (lines 636-649, 712-723). The attacker requests an instant withdraw, waits for the CDO-side `instantWithdrawDelay` gating to elapse, then calls `claimInstantWithdrawRequest` before their receipt is funded. Caveat: the exact claim-time gating inside `IdleCDOEpochVariant.claimInstantWithdrawRequest` was not fully traced in this pass; if the CDO blocks claims while `pendingInstantWithdraws` is non-zero, the attack reduces to a first-come-first-served race among receipt holders, still breaking the "one receipt, one payout" and fair-queue invariants whenever a partial-funding window exists.

### Recommendation
In `claimInstantWithdrawRequest`, verify the receipt was funded before paying: e.g., require `pendingInstantWithdraws == 0`, or track per-user funded basis (already stored per-epoch in `instantWithdrawsRequestsByEpoch`) and cap the payout at `instantBasis - pendingInstantWithdraws` pro rata, mirroring how `_claimDefaultedInstantWithdrawRequest` (line 842-856) reconciles funded vs. unfunded portions at default time.

### Proof of Concept
```solidity
// Fork test (Foundry), modeled on test/foundry/IdleCreditVault.t.sol testClaimInstantWithdrawRequest
function testUnfundedInstantClaimStealsPooledFunds() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    idleCDO.depositAA(amountWei);
    idleCDO.depositBB(amountWei);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // honest user requests instant withdraw (APR drop path)
    address honest = makeAddr('honest');
    _depositWithUser(honest, amountWei, true);
    uint256 honestReq = _requestInstantFor(honest); // requestWithdraw routed to instant mode

    // attacker requests instant withdraw for the same epoch
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, amountWei, true);
    uint256 attackerReq = _requestInstantFor(attacker);

    // IdleCDO funds ONLY the honest request: collectInstantWithdrawFunds(honestReq)
    // pendingInstantWithdraws still > 0 (attacker's part unfunded)
    deal(defaultUnderlying, address(cdoEpoch), honestReq);
    vm.prank(address(cdoEpoch));
    IdleCreditVault(address(strategy)).collectInstantWithdrawFunds(honestReq);

    // wait out instantWithdrawDelay, then attacker claims first
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - pre, 0, 'unfunded claim paid from pooled cash');

    // honest claim now fails / pays less: permanent freezing of the honest claim
    vm.prank(honest);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note: if a deeper audit shows the IdleCDO's `claimInstantWithdrawRequest` already reverts while `pendingInstantWithdraws != 0`, this analog does not hold and the finding should be downgraded to a race among funded receipts only.
