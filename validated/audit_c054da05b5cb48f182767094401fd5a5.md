### Title
Blocking-minority (>30%) gossip can poison the v2 signer's `current_miner` view, letting `GlobalStateView::check_proposal` trust an unverified miner identity - ([File: stacks-signer/src/v0/signer_state.rs], [File: stacks-signer/src/chainstate/v2.rs])

### Summary
In the TRST-M-2 analog, `TimeswapV2PoolFactory.create()` trusted an options-contract address supplied by the caller instead of verifying it came from the official `TimeswapV2OptionFactory`. The stacks-signer analog is `SignerStateMachine::current_miner` (v2 protocol path): the signer's `capitulate_miner_view` function adopts a peer-reported `ActiveMiner` identity (`current_miner_pkh`, `tenure_id`, `parent_tenure_id`, `parent_tenure_last_block`) supplied via gossiped `StateMachineUpdate` messages, and — once that tenure already has at least one globally-accepted block — accepts it on only a **blocking-minority (>30%) weight**, without ever independently verifying that `current_miner_pkh` matches the actual sortition winner recorded on-chain for that `tenure_id`. `GlobalStateView::check_proposal` (v2) then treats this self-reported `current_miner` as ground truth when validating/signing future block proposals, with no independent sortition lookup like v1 performs.

### Finding Description
`capitulate_miner_view` in [1](#0-0)  tallies weighted votes for each peer-reported `ActiveMiner` state and only requires the **disagreement/blocking-minority threshold** (`eval.reached_disagreement`, i.e. more than 30% of total weight, computed in [2](#0-1)  as strictly greater than `(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)/10`) to enter the candidate pool:

```
let entry = miners.entry(miner_state).or_insert(0);
*entry += weight;
if !eval.reached_disagreement(*entry) {
    continue;
}
let nmb_blocks = signerdb.get_globally_accepted_block_count_in_tenure(tenure_id).unwrap_or(0);
if nmb_blocks == 0 && !eval.reached_agreement(*entry) {
    continue;
}
```

The full 70% agreement threshold (`eval.reached_agreement`) is only enforced when `nmb_blocks == 0`. Once a tenure already has ≥1 globally accepted block in `signerdb` — which is true for any previously-active, now-superseded tenure — a colluding blocking minority (>30%, not a majority) can get their self-reported `miner_state` accepted as a `potential_match`, and it can become `new_miner` if it has the tallest reported `parent_tenure_last_block_height` [3](#0-2) .

The only sanity check against the real sortition winner is applied afterward in `capitulate_viewpoint`, and it only compares against `cur_sortition` (the *current* sortition), not against the sortition that actually produced `new_miner.tenure_id`:

```
if current_miner_pkh != sortition_state.cur_sortition.data.miner_pkh {
    sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock
}
``` [4](#0-3) 

If the poisoned `new_miner.tenure_id` refers to an older/last-sortition tenure (not `cur_sortition`), this guard never fires, and the adopted state is installed unconditionally as the new `SignerStateMachine.current_miner` [5](#0-4) .

For protocol v2, this `current_miner` is exactly what `GlobalStateView::check_proposal` uses as its sole ground truth for miner identity — there is no separate, independently-fetched sortition record consulted in this path, unlike v1's `SortitionsView::check_proposal`, which uses `cur_sortition`/`last_sortition` fetched independently from the node via `fetch_view`:

```
let MinerState::ActiveMiner { current_miner_pkh, tenure_id, parent_tenure_id, .. } = &self.signer_state.current_miner else { ... };
if &block.header.consensus_hash != tenure_id { ... return Err(RejectReason::ConsensusHashMismatch{..}); }
...
if current_miner_pkh != &miner_pkh { ... return Err(RejectReason::PubkeyHashMismatch); }
``` [6](#0-5) 

Consequently, a blocking minority can plant a `current_miner_pkh`/`tenure_id`/`parent_tenure_id` combination in an honest signer's local state machine without that identity ever having been checked against the actual sortition winner, mirroring the Timeswap bug's core defect: trusting an unverified identity/artifact instead of validating it against the authoritative source.

### Impact Explanation
This breaks the equality that v2's `check_proposal` is supposed to enforce (`current_miner_pkh == validated sortition winner pubkey hash`). Once poisoned, the signer's "ground truth" for what tenure/miner is valid no longer derives from an independently-verified sortition record; it derives from gossiped, self-reported peer state that only needed >30% weight to be adopted (for a tenure with prior accepted blocks). This can be leveraged to either wedge the signer (rejecting legitimate proposals from the true current miner because `current_miner_pkh`/`tenure_id` no longer matches) or to steer the signer's acceptance criteria toward an attacker-influenced miner identity for signing decisions — a liveness wedge and a threat to the invalid/non-canonical block signing guarantee, without requiring a signer majority.

### Likelihood Explanation
Requires only a blocking minority (>30% signer weight) of malicious or compromised signers broadcasting crafted `StateMachineUpdate` messages via StackerDB gossip — no access to another signer's key, no node consensus majority, and it only needs an existing tenure that already has ≥1 globally accepted block (a common condition once tenures progress). This is a plausible, moderate-likelihood path reachable by a coordinated blocking minority alone.

### Recommendation
When a threshold-weighted `miner_state` candidate is being considered for adoption in `capitulate_miner_view`, independently verify `current_miner_pkh` against the canonical sortition winner for `tenure_id` (as v1's `SortitionsView` does) before installing it as `SignerStateMachine.current_miner`, rather than relying solely on the peer-reported gossip weight. Additionally, apply the `cur_sortition`/`last_sortition` pubkey-hash cross-check unconditionally against whichever sortition record corresponds to the adopted `tenure_id` (not only `cur_sortition`), so a mismatch always invalidates the adopted state before it can be used by `GlobalStateView::check_proposal`.

### Proof of Concept
1. Wait for/target a tenure `T` (consensus hash `ch_T`) that already has ≥1 globally accepted block recorded in `signerdb` (`get_globally_accepted_block_count_in_tenure(ch_T) > 0`), and where `T` is not the current sortition's tenure (e.g., `last_sortition`).
2. A blocking minority (>30% signer weight) of colluding signers broadcasts `StateMachineUpdate` (`StateMachineUpdateContent::V0 { current_miner: ActiveMiner { current_miner_pkh: <attacker_pkh>, tenure_id: ch_T, parent_tenure_id, parent_tenure_last_block, parent_tenure_last_block_height: <max_reported_height> }, .. }`) over StackerDB, agreeing on the same burn view as everyone else.
3. On the victim signer, `capitulate_viewpoint` → `capitulate_miner_view` ( [7](#0-6) ) tallies these updates; since `nmb_blocks > 0` for `ch_T`, only `reached_disagreement` (>30%) is required, and if this candidate has the tallest `parent_tenure_last_block_height` among `potential_matches`, it becomes `new_miner`.
4. Because `new_miner.tenure_id == ch_T != sortition_state.cur_sortition.data.consensus_hash`, the post-adoption guard comparing `current_miner_pkh` to `cur_sortition.data.miner_pkh` ( [4](#0-3) ) never fires, so `attacker_pkh`/`ch_T` are installed unchecked as `SignerStateMachine.current_miner`.
5. Subsequent calls to `GlobalStateView::check_proposal` ( [6](#0-5) ) use this poisoned `current_miner` as ground truth, rejecting the true current miner's valid proposals (`ConsensusHashMismatch`/`PubkeyHashMismatch`) even though they never came from a verified sortition-winner mismatch.

Note: I could not fully trace, within the available index, exactly how/when `GlobalStateView` (v2) vs `SortitionsView` (v1) is selected at runtime in `stacks-signer/src/v0/signer.rs` for a given active protocol version, so the precise conditions under which v2's `check_proposal` (rather than v1's) is the active gate should be double-checked in a live session.

                crate::monitoring::SignerAgreementStateConflict::BurnBlockDelay,
            );
            return None;
        }

        let mut potential_matches = HashSet::new();

        for (address, update) in &eval.address_updates {
            let Some(weight) = eval.address_weights.get(address) else {
                continue;

            let burn_block = update.content.burn_block_view().0;
            if burn_block != global_burn_block {
