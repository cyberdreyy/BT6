### Title
Global capability lookup with no per-user/workflow ownership check allows run-role user to invoke arbitrary registered capabilities via `/v2/execute_capability` - ([File: core/web/capability_controller.go])

### Summary
`CapabilityController.ExecuteCapability` resolves a capability purely by its `CapabilityName` string against the node-wide `CapabilitiesRegistry` and executes it directly, with no check that the calling session is authorized for that specific capability instance or the workflow/job it is bound to. Combined with the route being gated only by `build.IsDev()` and `auth.RequiresRunRole` (per the router configuration referenced in the question), any authenticated run-role session can invoke any capability currently registered on the node, not just ones tied to its own jobs/workflows.

### Finding Description
`ExecuteCapability` in `core/web/capability_controller.go` does the following: [1](#0-0) 
It fetches the shared, node-level `CapabilitiesRegistry` via `cc.App.GetCapabilitiesRegistry()` and calls `GetExecutable(ctx, capabilityRequestOuter.CapabilityName)` — a lookup keyed only by name, with no binding to the requesting principal, job ID, or workflow ID. It then unmarshals an attacker-supplied `CapabilityRequest` byte payload and calls `capability.Execute(ctx, capabilityRequest)` directly: [2](#0-1) 

There is no code path in this handler that checks whether the invoking user's session/API token is associated with the job or workflow that registered that named capability. Any caller who can reach this endpoint and knows (or guesses/enumerates) a capability name can execute it and receive its response directly in the HTTP response body, bypassing the normal workflow-engine binding that would otherwise scope capability inputs/outputs (and any secrets/config baked into that capability instance) to the owning workflow.

Per the question's stated router configuration, this endpoint is registered only when `build.IsDev()` is true, and is protected solely by `auth.RequiresRunRole` — a low-privilege role — with no additional ownership/admin gate. I was not able to directly view the exact router.go lines confirming the `build.IsDev` conditional and `RequiresRunRole` wrapper in this session (tool budget exhausted after locating the matches), so that specific gating detail should be independently confirmed, but the handler-level lack of ownership checks is directly confirmed in `capability_controller.go`.

### Impact Explanation
If reachable, a low-privileged run-role user can invoke any capability registered on the node regardless of which job/workflow owns it, and receive the raw capability response. For capabilities that embed secrets, credentials, or perform privileged actions (e.g., target capabilities that call external APIs with bound keys), this constitutes cross-user disclosure of capability-bound secrets/results and unauthorized invocation of another user's capability — matching the "unauthorized job run" / "key or secret disclosure" bounty impact classes.

### Likelihood Explanation
Preconditions: `build.IsDev()` must evaluate true (a build-time condition, not attacker-controlled) and the attacker needs only a valid run-role session — the lowest privilege authenticated role in the node's session system. If those preconditions hold in a given deployment (e.g., staging/dev builds), the exploit path requires only two ordinary API calls (login, then POST to the endpoint) and is trivially repeatable and scriptable.

### Recommendation
- Scope `GetExecutable` lookups (or add a subsequent authorization check) to verify the requesting principal owns/administers the job or workflow that registered the target capability before executing it.
- Require an admin-level role (not just `RequiresRunRole`) for direct capability execution endpoints, since they bypass normal workflow-engine secret binding.
- If this endpoint is intended purely for local development/debugging, ensure it cannot be enabled in any build/config reachable by remote, non-admin credentials, and add an explicit runtime check (not just `build.IsDev()`) tied to `Insecure().DevWebServer()` or similar operator-controlled config.

### Proof of Concept
Go handler-level integration test plan:
1. Start a test node with `build.IsDev()` forced true and two run-role users, `UserA` and `UserB`.
2. Register two capabilities in the `CapabilitiesRegistry`: `capA` bound to `UserA`'s workflow (with a distinguishing secret/config in its execution response) and `capB` bound to `UserB`'s workflow.
3. Authenticate as `UserB` via `POST /sessions`.
4. As `UserB`, send `POST /v2/execute_capability` with `capabilityName = "capA"`.
5. Assert: the response returns `200 OK` with `capA`'s execution result/secret data, proving `UserB` executed and read output from `UserA`'s capability with no ownership check — expected/desired behavior would be a `403 Forbidden` or `404 Not Found` when the capability does not belong to the calling user's jobs/workflows.
