### Title
User enumeration via distinguishable "Invalid email" vs "Invalid password" error messages returned by `POST /sessions` - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` in `core/sessions/localauth/orm.go` returns two different error messages — `"Invalid email"` when the email is not found (or fails the constant-time compare) and `"Invalid password"` when the password check fails [1](#0-0) . These errors flow unmodified to the HTTP client because `jsonAPIError` serializes `err.Error()` directly into the JSON response body [2](#0-1) , allowing an unauthenticated attacker to distinguish registered emails from unregistered ones by inspecting the response text.

### Finding Description
The `POST /sessions` route is unauthenticated and rate-limited only, not blocked [3](#0-2) . `SessionsController.Create` forwards any error from `AuthenticationProvider().CreateSession` straight to `jsonAPIError(c, http.StatusUnauthorized, err)` [4](#0-3) , and `jsonAPIError` embeds `err.Error()` verbatim in the JSON body when the error is not a `*models.JSONAPIErrors` [2](#0-1) .

In `CreateSession`, an email that doesn't exist in the DB (or fails `constantTimeEmailCompare`) yields `pkgerrors.New("Invalid email")`, while a correct email with a wrong password yields `pkgerrors.New("Invalid password")` [1](#0-0) . These two distinct strings are returned to the caller with different HTTP body content, letting an attacker distinguish "email exists" from "email doesn't exist" by reading the response, without needing to measure timing at all — the message text itself is the oracle. The code comment at line 152-153 claims the ordering is meant "to prevent extra database look up for MFA tokens leaking," but the controller already performs a `GetUserWebAuthn` lookup for every submitted email *before* calling `CreateSession` [5](#0-4) , so this ordering does not actually protect MFA-enablement leakage, and it does nothing to prevent the "Invalid email"/"Invalid password" message difference.

The existing constant-time comparison (`constantTimeEmailCompare`, `subtle.ConstantTimeCompare`) only defends against timing side channels on the email comparison itself [6](#0-5) ; it does not address the fact that two different literal strings are returned for the two failure modes.

The existing test suite for this endpoint (`TestSessionsController_Create`) only asserts `resp.StatusCode >= 400` for negative cases and does not compare response bodies, so this discrepancy is not currently covered/caught by tests [7](#0-6) .

### Impact Explanation
This is a user/account enumeration vulnerability: an unauthenticated attacker can send `POST /sessions` with a guessed email and observe whether the response says "Invalid email" or "Invalid password" to determine if the account is registered on the node. Combined with the fact that MFA (WebAuthn) presence is also queried during `Create` regardless of credential validity, this can help an attacker build a target list to focus subsequent credential-stuffing or brute-force attempts, and specifically identify accounts without MFA once their password is later compromised through another channel. This maps to Chainlink's "information disclosure aiding account targeting" class — it is not by itself an authentication bypass, but it materially reduces attacker cost for follow-on credential attacks.

### Likelihood Explanation
Fully unauthenticated, trivially reproducible: a single `POST /sessions` request per candidate email with any password. The only mitigating control is the endpoint's rate limiter (`rl.UnauthenticatedPeriod()` / `rl.Unauthenticated()` in `sessionRoutes`) [8](#0-7) , which slows but does not prevent enumeration over time or across IPs/tokens.

### Recommendation
Return a single generic error message (e.g., `"Invalid email or password"`) for both the email-mismatch and password-mismatch branches in `CreateSession`, and ensure `jsonAPIError` on `/sessions` does not leak the underlying distinguishing text. Keep the audit-log entries (`AuthLoginFailedEmail` / `AuthLoginFailedPassword`) distinct server-side for diagnostics, but do not let the distinction leak to the HTTP response.

### Proof of Concept
Go handler-level integration test plan:
1. Start `web.Router` with a test app; create one known user via `AuthenticationProvider().CreateUser`.
2. Issue `POST /sessions` with `{"email":"unknown@test.com","password":"whatever"}` and capture response body.
3. Issue `POST /sessions` with `{"email":"<known>@test.com","password":"wrongpassword"}` and capture response body.
4. Assert both responses currently differ (`"Invalid email"` vs `"Invalid password"`), demonstrating the enumeration oracle — this assertion should fail once fixed to return identical generic text.
5. Optionally add a unit test directly on `orm.CreateSession` asserting `err.Error()` is identical (e.g., `"invalid credentials"`) for both invalid-email and invalid-password cases.

```go
const constantTimeEmailLength = 256

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
```
