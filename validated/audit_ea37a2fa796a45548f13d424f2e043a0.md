### Title
Yield-stealing via front-run/back-run sandwich of `lending_pool_emissions_deposit` - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
The reported StUSR issue is a class of bug where a permissionless lump-sum reward distribution instantly re-values all currently-outstanding shares, allowing an attacker to front-run the distribution with a large stake, capture a pro-rata share of rewards they never earned, and immediately withdraw. Marginfi has a directly analogous mechanism: `lending_pool_emissions_deposit`, a permissionless instruction that deposits "same-bank emissions" into a bank's liquidity vault and instantly re-prices `asset_share_value` across all outstanding `total_asset_shares` [1](#0-0) , exposed on-chain via `lib.rs` as `(permissionless) Deposit same-bank emissions ... increase depositors' value via asset_share_value` [2](#0-1) .

### Finding Description
`lending_pool_emissions_deposit` computes the new share price as `(total_assets + amount) / total_asset_shares`, then sets `bank.asset_share_value` to this new value in a single atomic step [3](#0-2) . This is functionally identical to a StUSR-style `RewardDistributor.distribute()`: a lump sum is dropped into the pool and instantly, uniformly re-prices every share outstanding at that moment, regardless of how long each depositor has held their shares.

Because this instruction is explicitly permissionless (any `depositor: Signer` can call it, as long as they fund the `emissions_funding_account` transfer) [4](#0-3) , and because these deposits are typically funded by third parties (partners running a "Campaign", per the emissions guide) whose transactions land in the public mempool, an attacker who observes a pending `lending_pool_emissions_deposit` transaction can:
1. Front-run with `lending_account_deposit` of a large amount into the same bank, minting `asset_shares` at the pre-distribution `asset_share_value` (accrue_interest runs first but this doesn't block the deposit) [5](#0-4) .
2. Let the emissions-deposit transaction execute, which re-prices `asset_share_value` for ALL current shares, including the attacker's newly minted shares [6](#0-5) .
3. Back-run with `lending_account_withdraw` to realize the increased share value immediately, capturing a pro-rata cut of the emissions deposit that is proportional to their share of `total_asset_shares` at that instant — despite having deposited seconds earlier.

The test suite explicitly documents that this deposit increases `asset_share_value` uniformly for `total_asset_shares` at the time of the call, with shares before/after being unchanged and the multiplier applied to all shares [7](#0-6) . There is no vesting, no checkpointing of "shares as of tx submission" vs. "shares added mid-flight," and no minimum holding-period enforcement visible in the `LendingAccountDeposit`/`LendingAccountWithdraw` accounts structs that would prevent this sandwich.

### Impact Explanation
If exploited, an attacker captures reward value intended for long-standing depositors of a bank, diluting the yield legitimate depositors receive from a Campaign/emissions drop. This is a direct value-redirection/economic exploit consistent with "exploitable misvaluation... with financial effect." The magnitude scales with the size of the emissions deposit and the attacker's ability to temporarily dominate `total_asset_shares` (e.g., via a large capital injection, potentially via flash-borrowed capital from elsewhere, subject to marginfi's flashloan restrictions).

### Likelihood Explanation
Likelihood depends on:
- Whether `lending_pool_emissions_deposit` transactions are actually sent via a public mempool (Solana transactions are visible pre-confirmation, similar to Ethereum mempool sandwiching, though Solana's leader-based execution model changes the practical mechanics of front/back-running compared to Ethereum).
- Whether depositing/withdrawing large amounts in the same or adjacent transactions triggers any deposit/withdraw caps, rate limiters, or health-engine checks that would block or unwind the attack. I found a `rate_limiter.rs` / `configure_rate_limits.rs` subsystem in the codebase [8](#0-7)  but did not have the opportunity to confirm whether it specifically throttles same-bank deposit+withdraw sequences within a single slot/transaction bundle, which would materially reduce (or eliminate) the exploitability of this pattern. This is a genuine gap in verification, not a confirmed mitigant.
- Whether `deposit_limit`/`borrow_limit` caps on the bank would restrict how large a front-run deposit could be, limiting attacker profit.

Given the uncertainty about mitigating rate limits, likelihood should be treated as **Medium** rather than confirmed-High.

### Recommendation
- Snapshot eligible shares (e.g., record `total_asset_shares` as of the last accrual/checkpoint prior to the emissions deposit, and require deposits made within the same transaction or slot as the emissions deposit to be excluded from that specific distribution).
- Alternatively, convert `lending_pool_emissions_deposit` from an instant lump-sum re-pricing into a streamed/vested accrual (similar to `emissions_rate` APR-based streaming that already exists in `Bank`), so a flash deposit cannot capture more than a proportional, time-weighted sliver of the reward.
- Consider requiring `lending_pool_emissions_deposit` to only be callable by a trusted keeper/admin with a private RPC/relay to reduce mempool visibility, mirroring the report's original recommendation, though this only reduces likelihood rather than eliminating the root cause.
- Verify whether the existing `rate_limiter` mechanism already covers this scenario; if not, extend it to guard against same-block/adjacent deposit-then-withdraw sequences around `lending_pool_emissions_deposit`.

### Proof of Concept
Conceptual sequence (not independently executed against a live cluster, based on code-level tracing of the three instructions):
1. Bank B has `total_asset_shares = S`, `asset_share_value = V`, so total assets = `S*V`.
2. Attacker observes pending `lending_pool_emissions_deposit(amount=R)` for bank B in mempool/upcoming block.
3. Attacker calls `lending_account_deposit(D)` on bank B, minting `D/V` new shares. New `total_asset_shares = S + D/V`.
4. `lending_pool_emissions_deposit(R)` executes: `new_V = (S*V + D + R) / (S + D/V)`.
5. Attacker calls `lending_account_withdraw` for their full position, redeeming `(D/V) * new_V` tokens.
6. Attacker's profit ≈ `R * (D/V) / (S + D/V)` minus any interest/fees accrued in the interim — i.e., they capture a slice of `R` proportional to their (very recently deposited) share of the pool, exactly mirroring the StUSR sandwich pattern described in the source report.

Note: I was not able to fully confirm within the available exploration whether marginfi's `rate_limiter` subsystem [9](#0-8)  would block or dampen this specific deposit-then-withdraw sequence; this should be verified in a live/test-validator PoC before treating this as a confirmed, unmitigated vulnerability.

/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();

    bank.update_bank_cache(&group)?;

    msg!(
        "Deposited {} same-bank emissions into liquidity vault",
        amount
    );

    Ok(())
}
