### Title
Denied Address Cannot Withdraw Regulated-Coin Funds from Address-Balance Accumulator — Permanent Fund Lock - (File: `crates/sui-types/src/deny_list_v2.rs`)

---

### Summary

When an address is added to a regulated coin's deny list via `coin::deny_list_v2_add`, the signing-time check in `check_coin_deny_list_v2_during_signing` also blocks any transaction that declares a `withdraw<Balance<T>>` argument for that coin type. Because the address balance accumulator is the only place those funds live, the denied address has no path to recover its own pre-existing balance. The funds are permanently locked until the coin issuer voluntarily removes the address from the deny list.

---

### Finding Description

Sui's deny-list v2 enforces two separate checks:

**Signing-time** (`check_coin_deny_list_v2_during_signing`, `crates/sui-types/src/deny_list_v2.rs` lines 117–140): collects coin types from input objects, receiving objects, *and* `funds_withdraw_types` (the set of coin types declared in `withdraw<Balance<T>>` PTB arguments). If the transaction sender is denied for any of those types, the transaction is rejected before it reaches execution. [1](#0-0) 

**Signing-time wiring** (`handle_coin_deny_list_checks`, `crates/sui-core/src/authority.rs` lines 1182–1225): extracts `funds_withdraw_types` from the declared withdrawals and passes them into both the v1 and v2 signing checks. [2](#0-1) 

The address-balance accumulator (`balance::send_funds` / `balance::redeem_funds`) is the canonical way to hold and move regulated-coin balances without coin objects. [3](#0-2) 

When a user's address is added to the deny list after funds have already been deposited into their accumulator, the only way to move those funds is to submit a PTB that includes `withdraw<Balance<REGULATED_COIN>>(amount)`. That argument causes the regulated coin type to appear in `funds_withdraw_types`, which triggers the signing check, which rejects the transaction because the sender is denied. There is no alternative path: the accumulator is not a coin object, so `transfer-object` does not apply; `balance::redeem_funds` requires a `Withdrawal` argument that itself requires the `withdraw<…>` PTB input.

The test snapshot confirms this exact failure: [4](#0-3) 

```
task 8, lines 67-72:

```

The test was written to document the behavior, not to flag it as a bug. No emergency-withdrawal path exists in the framework.

---

### Impact Explanation

Any regulated-coin balance that has been deposited into a denied address's accumulator via `balance::send_funds` or `coin::send_funds` is inaccessible to that address for as long as it remains on the deny list. Because the coin issuer may never remove the address, the lock is effectively permanent from the user's perspective. This matches the **permanent fund lock** impact class (High/Medium) in the allowed impact gate.

The locked value is bounded only by how much of the regulated coin was sent to the address before denial; there is no protocol-level cap.

---

### Likelihood Explanation

The scenario requires:
1. A regulated coin with an active deny list (any `create_regulated_currency_v2` coin).
2. Funds deposited into the target address's accumulator before or during the same epoch as denial (the receiver check is epoch-delayed, so deposits in the same epoch as `deny_list_v2_add` still land).
3. The coin issuer adding the address to the deny list.

All three steps are ordinary, publicly reachable operations. The coin issuer need not be malicious — a compliance-driven denial (e.g., OFAC screening) is sufficient to trigger the lock.

---

### Recommendation

Add an escape-hatch path that allows a denied address to move its existing accumulator balance to a different address without the signing-time deny-list check blocking the withdrawal. Concretely:

- Introduce a dedicated `emergency_withdraw_from_accumulator` entry point (or a PTB argument variant) that is exempt from the `funds_withdraw_types` deny-list check at signing time, but still subject to the execution-time receiver check so the funds cannot be re-deposited into another denied address.
- Alternatively, exempt `withdraw<Balance<T>>` arguments from the signing-time deny check when the withdrawal owner equals the transaction sender and the destination is not itself denied, mirroring the intent of the existing `redeem_funds` → `send_funds` pattern.

---

pub fn check_coin_deny_list_v2_during_signing(
    address: SuiAddress,
    input_objects: &CheckedInputObjects,
    receiving_objects: &ReceivingObjects,
    funds_withdraw_types: BTreeSet<String>,
    object_store: &dyn ObjectStore,
) -> UserInputResult {
    let mut coin_types =
        input_object_coin_types_for_denylist_check(input_objects, receiving_objects);
    coin_types.extend(funds_withdraw_types);

    for coin_type in coin_types {
        let Some(deny_list) = get_per_type_coin_deny_list_v2(&coin_type, object_store) else {
            continue;
        };
        if check_global_pause(&deny_list, object_store, None) {
            return Err(UserInputError::CoinTypeGlobalPause { coin_type });
        }
        if check_address_denied_by_config(&deny_list, address, object_store, None) {
            return Err(UserInputError::AddressDeniedForCoin { address, coin_type });
        }
    }
    Ok(())
}
