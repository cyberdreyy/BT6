### Title
Compute-budget instruction index truncation (`i as u8`) causes silently wrong `TransactionError::DuplicateInstruction`/`InstructionError` index attribution for transactions with 256+ instructions - ([File: compute-budget-instruction/src/compute_budget_instruction_details.rs])

### Summary
`ComputeBudgetInstructionDetails::try_from` enumerates a transaction's instructions and truncates the loop index to `u8` via `i as u8` before recording/validating compute-budget instructions. For a message with more than 256 instructions, two distinct instruction positions whose indices differ by a multiple of 256 collide onto the same `u8` value, causing `process_instruction` to misattribute or misreport the instruction index in `TransactionError::DuplicateInstruction`/`InstructionError`. Because Rust's `as u8` cast wraps silently rather than panicking, this is not a crash but a decoder misreporting bug.

### Finding Description
In `ComputeBudgetInstructionDetails::try_from`, the per-instruction loop is: [1](#0-0) 

The `i` value comes from `.enumerate()` over the full instruction list and is truncated with `i as u8` before being passed to `process_instruction`, which stores `(index, value)` tuples and raises `TransactionError::DuplicateInstruction(index)` on repeated compute-budget instruction kinds: [2](#0-1) 

If a legacy/v0 message contains more than 256 top-level instructions, any two real instruction positions `i` and `i + 256*k` collapse to the same stored `u8` index. If both positions contain `ComputeBudgetInstruction::SetComputeUnitLimit` (or any other compute-budget variant), the second occurrence is reported as `TransactionError::DuplicateInstruction(i mod 256)` instead of reflecting its true position `i + 256`, and if the first position is a *different* kind of instruction whose real index happens to alias, the stored `(index, value)` tuple used later in `sanitize_and_convert_to_compute_budget_limits`'s `InstructionError` reporting is likewise wrong. This path is reachable from `try_from` in `RuntimeTransaction::try_create`, which is invoked by `sanitize_transaction` from `rpc.rs`'s `simulate_transaction` handler for an unprivileged, unsigned-or-signed `simulateTransaction` JSON-RPC call. No existing guard in this function limits instruction count to ≤255 before the enumeration/cast; the `u8` truncation is unconditional. Note that Rust's `as u8` cast is a non-panicking wrapping cast, so this does **not** cause a validator panic/abort — the earlier premise of a crash is incorrect, but the wrong-index misreporting is real and directly reachable.

### Impact Explanation
A single `simulateTransaction` call with a crafted message containing 257+ instructions (two `SetComputeUnitLimit` instructions at real positions `i` and `i+256`) causes the validator to report a `TransactionError::DuplicateInstruction` (or `InstructionError`) with an index that does not correspond to the real, wire-format instruction index. This matches the explicitly accepted "decoder ... misreporting" category in SECURITY.md's scope; it is not a crash and does not corrupt consensus state, but it does return misleading transaction-error metadata to a client from a legitimate single RPC call.

### Likelihood Explanation
Feasible with one unprivileged `simulateTransaction` call. Building a message with 256+ minimal instructions (each roughly 3 bytes: 1-byte program-id index + compact-array headers for 0 accounts/0 data) is well within the base64-encoded size handled by the RPC decode path, since minimal instructions can fit hundreds of entries in well under the wire packet-size envelope. No commitment, subscription-quota, or explicit instruction-count guard blocks this in `ComputeBudgetInstructionDetails::try_from`. Reproducible deterministically for any instruction count ≥ 256 with the described collision pattern.

### Recommendation
Bound the instruction-index type/consistency: either reject messages with more than 255 instructions before calling `ComputeBudgetInstructionDetails::try_from` (consistent with the `u8` index domain), or change the stored index type to a wider integer (e.g., `u16`) throughout `ComputeBudgetInstructionDetails` and the corresponding `TransactionError`/`InstructionError` index fields so no truncation/collision can occur, using `try_into` with an explicit error path instead of `as u8` if a hard cap is required.

### Proof of Concept
```rust
// compute-budget-instruction/src/compute_budget_instruction_details.rs (test module)
#[test]
fn test_try_from_index_truncation_collision() {
    let payer_keypair = Keypair::new();
    let mut instructions = Vec::new();
    // filler instruction at index 0 (non compute-budget)
    instructions.push(Instruction::new_with_bincode(Pubkey::new_unique(), &(), vec![]));
    // pad with 255 more filler instructions so the second CU-limit ix lands at real index 256
    for _ in 0..255 {
        instructions.push(Instruction::new_with_bincode(Pubkey::new_unique(), &(), vec![]));
    }
    // real index 0: SetComputeUnitLimit
    instructions[0] = ComputeBudgetInstruction::set_compute_unit_limit(1_000);
    // real index 256: SetComputeUnitLimit (aliases to u8 index 0)
    instructions.push(ComputeBudgetInstruction::set_compute_unit_limit(2_000));

    let tx = build_sanitized_transaction(&instructions);
    let result = ComputeBudgetInstructionDetails::try_from(
        SVMStaticMessage::program_instructions_iter(&tx),
    );

    // BUG: reports DuplicateInstruction(0) even though the real duplicate
    // instruction is at wire index 256, not 0.
    assert_eq!(result, Err(TransactionError::DuplicateInstruction(0)));
    // Expected (post-fix) behavior would be a distinguishable/correct index,
    // e.g. DuplicateInstruction(256) if index type were widened, or an
    // explicit "too many instructions" rejection before reaching try_from.
}
```
