### Title
Stale order fee bound: `order_execution_max_fee` is re-read at execution time instead of being snapshotted when the order is placed - ([File: programs/marginfi/src/instructions/marginfi_account/order.rs])

### Summary
This is a structural analog of the SYMM-IO "fee changed → refund/enforcement mismatch" bug class. In marginfi-v2, a user's take-profit/stop-loss `Order` is created via `place_order` without recording the `order_execution_max_fee` that was in effect at creation time. When the order is later executed via `end_execute_order`, the program reads the *current* global `fee_state.order_execution_max_fee` to compute the maximum share of the position a keeper may extract as profit. If the global fee admin changes this parameter between order placement and order execution, the fee bound actually enforced against the user's position differs from the bound that existed (and that the user implicitly relied on) when the order was created.

### Finding Description
When a user places a take-profit order, no fee-related value besides the flat SOL init fee is stored on the `Order` account: [1](#0-0) 

The `Order` struct itself only stores `stop_loss`, `take_profit`, `max_slippage`, `tags`, etc. — it does not persist a per-order fee bound: [2](#0-1) 

Later, at execution time (`end_execute_order`), the program loads the *current* `fee_state` account and uses its `order_execution_max_fee` field live to compute the fraction of the position value a keeper is allowed to withdraw as profit for a take-profit order: [3](#0-2) 

The `order_execution_max_fee` field lives in the global, singleton `FeeState` account and can be changed at any time by the `global_fee_admin` via `edit_global_fee_state` / `edit_fee_state`: [4](#0-3) [5](#0-4) 

This mirrors the SYMM-IO root cause exactly: `getTradingFee` is computed using the *current* `symbol.tradingFee` both at quote-creation and at cancel/refund time, so a fee change between the two events causes a mismatch between what was charged and what is later used to settle. Here, the analogous "commit-then-settle" gap is: the max-fee bound is not fixed/snapshotted at `place_order` time, but is instead re-evaluated with the live global config at `end_execute_order` time — a permissionless action that can be called by any keeper, potentially long after the order was placed.

### Impact Explanation
If the global fee admin raises `order_execution_max_fee` after a user places a take-profit order, the `max_fee_frac` used in the check `net >= allowed_diff` becomes looser, allowing a keeper to extract a materially larger profit margin from the user's position than existed (and was implicitly bounded) at the time the user placed the order. The user has no ability to consent to, anticipate, or cancel this changed treatment except by manually closing the order before it triggers, and may not even be aware their standing order's economics have shifted. This is a direct, exploitable value-redirection from the order-placing user to the executing keeper, driven purely by re-reading a mutable global parameter at settlement instead of locking it in at order creation — the same defect class as the referenced SYMM-IO issue.

### Likelihood Explanation
Likelihood is moderate: it requires the fee admin to actually change `order_execution_max_fee` while orders are outstanding, which is an expected/legitimate operational action (the config is designed to be admin-tunable, as shown in `edit_fee_state`), not an attack. Any live order placed before such a change is retroactively affected the next time a keeper executes it, with no re-confirmation from the order owner.

### Recommendation
Snapshot the relevant fee bound (`order_execution_max_fee`) into the `Order` account at `place_order` time, and use that stored value in `end_execute_order` rather than re-reading the live `FeeState`. This ensures the max-fee guarantee visible to the user when placing the order remains fixed for the life of that order, consistent with the SYMM-IO fix recommendation of storing the fee at creation time and using the stored value at settlement.

### Proof of Concept
1. User deposits collateral and borrows, then calls `place_order` to create a take-profit `Order` while `fee_state.order_execution_max_fee = 5%` (the deployed default per `ORDER_EXECUTION_MAX_FEE`). [6](#0-5) 
2. Before the order triggers, the `global_fee_admin` calls `edit_global_fee_state` and raises `order_execution_max_fee` to, e.g., 20%. [4](#0-3) 
3. Once the take-profit trigger condition is met, any keeper calls `start_execute_order` / `end_execute_order`. In `end_execute_order`, `max_fee_frac` is computed from the now-20% `order_execution_max_fee`, permitting the keeper to leave the user with `net >= (1 - 0.20) * start_health` instead of the `(1 - 0.05) * start_health` bound that existed when the user placed the order. [3](#0-2) 
4. The keeper extracts up to 20% of the position's equity as profit — 4x what the user could have expected based on the fee configuration in place when they created the order — without the user's knowledge or consent.

(Note: full call chain wiring for `start_execute_order`/`ExecuteOrderRecord` could not be fully re-verified within the available tool budget due to a read_file parameter error late in the investigation; the analysis above is based on the confirmed code at `end_execute_order` reading `fee_state.order_execution_max_fee` live and the `Order`/`place_order` code confirmed not to persist any fee bound.)

```rust
impl OrderImpl for Order {
    fn initialize(
        &mut self,
        marginfi_account: Pubkey,
        trigger: OrderTrigger,
        tags: [u16; ORDER_ACTIVE_TAGS],
        bump: u8,
    ) -> MarginfiResult {
        self.marginfi_account = marginfi_account;
        match trigger {
            OrderTrigger::StopLoss {
                threshold,
                max_slippage,
            } => {
                self.trigger = OrderTriggerType::StopLoss;
                self.stop_loss = threshold;
                self.max_slippage = max_slippage;
                self.take_profit = WrappedI80F48::default();
                // Threshold must be > 0
                let val: I80F48 = self.stop_loss.into();
                check!(
                    val > I80F48::ZERO,
                    MarginfiError::InvalidOrderTakeProfitOrStopLoss
                );
            }
            OrderTrigger::TakeProfit {
                threshold,
                max_slippage,
            } => {
                self.trigger = OrderTriggerType::TakeProfit;
                self.take_profit = threshold;
                self.max_slippage = max_slippage;
                self.stop_loss = WrappedI80F48::default();
                // Threshold must be > 0
                let val: I80F48 = self.take_profit.into();
                check!(
                    val > I80F48::ZERO,
                    MarginfiError::InvalidOrderTakeProfitOrStopLoss
                );
            }
            OrderTrigger::Both {
                stop_loss,
                take_profit,
                max_slippage,
            } => {
                self.trigger = OrderTriggerType::Both;
                self.stop_loss = stop_loss;
                self.take_profit = take_profit;
                self.max_slippage = max_slippage;
                // Both thresholds must be > 0 && tp > sl
                let sl: I80F48 = self.stop_loss.into();
                let tp: I80F48 = self.take_profit.into();
                check!(
                    sl > I80F48::ZERO && tp > sl,
                    MarginfiError::InvalidOrderTakeProfitOrStopLoss
                );
            }
        }

        // Orders are capped at MAX_ORDER_SLIPPAGE. Stop-loss execution is also gated by maintenance
        // health. Take-profit execution is additionally bounded by ORDER_EXECUTION_MAX_FEE, which
        // usually dominates the slippage constraint at this cap,
        check!(
            self.max_slippage <= MAX_ORDER_SLIPPAGE,
            MarginfiError::SlippageTooHigh
        );

        self.tags = tags;
        self.bump = bump;

        Ok(())
    }
```
