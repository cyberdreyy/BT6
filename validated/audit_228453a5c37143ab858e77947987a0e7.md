### Title
Unprotected `initializeConfig` in `BridgeCommittee` Can Be Front-Run to Permanently Misconfigure the Bridge — (`bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` is an `external` function with no access control. It can be called by any address between the moment the `BridgeCommittee` proxy is deployed and the moment the deployer calls it. An attacker who front-runs this call can permanently bind the committee to a malicious `IBridgeConfig` implementation, corrupting every downstream bridge operation that depends on config (token address resolution, chain support checks, rate-limit USD calculations). Because there is no `updateConfig` path, the only recovery is a full committee-signed contract upgrade.

---

### Finding Description

`BridgeCommittee.initializeConfig` is declared `external` with a single guard:

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

There is no `onlyOwner`, no committee-signature check, and no `initializer` modifier. The only protection is the one-time `config == address(0)` guard, which means whoever calls this function first wins permanently.

The deployment script submits these as **separate on-chain transactions** in sequence:

1. Deploy `BridgeCommittee` proxy (atomically calls `initialize`)
2. Deploy `BridgeConfig` proxy (atomically calls `initialize`)
3. Call `BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig))` ← **front-runnable**
4. Call `committeeImplementation.initializeConfig(address(bridgeConfig))` ← **front-runnable**
5. Deploy `BridgeLimiter` (calls `committee.config().isChainSupported()` during init)
6. Deploy `SuiBridge` [2](#0-1) 

Between steps 1 and 3, the `BridgeCommittee` proxy exists on-chain with `config == address(0)`, and any address can call `initializeConfig` with an arbitrary `_config` argument.

The `CommitteeUpgradeable` base contract does call `_disableInitializers()` in its constructor, which protects the `initialize()` function on the bare implementation contract. However, `initializeConfig` carries **no** `initializer` modifier, so `_disableInitializers()` provides zero protection for it. [3](#0-2) 

---

### Impact Explanation

Every critical bridge path reads from `committee.config()`:

- `SuiBridge.transferBridgedTokensWithSignatures` resolves the ERC-20 token address via `committee.config().tokenAddressOf(tokenID)` and checks the target chain via `committee.config().isChainSupported()`.
- `BridgeLimiter.calculateAmountInUSD` calls `committee.config().tokenAddressOf(tokenID)` and `committee.config().tokenPriceOf(tokenID)`.
- `BridgeLimiter.initialize` calls `committee.config().isChainSupported(chainIDs[i])` during its own initialization. [4](#0-3) [5](#0-4) 

A malicious `IBridgeConfig` can:

| Malicious return value | Downstream effect |
|---|---|
| `tokenAddressOf()` → `address(0)` | Every `transferBridgedTokensWithSignatures` reverts at `IERC20Metadata(address(0)).decimals()` → vault funds permanently locked |
| `tokenPriceOf()` → `0` | `calculateAmountInUSD` returns 0 → rate limiter is silently disabled |
| `isChainSupported()` → always `true` | `BridgeLimiter.initialize` accepts any chain ID; `onlySupportedChain` modifier is bypassed |

Once set, `config` cannot be changed without a committee-signed `upgradeWithSignatures` call. If the bridge is already live and holding user funds when the malicious config is injected (or if the deployer does not detect the failure and proceeds), those funds are permanently locked in `BridgeVault` because every withdrawal path through `SuiBridge` will revert.

---

### Likelihood Explanation

- The attack requires only a standard Ethereum mempool front-run: watch for the `BridgeCommittee` proxy deployment, then submit `initializeConfig(maliciousConfig)` with a higher gas price before the deployer's transaction lands.
- No special privilege, stake, or committee membership is required — any EOA can execute this.
- The deployment script broadcasts each step as a separate transaction, creating an unavoidable window on any public network. [6](#0-5) 

---

### Recommendation

**Short term:** Add an access-control check to `initializeConfig`. The simplest fix is to restrict it to the deployer address captured during `initialize`, or to require a committee-signed message:

```solidity
// Option A: restrict to the address that called initialize
address private _deployer;

function initialize(...) external initializer {
    _deployer = msg.sender;
    ...
}

function initializeConfig(address _config) external {
    require(msg.sender == _deployer, "BridgeCommittee: unauthorized");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
    _deployer = address(0); // clear after use
}
```

**Alternative:** Fold `initializeConfig` into the main `initialize` call by passing `_config` as a parameter, eliminating the two-step window entirely.

**Long term:** Audit all `external` functions that lack the `initializer` modifier but perform one-time state writes. The `_disableInitializers()` guard in `CommitteeUpgradeable`'s constructor only protects functions decorated with `initializer`; it does not protect ad-hoc one-time setters like `initializeConfig`. [7](#0-6)

    function isChainSupported(uint8) external pure returns (bool) { return true; }
