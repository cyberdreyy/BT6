### Title
Reentrant `transferFrom` inflates tranche mint via balance-delta accounting, draining the vault - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.depositAA`/`depositBB` (lines 99-110) are not reentrancy-guarded. `_deposit` snapshots `preBal`, calls `_transferUnderlyingsFrom`, then mints tranche shares for the full post-transfer balance delta (lines 203-206). If the vault's underlying `token` executes a sender/receiver hook during `transferFrom` (e.g., an ERC777-style token), the attacker can reenter `depositAA` inside the outer transfer. The inner deposit's tokens are still in the contract when the outer call resumes, so the outer delta covers both deposits — the same underlying is credited as new NAV twice, minting unbacked tranche shares.

### Finding Description
- `depositAA(_amount)` → `_deposit(_amount, AATranche)` at `contracts/IdleCDOCreditVault.sol:99-110`, no `nonReentrant` modifier anywhere on the credit-vault deposit path.
- `_deposit` computes `_preBal = _contractTokenBalance(token)` (line 203), transfers (line 204), then `_mintSharesAtCurrPrice(balance - _preBal, msg.sender, _tranche)` (line 206), which also adds that delta to `lastNAVAA`/`lastNAVBB` via `_mintShares` (lines 355-363).
- Sequence: attacker calls `depositAA(A)`. During `transferFrom`, the token's `tokensToSend` hook reenters `depositAA(B)` (attacker pre-approved 2A). Inner `_deposit` mints B shares for B tokens received. Outer `_deposit` resumes and measures `balance - _preBal = A + B`, minting `A + B` shares. Total shares minted = `A + 2B` for only `A + B` tokens paid; NAV attribution is likewise overstated by B.
- The strategy pull `IIdleCDOStrategy(strategy).deposit(_amount)` (line 211) still succeeds because total received equals total pulled; only the share issuance is corrupted.
- Existing guards don't stop it: `whenNotPaused`, `_guarded`, KYC (`isWalletAllowed`) and the balance-delta skim protection all operate on the assumption that each `_deposit`'s delta contains only its own transfer.

### Impact Explanation
Direct theft / insolvency. The attacker mints tranche shares exceeding their paid-in basis by B per reentrant nesting (repeatable). Since tranche shares redeem against `getContractValue()` / epoch withdraw flows, the inflated supply lets the attacker claim more than deposited, socializing the shortfall onto honest AA/BB lenders — effectively draining the vault pro rata up to the recycled amount.

### Likelihood Explanation
Requires the vault's underlying token to invoke a controllable callback inside `transferFrom` (ERC777-style send/receive hooks) — plausible for vaults whose pool currency is an ERC777 or hook-enabled stablecoin. No privileged role needed; any KYC-passing lender can execute it in the buffer phase via a single transaction. For plain ERC20 underlyings without hooks (e.g., USDC), the path is not exploitable.

### Recommendation
Add `nonReentrant` (e.g., inherit `ReentrancyGuardInitialize`/`ReentrancyGuardUpgradeable` as `IdleCreditVault` already does) to `depositAA`, `depositBB`, and all withdraw/claim entry points in `IdleCDOCreditVault`/`IdleCDOEpochVariant`. Alternatively, mint based on a fixed `_amount` captured before the transfer and measure the delta only for fee-on-transfer tolerance with an upper bound of `_amount`.

    address public attacker;
    bool public armed;
    constructor() ERC20("H", "H") {}
    function setAttacker(address a) external { attacker = a; }
    function arm(bool v) external { armed = v; }
    function mint(address to, uint256 amt) external { _mint(to, amt); }
    function transferFrom(address from, address to, uint256 amt) public override returns (bool) {
        bool ok = super.transferFrom(from, to, amt);
        if (armed && msg.sender != attacker && from == attacker) {
            armed = false;
            // reenter the CDO during the outer deposit's transfer
            IdleCDOCreditVault(msg.sender).depositAA(amt);
        }
        return ok;
    }
}
