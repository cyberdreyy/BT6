### Title
Stale instant-withdraw receipt basis corrupts default-recovery accounting and strands recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a use-after-free: `xa_for_each()` iterates an xarray while a concurrent `ucma_leave_multicast()` frees the `mc` entry, so the scan reads stale/freed membership data. The vault analog is the same shape: instant-withdraw claims are keyed per epoch (`instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`), but a *successful funded claim* never clears the per-epoch entry. Later, `finalizeDefaultRecovery` re-reads ("iterates") that per-epoch aggregate as if it still represented live claims, and `_claimDefaultedInstantWithdrawRequest` re-reads the per-user entry. The cleanup pass consumes entries that were already paid out — a stale-basis consumption identical in consequence to the kernel's scan of a freed `mc`.

### Finding Description
`requestInstantWithdraw` records two accounting layers: the aggregate `instantWithdrawsRequests[_user]` and the per-epoch `instantWithdrawsRequestsByEpoch[_user][epochNumber]` / `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) .

When the CDO funds instant claims (`collectInstantWithdrawFunds` reduces only `pendingInstantWithdraws`) and a user claims via `claimInstantWithdrawRequest`, the function burns the receipt and zeroes `instantWithdrawsRequests[_user]` — but **does not** clear `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrement `instantWithdrawClaimsByEpoch[epoch]` [2](#0-1) . The per-epoch entry is logically freed (claim paid) but the bookkeeping still points at it — the exact "element freed while still linked in the collection" pattern.

Consequences at `finalizeDefaultRecovery` (reachable when `pendingInstantWithdraws != 0`, i.e., a partially funded instant queue at default):

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes already-claimed amounts → `totalBasis` overstated [3](#0-2) .
2. `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as "already-held underlying reserved for those claims" and adds it to `reserveAmount` — but that portion was already paid out to claimers, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed on phantom reserve [4](#0-3) [5](#0-4) .
3. Post-finalization, `_claimDefaultedInstantWithdrawRequest` still finds stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` for users who already claimed; `instantWithdrawsRequests[_user] -= claimBasis` underflows on a zeroed entry and reverts, permanently DoS-ing `claimInstantWithdrawRequest` for any address that both claimed a funded instant receipt and still holds any later instant position [6](#0-5) .

### Impact Explanation
Invariant broken: **one receipt one payout / solvency of the recovery reserve**. The reserve math counts paid-out underlying as held collateral, so `defaultRecoveryPrice` is set above what the strategy actually holds for pending claims. Earlier default claimants (normal pending withdraws via `_claimDefaultedWithdrawRequest` and unfunded instant claims) are over-paid relative to true holdings, and the last claimants' `_transferDefaultRecovery` transfers revert on insufficient balance — permanent freezing of unclaimed recovery. Quantified loss: up to the total amount of instant receipts claimed funded in the default epoch, i.e., `instantWithdrawClaimsByEpoch[defaultEpoch] - pendingInstantWithdraws` worth of phantom reserve. No existing guard stops this: the `defaultRecoveryFinalized`/`defaultInstantWithdrawsFinalized` path assumes the per-epoch aggregate equals live claims, and the underflow revert locks the inconsistency in place.

### Likelihood Explanation
Requires a specific-but-organic sequence in one epoch (attacker need not be privileged — a KYC'd lender/tranche holder suffices as the instant-withdrawer):

- Epoch running with instant-withdraw enabled; users request instant withdraws.
- CDO funds only part of the queue (`getInstantWithdrawFunds`/partial collect), so `pendingInstantWithdraws != 0` while `instantWithdrawClaimsByEpoch[epoch]` exceeds it.
- Some users claim their funded receipts (ordinary `claimInstantWithdrawRequest` — this is the "free" that leaves the stale entry).
- Borrower defaults mid-epoch; manager/owner call the honest `finalizeDefault`/`finalizeDefaultRecovery` path.

Likelihood is moderate: it needs a partial instant funding followed by a default in the same epoch, but every step is a normal protocol operation, not attacker-exotic.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting alongside the aggregate: `instantWithdrawsRequestsByEpoch[_user][epoch]` must be decremented (and `instantWithdrawClaimsByEpoch[epoch]` reduced by the claimed basis, tracking the request epoch) when the claim is paid, mirroring how `_claimDefaultedInstantWithdrawRequest` already does the decrement on the recovery path. Alternatively, key the funded-claim cleanup by `lastWithdrawRequest`-style epoch tracking so finalization only ever sees live claims — i.e., hold the "lock" on the entry's lifecycle: remove it from the collection when it is freed.

### Proof of Concept
Foundry fork PoC sketch (solidity, against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// setup: enable instant withdraw, deposit via AA tranche with KYC'd users
// epoch N running
// 1) user1 requests instant withdraw X, user2 requests Y
// 2) CDO collects funds for X only: collectInstantWithdrawFunds(X)
//    -> pendingInstantWithdraws == Y, instantWithdrawClaimsByEpoch[N] == X+Y
// 3) user1.claimInstantWithdrawRequest()   // paid X, per-epoch entry NOT cleared
// 4) borrower defaults; owner calls _handleBorrowerDefault -> finalizeDefaultRecovery(recovered, src)
//    -> basis includes X+Y (X stale), prefundedReserve += X (phantom)
//    -> recoveryPrice computed on reserve that includes already-paid X
// assert: strategy.underlying balance < reserveAmount * recoveryPrice-implied claims
// 5) user2 claims default epoch -> paid at inflated price
// 6) last claimant or user1's subsequent claimInstantWithdrawRequest reverts
//    (underflow on instantWithdrawsRequests[user1] or insufficient reserve)
```

Assert `underlying.balanceOf(strategy)` after finalization is less than `defaultRecoveryReserve` predicts, and that the final claimant's `_transferDefaultRecovery` reverts — demonstrating permanent freezing of unclaimed recovery funded by the stale-entry scan.
