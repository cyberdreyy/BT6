I have enough evidence to confirm the vulnerability. The `requestID` namespace in `httpTriggerHandler.callbacks` is global across all workflows (`map[string]savedCallback // requestID -> savedCallback`), and the duplicate-ID check in `setupCallback` only checks `h.callbacks[requestID]` — it never scopes by `workflowID`. Since `authorizeRequest` only validates that the caller owns *some* valid, authorized key for the workflow referenced in *their own* request (not that the `requestID` is unique to them), any actor holding valid JWT credentials for *any* workflow (including a trivially cheap workflow they register themselves) can pre-empt/squat an arbitrary client-chosen `requestID` string that belongs to a *different* workflow/user, causing the legitimate request with that same ID to be rejected with `ErrConflict` ("in-flight request").

### Title
Cross-workflow `requestID` squatting causes denial-of-service against arbitrary victim HTTP-trigger executions - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler` deduplicates incoming trigger requests using a single global map keyed only by the client-supplied `requestID`, with no binding to the requesting workflow or workflow owner. Any authenticated workflow caller can therefore choose a `requestID` that collides with another user's (current or anticipated) request and block that request from being processed, similarly to the `vestFor` bug where an unauthenticated/low-cost actor could lock a victim by racing an insignificant, unauthorized action into a shared, unscoped state slot.

### Finding Description
`HandleUserTriggerRequest` resolves the workflow (`resolveWorkflowID`), authorizes the caller against that workflow's authorized keys (`authorizeRequest`), checks rate limits, and only then calls `setupCallback`, which enforces uniqueness purely on `requestID`: [1](#0-0) [2](#0-1) 

The `callbacks` field is explicitly documented as `requestID -> savedCallback`, a flat namespace shared by all workflows served by the gateway: [3](#0-2) 

`authorizeRequest` only checks that the signer is an authorized key *for the workflow ID present in that specific request*; it does nothing to reserve or verify uniqueness of `requestID` with respect to other workflows: [4](#0-3) 

The only restriction on `requestID` content is that it be non-empty and not contain `/`; it is otherwise entirely attacker-chosen and unrelated to the workflow being authorized: [5](#0-4) 

Because the JWT/`authorizeRequest` check only validates the caller's own workflow ownership and never ties `requestID` to that specific workflow, a caller who is fully authorized on *Workflow A* (which they can register cheaply themselves, e.g. a throwaway test workflow) can submit a request carrying `requestID = X`, even though `X` is a value they know or predict will be used by a victim calling *Workflow B*. This is analogous to `vestFor` in the report: no cross-user authorization boundary exists on the shared/global resource (the `vestFor` amount timer vs. here the `requestID` slot), so a cheap, unrelated, "legitimate-looking" action from one actor can lock out a completely different, unrelated user.

### Impact Explanation
When the victim's legitimate request with the same `requestID` arrives, `setupCallback` returns `ErrConflict` ("in-flight request") and the victim's HTTP-triggered workflow execution is rejected/never delivered to their DON shard, as shown by the existing "duplicate request ID" test which exercises this exact code path: [6](#0-5) 

Impact is denial of service against a targeted user's workflow execution triggered via the gateway's HTTP trigger — the same execution attempt is blocked and the caller must retry with a different, unpredictable ID, which requires client-side coordination and defeats idempotency guarantees the `requestID` mechanism is meant to provide.

### Likelihood Explanation
Likelihood depends on the attacker's ability to predict or observe a victim's `requestID` before the victim's request lands (e.g., IDs generated with low entropy, reused, or observable via client-side/application logs), similar to the `vestFor` report which also required timing/front-running. Once a matching ID is guessed, exploitation itself is essentially free: registering a workflow to obtain a valid signing key is a normal, low-cost operation available to any onboarded workflow owner, and no elevated privilege is required to become "authorized" for the attacker's own workflow.

### Recommendation
Scope the `callbacks` map (and the duplicate-ID/conflict check) by a composite key of `(workflowID, requestID)` or `(workflowOwner, requestID)` rather than `requestID` alone, so that one workflow's requests can never collide with, or be blocked by, another workflow's `requestID` choices. This mirrors the reporter's suggested mitigation of scoping privileged/state-changing actions to the entity that legitimately owns the resource, rather than trusting an unscoped, attacker-controlled identifier.

### Proof of Concept
1. Attacker registers/owns Workflow A and obtains a valid authorized signing key for it (a normal, low-barrier operation).
2. Attacker learns or predicts that Victim will soon submit a trigger request to Workflow B using `requestID = "X"` (e.g., a deterministic or observable client-generated ID).
3. Attacker sends a `workflows.execute` JSON-RPC request for Workflow A with `id = "X"`, correctly signed with their own authorized key, which passes `authorizeRequest` for Workflow A and successfully calls `setupCallback`, inserting `h.callbacks["X"]`.
4. Victim's subsequent legitimate request for Workflow B with `id = "X"` reaches `setupCallback`, finds `h.callbacks["X"]` already populated, and is rejected with `jsonrpc.ErrConflict` ("in-flight request ID"), exactly as demonstrated by the existing test `t.Run("duplicate request ID", ...)`. func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
