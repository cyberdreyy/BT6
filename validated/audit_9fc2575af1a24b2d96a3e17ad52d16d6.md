### Title
ETH sent to `ConvexStrategyETH` is permanently locked — `receive()` accepts ETH but no function can recover it - (File: contracts/strategies/convex/ConvexStrategyETH.sol)

### Summary
`ConvexStrategyETH` declares a bare `receive() external payable {}` that accepts ETH from any sender, but neither it nor `ConvexBaseStrategy` exposes any ETH-aware recovery path. The only rescue function, `transferToken`, uses `IERC20Detailed(_token).safeTransfer`, which cannot move native ETH. Any ETH held by the strategy is permanently frozen.

### Finding Description
In `_depositInCurve`, the strategy unwraps its full WETH balance into ETH and forwards it to a Curve ETH pool via `add_liquidity{value: _balance}` [1](#0-0) . ETH can remain or arrive at the contract through several realistic paths:

- Curve ETH pools (e.g. steth/eth-style pools using `use_eth`) can return unspent ETH change to `msg.sender` on `add_liquidity`; the strategy's `receive()` accepts it and it sits idle.
- Anyone can force ETH into the contract via `selfdestruct`, or simply send ETH to the payable `receive()` — unlike `LidoCDOTrancheGateway`, which restricts `receive()` to the WETH contract [2](#0-1) .
- Any ETH left behind after a harvest is never redeployed: the next `redeemRewards` unwraps only the WETH balance, and `price()` accounts only for staked LP tokens [3](#0-2) .

The owner-only `transferToken` emergency function cannot help: passing `address(0)` or the `0xEeee...` pseudo-address to `safeTransfer` would execute a low-level call to a non-token address (either reverting or being a no-op), never moving the native balance [4](#0-3) . No other function in `ConvexBaseStrategy`, `BaseStrategy`, or the CDO reads or transfers `address(this).balance`.

### Impact Explanation
Any ETH that lands in the strategy — whether refunded by Curve, force-sent via `selfdestruct`, or accidentally transferred — is permanently frozen. It is excluded from `price()`/`totalLpTokensStaked`, so it is not credited to any depositor and cannot be withdrawn by the owner, the CDO, or governance. This is a direct loss equal to the stuck ETH amount.

### Likelihood Explanation
Low-to-moderate. The primary realistic trigger is Curve refunding dust ETH after `add_liquidity` on ETH-paired pools, plus the ever-present possibility of forced `selfdestruct` transfers or mistaken sends. The contract intentionally exposes `receive()` to support the WETH-unwrap flow, but the unrestricted acceptance combined with a purely ERC20-only rescue path guarantees permanence for any stuck balance. Since the strategy is deployed behind an upgradeable proxy pattern, an upgrade could in principle recover funds, but the deployed code itself contains no mechanism — same severity class as the referenced XProvider finding.

### Recommendation
Either:
- Restrict `receive()` to the WETH contract (`require(msg.sender == WETH)`), matching the `LidoCDOTrancheGateway` pattern, so only the intended unwrap can send ETH; or
- Extend `transferToken` (or add `sweepETH`) to handle native ETH, e.g. `(bool ok,) = _to.call{value: address(this).balance}("")`.

        assertEq(address(strategy).balance, 1 ether);

        // No callable path moves ETH out:
        // - transferToken() only calls IERC20Detailed.safeTransfer (ERC20 only)
        // - price() only accounts totalLpTokensStaked
        // Owner has no ETH recovery function -> 1 ether is permanently frozen.
    }

contract Stub is ConvexStrategyETH {
    function _curveUnderlyingsSize() internal pure override returns (uint256) { return 2; }
    function _depositInCurve(uint256) internal override {}
}

contract SelfDestructSender {
    constructor() payable {}
    function destroy(address payable target) external {
        selfdestruct(target);
    }
}

On a mainnet fork the same can be shown by deploying the real `ConvexStrategyETH`, sending ETH to it (or invoking a Curve `add_liquidity` that returns ETH change), and observing `address(strategy).balance > 0` with no function able to transfer it out.


In ThankGod76/idle-tranches--012, modify contracts/strategies/convex/ConvexStrategyETH.sol. The contract declares `receive() external payable {}` at line 35 and accepts ETH from anyone, but neither it nor ConvexBaseStrategy.sol (transferToken at lines 423-429 only handles ERC20 via safeTransfer) can move native ETH, permanently freezing refunded/forced/accidental ETH. Fix by either (a) restricting receive to the WETH contract: `receive() external payable { require(msg.sender == WETH, "only-weth"); }` matching contracts/strategies/lido/LidoCDOTrancheGateway.sol lines 99-101, or (b) adding an onlyOwner `sweepETH(address _to)` function that transfers `address(this).balance` via `.call{value:...}`. Add a Foundry test verifying ETH can no longer be sent by arbitrary addresses, or that sweep works, under test/foundry/.
