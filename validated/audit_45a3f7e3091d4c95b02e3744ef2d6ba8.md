### Title
Instant-withdraw receipts of the defaulted epoch are skipped by default-recovery accounting due to an `epochNumber` boundary mismatch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` keys a user's receipt under the `epochNumber` that was current **at request time**. But `epochNumber` is incremented inside `deposit()` while `isEpochRunning()` is still true — i.e., during `stopEpoch`, *before* any default handling or recovery finalization. All post-stop lookups (`defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, `_claimDefaultedInstantWithdrawRequest`, `defaultRecoveryEpoch`) read `instantWithdrawClaimsByEpoch[epochNumber]` / `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` at the **incremented** index, so receipts recorded under the just-ended epoch are invisible. This is the same bug class as the Etron xHCI fix: a check performed after the "segment pointer" already points at the boundary element, so the next index resolves to an empty slot instead of the real data.

### Finding Description
- `deposit()` bumps the epoch counter while the epoch is still flagged running (`IdleCreditVault.sol:607-611`). During `stopEpoch`/`stopEpochWithDuration`, the CDO deposits into the strategy before `isEpochRunning` flips false and before `_handleBorrowerDefault` runs, so by the time default is declared `epochNumber` is already `N+1`.
- Instant receipts requested during epoch `N` were recorded under `instantWithdrawsRequestsByEpoch[user][N]` and `instantWithdrawClaimsByEpoch[N]` (`IdleCreditVault.sol:367-374`).
- `finalizeDefaultRecovery` stores `defaultRecoveryEpoch = epochNumber` (= N+1) and computes `defaultPendingClaimBasis()` as `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (= key N+1 = 0) (`IdleCreditVault.sol:644-649, 693`).
- `_defaultPrefundedInstantReserve` compares `instantWithdrawClaimsByEpoch[epochNumber]` (0) against `pendingInstantWithdraws` (>0), so `instantBasis > pendingInstant` is false and the already-collected instant funds are *not* added to the reserve even though the contract holds them (`IdleCreditVault.sol:716-723`).
- `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` = `[user][N+1]` = 0 and returns without paying or burning (`IdleCreditVault.sol:843-845`), while `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` is true, so the gate `claimInstantWithdrawRequest` passes yet finds nothing.

### Impact Explanation
Two consequences: (1) the recovery price is computed on a `totalBasis` that excludes the unfunded instant claims of the defaulted epoch, overpaying normal receipt holders/active LPs at the expense of instant claimants; (2) instant-receipt holders of epoch N can never claim — their receipt tokens remain minted but `_claimDefaultedInstantWithdrawRequest` finds zero basis at key N+1, permanently freezing their share of the recovery reserve, and the "prefunded" portion that is actually held by the strategy is neither reserved nor claimable, so it is stranded. This is direct loss/freezing of unclaimed yield for an unprivileged instant-withdraw requester; no privileged role misbehavior is required, only the honest manager stopEpoch → default-finalization sequence.

### Likelihood Explanation
Requires the borrower to default (or funding to fail) in the same epoch in which at least one instant-withdraw request is pending/unfunded — i.e., `pendingInstantWithdraws != 0` at finalization. Instant withdrawals are triggered on APR decreases, which correlate with borrower stress, so co-occurrence is plausible. Caveat: I verified the read/write keys and the increment site, but did not fully trace every `stopEpoch` ordering path in `IdleCDOEpochVariant`/`IdleCDOEpochVariantPrefunded` (e.g., whether `deposit()` is always invoked before `_handleBorrowerDefault` in all default branches, including the prefunded variant). If any path declares default *before* the incrementing `deposit()`, this specific epoch-N case narrows to requests made in earlier epochs that were never claimed — which are still keyed at their old epoch and equally missed by `[epochNumber]` lookups.

### Recommendation
Track instant claims by the epoch in which they were requested *relative to the boundary*: either (a) snapshot `instantWithdrawClaimsByEpoch` into a "last epoch" slot before `epochNumber += 1` in `deposit()`, (b) record `defaultRecoveryEpoch` as the request epoch (e.g., `epochNumber - 1` when the default follows the stop-epoch increment), or (c) have `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest` aggregate claims for both `epochNumber` and `epochNumber - 1` (or maintain a `lastInstantClaimsEpoch` pointer set at request time). The equivalent of the kernel fix is to compare state rather than dereference the advanced pointer: gate recovery inclusion on the stored request epoch, not on the post-stop counter.

### Proof of Concept
```solidity
// Foundry fork PoC (contracts/strategies/idle/IdleCreditVault.sol)
function testInstantReceiptMissedOnDefault() public {
    // setup: deposits, startEpoch with instant withdrawals enabled
    _startEpochAndCheckPrices(0);

    // 1) user requests instant withdraw during epoch N (epochNumber == N)
    idleCDO.requestWithdraw(amount, AAtranche); // triggers requestInstantWithdraw via APR-delta path
    // instantWithdrawsRequestsByEpoch[user][N] = amount; instantWithdrawClaimsByEpoch[N] = amount

    // 2) warp past epoch end; manager stops epoch. Inside stopEpoch the CDO
    //    calls strategy.deposit(...) while isEpochRunning() == true -> epochNumber becomes N+1
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // borrower fails to fully fund -> _handleBorrowerDefault, then finalizeDefaultRecovery
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, interest); // funding partially fails -> defaulted = true

    // 3) finalize recovery
    cdoEpoch.finalizeDefault(...); // -> IdleCreditVault.finalizeDefaultRecovery(recovered, source)

    // defaultRecoveryEpoch == N+1 but receipts live under key N
    assertEq(strategy.instantWithdrawsRequestsByEpoch(user, strategy.defaultRecoveryEpoch()), 0);
    assertEq(strategy.instantWithdrawsRequestsByEpoch(user, N), amount);

    // 4) user can never claim the haircutted instant receipt
    vm.prank(address(cdoEpoch));
    strategy.claimInstantWithdrawRequest(user); // pays 0; instantWithdrawsRequests[user] stays > 0
    // user's underlying share of the reserve is permanently stranded in the strategy
}
```
Expected: the claim at step 4 returns 0 while `instantWithdrawsRequests[user] == amount` and the strategy retains the prefunded instant cash excluded from `defaultRecoveryReserve`, demonstrating both the under-priced recovery basis and the permanently unclaimable receipt.
