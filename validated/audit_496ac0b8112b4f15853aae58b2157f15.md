### Title
IDOR on GET /v2/jobs/:ID/runs/:runID allows reading pipeline run data (including task outputs) for jobs unrelated to the caller - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Show` fetches a pipeline run purely by `runID` and never validates that the run actually belongs to the `:ID` job segment in the URL, nor does it check that the authenticated principal (User or External Initiator) has any relationship to that job. Any authenticated caller (including an EI credential scoped to one job) can enumerate the auto-incrementing `runID` and retrieve run details — including task-run outputs that may contain sensitive bridge response data — belonging to any other job.

### Finding Description
`Show` parses only `c.Param("runID")`, builds a `pipeline.Run{}`, and calls `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)`: [1](#0-0) 

The `:ID` (job ID) path parameter is read nowhere in this handler — it is not used to look up the job, and it is not cross-checked against `pipelineRun.PipelineSpec.JobID` (or equivalent) after `FindRun` returns. Contrast this with `Create`, which explicitly special-cases `isUser` vs. EI callers using `auth.GetAuthenticatedUser(c)` before allowing an action: [2](#0-1) 

No such ownership/role check exists in `Show`. Because `pipeline.Run.ID` is a database-generated sequential identifier, once a caller is authenticated at all (any valid session, restricted API token, or EI credential accepted by the surrounding router middleware), it can query `GET /v2/jobs/{anyJobID}/runs/{guessedOrEnumeratedRunID}` and receive the full `presenters.NewPipelineRunResource` payload for a run belonging to an entirely different job, regardless of what job (if any) it is legitimately associated with. This is a cross-user/cross-job IDOR rooted purely in application logic in the handler itself, independent of whatever generic authentication wrapper is applied at the router level.

I was unable to fully inspect the exact route registration and middleware stack in `core/web/router.go` for this endpoint within the available search budget (matches for `PipelineRunsController` were found in that file, but I could not retrieve the surrounding route-group/role-wrapper code to confirm exactly which auth middleware wraps `Show`). Regardless of which generic authentication check gates the route, the vulnerability is that the handler performs no per-request authorization/ownership check tying the caller (or the `:ID` job) to the fetched run — so even a "just authenticated" check does not stop cross-job disclosure.

### Impact Explanation
An attacker holding only a low-privilege credential (e.g., an EI credential scoped to a single job, or a restricted API session) can read pipeline run details for arbitrary other jobs, including task-run inputs/outputs that may embed sensitive bridge response data, API keys embedded in task configs, or other job owners' data. This is a cross-user response confusion / unauthorized access to another job's run data, matching the "unauthorized job run" / sensitive data disclosure impact class.

### Likelihood Explanation
Exploitability requires only: (1) any valid, low-privilege authenticated credential accepted by whatever middleware wraps `/v2/jobs/:ID/runs/:runID`, and (2) knowledge or brute-force enumeration of a sequential `runID`. No special role, admin access, or job relationship is needed. This is trivially repeatable and scriptable (simple integer enumeration), making likelihood high once basic authentication is obtained.

### Recommendation
In `Show`, resolve and validate the job identified by `c.Param("ID")` first, then verify that the fetched `pipelineRun`'s associated job ID matches it before returning data (mirroring the job-scoped lookup already used in `Index`, which correctly filters `PipelineRuns` by `jobSpec.ID`). Additionally, if the caller is an External Initiator, restrict lookups to runs of jobs that EI is registered against, similar to the `isUser` gating already performed in `Create`.

### Proof of Concept
1. Create Job A (owned by/associated with EI-A) and Job B (unrelated job) each with at least one pipeline run, ensuring Job B's run's task outputs contain a distinguishable sensitive value (e.g., a fake bridge secret).
2. Authenticate as EI-A only (no relationship to Job B).
3. Call `GET /v2/jobs/{jobB.ID}/runs/{jobBRun.ID}` using EI-A's credentials.
4. Assert the response is `403`/`404` — currently, per the code path in `Show`, the handler returns `200` with the full `pipelineRun` presenter payload for Job B's run, disclosing Job B's data to EI-A.
5. Compare against `Index`, calling `GET /v2/jobs/{jobA.ID}/runs`, and confirm it correctly returns only Job A's runs (via `PipelineRuns(ctx, &jobSpec.ID, ...)`), highlighting the missing equivalent scoping in `Show`.

func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
