### Title
Unbounded `operator_fee_scalar` / `operator_fee_constant` Derived From L1 Deposit Data Allows Unlimited Per-Transaction Fee Extraction - (File: `crates/common/l1-fees/src/params.rs`)

### Summary
The Isthmus/Jovian operator-fee mechanism charges every L2 transaction an additional fee computed from `operator_fee_scalar` (`u32`) and `operator_fee_constant` (`u64`). These two values are decoded verbatim from the L1 attributes deposit transaction / `SystemConfig` update log and applied to fee computation with **no upper-bound validation anywhere in the derivation or execution path** — the same class of bug as the reported `_FEE_RATE_` issue, where a fee-rate-like variable can be set to an arbitrarily large value because no `require(feeRate <= MAX_FEE_RATE)`-style check exists.

### Finding Description
`OperatorFeeUpdate::try_from` decodes the scalar/constant straight from log bytes with only a length/pointer sanity check, not a value-range check: [1](#0-0) [2](#0-1) 

The Isthmus L1-info deposit calldata format also decodes these fields as raw fixed-width integers with no bound check applied: [3](#0-2) 

These unbounded values then feed directly into the fee formula that every non-deposit transaction pays, with only saturating arithmetic (no ceiling on the resulting fee amount): [4](#0-3) 

Unlike `l1_base_fee_scalar`/`l1_blob_base_fee_scalar` (which are themselves also unbounded but reflect a real, externally-observable L1 cost), `operator_fee_scalar`/`operator_fee_constant` are pure protocol-controlled multipliers with no cap comparable to the `MAX_FEE_RATE` the original report asked for. Both the txpool admission path (`apply_base_checks` / `tx_cost`) and the execution/settlement path (`BaseTxHandlerHooks::before_execution`/`operator_fee_charge`) trust this value unconditionally: [5](#0-4) [6](#0-5) 

### Impact Explanation
If `operator_fee_scalar` is set near `u32::MAX` (or `operator_fee_constant` near `u64::MAX`), every non-deposit transaction on the chain is charged an operator fee that can dwarf the gas cost itself (post-Jovian the scalar is additionally multiplied by `OPERATOR_FEE_JOVIAN_MULTIPLIER = 100`, so the effective ceiling is even higher: `gas * scalar * 100`). This lets whoever controls the `SystemConfig`/L1-attributes update effectively confiscate almost all of a transaction sender's declared max fee on every transaction — the same "steal tokens / excessive fees" impact described in the original report — with no on-chain safety rail comparable to a `MAX_FEE_RATE` check. It can also be used to grief the network by pricing all transactions out of anyone's ability to pay, since `ensure_can_pay_fees`/txpool admission will simply reject transactions once the operator fee exceeds the sender's balance, halting normal usage of the chain.

### Likelihood Explanation
The value is only settable by whoever can post the `OperatorFee` system-config update on L1 (protocol governance), so this is not exploitable by a generic unprivileged actor — it depends on that operator update path (governance key compromise, or governance error) rather than an unprivileged transaction. This mirrors the original finding's own caveat that the impact/likelihood depends on trusting the fee-setting role, and the report was still classified as valid specifically because no bound existed at all.

### Recommendation
Add an explicit maximum bound (e.g., a `MAX_OPERATOR_FEE_SCALAR` / `MAX_OPERATOR_FEE_CONSTANT`, or a combined maximum effective-fee-per-gas cap) enforced when applying `OperatorFeeUpdate` in `crates/common/genesis/src/updates/operator_fee.rs` and/or when decoding the Isthmus L1-info fields in `crates/consensus/protocol/src/info/isthmus.rs`, so `operator_fee_charge_inner` in `crates/common/l1-fees/src/params.rs` can never produce a fee representing an unreasonable multiple of the transaction's own gas cost — consistent with the recommendation to cap `_FEE_RATE_` in the original report.

### Proof of Concept
1. Post an L1 `SystemConfig` operator-fee update (or craft the Isthmus L1-attributes deposit calldata) with `operator_fee_scalar = u32::MAX` and `operator_fee_constant = u64::MAX`.
2. Once derived, `L1FeeParams::operator_fee_charge_inner` (`crates/common/l1-fees/src/params.rs:188-199`) computes `gas.saturating_mul(operator_fee_scalar) [* 100 post-Jovian] / 1_000_000 + operator_fee_constant` for every subsequent transaction.
3. Any user submitting a normal transaction is charged this inflated operator fee via `BaseTxHandlerHooks::before_execution`/`prepay` (`crates/common/evm2/src/handler.rs:108-132`, `crates/common/evm/src/eip8130.rs:1132-1174`), draining funds far beyond the transaction's actual gas cost, with no protocol-enforced ceiling to prevent it.

```rust
    /// Returns the Isthmus operator fee for `envelope` over `gas`. Zero for deposits and before
    /// Isthmus.
    ///
    /// The operator fee is an Isthmus feature; `L1FeeParams::operator_fee_charge` computes it
    /// unconditionally, so the Isthmus gate is applied here (matching the reference, which gates
    /// in its `reward_beneficiary`). The Base upgrade ladder is discriminant-ordered.
    fn operator_fee(host: &mut Evm<'_, BaseEvmTypes>, envelope: &BaseTxEnvelope, gas: u64) -> U256 {
        let Some(enveloped) = envelope.enveloped() else {
            return U256::ZERO;
        };
        let upgrade = host.config_spec_id().upgrade();
        if (upgrade as u8) < (BaseUpgrade::Isthmus as u8) {
            return U256::ZERO;
        }
        host.block_env().ext.operator_fee_charge(enveloped, U256::from(gas), upgrade)
    }
```
