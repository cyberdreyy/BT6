## Analysis: OETH Non-Rebasing Yield-Accounting Analog in Agave

### Title
SPL Token-2022 pre/post transaction balances and parsed instruction amounts ignore `InterestBearingConfig`/`ScaledUiAmountConfig`, causing RPC misreporting of token balances - (File: `runtime/src/transaction_balances.rs`)

### Summary
The external report describes a design flaw where a yield-bearing token (OETH) is held with a "rebasing/accrual" feature disabled, so the reported balance never reflects the token's true accrued value. Agave has a structurally identical bug class in its SPL Token-2022 balance/amount reporting paths: some code paths correctly resolve the mint's interest-bearing/scaled-UI-amount extension state to compute the "real" UI amount, while other, unprivileged-user-facing paths deliberately use only raw `decimals` and skip the extension config, silently under/over-reporting the token's true value.

### Finding Description
For SPL Token-2022 mints with the `InterestBearingConfig` or `ScaledUiAmountConfig` extensions, the canonical UI-amount computation is `token_amount_to_ui_amount_v3`, which requires an `SplTokenAdditionalDataV2` containing the extension config plus a timestamp in order to scale the raw amount correctly [1](#0-0) .

The RPC "current state" paths correctly populate this extension data by reading the mint account and extracting `InterestBearingConfig`/`ScaledUiAmountConfig`: [2](#0-1) [3](#0-2) 

However, the transaction-status pipeline that produces `preTokenBalances`/`postTokenBalances` for `getTransaction` explicitly and intentionally skips this extension resolution, using only `SplTokenAdditionalDataV2::with_decimals(decimals)`: [4](#0-3) 

The in-line comment confirms this is a known, deliberate simplification shared with the parsed-instruction path: "Same as parsed instruction data, ledger data always uses the raw token amount, and does not calculate the UI amount with any consideration for interest." The instruction-parsing code in `transaction-status/src/parse_token.rs` follows the same pattern when building `uiTokenAmount`/`amount` fields for `Transfer`/`TransferChecked`/etc. via `token_amount_to_ui_amount_v3` with a decimals-only `SplTokenAdditionalDataV2` [5](#0-4) .

### Impact Explanation
For any SPL Token-2022 mint using `InterestBearingConfig` or `ScaledUiAmountConfig` (the on-chain analogs of OETH's "rebasing" accrual), an unprivileged RPC client calling `getTransaction` sees `preTokenBalances`/`postTokenBalances.uiTokenAmount` values that do not reflect the same accrued/scaled value that `getTokenAccountBalance` or `getAccountInfo` (with `jsonParsed` encoding) would report for the exact same account and mint. This is a genuine "wrong ... account data returned" condition reachable via a single unprivileged JSON-RPC call, and it creates a persistent, silent inconsistency between two supposedly-equivalent read paths for the same protocol-level economic state — the direct analog of the OETH report where the reported/consumed balance is decoupled from the token's real accrued value because a scaling/accrual mechanism is not applied end-to-end.

### Likelihood Explanation
Any dApp, wallet, or explorer relying on `getTransaction`'s token balance deltas (a very common and unprivileged usage pattern) for a Token-2022 mint with either extension enabled will observe this discrepancy on every transaction, with no special preconditions beyond the mint using an extension that is broadly supported and increasingly adopted (interest-bearing/rebasing stablecoins, LSTs).

### Recommendation
Thread the mint's `InterestBearingConfig`/`ScaledUiAmountConfig` (and the relevant `unix_timestamp`) into `svm_token_info_to_token_balance` and the transaction-status instruction parsers, mirroring the resolution already done in `rpc/src/parsed_token_accounts.rs::get_additional_mint_data`, so that `preTokenBalances`/`postTokenBalances` and parsed instruction `uiTokenAmount` fields are consistent with `getTokenAccountBalance`/`getAccountInfo` for the same mint and slot.

### Proof of Concept
Not required beyond the existing code: the discrepancy is directly demonstrated by comparing `rpc/src/rpc.rs::get_token_supply`/`get_token_account_balance` (which build `SplTokenAdditionalDataV2` with `interest_bearing_config`/`scaled_ui_amount_config` populated, e.g. [6](#0-5) ) against `runtime/src/transaction_balances.rs::svm_token_info_to_token_balance` (which never populates either field, per the code's own comment at [7](#0-6) ).

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}

pub fn svm_token_info_to_token_balance(svm_info: SvmTokenInfo) -> TransactionTokenBalance {
    let SvmTokenInfo {
        account_index,
        mint,
        amount,
        owner,
        program_id,
        decimals,
    } = svm_info;
    TransactionTokenBalance {
        account_index,
        mint: mint.to_string(),
        ui_token_amount: token_amount_to_ui_amount_v3(
            amount,
            // NOTE: Same as parsed instruction data, ledger data always uses
            // the raw token amount, and does not calculate the UI amount with
            // any consideration for interest.
            &SplTokenAdditionalDataV2::with_decimals(decimals),
        ),
        owner: owner.to_string(),
        program_id: program_id.to_string(),
    }
}
