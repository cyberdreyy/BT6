### Title
Unbounded, admin-controlled Isthmus operator fee parameters allow the L1 SystemConfig owner to drain L2 transaction senders - ([File: crates/common/genesis/src/updates/operator_fee.rs])

### Summary
The Isthmus `operator_fee_scalar` (`u32`) and `operator_fee_constant` (`u64`) are set by the privileged L1 `SystemConfig` owner via a `ConfigUpdate(OperatorFee)` log and are applied by the L2 node with no upper-bound validation whatsoever, directly mirroring the reported class of bug: a privileged admin/owner role can set an unconstrained fee parameter that is later charged against ordinary users with no cap.

### Finding Description
`OperatorFeeUpdate::try_from` decodes the raw `operator_fee_scalar`/`operator_fee_constant` values straight from the L1 log payload with only structural (ABI-encoding) validation, and `OperatorFeeUpdate::apply` writes them into `SystemConfig` unconditionally, with no range/sanity check on the values. [1](#0-0) [2](#0-1) 

These values propagate through `SystemConfigUpdate::apply` into the L1 attributes deposit for every subsequent L2 block, and are read back by the EVM execution layer (`L1BlockInfo`/`L1FeeParams`) to compute the operator fee charged on every non-deposit transaction. [3](#0-2) [4](#0-3) 

The computed fee is deducted from the transaction sender's balance up front, with the transaction rejected outright if the sender cannot cover it, and with no ceiling anywhere in the pipeline limiting how large `operator_fee_scalar`/`operator_fee_constant` (and therefore the charged fee) can be. [5](#0-4) [6](#0-5) 

No bound-checking constants (e.g., a `MAX_OPERATOR_FEE_SCALAR`) exist anywhere in the codebase for these fields — searches for any max/limit constant related to the operator fee scalar/constant return nothing relevant to enforcement, only the fixed-point decimal scaling constant `OPERATOR_FEE_SCALAR_DECIMAL` used purely for the fee math, not as a cap. [7](#0-6) 

### Impact Explanation
Because `operator_fee_scalar` is a `u32` (up to ~4.29B) and `operator_fee_constant` is a `u64`, and both are multiplied/added with saturating arithmetic against the transaction's gas limit, the L1 `SystemConfig` owner can set these to extreme values and cause every subsequent L2 transaction to be charged an enormous (effectively unbounded) operator fee, or reject/underfund every sender, up to draining a user's entire balance in a single transaction's upfront charge. This is a direct, protocol-level centralization risk equivalent to the reported "protocol owner can charge high fee with no upper limit" — funds theft from every L2 user is possible via a single privileged L1 config update with no code-level cap.

### Likelihood Explanation
The `SystemConfig` owner is a privileged, permissioned role (analogous to the reported "protocol owner"), so this is not attacker-arbitrary but is a legitimate centralization/trust-assumption weakness: the on-chain L1 contract encodes and emits the update, and the L2 node's derivation and execution code applies it without any additional safety bound, so exploitation requires only a single authorized L1 transaction from that owner, with no additional preconditions on the L2 side.

### Recommendation
Enforce a maximum bound (e.g., a hard-coded ceiling analogous to caps used elsewhere for gas/fee parameters) on `operator_fee_scalar` and `operator_fee_constant` when applying `OperatorFeeUpdate` to `SystemConfig`, rejecting or clamping updates that exceed a safe threshold, and/or make the resulting per-transaction operator fee subject to a maximum fraction of the transaction's total cost so a single config update cannot arbitrarily drain user balances.

### Proof of Concept
1. The `SystemConfig` owner emits a `ConfigUpdate(OperatorFee)` log on L1 with `operator_fee_scalar = u32::MAX` and `operator_fee_constant = u64::MAX` (structurally valid per `UpdateDataValidator::validate`, so `OperatorFeeUpdate::try_from` succeeds — see the test at [8](#0-7)  for the decode path with arbitrary values).
2. On the next L1 epoch, the L2 derivation pipeline applies this via `SystemConfigUpdate::apply`, updating `SystemConfig.operator_fee_scalar`/`operator_fee_constant` with no bound check.
3. Every subsequent L2 transaction now has `operator_fee_charge_inner` compute a fee using these values (`gas.saturating_mul(operator_fee_scalar)/DECIMAL + operator_fee_constant`, or multiplied further under Jovian) — see [4](#0-3) .
4. `BaseTxHandlerHooks::before_execution` charges this fee upfront from the caller and rejects the transaction if the caller's balance is insufficient, or otherwise deducts the full (attacker-set) fee — see [5](#0-4) , with no independent cap on the fee magnitude.

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

        operator_fee: U256,
    ) -> HandlerResult<()> {
        let Some(tx) = envelope.as_standard() else {
            return Ok(());
        };
        if !host.feature(EvmFeatures::FEE_CHARGE) || !host.feature(EvmFeatures::BALANCE_CHECK) {
            return Ok(());
        }
        let required = U256::from(tx.gas_limit())
            .saturating_mul(U256::from(tx.max_fee_per_gas()))
            .saturating_add(tx.value())
            .saturating_add(l1_fee)
            .saturating_add(operator_fee);
        let balance =
            host.state_mut().account(&caller, false).map_err(HandlerError::Fatal)?.balance();
        if balance < required {
            return Err(HandlerError::InsufficientFunds);
        }
        Ok(())
    }

impl TxHandlerHooks<BaseEvmTypes> for BaseTxHandlerHooks {
    fn before_execution(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        upfront_fee: U256,
    ) -> HandlerResult<()> {
        // Charge the upfront gas cost, the L1 data fee, and the operator fee (on the gas limit)
        // from the caller. Both fees are stashed for settlement so it charges/refunds against the
        // exact amounts collected here, without recomputing them.
        let l1_fee = Self::l1_fee(host, envelope);
        let operator_fee = Self::operator_fee(host, envelope, envelope.gas_limit());
        let ext = host.ext_mut();
        ext.l1_fee = l1_fee;
        ext.operator_fee = operator_fee;
        // `validate_sender` only checks the gas cost and value; the L1 and operator fees are
        // charged on top here via `charge_upfront`'s wrapping subtraction, so reject an
        // underfunded caller up front rather than let its balance wrap to a spurious value.
        Self::ensure_can_pay_fees(host, envelope, caller, l1_fee, operator_fee)?;
        charge_upfront(
            host,
            caller,
            upfront_fee.saturating_add(l1_fee).saturating_add(operator_fee),
        )
    }
