### Title
Stale Confirmations From Deleted Multisig Members Are Still Counted Toward the Confirmation Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` authorizes execution of a request purely by counting entries in the `confirmations: HashSet<String>` for that request against `num_confirmations`. `delete_member` only purges confirmations belonging to requests that were *created by* the deleted member; it never scans other outstanding requests to strip that member's confirmation from them. As a result, a confirmation cast by a member who is later removed from the multisig remains valid and continues to count toward the execution threshold, letting a request execute with fewer live, currently-authorized members than `num_confirmations` requires.

### Finding Description
The relevant binding that must hold is:

```
confirmations counted toward execution == confirmations from members who are still live/authorized
```

`confirm()` checks only the raw count: [1](#0-0) 

`delete_member()` removes the departing member from `self.members` and clears `num_requests_pk`, but only deletes/cleans confirmations for requests where `r.member == member` (i.e., requests *created* by that member) — it does not remove that member's string identity from the `confirmations` set of any other outstanding request they may have already confirmed: [2](#0-1) 

Concrete scenario (num_confirmations = 3, members = {A, B, C, D}):
1. A calls `add_request` creating request `X` (e.g. a `Transfer`). `confirmations[X] = {}`.
2. B calls `confirm(X)` → `confirmations[X] = {B}` (len 1 < 3, stored not executed).
3. C calls `confirm(X)` → `confirmations[X] = {B, C}` (len 2 < 3, stored not executed).
4. Separately, members execute a `DeleteMember{B}` request (itself reaching the 3-confirmation threshold using still-live members). `delete_member` removes B from `self.members`, but since request `X`'s creator (`r.member`) is A, not B, `X`'s confirmations are untouched — `confirmations[X]` still contains B.
5. D now calls `confirm(X)`: `confirmations.len() (2) + 1 >= num_confirmations (3)` → true → `X` executes.

At execution time the live/authorized member set is `{A, C, D}`, yet the request executed with confirmations effectively from only `C` and `D` plus a stale entry from the removed member `B`. The quorum requirement of 3 *current* members was never actually met — the equality "confirmed-count == live-member confirmations" was broken.

### Impact Explanation
This is a threshold/authorization bypass: a multisig request (including `Transfer`, `FunctionCall`, `AddKey`/full-access-key grants, `DeployContract`, or further `AddMember`/`DeleteMember` changes) can be executed with confirmations from fewer live/authorized members than `num_confirmations` mandates. This matches the Critical impact category "a multisig request executed below threshold," since funds or privileged operations can move/execute without the intended number of currently-authorized signers agreeing.

### Likelihood Explanation
This requires no external preconditions beyond ordinary multisig operation: any request that collects partial confirmations, followed by removal of one of the confirming members (a routine `DeleteMember` action, e.g. key rotation or offboarding), followed by one more live member confirming, triggers the bug. No malicious deployment, redeploy, or privileged access beyond normal multisig member actions is needed — it can occur from ordinary key-rotation workflows.

### Recommendation
When removing a member in `delete_member`, iterate over all outstanding `requests`/`confirmations` (not just those authored by the removed member) and strip the removed member's identity from every confirmation set, or alternatively re-validate at `confirm()`-time / execution-time that all addresses present in a request's `confirmations` set are still contained in `self.members` before counting them toward `num_confirmations`.

### Proof of Concept
Using the existing test harness in `multisig2/src/lib.rs` (`members()` helper, `MultiSigContract::new`):
1. Instantiate with `num_confirmations = 3` and the 4 members from `members()`.
2. Have member A `add_request` a `Transfer`.
3. Have member B `confirm` it, then member C `confirm` it (leaves it un-executed, `confirmations.len() == 2`).
4. Execute a separate confirmed `DeleteMember{member: B}` request (reachable with the 3 remaining/other members confirming, since removing B still leaves `members.len() - 1 >= num_confirmations`).
5. Have member D `confirm` the original transfer request — assert it now executes (`c.requests.len() == 0` and the transfer promise scheduled), despite only 2 currently-live members (C, D, plus creator A who never confirmed) actually having confirmed post-removal. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
