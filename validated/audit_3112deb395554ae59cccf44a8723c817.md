### Title
Signer weight double-counted when a slot rejects then later accepts the same block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
In `StackerDBListener::run`, the `BlockResponse::Accepted` handler only checks `block.gathered_signatures.contains_key(&slot_id)` before adding a signer's weight to `total_weight_approved`, while the `BlockResponse::Rejected` handler checks/marks a different set, `block.responded_signers`. A single signer (one slot) that first sends a `Rejected` message and later sends an `Accepted` message for the same `signer_signature_hash` gets its weight counted in both `total_weight_rejected` and `total_weight_approved`, because the accept-path guard never consults `responded_signers`/the fact that this slot already contributed to the rejection tally.

### Finding Description
The invariant the code is supposed to maintain is: for a fixed `slot_id` and block hash, at most one of `total_weight_approved` / `total_weight_rejected` should ever include that slot's weight.

Tracing the two branches in `stackerdb_listener.rs`:

- Rejected branch (uses `responded_signers` as the idempotency/mutual-exclusion guard): [1](#0-0) 
`block.responded_signers.insert(slot_id)` returns `true` only the first time this slot_id is inserted, and that's when `total_weight_rejected` is incremented.

- Accepted branch (uses a *different* map, `gathered_signatures`, as its idempotency guard): [2](#0-1) 
This only prevents double-counting of repeated *Accepted* messages from the same slot_id (since `gathered_signatures` is only ever written to from this branch). It does **not** check `responded_signers`, so if the slot already rejected earlier (and is thus already in `responded_signers`), the accept path still finds `gathered_signatures` empty for that slot and adds the weight to `total_weight_approved` unconditionally — while the weight is *still* present in `total_weight_rejected` (there is no code path that decrements or removes it; `reset_rejections` only clears rejections on an externally triggered retry, not automatically on a later accept).

Exploit sequence (attacker controls exactly one signer slot's key, per threat model):
1. Attacker's signer sends `BlockResponse::Rejected` for block B (signer_signature_hash = H) → `total_weight_rejected += w` where `w` is the attacker's signer weight, and slot_id is added to `responded_signers`.
2. Same attacker signer later sends `BlockResponse::Accepted` for the same H (a valid signature over H, signed with the same key — allowed, since nothing prevents a signer from equivocating on its own vote) → because `gathered_signatures` does not yet contain this slot_id, `total_weight_approved += w` as well.
3. Now `w` is counted in both `total_weight_approved` and `total_weight_rejected` for the same block — the two counters are no longer mutually exclusive per slot, so `total_weight_approved + total_weight_rejected` can exceed the sum of unique signer weights that actually responded.

This breaks the equality the aggregation logic depends on. `SignerCoordinator`'s block-status determination (comparing `total_weight_approved` against `weight_threshold`, and `total_weight_rejected + weight_threshold > total_weight` for rejection) assumes each slot contributes to exactly one side. With double counting, weight that has already been "spent" toward rejecting a block can also be reused toward approving it, undermining the intended threshold arithmetic. I was not able to fully verify from the fragments retrieved how `signer_coordinator.rs`'s `get_block_status` combines these fields (grep results for that file did not return excerpts), so I cannot confirm the exact end-to-end numeric effect on the final decision, but the double-counting itself at the aggregation layer in `stackerdb_listener.rs` is directly demonstrable from the code above.

### Impact Explanation
This is exactly the "rejection recounted as acceptance" category called out as Critical: a slot's weight that was already tallied as a rejection is also tallied as an approval, without the earlier rejection being retracted. If enough signers do this (each needs only to flip from reject to accept for the same block, which a single attacker-controlled slot can always do with its own key), the accounting invariant `Σ per-slot contributions ≤ total_weight` breaks down, corrupting the correctness of any downstream logic that assumes `total_weight_approved` and `total_weight_rejected` are disjoint partitions of responding weight. This is repeatable per block/proposal cycle and costs nothing beyond owning one signer slot.

### Likelihood Explanation
- Precondition: block already exists in the `blocks` map (i.e., it has been proposed and is actively being tracked) — this happens for every block proposal.
- Attacker needs only their own signer key/slot (weight `w`), which is within the stated threat model ("running at most one signer's weight").
- Attacker cost: two gossiped StackerDB chunks (a `Rejected` then an `Accepted` for the same `signer_signature_hash`), both validly signed by the attacker's own key — no compromise of any other party needed.
- Fully repeatable for every block the attacker's signer is asked to vote on.

### Recommendation
Make the Accepted-branch idempotency/exclusivity check use the same authoritative set as the Rejected branch. Specifically, gate weight addition on whether `slot_id` is already present in `responded_signers` (not just `gathered_signatures`), and if the slot previously contributed to `total_weight_rejected`, subtract that contribution (or reject the late "accept" outright) before adding it to `total_weight_approved`. E.g.:
```rust
if !block.responded_signers.contains(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
} else if !block.gathered_signatures.contains_key(&slot_id) {
    // slot previously rejected; retract prior rejection weight before approving
    block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```
and symmetrically guard the Rejected branch against a slot that has already been counted as approved.

### Proof of Concept
```rust
// Pseudocode signer-coordinator style test against StackerDBListener's block map
#[test]
fn test_reject_then_accept_double_counts_weight() {
    // setup: single block B tracked, signer at slot_id = 3 with weight w
    comms.insert_block(&header_b);

    // Step 1: slot 3 rejects B
    dispatch(SignerMessageV0::BlockResponse(BlockResponse::Rejected(
        make_rejected(slot_id=3, hash=H, key=signer3_key)
    )));
    let status = blocks.get(&H).unwrap();
    assert_eq!(status.total_weight_rejected, w);
    assert_eq!(status.total_weight_approved, 0);

    // Step 2: same slot 3 later accepts B (equivocation, valid signature)
    dispatch(SignerMessageV0::BlockResponse(BlockResponse::Accepted(
        make_accepted(slot_id=3, hash=H, key=signer3_key)
    )));
    let status = blocks.get(&H).unwrap();

    // UNIQUENESS assertion that currently FAILS:
    assert!(
        status.total_weight_approved + status.total_weight_rejected <= signer_entries[3].weight
            + other_slots_total_weight_that_never_double_reported,
        "slot 3's weight was counted in both total_weight_approved ({}) and total_weight_rejected ({})",
        status.total_weight_approved, status.total_weight_rejected
    );
    // Concretely: status.total_weight_rejected == w (still, never retracted)
    // AND status.total_weight_approved == w (newly added)
    // i.e. slot 3's weight w appears in BOTH counters simultaneously.
}
```
