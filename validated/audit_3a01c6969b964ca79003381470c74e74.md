### Title
Claimed instant-withdraw receipts are never purged from epoch accounting and are double-counted in default recovery basis - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the expired-slashing-proposal bug, `IdleCreditVault` permanently keeps instant-withdraw receipt entries in `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` after the receipt has been funded and claimed. `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]`, never the per-epoch buckets. If the borrower defaults in the same epoch while any other instant request is still unfunded (`pendingInstantWithdraws != 0`), `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` count the already-claimed, already-paid receipts again, both inflating the recovery claim basis and pretending their already-spent underlyings are still held as reserve.

### Finding Description
`requestInstantWithdraw` records receipts in `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) . When the CDO collects funds via `collectInstantWithdrawFunds`, only `pendingInstantWithdraws` is reduced [2](#0-1) . When the user later claims, `claimInstantWithdrawRequest` burns the aggregate receipt and pays out, but the per-epoch entries are left untouched [3](#0-2)  — the stale entries are "kept in the pending list" exactly like the expired slashing proposals.

At default finalization, `defaultPendingClaimBasis` adds the whole `instantWithdrawClaimsByEpoch[epochNumber]` (including already-claimed receipts) whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` — which includes the claimed amount — as underlying still held by the strategy [5](#0-4) . Both flow into `reserveAmount` and `totalBasis` in `finalizeDefaultRecovery`, corrupting `defaultRecoveryPrice` and `defaultRecoveryReserve` [6](#0-5) .

### Impact Explanation
Two broken invariants follow:

1. **Insolvency / permanent freeze of recovery funds**: `_defaultPrefundedInstantReserve` reports already-paid-out underlyings as held reserve. `defaultRecoveryPrice` is therefore computed over a reserve that is partially phantom. Early recovery claimants (defaulted normal receipts, post-default requests) are paid through `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` [7](#0-6) . Once real balance is exhausted, subsequent claims either revert (`safeTransfer` failure or `defaultRecoveryReserve -= amount` underflow) or pay more than par to the first claimants, permanently locking the remaining reserve for later claimants.
2. **Self-DoS on the legitimate claim path**: the user whose stale per-epoch entry remains cannot execute `_claimDefaultedInstantWithdrawRequest`, because `instantWithdrawsRequests[_user] -= claimBasis` underflows once their aggregate was zeroed by the earlier claim, and `_burn(_user, claimBasis)` exceeds their receipt balance [8](#0-7)  — yet their stale basis was already counted at finalization.

An unprivileged lender (KYC-passing tranche holder) triggers the stale state purely through `requestInstantWithdraw` + `claimInstantWithdrawRequest`; the default itself is an honest borrower/manager event, not attacker-controlled.

### Likelihood Explanation
Requires a credit vault running the instant-withdraw mode where, within a single epoch, one instant request is funded and claimed while a second request remains unfunded (`pendingInstantWithdraws > 0`), followed by borrower default and `finalizeDefaultRecovery` in that same epoch. Partial funding is a documented flow (`_defaultPrefundedInstantReserve` exists precisely for it), and `claimInstantWithdrawRequest` pays the full aggregate without checking per-epoch funding. No privileged misbehavior is needed.

### Recommendation
Purge instant-withdraw per-epoch accounting at claim time, mirroring `_clearWithdrawClaimForEpoch`: in `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` for the claimed epochs, or track per-epoch funded-vs-claimed splits so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` only count still-outstanding receipts. Add a regression test where a funded-and-claimed instant receipt coexists with an unfunded one at default finalization.

```solidity
function testStaleInstantReceiptInflatesDefaultRecovery() external {
    // Epoch N running with instant withdraws enabled.
    _startEpochAndCheckPrices(0);
    uint256 epoch = strategy.epochNumber();

    // Attacker (KYC'd lender) requests instant withdraw X and another user Y.
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 100e6, true);
    vm.prank(attacker); cdoEpoch.requestInstantWithdraw(60e6, address(AAtranche));
    address victim = makeAddr('victim');
    _depositWithUser(victim, 100e6, true);
    vm.prank(victim); cdoEpoch.requestInstantWithdraw(50e6, address(AAtranche));

    // Honest manager/owner flow: CDO funds only part (60e6) of the instant queue.
    // collectInstantWithdrawFunds(60e6) -> pendingInstantWithdraws == 50e6.
    // Attacker claims; aggregate cleared but instantWithdrawsRequestsByEpoch[attacker][epoch]
    // and instantWithdrawClaimsByEpoch[epoch] still hold the stale 110e6 basis.
    vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epoch), 60e6); // stale
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 110e6);             // stale

    // Borrower defaults in the same epoch; owner finalizes recovery.
    _defaultAndFinalize();

    // defaultPendingClaimBasis double-counted the claimed 60e6;
    // _defaultPrefundedInstantReserve counted it as held underlying.
    // Later recovery claims revert on safeTransfer / reserve underflow while
    // defaultRecoveryReserve still shows positive accounting -> funds frozen.
}

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
