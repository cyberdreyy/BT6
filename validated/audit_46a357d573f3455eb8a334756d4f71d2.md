### Title
HTTP Action Response Cache Ignores WorkflowID, Violating Documented Workflow Isolation and Enabling Cross-Workflow Response Confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's HTTP Action response cache is documented and intended to scope cached HTTP responses per workflow (`"Cache Key: Generated from workflow ID and request hash"`, `"Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"`), but the actual cache-key computation (`OutboundHTTPRequest.Hash()`) excludes `WorkflowID` entirely. Two distinct workflow executions (even under the same workflow owner) that issue requests with identical method/URL/headers/body will collide on the same cache entry, so one workflow's cached HTTP response can be served back for a different workflow's request — the same class of "declared invariant vs. actual enforced value mismatch" described in the external report (declared amount/root vs. actual balance).

### Finding Description
The gateway HTTP Handler V2 documents its `responseCache` component as workflow-scoped for isolation purposes: [1](#0-0) 

However, the actual cache implementation keys entries only by `req.Hash()`, and the code comment states the hash is over "(method, URL, headers, body, workflowOwner)" — `WorkflowID` is not part of the key: [2](#0-1) 

The `Fetch` and `Set` paths both use this same `req.Hash()` as the sole cache key, with no additional dimension for the calling workflow: [3](#0-2) 

This is directly confirmed by the test suite, which explicitly asserts (and thus locks in) the behavior that differing `WorkflowID` values produce the *same* hash: [4](#0-3) 

The request flows into this cache from `makeOutgoingRequest`, which is invoked per HTTP Action request coming from workflow-DON nodes via the gateway, using `req.CacheSettings.MaxAgeMs`/`Store` to decide caching behavior: [5](#0-4) 

Root cause: the code's actual key-derivation logic (method/URL/headers/body/workflowOwner) does not match the documented/intended invariant (workflow ID scoping), the same category of defect flagged in the external report — a value that is supposed to constrain/scope an operation (there: the declared distribution amount vs. actual balance; here: the cache key vs. the workflow execution context) is not actually validated/enforced to match, so an unexpected cross-context result is served.

### Impact Explanation
Because the cache key does not include `WorkflowID`, a workflow execution can receive an HTTP response that was fetched and cached on behalf of a *different* workflow execution (as long as method/URL/headers/body/owner match). This breaks the documented workflow isolation guarantee and can lead to:
- Cross-workflow response confusion: a workflow processes data that was never actually returned for its own request/execution context, potentially driving incorrect on-chain actions, reports, or triggers.
- Stale/incorrect caching semantics across workflows sharing the same owner, undermining the freshness guarantees each workflow's `CacheSettings.MaxAgeMs` is meant to provide independently.

### Likelihood Explanation
This is reachable under normal, unprivileged operation of the gateway HTTP Action capability — no special authentication bypass is needed. Any two workflows under the same owner that happen to call the same URL/method/headers/body (a very plausible occurrence, e.g., shared public APIs, common price feeds, or identical boilerplate requests) will trigger the collision automatically whenever `CacheSettings.Store`/`MaxAgeMs` are used. The behavior is also explicitly codified as "correct" in the test suite, meaning it is not a latent implementation slip but a currently-accepted (and undocumented-as-intentional-elsewhere) discrepancy from the stated design in the README.

### Recommendation
Include `WorkflowID` (or the full execution-scoping identifier the system intends to isolate on) in the `Hash()` computation used as the cache key, consistent with the README's documented design ("Cache Key: Generated from workflow ID and request hash"). Add regression tests asserting that differing `WorkflowID` values produce *different* hashes (the inverse of the current test), and audit other callers/consumers of `responseCache` to ensure per-workflow isolation is actually enforced end-to-end.

### Proof of Concept
1. Workflow A (owner `O`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", WorkflowID: "wf-A", CacheSettings: {Store: true, MaxAgeMs: 600000}}` through the gateway; the gateway calls the external endpoint and, via `Set`/`Fetch`, stores the response keyed by `req.Hash()` (which excludes `WorkflowID`), per `response_cache.go`.
2. Workflow B (same owner `O`, different `WorkflowID: "wf-B"`) issues an outwardly-identical request (`same Method/URL/Headers/Body`) with `MaxAgeMs > 0`.
3. Per `response_cache_test.go:139-149`, `req.Hash()` is identical for A and B despite differing `WorkflowID`, so `Fetch` returns Workflow A's cached response to Workflow B without ever calling the external endpoint on B's behalf — demonstrating cross-workflow response confusion contrary to the documented "Workflow Isolation" guarantee.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

	var req gateway_common.OutboundHTTPRequest

	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
