## Analysis

The Sherlock bug class is: a deterministic, content-derived identifier (CREATE2 salt/address) is used as a one-time gate, but nothing binds *consumption* of that gate to the legitimate caller — so anyone who can predict/replicate the deterministic input can front-run and permanently consume the slot, causing denial-of-service for the intended party.

The Vault gateway flow in this repo has an analogous pattern: authorization of `AllowListBasedAuth` requests is based purely on a deterministic digest matching a pre-registered on-chain allowlist entry, and that match is treated as a single-use credential via a replay guard — with no check that the HTTP caller is actually the workflow owner.

### Root cause [1](#0-0) computes `req.Digest()` from the request content and checks it against digests the workflow owner registered on-chain via the `WorkflowRegistry` contract [2](#0-1) . If the digest matches an allowlisted entry (regardless of who sent the HTTP request), the caller is granted the owner's identity as `AuthResult.workflowOwner`.

That `AuthResult` is then fed into `authorizer.AuthorizeRequest`, which immediately calls the replay guard to record the digest as consumed for the remainder of its expiry window: [3](#0-2) . The guard is a simple "first digest wins" map with no binding to session, connection, or sender identity: [4](#0-3) .

The gateway's HTTP entrypoint, `gateway.ProcessRequest`, accepts raw JSON-RPC bytes from any internet client and dispatches to the handler without verifying that the sender is the workflow owner (auth/signature check happens later, downstream, inside the Vault-specific pipeline described above): [5](#0-4) .

For `MethodSecretsDelete` and `MethodSecretsList`, the request params contain only public/guessable fields (owner address, secret key, namespace, request ID) with no randomized ciphertext, so their digest is fully reconstructible by anyone who knows (or can observe/guess) those values — unlike `SecretsCreate`/`SecretsUpdate`, whose params include probabilistically-encrypted ciphertext that is not practically predictable. See the processing paths: [6](#0-5) .

### Impact

An unprivileged attacker who reconstructs the exact deterministic request content for a `SecretsDelete`/`SecretsList` operation (analogous to knowing the constructor args/salt in `createStream()`) can submit it to the public gateway HTTP endpoint before the legitimate owner's client does. Because the replay guard consumes the on-chain-allowlisted digest on first successful match, the legitimate owner's subsequent identical request is rejected with `ErrRequestAlreadySeen` ("request was already authorized previously") until the owner re-allowlists a new digest on-chain and waits for `workflowRegistrySyncer` propagation (comment notes ~12s+ polling interval): [7](#0-6) . This is a front-running/griefing DoS on the owner's intended vault operation, directly analogous to the reported bug class (consuming a deterministic single-use slot before the rightful party can).

### Caveats / uncertainty

- I could not fully inspect `req.Digest()` (in `chainlink-common/pkg/jsonrpc2`) to confirm exactly which fields are hashed; this affects how guessable the digest truly is in practice.
- The severity is bounded to DoS/griefing (blocking a delete/list action), not fund loss or secret disclosure — for `SecretsCreate`/`Update` the randomized ciphertext makes this attack impractical, so the exploitable surface is narrower than the original report's "protocol becomes useless" framing.
- Whether an attacker can realistically learn the exact deterministic params before the owner submits them (vs. this being purely a race between the owner's own automated retries) is not verified in code; it depends on operational/observability factors outside this repo.

### Recommendation

Bind the replay-guard consumption (and the allowlist match) to proof of sender identity — e.g., require the caller to also present a signature over the request from the owner's key (as the JWT path already does), rather than authorizing solely by digest match against a publicly-derivable on-chain entry. Alternatively, do not treat the first digest match as authoritative; instead validate that the HTTP-received request digest was submitted by the same channel/session that registered it, or shrink the allowlist window / rate-limit repeated first-attempt failures per requestID so a race is not decisive.

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")

		return nil, err

		return nil, err
	}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

	jsonRequest, err := jsonrpc2.DecodeRequest[json.RawMessage](rawRequest, auth)

		return newError("", api.UserMessageParseError, err.Error())

		return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())

		return newError(jsonRequest.ID, api.UserMessageParseError, "request ID is too long: "+strconv.Itoa(len(jsonRequest.ID))+". max is 200 characters")

	var isLegacyRequest = false
	var h handlers.Handler

	if msg == nil || msg.Body.DonId == "" {
		serviceName := jsonRequest.ServiceName()
		if handler, ok := g.serviceToMultiHandler[serviceName]; ok {
			h = handler
			handlerKey = serviceName
		} else if donID, ok := g.serviceNameToDonID[serviceName]; ok {
			// Fallback to legacy service name -> DON ID mapping
			if handler, ok := g.handlers[donID]; ok {
				h = handler
				handlerKey = donID
			}
		}

		}

func (p *GatewayVaultRequestProcessor) processDeleteSecretsRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var deleteReq vaultcommon.DeleteSecretsRequest
	if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		deleteReq.RequestId = req.ID
		if err := marshalVaultParams(req, &deleteReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		deleteReq.RequestId = coalesceRequestID(deleteReq.RequestId, req.ID)
	}

	if err := p.validator.ValidateDeleteSecretsRequest(ctx, &deleteReq); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		deleteReq.RequestId = prefixedRequestID
		vaultutils.ApplySecretIdentifierNamespaceDefaults(deleteReq.Ids)
		return marshalVaultParams(req, &deleteReq)
	})
}
