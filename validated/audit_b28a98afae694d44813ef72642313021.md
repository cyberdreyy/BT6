### Title
Malicious ERC4626 vault depositor can freeze `stopEpoch` by draining vault liquidity, permanently blocking epoch settlement - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In programmable-borrower mode, `IdleCDOEpochVariant.stopEpoch` unconditionally calls `IProgrammableBorrower.onStopEpoch`, which calls `vault.withdraw(shortfall, ...)` on an external ERC4626 vault whose share valuation (`convertToAssets`) reports full assets even when all real liquidity has been borrowed out. Any unprivileged user of that vault can borrow the vault's entire liquid balance so `vault.withdraw` reverts, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, and the whole `stopEpoch` reverts — freezing every LP's funds and all pending withdraw claims for as long as the attacker keeps the vault's liquidity drained. This mirrors CVE-2024-36472: an attacker-controlled, untrusted input (vault liquidity state) is automatically consumed inside a privileged flow (`stopEpoch`), causing resource unavailability.

### Finding Description
`ProgrammableBorrower.onStopEpoch` computes the shortfall between IdleCDO's pull amount and on-hand cash, then checks `shortfall > _currentVaultAssets()` to decide whether to withdraw. `_currentVaultAssets` uses `vault.convertToAssets(shares)` (ProgrammableBorrower.sol:546-548), which reports total supplied assets — including assets currently lent out. For a lending-style ERC4626 (e.g., a Morpho/ERC4626 vault, which the test suite uses), `convertToAssets` does not decrease when liquidity is borrowed, so the check passes, `vault.withdraw(shortfall, ...)` is attempted, and it reverts on insufficient liquidity. The catch block reverts `StopEpochVaultLiquidityUnavailable` (ProgrammableBorrower.sol:246-252).

In `IdleCDOEpochVariant._stopEpoch`, the `onStopEpoch` call at line 398 is a direct call, not wrapped in try/catch, so the revert propagates and the entire `stopEpoch` fails. Only the subsequent `getFundsFromBorrower` transfer is guarded by try/catch (line 408). Because `epochAccountingActive` and all CDO epoch state remain untouched, owner/manager cannot stop the epoch, pending withdraw requests cannot be fulfilled, deposits are paused, and borrowers cannot borrow (`epochAccountingActive` stays true but `availableToBorrow` still shows liquidity that cannot actually be withdrawn).

Notably the guard at line 245 makes this worse: when the vault reports enough assets, the code assumes the withdrawal will succeed and reverts loudly; the attacker controls exactly the gap between `convertToAssets` (accounting truth) and actual vault liquidity (withdrawable truth).

### Impact Explanation
Temporary freezing of all funds in the pool. While the attacker maintains the borrow on the external vault:

- `stopEpoch` always reverts, so the epoch can never end and `allowAAWithdrawRequest`/`allowBBWithdrawRequest`/deposit unpausing never re-enable.
- All pending withdraw requests from the previous epoch (`pendingWithdraws`) cannot be collected or claimed via `claimWithdrawRequest`.
- If the CDO is in minted-interest mode, the attacker additionally defers `mintStrategyTokens` and fee minting indefinitely.

Quantified loss: 100% of pool NAV plus all pending withdraw claims are locked for the duration of the attack; the attacker's cost is only the borrow interest on the external vault (which can be a flash-duration or renewable position), not the pool's assets. Repeated across buffer windows, the attacker can keep the facility frozen nearly indefinitely at linear cost while LP funds are fully immobilized.

### Likelihood Explanation
Requires the pool to run in `isProgrammableBorrower` mode against an ERC4626 vault with a public borrow/withdraw surface (the intended design — undrawn capital is parked in a yield vault whose other users are unprivileged). The attacker is an ordinary vault depositor/borrower — explicitly an in-scope unprivileged class. The attack needs no precision timing: the attacker only needs vault liquidity exhausted at the moment manager calls `stopEpoch`, and can monitor mempool for the stopEpoch transaction to borrow just-in-time. Honest privileged roles cannot mitigate: `emergencyExitVault` also calls `vault.redeem` and reverts on the same liquidity shortage, and `setVault` is blocked while `epochAccountingActive` or shares remain.

### Recommendation
In `onStopEpoch`, bound the withdrawal to actually-available vault liquidity rather than `convertToAssets`-implied assets: query `vault.maxWithdraw(address(this))` (or the underlying's liquid balance of the vault) and only attempt `vault.withdraw(min(shortfall, maxWithdrawable))`. If the residual shortfall cannot be covered, return `false` (or a distinct partial-liquidity signal) so IdleCDO's existing `_handleBorrowerDefault` path runs deterministically instead of reverting — a real, irreversible liquidity failure should be a default decision, not a retryable revert that lets an external vault's other users veto epoch settlement. Alternatively, add a degraded stop path in `IdleCDOEpochVariant._stopEpoch` that catches `StopEpochVaultLiquidityUnavailable` and lets the manager proceed with a reduced `_pendingWithdraws`/interest settlement rather than reverting the entire epoch.

### Proof of Concept
Foundry fork PoC (target: a real ERC4626 lending vault, e.g. a Morpho vault with borrowable underlying):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "contracts/IdleCDOEpochVariant.sol";
import {ProgrammableBorrower} from "contracts/strategies/idle/ProgrammableBorrower.sol";
import {IERC4626} from "contracts/interfaces/IERC4626.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

contract VaultLiquidityFreezePoC is Test {
    IdleCDOEpochVariant cdo;
    ProgrammableBorrower pb;
    IERC4626 vault;      // external ERC4626 lending vault used by pb
    IERC20 underlying;

    address owner   = address(0xA11CE);
    address manager = address(0xB0B);
    address lp1     = address(0x1);   // honest AA LP
    address lp2     = address(0x2);   // honest BB LP
    address attacker = address(0xBAD);

    function setUp() public {
        // Deploy/fork: cdo in programmable mode with pb as borrower,
        // pb.vault = a public ERC4626 lending vault (underlying = USDC).
        // lp1/lp2 deposit via idleCDO.depositAA/depositBB, manager calls
        // cdo.startEpoch() -> pb.onStartEpoch deposits idle funds into vault.
    }

    function test_AttackerFreezesStopEpoch() public {
        // --- Epoch running; lp1 requested a withdraw last epoch (pendingWithdraws > 0) ---
        vm.warp(cdo.epochEndDate() + 1);

        uint256 shortfall = pb.totalInterestDueNow() + pb.epochPendingWithdraws()
                          - underlying.balanceOf(address(pb));
        assertGt(shortfall, 0, "need vault withdrawal path");
        // convertToAssets still reports full coverage:
        assertGe(pb.vault().convertToAssets(pb.vaultSharesBalance()), shortfall);

        // Attacker (ordinary vault user) drains all liquid underlying from the vault:
        vm.startPrank(attacker);
        // e.g. vault.borrowAll() on Morpho-style vault, or repeatedly withdraw supplied
        // liquidity via a leveraged loop until vault's idle balance == 0
        drainVaultLiquidity(vault);
        vm.stopPrank();

        // Manager tries to stop the epoch -> onStopEpoch -> vault.withdraw reverts ->
        // StopEpochVaultLiquidityUnavailable bubbles up and reverts stopEpoch entirely.
        vm.prank(manager);
        vm.expectRevert(); // StopEpochVaultLiquidityUnavailable (or vault liquidity error)
        cdo.stopEpoch(0, 0);

        // Frozen state: epoch still running, withdraws still disabled, deposits paused.
        assertTrue(cdo.isEpochRunning());
        assertFalse(cdo.allowAAWithdrawRequest());
        vm.expectRevert();
        vm.prank(lp1);
        cdo.claimWithdrawRequest(); // pending request can never be funded

        // Attacker renews the borrow / re-drains on every manager retry:
        for (uint i; i < 5; ++i) {
            drainVaultLiquidity(vault);
            vm.prank(manager);
            vm.expectRevert();
            cdo.stopEpoch(0, 0);
        }
        // Result: 100% of pool NAV + pending claims locked while attack is maintained.
    }

    function drainVaultLiquidity(IERC4626 v) internal {
        // borrow or withdraw until v's underlying.balanceOf(address(v)) == 0
    }
}
```
