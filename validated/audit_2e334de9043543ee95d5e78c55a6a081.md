### Title
`check_block_has_valid_tenure` verifies canonicity against an attacker-selected `burn_view_consensus_hash` fork instead of the true canonical sortition tip - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
`check_block_has_valid_tenure` calls `db_handle.has_consensus_hash(tenure_id)`, but `db_handle` is rooted at the sortition identified by `burn_view_consensus_hash`, a value taken from the block's own `TenureChange` payload and only checked for *connectivity* to the parent block's burn view - never checked against the node's actual canonical burnchain tip. This lets the "canonical tenure" check be satisfied relative to a non-canonical/stale fork chosen by the block's own miner.

### Finding Description
The equality the signer needs is: *the tenure the signer approves == the tenure on the node's true canonical sortition fork*. The code instead checks: *the tenure is an ancestor of whatever sortition `burn_view_consensus_hash` names*.

Path:
- `validate()` computes `burn_view_consensus_hash = NakamotoChainState::get_block_burn_view(sortdb, &self.block, &parent_stacks_header)` [1](#0-0) 
- `get_block_burn_view` takes `tenure_change.burn_view_consensus_hash` directly from the proposed block's `TenureChange` tx when present, and only verifies that this value descends from the parent's own burn view via `get_ancestor_sort_id` on a handle opened at that consensus hash - it never compares it to `SortitionDB::get_canonical_burn_chain_tip` [2](#0-1) 
- `validate()` then opens `db_handle = sortdb.index_handle(&sort_tip.sortition_id)` where `sort_tip` is the snapshot for that (attacker-influenced) `burn_view_consensus_hash`, and passes this handle into `check_block_has_valid_tenure` [3](#0-2) 
- `check_block_has_valid_tenure` only calls `db_handle.has_consensus_hash(tenure_id)` [4](#0-3) 
- `has_consensus_hash` checks canonicity **relative to `self.context.chain_tip`** (i.e., the handle's own root, which is the attacker-influenced `burn_view_consensus_hash`'s sortition), not relative to the node's true global canonical tip: `get_ancestor_sort_id(self, sn.block_height, &self.context.chain_tip)` [5](#0-4) 

By contrast, the real consensus-layer tenure-canonicity check used elsewhere, `validate_nakamoto_tenure_snapshot`, explicitly re-derives the tip via `SortitionDB::get_canonical_burn_chain_tip(db_handle)` (the actual global canonical tip) and checks ancestry against *that*, not against the handle's own pre-selected root [6](#0-5) . `postblock_proposal.rs::check_block_has_valid_tenure` does not perform this equivalent re-anchoring step, so it inherits whatever fork `burn_view_consensus_hash` names as its notion of "canonical."

Exploit sketch: an attacker who wins a single sortition on a burnchain fork that a signer's node has recorded but that is not (or is no longer) the canonical tip - e.g., during a natural, brief burnchain reorg window where the node's SortitionDB still retains the losing fork's sortitions - crafts a `NakamotoBlockProposal` whose `TenureChange.burn_view_consensus_hash` and `header.consensus_hash` both lie on that non-canonical fork, consistent with the parent's own burn view. `get_block_burn_view`'s connectivity check passes (it only checks fork continuity, not global canonicity), `db_handle` is opened rooted at the non-canonical fork's tip, and `has_consensus_hash` reports `true` because the tenure is canonical *within that self-selected sub-fork*, even though it is not canonical on the node's actual best chain.

### Impact Explanation
This breaks the CANONICITY safety property the comment above the call explicitly claims to enforce ("Verify that the block's tenure is on the canonical sortition history") [7](#0-6) . A signer could be induced to sign a block whose tenure is not on the node's true canonical fork, which is the Critical category: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
The attacker needs one miner slot (to win a sortition and produce the block/`TenureChange`) plus gossip of the resulting `BlockProposal`/StackerDB messages, matching the allowed threat model. The limiting precondition is that the SortitionDB of the validating node must still contain a non-canonical-but-connected fork sortition matching the attacker's tenure/burn-view claim; this occurs naturally during transient burnchain reorgs (the SortitionDB retains observed-but-orphaned sortitions) rather than requiring the attacker to control burnchain hash power. This narrows the exploit window compared to an always-available bug, but it does not require majority signers, node-operator privilege, or the auth token - only timing around an observed reorg plus one won sortition.

### Recommendation
In `check_block_has_valid_tenure` (or in `validate()` before calling it), re-derive the true canonical tip via `SortitionDB::get_canonical_burn_chain_tip` and require the ancestor check to be performed against that canonical tip's sortition, mirroring `validate_nakamoto_tenure_snapshot`'s logic, instead of trusting `db_handle.context.chain_tip` (which is rooted at the attacker/miner-supplied `burn_view_consensus_hash`).

### Proof of Concept
Rust test plan (in `postblock_proposal.rs` test module or a chainstate test harness):
1. Build a test `SortitionDB` with two forks at the same height: fork A (canonical, higher total burn) and fork B (non-canonical, orphaned, still stored).
2. Construct a `NakamotoBlock`/`TenureChange` whose `burn_view_consensus_hash` and `header.consensus_hash` are set to sortitions on fork B, with a parent burn view chosen so that `get_ancestor_sort_id` connectivity in `get_block_burn_view` passes against fork B.
3. Call `NakamotoChainState::get_block_burn_view` and confirm it returns fork B's consensus hash without error (demonstrating no canonical-tip check).
4. Open `db_handle = sortdb.index_handle(&fork_B_sortition_id)` and call `NakamotoBlockProposal::check_block_has_valid_tenure(&db_handle, &fork_B_tenure_ch)`.
5. Assert it returns `Ok(())` (incorrectly accepting a non-canonical tenure), while `SortitionDB::get_canonical_burn_chain_tip` shows fork A as canonical and `fork_B_tenure_ch` is not an ancestor of fork A's tip - proving the equality "approved tenure == canonical sortition" is violated.

```rust
        db_handle: &SortitionHandleConn,
        tenure_id: &ConsensusHash,
    ) -> Result<(), BlockValidateRejectReason> {
        // Verify that the block's tenure is on the canonical sortition history
        if !db_handle.has_consensus_hash(tenure_id)? {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's tenure consensus hash is not on the canonical Bitcoin fork",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NonCanonicalTenure,
                reason: "Tenure consensus hash is not on the canonical Bitcoin fork".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }
```

```rust
    /// Is a consensus hash's sortition valid on the fork represented by this handle?
    /// Return Ok(true) if so
    /// Return Ok(false) if not (including if there is no sortition with this consensus hash)
    /// Return Err(..) on DB error
    pub fn has_consensus_hash(&self, consensus_hash: &ConsensusHash) -> Result<bool, db_error> {
        let Some(sn) = SortitionDB::get_block_snapshot_consensus(self, consensus_hash)? else {
            // no sortition with this consensus hash
            return Ok(false);
        };

        let Some(expected_sortition_id) =
            get_ancestor_sort_id(self, sn.block_height, &self.context.chain_tip)?
        else {
            // no ancestor at this sortition height relative to this chain tip
            // (e.g. perhaps this consensus hash is in the "future" relative to this chain tip)
            return Ok(false);
        };

        Ok(sn.sortition_id == expected_sortition_id)
    }
```
