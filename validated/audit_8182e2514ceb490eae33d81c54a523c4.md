## Finding

The bug class from the report — an unrelated/foreign contract using an origin-style identity primitive as an authorization check, letting an untrusted call impersonate a party who never approved that specific call — has a direct analog in the `ITransactionContext` precompile that backs EIP-8130.

### Title
Sponsor/payer impersonation via the `TxContext` precompile's origin-like sender/payer getters - (File: `crates/common/precompiles/src/tx_context/storage.rs`)

### Summary
EIP-8130 introduces a `TxContext` precompile (`0x813000000000000000000000000000000000aa02`) exposing `getTransactionSender()` and `getTransactionPayer()`. These getters resolve to the *whole-transaction* identity (the authenticated EIP-8130 sender/payer), not the immediate caller, and are readable from anywhere in the call tree that a sender's signed `calls` reach — mirroring `tx.origin` semantics exactly, including its confused-deputy weakness.

### Finding Description
`TxContextStorage::set_context` publishes the resolved `sender`/`payer` once, at the start of transaction processing, into transient storage that is visible to every call made during that transaction: [1](#0-0) 

The getters simply read that transient slot and fall back to `tx.origin` when unset, explicitly documented as giving callers "the actual transaction originator uniformly across tx types": [2](#0-1) 

`Eip8130Executor::execute` writes this context once via `set_context(sender, payer, sender_actor_id)` before dispatching any of the transaction's `calls`: [3](#0-2) 

Every call in every phase is then dispatched as a **top-level** frame with `caller = outcome.sender` (not chained from the previous call's target), and the module doc states plainly that `tx.origin == sender` for the whole transaction: [4](#0-3) [5](#0-4) 

So `getTransactionSender()` / `getTransactionPayer()` behave exactly like `tx.origin`: any contract reachable from an attacker-chosen `call.to` — including contracts several calls deep that the attacker's target contract itself calls — sees the resolved sender/payer, not its direct caller.

Critically, the **payer** is a separate, independently-signing party (a gas sponsor) whose authorization only binds to the sender account and fee terms, not to the specific calls being sponsored: [6](#0-5) 

This is structurally identical to the report's scenario: the **payer/sponsor plays the role of the "Relayer"** — it authorizes participation in a transaction (paying gas) without reviewing or controlling the arbitrary `calls`/targets the sender dispatches. If any downstream (foreign) contract reachable via those attacker-controlled calls uses `getTransactionPayer()` (or `getTransactionSender()`) as an authorization/identity check — e.g., "only the registered sponsor address may withdraw," analogous to a `tx.origin` check in the report — an attacker can trivially satisfy that check for any call it wants to make, because the getter returns the payer's address regardless of which contract or how deep in the call graph the query originates.

### Impact Explanation
Any Base-deployed contract that treats `ITransactionContext.getTransactionPayer()` (or `getTransactionSender()`) as a caller-equivalent authorization primitive — which the interface's own documentation actively encourages, presenting it as a safer drop-in for `tx.origin`/`msg.sender` reasoning across AA transaction types — is exposed to confused-deputy theft: an attacker constructs an EIP-8130 transaction whose `sender` is themselves but whose `payer` is a legitimate third-party sponsor (who only signed to cover gas), then routes a `call` to the victim contract so it observes `getTransactionPayer() == sponsor` and authorizes an operation (withdrawal, transfer, credential use) the sponsor never intended. This is a direct unauthorized-operation/theft-of-funds vector against any payer/sponsor account participating in EIP-8130 sponsored transactions.

### Likelihood Explanation
This requires ecosystem contracts to adopt `getTransactionPayer()`/`getTransactionSender()` as an authorization check in place of `msg.sender` — which is exactly the intended, documented use case for the precompile (it is billed as more reliable than `tx.origin`). Sponsored (SPONSOR_PAYER-scoped) transactions are a first-class EIP-8130 feature, so payer/sender divergence is an expected, common configuration, not an edge case. The attacker needs only to submit a normal signed EIP-8130 transaction with an arbitrary `calls` batch — no privileged access required.

### Recommendation
Document clearly (in the `ITransactionContext` interface and EIP-8130 developer docs) that `getTransactionSender()`/`getTransactionPayer()` are transaction-wide identities exactly like `tx.origin`, and must **never** be used as an authorization/allow-list check by contracts, especially for the `payer`, whose signature does not commit to the `calls` content. Consider additionally exposing a call-depth-aware "immediate caller was directly dispatched by sender/payer" signal, or scoping payer visibility so it is only queryable by contracts explicitly named as direct `call.to` targets, to reduce the risk that this precompile becomes a systemic tx.origin-style trap for third-party contract authors, mirroring the original recommendation that "relayers"/payers should not be treated as trusted identities reachable by arbitrary foreign code.

### Proof of Concept
1. Sponsor `P` signs a payer authorization for sender `S`'s EIP-8130 transaction (SPONSOR_PAYER scope), covering only the fee terms and `S`'s account — not the `calls` payload, per `crates/execution/eip8130/src/verify.rs:83-101`.
2. Attacker (as `S`) sets `calls = [[Call { to: VictimContract, data: <withdraw()> }]]`.
3. `Eip8130Executor::execute` publishes `set_context(S, P, actor_id)` before dispatching calls (`crates/common/evm/src/eip8130.rs:894-897`), then invokes `VictimContract` as a top-level frame from `S` (`crates/common/evm/src/eip8130.rs:1220-1233`).
4. `VictimContract`, which was built trusting `ITransactionContext.getTransactionPayer()` as an authorized-caller check (e.g. "only P may withdraw P's escrowed balance"), calls the `TxContext` precompile and reads back `P` — regardless that `P` never selected `VictimContract` or `withdraw()` as the call target, since `TxContextStorage::payer()` simply returns the transaction-wide resolved payer (`crates/common/precompiles/src/tx_context/storage.rs:54-62`).
5. The withdrawal executes, moving `P`'s funds to an address the attacker controls, with `P` never having reviewed or approved this specific call.

**Uncertainty:** I could not fully verify within this session whether `payer_signature_hash` binds to any additional transaction fields beyond the sender account (I confirmed it binds to `sender.account` at `crates/execution/eip8130/src/verify.rs:85` but did not view the full hash-construction routine in `crates/common/consensus/src/transaction/eip8130/tx.rs` or `signed.rs`). If the payer's signature does in fact commit to the `calls` payload, likelihood would be substantially reduced. I also could not confirm whether any existing Base-owned system contract actually consumes `getTransactionPayer()` for authorization (the risk as described is primarily to third-party/foreign contracts deployed on Base, consistent with the original report's scope).

    /// Returns the resolved sender, falling back to `tx.origin` when unset
    /// (i.e. outside an EIP-8130 transaction).
    pub fn sender(&self) -> Result<Address> {
        let raw = self.storage.tload_unmetered(Self::ADDRESS, Self::SENDER_SLOT)?;
        if raw.is_zero() {
            return Ok(self.storage.origin());
        }
        Ok(Address::from_word(B256::from(raw.to_be_bytes::<32>())))
    }

    /// Returns the resolved payer, falling back to `tx.origin` when unset
    /// (i.e. outside an EIP-8130 transaction).
    pub fn payer(&self) -> Result<Address> {
        let raw = self.storage.tload_unmetered(Self::ADDRESS, Self::PAYER_SLOT)?;
        if raw.is_zero() {
            return Ok(self.storage.origin());
        }
        Ok(Address::from_word(B256::from(raw.to_be_bytes::<32>())))
    }
