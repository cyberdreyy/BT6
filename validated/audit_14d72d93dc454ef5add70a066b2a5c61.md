### Title
Instant-withdraw receipts are claimable before borrower funding, letting an attacker drain funded withdraw reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug class (TOCTOU: exploit a window before a state transition completes) maps to the instant-withdraw lifecycle in `IdleCreditVault`. `requestInstantWithdraw` mints an unrestricted receipt and bumps `pendingInstantWithdraws`, but `claimInstantWithdrawRequest` pays the full `instantWithdrawsRequests[_user]` balance with no epoch gate, no funded-flag check, and no requirement that `collectInstantWithdrawFunds` (driven by the honest manager via `IdleCDOEpochVariant.getInstantWithdrawFunds`) has actually moved the borrower's underlying into the strategy. An attacker who races their claim in before the funding transaction withdraws underlying that belongs to already-funded normal withdraw receipts and strategy reserves, and the still-outstanding `pendingInstantWithdraws` entry then causes the borrower's subsequent funding to arrive unowned — a second, donation-like leak.

### Finding Description
`requestInstantWithdraw` (lines 356–375) burns CDO strategy tokens, mints the user a 1:1 receipt, records `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and increases `pendingInstantWithdraws`. The matching claim path at lines 380–393 does:

```solidity
function claimInstantWithdrawRequest(address _user) external {
  _onlyIdleCDO();
  if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);
  }
  uint256 amount = instantWithdrawsRequests[_user];
  _burn(_user, amount);
  instantWithdrawsRequests[_user] = 0;
  _transferFundedClaim(_user, amount);
}
```

Contrast with the normal withdraw path: `_claimFundedWithdrawRequest` reverts while `epochNumber <= lastWithdrawRequest[_user]`, guaranteeing at least one full `stopEpoch` — and therefore the borrower's `collectWithdrawFunds` funding transfer — has occurred between request and claim (lines 319–350). The instant path has no equivalent ordering constraint and, critically, `claimInstantWithdrawRequest` never decrements `pendingInstantWithdraws`; only `collectInstantWithdrawFunds` does (lines 398–403). The CDO-side entry point `claimInstantWithdrawRequest()` in `IdleCDOEpochVariant.sol` (lines 975–979) only checks the `allowInstantWithdraw` flag.

So the sequencing window is: attacker calls `requestWithdraw` while `lastEpochApr > currentApr + instantWithdrawAprDelta` (an honest condition after an APR decrease, reachable during the buffer phase), receives receipts, then calls `claimInstantWithdrawRequest` in the same epoch before the manager's `getInstantWithdrawFunds` executes. The strategy pays the claim out of its existing underlying balance — which backs funded normal withdrawals, the `defaultRecoveryReserve`, and not-yet-lent deposits — even though the borrower's funds for this instant request have not arrived.

### Impact Explanation
The attacker extracts up to the full instant-withdraw amount at par, immediately, funded by other users' money: underlying held by the strategy for `withdrawsRequests` claimants and reserve balances. When the honest manager later calls `getInstantWithdrawFunds`, `collectInstantWithdrawFunds` still pulls `pendingInstantWithdraws` (which was never decremented by the premature claim) from the CDO/borrower, leaving unowned surplus in the strategy — a double-counted payout. Net effect: direct theft of funded withdraw reserves and/or NAV belonging to other LPs, quantified as the full `instantWithdrawsRequests` amount the attacker requested (bounded only by their tranche holdings, which they controlled).

### Likelihood Explanation
Requires `allowInstantWithdraw` enabled and a natural APR decrease exceeding `instantWithdrawAprDelta` — both routine, honest-side conditions. The attacker needs only a KYC'd tranche position and transaction sequencing before the manager's funding call, i.e., claiming during the buffer/running transition window. No privileged cooperation is needed; the honest manager's subsequent `getInstantWithdrawFunds` actually makes the double-spend worse rather than preventing it. Medium likelihood gated mainly by deployment mode.

### Recommendation
Gate instant claims on funding: either record per-epoch funded status and require `collectInstantWithdrawFunds` to have covered the request epoch before `claimInstantWithdrawRequest` pays, or decrement `pendingInstantWithdraws` in the claim path and have `_transferFundedClaim` verify the strategy holds dedicated funded balance (a funded-claims counter incremented only by `collectInstantWithdrawFunds`/`collectWithdrawFunds`). At minimum, mirror the normal-path invariant by forbidding claims for receipts created in `epochNumber` until the funding transition completes.

### Proof of Concept
```solidity
// Fork test sketch (Foundry), credit vault with allowInstantWithdraw = true.
// Setup: depositAA, run epoch 0, stopEpoch so lastEpochApr is set.
// Epoch 1 starts with a lower APR (initialProvidedApr / 2 as in
// testClaimWithdrawRequestWithInstantDefault), enabling instant withdraws.

uint256 requested = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
// ^ takes instant path: mints receipt, bumps pendingInstantWithdraws.

// RACE: claim in the same block/epoch, BEFORE manager calls getInstantWithdrawFunds.
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimInstantWithdrawRequest();           // no epoch/funding gate on vault side
assertEq(underlying.balanceOf(attacker) - balPre, requested); // paid from strategy reserves

// Honest manager then funds the queue as usual:
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();
// pendingInstantWithdraws still includes `requested` -> strategy pulls funds
// that no longer correspond to any live receipt: funded claims double-paid.
```

Uncertainty note: the index did not expose the body of `_transferFundedClaim`; if it enforces a dedicated funded-balance counter rather than transferring from the raw token balance, the theft leg narrows to the `pendingInstantWithdraws` non-decrement / double-funding inconsistency. The absence of any epoch gate in `claimInstantWithdrawRequest` (visible at lines 380–393) versus the explicit gate in `_claimFundedWithdrawRequest` is confirmed and is itself the broken ordering invariant.
