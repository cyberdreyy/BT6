### Title
Mid-epoch deposit credits and forwards the stated `_amount` instead of the amount actually received, so a fee-on-transfer underlying mints unbacked tranche shares and drains the vault - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The external Blueberry issue is a mismatch between the recorded deposit amount and the tokens actually received when the underlying charges a transfer fee. In `IdleCDOEpochVariant.depositDuringEpoch` the vault transfers `_amount` from the user, mints tranche shares and mints strategy tokens against the stated `_amount`, then pushes `_amount` underlyings to the borrower. The same pattern exists in `IdleCreditVault.deposit`, which mints 1:1 strategy tokens for the stated `_amount` pulled via `safeTransferFrom`. If the underlying ever takes a transfer fee (e.g., USDT with its fee enabled, PAXG/USDC-class tokens with fee switches), the vault records and pays out more than it holds.

### Finding Description
`_deposit` in `IdleCDO`/`IdleCDOCreditVault` correctly mints shares on the balance delta (`_contractTokenBalance(_token) - _preBal`), so it is immune to fee-on-transfer underlyings. [1](#0-0) 

`depositDuringEpoch` does not follow that pattern: it pulls `_amount`, computes `interest`/`_minted` from `_amount`, calls `IdleCreditVault(strategy).mintStrategyTokens(_amount)` and finally `_transferUnderlyings(_borrower(), _amount)` — all using the nominal amount rather than the received balance. [2](#0-1) [3](#0-2) 

Likewise `IdleCreditVault.deposit` mints `_amount` strategy tokens after `safeTransferFrom`, so the strategy's 1:1 backing (price() always returns `oneToken`) is overstated by the fee. [4](#0-3) [5](#0-4) 

### Impact Explanation
With a fee-on-transfer underlying, each mid-epoch deposit of `_amount` delivers only `_amount - fee` to the vault, yet the vault mints `(amount + trancheInterest)`-based tranche shares and forwards the full `_amount` to the borrower, spending prior depositors' funds or reverting when the balance is insufficient (DoS of `depositDuringEpoch`). Strategy tokens minted via `IdleCreditVault.deposit`/`mintStrategyTokens` are backed 1:1 in `price()` accounting, so `getContractValue`, tranche NAVs and pending-withdraw funding are inflated by the shortfall — a solvency break of the fair mint/burn invariant, socialized onto the remaining LPs at `stopEpoch`/withdraw funding or via `defaultRecoveryPrice` dilution.

### Likelihood Explanation
Requires the vault's underlying to be a fee-on-transfer token. Underlyings are chosen at deployment (USDC/USDT/DAI class), and USDT specifically has an owner-enabled fee flag — no malicious privileged actor is needed; an unprivileged KYC'd depositor triggers it by calling `depositDuringEpoch` while `isEpochRunning` and deposits are enabled (`isDepositDuringEpochDisabled == false`, non-AYS, non-programmable). Any borrower repayment, write-off fulfilment, or epoch funding pull through the nominal-amount paths is affected the same way. Medium likelihood, high impact when triggered.

### Recommendation
Measure received tokens in `depositDuringEpoch` and `IdleCreditVault.deposit` by taking `balanceBefore`/`balanceAfter` around `safeTransferFrom`, and use the delta (not `_amount`) for share minting, `mintStrategyTokens`, the borrower transfer and `totEpochDeposits`; or explicitly document/enforce that fee-on-transfer underlyings are unsupported (e.g., revert in initialize when a probe transfer yields less than sent).

### Proof of Concept
Foundry fork test outline:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract FeeTokenMock {
    // minimal ERC20 that burns `feeBps` on every transferFrom (models USDT fee flag / PAXG)
}

contract FeeOnTransferDepositTest is Test {
    IdleCDOEpochVariant cdo;      // deployed with FeeTokenMock as `token`
    IdleCreditVault strategy;
    address alice; // KYC'd wallet (pass isWalletAllowed)

    function test_DepositDuringEpoch_Overcredits() public {
        // setup: owner starts epoch, AA+BB seeded so _trancheTotSupply > 0,
        // isDepositDuringEpochDisabled == false, unscaledApr > 0, not AYS/programmable.

        uint256 amount = 1_000_000e6;
        // token configured with 1% transfer fee
        uint256 balBefore = token.balanceOf(address(cdo));

        vm.prank(alice);
        cdo.depositDuringEpoch(amount, cdo.AATranche());

        uint256 received = token.balanceOf(address(cdo)) - balBefore;
        assertEq(received, amount * 99 / 100);          // fee taken
        // but borrower was sent `amount` — sourced from other depositors' balance,
        // and strategy tokens minted == amount while backing == received.
        assertEq(strategy.balanceOf(address(cdo)), amount); // 1:1 backing claimed
        // invariant broken: minted shares priced on `amount`, vault only holds `received`
    }
}
```

Expected result: tranche tokens minted on the nominal `_amount`, borrower receives `_amount`, and `balanceOf(strategy)`/`getContractValue` overstates real holdings by the fee — reproducing the Blueberry "stored amount ≠ real balance" insolvency primitive on the credit-vault deposit path.
