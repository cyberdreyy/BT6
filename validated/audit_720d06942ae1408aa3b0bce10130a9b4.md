**Reasoning:**

`pending_attribution_snapshot` is a pure `#[view]` function — it performs no state mutation and is never called from within any state-changing entry function in `staking_contract.move`. [1](#0-0) 

Its only consumer in the repo is the off-chain Rosetta balance-reporting client, which uses it purely for informational display of a pending balance and does not feed the result back into any withdrawal, unlock, or distribution transaction. [2](#0-1) 

The actual state-changing accounting paths — `unlock_stake`, `request_commission_internal`, and `distribute_internal` — never read `pending_attribution_snapshot`. Instead they recompute everything directly and atomically from `stake::get_stake`, `staking_contract.principal`, and the live `distribution_pool` contents within the same transaction: `distribute_internal` withdraws `inactive + pending_inactive` directly from the stake pool and updates the pool immediately before paying out, [3](#0-2)  and `unlock_stake` forces a `distribute_internal` and `request_commission_internal` call (which resets `principal`) before recording the new distribution and calling `stake::unlock_with_cap`, all within the same atomic transaction. [4](#0-3) 

Because no code path — on-chain or off-chain — treats the snapshot's return value as an authoritative balance to drive a subsequent unlock/distribute decision, and the function's own doc comment explicitly warns "This function MUST NOT be interpreted as a real-time or pool-level balance," [5](#0-4)  there is no mechanism by which an unprivileged caller relying on stale data from this view function could corrupt share, principal, or commission accounting. The proposed proof idea would only demonstrate that the view is stale relative to `distribute()`, which is already documented behavior, not a code-path where staleness is treated as authoritative.
