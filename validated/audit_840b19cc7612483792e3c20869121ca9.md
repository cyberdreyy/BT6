### Title
Stale confirmations from removed members allow a multisig request to execute below the required confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only removes pending requests that were *created* by the member being deleted; it never scans the `confirmations` map to strip that member's approval from requests created by *other* members. Because `confirm()` only checks the raw size of the confirmation set, a stale approval left behind by a removed member is still counted toward `num_confirmations`, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
The multisig invariant is that a request can only execute once `K` (`num_confirmations`) *current* members have approved it — i.e. `live confirmers on R == num_confirmations` should imply all confirmers are still in `self.members`.

`delete_member` only cleans up requests where the removed member was the original requester: [1](#0-0) 

It filters `self.requests` by `r.member == member` (the account that called `add_request`), and only for those matched requests does it call `self.confirmations.remove(&request_id)`. It does not iterate `self.confirmations` to remove the deleted member's key/account string from confirmation sets belonging to requests created by *other* members that this member had previously confirmed.

`confirm()` then blindly trusts the size of the stored `HashSet<String>` without re-validating that each entry is still a current member: [2](#0-1) 

So if member `B` confirms request `R` (created by member `A`), and `B` is later removed via a `DeleteMember` action, `R`'s confirmation set still contains `B`. `B`'s stale entry counts toward `num_confirmations` when other members later confirm `R`, letting `R` execute with fewer than `K` *live* approvals.

This breaks the custody binding: `live_member_confirmations(R) == num_confirmations` before executing any `MultiSigRequestAction::Transfer` (or `FunctionCall`, `AddKey`, etc.). After the exploit, `stored_confirmations(R).len() >= num_confirmations` while `live_member_confirmations(R) < num_confirmations`, i.e. an action is authorized without the required threshold of currently-trusted signers.

### Impact Explanation
This is a Critical-class issue per the custody-binding rules: "a multisig request executed below threshold." A wallet configured as, e.g., 3-of-4 can have a `Transfer`, `AddKey`, `FunctionCall`, or further `DeleteMember`/`AddMember` action executed with only 2 live approvals plus one phantom approval from a member who has already been removed (e.g., because their key was compromised or they left the organization) — precisely the scenario the removal was meant to protect against. Funds or account control can move without the intended quorum.

### Likelihood Explanation
Likelihood is realistic, not merely theoretical: member turnover/removal is a normal operational event for a multisig, and any request that received a partial confirmation before a member was removed remains latently vulnerable. No special privileges beyond being (or having been) a legitimate member are required to create the stale-confirmation state; execution of the exploit only needs the remaining members to confirm as usual, unaware that one of the "confirmations" no longer represents a live signer.

### Recommendation
When executing `DeleteMember`, iterate all entries of `self.confirmations` (not just requests created by the removed member) and strip the removed member's key/account from every confirmation set. Alternatively, at `confirm()` time (or at execution time), filter the stored confirmation set down to entries that are still present in `self.members` before comparing against `num_confirmations`, so stale approvals from removed members can never count toward the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request(R)` for `MultiSigRequestAction::Transfer { amount }` — `confirmations[R] = {}`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1 + 1 = 2 < 3, not executed yet).
4. Members submit and confirm a separate request `DeleteMember { member: B }` to threshold and it executes via `delete_member` (`multisig2/src/lib.rs:356-379`). Since `R` was created by `A` (not `B`), `R` is never touched, so `confirmations[R]` still contains `B`. `self.members` is now `{A, C, D}`.
5. `C` calls `confirm(R)` → `confirmations[R].len() (1) + 1 = 2 < 3`, inserts `C` → `confirmations[R] = {B, C}`.
6. `D` calls `confirm(R)` → `confirmations[R].len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` runs the `Transfer`.

Result: the transfer executes with only `C` and `D` as live confirming members (2 live approvals) plus the stale, no-longer-authorized confirmation of `B` — one below the configured 3-of-4 threshold, demonstrating a threshold bypass rooted in `delete_member` at `multisig2/src/lib.rs:356-379` and the unchecked count comparison in `confirm` at `multisig2/src/lib.rs:292-315`.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
