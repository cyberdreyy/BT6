### Title
Permissionless `lending_pool_emissions_deposit` allows flash-deposit sandwiching to steal a disproportionate share of same-bank emissions from existing depositors - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
The core defect in the external report is that a strategy computes share value using an asset balance that does not yet reflect value which is *about to be* materialized (unclaimed/harvested-but-unconverted rewards), and mints/burns shares atomically around that materialization event, letting an attacker capture value they never contributed. Marginfi's native interest accrual, Kamino integration, and JupLend integration all defensively call `accrue_interest` / `refresh_reserve` / `update_rate` **before** computing the shares for a deposit or withdrawal, closing off the exact GLP-style pattern in those paths. However, `lending_pool_emissions_deposit` reproduces the same underlying flaw: it distributes value ("emissions", i.e. rewards meant for the bank's existing lenders) by directly increasing `asset_share_value` in proportion to `total_asset_shares` at the instant the instruction runs, with no snapshot of who was entitled to those emissions and no minimum holding period.

### Finding Description
`lending_pool_emissions_deposit` is a **permissionless** instruction that anyone can call to deposit "same-bank emissions" directly into the bank's liquidity vault, immediately raising `asset_share_value` for all current shareholders: [1](#0-0) 

The critical lines are: [2](#0-1) 

```
let total_assets = bank.get_asset_amount(total_asset_shares)?;
let updated_total_assets = total_assets.checked_add(I80F48::from_num(amount))...;
bank.asset_share_value = updated_total_assets.checked_div(total_asset_shares)...;
```

This is functionally identical to the GLP `_currentBalance` bug's root cause: value that is meant to be distributed to *existing* depositors is instead spread pro-rata over *whoever holds shares at the moment the value is recognized*, regardless of when those shares were acquired. The test suite explicitly confirms this behavior — `total_asset_shares` is unchanged, but `asset_share_value` jumps up proportionally for every shareholder at that instant: [3](#0-2) 

Because deposit/withdraw are ordinary permissionless user instructions with no cooldown or minimum holding period, an attacker can, in the same slot (e.g. via a Jito bundle or by simply front-running/back-running a known/scheduled emissions deposit transaction with an externally flash-loaned amount):
1. Deposit a very large amount into the target bank immediately before an `lending_pool_emissions_deposit` call executes, minting shares at the pre-emissions `asset_share_value`.
2. Let the emissions deposit execute, which raises `asset_share_value` for the *entire* pool (including the attacker's freshly minted shares) based on `total_asset_shares` that now includes the attacker's inflated position.
3. Immediately withdraw, capturing a share of the emissions proportional to the attacker's now-dominant share of the pool, rather than proportional to any real contribution or time held.
4. Repay the flash loan, pocketing the difference — value that should have accrued only to depositors who were in the bank before the emissions arrived.

This mirrors the report's attack shape exactly: "deposit assets when there are unclaimed rewards ... obtain more shares than they should ... withdraw ... obtain a portion of the previously unclaimed rewards ... to obtain a greater portion, make as large a deposit as possible."

### Impact Explanation
Impact is direct value redirection/theft from legitimate long-term depositors of a bank to an attacker who contributes no real economic value and holds a position for effectively zero duration. The severity scales with (a) the size of the emissions deposit and (b) how large a deposit the attacker can stage relative to the bank's existing `total_asset_shares` (bounded only by `deposit_limit` and available flash-loan liquidity for that mint). For banks with periodic/large emissions programs and modest existing TVL, this could divert a large fraction of each distribution.

### Likelihood Explanation
Likelihood is high: the instruction is intentionally permissionless (`(permissionless) Deposit same-bank emissions directly into liquidity vault`), requires no special privileges, and Solana's transaction/bundle model (e.g. Jito) makes atomic front-run/back-run sandwiching around a known, chain-observable instruction straightforward. `SECURITY.md` explicitly states flash-loan attacks are **not** excluded from scope. No mitigation (lock-up, snapshotting eligible depositors, or minimum accrual duration before withdrawal) is present in the deposit/withdraw or emissions-deposit code paths reviewed.

### Recommendation
Do not distribute same-bank emissions purely by inflating `asset_share_value` for whoever currently holds shares. Instead:
- Snapshot eligible balances/shares before accepting new deposits into a distribution window, or
- Require emissions deposits to only affect balances present since a fixed prior checkpoint (e.g. a merkle/snapshot based distribution, similar to how `emissions_outstanding`/`last_update` already track a per-balance emissions cursor for other emissions in `Balance`), or
- Impose a minimum holding period / decay so freshly-deposited shares don't fully participate in an immediately-following emissions deposit, or
- At minimum, restrict `lending_pool_emissions_deposit` timing/cadence so it cannot be reliably sandwiched (e.g., require it to run via a keeper with randomized/committed timing, or split large distributions into many small unpredictable increments).

### Proof of Concept
1. Bank `B` has depositors with `total_asset_shares = S`, `asset_share_value = V`.
2. Admin/keeper plans to call `lending_pool_emissions_deposit(amount = E)` (this call is publicly visible pre-confirmation, e.g. in the mempool or as a scheduled/known keeper transaction).
3. Attacker takes a flash loan of `A` (mint of bank `B`), where `A >> S*V`.
4. Attacker calls `lending_account_deposit(A)`, minting `A/V` shares, bundled/ordered immediately before the emissions deposit tx.
5. Emissions deposit executes: `asset_share_value_new = (S*V + A + E) / (S + A/V)`.
6. Attacker calls `lending_account_withdraw` (or `withdraw_all`) immediately after, redeeming `(A/V) * asset_share_value_new ≈ A + E*(A/(S*V+A))` — as `A → ∞` relative to `S*V`, the attacker captures nearly all of `E`.
7. Attacker repays the flash loan, netting close to the full emissions amount `E` that was intended for the bank's pre-existing depositors.
This can be validated in the existing bankrun test harness (`programs/marginfi/tests/misc/emissions_deposit.rs`) by adding a large deposit immediately before/after the `try_emissions_deposit` call and comparing the attacker's realized gain versus a baseline depositor's share.

```rust
/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```
