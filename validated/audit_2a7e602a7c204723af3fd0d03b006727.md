### Title
Node-side signer weight double-counted across approve/reject tallies on vote flip - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::process_messages` maintains, per proposed block, two independent weight accumulators (`total_weight_approved`, `total_weight_rejected`) that are supposed to represent disjoint, mutually-exclusive contributions from each signer slot. On the `Rejected` path the accumulator is guarded by inserting the slot into `responded_signers` and only adding weight the first time that insert succeeds. On the `Accepted` path, however, the guard used to decide whether to add weight is a *different* set — `gathered_signatures.contains_key(&slot_id)` — not `responded_signers`. If a signer first rejects a block and later (after a valid, signer-state-machine-sanctioned re-evaluation) accepts the very same block, the slot is already present in `responded_signers` (from the rejection) but absent from `gathered_signatures`, so the `Accepted` handler adds that signer's weight to `total_weight_approved` a second time without ever removing it from `total_weight_rejected`. The same signer's weight is now counted in both ledgers simultaneously, exactly analogous to the LaunchBridge report's core defect: Ether received during `claim` was recorded into the "new deposit" bucket instead of being kept separate from/subtracted against the correct bucket, inflating totals that should have stayed disjoint.

The `Rejected` handler's dedup key is `responded_signers`. The `Accepted` handler's dedup key is `gathered_signatures`. These are two different maps/sets tracking different things (`gathered_signatures` stores the actual signature bytes; `responded_signers` is a generic "has this slot answered" set), and both handlers unconditionally insert into `responded_signers` at the end regardless of which branch ran. Because the `Accepted` branch never checks `responded_signers` before crediting weight, a signer slot that already rejected the block (and is thus already in `responded_signers`) can still credit its weight into `total_weight_approved` when it later sends an `Accepted` message for the same block hash.

On the signer side, this vote flip is an explicitly supported, non-adversarial state transition: `BlockInfo::check_state` permits `LocallyRejected -> LocallyAccepted` transitions (see `stacks-signer/src/signerdb.rs` `check_state`, lines 313-329 in the earlier read), and the flow doc's own state diagram documents `LocallyRejected --> LocallyAccepted : re-evaluated` as a normal path (proposal re-evaluation via `should_reevaluate_reject_reason`). A single signer can legitimately reject a proposal, then — after a later message, timeout expiry, or reconsideration — sign and broadcast an `Accepted` `BlockResponse` for that same `signer_signature_hash`. No majority, no forged key, and no StackerDB-transport trickery is required: it's a normal single-slot sequence of two authentic, correctly-signed messages relayed over StackerDB and consumed by `stackerdb_listener.rs`.

The consequence is that `total_weight_approved` and `total_weight_rejected`, which `signer_coordinator.rs::get_block_status` and `SignCoordinator` treat as if they always sum to at most `total_weight` (a supermajority/blocking-minority partition), can together exceed `total_weight` for a single block. This breaks the aggregated-weight vs. verified-accepts equality the node relies on to decide both "70% signed → accept" and "\>30% rejected → reject": [3](#0-2) 
```
if block_status
    .total_weight_rejected
    .saturating_add(self.weight_threshold)
    > self.total_weight
{
    ...
    return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    info!("Received enough signatures, block accepted"; ...);
    return Ok(block_status.gathered_signatures.values().cloned().collect());
}
```

Both branches key off the same possibly-inflated `total_weight_rejected`/`total_weight_approved` fields, so one signer's weight — counted twice — can move the miner's local threshold decision closer to (or past) either boundary using fewer genuinely-distinct signer endorsements than the protocol's 70%/30% split is supposed to require.

### Impact Explanation
This maps to the report's "Critical: aggregated-weight vs verified-accepts" break category. The block-acceptance and block-rejection weight tallies are the exact mechanism by which the miner decides "the required supermajority signed this block" (`total_weight_approved >= weight_threshold`) versus "a blocking minority rejected it" (`total_weight_rejected + weight_threshold > total_weight`). Double-crediting a single signer's weight into `total_weight_approved` corrupts the equality between the raw signer weight actually verified/accepted and the weight the coordinator believes it has. In the worst case this lowers the effective number of distinct signers needed to reach the 70% signing threshold (since one signer's weight is now "worth double" in the approved bucket while it never left the rejected bucket), weakening the safety margin the network relies on for block finality assembled by `signer_coordinator.rs`.

### Likelihood Explanation
High likelihood of occurrence with no adversarial coordination: the vulnerable path is triggered by a single signer's legitimate, protocol-sanctioned reconsideration of a previously rejected block (`LocallyRejected -> LocallyAccepted`, an explicitly modeled and expected transition in `BlockInfo::check_state` and the flow documentation), relayed over StackerDB exactly as any other signer response is. No forged signatures, no majority collusion, and no local/auth-token access are required — only that the same signer eventually emits two different, both fully valid, `BlockResponse` messages (`Rejected` then `Accepted`) for the same block hash, which the miner's `stackerdb_listener` then mis-tallies due to the mismatched dedup keys.

### Recommendation
Use the same dedup key (`responded_signers`, or an explicit "did we already count weight for this slot in either bucket" set) for both the `Accepted` and `Rejected` branches so that a slot's weight can only ever be credited into one of `total_weight_approved`/`total_weight_rejected`. If a signer flips its vote, either (a) ignore the later message for tallying purposes once the slot has already responded, or (b) explicitly move the slot's weight from one bucket to the other (subtract from the old bucket before adding to the new one) rather than allowing it to accumulate in both.

### Proof of Concept
1. Node proposes block `B` and is waiting on signer responses via `StackerDBListener`.
2. Signer slot `S` (weight `w`) submits `BlockResponse::Rejected` for `B`. `stackerdb_listener.rs` line 515 hits `responded_signers.insert(slot_id)` → true → `total_weight_rejected += w`.
3. Signer `S`, following a valid re-evaluation of the same proposal (`should_reevaluate_reject_reason` returning re-evaluable, e.g. after the node/chain state that caused the rejection changes), later signs and broadcasts `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. `stackerdb_listener.rs` line 443 checks `gathered_signatures.contains_key(&slot_id)` — false, since `S` has never been in `gathered_signatures` (it was only in `responded_signers` from step 2) — so `total_weight_approved += w` is executed.
5. Now both `total_weight_rejected` and `total_weight_approved` include `w` for the same signer `S`, even though `S` cast only one final vote. `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and `get_block_status` in `signer_coordinator.rs` evaluates its accept/reject thresholds against these inflated numbers.

Note: I was not able to execute this scenario in a live/test environment (no runtime access in this session); the above is derived purely from static code-path analysis of `stackerdb_listener.rs` and the documented signer state machine (`signerdb.rs`, `docs/signer-flows.md`). Confirming the exact real-world triggers for a `Rejected → Accepted` flip (which reject reasons are actually re-evaluable, and how often such a flip is expected in practice) would benefit from tracing `should_reevaluate_reject_reason`/`RejectReasonPrefix` more fully in `stacks-signer/src/signerdb.rs` and `libsigner/src/v0/messages.rs`, which were only partially reviewed before this session's tool budget was exhausted.
