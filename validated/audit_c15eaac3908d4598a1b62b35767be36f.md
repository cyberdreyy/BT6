### Title
Stale confirmations from removed multisig members/keys still count toward the confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The `DeleteKey` action in `multisig/src/lib.rs` (v1) and the analogous `DeleteMember` action in `multisig2/src/lib.rs` (v2) only purge requests and confirmations that were *originated* by the removed key/member. They never scrub that key/member's public key/identity out of the `confirmations` set of *other* still-pending requests that it had merely confirmed (but not created). Because `confirm()` counts entries in that set toward `num_confirmations` without re-checking membership at execution time, a request can be executed with fewer currently-authorized signers than the configured threshold — the exact class of bug described in the report ("approvals/authorizations not cleared after the underlying grant is revoked").

### Finding Description
In `multisig/src/lib.rs`, `execute_request`'s `DeleteKey` branch only removes requests whose `signer_pk` equals the deleted key, and clears `num_requests_pk` for that key: [1](#0-0) 

However, `confirm()` adds *any* signer's public key to the `confirmations` `HashSet` for a request regardless of who created it: [2](#0-1) 

If key `K2` confirmed a request `R` created by key `K1` (adding `K2` into `confirmations[R]`), and `K2` is later removed via a separate `DeleteKey { public_key: K2 }` request, the `DeleteKey` handler only looks at `self.requests` filtered by `r.signer_pk == K2` — it does not touch `confirmations[R]`, since `R`'s `signer_pk` is `K1`, not `K2`. `R`'s confirmation count therefore still includes the now-revoked `K2`. When a third live key `K3` later confirms `R`, the check `confirmations.len() as u32 + 1 >= self.num_confirmations` (e.g. `2 + 1 >= 3`) passes and the request executes — counting a confirmation from a key that is no longer a valid signer on the account.

The identical structural flaw exists in `multisig2/src/lib.rs`: `DeleteMember`/`delete_member` (invoked from `execute_request`) removes membership and associated requests originated by that member, but `confirm()` stores confirmations keyed only by `member.to_string()` in a `HashSet<String>` per request, with no re-validation against current `self.members` at confirm/execution time: [3](#0-2) [4](#0-3) 

This is a direct analog of the reported bug class: an approval/authorization record (`confirmations[request_id]`) is not cleared when the underlying authority (`keyManagerOf`/access key or member) that granted it is revoked, so the stale record continues to satisfy a security check (`onlyKeyManagerOrApproved` → here, `num_confirmations` threshold gating) that should only be satisfiable by currently-authorized parties.

**Binding broken:** `confirmations counted for request R` should equal `confirmations from members who are still live members/keys at the time of the threshold check`. Before the `DeleteKey`/`DeleteMember` call, both sides matched (K2 was a live signer). After it, the left side (recorded confirmation count) still includes K2, while the right side (live-signer confirmations) does not — the ledger and reality diverge, and `execute_request` acts on the stale, inflated count.

### Impact Explanation
This allows a multisig request to be executed with fewer currently-authorized confirmations than the configured `num_confirmations` threshold, i.e. "a multisig request executed below threshold" — explicitly listed as a Critical impact. Since `execute_request` can perform `Transfer`, `AddKey`, `DeployContract`, `FunctionCall`, etc., an attacker who was once a legitimate signer (and is later removed, e.g., after an employee offboarding or a compromised-key rotation) can leave behind a "banked" confirmation on a pending request that later gets pushed over threshold by remaining legitimate signers who are unaware the count is stale, or the departing signer can pre-confirm several sensitive pending requests before being removed, effectively retaining influence they should have lost.

### Likelihood Explanation
Requires: (1) a pending multi-step confirmation request that a subsequently-removed key/member had already confirmed, and (2) that key/member being removed via `DeleteKey`/`DeleteMember` without the remaining signers manually noticing/deleting the stale pending request (requests persist until confirmed/executed or explicitly deleted after the 15-minute cooldown via `delete_request`). This is a realistic operational sequence for any multisig account rotating signers (a common security practice), making likelihood moderate rather than requiring an unusual attack setup — no privileged access beyond having once been a legitimate signer is needed.

### Recommendation
- In the `DeleteKey`/`DeleteMember` execution branch, iterate over all pending `requests`/`confirmations` entries and remove the deleted key's/member's entry from every `confirmations[request_id]` set, not just requests it originated.
- Alternatively (and more robustly), validate membership of every entry in `confirmations` against the current `members`/valid-key set at the time `confirm()` computes whether the threshold is met, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` (v1) with `num_confirmations = 3` and three access keys `K1, K2, K3`.
2. `K1` calls `add_request` to create request `R` (e.g. `Transfer`); `signer_pk` of `R` is `K1`.
3. `K2` calls `confirm(R)` → `confirmations[R] = {K2}` (len 1, `1+1 < 3`, so not yet executed).
4. Separately, `K1` and `K3` (or any 3 confirmers, depending on setup) push through a `DeleteKey { public_key: K2 }` request, which executes and calls `promise.delete_key(K2)`. This removes `K2` from `num_requests_pk` and deletes any requests where `signer_pk == K2`, but `confirmations[R]` still equals `{K2}` because `R.signer_pk == K1`.
5. `K3` calls `confirm(R)`: `confirmations.len() (1) + 1 >= 3` is true, so `R` executes — a `Transfer` goes out having been "confirmed" by only `K1` (creator) and `K3` (live), plus a stale confirmation from the now-deleted `K2`, i.e., below the intended 3-live-signer threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
