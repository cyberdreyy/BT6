I found a strong candidate. Let me verify the funded instant-claim path leaves stale per-epoch data that inflates default recovery accounting.### Title
Funded instant-withdraw claims never clear per-epoch receipt basis, permanently corrupting default recovery pricing - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]` and burns the receipt tokens, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . If the borrower defaults later in the same epoch while other instant receipts remain unfunded, `finalizeDefaultRecovery` counts the already-paid (stale) basis again via `defaultPendingClaimBasis` [2](#0-1) , diluting `defaultRecoveryPrice` for every defaulted-epoch claimant and permanently stranding the excess reserve.

### Finding Description
Analogous to the kernel bug (a struct pushed to consumers with stale/unwritten fields), the per-epoch instant-claim buckets are written on `requestInstantWithdraw` [3](#0-2)  but the funded claim path leaves them populated. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to `pendingWithdraws` whenever `pendingInstantWithdraws != 0` at finalization, and `_defaultPrefundedInstantReserve` uses the same stale `instantBasis` [4](#0-3) . `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore computed against an inflated `totalBasis` [5](#0-4) .

Sequence (attacker is an ordinary KYC'd lender; all privileged roles honest):
1. Epoch N running. Attacker calls `requestInstantWithdraw` (via CDO) for X.
2. Honest manager/borrower funding flows through `collectInstantWithdrawFunds`; attacker calls `claimInstantWithdrawRequest` and receives X underlying. `instantWithdrawsRequestsByEpoch[attacker][N] = X` and `instantWithdrawClaimsByEpoch[N]` still contain X.
3. Another user requests instant withdraw Y that remains unfunded (`pendingInstantWithdraws > 0`), or normal `pendingWithdraws > 0` exists.
4. Borrower defaults in epoch N; `finalizeDefaultRecovery` runs with `defaultRecoveryEpoch = N`. `defaultPendingClaimBasis` = `pendingWithdraws + instantWithdrawClaimsByEpoch[N]`, which wrongly includes the already-paid X.
5. `defaultRecoveryPrice` is depressed by factor `realBasis/(realBasis + X)`. Every pending receipt and every active tranche holder claims at the diluted price; the unallocated recovery (`X * price`) stays in `defaultRecoveryReserve` forever — no function can release it.

A secondary consequence: the attacker's own `instantWithdrawsRequestsByEpoch` entry is stale, so `_claimDefaultedInstantWithdrawRequest` would attempt `_burn(_user, X + Y)` against only Y minted receipts and revert [6](#0-5) , meaning the stale basis is unclaimable — the X share of the reserve is permanently frozen.

### Impact Explanation
All defaulted-epoch claimants (pending withdrawers, unfunded instant requesters, and AA/BB tranche holders whose NAV is force-updated to `activeBasis * recoveryPrice`) recover strictly less than entitled. With `X` equal to the claimed instant amount, the loss to honest claimants is approximately `recoveryReserve * X / (realBasis + X)`, and an equal amount of recovered funds is locked in the strategy permanently. This is direct misdistribution of recovered funds plus permanent freezing of unclaimed recovery.

### Likelihood Explanation
Requires only: (a) an instant withdraw requested, funded, and claimed, and (b) a borrower default finalized within the same epoch while any instant or normal pending basis exists. Epochs span a full duration plus buffer, so the same-epoch window is wide; instant claims during a running epoch are a designed flow (prefunded/instant mode). The attacker needs no privileges — a KYC-passing lender suffices — and triggers the corruption simply by claiming a legitimately funded instant withdraw before the default. No existing guard (skim, flags, `_ensureDefaultRecoveryInitialized`, only-CDO) clears the stale per-epoch entries.

### Recommendation
In `claimInstantWithdrawRequest`, when paying the funded path, also clear the per-epoch accounting: determine the user's request epoch entries (or store the user's last instant-request epoch analogously to `lastWithdrawRequest`), subtract the claimed amount from `instantWithdrawClaimsByEpoch[reqEpoch]` and zero `instantWithdrawsRequestsByEpoch[_user][reqEpoch]`, so funded claims can never be re-counted by `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`.

### Proof of Concept
Foundry fork-style PoC (structure mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantBasisDilutesDefaultRecovery() external {
    // setup: epoch running, attacker + victim deposited via AA tranche
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _depositWithUser(makeAddr("victim"), 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    uint256 epoch = creditVault.epochNumber();

    // 1) attacker requests instant withdraw for X
    uint256 X = 5_000 * ONE_SCALE;
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(X, address(AAtranche)); // strategy mints receipt, records by-epoch

    // 2) honest manager funds instant queue; attacker claims X
    deal(defaultUnderlying, borrower, X);
    // CDO pulls funding -> collectInstantWithdrawFunds(X)
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest(); // receives X, by-epoch basis stays stale

    assertEq(creditVault.instantWithdrawsRequestsByEpoch(attacker, epoch), X, "stale basis");

    // 3) victim opens a normal withdraw request (pending basis exists)
    vm.prank(makeAddr("victim"));
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 4) borrower defaults; manager finalizes recovery with recoveredAmount R
    //    pendingInstantWithdraws left non-zero (or pendingWithdraws > 0)
    //    -> cdoEpoch.finalizeDefaultRecovery(R, recoverySource)

    uint256 basis = creditVault.defaultPendingClaimBasis();
    // basis wrongly includes X -> defaultRecoveryPrice < reserve/realBasis
    assertGt(basis, creditVault.pendingWithdraws(), "inflated by stale instant basis");
    // Every claimant is paid at the diluted price; X*price of reserve is stranded forever.
}
```

Note: this assumes index coverage; the exact CDO entry-point names (`requestInstantWithdraw`/`claimInstantWithdrawRequest` on `IdleCDOEpochVariant`, default-finalization entry point) should be confirmed in a live session.
