### Title
Loss-adjusted withdraw receipts are paid at par when a newer request overwrites `lastWithdrawRequest` — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault` tracks each user's pending withdraw receipts both per-epoch (`withdrawsRequestsByEpoch`) and as a single aggregate (`withdrawsRequests`), and marks the *latest* request epoch in `lastWithdrawRequest[_user]`. When an epoch ends in a partial loss via `stopEpochWithDuration`, the borrower funds only `pendingToFund < pendingBasis` and the haircut is recorded in `lossRecoveryPriceByEpoch[epochNumber]` (`collectWithdrawFunds`, lines 411-430). The claim path recovers that haircut only by looking up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`_claimLossAdjustedWithdrawRequest`, lines 789-801). If the same user makes a new withdraw request in a later epoch before claiming, `lastWithdrawRequest` is overwritten (line 282) and the haircutted epoch's receipt falls through to `_claimFundedWithdrawRequest`, which pays the full `withdrawsRequests[_user]` aggregate — including the haircutted epoch's basis — at par (lines 338-349). This is the credit-vault analog of a resource leaked on a failure path: the per-epoch loss marker is orphaned ("not released"/not applied) once a newer request takes its slot.

### Finding Description

In `requestWithdraw` (lines 271-295) the strategy:

- mints a receipt and adds `_amount` to `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]`,
- sets `lastWithdrawRequest[_user] = currentEpoch` unconditionally.

In `collectWithdrawFunds` (lines 411-430), when the borrower under-funds (`_amount < pendingBasis`), `pendingWithdraws` is zeroed and `lossRecoveryPriceByEpoch[epochNumber]` stores the recovery ratio — the haircut is *only* keyed by epoch.

In `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

Only the *most recent* request epoch is checked. Then `_claimFundedWithdrawRequest` (lines 319-350) computes `amount = withdrawsRequests[_user] + apr0…`, burns `normalAmount`, zeroes the aggregate, and pays via `_transferFundedClaim`.

Exploit sequence (running epoch N, fixed-APR mode):

1. Attacker (KYC-passing AA holder) calls `cdoEpoch.requestWithdraw(x, AA)` in epoch N.
2. Epoch N stops with a realized loss: `stopEpochWithDuration(apr, interest, duration, lossAmount)` → borrower funds only `pendingToFund`; `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`.
3. Before claiming, attacker calls `requestWithdraw(y, AA)` in epoch N+1 (buffer period). `lastWithdrawRequest[user]` becomes N+1.
4. Epoch N+1 stops normally and funds `y` fully.
5. Attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[N+1]` → 0 → skipped. `_claimFundedWithdrawRequest` pays `x + y` at par, even though only `x·p/RECOVERY_FULL + y` was ever funded.

The same escape applies to the default path mirror: the epoch-keyed basis that should have been reduced by the loss price is silently folded into the funded aggregate.

### Impact Explanation

Direct theft / insolvency. The strategy was funded `x·p` for the loss epoch but pays `x`, so the difference `x·(1 − p)` is taken from underlyings reserved for other claimants' funded receipts or the default recovery reserve (`_transferFundedClaim` only reverts when it would dip into `defaultRecoveryReserve`; with no active reserve it simply drains the balance). Quantified loss: for a 50% recovery price and a receipt of 100k USDC basis, the attacker steals ~50k USDC. Every later claimer is haircutted indirectly, breaking the loss-socialization invariant that all pending receipts share the epoch loss pro rata.

### Likelihood Explanation

High once a loss epoch occurs: the attacker only needs an unclaimed receipt in the loss epoch plus one ordinary `requestWithdraw` in the next epoch — both are unprivileged actions, and comments in `_claimFundedWithdrawRequest` explicitly allow re-requesting while an old receipt is pending. The bug requires a `stopEpochWithDuration` with `lossAmount > 0`, which is an honest-manager flow (borrower under-repayment), not attacker-controlled, so likelihood is conditional on a realized-loss event but the attack itself has no further barrier.

### Recommendation

Resolve all outstanding haircut epochs in `_claimLossAdjustedWithdrawRequest`/`claimWithdrawRequest`, not just `lastWithdrawRequest`. Concretely: when clearing via `_clearWithdrawClaimForEpoch` for epoch N, also scan/record which epochs of the user carry a `lossRecoveryPriceByEpoch != 0` (e.g., store a per-user list/flag `userHasLossEpoch[user][epoch]` set at `requestWithdraw` time or at `collectWithdrawFunds` via per-epoch pending snapshot), and apply the haircut to each such epoch's basis in the funded-claim path rather than paying `withdrawsRequests[_user]` verbatim. Alternatively, block `requestWithdraw` while `_hasWithdrawRequest(_user)` is true and any of the user's epochs has a non-zero `lossRecoveryPriceByEpoch` unclaimed.

```solidity
// setup: deal USDC to attacker, depositAA, startEpoch
// 1) attacker requests withdraw in running epoch N
cdoEpoch.requestWithdraw(attackTranches, address(AAtranche));
// 2) warp past epochEndDate; borrower repays interest + pendingToFund only
uint256 pending = strategy.pendingWithdraws();
uint256 loss = pending / 2;                       // 50% loss on pending receipts
(uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
deal(usdc, borrower, expectedInterest + pendingToFund, true);
vm.prank(borrower); IERC20(usdc).approve(cdo, type(uint256).max);
vm.prank(manager); cdo.stopEpochWithDuration(apr, interest, duration, loss);
// 3) attacker requests again in next epoch (lastWithdrawRequest overwritten)
vm.prank(manager); cdo.startEpoch();
cdoEpoch.requestWithdraw(moreTranches, address(AAtranche));
// 4) next epoch stops fully funded; attacker claims
_stopCurrentEpoch();
cdoEpoch.claimWithdrawRequest();
// assert received == attackBasis + moreBasis  (par)
// while strategy was funded only attackBasis/2 + moreBasis
// and a second user's funded claim now reverts/underpays
```
