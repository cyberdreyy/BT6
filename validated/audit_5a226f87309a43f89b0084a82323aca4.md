### Title
Blacklisted user cannot claim withdraw receipts — funds permanently stuck because claims are address-bound and receipt transfers are disabled - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes a contract where only a fixed `_USER` address can withdraw, so a USDC-blacklisted user's funds are permanently stuck. The analogous surface in idle-tranches is the withdraw-claim flow in `IdleCreditVault` reached via `IdleCDOEpochVariant`: every claim path pays out to `msg.sender` with no recipient override, and the strategy-token receipts that prove the claim are non-transferable by design (`_transfer` reverts for anyone but the CDO, `canTransfer` cannot be re-enabled). When the underlying is a blackl istable token (the vault's underlying is USDC), a blacklisted lender can never receive the payout and cannot delegate or transfer the claim to a clean address — the funds are permanently frozen.

### Finding Description
All payout paths hard-code the receiver as the claimant address:

- `IdleCDOEpochVariant.claimWithdrawRequest()` / `claimInstantWithdrawRequest()` pass `msg.sender` as `_user` to the strategy [1](#0-0) 
- `IdleCreditVault.claimWithdrawRequest(_user)` and `claimInstantWithdrawRequest(_user)` ultimately call `_transferFundedClaim(_user, amount)` / `_transferDefaultRecovery(_user, amount)`, which do `underlyingToken.safeTransfer(_user, _amount)` [2](#0-1) 
- The same holds for `IdleCDOEpochQueue.claimWithdrawRequest`, which does `underlying.safeTransfer(msg.sender, ...)` [3](#0-2) 

Unlike `DefaultDistributor.claim(address _to)`, which lets a holder redirect the payout to an arbitrary recipient [4](#0-3) , none of the vault/queue claim functions accept a recipient parameter.

The escape hatch that normally mitigates this bug class — transferring the claim receipt to another address that claims on the user's behalf — is deliberately closed. Withdraw receipts are minted as strategy tokens to `_user` in `requestWithdraw`/`requestInstantWithdraw` [5](#0-4) , but `_transfer` reverts unless `msg.sender == idleCDO`, and `setCanTransfer` can only ever set the flag to `false` [6](#0-5) . Likewise, `requestWithdraw` requires the caller to burn tranche tokens, so a third party cannot claim on behalf of the blacklisted user.

Result: a user whose address is added to the USDC blacklist after opening a withdraw request (or holding claimable queue entitlements `userWithdrawalsEpochs`) has every call to `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert inside `USDC.transfer`, forever.

### Impact Explanation
Permanent freezing of funds. All underlying owed to the blacklisted user — funded receipts, loss-adjusted receipts (`lossRecoveryPriceByEpoch`), default-recovery claims (`_claimDefaultedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`), instant-withdraw claims, and queued `userWithdrawalsEpochs` entitlements — becomes unclaimable. The loss equals 100% of that user's claim basis. The locked receipts also keep `withdrawsRequests`/`apr0Users`/`defaultRecoveryReserve` accounting pinned for that user indefinitely.

### Likelihood Explanation
USDC blacklisting is a real and recurring event (Circle freezes sanctioned/flagged addresses). Any KYC'd lender, tranche holder, or queue user can be blacklisted between requesting a withdrawal and claiming it. No privileged misbehavior is required. It is a conditional rather than attacker-driven scenario, which typically caps severity at Medium under contest conventions, but the fund-freezing impact is unconditional once it occurs.

### Recommendation
Add an explicit recipient parameter to the claim path, e.g. `IdleCDOEpochVariant.claimWithdrawRequest(address _to)` / `claimInstantWithdrawRequest(address _to)` forwarded to `IdleCreditVault.claimWithdrawRequest(msg.sender, _to)` and paying `_to`, plus `IdleCDOEpochQueue.claimWithdrawRequest(uint256 _epoch, address _to)`. Keep `msg.sender` as the receipt owner for accounting (`_burn(msg.sender, ...)`, `withdrawsRequests[msg.sender]`) so only the entitlement owner can redirect the payout. This matches the existing `DefaultDistributor.claim(_to)` pattern already used in the codebase.

### Proof of Concept
Foundry fork test (mainnet, USDC as `defaultUnderlying`). Sketched against `test/foundry/IdleCreditVault.t.sol` helpers:

```solidity
// test/foundry/BlacklistClaim.t.sol
function testBlacklistedUserCannotClaim() external {
    address user = makeAddr('blacklistedUser');
    uint256 amount = 10_000 * ONE_SCALE;

    _depositWithUser(user, amount, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    vm.prank(user);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // burns tranches, mints receipt to user

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());
    // receipts are now funded and claimable (epochNumber > lastWithdrawRequest)

    // Simulate Circle blacklisting `user` on real USDC.
    // USDC FiatTokenV2: isBlacklisted(address) getter + Blacklister role.
    vm.mockCall(
        defaultUnderlying,
        abi.encodeWithSignature("isBlacklisted(address)", user),
        abi.encode(true)
    );
    // For a stricter variant, prank the real USDC blacklister:
    // vm.prank(USDC_BLACKLISTER);
    // FiatTokenV2(defaultUnderlying).blacklist(user);

    vm.prank(user);
    vm.expectRevert(); // USDC.transfer reverts: "Blacklistable: account is blacklisted"
    cdoEpoch.claimWithdrawRequest();

    // No alternative path exists:
    // - strategy token receipt cannot be transferred (_transfer reverts unless msg.sender == idleCDO)
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    IERC20(address(strategy)).transfer(makeAddr('clean'), 1);

    // - claimWithdrawRequest/claimInstantWithdrawRequest have no recipient param
    // - setCanTransfer(true) is impossible; manager can only set false
    vm.prank(strategy.manager());
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    strategy.setCanTransfer(true);

    // The user's claim basis stays locked forever
    assertGt(strategy.withdrawsRequests(user), 0);
}
```

The same PoC applies to `IdleCDOEpochQueue.claimWithdrawRequest` (queue user blacklisted after `processWithdrawalClaims`) and to the post-default recovery claims (`_transferDefaultRecovery` also pays `_user` only).

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @inheritdoc ERC20Upgradeable
  /// @dev Receipt claims are address-bound, so only the IdleCDO can move strategy tokens.
  function _transfer(address sender, address recipient, uint256 amount) internal virtual override {

    super._transfer(sender, recipient, amount);
  }

      epochPendingClaims[_epoch] != 0

      IERC20Detailed(underlying).safeTransfer(msg.sender, amount * _withdrawPrice / ONE_TRANCHE);
