### Title
`get_builder_withdrawals()` emits the *requested* withdrawal amount uncapped, while `apply_withdrawals()` deducts only `min(amount, builder.balance)` — Gwei created for the fee recipient - (File: `specs/gloas/beacon-chain.md`)

### Summary
In the Gloas fork, builder withdrawals are two-step: `get_builder_withdrawals()` builds the `Withdrawal` objects (which are what the execution layer actually mints to `address`), and `apply_withdrawals()` separately deducts the corresponding amount from CL-side accounting (`state.builders[...].balance`). These two paths use different amounts when a builder's balance is insufficient to cover its own pending withdrawal request, breaking the invariant that "Gwei withdrawn from CL state == Gwei credited on EL state."

### Finding Description
`get_builder_withdrawals()` copies the requested amount from `state.builder_pending_withdrawals` verbatim into the `Withdrawal.amount` field with no capping to the builder's actual balance: [1](#0-0) 

That `Withdrawal` object (`amount=withdrawal.amount`, uncapped) is exactly what is appended to `state.payload_expected_withdrawals`/the execution payload's `withdrawals` list, which the execution layer is bound to honor and credit in full to `address` (this is a core cross-layer invariant for beacon-chain withdrawals — the EL mints the withdrawal amount unconditionally).

Meanwhile, `apply_withdrawals()` deducts a **different, capped** amount from the CL builder balance: [2](#0-1) 

```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
```

So if `withdrawal.amount > builder_balance`, the CL only debits `builder_balance` (i.e., zeroes it out), but the `Withdrawal` object still carries the full, uncapped `withdrawal.amount`, which the EL will mint to `fee_recipient`. The delta (`withdrawal.amount - builder_balance`) is Gwei created out of nothing and paid to the fee recipient, with no corresponding CL-side balance ever having existed to back it.

This is confirmed directly in-repo by the spec's own test suite documentation and test cases: [3](#0-2) [4](#0-3) 

`test_builder_withdrawal_insufficient_balance` explicitly sets up: builder balance = 1 ETH, pending withdrawal request = 5 ETH, and asserts the post-state has:
- `builders[0].balance == 0` (deduction capped to 1 ETH)
- `withdrawal.amount == 5 ETH` (the uncapped, requested amount) still present in `payload_expected_withdrawals`

i.e. the spec (and its tests) explicitly accept as correct behavior that the CL commits a `Withdrawal` for 5 ETH to be minted on the EL side while only ever having deducted 1 ETH of real balance.

Compare this with how validator partial/full withdrawals are computed: there, the amount placed into the `Withdrawal` object is *always* pre-capped to the actual balance before being emitted (e.g. `amount=min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)` in Electra's partial withdrawal path, or `amount=balance` for full withdrawals): [5](#0-4) 

The builder pending-withdrawal path is the odd one out — it defers the capping to `apply_withdrawals()` instead of capping it up front when constructing the `Withdrawal`, so the two paths disagree on the amount actually available.

### Impact Explanation
A builder (or an operator that can enqueue a `BuilderPendingWithdrawal`, e.g. via `settle_builder_payment` after `process_execution_payload_bid`) can have their balance reduced below a previously-queued pending-withdrawal amount (e.g. through subsequent slashable-adjacent activity is not needed — simply having *any* two pending withdrawals queued whose sum exceeds current balance, or a withdrawal request queued before balance decreases from later withdrawals in the same processing pass, triggers this). When such an under-collateralized pending withdrawal is processed, the execution layer receives and must honor a `Withdrawal` with the full uncapped amount, minting ETH to `fee_recipient` that was never backed by the builder's CL balance. This is a direct "Gwei created and paid to a non-owner-derived amount" bug — it inflates total ETH supply relative to what the beacon chain believes it has debited, undermining the equality that (CL balance decrease) == (EL amount credited) that the withdrawal mechanism is supposed to enforce.

### Likelihood Explanation
This does not require any external or malicious actor; it is inherent to the current spec logic and is reachable purely through legitimate use: multiple builder pending withdrawals for the same builder queued while balance is insufficient to cover all of them (a scenario the spec's own tests deliberately construct, showing the authors are aware of and have accepted this state, but the tests only check CL-side balance capping, not the cross-layer supply invariant). Given `MAX_WITHDRAWALS_PER_PAYLOAD` allows multiple withdrawals to be queued per builder and processed in the same block (see `test_duplicate_builder_index_in_pending_withdrawals`), and `builder_pending_withdrawals` accumulates amounts that are never validated for solvency against `builder.balance` at insertion time, the insufficient-balance state is trivially reachable.

### Recommendation
Cap the amount placed into the `Withdrawal` object inside `get_builder_withdrawals()` to the builder's *current, running* balance (accounting for any prior withdrawals already queued for the same builder in this block, analogous to how `get_pending_partial_withdrawals` and `get_validators_sweep_withdrawals` use `get_balance_after_withdrawals` / `all_withdrawals` to track cumulative effects), so that the amount ultimately emitted for EL minting never exceeds the amount actually deducted from `state.builders[...].balance`. This restores the invariant that the Gwei debited on the CL equals the Gwei credited on the EL.

### Proof of Concept
Using the same scenario the repo's own test constructs:
1. `state.builders[0].balance = 1_000_000_000` (1 ETH).
2. `state.builder_pending_withdrawals` contains one entry: `BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=X)`.
3. `process_withdrawals(state)` runs:
   - `get_builder_withdrawals` emits `Withdrawal(validator_index=builder_index_flag(0), address=X, amount=5_000_000_000)` — unchanged from the raw request.
   - `apply_withdrawals` executes `state.builders[0].balance -= min(5_000_000_000, 1_000_000_000)` → `state.builders[0].balance = 0`.
4. This `Withdrawal` (amount = 5 ETH) is included in `state.payload_expected_withdrawals`, which the execution layer is bound to apply, minting 5 ETH to address `X`.
5. Net result: CL debited only 1 ETH from the builder, but 5 ETH was minted on the EL — 4 ETH of Gwei created without any backing balance ever existing.

This exact behavior is asserted as expected/correct in-repo: [6](#0-5)
