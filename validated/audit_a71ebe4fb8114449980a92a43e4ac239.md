## Title
Griefing DoS in `staking_contract::distribute_internal` and `vesting::distribute` via `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` abort — one unprivileged shareholder can permanently strand stake, rewards, and commission for all co-shareholders - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` and `vesting::distribute` pay out all shareholders of a shared `distribution_pool`/`grant_pool` in a single atomic loop, using `aptos_account::deposit_coins` for each recipient. `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is unregistered for `AptosCoin` and has disabled direct transfers via `aptos_account::set_allow_direct_coin_transfers`. Because any account, including any of the shareholders in a shared vesting contract, can unilaterally set this flag on itself, any single unprivileged shareholder can make the entire batched distribution transaction permanently and irrecoverably revert, blocking commission and reward withdrawal for every other party sharing that same staking/vesting contract. This mirrors the tokenfactory `BeforeSendHook` DoS pattern: an unprivileged actor makes their own inbound transfer fail, and that failure propagates to abort an entire multi-party payout that other honest, unrelated parties depend on.

### Finding Description
`distribute_internal` in `staking_contract.move` iterates over every shareholder in the `distribution_pool` (staker + operator/beneficiary) and calls `aptos_account::deposit_coins` for each, inside one atomic while-loop: [1](#0-0) 

`aptos_account::deposit_coins` will abort if the target is not yet registered for `AptosCoin` and has explicitly disabled arbitrary/direct coin transfers: [2](#0-1) 

The `allow_arbitrary_coin_transfers` flag that gates this check is fully self-controlled — any account (unprivileged) can call `aptos_account::set_allow_direct_coin_transfers` to disable it on itself at any time: [3](#0-2) 

Because Move transactions revert entirely on abort, if any shareholder in the shared `distribution_pool` (e.g., the staker itself, or — in the `vesting.move` grant_pool case — any one of potentially many shareholders) is unregistered for `AptosCoin` and has this flag disabled, the whole `distribute`/`distribute_internal` transaction aborts. This happens *after* `stake::withdraw_with_cap` has already pulled funds out of the stake pool into a local `Coin<AptosCoin>` — but since the abort unwinds the whole transaction, no funds move and nothing is permanently corrupted at the ledger level per se; however, the distribution path becomes permanently blocked for every other stakeholder sharing that same `StakingContract`/`VestingContract`, since `distribute`/`distribute_internal` is the only path to move inactive/pending_inactive stake into the shareholders' wallets, and every call will hit the same failing recipient and abort deterministically, every time, for as long as that malicious shareholder keeps the flag disabled and stays unregistered.

`vesting.move`'s own `distribute` (called after `staking_contract::distribute`) similarly pays out `grant_pool` shareholders that can include multiple unrelated parties in a single vesting contract; the same self-inflicted-but-externally-blocking abort pattern applies there.

This is the exact structural analog of the external report: in the Cosmos case, a malicious token creator sets a hook address that fails on every transfer, which aborts `BeforeDelegationSharesModified`/reward distribution for *all* co-participants of a shared stake pool. Here, an unprivileged co-shareholder of a shared Aptos `staking_contract`/`vesting` pool can similarly weaponize a legitimate, self-controlled configuration flag (`allow_arbitrary_coin_transfers`) to make the shared distribution function abort unconditionally, denying all other co-shareholders (including the operator's commission and the staker's/other-shareholders' rewards) their rightful payout indefinitely.

### Impact Explanation
- Any co-shareholder of a `staking_contract` (staker vs. operator/beneficiary) or a `vesting` grant pool (multiple shareholders) can permanently block `distribute`/`request_commission`-triggered distribution for every other party sharing that pool, by disabling direct coin transfers on their own unregistered account.
- This traps operator commission and other shareholders' vested/reward stake in a perpetually stuck state — the underlying `StakePool`'s inactive/pending_inactive stake can never be moved out via this path while the malicious flag/registration state persists, since every retry hits the identical abort.
- This qualifies under "Permanent lock or non-recoverable loss of claim rights in stake, commission, beneficiary, or vesting flows" and "share-accounting corruption ... that traps value," reachable by any unprivileged account that is itself a legitimate shareholder in the affected pool.

### Likelihood Explanation
Likelihood is moderate: the attacker must be a legitimate shareholder of the target `staking_contract`/`vesting_contract` (i.e., already a delegator/operator/vesting-beneficiary in that specific pool) and must not yet be registered for `AptosCoin` while explicitly disabling direct transfers — both of which are trivially achievable by a griefing insider (e.g., a vesting-contract co-shareholder who wants to hold other shareholders' funds hostage, or a staker who wants to block the operator's commission). It requires no special privilege beyond already being a participant in the shared pool, matching the "unprivileged users" scope of this scan.

### Recommendation
- In `distribute_internal` (`staking_contract.move`) and `vesting::distribute`, do not let a single recipient's deposit failure abort the entire batch. Wrap each `aptos_account::deposit_coins` call so failures are isolated per-recipient (e.g., retain/re-queue that recipient's redeemed share instead of aborting the whole loop), or pre-validate recipients before committing withdrawals from the stake pool.
- Alternatively, use a "pull" pattern for individual shareholders' funds instead of a "push" loop, so that one recipient's unwillingness/inability to receive funds cannot block others' withdrawals.

### Proof of Concept
1. Admin creates a `vesting_contract` with two shareholders, A (honest) and B (attacker), plus an operator.
2. B calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account and ensures they are not registered for `AptosCoin` (e.g., a fresh resource/derived address never funded directly).
3. Stake pool accrues rewards; lockup expires so funds become inactive/withdrawable.
4. Anyone calls `vesting::distribute(contract_address)` (public, permissionless per `staking_contract.move` comment "Allow anyone to distribute already unlocked funds").
5. `staking_contract::distribute_internal` succeeds (single staker recipient = vesting contract's resource account), but `vesting::distribute`'s subsequent shareholder payout loop hits B's address, `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, and the entire transaction reverts.
6. A (honest shareholder) can never receive their vested/rewarded funds through `distribute`/`distribute_many` as long as B maintains this state, since every retry deterministically fails at the same point.

Note: I could not execute this in a live Move test environment within this session; the trace is derived from static analysis of `aptos_account::deposit_coins` at [2](#0-1)  combined with the atomic shareholder loop in `distribute_internal` at [1](#0-0) . I was unable to fully inspect the body of `vesting::distribute` (lines 719–750) due to index truncation, so the exact shareholder-loop implementation in `vesting.move` should be verified directly in a full checkout before finalizing severity, though the `staking_contract.move` path alone is sufficient to demonstrate the core invariant break.
