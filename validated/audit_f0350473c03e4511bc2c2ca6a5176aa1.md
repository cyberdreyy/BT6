### Title
Stale rejection weight is never retracted when a signer flips to Accepted, letting a fully-signed block be miscounted as globally rejected - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` maintains two independent, additive tallies per block — `total_weight_approved` and `total_weight_rejected` — inside a shared `BlockStatus` struct [1](#0-0) . When a signer who previously rejected a block later reconsiders and accepts the same block (a state transition the signer protocol explicitly supports), the `Accepted` handler adds that signer's weight to `total_weight_approved` but never removes it from `total_weight_rejected`. Just like the `removeLiquidity()` bug where `poolAmount` was decremented by only `netOutAmount` while `pFee` stayed tracked separately, here a single signer's weight is left permanently "double booked" across two supposedly mutually-exclusive buckets, inflating `total_weight_rejected` beyond what current signer opinions justify.

### Finding Description
`BlockStatus` tracks a shared `responded_signers: HashSet<u32>` plus two separate weight counters [1](#0-0) .

In the `Rejected` branch, weight is only added when the signer is being recorded for the *first* time (`responded_signers.insert(slot_id)` returns `true`): [2](#0-1) 

In the `Accepted` branch, however, the guard checked is `gathered_signatures.contains_key(&slot_id)`, **not** `responded_signers.contains(&slot_id)**: [3](#0-2) 

Sequence that breaks the invariant "each signer's weight counts in exactly one bucket":
1. Signer X sends `BlockResponse::Rejected` for block `H`. `responded_signers.insert(X)` succeeds → `total_weight_rejected += weight(X)`.
2. Signer X later reconsiders (the signer state machine explicitly allows reconsidering a previously rejected proposal for certain reject reasons — see `stacks-signer/CHANGELOG.md` "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected") and sends `BlockResponse::Accepted` for the **same** `signer_signature_hash` `H`.
3. In the `Accepted` handler, `gathered_signatures` does not yet contain X's slot, so `total_weight_approved += weight(X)`. `responded_signers.insert(X)` is a no-op (already present) — but critically, nothing ever decrements `total_weight_rejected`.

The result: X's weight is now counted in both `total_weight_approved` and `total_weight_rejected` simultaneously for the lifetime of that `BlockStatus` entry. This breaks the aggregated-weight-vs-verified-decisions equality that `SignerCoordinator::get_block_status` relies on to make its accept/reject decision: [4](#0-3) 

Because the rejection-threshold branch (`total_weight_rejected + weight_threshold > total_weight`) is checked and returned as an `Err` *before* the approval branch (`total_weight_approved >= weight_threshold`) is ever reached in the same `if/else if` chain, a block that has genuinely collected enough accepting weight from **every** signer (including those who initially rejected and later reconsidered) can still be misclassified as `SignersRejected` purely because of stale weight from votes that are no longer current.

### Impact Explanation
This is a liveness wedge on the block-production coordinator: the node running `SignerCoordinator::get_block_status` can treat a block that has actually reached full/adequate signer support as globally rejected, aborting the proposal and forcing a resubmission cycle, purely due to an accounting defect (stale rejection weight never retracted) rather than any genuine lack of support. It undermines the aggregated-weight vs. verified-accepts equality the coordinator depends on for its threshold decision, matching the "wedge the state machine" category in scope. This does not require a majority of signers or another signer's key — a single signer legitimately exercising the documented "reconsider a previously rejected block" behavior is sufficient to corrupt the tally for that block.

### Likelihood Explanation
High. The "reconsider a previously rejected proposal" behavior is a standard, non-adversarial part of the signer protocol (documented in the CHANGELOG as intentional functionality for certain reject reasons), so this reject→accept sequence for the same block hash can occur in ordinary operation whenever a signer initially rejects (e.g., due to a transient validation/timing issue) and later legitimately signs the same block. No majority collusion, forged signatures, or protocol violation is required — only the natural timing of one signer's opinion change.

### Recommendation
Track responded signers with their current decision (accept/reject) rather than two independently-accumulating counters keyed only by insertion order. When an `Accepted` message supersedes a prior `Rejected` for the same slot_id (or vice versa), subtract the signer's weight from the stale bucket before adding it to the new one, e.g.:
```rust
if let Some(prev) = block.decisions.insert(slot_id, Decision::Accepted) {
    if prev == Decision::Rejected {
        block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
    }
}
```
so that `total_weight_approved` and `total_weight_rejected` always reflect only the signer's *current* decision.

### Proof of Concept
1. Coordinator proposes block `H` and calls `get_block_status`, populating a fresh `BlockStatus` for `H` [5](#0-4) .
2. Signer X (weight `w_x`) sends `BlockResponse::Rejected(H)`. `stackerdb_listener` records `total_weight_rejected += w_x` and `responded_signers.insert(X)` [2](#0-1) .
3. Enough other signers reject too, but not (yet) enough to cross the blocking-minority threshold.
4. Signer X reconsiders and sends `BlockResponse::Accepted(H)` for the identical `signer_signature_hash`. Because `gathered_signatures` does not contain X, `total_weight_approved += w_x` is applied [3](#0-2) , but `total_weight_rejected` is left unchanged (still includes `w_x`).
5. If the remaining set of signers (excluding X, whose weight is now double-booked) subsequently all accept, `total_weight_approved` can reach `weight_threshold`, but `total_weight_rejected` (still inflated by `w_x` from step 2, plus other stale rejecters) also independently crosses `total_weight - weight_threshold`.
6. In `get_block_status`'s `if/else if` chain, the rejection branch is evaluated first and returns `Err(NakamotoNodeError::SignersRejected{...})` [6](#0-5) , even though every signer currently supports the block — a valid, fully-signable block is discarded as rejected due to the un-retracted stale weight.
