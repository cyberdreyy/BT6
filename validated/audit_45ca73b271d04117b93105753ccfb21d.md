### Title
Miner-Controlled `last_activity_time` Reset Suppresses the Inactivity Timeout, Wedging the Signer's Fallback-to-Prior-Miner Liveness Guard - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` re-arms the tenure's inactivity clock (`update_last_activity_time`) whenever the *current* sortition-winning miner sends *any* competing/invalid block proposal at or below the height of the already-signed tip — including one that is later rejected. That same `last_activity_time` value is the sole input to `SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs`), which gates the signer set's fallback to the prior miner. A single miner can therefore stall the inactivity timeout indefinitely by repeatedly sending cheap, invalid/conflicting proposals, exactly mirroring the "reset a liveness/accrual timestamp with a trivial call" bug class in the referenced report.

### Finding Description
`check_latest_block_in_tenure` compares an incoming proposal's `chain_length` against the tenure's last signed block. If the new proposal does **not** advance the chain (`block.header.chain_length <= info.block.header.chain_length`), the function still calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` before returning `Ok(false)` (rejecting the block): [1](#0-0) 

This is deliberate "count invalid proposals as miner activity" logic (confirmed by the test `pre_committed_block_does_not_veto_replacement`, which asserts that a proposal conflicting with a fresh pre-commit "still counts as miner activity"): [2](#0-1) 

`last_activity_time` is stored per tenure (`consensus_hash`) with no per-signer/per-source distinction and no rate limit: [3](#0-2) 

It is consumed exclusively by `SortitionState::is_timed_out`, which computes `elapsed` since `last_activity_time` (falling back to burn-block receive time only if never set) and declares the miner inactive only once `elapsed > block_proposal_timeout`: [4](#0-3) 

Because the *only* actor who can legitimately produce block headers for a tenure is that tenure's sortition-winning miner, this is a single-miner-controlled input, exactly analogous to the report's `depositWeth(receiver, 1)` griefing: a minimal, cheap action (send a stale/invalid/conflicting proposal) resets a timestamp that gates a liveness/safety mechanism for someone else (the rest of the signer set, and the next legitimate miner).

### Impact Explanation
The inactivity timeout (`is_timed_out`) is the mechanism by which the signer set decides the current miner has gone dark and it is safe to accept a tenure-extend / fall back to the prior miner (see `docs/signer-flows.md` section 8, "current tenure timed out? check_miner_inactivity → v1/v2 SortitionState::is_timed_out"). A miner who has stopped producing *valid, advancing* blocks — but who keeps re-sending old/invalid/conflicting proposals at zero cost — perpetually refreshes `last_activity_time` and thus is never marked inactive. This wedges the signer set into waiting on a miner that will never again produce a valid block, i.e., "a signer wedged into never signing valid blocks" for that tenure: no fallback is triggered, no tenure-extend is authorized, and block production for that burn view stalls until the next Bitcoin block/sortition. This is a liveness break attributable to a single one-slot miner with no majority/collusion required.

### Likelihood Explanation
High. The attacking miner already controls the tenure (it is the current sortition winner) and needs only to submit a proposal whose `chain_length` does not exceed the tenure's current signed tip — trivially constructible, and it doesn't even need to pass node validation, since the reject path in `check_latest_block_in_tenure` fires before validation is spent and is purely a local, height-based comparison. Repeating this on a fast cadence (well within `block_proposal_timeout`, default 4 hours per the CHANGELOG note) keeps `elapsed` from ever crossing the threshold, at negligible cost and with no signer-side rate limiting on this specific update path.

### Recommendation
- Do not treat an invalid/non-advancing proposal from the *same* miner as fresh "activity" once a threshold number of such re-proposals have been observed for the same `chain_length`/consensus hash within a short window; require it to be a materially distinct or higher-signed proposal.
- Separate "the miner is alive on the network" from "the miner is trying to reorg/replace the tip": count basic liveness via burn-block/keep-alive signals rather than via arbitrary attacker-suppliable block headers, or cap how much cumulative time an unbounded stream of invalid proposals can keep `is_timed_out` suppressed (e.g., use `min(now, first_seen_invalid_proposal_time + max_grace)` rather than the latest reset each time).
- Consider bounding `update_last_activity_time` calls per tenure per unit time so a miner cannot indefinitely refresh the timer just by flooding conflicting proposals.

### Proof of Concept
1. Sortition elects Miner M for tenure `T` (consensus hash `ch_T`). M proposes and the signer set signs block `B` at `chain_length = N` (`get_last_signed_block(ch_T) == B`).
2. M goes idle with respect to producing new valid blocks but, just before `block_proposal_timeout` would otherwise elapse since `last_activity_time`, resubmits (or crafts) any proposal `B'` for `ch_T` with `chain_length <= N` (e.g., re-send `B` itself, or any lower/equal-height block).
3. `check_latest_block_in_tenure` finds `B'.chain_length <= B.chain_length`, logs the rejection, and — because `info.signed_group` is either `None` or recent — calls `signer_db.update_last_activity_time(ch_T, now)` per `stacks-signer/src/chainstate/mod.rs:403-417`, then returns `Ok(false)`.
4. Repeat step 2 on a cadence shorter than `block_proposal_timeout`. Each iteration resets `last_activity_time`, so in `SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs:76-93`) `elapsed` never exceeds `block_proposal_timeout`, and `is_timed_out` never returns `true`.
5. Consequently `check_miner_inactivity`/`capitulate_viewpoint` (per `docs/signer-flows.md` section 8) never falls back to the prior miner, and the signer set remains wedged waiting on M, which never produces another valid, advancing block — a sustained liveness stall triggerable by the single elected miner with only cheap, locally-rejected proposals.

Note: I was not able to fully trace `check_miner_inactivity`'s exact call frequency/gating in `stacks-signer/src/v0/signer_state.rs` within the available iterations (only its declaration site was located, not its body), so the precise cadence at which `is_timed_out` is polled is not independently confirmed here — this should be verified in a follow-up review of `stacks-signer/src/v0/signer_state.rs`.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
