### Title
A new `requestWithdraw` resets the epoch timer on a user's already-matured withdraw receipt, re-locking claimable funds for a full epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external report describes an unfair unlock-time accounting: making any additional deposit resets (or disproportionately extends) the unlock timer for the user's entire locked balance, including amounts that were about to vest or had already vested. The same defect exists in `IdleCreditVault`: each `requestWithdraw` call overwrites `lastWithdrawRequest[_user] = currentEpoch`, while `_claimFundedWithdrawRequest` only allows claiming when `epochNumber > lastWithdrawRequest[_user]`. A user with a fully matured, claimable withdrawal who submits even a dust-sized new request re-locks the entire matured receipt for another full epoch.

### Finding Description

`requestWithdraw` in `IdleCreditVault` unconditionally stamps the request at the current epoch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:281-294
lastWithdrawRequest[_user] = currentEpoch;
...
withdrawsRequests[_user] += _amount;
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

and `_claimFundedWithdrawRequest` gates the claim on that single per-user timestamp:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:326-328
if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
  revert NotAllowed();
}
```

Two unfair paths mirror the report:

1. **Pending-but-old request dragged along.** User requests withdrawal of amount A in epoch N. In epoch N+1 the receipt is still pending claim; the user requests an additional dust amount. `lastWithdrawRequest[_user]` is set to N+1, so the whole `withdrawsRequests[_user]` (A + dust) cannot be claimed until epoch N+2 stops — even though the A portion had already waited its full epoch.

2. **Fully matured, funded receipt re-locked.** User requested in epoch N, the epoch ended, funds are already transferred to the contract and claimable. The user creates any new withdraw request in epoch N+1 (e.g., a new lender redeeming a small remainder). `lastWithdrawRequest` is overwritten to N+1 and `claimWithdrawRequest` reverts until epoch N+2, even though the previously-matured funds were already sourced and sitting in the vault.

The code even documents the first path in a comment ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests"), but the second path — re-locking *already-funded and claimable* receipts — is strictly worse: the funds have already been pulled from the borrower and deducted from live NAV, so the lock serves no accounting purpose.

### Impact Explanation

Temporary freezing of user funds up to one full `epochDuration` (plus buffer) per additional request, on amounts that were already claimable. For a vault with e.g. 30-day epochs, a lender who re-requests a small amount before claiming loses access to the entire matured balance for ~30 days. Like the original report, this creates a perverse incentive: users are penalized for making incremental withdrawals rather than one lump request, and a rational user is discouraged from interacting with the protocol a second time. No privileged action is needed; the lock-out is triggered purely by the victim's own legitimate `requestWithdraw`.

### Likelihood Explanation

High occurrence likelihood: any lender who partially redeems in tranches, or who requests again before remembering to claim, hits this automatically because all receipts are aggregated under a single `withdrawsRequests[_user]` / `lastWithdrawRequest[_user]` pair regardless of which epoch funded them. Funds are not stolen, so the impact is capped at temporary freezing — matching Medium severity.

### Recommendation

Track maturity per epoch rather than per user. `withdrawsRequestsByEpoch[_user][currentEpoch]` already records per-epoch amounts; the claim path should:

- Sum `withdrawsRequestsByEpoch[_user][e]` only for epochs `e < epochNumber` (matured), and only burn/transfer those, instead of gating the entire `withdrawsRequests[_user]` on the latest `lastWithdrawRequest[_user]`.
- Alternatively, auto-claim any matured receipt inside `requestWithdraw` before recording the new request, so already-funded funds are paid out immediately instead of being re-locked.

### Proof of Concept

Foundry fork PoC (scenario 2 — re-lock of a funded receipt):

```solidity
// epoch N: user deposits AA, epoch starts and stops
cdoEpoch.requestWithdraw(amountA, AATranche);      // request in epoch N
// manager: startEpoch / stopEpoch -> epochNumber becomes N+1,
// pendingWithdraws funded, receipt claimable
assertEq(cdoEpoch.claimWithdrawRequest_succeeds(), amountA); // sanity: claimable now

// same epoch N+1 buffer: user requests 1 wei more
cdoEpoch.requestWithdraw(1, AATranche);            // lastWithdrawRequest = N+1

// now the previously-claimable amountA reverts until epoch N+2 stops
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimWithdrawRequest();

// only after the *next* epoch ends can the user claim amountA + 1
// => matured funds frozen for a full extra epochDuration by a dust request
```
