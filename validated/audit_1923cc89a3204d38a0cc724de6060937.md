### Title
Loss-adjusted withdraw receipts keyed to the wrong epoch escape the haircut and can be claimed at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` tracks withdraw receipts per request epoch (`withdrawsRequestsByEpoch[user][epoch]`, `lastWithdrawRequest[user]`), but when `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]` using the *current* `epochNumber`. `epochNumber` is incremented inside `deposit()` when `isEpochRunning()` is still true (lines 607–611). If the CDO's stop-epoch flow funds pending receipts after the epoch counter has been bumped, the haircut is stored under epoch N+1 while every affected receipt was recorded under request epoch N. `lastWithdrawRequest[_user]` still points at N, `lossRecoveryPriceByEpoch[N]` is 0, and the loss-adjusted claim path silently returns zero — so the funded-claim path pays the full un-haircutted basis from a contract that only received the reduced amount.

### Finding Description
The request side keys everything to the epoch at request time: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch` (lines 282–293 of `requestWithdraw`).

The loss side keys the recovery price to `epochNumber` at *collection* time:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:411-426
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

Meanwhile `deposit()` mutates `epochNumber` mid-stopEpoch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:607-611
if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
  totEpochDeposits = 0;
  epochNumber += 1;
}
```

This is the same bug class as the Zebra fix: two pieces of consensus/state data (receipt epoch vs. recovery-price epoch) written under different keys in one logical operation, so later reads see an inconsistent pair. The claim path then resolves the wrong epoch:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789–792). If the price was stored under the post-increment epoch, it reads 0 and returns early.
- `_claimFundedWithdrawRequest` (lines 319–349) then pays `normalAmount` at par via `_transferFundedClaim`, even though `collectWithdrawFunds` only pulled `_amount < pendingBasis` underlying from the CDO and zeroed `pendingWithdraws`.
- The guard in `requestWithdraw` (lines 263–271) that is supposed to force claiming a loss-adjusted receipt before opening a new one also reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — it too sees 0, so the "must claim haircutted receipt first" invariant is broken as well.

Symmetrically, receipts requested *during* the epoch in which the price is stored (post-increment epoch N+1 requests made in the next buffer before the next stop) would be haircutted by a loss they never participated in.

### Impact Explanation
The funded-claim path pays `claimBasis` (full receipt principal + APR0 interest) while the strategy only holds `claimBasis * lossRecoveryPrice` for those receipts. The first claimants drain the strategy's underlying balance at par; later claimants' `_transferFundedClaim` either reverts or consumes funds belonging to other receipt holders / the default-recovery reserve boundary. Result: direct theft/insolvency of unclaimed withdraw receipts, scaled to `pendingBasis * (1 - lossRecoveryPrice)` — i.e., the full realized loss is socialized onto whoever claims last rather than onto the pending receipt holders it was assigned to.

### Likelihood Explanation
Requires a `stopEpochWithDuration(_lossAmount > 0)` (realized borrower loss, an honest-manager path) while `pendingWithdraws > 0` and `defaultRecoveryInitialized` — a normal operating mode, not an edge configuration. The exploit is automatic once the storage-key mismatch occurs: the first user to call `claimWithdrawRequest` via the CDO takes the excess. No privileged misbehavior needed. One caveat: this hinges on `epochNumber` being incremented before `collectWithdrawFunds` runs within the same stopEpoch transaction (I was unable to fully verify the exact call order inside `IdleCDOEpochVariant.stopEpoch` before the iteration limit; if collection happens strictly before the incrementing `deposit()`, the keys coincide and this specific instance collapses — the general risk of the dual-key epoch indexing remains).

### Recommendation
Pass the claim epoch explicitly instead of reading mutable global `epochNumber` at collection time: have `collectWithdrawFunds` (and `prepareStopEpochWithApr0`'s `apr0RateByEpoch` write at line 537, which shares the same hazard) accept the epoch the receipts were booked under, or snapshot `epochNumber` before any incrementing `deposit()` in the stopEpoch flow and use that single snapshot for all per-epoch writes in the same operation. Add an invariant test that `lossRecoveryPriceByEpoch[lastWithdrawRequest[u]] != 0` for every user whose receipts were pending when a loss was realized.
