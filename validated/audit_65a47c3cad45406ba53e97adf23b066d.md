### Title
Missing message-uniqueness/replay protection for legacy WebAPI trigger messages allows re-triggering of workflow execution - ([File: core/services/gateway/handlers/capabilities/handler.go], [File: core/capabilities/webapi/trigger/trigger.go])

### Summary
`gateway.ProcessRequest` and the legacy `capabilities` handler's `HandleLegacyUserMessage` never enforce message-ID or nonce uniqueness beyond a transient in-memory `savedCallbacks` map used only for response correlation. The only "freshness" check is a *stale-message lower bound* (`MaxAllowedMessageAgeSec`), which does not prevent replay of an identical, previously-valid signed message within that window. Downstream, the node-side `triggerConnectorHandler.processTrigger` also performs no dedup across separate invocations, so a captured message can be resent to re-emit a workflow trigger event.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) decodes the request, calls `msg.Validate()` (signature/shape validation only — no nonce or one-time-use check), and dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)`.

For the `webapicap` legacy trigger path, `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) performs:
1. JSON decode of `TriggerRequestPayload`.
2. A **staleness-only** check: `if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` — this rejects messages *older* than the configured window but places no restriction on a message being seen more than once inside that window.
3. Stores the callback keyed only by `msg.Body.MessageId` in `h.savedCallbacks` (an *unconditional overwrite*, not a "reject if exists" check), then forwards the message to all DON members via `don.SendToNode`.

There is no persistent or per-sender nonce/message-ID replay cache comparable to the `jwtReplayCache` used elsewhere in the codebase (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:29-34,399-412`) for the JWT-based v2 flow. The legacy signed-`Message` flow has no equivalent protection.

On the node side, `triggerConnectorHandler.HandleGatewayMessage` → `processTrigger` (`core/capabilities/webapi/trigger/trigger.go:80-149,151-194`) re-validates sender/topic/rate-limit but computes `TriggerEventID := body.Sender + payload.TriggerEventId` and emits a fresh `capabilities.TriggerResponse` onto the registered trigger channel **every time it is called**, without checking whether that `TriggerEventID` (or `MessageId`) has already been processed. The "can only be triggered once" comment at line 136 refers only to per-topic fan-out within a single invocation, not across separate calls over time.

`RequestCache.NewRequest` (`core/services/gateway/handlers/common/requestcache.go:50-76`) does reject *concurrent* duplicate `(sender, MessageId)` keys, but this cache is not used by the legacy capabilities/webapi-trigger handler at all, and even where it is used, its protection is scoped to concurrency, not time-separated replay — entries are deleted on completion/timeout (`c.deleteAndSendOnce`), after which the identical key becomes reusable.

Net effect: an attacker who has captured one previously valid signed legacy `Message` (e.g., from logs, as illustrated by `TestGateway_LegacyRequest_HandlerResponse`, `core/services/gateway/gateway_test.go:498-519`, which shows the exact wire format) can resubmit the identical raw bytes to the gateway HTTP endpoint multiple times as long as `payload.Timestamp` is still within `MaxAllowedMessageAgeSec`. Each resubmission passes signature validation (it's the same valid signature over the same bytes), passes the staleness check, and is forwarded to the DON, which re-emits the trigger event and re-invokes `processTrigger`/workflow execution — all attributable to the original signer, without their consent or a fresh signature.

### Impact Explanation
This allows unauthorized re-execution of a victim's authorized action (re-triggering a workflow execution, or repeatedly consuming a rate-limited/paid trigger budget) using only a captured, previously-valid message — no private key required. This maps to Chainlink's "unauthorized job run" impact class: a legacy WebAPI trigger message intended to fire a workflow exactly once can be fired multiple times by a passive attacker who observed the wire bytes, within the freshness window (`MaxAllowedMessageAgeSec`, developer-configured, potentially minutes).

### Likelihood Explanation
- Requires no credentials beyond possession of one previously-transmitted, valid signed `Message` (e.g., sniffed from an insecure transport, logged in error responses, or observed via a compromised intermediary/proxy) — no private key needed to replay.
- Requires only replaying the exact same raw bytes to the same, unauthenticated gateway HTTP endpoint (`auth` parameter is not tied to per-message uniqueness).
- Bounded by `MaxAllowedMessageAgeSec`, but within that window, replay is unlimited (subject only to the sender's rate limiter in `processTrigger`, which is a quota, not a uniqueness check, and can itself be exhausted or is calibrated to allow normal legitimate traffic volume).
- Repeatable: each replay is processed identically since there is no persisted record that the specific `MessageId`/`TriggerEventId` was already consumed.

### Recommendation
Add explicit replay protection to the legacy trigger path:
- Maintain a persistent (not just per-callback) seen-message-ID/TriggerEventId cache per sender in `handler.HandleLegacyUserMessage` and/or `triggerConnectorHandler.processTrigger`, similar to the existing `jwtReplayCache` pattern, and reject any message whose `(Sender, MessageId)` or `(Sender, TriggerEventId)` has already been processed, independent of whether the original request is still "in flight."
- Ensure this cache's retention window is at least as long as `MaxAllowedMessageAgeSec`, so replay cannot succeed at any point the message is still considered "fresh."
- Consider deriving idempotency directly from `workflowExecutionID` (already computed) and refusing to re-emit a `TriggerResponse` for an execution ID already dispatched within the freshness window.

### Proof of Concept
Go handler-level integration test plan (extending `core/services/gateway/gateway_test.go` patterns):
1. Build a signed legacy trigger `Message` via `newSignedLegacyRequest`/`triggerRequest` helpers with a fixed `Timestamp` and `TriggerEventId`.
2. Submit it once through `gw.ProcessRequest` and assert `200`/success and that the mock handler's `don.SendToNode` (or `trigger.ch`) was invoked once with the trigger event.
3. Wait past the point where any short-lived cache entry (savedCallback/RequestCache) is deleted (e.g., after callback `Wait` completes), but still within `MaxAllowedMessageAgeSec`.
4. Resubmit the *exact same raw bytes* through `gw.ProcessRequest` again.
5. Assert (current/expected-vulnerable behavior): the second submission is again accepted with `200`, and `don.SendToNode`/`trigger.ch` receives a second identical trigger event with the same `MessageId`/`TriggerEventId` — demonstrating no nonce/uniqueness rejection occurs, only the (currently absent) intended fix should return a distinct "duplicate/replay" error instead of processing it as fresh.
