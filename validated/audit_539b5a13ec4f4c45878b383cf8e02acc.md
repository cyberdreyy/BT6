### Title
Unsynchronized read of `h.authorizedKeys` in `Authorize` races with `syncMetadata`'s writes, causing a Go fatal concurrent-map crash (DoS) - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` at line 92 without acquiring `h.mu.RLock()`, while `syncMetadata` (invoked periodically by a background ticker) reassigns the entire `h.authorizedKeys` map under `h.mu.Lock()` at line 178. Because Go maps are not safe for concurrent read/write, any external caller sending ordinary signed trigger requests that reach `Authorize` while a metadata sync tick is in progress can trigger a fatal, unrecoverable runtime error (`fatal error: concurrent map read and map write`) that terminates the gateway process, or in non-detected interleavings can observe an inconsistent map state.

### Finding Description
`WorkflowMetadataHandler` embeds a `sync.RWMutex` (`h.mu`) intended to protect `authorizedKeys`, `workflowRefToID`, `workflowIDToRef`, and `workflowShards`. All other accessors correctly take the lock: `WorkflowShards` [1](#0-0) , `GetWorkflowID` [2](#0-1) , and `GetWorkflowReference` [3](#0-2)  all take `h.mu.RLock()`.

However, `Authorize` reads the map directly with no lock at all: [4](#0-3) 

Meanwhile `syncMetadata` builds a brand-new map locally and then swaps it into `h.authorizedKeys` while holding the write lock: [5](#0-4) 

`syncMetadata` is scheduled to run on a periodic ticker started in `Start`, at interval `MetadataAggregationIntervalMs`: [6](#0-5) 

`Authorize` is invoked from the HTTP trigger request path (`http_trigger_handler.go`) for every incoming signed trigger request — a path directly reachable by any external client holding a workflow-signed JWT, i.e., an unprivileged/ordinary caller of the trigger capability, not an operator or admin. Because Go's runtime map implementation is not safe for concurrent use, a concurrent unsynchronized read (`Authorize`) racing with a write (map assignment `h.authorizedKeys = authorizedKeys` in `syncMetadata`) can trigger the Go runtime's built-in concurrent map access detector, which raises a **fatal, unrecoverable error** (not a normal panic — `recover()` cannot catch it), crashing the entire process. This is a classic Go concurrency bug and is deterministically detectable via `go test -race`.

None of the surrounding authorization/JWT verification logic in `Authorize` (JWT signature check, replay-cache check) mitigates this — the race is purely on the internal map, independent of whether the JWT is otherwise valid or malicious. An attacker only needs to be able to send trigger requests at a rate/timing likely to overlap with a periodic `syncMetadata` tick, which happens on a fixed configured interval and is thus predictable/exploitable by simply sending requests continuously.

### Impact Explanation
This matches the "Denial of Service" impact class: sending ordinary trigger requests (no special privilege required beyond being able to reach the gateway's trigger endpoint) can crash the gateway process due to a Go fatal concurrent-map-access error, taking down node/gateway availability for all workflows and tenants served by that gateway instance. Because the fatal error is unrecoverable panic, it cannot be caught by any deferred recover in the request handler and will crash the whole process, not just the request goroutine.

### Likelihood Explanation
- Preconditions: only requires unauthenticated/ordinary ability to send trigger requests to the gateway (a JWT-signed request is required by `Authorize`'s JWT verification, but this is the standard workflow trigger authentication a normal caller would already have or can request/craft for a registered workflow — no elevated privilege is needed beyond standard trigger-capability access).
- The race window opens on every `MetadataAggregationIntervalMs` tick (periodic, deterministic), so an attacker sending high-frequency requests continuously has a high probability of overlapping with a sync tick.
- Repeatable: this is a genuine, reproducible Go data race (confirmed by static code reading — `Authorize` has no `h.mu` acquisition anywhere), and running the process with the race detector or under sufficient load in production will surface it.

### Recommendation
Acquire `h.mu.RLock()`/`defer h.mu.RUnlock()` in `Authorize` before reading `h.authorizedKeys[workflowID]`, consistent with the locking pattern already used in `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`.

### Proof of Concept
```go
func TestWorkflowMetadataHandler_AuthorizeSyncRace(t *testing.T) {
    h := newTestWorkflowMetadataHandler(t) // construct via NewWorkflowMetadataHandler with test shards/config
    workflowID := "test-workflow-id-32-bytes-hex..."

    stop := make(chan struct{})
    var wg sync.WaitGroup

    // Goroutine 1: repeatedly call syncMetadata (simulating the periodic ticker)
    wg.Add(1)
    go func() {
        defer wg.Done()
        for {
            select {
            case <-stop:
                return
            default:
                h.syncMetadata(context.Background())
            }
        }
    }()

    // Goroutine 2: repeatedly call Authorize (simulating attacker trigger requests)
    wg.Add(1)
    go func() {
        defer wg.Done()
        for i := 0; i < 10000; i++ {
            token, req := buildSignedTriggerRequestJWT(t, workflowID) // valid JWT per iteration to avoid replay-cache
            _, _ = h.Authorize(workflowID, token, req)
        }
    }()

    time.Sleep(200 * time.Millisecond)
    close(stop)
    wg.Wait()
}
```
Run with `go test -race -run TestWorkflowMetadataHandler_AuthorizeSyncRace ./core/services/gateway/handlers/capabilities/v2/...`. Expected: the race detector reports `DATA RACE` on `h.authorizedKeys` between the read at `Authorize` (line 92) and the write at `syncMetadata` (line 178); under sufficient load without `-race`, the process can also fatally crash with `fatal error: concurrent map read and map write`. After applying the fix (adding `h.mu.RLock()`/`RUnlock()` around the read in `Authorize`), the test should pass with no race reported.

func (h *WorkflowMetadataHandler) GetWorkflowID(workflowOwner, workflowName, workflowTag string) (string, bool) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	workflowRef := workflowReference{
		workflowOwner: workflowOwner,
		workflowName:  workflowName,
		workflowTag:   workflowTag,
	}
	workflowID, exists := h.workflowRefToID[workflowRef]
	if !exists {
		return "", false
	}
	return workflowID, true
}
