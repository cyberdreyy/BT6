### Title
Unbounded decay of `DynamicPacketToProcessThreshold::max_packets` can converge to a floor that permanently drops repair-response packets - ([File: core/src/repair/packet_threshold.rs])

### Summary
`DynamicPacketToProcessThreshold` mirrors the reported bug class: a value that changes monotonically over time/load with no floor check before being used as a fund/availability gate. Here the "gate" is packet ingestion for repair responses (ancestor-hashes / block-id repair), not funds, but the mechanism — repeated multiplicative decrease with no lower bound enforced before use in a pass/fail comparison — is structurally the same pattern as the `newRatio` decay in the reported Auction bug.

### Finding Description
`PacketThresholdUpdate::calculate` decreases `max_packets` by a fixed 90% factor every time `update()` observes `compute_time > TIME_THRESHOLD` while `total_packets >= self.max_packets`: [1](#0-0) 

`update()` applies this repeatedly with no minimum bound: [2](#0-1) 

`should_drop()` then gates whether incoming packets are processed or dropped, purely based on `total >= self.max_packets`: [3](#0-2) 

Because `calculate` uses `usize` integer division (`current * 90 / 100`), repeated decreases asymptotically approach 0 and, once `max_packets` reaches a small value (e.g., 1), integer division can pin it there or drive it to 0. Once `max_packets == 0`, `should_drop(total)` returns `true` for any `total >= 0`, i.e., **all** subsequent packets are dropped, since `total_packets >= self.max_packets` will also perpetually be true (0 >= 0), keeping the threshold locked in the decrease branch forever with no recovery path back to the `Increase` branch (which requires `total_packets >= self.max_packets`, trivially satisfied at 0, but `compute_time <= TIME_THRESHOLD` is needed to increase — so under sustained load with `compute_time` fluctuating around the threshold, the value can get stuck near 0).

This differs from the report's fund-theft impact, but is the closest reachable analog within the allowed categories (TPU/repair ingest limits) — an unbounded, one-directional decaying threshold used directly as a binary gate with no sanity floor, exactly the root cause pattern flagged in the external report (`newRatio` with no `> ibRatio` floor check before being used to gate withdrawals).

### Impact Explanation
If exploitable, this would result in `DynamicPacketToProcessThreshold` for a repair path (ancestor-hashes service, block-id repair service) collapsing toward zero and never recovering, causing the validator to drop legitimate repair-response packets indefinitely — an ingest-starvation condition for the repair subsystem. This is a liveness/availability degradation for repair, not a fund-loss or consensus-divergence bug.

### Likelihood Explanation
Low-to-moderate. It requires sustained high packet volume combined with `compute_time` staying above `TIME_THRESHOLD` (1 second) across many consecutive `update()` calls, driving `max_packets` down via repeated 90% multiplicative shrink with integer division. Whether this is practically reachable depends on real-world compute times for the repair packet-processing batches in `ancestor_hashes_service.rs` / `block_id_repair_service.rs`, which I could not fully trace within the remaining budget (usages confirmed present but the exact call sites and typical `compute_time` values were not fully inspected).

### Recommendation
Add a floor (e.g., a `MIN_MAX_PACKETS` constant) to `PacketThresholdUpdate::Decrease::calculate` so `max_packets` cannot fall below a safe minimum, analogous to the reported mitigation of requiring `newRatio > basket.ibRatio()` before it is used as a withdrawal gate. E.g.:
```rust
PacketThresholdUpdate::Decrease => current
    .saturating_mul(Self::PERCENTAGE)
    .saturating_div(100)
    .max(MIN_MAX_PACKETS),
```

impl PacketThresholdUpdate {
    const PERCENTAGE: usize = 90;

    fn calculate(&self, current: usize) -> usize {
        match *self {
            PacketThresholdUpdate::Increase => {
                current.saturating_mul(100).saturating_div(Self::PERCENTAGE)
            }
            PacketThresholdUpdate::Decrease => {
                current.saturating_mul(Self::PERCENTAGE).saturating_div(100)
            }
        }
    }

    pub fn update(&mut self, total_packets: usize, compute_time: Duration) {
        if total_packets >= self.max_packets {
            let threshold_update = if compute_time > Self::TIME_THRESHOLD {
                PacketThresholdUpdate::Decrease
            } else {
                PacketThresholdUpdate::Increase
            };
            self.max_packets = threshold_update.calculate(self.max_packets);
        }
    }
