### Title
Stale Confirmations from Deleted Multisig Members Allow Request Execution Below Confirmation Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges confirmations for requests that were *created by* the removed member, but never scans the `confirmations` map to strip that member's confirmation entries from requests created by *other* members. Because `confirm()` counts entries in that stale set toward `num_confirmations`, a request can later execute using a confirmation from an account that is no longer a member — i.e., the multisig executes a request with fewer live, currently-authorized confirmations than the configured threshold.

### Finding Description
The bug-class from the external report is: a value recorded at time T1 (shares owed) is compared against a value recomputed/valid at time T2 (current price) without reconciling the two, producing an incorrect pass/fail on a critical invariant check. The structural analog here is the equality that should hold for every executed request:

`confirmations(request_id) == {confirmations given by accounts that are still live members}`

`delete_member` breaks this invariant: [1](#0-0) 

It filters and removes only the requests *originated by* the deleted member (`r.member == member`), and removes that member from `num_requests_pk` and `self.members`. It never touches `self.confirmations` entries belonging to requests created by *other* members that the now-deleted member had previously confirmed.

`confirm()` then blindly counts whatever is stored in the `confirmations` set for the request, regardless of whether those entries still correspond to live members: [2](#0-1) 

So a stale confirmation from a removed member remains permanently counted toward `num_confirmations` for any request it was attached to (as long as that request was not created by the removed member), even though `current_member()` would reject that same account from confirming *new* requests: [3](#0-2) 

### Impact Explanation
This directly matches the Critical-impact category "a multisig request executed below threshold." A `Transfer`, `AddKey`, `FunctionCall`, or any other `MultiSigRequestAction` (including moving NEAR out of the contract) can be executed with strictly fewer *live* confirming members than `num_confirmations` requires, because a stale confirmation from a deleted member is silently counted. This defeats the k-of-n security guarantee the multisig is supposed to provide and can lead to unauthorized movement of NEAR held by the contract.

### Likelihood Explanation
Member rotation (adding/removing signers, e.g., when an employee leaves or a key is rotated) is a normal, expected multisig lifecycle operation, and it is very plausible for a member to have already confirmed one or more pending requests before being removed. No special privilege beyond the normal multisig workflow is needed to trigger the flaw — it can occur as an unintended side effect of routine member removal, or be deliberately engineered by a member who confirms sensitive requests before being rotated out, leaving the stale confirmation in place to help push a malicious request over threshold later.

### Recommendation
When executing `DeleteMember`, iterate over all requests in `self.confirmations` (not just the ones the removed member created) and remove the deleted member's confirmation entry from each. Alternatively, validate at `confirm()`/execution time that every entry in the confirmations set still corresponds to a current member of `self.members`, discounting stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. Member `B` calls `add_request` to create request `R1` (e.g., `Transfer` of contract funds to an attacker-controlled account). `R1.member = B`.
3. Member `A` calls `confirm(R1)`. `confirmations(R1) = {A}` (1 < 3, not yet executed).
4. Through a separate, legitimately-confirmed `DeleteMember { member: A }` request, `A` is removed: `self.members` no longer contains `A`; `delete_member` only removes requests where `r.member == A`, so `R1` (created by `B`) and its confirmation set `{A}` are left untouched — see `multisig2/src/lib.rs:361-371`.
5. Member `C` calls `confirm(R1)`: `confirmations.len() (1) + 1 = 2 < 3` → not executed, inserted. `confirmations(R1) = {A, C}`.
6. Member `D` calls `confirm(R1)`: `confirmations.len() (2) + 1 = 3 >= 3` → `R1` executes via `execute_request`.
7. Result: `R1` executed with confirmations from only two *live* members (`C`, `D`); the third counted confirmation belongs to `A`, who was removed from the multisig in step 4. The transfer request executed below the configured 3-of-4 threshold. [2](#0-1) [4](#0-3)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
