### Title
Unintended silent reset of the "other" commission collector during V3→V4 vote-account auto-conversion in `update_commission_collector` - (File: programs/vote/src/vote_state/mod.rs)

### Summary
`update_commission_collector` (SIMD-0232), when invoked against a vote account still stored in the legacy `VoteStateVersions::V3` format, triggers an implicit V3→V4 conversion. That conversion writes *both* `inflation_rewards_collector` and `block_revenue_collector` fields, but only one of them is the value the caller intended to change — the other is silently overwritten with a hard-coded default (`vote_pubkey` for inflation rewards, `node_pubkey` for block revenue) rather than preserving whatever the authority previously configured. This mirrors the `SecondSwap_VestingManager.setSellable` bug class: a single authorized call meant to change one setting silently resets an unrelated setting to a "default" value.

### Finding Description
`update_commission_collector` is reachable by any transaction signed by the vote account's withdraw authority. When acting on a V3 vote account, the underlying account state must first be converted to V4 (since `inflation_rewards_collector` / `block_revenue_collector` only exist in V4). The conversion path is documented and reproduced by the codebase's own regression test: [1](#0-0) 

The test explicitly asserts the vulnerable behavior: after calling `update_commission_collector` for `CommissionKind::InflationRewards` only, the *unrelated* `BlockRevenue` collector field is overwritten to a "V4-conversion default" (`node_pubkey`) instead of being left as previously configured (or defaulting to a value the withdraw authority actually chose). The comment in the test itself states:

"V3 -> V4 auto-conversion side-effect: updating one collector against a V3-serialized account causes the 'other' collector to be written as its V4 default ... per `try_convert_to_vote_state_v4`."

This is functionally identical to the reported bug class: an authorized, narrowly-scoped update instruction (`update_commission_collector`, analogous to `setSellable`) has a side effect on an unrelated field (`block_revenue_collector`/`inflation_rewards_collector`, analogous to `maxSellPercent`) because the value is derived from a "not yet initialized in V4" default rather than being preserved from prior state.

### Impact Explanation
If a vote account operator had never explicitly set a V4 commission collector (because the account was created/migrated as V3) and later calls `update_commission_collector` to update just one collector kind, the other collector is silently forced to a default recipient (`vote_pubkey` or `node_pubkey`) that the withdraw authority did not choose. Since these collector fields determine where inflation rewards and block-revenue-sharing lamports are routed, this can result in reward lamports being redirected to an unintended account. This falls into the "stake or reward corruption" impact category — the vote account's future rewards distribution silently diverges from the authority's actual configuration/intent, without any error or warning being surfaced by the instruction.

### Likelihood Explanation
Likelihood depends on the prevalence of V3-format vote accounts persisting after SIMD-0185/SIMD-0232 rollout and on withdraw authorities calling `update_commission_collector` before/without ever having explicitly configured both collector kinds under V4. Since V3→V4 auto-conversion happens transparently and is not something the caller is required to be aware of, an authority naively calling the instruction to update just one collector could unknowingly reset the other. This is a realistic accidental-trigger scenario (same likelihood profile as the original report, which is triggered by ordinary/expected admin operations, not by an attacker crafting adversarial input).

### Recommendation
When converting a V3 vote account to V4 as a side effect of `update_commission_collector` (or any V4-only instruction), the conversion routine `try_convert_to_vote_state_v4` should preserve any commission-collector configuration the caller is not currently modifying by deriving it from explicit, authority-approved defaults (or requiring the instruction to specify both collectors on first V4 initialization), rather than silently writing a hard-coded default for the untouched field. Concretely, introduce an "initialized" marker for V4 collector fields (analogous to the recommended `initiated` flag in the referenced report) so that only the fields the transaction explicitly sets are updated, and any prior/expected values are not clobbered by conversion-time defaults.

### Proof of Concept
The existing unit test in the repository already demonstrates the issue end-to-end: [1](#0-0) 
1. Build a V3-serialized vote account (`get_max_sized_vote_state_v3`), padded to V4 size.
2. Withdraw authority signs and submits `UpdateCommissionCollector` for `CommissionKind::InflationRewards` only.
3. Observe that `inflation_rewards_collector` correctly updates to `new_collector`, but `block_revenue_collector` — never touched by the instruction — is overwritten to `v3_node_pubkey` (the V4-conversion default), not preserved from any prior configuration.

        // V3 -> V4 auto-conversion side-effect: updating one collector against a
        // V3-serialized account causes the "other" collector to be written as
        // its V4 default (inflation_rewards_collector = vote_pubkey,
        // block_revenue_collector = node_pubkey), per try_convert_to_vote_state_v4.
        {
            let v3 = get_max_sized_vote_state_v3();
            let v3_node_pubkey = v3.node_pubkey;
            let v3_withdrawer = v3.authorized_withdrawer;
            let v3_vote_pubkey = solana_pubkey::new_rand();

            let v4_size = VoteStateV4::size_of();
            let mut account_data = vec![0u8; v4_size];
            bincode::serialize_into(&mut account_data[..], &VoteStateVersions::V3(Box::new(v3)))
                .unwrap();
            let mut v3_vote_account =
                AccountSharedData::new(rent.minimum_balance(v4_size), v4_size, &id());
            v3_vote_account.set_data_from_slice(&account_data);

            let v3_signers: HashSet<Pubkey> = vec![v3_withdrawer].into_iter().collect();

            let transaction_context = new_transaction_context(
                vec![
                    (id(), processor_account.clone()),
                    (v3_vote_pubkey, v3_vote_account),
                    (new_collector, collector_account.clone()),
                ],
                vec![
                    InstructionAccount::new(1, false, true),
                    InstructionAccount::new(2, false, true),
                ],
                &rent,
            );
            let instruction_context = transaction_context.get_next_instruction_context().unwrap();
            let mut borrowed_vote_account = instruction_context
                .try_borrow_instruction_account(0)
                .unwrap();

            update_commission_collector(
                &mut borrowed_vote_account,
                target_version,
                NewCommissionCollector::NewAccount(
                    instruction_context
                        .try_borrow_instruction_account(1)
                        .unwrap(),
                ),
                CommissionKind::InflationRewards,
                &v3_signers,
                &rent,
            )
            .unwrap();

            // The updated field reflects the caller's new collector.
            assert_eq!(
                get_commission_collector(&borrowed_vote_account, CommissionKind::InflationRewards),
                new_collector,
            );
            // The *other* field was reset to its V4-conversion default
            // (block_revenue_collector = node_pubkey from the V3 source).
            assert_eq!(
                get_commission_collector(&borrowed_vote_account, CommissionKind::BlockRevenue),
                v3_node_pubkey,
            );
        }
