### Title
Unchecked subtraction in `getSupply` RPC handler can underflow and crash or misreport circulating supply - ([File: rpc/src/rpc.rs])

### Summary
The `getSupply` RPC handler computes `circulating: total_supply - non_circulating_supply.lamports` using a plain, un-checked `u64` subtraction [1](#0-0) . This assumes the invariant `non_circulating_supply.lamports <= total_supply` always holds, but the two values are computed from two different, non-atomic reads of a potentially mutable (working) bank, so the invariant can be violated, leading to an underflow. This mirrors the reported bug class where `freezeBuckets.getLockedAmount()` could exceed the pool's live balance because the "locked" and "available" quantities were computed from state that changed between reads, and the resulting subtraction was not defensively guarded.

### Finding Description
`get_supply` in `rpc/src/rpc.rs` does:
```rust
let bank = self.bank(config.commitment);
let non_circulating_supply = self.calculate_non_circulating_supply(&bank).await...;
let total_supply = bank.capitalization();
...
circulating: total_supply - non_circulating_supply.lamports,
``` [2](#0-1) 

`total_supply` is read via `bank.capitalization()` (an `AtomicU64` snapshot) while `non_circulating_supply` is produced by `calculate_non_circulating_supply`, which is dispatched to a blocking task and performs a scan over stake-program accounts plus a fixed list of known non-circulating pubkeys, summing `bank.get_balance(pubkey)` for each [3](#0-2) . These two quantities are captured via separate, non-atomic operations against the bank.

Notably, the sibling REST endpoint that performs the same computation (`/v0/circulating-supply`) explicitly guards against this by using `saturating_sub`:
```rust
Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
``` [4](#0-3) 

The JSON-RPC `getSupply` path, however, uses the raw `-` operator, which is inconsistent with the defensive pattern used elsewhere in the same codebase for the identical computation. If `config.commitment` resolves to a non-frozen "working" bank (e.g. `processed`/`confirmed` commitment) that continues executing transactions concurrently with the account scan, the two reads (`capitalization()` at one point in time, account balances scanned slightly later/earlier) can become inconsistent enough that `non_circulating_supply.lamports > total_supply`, causing the subtraction to underflow.

### Impact Explanation
- If the crate is compiled with overflow checks enabled, the underflow triggers a Rust arithmetic-overflow panic inside the RPC-serving thread, aborting the connection thread; depending on how the JSON-RPC server pool handles panics, this can escalate into unhandled thread panics from a single unprivileged `getSupply` call.
- If overflow checks are disabled, the subtraction silently wraps to a value near `u64::MAX`, and the RPC returns a grossly incorrect `circulating` supply figure to the caller — this is a wrong-data-returned condition from a single, unprivileged, unauthenticated RPC call (`getSupply` requires no special privileges).

Either outcome satisfies the "concrete... crash... or wrong data returned" impact bar from a single low-rate call, since `getSupply` can be invoked freely and repeatedly by any JSON-RPC client.

### Likelihood Explanation
The window for the race is real whenever a client queries `getSupply` against a non-frozen bank (`processed`/`confirmed` commitment, which are common defaults), because the bank keeps mutating (processing transactions, rewards, rent) between the `capitalization()` read and the completion of the account scan performed in `calculate_non_circulating_supply`. The bug is not certain to trigger on every call — it requires the transient race to shift the sum in the "wrong" direction by an amount exceeding the small buffer between `total_supply` and `non_circulating_supply.lamports` — but it is a plain logic bug (missing use of `saturating_sub`, unlike the equivalent REST handler) rather than a purely theoretical one, and is reachable by any unauthenticated caller with a single, low-rate RPC call.

### Recommendation
Change the subtraction in `get_supply` (`rpc/src/rpc.rs`) to use `total_supply.saturating_sub(non_circulating_supply.lamports)`, matching the existing defensive pattern already used in `calculate_circulating_supply_async` (`rpc/src/rpc_service.rs`), to eliminate the underflow/panic and the wrap-around misreporting.

### Proof of Concept
1. Start a validator/RPC node and repeatedly issue `getSupply` with `commitment: "processed"` (or `confirmed`) against a bank that is actively processing transactions that move lamports into/out of accounts tracked as non-circulating (e.g., stake accounts with an active lockup, or accounts in the hardcoded `non_circulating_accounts()` list) [5](#0-4) .
2. Because `bank.capitalization()` is read once and the account-balance scan in `calculate_non_circulating_supply` runs afterward on a separate blocking thread, a transaction that increases a non-circulating account's balance (e.g., a reward or transfer) occurring between the two reads can cause `non_circulating_supply.lamports` to be greater than the previously captured `total_supply`.
3. The subtraction `total_supply - non_circulating_supply.lamports` in `get_supply` then either panics (overflow-checked build) or wraps to a near-`u64::MAX` value returned as `circulating` in the JSON-RPC response — unlike the REST `/v0/circulating-supply` handler which is immune due to its use of `saturating_sub`. pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
    let total_supply = bank.capitalization();
    let bank = Arc::clone(bank);
    let non_circulating_supply =
        tokio::task::spawn_blocking(move || calculate_non_circulating_supply(&bank))
            .await
            .expect("Failed to spawn blocking task")
            .map_err(|e| SupplyCalcError::Scan(e.to_string()))?;

    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
}
