### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
`execute_request`'s `DeleteKey`/`DeleteMember` handling only removes requests whose *original signer* matches the key/member being deleted, and only clears `num_requests_pk`. It never scans the `confirmations` map for other, still-open requests that the removed key/member had already confirmed. Those confirmations remain valid and are counted the next time `confirm` totals up votes, so a request can execute with fewer live signers than `num_confirmations` requires.

### Finding Description
In `execute_request`, the `DeleteKey` action (multisig) / `DeleteMember` action (multisig2) removes only requests that key *originated*: [1](#0-0) 

`delete_member` in multisig2 does the analogous filtering, again only by request ownership, and only removes `num_requests_pk` and `members`: [2](#0-1) 

Neither routine walks `self.confirmations` to strip out entries contributed by the deleted key/member on *other* pending requests that someone else originated. `confirm` simply counts set membership size against `num_confirmations` without re-validating that every confirming signer/member is still current: [3](#0-2) 

This mirrors the Unlock `MixinTransfer` root cause exactly: a per-entity authorization/role field (`keyManager`, here "is this pk/member a live confirmation") is supposed to be invalidated when the underlying binding changes (`transferFrom`'s ownership change → the transfer path that omits the reset; here, key/member removal → the confirmation-count path that omits the reset), but one code path clears it and another does not, so the stale grant survives and can be replayed.

### Impact Explanation
This breaks the equality that the confirmation count must equal live-member approvals: `count(confirmations[request_id]) == count(live signers who approved)`. After removal, a confirmation from an ex-member/ex-key still counts, so `count(confirmations[request_id]) > count(live members who approved)`. A request can therefore reach `num_confirmations` and execute (transfer funds, deploy code, add/delete keys, change `num_confirmations`) with fewer currently-authorized approvers than the contract's own threshold guarantees. This is a "multisig request executed below threshold" event, which the rules classify as Critical impact — the multisig's core security guarantee (N confirmations from current members) is silently weakened.

### Likelihood Explanation
Requires only the ordinary lifecycle of a multisig: a member/key confirms a request, is later removed (e.g., employee offboarding, key rotation, compromised-key removal) via `DeleteKey`/`DeleteMember` while other requests they confirmed are still pending, and the remaining threshold is met with the assistance of the stale confirmation. No exotic reentrancy or timing race is needed; it is a straightforward missing-cleanup path that triggers on the intended, normal `DeleteKey`/`DeleteMember` flow.

### Recommendation
When executing `DeleteKey` (multisig) or `DeleteMember` (multisig2), iterate over **all** entries in `self.requests`/`self.confirmations` and remove the deleted key/member's confirmation from every pending request's confirmation set (not just requests it originated), re-checking whether removal drops any request below its already-recorded confirmation progress. Alternatively, validate at `confirm`-time (and before scheduling execution) that every public key/member in a request's confirmation set is still present in the live member/access-key set, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy a multisig with `num_confirmations = 3` and members `A, B, C, D`.
2. Member `X` (not yet removed) creates Request R1 (e.g., transfer funds) and confirms it → `confirmations[R1] = {X}`.
3. Members agree to remove `X` (e.g., key compromise) and create/confirm a separate self-request using `DeleteKey { public_key: X }`; this only removes requests where `signer_pk == X`, so R1 (created/confirmed by `X` but not filtered because filtering matches signer of *that* request, i.e., R1's own `signer_pk` is `X`, so in this exact case it would be removed — to make R1 survive, have `X` merely *confirm* a request originated by `A`) — i.e., `A` creates Request R1, `X` confirms it (`confirmations[R1] = {A, X}`), then the group executes `DeleteKey{X}`. Because the filter only matches `r.signer_pk == pk` and R1's `signer_pk` is `A`, R1 is **not** removed and `confirmations[R1]` still contains `X`.
4. `X`'s access key is now deleted from the account, yet `confirmations[R1]` still has 2 entries (`A`, `X`).
5. Member `B` confirms R1 → `confirmations[R1]` reaches size 3 (`A, X, B`) and `execute_request` fires, even though only `A` and `B` are live/authorized signers — one confirmation below the intended live-member threshold. [4](#0-3)

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
