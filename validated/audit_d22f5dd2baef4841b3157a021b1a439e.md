### Title
`pending_delegator_rewards` is never decremented after block-reward distribution, causing unbounded reward re-distribution and unfair dilution of stakers (SIMD-0123) - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The SIMD-0123 "block revenue sharing" mechanism lets any signer permissionlessly deposit lamports into a vote account via `DepositDelegatorRewards`, which increments the vote account's `pending_delegator_rewards` counter. Every epoch, this pooled amount is distributed to the vote account's current delegators proportional to `stake / total_active_stake`, exactly the same "feesOwed × individual / total" pattern that caused H‑1 in the referenced report. Unlike a correctly-designed fee pool, `pending_delegator_rewards` is only ever incremented (`add_pending_delegator_rewards`) and read (`pending_delegator_rewards()`); no code path decrements it after the pool is paid out.

### Finding Description
`deposit_delegator_rewards` (permissionless, callable by any transaction signer) transfers lamports into the vote account and increments `vote_state.pending_delegator_rewards` via `add_pending_delegator_rewards`: [1](#0-0) [2](#0-1) 

Each epoch, `calculate_block_reward` reads the vote account's current `pending_delegator_rewards` and computes each stake delegation's share as `pending_delegator_rewards * stake / total_active_stake` — the exact analog of the Sherlock H-1 `feesOwed * individual_lent / total_lent` calculation: [3](#0-2) 

This value is fed into `store_stake_accounts_in_partition`, which credits stake accounts with `partitioned_stake_reward.block_reward` via `checked_add_lamports`: [4](#0-3) 

I searched the entire vote program and reward-distribution code paths (`vote_state/mod.rs`, `vote_state/handler.rs`, `vote_processor.rs`, `partitioned_epoch_rewards/calculation.rs`, `partitioned_epoch_rewards/distribution.rs`) for any code that decrements `pending_delegator_rewards` after it has been paid out as `block_reward`, and found none — the only mutator of the field is `add_pending_delegator_rewards` (increment only). Correspondingly, `distribute_epoch_rewards_in_partition` only adjusts capitalization for burned block rewards, not for distributed ones, implying the design assumes distributed block rewards are drawn down from an already-capitalized pool rather than freshly minted: [5](#0-4) 

Because `pending_delegator_rewards` is never reduced and the vote account's own lamport balance is never debited by the distributed portion, the same "fee pool" balance:
1. Is redistributed to stakers again in every subsequent epoch (the pool never shrinks), while stake accounts are freshly credited via `checked_add_lamports` with no corresponding debit — effectively minting the same lamports repeatedly.
2. Continues to be split by whatever the *current* epoch's stake distribution happens to be, so any staker who delegates after the deposit was made receives a full pro-rata share of rewards that accrued before their stake existed, diluting stakers who were delegated at deposit time — the same "newer participant steals older participant's accrued share" bug class as H-1.

### Impact Explanation
This directly causes unauthorized/incorrect lamport minting and unfair fund distribution among stakers of a vote account: (a) rewards deposited once are effectively paid out to stakers on every subsequent epoch boundary rather than once, inflating total distributed lamports without a matching capitalization debit from the vote account, and (b) new delegators can capture shares of `pending_delegator_rewards` accrued before they staked, at the expense of the stakers who were delegated when the deposit occurred — a direct loss of funds for existing stakers and a way for an attacker to “rent” stake briefly to skim accumulated block-revenue-sharing rewards.

### Likelihood Explanation
`DepositDelegatorRewards` is a permissionless vote-program instruction reachable by any ordinary transaction once SIMD-0123/0185/0232/0291 features are active, and the reward calculation runs automatically at every epoch boundary for all vote accounts with non-zero `pending_delegator_rewards`. No privileged access is required; an attacker only needs to delegate stake to a vote account that has (or will have) a non-trivial `pending_delegator_rewards` balance to receive a share of it in the following epoch's reward calculation, and the flaw reoccurs automatically every epoch as long as the balance is non-zero.

### Recommendation
Decrement `pending_delegator_rewards` by the exact amount distributed as `block_reward` for a vote account during `store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition`, and debit the corresponding lamports from the vote account itself (mirroring how `distribute_reward_commissions` handles commission payouts), so that each unit of deposited revenue is paid out exactly once and new delegators cannot retroactively claim shares of rewards accrued before their stake existed.

### Proof of Concept
1. Any signer calls `DepositDelegatorRewards` on vote account `V` with `deposit = D`, incrementing `V.pending_delegator_rewards` to `D` [6](#0-5) .
2. At the next epoch boundary, `calculate_block_reward` computes each staker's share of `D` based on `stake / total_active_stake` at that epoch and credits stake accounts accordingly [7](#0-6) , but `V.pending_delegator_rewards` remains `D` (no decrement path exists).
3. At the following epoch boundary, the same `D` is split again among whoever is currently staked to `V` (potentially a different set of stakers who joined after step 1), each receiving another payout from the same nominal pool — repeating indefinitely and diluting/stealing from the originally-intended recipients.

        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {

            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
