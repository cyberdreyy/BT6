## Analysis

`EscrowDst.cancel()` has no persistent "already cancelled" state variable. Every guard on the function is stateless and re-evaluates true on every call: [1](#0-0) 

- `onlyCaller(immutables.taker.get())` — only checks `msg.sender`, not whether cancel already ran.
- `onlyValidImmutables(immutables.hash())` — only checks the CREATE2 address derivation, unaffected by prior calls.
- `onlyAfter(...DstCancellation)` — a one-way time gate that stays true forever once passed.

None of these track whether the payout already happened, and the function does not check the escrow's actual token/native balance against what it has already disbursed — it simply calls: [2](#0-1) 

`_uniTransfer`/`_ethTransfer` in `BaseEscrow.sol` perform a plain `safeTransfer`/raw call with no balance bookkeeping of their own: [3](#0-2) 

So if, after a successful `cancel()`, the clone's balance is topped back up to at least `immutables.amount` (an ERC20 `transfer()` directly to the clone address needs no `receive()`/`fallback()` — and none exists on `EscrowDst`/`Escrow`/`BaseEscrow` — and a forced native-ETH send via `selfdestruct` bypasses the missing `receive()` too), the same taker can call `cancel(immutables)` again, since every modifier still passes, and it will transfer another `immutables.amount` plus another `safetyDeposit` (if native ETH is present) to the taker/caller. This can repeat indefinitely for every refill.

Notably, the protocol already has an intended mechanism for a taker to eventually claim stray/leftover balances in a resolved escrow — `rescueFunds`, gated by `onlyAfter(immutables.timelocks.rescueStart(RESCUE_DELAY))`: [4](#0-3) 

The unguarded replay of `cancel()` lets the taker achieve the same "sweep whatever balance sits at this address" effect immediately after `DstCancellation`, completely bypassing the `RESCUE_DELAY` timelock that was specifically designed to delay this kind of appropriation.

That said, for this to produce actual theft of *someone else's* funds, a balance refill has to occur at that specific, hashlock-derived clone address after cancellation — which does not happen through any normal protocol flow (`createDstEscrow` cannot be called twice for the same immutables since `CREATE2`/clone deployment reverts if code already exists at that address, and no other in-scope function re-funds an already-resolved destination escrow). The realistic trigger is a third party mistakenly/independently sending tokens or forcing ETH to that exact address, which is external to the fill/create/withdraw/cancel attack surface rather than a break in the swap's own accounting invariant.

### Title
Missing cancelled-state flag lets taker replay `EscrowDst.cancel()` to bypass `RESCUE_DELAY` and drain any post-cancellation balance refill - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst.cancel()` performs no check that the escrow has already paid out, and no `receive()`/`fallback()` restriction prevents the clone from later holding additional token/native balance. As a result, the taker can call `cancel()` more than once, and each call after `DstCancellation` will pay out `immutables.amount` + `safetyDeposit` again as long as the contract's balance is refilled, effectively bypassing the `RESCUE_DELAY` protection that governs the intended sweep path (`rescueFunds`).

### Finding Description
`cancel()`'s modifiers (`onlyCaller`, `onlyValidImmutables`, `onlyAfter`) are all stateless re-checks and never latch a "cancelled" flag [1](#0-0) . `_uniTransfer`/`_ethTransfer` unconditionally attempt the transfer with no ledger of prior payouts [3](#0-2) . Any balance later present at the clone address (ERC20 `transfer()` needs no receiver hook; native ETH can be force-sent via `selfdestruct` since there's no `receive()`) can be extracted by simply calling `cancel()` again.

### Impact Explanation
If the refill scenario occurs (accidental/duplicate transfer to the resolved clone address, or a forced ETH send), the taker can extract those funds immediately, bypassing the `RESCUE_DELAY` timelock that is the protocol's designed guard for exactly this kind of leftover-balance claim.

### Likelihood Explanation
Low in ordinary operation: no in-scope function (`createDstEscrow`, `withdraw`, `publicWithdraw`, `publicCancel`) re-funds an already-cancelled destination escrow, and CREATE2/clone redeployment at the same address is not possible. The trigger depends on an external/accidental deposit to a hashlock-derived address, which is outside the defined fill/create/withdraw/cancel attack surface, making this closer to a defense-in-depth/idempotency defect than a directly reachable fund-theft path under normal protocol usage.

### Recommendation
Add a `bool cancelled` (or similarly a `withdrawn`/`resolved`) storage flag set on successful `cancel()`/`_withdraw()`, and require it be unset before allowing another payout, so each clone can only ever pay out once regardless of subsequent balance changes.

### Proof of Concept
1. Deploy `EscrowDst` clone via `createDstEscrow`, fund with `amount` + `safetyDeposit`.
2. After `DstCancellation`, taker calls `cancel(immutables)` — succeeds, clone balance drained to 0.
3. Send another `amount` of the destination token directly to the clone address (plain ERC20 `transfer`), or force-send `safetyDeposit` worth of ETH via a `selfdestruct` helper contract.
4. Taker calls `cancel(immutables)` again — all modifiers pass again, and the refilled balance is paid out to the taker, without waiting for `RESCUE_DELAY`.

            _ethTransfer(to, amount);

        }

    function _ethTransfer(address to, uint256 amount) internal {
        (bool success,) = to.call{ value: amount }("");

    }
