### Title
Cross-workflow response confusion via requestID reuse in `httpTriggerHandler` callback map - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`HandleNodeTriggerResponse` looks up the pending callback purely by the client-chosen string `resp.ID` in `h.callbacks` map, with no binding to the workflow/execution that originally registered it. Because `cleanupCallback` deletes the map entry and allows the same ID to be immediately reused by a different, unrelated workflow via `setupCallback`, a late-arriving (but genuine) node response tied to the *first* execution can be captured by the *second* execution's freshly created response aggregator if it shares a shard/DON assignment, causing one workflow's data to be delivered to a different workflow's caller.

### Finding Description
`h.callbacks` is a `map[string]savedCallback` keyed only by `requestID` [1](#0-0) . `requestID` is entirely client-controlled (`req.ID` from the JSON-RPC request), and the only uniqueness enforcement is a check against currently in-flight IDs at `setupCallback` time [2](#0-1) . Once `cleanupCallback` fires — which happens as soon as *any one* shard reaches quorum, closes `doneCh`, and deletes the map entry [3](#0-2) [4](#0-3)  — the same ID is free to be reused by a brand-new, unrelated `setupCallback` call for a different workflow, creating a fresh `savedCallback` with its own `responseAggregators` keyed by donID [5](#0-4) .

Meanwhile, `sendToShard` goroutines for shards that hadn't yet reached quorum for the first request keep running independently until they see `doneCh` closed or `ctx` cancelled [6](#0-5) ; the underlying node network round-trip for outstanding sends is not cancelled instantly, so a node can still be processing and legitimately reply with `resp.ID = X` after cleanup. When that response arrives, `HandleNodeTriggerResponse` re-looks up `h.callbacks[resp.ID]`, finds the *new* entry (workflowB), resolves `shard := h.nodeAddrToShard[nodeAddr]`, and if that donID happens to be one workflowB is also assigned to, it accepts the response into workflowB's aggregator without any check that this node/response actually belongs to workflowB's execution [7](#0-6) . If enough such straggling, content-identical node responses (all echoing workflowA's real execution result) accumulate to reach workflowB's aggregator threshold — trivially true when threshold is 1 for small/single-node shards — `CollectAndAggregate` returns the aggregated response, and it is sent to workflowB's caller via `saved.SendResponse` [8](#0-7) .

No check exists that binds a `savedCallback` to a specific registration instance (e.g., an epoch/generation counter or workflowID stamped into the callback and validated against the response), so the isolation invariant "a response can only satisfy the request that produced it" is not enforced beyond the raw string ID match.

### Impact Explanation
Scoped impact: a caller of workflowB can receive response payload data that actually originated from workflowA's execution (a different tenant/workflow), i.e., cross-user response confusion / unintended cross-tenant data disclosure through the gateway's HTTP trigger response channel. This matches the "cross-user response confusion" impact class called out in the rules.

### Likelihood Explanation
This requires: (1) two sequential trigger requests presented to the same `httpTriggerHandler` instance using an identical client-chosen `requestID`, (2) the second request's `setupCallback` to occur after the first's `cleanupCallback`, (3) the two workflows to share at least one shard/donID assignment, and (4) a still in-flight node response for the first request to arrive after the second registration. Preconditions (1)-(2) are entirely under a caller's control since `requestID` is unrestricted arbitrary client input (only checked for non-empty and no `/`) [9](#0-8) ; conditions (3)-(4) depend on DON/shard topology and network timing that the attacker does not fully control, and in a real multi-tenant deployment, actually delivering another tenant's payload requires an accidental (not attacker-forced) ID collision with a genuinely concurrent second request from a different tenant, since a caller cannot dictate what ID another tenant chooses. The bug is reliably reproducible as an isolation violation in a controlled/unit-test setting (single actor driving both requests), but exploiting it against an unrelated victim tenant in production requires a coincidental ID collision, reducing real-world likelihood.

### Recommendation
Bind each `savedCallback` to an immutable execution identity (e.g., a monotonically increasing epoch/generation counter or the `workflowID`/`legacyExecutionID`) stored on registration, and have `HandleNodeTriggerResponse` validate that the response's originating request context matches this identity before routing it into `responseAggregators`, rejecting/logging otherwise. Alternatively, embed a per-registration nonce into the ID sent to nodes (not just the raw user-supplied string) so that stale responses addressed to a previous registration can never match a newer one.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go`:
1. Configure a `httpTriggerHandler` with a single shard/donID shared by two workflows, workflowA and workflowB, with the shard aggregation threshold set to 1 (or drive multiple identical late node responses if threshold > 1).
2. Call `setupCallback(ctx, "X", callbackA, ..., workflowA)`, then simulate `HandleNodeTriggerResponse` for workflowA reaching quorum and confirm `cleanupCallback("X")` is triggered (map entry removed, `doneCh` closed).
3. Immediately call `setupCallback(ctx, "X", callbackB, ..., workflowB)`, registering a fresh `savedCallback` for the same ID.
4. Invoke `HandleNodeTriggerResponse` again with `resp.ID = "X"` and a payload representing workflowA's stale result, coming from a node belonging to the shared shard.
5. Assert (currently failing) that `callbackB.SendResponse` is NOT invoked with workflowA's payload — i.e., the response should be rejected because it does not belong to workflowB's current registration, rather than being silently aggregated and delivered as shown in the current implementation.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) cleanupCallback(requestID string) {
	saved, exists := h.callbacks[requestID]
	if !exists {
		return
	}
	close(saved.doneCh)
	delete(h.callbacks, requestID)
}
