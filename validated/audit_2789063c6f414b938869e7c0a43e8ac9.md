## Analysis

The Gravity Bridge bug is a class of **unbounded response size from a filtered on-chain scan**, where an attacker controls the size of the underlying data being scanned (ERC20 name/symbol/denom) and the querying code has no chunking/limit logic, leading to a perpetual DoS in the watcher/oracle loop.

The closest reachable analog in `agave--008` is Solana's `getProgramAccounts` RPC path when the `program-id` secondary account index is **not** enabled (which is the default/common validator configuration, since account indexes are opt-in and impose extra memory/CPU overhead). In that code path, unlike the indexed path, there is **no byte-size limit enforcement** at all on the scan result.

### Title
Unbounded `getProgramAccounts` Scan Allows Attacker-Controlled Account Data to Exhaust/Crash RPC Nodes - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_filtered_program_accounts` has two code paths: an indexed path that enforces `scan_results_limit_bytes` via `accumulate_and_check_scan_result_size`/`byte_limit_for_scan`, and a non-indexed (default) path that performs a full linear scan with **no size limit whatsoever**, explicitly noted in a comment as intentional.

### Finding Description
When `AccountIndex::ProgramId` is not configured (the default; it must be opt-in via `--account-index program-id`), `get_filtered_program_accounts` falls into the `else` branch that calls `bank.get_filtered_program_accounts(&program_id, ...)` directly, with no accumulation/size check: [1](#0-0) 

Compare this to the indexed path, which explicitly guards against unbounded results using `scan_results_limit_bytes`: [2](#0-1) [3](#0-2) 

An ordinary, unprivileged user can deploy a BPF program (any user-owned program ID) and then, via ordinary `CreateAccount`/`Allocate`/realloc system-program instructions, create/own an arbitrary number of accounts with data sizes up to `MAX_ACCOUNT_DATA_LEN` (10 MiB per account): [4](#0-3) [5](#0-4) 

Since this scan path has no byte-limit or entry-count cap, calling `getProgramAccounts` against that program ID forces the RPC node to load and JSON-encode the entire (attacker-sized) set of accounts in one synchronous blocking task, with no chunking or streaming, unlike the Gravity fix recommendation of "chunk the search size into 2 and try again."

The RPC config only bounds *incoming* request body size (`MAX_REQUEST_BODY_SIZE`, 50 KiB) and per-call account count for `getMultipleAccounts` (`MAX_MULTIPLE_ACCOUNTS`), not the *outgoing* response for `getProgramAccounts` on the non-indexed path: [6](#0-5) 

### Impact Explanation
An attacker can deploy accounts under their own program (or trigger it for well-known but non-indexed programs) sized to exceed available memory/response limits on any full-API RPC node that does not enable the `program-id` secondary index (the default). Calling `getProgramAccounts` on that program causes the targeted RPC node to attempt to materialize and serialize the entire account set in memory in one blocking call, which can exhaust memory or stall the RPC thread pool, denying service to legitimate RPC clients of that node. This is a single-node RPC availability impact (not a consensus/validator-core freeze, since RPC is decoupled from consensus in Solana), but it satisfies the "RPC crash / resource exhaustion" acceptance category.

### Likelihood Explanation
Likelihood is high for any public RPC provider running with `--full-rpc-api` and without `--account-index program-id` enabled (the common/default setup, since indexing has its own overhead). No special privileges are needed — creating accounts and calling `getProgramAccounts` are both ordinary, permissionless operations.

### Recommendation
Apply the same `scan_results_limit_bytes`/`byte_limit_for_scan` accumulation-and-abort mechanism used in the indexed path (`accumulate_and_check_scan_result_size`) to the non-indexed `get_filtered_program_accounts` branch in `rpc/src/rpc.rs`, rather than skipping the check because "we only want to support secondary indexes." Consider also imposing a maximum result count/size independent of whether an index is configured, and streaming/paginating large responses instead of buffering them fully in memory.

### Proof of Concept
1. Run a full-API RPC node without `--account-index program-id`.
2. As an ordinary user, deploy a program `P` and create N accounts owned by `P`, each with `MAX_ACCOUNT_DATA_LEN` (10 MiB) of data, using standard `CreateAccount`/`Allocate` system instructions.
3. Call `getProgramAccounts(P)` against the target RPC node.
4. Observe the RPC node performing an unbounded scan and JSON-encoding of the full data set in `get_filtered_program_accounts`'s non-indexed branch (`rpc/src/rpc.rs:2283-2307`), consuming disproportionate memory/CPU and potentially causing the RPC service to stall or OOM, denying service to other RPC clients — analogous to the unbounded `eth_getLogs` response DoS described in the source report.

    pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;

    fn calc_scan_result_size(account: &AccountSharedData) -> usize {
        account.data().len()
            + std::mem::size_of::<AccountSharedData>()
            + std::mem::size_of::<Pubkey>()
    }

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }
