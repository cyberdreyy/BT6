### Title
Unprivileged ERC4626 vault liquidity drain indefinitely freezes `stopEpoch` and all pending withdrawals — (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The XXE report's bug class is "untrusted external input is processed with unsafe defaults, letting an attacker-controlled external entity dictate the outcome." The credit-vault analog is `ProgrammableBorrower.onStopEpoch`, which hard-depends on the external ERC4626 `vault` it trusts: if `vault.withdraw()` cannot be satisfied, the hook reverts with `StopEpochVaultLiquidityUnavailable` and the revert bubbles into `IdleCDOEpochVariant._stopEpoch`, making epoch settlement impossible while the vault is illiquid. Any ordinary depositor of the configured ERC4626 vault — an explicitly unprivileged actor — can keep the vault drained and freeze the CDO's epoch, blocking all queued withdraw claims.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(...)` and lets hook reverts bubble up, explicitly so "transient ERC4626 liquidity failures can be retried" [1](#0-0) .

Inside `ProgrammableBorrower.onStopEpoch`, when the on-hand balance is below `_amountRequired`, the contract computes the shortfall and checks it against `convertToAssets`-based vault valuation — which stays high even when the vault has zero redeemable liquidity — then calls `vault.withdraw(shortfall, ...)`. A liquidity-based revert is rethrown as `StopEpochVaultLiquidityUnavailable` [2](#0-1) .

Because `_currentVaultAssets()` measures share *value* via `vault.convertToAssets(shares)` rather than redeemable *liquidity* (`maxWithdraw`), the `shortfall > _currentVaultAssets()` early-return path is not taken when the vault is merely illiquid — the code proceeds to the reverting withdraw every time [3](#0-2) .

Sequence:

1. Epoch running, programmable mode, pending withdraw requests queued (`epochPendingWithdraws > 0`).
2. Attacker, a regular LP of the configured ERC4626 vault (e.g., a Morpho/Yearn-style vault where liquidity is borrowable/withdrawable by anyone), withdraws or borrows the vault's liquid balance down to below the shortfall.
3. Honest manager calls `stopEpoch`/`stopEpochWithDuration` → `onStopEpoch` → `vault.withdraw` reverts → `StopEpochVaultLiquidityUnavailable` → entire `stopEpoch` reverts. `isEpochRunning` stays `true`, `expectedEpochInterest`/`pendingWithdraws` unsettled, and `defaulted` is never set because `_handleBorrowerDefault` is only reached on a `false` return or a failed `getFundsFromBorrower` self-call, not on a hook revert [4](#0-3) .
4. Attacker frontruns every retry with a liquidity withdrawal (or simply keeps funds borrowed), sustaining the freeze at no cost beyond capital already deployed in the vault.
5. Owner escape hatches do not help: `emergencyExitVault` calls `vault.redeem`, which fails under the same illiquidity [5](#0-4) , and `rescueTokens` cannot touch vault-held shares.

### Impact Explanation
Temporary freezing of funds with a quantifiable bound: every pending withdraw request (`pendingWithdraws`, i.e., up to the full queued redemption amount) plus all tranche principal awaiting epoch settlement cannot be claimed while the vault is kept illiquid, since claims are gated behind a successful `stopEpoch`. The freeze persists exactly as long as the attacker sustains vault illiquidity and can be re-triggered on each retry, so it is not "transient" in practice. On many ERC4626 vaults, executing this requires only holding/borrowing a liquidity position comparable to the shortfall — far less than the CDO's TVL.

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault has third-party liquidity that can be drained below `shortfall`, and an attacker willing to hold that liquidity position. The in-code comments acknowledge that transient withdraw failures are deliberately made retryable, which partially mitigates accidental cases but does nothing against an adversary who re-drains liquidity each block; that adversarial case is the unacknowledged part. In minted/fixed-APR modes the delay also keeps borrower interest accruing, compounding the distortion. Likelihood is moderate: conditions are specific to programmable deployments with shared-liquidity vaults, but no privileged action or timing luck is needed once the configuration exists.

### Recommendation
Make the stop flow robust to vault illiquidity rather than unboundedly retryable:

- In `onStopEpoch`, check `vault.maxWithdraw(address(this))` (redeemable liquidity) instead of only `convertToAssets` share value; if the withdraw cannot be served, return `false` so IdleCDO routes through `_handleBorrowerDefault` — or a new explicit "settlement-pending" path — instead of reverting forever.
- Alternatively, bound retries: after N failed `stopEpoch` attempts or a timeout, allow the manager to force the default/accounting path so pending withdrawals can be settled against recovered value.
- Document that share-value solvency and withdraw liquidity are distinct, and treat sustained `StopEpochVaultLiquidityUnavailable` as a default-trigger condition rather than an open-ended retry.

### Proof of Concept
Foundry fork test (mainnet fork with a real shared-liquidity ERC4626 vault, e.g., a Morpho or Yearn vault holding the same underlying):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

import "forge-std/Test.sol";

// Rough outline — wire addresses to the deployed programmable-borrower pool on fork.
contract OnStopEpochLiquidityFreezeTest is Test {
    IdleCDOEpochVariant cdo;
    ProgrammableBorrower borrower;
    IERC4626 vault;        // real external ERC4626 used by the borrower
    IERC20Detailed underlying;
    address manager;
    address attacker = makeAddr("attacker"); // plain vault LP, unprivileged

    function setUp() public {
        // 1. Fork mainnet at a block where the programmable pool exists.
        // 2. KYC a lender, deposit into AA/BB, manager calls startEpoch so
        //    borrower.onStartEpoch() parked idle cash into `vault`.
        // 3. Queue withdraw requests so epochPendingWithdraws > 0.
    }

    function test_freezeStopEpoch_viaVaultLiquidityDrain() public {
        uint256 shortfall =
            /* amount stopEpoch will request */ 1; // computed from pendingWithdraws + interest

        // Attacker drains vault liquidity below the shortfall (withdraw and/or
        // borrow on the underlying lending market that backs the vault).
        uint256 liquidity = underlying.balanceOf(address(vault));
        vm.startPrank(attacker);
        // ...attacker withdraws/borrows until liquidity < shortfall...
        vm.stopPrank();
        assertLt(underlying.balanceOf(address(vault)), shortfall);

        // Honest manager tries to stop the epoch: revert bubbles up.
        vm.prank(manager);
        vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(newApr, interest);

        // Epoch still running, nothing settled, claims impossible.
        assertTrue(cdo.isEpochRunning());
        assertFalse(cdo.defaulted());

        // Owner escape hatch also fails under illiquidity.
        vm.prank(borrower.owner());
        vm.expectRevert();
        borrower.emergencyExitVault(0);

        // Attacker keeps vault drained; every retry reverts identically,
        // so pending withdraws stay frozen for as long as the attack runs.
        vm.prank(manager);
        vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(newApr, interest);
    }
}
```

Uncertainty: on a vault whose liquidity cannot be reduced below the shortfall by unprivileged actors (e.g., an isolated vault holding only this facility's deposits), the attack surface shrinks; the finding applies to deployments pointed at shared-liquidity ERC4626 vaults, which the `setVault` interface explicitly permits [6](#0-5) .
