### Title
Non-anchored regex matching in `evaluateOverwrite`/`overwriteRegexCheck` allows partial-string bypass of `ServiceAccountOverwriteAllowed` (and other overwrite) patterns - (executors/kubernetes/overwrites.go)

### Summary
`createOverwrites` reads `KUBERNETES_SERVICE_ACCOUNT_OVERWRITE` from job variables and validates it against the operator-configured `ServiceAccountOverwriteAllowed` regex via `evaluateOverwrite` → `overwriteRegexCheck`, which calls `regexp.(*Regexp).MatchString`. Because `MatchString` reports whether the pattern matches *anywhere* in the string rather than requiring a full-string match, an operator-supplied pattern like `ci-.*` (without `^`/`$` anchors) can be satisfied by a value that merely *contains* `ci-` as a substring, not one that matches the pattern in its entirety from the start.

### Finding Description
The relevant code path is: [1](#0-0) 
which pulls the attacker-controlled `KUBERNETES_SERVICE_ACCOUNT_OVERWRITE` job variable and passes it to `evaluateOverwrite`: [2](#0-1) 
which in turn delegates the actual check to `overwriteRegexCheck`: [3](#0-2) 

`overwriteRegexCheck` uses `r.MatchString(value)`, which is Go's standard "does the regex match anywhere in the string" semantics, not a full-string anchored match. If the operator writes `ServiceAccountOverwriteAllowed: "ci-.*"` intending "value must start with `ci-`", the check actually just requires the substring `ci-` to appear anywhere, followed by the rest of the string (`.*` consumes everything to the end regardless). A crafted value such as `"privileged-service-account-ci-anything"` (or, even more simply, `"xci-y"`) will pass the check via `MatchString`, and the *entire* attacker-controlled string — not just the matched portion — becomes `o.serviceAccount` (see `evaluateOverwrite` returning `overwriteValue` unmodified at line 617), which is then used verbatim as the Kubernetes ServiceAccount for the job pod.

No other check re-validates or normalizes the value before it's used to configure the pod's service account, so if an operator's regex is not properly anchored, an unprivileged CI job author can supply a ServiceAccount name of their choosing as long as it happens to contain the operator's expected token as a substring.

This is a real, exploitable logic gap contingent on a class of common operator misconfiguration (non-anchored regex), and it applies identically to `NamespaceOverwriteAllowed`, `PodLabelsOverwriteAllowed`, `NodeSelectorOverwriteAllowed`, etc., since they all funnel through the same `overwriteRegexCheck`/`evaluateMapOverwrite` logic.

### Impact Explanation
If exploited against a loosely-anchored `ServiceAccountOverwriteAllowed` pattern, a job pipeline author can set `KUBERNETES_SERVICE_ACCOUNT_OVERWRITE` to an arbitrary Kubernetes ServiceAccount name that merely contains the operator's expected token as a substring, letting the job pod authenticate to the Kubernetes API as an unintended, potentially more privileged ServiceAccount than the operator intended to allow. This directly violates the invariant that only operator-sanctioned service accounts may be used by a job.

### Likelihood Explanation
Exploitability is entirely dependent on operator configuration: it requires the operator to configure `ServiceAccountOverwriteAllowed` with a non-anchored regex (e.g., `ci-.*`, `.*ci.*`) instead of an anchored one (`^ci-.*$`). This is a common regex-authoring mistake and the risk is compounded because `MatchString`'s substring-matching behavior is non-obvious to most operators, and the runner does not document, warn about, or enforce anchoring anywhere in `overwriteRegexCheck`. Given an unanchored pattern is in place, exploitation is trivial and 100% reproducible for any unprivileged pipeline author who can set CI/CD variables.

### Recommendation
Enforce full-string matching regardless of operator regex authoring style, e.g. wrap the pattern in `^(?:` + regex + `)$` before compiling in `overwriteRegexCheck`, or document/require anchoring and add validation at config-load time that warns/rejects unanchored overwrite-allowed patterns. Alternatively, switch to `regexp.Regexp.FindString` combined with a length comparison to `len(value)` to guarantee the whole string was consumed by the match.

### Proof of Concept
```go
// executors/kubernetes/overwrites_test.go
func TestServiceAccountOverwrite_UnanchoredRegexBypass(t *testing.T) {
    logger := stdoutLogger()
    o := &overwrites{}

    // Operator intends to only allow service accounts starting with "ci-"
    // but forgets to anchor the regex.
    regex := "ci-.*"

    // Attacker-controlled value: does NOT start with "ci-", but contains it
    // as a substring, so MatchString still succeeds.
    maliciousValue := "cluster-admin-sa-ci-x"

    result, err := o.evaluateOverwrite("ServiceAccount", "default", regex, maliciousValue, logger)

    assert.NoError(t, err, "expected the unanchored regex to incorrectly permit the value")
    assert.Equal(t, maliciousValue, result, "the full attacker-controlled ServiceAccount name is accepted verbatim")
    // Demonstrates the value was never actually anchored to start with "ci-"
    assert.False(t, strings.HasPrefix(result, "ci-"))
}
```
Expected assertions: the test passes today, proving `evaluateOverwrite`/`overwriteRegexCheck` accept a ServiceAccount name that does not conform to the operator's intended prefix restriction, confirming the non-anchored `MatchString` bypass.

func overwriteRegexCheck(regex, value string) error {
	var err error
	var r *regexp.Regexp
	if r, err = regexp.Compile(regex); err != nil {
		return err
	}
	if match := r.MatchString(value); !match {
		return &malformedOverwriteError{value: value, pattern: regex}
	}
	return nil
}
