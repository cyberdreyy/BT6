Confirmed: `accrue_interest` is called unconditionally at the start of nearly every state-changing instruction — `withdraw.rs`, `repay.rs`, `borrow.rs`, `deposit.rs`, `close_balance.rs`, `liquidate.rs`, `handle_bankruptcy.rs`, `super_admin_deposit.rs`, `super_admin_withdraw.rs`, and `configure_bank.rs` — with zero graceful-degradation fallback.

### Title
`accrue_interest` hard-reverts on arithmetic overflow, permanently freezing withdraw/repay/borrow/liquidate for the affected bank - (File: `programs/marginfi/src/state/bank.rs`)

### Summary
`Bank::accrue_interest` in [1](#0-0)  and the underlying rate/accrual math in [2](#0-1)  use `.ok_or_else(math_error!())?` at every arithmetic step, with no saturating or overflow-tolerant fallback anywhere in the chain. Because `accrue_interest` is called unconditionally as the first step of `withdraw`, `repay`, `borrow`, `deposit`, `close_balance`, and `liquidate`, any single overflow in this calculation permanently blocks all of those operations for the affected bank, exactly the liveness-breaking bug class described in the report (Cache.sol `initVaultCache`).

### Finding Description
`accrue_interest` computes `total_assets`/`total_liabilities` [3](#0-2)  then calls `calc_interest_rate_accrual_state_changes`, which multiplies principal share values by `(1 + apr * time_delta / SECONDS_PER_YEAR)`: [4](#0-3) 

Every step (`checked_mul`, `checked_div`, `checked_add`) is wrapped with `.ok_or_else(math_error!())?`, so on overflow the function returns `Err`, not a saturated/clamped value: [5](#0-4) 

Back in `Bank::accrue_interest`, the resulting share values are further multiplied against `total_asset_shares`/`total_liability_shares` for cache bookkeeping, again with `.ok_or_else(math_error!())?`: [6](#0-5) 

`Bank::accrue_interest` is invoked unconditionally, before any funds move, in every user-facing state-changing instruction: [7](#0-6) [8](#0-7) [9](#0-8) 

The permissionless `lending_pool_accrue_bank_interest` instruction that could otherwise be called proactively to "settle" interest in small increments also calls the exact same failing function: [10](#0-9) 

Because `apr` is clamped only at the top (max 1000% via `rate_from_u32`/`milli_to_u32`) but `time_delta` (seconds since `last_update`) is unbounded, and because interest compounds multiplicatively on every call, a bank configured with a high `hundred_util_rate` that sustains high utilization for a long enough period (or simply goes un-accrued for a long stretch, which is entirely possible since accrual is permissionless but not enforced) will eventually produce a `checked_mul`/`checked_add` overflow inside `calc_accrued_interest_payment_per_period` or in the `total_*_shares` multiplication in `bank.rs`. Once that happens, `accrue_interest` returns `Err` every single subsequent call, because `time_delta` only grows and the same (now-overflowing) computation is repeated identically on every invocation — there is no way to reset `last_update` without successfully completing `accrue_interest` itself.

### Impact Explanation
Once a bank's `accrue_interest` starts overflowing, `withdraw`, `repay`, `borrow`, `deposit`, `close_balance`, and both liquidation code paths for that bank become permanently unusable, since all of them call `accrue_interest` unconditionally before performing any other logic and propagate its `Err` up via `?`. This is a durable freeze of all user funds (deposits and collateral) associated with that bank, and specifically removes the ability to liquidate unhealthy positions in that bank, which has a direct, lasting financial impact (frozen collateral/debt, unrecoverable via normal instructions) matching the reported bug class exactly — liveness of withdraw/repay/liquidate broken by an interest-accrual overflow revert.

### Likelihood Explanation
This requires either (a) an admin-configured bank with an extreme `hundred_util_rate`/`points` curve sustaining high utilization over a long compounding period, or (b) a bank that is simply left un-accrued for an extended time while carrying large-enough share balances/rates that the compounded multiplication exceeds I80F48's range. Both scenarios are governance/operational rather than requiring a malicious unprivileged actor to directly force the overflow in a single transaction, but no permission or authorization check exists to prevent them, and no on-chain component detects or gracefully degrades from the condition once it starts, unlike the well-known "interest overflow" caveat that Euler documented for Cache.sol. The lack of any fallback for a genuinely permissionless, protocol-wide accrual computation used by all account-level instructions makes this a realistic operational-risk finding.

### Recommendation
Mirror the Euler fix referenced in the report: make `accrue_interest`'s liveness-critical paths (or at least a fallback path invoked from `withdraw`/`repay`/`liquidate`) tolerant of overflow — e.g., saturate the accumulator/share-value growth at the numeric ceiling rather than propagating a hard error, so that principal-affecting operations (withdraw, repay, liquidate) always remain executable even if interest simply stops growing. At minimum, clamp/cap `time_delta` and the compounding multiplier before they are used in `calc_accrued_interest_payment_per_period`, and add inline documentation (as Spearbit recommended for Euler) explaining the overflow-safety assumptions baked into `accrue_interest` and the interest-rate curve bounds.

### Proof of Concept
1. Admin creates/configures a bank with `hundred_util_rate` near the maximum (1000% APR) and a curve that sustains high APR at moderate-to-high utilization (`configure_bank`).
2. Ensure the bank sustains high utilization (large borrow relative to deposits) for a long period without anyone calling `lending_pool_accrue_bank_interest` (permissionless but optional), or via many small periodic accruals that compound `asset_share_value`/`liability_share_value` toward I80F48's integer bound over time.
3. Eventually, on some caller's `withdraw`/`repay`/`borrow`/`liquidate`, the `checked_mul` in `calc_accrued_interest_payment_per_period` (`interest_rate.rs:378`) or `total_asset_shares` multiplication in `bank.rs:571` overflows and returns `None`, causing `math_error!()` to fire and the whole instruction to revert.
4. From that point on, `time_delta` only increases, so the identical overflow reproduces on every future call to `accrue_interest` for that bank — `withdraw`, `repay`, `deposit`, `borrow`, `close_balance`, and `liquidate` (both classic and receivership) for that bank are permanently blocked, freezing all associated user funds.

fn calc_accrued_interest_payment_per_period(
    apr: I80F48,
    time_delta: u64,
    value: I80F48,
) -> Option<I80F48> {
    let ir_per_period: I80F48 = apr
        .checked_mul(time_delta.into())?
        .checked_div(SECONDS_PER_YEAR)?;

    let new_value: I80F48 = value.checked_mul(I80F48::ONE.checked_add(ir_per_period)?)?;

    Some(new_value)
}

/// Calculates the interest payment for a given period `time_delta` in a principal value `value` for interest rate (in APR) `arp`.
/// Result is the interest payment.
fn calc_interest_payment_for_period(apr: I80F48, time_delta: u64, value: I80F48) -> Option<I80F48> {
    if apr.is_zero() {
        return Some(I80F48::ZERO);
    }

    let interest_payment: I80F48 = value
        .checked_mul(apr)?
        .checked_mul(time_delta.into())?
        .checked_div(SECONDS_PER_YEAR)?;

    Some(interest_payment)
}
