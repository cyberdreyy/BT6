### Title
Loss-adjusted withdraw receipts claimable at par after `stopEpochWithDuration` loss because `lossRecoveryPriceByEpoch` is keyed by the post-increment `epochNumber` while `lastWithdrawRequest` still points to the request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` records a user's receipt under `epochNumber` and stores that epoch in `lastWithdrawRequest[_user]`. When `stopEpoch`/`stopEpochWithDuration` runs with a realized loss, `collectWithdrawFunds` writes the haircut to `lossRecoveryPriceByEpoch[epochNumber]` — but `epochNumber` has already been incremented inside `deposit()` earlier in the same stopEpoch call (`epochNumber += 1` when `isEpochRunning`). The haircut is therefore stored under epoch `E+1` while the user's `lastWithdrawRequest` still points to `E`, so `_claimLossAdjustedWithdrawRequest` reads a zero price and the full receipt falls through to `_claimFundedWithdrawRequest`, which pays it at par against a strategy that only holds the haircut amount.

### Finding Description
The external bug class is use of a stale reference after a lifetime transition (RCU-protected pointer used after the object moved on). The analog is the per-epoch receipt pointer `lastWithdrawRequest[_user]`:

- `requestWithdraw` snapshots `currentEpoch = epochNumber` and writes `withdrawsRequestsByEpoch[_user][currentEpoch]`, `lastWithdrawRequest[_user] = currentEpoch` (contracts/strategies/idle/IdleCreditVault.sol, lines ~260–293).
- During `stopEpoch`/`stopEpochWithDuration`, `IdleCDOEpochVariant` calls `strategy.deposit(...)`/`getFundsFromBorrower` while the epoch is still running; `deposit()` then executes `epochNumber += 1` (contracts/strategies/idle/IdleCreditVault.sol, lines 607–610, comment: "deposit done on stopEpoch (before setting the var to false)").
- Immediately afterwards `IdleCDOEpochVariant._beforeStopEpoch` calls `_strategy.collectWithdrawFunds(_pendingWithdraws)` (contracts/IdleCDOEpochVariant.sol, lines 408–410), which, on partial funding, stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` — under the *new* epoch number (line 421).
- On claim, `_claimLossAdjustedWithdrawRequest` resolves `lossEpoch = lastWithdrawRequest[_user]` (the *old* epoch) and reads `lossRecoveryPriceByEpoch[lossEpoch] == 0`, returning 0 (lines 789–795).
- `claimWithdrawRequest` then adds `_claimFundedWithdrawRequest(_user)` (lines 301–350), which burns the receipt and transfers the full unhaircut `withdrawsRequests[_user]` amount via `_transferFundedClaim`, since the gating check `epochNumber <= lastWithdrawRequest[_user]` passes once the epoch ended.

The net effect: a haircut `lossRecoveryPrice` (e.g. 50%) exists in storage but is unreachable by any user because their receipt pointer references the pre-increment epoch.

### Impact Explanation
Direct theft/insolvency: every pending withdraw receipt created in the loss epoch claims at 100% while the strategy only received `pendingToFund = pendingBasis - pendingLoss` from the borrower. The first claimants drain `defaultRecoveryReserve`/funded underlyings beyond their entitlement; later claimants (including defaulted-epoch recovery claimants and other receipt holders) are left permanently underpaid or unable to claim. The loss waterfall invariant "receipt holders absorb `pendingLoss` pro rata" is silently broken; the shortfall equals `pendingBasis - pendingToFund = pendingLoss` across the epoch.

### Likelihood Explanation
Any `stopEpochWithDuration` (or `stopEpoch` with partial borrower repayment) with `_lossAmount > 0` and non-zero `pendingWithdraws` triggers it — a normal manager-driven flow, not an edge case. The only precondition is an ordinary user `requestWithdraw` during the epoch that ends with a loss. The guard at lines 263–270 and the zero-price revert at line 419 do not prevent it, because the haircut is stored under the wrong key, not absent. Loss-adjusted claims were intended by `previewLossAdjustedWithdrawFunds` (lines 440–460).

### Recommendation
Key `lossRecoveryPriceByEpoch` by the epoch in which the receipts were requested (the pre-increment `epochNumber`), or defer the `epochNumber += 1` in `deposit()` until after `collectWithdrawFunds`/`collectInstantWithdrawFunds` run, or record the loss epoch explicitly when `collectWithdrawFunds` is invoked (e.g. pass the request-epoch from the CDO). Equivalently, `_claimLossAdjustedWithdrawRequest` could iterate the user's non-empty `withdrawsRequestsByEpoch` entries rather than relying solely on `lastWithdrawRequest` as the lookup key.

### Proof of Concept
Foundry fork test (existing harness in `test/foundry/IdleCDOEpochQueue.t.sol` is directly adaptable — see the loss path in `testProcessWithdrawalClaimsWithZeroPayout`-style setup, lines ~811–858):

```solidity
// test/foundry/IdleCreditVault_LossEpochMismatch.t.sol
function testLossAdjustedReceiptClaimsAtPar() external {
    uint256 reqEpoch = strategy.epochNumber();
    _requestWithdrawWithUser(FASA, 100 * ONE_TRANCHE);   // withdrawsRequestsByEpoch[FASA][reqEpoch]
    _stopCurrentEpochWithApr(10e18);                     // epochNumber++, funds, no loss yet

    vm.prank(manager);
    cdoEpoch.startEpoch();
    _requestWithdrawWithUser(FASA, 100 * ONE_TRANCHE);   // request epoch E
    uint256 E = strategy.epochNumber();

    // borrower repays only 50% of pending basis -> loss
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 lossAmount   = pendingBasis / 2 * (activeBasis + pendingBasis) / pendingBasis; // ~50% pending haircut
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(address(underlying), strategy.borrower(), repay, true);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);

    // haircut stored under E+1, user pointer is E
    assertEq(strategy.lossRecoveryPriceByEpoch(E), 0, "loss keyed to wrong epoch");
    assertGt(strategy.lossRecoveryPriceByEpoch(E + 1), 0, "haircut unreachable");

    uint256 balPre = underlying.balanceOf(FASA);
    vm.prank(address(cdoEpoch));
    // user claims FULL amount at par instead of pendingToFund share
    strategy.claimWithdrawRequest(FASA);
    assertGt(underlying.balanceOf(FASA) - balPre, pendingToFund, "overpaid at par");
}
```

Expected: the claim pays `withdrawsRequests[FASA]` in full rather than `claimBasis * lossRecoveryPriceByEpoch[E] / 1e18`, exceeding the funded amount and leaving the deficit to other claimants.
