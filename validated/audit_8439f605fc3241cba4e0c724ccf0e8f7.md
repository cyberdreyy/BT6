### Title
Unchecked instruction-account indexing panics the JSON-RPC transaction/block decoder - ([File: transaction-status/src/lib.rs])

### Summary
`transaction-status` decodes on-chain instructions into their `jsonParsed` RPC representation by indexing directly into an `AccountKeys` slice using the raw `program_id_index`/`accounts` values taken from a `CompiledInstruction`. Unlike every other per-program parser in the same crate, this top-level/fallback decoding path performs no bounds check before indexing, so any mismatch between the instruction's embedded indices and the actual `account_keys` length reaching this code causes the RPC/validator process to panic.

### Finding Description
`parse_ui_instruction` and its fallback helper `make_ui_partially_decoded_instruction` index `account_keys` directly: [1](#0-0) [2](#0-1) 

`account_keys[instruction.program_id_index as usize]` and `account_keys[i as usize]` are plain slice-index operations, which panic on out-of-range indices.

This is inconsistent with every program-specific parser in the same crate, all of which defensively verify that the instruction's account indices fit inside `account_keys` *before* indexing, explicitly noting that the runtime is expected to guarantee this but adding the check anyway as defense-in-depth: [3](#0-2) [4](#0-3) [5](#0-4) 

The bug-class analog to the report is direct: the external report describes a system where an "index" is trusted to always correctly reference a position in an accompanying data structure (the Merkle tree/bitmap), and when that invariant silently breaks (tree updated, layout shifts), the code does unsafe things with the stale index instead of validating it. Here, `program_id_index`/`accounts` entries are indices that are trusted to always be `< account_keys.len()` because "the runtime already validated the message." Every other parser in the crate treats that as an assumption worth re-checking defensively; `parse_ui_instruction`/`make_ui_partially_decoded_instruction` do not, so if that invariant is ever violated (e.g., `AccountKeys` constructed with a truncated/mismatched key set relative to the compiled indices — for instance a `V0` message whose address-table-lookup–derived keys are built from a different resolution than the one used to compile the instruction, or bugs/inconsistencies in code that assembles `AccountKeys` for RPC encoding), the process panics instead of returning a parse error like the other parsers do.

### Impact Explanation
A panic in this decoding path is invoked from user-facing JSON-RPC calls (`getTransaction`, `getBlock`, `getConfirmedTransaction`/`getConfirmedBlock` with `encoding=jsonParsed`) which any unprivileged client can issue with a single request against transaction data the validator already has (transaction-status/blockstore reads). A panic here can crash the RPC-serving thread/process, matching the accepted "concrete validator-process crash... from one request" impact class. It is also a "decoder panic" in the transaction-status/instruction-parsing category explicitly called out as in-scope.

### Likelihood Explanation
Likelihood is Low-to-Medium: under normal conditions, `Message::sanitize()` and transaction processing are expected to guarantee `program_id_index`/instruction account indices are always `< account_keys.len()` for any transaction that reaches storage/serving. However, that guarantee is exactly the kind of implicit, unenforced invariant the external report warns about — as evidenced by the fact that every *other* parser in this same crate does not trust it and re-validates anyway. Any divergence in how `AccountKeys` is assembled for encoding purposes versus how the instruction was compiled (particularly around versioned transactions and address-lookup-table–resolved keys, which are reconstructed independently for RPC display) removes the safety net that protects `parse_system`, `parse_token`, and `parse_address_lookup_table`, but not `parse_ui_instruction`'s own indexing and its `PartiallyDecoded` fallback.

### Recommendation
Add the same defensive bounds check used throughout the rest of the crate to `parse_ui_instruction` and `make_ui_partially_decoded_instruction` before indexing `account_keys`, returning a decode error (e.g., produce an `UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(...))` with an error marker, or propagate a `ParseInstructionError`) instead of panicking when `instruction.program_id_index` or any entry of `instruction.accounts` is `>= account_keys.len()`.

### Proof of Concept
Not independently reproducible from the indexed code alone (requires exercising the exact call path that constructs `AccountKeys` for `parse_ui_instruction` from a `V0`/ALT-resolved transaction, which is outside what indexed context provides). Conceptually: construct/encode a versioned (`V0`) transaction whose `CompiledInstruction.program_id_index` or `.accounts` values are large enough to only be valid once address-lookup-table addresses are appended, then trigger a code path where `parse_ui_instruction`/`make_ui_partially_decoded_instruction` is invoked with an `AccountKeys` that does not include the expected loaded addresses (e.g. a resolution/formatting mismatch), producing an out-of-bounds slice index panic. Confirming an end-to-end unprivileged trigger would require a Devin session with full repo/build access to trace every caller of `parse_ui_instruction`/`AccountKeys` construction in the RPC/transaction-status encoding pipeline.

fn make_ui_partially_decoded_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiPartiallyDecodedInstruction {
    UiPartiallyDecodedInstruction {
        program_id: account_keys[instruction.program_id_index as usize].to_string(),
        accounts: instruction
            .accounts
            .iter()
            .map(|&i| account_keys[i as usize].to_string())
            .collect(),
        data: bs58::encode(instruction.data.clone()).into_string(),
        stack_height,
    }
}

pub fn parse_ui_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiInstruction {
    let program_id = &account_keys[instruction.program_id_index as usize];
    if let Ok(parsed_instruction) = parse(program_id, instruction, account_keys, stack_height) {
        UiInstruction::Parsed(UiParsedInstruction::Parsed(parsed_instruction))
    } else {
        UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(
            make_ui_partially_decoded_instruction(instruction, account_keys, stack_height),
        ))
    }
}
