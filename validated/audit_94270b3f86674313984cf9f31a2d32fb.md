`StateDelta::next_version` is a low-level storage-layer accessor that simply delegates to `self.current.next_version()` [1](#0-0)  — it tracks the SMT version number for the in-memory state delta (`base`/`current`/`shards` layered map), which is purely a storage/versioning construct [2](#0-1) .

This has no connection to stake-pool reward synchronization, `pending_active`/`pending_inactive`/`active`/`inactive` share accounting, or epoch-boundary promotion logic, all of which live in the Move `stake.move` module and operate on Move resource state, not on Rust-level `StateDelta` version counters. The version number here is an internal bookkeeping detail of the JMT/state-merkle storage engine that reflects how many writes have been applied to the persistent state tree — it is not read or consumed by stake reward-sync logic to determine which stake-pool writes are "included." No unprivileged transaction sequence of `add_stake`/`unlock` calls can influence `StateDelta::next_version` in a way that causes epoch-boundary stake logic to skip a write, because the version counter is derived from the state tree's own commit history, not from any stake-specific accounting the attacker could desynchronize.

The premise conflates a storage-engine version counter with Move-level stake-pool state transitions; these are architecturally decoupled, so the described proof idea does not correspond to any real code path in the stake, delegation, or vesting modules.

        let shards = Arc::new(std::array::from_fn(|shard_id| {
            current.shards()[shard_id].view_layers_after(&base.shards()[shard_id])
        }));

        }
