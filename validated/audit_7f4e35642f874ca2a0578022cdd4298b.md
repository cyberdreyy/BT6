## Finding: Confirmed

The ordering issue described is real. `switch_operator` moves a `StakingContract` record from the `old_operator` key to the `new_operator` key while a pending commission distribution owed to `old_operator` is still queued (unlocked but not yet inactive/withdrawable), and this causes that pending commission to permanently bypass `old_operator`'s beneficiary redirection when it is eventually paid out.

### Title
Stale `distribution_pool` shareholder after `switch_operator` bypasses beneficiary redirection for old operator's queued commission - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` is an unprivileged, staker-callable entry function [1](#0-0)  that, before re-keying the `StakingContract` from `old_operator` to `new_operator`, calls `distribute_internal` and then `request_commission_internal` under the `old_operator` context. `request_commission_internal` records a fresh commission entry keyed by `old_operator` inside `distribution_pool` via `add_distribution(operator, ..., operator, commission_amount)` [2](#0-1) , and unlocks that amount from the stake pool (it does not pay it out immediately — it must first become fully inactive). Immediately afterward, the whole `StakingContract` (including this pending `distribution_pool` entry keyed by `old_operator`) is re-inserted into the store under the `new_operator` key [3](#0-2) .

### Finding Description
`distribute_internal`'s beneficiary-redirection logic only fires when the pool's `recipient` matches the `operator` parameter that was passed into the current call:
```
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
``` [4](#0-3) 

After `switch_operator`, all future calls to `distribute`/`distribute_internal` for this record are made with `operator = new_operator` (since the record now lives under that key in the `Store`) [5](#0-4) . When the previously-queued commission (recipient == `old_operator`) is finally redeemed once the unlocked stake becomes inactive, the equality check `recipient == operator` (`old_operator == new_operator`) fails, so `beneficiary_for_operator(old_operator)` is never invoked. The coins are instead deposited directly to the raw `old_operator` address via `aptos_account::deposit_coins` [6](#0-5) , bypassing whatever beneficiary `old_operator` had configured (or later configures) with `set_beneficiary_for_operator`.

This is a break of the invariant that the module documents and depends on: the beneficiary lookup is meant to happen dynamically at payout time regardless of when the commission accrued [7](#0-6) . That invariant silently holds only because, absent a `switch_operator`, a pool entry's `recipient` always equals the `operator` key under which `distribute_internal` is invoked. `switch_operator` breaks this coupling by relocating the `StakingContract` (and its still-populated `distribution_pool`) to a new key while leaving the old recipient address inside the pool.

### Impact Explanation
The commission still lands with `old_operator` (the party that actually earned it) — it is not stolen by the staker or by `new_operator`. However, it is misrouted away from `old_operator`'s registered beneficiary, which is a distinct address/entity that `old_operator` explicitly designated to receive commission payouts (e.g., a custodial or business payout address). This breaks the operator/beneficiary boundary the module is designed to preserve, and the misdirection is triggered purely by an unprivileged staker action (`switch_operator`) with no cooperation from `old_operator` needed. This is a moderate accounting/routing correctness bug rather than a fund-theft primitive, since value stays under `old_operator`'s ultimate control (their own account key) rather than going to an attacker or to `new_operator`.

### Likelihood Explanation
This triggers deterministically whenever: (1) the old operator has an outstanding, non-zero unpaid commission accrued at the time of a `switch_operator` call (a common, easily-reachable state since commissions accrue continuously and stakers can call `switch_operator` at will), and (2) that commission is still in-flight (unlocked but not yet inactive) at the switch, or the operator sets/changes a beneficiary any time after the switch but before that leftover distribution is finally paid out. No special privileges beyond normal staker ownership of the staking contract are required.

### Recommendation
Track distribution-pool shareholders in a way that survives operator re-keying, or resolve the beneficiary based on the recorded recipient address at redemption time instead of comparing against the ambient `operator` parameter, e.g. change the redemption check to always attempt `beneficiary_for_operator(recipient)` for any recipient that constitutes an "operator" role (this requires distinguishing operator-recipients from staker-recipients explicitly, e.g., via a tagged distribution or a separate set of "operator addresses ever associated with this pool"). At minimum, `switch_operator` should fully flush/settle all pending distributions (including ones just unlocked by `request_commission_internal`) belonging to `old_operator`, or refuse to switch while the old operator has non-zero commission still in the unlock/pending window.

### Proof of Concept
1. Staker creates a staking contract with `operator_A`, non-zero `commission_percentage`.
2. `operator_A` calls `set_beneficiary_for_operator` to point to `beneficiary_A` (distinct address).
3. Stake pool accrues rewards; staker (or operator_A) calls `request_commission`/`unlock_stake` is not needed — simply invoke `switch_operator(staker, operator_A, operator_B, new_pct)` while rewards are unpaid. Internally this calls `request_commission_internal` which unlocks commission and adds a `distribution_pool` entry keyed to `operator_A`, then the `StakingContract` is moved to key `operator_B`.
4. Advance epochs until the lockup expires so the unlocked commission becomes `inactive`.
5. Call `distribute(staker, operator_B)` (the only valid way to reach this record now). Inside `distribute_internal`, `operator == operator_B`; the pending entry's `recipient == operator_A`; the equality check fails, so `beneficiary_for_operator(operator_A)` is skipped and the coins are deposited straight to `operator_A`'s account address instead of `beneficiary_A`.
6. Assert: `beneficiary_A`'s balance is unchanged, and `operator_A`'s raw account balance increased by the commission amount — demonstrating the beneficiary redirection was bypassed as a direct consequence of the `distribute_internal` → `request_commission_internal` → `stake::set_operator_with_cap` ordering inside `switch_operator`.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

    public entry fun switch_operator(
        staker: &signer,
        old_operator: address,
        new_operator: address,
        new_commission_percentage: u64
    ) acquires Store, BeneficiaryForOperator {
        let staker_address = signer::address_of(staker);
        assert_staking_contract_exists(staker_address, old_operator);

        assert!(
            new_commission_percentage <= 100,
            error::invalid_argument(EINVALID_COMMISSION_PERCENTAGE)
        );
        // Merging two existing staking contracts is too complex as we'd need to merge two separate stake pools.
        let store = borrow_global_mut<Store>(staker_address);
        let staking_contracts = &mut store.staking_contracts;
        assert!(
            !staking_contracts.contains_key(&new_operator),
            error::invalid_state(ECANT_MERGE_STAKING_CONTRACTS)
        );

        let (_, staking_contract) = staking_contracts.remove(&old_operator);
        // Force distribution of any already inactive stake.
        distribute_internal(
            staker_address,
            old_operator,
            &mut staking_contract,
        );

        // For simplicity, we request commission to be paid out first. This avoids having to ensure to staker doesn't
        // withdraw into the commission portion.
        request_commission_internal(
            old_operator,
            &mut staking_contract,
        );

        // Update the staking contract's commission rate and stake pool's operator.
        stake::set_operator_with_cap(&staking_contract.owner_cap, new_operator);
        staking_contract.commission_percentage = new_commission_percentage;

        let pool_address = staking_contract.pool_address;
        staking_contracts.add(new_operator, staking_contract);
        emit(SwitchOperator { pool_address, old_operator, new_operator });
    }
