### Title
Stale-miner block can be signed and pushed because `check_block_against_signer_db_state` never re-verifies miner/tenure authorization (`PubkeyHashMismatch`/`ConsensusHashMismatch`) that `check_proposal` only checks once, at proposal time - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The signer's two-round commit protocol (pre-commit → 70% → signature) is designed so a signature is only produced after "one last look" at the world. That re-check, `check_block_against_signer_db_state`, is deliberately narrow: it only re-verifies tenure-confirmation (`check_tenure_change_confirms_parent` / `check_latest_block_in_tenure`). It does **not** re-run the authorization checks that gated the original proposal — `RejectReason::ConsensusHashMismatch`, `RejectReason::PubkeyHashMismatch`, `RejectReason::InvalidMiner` — which live only in `GlobalStateView::check_proposal` (v2) / `SortitionsView::check_proposal` (v1) and are documented as running "only at proposal arrival, never again."

### Finding Description
`check_block_against_signer_db_state` is the single "re-check" function invoked both at `handle_block_validate_ok` (validate-ok path) and at `handle_block_pre_commit` right before the 70%-threshold signature is produced: [1](#0-0) 

It only calls `check_tenure_change_confirms_parent` or `check_latest_block_in_tenure` — i.e. it re-verifies that the proposal still confirms the expected tip of a tenure. It never re-checks that the block's `consensus_hash`/miner pubkey still match the signer's *current* `MinerState::ActiveMiner` view, which is exactly what `GlobalStateView::check_proposal` checks, but only once, at proposal arrival: [2](#0-1) 

The project's own documentation states this gap explicitly and only claims it is covered "the same ground" by a *different* guard (the same-tenure `get_signed_conflicts` conflict check in section 5) for the `DuplicateBlockFound` case — it makes no such claim for `PubkeyHashMismatch`/`ConsensusHashMismatch`/`InvalidMiner`: [3](#0-2) 

Concretely: a miner proposes block B for tenure T. The signer validates B (node round-trip can take real time), marks it `PreCommitted`, and broadcasts a pre-commit. Before B's pre-commits reach the 70% weight threshold, a new Bitcoin block arrives and a *new* sortition elects a different miner/tenure T'. The signer's own `LocalStateMachine`/`GlobalStateView.current_miner` updates to reflect T' (via `bitcoin_block_arrival`/`capitulate_viewpoint`), but block B, already stored with `valid = Some(true)`, is never re-run through `check_proposal`. When B's pre-commit weight subsequently crosses 70% (e.g., because enough signers pre-committed just before the new sortition, or straggling pre-commits/replayed pending pre-commits arrive afterward), `handle_block_pre_commit` re-checks only `check_block_against_signer_db_state` (tenure-confirmation), which B still passes since nothing about *its own* tenure's tip changed — and the signer signs B: [4](#0-3) 

The `get_signed_conflicts`/`conflict_still_blocks` guard that runs afterward only blocks on *other signed blocks*; since nothing has been signed yet for the new tenure T', there is no conflict to detect, and the stale-miner block for the superseded tenure sails through to a full signature.

### Impact Explanation
This breaks the "approved-parent vs canonical" equality the scan targets: a signer set can end up producing a valid 70%-threshold signature (Critical-adjacent — a non-canonical block gets signed) over a block proposed by a miner/tenure that is no longer the active/canonical one according to the signer's own global state machine, purely because of the natural timing gap between pre-commit accumulation and Bitcoin block arrival — no majority collusion, no compromised keys, just ordinary chain progression during the pre-commit window. This can also feed into `broadcast_signed_block`/`handle_post_block`, pushing the stale block to the node.

### Likelihood Explanation
Requires no adversarial signer behavior — only a normally-timed new Bitcoin block/sortition landing between "70% pre-commit reached for block B" being nearly satisfied and the final threshold-crossing pre-commit/PreCommit-replay arriving (a window governed by ordinary network latency and `block_proposal_timeout`/`tenure_last_block_proposal_timeout`, not an attacker-controlled parameter). Because pre-commits (unlike signatures) carry no freshness/staleness re-derivation against the *current miner*, and because `should_reevaluate_block`'s `PreCommitted` re-evaluation path also only re-runs `handle_block_pre_commit` (i.e., the same narrow `check_block_against_signer_db_state`) rather than the full `check_proposal`, the gap is structural rather than a one-off race.

### Recommendation
Re-run the authorization portion of `check_proposal` (consensus-hash-vs-current-miner and pubkey-hash-vs-current-miner checks, i.e. what currently lives only in `GlobalStateView::check_proposal`/`SortitionsView::check_proposal`) inside `check_block_against_signer_db_state`, or otherwise ensure the pre-commit-threshold re-check in `handle_block_pre_commit` (and the `PreCommitted` branch of `should_reevaluate_block`) re-validates that the block's tenure/miner is still the signer's current active miner before signing.

### Proof of Concept
Not independently executable within the scope of this review (requires a live multi-signer/multi-node harness with controlled Bitcoin-block timing, akin to the existing `stacks-node/src/tests/signer/v0/*` integration tests). The structural gap is demonstrated purely by code inspection:
1. `GlobalStateView::check_proposal` (chainstate/v2.rs:111-163) enforces `ConsensusHashMismatch`/`PubkeyHashMismatch`/`InvalidMiner` only when a *new* `BlockProposal` event is processed (docs/signer-flows.md:174-203).
2. `check_block_against_signer_db_state` (signer.rs:1803-1880), the only re-check run at validate-ok and at pre-commit-threshold-crossing time (signer.rs:1946-1947, 1345-1346), calls only `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure` — no miner/consensus-hash re-verification.
3. `docs/signer-flows.md:425-437` documents this omission and only claims the `own-tenure conflict guard` (section 5, `get_signed_conflicts`) as compensation for the `DuplicateBlockFound` case, not for miner/tenure-authorization staleness — confirming no other code path fills this gap.

```markdown
Two things belong to the proposal path only and are **not** re-run at validate-ok
or at signing:

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
  have already accepted a block in the tenure a tenure-change block is starting.
  v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1
  counts only globally accepted ones (`get_last_globally_accepted_block`).
- the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the
  pox bitvec, and tenure-extend rules before delegating here.

Because the duplicate check never runs again, a block that crosses the pre-commit
threshold long after it was proposed relies on section 5's own-tenure conflict
guard to cover the same ground.
```
