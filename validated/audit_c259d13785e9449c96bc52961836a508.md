### Title
A KYC'd lender can jam the prefunded queue with a deposit above the guarded TVL limit, permanently blocking `stopEpochWithDuration`, then cancel for a full refund - (contracts/IdleCDOEpochQueue.sol)

### Summary
`IdleCDOEpochQueue.requestDeposit` lets any Keyring-allowed wallet queue a next-epoch deposit while the epoch is running, and `deleteRequest` lets the same wallet cancel and reclaim its underlyings at any time before the epoch price is set. In the prefunded variant, the manager can only flush the queue via `processDepositsToBorrower`, which calls `checkPrefunding(_pending)` on the whole pending aggregate — a check that reverts if `_guarded(_amount)` (the launch TVL limit) is exceeded. If any pending deposit remains when the manager calls `stopEpochWithDuration`, the stop reverts (enforced by test `testStopEpochWithDurationRevertsIfPrefundedQueueWasNotPrefunded`). A single griefer can therefore deposit enough to push `epochPendingDeposits[nextEpoch]` above `limit`, making `checkPrefunding` revert forever, which makes `stopEpochWithDuration` revert forever — the running epoch can never stop while the griefing deposit sits in the queue. The attacker loses nothing: `deleteRequest` is always available (no epoch-price is ever set for a stuck epoch), so the attack is refundable gas-only grief, exactly matching the "front-run and cancel" bug class.

### Finding Description
The relevant code paths:

1. `requestDeposit` only enforces the cutoff window and per-deposit `checkPrefunding(epochPendingDeposits[nextEpoch] + amount)`. Each individual deposit passes `_guarded`, but there is no per-epoch cap that keeps the *aggregate* under the limit — a griefer can be the sole depositor and deliberately exceed it in one shot, or top up after honest deposits arrive. [1](#0-0) 
2. `processDepositsToBorrower` is owner/manager-only and requires `checkPrefunding(_pending)` on the full pending amount. If `pending > limit - getContractValue()`, this reverts unconditionally — the manager has no way to prefund only part of the queue. [2](#0-1) 
3. `checkPrefunding` reverts when defaulted or when `_guarded(_amount)` fails (TVL limit reached). [3](#0-2) 
4. With `epochQueue` set, `stopEpochWithDuration` reverts while the next epoch still has pending (non-prefunded) queue deposits, as demonstrated by the revert test — so the epoch end is unreachable. [4](#0-3) 
5. The griefer escapes free: `deleteRequest` only requires `epochPrice == 0 && epochPrefundedDeposits == 0`, which always holds for the stuck epoch, and refunds the full underlying amount. [5](#0-4) 

### Impact Explanation
While the grief deposit is queued, `stopEpochWithDuration` always reverts, so the entire vault TVL — all AA/BB principal and all pending withdrawal funding — is frozen: no epoch stop, no interest settlement, no withdrawal processing, no default handling through the normal path. The freeze lasts until either the attacker cancels or the honest owner raises `limit`/`_setLimit` high enough to let `checkPrefunding` pass, which the attacker can counter by topping up `requestDeposit` again (still inside the deposit window or with `prefundedDepositWindow == 0`, until `epochEndDate`). Denominator is the full vault NAV; attacker cost is only gas plus temporarily locked capital that is fully refundable. This is temporary-to-persistent freezing of all user funds, with quantified loss equal to the vault TVL for the duration and delayed interest accrual.

### Likelihood Explanation
Requires: prefunded variant with `epochQueue` configured, and a non-zero guarded `limit` such that the attacker can fund `limit - getContractValue() + ε` — plausible for guarded-launch pools where the limit is intentionally small, or whenever the attacker has capital comparable to remaining capacity. The attacker needs to pass `isWalletAllowed` (Keyring KYC), which is in scope. No privileged cooperation is needed; the honest manager's own `processDepositsToBorrower` / `stopEpochWithDuration` calls are what get bricked.

### Recommendation
Prevent the aggregate pending deposit from exceeding what `checkPrefunding` can accept, and/or make over-limit deposits impossible to strand the epoch:

- In `requestDeposit`, revert when `epochPendingDeposits[nextEpoch] + amount` would exceed the remaining guarded capacity (i.e., the same bound `checkPrefunding` enforces), so the queue can never hold more than can be prefunded.
- Alternatively, allow `processDepositsToBorrower` to prefund a partial amount, or give the manager a `refundRequest(user, epoch)` escape hatch (and/or permissionless refund of any deposit that exceeds capacity) so a single oversized request cannot veto `stopEpoch`.
- Optionally bind requests to the depositor's identity in the epoch accounting (the analog of adding `proposer` to the proposal hash): track the max-allowed aggregate per epoch and reject top-ups that push over it.

### Proof of Concept
Foundry fork test sketch against `IdleCDOEpochVariantPrefunded` + `IdleCDOEpochQueue` (mirroring the setup in `test/foundry/IdleCDOEpochVariantPrefunded.t.sol`):

```solidity
function testGrieferBlocksEpochStop() public {
    // setup: prefunded queue enabled, guarded limit L set
    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    vm.prank(manager);
    queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);

    // attacker (KYC-passing lender) deposits limit - contractValue + 1
    uint256 room = cdoEpoch.limit() - cdoEpoch.getContractValue();
    deal(address(underlying), attacker, room + 1);
    vm.startPrank(attacker);
    underlying.approve(address(queue), room + 1);
    // each requestDeposit individually passes checkPrefunding until it pushes
    // aggregate over the limit; split into two txs if needed
    queue.requestDeposit(room + 1);
    vm.stopPrank();

    // honest manager tries to prefund -> checkPrefunding reverts on aggregate
    _enterPrefundedWindow(PREFUNDED_DEPOSIT_WINDOW);
    vm.prank(manager);
    vm.expectRevert(); // ContractLimitReached inside checkPrefunding
    queue.processDepositsToBorrower();

    // epoch end arrives; manager tries to stop -> reverts: pending deposits not prefunded
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), 0);

    // grief is free: attacker cancels and recovers all funds
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    queue.deleteRequest(strategy.epochNumber() + 1);
    assertEq(underlying.balanceOf(attacker) - balPre, room + 1);
}
```

Uncertain elements I could not fully verify within this review: the exact revert site for the "queue not prefunded" check inside `stopEpochWithDuration`/`_afterStopEpochWithDuration` (the test at `IdleCDOEpochQueue.t.sol:389-420` confirms the revert exists), and whether production deployments set a bounded `limit` — without a guarded limit the attacker's required capital is the pool's remaining capacity, weakening but not eliminating the grief (any deposit that makes `processDepositsToBorrower` uneconomical still strands the epoch until cancelled).

```text
    // check if the wallet is allowed to deposit (ie epoch is running and keyring KYC completed)
    _checkAllowed(msg.sender);

    IdleCDOEpochVariant _cdo = IdleCDOEpochVariant(idleCDOEpoch);
    uint256 nextEpoch = IdleCreditVault(strategy).epochNumber() + 1;
    uint256 _prefundedWindow = prefundedDepositWindow;
    // Only the AA prefunded queue enforces a deposit cutoff for the next epoch.
    if (tranche == _cdo.AATranche() && _isPrefundedQueueEnabled()) {
      IdleCDOEpochVariantPrefunded(idleCDOEpoch).checkPrefunding(epochPendingDeposits[nextEpoch] + amount);
      // Once funds are prefunded, or once the subscription window is reached, the next epoch is closed.
      _checkNotAllowed(
        epochPrefundedDeposits[nextEpoch] != 0 || (
        _prefundedWindow != 0 && block.timestamp + _prefundedWindow >= _cdo.epochEndDate()
      ));
    }

    // get underlying tokens from user
    IERC20Detailed(underlying).safeTransferFrom(msg.sender, address(this), amount);
    // deposit will be made in the next buffer period (ie next epoch)
    // updated user queued amount for the next epoch
    userDepositsEpochs[msg.sender][nextEpoch] += amount;
    // update pending deposits
    epochPendingDeposits[nextEpoch] += amount;
  }
```

```text
  function processDepositsToBorrower() external {
    IdleCDOEpochVariant _cdo = IdleCDOEpochVariant(idleCDOEpoch);
    IdleCreditVault _strategy = IdleCreditVault(strategy);
    // only owner or strategy manager can move queued funds to the borrower
    _checkOnlyOwnerOrManager();
    // prefunded flow is supported only for AA queue
    // queue must be explicitly enabled on the prefunded CDO variant
    _checkNotAllowed(tranche != _cdo.AATranche() || !_isPrefundedQueueEnabled());

    // prefunding can be done only while epoch is running
    if (!_cdo.isEpochRunning()) {
      revert EpochNotRunning();
    }
    // Keep prefunding aligned with the same cutoff enforced for new queued deposits.
    uint256 _prefundedWindow = prefundedDepositWindow;
    _checkNotAllowed(_prefundedWindow == 0 || block.timestamp + _prefundedWindow < _cdo.epochEndDate());

    uint256 _epoch = _strategy.epochNumber() + 1;
    // prefunding can happen only once for an epoch
    _checkNotAllowed(epochPrefundedDeposits[_epoch] != 0);
    uint256 _pending = epochPendingDeposits[_epoch];
    if (_pending == 0) {
      return;
    }
    // Recheck after the cutoff because emergency state or the TVL limit can change while queued.
    IdleCDOEpochVariantPrefunded(idleCDOEpoch).checkPrefunding(_pending);

    // Switch the epoch from "queue-held" to "already at borrower" before transferring funds.
    epochPendingDeposits[_epoch] = 0;
    epochPrefundedDeposits[_epoch] = _pending;
    IERC20Detailed(underlying).safeTransfer(_strategy.borrower(), _pending);
  }
```

```text
  function deleteRequest(uint256 _requestEpoch) external {
    // if the epoch price is already set, deposits were already processed so
    // the deposit request can't be deleted.
    _checkNotAllowed(epochPrice[_requestEpoch] != 0 || epochPrefundedDeposits[_requestEpoch] != 0);

    uint256 amount = userDepositsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user deposit for the epoch
    userDepositsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending deposits
    epochPendingDeposits[_requestEpoch] -= amount;
    // transfer underlyings back to the user
    IERC20Detailed(underlying).safeTransfer(msg.sender, amount);
  }
```

```text
    uint256 pendingWithdraw = strategy.pendingWithdraws();

    uint256 toRepay = interest + pendingWithdraw;

    deal(address(underlying), borrower, toRepay);
```
