### Title
Overspend in workflow metering settlement is silently discarded instead of debited, allowing free excess capability spend - ([File: core/services/workflows/metering/metering.go])

### Summary
`Report.Settle` refunds the difference between the amount earmarked at `Deduct` time and the actual reported spend via `r.balance.Add(step.Deduction.Sub(spentCredits))`. When actual spend exceeds the earmarked deduction (a negative delta), `balanceStore.Add` rejects any negative amount with `ErrInvalidAmount` and performs no balance mutation at all, rather than debiting the excess from the balance.

### Finding Description
`Settle` computes `spentCredits` from capability-reported `MeteringNodeDetail.SpendValue`/`SpendValueInGasUnits` values [1](#0-0)  and then attempts to true up the local balance:

```go
if err := r.balance.Add(step.Deduction.Sub(spentCredits)); err != nil {
    // invariant: capability should not let spend exceed reserve
    r.lggr.Info("invariant: spend exceeded reserve")
}
r.balance.AddSpent(spentCredits)
``` [2](#0-1) 

`balanceStore.Add` explicitly refuses negative arguments:
```go
func (bs *balanceStore) Add(amount decimal.Decimal) error {
    ...
    if amount.LessThan(decimal.Zero) {
        return ErrInvalidAmount
    }
    bs.balance = bs.balance.Add(amount)
    return nil
}
``` [3](#0-2) 

So when `spentCredits > step.Deduction` (i.e., the capability/DON reports spend larger than what was reserved), `step.Deduction.Sub(spentCredits)` is negative, `Add` returns `ErrInvalidAmount`, and the code only logs "invariant: spend exceeded reserve" — the balance is left completely unchanged for that overage. Meanwhile `r.balance.AddSpent(spentCredits)` still records the full `spentCredits` in the "spent" counter used for billing (`GetSpent`, consumed in `SendReceipt`'s `CreditsConsumed`) [4](#0-3) [5](#0-4) , but the in-execution `balance` used by `getMaxSpendForInvocation` to gate subsequent `Deduct` calls is never reduced by the excess — it only ever reflects the originally-earmarked amount, not the true consumption. This is directly analogous to the GMX bug class: an operation that should reduce a value-tracking balance when a loss/overspend occurs instead leaves it unchanged (i.e., asymmetric handling of the "loss" branch), because the sign-guard in `Add` was designed only for the refund path and doesn't handle the overspend path.

This is reachable by an unprivileged actor because `SpendValue` in `MeteringNodeDetail` is populated straight from the DON/capability's `CapabilityResponse.Metadata.Metering`, which is attacker-influenceable in scenarios where the workflow owner controls or configures the capability being invoked (e.g., a custom/compute capability reporting its own spend) [6](#0-5) .

### Impact Explanation
A workflow that can cause a capability to report `SpendValue` greater than its earmarked `Deduction` benefits from unbilled/under-debited local balance: the in-memory `balance` is not decremented for the excess, letting subsequent `Deduct` calls (`ByDerivedAvailability`, `getMaxSpendForInvocation`) compute available credit as if the overspend never happened, letting a workflow run more (or more expensive) capability calls than its actual reserved credit should allow. This can also mask real resource exhaustion until `SendReceipt` posts the full amount to billing, at which point the discrepancy between the tracked local balance and actual billed consumption has already allowed excess execution.

### Likelihood Explanation
Requires a scenario where a capability's reported `SpendValue` exceeds the deduction reserved for it in a given step; this is plausible for compute/gas capabilities where usage is measured after execution and can vary, or where a workflow-controlled capability misreports spend. The `r.lggr.Info(...)` message wording ("invariant: spend exceeded reserve") suggests this was recognized as an unexpected condition but handled as a no-op rather than a corrective debit.

### Recommendation
When `step.Deduction.Sub(spentCredits)` is negative, debit the balance by the excess (symmetric to `MKTU-1`'s `Calc.sum(value, -pnl)` fix) instead of no-op'ing, e.g. call `r.balance.Minus(spentCredits.Sub(step.Deduction))` in that branch so the local balance always reflects actual net spend, not just the refund case.

### Proof of Concept
1. Reserve a report and `Deduct("step1", ByResource(unit, capID, decimal.NewFromInt(2)))` — earmarks 2 credits (`step.Deduction = 2`).
2. Call `Settle("step1", metadata)` where `metadata.Metering` reports a `SpendValue` that converts to `spentCredits = 5` (greater than the 2 earmarked).
3. `step.Deduction.Sub(spentCredits) = -3`; `r.balance.Add(-3)` returns `ErrInvalidAmount`, balance is unchanged.
4. `r.balance.AddSpent(5)` still records 5 as spent for billing purposes, but `r.balance.Get()` (used to gate future `Deduct`/`getMaxSpendForInvocation` calls) is unaffected by the 3-credit overage, letting the workflow continue as if only 2 credits (not 5) were consumed for subsequent local gating decisions, exactly mirroring the "pool value with inverse PnL"-style loss-not-recorded defect.

	bs.mu.Lock()

	return nil
