### Title
Miner can indefinitely suppress the inactivity fallback by resubmitting non-advancing proposals, which keep resetting `last_activity_time` - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` treats any block proposal that *conflicts* with an already-accepted or pre-committed block — including proposals whose height is `<=` the height already known — as valid "miner activity" and calls `update_last_activity_time` for it. `SortitionState::is_timed_out` (v1 and v2) uses exactly this timestamp, together with `has_signed_block_in_tenure`, to decide whether the current miner has gone inactive and should be replaced by the prior tenure's miner. Because a non-advancing (same-or-lower-height) re-proposal is enough to bump the timer, a miner that stops making real progress can still keep resubmitting stale/duplicate proposals forever, resetting the clock each time and preventing the signer set from ever falling back to a live prior miner — this is the same equality-based "reset trigger" class as the Solidity report, where an action that produces no real state progress (same/lower position) is nevertheless treated the same as legitimate progress and reuses the reset path.

### Finding Description
`check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-448`) is invoked on every block proposal a miner sends for a tenure. When a proposed block's height is `<=` the last signed block's height, it is rejected as stale [1](#0-0) , but rejection still triggers `update_last_activity_time` whenever `signed_group` is unset or recent [2](#0-1) . Separately, when the last accepted block is only pre-committed (no signature) and still "fresh," a same-or-lower-height conflicting proposal *also* bumps the activity timer [3](#0-2) .

`SortitionState::is_timed_out` for both protocol versions computes elapsed inactivity purely from `get_last_activity_time` (falling back to burn-block receive time), gated only by `has_signed_block_in_tenure` [4](#0-3) [5](#0-4) . Since a miner can freely resubmit non-advancing (same/lower height) block proposals for its own tenure without ever getting a real signature, it can perpetually re-trigger `update_last_activity_time`, which resets the elapsed-time computation to zero on every call — analogous to the reported bug where an equality condition (`newPosition <= prevPosition`, here `chain_length <= info.chain_length`) that should represent "no real progress" is instead wired into the same reset path used for legitimate activity.

This is distinct from the two prior fixes already present in the codebase (`stacks-signer/changelog.d/precommit-suppresses-miner-timeout.fixed`, treating pre-commits themselves as signed; and `no-fallback-to-stopped-miner.fixed`, gating fallback on canonical-tip tenure), both of which harden `is_timed_out`/`check_miner_inactivity` against *other* variants of this class but do not address the activity-timer reset performed inside `check_latest_block_in_tenure` for non-advancing proposals.

### Impact Explanation
This can wedge the signer state machine into never falling back away from a stalled or adversarial current miner: as long as the miner (or anyone relaying `MinerMessages` on its behalf) keeps resubmitting stale/duplicate proposals, `is_timed_out` never returns `true`, `check_miner_inactivity`/`check_proposal`'s timeout branch never fires, and signers never revert to the valid prior-tenure miner even though the current miner is not producing any real, higher block. That matches the High-impact category "a signer wedged into never signing valid blocks" for the tenure, since a live prior miner that could otherwise be selected is permanently blocked from taking over.

### Likelihood Explanation
Medium: no majority or protocol violation is required — a single miner (or anyone forwarding its signed proposals via `MinerMessages` gossip) can trigger this by repeatedly resubmitting the same or a lower-height block proposal. There is limited direct financial upside for the miner beyond stalling the chain / denying block production to a competitor, similar to the "no direct benefit but no preconditions" characterization in the original report.

### Recommendation
Do not update `last_activity_time` for proposals that do not represent forward progress. Specifically, only count a proposal as activity when its height is strictly greater than the previously known signed/pre-committed height for the tenure (mirroring the `<` vs `<=` fix suggested in the analog report), or introduce an explicit "genuine progress" flag distinguishing a legitimately-reproposed block (e.g., after a timeout) from a spammed duplicate/stale one, so `is_timed_out` cannot be reset by resubmission alone.

### Proof of Concept
1. Miner M wins a tenure and proposes block B1 at height H; signers pre-commit or locally accept B1 but it never reaches global signature.
2. M (or a relay) repeatedly resubmits B1 (or any block ≤ height H) as `MinerMessages` proposals.
3. Each resubmission enters `check_latest_block_in_tenure`, hits the `chain_length <= info.block.header.chain_length` branch, and calls `update_last_activity_time` [6](#0-5)  (or the fresh-pre-commit branch at lines 422-447).
4. `is_timed_out` recomputes `elapsed` from the just-refreshed `last_activity_time` and never exceeds `block_proposal_timeout` [7](#0-6) .
5. `check_miner_inactivity`/`check_proposal`'s fallback-to-prior-miner path is never reached, wedging the tenure indefinitely as long as resubmissions continue.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)

            return Ok(false);
