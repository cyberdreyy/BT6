## Title
Stale confirmations from removed multisig members count toward quorum, allowing request execution below the live member threshold - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
The reported nano-node bug is a race condition where a test assumes a state (block confirmation) that nothing actually waits for, letting an unrelated event occupy the slot the test expected. The structural analog here is that `MultiSigContract::confirm` counts entries in a request's `confirmations` set toward `num_confirmations` without verifying that every confirming identity is still a current member. `delete_member` only purges *requests created by* the removed member, not that member's *confirmations left on other members' requests*, so a departed member's stale confirmation silently continues to count toward the K-of-N quorum forever.

### Finding Description
`confirm()` computes reaching quorum purely from the size of the `confirmations` set, with no re-validation of membership for entries other than the caller: [1](#0-0) 

When a member is removed via `delete_member`, cleanup only targets requests whose *creator* (`r.member`) equals the removed member — it does not scan and strip that member's public key/account from the `confirmations` sets of requests created by *other* members: [2](#0-1) 

The only membership-size guard at removal time is that `members.len() - 1 >= num_confirmations`, which says nothing about whether previously recorded confirmations remain attached to a still-active identity: [3](#0-2) 

Consequently, `confirmations.len()` for an old pending request can include one or more identities that are no longer in `self.members`, so the equality the contract is supposed to guarantee —

`confirmations by current members == num_confirmations required`

— degrades to

`confirmations by current members + stale confirmations by removed members >= num_confirmations`

allowing execution (including `Transfer`, `FunctionCall`, `AddMember`/`DeleteMember`, `AddKey`) with fewer live approvals than the configured threshold. The identical pattern exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` only removes requests whose `signer_pk` equals the deleted key, not that key's confirmations on requests created by other keys: [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the multisig's core custody guarantee — that any privileged action (fund transfer, member/key management, deployment) requires `num_confirmations` approvals from currently trusted parties. A request can be executed with fewer live approvals than the threshold if it was left pending long enough for one of its confirmers to be later removed as a member/key holder. This maps to the Critical impact category: "a multisig request executed below threshold," potentially enabling unauthorized NEAR transfers or unauthorized privilege changes (e.g., adding an attacker-controlled key/member) out of an account meant to be protected by K-of-N consensus.

### Likelihood Explanation
No special privilege beyond being one of the N members is required, and no owner/foundation/redeploy action is needed. This can occur through entirely ordinary governance operations: a request is opened and partially confirmed, a member departure/rotation happens later (a routine `DeleteMember`/`DeleteKey` request), and the old pending request is confirmed afterward. Because `add_request`/`confirm` allow requests to remain outstanding indefinitely (bounded only by the 15-minute `REQUEST_COOLDOWN` before deletion is *allowed*, not required), an attacker or negligent member need only wait for a routine membership change to weaponize an existing stale confirmation.

### Recommendation
When removing a member/key (`delete_member` in `multisig2`, `DeleteKey` in `multisig`), iterate over all `confirmations` entries for every outstanding request and strip the removed member's identity from each set (not just requests it created). Alternatively, re-validate at `confirm()`/execution time that every identity present in a request's `confirmations` set is still contained in `self.members` before counting it toward quorum.

### Proof of Concept
1. Deploy `multisig2` with members `[Alice, Bob, Carol, Dave]` and `num_confirmations = 3`.
2. Alice calls `add_request` for `Transfer { amount }` to some receiver → `request_id = R`.
3. Bob calls `confirm(R)` → `confirmations(R) = {Bob}` (1/3).
4. Separately, Alice, Carol, and Dave create and confirm a `DeleteMember { member: Bob }` request (reaching 3/4 confirmations without Bob) → Bob is removed from `self.members`; `delete_member` only deletes requests where `r.member == Bob` (none, since Bob didn't create `R`), so `confirmations(R)` still contains Bob.
5. Alice calls `confirm(R)` → `confirmations(R) = {Bob, Alice}` (2/3, per stored count, but Bob is no longer a member).
6. Carol calls `confirm(R)` → count reaches 3 → `execute_request` fires the `Transfer`, even though only Alice and Carol (2 of the current 3 live members) actually approved it — below the intended 3-of-3 live quorum.

        self.assert_valid_request(request_id);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
