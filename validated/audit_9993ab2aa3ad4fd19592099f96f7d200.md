### Title
Unbounded JSON allocation on `getAccountInfo(jsonParsed)` for maximal-size Address Lookup Table accounts - ([File: account-decoder/src/parse_address_lookup_table.rs])

### Summary
An unprivileged user can create and extend an address-lookup-table-owned account up to the runtime's maximum account size, filling essentially the entire account with raw 32-byte pubkey entries. A single `getAccountInfo` (or `getMultipleAccounts`/`getProgramAccounts`) call with `encoding: jsonParsed` on that account causes `account_decoder::parse_address_lookup_table::parse_address_lookup_table` to deserialize every entry and `Into<UiLookupTable>` to `.to_string()` and collect every pubkey into a `Vec<String>`, producing an unbounded-size JSON array proportional only to the attacker-controlled account size, not to any RPC-side limit.

### Finding Description
`account_decoder::parse_address_lookup_table::parse_address_lookup_table` calls `AddressLookupTable::deserialize(data)`, which derives the number of address entries directly from `data.len()` (bytes after the fixed `LOOKUP_TABLE_META_SIZE` header, chunked into 32-byte pubkeys), with no explicit cap on the resulting `addresses` count: [1](#0-0) 

The resulting `AddressLookupTable` is converted with `Into<UiLookupTable>`, which iterates over every address and formats it as a base58 string into a `Vec<String>` with no length ceiling: [2](#0-1) 

This is reached from the live RPC `getAccountInfo` path: `JsonRpcRequestProcessor::get_account_info` → `get_encoded_account` → `encode_account`/`parse_account_data_v3` (feature-gated `agave-unstable-api`, which is enabled for the `rpc` crate per `rpc/Cargo.toml`), and `UiAccountEncoding::JsonParsed` unconditionally invokes the parser regardless of `dataSlice` settings: [3](#0-2) [4](#0-3) [5](#0-4) 

An unprivileged attacker can grow an ALT-owned account up to `MAX_PERMITTED_DATA_LENGTH` (10 MiB) using ordinary, permissionless `CreateLookupTable`/`ExtendLookupTable` instructions over multiple transactions (no special authority is required beyond being the table's own authority, which the attacker controls). With the account packed with pubkey-sized entries, `(10 MiB - 56) / 32 ≈ 327,000` addresses are implied by `data.len()` alone. There is no guard in `get_encoded_account`, `encode_account`, or `parse_address_lookup_table` that bounds the number of addresses parsed/serialized per request — unlike `getMultipleAccounts`, which enforces `MAX_MULTIPLE_ACCOUNTS`, single-account jsonParsed decoding has no analogous cap: [6](#0-5) 

### Impact Explanation
A single low-rate JSON-RPC call (`getAccountInfo` with `encoding: jsonParsed`, or `getProgramAccounts`/`getMultipleAccounts` touching the same account) forces the validator to allocate and serialize a JSON array with on the order of hundreds of thousands of base58 pubkey strings for one client, at a cost bounded only by attacker-authored on-chain data size rather than any explicit RPC parameter or response-size limit. This matches the "unbounded cost for a single low-rate call" category — a resource-amplification / RPC-DoS-adjacent bug scoped to a single request.

### Likelihood Explanation
Fully feasible with only unprivileged capabilities: creating and extending an address lookup table is a normal, permissionless operation available to any funded account; extending to the maximum account size requires multiple `ExtendLookupTable` transactions (each bounded by transaction size/CU limits) but no protocol-level restriction prevents reaching `MAX_PERMITTED_DATA_LENGTH`. Once created, the account is permanently queryable, so the attack is trivially repeatable by any client at ≤1 request per `CLUSTER_SLOT_TIME_TARGET / 2`.

### Recommendation
Enforce an explicit maximum on the number of addresses parsed/serialized in `parse_address_lookup_table` (and mirror it in the `transaction-status`/account-decoder client-visible types), rejecting or truncating with a `ParseAccountError` when the implied address count exceeds a sane bound (e.g., matching the protocol's `MAX_LOOKUP_TABLE_ADDRESSES` or a fixed cap well below account-size derived worst case), and/or apply `dataSlice`-aware limits before invoking jsonParsed decoding for large accounts.

### Proof of Concept
```rust
// account-decoder/src/parse_address_lookup_table.rs (integration test)
#[test]
fn test_parse_max_size_lookup_table_allocation_bound() {
    use solana_address_lookup_table_interface::state::{LookupTableMeta, AddressLookupTable};
    use std::borrow::Cow;
    use solana_pubkey::Pubkey;
    use std::time::Instant;

    const LOOKUP_TABLE_META_SIZE: usize = 56;
    const MAX_PERMITTED_DATA_LENGTH: usize = 10 * 1024 * 1024; // 10 MiB
    let num_addresses = (MAX_PERMITTED_DATA_LENGTH - LOOKUP_TABLE_META_SIZE) / 32;

    let mut addresses = Vec::with_capacity(num_addresses);
    addresses.resize_with(num_addresses, Pubkey::new_unique);
    let lookup_table = AddressLookupTable {
        meta: LookupTableMeta::default(),
        addresses: Cow::Owned(addresses),
    };
    let data = AddressLookupTable::serialize_for_tests(lookup_table).unwrap();
    assert!(data.len() <= MAX_PERMITTED_DATA_LENGTH);

    let start = Instant::now();
    let result = parse_address_lookup_table(&data).unwrap();
    let elapsed = start.elapsed();

    if let LookupTableAccountType::LookupTable(ui) = result {
        // Assert no bound is enforced today (demonstrates the bug):
        assert_eq!(ui.addresses.len(), num_addresses);
    }
    // Expected fix: this should fail once a max-address cap is enforced,
    // or `elapsed`/allocation size should stay under a defined ceiling
    // (e.g., a few milliseconds / a few KB), not scale with account size.
    println!("parsed {} addresses in {:?}", num_addresses, elapsed);
}
```
This test demonstrates that a maximum-size ALT account produces an unbounded `addresses` vector and JSON payload with no ceiling enforced by `parse_address_lookup_table`, confirming the per-request cost scales with attacker-controlled on-chain data size.

pub fn parse_address_lookup_table(
    data: &[u8],
) -> Result<LookupTableAccountType, ParseAccountError> {
    AddressLookupTable::deserialize(data)
        .map(|address_lookup_table| {
            LookupTableAccountType::LookupTable(address_lookup_table.into())
        })
        .or_else(|err| match err {
            InstructionError::UninitializedAccount => Ok(LookupTableAccountType::Uninitialized),
            _ => Err(ParseAccountError::AccountNotParsable(
                ParsableAccount::AddressLookupTable,
            )),
        })
}

fn get_encoded_account(

                encode_account(&account, pubkey, encoding, data_slice)?

            Ok(Some(response))

    }
