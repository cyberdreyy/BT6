### Title
Unauthenticated `setApr`/`setAprs` while `idleCDO` is unset lets any EOA pin an arbitrary epoch APR before the trust anchor is wired — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr` treats `idleCDO == address(0)` as an implicit "trusted setup mode" and skips the caller check entirely. Like `cSpell.trustedWorkspace` defaulting to true, the configuration value itself is the trust flag: until the owner wires the real CDO via `setWhitelistedCDO`, any unprivileged caller can write `lastApr` and `unscaledApr` up to `maxApr` (or uncapped if `maxApr` is later set to 0, as in the programmable-borrower deployment pattern). Once the CDO is connected, `startEpoch` reads the attacker-pinned `lastApr` through `_getStrategyApr()`/`_setScaledApr()`, so the forged APR persists into live epochs without any further attacker action. An attacker who deposits as a lender in this window is paid inflated fixed yield funded by the honest borrower.

### Finding Description
In `IdleCreditVault.setApr` (contracts/strategies/idle/IdleCreditVault.sol:225-235):

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

The access control is conditional on a configuration value (`idleCDO != 0`) rather than on an authenticated caller. `setAprs` (lines 206-210) and `setAprsWithBuffer` (lines 217-220) both funnel into `setApr` and additionally let the attacker set `unscaledApr`, which is the value `IdleCDOEpochVariant._getStrategyApr()`/`_setScaledApr()` consumes at `startEpoch`.

Attack sequence:

1. Owner deploys and initializes the vault (`initialize`, lines 124-158). `idleCDO` is `address(0)`; `setWhitelistedCDO` (lines 953-957) has not yet run. In the programmable-borrower deployment flow the owner also later calls `strategy.setMaxApr(0)` (test/foundry/ProgrammableBorrowerCreditVault.t.sol:144), which fully disables the APR cap — but even the default `DEFAULT_MAX_APR = 20e18` cap permits a 20% forged APR.
2. Attacker EOA front-runs or races the wiring transaction and calls `setAprs(forgedApr, forgedScaledApr)`, setting both `unscaledApr` and `lastApr` with no authorization.
3. Attacker passes Keyring KYC and calls `depositAA`/`depositBB` on `IdleCDOEpochVariant` during the buffer phase.
4. Manager calls `startEpoch`. `IdleCDOEpochVariant` scales the strategy APR (`_setScaledApr(_getStrategyApr())`, contracts/IdleCDOEpochVariant.sol:89) — it reads back the attacker-pinned `unscaledApr`, so the forged rate survives even though `setApr` re-checks `msg.sender` once `idleCDO` is set. The CDO's own `setApr` call just re-stamps the same value.
5. At `stopEpoch`, `expectedEpochInterest`/`_calcInterestWithApr` owe the attacker's tranche position yield at the forged rate, funded by the honest borrower through the normal repayment path (`sendInterestAndDeposits`/`collectWithdrawFunds`).

The broken invariant is access control on yield-rate configuration: the effective trust decision ("is this caller the CDO or manager") is derived from a mutable config slot that is `0` exactly when the system is most exposed, rather than from a real authenticated state. No existing guard stops it: `_onlyIdleCDO` is not applied to `setApr`, `maxApr` only bounds the magnitude (and can be 0), and Keyring/KYC only gates depositing, not APR setting.

### Impact Explanation
Direct theft of yield: every epoch that runs on the forged APR over-charges the borrower and over-pays tranche holders proportionally to attacker deposits. With the default cap, a 20e18 scaled APR on e.g. a 1M USDC attacker deposit over a 30-day epoch extracts ~16.4k USDC of unearned interest per epoch, funded by the honest borrower's repayment; if `maxApr` was set to 0 (the documented programmable-mode configuration), the forged rate is uncapped and the attacker's whole deposit can effectively demand arbitrary "interest" limited only by what the borrower funds at `stopEpoch` before reverting. If the borrower cannot fund it, the epoch stop reverts, causing temporary freezing of all pending withdraw receipts. Additionally, an attacker can set APR to a dust value to grief honest LPs' expected yield in the same window.

### Likelihood Explanation
Requirements: a vault deployment/configuration window where `initialize` and `setWhitelistedCDO` are not atomically executed (or are front-runnable on a public mempool), plus the attacker holding a KYC-passing wallet to deposit. Both are realistic: the test harness itself performs `initialize`, `setWhitelistedCDO`, and `setMaxApr` as separate transactions (test/foundry/ProgrammableBorrowerCreditVault.t.sol:129-144), and the code comment acknowledges the unauthenticated setup path. Likelihood is bounded by the size of the deployment window and by the fact that a diligent owner/manager may overwrite APR at each epoch boundary — but nothing forces them to, and the forged `unscaledApr` is self-perpetuating because `startEpoch` reads it back from the strategy rather than from an independent source. Once wired, the bug is no longer exploitable, so impact concentrates on the first epoch(s).

### Recommendation
Remove the `idleCDO == address(0)` bypass: gate `setApr` (and therefore `setAprs`/`setAprsWithBuffer`) behind `msg.sender == owner() || msg.sender == manager` while `idleCDO` is unset, or require `idleCDO` to be passed to `initialize`/`setWhitelistedCDO` atomically so no unauthenticated window exists. At minimum, have `IdleCDOEpochVariant.startEpoch` treat the strategy-reported APR as untrusted and require an explicit manager-set rate per epoch.

### Proof of Concept
Foundry fork PoC sketch (USDC mainnet fork, mirroring `ProgrammableBorrowerCreditVault.t.sol` setup):

```solidity
function testForgedAprBeforeWhitelistedCDO() external {
    // 1. Owner initializes vault but has NOT yet called setWhitelistedCDO
    IdleCreditVault strat = new IdleCreditVault();
    stdstore.target(address(strat)).sig(strat.token.selector).checked_write(address(0));
    strat.initialize(USDC, owner, manager, borrower, "B", 10e18);
    assertEq(strat.idleCDO(), address(0));

    // 2. Attacker EOA pins max APR with no auth
    address attacker = makeAddr("attacker");
    vm.prank(attacker);
    strat.setAprs(20e18, 20e18); // no revert: _cdo == 0 skips the check
    assertEq(strat.unscaledApr(), 20e18);
    assertEq(strat.lastApr(), 20e18);

    // 3. Owner wires CDO afterwards
    cdoEpoch.initialize(0, USDC, address(this), owner, rebalancer, address(strat), 100000);
    vm.prank(owner);
    strat.setWhitelistedCDO(address(cdoEpoch));

    // 4. Attacker deposits AA during buffer; epoch starts and re-scales the forged unscaledApr
    deal(USDC, attacker, 1_000_000e6);
    vm.startPrank(attacker);
    IERC20(USDC).approve(address(cdoEpoch), type(uint256).max);
    cdoEpoch.depositAA(1_000_000e6);
    vm.stopPrank();

    vm.prank(manager);
    cdoEpoch.startEpoch(); // _setScaledApr(_getStrategyApr()) reads attacker-set unscaledApr

    // 5. At stopEpoch the borrower owes interest at forged rate on attacker principal
    vm.warp(cdoEpoch.epochEndDate());
    uint256 owed = cdoEpoch.expectedEpochInterest();
    assertGt(owed, 1_000_000e6 * 20e18 * 30 days / (365 days * 100e18) - 1);
}
```

Uncertainty I could not fully resolve within the iteration limit: whether `IdleCreditVaultFactory` wires `setWhitelistedCDO` atomically in the same transaction as `initialize` in production deployments — if it does, the attack reduces to mempool front-running of that transaction, which is still feasible on mainnet but narrower. The authorization gap itself is unconditional in the code.
