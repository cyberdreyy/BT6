Based on my investigation, the strongest analog to the reported check‑effect‑interaction (CEI) reentrancy bug class in the Solidity report exists in the Chainlink Gateway's HTTP-trigger JWT replay-protection logic.

### Title
JWT single-use replay-protection check-then-act race allows unauthorized duplicate workflow trigger execution - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
`WorkflowMetadataHandler.Authorize()`, invoked by the gateway on every unauthenticated/unprivileged HTTP trigger request before dispatching a workflow execution, checks whether a JWT `jti` (nonce) has already been used, and only marks it used at the very end of the function — after workflow lookup and authorized-key validation succeed. The "check" (`isReplay`) and the "effect" (`recordUsage`) are two separate, non-atomic critical sections guarded independently by `jwtReplayCache.mu`. This mirrors the Solidity finding's root cause exactly: state that should gate a privileged action is updated only *after* other logic completes, leaving a window where a second concurrent call can pass the same check before the first call's effect is committed.

### Finding Description
`Authorize()` performs the following sequence: [1](#0-0) 

1. `claims, signer, err := utils.VerifyRequestJWT(token, *req)` — verifies the JWT signature.
2. `if h.jwtCache.isReplay(claims.ID)` — **check**: looks up `jti` in `jwtReplayCache.cache` under an `RLock`, returns immediately if not found.
3. Workflow/authorized-key lookups (`h.authorizedKeys[workflowID]`).
4. `h.jwtCache.recordUsage(claims.ID)` — **effect**: marks `jti` used, only reached at the very end, under a separate `Lock`.

Because steps 2 and 4 are not part of a single atomic critical section, two concurrent `HandleUserTriggerRequest` calls presenting the *same* signed JWT (same `jti`, same signature — trivially replayable by any external client since the token itself is just replayed bytes, not single-use at the transport level) can both execute `isReplay()` and see "not yet used" before either reaches `recordUsage()`. Both then pass authorization and proceed to trigger the workflow.

This is called directly from the request path reachable by any unprivileged external client hitting the Gateway's HTTP trigger endpoint: [2](#0-1) 

`authorizeRequest` (line 99) calls into `workflowMetadataHandler.Authorize`, gating whether the request proceeds to `sendWithRetries`, which fans the trigger out to all DON nodes and ultimately causes a workflow execution.

### Impact Explanation
A single-use JWT is meant to strictly bound a workflow trigger to one execution (the code and its tests explicitly assert single-use semantics — see `TestHttpTriggerHandler_HandleUserTriggerRequest` "duplicate JWT token and request ID" sub-test, which checks that a *sequential* second use is rejected with `"token has already been used"`): [3](#0-2) 

That test, however, only proves rejection for **sequential** replays; it does not cover concurrent/racing replays, which is exactly the class of behavior the external report calls out. If two identical requests are sent in parallel (trivial for an unprivileged client — no additional secrets or state are required beyond re-sending the exact same HTTP body/JWT twice), both can bypass the "already used" guard and cause the DON to execute the workflow twice with the same signed authorization. Depending on the workflow's action (e.g. one that moves funds, submits a transaction, or performs a non-idempotent external side effect), this results in an unauthorized duplicate job run/execution — matching the "unauthorized job run" acceptance criterion.

### Likelihood Explanation
Likelihood is high for any unprivileged actor with a single valid signed HTTP-trigger JWT: they merely need to send the same signed request twice concurrently (e.g. two parallel HTTP POSTs), which requires no additional privilege, secret material, or protocol knowledge beyond what a legitimate single caller already possesses. No network-layer or node-compromise assumptions are needed — this is a pure request-race exploitable at the ingress HTTP layer.

### Recommendation
Make replay-check-and-record atomic: acquire the `jwtReplayCache` write lock once, and perform the "already used" check and the "mark used" write inside the same critical section (i.e., collapse `isReplay` + `recordUsage` into a single `CheckAndRecord` method) before any downstream workflow dispatch logic runs, so a second concurrent caller with the same `jti` is rejected regardless of timing, following check-effect ordering under one lock.

### Proof of Concept
1. Obtain/craft one valid signed workflow trigger JWT with `jti = X` for an authorized signer.
2. Fire two (or more) concurrent `HandleUserTriggerRequest` calls to the gateway with the identical JWT/request payload.
3. Both goroutines call `Authorize()`; both execute `h.jwtCache.isReplay(X)` before either has called `h.jwtCache.recordUsage(X)`, since these are separate lock acquisitions with unrelated logic (workflow lookup, key comparison) executing in between.
4. Both requests pass authorization and are forwarded via `sendWithRetries` to the DON, resulting in two workflow executions from a single-use token — analogous to the Solidity report's `initId`/`_limitOrders` being set based on stale pre-reentrancy state due to the effect (state update) occurring after other logic instead of atomically with the check. func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

		return err
	}
