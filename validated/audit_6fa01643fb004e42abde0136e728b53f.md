### Title
Unregistered/opt-out beneficiary permanently blocks all commission and staker withdrawals in `staking_contract`'s shared `distribution_pool` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` pays out every pending entry in a `staking_contract`'s single `distribution_pool` in one atomic loop, using `aptos_account::deposit_coins` for each recipient. If any one recipient in that shared pool cannot accept the deposit, the whole transaction aborts, and — unlike the OrderBook cyclic buffer — every future call to `distribute`, `request_commission`, `unlock_stake`, and `switch_operator` for that staker/operator pair hits the exact same recipient and aborts again, indefinitely.

### Finding Description
`distribute_internal` withdraws all inactive/pending_inactive stake at once and then loops over every shareholder recorded in `staking_contract.distribution_pool`, sending funds via `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the target account exists, is not yet registered for the coin type, and has opted out of direct transfers via `can_receive_direct_coin_transfers`: [2](#0-1) 

Any account can call `set_allow_direct_coin_transfers(false)` on itself at any time — an entirely unprivileged action: [3](#0-2) 

Critically, `set_beneficiary_for_operator` lets an operator redirect commission payouts to an arbitrary address **without any registration or acceptance check**, unlike `vesting::set_beneficiary`, which explicitly calls `assert_account_is_registered_for_apt`: [4](#0-3) [5](#0-4) 

`unlock_stake`, `switch_operator`, and `request_commission` all call `distribute_internal` first "for accounting simplicity" before doing anything else, and always pay the operator's commission ahead of the staker's own withdrawal: [6](#0-5) [7](#0-6) 

Because `distribution_pool` is shared by the operator's commission entry and the staker's withdrawal entry, and every entry-point that could ever drain it (`distribute`, `request_commission`, `unlock_stake`, `switch_operator`) processes them together in one atomic loop, a single unpayable recipient (the operator's own beneficiary address) makes the entire pool permanently stuck — exactly the OrderBook pattern of "one broken/unclaimable slot blocks the whole shared queue," except here there is no cyclic-buffer overwrite escape hatch at all; the same poisoned entry is retried on every single call, forever.

### Impact Explanation
An operator (unprivileged relative to the staker's stake) can:
1. Call `set_beneficiary_for_operator` to point commission payouts at an address they control.
2. Have that address call `set_allow_direct_coin_transfers(false)` (or simply never register for `AptosCoin`).
3. From then on, any commission accrual makes `distribute_internal` abort whenever it tries to pay that beneficiary — and since `unlock_stake`, `switch_operator`, and `request_commission` all invoke `distribute_internal` before doing their own work, **the staker's own withdrawal of principal and rewards becomes permanently blocked** as long as the operator keeps the beneficiary in that non-accepting state.

This matches the required impact "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows" and "Operator commission, beneficiary payout... corruption that... traps value." The staker's stake remains locked in the underlying stake pool (inactive/pending_inactive) with no way to retrieve it via the `staking_contract` module while the operator withholds cooperation — a griefing/hostage vector over funds not owned by the operator.

### Likelihood Explanation
High. Both prerequisite actions (`set_beneficiary_for_operator`, `set_allow_direct_coin_transfers`) are permissionless entry functions requiring no special privilege beyond being the operator of an existing `staking_contract` — a role any operator legitimately holds. No cliff, minimum stake, or special timing is required; a malicious or coerced operator can trigger this at will and hold it indefinitely.

### Recommendation
- In `staking_contract::set_beneficiary_for_operator`, require the new beneficiary to be registered/willing to receive `AptosCoin`, mirroring `vesting::set_beneficiary`'s `assert_account_is_registered_for_apt` check.
- In `distribute_internal`, do not let one recipient's failed deposit block the rest of the pool: catch/skip failures per-recipient (e.g., route unpayable amounts to a claimable "stuck funds" balance) instead of aborting the whole atomic loop, so a poisoned or opted-out recipient cannot hold every other shareholder's funds hostage.

### Proof of Concept
1. Staker creates a `staking_contract` with `operator` and stakes funds; validator earns rewards.
2. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, controlled_addr)` where `controlled_addr` is a fresh, unregistered account.
3. `controlled_addr` calls `aptos_account::set_allow_direct_coin_transfers(&controlled_addr_signer, false)`.
4. `staking_contract::request_commission` is called (by anyone) once commission accrues → `distribute_internal` tries `aptos_account::deposit_coins(controlled_addr, ...)` → aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. Staker calls `unlock_stake` to withdraw their own principal → same `distribute_internal` call path aborts identically, so the staker's withdrawal never succeeds while `controlled_addr` keeps opting out — this can be repeated indefinitely with no time-bound cyclic-buffer recovery, unlike the original OrderBook bug.

Note: I was not able to fully trace `add_distribution`/`update_distribution_pool` line-by-line implementation (search tooling returned only match counts, not content, in the final iteration) to confirm whether a commission entry is created even for `commission_amount == 0`; this does not affect the core finding since any nonzero commission accrual (which happens automatically from staking rewards) is sufficient to trigger the block.

    public entry fun set_beneficiary_for_operator(

    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.

        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
