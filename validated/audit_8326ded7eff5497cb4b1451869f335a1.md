### Title
Timeout-freed validation slot is stolen by the newest proposal instead of draining the FIFO pending queue, permanently starving a validly-queued block - (File: stacks-signer/src/v0/signer.rs)

### Summary
`check_submitted_block_proposal` frees `submitted_block_proposal` on timeout but never drains `block_validations_pending`; the only code that submits a *queued* proposal is `check_pending_block_validations`, called solely from `handle_block_validate_response`. Because `handle_block_proposal` unconditionally submits the *currently arriving* proposal itself as soon as it sees `submitted_block_proposal.is_none()`, a miner who keeps timing new proposals to arrive right after each timeout can perpetually re-occupy the single validation slot, leaving an earlier, legitimately queued block permanently stuck in the pending table.

### Finding Description
The equality that should hold is: every valid block proposal is eventually submitted for node validation within a bounded number of timeout cycles (FIFO fairness via `block_validations_pending`, ordered by `added_time`).

The actual code path breaks this:
- `handle_block_proposal` (stacks-signer/src/v0/signer.rs:1681-1714) calls `self.check_submitted_block_proposal()` and then, if `self.submitted_block_proposal.is_none()`, submits the *current* proposal directly via `submit_block_for_validation`, without ever consulting `block_validations_pending`. [1](#0-0) 
- Only if the slot is busy does the current proposal go into the FIFO queue via `insert_pending_block_validation`. [2](#0-1) 
- The queue is drained strictly FIFO by `check_pending_block_validations`, which pulls the oldest entry via `get_and_remove_pending_block_validation` (`ORDER BY added_time ASC`). [3](#0-2) [4](#0-3) 
- Critically, `check_pending_block_validations` is invoked only from `handle_block_validate_response`, i.e. only after the node actually answers a submitted validation. [5](#0-4) 
- `check_submitted_block_proposal`, which fires on a **timeout** (no node answer ever received), simply frees the slot and marks the timed-out block locally rejected — it never calls `check_pending_block_validations` to drain the queue. [6](#0-5) 

Consequently, after a timeout, the freed slot is up for grabs, and whichever *new* proposal happens to arrive next (via `handle_block_proposal`) grabs it for itself instead of the older queued entry. An attacker who wins one miner slot can broadcast a stream of distinct-but-plausible block proposals (B1, B2, B3, …) at the same height, each engineered so node validation never completes before `block_proposal_validation_timeout` elapses (e.g., referencing a parent that resolves slowly). By timing each new proposal's arrival to land immediately after the prior one's timeout, the attacker's own proposal always wins `submitted_block_proposal.is_none()` race in `handle_block_proposal`, while an honest B0 that got queued earlier via `insert_pending_block_validation` (stacks-signer/src/v0/signer.rs:1709-1713) is never drained, because the only drain path requires an actual `BlockValidateResponse`, which never fires for the attacker's stalled submissions.

### Impact Explanation
This breaks the bounded-liveness guarantee: a legitimately valid block proposal can be wedged indefinitely in `block_validations_pending`, never submitted to the node, never validated, and never signed by this signer — matching the High-severity liveness category ("a signer wedged into never signing valid blocks"). The bug is repeatable indefinitely as long as the attacker retains a miner slot and can keep timing proposal submissions relative to `block_proposal_validation_timeout`.

### Likelihood Explanation
Preconditions: attacker needs one won miner slot (to sign block proposals) and gossip access to submit StackerDB chunks — both already assumed unprivileged capabilities. The attacker needs reasonably precise timing control (submit each next proposal shortly after `block_proposal_validation_timeout` elapses for the previous one), which is feasible since the attacker fully controls submission timestamps and `block_proposal_validation_timeout` is a known, generally static config value (default 120s). No majority of signers, no compromised keys, no auth_token needed — this only affects a single signer's local slot-management logic, but since every signer independently runs this same logic against the same gossip stream, the attack affects all signers simultaneously and is fully repeatable.

### Recommendation
In `check_submitted_block_proposal`, after freeing the slot on timeout, immediately call `check_pending_block_validations` (or equivalent) to drain and submit the oldest queued proposal before any newly-arriving proposal in `handle_block_proposal` is allowed to claim the freed slot. Alternatively, in `handle_block_proposal`, before submitting the *current* proposal directly, first check whether `block_validations_pending` is non-empty and if so enqueue the current proposal and drain the oldest pending entry instead, preserving strict FIFO order.

### Proof of Concept
Rust test plan (stacks-signer unit/integration test driving `Signer` state machine directly, mirroring existing tests like `block_validation_pending_table`):
1. Construct a `Signer` with a short `block_proposal_validation_timeout` (e.g. 2s) and a stub `StacksClient` that always accepts submission but never returns a response (simulating stall).
2. Craft `BlockProposal` B0 (a valid, honest block at height h) and call `handle_block_proposal(B0)` while `submitted_block_proposal` is already occupied by a prior stalled proposal A — assert B0 lands in `block_validations_pending` via `signer_db.has_pending_block_validation(&B0_sighash)`.
3. Sleep past `block_proposal_validation_timeout`; craft B1 (a new proposal at the same height/tenure, distinct sighash, engineered to also stall) and call `handle_block_proposal(B1)`.
4. Assert: (a) `check_submitted_block_proposal` freed the slot for A (A is now `LocallyRejected`/rejected via `ConnectivityIssues`), and (b) `submitted_block_proposal` is now `Some(B1_sighash, _)` — i.e., B1 stole the slot — while `signer_db.has_pending_block_validation(&B0_sighash)` is still `true`.
5. Repeat steps 3-4 for B2, B3, … N cycles.
6. Assert that after N cycles (bounded, e.g. 10), B0 is *never* submitted (`submitted_block_proposal` never equals `Some(B0_sighash, _)`), demonstrating the wedge: B0 remains in the pending table indefinitely while newer attacker proposals keep winning the slot.

    /// Check the current tracked submitted block proposal to see if it has timed out.
    /// Broadcasts a rejection and marks the block locally rejected if it has.
    fn check_submitted_block_proposal(&mut self) {
        let Some((proposal_signer_sighash, block_submission)) =
            self.submitted_block_proposal.take()
        else {
            // Nothing to check.
            return;
        };
        if block_submission.elapsed() < self.block_proposal_validation_timeout {
            // Not expired yet. Put it back!
            self.submitted_block_proposal = Some((proposal_signer_sighash, block_submission));
            return;
        }
        // For mutability reasons, we need to take the block_info out of the map and add it back after processing
        let mut block_info = match self.signer_db.block_lookup(&proposal_signer_sighash) {
            Ok(Some(block_info)) => {
                if block_info.has_reached_consensus() {
                    // The block has already reached consensus.
                    return;
                }
                block_info
            }
            Ok(None) => {
                // This is weird. If this is reached, its probably an error in code logic or the db was flushed.
                // Why are we tracking a block submission for a block we have never seen / stored before.
                error!("{self}: tracking an unknown block validation submission.";
                    "signer_signature_hash" => %proposal_signer_sighash,
                );
                return;
            }
            Err(e) => {
                error!("{self}: Failed to lookup block in signer db: {e:?}",);
                return;
            }
        };
        // We cannot determine the validity of the block, but we have not reached consensus on it yet.
        // Reject it so we aren't holding up the network because of our inaction.
        warn!(
            "{self}: Failed to receive block validation response within {} ms. Rejecting block.", self.block_proposal_validation_timeout.as_millis();
            "signer_signature_hash" => %proposal_signer_sighash,
        );
        let rejection = self.create_block_rejection(
            RejectReason::ConnectivityIssues(
                "failed to receive block validation response in time".to_string(),
            ),
            &block_info.block,
        );
        block_info.reject_reason = Some(rejection.response_data.reject_reason.clone());
        if let Err(e) = block_info.mark_locally_rejected() {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally rejected: {e:?}");
            }
        };
        self.send_block_response(&block_info.block, rejection.into());

        self.signer_db
            .insert_block(&block_info)
            .unwrap_or_else(|e| self.handle_insert_block_error(e));
    }

    pub fn get_and_remove_pending_block_validation(
        &self,
    ) -> Result<Option<(Sha512Trunc256Sum, u64)>, DBError> {
        let qry = "DELETE FROM block_validations_pending WHERE signer_signature_hash = (SELECT signer_signature_hash FROM block_validations_pending ORDER BY added_time ASC LIMIT 1) RETURNING signer_signature_hash, added_time";
        let args = params![];
        let mut stmt = self.db.prepare(qry)?;
        let result: Option<(String, i64)> = stmt
            .query_row(args, |row| Ok((row.get(0)?, row.get(1)?)))
            .optional()?;
        Ok(result.and_then(|(sighash, ts_i64)| {
            let signer_sighash = Sha512Trunc256Sum::from_hex(&sighash).ok()?;
            let ts = u64::try_from(ts_i64).ok()?;
            Some((signer_sighash, ts))
        }))
    }
