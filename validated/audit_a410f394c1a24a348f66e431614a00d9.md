### Title
Stale Confirmations From Removed Multisig Members Count Toward Execution Threshold - (`multisig2/src/lib.rs`)

### Summary
`delete_member` only purges pending requests *authored* by the removed member; it does not scrub that member's confirmations recorded on requests authored by *other* members. `confirm` later counts these stale confirmations toward `num_confirmations`, letting a request execute even though fewer live members actually confirmed it than the threshold requires.

### Finding Description
When a request is created with `add_request`, it is stored keyed by the creating `member`, and an empty confirmation set is created for it: [1](#0-0) 

Any current member (not necessarily the creator) can later call `confirm`, which inserts their identity string into the request's `confirmations` set and executes the request once the set size reaches `num_confirmations`: [2](#0-1) 

When a member is removed via `delete_member`, the code only removes *requests whose `member` field equals the removed member* (i.e., requests that member created) and clears confirmations for those specific requests: [3](#0-2) 

It never scans other members' pending requests to strip a removed member's confirmation entries from their `confirmations` sets. Since `assert_valid_request` only checks that the *caller* is currently a member, and never re-validates the *existing* entries in a stored confirmations set: [4](#0-3) 

a confirmation given while a member was still valid remains permanently counted toward the threshold on any request they didn't author, even after that member is removed from the multisig.

The custody binding broken is: `confirmations counted == confirmations from currently-live members`. After a member removal, this becomes `confirmations counted > confirmations from currently-live members`, because a stale entry from a removed member still occupies a slot in the set used by the `>= self.num_confirmations` check.

### Impact Explanation
This lets a request execute (including `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, etc.) with genuine confirmations from *fewer* live members than `num_confirmations` requires — i.e., "a multisig request executed below threshold," which is explicitly a Critical impact. Concretely, NEAR can be transferred out of the multisig account with only one live member actually approving a 2-of-3 request, because a second, now-removed member's old confirmation is still silently counted.

### Likelihood Explanation
This requires only the ordinary sequence of multisig operations already supported by the contract: (1) a member confirms a pending, not-yet-executed request created by someone else, (2) that confirming member is later removed via a normal `DeleteMember` request, and (3) any remaining member confirms the still-pending request to complete it. No malicious code deployment, foundation privilege, or external key compromise is needed — it is a direct consequence of `delete_member`'s incomplete cleanup logic and can occur even accidentally in normal multisig operation, e.g. member rotation on a multisig holding pending transfer requests.

### Recommendation
When removing a member in `delete_member`, iterate over all pending requests' confirmation sets (not just requests authored by the removed member) and remove the departing member's confirmation entry from each. Alternatively, when checking the threshold in `confirm`, filter the stored confirmations against the current `self.members` set before comparing against `num_confirmations`, so stale confirmations from removed members never count.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `B` calls `add_request` with a `Transfer` request `R` to some `receiver_id` (not auto-confirmed) — `confirmations[R] = {}`.
3. `A` calls `confirm(R)` — `confirmations[R] = {A}` (below threshold, request stays pending) — see `confirm` at [2](#0-1) .
4. `B` and `C` jointly pass a separate `DeleteMember { member: A }` request (2-of-3 reached normally), which calls `delete_member`. Because `R.member == B` (not `A`), `R`'s confirmations are left untouched — see filter at [5](#0-4) . `A` is now removed from `self.members` and can no longer call any multisig method.
5. `C` calls `confirm(R)` — `confirmations[R]` becomes `{A, C}`, size 2 `>= num_confirmations (2)`, so `R` executes and the transfer promise is scheduled — even though only `C`, a single live member, actually approved it after `A`'s removal.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
