### Title
Pre-finalization par claim of defaulted-epoch withdraw receipts double-counts claim basis and drains the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimWithdrawRequest` lets a user claim a withdraw receipt at par as soon as `epochNumber > lastWithdrawRequest`, even when the epoch that funded it ended in a borrower default and `finalizeDefaultRecovery` has not run yet. Because `_claimFundedWithdrawRequest` pays from the vault's underlying balance without decrementing `pendingWithdraws` or marking the per-epoch receipt consumed for default accounting, the same claim basis is then counted a second time inside `defaultPendingClaimBasis()` during `finalizeDefaultRecovery`. The result is a stale-state reuse analog of CVE-2019-11940's corrupted-table use-after-free: a receipt that was already "freed" (paid at par) is still referenced by the default-recovery accounting, inflating `totalBasis`, diluting `defaultRecoveryPrice`, and paying the attacker twice for one receipt.

### Finding Description
In `requestWithdraw`, a normal request increments `pendingWithdraws`, records `withdrawsRequestsByEpoch[user][epochNumber]`, mints receipt strategy tokens, and sets `lastWithdrawRequest[user]` [1](#0-0) .

`claimWithdrawRequest` routes to `_claimFundedWithdrawRequest` whenever `defaultRecoveryFinalized` is false, and the only temporal check is `epochNumber <= lastWithdrawRequest[_user]` [2](#0-1) . A borrower default at `stopEpoch` increments `epochNumber` without funding `pendingWithdraws`, so that check passes immediately after the defaulting stop. `_claimFundedWithdrawRequest` then burns the receipt and calls `_transferFundedClaim`, paying par from vault-held underlying — which exists when instant-withdraw prefunding was collected via `collectInstantWithdrawFunds` or earlier funded receipts' underlyings sit in the vault [3](#0-2) [4](#0-3) .

Crucially, the funded-claim path never reduces `pendingWithdraws` and never clears `withdrawsRequestsByEpoch`. When `finalizeDefaultRecovery` later runs, `defaultPendingClaimBasis()` still includes the attacker's already-paid basis via `pendingWithdraws`, so the recovered funds are split over an inflated `totalBasis` [5](#0-4) . Neither `IdleCDOEpochVariant.claimWithdrawRequest` nor the strategy claim path checks `cdo.defaulted()` before the par payout [6](#0-5) .

### Impact Explanation
The attacker (any KYC-passed lender with a pending withdraw receipt in the defaulted epoch) is paid 100% at par from vault-held underlying, while their claim basis remains inside `pendingWithdraws`. Finalization then spreads the real recovery over the inflated basis, lowering `defaultRecoveryPrice` for every other defaulted receipt holder and active LP. The stolen amount equals the attacker's par payout minus their pro-rata recovery share, up to the full prefunded/vault balance; losses to honest users scale with the fraction of `pendingWithdraws` claimed pre-finalization. This is direct theft plus permanent dilution of the default recovery reserve.

### Likelihood Explanation
Requires only: an unclaimed withdraw receipt in the epoch that defaults, and underlying liquidity parked in the vault (instant-withdraw prefunding or other funded claims) — both routine states. The window between the defaulting `stopEpoch` and the manager's `finalizeDefaultRecovery` call is the exploit window; since claims are permissionless, the attacker can race finalization. No privileged cooperation needed.

### Recommendation
Gate the par-claim path on the CDO's default state: in `claimWithdrawRequest`/`_claimFundedWithdrawRequest`, revert or defer to recovery accounting when `IIdleCDOEpochVariant(idleCDO).defaulted()` is true and `defaultRecoveryFinalized` is false. Alternatively, have `_claimFundedWithdrawRequest` decrement `pendingWithdraws` and clear `withdrawsRequestsByEpoch` so pre-finalization par claims cannot be double-counted by `defaultPendingClaimBasis`.

### Proof of Concept
Foundry fork PoC sketch:

1. Deposit underlying via `depositAA`; `startEpoch`; `stopEpoch` normally to reach epoch N buffer.
2. Attacker calls `cdoEpoch.requestWithdraw(amount, AAtranche)` → `IdleCreditVault.requestWithdraw` mints receipt, `pendingWithdraws += amount`, `lastWithdrawRequest = N`.
3. Also create an instant withdraw request so `collectInstantWithdrawFunds` pulls underlying into the vault at `startEpoch` (funding source).
4. Warp past `epochEndDate`; borrower repays nothing → `stopEpoch` defaults; `epochNumber` becomes N+1.
5. Before `finalizeDefaultRecovery`, attacker calls `cdoEpoch.claimWithdrawRequest()` → `_claimFundedWithdrawRequest` passes (`N+1 > N`), burns receipt, transfers `amount` underlying at par.
6. Manager calls `finalizeDefaultRecovery(recovered, source)` → `defaultPendingClaimBasis()` still includes the attacker's `amount` in `pendingWithdraws`; `defaultRecoveryPrice = reserve * RECOVERY_FULL / inflatedBasis` is diluted; honest users' `claimWithdrawRequest`/`DefaultDistributor.claim` payouts are reduced by the attacker's double-counted share.

Note: I verified the claim path and accounting in `IdleCreditVault.sol`, but could not fully confirm in this session that no higher-level guard in `stopEpoch`/`_handleBorrowerDefault` blocks claims during the default window; the PoC hinges on that window being open, which the code shown (`claimWithdrawRequest` has no `defaulted()` check) supports.

  function claimWithdrawRequest(address _user) external returns (uint256 amount) {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized) {
      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);

  /// @notice Finalize strategy-side default recovery accounting.
  /// @dev Called by the CDO. `_recoverySource` must approve this strategy for `_recoveredAmount`.
  /// `_recoveredAmount` is the exact external recovery to pull; already-held strategy funds
  /// are added separately because they should not be pulled from `_recoverySource` again.
  /// A zero or subprecision aggregate recovery finalizes at price zero. Active tranche prices are
  /// then zero and pending receipts can be cleared without a payout; any positive reserve too small
  /// to represent at `RECOVERY_FULL` precision remains isolated as recovery dust.
  /// @param _recoveredAmount exact amount of recovered underlying supplied by `_recoverySource`
  /// @param _recoverySource address that supplies recovered underlying
  /// @return defaultBBNav BB's final recovered active NAV
  function finalizeDefaultRecovery(uint256 _recoveredAmount, address _recoverySource) external returns (uint256 defaultBBNav) {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    if (defaultRecoveryFinalized || !cdo.defaulted()) revert NotAllowed();
    if (_recoveredAmount != 0 && _recoverySource == address(0)) revert NotAllowed();

    // Active holders are still represented by strategy tokens owned by the CDO. Add the
    // default-epoch net interest so they use the same claim basis as pending redeemers.
    // Split gross backing by saved NAV and default interest by the configured APR split.
    // The CDO strategy-token balance is its gross active value before `unclaimedFees`.
    // Using it directly restores those waived unpaid fees to active recovery basis.
    uint256 activeBalance = balanceOf(idleCDO);
    uint256 activeInterest = _defaultActiveInterestBasis(cdo);
    uint256 activeBasis = activeBalance + activeInterest;
    defaultBBNav = _defaultBBBasis(cdo, activeBalance, activeInterest);
    // Pending receipts have already left active CDO NAV, so they are added as a separate basis.
    uint256 pendingBasis = defaultPendingClaimBasis();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (totalBasis == 0) revert NotAllowed();

    // Some recovery funds may already be in this strategy: partially prefunded instant requests
    // and borrower-send funds that failed at epoch start. Count both without pulling them again.
    uint256 prefundedReserve = _defaultPrefundedInstantReserve();
    uint256 reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve;
    // Recovery can be above par if the recovered funds exceed the computed basis.
    uint256 recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis;

    defaultRecoveryFinalized = true;
    defaultRecoveryReserve = reserveAmount;
    defaultRecoveryPrice = recoveryPrice;
    defaultRecoveryEpoch = epochNumber;
