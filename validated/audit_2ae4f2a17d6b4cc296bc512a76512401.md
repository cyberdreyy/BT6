### Title
Transaction-replay enforcement after a Bitcoin fork is silently disabled by default (`validate_with_replay_tx = false`), letting a miner get a post-reorg block signed while skipping the consensus-mandated replay set - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The signer's post-Bitcoin-reorg transaction-replay guard is gated entirely on the local config flag `validate_with_replay_tx`, which defaults to `false`. Even when the signer's own state machine (and the network's global consensus view) has computed a non-empty `tx_replay_set` that MUST be replayed before new transactions are mined, the signer never forwards that replay set to the node for the `/v3/block_proposal` validation call unless the operator manually opts in. The node-side enforcement (`validate_replay` in `postblock_proposal.rs`) is a no-op whenever `replay_txs` is `None`, so with the shipped default the "signed" (accepted-for-mining) proposal and the "consensus-required" (replay-obligated) proposal diverge: the signer signs a block that the network's own replay-set consensus says should have been rejected.

### Finding Description
`GlobalConfig`/`SignerConfig` carries `validate_with_replay_tx: Option<bool>` with default `DEFAULT_VALIDATE_WITH_REPLAY_TX = false` (documented as `@default: false`, "Experimental feature") [1](#0-0) . This value ships as the commented-out default in the reference mainnet config as well [2](#0-1) .

At the same time, the signer's own local/global state machine actively tracks and computes a `tx_replay_set` (`ReplayTransactionSet`) representing the transactions from orphaned tenures that a Bitcoin reorg requires to be replayed before new user transactions may be mined [3](#0-2) . This set is derived via majority/consensus coalescing across signers [4](#0-3)  and is threaded into the local per-signer view during burn-block advancement [5](#0-4) .

However, when the signer actually submits a block proposal to its node for the authoritative validity check, it only attaches the replay set if `self.validate_with_replay_tx` is `true`; otherwise it passes `None`: [6](#0-5) 

On the node side, `validate_replay` is the sole enforcement point for the replay set, and it short-circuits immediately to "no replay obligation" (`Ok(false)`, i.e., no rejection) whenever `self.replay_txs` is `None`: [7](#0-6) 

There is no other local, pre-submission gate in the signer that independently enforces the replay set before deciding to sign — the pre-validation checks (`check_block_against_state` / chainstate `check_proposal` in v1/v2) reference protocol-version consensus, static validity, and problematic-transaction filters, but no `tx_replay_set` cross-check was found gating submission. The signer only "trusts" the node's Ok/Reject verdict once submitted (`determine_response` and the validation-response handlers), so if the node was never told about the required replay set, its `Ok` verdict is taken at face value and the signer proceeds to sign: [8](#0-7) [9](#0-8) 

The severity of skipping this check is demonstrated by the existing integration test, which shows that with `validate_with_replay_tx = true`, a miner proposal omitting the mandated replay transactions is globally rejected with `ValidateRejectCode::InvalidTransactionReplay`: [10](#0-9) 

With the shipped default (`false`), that same proposal is never checked for replay-set compliance at all, and the node's validation logic path that would reject it (`postblock_proposal.rs` replay loop that returns `InvalidTransactionReplay` on missing/mismatched txs) is never invoked [11](#0-10) .

### Impact Explanation
This breaks the "signed-block equals validated-block" equality that the signer's design otherwise strictly preserves (`signer_waits_for_validation_before_signing` documents this invariant). Because `validate_with_replay_tx` defaults to `false` for every signer that has not explicitly opted in, the network-wide replay-set consensus derived by the signer state machine is effectively unenforced at the one place that matters — the node validation call that gates signing. A miner that skips or reorders the mandated replay transactions after a Bitcoin fork can get its proposal validated as "Ok" (since the node was never given a replay set to check against) and subsequently signed and accepted, even though the signer network's own consensus state considered that transaction-replay obligation active. This matches the "Critical" bucket in the rules: a signer signing a block that violates a consensus-mandated ordering/replay obligation (i.e., a non-canonical-per-protocol-consensus block from the network's own point of view), triggerable purely by a one-slot miner controlling block contents/ordering after a reorg, requiring no majority of signers and no key compromise.

### Likelihood Explanation
High. `validate_with_replay_tx` is off by default in both the code default (`stacks-signer/src/config.rs`) and the reference/mainnet sample config that operators are expected to copy from (`sample/conf/signer/mainnet-signer-conf.toml`). The feature is explicitly labeled "Experimental," which strongly suggests it is not universally enabled across the live signer set. Any signer running with the unmodified default silently drops replay enforcement for every block it validates and signs, and this requires no attacker action beyond normal miner behavior (proposing a block after a Bitcoin reorg while ignoring the expected replay set) — exactly the "one-slot miner (plus gossip)" trigger class described.

### Recommendation
- Make replay-set enforcement mandatory whenever the signer's own state machine has a non-empty `tx_replay_set`, independent of the `validate_with_replay_tx` toggle — i.e., always forward `self.global_state_evaluator.get_global_tx_replay_set()` to `submit_block_for_validation` when it is non-empty, rather than gating the entire mechanism behind an opt-in flag.
- Alternatively, add a local pre-submission check in the signer (mirroring `check_block_against_state`) that rejects/holds any proposal whose transactions do not honor the locally-known `tx_replay_set`, so that a node-side toggle cannot silently disable a network-consensus-relevant safety property.
- If the flag is to remain, change its default to `true` (secure-by-default) and require explicit opt-out, consistent with the "deny by default" principle highlighted by the referenced CVE.

### Proof of Concept
1. Configure a majority of signers with the default config (`validate_with_replay_tx` unset ⇒ `false`).
2. Trigger a Bitcoin reorg that orphans a tenure containing a user transaction, causing the signer state machine to establish a non-empty `tx_replay_set` (as exercised in `stacks-node/src/tests/signer/v0/tx_replay.rs`).
3. Have the miner propose the next block WITHOUT including the required replay transactions (i.e., skip/reorder them), analogous to the `TEST_EXCLUDE_REPLAY_TXS` fault-injection path exercised by `tx_replay_reject_invalid_proposals_during_replay`.
4. Because each signer's `submit_block_for_validation` call passes `replay_txs: None` (since `validate_with_replay_tx == false`), the node's `validate_replay` returns `Ok(false)` immediately without checking replay-set compliance, so the block validates successfully [12](#0-11) .
5. The signer treats the node's `Ok` verdict as valid, proceeds to pre-commit and sign it — a block that, under the flag-enabled configuration, would have been globally rejected with `ValidateRejectCode::InvalidTransactionReplay` as demonstrated in the existing test at `stacks-node/src/tests/signer/v0/tx_replay.rs:402-421`.
