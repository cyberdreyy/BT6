### Title
Unprotected `initializeConfig` on `BridgeCommittee` Allows Any Caller to Inject a Malicious Config, Permanently Misconfiguring the Bridge - (File: `bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig()` carries no access-control modifier. Any externally-owned account can call it in the window between the proxy deployment and the deployer's own call, permanently pointing the committee at an attacker-controlled `BridgeConfig`. Because the guard only prevents a second call (`config == address(0)`), the slot is write-once and cannot be corrected without a full committee-signed upgrade of `BridgeCommittee` itself.

---

### Finding Description

`BridgeCommittee` is deployed and initialized in two separate on-chain transactions. The first transaction calls `initialize()` (committee members + stake). The second transaction calls `initializeConfig()` to bind the `BridgeConfig` contract.

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  lines 63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

There is no `onlyOwner`, no `initializer`, and no deployer-address check. The sole guard is the zero-address check, which only prevents a *second* call — it does nothing to prevent a *first* call from an attacker who races the deployer.

The production deploy script confirms the two-transaction gap:

```solidity
// bridge/evm/script/deploy_bridge.s.sol  lines 124-178
address bridgeCommittee = Upgrades.deployUUPSProxy("BridgeCommittee.sol", ...);  // tx 1
address bridgeConfig    = Upgrades.deployUUPSProxy("BridgeConfig.sol",    ...);  // tx 2
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));         // tx 3  ← front-runnable
```

Between tx 1 and tx 3, any caller can execute:

```
BridgeCommittee(bridgeCommittee).initializeConfig(address(maliciousConfig));
```

After that, the deployer's tx 3 reverts with `"BridgeCommittee: Config already initialized"`, and the committee is permanently bound to the attacker's config.

---

### Impact Explanation

Every downstream bridge operation reads `committee.config()`:

- `SuiBridge.transferBridgedTokensWithSignatures()` calls `committee.config().tokenAddressOf(tokenID)` and `committee.config().chainID()` to validate and route token unlocks.
- `BridgeLimiter.recordBridgeTransfers()` calls `committee.config().tokenAddressOf()` and `committee.config().tokenPriceOf()` to compute USD value and enforce the rolling-window limit.

A malicious `BridgeConfig` can:

1. **Permanent fund lock** — return `address(0)` for all `tokenAddressOf()` calls, causing every `transferBridgedTokensWithSignatures()` to revert at `"SuiBridge: Unsupported token"`. All tokens already deposited in `BridgeVault` become permanently inaccessible.
2. **Limiter bypass / illegitimate unlock** — return `tokenPriceOf(tokenID) = 1` (minimum USD value) so `willAmountExceedLimit` never triggers, allowing the attacker to drain the vault in a single committee-signed transfer message.
3. **Chain-ID spoofing** — return `isChainSupported(x) = true` for arbitrary chain IDs, bypassing the `onlySupportedChain` guard and enabling cross-chain replay.

The `upgradeWithSignatures()` path in `CommitteeUpgradeable` does not read `config` (it only calls `verifySignatures()` which uses stake mappings), so the committee can eventually upgrade `BridgeCommittee` to fix the slot — but only after collecting a quorum of committee signatures, which takes time and leaves the bridge broken in the interim.

---

### Likelihood Explanation

The attack requires only:
1. Watching the mempool for the `BridgeCommittee` proxy deployment transaction.
2. Deploying a malicious `BridgeConfig` (any contract implementing `IBridgeConfig`).
3. Calling `initializeConfig(maliciousConfig)` before the deployer's follow-up transaction lands.

This is a standard front-run pattern. MEV infrastructure on Ethereum mainnet makes it trivially automatable. No privileged role, no committee membership, and no special knowledge beyond reading the deployment script is required.

---

### Recommendation

Remove the two-transaction gap by passing the `BridgeConfig` address directly into `initialize()` and deleting the separate `initializeConfig()` entry point:

```solidity
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // ← add this
) external initializer {
    __CommitteeUpgradeable_init(address(this));
    __UUPSUpgradeable_init();
    // ... existing stake setup ...
    require(_config != address(0), "BridgeCommittee: zero config");
    config = IBridgeConfig(_config);
}
```

If the circular dependency (committee needs config address, config needs committee address) prevents this, use a factory contract that deploys both in a single transaction and calls `initializeConfig()` atomically — exactly the factory-pattern remedy recommended in the external report.

As a minimum fix, add an `onlyDeployer` guard (set `deployer = msg.sender` in the constructor of the implementation, before `_disableInitializers()`) and restrict `initializeConfig()` to that address.

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "../contracts/BridgeCommittee.sol";
import "../contracts/interfaces/IBridgeConfig.sol";

contract MaliciousConfig is IBridgeConfig {
    // Returns address(0) for every token → "SuiBridge: Unsupported token" on every unlock
    function tokenAddressOf(uint8) external pure override returns (address) { return address(0); }
    function tokenSuiDecimalOf(uint8) external pure override returns (uint8)  { return 1; }
    function tokenPriceOf(uint8) external pure override returns (uint64)      { return 1; }
    function isTokenSupported(uint8) external pure override returns (bool)    { return false; }
    function isChainSupported(uint8) external pure override returns (bool)    { return true; }
    function chainID() external pure override returns (uint8)                 { return 12; }
}

contract FrontRunInitializeConfig {
    function attack(address committeeProxy) external {
        MaliciousConfig bad = new MaliciousConfig();
        // Callable by anyone; no access control on initializeConfig
        BridgeCommittee(committeeProxy).initializeConfig(address(bad));
        // Deployer's subsequent initializeConfig call will revert:
        // "BridgeCommittee: Config already initialized"
    }
}
```
