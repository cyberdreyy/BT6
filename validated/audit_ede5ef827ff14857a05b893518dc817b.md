### Title
`v1::validate_tenure_change_payload` misses `DuplicateBlockFound` for locally-accepted-only tenure-start blocks - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`v1::validate_tenure_change_payload` still checks `get_last_globally_accepted_block` when deciding whether a tenure already has a signed block, while `v2::validate_tenure_change_payload` was patched to use `get_last_signed_block` (which also covers `LocallyAccepted`). During any period where the negotiated `active_signer_protocol_version` resolves to `SortitionStateVersion::V1` (protocol version < `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION = 2`, e.g. mixed-version fleets during an upgrade, or fallback to local version when there's no global-state consensus), a signer can be tricked into missing the duplicate-tenure-start check for a block it has already locally accepted (signed) but the node has not yet ingested.

### Finding Description
`SignerDb::get_last_signed_block` (`stacks-signer/src/signerdb.rs:1572-1585`) returns the tenure tip counting both `GloballyAccepted` and `LocallyAccepted` states, deliberately excluding only `PreCommitted` (no signature yet). `SignerDb::get_last_globally_accepted_block` only returns blocks whose state is `GloballyAccepted`.

`v2::validate_tenure_change_payload` (`stacks-signer/src/chainstate/v2.rs:340-357`) was fixed to call `get_last_signed_block`, with an explicit comment: "Only blocks we have signed (locally or globally accepted) count here." This fix is backed by a regression test, `check_tenure_change_rejects_when_locally_accepted_block_exists` (`stacks-signer/src/chainstate/tests/v2.rs:748-850`), whose docstring states the bug explicitly: "previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change."

`v1::validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505-518`) was never updated to match — it still calls `get_last_globally_accepted_block`. There is no equivalent regression test for v1 guarding against a locally-accepted-only conflict.

Which chainstate implementation actually runs is decided dynamically per-proposal by `SortitionStateVersion::from_protocol_version` (`stacks-signer/src/chainstate/mod.rs:532-540`), driven by `determine_active_signer_protocol_version` (`stacks-signer/src/v0/signer.rs:783-807`), which negotiates the network-wide minimum supported protocol version via `GlobalStateEvaluator`, and explicitly falls back to the signer's own local version when there is no global consensus on protocol version (and the local version doesn't itself use global state). Since `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION = 2` (`stacks-signer/src/v0/signer_state.rs:51-53`), any signer/network state that negotiates to version < 2 (mixed-fleet during an upgrade, a signer configured/rolled back to an older supported version, or lack of quorum on protocol version) causes `SortitionState::V1` and thus the buggy `get_last_globally_accepted_block` check to run.

Exploit flow: A miner proposes tenure-start block A for tenure T. Enough signer weight (≥70%) signs it, so on this victim signer it becomes `LocallyAccepted` (a real signature was produced — `store_and_process_block_signature`, `stacks-signer/src/v0/signer.rs:2442-2537`, calls `mark_locally_accepted` at line 2528), but before the Stacks node processes/broadcasts it as its new tip (so `get_last_globally_accepted_block` still returns `None` for T). During this window, if the negotiated protocol version is V1 (or falls back to V1), the same or a colluding miner proposes a second, different tenure-start block B for the same tenure T (a re-proposal with different transactions, exactly as reproduced by the `check_tenure_change_rejects_when_locally_accepted_block_exists` v2 test). `check_proposal` → `validate_tenure_change_payload` (v1 branch) queries `get_last_globally_accepted_block(T)`, gets `None`, so `DuplicateBlockFound` is never raised, and the signer proceeds to potentially sign block B as well — producing two conflicting, signed tenure-start blocks for the same tenure T from the same signer.

### Impact Explanation
This breaks the uniqueness/one-tenure-start-per-tenure invariant that the duplicate check exists to enforce. If enough signers hit this window under V1 semantics, two conflicting tenure-start blocks for tenure T can both gather signatures, which is a Critical chain-safety violation (a signer signing a conflicting/non-canonical block, matching the stated Critical impact category "a signer signing an invalid, non-canonical, or conflicting block (chain safety) ... uniqueness"). It is repeatable any time the network is running/negotiating a sub-V2 protocol version and the locally-accepted/not-yet-globally-accepted timing window occurs, which is a normal occurrence during signature-threshold-to-node-ingestion latency.

### Likelihood Explanation
Preconditions: (1) the negotiated `active_signer_protocol_version` on at least one signer resolves to `SortitionStateVersion::V1` (network still below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION=2`, mid-upgrade fleets, or fallback-to-local-version when there's no cross-signer version consensus); (2) the ordinary race window between reaching the 70% local signature threshold (`mark_locally_accepted`) and the node acknowledging the block as its tip (`mark_globally_accepted`). Neither precondition requires majority-signer collusion, node-operator privilege, or the auth_token — the attacker only needs to win one miner slot and re-propose a sibling tenure-start block while gossiping it to signers, matching the allowed unprivileged attacker capability. The likelihood is tied to how often V1 semantics are actually negotiated in a live network; on a fully-upgraded fleet where every signer reports protocol version ≥ 2, this path is unreachable. The prompt's premise ("mixed-version network during upgrade") is exactly the condition under which `determine_active_signer_protocol_version` can select V1 for some/all evaluations.

### Recommendation
Update `v1::validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505`) to call `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 fix, and add a regression test analogous to `check_tenure_change_rejects_when_locally_accepted_block_exists` but exercising the V1 (`SortitionsView`/local-state) proposal path.

### Proof of Concept
Rust test plan (modeled directly on the existing v2 regression test at `stacks-signer/src/chainstate/tests/v2.rs:748-850`, but driving the V1 path):
1. Build a V1 test environment (`SortitionStateVersion::V1` / `SortitionsView` via `SortitionState::new`), analogous to `setup_test_environment` used in v1 tests.
2. Insert a `BlockInfo` for tenure T with `mark_locally_accepted(false)` (never `mark_globally_accepted`) — same as the v2 test's `existing_block_info.mark_locally_accepted(false)`.
3. Construct a second tenure-start `NakamotoBlock` (`TenureChangeCause::BlockFound` + coinbase) for the same tenure T (same `consensus_hash`), differing in transactions from the first.
4. Call `SortitionsView::check_proposal` (v1) with this second block.
5. **Assertion for the broken equality**: assert `result` is `Ok(())` (or any error other than `DuplicateBlockFound`), demonstrating that unlike the v2 counterpart (which asserts `Err(RejectReason::DuplicateBlockFound)`), the V1 path fails to flag the duplicate.
6. To show the uniqueness violation concretely, extend the test to simulate signature gathering for block B (call `store_and_process_block_signature`-equivalent helpers or directly assert both `existing_block_info` and the new block's `BlockInfo` reach `LocallyAccepted`/signed state in `signer_db` for the same `consensus_hash` T) — asserting that `signer_db.get_last_signed_block(T)` after processing both would report two distinct signed `signer_signature_hash` values under T, which violates the intended one-tenure-start-per-tenure invariant.
