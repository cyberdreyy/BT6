### Title
Deleting a multisig member does not purge their existing confirmations on requests they did not create, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`DeleteMember` (in `multisig2`) and `DeleteKey` (in `multisig`) only remove pending *requests created by* the removed member, but never scrub that member's *confirmations* recorded on requests created by other members. Because `confirm()` counts raw confirmation-set size against `num_confirmations` without re-validating that every confirming entry still belongs to a live member, a request can execute with fewer live-member approvals than the configured threshold — the "revoke a stale approval" gap that is the root cause the external report describes for `approvedHashes`, reachable here through the member-removal path instead of `revokeHash`.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only cleans up requests where the removed member was the *creator*: [1](#0-0) 

It filters `self.requests` by `r.member == member` (the original requester) and removes those requests' confirmation sets. It never inspects `self.confirmations` values (the `HashSet<String>` of confirming members) to strip out the entry belonging to the member being deleted from *other* still-pending requests that the removed member had already confirmed but did not create.

`confirm()` then counts stale confirmations toward the threshold with no re-check that each entry is still a current member: [2](#0-1) 

`assert_valid_request` (called at the top of `confirm`) only validates that the *caller* is currently a member; it performs no validation over the *existing* entries already stored in the confirmation set: [3](#0-2) 

The equality that should hold is:
`confirmations.len() == number of currently-live members who approved this specific request`

After a member is removed while having an outstanding confirmation on someone else's request, this becomes:
`confirmations.len() == (live approvers) + (approvals from now-removed members)`

so the threshold check `confirmations.len() + 1 >= num_confirmations` can be satisfied with fewer live approvers than `num_confirmations` requires.

The same pattern exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` only removes requests where `r.signer_pk == pk` (the creator), never scrubbing `pk` from `confirmations` sets of other requests: [4](#0-3) 

### Impact Explanation
This crosses the authorisation-threshold boundary described in the rules: a multisig request can be executed with confirmation count reaching `num_confirmations`, while the number of *live* members who actually approved it is strictly lower. Concretely:

1. Multisig has members `{A, B, C}`, `num_confirmations = 2`.
2. `A` creates request `R` (e.g. `Transfer` funds to an account `A` controls, or any other sensitive action).
3. `B` confirms `R` → `confirmations(R) = {B}` (len 1 < 2, not yet executed).
4. Separately, members agree to remove `B` via a `DeleteMember{member: B}` request (this only requires `A`/`C` confirmations and executes normally).
5. `delete_member` removes `B` from `members` and deletes only requests *created by* `B`; `R`'s confirmation set is untouched, still containing `B`.
6. `C` (the only other live member) confirms `R`: `confirmations.len() (1, from removed B) + 1 (C) = 2 >= num_confirmations (2)` → `execute_request(R)` runs and funds move.

Only one currently-live member (`C`) actually approved `R`, yet it executed as if the 2-of-3 threshold were met — a multisig request executed below the intended live-member threshold, matching the Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
This requires only ordinary multisig usage (no attacker-controlled deployment, no owner/foundation privilege beyond being one of the existing members) — a member confirms a request, is later removed through the normal `DeleteMember`/`DeleteKey` flow (e.g., because they left the organization or their key was rotated), and any pending request they had previously confirmed retains their stale approval indefinitely (there is no request expiry other than the manual `delete_request` cooldown path, which is optional and not automatically triggered on member removal). Any remaining member set can trivially trigger execution of such a stale request.

### Recommendation
When deleting a member (`delete_member`/`DeleteKey`), also scan every `confirmations` entry (not just requests created by that member) and remove the departing member's confirmation from all pending requests. Alternatively, at `confirm()` time, filter/recompute `confirmations` against `self.members` before comparing against `num_confirmations`, so only confirmations from currently-live members are counted toward the threshold.

### Proof of Concept
See the step-by-step scenario in Impact Explanation, exercised against `multisig2::MultiSigContract`:
1. `new(members = [A, B, C], num_confirmations = 2)`.
2. `A.add_request(Transfer{..})` → `request_id = R`.
3. `B.confirm(R)` → confirmations = `{B}`.
4. `A.add_request_and_confirm(DeleteMember{member: B})`, then `C.confirm(...)` → executes, `B` removed from `members`, but `confirmations[R]` still `{B}` (see `delete_member` at `multisig2/src/lib.rs:356-379`, which only filters `self.requests` by creator, never touching `self.confirmations`).
5. `C.confirm(R)` → `assert_valid_request` passes (`C` is a live member); `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` → `execute_request(R)` fires the `Transfer`, even though only `C` (one live member) actually approved it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
