## Analysis

`Secrets` is `map[string]Secret` keyed by the CI-config-controlled variable name, and `defaultSecretsResolver.Resolve` iterates `for variableKey, secret := range secrets` [1](#0-0) , passing that key unmodified into `spec.Variable{Key: variableKey, ...}` [2](#0-1) . This key ultimately originates from the `secrets:` block's map key in `.gitlab-ci.yml`, which an unprivileged pipeline author fully controls.

`BashWriter.Variable` handles File-type variables (the default, per `Secret.IsFile()` [3](#0-2) ) by calling `b.TmpFile(variable.Key)`: [4](#0-3) 

`path.Join(b.TemporaryPath, name)` lexically cleans `..` segments — so `path.Join("/builds/x", "../../../etc/cron.d/evil")` resolves to a path outside `/builds/x`, and `Absolute()` just returns it as-is if already absolute-looking after Join (it will be absolute since TemporaryPath is absolute). The result feeds directly into the emitted script: [5](#0-4) 

This writes `printf '%s' <secret-value> > <traversed-path>` and also does `export ../../../etc/cron.d/evil="<path>"`, which would actually be a bash syntax error for the export statement (invalid identifier), but the `printf ... > %q` line executes *before* that as a separate shell statement, so the file write happens regardless of whether the subsequent `export` line fails.

However, I could not fully verify within this codebase whether GitLab Rails-side validation constrains secret variable **keys** before they reach the Runner (i.e., whether arbitrary strings containing `/` and `..` can even be accepted as a `secrets:` block key and forwarded in the job payload). This constraint lives outside `gitlab-runner`, in the GitLab Rails/CI YAML processor, which is not part of this repository and thus not directly checkable here. Within the Runner codebase itself, I found **no validation, sanitization, or traversal guard** on `variableKey` in `common/secrets.go`, `spec.Variable`, or `BashWriter.TmpFile`/`Absolute`/`cleanPath` — the `isTmpFile` check exists only for reusing an already-resolved value, not for validating a key before path construction [6](#0-5) .

### Title
Unsanitized secret variable key enables path traversal in `BashWriter.TmpFile`/`Variable` - ([File: shells/bash.go])

### Summary
`defaultSecretsResolver.handleSecret` places the raw, pipeline-author-controlled `secrets:` block key into `spec.Variable.Key` without any validation, and `BashWriter.Variable`/`TmpFile` joins that key directly onto the job's `TemporaryPath` using `path.Join`, which does not prevent `..` traversal. For a File-type secret (the default), this can cause the generated shell script's `printf '%s' <secret> > %q` to write the secret's content to a path outside the job's temporary/workspace directory.

### Finding Description
- `Resolve()` iterates the `secrets:` map keys from the job payload and passes each key (`variableKey`) unchanged into `handleSecret`, which builds `spec.Variable{Key: variableKey, File: secret.IsFile(), ...}` [7](#0-6) .
- `Secret.IsFile()` defaults to `true` when `file:` is not explicitly set to `false` [3](#0-2) , so a standard `secrets:` entry with no `file: false` override is written to a temp file by default.
- `BashWriter.Variable` calls `b.TmpFile(variable.Key)` for File-type variables, and `TmpFile` does `path.Join(b.TemporaryPath, name)` with no traversal guard, then `cleanPath`/`Absolute` just returns the absolute path unchanged [4](#0-3) [8](#0-7) .
- The generated script line `printf '%%s' %s > %q` writes the secret value to that computed path [9](#0-8) .
- No component in this repository (`common/secrets.go`, `common/spec/spec.go`, `shells/bash.go`) validates that the key is a safe bash identifier or rejects path-separator/`..` characters before it is used to build a filesystem path.

### Impact Explanation
If reachable with a raw, uncontrolled key, this allows a File-type secret's decrypted value to be written to an arbitrary path on the executor host/container filesystem outside the job's `TemporaryPath`/build root, violating the "file operations must stay within intended build/cache/artifact roots" invariant. Scoped impact is a confined-but-real "write outside workspace" primitive (the specific `/etc/cron.d/evil` example would additionally require the job to run as a user allowed to write there, which is executor/host-configuration dependent and outside this scope).

### Likelihood Explanation
Feasibility depends entirely on a precondition I could not verify inside this repository: whether the GitLab server-side CI/CD config processor (Rails), which is outside `gitlab-runner`, restricts `secrets:` block keys to safe identifier characters (typical CI variable name patterns disallow `/` and are restricted to `[A-Za-z_][A-Za-z0-9_]*`) before ever sending the job payload to Runner. If that server-side restriction exists and is enforced, this Runner-side code path is unreachable by an unprivileged user despite the missing guard here. I found no such validation in the Runner code itself, and no evidence one way or another for the Rails side in this repo.

### Recommendation
Add defense-in-depth validation in `common/secrets.go`'s `handleSecret` (or in `spec.Variable` construction) to reject/sanitize secret keys that are not valid shell-identifier-safe strings (matching something like `^[A-Za-z_][A-Za-z0-9_]*$`), and independently harden `BashWriter.TmpFile`/`Absolute` (and the PowerShell equivalent) to reject or strip path traversal/absolute-path segments in `name` before joining with `TemporaryPath`, regardless of server-side guarantees.

### Proof of Concept
Go unit test in `shells/bash_test.go` style:
```go
func TestBashWriter_Variable_FileKeyTraversal(t *testing.T) {
    w := &BashWriter{TemporaryPath: "/builds/x"}
    w.Variable(spec.Variable{
        Key:   "../../../etc/cron.d/evil",
        Value: "malicious",
        File:  true,
    })
    script := w.String()
    // Assert the emitted file path stays within TemporaryPath
    assert.NotContains(t, script, "/etc/cron.d/evil")
    assert.Contains(t, script, "/builds/x/")
}
```
Expected: the assertion fails today because `TmpFile` resolves to a path outside `/builds/x`, confirming the missing traversal guard at the Runner level. Whether this is exploitable end-to-end additionally requires confirming (outside this repo) that GitLab Rails does not already reject such keys before job dispatch.

func (r *defaultSecretsResolver) handleSecret(variableKey string, secret spec.Secret) (*spec.Variable, error) {
	sr, err := r.secretResolverRegistry.GetFor(secret)
	if err != nil {
		r.logger.Warningln(fmt.Sprintf("Not resolved: %v", err))
		return nil, nil
	}

	r.logger.Println(fmt.Sprintf("Using %q secret resolver...", sr.Name()))

	value, err := sr.Resolve()
	if errors.Is(err, ErrSecretNotFound) {
		if !r.featureFlagOn(featureflags.EnableSecretResolvingFailsIfMissing) {
			err = nil
		} else {
			err = fmt.Errorf("%w: %v", err, variableKey)
		}
	}
	if err != nil {
		return nil, err
	}

	variable := &spec.Variable{
		Key:    variableKey,
		Value:  value,
		File:   secret.IsFile(),
		Masked: true,
		Raw:    true,
	}

	return variable, nil
}

func (b *BashWriter) Variable(variable spec.Variable) {
	if variable.File {
		variableFile := b.TmpFile(variable.Key)
		b.Linef("mkdir -p %q", helpers.ToSlash(b.TemporaryPath))
		b.Linef("printf '%%s' %s > %q", b.escape(variable.Value), variableFile)
		b.Linef("export %s=%q", b.escape(variable.Key), variableFile)
	} else {
		if b.isTmpFile(variable.Value) {
			variable.Value = b.cleanPath(variable.Value)
		}
		b.Linef("export %s=%s", b.escape(variable.Key), b.escape(variable.Value))
	}
}
