### Title
Post-default instant-withdraw receipts corrupt the defaulted-epoch claim bucket and drain `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` lacks the `defaultRecoveryFinalized` guard that `requestWithdraw` has. After a default is finalized, `epochNumber` still equals `defaultRecoveryEpoch`, so new instant-withdraw receipts are booked into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` and `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` — the same metadata slots used for pre-default defaulted receipts. When claimed, `_claimDefaultedInstantWithdrawRequest` treats the whole polluted bucket as defaulted-epoch basis and pays it out of `defaultRecoveryReserve` at `defaultRecoveryPrice`, while `pendingInstantWithdraws` is clamped to zero. The reserve, sized only for pre-default basis at finalization, is thus drained by post-default claims that were never part of the recovery accounting — analogous to the OpenSIPS bug where a malformed record corrupts shared state that a later "clone" (here, the per-epoch claim aggregation) consumes blindly.

### Finding Description
In `requestWithdraw` (IdleCreditVault.sol:247-258), post-default requests are explicitly rerouted to `postDefaultRequests` and paid from a dedicated path. `requestInstantWithdraw` (lines 356-375) performs `_ensureDefaultRecoveryInitialized` but has **no** `defaultRecoveryFinalized` branch: it unconditionally does `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount`, `instantWithdrawClaimsByEpoch[epochNumber] += _amount`, and `pendingInstantWithdraws += _amount`.

After `finalizeDefaultRecovery` (lines 661-710), `epochNumber` is unchanged, so `epochNumber == defaultRecoveryEpoch`. On the next claim, `claimInstantWithdrawRequest` (lines 380-393) sees `defaultInstantWithdrawsFinalized == true` and calls `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — now containing both the user's defaulted receipt and their post-default receipt — burns the sum, pays `claimBasis * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve`, and zeroes/clamps `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[defaultEpoch]` (line 852-853), corrupting the aggregate for remaining claimants. Any residual `instantWithdrawsRequests` is then paid at par via `_transferFundedClaim`, which prefers non-reserve funds but draws on the reserve when they are exhausted.

### Impact Explanation
Direct theft / insolvency: `defaultRecoveryReserve` was computed in `finalizeDefaultRecovery` as `reserveAmount` covering exactly `totalBasis`. Each post-default instant receipt inflates `claimBasis` without any corresponding addition to the reserve, so an attacker (any tranche-token holder able to trigger `requestInstantWithdraw` through the CDO) extracts `defaultRecoveryPrice` per token of post-default request, leaving later defaulted-epoch claimants underfunded — permanent loss of unclaimed recovery, quantified as the attacker's post-default receipt times `defaultRecoveryPrice`.

### Likelihood Explanation
Requires a finalized default (honest borrower default is in scope) and that `IdleCDOEpochVariant.requestInstantWithdraw` still routes to the strategy after `defaulted()` is set; the strategy-side code imposes no such block. If the CDO blocks post-default instant requests entirely, the post-default receipt cannot be created and the vector collapses — this CDO-side gating could not be fully confirmed within the search budget and is the key uncertainty. A secondary, weaker variant exists pre-finalization: instant requests made between `defaulted` and `finalizeDefaultRecovery` are silently merged into the default-epoch basis (`defaultPendingClaimBasis` reads `instantWithdrawClaimsByEpoch[epochNumber]`), which is by-design only if intended.

### Recommendation
In `requestInstantWithdraw`, mirror the `requestWithdraw` post-default branch: when `defaultRecoveryFinalized`, either revert or book the receipt under a post-default namespace (e.g. a dedicated mapping keyed separately from `defaultRecoveryEpoch`) so it can never be paid from `defaultRecoveryReserve`. Additionally, reject new instant requests while `defaulted` and unfinalized, or exclude them from `defaultPendingClaimBasis`.
