### Title
Signer permanently marked `NotRegistered` for a reward cycle when the node's reward set isn't ready yet, wedging it out of signing for the entire cycle - ([File: stacks-signer/src/runloop.rs])

### Summary
`RunLoop::refresh_signer_config` treats a reward cycle as "configured" the moment it records *any* outcome for that cycle — including the negative outcome `ConfiguredSigner::NotRegistered`. Because `is_configured_for_cycle` only compares reward-cycle numbers and never re-queries the node once a cycle has been "resolved," a transient node-side condition (the reward set not yet being calculated when the signer first checks during the prepare phase) permanently locks the signer out of participating in that entire reward cycle, even after the reward set becomes available and the signer is actually part of it.

### Finding Description
`ConfiguredSigner::reward_cycle()` returns the cycle number for both variants without regard to whether the signer is actually registered: [1](#0-0) 

`is_configured_for_cycle` uses exactly this equality check to decide whether a refresh is needed: [2](#0-1) 

`refresh_signer_config` calls `get_signer_config`, which returns `Ok(None)` whenever the node hasn't calculated/published the reward set yet for the requested cycle (`get_parsed_reward_set` returns `None`, e.g. anchor block not yet selected in a fresh prepare phase): [3](#0-2) 

When that happens, the runloop stores `ConfiguredSigner::not_registered(reward_cycle)` for that cycle, unconditionally: [4](#0-3) 

`refresh_runloop` is the only path that would re-attempt registration, and it is gated entirely by `!is_configured_for_cycle(...)`: [5](#0-4) 

Since `NotRegistered { cycle }.reward_cycle() == cycle`, `is_configured_for_cycle(cycle)` returns `true` the instant the negative result is cached — identical to how a real registration would satisfy the check. There is no mechanism that re-checks whether the underlying reward set (now available) actually includes this signer. `cleanup_stale_signers` only removes entries once `reward_cycle < current_reward_cycle`, i.e., only after the whole reward cycle has *already elapsed*: [6](#0-5) 

So the sequence is:
1. During the prepare phase for cycle `C+1`, `refresh_runloop` calls `refresh_signer_config(C+1)` because `is_in_next_prepare_phase` is true and the cycle isn't configured yet.
2. If the node hasn't finished computing/publishing the `C+1` reward set at that exact burn-block event (a normal, benign timing/latency condition — no malicious actor or majority collusion required), `get_signer_config` returns `Ok(None)`, and the entry `ConfiguredSigner::NotRegistered{cycle: C+1}` is cached.
3. On every subsequent burn-block event for the rest of the prepare phase and for the entirety of cycle `C+1` (until `current_reward_cycle` advances past `C+1`), `is_configured_for_cycle(C+1)` returns `true`, so `refresh_signer_config(C+1)` is never called again.
4. Even though the reward set for `C+1` becomes available shortly afterward (as it must, per Nakamoto consensus rules) and this signer may legitimately be a member of it, the signer never re-queries and never transitions to `RegisteredSigner`.
5. Result: this signer produces no `BlockResponse`/signature at all for the entire reward cycle `C+1`, despite being a legitimately registered signer with real signing weight.

### Impact Explanation
This is a High-impact liveness wedge as defined in the scope: "a signer wedged into never signing valid blocks." The signer will silently sit in `NoRegisteredSigners`/`NotRegistered` state for an entire reward cycle, contributing none of its signing weight to any block during that cycle, without operator awareness beyond a log line at the moment of the original failed check. If this occurs simultaneously for multiple signers around a cycle boundary (a plausible correlated event, since all signers query the node around the same burn height), it can measurably erode the total available signing weight for that cycle, increasing the risk of missed block-signing thresholds or requiring the anomaly to be manually diagnosed and the signer process restarted (which re-runs `initialize_runloop` and would query fresh).

### Likelihood Explanation
No malicious action or majority collusion is required — only ordinary asynchrony between the signer's polling of `/v2/... reward_set` endpoints and the node's completion of reward-set calculation during the prepare phase, which is an expected, common occurrence (the code path is explicitly designed to be reachable enough that a regression test, `reloads_signer_set_in`, exists for a related scenario). The bug is triggered purely by the timing of a single signer's own poll relative to its own node's computation, i.e., it is reachable by ordinary operation/gossip timing without any adversary.

### Recommendation
Do not conflate "already resolved this cycle" with "registered for this cycle" in the refresh gate. `is_configured_for_cycle` (or the caller in `refresh_runloop`) should re-attempt `refresh_signer_config` for cycles currently marked `NotRegistered` as long as the reward set for that cycle was not yet known at the time of the previous check (or simply retry on every event while `NotRegistered` and the cycle is current/upcoming, distinguishing "reward set absent" from "reward set present but excludes me"). Concretely: track whether the `NotRegistered` determination was made because the reward set didn't exist yet vs. because the signer's key was absent from an already-published set, and only skip re-querying in the latter case.

### Proof of Concept
1. Start a signer whose reward-cycle prepare phase begins at burn height `H`.
2. Arrange for the stacks-node to answer `get_reward_set_signers(C+1)` with `None` at the very first burn-block event inside the prepare phase (this is the normal state before the anchor block for `C+1` is selected/known — see `reloads_signer_set_in`'s own setup, which artificially targets `before_epoch_3_reward_set_calculation`).
3. `refresh_runloop` calls `refresh_signer_config(C+1)`; `get_signer_config` returns `Ok(None)`; `ConfiguredSigner::not_registered(C+1)` is stored.
4. Advance the burnchain so that the node completes calculation of the `C+1` reward set and this signer's key is present in it (verifiable via `get_reward_set_signers`).
5. Continue delivering burn-block events to the signer runloop through the rest of the prepare phase and into cycle `C+1`.
6. Observe via `StateInfo`/`running_signers` (returned on `SignerEvent::StatusCheck`) that the signer remains `NotRegistered` for `C+1` for the whole cycle, and it never appears in `signer_state_machines` as a `RegisteredSigner`, confirming it never processes or signs any block proposals for `C+1` despite being present in the reward set.

    /// Refresh signer configuration for a specific reward cycle
    fn refresh_signer_config(&mut self, reward_cycle: u64) {
        let reward_index = reward_cycle % 2;
        let new_signer_config = match self.get_signer_config(reward_cycle) {
            Ok(Some(new_signer_config)) => {
                let signer_mode = new_signer_config.signer_mode.clone();
                let new_signer = Signer::new(&self.stacks_client, new_signer_config);
                info!("{new_signer} Signer is registered for reward cycle {reward_cycle} as {signer_mode}. Initialized signer state.");
                ConfiguredSigner::RegisteredSigner(new_signer)
            }
            Ok(None) => {
                warn!("Signer is not registered for reward cycle {reward_cycle}");
                ConfiguredSigner::not_registered(reward_cycle)
            }
            Err(e) => {
                warn!("Failed to get the reward set info: {e}. Will try again later.");
                return;
            }
        };

        self.stacks_signers.insert(reward_index, new_signer_config);
    }

    fn cleanup_stale_signers(&mut self, current_reward_cycle: u64) {
        #[cfg(any(test, feature = "testing"))]
        if TEST_SKIP_SIGNER_CLEANUP.get() {
            warn!("Skipping signer cleanup due to testing directive.");
            return;
        }
        let mut to_delete = Vec::new();
        for (idx, signer) in &mut self.stacks_signers {
            let reward_cycle = signer.reward_cycle();
            if reward_cycle >= current_reward_cycle {
                // We are either the current or a future reward cycle, so we are not stale.
                continue;
            }
            match signer {
                ConfiguredSigner::RegisteredSigner(signer) => {
                    if !signer.has_unprocessed_blocks() {
                        debug!("{signer}: Signer's tenure has completed.");
                        to_delete.push(*idx);
                    }
                }
                ConfiguredSigner::NotRegistered { .. } => {
                    debug!("{signer}: Unregistered signer's tenure has completed.");
                    to_delete.push(*idx);
                }
            }
        }
        for idx in to_delete {
            self.stacks_signers.remove(&idx);
        }
    }
