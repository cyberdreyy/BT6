## Title
Signers can sign a block from a miner already marked invalid (timed-out or disallowed reorg) because the pre-signing recheck is documented as incomplete and skips miner/sortition validity - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The bug class in GHSA-75c5-f4gw-38r9 is that a sanitization routine only covered one attack surface (`phar://`) while an equivalent surface (`file://`) was left unguarded, letting stale/incomplete validation stand in for full validation. The stacks-signer v0 codebase has a structurally identical gap: the only re-validation performed between "willing to sign" (pre-commit) and the irreversible act of producing a block signature is `check_block_against_signer_db_state`, which is explicitly documented in its own doc-comment as **"an incomplete check"** [1](#0-0) . It re-verifies only tenure-confirmation (`check_latest_block_in_tenure` / `check_tenure_change_confirms_parent`), but never re-runs the miner/sortition-status checks that live only in `SortitionsView::check_proposal`/`GlobalStateView::check_proposal`, which are the checks that mark a miner `InvalidatedBeforeFirstBlock` on timeout or on an unauthorized parent-tenure choice [2](#0-1) .

### Finding Description
The proposal-time path (`handle_block_proposal` → `check_block_against_state` → `SortitionsView::check_proposal`) is the only place that checks whether the current miner/tenure is still valid: it detects miner timeout (`SortitionState::is_timed_out`) and unauthorized reorgs (`check_parent_tenure_choice`), and if either fails it flips `self.cur_sortition.miner_status` to `SortitionMinerStatus::InvalidatedBeforeFirstBlock` [2](#0-1) .

Once a block passes that check and is validated OK by the node, the signer moves to `PreCommitted` and waits for the 70% pre-commit weight threshold. When the threshold is reached, `handle_block_pre_commit` re-runs only `check_block_against_signer_db_state` before signing: [3](#0-2) 

That recheck function is explicitly documented as incomplete and only re-verifies tenure confirmation, not miner/sortition validity [4](#0-3) . The project's own architecture notes confirm the gap: "the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the pox bitvec, and tenure-extend rules before delegating here" are explicitly *not* re-run at validate-ok or at signing time [5](#0-4) .

The time window between proposal arrival (when `check_proposal` last ran) and the pre-commit threshold being crossed (when the signature is actually produced) can be arbitrarily long — waiting on gossip, node validation latency, and other signers' pre-commits. During that window, purely as a function of time or an ordinary burn-chain fork (not requiring any signer to misbehave or collude), the miner backing the pre-committed block can become `InvalidatedBeforeFirstBlock` (timeout) or fail the parent-tenure check (disallowed reorg) in every signer's local `SortitionsView`. Because the final signing gate never asks that question again, every signer that already pre-committed will still sign once 70% weight is reached, producing a signature over a block that the signer set's own current view considers non-canonical/invalid.

### Impact Explanation
This breaks the equality that a signature must only be produced for a block whose miner/tenure is still valid per `check_proposal`. It falls squarely in the "Critical" bucket defined by the rules: a signer set can put signatures over an invalid/non-canonical block, without any signer acting maliciously and without needing a majority of signers to collude — the flaw exists identically for every honest signer.

### Likelihood Explanation
No malicious signer or majority collusion is required. The only actor with any agency here is the single miner (in scope) whose tenure can time out (`block_proposal_timeout`) or get invalidated by an ordinary burn-fork race for the next sortition — both are events a single miner/attacker can help trigger by delaying activity or racing block-commits, and gossip timing naturally creates the window between "pre-commit sent" and "70% pre-commit threshold crossed." The affected recheck function's own doc-comment admits the incompleteness, and the project's own documentation lists the exact checks skipped, indicating the gap is a known, load-bearing shortcut rather than a hypothetical edge case.

### Recommendation
Re-run the full `check_proposal` (or at minimum the miner/sortition-status portion of it — timeout and parent-tenure-choice validity) as part of the final pre-signing recheck in `handle_block_pre_commit`, not just `check_block_against_signer_db_state`'s tenure-confirmation subset. Any RejectReason produced (`InvalidMiner`, `ReorgNotAllowed`) at that point should abort the signature exactly as a failed `check_block_against_signer_db_state` does today.

### Proof of Concept
1. Miner proposes block `X` for tenure `T`; all signers run `check_proposal`, find the miner status `Valid`, validate `X` OK via the node, and broadcast pre-commits.
2. Before 70% pre-commit weight is reached (due to normal network/validation latency), the burn chain advances such that a competing sortition wins and `SortitionsView::check_proposal`, when evaluated against the *new* tip, would mark tenure `T`'s miner `InvalidatedBeforeFirstBlock` (timeout) or fail `check_parent_tenure_choice` (disallowed reorg) — this is deterministic once `block_proposal_timeout` elapses or the fork resolves, requiring no cooperation from any signer.
3. The remaining honest signers reach the 70% pre-commit threshold and call `handle_block_pre_commit`, which invokes only `check_block_against_signer_db_state` (tenure-confirmation only) [3](#0-2) ; this check passes because it never re-examines miner/sortition validity.
4. Signers sign and broadcast acceptance for block `X`, even though their own current `SortitionsView` would reject a fresh proposal of `X` with `RejectReason::InvalidMiner` or `RejectReason::ReorgNotAllowed` were it re-evaluated through `check_proposal`.
