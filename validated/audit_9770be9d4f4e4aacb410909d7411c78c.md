### Title
`new_authority` in `TransferToNewAccount`/`TransferToNewAccountPda` is never validated against `Pubkey::default()`, permanently bricking migrated funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The Canto/Plex-Engineer bug allowed a critical address (`_accountant`) to be set to the zero address because the code only checked authorization *conditionally* (`if != address(0))`), never validating that the new value itself was non-zero. In marginfi-v2, the `transfer_to_new_account` and `transfer_to_new_account_pda` instructions accept an arbitrary `new_authority: UncheckedAccount` that is copied directly into the new `MarginfiAccount.authority` field with **no validation at all**, not even an equality check against `Pubkey::default()`. The only place such a check exists is client-side, in the CLI helper, which is trivially bypassable by anyone calling the program instruction directly.

### Finding Description
`transfer_to_new_account` initializes a brand-new `MarginfiAccount`, copies over the *entire* `lending_account` (all deposit/borrow balances) from the old account, and sets the new account's authority to whatever `new_authority` pubkey was supplied: [1](#0-0) 

The account struct explicitly documents that this field is unchecked: [2](#0-1) 

The same pattern exists in the PDA variant, `TransferToNewAccountPda`: [3](#0-2) [4](#0-3) 

Nowhere in `initialize_migrated_account` or in the account constraints is `new_authority` checked to be non-default: [5](#0-4) 

The only defense against setting `new_authority` to the zero pubkey exists purely in the off-chain CLI tooling, not in the on-chain program: [6](#0-5) 

This mirrors exactly the root cause pattern in the referenced report: a value that flows into a security-critical field (there, `_accountant`; here, `authority`) is validated in exactly one place (an `if` condition guarding a different check, or a client-side wrapper) rather than being checked directly and unconditionally on-chain.

### Impact Explanation
Any account holder (an unprivileged, ordinary user — the `authority` signer of their own `MarginfiAccount`) can call `transfer_to_new_account`/`transfer_to_new_account_pda` directly (bypassing the CLI) with `new_authority = Pubkey::default()`. The instruction will:
1. Migrate the entire `lending_account` (all deposit/borrow balances) into the new account.
2. Disable the old account (`ACCOUNT_DISABLED`, `migrated_to` set) so it can never be used again.
3. Set the new account's `authority` field to the zero pubkey.

Since `Pubkey::default()` has no corresponding private key, no signer can ever satisfy `is_signer_authorized`/`authority` checks for the new account going forward. All of the user's collateral/borrow positions that were just migrated become permanently unreachable — deposits can never be withdrawn, borrows can never be repaid, and the position cannot be liquidated through the normal authority path either. This is a durable, on-chain, financially significant freeze of user funds, directly analogous to Impact C in the referenced report ("Accounting contract could lose funds/tokens" — tokens irrecoverably sent to the zero address).

Because the check that should prevent this exists only client-side and is absent from the actual program logic, this is a genuine on-chain authorization/validation gap rather than a theoretical or purely off-chain issue.

### Likelihood Explanation
Likelihood is Medium: like the original finding, this requires a misconfiguration/misuse (a user or an automated integrator submitting a zero pubkey) rather than a third party attacking someone else's account — the constraint `is_signer_authorized` still requires the *old* account's own authority to sign, so this cannot be executed against another user's account without their signature. However, unlike the original finding it is self-inflicted by design of the affected party, so it may be considered griefing/foot-gun rather than an externally exploitable attack. Given the same judge rationale that decreased the Cantor finding to Medium ("contingent on a misconfiguration"), this analog is best classified as Medium severity: the value-loss condition is real, on-chain, and unconditionally reachable by an unprivileged party, but requires that a caller supply an invalid input (accidentally, via a buggy integrator, or via a malicious frontend/dApp/CPI wrapper tricking the user into signing a transaction with `new_authority = 0`).

### Recommendation
Add an explicit on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that rejects `new_authority == Pubkey::default()` before any state is written, e.g.:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority // or similar
);
```
placed prior to `initialize_migrated_account` in both instruction handlers (`programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`, lines ~91 and ~233), so protection does not rely solely on off-chain tooling.

### Proof of Concept
1. User A owns `MarginfiAccount` `old_acc` with active deposit/borrow balances.
2. User A signs and submits a `TransferToNewAccount` (or `TransferToNewAccountPda`) instruction directly against the on-chain program (not via the CLI, which would have blocked this), setting `new_authority = Pubkey::default()`.
3. The instruction succeeds: `old_acc` is disabled and its `lending_account` state is copied into `new_acc`, whose `authority` field is now `Pubkey::default()` per [1](#0-0) .
4. No further instruction referencing `new_acc` (withdraw, repay, close balance, liquidate via authority path, etc.) can ever be authorized, because no signer can produce a signature matching `Pubkey::default()`.
5. All funds represented by `new_acc`'s balances are permanently frozen/unreachable through the standard user-authority flow.
