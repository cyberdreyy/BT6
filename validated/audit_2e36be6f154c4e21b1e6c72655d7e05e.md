### Title
Signer weight double-counted across accept/reject tallies due to asymmetric dedup keys - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
In the node-side StackerDB listener that tallies signer votes for a block proposal, the "already counted" check used to gate weight accumulation differs between the `Accepted` and `Rejected` message branches. The accept branch dedups on `block.gathered_signatures` (a `HashMap<slot_id, signature>`), while the reject branch dedups on `block.responded_signers` (a `HashSet<slot_id>`) — but the accept branch *also* unconditionally inserts into `responded_signers`. This creates an order-dependent asymmetry that lets a single signer's weight be counted on **both** sides of the tally if it sends a Reject followed later by an Accept for the same block.

### Finding Description
The relevant logic: [1](#0-0) 

```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```

versus the reject branch: [2](#0-1) 

```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```

Tracing both orderings for a single `slot_id`:
- **Accept then Reject**: accept adds weight to `total_weight_approved` and inserts `slot_id` into both `gathered_signatures` and `responded_signers`. When the Reject later arrives, `responded_signers.insert(slot_id)` returns `false` (already present), so the reject weight is correctly *not* added. No double count here.
- **Reject then Accept**: reject adds weight to `total_weight_rejected` and inserts `slot_id` into `responded_signers` only (`gathered_signatures` is untouched by the reject branch). When the Accept later arrives, the guard checked is `!block.gathered_signatures.contains_key(&slot_id)`, which is still `true` because `gathered_signatures` was never touched by the reject path. The accept branch therefore adds the same signer's weight to `total_weight_approved` a second time, even though that signer's weight is already counted in `total_weight_rejected`.

The result is that a single signer that first rejects and later accepts the same block (an equivocation, or simply a legitimate re-vote after re-evaluating the proposal, since signers are permitted to change their vote per the `docs/signer-flows.md` state machine) has its weight recorded in *both* `total_weight_approved` and `total_weight_rejected` simultaneously. This breaks the invariant that the sum of any signer's contributed weight across the two tallies must equal (at most) that signer's own weight — analogous to the Allora report's broken invariant where the same "unit" of value is counted more than once across two accounting buckets that are supposed to be complementary.

### Impact Explanation
`total_weight_approved` is used by `SignCoordinator::get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) to decide when a block has reached the ≥70% signing threshold and can be pushed/accepted: [3](#0-2) 

Because `total_weight_approved` can include weight from a signer that has also voted to reject (and whose weight is simultaneously counted toward `total_weight_rejected`), the sum `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`. This inflates the approved tally relative to genuinely-still-approving signers, which can let the coordinator perceive the 70% acceptance threshold as reached earlier than the honest, currently-approving weight actually justifies — i.e., a rejection is effectively re-counted toward acceptance. This matches the "rejection recounted as an accept" impact category (Critical), since it can cause the network to push/accept a block based on inflated approval weight that includes weight from a signer who has an outstanding rejection on record for that same block.

### Likelihood Explanation
This requires no majority and no key compromise — a single signer (or a compromised/misbehaving signer, or even a signer that legitimately flips its vote from reject to accept after re-evaluation, which the v0 signer state machine explicitly allows per `docs/signer-flows.md` section 2's `LocallyRejected --> LocallyAccepted : re-evaluated` transition) can trigger this by sending a `Rejected` message for a block followed later by an `Accepted` message for the same block hash. This is a normal, reachable code path (not requiring adversarial signature forgery), making the likelihood high whenever votes can be revised.

### Recommendation
Use a single, shared dedup structure (or track per-slot the last recorded vote type) so that when a signer transitions its vote from reject to accept (or vice versa), the previously-counted weight is subtracted from the old bucket before being added to the new one, rather than accumulating in both. E.g., maintain `responded_signers: HashMap<slot_id, VoteKind>` and adjust `total_weight_approved`/`total_weight_rejected` based on the transition rather than independently checking two different structures.

### Proof of Concept
1. Node receives `Rejected` from `slot_id=5` (weight=10) for block `H`: `total_weight_rejected += 10`, `responded_signers = {5}`, `gathered_signatures = {}`.
2. Same signer later re-evaluates and sends `Accepted` for block `H`: guard `!gathered_signatures.contains_key(&5)` is `true` (never touched), so `total_weight_approved += 10`.
3. Now `total_weight_approved` and `total_weight_rejected` both include signer 5's weight of 10, i.e., `total_weight_approved + total_weight_rejected` exceeds `self.total_weight` by 10 — the accounting invariant "each signer's weight counted at most once across the two tallies" is broken, and `get_block_status` in `signer_coordinator.rs` may cross the 70% approval threshold using this inflated figure.
