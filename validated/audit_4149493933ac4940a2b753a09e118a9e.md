### Title
Dust APR=0 withdraw request permanently bricks `stopEpoch` once APR is raised, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The DoS bug class of CVE-2018-3080 (a cheap privileged-adjacent trigger causing a repeatable crash/hang) maps onto the epoch state machine: an unprivileged KYC-passing lender can plant a dust-sized APR=0 withdraw receipt that makes every subsequent `stopEpoch`/`stopEpochWithDuration` call revert in `prepareStopEpochWithApr0`, halting the epoch state machine and freezing all deposits.

### Finding Description
When the vault APR is 0 (`unscaledApr == 0`), `requestWithdraw` routes the request into the APR0 bucket via `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` with no minimum-amount check [1](#0-0) . There is no dust threshold: `_amount` only needs to exceed the upfront management fee, which for a small request rounds to zero, so a request of a few wei suffices [2](#0-1) .

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0 && unscaledApr != 0` [3](#0-2) . The APR0 bucket is only populated while `unscaledApr == 0`, but `unscaledApr` can legitimately become non-zero before the next stop: the manager may call `setAprs`/`setAprsWithBuffer` directly at any time (manager is an honest role, and raising APR mid-epoch is a normal operation) [4](#0-3) . Once that happens, `_stopEpoch` reverts at the `prepareStopEpochWithApr0` call before any borrower pull, so the epoch can never be stopped — including the `_interest == 1` "recall everything" emergency close, which hits the same code path [5](#0-4) .

Attack sequence:

1. Epoch ends with `_newApr = 0`; buffer period begins, `unscaledApr == 0`.
2. Attacker (any KYC-passing lender) deposits dust and calls `requestWithdraw(dustAmount, AATranche)`, which lands in the APR0 bucket: `apr0TotalPrincipal = dust`, `apr0Users[attacker].principal = dust` [6](#0-5) .
3. Manager starts the next epoch and later sets a non-zero APR via `setAprs` (normal management operation), or the stop-epoch flow is attempted after APR was raised by any honest path.
4. Every `stopEpoch` reverts in `prepareStopEpochWithApr0` → `isEpochRunning` stays true, deposits/requests remain gated, no claims can mature (`epochNumber` never advances, so `_claimFundedWithdrawRequest`'s `epochNumber <= lastWithdrawRequest` check keeps reverting) [7](#0-6) .

The only remediation is for the manager to set APR back to 0 and run a stopEpoch — forcing a zero-interest epoch and delaying the recall path — so the griefing converts a ~zero-cost dust deposit into an epoch-length freeze of the entire pool plus an epoch of lost yield for all LPs. Note this also blocks `stopEpoch(_newApr, 1)` (close-pool recall), so even the emergency "get everything back" path is unavailable while APR is non-zero.

### Impact Explanation
Temporary freezing of all user funds: with `isEpochRunning` stuck true, deposits and withdraw requests stay disabled (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` are false during a running epoch), pending receipts cannot be claimed because `epochNumber` never increments, and the borrower recall path reverts. The attacker's cost is a dust deposit; the pool loses at least one full epoch of yield and cannot close until APR is forced back to 0. Broken invariant: epoch state machine liveness — an unprivileged user can permanently veto `stopEpoch` while APR ≠ 0.

### Likelihood Explanation
Requires the vault to operate an APR=0 epoch (a supported mode — `requestWithdraw` explicitly routes it) and a later APR raise before that epoch's stop settles the bucket. The attacker controls the dust request; the APR change is a normal manager action, so no malicious privileged role is needed. Guards do not prevent it: `_onlyIdleCDO` is satisfied, there is no minimum request size, and the `NotAllowed` revert in `prepareStopEpochWithApr0` is unconditional once both conditions hold.

### Recommendation
Enforce a minimum principal for APR0 requests (e.g., require `_amount` above a non-trivial threshold in `_requestWithdrawApr0`), or clear/ignore the APR0 bucket instead of reverting when `unscaledApr != 0` — e.g., settle APR0 receipts at zero interest when the APR was raised, so a stale dust bucket can never veto `stopEpoch`. Alternatively, snapshot `unscaledApr` per epoch in `apr0RateByEpoch`-style storage rather than gating on the live APR.

### Proof of Concept
Foundry fork PoC outline:

```solidity
// Setup: deploy IdleCDOEpochVariant + IdleCreditVault, KYC-attacker deposits dust.
// Epoch N stops with _newApr = 0 -> unscaledApr == 0, buffer begins.

// 1) Attacker plants dust APR0 receipt
vm.prank(attacker);
cdo.requestWithdraw(dust, AA);            // apr0TotalPrincipal = dust
assertGt(vault.apr0TotalPrincipal(), 0);

// 2) Manager starts next epoch, then raises APR mid-epoch (honest action)
vm.prank(manager); cdo.startEpoch();
vm.prank(manager); vault.setAprs(5e18, scaledApr); // unscaledApr != 0 now

// 3) Warp past epochEndDate; every stopEpoch reverts
vm.warp(cdo.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpoch(newApr, 0);

// 4) Emergency recall path also bricked
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpoch(0, 1); // _interest == 1 still hits prepareStopEpochWithApr0

// 5) All withdrawals frozen: epochNumber cannot advance
vm.expectRevert(NotAllowed.selector);
cdo.claimWithdrawRequest(); // epochNumber <= lastWithdrawRequest
```

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.

    if (_apr0User.principal == 0) {
