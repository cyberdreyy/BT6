### Title
Loss-adjusted withdraw receipts keyed to `lastWithdrawRequest` escape their haircut when a user has requests in multiple epochs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` looks up the loss-recovery price only at `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Because `lastWithdrawRequest` stores a single epoch (overwritten on every `requestWithdraw`), a user who holds a loss-adjusted receipt from epoch N and then makes a new withdraw request in a later epoch M has that receipt mis-indexed: the loss-adjusted slice is cleared under epoch N's ownership records but paid at par through the funded-claim path, draining underlyings reserved for other claimants. This mirrors CVE-2022-3599's out-of-bounds/stale-offset read: the claim logic reads the wrong epoch bucket for a multi-epoch receipt set.

### Finding Description
In `requestWithdraw`, each request records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` [1](#0-0) . When the borrower underfunds a stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` [2](#0-1) .

The claim path is:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;
    ...
}
function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    ...
    uint256 normalAmount = withdrawsRequests[_user];
    amount = normalAmount + ...;
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
}
``` [3](#0-2) [4](#0-3) 

Two broken cases:

1. **Re-request before claim.** User requests in epoch N; borrower underfunds → `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`. User requests again in epoch N+1 → `lastWithdrawRequest[user] = N+1`. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0, so the epoch-N slice in `withdrawsRequestsByEpoch[user][N]` is never cleared. After epoch N+1 ends, `_claimFundedWithdrawRequest` passes its gate and pays the entire `withdrawsRequests[user]` aggregate — including the epoch-N haircutted slice — at par.

2. **Default after a prior loss epoch.** User's epoch-N loss-adjusted receipt is still open when a default finalizes at epoch M (`defaultRecoveryEpoch = M`). `_claimDefaultedWithdrawRequest` clears only epoch M via `_clearWithdrawClaimForEpoch`, and because `lastWithdrawRequest[user] == M` it resets the marker to 0 [5](#0-4) . The epoch-N slice then bypasses `_claimLossAdjustedWithdrawRequest` (lookup at epoch 0) and is paid at par by `_claimFundedWithdrawRequest`.

### Impact Explanation
Direct theft / insolvency. The loss-adjusted underlyings collected by `collectWithdrawFunds` sit in the strategy as a commingled pool sized to cover all claimants at `lossRecoveryPrice`, not at par. A user whose epoch-N slice escapes the haircut withdraws `claimBasis` instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL`; the excess comes from funds owed to other loss-adjusted claimants (or, post-default, non-reserve funded balance guarded only by `defaultRecoveryReserve` [6](#0-5) ). With `lossRecoveryPrice` of e.g. 50%, an attacker controlling a large epoch-N receipt plus a dust re-request in epoch N+1 roughly doubles their payout and leaves later claimants' transfers reverting on insufficient balance — permanent freezing of unclaimed yield for honest users. No privileged misbehavior is required: underfunding is the honest stopEpochWithDuration path, and re-requesting is an explicitly supported flow.

### Likelihood Explanation
Requires (a) a stop where the borrower underfunds pending receipts or a default, and (b) a user holding a loss-adjusted receipt who makes a second request in a later epoch. Underfunded stops are a designed feature (`previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds`), and nothing prevents re-requesting while a receipt is unclaimed — the code comments even anticipate it. The exploit is a pure sequencing attack by an unprivileged tranche holder.

### Recommendation
Track claim resolution per epoch rather than via the single `lastWithdrawRequest` slot. Concretely: in `_claimLossAdjustedWithdrawRequest`, iterate (or track) all epochs in `withdrawsRequestsByEpoch[_user]` that have a non-zero `lossRecoveryPriceByEpoch`, or maintain a per-user list/bitmap of loss-adjusted epochs; clear each slice at its own haircut before falling through to `_claimFundedWithdrawRequest`. Alternatively, revert in `requestWithdraw` when the user holds an uncleared receipt in a loss-adjusted epoch, forcing them to claim the haircut first.

### Proof of Concept
Foundry fork scenario (mainnet IdleCDOEpochVariant + IdleCreditVault, `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. Epoch N running. user1 and user2 each hold AA tranches.
cdoEpoch.requestWithdraw(user1AA, address(AAtranche)); // user1
cdoEpoch.requestWithdraw(user2AA, address(AAtranche)); // user2, equal size

// 2. Manager stops epoch; borrower funds only 50% of pendingWithdraws.
uint256 pending = vault.pendingWithdraws();
deal(underlying, borrower, pending / 2);
cdoEpoch.stopEpochWithDuration(loss /* covers 50% of pending */, ...);
// => vault.lossRecoveryPriceByEpoch[N] == RECOVERY_FULL/2, pendingWithdraws == 0

// 3. Epoch N+1 starts. user1 does NOT claim; instead re-requests dust.
cdoEpoch.requestWithdraw(1, address(AAtranche)); // user1: lastWithdrawRequest -> N+1

// 4. Epoch N+1 stops fully funded.
cdoEpoch.stopEpoch(0, interest);

// 5. user1 claims.
cdoEpoch.claimWithdrawRequest(); // via IdleCDO for user1
// _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N+1] == 0 -> skips
// _claimFundedWithdrawRequest pays full withdrawsRequests[user1] at par:
//   epoch-N principal (should be ~50%) + dust at 100%
// user1 receives ~2x the entitled epoch-N amount.

// 6. user2 claims -> underlying transfer reverts (insufficient balance),
//    or user2 receives less than claimBasis * lossRecoveryPrice / RECOVERY_FULL.
assertLt(underlying.balanceOf(user2), expectedUser2Payout); // honest user shortfall
```

Assert `vault.lossRecoveryPriceByEpoch(N)` is non-zero and `withdrawsRequestsByEpoch(user1, N)` was never cleared — the user1 payout equals `epochN_basis + dust` instead of `epochN_basis * price / RECOVERY_FULL + dust`, quantifying the stolen excess as `epochN_basis * (RECOVERY_FULL - price) / RECOVERY_FULL`.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
