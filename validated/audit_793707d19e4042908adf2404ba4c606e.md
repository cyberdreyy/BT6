## Analysis

This describes a real gap in the contracts, not a false claim.

**Mechanism:**
`createDstEscrow` is a fully permissionless entrypoint — anyone can call it with an arbitrary `IBaseEscrow.Immutables` struct, including an arbitrary `parameters` byte blob, as long as they pay the matching native amount/safety deposit. [1](#0-0) 

There is no validation anywhere in `createDstEscrow` of the length or structure of `dstImmutables.parameters` before the clone is deployed and funded. [2](#0-1) 

`EscrowDst._withdraw` unconditionally decodes fee amounts, and — only if a decoded fee amount is non‑zero — also decodes the corresponding fee recipient: [3](#0-2) 

`ImmutablesLib` enforces strict minimum lengths for each field (`0x20` for `protocolFeeAmount`, `0x40` for `integratorFeeAmount`, `0x60` for `protocolFeeRecipient`, `0x80` for `integratorFeeRecipient`), reverting with `IndexOutOfRange` otherwise: [4](#0-3) 

So a 65‑byte `parameters` blob with a non-zero value encoded in the second word (bytes 32–64, the `integratorFeeAmount` slot) passes `integratorFeeAmountCd()` (needs ≥64 bytes) but then unconditionally fails `integratorFeeRecipientCd()` (needs ≥128 bytes) inside `_withdraw`, on every call to `withdraw` and `publicWithdraw`, for the lifetime of that specific clone. `cancel()`, however, does not touch `ImmutablesLib` fee decoding at all and always succeeds after the `DstCancellation` timelock, returning the destination token amount and safety deposit to the **taker**, not the maker. [5](#0-4) 

**Why this is a real but narrow issue:**
- The CREATE2 salt is derived from the full immutables hash (`ImmutablesLib.hashMem`), so this only affects the escrow the attacker themselves deployed with these bad parameters — it cannot be used to corrupt an already-deployed, correctly-parameterized escrow belonging to someone else. [6](#0-5) 
- The only way this harms a third party (the maker) rather than just the depositor is if the depositor is the legitimate taker of a real swap and deliberately submits a `parameters` blob that doesn't match what was implicitly agreed for that order, and the maker/resolver's off-chain verification does not catch the mismatched/short `parameters` before releasing the secret. There is no on-chain cross-check between `dstImmutables.parameters` supplied to `createDstEscrow` and the `DstImmutablesComplement.parameters` emitted from the source-chain `_postInteraction`. [7](#0-6) 
- That reliance on off-chain parameter validation before secret release is exactly the kind of "off-chain trust failure" the review rules ask to reject, and the taker role here is a normal, permissionless participant of the swap (not admin/governance), so it is not cleanly excluded either.

Given the on-chain invariant stated in the question ("Every funded destination escrow should remain withdrawable with the exact parameters used to create it") is genuinely violated — `withdraw`/`publicWithdraw` become permanently unusable for any escrow whose `parameters` blob is shorter than required for a non-zero fee it encodes — this is a legitimate finding, though its economic severity depends on off-chain acceptance checks that are outside contract scope.

### Title
Missing length/consistency validation of `dstImmutables.parameters` in `createDstEscrow` permanently bricks `EscrowDst.withdraw`/`publicWithdraw` - (File: `contracts/BaseEscrowFactory.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`createDstEscrow` accepts and immutably binds an attacker-supplied `parameters` byte blob without validating its length against the fee amounts it encodes. If the blob is long enough to yield a non-zero `integratorFeeAmount`/`protocolFeeAmount` but too short to contain the corresponding recipient address, every future call to `EscrowDst.withdraw`/`publicWithdraw` reverts inside `ImmutablesLib`, because the recipient getters require additional length that is missing.

### Finding Description
`_withdraw` in `EscrowDst.sol` reads `integratorFeeAmountCd()` and `protocolFeeAmountCd()` (requiring only 64/32 bytes of `parameters`), and conditionally, only when those amounts are non‑zero, reads `integratorFeeRecipientCd()`/`protocolFeeRecipientCd()` (requiring 128/96 bytes). `ImmutablesLib` reverts with `IndexOutOfRange` when the required length isn't met. `createDstEscrow` never validates that `parameters` is long enough for whatever fee values it encodes before deploying and funding the clone, so a `parameters` blob of, e.g., 65 bytes with a non-zero value in the second word will pass the amount checks but permanently fail the recipient checks on every withdrawal attempt.

### Impact Explanation
Once such an escrow is deployed and funded, `withdraw` and `publicWithdraw` can never succeed — the destination payout to the maker cannot occur through the normal withdrawal path. The only recovery path, `cancel()`, does not use `ImmutablesLib` fee decoding, so funds are eventually returned to the **taker** (the original depositor) after the cancellation timelock, not the maker. This produces at least a temporary freeze of the maker's expected payout for the life of the escrow, and — if paired with an off-chain flow where the maker releases the secret without independently re-validating `parameters` byte-for-byte — could result in the maker losing the swap value entirely while the taker reclaims their deposit via `cancel()` and separately withdraws the maker's source-chain funds using the revealed secret.

### Likelihood Explanation
The entrypoint (`createDstEscrow`) is fully permissionless and the `parameters` field is entirely attacker-controlled, so triggering the on-chain revert condition requires no privilege at all. However, converting this into actual value theft from a third party depends on off-chain secret-release logic not catching the malformed/mismatched `parameters`, which is outside the audited contracts.

### Recommendation
Validate `dstImmutables.parameters` in `createDstEscrow` before deployment: either enforce an exact expected length (e.g., always require the full 128-byte 4-word layout) or require that if a fee amount is non-zero, the length needed for its recipient is also present, and revert `createDstEscrow` otherwise. Alternatively, cross-check `dstImmutables.parameters` on-chain against the `DstImmutablesComplement.parameters` emitted for the corresponding order to prevent a taker from unilaterally supplying inconsistent fee data.

### Proof of Concept
1. Attacker (acting as taker) calls `createDstEscrow` with a native destination token, correct `amount`/`safetyDeposit`, and `parameters = abi.encodePacked(uint256(0), uint256(1))` truncated to 65 bytes (any length in `[0x40, 0x80)` with the second word non-zero). [2](#0-1) 
2. Wait for the `DstWithdrawal` timelock stage and call `withdraw(secret, immutables)`; execution reaches `integratorFeeAmountCd()` (succeeds, returns 1), enters the `if (integratorFeeAmount > 0)` branch, calls `integratorFeeRecipientCd()`, which reverts with `IndexOutOfRange` because `parameters.length` (65) `< 0x80`. [8](#0-7) [9](#0-8) 
3. `publicWithdraw` fails identically for any caller. Only `cancel()`, callable by the taker after `DstCancellation`, can retrieve the escrowed funds, and it returns them to the taker rather than paying the maker. [5](#0-4)

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function hashMem(IBaseEscrow.Immutables memory immutables) internal pure returns(bytes32 ret) {
        // Compute the EIP-712 hash for the immutables struct
        // Patch the last word (bytes parameters) in the struct with the hash of it
        bytes memory parameters = immutables.parameters;
        assembly ("memory-safe") {
            let parametersHash := keccak256(add(parameters, 0x20), mload(parameters))
            let patchLocation := sub(add(immutables, IMMUTABLES_SIZE), 0x20)
            let backup := mload(patchLocation)

            // Patch the last word with the hash of parameters to compute the EIP-712 hash
            mstore(patchLocation, parametersHash)
            ret := keccak256(immutables, IMMUTABLES_SIZE)

            mstore(patchLocation, backup) // Restore the original value
        }
    }
