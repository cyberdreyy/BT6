### Title
Attacker-controlled `idx` truncation in `MerkleStorageInvalidator.takerInteraction` permanently corrupts partial-fill validation state - (File: `contracts/MerkleStorageInvalidator.sol`)

### Summary
`MerkleStorageInvalidator.takerInteraction` verifies a Merkle proof using `uint64(takerData.idx)` (a truncated value) but persists the **untruncated** `takerData.idx + 1` into `lastValidated[key].index`. Because `takerData.idx` is a `uint256` fully controlled by the calling taker via the `interaction` calldata, an attacker can submit `idx = validIdx + k·2^64` for any `k`. The truncated hash still matches a legitimate Merkle leaf (so `InvalidProof` is not triggered), but the stored `index` becomes astronomically larger than any value `_isValidPartialFill` in `BaseEscrowFactory.sol` can ever match again, permanently bricking further partial fills of that order.

### Finding Description
`takerInteraction` computes the verified leaf as: [1](#0-0) 

```solidity
uint240 rootShortened = uint240(uint256(extraDataArgs.hashlockInfo));
bytes32 key = keccak256(abi.encodePacked(orderHash, rootShortened));
bytes32 rootCalculated = takerData.proof.processProofCalldata(
    keccak256(abi.encodePacked(uint64(takerData.idx), takerData.secretHash))
);
if (uint240(uint256(rootCalculated)) != rootShortened) revert InvalidProof();
lastValidated[key] = ValidationData(takerData.idx + 1, takerData.secretHash);
```

`takerData.idx` is declared as `uint256` in the interface: [2](#0-1) 

and is decoded directly from taker-supplied `extraData`/`interaction` bytes passed into `fillOrderArgs`/`fillContractOrderArgs` (attacker-controlled, no bounds check). The Merkle-proof check only validates the **low 64 bits** of `idx` against the tree leaf `keccak256(uint64(idx), secretHash)`, exactly like the off-chain tree construction in tests, which uses `uint64 i` loop indices. However, the value written into storage for the same order key is the *entire unmasked* `idx + 1`, with no equivalent truncation.

`partsAmount` (the number of Merkle-tree secrets/leaves for an order) is derived from only the top 16 bits of the packed hashlock info: [3](#0-2) 

```solidity
uint256 partsAmount = uint256(extraDataArgs.hashlockInfo) >> 240;
if (partsAmount < 2) revert InvalidSecretsAmount();
bytes32 key = keccak256(abi.encodePacked(orderHash, uint240(uint256(extraDataArgs.hashlockInfo))));
ValidationData memory validated = lastValidated[key];
hashlock = validated.leaf;
if (!_isValidPartialFill(makingAmount, remainingMakingAmount, order.makingAmount, partsAmount, validated.index)) {
    revert InvalidPartialFill();
}
```

so `partsAmount ≤ 65535`, meaning legitimate `calculatedIndex` values (in `_isValidPartialFill`) are always tiny relative to `2^64`: [4](#0-3) 

An attacker who is a normal, unprivileged taker/resolver can therefore:
1. Pick any legitimate leaf index `validIdx` (0..partsAmount) with its real `secretHash` and valid Merkle `proof`.
2. Submit `idx = validIdx + 2^64` (or any multiple of `2^64`) as `TakerData.idx` in the `interaction` bytes of a real `fillOrderArgs` call, with a `makingAmount` chosen so the fill's partial-fill math momentarily matches `validIdx`.
3. `uint64(takerData.idx) == validIdx`, so the Merkle-proof check in `takerInteraction` passes and the fill succeeds normally.
4. `lastValidated[key].index` is now set to `validIdx + 2^64 + 1`, a value orders of magnitude larger than any `calculatedIndex + 1`/`calculatedIndex + 2` that `_isValidPartialFill` can ever compute for that order (bounded by `partsAmount ≤ 65535`).
5. Every subsequent `fillOrderArgs`/`fillContractOrderArgs` call attempting to fill any remaining portion of that specific multiple-fill order will now revert with `InvalidPartialFill`, because `validated.index` can never again match a legitimately calculated index.

This is the exact analog of the reported bug class: an explicit narrowing type conversion (`uint256 -> uint64`) is used only for the security check, while the corresponding "canonical" value stored in state/mapping keeps its full, unmasked width — creating an inconsistency that an unprivileged party can exploit to corrupt protocol state (here, `lastValidated`) and break subsequent legitimate operations, mirroring the `pairId` truncation/overwrite issue in the original report.

### Impact Explanation
Any unprivileged taker filling a multi-fill ("allow multiple fills") Fusion order can permanently disable further partial fills of that specific order by corrupting `lastValidated[key].index`. Once corrupted, the maker's remaining un-filled order amount can never be progressed through the intended partial-fill flow again — this is a protocol-availability break caused entirely by attacker-supplied input, fitting the Medium-severity bounty criterion "smart contract unable to operate because required token/native balances can be broken by an unprivileged actor," and, since it blocks completion of an in-flight multi-fill swap, also risks temporarily freezing the maker's remaining funds during the live swap lifecycle.

### Likelihood Explanation
High likelihood: the attacker only needs to be a normal taker able to call `fillOrderArgs`/`fillContractOrderArgs` with custom `interaction` calldata for a multiple-fills order — no privileged role, no race condition, and no cost beyond a normal partial fill transaction (the attacker even completes a legitimate partial fill in the same transaction that corrupts the state).

### Recommendation
- Truncate consistently: mask/validate `takerData.idx` to the same width used for hashing/storage (e.g., require `idx <= type(uint64).max`, or better, bound `idx` to `partsAmount` before use), and/or store the same truncated value (`uint64(takerData.idx) + 1`) rather than the raw unmasked `idx + 1` in `lastValidated`.
- Explicitly `revert` if `takerData.idx` exceeds `type(uint64).max` (or the current `partsAmount` bound) instead of silently truncating in the hash computation.
- Add invariant tests/fuzzing (e.g., Echidna) asserting that no attacker-controlled index above the valid range for a given `partsAmount` can be written into `lastValidated`.

### Proof of Concept
1. Create a multiple-fills order with `partsAmount = N` and a Merkle tree of `N+1` secrets, as in `MerkleStorageInvalidatorIntTest.setUp` (`test/integration/MerkleStorageInvalidator.t.sol`).
2. Choose `idx = 0` (any valid leaf) with its real `hashedSecrets[0]` and `merkle.getProof(hashedPairs, 0)`.
3. Instead of encoding `idx` as `0`, encode `idx = 0 + 2**64` in the `interaction` bytes: `abi.encodePacked(escrowFactory, abi.encode(proof, uint256(2**64), hashedSecrets[0]))`.
4. Call `limitOrderProtocol.fillOrderArgs(...)` with a `makingAmount` corresponding to the first partial fill (as in `test_MultipleFillsFillFirst`).
5. Observe the fill succeeds (the Merkle check uses `uint64(2**64) == 0`, matching the real leaf), but `lastValidated[key].index` now equals `2**64 + 1` instead of `1`.
6. Attempt any further legitimate partial fill of the same order (e.g., `test_MultipleFillsTwoFills`-style second fill) — it now reverts with `IEscrowFactory.InvalidPartialFill`, proving the order's partial-fill mechanism is permanently broken.

    function _isValidPartialFill(
        uint256 makingAmount,
        uint256 remainingMakingAmount,
        uint256 orderMakingAmount,
        uint256 partsAmount,
        uint256 validatedIndex
    ) internal pure returns (bool) {
        uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;

        if (remainingMakingAmount == makingAmount) {
            // If the order is filled to completion, a secret with index i + 1 must be used
            // where i is the index of the secret for the last part.
            return (calculatedIndex + 2 == validatedIndex);
        } else if (orderMakingAmount != remainingMakingAmount) {
            // Calculate the previous fill index only if this is not the first fill.
            uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
            if (calculatedIndex == prevCalculatedIndex) return false;
        }

        return calculatedIndex + 1 == validatedIndex;
    }
