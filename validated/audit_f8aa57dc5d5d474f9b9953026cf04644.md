Based on the code paths I traced, there's a legitimate equality-break analog to the "unsanitized identifier used as a scope key" bug class in `stacks-signer`. The unsanitized identifier here is `TenureChangePayload::prev_tenure_consensus_hash` — a miner-supplied field inside the block, analogous to `sessionId`/`sessionFile` in the advisory — which is trusted as a lookup key for "what tenure must this block confirm" in one code path but is cross-validated against the true canonical parent tenure in another.

### Title
Stale/attacker-chosen `prev_tenure_consensus_hash` bypasses the pre-commit re-check, letting a signer's chainstate "approved-parent" check diverge from the canonical parent - (File: stacks-signer/src/v0/signer.rs)

### Summary
`GlobalStateView::check_proposal` (proposal-arrival path) validates that a tenure-change block's `prev_tenure_consensus_hash` equals the signer's independently-derived `parent_tenure_id` before ever consulting the DB/node for "does it confirm enough blocks." But the later re-check that runs at validate-ok and again at the pre-commit-threshold ("is this still consistent with our DB?") — `check_block_against_signer_db_state` — skips that equality check entirely and calls `SortitionData::check_tenure_change_confirms_parent` directly with the block's own `tenure_change.prev_tenure_consensus_hash` as the tenure identifier.

### Finding Description
In `stacks-signer/src/chainstate/v2.rs`, `GlobalStateView::validate_tenure_change_payload` explicitly enforces: [1](#0-0) 
before it will even call `SortitionData::check_tenure_change_confirms_parent`: [2](#0-1) 

This runs only once, at proposal arrival (`check_block_against_state` → `check_proposal`, per `docs/signer-flows.md`): [3](#0-2) 

But `check_block_against_signer_db_state` in `stacks-signer/src/v0/signer.rs`, which re-verifies chainstate consistency both right after node validation (`handle_block_validate_ok`) and again at the pre-commit weight threshold (`handle_block_pre_commit`), calls `check_tenure_change_confirms_parent` directly on the block's own claimed `tenure_change` payload without re-deriving/re-checking `prev_tenure_consensus_hash` against the current known-good parent tenure: [4](#0-3) 

`check_tenure_change_confirms_parent` simply forwards `tenure_change.prev_tenure_consensus_hash` as the `tenure_id` argument to `check_latest_block_in_tenure`: [5](#0-4) 

`check_latest_block_in_tenure` looks up `get_tenure_last_block_info(tenure_id, ...)` in the signer's local DB, and if that tenure is unknown/timed out locally, falls through to asking the node for the tenure tip — and if the node lookup itself fails, it defaults to **assuming the proposal is valid**: [6](#0-5) 

So the identifier that gates "does this block confirm the correct parent tenure" is taken unsanitized from the block itself at the two re-check call sites, whereas the proposal-arrival path insists it match the independently-derived `parent_tenure_id` from the active-miner state machine. If the active miner/parent-tenure view changes between proposal arrival and the pre-commit threshold being crossed (a normal, expected occurrence per section 8 of `docs/signer-flows.md`, since burn blocks and state-machine updates are processed continuously), the re-check has no mechanism to notice that the block's `prev_tenure_consensus_hash` no longer matches the canonical parent tenure — it only asks "is there a higher signed/tip block in the tenure named by this hash," which is silent (`Ok(true)`) whenever that named tenure is unknown to both the local DB and the node.

### Impact Explanation
This breaks the "approved-parent vs canonical" equality: a single miner (the only party who constructs `TenureChangePayload`) can cause the signer to sign a tenure-change block whose declared parent tenure was correct at proposal time but is no longer the canonical parent by the time the pre-commit threshold is reached, because the mismatch check (`prev_tenure_consensus_hash != parent_tenure_id`) is never repeated in the two later consistency re-checks. This can allow a stale-parent tenure-change block to be signed after the canonical parent has already changed underneath it — a signer signing a proposal that is no longer consistent with canonical chain state, which is the Critical-tier "non-canonical block" class described in the rules.

### Likelihood Explanation
Reaching pre-commit threshold minutes after proposal (during which sortition/tenure state legitimately changes) is a normal, frequently-hit code path per the documented flow (`docs/signer-flows.md` section 5), and requires no signer collusion or majority — only the proposing miner needs to submit a tenure-change block whose `prev_tenure_consensus_hash` was valid at submission time. The bug is a missing re-validation, not a crafted malformed value, so it is reachable purely through normal timing/latency between proposal and pre-commit threshold, i.e., a single miner and ordinary network conditions.

### Recommendation
Have `check_block_against_signer_db_state` (or `check_tenure_change_confirms_parent` itself) re-derive the current canonical `parent_tenure_id` (as `validate_tenure_change_payload` does from the active miner state) and re-assert `tenure_change.prev_tenure_consensus_hash == parent_tenure_id` on every re-check call site, not only at initial proposal evaluation.

### Proof of Concept
1. Miner proposes a valid tenure-change block `B` whose `prev_tenure_consensus_hash` correctly matches the then-current `parent_tenure_id`; it passes `GlobalStateView::check_proposal` and is submitted for node validation.
2. Before pre-commit threshold is reached, a new Bitcoin block/sortition arrives, updating the signer's active-miner/parent-tenure view (`ActiveMiner.parent_tenure_id` changes) — `B`'s `prev_tenure_consensus_hash` is now stale/non-canonical.
3. Node validation returns OK; `handle_block_validate_ok` calls `check_block_against_signer_db_state`, which calls `check_tenure_change_confirms_parent(tenure_change, B, ...)` using `B`'s own (now-stale) `prev_tenure_consensus_hash` — never comparing it to the updated `parent_tenure_id`.
4. If the stale tenure is unknown to this signer's local DB and the node's tenure-tip lookup for it errors, `check_latest_block_in_tenure` returns `Ok(true)` ("assume higher"), the recheck passes, and the signer pre-commits/signs `B` despite it no longer confirming the canonical parent tenure.

    ///
    /// Re-verify a block's chain length against the last signed block within signerdb.
    /// This is required in case a block has been approved since the initial checks of the block validation endpoint.
    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }
