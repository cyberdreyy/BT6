### Title
Post-default withdraw requests can permanently strand claimants’ recovery funds - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
After default recovery is finalized, a user can create a new `postDefaultRequests` receipt that is paid from `defaultRecoveryReserve`, but `finalizeDefaultRecovery` may set `defaultRecoveryPrice` above `RECOVERY_FULL` when recovered assets exceed the aggregate claim basis. The excess remains inside the reserve without any rescue path that preserves claim isolation, causing recovery funds to be permanently locked.

### Finding Description
`finalizeDefaultRecovery` calculates the recovery ratio from all recovered and already-reserved funds divided by the active and pending claim basis. If `reserveAmount > totalBasis`, `defaultRecoveryPrice` can exceed `1e18`. The full recovered amount is then assigned to `defaultRecoveryReserve`.

Relevant flow:

- Recovery basis and reserve include active claims, pending claims, prefunded instant claims, and existing reserves.
- `defaultRecoveryPrice` is `reserveAmount * RECOVERY_FULL / totalBasis`.
- All of `reserveAmount` is stored as `defaultRecoveryReserve`.
- Defaulted and post-default claims consume reserve at the configured ratio.
- `transferToken` is owner-only and unrestricted, but the stated trust model treats privileged roles as honest; there is no claim-preserving function that isolates only the excess.

This violates the intended invariant that one receipt corresponds to one reserve-backed payout while unclaimable excess recovery remains recoverable without touching claim backing. If no later post-default request is made, the above-par excess remains permanently trapped as reserve. If later requests are created, reserve accounting treats them as ordinary reserved claims even though part of the reserve is technically surplus from the earlier over-recovery.

The likely affected scenario is an honest recovery finalization where the borrower or recovery source returns more than the calculated basis—for example, including interest, liquidation proceeds, or prefunded assets not represented in `totalBasis`.

### Impact Explanation
The direct impact is permanent freezing of recovered protocol/user funds. The trapped amount is:

```solidity
lockedExcess = defaultRecoveryReserve - claimableReserveObligations
```

For `defaultRecoveryPrice > 1e18`, every claim consumes `claimBasis * defaultRecoveryPrice / 1e18`. Once the represented basis is exhausted, an amount corresponding to recovery dust or excess remains assigned to `defaultRecoveryReserve`. The reserve can only be consumed by `_transferDefaultRecovery`, and no public or privileged function releases excess while preserving the reserve invariant.

The attack surface is primarily a recovery-data/accounting defect rather than an attacker-controlled exploit primitive. It becomes economically relevant whenever recovered proceeds exceed the computed claim basis, including a positive recovery premium.

### Likelihood Explanation
Likelihood is conditional but realistic:

1. A borrower default occurs.
2. `finalizeDefault` calls `finalizeDefaultRecovery`.
3. The returned cash plus prefunded/default reserves exceeds `activeBasis + pendingBasis`.
4. `defaultRecoveryPrice` is set above `RECOVERY_FULL`.
5. Claimants consume their proportional claims, but surplus remains locked.

The code explicitly comments that “Recovery can be above par,” confirming that over-par recovery is anticipated, but it stores the entire amount in the claim reserve instead of splitting claim backing from recoverable surplus.

### Recommendation
Cap the claim reserve to the amount needed to satisfy the claim basis, and track excess separately:

```solidity
uint256 reserveForClaims;
if (recoveryPrice > RECOVERY_FULL) {
    recoveryPrice = RECOVERY_FULL;
    reserveForClaims = totalBasis;
    excessRecovery = reserveAmount - totalBasis;
} else {
    reserveForClaims = reserveAmount;
}
```

Then:

- Store `reserveForClaims` in `defaultRecoveryReserve`.
- Store the remainder in a separate `excessRecovery` variable or transfer it to the fee receiver/owner during finalization.
- Ensure `_transferFundedClaim` and `transferToken` cannot consume `defaultRecoveryReserve`.
- Add tests for `reserveAmount > totalBasis`, exact-par recovery, and below-par recovery.

### Proof of Concept
```solidity
// Foundry-style conceptual PoC.
// Assumes a defaulted pool with:
// activeBasis + pendingBasis = 100e6
// recoveredAmount + prefundedReserve + oldReserve = 110e6

function testOverParRecoveryLocksExcess() external {
    _createDefaultWithBasis(100e6);

    // Recovery source approves the strategy for the full recovered amount.
    vm.prank(recoverySource);
    underlying.approve(address(strategy), 110e6);

    vm.prank(manager);
    cdo.finalizeDefault(110e6, recoverySource);

    // Recovery price is above par.
    assertEq(strategy.defaultRecoveryPrice(), 1.1e18);

    // All recovered assets become recovery reserve.
    assertEq(strategy.defaultRecoveryReserve(), 110e6);

    // Every claimant claims their haircut/full claim.
    _claimAllDefaultedReceiptsAndActivePositions();

    // If all original basis was represented, the modeled claim obligation is 100e6.
    // Depending on the active-claim realization path, up to 10e6 remains isolated as
    // reserve surplus with no mechanism that distinguishes it from claim backing.
    assertGt(strategy.defaultRecoveryReserve(), 0);
    assertGt(underlying.balanceOf(address(strategy)), 0);
}
```
