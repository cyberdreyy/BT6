## Title
Stale confirmations from removed multisig members are still counted toward quorum, allowing requests to execute below the required live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`confirm()` in the multisig contract counts confirmations by simply checking `confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) . When a member is removed via `DeleteMember`, `delete_member()` only purges requests and confirmations *created by* that member, not confirmations that member had already cast on *other still-pending* requests [2](#0-1) . A removed member's stale confirmation therefore remains in the `confirmations` set and is still counted toward quorum, letting a request execute with fewer live-member approvals than `num_confirmations` requires. The same pattern exists in the legacy `multisig/src/lib.rs` contract's `DeleteKey` handler [3](#0-2) .

### Finding Description
The custody binding that must hold is: **confirmations counted for a request == confirmations actually cast by currently-live members**. The contract breaks this equality.

- `confirm()` records the caller's identity into `self.confirmations[request_id]` and compares the *size* of that set (plus the new confirmer) against `self.num_confirmations` [4](#0-3) . It never re-validates that every entry already stored in `confirmations` still corresponds to a member present in `self.members`.
- `delete_member()` explicitly filters and cleans up only requests where `r.member == member` — i.e., requests the removed member originally *created* — and removes that member's `num_requests_pk` bookkeeping entry [5](#0-4) . It performs no scan of the `confirmations` map to strip the departing member's confirmation string from other pending requests they had merely co-signed.
- The guard in `delete_member()` only checks that `self.members.len() - 1 >= self.num_confirmations` [6](#0-5) , which protects against making quorum unreachable, but does nothing to invalidate confirmations already contributed by the member being removed.

As a result, a confirmation cast by an account that is no longer a member is silently still "spent" toward the quorum of any other outstanding request.

### Impact Explanation
This is a **multisig request executed below threshold** — explicitly a Critical-impact custody-binding violation. The multisig contract can hold NEAR funds and authorize `Transfer`, `FunctionCall`, `AddKey`/`DeleteKey`, and `DeployContract` actions [7](#0-6) . Because a removed member's stale confirmation still counts, an action (e.g., transferring the contract's NEAR balance) can be executed with fewer genuinely live approvals than `num_confirmations` mandates, undermining the entire security guarantee the multisig is designed to provide.

### Likelihood Explanation
No attacker privilege escalation is required beyond the normal, expected multisig lifecycle: members are removed over time as part of routine key/membership rotation, which is a standard, documented operation (`DeleteMember`/`DeleteKey`). Any pending request that already accumulated confirmations from a member before that member's removal will retain the stale confirmation indefinitely, since there is no sweep or invalidation logic. The only requirement is that a request remains open (unconfirmed to completion) at the time a confirming member is removed, and that the remaining active members later confirm it — a plausible and easily triggered sequence.

### Recommendation
When removing a member (`delete_member` in `multisig2/src/lib.rs`, and `DeleteKey` in `multisig/src/lib.rs`), iterate over **all** pending requests' confirmation sets (not just requests the member itself created) and remove the departing member's identity from each. Alternatively, when tallying confirmations in `confirm()`, filter the stored confirmation set against `self.members` before comparing against `self.num_confirmations`, so that only confirmations from currently-live members count toward quorum.

### Proof of Concept
1. Initialize a multisig with 4 members (M1–M4) and `num_confirmations = 3` via `MultiSigContract::new` [8](#0-7) .
2. M4 calls `add_request` to create request `R` (e.g., a `Transfer`), then confirms it — `confirmations[R] = {M4}` (count = 1) [9](#0-8) .
3. Members legitimately approve and execute a separate `DeleteMember { member: M4 }` request, removing M4 from `self.members`. `delete_member()` only cleans requests M4 *created* (none relevant here) and leaves `confirmations[R] = {M4}` untouched [2](#0-1) .
4. M1 calls `confirm(R)` → count becomes 2 (`{M4, M1}`).
5. M2 calls `confirm(R)` → `confirmations.len() as u32 + 1 = 3 >= num_confirmations (3)`, so `execute_request(R)` runs [10](#0-9) .
6. `R` executes (e.g., transferring funds) with only 2 live-member approvals (M1, M2) instead of the required 3, because M4's stale confirmation was still counted after M4 was removed as a member.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
