### Title
ERC4626 liquidity abort can repeatedly revert `stopEpoch` and freeze withdrawal settlement - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In programmable-borrower mode, an ERC4626 vault user can make the vault temporarily unable to satisfy the liquidity recall required by `ProgrammableBorrower.onStopEpoch`. The resulting revert bubbles through `IdleCDOEpochVariant._stopEpoch`, leaving the epoch running and preventing pending withdrawal receipts from becoming claimable. This is analogous to terminating a handshake before completion: the vault withdrawal is interrupted after the credit vault has committed to stopping the epoch, but before the CDO can fund pending claims.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, ...)` before transferring funds from the borrower. [1](#0-0) 

`ProgrammableBorrower.onStopEpoch` first checks the borrower’s on-hand balance and then calls `vault.withdraw(shortfall, address(this), address(this))` for the missing amount. If the ERC4626 withdrawal reverts, the catch block intentionally reverts with `StopEpochVaultLiquidityUnavailable`. [2](#0-1) 

Because this hook is not wrapped in a `try/catch` by the CDO, the revert aborts the whole stop transaction before `collectWithdrawFunds`, `_updateAccounting`, or the normal end-of-epoch state transition executes. [3](#0-2)  The epoch therefore remains running, and normal receipt claims remain gated until the epoch number advances through a successful stop. [4](#0-3) 

An unprivileged participant in the programmable borrower’s ERC4626 vault can induce this condition by removing or borrowing enough vault liquidity that `withdraw` fails even though `convertToAssets` still reports sufficient nominal share value. The code explicitly retries transient withdrawal failures rather than defaulting, which preserves solvency but creates a repeatable settlement-abort surface. [5](#0-4) 

### Impact Explanation
All pending normal withdrawals represented by `pendingWithdraws`, along with settlement of the active LP NAV, remain unavailable for as long as the ERC4626 vault refuses the withdrawal. The frozen amount is quantified as:

`pendingWithdraws + expectedEpochInterest`, or the entire strategy-token principal in close-pool mode.

This is temporary freezing rather than direct theft: the vault shares may still represent the assets, but users cannot mature or claim receipts while the attacker keeps vault liquidity exhausted. Existing tests confirm that the failed stop leaves `isEpochRunning`, borrower accounting, and `pendingWithdraws` unchanged. [6](#0-5) 

### Likelihood Explanation
The attacker only needs to be a user of the external ERC4626 venue and the ability to keep its redeemable liquidity below the requested `shortfall`. No privileged Idle role is required. The condition is most feasible when the ERC4626 vault is highly utilized, has a withdrawal queue/cap, or permits borrowers to retain most of its liquidity through an epoch boundary.

The impact is limited to temporary freezing because the CDO intentionally retries the operation instead of treating an otherwise-covered vault withdrawal failure as borrower default. [7](#0-6) 

### Recommendation
Avoid requiring the full `shortfall` to be recalled in one external ERC4626 withdrawal. `onStopEpoch` should:

1. Use `maxWithdraw(address(this))` or an equivalent bounded recall amount.
2. Withdraw the available portion and report the actual liquidity shortfall to the CDO.
3. Let the CDO either fund what is available, enter the defined partial-loss/default path, or expose an explicit delayed-settlement state.
4. Record a liquidity retry deadline so indefinite ERC4626 illiquidity cannot keep the epoch alive forever.

At minimum, emit the available and unavailable amounts so operators can distinguish temporary vault illiquidity from borrower insolvency.

function testErc4626AbortFreezesStopEpoch() external {
    // Existing fork setup for programmable-borrower credit vault.
    _setUpProgrammableBorrowerCreditVault(
        GAUNTLET_FORK_BLOCK,
        GAUNTLET_USDC_PRIME
    );

    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);

    // A KYC-passing lender creates a pending normal withdrawal.
    uint256 pending = cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );

    _startEpochAndCheckPrices(0);
    assertGt(strategy.pendingWithdraws(), 0);

    // Attacker, as an ERC4626 vault user, makes vault liquidity unavailable.
    // In the local mock this is represented by setWithdrawLimit; on a lending
    // ERC4626 this corresponds to borrowing/reducing available cash.
    MockStopEpochLiquidityVault limitedVault =
        MockStopEpochLiquidityVault(address(programmableBorrower.vault()));
    limitedVault.setWithdrawLimit(strategy.pendingWithdraws() - 1);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Settlement aborted before state transition; receipts remain immature.
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pending);

    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}

    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

contract MockStopEpochLiquidityVault is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public withdrawLimit = type(uint256).max;

  constructor(address _asset) ERC20("Stop Epoch Liquidity Vault", "SELV") {
    assetToken = IERC20Detailed(_asset);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    if (supply == 0) return shares;
    return shares * assetToken.balanceOf(address(this)) / supply;
  }

  function maxWithdraw(address owner) external view returns (uint256) {
    uint256 assets = convertToAssets(balanceOf(owner));
    return assets < withdrawLimit ? assets : withdrawLimit;
  }

  function setWithdrawLimit(uint256 assets) external {
    withdrawLimit = assets;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0 ? assets : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function withdraw(uint256 assets, address receiver, address owner) external returns (uint256 shares) {
    require(assets <= withdrawLimit, "insufficient-liquidity");
    shares = _toSharesRoundUp(assets);
    if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function redeem(uint256 shares, address receiver, address owner) external returns (uint256 assets) {
    assets = convertToAssets(shares);
    require(assets <= withdrawLimit, "insufficient-liquidity");
    if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function _toSharesRoundUp(uint256 assets) internal view returns (uint256 shares) {
    uint256 supply = totalSupply();
    uint256 managedAssets = assetToken.balanceOf(address(this));
    if (supply == 0 || managedAssets == 0) return assets;
    shares = assets * supply / managedAssets;
    if (shares * managedAssets < assets * supply) shares += 1;
  }
}
