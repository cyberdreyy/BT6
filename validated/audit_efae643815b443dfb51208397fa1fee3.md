This confirms the concrete analog. Base's `batch_mint` (both `B20Asset` and callers via the `IB20Asset::batchMint` precompile ABI) mints to a list of recipients in a single loop, and each inner call to `mint()` re-enforces the `MintReceiver` policy per recipient via `B20Guards::ensure_policy_type(token, B20PolicyType::MintReceiver, to)`, propagating any `Err` out of the loop with `?`. Because the batch is documented and implemented as "All-or-nothing," a single blocklisted/non-allowlisted recipient anywhere in the `recipients` array reverts the entire batch and prevents mints to every other, legitimate recipient in that same call — mirroring the H-02 pattern where one unwithdrawable/blacklisted party blocks a shared, batched operation for everyone else.

### Title
Single policy-blocked recipient in `batchMint` reverts mints to all other recipients (all-or-nothing DoS) - (File: crates/common/precompiles/src/b20_asset/logic/v1.rs, crates/common/precompiles/src/b20_asset/logic/v2.rs)

### Summary
`B20Asset::batchMint` iterates a caller-supplied `recipients`/`amounts` array and calls the same `mint()` logic used by the single-recipient path for every entry, propagating the first error with `?`. `mint()` unconditionally re-checks the `MintReceiver` policy for each recipient, even when the caller is privileged. Because the array is applied atomically ("All-or-nothing" per the doc comment), a single entry whose address is blocked by the token's `MintReceiver` policy aborts the whole transaction, denying the mint to every co-batched recipient.

### Finding Description
`batchMint` is declared "All-or-nothing" in the ABI doc comment [1](#0-0) , and the loop that implements it calls `self.mint(token, caller, recipient, amount, true)?` for each pair, so the first failing recipient short-circuits the remaining ones [2](#0-1) . `mint()` enforces the `MintReceiver` policy on every call regardless of the `privileged` flag: `B20Guards::ensure_policy_type(token, B20PolicyType::MintReceiver, to)?` [3](#0-2) . A test explicitly documents that this policy check is bypass-proof even for privileged callers: "The inner mints enforce the MintReceiver policy even when privileged" [4](#0-3) , and a dedicated action test shows a single `MINT_RECEIVER_POLICY`-blocked recipient reverting a mint transaction outright: "mint must revert when recipient is blocked by MINT_RECEIVER_POLICY" [5](#0-4) . The same pattern exists verbatim in the V1 logic module [6](#0-5) .

Any account can become "blocked" for `MintReceiver` purposes if the token admin has wired an `ALLOWLIST`/`BLOCKLIST` `PolicyRegistry` policy to that scope — the same mechanism demonstrated in `updatePolicy({policyScope: MintReceiver, ...})` tests [7](#0-6) . Once such a policy is active, any address excluded from it (e.g. removed from an allowlist, or newly added to a blocklist) will cause `batchMint` calls that include it to revert entirely, even though every other recipient in the batch is fully compliant.

### Impact Explanation
This maps to the H-02 report's DoS class: a single non-compliant/blocked party inside a shared, batched operation blocks legitimate value transfer to every other party in that same call. Here, an operator running a payroll- or airdrop-style `batchMint` that includes even one now-blocked address (deliberately or accidentally) cannot mint to any of the other, otherwise-eligible recipients in that transaction — the whole batch reverts. This is a griefing/DoS vector against the token issuer's batch-mint workflow: a malicious insider who knows they will later be blocklisted, or anyone who can get added to a blocklist, can be included in a batch to force full-transaction failure, wasting gas and blocking value delivery to co-batched legitimate recipients until the issuer manually detects and removes the offending entry and resubmits.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the token to have a `MintReceiver` policy actually wired (not the default `ALWAYS_ALLOW`), and (b) at least one entry in a `batchMint` call to be excluded by that policy. Both conditions are entirely realistic for regulated/whitelisted B-20 assets, which is precisely the use case the `PolicyRegistry`/`MintReceiver` scope exists for [8](#0-7) . Given the ABI explicitly documents "All-or-nothing" semantics as an intentional design choice [1](#0-0) , this is a design-level tradeoff rather than an accidental omission, but it still creates a reachable operational DoS whenever an issuer batches multiple recipients together under an active receiver policy.

### Recommendation
Either (a) explicitly document and enforce that `batchMint` callers must pre-filter recipients against the currently-wired `MintReceiver` policy before submission (and provide a view function to check authorization per-address so integrators can pre-validate), or (b) offer a best-effort/partial variant of `batchMint` that skips and reports individually-blocked recipients rather than reverting the entire batch, mirroring the "wrap transfers in a try/catch"-style mitigation adopted for the analogous C4 finding. If atomicity is a deliberate business requirement (e.g., for accounting simplicity), keep the current all-or-nothing behavior but ensure operational tooling always dry-runs/simulates each recipient's `MintReceiver` authorization before constructing a batch, so a blocked recipient never silently blocks the whole batch on-chain.

### Proof of Concept
1. Token admin wires an `ALLOWLIST` policy to `B20PolicyType::MintReceiver` (as in `b20_always_block_mint_receiver_policy_blocks_mint_recipient` [9](#0-8) ), or a `BLOCKLIST` policy that includes one target address.
2. A mint-role holder calls `batchMint(recipients=[good_1, good_2, blocked_addr], amounts=[...])`.
3. The loop in `batch_mint` reaches `blocked_addr`, and the inner `mint()` call's `B20Guards::ensure_policy_type(token, B20PolicyType::MintReceiver, to)` reverts with `PolicyForbids` [10](#0-9) .
4. The `?` propagation aborts the whole `batchMint` transaction — `good_1` and `good_2` receive nothing, matching the "All-or-nothing" contract, despite being fully compliant recipients [11](#0-10) .

    fn batch_mint(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        recipients: Vec<Address>,
        amounts: Vec<U256>,
        privileged: bool,
    ) -> Result<()> {
        // The pause and role guards below are the sole authorization gate for the batch: the inner
        // mints run privileged to avoid re-checking per recipient. Do not remove or conditionalize
        // these guards. Check order: PAUSE -> ROLE -> INPUT -> BUSINESS.
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::MINT)?;
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::Mint)?;
        }
        if recipients.len() != amounts.len() {
            return Err(BasePrecompileError::revert(IB20Asset::LengthMismatch {
                leftLen: U256::from(recipients.len()),
                rightLen: U256::from(amounts.len()),
            }));
        }
        if recipients.is_empty() {
            return Err(BasePrecompileError::revert(IB20Asset::EmptyBatch {}));
        }
        for (recipient, amount) in recipients.into_iter().zip(amounts) {
            self.mint(token, caller, recipient, amount, true)?;
        }
        Ok(())
    }

#[tokio::test]
async fn b20_always_block_mint_receiver_policy_blocks_mint_recipient() {
    let mut scenario = B20PolicyScenario::new().await;

    let grant_mint_role = scenario.token_tx(IB20::grantRoleCall {

        account: BerylTestEnv::alice(),

    assert!(scenario.env.user_tx_succeeded(&block, 0), "MINT_ROLE grant must succeed");

    let mint_allowed =
        scenario.token_tx(IB20::mintCall { to: BerylTestEnv::bob(), amount: TRANSFER_AMOUNT });
    let block = scenario.build_block(vec![mint_allowed]).await;
    assert!(
        scenario.env.user_tx_succeeded(&block, 0),
        "mint must succeed before policy is blocked"
    );
    scenario.assert_balance(BerylTestEnv::bob(), 1);

    let wire_mint_receiver = scenario.token_tx(IB20::updatePolicyCall {
        policyScope: B20PolicyType::MintReceiver.id(),
        newPolicyId: PolicyRegistryStorage::ALWAYS_BLOCK_ID,
    });
    let block = scenario.build_block(vec![wire_mint_receiver]).await;

    );

    scenario.assert_balance(BerylTestEnv::carol(), 0);
