### Title
Instant-withdraw receipts claimed at par between default and `finalizeDefault` are re-counted as pending basis and phantom prefunded reserve, inflating `defaultRecoveryPrice` and draining the recovery reserve — (`File: contracts/strategies/idle/IdleCreditVault.sol`)

### Summary

The external bug is a callback (`ndo_set_rx_mode`) that is invoked under two different calling contexts (with and without the RTNL lock) and misbehaves because it assumes one fixed context; the fix defers execution to a work queue. The direct analog in this codebase is `IdleCreditVault.claimInstantWithdrawRequest`: the same receipt-claim path executes under two different accounting contexts — the normal "funded claim" context and the post-`finalizeDefaultRecovery` context — without clearing the per-epoch receipt ledgers (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`). In the window between a defaulting `stopEpoch` (which sets `allowInstantWithdraw = true`) and `finalizeDefault`, a lender can claim their instant receipt at par via `_transferFundedClaim`, after which finalization still counts that same receipt as outstanding claim basis and as already-held "prefunded" reserve. The recovery price is therefore computed over phantom assets, letting early claimants drain the real reserve while later claims permanently revert.

### Finding Description

The instant-withdraw claim path in `contracts/strategies/idle/IdleCreditVault.sol:380-393` burns the aggregate `instantWithdrawsRequests[_user]` and pays `_amount` through `_transferFundedClaim`, but it never:

- clears `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (set in `requestInstantWithdraw`, lines 367-372),
- decrements `instantWithdrawClaimsByEpoch[epochNumber]` or `pendingInstantWithdraws`.

The per-epoch ledgers are only ever cleared inside `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which is reachable only after `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`.

Meanwhile `IdleCDOEpochVariant._handleBorrowerDefault` (contracts/IdleCDOEpochVariant.sol:219-221) deliberately sets `allowInstantWithdraw = true` so instant claims stay possible, and `IdleCDOEpochVariant.claimInstantWithdrawRequest` (lines 975-979) checks only that flag. So after a defaulting `stopEpoch` and before the manager calls `finalizeDefault` (which is a separate, non-atomic transaction invoking `finalizeDefaultRecovery`, contracts/IdleCDOEpochVariant.sol:194-199), any lender with an instant receipt in the current epoch can claim it **at par**.

At finalization, `defaultPendingClaimBasis` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve` (lines 716-723) credits `instantBasis - pendingInstant` as already-held reserve. Both still include the already-paid attacker receipt, so:

- `totalBasis` is inflated (the paid receipt is counted twice in substance: it was already redeemed yet remains in basis),
- `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` counts underlyings that were already transferred out, inflating `defaultRecoveryPrice` (line 688) above what the strategy actually holds,
- `defaultInstantWithdrawsFinalized` is set true (line 696), activating the default-epoch claim path whose `_burn`/`instantWithdrawsRequests[_user] -= claimBasis` (line 848) underflows for the attacker (harmless to them — they already exited) while honest claimants are paid from a reserve that is smaller than `defaultRecoveryReserve` claims.

The funded-claim guard `_transferFundedClaim` (lines 897-907) only protects `defaultRecoveryReserve` *after* finalization (`reserve != 0`); before finalization the reserve is typically zero, so the pre-finalization claim can also consume underlyings earmarked for other funded receipts.

### Impact Explanation

Unprivileged KYC-passed lenders holding instant-withdraw receipts in the defaulting epoch can:

1. Be paid **at par** during the gap, extracting the unfunded portion of their receipt from underlyings that belong to other claimants or to the recovery pool (theft, not merely a haircut escape).
2. Cause `defaultRecoveryPrice` to be computed over phantom prefunded assets, so subsequent `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls pay out more than the real balance until the strategy's underlying is exhausted; all later recovery claims then revert in `_transferDefaultRecovery`/`safeTransfer` — permanent freezing of the remaining claimants' recovery funds.

Loss is bounded by the current-epoch instant claim basis (`instantWithdrawClaimsByEpoch[epochNumber]`), which is a quantified, real fund impact: direct theft of funded recovery underlyings plus insolvency of the reserve for honest claimants.

### Likelihood Explanation

The preconditions are: instant withdrawals enabled (non-programmable borrower, `disableInstantWithdraw == false`), an epoch where instant requests are only partially funded at `startEpoch` (`pendingInstant > totUnderlyings` branch, contracts/IdleCDOEpochVariant.sol:286-289, or partial `collectInstantWithdrawFunds`), and the borrower then defaulting so `stopEpoch` routes to `_handleBorrowerDefault`. `stopEpoch` and `finalizeDefault` are separate privileged transactions, so the exploit window exists in every default scenario — the attacker simply needs one transaction in between, which they can always land since `claimInstantWithdrawRequest` is permissionless once `allowInstantWithdraw` is set. No malicious privileged role is required; owner/manager act honestly in sequence.

### Recommendation

Mirror the kernel fix's intent — make the claim behave identically regardless of invocation context — by making `claimInstantWithdrawRequest` state-consistent:

- When `defaulted()` is true but recovery is not yet finalized, either revert instant claims entirely in `IdleCDOEpochVariant.claimInstantWithdrawRequest` until `defaultRecoveryFinalized`, or route them through a path that settles against the not-yet-finalized haircut.
- Alternatively, clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` (and track per-user funded vs unfunded portions) inside `claimInstantWithdrawRequest`, so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` never count already-redeemed receipts.
- The minimal safe fix is a `defaulted` gate on the CDO-side `claimInstantWithdrawRequest` so no funded-claim path runs between `_handleBorrowerDefault` and `finalizeDefaultRecovery`.

### Proof of Concept

Foundry fork PoC sketch (built on `test/foundry/IdleCDOEpochQueue.t.sol` helpers such as `_useStandardEpochVariant`, `_depositWithUser`, `_stopCurrentEpochWithApr`, and the pattern in `testProcessPostDefaultWithdrawalAsNormalClaim`):

```solidity
function testInstantClaimBetweenDefaultAndFinalizeDrainsRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);               // buffer of epoch N, apr 10%

    // enable instant withdrawals
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address attacker = makeAddr('attacker');
    address honest   = makeAddr('honest');
    uint256 tA = _depositWithUser(attacker, 50e6);
    uint256 tH = _depositWithUser(honest,   50e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();
    _stopCurrentEpochWithApr(1e18);                // apr drops -> instant mode armed

    // attacker + honest file instant withdraw requests during buffer
    vm.prank(attacker); cdoEpoch.requestWithdraw(tA, address(tranche));
    vm.prank(honest);   cdoEpoch.requestWithdraw(tH, address(tranche));

    // startEpoch: CDO holds less than pendingInstant -> only partial funding
    // (arrange via deposits/loss so totUnderlyings < pendingInstant)
    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // borrower defaults: empty borrower wallet, warp past epochEndDate
    deal(address(underlying), strategy.borrower(), 0, true);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(cdoEpoch.owner());
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());
    assertTrue(cdoEpoch.allowInstantWithdraw());   // gate is open pre-finalize

    // ATTACK: claim instant receipt at par before finalizeDefault
    uint256 aPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();        // pays full receipt at par
    assertGt(underlying.balanceOf(attacker) - aPre, 0);

    // stale ledgers still count the paid receipt
    assertEq(
        strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()),
        tA, // still nonzero -> counted in basis + prefunded reserve
    );

    // manager finalizes with recovered funds
    uint256 recovered = /* ... */;
    deal(address(underlying), manager, recovered, true);
    vm.startPrank(manager);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // recoveryPrice was computed over phantom assets:
    // honest user's recovery claim either overpays relative to real balance
    // (draining reserve) or reverts once reserve is exhausted.
    vm.expectRevert(); // reserve exhausted by inflated price / prior claims
    vm.prank(honest);
    cdoEpoch.claimInstantWithdrawRequest();
}
```

The key assertion is that `instantWithdrawsRequestsByEpoch[attacker][epochNumber]` (and therefore `instantWithdrawClaimsByEpoch`/`defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`) still includes a receipt that was already paid out at par, so `defaultRecoveryPrice` exceeds the ratio backed by actual underlyings and the tail claimants are left with an insolvent reserve.

Caveat: I could not fully verify the exact balance bookkeeping in `sendInterestAndDeposits`/`collectInstantWithdrawFunds` edge cases within the iteration limit, but the ledger-clearing asymmetry in `claimInstantWithdrawRequest` vs `_claimDefaultedInstantWithdrawRequest` and the open `allowInstantWithdraw` gate after `_handleBorrowerDefault` are directly visible in the cited code.     _onlyIdleCDO();

```text
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.

    _burn(_user, amount);

    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
