**No vulnerability found for this question.**

The claimed attack is not possible because `create_vesting_contract` derives the target `AdminStore` address strictly from the transaction signer, not from any attacker-controllable parameter:

```
let admin_address = signer::address_of(admin);
if (!exists<AdminStore>(admin_address)) {
    move_to(admin, AdminStore { vesting_contracts: vector::empty<address>(), ... });
};
...
let admin_store = borrow_global_mut<AdminStore>(admin_address);
admin_store.vesting_contracts.push_back(contract_address);
``` [1](#0-0) 

Both the `move_to` initialization and the subsequent `borrow_global_mut<AdminStore>` lookup use `admin_address`, which is `signer::address_of(admin)` — i.e., the address of whichever account actually signs the transaction. Move's type system guarantees a `&signer` cannot be forged or obtained for an account the transaction sender does not control, so it is impossible for an attacker to make this function write into a different admin's `AdminStore.vesting_contracts` vector. The new vesting contract address is always appended to the caller's own store.

The `types/src/vesting.rs` file cited in the question, `VestingAdminStore`, is only a Rust-side deserialization mirror used by tooling (e.g., the CLI's `RequestCommission` command) to read the on-chain `0x1::vesting::AdminStore` resource — it is not an entrypoint and has no bearing on which admin's store gets mutated on-chain. [2](#0-1) [3](#0-2) 

The Move specification also documents this invariant explicitly: creating a vesting contract account requires the signer (admin) to own the admin store, and the `vesting_contracts(admin)` getter/spec confirms the store is keyed and read by the specific `admin` address, not attacker-supplied. [4](#0-3) [5](#0-4) 

There is no unprivileged path that lets an attacker append to, or otherwise corrupt, another admin's `AdminStore.vesting_contracts`.
