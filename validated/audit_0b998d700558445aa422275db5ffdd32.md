### Title
Gateway routes legacy user requests to any DON solely by attacker-controlled `msg.Body.DonId` with no membership check, and the WebAPI handler forwards them to all DON nodes without an allowlist check - (File: core/services/gateway/gateway.go, core/services/gateway/handlers/capabilities/handler.go)

### Summary
`gateway.(*gateway).ProcessRequest` selects the target DON handler purely by looking up `msg.Body.DonId` (attacker-supplied) in `g.handlers`, with no check that the signer is a member of that DON. `msg.Validate()` only verifies the signature is internally consistent with the message body (including `DonId`), not that the signer belongs to the DON named in `DonId`. The WebAPI capabilities `HandleLegacyUserMessage` then forwards the request to every node of that (unrelated) DON with an explicit `// TODO: apply allowlist and rate-limiting here` comment, meaning no allowlist enforcement happens at the gateway layer.

### Finding Description
In `core/services/gateway/gateway.go` (`ProcessRequest`, lines 250-262), when `msg.Body.DonId != ""` the code does: [1](#0-0) 
`msg.Validate()` is called, but validation (`core/services/gateway/api/message.go`, lines 54-88) only checks field lengths/format and that the signature recovers to *some* signer consistent with the signed bytes (`MessageId`, `Method`, `DonId`, `Receiver`, `Payload`): [2](#0-1) 
Because `DonId` is part of the signed payload, an attacker who controls only their own private key can freely choose *any* `DonId` value (including one belonging to a DON they are not a member of) and produce a self-consistent signature — `Validate()` has no notion of "this signer is authorized for this DON," it only confirms the signer signed exactly this content. The gateway then does a raw map lookup `g.handlers[handlerKey]` using that attacker-chosen `DonId` and, if it matches any configured DON, dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` for that unrelated DON's handler.

For the WebAPI capabilities handler (`core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage`, lines 341-421), the message is processed and forwarded to **all** members of that target DON's `donConfig.Members` without any authorization/allowlist check — this is confirmed by the code comment `// TODO: apply allowlist and rate-limiting here` immediately preceding the method-name check: [3](#0-2) 
This matches the corresponding test file's own acknowledgment that this is an open item: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`. [4](#0-3) 

### Impact Explanation
An attacker with a valid signing key (which need not be tied to any particular DON) can craft a legacy `api.Message` with `DonId` set to any DON configured on the gateway and have it routed to that DON's handler and forwarded to all of that DON's nodes as a well-formed trigger request. This is a DON-ID binding / cross-tenant authorization gap at the gateway layer: the gateway does not verify DON membership before dispatch, deferring that entirely to node-side logic. The concrete impact is bounded by what node-side processing (e.g., workflow/allowlist checks inside the WebAPI trigger capability on the receiving nodes) does with an unauthorized sender — this repo does not show gateway-level protection, and the explicit TODO confirms the gap is real and unaddressed at this layer. Full confirmation of end-to-end exploitability (i.e., whether node-side trigger logic independently rejects unauthorized senders) could not be completed within the available investigation — the node-side `core/capabilities/webapi/trigger/trigger.go` allowlist logic was located but not fully reviewed.

### Likelihood Explanation
Low additional privilege is required: any entity capable of signing a legacy gateway message (an attacker with an ECDSA key, no DON membership or credentials required) can set an arbitrary `DonId` in the request body. The request will pass `msg.Validate()` as long as it is well-formed and self-signed, and will be routed to the target DON's handler purely based on the `DonId` string matching a configured DON ID in `g.handlers`. This is fully repeatable and requires no timing/race conditions or special network position — it is a straightforward crafted-request attack.

### Recommendation
Enforce DON membership at the gateway/handler layer before dispatching: verify `msg.Body.Sender` (post-`Validate()`) against an authorized-sender/allowlist for the target `DonId` before calling `HandleLegacyUserMessage`, or reject requests where the signer is not a recognized principal for that DON. Implement the pending `// TODO: apply allowlist and rate-limiting here` in `core/services/gateway/handlers/capabilities/handler.go` so unauthorized cross-DON messages are rejected at the gateway rather than being forwarded to node infrastructure.

### Proof of Concept
Go handler-level integration test plan:
1. Configure a gateway with two DON handlers, `donA` (with member keys/allowlist for sender X) and `donB` (with member keys/allowlist for sender Y), using `capabilities.NewHandler` (or the mock-backed handler from `gateway_test.go`).
2. Generate an unrelated attacker keypair Z that is not a member of either DON.
3. Build an `api.Message` with `Body.DonId = "donB"`, `Body.Method = MethodWebAPITrigger`, and a valid `TriggerRequestPayload`; sign it with attacker key Z (`msg.Sign(privateKeyZ)`), matching the pattern in `core/services/gateway/handlers/capabilities/handler_test.go` `triggerRequest`.
4. Call `gw.ProcessRequest(ctx, rawSignedRequest, "")` and assert:
   - The request is routed to `donB`'s handler (`h.handlers["donB"]`), confirmed via mock `don.SendToNode` call assertions.
   - `HandleLegacyUserMessage` is invoked and forwards the message to `donB`'s member nodes despite `msg.Body.Sender` (attacker Z) not being an authorized member of `donB`.
5. Expected (failing) assertion demonstrating the bug: `don.AssertNotCalled(t, "SendToNode", ...)` for `donB`'s nodes when sender is not an authorized member — this currently fails because no such check exists, proving the gap.

// Message signatures are over the following data:
//  1. MessageId aligned to 128 bytes
//  2. Method aligned to 64 bytes
//  3. DonId aligned to 64 bytes
//  4. Receiver (in hex) aligned to 42 bytes
//  5. Payload (raw bytes before parsing)
func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := gw_common.SignData(privateKey, rawData...)
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(crypto.PubkeyToAddress(privateKey.PublicKey).Hex())
	return nil
}
