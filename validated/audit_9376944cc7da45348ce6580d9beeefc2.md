## Title
`getSignatureStatuses` returns internally inconsistent, mixed-slot confirmation data because mutable commitment state is re-read per-signature instead of snapshotted once for the whole batch - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_signature_statuses` fetches a single "processed" `Bank` once before iterating over the caller-supplied signature list, but then calls `get_transaction_status()` once per signature [1](#0-0) . Inside that per-item helper, two additional mutable, concurrently-updated pieces of shared state are re-read fresh on every iteration: the "confirmed" bank via `self.bank(Some(CommitmentConfig::confirmed()))` and the `block_commitment_cache` RwLock [2](#0-1) . This is the same bug class as the reported Bancor formula issue: a value that should be fixed for the duration of one logical "batch" (here, one JSON-RPC response covering many signatures) is instead read live and can change mid-batch due to concurrent state mutation (new blocks becoming confirmed/rooted between iterations), producing an internally-inconsistent response.

### Finding Description
`get_signature_statuses` snapshots only the "processed" bank once: `let bank = self.bank(Some(CommitmentConfig::processed()));` [3](#0-2) . It then loops over every requested signature and, for each, calls `self.get_transaction_status(signature, &bank)` [4](#0-3) .

`get_transaction_status` independently re-fetches the "confirmed" commitment bank and the `block_commitment_cache` fresh on every single call:
```rust
fn get_transaction_status(&self, signature: Signature, bank: &Bank) -> Option<TransactionStatus> {
    let (slot, status) = bank.get_signature_status_slot(&signature)?;
    let optimistically_confirmed_bank = self.bank(Some(CommitmentConfig::confirmed()));
    let optimistically_confirmed = optimistically_confirmed_bank.get_signature_status_slot(&signature);
    let r_block_commitment_cache = self.block_commitment_cache.read().unwrap();
    let confirmations = if r_block_commitment_cache.root() >= slot
        && is_finalized(&r_block_commitment_cache, bank, &self.blockstore, slot)
    { None } else { r_block_commitment_cache.get_confirmation_count(slot).or(Some(0)) };
    ...
}
``` [5](#0-4) 

`self.bank(commitment)` for the `Confirmed` case reads `optimistically_confirmed_bank` under its own `RwLock`, independent of the fixed `bank` from the caller [6](#0-5) . Both `optimistically_confirmed_bank` and `block_commitment_cache` are mutated concurrently and continuously by the validator's replay/vote-listener pipeline (root advances, new confirmed banks are swapped in) while a single `getSignatureStatuses` RPC call is being served, since the loop over signatures is not wrapped in any single consistent snapshot.

As a result, for a single client request containing multiple signatures, signature N might be evaluated against optimistic-confirmation state and commitment-cache root as of time T1, while signature N+1 (processed a few lines later, potentially after other threads have advanced state) is evaluated against a materially different, more-advanced root/optimistic-bank state at time T2. This is precisely the "value read fresh mid-batch instead of snapshotted once" bug class described in the Bancor formula report — instead of a market-maker computing prices in a batch off a single formula reference, this RPC endpoint computes `confirmation_status`/`confirmations` for a single logical batch (one API response) off values that can silently shift between array elements.

### Impact Explanation
This yields wrong/inconsistent fork-commitment data returned to unprivileged callers of the public `getSignatureStatuses` JSON-RPC method: within one response, some entries can report `Finalized` while a "more recent" signature in the same call incorrectly reports `Confirmed`/`Processed` based on state that had not yet advanced when it was computed, or vice versa, misrepresenting the actual point-in-time state of the node. Callers (wallets, exchanges, bridges) commonly use `getSignatureStatuses` in a single call to make finality decisions across many transactions; internally inconsistent confirmation levels within one response can lead to incorrect finality assumptions.

### Likelihood Explanation
This requires no special privileges — a single unprivileged `getSignatureStatuses` JSON-RPC call with multiple signatures is sufficient, and the underlying commitment-cache/optimistically-confirmed-bank updates happen continuously and independently of the caller on any live, active validator. The race window grows with the number of signatures per call (up to `MAX_GET_SIGNATURE_STATUSES_QUERY_ITEMS`) and with commitment-cache update frequency, both of which are effectively out of caller's control but naturally occurring, making the race easy to hit in practice on a busy node.

### Recommendation
Snapshot the "confirmed" bank and the `block_commitment_cache` contents (or the whole `CommitmentSlots`) once at the top of `get_signature_statuses`, before the per-signature loop, and pass these fixed snapshots into `get_transaction_status` for every iteration, mirroring the recommended fix for the Bancor case (freeze the mutable dependency for the duration of the batch rather than re-reading it per item).

### Proof of Concept
1. Start a validator RPC node under normal operation so `optimistically_confirmed_bank` and `block_commitment_cache` are updated continuously by replay/vote-listener threads.
2. Submit a `getSignatureStatuses` request with a large list of many recent signatures (multiple slots' worth) in a single call.
3. While the request is processing signature-by-signature in the loop at `rpc/src/rpc.rs:1687-1727`, the background threads root a new slot / advance `optimistically_confirmed_bank`, exactly in between two iterations of the loop.
4. Observe the JSON response: early entries in the array reflect the pre-advance commitment state and later entries reflect the post-advance state (e.g., differing `confirmation_status` classification for signatures from adjacent slots that should be classified consistently), demonstrating the batch is not computed against a single consistent view.
