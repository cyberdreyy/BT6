### Title
`SetNumConfirmations` request action can set `num_confirmations` above the live member count, permanently freezing multisig funds - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
The multisig contracts enforce the invariant `num_confirmations <= members.len()` at construction time and when deleting a member, but the `SetNumConfirmations` request action — which lets members change the confirmation threshold at runtime — performs no such check. A confirmed `SetNumConfirmations` request can set the threshold above the number of live members (or an arbitrarily large value), after which no future request, including one to lower the threshold back down, can ever gather enough confirmations. This permanently freezes the account and any NEAR balance it holds.

### Finding Description
At initialization, `MultiSigContract::new` asserts `members.len() >= num_confirmations`: [1](#0-0) 

`delete_member` similarly enforces the same invariant whenever a member is removed: [2](#0-1) 

However, the `SetNumConfirmations` branch of `execute_request` sets `self.num_confirmations` directly from user input with no bound check against `self.members.len()` (or against the previous value): [3](#0-2) 

The same missing check exists in the original `multisig/src/lib.rs` implementation: [4](#0-3) 

This is the same bug class as the reported `HatsSignerGateBase._setTargetThreshold()` issue: one code path (`new` / `delete_member` for `targetThreshold`/`minThreshold` in the Hats case) enforces a threshold-vs-population invariant, while a sibling mutator (`SetNumConfirmations` for `_setTargetThreshold`) that changes the same guarded value skips the check entirely, allowing the invariant `num_confirmations <= members.len()` (i.e. "confirmations counted versus live members") to be violated.

### Impact Explanation
Once `num_confirmations` exceeds `members.len()`, `confirm()` can never satisfy `confirmations.len() + 1 >= self.num_confirmations` for any request, including a corrective `SetNumConfirmations` request to lower the threshold again: [5](#0-4) 

Since no member and no code path in the contract can execute another action once this state is reached, all NEAR held by the multisig account, and all administrative control over it (adding/removing keys, upgrading the contract), are permanently frozen. This matches the "Critical - funds permanently frozen" impact category.

### Likelihood Explanation
Any legitimately confirmed `SetNumConfirmations` request can trigger this — no special privilege beyond being a normal multisig member is required, and if the multisig is currently configured with `num_confirmations = 1` (a valid, common configuration for e.g. a 1-of-N setup), a single member acting alone can set the threshold arbitrarily high and lock the account with a single transaction. Even in K-of-N configurations with K>1, the check is entirely absent, so any group that confirms such a request (by mistake or intentionally) bricks the account with no recovery path in-contract.

### Recommendation
Add a bound check in the `SetNumConfirmations` branch of `execute_request` in both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, mirroring the check already used in `new()` and `delete_member()`:
```rust
MultiSigRequestAction::SetNumConfirmations { num_confirmations } => {
    self.assert_one_action_only(receiver_id, num_actions);
    assert(
        num_confirmations as u64 <= self.members.len(), // or access-key count in multisig v1
        "num_confirmations must not exceed number of members",
    );
    self.num_confirmations = num_confirmations;
    return PromiseOrValue::Value(true);
}
```

### Proof of Concept
1. Deploy `multisig2` with `members = [A]` (or any set) and `num_confirmations = 1`.
2. Member `A` calls `add_request_and_confirm` with a `SetNumConfirmations { num_confirmations: 100 }` request. Since `num_confirmations` is currently `1`, this single confirmation immediately executes and sets `self.num_confirmations = 100` — no check rejects it because `members.len()` (1) is never compared against the new value.
3. From this point, `confirm()` can never reach `confirmations.len() + 1 >= 100` with only 1 member, so no request — including a `SetNumConfirmations` request to restore a sane threshold — can ever be confirmed and executed again.
4. Any NEAR balance held by the multisig account, and control over its access keys/contract code, is now permanently inaccessible. [1](#0-0) [3](#0-2) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
