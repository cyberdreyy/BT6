### Title
Deny-List v2 Execution-Time Recipient Check Bypassed via Coin Wrapping — (`sui-execution/latest/sui-adapter/src/static_programmable_transactions/execution/context.rs`)

### Summary
The execution-time deny-list v2 check only collects coin recipients by calling `coin_type_maybe()` on each entry in `written_objects`. Because `Coin<T>` has the `store` ability it can be wrapped inside any custom struct, causing the coin object to disappear from `written_objects` and be replaced by a wrapper whose type returns `None` from `coin_type_maybe()`. The denied recipient's address is therefore never submitted to `check_coin_deny_list_v2_during_execution`, and the deny check silently passes.

### Finding Description
`check_coin_deny_list_v2_during_execution` is fed a map built by the loop at lines 2393–2403 of `context.rs`. The loop calls `object.type_().and_then(|ty| ty.coin_type_maybe())` and only inserts an owner when that returns `Some`. `coin_type_maybe()` is defined to return `Some` only for `MoveObjectType_::GasCoin` and `MoveObjectType_::Coin(inner)`; any other struct — including a user-defined wrapper — maps to `MoveObjectType_::Other(_)` and returns `None`. When a `Coin<T>` is wrapped, the coin object is consumed and its bytes are embedded in the wrapper; the wrapper is what appears in `written_objects`. The wrapper's type is `Other(...)`, so `coin_type_maybe()` → `None`, the owner is not collected, and the deny check never fires for the recipient.

The signing-time check (`check_coin_deny_list_v2_during_signing`) only checks the **sender** against coin types present in input objects. It does not check the recipient, and it also uses `coin_type_maybe()`, so a wrapper input also evades it.

### Impact Explanation
A denied address can receive regulated coin value wrapped in a custom struct, violating the invariant that all regulated coin recipients are checked at execution time. The denied address can hold the wrapper, transfer it freely (no deny check fires on wrapper transfers), and can unwrap and re-transfer the coin to a third address in a single transaction — with neither the signing-time nor the execution-time check firing — effectively laundering regulated coin value through a sanctioned address. This constitutes harmful smart-contract behavior: the deny-list enforcement guarantee offered to regulated coin issuers is silently broken for any coin with the `store` ability (which includes all standard `Coin<T>`).

### Likelihood Explanation
Exploitability requires only: (1) a published package containing a wrapper struct (any ordinary package publish), and (2) a non-denied address holding the regulated coin. Both are standard public transaction paths. No privileged role, leaked key, or malicious validator is needed.

### Recommendation
The execution-time check must account for wrapped coins. Options include:
- Tracking coin-wrapping events at the VM level and adding the wrapper recipient's address to `receiving_funds_type_and_owners` with the wrapped coin's type.
- Recursively inspecting the BCS contents of written objects for embedded `Balance<T>` or `Coin<T>` fields when the object type is not itself a coin.
- Restricting `Coin<T>` from having the `store` ability for regulated coin types (a breaking change, but closes the wrapping vector entirely).

    DenyListResult {
