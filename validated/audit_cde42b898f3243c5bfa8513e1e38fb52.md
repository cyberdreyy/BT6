### Title
Cross-instance DKG result enumeration via VerifyDKGResult lacking instance/job ownership binding - ([File: core/web/vault_controller.go])

### Summary
`VaultController.VerifyDKGResult` looks up a DKG result solely by the caller-supplied `instanceId` with no check that the caller's authenticated session/token is associated with that specific DKG instance or job. Any caller holding a valid edit-role session token can submit arbitrary `instanceId` values and distinguish between "instance does not exist" (404) and "instance exists but verification failed" (400) responses, enabling enumeration of DKG instances present on the node.

### Finding Description
`VerifyDKGResult` decodes the request body into `VerifyDKGResultRequest{InstanceID, MasterPublicKey}` and, after validating the DKG recipient key exists, calls `orm.ReadResultPackage(ctx, dkgocrtypes.InstanceID(req.InstanceID))` [1](#0-0) . The ORM query is a flat, global lookup: `SELECT ... FROM dkg_results WHERE instance_id = $1` with no additional predicate tying the row to the requesting session, job, or tenant [2](#0-1) . There is no data model or code path here for associating a caller/session with a specific `instanceId`; the only inputs used for authorization are gin's route-level role middleware (edit-role required to reach the handler at all), not instance-level ownership.

Consequently, the handler's responses leak instance existence:
- If no row is found: `404 "DKG result not found"` [3](#0-2) 
- If a row is found but `vaultcap.VerifyDKGResult` fails (e.g., wrong `masterPublicKey`): `400 "DKG result verification failed: ..."` [4](#0-3) 

These two distinct status codes/messages let any edit-role-authenticated caller distinguish "instance exists" from "instance does not exist" for any `instanceId` string, regardless of whether that instance is related to a job/workflow the caller is authorized to operate on. The identical pattern also exists in `ExportDKGResult`, which similarly performs a global-keyed lookup with only a top-level not-found check [5](#0-4) .

### Impact Explanation
This is an information-disclosure / enumeration issue: it allows a caller with generic edit-role API access (not scoped to any particular DKG instance) to determine which DKG instance IDs are provisioned on the node, effectively probing for the existence of other tenants'/workflows' vault DKG ceremonies. This maps to Chainlink's "sensitive information disclosure" bounty class — it does not directly disclose the DKG shares or master key (verification failure does not leak secret material), but it discloses instance existence across job/tenant boundaries, which the endpoint's design does not intend to expose to anyone without a legitimate relationship to that instance.

### Likelihood Explanation
Preconditions: attacker must already hold a valid edit-role session/API token on the node (i.e., authenticated node operator UI/API access), but need not have any relationship to the specific DKG instance being probed. Given that precondition, the attack is trivial and fully repeatable: POST to `/v2/vault/dkg_results/verify` (or `/export`) with guessed/enumerated `instanceId` values and observe the 404 vs 400 status/message difference. No rate limiting or per-instance authorization exists in the handler itself to block this.

### Recommendation
Bind `instanceId` lookups to the authenticated caller's authorized job/workflow scope before querying the ORM (e.g., verify the session's associated job/feed owns the given `instanceId`, or require a capability-scoped token minted per DKG instance). Additionally, normalize the not-found and verification-failure responses to avoid leaking existence (e.g., return a uniform 404/403 for both "no such instance" and "not authorized for this instance"), and apply the same fix to `ExportDKGResult`.

### Proof of Concept
Go handler-level integration test plan:
1. Seed two rows in `dkg_results` for `instanceId = "tenant-A-instance"` and `instanceId = "tenant-B-instance"`, each with a valid `ReportWithResultPackage`, via `orm.WriteResultPackage`.
2. Construct a `gin.Context`/test HTTP server with `VaultController` wired to an edit-role authenticated session that has no association with either instance.
3. POST `/v2/vault/dkg_results/verify` with `{"instanceId":"tenant-A-instance","masterPublicKey":"<wrong-key>"}` — assert response is `400 DKG result verification failed`.
4. POST same endpoint with `{"instanceId":"nonexistent-instance","masterPublicKey":"<any-key>"}` — assert response is `404 DKG result not found`.
5. Assert that the differing status codes/messages allow the test to reliably distinguish "instance A exists" from "instance does not exist," without the caller possessing any authorization tied to instance A, confirming the enumeration oracle.

```go
func (o *orm) ReadResultPackage(ctx context.Context, iid dkgocrtypes.InstanceID) (*dkgocrtypes.ResultPackageDatabaseValue, error) {
	var configDigest []byte
	var seqNr uint64
	var reportWithResultPackage []byte
	var signatures pq.ByteaArray
	var signerOracleIDs []byte

	query := `SELECT config_digest, seq_nr, report_with_result_package, signatures, signer_oracle_ids FROM dkg_results WHERE instance_id = $1;`
	row := o.ds.QueryRowxContext(ctx, query, iid)
	err := row.Scan(&configDigest, &seqNr, &reportWithResultPackage, &signatures, &signerOracleIDs)
	if errors.Is(err, sql.ErrNoRows) {
		return nil, nil
	}
	if err != nil {
		return nil, errors.Wrap(err, "failed to read dkg result")
	}
```
