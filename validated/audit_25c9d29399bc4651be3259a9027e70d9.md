### No vulnerability found for this question.

**Analysis:** The reservation/release pair in `runtime/runtime/src/cache_warming.rs` is correctly balanced. `try_reserve_pending_slot` and `release_pending_slot` both operate on the same `parking_lot::Mutex<usize>` guarded counter [1](#0-0) , so concurrent calls from multiple chunks/threads are fully serialized by the mutex — there is no possible interleaving that double-counts a reservation.

Each call to `spawn_warming` reserves at most one slot and, only on success, spawns exactly one boxed closure whose first unconditional statement is `release_pending_slot()` [2](#0-1) . Since the release happens before any fallible work (`get_code()`, `try_precompile_contract`), a panic or early return inside the closure cannot skip the release. The 1:1 pairing (one reserve ⇒ one spawn ⇒ one release) is enforced entirely within `spawn_warming`'s own control flow, not across independent call sites, so there's no way for attacker-driven `DeployContract` volume to cause the increment and decrement to diverge.

The only way `release_pending_slot` could fail to run is if `background_runtime_tasks().spawn_boxed` never executes the enqueued job — which only happens on process shutdown (`ThreadPool::drop` sets `shutdown = true`) [3](#0-2) , not a state reachable via ordinary transaction submission. Absent that, `run_worker`'s loop dequeues and executes every job unconditionally [4](#0-3) .

Thus there is no reachable attacker-driven scenario (via `Action::DeployContract` volume or concurrent chunk application) that causes `WARMING_PENDING_SUBMISSIONS` to diverge from in-flight closures, and no underflow/panic path exists under normal transaction-driven load.

```rust
static WARMING_PENDING_SUBMISSIONS: Mutex<usize> = Mutex::new(0);

/// Try to claim a slot for a new warming submission. Returns `true` on
/// success; caller must invoke [`release_pending_slot`] once the worker has
/// dequeued the closure (so a freshly running worker frees the slot for the
/// next submission).
fn try_reserve_pending_slot() -> bool {
    let mut count = WARMING_PENDING_SUBMISSIONS.lock();
    if *count >= WARMING_PENDING_SUBMISSIONS_CAP {
        return false;
    }
    *count += 1;
    true
}

fn release_pending_slot() {
    *WARMING_PENDING_SUBMISSIONS.lock() -= 1;
}
```

```rust
fn spawn_warming(
    get_code: Box<dyn FnOnce() -> Option<Arc<ContractCode>> + Send>,
    config: Arc<Config>,
    cache_handle: Box<dyn ContractRuntimeCache>,
) {
    if !try_reserve_pending_slot() {
        COMPILATION_CACHE_WARMING_DROPPED_TOTAL.inc();
        return;
    }
    background_runtime_tasks().spawn_boxed(Box::new(move || {
        release_pending_slot();
        let Some(code) = get_code() else {
            return;
        };
        let result = try_precompile_contract(code.as_ref(), config, Some(&*cache_handle));
        update_compilation_cache_warming_metrics(result);
    }));
```

```rust
fn run_worker<Q: JobQueue>(state: Arc<ThreadPoolState<Q>>, idle_timeout: Duration) {
    // `_thread_count_guard` must be declared before `state_guard` so that
    // the mutex lock is dropped first during unwinding (reverse declaration
    // order), avoiding deadlock when the guard acquires the lock in its Drop.
    let _thread_count_guard = ThreadCountGuard(state.clone());
    let mut state_guard = state.inner.lock();
    loop {
        if state_guard.shutdown {
            tracing::trace!(
                target: "near_async::thread_pool",
                pool = state_guard.name,
                "terminate thread at shutdown"
            );
            break;
        }
        if let Some(job) = state_guard.dequeue() {
            drop(state_guard);
            job();
            state_guard = state.inner.lock();
        } else {
            state_guard.inc_idle_threads();
            let timeout_res = state.condvar.wait_for(&mut state_guard, idle_timeout);
            state_guard.dec_idle_threads();
            // Note on queue check on timeout:
            // If an idle thread's `wait_for` times out concurrently with `spawn_boxed` enqueueing a job and
            // calling `notify_one()` (which saw `idle_threads > 0` and thus didn't spawn a new thread), the job
            // can be orphaned in the queue. So we need to make sure the queue is empty before exiting the thread.
            if timeout_res.timed_out() && state_guard.queue.is_empty() {
                tracing::trace!(
                    target: "near_async::thread_pool",
                    pool = state_guard.name,
                    "terminate idle thread"
                );
                break;
            }
        }
    }
}
```
