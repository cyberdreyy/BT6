### Title
Tenure-change duplicate-block guard in the legacy `SortitionsView` (v1) checks only globally-accepted blocks, unlike `GlobalStateView` (v2), letting a v1 signer sign two tenure-start blocks for the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`GlobalStateView::validate_tenure_change_payload` (v2 chainstate) and `SortitionsView::validate_tenure_change_payload` (v1 chainstate) both exist to stop a signer from approving a second, competing tenure-start block for a tenure it has already committed to. The two implementations use different SignerDb lookups for this guard, and the v1 lookup is strictly weaker than the v2 lookup, mirroring the filebrowser bug class where a security restriction added on one code path (signup) was never propagated to the sibling path (proxy auth).

### Finding Description
In `stacks-signer/src/chainstate/v2.rs`, `validate_tenure_change_payload` explicitly documents and implements the intended invariant: [1](#0-0) 

It calls `signer_db.get_last_signed_block(&block.header.consensus_hash)`, which per its own doc comment returns a block in `GloballyAccepted` **or** `LocallyAccepted` state: [2](#0-1) 

By contrast, the older `SortitionsView::validate_tenure_change_payload` in `v1.rs` performs the equivalent check with `signer_db.get_last_globally_accepted_block(...)`, which only matches blocks in the `GloballyAccepted` state: [3](#0-2) 

This is exactly the "fix applied on one path, not the sibling path" pattern from the report: v2's comment ("Only blocks we have signed (locally or globally accepted) count here…") shows the invariant was deliberately widened to include `LocallyAccepted` (i.e., blocks the signer has already put its own signature `signed_self` on, even if global 70% consensus/`NewBlock` broadcast hasn't happened yet). v1 never received the same widening — it still only looks at `GloballyAccepted`.

Concretely: if a signer running the v1 (`SortitionsView`) code path has already locally signed (`signed_self` set, state `LocallyAccepted`) a block in a given tenure, but that block has not yet reached global acceptance (e.g., its own vote didn't cross 70%, or the node hasn't relayed `NewBlock` yet), `validate_tenure_change_payload`'s `DuplicateBlockFound` guard in v1 will not trigger for a second, competing tenure-change block proposed for the *same* tenure by a one-slot-controlling miner. The check-proposal phase (`CHECK` step in the flow, `check_block_against_state`) therefore does not reject the conflicting proposal outright, and it proceeds to validation/pre-commit.

### Impact Explanation
This breaks the "no double sign within a tenure" equality directly at the `check_proposal` layer for v1 signers. Whether it results in an actual second signature depends on whether the later pre-commit-stage backstop (`check_block_against_signer_db_state` / `get_signed_conflicts`, described in `docs/signer-flows.md` section 5) independently catches the conflict. That backstop is scoped by Stacks height across tenures, and I was not able to fully confirm within the remaining budget whether it always covers the specific "second tenure-start block in the *same* tenure, both at the tenure's first height" case that `validate_tenure_change_payload`'s `DuplicateBlockFound` is specifically designed to catch at proposal time — the documentation explicitly calls out that this proposal-time check is one of only two places this particular duplicate-tenure-start scenario is guarded (`docs/signer-flows.md` lines 280–286), stating the pre-commit backstop only ever looks at *one* tenure per evaluation and has "blind spots." This raises the possibility that, for v1 signers, a same-tenure duplicate tenure-start block that slips past `check_proposal` might also slip past the pre-commit backstop, leading the signer to sign two conflicting tenure-start blocks (an equivocation / conflicting-block signature) — a Critical-class outcome per the rules. However, I could not fully verify this end-to-end without reading `get_signed_conflicts` and `check_block_against_signer_db_state` in full, since tool budget ran out before completing that read.

### Likelihood Explanation
Reachable by a single miner/tenure operator who can create two competing tenure-change proposals for the same tenure (e.g., after a brief fork/reorg-recovery window) while a v1 signer has locally-but-not-globally accepted the first one — no cooperation from other signers or a majority is required, matching the "one-slot miner plus gossip" threat model in scope.

### Recommendation
Align `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` with `v2.rs`: replace the `get_last_globally_accepted_block` lookup with `get_last_signed_block` (or equivalent) so that a locally-accepted-but-not-yet-globally-accepted block in the current tenure also blocks a competing tenure-change proposal, consistent with the documented invariant in v2.

### Proof of Concept
Not independently reproduced against a running signer/network in this pass; the finding is based on direct code comparison of the two `validate_tenure_change_payload` implementations and the differing semantics of `get_last_signed_block` vs `get_last_globally_accepted_block` in `stacks-signer/src/signerdb.rs`. Full confirmation of end-to-end signability (i.e., that the pre-commit backstop doesn't independently prevent the second signature) would require tracing `check_block_against_signer_db_state` and `get_signed_conflicts` in `stacks-signer/src/v0/signer.rs` and `signerdb.rs`, which was not completed before the tool budget was exhausted.
