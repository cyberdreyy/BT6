### Title
Signer vote-switch (accept↔reject) is double-counted by the miner's weight aggregator, letting a stale/retracted acceptance keep counting toward the signing threshold - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block using two different idempotency keys (`gathered_signatures` for accepts, `responded_signers` for rejects), but never reconciles the two when a single signer legitimately switches its vote (a transition the signer's own state machine explicitly supports: `LocallyAccepted --> LocallyRejected : re-evaluated`, per `docs/signer-flows.md:145`). This lets a signer's rescinded acceptance keep counting toward the 70% approval threshold while their newer rejection is silently dropped.

### Finding Description
Each signer's `BlockResponse` is handled in `stackerdb_listener.rs`. On `Accepted`, weight is added to `total_weight_approved` gated only by `!block.gathered_signatures.contains_key(&slot_id)`, and `slot_id` is unconditionally inserted into both `gathered_signatures` and `responded_signers`: [1](#0-0) 

On `Rejected`, weight is added to `total_weight_rejected` gated by `block.responded_signers.insert(slot_id)` (i.e., "have we ever heard from this signer before, for either accept or reject?"): [2](#0-1) 

Because both branches share the single `responded_signers` set, and only the accept branch also populates `gathered_signatures`, the two vote types are not symmetric:
- Accept → later Reject: `responded_signers.insert(slot_id)` was already `true` from the earlier Accept, so the new rejection's weight is **never added** to `total_weight_rejected`. The stale acceptance weight, however, remains in `total_weight_approved` forever — there is no removal/decrement path anywhere in this file.
- The signer's own local `signerdb.rs` state machine documents this exact scenario as expected, valid behavior (`BlockInfo::move_to`/`check_state` permits `LocallyAccepted -> LocallyRejected`, `docs/signer-flows.md:144-145`), so a single, honest signer re-evaluating a proposal (e.g. after a conflicting block becomes canonical) can trigger this without any malicious majority.

This breaks the "aggregated-weight vs. verified-accepts" equality that `SignerCoordinator::wait_for_signatures` in `signer_coordinator.rs` relies on: `block_status.total_weight_approved >= self.weight_threshold` is treated as ground truth for "block accepted," but the weight backing that number can include a signer who currently rejects the block, i.e., a rejection is left counted as an acceptance. [3](#0-2) 

### Impact Explanation
This matches the Critical category "a rejection recounted as acceptance": the coordinator can broadcast a block as validly signed using an aggregate weight that includes a signer whose current, more recent decision is a rejection. In borderline-threshold scenarios (weight near 70%), this stale weight can be the deciding factor that pushes the tally over the threshold when the currently-live set of accepting signers does not actually meet it. It requires only a single signer changing its mind — not a majority — to corrupt the count.

### Likelihood Explanation
Vote reconsideration (`LocallyAccepted -> LocallyRejected`) is a normal, documented code path in the signer's own state machine (re-evaluation on reproposal or on a conflicting sibling/reorg), not an exotic edge case, so the underlying trigger condition is expected to occur in practice, particularly in fork/tie-break windows highlighted in `docs/signer-flows.md` section 5 (pre-commit conflict resolution).

### Recommendation
Track approve/reject membership with a single, unified per-signer vote state (e.g., an enum keyed by `slot_id`) instead of two independently-gated maps/sets. When a signer's vote flips from Accepted to Rejected (or vice versa), atomically move their weight from one total to the other rather than only gating on "first time seen."

### Proof of Concept
1. Two signers, weights 40 and 60 (`total_weight` = 100), `weight_threshold` = 70.
2. Signer A (weight 40) sends `BlockResponse::Accepted` for block `H`. `total_weight_approved` = 40, `responded_signers` = {A}, `gathered_signatures` = {A}.
3. Signer A legitimately re-evaluates (e.g. observes a conflicting canonical block) and sends `BlockResponse::Rejected` for `H`. In the reject handler, `responded_signers.insert(A)` returns `false` (already present) → `total_weight_rejected` stays at 0; A's rejection is silently dropped.
4. Signer B (weight 60) sends `Accepted` for `H`: `gathered_signatures.contains_key(B)` is false → `total_weight_approved` = 40 + 60 = 100.
5. `SignerCoordinator::wait_for_signatures` sees `total_weight_approved (100) >= weight_threshold (70)` and returns the block as accepted, even though Signer A currently rejects it — A's weight (40) is stuck counted as an accept that can never be un-counted.
