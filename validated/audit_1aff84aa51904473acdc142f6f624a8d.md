### Title

Unprotected ERC4626 deposit lets an attacker steal the programmable borrower’s idle liquidity - ([File: `contracts/strategies/idle/ProgrammableBorrower.sol`])

### Summary

`ProgrammableBorrower` deposits the entire idle balance into an arbitrary ERC4626 vault without enforcing a minimum amount of shares or comparing the returned shares with the deposited assets. An unprivileged user of that vault can inflate its share price before `onStartEpoch`, causing the borrower contract to receive zero or economically worthless shares for its deposit. The attacker then redeems their preexisting shares and extracts the newly deposited pool assets.

### Finding Description

The programmable borrower architecture parks undrawn credit in an external ERC4626 vault. During `onStartEpoch`, the contract measures its idle balance and calls `_depositToVault` with the full balance. `_depositToVault` executes `vault.deposit(_assetAmount, address(this))` but accepts any returned `shares` value, including zero.

The vulnerable flow is:

1. The configured ERC4626 vault is empty or has negligible share supply.
2. An attacker deposits `1 wei`, receiving one initial share.
3. The attacker directly transfers `X` underlying tokens to the vault. For a balance-accounted ERC4626 vault, the sole share is now backed by approximately `X + 1` assets.
4. During epoch start, `ProgrammableBorrower` deposits `D` pool assets. A conventional floor-based conversion returns `D / (X + 1)` shares.
5. If `X + 1 > D`, the borrower receives zero shares while the vault keeps its deposit.
6. The attacker redeems the only outstanding share for approximately `X + 1 + D` assets.

`ProgrammableBorrower.initialize` validates only that the vault asset matches the CDO underlying and grants unlimited allowance to the vault. `setVault` only requires an inactive epoch and a zero current vault share balance. Neither check protects the next deposit from an inflated exchange rate.

Relevant code:

- `onStartEpoch` snapshots the on-hand balance and immediately deposits all of it into the ERC4626 vault. [1](#0-0) 
- `_depositToVault` records the returned shares only in an event and applies no lower bound. [2](#0-1) 
- `initialize` checks only asset compatibility before approving the vault. [3](#0-2) 
- `setVault` permits a replacement vault when epoch accounting is inactive and the current share balance is zero. [4](#0-3) 

### Impact Explanation

The attacker directly steals the idle assets deposited into the external vault. For a programmable epoch deposit of `D`, a donation of at least `D` underlying units can cause the borrower to receive zero shares under floor-based share conversion. The attacker’s sole share can then be redeemed for the attacker’s deposit, donation, and the borrower’s `D` assets.

If the borrower receives nonzero but severely understated shares, the same attack extracts a proportional fraction of the deposit. The affected assets are LP funds previously transferred from `IdleCDOEpochVariant` to the programmable borrower, so the resulting shortfall reduces the assets available for pending withdrawals and epoch settlement. The deficiency is subsequently handled as vault loss or borrower default rather than being recovered from the attacker. [5](#0-4) 

### Likelihood Explanation

Likelihood depends on deploying the programmable borrower against an ERC4626 whose share price can be inflated through direct asset transfers and whose deposits can round down to zero or near-zero shares. The integration interface permits any ERC4626 vault and does not require the vault to implement inflation-resistant virtual shares, minimum initial liquidity, or deposit slippage controls. [6](#0-5) 

The attack does not require control of `IdleCDO`, the strategy, the borrower, the owner, or the manager. The attacker only needs to transact with the configured public ERC4626 before an epoch-start deposit. Existing donation-skimming logic in `IdleCDOEpochVariant` does not help because the donation is sent to the external vault, not to the CDO contract. [7](#0-6) 

### Recommendation

Require every vault deposit to return an economically acceptable amount of shares. In particular:

- Query `vault.previewDeposit(_assetAmount)` immediately before depositing and require the actual returned shares to meet a configured minimum or to equal the preview within bounded slippage.
- Revert if `shares == 0` for a nonzero deposit.
- Prefer deploying an inflation-resistant ERC4626 with virtual assets/shares or a nonzero dead-share seed.
- Before first use, seed the vault with protocol-owned minimum liquidity and prevent switching to an unseeded vault.
- Reconcile `vault.convertToAssets(vault.balanceOf(address(this)))` after depositing with the deposited principal and revert or enter a controlled recovery path if the discrepancy exceeds a bounded rounding amount.

### Proof of Concept

A Foundry PoC can reproduce the issue with an ERC4626 whose `convertToShares` uses `assets * totalSupply / totalAssets`:

```solidity
function testFirstEpochDepositShareInflation() public {
    uint256 idleDeposit = 1_000_000e18;
    uint256 donation = idleDeposit + 1;

    // The configured ERC4626 starts empty.
    assertEq(vault.totalSupply(), 0);

    // Unprivileged vault user creates one share and inflates its price.
    asset.mint(attacker, donation + 1);
    vm.startPrank(attacker);
    asset.approve(address(vault), type(uint256).max);
    vault.deposit(1, attacker);
    asset.transfer(address(vault), donation);
    vm.stopPrank();

    // LPs fund the IdleCDO, then the honest manager starts the epoch.
    // startEpoch transfers `idleDeposit` to ProgrammableBorrower and calls onStartEpoch().
    uint256 sharesBefore = vault.balanceOf(address(programmableBorrower));
    vm.prank(manager);
    cdo.startEpoch(epochDuration);

    // The borrower's assets were accepted but converted to zero shares.
    assertEq(sharesBefore, 0);
    assertEq(vault.balanceOf(address(programmableBorrower)), 0);
    assertEq(asset.balanceOf(address(vault)), donation + 1 + idleDeposit);

    // The attacker owns all shares and redeems the borrower-funded vault balance.
    vm.prank(attacker);
    uint256 stolen = vault.redeem(
        vault.balanceOf(attacker),
        attacker,
        attacker
    );

    assertEq(stolen, donation + 1 + idleDeposit);
    assertEq(programmableBorrower.vaultSharesBalance(), 0);
}
```

The relevant transaction sequence is `vault.deposit(1)`, direct asset transfer to the vault, honest `cdo.startEpoch`, and attacker `vault.redeem`. The invariant violated is fair asset-to-share conversion: `ProgrammableBorrower` deposits `D` assets but receives shares backed by zero assets, transferring custody of the LP deposit to the attacker’s preexisting share position. [8](#0-7)

  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
    emit EpochAccountingStarted(startAssets);

  /// @notice Move a specific amount of idle underlying into the vault.
  /// @param _assetAmount Amount of underlying to deposit
  /// @param _principalAssets Portion of the deposited assets that should extend the epoch principal
  /// baseline instead of being recognized as current-epoch profit.
  function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
    if (_assetAmount == 0) return;
    uint256 shares = vault.deposit(_assetAmount, address(this));
    if (epochAccountingActive && _principalAssets != 0) {
      epochDepositedToVault += _principalAssets;
    }
    emit DepositedIntoVault(_assetAmount, shares);
