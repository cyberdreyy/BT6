Signer weight double-counted into both `total_weight_approved` and `total_weight_rejected` on Reject→Accept flip - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The mining coordinator's per-block vote tally (`BlockStatus`) tracks acceptance and rejection weight using two independently-maintained structures — a `gathered_signatures: BTreeMap<slot_id, signature>` gating the approve-weight add, and a `responded_signers: HashSet<slot_id>` gating the reject-weight add — that are not kept in sync, exactly mirroring the reported bug class (two parallel bookkeeping structures for the same logical state, updated inconsistently).

### Finding Description
In `stackerdb_listener.rs`, `BlockAccepted` handling only checks/updates `gathered_signatures` before adding to `total_weight_approved`, but *also* inserts the slot into the shared `responded_signers` set: [1](#0-0) 

`BlockResponse::Rejected` handling only checks/updates `responded_signers` before adding to `total_weight_rejected`: [2](#0-1) 

Because these are two different structures, the two directions of a vote flip are handled asymmetrically:
- Accept → Reject (same signer, same block): `responded_signers` already contains the slot from the earlier Accept, so `responded_signers.insert(slot_id)` returns `false` and `total_weight_rejected` is correctly *not* incremented.
- Reject → Accept (same signer, same block): `gathered_signatures` was never touched by the reject path, so `gathered_signatures.contains_key(&slot_id)` is `false`, and `total_weight_approved` **is** incremented — while `total_weight_rejected` is never decremented or cleared. The signer's weight now sits permanently in *both* totals.

This is not a hypothetical scenario: the signer protocol explicitly supports a signer reversing an earlier rejection to a later acceptance for the *same block* once it is re-evaluated as legitimate (re-proposal, chain catch-up, etc.), and this is a tested code path: [3](#0-2) 
The signer-side `SignerDb` even enforces the correct mutually-exclusive bookkeeping for this exact case (a signature clears a stored rejection), showing the intended invariant that a signer should count toward at most one side: [4](#0-3) 
The node-side coordinator's `stackerdb_listener.rs` bookkeeping does not implement the same invariant.

### Impact Explanation
`signer_coordinator.rs`'s polling loop checks `total_weight_rejected` against the blocking-minority threshold on every message and aborts the mining attempt as soon as it is crossed: [5](#0-4) 
Because `total_weight_rejected` is never reduced when a signer legitimately reverses their rejection to an acceptance, a stale/retracted rejection weight can combine with other genuinely rejecting signers' weight to spuriously cross the >30% blocking-minority threshold, or to keep it crossed even after the signer's flip should have relieved it. This causes the coordinator to treat the block as dead (`NakamotoNodeError::SignersRejected`) and abandon it, based on weight that no longer reflects the signer's current, legitimate vote — an aggregated-weight-vs-verified-accepts mismatch that wedges the miner into needlessly discarding legitimate blocks/tenures (liveness degradation), reachable without requiring a majority of colluding signers — only one signer naturally reconsidering, combined with an independent minority of genuine rejecters, is needed.

### Likelihood Explanation
This requires no signer collusion, no stolen keys, and no majority: it only needs one signer to send a `Rejected` response followed later by an `Accepted` response for the same block hash — a flow the codebase explicitly supports and tests (`signer_can_accept_rejected_block`). Any block that is briefly rejected (e.g., due to node lag on the parent block, or a stale check) and later re-validated will trigger this code path on the node/coordinator side.

### Recommendation
Track approval/rejection membership with a single per-slot state (e.g., an enum `Accepted`/`Rejected` keyed by `slot_id`) rather than two independently-gated collections (`gathered_signatures` vs `responded_signers`). When a slot's vote flips, subtract the previously counted weight from the old total before adding it to the new total, so `total_weight_approved` and `total_weight_rejected` always reflect only the signer's current, latest vote.

### Proof of Concept
1. Configure a reward set with signer weights, e.g. A=15%, B=15%, C=40%, D=30% (`weight_threshold` = 70%, blocking minority = 30%).
2. Miner proposes block X. A and B reject (25% total rejected, below 30% blocking minority — no abort yet).
3. C initially also rejects (due to stale parent info) — now 65% total_weight_rejected, which is `>` blocking minority (30%), triggering the coordinator to already treat the block dead via the check in `signer_coordinator.rs` lines 509-540. To isolate the double-count bug specifically (rather than a legitimate independent rejection majority), use weights where C's initial reject alone does *not* cross blocking minority, e.g. A=10%, B=10%, C=15%, D=65%; A+B=20% reject (below 30%).
4. C then rejects too: 35% total rejected — crosses 30% blocking minority: coordinator aborts (`SignersRejected`) using C's weight.
5. C subsequently re-evaluates and sends `Accepted` for block X. Per `stackerdb_listener.rs` line 443, `gathered_signatures` doesn't contain C's slot yet, so `total_weight_approved` is incremented by C's weight (15%) — but `total_weight_rejected` still contains C's weight (still 35%, never cleared).
6. Even if the coordinator loop is re-entered for a new attempt reusing the same `BlockStatus` (or in any flow where the reject check is evaluated after the flip), `total_weight_rejected` remains inflated by C's stale vote, permanently contributing to a rejection tally that no longer reflects C's actual (accepting) vote — demonstrating the loss of the approve/reject mutual-exclusivity invariant at the coordinator layer.
