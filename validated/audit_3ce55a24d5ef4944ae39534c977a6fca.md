### Title
Withdrawal claims bypass Keyring/KYC authorization — permission checked on the request, not on the transformed receipt holder - (contracts/IdleCDOEpochVariant.sol)

### Summary
The SurrealDB advisory is about authorization being enforced against the wrong stage of a value's lifecycle: permissions are checked on the original document, but transformed/derived outputs (aliased fields, `SELECT VALUE`, `RETURN BEFORE`) escape the check. The direct analog in this codebase is the withdraw-request lifecycle: `requestWithdraw` enforces `isWalletAllowed(msg.sender)` (Keyring KYC), but both claim paths — `claimWithdrawRequest` and `claimInstantWithdrawRequest` — perform no wallet-allowance check at all. The strategy mints a plain transferable ERC20 receipt (`_mint(_user, _amount)`) to the requester, so the KYC-gated position is transformed into a bearer instrument that any non-KYC address can redeem for underlying.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw`, the caller is gated by `isWalletAllowed` plus the per-tranche allow flags before the receipt is created [1](#0-0) . The vault then mints strategy tokens 1:1 to the user as a withdrawal receipt [2](#0-1) .

However, the claim functions that turn those receipts into underlying are permissionless — `claimWithdrawRequest` just forwards `msg.sender` to the vault with no `isWalletAllowed` check, and `claimInstantWithdrawRequest` only checks the global `allowInstantWithdraw` flag [3](#0-2) . The vault's `claimWithdrawRequest(_user)` only gates on `_onlyIdleCDO`, burns the caller-held receipt and pays `_user` (which is the CDO's `msg.sender`, i.e., whoever redeems the receipt) [4](#0-3) . Nothing in the epoch-gating logic (`epochNumber <= lastWithdrawRequest[_user]`) ties the claim to the originally authorized wallet [5](#0-4) .

The same split exists in `IdleCDOEpochQueue`: `requestDeposit`/`requestWithdraw` call `_checkAllowed` (epoch running + `isWalletAllowed`), while `claimDepositRequest`/`claimWithdrawRequest` have no KYC check [6](#0-5) .

Non-KYC wallets can already hold tranche tokens: `WriteOffEscrow.fullfillWriteOffRequest` is explicitly designed to let a non-credentialed buyer acquire an LP's tranches (the suite's own test confirms a non-Keyring buyer can fulfill, and only `requestWithdraw` reverts for them — claims are never exercised) [7](#0-6) .

### Impact Explanation
The Keyring credential check is the vault's only access control for redeeming underlying. Because it is applied to the request transaction but not to the transformed receipt (strategy tokens / epoch queue balances), the permission is evaluated against the "original document" while the payout is delivered to the "aliased document" holder — the exact ordering flaw in the advisory. Concretely:

- A KYC'd lender opens a withdraw request, then transfers the minted strategy-token receipt to a sanctioned/non-KYC address, which calls `claimWithdrawRequest` and receives underlying directly.
- A non-KYC buyer acquires tranches via `WriteOffEscrow` or secondary transfer, has a KYC'd intermediary request the withdrawal for them (receipt is minted to the requester, then transferred), and redeems.
- Any wallet that loses or has revoked KYC credentials mid-cycle still claims freely, but the reverse — an unauthorized party extracting funds — is the security-relevant direction.

The broken invariant is access control: underlying leaves the system to an address that the configured Keyring policy explicitly forbids from interacting with the vault. The loss is the full withdrawal amount plus accrued interest for whatever volume flows through this path, and it is a compliance/licensing violation even when economically the redeemer "paid" for the position.

### Likelihood Explanation
High. It requires no privileged role, no timing manipulation, and no price condition — only that the withdraw receipt be transferable (it is a normal ERC20 `_mint`) and that `claim*` functions lack the check the request function has. The codebase itself demonstrates the attacker profile in tests (`testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw`), and the gap persists in every mode (fixed-APR, APR0, instant, post-default via `_claimPostDefaultWithdrawRequest`/`_claimDefaultedWithdrawRequest`, none of which check the claimant).

### Recommendation
Mirror the request-time gate on the claim side: add `isWalletAllowed(msg.sender)` (or reuse `_checkAllowed` semantics minus the epoch-running requirement) in `IdleCDOEpochVariant.claimWithdrawRequest` and `claimInstantWithdrawRequest`, and in `IdleCDOEpochQueue.claimDepositRequest`/`claimWithdrawRequest`. Alternatively — stronger and consistent with the advisory's fix of checking permissions "after changes to the document" — make the strategy-token receipt non-transferable or enforce the credential check inside `IdleCreditVault.claimWithdrawRequest`/`claimInstantWithdrawRequest` against the final recipient.

### Proof of Concept
Foundry fork sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testNonKycClaimBypass() external {
    // LP is KYC'd; buyer is not (Keyring mock returns false for buyer)
    vm.prank(LP);
    cdoEpoch.requestWithdraw(amountTranche, address(tranche)); // passes isWalletAllowed

    // receipt: strategy tokens minted to LP
    uint256 receipt = strategy.balanceOf(LP);
    vm.prank(LP);
    strategy.transfer(buyer, receipt); // plain ERC20 receipt is transferable

    _stopCurrentEpoch(); // manager/borrower fund the withdrawal honestly

    vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector), abi.encode(false));
    assertFalse(cdoEpoch.isWalletAllowed(buyer));

    // non-KYC buyer redeems underlying anyway — no isWalletAllowed check on the claim path
    uint256 balPre = underlying.balanceOf(buyer);
    vm.prank(buyer);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(buyer), balPre); // KYC policy bypassed, funds paid out
}
```

A variant exercises `claimInstantWithdrawRequest` under an APR-drop instant-withdraw epoch, and a third uses `WriteOffEscrow.fullfillWriteOffRequest` as the acquisition vector for a non-KYC holder.
