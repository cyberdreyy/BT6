### Title
Loss haircut is keyed to the last request epoch only: receipts requested in an earlier epoch escape `lossRecoveryPriceByEpoch` and are paid at par, overpaying the claimant against the underfunded pending pool - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is an unchecked queue size/index: the driver trusts `qsize`/`new_wr_idx` and writes past the real buffer. The analog in this codebase is a missing bounds check between a per-epoch receipt index and the aggregate it was funded against. `collectWithdrawFunds` applies a pro-rata haircut (`lossRecoveryPrice`) to the *entire* `pendingWithdraws` aggregate, but stores the recovery price only under the single key `lossRecoveryPriceByEpoch[epochNumber]`. `_claimLossAdjustedWithdrawRequest` then looks up the haircut only via `lastWithdrawRequest[_user]`, so only receipts recorded under that one epoch are haircutted. An attacker who deliberately holds withdraw receipts from two different request epochs gets the older receipt paid at par through `_claimFundedWithdrawRequest` even though the shared funded pool was sized for a haircut on all of them.

### Finding Description
- `requestWithdraw` records receipts per epoch: `withdrawsRequests[_user] += _amount; withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;` and sets `lastWithdrawRequest[_user] = currentEpoch`. Multiple pending receipts across different epochs are explicitly supported (comment at `IdleCreditVault.sol:323`: "if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests"). [1](#0-0) 
- On a lossy `stopEpochWithDuration`, `previewLossAdjustedWithdrawFunds` computes `pendingToFund = pendingBasis - pendingLoss` against the *whole* `pendingWithdraws` aggregate — i.e., the borrower funds every pending receipt at the same haircut ratio. [2](#0-1) 
- `collectWithdrawFunds` stores that single ratio under only one index: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`, then zeroes `pendingWithdraws`. [3](#0-2) 
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]`; `_clearWithdrawClaimForEpoch` then resets `lastWithdrawRequest[_user] = 0` so the remainder of `withdrawsRequests[_user]` — the older-epoch receipt — falls through to `_claimFundedWithdrawRequest`, which pays it at par (`amount = normalAmount + ...`). [4](#0-3) [5](#0-4) 

The broken invariant is "one receipt one payout sized by the funded amount": the funding transaction haircut `pendingBasis` assuming *all* pending receipts share the loss, but the per-epoch index used at claim time only covers receipts whose request epoch equals `lastWithdrawRequest`. Receipts indexed to earlier epochs "write" a claim outside the funded size — the direct analog of `new_wr_idx < qsize` not being enforced against the real buffer.

### Impact Explanation
Direct theft / insolvency. With a haircut of e.g. 50% on `pendingBasis`, an attacker holding an old-epoch receipt of size X plus a current-epoch receipt of size Y receives `X + Y*0.5` while the strategy only received `0.5*(X+Y)` from the borrower for the pending bucket. The excess `X*0.5` is paid out of underlying that is meant to back other users' haircutted claims (or reserve), so subsequent claimants' `_transferFundedClaim`/payouts are drained or revert — permanent loss for other withdrawers equal to the par-paid delta on stale receipts.

### Likelihood Explanation
Exploitable by any KYC-passing lender / tranche holder with no privileged role: (1) request a normal withdraw in epoch N buffer and do not claim; (2) request again in epoch N+1 buffer so `lastWithdrawRequest = N+1` while the epoch-N basis stays in `withdrawsRequests`; (3) wait for a `stopEpochWithDuration` loss (borrower underfunds — a normal, honest-manager path). The sequence uses only honest privileged calls (manager `stopEpochWithDuration`, borrower partial funding). It requires a loss event to occur while the attacker holds receipts from ≥2 epochs, which is a realistic state and is even a documented supported flow in the code comments.

### Recommendation
Apply the haircut by claim, not by epoch index: either store `lossRecoveryPriceByEpoch` for every epoch that has a non-zero pending receipt, or carry a global `fundedBasis`/`paidBasis` so that `_claimFundedWithdrawRequest` pays `min(claimBasis, shareOfFundedAmount)`. Simplest fix: when computing the claim in `_claimLossAdjustedWithdrawRequest`, clear `withdrawsRequests[_user]` proportionally — i.e., haircut the user's *entire* pending basis (`withdrawsRequests[_user]` + apr0 principal), not just the slice keyed by `lastWithdrawRequest`, matching exactly what `previewLossAdjustedWithdrawFunds` haircutted at funding time.

### Proof of Concept
Foundry scenario (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleEpochReceiptEscapesLossHaircut() external {
    // deposit as attacker
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // epoch N request, never claimed
    uint256 req1 = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // epoch N+1 request -> lastWithdrawRequest = N+1
    uint256 req2 = cdoEpoch.requestWithdraw(remainingTranches, address(AAtranche));

    // epoch N+1 ends with a loss: borrower funds only part of pendingWithdraws
    // via stopEpochWithDuration(_lossAmount) -> collectWithdrawFunds(pendingToFund)
    _toggleEpochWithLoss(...); // lossRecoveryPriceByEpoch[epochNumber] = r < 1e18

    // attacker claims: req2 * r (haircut) + req1 * 1.0 (par, via _claimFundedWithdrawRequest)
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balPre;

    uint256 funded = (req1 + req2) * r / 1e18; // what the borrower actually paid in
    assertGt(got, funded, "attacker paid at par on stale receipt, exceeding funded pool");
}
```

The assertion shows total payout to this user alone exceeds the aggregate funded amount, proving the older-epoch receipt bypassed the loss haircut applied to the shared `pendingWithdraws` pool.

      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
