### Title
Broken `max_timestamp` Tracking in `MetaOracle::add_simple_oracle` Allows Stale Price Data to Bypass Freshness Filter — (`File: crates/sui-oracle/move/oracle/sources/meta_oracle.move`)

---

### Summary

`MetaOracle::add_simple_oracle` unconditionally overwrites `max_timestamp` with each successive oracle's timestamp instead of keeping the running maximum. Because `combine` derives its staleness cut-off as `max_timestamp - time_window_ms`, the cut-off is anchored to the **last** oracle added rather than the **freshest** one. Any caller who adds oracles in an order where the last oracle carries a stale timestamp causes the freshness filter to collapse, allowing arbitrarily old price data from every oracle to pass as "fresh."

---

### Finding Description

`MetaOracle` is the Sui oracle framework's multi-source aggregator. Its staleness logic works as follows:

1. `add_simple_oracle` is called once per source oracle. It reads the latest stored price and is supposed to track the highest (most recent) timestamp seen so far in `max_timestamp`.
2. `combine` computes `min_timestamp = max_timestamp - time_window_ms` and discards any data point whose timestamp is ≤ `min_timestamp`.
3. `median` calls `combine` and returns the median of the surviving values.

The defect is in step 1:

```move
// crates/sui-oracle/move/oracle/sources/meta_oracle.move  lines 38-44
public fun add_simple_oracle<T: copy + drop + store>(
    meta_oracle: &mut MetaOracle<T>,
    oracle: &SimpleOracle
) {
    let oracle_data = oracle::simple_oracle::get_latest_data(oracle, meta_oracle.ticker);
    if (option::is_some(&oracle_data)) {
        // BUG: unconditional assignment, not a max() operation
        meta_oracle.max_timestamp = data::timestamp(option::borrow(&oracle_data));
    };
    vector::push_back(&mut meta_oracle.oracle_data, oracle_data);
}
``` [1](#0-0) 

Every call overwrites `max_timestamp` with the current oracle's timestamp. After N calls, `max_timestamp` equals the timestamp of the **Nth** oracle, not the maximum across all N oracles.

`combine` then uses this corrupted value:

```move
// lines 51-66
fun combine<T: copy + drop>(meta_oracle: MetaOracle<T>): (vector<T>, vector<address>) {
    let MetaOracle { mut oracle_data, threshold, time_window_ms, ticker: _, max_timestamp } = meta_oracle;
    let min_timestamp = max_timestamp - time_window_ms;   // anchored to last oracle, not freshest
    ...
    if (data::timestamp(&oracle_data) > min_timestamp) {  // filter is wrong
        vector::push_back(&mut values, *data::value(&oracle_data));
    };
``` [2](#0-1) 

**Scenario A – stale last oracle:** If oracle1 (fresh, T=1000) is added before oracle2 (stale, T=10), `max_timestamp` becomes 10. `min_timestamp = 10 - time_window_ms`. If `time_window_ms = 60000` (60 s), Move's unsigned subtraction underflows and the transaction aborts — a public-input DoS.

**Scenario B – stale first oracle, fresh last oracle:** If oracle1 (stale, T=10) is added before oracle2 (fresh, T=1000), `max_timestamp` becomes 1000 and `min_timestamp = 940`. Oracle1's stale value (T=10) is correctly filtered. This is the only ordering that works correctly — but it is not enforced anywhere.

**Scenario C – all oracles stale, last oracle least stale:** `max_timestamp` is the least-stale value; `min_timestamp` is computed relative to it. All other oracles, which may be far older, pass the filter because their timestamps are still above `min_timestamp`. The median is computed over stale data.

The `simple_oracle::get_latest_data` function itself performs no staleness check — it returns whatever was last written:

```move
// crates/sui-oracle/move/oracle/sources/simple_oracle.move  lines 51-58
public fun get_latest_data<T: store + copy>(oracle: &SimpleOracle, ticker: String): Option<Data<T>> {
    if (!df::exists_(&oracle.id, ticker)) { return option::none() };
    let data: &StoredData<T> = df::borrow(&oracle.id, ticker);
    let StoredData { value, sequence_number, timestamp, identifier } = *data;
    option::some(data::new(value, ticker, sequence_number, timestamp, oracle.address, identifier))
}
``` [3](#0-2) 

No wall-clock comparison against `sui::clock::Clock` is performed at read time. The entire freshness guarantee is delegated to `MetaOracle::combine`, which is broken.

The reference test module shows that callers pass oracle objects as PTB arguments, meaning the ordering is caller-controlled:

```move
// crates/sui-oracle/tests/data/Test/sources/test_module.move  lines 67-72
let mut meta_oracle = meta_oracle::new<DecimalValue>(3, 60000, string::utf8(b"SUIUSD"));
meta_oracle::add_simple_oracle(&mut meta_oracle, oracle1);
meta_oracle::add_simple_oracle(&mut meta_oracle, oracle2);
meta_oracle::add_simple_oracle(&mut meta_oracle, oracle3);
let trusted_data = meta_oracle::median(meta_oracle);
``` [4](#0-3) 

---

### Impact Explanation

Any on-chain protocol that uses `MetaOracle` to price assets, collateral, or liquidation thresholds can receive a stale median price. Depending on the protocol:

- Incorrect liquidations (users liquidated when they should not be, or not liquidated when they should be).
- Loans priced against stale collateral values, enabling under-collateralised borrowing.
- Arithmetic underflow abort (Scenario A) causes a transaction-level DoS for any caller who adds oracles in decreasing timestamp order.

This matches the "harmful smart-contract behavior" class in the HackenProof High/Medium gate.

---

### Likelihood Explanation

- `MetaOracle` is a public framework API with no access control; any package can call it.
- The oracle ordering is determined by the caller at PTB construction time. A caller who passes a stale oracle last (intentionally or accidentally) triggers the vulnerability.
- `SimpleOracle` objects are shared objects; their staleness depends entirely on whether the oracle operator has submitted recent data. Network congestion or operator failure can make any oracle stale without warning.
- No existing guard in `add_simple_oracle` or `combine` compares any timestamp against `sui::clock::Clock`, so there is no on-chain circuit-breaker.

---

### Recommendation

Replace the unconditional assignment in `add_simple_oracle` with a proper maximum:

```move
public fun add_simple_oracle<T: copy + drop + store>(
    meta_oracle: &mut MetaOracle<T>,
    oracle: &SimpleOracle,
    clock: &Clock,                          // add clock parameter
) {
    let oracle_data = oracle::simple_oracle::get_latest_data(oracle, meta_oracle.ticker);
    if (option::is_some(&oracle_data)) {
        let ts = data::timestamp(option::borrow(&oracle_data));
        // 1. Reject data older than an absolute wall-clock threshold
        assert!(
            clock::timestamp_ms(clock) - ts <= MAX_STALENESS_MS,
            EStalePriceFeed
        );
        // 2. Track the true maximum
        if (ts > meta_oracle.max_timestamp) {
            meta_oracle.max_timestamp = ts;
        };
    };
    vector::push_back(&mut meta_oracle.oracle_data, oracle_data);
}
```

Additionally, guard against underflow in `combine`:

```move
let min_timestamp = if (max_timestamp >= time_window_ms) {
    max_timestamp - time_window_ms
} else {
    0
};
```

### Proof of Concept

1. Deploy the `oracle` package on a local Sui network.
2. Create three `SimpleOracle` shared objects: `O1`, `O2`, `O3`.
3. Submit data to `O1` at clock time T=1000 (fresh).
4. Submit data to `O2` at clock time T=500 (moderately stale).
5. Submit data to `O3` at clock time T=5 (very stale, price = 9999).
6. Call `trusted_fx(O1, O2, O3, amount)` — oracles added in order O1→O2→O3.
   - After step: `max_timestamp = 5`, `min_timestamp = 5 - 60000` → **underflow abort** (DoS).
7. Call `trusted_fx(O3, O2, O1, amount)` — oracles added in order O3→O2→O1.
   - After step: `max_timestamp = 1000`, `min_timestamp = 940`.
   - O3 (T=5) is filtered out. O2 (T=500) is filtered out. Only O1 survives.
   - `threshold = 3` but only 1 value survives → **assert fires** (DoS).
8. Call `trusted_fx(O3, O1, O2, amount)` — oracles added in order O3→O1→O2.
   - After step: `max_timestamp = 500`, `min_timestamp = -59500` → underflow abort (DoS).
9. Call `trusted_fx(O2, O3, O1, amount)` — oracles added in order O2→O3→O1.
   - After step: `max_timestamp = 1000`, `min_timestamp = 940`.
   - O2 (T=500) filtered, O3 (T=5) filtered, O1 (T=1000) passes.
   - Only 1 value, threshold=3 → assert fires (DoS).
10. Call `trusted_fx(O1, O3, O2, amount)` — oracles added in order O1→O3→O2.
    - After step: `max_timestamp = 500`, `min_timestamp = -59500` → underflow abort.

In every ordering except O3→O2→O1 (which still DoSes due to threshold), the broken `max_timestamp` either causes an underflow abort or allows stale data through. A protocol that fixes the ordering to avoid DoS (e.g., always adds fresh oracle last) will silently accept stale data from earlier oracles whenever those oracles fall behind.
