### Title
Signer's equivocation guard is not reconstructed from gossip after local SignerDB loss — restart can allow signing a conflicting block (`stacks-signer/src/v0/signer.rs`)

### Summary
The Apache Airflow CVE is a session-fixation bug: an event that should invalidate prior authorization (password reset) failed to tear down the pre-existing session, letting the old session keep acting as if nothing changed. The structural analog here is the signer's block-signing history ("session" that must survive across restarts to keep the equivocation guard alive) not being reconstructed from the gossip layer (StackerDB) when the local `SignerDb` is lost or reset, unlike the miner-state view, which explicitly *is* rebuilt from StackerDB on startup.

### Finding Description
`Signer::new` [1](#0-0)  initializes a fresh `SignerDb` and, on start-up, pulls only `StateMachineUpdate` chunks from the `MessageSlotID::StateMachineUpdate` StackerDB contract to seed `global_state_evaluator` and rebuild `LocalStateMachine` [2](#0-1) . It performs **no equivalent reconstruction** of the block-signing/pre-commit history (the `blocks` table) from the `BlockResponse` or pre-commit StackerDB slots.

That `blocks` table is the sole backing store for the equivocation guard used throughout the pre-commit → signature path:
- `get_last_signed_block` [3](#0-2)  — used by `check_block_against_signer_db_state` to decide whether a tenure already has a signed tip.
- `get_signed_conflicts` [4](#0-3)  — used at pre-commit time to find any block this signer (or the group) already signed at or above a given height, in *any* tenure, before allowing a new signature [5](#0-4) .
- `has_signed_block_in_tenure` — regression-tested specifically so a pre-commit (no signature) is never mistaken for a signed commitment [6](#0-5) .

All of this state lives only in the local SQLite file and is populated incrementally as `insert_block` is called during normal operation; it is never replayed from `BlockResponse`/pre-commit StackerDB messages the way `StateMachineUpdate` is. The project's own regression test `signer_loads_stackerdb_updates_on_startup` [7](#0-6)  explicitly documents a scenario where the SignerDB is cleared and the signer restarts — but the test's stated guarantee ("Verifies that updates are loaded from stackerdb on init") only covers the miner/state-machine view, not the block-signature equivocation guard. After such an event, `get_signed_conflicts` and `get_last_signed_block` for the affected tenures return empty, so `handle_block_pre_commit`'s conflict check [5](#0-4)  finds no historical conflict at all, even though the signer previously put a signature on a different block at the same height (e.g., a rival block from the pre-restart tenure, or a sibling produced by a miner re-proposing after a timeout).

### Impact Explanation
If the local SignerDB is lost or reset (crash before an fsync, disk fault, node migration, or any operational event that truncates/loses the sqlite file) while the signer keeps its StackerDB slot and reward-cycle registration, the restarted signer resumes signing with a "clean" equivocation guard. A one-slot miner (or gossip replay of a stale/rival block) can then get this signer to sign a second, conflicting block at a height/tenure it had already signed pre-restart — this is a concrete safety break (a signer signing a conflicting block), matching the "Critical: a signer signing an invalid, non-canonical, or conflicting block" impact class, though it requires the specific operational precondition of local state loss (so effective severity sits between High and Critical depending on how the guard-loss is triggered).

### Likelihood Explanation
The precondition (loss/reset of local SignerDB without a corresponding gossip resync of block history) is explicitly exercised in-repo by the maintainers' own test description, showing it is a recognized, reachable operational scenario for a single signer (crash mid-cycle, DB reset). No majority collusion or another signer's key is needed — only the affected signer's own restart plus a miner/gossip re-proposal of a conflicting block at the previously-signed height.

### Recommendation
On `Signer::new`, in addition to replaying `StateMachineUpdate` chunks, replay the `BlockResponse` (accept/reject) and pre-commit StackerDB slots for the reward cycle to reconstruct enough of the `blocks` table (at minimum, `signed_self`/`signed_group` timestamps and heights per consensus hash) to repopulate `get_signed_conflicts`/`get_last_signed_block` before the signer is allowed to answer new proposals. Alternatively, refuse to participate in signing for a reward cycle until the signer has observed a full round of gossip that lets it reconstruct its own recent signing history, mirroring the special-casing already done for `StateMachineUpdate`.

### Proof of Concept
1. Signer S signs block A at height H in tenure T1 (updates `blocks` table with `signed_self`).
2. S's SignerDb file is lost/reset (crash, disk issue, or manual recovery) while S remains registered and its StackerDB slot is intact.
3. S restarts; `Signer::new` reloads `StateMachineUpdate` from StackerDB but leaves the `blocks` table empty — `get_signed_conflicts` and `get_last_signed_block` for T1 now return nothing.
4. A miner or gossiped pre-commit re-proposes block B at height H (same tenure T1 or a sibling tenure) that conflicts with A.
5. `handle_block_pre_commit`'s conflict check finds no conflict (guard is empty) and allows S to sign B, producing two signer signatures over conflicting blocks at height H from the same signer — the exact equivocation the guard exists to prevent [5](#0-4) .
