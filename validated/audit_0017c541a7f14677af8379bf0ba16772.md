### Title
Blacklisted lender permanently unable to claim funded withdraw proceeds — no alternative recipient - ([IdleCreditVault.sol: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
When a lender calls `requestWithdraw`, `IdleCreditVault.requestWithdraw` burns the CDO's strategy tokens and mints a receipt to the user while bookkeeping the claim under `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user]` keyed to `msg.sender` [1](#0-0) . Later, `claimWithdrawRequest(_user)` — reachable only through `IdleCDOEpochVariant.claimWithdrawRequest()`, which hardcodes `msg.sender` as `_user` [2](#0-1)  — burns the user's receipt and sends the funded underlying to that same address via `_transferFundedClaim` [3](#0-2) . If the underlying is a blacklistable stablecoin (USDC/USDT) and the user's address is blacklisted between request and claim, every claim path reverts on the token transfer, permanently freezing the user's already-funded proceeds.

### Finding Description
The bug-class translation is direct: like OpenQ's `refundDeposit`, all payout functions push tokens to a fixed address with no `to` parameter:

- `_claimFundedWithdrawRequest` burns the receipt then calls `_transferFundedClaim(_user, amount)` [3](#0-2) .
- `claimInstantWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `_claimLossAdjustedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`, and `_claimDefaultedInstantWithdrawRequest` all pay `_user` identically [4](#0-3) [5](#0-4) .
- `IdleCDOEpochQueue.claimWithdrawRequest` and `claimDepositRequest` likewise send underlying/tranche tokens to `msg.sender` only [6](#0-5) .

Crucially, the claim entitlement is ledger-based, not token-based: `withdrawsRequests`, `withdrawsRequestsByEpoch`, `apr0Users`, `instantWithdrawsRequests`, and `postDefaultRequests` are all keyed by address. Although strategy-token receipts are minted to the user, the minted tokens alone do not carry the claim — `_burn(_user, ...)` burns from `_user` but the amounts paid come from the per-address ledgers. A blacklisted user cannot transfer their claim position to a clean address: the minted receipt balance is what gets burned, and the ledger entries stay bound to the blacklisted address. There is no rescue path — `requestWithdraw` for a new request is independent of the old ledger entries, and no privileged or unprivileged function can redirect a claim to a different recipient.

Note the claim is atomic (state resets and burn revert together with the failed transfer), so funds are not stolen — they sit in the strategy forever, since `withdrawsRequests[_user]` can only be cleared by the same reverting transfer.

### Impact Explanation
A KYC-passing lender whose address is blacklisted by the underlying issuer (e.g., USDC blacklist, sanctions) after requesting a withdrawal permanently loses access to their funded claim. Because claims are funded at `stopEpoch` into the strategy and only releasable via the fixed-recipient transfer, the user has zero recovery options: cannot claim, cannot delegate, cannot move the ledger entry. This is permanent freezing of user funds, quantified as the full `withdrawsRequests[_user] + apr0 + instant + postDefault` claim balance.

### Likelihood Explanation
Requires the underlying to be a centrally-controlled token with blacklist/freeze functionality and the user's address to be blacklisted in the window between `requestWithdraw` and claim — an externally-driven condition, not attacker-induced, matching the Medium severity of the source report.

### Recommendation
Add a recipient parameter, e.g. `claimWithdrawRequest(address _to)` on `IdleCDOEpochVariant` forwarded to `IdleCreditVault.claimWithdrawRequest(msg.sender, _to)`, so the transfer goes to `_to` while ledger clearing and receipt burning stay keyed to `msg.sender`. Apply the same `_to` parameter to `claimInstantWithdrawRequest` and to `IdleCDOEpochQueue.claimDepositRequest`/`claimWithdrawRequest`.

### Proof of Concept
Foundry fork PoC (USDC as `defaultUnderlying`):

1. Deploy CDO + `IdleCreditVault`; user completes Keyring KYC, deposits AA via `idleCDO.depositAA`.
2. `startEpoch`; borrower repays at `stopEpoch` so the epoch cycles normally.
3. User calls `cdoEpoch.requestWithdraw(trancheAmount, AATranche)` → `withdrawsRequests[user]` set, receipt minted.
4. `startEpoch`; fund borrower, `stopEpoch` → strategy `collectWithdrawFunds` pulls underlying; claim becomes funded.
5. `vm.prank(usdcMasterMinter)` / `blacklister.blacklist(user)` on USDC mainnet.
6. `vm.prank(user); vm.expectRevert(); cdoEpoch.claimWithdrawRequest();` — `claimWithdrawRequest` → `_claimFundedWithdrawRequest` → `_transferFundedClaim` → USDC `safeTransfer` reverts.
7. Assert `withdrawsRequests[user]` unchanged and no path exists for the user to recover the claim (transferring receipt tokens does not move the ledger entry; re-requesting is `revert NotAllowed` only post-default, but even a fresh request still pays the blacklisted address).

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  function claimWithdrawRequest(uint256 _epoch) external {
    // check if withdraw requests were processed and claimed for the epoch
    uint256 _withdrawPrice = epochWithdrawPrice[_epoch];
    _checkNotAllowed(
      (_withdrawPrice == 0 && !isEpochWithdrawZero[_epoch]) ||
      epochPendingClaims[_epoch] != 0
    );
    // amount is in tranche tokens
    uint256 amount = userWithdrawalsEpochs[msg.sender][_epoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request counter for the epoch
    userWithdrawalsEpochs[msg.sender][_epoch] = 0;
    // transfer underlyings to user based on the withdraw price of that epoch
    if (_withdrawPrice != 0) {
      IERC20Detailed(underlying).safeTransfer(msg.sender, amount * _withdrawPrice / ONE_TRANCHE);
    }
