### Title
`getProgramAccounts` scans can return accounts no longer owned by the queried program due to stale `ProgramId` secondary index entries - (File: `rpc/src/rpc.rs`, `accounts-db/src/accounts_db.rs`)

### Summary
The Metamorphic Contract Attack report describes a scenario where an on-chain entity's identity at a given address diverges from its recorded/expected implementation, causing callers to trust stale state. The closest concrete analog reachable via unprivileged RPC in Agave is the documented staleness of the `AccountIndex::ProgramId` secondary index in `accounts-db`, combined with an RPC path (`get_filtered_program_accounts`) that does not apply an owner post-filter when the index path is used.

### Finding Description
`AccountsDb::update_secondary_indexes` inserts a `(program_id -> pubkey)` mapping into the `ProgramId` secondary index whenever an account is stored, but old mappings for a pubkey are only removed when the pubkey dies out of the accounts index entirely (see the extensive comments on stale entries in `accounts-db/src/accounts_db.rs:1359-1388` and `accounts_index.rs:614-660`). When an account is "wiped and reinitialized" — i.e., closed to zero lamports and then recreated under a *different* owning program at the *same address* — the old `(old_owner -> pubkey)` secondary-index entry can persist until the key is fully purged from the write cache and primary index.

This is explicitly demonstrated in `runtime/src/bank/tests.rs:3470-3572` (`test_get_filtered_indexed_accounts`), where an account re-stored under `another_program_id` is still returned by `get_filtered_indexed_accounts(&IndexKey::ProgramId(program_id), ...)` for the **original** `program_id`, and the test comment says: *"This demonstrates the need for a redundant post-processing filter."* [1](#0-0) 

Agave's RPC layer is aware of this and defends against it for SPL-token secondary indexes (`SplTokenOwner`/`SplTokenMint`) by pushing extra `TokenAccountState`/`Memcmp` filters before calling `get_filtered_indexed_accounts`: [2](#0-1) [3](#0-2) 

However, the `ProgramId` index path in `get_filtered_program_accounts` does **not** add an equivalent post-filter that checks `account.owner() == program_id` before returning results from `get_filtered_indexed_accounts`: [4](#0-3) 

The only owner-check filter applied comes from `filters` supplied by the caller in the RPC request (`filter_allows`); if the caller supplies no owner-specific filter (which is the normal `getProgramAccounts` case since the program id is implicit and not re-validated), stale index-driven pubkeys owned by a different program can be surfaced.

### Impact Explanation
An unprivileged client calling the `getProgramAccounts` JSON-RPC method with a `programId` that has previously had `ProgramId` accounts index-only recreated under a different owner could receive results that include accounts **no longer owned by the queried program** — i.e., wrong/stale data returned for a single low-rate, unprivileged read. This maps to the "wrong-slot/fork/account data returned" acceptance criterion. It does not crash the validator or affect consensus, but it does violate the invariant that `getProgramAccounts` results are owned by the requested program, which downstream consumers (wallets, indexers) implicitly trust — the same trust violated by the metamorphic-contract analog in the original report (address ↔ implementation binding no longer holding).

### Likelihood Explanation
This requires: (1) the validator to have `--account-index program-id` enabled (secondary indexes are opt-in, not default), and (2) an account being closed to zero lamports and re-created under a different owner at the same pubkey — both of which are permissionless, ordinary Solana operations (any account can be zeroed and reinitialized by its owning program, e.g. `system_program::assign` + re-init). No special privilege is needed to trigger the underlying state transition; only the RPC operator needs to have opted into secondary indexes, which is a common configuration to speed up `getProgramAccounts`. This is not in the SECURITY.md exclusion list (it's a single call, not a scan requiring an index bypass — indeed it's a case *with* the index enabled).

### Recommendation
Add a post-filter to `get_filtered_program_accounts` in `rpc/src/rpc.rs` analogous to the ones already used for `get_filtered_spl_token_accounts_by_owner`/`by_mint`, ensuring that when the `ProgramId` secondary index path is taken, results are filtered to accounts whose current `owner()` equals the queried `program_id` before being returned to the client.

### Proof of Concept
1. Run a validator/RPC node with `--account-index program-id` enabled.
2. Create account `A` owned by `Program1`.
3. Zero out account `A` (e.g. transfer away all lamports so it's reclaimed to `AccountSharedData::default()`), then, in a subsequent slot, re-create the same address `A` this time owned by `Program2` (as shown in `runtime/src/bank/tests.rs:3505-3551`, which is a unit test exercising exactly this scenario at the `Bank`/`AccountsDb` layer).
4. Call `getProgramAccounts(Program1)` over RPC before the stale `ProgramId` secondary-index entry for `Program1 -> A` is purged (purging depends on cache eviction/rooting timing per the comments in `accounts_db.rs:1359-1388`).
5. Observe that `A` (now genuinely owned by `Program2`) can still be returned in the `Program1` result set, because `get_filtered_program_accounts`'s indexed path applies only caller-supplied filters, not an owner-equality post-filter. [5](#0-4) [6](#0-5) [7](#0-6)

    /// Use a set of filters to get an iterator of keyed program accounts from a bank
    #[allow(clippy::result_large_err)]
    async fn get_filtered_program_accounts(
        &self,
        bank: Arc<Bank>,
        program_id: Pubkey,
        mut filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> RpcCustomResult<Vec<(Pubkey, AccountSharedData)>> {
        optimize_filters(&mut filters);
        if self
            .config
            .account_indexes
            .contains(&AccountIndex::ProgramId)
        {
            if !self.config.account_indexes.include_key(&program_id) {
                return Err(RpcCustomError::KeyExcludedFromSecondaryIndex {
                    index_key: program_id.to_string(),
                });
            }
            self.get_filtered_indexed_accounts(
                &bank,
                &IndexKey::ProgramId(program_id),
                &program_id,
                filters,
                sort_results,
            )
            .await
            .map_err(|e| RpcCustomError::ScanError {
                message: e.to_string(),
            })
        } else {
            // this path does not need to provide a mb limit because we only want to support secondary indexes
            let mut accounts = self
                .runtime
                .spawn_blocking(move || {
                    bank.get_filtered_program_accounts(
                        &program_id,
                        |account: &AccountSharedData| {
                            filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                        },
                    )
                    .map_err(|e| RpcCustomError::ScanError {
                        message: e.to_string(),
                    })
                })
                .await
                .expect("Failed to spawn blocking task")?;
            if sort_results {
                // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
                accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
            }
            Ok(accounts)
        }
    }

    /// Purges each key in `removed_keys` from the enabled secondary indexes, unless the key is
    /// still alive in the write cache. `removed_keys` must be keys that are not present in the
    /// primary index
    ///
    /// The cache check is all-or-nothing per key: a key kept because it is cache-live retains all
    /// of its secondary entries, including stale ones from its dead rooted versions (e.g. an old
    /// mint after the account is re-created with a new one). Scans tolerate stale entries by
    /// post-filtering against account data, and they are removed the next time the key dies while
    /// not cache-resident.
    ///
    /// Cache writes populate the secondary indexes but not the primary index, so a key that is gone
    /// from the primary index can still be alive in the write cache and must keep its secondary
    /// entries. This is tricky due to the races that need to be considered:
    /// 1) Removed from the cache then re-added to the cache by replay
    /// - This is protected by re-checking the cache in the closure passed to purge. Since purge
    ///   holds the secondary index's reverse-index lock when it re-checks cache presence, and a
    ///   cache store writes the cache before inserting into the secondary index under that same
    ///   lock, either the re-check sees the cache write and the entry is not removed, or the
    ///   removal wins and the store's later insert re-adds it.
    /// 2) Removed from the cache, and also simultaneously removed from storage by clean
    /// - Since both the cache removal and the index removal are done before the removal from the
    ///   secondary index, the worst case is a double removal (both paths remove the same secondary
    ///   index entry). This is safe since the secondary index removal is idempotent.
    /// 3) Removed from the storage, but still present in the cache
    /// - This is protected by checking the cache presence in the closure. If the pubkey is still
    ///   present in the cache, the secondary index entry is not removed.
    ///
    /// We do not need to consider removed from cache -> added to storage. Adding to storage
    /// requires a cache entry to be present first, so a fresh store of the key would have to be
    /// rooted and flushed inside this window — impossible because rooting is driven by the same
    /// ReplayStage thread that purges unrooted slots, and clean runs serially with flush on the
    /// ABS thread.
