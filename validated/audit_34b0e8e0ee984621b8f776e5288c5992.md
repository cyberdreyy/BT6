### Title
Defaulted-epoch APR0 receipts settled before default finalization are paid twice — once inside the haircutted claim and again at par through the funded-claim path - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The upstream bug is a use-after-free in an error path: cleanup frees an object, then a later error path frees it again. The analog in `IdleCreditVault.claimWithdrawRequest` is a double payout in the claim path: after default recovery is finalized, the function first clears the defaulted-epoch receipt (`_claimDefaultedWithdrawRequest`) and then unconditionally falls through to `_claimLossAdjustedWithdrawRequest` and `_claimFundedWithdrawRequest`, which re-pay APR0 amounts for the same defaulted epoch at par because they live in the *settled* buckets (`apr0Users[_user].settledPrincipal` / `settledInterest`) that `_clearWithdrawClaimForEpoch` never clears.

### Finding Description
`claimWithdrawRequest` composes three claim sub-paths in a single call:

- `_claimPostDefaultWithdrawRequest(_user)` — returns early only if it paid something.
- `_claimDefaultedWithdrawRequest(_user)` — clears `withdrawsRequestsByEpoch` and the *open* `apr0User.principal` for `defaultRecoveryEpoch` via `_clearWithdrawClaimForEpoch`, decrements `pendingWithdraws`, burns the receipt, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve`.
- `_claimFundedWithdrawRequest(_user)` — calls `_settleApr0(_user)` then pays `withdrawsRequests[_user] + apr0User.settledPrincipal + apr0User.principal + apr0User.settledInterest` **at par** via `_transferFundedClaim` and `delete apr0Users[_user]`.

The bug-class match: `_clearWithdrawClaimForEpoch` "frees" the defaulted-epoch claim state, but only touches `apr0User.principal` / `principalEpoch` (lines 821–831). It never touches `apr0User.settledPrincipal` or `apr0User.settledInterest`. The code itself acknowledges that `prepareStopEpochWithApr0` may close the global APR0 bucket before default finalization (comment at line 826), i.e. APR0 principal belonging to the defaulted epoch can already have been moved into `settledPrincipal`/`settledInterest` by epoch settlement. `_withdrawClaimAmountsForEpoch` (lines 862–881) only counts `apr0User.principal` when building the defaulted claim basis, so:

- If the APR0 request was settled into `settledPrincipal`/`settledInterest` before default finalization, those amounts are excluded from the haircutted claim (no haircut applied, no `pendingWithdraws` decrement) but are still paid at par by `_claimFundedWithdrawRequest` in the same call — escaping the loss waterfall entirely.
- If they remained in `principal` (covered by the defaulted claim), `delete apr0Users[_user]` in the funded path removes them a second time after `_clearWithdrawClaimForEpoch` already zeroed them — the second "free" is benign for `principal` but the symmetric settled-bucket double-pay above is not.

In both cases the extra payment goes through `_transferFundedClaim`, whose only guard protects `defaultRecoveryReserve` (lines 897–907); it does not verify the amount was actually funded by the borrower. The paid tokens come out of the vault's general funded-claim balance.

### Impact Explanation
A KYC-passing lender with an APR0 withdraw request in the defaulted epoch can claim APR0 principal + interest at 100 cents on the dollar (instead of `defaultRecoveryPrice`), and in the settled-bucket case receives value that was never borrower-funded for them. Each such claim drains underlyings earmarked for other funded receipt holders, breaking the loss-socialization invariant (haircut should apply to all defaulted-epoch receipts) and causing insolvency for later claimants — a direct theft/extraction of funds quantified as `settledPrincipal + settledInterest - (claimBasis * defaultRecoveryPrice / RECOVERY_FULL)` per abusing user, bounded by the vault's funded balance.

### Likelihood Explanation
Requires a borrower default (honest-privileged sequence: manager calls `stopEpoch`/default handling and `finalizeDefaultRecovery`), plus an attacker who holds an APR0-mode withdraw request whose settlement (`_settleApr0` during `prepareStopEpochWithApr0`/stopEpoch) ran before `defaultRecoveryFinalized` — a sequencing the code comments explicitly contemplate. After that the attack is a single `claimWithdrawRequest` call routed through `IdleCDOEpochVariant`; no further privileged cooperation is needed. Likelihood is gated on a real default occurring, but conditional on default the payout discrepancy is deterministic.

### Recommendation
In `_clearWithdrawClaimForEpoch`, also fold `apr0User.settledPrincipal` and `apr0User.settledInterest` belonging to the claim epoch into `claimBasis`/`burnAmount` (or zero them and include them in the haircutted payout), and in `_claimFundedWithdrawRequest` exclude settled buckets tagged with `defaultRecoveryEpoch`. Alternatively, gate the funded-claim fall-through so defaulted-epoch settled APR0 amounts are claimed only once, at `defaultRecoveryPrice`.
