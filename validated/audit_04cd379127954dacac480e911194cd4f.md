### Title
Withdrawal fees can exceed principal+interest, reverting `requestWithdraw` and bricking `stopEpoch` fee transfer — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to the sudo bug where `protocolFee + tradeFee + royalty` can exceed `inputAmount` and cause the last transfer to revert or drain the contract's balance, `requestWithdraw` subtracts the combined upfront management fee and performance fee from `principal + interest` without checking that the fee total is bounded by the amount being withdrawn. When the upfront management fee exceeds `principal + interest`, the subtraction underflows and the request reverts. Worse, the fees that *were* successfully charged are accumulated into `pendingWithdrawFees`, and `stopEpoch` pays them out via `_transferFeeUnderlyings(_pendingWithdrawFees)` from the same pot pulled from the borrower. If the accumulated fees exceed `expectedInterest + netPendingWithdraws`, the fee transfer either reverts (bricking `stopEpoch`, freezing all vault funds) or consumes unrelated contract balance. There is no `fees < amount` guard anywhere in the fee path, exactly the missing check in the external report.

### Finding Description
In `requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:772-778`):

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
```

`_totalWithdrawFees` (`contracts/IdleCDOEpochVariant.sol:900-906`) returns the raw management fee whenever `_mgmtFee >= _interest`:

```solidity
uint256 _mgmtFee = _calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration());
return _mgmtFee >= _interest ? _mgmtFee : _interest - _netGainAfterFees(_interest, _mgmtFee);
```

The management fee is charged on the *full principal* for `epochDuration + remaining buffer` (`_withdrawRequestManagementFeeDuration`, lines 925-931), which can exceed one year for long epochs plus the buffer. So `_mgmtFee` can exceed `principal + interest` (e.g., managementFee ≈ 100%/yr of `FULL_ALLOC` with `epochDuration = 365 days` and a request made early in the buffer gives a fee > principal), and `principal + interest - totalFees` underflows → revert. There is no `totalFees < principal + interest` check, the direct analog of the missing `protocolFee + royaltyTotal + tradeFeeAmount < inputAmount` check.

The second-order effect is the balance-drain half of the sudo bug: `pendingWithdrawFees` is accumulated at request time but only paid at `stopEpoch`, where `_transferFeeUnderlyings(_pendingWithdrawFees)` (line 419) is executed out of the cash pulled by `getFundsFromBorrower(_expectedInterest + _pendingWithdraws)`, and `_pendingWithdraws` is already *net of fees*. Since each valid request guarantees only `net = principal + interest - fees ≥ 0`, the pulled amount equals `expectedInterest + Σ(principal + interest − fees)`, which is ≥ `Σfees` only when `expectedInterest + Σprincipal + Σinterest ≥ 2·Σfees`. When a large share of TVL requests withdrawal under a high fee regime, the pulled amount can be smaller than `pendingWithdrawFees`, so the `safeTransfer` reverts — making `stopEpoch` permanently uncallable and freezing all lender funds — or consumes residual contract balance meant for other purposes. Donated assets cannot rescue it because `_skimDonatedAssets()` (line 355) zeroes the raw balance before the pull.

### Impact Explanation
Two failure modes, both matching the external report:

1. `requestWithdraw` reverts for every request whenever `_calculateManagementFee(principal, epochDuration + remainingBuffer) > principal + interest` — all new withdrawal requests are frozen while the parameter set holds (temporary freezing, lifted only by owner reducing `managementFee`, `epochDuration`, or `bufferPeriod` — note `bufferPeriod` is baked into `epochEndDate + bufferPeriod` for the current epoch).
2. Once enough `pendingWithdrawFees` accrue from requests where `fees` approaches `principal`, `stopEpoch`'s fee transfer exceeds the pulled borrower amount and reverts → the epoch can never be stopped → permanent freezing of all vault funds (every tranche holder's principal and interest).

### Likelihood Explanation
Requires a high-but-honest fee configuration: `managementFee` on the order of ~50–100% of `FULL_ALLOC` per year combined with long `epochDuration`/`bufferPeriod` (both are within the allowed parameter space; tests already use `epochDuration = 365 days`). An unprivileged KYC-passing lender triggers it simply by calling `requestWithdraw` — no malicious privileged role needed; the owner/manager only set permitted parameters. Mass withdrawal requests during the buffer window maximize the accrued `pendingWithdrawFees` vs. the pullable amount, enabling the `stopEpoch`-bricking path. No existing guard (`_checkAmountTooHigh`, skim, fee caps, epoch gating) bounds `totalFees` against `principal + interest` or `pendingWithdrawFees` against the pulled amount.

### Recommendation
- In `requestWithdraw`, clamp or explicitly check `totalFees < principal + interest` and revert with a dedicated error (or cap `totalFees` at `principal + interest`).
- Bound `managementFee * (epochDuration + bufferPeriod)` to `< FULL_ALLOC * 365 days` in the parameter setters so the upfront fee can never exceed principal.
- In `_stopEpoch`, check `_pendingWithdrawFees <= _amountToPullFromBorrower + _pendingWithdraws` (or cap the fee transfer at the pulled amount) so the fee transfer can neither revert nor consume unrelated balance — the same ordering/consistency fix recommended for the sudo pair contracts.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.x;
import "forge-std/Test.sol";

// Fork: mainnet; uses the repo's own test helpers (_setFeeParams, _setManagementFee).
contract WithdrawFeeExceedsInputPoC is Test {
    // Constants mirroring test/foundry/IdleCreditVault.t.sol setup
    uint256 constant ONE_SCALE = 1e6;           // USDC underlying
    uint256 constant FULL_ALLOC = 100_000;

    function testRequestWithdrawRevertsWhenMgmtFeeExceedsPrincipalPlusInterest() external {
        uint256 amount = 10_000 * ONE_SCALE;

        // Honest owner config: 100%/yr management fee, 0 performance fee
        _setFeeParams(FEE_RECEIVER, 0, FULL_ALLOC, 0);
        _setManagementFee(FULL_ALLOC);          // 100% annualized

        uint256 trancheAmount = idleCDO.depositAA(amount);
        _transferBurnedTrancheTokens(address(this), true);

        // Long epoch: 365 days + buffer makes fee duration > 1 year
        vm.prank(manager);
        cdoEpoch.setEpochParams(365 days, 30 days);

        // Request made inside the buffer => fee duration = epochDuration + remainingBuffer
        // mgmtFee = principal * 1.0 * (365+30)d / 365d > principal + interest
        // => principal + interest - totalFees underflows -> revert
        vm.expectRevert(); // stdError.arithmeticError
        cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));
    }

    function testStopEpochBrickedWhenPendingWithdrawFeesExceedPull() external {
        uint256 amount = 10_000 * ONE_SCALE;

        // managementFee ~60%/yr: each request still passes (fees < principal + interest)
        // but aggregate fees exceed interest + net receipts pulled at stopEpoch.
        _setFeeParams(FEE_RECEIVER, 0, FULL_ALLOC, 0);
        _setManagementFee(60_000);

        uint256 trancheAmount = idleCDO.depositAA(amount);
        _transferBurnedTrancheTokens(address(this), true);

        vm.prank(manager);
        cdoEpoch.setEpochParams(365 days, 30 days);

        // Majority of TVL requests withdrawal during buffer -> fees ~0.6*principal*1.08,
        // net receipts small; pendingWithdrawFees accumulates
        cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));

        vm.prank(manager);
        cdoEpoch.startEpoch();

        // Borrower repays expected interest + pending withdraws (net of fees)
        deal(underlying, borrower, cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws());
        vm.prank(borrower);
        IERC20(underlying).approve(address(cdoEpoch), type(uint256).max);
        vm.warp(cdoEpoch.epochEndDate() + 1);

        // _transferFeeUnderlyings(_pendingWithdrawFees) exceeds pulled cash -> revert
        // -> epoch can never stop -> all funds frozen
        vm.prank(manager);
        vm.expectRevert(); // ERC20 transfer amount exceeds balance
        cdoEpoch.stopEpoch(0, 0);
    }
}
```

Caveat: the exact upper bound enforced on `managementFee` inside `setFeeParams`/`_setManagementFee` could not be confirmed from the indexed context; the PoC assumes values up to `FULL_ALLOC` are accepted. If a stricter cap exists, the required `epochDuration`/`bufferPeriod` combination scales accordingly, but the missing `fees < amount` check remains.
