### Title
Reorg-timing "at most one signed block" rule counts only globally-accepted blocks, letting a fast second sortition make signers sign a conflicting tenure over an already 70%-signed chain - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` is supposed to permit a tenure reorg only when every reorged tenure produced zero blocks, or produced exactly one block proposed very close to the burn-block transition [1](#0-0) . The actual disallow test only checks `get_globally_accepted_block_count_in_tenure`, i.e. blocks the *node* has confirmed as globally accepted, not blocks the signer set has already *signed* (`LocallyAccepted`, i.e. 70%-weight threshold reached) [2](#0-1) . A locally-accepted block that hasn't yet been observed by the node as its canonical tip is invisible to this count, confirmed by the test showing `get_globally_accepted_block_count_in_tenure` returns 0 for a merely `LocallyAccepted` block [3](#0-2) . A one-slot miner can exploit this gap purely through proposal/sortition timing.

### Finding Description
The equality this rule is meant to enforce is: "a tenure with more than one *signed* block must never be reorged." But the code checks a strictly weaker, asynchronous proxy - `state == GloballyAccepted` - which only becomes true after the stacks-node processes a `NewBlock` event [2](#0-1) . Between the moment a block reaches the 70% pre-commit/signature threshold (`mark_locally_accepted`, `signed_group` set) and the moment the node reports it as its tip (`mark_globally_accepted`), there is a window in which the block is fully signed by the network but does not count toward this check.

If the reorg-disallow test does not trip (0 or 1 globally-accepted blocks), the function falls through to the timing branch, which asks only about the *first* approved block in the tenure via `get_first_approved_block_in_tenure` and its `approved_time` [4](#0-3) . It never looks at any later, still-only-locally-accepted block. So a tenure that in reality has two (or more) fully signed blocks - one globally accepted (or none) and one merely locally accepted - is evaluated solely on the *first* block's timing, and can be judged "poorly timed" (i.e., produced close enough to the sortition) and therefore reorg-eligible, even though a second block was already signed by the full weight of signers well after that window.

Once `check_parent_tenure_choice` returns `true`, the reorging tenure is recorded as superseded via `record_superseded_tenure`/`mark_tenure_superseded` [5](#0-4) , and that record makes the earlier signed blocks stop counting as conflicts in `get_signed_conflicts`, explicitly so "our own signature over what they built does not then block the replacement" [6](#0-5) . This is exactly the mechanism by which the whole signer set is led to place fresh signatures on a new tenure that conflicts with a chain state it had already signed off on (2+ blocks), because the reorg-permission decision undercounted "signed" state by conflating it with "node has already processed it."

### Impact Explanation
This breaks the "signed vs validated" and "one-per-height" equalities the scan is scoped to protect: the reorg-timing guard is meant to guarantee that a tenure with real, network-confirmed signer commitment (more than one signed block) can never be legitimately superseded by a later, faster-arriving sortition. Because the check is keyed to the node's global-acceptance state rather than the signer set's own signed state, a miner can arrange (via ordinary tenure timing - propose two blocks quickly, then win the very next sortition before the second block's `NewBlock` event propagates to the node) for the whole honest signer set to sign a conflicting tenure over blocks it, collectively, had already signed. That is a "signer signing a conflicting block" outcome - a Critical-class safety break under the given impact taxonomy, achievable with ordinary mining/proposal timing and no signer-key compromise or majority collusion, mirroring the NFT-withdrawal report's core lesson: relying on an asynchronous/observed proxy for a fact (NFT presence vs. loan state; here, "node has processed it" vs. "signer set has signed it") lets a single actor manufacture a window where the check passes when the underlying invariant it is supposed to protect no longer holds.

### Likelihood Explanation
The trigger requires only ordinary miner behavior: winning two tenures in quick succession and mining more than one block in the first before it stalls, timed so the second block's global confirmation lags behind the next sortition - which is explicitly the same "fast burn-block arrival" scenario the `first_proposal_burn_block_timing` mechanism is designed to handle (see the existing `allow_reorg_within_first_proposal_burn_block_timing_secs` test, which already demonstrates the general timing-based-reorg-allowance pattern in this codebase) [7](#0-6) . No majority-signer collusion, key compromise, or auth-token access is needed - it depends only on normal node/signer processing latency for the `NewBlock` event, which is entirely outside the miner's or the signers' control but is fully anticipatable/exploitable by an adversarial miner who controls proposal cadence and sortition timing.

### Recommendation
Change the reorg-disallow check in `check_parent_tenure_choice` to count blocks the signer set has *signed* (`LocallyAccepted` or `GloballyAccepted` - i.e. use something equivalent to `get_last_signed_block`/a "signed block count" query) instead of `get_globally_accepted_block_count_in_tenure`, and similarly make the timing fallback evaluate the *last* signed block's approval time (or refuse the reorg outright whenever more than one block was ever signed, regardless of the node's confirmation state), so a block's global-acceptance lag can never be used to hide the fact that the tenure already carries a full signer-weight signature over more than one block.

### Proof of Concept
1. Miner M wins tenure T1's sortition and proposes block A (tenure-start). Signers reach 70% pre-commit/signature threshold and sign it: `mark_locally_accepted` sets `signed_group`, but the node has not yet emitted the `NewBlock` event for A (network/processing latency) [8](#0-7) .
2. M immediately proposes block B in the same tenure T1, confirming A. Signers likewise reach threshold and sign B (`LocallyAccepted`), again before the node has processed either A or B as globally accepted. `get_globally_accepted_block_count_in_tenure(T1)` is now `0`, even though two blocks are fully signed [3](#0-2) .
3. M stalls T1 (or another node quickly wins the next sortition) so a new sortition happens fast enough that the elapsed time since A's `approved_time` is within `first_proposal_burn_block_timing` [9](#0-8) .
4. M (or any miner) wins T2's sortition, proposing a tenure-change block whose `parent_tenure_id` skips T1 (a reorg attempt). `check_parent_tenure_choice` sees `globally_accepted_blocks == 0` (not `> 1`), evaluates the "poorly timed" branch against A's timing only, finds it satisfied, and returns `true` - permitting the reorg even though T1 actually has two signed blocks (A and B) [10](#0-9) .
5. T1 is recorded as `superseded`, which clears A's and B's signatures as conflicts in `get_signed_conflicts` [11](#0-10) , and the whole signer set proceeds to sign T2's block, producing a signed, conflicting alternate history over a tenure that had already collected two full signer-weight signatures.
