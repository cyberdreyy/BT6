### Title
Claimed instant-withdraw receipts are never cleared from the per-epoch ledger, so they are counted again as prefunded recovery reserve on default - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out and zeroes only the aggregate `instantWithdrawsRequests[user]`, but never clears `instantWithdrawsRequestsByEpoch[user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. This is the exact analog of "release without NULLing the pointer": the receipt is released (paid) but its per-epoch reference remains dangling. If the *same* epoch later ends in a borrower default with a partially unfunded instant queue, `finalizeDefaultRecovery` re-reads that stale entry via `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` and books already-paid-out funds as held recovery reserve, inflating `defaultRecoveryPrice` and making the `defaultRecoveryReserve` insolvent for later claimants.

### Finding Description
In `IdleCreditVault.sol`:

```solidity
// claimInstantWithdrawRequest (lines 380-393)
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Only the aggregate counter is reset. `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` keep their stale values.

At default finalization:

```solidity
// defaultPendingClaimBasis (lines 644-649)
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber]; // includes already-claimed receipts
}

// _defaultPrefundedInstantReserve (lines 716-723)
if (instantBasis > pendingInstant) {
  prefundedReserve = instantBasis - pendingInstant;  // counts paid-out funds as held
}
```

`prefundedReserve` is added to `reserveAmount` in `finalizeDefaultRecovery` (line 686) even though those underlyings were already transferred out to claimants, so `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed on phantom funds.

### Impact Explanation
The recovered reserve is priced as if already-claimed instant funds were still held. Recovery claimants are paid `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` against a `defaultRecoveryReserve` that does not actually contain the phantom amount. Payouts proceed in claim order until the real balance is exhausted; subsequent `_transferDefaultRecovery` calls underflow `defaultRecoveryReserve` or fail the ERC20 transfer, permanently freezing the recovery claims of later defaulted-epoch and post-default claimants, while early claimants are overpaid relative to the true recovery ratio. Loss equals the stale claimed instant amount.

### Likelihood Explanation
Requires, in a single epoch: (a) an instant withdrawal requested and fully funded via `collectInstantWithdrawFunds`, claimed by the user mid-epoch; (b) a second, only-partially-funded instant request in the same epoch (`pendingInstantWithdraws != 0` at stop); (c) the borrower defaults at that `stopEpoch` and `finalizeDefaultRecovery` is invoked. All steps use honest privileged actors and ordinary unprivileged user actions (request + claim instant withdrawal). No guard prevents it: the funded claim path deliberately skips per-epoch cleanup, and `_defaultPrefundedInstantReserve` has no way to distinguish paid from unpaid receipts.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers for each epoch contributing to the claimed amount (iterate or track the request epochs): set `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed basis, mirroring what `_claimDefaultedInstantWithdrawRequest` does. Alternatively, keep a per-epoch "claimed" flag so finalized accounting never re-reads released receipts.

### Proof of Concept
Foundry fork sequence (instant-withdraw-enabled pool):

```solidity
// 1. Epoch N running. Attacker requests instant withdraw of A.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(A, address(AAtranche)); // via CDO helper
// instantWithdrawsRequestsByEpoch[attacker][N] = A; instantWithdrawClaimsByEpoch[N] = A

// 2. Borrower/manager fund the instant queue; attacker claims A at par.
//    (collectInstantWithdrawFunds pulls A, pendingInstantWithdraws -> 0)
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// BUG: instantWithdrawsRequestsByEpoch[attacker][N] still == A
//      instantWithdrawClaimsByEpoch[N] still == A

// 3. Victim requests instant withdraw of B in same epoch; only partially funded.
vm.prank(victim);
cdoEpoch.requestInstantWithdraw(B, address(AAtranche));
// pendingInstantWithdraws == B (unfunded remainder), instantWithdrawClaimsByEpoch[N] == A + B

// 4. Epoch N ends in default (borrower repays 0). Manager finalizes.
//    basis += instantWithdrawClaimsByEpoch[N]  (= A + B, A is stale)
//    prefundedReserve = (A + B) - B = A        (phantom, already paid out)
//    recoveryPrice priced on reserveAmount including phantom A

// 5. Assert: sum of all claimants' _transferDefaultRecovery payouts exceeds
//    actual underlying held; last claimant's claim reverts.
//    defaultRecoveryReserve underflows / safeTransfer fails before all
//    instantWithdrawsRequestsByEpoch[*][N] claims are paid.
```

Key assertion: after step 2, `strategy.instantWithdrawsRequestsByEpoch(attacker, N)` returns `A` and `strategy.instantWithdrawClaimsByEpoch(N)` returns `A`, even though the receipt was fully paid — demonstrating the dangling released-receipt state that corrupts `finalizeDefaultRecovery`.
