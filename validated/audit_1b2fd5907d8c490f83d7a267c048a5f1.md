### Title
Stale confirmations from a deleted multisig member are still counted toward the confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges confirmations for requests that were *originally created* by the member being removed. It does not scan the `confirmations` set of *other* pending requests to strip out that member's confirmation votes. As a result, a member who was removed (e.g., because they were found to be malicious/compromised, mirroring the "malicious node" scenario in the report) can still have their previously-cast `confirm()` vote counted toward `num_confirmations` on any request they confirmed but did not create, letting the remaining members execute a request with fewer *live* confirmations than the configured threshold.

### Finding Description
`confirm()` stores confirmations as a `HashSet<String>` keyed by `request_id`, containing the string form of whichever `MultisigMember` confirmed: [1](#0-0) 

`delete_member()` is the only place that removes stale confirmations, but its cleanup is scoped to `r.member == member`, i.e. only requests that the removed member personally *created* via `add_request`: [2](#0-1) 

It never inspects `self.confirmations` for entries belonging to `member.to_string()` on requests created by *other* members. The threshold check in `confirm()` (`confirmations.len() as u32 + 1 >= self.num_confirmations`) counts set membership only, with no re-validation that every entry in the set corresponds to a currently-active `MultisigMember`: [3](#0-2) 

The binding that should hold is:
```
count(confirmations for request R) == count(live members who confirmed R)
```
After a `DeleteMember` action, a stale confirmation from the deleted member remains in the set, breaking this equality: `count(confirmations)` includes an entry that no longer corresponds to a live member.

The same defect exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` cleanup is likewise scoped only to `r.signer_pk == pk` (requests created by that key), leaving stale confirmations by that key on other requests intact: [4](#0-3) 

### Impact Explanation
This maps to the explicitly listed Critical impact: "a multisig request executed below threshold." A malicious or compromised member's vote persists as valid "signature weight" even after the multisig group revokes their membership specifically to strip their authority. Combined with a second, low-cooldown request created by the malicious member before removal (which is unaffected because `r.member == member` cleanup only fires when the malicious member is the *creator*, not the confirmer, of the request in question), the remaining `num_confirmations - 1` legitimate members can unknowingly (or if colluding with an attacker who timed their exit) finalize a `Transfer`, `AddKey`, `FunctionCall`, or `DeployContract` action that never actually received `num_confirmations` worth of live authorization. This directly undermines the K-of-N custody guarantee the multisig is meant to enforce over funds/keys held by the account.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a member later removed for being malicious/compromised to have first confirmed a request they did not create, and (b) that request to remain pending (not yet executed) at removal time. This is realistic in exactly the scenario this bug class targets — discovering a malicious signer and trying to excise their influence — since the natural remediation flow is: notice bad behavior → submit `DeleteMember` request → confirm and execute it. Any request the malicious member had already confirmed (on top of the one that triggers their removal) keeps its stale vote. No special privilege beyond ordinary multisig membership is needed to have cast the original confirmation; the "unauthorized" step is that the vote continues to count after the member has been stripped of standing.

### Recommendation
When executing `DeleteMember` (and `DeleteKey` in the legacy `multisig` contract), iterate over *all* pending requests' confirmation sets and remove any entry matching `member.to_string()` (or `signer_pk`), not just requests created by that member. Alternatively, validate at `confirm()` time (recompute effective confirmations by intersecting the stored set with `self.members` before comparing to `num_confirmations`) so a stale entry can never contribute to reaching the threshold.

### Proof of Concept
1. Initialize a 3-of-5 `multisig2` contract with members `{A, B, C, D, E}`, `num_confirmations = 3`.
2. Member `A` (later found malicious) calls `add_request` for a benign-looking Transfer request `R1` created by member `B` and confirms it: `B.add_request(R1)` then `A.confirm(R1)` → confirmations(R1) = `{B, A}` (2 confirmations, threshold 3 not yet reached).
3. Members discover `A` is malicious and submit/confirm a `DeleteMember { member: A }` request; `delete_member` executes, removing `A` from `self.members` and deleting `A`'s access key, but only purges confirmations for requests where `r.member == A` — `R1` (created by `B`) is untouched, so confirmations(R1) still contains `A`.
4. Member `C` calls `confirm(R1)`. `confirmations.len() as u32 + 1 == 3 >= num_confirmations (3)` → `R1` executes with only 2 truly live members (`B`, `C`) having confirmed, even though `A` is no longer a member.
5. Any funds/actions in `R1` are moved/executed despite failing the intended live-K-of-N guarantee — a multisig request executed below the effective threshold of live signers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
