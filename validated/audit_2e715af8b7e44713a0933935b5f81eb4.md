### Title
Miner-activity reset lacks a freshness bound when the tenure's last block is only locally accepted, letting a stalled/malicious miner block the inactivity fallback indefinitely - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` decides whether a conflicting/duplicate block proposal should still be treated as "miner activity" (which resets the inactivity clock that would otherwise trigger `check_miner_inactivity`'s fallback to the prior tenure's miner). For a `LocallyAccepted`-but-not-yet-`GloballyAccepted` tip, the freshness check that bounds this reset is unconditionally skipped, so the reset has no expiry, unlike the equivalent guard for a globally accepted tip.

### Finding Description
`check_latest_block_in_tenure` looks up the current highest signed block of the tenure via `get_tenure_last_block_info`/`get_last_signed_block`, which returns a block whenever it is `LocallyAccepted` or `GloballyAccepted` [1](#0-0) . When a new proposal does not exceed that block's height, the function decides whether to still record the attempt as miner activity:

```
if info.signed_group.is_none_or(|signed_time| {
    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
}) {
    ...
    signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs());
}
``` [2](#0-1) 

`signed_group` is only populated once the block is observed as globally/group-signed; a block that is merely `LocallyAccepted` (this signer signed it, but the 70% group threshold or global acceptance was never reached/observed) has `signed_group == None`. `Option::is_none_or` evaluates to `true` whenever the option is `None`, so for a merely-locally-accepted tip the freshness bound (`reorg_attempts_activity_timeout`) is never applied — every conflicting/duplicate proposal at or below that height unconditionally calls `update_last_activity_time`, with no expiry. This is asymmetric with the `Some(signed_time)` (globally observed) branch, which explicitly bounds the reset to `reorg_attempts_activity_timeout` after the signature time, and with the analogous pre-commit branch a few lines below, which is likewise bounded by `tenure_last_block_proposal_timeout` via `is_fresh_pre_commit` [3](#0-2) .

`update_last_activity_time` directly feeds `is_timed_out`/`check_miner_inactivity`, whose entire purpose is to detect that "the tenure timed out, try to see if we can use the prior tenure instead" [4](#0-3) . As long as `last_activity` keeps being refreshed, `elapsed > block_proposal_timeout` never holds, so the fallback path is never taken [5](#0-4) .

Because `check_latest_block_in_tenure` is invoked (through `check_block_against_signer_db_state`) on every block proposal received from the tenure's expected miner — at proposal arrival, at validate-ok, and at pre-commit-threshold time [6](#0-5)  — the current miner (the only party who can pass the earlier "expected miner" check) can keep this reset alive by repeatedly submitting cheap, doomed, conflicting/duplicate-height proposals, exactly mirroring the referenced report's pattern: a cheap, repeatable self-triggered action (`stake(1)`) that indefinitely defeats a same-block/timing guard meant to stop exactly that kind of abuse (`checkpointProtection`).

This is a "one-slot miner" analog: the actor able to trigger this is the current tenure's miner (plus whichever signers relay its messages), consistent with the allowed trigger surface in scope.

### Impact Explanation
While the current tenure's block is stuck at `LocallyAccepted` (e.g. a signer-set split, a slow/censoring group, or a miner who deliberately withholds broadcasting the signed block widely enough to reach global acceptance), the miner can indefinitely suppress `is_timed_out`/`check_miner_inactivity`'s fallback to the honest prior-tenure miner by repeatedly sending harmless-looking conflicting/duplicate proposals. This wedges the signer set into perpetually treating a stalled or uncooperative miner as "active," preventing it from ever considering the valid blocks a legitimate fallback miner would produce — a liveness wedge matching the High-impact category of a signer being kept from ever signing valid blocks from the miner that should take over.

### Likelihood Explanation
The trigger requires only the current tenure's miner to keep sending ordinary block proposals it already has the right to send; no majority collusion, no other signer's key, and no `auth_token`/local access are needed. The condition (last known block only `LocallyAccepted`, not `GloballyAccepted`) is a normal, frequently-reachable network state (any temporary signer-set delay or split), making this both easy to trigger and easy to sustain for as long as the miner wishes.

### Recommendation
Apply the same freshness bound used for the `Some(signed_time)` / pre-commit branches to the `signed_group.is_none()` case: derive a bounded window (e.g., from `signed_self`, or from the time the block first became `LocallyAccepted`) instead of unconditionally treating every conflicting proposal against a locally-accepted tip as fresh activity. This keeps the "miner may be slow" allowance while preventing indefinite suppression of the inactivity timeout.

### Proof of Concept
1. Miner M proposes and gets its block B (height H) signed locally by the signer (S), but B never reaches global/group acceptance (e.g., other signers are offline or slow), so `signed_self` is set but `signed_group` stays `None`.
2. M repeatedly proposes conflicting/duplicate blocks at height ≤ H (cheap to produce, since they are never expected to be accepted).
3. Each call reaches `check_latest_block_in_tenure`; since `info.signed_group` is `None`, `is_none_or` returns `true` unconditionally, and `update_last_activity_time` is invoked every time, with no expiry check [2](#0-1) .
4. Because `last_activity_time` never goes stale, `SortitionState::is_timed_out` never returns `true` for this tenure, so `check_miner_inactivity` never falls back to the prior (valid) tenure's miner [7](#0-6) , wedging the signer set on the stalled miner indefinitely.

```markdown
`check_latest_block_in_tenure` answers "does this block confirm the tip we
expect?" and it runs in three places: at proposal arrival (inside
`check_proposal`), at validate-ok, and at the moment of signing. _Which_ tenure
it is asked about depends on the block: a tenure-change block is checked against
its **parent** tenure, every other block against its **own**. Never both. The
pivotal helper is `get_tenure_last_block_info`, which considers only blocks that
carry a signature (`get_last_signed_block`): a pre-commit never vetoes anything,
it only counts as miner activity.
