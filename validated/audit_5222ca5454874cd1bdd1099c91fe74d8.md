### Title
Funded `claimInstantWithdrawRequest` never decrements per-epoch receipt counters, inflating defaulted-epoch claim basis and permanently pinning `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Netty bug is an unbalanced reference count on the *successful* path: a nested TLV parses fine, the message is released, but the backing buffer stays pinned forever. The vault analog is the successful `claimInstantWithdrawRequest` path in `IdleCreditVault`: it clears the aggregate `instantWithdrawsRequests[_user]` and burns the receipt, but never decrements the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that the default-recovery path relies on. The default-epoch claim path (`_claimDefaultedInstantWithdrawRequest`) treats those ledgers as the authoritative receipt count, so a receipt that was already paid out at par is still counted again when a default in the same epoch is finalized.

### Finding Description
`requestInstantWithdraw` maintains three counters for the same receipt (`IdleCreditVault.sol:366-374`):

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

The funded claim path (`IdleCreditVault.sol:380-393`) clears only the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Neither `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` is decremented. Compare with `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`), which does decrement all three and additionally reduces `pendingInstantWithdraws` with the comment that any excess over `pending` "was already counted as prefunded reserve during default finalization". In other words, the per-epoch counters are the reference count for how much of the epoch's instant-withdraw basis is still owed a recovery payout.

The attack sequence:

1. Epoch N is running. Unprivileged user requests an instant withdrawal of amount `A` (`requestInstantWithdraw` via `IdleCDOEpochVariant`). All three counters record `A`.
2. The CDO fulfills it (`collectInstantWithdrawFunds` drops `pendingInstantWithdraws` by `A` and pulls underlying from the CDO), and the user claims via `claimInstantWithdrawRequest`. User receives `A` underlying. `instantWithdrawsRequests[_user] = 0`, but `instantWithdrawsRequestsByEpoch[_user][N]` and `instantWithdrawClaimsByEpoch[N]` still hold `A`.
3. Before `stopEpoch`, the borrower defaults in epoch N (e.g., `epochEndDate` passes, `stopEpoch(0,0)` marks `defaulted`, manager calls `finalizeDefault`).
4. During default finalization the defaulted-epoch instant-claim basis is taken from `instantWithdrawClaimsByEpoch[N]` (the only per-epoch record of which receipts existed in that epoch). The already-paid `A` is counted as a still-outstanding funded/defaulted receipt, so `defaultRecoveryReserve` is sized too large — or, if the reserve is funded to cover it, the surplus `A` can never leave the contract.

This is exactly the Netty shape: the success path releases the caller-visible object (aggregate counter, receipt tokens) but leaks the per-epoch "nested" reference, permanently pinning the underlying buffer (`defaultRecoveryReserve`).

### Impact Explanation
- **Permanently locked recovery reserve**: recovery funding earmarked for the already-paid `A` sits in `defaultRecoveryReserve` with no legitimate claim path. `_claimDefaultedInstantWithdrawRequest` would attempt `instantWithdrawsRequests[_user] -= claimBasis` (`0 - A` underflows, revert) and `_burn(_user, A)` on a zero balance (revert), so the inflated reserve entry is unclaimable — funds are frozen, not merely mislabeled.
- **Skewed recovery price / blocked finalization**: if `defaultRecoveryPrice` is computed as `recovered / totalDefaultBasis` where the basis includes the stale `A`, every honest defaulted-epoch claimant receives a smaller haircut-adjusted payout than entitled (dilution of the recovery waterfall). If finalization instead requires the reserve to be funded to the inflated basis, `finalizeDefault`/`finalizeDefaultRecovery` can revert until extra underlying is supplied, delaying all claims.
- The loss scales linearly with the instant-withdraw volume claimed inside the defaulted epoch: an attacker (any KYC-passing lender) maximizes `A` via repeated request→fund→claim cycles before default, inflating the stuck amount.

### Likelihood Explanation
- Requires only unprivileged actions: instant withdraw requests and claims are available to any wallet passing `isWalletAllowed`/Keyring checks, and instant withdrawals are fulfilled *during* the epoch precisely so users can exit mid-epoch — so step 2 is routine, not adversarial gymnastics.
- The trigger (borrower default in the same epoch as a claimed instant withdrawal) is an honest-manager/honest-borrower event; the attacker merely needs receipts in the right epoch.
- No existing guard stops it: `_ensureDefaultRecoveryInitialized` only blocks while `pendingInstantWithdraws != 0` (unfunded remainder), `_transferFundedClaim` protects the reserve but says nothing about the per-epoch ledgers, and `instantWithdrawsRequests[_user] == 0` does not gate the default-epoch basis derived from `instantWithdrawClaimsByEpoch`.
- One caveat I could not fully verify within available iterations: the exact arithmetic in `finalizeDefault`/`finalizeDefaultRecovery` that consumes `instantWithdrawClaimsByEpoch` (whether it sizes `defaultRecoveryReserve` directly or feeds `defaultRecoveryPrice`). Either consumption mode yields fund impact (frozen reserve or diluted recovery price), but the PoC should assert the actual reserve/price deltas.

### Recommendation
In `claimInstantWithdrawRequest`, decrement the same per-epoch ledgers the request incremented, mirroring `_claimDefaultedInstantWithdrawRequest`:

```solidity
uint256 reqEpoch = lastWithdrawRequest[_user]; // or track the instant request epoch per user
instantWithdrawsRequestsByEpoch[_user][reqEpoch] -= amount;
instantWithdrawClaimsByEpoch[reqEpoch] -= amount;
```

(Store the request epoch — e.g., a `lastInstantWithdrawRequest[_user]` marker — since `lastWithdrawRequest` only tracks normal requests.) Alternatively, key default-epoch instant basis off `instantWithdrawsRequestsByEpoch` only when the aggregate `instantWithdrawsRequests[_user]` is nonzero, so a fully claimed receipt cannot re-enter recovery accounting.

### Proof of Concept
```solidity
// Foundry fork test (scaffold in test/foundry/IdleCreditVault.t.sol style)
function testClaimedInstantWithdrawStillCountsInDefaultEpoch() external {
    uint256 A = 1_000 * ONE_SCALE;

    _startEpochAndCheckPrices(0);
    uint256 epochN = strategy.epochNumber();

    // 1. KYC'd user requests + gets funded + claims instant withdraw in epoch N
    deal(address(underlying), address(this), A, true);
    // depositAA(A) then requestInstantWithdraw(A) via cdoEpoch, manager fulfills
    // via getInstantWithdrawFunds/collectInstantWithdrawFunds, then:
    cdoEpoch.claimInstantWithdrawRequest(); // user paid A at par
    assertEq(strategy.instantWithdrawsRequests(address(this)), 0);
    // BUG: per-epoch ledgers still count the paid receipt
    assertEq(strategy.instantWithdrawsRequestsByEpoch(address(this), epochN), A); // stale
    assertEq(strategy.instantWithdrawClaimsByEpoch(epochN), A);                   // stale

    // 2. Borrower defaults in epoch N; owner stops epoch defaulted, manager finalizes
    deal(address(underlying), borrower, 0, true);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(owner);
    cdoEpoch.stopEpoch(0, 0);                    // defaulted
    // manager funds recovery = honest claimants' basis only (excludes stale A)
    vm.startPrank(manager);
    underlying.approve(address(strategy), honestBasis);
    cdoEpoch.finalizeDefault(honestBasis, manager);
    vm.stopPrank();

    // 3a. If reserve was sized from instantWithdrawClaimsByEpoch[N]:
    //     -> either finalizeDefault reverted demanding A extra, or
    //     -> defaultRecoveryReserve contains A that is unclaimable:
    vm.expectRevert(); // underflow on instantWithdrawsRequests[_user] -= A
    cdoEpoch.claimInstantWithdrawRequest();
    // assertGt(strategy.defaultRecoveryReserve(), honestClaimsTotal); // pinned surplus A
}
```

Expected: `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` for epoch N return `A` after the funded claim, and post-finalization the reserve/basis retains `A` with no valid claim path, demonstrating frozen recovery funds (or diluted `defaultRecoveryPrice` harming honest claimants).
