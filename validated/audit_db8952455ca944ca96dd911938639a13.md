### Title
Withdrawal recipients cannot reroute payouts after underlying-token blacklisting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Matured withdrawal and instant-withdrawal receipts are address-bound and always pay the original `msg.sender`; if that address becomes blacklisted by the underlying asset, the payout transfer reverts and there is no safe way to redirect or transfer the claim. [1](#0-0) [2](#0-1) 

### Finding Description
`requestWithdraw` mints a strategy-token receipt to `_user` and records that address in `withdrawsRequests`, `withdrawsRequestsByEpoch`, and `lastWithdrawRequest`. [3](#0-2)  After the request matures, `IdleCDOEpochVariant.claimWithdrawRequest` forwards only `msg.sender`, with no recipient parameter. [4](#0-3)  `IdleCreditVault._claimFundedWithdrawRequest` clears the ledger and burns the receipt before `_transferFundedClaim` sends the underlying directly to `_user`. [5](#0-4)  Because the transfer happens in the same transaction, a blacklist-induced revert rolls back the burns and ledger clearing, but leaves the claimant permanently bound to the blocked address. [6](#0-5) 

The receipt cannot be reassigned to another address because `IdleCreditVault._transfer` rejects every transfer not initiated by `idleCDO`. [2](#0-1)  The instant-withdrawal path has the same fixed-recipient behavior: `_burn(_user, amount)` is followed by `_transferFundedClaim(_user, amount)`. [7](#0-6)  Default-recovery claims likewise send only to `_user` through `_transferDefaultRecovery`. [8](#0-7) 

An attacker can exploit this during the delay between request and claim by transferring stolen, sanctioned, or otherwise tainted underlyings to the claimant and triggering an asset-issuer compliance action against that address. A representative sequence is:

1. A KYC-approved lender requests 10,000 USDC through `requestWithdraw`.
2. The epoch stops normally and `collectWithdrawFunds` moves the funded USDC into `IdleCreditVault`. [9](#0-8) 
3. Before the lender calls `claimWithdrawRequest`, an attacker sends tainted USDC to the lender's address.
4. The USDC issuer blacklists that address while the funded claim remains outstanding.
5. Every `claimWithdrawRequest` call reverts at the USDC transfer, so the receipt remains outstanding but cannot pay out to a replacement address.

The owner-only `transferToken` rescue does not provide an accounting-safe remedy because moving the reserved underlying does not clear the claimant's ledger entries or burn their receipt, leaving an outstanding duplicate claim if the address is later unblacklisted. [10](#0-9) 

### Impact Explanation
The entire funded withdrawal, instant-withdrawal claim, or default-recovery entitlement can remain frozen indefinitely while the claimant is blacklisted. [1](#0-0)  In the example above, the victim loses access to 10,000 USDC even though the vault holds the funded payout and the withdrawal receipt remains recorded. [11](#0-10)  Existing epoch gating, reserve isolation, `_onlyIdleCDO`, and nontransferability do not mitigate this condition; the nontransferable receipt is what prevents recovery through a clean recipient. [12](#0-11) 

### Likelihood Explanation
Likelihood depends on the underlying having an issuer-controlled blacklist and on the issuer acting against an address after receiving tainted funds. Normal operation requires an extended window between request creation and claim, which already exists because funded requests cannot be claimed until the next epoch boundary. [13](#0-12)  Instant withdrawals reduce that timing window, but delayed-funded instant requests and default-recovery receipts can retain the same fixed-recipient exposure. [14](#0-13) 

### Recommendation
Allow the original claimant to redirect an unclaimed funded receipt to a fresh recipient, preferably by accepting a payout recipient on `claimWithdrawRequest` and `claimInstantWithdrawRequest` while keeping the accounting owner as `msg.sender`. [15](#0-14)  The redirected recipient should be validated against the same wallet-allowance policy as the claimant, and the same capability should be exposed for funded, loss-adjusted, defaulted, instant, and post-default claims. [16](#0-15)  Alternatively, add an explicit governance recovery path that atomically clears the user's receipt and pays an approved replacement address rather than using `transferToken` while the claim remains outstanding. [10](#0-9) 

### Proof of Concept
The following Foundry mainnet-fork test can be added to the existing `IdleCreditVault.t.sol` harness and models the issuer reaction after the attacker's tainted direct-token transfer:

```solidity
interface IFiatTokenBlacklist {
  function blacklister() external view returns (address);
  function blacklist(address account) external;
  function isBlacklisted(address account) external view returns (bool);
}

function testBlacklistedClaimantCannotRedirectMaturedWithdrawal() external {
  address victim = makeAddr('victim');
  address attacker = makeAddr('attacker');
  uint256 depositAmount = 10_000 * ONE_SCALE;

  _depositWithUser(victim, depositAmount, true);

  vm.prank(victim);
  uint256 claimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

  assertEq(
    IdleCreditVault(address(strategy)).withdrawsRequests(victim),
    claimBasis,
    'claim was not funded and recorded'
  );

  // The attacker taints the victim while the payout is awaiting claim.
  deal(address(underlying), attacker, 1);
  vm.prank(attacker);
  underlying.transfer(victim, 1);

  // Fork-only representation of the issuer's subsequent compliance action.
  IFiatTokenBlacklist fiat = IFiatTokenBlacklist(address(underlying));
  vm.prank(fiat.blacklister());
  fiat.blacklist(victim);
  assertTrue(fiat.isBlacklisted(victim));

  uint256 vaultBalanceBefore = underlying.balanceOf(address(strategy));

  vm.prank(victim);
  vm.expectRevert();
  cdoEpoch.claimWithdrawRequest();

  // The failed payout leaves the claim and receipt outstanding, but the user
  // has no call path that selects a clean payout recipient.
  assertEq(
    IdleCreditVault(address(strategy)).withdrawsRequests(victim),
    claimBasis,
    'failed payout unexpectedly cleared receipt accounting'
  );
  assertEq(
    IERC20Detailed(address(strategy)).balanceOf(victim),
    claimBasis,
    'receipt was unexpectedly burned'
  );
  assertEq(
    underlying.balanceOf(address(strategy)),
    vaultBalanceBefore,
    'funds unexpectedly left the vault'
  );

  // The user also cannot transfer the receipt to a clean beneficiary.
  address cleanRecipient = makeAddr('clean-recipient');
  vm.prank(victim);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  IERC20Detailed(address(strategy)).transfer(cleanRecipient, claimBasis);
}
```

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.

  /// @notice Claim an already-funded post-default withdraw request.
  /// @param _user address of the user
  /// @return amount amount claimed from default recovery reserve
  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }

  /// @notice Claim a defaulted normal withdraw receipt with the finalized recovery haircut.
  /// @param _user address of the user
  /// @return amount amount paid from default recovery reserve
  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  /// @notice Claim a stopEpochWithDuration loss-adjusted withdraw receipt.
  /// @param _user address of the user
  /// @return amount amount paid from funded strategy underlyings
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
