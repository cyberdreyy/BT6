### Title
Stale write-off requests can be fulfilled indefinitely, letting a fulfiller buy escrowed tranche tokens below their current NAV - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow` lets a tranche holder post an order: the user escrows `tranches` and names a fixed `underlyingsRequested` price. The design intent is that an unfilled order can be taken back at any time via `deleteWriteOffRequest`, i.e. a request that should no longer be executed is expected to be revoked. But `fullfillWriteOffRequest` has no expiry, no epoch-validity check, and no price sanity check: any EOA can fill a request arbitrarily many epochs later, after tranche NAV has appreciated far above the stale fixed price. The unprivileged fulfiller captures the difference between the stale ask and current `virtualPrice`, paid by the user.

### Finding Description
`createWriteOffRequest` requires `isEpochRunning()` and locks tranche tokens in the escrow at a user-chosen fixed underlying amount [1](#0-0) . Fulfillment checks only that the caller passes the exact tranche amount and at least the requested underlyings [2](#0-1) . There is:

- no deadline or TTL on the request,
- no check that the epoch in which the request was created is still running (fulfillment is permitted in buffer, stopped, defaulted or even closed state),
- no link between `underlyingsRequested` and current `virtualPrice`.

Tranche NAV grows each epoch because interest accrues into `tranchePrice`/`virtualPrice`. A request created at price ~1.0 becomes strictly profitable to a fulfiller after a few epochs of positive APR: the fulfiller pays `underlyingsRequested` (minus the 0.1% `exitFee` borne by the user), receives the escrowed tranche tokens, and can redeem them during the next buffer period through `requestWithdraw`/`claimWithdrawRequest` at the appreciated NAV. The user, who could not have anticipated NAV at fill time and whose revocation only works until the fill lands, receives the stale price minus the exit fee. This mirrors the external report exactly: the revocation guarantee ("I can always delete my request") is worthless once a counterparty can still process the stale request at the moment it becomes profitable, and the window in which the order is dangerous grows monotonically with time.

### Impact Explanation
Unprivileged attacker profit equals `tranches * (currentVirtualPrice - stalePrice) / 1e18 - fees`, directly extracted from the requesting user. For a 10,000e18 tranche request priced at 10,000 underlyings, ~5–10% NAV appreciation (a few epochs at typical APRs) yields hundreds to thousands of underlying units of theft per request. Since requests accumulate (`userRequests[msg.sender]` aggregates `tranches` and `underlyings`) and are never auto-expired, every forgotten request eventually becomes a free option for any fulfiller.

### Likelihood Explanation
High. Requests persist across epochs; tranche NAV only trends upward absent a default (and on default the attack simply isn't profitable, no cost to trying later if recovery occurs). The attacker is any EOA — no KYC, no tranche balance required beforehand. The only mitigation is the user actively monitoring and racing to call `deleteWriteOffRequest`, which is precisely the "user should have revoked" situation the analogous report flags as insufficient protection. Note `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw` confirms fulfillment is permissionless and available to non-KYC'd wallets [3](#0-2) .

### Recommendation
Add an expiry or validity window to `WriteOffRequest` (e.g. store the epoch/timestamp at creation and revert in `fullfillWriteOffRequest` if elapsed), and/or require `IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()` and bound `underlyingsRequested` relative to current tranche `virtualPrice` at fulfillment time so orders cannot be filled at prices divorced from NAV.

### Proof of Concept
Foundry fork test (same setup as `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, mainnet fork block 23032567):

```solidity
function testStaleWriteOffRequestSnipedAfterNavAppreciates() external {
    // LP posts a sell order: 10_000 AA tranches for 10_000 USDC (price ~1.0)
    vm.prank(LP);
    escrow.createWriteOffRequest(10_000e18, 10_000e6);

    // epochs pass; tranche NAV appreciates with accrued interest
    for (uint256 i; i < 3; ++i) {
        _startEpochAndCheckPrices(i);          // manager starts epoch
        _stopEpochAndCheckPrices(i, initialProvidedApr, _expectedFundsEndEpoch());
    }
    uint256 nav = cdoEpoch.virtualPrice(address(tranche));
    assertGt(nav, 1.02e6); // >2% appreciation

    // LP never deleted the request; any EOA fills it at the stale price
    address sniper = makeAddr("sniper");
    deal(address(underlying), sniper, 10_000e6);
    uint256 lpBalPre = underlying.balanceOf(LP);
    vm.startPrank(sniper);
    underlying.approve(address(escrow), 10_000e6);
    escrow.fullfillWriteOffRequest(LP, 10_000e18, 10_000e6);
    vm.stopPrank();

    // Sniper's tranches are worth nav * tranches / 1e18 > amount paid
    uint256 sniperValue = 10_000e18 * nav / 1e18;
    assertGt(sniperValue, 10_000e6);           // profit = appreciation minus nothing
    // LP received only the stale price minus exitFee
    assertEq(underlying.balanceOf(LP) - lpBalPre, 10_000e6 - (10_000e6 * 100 / 100_000));
}
```

The helpers `_startEpochAndCheckPrices` / `_stopEpochAndCheckPrices` and `LP` already exist in the escrow test harness; `deal` funds the arbitrary `sniper` EOA, satisfying the unprivileged-attacker requirement.

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }
```

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];
```
