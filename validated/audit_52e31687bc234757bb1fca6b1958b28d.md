Based on my investigation, here's the analysis:

`BridgeResource` (in `core/web/presenters/bridges.go`) has two secret-like fields: `IncomingToken` (tagged `omitempty`, and only populated manually in `BridgeTypesController.Create` from the ephemeral `bta.IncomingToken` returned by `bridges.NewBridgeType`, never persisted/read back from the DB via `NewBridgeResource`) and `OutgoingToken` (tagged plain `json:"outgoingToken"`, always populated from the persisted `bridges.BridgeType` via `NewBridgeResource`) [1](#0-0) [2](#0-1) .

`BridgeTypesController.Show` calls `presenters.NewBridgeResource(bt)` directly on the ORM-fetched bridge and returns it without any redaction, meaning `OutgoingToken` (the credential used by the node to authenticate to the external adapter) is included in the response [3](#0-2) . `IncomingToken`, however, is not leaked via `Show` because it's never populated from persisted data by `NewBridgeResource` — it's only set in `Create`'s in-memory response object from the transient bridge-type-authentication value [4](#0-3) .

I was unable to fully confirm the exact role-gating on the `/v2/bridge_types/:BridgeName` GET route in `core/web/router.go` within the remaining budget — the grep matched lines in that file but I could not read the surrounding route-group/middleware structure (e.g., which `authenticatedRoutes.Use(...)` group wraps `Show` vs. `Create/Update/Destroy`) to confirm whether `Show` is behind only session/token auth (any role) rather than `auth.RequiresEditRole`. Given the audit prompt's premise, if `Show` is indeed reachable by any authenticated role (not gated by `RequiresEditRole`), then a low-privileged/view-role authenticated user can retrieve another bridge's `OutgoingToken` via `GET /v2/bridge_types/{name}`.

### Title
Bridge `OutgoingToken` credential disclosed to any authenticated user via `BridgeTypesController.Show` - (File: core/web/bridge_types_controller.go)

### Summary
`BridgeTypesController.Show` returns a `presenters.BridgeResource` built directly from the persisted bridge record without redacting `OutgoingToken`, and this field lacks `omitempty`/masking, unlike `IncomingToken` which is never populated from stored data on this path.

### Finding Description
`Show` (`core/web/bridge_types_controller.go:125-146`) fetches the bridge type by name from `BridgeORM().FindBridge` and serializes it with `presenters.NewBridgeResource(bt)`, which unconditionally copies `b.OutgoingToken` into the response JSON (`core/web/presenters/bridges.go:37`). There is no role check or field-level redaction inside `Show` itself; any authorization must come purely from route-level middleware in `core/web/router.go`. If that route is registered only under generic session/authentication requirements (rather than `auth.RequiresEditRole`, which is documented to gate `Create/Update/Destroy`), any authenticated principal — including a view-only role — can call `GET /v2/bridge_types/{name}` and receive the bridge's outgoing credential in the response body.

### Impact Explanation
Disclosure of `OutgoingToken` allows an unprivileged authenticated user to impersonate the node when calling the external adapter/bridge endpoint that expects that token, potentially triggering unauthorized external-adapter actions or pivoting to further compromise depending on what the token grants. This matches the "sensitive credential disclosure" bounty impact class.

### Likelihood Explanation
If confirmed, this requires only a valid session/API token with the lowest role (view/run) — no special preconditions — and is trivially repeatable via a single GET request per bridge name.

### Recommendation
Add `omitempty`-style redaction or strip `OutgoingToken` (and any other bridge secret) from the `Show`/`Index` response paths, and/or gate the `Show` route behind `auth.RequiresEditRole` (or a stricter role) in `core/web/router.go` so that only privileged users can retrieve bridge credentials.

### Proof of Concept
1. In `core/web/bridge_types_controller_test.go`, create a bridge as an admin/edit-role user (populating `OutgoingToken`).
2. Authenticate a client fixture using a view/run-role session (see helpers in `core/internal/cltest/cltest.go` for role-scoped test clients).
3. Issue `GET /v2/bridge_types/{name}` with that low-privilege client.
4. Assert the HTTP status is `200` and decode the JSON body; assert failure if `data.attributes.outgoingToken` is non-empty, or assert the request should have been rejected with `401/403` if role gating is intended.
5. Cross-check against `core/web/router.go`'s route registration for `bridge_types/:BridgeName` GET to confirm which middleware group it belongs to, since this determines whether the vulnerability is real or already mitigated by an existing role gate not captured in this analysis.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
