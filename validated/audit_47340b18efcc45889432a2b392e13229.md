### Title
Unrestricted `GET /v2/bridge_types/:BridgeName` route leaks bridge `OutgoingToken` to any authenticated non-edit-role user - ([File: core/web/router.go], [File: core/web/bridge_types_controller.go], [File: core/web/presenters/bridges.go])

### Summary
The `bridge_types/:BridgeName` GET route is registered without any role wrapper (`auth.RequiresEditRole`/`auth.RequiresRunRole`), unlike the sibling `POST`/`PATCH`/`DELETE` routes for the same resource. The `Show` handler serializes the bridge via `presenters.NewBridgeResource`, which unconditionally includes the bridge's `OutgoingToken` (the secret token the Chainlink node uses to authenticate itself to the external adapter) in the JSON response, exposing it to any authenticated session/token holder regardless of role.

### Finding Description
In `core/web/router.go`, the bridge-type routes are defined as: [1](#0-0) 
`Index`, `Show` on `authv2` group only requires generic authentication (`auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)`), while `Create`, `Update`, `Destroy` are wrapped with `auth.RequiresEditRole`.

`BridgeTypesController.Show` fetches the bridge and returns it via `presenters.NewBridgeResource(bt)` with no field filtering based on caller role: [2](#0-1) 

`presenters.NewBridgeResource` copies `b.OutgoingToken` directly into the response resource, and the field lacks `omitempty`, so it's always emitted in the JSON payload: [3](#0-2) 

Any authenticated user reaching this endpoint — including a view-role session, a run-role session, or an EI (external-initiator) credential forced into run role via `auth.AuthenticateByToken` — can call `GET /v2/bridge_types/<name>` and receive the bridge's `Confirmations` and `OutgoingToken` in the response, since no edit-role check exists to block them.

Regarding `IncomingToken`: the `Show` handler builds the resource from `bridges.BridgeType` (`bt`, from `FindBridge`), not from a `BridgeTypeAuthentication`/`BridgeTypeRequest` object that carries the plaintext `IncomingToken` — that field is only populated in `Create` (`resource.IncomingToken = bta.IncomingToken`, see `core/web/bridge_types_controller.go` lines 98-99). Because `BridgeResource.IncomingToken` has `omitempty` and is never set in `Show`, the plaintext `IncomingToken` is **not** exposed by this endpoint — only `OutgoingToken` and `Confirmations` are.

### Impact Explanation
Disclosure of a bridge's `OutgoingToken` allows an unprivileged, non-edit-role authenticated party (view-role user, run-role user, or an EI credential holder) to impersonate the Chainlink node when calling the external adapter that the bridge fronts, since that token is the credential the node presents to authenticate outbound requests to the adapter. This matches the "secret/credential disclosure enabling request impersonation" bounty impact class, scoped to the specific external adapter bridge rather than node-wide compromise.

### Likelihood Explanation
Exploitation requires only a valid authenticated session or API token with any role (view or run) — no edit/admin privilege is needed, and no misconfiguration is required beyond the default routing table. The request is a single unauthenticated-relative-to-role `GET /v2/bridge_types/:BridgeName` call, fully repeatable and deterministic for any bridge name known to the caller (bridge names are also enumerable via the unrestricted `GET /v2/bridge_types` index route).

### Recommendation
Wrap the `Show` route with `auth.RequiresEditRole` (or introduce field-level redaction so `OutgoingToken`/`Confirmations` are only serialized for edit/admin roles), consistent with `Create`, `Update`, and `Destroy`. Alternatively, have `presenters.NewBridgeResource` accept the caller's role and omit `OutgoingToken` unless the caller has edit privileges.

### Proof of Concept
Go handler-level test plan (extending `TestBridgeController_Show` in `core/web/bridge_types_controller_test.go`):
1. Create an application (`cltest.NewApplication`) and a bridge via `app.BridgeORM().CreateBridgeType` with a known `OutgoingToken`.
2. Create an HTTP client authenticated with a **view-role** user session (`app.NewHTTPClient(cltest.APIEmailAdmin)` replaced with a view-role fixture, or a run-role EI token) instead of the default admin client.
3. Call `client.Get("/v2/bridge_types/" + bt.Name.String())`.
4. Assert `resp.StatusCode == http.StatusOK` (no role check blocks it) and parse the JSONAPI response into `presenters.BridgeResource`.
5. Assert `resource.OutgoingToken == bt.OutgoingToken` is non-empty and matches the stored secret — demonstrating the secret is returned to a non-edit-role caller.
6. Assert `resource.IncomingToken == ""` to confirm only `OutgoingToken`/`Confirmations` (not the plaintext `IncomingToken`) leak via this path.

```go
// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```
