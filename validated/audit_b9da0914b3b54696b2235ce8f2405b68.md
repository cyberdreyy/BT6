## Analysis



### Title
Unvalidated `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permits permanent freezing of migrated funds - (File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs)

### Summary
The `TransferToNewAccount` and `TransferToNewAccountPda` account structs accept `new_authority` as a fully unchecked `UncheckedAccount`, and its key is written directly into the newly created `MarginfiAccount.authority` field with no validation that it is non-zero. If `new_authority` is `Pubkey::default()`, the new account becomes permanently unusable while the old account's lending position has already been zeroed and disabled, causing a durable freeze of the user's funds.

### Finding Description
`transfer_to_new_account` and `transfer_to_new_account_pda` both take `new_authority: UncheckedAccount<'info>` with the comment `/// CHECK: WARN: New authority is completely unchecked`. [1](#0-0) 

The handler unconditionally assigns `ctx.accounts.new_authority.key()` as the new account's `authority` via `initialize_migrated_account`, with no check that it is non-default: [2](#0-1) [3](#0-2) 

In the same transaction, the old account's lending position is wiped and the account is permanently disabled before the new account's authority is even validated: [4](#0-3) 

`is_signer_authorized`, used as the access-control gate on `old_marginfi_account`, only accepts the account's `authority` field being matched against a real transaction `Signer`: [5](#0-4) 

Since `Pubkey::default()` (the all-zero key) has no corresponding private key, no wallet can ever sign as that authority. Once `new_authority` is set to zero, every subsequent instruction gated by `is_signer_authorized` (deposit, withdraw, borrow, repay, close, further transfers, emissions destination changes, etc.) on the new account becomes permanently unreachable — exactly the "blocked essential functions" bug class described in the report, except here the consequence is a durable freeze of the user's migrated collateral/liabilities rather than a mere admin inconvenience.

### Impact Explanation
Because the old account's `lending_account` is zeroed and the account is flagged `ACCOUNT_DISABLED` in the same transaction that creates the new account, the migration is irreversible. If `new_authority` resolves to the zero address (accidentally via a buggy integrator/front-end, or maliciously via a crafted transaction that a user is induced to sign, e.g. through a compromised or malicious third-party integrator using the CPI path gated by `third_party_id`), the user's entire position becomes permanently inaccessible: no key exists to satisfy `marginfi_account.authority == signer`, and the frozen-account admin-only bypass in `is_signer_authorized` does not apply here since the account isn't marked frozen. This is a durable, financial-impact freeze of user funds, directly analogous to the reported bug's "essential functions blocked" pattern.

### Likelihood Explanation
Exploitation/triggering requires either integrator error (a dapp passing an uninitialized/default account as `new_authority`) or a malicious integrator crafting a transaction that the account authority signs without noticing the `new_authority` field is the zero key — plausible given the instruction explicitly documents `new_authority` as "completely unchecked" and the CPI path (`transfer_to_new_account_pda` with `third_party_id`) is designed to be invoked by third-party integrator programs. There is no on-chain safeguard preventing this outcome.

### Recommendation
Add an explicit non-default check on `new_authority` (and reject `Pubkey::default()`) before finalizing the migration in both `transfer_to_new_account` and `transfer_to_new_account_pda`, e.g.:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::Unauthorized // or a new dedicated error
);
```
This should be enforced prior to zeroing/disabling the old account so that a bad `new_authority` value fails the whole transaction atomically rather than leaving funds stranded.

### Proof of Concept
1. User (or a dapp on the user's behalf) creates and signs a `transfer_to_new_account_pda` transaction with `authority` = user's real keypair, but `new_authority` = `Pubkey::default()` (e.g., due to a bug in front-end account derivation, or maliciously constructed by a third-party integrator using the allowed CPI path).
2. Transaction executes: `old_account.migrated_to` is set, `old_account.lending_account` zeroed, `ACCOUNT_DISABLED` flag set [6](#0-5) ; `new_account.authority` is set to `Pubkey::default()` [7](#0-6) .
3. Any subsequent attempt to withdraw/borrow/repay/close on `new_account` fails permanently because no signer can ever satisfy `marginfi_account.authority == signer` for the zero pubkey [8](#0-7) , and the old account is already disabled and empty, so the user's collateral/liabilities are unrecoverable.

```rust
pub fn is_signer_authorized(
    marginfi_account: &MarginfiAccount,
    group_admin: Pubkey,
    signer: Pubkey,
    allow_receivership: bool,
    allow_order_execution: bool,
) -> bool {
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer; // forbidden to take receivership of your own account
    }

    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }

    marginfi_account.authority == signer
}
```
