### Title
Un-persisted, non-gossiped `tx_replay_scope` causes a signer to silently drop transaction-replay enforcement after a restart, letting it approve non-canonical blocks other signers reject - ([File: stacks-signer/src/v0/signer_state.rs])

### Summary
The tx-replay mechanism, like the ZK-chain's dual "priority queue / priority tree" design in the external report, tracks the same logical fact (which transactions must be replayed after a Bitcoin fork) in two places that are supposed to stay in lock-step: the gossiped/consensus-visible `tx_replay_set` (part of `SignerStateMachine`, propagated via `StateMachineUpdate` and persisted through `signer_states`) and the purely local, in-process `tx_replay_scope: ReplayScopeOpt` field on `Signer` [1](#0-0) . Exactly like the GW→L1 case where only the priority tree's `startIndex`/commitment migrates while the priority queue's `firstUnprocessedPriorityTx` does not, here only `tx_replay_set` can be recovered/derived after a "context switch" (a signer process restart), while `tx_replay_scope` is explicitly never persisted.

### Finding Description
`ReplayState::infer_state` documents the coupling and its failure mode directly in the code: [2](#0-1) 

If `replay_set` (the gossip/consensus-derived component) is non-empty but `scope_opt` (the local-only component) is `None`, `infer_state` returns `None`, and the comment explicitly states the cause: *"Possibly caused by the scope being a local state in the Signer struct, which is not persisted."*

`Signer::new` always initializes `tx_replay_scope: None` on process start/restart [3](#0-2) , regardless of whatever `tx_replay_set` is later reconstructed into `LocalStateMachine` from signer DB/gossip via `LocalStateMachine::new`. This is the exact analog of the report's flaw: one data structure (`tx_replay_set`, akin to the priority tree that gets its state transferred/reconstructed) survives the "migration" (restart), while the other (`tx_replay_scope`, akin to the priority queue's `firstUnprocessedPriorityTx` that is never transferred) does not.

In `bitcoin_block_arrival`, when a new burn block is expected and the prior state machine still carries a non-empty `tx_replay_set` (e.g., recovered from a prior gossiped `StateMachineUpdate` seen right before restart, or from another signer's broadcasted state being adopted via `capitulate_miner_view`), but the freshly-restarted signer's local `tx_replay_scope` is `None`: [4](#0-3) 

the call errors with `SignerChainstateError::LocalStateMachineNotReady`. Because `self` was already replaced with `Self::Uninitialized` at the top of the function before this early return [5](#0-4) , and no reset happens before the `return Err(...)`, the local state machine is left `Uninitialized` for that iteration.

On the next call, `prior_state_machine` is regenerated from `Self::place_holder`, which effectively re-derives a fresh state (empty `tx_replay_set`), so `infer_state` no longer errors - but this "recovery" is a silent loss of the replay obligation, not a correct resumption of it. The signer proceeds with `ReplayState::Unset` even though the tx-replay set/scope was genuinely still in progress network-wide. Other signers who did not restart still enforce `validate_with_replay_tx` and the strict in-order replay check in `postblock_proposal.rs`'s `validate_replay` (see `ValidateRejectCode::InvalidTransactionReplay` cases) [6](#0-5) . A restarted signer, having dropped its scope, evaluates block proposals via `check_block_against_local_state` using `self.global_state_evaluator.get_global_tx_replay_set()` [7](#0-6) , but its own `LocalStateMachine`/`capitulate_viewpoint` logic can diverge from the group's replay tracking because its local `tx_replay_scope` (needed to correctly recompute the replay set on subsequent forks via `handle_fork_on_in_progress_replay`/`compute_forked_txs_set_in_same_cycle`) is gone. This breaks the equality between "what this signer believes must be replayed" and "what the rest of the signer set/node enforces," which is precisely the accepted class: a signer capable of signing (or wrongly rejecting/accepting) a block that is non-canonical relative to the correct replay requirement.

### Impact Explanation
This maps to the "Critical" bucket: a signer can end up approving (locally accepting/signing) a block proposal that omits mandatory replay transactions that the rest of the honest signer set still requires, because its local `tx_replay_scope`/`tx_replay_set` view has silently reset to `Unset` after a restart during an in-progress replay window. Equivalently, it can produce a `LocalStateMachineNotReady` failure that stalls that signer's local state machine update for a cycle (minor liveness impact), but the more serious consequence is the quiet divergence from the correct replay obligation once the placeholder state resets it to `Unset` - i.e., the signer's local acceptance criteria for a block no longer matches the canonical/consensus-expected replay content, mirroring the report's "double spending via re-executed/omitted required operations" theme.

### Likelihood Explanation
Requires: (1) a Bitcoin fork that puts the signer set into an in-progress tx-replay window (`ReplayState::InProgress`), and (2) a restart of a single signer process during that window (deployment restarts, crashes, upgrades) before the replay window closes. This does not require a majority of signers or any key compromise - a single signer's ordinary restart during a fork-driven replay window is sufficient to trigger the divergence, which is a realistic operational scenario, especially since `tx_replay_scope` is explicitly called out in the code as unpersisted local state.

### Recommendation
Persist `tx_replay_scope` (or reconstruct it deterministically from the same DB inputs used to build `tx_replay_set`) across restarts in `SignerDb`, or derive `tx_replay_scope` from the persisted `fork_origin`/`past_tip` info directly rather than only relying on process-local memory, so that `ReplayState::infer_state` never has to guess and lose obligations on restart. Alternatively, when `infer_state` returns `None` because scope is missing but set is non-empty, the signer should not silently fall back to `Unset` on the next cycle; it should attempt to reconstruct `ReplayScope` from historical burn-block data in `SignerDb` (fork origin/past tip) before treating the replay obligation as cleared.

### Proof of Concept
1. Configure `validate_with_replay_tx = true` and trigger a Bitcoin fork so the signer set enters `ReplayState::InProgress(tx_replay_set, scope)` per `handle_fork_for_new_replay` [8](#0-7) .
2. Restart one signer process while the replay window is still open (before `reset_replay_set_after_fork_blocks` elapses). On restart, `Signer::new` sets `tx_replay_scope: None` [3](#0-2)  while `LocalStateMachine::new` may still recover a non-empty `tx_replay_set` (e.g., via gossip-derived global state or DB-backed `signer_state_machine_updates`).
3. On the next `bitcoin_block_arrival` call, `ReplayState::infer_state(&tx_replay_set, &tx_replay_scope)` returns `None` because `tx_replay_set` is non-empty and `tx_replay_scope` is `None`, producing `Err(SignerChainstateError::LocalStateMachineNotReady)` and leaving `self` as `Uninitialized` [9](#0-8) .
4. On the following call, `Self::place_holder` reinitializes the state machine with an empty replay set, so the restarted signer now believes `ReplayState::Unset` even though the group replay window is still active - diverging from other signers still correctly enforcing `validate_with_replay_tx` against `ValidateRejectCode::InvalidTransactionReplay` in `postblock_proposal.rs`.

Note: I was unable to fully trace every downstream code path that consumes the restarted signer's now-cleared local replay state to confirm whether it can actually cast a differing consensus-relevant vote (accept vs. reject) versus just losing the “failsafe”/timeout bookkeeping - this would require deeper analysis of `capitulate_viewpoint`, `check_block_against_local_state`, and `get_global_tx_replay_set` interplay across multiple signers that the index/documents available here do not fully expose.

    /// Infers the appropriate `ReplayState` based on the contents of the replay transaction set
    /// and the optional scope.
    ///
    /// # Arguments
    ///
    /// * `replay_set` - A reference to a set of transactions intended for replay.
    /// * `scope_opt` - An optional scope defining the boundaries or context for the replay.
    ///
    /// # Returns
    ///
    /// * `Some(ReplayState::Unset)` if the `replay_set` is empty.
    /// * `Some(ReplayState::InProgress)` if the `replay_set` is non-empty and a `scope` is provided.
    /// * `None` if the `replay_set` is non-empty but no `scope` is provided.
    ///   - Possibly caused by the scope being a local state in the `Signer` struct, which is not persisted.
    fn infer_state(replay_set: &ReplayTransactionSet, scope_opt: &ReplayScopeOpt) -> Option<Self> {
        if replay_set.is_empty() {
            return Some(Self::Unset);
        }

        scope_opt
            .as_ref()
            .map(|scope| Self::InProgress(replay_set.clone(), scope.clone()))
    }
