### Title
Loss-adjusted withdrawal haircut bypassed via epoch-key mismatch between `lastWithdrawRequest` and `lossRecoveryPriceByEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the Gitea PKCE flaw — where the S256 challenge method was not persisted at authorization time so the verifier check at token exchange silently no-ops — `IdleCreditVault` records withdraw receipts under the epoch number at *request* time (`lastWithdrawRequest[_user]`, `withdrawsRequestsByEpoch[_user][currentEpoch]`) but records the loss haircut under the epoch number at *collection* time (`lossRecoveryPriceByEpoch[epochNumber]` inside `collectWithdrawFunds`). Since `epochNumber` is incremented at `stopEpoch` (per the comment at `IdleCreditVault.sol:322-323` and the test assertion `strategy.epochNumber() == claimEpoch` after `stopEpoch`), a loss price written during `stopEpoch` is keyed to the *new* epoch N+1 while every affected receipt still points at the request epoch N. `_claimLossAdjustedWithdrawRequest` then reads `lossRecoveryPriceByEpoch[N] == 0` and returns 0, so the claim falls through to `_claimFundedWithdrawRequest` and pays the full un-haircut basis from a reserve that was only funded with the post-loss amount.

### Finding Description
- `requestWithdraw` persists the receipt epoch as `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` while epoch N is running (`IdleCreditVault.sol:282-293`).
- On `stopEpochWithDuration(_lossAmount)`, the CDO calls `collectWithdrawFunds(pendingToFund)` which, when `_amount < pendingBasis`, writes `lossRecoveryPriceByEpoch[epochNumber]` (`IdleCreditVault.sol:411-421`). If `epochNumber` has already been incremented inside the same `stopEpoch` flow (the documented behavior: "Epoch number is increased at stopEpoch"), the haircut is stored under N+1.
- At claim time, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns early without burning or clearing anything (`IdleCreditVault.sol:789-795`). `_claimFundedWithdrawRequest` then passes its gate (`epochNumber (N+1) > lastWithdrawRequest (N)`), burns the receipt, and transfers the full `normalAmount` at par (`IdleCreditVault.sol:326-349`).
- The "persisted-key mismatch" also disables the protective revert at `IdleCreditVault.sol:263-271`, so users can stack further requests while their loss-adjusted receipt is invisible to the guard.

### Impact Explanation
All receipts of the loss epoch claim 100% of their basis even though the vault only received `pendingToFund < pendingBasis` underlying. Early claimants drain the funded reserve at par; later claimants (or other funded claims) revert on transfer — i.e., direct theft of the shortfall plus insolvency equal to the applied `pendingLoss` share of `_lossAmount`. In the fork test the full `pendingBasis` is claimed while only `pendingBasis - pendingLoss` was collected.

### Likelihood Explanation
Requires only an unprivileged tranche holder calling `requestWithdraw` during a running epoch that ends in `stopEpochWithDuration` with a nonzero loss — a normal, expected code path (honest manager/borrower sequence). No attacker control over privileged roles is needed. The sole precondition is that `epochNumber` is incremented before `collectWithdrawFunds` executes within `stopEpoch`; if the implementation instead increments after collection, the keys match and this does not trigger — this ordering could not be fully confirmed from the indexed sources and is the one assumption the PoC verifies.

### Recommendation
Key the loss price by the epoch that the pending receipts were recorded under — e.g., store a `pendingWithdrawsEpoch` when requests accumulate and write `lossRecoveryPriceByEpoch[pendingWithdrawsEpoch]`, or capture `epochNumber` at request time into a dedicated `lastLossEpoch` and have `_claimLossAdjustedWithdrawRequest` look up the haircut by the receipt's own epoch mapping rather than `lastWithdrawRequest`. Alternatively, snapshot `epochNumber` at the start of `stopEpoch` before incrementing and pass it to `collectWithdrawFunds`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

/// Fork test against deployed IdleCDOEpochVariant + IdleCreditVault.
contract LossEpochKeyMismatchPoC is Test {
    // addresses wired to the deployed CDO epoch variant, credit vault, underlying
    function testLossHaircutBypassedByEpochKey() public {
        // 1. USER (unprivileged AA holder) requests full withdraw during running epoch N
        //    requestWithdraw persists lastWithdrawRequest[USER] = N,
        //    withdrawsRequestsByEpoch[USER][N] = amount
        vm.prank(USER);
        cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));

        // 2. Honest manager stops epoch N with a realized loss.
        //    stopEpoch increments strategy.epochNumber() to N+1, then the CDO
        //    calls collectWithdrawFunds(pendingToFund) which writes
        //    lossRecoveryPriceByEpoch[N+1] = price < 1e18
        uint256 loss = 500 * ONE_SCALE;
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, loss);

        // Assert the mismatch: haircut stored under N+1, receipt keyed under N
        uint256 reqEpoch = strategy.lastWithdrawRequest(USER);
        assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);        // haircut invisible
        assertGt(strategy.lossRecoveryPriceByEpoch(reqEpoch + 1), 0);    // haircut stored one epoch late

        // 3. USER claims: _claimLossAdjustedWithdrawRequest returns 0,
        //    _claimFundedWithdrawRequest pays FULL basis at par.
        uint256 balPre = underlying.balanceOf(USER);
        uint256 vaultBalPre = underlying.balanceOf(address(strategy));
        vm.prank(USER);
        cdoEpoch.claimWithdrawRequest();
        uint256 paid = underlying.balanceOf(USER) - balPre;

        // Paid the full un-haircut basis even though vault was only funded
        // pendingBasis * lossRecoveryPrice / 1e18 -> reserve drained / insolvent
        assertEq(paid, strategyFullBasis(USER));
        assertLt(vaultBalPre - paid + paid /*other claims now underfunded*/, vaultBalPre);
    }
}
```

The PoC hinges on one unverified detail: whether `epochNumber` is incremented before `collectWithdrawFunds` is invoked inside `stopEpoch`. The indexed code supports this reading (requests record the pre-stop epoch, `collectWithdrawFunds` reads live `epochNumber`, and tests show `epochNumber` already incremented immediately after `stopEpoch` returns), but the exact call ordering inside `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration` was not fully indexed; if the increment occurs after fund collection, the keys coincide and this finding collapses.
