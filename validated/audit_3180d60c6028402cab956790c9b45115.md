### Title
Stale `deposit_amount` during `withdraw_from_staking_pool` async window lets the owner double-count withdrawn NEAR and release locked/unvested tokens early - (File: `lockup/src/owner_callbacks.rs`, `lockup/src/getters.rs`)

### Summary
`get_owners_balance()`/`get_liquid_owners_balance()` compute liquidity as `account_balance() + known_deposited_balance() - locked_amount()`, but `known_deposited_balance()` (`staking_information.deposit_amount`) is only decremented in the `on_staking_pool_withdraw` callback, after the actual NEAR transfer from the staking pool has already landed on the lockup account and inflated `account_balance()`. In the interval between the transfer arriving and the callback firing, the same withdrawn NEAR is counted both as "still deposited in the pool" and as "already in the account," inflating `get_owners_balance()` by the withdrawn amount and defeating the `locked_amount` subtraction that is supposed to keep locked/unvested tokens untransferable.

### Finding Description
The binding that should hold at all times is:
`get_balance() == env::account_balance() + staking_information.deposit_amount.0` should represent the *true, non-duplicated* total of (funds physically in the account) + (funds still on the pool), with no NEAR counted twice.

Trace:
- `withdraw_from_staking_pool` (`lockup/src/owner.rs:216-252`) fires `ext_staking_pool::withdraw(amount, ...)` and chains `.then(ext_self_owner::on_staking_pool_withdraw(amount, ...))`. It does **not** touch `deposit_amount` itself.
- On the staking-pool side, `internal_withdraw` (`staking-pool/src/internal.rs:42-68`) immediately does `Promise::new(account_id).transfer(amount); self.last_total_balance -= amount;` — i.e., the real NEAR transfer to the lockup account is dispatched as soon as `withdraw` executes.
- Only in the callback `on_staking_pool_withdraw` (`lockup/src/owner_callbacks.rs:105-145`) does the lockup contract do `staking_information.deposit_amount.0 = deposit_amount.0.saturating_sub(amount.0)`.
- `get_known_deposited_balance()` (`lockup/src/getters.rs:24-30`) reads `staking_information.deposit_amount` directly, and `get_balance()` / `get_owners_balance()` / `get_liquid_owners_balance()` (`lockup/src/getters.rs:163-178`) combine it with `env::account_balance()`.

The contract's own unit test `test_staking_pool_owner_balance` (`lockup/src/lib.rs:967-998`) explicitly models this: after calling `withdraw_from_staking_pool(amount)`, the test bumps `context.account_balance += amount` to simulate the real transfer landing, and only afterwards calls `contract.on_staking_pool_withdraw(amount)` to decrement `get_known_deposited_balance()`. Between those two steps, `get_owners_balance()` and `get_liquid_owners_balance()` are not asserted — but if evaluated in that window they would reflect `account_balance (already +amount)` + `deposit_amount (not yet -amount)`, i.e. `amount` counted twice.

Because `get_owners_balance()` also feeds `get_locked_amount()`'s subtraction (via `get_owners_balance = total - locked_amount`), the extra phantom `amount` cancels out part or all of the deduction the vesting/lockup schedule is supposed to enforce. If this window is hit precisely when `get_unvested_amount` transitions across `vesting_schedule.cliff_timestamp` (still fully locked, `unvested_amount == lockup_amount`, so `locked_amount == lockup_amount`), the double-counted `amount` from the pool withdrawal directly offsets the locked-amount subtraction, inflating `get_liquid_owners_balance()` (`getters.rs:176-178`, `min(owners_balance, account_balance())`) up to the real, physically-held `account_balance()` — i.e., the `min()` cap stops protecting anything because `owners_balance` itself is now artificially ≥ `account_balance()`.

The owner (attacker, who is the unprivileged creator/owner of their own lockup via the open `LockupFactory::create`) can then call `transfer(amount, receiver_id)` (`lockup/src/owner.rs:467-487`) or `add_full_access_key` (`lockup/src/owner.rs:502-514`, gated only by `get_locked_amount().0 == 0`) while the phantom double-count is in effect, moving/unlocking NEAR that the vesting schedule — set up by the NEAR Foundation as grantor — says should still be locked.

None of the existing guards catch this: `assert_owner` only checks predecessor is the owner (true here — the owner is the attacker of their own contract), `assert_no_staking_or_idle`/`assert_staking_pool_is_idle` check `staking_information.status`, which is `Busy` only while the withdraw promise is in flight and set back to `Idle` inside the very callback that is racing — it does not protect the window between the external transfer landing and that callback executing. `assert_self()` protects the callback from being called by anyone but the contract itself, but does nothing about receipt-ordering/staleness. There is no invariant check anywhere that reconciles `account_balance()` against `deposit_amount` before allowing `transfer`/`add_full_access_key`.

### Impact Explanation
This lets the lockup owner extract NEAR that is still legally locked/unvested according to the vesting schedule set by the grantor (NEAR Foundation) — i.e., NEAR leaves the lockup account (via `transfer`) or the account becomes fully owner-controlled (via `add_full_access_key`) before the entitled party (the grantor / future rightful claim, or in a termination scenario the foundation's clawback right) authorized it. This matches the stated Critical impact category: "locked or unvested tokens released early." The blast radius is bounded by whatever amount is mid-flight through `withdraw_from_staking_pool` at the time (which the owner fully controls — they choose the `amount` to withdraw), and is repeatable across withdrawal cycles and across every lockup contract instance an attacker creates for themselves.

### Likelihood Explanation
Preconditions: attacker must be the owner of a lockup contract with an active vesting schedule and a selected staking pool with unstaked funds ready to withdraw (fully attacker-controlled state, achievable by anyone who creates their own lockup and delegates/unstakes/waits epochs on a pool they also control). The attacker must land a `transfer`/`add_full_access_key` call inside the async gap between the pool's outgoing NEAR transfer landing on the lockup account and the `on_staking_pool_withdraw` callback executing. Whether this window is practically exploitable depends on NEAR receipt-scheduling/ordering behavior for sibling receipts generated from the same promise chain (the transfer sub-receipt from the pool and the `.then()` callback receipt are both scheduled to fire off the completion of the same `withdraw()` call and typically land in the same target block) — this is a protocol-level timing detail this analysis could not fully verify without a live/near-workspaces multi-block simulation, so exploitability in production is uncertain even though the state-level double-counting defect in the contract's own accounting model is real and demonstrable in a unit test.

### Recommendation
Do not read `env::account_balance()` optimistically as if a withdrawal has already been reconciled. Either (a) decrement `deposit_amount` synchronously at call time (in `withdraw_from_staking_pool`) and only roll it back on failure in the callback, so the pool-side accounting is always conservative, or (b) block `transfer`/`add_full_access_key`/further owner balance-changing calls while any staking-pool operation is `Busy` in a way that also covers the async transfer-landing window, e.g. by tracking a separate "pending withdrawal" amount that is excluded from `get_owners_balance()` until the callback confirms it, instead of relying solely on `TransactionStatus::Busy`/`Idle` toggled inside the same racing callback.

    pub fn on_staking_pool_withdraw(&mut self, amount: WrappedBalance) -> bool {
        assert_self();

        let withdraw_succeeded = is_promise_success();
        self.set_staking_pool_status(TransactionStatus::Idle);

        if withdraw_succeeded {
            {
                let staking_information = self.staking_information.as_mut().unwrap();
                // Due to staking rewards the deposit amount can become negative.
                staking_information.deposit_amount.0 = staking_information
                    .deposit_amount
                    .0
                    .saturating_sub(amount.0);
            }
            env::log(
                format!(
                    "The withdrawal of {} from @{} succeeded",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        } else {
            env::log(
                format!(
                    "The withdrawal of {} from @{} failed",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        }
        withdraw_succeeded
    }

    /// Returns the amount of tokens that are locked in this account due to vesting schedule.
    /// Takes raw vesting schedule, in case the internal vesting schedule is private.
    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }
        }
    }

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

            account.unstaked_available_epoch_height <= env::epoch_height(),

                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }
