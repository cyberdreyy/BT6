### Title
Cross-epoch instant-withdraw receipts escape default haircut and are permanently frozen — epoch-index confusion in `IdleCreditVault` default recovery — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The LuaJIT analog is a type/level confusion: `debug.getinfo` resolves a stack frame using the wrong "level" domain. In `IdleCreditVault`, instant-withdraw receipts are keyed per request epoch (`instantWithdrawsRequestsByEpoch[user][epoch]`), but the global counter `pendingInstantWithdraws` aggregates unfunded basis across **all** epochs. During `finalizeDefaultRecovery`, only the *current* epoch's instant claims are added to the recovery basis (`defaultPendingClaimBasis` uses `instantWithdrawClaimsByEpoch[epochNumber]`) and `_claimDefaultedInstantWithdrawRequest` clears only `defaultRecoveryEpoch`. An unfunded instant receipt opened in an earlier epoch is never haircut, never reserved, and can never be paid: `_transferFundedClaim` refuses to spend `defaultRecoveryReserve`, so the claim reverts forever.

### Finding Description
Three pieces disagree about which "level" (epoch) an instant receipt belongs to:

1. `requestInstantWithdraw` records the receipt at `instantWithdrawsRequestsByEpoch[user][epochNumber]` but adds to the epoch-agnostic `pendingInstantWithdraws` (lines 366-374).
2. `defaultPendingClaimBasis` adds instant basis only for `instantWithdrawClaimsByEpoch[epochNumber]` — the *finalization* epoch — while `pendingInstantWithdraws != 0` may still contain earlier-epoch unfunded claims (lines 644-648).
3. `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`; the remainder of `instantWithdrawsRequests[user]` falls through to `claimInstantWithdrawRequest`, which tries to pay it 1:1 through `_transferFundedClaim` (lines 380-393, 842-856).

`_transferFundedClaim` enforces `balance - defaultRecoveryReserve >= amount`, so an unfunded earlier-epoch claim reverts with `NotAllowed` (lines 897-907). There is no path that applies `defaultRecoveryPrice` to a non-default-epoch instant receipt — the recovery invariant is broken for exactly the same reason as the CVE: an index/level that is valid in one domain is dereferenced in another.

### Impact Explanation
Permanent freezing of unclaimed yield: lenders whose instant-withdraw receipts span an epoch boundary into the defaulted epoch lose their entire claim — they cannot claim at par (funded path reverts) and cannot claim at the recovery price (their per-epoch entry at `defaultRecoveryEpoch` is 0, so `_claimDefaultedInstantWithdrawRequest` returns 0). Additionally, `defaultPendingClaimBasis` undercounts the haircut basis, so `recoveryPrice` is set too high for the receipts that *are* covered; the last default-epoch claimants then find `defaultRecoveryReserve` exhausted and their claims revert too. Quantified loss: up to the full earlier-epoch unfunded instant basis plus the reserve shortfall.

### Likelihood Explanation
Requires `pendingInstantWithdraws > 0` at `finalizeDefaultRecovery` with instant claims recorded in an epoch earlier than `defaultRecoveryEpoch`. This is reachable with honest actors only: a lender calls `requestWithdraw`/`requestInstantWithdraw` during a buffer, the epoch rolls (`stopEpoch` → `epochNumber++`), the borrower fails to fund the instant queue (`getInstantWithdrawFunds` collects less than pending), and the pool defaults and is finalized in the next epoch. All privileged calls (manager `stopEpoch`, owner `finalizeDefault`) are honest-sequence. No guard prevents instant requests in consecutive epochs, and `_ensureDefaultRecoveryInitialized` only blocks on *aggregate* `pendingInstantWithdraws`, not on stale per-epoch entries.

### Recommendation
In `finalizeDefaultRecovery`, include the full unfunded instant basis (`pendingInstantWithdraws`, or the sum across all epochs, not just `instantWithdrawClaimsByEpoch[epochNumber]`) in `defaultPendingClaimBasis`, and in `_claimDefaultedInstantWithdrawRequest` clear *all* of `instantWithdrawsRequests[user]` at the recovery price rather than only the `defaultRecoveryEpoch` bucket — or iterate the user's per-epoch instant entries and apply `defaultRecoveryPrice` to each unfunded one.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
