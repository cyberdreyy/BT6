### Title
Instant-withdraw claims are not earmarked: a claimant drains underlyings collected for pending normal-withdraw receipts and the request stays double-counted in `pendingInstantWithdraws` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` pays a user's full `instantWithdrawsRequests[_user]` balance at par via `_transferFundedClaim`, straight out of the strategy's `underlyingToken.balanceOf(this)`. That balance is the same pool that `collectWithdrawFunds` fills to back already-funded (or loss-haircutted) normal withdraw receipts tracked in `pendingWithdraws`/`lossRecoveryPriceByEpoch`. There is no accounting linking an instant claim to funds actually collected via `collectInstantWithdrawFunds`, and the claim never decrements `pendingInstantWithdraws` (only `collectInstantWithdrawFunds` and `_claimDefaultedInstantWithdrawRequest` do). This mirrors CVE-2023-2006's bug class: operations on a shared accounting object (the vault's underlying balance + pending counters) without proper sequencing/locking over ownership boundaries.

### Finding Description
Relevant code paths, all in `contracts/strategies/idle/IdleCreditVault.sol`:

1. `requestInstantWithdraw` burns CDO-held strategy tokens, mints a receipt to `_user`, and increases `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` (lines 356-375).
2. `collectWithdrawFunds` pulls `_amount` of underlying from the CDO into the strategy's own balance to fund `pendingWithdraws`; on shortfall it records `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` (lines 411-430).
3. `claimInstantWithdrawRequest` burns the user's receipt and calls `_transferFundedClaim(_user, amount)` (lines 380-393). `_transferFundedClaim` only checks the `defaultRecoveryReserve` isolation guard — `balance - reserve >= amount` — and then transfers (lines 897-907). It does **not** verify that the instant request's funds were ever collected by `collectInstantWithdrawFunds`, and it does **not** reduce `pendingInstantWithdraws`.

Consequences of the missing earmark/decrement:

- **Queue-jumping theft:** underlying sitting in the vault to satisfy funded normal-withdraw receipts (post-`collectWithdrawFunds`) or APR0 `settledPrincipal`/`settledInterest` is fungible with instant-withdraw payouts. An instant claimant can take it before the rightful receipt holders call `claimWithdrawRequest`, leaving them with `safeTransfer` reverts — permanent freezing of their claims.
- **Double funding / borrower overcharge:** because `claimInstantWithdrawRequest` leaves `pendingInstantWithdraws` unchanged after paying the user, the CDO will still collect the same instant basis again at `stopEpoch` via `collectInstantWithdrawFunds`, inflating what the borrower must repay for an already-paid request.

The guards present (`_onlyIdleCDO`, `defaultRecoveryReserve` check, `isWalletAllowed` at the CDO layer, epoch gating on normal claims) do not stop this: the attacker only needs CDO-allowed instant-withdraw access (a KYC-passing lender during an epoch where instant withdraws are enabled), and the reserve guard explicitly excludes non-default pools.

### Impact Explanation
Direct theft and permanent freezing of unclaimed withdraw proceeds: the instant claimant extracts underlying earmarked for other users' funded receipts; when those users later call `claimWithdrawRequest`/`_claimFundedWithdrawRequest`/`_claimLossAdjustedWithdrawRequest`, `safeTransfer` reverts on insufficient balance, freezing their claims permanently unless the vault is topped up. Quantified loss equals the instant-claimed amount drawn against the funded-receipt pool, up to `pendingWithdraws`-funded balance in the vault.

### Likelihood Explanation
Requires an epoch where instant withdraws are enabled and where normal withdraw receipts have been funded into the strategy (post `collectWithdrawFunds`) or APR0 settled balances exist. Ordering is fully attacker-controlled: the claim can be executed in the same block as the CDO's funding transaction (or any time after), which is precisely the race-condition analog — no sequencing constraint ties the payout to actual collection. Not contingent on defaults, privileged misbehavior, or oracle data.

### Recommendation
- Decrement `pendingInstantWithdraws` in `claimInstantWithdrawRequest` (and keep `instantWithdrawClaimsByEpoch` consistent) so a paid request cannot be collected a second time at `stopEpoch`.
- Track a dedicated `instantWithdrawFunded`/`instantReserve` balance, incremented by `collectInstantWithdrawFunds` and consumed by `claimInstantWithdrawRequest`, and have `_transferFundedClaim` (or a separate instant-claim transfer) draw only from that bucket — never from underlying earmarked for `pendingWithdraws`, `lossRecoveryPriceByEpoch` receipts, or APR0 settled balances.

### Proof of Concept
Fork-PoC sketch (Foundry, mainnet fork, epoch running, instant withdraws enabled):

```solidity
// setup: pool with AA lender Alice (normal withdraw requester) and
// KYC'd attacker Bob; unscaledApr != 0.

// 1. Alice deposits, epoch runs. Alice calls CDO.withdrawRequest(amountA)
//    -> vault.requestWithdraw mints her a receipt, pendingWithdraws += amountA.
// 2. Honest stopEpoch: borrower repays; CDO calls
//    vault.collectWithdrawFunds(pendingWithdraws) -> vault balance now
//    holds amountA earmarked for Alice (lossRecoveryPrice may be < 1e18).
// 3. New epoch starts. Bob calls CDO instant withdraw entry:
//    vault.requestInstantWithdraw(amountA, bob) mints Bob a receipt,
//    pendingInstantWithdraws += amountA.
// 4. Bob immediately calls CDO.claimInstantWithdrawRequest(bob):
//    _transferFundedClaim passes (no defaultRecoveryReserve), Bob receives
//    amountA — Alice's funded underlying.
// 5. Alice calls CDO.claimWithdrawRequest(alice):
//    _claimFundedWithdrawRequest -> _transferFundedClaim -> safeTransfer
//    reverts on insufficient balance. Alice's receipt is permanently frozen.
// 6. At next stopEpoch the CDO again collects pendingInstantWithdraws
//    (still >= amountA) from the borrower — double-charging an already-paid
//    request.

assertEq(underlying.balanceOf(bob), amountA);
vm.expectRevert(); // Alice's claim reverts / insolvent vault
cdo.claimWithdrawRequest(alice);
```

Key assertions: (a) Bob's payout succeeds despite `collectInstantWithdrawFunds` never being called for him; (b) `pendingInstantWithdraws` remains non-zero after his claim, proving the counter is not decremented on payout; (c) Alice's funded claim reverts, proving the earmarked pool was consumed.

Note: I could not fully read `IdleCDOEpochVariant.sol`'s instant-withdraw entry points within the tool budget; the finding assumes the CDO exposes instant withdraw + claim to allowed (KYC'd) users during a running epoch, which matches the `requestInstantWithdraw`/`claimInstantWithdrawRequest` design comments and the `isWalletAllowed` gate seen in `IdleCDOEpochQueue.sol` (lines 415-420). If the CDO only permits instant claims after it has already collected instant funds into a segregated path, the theft leg is mitigated, but the `pendingInstantWithdraws` non-decrement (double borrower funding) stands independently.
