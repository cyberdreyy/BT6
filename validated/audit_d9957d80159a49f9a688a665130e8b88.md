## Analog Found: Unvalidated Fee Parameters in `createDstEscrow` Allow Resolver to Zero Out Protocol/Integrator Fees

### Title
Resolver-controlled `parameters` field in `createDstEscrow` allows fee-value forgery, permanently diverting protocol/integrator fees - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
The `AccountSystem`/`GigaNameNFT` bug involved a price value that is correctly computed and enforced in one code path (`mintWithEth`) but is trivially bypassable through a second path (`mintUsername`) that references an independent, unset (zero) copy of the same value. The same root cause — a single logical value (fee amount) that must be consistent across two deployment/execution paths, but is only validated in one of them — is reproduced in this repository's destination-escrow creation flow.

### Finding Description
On the source chain, `_postInteraction` computes the correct `protocolFeeAmount` and `integratorFeeAmount` via `FeeTaker._getFeeAmounts` and encodes them into `DstImmutablesComplement.parameters`, which is only emitted in the `SrcEscrowCreated` event for off-chain consumption: [1](#0-0) 

However, `createDstEscrow` takes the entire `IBaseEscrow.Immutables` struct — including the `parameters` field that encodes `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, and `integratorFeeRecipient` — directly as attacker-supplied calldata from an unprivileged caller (the resolver/taker), with no on-chain cross-check against the values computed during `_postInteraction`/emitted in `SrcEscrowCreated`: [2](#0-1) 

The only validations performed are on `msg.value` (safety deposit/native amount) and the cancellation-timestamp ordering; nothing constrains `dstImmutables.parameters`: [3](#0-2) 

These attacker-controlled fee fields are later read directly out of calldata by `EscrowDst._withdraw` to route funds: [4](#0-3) 

Because `protocolFeeAmount`/`integratorFeeAmount` are decoded straight from `immutables.parameters` (which the resolver freely chose when calling `createDstEscrow`), the resolver can set both to `0` (or any value it prefers) — just as `GigaNameNFT.mintUsername` references an independent, always-zero price table instead of the value enforced by `AccountSystem.mintWithEth`. In both cases an unprivileged actor reaches a state-changing entry point that reads a "should-be-fixed" economic value from a source that is never reconciled with the value the protocol actually computed.

### Impact Explanation
By deploying the destination escrow with a forged `parameters` field, the resolver diverts what should be `protocolFeeAmount`/`integratorFeeAmount` to the maker (or to itself, by choosing the fee recipient fields it controls) at withdrawal time. This is a permanent, on-chain loss of fee-like value owed to the protocol and integrator — the funds are transferred out of the escrow to the wrong recipient and unrecoverable once withdrawn. This matches the "High: theft or permanent loss of unclaimed fee-like value" category in the bounty scope.

### Likelihood Explanation
Likelihood is high: `createDstEscrow` is a normal, expected, unprivileged entry point in the live swap lifecycle (every resolver calls it to create every destination escrow), and no special conditions, front-running, or race are required — the resolver simply passes different `parameters` bytes than the ones it (or another resolver) advertised via `SrcEscrowCreated`.

### Recommendation
`createDstEscrow` should not accept a fully attacker-controlled `parameters`/fee payload. Either (a) derive the destination fee amounts and recipients on-chain from the corresponding `SrcEscrowCreated`/`DstImmutablesComplement` data keyed by `orderHash` (analogous to how `MerkleStorageInvalidator` binds validated data to `orderHash`), or (b) have the factory independently recompute/verify `protocolFeeAmount`/`integratorFeeAmount`/recipients against a canonical on-chain record before accepting `dstImmutables`, rather than trusting the caller-supplied bytes verbatim.

### Proof of Concept
1. Resolver fills a source order; `_postInteraction` computes `protocolFeeAmount = X`, `integratorFeeAmount = Y` and emits `SrcEscrowCreated` with these values in `immutablesComplement.parameters`.
2. Instead of reusing those values, the resolver calls `createDstEscrow` directly with `dstImmutables.parameters = abi.encode(0, 0, protocolFeeRecipient, integratorFeeRecipient)` (fees zeroed), satisfying `msg.value == nativeAmount` and the timestamp check — both of which are independent of `parameters`.
3. `BaseEscrowFactory.createDstEscrow` deploys `EscrowDst` with these attacker-chosen immutables; no revert occurs because `parameters` is unchecked. [2](#0-1) 
4. At withdrawal, `EscrowDst._withdraw` reads `integratorFeeAmount = 0`, `protocolFeeAmount = 0` from `immutables.parameters` and pays the maker the full `immutables.amount`, permanently bypassing the intended protocol/integrator fee split. [4](#0-3)

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
