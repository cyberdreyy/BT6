One candidate stands out: `_claimLossAdjustedWithdrawRequest` uses `lastWithdrawRequest[_user]` (the *latest* request epoch) to look up `lossRecoveryPriceByEpoch`. If a user has a loss-adjusted receipt in an earlier epoch and then makes a new request in a later epoch, the loss claim path returns 0 and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` at par — letting the user claim the haircut portion twice/at full value. Let me verify the epoch gating around `stopEpochWithDuration` and whether a user can request again afterward.### Title
Loss-adjusted withdrawal receipts can be claimed at par after a later request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimWithdrawRequest` applies the `stopEpochWithDuration(_lossAmount)` haircut only to the epoch stored in `lastWithdrawRequest[_user]`. A user whose pending receipt was haircutted in a loss epoch can simply make a new `requestWithdraw` in the following buffer period: `lastWithdrawRequest` is overwritten to the new epoch, the loss-adjusted path finds `lossRecoveryPriceByEpoch[newEpoch] == 0` and skips, and `_claimFundedWithdrawRequest` then pays the aggregate `withdrawsRequests[_user]` — which still contains the un-haircutted basis of the loss-epoch receipt — at par.

### Finding Description
When the manager stops an epoch with a loss via `IdleCDOEpochVariant.stopEpochWithDuration` → `_stopEpoch` → `collectWithdrawFunds(_pendingWithdraws)`, the strategy stores `lossRecoveryPriceByEpoch[epochNumber]` and clears `pendingWithdraws`, funding only `basis * price` of the receipts ( [1](#0-0) ). The haircut is enforced at claim time only in `_claimLossAdjustedWithdrawRequest`, which looks up the price using `lastWithdrawRequest[_user]` — the user's *latest* request epoch ( [2](#0-1) ).

`requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds the new amount to the aggregate `withdrawsRequests[_user]` ( [3](#0-2) ). After a loss stop that did not trigger emergency shutdown, `_stopEpoch` re-enables `allowAAWithdrawRequest`/`allowBBWithdrawRequest` ( [4](#0-3) ), so the user can request a new withdrawal in the next buffer period. On the subsequent claim:

1. `_claimLossAdjustedWithdrawRequest` reads `lastWithdrawRequest` = new epoch → `lossRecoveryPrice == 0` → returns 0 without clearing anything.
2. `_claimFundedWithdrawRequest` passes the `epochNumber <= lastWithdrawRequest` gate after the next `stopEpoch`, then pays `amount = withdrawsRequests[_user]` — the *full un-haircutted* basis of the old receipt plus the new one ( [5](#0-4) ).

The strategy only received `basis * lossRecoveryPrice` for the old receipt but pays `basis`. The excess `(1 - lossRecoveryPrice) * oldBasis` is transferred from funds reserved for other claimants / the `defaultRecoveryReserve` guard only protects the reserve, not funded-claim balances ( [6](#0-5) ).

### Impact Explanation
Direct theft / insolvency: the attacker recovers the haircut portion of their loss-epoch receipt at par, draining funded liquidity owed to other withdraw requesters. Quantified loss per attack: `oldBasis * (1 - lossRecoveryPrice)` — e.g. with a 50% loss price and a 10,000 USDC receipt, the attacker extracts ~5,000 USDC beyond entitlement, leaving the last claimants' receipts unpayable.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder with a pending receipt during a loss epoch, plus a second small `requestWithdraw` in the next buffer period (allowed since a non-terminal loss stop re-enables requests). No privileged collusion needed; sequencing is trivially achievable in normal operation.

### Recommendation
Track loss adjustment per receipt epoch, not via the mutable `lastWithdrawRequest`. Iterate/accumulate all epochs with `lossRecoveryPriceByEpoch != 0` for the user (e.g., store a per-user list of request epochs, or check `withdrawsRequestsByEpoch[_user]` across epochs), or store the haircutted amount directly at claim-epoch granularity so the funded path never sees the pre-haircut basis.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
