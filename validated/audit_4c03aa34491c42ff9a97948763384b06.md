Confirmed: in `multisig2/src/lib.rs`, `delete_member` (lines 356-379) only purges requests/confirmations for requests the removed member originally *created* (filtered on `r.member == member`), but never scans the `confirmations` map for other pending requests the removed member had merely *confirmed*. Since `confirm()` (lines 294-315) only checks the raw set length (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without validating that each entry in the set is still a current member, a stale confirmation left behind by a deleted member is still counted toward the threshold on any other still-pending request. The identical pattern exists in the legacy `multisig/src/lib.rs` (`DeleteKey` action, lines 198-216, and `confirm`, lines 246-266): outstanding requests *created* by the deleted key are purged, but confirmations that key placed on requests created by *other* keys are never scrubbed.

### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing execution below the live-member threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
`delete_member`/`DeleteKey` only removes requests *created* by the removed member/key; it does not scrub that member's entries from the `confirmations` set of *other* pending requests. `confirm()` counts raw set length, not live membership, so a pending request that already carries a confirmation from a member who is later removed only needs `num_confirmations - 1` additional confirmations from remaining live members to execute — one fewer than the currently configured threshold requires.

### Finding Description
`MultiSigContract::confirm` in [1](#0-0)  executes a request once `confirmations.len() as u32 + 1 >= self.num_confirmations`, purely a cardinality check on the `HashSet<String>` stored per request. It never re-validates that the members represented in that set are still members of `self.members`.

`delete_member`, invoked from `execute_request` for the `DeleteMember` action, is the only place membership changes are propagated: [2](#0-1) . It asserts `members.len() - 1 >= num_confirmations` (protects against the threshold becoming unreachable), removes the member from `self.members`, and removes only the requests where `r.member == member` — i.e. requests the deleted member itself *created*. It does not iterate `self.confirmations` to strip the deleted member's entries from requests created by other members that this member had merely confirmed.

Concretely:
1. `num_confirmations = 2`, members = {A, B, C, D}.
2. B creates request X (a `Transfer` to an attacker-controlled or colluding account) and it currently has 0 confirmations.
3. A confirms request X → `confirmations(X) = {A}` (1 confirmation, below threshold, not yet executed).
4. Separately, a `DeleteMember { member: A }` request is created and gets the required 2 confirmations from other members (e.g. C and D), and executes. `self.members.len() - 1 = 3 >= 2` so the assertion passes; A is removed from `self.members` and their access key is deleted. Request X is untouched because `r.member` for X is B, not A.
5. C confirms request X. `confirm()` sees `confirmations(X).len() = 1` (A's stale entry) `+ 1 (C) = 2 >= num_confirmations(2)`, so it executes the `Transfer`.

The transfer executed with only one live, current member (C) actually confirming plus one stale entry from a member (A) who had already been removed from the multisig at the time of execution. The identical logic exists in the legacy `multisig/src/lib.rs`: `DeleteKey` purges only requests where `r.signer_pk == pk` ( [3](#0-2) ), leaving that key's confirmations intact on requests created by other keys, and `confirm` ( [4](#0-3) ) does the same length-only check.

This breaks the intended custody binding: *confirmations actually cast by currently-authorized members* should equal *the number of confirmations counted toward the threshold*. Here, `confirmations counted > confirmations from live members`.

### Impact Explanation
This allows a `MultiSigRequestAction::Transfer` (or `FunctionCall`, `AddKey`, `DeployContract`, etc.) to execute with fewer live-member confirmations than `num_confirmations` requires — i.e., NEAR (or any other action gated by the multisig, including wNEAR transfers via `FunctionCall`) can be moved out of the multisig account by a coalition of members that is smaller than the configured threshold. This is a Critical-severity impact per the rubric: funds moved/an action executed by a party (or a smaller group) not entitled to do so under the account's configured authorization policy.

### Likelihood Explanation
Exploitation requires only that: (a) a request is confirmed by a member who is later removed (a normal event — members are expected to be added/removed over the account's lifetime), and (b) the remaining request isn't independently deleted or re-confirmed to invalidate the stale confirmation before the remaining members finish confirming it. No privileged/foundation access is needed beyond membership already granted for ordinary multisig operation, and the actors executing the final confirmation are themselves legitimate current members — they just benefit from an authorization count that silently includes a party no longer entitled to approve. This is a realistic operational sequence (member rotation is a normal multisig lifecycle event), making likelihood moderate-to-high whenever member turnover occurs while requests are outstanding.

### Recommendation
When a member is deleted (`delete_member` in `multisig2`, `DeleteKey` in `multisig`), iterate all entries in the `confirmations` map (not just requests created by that member) and remove the deleted member's/key's entry from every pending request's confirmation set. Alternatively, at confirmation-count time, filter `confirmations` against `self.members` before comparing to `num_confirmations`, so removed members' stale confirmations are never counted.

### Proof of Concept
Using `multisig2/src/lib.rs`'s existing test harness (`members()`, `context_with_account`, etc.):
1. `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 2)`.
2. As B: `add_request(Transfer{...})` → `request_id = X` (no confirm).
3. As A: `confirm(X)` → `confirmations(X) = {A}`, not yet executed (1 < 2).
4. As C: `add_request_and_confirm(DeleteMember{member: A})` → 1 confirmation.
5. As D: `confirm(delete_request_id)` → 2 confirmations ≥ 2 → executes `delete_member(A)`; `self.members = {B, C, D}`; request X untouched (`r.member == B`, not `A`).
6. As C: `confirm(X)` → `confirmations(X).len() == 1` (stale A) `+ 1 == 2 >= num_confirmations(2)` → `Transfer` executes, moved by only one truly-current confirming member (C) plus B (creator) instead of the required 2 independent live confirmations.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
