### Title
Batched direct-solve reverts entirely on a single malicious/blacklisted receiver, DOSing co-batched requests - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.solveRequestsDirect` iterates over an array of user-supplied `RequestV2` structs and, for each one, calls `_solveRequestDirect`, which performs raw `safeTransfer`/`safeTransferFrom` calls to `request.receiver` with no try/catch or fallback. Since `receiver` is fully attacker-controlled at request-creation time and `solveRequestsDirect` is unauthenticated, an attacker can create one request with a receiver that reverts on transfer (e.g., blacklisted on USDC, or a contract that reverts on token receipt), which will cause the entire batched call to revert, blocking every other honest request bundled in the same transaction. This mirrors the reported Gitcoin `DonationVotingMerkleDistributionBaseStrategy._distribute` griefing pattern, where a loop over recipients aborts the whole batch on one bad transfer.

### Finding Description
`requestDeposit`/`requestRedeem` let any user create an async request with an arbitrary `receiver` field [1](#0-0) . Anyone (no `requiresAuth`) may call: [2](#0-1) 

which loops over the caller-supplied `requests[]` and calls `_solveRequestDirect` for each entry without any isolation between iterations.

Inside `_solveRequestDirect`, for the non-refund ("solved") branch, transfers to `request.receiver` are performed with plain `safeTransfer`/`safeTransferFrom`, not the `_transferWithFallback` helper that is used elsewhere for refund paths: [3](#0-2) 

Compare this to the refund branch and to `_transferWithFallback`, which explicitly guards against a non-cooperative receiver by falling back to the requester: [4](#0-3) 

No such fallback exists for the "solved" branch's transfers in `_solveRequestDirect`. If `request.receiver` is a blacklisted address for the ERC20 `token` (e.g., a USDC-style blacklist), or a contract without a receive/fallback (for native-wrapped flows) or one that reverts on transfer, the `safeTransfer`/`safeTransferFrom` call reverts, and since `solveRequestsDirect` has no per-item try/catch, the entire batch transaction reverts — exactly the root cause described in the report (a loop over recipients where a single bad actor DOSes the whole batch).

### Impact Explanation
Any solver who batches multiple pending direct-solve requests together (to save gas/gain tips) can have their entire transaction reverted by a single malicious request planted by an attacker (who creates their own request with a poisoned `receiver`). This delays settlement (and solver tip collection) for all honest requesters bundled in that same call, and can be repeated indefinitely by re-submitting new malicious requests, creating a persistent temporary freeze of user deposit/redeem finality — a Medium-severity temporary-freeze condition per Immunefi's classification.

### Likelihood Explanation
High feasibility: the attacker needs only to call `requestDeposit`/`requestRedeem` (both public, unauthenticated user entry points) with `receiver` set to a token-blacklisted or reverting address, and wait for a solver to include the malicious request hash in a batched `solveRequestsDirect` call together with other pending requests. No privileged role, oracle failure, or race condition is required — solvers naturally batch to save gas, making inclusion likely without solver-side filtering, and even a targeted attacker can craft calldata to include their own poisoned request alongside a specific victim request they observe as pending in the mempool/state.

### Recommendation
In `_solveRequestDirect` (and any other per-request loop in `ProvisionerV2` that transfers directly to `request.receiver`), use the same non-reverting `trySafeTransfer`-with-fallback pattern already used for refunds (`_transferWithFallback`), or wrap the transfer in a try/catch that marks the individual request as failed/skipped (emitting an event) rather than letting a single failure revert the whole batch.

### Proof of Concept
1. Deploy `ProvisionerV2` wired to a mock ERC20 `token` that supports a `blacklist(address)` function which makes `transfer`/`transferFrom` to a blacklisted address revert (mimic USDC).
2. User A calls `requestDeposit(token, tokensIn, minUnitsOut, ..., receiver = <blacklisted address controlled by A>)`; token then blacklists that receiver (or receiver is pre-blacklisted).
3. User B calls `requestDeposit(token, tokensIn, minUnitsOut, ..., receiver = B)` normally — a legitimate, fully solvable request.
4. A solver calls `solveRequestsDirect(token, [requestA, requestB])`.
5. Assert: the transaction reverts entirely (due to A's blacklisted receiver failing `safeTransferFrom`/`safeTransfer` inside `_solveRequestDirect`), even though B's request is valid and solvable — demonstrating that B's legitimate request is blocked/delayed solely because it was batched with A's request.
6. Repeat with B's request alone (no batching) to confirm it succeeds in isolation, proving the DOS is caused specifically by batching with the malicious request.

    function solveRequestsDirect(IERC20 token, RequestV2[] calldata requests) external nonReentrant {
        // Requirements: vault is not paused in the priceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());

        uint256 length = requests.length;
        TokenDetailsV2 storage tokenDetails = tokensDetails[token];
        for (uint256 i = 0; i < length; i++) {
            RequestV2 calldata request = requests[i];
            RequestType requestType = request.requestType;

            // Requirements: direct solves can only solve fixed price requests
            require(!_isRequestTypeAutoPrice(requestType), Aera__AutoPriceSolveNotAllowed());

            if (_isRequestTypeDeposit(requestType)) {
                // Requirements: async deposit is enabled
                require(tokenDetails.asyncDepositEnabled, Aera__AsyncDepositDisabled());
            } else {
                // Requirements: async redeem is enabled
                require(tokenDetails.asyncRedeemEnabled, Aera__AsyncRedeemDisabled());
            }

            // Requirements + Effects + Interactions: solve direct request
            _solveRequestDirect(token, request);
        }
    }

    function _solveRequestDirect(IERC20 token, RequestV2 calldata request) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        if (_guardInvalidRequestHash(requestHash)) return;

        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;

        bool isDeposit = _isRequestTypeDeposit(request.requestType);

        if (request.deadline >= block.timestamp) {
            if (isDeposit) {
                // Interactions: pull units from sender(solver) to receiver
                IERC20(MULTI_DEPOSITOR_VAULT).safeTransferFrom(msg.sender, request.receiver, request.units);
                // Interactions: transfer tokens from provisioner to sender
                token.safeTransfer(msg.sender, request.tokens);

                // Log solved event
                emit DepositSolved(requestHash);
            } else {
                // Interactions: transfer units from provisioner to sender
                IERC20(MULTI_DEPOSITOR_VAULT).safeTransfer(msg.sender, request.units);
                // Interactions: pull tokens from sender(solver) to receiver
                token.safeTransferFrom(msg.sender, request.receiver, request.tokens);

                // Log solved event
                emit RedeemSolved(requestHash);
            }
        } else {
            // Interactions: transfer escrowed asset to receiver, fallback to requester on transfer failure
            if (isDeposit) {
                _transferWithFallback(token, request.user, request.receiver, request.tokens);

                // Log refunded event
                emit DepositRefunded(requestHash);
            } else {
                _transferWithFallback(IERC20(MULTI_DEPOSITOR_VAULT), request.user, request.receiver, request.units);

                // Log refunded event
                emit RedeemRefunded(requestHash);
            }
        }
    }

    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
