### Title
Post-default withdraw requests drain the shared default recovery reserve, permanently freezing earlier claimants' recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After `finalizeDefaultRecovery` crystallizes a haircut (`defaultRecoveryPrice < RECOVERY_FULL`), `IdleCreditVault.requestWithdraw` still accepts new withdraw requests into `postDefaultRequests` and `_claimPostDefaultWithdrawRequest` pays them **1:1 out of `defaultRecoveryReserve`** — the same reserve that was sized at finalization to exactly cover only the claimants existing at that time. Because the reserve is not increased when a post-default request is created, every post-default claim steals recovery from defaulted-epoch claimants; the last claimants' `_transferDefaultRecovery` reverts on underflow/insufficient balance, permanently freezing their recovery.

### Finding Description
`finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` and stores `defaultRecoveryReserve = reserveAmount`, where `totalBasis` includes only the active tranche basis and the pending receipts that existed at default time (contracts/strategies/idle/IdleCreditVault.sol:679-692). Nothing is added to the reserve later.

After finalization, `requestWithdraw` takes a dedicated branch: the CDO's strategy tokens are burned, a receipt is minted to the user, and `postDefaultRequests[_user] = _amount` is recorded — but `defaultRecoveryReserve` is untouched (IdleCreditVault.sol:247-257). The comment says the CDO passes an already-haircut amount, which keeps the *price* consistent, but the *reserve* was sized to pay `sum(claimBasis_i * recoveryPrice)` for the pre-finalization claimants only.

In `claimWithdrawRequest`, post-default claims are serviced **first**, before defaulted-epoch receipts: `amount = _claimPostDefaultWithdrawRequest(_user); if (amount != 0) return amount;` (IdleCreditVault.sol:303-310). `_claimPostDefaultWithdrawRequest` then calls `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` and transfers underlying (IdleCreditVault.sol:760-767, 912-917).

Net effect: total obligations against the reserve become `reserveAmount + Σ postDefaultRequests` while the balance is only `reserveAmount`. An attacker holding tranches who requests a withdraw right after finalization (or a user whose request was pending and routed to `postDefaultRequests`) is paid before — and out of — the haircut reserve, so the sum of remaining claimants' entitlements exceeds the remaining reserve. The last claimants revert in `_transferDefaultRecovery` (`defaultRecoveryReserve -= _amount` underflows, or the ERC20 transfer fails), permanently freezing their recovery.

Broken invariant: one receipt one payout / reserve solvency — the post-default path violates the isolation guarantee that `_transferFundedClaim` explicitly enforces for the reserve (IdleCreditVault.sol:897-906), yet `_transferDefaultRecovery` itself has no check that the reserve can cover all outstanding claims.

### Impact Explanation
A post-default claimant extracts `postDefaultRequests[_user]` underlying at par from a reserve intended to pay all finalized claims at `defaultRecoveryPrice`. The loss falls on the last defaulted-epoch (and other post-default) claimants, whose legitimate recovery claims become unpayable — a direct theft plus permanent freezing of unclaimed recovery, quantified as exactly the cumulative post-default payout amount. With `recoveryPrice` near 1 (e.g. a near-full borrower recovery), even small post-default requests fully drain the margin; the shortfall grows linearly with post-default volume.

### Likelihood Explanation
- No privileged actor is required: any tranche-token holder can call `IdleCDOEpochVariant.requestWithdraw` after default finalization; the strategy branch is explicitly designed to accept such requests (`postDefaultRequests` exists precisely for this UX).
- The condition — a finalized default with `recoveryPrice < RECOVERY_FULL` and at least one post-default withdraw — is a normal protocol path, reached whenever a default is finalized while users still hold tranches and want out.
- No existing guard stops it: `_ensureDefaultRecoveryInitialized` only gates legacy state; `claimWithdrawRequest` deliberately prioritizes post-default claims; `_transferDefaultRecovery` has no reserve-solvency check.

Uncertainty: the exact CDO-side call path (`IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw` while `defaulted()` is true) was not fully traced in this session. If the CDO reverts post-default requests, the finding reduces to users whose requests are created via the still-open path the code explicitly supports (`postDefaultRequests` mapping and claim path exist and are exercised in tests such as `testProcessPostDefaultWithdrawalAsNormalClaim`).

### Recommendation
Either fund post-default claims from a separate source, or account for them in the reserve. Concretely: when `requestWithdraw` records `postDefaultRequests[_user]`, do not pay it from `defaultRecoveryReserve` — instead require the CDO to transfer the corresponding underlying (the burned tranche's recovery-value backing) into the strategy first, or track post-default claims against a distinct bucket. Alternatively, apply the same `defaultRecoveryPrice` haircut at claim time and treat post-default basis as sharing the remaining reserve pro rata, updating `defaultRecoveryReserve` accounting so `Σ payouts ≤ reserve`.

```solidity
// 1. Users A (attacker) and V (victim) deposit, epochs run normally.
// 2. Victim requests withdraw; attacker keeps tranches.

// 4. manager calls finalizeDefault(recovered, source) with recovered < totalBasis

//    strategy mints postDefaultRequests[attacker] (reserve unchanged).

//    _claimPostDefaultWithdrawRequest pays 1:1 from defaultRecoveryReserve.
assertEq(postDefaultPayout, attackerRequestAmount);
// 7. Victim calls claimWithdrawRequest():
//    _claimDefaultedWithdrawRequest -> _transferDefaultRecovery reverts

vm.expectRevert();

```

Key assertions: `defaultRecoveryReserve` after step 6 equals `reserveAmount - attackerPayout`, while the sum of remaining finalized claim bases times `defaultRecoveryPrice` exceeds it by exactly `attackerPayout`.
