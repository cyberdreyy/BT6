### Title
APR=0 withdraw request can permanently brick `stopEpoch` once APR is set non-zero, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to `settleAuction`'s `a - b` underflow reverting at settlement after a user has already locked tokens, `prepareStopEpochWithApr0` in `IdleCreditVault` hard-reverts whenever an APR=0 withdraw request is pending (`apr0TotalPrincipal != 0`) but the vault's `unscaledApr` is no longer zero. A lender who calls `requestWithdraw` while APR is 0 locks their receipt into the `apr0TotalPrincipal` bucket; if the borrower/manager later sets a non-zero APR (a normal, honest operation between or during epochs), every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts at `IdleCreditVault.sol:506-508`, and since `apr0TotalPrincipal` is only cleared at the end of that same reverting function (`line 540`), the bucket can never be closed. The epoch state machine is permanently stuck.

### Finding Description
`requestWithdraw` on the CDO burns the user's tranche tokens and routes through `IdleCreditVault.requestWithdraw`, which records APR=0 requests via `_requestWithdrawApr0`, incrementing `apr0TotalPrincipal` (lines 567-577). At epoch settlement, `IdleCDOEpochVariant.stopEpoch` calls `prepareStopEpochWithApr0`, which contains:

```solidity
if (_principal == 0) { return ...; }
if (unscaledApr != 0) {
    revert NotAllowed();
}
```

(cite: `contracts/strategies/idle/IdleCreditVault.sol:502-508`)

The intent is presumably to guarantee APR0 accounting consistency, but there is no escape path: `apr0TotalPrincipal` cannot be decreased by the user, cannot be settled early, and is zeroed only inside this function after the revert guard. `unscaledApr` is set by `setAprs` (borrower/manager driven), which the protocol expects to change over the vault's lifetime — including raising APR back above zero after an APR=0 period. Once that happens while any APR0 receipt is open, the invariant "an epoch can always be stopped" breaks permanently.

### Impact Explanation
Permanent freezing of all pool funds. With `stopEpoch` unreachable, borrower principal+interest can never be recalled, `epochNumber` never increments, and every pending withdraw request (normal, APR0, instant) plus all active tranche holders' NAV is frozen indefinitely. Loss magnitude equals the entire vault TVL plus pending receipt basis — identical in spirit to the auction's `bondForRebalance` locking tokens at a point where `settleAuction` can never succeed.

### Likelihood Explanation
Requires a narrow but legitimate sequence: an epoch running at APR=0 (a supported mode — dedicated `apr0Users`, `apr0RateByEpoch`, and `apr0TotalPrincipal` accounting exists), a KYC-passed lender calling `requestWithdraw` (unprivileged, enabled via `allowAAWithdrawRequest`/`allowBBWithdrawRequest`), and a subsequent APR increase via `setAprs`. APR changes are routine borrower/manager operations, not adversarial. The revert is deterministic — no rounding or economic condition is needed.

### Recommendation
Replace the hard revert in `prepareStopEpochWithApr0` with graceful handling: when `unscaledApr != 0`, either (a) settle the outstanding APR0 principal bucket at par with zero interest and clear `apr0TotalPrincipal`, or (b) block `setAprs` from raising APR while `apr0TotalPrincipal != 0` so the inconsistent state is prevented at request time rather than discovered at settlement. Users should never be able to lock receipts into a state where epoch settlement mathematically cannot proceed.

### Proof of Concept
Foundry fork outline (solidity, based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Setup: epoch vault deployed, lender KYC'd, deposits into AA
idleCDO.depositAA(10000 * ONE_SCALE);

// 1) Manager sets APR to 0 and starts epoch
vm.prank(manager);
IdleCreditVault(address(strategy)).setAprs(0, 0);
_startEpochAndCheckPrices(0);

// 2) Attacker (ordinary KYC'd lender) requests withdraw during APR0 epoch
//    -> tranche tokens burned, apr0TotalPrincipal > 0
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // full balance
assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

// 3) Honest borrower/manager raises APR back above zero
vm.prank(manager);
IdleCreditVault(address(strategy)).setAprs(5e18, 5e18);

// 4) Warp past epochEndDate; every stopEpoch attempt now reverts
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(5e18, 0);
// stopEpochWithDuration reverts identically; apr0TotalPrincipal can never be cleared.
// All lender funds, pending receipts, and borrower repayments are frozen.
```

Note: this assessment relies on the indexed code paths; I did not fully trace whether `setAprs` is blocked while an epoch is running or while `apr0TotalPrincipal != 0` — if such a guard exists elsewhere it would weaken likelihood but the missing synchronization between `unscaledApr` changes and the APR0 bucket remains the defect.
