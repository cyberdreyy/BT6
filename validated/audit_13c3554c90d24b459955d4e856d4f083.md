### Title
Multisig `confirm` counts confirmations from access keys that have since been deleted, allowing request execution below the configured confirmation threshold - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig/src/lib.rs` tallies confirmations for a request by comparing `confirmations.len()` against `self.num_confirmations`, but confirmations are recorded by `PublicKey` and are never purged from a request's confirmation set when that key is later removed from the account via a `DeleteKey` request. This breaks the equality that is supposed to hold between "confirmations recorded" and "confirmations from currently-live multisig keys," letting a request execute with fewer genuinely live approvals than `num_confirmations` requires.

### Finding Description
`confirm()` only checks that the calling key hasn't already confirmed and then compares the size of the confirmation set to the threshold: [1](#0-0) 

The `DeleteKey` action, executed as part of `execute_request`, removes *only* the pending requests that were originally *added* by the deleted key (`r.signer_pk == pk`) and decrements `num_requests_pk`. It never scans `self.confirmations` to strip the deleted key from confirmation sets of *other* pending requests that key may have confirmed: [2](#0-1) 

Because `confirm()` never re-validates that every `PublicKey` already stored in `confirmations` for the request still exists as a valid access key on the account (`assert_valid_request` only checks the request/confirmation map exist, not key liveness): [3](#0-2) 

a confirmation recorded by a key that is later deleted continues to count toward the threshold. If request R already has one confirmation from key A, and key A is subsequently deleted (e.g., a member is removed/rotated via a separate, properly-confirmed `DeleteKey` request), R still shows 1 confirmation. Any other live key confirming R will push the tally to `num_confirmations`, and `execute_request` will run — even though only one currently-authorized key ever approved it.

This is the direct analog of the "recorded claims vs. what is actually held" bug class from the reference report: the contract trusts a recorded confirmation count instead of re-deriving it from the set of keys presently entitled to grant that trust (i.e., "confirmations counted versus live members").

### Impact Explanation
This breaks the core security guarantee of the multisig scheme: that `K` of the *current* `N` keys must approve before any `Transfer`, `FunctionCall`, `AddKey`, `DeleteKey`, etc. is executed. A request can be executed with effectively `K-1` (or fewer) live approvals, i.e., a multisig request executed below threshold. Given that `MultiSigRequestAction::Transfer` and `MultiSigRequestAction::FunctionCall` are among the actions gated by this same threshold check, this can lead to NEAR being moved, or an access key/contract being deployed, without the intended quorum — a Critical impact per the stated criteria ("a multisig request executed below threshold").

### Likelihood Explanation
The condition arises naturally whenever key rotation/removal is combined with any pending (unconfirmed-to-completion) request — a routine multisig maintenance operation (revoking a compromised or departing member's key) rather than an exotic scenario. No foundation privilege, redeploy, or social engineering is required; it only requires the normal multisig workflow of adding/confirming a request and later deleting a key while other requests are outstanding, which is explicitly supported functionality of this contract.

### Recommendation
When executing `DeleteKey` (and any equivalent member-removal action), iterate over all entries in `self.confirmations` and remove the deleted public key from every confirmation set, not only from requests originated by that key. Alternatively, re-validate at confirmation-count time that every key present in a request's confirmation set corresponds to an access key currently attached to the account before counting it toward `num_confirmations`.

### Proof of Concept
1. Multisig account is configured with `num_confirmations = 2` and keys `A`, `B`, `C`.
2. `A` calls `add_request_and_confirm` for a `Transfer` request `R` (confirmations = `{A}`, count 1/2).
3. Members legitimately submit and confirm a separate `DeleteKey{public_key: A}` request (reaching 2/2 with `B`+`C`), which executes and removes `A`'s access key. Per `multisig/src/lib.rs:198-216`, this only deletes requests where `signer_pk == A`; `R` was added by `A` too in this minimal example, so to isolate the bug, instead have `B` add request `R` and `A` confirm it (so `R.signer_pk == B`, confirmations = `{A}`) before `A` is deleted — `R` is not cleaned up since `B` (not `A`) is the original signer.
4. `A`'s key is deleted via step 3's `DeleteKey` request; `R`'s confirmation set still contains `A`'s (now invalid) public key.
5. `C` (a single live key) calls `confirm(R)`. `confirmations.len() + 1 = 2 >= num_confirmations (2)`, so `execute_request` runs the `Transfer`, even though only one currently valid key (`C`) actually approved `R` post-deletion.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
