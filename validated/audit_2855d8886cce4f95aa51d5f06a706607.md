### Title
Case-sensitive drive-letter comparison in `windowsPath.convert`/`Contains` causes `IsHostMountedVolume` false negative - ([File: executors/docker/internal/volumes/parser/windows_path.go])

### Summary
The cross-platform (`//go:build !windows`) implementation of `windowsPath.Contains`, used to approximate Windows path semantics when the GitLab Runner binary itself is not running on Windows (e.g. a Linux/macOS host managing a remote Docker Engine that runs Windows containers), performs a case-sensitive `strings.HasPrefix` comparison after `convert`. Because `convert` neither normalizes the drive letter's case nor otherwise case-folds the path, two paths that refer to the identical location on a real (case-insensitive) Windows/NTFS filesystem but differ only in drive-letter or path casing (e.g. `c:\Foo` vs `C:\foo`) will not match, causing `IsHostMountedVolume` to wrongly return `false`.

### Finding Description
`windowsPath.Contains` and its helper `convert` are defined in [1](#0-0) . `convert` strips the colon from a drive prefix and replaces separators, but never lower-cases (or upper-cases) the drive letter or any other path segment:

```go
func (p *windowsPath) Contains(basePath, targetPath string) bool {
	return strings.HasPrefix(p.convert(targetPath, true), p.convert(basePath, true))
}
```

Given `basePath = "C:\\foo"` and `targetPath = "c:\\Foo\\bar"`, `convert` produces `"/C/foo/"` and `"/c/Foo/bar/"` respectively — `strings.HasPrefix` returns `false` even though on a real Windows/NTFS volume these two paths address the same directory tree.

This implementation is selected in `newWindowsPath()` only when compiled with the `!windows` build tag [2](#0-1) . Note: the file the question names, `windows_path_windows.go` (build tag `windows`), does **not** contain `convert` — it instead delegates to `helpers/path.NewWindowsPath()` [3](#0-2) , whose `Contains` uses Go's `filepath.Rel` [4](#0-3) . Go's `path/filepath` package on actual Windows builds performs case-insensitive comparisons internally, so that code path is not affected by this bug. The vulnerable `convert`-based logic only runs when the Runner binary itself is compiled/executed on a non-Windows host (e.g. Linux) while parsing Windows-style container volume destinations — a legitimate, supported configuration for controlling a remote Docker Engine that runs Windows containers.

`IsHostMountedVolume` calls `volumeParser.Path().Contains(parsedVolume.Destination, dir)` to decide if a build directory falls inside an admin-configured bind-mounted volume [5](#0-4) . If `Contains` returns a false negative due to case mismatch between the admin-configured `volumes` destination and the effective build directory casing, `IsHostMountedVolume` returns `false` when the directory is in fact host-mounted, causing downstream logic to treat the directory as a disposable, non-host path.

### Impact Explanation
Existing test coverage explicitly enumerates only exact-case matches (`"c:\\path"` vs `"c:\\path\\to\\dir"`) [6](#0-5)  and never verifies cross-case equivalence, so the gap is untested. If a runner admin configures a host-mounted volume destination with one letter-case (e.g., `C:\shared`) and the resolved build directory used for the job differs in case only, `IsHostMountedVolume` incorrectly reports "not host mounted." Any cleanup/permission-normalization logic gated on this check would then run against what is actually a host-mounted, potentially cross-project-shared directory, risking unintended modification/deletion of host-side data outside the intended build/cache root — a path-boundary violation of the "file operations must stay within intended build/cache/artifact roots" invariant.

### Likelihood Explanation
Exploitability requires: (1) the Runner is compiled/running on a non-Windows host and orchestrating Windows containers (a supported but non-default configuration), (2) an admin-configured host-mounted volume whose destination casing differs from the effective build-path casing that ends up being compared, and (3) that casing divergence being reachable via CI-controlled inputs (e.g., project path segments feeding into `CI_PROJECT_DIR`/build directory construction). This is a real, deterministic logic defect but is conditioned on a specific deployment topology (non-Windows-hosted runner managing Windows containers) and admin-chosen mixed-case volume configuration, making it a legitimate but narrowly-scoped correctness/security bug rather than a broadly and trivially exploitable one.

### Recommendation
Normalize case before comparison in `convert` (or in `Contains` directly), e.g., lower-case the entire converted path (drive letter and all segments) before calling `strings.HasPrefix`, matching NTFS/Windows case-insensitive semantics — mirroring how `helpers/path/windows_path.go`'s Windows-native implementation behaves via `filepath.Rel`. Add regression tests asserting `Contains` case-insensitivity across drive-letter and full-path case permutations.

### Proof of Concept
Add to `executors/docker/internal/volumes/parser/windows_path_test.go`:
```go
func TestWindowsContainsCaseInsensitiveDriveLetter(t *testing.T) {
	p := newWindowsPath()
	// same directory, differing only by drive-letter/path case
	assert.True(t, p.Contains("C:\\foo", "c:\\Foo\\bar"),
		"Contains must be case-insensitive for Windows drive letters/paths")
}
```
Expected current behavior: assertion fails (returns `false`), confirming the false negative. After applying a case-normalization fix in `convert`, the assertion should pass.

```go
func (p *windowsPath) Contains(basePath, targetPath string) bool {
	return strings.HasPrefix(p.convert(targetPath, true), p.convert(basePath, true))
}

// convert absolute path to a regular and absolute forward-slash based path,
// useful only for comparisons.
//
// c:\hello\world -> /c/hello/world/
// \\server_name/hello -> /server_name/hello/
func (p *windowsPath) convert(pathname string, dir bool) string {
	if len(pathname) > 1 && pathname[1] == ':' {
		pathname = pathname[:1] + pathname[2:]
	}
	pathname = strings.NewReplacer("\\", "/", ":", "/").Replace(pathname)
	pathname = gopath.Clean("/" + pathname)

	if dir && !strings.HasSuffix(pathname, "/") {
		return pathname + "/"
	}
	return pathname
}
```

```go
func (p *windowsPath) Contains(basePath, targetPath string) bool {
	// we use `filepath.Rel` as this perform OS-specific comparison
	// and this set of functions is compiled using OS-specific golang filepath
	relativePath, err := filepath.Rel(basePath, targetPath)
	if err != nil {
		return false
	}

	// if it starts with `..` it tries to escape the path
	if strings.HasPrefix(relativePath, "..") {
		return false
	}

	return true
}
```

```go
func IsHostMountedVolume(volumeParser parser.Parser, dir string, volumes ...string) (bool, error) {
	if !volumeParser.Path().IsAbs(dir) {
		return false, errDirectoryNotAbsolute
	}

	if volumeParser.Path().IsRoot(dir) {
		return false, errDirectoryIsRootPath
	}

	for _, volume := range volumes {
		parsedVolume, err := volumeParser.ParseVolume(volume)
		if err != nil {
			return false, err
		}

		if parsedVolume.Len() < 2 {
			continue
		}

		if volumeParser.Path().Contains(parsedVolume.Destination, dir) {
			return true, nil
		}
	}
	return false, nil
}
```
