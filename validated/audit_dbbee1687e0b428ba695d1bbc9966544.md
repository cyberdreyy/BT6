### Title
Vault/secret `File=true` variable's `Key` is embedded unsanitized into shell script paths/quotes, enabling path traversal and command injection via `$()`/backticks - ([File: shells/bash.go])

### Summary
`BashWriter.Variable` (shells/bash.go:229-241) builds the file path for a `File=true` secret variable from `b.TmpFile(variable.Key)` and writes it into the script using Go's `%q` formatting verb rather than the writer's own shell-escaping routine (`b.escape`, i.e. `ShellEscape`/`PosixShellEscape` in helpers/shell_escape.go). Because `variable.Key` originates from the job's `secrets:` block key name (`common/secrets.go:100,137` — `variableKey` becomes `spec.Variable.Key`), an attacker who controls the CI YAML's secrets mapping key controls this string end-to-end, and it reaches the generated shell script without sanitization for path traversal or shell metacharacters.

### Finding Description
In `defaultSecretsResolver.handleSecret` (common/secrets.go:116-146), the YAML map key of the `secrets:` block (`variableKey`) is placed directly into `spec.Variable.Key` with no character-set validation: [1](#0-0) 

This variable flows to `AbstractShell.writeExports` → `w.Variable(variable)` for every build variable, including resolved secrets: [2](#0-1) 

In `BashWriter.Variable`, when `variable.File` is true: [3](#0-2) 

- `variableFile := b.TmpFile(variable.Key)` builds the destination path via `path.Join(b.TemporaryPath, name)` then `b.Absolute(...)` — no rejection of `..`, no character allow-list.
- The path is embedded with `%q` — this is Go's `fmt` `%q` verb (Go-syntax quoting), not a shell-safe quoting function. Go's `%q` escapes backslashes/double-quotes/control characters for Go string literal syntax, but it does **not** escape `$`, backticks, or `!`, which remain special inside a bash double-quoted string.
- Contrast this with the `export %s=%q` line for the *value*, whose key output uses `b.escape(variable.Key)` (proper shell escaping producing `$'...'` ANSI-C quoting) — but the **path** literal is not run through `b.escape`, only through `%q`.

Because the key is never restricted to a safe variable-name character set (e.g., `^[A-Za-z_][A-Za-z0-9_]*$`) before being used as a filesystem path component, an attacker-supplied key such as:
- `../../etc/cron.d/pwn` → `path.Join` collapses `..` segments, letting the resulting `mkdir -p`/`printf ... >` write outside `TemporaryPath` (`b.TemporaryPath`, i.e. `build.TmpProjectDir()`), confined only by the job's OS-level file permissions (still a sandbox-confinement violation for shell/docker-executor jobs sharing a filesystem).
- `KEY$(id > /tmp/pwned)` or `` KEY`id`  `` → because the substring lands inside a double-quoted bash string via bare `%q` (not `b.escape`), bash performs command substitution when the generated script executes the `printf '%s' ... > "TMP/KEY$(id > /tmp/pwned)"` line, resulting in arbitrary command execution in the job's shell context.

The existing `isTmpFile`/`cleanPath` checks (shells/bash.go:215-227) only reason about *values* that already look like `TemporaryPath`-prefixed paths and do nothing to sanitize `Key` for the `File=true` branch. `b.escape` is bypassed entirely for the file-path component of `Variable()`.

### Impact Explanation
An unprivileged pipeline author who can define a `secrets:` block with a crafted key name can achieve command injection in the job's own shell execution (arbitrary command execution already available to a normal job author trivially via `script:`, so this alone is low novel value) or write files outside `TemporaryPath` via path traversal in the key. The traversal aspect is the more meaningful boundary violation: it lets a job write attacker-controlled secret-value content to paths outside the intended `TemporaryPath` sandbox on the executor's filesystem (e.g., shared-host shell executor, or a container filesystem shared across build/cleanup stages), which can affect cleanup logic, later stages of the same job, or persistent executor state if not fully torn down. The command-injection variant does not grant privilege beyond what a job author already has (they control `script:` execution), so the scoped/concrete impact is chiefly the **path-confinement bypass** of file-writes intended to stay under `TemporaryPath`.

### Likelihood Explanation
Reachable whenever a job defines a `secrets:` entry with `file: true` (or default, since default is file=true per common/secrets_test.go:85-98) and controls the key name of that entry. GitLab Rails' CI schema may constrain `secrets:` keys server-side, but Runner itself performs no independent validation of `variable.Key` before using it as a filesystem path component and format-string content — this is a missing defense-in-depth check inside Runner, exploitable by any path that can hand Runner a job payload with such a key (e.g., non-standard/self-hosted coordinators, or any future flow that doesn't enforce the same key-naming rule GitLab.com enforces).

### Recommendation
In `BashWriter.Variable` (and the equivalent `PsWriter.Variable`), validate `variable.Key` against a strict variable-name pattern (e.g., `^[A-Za-z_][A-Za-z0-9_]*$`) before using it to build `TmpFile(variable.Key)`, rejecting/sanitizing keys containing `/`, `..`, or shell metacharacters. Additionally, ensure the file-path literal is emitted through the same shell-safe escaping (`b.escape`) used for values/keys elsewhere, not bare `%q`, so that even if a malformed key slips through it cannot be interpreted as command substitution by bash.

### Proof of Concept
Go unit test extending `Test_BashWriter_Variable` in shells/bash_test.go:
```go
func Test_BashWriter_Variable_MaliciousKey(t *testing.T) {
    writer := BashWriter{TemporaryPath: "/tmp/build"}
    writer.Variable(spec.Variable{
        Key:   "KEY$(touch /tmp/pwned)",
        Value: "secret",
        File:  true,
    })
    out := writer.String()
    // Assert the generated script's file path/command does NOT contain
    // unescaped, executable $() sequences reachable outside quoting context.
    assert.NotContains(t, out, "$(touch /tmp/pwned)")

    writer2 := BashWriter{TemporaryPath: "/tmp/build"}
    writer2.Variable(spec.Variable{
        Key:   "../../etc/passwd_overwrite",
        Value: "secret",
        File:  true,
    })
    out2 := writer2.String()
    assert.True(t, strings.HasPrefix(extractPathFromPrintf(out2), "/tmp/build"),
        "file write path escaped TemporaryPath sandbox")
}
```
Expected (current) result: both assertions fail — the `$()` sequence is preserved verbatim in the double-quoted destination path, and the traversal key produces a path outside `/tmp/build`, confirming the bug.

```go
func (b *BashWriter) Variable(variable spec.Variable) {
	if variable.File {
		variableFile := b.TmpFile(variable.Key)
		b.Linef("mkdir -p %q", helpers.ToSlash(b.TemporaryPath))
		b.Linef("printf '%%s' %s > %q", b.escape(variable.Value), variableFile)
		b.Linef("export %s=%q", b.escape(variable.Key), variableFile)
	} else {
		if b.isTmpFile(variable.Value) {
			variable.Value = b.cleanPath(variable.Value)
		}
		b.Linef("export %s=%s", b.escape(variable.Key), b.escape(variable.Value))
	}
}
```
