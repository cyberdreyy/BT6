### Title
Unauthorized draining of lamports from any Uninitialized `bpf_loader_upgradeable` account via the `Close` instruction - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::Close` handler in the upgradeable BPF loader allows any transaction sender to drain the lamports of **any** account owned by `bpf_loader_upgradeable` that is currently in the `UpgradeableLoaderState::Uninitialized` state, to a recipient of their choosing, without any signature or authority check on the account being closed. This mirrors the reported bug class: an account that sits in an "uninitialized" window between creation and its intended initialization is not protected against takeover/abuse by an unrelated third party.

### Finding Description
In `process_loader_upgradeable_instruction`, the `Close` arm is dispatched based on the current state of the account being closed: [1](#0-0) 

For the `Buffer` and `ProgramData` branches, the code correctly resolves the account's `authority_address` and requires that authority to sign (via `common_close_account`, which performs signer/authority validation) before any lamports move. However, for the `UpgradeableLoaderState::Uninitialized` branch, the code performs **no signer check at all** on the account being closed (`instruction account 0`) and applies **no authorization check whatsoever** — it unconditionally transfers all of the account's lamports to whatever account is passed as instruction account 1 (the recipient), which also does not need to be a signer or otherwise privileged: [2](#0-1) 

The only guard present is that account 0 and account 1 must be different indices, which is enforced earlier: [3](#0-2) 

In normal usage, buffer/program-data accounts are created via `system_instruction::create_account` (owner = `bpf_loader_upgradeable`) and remain in the `Uninitialized` state until a subsequent instruction (`InitializeBuffer` or `DeployWithMaxDataLen`) sets their state. During that window — which is a separate, non-atomic transaction in typical client flows (e.g. `create_buffer` in `solana_loader_v3_interface`) — the account is loader-owned but has no established authority. Since a Solana transaction can reference any account pubkey as a non-signer, writable account without possessing its private key, any unrelated party can submit a transaction naming the victim's freshly-created (but not yet initialized) buffer/programdata account as instruction account 0 and themselves as instruction account 1, draining all of the rent-exempt lamports the victim just paid to create that account — with zero signature from the account owner and zero relationship to the account's intended controller.

This is directly analogous to the reported `subGauge` issue: an object that has been created but not yet initialized is left in a state where an unprivileged, unrelated actor can seize control of (or in this case, drain value from) it before the legitimate initializer's follow-up transaction executes.

### Impact Explanation
This allows unconditional, unsigned lamport theft from any `bpf_loader_upgradeable`-owned account sitting in the `Uninitialized` state (e.g., a buffer account created but not yet passed to `InitializeBuffer`, or a programdata account created but not yet passed to `DeployWithMaxDataLen`). The attacker needs no signature from the victim and pays only the transaction fee, making this a concrete, high-impact unsigned fund movement.

### Likelihood Explanation
Likelihood is high for any account creation flow that separates `CreateAccount` from `InitializeBuffer`/`DeployWithMaxDataLen` into different transactions (a common and even documented pattern for buffer accounts used in program deployment, given size/compute limits often require multiple transactions to fill a buffer before deployment). Any observer monitoring the mempool/confirmed transactions for such `CreateAccount` calls targeting `bpf_loader_upgradeable` can race to close the account before its intended initialization lands.

### Recommendation
Require the account being closed (instruction account 0) to be a signer, or otherwise validate an authority, in the `UpgradeableLoaderState::Uninitialized` branch of the `Close` handler in `programs/bpf_loader/src/lib.rs`, consistent with the authority checks already performed for the `Buffer` and `ProgramData` branches via `common_close_account`.

### Proof of Concept
1. Victim submits `system_instruction::create_account` creating account `B` with `owner = bpf_loader_upgradeable::id()`, funded with rent-exempt lamports, intending to call `InitializeBuffer` on `B` in a follow-up transaction.
2. Once `B`'s `CreateAccount` transaction is confirmed (and before the victim's `InitializeBuffer` transaction lands), `B`'s on-chain state is `UpgradeableLoaderState::Uninitialized`.
3. Attacker submits a transaction invoking `bpf_loader_upgradeable`'s `Close` instruction with:
   - account 0 = `B` (writable, non-signer — attacker does not have `B`'s private key)
   - account 1 = attacker's own wallet (recipient, non-signer)
4. In `process_loader_upgradeable_instruction`, `close_account.get_state()?` returns `Uninitialized`, so the code at [4](#0-3)  executes, adding all of `B`'s lamports to the attacker's account and zeroing `B`'s lamports — with no signature or authority check performed anywhere in this branch.
5. The victim's subsequent `InitializeBuffer` transaction fails or operates on a drained account, and the victim's rent-exempt deposit is stolen.
