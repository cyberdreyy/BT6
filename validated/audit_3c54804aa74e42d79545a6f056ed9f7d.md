### Title
Cache-volume "protected" isolation can be forged by cache key naming, letting an unprotected-ref job mount a protected-ref's cache volume - ([File: executors/docker/internal/volumes/manager.go])

### Summary
The Docker executor decides whether a cache volume gets the `-protected` suffix based on `e.Build.IsProtected() || protectedKeyIdx >= 0`, where `protectedKeyIdx` is found by scanning **user-controlled** `.gitlab-ci.yml` `cache.key` values for a `-protected` suffix. Because the resulting volume *name* is derived only from the project's `UniqueName` and an MD5 hash of the mount **destination path** — not from the ref, the actual cache key content, or protection status — an attacker running a job on an unprotected branch can set a cache key ending in `-protected` to force their own job to compute and mount the exact same volume name a legitimately protected-ref job would use for the same cache path.

### Finding Description
`createVolumesManager` in `executors/docker/volume.go` computes: [1](#0-0) 

`protectedKeyIdx` is derived purely from `e.Build.Cache[].Key`, a field fully controlled by whoever authors the `.gitlab-ci.yml` `cache:` block for the job (an unprivileged pipeline author). Setting `Protected: e.Build.IsProtected() || protectedKeyIdx >= 0` means a job on a non-protected ref can flip `config.Protected` to `true` simply by naming any cache key with a `-protected` suffix.

That `Protected` flag then flows into `createCacheVolume`: [2](#0-1) 

The volume name is `withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))`, where `name` is `m.config.UniqueName` (project-scoped, ref-independent — set from `e.Build.ProjectRealUniqueName()`) and `hashedDestination` is an MD5 hash of the mount destination path only: [3](#0-2) 

Crucially, the actual `cache.key` string an author picks (other than triggering the suffix check) never enters the hash — only the destination path does. So for the same project (`UniqueName`) and same cache mount path (e.g. the default `.cache`, `node_modules`, etc.), a legitimately protected-ref build and an attacker-controlled unprotected-ref build compute the identical `withProtected(...)` volume name once the attacker forces `Protected=true` via the cache-key-suffix trick. Docker `VolumeCreate` with an existing name is idempotent and simply returns the existing volume, so the attacker's job binds and reads/writes the *same* Docker volume that protected pipelines use to cache/persist data across builds.

The `-protected` suffix mechanism (referenced by comments and work item 494478) exists specifically to prevent unprotected-ref jobs from reusing a protected-ref's cache volume, since protected-ref jobs may populate that cache with content derived from protected CI/CD variables (e.g., built artifacts, dependency caches fetched using protected deploy tokens, or generated files containing secrets). The flaw is that the *decision to opt into the protected namespace* is trusted from attacker-controlled job configuration (`cache.key`) rather than solely from the runner/GitLab-verified `IsProtected()` ref status, defeating the isolation the suffix was designed to provide.

### Impact Explanation
An unprivileged pipeline author (anyone who can push a branch or open an MR without protected-branch privileges) can craft a job with a cache path matching one used by a protected-branch job and a cache key ending in `-protected`, causing their job to mount the same reusable Docker volume that a protected-ref job uses. This lets them:
- Read cached content written during protected-ref builds (potential secret/artifact disclosure) at that same runner's cache directory/volume.
- Write/poison that volume so a subsequent protected-ref build consumes attacker-controlled cached data, a supply-chain-style build poisoning within the same runner+project scope.

This is scoped to jobs sharing the same runner and project, since `UniqueName` is project-scoped, so it does not cross project boundaries, but it does break the "protected vs unprotected" isolation boundary that the `-protected` suffix is documented to enforce.

### Likelihood Explanation
Exploitation only requires the ability to define a job's `cache: key:` and `cache: paths:` in `.gitlab-ci.yml` on a non-protected branch/MR — no special runner or GitLab privileges are needed. It is deterministic and fully repeatable: same `UniqueName`, same cache path, same suffix condition always yields the same volume name.

### Recommendation
Do not let user-controlled cache-key strings influence the `Protected` decision for volume naming/isolation. Base the protected-volume suffix solely on `e.Build.IsProtected()` (server-verified ref protection), and if job-level opt-in into a "protected" cache namespace is desired, validate/authorize it against actual ref protection state rather than trusting the literal string suffix chosen by the pipeline author. At minimum, incorporate a value that an unprotected-ref job cannot forge (e.g., only ever append `-protected` when `IsProtected()` is true, regardless of `cache.key` content).

### Proof of Concept
Go unit test targeting `executors/docker/volume.go` `createVolumesManager` and `executors/docker/internal/volumes/manager.go` `createCacheVolume`:
```go
func TestProtectedCacheVolumeNameCollision(t *testing.T) {
    // Simulate protected-ref build
    protectedBuild := &common.Build{ /* ref marked protected */ }
    protectedCfg := volumes.ManagerConfig{
        UniqueName: "proj-uniq",
        Protected:  true, // from IsProtected()==true
    }

    // Simulate attacker unprotected-ref build with forged cache key
    attackerBuild := &common.Build{
        Cache: []spec.Cache{{Key: "anything-protected"}},
        // ref NOT protected -> IsProtected() == false
    }
    protectedKeyIdx := slices.IndexFunc(attackerBuild.Cache, func(c spec.Cache) bool {
        return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
    })
    attackerCfg := volumes.ManagerConfig{
        UniqueName: "proj-uniq", // same project/runner scope
        Protected:  attackerBuild.IsProtected() || protectedKeyIdx >= 0, // becomes true
    }

    destination := "/builds/project/.cache"

    protectedName := computeCacheVolumeName(protectedCfg, destination)
    attackerName := computeCacheVolumeName(attackerCfg, destination)

    assert.Equal(t, protectedName, attackerName,
        "attacker-controlled cache key forged the same protected volume name")
}
```
Expected assertion: `protectedName == attackerName`, demonstrating the attacker's unprotected job resolves to the identical Docker volume name as the protected build for the same destination path, confirming the isolation bypass. (`computeCacheVolumeName` mirrors the private logic in `createCacheVolume`; an integration-level PoC would instead run two real jobs — one on a protected branch, one on a feature branch with a forged `cache.key: foo-protected` and identical `cache.paths` — and assert via `docker volume inspect` that both bind to the same volume name/ID.)

var createVolumesManager = func(e *executor) (volumes.Manager, error) {
	// Note if any of the cache keys includes the `-protected` suffix (but not the `-non_protected` suffix).
	// See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
	protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
		return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
	})

	config := volumes.ManagerConfig{
		CacheDir:      e.Config.Docker.CacheDir,
		BasePath:      e.Build.FullProjectDir(),
		UniqueName:    e.Build.ProjectRealUniqueName(),
		TemporaryName: e.getProjectUniqRandomizedName(),
		DisableCache:  e.Config.Docker.DisableCache,
		Driver:        e.Config.Docker.VolumeDriver,
		DriverOpts:    e.Config.Docker.VolumeDriverOps,
		// the volume should be protected if the ref is protected OR if any of the cache volumes have the protected
		// suffix. See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
		Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
	}
