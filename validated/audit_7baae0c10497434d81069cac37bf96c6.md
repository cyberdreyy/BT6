### Title
TOCTOU on Keyring allowlist: credentials checked at request time, funds released at claim time without re-validation - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The SSRF report is a classic check-time-vs-use-time bug: an allowlist validation (DNS → IP) is resolved once, then the privileged action resolves the target independently. The credit-vault analog is the Keyring/KYC allowlist: `isWalletAllowed` is enforced only when a receipt is *created* (deposit / `requestWithdraw` / `requestInstantWithdraw` / queue `requestDeposit`/`requestWithdraw`), while every path that *pays out* underlying or tranche tokens (`claimWithdrawRequest`, `claimInstantWithdrawRequest`, `IdleCDOEpochQueue.claimWithdrawRequest`, `claimDepositRequest`, and `WriteOffEscrow.fullfillWriteOffRequest` for the buyer side) performs no re-validation. A user who passes KYC at request time can have the credential revoked (sanctions, fraud, `KeyringIdleWhitelist.setWhitelistStatus(entity, false)`) and still drain their claim, because the claim resolves entitlement from stale per-epoch storage rather than the live credential — exactly the TOCTOU shape of the report.

### Finding Description [1](#0-0) 

`isWalletAllowed` consults `IKeyring(keyring).checkCredential` at call time — i.e., it is a live external check, like the DNS resolution in the report.

It is invoked at request/entry points:
- `_deposit` (line 645)
- `depositDuringEpoch` (line 668)
- `requestWithdraw` (line 743)
- `requestInstantWithdraw` in the CDO wrapper and queue `_checkAllowed` (`contracts/IdleCDOEpochQueue.sol:415-420`)

But the corresponding payout functions — executed one or more epochs later — do not re-check: [2](#0-1) 

`claimWithdrawRequest()` and `claimInstantWithdrawRequest()` forward straight to `IdleCreditVault.claimWithdrawRequest(msg.sender)` / `claimInstantWithdrawRequest(msg.sender)`, which burn the user's receipt tokens and call `_transferFundedClaim` / `_transferDefaultRecovery` (`contracts/strategies/idle/IdleCreditVault.sol:301-393`) with no credential check anywhere on the path. The same gap exists in `IdleCDOEpochQueue.claimWithdrawRequest`/`claimDepositRequest` (`contracts/IdleCDOEpochQueue.sol:373-411`), which `safeTransfer` underlying/tranche tokens to `msg.sender` based solely on `userWithdrawalsEpochs`/`userDepositsEpochs` recorded earlier under a then-valid credential. The escrow test even encodes the asymmetry: a non-Keyring buyer receives tranche tokens via `fullfillWriteOffRequest` and is only blocked later at `requestWithdraw` — confirming the system intends KYC to gate value receipt, yet never enforces it on the claim side (`test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:247-293`).

The state used at "use time" (`withdrawsRequests`, `instantWithdrawsRequests`, `withdrawsRequestsByEpoch`, `epochWithdrawPrice`, `userWithdrawalsEpochs`) is frozen at check time; the authorization input (Keyring credential) is independently re-resolvable but is simply never re-resolved — the precise TOCTOU pattern.

### Impact Explanation
A KYC-passing lender (in-scope attacker class) creates withdraw receipts, gets de-credentialed by the honest Keyring admin or `KeyringIdleWhitelist.admin` (e.g., sanctions hit), and still calls `claimWithdrawRequest`/`claimInstantWithdrawRequest` (or queue `claimWithdrawRequest`) to receive underlying. The protocol's stated compliance boundary — only credentialed wallets may interact and receive funds — is violated for the entire withdrawal tail: an epoch in this design spans a full buffer + epoch duration, so the revocation window is large. Funds released are the attacker's own principal plus yield, so there is no direct theft from other LPs; the concrete loss is the protocol paying out to a sanctioned/de-whitelisted entity it explicitly intended to block, including APR0 interest and instant-withdraw liquidity that should have been frozen for that identity. Queue claims are additionally payable to an arbitrary `msg.sender` holding the epoch entitlement.

### Likelihood Explanation
Low-to-medium. Exploitation requires (a) a deployed `keyring`/`keyringPolicyId` (the intended configuration for these regulated credit vaults, per `IdleCreditVaultFactory` wiring `KeyringIdleWhitelist`), and (b) the user's credential being revoked between request and claim — an externally triggered but realistic event, since revocation is precisely what KYC infrastructure exists for. No privileged-role misbehavior, timing race, or oracle manipulation is needed; the claim path is permissionless once the receipt exists. Severity is capped because the attacker only recovers their own funds plus accrued interest, not third-party value.

### Recommendation
Re-validate `isWalletAllowed(msg.sender)` (or the credited beneficiary) inside `IdleCDOEpochVariant.claimWithdrawRequest` and `claimInstantWithdrawRequest`, and add `_checkWalletAllowed`-style gating (without the `isEpochRunning` requirement) to `IdleCDOEpochQueue.claimWithdrawRequest`, `claimDepositRequest`, and `WriteOffEscrow.fullfillWriteOffRequest` on the receiving side. If revoked users must still exit for legal reasons, gate claims behind an explicit guardian-approved escape rather than silently inheriting a stale credential.

### Proof of Concept
```solidity
// Foundry fork-style PoC sketch
// Setup: CDO epoch variant with keyring = KeyringIdleWhitelist, policyId = 1.
// Attacker: KYC-passing lender.

// 1. Buffer phase: user is whitelisted, deposits and requests withdraw.
keyringWhitelist.setWhitelistStatus(user, true);          // honest admin action
cdoEpoch.depositAA(100_000e6);                            // isWalletAllowed OK
cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche)); // isWalletAllowed OK

// 2. Epoch runs; borrower repays; manager stops epoch -> receipt funded.
//    Meanwhile admin revokes the user's credential (sanctions hit).
keyringWhitelist.setWhitelistStatus(user, false);         // honest admin action
assertFalse(cdoEpoch.isWalletAllowed(user));

// 3. Use-time: no re-check on the claim path.
vm.prank(user);
cdoEpoch.claimWithdrawRequest();                          // succeeds -> underlying to revoked user

// Expected (fix): revert NotAllowed.
// Actual: user receives full funded claim; same for claimInstantWithdrawRequest
// and queue.claimWithdrawRequest(epoch)/claimDepositRequest(epoch).
```
Pre-state: user holds a funded `withdrawsRequests` receipt from epoch N; `epochNumber > lastWithdrawRequest` so `_claimFundedWithdrawRequest` passes its only gate (`contracts/strategies/idle/IdleCreditVault.sol:326`). Post-state: `underlying.balanceOf(user)` increases by the claim amount while `isWalletAllowed(user) == false`, demonstrating the check-time/use-time divergence.
