### Title
Multisig executes requests using confirmations from removed members - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` removes a member and their own outstanding requests, but leaves that member's confirmations attached to requests created by *other* members untouched. A later `confirm` call by a still-legitimate member can then push the confirmation count over `num_confirmations`, executing the request with contributions from a member who is no longer part of the multisig.

### Finding Description
`confirm` in `multisig2/src/lib.rs` compares `confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) . The `confirmations` set is keyed only by `request_id` and stores member identity strings without any re-validation against current membership at execution time; `assert_valid_request` only checks that the *caller* is currently a member, not that prior entries in the confirmation set still are [2](#0-1) .

`delete_member` only purges requests where `r.member == member` (i.e., requests the removed member themselves created), removing `confirmations` and `requests` entries solely for those: `self.confirmations.remove(&request_id); self.requests.remove(&request_id);` inside that filtered loop [3](#0-2) . Any request created by *another* member that the now-deleted member had already confirmed retains that confirmation string in `self.confirmations`, since nothing iterates over all pending requests to strip the removed member's entry from their confirmation sets.

Consequently, the equality the contract is supposed to guarantee — "confirmations counted == approvals from live members" — is broken: `confirmations.len()` can include one or more confirmations from members who are no longer part of `self.members`.

### Impact Explanation
This is Critical impact under "a multisig request executed below threshold": an arbitrary request (fund transfer, key addition, `FunctionCall`, etc.) can be executed with fewer live-member approvals than `num_confirmations` requires, because a stale confirmation from a removed/compromised member is silently counted as if it were still valid. This defeats the entire security assumption of the multisig — that `num_confirmations` *current* trusted parties signed off before any action executes.

### Likelihood Explanation
Likelihood is high in realistic operational scenarios: removing a member (e.g., because a key was compromised or an employee departed) is a normal multisig lifecycle event, and it is common for a compromised/departing member to have already confirmed some pending request before being removed. No special privileges beyond normal multisig usage are required to trigger the bug — the flaw is in the member-removal bookkeeping itself, not in any attacker-supplied malicious input.

### Recommendation
When executing `DeleteMember`, iterate over all pending requests' confirmation sets (not only requests created by the removed member) and remove the deleted member's entry from each. Alternatively, at `confirm`-time, filter `confirmations` to only those entries whose member is still `self.members.contains(...)` before comparing the count against `num_confirmations`, so stale approvals from removed members never count toward execution.

### Proof of Concept
1. Deploy `multisig2` with members `A, B, C, D` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R)` where `R` is a malicious `Transfer` request — `confirmations(R) = {A}` (1/3) [4](#0-3) .
3. `C` calls `confirm(R)` — `confirmations(R) = {A, C}` (2/3, still pending, stored via the `else` branch) [5](#0-4) .
4. The organization discovers `C`'s key is compromised and executes a separate `DeleteMember { member: C }` request (approved by `A, B, D`). `delete_member` removes `C` from `self.members` and deletes any requests `C` created, but request `R` (created by `A`) is untouched, so `confirmations(R)` still contains `{A, C}` [6](#0-5) .
5. `B` calls `confirm(R)` — `confirmations.len() + 1 == 3 >= num_confirmations`, so `R` executes immediately [7](#0-6) , even though only `A` and `B` are currently live members who approved it; `C`'s stale, now-invalid confirmation was decisive in reaching the threshold.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
