## Analog found

The reported pattern — a strict `>`/`<` timestamp comparison that should have been `>=`/`<=`, letting an ordinary user land a transaction exactly on the boundary timestamp to dodge an intended fee — has a structural analog in `ProvisionerV2.cancelRequest`. [1](#0-0) 

### Title
Off-by-one boundary mismatch between `cancelRequest`'s fee condition (`block.timestamp < request.deadline`) and the solve path's liveness condition (`request.deadline >= block.timestamp`) lets a user skip the cancellation fee on a still-"active" request - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`cancelRequest` only charges the pre-deadline cancellation fee while `block.timestamp < request.deadline`, so at the exact instant `block.timestamp == request.deadline` the fee is skipped entirely. However, the solve paths (`_solveDepositVaultAutoPrice`, `_solveDepositVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, `_solveRedeemVaultFixedPrice`, `_solveRequestDirect`) all treat the request as still solvable/"active" whenever `request.deadline >= block.timestamp` — i.e., including the equality instant. This means at `t == deadline` the request is simultaneously "active" for solving purposes yet exempt from the cancellation fee that is supposed to apply to active requests.

### Finding Description
Because `deadline` is a user-supplied parameter validated only by `_validateRequest` (`deadline > block.timestamp` at creation time, capped by `MAX_SECONDS_TO_DEADLINE`), the requester fully controls the boundary value. [2](#0-1) 

The fee-applicability guard in `cancelRequest` is:
```solidity
if (block.timestamp < request.deadline) { ... apply cancellationFee ... }
``` [3](#0-2) [4](#0-3) 

while every solve path checks the opposite boundary as still-live:
```solidity
if (request.deadline >= block.timestamp) { ... process normally ... }
``` [5](#0-4) [6](#0-5) 

At `block.timestamp == request.deadline`, the request is classified as active/solvable by every solve function, yet `cancelRequest` treats it as if the pre-deadline window has already closed, waiving the fee. A user can deposit/redeem-request with a self-chosen `deadline`, then submit `cancelRequest` in the exact block whose timestamp equals that deadline (deadlines are chosen in whole seconds and Ethereum PoS slots are fixed 12-second intervals, making this reliably targetable), collecting a full refund with zero cancellation fee.

### Impact Explanation
The cancellation fee (paid to `MULTI_DEPOSITOR_VAULT` for deposits, or burned as escrowed units for redeems) is meant to be a donation/penalty benefiting the vault's remaining unit holders whenever a user self-cancels while their request is still live and solvable. [7](#0-6) [8](#0-7) 
By exploiting the boundary mismatch, an ordinary requester escapes this fee, resulting in a loss of expected fee-derived value to other unit holders — the same broken-invariant category as the referenced report (forgone fee revenue that should have accrued to remaining stakers).

### Likelihood Explanation
The requester needs no privileged role. The only preconditions are: (1) deposit or redeem cancellations enabled (`_depositCancellationsEnabled` / `_redeemCancellationsEnabled`, a normal operating configuration for a live vault supporting this feature), and (2) the ability to submit a transaction whose block timestamp exactly equals a `deadline` the user chose at request time. Since the user picks `deadline` and Ethereum block timestamps advance in fixed slots, this is deterministically achievable, not probabilistic.

### Recommendation
Align the fee-applicability check in `cancelRequest` with the solve paths' liveness definition, e.g. change `if (block.timestamp < request.deadline)` to `if (block.timestamp <= request.deadline)` (or equivalently express both as `request.deadline >= block.timestamp` consistently), so the fee applies for the entire window the request is still considered solvable.

### Proof of Concept
1. Fork mainnet with the deployed `ProvisionerV2`/`MultiDepositorVault`; ensure `_redeemCancellationsEnabled` (or deposit equivalent) and a non-zero `_redeemCancellationFeeNumeraire`/`_depositCancellationFeeNumeraire` are configured.
2. As an ordinary user, call `requestRedeem`/`requestDeposit` with `deadline = block.timestamp + N` for a chosen small `N`.
3. Warp the fork so `vm.warp(deadline)` exactly.
4. Call `cancelRequest` with the matching `RequestV2`; assert `cancellationFee == 0` was applied (full `refundAmount` returned) via emitted `RedeemRefunded`/`DepositRefunded` and balance deltas.
5. In a second scenario, call one of the solve functions (`_solveRedeemVaultFixedPrice`, etc.) at the same `block.timestamp == deadline` for an identical request and confirm it takes the "active" branch (`request.deadline >= block.timestamp`), proving the request was still classified as live — demonstrating the inconsistency directly caused the fee bypass.

    function cancelRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: self-cancel caller must be request user
        require(msg.sender == request.user, Aera__CallerIsNotRequestUser());

        if (_isRequestTypeDeposit(request.requestType)) {
            // Requirements: deposit cancellation toggle must be enabled
            require(_depositCancellationsEnabled, Aera__DepositRequestCancellationDisabled());

            uint256 refundAmount = request.tokens;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeDepositCancellationFeeTokens(token);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;
                    }
                    // Interactions: transfer cancellation fee to vault
                    token.safeTransfer(MULTI_DEPOSITOR_VAULT, cancellationFee);
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net token amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token);
        } else {
            // Requirements: redeem cancellation toggle must be enabled
            require(_redeemCancellationsEnabled, Aera__RedeemRequestCancellationDisabled());

            // Interactions: compute redeem request size in numeraire with protocol-favoring rounding
            uint256 requestNumeraire = PRICE_FEE_CALCULATOR.convertUnitsToNumeraire(
                MULTI_DEPOSITOR_VAULT, request.units, Math.Rounding.Ceil
            );
            // Requirements: redeem self-cancel must not exceed configured cap
            require(requestNumeraire <= _redeemCancellationCapNumeraire, Aera__RequestAmountExceedsRefundCap());

            uint256 refundAmount = request.units;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeRedeemCancellationFeeUnits(requestNumeraire);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;
                    }
                    // Interactions: burn cancellation fee units from provisioner escrow
                    IMultiDepositorVault(MULTI_DEPOSITOR_VAULT)
                        .exit(address(this), token, 0, cancellationFee, address(this));
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net unit amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, IERC20(MULTI_DEPOSITOR_VAULT));
        }

    function _validateRequest(address receiver, uint256 solverTip, uint256 deadline, bool isFixedPrice) internal view {
        // Requirements: receiver is not zero address
        require(receiver != address(0), Aera__ZeroAddressReceiver());
        // Requirements: deadline is in the future and not too far in the future
        require(deadline > block.timestamp, Aera__DeadlineInPast());
        unchecked {
            require(deadline - block.timestamp <= MAX_SECONDS_TO_DEADLINE, Aera__DeadlineTooFarInFuture());
