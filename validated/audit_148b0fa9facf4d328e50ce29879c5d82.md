### Title
Instant-withdraw claims pay the all-epochs aggregate at par, letting an unclaimed old receipt plus a fresh unfunded request drain funds reserved for other users' withdrawals - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` records each request per-epoch in `instantWithdrawsRequestsByEpoch[user][epochNumber]` while funding arrives per-epoch through `collectInstantWithdrawFunds` (which only decrements the global `pendingInstantWithdraws`). However, `claimInstantWithdrawRequest` pays the cross-epoch aggregate `instantWithdrawsRequests[_user]` at par, with no check that the current-epoch tranche of the receipt was ever funded. An attacker can open a new instant-withdraw request while the strategy still holds underlying collected for other users' funded claims, then claim the full aggregate, spending funds that belong to other receipt holders (wrong-slot-write / boundary analog: the write lands in epoch slot M, but the read path pays slot M using funds collected for slot N).

### Finding Description
In `IdleCreditVault.requestInstantWithdraw` (IdleCreditVault.sol:356-375), a new instant request mints receipt strategy tokens to the user and increments both `instantWithdrawsRequests[_user]` (aggregate) and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` plus `pendingInstantWithdraws`. Funding is strictly per-epoch: `collectInstantWithdrawFunds` (IdleCreditVault.sol:398-403) pulls exactly `_amount` from the CDO and reduces `pendingInstantWithdraws`, so at any moment the strategy's underlying balance is only guaranteed to cover already-funded receipts (normal withdraw claims paid via `_transferFundedClaim` sit in the same balance).

`claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) ignores the per-epoch accounting entirely:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` only avoids spending `defaultRecoveryReserve`; it does not verify that this user's receipt was funded. So a user who requests an instant withdraw in epoch M — before `stopEpoch`/`collectInstantWithdrawFunds` funds epoch-M `pendingInstantWithdraws` — can immediately claim and be paid out of underlying collected for epoch-M normal withdraw requests (`collectWithdrawFunds`) or other users' funded instant receipts.

The per-epoch write (`instantWithdrawsRequestsByEpoch`) is only consulted on the default path (`_claimDefaultedInstantWithdrawRequest`); on the happy path the code writes the request into the new epoch slot but settles it against the aggregate, which is exactly the "index/write lands out of bounds of the funded region" shape of the ICC buffer overflow.

### Impact Explanation
- An attacker with a KYC'd wallet requests an instant withdraw of amount X during a running epoch (epoch M), when the strategy is holding underlying collected at the last `stopEpoch` for epoch-(M-1) funded withdraw claims.
- `claimInstantWithdrawRequest` pays X to the attacker immediately, reducing the strategy balance that backs other users' funded claims and `pendingWithdraws`-backed receipts.
- When those users later call `claimWithdrawRequest`, their transfers revert for lack of balance → temporary freezing of funded claims; if epoch-M collection never materializes (e.g., pool defaults/loss before funding), the shortfall becomes permanent and is effectively socialized onto the remaining claimants — a broken "one funded receipt, one funded payout" invariant.
- Quantified: up to `min(attacker request size, strategy underlying balance held for funded claims)` — the attacker is bounded only by their tranche position value.

### Likelihood Explanation
- Attacker needs only to be a tranche holder with KYC (in-scope role) and sufficient tranche balance; no privileged action required. Honest roles (manager/queue/owner) calling `stopEpoch`/`collectInstantWithdrawFunds` on their normal schedule create the funded-reserve window.
- Preconditions: the pool must accept instant withdraws in a running epoch and hold non-trivial collected underlying at the time of the request. This holds whenever funded normal or instant receipts remain unclaimed — a common steady state.
- Uncertainty: whether `IdleCDOEpochVariant.claimInstantWithdrawRequest` adds its own gating (e.g., only allowing claims after funding) could not be fully verified within this session; if the CDO blocks claims while `pendingInstantWithdraws` is unfunded for the user, severity drops to bookkeeping drift rather than theft.

### Recommendation
- Settle instant claims per funded epoch instead of by aggregate: pay only `instantWithdrawsRequestsByEpoch[_user][e]` for epochs `e` whose funds were collected, or track a per-user funded amount incremented in `collectInstantWithdrawFunds` pro-rata.
- Alternatively, gate `claimInstantWithdrawRequest` so a request made in `epochNumber` cannot be claimed until that epoch's instant bucket has been collected (mirroring the `epochNumber <= lastWithdrawRequest` check used for normal claims), and decrement `instantWithdrawClaimsByEpoch`/the by-epoch slot on claim to keep aggregate and per-epoch views consistent.

### Proof of Concept
Foundry fork sketch (structure; adapt helpers from `test/foundry/IdleCreditVault.t.sol`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.17;

function testInstantClaimDrainsFundedReserve() external {
    // Setup: victim deposits AA, requests a normal withdraw in epoch 0.
    address victim = makeAddr("victim");
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // normal request

    // Epoch 0 stop collects pendingWithdraws into the strategy (funded, unclaimed).
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    // strategy now holds underlying reserved for victim's funded claim.

    // Attacker (KYC'd tranche holder) deposits and opens an INSTANT withdraw
    // request in the new running epoch 1 - this amount is NOT yet collected.
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 5_000 * ONE_SCALE, true);
    uint256 attackAmt = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(attackAmt, address(AAtranche)); // epoch 1, unfunded

    // BUG: claim pays the aggregate at par from strategy balance
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = underlying.balanceOf(attacker) - pre;
    assertGt(stolen, 0);

    // Victim's funded claim now underflows the strategy balance
    vm.prank(victim);
    vm.expectRevert(); // ERC20 transfer insufficient balance
    cdoEpoch.claimWithdrawRequest();
}
```

Note: this PoC assumes `requestInstantWithdraw`/`claimInstantWithdrawRequest` on the CDO do not themselves require the epoch's instant bucket to be funded; verify those CDO-side guards when reproducing.
