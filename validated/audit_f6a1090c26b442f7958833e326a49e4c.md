### Title
Stale confirmations from deleted keys still count toward `num_confirmations`, allowing execution of a fund-transfer request below live-key quorum - (`multisig/src/lib.rs`)

### Summary
The `DeleteKey` action in `execute_request` only purges pending requests whose *creator* (`signer_pk`) matches the deleted key; it never scans other outstanding requests for *confirmations* that were previously cast by that key. A confirmation recorded by a key that is later removed remains in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map and keeps counting toward `num_confirmations`, letting a request with `receiver_id` set to an outside account execute with fewer genuinely live keys than the policy requires.

### Finding Description
The broken invariant, stated as an equality, is:
`confirmations_counted_at_execution == confirmations_from_currently_live_access_keys`

The code never enforces this. `confirm()` only checks that the *current* signer hasn't already confirmed and that the request/confirmations entries exist: [1](#0-0) 

`assert_valid_request` only checks `predecessor_account_id == current_account_id` (any access key on the account) and that the request/confirmation entries exist — it does not validate that every public key already present in the stored `confirmations` `HashSet<PublicKey>` still exists as an access key on the account: [2](#0-1) 

The only place confirmations are ever purged for a deleted key is inside the `DeleteKey` branch of `execute_request`, and it filters by the *request's original signer* (`r.signer_pk == pk`), not by whether `pk` appears in the confirmation set of *other* requests: [3](#0-2) 

**Exploit flow:**
1. A key holder (`K_attacker`) — one of the account's legitimate access keys per the entrypoint model ("any access key on the multisig account") — uses `add_request`/`add_request_and_confirm` to create a request `R` with `receiver_id` set to an account outside the multisig (e.g. `Transfer { amount }` to an attacker-controlled account). Since the action is `Transfer`, `assert_self_request` is never invoked, so `receiver_id` can be anything. `K_attacker` confirms `R`, adding its own pubkey to `confirmations[R]`.
2. At some later point, the account's remaining owners rotate/remove `K_attacker` via a separate `DeleteKey { public_key: K_attacker }` request. Since `R`'s `signer_pk` is not `K_attacker` (it was created by a different key, or `K_attacker` only confirmed but did not create it), the cleanup loop in the `DeleteKey` branch does not touch `R` or its confirmation set — `K_attacker`'s stale confirmation on `R` survives.
3. Two (or `num_confirmations - 1`) genuinely live keys subsequently confirm `R` for unrelated, legitimate reasons. When the last live confirmation is added, `confirmations.len() + 1 >= num_confirmations` becomes true, and `execute_request` fires the `Transfer` — even though only `num_confirmations - 1` currently-valid keys ever confirmed it.

This directly moves funds out of the multisig account to an outside `receiver_id` while only meeting quorum by counting a confirmation from a key that no longer exists on the account, breaking "confirmations from removed keys never count" and "a multisig request executed below `num_confirmations` live members."

### Impact Explanation
NEAR is transferred out of the multisig account via `Promise::transfer` in `execute_request` without the account ever having achieved the configured live-key quorum. This is exactly the Critical category "a multisig request executed below `num_confirmations` live members," resulting in unauthorized movement of the account's funds. The bug is repeatable for any pending request that a key confirmed before being removed, and for any multisig account regardless of `num_confirmations` setting, as long as at least one request exists that was confirmed-but-not-created by the key being deleted.

### Likelihood Explanation
The precondition is common in normal multisig lifecycle usage: a key holder confirms a request, and later that same key is rotated out (lost device, compromised key, personnel change) via `DeleteKey`, while the originally confirmed request is still pending (has not yet reached quorum). No special privilege beyond already holding one of the account's access keys is required — the entrypoint itself only checks `predecessor_account_id == current_account_id`, which any key on the account satisfies. Because `DeleteKey` cleanup is keyed off request authorship rather than confirmation membership, this stale-confirmation state arises from ordinary key-rotation operations, not just adversarial timing, making the flaw highly likely to be triggered accidentally or exploited deliberately.

### Recommendation
When executing `DeleteKey { public_key }`, iterate over all entries in `self.confirmations` (not just requests where `signer_pk == pk`) and remove `pk` from every confirmation set; additionally, re-check whether removing `pk` should also reduce/recount confirmations that already reached quorum but not yet executed. Alternatively, validate at `confirm()`/execution time that all keys present in the stored confirmation set for the request are still valid access keys on the account (e.g., checking against `num_requests_pk` or an explicit live-key registry) before counting them toward `num_confirmations`.

### Proof of Concept
```rust
// multisig/src/lib.rs test module
#[test]
fn test_stale_confirmation_after_delete_key_counts_toward_quorum() {
    let amount = 1_000;
    let key_a = Base58PublicKey::try_from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy").unwrap().into();
    let key_b = Base58PublicKey::try_from("HghiythFFPjVXwc9BLNi8uqFmfQc1DWFrJQ4nE6ANo7R").unwrap().into();
    let key_c = Base58PublicKey::try_from("2EfbwnQHPBWQKbNczLiVznFghh9qs716QT71zN6L1D95").unwrap().into();

    // num_confirmations = 3
    testing_env!(context_with_key(key_a.clone(), amount));
    let mut c = MultiSigContract::new(3);

    // key_a creates the attack request: transfer to an outside account (bob)
    let attack_request = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let request_id = c.add_request(attack_request.clone());

    // key_b confirms it (this is the key that will be revoked afterward)
    testing_env!(context_with_key(key_b.clone(), amount));
    c.confirm(request_id);
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 1);

    // key_a now creates+confirms a DeleteKey request to revoke key_b
    testing_env!(context_with_key(key_a.clone(), amount));
    let delete_key_request = MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteKey { public_key: key_b.clone() }],
    };
    c.add_request_and_confirm(delete_key_request); // num_confirmations for delete request path may need matching quorum; use new(1) if isolating this check

    // EQUALITY CHECK: key_b's stale confirmation on `request_id` should have been purged, but is NOT
    assert!(
        c.confirmations.get(&request_id).unwrap().contains(&key_b),
        "BUG: stale confirmation from deleted key_b still present"
    );

    // Two more live keys (key_a, key_c) confirm -> total confirmations reach 3,
    // but only key_a and key_c are actually live -> quorum of 3 met with 2 live keys.
    testing_env!(context_with_key(key_a.clone(), amount));
    c.confirm(request_id); // now len == 2 (key_b stale + key_a)
    testing_env!(context_with_key(key_c.clone(), amount));
    c.confirm(request_id); // reaches 3 -> execute_request fires Transfer to bob

    assert_eq!(c.requests.len(), 0); // request executed despite only 2 live confirmers
}
```
Run with `cargo test -p multisig test_stale_confirmation_after_delete_key_counts_toward_quorum`. The test demonstrates `confirmations_counted_at_execution (3) != confirmations_from_currently_live_access_keys (2)`, confirming the invariant break and unauthorized execution of the outside `Transfer`.
