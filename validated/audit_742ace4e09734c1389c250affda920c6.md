### Title
Stale per-epoch instant-withdraw receipts inflate default claim basis and fabricate recovery reserve, diluting and insolventing post-default payouts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2017-11714 mishandled references to scanner state, leaving stale pointers that produced out-of-bounds reads. The analog in `IdleCreditVault` is stale per-epoch receipt references: `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]` for already-paid receipts. If that same `epochNumber` later defaults, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read those stale entries as if the funds were still owed and still held, inflating `totalBasis` with phantom claims and counting already-distributed underlying as "prefunded reserve".

### Finding Description
In `requestInstantWithdraw`, each request records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (lines 371-372). When the CDO funds the request via `collectInstantWithdrawFunds`, `pendingInstantWithdraws` decreases (line 401). `claimInstantWithdrawRequest` (lines 380-393) then pays the user and zeroes only `instantWithdrawsRequests[_user]` — the two per-epoch mappings are never touched on the funded path:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
// instantWithdrawsRequestsByEpoch / instantWithdrawClaimsByEpoch NOT cleared
```

Later, if the epoch in which those receipts were recorded defaults and `finalizeDefaultRecovery` runs while `defaultRecoveryEpoch == epochNumber`, two correlated errors occur:

1. `defaultPendingClaimBasis()` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes already-paid receipts, inflating `pendingBasis`/`totalBasis` and depressing `defaultRecoveryPrice` for every genuine claimant (line 688).
2. `_defaultPrefundedInstantReserve()` (lines 716-723) computes `instantBasis - pendingInstant` and adds it to `reserveAmount` (line 686). The claimed portion of `instantBasis` was already transferred out, so the strategy accounts for reserve it does not hold — a phantom reserve baked into `defaultRecoveryReserve`.

The comment at lines 637-640 confirms the intent is "current-epoch pending instant receipts"; already-claimed receipts are not pending, so reading them is a stale-state bug, not intended accounting.

### Impact Explanation
- **Recovery dilution (theft-by-pricing):** `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`. Phantom basis pushes `recoveryPrice` below the ratio implied by real funds, so every legitimate defaulted-epoch and funded receipt is underpaid pro rata to the stale amount.
- **Insolvency / permanent freezing:** `reserveAmount` counts underlying that was already paid out. Claims are paid via `_transferDefaultRecovery`, which debits `defaultRecoveryReserve`; because the real balance is short by the phantom amount, the last claimants' transfers revert or the reserve runs dry, permanently freezing part of the recovery.
- Quantified example: user A requests and is paid 100e6 USDC instant in epoch N; user B requests 50e6 still pending; epoch N defaults with recovered amount R. `instantBasis` reads 150e6 instead of 50e6; `prefundedReserve` reads 100e6 of nonexistent funds. `totalBasis` is inflated by 100e6, cutting every claimant's price by `paidBasis/(realBasis+paidBasis)`, and the reserve is short exactly 100e6.

### Likelihood Explanation
Reachable by any unprivileged user (no privileged role needed): request an instant withdraw during the epoch that later defaults, have it funded and claim it, while at least one other instant receipt remains unfunded (`pendingInstantWithdraws != 0` is required for `defaultInstantWithdrawsFinalized`, line 696). Whether the CDO allows collect-and-claim inside the same `epochNumber` is the one step I could not fully verify from `IdleCDOEpochVariant.sol` (index snippet truncated); if instant funding only occurs at `stopEpoch`, `epochNumber` would already have rolled, breaking the epoch-key alignment and downgrading this to a latent accounting inconsistency rather than an exploitable hole.

### Recommendation
In `claimInstantWithdrawRequest`, clear the stale references before paying: delete `instantWithdrawsRequestsByEpoch[_user]` entries for each request epoch the user claimed in (track the epoch in the request record, or iterate/reset when `instantWithdrawsRequests[_user]` is fully paid), and decrement `instantWithdrawClaimsByEpoch[epoch]` by the paid amount. Alternatively, snapshot each instant request's epoch in a per-user field so `_claimDefaultedInstantWithdrawRequest` and `defaultPendingClaimBasis` can exclude already-claimed receipts.

### Proof of Concept
Foundry fork sketch (instant-mode vault):

```solidity
// epoch N running, instant withdraws enabled
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(100e6, AAtranche);      // instantWithdrawClaimsByEpoch[N] = 100e6
// borrower/CDO funds it
vm.prank(address(cdoEpoch));
strategy.collectInstantWithdrawFunds(100e6);            // pendingInstantWithdraws -> 0
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();                 // paid; stale per-epoch entries remain
// victim requests 50e6 instant, stays unfunded
vm.prank(victim);
cdoEpoch.requestInstantWithdraw(50e6, AAtranche);       // instantWithdrawClaimsByEpoch[N] = 150e6, pending = 50e6
// borrower repays nothing -> default, then finalize
_stopEpochWithDefault();
cdoEpoch.finalizeDefault(recovered, recoverySource);    // basis includes stale 100e6; reserve += phantom 100e6
vm.prank(victim);
cdoEpoch.claimInstantWithdrawRequest();                 // underpaid vs pro-rata share
// later claimants' _transferDefaultRecovery reverts / reserve exhausted
```

Assertions: `strategy.instantWithdrawClaimsByEpoch(N)` still equals 150e6 after the attacker was paid (stale read), `defaultRecoveryPrice` is lower than `realReserve/realBasis`, and final recovery claims consume more than the strategy's actual underlying balance.
