### Title

Temporary freezing of LP funds through ERC4626 liquidity exhaustion in `ProgrammableBorrower.onStopEpoch` - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary

An unprivileged user of the programmable borrower’s ERC4626 vault can temporarily freeze all credit-vault funds by exhausting the vault’s available underlying liquidity immediately before `IdleCDOEpochVariant.stopEpoch` is called.

`ProgrammableBorrower.onStopEpoch` treats `vault.convertToAssets(shares)` as proof that a withdrawal is covered, but it does not check `vault.maxWithdraw(address(this))` or otherwise confirm that the ERC4626 vault currently has enough redeemable liquidity. If the position is economically backed but temporarily cannot withdraw the required amount, `vault.withdraw` reverts and `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, leaving the epoch running and LP withdrawals unavailable.

### Finding Description

During a running programmable-borrower epoch, `IdleCDOEpochVariant._stopEpoch` calls `onStopEpoch` before attempting to pull borrower funds. The requested amount is `_amountToPullFromBorrower + _pendingWithdraws`. [1](#0-0) 

`ProgrammableBorrower.onStopEpoch` calculates the shortfall and compares it with `_currentVaultAssets()`, which is only `vault.convertToAssets(vault.balanceOf(address(this)))`. This measures the position’s accounting value, not currently withdrawable liquidity. [2](#0-1) [3](#0-2) 

If `convertToAssets` reports sufficient value but the ERC4626 vault’s liquid asset balance or withdrawal queue cannot satisfy the withdrawal, `vault.withdraw` reverts. The catch block then reverts `StopEpochVaultLiquidityUnavailable`, so `stopEpoch` aborts without setting `isEpochRunning` false. [4](#0-3) 

Withdrawal requests are disabled while the epoch is running, and `requestWithdraw` cannot be used to exit the active epoch. Therefore, an attacker who repeatedly front-runs `stopEpoch` and keeps the configured ERC4626 vault short on immediate liquidity can keep the epoch from ending. [5](#0-4) [6](#0-5) 

This is distinct from an insolvency check: the attack works when the programmable borrower’s vault shares remain fully backed according to `convertToAssets`, but the vault temporarily lacks withdrawable underlying.

### Impact Explanation

The affected funds are the programmable borrower facility’s active LP principal and pending withdrawal obligations.

Because `stopEpoch` reverts, `isEpochRunning` remains true. Withdrawal requests remain disabled, deposits remain paused, and LP funds remain locked in the programmable borrower’s vault position. In a close-pool call, the requested amount can be the entire recalled strategy balance plus pending withdrawals. [7](#0-6) 

The attack requires maintaining or repeatedly recreating ERC4626 liquidity exhaustion around manager stop transactions, so the impact is temporary freezing rather than theft. The frozen amount can equal the facility’s full vault position.

### Likelihood Explanation

The attacker only needs to be a user of the configured ERC4626 vault or an actor capable of reducing its immediately withdrawable liquidity through ordinary vault market operations. No privileged Idle role, malicious borrower, oracle manipulation, or invalid contract upgrade is required.

The conditions are:

1. The vault is configured for programmable-borrower mode.
2. An epoch is running and `epochEndDate` has passed.
3. The programmable borrower must withdraw underlying from the ERC4626 vault to satisfy the stop amount.
4. The vault’s `convertToAssets` value covers the shortfall, but its currently withdrawable liquidity does not.
5. The attacker can maintain or repeatedly restore that liquidity shortage when the honest manager retries.

The current code explicitly expects transient ERC4626 withdrawal failures, but retryability does not prevent an attacker from repeatedly recreating the shortage. [8](#0-7) 

### Recommendation

`onStopEpoch` should distinguish accounting value from withdrawable liquidity.

At minimum, use the ERC4626 liquidity preview:

```solidity
uint256 maxWithdrawable = vault.maxWithdraw(address(this));
if (shortfall > maxWithdrawable) {
    // Use an explicit liquidity-unavailable/default path rather than relying on
    // convertToAssets plus a reverting withdraw.
}
```

Depending on the intended risk model, either:

- expose a manager-controlled path that defaults only on confirmed borrower insolvency while preserving retryable vault-liquidity failures; or
- allow partial withdrawals up to `maxWithdraw(address(this))`, combine them with on-hand liquidity, and return a structured result to `IdleCDOEpochVariant`; and
- make the CDO record a bounded retry window so a third-party vault cannot keep the epoch open indefinitely without an explicit operator decision.

A partial-withdrawal implementation must update `epochWithdrawnFromVault` by the amount actually received, not by the originally requested `shortfall`.

### Proof of Concept

The following Foundry-style test demonstrates the broken invariant with a public ERC4626 vault that is fully backed but temporarily lacks withdrawable liquidity.

```solidity
function testVaultLiquidityExhaustionKeepsEpochRunning() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 pendingAmount = 1_000 * ONE_SCALE;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // Create a normal pending withdrawal in the preceding buffer, then start
    // the epoch being attacked. In the deployed test setup this can use the
    // existing request/start helpers.
    cdoEpoch.requestWithdraw(pendingAmount, address(aaTranche));

    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 required =
        strategy.pendingWithdraws();

    uint256 onHand = underlying.balanceOf(address(programmableBorrower));
    uint256 shortfall = required - onHand;

    uint256 shares = morphoVault.balanceOf(address(programmableBorrower));
    uint256 accountedAssets = morphoVault.convertToAssets(shares);

    // The position remains solvent and convertToAssets covers the shortfall.
    assertGe(accountedAssets, shortfall);

    // An unprivileged ERC4626 vault user/borrower drains the vault's immediate
    // liquidity through ordinary vault/Morpho operations before stopEpoch.
    _drainVaultLiquidityLeavingSolventShares(
        address(morphoVault),
        morphoVault.maxWithdraw(address(programmableBorrower))
    );

    assertLt(
        morphoVault.maxWithdraw(address(programmableBorrower)),
        shortfall,
        "vault liquidity still available"
    );

    vm.prank(manager);
    vm.expectRevert(
        ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector
    );
    cdoEpoch.stopEpoch(0, 0);

    // The epoch is not stopped and user exits remain unavailable.
    assertTrue(cdoEpoch.isEpochRunning(), "epoch unexpectedly stopped");
    assertFalse(cdoEpoch.defaulted(), "liquidity failure became default");

    vm.prank(address(this));
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.requestWithdraw(0, address(aaTranche));
}
```

The concrete `_drainVaultLiquidityLeavingSolventShares` implementation depends on the configured ERC4626 integration. For a Morpho-style deployment it can withdraw/redeem available liquidity or open a sufficiently collateralized market borrow that consumes the vault’s idle asset balance. The key assertion is that `convertToAssets` still covers the shortfall while `maxWithdraw` does not, proving that the failure is liquidity exhaustion rather than loss of backing.
