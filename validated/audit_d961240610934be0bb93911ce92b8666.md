### Title
Unsanitized cache key reaches `AlternateKey`/`--alternate-file` path when `FF_HASH_CACHE_KEYS` is enabled, allowing path traversal outside `CacheDir` - (File: functions/concrete/builder/builder.go, functions/concrete/run/stages/cache_archive.go)

### Summary
`builder.cacheKey` only runs `cachekey.Sanitize` on the cache key when `FF_HASH_CACHE_KEYS` is off; when the flag is on, `humanKey` is the raw, unsanitized, variable-expanded `cache.key`. `buildCacheArchive`'s `alternateResolved` computation uses this raw `humanKey` verbatim as `stages.CacheArchive.AlternateKey` whenever the flag is on, and that value flows unsanitized into `cacheArchivePath`/`--alternate-file`, which is then used by `CacheArchiverCommand.tryRenameAlternateFile` to `os.Rename` a file at an attacker-influenced path.

### Finding Description
In `functions/concrete/builder/builder.go`, `cacheKey()` (lines 570-603) does: [1](#0-0) 
- If `HashCacheKeys` is ON: `humanKey = rawKey` — **no call to `cachekey.Sanitize`**.
- If OFF: `humanKey = cachekey.Sanitize(rawKey)` — traversal is fully collapsed against a virtual root.

In `buildCacheArchive()` (lines 361-370): [2](#0-1) 
`alternateResolved := humanKey`, and it is only hashed `if !isFeatureFlagOn(HashCacheKeys)`. So when the flag **is** on, `alternateResolved` stays equal to the **unsanitized** `humanKey` (i.e., the raw, attacker-controlled `cache.key` after variable expansion, potentially containing `../` sequences), while the primary `resolvedKey` used for `archive.Key` is safely hashed via SHA-256.

This unsanitized value becomes `stages.CacheArchive.AlternateKey`, which is consumed in `functions/concrete/run/stages/cache_archive.go`: [3](#0-2) [4](#0-3) 
`cacheArchivePath` does `filepath.Join(e.CacheDir, key, "cache.zip")`. Because `filepath.Join`/`filepath.Clean` only clamps `..` at the filesystem root (`/`), not at `CacheDir`, an attacker-supplied key like `"../../../etc/cron.d/x"` can consume `CacheDir`'s own path segments and continue upward, landing at an absolute path outside `CacheDir` (e.g. `/etc/cron.d/x/cache.zip`), depending on how many segments `CacheDir` has. The subsequent `filepath.Rel(e.WorkingDir, absPath)` merely re-expresses that same absolute location relatively; it does not re-confine the path.

This crafted path is passed as `--alternate-file` to the `cache-archiver` helper command, which is handled by `CacheArchiverCommand.tryRenameAlternateFile` in `commands/helpers/cache_archiver.go`: [5](#0-4) 
If the primary `c.File` doesn't already exist and an existing file happens to exist at the traversed `c.AlternateFile` path (attacker-controlled name, but the attacker does not directly control file *contents* at that path unless they can already place a file there from a prior job/cache download), the code does `os.Rename(c.AlternateFile, c.File)`. This moves/deletes an arbitrary file from outside `CacheDir` into the (safe) primary cache path — this is a real containment-boundary violation (an unintended file is read from an attacker-chosen location outside `CacheDir`), even though it does not directly grant arbitrary file *write* to attacker-chosen destination content, since `c.File` is always the sanitized/hashed primary path.

The `cachekey.Sanitize` guard (`cache/cachekey/cachekey.go`) is real and effective when it's actually invoked, but it is bypassed entirely for the alternate-key computation path whenever `FF_HASH_CACHE_KEYS=true`.

### Impact Explanation
When the runner (or GitLab instance) has `FF_HASH_CACHE_KEYS` enabled, a pipeline author who controls `cache.key` (directly or via `$CACHE_KEY`-style variable expansion) can craft a key containing `../` segments. This unsanitized value is used to build the `--alternate-file` path for `cache-archiver`, allowing `filepath.Join`/`filepath.Rel` to compute a path outside `e.CacheDir`. The concrete, reachable outcome is `os.Rename` operating on a path outside the intended cache root — i.e., a job can cause the runner helper to touch/move a file outside `CacheDir` into the cache tree, an isolation-boundary violation of the stated invariant ("File operations must stay within intended build/cache/artifact roots"). This is scoped to the runner host/cache filesystem accessible to the job (shell/host-backed cache directories), not a remote/object-storage cache.

### Likelihood Explanation
- Requires `FF_HASH_CACHE_KEYS=true` to be enabled (not the default; `DefaultValue: false` per `helpers/featureflags/flags.go` line 460). This is a precondition outside the attacker's control but is a legitimate, documented, user-facing feature flag that operators can and do enable.
- Requires attacker control of `cache.key` (a standard `.gitlab-ci.yml` field/variable), which any pipeline author has.
- No other check intercepts the raw key before it becomes `AlternateKey`; `cachekey.Sanitize` is simply skipped in this branch, confirmed by direct code reading.
- Exploitability is bounded by needing the traversal to line up with `CacheDir`'s directory depth and by requiring a target file to actually exist at the traversed alternate path for the `os.Rename` to trigger (per the `os.Stat` guard in `tryRenameAlternateFile`).

### Recommendation
Always sanitize `humanKey`/the raw cache key with `cachekey.Sanitize` before it is used to derive `alternateResolved`/`AlternateKey`, regardless of `FF_HASH_CACHE_KEYS` state, i.e., compute `humanKey` via `cachekey.Sanitize(rawKey)` unconditionally (using the sanitized value both as the human-readable name and as the input to `alternateResolved`'s SHA-256/raw branching), so unsanitized attacker input never reaches path-construction code in `cacheArchivePath`. Additionally, harden `cacheArchivePath` itself to explicitly verify (e.g., via `filepath.Rel` + reject any `..` prefix, or `strings.HasPrefix` after `filepath.Clean`) that the resolved absolute path is a descendant of `e.CacheDir` before use, as defense-in-depth independent of upstream sanitization.

func cacheArchivePath(e *env.Env, key string) string {
	absPath := filepath.Join(e.CacheDir, key, "cache.zip")
	rel, err := filepath.Rel(e.WorkingDir, absPath)
	if err != nil {
		return absPath
	}
	return rel
}
