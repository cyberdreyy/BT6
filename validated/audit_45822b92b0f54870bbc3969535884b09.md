### Title
Stale `lastWithdrawRequest` pointer lets a settled APR0 receipt escape its `stopEpochWithDuration` loss haircut and claim at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` tracks a user's pending withdraw receipt via a single "latest epoch" pointer, `lastWithdrawRequest[_user]`. Loss-adjusted claims (`_claimLossAdjustedWithdrawRequest`, `IdleCreditVault.sol:789`) resolve the haircut exclusively through that pointer (`lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`), and the guard in `requestWithdraw` (`IdleCreditVault.sol:263-271`) only blocks a new request when the *latest* epoch still holds an unclaimed normal receipt (`withdrawsRequestsByEpoch[user][lossEpoch] != 0`) or an *open* APR0 principal (`apr0Users[user].principal != 0 && principalEpoch == lossEpoch`). It does not check `settledPrincipal`/`settledInterest`. When `stopEpochWithDuration` settles the APR0 bucket (`prepareStopEpochWithApr0`, called at `IdleCDOEpochVariant.sol:362` *before* `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch` at line 421), an APR0 request's `principal`/`principalEpoch` are consumed into the settled fields. A subsequent `requestWithdraw` then overwrites `lastWithdrawRequest` to a newer epoch — the stale-pointer/UAF analog — orphaning the loss-epoch haircut so the old basis is later paid at par through `_claimFundedWithdrawRequest`.

### Finding Description
The bug-class analog of CVE-2016-7978 (stale reference after the referent is released) is the single-slot `lastWithdrawRequest[_user]` epoch pointer combined with per-epoch loss pricing in `lossRecoveryPriceByEpoch`:

1. `_claimLossAdjustedWithdrawRequest` only ever looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and clears the claim for exactly that one epoch (`_clearWithdrawClaimForEpoch`). Receipts recorded under any *other* epoch (`withdrawsRequestsByEpoch[user][E_old]`, APR0 `settledPrincipal`) are then funneled into `_claimFundedWithdrawRequest`, which pays `normalAmount + settledPrincipal + settledInterest` at par (`IdleCreditVault.sol:338-349`).
2. The protective guard in `requestWithdraw` covers exactly two shapes of the latest-epoch receipt: a normal `withdrawsRequestsByEpoch` entry, or an *open* `apr0User.principal` whose `principalEpoch` matches. Once `prepareStopEpochWithApr0` settles the APR0 request at the end of its epoch (moving basis into `settledPrincipal`/`settledInterest`), `principal == 0`, so neither condition detects that the just-finished epoch was assigned `lossRecoveryPriceByEpoch[E] < RECOVERY_FULL` by `collectWithdrawFunds` (`IdleCreditVault.sol:414-421`).
3. The attacker then calls `requestWithdraw` again; `lastWithdrawRequest[_user]` is overwritten to the current epoch (`IdleCreditVault.sol:282`). The epoch-E haircut is now unreachable: `_claimLossAdjustedWithdrawRequest` resolves the new epoch (no loss price → early return), and the loss-bearing basis survives in the aggregate `withdrawsRequests[_user]`/settled fields, which `_claimFundedWithdrawRequest` pays 1:1.

The intended invariant — one haircutted receipt, one discounted payout — is broken because the epoch that "owns" the haircut is freed from the pointer while its basis remains claimable.

### Impact Explanation
Direct theft/insolvency. Every basis unit in the orphaned epoch-E receipt is paid at 100% instead of `lossRecoveryPriceByEpoch[E]`, i.e. the attacker extracts `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` of underlyings that were explicitly haircut because the borrower did not fund them. Those underlyings are drawn via `_transferFundedClaim` from the same strategy balance that backs other users' funded receipts and, after a later default, must respect `defaultRecoveryReserve` — so the excess payout is socialized onto honest claimants and can leave the last claimants' `_transferFundedClaim` reverting on insufficient balance (permanent freezing of residual claims). Loss scales with the attacker's deposited principal and the configured `_lossAmount`; with a 10% loss epoch a 1M-USDC receipt steals ~100k USDC.

### Likelihood Explanation
Requires no privileged misbehavior: `stopEpochWithDuration` with `_lossAmount > 0` is a normal manager action used to realize partial losses (`IdleCDOEpochVariant.sol:520`). The attacker is an ordinary KYC-passing lender who (a) deposits AA/BB, (b) calls `requestWithdraw` during a zero-APR epoch so the receipt is tracked as APR0, (c) waits for the lossy stop, (d) re-requests, (e) claims at par after the next epoch boundary. The gap hinges on `prepareStopEpochWithApr0`/`_settleApr0` clearing `apr0User.principal`/`principalEpoch` at settlement (consistent with the guard only inspecting `principal`, and with `settledPrincipal` being excluded from `_withdrawClaimAmountsForEpoch`'s per-epoch basis at lines 869-880); if settlement retains `principalEpoch`, the guard still fails whenever the settled receipt's epoch differs from the (newer) `lastWithdrawRequest`. No existing guard — skim, default revert, epoch gating, KYC — intercepts this sequence.

### Recommendation
- In `requestWithdraw`, extend the loss-epoch guard to also revert when `apr0Users[_user].settledPrincipal != 0 || apr0Users[_user].settledInterest != 0` while `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`, or store the APR0 receipt's origin epoch separately (e.g. `settledPrincipalEpoch`) and include it in the check.
- Alternatively, make `_claimLossAdjustedWithdrawRequest` iterate/derive the claimant's loss epochs from `withdrawsRequestsByEpoch`/APR0 epoch fields instead of relying solely on the single `lastWithdrawRequest` slot, so an overwritten pointer cannot orphan a haircut.
- Ensure `collectWithdrawFunds` records the haircut *before* APR0 settlement consumes the epoch attribution, or persist per-epoch APR0 claim basis so settled receipts keep their loss price.

### Proof of Concept
Foundry fork sketch (mainnet fork, pool in APR0 mode):

```solidity
// 1. Attacker (KYC'd EOA) deposits into AA during buffer of epoch E.
idleCDO.depositAA(1_000_000e6);

// 2. Manager starts epoch E with unscaledApr == 0.
vm.prank(manager); cdoEpoch.startEpoch();

// 3. Attacker requests full withdraw -> routed to _requestWithdrawApr0,
//    apr0Users[attacker].principal = P, principalEpoch = E, lastWithdrawRequest = E.
cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));

// 4. Warp past epochEndDate; borrower funds only pendingBasis - pendingLoss.
//    Manager calls stopEpochWithDuration(_newApr=0, _interest, dur, lossAmount):
//      - prepareStopEpochWithApr0 settles principal -> settledPrincipal (principal cleared)
//      - previewLossAdjustedWithdrawFunds/collectWithdrawFunds set
//        lossRecoveryPriceByEpoch[E] = funded * RECOVERY_FULL / pendingBasis (< 1e18)
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(0, interest, duration, lossAmount);

// 5. Guard bypass: apr0User.principal == 0 and (if cleared) principalEpoch != E,
//    so requestWithdraw succeeds and overwrites lastWithdrawRequest -> E+1.
cdoEpoch.requestWithdraw(dust, address(AAtranche));

// 6. Next epoch runs and stops normally; attacker calls claimWithdrawRequest.
//    _claimLossAdjustedWithdrawRequest reads lastWithdrawRequest = E+1 -> price 0 -> skip.
//    _claimFundedWithdrawRequest pays settledPrincipal + withdrawsRequests at PAR.
//    assert: underlyingReceived == P   (expected haircut: P * lossRecoveryPriceByEpoch[E] / 1e18)
```

Note: I was unable to read the bodies of `_settleApr0`/`_requestWithdrawApr0` within the available iterations; the finding assumes settlement clears `principal`/`principalEpoch` (or that `settledPrincipal` simply isn't covered by the guard). If settlement leaves `principal`/`principalEpoch` intact until claim, step 5 would revert and the issue reduces to a blocker (funds frozen until claimed) rather than par-payment theft — that residual case should be confirmed by inspecting `_settleApr0` before finalizing severity.
