### Title
Blacklisted underlying token (USDC/USDT) permanently freezes funded withdraw and instant-withdraw claims because `claimWithdrawRequest`/`claimInstantWithdrawRequest` always pay `msg.sender` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Surge report's bug class — a withdrawal path that force-transfers a blacklistable token to `msg.sender` with no `recipient` parameter — maps directly onto the epoch withdraw-claim flow of `IdleCDOEpochVariant` / `IdleCreditVault`. Both `IdleCDOEpochVariant.claimWithdrawRequest()` and `claimInstantWithdrawRequest()` hardcode `msg.sender` as the beneficiary (`IdleCDOEpochVariant.sol:967-979`), and the strategy-side `_transferFundedClaim(_user, amount)` pushes the underlying to that same address. Unlike the base `IdleCDO.withdrawAA/withdrawBB` path — where tranche tokens are freely transferable ERC20s and a blacklisted user can move them to a clean address and redeem there — the withdraw *receipts* in `IdleCreditVault` are strategy tokens whose transfers are address-bound and gated (the `canTransfer` flag can only ever be cleared to `false` by the manager, and post-default receipts are permanently non-transferable, as verified by `testReceiptTransfersRemainDisabledAfterDefault` and `testManagerCanOnlyClearLegacyReceiptTransferFlag` in `test/foundry/IdleCreditVault.t.sol:4655-4740`). Once a receipt exists, only the recorded `_user` can ever claim, and the underlying is pushed to that exact address — so a user blacklisted by the underlying token (e.g., USDC/USDT blacklist after interacting with a sanctioned mixer) can never collect their funded, matured withdrawal.

### Finding Description
Flow for a normal withdraw:

1. During the buffer phase a lender calls `IdleCDOEpochVariant.requestWithdraw`, which burns tranche tokens and calls `IdleCreditVault.requestWithdraw(_underlyings, msg.sender, principal)`, minting the receipt (strategy tokens) to `msg.sender` (`IdleCDOEpochVariant.sol:739-791`).
2. After `stopEpoch` funds the strategy via `collectWithdrawFunds`, the user calls `IdleCDOEpochVariant.claimWithdrawRequest()`, which forwards `msg.sender` as `_user` (`IdleCDOEpochVariant.sol:967-971`).
3. `IdleCreditVault._claimFundedWithdrawRequest` burns the receipt from `_user`, zeroes `withdrawsRequests[_user]` / `lastWithdrawRequest[_user]` / `apr0Users[_user]`, and calls `_transferFundedClaim(_user, amount)` — a `safeTransfer` of `underlyingToken` to `_user` (`IdleCreditVault.sol:319-350`).

The identical pattern exists for instant withdrawals: `claimInstantWithdrawRequest(_user)` burns `_user`'s receipt and calls `_transferFundedClaim(_user, amount)` (`IdleCreditVault.sol:380-393`). The same applies to the post-default recovery paths `_claimDefaultedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`, and `_transferDefaultRecovery`, all of which pay out to the recorded `_user`.

Because the receipt token is non-transferable (default `canTransfer == false`; permanently disabled after default finalization), there is no workaround: the user cannot move the claim to a fresh, non-blacklisted address, and no `recipient` parameter exists anywhere in the chain `requestWithdraw → claimWithdrawRequest → _transferFundedClaim`.

### Impact Explanation
If a lender's address lands on the underlying token's blacklist (USDC, USDT, etc.) after requesting a withdrawal but before claiming — or was blacklisted at any point — the final `underlyingToken.safeTransfer(_user, amount)` reverts on every call. Since the claim burns state and pushes tokens in the same transaction, the user can never receive the funds, while the underlying sits locked in `IdleCreditVault` forever. This is permanent freezing of the user's principal plus accrued yield — identical impact to the source report (user loses access to collateral). The loss is bounded by the user's full claim amount; for a defaulted pool this also covers recovery payouts via `_transferDefaultRecovery`/`DefaultDistributor`-style claims paid to recorded addresses.

### Likelihood Explanation
Requires a specific external condition (the user's address being blacklisted by the underlying token issuer), which is a real and recurring occurrence for USDC/USDT (OFAC-sanctioned and frozen addresses). It needs no attacker action and no privileged misbehavior — the vulnerable sequence is the ordinary `requestWithdraw` → `stopEpoch` → `claimWithdrawRequest` path. The absence of any alternative exit (non-transferable receipts, no recipient parameter) makes the freeze unconditional once the precondition holds, matching the "High" assessment of the original finding.

### Recommendation
Add a `recipient` parameter (or a `claimFor`-style override) to the claim chain:

```solidity
// contracts/IdleCDOEpochVariant.sol
function claimWithdrawRequest(address _recipient) external {
    IdleCreditVault(strategy).claimWithdrawRequest(msg.sender, _recipient);
}

// contracts/strategies/idle/IdleCreditVault.sol
function _claimFundedWithdrawRequest(address _user, address _recipient) internal returns (uint256) {
    ...
    _transferFundedClaim(_recipient, amount);
}
```

Burn the receipt from `_user` (the recorded owner) but transfer the underlying to the caller-supplied `_recipient`. Apply the same change to `claimInstantWithdrawRequest`, `_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, and `_claimDefaultedInstantWithdrawRequest`. Note this requires care: `_onlyIdleCDO` currently ensures only the CDO calls the strategy, so the recipient must be threaded through from the user's `msg.sender` at the CDO layer — never trust a `_recipient` supplied directly to the strategy.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` harness which already provides `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testBlacklistedUserCannotClaimFundedWithdraw() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    address user = makeAddr("user");

    // 1. User deposits and requests a normal withdraw during buffer phase
    _depositWithUser(user, amountWei, true);
    vm.prank(user);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 2. Epoch runs and is stopped; borrower funds the withdraw -> receipt is claimable
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // 3. Underlying token issuer (e.g., USDC on a mainnet fork) blacklists `user`
    //    vm.prank(usdcBlacklister); usdc.addToBlockedList(user);  // or via stdstore on the blacklist slot

    // 4. Receipt cannot be moved to a clean address (transfers disabled)
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    IERC20Detailed(address(strategy)).transfer(makeAddr("clean"), amountWei);

    // 5. Every claim attempt reverts inside safeTransfer to the blacklisted `_user`
    vm.prank(user);
    vm.expectRevert(); // USDC blacklist revert
    cdoEpoch.claimWithdrawRequest();

    // 6. No recipient parameter exists -> user's principal+interest is frozen in
    //    IdleCreditVault permanently; vault balance retains the funded claim.
    assertGt(underlying.balanceOf(address(strategy)), 0);
}
```

The same PoC applies to `claimInstantWithdrawRequest` (request instant withdraw when APR drops, let `getInstantWithdrawFunds` fund it, then blacklist the user) and to the post-default `_claimDefaultedWithdrawRequest` path, where receipt transfers are permanently disabled, removing even a hypothetical escape hatch.

**Uncertainty note:** the exact line-level body of `_transferFundedClaim` and the `_transfer`/`canTransfer` gating in `IdleCreditVault.sol` were not fully read (grep confirmed the symbols exist but did not return line contents). The conclusion that receipts are non-transferable by default is supported by `test/foundry/IdleCreditVault.t.sol:4690-4740` (manager can only *clear* the flag; transfers revert with `NotAllowed`), but if `canTransfer` defaults to `true` on some deployment the escape of moving the receipt to a clean wallet exists pre-default, which would weaken the normal-path finding while leaving the post-default path (permanently non-transferable, per `testReceiptTransfersRemainDisabledAfterDefault`) still vulnerable.
