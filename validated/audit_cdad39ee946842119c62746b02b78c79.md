### Title
Job-supplied `trap ... TERM` command overrides the SIGTERM-dump protection installed by `ScriptHeader.Generate` - ([File: functions/script_legacy/internal/script_header.go])

### Summary
`ScriptHeader.Generate` writes a single top-level `trap exit 1 TERM` at the start of the generated script to prevent bash from dumping the currently-executing (and variable-expanded) command line to the job trace when SIGTERM is delivered on cancellation. Unlike the parallel implementation in `shells/bash.go`/`scriptwriter.go`, this legacy path never wraps the job's commands in a subshell that re-installs the trap, and `CommandProcessor.ProcessCommand` writes user-supplied command strings into the script completely unfiltered, so a job author can neutralize the protection with a plain `trap - TERM` (or `trap 'cmd' TERM`) command line.

### Finding Description
`ScriptGenerator.GenerateScript` concatenates the header and all commands into one flat script executed as a single shell process: [1](#0-0) 

The header installs the protective trap once, at the top level: [2](#0-1) 

`CommandProcessor.ProcessCommand`/`writeNormalCommand` then writes each job-supplied command string verbatim into the same script, with no filtering, escaping-as-data, or rejection of shell built-ins such as `trap`: [3](#0-2) 

Because bash's `trap` builtin simply overwrites any prior handler for the same signal in the current shell, a job command such as `trap - TERM` (reset to default) or `trap 'do_something' TERM` executed at the same top-level shell context as the header's trap will silently replace it for the remainder of the script. This is qualitatively worse than the design used in `shells/bash.go`/`scriptwriter.go`, which explicitly re-installs the trap *inside* a subshell specifically because "traps reset to defaults across the subshell boundary" — that comment documents the known bash behavior (issue 39005) that this legacy generator does not defend against at all, since there isn't even a subshell boundary here; a job command can simply overwrite the trap directly, and nothing detects or blocks it.

`scriptInput` (the `script` array) is attacker-controlled, sourced directly from `builtinCtx.GetInput("script", ...)`: [4](#0-3) 

### Impact Explanation
If the header's TERM trap is neutralized and the job is subsequently cancelled (SIGTERM sent by Runner), bash (on affected versions per the documented issue 39005) can print the currently executing command line — with variable expansion already applied — to the job's stdout/trace before dying. If that command line references a protected/masked CI/CD variable (e.g., a deploy token supplied by a pipeline/project setting the job author does not otherwise have read access to), the expanded value could be written into the job log, which the job author who triggered/authored the job can read. This is a self-inflicted-but-effective mechanism to defeat a protection that was specifically added to stop exactly this kind of secret disclosure on cancellation.

### Likelihood Explanation
This requires only: (1) using the `script_legacy` builtin path (`scriptv2`/`FF_SCRIPT_TO_STEP_MIGRATION`-style step) with a job-controlled `script` array, (2) including an early `trap - TERM` (or similar) command, and (3) the job being cancelled while a command referencing a masked/protected variable is executing. All of these are attacker-reachable without any elevated privilege — the job author fully controls the `script` array contents. The only external dependency is a cancellation event and a susceptible bash version, both realistic and already acknowledged as a real, previously-mitigated issue elsewhere in the codebase (gitlab-runner#39005), confirming feasibility.

### Recommendation
- Re-implement the same isolation used in `shells/bash.go`/`scriptwriter.go`: execute the job's command body inside an explicit subshell (`(trap 'exit 1' TERM; eval "$body") < /dev/null`) so that the trap re-installed at that boundary is not overridable by earlier top-level commands, and any job-level `trap ... TERM` only affects the subshell scope after the protective trap is (re-)established at subshell entry — order it so the protective trap is the last thing set before the eval'd body runs, or re-assert it immediately before exit-handling.
- Alternatively/additionally, detect and reject or neutralize job commands that attempt to modify the `TERM` trap (`trap ... TERM`, `trap - TERM`), or install the protective trap in a way that job code cannot rebind (e.g., a `DEBUG`/`EXIT` trap chain guard, or `readonly`-style enforcement is not directly possible for traps, so the subshell approach is the correct fix).
- Align `functions/script_legacy/internal/script_header.go` and `script_generator.go` with the already-fixed pattern in `shells/bash.go` (`bashExitOnScriptTerminationSignal` re-installed inside the eval subshell) to close this gap.

### Proof of Concept
Go unit test in `functions/script_legacy/internal` asserting the trap cannot be overridden by job input, and that commands execute inside a subshell boundary that re-asserts the trap:

```go
func TestScriptGenerator_UserTrapCannotOverrideTermTrap(t *testing.T) {
    gen := NewScriptGenerator(ScriptGeneratorConfig{ShellPath: "/bin/bash"})
    commands := []string{
        "trap - TERM", // attacker-controlled job command attempting to clear the protective trap
        "echo $SOME_MASKED_VAR",
    }
    script := gen.GenerateScript(commands)

    // Current behavior (bug): the job's "trap - TERM" line sits at the same shell
    // level as the header's trap, so it silently overrides it.
    // Expected (fixed) behavior: the trap-protected region must be a subshell,
    // so a job-level "trap - TERM" cannot affect the outer/protective trap.
    require.Contains(t, script, "(trap 'exit 1' TERM;", "commands must run inside a trap-protected subshell boundary")
    idx := strings.Index(script, "(trap 'exit 1' TERM;")
    trapLineIdx := strings.Index(script, "trap - TERM")
    require.Greater(t, trapLineIdx, idx, "job trap override must be inside the protected subshell, not able to precede/replace the outer trap")
}
```

Integration-level PoC: submit a job with `script: ["trap - TERM", "sleep 30", "echo $MASKED_TOKEN"]` referencing a masked CI/CD variable, cancel the job mid-`sleep`, and assert the job trace does not contain the expanded value of `$MASKED_TOKEN` or any raw bash pipeline-dump text — under the current implementation this assertion would fail on affected bash versions once the trap has been cleared by the job's own command.

	}

func (p *CommandProcessor) ProcessCommand(buf *strings.Builder, index int, command string) {
	command = strings.TrimSpace(command)

	if command == "" {
		buf.WriteString("echo\n")
		return
	}

	if p.shouldUseTraceSection(command) {
		p.sectionWriter.WriteSection(buf, index, command)
	} else {
		p.writeNormalCommand(buf, command)
	}
}

func (p *CommandProcessor) shouldUseTraceSection(command string) bool {
	return p.traceSections && isMultiline(command)
}

func (p *CommandProcessor) writeNormalCommand(buf *strings.Builder, command string) {
	logLine := p.formatter.FormatLogLine(command)
	buf.WriteString(logLine)
	buf.WriteString("\n")

	buf.WriteString(command)
	buf.WriteString("\n")

	if p.checkForErrors {
		buf.WriteString(exitCodeCheck)
		buf.WriteString("\n")
	}
}
