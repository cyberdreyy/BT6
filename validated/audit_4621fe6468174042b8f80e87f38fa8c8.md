### Title
Unprivileged fulfiller can buy escrowed tranche tokens at a stale, below-value ask by frontrunning `createWriteOffRequest`/`deleteWriteOffRequest` updates - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow` lets any lender escrow tranche tokens against a fixed `underlyingsRequested` ask while an epoch runs, and `fullfillWriteOffRequest` lets any wallet fill that standing order. The ask is a raw number with no price floor against current tranche NAV and no freshness/oracle check. A fulfiller can wait for (or frontrun a repricing of) an ask that sits below the current fair value of the escrowed tranches, atomically pay the stale ask and receive tranche tokens redeemable for more underlying, extracting the difference from the lender. This mirrors the Lido bug class: a permissioned-adjacent actor (any fulfiller, explicitly unprivileged per scope) quietly extracting a small slice of user funds through a bookkeeping loophole rather than an overt privilege.

### Finding Description
- `createWriteOffRequest(amount, underlyingsRequested)` escrows the caller's tranche tokens and records an arbitrary `underlyings` ask, only requiring `isEpochRunning()` and `amount != 0` (contracts/IdleCreditVaultWriteOffEscrow.sol:86-102). There is no `isWalletAllowed` check and no comparison of `underlyingsRequested` to `_trancheToUnderlyings(amount)`.
- `fullfillWriteOffRequest(_user, _tranches, _underlyings)` is callable by "any wallet" (line 122 dev note) and only enforces `currentRequest.tranches == _tranches` and `_underlyings >= currentRequest.underlyings` (lines 123-131). It then pays `_user` the ask minus `exitFee` and hands all escrowed tranche tokens to `msg.sender` (lines 139-151).
- The write-off flow exists because a lender exiting mid-epoch expects a discount, but nothing anchors the discount to tranche value. Two concrete theft paths for an unprivileged fulfiller:
  1. **Accrual drift**: requests live for the whole running epoch. Tranche NAV rises over the epoch (interest accrual in `_updateAccounting`/`_tranchePrice`), so a request priced fairly at creation becomes underpriced as `priceAA`/`priceBB` climb. The fulfiller fills at the stale ask and later redeems/requests withdrawal at the higher NAV, pocketing `trancheValue - ask - exitFee`.
  2. **Repricing frontrun**: because `createWriteOffRequest` *adds* to the existing request (lines 97-101), a lender who wants to raise the ask must either call `createWriteOffRequest` again or `deleteWriteOffRequest` and recreate. A fulfiller watching the mempool fulfills at the old lower ask in the same block, forcing a sale below current value. Since fulfillment requires `currentRequest.tranches == _tranches`, the fulfiller can even wait until a second `createWriteOffRequest` lands and then fill the aggregated request as long as the average ask stays below NAV.
- Existing guards do not stop this: `nonReentrant` only blocks reentrancy, `EpochNotRunning` only gates creation, `exitFee` (max 1%) is far smaller than the NAV drift over a full epoch, and the `WrongRequest` check protects only against underpaying the *ask*, not the *value*. Unlike `IdleCDOEpochVariant.requestWithdraw`, no `isWalletAllowed` is enforced on the fulfiller either.

### Impact Explanation
Direct theft of lender funds: the fulfiller receives tranche tokens whose redemption value exceeds what they paid. Loss per fill = `tranchePrice * tranches / 1e18 - (underlyingsAsk - exitFeeAmount)`. For requests outstanding across a multi-week epoch with meaningful APR, the drift alone can reach a few percent of the escrowed position; with frontrunning of repricing the gap can be arbitrarily large (bounded by the lender's mistake size). Funds at risk equal the aggregate `pendingUnderlyings`-denominated asks of all open requests.

### Likelihood Explanation
Requires (a) a lender to post an ask below eventual tranche value and (b) a fulfiller willing to monitor and fill. Both are routine: any EOA may fulfill (no KYC needed on the buy side per the code and confirmed by `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw`), requests are designed to sit for a whole epoch while NAV accrues, and liquidation/MEV bots naturally fill mispriced OTC orders. Medium likelihood, bounded per-request loss.

### Recommendation
- Enforce a floor on `underlyingsRequested` at creation time, e.g. `underlyingsRequested >= _trancheToUnderlyings(amount) * minRecoveryBps / FULL_ALLOC` read from `IdleCDOEpochVariant`, and/or a max age after which requests auto-expire or must be refreshed.
- Make `createWriteOffRequest` overwrite (not accumulate) the ask so a lender can reprice atomically in one transaction, eliminating the delete-then-recreate frontrun window.
- Apply `isWalletAllowed` to `createWriteOffRequest` for consistency with the rest of the vault surface.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
// Setup mirrors test/foundry/IdleCreditVaultWriteOffEscrow.t.sol

function testStaleAskFulfillmentStealsNavDrift() external {
    uint256 requestedTranches = 10000e18;
    uint256 askedUnderlyings  = 10000e6; // fair at creation (price ~1)
    address attacker = makeAddr("attacker"); // NOT kyc'd, any wallet works

    // Epoch running; lender posts ask
    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, askedUnderlyings);

    // Time passes mid-epoch; interest accrues, tranche price rises.
    // Simulate price appreciation via _updateAccounting / harvest.
    _accrueEpochInterest(); // helper: advance time + trigger _updateAccounting
    uint256 fairValue = cdoEpoch.tranchePrice(address(tranche)) * requestedTranches / 1e18;
    assertGt(fairValue, askedUnderlyings); // ask now below NAV

    // Attacker fulfills at stale ask
    deal(address(underlying), attacker, askedUnderlyings);
    vm.startPrank(attacker);
    underlying.approve(address(escrow), askedUnderlyings);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, askedUnderlyings);
    vm.stopPrank();

    // Attacker holds tranches worth fairValue; paid only askedUnderlyings.
    // Profit = fairValue - askedUnderlyings (minus lender's exitFee).
    uint256 profit = fairValue - askedUnderlyings;
    assertGt(profit, 0);
}

function testRepricingFrontrun() external {
    // LP created request at 9000e6, now wants to raise ask to 9900e6.
    // Attacker sees deleteWriteOffRequest/createWriteOffRequest in mempool
    // and fulfills at the old 9000e6 ask first, forcing below-value sale.
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, 9000e6); // succeeds, LP cannot abort
}
```

Caveat: I verified the escrow logic, its guards, and the non-KYC fulfill path in the existing test suite, but did not fully trace `_tranchePrice` drift magnitude within a single epoch against real harvest timing; the PoC's `_accrueEpochInterest` helper should be built on the existing `_stopCurrentEpoch`/harvest helpers in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` to quantify the drift precisely.
