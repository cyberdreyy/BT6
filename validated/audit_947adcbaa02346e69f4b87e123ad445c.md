### Title
Signer broadcasts a block based solely on peer signature weight without checking its own validation state - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`store_and_process_block_signature` tallies a peer's block-acceptance signature and, once the accumulated weight crosses the 70% threshold, marks the block locally accepted and calls `broadcast_signed_block` — all without ever checking `block_info.valid`. This mirrors the reported bug class: a downstream action (liquidation / here, block broadcast) is gated on one comparison (signature weight ≥ threshold) while a second, logically-required comparison (the block's own validity) is never enforced, allowing the guarded action to fire even when the underlying object (the loan / the block) does not actually satisfy the precondition the check was meant to imply.

### Finding Description
In the sibling code path `handle_block_pre_commit`, the signer explicitly guards against acting on unvalidated blocks: [1](#0-0) 

But `store_and_process_block_signature`, which is invoked from `handle_block_signature` whenever a peer's `BlockAccepted` message is received, performs no equivalent check on `block_info.valid`: [2](#0-1) 

It proceeds straight to computing `total_signature_weight` against `min_weight` and, once the threshold is reached, calls `mark_locally_accepted` and `broadcast_signed_block`: [3](#0-2) 

The only prior touchpoint, `handle_block_signature`, authenticates the signer's public key but likewise never inspects the local block's own validation outcome before delegating to `store_and_process_block_signature`: [4](#0-3) 

Because `block_lookup_by_reward_cycle` returns whatever `BlockInfo` is stored regardless of its `valid` field (`None` if never submitted for validation, or `Some(false)` if this signer's own node explicitly rejected it), a signer can accumulate enough *other* signers' acceptance messages to cross the 70% threshold and push/broadcast a block that this signer's own node never validated, or actively deemed invalid — exactly the "equality never actually checked" pattern from the report (there, LTV vs. MAX_PENALTY_LTV was assumed to imply threshold vs. LTV; here, weight ≥ threshold is assumed to imply block validity, but nothing enforces it).

### Impact Explanation
This falls under "a signer signing an invalid, non-canonical, or conflicting block" (broadcast/push here plays the equivalent role of a signature action being finalized) since the local node's own view of block validity is bypassed once peer weight is collected. A miner or colluding minority relaying crafted `BlockAccepted` messages for a block this signer never validated (or a slow/partitioned signer that never receives a `BlockValidateResponse` before peer signatures arrive) could cause `broadcast_signed_block` to run against an unverified `BlockInfo`.

### Likelihood Explanation
Reachable purely via a one-slot miner plus ordinary gossip: no majority key compromise or auth_token access is required, since the vulnerable code only consumes already-authenticated `BlockAccepted` StackerDB messages and never re-derives them from anything requiring a majority of signers. The scenario needing this signer to have a stale/missing local `valid` determination (e.g., timing race between validation and inbound peer signatures) is realistic given that `submit_block_for_validation` / `handle_block_validate_response` run asynchronously relative to StackerDB message ingestion documented in `docs/signer-flows.md` sections 4–6.

### Recommendation
Add an explicit `if !block_info.valid.unwrap_or(false) { … return/park … }` guard in `store_and_process_block_signature` (mirroring the one in `handle_block_pre_commit`) before tallying weight and before calling `mark_locally_accepted`/`broadcast_signed_block`, so peer acceptance messages cannot cause this signer to push a block it has not itself validated as valid.

### Proof of Concept
1. Signer S receives a `BlockProposal` for block B and submits it for validation, but the validation response has not yet returned (`block_info.valid == None`), or the node has responded `Reject` (`block_info.valid == Some(false)`).
2. Attacker/miner broadcasts `BlockAccepted` messages from ≥70% weight of signers (possible if a miner colludes with, or replays cached signatures from, a supermajority — no signer secret keys of S required, since S only authenticates *other* signers' signatures via `recover_to_pubkey_without_validating_low_s` and `is_valid_signer`).
3. `handle_block_signature` → `store_and_process_block_signature` on S accumulates weight, crosses `min_weight`, and calls `broadcast_signed_block` for a block S's own node never approved.

Note: I could not fully trace the internals of `BlockInfo::mark_locally_accepted` (whether it independently vetoes on `valid`) within the available iterations; this should be verified before treating the finding as fully confirmed. [5](#0-4)
