### Title
Seize-target can indefinitely delay/deny a compliance `seizeWithMemo` by front-running to shrink their own balance below the requested amount - (File: `crates/common/precompiles/src/b20_asset/logic/v2.rs`, `crates/common/precompiles/src/b20_stablecoin/logic/v2.rs`)

### Summary
`seizeWithMemo` and `move_balance` revert the entire seize operation whenever `from_balance < amount`, exactly analogous to the Tessera `rejectProposal` bug: a party who monitors the mempool and controls the "collateral"/balance being acted on can front-run the privileged action with a small self-transfer that drops their balance just below the requested `amount`, forcing the seize transaction to revert. Because `SeizeExempt` (whether an account is seizable at all) is enforced independently of `TransferSender`/blocked status, an account can be simultaneously "seizable" and still fully able to send ordinary transfers, giving it the means to repeatedly grief the seize call.

### Finding Description
`move_balance` (shared by `transfer_inner` and `seize_with_memo`) checks the source balance and reverts the whole call if it is insufficient: [1](#0-0) 

`seize_with_memo` calls this same primitive after only checking role/pause/seizability/receiver-policy, with no re-derivation or capping of `amount` against the live balance beyond the hard revert: [2](#0-1) 

Crucially, seizability (`SeizeExempt`) and transfer-blocking (`TransferSender`) are independent policy scopes — the guard code explicitly documents and tests that an account can be seizable while still being authorized to transfer (i.e., not blocked): [3](#0-2) [4](#0-3) 

Because the L2 mempool exposes pending transactions and Base's block building allows ordinary users to submit and be included ahead of a pending call (front-running/priority-ordering), the seize target (`from`) can watch for a pending `seizeWithMemo(from, to, amount, memo)` call and submit an ordinary `transfer`/`transferFrom` moving `balance - amount + 1` tokens out of `from` immediately before it lands. This drops `from_balance` below `amount`, and `move_balance` reverts the seize with `InsufficientBalance` (mirroring `IB20::InsufficientBalance`), exactly as `OptimisticListingSeaport.rejectProposal` reverted on `proposedListing.collateral < _amount`.

### Impact Explanation
A designated compliance/enforcement operator (holder of `B20TokenRole::Seize`) attempting to seize funds from a sanctioned/compromised account can be perpetually stalled: the target repeats the self-transfer-and-revert pattern for as long as they have residual balance and gas to burn, similarly to how the Tessera attacker repeatedly reduced `proposedListing.collateral` by 1 to block `rejectProposal`. This defeats the intended purpose of the seize mechanism — a security/compliance control meant to freeze or recover funds from a bad actor — and can let the target eventually move remaining funds out entirely (to another address or by burning/paying gas fees away) before the admin can react, resulting in effective, practically-permanent evasion of an intended freeze/recovery action. This is not merely a UX nuisance; the seize primitive exists specifically to counteract theft/compliance violations, so defeating it is a concrete security-control bypass.

### Likelihood Explanation
Requires: (1) the target address to still be capable of ordinary transfers (not also globally blocked — which the guard code proves is possible and independent of seizability), (2) the target monitoring the mempool for pending seize calls naming it, and (3) enough balance/gas to keep front-running. All are realistic assumptions for a sophisticated actor who is the specific target of an on-chain seizure (e.g., an attacker who just stole B-20 assets and is trying to move them before compliance intervenes) — this is the highest-motivation actor for exactly this griefing pattern, mirroring the "Medium" judged severity of the original Tessera finding given similar external requirements (attacker must actively defend against every seize attempt, at some gas cost).

### Recommendation
When `from_balance < amount` in the seize path, clamp the seized amount to `min(from_balance, amount)` and move the available balance (or reject after re-checking with a small buffer) instead of hard-reverting the entire admin operation. Alternatively, treat `seizeWithMemo` as capable of seizing all available balance up to the requested amount, and emit `Seized` with the actual moved amount, so no self-transfer race can prevent an issuer from removing whatever balance remains at execution time — matching the recommended mitigation in the referenced Tessera finding (adjust the acted-upon amount to what's actually available rather than reverting).

### Proof of Concept
1. Admin holding `Seize` role and target account `ALICE` with `SEIZE_EXEMPT_POLICY` configured so `ALICE` is seizable (`make_seizable`), per test setup: [5](#0-4) 
2. `ALICE` holds `balance = 100` and is NOT subject to `TransferSender` blocking (independent policy scope, see guards test above), so she can freely call `transfer`.
3. Admin broadcasts `seizeWithMemo(from: ALICE, to: TREASURY, amount: 100, memo)`.
4. `ALICE` observes this pending transaction in the mempool and submits `transfer(to: BOB, amount: 1)` with higher priority fee, reducing her balance to 99.
5. The seize transaction executes against `move_balance`, sees `from_balance(99) < amount(100)`, and reverts with `InsufficientBalance`: [1](#0-0) 
6. Admin retries with `amount: 99`; `ALICE` repeats step 4, transferring 1 more token away each round.
7. This repeats until `ALICE` has drained/relocated all funds she wishes to protect, or the admin gives up — the seize never completes for the amount originally targeted.

    fn seize_with_memo(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        from: Address,
        to: Address,
        amount: U256,
        memo: B256,
    ) -> Result<()> {
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::SEIZE)?;
        B20Guards::ensure_token_role(token, caller, B20TokenRole::Seize)?;
        // `to != 0` guards against a disguised burn; `from != 0` guards against a disguised mint
        // (`Transfer(0x0, to, ...)`), matching `transfer_inner`.
        if to == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        if from == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSender { sender: from }));
        }
        if from == to {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        B20Guards::ensure_seizable(token, from)?;
        // Gate the destination like `mint` gates `MintReceiver`: an unset scope is always-allow, so a
        // treasury need not be allowlisted by default.
        B20Guards::ensure_policy_type(token, B20PolicyType::SeizeReceiver, to)?;
        self.move_balance(token, from, to, amount)?;
        // `Memo` must immediately follow the `Transfer` (from `move_balance`), before `Seized`.
        self.emit_memo(token, caller, memo)?;
        token
            .accounting_mut()
            .emit_event(IB20::Seized { caller, from, to, amount }.encode_log_data())
    }

    /// Ensures `account` is blocked by the current transfer-sender policy.
    ///
    /// Accounts are blocked when the configured registry policy does not authorize them.
    pub fn ensure_blocked<T: Token + ?Sized>(token: &T, account: Address) -> Result<()> {
        let policy_scope = B20PolicyType::TransferSender.id();
        let policy_id = token.accounting().policy_id(policy_scope)?;
        if token.policy().is_authorized(token.policy_storage(), policy_id, account)? {
            Err(BasePrecompileError::revert(IB20::AccountNotBlocked { account }))
        } else {
            Ok(())
        }
    }

    /// Ensures `account` is seizable, i.e. NOT authorized by the current seize-exempt policy.
    ///
    /// Mirrors [`Self::ensure_blocked`] but consults `SEIZE_EXEMPT_POLICY` instead of the
    /// transfer-sender policy: accounts authorized by that scope are exempt from seizure, so an
    /// account is seizable only when the configured registry policy does not authorize it, and
    /// the unset always-allow default keeps seizure closed until an issuer configures the slot.
    /// Used by `seizeWithMemo`. Enforced unconditionally, including in the factory bootstrap
    /// window. Reverts `AccountNotSeizable` (distinct from `ensure_blocked`'s `AccountNotBlocked`)
    /// so the seize path and the deprecated `burnBlocked` report separately.
    pub fn ensure_seizable<T: Token + ?Sized>(token: &T, account: Address) -> Result<()> {
        let policy_scope = B20PolicyType::SeizeExempt.id();
        let policy_id = token.accounting().policy_id(policy_scope)?;
        if token.policy().is_authorized(token.policy_storage(), policy_id, account)? {
            Err(BasePrecompileError::revert(IB20::AccountNotSeizable { account }))
        } else {
            Ok(())
        }
    }

    #[test]
    fn test_ensure_seizable_is_independent_of_transfer_sender_policy() {
        // A token with the transfer-sender policy set must NOT make an account seizable: the
        // seizable scope is unset (ALWAYS_ALLOW), so every account is authorized => not seizable.
        let allowed = Address::repeat_byte(0xaa);
        let denied = Address::repeat_byte(0xbb);
        let token = token_with_transfer_sender_policy(allowed);

        // `allowed` is authorized by transfer-sender AND by unset seizable (ALWAYS_ALLOW).
        assert_eq!(
            B20Guards::ensure_seizable(&token, allowed).unwrap_err(),
            BasePrecompileError::revert(IB20::AccountNotSeizable { account: allowed })
        );

        // `denied` is NOT authorized by transfer-sender, but still not seizable because the
        // seizable policy is unset (ALWAYS_ALLOW) — proving the two scopes are independent.
        assert_eq!(
            B20Guards::ensure_seizable(&token, denied).unwrap_err(),
            BasePrecompileError::revert(IB20::AccountNotSeizable { account: denied })
        );
    }
