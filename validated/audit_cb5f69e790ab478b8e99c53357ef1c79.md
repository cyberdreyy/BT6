### Title
Signer weight double-counted across accept/reject tallies when a signer switches its vote — `StackerDBListener` weight tracking breaks the aggregated-weight-vs-verified-accepts invariant (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` for a block using two *different* dedup keys — `gathered_signatures` (keyed by slot) for accepts and `responded_signers` (keyed by slot) for rejects — but both sets are populated independently and neither branch removes a signer's weight from the other bucket. A signer that first rejects and later accepts the same block (a transition the signer-side state machine explicitly permits, since "a rejection is a revocable opinion" [1](#0-0) ) ends up with its weight counted in **both** `total_weight_rejected` and `total_weight_approved` simultaneously, breaking the invariant that `total_weight_approved + total_weight_rejected <= total_weight`.

### Finding Description
For an `Accepted` response, the weight is added only if the slot is missing from `gathered_signatures`: [2](#0-1) 

For a `Rejected` response, the weight is added only if the slot is newly inserted into `responded_signers`: [3](#0-2) 

Both branches unconditionally call `block.responded_signers.insert(slot_id)` on the accept path too (line 465), but that call happens *after* the weight has already been added via the `gathered_signatures` check, and it is a no-op if the slot was already marked responded by an earlier rejection — it never triggers removal of the previously-added `total_weight_rejected` contribution. Consequently:

1. Signer S sends `Rejected` for block B. `responded_signers.insert(slot)` → `true` (first time) → `total_weight_rejected += weight(S)`.
2. Signer S later sends `Accepted` for the same block B (its local state machine legitimately re-evaluates and signs, as validated by the "rejection is revocable" design documented in `signerdb.rs`). `gathered_signatures.contains_key(slot)` is `false` (nothing was ever added to `gathered_signatures` on the reject path) → `total_weight_approved += weight(S)`.

Now `weight(S)` is present in *both* `total_weight_rejected` and `total_weight_approved`. There is no code path that decrements `total_weight_rejected` when a signer's later acceptance supersedes its earlier rejection.

### Impact Explanation
This directly breaks the aggregated-weight-vs-verified-accepts equality that `SigningCoordinator` relies on to decide the fate of a block: [4](#0-3) 

The rejection-threshold check is evaluated **before** the acceptance-threshold check. Because a flipped signer's weight lingers in `total_weight_rejected` forever, the sum `total_weight_rejected + total_weight_approved` can exceed `self.total_weight`. In particular, a block that legitimately reaches the ≥70% acceptance-weight threshold (because the flipping signer, plus enough other signers, actually accepted) can simultaneously satisfy `total_weight_rejected + weight_threshold > total_weight` due to the stale double-booked rejection weight. Since the coordinator checks rejection first, it will erroneously treat a properly, sufficiently-signed block as globally rejected (`NakamotoNodeError::SignersRejected`), and — worse — permanently ban transactions that a mere stale-minority reported as "problematic" via `permanently_excluded_txids`/`temporarily_excluded_txids`, computed from the same inflated `block_status.failed_txids` weight figures: [5](#0-4) 

This is a liveness wedge (a miner refuses/discards a block that the signer set actually approved) and a safety-relevant miscount (a rejection is effectively "recounted" alongside an accept for the same signer, corrupting the weight equality the entire consensus threshold logic depends on). No majority of signers, no other signer's key, and no StackerDB/transport exploit is required — only a single signer's own, otherwise legitimate, reject→accept sequence for one block.

### Likelihood Explanation
The reject→accept transition for the same block is not a contrived edge case; the signer flow documentation explicitly states that a rejection is revocable and a signer may later sign the same block once conditions change (e.g., pre-commit threshold reached, or a previously-blocking conflict goes stale): [6](#0-5) 

Any timing window where a signer's local view causes an initial reject (e.g., a transient validation error, timeout, or race during the async validation window described in the sibling-block tests) followed by a later accept once the miner resubmits or the view catches up, will trigger this double-count on the node side. This requires no adversarial signer, just normal asynchronous re-evaluation.

### Recommendation
Track a single per-slot "current vote" (accept, reject, or none) instead of two independently-guarded sets, and when a signer's vote transitions from reject to accept (or vice versa), subtract the previously counted weight from the old bucket before adding it to the new one. Concretely, replace the `gathered_signatures`-keyed guard and the `responded_signers`-keyed guard with a single map from `slot_id` to the last recorded verdict + weight, and make both the `Accepted` and `Rejected` handlers check/update that single source of truth so a signer's weight is attributed to exactly one bucket at a time.

### Proof of Concept
1. Configure a signer set where signer `S` has weight `w`, and the sum of all other honest signers' weight is exactly `weight_threshold` (i.e., without `S`, honest weight alone clears 70%).
2. Signer `S` sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for block `B` to the node's StackerDB slot. `stackerdb_listener.rs` records: `responded_signers.insert(slot_S) == true` → `total_weight_rejected += w` (lines 515-518).
3. Shortly after, `S`'s local signer state machine reconsiders (e.g. the block subsequently reaches pre-commit threshold and passes the chainstate recheck) and it broadcasts `BlockResponse::Accepted(...)` for the same `B`. The listener finds `gathered_signatures` has no entry for `slot_S` and adds `total_weight_approved += w` (lines 443-465).
4. All other signers accept normally, bringing `total_weight_approved` to (honest weight) + `w` ≥ `weight_threshold`, while `total_weight_rejected` still equals `w` from step 2 (never cleared).
5. In `signer_coordinator.rs::wait_for_signer_signatures_or_timeout`, if `w + weight_threshold > total_weight` (true whenever `w` is non-trivial relative to the 30% margin), the rejection branch fires first and the coordinator returns `NakamotoNodeError::SignersRejected` even though the block actually gathered ≥70% weight of *current* signer acceptances — demonstrating the broken equality and the resulting liveness wedge / erroneous rejection of a validly-signed block.
