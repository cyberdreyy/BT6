### Title
Unvalidated `user_reward_ata` in `kamino_harvest_reward` allows draining the bank's real liquidity vault when reward mint equals bank mint - (File: `programs/marginfi/src/instructions/kamino/harvest_reward.rs`)

### Summary
`KaminoHarvestReward` mirrors the Curve/Convex bug class described in the report: an adapter/CPI path fails to constrain which token account (analogous to `data.route`/`trade.sellToken`) is used as the source of an outgoing transfer, allowing an attacker to substitute the protocol's real asset vault for the intended "reward" account.

### Finding Description
In `kamino_harvest_reward`, `user_reward_ata` is declared as a bare `UncheckedAccount` with only a doc comment claiming it should be "An initialized ATA of type reward mint owned by liquidity vault" — there is no Anchor `associated_token::mint =` / `associated_token::authority =` constraint enforcing this [3](#0-2) . Likewise `reward_mint` is an arbitrary `InterfaceAccount<Mint>` with no constraint tying it to the bank's actual reward configuration or excluding it from being equal to `bank.mint` [4](#0-3) .

The instruction:
1. Reads the pre-balance of `user_reward_ata` [5](#0-4) .
2. CPIs into Kamino Farms `harvest_reward`, passing `user_reward_ata` as `user_reward_token_account` [6](#0-5) .
3. Computes `received = post - pre` and unconditionally transfers that amount **out of** `user_reward_ata` to `destination_token_account` (the global fee wallet), signed by the `liquidity_vault_authority` PDA [7](#0-6) .

Because `liquidity_vault_authority` is the SPL owner of both (a) the correct reward ATA and (b) the bank's real `liquidity_vault` deposit account (holding all depositor funds in `bank.mint`) [8](#0-7) , an attacker can call `kamino_harvest_reward` supplying `reward_mint = bank.mint` and `user_reward_ata = liquidity_vault` (the real vault address) instead of the correct reward ATA. The SPL `transfer_checked` authorization only checks that the token account's owner matches the signing authority — which it does, since `liquidity_vault_authority` legitimately owns `liquidity_vault`. This is structurally identical to the Curve report's root cause: the adapter trusts a caller-supplied "sell"/source account without verifying it is restricted to the intended token, letting an attacker redirect a transfer away from the intended token/vault.

If the Kamino farm attached to the bank's obligation ever distributes rewards denominated in the bank's own underlying mint (directly analogous to the report's "reward tokens equal to primary/secondary tokens" scenario), the harvested amount lands in `liquidity_vault` and is then swept in full to `destination_token_account`, moving real user deposits — not just reward proceeds — to the fee wallet.

### Impact Explanation
If exploitable (i.e., reward mint coincides with bank mint), any user (the instruction has no signer/authority requirement) could trigger transfer of principal balance from `liquidity_vault` to the global fee wallet, directly reducing backing for depositor withdrawals — a durable, financially damaging state change. This matches the report's "draining assets from the vault" impact class.

### Likelihood Explanation
Exploitability is conditional (as in the original report) on a reward mint coinciding with the bank's own mint, or on `harvest_reward`'s Kamino-side mint validation being bypassable. This is a narrower precondition than a fully unconditional bug, but the missing Anchor-level constraint (`associated_token::mint = reward_mint, associated_token::authority = liquidity_vault_authority` on `user_reward_ata`, as correctly implemented in the analogous `drift_harvest_reward` via `intermediary_token_account`, see [9](#0-8) ) is a real, unpatched gap that departs from the defense-in-depth pattern used elsewhere in the same codebase for the identical purpose.

### Recommendation
Add the same constraints used in `DriftHarvestReward` to `KaminoHarvestReward`: declare `user_reward_ata` as `InterfaceAccount<TokenAccount>` with `associated_token::mint = reward_mint`, `associated_token::authority = liquidity_vault_authority`, `associated_token::token_program = token_program`. Additionally, add an explicit check that `reward_mint != bank.load()?.mint` (mirroring the Drift adapter's `harvest_drift_spot_market.load()?.mint != bank.load()?.mint` check) to prevent reward-harvesting flows from ever touching the bank's core liquidity mint.

### Proof of Concept
1. Attacker identifies a Kamino bank where `liquidity_vault_authority` PDA and its `liquidity_vault` (bank mint = `M`) are known (both are deterministic PDAs derivable from the public bank account).
2. Attacker calls `kamino_harvest_reward` with `reward_mint = M` and `user_reward_ata = liquidity_vault` address, along with a `reward_index`/farm state that Kamino accepts for that mint (or that otherwise does not revert the CPI mint checks).
3. `cpi_harvest_rewards` CPIs to Kamino Farms; Kamino transfers accrued reward `M` tokens into `liquidity_vault` (since the passed `user_reward_token_account` is that same account) [10](#0-9) .
4. `received` is computed as the balance delta of `liquidity_vault`.
5. `cpi_transfer_obligation_owner_to_destination` transfers `received` from `liquidity_vault` to `destination_token_account`, signed by `liquidity_vault_authority` [7](#0-6) .
6. Because `liquidity_vault` also holds depositor principal in mint `M`, and the transfer amount is derived from a raw balance delta on an account the attacker chose to be the real vault, any timing window where deposits arrive concurrently, or any case where Kamino's reward transfer target validation can be satisfied with `liquidity_vault` as destination, allows principal to be swept out alongside (or instead of) genuine rewards.

Note: full confirmation that Kamino Farms' `harvest_reward` CPI does not itself reject `user_reward_token_account` when its mint differs from the farm's configured reward mint, or when reward_index maps to `M`, could not be verified from the mock/CPI interface alone within the scope of this review; this is flagged as an assumption requiring on-chain/Kamino-program-level verification, but the missing Anchor-level account constraint on `user_reward_ata` (in contrast to the properly-constrained Drift analog) is a confirmed, concrete code gap.

    pub fn cpi_transfer_obligation_owner_to_destination(&self, amount: u64) -> MarginfiResult {
        let program = self.token_program.to_account_info();
        let accounts = TransferChecked {
            from: self.user_reward_ata.to_account_info(),
            to: self.destination_token_account.to_account_info(),
            authority: self.liquidity_vault_authority.to_account_info(),
            mint: self.reward_mint.to_account_info(),
        };
        let bump = self.bank.load()?.liquidity_vault_authority_bump;
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(program.key(), accounts, signer_seeds);
        let decimals = self.reward_mint.decimals;
        transfer_checked(cpi_ctx, amount, decimals)?;
        Ok(())
    }
