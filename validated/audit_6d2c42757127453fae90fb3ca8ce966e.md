### Title
`ExtractZipFile` performs no path-containment check, allowing Zip Slip writes to arbitrary paths later sourced/executed - (File: helpers/archives/zip_extract.go)

### Summary
`ExtractZipArchive`/`extractZipFile` in `helpers/archives/zip_extract.go` writes each zip entry to `file.Name` verbatim, with no validation against `..` traversal, absolute paths, or symlink escape, unlike the sibling `tarzstd` extractor which explicitly enforces containment. An attacker who controls artifact or cache archive bytes consumed by a job can therefore make the Runner helper write/overwrite files outside the intended build/cache/artifact root, including files that later job stages implicitly source or execute.

### Finding Description
`extractZipFile` (helpers/archives/zip_extract.go:61-83) calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and then, depending on entry type, `extractZipDirectoryEntry`, `extractZipSymlinkEntry`, or `extractZipFileEntry` — each of which uses `file.Name` directly as the filesystem path passed to `os.Mkdir`, `os.Symlink`, or `os.OpenFile` [1](#0-0) . There is no `filepath.Clean`, no rejection of absolute paths, and no `strings.HasPrefix(path, rootDir)` containment check anywhere in this file. The only sanity check present, `errorIfGitDirectory`, only detects `.git` directory entries for warning purposes and does not stop extraction or reject traversal [2](#0-1) .

This is in stark contrast to the tar+zstd extractor used for other archive formats, which explicitly resolves each entry to an absolute path and rejects any path escaping the extraction root: `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name)); if !strings.HasPrefix(path, e.dir+string(filepath.Separator)) ... return fmt.Errorf("cannot be extracted outside of chroot")` [3](#0-2) . The zip path has no equivalent guard.

Compounding this, the legacy zip extractor wrapper (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) does not even use the `dir` parameter it is given — it calls `archives.ExtractZipArchive(zr)` directly, relying entirely on the process's current working directory being correct [4](#0-3) . A test comment elsewhere acknowledges this fragility: "hack: legacy archiver require being in the correct working dir" [5](#0-4) .

`ExtractZipFile`/`ExtractZipArchive` is reachable from `CacheExtractorCommand.Execute` and `ArtifactsDownloaderCommand.Execute`, both of which extract attacker-influenced archive bytes (job cache or job artifacts, potentially originating from a different job/pipeline via `needs`/cross-project artifact consumption) directly into the job's working directory [6](#0-5) [7](#0-6) .

Exploit flow: an attacker crafts a zip archive (as a job artifact or cache) containing entries named with `../../` sequences or absolute paths, or a symlink entry pointing outside the intended root. When a victim job restores this cache/artifact, `extractZipFile` writes the attacker's bytes (or creates a symlink) to the resolved out-of-root path. If that path coincides with a file that later pipeline stages source or execute unconditionally — e.g. a shell startup file (`~/.bashrc`, `~/.profile`, `/etc/profile.d/*.sh`) inside the same execution environment, or a predictable script/config file consumed by the next Runner-driven stage — the attacker's bytes get executed with the trust level of that later stage/session, without any additional confirmation or re-validation.

### Impact Explanation
Because there is no root-containment check, extraction can overwrite files outside the designated build/cache/artifact directory within the execution environment (container filesystem for Docker/Kubernetes, or the runner-user's filesystem for shell/custom executors). If the overwritten file is one implicitly sourced or executed later in the same job (shell init files, profile scripts) this results in attacker-controlled code execution in a later, more-trusted step, and potentially exposure of secrets available to that later step (masked variables, injected credentials) — matching the "stronger-context execution or secret exposure" impact category.

### Likelihood Explanation
Preconditions: a job must extract a cache or artifact whose zip archive bytes are attacker-influenced (e.g., the job's own cache/artifact from a prior stage, or an artifact pulled across projects/pipelines via `needs`). This is a standard, always-available capability for any pipeline author (uploading job artifacts and caches is core CI functionality) and requires no special permissions beyond normal job execution. The bug is deterministic and repeatable — any zip entry with `../` or absolute-path names, or malicious symlink targets, triggers it every time, since no code path in `zip_extract.go` rejects such names.

### Recommendation
Add the same containment logic used in `tarzstd_extractor.go` to the zip extraction path: resolve each entry against the intended extraction root with `filepath.Join(dir, filepath.Clean(file.Name))`, take `filepath.Abs`, and reject any entry whose resolved path does not have `dir` as a prefix (including rejecting absolute entry names and validating symlink targets don't escape the root). Additionally, fix `ziplegacy.extractor.Extract` to actually pass and use its `dir` argument (chdir or joins) rather than relying on ambient CWD.

### Proof of Concept
Go unit test (add to `helpers/archives/zip_extract_test.go`):
```go
func TestExtractZipFile_PathTraversalEscapesRoot(t *testing.T) {
    testInWorkDir(t, func(t *testing.T, fileName string) {
        outsideDir := t.TempDir() // simulate a "trusted" sibling location, e.g. a fake home dir
        maliciousName := filepath.Join("..", filepath.Base(outsideDir), "profile_hook.sh")

        f, err := os.Create(fileName)
        require.NoError(t, err)
        archive := zip.NewWriter(f)
        w, err := archive.Create(maliciousName)
        require.NoError(t, err)
        _, err = w.Write([]byte("echo pwned"))
        require.NoError(t, err)
        require.NoError(t, archive.Close())
        f.Close()

        err = ExtractZipFile(fileName)
        require.NoError(t, err)

        // Assert the file landed outside the extraction working directory
        _, statErr := os.Stat(filepath.Join(outsideDir, "profile_hook.sh"))
        assert.NoError(t, statErr, "expected zip entry to escape extraction root — proves missing containment check")
    })
}
```
Expected assertion (pre-fix): the file is created outside the intended extraction directory, proving no containment check exists. Post-fix, `ExtractZipFile` should return an error such as `"... cannot be extracted outside of chroot ..."` for the malicious entry, and the outside file must not exist.

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}
