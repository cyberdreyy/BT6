### Title
`get_builder_withdrawals` commits the full requested amount while `apply_withdrawals` only deducts `min(amount, balance)`, letting Gwei be created for the fee recipient - (File: `specs/gloas/beacon-chain.md`)

### Summary
In `specs/gloas/beacon-chain.md`, the withdrawals-computation function `get_builder_withdrawals` emits a `Withdrawal` whose `amount` equals the raw requested `withdrawal.amount` from `state.builder_pending_withdrawals`, without capping it to the builder's current balance. That same `amount` is what gets committed into the execution payload (via `state.payload_expected_withdrawals` / `assert list(payload.withdrawals) == expected.withdrawals` in `process_withdrawals`), which is what the execution layer actually credits to the fee recipient. However, `apply_withdrawals` (the consensus-side balance bookkeeping) only deducts `min(withdrawal.amount, builder_balance)` from the builder's on-chain balance. If a builder's balance has fallen below the queued withdrawal amount by the time the withdrawal is processed, the amount credited on the EL side (full `amount`) will exceed the amount actually removed from the builder's stake, breaking the balance-conservation invariant.

### Finding Description
This mirrors the reported Yearn bug-class: a downstream “apply” step silently caps/truncates an amount relative to what the upstream step already committed, so the committed value and the applied value diverge.

- `get_builder_withdrawals` (specs/gloas/beacon-chain.md, ~L1802-1834) builds the `Withdrawal` entries straight from `state.builder_pending_withdrawals`, using `amount=withdrawal.amount` with no `min(..., builder.balance)` clamp: [1](#0-0) 

- These withdrawals are aggregated into `expected.withdrawals` by `get_expected_withdrawals`, which becomes `state.payload_expected_withdrawals`, and `process_execution_payload`/`process_withdrawals` assert the actual execution payload's withdrawals list equals this committed list — i.e., the execution layer credits `fee_recipient` with exactly the committed `amount` regardless of the builder's true remaining balance: [2](#0-1) 

- But `apply_withdrawals`, which mutates consensus state, caps the deduction to the *current* balance: [3](#0-2) 

So whenever `builder.balance < withdrawal.amount` at apply time, the two "stores" — the execution-layer credit (driven by the committed `Withdrawal.amount`) and the consensus-layer debit (`min(amount, balance)`) — disagree, and the difference is Gwei created out of nothing for the fee recipient (paid out but never subtracted from any balance).

### Impact Explanation
This is a Critical-class issue per the rubric: it is "Gwei created… or paid to a non-owner." The withdrawal amount actually delivered on the execution layer is not bound by what is deducted from the builder's stake, so value can be manufactured and paid to `withdrawal.fee_recipient` without a corresponding balance decrease anywhere in the system — a direct violation of Gwei conservation, analogous to the original report's core defect (committed amount ≠ actually-movable amount, but here inverted: the commitment can *exceed* the true available balance rather than fall short of it).

### Likelihood Explanation
Builder balance can decrease between the time a `BuilderPendingWithdrawal` is queued (in `process_builder_pending_payments`, or via the "older than previous epoch" direct-append path in `apply_parent_execution_payload`) and the time it is actually processed in `get_builder_withdrawals`. In the interim, the same builder could be slashed-equivalent-drained via further payments, other queued withdrawals ahead of it in the queue reducing `builder.balance` first (since `apply_withdrawals` processes withdrawals for the same builder sequentially and could zero out the balance from an earlier entry in the same block), or via `process_builder_exit_request`/other balance-decreasing operations occurring before this entry is applied. Because `get_builder_withdrawals` has no clamp at commitment time, any such balance reduction that occurs after the pending withdrawal is queued but before it is applied produces a mismatch. This does not require a malicious peer or coalition — it can happen from ordinary sequencing of a single honest proposer's queued builder withdrawals within `MAX_WITHDRAWALS_PER_PAYLOAD` slots.

### Recommendation
Clamp the amount at commitment time in `get_builder_withdrawals`, mirroring what `apply_withdrawals` does, e.g.:

```python
builder_index = withdrawal.builder_index
amount = min(withdrawal.amount, state.builders[builder_index].balance)
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=amount,
    )
)
```

This ensures the amount committed into the execution payload equals the amount actually deducted from the builder's balance, restoring the invariant that no more Gwei is paid out than is removed from the builder's stake.

### Proof of Concept
1. Builder `B` has `state.builders[B].balance = X`.
2. A `BuilderPendingWithdrawal(builder_index=B, amount=X, fee_recipient=F)` is queued via `process_builder_pending_payments` (specs/gloas/beacon-chain.md L1661-1677). [4](#0-3) 
3. Before this entry is processed by `get_builder_withdrawals`, another operation in the same block reduces `state.builders[B].balance` to `Y < X` — e.g., a second `BuilderPendingWithdrawal` for the same builder is enqueued and processed earlier in `state.builder_pending_withdrawals` within the same `process_withdrawals` call, or `apply_parent_execution_payload`/`process_builder_exit_request` alters the balance before this withdrawal is applied.
4. `get_builder_withdrawals` still emits `Withdrawal(amount=X, address=F, ...)` unconditionally (L1822-1829), which is included in `state.payload_expected_withdrawals` and asserted equal to `payload.withdrawals` in `process_withdrawals` — i.e., the execution layer credits `F` with `X`.
5. `apply_withdrawals` then executes `state.builders[B].balance -= min(X, Y) = Y`, leaving the builder's balance decreased by only `Y`, not `X`.
6. Net effect: `F` is credited `X` Gwei on the execution layer, but only `Y` Gwei was removed from any consensus-tracked balance — `X - Y` Gwei has been created from nothing, in violation of the invariant that all EL-credited withdrawal amounts must equal amounts debited from beacon-state balances.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
