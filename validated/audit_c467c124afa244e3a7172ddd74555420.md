### Title
External-initiator credentials can trigger arbitrary integer-ID job runs, contradicting the "EIs not allowed" access control comment - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the integer-job-ID run path solely on `auth.GetAuthenticatedUser(c)` returning `ok==true`, using the comment "only users are allowed to run jobs using int IDs - EIs not allowed" to justify the check. However, `auth.AuthenticateExternalInitiator` also calls `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})`, so a request authenticated purely as an external initiator satisfies `isUser == true` and reaches `prc.App.RunJobV2(ctx, jobID, nil)` for an attacker-chosen `int32` job ID.

### Finding Description
The route is registered in `core/web/router.go`: [1](#0-0) 
combining `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, and `auth.AuthenticateBySession` as acceptable auth methods, wrapped only by `auth.RequiresRunRole`.

In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` explicitly fabricates a user session on success: [2](#0-1) 
This means `GetAuthenticatedUser(c)` (used by `Create`) returns `(&clsessions.User{Role: UserRoleRun}, true)` for a request that never used a real user session or API token — only EI access-key/secret headers.

In `PipelineRunsController.Create`: [3](#0-2) 
the `isUser` check treats this synthetic EI-derived user as a legitimate user, allowing the integer-ID branch to execute and call `prc.App.RunJobV2`. `auth.RequiresRunRole` at the router level does not distinguish EI-originated sessions from real user sessions either, since it only checks `user.Role != UserRoleView`: [4](#0-3) 

Historically the webhook/UUID job type (the one EIs were meant to trigger) was removed, and the comment "only users are allowed to run jobs using int IDs - EIs not allowed" was intended to close off int-ID job runs to EIs specifically. But because `AuthenticateExternalInitiator` masquerades as a `clsessions.User`, the code's own stated security boundary is not enforced — any valid external-initiator credential can run any job by integer ID, not just webhook jobs tied to that specific initiator.

### Impact Explanation
An external-initiator credential holder — which the codebase treats as a restricted, non-human, non-admin credential — can invoke `RunJobV2` for an arbitrary job ID, i.e., trigger job runs for jobs not associated with that external initiator at all. This is an authorization-bypass / unauthorized job execution: it lets a lower-privileged credential holder perform actions ("only users are allowed") the code comment explicitly says should be denied to it. Depending on what pipelines exist on the node (e.g., jobs that move funds, write on-chain transactions, or call other integrations), this can result in unauthorized job runs and potential unintended fund movement or side effects triggered by an entity that should not have that capability.

### Likelihood Explanation
Exploitation requires only a valid external-initiator access key/secret (a credential class explicitly permitted as an attacker precondition), and knowledge/guessing of a target job's integer ID (job IDs are sequential/enumerable). No admin, host, or database access is needed. The request is a straightforward single HTTP POST to `/v2/jobs/:ID/runs` with the EI headers set instead of session cookie or user API token, making this trivially repeatable.

### Recommendation
Distinguish real user authentication from EI-derived authentication instead of overloading `SessionUserKey`. Either:
1. Do not set `SessionUserKey` in `AuthenticateExternalInitiator`; instead rely solely on `SessionExternalInitiatorKey` and have `RequiresRunRole` accept either a real user (role >= Run) or a genuine EI, while `PipelineRunsController.Create` should explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (403) if present, regardless of `GetAuthenticatedUser`.
2. Or tag the synthetic user object distinctly (e.g., add an `IsExternalInitiator` flag) so `Create`'s `isUser` check can differentiate and refuse EI-only sessions from the int-ID path, matching the existing code comment's intent.

### Proof of Concept
Go handler-level test plan (in `core/web/pipeline_runs_controller_test.go` style):
1. Set up a test app with a mocked `chainlink.Application` whose `RunJobV2` is asserted via `mock.AssertNotCalled` or similar.
2. Create an `ExternalInitiator` record with known access key/secret via `bridges.NewExternalInitiator`.
3. Issue `POST /v2/jobs/123/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`) set to the EI's credentials, and no session cookie, no `X-API-KEY`/`X-API-SECRET`.
4. Current (buggy) expected result: response status 200/201 and `App.RunJobV2` invoked with jobID=123 — demonstrating the bypass.
5. After fix: assert response is `403 Forbidden` (or `401`) and `RunJobV2` is never called, confirming the "EIs not allowed" comment is now actually enforced.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
