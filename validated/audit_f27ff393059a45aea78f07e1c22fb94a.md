### Title
Terminal escape-sequence injection via `EscapeForAnsiC` hex-escaping that is re-decoded by bash's `$'...'` quoting at script execution time - ([File: functions/script_legacy/internal/command_formatter.go])

### Summary
`CommandFormatter.FormatLogLine` builds the trace "echo" line by wrapping the attacker-influenced command text in bash ANSI-C quoting (`echo $'...'`) after passing it through `EscapeForAnsiC`. That function converts control bytes such as raw `ESC` (0x1B) into the textual sequence `\x1b`, but because the surrounding quoting is `$'...'`, bash itself re-interprets `\xHH` escapes back into raw bytes when the generated script actually executes, defeating the intended protection and allowing attacker-controlled `ESC`/CSI/OSC byte sequences to reach the raw trace stream.

### Finding Description
`EscapeForAnsiC` (functions/script_legacy/internal/escape.go, lines 38-46) hex-escapes control characters, `0x7F`, and non-ASCII bytes into a literal `\xHH` textual representation, with a comment claiming this "prevents ANSI escape sequences ... from manipulating terminal". This output is then embedded by `FormatLogLine` (functions/script_legacy/internal/command_formatter.go, lines 31-39) into `fmt.Sprintf("echo $'%s'", EscapeForAnsiC(command))` — i.e., bash **ANSI-C quoting**.

The critical flaw: bash's `$'...'` quoting mechanism itself interprets `\xHH` hex escapes at *shell-execution time*, converting them back into the original raw bytes before they are written to `echo`'s argument and printed to stdout. So `\x1b` inside `$'...'` becomes the literal `ESC` byte again once the generated script line is executed by bash. The hex-escaping only protects the *literal source text* of the generated script from containing dangerous/unparseable raw bytes (a script-generation-time concern); it provides no protection against the resulting **runtime stdout** containing raw control bytes, because the very shell semantics chosen to embed the string reconstitute them.

Attack path:
1. Pipeline author supplies a `script:` command string (or any input reflected into the generated build script) containing raw bytes such as `ESC ] 52 ; ... BEL` (OSC 52 clipboard write) or `ESC [ ... ` cursor-addressing sequences embedded as literal bytes in the job's shell script text.
2. `CommandProcessor.ProcessCommand` → `writeNormalCommand` calls `formatter.FormatLogLine(command)` (functions/script_legacy/internal/command_processor.go, lines 49-55), which produces `echo $'...\x1b]52;c;<base64>\x07...'`.
3. This generated line becomes part of the actual build script executed by bash on the runner.
4. When bash executes it, `$'...'` decodes `\x1b`/`\x07` back to raw `ESC`/`BEL` bytes, and `echo` prints them to stdout, which is streamed as the job trace/log.
5. A downstream viewer's terminal (or a terminal-emulating log viewer) rendering the raw trace will interpret the reconstituted OSC/CSI sequence, potentially triggering clipboard writes, cursor movement, or other terminal side effects.

Existing checks that fail to stop this: there is no check on the raw `command` text for the actual command execution line (`buf.WriteString(command)` at command_processor.go line 54 is also fed to bash unescaped, as it must be to run as a shell command); and the `FormatLogLine` "protection" only defends the trace/echo portion, but does so via a mechanism (`$'...'`) that itself undoes the escaping upon execution.

### Impact Explanation
Any pipeline job (unprivileged pipeline author) that includes raw ANSI/OSC control bytes in a script line can cause those bytes to appear unmangled in the job's own trace output stream when a human or tool later views the raw log/trace in a real terminal. This can result in terminal session manipulation for whoever views the raw trace (e.g., via `curl | less -R`, terminal-based log tail, or any client that renders raw bytes instead of GitLab's web UI, which independently sanitizes ANSI in HTML rendering). Concretely this includes OSC 52 clipboard exfiltration/injection, cursor-addressing to overwrite prior visible log content, or DCS-based terminal reprogramming against the viewer's terminal emulator.

### Likelihood Explanation
- Precondition: attacker only needs the ability to define a `script:` line/CI job step containing raw control bytes (fully within reach of an unprivileged pipeline author).
- The vulnerable code path (`FormatLogLine` → `echo $'...'`) is on the default bash-mode trace generation path (`posixMode == false`), which is the common case for the bash/sh shell executors.
- No secrets or elevated permissions are required; the bug is fully reproducible and deterministic given a crafted script string containing `0x1B` bytes.
- The only mitigating factor is that GitLab's own web-based job log viewer performs its own ANSI-sequence allow-listing/sanitization before rendering, which may reduce impact for users only viewing logs through the standard web UI; the risk materializes for any consumer of the *raw* trace/log stream (raw log download, `cat`/`less` in a terminal, third-party log tools, API-fetched raw traces).

### Recommendation
Do not rely on `$'...'` (ANSI-C quoting) to carry data that must remain byte-for-byte "escaped" in the final stdout output. Instead:
1. Keep `EscapeForAnsiC` for constructing valid bash script source, but recognize that its hex-escapes will be decoded at runtime — this is only appropriate when the intent is for the terminal to *receive* the decoded bytes (e.g., the deliberate `ansiGreen`/`ansiReset` codes).
2. For attacker-controlled command text portions, strip or re-encode control/escape bytes (e.g., replace `0x1B` and other C0/C1 control bytes, excluding `\n`,`\t`, with a visible placeholder like `^[` or `\x1b` *as literal printed text*, e.g. by printing via `printf '%s'` with the bytes converted to a non-executable representation) so that after the shell actually runs the `echo`, the emitted trace bytes are the *visible* escaped text, not the raw control byte.
3. Alternatively, use a `printf` implementation that emits literal backslash-x-hex text (not decoded), e.g. build the display string so the final byte sequence written to stdout is `\`,`x`,`1`,`b` (four printable bytes) rather than the single `0x1B` byte, by not routing through `$'...'` decode-on-execute quoting for the command-derived, attacker-controlled substring.
4. Add regression coverage asserting that the *executed* output of `FormatLogLine` (i.e., after actually running the generated `echo $'...'` line through bash), not just its Go-source string form, contains no raw bytes in `0x00-0x1F \ 0x7F \ 0x9B` outside of the intentional `ansiGreen`/`ansiReset` sequences.

### Proof of Concept
Go integration test (bash required):
```go
func TestFormatLogLine_RawEscapeSurvivesExecution(t *testing.T) {
    formatter := NewCommandFormatter(false) // bash mode
    // Attacker-controlled command containing raw ESC + OSC 52 sequence
    malicious := "echo hi\x1b]52;c;bWFsaWNpb3Vz\x07"
    logLine := formatter.FormatLogLine(malicious)

    // Sanity: Go-source string is textually hex-escaped
    assert.NotContains(t, logLine, "\x1b", "source text should not contain raw ESC byte")

    // Execute the generated line with real bash and capture raw stdout bytes
    cmd := exec.Command("bash", "-c", logLine)
    out, err := cmd.Output()
    require.NoError(t, err)

    // BUG: raw ESC (0x1B) reappears in actual executed output
    assert.Contains(t, string(out), "\x1b]52;", "raw OSC 52 sequence reconstructed by bash at runtime")
}
```
Expected (buggy) result: the assertion `assert.Contains(t, string(out), "\x1b]52;")` passes, proving that despite `EscapeForAnsiC` hex-escaping the byte in the generated script text, bash's `$'...'` decoding reconstitutes the raw OSC 52 escape sequence in the actual job trace bytes emitted to stdout. func (f *CommandFormatter) FormatLogLine(command string) string {
	command = ansiGreen + commandPrefix + f.getDisplayCommand(command) + ansiReset

	if f.posixMode {
		return fmt.Sprintf("echo %s", EscapeForPosix(command))
	}

	return fmt.Sprintf("echo $'%s'", EscapeForAnsiC(command))
}
