### Title
Unbounded `Bundle.txs` list fans `base_meterBundle` into unmetered, per-transaction EVM execution before any aggregate limit is enforced - ([File: crates/common/bundles/src/bundle.rs])

### Summary
The `base_meterBundle` JSON-RPC method (`MeteringApi::meter_bundle`, `crates/execution/metering/src/rpc.rs`) accepts a `Bundle { txs: Vec<Bytes> }` with no bound on the number of entries in `txs` (`crates/common/bundles/src/bundle.rs`). Each element is separately decoded, recovered, and executed in the EVM by `meter_bundle` (`crates/execution/metering/src/meter.rs`), one transaction at a time, against live canonical state, before any aggregate cost or count check is applied. This mirrors the vLLM advisory's root cause: an outer, attacker-controlled list is expanded into one backend unit of work per element with no upper bound on element count, prior to any per-request resource budget.

### Finding Description
`Bundle` is declared as:
```rust
// crates/common/bundles/src/bundle.rs
pub struct Bundle {
    pub txs: Vec<Bytes>,
}
```
with no `#[serde]` length limit or custom bounded deserializer (contrast this with the txpool's `deserialize_bounded_predicates`, which explicitly aborts mid-stream once a validity-predicate array exceeds `DEFAULT_MAX_VALIDITY_PREDICATES`, in `crates/execution/txpool/src/validity.rs`). `MeteringApi::meter_bundle` takes this `Bundle` directly as an RPC parameter:
```rust
// crates/execution/metering/src/traits.rs
#[method(name = "meterBundle")]
async fn meter_bundle(&self, bundle: Bundle) -> RpcResult<MeterBundleResponse>;
```
The implementation (`crates/execution/metering/src/rpc.rs`) only logs `bundle.txs.len()`, fetches canonical state once, converts the bundle (`ParsedBundle::try_from`), and calls `meter_bundle(MeterBundleInput { .. })`, which iterates every transaction and executes it against a shared EVM/state builder (`crates/execution/metering/src/meter.rs`). There is no check anywhere on this path that rejects an oversized `txs` array before the per-element decode/recover/execute loop runs — the only guard present (`MAX_NONCE_AHEAD`) is a per-transaction nonce-distance check, not an aggregate count limit.

This is analogous to the vLLM issue: `CompletionRequest.prompt` (list) → `prompt_to_seq` → one engine generator per element, with no outer bound checked before fan-out. Here, `Bundle.txs` (list) → per-element decode/recovery/EVM execution, with no outer bound checked before fan-out.

The RPC surface is registered unconditionally when the metering extension is enabled (`crates/execution/metering/src/extension.rs`, `MeteringExtension::apply`), via `ctx.modules.merge_configured(metering_api.into_rpc())`, with no visible per-method auth/namespace restriction distinguishing it from other public `base_*` RPC methods exposed by the standard node build (`crates/execution/cli/src/standard_node.rs` installs `MeteringExtension` alongside other externally-facing extensions). Some Base deployments additionally use it as an internal simulation endpoint fronted by `ingress-rpc` (`crates/infra/ingress-rpc/src/service.rs`), which forwards a caller-controlled bundle (built from a single `eth_sendRawTransaction` payload in that specific call path) to `base_meterBundle` — but the RPC method itself, as wired by `MeteringExtension`, does not enforce that bundles must originate only from that trusted forwarder, nor does it cap `txs.len()` independently of the caller.

### Impact Explanation
An RPC client able to reach `base_meterBundle` (whether the node's ingress-rpc default forwarder, or any client with direct access to a node exposing the metering RPC module) can submit a single request whose `txs` array contains an attacker-chosen number of raw transaction byte-strings. Each entry triggers decode, sender recovery, and a full read-only EVM execution against live canonical state on the node's execution/simulation node. Because no limit exists on `txs.len()` prior to this loop, one HTTP/WS request can force CPU, memory, and state-provider I/O proportional to an attacker-chosen count, independent of any block-gas or per-transaction limit (each simulated transaction is bounded individually by its own gas limit, but the *number* of transactions in the list is unbounded). This can degrade or exhaust the metering/simulation node, which sits in the ingestion/block-building path (CWE-400 resource exhaustion), matching the Medium-severity classification of the referenced vLLM advisory.

### Likelihood Explanation
Likelihood is bounded by how tightly `base_meterBundle` is exposed in a given deployment: if it is reachable only from the trusted `ingress-rpc` forwarder (an internal component), exploitation requires that forwarder's compromise or misconfiguration; if the metering RPC module is exposed directly to less-trusted callers (as the plain `MeteringExtension`/`merge_configured` wiring suggests is possible), it is directly reachable by any client permitted to call `base_*` methods. No signature, gas payment, or on-chain state change is required to trigger the resource cost — only a well-formed JSON-RPC call — making the request cheap to send and easy to scale by simply lengthening the array.

### Recommendation
Add an explicit, low outer bound on `Bundle.txs.len()`, enforced during deserialization (mirroring `deserialize_bounded_predicates` in `crates/execution/txpool/src/validity.rs`) or immediately at the top of `MeteringApiImpl::meter_bundle` before canonical state is fetched or any transaction is decoded/executed. Reject with a standard `InvalidParams` RPC error once the count exceeds the configured maximum (e.g., aligned with the builder's expected per-block transaction count, or a small constant such as the `MAX_BATCH_SIZE = 500` pattern already used for `persist_rejected_transaction_batch` in `crates/infra/audit/src/rpc.rs`). Regression tests should cover: an empty bundle, a bundle at the limit, and an oversized bundle failing fast with no state fetch or EVM execution performed.

### Proof of Concept
```json
// JSON-RPC request to base_meterBundle
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "base_meterBundle",
  "params": [
    { "txs": ["0x02f8...", "0x02f8...", "... repeated tens of thousands of times ..."] }
  ]
}
```
Each entry can be a syntactically valid (or even invalid, forcing early per-item decode-error handling) raw transaction; scaling the array length forces the node's `meter_bundle` loop (`crates/execution/metering/src/meter.rs`) to decode/recover/execute (or reject) each one sequentially against live state, with total work scaling linearly with attacker-supplied array length and no upper bound enforced before the loop begins.
