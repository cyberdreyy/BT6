## Title
Slashing an equivocating proposer silently forfeits an accepted builder payment, letting the builder keep committed Gwei without paying the fee recipient - (specs/gloas/beacon-chain.md)

### Summary
`process_execution_payload_bid` locks a builder's committed value into `state.builder_pending_payments` after checking `can_builder_cover_bid`, which is a solvency guarantee analogous to the audited contract's requirement that a `createDistribution()` commitment be fully covered and eventually paid out. In Gloas, `process_proposer_slashing` unilaterally deletes that `BuilderPendingPayment` entry if the payment's `proposer_index` matches a slashed validator, without ever moving the committed `bid.value` into `builder_pending_withdrawals` or otherwise crediting anyone. This breaks the equality "every accepted bid amount that a builder was proven solvent for and that the network committed to (via a valid, signed, in-window bid) is eventually paid to the promised `fee_recipient`."

### Finding Description
When a builder submits a signed bid with `value > 0`, `process_execution_payload_bid` verifies `can_builder_cover_bid` and stores a `BuilderPendingPayment` keyed by `proposer_index` and slot, committing the builder to pay `bid.value` to `bid.fee_recipient` once the block/payload is confirmed via `settle_builder_payment` or the quorum-based `process_builder_pending_payments`: [1](#0-0) 

The only path that actually pays out the pending payment is `settle_builder_payment` (called from `apply_parent_execution_payload`) or `process_builder_pending_payments` (epoch boundary, quorum-gated), both of which move the withdrawal into `builder_pending_withdrawals`: [2](#0-1) [3](#0-2) 

However, `process_proposer_slashing` deletes the pending payment outright whenever the slashed validator is the payment's recorded proposer and the payment is still within the 2-epoch window: [4](#0-3) 

Nothing in this path decreases `state.builders[builder_index].balance` or otherwise transfers value anywhere else — the `BuilderPendingPayment` is simply overwritten with `BuilderPendingPayment.empty()`. The builder that had already been debited-in-commitment (its solvency was consumed by `can_builder_cover_bid`'s accounting via `get_pending_balance_to_withdraw_for_builder`) is freed from the obligation and its `.balance` is untouched, so the builder effectively keeps the full bid amount it had promised to pay for the block. Because the bid was valid (correct signature, correct parent, sufficient balance) and the block containing it was itself valid — the proposer's fault (equivocating in a *different, unrelated* slot/header) is orthogonal to whether the *bid it accepted* was honest — this is not an attacker forfeiting only their own stake: it is the *builder* that unilaterally benefits from another party's (the proposer's) misbehavior, at the expense of the `fee_recipient` who was promised payment.

Unlike the contract-report analog, where the operator/owner controls topping up the pool and the shortfall is "acknowledged," here the state-transition function is spec-defined to *always* wipe the commitment on proposer slashing with no compensating credit — this is a protocol-level guarantee gap, not an operational balance shortfall.

### Impact Explanation
This matches the "High" bucket: "a builder payment or withdrawal misdirected, doubled or escaped." A previously validated and accepted builder payment obligation vanishes: the fee recipient that was promised `bid.value` Gwei never receives it, while the builder's balance is never decreased for that bid. No slashing, forced exit, or balance mutation applies to the builder — only the innocent expectation of the fee recipient is broken. This is a "Gwei ... paid to a non-owner" in the exact opposite direction of the intended: Gwei that should have flowed from builder to fee-recipient effectively stays with the builder.

### Likelihood Explanation
Reaching this state requires only: (1) a builder submits and gets a signed valid bid accepted for some slot, creating a `BuilderPendingPayment`, and (2) *that slot's proposer* gets slashed for an unrelated equivocation (signing two conflicting headers for that slot) within the 2-epoch window before settlement/quorum resolution. Proposer slashings are a normal, spec-legal operation any observer can submit given two conflicting signed headers from the slashed validator — no coalition, no client bug, and no cost to the builder is required. This is comparable in likelihood to normal proposer-slashing submission, which is a standard unprivileged spec operation.

### Recommendation
When `process_proposer_slashing` clears a `BuilderPendingPayment` tied to the slashed proposer, the committed `withdrawal` (fee_recipient + amount + builder_index) should still be honored — e.g., by appending `payment.withdrawal` to `state.builder_pending_withdrawals` (mirroring what `settle_builder_payment` does) before clearing the payment slot — so that a valid, already-accepted builder commitment is not silently erased. Only the *quorum weight* accounting (which rewards attesters/proposer) should be discarded; the underlying payment obligation to the builder's counterparties should survive an unrelated proposer slashing.

### Proof of Concept
1. Builder `B` with sufficient balance submits `SignedExecutionPayloadBid` with `value = V > 0` for slot `S`, proposer `P`. `process_execution_payload_bid` passes `can_builder_cover_bid` and records `state.builder_pending_payments[idx] = BuilderPendingPayment(weight=0, withdrawal=BuilderPendingWithdrawal(fee_recipient=F, amount=V, builder_index=B), proposer_index=P)` (specs/gloas/beacon-chain.md:2124-2137).
2. Before `idx`'s payment settles (before enough attestation weight accrues and before it's evicted at the 2-epoch boundary), submit a valid `ProposerSlashing` for `P` (two conflicting signed headers for slot `S`, unrelated to the accepted block/bid content).
3. `process_proposer_slashing` finds `payment.proposer_index == P` and sets `state.builder_pending_payments[idx] = BuilderPendingPayment.empty()` (specs/gloas/beacon-chain.md:2456-2469).
4. At no point is `state.builders[B].balance` decreased, nor is any `BuilderPendingWithdrawal` for `F` created. `F` never receives `V` Gwei that `B` had committed to pay and had been confirmed solvent for.

This scenario is corroborated by the existing test suite exercising exactly this deletion path (e.g. `test_builder_payment_deletion_current_epoch`, `test_builder_payment_deletion_previous_epoch`), which confirm the payment entry is unconditionally cleared with no substitute withdrawal created: [5](#0-4) [6](#0-5)

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
