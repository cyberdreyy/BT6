### Title
Instant-withdraw receipt ledger is never cleared on claim, so a same-epoch default permanently freezes the user's claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` allocates three pieces of per-epoch state — `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` — plus the global `pendingInstantWithdraws`. On the normal (non-default) claim path, `claimInstantWithdrawRequest` only resets `instantWithdrawsRequests[_user]` to 0; the per-epoch entries are never freed. This mirrors CVE-2021-46924: `pending_skb` allocated at probe time but never released on the remove path. Here the "leaked" per-epoch ledger entry is later re-read by `_claimDefaultedInstantWithdrawRequest` when a default is finalized with `defaultRecoveryEpoch` equal to that epoch, causing an underflow revert that permanently bricks `claimInstantWithdrawRequest` for that user.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

- `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (set at line 371) is not cleared.
- `instantWithdrawClaimsByEpoch[currentEpoch]` (line 372) is not decremented.

Later, after `finalizeDefault`, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest` (lines 382-385, 842-856):

```solidity
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
...
instantWithdrawsRequests[_user] -= claimBasis;   // underflows: aggregate is 0, stale epoch entry is not
_burn(_user, claimBasis);                        // would also revert: receipt already burned
```

If the user's instant request was made **and claimed** inside the same epoch that becomes `defaultRecoveryEpoch`, `claimBasis > 0` while `instantWithdrawsRequests[_user] == 0` and the user's receipt balance is 0. The subtraction at line 848 underflows (or `_burn` at line 854 reverts), so every subsequent `claimInstantWithdrawRequest` call for that user reverts.

### Impact Explanation
Permanent freezing of the victim's claims. If the user holds any other funded instant receipt, funded normal withdraw receipt routed through the same call sequence, or a `postDefaultRequests` balance, the funds backing those claims are unreachable because the shared claim entry point reverts before reaching `_transferFundedClaim` / `_claimPostDefaultWithdrawRequest`. Loss equals the full value of the user's remaining claimable receipts. The broken invariant is "one receipt, one payout path that terminates" — a stale epoch allocation is double-counted as an unclaimed defaulted receipt.

### Likelihood Explanation
Medium-low. Requires: (1) instant-withdraw mode enabled (`allowInstantWithdraw` true and the epoch not yet stopped, which is the normal operating mode — the test at `testInstantWithdraw` shows claims happen mid-epoch after `instantWithdrawDelay`); (2) the user requests and claims an instant withdrawal during epoch N; (3) the borrower defaults and the honest manager calls `finalizeDefault` while `epochNumber` is still N, so `defaultRecoveryEpoch == N`. Same-epoch claim-then-default is realistic because instant claims settle intra-epoch and defaults are epoch events. No attacker privilege is needed beyond being a tranche holder requesting a normal instant withdrawal — though notably the victim is the requester themselves, and the freeze is triggered by the honest borrower's default, so the exploitable surface is accidental rather than profitable. Confirmed gaps in existing guards: the `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` gate at line 382 does not distinguish already-claimed receipts, and no path clears `instantWithdrawsRequestsByEpoch` outside the default-claim branch itself.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the cleanup done by `_claimDefaultedInstantWithdrawRequest`: iterate the epochs covered by `instantWithdrawsRequests[_user]` (or track `lastInstantWithdrawRequest` per user) and zero `instantWithdrawsRequestsByEpoch[_user][epoch]` while decrementing `instantWithdrawClaimsByEpoch[epoch]`. Alternatively, in `_claimDefaultedInstantWithdrawRequest`, bound `claimBasis` by `instantWithdrawsRequests[_user]` and treat an already-burned receipt as claimed. Add a regression test: request → fund → claim instant withdrawal in epoch N → default + `finalizeDefault` in epoch N → assert `claimInstantWithdrawRequest` does not revert.

### Proof of Concept
```solidity
// test/foundry/InstantWithdrawStaleEpoch.t.sol — fork per RESEARCHER.md
function testStaleInstantEpochEntryFreezesClaimAfterDefault() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    address victim = makeAddr('victim');
    _depositWithUser(victim, 100 * ONE_SCALE);

    _startEpochAndCheckPrices(1);

    // 1) victim requests an instant withdraw during epoch N
    uint256 trancheBal = IERC20Detailed(address(AAtranche)).balanceOf(victim);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));

    // 2) manager funds instant liquidity; victim claims -> aggregate reset,
    //    but instantWithdrawsRequestsByEpoch[victim][N] remains non-zero
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();
    vm.prank(victim);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(IdleCreditVault(address(strategy)).instantWithdrawsRequests(victim), 0);
    assertGt(
        IdleCreditVault(address(strategy)).instantWithdrawsRequestsByEpoch(victim, strategy.epochNumber()),
        0,
        'stale per-epoch receipt leaked'
    );

    // 3) victim opens a second instant request (funded) in the same epoch
    vm.prank(victim);
    cdoEpoch.requestWithdraw(trancheBal / 4, address(AAtranche));
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();

    // 4) borrower defaults; manager finalizes in the same epoch N
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(); // triggers _checkDefault path
    uint256 recovered = /* recovered amount per finalizeDefault formula */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // 5) victim's claim reverts forever: stale epoch entry makes
    //    instantWithdrawsRequests[victim] -= staleBasis underflow
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note: I was unable to fully verify the gating inside `IdleCDOEpochVariant.claimInstantWithdrawRequest` (e.g., `allowInstantWithdraw` flag checks) and the exact epoch value assigned to `defaultRecoveryEpoch` at finalization, because tool access ended before those reads returned. If `defaultRecoveryEpoch` is set to `epochNumber` at finalization time, the scenario holds as written; if it is set at `stopEpoch`, the claim must land in the epoch preceding the default instead, which does not change the bug's nature.
