### Title
Deposit-receiver approval revocation can be frontrun to force-lock the receiver's vault units - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.setDepositReceiverApproval()` lets a receiver grant or revoke a depositor's permission to call `deposit()`/`mint()` on the receiver's behalf. When a receiver submits a revocation (`approved=false`), an approved depositor can watch the mempool and frontrun that transaction with a minimal `deposit()` call while the old approval is still active. This re-arms `userUnitsRefundableUntil[receiver]`, freezing the receiver's vault units from `redeem()`, `withdraw()`, and even plain transfers for a full `depositRefundTimeout` window — directly subverting the receiver's expressed intent, the same root cause as the referenced `toggleRoll()` frontrunning issue.

### Finding Description
`setDepositReceiverApproval` is an ordinary, unauthenticated (non-`requiresAuth`) user function: `depositReceiverApprovals[msg.sender][depositor] = approved;` [1](#0-0) 

`deposit()`/`mint()` validate the receiver via `_requireValidReceiver`, which only checks `receiver == msg.sender || depositReceiverApprovals[receiver][msg.sender]`: [2](#0-1) 

Both `deposit()` and `mint()` call `_syncDeposit`, which unconditionally sets `userUnitsRefundableUntil[receiver] = block.timestamp + depositRefundTimeout` for the *receiver*, regardless of who the caller (`msg.sender`, the depositor) is: [3](#0-2) 

This refundable-until timestamp is enforced as a hard lock in two places:
- Sync `redeem()`/`withdraw()` revert with `Aera__UnitsLocked` while locked: [4](#0-3) [5](#0-4) 
- `MultiDepositorVault._update` also blocks any ERC20 transfer of vault units while `areUserUnitsLocked(from)` is true: [6](#0-5) 

Broken invariant: a permission-toggle (`setDepositReceiverApproval`) that a user believes takes effect atomically with their transaction can instead be raced by the counterparty, whose transaction executes first using the still-valid old permission state, subverting the granter's intent — exactly the pattern described in the `toggleRoll()` report (a "disable" toggle transaction can be frontrun by an action that depends on the old, still-active permission).

Ordinary-user attack sequence:
1. Receiver `R` calls `setDepositReceiverApproval(D, true)` to let depositor `D` deposit on `R`'s behalf once (e.g., a one-off gift/service deposit).
2. `R` later decides to revoke: submits `setDepositReceiverApproval(D, false)`.
3. `D` observes this pending tx in the mempool and frontruns it with `deposit(token, tokensIn=1 wei-scale dust, minUnitsOut=0-ish, receiver=R)` (or `mint`), which is accepted because `depositReceiverApprovals[R][D]` is still `true` at execution time.
4. `_syncDeposit` sets/extends `userUnitsRefundableUntil[R]` to `block.timestamp + depositRefundTimeout`.
5. `R`'s revocation then lands, preventing further deposits, but `R`'s units are now locked for the full `depositRefundTimeout` window and `R` cannot `redeem`, `withdraw`, or transfer their existing vault-unit balance during that period.

Note that this griefing is not limited to the frontrunning-a-revocation scenario: as long as an approval remains active (before it is ever revoked), `D` can repeatedly re-lock `R` with dust deposits any time the lock expires, indefinitely denying `R` the ability to synchronously exit or transfer their position — but the strongest, most "ordinary-user, no privileged role" analog to the reported issue is the frontrun-the-revocation race, since it shows the exact same broken assumption as `toggleRoll()`: that a disabling transaction takes effect before the counterparty can act on the old state.

### Impact Explanation
This freezes the receiver's vault-unit balance (temporarily denying `redeem`, `withdraw`, and ERC20 `transfer`) for the duration of `depositRefundTimeout`, which is admin-configurable up to `MAX_DEPOSIT_REFUND_TIMEOUT` (defined in `Constants.sol`; exact value not confirmed from available context, but enforced as a hard cap in `setDepositDetails`). This matches a "temporary freeze of user funds" impact class, consistent with a Medium-severity live-bounty finding for locking (not stealing) legitimate user funds for a bounded but attacker-controllable period, at negligible attacker cost (a dust-sized deposit).

### Likelihood Explanation
Prerequisites: the receiver must have previously granted `setDepositReceiverApproval` to some depositor (a normal, expected use case for delegated/gift deposits), and that depositor must act maliciously or be compromised. The attack is cheap (one dust-sized `deposit`/`mint` call, `tokensIn` need only satisfy the non-zero check) and requires only standard mempool observation to frontrun the revocation transaction; no special roles, oracle manipulation, or privileged access are needed. Feasibility is high whenever such an approval exists and the depositor is adversarial or later turns adversarial before revocation propagates.

### Recommendation
Do not let deposits made by a third-party depositor (i.e., where `msg.sender != receiver`) extend or re-arm `userUnitsRefundableUntil` for the receiver, or make the refund-lock apply only to the actual depositor (`msg.sender`) rather than the receiver, when the two differ. Alternatively, allow the receiver to specify, at approval time, a cap on how many/how large deposits may be made and/or require the revocation to also clear or cap any pending lock immediately, avoiding the race window used to subvert the revocation.

### Proof of Concept
```solidity
// Foundry PoC sketch (fork test) against ProvisionerV2 + MultiDepositorVault
function testFrontrunApprovalRevocationLocksReceiver() public {
    address receiver = makeAddr("receiver");
    address depositor = makeAddr("depositor");

    // 1) Receiver approves depositor for a legitimate one-off deposit
    vm.prank(receiver);
    provisioner.setDepositReceiverApproval(depositor, true);

    // depositor performs the expected deposit
    deal(address(token), depositor, 1000e18);
    vm.startPrank(depositor);
    token.approve(address(provisioner), type(uint256).max);
    provisioner.deposit(token, 1000e18, 0, receiver);
    vm.stopPrank();

    // receiver later decides they no longer trust the depositor,
    // submits revocation tx (not yet mined)
    // -- depositor frontruns with dust deposit while approval still true --
    deal(address(token), depositor, 1);
    vm.startPrank(depositor);
    token.approve(address(provisioner), 1);
    provisioner.deposit(token, 1, 0, receiver); // re-arms lock on receiver
    vm.stopPrank();

    // revocation now lands
    vm.prank(receiver);
    provisioner.setDepositReceiverApproval(depositor, false);

    // Assert receiver is locked out of redeem/withdraw and transfer
    assertTrue(provisioner.areUserUnitsLocked(receiver));
    vm.prank(receiver);
    vm.expectRevert(IProvisionerV2.Aera__UnitsLocked.selector);
    provisioner.redeem(token, 1, 0, receiver);

    vm.prank(receiver);
    vm.expectRevert(); // Aera__UnitsLocked from MultiDepositorVault._update
    IERC20(address(vault)).transfer(makeAddr("someoneElse"), 1);
}
```
This demonstrates that even after the receiver's revocation transaction is mined, their previously deposited funds remain frozen for `depositRefundTimeout`, directly because the depositor's frontrun deposit exploited the stale approval state — the same broken invariant as the `toggleRoll()` report.

    /// @notice Handles a synchronous deposit, records the deposit hash, and enters the vault
    /// @dev Reverts if the deposit hash already exists. Sets the refundable period for the user
    /// @param token The ERC20 token to deposit
    /// @param tokenAmount The amount of tokens to deposit
    /// @param unitAmount The amount of vault units to mint for the user
    /// @param receiver The address receiving the minted units
    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }
