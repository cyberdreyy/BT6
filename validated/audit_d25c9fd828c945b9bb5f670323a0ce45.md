### Title
Permissionless `deployCreditVault` lets anyone spin up a public credit vault with self-controlled manager/borrower/feeReceiver and capture LP deposits - ([File: contracts/IdleCreditVaultFactory.sol](contracts/IdleCreditVaultFactory.sol))

### Summary
`IdleCreditVaultFactory.deployCreditVault` (and `deployRevolvingCreditVault`) are `external` with no access control. The only checks are `_checkMinimumFees` (5% performance fee or 0.5% management fee) and a nonzero `manager`. Any EOA can therefore deploy a fully functional `IdleCDOEpochVariant` credit vault where they choose the manager, guardian, borrower, fee receiver, and — critically — can pass `keyring = address(0)`, which disables KYC gating so any wallet can deposit. The attacker then runs the epoch as manager, routes deposited underlying to the strategy's borrower (also attacker-controlled), and never repays, socializing the loss onto depositors.

### Finding Description
`deployCreditVault` at `contracts/IdleCreditVaultFactory.sol:92-124` has no `onlyOwner`/`onlyTreasury`/whitelist check. The deployer supplies:

- `strategyData.manager` — becomes the vault guardian (`cv.setGuardian(manager)`, line 303) and strategy manager, i.e. the role that starts/stops epochs.
- `strategyData.borrower` — the recipient of the credit line via `IdleCreditVault` (line 189).
- `cvParams.feeReceiver` — skims performance/management fees (line 302).
- `ancillaryParams.keyring` — if `address(0)`, `_deployKeyring` returns `address(0)` (line 169), `cv.setKeyringParams(address(0), ...)` disables wallet gating, making the vault open to the public.

Ownership of the CDO/strategy is transferred to `treasury` (lines 113-114), but that only restricts admin tuning — it does not gate deposits, does not control the borrower, and does not prevent the attacker-chosen manager from running epochs. The attacker-deployed vault is a real `TransparentUpgradeableProxy` pointing at the official `IdleCDOEpochVariant`/`IdleCreditVault` implementations, emitting the same `CreditVaultDeployed` event as legitimate treasury deployments, so it is indistinguishable on-chain from an official vault.

Attack sequence:
1. Attacker calls `deployCreditVault` with `manager = attacker`, `borrower = attackerContract`, `keyring = address(0)`, a popular `underlying` (e.g. USDC), a high advertised `apr`, and fees at the enforced minimums.
2. Victim LPs (no KYC required) deposit underlying and receive AA tranche tokens.
3. Attacker (as manager) starts the epoch; the strategy disburses the pooled underlying to the attacker-controlled borrower.
4. Borrower defaults; the epoch is stopped with a loss / default flow, and LP funds are gone.

### Impact Explanation
Direct loss of LP funds: the entire TVL deposited into the attacker-deployed vault is lent to an attacker-controlled borrower with no underwriting, no Keyring screening, and no treasury vetting. Because the vault uses the real implementations and the shared factory event, victims have no on-chain signal distinguishing it from an official Idle credit vault — the same trust problem as the Astaria `newPublicVault` issue. Loss is bounded only by deposits attracted; with a real underlying and an attractive APR it can be arbitrarily large.

### Likelihood Explanation
Deployment costs only a call to the factory; minimum fees are payable to the attacker's own `feeReceiver`, so cost is gas only. The main mitigation against loss is that victims must voluntarily deposit into a fresh vault — the protocol cannot force deposits — but the identical deployment provenance (same factory, same event, same implementations, optional no-KYC) makes social-engineering/phishing of LP capital realistic. Likelihood of a malicious deployment is high; magnitude depends on attracted deposits.

### Recommendation
Restrict `deployCreditVault` and `deployRevolvingCreditVault` to `treasury` (or an allowlisted deployer set), e.g. `if (msg.sender != treasury) revert OnlyTreasury();` on both functions. Additionally, consider requiring `keyring != address(0)` so public vaults cannot be deployed without credential gating.
