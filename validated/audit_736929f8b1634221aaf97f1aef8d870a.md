### Title
Later withdraw request launders a loss-haircutted receipt into a full-par claim - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
When a `stopEpochWithDuration` loss causes `collectWithdrawFunds` to under-fund pending withdraw receipts, the haircut is stored per epoch in `lossRecoveryPriceByEpoch[epochNumber]` and the affected claim is paid at that reduced price only through `_claimLossAdjustedWithdrawRequest`, which locates the loss epoch via `lastWithdrawRequest[_user]`. Because `requestWithdraw` always overwrites `lastWithdrawRequest[_user]` with the current epoch and keeps the old amount inside the aggregate `withdrawsRequests[_user]`, a user who files any new withdraw request after the loss epoch permanently detaches their haircutted receipt from its recovery price and is paid the full basis at par by `_claimFundedWithdrawRequest`, stealing the haircut from the vault's funded reserve.

### Finding Description
`collectWithdrawFunds(_amount)` records a pro-rata loss when the borrower under-funds pending receipts: it zeroes `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` [1](#0-0) . The intended claim path for that haircut is `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and pays `claimBasis * lossRecoveryPrice / RECOVERY_FULL` [2](#0-1) . However, `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds the new amount into the same `withdrawsRequests[_user]` aggregate that still contains the haircutted epoch-N basis [3](#0-2) . Once `lastWithdrawRequest` moves to a later epoch with no loss entry, the loss path returns 0 and `_claimFundedWithdrawRequest` pays the entire aggregate `normalAmount` at par, burning the receipt tokens the user legitimately holds [4](#0-3) . `_clearWithdrawClaimForEpoch` — the only code that removes an epoch's basis from `withdrawsRequests` — is never reached because the loss path early-returns on the zero price [5](#0-4) . This mirrors the reported bug class: a fresh request acts like the relayer's alternate `tradeID`, letting evidence (the par claim) of one obligation settle a different, haircutted obligation in full.

### Impact Explanation
Direct theft of vault underlyings equal to `claimBasis_N * (1 - lossRecoveryPrice)`. The vault collected only the post-haircut amount for epoch-N receipts, yet pays the full pre-haircut basis, so the excess is drained from underlyings reserved for other funded claimants or the recovery reserve — breaking the "one receipt one payout" and loss-waterfall invariants. The attack scales with the attacker's epoch-N request size and requires no privilege beyond holding tranche tokens (KYC'd lender).

### Likelihood Explanation
Requires a `stopEpochWithDuration` partial-funding event (borrower repays less than `pendingWithdraws`), which occurs precisely during credit stress — a realistic scenario for a credit vault. The attacker only needs to have a pending request in that epoch (or frontrun `stopEpoch` with one) and then submit a dust-sized second request in a later epoch, wait one more epoch boundary, and call `claimWithdrawRequest`. No guard blocks it: `requestWithdraw` does not prevent requesting while a loss-adjusted receipt is pending, and `_transferFundedClaim` only checks the default-recovery reserve, not loss-epoch reserves [6](#0-5) .

### Recommendation
Key loss-adjusted claims by per-epoch data instead of `lastWithdrawRequest`. In `_claimLossAdjustedWithdrawRequest`, iterate or track the user's earliest request epoch that has a nonzero `lossRecoveryPriceByEpoch` (e.g., store a per-user pending-loss-epoch pointer set in `requestWithdraw` when the epoch was loss-adjusted, or scan `withdrawsRequestsByEpoch`), and clear that epoch's basis via `_clearWithdrawClaimForEpoch` before falling through to the par claim. Alternatively, revert in `requestWithdraw` when the user has an uncleared receipt in a loss epoch.

```solidity
function testLossReceiptLaunderedToParClaim() external {
    // epoch N: user deposits, requests withdraw of W
    uint256 mintedAA = idleCDO.depositAA(100_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    cdoEpoch.requestWithdraw(mintedAA, address(AAtranche)); // receipt minted 1:1

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 W = vault.withdrawsRequests(address(this));

    // borrower under-funds: stopEpochWithDuration with _lossAmount>0 so
    // collectWithdrawFunds stores lossRecoveryPriceByEpoch[N] < RECOVERY_FULL
    // (manager/owner-driven honest call)
    _stopEpochWithPartialFunding(); // pendingWithdraws=0, lossRecoveryPriceByEpoch[N]=p<1

    // epoch N+1: attacker files a dust request -> lastWithdrawRequest = N+1
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(1, address(AAtranche));

    // epoch N+1 stops fully funded -> epochNumber = N+2 > lastWithdrawRequest
    _stopCurrentEpoch();

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    // BUG: paid W + dust at par instead of W*p/RECOVERY_FULL + dust
    assertEq(underlying.balanceOf(address(this)) - balPre, W + 1);
}
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
```
