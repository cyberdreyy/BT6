### Title
`getSupply` RPC handler computes circulating supply via unchecked subtraction, unlike its sibling REST endpoint - ([File: rpc/src/rpc.rs])

### Summary
The Sherlock report describes a missing cap check before an arithmetic operation (`AddEcosystemTokensMinted`), so a later subtraction (`ecosystemMaxSupply.Sub(ecosystemTokensAlreadyMinted)`) can go negative and propagate a bad/negative value into consensus logic, compromising a block. The agave analog is the `getSupply` JSON-RPC handler's computation of `circulating`, which performs a raw, unchecked subtraction of two `u64` values instead of the `saturating_sub` used by the equivalent `/v0/circulating-supply` REST handler right next to it.

### Finding Description
In `get_supply` in [1](#0-0)  the circulating supply is computed as:
```rust
let total_supply = bank.capitalization();
...
circulating: total_supply - non_circulating_supply.lamports,
```
This is a plain `-` on `u64` values, with no `checked_sub`/`saturating_sub` guard.

By contrast, the near-identical computation used by the `/v0/circulating-supply` REST endpoint in `calculate_circulating_supply_async` explicitly guards against this exact case:
```rust
Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
``` [2](#0-1) 

`non_circulating_supply.lamports` is computed by `calculate_non_circulating_supply` as the sum of balances of a fixed non-circulating pubkey list plus any stake accounts matching lockup/withdraw-authority criteria, scanned from the live account set: [3](#0-2) . `total_supply` is `bank.capitalization()`, an atomically-tracked running total that is supposed to always be `>=` the sum of any subset of account balances — but it is a separately-maintained counter (`fetch_add`/`fetch_sub` in various code paths, e.g. [4](#0-3) ) rather than a value recomputed from the same live scan. Any drift between the incrementally-tracked `capitalization` and the true summed balances of the non-circulating account set (whether from a latent tracking bug, a race with concurrent bank updates during the scan, or a future capitalization-affecting code path) makes this unchecked subtraction underflow.

The two call sites diverge in defensiveness for what is otherwise the same computation, which is a strong signal that the unguarded one in `rpc.rs` is a real oversight analogous to the missing cap check in the reported bug: the bounding check exists in one place but was dropped in the other.

### Impact Explanation
An underflow here doesn't crash the validator (Rust release builds wrap `u64` subtraction rather than panic), but it silently returns a bogus, enormous `circulating` supply value to any client calling `getSupply` — i.e., wrong data returned from a single low-rate, unprivileged JSON-RPC call, which callers (exchanges, explorers, tooling) rely on for economic/circulating-supply reporting. This matches the "wrong data returned" acceptance category for a single request with no special privileges.

### Likelihood Explanation
Reachability is trivial: `getSupply` is a standard unauthenticated JSON-RPC method exposed by every RPC-enabled agave node [5](#0-4) . The likelihood of the underlying underflow condition firing depends on `capitalization` and the non-circulating-account scan staying perfectly consistent at all times; under normal steady-state operation this holds, but the divergence from the guarded `saturating_sub` sibling shows the invariant is not treated as guaranteed by the code itself.

### Recommendation
Use `total_supply.saturating_sub(non_circulating_supply.lamports)` (or `checked_sub` with explicit error handling) in `get_supply` in `rpc/src/rpc.rs`, mirroring the guard already present in `calculate_circulating_supply_async` in `rpc/src/rpc_service.rs`, so the two computations are consistent and cannot underflow regardless of any transient capitalization/scan drift.

### Proof of Concept
Not directly reproducible purely from client input, since it requires `bank.capitalization()` to fall below the true sum of non-circulating account balances at the moment of the scan (e.g., via a capitalization-tracking bug or a race between the background scan in `calculate_non_circulating_supply` and concurrent bank account/capitalization updates). No such triggering bug was found and confirmed independently in this codebase during this review, so this should be treated as a defense-in-depth/consistency issue rather than a demonstrated exploitable underflow today.

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}
