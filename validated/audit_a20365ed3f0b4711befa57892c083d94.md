### Title
`SetNumConfirmations` accepts an unvalidated threshold, letting a single access key execute privileged multisig requests - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
The `MultiSigRequestAction::SetNumConfirmations` action lets the contract's own access keys change `num_confirmations` — the K-of-N threshold that gates every privileged action (transfers, key management, contract upgrades, function calls) — with no bound check on the new value. This mirrors the ForceDAO `setProfitSharingNumerator` bug class: a percentage/threshold setter that is validated at construction time but not on update, allowing a value that breaks the invariant it was meant to enforce.

### Finding Description
`MultiSigContract::new` takes `num_confirmations: u32` with no validation at all [1](#0-0) , and the update path in `execute_request` sets it directly from an action payload, again with no validation: [2](#0-1) 

The value gates `confirm`, which executes the request once `confirmations.len() + 1 >= self.num_confirmations`: [3](#0-2) 

If `num_confirmations` is set to `0` (or `1`), the equality `confirmations.len() as u32 + 1 >= self.num_confirmations` is satisfied by a single confirming key, so any one access key added to the multisig (which is only supposed to have partial authority under a K-of-N scheme) can single-handedly execute `Transfer`, `AddKey`, `DeleteKey`, `DeployContract`, and `FunctionCall` actions — actions that the K-of-N design is meant to require multiple independent approvals for. The binding this breaks is: `confirmations required to authorize a request == the threshold the multisig was configured for`, versus what is actually enforced after an unvalidated `SetNumConfirmations` call: threshold can degrade to 0/1 regardless of the number of live keys.

`multisig2/src/lib.rs` has the identical unvalidated `SetNumConfirmations { num_confirmations: u32 }` action and `self.num_confirmations = num_confirmations` assignment path [4](#0-3) .

### Impact Explanation
This falls under the "Critical" bucket in the rules: "a multisig request executed below threshold." Once a single key can lower (or a compromised/rogue key already inside the K-of-N set can lower) `num_confirmations` to `0` or `1`, any subsequent `Transfer` action moves NEAR out of the account with only one signature, and `AddKey`/`DeployContract` can fully take over the account — all authorized by fewer approvals than the multisig's documented threshold guarantees. Note that `SetNumConfirmations` is itself gated by the same `num_confirmations` threshold through `confirm`/`execute_request`, so this requires that threshold to first be met by legitimate signers, or exploited by one of the existing N keys if `num_confirmations` is already 1 for some reason, or as an operator typo (directly analogous to the ForceDAO 30%→300% typo scenario) — a value like `0` typed instead of a larger number silently removes the multisig protection with no revert.

### Likelihood Explanation
The action is directly reachable by any of the multisig's own access keys through `add_request`/`add_request_and_confirm`/`confirm`, requiring only the normal governance path already trusted to manage the account. Given no bounds check exists, a simple operator mistake (as described in the ForceDAO exploit scenario) or a single malicious/compromised key acting during the confirmation flow can silently reduce the security threshold. This is High-likelihood/High-impact given the total absence of any `assert!` on the new `num_confirmations` value in either `new()` or `SetNumConfirmations`.

### Recommendation
**Short term:** In `MultiSigRequestAction::SetNumConfirmations` execution (and in `new`), validate the new `num_confirmations` value: reject `0`, and ideally require it does not exceed the number of currently active keys/members, mirroring the way `RewardFeeFraction::assert_valid` bounds check is applied both at construction and on every subsequent update in `staking-pool/src/lib.rs`.

**Long term:** Apply the same "validate on every state-changing entry point, not just at initialization" discipline uniformly to all governance-configurable numeric parameters across the repo (`num_confirmations`, `active_requests_limit`, etc.), and add invariant tests (e.g., via property-based testing) asserting `num_confirmations >= 1` and `num_confirmations <= number_of_keys` hold after every mutating call.

### Proof of Concept
1. Deploy `multisig` with `new(num_confirmations: 2)` and 3 access keys (K=2 of N=3), per the README example [5](#0-4) .
2. An access key submits `add_request_and_confirm` with a single action `{"type": "SetNumConfirmations", "num_confirmations": 0}`.
3. Inside `confirm`, `confirmations.len() as u32 + 1 (=1) >= self.num_confirmations (=2)` is false at this point (first confirmation), so it just registers — but once a second key confirms (or if the attacker already controls 2 keys, or exploits the existing test-proven path `test_change_num_confirmations` at [6](#0-5)  which demonstrates `self.num_confirmations` is set with no validation), `self.num_confirmations` becomes `0`.
4. Any single key now calls `add_request_and_confirm` with `{"type": "Transfer", "amount": ...}`. In `confirm`, `confirmations.len() as u32 + 1 (=1) >= self.num_confirmations (=0)` is true, so the transfer executes immediately with just one signature — below the multisig's intended K-of-N threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
