Looking at Aera's `ProvisionerV2.sol` (the closest conceptual analog — deposit/redeem request lifecycle with collateral-like escrow), the relevant functions consistently bind the caller/effects to the correct party:

- `cancelRequest` explicitly requires `msg.sender == request.user` before any refund logic runs. [1](#0-0) 
- `refundRequest` doesn't check `msg.sender` but the payout always goes to `request.receiver` (or falls back to `request.user`), not to the caller — so an arbitrary caller can trigger it but cannot redirect funds to themselves. [2](#0-1) [3](#0-2)
