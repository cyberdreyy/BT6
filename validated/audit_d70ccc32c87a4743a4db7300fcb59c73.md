### Title
Stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` basis survives a funded claim, inflating default recovery and enabling double payout - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Linux bug clears a dequeued skb from the receive queue but leaves the stale `u->oob_skb` pointer, so later logic (poll, GC) still acts on the removed item. The direct analog is `claimInstantWithdrawRequest`: it dequeues the claim — zeroes the aggregate `instantWithdrawsRequests[_user]` and transfers funds — but never clears the per-epoch receipt `instantWithdrawsRequestsByEpoch[_user][epochNumber]` or the global `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) . Those stale per-epoch markers are exactly what `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve` and `_claimDefaultedInstantWithdrawRequest` read if the borrower defaults in the same epoch [2](#0-1) [3](#0-2) .

### Finding Description
`requestInstantWithdraw` records three pieces of state: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [4](#0-3) . On the normal (funded) path, `claimInstantWithdrawRequest` burns the receipt and sets only the aggregate to 0 [1](#0-0) . The per-epoch ledgers are only decremented inside `_claimDefaultedInstantWithdrawRequest` [5](#0-4) , i.e. they are assumed to still be live until a default.

Consequences when the same epoch later defaults and is finalized with `pendingInstantWithdraws != 0`:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still counts receipts already paid at par. `finalizeDefaultRecovery` therefore computes `totalBasis` too large, so `defaultRecoveryPrice = reserve / totalBasis` is lower than it should be — every legitimate defaulted claimant (normal withdrawers, active LPs via `activeFinalNAV`, other instant requesters) is diluted [6](#0-5) .
2. `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as already-held reserve. Because `instantBasis` includes already-claimed receipts, the strategy books underlying it already paid out as reserve, further corrupting the haircut [7](#0-6) .
3. An attacker who claimed a funded instant withdrawal in epoch E can make a second instant request in the same epoch (re-minting receipt tokens), then after default finalization call `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[_user][E]` (old + new basis), decrements `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch`, and pays `(staleBasis + newBasis) * defaultRecoveryPrice` from `defaultRecoveryReserve` — a second payout for an already-settled receipt, directly draining recovery funds owed to honest defaulted users [3](#0-2) .

This is the same defect shape as CVE-2024-35970: the dequeue path clears the primary pointer but leaves the per-key marker, and a later pass (GC / default finalization) operates on the stale marker.

### Impact Explanation
Direct theft and misdistribution of the default-recovery reserve: already-paid instant receipts are counted again in the claim basis and can be re-claimed at `defaultRecoveryPrice`, while all other claimants receive a diluted recovery ratio. Loss is bounded by the aggregate instant-withdraw volume claimed in the defaulting epoch; with a near-total default (recovery price < 1) the double payment comes entirely from honest users' recovery.

### Likelihood Explanation
Requires the confluence of: instant withdraws enabled, a funded instant claim during epoch E, and borrower default at the stop of epoch E with `pendingInstantWithdraws != 0` so `defaultInstantWithdrawsFinalized` is set [8](#0-7) . All attacker actions (request/claim instant withdraw, request again pre-default, claim post-finalization) are available to any KYC-passing lender; the honest borrower/manager merely trigger the epoch transitions. No privileged misbehavior needed.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch bookkeeping when the receipt is dequeued: set `instantWithdrawsRequestsByEpoch[_user][epochNumber] = 0` (or subtract the claimed amount per epoch) and decrease `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, mirroring `_claimDefaultedInstantWithdrawRequest`. Equivalently, track and clear the request epoch per user so a funded claim cannot leave residual basis for default finalization.

### Proof of Concept
Foundry fork sketch on the IdleCreditVault suite (`test/foundry/IdleCreditVault.t.sol`):

```solidity
// epoch N running, instant withdraws enabled (setInstantWithdrawParams)
uint256 amt = 100e6;
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(amt, address(AAtranche)); // via CDO entrypoint
// manager collects instant funds -> CDO funds attacker
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();            // funds pendingInstantWithdraws
skip(instantDelay + 1);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();        // paid at par
// BUG: instantWithdrawsRequestsByEpoch[attacker][N] == amt still,
//      instantWithdrawClaimsByEpoch[N] still includes amt
assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, N), amt); // stale

// attacker re-requests small amount to re-mint receipt tokens
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(amt, address(AAtranche));

// borrower defaults at stopEpoch of epoch N; owner finalizes recovery
// defaultPendingClaimBasis() now counts attacker's already-paid amt twice
// -> defaultRecoveryPrice diluted for all claimants
// attacker then:
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();        // pays (stale+new) * recoveryPrice
// assert: attacker recovered > newBasis * recoveryPrice; reserve drained
```

The pre-default assertion on `instantWithdrawsRequestsByEpoch` demonstrates the stale marker; the post-finalization claim demonstrates theft from `defaultRecoveryReserve`.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
