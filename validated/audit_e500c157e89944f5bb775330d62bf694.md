### Title
No role restriction on `GET /v2/config` and `/v2/config/v2` allows view-role users to read effective node configuration - ([File: core/web/router.go])

### Summary
`v2Routes` registers `ConfigController.Show` at `authv2.GET("/config", cc.Show)` and `authv2.GET("/config/v2", cc.Show)` without any `auth.RequiresXRole` wrapper, unlike almost every other sensitive endpoint in the same group. Since the `authv2` group only requires successful authentication (session or API token) and not a minimum role, any authenticated user—including one holding the lowest-privilege `view` role—can retrieve the full effective TOML configuration.

### Finding Description
In `core/web/router.go`, the `authv2` group is created with `auth.Authenticate(...)` covering `AuthenticateByToken` and `AuthenticateBySession`, which only verifies that the caller holds valid credentials of *any* role and does not enforce a minimum role: [1](#0-0) 

Within that group, most sensitive routes are explicitly wrapped with `auth.RequiresEditRole`, `auth.RequiresRunRole`, or `auth.RequiresAdminRole` (e.g., user management, key export/import, transfers). However, the config routes are registered bare: [2](#0-1) 

`ConfigController.Show` then calls `cfg.ConfigTOML()` and returns the effective (or user) TOML directly with no further authorization or field-level redaction check performed inside the handler: [3](#0-2) 

`ConfigTOML()` returns `g.inputTOML` and `g.effectiveTOML`, which are the full parsed configuration (not the separately redacted `secretsTOML`), including sections like `WebServer`, `Database`, chain configs (EVM/Solana/Cosmos/etc.), P2P, Pyroscope, Mercury, Threshold, CRE, and other operational settings: [4](#0-3) 

`RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` explicitly gate other routes by comparing `user.Role` against `clsessions.UserRoleView`/`UserRoleRun`/`UserRoleAdmin`, demonstrating that a `view` role is meant to be the most restricted tier in this authorization model: [5](#0-4) 

Since `/config` and `/config/v2` have no such wrapper, a `view`-role session or API token—normally intended only for read-only monitoring dashboards—can pull the full effective configuration TOML, which is inconsistent with the authorization-exactness invariant applied elsewhere in the same router.

### Impact Explanation
This is an information-disclosure issue: it exposes internal operational configuration (chain RPC endpoints, database settings, telemetry/Pyroscope endpoints, feature flags, webserver settings, etc.) to the lowest-privilege authenticated principal. It does not by itself expose secrets/passwords (those live in `secretsTOML`, which is not returned by this endpoint), and does not directly enable fund movement or job manipulation. It maps to a low/informational "information disclosure of node internals" class in the Chainlink bounty program rather than a critical/high finding, since the exposed data is operational configuration rather than private keys or credentials.

### Likelihood Explanation
Exploitation requires only a valid `view`-role session cookie or `view`-scoped API token/secret pair—no privilege escalation, timing, or race condition needed. Any attacker who has been issued (or otherwise obtains) view-only credentials can trivially and repeatably issue `GET /v2/config` or `GET /v2/config/v2` to retrieve the data. This is fully deterministic and reproducible.

### Recommendation
Wrap the config routes with an appropriate role check consistent with the rest of the router, e.g.:
```go
authv2.GET("/config", auth.RequiresEditRole(cc.Show))
authv2.GET("/config/v2", auth.RequiresEditRole(cc.Show))
```
or at minimum `auth.RequiresRunRole` if view-only access to non-sensitive config fields is desired, combined with redacting operationally sensitive fields (endpoint URLs, database DSNs, telemetry endpoints) from the TOML returned to non-admin roles.

### Proof of Concept
Go handler-level integration test plan (in `core/web`, alongside existing `config_controller_test.go` style tests):
1. Build a test app via `cltest.NewApplicationWithConfig`/`setupConfigControllerTests` (or equivalent helper used in existing controller tests) with a known TOML config containing an identifiable, non-default field, e.g. a distinctive `WebServer.AllowOrigins` or `EVM` RPC URL value.
2. Create a user with `Role = clsessions.UserRoleView` and obtain either a session cookie (via `/sessions` login) or a `view`-scoped API token/secret pair.
3. Issue `client.Get("/v2/config")` and `client.Get("/v2/config/v2")` using only the view credentials.
4. Assert `resp.StatusCode == http.StatusOK` (not `401`/`403`).
5. Parse the JSON API response body into `ConfigV2Resource` and assert `resource.Config` (the TOML string) contains the distinctive marker value planted in step 1, proving full effective config disclosure to a view-role principal.
6. As a control, repeat the same request against another bare-but-should-be-restricted route (e.g. `auth.RequiresEditRole`-wrapped route) with the same view credentials and assert it returns `401 Unauthorized`, confirming the role-enforcement mechanism works generally but is simply missing on `/config` and `/config/v2`.

```go
func (cc *ConfigController) Show(c *gin.Context) {
	cfg := cc.App.GetConfig()
	var userOnly bool
	if s, has := c.GetQuery("userOnly"); has {
		var err error
		userOnly, err = strconv.ParseBool(s)
		if err != nil {
			jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("invalid bool for userOnly: %w", err))
			return
		}
	}
	var toml string
	user, effective := cfg.ConfigTOML()
	if userOnly {
		toml = user
	} else {
		toml = effective
	}
	jsonAPIResponse(c, ConfigV2Resource{toml}, "config")
}
```

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
