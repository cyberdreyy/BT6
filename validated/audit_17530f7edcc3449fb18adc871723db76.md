### Title
Rejection signatures can be replayed as acceptance signatures because `BlockAccepted`/`BlockRejection` sign only `signer_signature_hash`, with no decision binding - (File: `libsigner/src/v0/messages.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
`BlockAccepted::new` and `BlockRejection::new`/`from_validate_rejection` both compute their `signature` as `private_key.sign(signer_signature_hash.bits())` — the ECDSA signature covers only the block hash, never an accept/reject discriminant. When peer signers ingest an observed `BlockAccepted` via `handle_block_signature`, they recover the signer's public key straight from that signature and credit the corresponding signer's weight as an *acceptance*, with no check that the message actually originated from that signer's own StackerDB slot.

### Finding Description
`BlockRejection::new` and `BlockAccepted::new` sign identical data — `signer_signature_hash.bits()` — with no domain tag distinguishing "I accept H" from "I reject H": [1](#0-0) [2](#0-1) 

Because rejections are broadcast in the clear on the public StackerDB `BlockResponse` contract, an attacker (a single signer slot, no special access) can observe any honest signer Y's `BlockRejection{signer_signature_hash: H, signature: S}` for a block they also see proposed, and extract `S`. `S` is a valid secp256k1 signature over `H` signed by Y's private key — nothing about `S` encodes "rejected."

The attacker then constructs `BlockResponse::Accepted(BlockAccepted{signer_signature_hash: H, signature: S, ..})` and gossips it through their own StackerDB slot (the only slot they legitimately control; the StackerDB transport-layer `chunk.sig` check only verifies the *chunk* was written by the attacker's own key, not that its payload content originates from that same key).

Peer signers process incoming `BlockAccepted` messages in `handle_block_signature`: [3](#0-2) 
This function recovers the public key directly from the embedded signature (`recover_to_pubkey_without_validating_low_s(block_hash.bits(), signature)`), then only checks `is_valid_signer(signer_address)` — membership in the whole signer set — with no verification that the delivering StackerDB slot_id corresponds to that recovered address. `S`, being genuinely Y's signature over `H`, recovers to Y's real address, passes `is_valid_signer`, and Y's acceptance weight is credited via `store_and_process_block_signature`, even though Y actually rejected the block.

This contrasts with the miner-side ingestion path in `stackerdb_listener.rs`, which does bind the recovered pubkey to the expected pubkey for the delivering `slot_id`: [4](#0-3) 
— but the signer-to-signer aggregation path (`handle_block_signature`) has no equivalent slot binding, so the splice succeeds there.

### Impact Explanation
This breaks chain safety by turning a rejection into a counted acceptance ("a rejection recounted as acceptance"). If enough honest rejections for an invalid/non-canonical block are spliced this way, an attacker (holding only one signer slot) can manufacture apparent acceptance weight from other honest signers who actually rejected the block, potentially pushing the block's tallied acceptance weight over the signing threshold and causing an invalid or non-canonical block to be signed. The attack is repeatable for every rejection an honest signer broadcasts, and costs nothing beyond observing public StackerDB traffic and posting one gossip message from the attacker's own slot.

### Likelihood Explanation
Preconditions are minimal: the attacker needs a single signer slot (to post to StackerDB) and must observe a `BlockRejection` from any other signer for the block hash in question — both trivially available since rejections and acceptances are broadcast publicly on the `BlockResponse` StackerDB contract. No majority of signers, no node-operator access, no other signer's key, and no auth token are required. The attack is fully repeatable across proposals and reward cycles, since the only enforcement (`is_valid_signer`) checks address set membership, not slot provenance.

### Recommendation
Bind the signed payload's decision (accept vs reject) and message context into the signed digest, e.g. sign `Sha256(domain_tag || decision_byte || signer_signature_hash)` instead of raw `signer_signature_hash.bits()`, so a rejection signature cannot verify as an acceptance signature for the same hash. Additionally, in `handle_block_signature` (and the equivalent rejection handler), verify that the recovered public key matches the expected signer for the StackerDB `slot_id` the message arrived on, mirroring the check already present in `stackerdb_listener.rs`.

### Proof of Concept
```rust
// libsigner/src/v0/messages.rs test module
#[test]
fn reject_signature_verifies_as_accept_signature() {
    let sk = StacksPrivateKey::random();
    let pk = StacksPublicKey::from_private(&sk);
    let hash = Sha512Trunc256Sum([7u8; 32]);

    // Honest signer rejects block H
    let rejection = BlockRejection::new(
        hash,
        RejectReason::SortitionViewMismatch,
        &sk,
        false,
        0,
        0,
    );

    // Attacker splices the captured rejection signature into an "accepted" response
    let spliced_accept = BlockResponse::accepted(hash, rejection.signature, 0, 0);
    let accepted = spliced_accept.as_block_accepted().unwrap();

    // Signature is indistinguishable from a genuine acceptance signature over H
    assert!(pk.verify(hash.bits(), &accepted.signature).unwrap());
    // handle_block_signature would recover `pk` and credit it as an acceptance
    // despite the underlying key having only ever signed a rejection of H.
}
```
This demonstrates the accept/reject decision is not cryptographically bound — only conveyed by unsigned message framing — confirming the vulnerability.
