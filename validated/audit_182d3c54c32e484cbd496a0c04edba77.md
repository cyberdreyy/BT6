### Title
Block-validation deadline not enforced during `load_tenure_info`/`tenure_begin` setup, allowing a slow tenure-open to force an immediate "timeout" rejection of a valid block - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
In `NakamotoBlockProposal::validate`, the `block_deadline` used to bound per-tx validation time is computed only *after* `builder.load_tenure_info(...)` and `builder.tenure_begin(...)` complete, at `stackslib/src/net/api/postblock_proposal.rs:726-731`. If those setup calls are slow, the deadline is already in the past by the time the tx loop starts, and the first transaction is rejected with a generic `ValidateRejectCode::InvalidBlock` / "Block validation timed out" message.

### Finding Description
The relevant code: [1](#0-0) 
shows that `load_tenure_info` and `tenure_begin` are invoked unconditionally before `block_deadline` is even constructed, and the deadline is only checked inside the `for (i, tx) in self.block.txs.iter().enumerate()` loop. This matches the claim that setup cost is not bounded by `timeout_secs` and that overrun setup time is folded into the very first deadline check, producing a rejection indistinguishable from a genuine per-tx timeout (both use `ValidateRejectCode::InvalidBlock` with a "Block validation timed out" reason, per the existing test `test_block_proposal_validation_timeout` in `stackslib/src/net/api/tests/postblock_proposal.rs:517-534`).

However, I was unable to confirm the load-bearing premise of the exploit: that `load_tenure_info`/`tenure_begin` can be made "arbitrarily slow" by crafting an expensive `parent_stacks_header` chain. I attempted to locate and read the bodies of `NakamotoBlockBuilder::load_tenure_info` and `NakamotoBlockBuilder::tenure_begin` in `stackslib/src/chainstate/nakamoto/miner.rs` to check whether these functions perform any work whose cost scales with prior chain/contract state (e.g. full state replay), or whether they merely open a Clarity/MARF handle rooted at the parent block (an O(1)-ish operation independent of how "expensive" the parent's stored contracts are). The search for their definitions matched but I did not get their contents rendered before running out of iterations, so this key causal step is unverified.

This matters because:
- Every other node in the network (miners producing the actual block, and every full node accepting it into the chainstate) must also call the equivalent tenure-open logic when processing this same block/tenure. If tenure-open cost genuinely scaled with "expensive prior Clarity state," this would be a general chain-wide performance/consensus problem, not a validation-specific flaw exploitable by a lone unprivileged miner-slot holder — and it would already need to be bounded by Clarity's own cost-limit/MARF-lookup design (which is O(1) per key, not O(chain depth) or O(prior contract complexity)) to keep the chain live at all.
- The attacker precondition given ("attacker controls tenure setup cost via legitimate but expensive contract state from prior blocks they mined") does not establish a mechanism by which `tenure_begin`'s or `load_tenure_info`'s cost is unbounded or attacker-controllable beyond ordinary block cost limits, which are already enforced per-block during normal chain processing (not specific to this validation path).

### Impact Explanation
If confirmed, an attacker who can make `load_tenure_info`/`tenure_begin` take longer than `timeout_secs` could force per-signer rejection of an otherwise valid block on liveness grounds, with reject reason indistinguishable from an ordinary per-tx timeout. This would match the High "signer wedged into never signing valid blocks" liveness category — but only if the setup cost is genuinely and repeatably attacker-controllable independent of normal cost-limit enforcement that already governs block-level Clarity execution cost. Without confirmation that `tenure_begin`/`load_tenure_info` scale with attacker-chosen prior state (as opposed to being bounded MARF/trie lookups), this cannot be confirmed as a distinct vulnerability beyond the already-known fact that the block-level deadline is a coarse, non-monotonic check (documented and tested behavior, not a hidden defect).

### Likelihood Explanation
Unconfirmed. The described precondition (mining a chain of prior expensive blocks to inflate future validation setup cost) is not, on the evidence gathered, a defined attack surface — Clarity/MARF operations to open the chainstate at a specific block header are generally not scan/replay operations across chain history, and Clarity execution cost is separately budgeted and enforced per block during ordinary mining/validation, which is out of scope per the audit rules ("node-side consensus acceptance" and "volumetric DoS" are explicitly excluded).

### Recommendation
N/A pending confirmation. If a genuine unbounded-cost path is found inside `load_tenure_info`/`tenure_begin`, the fix would be to start the `block_deadline` clock before those calls (or apply a bounded budget to them directly) so that setup time is counted against `timeout_secs`, and to emit a distinct reject code (e.g. `ValidateRejectCode::SetupTimeout`) so the signer's retry/backoff logic in `stacks-signer` can distinguish "block cannot execute in time" from "chain state itself is too expensive to open," avoiding permanent blacklisting of the block hash on a transient/setup timeout.
