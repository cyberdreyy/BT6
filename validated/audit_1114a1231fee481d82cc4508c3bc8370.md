### Title
Miner-controlled shadow-block version bit reaches an `assert!` panic in normal block-proposal validation - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
A block proposal's `version` field is fully miner-controlled data that is authenticated only by the signer/miner signatures over the header, not restricted in value before static validation. The high bit of `version` (`0x80`) is the shadow-block flag [1](#0-0) . Nakamoto's own header static-validation test confirms that a header with the shadow-block bit set alongside an otherwise-correct low-7-bit version number **passes** `validate_header_static` [2](#0-1) . However, the node-side path used to validate an incoming (non-shadow, network-submitted) block proposal, `validate_normal_nakamoto_block_burnchain`, begins with an unconditional `assert!(!block.is_shadow_block())` [3](#0-2) , and this is the very function the `postblock_proposal.rs` request handler invokes as its first "static validation check" on a miner-submitted proposal [4](#0-3) .

### Finding Description
This mirrors the Hats `address(0)` bug-class in the following sense: a piece of attacker-controlled data (`version`'s shadow bit, analogous to the hat being sent to `address(0)`) is accepted as syntactically well-formed by one code path (`validate_header_static`, analogous to `isWearerOfHat`/`balanceOf`), but a downstream invariant that a *different*, security-critical code path silently assumes ("proposals reaching normal-block validation are never shadow blocks") is enforced only by an `assert!`, not by a graceful rejection. Since a single miner fully controls the `version` byte of the block header it proposes over StackerDB/RPC, it can set the `0x80` bit while keeping the rest of the header (and low 7 version bits) valid for the current epoch. This block will:
1. Pass `validate_header_static` (per the test at `nakamoto/tests/mod.rs:578-585`), which explicitly ignores the shadow bit when checking the version number.
2. Be routed by `postblock_proposal.rs`'s `process_request` to `validate_normal_nakamoto_block_burnchain` as the very first static check performed on the proposal.
3. Immediately hit `assert!(!block.is_shadow_block())`, which is a hard Rust panic, not a `Result`-based rejection.

No majority of signers, key access, or auth token is required — only the ability to submit a block proposal (i.e., control of a single mining slot / miner keypair), which is squarely within the analog scope this task allows.

### Impact Explanation
This breaks the liveness of the block-validation path (`postblock_proposal.rs`) that every connected signer depends on to validate and sign blocks. A panic occurring inside the request-handling logic for `POST /v3/block_proposal` can, depending on the runtime's panic-catching behavior around that specific call, either fail only that request (in which case the signer/miner simply times out waiting for a validation response for that particular proposal and must resubmit) or, if that panic is not isolated by a `catch_unwind` boundary around this handler, take down the worker thread/task servicing block-proposal validation for the node, denying validation service to all signers attached to that node until it is restarted. Either way, this is a signer-liveness wedge: signers are unable to obtain a validation verdict for what would otherwise be normal, well-signed blocks, matching the "High — signer wedged into never signing valid blocks" impact category. I could not fully verify from the indexed context whether the HTTP/RPC dispatch layer wraps each request in `catch_unwind` (which would bound the blast radius to a single failed request rather than a full service crash); this is the main source of uncertainty in severity.

### Likelihood Explanation
Any single miner (one slot, no consensus from other parties needed) can trigger this by setting one bit in the `version` field of a block header it proposes — an extremely low-cost, always-reachable action requiring no timing race, no majority, and no special access. The only defense would be an early, explicit rejection of the shadow bit for network-submitted proposals, which does not currently exist prior to the `assert!`.

### Recommendation
In `validate_normal_nakamoto_block_burnchain` (`stackslib/src/chainstate/nakamoto/mod.rs`), replace the `assert!(!block.is_shadow_block())` with an explicit, non-panicking rejection (e.g., return `Err(ChainstateError::InvalidStacksBlock("shadow block bit set on normally-submitted block".into()))`), so that any miner-supplied proposal with the shadow-block version bit set is cleanly rejected by `postblock_proposal.rs` rather than causing a panic in the validation path used by all connected signers.

### Proof of Concept
1. A miner builds a normal, well-formed Nakamoto block for the current epoch (correct low-7-bit version, valid txs, valid miner signature) as it would for any tenure.
2. Before broadcasting the proposal (over StackerDB / to the node's `postblock_proposal` RPC), the miner sets the high bit of `header.version` (`header.version |= 0x80`), matching the shadow-block test fixture pattern shown in `nakamoto/tests/mod.rs:578-585`.
3. The block header hash is recomputed with this version (version is part of both `miner_signature_hash_inner` and `signer_signature_hash_inner` per `stackslib/src/chainstate/nakamoto/mod.rs:1008-1045`), so it is still internally self-consistent and passes `validate_header_static`.
4. The miner submits this proposal to a stacks-node's `postblock_proposal` endpoint.
5. `process_request` calls `NakamotoChainState::validate_normal_nakamoto_block_burnchain`, which immediately executes `assert!(!block.is_shadow_block())` and panics because `is_shadow_block()` returns `true` for this header.
6. The signer(s) depending on this node's validation response never receive a proper accept/reject and cannot make progress on this (or, if the panic escapes request isolation, any subsequent) proposal, wedging block signing.
