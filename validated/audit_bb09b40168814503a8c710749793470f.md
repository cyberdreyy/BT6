## Finding

### Title
Malicious maker/receiver can block `EscrowDst._withdraw` when the destination asset is native ETH, temporarily freezing the taker's escrowed funds - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` sends the destination asset to the maker (or the order's designated `receiver`) via `_uniTransfer`, which for native ETH (`token == address(0)`) resolves to `_ethTransfer`, a low-level `call{value: amount}("")` forwarding all remaining gas [1](#0-0) . If that call fails, the whole transaction reverts with `NativeTokenSendingFailure`, and this failure is unconditionally propagated up through both `withdraw()` and `publicWithdraw()` since they share the same internal `_withdraw` [2](#0-1) . An unprivileged maker who sets a contract with a reverting/gas-heavy fallback as the receiving address for the destination leg can therefore make every withdrawal attempt (private and public) permanently fail, exactly mirroring the root cause described in the referenced report: an untrusted recipient's fallback blocking a keeper/taker-driven state transition that also pays out a reward to the caller.

### Finding Description
The destination-escrow's recipient address is populated from data the maker fully controls at order-signing time: `immutablesComplement.maker = order.receiver.get() == address(0) ? order.maker : order.receiver` [3](#0-2) . This value flows unchanged into `Immutables.maker` used by the taker when calling `createDstEscrow` and later `withdraw`/`publicWithdraw` [4](#0-3) .

When the destination token is native ETH (`dstImmutables.token == address(0)`), `createDstEscrow` requires the taker to fund the clone with `safetyDeposit + amount` in native currency [5](#0-4) . Later, `_withdraw` pays fees, then sends the remaining `amount` to `immutables.maker.get()` via `_uniTransfer`, which for native token calls `_ethTransfer` with unlimited forwarded gas and reverts the entire transaction on failure [6](#0-5) [7](#0-6) .

Both the private path (`withdraw`, restricted to the taker) and the public path (`publicWithdraw`, open to any access-token holder) call this same `_withdraw` function [8](#0-7) . Since the maker (an unprivileged order signer) fully controls the receiving address and can deploy a contract there whose `receive`/fallback always reverts, every call to `withdraw` or `publicWithdraw` for that swap will revert, for the entire withdrawal window (private + public), for every taker/resolver that tries.

This does not require any privileged role — it is triggered purely by the maker choosing a hostile `receiver` address in their signed order, which is then honored as-is by `_postInteraction`/`createDstEscrow`.

### Impact Explanation
While the taker/resolver eventually recovers their funds via `cancel()` once the `DstCancellation` timelock is reached — because `cancel()` sends the token to `taker.get()` (i.e., to `msg.sender` under `onlyCaller(taker)`, bypassing the malicious maker address) [9](#0-8)  — the resolver's escrowed native ETH (the `amount` plus safety deposit) is unusable and frozen for the full withdrawal window of the live swap. No resolver can ever complete the intended withdrawal to the maker, and the safety-deposit incentive that should reward whichever keeper calls withdraw is unreachable during that time. This matches the "temporary freezing of funds during the live swap lifecycle" High-impact category in the bounty scope.

### Likelihood Explanation
Likelihood is high in the sense that it requires no special privilege — only that the maker signs an order specifying, as `receiver`, a contract address with a reverting fallback, and that the destination token for that leg is native ETH. Any user who wants to disrupt/DoS a particular resolver's destination-side withdrawal (e.g., to force settlement to go through `cancel()` instead, or purely for griefing) can do so deterministically for every native-ETH destination swap they create.

### Recommendation
Do not let a hostile recipient's native-transfer failure block core escrow state transitions that also pay a reward to the caller. Options:
- Use a bounded-gas transfer (e.g., a fixed low gas stipend) for the native transfer to the maker, and fall back to a pull-based withdrawal (crediting an internal balance the maker can later `claim()`) instead of reverting the whole transaction on failure.
- Alternatively, decouple the safety-deposit/caller-reward payment from the maker-facing transfer so a maker's revert cannot block a resolver's incentive and cannot indefinitely block `publicWithdraw`.

### Proof of Concept
1. Maker signs a Fusion order with `order.receiver` set to `MaliciousReceiver`, a contract whose `receive()` always reverts, and with `dstToken == address(0)` (native ETH) for the destination leg.
2. Taker fills the order; `_postInteraction` records `immutablesComplement.maker = order.receiver` (the malicious contract) [3](#0-2) .
3. Taker calls `createDstEscrow` funding it with `safetyDeposit + amount` in ETH [4](#0-3) .
4. During the withdrawal window, taker calls `withdraw(secret, immutables)`; `_withdraw` attempts `_ethTransfer(MaliciousReceiver, amount)`, which reverts, causing the whole `withdraw` call to revert with `NativeTokenSendingFailure` [2](#0-1) .
5. Any other resolver calling `publicWithdraw` during the public-withdrawal window hits the same revert.
6. Funds remain frozen in the `EscrowDst` clone until the `DstCancellation` timelock elapses, at which point the taker must use `cancel()` to recover funds (the maker never receives the intended tokens).

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```
