### Title
Unbounded per-epoch deposit aggregation causes unrecoverable deposits-only payload import failure - ([File: crates/consensus/derive/src/attributes/stateful.rs])

### Summary
`StatefulAttributesBuilder::prepare_payload_attributes` pulls **all** `TransactionDeposited` logs from a single L1 origin block via `derive_deposits` and unconditionally packs every decoded deposit into the mandatory L2 block's transaction list, with no cap on deposit count or cumulative `gas_limit`. If the aggregate reserved gas of the deposits in one L1 epoch exceeds the L2 block gas limit, the resulting deposits-only payload cannot be executed, and the engine's failure-handling path treats this as an unrecoverable critical error rather than something that can be dropped or retried, because deposits — unlike sequencer transactions — cannot be stripped out.

### Finding Description
`derive_deposits` scans every receipt/log in the L1 origin block and returns a `Vec<Bytes>` of encoded deposit transactions with no upper bound on the number of deposits or their total `gas_limit`: [1](#0-0) 

These deposits are then unconditionally appended to the block's transaction list that becomes the `BasePayloadAttributes.transactions` for the *next mandatory L2 block* of that epoch — there is no gas-budget check performed here, only later during execution: [2](#0-1) 

At execution time, each transaction's `gas_limit` is checked against the block's remaining gas, and post-Regolith deposits are **not** exempt from this check: [3](#0-2) [4](#0-3) 

When the L1-origin-adopting block consists solely of deposits (`is_deposits_only()` returns true) and import fails because the deposits collectively exceed the block gas limit, `SealTask::insert_payload` treats this as a **critical, unrecoverable** condition instead of attempting a normal Holocene deposits-only fallback (which is only used for *non*-deposits-only blocks, by stripping non-deposit transactions): [5](#0-4) 

Since every deposit-only payload derived from that same L1 epoch is identical for every honest sequencer/verifier node (they all replay the same L1 receipts through `derive_deposits`), this failure is deterministic and not something a single node can route around — it reproduces on all nodes attempting to derive/execute that epoch.

### Impact Explanation
This is directly analogous to the reported Centrifuge `Gateway.withBatch()` bug: on the "sending" side (`derive_deposits`/attributes builder), an unbounded number of L1-originated messages (deposit transactions) are batched into a single atomic unit (the mandatory L2 block for that epoch) without any validation of aggregate resource cost. On the "receiving" side (block execution / engine import), the batch either fits or the whole unit fails. Unlike ordinary sequencer transactions, deposits are mandatory and cannot be selectively dropped, so a failure here surfaces as `SealTaskError::DepositOnlyPayloadFailed`, which the code explicitly logs as `"Critical: Deposit-only payload import failed"` with no retry/skip path. This can halt sequencer block production and/or verifier derivation for that epoch, matching the "node halt" / permanent-DOS impact class.

### Likelihood Explanation
Reaching `derive_deposits` requires only that many `TransactionDeposited` logs be emitted from the configured deposit contract within a single L1 block — i.e., an unprivileged L1 depositor issuing many cheap deposit calls (each requiring only L1 gas for the depositing transaction itself, while the requested L2 `gas_limit` field is attacker-controlled up to whatever cap the L1-side deposit contract enforces). This repository's derivation/execution code does not itself impose any secondary cap on the number of deposits or their cumulative reserved gas before committing them to a mandatory block, so the only mitigating control would have to live in the L1 deposit contract (e.g., an OP-stack-style `ResourceMetering` gas-throttling mechanism). That L1 contract is outside this repository's scope and was not available to verify here, so I cannot confirm whether it fully closes this gap; absent such an L1-side control (or if it is misconfigured/bypassed), this path is reachable by any ordinary L1 account.

### Recommendation
Add an explicit, protocol-enforced cap in `derive_deposits`/`prepare_payload_attributes` limiting either the number of deposits or their cumulative reserved gas admitted from a single L1 origin block relative to the L2 `SystemConfig.gas_limit`, and return a clean, well-typed pipeline error (not a "critical" unrecoverable halt) when the cap is exceeded, so operators have a defined recovery path instead of a permanent derivation/import stall.

### Proof of Concept
1. An attacker issues N `TransactionDeposited` events from the configured deposit contract inside a single L1 block, each with `gas_limit` set high enough that their sum exceeds the L2 chain's configured block `gas_limit` (e.g., many deposits each requesting close to the max per-deposit gas allowed by the L1 depositing contract).
2. When the derivation pipeline processes this L1 origin block, `derive_deposits` (crates/consensus/derive/src/attributes/stateful.rs:286-311) returns all N deposits unfiltered.
3. `prepare_payload_attributes` builds a deposits-only payload containing all N deposit transactions (stateful.rs:220-239), with `gas_limit` set from `SystemConfig.gas_limit`.
4. During block building/import, the EL rejects the block once cumulative deposit gas exceeds `block_gas_limit` (crates/common/evm2/src/executor.rs:252-277).
5. `SealTask::insert_payload` sees `is_deposits_only() == true` and returns `SealTaskError::DepositOnlyPayloadFailed` (crates/consensus/engine/src/task_queue/tasks/seal/task.rs:94-99) — a critical failure with no fallback, reproducible by every node deriving the same L1 epoch.

async fn derive_deposits(
    block_hash: B256,
    receipts: &[Receipt],
    deposit_contract: Address,
) -> Result<Vec<Bytes>, PipelineEncodingError> {
    let mut global_index = 0;
    let mut res = Vec::new();
    for r in receipts {
        if Eip658Value::Eip658(false) == r.status {
            continue;
        }
        for l in &r.logs {
            let curr_index = global_index;
            global_index += 1;
            if l.data.topics().first().is_none_or(|i| *i != Deposits::EVENT_ABI_HASH) {
                continue;
            }
            if l.address != deposit_contract {
                continue;
            }
            let decoded = Deposits::decode(block_hash, curr_index, l)?;
            res.push(decoded);
        }
    }
    Ok(res)
}

        let ty = tx.ty();
        let is_deposit = tx.is_deposit();

        // Reject a transaction whose reserved gas exceeds the block's remaining gas, before
        // executing it. For an EIP-8130 transaction the reservation adds the payer's worst-case
        // authentication gas (metered on top of the sender-signed gas limit), matching the
        // reference `reserved_block_gas`. Pre-Regolith deposits are exempt (matching the reference's
        // `is_regolith || !is_deposit` guard); every other transaction is checked.
        let mut reserved_gas = tx.gas_limit();
        if let Some(signed) = tx.as_eip8130() {
            let payer_auth =
                IntrinsicGas::max_payer_auth_cost(signed).map_err(HandlerError::external)?;
            reserved_gas = reserved_gas.saturating_add(payer_auth);
        }
        let block_gas_limit = self.evm.block().gas_limit.saturating_to::<u64>();
        let block_available_gas = block_gas_limit.saturating_sub(self.gas_used);
        let is_regolith =
            (self.evm.config_spec_id().upgrade() as u8) >= (BaseUpgrade::Regolith as u8);
        if reserved_gas > block_available_gas && (is_regolith || !is_deposit) {
            return Err(HandlerError::external(BlockGasLimitExceeded {
                transaction_gas_limit: reserved_gas,
                block_available_gas,
            }));
        }
