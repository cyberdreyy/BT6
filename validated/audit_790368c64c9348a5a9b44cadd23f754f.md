### Title
Multisig executes requests using confirmations from removed members, letting requests pass below the live K-of-N threshold - (File: multisig2/src/lib.rs)

### Summary
The multisig contract's `DeleteMember`/`DeleteKey` action only purges pending confirmations for requests that the removed member **created**, but never purges the removed member's confirmations recorded on requests that member merely **confirmed**. `confirm()` counts entries in that stale `confirmations` set without re-validating that every recorded confirmor is still a current member, so a request can execute once the set's length reaches `num_confirmations` even though one or more of the confirmors it contains have since been removed from the multisig. This mirrors the reported TSS bug class of "confirmations/approvals counted vs. currently-live/eligible parties" — a request can be authorized and executed with fewer genuinely-live confirmors than the configured threshold.

### Finding Description
`confirm()` in [1](#0-0)  only checks that the *current caller* is a member (`current_member()`), then tests `confirmations.len() as u32 + 1 >= self.num_confirmations` and, if satisfied, executes the request. It never re-validates that the *other* addresses already stored in `confirmations` are still members.

`delete_member()` in [2](#0-1)  removes pending requests and confirmations only for requests where `r.member == member` (i.e. requests the removed member *created*):
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
It does not scan `self.confirmations` for entries containing the removed member as a mere *confirmor* on requests created by someone else. Those stale confirmations remain in the `HashSet<String>` for `confirmations` (declared at [3](#0-2)  ), where the key `member.to_string()` is compared purely by string equality, independent of live `self.members` membership.

The v1 contract has the identical pattern: `DeleteKey` in [4](#0-3)  only cleans requests where `r.signer_pk == pk` (the creator), leaving stale confirmor entries for that `pk` on other pending requests, which `confirm()` at [5](#0-4)  counts the same way.

Concretely, with members `{A, B, C, D}` and `num_confirmations = 3`:
1. `A` creates request `X` (e.g. `Transfer`) and self-confirms — `confirmations(X) = {A}` (1/3).
2. `B` confirms `X` — `confirmations(X) = {A, B}` (2/3, below threshold, no execution yet).
3. Separately, members vote to remove `B` via `DeleteMember{B}` (a legitimate, unrelated governance action; `delete_member` only requires the remaining member count to stay `>= num_confirmations`, which holds: 3 remaining members `{A,C,D}` for a threshold of 3). `B`'s confirmation on `X` is **not** cleaned up because `X` was created by `A`, not `B`.
4. `C` confirms `X` — `confirmations(X).len() + 1 == 3 >= num_confirmations` → the request executes, using confirmations `{A, B, C}`, even though `B` is no longer a member.

The transfer thus executes with only 2 genuinely live authorizing members (`A`, `C`) instead of the required 3, breaking the K-of-N custody binding the contract is supposed to enforce (`live confirmors == num_confirmations`, not `stored confirmation entries == num_confirmations`).

### Impact Explanation
This is a Critical-severity issue per the rubric ("a multisig request executed below threshold"): funds held by the multisig account can be transferred, keys added/deleted, or contracts deployed/upgraded with fewer live, currently-authorized members than the configured `num_confirmations` threshold — i.e. an unauthorized move of NEAR (or any privileged multisig action) below the intended security threshold.

### Likelihood Explanation
The precondition is only that a request accumulates confirmations over multiple blocks/transactions before reaching threshold (normal usage — confirmations are not required to be submitted atomically) and that membership changes (a normal, expected multisig operation) occur in between. No foundation, owner, or out-of-band privilege is needed beyond being one of the existing members whose confirmation later becomes stale; this is a realistic operational sequence for any multisig with rotating membership and is not dependent on mempool timing, redeploys, or social engineering.

### Recommendation
When removing a member (`DeleteMember`/`DeleteKey`), scan and purge that member's confirmation entry from **every** pending request's `confirmations` set, not just requests they created. Alternatively/additionally, have `confirm()` re-validate at execution time that every entry in the stored `confirmations` set still corresponds to a current member of `self.members` before comparing the count against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. As `A`: `add_request_and_confirm` a `Transfer` request `X` to an attacker-controlled account → `confirmations(X) = {A}`.
3. As `B`: `confirm(X)` → `confirmations(X) = {A, B}` (2/3, not executed).
4. As `A`/`C`/`D` (any 3 members): create and confirm a `DeleteMember{member: B}` request → `B` removed from `self.members`; `X` is untouched because `X.member == A`.
5. As `C`: `confirm(X)` → `confirmations(X).len() + 1 == 3 >= num_confirmations` → `execute_request` runs `Transfer` to the attacker's account, despite only `A` and `C` being live members who ever authorized `X`. [1](#0-0) [2](#0-1)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
