### Title
Reorg-timing bypass in `check_parent_tenure_choice`: an unknown local timestamp is silently treated as "proven late", letting a signer approve a reorg it should reject - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` is supposed to permit a miner to reorg (skip) a prior tenure only when that tenure's first block was demonstrably "poorly timed" — i.e., it arrived within `first_proposal_burn_block_timing` of the next sortition. When the signer has no local `approved_time` for that block, the code substitutes a hard-coded value of `0`, which always satisfies the "poorly timed" comparison. This turns "we don't actually know when this arrived" into "it definitely arrived late", silently granting the reorg permit that the timing rule was designed to withhold.

### Finding Description
In `check_parent_tenure_choice`: [1](#0-0) 

```
let checked_proposal_timing = if let Some(sortition_state_received_time) = sortition_state_received_time {
    let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
        sortition_state_received_time.saturating_sub(approved_at)
    } else {
        info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
        0
    };
    if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
        // ... permit the reorg (push tenure into superseded_tenures) ...
        continue;
    }
    true
} else {
    false
};
```

The intended equality here is: *reorg allowed* ⇔ *(sortition_time − proposal_time) < first_proposal_burn_block_timing*, i.e. the superseded tenure's block genuinely arrived late relative to the burn chain. But when `local_block_info.approved_time` is `None` — which happens whenever this signer never itself pre-committed to or locally accepted that block (per `BlockInfo::check_state`/`mark_locally_accepted`/`mark_pre_committed` semantics, `approved_time` is only stamped on those paths) — the code substitutes `proposal_to_sortition = 0`. Since `0 < first_proposal_burn_block_timing` for any positive configured timing, the branch unconditionally takes the "permit the reorg" path, exactly as if the block had arrived instantly before the next sortition. This is true even if the block was actually mined and globally accepted immediately after the prior sortition, i.e., the opposite of "poorly timed."

This "no local record" condition is reachable without the signer ever needing to have voted maliciously: a signer that (re)joins the signer set, restarts and reloads its DB, or learns about the tenure's tip purely through `check_latest_block_in_tenure`'s node-sync path (which calls `mark_globally_accepted()` on a block fetched from the node's tip, not through the pre-commit/local-acceptance flow that stamps `approved_time`) will have `get_first_approved_block_in_tenure` return a `BlockInfo` whose `approved_time` is `None`, even though the tenure produced exactly one properly-timed block. [2](#0-1) 

A miner fully controls the input side of this check: it proposes a tenure-change block whose `prev_tenure_consensus_hash`/parent tenure choice reorgs a prior sortition's tenure. The signer-side rule that is supposed to gate this (`check_parent_tenure_choice`, called from both v1's `check_proposal`/`validate_tenure_change_payload` and v2's `validate_tenure_change_payload`) is what decides `RejectReason::ReorgNotAllowed` vs. acceptance: [3](#0-2) [4](#0-3) 

### Impact Explanation
Any signer that hits the `approved_time == None` branch will incorrectly record the reorg as permitted (`mark_tenure_superseded`) and pass `check_parent_tenure_choice` for a reorg that the protocol's own timing rule says should be refused (`ReorgNotAllowed`). Because `reorg_permit_stands` later excludes any conflicting signature outright once a permit is recorded, that same signer will go on to co-sign (pre-commit and eventually sign) the reorging tenure-change block instead of rejecting it — i.e., the signer signs a block/tenure transition that its own chainstate rules were designed to block. This matches the "Critical" bar: a signer signing a non-canonical/conflicting block it should have rejected.

### Likelihood Explanation
The vulnerable branch does not require any signer collusion, majority control, or key compromise — it is triggered purely by the *absence* of a local timestamp, a state reachable through ordinary signer lifecycle events (restart, resync, late join to the signer set, or DB migration) combined with a single miner choosing to reorg a tenure whose first block was, in fact, well-timed (not poorly timed). The miner needs no special access beyond normal block-proposal authorship for its slot.

### Recommendation
Do not default `proposal_to_sortition` to `0` (i.e., "definitely late") when `approved_time` is unknown. Instead, treat an unknown local timestamp as inconclusive and fail closed — i.e., do not grant the reorg permit purely on the basis of missing local data; either query the node/other trusted source for corroborating information about when the tenure's first block actually appeared, or default to disallowing the reorg (`return Ok(false)`) when this information cannot be established locally.

### Proof of Concept
1. Signer `S` restarts (or newly joins the signer set) after tenure `T1` has already produced and had globally accepted its single block `B1`; `S` never itself set `approved_time` for `B1` (it only observes `B1` as already globally accepted via `check_latest_block_in_tenure`'s node-tip sync path, which calls `mark_globally_accepted()` without stamping `approved_time`).
2. A miner starts tenure `T2`, choosing to reorg past `T1` (i.e., its block-commit's parent tenure is not `T1`, even though `T1` produced exactly one block, `B1`, that was *not* poorly timed).
3. `S` receives the `T2` tenure-change block proposal. `validate_tenure_change_payload` → `check_parent_tenure_choice` is invoked; `tenures_reorged` includes `T1`; `get_globally_accepted_block_count_in_tenure(T1) == 1` so the "more than one block" guard does not fire; `get_first_approved_block_in_tenure(T1)` returns `Some(B1)` with `approved_time == None`.
4. The `else` branch sets `proposal_to_sortition = 0`, which is `< first_proposal_burn_block_timing`, so the reorg is treated as permitted and `T1` is marked superseded.
5. `S` proceeds to pre-commit/sign the `T2` tenure-change block, even though, under the intended rule, `T1`'s `B1` was not poorly timed and the reorg should have been rejected with `RejectReason::ReorgNotAllowed`.
