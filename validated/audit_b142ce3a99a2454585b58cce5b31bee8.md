### Title
ERC4626 withdraw-cap bypass check can indefinitely delay epoch settlement - (contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

`ProgrammableBorrower.onStopEpoch` validates a required withdrawal against the vault’s total share value (`_currentVaultAssets()`), but it does not check the ERC4626-configured withdrawal limit before calling `vault.withdraw(shortfall)`. If a vault user drains immediately withdrawable liquidity so that `maxWithdraw(address(this)) < shortfall <= _currentVaultAssets()`, `stopEpoch` reverts with `StopEpochVaultLiquidityUnavailable` instead of settling or defaulting.

### Finding Description

During `stopEpoch`, `IdleCDOEpochVariant` asks the programmable borrower to provide `_amountToPullFromBorrower + _pendingWithdraws`. `onStopEpoch` treats the vault’s full convertible asset value as coverage:

```solidity
if (shortfall > _currentVaultAssets()) return true;
try vault.withdraw(shortfall, address(this), address(this)) { ... }
catch {
  revert StopEpochVaultLiquidityUnavailable();
}
```

This conflates economic coverage with currently withdrawable liquidity. ERC4626 vaults can report a positive asset value while `maxWithdraw` is lower due to a configured withdrawal cap, illiquid allocation, or depleted idle liquidity.

Because the hook reverts, the CDO leaves `isEpochRunning` enabled, does not mark the pool defaulted, and leaves withdrawal receipts pending. If the liquidity shortage persists, the same revert can recur indefinitely.

### Impact Explanation

All lenders’ funds can be temporarily frozen for the duration of the vault liquidity shortage. Withdrawal requesters cannot claim while the epoch remains running, and a healthy pool also cannot transition into the buffer state or settle epoch yield.

The frozen amount is the CDO’s full outstanding NAV plus pending withdrawal claims. There is no upper protocol-enforced bound on the delay while the vault remains illiquid.

### Likelihood Explanation

An unprivileged user of the programmable borrower’s ERC4626 vault can withdraw available idle liquidity from that vault. Once `maxWithdraw` falls below the borrower’s shortfall while the borrower’s shares still economically cover the amount, every `stopEpoch` call reverts.

No privileged role, borrower misconduct, forged accounting, or price manipulation is required. The existing `StopEpochVaultLiquidityUnavailable` catch prevents a false default but converts the liquidity limit into a retryable settlement block.

### Recommendation

Before attempting the withdrawal, query `vault.maxWithdraw(address(this))` and handle a limit shortfall explicitly. Possible mitigations include:

- withdraw only the currently available `maxWithdraw` portion and expose a dedicated resumable settlement path;
- make persistent liquidity exhaustion route to an explicit delayed-default state after a bounded grace period;
- provide a manager-controlled epoch-settlement path that can mark the borrower delinquent after a configured deadline rather than leaving the epoch running indefinitely.

The accounting check should distinguish “economically covered but temporarily illiquid” from “covered and presently withdrawable.”

### Proof of Concept

A Foundry test can reproduce this with the existing programmable-borrower fixture and a controllable ERC4626 vault:

```solidity
function testStopEpochBlockedWhenMaxWithdrawBelowShortfall() public {
    uint256 depositAmount = 10_000 * oneScale;
    uint256 drawAmount = 5_000 * oneScale;

    idleCDO.depositAA(depositAmount);
    _startEpochAndCheckPrices(0);

    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(drawAmount);

    // A normal ERC4626 vault user consumes all immediately withdrawable liquidity.
    // The programmable borrower's shares still represent sufficient assets, so
    // shortfall <= convertToAssets(shares), but withdraw(shortfall) is capped.
    vm.prank(vaultUser);
    vault.withdraw(vault.maxWithdraw(vaultUser), vaultUser, vaultUser);

    uint256 required = programmableBorrower.borrowerInterestOwedNow()
        + strategy.pendingWithdraws();
    uint256 onHand = underlying.balanceOf(address(programmableBorrower));
    uint256 shortfall = required - onHand;

    assertGt(shortfall, vault.maxWithdraw(address(programmableBorrower)));
    assertLe(shortfall, vault.convertToAssets(vault.balanceOf(address(programmableBorrower))));

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pendingWithdrawsBefore);
}
```

The important assertion is that `_currentVaultAssets()` says the withdrawal is covered while `maxWithdraw` says it cannot currently be executed.
