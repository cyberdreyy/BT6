### Title
Stale per-epoch instant-withdraw basis inflates default recovery and breaks final claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` — the same "already removed" inconsistency class as the reference bug. When the borrower later defaults in the same epoch, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` read the stale per-epoch key and count already-paid-out instant claims as still-backed reserve, producing an inflated `defaultRecoveryPrice` that the strategy's real balance cannot honor.

### Finding Description
The vault tracks instant withdrawals under two keys:

- aggregate: `instantWithdrawsRequests[_user]` (IdleCreditVault.sol:366)
- per-epoch: `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (IdleCreditVault.sol:371-372)

On a normal claim, only the aggregate is cleared:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [1](#0-0) 

The per-epoch entries are only cleared inside `_claimDefaultedInstantWithdrawRequest` (IdleCreditVault.sol:842-856), which runs solely when a default has been finalized — and by then the stale values have already been consumed by accounting:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (IdleCreditVault.sol:644-648).
- `_defaultPrefundedInstantReserve` returns `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as "already-held" reserve (IdleCreditVault.sol:716-723).

`collectInstantWithdrawFunds` (IdleCreditVault.sol:398-403) reduces `pendingInstantWithdraws` when the CDO funds claims, but not the epoch basis. So the difference `instantBasis - pendingInstant` is meant to be "collected but unclaimed" cash sitting in the strategy — yet it silently includes claims whose underlying was already transferred out.

### Impact Explanation
Scenario (running epoch N, instant mode):

1. Users A and B request instant withdrawals of 100 each: `instantWithdrawClaimsByEpoch[N] = 200`, `pendingInstantWithdraws = 200`.
2. CDO calls `collectInstantWithdrawFunds(200)` → `pendingInstantWithdraws = 0`. Wait — if it fully collects, `defaultInstantWithdrawsFinalized` is false and the epoch basis is skipped, so the exploitable window requires partial collection/coverage or new requests. More precisely: A claims 100 (aggregate cleared, underlying leaves the strategy, `instantWithdrawsRequestsByEpoch[A][N]` stays 100). B's request remains partially unfunded so `pendingInstantWithdraws > 0`.
3. Borrower defaults; `finalizeDefaultRecovery` runs:
   - `defaultPendingClaimBasis` still counts the full `instantWithdrawClaimsByEpoch[N] = 200` including A's already-paid 100.
   - `_defaultPrefundedInstantReserve` reports `instantBasis - pendingInstant` as held cash, but A's 100 is gone — reserve is overstated by exactly the claimed amount.
4. `defaultRecoveryPrice = reserveAmount / totalBasis` is computed on real underlyings that do not exist. B's defaulted claim pays `(claimBasis * price) / 1e18` from `defaultRecoveryReserve` via `_transferDefaultRecovery`; the last claimers' transfers underflow the actual balance and revert, or earlier claims drain more than their fair share.

Broken invariant: one receipt → one payout, and reserve accounting must equal held underlying. The result is mispriced recovery (effective theft between claimants) and permanent freezing of the tail of recovery claims; additionally `defaultInstantWithdrawsFinalized` and reserve are computed off phantom backing, so `defaultRecoveryReserve` exceeds the strategy balance. Note A cannot double-claim directly because `instantWithdrawsRequests[A] -= claimBasis` underflows (IdleCreditVault.sol:848) — the damage is the inflated reserve/price, not a second payout to A.

### Likelihood Explanation
Requires: instant-withdraw mode enabled for the epoch, at least one user claiming collected instant funds, at least one instant receipt still unfunded, then a borrower default and `finalizeDefaultRecovery` in the same epoch. Borrower default is an ordinary (honest-actor) event; the attacker is simply an unprivileged lender who claimed early — no privileged action needed to trigger the mispricing. The stale-key pattern is structurally identical to the reference report: a getter/check reads a key that the mutation path never cleared.

### Recommendation
In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][currentRequestEpoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` symmetrically with `instantWithdrawsRequests[_user]` — i.e., keep every representation of "an instant receipt exists in epoch N" consistent, and update state before any function that re-reads it (same remediation as the reference fix). Because `instantWithdrawsRequests` is aggregated across epochs, the claim should track which epoch basis each receipt belongs to (e.g., a `lastInstantWithdrawRequest` marker analogous to `lastWithdrawRequest`) so the correct epoch key is cleared.

### Proof of Concept
Foundry fork sketch (see `test/foundry/IdleCreditVault.t.sol` helpers like `_depositWithUser`, `stdstore` patterns):

```solidity
// epoch N running, instant withdrawals enabled
// A and B deposit AA and requestInstantWithdraw via cdoEpoch
// CDO collects only part of instant funds:
//   collectInstantWithdrawFunds(X) with X < instantBasis so pendingInstantWithdraws > 0
// A calls cdoEpoch.claimInstantWithdrawRequest() -> receives underlying
assert(strategy.instantWithdrawsRequests(A) == 0);
// BUG: per-epoch key still set
assert(strategy.instantWithdrawsRequestsByEpoch(A, epochN) != 0);

// borrower defaults in epoch N -> finalizeDefaultRecovery via CDO
// assert strategy.defaultPendingClaimBasis() still includes A's paid 100
// assert _defaultPrefundedInstantReserve overcounts by A's claimed amount
// after recovery claims:
// sum(payouts) > actual underlying held by strategy -> last claim reverts
```

Key assertions: `instantWithdrawsRequestsByEpoch[A][epochN]` remains non-zero after A's successful claim, and `instantWithdrawClaimsByEpoch[epochN]` is not reduced — mirroring `getHeldTokenExistence` returning true after `remove`.
