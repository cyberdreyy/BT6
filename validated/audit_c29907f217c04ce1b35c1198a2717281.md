### Title
Stale stake/vote cache entries survive an unprivileged owner-reassignment, corrupting delegated-stake accounting used for consensus - (File: `runtime/src/stakes.rs`)

### Summary
`StakesCache::check_and_store` decides whether to keep, update, or evict a cached stake/vote delegation purely by re-inspecting the *current* owner and lamports of the account being stored. If a previously-cached stake or vote account has its `owner` changed away from the Stake/Vote program (e.g. reassigned to the System program) while it still holds lamports, the function takes neither the "zero lamports" removal branch nor the vote/stake upsert branch — it silently returns without touching the existing cache entry. The stale `Delegation`/`VoteAccount` entry therefore remains in `Stakes<StakeAccount>` (`stake_delegations`, `delegated_stakes`, `vote_accounts`) even though the on-chain account is no longer a stake/vote account at all.

### Finding Description
`StakesCache::check_and_store` explicitly documents this gap: [1](#0-0) 

The code only removes a cache entry when `account.lamports() == 0` (i.e., account closed), and only upserts when the current `owner` matches the Vote or Stake program id. If the owner is changed to any other program (e.g. System program) while lamports remain non-zero, none of the branches fire, so the previous stake/vote cache entry for that pubkey is left untouched — exactly the same bug class as the reported issue where removing an association (`BaseV2Gauge::removeBribeFlywheel`) fails to clean up the corresponding registry entry (`MultiRewardsDepot`), leaving stale state that no longer matches the true, current relationship.

Ownership of an arbitrary account (including a stake account) can be reassigned by the account's own signer via the System program's `Assign`/`AssignWithSeed` instructions, which only require the target account itself to sign — no stake-authority or vote-authority check is involved: [2](#0-1) [3](#0-2) 

Because a stake account's keypair holder (not necessarily the stake/withdraw authority conceptually, but whoever controls the account's private key) can issue `SystemInstruction::Assign` to change the account's owner from the Stake program to the System program (or any other program) in a single unprivileged transaction, the bank's post-transaction `check_and_store` call sees an account with non-zero lamports whose owner is no longer `stake_program`/`solana_vote_program`, and takes no action — leaving the old `StakeAccount`/`VoteAccount` entry (and its contribution to `delegated_stakes` and `vote_accounts`'s stake totals) permanently cached.

### Impact Explanation
`Stakes<StakeAccount>` and its `delegated_stakes`/`vote_accounts` totals feed directly into consensus-critical stake-weight computations (leader schedule, vote-account stake weighting, and reward/stake calculations), as seen in the surrounding upsert/removal logic that carefully maintains `delegated_stakes` and `vote_accounts` invariants on legitimate state transitions: [4](#0-3) [5](#0-4) 

If the owner-change path is not routed through the same removal logic, the cached delegation becomes decoupled from the real, current state of the account (it is no longer a stake account at all), so a validator's derived stake weight for the associated vote account no longer reflects reality. This is a stake-accounting corruption analogous to the reported bug's "stale asset not removed from registry" pattern, potentially causing divergence between cached (used-for-consensus) stake state and actual on-chain account state.

### Likelihood Explanation
Reaching this path requires only a single transaction, signed by the stake account's own keypair, invoking the System program's `Assign` instruction to change the stake account's owner while it retains lamports — no elevated privilege, no special validator/leader/network position is needed. This is directly reachable by any unprivileged transaction sender who controls a stake account's keypair.

### Recommendation
In `StakesCache::check_and_store`, before dispatching purely on the account's *current* owner, first check whether the pubkey has an existing cached stake or vote entry whose owner no longer matches the account's current owner, and explicitly evict it (call `remove_stake_delegation`/`remove_vote_account`) in that case, as flagged by the existing TODO comment referencing solana-labs/solana#24200.

### Proof of Concept
Conceptual PoC (not independently executed, based on static code analysis):
1. Create and fund a stake account `S`, delegate it to vote account `V` (so `S` is cached in `Stakes<StakeAccount>` with `delegated_stakes[V] += stake`).
2. Using the private key of `S` (the account itself, not the stake/withdraw authority), submit a transaction with `SystemInstruction::Assign { owner: system_program::id() }` targeting `S`.
3. After execution, `S.owner()` is now the System program, `S.lamports() > 0`. `StakesCache::check_and_store` is invoked for `S`; since `lamports() != 0` and owner matches neither vote nor stake program, no removal branch runs.
4. `Stakes::stake_delegations` and `delegated_stakes[V]` still contain `S`'s stake, even though `S` no longer is a stake account — the cached, consensus-relevant stake weight for `V` no longer corresponds to any real stake account.

        // Zero lamport accounts are not stored in accounts-db

                    stakes.remove_vote_account(pubkey)
                };

                stakes.remove_stake_delegation(
                    pubkey,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
            }
            return;
        }

    fn upsert_stake_delegation(
        &mut self,
        stake_pubkey: Pubkey,
        stake_account: StakeAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,
    ) {
        debug_assert_ne!(stake_account.lamports(), 0u64);
        let delegation = stake_account.delegation();
        let voter_pubkey = delegation.voter_pubkey;
        let stake = delegation_effective_stake(
            delegation,
            self.epoch,
            &self.stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        match self.stake_delegations.insert(stake_pubkey, stake_account) {
            None => {
                self.add_delegated_stake(voter_pubkey, stake);
                self.vote_accounts.add_stake(&voter_pubkey, stake);
            }
            Some(old_stake_account) => {
                let old_delegation = old_stake_account.delegation();
                let old_voter_pubkey = old_delegation.voter_pubkey;
                let old_stake = delegation_effective_stake(
                    old_delegation,
                    self.epoch,
                    &self.stake_history,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
                if voter_pubkey != old_voter_pubkey || stake != old_stake {
                    self.sub_delegated_stake(&old_voter_pubkey, old_stake);
                    self.add_delegated_stake(voter_pubkey, stake);
                    self.vote_accounts.sub_stake(&old_voter_pubkey, old_stake);
                    self.vote_accounts.add_stake(&voter_pubkey, stake);
                }
            }
        }
    }

fn assign(
    account: &mut BorrowedInstructionAccount,
    address: &Address,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    // no work to do, just return
    if account.get_owner() == owner {
        return Ok(());
    }

    if !address.is_signer(signers) {
        ic_msg!(invoke_context, "Assign: account {:?} must sign", address);
        return Err(InstructionError::MissingRequiredSignature);
    }

    account.set_owner(&owner.to_bytes())
}
