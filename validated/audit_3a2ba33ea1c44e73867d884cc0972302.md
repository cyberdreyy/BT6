The clearest analog to the “anyone can call `initialize()`” bug class is the `init_global_fee_state` instruction, which creates the program-wide singleton `FeeState` PDA with **no caller authorization check** and lets the caller supply the `admin_key` argument directly.

### Title
Permissionless `init_global_fee_state` allows front-running to seize global fee-admin authority - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
`init_global_fee_state`/`initialize_fee_state` initializes the program's single, global `FeeState` PDA (seeded only by the constant `FEE_STATE_SEED`, with no user-specific component). The instruction's account context (`InitFeeState`) requires only a fee-paying `Signer`, with no check that the caller is the program's upgrade authority, deployer, or any pre-established privileged account. The handler blindly assigns the caller-supplied `admin_key` and `fee_wallet` arguments to `fee_state.global_fee_admin` and `fee_state.global_fee_wallet`.

### Finding Description
`InitFeeState` derives the `fee_state` account from the fixed seed `[FEE_STATE_SEED.as_bytes()]` only: [1](#0-0) 

and the handler sets the caller-controlled `admin_key`/`fee_wallet` with no authorization gating at all: [2](#0-1) 

Because the PDA is a program-wide singleton (there is exactly one `FeeState` account for the whole deployed program, unlike `MarginfiGroupInitialize`, which creates an independent group scoped to its own creator), the *first* successful call to this instruction permanently claims `global_fee_admin` for that caller — this is analogous to the reported `Staking.sol` issue where `initialize()` lacking `onlyOwner` lets "anyone" set critical initial state. Any address that submits this instruction before the legitimate deployer's setup transaction lands (e.g., by front-running it in the same slot/block, or racing a delayed deployment script) becomes the permanent `global_fee_admin`, and sets an arbitrary `global_fee_wallet` of their choosing.

The lib.rs entrypoint documents this as "(Runs once per program)" with no admin gate in the doc comment, corroborating that access control was never intended to be enforced beyond "whoever gets there first": [3](#0-2) 

Once `global_fee_admin` is attacker-controlled, the attacker gains persistent authority over protocol-wide fee configuration via `edit_global_fee_state` (fees, wallet, `pause_delegate_admin`), and control of `global_fee_wallet`, which is the destination for all SOL fees (and canonical ATA target for non-SOL fees) collected protocol-wide, as documented in the `FeeState` struct: [4](#0-3) 

### Impact Explanation
This grants an unauthorized attacker persistent control of the single, program-wide fee-admin role and fee-collection wallet. Every group's fees (`fee_state_cache`, propagated via `propagate_fee_state`), and future `edit_global_fee_state` calls (fixed/rate fees, liquidation/order fees, pause-delegate admin) would be attacker-controlled, redirecting protocol revenue and enabling further abuse (e.g., setting `pause_delegate_admin` to pause the protocol, or draining fee flows to an attacker wallet). This is a durable, financial-effect authorization bypass at the highest privilege tier in the fee subsystem.

### Likelihood Explanation
Exploitability is fully dependent on winning a one-time race to be the very first caller of `init_global_fee_state` after program deployment. On a public network this is a realistic front-running/MEV scenario (the instruction and its expected accounts are fully public/derivable, and no secret or off-chain gate protects the deployer's initialization transaction). In practice, teams generally initialize such singletons immediately after deploy, which narrows but does not eliminate the window (e.g., deploy-then-configure scripts, delayed multisig-driven configuration, or localnet/testnet/staging deployments where the race window is longer).

### Recommendation
Restrict `init_global_fee_state` (and `init_global_fee_state_v2`) to a verifiably privileged caller — e.g., require the signer to match the program's upgrade authority (checked via the `ProgramData` account, as Solana programs commonly do for one-time admin bootstrap instructions) rather than accepting an arbitrary `admin_key`/`fee_wallet` from an unauthenticated signer.

### Proof of Concept
1. Attacker observes/derives the `FeeState` PDA address for the deployed `marginfi` program (`Pubkey::find_program_address(&[FEE_STATE_SEED], marginfi::ID)`).
2. Before the legitimate deployer's `init_global_fee_state` transaction is confirmed (e.g., by front-running in the same slot, or racing a delayed setup script), attacker submits their own `init_global_fee_state` transaction with `admin_key = attacker_pubkey`, `fee_wallet = attacker_wallet`.
3. Because `InitFeeState` only requires a fee-paying `Signer` and `init`s the PDA with `payer = <attacker>`, the transaction succeeds and `fee_state.global_fee_admin`/`global_fee_wallet` are now attacker-controlled permanently (subsequent legitimate `init_global_fee_state` calls fail since the account already exists).
4. Attacker subsequently calls `edit_global_fee_state` as `global_fee_admin` to redirect protocol fees or manipulate `pause_delegate_admin`.

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
