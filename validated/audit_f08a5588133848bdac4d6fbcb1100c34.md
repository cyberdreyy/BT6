### Title
Cross-user response hijack via colliding client-chosen MessageId in savedCallbacks map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` keys the shared `h.savedCallbacks` map solely by `msg.Body.MessageId`, a value fully controlled by the requesting client and not scoped by sender/address. Two different (unprivileged) users can pick the same `MessageId`, causing the second request to silently overwrite the first user's pending `Callback`, so the DON's eventual response is delivered to the wrong caller and the original caller never receives a response.

### Finding Description
`HandleLegacyUserMessage` stores the callback with:
```go
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [1](#0-0) 

`MessageId` is part of `MessageBody` and is set by the client/gateway-user request (validated only for length/format in `Message.Validate`, not for uniqueness or per-sender scoping): [2](#0-1) [3](#0-2) 

`Sender` is derived from the signature (`ExtractSigner`), so distinct users produce distinct `Sender` values, but `Sender` is never included in the map key. When a node response later arrives, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `msg.Body.MessageId` and delivers the response to whichever `Callback` is currently stored:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [4](#0-3) 

Exploit flow: Attacker A sends `HandleLegacyUserMessage` with `MessageId = X` (properly signed by A, so it passes `Validate`/signature checks — no privilege beyond being any allowed webAPI-trigger caller is needed). Legitimate user B sends a request with the same client-chosen `MessageId = X` before the DON responds to A's request. B's call overwrites `h.savedCallbacks[X]` with B's `Callback`, silently discarding A's pending callback reference (A's original callback object is simply dropped from the map, not notified). When the DON node responds for `MessageId=X`, `handleWebAPITriggerMessage` delivers the single stored response to B's callback — if B is actually the attacker, the attacker receives A's response payload; conversely if A is the attacker aiming to deny/capture B's flow, A can pre-register `X` and let B's later request silently clobber the map first (whichever request lands last "wins" the callback slot), and the request whose callback got evicted receives no response at all (hang/timeout). Neither the DON->node send path nor the `Validate()` checks enforce MessageId uniqueness or scope the map key by `Sender`, so nothing prevents the collision.

### Impact Explanation
This is a cross-user response confusion / hijack: one user's job-run response (which may include return data, e.g., HTTP fetch payloads/results processed via the web API trigger flow) can be delivered to a different, unrelated caller, and the legitimate caller's request silently never completes (denial of response). This matches Chainlink's "cross-user data exposure / unauthorized access to another user's request-response" impact class, scoped to the gateway `capabilities` webAPI trigger handler.

### Likelihood Explanation
Exploitability requires only two accounts allowed to call the webAPI trigger endpoint (no elevated role) and the ability to choose an arbitrary `MessageId` string (bounded to ≤128 bytes, non-null-terminated) in a signed request — both trivially satisfied by any caller of the endpoint. The race window is the time between message submission and DON node response, which is normally on the order of the round trip to nodes plus processing, giving an attacker ample opportunity to submit a colliding second request. This is deterministic and repeatable, not a low-probability race.

### Recommendation
Scope the `savedCallbacks` map key by both `Sender` and `MessageId` (e.g., `fmt.Sprintf("%s:%s", msg.Body.Sender, msg.Body.MessageId)`), or reject/queue a new request with `HandleLegacyUserMessage` if an entry for that key already exists rather than silently overwriting it. Apply the same composite key when looking up/deleting in `handleWebAPITriggerMessage`, using the corresponding DON node response's associated sender/session context.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler `h` with mocked `handlers.DON` (no-op `SendToNode`).
2. Create two distinct mock `handlers.Callback` instances, `cbA` (records last received `UserCallbackPayload`) and `cbB`.
3. Build two `api.Message` values signed by two different private keys (`userA`, `userB`), both with `Body.MessageId = "X"`, `Body.Method = MethodWebAPITrigger`, valid `Payload.Timestamp`.
4. Call `h.HandleLegacyUserMessage(ctx, msgA, cbA)` then `h.HandleLegacyUserMessage(ctx, msgB, cbB)`.
5. Assert `len(h.savedCallbacks) == 1` and that the stored callback is `cbB` (proving `cbA` was silently overwritten) — this demonstrates the missing sender-scoping.
6. Simulate a node response for `MessageId = "X"` via `h.handleWebAPITriggerMessage(ctx, nodeRespMsg, nodeAddr)`, and assert that `cbB.SendResponse` was invoked while `cbA.SendResponse` was never called — proving cross-user delivery/loss.
7. Expected (fixed) behavior: the map key should incorporate `Sender`, so both `cbA` and `cbB` entries coexist independently and each receives only its own response, or the second `HandleLegacyUserMessage` call for a colliding id from a different sender should be rejected with an error response instead of silently overwriting.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
