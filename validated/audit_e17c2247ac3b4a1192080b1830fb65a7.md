## Analysis

The reported Sherlock issue is: a function computes a "requested" amount, but when actual funds fall short, execution silently continues and distributes an amount that isn't backed by what was actually available — breaking the equality between "amount deducted from the source" and "amount paid to the recipient."

An analog of this exact defect exists in the Gloas (EIP-7732) builder-withdrawal machinery in `specs/gloas/beacon-chain.md`.

### Root cause

`get_builder_withdrawals` builds each `Withdrawal` using the **requested** amount from the queue entry, with no check against the builder's actual balance: [1](#0-0) 

That `Withdrawal.amount` is exactly what gets committed to `state.payload_expected_withdrawals` (and thus to the execution-layer withdrawal, which the EL credits to `fee_recipient` in full, since the CL/EL contract is "the EL mints/credits exactly the committed amount").

But the *actual* balance deduction on the CL side, in `apply_withdrawals`, is silently capped to whatever is left in `builder.balance`: [2](#0-1) 

So when `withdrawal.amount > builder.balance` (e.g. one over-large pending withdrawal, or several queued withdrawals for the same builder that cumulatively exceed the balance), the state only debits `min(amount, balance)` from the builder, while the `Withdrawal` object recorded in `payload_expected_withdrawals` — the thing the execution layer actually pays out — still carries the full, uncapped `amount`. This is confirmed by the existing test fixture, which explicitly asserts this behavior: withdrawal amount = requested (5 ETH) even though the builder only had 1 ETH and only 1 ETH is deducted from `builders[0].balance`: [3](#0-2) 

### Title
Builder pending withdrawals can commit a payment larger than the deducted balance, minting uncollateralized Gwei — (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` places the full requested `amount` from `state.builder_pending_withdrawals` into the `Withdrawal` committed by the block, without capping it to `builder.balance`. `apply_withdrawals` then only decreases the builder's balance by `min(withdrawal.amount, builder_balance)`. The execution layer, however, must honor the committed `Withdrawal.amount` in full. When a builder's requested withdrawal(s) exceed its tracked balance, the amount actually paid out to `fee_recipient` (uncapped) diverges from the amount actually deducted from the protocol's ledger (capped), creating Gwei that is not backed by any real balance decrease.

### Finding Description
For a builder-pending withdrawal entry with `amount > builders[index].balance`:
- `get_builder_withdrawals` unconditionally emits `Withdrawal(amount=withdrawal.amount, ...)` — the raw requested amount — into `payload_expected_withdrawals`, per [4](#0-3) .
- `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`, per [5](#0-4) .
- The block's `payload_expected_withdrawals` is exactly what the execution layer is bound to pay out to the `fee_recipient` address (this is stated as the general withdrawal contract in the spec's own commentary at [6](#0-5) , which acknowledges that "the execution layer mints the full committed amount regardless" and that CL-side saturation "creates a net supply inflation" — but that note only discusses the cross-slot validator/consolidation case, not this intra-block builder case).

Concretely, before/after on a minimal state: builder balance = 1 ETH, one pending withdrawal entry requesting 5 ETH. Before: `builders[0].balance = 1e9 Gwei`. After `process_withdrawals`: `builders[0].balance = 0`, but the committed `Withdrawal.amount = 5e9 Gwei` is what the execution layer will credit to `fee_recipient`. 4 ETH is paid out that was never subtracted from anyone's tracked balance — it is minted out of thin air by the CL/EL contract.

### Impact Explanation
This breaks the "Gwei created and paid to a non-owner" invariant: `fee_recipient` receives Gwei that no validator, builder, or pool ever held, i.e., net protocol-level inflation triggered purely by a builder queuing a withdrawal request larger than its own balance (which nothing prevents, since `process_builder_pending_withdrawal`/queue insertion is not shown to validate against current balance at enqueue time, and even if it were, balance can shrink between enqueue and processing via other pending entries or, generally, balance-affecting operations). This is a Critical-class issue per the given severity rubric (Gwei created and paid to a non-owner).

### Likelihood Explanation
Reachable by any builder (or anyone able to enqueue a `BuilderPendingWithdrawal`, which is a permissionless execution-layer request per EIP-7732) requesting a withdrawal amount exceeding its current balance, or by queuing multiple withdrawals whose sum exceeds the balance. No coalition, malicious peer, or client bug is required — a single builder acting alone, honestly following the spec's public interfaces, can trigger the divergence. It is a straightforward, deterministic path through the in-scope spec text (`get_builder_withdrawals` and `apply_withdrawals` in `specs/gloas/beacon-chain.md`), not a resource-exhaustion or timing issue.

### Recommendation
Cap the amount placed in the `Withdrawal` object at enqueue/withdrawal-construction time to `min(withdrawal.amount, builder.balance)` inside `get_builder_withdrawals` (mirroring what `apply_withdrawals` actually deducts), so that the committed payment and the actual deduction always agree, e.g.:
```python
actual_amount = min(withdrawal.amount, state.builders[builder_index].balance)
withdrawals.append(Withdrawal(..., amount=actual_amount))
```
and track running balance across multiple queued entries for the same builder within the same call so cumulative requests cannot exceed the builder's real balance.

### Proof of Concept
1. Set `state.builders[0].balance = 1_000_000_000` (1 ETH).
2. Enqueue `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=X)]`.
3. Call `process_withdrawals(state)`.
4. Observe: `state.builders[0].balance == 0` (only 1 ETH deducted), but `state.payload_expected_withdrawals[0].amount == 5_000_000_000` (5 ETH), which the execution layer will credit to `X` — exactly the scenario already exercised (with assertions accepting this outcome as correct) in [7](#0-6) .

layer mints the full committed amount regardless, any CL-side saturation creates
