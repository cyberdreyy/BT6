### Title
Post-default instant-withdraw receipts are honored at par without any funding counterpart - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` unconditionally mints receipt tokens and increments `instantWithdrawsRequests`/`pendingInstantWithdraws` even after `defaultRecoveryFinalized` is set, while the normal `requestWithdraw` path explicitly guards that state and routes post-default requests into the reserve-backed `postDefaultRequests` bucket. `claimInstantWithdrawRequest` then pays the full accumulated receipt balance at par through `_transferFundedClaim`, whose only protection is the `defaultRecoveryReserve` guard. The result mirrors the kernel bug class — a reference/liability is created on one path (unconditional increment) but the symmetric funding counterpart (`collectInstantWithdrawFunds`) can never run post-default because no further `stopEpoch` occurs — so an unprivileged tranche holder can mint a receipt out of thin air and drain underlyings that were collected to fund other users' pending withdraw claims.

### Finding Description
In `requestWithdraw`, once `defaultRecoveryFinalized` is true, the function burns/mints only `postDefaultRequests[_user]`, which is later paid strictly from `defaultRecoveryReserve` via `_transferDefaultRecovery` [1](#0-0) . By contrast, `requestInstantWithdraw` has no `defaultRecoveryFinalized` check at all: it burns CDO-held strategy tokens, mints an equal receipt to the user, and increments `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch` and `pendingInstantWithdraws` [2](#0-1) .

On the claim side, `claimInstantWithdrawRequest` only diverts the default-epoch basis through `_claimDefaultedInstantWithdrawRequest` when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`; it then burns the *entire* remaining `instantWithdrawsRequests[_user]` and pays it via `_transferFundedClaim` [3](#0-2) . A post-default receipt is recorded under a new `currentEpoch` (or whatever `epochNumber` is frozen at, distinct from `defaultRecoveryEpoch`), so `_claimDefaultedInstantWithdrawRequest` does not touch it — `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` is zero for it [4](#0-3) . It survives into the par-paid `_transferFundedClaim` path.

The only funding entry point for instant receipts is `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls tokens from the CDO [5](#0-4) . After default finalization no stopEpoch/collect flow runs, so the increment has no matching decrement — the exact refcount-style imbalance: the liability side is booked unconditionally, the asset side never arrives. `_transferFundedClaim` only reverts if `balance - defaultRecoveryReserve < _amount`, i.e., it protects the recovery reserve but happily spends any underlyings sitting in the strategy that were collected via `collectWithdrawFunds` to satisfy other users' funded normal-withdraw receipts [6](#0-5) .

### Impact Explanation
Direct theft with a quantified loss. Any unprivileged tranche-token holder (KYC-passing lender) who still holds AA/BB positions after default finalization calls `requestInstantWithdraw` through the CDO, receives a receipt with zero funding, then calls `claimInstantWithdrawRequest` and is paid 1:1 from the strategy's underlying balance above `defaultRecoveryReserve`. Those underlyings are the funded pool reserved for honest users' pending withdraw receipts (funded by the borrower via `collectWithdrawFunds`), so each unit claimed is a unit stolen from those claimants — up to `balance - defaultRecoveryReserve`. The fair-mint/burn and one-receipt-one-funded-payout invariants are broken: the receipt is minted with no asset backing and redeemed at par.

### Likelihood Explanation
Requirements: the vault must have reached `defaultRecoveryFinalized` and hold funded underlyings beyond the recovery reserve (a normal post-default state while pending claims await collection), and the attacker needs a tranche position to pass through the CDO's `requestInstantWithdraw`. Both are attainable by the defined attacker set with no privileged collusion. Uncertainty I could not fully resolve within the tool budget: whether `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` impose an additional `defaulted()`/epoch-phase gate that would block reaching the strategy functions post-default; the strategy-level asymmetry (guarded `requestWithdraw` vs unguarded `requestInstantWithdraw`) strongly suggests the path is reachable, but a PoC must confirm the CDO entry point does not revert.

### Recommendation
Add the same post-default guard used in `requestWithdraw` to `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert or route the amount through the reserve-backed post-default bucket (and require claim from `defaultRecoveryReserve` at the haircut price instead of `_transferFundedClaim`). Symmetrically, ensure `claimInstantWithdrawRequest` only pays non-default-epoch receipts that were actually funded via `collectInstantWithdrawFunds` — e.g., track a funded instant-claim balance per user rather than paying the raw `instantWithdrawsRequests` total.

function test_PostDefaultInstantWithdrawDrainsFundedClaims() public {
    // 1. Running epoch: user1 deposits via AA tranche, requests a normal withdraw.
    // 2. Warp past epochEndDate; borrower default -> manager calls stopEpoch with
    //    partial repayment so pendingWithdraws are funded via collectWithdrawFunds,
    //    then finalizeDefaultRecovery so defaultRecoveryFinalized = true and
    //    defaultRecoveryReserve is set.
    // 3. Attacker (another KYC'd AA holder):
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(attackerAmount, address(AAtranche));
    // strategy mints receipt, pendingInstantWithdraws += attackerAmount,
    // but NO collectInstantWithdrawFunds will ever run.
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // 4. Assert attacker received attackerAmount underlying while
    //    strategy balance dropped below (fundedPending + reserve): user1's
    //    later claimWithdrawRequest reverts in _transferFundedClaim / underpays.

```

Expected outcome per the code: step 4 pays the attacker at par from underlyings collected for user1's funded receipt, and user1's subsequent `claimWithdrawRequest` either reverts (reserve guard) or leaves the vault insolvent — confirming theft of funded claim proceeds. If step 3's CDO entry reverts on `defaulted()`, the strategy-level fix is still required for defense-in-depth, but the exploit severity would depend on that gate.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;

    // finalization we can distinguish "default-epoch pending instant receipts"

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests

  }

    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
