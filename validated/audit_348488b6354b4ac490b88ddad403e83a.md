### Title
Unfunded instant-withdraw receipts can be claimed by piggybacking on an older funded receipt, draining the shared claim reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2023-42670, where multiple incompatible "listeners" erroneously compete for the same resource, `IdleCreditVault.claimInstantWithdrawRequest` treats all generations of a user's instant-withdraw receipts as a single aggregate balance and pays the total from the same funded claim reserve. A user who holds an already-funded instant receipt can append a new, not-yet-funded instant request in the current epoch and then claim, receiving underlying for the unfunded portion at the expense of other pending claimants.

### Finding Description
`requestInstantWithdraw` (IdleCreditVault.sol:356-375) burns CDO strategy tokens and mints the user a 1:1 receipt, incrementing `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `pendingInstantWithdraws`. The underlyings backing a receipt only arrive later, when the CDO calls `collectInstantWithdrawFunds` (line 398-403) during `stopEpoch`, which debits `pendingInstantWithdraws` and pulls tokens into the strategy reserve.

`claimInstantWithdrawRequest` (line 380-393) then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Unlike the normal path (`_claimFundedWithdrawRequest`, line 326, which reverts while `epochNumber <= lastWithdrawRequest[_user]` so only funded generations can be claimed), the instant claim has no per-epoch funding check. `instantWithdrawsRequests[_user]` is the sum of every generation — the epoch-N receipt whose funds were already collected, plus any epoch-N+1 receipt whose `pendingInstantWithdraws` share has not yet been collected. The claim therefore pays both from one reserve that was only funded for the first.

### Impact Explanation
An unprivileged tranche holder (KYC-passing lender) can:

1. Make an instant withdraw request in epoch N; after `stopEpoch`, the strategy holds collected funds backing it.
2. In epoch N+1 (running epoch, where instant requests remain enabled), submit a second instant request of amount X. Funds for X are only collectible at the next `stopEpoch`.
3. Immediately call the CDO's `claimInstantWithdrawRequest`. The strategy burns `funded + X` receipts and transfers `funded + X` underlyings.

The X paid early is taken from the common claim reserve, which also backs other users' pending normal withdraws (`collectWithdrawFunds`), APR0 claims and other instant claims. The result is direct theft/insolvency: later claimants find the reserve short by up to the attacker's second-request size (bounded only by their tranche balance). One receipt effectively receives a payout funded by another epoch's claims — the broken invariant is "one funded receipt, one funded payout".

### Likelihood Explanation
Requires only that instant withdrawals be enabled and that the attacker hold tranche tokens across two consecutive epochs — normal, expected usage. No privileged cooperation is needed: `requestInstantWithdraw` performs no check for existing pending/unclaimed receipts (compare `requestWithdraw`, which explicitly reverts at line 249 when prior receipts exist post-default). On the CDO side the claim is only delayed by `instantDelay` after epoch start, not conditioned on all of the user's receipts being funded, so sequencing the two requests and the claim is straightforward during a running epoch.

### Recommendation
Track funded instant-withdraw claims per epoch (e.g., only pay `instantWithdrawsRequestsByEpoch[_user][e]` for epochs `e` whose `instantWithdrawClaimsByEpoch` funds were already collected), or reject `requestInstantWithdraw` while `instantWithdrawsRequests[_user] != 0`, mirroring the pending-receipt guard already present in `requestWithdraw`.

### Proof of Concept
A Foundry fork PoC would: deploy `IdleCDOEpochVariant` + `IdleCreditVault` with instant withdrawals enabled (`setInstantWithdrawParams`); have attacker deposit, run epoch N, `requestWithdraw` routed to instant for amount A; let manager `stopEpoch` (funds for A collected into the strategy); in running epoch N+1 have the attacker request instant withdraw for amount B; then call `claimInstantWithdrawRequest()` and assert the attacker received `A + B` underlyings while `pendingInstantWithdraws` still shows B uncollected — demonstrating the reserve is overdrawn by B against other claimants.

Caveat: I was unable to fully read `IdleCDOEpochVariant`'s instant-claim gating before the tool limit; if the CDO additionally blocks claims until all of a user's instant requests are funded (e.g., a per-user funding timestamp), the exploitability would depend on that check being absent or bypassable — the strategy-side aggregate claim itself is confirmed to lack per-epoch funding validation.
