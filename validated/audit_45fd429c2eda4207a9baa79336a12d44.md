## Title
Stale confirmations from deleted multisig keys/members still count toward quorum, allowing a request to execute below the configured threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` implement a K-of-N confirmation scheme where a request executes once `confirmations.len() + 1 >= num_confirmations`. When a key (or member) is removed via `DeleteKey`/`DeleteMember`, the contract only purges *requests originated by* that key/member, but never scrubs that key/member's *confirmations recorded on other still-pending requests*. A stale confirmation from a revoked key therefore still counts toward the quorum needed to execute an unrelated pending request, letting that request execute with fewer live, currently-authorized confirmers than `num_confirmations` requires.

### Finding Description
In `multisig/src/lib.rs`, `confirm()` checks the size of the `confirmations` set against `num_confirmations`: [1](#0-0) 

The `DeleteKey` handler inside `execute_request` only removes requests where the *deleted* key is the original signer of the request; it does not touch confirmations that the same key placed on *other* requests: [2](#0-1) 

Concretely: the filter is `r.signer_pk == pk` (matching the request *creator*), which has nothing to do with the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map that tracks who *confirmed* each request. So if key `B` confirmed request `R1` (created by key `A`) and is later deleted via a different, unrelated `DeleteKey` request, `R1`'s `confirmations` set still contains `B`'s public key. When `A` later confirms `R1`, the stale entry for `B` is counted, satisfying `confirmations.len() + 1 >= num_confirmations` even though `B` no longer holds a valid key on the account.

The same pattern exists in `multisig2/src/lib.rs`. `delete_member` only removes requests *authored by* the deleted member: [3](#0-2) 

but confirmations left by that member on other requests, stored in `confirmations: LookupMap<RequestId, HashSet<String>>`, are never invalidated, and `confirm()` again just compares set length: [4](#0-3) 

This breaks the intended equality that the contract's security model depends on:
`confirmations counted (recorded in the `confirmations` set) == confirmations from members who are live/authorized at execution time`.
After a member/key removal, `confirmations counted > live authorized confirmers` for any request the removed party had confirmed but did not create.

### Impact Explanation
This is a Critical-class issue per the multisig threshold guarantee: "a multisig request executed below threshold." A `Transfer`, `DeployContract`, `AddKey`/`AddMember`, or `FunctionCall` request can be pushed to execution with the participation of a revoked key/member counted toward quorum, meaning the actual number of currently-trusted approvers is strictly less than `num_confirmations`. Since `Transfer` actions move NEAR directly out of the multisig account, this can result in unauthorized fund movement approved by fewer live signers than the account's own security policy requires.

### Likelihood Explanation
This does not require any special attacker privilege beyond being (or having been) one of the multisig's own members/key-holders, which is the expected actor set for this contract. It requires only an ordinary sequence of legitimate multisig operations that any real multisig will perform over its lifetime: a pending request gets a partial confirmation from a member who is later removed (e.g., due to key rotation, compromise response, or team member offboarding) before the original request is confirmed or deleted. The removed member's confirmation is never invalidated, so any subsequent confirmer completes the quorum using the stale, revoked confirmation. No special timing race or elevated permission is needed beyond normal multisig usage.

### Recommendation
When executing `DeleteKey`/`DeleteMember`, iterate over **all** pending requests' confirmation sets (not just requests originated by that key/member) and remove the deleted key/member's entry from each. Alternatively, when confirming a request, validate that every entry in the `confirmations` set still corresponds to a current member (e.g., by intersecting with `self.members` in `multisig2` or checking `num_requests_pk`/an authoritative live-key registry in `multisig`) and discard stale confirmations before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 2` and access keys `A`, `B`, `C`.
2. `A` calls `add_request(R1)` for `Transfer{amount}` to some receiver (confirmations for `R1` = `{}`).
3. `B` calls `confirm(R1)` → confirmations for `R1` = `{B}` (1 of 2, not yet executed).
4. Separately, `A` and `C` create and confirm a `DeleteKey{public_key: B}` request (`R2`), reaching quorum with two currently-live keys and removing `B`'s access key from the account. Per `execute_request`'s `DeleteKey` branch, only requests where `signer_pk == B` are purged — `R1` (signed by `A`) is untouched, and `B`'s entry remains in `R1`'s `confirmations` set.
5. `A` calls `confirm(R1)`. `confirmations.len() + 1 == 2 >= num_confirmations (2)`, so `R1` executes and the transfer is scheduled — even though `B`'s key was already revoked and only one live key (`A`) ever actually approved `R1` after the revocation. [5](#0-4)
