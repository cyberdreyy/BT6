Confirmed: this is a genuine equality-breaking bug in the Gloas (EIP-7732) spec's builder withdrawal path.

**Root cause.** `get_builder_withdrawals` in [1](#0-0)  builds each `Withdrawal.amount` directly from `withdrawal.amount` in `state.builder_pending_withdrawals` — the *requested* amount, uncapped by the builder's actual balance. That `Withdrawal` is committed into `state.payload_expected_withdrawals` in `get_expected_withdrawals`/`process_withdrawals` ( [2](#0-1) ), and the execution layer is required to honor exactly that committed withdrawal amount to `fee_recipient` (per the note at lines 1969-1975: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer").

Meanwhile, `apply_withdrawals` (Gloas-modified) only *deducts* `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`: [3](#0-2) 

So if a builder's balance is less than the pending withdrawal's requested `amount` (e.g. balance = 1 ETH, pending withdrawal amount = 5 ETH), the CL commits the EL to mint/pay the full 5 ETH to `fee_recipient`, while only 1 ETH is actually subtracted from CL supply (`state.builders[...].balance` saturates at 0). This is confirmed directly by the spec's own test suite, which explicitly asserts this behavior as correct: [4](#0-3) 
and the helper's comment "Builder withdrawals cap at available balance (spec uses min())" while `withdrawal_amounts_builders` (the amount committed to the EL) is asserted to be the full, uncapped `5_000_000_000` Gwei: [5](#0-4) 

This breaks the equality "Gwei paid out to the EL fee_recipient == Gwei debited from CL total supply." A `4 ETH` gap materializes: the CL total effective stake decreases by only 1 ETH, but the EL mints 5 ETH to an external address — net Gwei creation, analogous to the Bitallx report's "amount paid ≠ amount actually available/owed."

How can `builder_pending_withdrawals.amount` exceed the builder's balance in the first place? `process_execution_payload_bid` in the same file only checks `can_builder_cover_bid` at bid time ( [6](#0-5) ), which nets against *other* pending payments/withdrawals via `get_pending_balance_to_withdraw_for_builder` ( [7](#0-6) ) — but a builder's balance can still drop below a previously-queued withdrawal amount through later events (e.g. additional bids/payments settling before the queued pending withdrawal is dequeued, or `settle_builder_payment` appending new entries). The queue is FIFO and processed by `get_builder_withdrawals`/`apply_withdrawals`, so any such balance shortfall at dequeue time triggers the amount-vs-deduction mismatch described above — exactly what the test `test_builder_withdrawal_insufficient_balance` exercises and treats as expected/correct behavior.

### Title
Builder withdrawal EL payment exceeds CL balance deduction on insufficient balance - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas (EIP-7732) beacon-chain spec, `get_builder_withdrawals` commits the full requested `withdrawal.amount` from `state.builder_pending_withdrawals` into `payload_expected_withdrawals`, which the execution layer is spec-required to honor as a payment to `fee_recipient`. But `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from the builder's CL balance. When a builder's balance is less than its queued pending-withdrawal amount, the EL pays out more Gwei than is debited from the CL, creating Gwei out of thin air.

### Finding Description
- `get_builder_withdrawals` (specs/gloas/beacon-chain.md:1802-1834) constructs `Withdrawal(amount=withdrawal.amount, ...)` directly from the queued `BuilderPendingWithdrawal.amount`, with no cap against `state.builders[builder_index].balance`.
- This withdrawal is included in `state.payload_expected_withdrawals` via `get_expected_withdrawals`/`process_withdrawals` (specs/gloas/beacon-chain.md:1876-2018), which the spec's own comments state execution-layer nodes "are required to honor."
- `apply_withdrawals` (specs/gloas/beacon-chain.md:1920-1932) then debits only `min(withdrawal.amount, builder_balance)` from the builder's actual balance — capping at whatever balance remains, silently saturating to 0 rather than reverting or truncating the committed withdrawal amount.
- Result: the committed EL payment (`withdrawal.amount`) and the CL balance deduction (`min(withdrawal.amount, builder_balance)`) diverge whenever `builder_balance < withdrawal.amount`.

### Impact Explanation
This is a Critical-severity Gwei-creation bug: the execution layer mints/transfers the full committed `withdrawal.amount` (e.g., 5 ETH) to an arbitrary `fee_recipient` address chosen by the pending withdrawal entry, while the consensus layer only removes the smaller, actually-available balance (e.g., 1 ETH) from total supply. The difference is Gwei created and paid to a non-owner, breaking the fundamental invariant that CL debits must equal EL credits for every committed withdrawal.

### Likelihood Explanation
The path is directly reachable without any adversarial coalition: a builder's balance can fall below an already-queued `builder_pending_withdrawals` entry through ordinary subsequent state transitions (e.g., additional withdrawal requests or another `settle_builder_payment` appending a further pending withdrawal for the same builder before the first is dequeued — `can_builder_cover_bid` at bid-time only checks the *bid*, not future queue growth). The spec's own test suite (`test_builder_withdrawal_insufficient_balance`, `test_builder_withdrawal_insufficient_balance_realistic_bounds`) demonstrates and explicitly asserts this exact scenario, treating the mismatch (committed amount 5 ETH vs. balance decrease of 1 ETH) as expected behavior.

### Recommendation
Cap the withdrawal amount emitted by `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)` at the point the `Withdrawal` object is constructed (before it is committed to `payload_expected_withdrawals`), so the amount the EL is obligated to pay always matches the CL balance actually being debited. Alternatively, ensure `state.builder_pending_withdrawals` entries can never exceed the builder's balance at the time they are enqueued and remain so until dequeued (e.g., by re-validating/truncating amounts whenever the builder's balance changes).

### Proof of Concept
Using the spec's own test as the concrete PoC (`tests/core/pyspec/eth_consensus_specs/test/gloas/block_processing/test_process_withdrawals.py::test_builder_withdrawal_insufficient_balance`):
1. `state.builders[0].balance = 1_000_000_000` (1 ETH).
2. `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=X)]` (5 ETH requested).
3. Run `process_withdrawals(state)`.
4. Post-state: `payload_expected_withdrawals[0].amount == 5_000_000_000` (committed EL payment to `X` is 5 ETH) while `state.builders[0].balance == 0` (only 1 ETH actually debited).
5. The execution layer, honoring the committed withdrawal, pays `X` 5 ETH while only 1 ETH was ever removed from CL total stake — 4 ETH of Gwei created and sent to `X`, a non-owner of that value.

def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
