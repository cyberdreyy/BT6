### Title
v1 chainstate `DuplicateBlockFound` check uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, allowing a signer to sign two conflicting tenure-change blocks for the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` guards against a miner proposing two competing tenure-start blocks for the same tenure by checking whether a block has *already been signed* in that tenure. Unlike the v2 implementation, which was hardened to look at any signed block (locally **or** globally accepted), the v1 path still only checks `get_last_globally_accepted_block`, i.e. it is blind to a block this signer (or the group) has already **locally** accepted or pre-committed but that has not yet reached the node/global-acceptance state. This is the same class of bug as the Mise report: two parallel code paths that are supposed to enforce an identical trust/consistency guard, where one path was hardened and the other was left with the weaker check, creating a bypass window.

### Finding Description
`validate_tenure_change_payload` (v1) performs the "have we already signed a tenure-start block for this tenure" check like this: [1](#0-0) 

It queries only `get_last_globally_accepted_block`, which requires the block to have reached `BlockState::GloballyAccepted` (i.e. the whole signer set signed it **and** the stacks-node adopted it).

The v2 equivalent was already fixed to close exactly this gap: [2](#0-1) 

`get_last_signed_block` matches on `BlockState::GloballyAccepted` **or** `BlockState::LocallyAccepted`, per its own documentation: [3](#0-2) 

The v2 fix is accompanied by an explicit regression test documenting exactly this weakness: [4](#0-3) 

That test comment states verbatim: *"previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change."* The v1 path was never updated to match, so the same regression is still live there.

`validate_tenure_change_payload` is invoked only from `check_proposal` at proposal-arrival time, and per the documented design this check is **not re-run** at validate-ok or at signing: [5](#0-4) 

Signing-time protection relies entirely on the shared "own-tenure conflict" guard driven by `get_signed_conflicts`, which only fires once a competing block in the same tenure has actually accrued a signature (`signed_self`/`signed_group`): [6](#0-5) 

This creates the following window on a v1-protocol signer: a single miner proposes tenure-change block B1; the signer reaches its own local pre-commit threshold and marks B1 `PreCommitted`/`LocallyAccepted`, but this has not yet become `GloballyAccepted` (node hasn't processed it, or another portion of the signer set is still validating). Before that happens, the miner (or a re-mined tenure-start after a stall/fork) proposes a second, conflicting tenure-change block B2 for the *same tenure*. Because `get_last_globally_accepted_block` returns `None` for B1 (it is only local/pre-committed), `validate_tenure_change_payload` does **not** reject B2 with `DuplicateBlockFound` at proposal time — unlike the v2 path, which would catch it via `get_last_signed_block`. B2 is then submitted for node validation and can proceed through the same pipeline as B1. The only remaining backstop is the pre-commit-threshold "own tenure conflict" check in `handle_block_pre_commit`, which is a *silent, best-effort* guard (not a hard rejection) that only engages once a signature actually exists on one side of the conflict and is subject to staleness/liveness edge cases documented in `conflict_still_blocks`. It was never designed to be the sole defense for this scenario — the proposal-time `DuplicateBlockFound` check exists specifically to close this window early and deterministically, which is exactly why it was hardened for v2.

### Impact Explanation
This breaks the "one signed block per tenure" equality that the signer state machine is supposed to enforce for v1-protocol signers. A single miner (plus normal StackerDB gossip of proposals — no majority of signers or additional signer keys needed) can drive a v1 signer into locally/group-accepting one tenure-start block and then, before the earlier one reaches full global acceptance, get a *conflicting* tenure-start block far enough through validation that only the fragile, timing-dependent own-tenure conflict guard stands between it and a second signature. This directly matches the Critical impact criterion: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
The trigger requires only a single miner producing two tenure-change proposals for the same tenure in quick succession (a normal capability of block production/re-mining, e.g. after a stall or minor fork) combined with the natural latency between a signer's local acceptance and full network/node-level global acceptance — no privileged access, no majority collusion, and no auth token is needed. The bug is a straightforward divergence between two structurally parallel functions (`v1::validate_tenure_change_payload` vs `v2::validate_tenure_change_payload`), one of which was already known to need hardening (per the existing regression test for v2), making this a concrete, provable regression rather than a theoretical concern.

### Recommendation
Update `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (matching v2's fix) instead of `get_last_globally_accepted_block`, so that a `LocallyAccepted` or otherwise-signed block in the tenure is also caught by the `DuplicateBlockFound` rejection at proposal time. Add a v1-side regression test mirroring `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs` to prevent this parity gap from re-appearing.

### Proof of Concept
1. Run a signer configured for the v1 (pre-global-state) signer protocol.
2. Miner proposes tenure-change block B1 for tenure T; the signer network reaches the pre-commit/local-acceptance threshold for B1 on this signer (`BlockState::LocallyAccepted`), but B1 has not yet been observed as `GloballyAccepted` (e.g., node hasn't ingested the aggregated signature yet).
3. The same miner proposes a second, conflicting tenure-change block B2 also targeting tenure T (e.g., differing transaction set/parent choice) before B1 reaches global acceptance.
4. `SortitionsView::check_proposal` → `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&B2.header.consensus_hash)`, which returns `None` because B1 is only `LocallyAccepted`, so the `DuplicateBlockFound` rejection is skipped for B2 [1](#0-0) .
5. B2 proceeds to node validation/pre-commit; whether it ultimately gets signed depends on the timing-sensitive `get_signed_conflicts`/`conflict_still_blocks` backstop in `handle_block_pre_commit`, rather than on the deterministic proposal-time guard that v2 provides for the identical scenario (confirmed fixed by the regression test at `stacks-signer/src/chainstate/tests/v2.rs:748-756`).
