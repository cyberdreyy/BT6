### Title
Stale rejection weight is never cleared when a signer flips to accept the same block, causing block acceptance/rejection tallies to double-count weight - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::handle_signer_messages` tracks two independent u32 accumulators, `total_weight_approved` and `total_weight_rejected`, that are supposed to reflect the *current* stance of each signer on a given `BlockStatus` (keyed by `signer_signature_hash`). The code deduplicates an `Accepted` message against `block.gathered_signatures` (keyed by `slot_id`) but deduplicates a `Rejected` message against the separate `block.responded_signers` set. Because these two "have I already counted this signer" checks use different keys and neither branch ever removes/decrements the *other* accumulator, a signer who first rejects and later accepts the same proposal has its weight permanently retained in `total_weight_rejected` while also being freshly added to `total_weight_approved`. This lets `total_weight_approved + total_weight_rejected` exceed `self.total_weight`, corrupting the aggregated-weight-vs-verified-accepts/rejects equality that `SignCoordinator::watch_for_block_signatures` relies on to decide whether a block is signed or blocked.

### Finding Description
In the `Accepted` branch: [1](#0-0) 
the code only checks `block.gathered_signatures.contains_key(&slot_id)` before adding `signer_entry.weight` to `total_weight_approved`, and unconditionally inserts into both `gathered_signatures` and `responded_signers`.

In the `Rejected` branch: [2](#0-1) 
the code only checks `block.responded_signers.insert(slot_id)` (i.e. "have I ever recorded a response from this slot before") before adding weight to `total_weight_rejected`.

Sequence:
1. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for block `H`. `responded_signers.insert(slot_S)` → `true`, so `total_weight_rejected += w`.
2. The same signer later re-evaluates and sends `BlockResponse::Accepted` for the same block `H` (the signer protocol explicitly supports this: `stacks-signer/src/v0/tests.rs` documents a signer that is first refused/pre-committed and later signs the identical block once conditions clear, e.g. `stale_sibling_replaced_when_canonical_tip_below`, and `handle_block_pre_commit`/`store_and_process_block_signature` in `stacks-signer/src/v0/signer.rs` allow re-evaluation and later signing of a previously-rejected block via `should_reevaluate_reject_reason`). [3](#0-2) 
3. Back on the miner/coordinator side, since `gathered_signatures` did not contain `slot_S` yet, the `Accepted` branch adds `w` to `total_weight_approved` as well. `responded_signers` already contains `slot_S`, so that insert is a no-op, but `total_weight_rejected` is never decremented.

The result: `S`'s weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` for the same block, simultaneously and permanently (there is no code path that ever subtracts weight from either accumulator). This breaks the equality the coordinator depends on — that each signer's weight should count toward at most one side of the tally at any time.

### Impact Explanation
`SignCoordinator::watch_for_block_signatures` in `stacks-node/src/nakamoto_node/signer_coordinator.rs` polls the same shared `BlockStatus` and, on each iteration, checks the reject condition before the accept condition: [4](#0-3) 
Because `total_weight_rejected` can retain stale weight from a signer that has since switched to accept, the blocking-minority check (`total_weight_rejected + weight_threshold > total_weight`) can be satisfied by a mix of genuinely-rejecting signers plus stale, already-reversed rejection weight, even though the *current* set of signers standing behind a rejection is below the true 30% blocking minority and the block has (or is about to) legitimately reach the 70% approval threshold. This wedges block production: a block that has in fact accumulated sufficient current signature weight can be miscounted as globally rejected (`NakamotoNodeError::SignersRejected`), and the associated transactions can even be temporarily/permanently excluded from future proposals (`permanently_excluded_txids`/`temporarily_excluded_txids`) based on this corrupted tally. This is a liveness wedge on block/tenure production driven purely by one signer's ordinary vote-then-revote behavior, without needing a majority of signers or any key compromise.

### Likelihood Explanation
This does not require a malicious signer or majority collusion — it only requires one honest signer's normal re-evaluation flow (reject a proposal, then later accept the identical proposal after conditions change, e.g. after a reorg-timing/re-proposal event as already exercised by the codebase's own tests: `stale_sibling_replaced_when_canonical_tip_below`, `reproposal_cannot_bypass_fresh_conflict` in `stacks-signer/src/v0/tests.rs`). Because `BlockStatus` is keyed by `signer_signature_hash` and persists for the lifetime of that specific block proposal in the coordinator's `blocks` map, any legitimate reject→accept transition by a single signer on the same proposal triggers the double count. This makes the bug reachable by ordinary single-signer/gossip behavior, matching the rules' bar for a miner-plus-gossip-triggerable analog.

### Recommendation
Track a signer's *current* vote (Accept/Reject) per `slot_id` in a single map instead of two independently-updated weight counters plus two different de-duplication sets. When a new response for a slot_id supersedes a prior one, subtract the old contribution from whichever accumulator it was previously counted toward before adding the new contribution, e.g.:
```rust
// pseudo-fix
if let Some(prev_vote) = block.vote_by_slot.insert(slot_id, Vote::Accepted(signature)) {
    match prev_vote {
        Vote::Rejected => block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight),
        Vote::Accepted(_) => { /* already counted, no-op */ }
    }
}
block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
```
and symmetrically for the `Rejected` branch, so a signer's weight is always attributed to exactly one side of the tally.

### Proof of Concept
1. Coordinator opens a `BlockStatus` for proposal `H` with `total_weight = 100`, `weight_threshold = 70`.
2. Signer `S` (weight 25) sends `BlockResponse::Rejected(H)` → `total_weight_rejected = 25`.
3. Enough other signers (weight 6 more, e.g. total 31) send `Rejected(H)` as well is not even required — assume no more rejects arrive.
4. Signer `S` later sends `BlockResponse::Accepted(H)` for the identical block (a legitimate re-evaluation, as exercised in `stacks-signer` re-proposal tests) → `total_weight_approved = 25`, but `total_weight_rejected` remains `25` (never decremented) — see `stackerdb_listener.rs` lines 443-465 and 515-518.
5. Suppose 70 more weight of distinct signers then legitimately accept: `total_weight_approved = 95 ≥ 70` (threshold met) while `total_weight_rejected` still erroneously shows `25` from `S`'s stale, reversed vote. If instead only ~46 more distinct weight had rejected (`total 25(stale)+46=71 > 30` blocking minority) while the *true* current reject weight from still-rejecting signers is only 46 (below the 30-weight-point/blocking-minority bar once `S`'s stale 25 is excluded), the coordinator's reject-branch-checked-first logic (`signer_coordinator.rs` lines 509-519) can fire `NakamotoNodeError::SignersRejected` on a block that legitimately should not be blocked, or conversely leave stale rejected weight permanently inflating tallies for the life of that `BlockStatus` entry, corrupting all subsequent weight-based decisions for it.
