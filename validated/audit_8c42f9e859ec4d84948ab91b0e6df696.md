## Analysis

The core mechanism is confirmed: `vesting::set_beneficiary` performs a one-time registration check via `assert_account_is_registered_for_apt(new_beneficiary)`, and the code comment explicitly states this check exists *specifically* to prevent `distribute()` from aborting and blocking all other shareholders: [1](#0-0) 

That check only validates state at call time — it does not, and cannot, guarantee registration remains valid at the time `distribute()` actually executes: [2](#0-1) 

The deposit path used for payouts, `aptos_account::deposit_coins`, only auto-creates/registers the recipient account if the account itself doesn't exist yet (`!account::exists_at(to)`). If the account already exists but its `CoinStore<AptosCoin>` was later removed (e.g., via `coin::close_coin_store`, an unprivileged self-service action any account holder can call once balance is zero), `exists_at` is still `true`, so no re-registration occurs, and the subsequent `coin::deposit` call aborts because `CoinStore<AptosCoin>` no longer exists: [3](#0-2) 

The analogous commission-distribution loop in `staking_contract::distribute_internal` demonstrates the pattern of iterating over all pool shareholders and calling `aptos_account::deposit_coins` for each one in a single atomic loop — any single abort inside that loop reverts the entire transaction, undoing all share redemptions for every other shareholder in the same call: [4](#0-3) 

`vesting::distribute` follows the same design intent (per the explicit comment at `set_beneficiary`), redeeming pool shares and depositing to each shareholder/beneficiary in one transaction. I was not able to fully read the loop body of `vesting::distribute` (lines ~680–750) in this session due to tool-call limits, so I cannot cite its exact deposit-loop structure line-by-line, but the design comment at `set_beneficiary` directly confirms the intended invariant ("distribute() wouldn't fail and block all other accounts... if one beneficiary is not registered") and that this invariant is enforced only at set-time.

Because Move transactions are atomic, if a beneficiary's `CoinStore<AptosCoin>` is closed after being set (but before `distribute()` runs), any subsequent call to `distribute()` for that vesting contract will abort on the failed deposit to that one beneficiary, and — since it's a single atomic transaction — no other shareholder in the same `grant_pool` receives their share either. This can repeat indefinitely since `distribute()` will keep re-attempting the same failing deposit on every call, permanently freezing payouts to all shareholders of that vesting contract until either the beneficiary re-registers for APT or the admin calls `reset_beneficiary`/`set_beneficiary` again to point elsewhere.

### Title
Stale beneficiary APT-registration check in `vesting::set_beneficiary` allows a beneficiary to permanently block `distribute()` for all shareholders - (File: aptos-move/framework/aptos-framework/sources/vesting.move)

### Summary
`set_beneficiary` verifies APT registration only once, at assignment time. A beneficiary can later close their own `CoinStore<AptosCoin>` (an unprivileged, self-controlled action), causing every future `distribute()` call on that vesting contract to abort, freezing distributions for all shareholders sharing the same grant pool.

### Finding Description
`assert_account_is_registered_for_apt` is a point-in-time check with no ongoing enforcement [5](#0-4) . `aptos_account::deposit_coins`, used to pay out distributions, only registers an account if it does not yet exist at all [3](#0-2) ; it does not re-register an existing account whose `CoinStore` was later removed. Since payouts for all shareholders of a vesting grant pool happen within one atomic transaction (as in the equivalent `staking_contract::distribute_internal` loop) [6](#0-5) , one failing deposit reverts the whole call, blocking payouts to every other shareholder as well.

### Impact Explanation
This is a value-availability issue, not a theft: no funds are stolen or redirected, but distributions to *all* shareholders in the affected vesting contract can be perpetually stuck as long as the unregistered beneficiary remains unregistered, since every retry of `distribute()`/`distribute_many` hits the same aborting deposit.

### Likelihood Explanation
Moderate-to-low likelihood: it requires (a) an admin having set a beneficiary for a shareholder, and (b) that specific beneficiary account voluntarily closing its `AptosCoin` store afterward — either by mistake or intentionally to grief co-shareholders in the same vesting pool. This is easy to trigger deliberately by a disgruntled or malicious beneficiary.

### Recommendation
Add resilience to `distribute()`/`distribute_internal`/`distribute_many` so that a single failed deposit does not revert the whole batch — e.g., wrap the per-recipient deposit in a way that on registration failure, funds are instead retained/escrowed for that recipient (or routed to a fallback) rather than aborting the entire distribution, or re-validate/re-register at distribute time using the same create-account-if-unregistered semantics already used for non-existent accounts.

### Proof of Concept
Move test sketch (extending the existing `vesting.move` test module):

```
// beneficiary account closes its own AptosCoin store
coin::close_coin_store<AptosCoin>(&beneficiary_signer); // or equivalent unregister call, self-invoked
// advance time / accumulate vested amount for multiple shareholders

// assert other shareholders' balances did NOT change, proving the whole grant pool is stuck
```
