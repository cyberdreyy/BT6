### Title
`delete_member` fails to purge a removed member's confirmations from other requests, allowing execution below live `num_confirmations` - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only clears confirmations for requests that the departing member originally *created* (`r.member == member`), not for requests the member merely *confirmed*. A stale confirmation from a since-removed member therefore continues to count toward `num_confirmations` in `confirm`, letting a request execute with fewer live confirmers than the required threshold.

### Finding Description
The binding that must hold is: `count(distinct live members whose confirmation is in self.confirmations.get(R)) == num_confirmations` at the moment `execute_request` runs. `delete_member` breaks this invariant.

`delete_member` (multisig2/src/lib.rs:356-379) computes `request_ids` as requests created by the departing member: [1](#0-0) 
and removes `self.confirmations` only for those request IDs. It does not scan `self.confirmations` for *other* requests that the departing member confirmed but did not create. So if member C confirms request R (created by a different member), `self.confirmations.get(&R)` becomes `{C}` via the insert path in `confirm`: [2](#0-1) 
When C is later removed via a separate `DeleteMember` request executed through `execute_request`/`delete_member`, R's entry in `self.confirmations` is left untouched, still containing `C.to_string()`, while C is removed from `self.members` (multisig2/src/lib.rs:374) and can no longer act as a confirmer.

Subsequently, any remaining live member D calls `confirm(R)`. `assert_valid_request` (multisig2/src/lib.rs:407-423) only checks that D is currently a member and that the request/confirmations exist — it never re-validates that the *existing* entries in `confirmations` still belong to current members. The size check `confirmations.len() as u32 + 1 >= self.num_confirmations` (line 304) counts C's stale entry plus D's new one, reaching `num_confirmations` with only one live confirmer (D), and `execute_request` runs the action (e.g., `Transfer` or `AddKey`).

No existing guard (`assert_valid_request`, `assert_self_request`, `assert_one_action_only`) checks that entries inside `confirmations` correspond to *current* members, so the divergence is never caught.

### Impact Explanation
This allows a multisig `Transfer` or `AddKey` action to be executed by a single live confirmer when `num_confirmations = 2` (or more generally, below the configured live-confirmer threshold), moving NEAR out of the multisig or granting a full-access key without the required number of legitimate approvals. This is a direct violation of the "multisig request executed below `num_confirmations` live members" Critical category, and is repeatable for any request that received a confirmation from a member prior to that member's removal.

### Likelihood Explanation
Preconditions are ordinary multisig operation, not attacker-controlled inputs: (1) a member confirms a request without immediately reaching quorum, (2) that member is later removed from the multisig via a normal `DeleteMember` request (a routine membership-management action), and (3) a remaining member confirms the still-pending request. No special privileges beyond normal multisig membership are needed, and the sequence can arise from ordinary usage or be deliberately engineered by a member who confirms a request, then arranges/waits for their own or a colluding member's removal, followed by one more confirmation to trigger execution with insufficient live approvals.

### Recommendation
In `delete_member`, iterate over all entries in `self.confirmations` (not just requests created by the departing member) and remove the departing member's `to_string()` entry from every confirmation set; alternatively, revalidate in `confirm`/`execute_request` that every account/key in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_counts_after_delete_member() {
    // 3 members: alice, bob, key-member C; num_confirmations = 2
    testing_env!(context_with_account(alice(), 1_000));
    let mut c = MultiSigContract::new(
        vec![
            MultisigMember::Account { account_id: alice() },
            MultisigMember::Account { account_id: bob() },
            MultisigMember::AccessKey { public_key: c_key() },
        ],
        2,
    );

    // Alice creates request R (transfer), not yet confirmed by anyone
    let r = c.add_request(MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: 100.into() }],
    });

    // C confirms R -> confirmations(R) = {C}, does not reach quorum (1 < 2)
    testing_env!(context_with_key(c_key(), 1_000));
    c.confirm(r);
    assert_eq!(c.confirmations.get(&r).unwrap().len(), 1);

    // Separately: alice + bob remove member C via DeleteMember request
    testing_env!(context_with_account(alice(), 1_000));
    let del_req = c.add_request(MultiSigRequest {
        receiver_id: alice(), // current_account_id in test context
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::AccessKey { public_key: c_key() },
        }],
    });
    c.confirm(del_req); // alice confirms, 1 < 2
    testing_env!(context_with_account(bob(), 1_000));
    c.confirm(del_req); // bob confirms -> 2 >= 2, executes delete_member(C)

    // BUG: R's confirmations still contain C, even though C is no longer a member
    assert!(!c.get_members().contains(&MultisigMember::AccessKey { public_key: c_key() }));
    assert!(c
        .confirmations
        .get(&r)
        .unwrap()
        .contains(&MultisigMember::AccessKey { public_key: c_key() }.to_string()));

    // Bob (single live confirmer) confirms R -> stale C entry + bob = 2 >= num_confirmations
    testing_env!(context_with_account(bob(), 1_000));
    c.confirm(r);

    // Request executed with only 1 live confirmer (bob), violating num_confirmations = 2
    assert_eq!(c.requests.len(), 0); // request removed/executed despite only 1 live confirmer
}
```
