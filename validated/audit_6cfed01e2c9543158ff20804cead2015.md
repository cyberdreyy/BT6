### Title
ERC4626 liquidity griefing can keep an epoch permanently unstoppable - ([File: `contracts/strategies/idle/ProgrammableBorrower.sol`](contracts/strategies/idle/ProgrammableBorrower.sol)) [1](#0-0) 

### Summary
An unprivileged user of the configured ERC4626 vault can temporarily drain its withdrawable liquidity immediately before `stopEpoch`, causing `ProgrammableBorrower.onStopEpoch` to revert even when the borrower-side share position economically covers the withdrawal. [2](#0-1) 

Because the revert propagates out of `IdleCDOEpochVariant._stopEpoch`, the epoch remains running, deposits remain paused, withdrawal requests remain closed, and pending withdrawal funds cannot be settled until the attacker allows vault liquidity to become available. [3](#0-2) [4](#0-3) 

### Finding Description
During an active programmable-borrower epoch, `ProgrammableBorrower` reserves `epochPendingWithdraws` for pending withdrawal requests. [5](#0-4) 

When the epoch is stopped, `IdleCDOEpochVariant._stopEpoch` calls `onStopEpoch` with the amount that must be available for the subsequent `transferFrom`. [6](#0-5) 

`onStopEpoch` compares the cash shortfall with `_currentVaultAssets`, which values the borrower's ERC4626 shares rather than checking the vault's currently withdrawable liquidity. [7](#0-6) [8](#0-7) 

If the share valuation covers the shortfall but the vault does not currently have enough liquid underlying, `vault.withdraw` reverts and the catch block rethrows `StopEpochVaultLiquidityUnavailable`. [9](#0-8) 

The caller does not catch this hook revert, so the complete stop transaction is rolled back before `isEpochRunning`, withdrawal flags, accounting, or default state can change. [3](#0-2) [10](#0-9) 

The ordinary borrower-default path is not reached because it is only entered after `onStopEpoch` returns `false` or after the later `getFundsFromBorrower` self-call fails. [3](#0-2) [11](#0-10) 

`emergencyExitVault` does not provide a reliable escape because it calls `vault.redeem`, which is subject to the same external-liquidity condition. [12](#0-11) 

The vault also cannot be replaced while shares remain, because `setVault` rejects a nonzero old-vault share balance. [13](#0-12) 

### Impact Explanation
A vault user can temporarily freeze all pool funds whose epoch settlement depends on liquidity held through `ProgrammableBorrower`. [2](#0-1) 

For example, if pending withdrawals are 1,000,000 USDC and the programmable borrower holds enough ERC4626 shares to cover them, an ordinary vault participant can redeem or withdraw the vault's available USDC below 1,000,000 immediately before the manager calls `stopEpoch`. [2](#0-1) 

The stop transaction then reverts, so the epoch remains running, the pool remains paused, ordinary withdrawal requests remain disabled, and the 1,000,000 USDC pending withdrawal obligation remains unclaimable. [14](#0-13) [4](#0-3) 

The attacker can repeat this whenever the manager retries, extending the freeze for as long as they can keep the shared vault below the required liquidity threshold. [3](#0-2) 

This is a temporary-freeze impact rather than only a liveness inconvenience: user principal and yield represented by tranche tokens and pending receipts cannot exit while the epoch cannot be stopped. [3](#0-2) [4](#0-3) 

### Likelihood Explanation
The attack requires a pending withdrawal or another stop-time cash requirement, an active programmable-borrower epoch, and a shared ERC4626 vault whose available liquidity can be reduced by an ordinary depositor. [3](#0-2) [2](#0-1) 

No privileged role, borrower misbehavior, invalid oracle value, or malicious vault implementation is required; a normal withdrawal by a preexisting ERC4626 shareholder is sufficient when it leaves less liquid underlying than `shortfall`. [9](#0-8) 

The economic-coverage check does not stop the attack because `convertToAssets` can continue valuing illiquid shares at or above the required amount while `withdraw` is temporarily unavailable. [7](#0-6) [8](#0-7) 

Likelihood is therefore deployment-dependent: it is low for a vault with ample sticky liquidity or restrictive withdrawals, but material for a liquid shared ERC4626 where the attacker controls enough shares to consume the relevant liquidity. [2](#0-1) 

### Recommendation
Separate transient ERC4626 illiquidity from borrower default and from a permanently retryable hook revert. [3](#0-2) 

A safe design would add an explicit owner/manager recovery path for an unavailable vault that can transition the facility into recovery without calling `convertToAssets`, `withdraw`, or `redeem`, while preserving borrower debt accounting and recording the vault position separately for later recovery. [15](#0-14) 

At minimum, check `vault.maxWithdraw(address(this))` or equivalent liquidity rather than only `convertToAssets`, and return a distinct external-liquidity failure status so the CDO can enter a dedicated halted/recovery state instead of leaving the active epoch unchanged. [2](#0-1) 

### Proof of Concept
The following Foundry fork test outline uses the existing `ProgrammableBorrowerCreditVault` fixture names conceptually; it requires a fork where the configured ERC4626 vault has a real nonprivileged shareholder able to withdraw enough liquidity. [1](#0-0) [3](#0-2) 

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";
import {IERC4626} from "../contracts/interfaces/IERC4626.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";

contract StopEpochVaultLiquidityGriefPoC is Test {
    // Existing production deployment / fixture objects.
    IdleCDOEpochVariant cdo;
    ProgrammableBorrower borrowerAdapter;
    IERC4626 externalVault;
    IERC20Detailed underlying;

    address manager;
    address kycLender;
    address vaultWhale;

    function test_vaultLiquidityDrain_blocksStopEpoch() external {
        // Setup:
        // 1. `cdo` is configured with `isProgrammableBorrower == true`,
        //    `isInterestMinted == true`, and `borrowerAdapter` as borrower.
        // 2. `kycLender` has already passed `isWalletAllowed`.
        // 3. `vaultWhale` is an ordinary holder of `externalVault` shares.

        uint256 pending = 1_000_000e6;

        // KYC lender deposits and creates a pending epoch withdrawal.
        vm.startPrank(kycLender);
        underlying.approve(address(cdo), pending);
        cdo.depositAA(pending);
        cdo.requestWithdrawAA(cdo.AATranche().balanceOf(kycLender) /* actual tranche API per fixture */);
        vm.stopPrank();

        // Manager starts the programmable-borrower epoch.
        vm.prank(manager);
        cdo.startEpoch();

        // Epoch end passes.
        vm.warp(cdo.epochEndDate() + 1);

        // Ordinary ERC4626 participant drains current vault liquidity below
        // the amount required by ProgrammableBorrower.onStopEpoch.
        // On a fork this is a real whale redemption, not a mock or privileged action.
        uint256 whaleShares = externalVault.balanceOf(vaultWhale);
        vm.prank(vaultWhale);
        externalVault.redeem(whaleShares, vaultWhale, vaultWhale);

        // Optional assertion on forks exposing liquidity through maxWithdraw:
        // assertLt(externalVault.maxWithdraw(address(borrowerAdapter)), pending);

        // The share position can still economically cover `pending`, so the
        // `shortfall > _currentVaultAssets()` early return is bypassed. The
        // physical ERC4626 withdrawal nevertheless reverts, and the custom
        // error propagates through CDO.stopEpoch.
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(0, 0);

        // Nothing was settled and the pool remains in the active-epoch state.
        assertTrue(cdo.isEpochRunning());
        assertTrue(cdo.paused());
        assertFalse(cdo.allowAAWithdrawRequest());
        assertFalse(cdo.allowBBWithdrawRequest());
    }
}
```

    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // if we want to close the pool and the borrower still owes any amount, consider it a failure and let IdleCDO handle it as a default instead of a close. 
    if (_isRequestingAllFunds && (borrowerPrincipal != 0 || borrowerInterestDebt != 0 || borrowerInterestAccrued != 0)) {
      return false;
    }

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (_amountRequired > onHand) {
      uint256 shortfall = _amountRequired - onHand;
      // If the vault shares do not economically cover the shortfall, let IdleCDO's later
      // transferFrom fail and use the existing default path. Only an otherwise-covered ERC4626

          epochWithdrawnFromVault += shortfall;

  /// @notice Abort active epoch accounting after IdleCDO defaulted the facility.
  /// @dev This keeps borrower-side epoch state aligned with IdleCDO's stopped/defaulted state
  /// without depending on a live ERC4626 valuation. A hard default is terminal for the normal
  /// epoch flow, so there is no next buffer period that needs a `bufferStartVaultAssets` baseline.
  function onDefault() external nonReentrant {
    _checkOnlyIdleCDO();
    if (!epochAccountingActive) return;

    bufferedVaultDelta = 0;
    bufferInterest = 0;
    // Do not call `convertToAssets` here. Even if the external vault's valuation view is
    // unavailable during stress, CDO default handling must still be able to shut down borrowing.
    bufferStartVaultAssets = 0;
    epochPendingWithdraws = 0;
    epochAccountingActive = false;
    emit EpochAccountingStopped();
  }
