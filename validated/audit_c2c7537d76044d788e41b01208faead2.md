Based on my research, `createDstEscrow` in `BaseEscrowFactory.sol` has no whitelist/access-token gate — the function is `external payable` with only a native-value check and a timelock-vs-`srcCancellationTimestamp` check [1](#0-0) . Any caller supplies the full `Immutables` struct, including the `parameters` bytes that encode `protocolFeeAmount`/`integratorFeeAmount`/fee recipients, and these values are never checked against `immutables.amount` at deployment time [2](#0-1) .

### Title
Unchecked destination fee amounts in `createDstEscrow` allow permanent underflow-revert DoS of `EscrowDst.withdraw`/`publicWithdraw` - (File: contracts/BaseEscrowFactory.sol / contracts/EscrowDst.sol)

### Summary
The `_postInteraction` fee-amount sanity check only validates the fee amounts that `FeeTaker._getFeeAmounts` computes for the emitted `SrcEscrowCreated` event's `immutablesComplement.parameters` [3](#0-2) . It does not constrain what is actually supplied to `createDstEscrow`, since the caller of `createDstEscrow` builds the `dstImmutables.parameters` field independently and the function performs no cross-validation of `protocolFeeAmount + integratorFeeAmount < immutables.amount` [1](#0-0) .

### Finding Description
`EscrowDst._withdraw` computes `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` without any check that the subtrahends are bounded by `immutables.amount` [4](#0-3) . Both `withdraw` and `publicWithdraw` route into `_withdraw` [5](#0-4) , so if `protocolFeeAmount + integratorFeeAmount >= immutables.amount`, every withdrawal path underflows and reverts (Solidity 0.8 panic), for the entire life of the escrow. Since `immutables` is fixed at deployment (validated only by hash equality via `onlyValidImmutables`), there is no way to correct the bad parameters after the fact — the only remaining path is `cancel()` after the `DstCancellation` timelock, which returns `immutables.amount` (the full destination amount) to `immutables.taker`, not the maker [6](#0-5) .

### Impact Explanation
This mirrors the H-06 root cause: an arithmetic operation subtracts an attacker/caller-controlled value from a balance without bounding it, causing a hard revert that blocks the legitimate beneficiary (here, the maker) from ever withdrawing. In this protocol's flow, the party calling `createDstEscrow` (the taker/resolver) fully controls the `parameters` bytes with no on-chain cross-check against the amount, allowing them to make dst-side withdrawal for the maker permanently impossible, while `cancel()` after timeout returns the entire destination amount to the taker. This corresponds to permanent loss/freezing of maker funds on the destination chain — within the temporary/permanent freezing-of-funds bounty categories.

### Likelihood Explanation
Uncertain/lower confidence: this requires the taker (who is a swap counterparty, not `owner`/`governance`) to supply malformed `parameters` when calling `createDstEscrow`. I could not fully verify within available tool calls whether `createDstEscrow` (or an upstream off-chain/relayer process, or the `ResolverExample` mock) is expected to always mirror the `immutablesComplement.parameters` emitted from `SrcEscrowCreated` bit-for-bit, nor whether the bounty considers a taker/resolver crafting their own dst escrow deployment a "privileged resolver" (which is explicitly out of scope) or a plain unprivileged swap counterparty. This distinction is decisive for whether this qualifies under the bounty's attacker model, and I was unable to conclusively resolve it from the indexed code alone.

### Recommendation
Add a check in `createDstEscrow` (or in `EscrowDst._withdraw`) enforcing `dstImmutables.protocolFeeAmount() + dstImmutables.integratorFeeAmount() < dstImmutables.amount`, reverting with `InvalidFeeAmounts()` (already defined in `BaseEscrowFactory.sol`) if violated, analogous to the existing check on the src side.

### Proof of Concept
1. Taker/resolver calls `createDstEscrow` with `dstImmutables.amount = A` and `parameters` encoding `protocolFeeAmount = A`, `integratorFeeAmount = 1` (or any combination where `protocolFeeAmount + integratorFeeAmount >= A`), sending the correct `msg.value` per the balance check in `createDstEscrow` [7](#0-6) .
2. After the withdrawal timelock, maker or resolver calls `withdraw`/`publicWithdraw` with the matching secret; `_withdraw` reverts on `immutables.amount - integratorFeeAmount - protocolFeeAmount` underflow [4](#0-3) .
3. After `DstCancellation`, the taker calls `cancel()`, receiving the full `immutables.amount` back to themselves [6](#0-5) , while the maker (who already released src-side funds to the taker on secret reveal) receives nothing on the destination chain.

**Caveat:** I was unable to fully verify (within available search) whether this scenario is excluded under the bounty's "privileged resolver assumptions" carve-out, since the attacker here is the resolver/taker acting during a step (`createDstEscrow`) that they are normally expected to perform honestly. If it is intended that resolvers are semi-trusted for constructing correct dst immutables, this finding would fall outside the bounty's accepted attacker model, and a background Devin session or the project maintainers should confirm the trust assumptions around `createDstEscrow` callers before treating this as valid.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
