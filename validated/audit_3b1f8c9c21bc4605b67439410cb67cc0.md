### Title
`get_token_largest_accounts` silently reports a large-but-unparsable token account's amount as `0`, corrupting ranked output - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_token_largest_accounts` unpacks each candidate token account with `StateWithExtensions::<TokenAccount>::unpack` and falls back to `.unwrap_or(0)` on failure, rather than excluding the account or surfacing the raw base-struct amount. An unprivileged attacker who owns a token account for a given mint can make the account's trailing extension bytes malformed (while keeping a valid base `Account` struct and a large `amount`), causing `unpack` to fail as a whole; the RPC will then rank that account as balance `0`, so smaller-but-cleanly-parsable accounts are reported as "largest" instead.

### Finding Description
The relevant code is: [1](#0-0) 

```rust
for (address, account) in self
    .get_filtered_spl_token_accounts_by_mint(...)
    .await?
{
    let amount = StateWithExtensions::<TokenAccount>::unpack(account.data())
        .map(|account| account.base.amount)
        .unwrap_or(0);
    ...
}
```

Candidates are gathered via `get_filtered_spl_token_accounts_by_mint`, which applies only a `Memcmp` filter on the mint field and a `RpcFilterType::TokenAccountState` filter (`Account::valid_account_data`), not a full TLV/extension unpack: [2](#0-1) [3](#0-2) 

Because these filters only validate the base 165-byte `Account` layout (mint offset, account state byte), an account whose bytes beyond the base struct (Token-2022 extension TLV data / `account_type` byte) are corrupted can still pass the filter and be included in the candidate set. When such an account is then run through `StateWithExtensions::<TokenAccount>::unpack` in `get_token_largest_accounts`, the whole unpack fails (extension parsing is part of `unpack`, not `valid_account_data`), and the code substitutes `amount = 0` via `.unwrap_or(0)` instead of skipping the account or reporting an error. Any attacker can create an SPL Token-2022 account for an arbitrary mint (mints and their accounts are permissionless to create on-chain), set a large `amount` in the base struct, and append invalid extension bytes after it (e.g., a bogus `account_type`/TLV length so `StateWithExtensions::unpack` returns `Err`). No validator-owned guard checks or repairs this before the amount is used for ranking.

### Impact Explanation
This is a misreporting bug in Agave's own RPC aggregation logic (not the sBPF interpreter or the SPL dependency's parsing correctness): the query result for `getTokenLargestAccounts` can present a smaller balance as the top "largest" holder while silently zeroing out a genuinely larger, malformed-but-owned account. Downstream integrators (explorers, analytics, compliance tooling) that rely on this RPC method for supply/holder-concentration analysis get a wrong answer. This matches the explicitly accepted category "decoder panic and misreporting" / "wrong ... account data returned" from a single low-rate RPC call.

### Likelihood Explanation
Fully attacker-controlled and requires no privileges: any client can create a Token-2022 account with an extension and mangle only the trailing extension bytes while leaving the base `Account` struct (and hence `amount`) valid and large. A single `getTokenLargestAccounts` call then exhibits the misordering. It is deterministic and repeatable, and only needs one JSON-RPC call to trigger, well within the single-call constraint.

### Recommendation
In `get_token_largest_accounts`, do not silently coerce unpack failures to `0`. Either:
- Skip/exclude accounts whose `StateWithExtensions::<TokenAccount>::unpack` fails (log/count them separately) rather than ranking them at balance 0, or
- Fall back to reading the raw `amount` field directly from the fixed base-struct offset (bytes 64..72) when the full TLV unpack fails, since the base struct is still well-formed and the amount is deterministically at that offset regardless of extension corruption.
