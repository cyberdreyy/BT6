### Title
Misreported token transfer amounts in `jsonParsed` instruction decoding when Token-2022 transfer-fee extension is active - (File: `transaction-status/src/parse_token.rs`)

### Summary
Agave's transaction-status decoder parses SPL-Token `Transfer`/`TransferChecked`/`Approve`/`MintTo`/`Burn` instructions by echoing the `amount` field taken verbatim from the instruction's raw data, without ever cross-checking it against the actual pre/post account balance change recorded by the SVM for that transaction. This mirrors the Sudoswap `_validateTokenInput()` finding, where one code path trusts a caller-declared transfer amount instead of verifying the token balance actually moved. Because Token-2022 mints can carry a `TransferFeeConfig` extension that silently withholds a portion of every transfer, the plain `transfer`/`transferChecked` parsed output can misreport how many tokens the destination actually received.

### Finding Description
In `transaction-status/src/parse_token.rs`, the `Transfer` and `TransferChecked` instruction variants build their JSON `info` purely from the instruction-supplied `amount`: [1](#0-0) [2](#0-1) 

Only the dedicated `TransferCheckedWithFee` extension instruction explicitly reports a separate `feeAmount` alongside `tokenAmount`: [3](#0-2) 

However, for a mint that has the `TransferFeeConfig` extension enabled, a wallet/authority is still able to submit an ordinary `Transfer`/`TransferChecked` instruction (the on-chain token-2022 program silently withholds the configured basis-point fee from the destination regardless of which transfer variant is used). Agave's decoder has no logic that consults the mint's `TransferFeeConfig` extension when parsing plain `transfer`/`transferChecked`, so it always reports the full instruction `amount` as delivered, even though the SVM's own post-transfer account state (and the correctly-computed `pre_token_balances`/`post_token_balances` derived from `SvmTokenInfo::unpack_token_account`, which reads the real on-chain `amount` field) would show a smaller amount actually credited: [4](#0-3) 

This is the same root cause pattern as the reported bug: one path (the pre/post token-balance computation, analogous to `router.pairTransferERC20From()`'s balance check) validates the real transferred amount, while another path (the parsed-instruction `amount`/`tokenAmount` field, analogous to the unchecked `safeTransferFrom()` branch) simply trusts the requested/declared value without confirming it against actual account state.

### Impact Explanation
This decoder is reachable by any unprivileged JSON-RPC client through `getTransaction`, `getBlock`, and `getConfirmedTransaction` with `encoding: "jsonParsed"`, which invoke `parse_token` via `parse_instruction.rs`'s dispatch on `ParsableProgram::SplToken`. Downstream consumers (explorers, wallets, exchanges, indexers) commonly treat the parsed `amount`/`tokenAmount` field as authoritative evidence of how many tokens moved. For Token-2022 mints with an active transfer-fee extension, this leads to systematically overstated reported transfer amounts (wrong data returned from a query), which can misinform accounting, compliance, and reconciliation systems built on Agave RPC responses even though the ground-truth `pre_token_balances`/`post_token_balances` in the same transaction metadata are correct.

### Likelihood Explanation
Any user can create a Token-2022 mint with `TransferFeeConfig` and send `Transfer`/`TransferChecked` instructions against it (this is standard, permitted usage of the SPL Token-2022 program, not a maliciously crafted edge case). Every `getTransaction`/`getBlock` call with `jsonParsed` encoding against such a transaction will exhibit the misreporting, making this trivially and repeatably reachable with a single unprivileged RPC call.

### Recommendation
When parsing `Transfer`/`TransferChecked` (and other amount-bearing instructions) for a mint carrying `TransferFeeConfig`, either avoid reporting a bare `amount`/`tokenAmount` as "delivered" or additionally surface the fee derived from the mint's extension configuration (as is already done for `TransferCheckedWithFee`), so that RPC consumers cannot mistake the raw instruction amount for the amount actually credited to the destination account.

### Proof of Concept
1. Create a Token-2022 mint with the `TransferFeeConfig` extension (e.g., 100 bps fee).
2. Submit a plain `Transfer` or `TransferChecked` instruction moving `1_000_000` tokens from account A to account B.
3. Call `getTransaction` with `{"encoding": "jsonParsed"}` on the resulting signature.
4. Observe the parsed instruction reports `"amount": "1000000"` (or `tokenAmount.amount: "1000000"`) with no fee field, while the transaction's `postTokenBalances`/`preTokenBalances` (computed via `SvmTokenInfo::unpack_token_account`) show that account B's actual balance only increased by `990000`, confirming the parsed instruction data misreports the real transferred amount.

impl SvmTokenInfo {
    fn unpack_token_account<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        account: &AccountSharedData,
        index: usize,
    ) -> Option<Self> {
        let program_id = *account.owner();
        let generic_token::Account {
            mint,
            owner,
            amount,
        } = generic_token::Account::unpack(account.data(), &program_id)?;

        let mint_account = account_loader.load_account(&mint)?;
        if *mint_account.owner() != program_id {
            return None;
        }

        let generic_token::Mint { decimals, .. } =
            generic_token::Mint::unpack(mint_account.data(), &program_id)?;

        Some(Self {
            account_index: index.try_into().ok()?,
            mint,
            amount,
            owner,
            program_id,
            decimals,
        })
    }
