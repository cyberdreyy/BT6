### Title
Manipulable ERC4626 `convertToAssets` lets an attacker inflate `totalInterestDueNow` and mint phantom epoch yield - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` values its vault sleeve purely via `vault.convertToAssets(shares)`. An unprivileged user of the underlying ERC4626 vault can move that exchange rate (direct underlying donation / share-price manipulation), inflating the vault PnL reported to `IdleCDOEpochVariant` at `stopEpoch`. The pool then books interest that was never earned, inflating tranche NAV/prices so the attacker (as a tranche holder / withdrawal requester) is paid more than the real assets, leaving residual lenders insolvent.

### Finding Description
The analog to "low-liquidity pool used as price oracle" is the ERC4626 share price used as the accounting oracle:

- `_currentVaultAssets()` converts the borrower's vault shares to underlying with `vault.convertToAssets(shares)` (`ProgrammableBorrower.sol:546-549`). This is the sole price source for the sleeve.
- `_vaultNetInterest()` computes `netDelta = bufferedVaultDelta + (currentVaultAssets + epochWithdrawnFromVault) - (epochStartVaultAssets + epochDepositedToVault)` (`ProgrammableBorrower.sol:337-347`). A manipulated `convertToAssets` directly manufactures positive `interest`.
- `totalInterestDueNow()` returns `vaultInterest + borrowerInterestAccruedNow + bufferInterest - loss` (`ProgrammableBorrower.sol:330-334`) and is the single value `IdleCDOEpochVariant` reads at `stopEpoch` to price the epoch.
- In interest-minted mode the "gain" is minted (not pulled as cash), so NAV and tranche prices are inflated without any real underlying arriving; `onStopEpoch` only pulls `_amountRequired` for pending withdraws, not the minted interest (`ProgrammableBorrower.sol:231-268`).

Attack path (running epoch, programmable/minted-interest mode):
1. Attacker is a KYC lender holding tranche tokens (or a queued withdrawal) and also holds shares of the configured ERC4626 vault.
2. During the running epoch, attacker donates underlying directly to the ERC4626 vault (or otherwise pumps the share price), raising `convertToAssets` for the borrower's shares by `X`.
3. Honest owner calls `stopEpoch`: `totalInterestDueNow()` is inflated by `X`, the CDO accounts a fake gain and raises `priceAA`/`priceBB`.
4. Attacker withdraws / claims at the inflated price. Since no real `X` exists, later redeemers cannot be paid — solvency broken.
5. The attacker redeems their own vault shares afterwards, recovering ~all of the donation, so the donated amount is not actually lost.

No guard stops this: `onStopEpoch` only checks `shortfall > _currentVaultAssets()` using the same inflated price; `_skimDonatedAssets`/`unclaimedFees` apply to the CDO's own token balance, not the external vault's share price; `onDefault` avoids the view but only after a default path that is never triggered here.

### Impact Explanation
Fabricated vault yield is distributed across tranche NAV at epoch stop. The attacker extracts underlying against a NAV that includes nonexistent yield, causing direct insolvency: last redeemers' claims exceed remaining real assets. Loss is bounded by the attacker-controlled share-price delta of the ERC4626 vault, up to the full recorded `vaultInterest`.

### Likelihood Explanation
Requires the configured ERC4626 vault to have a manipulable `convertToAssets` (donation-sensitive vaults, vaults priced on thin liquidity, or vaults whose `totalAssets` reads a manipulable source). The attacker only needs to be a vault user plus a tranche holder — both explicitly unprivileged roles. The honest owner calling `stopEpoch` completes the attack. Feasibility depends on the specific deployed vault, which is a deployment-time assumption not enforced on-chain (`setVault` only checks `asset()` matching).

### Recommendation
- Track vault PnL from cash flows (`epochDepositedToVault`/`epochWithdrawnFromVault` and actual redeemed amounts) instead of `convertToAssets`, or bound the recognized gain by assets actually withdrawn.
- Alternatively, validate `convertToAssets` against a snapshot price taken at `onStartEpoch` and cap per-epoch recognized vault interest.
- Restrict eligible vaults to donation-resistant implementations (virtual shares/assets offset) and document that assumption in `setVault`.
