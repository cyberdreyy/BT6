### Title
Loss-adjusted withdraw receipts keyed to the wrong epoch are paid at par, draining active LP funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.collectWithdrawFunds` stores the realized-loss haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is incremented inside `deposit()` during the same `stopEpoch` while `isEpochRunning()` is still true. Receipts were recorded under the pre-increment epoch in `lastWithdrawRequest`/`withdrawsRequestsByEpoch`, so `_claimLossAdjustedWithdrawRequest` looks up a `lossRecoveryPrice` of zero and the claim falls through to `_claimFundedWithdrawRequest`, which pays the full un-haircut `withdrawsRequests[_user]` amount. This mirrors the use-after-free pattern of CVE-2023-1670: state (the haircut) is written under a stale/freed key while a dangling reference (the old `lastWithdrawRequest` epoch) is dereferenced later.

### Finding Description
In `requestWithdraw`, receipts are tagged with the current epoch: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` [1](#0-0) . `epochNumber` is incremented inside `deposit()` whenever `idleCDO.isEpochRunning()` is true [2](#0-1) . During `_stopEpoch`, borrower repayments are deposited to the strategy while the epoch is still flagged running, so `epochNumber` bumps from `N` to `N+1` before `collectWithdrawFunds(_pendingToFund)` executes [3](#0-2) . `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber]` — i.e. under `N+1`, not `N` [4](#0-3) .

On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. epoch `N`, finds `0`, and returns early [5](#0-4) . `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` at par (the epoch gate `epochNumber <= lastWithdrawRequest` passes because `epochNumber` was bumped) [6](#0-5) .

### Impact Explanation
When `stopEpochWithDuration(_lossAmount)` partially funds pending receipts, the haircut is never applied. Only `pendingToFund < pendingBasis` underlying is transferred to the strategy, but claimants withdraw `pendingBasis` at par via `_transferFundedClaim`. The deficit is covered by underlying backing active tranche NAV held in the strategy, so loss-adjusted redeemers steal directly from non-redeeming AA/BB LPs. Broken invariant: loss waterfall — pending-receipt losses are silently socialized onto active LPs instead of the receipt holders, and the strategy becomes under-collateralized by `pendingBasis - pendingToFund`. Note: `previewLossAdjustedWithdrawFunds` computes the split correctly; only the epoch keying breaks [7](#0-6) .

### Likelihood Explanation
Triggering requires `stopEpochWithDuration` to realize a loss while pending normal withdraw receipts exist — a routine distressed-epoch path, reachable with honest owner/manager/borrower sequencing. Any user with a pending receipt (a KYC-passing lender is sufficient) then claims. No privileged attacker needed; every receipt holder claiming after the lossy stop over-draws. Caveat: the exploit depends on `collectWithdrawFunds` being invoked after the `deposit()` call that increments `epochNumber` inside `_stopEpoch`; I could not read the post-line-400 tail of `_stopEpoch`/`stopEpochWithDuration` to confirm that ordering, but `deposit()` is the only `epochNumber` mutator and it must run while `isEpochRunning` is true, so the increment necessarily precedes or coincides with the collection within the same transaction.

### Recommendation
Store the loss recovery price under the request epoch, not the live counter. Either capture `epochNumber` in `collectWithdrawFunds` before any increment (e.g. pass the request epoch from the CDO, or store `lossRecoveryPriceByEpoch[epochNumber - 1]` when called during stop), or record in `requestWithdraw` the epoch under which the haircut will be written. Alternatively, write `lossRecoveryPriceByEpoch` keyed by each request epoch present in `pendingWithdraws` rather than the post-increment global.

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
