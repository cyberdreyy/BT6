### Title
Unvalidated symlink target allows dangling/absolute-path symlink creation during zip extraction - (File: helpers/archives/zip_extract.go)

### Summary
`extractZipSymlinkEntry` reads the zip entry's file content and passes it directly to `os.Symlink` as the link target without validating that it is a relative path confined to the extraction root. An attacker who controls a cache or artifact zip (e.g. a pipeline author) can plant a symlink entry whose target is an absolute path or contains `../` segments, causing the victim's extraction to create a symlink pointing outside the job workspace.

### Finding Description
In `extractZipFile`, entries with `os.ModeSymlink` are routed to `extractZipSymlinkEntry`: [1](#0-0) 

`extractZipSymlinkEntry` reads the entry's content (which for a zip symlink entry is defined to be the link target) and calls `os.Symlink(string(data), file.Name)` with no validation of `data`: [2](#0-1) 

The only path-safety check applied during extraction (`errorIfGitDirectory`, checked in `ExtractZipArchive`) only rejects entries whose *name* starts with `.git`; it does not inspect the symlink target content and does not reject absolute paths or `../` sequences in either the entry name or the symlink target: [3](#0-2) [4](#0-3) 

Since a cache/artifact zip is fully attacker-controlled content (a pipeline author defines `cache:` / `artifacts:` paths and their contents are packed by the runner from job-writable directories), an attacker can craft a zip with a symlink entry named e.g. `link` whose content is `/etc/passwd` or `../../other-job-workspace/secrets.env`. When this cache/artifact is restored by `ExtractZipArchive` → `extractZipFile` → `extractZipSymlinkEntry`, a dangling (or valid) symlink named `link` is created inside the job workspace but pointing outside of it. This by itself is a symlink-planting primitive; combined with a legitimate subsequent job step that writes into `link` (a normal build/test command, or re-upload of that path as an artifact), that write is dereferenced through the symlink and lands at the attacker-chosen external path.

### Impact Explanation
This is a "symlink planting" primitive: extraction alone creates an out-of-workspace-pointing symlink without any write validation on the target. The actual data corruption/read requires a follow-on action (the job's own build step or CI config writing to the linked path, or artifact upload following the symlink). Scoped impact is host file write/overwrite outside the job workspace if a subsequent step writes to the planted path, and potential cross-project impact if the target path is another job's or project's workspace on a shared host/executor. The severity depends heavily on executor isolation: on properly isolated executors (docker with per-job containers/volumes) the write is confined to that container's filesystem view, limiting impact to files reachable from within the container.

### Likelihood Explanation
Feasibility is high on the extraction side — crafting a zip with a symlink whose content is an absolute path or traversal sequence is trivial and requires only the ability to author a `.gitlab-ci.yml` cache/artifact definition and control job workspace content, which matches the "unprivileged pipeline author" threat model. However, realizing concrete file-write impact requires an additional trigger (the job or a later job step must write through the symlink path), and impact is bounded by executor filesystem isolation, which reduces likelihood of true cross-project/host impact in default (containerized) executor configurations.

### Recommendation
Validate symlink targets in `extractZipSymlinkEntry` (and the equivalent tar handling, if any) before calling `os.Symlink`: reject targets that are absolute paths, and reject targets that, once resolved relative to the entry's directory, would escape the extraction root (e.g. using `filepath.Clean`/`filepath.IsAbs` plus a `filepath.Rel`/prefix check against the archive root). Apply the same containment check to the entry name itself, not just the `.git` check.

### Proof of Concept
```go
func TestExtractZipSymlinkEntry_RejectsAbsoluteTarget(t *testing.T) {
    dir := t.TempDir()
    zipPath := filepath.Join(dir, "evil.zip")

    // build a zip with one entry: name="link", mode=symlink, content="/etc/passwd"
    f, _ := os.Create(zipPath)
    zw := zip.NewWriter(f)
    hdr := &zip.FileHeader{Name: "link"}
    hdr.SetMode(os.ModeSymlink | 0o777)
    w, _ := zw.CreateHeader(hdr)
    w.Write([]byte("/etc/passwd"))
    zw.Close()
    f.Close()

    extractDir := filepath.Join(dir, "extract")
    os.MkdirAll(extractDir, 0o755)
    old, _ := os.Getwd()
    os.Chdir(extractDir)
    defer os.Chdir(old)

    err := archives.ExtractZipFile(zipPath)
    require.NoError(t, err)

    target, err := os.Readlink(filepath.Join(extractDir, "link"))
    require.NoError(t, err)
    // Expected (after fix): extraction should fail or target must be confined to extractDir
    assert.NotEqual(t, "/etc/passwd", target, "symlink target escapes extraction root")
}
```
Expected current behavior: the symlink `link` is created pointing to `/etc/passwd`, demonstrating the missing validation; after a fix, extraction should reject the entry or rewrite/clamp the target to remain inside the extraction root.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
