### Title
WebAPI Trigger message timestamp check only rejects stale messages, not future-dated ones, allowing indefinite message validity / replay - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
Analogous to the reported "proposals do not have an expiration date" bug class, the Chainlink Gateway's `HandleLegacyUserMessage` staleness check only enforces a *lower* bound on message age and never enforces an *upper* bound (i.e., rejecting messages whose `Timestamp` is in the future). A signed, otherwise-valid message with an arbitrarily far-future `Timestamp` will never be considered "stale" and can be accepted by the gateway indefinitely, defeating the intended freshness/expiration guarantee.

### Finding Description
`HandleLegacyUserMessage` validates message freshness with: [1](#0-0) 

The check `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` only fails (rejects) when the message is *older* than `MaxAllowedMessageAgeSec`. There is no corresponding check that `payload.Timestamp` is not too far in the future. Because the subtraction is done in `uint`, if `payload.Timestamp` is set to a very large future value, the left-hand side stays small and the comparison never triggers the "stale message" rejection path, so the message is treated as fresh regardless of how far in the future its timestamp is set.

This mirrors the reported bug class where a "proposal" (here, a signed gateway message) lacks a true expiration bound and can therefore be valid/executable indefinitely, since an unprivileged but otherwise legitimately-signed message sender fully controls the `Timestamp` field embedded in the JSON payload (it is not part of the cryptographically committed envelope fields checked elsewhere, and the freshness gate itself is one-sided).

The rest of the envelope (`Message.Validate()`) validates ID/method/DonID lengths and signature format but does not perform any timestamp bound-checking itself: [2](#0-1) 

### Impact Explanation
An attacker (a party with a valid signing key for their own node/workflow, i.e., an "unprivileged" actor relative to gateway operators) can craft a `web_api_trigger` message with a future timestamp and have it accepted by the gateway well beyond the intended freshness window. Combined with the message-ID based dedupe in `savedCallbacks` (which only prevents concurrent duplicate IDs, not long-term replay), this weakens the intended anti-replay/anti-staleness protections for the internet-facing gateway's user message handling path, potentially enabling delayed or repeated processing of trigger requests that operators assumed were time-bound.

### Likelihood Explanation
Likely low-to-moderate: exploitation only requires control over the `Timestamp` field of a payload that the caller already signs and submits, which is a normal part of the request they construct. No cryptographic bypass is needed — it is a pure logic gap in the freshness check.

### Recommendation
Add an upper-bound check rejecting messages whose `Timestamp` is further in the future than an allowed clock-skew tolerance (mirroring how `AuthTimestampToleranceSec` is enforced symmetrically in `core/services/gateway/connector/connector.go`'s `ChallengeResponse`, which checks both `ts < nowTs-tolerance` and `nowTs+tolerance < ts`). Apply the same symmetric bound in `HandleLegacyUserMessage`.

### Proof of Concept
1. Construct a valid `web_api_trigger` `api.Message` with a correctly computed signature but set `payload.Timestamp` to `time.Now().Unix() + 10_000_000` (far future).
2. Submit it to the gateway's `HandleLegacyUserMessage` path.
3. Observe that the staleness check `uint(time.Now().Unix())-MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates to `false` (since `payload.Timestamp` is far larger than the left side), so the message passes the "stale message" check and is forwarded to DON nodes, despite being nonsensically far in the future and never subject to any expiration.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
