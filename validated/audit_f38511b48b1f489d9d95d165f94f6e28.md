### Title
`onStopEpoch` validates vault coverage with `convertToAssets` but `vault.withdraw` resolves liquidity separately, letting a vault user block `stopEpoch` (check/act mismatch analog to DNS-rebinding SSRF) - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
In `ProgrammableBorrower.onStopEpoch`, coverage of the `stopEpoch` shortfall is checked against `vault.convertToAssets(shares)` — a nominal valuation — while the actual liquidity is obtained in a separate step via `vault.withdraw(shortfall)`, which succeeds only if the ERC4626 vault has *redeemable liquidity* at that moment. This mirrors the TypeBot DNS-rebinding bug class: a value is "resolved" and approved once, then the real action re-resolves against live external state that an attacker can change between (or around) the check and the use. A user of the programmable borrower's ERC4626 vault can drain or keep drained the vault's available liquidity, making the check pass (or be skipped) while `withdraw` reverts, causing `stopEpoch` to revert with `StopEpochVaultLiquidityUnavailable` and freezing the epoch/withdrawal flow.

### Finding Description
The relevant code is `onStopEpoch` in `contracts/strategies/idle/ProgrammableBorrower.sol`:

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  // check: nominal coverage only
  if (shortfall > _currentVaultAssets()) return true;
  // action: fresh resolution against live vault liquidity
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) { ... }
  catch { revert StopEpochVaultLiquidityUnavailable(); }
}
```

`_currentVaultAssets()` (lines 546–549) is `vault.convertToAssets(balanceOf(this))`. For lending-style or credit ERC4626 vaults, `convertToAssets` values shares against *total* managed assets, including assets currently lent out or otherwise illiquid — it does not equal `maxWithdraw`/`maxRedeem`. So the guard can conclude "covered" while the subsequent `withdraw` deterministically reverts for lack of vault liquidity.

Two exploitation paths for an unprivileged user of the same ERC4626 vault:

1. **Liquidity drain**: the attacker withdraws/borrows essentially all of the vault's free liquidity (or keeps it out via an open borrow), then lets the manager call `stopEpoch`. The check passes (or `shortfall <= _currentVaultAssets()` holds), `vault.withdraw` reverts, and `stopEpoch` reverts via `StopEpochVaultLiquidityUnavailable`. The epoch cannot be stopped, `pendingWithdraws` cannot be funded, and tranche holders' withdrawals are frozen for as long as the attacker keeps the vault drained.
2. **False "covered" → forced default**: with `shortfall > _currentVaultAssets()` the hook returns `true` without pulling liquidity, deferring failure to IdleCDO's `transferFrom`, which then fails and routes into the default path — the check/act mismatch can downgrade a liquidity problem into a borrower-default handling even though the borrower ledger is solvent.

Unlike the DNS case the check and use are in one transaction, but the exploitable property is identical: the validator measures a *different quantity* (share valuation / resolvable name) than the one the action actually depends on (redeemable liquidity / connected IP), and an external party controls that quantity.

### Impact Explanation
Temporary freezing of all LP funds in the facility: `stopEpoch` cannot complete while the vault is drained, so `pendingWithdraws` (queued withdraw receipts owed to tranche holders) and all NAV stay locked, and borrowers' `epochPendingWithdraws` reservation cannot be released. The frozen amount equals the full pool NAV plus pending withdraws for the duration of the liquidity drain; on shared credit vaults an attacker can sustain the drain arbitrarily (e.g., by continually re-borrowing), extending the freeze. The second path additionally risks an unwarranted default flow (haircut via `defaultRecoveryPrice` at finalization) from a pure liquidity timing issue.

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault admits third-party users whose actions reduce `maxWithdraw` below `convertToAssets` (shared lending/credit vaults). The attacker needs capital roughly equal to the vault's free liquidity, or an open borrow position; no privileged role is needed. The attack is front-runnable against the honest manager's `stopEpoch` call each time liquidity reappears.

### Recommendation
- Replace the valuation check with a liquidity-aware check: `vault.maxWithdraw(address(this))` (or `maxRedeem`) before calling `withdraw`, so the validated quantity is exactly what the action uses — analogous to pinning the validated IP in the SSRF fix.
- On `withdraw` failure, do not revert the whole stop; fall back to the same path as the `shortfall > coverage` branch (return `true` and let IdleCDO's pull fail atomically) or retry with `redeem`/`maxWithdraw`-sized amounts.
- Alternatively, withdraw `min(shortfall, vault.maxWithdraw(address(this)))` and only revert if the total pull is still insufficient.

### Proof of Concept
Foundry fork test outline (deployment: `IdleCDOEpochVariant` + `IdleCreditVault` + `ProgrammableBorrower` pointed at a shared ERC4626 vault, e.g. a Yearn/Morpho-style vault with external users):

```solidity
// test/foundry/ProgrammableBorrowerLiquidityTOCTOU.t.sol
function testStopEpochFrozenByVaultLiquidityDrain() external {
  // 1. Lender deposits AA tranche; manager starts epoch 0.
  idleCDO.depositAA(amount);
  cdoEpoch.startEpoch();              // onStartEpoch deposits idle cash into vault

  // 2. Borrower draws normally; epoch runs; user requests withdraw.
  vm.prank(borrower); pb.borrow(drawAmount);
  cdoEpoch.requestWithdraw(trancheBal, AAtranche); // creates pendingWithdraws

  // 3. Attacker (unprivileged vault user) drains vault liquidity:
  //    borrows/withdraws vault maxWithdraw() so convertToAssets still
  //    reports full coverage but redeemable liquidity ~0.
  vm.prank(attacker);
  vault.borrow(vault.maxWithdraw(address(pb))); // or withdraw for pure vaults

  // sanity: check passes nominally
  assertGe(vault.convertToAssets(vault.balanceOf(address(pb))), shortfall);
  assertLt(vault.maxWithdraw(address(pb)), shortfall);

  // 4. Honest manager calls stopEpoch -> withdraw reverts ->
  //    StopEpochVaultLiquidityUnavailable; epoch cannot stop.
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
  cdoEpoch.stopEpoch(0, expectedInterest);

  // 5. Claim is frozen: pending withdraw receipt cannot be funded.
  vm.expectRevert();
  cdoEpoch.claimWithdrawRequest();

  // 6. Attacker can repeat the drain each time liquidity returns,
  //    extending the freeze indefinitely; lender funds remain locked.
}
```

Expected result: `stopEpoch` reverts despite `convertToAssets` showing full coverage, demonstrating that the guard validates share valuation while the action depends on live redeemable liquidity controlled by a third party — freezing `pendingWithdraws` and pool NAV for the duration of the drain.
