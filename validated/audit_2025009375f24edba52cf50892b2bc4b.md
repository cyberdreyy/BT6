### Title
`claimInstantWithdrawRequest` pays the aggregate receipt balance without checking the unfunded `pendingInstantWithdraws` bucket, letting partially-funded instant claimants drain other users' funded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The GOAUTH bug class is a scope-confusion failure: credentials that should be segmented by domain were served to any requester. The analog in `IdleCreditVault` is that instant-withdraw claims are not segmented by funding status. `instantWithdrawsRequests[user]` is an aggregate across funded and unfunded receipts, while `pendingInstantWithdraws` is the only tracker of the still-unfunded "domain". `claimInstantWithdrawRequest` pays the full aggregate via `_transferFundedClaim` without ever reading `pendingInstantWithdraws`, so an underfunded instant receipt can spend underlyings reserved for other claimants.

### Finding Description
- `requestInstantWithdraw` increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, and `pendingInstantWithdraws` [1](#0-0) .
- Funding arrives later via `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` [2](#0-1) .
- The code itself documents that instant receipts can be only *partially* funded: `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as the prefunded part of the current epoch's instant queue [3](#0-2) , and `defaultPendingClaimBasis`/`defaultInstantWithdrawsFinalized` acknowledge a non-zero unfunded instant bucket surviving epoch processing [4](#0-3) .
- Yet `claimInstantWithdrawRequest` pays `instantWithdrawsRequests[_user]` in full through `_transferFundedClaim`, with no check that the requester's share was actually collected — the funded vs. unfunded domains are collapsed into one aggregate [5](#0-4) .
- `_transferFundedClaim` only protects `defaultRecoveryReserve`, not the funded-withdraw bucket of other users [6](#0-5) .

### Impact Explanation
When `startEpoch` moves CDO cash covering only part of the instant queue (the scenario described at lines 637-640), the strategy holds underlying belonging proportionally to all queued instant claimants, but `pendingInstantWithdraws` marks the remainder unfunded. An attacker whose instant request is only partially funded calls `claimInstantWithdrawRequest` first and receives their *entire* aggregate basis. Later honest claimants' instant receipts revert on `safeTransfer` for lack of balance — direct theft of funded claim underlyings proportional to the shortfall. This is a first-come, first-served race seeded by an ordinary unprivileged instant withdraw request in a running epoch.

### Likelihood Explanation
Requires the instant queue to be partially funded (borrower liquidity shortfall at epoch start or default-window conditions), then the attacker simply claims before honest users. No privileged cooperation needed; any KYC-passing lender can request an instant withdraw. Uncertainty: if the CDO atomically guarantees full funding at request time in all paths other than the partial-prefund path documented in the contract, the window narrows to that documented scenario, which the code explicitly treats as reachable.

### Recommendation
Segment instant claims by funding domain: track a per-user funded allowance (e.g., `fundedInstantWithdraws[user]`) credited in `collectInstantWithdrawFunds` pro-rata or FIFO by epoch, and cap `claimInstantWithdrawRequest` payouts to the funded allowance rather than the aggregate `instantWithdrawsRequests`. Alternatively, pay unfunded instant receipts exclusively through `lossRecoveryPriceByEpoch`/default recovery.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness):
1. Users A (attacker) and B each deposit AA and call `requestInstantWithdraw`; both get receipts, `pendingInstantWithdraws` = A + B.
2. Manager `startEpoch` with borrower liquidity covering only B's request (partial prefund per `_defaultPrefundedInstantReserve` semantics): `collectInstantWithdrawFunds(B)` reduces `pendingInstantWithdraws` to A's amount.
3. Additional funded underlyings exist in the strategy (e.g., other funded withdraw claims).
4. Attacker calls `cdoEpoch.claimInstantWithdrawRequest()` → receives full `instantWithdrawsRequests[A]` despite zero funding for A.
5. B's subsequent claim reverts on `safeTransfer`; assert B's recovered amount < basis.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
