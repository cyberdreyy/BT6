### Title
Division-Before-Multiplication in Jovian DA-Footprint Gas Calculation Causes Systematic Under-Charging of L1 Data-Availability Gas - (File: crates/common/l1-fees/src/params.rs)

### Summary
`L1FeeParams::jovian_da_footprint` computes the Jovian DA-footprint gas by dividing the FastLZ-scaled estimated size by `1_000_000` *before* multiplying by the DA-footprint gas scalar, instead of multiplying first and dividing last. This is the same division-before-multiplication rounding-error class flagged in the external report's `floorTick` example, and it truncates precision on every transaction whose estimated compressed size is not an exact multiple of `1e6`.

### Finding Description
`tx_estimated_size_fjord` returns the FastLZ-estimated compressed size **scaled by `1e6`** (i.e. `max(minTransactionSize, intercept + fastlzCoef*fastlzSize)`), as documented in its own doc-comment: "Calculate the estimated compressed transaction size in bytes, scaled by 1e6." [1](#0-0) 

The correct (multiply-before-divide) pattern is used elsewhere in the same file, e.g. `data_gas_fjord`:
```
estimated_size.saturating_mul(NON_ZERO_BYTE_COST).wrapping_div(1_000_000)
``` [2](#0-1) 

and in `L1FeeParams::data_gas` for the Fjord L1-cost path, which also multiplies first then divides: [3](#0-2) 

However, `jovian_da_footprint` reverses this order — it divides the scaled size by `1_000_000` **first**, and only then multiplies by the scalar: [4](#0-3) 

Because `tx_estimated_size_fjord` is itself `max(minTransactionSize, intercept + fastlzCoef*fastlzSize)`, its raw value (scaled by `1e6`) is very frequently not an exact multiple of `1_000_000` (the `fastlzCoef*fastlzSize - intercept` term depends on arbitrary calldata compression sizes). Performing `wrapping_div(1_000_000)` first floors away the fractional-byte remainder permanently; multiplying by `scalar` afterward cannot recover that lost precision. If the multiplication were done first (`estimated_size.saturating_mul(scalar).wrapping_div(1_000_000)`), the rounding error would be bounded to less than 1 unit of gas regardless of `scalar`; with the current order, the rounding error is amplified by the scalar value — for any `scalar > 1`, up to `(scalar - 1)` gas units of underestimation per transaction.

### Impact Explanation
`jovian_da_footprint` feeds directly into the Jovian upgrade's DA-footprint gas accounting inside the block executor (confirmed as consumed via `crates/common/evm/src/executor/block_executor.rs`, `crates/execution/flashblocks/src/state_builder.rs`, and `crates/common/evm2/src/executor.rs`), which is the mechanism by which Base charges/accounts for L1 data-availability resource consumption per transaction once Jovian is active. Systematic under-computation of this footprint means:
- Every transaction is charged less DA-footprint gas than the correct formula intends, scaled by the configured `da_footprint_gas_scalar`.
- Because this bias is deterministic and reproducible from public inputs (calldata + scalar), it is exploitable by any unprivileged transaction sender to consistently under-pay for DA resource usage, which is a resource/fee-accounting correctness issue affecting the protocol's DA-gas metering model.
- This does not directly enable theft of funds or state-root divergence by itself (the biased value is deterministic and would be computed identically by any correctly-following-the-code node), so it does not cause a chain split as long as all nodes run the same (buggy) code. The primary impact is a fee-accounting/gas-metering integrity defect: the "DA-footprint gas" no longer reflects actual DA cost, which under-prices L1 data availability and could be leveraged to submit more DA-heavy transactions per unit of gas paid than the protocol design intends.

### Likelihood Explanation
The bug is triggered on every transaction once Jovian is enabled and a `da_footprint_gas_scalar` is configured, since `tx_estimated_size_fjord`'s output is virtually never an exact multiple of `1_000_000` in practice. No special conditions or privileges are required — it is reachable by any transaction included via the normal execution path.

### Recommendation
Reorder the arithmetic in `jovian_da_footprint` to multiply before dividing, matching the pattern already used in `data_gas` and `data_gas_fjord`:
```rust
pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
    let Some(scalar) = self.da_footprint_gas_scalar else {
        return 0;
    };
    U256::from(tx_estimated_size_fjord(input))
        .saturating_mul(scalar)
        .wrapping_div(U256::from(1_000_000u64))
        .saturating_to::<u64>()
}
``` [4](#0-3) 

### Proof of Concept
Given `tx_estimated_size_fjord(input) = 1_999_999` (scaled size, i.e. 1.999999 bytes) and `scalar = 3`:
- Current (buggy) order: `1_999_999 / 1_000_000 = 1` (floor), then `1 * 3 = 3`.
- Correct order: `1_999_999 * 3 = 5_999_997`, then `/ 1_000_000 = 5` (floor).

The buggy path returns `3` instead of the intended `5` — a 40% undercharge that grows proportionally with `scalar` for any input whose scaled size has a fractional remainder against `1e6`, confirmed reachable for arbitrary attacker-supplied calldata via `tx_estimated_size_fjord`. [5](#0-4)
