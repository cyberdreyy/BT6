### Title
APR0 withdraw bucket permanently bricks `stopEpoch` when APR is raised above 0 - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` contains a circular dependency analogous to CVE-2018-6346's circular HTTP/2 priority graph: clearing `apr0TotalPrincipal` requires a successful `stopEpoch`, but `stopEpoch` reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` in the same state. Once a vault has open APR=0 withdraw requests and the APR is raised, the epoch state machine can never advance and all lender funds are frozen.

### Finding Description
In `IdleCreditVault.requestWithdraw`, withdraw requests made while `unscaledApr == 0` are routed into the APR0 bucket and increase the global `apr0TotalPrincipal` counter [1](#0-0) . At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which first checks `if (_principal == 0) return`, then hard-reverts `NotAllowed` when `unscaledApr != 0` while `apr0TotalPrincipal` is still non-zero [2](#0-1) . The only line that ever resets `apr0TotalPrincipal` is at the end of the same function — reachable only if the revert is not hit [3](#0-2) .

No other path clears the counter: `_settleApr0` only migrates the user's `principal` into `settledPrincipal` without touching `apr0TotalPrincipal` [4](#0-3) , and `_clearWithdrawClaimForEpoch` decrements it exclusively on the post-default `_isClearingApr0` path [5](#0-4) . Meanwhile, `_claimFundedWithdrawRequest` gates every normal claim on `epochNumber > lastWithdrawRequest[user]`, and `epochNumber` only increments through `deposit`/epoch progression — which requires `stopEpoch` to succeed [6](#0-5) .

Cycle: `apr0TotalPrincipal` reset → needs `stopEpoch` → `stopEpoch` → needs `prepareStopEpochWithApr0` → reverts while `apr0TotalPrincipal != 0 && unscaledApr != 0`.

### Impact Explanation
While APR is non-zero with open APR0 principal, every `stopEpoch` reverts. Withdraw receipt holders cannot claim (epoch never rolls), active depositors cannot exit a running epoch, and loss crystallization is blocked. If the borrower cannot or does not restore APR to 0, this is permanent freezing of the entire vault TVL; otherwise it is temporary freezing quantified as all queued withdraw principal plus active NAV for the duration.

### Likelihood Explanation
Requires a vault operating at `unscaledApr == 0` (an explicitly supported mode — the APR0 branch exists precisely for it) with at least one pending APR0 withdraw request, followed by an APR increase by the honest borrower/manager — a normal operational action the vault permits, since `requestWithdraw` itself dynamically routes on the current APR [7](#0-6) . An unprivileged requester can deliberately keep a small APR0 receipt open to maximize the freeze window. I could not fully verify whether the APR setter is callable mid-epoch or blocked while `apr0TotalPrincipal != 0`; if it is blocked, the deadlock window narrows accordingly.

### Recommendation
In `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, settle the open APR0 bucket at zero incremental rate (store `apr0RateByEpoch[epochNumber] = 0` or pay the pending principal at par) and zero `apr0TotalPrincipal` instead of reverting, so a single honest APR change cannot deadlock the epoch machine.

### Proof of Concept
```solidity
// Foundry fork test against an APR0-configured IdleCreditVault deployment
function testApr0CircularLock() public {
    // buffer phase, unscaledApr == 0
    _depositWithUser(alice, 100e6);
    vm.prank(manager); cdo.startEpoch();

    // alice opens an APR0 withdraw receipt -> apr0TotalPrincipal > 0
    _requestWithdrawWithUser(alice, trancheBal);

    // honest borrower raises APR mid-epoch
    vm.prank(borrower); strategy.setApr(500); // unscaledApr != 0

    // every subsequent stopEpoch reverts: epoch machine deadlocked
    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager); cdo.stopEpoch(0);
    // alice can never claim: epochNumber <= lastWithdrawRequest[alice]
    vm.expectRevert(NotAllowed.selector);
    cdo.claimWithdrawRequest(alice);
}
```

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }
