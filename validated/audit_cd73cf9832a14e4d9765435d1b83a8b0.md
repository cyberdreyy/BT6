### Title
Malicious/uncooperative operator can permanently DoS distribution of staker's unlocked stake by setting a beneficiary that rejects direct coin deposits - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`distribute_internal` in `staking_contract.move` processes **all** shareholders of a `StakingContract`'s `distribution_pool` (staker, operator/beneficiary, and any prior operators with pending distributions) in a single atomic loop, paying each one via `aptos_account::deposit_coins`. `aptos_account::deposit_coins` aborts if the recipient has not registered a `CoinStore<AptosCoin>` and has explicitly disabled direct coin transfers via `DirectTransferConfig`. Because the loop distributes to every shareholder in one transaction, a single "poisoned" recipient — most easily the operator's own `beneficiary` (which the operator fully controls via `set_beneficiary_for_operator`) — can cause the whole `distribute` call to revert every time, blocking the staker's own principal/rewards withdrawal indefinitely.

### Finding Description
`distribute_internal` withdraws all inactive/pending-inactive stake from the underlying stake pool and then pays out every shareholder in the `distribution_pool` in one atomic loop: [1](#0-0) 

If the recipient being paid is the operator, the code redirects the payment to `beneficiary_for_operator(operator)`: [2](#0-1) 

The operator fully controls this beneficiary address via the permissionless `set_beneficiary_for_operator` entry function, which requires no validation that the address can actually receive funds: [3](#0-2) 

`aptos_account::deposit_coins` — used for every payout in the loop — aborts (`EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`) if the target address is not registered for the coin type and has opted out of direct coin transfers: [4](#0-3) 

Because Move transactions are atomic, if the deposit to the beneficiary aborts partway through the shareholder loop, the *entire* transaction — including the `stake::withdraw_with_cap` extraction and the `redeem_shares` calls already performed for other shareholders (e.g., the staker) — is rolled back. `distribute` is a permissionless entry function so anyone (typically the staker) can attempt it, but every attempt will fail identically as long as the poisoned beneficiary remains in the pool, since `distribute_internal` re-reads `beneficiary_for_operator(operator)` fresh on each call: [5](#0-4) 

`distribute_internal` is also invoked internally from `request_commission`, `update_commision`, and `switch_operator`, so those flows are blocked too as long as unpaid distribution shares for the poisoned beneficiary exist in the same pool: [6](#0-5) [7](#0-6) 

This means the staker's unrelated, independently-owed principal/rewards share sitting in the same `distribution_pool` becomes non-withdrawable as long as the operator's beneficiary entry cannot be paid — a design flaw where unrelated shareholders' claim rights are coupled into one atomic payout instead of being isolated per-recipient (e.g., via a pull-based claim pattern).

### Impact Explanation
This is a griefing/denial-of-funds vector against the staker (and any other legitimate shareholder in the pool, e.g. a previous operator with pending distribution after `switch_operator`). The staker's already-unlocked stake and accumulated rewards can be rendered permanently non-withdrawable through the ordinary `distribute`/`request_commission`/`switch_operator` entry points as long as the operator (who is not necessarily trusted with custody, only with running the validator) keeps a non-receiving beneficiary configured. Because Move execution is atomic and the loop is all-or-nothing, there is no partial distribution to unaffected shareholders and no permissionless way to skip or evict the poisoned recipient from `distribution_pool`. This matches the "permanent lock or non-recoverable loss of claim rights" impact class for stake/commission/beneficiary flows.

### Likelihood Explanation
Low-to-medium. It requires the operator (a role already delegated some trust for running the validator, but not custody of the staker's principal) to deliberately or negligently set (via `set_beneficiary_for_operator`) a beneficiary address that has called `set_allow_direct_coin_transfers(false)` and never registered a `CoinStore<AptosCoin>`. This is achievable unilaterally by the operator with no cooperation needed from the staker, and the operator does not need any special privilege beyond the operator role it already holds in a normal staking_contract relationship.

### Recommendation
- Make `distribute_internal` resilient to a single failing payout: catch/skip a recipient whose deposit would abort (e.g., check `coin::is_account_registered` and `aptos_account::can_receive_direct_coin_transfers` before attempting `deposit_coins`, and if the recipient cannot receive funds, retain their shares in the pool / route to a claimable escrow instead of aborting the whole loop) so that other shareholders (the staker in particular) can still be paid.
- Alternatively, switch to a pull-based accounting model where each shareholder withdraws their own share in a separate transaction, so one recipient's payout failure cannot block others.
- Consider validating that `new_beneficiary` in `set_beneficiary_for_operator` is capable of receiving `AptosCoin` (registered or opted-in) before accepting the update, or at minimum documenting/enforcing that operators cannot brick distribution for unrelated stakers.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `create_staking_contract`, deposits stake; operator joins the validator set and accrues rewards.
2. `operator` (address A) sets an address `B` as beneficiary via `staking_contract::set_beneficiary_for_operator(operator, B)`.
3. From `B`, call `aptos_account::set_allow_direct_coin_transfers(B_signer, false)` and ensure `B` never registers `CoinStore<AptosCoin>` (a brand-new/otherwise-unused address).
4. Operator requests commission (`request_commission`), which internally records `B`'s pending share in `distribution_pool` via `update_distribution_pool`.
5. Stake pool's lockup ends; funds move to `inactive`.
6. Staker (or anyone) calls `staking_contract::distribute(staker, operator)`. The internal loop reaches `B`'s share, calls `aptos_account::deposit_coins(B, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` since `B` is unregistered and has opted out.
7. The entire transaction reverts — the staker's own already-unlocked principal (also a shareholder being processed in the same loop) is not paid out. Every subsequent call to `distribute`, `request_commission`, or `switch_operator` for this `(staker, operator)` pair fails the same way as long as `B` remains beneficiary with a nonzero pending share, since `beneficiary_for_operator` is re-resolved each call.

Note: I was unable to fully verify from the indexed code whether `pool_u64`'s `shareholders()`/`redeem_shares` provide any built-in mechanism to skip or forcibly evict a shareholder mid-loop (the pool_u64 source itself wasn't fully inspected); if such a skip mechanism exists it could mitigate this specific path, so this finding should be validated against the full `pool_u64.move` / `pool_u64_unbound.move` implementation in a live session before treating it as fully confirmed.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
