### Title
Attacker-driven ERC4626 liquidity lock converts the retryable `StopEpochVaultLiquidityUnavailable` revert into a permanent epoch halt, freezing all pool funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The Cosmos packet-forward-middleware bug is a chain-halt caused by an error path that can neither succeed nor finalize. The direct analog in idle-tranches is `ProgrammableBorrower.onStopEpoch`: when IdleCDO needs to recall cash, the hook tries `vault.withdraw(shortfall)` and **reverts** `StopEpochVaultLiquidityUnavailable` whenever the vault has valuable shares but insufficient *liquid* assets. Because that revert bubbles out of `stopEpoch`, no default is ever declared, the epoch stays `isEpochRunning`, deposits stay paused, withdraw requests stay disabled, and neither `setIsProgrammableBorrower` nor `setEpochParams`/`getInstantWithdrawFunds` can be used as an escape hatch. An unprivileged user of the programmable borrower's ERC4626 vault can hold the vault's liquidity at zero (e.g., by keeping the underlying lending markets fully borrowed), so the "retryable" failure never clears — a halt identical in effect to the PFM chain-halt.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, programmable mode routes through the borrower hook before pulling funds:

- `contracts/IdleCDOEpochVariant.sol` lines 395-404: `if (!IProgrammableBorrower(_borrower()).onStopEpoch(...))` — `false` → `_handleBorrowerDefault`, but a **revert propagates** and aborts the entire stop.
- `contracts/strategies/idle/ProgrammableBorrower.sol` lines 239-253: when `onHand < _amountRequired`, the hook checks `shortfall > _currentVaultAssets()` (share *value*) and only then attempts `vault.withdraw(shortfall)`; on revert it executes `revert StopEpochVaultLiquidityUnavailable()`.

The check compares the cash shortfall to `convertToAssets(vaultShares)` — the economic value of the position — not to the vault's `maxWithdraw`/liquidity. An ERC4626 vault can hold shares worth far more than its instantly withdrawable liquidity (lending vaults lend the assets out). In that state:

1. `shortfall <= _currentVaultAssets()` → the early `return true` (default) path is skipped.
2. `vault.withdraw(shortfall)` reverts on insufficient liquidity.
3. `StopEpochVaultLiquidityUnavailable` bubbles through `stopEpoch`, reverting the whole transaction.

Crucially, every avenue to resolve the state is closed while this persists:

- `stopEpoch`/`stopEpochWithDuration` always hit the same revert (`IdleCDOEpochVariant.sol:398` hook runs before the `try/catch` around `getFundsFromBorrower`, so the default fallback is unreachable).
- `getInstantWithdrawFunds` reverts unconditionally when `isProgrammableBorrower` (`IdleCDOEpochVariant.sol:561`).
- `setIsProgrammableBorrower(false)` reverts while `isEpochRunning` (`IdleCDOEpochVariant.sol:178`), and `isEpochRunning` can only be cleared by `stopEpoch` or `_handleBorrowerDefault` — both unreachable.
- `setEpochParams` reverts while `isEpochRunning` (`IdleCDOEpochVariant.sol:122`), and `startEpoch` is gated on the epoch not running.
- LP deposits are paused from `startEpoch`, and `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are false, so lenders cannot exit at all.

An unprivileged attacker who is a user of the vault's underlying markets keeps liquidity drained (e.g., maximum borrows, re-borrowing any repayments each block — standard for Morpho-style vaults where borrowing is permissionless). `convertToAssets` still reports full share value, so the stop reverts deterministically on every attempt while never qualifying for the default path. This mirrors the PFM bug exactly: an error branch (`catch { revert }` instead of default-forwarding) makes forward progress impossible.

### Impact Explanation
Temporary-to-permanent freezing of **all** pool funds: every LP's tranche position, all pending withdraw receipts, and all queued/prefunded deposits are locked for as long as the attacker holds vault liquidity below `shortfall`. Unlike a normal borrower default — which is recovered through `finalizeDefault`/`DefaultDistributor` — no default can even be declared, so no recovery process can start. The attacker only pays borrow interest on the drained liquidity; for a pool whose TVL is orders of magnitude larger than the borrow cost, the griefing ratio is extreme. If the illiquidity is structural (e.g., a market the vault allocated to becomes permanently illiquid or capped), the freeze is permanent: the pool can never stop, close (`_interest == 1` also routes through `onStopEpoch`), or default.

### Likelihood Explanation
High whenever the programmable borrower is configured against an ERC4626 lending vault whose underlying markets allow permissionless borrowing — the pool's epoch stop is then held hostage to a third party's liquidity at every epoch boundary. The codebase's own tests confirm the mechanism (`testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`, `ProgrammableBorrowerCreditVault.t.sol:372-399`) but treat it as benign because they assume the failure is transient; they do not test an adversary keeping liquidity at zero across repeated stops. No manager/owner action can force resolution while `isEpochRunning` remains true.

### Recommendation
Bound the retryable path. In `onStopEpoch`, compare `shortfall` against `vault.maxWithdraw(address(this))` (actual withdrawable liquidity) instead of `_currentVaultAssets()`, so economically uncovered stops take the `return true` → `transferFrom` failure → default path. Additionally, add a deterministic escape hatch in `IdleCDOEpochVariant`: e.g., after `N` consecutive `StopEpochVaultLiquidityUnavailable` reverts (or a configured grace period past `epochEndDate`), allow the manager to invoke `_handleBorrowerDefault` directly, or allow `setIsProgrammableBorrower(false)` while running so the next stop uses the direct `transferFrom`/default path. Treating vault illiquidity as a borrower default after a timeout converts an unbounded halt into the already-designed recovery flow.

### Proof of Concept
Foundry fork-style PoC (modeled on `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// Pool in programmable + minted-interest mode, epoch running, pendingWithdraws > 0
// so onStopEpoch must recall cash from the vault.
function testStopEpochPermanentlyHaltedByVaultIlliquidity() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0);

    uint256 pendingWithdraws = strategy.pendingWithdraws();
    assertGt(pendingWithdraws, 1, "stop needs liquidity recall");

    // Attacker (unprivileged user of the vault's underlying markets):
    // drains/borrows all liquid assets. Shares retain value:
    // convertToAssets(shares) >= shortfall  but  maxWithdraw / liquidity == 0.
    vault.borrowAllLiquidity(); // liquidity() == 0, shares still valuable
    assertGt(vault.convertToAssets(vault.balanceOf(address(programmableBorrower))), pendingWithdraws);
    assertEq(vault.maxWithdraw(address(programmableBorrower)), 0);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Every stop attempt reverts; never defaults; epoch never ends.
    for (uint256 i; i < 5; ++i) {
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);
    }

    // Attacker keeps liquidity at zero (re-borrows repayments) -> repeat forever.
    // No escape hatch exists:
    vm.expectRevert(NotAllowed.selector);
    vm.prank(owner);
    cdoEpoch.setIsProgrammableBorrower(false);      // blocked: isEpochRunning

    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();              // blocked: isProgrammableBorrower

    // Close-pool path is equally bricked:
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);

    // Final state: funds frozen, no default, no recovery path.
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pendingWithdraws);
    // LP exit impossible: paused() && !allowAAWithdrawRequest && !allowBBWithdrawRequest
}
```

Uncertainty note: the exact production vault wired to `ProgrammableBorrower` was not verifiable within index limits, so the PoC assumes a lending-style ERC4626 where liquidity can diverge from share value — the pattern the repo's own mock (`MockStopEpochLiquidityVault`) already encodes.
