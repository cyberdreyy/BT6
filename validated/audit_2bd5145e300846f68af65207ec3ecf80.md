Based on tracing the contract logic:

**The equality claim in the question is false — the guard does hold.**

`is-novel-aggregate-public-key` is defined as:
```
(is-eq (default-to reward-cycle (map-get? used-aggregate-public-keys key)) reward-cycle)
```

For a key that was already approved in cycle N, `used-aggregate-public-keys` holds `key -> N` (set at line 171 via `map-set used-aggregate-public-keys key reward-cycle` on every successful vote). `map-set` (not `map-insert`) always overwrites, but the value stored is always the *actual* reward-cycle in which the vote occurred, not a stale/default placeholder. [1](#0-0) 

When the same signer (or any signer) later calls `vote-for-aggregate-public-key` with the identical key at reward-cycle N+2, `map-get? used-aggregate-public-keys key` returns `Some(N)` — this is *not* `None`, so `default-to` does **not** fall back to the queried `reward-cycle` argument; it uses the stored value `N`. The comparison becomes `is-eq N (N+2)` → `false`. Consequently `is-novel-aggregate-public-key` returns `false`, and the `asserts!` at line 159 fails with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY`, rejecting the vote. [2](#0-1) 

The `default-to reward-cycle ...` fallback only ever activates on the `None` branch — i.e., only the *first* time a key is ever seen — which correctly yields `true` (novel) for a genuinely unused key at any cycle. Once a key transitions to `Some(...)`, the fallback path is permanently bypassed for that key, and the stored cycle is compared exactly against the queried cycle. `update-last-round` (lines 117-122) only manages the `rounds` map (tracking voting rounds within a single reward cycle) and has no interaction with, or ability to reset, `used-aggregate-public-keys`. There is no code path — round restart, multi-round voting, or otherwise — that clears or re-defaults an entry in `used-aggregate-public-keys` once set.

The only case where `is-novel-aggregate-public-key` returns `true` for an already-`Some`-mapped key is when the *queried* `reward-cycle` argument equals the *stored* cycle — which is exactly the case of repeated voting for the same key **within the same cycle** (allowed and intended, since multiple signers/rounds must vote for the same candidate key to reach threshold before `aggregate-public-keys` is populated and the `is-none` guard at line 155 kicks in).

No vulnerability found for this question.
