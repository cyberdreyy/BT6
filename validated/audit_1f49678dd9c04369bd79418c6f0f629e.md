### Title
Claimed instant withdrawals remain in epoch accounting and can be paid again from default recovery - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests` balance and leaves `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` populated after the user has already been paid. If the same epoch later defaults while another instant withdrawal remains unfunded, finalization treats the stale epoch balance as an outstanding claim, reserves a phantom prefunded amount, and lets the original claimant draw recovery funds again through `_claimDefaultedInstantWithdrawRequest`.

### Finding Description
During an epoch with instant withdrawals enabled, a user’s instant request is recorded in `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch[user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, and `pendingInstantWithdraws`. [1](#0-0) 

After the manager funds the queue, `claimInstantWithdrawRequest` burns the user’s receipt, clears only `instantWithdrawsRequests[user]`, and transfers the funded amount; it never deletes the user’s per-epoch basis or reduces `instantWithdrawClaimsByEpoch`. [2](#0-1) 

If another user later creates an unfunded instant request in the same epoch and the borrower defaults, `defaultPendingClaimBasis` adds the entire current-epoch `instantWithdrawClaimsByEpoch`, including the already-claimed stale receipt, whenever `pendingInstantWithdraws` is nonzero. [3](#0-2) 

`finalizeDefaultRecovery` then calculates `prefundedReserve` as `instantWithdrawClaimsByEpoch - pendingInstantWithdraws`, so the already-paid withdrawal is incorrectly considered recovery cash already held by the strategy. [4](#0-3) 

After finalization, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch amount, subtracts it from aggregate and epoch accounting, burns the corresponding receipt amount, and pays `claimBasis * defaultRecoveryPrice` from `defaultRecoveryReserve`. [5](#0-4) 

This is the same resource-lifecycle bug class as the kernel report: a later state transition treats an object as still owned because the earlier path overwrote or cleared only the active reference while leaving the backing claim reachable.

### Impact Explanation
An ordinary tranche-token holder can receive the same instant withdrawal twice: once at par after `getInstantWithdrawFunds`, and again at the default recovery price after finalization.

For example, if attacker A requests and claims 100 underlying, victim B later leaves 50 underlying unfunded, and default recovery is priced at 50%, A can claim another 50 underlying from recovery despite having no outstanding receipt. The stale 100 also inflates both the pending claim basis and the calculated prefunded reserve, distorting `defaultRecoveryPrice` and diluting legitimate active holders and pending claimants. [3](#0-2) 

The direct loss is bounded by the previously claimed instant-withdrawal amount times the finalized recovery price, and the accounting distortion can further shift recovery value away from legitimate claimants.

### Likelihood Explanation
The sequence requires an APR decrease that enables instant withdrawals, successful funding and claiming of one request, a second unfunded request in the same epoch, and a subsequent borrower default before epoch settlement. [6](#0-5) 

All roles can remain honest: the attacker only uses ordinary tranche holdings and calls `requestWithdraw` and `claimInstantWithdrawRequest`, while the manager funds the first instant queue and default/finalization proceed through the normal borrower-default path.

Existing checks do not prevent the replay because the normal claim path only verifies the aggregate balance, and the defaulted-claim path trusts the stale per-epoch mapping after `defaultInstantWithdrawsFinalized` becomes true. [2](#0-1) 

### Recommendation
When an instant withdrawal is claimed normally, clear both `instantWithdrawsRequestsByEpoch[user][requestEpoch]` and `instantWithdrawClaimsByEpoch[requestEpoch]`, not only the aggregate `instantWithdrawsRequests`.

Because a user may hold receipts from multiple epochs, store or derive the funded epochs being claimed, or make instant requests non-composable across epochs and explicitly delete the active epoch receipt on payout.

Additionally, derive `_defaultPrefundedInstantReserve` only from uncleared current-epoch claims and add an invariant test that a fully claimed instant withdrawal contributes zero basis and zero reserve during later default finalization.

### Proof of Concept
A reproducible Foundry test should perform the following transactions on a forkable credit-vault fixture:

1. Configure a running epoch with instant withdrawals enabled and `lastEpochApr > unscaledApr + instantWithdrawAprDelta`. [7](#0-6) 
2. Attacker calls `IdleCDOEpochVariant.requestWithdraw(attackerAmount, AATranche)`, creating an instant receipt in the current strategy epoch.
3. Honest manager calls `getInstantWithdrawFunds`, transferring the pending amount to `IdleCreditVault`, reducing `pendingInstantWithdraws` to zero, and enabling claims. [8](#0-7) 
4. Attacker calls `claimInstantWithdrawRequest`; assert that underlying is received while `instantWithdrawsRequestsByEpoch[attacker][epoch]` remains nonzero.
5. Victim creates another instant request in the same epoch so `pendingInstantWithdraws != 0`.
6. Trigger borrower default through the existing failed borrower-funding path, then call `finalizeDefault(recoveredAmount, recoverySource)` through the honest privileged role.
7. Assert `defaultPendingClaimBasis()` includes both the victim request and the attacker’s already-claimed stale request.
8. Attacker calls `claimInstantWithdrawRequest` again.
9. Assert the attacker receives `staleAmount * defaultRecoveryPrice / 1e18` and `defaultRecoveryReserve` decreases by that amount.

The decisive assertions are:

```solidity
uint256 epoch = creditVault.epochNumber();

// First claim succeeds.
cdo.claimInstantWithdrawRequest();
assertEq(creditVault.instantWithdrawsRequests(attacker), 0);
assertGt(creditVault.instantWithdrawsRequestsByEpoch(attacker, epoch), 0);

// After default finalization, the stale epoch receipt is claimed again.
uint256 balanceBefore = underlying.balanceOf(attacker);
cdo.claimInstantWithdrawRequest();
assertGt(underlying.balanceOf(attacker), balanceBefore);
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

```text
  /// @notice Get funds from borrower to fullfill instant withdraw requests
  /// Manager should call this method after instantWithdrawDeadline (when epoch is running)
  /// @dev Instant withdrawals are not supported when a programmable borrower is configured.
  function getInstantWithdrawFunds() external {
    _checkOnlyOwnerOrManager();
    // Check that programmable mode is disabled, the epoch is running and the deadline passed.
    _checkNotAllowed(isProgrammableBorrower || !isEpochRunning || block.timestamp < instantWithdrawDeadline);

    IdleCreditVault _strategy = IdleCreditVault(strategy);
    uint256 _instantWithdraws = _pendingInstant();
    // transfer funds for instant withdraw to this contract
    try this.getFundsFromBorrower(_instantWithdraws) {
      // transfer funds to IdleCreditVault and decrease pendingInstantWithdraws
      _strategy.collectInstantWithdrawFunds(_instantWithdraws);
      // allow instant withdraws
      allowInstantWithdraw = true;
    } catch {
      _handleBorrowerDefault(_instantWithdraws);
    }
```
