### Title
Predictable `keyPath` in `store.Open` enables symlink-based arbitrary file write via `os.WriteFile` - ([File: commands/helpers/internal/store/store.go])

### Summary
`store.Open(dir)` derives `keyPath` deterministically as `sha256(filepath.Join(dir, "masking.db"))`, with no randomness or attacker-unknown input. If an unprivileged actor can write to `dir` before the store is initialized (e.g. a shared cache/builds/tmp directory the runner process also has write access to), they can pre-compute the exact `keyPath` filename and plant a symlink there, causing `os.WriteFile(keyPath, generateKey(), 0o644)` to follow the symlink and overwrite an attacker-chosen target file with 32 random bytes under the runner process's privileges.

### Finding Description
In `commands/helpers/internal/store/store.go`, `Open` computes: [1](#0-0) 
`pathname` and `keyPath` are fully deterministic functions of `dir` — a `sha256` hash of a known string is not a secret; any actor who knows `dir` (a directory path, not a secret) can compute `keyPath` offline before the runner ever touches the directory.

The vulnerable sequence is:
1. `os.Stat(pathname)` fails (masking.db doesn't exist yet — true on first run in a fresh directory).
2. The code calls `os.WriteFile(keyPath, generateKey(), 0o644)`. `os.WriteFile` opens the target with `O_CREATE|O_WRONLY|O_TRUNC` and does **not** use `O_NOFOLLOW`/`O_EXCL`; if `keyPath` is a symlink, the write follows it and truncates/overwrites the symlink target.

If an attacker has write access to `dir` (or any ancestor allowing symlink creation) prior to this call, they can create `keyPath` as a symlink pointing at any file writable by the runner process (e.g. another job's artifacts, a config file, a script later executed with elevated trust, etc.), and the runner will overwrite that target with 32 random bytes.

No existing check mitigates this: there is no `O_EXCL`/`lstat` check before the `WriteFile`, no verification that `keyPath` is a regular file, and no restriction that `dir` must be private to the runner. The vulnerability is a **classic TOCTOU/symlink-following arbitrary-write bug**, not just "predictability" of a secret — the security-relevant fact is that the filename is guessable and the write follows symlinks blindly.

### Impact Explanation
An unprivileged attacker with write access to the store's `dir` before first initialization can cause the runner to overwrite an arbitrary file (that the runner process can write) with 32 random bytes, via symlink planting at the predictable `keyPath`. This is a targeted-corruption / denial-of-service primitive (destroying a file's contents), scoped to whatever the runner process has write permission over. It does not leak the derived AEAD key itself (since `key1` from `masking.db` is independently random and XORed with `key2`), so this is a file-integrity/availability bug rather than a key-disclosure bug.

### Likelihood Explanation
Exploitability requires: (1) the attacker can write to the `dir` argument passed to `Open` before `masking.db` exists there, and (2) the runner process has write access to some file the attacker wants to target via a planted symlink. This is only reachable on setups where `dir` is a location shared between the attacker's job/context and the runner's store, and where the runner is not adequately isolating that directory from unprivileged actors — a precondition that must be independently verified against how `Open`'s callers set `dir` in production (the exact call sites were not fully confirmed within the available context). Absent confirmation that `dir` is genuinely attacker-writable in a realistic Runner deployment (e.g., a per-job directory reused across privilege boundaries), this remains a code-level weakness whose real-world reachability is uncertain.

### Recommendation
- Open `keyPath` (and `pathname`) with `O_CREATE|O_EXCL|O_WRONLY` (or `os.OpenFile` with `O_NOFOLLOW` where supported) instead of `os.WriteFile`, so pre-existing symlinks cause an error rather than being followed.
- `lstat` the target path first and refuse to proceed if it is a symlink.
- Ensure the parent `dir` is created with restrictive permissions and is not shared with untrusted writers.

### Proof of Concept
Go unit test sketch for `commands/helpers/internal/store`:
```go
func TestOpen_SymlinkKeyPathOverwrite(t *testing.T) {
    dir := t.TempDir()
    pathname := filepath.Join(dir, "masking.db")
    sum := sha256.Sum256([]byte(pathname))
    keyPath := filepath.Join(dir, "runner"+hex.EncodeToString(sum[:]))

    target := filepath.Join(t.TempDir(), "victim.txt")
    require.NoError(t, os.WriteFile(target, []byte("important-data"), 0o644))
    require.NoError(t, os.Symlink(target, keyPath)) // attacker plants symlink at predictable path

    _, err := store.Open(dir)
    require.NoError(t, err)

    data, _ := os.ReadFile(target)
    require.NotEqual(t, "important-data", string(data)) // victim file overwritten with random key bytes
}
```
Expected assertion: `target`'s original contents are destroyed after `store.Open` runs, confirming the symlink-following overwrite via the predictable `keyPath`.
