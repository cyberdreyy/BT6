### Title
Repeated `unstake` calls reset the withdrawal cooldown for the entire unstaked balance, indefinitely delaying already-eligible withdrawals - (File: staking-pool/src/internal.rs)

### Summary
The staking pool's `Account` struct tracks a single scalar `unstaked_available_epoch_height` per delegator rather than per unstake request. Every call to `unstake`/`unstake_all` overwrites this single value to `current_epoch + NUM_EPOCHS_TO_UNLOCK`, even though it also increases (accumulates into) `account.unstaked`, which combines the newly-unstaked amount with any previously-unstaked amount that may already be near or past its original unlock epoch.

### Finding Description
`inner_unstake` in [1](#0-0)  accumulates the unstaked amount into the account's existing balance (`account.unstaked += receive_amount`) and then unconditionally resets the single cooldown timer: `account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;` [2](#0-1) . This value is exposed publicly via `is_account_unstaked_balance_available` and `get_account`, which gate `withdraw`/`withdraw_all`: [3](#0-2) , and `internal_withdraw` enforces `account.unstaked_available_epoch_height <= env::epoch_height()` before releasing funds [4](#0-3) .

Because the field is a single scalar shared across the whole `unstaked` balance rather than tracked per-unstake-request, any new `unstake`/`unstake_all` call — issued unilaterally by the account owner (an unprivileged, self-serving action) — pushes back the unlock epoch for funds that were already unstaked and possibly already close to (or past) their original unlock time. This reproduces exactly the reported "cooling period reset on multiple requests" bug class: the schedule binding "funds unstaked at epoch E1 unlock at E1+4 regardless of later actions" is broken, becoming "unlock epoch = last unstake epoch + 4" for the combined balance.

### Impact Explanation
This is a self-inflicted griefing scenario for a delegator (there's no way to attack another user's account, since `account_id` is always `env::predecessor_account_id()`), so it does not let one party steal from another. It does, however, mean the contract's documented invariant — "The contract should not lock unstaked funds for longer than 4 epochs after unstake action" (staking-pool/README.md) — can be silently violated for a user's own already-unstaked portion whenever they issue a follow-up unstake call inside the existing cooldown window, freezing part of their unstaked funds beyond the advertised 4-epoch bound.

### Likelihood Explanation
Trivially reachable: any delegator can call `unstake` twice within 4 epochs of each other with no special privileges, e.g. via wallet UI flows that call unstake for incremental amounts. No attacker gain against a victim exists here since `account_id` is always the caller's own account.

### Recommendation
Track withdrawal eligibility per unstake request (e.g., a per-epoch queue or `WithdrawNFT`-like enumerable record as referenced in the external report) instead of a single scalar `unstaked_available_epoch_height`, or only extend the timer for the newly added increment while allowing withdrawal of amounts whose original cooldown has elapsed independently of later unstake actions.

### Proof of Concept
1. Delegator stakes and then calls `unstake(X1)` at epoch `E`. `account.unstaked = X1`, `unstaked_available_epoch_height = E + 4`.
2. 3 epochs later (epoch `E+3`), the same delegator calls `unstake(X2)`. `inner_unstake` runs: `account.unstaked = X1 + X2`, and `unstaked_available_epoch_height = (E+3) + 4 = E+7`.
3. At epoch `E+4` (when `X1` should have become withdrawable per the original schedule and the "no lock beyond 4 epochs" invariant), `withdraw`/`withdraw_all` still fails because `internal_withdraw`'s check `account.unstaked_available_epoch_height <= env::epoch_height()` evaluates `E+7 <= E+4` = false, blocking withdrawal of `X1` for 3 additional epochs beyond its original unlock time.
