### Title
Secret variable key (`variableKey`) is used unsanitized as a file path segment for `File:true` variables, allowing path traversal out of the runner temp directory into the job workspace - (File: common/secrets.go, shells/bash.go, shells/powershell.go)

### Summary
`handleSecret` in `common/secrets.go` sets `Variable{Key: variableKey, File: secret.IsFile(), Masked: true, Raw: true}` using the attacker-controlled `secrets:` map key from `.gitlab-ci.yml` directly as `variable.Key`, with no character/format validation. [1](#0-0)  When shells render `File:true` variables, they call `TmpFile(variable.Key)`, which does `path.Join(TemporaryPath, name)` without ever checking for `..` traversal segments, and then write the raw secret value to that computed path. [2](#0-1) [3](#0-2) 

### Finding Description
`TemporaryPath` for file-mode variables is a directory that is a *sibling* of the job's project/build directory (e.g. `.../builds/0/project-1.tmp` next to `.../builds/0/project-1`), as shown in the shell-generation snapshot tests. [4](#0-3)  The write path is computed as `b.TmpFile(variable.Key)` → `path.Join(b.TemporaryPath, name)` in `BashWriter.Variable`/`PsWriter.Variable`. [2](#0-1) 

`Go`'s `path.Join` lexically cleans the resulting path, so if `variable.Key` (equal to the attacker-supplied `secrets:` map key, i.e. `variableKey` in `handleSecret`) contains `../` segments, the join can resolve outside `TemporaryPath` — including back into the sibling project/build directory (`project-1`), which is exactly the tree that `artifacts:`/`cache:` glob patterns (e.g. `**/*`) operate on. There is no validation of `variableKey`/`variable.Key` anywhere in `common/secrets.go` or in the `Variable`-writing shell code that rejects path-separator or `..` characters; the only validation code I found in the codebase (`common/labels.go` label-key regex) governs runner *labels*, not job/secret variable keys, and does not apply here. [5](#0-4) 

Exploit flow:
1. Attacker (pipeline author) defines a `secrets:` entry whose YAML key is a traversal string, e.g. `"../project-1/evil": { vault: { ... } }`. This key becomes `variableKey` in `Resolve`/`handleSecret`. [6](#0-5) 
2. `handleSecret` builds `Variable{Key: variableKey, File: true, Masked: true, Raw: true}` unchanged. [7](#0-6) 
3. During shell script generation, `BashWriter.Variable`/`PsWriter.Variable` computes `TmpFile(variable.Key)` = `path.Join(TemporaryPath, "../project-1/evil")`, which normalizes to a path inside the project working directory rather than the isolated temp dir, then writes the raw secret value there via `printf`/`WriteAllText`. [8](#0-7) [3](#0-2) 
4. A subsequent `artifacts:`/`cache:` rule such as `paths: ["**/*"]` in the same job, defined by the same attacker, then picks up the escaped file from within the project directory and uploads/persists it, since it now lives under the archived root.
5. Masking (the `Masked: true` flag) only redacts known-length secret substrings from *log output*, not from binary archive contents, so it provides no protection once the raw file is captured into an artifact/cache tarball.

Existing checks that fail to stop this: no key-format validation on `secrets:` map keys or `Variable.Key` before it is used as a filesystem path component; `TmpFile`/`path.Join` performs no bounds check confirming the result stays under `TemporaryPath`; `isTmpFile` only checks `strings.HasPrefix(path, TemporaryPath)` for *values*, not for validating the write destination itself, and is not even used on the write path for `File:true` variables. [9](#0-8) 

### Impact Explanation
A malicious/careless pipeline author can cause the runner to write a raw (unmasked-in-binary) secret value to an attacker-chosen location inside the job's own build/project directory instead of the isolated `.tmp` variables directory. Combined with an attacker-controlled `artifacts:`/`cache:` glob in the same job, the secret file becomes part of the uploaded artifact or cache archive, which is retrievable by anyone with access to that build/pipeline (and, via cache-key collision across branches/MRs in the same project, potentially by other pipeline authors in the same project). This breaks the invariant that file-mode secrets are only ever written to the job's isolated temp directory, converting an in-log masking control into something that can be bypassed entirely via archive exfiltration.

### Likelihood Explanation
Preconditions are minimal and fully within an ordinary pipeline author's control: define a `secrets:` block with a key containing `../` segments and an `artifacts:`/`cache:` rule with a broad path pattern in the same `.gitlab-ci.yml`. No special runner configuration, privileged executor, or admin action is required. The only open question is whether GitLab Rails' YAML/CI-lint validation restricts `secrets:` map keys to a strict identifier pattern before submission to the Runner — that check lives outside this repository and I could not verify it from the Runner codebase. If Rails does enforce a strict identifier regex on secrets keys, this specific vector is blocked upstream; but the Runner code itself contains no defense-in-depth validation, so any other caller/executor path that constructs `spec.Variable{File: true}` with an attacker-influenced `Key` (e.g., future secret backends, direct API job submission, or bypassing Rails validation) would be equally exploitable.

### Recommendation
- In `common/secrets.go` `handleSecret`, validate `variableKey` against a strict environment-variable-name pattern (e.g. `^[A-Za-z_][A-Za-z0-9_]*$`) before constructing the `Variable`, rejecting or sanitizing keys containing `/`, `\`, or `..`.
- Defensively harden `BashWriter.TmpFile`/`PsWriter.TmpFile` (and any other `File:true` variable writer) to reject or sanitize `name` inputs that would cause the joined path to escape `TemporaryPath`, e.g. by computing `filepath.Clean(joined)` and verifying it still has `TemporaryPath` as a prefix, returning an error otherwise.
- Add a regression test asserting that a `Variable{Key: "../evil", File: true}` either errors out or resolves strictly under `TemporaryPath`.

### Proof of Concept
Go unit test (place near `shells/bash_test.go` `Test_BashWriter_Variable`):
```go
func Test_BashWriter_Variable_PathTraversal(t *testing.T) {
    w := BashWriter{TemporaryPath: "/builds/0/project-1.tmp"}
    v := spec.Variable{Key: "../project-1/evil", Value: "SECRET_VALUE", File: true}
    w.Variable(v)
    out := w.String()

    // Assert the resulting write path does NOT escape TemporaryPath.
    assert.NotContains(t, out, "/builds/0/project-1/evil",
        "file-mode secret must not be writable outside TemporaryPath")
}
```
Expected (current, buggy) behavior: the generated script contains `printf '%s' $'SECRET_VALUE' > "/builds/0/project-1/evil"`, i.e. the secret is written inside the project directory (`project-1`), sibling to and escaping `TemporaryPath` (`project-1.tmp`) — proving the traversal. An integration-level PoC would additionally define an `artifacts: paths: ["**/*"]` job with such a secret and assert the produced artifact zip/tar contains the literal string `SECRET_VALUE`.

```go
func (r *defaultSecretsResolver) handleSecret(variableKey string, secret spec.Secret) (*spec.Variable, error) {
	sr, err := r.secretResolverRegistry.GetFor(secret)
	if err != nil {
		r.logger.Warningln(fmt.Sprintf("Not resolved: %v", err))
		return nil, nil
	}

	r.logger.Println(fmt.Sprintf("Using %q secret resolver...", sr.Name()))

	value, err := sr.Resolve()
	if errors.Is(err, ErrSecretNotFound) {
		if !r.featureFlagOn(featureflags.EnableSecretResolvingFailsIfMissing) {
			err = nil
		} else {
			err = fmt.Errorf("%w: %v", err, variableKey)
		}
	}
	if err != nil {
		return nil, err
	}

	variable := &spec.Variable{
		Key:    variableKey,
		Value:  value,
		File:   secret.IsFile(),
		Masked: true,
		Raw:    true,
	}

	return variable, nil
}
```
