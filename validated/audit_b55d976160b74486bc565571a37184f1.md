### Title
Discarded error from `gz.Close()` in `writeGzipFile` allows corrupted/truncated gzip archives to be reported as successful - (File: helpers/archives/gzip_create.go)

### Finding Description
`writeGzipFile` creates a `pgzip.Writer` wrapping the caller-supplied `io.Writer` and defers its close with the error explicitly discarded: `defer func() { _ = gz.Close() }()` [1](#0-0) . The function's only propagated error comes from `io.Copy(gz, file)` [2](#0-1) .

`pgzip` (klauspost/pgzip) is a parallel/buffered gzip implementation: writes to the `Writer` are buffered and compressed asynchronously, and the final compressed blocks are flushed to the underlying `io.Writer` only when `Close()` (or `Flush()`) is called. This means `io.Copy` can complete successfully while the actual write of compressed data to the destination writer (a file being written to disk, or a pipe feeding a network upload) has not yet happened. If that underlying write fails during `Close()` — e.g. due to disk-full conditions from an attacker-sized cache/artifact payload, or a broken pipe on an upload stream — the error is swallowed by `_ = gz.Close()`, and `writeGzipFile` returns `nil` from the prior successful `io.Copy` call. `CreateGzipArchive` then treats the file as successfully archived and, if it's the last file, returns `nil` overall [3](#0-2) .

This path is reachable from the legacy gzip cache/artifact archiver, `gziplegacy.archiver.Archive`, which calls `archives.CreateGzipArchive(a.w, sorted)` directly on the writer passed to the archive command, with no additional integrity check afterward [4](#0-3) . A pipeline author who controls job artifact/cache contents (attacker-sized files) can trigger disk pressure or an upload-stream failure during the flush phase, and Runner would still report the archive step as successful.

### Impact Explanation
A truncated/corrupted gzip stream can be produced and reported as a successful archive, meaning the cache or artifact accepted and potentially uploaded to GitLab does not match the actual job output. Since caches are shared by cache key across pipelines/branches (and in some setups across projects), a corrupted cache silently marked "valid" can propagate corrupted build state to later, unrelated job runs that restore the same cache key — a data-integrity issue best characterized as a low-privilege cache-poisoning/corruption channel rather than sandbox escape or secret leakage.

### Likelihood Explanation
Requires disk pressure or a failing writer at flush time (e.g., attacker-controlled large cache/artifact content exhausting disk space, or a broken upload pipe) — feasible for a pipeline author who can generate arbitrarily large job outputs, and repeatable via a synthetic faulty `io.Writer` in tests. It does not require any elevated privileges, only normal job-authoring capability.

### Recommendation
Capture and propagate the error from `gz.Close()` in `writeGzipFile` instead of discarding it, e.g.:
```go
var closeErr error
defer func() { closeErr = gz.Close() }()
...
if _, err = io.Copy(gz, file); err != nil {
    return err
}
return closeErr
```
or restructure to check `gz.Close()`'s return value explicitly after `io.Copy` and return it if `io.Copy` succeeded, ensuring `CreateGzipArchive` fails loudly on flush errors.

### Proof of Concept
Go unit test using a faulty `io.Writer` that fails only on the underlying write invoked during `Close()`'s flush:
```go
type flakyWriter struct{ failAfter int; n int }
func (f *flakyWriter) Write(p []byte) (int, error) {
    f.n++
    if f.n > f.failAfter {
        return 0, errors.New("disk full")
    }
    return len(p), nil
}

func TestCreateGzipArchive_PropagatesCloseFlushError(t *testing.T) {
    file, _ := os.CreateTemp("", "test")
    defer os.Remove(file.Name())
    file.Write([]byte("some content"))
    file.Close()

    w := &flakyWriter{failAfter: 1} // succeeds on header write, fails on flushed compressed block
    err := archives.CreateGzipArchive(w, []string{file.Name()})
    require.Error(t, err) // currently fails: err is nil despite write failure
}
```
Assertion: with the current implementation the test fails because `CreateGzipArchive` returns `nil` even though the underlying writer errored during `gz.Close()`'s flush; after the fix, the error should propagate.

```go
func CreateGzipArchive(w io.Writer, fileNames []string) error {
	for _, fileName := range fileNames {
		fi, err := os.Lstat(fileName)
		if os.IsNotExist(err) {
			logrus.Warningln("File ignored:", err)
			continue
		} else if err != nil {
			return err
		}

		err = writeGzipFile(w, fileName, fi)
		if err != nil {
			return err
		}
	}

	return nil
}
```
