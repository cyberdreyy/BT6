### Title
Stale miner-pubkey/consensus-hash and duplicate-tenure-block checks are only run at proposal time, never re-verified before the signature is actually placed - (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/chainstate/v2.rs`, `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_block_against_signer_db_state` — the "one last look" re-check that runs both after node validation (`handle_block_validate_ok`) and immediately before a signature is placed (`handle_block_pre_commit`) — only re-runs `check_latest_block_in_tenure` / `check_tenure_change_confirms_parent`. It never re-runs the miner-pubkey-hash, consensus-hash, or `DuplicateBlockFound` checks that `GlobalStateView::check_proposal` (v2) and `SortitionsView::check_proposal` (v1) perform once, at proposal arrival only.

### Finding Description
The "quote vs. execution" gap here is structurally the same shape as the missing-slippage-check bug class: a value/condition is validated once (at proposal time, based on the world as it looked then) and the irreversible action (placing a signature) is taken later, after a pre-commit round that can take arbitrarily long, without re-checking that same condition.

Concretely:
- `GlobalStateView::check_proposal` (`stacks-signer/src/chainstate/v2.rs:113-197`) checks, at proposal time only: the block's `consensus_hash` matches the currently active miner's `tenure_id`, the miner pubkey hash matches the winning pubkey hash for the sortition, the bitvec is all-1s, and (for tenure-change blocks) `validate_tenure_change_payload` rejects on `DuplicateBlockFound` if a block has already been signed in that tenure.
- These checks are documented and confirmed in code as never re-run again: [1](#0-0) .
- The actual re-check function used both at validate-ok and immediately before signing, `check_block_against_signer_db_state`, only calls `check_tenure_change_confirms_parent` / `check_latest_block_in_tenure`: [2](#0-1)  — its own doc-comment even flags it as "an incomplete check. Do NOT call this function PRIOR to `check_proposal`".
- `handle_block_pre_commit` calls exactly this incomplete recheck right before flipping the block to `LocallyAccepted` (i.e., producing the actual signature) once the ≥70% pre-commit weight threshold is reached: [3](#0-2) .
- The pre-commit-to-signature gap is explicitly acknowledged as a window where "the world" can change: [4](#0-3) .
- The duplicate-tenure-block gap is explicitly documented as relying only on the height-based "own-tenure conflict guard" in `handle_block_pre_commit`, not on re-running `DuplicateBlockFound`: [5](#0-4) .

The miner-pubkey-hash / consensus-hash / bitvec checks, however, have **no equivalent fallback guard at all** at signing time — unlike the duplicate-block case, there is no "own-tenure conflict" mechanism that substitutes for re-verifying `PubkeyHashMismatch` or `ConsensusHashMismatch`. If the signer's view of the active/winning miner for a tenure changes between proposal-time validation and the moment the pre-commit threshold is crossed (e.g. due to a later-observed sortition-related state-machine update, or a burn-view/`ActiveMiner` transition that invalidates the previously-accepted `current_miner_pkh`/`tenure_id` pairing recorded via `self.signer_state.current_miner`), the signer will still place its actual, irreversible signature on the block purely on the strength of the stale proposal-time check, because the re-check performed at `handle_block_pre_commit` (`check_block_against_signer_db_state`) does not touch `MinerState::ActiveMiner`/`current_miner_pkh`/`tenure_id` at all.

### Impact Explanation
If the miner/consensus-hash equality that `check_proposal` enforces silently breaks between proposal time and signing time (the pre-commit round can span the full ≥70%-weight collection window, which is unbounded in adversarial/slow-network conditions), a signer can end up putting its signature on a block whose miner is no longer the one the signer's current state machine considers canonical for that tenure — i.e., a signature over a block that is stale/non-canonical relative to the signer's own most up-to-date view, without ever re-verifying that equality at the point the signature is actually produced. This falls squarely in the "signer signing a non-canonical/invalid/conflicting block" impact category, since the safety property ("a signature is never given away cheaply," re-verified "one last look" before signing) is explicitly claimed by the design (`docs/signer-flows.md:15-22`) but not actually implemented for these specific fields.

### Likelihood Explanation
This does not require a signer majority or another signer's key — a single miner (plus the normal gossip of pre-commits from honest signers reaching 70% weight, which is the expected/required path for any block to ever get signed) can trigger the gap simply by having its tenure/miner status become stale during the pre-commit collection window, which the docs themselves note is where "most of the subtlety lives" because "time passes, the burn chain can fork, and another block may win the same slot." The condition is a natural consequence of the two-round sign protocol's timing, not a contrived edge case, making it a realistically reachable TOCTOU (time-of-check-to-time-of-use) gap rather than a purely theoretical one.

### Recommendation
Re-run the full `check_proposal` miner-identity checks (consensus-hash match against the currently tracked active miner, pubkey-hash match, bitvec, and `DuplicateBlockFound`), not just `check_latest_block_in_tenure`, inside `check_block_against_signer_db_state` so that both the validate-ok recheck and the pre-commit-threshold recheck immediately preceding signature production re-verify every equality that gated the original acceptance, mirroring how a slippage check re-verifies the trade's outcome against the caller's original expectation right before the irreversible transfer executes.

### Proof of Concept
Conceptual (from the async-sibling-validation timing test, which demonstrates the same gap class but for the duplicate-block dimension only): a signer accepts and pre-commits to a proposal at time T0 when it is the active miner's tenure and pubkey. Before ≥70% pre-commit weight is reached, the signer's tracked `MinerState::ActiveMiner` (via `SignerStateMachine`) transitions such that `current_miner_pkh`/`tenure_id` no longer match the pre-committed block — this can legitimately happen due to a burn-chain fork or a new sortition observed through gossip/state-machine updates. When the ≥70% pre-commit threshold is subsequently reached, `handle_block_pre_commit` calls `check_block_against_signer_db_state`, which only re-verifies `check_latest_block_in_tenure`/`check_tenure_change_confirms_parent` [6](#0-5) , so the stale miner/pubkey mismatch is never caught, and the signer proceeds to `mark_locally_accepted` and broadcast its signature [7](#0-6) . This is a design-level gap I identified by cross-referencing the documented "not re-run" list in `docs/signer-flows.md:425-437` against the actual recheck implementation; I was not able to build and run an executable end-to-end reproduction within this session, so this should be validated by constructing a concrete test analogous to the existing `async_sibling_validation` module in `stacks-signer/src/v0/tests.rs`, but targeting a mid-pre-commit miner/pubkey-hash state-machine transition rather than a duplicate-block race.

    ///
    /// Re-verify a block's chain length against the last signed block within signerdb.
    /// This is required in case a block has been approved since the initial checks of the block validation endpoint.
    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }
