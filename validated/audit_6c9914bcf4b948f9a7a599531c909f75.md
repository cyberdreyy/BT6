### Title
Late-buffer depositors earn buffer-period interest without being locked during the buffer - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The epoch APR is scaled upward to cover `epochDuration + bufferPeriod`, so every depositor is compensated for time their funds sit idle during the buffer between epochs. Because ordinary deposits stay open for the entire buffer and share price is flat during it, an attacker can deposit in the last block before `startEpoch()` and receive the full buffer-scaled interest for the next epoch — identical yield to lenders whose capital was locked for the whole buffer — while bearing zero buffer exposure. This is the direct analog of the Carapace "renewal not charged for the grace period" bug: the user is not charged (in lost time/exposure) for the grace (buffer) period but still collects its yield.

### Finding Description
`startEpoch()` computes the borrower's interest obligation as `_calcInterest(getContractValue())` [1](#0-0) , where `_calcInterest` applies the scaled APR over `epochDuration` [2](#0-1) . The scaled APR is set via `_setScaledApr`, which multiplies the intended APR by `(epochDuration + bufferPeriod) / epochDuration` inside `setAprsWithBuffer` [3](#0-2) . The code explicitly documents that this extra scaling compensates lenders for the buffer wait — withdrawers deliberately have the buffer component stripped because "they can withdraw a block after the buffer period starts" [4](#0-3) .

However, the same asymmetric treatment is not applied on the deposit side. `_deposit` only checks `whenNotPaused` and KYC, and the pool is unpaused for the entire buffer (`_pause()` is only called inside `startEpoch`) [5](#0-4) . Between `stopEpoch` and the next `startEpoch` (`epochEndDate + bufferPeriod` gate [6](#0-5) ), tranche `virtualPrice` is constant: no interest accrues during the buffer. A deposit made at `block.timestamp == epochEndDate + bufferPeriod - 1` therefore mints shares at the same price as a deposit made at the start of the buffer, yet both are included in `getContractValue()` at `startEpoch` and earn identical scaled interest for the coming epoch.

Quantified free yield for the attacker: `amount * unscaledApr * bufferPeriod / 365 days` (e.g., 10% APR, 5-day buffer on 1M USDC ≈ 1,370 USDC per epoch cycle, repeatable every epoch). The payment is real — it is added to `expectedEpochInterest` and pulled from the borrower at `stopEpoch`, accruing to the attacker's tranche price.

### Impact Explanation
An unprivileged KYC-passed lender extracts buffer-scaled yield without buffer lockup each epoch. The excess interest is funded by borrower repayments baked into `expectedEpochInterest`, i.e., the pool pays yield for a period during which the attacker's capital was not deposited. Existing long-term depositors' fair compensation for the buffer wait is economically diluted: the protocol commits to paying the buffer premium on capital that never waited. Loss is bounded by `amount * apr * bufferPeriod / year` per epoch and is repeatable every cycle.

### Likelihood Explanation
Requires only a whitelisted wallet and underlying balance — no privileged role, no timing race more precise than depositing any time in the buffer window (days wide by default). Profit scales linearly with deposit size, and the maneuver can be repeated every epoch and combined with a withdraw request in the following buffer to re-enter at the next buffer's end. The only friction is that the capital is lent for the full epoch like everyone else's — but that is the normal deposit deal, so the buffer premium is pure excess.

### Recommendation
Track deposit timestamp within the buffer and discount the buffer component for late depositors, e.g., store `lastDepositTimestamp`/`depositEpochIndex` per position or per tranche share class and scale the earned interest at the next `stopEpoch`/`requestWithdraw` by `(epochEndDateOfDeposit - depositTime) / bufferPeriod`. Alternatively, mint buffer-period deposits at a slightly discounted price so the buffer premium accrues only pro-rata to time actually spent in the buffer, mirroring the prorated math already used for `depositDuringEpoch` [7](#0-6) .

### Proof of Concept
Foundry fork test (pattern follows `testDepositDuringEpochNumericalAA` in `test/foundry/IdleCreditVault.t.sol:1591`):

```solidity
function testBufferEndDepositEarnsUnearnedBufferYield() external {
    // 10% apr, 30-day epoch, 5-day buffer (scaled apr = 11.67%)
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(30 days, 5 days);
    IdleCreditVault(address(strategy)).setAprs(10e18, _scaleAprWithBuffer(10e18));
    vm.stopPrank();

    // honest lender deposits at the very start of the buffer
    address early = makeAddr('early');
    deal(defaultUnderlying, early, 1000 * ONE_SCALE);
    vm.startPrank(early);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), type(uint256).max);
    idleCDO.depositAA(1000 * ONE_SCALE); // executed at buffer start
    vm.stopPrank();

    // attacker waits until the last second of the buffer
    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() - 1);
    address late = makeAddr('late');
    deal(defaultUnderlying, late, 1000 * ONE_SCALE);
    vm.startPrank(late);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), type(uint256).max);
    idleCDO.depositAA(1000 * ONE_SCALE);
    vm.stopPrank();

    // both got shares at the same flat buffer price
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _toggleEpoch(false, 10e18, _expectedFundsEndEpoch());

    uint256 price = cdoEpoch.virtualPrice(address(AAtranche));
    uint256 earlyVal = IERC20(address(AAtranche)).balanceOf(early) * price / 1e18;
    uint256 lateVal  = IERC20(address(AAtranche)).balanceOf(late)  * price / 1e18;
    // attacker earns ~5 days of yield he never waited for:
    assertApproxEqAbs(lateVal, earlyVal, 2);            // identical payout
    // lateVal - 1000e6 ≈ 1000e6 * 10% * 35/365 ≈ 9.59 USDC for 1s of buffer exposure
}
```
