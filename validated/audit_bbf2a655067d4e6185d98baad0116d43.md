### Title
Dust Pre-funding of a To-Be-Created Account Permanently Blocks `SystemInstruction::CreateAccount` (`AccountAlreadyInUse` Griefing) - (File: `programs/system/src/system_processor.rs`)

### Summary
The System program's `create_account` (used by `SystemInstruction::CreateAccount` and `SystemInstruction::CreateAccountWithSeed`) treats any account with `lamports > 0` as "already in use" and unconditionally fails the instruction, regardless of whether the account has actually been initialized/allocated. An unprivileged attacker who knows the target address in advance (e.g. a keypair-based account whose pubkey is published before the creation transaction lands, or a `create_with_seed` derived address) can front-run the legitimate creation transaction with a single dust `Transfer` (as little as 1 lamport) to that address. Once funded, every future `CreateAccount`/`CreateAccountWithSeed` targeting that address will hit the `to.get_lamports() > 0` branch and revert with `SystemError::AccountAlreadyInUse`, permanently denying account creation at that address via the standard instruction, exactly mirroring the ReraiseETHCrowdfund bug where a state check gated on a value (`previousVotingPower == 0` / here `lamports == 0`) can be pre-triggered by an attacker's dust contribution/transfer.

### Finding Description
In `create_account`:

The check equates "has any lamports" with "already in use," but lamports alone say nothing about whether the account is actually owned/allocated by another party — it is trivially satisfiable by anyone who can transfer 1 lamport to the target pubkey before the legitimate `CreateAccount` transaction executes. Because Solana transactions specify destination pubkeys explicitly (and derived/seed addresses are deterministic via `Pubkey::create_with_seed`), an attacker can predict and pre-fund the address with a plain `SystemInstruction::Transfer`, which has no signature requirement from the target and needs only knowledge of the pubkey. This is functionally identical to the reported bug class: a cheap, permissionless "dust" action performed by an attacker sets a state flag (`lamports != 0`, analogous to `previousVotingPower != 0`) that the legitimate flow relies on to decide "first-time" vs. "already exists," causing the legitimate flow to revert every time.

Agave's own repository acknowledges this exact griefing vector: it introduces a parallel instruction, `SystemInstruction::CreateAccountAllowPrefund`, whose processor explicitly skips the lamports check:
```
programs/system/src/system_processor.rs:184-186
/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
``` [3](#0-2) 
gated behind the `create_account_allow_prefund` feature flag [4](#0-3) . However, the legacy `CreateAccount` / `CreateAccountWithSeed` code paths — which remain the default and most widely used across wallets, CLIs (`create_nonce_account`, `create_account_with_seed` in `cli/src/nonce.rs`), and countless deployed programs — are unaffected by this mitigation and remain fully exposed to the dust-prefund DOS.

### Impact Explanation
Any unprivileged party observing a pending or future `CreateAccount`/`CreateAccountWithSeed` target address (which is always public, since Solana instructions name destination pubkeys explicitly, and seed-derived addresses are computable off-chain) can permanently deny creation of that specific account by sending 1 lamport to it beforehand. This is a state-mutation-triggered denial-of-service: it does not steal funds directly, but it can block legitimate protocol flows (e.g., nonce account creation used for durable-nonce transactions, PDA-adjacent seed accounts, escrow/vault initialization patterns relying on `CreateAccountWithSeed`) indefinitely, since the dust lamports remain in the account and the check `lamports > 0` never turns false without a manual reclaim by whoever controls the account (which the intended creator does not, since it was never signed/created by them). This matches the "DOS by dust" impact class in the report.

### Likelihood Explanation
High reachability, low cost: requires only a public RPC endpoint and a single, near-zero-cost `Transfer` instruction targeting a known/precomputable pubkey, with no special privileges, timing precision beyond ordinary front-running, or protocol-specific knowledge. The precondition (attacker knows the target pubkey before creation) is common: seed-derived addresses (`Pubkey::create_with_seed`) are fully deterministic and publicly computable, and even keypair-based "to-be-created" addresses are frequently published (e.g., in a prior instruction of the same transaction, in off-chain UI flows, or via mempool observation) before the `CreateAccount` instruction executes on-chain.

### Recommendation
For the legacy `create_account` path, replace the "already in use" heuristic from "`lamports > 0`" to solely checking data length and ownership (i.e., adopt the same allocate/assign preconditions used by `create_account_allow_prefund`), or default all such paths to prefund-tolerant semantics. Concretely, gate creation solely on `!account.get_data().is_empty() || !system_program::check_id(account.get_owner())` (as already done in `allocate`, see `programs/system/src/system_processor.rs:91-100`) rather than on the lamport balance, matching the intent already implemented in `create_account_allow_prefund`.

### Proof of Concept
1. Compute or observe the destination pubkey `T` for an upcoming `SystemInstruction::CreateAccount` (or `create_with_seed(base, seed, owner)` for `CreateAccountWithSeed`).
2. Attacker submits `system_instruction::transfer(attacker, T, 1)` — 1 lamport, no signature from `T` needed since `T` is the receiver, not sender.
3. Legitimate party submits `SystemInstruction::CreateAccount { lamports, space, owner }` targeting `T`.
4. `create_account()` executes `to.get_lamports() > 0` → true (balance = 1), returns `SystemError::AccountAlreadyInUse`, exactly as exercised by the existing test `test_create_already_in_use` for the "already has lamports" case: [5](#0-4) . Every retry with the same instruction fails identically, permanently blocking account creation at `T` via the standard path.
