### Title
Division-before-multiplication precision loss in Jovian DA-footprint gas estimation systematically underestimates per-transaction DA footprint - (File: crates/common/evm/src/executor/block_executor.rs)

### Summary
`BaseBlockExecutor::jovian_da_footprint_estimation` computes a transaction's Jovian DA-footprint gas by dividing the FastLZ-estimated, 1e6-scaled compressed size down to a byte count *before* multiplying by the per-byte `da_footprint_gas_scalar`, instead of multiplying first and dividing once at the end. This is the exact "divide-then-multiply" precision-loss pattern described in the referenced report, applied to a resource-metering fee-like value that gates per-transaction and per-block admission.

### Finding Description
`jovian_da_footprint_estimation` computes:
```rust
let encoded = tx_env.encoded_bytes()
    .map_or_else(..., |encoded| estimate_tx_compressed_size(encoded))
    .saturating_div(1_000_000);   // <-- division first
...
Ok(encoded.saturating_mul(da_footprint_gas_scalar))   // <-- multiplication after
``` [1](#0-0) 

`estimate_tx_compressed_size` (`tx_estimated_size_fjord`) returns the FastLZ-estimated size scaled by `1_000_000` (e.g. `fastlz_size * L1_COST_FASTLZ_COEF - L1_COST_INTERCEPT`, floored at `MIN_TX_SIZE_SCALED = 100_000_000`) [2](#0-1) . Dividing this scaled value by `1_000_000` *before* multiplying by `da_footprint_gas_scalar` truncates any fractional byte (up to `999_999/1_000_000` of a byte) before the scalar is applied, discarding a scalar-sized amount of footprint for every transaction whose estimated size is not an exact multiple of `1_000_000`. This mirrors the report's root cause (dividing a "bare" quantity before multiplying by a "share" factor loses far more precision than multiplying first).

This same computation also exists in `L1FeeParams::jovian_da_footprint` in `crates/common/l1-fees/src/params.rs` (lines 90-98), performing an identical divide-then-multiply, while the analogous `calculate_tx_l1_cost_fjord`/`calculate_tx_l1_cost_ecotone` functions in the same file correctly multiply first and divide once at the end [3](#0-2) , showing the fee-accounting code elsewhere in this codebase already follows the correct multiply-before-divide discipline — the DA-footprint path is the outlier.

The resulting `tx_da_footprint` is checked directly against the per-block DA-footprint budget and is accumulated into `da_footprint_used`, which is enforced per-transaction and reported as the block's `blob_gas_used`:
```rust
let tx_da_footprint = self.jovian_da_footprint_estimation(&tx_env, &tx)?;
if tx_da_footprint > da_footprint_available { ... reject ... }
``` [4](#0-3) 
and
```rust
self.da_footprint_used = self.da_footprint_used.saturating_add(blob_gas_used);
``` [5](#0-4) 

Every unprivileged transaction sender fully controls the input to this calculation (transaction size, hence the FastLZ-estimated size), so this is directly reachable via ordinary post-Jovian transaction submission.

### Impact Explanation
Because the truncation happens per-transaction before the scalar multiplication, a sender who crafts transaction sizes that fall just below an exact 1e6-scaled boundary systematically under-reports DA footprint by up to `(scalar - 1)` gas units per transaction. Aggregated across many transactions in a block, this allows more actual L1 data-availability bytes to be posted than the protocol's DA-footprint budget is meant to permit, i.e., a resource-metering / block-building limit bypass. Since both block building and block validation execute this same (deterministic) code path, this does not cause a chain split by itself, but it does mean the enforced DA-footprint limit is weaker than the value the protocol schedule intends, permitting sustained under-metering of DA usage across a chain's blocks (a resource-accounting/DoS-adjacent budget bypass rather than a fund-theft bug).

Note: this same divide-then-multiply pattern is explicitly documented as intentional in `crates/common/l1-fees/src/params.rs`'s doc comment ("divided back down by 1e6 and multiplied ... Mirrors the reference `jovian_da_footprint_estimation`"), referencing the official OP-stack Jovian spec. I could not verify against the external OP-stack specification whether integer-byte truncation before scalar multiplication is the spec-mandated formula or a deviation from it; if the upstream/reference implementation performs the identical division-first order, this would be intentional protocol design rather than an implementation defect, which would significantly weaken or invalidate this finding. This uncertainty should be resolved by comparing against the linked spec (`https://github.com/ethereum-optimism/specs/blob/main/specs/protocol/jovian/exec-engine.md#da-footprint-block-limit`) before treating this as an exploitable deviation.

### Likelihood Explanation
Reaching this code path requires only submitting an ordinary, unprivileged transaction post-Jovian activation; no special privileges, deposits, or precompile access are needed. However, because the loss per transaction is bounded to less than one byte's worth of scalar (not an arbitrarily large discrepancy as in the original report's `bareIncrease` example), and because the pattern is mirrored identically in two independent locations with an explicit "mirrors the reference" comment suggesting spec conformance, the likelihood that this represents an actual, currently-exploitable deviation from Base's intended/specified protocol behavior — rather than intentional, spec-conformant integer-byte truncation — is uncertain and could not be confirmed from the indexed code alone.

### Recommendation
Confirm against the OP-stack Jovian specification whether DA-footprint gas is defined as `floor(estimatedSize / 1e6) * scalar` or `floor(estimatedSize * scalar / 1e6)`. If the specification intends the multiply-then-divide order (to minimize truncation, consistent with the other L1 fee formulas in this codebase), change both `BaseBlockExecutor::jovian_da_footprint_estimation` (`crates/common/evm/src/executor/block_executor.rs`) and `L1FeeParams::jovian_da_footprint` (`crates/common/l1-fees/src/params.rs`) to multiply the raw scaled size by `da_footprint_gas_scalar` first and divide by `1_000_000` once, matching the pattern already used in `calculate_tx_l1_cost_fjord`/`calculate_tx_l1_cost_ecotone`.

### Proof of Concept
Given `tx_estimated_size_fjord(input) = 145_246_900` (i.e., 145 bytes + 246,900/1,000,000 of a byte) and `da_footprint_gas_scalar = 10_000`:
- Current implementation: `145_246_900 / 1_000_000 = 145`, then `145 * 10_000 = 1_450_000`.
- Multiply-first implementation: `(145_246_900 * 10_000) / 1_000_000 = 1_452_469`.

The current order under-reports the transaction's DA footprint by `2_469` gas units for this single transaction; a sender can construct many such transactions (sizes just below a 1e6-scaled boundary) to accumulate meaningful undercounting of `da_footprint_used` against the block's declared DA-footprint gas limit, analogous to the `feeAmount` undercount demonstrated in the referenced report's PoC.

/// Calculate the estimated compressed transaction size in bytes, scaled by 1e6.
/// This value is computed based on the following formula:
/// max(minTransactionSize, intercept + fastlzCoef*fastlzSize)
pub fn tx_estimated_size_fjord(input: &[u8]) -> u64 {
    let fastlz_size = flz_compress_len(input) as u64;

    fastlz_size
        .saturating_mul(L1_COST_FASTLZ_COEF)
        .saturating_sub(L1_COST_INTERCEPT)
        .max(MIN_TX_SIZE_SCALED)
}

    /// Post-Fjord L1 cost:
    /// `estimatedSize * (baseFeeScalar*l1BaseFee*16 + blobFeeScalar*l1BlobBaseFee) / 1e12`.
    pub fn calculate_tx_l1_cost_fjord(&self, input: &[u8]) -> U256 {
        if Self::is_fee_exempt(input) {
            return U256::ZERO;
        }
        let l1_fee_scaled = self.calculate_l1_fee_scaled_ecotone();
        if l1_fee_scaled.is_zero() {
            return U256::ZERO;
        }
        U256::from(tx_estimated_size_fjord(input))
            .saturating_mul(l1_fee_scaled)
            .wrapping_div(U256::from(1_000_000_000_000u64))
    }
