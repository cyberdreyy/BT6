### Title
Incorrect ProgramData offset in `parse_bpf_upgradeable_loader` corrupts reported program bytes for accounts with `upgrade_authority_address = None` - ([File: account-decoder/src/parse_bpf_loader.rs])

### Summary
`Bank::new_target_program_data_account` always writes the program ELF starting at the fixed offset `UpgradeableLoaderState::size_of_programdata_metadata()`, regardless of whether `upgrade_authority_address` is `Some` or `None`. `parse_bpf_upgradeable_loader`, however, subtracts `serialized_size(&Pubkey::default())` from that offset when the parsed `upgrade_authority_address` is `None`, producing a smaller slice-start offset that does not match the actual on-chain layout. This causes the decoder to prepend ~32 bytes of zero-padding metadata to the base64-encoded program data returned to RPC clients for any immutable (authority-less) `ProgramData` account.

### Finding Description
`Bank::new_target_program_data_account` computes a single, fixed constant: [1](#0-0) 
`programdata_metadata_size = UpgradeableLoaderState::size_of_programdata_metadata()` is used unconditionally as the byte offset at which the ELF is copied into the account, irrespective of whether `upgrade_authority_address` is `Some(..)` or `None`. `size_of_programdata_metadata()` is defined as the bincode-serialized size of the `ProgramData` variant assuming `upgrade_authority_address = Some(Pubkey::default())` (the maximum-size encoding), so it is always larger than the actual bincode length of a `ProgramData { upgrade_authority_address: None, .. }` value (by exactly `serialized_size(&Pubkey::default())`, i.e. 32 bytes). Because `AccountSharedData::new_data_with_space` allocates `space` bytes and bincode-serializes the (possibly shorter) `None` variant into the front of that buffer, the remaining bytes up to the fixed offset are left as zero padding, and the ELF write always starts exactly at that fixed offset — for both `Some` and `None` cases. This same fixed-offset convention is reused consistently elsewhere in the migration code, e.g. in `directly_invoke_loader_v3_deploy`: [2](#0-1) 
and is asserted directly by the existing test helper, which reads the ELF from `program_data_account.data()[programdata_metadata_size..]` for both `Some` and `None` authority test cases: [3](#0-2) 

In contrast, `parse_bpf_upgradeable_loader` in `account-decoder` computes a *different, smaller* offset when the decoded `upgrade_authority_address` is `None`: [4](#0-3) 
`offset = size_of_programdata_metadata() - serialized_size(&Pubkey::default())`. This value equals the *actual bincode length* of the `None` variant (13 bytes vs. the fixed 45-byte constant assuming `Some`), not the *fixed offset actually used when the account was written* (45 bytes). Consequently `data[offset..]` includes the 32 bytes of zero padding between the true end of the serialized metadata and the real ELF start, which get base64-encoded and returned as part of `UiProgramData.data`.

This is directly reachable via any `getAccountInfo`/`getProgramAccounts` RPC call with `jsonParsed` encoding on a `ProgramData` account whose `upgrade_authority_address` is `None` (an immutable/frozen upgradeable program) — a common, legitimate on-chain state (e.g. produced by `SetAuthority`-to-`None`, or by Core BPF migrations/Loader v2→v3 upgrades performed with `upgrade_authority_address = None`, as at: [5](#0-4) 
No existing guard checks or reconciles this offset against the actual write-side layout; the existing unit test in `parse_bpf_loader.rs` happens to pass only because it manually serializes account data using `bincode::serialize` (which produces the *actual variable-length* encoding for `None`) rather than using the fixed-offset write convention that `new_target_program_data_account` (and the rest of the loader) actually use, masking the discrepancy.

### Impact Explanation
Any unprivileged client issuing a single `getAccountInfo` (or `getProgramAccounts`) RPC call with `jsonParsed` encoding against a `ProgramData` account with no upgrade authority receives corrupted/misreported program bytes (32 extra leading zero bytes prepended to the real ELF). This matches the "decoder panic and misreporting" / wrong account data returned category in scope — RPC clients (explorers, tooling, program verifiers) relying on `jsonParsed` output for such accounts get an incorrect ELF image.

### Likelihood Explanation
Highly likely to be triggered in practice: setting the upgrade authority to `None` (freezing a program) is a completely normal, single-instruction, unprivileged action any user can perform on their own upgradeable program, and immutable programs are common (many mainnet programs are frozen this way, and Core BPF migrations frequently configure `upgrade_authority_address = None`). No special conditions are needed beyond issuing a standard `jsonParsed` RPC query against such an account.

### Recommendation
Fix `parse_bpf_upgradeable_loader` in `account-decoder/src/parse_bpf_loader.rs` to use the fixed `UpgradeableLoaderState::size_of_programdata_metadata()` offset unconditionally for the `ProgramData` branch (matching the write-side convention in `Bank::new_target_program_data_account` / `directly_invoke_loader_v3_deploy`), removing the `Pubkey`-size subtraction for the `None` case. Add a differential regression test that constructs account data the same way the runtime does (fixed-offset ELF placement regardless of authority state) and asserts the decoder recovers the exact original ELF bytes for both `Some` and `None` authority states.

### Proof of Concept
```rust
// account-decoder/src/parse_bpf_loader.rs (new test)
#[test]
fn test_programdata_none_authority_offset_matches_runtime_layout() {
    use solana_loader_v3_interface::state::UpgradeableLoaderState;

    let elf = vec![7u8; 64];
    let programdata_metadata_size = UpgradeableLoaderState::size_of_programdata_metadata();

    // Mirror Bank::new_target_program_data_account's actual write layout:
    // account space = metadata_size (fixed, Some-based) + elf.len(),
    // ELF is always copied starting at the FIXED offset, matching mod.rs:113.
    let space = programdata_metadata_size + elf.len();
    let mut data = vec![0u8; space];
    let metadata = UpgradeableLoaderState::ProgramData {
        slot: 42,
        upgrade_authority_address: None,
    };
    let serialized = bincode::serialize(&metadata).unwrap();
    data[..serialized.len()].copy_from_slice(&serialized);
    data[programdata_metadata_size..].copy_from_slice(&elf); // fixed offset, as in mod.rs

    let parsed = parse_bpf_upgradeable_loader(&data).unwrap();
    match parsed {
        BpfUpgradeableLoaderAccountType::ProgramData(ui) => {
            let expected = BASE64_STANDARD.encode(&elf);
            let actual = match ui.data {
                UiAccountData::Binary(b64, _) => b64,
                _ => panic!("expected binary"),
            };
            // FAILS today: decoder offset = programdata_metadata_size - 32,
            // so `actual` contains 32 leading zero bytes not present in `elf`.
            assert_eq!(actual, expected, "decoder misreports ELF bytes for None authority");
        }
        _ => panic!("expected ProgramData"),
    }
}
```
This test currently fails, demonstrating that `parse_bpf_upgradeable_loader` returns 32 extra leading zero bytes instead of the exact ELF for `upgrade_authority_address: None`, while using the correct fixed-offset for `Some` passes.
