### Title
Unprivileged callers can set vault APR config while `idleCDO` is unset — permission gap on privileged parameter write - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.setApr` (and its wrappers `setAprs`/`setAprsWithBuffer`) intentionally skips the caller check whenever `idleCDO == address(0)`, allowing any EOA to write the privileged `lastApr`/`unscaledApr` configuration. This is the same bug class as CVE-2017-18896 (CWE-732: a sensitive, privileged-write endpoint left reachable by unauthenticated callers). [1](#0-0) 

### Finding Description
In `setApr`, the authorization check is conditional:

```solidity
if (_cdo != address(0)) {
  if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
}
```

`idleCDO` is only assigned later via `setWhitelistedCDO` (onlyOwner), and is `address(0)` right after `initialize`. [2](#0-1)  During that window any external caller can invoke:

- `setApr(_apr)` — sets `lastApr` up to `maxApr` (default `20e18`, i.e. a 20x-scaled APR). [3](#0-2) 
- `setAprs(_unscaledApr, _apr)` — additionally writes `unscaledApr`, which has **no cap at all**. [4](#0-3) 
- `setAprsWithBuffer` — same gap, with attacker-chosen scaling. [5](#0-4) 

`lastApr`/`unscaledApr` drive borrower interest obligations at `stopEpoch` (`expectedEpochInterest`) and gate the APR0 settlement path in `prepareStopEpochWithApr0`, which reverts with `NotAllowed` if `unscaledApr != 0` while `apr0TotalPrincipal > 0`. [6](#0-5) 

### Impact Explanation
Two concrete paths depending on timing:

1. **Pre-CDO window (deployment/misconfiguration)**: an attacker who is a KYC-passing lender deposits, then inflates `lastApr` toward `maxApr` before `idleCDO` is wired. If the borrower funds `stopEpoch` at the inflated expected interest, the attacker-LP captures yield far above the agreed rate — direct theft of borrower-supplied funds proportional to `tvl * apr * duration / YEAR`. If the borrower cannot fund it, the epoch cannot close and lender funds are frozen until manager intervention.
2. **APR0 sabotage**: writing any non-zero `unscaledApr` while APR0 receipts are outstanding forces `prepareStopEpochWithApr0` to revert at every `stopEpoch`, temporarily freezing all pending APR0 withdrawals. Recovery requires the manager to re-set APRs (privileged, honest), so this is a temporary-freeze severity rather than permanent.

The broken invariant is access control: a privileged accounting parameter is writable by unauthorized callers. No existing guard (`_onlyIdleCDO`, `nonReentrant`, `maxApr` on `lastApr` only) prevents it, and `unscaledApr` is entirely uncapped.

### Likelihood Explanation
The gap only exists while `idleCDO == address(0)`. If `IdleCreditVaultFactory` wires `setWhitelistedCDO` atomically with clone `initialize`, the window is limited to deployments/upgrades done in separate transactions and to any vault where the owner delay between the two calls is nonzero — a realistic pattern for upgradeable admin operations executed via multisig/queue. I was not able to fully verify `IdleCreditVaultFactory` call ordering within this analysis, so likelihood is conditional on that sequencing; the code-level missing-auth defect is unambiguous regardless.

### Recommendation
Remove the `idleCDO == address(0)` exemption: require `msg.sender == idleCDO || msg.sender == manager` unconditionally (allow `manager` alone pre-CDO since `manager` is set in `initialize`), or perform APR seeding inside `initialize`/`setWhitelistedCDO` so no external setter is callable before the CDO is bound.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVaultAprPoison.t.sol
function test_PoisonAprBeforeCDOSet() public {
    // Deploy clone + initialize with legit borrower/manager; do NOT call setWhitelistedCDO yet.
    // (simulates non-atomic deployment / upgrade gap)
    address attacker = makeAddr("attacker");

    vm.prank(attacker);
    // unscaledApr has no cap; lastApr capped only by maxApr (20e18)
    vault.setAprs(type(uint256).max / 1e18, vault.maxApr());

    assertEq(vault.unscaledApr(), type(uint256).max / 1e18);
    assertEq(vault.getApr(), vault.maxApr()); // expectedEpochInterest now inflated

    // In an APR0 pool, prepareStopEpochWithApr0 now reverts NotAllowed at every stopEpoch
    // until manager repairs the config -> pending withdraws frozen.
}
```

Note: exact PoC wiring (fork block, factory vs manual clone path, and whether `initialize` + `setWhitelistedCDO` are atomic in the deployed factory) should be confirmed against `IdleCreditVaultFactory.sol` and the target vault's deployment history; the pre-CDO unauthenticated write itself is confirmed by inspection of lines 225–235.
