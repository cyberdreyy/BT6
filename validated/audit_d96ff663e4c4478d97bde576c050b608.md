## Finding

### Title
Password reset does not revoke standing API tokens, allowing persistent backdoor access after account compromise remediation - (File: core/web/user_controller.go, core/web/resolver/mutation.go)

### Summary
Chainlink Node users can authenticate either via a browser session cookie or via a long-lived API access token (`token_key` / `token_hashed_secret`) created through `NewAPIToken`/`CreateAndSetAuthToken`. Both the REST `UpdatePassword` handler and the GraphQL `UpdateUserPassword` mutation, which exist precisely so a user can lock out anyone who has compromised their account, only invalidate *session* cookies and never touch the user's API token. Just like the Arcadia `approvedCreditor` backdoor that survives an account-ownership transfer, a Chainlink API token survives the "ownership recovery" action (password change) that the user believes revokes all standing access.

### Finding Description
`UserController.updateUserPassword` (invoked from `UpdatePassword`) only calls `ClearNonCurrentSessions` and `SetPassword`: [1](#0-0) 

The GraphQL equivalent, `Resolver.UpdateUserPassword`, does the same two calls — `ClearNonCurrentSessions` then `SetPassword` — with no call to `DeleteAuthToken`/`SetAuthToken`: [2](#0-1) 

The API token, however, is a wholly separate, independently long-lived credential stored on the same `users` row (`token_key`, `token_salt`, `token_hashed_secret`), created via `NewAPIToken`/`SetAuthToken` and consumed via `FindUserByAPIToken`: [3](#0-2) [4](#0-3) 

`AuthenticationProvider` explicitly exposes `DeleteAuthToken`/`SetAuthToken` as first-class, independent operations from `SetPassword`/`ClearNonCurrentSessions`: [5](#0-4) 

So, exactly as in the Arcadia report where `_transferOwnership` fails to reset `approvedCreditor`, leaving the old owner's secondary credential live — here, the "kick out attacker" action (password change) fails to reset the secondary, independently-authenticating credential (the API token). If an attacker who compromised a user's session or password had also minted an API token (`NewAPIToken`, only requiring the then-known password), that token keeps working with full account privileges after the legitimate user "recovers" the account by changing the password. Unlike `ClearNonCurrentSessions`, which is deliberately invoked to sever standing access, there is no equivalent step for the token-based channel.

### Impact Explanation
This is a genuine unprivileged-reachable authentication bypass: any authenticated node user (any role, since `UpdatePassword`/`UpdateUserPassword` require only being logged in as that user) who attempts to remediate a compromised account by changing their password leaves a still-valid, full-privilege API token active. An attacker holding that token retains unauthorized, persistent API access to the node (job management, keys, bridges, etc., depending on role) indefinitely — a concrete "request impersonation"/authentication bypass, not merely theoretical.

### Likelihood Explanation
Medium: it requires (a) an attacker having obtained the account's credentials long enough to call `NewAPIToken` (which itself requires the current password), and (b) the legitimate owner believing that a password change alone revokes all access. Chainlink node documentation and UX around `ClearNonCurrentSessions` suggest exactly that expectation — that a password change severs unauthorized access — making this a realistic, likely-to-be-hit gap during real incident response.

### Recommendation
When a user's password is changed (`SetPassword` path in both `UserController.updateUserPassword` and `Resolver.UpdateUserPassword`), also invalidate the user's existing API token by calling `DeleteAuthToken` (or rotating it), in the same transaction/flow that already purges non-current sessions, so that all standing credentials for the account are revoked together — mirroring how the Arcadia fix recommends resetting `approvedCreditor` on any transfer of account authority.

### Proof of Concept
1. Attacker compromises User A's session or password (e.g. via phishing) and, while access lasts, calls `POST /v2/user/tokens` (`NewAPIToken`) to mint a standing API token for User A's account.
2. User A detects the compromise and calls `PATCH /v2/user/password` (or the `updateUserPassword` GraphQL mutation) to change their password, believing this fully revokes attacker access.
3. `updateUserPassword`/`UpdatePassword` calls `ClearNonCurrentSessions` (killing session cookies) and `SetPassword`, but never calls `DeleteAuthToken`.
4. Attacker continues to authenticate to the node's REST/GraphQL API using the previously minted API token (`Authorization` header), retaining full account privileges despite the password reset.

func (u *UserController) updateUserPassword(c *gin.Context, user *clsession.User, newPassword string) error {
	ctx := c.Request.Context()
	sessionID, err := getCurrentSessionID(c)
	if err != nil {
		return err
	}
	orm := u.App.AuthenticationProvider()
	if err := orm.ClearNonCurrentSessions(ctx, sessionID); err != nil {
		u.App.GetLogger().Errorf("failed to clear non current user sessions: %s", err)
		return errors.New("unable to update password")
	}
	if err := orm.SetPassword(ctx, user, newPassword); err != nil {
		if errors.Is(err, clsession.ErrNotSupported) {
			return errUnsupportedForAuth
		}
		u.App.GetLogger().Errorf("failed to update current user password: %s", err)
		return errors.New("unable to update password")
	}
	return nil
}

func (r *Resolver) UpdateUserPassword(ctx context.Context, args struct {
	Input UpdatePasswordInput
}) (*UpdatePasswordPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	session, ok := webauth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return nil, errors.New("couldn't retrieve user session")
	}

	dbUser, err := r.App.AuthenticationProvider().FindUser(ctx, session.User.Email)
	if err != nil {
		return nil, err
	}

	if !utils.CheckPasswordHash(args.Input.OldPassword, string(dbUser.HashedPassword)) {
		r.App.GetAuditLogger().Audit(audit.PasswordResetAttemptFailedMismatch, map[string]any{"user": dbUser.Email})

		return NewUpdatePasswordPayload(nil, map[string]string{
			"oldPassword": "old password does not match",
		}), nil
	}

	if err = r.App.AuthenticationProvider().ClearNonCurrentSessions(ctx, session.SessionID); err != nil {
		return nil, clearSessionsError{}
	}

	err = r.App.AuthenticationProvider().SetPassword(ctx, &dbUser, args.Input.NewPassword)
	if err != nil {
		return nil, failedPasswordUpdateError{}
	}

	r.App.GetAuditLogger().Audit(audit.PasswordResetSuccess, map[string]any{"user": dbUser.Email})
	return NewUpdatePasswordPayload(session.User, nil), nil
}

func (o *orm) CreateAndSetAuthToken(ctx context.Context, user *sessions.User) (*auth.Token, error) {
	newToken := auth.NewToken()

	err := o.SetAuthToken(ctx, user, newToken)
	if err != nil {
		return nil, err
	}

	return newToken, nil
}

// SetAuthToken updates the user to use the given Authentication Token.
func (o *orm) SetAuthToken(ctx context.Context, user *sessions.User, token *auth.Token) error {
	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(token, salt)
	if err != nil {
		return pkgerrors.Wrap(err, "user")
	}
	sql := "UPDATE users SET token_salt = $1, token_key = $2, token_hashed_secret = $3, updated_at = now() WHERE email = $4 RETURNING *"
	return o.ds.GetContext(ctx, user, sql, salt, token.AccessKey, hashedSecret, user.Email)
}

// DeleteAuthToken clears and disables the users Authentication Token.
func (o *orm) DeleteAuthToken(ctx context.Context, user *sessions.User) error {
	sql := "UPDATE users SET token_salt = '', token_key = '', token_hashed_secret = '', updated_at = now() WHERE email = $1 RETURNING *"
	return o.ds.GetContext(ctx, user, sql, user.Email)
}
