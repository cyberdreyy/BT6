### Title
Signer vote-type confusion: a `BlockRejection` signature is a valid `BlockAccepted` signature for the same block, allowing a rejection to be recounted as an acceptance - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_signature` authenticates an incoming `BlockAccepted` purely by recovering a public key from `(signer_signature_hash, signature)` and checking that the recovered address belongs to the signer set — it never verifies that the signature came from a message the signer actually intended as an *acceptance*. Because the payload signed for a `BlockAccepted` is exactly the block's `signer_signature_hash` [1](#0-0) , and a signer's rejection (`BlockRejection`) also carries a `signature` field keyed to the very same `signer_signature_hash` (the field is populated from `BlockRejection::new(signer_signature_hash, reject_reason, private_key, …)` and consumed by the same style of `recover_public_key`/`verify` helper) [2](#0-1) , the two "opposite" votes are cryptographically indistinguishable: nothing in the signed bytes encodes "accept" vs "reject". A signature that a signer produced while rejecting a block is bit-for-bit a valid signature to satisfy `handle_block_signature`'s check for that same block.

### Finding Description
`BlockAccepted`'s inner signature is verified as:
```
Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(block_hash.bits(), signature)
```
and the recovered address is only checked against `is_valid_signer` [3](#0-2) . There is no domain separation tag, no polarity byte, and no binding to `RejectReason`/`response_data` in the signed message — the message is simply the block's `signer_signature_hash`, the same hash Nakamoto block headers use for the multisig assembled into `NakamotoBlockHeader::signer_signature` and verified in `verify_signer_signatures` [4](#0-3) .

`handle_block_rejection` performs the mirrored authentication path (`recover_public_key`, then `is_valid_signer`) on `BlockRejection.signature` before treating the rejection as validly attributable to that signer [5](#0-4) . Since `BlockRejection` is keyed on the identical `signer_signature_hash` field (see its `consensus_serialize`/`consensus_deserialize` layout, which independently carries `reason`, `reason_code`, `signer_signature_hash`, `signature`) [6](#0-5) , an attacker who observes a signer's broadcast rejection (rejections are gossiped in the clear over StackerDB, exactly as acceptances are) can lift the raw `signature` bytes and rewrap them inside a freshly-constructed `SignerMessage::BlockResponse(BlockResponse::Accepted(BlockAccepted{ signer_signature_hash, signature: <copied>, .. }))`. This new message only needs to be published from a slot the attacker legitimately controls (the outer StackerDB chunk signature is the attacker's own key — no other signer's private key material is ever required, satisfying the "no majority / no other signer's key" scoping).

When honest signers process this crafted `BlockAccepted` via `handle_block_signature` → `store_and_process_block_signature`, they will:
1. Recover the honest rejecting signer X's public key from the copied signature.
2. Confirm X is a valid signer (`is_valid_signer`).
3. Call `add_block_signature(block_hash, X, signature)` and count X's weight toward the 70% acceptance threshold [7](#0-6) .

X's explicit rejection is thereby recounted as an acceptance. If enough such messages are relayed, `store_and_process_block_signature` will assemble and broadcast the block as globally accepted using X's mis-attributed signature [8](#0-7) , and because the same signature bytes are also valid entries for the block header's `signer_signature` vector, they can be gathered by the node/coordinator (`signer_coordinator.rs`, `gathered_signatures`) as if X approved the block [9](#0-8) .

### Impact Explanation
This is exactly the "rejection recounted as an accept" break called out as Critical: a signer's negative vote on an invalid/non-canonical/conflicting block can be turned into a counted positive vote without compromising that signer's private key, undermining the entire pre-commit/70%-threshold safety property the signer protocol relies on to prevent signing invalid or conflicting blocks.

### Likelihood Explanation
Rejections and acceptances are routinely broadcast in plaintext to all participants over StackerDB, so the raw signature bytes needed for the attack are always available to any single participant with write access to their own slot (a one-slot actor plus gossip observation, matching the allowed threat model). No majority collusion, no other signer's key, and no auth_token is required — only re-wrapping an already-public signature into a different message envelope. The exact byte-level equivalence of the `BlockRejection` signature payload could not be double-checked against `BlockRejection::new`'s implementation within the available tool budget (the function body itself was not retrieved), so this should be validated by inspecting `BlockRejection::new` / `recover_public_key` in `libsigner/src/v0/messages.rs` to confirm the signed preimage is identical to `BlockAccepted`'s (`signer_signature_hash.bits()`), with no additional context (reason, vote polarity, chain_id, nonce) folded into the signature.

### Recommendation
Bind the signed message to the vote's semantics: include a polarity/domain-separation tag (e.g., hash of `(signer_signature_hash, "accept"|"reject")`) or otherwise incorporate the `RejectReason`/vote type into the data that is actually signed, so an acceptance signature and a rejection signature for the same block can never be interchangeable. Apply the same fix to the `BlockPreCommit` message type if it shares the same underlying signed hash.

### Proof of Concept
1. Signer X (part of the reward-cycle signer set) receives an invalid block proposal, rejects it, and broadcasts `SignerMessage::BlockResponse(BlockResponse::Rejected(BlockRejection{ signer_signature_hash: H, signature: S, .. }))` over its own StackerDB slot.
2. An attacker who controls a different, independent StackerDB slot for the same message type observes this message (all `BlockResponse` chunks are public) and extracts `S`.
3. The attacker constructs `SignerMessage::BlockResponse(BlockResponse::Accepted(BlockAccepted{ signer_signature_hash: H, signature: S, metadata: <attacker-chosen>, response_data: <attacker-chosen> }))` and writes it to its own slot, signed with its own key at the StackerDB layer.
4. Every honest signer processing this message calls `handle_block_signature`, recovers X's public key from `S` over `H`, confirms X is a valid signer, and records X's weight as an acceptance via `add_block_signature`/`store_and_process_block_signature` [10](#0-9) , even though X never accepted block `H`.

        if !self.is_valid_signer(&signer_address) {

                signature,

                warn!("{self}: Failed to add pending block signature response: {e:?}");
            }
            return;

    fn store_and_process_block_signature(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        signer_address: &StacksAddress,
        signature: &MessageSignature,
    ) {
        let block_hash = &block_info.signer_signature_hash();
        // signature is valid! store it.
        // if this returns false, it means the signature already exists in the DB, so just return.
        if !self
            .signer_db
            .add_block_signature(block_hash, signer_address, signature)
            .unwrap_or_else(|_| panic!("{self}: Failed to save block signature"))
        {
            return;
        }

        // If this isn't our own signature and we haven't seen a pre-commit from this signer yet, try treating it as a pre-commit in case the caller is running an outdated version
        if signer_address != &self.stacks_address && !self.signer_db.has_committed(block_hash, signer_address).inspect_err(|e| warn!("Failed to check if pre-commit message already considered for {signer_address:?} for {block_hash}: {e}")).unwrap_or(false) {
            self.handle_block_pre_commit(stacks_client, sortition_state, signer_address, block_hash);
            return;
        }

        if block_info.signed_group.is_some() {
            // We have already processed this block to the accepted state. Adding more signatures will not change anything so nothing to check.
            return;
        }
        // do we have enough signatures to broadcast?
        // i.e. is the threshold reached?
        let signatures = self
            .signer_db
            .get_block_signatures(block_hash)
            .unwrap_or_else(|_| panic!("{self}: Failed to load block signatures"));

        // put signatures in order by signer address (i.e. reward cycle order)
        let addrs_to_sigs: HashMap<_, _> = signatures
            .into_iter()
            .filter_map(|sig| {
                let Ok(public_key) = Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(
                    block_hash.bits(),
                    &sig,
                ) else {
                    return None;
                };
                let addr = StacksAddress::p2pkh(self.mainnet, &public_key);
                Some((addr, sig))
            })
            .collect();

        let signature_weight = self.signer_weights.get(signer_address).unwrap_or(&0);
        let total_signature_weight = self.compute_signature_signing_weight(addrs_to_sigs.keys());
