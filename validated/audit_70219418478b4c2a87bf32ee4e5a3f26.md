### Title
A vault liquidity drain makes `stopEpoch` revert indefinitely, freezing all pending withdraws and epoch settlement — (`contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
In programmable-borrower mode, `ProgrammableBorrower.onStopEpoch` assumes that whenever the borrower's ERC4626 shares economically cover the stop-epoch shortfall, `vault.withdraw()` will succeed — analogous to snapd assuming every squashfs entry it reads is a regular file. When the vault has no redeemable liquidity (a "non-regular file"), `withdraw` reverts, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, and `IdleCDOEpochVariant.stopEpoch` reverts as a whole. An unprivileged user of the same ERC4626 vault can keep its underlying liquidity fully drained (e.g., borrow the entire idle liquidity in the underlying Morpho market, or redeem liquidity ahead of every `stopEpoch`), so every `stopEpoch` call reverts and the epoch can never be stopped while the condition holds.

### Finding Description
The flow in `IdleCDOEpochVariant._stopEpoch` (contracts/IdleCDOEpochVariant.sol:395-404) calls `IProgrammableBorrower.onStopEpoch(...)`. Inside `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:239-253): [1](#0-0) 

Two cases are handled, but a third is not:

1. `shortfall > _currentVaultAssets()` → returns `true`, `getFundsFromBorrower`'s `transferFrom` fails, and `_handleBorrowerDefault` runs (real insolvency → default).
2. `shortfall <= _currentVaultAssets()` and `vault.withdraw` succeeds → normal stop.
3. `shortfall <= _currentVaultAssets()` but `vault.withdraw` **reverts** (shares are valuable on paper but the vault has no cash) → `catch { revert StopEpochVaultLiquidityUnavailable(); }` bubbles up and reverts the entire `stopEpoch`.

Case 3 is exactly the file-type confusion: shares "cover" the read, but the underlying resource is a pipe — reading it blocks forever. Because `epochAccountingActive`, `isEpochRunning`, `pendingWithdraws`, and all receipt accounting remain unchanged (verified by `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`, test/foundry/ProgrammableBorrowerCreditVault.t.sol:372-399), the retry never converges while an attacker keeps vault liquidity at zero. `emergencyExitVault` (line 361-372) does not help: it calls `vault.redeem`, which reverts under the same liquidity condition. Unlike snapd blocking on a FIFO, here the "file" is an ERC4626 whose `withdraw`/`redeem`/`maxWithdraw` contractually do not guarantee liquidity.

### Impact Explanation
Temporary freezing of funds with quantified scope: while vault liquidity is exhausted, the honest manager's `stopEpoch` always reverts, so:

- the epoch cannot stop — `epochEndDate` passes but settlement never happens;
- all `pendingWithdraws` receipts cannot be funded, so `claimWithdrawRequest`/`claimInstantWithdrawRequest` reverts via `epochNumber <= lastWithdrawRequest[user]` (contracts/strategies/idle/IdleCreditVault.sol:326-328);
- epoch interest is never realized into tranche prices and `unclaimedFees` stays frozen;
- the pool cannot be closed (`_interest == 1` close-pool path goes through the same hook).

All lender principal and all pending withdraw-request payouts (potentially the entire pool NAV) are frozen for as long as the attacker maintains zero vault liquidity. There is no fund loss, but there is a real, unbounded-duration availability loss driven by an unprivileged third party.

### Likelihood Explanation
The attacker needs no role in the Idle system — only the ability to influence the ERC4626 vault's free liquidity, an explicitly in-scope persona ("a user of the programmable borrower's ERC4626 vault"). For MetaMorpho-style vaults this is cheap and repeatable: borrow all available liquidity in the underlying market around the expected `epochEndDate`, or sandwich `stopEpoch` transactions with liquidity withdrawals. The attack can be sustained per epoch at the cost of borrow interest on the drained amount. The code even encodes the assumption in a comment ("transient ERC4626 liquidity failures can be retried", IdleCDOEpochVariant.sol:396-397), which shows the revert path was designed for accidental transience, not for a persistent adversary — nothing bounds the retry window or escalates to default when retries keep failing.

### Recommendation
Bound the retry loop on the CDO side: if `onStopEpoch` reverts due to vault illiquidity for N consecutive attempts or past a grace deadline, escalate to `_handleBorrowerDefault`/`_handleVaultLoss` so receipts are haircut and finalized instead of frozen. Alternatively, treat "shares cover but withdraw reverts" as a realized vault loss (`vaultLoss`) and let `stopEpoch` proceed applying the loss waterfall rather than reverting, keeping `epochAccountingActive` semantics consistent.

### Proof of Concept
```solidity
// Foundry fork PoC (mirrors testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable)
function testStopEpochPermanentlyFrozenWhileVaultLiquidityDrained() external {
    _setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0);

    // ATTACKER: unprivileged user of the ERC4626 vault drains all underlying
    // liquidity (e.g., borrows the full idle amount in the underlying Morpho
    // market). Vault shares of ProgrammableBorrower still cover the shortfall.
    address attacker = makeAddr("vaultUser");
    drainVaultLiquidity(attacker); // helper: attacker borrows/redeems so
                                 // asset.balanceOf(vault) == ~0

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Every manager stopEpoch reverts: withdraw fails, StopEpochVaultLiquidityUnavailable
    for (uint i; i < 5; ++i) {
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);
        vm.warp(block.timestamp + 1 days);
    }

    // Funds remain frozen: epoch still running, receipts unfunded, claims revert
    assertTrue(cdoEpoch.isEpochRunning());
    assertGt(strategy.pendingWithdraws(), 0);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();

    // emergencyExitVault cannot help either: redeem reverts on same illiquidity
    vm.expectRevert();
    vm.prank(manager);
    programmableBorrower.emergencyExitVault(0);
}
```
