## Analysis Result

### Title
Builder pending-withdrawal amount is committed to the execution payload uncapped, while only the capped amount is deducted from state — minting Gwei not backed by any balance decrease - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` places the raw, unclamped `BuilderPendingWithdrawal.amount` into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` (and therefore the execution payload the EL must honor), while `apply_withdrawals` only ever deducts `min(withdrawal.amount, builder_balance)` from the builder's actual `balance`. When a builder's balance is smaller than the requested withdrawal, the CL commits to a withdrawal amount that exceeds what was ever removed from any account, so the EL mints the full requested amount to `fee_recipient` while the builder's stake is only reduced to zero — the difference is Gwei created from nothing.

### Finding Description
`get_builder_withdrawals` builds withdrawal entries directly from the queue without capping to the builder's balance: [1](#0-0) 

Compare this to the validator-side `get_pending_partial_withdrawals`, which explicitly computes the available balance and clamps the requested amount before recording it: [2](#0-1) 

For builders there is no equivalent `min(...)` when constructing the `Withdrawal`, so `withdrawal.amount == withdrawal.amount requested` unconditionally, even if it exceeds `builder.balance`.

Later, `apply_withdrawals` reads the *current* balance and only deducts the capped amount: [3](#0-2) 

Both of these functions are called from `process_withdrawals`/`get_expected_withdrawals`, and `state.payload_expected_withdrawals` (populated with the *uncapped* `withdrawal.amount`) is exactly what the block's execution payload must match: [4](#0-3) 

The repo's own generated test explicitly documents and asserts this exact mismatch: a builder with 1 ETH balance and a pending withdrawal request for 5 ETH produces a committed `Withdrawal.amount == 5 ETH`, while the builder's balance is only reduced by 1 ETH (to 0): [5](#0-4) 

This breaks the equality that must hold between "Gwei removed from beacon state" and "Gwei paid out via the execution payload": 4 ETH is paid to `fee_recipient` on the EL side that was never actually held or deducted from any validator/builder balance in the CL state.

### Impact Explanation
This is a Critical-severity issue under the given rubric: it is a case of Gwei being created and paid to a (possibly attacker-controlled) `fee_recipient` address that does not correspond to any real balance decrease. Any actor who can enqueue a `BuilderPendingWithdrawal` with `amount` greater than the target builder's `balance` (e.g., via a builder withdrawal request, or simply because the builder's balance has since dropped due to slashing-like penalties/bid payments) can force the protocol to commit to minting the shortfall on the execution layer, inflating total ETH supply beyond what consensus-layer accounting reflects.

### Likelihood Explanation
The bug is reachable on the ordinary "happy path" of builder withdrawal processing — no malicious peer, coalition, or client bug is required. It only requires a `BuilderPendingWithdrawal` entry whose `amount` exceeds the corresponding builder's current `balance` at processing time (e.g., balance reduced between request time and processing time by other state transitions, or an intentionally oversized request), which the spec's own generated regression tests demonstrate is a normal, currently-passing scenario rather than an edge case guarded against.

### Recommendation
In `get_builder_withdrawals` (and any other place constructing builder `Withdrawal` entries from `BuilderPendingWithdrawal`), clamp the recorded amount to the builder's available balance *at commitment time*, consistent with how `get_pending_partial_withdrawals` clamps validator partial withdrawals, and make sure to account for balance already consumed by prior withdrawals for the same builder within the same batch (analogous to `get_balance_after_withdrawals`). The invariant to enforce is: the `Withdrawal.amount` committed into `payload_expected_withdrawals` must always equal the amount actually deducted from `state.builders[*].balance` in `apply_withdrawals`.

### Proof of Concept
1. Create a builder with `balance = 1 ETH`.
2. Enqueue a `BuilderPendingWithdrawal` for that builder with `amount = 5 ETH` and some `fee_recipient` address.
3. Call `process_withdrawals(state)`.
4. Observe: `state.payload_expected_withdrawals[0].amount == 5 ETH` (committed to the EL), but `state.builders[builder_index].balance == 0` (only 1 ETH was ever deducted) — matching the assertions in `test_builder_withdrawal_insufficient_balance`: [6](#0-5) 
5. When this withdrawal is honored by the execution layer, `fee_recipient` receives 5 ETH even though only 1 ETH of stake existed and was removed — 4 ETH created out of thin air.
