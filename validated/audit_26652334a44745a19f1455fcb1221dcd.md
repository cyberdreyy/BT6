### Title
BridgeTypesController.Create leaks raw Postgres error details due to dead pgError-handling code checking stale `err` instead of `CreateBridgeType`'s returned `e` - ([File: core/web/bridge_types_controller.go])

### Summary
In `BridgeTypesController.Create`, when `orm.CreateBridgeType` fails (e.g., with a Postgres unique-constraint violation on `external_initiators_name_key`), the handler returns immediately at the `if e := orm.CreateBridgeType(ctx, bt); e != nil` branch using the raw error `e`, before the subsequent `errors.As(err, &pgErr)` check ever executes. That later block is unreachable dead code because it inspects the stale, already-`nil`-checked `err` variable from `bridges.NewBridgeType`, not `e`. As a result, the intended sanitized "bridge Type conflict" (409) response is never produced, and the raw `pgconn.PgError` (including constraint name, SQL state, and detail text) is serialized directly into the JSON API error response with a 500 status.

### Finding Description
`BridgeTypesController.Create` (core/web/bridge_types_controller.go:61-97):
```go
bta, bt, err := bridges.NewBridgeType(btr)
if err != nil { ... return }
...
if e := orm.CreateBridgeType(ctx, bt); e != nil {
    jsonAPIError(c, http.StatusInternalServerError, e)   // raw error returned here, function returns
    return
}
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) {   // dead code: `err` is guaranteed nil here (checked earlier), and this only runs if CreateBridgeType returned nil
    ...
}
```
`jsonAPIError` (core/web/helpers.go:21-29) serializes `err.Error()` directly into the JSON body unless the error is a `*models.JSONAPIErrors`. A `*pgconn.PgError` is not that type, so its `.Error()` output — which includes the Postgres error code, message, detail, and constraint name — is returned verbatim to the caller.

The pgError-specific handling block (checking `ConstraintName == "external_initiators_name_key"` and substituting a generic "bridge Type %v conflict" message with 409 Conflict) was clearly intended to catch this exact case but is unreachable: it only fires when `CreateBridgeType` succeeds (`e == nil`) and `err` (from the earlier `NewBridgeType` call, already validated non-nil-checked) is somehow a pgError, which cannot happen since that branch already returned on non-nil `err`.

Any caller permitted to hit `POST /v2/bridge_types` who supplies a bridge name colliding with an existing external initiator name (or otherwise triggers any DB constraint/error surfaced by `CreateBridgeType`) receives the raw Postgres error text instead of the sanitized conflict message, and a `500` instead of `409`.

### Impact Explanation
This causes disclosure of internal database implementation details (constraint names, SQL error codes/detail strings) to a client via the API response, which is a low-severity internal information disclosure. It also causes incorrect HTTP status codes for a client's error handling. It does not by itself provide credential disclosure, privilege escalation, or fund movement — the impact is limited to leaking schema/constraint metadata and defeating the intended "generic conflict" abstraction. This is best classified as an information disclosure / improper error handling finding, not a critical/high severity node compromise.

### Likelihood Explanation
Reaching this path only requires being able to call the bridge creation endpoint with a name that collides with an existing `external_initiators` record's name (or otherwise causes `CreateBridgeType` to return a DB error), which requires whatever role/token is permitted to create bridges. This is deterministic and repeatable — any caller with bridge-create access can trigger it every time by reusing a known external-initiator name.

### Recommendation
Fix the dead-code bug by checking the actual error returned from `CreateBridgeType` (`e`), not the stale `err`:
```go
if e := orm.CreateBridgeType(ctx, bt); e != nil {
    var pgErr *pgconn.PgError
    if errors.As(e, &pgErr) && pgErr.ConstraintName == "external_initiators_name_key" {
        jsonAPIError(c, http.StatusConflict, fmt.Errorf("bridge Type %v conflict", bt.Name))
        return
    }
    jsonAPIError(c, http.StatusInternalServerError, e)
    return
}
```
Additionally, avoid passing raw `error.Error()` text from DB-layer errors to `jsonAPIError` for non-JSONAPIErrors types generally, to prevent future leaks of internal error strings.

2. Call `BridgeTypesController.Create` via `POST /v2/bridge_types` with a valid `BridgeTypeRequest` JSON body, authenticated as a normal write/edit-role user.
3. Assert:
   - Expected (fixed) behavior: HTTP status `409`, response body message equals `"bridge Type <name> conflict"` only, with no `pgErr`/SQL text leaked.

// jsonAPIError adds an error to the gin context and sets
// the JSON value of errors.
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
