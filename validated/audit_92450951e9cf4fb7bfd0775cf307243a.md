Based on my investigation, `get_pending_logs`, `get_pending_transactions`, `get_pending_transactions_with_logs`, and `get_pending_transaction_hashes` in `PendingBlocks` iterate over the entire in-memory `self.transactions` collection with no cap, and the pending-state update queue that feeds it is explicitly documented as unbounded.

### Title
`eth_getLogs`/pending-state RPC handlers scan an unbounded flashblocks transaction buffer, risking DoS as pending backlog grows - (File: crates/execution/flashblocks/src/pending_blocks.rs)

### Summary
`PendingBlocks::get_pending_logs`, `get_pending_transactions`, `get_pending_transactions_with_logs`, and `get_pending_transaction_hashes` perform a full linear scan over `self.transactions` for every call, with no limit on the number of transactions that can accumulate in that buffer.

### Finding Description
`get_pending_logs` iterates every transaction in `self.transactions`, looks up its receipt, and filters logs against the caller-supplied filter — an O(n) scan per RPC call with no page/size cap: [1](#0-0) 
`get_pending_transactions`, `get_pending_transactions_with_logs`, and `get_pending_transaction_hashes` similarly clone/collect the entire transaction set: [2](#0-1) 

This buffer is populated by `FlashblocksState`, whose update queue is an unbounded mpsc channel and whose own README documents that "the update queue is unbounded" and warns that "a sustained burst of payloads that are all ahead of the tip still grows memory. A hard bound on the queue is separate work": [3](#0-2) 


`get_pending_logs` is directly reachable via the public `eth_getLogs` RPC path when a query's `toBlock` is `pending`, merging historical logs with a full scan of pending logs on every call: [4](#0-3) 

This is the same bug class as `BlueBerryBank.getPositionIdsByOwner`: an unbounded, ever-growing collection is walked in full inside a query path with no pagination, index, or cap, so cost grows linearly (here, per RPC call rather than per on-chain gas budget) with the size of an attacker/builder-influenced backlog.

### Impact Explanation
If the pending/flashblocks buffer backs up (e.g., under sustained flashblock bursts ahead of the canonical tip, as the crate's own documentation warns can happen), each `eth_getLogs("pending")`, and each internal consumer of `get_pending_transactions*`, does a full linear pass over a growing in-memory vector. Under sustained load this degrades RPC latency and CPU usage for the node servicing pending-block queries, potentially making the node unable to serve `eth_getLogs` and related pending-state RPCs promptly for all callers — an RPC-serviceability degradation matching the rule's "an RPC the node can no longer serve" acceptance criterion.

### Likelihood Explanation
The flashblocks README itself documents that the underlying queue is unbounded and that a hard bound is "separate work" not yet implemented, meaning the size of the transaction buffer these functions scan is not currently capped by protocol invariant, only by depth-based pruning of stale snapshots (`max_pending_blocks_depth`) — which bounds staleness, not the number of transactions accumulated while a snapshot remains fresh. Because `eth_getLogs` with `toBlock: pending` is a normal, unprivileged, anonymous RPC query, any client can trigger repeated full scans, and a builder/sequencer emitting many flashblocks per block window before finalization can directly grow the scanned set.

### Recommendation
Bound the flashblocks pending transaction/log buffer size (not just its staleness depth), and/or maintain an index (e.g., an address/topic-keyed log index alongside the flat `transactions` vector) so `get_pending_logs` does not need a full linear scan per call. Consider also capping or paginating `get_pending_transactions`/`get_pending_transactions_with_logs` responses.

### Proof of Concept
Not independently verifiable from static review alone — I was unable to confirm from the index whether `max_pending_blocks_depth` or other runtime configuration effectively caps `self.transactions` length in practice, or whether there is an additional per-flashblock transaction-count limit enforced elsewhere in the pipeline. A background Devin session with full repository access would be needed to trace `StateProcessor`/`PendingBlocksBuilder` construction paths end-to-end and construct a reproducible load test (e.g., feeding many synthetic flashblocks with large transaction counts and measuring `eth_getLogs("pending")` latency) to confirm the growth is unbounded in a running node.

    pub fn get_pending_logs(&self, filter: &Filter) -> Vec<Log> {
        let mut logs = Vec::new();

        for tx in &self.transactions {
            if let Some(receipt) = self.transaction_receipts.get(&tx.tx_hash()) {
                for log in receipt.inner.logs() {
                    if filter.matches(log.as_ref()) {
                        logs.push(log.inner.clone());
                    }
                }
            }
        }

        logs
    }

    async fn get_logs(&self, filter: Filter) -> RpcResult<Vec<BaseLogResponse>> {
        debug!(
            message = "rpc::get_logs",
            address = ?filter.address
        );

        // Check if this is a mixed query (toBlock is pending)
        let (from_block, to_block) = match &filter.block_option {
            alloy_rpc_types_eth::FilterBlockOption::Range { from_block, to_block } => {
                (*from_block, *to_block)
            }
            _ => {
                // Block hash queries or other formats - delegate to eth API
                return self.eth_filter.logs(filter).await;
            }
        };

        // If toBlock is not pending, delegate to eth API
        if !matches!(to_block, Some(BlockNumberOrTag::Pending)) {
            return self.eth_filter.logs(filter).await;
        }

        // Mixed query: toBlock is pending, so we need to combine historical + pending logs
        Metrics::rpc_get_logs().increment(1);
        let mut all_logs = Vec::new();

        let pending_blocks = self.flashblocks_state.get_pending_blocks();

        let mut fetched_logs = HashSet::new();
        // Get historical logs if fromBlock is not pending
        if !matches!(from_block, Some(BlockNumberOrTag::Pending)) {
            // Create a filter for historical data (fromBlock to latest)
            let mut historical_filter = filter.clone();
            historical_filter.block_option = alloy_rpc_types_eth::FilterBlockOption::Range {
                from_block,
                to_block: Some(BlockNumberOrTag::Latest),
            };

            let historical_logs: Vec<BaseLogResponse> =
                self.eth_filter.logs(historical_filter).await?;
            for log in &historical_logs {
                fetched_logs.insert((log.block_number, log.log_index));
            }
            all_logs.extend(historical_logs);
        }

        // Always get pending logs when toBlock is pending
        let pending_logs = pending_blocks.get_pending_logs(&filter);

        // Dedup any logs from the pending state that may already have been covered in the historical logs
        let deduped_pending_logs: Vec<BaseLogResponse> = pending_logs
            .iter()
            .filter(|log| !fetched_logs.contains(&(log.block_number, log.log_index)))
            .cloned()
            .map(BaseLogResponse::from)
            .collect();
        all_logs.extend(deduped_pending_logs);

        Ok(all_logs)
    }
