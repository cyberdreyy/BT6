### Title
Unfunded instant-withdraw receipts are paid from any strategy balance, letting claimants steal borrower repayments and funded normal-withdraw reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out the entire aggregated `instantWithdrawsRequests[_user]` balance — burning and transferring the full amount via `_transferFundedClaim` — without checking which portion of that aggregate has actually been funded through `collectInstantWithdrawFunds`. The per-epoch accounting (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`) exists to track the unfunded remainder, but the claim path ignores it entirely before a default is finalized. Any underlying sitting in the strategy — borrower repayments sent via `sendInterestAndDeposits`, funds collected for pending normal withdraws via `collectWithdrawFunds`, or partially collected instant funds — can be drained by an instant-withdraw claimant whose receipt was never funded.

### Finding Description
`requestInstantWithdraw` burns CDO strategy tokens, mints a 1:1 receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch` and `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375). Receipts are meant to be funded later when the CDO calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying from the CDO into the strategy (lines 398-403).

The claim path, however, is:

```
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

(contracts/strategies/idle/IdleCreditVault.sol:387-392)

`_transferFundedClaim` only checks that the strategy's raw underlying balance, minus `defaultRecoveryReserve` (zero pre-default), covers `amount` (lines 897-907). There is no epoch gate, no comparison against `pendingInstantWithdraws`, and no per-epoch funded/unfunded split — the exact counterpart of a bounds check that a buffer overflow lacks: the write (payout) reads past the funded boundary of the receipt buffer.

Concrete sequence (running epoch, fixed-APR mode):

1. Epoch N is running; borrower holds the pool funds.
2. Attacker (KYC'd lender holding tranche tokens) calls `requestInstantWithdraw` for amount X. `pendingInstantWithdraws = X`; the strategy holds ~0 underlying.
3. Honest sequence: at `stopEpoch`/`startEpoch` the borrower repays interest/principal; the CDO calls `collectInstantWithdrawFunds` for only part of the queue, or the borrower sends funds into the strategy via `sendInterestAndDeposits`/`deposit`, or `collectWithdrawFunds` funds normal pending receipts.
4. The instant any underlying lands in the strategy, the attacker calls `claimInstantWithdrawRequest` through the CDO and receives the full X, even though `pendingInstantWithdraws` still records X (or a remainder) as unfunded.
5. The paid-out underlying was earmarked for other users' funded normal withdraw receipts or for borrower-accounted epoch funds, so those claims later revert on insufficient balance — direct theft plus insolvency of remaining receipts.

The broken invariant is "one receipt, one funded payout": receipt minting and payout are decoupled from the funding watermark, so a receipt spends funds belonging to a different queue. The `defaultRecoveryReserve` guard in `_transferFundedClaim` only protects post-default reserves, and `claimInstantWithdrawRequest`'s defaulted-epoch branch only runs when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` (line 382), leaving the entire pre-default surface unguarded.

### Impact Explanation
Direct theft of underlying tokens and consequent insolvency: an unprivileged tranche holder with an unfunded instant-withdraw receipt can withdraw funds that belong to pending normal withdrawers or to the epoch's active-LP/borrower accounting. The loss equals the smaller of the unfunded receipt and the transient strategy balance (bounded by the queue size, which can be the full NAV for instant queues). Once drained, legitimate `claimWithdrawRequest`/interest payments revert, permanently impairing funded claimants.

### Likelihood Explanation
Likelihood depends on the strategy ever holding underlying while unfunded instant receipts exist. That occurs whenever `collectInstantWithdrawFunds` only partially fills the queue, when normal-withdraw funding (`collectWithdrawFunds`) lands while instant receipts are pending, or on borrower repayments routed through the strategy. An attacker only needs a tranche position and one instant request. I was unable to fully verify the CDO-side gating in `IdleCDOEpochVariant.sol` (its `claimInstantWithdrawRequest` wrapper may impose additional conditions that reduce exploitability); if the CDO claims on behalf of users without checking the strategy's funded watermark, the bug is directly triggerable. If the CDO already gates claims on `pendingInstantWithdraws == 0` per user, the finding reduces to a dust/rounding concern, which I could not rule out in this pass.

### Recommendation
Track a funded watermark per user/epoch for instant receipts the same way normal receipts are gated: only pay `min(instantWithdrawsRequests[_user], fundedInstantBasis)` where funded basis = `instantWithdrawClaimsByEpoch` totals minus `pendingInstantWithdraws` attributed per user, or require `pendingInstantWithdraws == 0` (fully funded epoch) before paying the aggregate in `claimInstantWithdrawRequest`. Alternatively, burn and pay only the funded portion and keep the unfunded remainder queued.

### Proof of Concept
Foundry fork sketch (notation, requires harness around `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
// epoch running, borrower funded with pool assets
vm.prank(attackerCDOSide); // via CDO.requestInstantWithdraw path
vault.requestInstantWithdraw(X, attacker);
assertEq(vault.pendingInstantWithdraws(), X);

// simulate partial funding or a normal-withdraw funding landing in strategy
deal(underlying, address(vault), Y); // Y >= X, e.g. borrower repayment / collectWithdrawFunds

// attacker claims full X even though receipt is unfunded
cdo.claimInstantWithdrawRequest(attacker); // burns X receipt, transfers X underlying
assertEq(underlying.balanceOf(attacker), X);
// vault.pendingInstantWithdraws() still == X -> double spend of funding
```

Not verified end-to-end against `IdleCDOEpochVariant.claimInstantWithdrawRequest`; if that wrapper enforces a funded check the exploit path closes.
