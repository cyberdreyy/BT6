### Title
Broadcasting an out-of-order `Accepted` response wedges a signer into never noticing group consensus - (File: `stacks-signer/src/v0/signer.rs`)

### Summary

### Finding Description
When a signer receives a peer's `BlockResponse::Accepted`, `store_and_process_block_signature` first stores the signature, then checks whether it has ever seen a `BlockPreCommit` from that peer for this block via `self.signer_db.has_committed(...)`. If not, the code assumes the sender is "an outdated version" that skipped the two‑phase pre‑commit step, and *reroutes the whole event* into `handle_block_pre_commit`, returning immediately without ever computing `total_signature_weight` for the acceptance tally: [1](#0-0) 

`handle_block_pre_commit` is built to decide *whether this signer itself should sign*, not to check whether the group has already crossed the acceptance (signature) threshold. If this signer has already signed the block itself (`block_info.signed_self.is_some()`), the function returns immediately with "nothing to do": [2](#0-1) 

The only place that recomputes `total_signature_weight`, compares it to `min_weight`, and — on success — calls `mark_locally_accepted(true)` plus `broadcast_signed_block` (pushing the assembled, thresholded signature set to the node) is the tail of `store_and_process_block_signature`, *after* the outdated-peer branch: [3](#0-2) 

So the sequence:
1. Signer S has already validated and self-signed block B (`signed_self` set), and is now only waiting to observe that ≥70% signature weight has accumulated so it can assemble and push the block to its node.
2. A peer P (a single signer slot) sends only a `BlockResponse::Accepted` for B and never sends a `BlockPreCommit` for B — either because P is byzantine and deliberately withholds the pre-commit message, or because the pre-commit chunk was simply lost/delayed on StackerDB while the acceptance arrived.
3. On S, `add_block_signature` successfully stores P's signature (weight is now, say, exactly at or above the 70% threshold when combined with previously stored signatures).
4. Because `has_committed(B, P)` is false, S takes the "outdated peer" branch and calls `handle_block_pre_commit`, which — since `signed_self` is already set on S — returns at the "nothing to do" branch without ever reaching the pre-commit-threshold logic, and (crucially) without ever falling through to the acceptance-threshold computation that lives further down in `store_and_process_block_signature`.
5. P's now-stored signature is never re-evaluated against the acceptance threshold until *some other* triggering event recomputes `get_block_signatures`/`total_signature_weight` for B (e.g. `store_and_process_block_signature` being invoked again with `signer_address == self.stacks_address`, or another peer's genuine pre-commit/acceptance sequence). If no such event ever arrives — because every other honest signer already completed its own two-phase handshake earlier and has no reason to resend anything for this block — S never notices that the group has reached consensus, never calls `mark_locally_accepted(true)`, and never calls `broadcast_signed_block` to push the finished block to its own node.

This breaks the "aggregated-weight vs verified-accepts" equality described in the docs (`docs/signer-flows.md` section 6): a verified, stored `Accepted` signature exists in the DB and counts toward on-chain acceptance, but S's local bookkeeping never re-derives that the aggregate crossed the threshold, because the single code path that both stores the signature *and* checks the threshold was short-circuited into the pre-commit-only path.

### Impact Explanation
This matches the High-impact criterion "a signer wedged into never signing valid blocks" / more precisely into never *recognizing* that a valid block reached consensus and thus never pushing it to its node. A single one-slot signer (attacker-controlled, or simply a peer whose pre-commit chunk did not arrive before its acceptance did) can cause another specific signer to become permanently stuck, unable to relay the fully-signed block to its own node even though a valid supermajority signature exists. Depending on how many signers are wedged this way simultaneously, this can materially delay or, in adversarial conditions, stall block finalization for the affected signer(s)/miner path, without requiring a majority of signers to be malicious — only the one attacker who deliberately omits the pre-commit message needs to be byzantine.

### Likelihood Explanation
Likelihood is moderate to high: nothing prevents an unmodified, current-version signer implementation from being made to send an `Accepted` `BlockResponse` while suppressing its own `BlockPreCommit` broadcast (or, in the honest case, a `BlockPreCommit` chunk merely arriving late/out of order on StackerDB, which the design docs themselves acknowledge as an expected occurrence — "the pre-commit message was somehow dropped"). No majority collusion or privileged access is required; the flaw is purely in how the target signer's own event-handling code routes an out-of-order acceptance once it has already signed the block itself.

### Recommendation
In `store_and_process_block_signature`, the "outdated peer" fallback should not unconditionally short-circuit into `handle_block_pre_commit` and return. Even when routing the acceptance into the pre-commit accounting for weight purposes, the function should also (or instead) fall through to recompute `total_signature_weight` from `get_block_signatures` and check it against `min_weight`, regardless of whether `block_info.signed_self` is already set, so that a newly-stored acceptance signature is never left unexamined for group-threshold purposes. Equivalently, `handle_block_pre_commit`'s early "already signed" return should not skip a check of whether the acceptance-signature threshold has been reached and the block should be pushed to the node.

### Proof of Concept
Deterministic sequence on a single signer S (no majority collusion needed, only one byzantine peer P):
1. Block B is proposed and validated by all signers; S completes the normal two-phase flow and self-signs B (`signed_self` set), broadcasting its own `Accepted`.
2. All other honest signers except P have already exchanged `BlockPreCommit` + `Accepted` with S earlier and will not resend anything further for B.
3. P, holding back its `BlockPreCommit` message, sends only `BlockResponse::Accepted(B)` to S at a point where P's weight is exactly what's needed to cross the 70% acceptance threshold.
4. On S: `handle_block_response` → `handle_block_signature` → `store_and_process_block_signature` stores P's signature via `add_block_signature` (success), then takes the branch at `stacks-signer/src/v0/signer.rs:2463-2466` because `has_committed(B, P)` is false, calling `handle_block_pre_commit`.
5. Inside `handle_block_pre_commit`, `block_info.signed_self.is_some()` is true (S already signed), so the function returns at line 1316-1321 without evaluating the acceptance/signature threshold.
6. `store_and_process_block_signature`'s tail (lines 2468-2537), which would have computed `total_signature_weight`, checked it against `min_weight`, called `mark_locally_accepted(true)`, and invoked `broadcast_signed_block`, is never reached for this event.
7. No further event recomputes the threshold for B on S, so S never pushes the fully-signed B to its node, even though the required signature weight (including P's now-stored signature) already exists in `signer_db`. [4](#0-3) [5](#0-4)

    /// Store the block acceptance signature and check if we have reached a consensus decision on the block because of it. If we have, update the block state accordingly and broadcast the block if accepted.
    fn store_and_process_block_signature(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        signer_address: &StacksAddress,
        signature: &MessageSignature,
    ) {
        let block_hash = &block_info.signer_signature_hash();
        // signature is valid! store it.
        // if this returns false, it means the signature already exists in the DB, so just return.
        if !self
            .signer_db
            .add_block_signature(block_hash, signer_address, signature)
            .unwrap_or_else(|_| panic!("{self}: Failed to save block signature"))
        {
            return;
        }

        // If this isn't our own signature and we haven't seen a pre-commit from this signer yet, try treating it as a pre-commit in case the caller is running an outdated version
        if signer_address != &self.stacks_address && !self.signer_db.has_committed(block_hash, signer_address).inspect_err(|e| warn!("Failed to check if pre-commit message already considered for {signer_address:?} for {block_hash}: {e}")).unwrap_or(false) {
            self.handle_block_pre_commit(stacks_client, sortition_state, signer_address, block_hash);
            return;
        }
