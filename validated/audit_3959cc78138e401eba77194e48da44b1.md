### Title
View-role/any-authenticated-role users can read `MinimumContractPayment` and `UseConnectionManager` bridge configuration via `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` - ([File: core/web/bridge_types_controller.go])

### Summary
The `Index` and `Show` handlers of `BridgeTypesController` are mounted in `core/web/router.go` without any role gate (`auth.RequiresEditRole`/`auth.RequiresRunRole`), unlike the `Create`/`Update`/`Destroy` routes on the same resource which are explicitly wrapped with `auth.RequiresEditRole`. Any session or API-token holder authenticated via `auth.Authenticate` — including accounts assigned only the `view` role — can therefore call these GET endpoints and receive the full `presenters.BridgeResource` JSON, which includes `MinimumContractPayment` and `UseConnectionManager`.

### Finding Description
`v2Routes` registers:
```go
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
authv2.GET("/bridge_types/:BridgeName", bt.Show)
authv2.PATCH("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Update))
authv2.DELETE("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Destroy))
```
The `authv2` group itself only enforces authentication (`auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`), not any specific role, so any authenticated principal — regardless of role — reaches `bt.Index`/`bt.Show`. Both handlers call `presenters.NewBridgeResource(bt)`, which populates `MinimumContractPayment` and `UseConnectionManager` from the underlying `bridges.BridgeType` model with no field-level redaction based on caller role. This is asymmetric relative to the explicit `auth.RequiresEditRole` wrapping applied to the mutating routes for the same resource, suggesting the read endpoints were intended to be similarly restricted (or at minimum, that the currently exposed fields were intended for edit/admin operators as implied by the audit question, though I found no repo documentation explicitly stating this scoping intent for GET routes — this is the main point of uncertainty).

### Impact Explanation
A low-privileged authenticated caller (view role or scoped API token) can enumerate all configured bridges and learn each bridge's `MinimumContractPayment` (LINK payment threshold) and `UseConnectionManager` flag. This is an information-disclosure issue: it does not by itself grant fund movement or write access, but it discloses operational/financial configuration that could inform targeted abuse (e.g., crafting job specs or external requests calibrated to the bridge's payment threshold). Impact is limited to disclosure of non-secret configuration values, not credentials or keys — `OutgoingToken`/`IncomingToken` are separate fields already present in the resource, but `IncomingToken` is only populated on `Create` (`omitempty`), so this specific question's tokens aren't the primary exposure; the concrete leak is `MinimumContractPayment`/`UseConnectionManager` as stated.

### Likelihood Explanation
Highly likely and trivially repeatable: any authenticated session (obtainable at `view` role) or valid API token can immediately call `GET /v2/bridge_types` or `GET /v2/bridge_types/:BridgeName` with no additional role check, as shown by the absence of `auth.RequiresEditRole`/`RequiresRunRole` wrapping in `core/web/router.go` lines 269 and 271, in contrast to lines 270, 272, 273.

### Recommendation
Decide the intended role scope for bridge configuration visibility. If `MinimumContractPayment`/`UseConnectionManager` are meant to be edit/admin-only, either (a) wrap `bt.Index`/`bt.Show` with `auth.RequiresEditRole` in `core/web/router.go`, or (b) keep the routes at current auth level but strip those fields from `presenters.BridgeResource` for callers below edit role (would require passing caller role into the presenter/controller). Given Chainlink's role model treats `view` as read-only for standard resources, restricting these GET routes to at least `RequiresEditRole`-equivalent (or documenting that bridge configuration, unlike jobs, is edit-tier-only viewable) is the consistent fix.

### Proof of Concept
Go handler-level integration test plan (using existing patterns from `core/web/bridge_types_controller_test.go` and `core/web/router_test.go`):
1. Set up a test app via `cltest.NewApplicationWithConfig`/`setupBridgeControllerTests` helper, create a bridge with non-zero `MinimumContractPayment` and `UseConnectionManager: true`.
2. Create a session/API client authenticated with `sessions.User{Role: sessions.UserRoleView}` (view role) using existing test helpers (`cltest.CreateUserWithRole` / similar in `core/web/router_test.go` / `core/sessions`).
3. Issue `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` with the view-role session cookie.
4. Assert HTTP 200 is returned (not 401/403) and that the parsed `presenters.BridgeResource` JSON contains non-zero/non-default `minimumContractPayment` and `useConnectionManager` fields.
5. Expected (fixed) behavior: either the request is rejected with 401/403 for view role, or the returned JSON omits/nulls these two fields for view-role callers — the current code fails this assertion because no role check exists on these routes.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
