### Title
Non-atomic supply computation in `getSupply` can return inconsistent circulating supply or panic on subtraction underflow - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_supply` computes `non_circulating_supply` and `total_supply` from the same `Arc<Bank>` handle but at two different points in time, without holding the bank in a frozen/consistent state across both reads. Because `non_circulating_supply` is derived from a background scan (`spawn_blocking`) that can take a non-trivial amount of time, and `total_supply` (`bank.capitalization()`) is read only after that scan completes, the two values can reflect different, non-matching states of the same working bank if a `processed`/`confirmed` commitment is requested. This mirrors the reported Flayer bug class of "recording a quorum/aggregate value, then mutating state that the aggregate depended on, before combining them," where the mutation invalidates the earlier snapshot and produces an inconsistent derived result.

### Finding Description
`get_supply` in [1](#0-0)  does:
1. `let bank = self.bank(config.commitment);` — for non-finalized commitment levels this can be the actively mutating working bank rather than a frozen bank.
2. `calculate_non_circulating_supply(&bank)` is dispatched to a blocking thread pool and scans stake-program accounts and a fixed non-circulating address list, summing `bank.get_balance(pubkey)` for each account at whatever point during the scan the individual account reads occur, per [2](#0-1) .
3. Only after this scan returns does the code call `bank.capitalization()` to get `total_supply`, and compute `circulating: total_supply - non_circulating_supply.lamports` with a plain (unchecked) `u64` subtraction, as seen at [3](#0-2) .

Because the working bank is not frozen between steps 2 and 3 for non-finalized commitment levels, transactions can continue to be processed concurrently on that same bank while the scan runs. This means `non_circulating_supply.lamports` can reflect an "old" or "new" state that is inconsistent with the `capitalization()` value read afterward — analogous to the reported bug where `params.quorumVotes` (an aggregate value) is fixed based on a state that a subsequent mutation (`sunsetCollection`'s burn) then changes, producing a mismatched derived output (`claim amount`).

### Impact Explanation
If `non_circulating_supply.lamports` (computed from a stale/inconsistent snapshot of individual account balances collected over time) ends up larger than the `total_supply` captured afterward — e.g., because lamports moved into a non-circulating/locked stake account or one of the hardcoded non-circulating pubkeys during the scan window, while `capitalization()` decreased in the interim due to a burn or rent-collection event — the unchecked subtraction `total_supply - non_circulating_supply.lamports` can underflow. Depending on the build profile this either wraps to a huge `u64` value (silently returning wildly wrong "circulating supply" data to any RPC client — a "wrong data returned" outcome) or panics the validator process (crash) if overflow checks are enabled for that build. Either way, this is triggerable by a single unprivileged `getSupply` JSON-RPC call, with no special role required.

### Likelihood Explanation
The scan in `calculate_non_circulating_supply` walks all stake-program accounts (or an index of them) via `get_filtered_indexed_accounts`/`get_program_accounts`, which is not instantaneous on a busy validator, so there is a realistic window during which the working bank continues to be mutated by ongoing transaction processing when `processed` or `confirmed` commitment is requested (the default for many RPC clients is not `finalized`). This does not require adversarial account crafting, additional RPC calls beyond one, or multiple clients — a single `getSupply` call at the right moment is sufficient to observe the inconsistency described.

### Recommendation
Ensure both values used to compute circulating supply are derived from a single, immutable point-in-time view of the bank: use `bank.capitalization()` (or an equivalently snapshotted total) recorded before or atomically with the scan, and use `checked_sub`/`saturating_sub` for the `circulating` computation so an inconsistency between the two values cannot cause a panic or an unsigned overflow wraparound. If precise consistency is required, prefer computing supply figures only against frozen/rooted banks, or snapshot `bank.capitalization()` immediately alongside the accounts snapshot used by the scan.

### Proof of Concept
Not independently reproduced (would require a running cluster with realistic transaction throughput timed against a `getSupply` call at `processed`/`confirmed` commitment to force a scan-window race); the code path and unchecked subtraction are confirmed directly in [1](#0-0)  and [2](#0-1) . Whether the validator's release build enables `overflow-checks` (which would turn the wraparound into a panic/crash) could not be conclusively confirmed within the available search; this should be verified against the actual build profile configuration before relying on the crash variant of this impact.

    async fn get_supply(
        &self,
        config: Option<RpcSupplyConfig>,
    ) -> RpcCustomResult<RpcResponse<RpcSupply>> {
        let config = config.unwrap_or_default();
        let bank = self.bank(config.commitment);
        let non_circulating_supply =
            self.calculate_non_circulating_supply(&bank)
                .await
                .map_err(|e| RpcCustomError::ScanError {
                    message: e.to_string(),
                })?;
        let total_supply = bank.capitalization();
        let non_circulating_accounts = if config.exclude_non_circulating_accounts_list {
            vec![]
        } else {
            non_circulating_supply
                .accounts
                .iter()
                .map(|pubkey| pubkey.to_string())
                .collect()
        };

        Ok(new_response(
            &bank,
            RpcSupply {
                total: total_supply,
                circulating: total_supply - non_circulating_supply.lamports,
                non_circulating: non_circulating_supply.lamports,
                non_circulating_accounts,
            },
        ))
    }

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}
