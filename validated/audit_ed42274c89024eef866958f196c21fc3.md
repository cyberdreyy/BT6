## Title
Stale confirmations from removed multisig members allow request execution below the live confirmation threshold - (File: multisig2/src/lib.rs, also multisig/src/lib.rs)

### Summary
When a multisig member is removed via `DeleteMember` (or `DeleteKey` in the v1 `multisig` contract), the cleanup logic only purges pending **requests that the removed member itself created**. It never scans the `confirmations` map for requests created by *other* members that the removed member had already confirmed. Those stale confirmations remain counted toward `num_confirmations`, so a request can later be executed with fewer live-member confirmations than the configured threshold requires.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` cleans up only requests whose `member` field (the creator) equals the member being removed: [1](#0-0) 

Note the filter is `r.member == member`, i.e. it matches the request *creator*, not confirmers. It does not touch `self.confirmations`, which is a separate `LookupMap<RequestId, HashSet<String>>` keyed independently of request ownership: [2](#0-1) 

The confirmation-counting logic in `confirm` simply compares the size of this (possibly stale) `HashSet` against `num_confirmations`: [3](#0-2) 

Because a confirmation entry from a member who has since been deleted is never purged from requests they didn't author, that entry keeps contributing to the "confirmations vs. live members" count. This breaks the intended invariant `confirmations_from_live_members >= num_confirmations` that the K-of-N scheme is supposed to enforce — instead the actual check becomes `confirmations_ever_recorded >= num_confirmations`, which can be satisfied by fewer currently-authorized signers than required.

The identical defect exists in the original `multisig/src/lib.rs`'s `DeleteKey` action, which also only removes requests created by the deleted key, not confirmations that key placed on other members' requests: [4](#0-3) 

### Impact Explanation
This allows a multisig `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. request to execute with fewer effective (live) confirmations than `num_confirmations`, i.e. a **multisig request executed below threshold** — explicitly listed as a Critical-severity custody-binding break. Funds can move, or contract state can change (e.g. deploying new code, adding a full-access key), authorized by a smaller quorum than the multisig's documented security model guarantees.

### Likelihood Explanation
This requires a realistic and even routine multisig lifecycle event: a member is removed (e.g., because their key is thought compromised, or they leave the organization) after having already confirmed one or more still-pending requests. No malicious insider collusion beyond normal multisig operation is needed — it's a natural ordering of legitimate actions (confirm, then later remove a member, then further confirms) rather than an out-of-band privilege abuse. Any multisig with more than `num_confirmations` members and any pending, not-yet-fully-confirmed request is exposed.

### Recommendation
When removing a member (`DeleteMember`/`DeleteKey`), iterate over **all** pending requests' confirmation sets (not just those the member created) and strip the removed member's entry, or alternatively re-validate at execution time that every confirming identity in the `HashSet` is still present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and members `{A, B, C, D}`.
2. `A` calls `add_request` to create request `X` (e.g. `Transfer` to an attacker-controlled or third-party account).
3. `B` calls `confirm(X)` → confirmations = `{B}` (count 1).
4. `C` calls `confirm(X)` → confirmations = `{B, C}` (count 2, below threshold, request stays pending).
5. Separately, members confirm and execute a `DeleteMember { member: C }` request (a normal admin action, e.g. because `C`'s key is thought compromised). `delete_member` runs; since `X` was created by `A`, not `C`, `X` and its confirmation set `{B, C}` are left untouched — see [5](#0-4) .
6. `D` calls `confirm(X)` → confirmations = `{B, C, D}`, size 3 `>= num_confirmations (3)` → `execute_request` fires per [6](#0-5) .
7. Request `X` executes (e.g. transfers funds) with confirmations from only 2 currently-live members (`B`, `D`) plus a stale confirmation from removed member `C`, bypassing the intended 3-of-N live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
