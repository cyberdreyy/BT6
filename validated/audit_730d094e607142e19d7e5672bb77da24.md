## Finding

The chainlink-node analog to the PythOracle `commitRequested()`/`commit()` race lives in the gateway's HTTP trigger handler, where the "already used" guard is checked against a single global map keyed only on a caller-supplied `requestID`, without any binding to the specific workflow or caller that "owns" that ID.

### Title
Cross-user request-ID squatting in gateway HTTP trigger handler causes legitimate workflow triggers to be rejected - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
`httpTriggerHandler` stores in-flight requests in a single process-wide map `callbacks map[string]savedCallback` keyed purely by the client-supplied JSON-RPC `id` (`requestID`), shared across *all* workflows and *all* callers hitting the gateway node [1](#0-0) . `setupCallback` rejects any request whose `requestID` is already present in that map, regardless of which workflow or owner it belongs to [2](#0-1) .

### Finding Description
The request pipeline in `HandleUserTriggerRequest` performs, in order: request-shape validation, workflow-ID resolution, `authorizeRequest` (which only verifies the caller is authorized for *the workflow they specified*, not the one the eventual victim will use), rate-limit check, and only then `setupCallback`, which does the duplicate-ID check [3](#0-2) .

Because `authorizeRequest` only validates authorization for the workflow named in *that* request (`h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)`, line 363), an unprivileged caller does not need any relationship to a victim's workflow to claim a given `requestID` — they only need to be a valid caller for *some* workflow they control. If they submit a request using the same `id` value that a victim is about to (or will) use for their own, unrelated workflow execution, the map collision at line 402 causes the victim's subsequent legitimate request to be rejected with `jsonrpc.ErrConflict` and the message `"requestID: %s has already been used..."` [4](#0-3) .

This is structurally identical to the Pyth bug: two logically independent operations (different workflows/owners) share one mutable guard state (`lastCommittedPublishTime` in Pyth vs. the global `callbacks` map here) keyed on a value that either party can supply, and whichever party updates it first blocks the other's legitimate operation.

### Impact Explanation
An unprivileged, unrelated caller can deny a legitimate user's workflow trigger by pre-claiming (front-running) the same `requestID`, without needing authorization for the victim's workflow. This is a targeted denial-of-service against a specific execution request if the victim's `requestID` is predictable, observable, or reused (e.g., client libraries or automation using deterministic/sequential IDs), and can be used to selectively block time-sensitive workflow executions triggered via HTTP.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be an authorized caller for any workflow of their choosing (a low bar — anyone with an authorized workflow), and (2) the attacker be able to guess/observe the victim's chosen `requestID` before the victim's request lands (feasible when IDs are not cryptographically random, e.g., sequential counters, timestamps, or IDs echoed/observable via other channels). This is comparable to the "borderline low/medium" severity assessed for the original Pyth issue, since it interferes with legitimate operations without directly stealing funds/secrets.

### Recommendation
Scope the in-flight request de-duplication key by `(workflowID, requestID)` (or `(workflowOwner, workflowID, requestID)`) instead of `requestID` alone, so that request-ID collisions can only occur within the same workflow/owner namespace, mirroring the recommended Pyth fix of validating conflicts against the specific version/index the caller is entitled to affect rather than a globally shared state.

### Proof of Concept
1. Attacker registers/owns Workflow A and is a valid authorized caller for it.
2. Attacker predicts or observes that Victim (owner of unrelated Workflow B) will submit a `workflows.execute` gateway HTTP-trigger request with JSON-RPC `id = "X"`.
3. Attacker sends their own valid request for Workflow A using `id = "X"` first; `setupCallback` inserts `callbacks["X"]` [5](#0-4) .
4. Victim's legitimate request for Workflow B with `id = "X"` then hits `setupCallback`, finds `"X"` already present, and is rejected with `jsonrpc.ErrConflict` before ever being dispatched to any DON node [4](#0-3) .

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
