### Title
Dust queued deposit after the prefunding cutoff permanently bricks `stopEpochWithDuration`, freezing all vault funds at the borrower - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
In the prefunded CDO variant, `IdleCDOEpochQueue.prefundedDepositsToProcess()` hard-reverts whenever `epochPendingDeposits[epoch] != 0`, because raw underlyings must not remain in the queue when the epoch is settled [1](#0-0) . However `requestDeposit()` only checks `_checkAllowed` — epoch running + Keyring KYC — with no cutoff relative to `epochEndDate` [2](#0-1) . The cutoff (`prefundedDepositWindow`) is enforced only in `processDepositsToBorrower()`, the manager-called function that moves queued funds to the borrower [3](#0-2) . A KYC-passing attacker can therefore deposit 1 wei of underlying late in the epoch, after the prefunding cutoff, leaving a stranded `epochPendingDeposits` balance that makes the prefunded stop path revert forever. This is the analog of the MariaDB `Field::set_default` DoS: a cheap, unprivileged crafted input (a dust deposit) that makes a critical state-transition function permanently fail.

### Finding Description
Sequence:

1. Epoch N is running in a prefunded-variant deployment (`epochQueue()` enabled on `IdleCDOEpochVariantPrefunded`).
2. Honest users' queued deposits for epoch N+1 have been prefunded via `processDepositsToBorrower()` before the cutoff, so `epochPrefundedDeposits[N+1] > 0` and `epochPendingDeposits[N+1] == 0` [4](#0-3) .
3. Attacker (KYC-passing lender — in the allowed threat model) calls `queue.requestDeposit(1)`. `_checkAllowed` passes because the epoch is still running, so `epochPendingDeposits[N+1] = 1` and the queue holds 1 wei of underlying [5](#0-4) .
4. After `epochEndDate`, the manager calls `stopEpochWithDuration`. On the prefunded variant this settles through `prefundedDepositsToProcess()`, which calls `_prefundedEpochToProcess` and then `_checkNotAllowed(epochPendingDeposits[_epoch] != 0)` → `revert NotAllowed()` [6](#0-5) .
5. There is no permissionless recovery: `processDepositsToBorrower` cannot re-run for the same epoch (`epochPrefundedDeposits[_epoch] != 0` check at line 168) and is also past its own cutoff; `deleteRequest` lets only the attacker pull their own dust. The epoch can never be stopped.

Broken invariant: epoch liveness / solvency of the state machine. A single dust deposit permanently blocks the stop transition, so `epochNumber` never advances, `isEpochRunning` stays true, `allowAA/BBWithdrawRequest` stay false [7](#0-6) , and all LP principal remains locked at the borrower.

### Impact Explanation
Permanent freezing of all vault funds: no depositor can withdraw because withdrawals require epoch transitions, and the borrower-side principal can never be recalled through `stopEpoch(0, 1)` close-pool mode either, since the same prefunded settlement path is invoked. Cost to the attacker is 1 wei of underlying plus gas. Loss is 100% of pool TVL (frozen, not stolen).

### Likelihood Explanation
Requires only a KYC-passing wallet (explicitly in the attacker model) and a prefunded-variant deployment with the AA queue enabled. No privileged collusion, no oracle manipulation, no timing race — the deposit can be made any time between the prefunding cutoff and `epochEndDate`. The main caveat I could not fully verify within this iteration is the exact call site in `IdleCDOEpochVariantPrefunded.sol` that invokes `prefundedDepositsToProcess` during `stopEpochWithDuration` (grep confirms the variant references it), and whether a fallback settlement path exists for the stranded queue balance; if such a fallback exists, impact degrades to temporary freezing.

### Recommendation
Apply the same cutoff to `requestDeposit` that `processDepositsToBorrower` enforces: revert in `_checkAllowed`/`requestDeposit` when `prefundedDepositWindow != 0 && block.timestamp + prefundedDepositWindow >= epochEndDate`, or whenever `epochPrefundedDeposits[nextEpoch] != 0`. Alternatively, let `prefundedDepositsToProcess` sweep residual pending deposits into the prefunded bucket (or refund them to depositors) instead of reverting.

### Proof of Concept
Foundry fork PoC sketch (based on `test/foundry/IdleCDOEpochVariantPrefunded.t.sol` harness):

```solidity
// Setup: prefunded variant + AA queue, epoch running, PREFUNDED_DEPOSIT_WINDOW set
queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);
_requestDepositWithUser(user, 10_000e6);              // honest depositor
_enterPrefundedWindow(PREFUNDED_DEPOSIT_WINDOW);
vm.prank(manager);
queue.processDepositsToBorrower();                     // epochPrefundedDeposits > 0, pending == 0

// Attack: KYC'd attacker queues 1 wei after the cutoff but before epochEndDate
address attacker = makeAddr("attacker");               // assumed Keyring-allowed
deal(address(underlying), attacker, 1);
vm.startPrank(attacker);
underlying.approve(address(queue), 1);
queue.requestDeposit(1);                               // succeeds: only _checkAllowed gate
vm.stopPrank();
assertEq(queue.epochPendingDeposits(strategy.epochNumber() + 1), 1);

// Warp past epoch end and repay borrower dues
vm.warp(cdoEpoch.epochEndDate() + 1);
uint256 toRepay = cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws();
deal(address(underlying), borrower, toRepay);
vm.prank(borrower);
underlying.approve(address(cdoEpoch), toRepay);

// stopEpochWithDuration reverts forever via prefundedDepositsToProcess
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(apr, 0, duration, 0);
// Repeat at any later timestamp: still reverts -> epoch permanently unstoppable,
// all LP funds frozen at borrower.
```
