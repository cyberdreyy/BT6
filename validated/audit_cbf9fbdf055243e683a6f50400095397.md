### Title
Stale rejection weight from a flipped signer vote lets `SignerCoordinator`/`StackerDBListener` wedge a block that already has enough approvals - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The miner-side `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block using two independently-guarded accumulators. When a signer legitimately changes its vote from `Rejected` to `Accepted` for the same block (an explicitly supported transition, `LocallyRejected --> LocallyAccepted : re-evaluated`), the previously-added rejection weight is never subtracted, so it permanently pollutes `total_weight_rejected` even after the signer's real, current vote is `Accepted`. `SignerCoordinator::get_block_status` checks the rejection threshold before the approval threshold, so this stale weight can cause the coordinator to declare a block globally rejected (`SignersRejected`) even though the same or a genuinely larger set of signers, by weight, has actually approved it.

### Finding Description
Signature and rejection tallies are stored in a shared `BlockStatus` guarded by two independent structures: [1](#0-0) 

For a `BlockResponse::Accepted`, the weight is only added if the slot isn't already in `gathered_signatures`: [2](#0-1) 

For a `BlockResponse::Rejected`, the weight is only added if the slot isn't already in `responded_signers`: [3](#0-2) 

These two guards check two *different* maps/sets and neither branch clears or adjusts the other side's accumulator. Concretely:

1. Signer S rejects first: `responded_signers.insert(S)` succeeds → `total_weight_rejected += w_S`.
2. Signer S later re-evaluates (as `docs/signer-flows.md`'s documented `LocallyRejected --> LocallyAccepted : re-evaluated` transition allows) and sends `Accepted`. Since `gathered_signatures` never contained S's slot, the guard passes → `total_weight_approved += w_S`.
3. `total_weight_rejected` is never decremented for S. It permanently retains `w_S` even though S's live, current vote is Accept.

This breaks the accounting invariant that a signer's weight should count on at most one side of the tally at any given time (the report's analogous "using stale amount instead of remaining/current amount" root cause). `total_weight_approved + total_weight_rejected` can now exceed `total_weight`, and — more importantly — the stale rejected weight can push `total_weight_rejected` over the blocking-minority threshold on its own.

`SignerCoordinator::get_block_status` checks the reject condition *before* the approve condition each polling iteration: [4](#0-3) 

So if enough signers flip Reject→Accept such that the stale `total_weight_rejected` (containing weight from signers who have since switched to Accept) crosses `total_weight - weight_threshold`, the coordinator returns `NakamotoNodeError::SignersRejected` and drops the block — even in a state where the real, current approval weight (including the flipped signers) already meets or exceeds the 70% signing threshold. `reset_rejections` only clears this on a proposal timeout/retry, not on a per-signer vote flip within the same proposal round, so this stale accounting is not otherwise corrected: [5](#0-4) 

Notably, `stacks-signer/CHANGELOG.md` records that the analogous double-count between acceptance/rejection tallies for the *same signer/block* was fixed for the signer's own internal bookkeeping ("Do not count both a block acceptance and a block rejection for the same signer/block"), confirming this bug class was recognized and patched elsewhere, but the equivalent cross-check is absent from the node-side coordinator's `StackerDBListener` tally: [6](#0-5) 

### Impact Explanation
This is a liveness wedge on the node/coordinator side: a validly, currently-signed block (meeting the real 70% weight threshold) can be thrown away by the miner's coordinator due to stale rejection weight from signers who have since reconsidered and approved. The miner then must reattempt a new block/tenure, degrading throughput and potentially repeating if the same flip pattern recurs across proposals in a tenure. This matches the "wedged into never signing valid blocks" class of impact, applied to the coordinator that gatekeeps whether a genuinely-approved block gets pushed to the node.

### Likelihood Explanation
Requires only a single signer (no majority) to change its vote from Reject to Accept for the same block proposal within one coordination round — a scenario explicitly supported and tested elsewhere in the codebase (`LocallyRejected --> LocallyAccepted : re-evaluated`, and tests such as `signers_reprocess_bitcoin_block_not_found_proposals` and `signers_do_not_reconsider_globally_accepted_and_responded_blocks` exercise reconsideration flows). No majority collusion or privileged access is required; a single flipping signer combined with pre-existing rejections from other signers already crossing the blocking-minority threshold is sufficient.

### Recommendation
In `StackerDBListener`'s message handling, make the `Accepted` and `Rejected` branches mutually exclusive per signer by checking/clearing the opposite side's weight when a vote flips: track a per-signer "last verdict" (accept/reject) instead of two independently-guarded sets, and when a signer's verdict changes, subtract their weight from the stale side's total before adding it to the new side's total (or simply recompute both totals fully from the current per-signer verdict map each time, rather than incrementally accumulating deltas).

### Proof of Concept
1. Assume `total_weight = 100`, `weight_threshold = 70` (min_weight for 70%), signers A(40), B(30), C(30).
2. A rejects: `total_weight_rejected = 40`. B, C not yet responded.
3. `SignerCoordinator::get_block_status` reject-check: `40 + 70 = 110 > 100` → true! This alone can already trigger `SignersRejected` prematurely if A's 40 alone exceeds the blocking minority (30), well before B/C respond — demonstrating the check does not require a true 30%+ rejecting *set*, just enough weight from a single signer's rejection.
4. Now suppose weights are A(20), B(20), C(60), threshold 70 (min needed), blocking minority 30. A and B reject (`total_weight_rejected = 40`, exceeding 30 minority) → coordinator returns `SignersRejected` at that point even though C alone (60) plus a reconsidered A or B could reach 70.
5. If A subsequently re-evaluates and sends `Accepted` before the coordinator's next poll, `total_weight_approved` becomes `20 (A) + 60 (C, if already accepted) = 80 ≥ 70`, satisfying real consensus — yet `total_weight_rejected` still holds A's stale 40 (only B's 20 should remain), and depending on poll timing the reject branch (checked first) can still fire, discarding a block that has legitimate 70%+ approval.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
