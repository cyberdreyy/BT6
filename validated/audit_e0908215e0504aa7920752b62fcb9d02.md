### Title
Permanent ETH Fund Lock When Bridge Recipient Contract Lacks `receive`/`fallback` — (File: `bridge/evm/contracts/BridgeVault.sol`)

---

### Summary

`BridgeVault.transferETH` delivers unwrapped native ETH to the EVM recipient via a raw `call{value}`. If the recipient is a smart contract without a `receive()` or `fallback()` function, every attempt to settle the bridge transfer reverts. Because the corresponding ETH coins were already burned on Sui and the bridge message is immutable once validator-signed, the WETH remains permanently locked in the vault with no on-chain recovery path.

---

### Finding Description

The Sui native bridge's EVM-side settlement path for ETH transfers is:

**`SuiBridge._transferTokensFromVault` → `BridgeVault.transferETH`**

```
// SuiBridge.sol line 256-257
if (tokenID == BridgeUtils.ETH) {
    vault.transferETH(payable(recipientAddress), amount);
```

Inside `BridgeVault.transferETH` (lines 52–64):

```solidity
function transferETH(address payable recipientAddress, uint256 amount)
    external override onlyOwner nonReentrant
{
    wETH.withdraw(amount);                                    // line 59 – unwrap WETH → ETH
    (bool success,) = recipientAddress.call{value: amount}(""); // line 62 – push ETH
    require(success, "ETH transfer failed");                  // line 63 – revert on failure
}
```

The same pattern is replicated verbatim in `SuiBridgeV2._transferTokensFromVault` (line 201) for V2 messages.

`BridgeVault` itself has a `receive()` function (line 68) to accept ETH from the WETH contract during `wETH.withdraw`. However, **neither `SuiBridge` nor `SuiBridgeV2` has a `receive()` or `fallback()` function**, and more critically, **no guard validates that `recipientAddress` can accept native ETH**.

The `recipientAddress` is the EVM address the user encoded when calling `send_token` / `send_token_v2` on Sui. It is embedded in the bridge message, signed by the validator committee, and is immutable thereafter. If that address is a smart contract without a `receive()` or `fallback()` function (e.g., a DAO treasury, a custom multisig, a protocol contract), then:

1. `recipientAddress.call{value: amount}("")` returns `success = false`.
2. `require(success, "ETH transfer failed")` reverts the entire transaction.
3. `isTransferProcessed[message.nonce]` is **never set to `true`**.
4. Every subsequent retry of `transferBridgedTokensWithSignatures` / `transferBridgedTokensWithSignaturesV2` hits the same revert.
5. The WETH remains in the vault indefinitely; there is no admin function to redirect or recover it.

---

### Impact Explanation

**Permanent fund lock (High/Medium).**

On the Sui side, `bridge::send_token` burns the user's ETH coin object unconditionally before emitting the deposit event. That burn is irreversible. On the EVM side, the WETH is held in `BridgeVault` but can never be transferred to the intended recipient. The bridge nonce is never marked processed, so the message cannot be replayed to a different address. The contract is upgradeable in principle, but recovery requires a privileged governance upgrade — outside the ordinary-user attacker model and not guaranteed.

The user loses the full bridged ETH amount with no recourse.

---

### Likelihood Explanation

**Medium-low.** Most users specify EOA addresses. However, a meaningful subset of bridge users are protocols, DAOs, or multisig treasuries that specify a contract address as the EVM recipient. Many modern multisigs (Gnosis Safe) do have `receive()`, but custom contracts, proxy shells, or older multisigs often do not. A single such transfer permanently locks the funds.

---

### Recommendation

1. **Use WETH instead of native ETH for delivery.** Replace the `wETH.withdraw` + raw `call{value}` pattern with a direct `SafeERC20.safeTransfer(wETH, recipientAddress, amount)`. Any contract can receive an ERC-20 transfer; no `receive()` function is required. This is the safest fix.

2. **Alternatively, wrap-and-transfer with a pull model.** Keep WETH in the vault and let the recipient call a `claimWETH(nonce)` function, eliminating the push-ETH failure mode entirely.

3. **At minimum, document the restriction** that EVM recipient addresses for ETH bridges must be EOAs or contracts with a `receive()` / `fallback()` function, and enforce this with an off-chain warning in the bridge UI.

---

### Proof of Concept

**Step 1 – Deploy a no-receive contract on Ethereum:**
```solidity
contract NoReceive {
    // no receive() or fallback()
    function doNothing() external {}
}
```

**Step 2 – Bridge ETH from Sui to `NoReceive`:**
On Sui, call:
```move
bridge::send_token<ETH>(bridge, ETH_CHAIN_ID, no_receive_address_bytes, eth_coin, ctx);
```
This burns `eth_coin` and emits `TokenDepositedEvent`. The burn is irreversible.

**Step 3 – Validators sign; anyone calls settlement on EVM:**
```solidity
suiBridge.transferBridgedTokensWithSignatures(signatures, message);
// Internally: vault.transferETH(payable(noReceiveAddr), amount)
// → wETH.withdraw(amount) succeeds
// → noReceiveAddr.call{value: amount}("") returns (false, "")
// → require(success) REVERTS
// isTransferProcessed[nonce] remains false
```

**Step 4 – Every retry reverts identically.** The WETH is permanently locked in `BridgeVault`. The user's Sui ETH is gone.

        address tokenAddress = committee.config().tokenAddressOf(tokenID);

        // Check that the token address is supported
        require(tokenAddress != address(0), "SuiBridge: Unsupported token");

        // transfer eth if token type is eth
        if (tokenID == BridgeUtils.ETH) {
            vault.transferETH(payable(recipientAddress), amount);
        } else {
            // transfer tokens from vault to target address
            vault.transferERC20(tokenAddress, recipientAddress, amount);
        }

        // update amount bridged
        limiter.recordBridgeTransfers(sendingChainID, tokenID, amount);
    }
