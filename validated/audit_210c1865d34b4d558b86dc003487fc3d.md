### Title
Stale instant-withdraw per-epoch records inflate the default claim basis, diluting and freezing default-recovery payouts - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays the aggregate `instantWithdrawsRequests[_user]` at par but never clears the per-epoch bookkeeping (`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`). These stale entries are later dereferenced by `finalizeDefaultRecovery` (via `defaultPendingClaimBasis` / `_defaultPrefundedInstantReserve`) and by `_claimDefaultedInstantWithdrawRequest`, exactly like the Ledger bug: state is logically freed on claim but still pointed to by the default-finalization path, corrupting recovery accounting for all claimants.

### Finding Description
The normal-claim path only clears the aggregate receipt: [1](#0-0) 

The per-epoch entries written in `requestInstantWithdraw` remain: [2](#0-1) 

At default finalization those stale entries are still counted:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever any unfunded instant remainder exists.
- `_defaultPrefundedInstantReserve` returns `instantBasis - pendingInstant`, treating already-paid-out receipts as underlying still held by the strategy.
- `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch entry and computes `instantWithdrawsRequests[_user] -= claimBasis`, which underflows (user's aggregate is already 0), so the stale basis can never be claimed — its reserve share is permanently stranded.

### Impact Explanation
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed on a `totalBasis` inflated by already-paid instant receipts. Every legitimate defaulted-epoch claimant and every active LP (via the `_burn`/`_mint` NAV adjustment at lines 699-705) receives a proportionally smaller payout.
- `prefundedReserve` is overstated by the same stale amount, so `defaultRecoveryReserve` is booked higher than the strategy's real token balance. Once real tokens run out, `_transferDefaultRecovery` reverts, permanently freezing the tail of the recovery reserve.
- Quantified loss: if an attacker got X paid out via instant withdrawal in the default epoch and totalBasis is T, all other claimants lose `X/T` of their recovery, and `X * recoveryPrice` of reserve is unclaimable forever.

### Likelihood Explanation
Requires: (1) instant mode enabled with `instantDelay` such that an instant request is funded and claimed in the same epoch; (2) at least one other unfunded instant receipt (`pendingInstantWithdraws != 0`) at finalization; (3) a borrower default before the epoch ends. The attacker is an ordinary KYC'd lender — no privilege needed. The attacker does not even profit directly; this is a griefing/insolvency vector where already-paid receipts silently poison the recovery waterfall.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records the same way `_clearWithdrawClaimForEpoch` does for normal receipts: zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (and any older per-epoch entries) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, so finalization only counts genuinely outstanding receipts.

### Proof of Concept
Foundry fork scenario (modelled on `test/foundry/IdleCDOEpochQueue.t.sol` instant-withdraw tests):

```solidity
// setup: instant mode vault, epoch running
// 1. attacker requests instant withdraw, victim requests instant withdraw
cdoEpoch.requestInstantWithdraw(ATTACKER_AMOUNT, attacker);
cdoEpoch.requestInstantWithdraw(VICTIM_AMOUNT, victim);

// 2. manager funds only attacker's request (or both, then attacker claims first)
skip(instantDelay + 1);
// CDO collects funds; pendingInstantWithdraws decreased by funded amount
strategy.collectInstantWithdrawFunds(ATTACKER_AMOUNT); // via CDO
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest(attacker); // paid at par
// attacker per-epoch records remain set:
assertGt(strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()), 0);
assertGt(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0);

// 3. borrower defaults; victim's instant receipt still pending
// finalizeDefaultRecovery counts attacker's stale basis:
uint256 basis = strategy.defaultPendingClaimBasis();
// basis includes VICTIM (correct) + ATTACKER's already-paid amount (stale)
// -> recoveryPrice lower than justified; recoveryReserve booked > real balance

// 4. last claimant's _transferDefaultRecovery reverts / attacker-stranded share never paid
```

The assertion that `instantWithdrawClaimsByEpoch` still includes the claimed amount after `claimInstantWithdrawRequest` demonstrates the dangling state; the inflated `defaultPendingClaimBasis` demonstrates the accounting corruption.
