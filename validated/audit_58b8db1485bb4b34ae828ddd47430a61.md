### Title
Unbounded `mint_decimals` can panic the risk engine and permanently freeze a bank - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
`calc_value` and `calc_amount`, the core functions used by the risk engine to price a bank's asset/liability amounts, index into the fixed-size `EXP_10_I80F48` lookup table using `mint_decimals` without any bounds check. `EXP_10_I80F48` only has 24 entries (10^0..10^23). If a bank's underlying mint has `mint_decimals >= 24`, this indexing panics instead of returning a graceful error, which is the same underlying bug class as the reported "hardcoded decimals assumption" issue (in the report, hardcoded 18-decimal assumption produced an underflow/revert; here, a hardcoded ≤23-decimal assumption produces an out-of-bounds panic).

### Finding Description
`calc_value` and `calc_amount` compute the scaling factor as: [1](#0-0) [2](#0-1) 

Both directly do `EXP_10_I80F48[mint_decimals as usize]`, with `EXP_10_I80F48` defined with only `MAX_EXP_10_I80F48 = 24` entries in the drift-mocks constants module (mirrored by an equivalent table used across the program) [3](#0-2) . `mint_decimals` is a `u8` field on `Bank`, so its value can range 0–255; the code comment even states the invariant "Must be < 24" but this is documentation only, not an enforced check [4](#0-3) .

By contrast, the codebase does have a helper (`convert_decimals`) that explicitly guards against this same class of failure by returning `None` when `abs > 23` instead of indexing blindly [5](#0-4) , and drift-specific bank creation explicitly checks `bank_mint.decimals as u32 <= DRIFT_PRECISION_EXP` before creating a bank [6](#0-5) . However, the generic bank-creation paths I inspected — `lending_pool_add_bank` (standard banks) and `lending_pool_add_bank_permissionless` — construct `Bank::new(...)` directly from `bank_mint.decimals` with no equivalent upper-bound validation on decimals before calling `bank.config.validate()` [7](#0-6) [8](#0-7) . I was unable to fully confirm whether `bank.config.validate()` (defined in `programs/marginfi/src/state/bank_config.rs`, which I could not fully read before running out of tool budget) performs a decimals bound check — this is an open verification gap.

If such a bank is created (SPL Token-2022 mints can be configured with up to 19 decimals typically, but the underlying field is a `u8` so a malicious/misconfigured mint with `decimals >= 24` is not intrinsically impossible depending on what validation exists elsewhere), any subsequent call into the risk engine (deposit, withdraw, borrow, liquidate) that reaches `calc_value`/`calc_amount` for that bank would panic due to out-of-bounds array indexing.

### Impact Explanation
A panic in `calc_value`/`calc_amount` aborts the transaction, and because these functions are on the critical path of essentially all user-facing actions (deposits, withdrawals, borrows, liquidations, health checks), a bank with an out-of-range `mint_decimals` would become permanently unusable — funds already deposited into such a bank could become frozen/inaccessible, matching the class of "asset made unusable due to calculations always failing" described in the external report. This is a durable freeze with financial effect on any user who managed to deposit into such a bank before the freeze condition was hit.

### Likelihood Explanation
Likelihood depends entirely on whether `bank.config.validate()` or another gate enforces `mint_decimals < 24` before a bank is created — a check I could not fully confirm to exist in the generic (non-integration) bank-creation instructions given tool-call limits. If no such gate exists, admin bank creation (which is admin-only for the standard path) or the permissionless bank-creation path (which is more attacker-reachable) could create a bank for a mint with 24+ decimals, directly triggering this condition on first use.

### Recommendation
Explicitly validate `mint_decimals < MAX_EXP_10_I80F48` (24) in `bank.config.validate()` and/or immediately in every `lending_pool_add_bank*` instruction (mirroring the pattern already used for Drift banks with `DriftUnsupportedTokenDecimals`), returning a proper `MarginfiError` instead of allowing an unchecked array index that can panic in `calc_value`/`calc_amount`.

### Proof of Concept
Not independently reproduced in this session — reproducing would require verifying `bank.config.validate()`'s exact checks (not fully read) and then attempting `lending_pool_add_bank`/`lending_pool_add_bank_permissionless` with a mint configured with `decimals >= 24`, followed by any deposit/withdraw/borrow call that invokes `calc_value` or `calc_amount` for that bank, to confirm the out-of-bounds panic. This is flagged as unverified/uncertain pending that confirmation.

#[inline]
pub fn calc_amount(value: I80F48, price: I80F48, mint_decimals: u8) -> MarginfiResult<I80F48> {
    let scaling_factor = EXP_10_I80F48[mint_decimals as usize];

    let qt = value
        .checked_mul(scaling_factor)
        .ok_or_else(math_error!())?
        .checked_div(price)
        .ok_or_else(math_error!())?;

    Ok(qt)
}

/// Convert between decimal precisions. Returns None on unsupported diff or overflow.
#[inline]
pub fn convert_decimals(n: I80F48, from_dec: u8, to_dec: u8) -> Option<I80F48> {
    if from_dec == to_dec {
        return Some(n);
    }

    let diff = (to_dec as i32) - (from_dec as i32);
    let abs = diff.unsigned_abs() as usize;

    if abs > 23 {
        return None;
    }

    let scale: I80F48 = EXP_10_I80F48[abs];
