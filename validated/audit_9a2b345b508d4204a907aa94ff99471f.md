Based on my analysis, I've confirmed a concrete accounting bug in the node-side coordinator/listener that double-books a single signer's weight across both the approval and rejection tallies. Here's the finding:

### Title
Stale rejection weight is never retracted when a signer flips to Accepted, letting a validly-signed block be wrongly discarded as rejected - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tracks two independent weight counters per proposed block, `total_weight_approved` and `total_weight_rejected`, gated by two different, asymmetric guards. A signer who first rejects a block and later legitimately signs (accepts) it has their rejection weight counted into `total_weight_rejected` *permanently*, with no mechanism to retract it, while their acceptance weight is separately added to `total_weight_approved`. The same signer's weight is thus counted on both sides of the ledger simultaneously, breaking the aggregated-weight vs. verified-accepts (and verified-current-rejects) equality the coordinator relies on to decide a block's fate.

### Finding Description
On `BlockResponse::Accepted`, the gate that decides whether to add `signer_entry.weight` to `total_weight_approved` is `!block.gathered_signatures.contains_key(&slot_id)` [1](#0-0) . This check only asks "have we already recorded a signature from this slot", not "did this slot already register an opinion". `responded_signers.insert(slot_id)` is unconditionally performed as a side effect of the accept branch [2](#0-1) .

On `BlockResponse::Rejected`, the gate for adding weight to `total_weight_rejected` is `block.responded_signers.insert(slot_id)`, i.e. "has this slot ever responded at all" [3](#0-2) .

These two gates are asymmetric:
- Accept → Reject (same slot): blocked correctly, because `responded_signers` already contains the slot from the accept branch, so the reject branch's `insert` returns `false` and `total_weight_rejected` is not incremented. A signature can't be revoked — consistent with the documented design that "a signature is a bearer instrument" (see `docs/signer-flows.md` section 6: rejection is revocable, signature is not) [4](#0-3) .
- Reject → Accept (same slot): **not** blocked. The prior rejection already inserted the slot into `responded_signers`, but the accept branch's gate checks `gathered_signatures`, not `responded_signers`, so it happily adds the weight a second time to `total_weight_approved`. `total_weight_rejected` is never decremented for that slot, so the (now-superseded) rejection weight stays on the books forever.

The coordinator (`SignerCoordinator::wait_for_aggregate_public_key`/block-wait loop in `signer_coordinator.rs`) checks the blocking condition first and unconditionally trusts `total_weight_rejected`:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected ...)
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(... gathered_signatures ...)
}
``` [5](#0-4) 

Because `total_weight_rejected` can retain stale weight from signers who have since switched to Accepted, this counter no longer reflects the *current* set of dissenting signers. Combined with a modest number of genuinely-still-rejecting signers, the blocking-minority threshold (`total_weight_rejected + weight_threshold > total_weight`, i.e. rejecting weight > 30%) can be crossed using weight that the signer in question has actually already retracted by signing. This causes the miner to treat an otherwise properly, sufficiently-signed block as globally rejected (the reject branch is checked first and wins), even though the real, current signer opinions would have produced a valid 70%-weight acceptance.

### Impact Explanation
This is a liveness wedge reachable by a single flip-flopping (or simply slow/rebroadcasting) signer plus ordinary network conditions — no majority collusion is required, only that one signer's rejection message is processed before their (later, valid) acceptance, which is a normal and expected sequence under the documented "rejection is revocable" model. The result is a miner incorrectly discarding a block that has legitimately reached the 70% signing threshold, stalling tenure progress and forcing miner retries/tenure-extends. It maps to "a rejection recounted as an accept"-class defects generalized to a weight-tally class break: the aggregated `total_weight_rejected` no longer equals the verified, current set of rejecting signers' weight.

### Likelihood Explanation
The sequence (reject-then-later-accept from the same signer for the same block) is an ordinary, protocol-sanctioned event — the signer-side code (`signerdb.rs`/`signer.rs`) explicitly supports re-evaluating a block from `LocallyRejected` to `LocallyAccepted` [6](#0-5)  and treats rejection as revocable by design [4](#0-3) . Any signer whose local pre-commit conflict resolves (e.g. the sibling/conflict it initially rejected against goes stale) will naturally produce this exact reject→accept message sequence, making the node-side accounting bug easy to trigger without any adversarial intent.

### Recommendation
Make the accept-branch gate consult `responded_signers` (or an explicit per-slot "current vote" map) rather than `gathered_signatures`, and when a slot's vote flips from Rejected to Accepted, subtract that slot's weight from `total_weight_rejected` before adding it to `total_weight_approved` (or maintain a single per-slot vote enum and recompute both totals from it) so the two tallies never simultaneously double-count the same signer's weight.

### Proof of Concept
1. Reward set: signer A weight 25, signers B+C+D combined weight 45 (already `Accepted`), total weight 100, `weight_threshold` = 70.
2. Signer A sends `BlockResponse::Rejected` for block X → `total_weight_rejected = 25` (`responded_signers` now contains A's slot).
3. Signer A's local conflict later resolves and it legitimately signs the block, sending `BlockResponse::Accepted` for the same block X → gate `!gathered_signatures.contains_key(A)` is true → `total_weight_approved += 25` → now `total_weight_approved = 70` (correctly reaches threshold this time), but `total_weight_rejected` still equals 25 and is never cleared.
4. Now introduce one more real rejecting signer E with weight 6 rejecting a *different, still-open* proposal path/re-proposal for the same tenure height before A's flip is observed by the coordinator loop check: at the moment the loop observes `total_weight_rejected = 25` (stale, from A, who has actually since accepted) plus E's 6 = 31, `31 + 70 = 101 > 100` trips the reject branch first in `signer_coordinator.rs`, causing `SignersRejected` to be returned even though the *current* opinions (A accepted, E rejected) only account for 6 real dissenting weight — far short of the 30-weight blocking minority actually required.
