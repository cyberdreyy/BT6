### Title
Confirmations from deleted members remain counted toward `num_confirmations`, allowing requests to execute below the live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` decides whether to execute a request purely from `confirmations.len()` [1](#0-0) , without verifying that every stored confirmation string still corresponds to a member in `self.members`. `delete_member` only purges confirmations for requests that the removed member *created* (`r.member == member`), not for requests where the removed member merely *voted* [2](#0-1) . A stale confirmation from a now-removed (or removed-then-re-added) member therefore keeps counting toward the threshold, letting a request (including one containing a `DeployContract` action against the multisig account itself) execute with fewer genuinely live members' confirmations than `num_confirmations` requires.

### Finding Description
The invariant that should hold is: `confirmations.get(&request_id).len()` == the number of *currently live* members who confirmed request `request_id`. In reality, `delete_member` breaks this binding: it filters `self.requests` for entries whose `member == member_being_deleted` (i.e., requests that member *created*) and purges only those requests/confirmations [3](#0-2) . It resets `num_requests_pk` for that member [4](#0-3) , but does not scan other pending requests' `confirmations: HashSet<String>` to strip out this member's identity string where they had merely voted (not created) the request.

`confirm` never re-validates the membership of existing confirmers; it just checks `confirmations.len() as u32 + 1 >= self.num_confirmations` [5](#0-4) , and `assert_valid_request` only checks that the *caller* is currently a member, plus that the request/confirmations map exist [6](#0-5) . Neither guard re-checks the membership status of previously recorded confirmers.

Exploit flow:
1. Members {A, B, C, D}, `num_confirmations = 3`.
2. D creates a request `R` (e.g., containing `DeployContract` on the multisig account) via `add_request`.
3. A confirms (`confirmations = {A}`), B confirms (`confirmations = {A, B}`) — 2 of 3, request still pending.
4. Governance later removes B via a legitimately-confirmed `DeleteMember { member: B }` request. `delete_member` only cleans up requests *B created*; `R` (created by D) is untouched, so `confirmations = {A, B}` still contains B's stale vote.
5. C — a live member — confirms `R`. `confirmations.len() + 1 == 3 >= num_confirmations`, so `execute_request` runs, executing `DeployContract` and replacing the multisig's own code, even though only A and C are truly live confirmers (2 of the required 3).

If B is subsequently re-added, `num_requests_pk` for B is reset to 0 while B's stale confirmation on `R` (or any other request B voted on before removal) remains in place, further hiding the inconsistency between the two pieces of per-member state.

### Impact Explanation
This directly matches the listed Critical impact: "a multisig request executed below `num_confirmations` live members." The consequence can be arbitrary, including a `DeployContract` action that replaces the multisig account's code, or a `Transfer`/`AddKey` action moving funds or granting access, all while only 2 of 3 (or generally `k-1` of `k`) confirmations came from currently authorized members. This is repeatable for every request that received partial confirmations before a confirming member was removed, and blast radius is the full balance/control of the multisig account.

### Likelihood Explanation
This requires normal, expected multisig operations: a pending multi-step request accumulating confirmations, followed by a legitimate `DeleteMember` action (member rotation is an intended feature, not a rare edge case). No attacker needs to compromise keys or bypass any check — the flaw is inherent to `delete_member`'s incomplete cleanup, so it can be triggered by ordinary usage patterns or deliberately engineered by any current member who anticipates their own removal (or a colluding member's removal) to leave behind a "banked" stale vote.

### Recommendation
When deleting a member, iterate over all pending requests' `confirmations` sets (not just requests the member created) and remove the departing member's identity string from each. Alternatively, when counting confirmations in `confirm`, filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
```rust
// multisig2/src/lib.rs tests module
#[test]
fn test_stale_confirmation_after_member_removal_bypasses_threshold() {
    // members: alice, bob, carol, dave (all Account members), num_confirmations = 3
    let members = vec![
        MultisigMember::Account { account_id: alice() },
        MultisigMember::Account { account_id: bob() },
        MultisigMember::Account { account_id: carol() },
        MultisigMember::Account { account_id: dave() },
    ];
    testing_env!(context_with_account(dave(), 0));
    let mut c = MultiSigContract::new(members, 3);

    // Dave creates request R (DeployContract on self)
    testing_env!(context_with_account(dave(), 0));
    let request_id = c.add_request(MultiSigRequest {
        receiver_id: current_account_id(),
        actions: vec![MultiSigRequestAction::DeployContract { code: vec![].into() }],
    });

    // Alice confirms
    testing_env!(context_with_account(alice(), 0));
    c.confirm(request_id);
    // Bob confirms
    testing_env!(context_with_account(bob(), 0));
    c.confirm(request_id);
    assert_eq!(c.get_confirmations(request_id).len(), 2); // {alice, bob}

    // Bob is removed via DeleteMember governance flow (simulate directly)
    // delete_member only purges requests Bob CREATED; request_id was created by dave, so
    // bob's confirmation string remains in confirmations for request_id.
    let dummy_promise = Promise::new(current_account_id());
    c.delete_member(dummy_promise, MultisigMember::Account { account_id: bob() });

    // Confirmations for request_id still contain bob's stale vote
    assert!(c.get_confirmations(request_id).contains(&MultisigMember::Account{account_id: bob()}.to_string()));

    // Carol (live member) confirms -> reaches 3 confirmations (alice, bob[stale], carol)
    // even though bob is no longer a member: only alice+carol (2) are truly live.
    testing_env!(context_with_account(carol(), 0));
    let result = c.confirm(request_id); // executes DeployContract with only 2 live confirmations
    // Assert request executed (removed from pending requests) despite only 2 live confirmers
    assert!(c.get_request(request_id) panics / request no longer exists);
}
```
The assertion that fails the intended invariant: `live_confirmers(request_id).len() < num_confirmations` yet the request executes (`confirmations.len() + 1 >= num_confirmations` was satisfied using a stale, no-longer-a-member confirmation).

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
