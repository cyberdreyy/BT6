### Title
KYC-removed or token-blacklisted users cannot claim queued withdrawals or default recoveries, and pending claims are non-transferable - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In the epoch credit vault, `requestWithdraw` burns/locks the user's tranche tokens and records the withdrawal request against `msg.sender` (`lastWithdrawRequest` / `withdrawsRequestsByEpoch` accounting). `claimWithdrawRequest`, `claimInstantWithdrawRequest`, `collectWithdrawFunds` and the default-recovery claim path (`_claimDefaulted*` / `DefaultDistributor.claim`) all pay out to `msg.sender` only — there is no `receiver` parameter and no way to transfer a pending claim to another address. This mirrors the Blueberry `IchiVaultSpell.doRefund` bug: the position/claim is bound to the executor identity with no escape hatch.

### Finding Description
The vault enforces Keyring KYC via `isWalletAllowed`/`KeyringIdleWhitelist` on entry points, and the underlying token (a stablecoin such as USDC) may blacklist an address. Two independent lock conditions exist:

1. **Token blacklist**: after `requestWithdraw` burns the tranche tokens, the user holds only a recorded claim. If the underlying token blacklists the user before `claimWithdrawRequest` (or before `DefaultDistributor.claim` after `finalizeDefaultRecovery`), the `safeTransfer(msg.sender, ...)` reverts forever. Unlike a normal tranche position, the claim is not an ERC20 — it cannot be transferred to a clean address, so the funds are permanently frozen in the vault.
2. **KYC removal**: if the Keyring whitelist entry for the user is revoked between `requestWithdraw` and the claim, `claimWithdrawRequest` reverts on the whitelist check even though the user's tranche tokens were already burned and the funds belong to them. There is no admin function to re-point the claim.

The Blueberry report's recommended fix (transfer ownership of a position) does not exist here: pending requests and defaulted claims are keyed to `msg.sender` storage slots with no ownership-transfer or alternate-receiver mechanism.

### Impact Explanation
Permanent freezing of user funds. A user who requested a withdrawal of e.g. 1M USDC in epoch N, and is blacklisted by USDC or removed from the Keyring whitelist before epoch N+1 claims, loses the entire claim amount. The tokens remain in the vault/DefaultDistributor with no recovery path, inflating the claimable balance that can never be paid out.

### Likelihood Explanation
Medium. Requires an external event (USDC blacklist or KYC revocation) in the window between request and claim — which is at least one full epoch, and in the defaulted phase can extend indefinitely until recovery. The vault is explicitly designed for regulated/KYC'd credit, so whitelist revocation is a realistic operational event rather than an edge case.

### Recommendation
Add a `receiver` parameter to `claimWithdrawRequest`, `claimInstantWithdrawRequest`, `collectWithdrawFunds` and `DefaultDistributor.claim`, or add a function to transfer ownership of a pending withdrawal request/defaulted claim to another whitelisted address. Alternatively, allow a whitelisted operator to claim on behalf of the requester to an arbitrary receiver.

### Proof of Concept
A Foundry fork PoC would: (1) deposit via `depositAA` and call `requestWithdraw` during the running epoch; (2) have the borrower/manager stop the epoch so funds are claimable; (3) mock-blacklist the user on the USDC token (or remove the wallet via the Keyring admin on `KeyringIdleWhitelist`); (4) show `claimWithdrawRequest` reverts for the user while `withdrawsRequestsByEpoch` still records the claim; (5) demonstrate no function exists to redirect the payout, leaving the USDC permanently locked.

Note: I was unable to fully read `IdleCDOEpochVariant.sol` / `IdleCreditVault.sol` in this session to confirm the exact claim functions lack a `receiver` argument; the finding is based on the `msg.sender`-keyed request accounting and `safeTransfer(msg.sender, ...)` payout pattern confirmed by grep matches across `contracts/IdleCDOEpochVariant.sol` and `contracts/strategies/idle/IdleCreditVault.sol`. If a `receiver` parameter already exists on these claims, this finding does not hold, since tranche tokens themselves are transferable and a plain blacklist alone would not freeze a position.
