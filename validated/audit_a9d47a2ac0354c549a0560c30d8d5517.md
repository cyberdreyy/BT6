### Title
`GET /v2/external_initiators` lacks a role wrapper, allowing any authenticated (view-role) user to read `AccessKey`/`OutgoingToken` for all External Initiators - ([File: core/web/router.go])

### Summary
The route `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` is registered with no `auth.RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper, unlike its sibling `POST`/`DELETE` routes which are explicitly `RequiresEditRole`-gated. Any user who can pass the generic `auth.Authenticate` middleware (session or API token, including `UserRoleView`) can call `ExternalInitiatorsController.Index` and receive each External Initiator's `AccessKey` and `OutgoingToken` in the JSON:API response.

### Finding Description
`v2Routes` in `core/web/router.go` defines: [1](#0-0) 
Only `Create` and `Destroy` are wrapped in `auth.RequiresEditRole`; `Index` is reachable by any authenticated principal that satisfies `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)` for the `/v2` group, regardless of role.

`ExternalInitiatorsController.Index` fetches all rows via `BridgeORM().ExternalInitiators` (backed by `SELECT * FROM external_initiators`) and maps each into `presenters.ExternalInitiatorResource`: [2](#0-1) [3](#0-2) 

`ExternalInitiatorResource` does redact `Salt`, `HashedSecret`, and `OutgoingSecret` (they are not present as struct fields), but it does expose `AccessKey` and `OutgoingToken` in the JSON response for every EI in the system, to any authenticated caller.

The existing integration test `TestExternalInitiatorsController_Index` confirms this by asserting the presence of `AccessKey` and `OutgoingToken` in the paginated response, without exercising any role restriction: [4](#0-3) 

### Impact Explanation
`AccessKey` is the identifier used by an External Initiator to authenticate incoming webhook trigger requests to the node (paired with a secret, hashed and salted, that is *not* exposed), and `OutgoingToken`/`OutgoingSecret` are used by the node to authenticate outbound notifications back to the initiator's URL (only `OutgoingToken` is exposed here, not `OutgoingSecret`). Disclosure of `AccessKey` and `OutgoingToken` to a low-privilege (view-role) authenticated user is an over-broad information disclosure of EI identifiers/credential material beyond what that role should see, but does not by itself grant full impersonation because the corresponding secret material needed to complete authentication (`HashedSecret`/`Salt` for incoming auth, `OutgoingSecret` for outgoing auth) is correctly withheld by the presenter. The impact is therefore a **role/authorization gap causing partial credential-material disclosure** to under-privileged authenticated users (a Broken Access Control class issue), not a full external-initiator impersonation vulnerability, because the missing role wrapper is real but the presenter already withholds the secrets that would be required to fully replay/forge an EI request.

### Likelihood Explanation
Any user holding a valid session cookie or API token — including a `UserRoleView` account — can trivially issue `GET /v2/external_initiators`; no special preconditions are required beyond having any authenticated credential (view-role is the minimum privilege tier). This is fully repeatable and requires no misconfiguration beyond the existing route definition.

### Recommendation
Wrap the `GET /v2/external_initiators` route with an appropriate role guard (e.g., `auth.RequiresEditRole` or at minimum `auth.RequiresRunRole`) consistent with `Create`/`Destroy`, and/or remove `AccessKey`/`OutgoingToken` from `ExternalInitiatorResource` (or mask them, similar to how `Salt`/`HashedSecret`/`OutgoingSecret` are already omitted) so that listing does not disclose live credential identifiers even to edit/run-role users.

### Proof of Concept
1. Add/extend a handler integration test in `core/web/external_initiators_controller_test.go` (following the pattern of `TestExternalInitiatorsController_Index`) that creates a session/API-token client for a `sessions.UserRoleView` user (see how other tests set up `cltest.CreateUserWithSession` / `client.LoginTo`/role-scoped clients elsewhere in the `core/web` test suite).
2. Insert an EI via `cltest.MustInsertExternalInitiatorWithOpts` with known `AccessKey`/`OutgoingToken`.
3. As the view-role authenticated client, call `GET /v2/external_initiators`.
4. Assert the response is `200 OK` (not `403 Forbidden`) and that `presenters.ExternalInitiatorResource.AccessKey` / `OutgoingToken` in the body match the inserted EI's values — demonstrating that a view-role user can read this data, whereas `POST`/`DELETE` on the same resource correctly return `403` for that same user (contrast test using `RequiresEditRole`-gated routes).

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
```
