### Title
`RewardFeeFraction::assert_valid` permits a 100% reward fee (numerator == denominator) which is silently accepted by `create_staking_pool` and subsequently whitelisted, misattributing all delegator rewards to the pool owner - (File: staking-pool-factory/src/lib.rs)

### Summary
`RewardFeeFraction::assert_valid` only enforces `numerator <= denominator` and `denominator != 0`, so an attacker can pass `{numerator: 4294967295, denominator: 4294967295}` — a mathematically valid but economically 100% fee. `create_staking_pool` performs no additional bound and forwards this fraction unchanged into the deployed staking pool's `new` constructor, after which the pool is whitelisted through the ordinary success callback with no fee-sanity check.

### Finding Description
The broken binding: the codebase implicitly assumes `is_whitelisted(pool) == true` implies `reward_fee_fraction` is a "reasonable" fee that leaves delegators a nonzero rewards share, i.e. `numerator < denominator` (strictly less). In reality `assert_valid` only checks: [1](#0-0) 

This allows `numerator == denominator` (any value, including `u32::MAX`), which represents a 100% reward fee.

`create_staking_pool` calls `reward_fee_fraction.assert_valid()` and, if it passes, deploys the staking-pool contract with these exact arguments and no other validation of the fee value: [2](#0-1) 

The success callback `on_staking_pool_create` only checks `is_promise_success()` — i.e., whether the deployment/`new` call succeeded — before whitelisting the pool. It performs no inspection of the fee fraction that was set: [3](#0-2) 

Since the staking-pool contract's own constructor (which I was unable to fully inspect due to indexing limits, see below) accepts the fraction and only validates it via the same `assert_valid` semantics, a 100%-fee pool deploys and is whitelisted through the completely ordinary, unprivileged flow — no owner, foundation, or multisig involvement is required.

### Impact Explanation
Any delegator who stakes into this whitelisted pool will have their entire share of staking rewards routed to the fee mechanism, which staking-pool contracts of this era credit to the pool `owner_id` (the attacker) rather than to delegators. This matches the "rewards or owner fees attributed to the wrong party" High-severity category: NEAR that should accrue as delegator rewards accrues entirely to the attacker-controlled owner account instead. This is repeatable indefinitely — the attacker can create arbitrarily many such pools (bounded only by the `MIN_ATTACHED_BALANCE` cost of ~30 NEAR per pool) and rely on the whitelist as an implicit trust/quality signal to attract delegator stake.

### Likelihood Explanation
The attacker needs only: (1) enough NEAR to cover `MIN_ATTACHED_BALANCE` (30 NEAR) for pool creation, and (2) an unprivileged call to `create_staking_pool` with `reward_fee_fraction = {numerator: N, denominator: N}` for any `N > 0`. No special permissions, foundation approval, or owner/multisig access is required — this is the "normal successful flow" described in the question. Feasibility is high and the attack is trivially repeatable.

### Recommendation
Tighten `RewardFeeFraction::assert_valid` to reject degenerate/unreasonable fees, e.g. require `numerator < denominator` (strict) and/or enforce a maximum fee ceiling (e.g., fee ≤ some percentage such as 20-30%) enforced both at pool-factory creation time and whenever the owner updates the fee later in the staking-pool contract itself.

fn test_create_staking_pool_with_100_percent_fee_is_accepted_and_whitelisted() {

    contract.create_staking_pool(
        staking_pool_id(),
        account_pool_owner(), // attacker-controlled owner_id
        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".try_into().unwrap(),
        RewardFeeFraction {
            numerator: u32::MAX,
            denominator: u32::MAX,
        },
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));

    // Normal success path: whitelist call is issued exactly as for any legitimate pool.
    let res = contract.on_staking_pool_create(account_pool(), ntoy(31).into(), account_tokens_owner());
    // assert res is Promise (whitelisting attempted), i.e. no rejection based on fee value.
    match res {
        PromiseOrValue::Promise(_) => {}, // confirms whitelist call scheduled despite 100% fee
        PromiseOrValue::Value(_) => panic!("expected whitelist attempt"),
    }

    context.is_view = true;
    testing_env!(context.clone());
    assert_eq!(contract.get_number_of_staking_pools_created(), 1);
}

    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
