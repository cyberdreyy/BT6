## Title
`getLargestAccounts` RPC cache is keyed only by filter, not by commitment level, causing wrong-slot data to be returned across commitment levels - (File: rpc/src/rpc.rs, rpc/src/rpc_cache.rs)

### Summary
The `LargestAccountsCache` used by the `getLargestAccounts` JSON-RPC method caches results keyed solely by `RpcLargestAccountsFilter` (`Circulating`/`NonCirculating`/`None`), with no dependency on the `commitment` level or bank/slot that produced the result. Because the bank is selected based on `config.commitment` but the cache lookup ignores it, a cached result computed for one commitment level (e.g. `finalized`) can be served back for a request made with a different commitment level (e.g. `processed`), returning data (and a `context.slot`) that does not correspond to the bank the caller actually asked for. This is structurally the same class of bug as the reported yToken issue: a cache whose invalidation/keying does not track the value ("registry"/commitment) it is supposed to be consistent with, resulting in stale or mismatched output being handed to callers.

### Finding Description
`JsonRpcRequestProcessor::get_largest_accounts` first resolves a bank for the request's commitment, then checks the cache by filter only, ignoring commitment/slot entirely: [1](#0-0) 

The underlying cache implementation confirms the key is only `Option<RpcLargestAccountsFilter>`, with a `HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>` and a wall-clock TTL, with no notion of commitment or bank identity in the key: [2](#0-1) 

When the cache misses, the code correctly scans `bank.get_largest_accounts(...)` for the commitment-selected bank and stores the result under `set_cached_largest_accounts(&config.filter, bank.slot(), &accounts)`: [3](#0-2) 

Because the cache key does not include commitment, a subsequent call with a *different* commitment level but the *same* filter, arriving within the TTL window, will hit `get_cached_largest_accounts` and return the previously-cached `(slot, accounts)` pair — which was computed for a different bank/commitment than the one just resolved via `self.bank(config.commitment)`. The `bank` variable computed at line 1072 is discarded in the cache-hit branch; it is only used in the miss branch. This mirrors exactly the yToken pattern: a pointer/parameter (`registry` / `commitment`) can change, but the cache built for the old value is reused without any consistency check against the new value.

### Impact Explanation
This produces "wrong-slot data returned" from a query: a client requesting `getLargestAccounts` with `commitment: "processed"` can receive results and a `context.slot` that actually correspond to an earlier `finalized`-commitment scan (or vice versa), depending on request ordering, within the cache's TTL window. This can mislead any consumer relying on `getLargestAccounts` for up-to-date supply/whale-monitoring data, and the returned `context.slot` misrepresents which bank the data was drawn from, which is a correctness bug in an unprivileged, publicly reachable RPC method.

### Likelihood Explanation
This requires no privileged access — any RPC caller can trigger it by issuing two `getLargestAccounts` requests with the same `filter` but different `commitment` levels within the cache duration window (the cache is process-wide and shared across all callers, so it can also be triggered/observed by an attacker racing another client's request). No malicious input, crafted snapshot, or multiple-client coordination is required; it is a single extra RPC call relative to normal operation, well under the `CLUSTER_SLOT_TIME_TARGET / 2` restriction called out in scope rules.

### Recommendation
Include the effective commitment (or bank slot) in the `LargestAccountsCache` key, e.g. `HashMap<(CommitmentConfig, Option<RpcLargestAccountsFilter>), LargestAccountsCacheValue>`, or validate that `cached_slot` still corresponds to a bank compatible with the currently-requested commitment before returning a cache hit. Document that any change of the value used to select the underlying data source for a cache (here, commitment) must either be part of the cache key or must force cache invalidation, matching the general recommendation from the referenced report to add consistency checks or force a rebuild when the referenced "version" changes.

### Proof of Concept
1. Issue `getLargestAccounts` with `{"commitment": "finalized"}` — this populates the cache entry for filter `None` with the finalized bank's slot/results.
2. Immediately (within the cache TTL) issue `getLargestAccounts` with `{"commitment": "processed"}` while the processed bank has advanced past the finalized bank (normal validator operation) — the handler resolves the processed bank via `self.bank(config.commitment)` at rpc/src/rpc.rs:1072, but then hits the filter-only cache and returns the stale finalized-bank result/slot instead of scanning the processed bank.

Note: I was unable to verify the exact default TTL constant used to construct `LargestAccountsCache` (e.g., in `rpc_service.rs`) within the available searches, so the precise window size during which this race is exploitable is not confirmed here; a Devin session with full repo access would be needed to pin down that constant and write an executable integration test.

#[derive(Debug, Clone)]
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}

#[derive(Debug, Clone)]
struct LargestAccountsCacheValue {
    accounts: Vec<RpcAccountBalance>,
    slot: u64,
    cached_time: SystemTime,
}

impl LargestAccountsCache {
    pub(crate) fn new(duration: u64) -> Self {
        Self {
            duration,
            cache: HashMap::new(),
        }
    }

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }
