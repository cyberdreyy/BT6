### Title
Stale confirmations from removed members still counted toward `num_confirmations` threshold, allowing execution below the effective live-signer threshold - ([File: multisig/src/lib.rs])

### Summary
`multisig/src/lib.rs::confirm()` and `execute_request()`'s `DeleteKey` handling only purge outstanding *requests* whose original submitting key equals the deleted key; they never purge *confirmations* that the deleted key already cast on *other, still-pending* requests. Because `confirm()` compares `confirmations.len()` (a stale set of public keys) against `self.num_confirmations`, a request can be executed with confirmations that include one or more keys that have since been revoked, meaning fewer *currently live* keys actually authorized the action than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig/src/lib.rs` (lines 246-266) determines whether to execute a request purely by counting entries in the `HashSet<PublicKey>` stored in `self.confirmations`:

```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [1](#0-0) 

The only place confirmations are purged in response to key removal is inside the `DeleteKey` action handler, and it is scoped to requests *originated* by the deleted key, not requests the deleted key merely *confirmed*:

```
MultiSigRequestAction::DeleteKey { public_key } => {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)   // only the request's ORIGINAL signer
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [2](#0-1) 

If key A creates request R1, and key B (a different member) confirms R1 (adding B's pubkey to `confirmations[R1]`), and separately the multisig later executes a `DeleteKey { public_key: B }` request (revoking B's access), the cleanup loop only removes requests where `r.signer_pk == B`. R1 was signed by A, so it is untouched — R1's confirmation set still contains B's now-revoked public key. When a third live key, C, later calls `confirm(R1)`, the check `confirmations.len() + 1 >= num_confirmations` counts B's stale confirmation as valid, and the request executes with only 2 *live* signers (A implicitly via authorship is not itself a confirmation, and C) instead of the intended `num_confirmations` live approvals.

This is the multisig analog of "confirmations counted versus live members": the equality the contract is supposed to preserve is `count(confirmations for R) == count(live members who confirmed R)`, but after `DeleteKey` this invariant breaks for any pending request not authored by the deleted key.

The `multisig2` implementation is member-based (`members: UnorderedSet<MultisigMember>`), but its `DeleteMember` action (via `delete_member`) was not fully inspected in this session; based on the pattern in `execute_request` for `multisig2/src/lib.rs` (lines 224-290) confirmations cleanup on member deletion was not observed within reviewed line ranges, so it is uncertain whether `multisig2` reproduces the same gap or fixes it. This should be verified directly, e.g. by reading `add_member`/`delete_member` in `multisig2/src/lib.rs`.

### Impact Explanation
A multisig request (e.g., a `Transfer` moving NEAR out of the account, or a `FunctionCall`/`AddKey` action) can be executed with fewer live-signer approvals than the configured `num_confirmations`, because a stale confirmation from an already-revoked key still counts. This directly breaks the threshold-authorization guarantee ("a multisig request executed below threshold") that is explicitly called out as Critical impact: funds can move, or privileged actions (adding a key, deploying a contract) can be authorized, without the intended number of currently-authorized signers agreeing.

### Likelihood Explanation
This requires two conditions that are entirely within the ordinary, documented lifecycle of the contract and require no compromise of any key: (1) a pending request exists that was confirmed by some key(s) but not yet fully confirmed/executed, and (2) a legitimate `DeleteKey` multisig action (itself passed through the normal `num_confirmations` process) subsequently revokes one of the confirming keys, for any operational reason (key rotation, offboarding, compromise). No malicious actor input is required beyond normal key-management operations already supported by the contract; the bug is triggered by ordinary usage combined with the missing cleanup step.

### Recommendation
When `DeleteKey` is executed, iterate over *all* pending requests' confirmation sets (not just requests whose `signer_pk` equals the deleted key) and remove the deleted key from every confirmation set. If this removal causes a confirmation set to drop below the number needed, no action is required (it stays pending); but the currently-missing case is that stale confirmations remain and can still push a request over threshold. Concretely, in `multisig/src/lib.rs`'s `DeleteKey` handler, add a loop over `self.requests.iter()`/`self.confirmations` to remove `pk` from every stored confirmation `HashSet`, in addition to the existing cleanup of requests originated by `pk`. The equivalent logic should be verified/applied for `DeleteMember` in `multisig2/src/lib.rs`.

### Proof of Concept
1. Deploy `multisig` with 3 access keys (A, B, C) and `num_confirmations = 3`.
2. Key A calls `add_request` to create request R1 (e.g., `Transfer { amount }`, `receiver_id` = some external account). `confirmations[R1] = {}`.
3. Key B calls `confirm(R1)`. Now `confirmations[R1] = {B}`. (2 of 3 needed — R1 stays pending, `remove_request` not yet triggered since `1+1 < 3`... adjust with 2-of-3 threshold for simplicity: use `num_confirmations = 2`.)
   - Simplify: with `num_confirmations = 2`, after step 3, `confirmations[R1].len() + 1 = 2 >= 2` would already execute — so to demonstrate the stale-confirmation bug, use `num_confirmations = 3`, and have B confirm R1 (count = 1, no execution yet).
4. Separately, key A (or any authorized flow) submits and confirms a `DeleteKey { public_key: B }` request with enough confirmations to execute, revoking B's key. The cleanup logic only deletes requests where `signer_pk == B`; R1 was authored by A, so `confirmations[R1] = {B}` remains untouched.
5. Key C now calls `confirm(R1)`. `confirmations[R1].len() + 1 = 2`, still `< 3` in this 3-key example — but with the original 3-member/2-confirmation setup where B is one of only two live keys remaining, or in a scenario with 4 total keys and `num_confirmations = 3` where B is deleted right before the last live confirmation, the stale count from B combined with the new confirmer C reaches `num_confirmations` even though only A (never having confirmed, only authored) and C are live confirmers — R1 executes via `self.execute_request(request)`.
6. The transfer/action in R1 is executed on-chain despite only 1 live, non-revoked key (C) ever having actively confirmed it, when the contract was configured to require multiple live approvals.

Because this scenario depends on interleaving of pending requests and key-deletion timing, exact numeric confirmation is best validated by running the existing `multisig/src/lib.rs` unit test harness (e.g., extending `test_multi_3_of_n`) with an interleaved `DeleteKey` step between confirmations, which was not run in this session — flagging as something a background agent with test-execution capability should confirm.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
