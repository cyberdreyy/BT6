### Title
`claimInstantWithdrawRequest` pays a user's entire aggregate instant-withdraw receipt at par even when the epoch only partially funded `pendingInstantWithdraws`, so early claimants drain late claimants' funded shares - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (Text::LineFold applies its break operation to the *entire* input once per segment instead of per segment, duplicating output) maps onto `IdleCreditVault.claimInstantWithdrawRequest`: a per-segment notion (how much of an epoch's instant requests was actually funded) is applied to the *whole aggregate* `instantWithdrawsRequests[_user]`. The vault tracks funded vs. unfunded instant liquidity only via the global `pendingInstantWithdraws` counter, which `collectInstantWithdrawFunds` decrements by whatever amount the CDO actually pulls in. There is no per-epoch funded price (unlike `lossRecoveryPriceByEpoch` for normal withdraws) and no funded-share check on claim. The user-facing claim therefore pays the full `instantWithdrawsRequests[_user]` aggregate at par whenever the vault holds enough underlying for that user — even though only part of the epoch's instant bucket was funded.

### Finding Description
- `requestInstantWithdraw` mints a receipt, accumulates `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` (`contracts/strategies/idle/IdleCreditVault.sol` lines 356-375).
- Funding is pull-based and amount-parameterized: `collectInstantWithdrawFunds(_amount)` does `pendingInstantWithdraws -= _amount` and transfers `_amount` from the CDO (lines 398-403). Nothing enforces `_amount == pendingInstantWithdraws` — the CDO (`getInstantWithdrawFunds`) may only pull what the borrower returned, so an epoch can leave `pendingInstantWithdraws > 0` as the unfunded remainder.
- `claimInstantWithdrawRequest` (lines 380-393) then does `amount = instantWithdrawsRequests[_user]; _burn(_user, amount); _transferFundedClaim(_user, amount)` — it pays the whole aggregate at par with no check that this user's share was funded, and no haircut like the `lossRecoveryPriceByEpoch` mechanism used for normal withdraws in `collectWithdrawFunds` (lines 411-430) and `_claimLossAdjustedWithdrawRequest` (lines 789-801).

So the funded pool is split pro-rata *in accounting terms only* — in practice it is first-come-first-served. Like the LineFold bug, the "segment" (funded share) is ignored and the "whole string" (aggregate receipt) is paid out for each claimant until the funded balance is exhausted.

### Impact Explanation
Broken invariant: fair burn / one-receipt-one-funded-payout; solvency of the instant-withdraw pool.

If epoch instant requests of total `T` are only funded `F < T` (borrower underperforms / underpays before `instantWithdrawDeadline`), every user's receipt remains denominated at full par. The first claimants to call `claimInstantWithdrawRequest` (via `IdleCDOEpochVariant.claimInstantWithdrawRequest` / `IdleCDOEpochQueue.processWithdrawalClaims` in the instant branch) receive their full `instantWithdrawsRequests[_user]` from the vault's `F` balance; later claimants' transactions revert on insufficient balance or are paid `0`. An attacker tranche-token holder with an instant request can claim immediately upon funding and capture other users' funded shares — direct theft of unclaimed withdrawal proceeds equal to `min(attackerReceipt, F) - attackerReceipt * F / T`, i.e., up to the entire unfunded shortfall `T - F` redistributed to early claimants.

### Likelihood Explanation
Requires: instant withdrawals enabled (`allowInstantWithdraw`, `setInstantWithdrawParams`), an epoch where the borrower underpays so `collectInstantWithdrawFunds` receives less than `pendingInstantWithdraws`, and multiple instant requesters. The manager/borrower are honest per the threat model but are not required to fully fund instant requests by `instantWithdrawDeadline` — underpayment is a normal bad-credit scenario (the same code paths already anticipate partial funding for normal withdraws via `previewLossAdjustedWithdrawFunds`/`lossRecoveryPriceByEpoch`, and for default via `defaultRecoveryPrice`). The attacker only needs a KYC'd wallet and a tranche position to request an instant withdraw and then claim; sequencing a claim before other users is trivial once funding lands. Guard check: `defaultInstantWithdrawsFinalized` path only applies after default finalization; in the non-default underpayment scenario no revert (`NotAllowed`, epoch gating) protects the claim.

### Recommendation
Mirror the normal-withdraw loss machinery for instant withdraws: record a funded-ratio per epoch (e.g., `instantRecoveryPriceByEpoch[epoch] = collected * RECOVERY_FULL / instantWithdrawClaimsByEpoch[epoch]`) when `collectInstantWithdrawFunds` pulls less than the epoch's instant basis, and pay `instantWithdrawsRequestsByEpoch[_user][epoch] * price / RECOVERY_FULL` rather than the par aggregate. Alternatively, revert claims while `pendingInstantWithdraws != 0` for that epoch's receipts so only fully funded receipts are claimable at par.

### Proof of Concept
Foundry fork test sketch against `IdleCreditVault` + `IdleCDOEpochVariant`:

```solidity
// Setup: standard epoch variant, instant withdraws enabled via
// cdoEpoch.setInstantWithdrawParams(delay, 10e18, true) by manager.
// Users A (attacker) and B deposit AA tranches, epoch starts.

// 1. During running epoch, A and B each requestInstantWithdraw(50e6).
//    pendingInstantWithdraws == 100e6.

// 2. Borrower only returns 50e6 before instantWithdrawDeadline.
//    Manager calls getInstantWithdrawFunds -> collectInstantWithdrawFunds(50e6).
//    pendingInstantWithdraws == 50e6 (unfunded remainder).

// 3. Attacker A calls cdoEpoch.claimInstantWithdrawRequest():
//    strategy pays instantWithdrawsRequests[A] == 50e6 at par.
//    Vault balance now 0.

// 4. B calls claimInstantWithdrawRequest(): reverts / receives 0,
//    despite having an identical 50e6 receipt and identical funded share (25e6).

// Invariant violated: sum of par claims (100e6) > funded amount (50e6);
// first-come-first-served drain instead of pro-rata 25e6 each.
```

Caveat: this assumes the CDO's `getInstantWithdrawFunds` permits pulling less than `pendingInstantWithdraws` (i.e., does not revert on shortfall). I was unable to fully verify that call path within the iteration budget; if it hard-reverts on any shortfall, the instant bucket would instead remain entirely unfunded until topped up, and this specific finding would not hold — though the missing haircut mechanism for instant receipts remains an asymmetry worth flagging.
