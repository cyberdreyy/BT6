Based on my analysis of the vesting flow, I found a plausible Aptos-native analog to the "malicious reward token blocks withdrawal" pattern, centered on `vesting::distribute()`'s all-or-nothing payout loop combined with the opt-out mechanism in `aptos_account::deposit_coins`.

### Title
Unregistered/opted-out beneficiary can permanently DoS `distribute()` for all shareholders in a vesting pool - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting::distribute()` is a permissionless entry function (no signer required) that iterates over every shareholder in a vesting pool and calls `aptos_account::deposit_coins` to pay out their share in a single atomic transaction [1](#0-0) . `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient's account exists, is not yet registered for the coin, and has opted out via `DirectTransferConfig` [2](#0-1) . Because Move transactions are atomic, one unregistered/opted-out beneficiary reverts the whole `distribute()` call, blocking payouts to every other (unrelated) shareholder in the same vesting pool. This mirrors the C4 M-02 bug class where a single malicious/blocking token transfer in a shared loop prevents unrelated users from withdrawing.

### Finding Description
`distribute()` computes each shareholder's pro-rata share and sends it via `aptos_account::deposit_coins(recipient_address, share_of_coins)` inside a `for_each_ref` loop, where `recipient_address = get_beneficiary(vesting_contract, shareholder)` [3](#0-2) . `get_beneficiary` returns either the shareholder's own address or a beneficiary address previously set for that shareholder [4](#0-3) .

`aptos_account::deposit_coins` only performs the `can_receive_direct_coin_transfers` opt-out check when the recipient is **not yet registered** for the coin type; once registered, the check is permanently bypassed and only a (privileged) frozen `CoinStore` can block deposits [5](#0-4) . Any account holder can call `set_allow_direct_coin_transfers(false)` on their own account at any time — this is a fully unprivileged action.

If an address designated as a beneficiary (via the admin's `update_beneficiary` flow referenced in the module's doc comments) is not already registered for `AptosCoin`, that beneficiary can call `set_allow_direct_coin_transfers(false)` on their own account to opt out of unregistered-coin transfers. Any subsequent call to `distribute()` — which is permissionless and can be triggered by anyone, including via `distribute_many` or as part of `terminate_vesting_contract`/`admin_withdraw` flows — will abort entirely at that shareholder's deposit, reverting the whole transaction and blocking distribution for every other shareholder sharing that vesting pool.

**Caveat / unverified assumption:** I could not fully confirm within the available search budget whether `update_beneficiary` enforces `assert_account_is_registered_for_apt` on the new beneficiary address before accepting it (the module only clearly enforces this check on shareholders at `create_vesting_contract` time). If `update_beneficiary` does require prior registration, this specific griefing path would be closed (since registration cannot be reversed) and the finding would need re-scoping to some other unregistered recipient path. This should be verified against the exact body of `update_beneficiary` in `vesting.move` before treating this as confirmed.

### Impact Explanation
If the beneficiary-registration gap exists, this is a shared, pool-wide denial-of-service: unrelated shareholders' rewards and vested tokens become permanently un-distributable through `distribute()` as long as the griefing beneficiary remains both unregistered and opted-out, since `terminate_vesting_contract` also calls `distribute()` first and would likewise revert [6](#0-5) . This can strand vested APT and staking rewards for all shareholders in the pool, matching the "permanent lock or non-recoverable loss of claim rights ... in vesting flows" impact category.

### Likelihood Explanation
Low-to-uncertain until the `update_beneficiary` validation is confirmed. If beneficiaries are not required to be pre-registered, the likelihood is high since setting `allow_arbitrary_coin_transfers = false` is a single unprivileged, gas-cheap transaction, and `distribute()` is permissionless and commonly invoked.

### Recommendation
- Verify (and if missing, add) a registration/opt-in check on the beneficiary address inside `update_beneficiary` mirroring `assert_account_is_registered_for_apt` used for shareholders at contract creation.
- Regardless, make `distribute()` resilient to a single failing recipient by isolating each payout (e.g., skip-and-retry-later semantics, or an `emergencyWithdraw`/per-shareholder claim function) so that one blocked recipient cannot revert payouts to the rest of the pool.

### Proof of Concept
Conceptual PoC pending confirmation of `update_beneficiary`'s validation:
1. Admin creates a vesting contract with shareholders A and B.
2. Admin (or A) calls `update_beneficiary` to route A's distributions to address `M`, which exists on-chain but has never registered for `AptosCoin`.
3. `M` calls `aptos_account::set_allow_direct_coin_transfers(&M_signer, false)`.
4. Anyone calls `vesting::distribute(contract_address)`. The loop reaches A's payout to `M`, `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, and the entire transaction — including B's payout — reverts.
5. B can never receive their rewards/vested coins via `distribute()` (nor can the pool be `terminate_vesting_contract`-ed) until `M`'s opt-out state changes, which `M` fully controls.

This PoC's validity depends on confirming that `update_beneficiary` does not require the new beneficiary to already be a registered `AptosCoin` holder — a background engineer should read the exact `update_beneficiary` function body in `vesting.move` to confirm before treating this as an exploitable finding.

    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

    public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
        distribute(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);
        assert!(pending_active_stake == 0, error::invalid_state(EPENDING_STAKE_FOUND));

        // Unlock all remaining active stake.
        vesting_contract.state = VESTING_POOL_TERMINATED;
        vesting_contract.remaining_grant = 0;
        unlock_stake(vesting_contract, active_stake);
