### Title
Zip extraction allows symlink entries with unvalidated targets, enabling dangling symlink to escape extraction directory - (File: helpers/archives/zip_extract.go)

### Summary
`extractZipSymlinkEntry` reads the symlink target directly from the zip entry's file content and calls `os.Symlink(string(data), file.Name)` without validating that the target is relative and confined to the extraction directory. A job-controlled cache/artifact zip can therefore create a symlink named e.g. `evil` whose target is `/etc/passwd` or `../../../secret`, and any later file operation that follows that name (a subsequent `git`/build step, or a later archive/cache extraction that writes through an existing symlink) reads or writes through the dangling symlink outside the workspace.

### Finding Description
`extractZipFile` dispatches based on `file.Mode() & os.ModeType`; for `os.ModeSymlink` it calls `extractZipSymlinkEntry(file)`: [1](#0-0) . That function unconditionally uses the entry's own content as the symlink target with no path validation: [2](#0-1) . `file.Name` (the link path itself) also has no traversal validation beyond a `.git`-directory-name check (`errorIfGitDirectory`), which only rejects paths whose first cleaned component is `.git`, not `../` traversal: [3](#0-2) . `ExtractZipArchive` runs `errorIfGitDirectory` and then `extractZipFile` for every entry with no other name/target sanitization: [4](#0-3) .

By contrast, the tar+zstd extractor used elsewhere in the codebase explicitly validates the resolved path stays under the extraction root before performing any write (`filepath.Abs` + `strings.HasPrefix(path, e.dir+separator)` check), which the zip symlink path lacks entirely: [5](#0-4) . This asymmetry confirms the zip extractor is missing an equivalent confinement check for both the symlink's own name and its target.

Attacker-controlled input: any zip content a job can produce (cache archive uploaded by a job, or an artifact produced by an earlier job in the same pipeline and downloaded via `ExtractZipArchive`) is entirely attacker-controlled — file names and symlink target bytes are taken verbatim from the archive.

### Impact Explanation
Because `os.Symlink` creates the link with whatever target the attacker supplies, an entry can (a) place a symlink at an arbitrary relative path (subject only to the weak `.git` name check) and/or (b) point that symlink to an absolute host path or a path containing `../` segments. If any subsequent step in the job (later cache/artifact extraction that writes to the same name, a build script that appends to a file at that name, or a following stage of the same extraction such as `lchmod`/`processZipExtra` on that path) writes or reads through the dangling symlink, the effective file operation targets a location outside the job workspace. This is a workspace-confinement break of the file-operations invariant, though the concrete blast radius depends on what the runner process's user is permitted to touch (typically the runner/build user's own filesystem privileges, not privilege escalation).

### Likelihood Explanation
This is trivially reachable: creating a zip with a symlink entry (`archive/zip` supports setting `os.ModeSymlink` file mode and content) is standard, and both cache extraction and artifact download flows call `ExtractZipArchive`/`ExtractZipFile` on job/pipeline-controlled zip content. No special privileges are needed beyond being a pipeline author who controls cache or artifact contents (e.g., crafting the artifact/cache zip in an earlier job stage, or a malicious dependency that gets cached).

### Recommendation
In `extractZipSymlinkEntry`, resolve and validate that the symlink target, when joined with `filepath.Dir(file.Name)`, stays within the extraction root (reject absolute targets and targets whose cleaned relative form starts with `..`), mirroring the confinement check used in `tarzstd_extractor.go`. Additionally validate `file.Name` itself the same way (as zip-slip protection for all entry types, not just `.git`), rejecting entries whose cleaned path escapes the destination root or is absolute.

### Proof of Concept
```go
func TestExtractZipSymlinkEscapesWorkspace(t *testing.T) {
    testInWorkDir(t, func(t *testing.T, fileName string) {
        f, err := os.Create(fileName)
        require.NoError(t, err)
        archive := zip.NewWriter(f)

        hdr := &zip.FileHeader{Name: "evil_link"}
        hdr.SetMode(os.ModeSymlink | 0777)
        w, err := archive.CreateHeader(hdr)
        require.NoError(t, err)
        _, err = w.Write([]byte("/etc/passwd")) // or "../../../etc/passwd"
        require.NoError(t, err)
        require.NoError(t, archive.Close())
        f.Close()

        err = ExtractZipFile(fileName)
        require.NoError(t, err) // current code succeeds silently

        target, err := os.Readlink("evil_link")
        require.NoError(t, err)
        // Expect this to fail after fix: link target must be confined
        assert.False(t, filepath.IsAbs(target), "symlink target must not be absolute/outside workspace")
    })
}
```
Expected (post-fix) assertion: extraction of an entry whose symlink target is absolute or resolves outside the destination directory should either be rejected (`ExtractZipFile` returns/logs an error and skips the entry) or the target should be rewritten/confined, so `os.Readlink("evil_link")` never yields a path escaping the workspace.

```go
func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
```

```go
		}
```
