### Title
A second `requestWithdraw` overwrites `lastWithdrawRequest`, skipping the loss-adjusted claim path and paying a haircutted receipt at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records which epoch carries a realized-loss haircut by storing the recovery price in `lossRecoveryPriceByEpoch[epochNumber]` when `collectWithdrawFunds` is called with less than `pendingWithdraws`. The user-side lookup key for that haircut is `lastWithdrawRequest[_user]`. Because `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]` with the new epoch, a user with a loss-adjusted receipt can simply file a fresh withdrawal request in a later epoch. The loss-adjusted claim path then reads the wrong (new) epoch, finds no recovery price, and the old haircutted basis remains in `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch` to be paid at par by `_claimFundedWithdrawRequest`. This is the vault analog of a use-after-free: stale claim state is reused after the bookkeeping that should have enforced its haircut has been overwritten.

### Finding Description
When `stopEpochWithDuration` realizes a loss and the borrower funds only part of `pendingWithdraws`, `collectWithdrawFunds` zeroes `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber] = funded * RECOVERY_FULL / pendingBasis` (lines 411-430). The per-user receipt (`withdrawsRequests`, `withdrawsRequestsByEpoch`, `lastWithdrawRequest`) is intentionally left untouched so each user can later claim the haircutted amount.

At claim time, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which derives the claim epoch solely from `lastWithdrawRequest[_user]` (lines 789-801):

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

There is no per-epoch scan and no secondary marker of which epoch had a loss. `requestWithdraw` (lines ~250-295) does not force settlement of a prior request; it just sets `lastWithdrawRequest[_user] = currentEpoch` and accumulates the new amount into `withdrawsRequests`/`withdrawsRequestsByEpoch`. So the attack is:

1. Epoch N: attacker requests withdraw of `_amount`; `lastWithdrawRequest = N`, `withdrawsRequestsByEpoch[user][N] = _amount`.
2. `stopEpochWithDuration` realizes a loss; `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL` and the strategy receives only `p * basis` underlying for the pending bucket.
3. Epoch N+k (running): attacker calls `requestWithdraw` again with a dust amount (e.g. 1 wei of tranche). `lastWithdrawRequest` becomes N+k, and `withdrawsRequests[user]` still contains the full epoch-N basis plus the dust.
4. After the next `stopEpoch`, `epochNumber > lastWithdrawRequest` so the funded-claim gate passes. `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[N+k]` (no loss that epoch → 0) and returns early. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[user]` — the full pre-haircut epoch-N basis — at par via `_transferFundedClaim`.

No existing guard stops this: `deleteWithdrawRequest`-style clearing does not exist in the vault, `_clearWithdrawClaimForEpoch` is only reached if the correct epoch is looked up, and the funded-claim path has no way to know part of `withdrawsRequests` belonged to a loss epoch.

### Impact Explanation
Direct theft / insolvency. The attacker recovers `claimBasis` instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL`. The excess `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` is paid from underlying that was funded for other pending receipts or belongs to active tranche holders, breaking the loss-socialization invariant (`previewLossAdjustedWithdrawFunds` explicitly splits realized loss between pending receipts and active LPs). Loss magnitude scales with the realized-loss haircut: with e.g. a 50% recovery price on a 1M USDC pending receipt, the attacker extracts an extra ~500k USDC, leaving later claimants or LPs short by the same amount.

### Likelihood Explanation
High once a loss epoch occurs. The attacker is an ordinary tranche-token holder / withdraw requester (unprivileged). Preconditions: a `stopEpochWithDuration` with `_lossAmount > 0` that assigns part of the loss to pending receipts (a supported, manager-driven flow), and the ability to file a new `requestWithdraw` in a subsequent running epoch — which is unrestricted for any KYC-allowed wallet holding tranche tokens (or a dust amount acquirable on secondary). The cost of the trigger transaction is one dust withdraw request.

### Recommendation
Track the loss epoch explicitly instead of deriving it from `lastWithdrawRequest`. Options:

- Store a per-user/per-epoch loss marker, e.g. `lossEpochOf[_user] = epochNumber` set lazily, or iterate `withdrawsRequestsByEpoch` keys — simplest robust fix: in `requestWithdraw`, before overwriting `lastWithdrawRequest`, check `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and either force-settle the loss-adjusted claim (`_claimLossAdjustedWithdrawRequest(_user)` inside `requestWithdraw`) or revert until the user claims.
- Alternatively, in `_claimLossAdjustedWithdrawRequest`, scan the user's request epochs (or keep a separate `lossRequestEpoch[_user]` mapping set at request time) rather than trusting the mutable `lastWithdrawRequest` pointer.

A regression test should cover: request → loss-adjusted `stopEpochWithDuration` → new `requestWithdraw` → claim pays at most the haircutted amount.

### Proof of Concept
Foundry fork/test PoC sketch (adapt `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices` and the loss-adjusted flow in `test/foundry/IdleCDOEpochQueue.t.sol:811-858`):

```solidity
function testLossAdjustedReceiptPaidAtParAfterReRequest() external {
    // setup: deposit, start epoch, attacker requests withdraw in epoch N
    uint256 req = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // borrower funds only 50% of pending basis -> lossRecoveryPriceByEpoch[N] = RECOVERY_FULL/2
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 lossAmount = /* activeLoss share so that pendingToFund = pendingBasis/2 */;
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    deal(underlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount);

    // attacker does NOT claim; waits for a running epoch and re-requests dust
    vm.prank(manager);
    cdoEpoch.startEpoch();
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // overwrites lastWithdrawRequest

    vm.warp(cdoEpoch.epochEndDate() + 1);
    // borrower fully funds this epoch
    _stopEpochAndCheckPrices(...);

    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // BUG: got == full pre-haircut basis + dust, not basis * 50%
    assertGt(got, req * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL);
}
```

Expected: the assertion passes, demonstrating the epoch-N haircut is skipped and the receipt is paid at par, draining funds owed to other claimants.
