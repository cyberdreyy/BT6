### Title
Job-run authorization is not scoped to the authenticated principal, letting any External-Initiator credential trigger arbitrary job runs via `RunJobV2` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` and the `userOrEI` route group treat any successfully authenticated External Initiator (EI) exactly like a "Run"-role user, without binding the authenticated principal to any specific job or bridge. Because `AuthenticateExternalInitiator` unconditionally injects a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` into the Gin context, `RequiresRunRole` and the `isUser` check inside `Create` cannot distinguish "a real Run-role user" from "any EI holding valid AccessKey/Secret for bridge A", nor can they restrict which job ID that EI is allowed to trigger.

### Finding Description
- `core/web/router.go` wires `POST /v2/jobs/:ID/runs` behind `userOrEI := r.Group("/v2", auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession))` then `auth.RequiresRunRole(prc.Create)` [1](#0-0) .
- `AuthenticateExternalInitiator` authenticates the EI via `AccessKey`/`Secret` headers, then sets a **generic** session user object with `Role: clsessions.UserRoleRun`, with no reference to which bridge/EI it is or which job(s) it's permitted to run: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [2](#0-1) .
- `RequiresRunRole` only checks `user.Role != UserRoleView`, so this synthetic EI-derived user passes identically to any legitimate human Run-role user [3](#0-2) .
- Inside `Create`, the code calls `_, isUser := auth.GetAuthenticatedUser(c)` merely to check whether *any* `SessionUserKey` object exists, then parses `idStr` as an arbitrary int32 job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` with no ownership, ACL, or bridge-scoping check tying the job ID to the specific EI (or user) that authenticated [4](#0-3) .
- `RunJobV2` itself performs `jobORM.FindJob(ctx, jobID)` on whatever `jobID` is supplied, with no check that this job belongs to the calling EI's bridge [5](#0-4) .

However, `RunJobV2` also contains a build-mode gate:
```go
if build.IsProd() {
    return 0, errors.New("manual job runs not supported on secure builds")
}
```
with the comment "Only used for local testing, not supported by the UI" [6](#0-5) . This means that on an official/secure ("prod") build, `POST /v2/jobs/:ID/runs` unconditionally fails for *every* caller (user or EI), regardless of role. I was unable to fully trace the definition of `build.IsProd()` in this index (the `build` package source was not resolvable via search), so I cannot confirm with certainty whether self-compiled/community node builds default to `IsProd()==true` or `false`. This materially affects real-world exploitability and is the actual mitigating control against the described bypass.

Historically, EI-triggered runs were bound to a specific job via webhook UUIDs, but that path has been explicitly removed: `Create` rejects UUID-form IDs with `job.ErrJobTypeRemoved` ("cannot run job of type %q") before reaching the int32 branch [7](#0-6) . So the only remaining reachable path for an EI is the unscoped int32 `RunJobV2` call, gated solely by the `IsProd()` check, not by any job/bridge ownership check.

### Impact Explanation
If `build.IsProd()` evaluates to `false` for a given deployed node (e.g., self-built binaries, dev/test configurations, or any build lacking the official release ldflags), any holder of valid EI credentials for one bridge can trigger pipeline runs on **any** job by ID, entirely unrelated to that EI's associated bridge, potentially causing unintended on-chain transactions (ETH tx tasks, VRF fulfillment simulations, etc.) tied to jobs it has no legitimate relationship with. This matches "unauthorized job run" impact class. On builds where `IsProd()` is `true`, this specific endpoint is fully disabled for all callers, eliminating the impact.

### Likelihood Explanation
- Requires: a valid EI `AccessKey`/`Secret` for any bridge (low-privilege credential, not necessarily powerful), and the target node running in a non-"secure"/non-prod build mode.
- If those preconditions hold, the exploit is trivial and repeatable: a single unauthenticated-EI POST request with arbitrary job ID.
- The severity is capped by the `IsProd()` guard in `RunJobV2`, whose exact default across deployment types could not be conclusively determined from the indexed code.

### Recommendation
- Do not rely solely on a build-mode flag to gate this class of bug; enforce job/bridge scoping explicitly. Have `AuthenticateExternalInitiator` store the concrete `ExternalInitiator` (already done via `SessionExternalInitiatorKey`) and have `PipelineRunsController.Create` check `auth.GetAuthenticatedExternalInitiator(c)` explicitly (not merely `isUser`) and reject/limit EI-triggered runs to jobs associated with that EI's bridge, or remove EI eligibility from this route entirely given webhook/UUID-based job binding was already removed.
- Consider removing the `userOrEI` grouping from `POST /v2/jobs/:ID/runs` since the only functioning code path (`RunJobV2`) is explicitly documented as "local testing" only and not meant for EI or production use.

### Proof of Concept
Handler-level Go integration test plan (mirroring `core/web/pipeline_runs_controller_test.go` patterns):
1. Start a test `chainlink.Application` with `build.IsProd()` false (default test build).
2. Create two distinct jobs, Job A (associated with Bridge A) and Job B (unrelated bridge/job).
3. Create External Initiator `EI_A` via `POST /v2/external_initiators` (Edit-role user), capturing its `AccessKey`/`Secret`.
4. Issue `POST /v2/jobs/<JobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-AccessKey-Secret` set to `EI_A`'s credentials.
5. Assert current behavior: HTTP 200 with a `pipelineRun` resource for Job B is returned (bug reproduced) — expected/fixed behavior: HTTP 401/403 since `EI_A` has no relationship to Job B.
6. Additionally add a companion test compiling/running with `IsProd()` forced true (e.g., via build tag or dependency injection) to confirm the endpoint is blocked in that mode, establishing the exact boundary of exploitability.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
