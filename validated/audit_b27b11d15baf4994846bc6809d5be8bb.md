### Title
Stale `lastWithdrawRequest` lets an old loss-adjusted receipt be re-claimed at par, overpaying the user with other claimants' funded reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch` at the *latest* request epoch (`lastWithdrawRequest[_user]`). If a user has a loss-adjusted (partially funded) receipt in epoch E and then files a new withdraw request in a later epoch F, the loss-adjusted leg is never cleared at its haircut price. Instead, epoch E's claim basis remains inside the aggregate `withdrawsRequests[_user]` and is paid out **at par** by `_claimFundedWithdrawRequest`. This is the vault analog of a use-after-free / dangling-reference bug: the per-epoch loss price is keyed by a stale epoch pointer, so already-"freed" (haircut) receipt value is used again at full value.

### Finding Description
- `stopEpochWithDuration`-style partial funding calls `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws`, which stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` [1](#0-0) . The vault therefore only holds the haircut amount for that epoch's receipts.
- On claim, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` — i.e., only the **most recent** request epoch [2](#0-1) .
- `_clearWithdrawClaimForEpoch` clears `lastWithdrawRequest[_user]` to 0 only when it equals the claimed epoch, and decrements `withdrawsRequests[_user]` by the cleared epoch's `withdrawsRequestsByEpoch` piece [3](#0-2) .
- Attack path (running-epoch, normal mode, post-upgrade `defaultRecoveryInitialized == true`):
  1. User deposits via `idleCDO.depositAA/BB`, then calls `cdoEpoch.requestWithdraw` in epoch E.
  2. Borrower repays short; `stopEpochWithDuration`/`collectWithdrawFunds` funds only `pendingBasis - pendingLoss`; `lossRecoveryPriceByEpoch[E] < RECOVERY_FULL`.
  3. User does **not** claim. In a later epoch F the user requests withdraw again (allowed per the NOTE at line 323-324: "if a user does not claim … requests another withdraw"). `lastWithdrawRequest[user]` is now F.
  4. After epoch F ends, `claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` computes `lossRecoveryPriceByEpoch[F] == 0` → returns 0, leaving E's `withdrawsRequestsByEpoch[user][E]` intact.
  5. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[user]` — which still includes E's full pre-haircut `normalAmount` — **at par**, and burns the corresponding receipt [4](#0-3) .
- The funded-claim guard only protects `defaultRecoveryReserve`; it does not segregate other users' funded receipts [5](#0-4) . The shortfall (`claimBasis_E * (1 - lossRecoveryPrice)`) is paid out of underlyings reserved for other pending/funded claimants.
- The same stale-epoch logic can strand funds in the inverse direction: a *defaulted* claim cleared via `_claimDefaultedWithdrawRequest` zeroes `lastWithdrawRequest`, after which a separate older loss-adjusted epoch can never be located again (lossEpoch becomes 0/F), though the par-payment path above is the exploitable direction.

### Impact Explanation
Direct theft/insolvency: the attacker recovers the haircut portion of their own loss-adjusted receipt that was never funded, paid from other users' funded withdraw reserves. Quantified loss ≈ `claimBasis_E × (1 − lossRecoveryPriceByEpoch[E]/RECOVERY_FULL)`. With a 50% recovery price and a 100k USDC receipt, the attacker extracts ~50k USDC of other claimants' funds; the last claimants' receipts revert on insufficient balance (permanent freezing of their payouts). Broken invariants: loss waterfall socialization and "one receipt one haircut payout"; solvency of the funded-claim reserve.

### Likelihood Explanation
Medium-high. Requires (a) a `stopEpochWithDuration`-style partial funding that sets `lossRecoveryPriceByEpoch` (an honest-manager/borrower-driven event, per scope rules), and (b) the attacker simply holding two requests across epochs and claiming after the later one — no privileged action needed by the attacker. The bug-class hint (use-after-free via stale pointer after mutation) maps cleanly: `lastWithdrawRequest` is a single-slot "pointer" overwritten by the newer request, orphaning the keyed loss price. Caveat: I verified the claim/clear logic but not `requestWithdraw`'s exact bookkeeping of `lastWithdrawRequest`/`withdrawsRequestsByEpoch` in this iteration; the PoC assumes `requestWithdraw` sets `lastWithdrawRequest[user] = epochNumber` and accumulates `withdrawsRequestsByEpoch` per epoch, consistent with `_clearWithdrawClaimForEpoch` and the queue tests. If `requestWithdraw` instead blocks re-requesting while a loss-adjusted receipt is pending, this is not exploitable.

### Recommendation
Track loss-adjusted claims independently of `lastWithdrawRequest`: either iterate/record all epochs with a nonzero `lossRecoveryPriceByEpoch` receipt for the user (e.g., a per-user list of pending claim epochs), or have `requestWithdraw` refuse (or first settle) when `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0`. At minimum, in `_claimLossAdjustedWithdrawRequest`, check all epochs where `withdrawsRequestsByEpoch[user][e] != 0` against `lossRecoveryPriceByEpoch[e]`, not just the latest epoch.

### Proof of Concept

```solidity
// contracts: IdleCDOEpochVariant cdoEpoch; IdleCreditVault vault; underlying USDC
function testLossAdjustedReceiptRepaidAtPar() external {
    address victim = makeAddr('victim');   // honest funded claimant
    address attacker = makeAddr('attacker');

    // Epoch E buffer: both deposit
    _depositWithUser(victim, 100_000e6);
    uint256 aTranches = _depositWithUser(attacker, 100_000e6);
    _requestWithdrawWithUser(attacker, aTranches);      // request in epoch E
    _requestWithdrawWithUser(victim, tranche.balanceOf(victim));

    vm.prank(manager); cdoEpoch.startEpoch();
    // Borrower repays only ~50% of pending basis -> loss-adjusted funding
    _stopEpochWithDurationLoss( /* loss ~= 50% of pendingBasis */ );
    // vault.collectWithdrawFunds got _amount < pendingWithdraws =>
    // lossRecoveryPriceByEpoch[E] = ~0.5e18, pendingWithdraws = 0

    // Attacker does NOT claim; deposits again and requests withdraw in epoch F
    _depositWithUser(attacker, 10_000e6);
    _requestWithdrawWithUser(attacker, tranche.balanceOf(attacker));
    // lastWithdrawRequest[attacker] = F

    vm.prank(manager); cdoEpoch.startEpoch();
    _stopCurrentEpoch(); // epoch F fully funded

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // BUG: epoch-E receipt paid at par instead of ~50%
    assertGt(got, expectedFundedF + claimBasisE * 1e18 / 2, 'E overpaid at par');
    // victim's later claim reverts / is underpaid by the drained reserve
}
```

Key assertion: the vault's funded balance only ever received `claimBasisE * lossRecoveryPrice`, yet `_claimFundedWithdrawRequest` transfers the full `withdrawsRequests[attacker]` (E basis + F basis), so `got` exceeds what was funded for E — the delta is taken from reserves backing `victim`'s receipt.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
