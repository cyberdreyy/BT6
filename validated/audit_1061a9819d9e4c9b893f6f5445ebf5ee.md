## Verdict

Based on the code available, this is a **valid but different bug** from what the question hypothesizes — the root cause is not "the server ignores `ctx.Done()`" (that's an unverifiable claim about the external `step-runner` dependency), but a **missing explicit `Cancel` RPC in `runUserSteps`**, unlike the sibling code path in `steps/execute.go`.

### Title
Nested `run:` step dispatch never issues a graceful `Cancel` RPC, only tears down the client-side follow stream - (`functions/concrete/run/run_steps.go`)

### Summary
`(r *Runner).runUserSteps` dispatches a job's `run:` keyword to the shared step-runner socket and only relies on cancelling the local `scriptCtx` passed into `cli.RunAndFollow(ctx, ...)`. Unlike the outer/top-level dispatch path in `steps/execute.go`, which explicitly registers a callback that issues `c.Cancel(cancelCtx, request.Id)` on cancellation, `runUserSteps` never calls the equivalent `Cancel` RPC for the nested request.

### Finding Description
`Runner.Cancel()` cancels `r.scriptCancel`, which — for a `run:` step — is the `cancel` func installed in `runRunSteps` via `r.setCancel(cancel)` [1](#0-0) . That cancels `scriptCtx`, which is the `ctx` argument to `runUserSteps` and is passed straight into `cli.RunAndFollow(ctx, req, out)` [2](#0-1) .

Compare this to `steps/execute.go`'s `Execute`, which is the code path used for the outer/whole job: it registers a `RegisterCancel` callback whose body explicitly calls `c.Cancel(cancelCtx, request.Id)` against the step-runner server — documented as the mechanism that lets "step-runner run its post-cancel phases (e.g. cache/artifact upload) before exiting" [3](#0-2) . `runUserSteps` has no analogous call to `cli.Cancel(...)` anywhere in `run_steps.go` or in `runner.go`'s cancellation plumbing — grep across the repo shows `.Cancel(` RPC usage only in `steps/execute.go`, its tests, and unrelated files, never in `functions/concrete/run/run_steps.go`.

The test double in `steps/stepstest/server.go` documents the semantic gap precisely: `Run` returns immediately and the job is "running" until the explicit `Cancel` RPC is invoked [4](#0-3) ; `Status` only reports `cancelled` once `s.cancelled` has been closed by that RPC, otherwise it reports `running` indefinitely [5](#0-4) . `FollowLogs` does return early on either the explicit cancel or the stream context being cancelled [6](#0-5) , which is exactly what lets `runUserSteps`'s `RunAndFollow` call return and get classified as canceled by `classifyScriptContextError`/`interpretRunResult` [7](#0-6)  — but the underlying job's server-side `Status` (per this model) never actually transitions away from `running`, because no `Cancel` RPC was ever sent for it.

### Impact Explanation
If the real `step-runner` server behaves the way its own project's test double models it (job stays "running" server-side until an explicit `Cancel` RPC arrives, independent of the client's log-follow stream context), then cancelling a job whose `run:` block was dispatched as a nested step leaves the corresponding server-side execution running to completion (or indefinitely, for a long/blocking builtin) even though `gitlab-runner` reports "canceled" to GitLab and the outer client-side call returns. This matches the scoped impact: outer job reports canceled while server-side work for that tenant persists, consuming shared resources on the socket that other tenants/jobs depend on.

### Likelihood Explanation
Preconditions: a pipeline author writes a job using the `run:` keyword (nested step dispatch through concrete), and the job (or its `run:` phase specifically) is cancelled externally (user cancel, job timeout, or `script_timeout`) while the nested dispatch is in flight. This is entirely reachable by an ordinary pipeline author/user — no privileged access needed, only a normal cancel action on a job using `run:`. The bug is deterministic given the code structure: `runUserSteps` unconditionally omits the `Cancel` RPC call that the sibling `Execute` path performs, so every cancellation of a nested `run:` step takes this path, not just an edge case.

Caveat: I could not inspect the actual `step-runner` server implementation (it lives in the external `gitlab.com/gitlab-org/step-runner` module, not in this repo), so I cannot directly confirm the production server's runtime behavior beyond what its own maintained test double (`stepstest.Server`) documents. That said, the asymmetry between `steps/execute.go` (explicit `Cancel` RPC + comment explaining why it's needed) and `run_steps.go` (no such call) is a concrete, verifiable code defect in this repo regardless of the exact server-side consequence.

### Recommendation
In `runUserSteps` (or `runRunSteps`), mirror `steps/execute.go`'s pattern: on cancellation of `scriptCtx`/`jobCtx`, issue an explicit `cli.Cancel(cancelCtx, req.Id)` RPC (with a bounded timeout, independent of the now-cancelled `scriptCtx`) before/while tearing down `RunAndFollow`, so the server-side nested job actually receives a cancellation signal rather than relying solely on the follow-stream's context cancellation.

### Proof of Concept
Using the existing `steps/stepstest.Server` fake (or an equivalent minimal fake wired to `functions/concrete/run`'s `socketPath`/dialer):
1. Start `stepstest.New(t)` and point `run_steps.go`'s `socketPathOverride` at it via `SetSocketPath`.
2. Build a `Runner` with a `RunSteps` config, start `r.runRunSteps(jobCtx, steps)` in a goroutine.
3. Once the request has been sent (`Run` RPC observed), call `r.Cancel()`.
4. Assert `runUserSteps` returns promptly with a canceled error (it will, since `FollowLogs` unblocks on stream-ctx cancellation).
5. Assert `server.Cancels()` — this will be **empty**, proving no `Cancel` RPC was ever sent, i.e., the server-side job was never told to stop, only the client's follow stream was abandoned. [8](#0-7)

func interpretRunResult(status client.Status, runErr, flushErr error) error {
	if runErr == nil {
		runErr = flushErr
	}
	if runErr != nil {
		return fmt.Errorf("running user steps via step-runner: %w", runErr)
	}

	switch status.State {
	case client.StateSuccess:
		return nil
	case client.StateCancelled:
		return fmt.Errorf("%w: %s", ErrJobCanceled, status.Message)
	default:
		msg := status.Message
		if msg == "" {
			msg = status.State.String()
		}
		return errors.New(msg)
	}
}

// Options bundles the parameters Execute needs to run a step-runner job.
// RegisterCancel is optional; when set, Execute invokes it with a callback
// that issues a graceful Cancel to step-runner. The signature matches
// common.JobTrace.SetCancelFunc so callers can pass it directly. When the
// callback fires, step-runner runs its post-cancel phases (e.g.
// cache/artifact upload) before exiting, and the resulting cancelled status
// flows back as the build outcome. All fields except for RegisterCancel are required.
type Options struct {
	Connector      Connector
	JobInfo        JobInfo
	Steps          []schema.Step
	Trace          io.Writer
	RegisterCancel func(context.CancelFunc)
	Log            *logrus.Entry
}

func Execute(ctx context.Context, opts Options) error {
	dialFn, err := opts.Connector.Connect(ctx)
	if err != nil {
		return fmt.Errorf("creating connect dialer: %w", err)
	}

	dialer := &stdioDialer{dialFn: dialFn}
	c, err := extended.New(dialer)
	if err != nil {
		return fmt.Errorf("creating steps client: %w", err)
	}
	//nolint:errcheck
	defer c.CloseConn()

	out := extended.FollowOutput{Logs: opts.Trace}

	request, err := NewRequest(opts.JobInfo, opts.Steps)
	if err != nil {
		return fmt.Errorf("creating steps request: %w", err)
	}

	if opts.RegisterCancel != nil {
		opts.RegisterCancel(func() {
			// this context is for the Cancel request only.
			cancelCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
			defer cancel()
			if err := c.Cancel(cancelCtx, request.Id); err != nil {
				opts.Log.WithError(err).Warn("Failed to cancel step-runner job")
			}
		})
	}

// Cancels returns a snapshot of the job IDs the server has received Cancel
// RPCs for, in arrival order.
func (s *Server) Cancels() []string {
	s.mu.Lock()
	defer s.mu.Unlock()
	return append([]string(nil), s.cancels...)
}

// Connector returns a value implementing steps.Connector that dials this
// in-process server. The returned Connector can be passed directly into
// steps.Options or steps.Execute.
func (s *Server) Connector() *Connector {
	return &Connector{listener: s.listener}
}

// Run accepts the request and returns immediately; the job is treated as
// "running" until Cancel is invoked.
func (s *Server) Run(_ context.Context, _ *proto.RunRequest) (*proto.RunResponse, error) {
	return &proto.RunResponse{}, nil
}

// Cancel records the job ID and unblocks any in-flight FollowLogs streams.
// Repeated calls are recorded but only signal once.
func (s *Server) Cancel(_ context.Context, req *proto.CancelRequest) (*proto.CancelResponse, error) {
	s.mu.Lock()
	first := len(s.cancels) == 0
	s.cancels = append(s.cancels, req.Id)
	s.mu.Unlock()
	if first {
		close(s.cancelled)
	}
	return &proto.CancelResponse{}, nil
}

// FollowLogs streams nothing and returns when the job is cancelled or the

func (s *Server) FollowLogs(_ *proto.FollowLogsRequest, srv grpc.ServerStreamingServer[proto.FollowLogsResponse]) error {
	select {
	case <-s.cancelled:
		return nil
	case <-srv.Context().Done():
		return srv.Context().Err()
	}
}

// Status returns proto.StepResult_cancelled / StatusError_cancelled once the
// job has been cancelled, so that extended.RunAndFollow's post-Follow Status
// query produces the same result step-runner emits after a graceful cancel.
func (s *Server) Status(_ context.Context, req *proto.StatusRequest) (*proto.StatusResponse, error) {
	select {
	case <-s.cancelled:
		return &proto.StatusResponse{Jobs: []*proto.Status{{
			Id:        req.Id,
			Status:    proto.StepResult_cancelled,
			StartTime: timestamppb.Now(),
			EndTime:   timestamppb.Now(),
			Error: &proto.StatusError{
				Kind:    proto.StatusError_cancelled,
				Message: "cancelled",
			},
		}}}, nil

		return &proto.StatusResponse{Jobs: []*proto.Status{{
			Id:        req.Id,
			Status:    proto.StepResult_running,

		}}}, nil
	}
