### Title
Withdrawal requests can be unexpectedly haircut by a management-fee update - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
An open-buffer withdrawal request is priced using the current `managementFee`, but the function accepts no minimum-output, maximum-fee, or deadline parameter. If an honest owner’s `setFeeParams` transaction is ordered before a lender’s pending `requestWithdraw`, the lender’s receipt is minted at the newly increased fee rather than the fee observed when the transaction was submitted. In APR0 mode, the fee is deducted directly from principal.

### Finding Description
`requestWithdraw` converts tranche tokens to principal, calculates projected interest, deducts `_totalWithdrawFees`, and creates a fixed withdrawal receipt for the reduced amount. [1](#0-0)  The fee calculation charges an upfront annualized management fee over the next epoch plus any remaining buffer, and it can consume principal whenever the management fee is greater than projected interest. [2](#0-1)  `setFeeParams` updates `managementFee` immediately and allows a maximum annual rate of `MAX_FEE / 10`, or 10%. [3](#0-2) 

For example, during the buffer phase with a 365-day epoch and APR0 accounting, a lender observing a 0% management fee submits a withdrawal for 10,000 USDC of tranche principal. The owner submits a valid update to a 10% management fee. If the owner transaction executes first through ordinary ordering, a reorganization, gas pricing, or a delayed mempool transaction, `requestWithdraw` creates a receipt for only 9,000 USDC and records 1,000 USDC as pending fees. The 10% calculation follows `_nav * managementFee * duration / (FULL_ALLOC * 365 days)`. [4](#0-3) 

The existing guards do not prevent this sequence: the lender can pass KYC, withdrawal requests can remain enabled, and the strategy stores the post-fee APR0 principal without validating the lender’s expected payout. [5](#0-4) 

### Impact Explanation
The lender suffers an unexpected reduction in claimable underlying. With a 365-day epoch and the maximum 10% annual management fee, a 10,000-underlying request loses 1,000 underlying to fees. The impact scales with `epochDuration + remainingBuffer`; longer configured epochs produce a larger immediate principal haircut. The reduced amount is fixed into the withdrawal receipt, so the user cannot later recover the difference merely because the fee changed after transaction submission.

### Likelihood Explanation
No malicious privileged action is required. The sequence only needs a routine owner fee update to execute before an already-submitted withdrawal request. `requestWithdraw` provides no slippage bound that would revert when the fee differs from the lender’s expectation. The likelihood is constrained by the need for a parameter update to coincide with a pending user transaction and by the 10% annualized management-fee cap, but the resulting loss can still be material.

### Recommendation
Add a lender-controlled `minUnderlyingsOut` or `maxTotalFees` parameter to `requestWithdraw`, and optionally a deadline. Revert if the calculated receipt is below the supplied bound. Alternatively, schedule management-fee changes so they apply only to requests submitted after the update becomes effective, or use a timelock for fee parameter changes. Equivalent protection should also be considered for `depositDuringEpoch`, whose minted amount depends on current fee parameters.

### Proof of Concept
Add this test to `test/foundry/IdleCreditVault.t.sol`. The existing fork setup deploys `IdleCDOEpochVariant` and `IdleCreditVault` on mainnet fork block `18678289`. [6](#0-5) 

```solidity
function testRequestWithdrawFeeUpdateOrdering() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Configure a one-year epoch and APR0 mode. Management fee starts at zero.
    vm.prank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    vm.prank(owner);
    cdoEpoch.setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    uint256 trancheAmount = IERC20(address(AAtranche)).balanceOf(address(this));
    uint256 expectedAtSubmission = cdoEpoch.maxWithdrawable(
        address(this),
        address(AAtranche)
    );
    assertEq(expectedAtSubmission, trancheAmount * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN);

    // Honest owner update is ordered before the user's pending requestWithdraw.
    uint256 newManagementFee = 10_000; // 10% annualized, the configured maximum.
    vm.prank(owner);
    cdoEpoch.setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, newManagementFee);

    uint256 requested = cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));

    // 10% annual fee over a 365-day request period cuts principal by 10%.
    uint256 unexpectedFee = expectedAtSubmission / 10;
    assertEq(requested, expectedAtSubmission - unexpectedFee);
    assertEq(cdoEpoch.pendingWithdrawFees(), unexpectedFee);
    assertEq(
        IdleCreditVault(address(strategy)).apr0TotalPrincipal(),
        expectedAtSubmission - unexpectedFee
    );
}
```
