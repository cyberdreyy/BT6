### Title
Wrong-variable length check in `Store.List` allows a slice-bounds panic on masking-secret store entries - (File: `commands/helpers/internal/store/store.go`)

### Summary
`Store.List` validates the length of a decoded ciphertext against the length of its *pre*-decode, base64-encoded representation instead of the decoded byte slice, mirroring the external report's root cause: a length parameter that references the wrong buffer/encoding, letting malformed input reach a fixed-size slice operation.

### Finding Description
In `commands/helpers/internal/store/store.go`, `List()` reads base64 lines from `masking.db` and is supposed to guard against messages shorter than the AEAD nonce before slicing: [1](#0-0) 

The check `len(line) < s.c.NonceSize()` is performed on `line`, the raw base64 **string** (including its trailing `\n`), while the actual slice operation `msg[:s.c.NonceSize()], msg[s.c.NonceSize():]` operates on `msg`, the base64-**decoded** byte slice. Because base64 encoding expands data by roughly 4/3, `len(line)` is always larger than `len(msg)`. This is exactly the class of bug flagged in the external report: using the wrong length reference (there, `durationOffset_`/`_msg.length` instead of the correct fixed field sizes; here, the encoded length instead of the decoded length) when validating/slicing a decoded buffer.

For `chacha20poly1305.NewX`, `NonceSize()` is 24 bytes. A line whose base64 form is ≥24 characters can still decode to fewer than 24 raw bytes (e.g., a 24-character base64 string decodes to 18 bytes). In that case the length check passes (`len(line) >= 24`) but `msg` has only 18 bytes, so `msg[:24]` triggers a Go runtime slice-bounds-out-of-range panic instead of the intended graceful `"encrypted message length too small"` error.

### Impact Explanation
A panic in `List()` crashes the `gitlab-runner-helper proxy-exec` process that owns the masking store (constructed via `NewProxy`/`store.Open` in `commands/helpers/proxy_exec.go`, lines 45-59), which is invoked to add secret-masking phrases while proxying a job's stdout/stderr. A crash here disrupts job execution/masking for that job. However, note that `Store.Add` (the only code path that writes to `masking.db`) always writes well-formed `nonce || ciphertext` before base64-encoding it, so a properly functioning writer can never itself produce a line that triggers this panic — the malformed line has to originate from file corruption (e.g., a crash mid-write, disk-full truncation, or concurrent/interleaved writers to the same `masking.db` without any file locking) rather than a remote/network attacker-supplied payload.

### Likelihood Explanation
Exploitation likelihood is low to moderate. There is no direct externally-attacker-controlled path analogous to the Solidity codec (no untrusted network message is decoded here) — the only way to reach the buggy branch is for `masking.db` itself to already contain corrupted/truncated data. This can plausibly happen from a partial/interrupted write (crash, OOM-kill, disk pressure) between `f.Write` and `f.Sync` in `Store.Add`, or from unsynchronized concurrent writers, rather than from a hostile CI job payload. This weakens the case versus a pure remote-input decoding bug but the underlying coding defect — checking the wrong buffer's length before a fixed-size slice — is a legitimate correctness/robustness bug and a real analog of the reported vulnerability class.

### Recommendation
Validate the length of the decoded `msg`, not the encoded `line`, before slicing:
```go
msg, err := base64.StdEncoding.DecodeString(strings.TrimSuffix(line, "\n"))
if err != nil {
    return results, fmt.Errorf("decoding msg: %w", err)
}

if len(msg) < s.c.NonceSize() {
    return results, fmt.Errorf("encrypted message length too small")
}

nonce, ciphertext := msg[:s.c.NonceSize()], msg[s.c.NonceSize():]
```
This ensures the length check and the slice operation use the same buffer, preventing the panic regardless of how the corrupted line was produced.

### Proof of Concept
1. Craft a base64 string that is ≥24 characters long but decodes to fewer than 24 bytes, e.g. `"AAAAAAAAAAAAAAAAAAAAAAA="` (24 chars, decodes to 17 bytes) followed by `\n`.
2. Write this line directly at offset 32 into an existing `masking.db` file (simulating file corruption/partial write), leaving the 32-byte key header intact so `store.Open` succeeds.
3. Call `Store.List()` on that store.
4. `len(line)` (25, including `\n`) is `>= 24`, so the length guard passes; but `len(msg)` is 17, so `msg[:24]` panics with `slice bounds out of range [:24] with capacity 17`, crashing the calling process instead of returning the intended `"encrypted message length too small"` error. func (s *Store) List() ([]string, error) {
```go
	buf := bufio.NewReader(io.NewSectionReader(s.f, 32, math.MaxInt64))

	var results []string
	for {
		line, err := buf.ReadString('\n')
		if err != nil {
			if errors.Is(err, io.EOF) {
				return results, nil
			}
			return results, err
		}

		msg, err := base64.StdEncoding.DecodeString(line)
		if err != nil {
			return results, fmt.Errorf("decoding msg: %w", err)
		}

		if len(line) < s.c.NonceSize() {
			return results, fmt.Errorf("encrypted message length too small")
		}

		nonce, ciphertext := msg[:s.c.NonceSize()], msg[s.c.NonceSize():]
		plaintext, err := s.c.Open(nil, nonce, ciphertext, nil)
		if err != nil {
			return results, fmt.Errorf("opening encrypted message: %w", err)
		}

		results = append(results, string(plaintext))
	}
```
