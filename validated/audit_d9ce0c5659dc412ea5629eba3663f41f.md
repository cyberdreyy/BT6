### Title
Permissionless `solend_init_obligation` allows front-running to permanently bind a bank's Solend obligation to an attacker-chosen `lending_market` - (File: programs/marginfi/src/instructions/solend/init_obligation.rs)

### Summary
`solend_init_obligation` is explicitly documented as `(permissionless)` [1](#0-0) , and its `SolendInitObligation` account struct requires only an arbitrary `Signer` as `fee_payer`, with `lending_market` and `lending_market_authority` accepted as unchecked accounts "validated by the Solend program" [2](#0-1) . The obligation PDA (`integration_acc_2`) is derived solely from `[SOLEND_OBLIGATION_SEED, bank.key()]` and created via Anchor's `init` constraint, meaning whoever calls this instruction first permanently fixes the `lending_market` value baked into the Solend obligation, with no marginfi-side validation tying it to the bank's actual reserve/market.

### Finding Description
`lending_pool_add_bank_solend` (admin-only) fixes `bank.integration_acc_1` (the Solend reserve) at bank-creation time and derives the obligation PDA address, but does not initialize it nor store any `lending_market` value on the `Bank` account [3](#0-2) [4](#0-3) . The obligation itself is only created later by `solend_init_obligation`, which is permissionless [1](#0-0) .

In `SolendInitObligation`, `integration_acc_2` uses `init` with `seeds = [SOLEND_OBLIGATION_SEED, bank.key()]`, so it can only ever be initialized once for a given bank [5](#0-4) . `lending_market` and `lending_market_authority` are `UncheckedAccount`s with no `has_one`, `address`, or cross-account constraint linking them to `integration_acc_1` (the reserve) or any bank-stored field [6](#0-5) . `cpi_init_obligation` passes these directly into the Solend `InitObligation` CPI, which persists `lending_market` into the obligation's on-chain state, signed only by the bank's own `liquidity_vault_authority` PDA (so the *owner* is always correct, but the *market* is attacker-controlled) [7](#0-6) .

Because the only requirement to call this instruction is `require_gte!(amount, 10, ...)` and holding ≥10 native units of the bank mint plus SOL for rent [8](#0-7) , an unprivileged attacker can front-run the legitimate integration flow by submitting `solend_init_obligation` first with a `lending_market`/`lending_market_authority` pair from a market they control (Solend's own `InitLendingMarket` is itself permissionless), permanently fixing the obligation's `lending_market` field to that rogue market. Since the obligation PDA is `init`-only (cannot be re-initialized) and no reset/close instruction was found in the codebase, this binding is durable.

Downstream, `solend_deposit`/`solend_withdraw` similarly accept `lending_market` as an unchecked account with no on-chain validation against the reserve or obligation's actual stored market [9](#0-8) ; the only cross-check performed is `validate_solend_obligation(integration_acc_2, integration_acc_1.key())`, which checks the obligation-reserve relationship, not the lending market [10](#0-9) . When the legitimate team later attempts to deposit using the real reserve's actual lending market, the real Solend program's own invariant (obligation.lending_market must match the supplied `lending_market_info`, and reserve.lending_market must also match) will reject the CPI, since the obligation was bound to the attacker's rogue market rather than the reserve's real market.

### Impact Explanation
This is a durable freeze/corruption of the bank's Solend integration: once front-run, the obligation PDA for that bank is permanently bound to the wrong market and can never be reinitialized against the correct one (no reset path found), bricking all future `solend_deposit`/`solend_withdraw` operations for that bank and any funds already routed toward it. This is a genuine authorization/binding bypass (permissionless helper hijacking an integration-critical, otherwise admin-scoped binding) rather than a pure liquidity or DoS-by-traffic issue, and it has direct financial impact: the admin's nominal nonrecoverable nominal nominal deposit is lost, and the bank becomes unusable until abandoned and recreated with a new `bank_seed`.

### Likelihood Explanation
Highly feasible: the precondition is only that `lending_pool_add_bank_solend` has run but `solend_init_obligation` has not yet been called for that bank — an inherently racy window in any real deployment pipeline (bank creation and obligation initialization are two separate transactions/instructions with no atomicity or access control tying them together). Any attacker monitoring for newly created Solend banks can submit `solend_init_obligation` with a self-created Solend lending market before the legitimate integration team's transaction lands, requiring only a small token balance (≥10 units) and normal transaction fees.

### Recommendation
Restrict `solend_init_obligation` to the group/bank admin (e.g., require `has_one = admin` similar to `lending_pool_add_bank_solend`), or store the expected `lending_market`/`lending_market_authority` (and their canonical derivation) on the `Bank` account at `lending_pool_add_bank_solend` time and enforce `has_one`/`address` constraints on those accounts in `SolendInitObligation`, `SolendDeposit`, and `SolendWithdraw` so an arbitrary caller cannot bind or later manipulate the market association.

### Proof of Concept
1. Admin calls `lending_pool_add_bank_solend` to create a Solend bank with a genuine reserve (`integration_acc_1`); obligation PDA (`integration_acc_2`) is derived but not yet created.
2. Before the admin calls `solend_init_obligation`, an attacker (with a funded token account holding ≥10 units of the bank mint and a small SOL balance) creates their own Solend lending market via Solend's permissionless `InitLendingMarket`/`init_lending_market`, deriving a matching `lending_market_authority`.
3. Attacker calls `solend_init_obligation(amount = 10)` against the target bank, supplying their own `lending_market`/`lending_market_authority`; assert the transaction succeeds and `integration_acc_2` (obligation) is created and owned by the Solend program.
4. Admin subsequently attempts the intended `solend_init_obligation` call again with the correct/real Solend `lending_market` — assert it fails with an Anchor `already in use` error on `integration_acc_2` (since `init` cannot re-initialize).
5. Admin attempts `solend_deposit` using the real reserve and real `lending_market` — assert the CPI to Solend's `deposit_reserve_liquidity_and_obligation_collateral` fails due to obligation/lending-market mismatch, confirming the bank's Solend integration is permanently bricked.

pub fn solend_init_obligation(ctx: Context<SolendInitObligation>, amount: u64) -> MarginfiResult {
    // Arbitrarily setting minimum deposit to 10 absolute units to always keep the obligation alive.
    // Obligations auto close when empty, but we want to keep it open for future deposits.
    require_gte!(amount, 10, MarginfiError::ObligationInitDepositInsufficient);

    let authority_bump = ctx.accounts.bank.load()?.liquidity_vault_authority_bump;

    // Initialize the obligation
    ctx.accounts.cpi_init_obligation(authority_bump)?;
```

    pub fn cpi_init_obligation(&self, authority_bump: u8) -> MarginfiResult {
        let accounts = InitObligation {
            obligation_info: self.integration_acc_2.to_account_info(),
            lending_market_info: self.lending_market.to_account_info(),
            obligation_owner_info: self.liquidity_vault_authority.to_account_info(),
            rent_info: self.rent.to_account_info(),
            token_program_info: self.token_program.to_account_info(),
        };
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), authority_bump);

        // Create CPI context with signer
        let cpi_ctx =
            CpiContext::new_with_signer(self.solend_program.key(), accounts, signer_seeds);
        init_obligation(cpi_ctx)?;
        Ok(())
    }
```
