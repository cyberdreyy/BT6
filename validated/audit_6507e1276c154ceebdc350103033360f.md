## Analysis

The report's bug class — a threshold/limit computation that fails to account for state already committed on "the other side" of the calculation, letting a quantity be double-counted — maps to a concrete flaw in the mining-node's StackerDB vote tally in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`.

### Title
Signer weight can be double-counted into both `total_weight_approved` and `total_weight_rejected` for the same block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run` maintains, per proposed block (`BlockStatus`), two independent weight tallies — `total_weight_approved` and `total_weight_rejected` — plus a `responded_signers` set meant to make each signer's vote count once. The de-duplication guards used for the two message kinds are asymmetric: the `Accepted` branch only checks `gathered_signatures.contains_key(&slot_id)`, while the `Rejected` branch checks/updates `responded_signers`. This lets a signer that first rejects and later accepts the same block have its weight added to *both* tallies, breaking the invariant that `total_weight_approved + total_weight_rejected` should never exceed `total_weight` for a single distinct-signer vote.

Here the guard is `block.responded_signers.insert(slot_id)`, which returns `false` (skipping the increment) if that slot already appears in `responded_signers` — and the `Accepted` handler does insert into `responded_signers` unconditionally at line 465. So an Accept-then-Reject sequence from the same signer is correctly guarded (the second Reject is dropped). But the reverse order is not:

1. Signer `S` sends `Rejected` for block `B`. `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += weight(S)`; `responded_signers` now contains `slot_id`.
2. Signer `S` later sends a validly-signed `Accepted` for the *same* `block_sighash` `B` (e.g., after re-evaluating the proposal, as the signer-side logic in `stacks-signer/src/v0/signer.rs` explicitly allows reconsideration after a new proposal/chainstate recheck). The `Accepted` branch only checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` → `total_weight_approved += weight(S)` as well.

The result: `weight(S)` is now counted in *both* `total_weight_approved` and `total_weight_rejected` for the same block, exactly analogous to the external report's `min()` failing to subtract out a quantity (`currentExternalUnderlyingLend`) that had already been accounted for elsewhere — here, a signer's weight already spent on the "reject" side is not excluded from the "approve" side.

### Impact Explanation
This breaks the equality the mining coordinator relies on: `total_weight_approved` is supposed to represent weight from *distinct* signers who currently support the block, used to decide when to broadcast the block as signed [4](#0-3) . Because a single signer's weight can leak into both tallies, the true "distinct approving weight" total can be inflated by that signer's own weight beyond what a straightforward per-signer accounting would allow, letting a block cross the acceptance threshold with less real, coherent distinct-signer support than the 70% invariant is meant to guarantee. This is a signer-weight aggregation vs. verified-accepts equality break, consistent with the "aggregated-weight vs verified-accepts" class called out in scope.

### Likelihood Explanation
This requires only a single StackerDB slot (one signer) sending two ordinary, validly-signed protocol messages (`Rejected` then `Accepted`) for the same block hash — no majority collusion, no other signer's key, and no auth-token/local access needed. The signer-side code path explicitly supports a signer reconsidering and re-signing after an earlier rejection once new information arrives, so this reject→accept transition is a normal, reachable sequence, not a contrived edge case.

### Recommendation
Use a single per-slot vote record (e.g. one `HashMap<u32, Vote>` mapping slot to Accepted/Rejected) rather than two independently-guarded accumulators, or gate the `Accepted` branch's weight increment on `responded_signers.insert(slot_id)` (mirroring the `Rejected` branch) so that only the first vote from a slot — in either direction — is tallied, and any subsequent vote of the opposite kind is either ignored or explicitly moves the weight from one tally to the other rather than adding to both.
