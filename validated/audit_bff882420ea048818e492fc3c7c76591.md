### Title
Missing per-project concurrency dedup in `run-single` causes identical `ProjectRealUniqueName()`/cache volume paths for concurrently-running jobs of the same project - ([File: executors/docker/internal/volumes/manager.go])

### Summary
`manager.createHostBasedCacheVolume`/`addCacheVolume` derive the cache `hostPath` (and, for Docker-volume caching, the volume name) from `m.config.UniqueName`, which is set to `Build.ProjectRealUniqueName()` [1](#0-0) . `ProjectRealUniqueName()` is a deterministic hash of `Runner.GetToken()`, `Runner.GetSystemID()`, `JobInfo.ProjectID`, and `Build.ProjectRunnerID` [2](#0-1) . Unlike the `run` (multi-runner) command, `run-single`'s `processBuild` never assigns or deduplicates `ProjectRunnerID` (it stays `0` for every job), and `GenerateUniqueSystemID()` derives the `SystemID` from the host's machine-id rather than a per-process random value, so two independent `run-single` processes on the same host, using the same runner token, will compute an identical `ProjectRealUniqueName()`/cache path for concurrent jobs of the same project.

### Finding Description
- `commands/single.go`'s `processBuild` creates a fresh `Build` per job via `common.NewBuild` and runs it synchronously (`newBuild.Run(...)`), but at no point sets/dedups `Build.ProjectRunnerID` [3](#0-2) . `ProjectRunnerID` therefore always defaults to its zero value in this command.
- Compare with `commands/multi.go`, whose `mr.buildsHelper.addBuild(build)` walks all builds currently tracked *within that one process* and increments `build.ProjectRunnerID` until it's unique for the (token, project) pair [4](#0-3) . This dedup mechanism is process-local and is simply absent from `run-single`.
- `GenerateUniqueSystemID()` first tries `machineid.ID()` (an HMAC derived from `/etc/machine-id` or platform equivalent) and only falls back to a random ID if that fails [5](#0-4) . On any normal Linux/Windows/macOS host this succeeds, so `SystemID` is **deterministic per machine**, not per process. `RunSingleCommand.Execute` only auto-generates a `SystemID` if `r.RunnerConfig.SystemID == ""` [6](#0-5) , and that generation calls the same machine-id-derived function, so two separate `run-single` processes on the same host with the same runner token will independently compute the identical `SystemID`.
- Consequently, for two jobs belonging to the same `ProjectID`, processed concurrently by two separate `run-single` processes on the same host with the same runner token: `Runner.GetToken()` (same), `Runner.GetSystemID()` (same, machine-derived), `JobInfo.ProjectID` (same), `ProjectRunnerID` (both `0`, never bumped) ⇒ `ProjectRealUniqueName()` is identical for both builds.
- This identical `UniqueName` is fed into `volumes.ManagerConfig.UniqueName` [1](#0-0) , and used to build the cache `hostPath` in `createHostBasedCacheVolume` [7](#0-6)  or the reusable Docker volume name in `createCacheVolume` [8](#0-7) . Both cache-mount code paths key the shared resource purely on `UniqueName` + a hash of the mount destination, with no per-build/per-process nonce, so two concurrently-running build containers for the two jobs end up bind-mounting (or Docker-volume-mounting) the *same* host directory / volume simultaneously, one read-write into each.
- Existing safeguards (`m.managedVolumes.Add`, protected-suffix logic) only prevent duplicate volume definitions *within* one build's own volume list; they do nothing to prevent two independent `Build`/`manager` instances (in different OS processes) from computing the same path.

### Impact Explanation
Two concurrently-executing jobs of the same project, launched via separate `run-single` worker processes sharing a runner token on the same host, get their dynamic/cache volumes mounted to the identical host path or identical Docker named volume. Each build container has full read/write access to that shared directory while the other build is actively writing to it, enabling cross-job cache poisoning (one job's build injects malicious content that another concurrently-running job unpacks/executes) or exfiltration (one job reads cache data written concurrently by the other, including any secrets a script may have staged there). This is a violation of the invariant that "file operations must stay within intended build/cache/artifact roots" and that jobs be isolated from each other's workload.

### Likelihood Explanation
Preconditions: (1) the deployer runs more than one `gitlab-runner run-single` process configured with the same runner token/config for the same runner on the same host (a documented/common pattern for adding concurrency without the full `run` multi-runner daemon), and (2) two jobs for the same project happen to be scheduled concurrently on two different worker processes. Precondition (1) is an ordinary deployment choice, not an admin security misconfiguration — nothing in the docs warns that `run-single` requires manual `ProjectRunnerID`/`SystemID` differentiation, and the machine-id-based `SystemID` generation actively works against differentiation by making the same host produce the same ID by default. Precondition (2) is entirely within reach of an unprivileged pipeline author: simply triggering two pipelines (or two parallel/retried jobs) for the same project at the same time is enough to have the scheduler dispatch both to different `run-single` workers.

### Recommendation
- Add a per-process/per-run unique salt (e.g., a random component or PID/hostname/start-time nonce) to `ProjectRealUniqueName()`/`ProjectUniqueName()` when not disambiguated by `ProjectRunnerID`, or require `run-single` to perform the same kind of dedup as `commands/builds_helper.go`'s `addBuild` (impossible across processes without shared state, so a random per-process component is the practical fix).
- Alternatively/additionally, document and enforce that each `run-single` process must be configured with a distinct, non-machine-derived `SystemID`, and fail fast (or warn loudly) if `run-single` detects it's sharing a `SystemID`+token with cache/volume state from another live process.
- Consider incorporating a random per-manager `TemporaryName`-like nonce into the *reusable* (non-temporary) cache volume name/host path itself as a defense in depth, rather than relying solely on `UniqueName`.

### Proof of Concept
Go unit test in `common/build_test.go` demonstrating the collision (extends existing `TestProjectRealUniqueName`):
```go
func TestProjectRealUniqueName_CollisionAcrossProcesses(t *testing.T) {
    // Simulates two separate run-single processes on the same host,
    // sharing the same runner token and machine-derived SystemID,
    // processing two concurrent jobs of the same project.
    buildA := &Build{Runner: &RunnerConfig{}}
    buildA.Runner.RunnerCredentials.Token = "shared-token"
    buildA.Runner.SystemID = "s_samehostid" // machineid-derived, identical across processes
    buildA.Job.JobInfo.ProjectID = 42
    buildA.ProjectRunnerID = 0 // never set/deduped by run-single

    buildB := &Build{Runner: &RunnerConfig{}}
    buildB.Runner.RunnerCredentials.Token = "shared-token"
    buildB.Runner.SystemID = "s_samehostid"
    buildB.Job.JobInfo.ProjectID = 42
    buildB.ProjectRunnerID = 0

    assert.Equal(t, buildA.ProjectRealUniqueName(), buildB.ProjectRealUniqueName())
    assert.Equal(t, buildA.ProjectUniqueName(), buildB.ProjectUniqueName())
}
```
Follow-up integration-level PoC: build `volumes.ManagerConfig{UniqueName: <the colliding name>}` for two separate `manager` instances (mirroring two `run-single` processes) and assert that `createHostBasedCacheVolume("/cache")` produces the identical `hostPath` string for both, per the existing `TestDefaultManager_CreateUserVolumes_CacheVolume_HostBased` pattern [9](#0-8) .

func (b *Build) ProjectRealUniqueName() string {
	const byteLen = 16

	data := fmt.Sprintf("%s-%s-%d-%d",
		b.Runner.GetToken(),
		b.Runner.GetSystemID(),
		b.JobInfo.ProjectID,
		b.ProjectRunnerID,
	)

	sum := sha256.Sum256([]byte(data))
	return "runner-" + hex.EncodeToString(sum[:byteLen])
}

func (b *buildsHelper) addBuild(build *common.Build) {
	if build == nil {
		return
	}

	b.lock.Lock()
	defer b.lock.Unlock()

	runners := make(map[int]bool)
	projectRunners := make(map[int]bool)

	for _, otherBuild := range b.builds {
		if otherBuild.Runner.Token != build.Runner.Token {
			continue
		}
		runners[otherBuild.RunnerID] = true

		if otherBuild.JobInfo.ProjectID != build.JobInfo.ProjectID {
			continue
		}
		projectRunners[otherBuild.ProjectRunnerID] = true
	}

	for runners[build.RunnerID] {
		build.RunnerID++
	}

	for projectRunners[build.ProjectRunnerID] {
		build.ProjectRunnerID++
	}

func GenerateUniqueSystemID() (string, error) {
	const idLength = 12

	systemID, err := machineid.ID()
	if err == nil && systemID != "" {
		mac := hmac.New(sha256.New, []byte(systemID))
		mac.Write([]byte("gitlab-runner"))
		systemID = hex.EncodeToString(mac.Sum(nil))
		return "s_" + systemID[0:idLength], nil
	}

	// fallback to a random ID
	return generateRandomSystemID(idLength)
}

func (m *manager) createHostBasedCacheVolume(destination string) error {
	destination, err := m.absolutePath(destination)
	if err != nil {
		return fmt.Errorf("defining absolute path: %w", err)
	}

	err = m.managedVolumes.Add(destination)
	if err != nil {
		return fmt.Errorf("updating managed volumes list: %w", err)
	}

	// The leaf directory dir has a name with a length of:
	//	- 42 chars when protected
	//	- 32 chars when not protected (the length of the md5sum only)
	dir := m.withProtected(hashPath(destination))
	hostPath := m.parser.Path().Join(m.config.CacheDir, m.config.UniqueName, dir)

	m.appendVolumeBind(&parser.Volume{
		Source:      hostPath,
		Destination: destination,
	})

	return nil
}

func (m *manager) createCacheVolume(
	ctx context.Context,
	destination string,
	reusable bool,
) (string, error) {
	destination, err := m.absolutePath(destination)
	if err != nil {
		return "", fmt.Errorf("defining absolute path: %w", err)
	}

	err = m.managedVolumes.Add(destination)
	if err != nil {
		return "", fmt.Errorf("updating managed volumes list: %w", err)
	}

	hashedDestination := hashPath(destination)
	name := m.config.TemporaryName
	if reusable {
		name = m.config.UniqueName
	}

	// volumeName might get quite long. Docker is however happy to create volumes with long names. There is the "myth"
	// that volume names are treated like DNS labels, and thus only allow a length of 63 chars, however that does not hold
	// true. In fact, we already create way longer names, and would catch those issues in various integration tests.
	volumeName := m.withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))

	vBody := client.VolumeCreateOptions{
		Name:       volumeName,
		Driver:     m.config.Driver,
		DriverOpts: m.config.DriverOpts,
		Labels: m.labeler.Labels(map[string]string{
			"destination": destination,
			"protected":   strconv.FormatBool(m.config.Protected),
			"reusable":    strconv.FormatBool(reusable),
			"type":        "cache",
		}),
	}

	v, err := m.client.VolumeCreate(ctx, vBody)
	if err != nil {
		return "", fmt.Errorf("creating docker volume: %w", err)
	}

	if m.permissionSetter != nil {
		err = m.permissionSetter.Set(ctx, v.Name, m.labeler.Labels(map[string]string{"type": "cache-init"}))
		if err != nil {
			return "", fmt.Errorf("set volume permissions: %w", err)
		}
	}

	m.appendVolumeBind(&parser.Volume{
		Source:      v.Name,
		Destination: destination,
	})
	m.logger.Debugln(fmt.Sprintf("Using volume %q as cache %q...", v.Name, destination))

	return volumeName, nil
}
