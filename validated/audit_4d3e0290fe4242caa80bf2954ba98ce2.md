### Title
`get_confirmed_signatures_for_address2`'s `before`/`until` resolution decodes an entire block regardless of `limit`, making single-call cost proportional to slot transaction count - ([File: ledger/src/blockstore.rs])

### Summary
`Blockstore::get_confirmed_signatures_for_address2` resolves a `before` or `until` signature by calling `get_block_signatures_rev`, which calls `get_complete_block` to fully decode, sanitize, and materialize every transaction in that signature's slot before it can even locate the signature's position. This cost is paid once per `before`/`until` argument and is completely independent of the caller-supplied `limit`, so a single bounded `getSignaturesForAddress` call can force decode of an entire (potentially maximally-full) block.

### Finding Description
The RPC entrypoint is `JsonRpcRequestProcessor::get_signatures_for_address` [1](#0-0) , reached via the `get_signatures_for_address` RPC method after `verify_and_parse_signatures_for_address_params` validates and caps `limit` to `MAX_GET_CONFIRMED_SIGNATURES_FOR_ADDRESS2_LIMIT` (1000) [2](#0-1) . This limit only bounds the number of *returned* signatures — it does not bound the cost of resolving `before`/`until`.

Inside `Blockstore::get_confirmed_signatures_for_address2`, when `before` is `Some`, the slot containing that signature is looked up and then `get_block_signatures_rev(slot)` is called to build the ordered list of signatures in that slot purely so the position of `before` can be located and later entries excluded [3](#0-2) . The same happens independently for `until` [4](#0-3) .

`get_block_signatures_rev` does this by calling `self.get_complete_block(slot, false)` — a full block reconstruction (`do_get_complete_block_with_components`) that reads all shred components, flattens every entry's transactions, sanitizes each transaction, and returns full transaction/meta objects — then only takes the first signature of each transaction [5](#0-4) . `get_complete_block`/`do_get_complete_block_with_components` performs the full decode-and-sanitize path for every transaction in the slot [6](#0-5) .

Thus the cost of this step is O(transactions in that one slot), which can be up to whatever the attacker packed into it (thousands of transactions from a single slot), while the requested `limit` can be `1`. There is no check anywhere in this path that caps slot size, transaction count, or that skips the full decode when only a signature lookup is needed.

### Impact Explanation
A single, rate-compliant JSON-RPC call (`getSignaturesForAddress` with `limit=1` and `before`/`until` set to a signature from an attacker-filled slot) forces the validator to perform CPU/memory work proportional to the full transaction count of that slot rather than to the requested `limit`. This violates the invariant that a single bounded RPC call's cost should be bounded by explicit request parameters, not by the size of arbitrary on-chain data the attacker previously wrote. This matches the "unbounded cost for a single low-rate call" RPC DoS bounty category.

### Likelihood Explanation
Feasible and repeatable: an unprivileged user only needs to submit enough of their own transactions (with signature X) to be included in some slot S near its capacity — no leader/validator control required, just normal transaction submission. They then issue one `getSignaturesForAddress` call with `before=X` (or `until=X`) and `limit=1`. This can be repeated periodically (at most one call per `CLUSTER_SLOT_TIME_TARGET/2`) against different attacker-filled slots to sustain load, or via any `before`/`until` value from previously indexed heavy slots.

### Recommendation
Avoid decoding the full block just to locate a signature's position/order within a slot. Maintain or query a per-slot transaction-index-ordered signature index (the existing `address_signatures_cf` already stores `(address, slot, transaction_index, signature)`) instead of reconstructing the whole block via `get_complete_block`. Alternatively, cache the result of `get_block_signatures_rev` per slot, or add a lightweight code path that extracts just signatures without sanitizing/materializing full transaction metadata, and consider capping/streaming this operation so cost cannot exceed a bound independent of on-chain slot size.

### Proof of Concept
Rust unit test to add to `ledger/src/blockstore/tests.rs`, measuring `get_confirmed_signatures_for_address2` latency with `limit=1` and `before` set to a signature in slots of varying transaction counts:

```rust
#[test]
fn test_get_confirmed_signatures_for_address2_before_cost_scales_with_slot_size() {
    use std::time::Instant;

    let ledger_path = get_tmp_ledger_path_auto_delete!();
    let blockstore = Blockstore::open(ledger_path.path()).unwrap();
    let address = solana_pubkey::Pubkey::new_unique();

    // Helper: insert a rooted slot containing `n` transactions that reference `address`,
    // returning the last transaction's signature.
    fn fill_slot_with_txs(blockstore: &Blockstore, slot: Slot, n: usize, address: Pubkey) -> Signature {
        // ... build entries with `n` transactions each including `address` as an account key,
        // insert shreds for `slot`, set_roots([slot]) ...
        // return signature of the last transaction inserted
        unimplemented!()
    }

    let small_sig = fill_slot_with_txs(&blockstore, 1, 10, address);
    let large_sig = fill_slot_with_txs(&blockstore, 2, 5_000, address);

    let t0 = Instant::now();
    blockstore
        .get_confirmed_signatures_for_address2(address, 2, Some(small_sig), None, 1)
        .unwrap();
    let small_elapsed = t0.elapsed();

    let t1 = Instant::now();
    blockstore
        .get_confirmed_signatures_for_address2(address, 2, Some(large_sig), None, 1)
        .unwrap();
    let large_elapsed = t1.elapsed();

    // Assert: despite limit=1 in both calls, cost grows with slot transaction count,
    // demonstrating the request cost is not bounded by `limit`.
    assert!(
        large_elapsed.as_micros() > small_elapsed.as_micros() * 50,
        "expected cost to scale with slot size: small={:?}, large={:?}",
        small_elapsed,
        large_elapsed
    );
}
```

Expected result: latency for the `limit=1` call scales linearly with the transaction count of the slot containing `before`, confirming that `get_block_signatures_rev`'s `get_complete_block` call, not the caller's `limit`, dominates per-request cost.

```rust
    fn get_block_signatures_rev(&self, slot: Slot) -> Result<Vec<Signature>> {
        let block = self.get_complete_block(slot, false).map_err(|err| {
            BlockstoreError::Io(IoError::other(format!("Unable to get block: {err}")))
        })?;

        Ok(block
            .transactions
            .into_iter()
            .rev()
            .filter_map(|transaction_with_meta| {
                transaction_with_meta
                    .transaction
                    .signatures
                    .into_iter()
                    .next()
            })
            .collect())
    }
```
