### Title
Cross-account lamport pointer aliasing via `SolAccountInfo` in CPI when `syscall_parameter_address_restrictions` is inactive - ([File: program-runtime/src/cpi.rs])

### Summary
`CallerAccount::from_sol_account_info` only validates that `lamports_addr`/`owner_addr`/`data_addr`/`key_addr` match the expected serialized offsets (`account_metadata.vm_*_addr`) via `check_account_info_pointer` when `syscall_parameter_address_restrictions` is true [1](#0-0) . When that feature is inactive, the raw `account_info.lamports_addr` (and other fields) are dereferenced directly with `translate_type_mut_for_cpi` with no cross-check against the account they are supposed to represent [2](#0-1) , so a crafted C-ABI `SolAccountInfo` can point its `lamports_addr` into a different, unrelated account's serialized region of the shared VM input buffer.

### Finding Description
Account identity for CPI matching is derived solely by comparing pubkey bytes: `account_info_keys` are read via `translate_type::<Pubkey>(memory_mapping, key_addr(account_info), ...)` in `translate_account_infos` [3](#0-2) , and then matched against the real `account_key` (from the sanitized transaction accounts) in `translate_accounts_common` [4](#0-3) . Neither `key_addr` nor `lamports_addr`/`owner_addr`/`data_addr` are checked to fall within the specific account's own serialized region unless `syscall_parameter_address_restrictions` is true (gated blocks at lines 291-304 and 427-455). When the gate is off, an attacker can supply a `SolAccountInfo` whose `key_addr` points at memory containing account A's real pubkey (trivial to construct in the attacker's own writable buffer) but whose `lamports_addr` points at a completely different account B's serialized lamports slot elsewhere in the shared VM input region (B only needs to be present anywhere in the top-level transaction's account list; it need not appear in the CPI instruction's account metas).

Once matched to callee index `index_in_caller` for account A, `update_callee_account` (before executing the callee) and `update_caller_account` (after, gated on `instruction_account.is_writable()`) directly read/write through the raw `caller_account.lamports` pointer [5](#0-4) [6](#0-5) . Because that pointer physically resides inside account B's serialized bytes, the callee's write to "account A" ends up mutating B's serialized lamports field in the shared VM input buffer, which is later deserialized back into B's real `AccountSharedData` at top-level instruction exit — producing an unauthorized lamport mutation on B, an account the callee never declared or was authorized to touch.

The existing `check_account_info_pointer` mechanism (added specifically to prevent this class of pointer aliasing) is the only defense, and it is entirely feature-gated: `if syscall_parameter_address_restrictions { ... }` wraps all four pointer checks in `from_sol_account_info` (lines 427-455) as well as the analogous checks in `from_account_info` (lines 291-304, 315-326, 349-355).

### Impact Explanation
This is unauthorized lamport mutation of a third-party account (host-memory/account-state corruption via CPI pointer aliasing) — matching Solana's "Loss of Funds" bounty category — reachable purely by an unprivileged attacker who deploys their own C-ABI SBF program and crafts the account_infos buffer passed to `sol_invoke_signed`.

### Likelihood Explanation
The precondition is that `syscall_parameter_address_restrictions` is inactive in the active feature set. The code's own `FeatureSnapshot` documentation states it "should contain only features that have not been activated on all clusters" and explicitly still lists `syscall_parameter_address_restrictions` in that struct [7](#0-6) , meaning this gate is still treated by the codebase as not universally/permanently active across all clusters. I could not confirm from the repository alone whether this feature is currently activated on Mainnet-Beta specifically (feature activation is on-chain runtime state, not encoded statically in the source); if it is permanently active on every live cluster today, this path is unreachable in practice and only exercisable on a non-default/legacy feature-set (which the rules exclude). The test suite in `programs/sbf/tests/programs.rs` explicitly toggles this feature off/on and documents the "Invalid pointer" rejection only occurs when the restriction is enabled [8](#0-7) , confirming the vulnerable behavior exists in the "off" state by design of the legacy code path, not as an oversight bug.

### Recommendation
Given the confirmed uncertainty of live activation status, the underlying fix should be to remove the feature gate entirely and make `check_account_info_pointer` checks unconditional in `CallerAccount::from_sol_account_info` and `from_account_info`, eliminating any code path where CPI account pointer aliasing across accounts is possible regardless of feature-set state.

### Proof of Concept
Reachability could not be conclusively demonstrated end-to-end without confirming current on-chain feature activation status of `syscall_parameter_address_restrictions` across live clusters, which is outside what static repo analysis can determine. A concrete Rust unit test analogous to `test_account_info_in_account`/`test_account_info_rc_in_account` in `programs/sbf/tests/programs.rs` (lines 4933-5000, 5002-5093) — but crafting a `SolAccountInfo.lamports_addr` pointing into a *different, non-CPI-listed* account's serialized region rather than the tested overlap cases — would be needed to empirically confirm the cross-account lamport corruption, and should be run with `syscall_parameter_address_restrictions` deactivated to validate against the invariant "no syscall exposes host memory, aliases an unwritable account."
