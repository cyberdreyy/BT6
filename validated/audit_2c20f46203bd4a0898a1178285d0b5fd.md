### Title
Signer weight double-counted across Accepted and Rejected tallies when the same signer flips its verdict for the same block hash - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The external report's core defect is "no checks on a returned value that feeds a critical decision" — an unbounded, unreconciled input is trusted as-is. The direct analog in this repo is the miner-side StackerDB listener that tallies signer weight toward the 70% pre-commit/signature threshold: when a signer's `BlockResponse::Rejected` is later followed by a `BlockResponse::Accepted` for the *same* `signer_signature_hash`, the code that increments `total_weight_approved` never checks or reconciles against the fact that this same signer's weight was already counted into `total_weight_rejected`. Nothing subtracts the earlier tally or blocks the later one.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, `StackerDBListener`'s event loop processes both `BlockResponse::Accepted` and `BlockResponse::Rejected` messages for the block currently being gathered (keyed by `block_sighash` in `self.blocks`):

- Rejected path (line ~515): weight is added to `block.total_weight_rejected` gated by `block.responded_signers.insert(slot_id)` — i.e., only once per `slot_id`. [1](#0-0) 

- Accepted path (line ~443): weight is added to `block.total_weight_approved` gated only by `block.gathered_signatures.contains_key(&slot_id)`, a *separate* set from `responded_signers`. [2](#0-1) 

Because these are two independent maps/sets (`gathered_signatures` for accepts, `responded_signers` shared but only checked on the reject branch), a signer that first sends `Rejected` (incrementing `total_weight_rejected` and marking itself in `responded_signers`) and later sends `Accepted` for the identical `block_sighash` will pass the Accepted-branch gate (since `gathered_signatures` does not yet contain its `slot_id`) and get its weight added to `total_weight_approved` as well — with no subtraction from `total_weight_rejected`. The signer's weight is now counted in *both* tallies simultaneously.

This equality break matters because `signer_coordinator.rs` uses these two sums directly to decide the block's fate: [3](#0-2) 
`total_weight_rejected + weight_threshold > total_weight` triggers global rejection; `total_weight_approved >= weight_threshold` triggers "block accepted." Since a signer's weight can appear in both sums, `total_weight_rejected + total_weight_approved` can legitimately exceed `total_weight`, corrupting the assumption that these are disjoint partitions of the signer set's weight. This is exactly the class of bug the prompt calls out as Critical: "a rejection recounted as an accept" (aggregated-weight vs verified-accepts equality break).

A flip from Reject to Accept for the *same* block hash is not a hypothetical: the signer intentionally re-evaluates and can change its verdict for the identical `signer_signature_hash` under `should_reevaluate_block` / re-proposal flows, as demonstrated by the existing test `signer_reevaluates_proposal_with_missing_burn_view` in `stacks-node/src/tests/signer/v0/missing_burn_block_proposal.rs`, which shows a signer re-processing (not short-circuiting) an identical re-proposed block and re-emitting a fresh verdict for the same hash. [4](#0-3) 

The miner (a one-slot actor) fully controls when and how it re-proposes the identical block (same header/content ⇒ same `signer_signature_hash`), and can induce a transient rejection (e.g., a state briefly unavailable to a signer, such as `NotFoundError`/`ConnectivityIssues`) followed by a later successful re-validation and acceptance from that same signer, purely through normal gossip relay of `BlockResponse` messages — no other signer's key, no majority collusion, and no node compromise is required.

### Impact Explanation
If a single signer's weight becomes double counted (present in both `total_weight_rejected` and `total_weight_approved`), the miner's aggregate threshold logic can be pushed into an inconsistent state where the sums exceed the true total weight. In the boundary case, this can make the 70% approval threshold reachable with less than 70% of *distinct* signer weight actually agreeing to sign, or conversely trigger a false global rejection while an accept-threshold is also nominally met — undermining the safety guarantee that block approval requires supermajority-weight agreement from *distinct* signers. This matches the report's "no bounds/no reconciliation on a trusted external value" bug class, mapped onto weight aggregation rather than a price oracle.

### Likelihood Explanation
Requires only: (1) a miner controlling proposal/re-proposal timing (fully miner-controlled), and (2) at least one signer whose decision transiently flips from reject to accept for the identical block hash due to state re-evaluation — a documented, intentional signer behavior (re-evaluation on re-proposal), not an edge case requiring signer collusion or key compromise. The listener code path performing the tally has no cross-check between `gathered_signatures` and `responded_signers` to prevent this.

### Recommendation
Use a single, unified per-`slot_id` decision-state (e.g., an enum stored in one map: `NotResponded | Rejected | Accepted`) as the sole gate for both weight tallies. On receiving a new verdict for a slot_id that already has a prior verdict of the opposite kind, either (a) subtract the previous tally's weight before adding the new one, or (b) refuse to change the tally for that slot once set (treat the first verdict as final for that specific block hash), consistent with the "first decision wins" invariant already used elsewhere (e.g., `valid.is_some()` guards in `stacks-signer/src/v0/signer.rs`). Add a regression test that sends `Rejected` then `Accepted` from the same signer for the same `signer_signature_hash` and asserts `total_weight_approved + total_weight_rejected <= total_weight`.

### Proof of Concept
1. Miner proposes block B; signer S evaluates it and, due to a transient error (e.g. not-yet-visible burn view / `NotFoundError`), sends `BlockResponse::Rejected` for `signer_signature_hash(B)`. The listener records `total_weight_rejected += weight(S)` and `responded_signers.insert(slot_id(S))`.
2. Miner re-proposes the identical block B (same header ⇒ same `signer_signature_hash`). Signer S re-evaluates (per `should_reevaluate_block`/reprocessing semantics shown in `signer_reevaluates_proposal_with_missing_burn_view`) and this time validation succeeds; S sends `BlockResponse::Accepted` for the same `signer_signature_hash(B)`.
3. In `stackerdb_listener.rs`, the Accepted branch checks only `block.gathered_signatures.contains_key(&slot_id(S))`, which is false (S never previously accepted), so it adds `weight(S)` to `total_weight_approved` — with `total_weight_rejected` never decremented.
4. Now `total_weight_approved + total_weight_rejected > total_weight` for this block, i.e., S's weight is counted twice, corrupting the miner's threshold decision in `signer_coordinator.rs`.
