### Title
Job cleanup only signals the driver's process group, letting a `setsid`-detached grandchild survive job cancellation - ([File: helpers/process/killer_unix.go], [File: executors/custom/command/command.go])

### Summary
When a custom-executor job is cancelled or times out, `Run` calls `KillAndWait`, which sends `SIGTERM`/`SIGKILL` to the negative PID of the driver's `run_exec` process, i.e. its process group. A grandchild process that calls `setsid()` (or otherwise leaves the group) is no longer a member of that process group and is unaffected by these signals, so it survives job teardown while its parent job is reported as terminated.

### Finding Description
`Run` starts the driver command and races `c.waitCh` against `c.context.Done()`; on cancellation it delegates to `newProcessKillWaiter(...).KillAndWait(c.cmd, c.waitCh)`: [1](#0-0) 

`KillAndWait` calls `processKiller.Terminate()` then, after `gracefulKillTimeout`, `ForceKill()`: [2](#0-1) 

Both `Terminate` and `ForceKill` send the signal to `pk.getPID()`, which is the *negative* PID of the direct child process — i.e., a process-group-wide signal (`kill(2)` semantics: negative pid targets the whole group): [3](#0-2) 

The process group is established once, at `Start()`, via `Setpgid: true` on the direct child only: [4](#0-3) 

If the job's build script spawns a process that calls `setsid()` (e.g., `setsid sleep 999999 &`), that process creates a brand-new session and process group, detaching from the driver's group. The group-directed `SIGTERM`/`SIGKILL` sent by `KillAndWait` never reaches it, since `kill(-pgid, sig)` only targets members of that specific group, not children that have since called `setsid()`. This is not a race per se — it is a deterministic, always-reproducible gap in the cleanup mechanism whenever the job forks a detached process before (or even after) cancellation, because there is no equivalent supervision (e.g., cgroup-based kill, PID namespace, or explicit tracking of all descendant PIDs) to catch such detached descendants.

Existing checks: none of the custom-executor kill logic performs cgroup freezing/killing, PID-namespace confinement, or `/proc`-based descendant enumeration; it relies solely on POSIX process-group signaling, which is exactly the mechanism that `setsid()` is designed to escape.

### Impact Explanation
On a shared/multi-tenant runner host using a custom or shell executor without additional OS-level sandboxing (containers, cgroups, PID namespaces), an unprivileged job author can leave a detached background process running indefinitely after the job is cancelled/times out. That orphan can continue consuming CPU/memory/network/disk on the runner host, potentially interfering with subsequent jobs scheduled on the same host (resource exhaustion, port squatting, background scanning/mining, or lingering access to files still present in the workspace before it is reused).

### Likelihood Explanation
Highly feasible and fully attacker-controlled: any job author can put `setsid <command> &` (or equivalent double-fork/daemonize technique available in any shell/language) into their build script. It requires no elevated privileges, no host misconfiguration, and no race-window luck — it works reliably every time the job is cancelled or times out, as long as the underlying executor doesn't already sandbox at the container/cgroup/PID-namespace level (this specific code path is generic and used by the custom executor, which by design does not mandate such isolation).

### Recommendation
Do not rely solely on process-group signaling for cleanup. Track and kill the full descendant tree (e.g., walk `/proc/<pid>/task/*/children` recursively, or better, launch the driver process inside a dedicated cgroup and kill the entire cgroup on cancellation, or use a PID namespace so all descendants die when the namespace's init process is killed). At minimum, document this limitation prominently for the custom/shell executors and provide an opt-in cgroup-based job supervisor.

### Proof of Concept
Go integration test (extending `executors/custom/command/command_test.go` or a new integration test under `helpers/process`):
1. Build a `run_exec` script that runs `setsid sh -c 'sleep 999999' & echo $!` and writes the child's PID to a known file, then sleeps to simulate the job "hanging".
2. Start the job via `command.Run()` with a `context.Context` and cancel it shortly after start (simulating job cancellation/timeout).
3. Assert `Run()` returns (driver process/group is killed).
4. Read the PID written by the script and assert, via `syscall.Kill(pid, 0)`, that the process **still exists** after `Run()` returns — proving the `setsid`-detached grandchild was not reaped by `KillAndWait`.
5. Expected (buggy) result: the assertion in step 4 fails to show the process is dead — i.e., the orphan is still running, confirming the vulnerability.

```go
func (kw *osKillWait) KillAndWait(command Commander, waitCh chan error) error {
	process := command.Process()
	if process == nil {
		return ErrProcessNotStarted
	}

	log := kw.logger.WithFields(logrus.Fields{
		"PID": process.Pid,
	})

	processKiller := newProcessKiller(log, command)
	processKiller.Terminate()

	select {
	case err := <-waitCh:
		return err
	case <-time.After(kw.gracefulKillTimeout):
		processKiller.ForceKill()

		select {
		case err := <-waitCh:
			return err
		case <-time.After(kw.forceKillTimeout):
			return &KillProcessError{pid: process.Pid}
		}
	}
```

```go
func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}
```
