## Finding

<title>
Stale rejection weight never cleared when a signer later accepts — inflates `total_weight_rejected` in the miner's quorum tally (`File: stacks-node/src/nakamoto_node/stackerdb_listener.rs`)
</title>

### Summary
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the miner-side `StackerDBListener` tracks a `BlockStatus` per proposed block with two independent weight tallies, `total_weight_approved` and `total_weight_rejected`, gated by a single shared `responded_signers` set [1](#0-0) . The `Rejected` branch correctly gates on `responded_signers.insert(slot_id)` before adding weight, but the `Accepted` branch never checks `responded_signers` at all — it only checks `gathered_signatures.contains_key(&slot_id)` [2](#0-1) . Consequently, a signer who first rejects a block (their weight is added to `total_weight_rejected` and their slot is marked "responded") and later sends a genuine, cryptographically-valid `Accepted` message for the same block will have their weight *added* to `total_weight_approved`, while their earlier `total_weight_rejected` contribution is never removed. The signer's weight ends up permanently counted in both the "rejected" and "approved" quorum tallies for that block.

### Finding Description
`BlockStatus::responded_signers` appears to be the intended single-vote-per-signer gate, but it is only enforced asymmetrically:

- `Rejected` path: `if block.responded_signers.insert(slot_id) { block.total_weight_rejected += weight; ... }` [3](#0-2) 
- `Accepted` path: weight is added purely based on `gathered_signatures.contains_key(&slot_id)`, with no check of `responded_signers` and no reconciliation/decrement of any prior rejection weight [4](#0-3) 

This means: Reject → Accept is allowed and double-counts the signer's weight into *both* tallies (accept succeeds, but the earlier reject weight is never cleared). Accept → Reject is blocked (the reject branch's `responded_signers.insert` returns `false` since Accept already inserted the slot), so a signer cannot un-approve, but they *can* un-reject while leaving stale rejection weight behind. The two tallies (`total_weight_approved`, `total_weight_rejected`) are meant to reflect the current, mutually-exclusive, verified opinion of each signer, but the code allows this invariant to be violated by a single signer sending two sequential, honestly-signed messages (reject then accept) — this does not require a majority or a compromised key, any single signer/gossip relay can trigger it, exactly as the external report describes an actor's "revoked/stale" vote continuing to be tallied.

### Impact Explanation
`total_weight_rejected` is used by the miner (`SignerCoordinator::get_block_status`) to decide whether to abandon a block proposal: once `total_weight_rejected + weight_threshold > total_weight` the miner treats the block as `SignersRejected` and gives up on it [5](#0-4) . Because a signer's stale rejection weight from an earlier (retracted) rejection is never removed, that weight remains permanently "on the books" for the block, artificially inflating the effective rejection tally even after the signer has legitimately switched to acceptance. This lets fewer distinct currently-rejecting signers combine with the stale, retracted weight to cross the 30% blocking-minority threshold, causing the miner to wrongly abandon/deprioritize a block that in fact has (or could reach) sufficient current approval — a liveness wedge on block finalization that does not require compromising any signer's key or a majority of signers, only ordinary vote flip-flopping by one signer (which is a legitimate, expected occurrence as a signer's local view catches up).

### Likelihood Explanation
This requires no majority collusion and no key compromise — any single signer (even an honest one reacting to a changing view, e.g. rejecting a proposal then subsequently validating and accepting it once its own chain state catches up) can trigger the stale double count purely through the normal reject→accept lifecycle already supported and expected by the signer protocol (per `docs/signer-flows.md` section 6, flip-flopping between rejection and later acceptance is an anticipated flow) [6](#0-5) .

### Recommendation
In the `Accepted` branch of `stackerdb_listener.rs`, when adding a new acceptance for a `slot_id`, also check whether that slot previously contributed to `total_weight_rejected` and subtract that signer's weight from `total_weight_rejected` if so (or use a single per-signer "current vote" state instead of two independently-incrementing counters), so `total_weight_approved` and `total_weight_rejected` always reflect only the signer's *latest* verified response.

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListener` tracks `BlockStatus` with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `B`. Handler at `stackerdb_listener.rs:486-591` sets `responded_signers.insert(S.slot_id)` and `total_weight_rejected += w`.
3. Signer `S` later sends a valid `BlockResponse::Accepted` for the same `B` (e.g. after re-validating). Handler at `stackerdb_listener.rs:386-485` verifies the signature, finds `!gathered_signatures.contains_key(S.slot_id)` true, and does `total_weight_approved += w`; it never inspects or decrements `total_weight_rejected`.
4. Final state: `total_weight_rejected` still includes `w` from step 2 even though `S` has since accepted; this stale weight persists indefinitely and combines with other genuinely-rejecting signers' weight when the miner in `signer_coordinator.rs:509-540` evaluates `total_weight_rejected + weight_threshold > total_weight` to decide whether to abandon the block.
