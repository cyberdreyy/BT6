### Title
ERC4626 liquidity withdrawal griefing can repeatedly revert epoch settlement and freeze pending withdrawals - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary

In programmable-borrower mode, `stopEpoch` depends atomically on `ProgrammableBorrower.onStopEpoch()` withdrawing enough liquidity from the configured ERC4626 vault. An unprivileged liquidity participant can temporarily remove vault liquidity immediately before the manager calls `stopEpoch`, making `vault.withdraw()` revert, then restore the liquidity afterward. The failed call leaves the epoch running and all pending withdrawal receipts unclaimable until settlement is retried successfully.

### Finding Description

`IdleCDOEpochVariant._stopEpoch()` calls `IProgrammableBorrower(_borrower()).onStopEpoch()` before pulling borrower funds. A `false` return triggers default handling, but a revert propagates out of `stopEpoch`, reverting the entire settlement transaction without changing epoch state. [1](#0-0) 

`ProgrammableBorrower.onStopEpoch()` compares the required cash amount with the contract's on-hand balance and calls `vault.withdraw(shortfall)` for the remainder. Any ERC4626 withdrawal failure is converted to `StopEpochVaultLiquidityUnavailable`, so transient liquidity removal makes the whole epoch-settlement call fail even though the vault shares still economically cover the withdrawal. [2](#0-1) 

This is reachable in the normal programmable-borrower path because `onStartEpoch()` deposits all on-hand underlying into the external vault instead of retaining the pending withdrawal reserve locally. [3](#0-2) 

A normal withdrawal request cannot be claimed while `epochNumber <= lastWithdrawRequest[_user]`; the failed settlement leaves `epochNumber` unchanged, so the receipt remains frozen. [4](#0-3) 

### Impact Explanation

The attacker can temporarily freeze up to `_amountRequired`, which includes `pendingWithdraws` and any cash interest/pull amount, for the duration of the liquidity shortage. Because the revert occurs before `epochNumber` increments, pending withdrawal receipts cannot be paid through `claimWithdrawRequest`, and the manager must retry `stopEpoch` after liquidity returns. [5](#0-4) 

The attack can be repeated around each retry as long as the attacker can keep the ERC4626 vault's immediately withdrawable liquidity below the required amount. In close-pool mode the frozen amount can be the full recalled principal because `stopEpoch(0, 1)` requests all borrower funds. [6](#0-5) 

### Likelihood Explanation

The attack requires no IdleCDO, strategy, borrower, manager, or ERC20 role. An ERC4626 liquidity provider or a borrower in the markets backing that vault can temporarily remove enough liquidity before the privileged `stopEpoch` transaction and restore it afterward. The affected amount must be less than or equal to the ProgrammableBorrower's vault position; otherwise the existing covered-shortfall branch returns `true` and lets the normal transfer/default path handle it. [7](#0-6) 

The issue is limited to deployments using `isProgrammableBorrower`; normal borrower deployments do not use the external ERC4626 recall hook. The existing regression test also demonstrates that a covered but temporarily unavailable vault withdrawal causes `stopEpoch` to revert while leaving the epoch and pending withdrawals unchanged. [8](#0-7) 

### Recommendation

Do not make epoch settlement depend on a same-transaction ERC4626 withdrawal. Add a separate `prepareStopEpoch` or `prefundWithdrawals` step on `ProgrammableBorrower` that withdraws `epochPendingWithdraws` and the required interest amount to local underlying before `stopEpoch`. Once held locally, `availableToBorrow()` already excludes `epochPendingWithdraws`, so the real borrower cannot draw the reserved balance. [9](#0-8) 

Alternatively, reserve pending withdrawal liquidity outside the ERC4626 vault at `onStartEpoch()` rather than redepositing all available underlying. That removes the attacker-controlled external liquidity dependency from the settlement path.

### Proof of Concept

On a mainnet fork using the existing programmable-borrower setup:

```solidity
// Setup: programmable borrower + real ERC4626 vault, minted-interest/APR0 mode.
_setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);

vm.prank(owner);
cdoEpoch.setIsInterestMinted(true);

// Victim creates a normal pending withdrawal before the epoch starts.
idleCDO.depositAA(10_000 * oneScale);
uint256 victimReceipt =
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));

_startEpochAndCheckPrices(0);
uint256 pending = strategy.pendingWithdraws();
assertEq(pending, victimReceipt);

// Attacker is only a user/liquidity actor in the ERC4626 ecosystem.
// Immediately before manager.stopEpoch, reduce withdrawable vault liquidity
// below `pending`, while the programmable borrower's shares still cover it.
// With a MetaMorpho-style vault this can be done by redeeming a sufficiently
// large pre-existing LP position or borrowing liquidity from its backing markets.
vm.prank(externalVaultLiquidityActor);
removeVaultLiquidity(pending); // vault.withdraw/redeem or market borrow wrapper

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);

// Settlement never occurred, so the victim's receipt is still frozen.
assertTrue(cdoEpoch.isEpochRunning());
assertEq(strategy.epochNumber(), 1);
assertEq(strategy.pendingWithdraws(), pending);
assertEq(
    strategy.lastWithdrawRequest(address(this)),
    strategy.epochNumber()
);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimWithdrawRequest();

// The attacker restores liquidity; the manager can now settle.
vm.prank(externalVaultLiquidityActor);
restoreVaultLiquidity(pending);

vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);
cdoEpoch.claimWithdrawRequest();
```

The concrete attacker transactions are therefore `removeVaultLiquidity -> manager.stopEpoch reverts -> restoreVaultLiquidity`. This is the direct analog of the report's `swapWithEth -> withdrawNftWithInterest reverts -> repayWithNft` sandwich.

    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
    emit EpochAccountingStarted(startAssets);
