### Title
Artifact/cache extraction restores `.git` control paths despite git-path warning - ([File: helpers/archives/zip_extract.go], [File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
The archive extractors used by `downloadArtifacts` in `shells/abstract.go` extract into the job's working directory, and the only defense against restoring `.git`-prefixed paths is a warning log, not a blocking check. Both the zip extractor and the tar/zstd extractor allow an attacker-controlled earlier-job artifact/cache to overwrite `.git/config`, `.git/hooks/*`, or `.git/modules/*` files that are later trusted by `git`-driven checkout logic.

### Finding Description
`downloadArtifacts` in `shells/abstract.go` triggers extraction of a downloaded artifact archive into the project working directory. For zip archives, extraction goes through `helpers/archives/zip_extract.go`'s `ExtractZipArchive`, which calls `errorIfGitDirectory` per entry: [1](#0-0) 
The returned error is only used to log a warning (`tracker.actionable(err)` → `printGitArchiveWarning`) — it is never used to skip or reject the entry. `extractZipFile(file)` is called unconditionally right after, so the `.git/...` path is written regardless: [2](#0-1) 
This is confirmed by the existing test `TestExtractZipFileWithGitPath`, which asserts both that the warning is logged *and* that `.git/test_file` is created on disk: [3](#0-2) 

The `.git`-path check (`isPathAGitDirectory`/`errorIfGitDirectory`) is defined once in `helpers/archives/path_check_helper.go` and is only wired into `zip_create.go` and `zip_extract.go`: [4](#0-3) 
The tar/zstd extractor used for cache/artifact archives has no such check at all — it computes the destination path, validates only that it stays inside the chroot dir, and then writes regular files/dirs/symlinks without any git-path filtering: [5](#0-4) 

Meanwhile, GitLab Runner's own git-checkout stage (`functions/concrete/run/stages/get_sources.go`) explicitly documents that it must clean "potentially-malicious git configs and hooks from prior jobs" before trusting `.git`, via `cleanupGitState`: [6](#0-5) 
This cleanup only runs when `CleanGitConfig` is enabled, and only removes lock files, `post-checkout` hooks, and (conditionally) `config`/`hooks` directories — it does not comprehensively neutralize every attacker-writable `.git` path (e.g., other hooks such as `pre-commit`, `pre-push`, custom `.git/info/attributes`, `.git/modules/*/config` if submodules aren't detected, etc.), and it is not guaranteed to run before an artifact/cache restore that happens mid-job (`downloadArtifacts` is invoked between job stages, not exclusively before checkout).

Exploit flow:
1. Attacker (pipeline author) controls Job A, which produces an artifact/cache containing a crafted zip or tar.zst archive with entries under `.git/hooks/<hook>` or `.git/config`.
2. Job B (same project, later stage, `needs`/`dependencies` on Job A) downloads that artifact via Runner's normal artifact-download flow, which calls `downloadArtifacts` → extraction.
3. For zip, extraction proceeds with only a warning; for tar/zstd, there's no check whatsoever. The `.git` control files are written into Job B's working directory.
4. Subsequent git operations in Job B (e.g., `git checkout`, `git submodule update`, or any script invoking git) can execute attacker-controlled hooks or honor attacker-controlled config (e.g., `core.fsmonitor`, `core.sshCommand`, `credential.helper`), leading to command execution or credential exfiltration in the context of Job B's job token/permissions.

### Impact Explanation
An attacker who controls an earlier stage's artifact/cache content can plant executable git hooks or malicious git config that get restored into a later job's working tree, resulting in command execution and/or credential/job-token exfiltration in that job's context — i.e., protected-ref escalation or credential misuse via repo-control overwrite, matching the scoped Immunefi impact.

### Likelihood Explanation
Feasible and repeatable by any pipeline author with no special privileges: they only need to control the content of an artifact or cache produced by one job and consumed (`dependencies`/`needs`, or `cache:` reuse) by another job in the same pipeline/project — a completely standard CI pattern. No admin action or external compromise is required, and the `.git` warning is purely cosmetic for zip, and entirely absent for tar/zstd.

### Recommendation
- Make the `.git`-path check enforced (skip/reject the entry) rather than log-only in `helpers/archives/zip_extract.go`'s `ExtractZipArchive`.
- Add the same git-path validation to `commands/helpers/archive/tarzstd/tarzstd_extractor.go` (and any other tar-based extractor) before writing files/dirs/symlinks.
- Apply this check consistently to all restore paths reachable from `downloadArtifacts` (artifacts) and the cache-extraction path (`commands/helpers/cache_extractor.go`), not just the zip creation/extraction helpers.
- Consider always sanitizing `.git` control paths (hooks, config, `info/`) on both archive extraction and prior to any subsequent git operation, independent of the `CleanGitConfig` feature flag.

Analogous test should be added for `tarzstd.Extract` with a `.git/config` entry, asserting the file is not created in `e.dir` after extraction. An integration-level PoC job: Job A `mkdir -p .git/hooks && printf '#!/bin/sh\nid > /tmp/pwned' > .git/hooks/post-checkout && chmod +x .git/hooks/post-checkout` then declares it as an artifact; Job B declares `dependencies: [Job A]`, runs `git checkout` (normal Runner checkout flow) and asserts `/tmp/pwned` was created, proving hook execution from a restored artifact.

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}

// cleanupGitState removes stale lock files and (when CleanGitConfig is set)
// potentially-malicious git configs and hooks from prior jobs.
func (s GetSources) cleanupGitState(e *env.Env) {
	dotGitDir := filepath.Join(e.WorkingDir, ".git")

	// Remove lock files and stale post-checkout hook.
	lockFiles := []string{"index.lock", "shallow.lock", "HEAD.lock", "config.lock"}
	for _, f := range lockFiles {
		_ = os.Remove(filepath.Join(dotGitDir, f))
	}
	_ = os.Remove(filepath.Join(dotGitDir, "hooks", "post-checkout"))

	if s.hasSubmodules() {
		modulesDir := filepath.Join(dotGitDir, "modules")
		for _, f := range lockFiles {
			walkRemove(modulesDir, f, false)
		}
		// The old shell code also removed post-checkout recursively in modules.
		walkRemove(modulesDir, "post-checkout", false)
	}

	walkRemove(filepath.Join(dotGitDir, "refs"), ".lock", true)

	if !s.CleanGitConfig {
		return
