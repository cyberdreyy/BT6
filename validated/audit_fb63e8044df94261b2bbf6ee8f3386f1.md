### Title
Missing Zero-Address Validation for EVM `recipientAddress` in Bridge Token Transfer — (`bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/utils/BridgeUtils.sol`, `crates/sui-framework/packages/bridge/sources/bridge.move`)

---

### Summary

Both the Sui Move bridge package and the EVM bridge contracts fail to reject a zero EVM recipient address (`address(0)` / `0x0000000000000000000000000000000000000000`). An ordinary bridge user can initiate a Sui→EVM token transfer specifying the zero address as the EVM recipient. The committee will sign the resulting message (it is a structurally valid bridge event), and when the signed message is submitted on EVM, bridged ETH is permanently transferred to `address(0)` with no recovery path.

---

### Finding Description

**Sui Move side — `send_token` / `send_token_v2`**

`bridge.move` validates only that the EVM target address is exactly 20 bytes long:

```move
assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
assert!(token_amount > 0, ETokenValueIsZero);
```

There is no check that the 20 bytes are not all zeros. A user may pass `x"0000000000000000000000000000000000000000"` and the call succeeds, emitting a `TokenDepositedEvent` that the committee will observe and sign.

The test suite confirms this: `test_execute_send_token_zero_value` (line 271–279 of `bridge_tests.move`) uses `eth_address = x"0000000000000000000000000000000000000000"` without any `EInvalidEvmAddress` failure — the only guard that fires is `ETokenValueIsZero` when the coin amount is zero, not when the address is zero.

**EVM side — `decodeTokenTransferPayload` / `_transferTokensFromVault`**

`BridgeUtils.decodeTokenTransferPayload` extracts the recipient address from the payload using inline assembly:

```solidity
assembly {
    recipientAddress := mload(add(_payload, add(recipientAddressLength, offset)))
}
```

If the 20 payload bytes are all zeros, `recipientAddress` is `address(0)`. No check is performed after this extraction.

`_transferTokensFromVault` in `SuiBridge.sol` guards only the *token* address:

```solidity
require(tokenAddress != address(0), "SuiBridge: Unsupported token");
// ...
if (tokenID == BridgeUtils.ETH) {
    vault.transferETH(payable(recipientAddress), amount);   // recipientAddress unchecked
} else {
    vault.transferERC20(tokenAddress, recipientAddress, amount);
}
```

The identical pattern exists in `SuiBridgeV2._transferTokensFromVault` and `BridgeUtilsV2.decodeTokenTransferPayloadV2`.

For the ETH token type, `vault.transferETH(payable(address(0)), amount)` sends native ETH to the zero address via a low-level `.call{value: amount}("")`. This call succeeds and the ETH is permanently unrecoverable.

---

### Impact Explanation

A bridge user who (accidentally or through a buggy client) specifies `address(0)` as the EVM recipient will permanently lose all bridged ETH. The tokens leave the vault, the nonce is marked processed (`isTransferProcessed[nonce] = true`), and no refund or retry path exists. This constitutes **unintended permanent burning of bridged funds** below the 10 B SUI cap.

---

### Likelihood Explanation

Low-to-medium. The trigger requires a user to supply 20 zero bytes as the EVM recipient address. This can happen through:
- A buggy or malicious front-end that defaults the recipient field to zero.
- A programmatic caller that forgets to populate the address field.
- A user who intentionally burns tokens.

The committee will sign any structurally valid bridge event; it does not filter zero-address recipients.

---

### Recommendation

**Sui Move (`bridge.move`)** — add a non-zero check after the length assertion in both `send_token` and `send_token_v2`:

```move
assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
// add:
assert!(target_address != x"0000000000000000000000000000000000000000", EInvalidEvmAddress);
assert!(token_amount > 0, ETokenValueIsZero);
```

**EVM (`BridgeUtils.sol`, `BridgeUtilsV2.sol`)** — add a zero-address check immediately after the assembly extraction in `decodeTokenTransferPayload` and `decodeTokenTransferPayloadV2`:

```solidity
assembly {
    recipientAddress := mload(add(_payload, add(recipientAddressLength, offset)))
}
require(recipientAddress != address(0), "BridgeUtils: Invalid recipient address");
```

Alternatively (or additionally), add the check in `_transferTokensFromVault` in both `SuiBridge.sol` and `SuiBridgeV2.sol`:

```solidity
require(recipientAddress != address(0), "SuiBridge: Invalid recipient address");
```

### Proof of Concept

1. **Initiate on Sui.** Call `bridge::bridge::send_token<ETH>` with `target_address = x"0000000000000000000000000000000000000000"` and any non-zero ETH coin amount. The call succeeds because only the length (20 bytes) is validated. [1](#0-0) 

2. **Committee signs.** The emitted `TokenDepositedEvent` is a structurally valid bridge event. The committee observes it and produces a quorum-signed `BridgeUtils.Message` with the zero address encoded in bytes 35–54 of the payload.

3. **Submit on EVM.** Anyone calls `SuiBridge.transferBridgedTokensWithSignatures` with the signed message. The `verifyMessageAndSignatures` modifier passes (valid committee signatures). [2](#0-1) 

4. **Decode payload.** `BridgeUtils.decodeTokenTransferPayload` extracts `recipientAddress = address(0)` via assembly. No revert occurs. [3](#0-2) 

5. **Transfer to zero address.** `_transferTokensFromVault` checks `tokenAddress != address(0)` (passes) then calls `vault.transferETH(payable(address(0)), amount)`. The low-level call succeeds; ETH is permanently sent to `address(0)`. [4](#0-3) 

6. **Nonce consumed.** `isTransferProcessed[message.nonce] = true` is set. The message can never be replayed; the ETH is permanently lost with no recovery path. [5](#0-4) 

The same path applies to `SuiBridgeV2.transferBridgedTokensWithSignaturesV2` / `BridgeUtilsV2.decodeTokenTransferPayloadV2` / `SuiBridgeV2._transferTokensFromVault`. [6](#0-5) [7](#0-6)

        bytes[] memory signatures,

        onlySupportedChain(message.chainID)
    {

        BridgeUtils.TokenTransferPayload memory tokenTransferPayload =

        // convert amount to ERC20 token decimals

        );
