### Title
Instant-withdraw requests spanning multiple epochs evade the default-recovery haircut and can drain or permanently freeze the recovery reserve — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
HTTP request smuggling is a desynchronization bug: a front-end and a back-end disagree about the boundaries/ownership of a request, so one request is interpreted in two different ways. The direct analog in `IdleCreditVault` is the instant-withdraw accounting: `pendingInstantWithdraws` is a single aggregate bucket across *all* epochs, while default finalization only attributes `instantWithdrawClaimsByEpoch[epochNumber]` (the *current* epoch) to the recovery basis and the prefunded reserve. Instant receipts created in an earlier epoch and still unfunded when a later epoch defaults are "smuggled" past the haircut: they are never included in `defaultPendingClaimBasis()` yet remain claimable at par via `_transferFundedClaim`, letting their holders steal recovery funds (or permanently freezing claims once the reserve is exhausted, depending on claim order).

### Finding Description
In `requestInstantWithdraw` each receipt is recorded per-epoch (`instantWithdrawsRequestsByEpoch[user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) but the funding shortfall is tracked only in the aggregate `pendingInstantWithdraws` (lines 366–374). When the borrower defaults, `defaultPendingClaimBasis()` adds only the *current* epoch's claims:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

(lines 644–649), and `_defaultPrefundedInstantReserve()` similarly compares the aggregate `pendingInstantWithdraws` against only `instantWithdrawClaimsByEpoch[epochNumber]` (lines 716–723). Two desyncs follow:

1. **Wrong claims enter the basis.** If `pendingInstantWithdraws` is non-zero because of *older* epoch receipts, `instantWithdrawClaimsByEpoch[epochNumber]` from the new epoch is still added to the default basis even though its receipts may be the funded ones — while older unfunded receipts are excluded from the haircut entirely.
2. **Old receipts pay at par (or revert).** After finalization, `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (lines 842–856). An older-epoch receipt falls through to `instantWithdrawsRequests[_user]` and is paid 1:1 through `_transferFundedClaim` (lines 387–392), which merely requires `balance - defaultRecoveryReserve >= amount`. Since the strategy's remaining balance *is* partly the prefunded/recovery cash, the older claimant receives an unhaircutted payout ahead of haircutted claimants — first-come-first-served theft — or, if the reserve plus reserve-guard consumes the balance first, the claim reverts and the receipt is permanently frozen.

`epochNumber` is incremented inside `deposit()` during `stopEpoch` (lines 607–610), so any instant request left unfunded across a `stopEpoch`/`startEpoch` boundary automatically lands in a different epoch bucket than the aggregate `pendingInstantWithdraws` shortfall — no privileged misbehavior required, only ordinary epoch transitions around borrower underfunding.

### Impact Explanation
Broken invariant: one receipt — one haircut — one payout; loss socialization must apply uniformly to all unfunded claims. Instead, receipt epoch and the aggregate unfunded bucket desynchronize, so:

- Older-epoch instant claimants withdraw at par from cash that was partially reserved/attributed to defaulted-epoch claimants, directly stealing recovery value (they take funds that `finalizeDefaultRecovery` priced as belonging pro-rata to the current-epoch basis).
- If haircutted claimants go first, older receipts revert in `_transferFundedClaim` and are permanently frozen — unclaimable yield with no recovery path.
- `instantWithdrawClaimsByEpoch[oldEpoch]` is also never decremented, leaving permanently inconsistent accounting.

Quantified example: two epochs, two unfunded instant receipts of 100 each, 150 collected. With desynced attribution the older claimant can pull 100 at par while the defaulted-epoch claimant only receives 50 (50/100 basis × par-claimant leakage), or the older claim is bricked entirely.

### Likelihood Explanation
Requires: (a) an instant-withdraw request that remains partially unfunded across a `stopEpoch` boundary — this occurs whenever the borrower under-funds `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`; and (b) a subsequent default finalized via `finalizeDefaultRecovery` while `pendingInstantWithdraws != 0`. Both are unprivileged market conditions (borrower underpayment is an external event, not attacker-controlled privilege), and any affected holder triggers the misattribution simply by calling `claimInstantWithdrawRequest`. No guard (`_onlyIdleCDO`, reserve check, `NotAllowed` gating) detects the cross-epoch mismatch.

### Recommendation
Make funding attribution per-epoch instead of aggregate: track a funded/unfunded remainder per epoch (e.g., `pendingInstantWithdrawsByEpoch`), or include *all* epochs with outstanding instant claims in `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` (e.g., sum `instantWithdrawClaimsByEpoch` over non-claimed epochs), so every unfunded receipt receives the same `defaultRecoveryPrice` haircut and funded receipts are unambiguously reserved.

### Proof of Concept
Foundry fork PoC outline (against `IdleCreditVault` + `IdleCDOEpochVariant` deployments on mainnet fork):

```solidity
// test/foundry/InstantWithdrawEpochDesync.t.sol
function testInstantWithdrawCrossEpochDesync() public {
    // Epoch N: alice (AA tranche holder) requests instant withdraw of 100e6.
    // Borrower funds nothing -> pendingInstantWithdraws = 100e6,
    // instantWithdrawClaimsByEpoch[N] = 100e6.
    vm.prank(address(cdo));
    vault.requestInstantWithdraw(100e6, alice);

    // stopEpoch -> epochNumber becomes N+1 (deposit() inside stopEpoch bumps it).
    // Epoch N+1: bob requests instant withdraw of 100e6.
    // Borrower funds 150e6 via collectInstantWithdrawFunds ->
    // pendingInstantWithdraws = 50e6, instantWithdrawClaimsByEpoch[N+1] = 100e6.
    // The 150e6 sits in the strategy unattributed to any epoch.

    // Borrower defaults; manager finalizes recovery with _recoveredAmount = 0.
    // _defaultPrefundedInstantReserve: instantBasis(100) > pending(50) -> prefunded = 50
    // defaultPendingClaimBasis = pendingWithdraws(0) + claims[N+1](100) = 100
    // -> recoveryPrice = 50/100 = 0.5e18, reserve = 50e6.
    // Alice's 100e6 (epoch N) is excluded from basis and from the haircut.

    // Theft ordering: alice claims first -> _claimDefaultedInstantWithdrawRequest
    // finds basis[N+1]=0 for alice, falls through to funded path and pays
    // 100e6 AT PAR from the 150e6 balance (reserve guard allows: 150-50>=100).
    vm.prank(address(cdo));
    vault.claimInstantWithdrawRequest(alice); // alice gets 100e6, no haircut
    // Bob then claims only 50e6 (0.5 * 100) from reserve.
    // Uniform haircut would have given each ~75e6. Alice stole ~25e6.

    // Freeze ordering (reset): bob claims first -> reserve drains to 0,
    // balance = 100e6, reserve-guard needs balance-reserve>=100 -> ok once,
    // but with three claimants / partial prefund the last claimant's
    // _transferFundedClaim reverts NotAllowed/safeTransfer -> permanently frozen.
}
```

Run with `forge test --fork-url $MAINNET_RPC --match-test testInstantWithdrawCrossEpochDesync -vvv`. The desync reproduces with honest owner/manager/borrower sequencing: only ordinary epoch transitions plus an under-funded instant queue and a default are needed.
