### Title
Unprivileged front-running of `lockup-factory::create` lets an attacker deploy a lockup at a victim's derived address with attacker-chosen terms and no foundation - ([File: lockup-factory/src/lib.rs, lockup/src/lib.rs])

### Summary
`LockupFactory::create` derives the lockup account id deterministically from `sha256(owner_account_id)` and is callable by *any* predecessor with *any* `owner_account_id`, `lockup_duration`, `lockup_timestamp`, `release_duration`, and `vesting_schedule`, with no check binding the caller to the named owner. An attacker can therefore squat the address that will forever be associated with a victim account, initializing `LockupContract::new` with `vesting_schedule: None` (which forces `foundation_account_id: None`, permanently disabling the termination path) and transfers already enabled, before the victim's real grantor ever deploys the legitimate lockup there.

### Finding Description
The invariant the protocol relies on is: `lockup_account_id = hex(sha256(owner_account_id)[..20]).factory_account_id` implies `terms(lockup_account_id) == terms_chosen_by(owner_account_id's_grantor)`. This binding is broken because `create` performs no authorization check tying `env::predecessor_account_id()` to `owner_account_id`: [1](#0-0) 

Any account can call `create(owner_account_id: <victim>, lockup_duration, lockup_timestamp, vesting_schedule: None, release_duration, whitelist_account_id)` and attach only `MIN_ATTACHED_BALANCE` (3.5 NEAR). Because `vesting_schedule.is_some()` is false, the factory sets `foundation_account_id: None`: [2](#0-1) [3](#0-2) 

The factory also unconditionally sets `TransfersInformation::TransfersEnabled { transfers_timestamp: TRANSFERS_STARTED }` (a timestamp already in the past), so the deployed lockup has transfers live from the first block. `LockupContract::new` accepts these attacker-chosen parameters without validating who is calling on the victim's behalf — it only validates that account IDs are syntactically valid and that `foundation_account_id` is `None` whenever `vesting_schedule` is `None`: [4](#0-3) 

Since `lockup_account_id` is a NEAR sub-account of the factory (`<hash>.factory_account_id`), and `Promise::new(lockup_account_id).create_account()` is signed by the factory itself, any predecessor can trigger this deployment — `create_account` will simply fail on the *second* attempt for the same address (front-running / address squatting). No `assert_owner`, `assert_called_by_foundation`, or predecessor-vs-owner check exists anywhere in `create` or `new` to prevent this.

Exploit flow:
1. Attacker calls `lockup-factory.create(owner_account_id="victim.near", lockup_duration=0, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=None)` attaching `MIN_ATTACHED_BALANCE`.
2. The factory deploys and initializes a `LockupContract` at `sha256("victim.near")[..20].factory_account_id`, naming `"victim.near"` as owner, `foundation_account_id: None`, transfers already enabled, lockup duration 0 — i.e., all funds sent there are immediately liquid and never subject to vesting or foundation termination.
3. When the legitimate grantor later tries to run the real `create` (or a raw `createAccount` deploy) for `"victim.near"` at the same derived address, it fails because the account already exists, or — if the grantor instead performs a plain NEAR transfer to that pre-existing address believing it is the (not-yet-created) real lockup — the transferred grant funds land in the attacker-parameterised contract with no vesting/foundation oversight and can be withdrawn immediately by the owner.

### Impact Explanation
This matches the Critical category "a lockup deployed with parameters its rightful creator never chose" directly: the derived lockup address for any account can be permanently squatted by an unprivileged third party with attacker-chosen `lockup_duration`, `vesting_schedule` (or lack thereof), and `foundation_account_id` (forced to `None`), instead of the terms the real grantor intended. If real grant funds subsequently reach that address, previously-intended unvested/locked tokens are released early with no foundation termination possible, which is also independently a Critical impact. The blast radius is every account id whose lockup has not yet been created — repeatable once per victim account (each address can only be squatted once, but the attack is trivially repeatable across arbitrarily many victim accounts) for the cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) each.

### Likelihood Explanation
The attacker needs no special role — any account with 3.5 NEAR can call the public, `#[payable]` `create` method on the factory. The only precondition is that the derived address for the targeted `owner_account_id` has not already been created (true for any account that hasn't received its lockup yet, which is the normal state before a grant is issued). This is fully feasible and cheap, and repeatable across any number of target accounts before their real lockups are deployed.

### Recommendation
Restrict `LockupFactory::create` so that it can only be invoked by an authorized creator (e.g., require `env::predecessor_account_id() == self.foundation_account_id` or another explicitly whitelisted creator role), or require the `owner_account_id` to equal `env::predecessor_account_id()` for self-service lockups, and reject/refund otherwise. Additionally, consider having grantors verify account non-existence via a dedicated on-chain check before transferring grant funds, and never rely on bare transfers to a derived address without re-validating the deployed contract's `vesting_information` and `foundation_account_id`.

### Proof of Concept
```rust
// lockup-factory/src/tests (near-sdk-sim or unit test with MockedBlockchain)
#[test]
fn test_frontrun_lockup_creation_for_victim() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker (not the victim, not the foundation) calls create() naming victim as owner
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE; // attacker's own trivial deposit
    testing_env!(context.clone());

    // owner_account_id == victim.near, vesting_schedule == None => foundation_account_id forced to None
    contract.create(
        ValidAccountId::try_from("victim.near").unwrap(),
        0.into(),      // lockup_duration = 0, immediately liquid
        None,          // lockup_timestamp
        None,          // vesting_schedule -> forces foundation_account_id: None in LockupArgs
        None,          // release_duration
        None,          // whitelist_account_id
    );

    // Assert: the resulting LockupArgs sent to `new` has foundation_account_id == None
    // and transfers_information == TransfersEnabled{ TRANSFERS_STARTED } (already unlocked),
    // while predecessor_account_id ("attacker.near") != owner_account_id ("victim.near"),
    // proving the binding
    //   lockup_terms(hash(owner_account_id)) == terms_chosen_by(owner_account_id's grantor)
    // is violated: terms were chosen by an unrelated attacker, not victim.near's grantor,
    // and the termination path (foundation_account_id) can never run.
}
```
A second call to `create` (or a plain `create_account` transaction) targeting the same `owner_account_id` from the legitimate grantor would then fail with an account-already-exists error, confirming the squat, or — if funds are transferred directly to the existing address — the tokens are immediately withdrawable by the owner with no vesting/lockup constraints, confirmed by asserting `get_locked_amount() == 0` and `vesting_information == VestingInformation::None` on the squatted contract.
