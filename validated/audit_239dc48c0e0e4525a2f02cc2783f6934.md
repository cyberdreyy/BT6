### Title
Builder pending-withdrawal payload commits the full requested amount while `apply_withdrawals` only debits the capped (available) balance, minting uncollateralized Gwei - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` places the **uncapped, requested** `withdrawal.amount` into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` — the payload the execution layer is contractually bound to honor. `apply_withdrawals`, however, only debits the builder's CL-tracked balance by `min(withdrawal.amount, builder_balance)`. When a builder's pending withdrawal amount exceeds its current balance, the EL will pay the `fee_recipient` the full committed amount while the CL removes less than that from the builder's stake, creating Gwei that is not backed by any decrease in tracked balance.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md) builds the committed `Withdrawal` entry directly from the `builder_pending_withdrawals` queue, using the raw requested amount with no capping to the builder's current balance: [1](#0-0) 

That `Withdrawal` (uncapped `amount`) is what gets committed to `state.payload_expected_withdrawals` via `get_expected_withdrawals`/`update_payload_expected_withdrawals`, and the execution layer is required to honor it exactly (per the spec's own note that "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer"): [2](#0-1) 

But when the withdrawal is actually applied to the CL state, `apply_withdrawals` only reduces the builder's balance by the *capped* amount: [3](#0-2) 

The repository's own test explicitly documents this asymmetry: a builder with 1 ETH balance and a pending withdrawal request for 5 ETH produces a committed `Withdrawal.amount` of **5 ETH** (the requested amount) while the CL-side `builders[0].balance` is only reduced to 0 (i.e., a 1 ETH deduction), even though the EL must pay out the full 5 ETH committed in the payload: [4](#0-3) 

This breaks the fundamental invariant that every Gwei paid out on the execution layer must correspond to an equal Gwei debited from the beacon state. `MAX_EFFECTIVE_BALANCE`/`decrease_balance`-style saturation is explicitly noted elsewhere in the spec as a supply-inflation risk that the authors are aware of and manage carefully for validator sweep withdrawals (see the surrounding design note about "net supply inflation" from CL-side saturation), but the same saturation is present—unremediated—in the builder-pending-withdrawal path, and is baked into the committed payload amount itself, not merely a defensive-saturation edge case: [5](#0-4) 

### Impact Explanation
This is the consensus-layer analog of the ScopeLift report's core issue ("appears to succeed but the accounting doesn't match reality"): the withdrawal "succeeds" (it's included and processed, and the queue entry is popped), but the amount actually removed from consensus-tracked state does not match the amount the execution layer is obligated to pay to the `fee_recipient`. The result is Gwei created out of nothing and paid to an arbitrary `fee_recipient` address — a Critical-class issue per the equality "a Gwei created, destroyed or paid to a non-owner." No malicious peer, client bug, or coalition is required; it happens whenever a builder's queued pending-withdrawal amount(s) exceed its current balance at processing time (e.g., multiple pending withdrawals queued when solvent, balance later reduced by an earlier withdrawal in the same processing batch or sweep before this one executes).

### Likelihood Explanation
The order of withdrawal processing (builder-pending → partial → builder-sweep → validator-sweep) and the fact that `builder_pending_withdrawals` can queue multiple entries for the same builder means it is entirely plausible for a builder's aggregate pending withdrawal requests to exceed its balance by the time `apply_withdrawals` runs, purely through normal, spec-compliant sequencing — no attacker action beyond having previously registered legitimate pending withdrawals is needed.

### Recommendation
Cap the committed `Withdrawal.amount` in `get_builder_withdrawals` to the builder's currently available balance (accounting for withdrawals already queued earlier in the same batch), mirroring what `apply_withdrawals` actually debits, so the amount promised to the execution layer never exceeds what is actually deducted from consensus state. Alternatively, track a running "remaining balance" across all withdrawal-generation passes for a given builder and only emit a `Withdrawal` for the capped amount.

### Proof of Concept
Using the repo's own test as the concrete counterexample:
1. Builder 0 has `balance = 1 ETH`.
2. `builder_pending_withdrawals` contains an entry for builder 0 requesting `5 ETH`.
3. `get_builder_withdrawals` emits `Withdrawal(validator_index=<builder 0>, amount=5 ETH)` — this is what `state.payload_expected_withdrawals` commits the execution layer to pay.
4. `apply_withdrawals` executes `state.builders[0].balance -= min(5 ETH, 1 ETH)`, leaving `balance = 0` (only 1 ETH debited).
5. The execution layer, honoring the committed payload, pays the `fee_recipient` the full 5 ETH, while only 1 ETH was ever removed from tracked consensus-layer state — 4 ETH is created with no offsetting decrease anywhere in the beacon state. [4](#0-3)

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
