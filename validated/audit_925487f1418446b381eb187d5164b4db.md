Confirmed: `createDstEscrow` accepts `dstImmutables` (including `parameters` encoding `protocolFeeAmount`/`integratorFeeAmount`) directly from the calling resolver with no cross-check against the fee values computed and emitted by `_postInteraction` on the source chain, and `EscrowDst._withdraw` performs an unchecked subtraction of those fee amounts from `immutables.amount`.

### Title
Resolver-controlled destination-escrow fee parameters can force a permanent underflow revert in `EscrowDst._withdraw`, freezing/stealing maker funds - (File: contracts/EscrowDst.sol, contracts/BaseEscrowFactory.sol)

### Summary
`BaseEscrowFactory.createDstEscrow` deploys the destination escrow using `IBaseEscrow.Immutables` supplied entirely by the caller (the taker/resolver), including the ABI-encoded `parameters` field that carries `protocolFeeAmount` and `integratorFeeAmount`. These values are never validated against `dstImmutables.amount`, nor against the fee amounts that `_postInteraction` computed and emitted in `SrcEscrowCreated` on the source chain. `EscrowDst._withdraw` then computes `amount = immutables.amount - integratorFeeAmount - protocolFeeAmount` with Solidity 0.8 checked arithmetic [1](#0-0) . If the taker deploys the destination escrow with `integratorFeeAmount + protocolFeeAmount >= amount`, this subtraction always reverts, making `withdraw`/`publicWithdraw` permanently uncallable for that escrow.

### Finding Description
- `createDstEscrow` takes `dstImmutables` from calldata as-is and only validates the native-value/safety-deposit accounting; it performs no sanity check on `dstImmutables.parameters` (fee fields) versus `dstImmutables.amount`: [2](#0-1) .
- By contrast, on the source side `_postInteraction` explicitly guards against oversized fees with `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();` [3](#0-2)  — but this check is only applied to the values `_postInteraction` itself computes for the *source* escrow/complement data; it does not constrain what a resolver later passes into `createDstEscrow` for the *destination* escrow, since the two calls are independent and unlinked on-chain.
- The `parameters` bytes are hashed into the immutables hash used for `onlyValidImmutables` and address derivation [4](#0-3) , so whatever fee values the taker chooses at `createDstEscrow` time become binding for that specific deployed escrow, with no path to correct or update them later.
- `EscrowDst._withdraw` unconditionally computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` without any bound check first [5](#0-4) . If fee sum ≥ amount, this reverts every time `_withdraw` is invoked (both `withdraw` and `publicWithdraw` call it), for the life of the escrow.
- This mirrors the root cause of the referenced report: a percentage/amount value that is supposed to be validated and consistently applied before being used in a subtraction/limit calculation is instead left uncontrolled, so downstream settlement logic can be pushed outside its valid range and become permanently unusable.

### Impact Explanation
Because `withdraw`/`publicWithdraw` on `EscrowDst` become permanently reverting, the maker can never receive the destination funds through the normal path once the escrow is deployed with malformed fee parameters. Since `withdraw` requires the taker to already know the secret (`onlyCaller(taker)`), a resolver that has legitimately obtained the secret from the maker off-chain can create such a malformed dst escrow, use the (still-unrevealed, off-chain-shared) secret to withdraw the maker's tokens on the source chain via `EscrowSrc.withdraw` (which has no fee-subtraction bug), while the destination escrow can never release the intended funds to the maker and can only be reclaimed by the taker via `cancel()` after `DstCancellation`. This fits "temporary/permanent freezing of funds during the live swap lifecycle" and effectively enables theft of the maker's source-side assets without honoring the destination-side leg — a High/Critical-class outcome under the bounty's escrow/live-swap-lifecycle scope, triggered purely by an unprivileged taker.

### Likelihood Explanation
This requires no special privilege — any resolver/taker calling `createDstEscrow` (a normal, permissionless part of the flow) can supply arbitrary `parameters`. It requires the resolver to be dishonest (matching the "unprivileged user" attacker model, not a privileged/governance actor), and requires that the maker/verifier does not independently recompute and compare fee fields before revealing the secret — the `DstEscrowCreated` event does not surface the fee parameters for verification, only `escrow`, `hashlock`, and `taker` [6](#0-5) , making off-chain verification harder and the exploit practically reachable.

### Recommendation
In `createDstEscrow`, decode and validate `dstImmutables.parameters` and revert if `protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount` (mirroring the existing `InvalidFeeAmounts` check used in `_postInteraction`). Additionally, emit the fee parameters in `DstEscrowCreated` (or otherwise make them easily verifiable) so makers/relayers can cross-check destination fee amounts against the source-side `SrcEscrowCreated` event before revealing secrets.

### Proof of Concept
1. Maker and resolver agree on a swap; maker shares the secret with the resolver once conditions are met (required since only the taker can call `withdraw`).
2. Malicious resolver calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.amount = X` but `parameters = abi.encode(protocolFeeAmount = X, integratorFeeAmount = X, protocolFeeRecipient, integratorFeeRecipient)` (i.e., fee sum ≥ X), funding the escrow with `msg.value = safetyDeposit (+ X if native)`.
3. Resolver immediately calls `EscrowSrc.withdraw(secret, srcImmutables)` using the secret to claim the maker's source tokens.
4. Maker or anyone calls `EscrowDst.withdraw(secret, dstImmutables)`: `_withdraw` computes `amount = immutables.amount - integratorFeeAmount - protocolFeeAmount` which underflows and reverts every time, per `contracts/EscrowDst.sol` lines 84-93.
5. After `DstCancellation`, the resolver calls `cancel()` on the dst escrow and reclaims the full `amount` plus safety deposit, having already obtained the maker's source-chain tokens — the maker receives nothing from the destination side.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        // Compute the EIP-712 hash for the immutables struct
        bytes calldata parameters = immutables.parameters;
        assembly ("memory-safe") {
            let ptr := mload(0x40)

            // Copy immutables.parameters to memory and compute its hash
            calldatacopy(ptr, parameters.offset, parameters.length)
            let parametersHash := keccak256(ptr, parameters.length)

            calldatacopy(ptr, immutables, IMMUTABLES_SIZE)
            mstore(add(ptr, IMMUTABLES_LAST_WORD), parametersHash)
            ret := keccak256(ptr, IMMUTABLES_SIZE)
        }
    }
