### Title
Process-group–based kill in `unixKiller.Terminate/ForceKill` misses detached (setsid/double-forked) grandchildren, allowing secrets to survive job cancellation - (File: helpers/process/killer_unix.go)

### Summary
`unixKiller` terminates a job's process tree by sending `SIGTERM`/`SIGKILL` to the negative PID of the shell/custom executor's direct child, which relies on that child remaining the leader of the process group created via `Setpgid: true`. A job script that spawns a grandchild which calls `setsid()` (or otherwise re-parents/detaches, e.g. via a classic double-fork daemonization) moves that grandchild into a new session/process group, so it is not a member of the PGID being signaled and survives `KillAndWait`/`ForceKill`.

### Finding Description
The commander is started with `setProcessGroup` in [1](#0-0)  which only sets `Setpgid: true` on the immediate child. Termination in [2](#0-1)  always signals `pk.getPID()`, which is `-cmd.Process().Pid` — i.e., the negative of the direct child's PID, used as a process-group ID per `kill(2)` semantics, as documented in [3](#0-2) . This delivery mechanism only reaches processes that are still members of that specific process group.

If a job (running under the shell executor, or a custom executor invoking `NewOSCmd`/`CommandOptions` with attacker-influenced `Env` such as `CI_JOB_TOKEN`) spawns a child that calls `setsid(2)` — creating a new session and a new process group where it becomes the group leader — that process (and anything it further forks) is removed from the original PGID. `KillAndWait` in [4](#0-3)  calls `Terminate()` then, after a timeout, `ForceKill()`, both of which target only the original PGID via `syscall.Kill(pk.getPID(), ...)`. Neither call walks `/proc` or otherwise discovers descendants outside the group, so the detached grandchild is never signaled and keeps running (and keeps its inherited environment, including `CI_JOB_TOKEN`/masked variables) after the job is reported as killed/canceled.

No other layer in this repository compensates: there is no cgroup-based confinement, no PID-namespace isolation, and no post-kill reconciliation against `/proc/<pid>` shown in `job_unix.go`, `killer.go`, or `killer_unix.go`. The only isolation mechanism present is `Setpgid`, which is precisely what `setsid()` in a child defeats.

### Impact Explanation
On a shared host running the shell executor (or a custom executor without its own process-tree isolation), an unprivileged pipeline author can cause a process holding `CI_JOB_TOKEN`/masked CI variables to remain alive and running after the job is canceled/terminated. If the runner and its OS/PID namespace are reused for subsequent jobs (a normal, documented operating mode for the shell executor), the orphaned process's environment (`/proc/<pid>/environ`) or open resources can be read by anything with sufficient host access at that point in time, extending the token's exposure window beyond intended job lifetime. This matches the scoped impact: secrets surviving job teardown due to an incomplete process-tree reclaim.

### Likelihood Explanation
This is straightforward and highly reproducible: any job script (`before_script`/`script`) can run a one-liner such as a shell background job with `setsid nohup ... &` or a two-line Python/Go helper doing a double-fork, no special privileges required beyond normal job execution capability. It works identically whether the job is canceled by a user or timed out, since both paths funnel through `KillAndWait` → `Terminate`/`ForceKill`. This is a native/expected behavior of process groups vs. sessions, not a hypothetical: `setsid` detaching from `Setpgid`-created groups is exactly how daemonization tools traditionally escape parent supervision.

### Recommendation
Do not rely solely on `Setpgid`+negative-PID signaling for job cleanup. Options: track all descendant PIDs (walk `/proc/*/stat`'s `ppid` chain) and signal each explicitly, in addition to the group signal; or run job processes inside a PID namespace/cgroup that unconditionally reclaims all processes on job shutdown; or explicitly prevent jobs from calling `setsid`/detaching (not generally enforceable in shell executor) and instead adopt a cgroup-based kill (`cgroup.kill`) so freeze/kill semantics are independent of process-group membership.

### Proof of Concept
Go integration test extending `helpers/process/killer_unix_integration_test.go`/`killer_integration_test.go`:
1. Use `NewOSCmd` to start a shell script that immediately backgrounds a child via `setsid sh -c 'echo $SECRET_VAR; sleep 300' &` (or a small helper binary that calls `syscall.Setsid()` before sleeping), with `CommandOptions.Env` containing `SECRET_VAR=dummy-ci-job-token`.
2. Capture the grandchild's PID (e.g., have it write its own PID to a temp file after `Setsid()`).
3. Call `KillAndWait(command, waitCh)` on the top-level command (as `osKillWait` does), forcing both `Terminate` and, after `gracefulKillTimeout`, `ForceKill` to fire.
4. Assert: `command.Wait()`/`waitCh` reports the parent as killed, but `os.Stat("/proc/<grandchild_pid>")` still succeeds and `os.ReadFile("/proc/<grandchild_pid>/environ")` still contains `SECRET_VAR=dummy-ci-job-token`, proving the secret-bearing process survived full job termination.

func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}
```

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}

func (kw *osKillWait) KillAndWait(command Commander, waitCh chan error) error {
	process := command.Process()
	if process == nil {
		return ErrProcessNotStarted
	}

	log := kw.logger.WithFields(logrus.Fields{
		"PID": process.Pid,
	})

	processKiller := newProcessKiller(log, command)
	processKiller.Terminate()

	select {
	case err := <-waitCh:
		return err
	case <-time.After(kw.gracefulKillTimeout):
		processKiller.ForceKill()

		select {
		case err := <-waitCh:
			return err
		case <-time.After(kw.forceKillTimeout):
			return &KillProcessError{pid: process.Pid}
		}
	}
}
```
