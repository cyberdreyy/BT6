### Title
A new `requestWithdraw` overwrites `lastWithdrawRequest`, letting a user claim a loss-adjusted (haircutted) receipt again at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` under-funds pending receipts, `collectWithdrawFunds` records a per-epoch haircut in `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`, but it leaves each user's full pre-haircut basis in `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][epoch]`. The haircut is supposed to be applied lazily in `_claimLossAdjustedWithdrawRequest`, which looks up the haircut via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Because `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch`, a user who files any new withdraw request after the loss epoch permanently orphans the old haircutted receipt: the loss-adjusted branch reads the new (non-loss) epoch, finds price 0, returns early, and the stale basis falls through to `_claimFundedWithdrawRequest`, which pays the aggregate `withdrawsRequests[_user]` at par.

### Finding Description
Relevant code:

- `collectWithdrawFunds` (contracts/strategies/idle/IdleCreditVault.sol:411-430): on `_amount < pendingBasis` it stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and sets `pendingWithdraws = 0`. Crucially, per-user `withdrawsRequests`/`withdrawsRequestsByEpoch` still contain the un-haircutted basis.
- `_claimLossAdjustedWithdrawRequest` (lines 789-801): `lossEpoch = lastWithdrawRequest[_user]`; only if `lossRecoveryPriceByEpoch[lossEpoch] != 0` does it clear that epoch's basis via `_clearWithdrawClaimForEpoch` and pay `claimBasis * lossRecoveryPrice / RECOVERY_FULL`.
- `_claimFundedWithdrawRequest` (lines 319-350): after the one-epoch wait (`epochNumber > lastWithdrawRequest[_user]`, or `epochEndDate == 0` for a closed pool), it pays `amount = withdrawsRequests[_user] + apr0Principal + apr0Interest` in full and burns only the principal receipts.
- `requestWithdraw` (lines 281-293) sets `lastWithdrawRequest[_user] = currentEpoch` and adds the new basis to `withdrawsRequests[_user]`.

Attack sequence (all phases attacker-reachable):

1. Epoch N buffer: attacker (a KYC'd tranche holder) calls `requestWithdraw` for amount X. `withdrawsRequestsByEpoch[attacker][N] = X`, `lastWithdrawRequest[attacker] = N`.
2. Honest manager calls `stopEpochWithDuration` with a realized loss; borrower under-funds receipts. `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL` and clears `pendingWithdraws`. The strategy received only `X * p / RECOVERY_FULL` for the attacker's receipt.
3. Epoch N+1 buffer: attacker calls `requestWithdraw` again for any dust amount Y (even a tiny second tranche balance or a freshly deposited position). `lastWithdrawRequest[attacker] = N+1` and `withdrawsRequests[attacker] = X + Y`.
4. After epoch N+1 stops (or immediately if the pool was later closed, `epochEndDate == 0`), attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` and returns; `_claimFundedWithdrawRequest` then pays `X + Y` at par instead of `X*p/FULL + Y`.

The haircutted epoch-N basis in `withdrawsRequestsByEpoch[attacker][N]` is never cleared by any other path (`_clearWithdrawClaimForEpoch` is only reached through the loss-adjusted or defaulted-epoch branches), so it is silently repaid at par.

### Impact Explanation
Direct theft: the attacker recovers the loss that `stopEpochWithDuration` explicitly socialized onto pending receipts. The stolen amount is `X * (1 - lossRecoveryPriceByEpoch[N]/RECOVERY_FULL)`, paid from strategy-held underlyings that are reserved for other funded claimants, leaving later claimants (or active LPs through NAV) short by the same amount. The "one receipt one payout / haircut enforcement" invariant is broken.

### Likelihood Explanation
Requires a partial-funding epoch (`collectWithdrawFunds` with `_amount < pendingBasis`), which is a supported, manager-invoked mode (`stopEpochWithDuration`/`previewLossAdjustedWithdrawFunds` exist precisely for it), plus one ordinary withdraw request by the attacker in a later buffer window and a one-epoch wait. No privileged or malicious actions are needed; the attacker is a normal tranche-token holder.

### Recommendation
Track loss-adjusted receipts independently of `lastWithdrawRequest`, or iterate/record all epochs with `lossRecoveryPriceByEpoch` set per user. Minimal fix: in `claimWithdrawRequest`, check `lossRecoveryPriceByEpoch` for every epoch with a nonzero `withdrawsRequestsByEpoch[_user][e]` (or store a per-user `lossAdjustedEpoch` list at request time) instead of keying off `lastWithdrawRequest[_user]`; alternatively, apply the haircut eagerly in `collectWithdrawFunds` by iterating pending receipts, or block new `requestWithdraw`s while `withdrawsRequestsByEpoch[_user][lossEpoch] != 0` for any loss epoch.

### Proof of Concept
Foundry fork sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testPocLossReceiptRepaidAtPar() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, amount, true);      // KYC'd AA holder
    _depositWithUser(address(this), amount, true); // other LP

    _startEpochAndCheckPrices(0);

    // buffer: attacker requests full withdraw -> receipt basis X in epoch N
    vm.prank(attacker);
    uint256 X = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // honest manager stops epoch with realized loss -> partial funding
    uint256 loss = X / 2;
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - loss);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, epochDuration, loss);
    // lossRecoveryPriceByEpoch[N] = ~RECOVERY_FULL/2; attacker basis still X

    // next buffer: attacker deposits dust and files a new request (epoch N+1)
    deal(defaultUnderlying, attacker, ONE_SCALE);
    vm.startPrank(attacker);
    underlying.approve(address(cdoEpoch), ONE_SCALE);
    uint256 minted = cdoEpoch.depositAA(ONE_SCALE);
    cdoEpoch.requestWithdraw(minted, address(AAtranche)); // overwrites lastWithdrawRequest
    vm.stopPrank();

    // run epoch N+1 to completion so the funded-claim gate opens
    _startEpochAndCheckPrices(1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // attacker claims: epoch-N haircutted basis is repaid at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // expected fair payout ~ X/2 + dust; actual payout == X + dust
    assertGt(got, X, "haircutted epoch-N receipt repaid at par");
}
```

The extra `~X/2` comes out of underlyings the strategy holds for other pending/funded claims, confirming direct theft rather than a self-inflicted rounding artifact.
