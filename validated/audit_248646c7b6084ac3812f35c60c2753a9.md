### Title
Unprotected `initializeConfig` Allows Any Caller to Inject a Malicious Config into `BridgeCommittee` — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` carries no access-control modifier. Any Ethereum address can call it before the legitimate deployer does, permanently pointing the committee at an attacker-controlled `IBridgeConfig` implementation. Every downstream bridge operation that reads `committee.config()` — token-address resolution, decimal conversion, chain-ID checks — then operates on attacker-supplied data.

---

### Finding Description

`BridgeCommittee.initializeConfig` is declared `external` with a single guard:

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

There is no `onlyOwner`, no `initializer`, and no committee-signature check. The only protection is the one-time `address(config) == address(0)` guard, which is exactly the pattern the external report identifies as frontrunnable.

The deployment script calls `initializeConfig` in a **separate transaction** from the proxy deployment:

```solidity
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));
BridgeCommittee committeeImplementation =
    BridgeCommittee(Upgrades.getImplementationAddress(bridgeCommittee));
committeeImplementation.initializeConfig(address(bridgeConfig));
``` [2](#0-1) 

Between the proxy deployment (which calls the `initializer`-protected `initialize`) and the subsequent `initializeConfig` call, there is a window in which any mempool observer can submit a higher-gas transaction calling `initializeConfig` with an attacker-controlled address.

The `config` reference is consumed by `SuiBridge` in every critical path:

- `transferBridgedTokensWithSignatures` reads `committee.config()` for `chainID`, `tokenAddressOf`, and `tokenSuiDecimalOf`.
- `bridgeERC20` reads `committee.config()` for `isTokenSupported` and `tokenAddressOf`.
- `_transferTokensFromVault` reads `committee.config().tokenAddressOf(tokenID)` to decide which ERC-20 to release from the vault. [3](#0-2) 

---

### Impact Explanation

A malicious `IBridgeConfig` can:

1. **Remap token IDs to wrong ERC-20 addresses.** When the committee signs a legitimate `TOKEN_TRANSFER` message for tokenID=1 (wBTC), `_transferTokensFromVault` resolves the address through the malicious config and releases a different asset (e.g., wETH) from the vault. Deposited wBTC is permanently locked; wETH is drained instead.

2. **Return `address(0)` for all tokens.** Every `transferBridgedTokensWithSignatures` call reverts at the `require(tokenAddress != address(0))` check, permanently locking all vault funds.

3. **Return a false `chainID`.** The `tokenTransferPayload.targetChain == config.chainID()` check fails for every message, making the bridge permanently inoperable.

Because `initializeConfig` can only succeed once (`config == address(0)`), the state is irreversible without a committee-signed `upgradeWithSignatures` call — which itself requires the legitimate committee to be operational and aware of the compromise.

This matches the allowed impact: **permanent fund lock** and **harmful smart-contract behavior**.

---

### Likelihood Explanation

The attack requires only:
1. A standard Ethereum address (no special privilege).
2. A pre-deployed malicious contract implementing `IBridgeConfig`.
3. A higher-gas transaction submitted after the proxy `initialize` transaction is confirmed but before the `initializeConfig` transaction is mined.

Deployment scripts are public once broadcast to the mempool. Frontrunning infrastructure (flashbots, MEV bots) makes this trivially automatable. Likelihood is **Medium** — the window is narrow but the tooling to exploit it is widely available.

---

### Recommendation

Restrict `initializeConfig` to the deployer or to the committee itself. The simplest fix is to add an `onlyOwner` check (with the owner set during `initialize`) or to fold the config assignment directly into the `initialize` function so both operations occur atomically in the same `initializer`-protected call:

```solidity
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // add config here
) external initializer {
    __CommitteeUpgradeable_init(address(this));
    __UUPSUpgradeable_init();
    // ... existing stake setup ...
    config = IBridgeConfig(_config);
}
```

This eliminates the two-transaction window entirely.

---

### Proof of Concept

1. Attacker deploys `MaliciousConfig` implementing `IBridgeConfig` where `tokenAddressOf(1)` returns the address of wETH (instead of wBTC) and all other methods behave normally.
2. Deployer broadcasts the `BridgeCommittee` proxy deployment + `initialize` transaction (confirmed in block N).
3. Deployer broadcasts `BridgeCommittee(proxy).initializeConfig(realBridgeConfig)` — visible in the mempool.
4. Attacker broadcasts `BridgeCommittee(proxy).initializeConfig(maliciousConfig)` with higher gas — mined first in block N+1.
5. Deployer's `initializeConfig` reverts with `"BridgeCommittee: Config already initialized"`.
6. If the deployer does not notice and proceeds, `SuiBridge` is deployed pointing at the compromised committee.
7. Any subsequent `transferBridgedTokensWithSignatures` for tokenID=1 releases wETH from the vault instead of wBTC, draining wETH while wBTC remains permanently locked.
