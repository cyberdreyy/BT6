### Title
Instant-withdraw claims pay the aggregate of all epochs regardless of per-epoch funding, letting an unfunded receipt drain reserves belonging to other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out `instantWithdrawsRequests[_user]` — a scalar that aggregates instant-withdraw receipts across *all* epochs — without verifying that the epochs backing those receipts were actually funded. Like the bnxt_en bug, where `bnxt_set_dflt_rings` assumed a resource count (`num_tc`) that had silently changed, the claim path assumes the per-user aggregate maps 1:1 to the funded pool, while funding is tracked only globally and per epoch (`pendingInstantWithdraws`, `instantWithdrawClaimsByEpoch`, `collectInstantWithdrawFunds`). An unprivileged tranche holder can queue an unfunded instant receipt behind a funded one and withdraw underlying reserved for other claimants.

### Finding Description
On `requestInstantWithdraw`, receipts are minted 1:1 and accumulated into the single per-user counter `instantWithdrawsRequests[_user]`, while the funded/unfunded split lives only in global/per-epoch state: [1](#0-0) 

`collectInstantWithdrawFunds` decrements only `pendingInstantWithdraws` by whatever partial amount the CDO collected — the protocol explicitly supports partial funding (`_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as the already-funded remainder): [2](#0-1) [3](#0-2) 

But the claim path ignores funding entirely. It burns the full cross-epoch aggregate and calls `_transferFundedClaim`, which pays out of the strategy's underlying balance (dipping into `defaultRecoveryReserve` only if set, otherwise the shared funded pool): [4](#0-3) 

There is no equivalent of the funded-epoch gating used for normal withdraws (`epochNumber <= lastWithdrawRequest` revert in `_claimFundedWithdrawRequest`), and no per-epoch check that the user's instant basis ≤ the funded portion for that epoch. The defaulted path (`_claimDefaultedInstantWithdrawRequest`) correctly clears only `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — acknowledging that instant receipts are epoch-scoped — but the normal claim path forgets this and pays the whole multi-epoch aggregate at par. [5](#0-4) 

### Impact Explanation
Scenario: instant-withdraw mode enabled (APR dropped by more than `instantWithdrawAprDelta`, so `_isInstantWithdrawEnabled()` triggers in `IdleCDOEpochVariant`). Attacker, a KYC'd AA holder, calls `requestWithdraw` → `requestInstantWithdraw(X)` in epoch N; the borrower/strategy only partially funds the instant queue via `collectInstantWithdrawFunds`, so `pendingInstantWithdraws > 0` remains. In epoch N+1 the attacker requests another instant withdraw `Y`, also unfunded. The attacker then calls `claimInstantWithdrawRequest` through the CDO and receives `X + Y` in underlying — including the never-funded `Y` — paid from cash reserved for other users' funded instant receipts or funded normal receipts (`_transferFundedClaim`). Result: direct theft of funded reserves / insolvency for the remaining claimants, breaking the "one receipt, one funded payout" invariant. Loss is bounded only by the size of the unfunded receipt the attacker can mint, i.e., their tranche balance.

### Likelihood Explanation
Requires a partially unfunded instant-withdraw queue, which arises whenever borrower liquidity at `stopEpoch`/`startEpoch` covers only part of the instant claims (the codebase explicitly models this case via `pendingInstantWithdraws` and the prefunded-reserve accounting in `defaultPendingClaimBasis`). The attacker needs only a tranche balance and to sequence `requestInstantWithdraw` across two epochs before claiming — all unprivileged actions. No privileged misbehavior is needed; honest manager/borrower calls create the partial-funding precondition. Guard coverage is absent: nothing in `claimInstantWithdrawRequest` references `pendingInstantWithdraws` or `instantWithdrawClaimsByEpoch` before paying.

### Recommendation
Track funded instant-claim basis per epoch and consume it on claim, mirroring `lossRecoveryPriceByEpoch`/`withdrawsRequestsByEpoch` for normal withdraws. Concretely: on `collectInstantWithdrawFunds`, record a per-epoch funded ratio (e.g., `instantFundedPriceByEpoch[epoch]` or a funded-basis mapping); in `claimInstantWithdrawRequest`, iterate the user's request epochs and pay only `min(basis, fundedBasis)` per epoch, deferring the unfunded remainder instead of paying it. Alternatively, gate claims until `pendingInstantWithdraws == 0` or until the user's aggregated receipt epochs are fully funded.

### Proof of Concept
Fork-test outline (Foundry, mainnet fork of a live IdleCreditVault deployment with instant-withdraw enabled):

```solidity
function testUnfundedInstantReceiptDrainsFundedPool() external {
    // epoch 0: attacker and victim deposit AA; APR drops > instantWithdrawAprDelta
    // victim: cdo.requestWithdraw -> strategy.requestInstantWithdraw(V)
    // manager/borrower: collectInstantWithdrawFunds partially funds only V
    //   -> pendingInstantWithdraws == 0, strategy holds V underlying
    // epoch 1 (next epoch boundary): attacker requestInstantWithdraw(A)
    //   -> instantWithdrawsRequests[attacker] == A, pendingInstantWithdraws == A (unfunded)
    // attacker: cdo.claimInstantWithdrawRequest()
    //   -> burns A receipt, transfers A underlying: pays from victim's funded V reserve
    assertEq(attackerReceived, A);                 // paid despite zero funding
    assertLt(strategyBalance, V);                  // victim's claim now underfunded
    // victim claim reverts on transfer or leaves strategy insolvent
    vm.expectRevert();
    victimClaim();
}
```

Uncertainty noted: I verified the request/collect/claim code paths and the absence of a funding check in `claimInstantWithdrawRequest`, but did not fully trace `IdleCDOEpochVariant.claimInstantWithdrawRequest`'s wrapper or whether the CDO adds its own liquidity check before forwarding the claim. If the CDO-level call independently requires the strategy's underlying balance to cover `pendingInstantWithdraws`, the exploit window narrows to cross-claimant ordering, but the missing per-epoch funding attribution remains.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
