### Title
Missing replay protection in webapi-trigger `HandleLegacyUserMessage` path allows re-execution of previously captured signed capability trigger messages - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
Unlike the vault handler, which enforces a digest-based `RequestReplayGuard` (`core/capabilities/vault/authorizer.go`, `core/capabilities/vault/request_replay_guard.go`) rejecting any request digest seen before, the `capabilities` gateway handler's `HandleLegacyUserMessage` only checks that the message payload timestamp is not older than `MaxAllowedMessageAgeSec`. There is no check that a given `MessageId`/signature/digest has already been processed, so a captured, validly-signed `api.Message` can be resubmitted any number of times within the staleness window and will be re-forwarded to the DON as a fresh trigger.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:250-269`) validates the message's signature/format via `msg.Validate()` and then calls `h.HandleLegacyUserMessage(ctx, msg, callback)`. In `core/services/gateway/handlers/capabilities/handler.go:341-421`, the handler:
1. Decodes the `TriggerRequestPayload` and checks `payload.Timestamp == 0` (rejects zero) [1](#0-0) .
2. Rejects the message only if it's *older* than `MaxAllowedMessageAgeSec` [2](#0-1) .
3. Explicitly notes with a TODO that allowlisting/rate-limiting is not yet implemented [3](#0-2) .
4. Stores the callback keyed only by `msg.Body.MessageId` in `h.savedCallbacks` and forwards the message to all DON members via `don.SendToNode` [4](#0-3) .

There is no persistent/expiring store of already-seen `MessageId`s or signature digests analogous to `RequestReplayGuard.CheckAndRecord` used by the vault handler [5](#0-4)  and wired into `authorizer.AuthorizeRequest` [6](#0-5) . Consequently, resubmitting the exact same signature/payload bytes within the message-age window passes all checks identically to the first submission and is dispatched to the DON again as a new trigger, since `savedCallbacks` is only used to route the *eventual node response* back to the caller and does not perform any "already processed" rejection - a repeat submission simply overwrites/creates a new map entry and a new `SendToNode` fan-out occurs.

This contrasts with the node-handshake path (`ConnectionManager.StartHandshake`, tested in `core/services/gateway/connectionmanager_test.go:198-202`) and the connector's `ChallengeResponse` (`core/services/gateway/connector/connector.go:415-419`), both of which enforce a timestamp tolerance *and* are single-use challenge/response handshakes, and with the vault module which additionally applies digest-based replay rejection (`ErrRequestAlreadySeen`).

### Impact Explanation
An attacker who has captured a previously valid, signed `api.Message` destined for the webapi-trigger capability handler can replay it to cause the DON to re-execute the associated workflow trigger multiple times within the configured staleness window (`MaxAllowedMessageAgeSec`). Depending on the workflow's actions, this could cause duplicate/unauthorized re-execution of workflow logic (e.g., repeated external calls, repeated on-chain writes, or repeated resource-consuming operations), corresponding to the "unauthorized job run" bounty impact class. It does not, by itself, disclose secrets or bypass authentication (the signature is still valid and from the legitimate sender), but it breaks the replay-prevention invariant that other node-facing and vault-facing paths in this codebase already enforce.

### Likelihood Explanation
Preconditions: attacker must possess a previously captured, validly-signed `api.Message` (e.g., from network observation, log exposure, or being the legitimate signer resubmitting intentionally) and must replay it before `MaxAllowedMessageAgeSec` elapses. No node/operator/admin access needed - only capture of one legitimate signed payload, matching the "unprivileged attacker" threat model. This is straightforward and repeatable as many times as desired within the staleness window since there is no per-message-id/digest single-use enforcement.

### Recommendation
Add a digest- or `MessageId`-based replay guard to `capabilities.handler.HandleLegacyUserMessage` (and any other legacy/JSON-RPC user-message handlers lacking one), mirroring `core/capabilities/vault/request_replay_guard.go`: record `(sender, MessageId)` or a content digest with an expiry equal to `MaxAllowedMessageAgeSec`, and reject the request if it has already been seen, before creating a new `savedCallbacks` entry or forwarding to the DON.

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

```go
func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {

		return nil, err
```
