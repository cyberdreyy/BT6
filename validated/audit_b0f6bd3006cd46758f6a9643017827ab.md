### Title
Loss-adjusted `stopEpoch` haircut is applied only to a user's *latest* request epoch — older pending receipts claim at par and drain the strategy - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When the borrower short-funds pending withdrawals at `stopEpoch` (`collectWithdrawFunds` with `_amount < pendingWithdraws`), the strategy stores a single `lossRecoveryPriceByEpoch[epochNumber]` haircut that was computed over the **aggregate** `pendingWithdraws` basis. At claim time, however, `_claimLossAdjustedWithdrawRequest` only haircuts the receipts of the epoch stored in `lastWithdrawRequest[_user]` — which `requestWithdraw` overwrites on every new request. Receipts recorded under earlier epochs (`withdrawsRequestsByEpoch[user][olderEpoch]`) survive in `withdrawsRequests[_user]` and are later paid **at par** via `_claimFundedWithdrawRequest`, even though the borrower funded less than the full aggregate. First claimants overdraw the vault; later claimants' transactions revert, permanently freezing their funded receipts.

### Finding Description
`requestWithdraw` records each request both in the per-user aggregate `withdrawsRequests[_user]` and per epoch `withdrawsRequestsByEpoch[_user][currentEpoch]`, then unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` (IdleCreditVault.sol:282-293). There is no check preventing a user who already holds an unclaimed receipt from an older epoch from filing a new request — the code comment in `_claimFundedWithdrawRequest` explicitly documents this accumulation ("if a user does not claim ... he will have to wait for another epoch to claim both requests", lines 322-325).

If the following `stopEpoch` is funded short (realized loss path), `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingWithdraws` over the *entire* pending bucket and clears `pendingWithdraws` to 0 (lines 411-421). At claim time:

- `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` — only the *most recent* request epoch — and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]`, paying `claimBasis * lossRecoveryPrice` (lines 789-800).
- The remainder in `withdrawsRequests[_user]` (the older-epoch basis, left untouched by `_clearWithdrawClaimForEpoch` at lines 815-820) is then paid at par by `_claimFundedWithdrawRequest` (line 341: `amount = normalAmount + ...`).

So a user with receipts in epoch N-1 and epoch N receives `basis(N-1) * 1.0 + basis(N) * price`, while the strategy only received `price * totalPending`. The OOB-write analog: the "buffer" (aggregate pending basis) was short-funded once, but the flush loop only applies the short length to the last segment and writes the rest at full length.

### Impact Explanation
The strategy's underlying balance after `collectWithdrawFunds` is `price * totalPending < totalPending`. Every claimant whose receipts span multiple request epochs — or more importantly, every claimant processed before the haircut inconsistency is exhausted — extracts strictly more than their pro-rata funded share. The deficit is socialized onto the *last* claimants: `_transferFundedClaim` reverts (line 904/906, `safeTransfer` fails on insufficient balance), permanently freezing their already-funded withdraw receipts. Loss magnitude is up to `pendingLoss = _lossAmount * pendingBasis / totalBasis` (the same quantity `previewLossAdjustedWithdrawFunds` computes at lines 454-459), i.e. the entire haircut is borne by whoever claims last rather than pro rata. This is a direct solvency/fair-payout invariant break: "one receipt, one funded payout" is violated, and funded receipts become unclaimable.

### Likelihood Explanation
- Reachable by any KYC-passing lender (allowed attacker class): deposit in epoch 1, request withdraw during epoch 1 and *do not claim*; request a second withdraw during epoch 2. Both are unprivileged calls.
- Requires a `stopEpoch`/`stopEpochWithDuration` where the borrower funds less than `pendingWithdraws` (honest borrower/manager sequencing — partial loss is a designed flow, see `previewLossAdjustedWithdrawFunds`), which is exactly when the buggy branch runs.
- The guard at lines 263-270 only blocks a *new* request when the *old* receipt was already loss-adjusted; it does not block accumulating normal receipts, so the multi-epoch state is straightforward to reach.
- Demand: borrower underpayment/loss event at an epoch stop — an expected protocol event, not attacker-dependent.

### Recommendation
Apply the loss haircut to the user's **entire** pending basis at the loss epoch, not only the latest request epoch. Concretely: in `_claimLossAdjustedWithdrawRequest`, iterate/clear all `withdrawsRequestsByEpoch` entries for the user (or track a per-user list of pending request epochs), or store the loss price under a global "pending-claims" key and haircut the full `withdrawsRequests[_user]` + APR0 buckets in one shot. Alternatively, reject a new `requestWithdraw` while the user still has unclaimed normal receipts (extend the existing loss-adjusted guard to any nonzero `withdrawsRequests`), eliminating the multi-epoch aggregate.

### Proof of Concept
Foundry fork sketch (structure mirrors `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function test_LossHaircutOnlyAppliesToLastRequestEpoch() external {
    // Epoch 0: userA and userB deposit AA, epoch runs
    uint256 amt = 10_000 * ONE_SCALE;
    uint256 trA = idleCDO.depositAA(amt); // userA context
    _startEpochAndCheckPrices(0);

    // userA requests withdraw in epoch 0 running... but does NOT claim
    uint256 reqA1 = cdoEpoch.requestWithdraw(trA / 2, address(AAtranche));
    _stopEpochAndCheckPrices(0, apr, expectedFunds); // epochNumber -> 1, reqA1 funded normally
    // userA intentionally does not call claimWithdrawRequest()

    // Epoch 1 runs; userA requests again -> lastWithdrawRequest[userA] = 1,
    // withdrawsRequestsByEpoch[userA][0] still holds reqA1 basis
    _startEpochAndCheckPrices(1);
    uint256 reqA2 = cdoEpoch.requestWithdraw(trA / 2, address(AAtranche));

    // stopEpoch #1 with realized loss: borrower funds less than pendingWithdraws
    uint256 pending = strategy.pendingWithdraws(); // = reqA1 + reqA2 + others
    uint256 funded  = pending / 2;                 // 50% loss recovery price
    deal(defaultUnderlying, borrower, funded + strategy.expectedEpochInterest());
    cdoEpoch.stopEpochWithDuration(lossAmount, duration); // -> collectWithdrawFunds(funded < pending)

    // claim: _claimLossAdjustedWithdrawRequest haircuts only epoch-1 basis (reqA2 * 0.5)
    //        _claimFundedWithdrawRequest then pays reqA1 at PAR (price 1.0)
    uint256 balPre = underlying.balanceOf(userA);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(userA) - balPre;
    assertEq(got, reqA1 + reqA2 / 2); // overpaid vs funded share (reqA1 + reqA2) * 0.5

    // subsequent claimant's funded receipt reverts -> permanent freezing
    vm.expectRevert();
    // cdoEpoch.claimWithdrawRequest() for userB whose entire basis was haircut-funded
}
```

Key assertions: `strategy.lossRecoveryPriceByEpoch(epochNumber)` is set once over the aggregate, while `withdrawsRequestsByEpoch[userA][0]` remains nonzero after `_claimLossAdjustedWithdrawRequest` (IdleCreditVault.sol:811-820 only clears `lossEpoch`), and `_transferFundedClaim` (line 904-906) reverts for the last claimant because the balance was drained by par-paid older receipts.
