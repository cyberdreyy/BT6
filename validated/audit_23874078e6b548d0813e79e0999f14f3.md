### Title
Stale per-epoch instant-withdraw receipt is reused after its claim is paid, inflating the default claim basis and diluting/stranding default recovery — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`claimInstantWithdrawRequest` pays a user by burning the aggregate `instantWithdrawsRequests[_user]`, but never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]`. The "freed" claim leaves a dangling accounting reference. If the borrower defaults in that same epoch while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest` treat already-paid receipts as still outstanding.

### Finding Description
The analog of a use-after-free is a receipt that remains registered in per-epoch storage after its payout state was destroyed:

- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (`IdleCreditVault.sol:366-374`).
- `claimInstantWithdrawRequest` (pre-default path) only zeroes `instantWithdrawsRequests[_user]` and burns the aggregate; the per-epoch maps are untouched (`IdleCreditVault.sol:387-392`).
- Later, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the default claim basis whenever `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-649`), so `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over a basis inflated by claims that were already paid at par (`IdleCreditVault.sol:686-692`).
- `_claimDefaultedInstantWithdrawRequest` also still sees the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` for users who were already paid (`IdleCreditVault.sol:842-856`).

The user's second claim cannot mint extra funds because `_burn(_user, claimBasis)` requires balance (the receipt tokens were burned). However, the inflated `totalBasis` is real damage:

1. `defaultRecoveryPrice` is set too low, so every honest defaulted-epoch and post-default claimant is underpaid relative to their entitlement (`recoveryPrice` divides an unchanged reserve by a bigger basis).
2. The reserve share earmarked for the phantom claims is never drawn by anyone — `defaultRecoveryReserve` keeps it, and only post-default withdrawals can consume it at 1:1, effectively donating defaulted claimants' recovery to later claimants, or leaving it stranded if no post-default requests occur.

### Impact Explanation
Quantified loss: if `instantWithdrawClaimsByEpoch[defaultEpoch]` contains `X` of already-claimed basis and real pending basis is `B`, the recovery price is multiplied by `B/(B+X)`. With `R` total reserve, honest claimants lose `R * X/(B+X)`; that amount stays locked in `defaultRecoveryReserve` (permanent freezing) or is transferred to unrelated later claimants (theft of the defaulted cohort's recovery). With a large prior instant claim (e.g., a whale who claimed 90% of the epoch's instant queue before default), honest defaulted claimants can lose the majority of their entitled recovery.

### Likelihood Explanation
Requires: instant-withdraw mode enabled, a claim processed in epoch N, then an unfunded instant request outstanding (`pendingInstantWithdraws != 0`) when the borrower defaults and recovery is finalized in the same epoch N. Defaults are a designed-for state (`finalizeDefaultRecovery`, `defaulted()`), and the prefunded/partially-funded instant queue is explicitly contemplated by `_defaultPrefundedInstantReserve`. An attacker can engineer the condition cheaply by making and claiming a large instant request early in the epoch, but the trigger still depends on a real borrower default, so likelihood is moderate-low. The stale-entry issue itself is deterministic and requires no privileged misbehavior.

### Recommendation
In `claimInstantWithdrawRequest`, when paying a funded instant claim, also clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or iterate/settle the user's per-epoch entries) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the paid amount, so the epoch claim total only ever reflects outstanding receipts. Alternatively, snapshot the per-epoch claim total only at default time by excluding already-burned receipts.

### Proof of Concept
Foundry fork PoC sketch (based on `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. Epoch N running. Attacker deposits, requests instant withdraw X.
//    CDO funds it: strategy.collectInstantWithdrawFunds(X) -> pendingInstantWithdraws back to 0.
// 2. Attacker calls claimInstantWithdrawRequest -> paid X at par.
//    BUG: instantWithdrawsRequestsByEpoch[attacker][N] == X still,
//         instantWithdrawClaimsByEpoch[N] still includes X.
// 3. Victim requests instant withdraw Y in same epoch N; stays unfunded
//    -> pendingInstantWithdraws == Y.
// 4. Borrower defaults; manager calls finalizeDefaultRecovery(R, src).
//    defaultPendingClaimBasis() = pendingWithdraws + (X + Y)  // X is phantom
//    recoveryPrice = R * RECOVERY_FULL / (activeBasis + X + Y)  // diluted
// 5. Victim claims: receives Y * recoveryPrice / RECOVERY_FULL
//    instead of Y * R / (activeBasis + Y). Attacker's re-claim reverts on _burn,
//    but reserve share R * X / (activeBasis + X + Y) is stranded or absorbed
//    by later postDefaultRequests claimants.
// Assert: recovered victim payout < expected payout; defaultRecoveryReserve
// retains a surplus equal to the phantom basis share.
```
