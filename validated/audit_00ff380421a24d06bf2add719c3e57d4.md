### Title
External Initiator credentials are misidentified as authenticated Users, allowing EI holders to trigger int-ID job runs meant to be user-only - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets the same `SessionUserKey` context value that user-session/token auth sets, giving external initiators a synthetic `clsessions.User{Role: clsessions.UserRoleRun}`. Because `PipelineRunsController.Create` distinguishes "user vs EI" solely via `auth.GetAuthenticatedUser(c)` (which just checks for the presence of `SessionUserKey`), an EI-authenticated request is indistinguishable from a real user session and `isUser` evaluates to `true`, defeating the intended EI restriction.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` explicitly documents and enforces that jobs referenced by integer ID may only be run by Users, not External Initiators: [1](#0-0) 

The gate is `_, isUser := auth.GetAuthenticatedUser(c)`. However, `GetAuthenticatedUser` in `core/web/auth/auth.go` simply reads the `SessionUserKey` value from the gin context and type-asserts it to `*clsessions.User`: [2](#0-1) 

Critically, `AuthenticateExternalInitiator` — the auth method used for EI-authenticated requests — also sets `SessionUserKey`, populating it with a synthetic user object carrying `UserRoleRun`: [3](#0-2) 

Because both real user auth (`AuthenticateBySession`/`AuthenticateByToken`) and EI auth (`AuthenticateExternalInitiator`) populate `SessionUserKey`, `GetAuthenticatedUser` cannot distinguish between them — it returns `ok=true` in both cases. Consequently, `isUser` in `Create` is `true` for an EI-authenticated caller, and the code proceeds into the "int ID" branch and calls `prc.App.RunJobV2(ctx, jobID, nil)`, exactly the behavior the comment says should be blocked ("only users are allowed to run jobs using int IDs - EIs not allowed").

### Impact Explanation
An attacker holding only an External Initiator credential (a restricted, run-role-only credential intended solely to trigger webhook/EI-bound job runs) can invoke `POST /v2/jobs/{intID}/runs` for any job addressable by its numeric ID and cause `RunJobV2` to execute it — an unauthorized job run that bypasses the intended EI/User authorization boundary. This maps to Chainlink's "unauthorized job run" bounty impact class, since a lower-privilege credential type is able to perform an action reserved for full user sessions/tokens.

### Likelihood Explanation
Exploitation requires only possession of valid External Initiator access-key/secret credentials (obtainable by any principal set up as an EI, which is a much lower trust tier than a full node user) and knowledge/guessing of a target job's integer ID. No admin/operator access, no session hijacking, and no additional bypass is needed — the flaw is deterministic and 100% reproducible on every request since the root cause is in `GetAuthenticatedUser`'s inability to differentiate the two auth flows.

### Recommendation
Do not overload `SessionUserKey` for External Initiator authentication. Either:
1. Have `AuthenticateExternalInitiator` avoid setting `SessionUserKey` entirely, and have downstream role-checking middleware (e.g. `RequiresRunRole`) explicitly consult `GetAuthenticatedExternalInitiator` when appropriate, or
2. Introduce a distinct marker (e.g., a boolean/flag field on the synthetic user, or a separate context key such as `IsExternalInitiator`) that `PipelineRunsController.Create` checks in addition to/instead of `GetAuthenticatedUser`, so EI-derived pseudo-users are excluded from the `isUser` check.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a test app with an External Initiator record and credentials (as done in `core/web/pipeline_runs_controller_test.go`), plus a job with an integer ID (non-webhook type) in `JobORM`.
2. Send `POST /v2/jobs/{intID}/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (EI headers) rather than session cookie or API key/secret.
3. Assert, at the `auth.AuthenticateExternalInitiator` + `auth.GetAuthenticatedUser` layer, that `isUser` is currently `true` (demonstrating the flaw) via a unit test directly calling `GetAuthenticatedUser` after invoking `AuthenticateExternalInitiator` on a test gin context.
4. At the HTTP layer, assert current (vulnerable) behavior: the response is `200 OK` with a pipeline run resource (job actually ran), instead of the expected `422 Unprocessable Entity` with `"bad job ID"`.
5. After applying the fix, re-run the same request and assert the response is `422` with `"bad job ID"` and `RunJobV2` was never invoked.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
