### Title
Response cache key omits WorkflowID, causing cross-workflow HTTP response confusion in the CRE Gateway HTTP capability handler - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The v2 HTTP capability gateway handler caches outbound HTTP action responses keyed by `req.Hash()`, which per its own comment and unit tests is computed from method, URL, headers, body, and workflow **owner** only — explicitly excluding `WorkflowID`. This contradicts the handler's own documented design ("Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" and "Cache Key: Generated from workflow ID and request hash") in `core/services/gateway/handlers/capabilities/v2/README.md`. As a result, two different workflows belonging to the same owner that issue identical HTTP action requests will receive each other's cached responses.

### Finding Description
`makeOutgoingRequest` in `core/services/gateway/handlers/capabilities/v2/http_handler.go` unmarshals an `OutboundHTTPRequest` from a node message and, when `CacheSettings.MaxAgeMs > 0`, calls `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)`. [1](#0-0) 

`responseCache.Fetch` and `Set` key the cache map purely by `req.Hash()`: [2](#0-1) [3](#0-2) 

The struct comment explicitly states the hash is derived from "method, URL, headers, body, workflowOwner" (no `WorkflowID`): [4](#0-3) 

This is confirmed by the handler's own test suite, which asserts that differing `WorkflowID` values produce **the same hash**, while differing `WorkflowOwner` values produce different hashes: [5](#0-4) [6](#0-5) 

This directly contradicts the component's documented guarantee in the README: [7](#0-6) 

This is the same bug class as the Bonding.sol finding: an edge case in the design contract (per-workflow isolation) is assumed by callers/downstream logic and documented, but the underlying primitive (the cache key derivation) silently omits the discriminating field needed to actually enforce that isolation — causing state/response objects meant for one principal (workflow) to be delivered to another.

### Impact Explanation
An unprivileged workflow owner running multiple concurrent workflows (or an operator managing multiple workflows under one owner identity) that issue HTTP action requests with identical method/URL/headers/body but with `CacheSettings.MaxAgeMs > 0` will have Workflow A's cached HTTP response served to Workflow B (and vice versa) as long as both requests hash identically. This is a cross-workflow response confusion: a workflow can receive data that was fetched/cached in the context of a different workflow execution, undermining the "workflow-scoped caching" isolation the component advertises. Depending on how the external HTTP endpoint personalizes responses per workflow (e.g., via headers not part of `req.Hash()`'s inputs, dynamic upstream state, or endpoints that vary responses by caller identity out-of-band), this can leak data intended for a different workflow context into an unrelated workflow's execution, and cause functionally incorrect responses to be silently consumed. Because the cache is DON-shard-scoped and the field is entirely missing from the hash (not merely misconfigured), this occurs deterministically for any two workflows generating identical hashable requests, not as a narrow edge case.

### Likelihood Explanation
This is highly likely to be triggered unintentionally in normal operation: many CRE workflows commonly call the same external API/URL with the same static headers/body (e.g., a shared price feed or webhook endpoint) but different `WorkflowID`s, and workflow authors would reasonably enable `CacheSettings.MaxAgeMs` for such calls expecting caching to work "per workflow" as documented. No malicious actor action is required — regular, unprivileged workflow-owner activity (submitting two workflows that hit the same endpoint) is sufficient to trigger cross-workflow response reuse.

### Recommendation
Include `WorkflowID` in the cache-key hash computation (alongside method, URL, headers, body, and workflow owner) so that `req.Hash()` — or the map key derived from it in `responseCache` — uniquely scopes cache entries per workflow, consistent with the documented "Workflow Isolation" guarantee. Update `TestRequestHash`'s "having different workflowID results in same Hash" test case to instead assert that different `WorkflowID` values produce different hashes, and add a regression test verifying that `Fetch`/`Set` do not return a cached response across differing `WorkflowID`s with otherwise identical requests.

### Proof of Concept
1. Workflow A (`WorkflowID = "wf-1"`, `WorkflowOwner = "owner-x"`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {MaxAgeMs: 600000, Store: true}}` via the gateway's `makeOutgoingRequest`. The HTTP call succeeds and the response is stored in `responseCache` keyed by `req.Hash()` (per `core/services/gateway/handlers/capabilities/v2/response_cache.go:66-107`).
2. Workflow B (`WorkflowID = "wf-2"`, same `WorkflowOwner = "owner-x"`) issues an identical `OutboundHTTPRequest` (same method/URL/headers/body/cache settings) with a different `WorkflowID`.
3. Because `req.Hash()` does not include `WorkflowID` (verified directly by the test at `response_cache_test.go:139-149`), Workflow B's request hits the cache hit path in `Fetch` (`response_cache.go:71-77`) and receives Workflow A's cached response without ever contacting the external endpoint — despite being a distinct workflow.

Note: `req.Hash()` itself is implemented in the external `chainlink-common` package (`github.com/smartcontractkit/chainlink-common/pkg/types/gateway`), which is not part of this repository's index; its exact field list could not be directly inspected here, but its behavior is unambiguously pinned down by the `responseCache` struct comment and the passing unit tests in this repo, which together confirm `WorkflowID` is excluded from the hash while `WorkflowOwner` is included.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
