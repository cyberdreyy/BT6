### Title
A single queued deposit permanently bricks `stopEpochWithDuration` on the prefunded variant — (`contracts/IdleCDOEpochQueue.sol`, `contracts/IdleCDOEpochVariantPrefunded.sol`)

### Summary
In the prefunded CDO variant (`IdleCDOEpochVariantPrefunded` with `epochQueue` configured), the post-stop hook `prefundedDepositsToProcess()` reverts whenever `epochPendingDeposits[settledEpoch] != 0`. Any KYC-passing lender can keep a dust `requestDeposit` pending in the queue for the epoch being settled, making every `stopEpochWithDuration` call revert and permanently freezing the vault.

### Finding Description
`requestDeposit` lets any allowed wallet queue underlying for `epochNumber + 1` while the epoch is running (`IdleCDOEpochQueue.sol:103-127`). Deposits are only blocked for the settled epoch after prefunding happens (`epochPrefundedDeposits[nextEpoch] != 0`, line 115) or inside `prefundedDepositWindow` — which is optional (`prefundedDepositWindow == 0` disables the cutoff, line 116).

When `stopEpochWithDuration` runs, `_afterStopEpochWithDuration` unconditionally calls `queue.prefundedDepositsToProcess()` (`IdleCDOEpochVariantPrefunded.sol:77`). That function resolves the epoch to settle as `epochNumber` (post-increment) and reverts if `epochPendingDeposits[_epoch] != 0` (`IdleCDOEpochQueue.sol:277-282`):

```solidity
_prefunded = epochPrefundedDeposits[_epoch];
_checkNotAllowed(epochPendingDeposits[_epoch] != 0);
```

An attacker who deposited (even 1 wei) into the queue for the next epoch and never calls `deleteRequest` leaves `epochPendingDeposits != 0`, so the whole `stopEpochWithDuration` transaction reverts and all state rolls back. `deleteRequest` is only callable by the depositor (`IdleCDOEpochQueue.sol:184-199`) — there is no privileged path to clear or refund someone else's pending deposit. The direct `stopEpoch` selector is also blocked whenever a queue is configured (`_beforeStopEpoch`, `IdleCDOEpochVariantPrefunded.sol:43`), so there is no alternate stop path. This is the same bug class as the Flatcoin report: a queued order/deposit that can never be executed turns into an always-reverting path, and no mechanism exists to evict it.

### Impact Explanation
Permanent freezing of funds, quantified as the entire vault TVL. While `isEpochRunning` stays true: no buffer period can start, `processWithdrawRequests`/claims can't settle, borrower principal can't be recalled, and the pool can't be closed (`stopEpochWithDuration(..., _isRequestingAllFunds)` hits the same revert). Emergency/unpause paths that depend on the epoch state machine are also stuck.

### Likelihood Explanation
The attacker only needs to be a KYC-passing lender (an explicitly allowed attacker class) and deposit the smallest unit once during any running epoch on a prefunded-variant deployment with `epochQueue` set. It works even before `prefundedDepositWindow`, even if manager prefunds other deposits (attacker can deposit before prefunding is ever triggered, since deposits are only rejected after `epochPrefundedDeposits` is set — and even then only for that epoch; with window 0 an attacker can also re-deposit in subsequent epochs). Cost is ~1 wei of underlying plus gas; success is deterministic.

### Recommendation
Do not couple epoch settlement to user-controlled queue state. Options:
- In `prefundedDepositsToProcess`, treat leftover `epochPendingDeposits` for the settled epoch as still-claimable deposits (roll them into the next epoch or mark them refundable) instead of reverting.
- Give owner/manager a `forceDeleteRequest`/sweep that refunds a queued deposit to its owner, so a griefing deposit can be cleared.
- Enforce a mandatory `prefundedDepositWindow` and require `processDepositsToBorrower` (which zeroes `epochPendingDeposits`) before `stopEpochWithDuration`, so the settled epoch can never carry raw pending deposits.

### Proof of Concept
Foundry test (extend `test/foundry/IdleCDOEpochVariantPrefunded.t.sol` setup):

```solidity
function testStopEpochDosByPendingQueueDeposit() external {
    // configure prefunded queue
    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    // no cutoff window required for the attack
    // (or attacker deposits before the window)

    // KYC'd attacker queues a dust deposit for the next epoch
    address attacker = makeAddr("attacker");
    deal(address(underlying), attacker, 1);
    _requestDepositWithUser(attacker, 1); // requestDeposit(1)

    uint256 requestEpoch = strategy.epochNumber() + 1;
    assertEq(queue.epochPendingDeposits(requestEpoch), 1);

    // epoch ends; manager tries to stop
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(0, expectedInterest, cdoEpoch.epochDuration(), 0);

    // direct stopEpoch is also blocked when a queue is configured
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // closing the pool reverts too
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(0, 1, 0, 0);

    // attacker never calls deleteRequest -> epoch stays running forever,
    // borrower principal cannot be recalled and withdraw claims never settle
    assertTrue(cdoEpoch.isEpochRunning());
}
```

Note: I verified the revert path statically (`prefundedDepositsToProcess` at `IdleCDOEpochQueue.sol:277-282` called unconditionally from `_afterStopEpochWithDuration` at `IdleCDOEpochVariantPrefunded.sol:77`, gated only by `epochQueue != 0`; `stopEpoch` selector blocked at line 43; `deleteRequest` restricted to the depositor at lines 184-199). One residual uncertainty: `_prefundedEpochToProcess` returns `epochNumber` (or `+1` on default), and I inferred that `strategy.epochNumber()` increments inside the stop flow so the attacker's `epochNumber+1` deposit lands on the settled epoch id — the PoC should confirm the index alignment, but even if it lands on a different id the revert still triggers whenever the resolved epoch has pending deposits.
