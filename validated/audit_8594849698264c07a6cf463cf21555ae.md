### Title
Job process tree termination via process-group signaling does not kill descendants that detach into a new session/process group - ([File: helpers/process/job_unix.go])

### Summary
`setProcessGroup` in `helpers/process/job_unix.go` sets `Setpgid: true` so the job's shell process becomes the leader of a new process group, and `unixKiller.Terminate`/`ForceKill` in `helpers/process/killer_unix.go` kill that group via `syscall.Kill(pk.getPID(), sig)` using the negative PGID. Any grandchild process that calls `setsid(2)` (or otherwise `setpgid`s itself out of the original group) is no longer a member of that process group and is not reached by the group-directed signal, so it survives job cancellation/timeout.

### Finding Description
`setProcessGroup` (helpers/process/job_unix.go:36-40) configures the job's top-level `exec.Cmd` with `Setpgid: true`, making its PID also the PGID for itself and any children that don't change their own group. `unixKiller.getPID()` (helpers/process/killer_unix.go:50-52) returns `-PID` of that top-level process, and `Terminate`/`ForceKill` call `syscall.Kill(-PID, SIGTERM/SIGKILL)`, which per `kill(2)` semantics delivers the signal to every process whose *current* PGID equals PID. A job script is attacker-controlled shell/PowerShell/custom-executor script content; a job author can trivially run `setsid sleep 600 &` (or equivalent double-fork/`nohup`+`setsid` trick, or a compiled helper calling `setsid()`), which creates a new session and a new process group whose PGID is that child's own PID, detaching it from the job's original process group. When the runner subsequently calls `Terminate`/`ForceKill` (job timeout, pipeline cancellation, `KillAndWait` in helpers/process/killer.go), the group-directed kill only reaches processes still in the original PGID; the detached descendant keeps running. There is no cgroup, pid-namespace, or job-object-equivalent containment on Linux/macOS/BSD shell/ssh/custom executors — process-group signaling is the only mechanism, and it is bypassable by any process running as the job user.

### Impact Explanation
On shell, ssh, and custom executors (any executor lacking container/namespace isolation), an unprivileged job can leave behind a long-running or persistent process on the runner host that outlives the job's lifecycle and is not torn down when the job is cancelled, times out, or completes, violating the invariant that "a job's process tree is fully torn down at job end." This process runs with the privileges of the job's execution user and can continue consuming resources, hold open network listeners, or execute code after the runner believes the job has ended, and it persists across subsequent jobs run on the same host/user, giving out-of-band code execution outside the job lifecycle.

### Likelihood Explanation
Trivially reproducible by any pipeline author with shell access in their `.gitlab-ci.yml` script (`setsid <cmd> &`), requiring no special runner configuration beyond the shell/ssh/custom executor already trusting the job's shell environment (this is not the same as the excluded "shell executor trust on a shared host" caveat about privileged admin choices — this is a specific technical gap in process cleanup, not a documented trust boundary). It is fully deterministic and does not depend on timing races.

### Recommendation
On Linux, prefer cgroup-based process tracking/killing (freezer + kill all PIDs in the cgroup, or `cgroup.kill`) instead of/in addition to process-group signaling so detached/setsid'd descendants are still torn down; where cgroups aren't available, additionally scan `/proc` for descendants of the job's PID tree (via PPID chains) and signal them individually, or run jobs in a PID namespace so reparenting/detaching cannot escape the namespace's init reaper.

func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}

// KillAndWait will take the specified process and terminate the process and
// wait util the waitCh returns or the graceful kill timer runs out after which
// a force kill on the process would be triggered.
func (kw *osKillWait) KillAndWait(command Commander, waitCh chan error) error {
	process := command.Process()
	if process == nil {
		return ErrProcessNotStarted
	}

	log := kw.logger.WithFields(logrus.Fields{
		"PID": process.Pid,
	})

	processKiller := newProcessKiller(log, command)
	processKiller.Terminate()

	select {
	case err := <-waitCh:
		return err
	case <-time.After(kw.gracefulKillTimeout):
		processKiller.ForceKill()

		select {
		case err := <-waitCh:
			return err
		case <-time.After(kw.forceKillTimeout):
			return &KillProcessError{pid: process.Pid}
		}
	}
}
