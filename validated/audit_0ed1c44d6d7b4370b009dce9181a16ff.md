## Analysis

**Binding claimed:** For any live request `R`, `confirmations.get(&R).len() == |{m ∈ live_members : m approved R}|`, and execution only proceeds once that count is `>= num_confirmations` of **live** members.

**What the code actually does:** `delete_member` only purges requests/confirmations for the member being removed when that member was the *original submitter* of the request (`r.member == member`), it never scrubs that member's entry out of the `confirmations` set of requests submitted by *other* members that the removed member had already confirmed. [1](#0-0) 

`confirm()` then decides whether to execute purely from the raw size of the stored `HashSet<String>`, with no check that each string still corresponds to a current member: [2](#0-1) 

`assert_valid_request` only checks that the caller is a current member and that the request/confirmation-set exist — it never validates that every prior confirmer is still a member: [3](#0-2) 

The `delete_member` guard `self.members.len() - 1 >= self.num_confirmations` only protects against the member *count* dropping below `num_confirmations`; it does nothing about **stale confirmation strings** left behind in unrelated requests' confirmation sets.

### Exploit flow
With members `{A,B,C,D}` and `num_confirmations = 3`:
1. `A` calls `add_request` to create `R1` (e.g. `Transfer`).
2. `D` calls `confirm(R1)` → `confirmations[R1] = {D}` (1 of 3).
3. Separately, `A,B,C` reach quorum on a `DeleteMember{D}` request, which executes and removes `D` from `members`. `delete_member` only cleans requests where `r.member == D` (i.e., requests *D authored*), so `R1` (authored by `A`) and its confirmation set `{D}` are untouched — `D` no longer exists as a member, yet its stale approval remains counted toward `R1`.
4. `A` calls `confirm(R1)` → `{D, A}` (2 of 3).
5. `B` calls `confirm(R1)` → `{D, A, B}` → `confirmations.len() + 1 >= num_confirmations` (3 >= 3) → `execute_request` fires the `Transfer`.

Only two *live* members (`A`, `B`) actually approved; `C` never touched `R1`. The request executes with fewer than `num_confirmations` live approvals because a defunct member's leftover confirmation is counted.

## Finding

### Title
Stale confirmations from deleted members are counted toward `num_confirmations`, allowing request execution below live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` only removes requests/confirmations authored by the deleted member, leaving that member's confirmation entries intact in other members' requests' `confirmations` sets. `confirm()` counts raw set size against `num_confirmations` without verifying each confirmer is still a live member, letting a request execute with fewer than `num_confirmations` genuinely live approvals.

### Finding Description
The invariant that should hold is: the confirmation count used to gate `execute_request` in `confirm()` ( [4](#0-3) ) equals the number of currently-live members who approved that specific request. `delete_member` ( [1](#0-0) ) only scrubs requests it itself authored (`r.member == member`), never scanning other requests' `confirmations` sets to remove the departing member's entry. Since `confirmations` is a plain `LookupMap<RequestId, HashSet<String>>` with no back-reference to which members are still active, a confirmation string from a removed member silently persists and is later counted by `confirm()`'s `confirmations.len() as u32 + 1 >= self.num_confirmations` check, without `assert_valid_request` ( [3](#0-2) ) ever revalidating membership of prior confirmers.

Attacker flow: any of the remaining live members (who need not be malicious individually, but collectively exploit the ordering) can complete a `Transfer`/other request with one fewer live approval than `num_confirmations` by ensuring a member who already confirmed the target request is later removed via a separate `DeleteMember` request, then having the remaining members top up confirmations to reach the raw threshold.

### Impact Explanation
Funds (or any privileged multisig action — `AddKey`, `FunctionCall`, further membership changes) can be moved/executed with fewer than `num_confirmations` live members having actually approved it. This directly matches the Critical category "a multisig request executed below `num_confirmations` live members," since NEAR can leave the multisig account without the number of genuine approvals the multisig's own security parameter mandates. It's repeatable for any request/member-deletion ordering satisfying the described sequence.

### Likelihood Explanation
No special privilege beyond being a multisig member is required; the flow only needs normal multisig operations (`add_request`, `confirm`, a `DeleteMember` request) executed in an achievable order — no timing race, no external contract, no gas exhaustion. This is a straightforward miss in `delete_member`'s cleanup logic and is fully deterministic given the ordering described.

### Recommendation
When deleting a member, iterate all active requests' `confirmations` sets (not just those the member authored) and remove the departing member's string; alternatively, revalidate at `confirm()` time that every entry in `confirmations.get(&request_id)` still corresponds to a current `self.members` entry before counting them toward `num_confirmations`.

### Proof of Concept
`cargo test` in `multisig2` crate:
1. Build `MultiSigContract::new(members = [A,B,C,D], num_confirmations = 3)`.
2. As `A`, `add_request(R1 = Transfer{...})`.
3. As `D`, `confirm(R1)` → assert `confirmations.get(&R1).unwrap().len() == 1`.
4. As `A`, `add_request(R2 = DeleteMember{D})`; as `A,B,C` (context switches), `confirm(R2)` three times → assert `members` no longer contains `D` and `members.len() == 3`.
5. As `A`, `confirm(R1)` → assert `confirmations.get(&R1).unwrap().len() == 2` and set still contains stale `D` entry.
6. As `B`, `confirm(R1)` → assert `requests.get(&R1).is_none()` (executed) while only `A` and `B` are live confirmers (`C` never confirmed), demonstrating execution with `2 < num_confirmations = 3` live approvals.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));

            "Already confirmed this request with this key",
        );

            let request = self.remove_request(request_id);
            /********************************

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
