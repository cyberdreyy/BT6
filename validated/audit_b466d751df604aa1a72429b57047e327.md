### Title
Chainstate v1's tenure-duplicate check uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, letting a v1-era signer sign two conflicting tenure-start blocks for the same tenure - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView::validate_tenure_change_payload` (chainstate v1, pre-global-state signer protocol) and `GlobalStateView::validate_tenure_change_payload` (chainstate v2, global-state signer protocol) both implement the same invariant: a signer must refuse to sign a second tenure-start block for a tenure it has already signed a tenure-start block for. The two implementations enforce this equality check inconsistently.

### Finding Description
In v2 (`stacks-signer/src/chainstate/v2.rs:344-348`), the duplicate-tenure-start guard queries `signer_db.get_last_signed_block(&block.header.consensus_hash)`, which returns a block whenever this signer has *signed it* (locally accepted or globally accepted) — the comment explicitly states this is deliberate: "Only blocks we have signed (locally or globally accepted) count here." [1](#0-0) 

In v1 (`stacks-signer/src/chainstate/v1.rs:505-518`), the equivalent guard queries `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` instead — which only returns a block once the *node* has confirmed and adopted it (global acceptance), not merely once this signer has signed it. [2](#0-1) 

This is the same class of bug as the reported StudioCMS advisory: two code paths meant to enforce one authorization/consistency invariant use different comparison strengths, and the weaker one lets through what the stronger one blocks. Here, the invariant is "a signer signs at most one tenure-start block per tenure" (an equality/one-per-tenure guard, analogous to "signed vs validated" or "one-per-height" checks called out in scope). Chainstate v1's version of the check only fires after global acceptance (i.e., after the *node* processes and adopts a block), leaving a window between "I signed tenure-start block A" (`mark_locally_accepted`, `signed_self` set) and "the node processed A" (`mark_globally_accepted`) during which the v1 path treats the tenure as if nothing had been signed yet.

Concretely: a signer running the v1 (pre-global-state) protocol version signs tenure-start block A for tenure T (state becomes `LocallyAccepted`, `signed_self` set, own signature broadcast per `store_and_process_block_signature`/`handle_block_pre_commit`/`SIGN` path in `stacks-signer/src/v0/signer.rs:2442-2538` and `809-1000`). Before the node processes/announces block A (`NewBlock` → `mark_globally_accepted`, `stacks-signer/src/v0/signer.rs:715-726`), the same miner (or an attacker controlling the miner slot) proposes a competing tenure-start block B for the same tenure T. When this signer evaluates B via `check_block_against_local_state` → `SortitionsView::check_proposal` → `validate_tenure_change_payload`, the "already signed a block in this tenure" check calls `get_last_globally_accepted_block`, which still returns `None` because A has not yet been globally accepted — so the duplicate check passes and B is not rejected on this basis, unlike what would happen under v2's stricter `get_last_signed_block` check.

### Impact Explanation
If this discrepancy is not otherwise closed by the generic cross-tenure conflict logic in `handle_block_pre_commit` (`get_signed_conflicts`/`conflict_still_blocks`, documented in `docs/signer-flows.md` section 5) before the final signature is actually placed on B, a single signer running the v1 protocol path could end up signing two different tenure-start blocks (A and B) for the same tenure. That is a direct break of the "no signing conflicting blocks" invariant this repo's scope calls out as a Critical-severity outcome (a signer signing a conflicting block). Even if the later pre-commit-stage conflict check (`get_signed_conflicts`) is intended as the final backstop, `check_proposal`/`validate_tenure_change_payload` is documented as an early filter that is supposed to catch exactly this case per-tenure before the more expensive/height-scoped later check runs, so the v1/v2 inconsistency represents a real erosion of defense-in-depth around the "one signed tenure-start block per tenure" guarantee, applicable to any signer/fleet still running the v1 (non-global-state) chainstate path.

### Likelihood Explanation
This is triggerable by a single miner-controlled proposal sequence (propose A, then quickly propose a conflicting B before A is globally accepted) against any signer still evaluating proposals via the v1 chainstate path (`uses_global_state()` false, selected in `check_block_against_state`, `stacks-signer/src/v0/signer.rs:865-869`), requiring only normal miner/gossip capability — no majority of signers or additional keys needed to trigger the weaker-check code path itself.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the v2 implementation and its documented rationale, so that a locally-signed (but not yet globally accepted) tenure-start block also counts as "already signed" for the purposes of rejecting a competing tenure-start block in the same tenure.

### Proof of Concept
Not independently executable from the index alone (would require running the v1 (`SortitionsView`) signer path end-to-end with `signer_db` state and observing that `check_proposal` on block B for the same tenure passes the duplicate check because `get_last_globally_accepted_block` returns `None` while A is only `LocallyAccepted`). This is asserted from direct code comparison between `stacks-signer/src/chainstate/v1.rs:505-518` and `stacks-signer/src/chainstate/v2.rs:340-357`; I could not fully verify within this session whether `handle_block_pre_commit`'s later `get_signed_conflicts`/`conflict_still_blocks` check (in `stacks-signer/src/v0/signer.rs`) fully closes this gap before the final signature is emitted for the v1 path — a Devin session with the full repo and test harness would be needed to trace that interaction precisely and build a concrete reproduction.
