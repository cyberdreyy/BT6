### Title
Unbounded CPU/memory cost in `UiLookupTable::from` allows single `getAccountInfo(jsonParsed)` call to scale linearly with attacker-controlled ALT size - ([File: account-decoder/src/parse_address_lookup_table.rs])

### Summary
An unprivileged attacker can create an Address Lookup Table (ALT) account and repeatedly extend it (across many low-cost, unprivileged transactions) up to `MAX_ACCOUNT_DATA_LEN` (10 MiB), yielding hundreds of thousands of stored `Pubkey` entries. A single subsequent `getAccountInfo` (or `getMultipleAccounts`/`getProgramAccounts`) call with `encoding=jsonParsed` triggers `parse_address_lookup_table` → `AddressLookupTable::deserialize` → `UiLookupTable::from`, which allocates a `String` for every address in the account with no size/count cap, making the cost of one RPC call scale with attacker-controlled on-chain data size.

### Finding Description
The RPC path for `getAccountInfo` with `jsonParsed` encoding is:
`RpcClient::get_account_info` → `JsonRpcRequestProcessor::get_account_info` (`rpc/src/rpc.rs:534-560`) → `get_encoded_account` (`rpc/src/rpc.rs:2552-2573`) → `encode_account`/`encode_ui_account` (`account-decoder/src/lib.rs:46-101`) → for `UiAccountEncoding::JsonParsed`, unconditionally calls `parse_account_data_v3` regardless of `account.data().len()` [1](#0-0)  → `parse_address_lookup_table` (`account-decoder/src/parse_address_lookup_table.rs:8-21`) → `AddressLookupTable::deserialize(data)` → `UiLookupTable::from`, which does:

```rust
addresses: address_lookup_table.addresses.iter().map(|address| address.to_string()).collect(),
``` [2](#0-1) 

Unlike the base58/binary encoding path, which enforces `MAX_BASE58_BYTES` (128 bytes) before encoding [3](#0-2) , there is no equivalent size/count guard for `JsonParsed` encoding before `parse_account_data_v3` is invoked [1](#0-0) .

ALT accounts are owned by the `address_lookup_table` program and grow via repeated, unprivileged `ExtendLookupTable` instructions (`create_lookup_table` → repeated `extend_lookup_table`). Each account can grow up to `MAX_ACCOUNT_DATA_LEN` (10 MiB) [4](#0-3) , which after the fixed metadata (`LOOKUP_TABLE_META_SIZE`) yields on the order of hundreds of thousands of 32-byte `Pubkey` entries. A single `getAccountInfo` request with `jsonParsed` on this account causes `UiLookupTable::from` to iterate the entire address list, calling `to_string()` (base58 encoding, heap allocation) on each entry and collecting into a `Vec<String>`, then that entire vector is serialized to JSON for the RPC response — CPU and memory cost scale linearly (or worse) with the account's byte size, which is fully attacker-controlled and not bounded by any RPC-side limit.

### Impact Explanation
This is a single-client, single-request CPU/latency amplification on the account-decoder read path: one `getAccountInfo(jsonParsed)` call against an attacker-grown ALT account forces the RPC node to do work proportional to the maximum permitted account size (10 MiB / ~312k addresses) rather than work bounded by an explicit RPC-side limit. This matches the "cost bounded by explicit limits, not on-chain data size" invariant violation and falls into the RPC read-path unbounded-cost-for-a-single-low-rate-call bounty category described in the prompt.

### Likelihood Explanation
Fully feasible with only unprivileged capabilities: the attacker funds/creates the ALT account (rent cost scales with account size, which is a real but bounded cost the attacker pays once) and issues repeated `extend_lookup_table` transactions to reach near-`MAX_ACCOUNT_DATA_LEN`. This requires no leader/validator control and is a self-contained, repeatable on-chain data-crafting attack, followed by a single low-rate `getAccountInfo(jsonParsed)` request that any client could later issue.

### Recommendation
Add an explicit size/entry-count cutoff before attempting `jsonParsed` decoding of any account (or specifically before calling `AddressLookupTable::deserialize`/`UiLookupTable::from`), analogous to the existing `MAX_BASE58_BYTES` guard in `encode_bs58`. For example, in `encode_ui_account` (`account-decoder/src/lib.rs`), check `account.data().len()` against a fixed maximum before dispatching to `parse_account_data_v3` for `JsonParsed`, falling back to `Base64` binary encoding (as already done on parse failure) when the account exceeds the limit. Alternatively, cap the number of addresses processed/returned in `UiLookupTable::from` and return an error/fallback beyond that cap.

### Proof of Concept
```rust
// account-decoder/src/parse_address_lookup_table.rs (benchmark/PoC)
#[test]
fn poc_max_size_alt_decoding_cost_unbounded() {
    use std::{borrow::Cow, time::Instant};
    use solana_address_lookup_table_interface::state::{AddressLookupTable, LookupTableMeta, LOOKUP_TABLE_META_SIZE};
    use solana_pubkey::Pubkey;

    // Max permitted account data length (10 MiB); attacker can grow an ALT
    // account to (approximately) this size via repeated unprivileged
    // extend_lookup_table instructions.
    const MAX_ACCOUNT_DATA_LEN: usize = 10 * 1024 * 1024;
    let num_addresses = (MAX_ACCOUNT_DATA_LEN - LOOKUP_TABLE_META_SIZE) / 32;

    let mut addresses = Vec::with_capacity(num_addresses);
    addresses.resize_with(num_addresses, Pubkey::new_unique);
    let lookup_table = AddressLookupTable {
        meta: LookupTableMeta::default(),
        addresses: Cow::Owned(addresses),
    };
    let data = AddressLookupTable::serialize_for_tests(lookup_table).unwrap();

    let start = Instant::now();
    let parsed = parse_address_lookup_table(&data).unwrap(); // simulates one getAccountInfo(jsonParsed) call
    let elapsed = start.elapsed();

    if let LookupTableAccountType::LookupTable(ui) = parsed {
        assert_eq!(ui.addresses.len(), num_addresses);
    }

    // Expected assertion for a bounded-cost invariant (currently fails):
    // decoding cost must not scale with account size; e.g. assert elapsed
    // stays under a fixed bound regardless of num_addresses.
    assert!(
        elapsed.as_millis() < 50,
        "decoding cost scaled with account size: {:?} for {} addresses",
        elapsed, num_addresses
    );
}
```
This test demonstrates that `parse_address_lookup_table`/`UiLookupTable::from` performs `O(num_addresses)` allocation and string conversion work with no upper bound independent of account size, confirming the RPC `jsonParsed` path lacks a data-size cutoff before decoding is attempted (verified against `account-decoder/src/lib.rs:80-91`, which invokes `parse_account_data_v3` unconditionally for `JsonParsed`).
