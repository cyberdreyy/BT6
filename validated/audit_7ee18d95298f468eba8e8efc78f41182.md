### Title
Post-default withdraw requests are paid 1:1 from `defaultRecoveryReserve` that was sized only for defaulted-epoch claims, draining recovery funds owed to pre-default claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `defaultRecoveryFinalized` is true, `requestWithdraw` mints a fresh receipt to the user and records it in `postDefaultRequests`, which `_claimPostDefaultWithdrawRequest` later pays at par via `_transferDefaultRecovery`. That function spends `defaultRecoveryReserve`, but the reserve was sized in `finalizeDefaultRecovery` to exactly cover pre-default active and pending claims at `defaultRecoveryPrice`. Post-default claims therefore draw down a fixed reserve they were never accounted for in, leaving defaulted-epoch claimants unable to recover their full entitlement.

### Finding Description
The external bug (CVE-2025-14766, V8 out-of-bounds read/write) maps to an accounting "bounds" violation: claims are paid out of a reserve outside the set of claimants the reserve was provisioned for.

In `IdleCreditVault.finalizeDefaultRecovery`, the reserve is computed as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` only includes active CDO holdings plus `defaultPendingClaimBasis()` (pendingWithdraws + current-epoch instant claims). Post-default requests are not part of `totalBasis`. [1](#0-0) 

After finalization, `requestWithdraw` takes the `defaultRecoveryFinalized` branch: it burns `_amount` strategy tokens from the CDO, mints the same amount to the user as a receipt, and sets `postDefaultRequests[_user] = _amount`. No underlying is transferred into the strategy to back this new claim. [2](#0-1) 

`claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest`, which pays `amount` 1:1 through `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve`. [3](#0-2) [4](#0-3) 

Because the reserve equals exactly `recoveryPrice * totalBasis` (possibly with dust), any post-default claim paid at 1:1 reduces the reserve below what is owed to defaulted-epoch and instant claimants at `defaultRecoveryPrice`. The first post-default requester to claim extracts value that belongs to pre-default receipt holders.

### Impact Explanation
Broken invariant: one receipt one payout / recovery isolation. A post-default user (any tranche-token holder or KYC-passing lender who can still call the CDO's requestWithdraw path) receives full par payment funded by the recovery pool, directly shrinking the funds available to users whose claims were basis for `defaultRecoveryPrice`. Loss is bounded by the post-default amount claimed, and realized as defaulted claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` reverting or being underpaid once the reserve is exhausted — direct theft of recovery proceeds from honest claimants.

### Likelihood Explanation
Requires a vault to be in the `defaultRecoveryFinalized` state with a non-zero `defaultRecoveryReserve` and some defaulted-epoch claims not yet redeemed — a normal state between finalization and the (potentially long) claims window. The attacker only needs to be able to call the CDO's withdraw-request path post-default; `_transferDefaultRecovery` has no check that the payer basis was included in `totalBasis`. No privileged cooperation is needed.

### Recommendation
Fund post-default requests independently of `defaultRecoveryReserve`: either (a) require the CDO to pull repayment from the borrower and top up the reserve for each post-default request before it becomes claimable, or (b) track post-default claims in a separate accounting bucket paid only from funds collected after finalization, so `_claimPostDefaultWithdrawRequest` never decrements `defaultRecoveryReserve`. Additionally, include a post-default pending bucket in any subsequent reserve computations if top-ups are intended.

### Proof of Concept
Foundry fork sketch:

```solidity
// Setup: epoch vault with user A (defaulted-epoch pending withdraw) and attacker B.
// 1. Running epoch: A calls requestWithdraw(X) via CDO; epoch stops with borrower funding,
//    then borrower defaults before A claims.
// 2. Honest flow: CDO calls strategy.finalizeDefaultRecovery(recovered, recoverySource).
//    defaultRecoveryReserve = recovered (assume recoveryPrice < 1e18, totalBasis covers
//    active NAV + A's pendingBasis).
// 3. Attacker step: B, holding tranche tokens, calls CDO.requestWithdraw(Y) after
//    defaultRecoveryFinalized. Strategy mints Y receipt to B; postDefaultRequests[B] = Y.
// 4. B calls claimWithdrawRequest -> _claimPostDefaultWithdrawRequest transfers Y
//    underlying 1:1 from the strategy, decrementing defaultRecoveryReserve by Y.
// 5. Assert: remaining reserve < totalBasis * defaultRecoveryPrice / 1e18.
//    A (and other defaulted claimants) claiming now reverts on
//    defaultRecoveryReserve underflow or receives less than
//    claimBasis * defaultRecoveryPrice / RECOVERY_FULL.
```

Caveat: I verified the reserve sizing and the two payment paths directly in `IdleCreditVault.sol`, but I could not confirm within this pass whether the CDO tops up the reserve for post-default requests elsewhere (e.g., inside `IdleCDOEpochVariant` finalize/request flows). If the CDO transfers an equivalent amount of underlying into the strategy when creating a post-default request, the reserve stays solvent and the severity drops; that path should be checked in `IdleCDOEpochVariant.sol` before finalizing this finding.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
