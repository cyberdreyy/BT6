Confirmed vulnerability: builder withdrawal amounts sent to the execution layer are not capped to the builder's actual balance, breaking the Gwei accounting equality between what the CL debits and what the EL mints.

### Title
Builder withdrawal amount uncapped when handed to execution layer, but CL debit is capped — creates Gwei out of thin air - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` (and `get_expected_withdrawals`) construct the `Withdrawal` object sent to the execution layer using the *requested* `withdrawal.amount` from `state.builder_pending_withdrawals`, without capping it to the builder's actual `balance`. The CL-side debit, performed later in `apply_withdrawals`, is capped with `min(withdrawal.amount, builder_balance)`. This mirrors the reported bug class exactly: one code path (the EL-facing "mint"/credit instruction) is not kept in lock-step with the other path (the CL-side balance accounting), letting more Gwei be created for the fee recipient than is actually deducted from the payer's on-chain balance.

### Finding Description
`state.builder_pending_withdrawals` entries are appended from `settle_builder_payment`/`process_builder_pending_payments`/`apply_parent_execution_payload`, using the `bid.value` amount that was recorded when the bid was accepted: [1](#0-0) 

When these pending withdrawals are turned into concrete `Withdrawal` objects for the execution payload, the full requested `withdrawal.amount` is used verbatim, with no comparison to the builder's current balance: [2](#0-1) 

Only later, in `apply_withdrawals`, is the CL-side balance decrement capped: [3](#0-2) 

Because `process_withdrawals` asserts `payload.withdrawals == expected.withdrawals` and then applies the (separately-capped) balance decrease, the `Withdrawal.amount` value that is committed into the execution payload — and that the execution layer is expected to credit to `fee_recipient` — can exceed `min(withdrawal.amount, builder.balance)`, i.e. exceed what was actually deducted from the builder: [4](#0-3) 

The equality that is broken: `sum(EL_credited_to_fee_recipient) == sum(CL_debited_from_builder)`. The spec's own tests explicitly document and accept the divergence at the "amount" field level ("withdrawal.amount: 5 ETH (requested amount)" vs "builders[0].balance: 0 (deduction capped)"): [5](#0-4) 

This is the same class of bug as the SwiftSource report: one side of a payment (the "on-chain ledger" side, i.e. `builders[i].balance`) is decremented by a capped/adjusted amount, while the counterparty side (the recipient credited via the execution payload `Withdrawal`) is credited the original, uncapped amount — creating Gwei that was never actually backed by a real balance decrease. A builder can reach this state legitimately (not maliciously) any time its balance is drawn down between the time a bid/pending payment is queued and the time it settles as a withdrawal (e.g., multiple pending payments/withdrawals accumulate for the same builder, or its balance is otherwise reduced), since `can_builder_cover_bid` is only checked at bid-acceptance time, not re-verified at withdrawal-application time.

### Impact Explanation
This falls under Critical: "Gwei created ... or paid to a non-owner." The execution layer is instructed (via the committed `Withdrawal.amount` in the payload) to credit `fee_recipient` more Gwei than was actually removed from the builder's consensus-layer balance, inflating the total supply outside of the deposit/reward accounting rules, purely through normal (non-adversarial) sequencing of pending builder payments/withdrawals.

### Likelihood Explanation
Moderate-to-high. It requires no malicious behavior — only that a builder's `builder_pending_withdrawals`/`builder_pending_payments` total committed amount, at the time it is dequeued in `get_builder_withdrawals`, exceeds the builder's then-current `balance`. This can occur naturally whenever multiple payments accrue for a builder faster than balance is topped up, since `can_builder_cover_bid` is a point-in-time check at bid acceptance and is never re-validated at settlement/withdrawal time.

### Recommendation
Cap the withdrawal amount at the point the `Withdrawal` object is constructed in `get_builder_withdrawals` (and any other builder-withdrawal-producing function), using `min(withdrawal.amount, state.builders[builder_index].balance)`, consistent with how `apply_withdrawals` performs the balance decrement — analogous to the SwiftSource fix of aligning the value actually transferred with the value the downstream contract/EL is told to expect.

### Proof of Concept
1. Builder `B` has `balance = 1 ETH`.
2. Two builder payments settle into `state.builder_pending_withdrawals` for `B`, each requesting `amount = 5 ETH` (e.g., via `settle_builder_payment` being invoked twice across epoch boundaries before either is applied, as shown to be possible in `apply_parent_execution_payload`/`process_builder_pending_payments`).
3. `process_withdrawals` calls `get_builder_withdrawals`, which emits two `Withdrawal` entries each with `amount = 5_000_000_000 Gwei` (uncapped) into `payload_expected_withdrawals`, which becomes part of the committed execution payload instructing the EL to credit `fee_recipient` `10 ETH` total.
4. `apply_withdrawals` then runs: first withdrawal caps deduction to `min(5 ETH, 1 ETH) = 1 ETH` (builder balance → 0); second withdrawal caps deduction to `min(5 ETH, 0) = 0 ETH` (builder balance stays 0).
5. Net result: CL debited only `1 ETH` from the builder, but the execution payload commits to crediting `fee_recipient` `10 ETH` — an 9 ETH discrepancy of Gwei created without a corresponding debit, directly demonstrated by the existing spec test `test_builder_withdrawal_insufficient_balance` pattern (single-withdrawal case) generalized to the multi-withdrawal case. [5](#0-4)

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```
