### Title
Unbound `savedCallbacks` map keyed only by attacker-controlled `MessageId` allows request hijack via overwrite - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each callback in `h.savedCallbacks[msg.Body.MessageId]` without checking whether an entry already exists for that ID, and `MessageId` is a fully attacker-chosen, unsigned-binding string with no ownership/sender check tying it to the callback. An attacker who submits a request with the same `MessageId` as a victim's in-flight request overwrites the victim's callback with their own before the DON responds, causing the DON's response to be delivered to the attacker instead of the victim.

### Finding Description
`MessageId` is fully attacker-controlled: `MessageBody.MessageId` is just an arbitrary string bounded only by length checks in `Message.Validate()` [1](#0-0) , and it is not derived from or bound to the sender identity in the callback map key. In `HandleLegacyUserMessage`, the handler writes directly into the shared map with no existence check: [2](#0-1) 

Compare this to the vault handler's `newActiveRequest`, which explicitly rejects a request whose ID is already active: [3](#0-2) 

Because `HandleLegacyUserMessage` performs an unconditional map write (`h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}`), a second request using the same `MessageId` while the first is still pending silently replaces the map entry: the victim's `savedCallback` object is dropped (only the map pointer moves, not deleted/notified), and any subsequent `HandleNodeMessage`/`handleWebAPITriggerMessage` response for that ID is delivered to the *new* (attacker's) callback via `savedCb.SendResponse(...)`. This is confirmed by the response-delivery path, which looks the ID up in the same map and sends to whatever callback is currently stored: [4](#0-3) 

The periodic `pruneCallbacks()` routine only removes entries based on `createdAt` age or an LRU-style eviction when the map is oversized; it has no logic to detect or prevent this overwrite race, and by design cannot — the collision happens synchronously inside `HandleLegacyUserMessage`, before any pruning cycle runs: [5](#0-4) 

There is no allowlist/authorization/uniqueness check upstream either — the TODO comment at line 384 explicitly notes allowlisting is not yet applied, and routing through `multiHandler.HandleLegacyUserMessage` simply forwards the message to the capabilities handler with no MessageId ownership enforcement [6](#0-5) . The victim's original `callback.Wait()` (in the caller of `HandleLegacyUserMessage`, per the `Handler` interface doc) never receives a response and only resolves via gateway-level timeout [7](#0-6) .

### Impact Explanation
This is a cross-user response confusion / request-hijack vulnerability: an unprivileged attacker who can send signed gateway messages (any external client credentialed to talk to the gateway, no special DON/operator privilege) can capture a DON's real response intended for another user's request, and cause the victim's original request to silently time out instead of receiving its legitimate response. This matches the "request impersonation" / "cross-user response confusion" bounty class.

### Likelihood Explanation
Exploitation requires only: (1) the ability to send a signed `HandleLegacyUserMessage`-routed request (`web_api_trigger`) to the gateway with an attacker-chosen `MessageId`, and (2) timing the attacker's request to land after the victim's request but before the DON responds. Since `MessageId` has no server-side uniqueness enforcement across senders, and the write in `HandleLegacyUserMessage` is unconditional, this is trivially and repeatably exploitable by any client capable of signing gateway messages — no elevated role is needed.

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check whether an entry already exists for `msg.Body.MessageId` (under the same `h.mu` lock) and reject the new request (e.g., respond with a conflict/duplicate error similar to the vault handler's "request ID already exists" check) rather than overwriting it. Optionally also scope the callback map key by `(Sender, MessageId)` similar to `requestcache.go`'s `globalId{sender, id}` pattern, which already implements this correctly: [8](#0-7) 

### Proof of Concept
Go test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a mock `don`.
2. Build victim message `msgV` with `Method: MethodWebAPITrigger`, `MessageId: "shared"`, signed by victim key; create `callbackV := common.NewCallback()` (or mock `handlers.Callback`).
3. Call `h.HandleLegacyUserMessage(ctx, msgV, callbackV)`; assert `h.savedCallbacks["shared"]` is set and bound to `callbackV`.
4. Build attacker message `msgA` with same `MessageId: "shared"`, different `Sender`, signed by attacker key; create `callbackA`.
5. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` — assert (current buggy behavior) that this call succeeds and **overwrites** `h.savedCallbacks["shared"]` to point at `callbackA`, and expect the fix to instead return an error (e.g., `assert.ErrorContains(t, err, "already exists")`) and leave `callbackV`'s entry intact.
6. Simulate the DON response for `"shared"` via `h.HandleNodeMessage(ctx, resp, nodeAddr)`.
7. Assert `callbackA.Wait(ctx)` receives the response (proving hijack) while `callbackV.Wait(ctx)` times out/never resolves — this demonstrates the vulnerability; after the fix, assert step 5's rejection prevents this outcome entirely.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
