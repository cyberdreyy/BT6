## Analog Found: Unbounded `getProgramAccounts` Scan Path Bypasses the Only Existing Size Guard

### Title
Permissionless unbounded account creation lets `getProgramAccounts`/`getTokenAccountsBy{Owner,Delegate}` bypass the only scan-size guard, enabling RPC node DoS - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_filtered_program_accounts` has two code paths: an indexed path that enforces `scan_results_limit_bytes`, and a non-indexed path — the default configuration — that has no size limit at all and materializes every account owned by the queried program into memory before any filtering/pagination occurs.

### Finding Description
When a validator/RPC node is run with the default configuration (no `--account-index program-id`), `get_filtered_program_accounts` takes the `else` branch: [1](#0-0) 

```rust
} else {
    // this path does not need to provide a mb limit because we only want to support secondary indexes
    let mut accounts = self
        .runtime
        .spawn_blocking(move || {
            bank.get_filtered_program_accounts(
                &program_id,
                |account: &AccountSharedData| { ... },
            )
            ...
```

This delegates straight to `bank.get_filtered_program_accounts`, which performs an unbounded `scan_accounts` over `accounts-db` (see `accounts-db/src/accounts_db.rs` `scan_accounts`), collecting every matching account into a `Vec` with no early abort and no byte-size cap. The `scan_results_limit_bytes` guard exists only in `get_filtered_indexed_accounts` (used for the `ProgramId`/`SplTokenOwner`/`SplTokenMint` secondary-index paths): [2](#0-1) 

Since account creation on Solana is fully permissionless (any signer can create arbitrarily many accounts owned by any program, e.g. the System Program, `spl-token`, or any deployed program, for near the rent-exempt minimum in lamports), an attacker can grow the set of accounts owned by a given `program_id` without bound. Any ordinary RPC user can then call `getProgramAccounts` (or `getTokenAccountsByOwner`/`getTokenAccountsByDelegate` when the corresponding secondary index is not enabled) against that `program_id`, forcing the node to scan, clone, and serialize the entire unbounded set on a blocking thread — directly analogous to the `poolRewards` array in the external report: a permissionlessly-grown, unbounded collection that is iterated in full inside a critical/frequently-invoked code path with no cap.

### Impact Explanation
This scan runs on `self.runtime.spawn_blocking`, tying up an RPC blocking-thread-pool worker and accounts-db read resources for the duration of the (attacker-controlled-size) scan. Because there is no byte/entry limit on this path, an attacker can drive memory allocation and CPU cost proportional to the number of accounts they choose to create, exhausting RPC-node blocking threads/memory and degrading or crashing the JSON-RPC service for legitimate users — an ingest/availability DoS on a core public-facing service, matching the "RPC request handling"/"RPC crash" impact category.

### Likelihood Explanation
Likelihood is high: creating many low-value/rent-exempt-minimum accounts owned by an arbitrary program is cheap and fully permissionless, and `getProgramAccounts` is publicly exposed on most RPC endpoints by default (the indexed/limited path is opt-in via `--account-index`, not default). No special privileges, timing, or races are required.

### Recommendation
Apply the same `scan_results_limit_bytes` (or an equivalent hard cap/pagination) to the non-indexed branch of `get_filtered_program_accounts` (and the analogous non-indexed branches of `get_filtered_spl_token_accounts_by_owner`/`by_mint`/`get_token_accounts_by_delegate`), rather than restricting the guard to only the secondary-index scan path, so unindexed scans cannot return unboundedly large result sets.

### Proof of Concept
1. Run/target an RPC node with default config (no `--account-index program-id`).
2. Use a funded keypair to submit many cheap System Program `CreateAccount` transactions, each creating a new rent-exempt account owned by a chosen `program_id` (or reuse a widely-populated existing program, e.g. the SPL Token program, without the `SplTokenOwner`/`SplTokenMint` index enabled).
3. Call `getProgramAccounts(program_id)` (or `getTokenAccountsByOwner`) against the node.
4. Observe the request drives `bank.get_filtered_program_accounts` to scan and buffer the entire unbounded set in memory on a blocking thread, with no `scan_results_limit_bytes` enforcement, unlike the indexed path in `get_filtered_indexed_accounts` (which does return `ScanError` once `scan_results_limit_bytes` is exceeded, per the existing test `test_get_filtered_indexed_accounts_limit_exceeded` in `runtime/src/bank/tests.rs`).

    pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
