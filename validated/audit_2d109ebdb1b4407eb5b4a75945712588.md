### Title
Documented `!pattern` exclusion syntax for `allowed_images`/`allowed_services` is not implemented, silently allowing "excluded" images - (File: common/allowed_images.go)

### Summary
GitLab Runner's documentation instructs admins to block specific images/services (e.g. Kali) using a negated glob such as `allowed_images = ["**", "!*/kali*"]`. The actual enforcement function, `VerifyAllowedImage`, only ever performs positive `doublestar.Match` checks against each configured pattern and never interprets a leading `!` as negation, so the "exclusion" entry is inert and any image matched by an earlier permissive pattern (like `**`) is still allowed.

### Finding Description
`VerifyAllowedImage` in `common/allowed_images.go` iterates `options.AllowedImages` and calls `doublestar.Match(allowedImage, options.Image)` for each pattern, returning `nil` (allowed) on the first match: [1](#0-0) 
There is no code path anywhere in this function, or in the callers (`executors/docker/docker.go`, `executors/kubernetes/kubernetes.go`), that special-cases a `!`-prefixed pattern as a negative/exclusion rule. `doublestar.Match` (the `bmatcuk/doublestar` library) is a plain positive glob matcher; it does not natively support gitignore-style negation syntax.

Given the documented configuration `allowed_images = ["**", "!*/kali*"]`:
- The loop reaches `"**"` first. `doublestar.Match("**", "my.registry.tld/team/kali")` returns `true`, so the function returns `nil` (image allowed) immediately.
- The `"!*/kali*"` entry is never evaluated as an exclusion — even if it were reached, `doublestar.Match` would treat `"!*/kali*"` as a literal pattern requiring the image string to literally start with `!`, which no real image name does, so it could never exclude anything even if pattern order were reversed.

An unprivileged pipeline author who specifies `image: my.registry.tld/team/kali:latest` (or any other image the admin believed was excluded) in `.gitlab-ci.yml` will have that image accepted and run, contradicting the runner administrator's intended restriction.

### Impact Explanation
This is a broken security control rather than an attacker gaining new capability beyond what an unrestricted `allowed_images`/`allowed_services` config already would permit — but it means the config the admin explicitly wrote to reduce the job's attack surface is silently ineffective. An unprivileged pipeline author can specify explicitly-blocklisted images/services and have them run without any warning that the exclusion failed, undermining an intended isolation/hardening control the admin relied on to keep certain (e.g. known-malicious-tool) images out of the CI environment.

### Likelihood Explanation
Trivial and fully deterministic: any runner configured per the officially documented pattern (`["**", "!*/kali*"]` or similar) is affected, and any pipeline author with access to set the `image:`/`services:` keyword in `.gitlab-ci.yml` can reproduce it by simply referencing the "excluded" image. No special privileges beyond authoring a pipeline are needed.

### Recommendation
Either implement real negation support in `VerifyAllowedImage` (e.g., pre-process `AllowedImages`/`AllowedServices` into separate allow/deny lists, checking deny patterns first and rejecting on match, or using a library/algorithm that supports `!`-prefixed exclusion semantics matching the documented behavior), or remove the negation syntax from the documentation and clearly state that only positive glob patterns are supported, so administrators do not rely on a non-functional control.

### Proof of Concept
Go unit test extending `common/allowed_images_test.go`:
```go
func TestVerifyAllowedImage_NegationNotSupported(t *testing.T) {
    logger := buildlogger.New(nil, logrus.WithFields(logrus.Fields{}), buildlogger.Options{})
    options := VerifyAllowedImageOptions{
        Image:         "my.registry.tld/team/kali",
        OptionName:    "images",
        AllowedImages: []string{"**", "!*/kali*"},
    }
    err := VerifyAllowedImage(options, logger)
    // Documented behavior implies this should be rejected (ErrDisallowedImage),
    // but current implementation allows it because "**" matches first.
    assert.NoError(t, err, "kali image was NOT excluded despite '!*/kali*' rule — negation is non-functional")
}
```
Expected result with current code: `assert.NoError` passes, proving the exclusion pattern has no effect and the image the admin intended to block is allowed to run.
