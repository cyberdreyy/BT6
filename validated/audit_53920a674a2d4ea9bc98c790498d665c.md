### Title
Malicious SPL-Token-2022 mint with an extreme interest/scaled-UI-amount config causes `serde_json` serialization failure, panicking the RPC pubsub notifier thread - (File: rpc/src/rpc_subscriptions.rs)

### Summary
An unprivileged user can create an SPL-Token-2022 mint with an `InterestBearingConfig` or `ScaledUiAmountConfig` extension configured with an extreme rate/multiplier so that `token_amount_to_ui_amount_v3` computes `ui_amount = Some(f64::INFINITY)` for a held token account. When any client subscribes to that account via `accountSubscribe` (or otherwise triggers this account/token info to be pushed through `RpcSubscriptions`), the RPC notifier thread serializes the notification with `serde_json::to_writer(...).expect("serialization never fails")` in `RpcNotifier::notify`. Because `serde_json` cannot serialize `Infinity`/`NaN` floats, this call returns `Err`, and the `.expect()` panics, crashing the dedicated notification thread.

### Finding Description
`token_amount_to_ui_amount_v3` in `account-decoder/src/parse_token.rs` (lines 125-164) computes a UI amount from a raw `u64` token amount using mint-supplied config data (`InterestBearingConfig::amount_to_ui_amount` or `ScaledUiAmountConfig::amount_to_ui_amount`) and parses the resulting string back into an `f64` via `f64::from_str`. Existing unit tests directly demonstrate that a "huge" but otherwise valid config produces `ui_amount: Some(f64::INFINITY)`: [1](#0-0) [2](#0-1) 

This `UiTokenAmount { ui_amount: Option<f64>, .. }` struct is `#[derive(Serialize)]`: [3](#0-2) 

The resulting value flows into `parse_token_v3` for any token account (`account.base.amount`) whose associated mint carries such an extension: [4](#0-3) 

When such data reaches the RPC pubsub notification path (e.g., an `accountSubscribe` for the token account with `jsonParsed` encoding, processed in `RpcSubscriptions::notify_watchers` / `check_commitment_and_notify`), it is ultimately serialized by `RpcNotifier::notify`: [5](#0-4) 

The line `serde_json::to_writer(Cursor::new(&mut *buf), &notification).expect("serialization never fails")` assumes JSON serialization can never fail. This assumption is false for `f64::INFINITY`/`NaN` values — `serde_json` returns an error rather than emitting invalid JSON for such floats. Once that branch is hit, the `.expect()` panics.

### Impact Explanation
The panic occurs inside the dedicated `RpcNotifier`/pubsub notification processing thread (`process_notifications`), which is a single background thread shared by all subscribers. A panic there terminates that thread; depending on the panic-hook/process configuration used by the validator, an unhandled panic in a spawned thread can abort the whole validator process (Rust's default behavior for `panic = "abort"` builds, and even under "unwind" builds, the thread's abrupt death disables all subscription/notification services validator-wide). This is triggered purely by an unprivileged user creating a token mint and account and subscribing to it — no special validator/operator privilege is required. This matches the "concrete validator-process crash ... from one request" acceptance criterion.

### Likelihood Explanation
Creating an SPL-Token-2022 mint with `InterestBearingConfig`/`ScaledUiAmountConfig` and setting extreme rate/multiplier and timestamp values is fully permissioned to any user (mint authority of their own mint) and requires no special validator access. Subscribing to the resulting account via the public `accountSubscribe`/`programSubscribe` JSON-RPC pubsub API, or querying via `jsonParsed` encoding paths that reuse `token_amount_to_ui_amount_v3`, is a standard unprivileged RPC operation. The unit tests already prove the exact `f64::INFINITY` value is reachable with realistic-looking config values, so likelihood of reachability is high; the main uncertainty is confirming that a "jsonParsed" get/subscribe path is invoked with pubsub (rather than only synchronous getAccountInfo, whose error handling may differ) — this specific pubsub trigger path was not fully traced end-to-end within the available context and would benefit from live/dynamic verification.

### Recommendation
Replace `.expect("serialization never fails")` in `RpcNotifier::notify` (and any similarly unguarded `serde_json` serialization along the parsed-token JSON encoding paths) with fallible error handling that drops/logs the malformed notification instead of panicking. Additionally, clamp or reject non-finite `ui_amount` values in `token_amount_to_ui_amount_v3` (e.g., convert `Infinity`/`NaN` results to `None` before constructing `UiTokenAmount`), since a non-finite UI amount is not meaningful to API consumers regardless of the serialization concern.

### Proof of Concept
1. Create an SPL-Token-2022 mint with the `InterestBearingConfig` extension, setting `current_rate`/`pre_update_average_rate` to `32767` (max) and a large elapsed time (as in the existing unit test), or the `ScaledUiAmountConfig` extension with `new_multiplier` set to a value that causes overflow to infinity.
2. Create/mint a token account for that mint with a large `amount` (e.g., `u64::MAX`), reproducing the exact scenario validated by the existing test `test_ui_token_amount_with_interest`/`test_ui_token_amount_with_multiplier`, which asserts `ui_amount == Some(f64::INFINITY)`. [6](#0-5) 
3. Send an `accountSubscribe` request for that token account with `"encoding": "jsonParsed"` via the JSON-RPC pubsub WebSocket.
4. When the account is next included in a notification batch, `RpcNotifier::notify` attempts `serde_json::to_writer` on the notification payload containing `ui_amount: Infinity`, which fails and triggers the `.expect()` panic, crashing the notification thread/validator process.
