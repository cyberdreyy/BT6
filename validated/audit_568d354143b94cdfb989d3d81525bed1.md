### Title
Unbounded per-request cost in `get_signatures_for_address` via large single-slot `tx_by_addr` row fetch/decode independent of `limit` - ([File: storage-bigtable/src/lib.rs])

### Summary
`LedgerStorage::get_confirmed_signatures_for_address` fully fetches and deserializes the entire `tx_by_addr` BigTable row for the slot referenced by `before_signature` merely to compute its entry count (`starting_slot_tx_len`), before ever applying the caller-supplied `limit`. If an attacker previously packed many self-transactions for one address into a single slot, this row can contain an attacker-controlled, effectively unbounded number of entries, so a single `getSignaturesForAddress` call with `before=<sig-in-that-slot>` and `limit=1` forces CPU/memory cost proportional to the row size rather than to `limit`.

### Finding Description
`JsonRpcRequestProcessor::get_signatures_for_address` (`rpc/src/rpc.rs:1847`) calls into blockstore/bigtable to resolve signatures for an address, and when the request needs bigtable-backed history it reaches `LedgerStorage::get_confirmed_signatures_for_address` (`storage-bigtable/src/lib.rs:914`).

Inside that function:
- `first_slot` is resolved from `before_signature` via a `TX_TABLE_NAME` lookup (`storage-bigtable/src/lib.rs:931-945`).
- The code then fetches the **entire** `tx_by_addr` cell for `first_slot` and fully deserializes it (`Vec<LegacyTransactionByAddrInfo>` or protobuf `TransactionByAddr`) purely to compute its length, `starting_slot_tx_len` (`storage-bigtable/src/lib.rs:967-979`).
- This length is then added to the caller's `limit` to bound the *row count* (not entry count) of a follow-up `get_row_data` call (`storage-bigtable/src/lib.rs:984-999`).

The problem is that step of computing `starting_slot_tx_len` requires fetching and fully decoding the entire cell for `first_slot`, with cost `O(N)` where `N` is the number of `TransactionByAddrInfo` entries written into that slot's row for the target address — this happens *before* the `limit` truncation logic (`storage-bigtable/src/lib.rs:1030-1054`) is ever applied. An attacker who submits many self-transactions from a single address such that they land in one slot (an on-chain data-writing action, not requiring validator/leader control) can make `N` arbitrarily large. Any subsequent `getSignaturesForAddress` RPC call using `before=<signature from that slot>` — even with `limit=1` — forces the storage layer to fetch/deserialize that entire oversized row, so the request's CPU/memory cost scales with attacker-controlled on-chain history size, not with the requested `limit`.

No existing guard mitigates this: the RPC-level `limit` parameter is only applied after the full row has already been fetched and deserialized, and there is no cap on the size of a single `tx_by_addr` row or a byte-size limit on the initial length-probe read.

### Impact Explanation
This falls under "unbounded cost for a single low-rate call" — the RPC's protection (a small `limit` argument) does not bound the actual work performed by `LedgerStorage`, since the length-probe read of the `first_slot` row is unconditional and independent of `limit`. A single `getSignaturesForAddress` call from an unprivileged client can force the validator's bigtable-storage code path to allocate and CPU-process memory proportional to attacker-supplied on-chain transaction volume in one slot, rather than the small number of signatures requested.

### Likelihood Explanation
Feasible with only unprivileged actions: attacker submits many self-transactions from a single address, aiming for as many as possible to land in a single slot (bounded only by block compute/size limits, not by any address-specific limit), then issues one `getSignaturesForAddress(before=<sig from that slot>, limit=1)` call. This requires `bigtable_ledger_storage` to be enabled (explicitly stated precondition) and is fully repeatable — the attacker can re-trigger the expensive read on demand at the allowed call rate.

### Recommendation
Avoid a full-row fetch/decode purely to compute `starting_slot_tx_len`. Options: (1) store or track per-row entry counts out-of-band (e.g., in a separate lightweight index) so the length can be obtained without deserializing the entire row; (2) cap the number of entries read/deserialized from a single `tx_by_addr` cell to a fixed maximum, returning a paginated/partial result or error when a row exceeds that bound; (3) restructure the address-index write path to shard entries so no single row/slot can accumulate unbounded entries for one address.

### Proof of Concept
Integration test (bigtable emulator or mocked `BigTableConnection`):
1. Populate `TX_BY_ADDR_TABLE_NAME` with a single row keyed `"{address}/{slot_to_tx_by_addr_key(SLOT)}"` containing a `TransactionByAddr` protobuf with `N = 100_000` `TransactionByAddrInfo` entries for `address`.
2. Populate `TX_TABLE_NAME` so that one signature (`sig_in_slot`) resolves to `{slot: SLOT, index: 0}`.
3. Call `LedgerStorage::get_confirmed_signatures_for_address(address, Some(&sig_in_slot), None, 1)`.
4. Instrument/measure bytes read and deserialization time for the length-probe cell fetch (`storage-bigtable/src/lib.rs:967-979`); assert that fetched/decoded byte count and processing time grow linearly with `N` even though `limit == 1`.
5. Repeat with `N = 1_000_000` and assert the cost scales linearly, demonstrating the request cost is bounded by on-chain row size, not by `limit`.
