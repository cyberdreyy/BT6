It is used directly as the key into `handler.savedCallbacks` in `HandleLegacyUserMessage`.### Title
Caller-controlled, non-sender-scoped `MessageId` in `handler.HandleLegacyUserMessage` allows cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.NewHandler` (in `core/services/gateway/handlers/capabilities/handler.go`) creates a `handler` whose `savedCallbacks` map is keyed solely by the client-supplied `msg.Body.MessageId`, with no binding to the sender's address. Any signed request from an arbitrary EOA can reuse another in-flight requester's `MessageId`, silently overwriting the victim's saved callback so that the eventual DON response is delivered to the attacker instead of the original requester.

### Finding Description
The public entrypoint `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) decodes the JSON-RPC request and, for legacy requests, only validates the message via `msg.Validate()` (`core/services/gateway/api/message.go:54-88`) — which checks signature format/length, ID length/null-suffix, method/DonId length — and enforces `len(jsonRequest.ID) > 200` as the only additional constraint. `Validate()` never associates `MessageId` uniqueness with `Sender`; it only assigns `m.Body.Sender` from the ECDSA-recovered signer.

This validated message is handed to `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`), which stores the callback keyed purely by the caller-controlled ID: [1](#0-0) 

Because `h.savedCallbacks` is a plain `map[string]*savedCallback` (declared in the `handler` struct) with no per-sender namespace, a second request bearing the same `MessageId` — signed by any different EOA and satisfying `Validate()` — overwrites the entry: the map assignment is a last-writer-wins operation, with no existence check or ownership check performed beforehand.

Later, when a DON node responds (`h.don.SendToNode` triggers processing that eventually reaches `handleWebAPITriggerMessage`), the lookup is again purely by ID: [2](#0-1) 

If the attacker's overwrite occurred after the victim's request was already dispatched to DON nodes but before the DON's response for that ID arrived, the response — encoded via `codec.EncodeLegacyResponse(msg)` — is delivered to the attacker's callback (`savedCb.SendResponse`) rather than the victim's, since `savedCb` now points to the attacker's `handlers.Callback`.

No component in this path re-validates that the responding callback belongs to the same sender that originally issued the request with that ID; `HandleNodeMessage` (`core/services/gateway/handlers/capabilities/handler.go:248-267`) only checks `msg.Body.Sender != nodeAddr` (i.e., that the *node* signature matches, not that the *original user* matches), so the sender-mismatch check is orthogonal to this issue.

### Impact Explanation
This is a cross-user response confusion / request-hijacking primitive: an unprivileged attacker holding any EOA can cause a victim's expected trigger response (and, in the general `capabilities` handler flow, any node-relayed payload for the colliding ID, including `MethodWebAPITarget`/`MethodComputeAction`/`MethodWorkflowSyncer` outgoing-request responses) to be redirected to the attacker instead of the legitimate caller. Depending on what data the DON returns for a given workflow/trigger invocation, this could disclose response payload data intended for another user to the attacker. I could not confirm within this codebase that vault/DKG secret material specifically flows through this exact `capabilities` handler's `savedCallbacks` path (the `Response`/`webapicap.TriggerRequestPayload` types handled here are HTTP outbound request results and trigger acknowledgements, not vault secret shares), so the "Critical — vault/DKG secret disclosure" impact stated in the question is not directly substantiated by this file; the concretely demonstrable impact is unauthorized redirection of another user's gateway response (integrity/confidentiality of that response), matching a "request impersonation / cross-user response confusion" class.

### Likelihood Explanation
Exploitability requires: (1) knowledge of the victim's exact `MessageId` (up to 128 bytes, no forced randomness/entropy requirement is enforced by the gateway) and (2) a race window between the victim's request being forwarded to DON nodes and the DON's response arriving back at the gateway. If client-side ID generation is predictable, short, or attacker-influenced (e.g., sequential, timestamp-based, or client-chosen for idempotency), the precondition is trivial to satisfy; if IDs are high-entropy UUIDs generated client-side and never disclosed to third parties, exploitation requires guessing or otherwise learning the victim's ID, which is a real but non-trivial precondition. No operator/admin/DON privilege is needed — only the ability to sign and submit a gateway JSON-RPC request, which is available to any EOA holder. The bug is deterministic and repeatable once ID collision and timing are achieved (Go map writes overwrite unconditionally).

### Recommendation
Scope `savedCallbacks` keys to `(Sender, MessageId)` tuples instead of `MessageId` alone, or generate/verify request IDs server-side per sender. Reject `HandleLegacyUserMessage` calls where `msg.Body.MessageId` already exists in `savedCallbacks` under a different sender (return a conflict error) rather than silently overwriting. Additionally, verify on the response path that the responding DON message correlates to the same sender who originally issued the request with that ID.
