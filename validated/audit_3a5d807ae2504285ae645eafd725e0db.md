## Analysis Result

I identified a valid analog. It maps to the same bug class as the external report: a value is authorized/counted based on a **stale trust relationship** that was never invalidated when the underlying grantee lost its status, letting execution proceed on data that no longer reflects reality (there: an old BOC's allow-all flag was never revoked even though the paymaster still trusted it; here: a departed multisig member's confirmation is never revoked from requests it did not originate, even though the member is deleted).

### Title
Multisig `delete_member` Leaves Stale Confirmations From Removed Members On Other Pending Requests, Allowing Sub-Threshold Execution - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` decides whether to execute a request purely by comparing the size of the stored `confirmations` set to `num_confirmations` [1](#0-0) . `delete_member` only purges confirmations for requests that the removed member itself *originated* (`r.member == member`), not confirmations that member previously *added* to requests originated by other members [2](#0-1) . Consequently a request can be executed with confirmations counted from members who are no longer part of the multisig, breaking the binding `confirmations counted == confirmations by live members`.

### Finding Description
`add_request` stores a request keyed by an empty confirmation set, and any current member can add its identity into `confirmations[request_id]` via `confirm` [3](#0-2) . `confirm` only checks that the *calling* account is a current member (`assert_valid_request` → `current_member`), then compares the size of the previously accumulated `confirmations` set to `num_confirmations`, and if reached, executes the request [1](#0-0) [4](#0-3) . It never re-validates that the *previously stored* confirmations still belong to current members.

`delete_member` (executed via `DeleteMember` action, itself requiring quorum) removes stale requests and confirmations **only for requests originated by the removed member** (`filter_map(|(k, r)| if r.member == member ...)`) [5](#0-4) . If the removed member had confirmed (but not originated) a *different*, still-pending request, that confirmation entry is never cleaned from `confirmations[other_request_id]`. The removed member's access key is deleted from the account, and `num_requests_pk` for that member is cleared, but the string identity persists inside the `HashSet<String>` for other requests.

### Impact Explanation
This is a Critical-class custody-boundary break per the rules: "a multisig request executed below threshold." The multisig can be made to execute an authorization-gated action (transfer, `AddKey`/full-access-key grant, `DeployContract` upgrade, arbitrary `FunctionCall`) with fewer than `num_confirmations` *live* signers, because one of the counted confirmations comes from a member that has already been removed from the multisig by the time the request executes. This directly undermines the multisig's core guarantee that N distinct current members must approve any action.

### Likelihood Explanation
Exploitation requires ordinary, unprivileged multisig workflow, not any external attacker key: any member can (1) create/confirm a request `A` (e.g., a `Transfer`), (2) separately participate in removing themselves or another confirming member via a `DeleteMember` request on `B`, while `A` is still pending, and (3) get the remaining, now-insufficient set of live members to add one more confirmation to reach the raw counter threshold on `A`, causing execution even though fewer than `num_confirmations` current members actually approved. No code redeploy, foundation action, or malicious validator is required — only the documented `add_request`/`confirm`/`DeleteMember` API surface, matching the "confirmations counted versus live members" analog category explicitly called out in scope.

### Recommendation
When executing `delete_member`, iterate over **all** active requests' confirmation sets (not just requests originated by the removed member) and strip the removed member's entry from each. Alternatively, change `confirm`'s threshold check to only count confirmations whose corresponding member is still present in `self.members` at confirmation time, rather than trusting the raw stored set size.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [M1, M2, M3, M4], num_confirmations = 3)`.
2. M1 calls `add_request_and_confirm(request_A = Transfer{...})` → confirmations(A) = {M1}.
3. M2 calls `confirm(request_A)` → confirmations(A) = {M1, M2} (2/3, not yet executed).
4. Separately, M1, M2, M3 confirm a `DeleteMember{member: M2}` request (`request_B`) reaching threshold 3, which executes: M2's access key is deleted, `members` = {M1, M3, M4}. Because `r.member == M2` only matches requests M2 originated, `request_A` (originated by M1) is untouched — confirmations(A) still contains `M2`, a now-removed member.
5. M3 (now one of only 3 live members) calls `confirm(request_A)` → confirmations(A).len() + 1 = 3 ≥ `num_confirmations` (3) → `execute_request` runs the Transfer, even though only M1 and M3 are actually current, live approving members (2 live confirmations, not 3).

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
