### Title
Stale cross-epoch instant-withdraw receipts are excluded from `defaultPendingClaimBasis`, inflating the default recovery price and permanently freezing older claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks instant-withdraw receipt basis per request epoch (`instantWithdrawClaimsByEpoch`), but `pendingInstantWithdraws` is an aggregate across all epochs. When a default is finalized, `defaultPendingClaimBasis()` only adds the *current* epoch's instant basis, while the aggregate `pendingInstantWithdraws` may include unfunded receipts from earlier epochs. This mirrors the CVE-2024-56737 bug class — attacker-influenced out-of-scope data corrupting a fixed-size accounting structure — here a stale epoch boundary corrupts the recovery denominator, overpaying default-epoch claimants from `defaultRecoveryReserve` and permanently freezing pre-default instant receipts.

### Finding Description
`requestInstantWithdraw` records basis under `instantWithdrawsRequestsByEpoch[user][epochNumber]` and bumps `instantWithdrawClaimsByEpoch[epochNumber]`, while `pendingInstantWithdraws` accumulates globally (`IdleCreditVault.sol:366-374`). If the borrower does not fund an instant receipt, it survives into the next epoch because `epochNumber` is incremented inside `deposit()` when the epoch stops (`IdleCreditVault.sol:607-611`).

On default finalization, `finalizeDefaultRecovery` computes:

```
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];   // current epoch ONLY
}
recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis;
```
(`IdleCreditVault.sol:644-649`, `685-692`)

Instant receipts requested in any earlier epoch are part of `pendingInstantWithdraws` (the "unfunded remainder" per `_defaultPrefundedInstantReserve`, `IdleCreditVault.sol:716-723`) but are silently dropped from `totalBasis`. Consequences:

1. `recoveryPrice` is computed over too small a denominator → every default-epoch claimant (normal and instant) is paid more than their fair pro-rata share via `_transferDefaultRecovery` (`IdleCreditVault.sol:782-783`, `855`).
2. The older claimant's `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch] == 0` (`IdleCreditVault.sol:844`), so nothing is cleared at the recovery price. Their remaining `instantWithdrawsRequests[user]` then falls through to `_transferFundedClaim`, which explicitly forbids spending `defaultRecoveryReserve` (`IdleCreditVault.sol:899-905`). Since all post-default balance is reserve, their claim reverts forever — permanent freezing of a funded/claimable receipt.

### Impact Explanation
Direct theft plus permanent freezing. Example: victim has an unfunded instant receipt of 50 from epoch N-1; attacker requests instant withdraw of 100 in epoch N (the default epoch). Recovered funds = 75. Computed `totalBasis = 100`, `recoveryPrice = 75%`: attacker claims 75 and drains the reserve; the victim's fair share (25 at a correct basis of 150 / price 50%) is permanently unclaimable because `_transferFundedClaim` reverts once `balance == reserve`. In general, every defaulted-epoch claimant extracts up to `oldInstantBasis * recovered / (basis + oldInstantBasis)` extra from the reserve, and all pre-default instant receipt holders lose their entire recovery claim.

### Likelihood Explanation
Medium. Requires (a) an instant-withdraw request left unfunded across an epoch boundary — normal whenever borrower liquidity lags `getInstantWithdrawFunds` — and (b) a subsequent borrower default with partial recovery, an ordinary credit event this recovery machinery exists for. The attacker needs only to hold tranche tokens and request a normal/instant withdraw in the default epoch — an unprivileged KYC'd lender action. No guard prevents it: `_ensureDefaultRecoveryInitialized` only checks `pendingInstantWithdraws != 0` before lazily enabling accounting, and does not normalize per-epoch instant basis. The reserve-isolation guard in `_transferFundedClaim` makes the freeze deterministic rather than preventing the mispricing.

### Recommendation
Make the default claim basis aggregate-aware: either track `instantWithdrawClaimsByEpoch` cumulatively (add all outstanding instant basis regardless of `epochNumber`, e.g. a `totalInstantWithdrawClaims` counter), or iterate/aggregate all non-zero epochs. Additionally, allow pre-default instant receipts to be claimed at `defaultRecoveryPrice` from `defaultRecoveryReserve` (clear them in `_claimDefaultedInstantWithdrawRequest` by falling back to `instantWithdrawsRequests[user]` when the per-epoch entry is zero but `pendingInstantWithdraws` included them). Add an invariant test: `sum(instant claims) == defaultRecoveryReserve consumed` after finalization.

### Proof of Concept
Foundry fork sketch (against the credit vault + `IdleCDOEpochVariant` deployment used in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantReceiptStealsRecovery() public {
    // epoch N-1: victim deposits AA, requests instant withdraw 50e18, borrower does NOT fund it
    _depositAA(victim, 50e18);
    _requestInstantWithdraw(victim, 50e18);      // pendingInstantWithdraws = 50e18, basis epoch N-1

    // honest manager stops/starts epoch -> strategy.deposit() bumps epochNumber
    _stopAndStartEpoch();                        // epochNumber now N

    // epoch N: attacker deposits and requests instant withdraw 100e18, also unfunded
    _depositAA(attacker, 100e18);
    _requestInstantWithdraw(attacker, 100e18);   // pendingInstantWithdraws = 150e18,
                                                 // instantWithdrawClaimsByEpoch[N] = 100e18 only

    // honest owner/borrower: borrower defaults, recovery of 75e18 supplied
    _triggerBorrowerDefault();
    vm.prank(owner);
    idleCDO.finalizeDefaultRecovery(75e18, recoverySource); // totalBasis=100e18, price=75%

    // attacker claims 75e18 (fair would be 50e18 at basis 150e18)
    vm.prank(attacker);
    idleCDO.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker), 75e18);

    // victim's pre-default receipt: no epoch-N basis, and reserve guard blocks par claim
    vm.prank(victim);
    vm.expectRevert(NotAllowed.selector);        // or pays 0 -> permanently frozen
    idleCDO.claimInstantWithdrawRequest();
}
```

Note: the exact CDO entry points (`requestInstantWithdraw` on `IdleCDOEpochVariant`, `finalizeDefault`/`finalizeDefaultRecovery` sequencing) should be wired per `test/foundry/IdleCreditVault.t.sol` helpers; the strategy-side accounting mismatch at `IdleCreditVault.sol:644-649` and `899-905` is verified directly in the source above.
