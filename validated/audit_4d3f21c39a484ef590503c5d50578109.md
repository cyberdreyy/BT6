### Title
No vulnerability found - claimed cross-phase proof accounting gap is not a real invariant violation - ([File: chain/chain/src/runtime/trie_update_wrapper.rs])

### Summary
`TrieUpdateWitnessSizeWrapper`'s per-instance `read_keys`/`is_first_read` bookkeeping at [1](#0-0)  is intentionally scoped only to a single `prepare_transactions` invocation, and it is not meant to, nor required to, share state with the completely separate proof accounting done during actual receipt application. These are two independently-enforced soft/hard limits with their own authoritative checks, so there is no "totality" invariant spanning both phases that could be violated.

### Finding Description
`prepare_transactions_extra` creates a fresh `TrieUpdateWitnessSizeWrapper` per invocation over the current `TrieUpdate` and uses `state_update.recorded_storage_size()` purely to enforce `new_transactions_validation_state_size_soft_limit`, which bounds only the storage proof generated *while validating and admitting new transactions* into the chunk, as documented in [2](#0-1)  and [3](#0-2) . This wrapper's job is only to stop admission of new transactions once transaction-validation-generated proof crosses its own limit — it has never claimed to account for what promise-chain receipts will read at apply time.

Separately, actual receipt execution (including cross-receipt promise chains via `input_data_ids`) is metered against entirely different, independently-enforced limits: `main_storage_proof_size_soft_limit` for the whole chunk (checked via the real `Trie`'s own recorder in `recording_reads_with_proof_size_limit`, e.g. `apply_chunk` at [4](#0-3) ) and `per_receipt_storage_proof_size_limit` per individual receipt, enforced live during action execution at [5](#0-4) . These apply-time checks use the real `TrieRecorder` (`core/store/src/trie/trie_recording.rs`) which independently records every trie node actually touched during apply, regardless of what the (separate, already-discarded) `TrieUpdateWitnessSizeWrapper` instance from `prepare_transactions` counted earlier. There is no code path where the apply-time trie recorder consults or is under-credited by the prepare_transactions wrapper's `read_keys` set — they are different objects, different `TrieRecorder`/estimation mechanisms, and different `TrieUpdate`/`Trie` instances layered on the block's actual state root at apply time.

The premise that a "later transaction" admitted at `prepare_transactions` time under-counts proof size because "earlier promise-chain receipts already touched those trie nodes at apply time" misunderstands causality: `prepare_transactions` runs on the *previous* block's state to decide which new transactions to include in the *upcoming* chunk; it does not, and cannot, know what receipts will later read during that chunk's application, nor does its soft limit purport to bound the eventual chunk's total apply-time proof size — that is `main_storage_proof_size_soft_limit`'s job, enforced independently and correctly at apply time via the real trie recorder shared across all receipts processed in that chunk (see `process_receipt_with_metrics` at [6](#0-5)  and the chunk-wide check in `process_receipts` at [7](#0-6) ). The `TrieUpdateWitnessSizeWrapper`'s in-code documentation and test suite (`trie_update_wrapper.rs` tests) explicitly state its purpose: estimating storage proof for the transaction-admission phase, protecting against the *specific* attack of bypassing that admission-time limit via TrieUpdate-only reads (see `test_wrapper_worst_case_scenario`, [8](#0-7) ), not against under-accounting apply-time receipt execution proof across a chunk.

### Impact Explanation
None. The described "gap" is a difference between two independently-enforced, purpose-specific soft limits operating in different phases on different tries with their own trie recorders; it does not cause double-spend, theft, freezing of funds, state-root divergence, or a chain split. Total chunk witness size is bounded by the sum of all documented limits (`docs/misc/state_witness_size_limits.md`), each enforced by its own mechanism at its own phase; `new_transactions_validation_state_size_soft_limit` and `main_storage_proof_size_soft_limit` are additive, non-overlapping budgets by design, not a shared "metering totality" invariant that this wrapper is responsible for upholding across both phases.

### Likelihood Explanation
Not applicable — no exploitable condition exists. The attacker cannot cause a chunk witness to exceed the true 21MiB (approx.) design budget through this scoping choice, since apply-time proof accounting for promise-chain receipts is measured live and independently by the real trie recorder regardless of what happened during prepare_transactions for an unrelated transaction.

### Recommendation
No fix is needed for this specific claim. If reviewers want defense-in-depth, they could add a code comment near `TrieUpdateWitnessSizeWrapper` clarifying explicitly that its accounting is phase-local and not meant to interact with apply-time proof accounting, to preempt this kind of misreading, but this is documentation clarity, not a security fix.

### Proof of Concept
Not applicable; no code path exists whose behavior would differ if the two phases' proof accounting were unified, since `main_storage_proof_size_soft_limit` and `per_receipt_storage_proof_size_limit` already independently and correctly bound the apply-time promise-chain scenario, as validated by `test_main_storage_proof_size_soft_limit` [9](#0-8)  and `test_per_receipt_storage_proof_size_limit` [10](#0-9) .
