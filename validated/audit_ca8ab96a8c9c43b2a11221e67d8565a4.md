### Title
Stale rejection weight never retracted on flip-to-accept lets the mining coordinator falsely declare a validly-signed block globally rejected - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The miner-side `StackerDBListener::run` tallies `BlockAccepted`/`BlockRejected` StackerDB messages into `total_weight_approved` / `total_weight_rejected` for each block hash [1](#0-0) . The Accepted-message handler guards against being counted twice by checking `gathered_signatures.contains_key(&slot_id)`, but never checks whether that slot already contributed to `total_weight_rejected`, and never subtracts stale rejection weight when a signer later flips to Accepted for the same block hash [2](#0-1) . This asymmetry (the reverse direction — Accept-then-Reject — is correctly ignored because `Accepted` also populates `responded_signers`, so a later `Rejected`'s `responded_signers.insert` is a no-op [3](#0-2) ) lets one signer's weight be double-booked into both the approval and rejection tallies, permanently inflating `total_weight_rejected` with stale, retracted votes.

### Finding Description
`handle_block_response`-equivalent logic in the coordinator's StackerDB listener processes both message kinds per block hash:

- On `Accepted`: weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`; the slot id is then inserted into both `gathered_signatures` and `responded_signers` [2](#0-1) .
- On `Rejected`: weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., the slot was not already in `responded_signers`) [3](#0-2) .

Because `responded_signers` is populated by *both* handlers, a signer who Accepts first and later sends a stale/duplicate Reject is correctly ignored on the second message (the equality "one weight contribution per signer per block" holds in that direction). But the reverse order is not protected: a signer who first Rejects (weight counted in `total_weight_rejected`, slot added to `responded_signers`) and later legitimately re-evaluates the *same* block (same `signer_signature_hash`) and sends `Accepted`, passes the `!gathered_signatures.contains_key(&slot_id)` check (that map was never touched by the Reject path) and gets counted a second time in `total_weight_approved` — with no corresponding removal from `total_weight_rejected`.

This re-evaluation path is not hypothetical: the signer's own local state machine explicitly allows `LocallyRejected --> LocallyAccepted` transitions on re-evaluation of an identical block proposal (`BlockInfo::check_state`, `move_to`) [4](#0-3) , and the documented flow shows that a re-proposed, hash-identical block can be re-evaluated when its previous reject reason is deemed re-evaluable (`should_reevaluate_reject_reason`), or resubmitted after a validation timeout and re-validated successfully thereafter [5](#0-4) . The mining side's own retry loop is designed around exactly this scenario — it deliberately re-sends the identical proposal and expects rejection counts/timeouts to evolve as signer opinions change [6](#0-5) .

Once one signer's weight sits permanently in `total_weight_rejected` despite having since accepted, the coordinator's decision loop evaluates the rejection branch *before* the acceptance branch on every poll:

```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... })
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(...)
}
``` [7](#0-6) 

Because the stale rejection weight is never retracted, `total_weight_rejected` can reach the blocking-minority threshold (`> total_weight - weight_threshold`) purely from votes that are no longer current, even while `total_weight_approved` has genuinely crossed the 70% signing threshold from the *current* set of signer opinions. The rejection branch fires first and the miner treats the block as globally rejected (`SignersRejected`), discarding transactions and forcing a fresh proposal, even though a real, verifiable ≥70%-weight signature set for that exact block may already exist or be about to exist.

This breaks the equality the protocol depends on for liveness: "aggregated node-side weight tallies must reflect the current, not historical, set of signer verdicts for a given block hash." The coordinator instead acts on a stale/threshold-poisoned tally.

### Impact Explanation
This is a High-severity liveness wedge on the node/coordinator side: a single signer (no majority required) that transiently rejects a block for a recoverable reason (timeout, connectivity issue, stale sortition view) and then correctly flips to Accepted on re-evaluation of the identical proposal permanently and irreversibly inflates that block hash's rejection tally in the coordinator. This can cause the mining node to declare a legitimately, sufficiently-signed block as globally rejected (`SignersRejected`), forcing transaction exclusion and repeated re-proposals — i.e., the coordinator is "acting on a stale... threshold," matching the High-impact criterion in the rules. It requires only one signer's honest state transition (a normal occurrence under network jitter/timeouts) and no cooperation from a majority, no access to keys, and no auth token.

### Likelihood Explanation
Rejection-then-late-acceptance for the identical block hash is an expected, designed-for occurrence in this codebase: the coordinator itself resends the same proposal on rejection-weight growth or timeout [8](#0-7) , and the signer's local reject-reason re-evaluation logic exists precisely to let a signer change its verdict on a resent identical proposal [9](#0-8) . Under ordinary network conditions (validation timeouts, transient connectivity issues, momentarily stale sortition views) this flip can occur without any adversarial intent, making the double-count reachable with normal operation, let alone by a signer or relay deliberately timing its messages.

### Recommendation
Track a single canonical verdict per `(block_hash, slot_id)` instead of two independently-additive counters. When an `Accepted` message arrives for a slot that is already present in `total_weight_rejected`'s contributing set, subtract that signer's weight from `total_weight_rejected` before adding it to `total_weight_approved` (and symmetrically for a genuine Reject following a prior Accept, though that direction is already guarded). Concretely, maintain a `HashMap<u32, BlockResponseKind>` (or reuse `gathered_signatures`/rejection-set membership) as the single source of truth per slot, and recompute `total_weight_approved`/`total_weight_rejected` from that map rather than incrementing two independent counters that never decrease.

### Proof of Concept
1. Configure a reward set with signers `A` (weight w_A) and enough other signers so that `total_weight_approved` needs `A`'s weight to cross the 70% threshold, while `A`'s weight alone is enough (combined with any other already-rejecting signer) to reach the `>30%` blocking-minority threshold.
2. Miner proposes block `B` (hash `H`).
3. `A` initially rejects `B` with a re-evaluable reason (e.g. its local node is momentarily unreachable, or validation times out) → `StackerDBListener` records `total_weight_rejected += w_A`, `responded_signers += {A}` [10](#0-9) .
4. The miner's retry loop re-sends the identical proposal `B` (same hash `H`) after the rejection-based timeout [8](#0-7) .
5. `A` re-evaluates the identical block (`should_reevaluate_reject_reason` allows it for the recoverable reason), now validates it successfully, and broadcasts `Accepted` for hash `H`.
6. `StackerDBListener`'s Accepted handler sees `slot_id(A)` is not in `gathered_signatures` (only `responded_signers` was touched by step 3) and adds `w_A` to `total_weight_approved` [2](#0-1) . `total_weight_rejected` is never decremented.
7. Now `total_weight_approved` may reach the ≥70% `weight_threshold`, and `total_weight_rejected` (still holding `A`'s stale rejection plus any other legitimately rejecting signers) may simultaneously satisfy `total_weight_rejected + weight_threshold > total_weight`.
8. In `get_block_status`'s polling loop, the rejection check is evaluated first, so the miner returns `Err(SignersRejected { ... })` for block `B` even though the *current* signer verdicts (post re-evaluation) would legitimately cross the 70% acceptance threshold [7](#0-6) , wedging the node into discarding the block/txids and re-proposing, based on the stale, doubly-counted weight.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }

    /// Attempt to transition the block state
    pub fn move_to(&mut self, state: BlockState) -> Result<(), String> {
        if !self.check_state(state) {
            return Err(format!(
                "Invalid state transition from {} to {state}",
                self.state
            ));
        }
        self.state = state;
        Ok(())
    }
