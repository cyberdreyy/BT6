### Title
Stale per-epoch instant-withdraw receipts corrupt default-recovery accounting and freeze recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If a borrower default is later finalized in that same epoch, `finalizeDefaultRecovery` / `_defaultPrefundedInstantReserve` / `defaultPendingClaimBasis` read these stale per-epoch entries as if they were still-live unfunded claims — an out-of-bounds/stale-read analog of CVE-2026-3926 — inflating both the claim basis and the assumed prefunded reserve beyond the underlying actually held, permanently freezing or diluting recovery funds.

### Finding Description
In `IdleCreditVault.claimInstantWithdrawRequest` the funded (non-default) path only zeroes `instantWithdrawsRequests[_user]` and burns receipt tokens; it never touches `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` or `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` [2](#0-1) .

Later, `finalizeDefaultRecovery` computes the recovery basis via `defaultPendingClaimBasis()`, which adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [3](#0-2) . It also computes `_defaultPrefundedInstantReserve()` as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`, treating the stale difference as underlying already held in the strategy [4](#0-3) . Both quantities include receipts that were already paid out at par.

`defaultRecoveryReserve` is then set to `_recoveredAmount + prefundedReserve + defaultRecoveryReserve` [5](#0-4)  — a reserve figure larger than the contract's real underlying balance. Because the guard `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` [6](#0-5)  is satisfied, subsequent `claimInstantWithdrawRequest` calls route into `_claimDefaultedInstantWithdrawRequest`, which pays from this inflated reserve [7](#0-6) .

The sequence is reachable by unprivileged actors: a tranche holder requests an instant withdrawal in epoch N (partially funded by `collectInstantWithdrawFunds`), claims the funded amount at par, and epoch N then ends in borrower default with `pendingInstantWithdraws` still nonzero (partial instant funding is an explicitly supported state per the comments at lines 638-640).

### Impact Explanation
Two concrete harms, both with fund impact:

1. **Insolvency / permanent freezing of recovery funds.** `defaultRecoveryReserve` is credited with `prefundedReserve` underlying that was already paid out and is not in the contract. Once the genuinely-backed portion of the reserve is drained by legitimate claimants, `_transferDefaultRecovery`/`safeTransfer` reverts, permanently freezing the recovery payouts of remaining defaulted-epoch withdraw receipt holders and instant claimants.
2. **Theft/dilution of recovery.** `totalBasis` includes phantom already-claimed instant receipts, so `defaultRecoveryPrice` is depressed; honest defaulted-epoch claimants and active tranche holders (via `activeFinalNAV`/`defaultBBNav`) recover less than they should, while early claimants of the inflated reserve extract more than their pro-rata share.

Additionally, an already-paid user calling `claimInstantWithdrawRequest` after finalization reverts on `instantWithdrawsRequests[_user] -= claimBasis` underflow [8](#0-7) , though this only reverts that user's (empty) claim.

### Likelihood Explanation
Requires: instant withdrawals enabled, at least one instant request in epoch N that is partially funded and claimed, and a borrower default finalized while `epochNumber` still equals N and `pendingInstantWithdraws != 0`. Borrower defaults and partial instant funding are both designed-in states of the vault (the code explicitly handles "partially prefunded instant requests" at line 684). No privileged misbehavior is needed — the attacker is an ordinary instant-withdraw requester whose stale ledger entry corrupts honest-accounting state. Loss scales with the size of the stale per-epoch instant claims relative to the recovery reserve.

### Recommendation
In `claimInstantWithdrawRequest` (and anywhere funded instant receipts are paid at par), clear the per-epoch ledgers in the same way `_claimDefaultedInstantWithdrawRequest` does:

```solidity
// in claimInstantWithdrawRequest, before/while clearing instantWithdrawsRequests[_user]
uint256 epoch = epochNumber; // or track per-request epochs like lastWithdrawRequest
uint256 basis = instantWithdrawsRequestsByEpoch[_user][epoch];
if (basis != 0) {
    instantWithdrawsRequestsByEpoch[_user][epoch] = 0;
    instantWithdrawClaimsByEpoch[epoch] -= basis;
}
```

If a user can hold instant receipts across multiple epochs, track per-user request epochs (analogous to `lastWithdrawRequest`) so every funded claim clears its exact epoch bucket. Alternatively, make `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` derive the live instant basis from receipts not yet claimed rather than from cumulative per-epoch request totals.

### Proof of Concept
Foundry fork test (scaffold consistent with `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testStaleInstantEpochEntryInflatesDefaultRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);            // enter epoch #1 buffer

    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address alice = makeAddr('alice');
    address bob = makeAddr('bob');
    _depositWithUser(alice, 100e6);
    _depositWithUser(bob, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();                      // epoch #1 running, epochNumber == 1

    // Alice requests instant withdraw in epoch #1
    _requestInstantWithdrawWithUser(alice, 50e6);

    // Epoch stop only partially funds instant queue, then borrower defaults
    // (fund less than pendingInstantWithdraws so pendingInstantWithdraws != 0),
    // and trigger default + finalizeDefaultRecovery while epochNumber == 1.
    // ... stopEpoch with insufficient borrower repayment -> defaulted == true
    // idleCDO.finalizeDefaultRecovery(...) with recovered amount R

    // Before finalization Alice claims her funded instant receipt at par.
    // instantWithdrawsRequests[alice] -> 0, but
    // instantWithdrawsRequestsByEpoch[alice][1] and
    // instantWithdrawClaimsByEpoch[1] still hold the stale 50e6.

    // After finalizeDefaultRecovery:
    //   defaultPendingClaimBasis() included the stale 50e6
    //   _defaultPrefundedInstantReserve() counted up to 50e6 of "held" funds
    //   that were already paid to Alice -> defaultRecoveryReserve > balance
    uint256 reserve = strategy.defaultRecoveryReserve();
    assertGt(reserve, underlying.balanceOf(address(strategy)),
        "reserve exceeds actual held underlying");

    // Other claimants' defaulted-epoch claims eventually revert on transfer
    // (permanent freeze) or recover less than pro-rata (theft by dilution).
}
```

Note: exact stop/default choreography depends on `IdleCDOEpochVariant.stopEpoch`/`_handleBorrowerDefault` internals not fully inspected; the invariant violation (reserve > balance, basis including already-paid receipts) is verifiable directly against the strategy's post-conditions.
