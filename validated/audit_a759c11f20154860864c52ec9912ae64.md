### Title
`base_insertValidatedTransaction` trusts a caller-supplied sender address and skips signature verification, allowing forged transactions to enter the pool - ([File: crates/execution/txpool/src/builder/rpc.rs])

### Summary
The RUSTSEC-2026-0224 bug class is "a component treats an externally supplied claim about authenticity as if it had been cryptographically checked, and forwards it to the trusted store as verified." The closest reachable analog in this codebase is `BuilderApiImpl::insert_validated_transaction` (RPC method `base_insertValidatedTransaction`), which accepts a caller-declared `sender: Address` field alongside raw EIP-2718 transaction bytes and constructs the pooled transaction with `Recovered::new_unchecked(consensus_tx, sender)` — i.e. it binds the attacker-chosen `sender` to the transaction body **without ever performing ECDSA signature recovery** to prove that address actually signed it.

### Finding Description
`insert_validated_transaction` is defined as: [1](#0-0) 

The doc comment says explicitly: *"The transaction is EIP-2718 encoded with its sender address pre-recovered, allowing the builder to skip signature verification."* and the implementation comment says the sender addresses are "trusted from the forwarding mempool node."

The handler implementation: [2](#0-1) 

It decodes the raw bytes into `consensus_tx`, then does `Recovered::new_unchecked(consensus_tx, sender)` using the caller-supplied `sender`, not a value recovered from `consensus_tx`'s signature. That `Recovered` is inserted directly into the pool via `add_external_transaction`/`add_transaction`, and from there the normal pool/payload-builder pipeline treats `sender` as authoritative for nonce accounting, balance debits, and eventual inclusion (see `crates/execution/flashblocks/src/processor.rs` where `tx.recover_signer()` is otherwise the standard trust anchor for `sender`, at lines 916-975, contrasted with this bypass path).

Nothing in `BuilderApiImpl` or in the RPC registration path (`crates/builder/core/src/extension.rs`) enforces that the caller is actually the trusted forwarding node — there is no signature-based, mTLS-based, or token-based authentication comparable to what other genuinely-internal endpoints in this repo explicitly call out (e.g. the P2P/nitro RPC servers carry a `// SECURITY: This unauthenticated RPC server is an internal control-plane endpoint. Deployments must restrict it to trusted components on a private network.` comment — see `crates/proof/tee/nitro-host/src/server.rs:84-85` and `crates/consensus/service/src/actors/rpc/actor.rs:76-77`). `base_insertValidatedTransaction` carries no equivalent code-level restriction; its trust boundary is purely a documented assumption ("trusted from the forwarding mempool node") enforced only by network topology/deployment configuration, exactly the class of assumption that produced the caching bug in the report (data trusted as "already verified" when it was not).

### Impact Explanation
If this RPC endpoint is reachable by anyone other than the intended forwarding mempool node (misconfiguration, missing firewall rule, multi-tenant hosting, or a compromised low-privilege service on the same network), an attacker can:
- Submit `raw` bytes for *any* address's transaction shape while declaring an arbitrary `sender`, bypassing the entire signature-authentication step that normally proves transaction authorization.
- Impersonate any account, forging transactions that debit that account's balance / consume its nonce without ever possessing its private key — directly analogous to the "impersonation of any public key" impact called out in the RUSTSEC advisory.
- This is an unauthorized-operation / theft-of-funds vector once network-topology assumptions are violated, since the sequencer/builder can be made to execute and finalize transactions "signed" by nobody.

### Likelihood Explanation
This is intentionally by-design behavior gated by an *implicit, undocumented-in-code* deployment assumption (private-network-only reachability) rather than a runtime authentication mechanism. Unlike comparable genuinely-internal RPC servers in this codebase, no code path enforces that assumption for this specific method (no ProxyGetRequestLayer-style restriction, no auth token check, no origin allow-list at the `BuilderApiImpl` level). Whether it is exploitable in a given deployment therefore depends entirely on network topology outside this code, which I could not fully verify (e.g., whether `proxyd`/ingress configs universally exclude this method from public routing in every environment). I flag this uncertainty explicitly: the "vulnerability" is contingent on a topology/deployment assumption, not a pure code defect, so it sits close to the excluded "deployment/network topology" category in the validation rules — but the root cause (trusting an unverified authenticity claim as if verified) is a precise structural match to the reported bug class.

### Recommendation
- Require `insert_validated_transaction` to itself recover and verify the signer from the transaction signature (or from a `SignerRecoverable` recovery call) and reject the request if the recovered address does not match the declared `sender`, rather than trusting the caller-supplied value via `Recovered::new_unchecked`.
- If pre-recovery is kept for performance, gate the endpoint behind an explicit authenticated channel (mutual TLS, shared secret, or a signed forwarding envelope) enforced in code, matching the pattern used by other genuinely-internal RPC servers in this repo, and add an explicit `// SECURITY` restriction comment plus a network-binding default (loopback-only unless overridden).

### Proof of Concept
1. Obtain network access to a builder node's RPC port that has `BuilderApiExtension` installed (`base_insertValidatedTransaction`, e.g. `L2_BUILDER_HTTP_PORT` in `etc/docker/devnet-env`).
2. Craft any syntactically valid EIP-1559 transaction body (`raw`) with an arbitrary/garbage signature — decoding only requires a structurally valid EIP-2718 envelope, not a valid signature (see `create_eip1559_tx` test helper using `Signature::new(U256::from(1), U256::from(2), false)` in `crates/execution/txpool/src/builder/rpc.rs:232-249`, which the test suite itself uses to demonstrate a successful pool insertion despite the bogus signature).
3. Call `base_insertValidatedTransaction` with `{ sender: <victim_address>, raw: <crafted_bytes>, extensions: {} }`.
4. The handler decodes `raw`, builds `Recovered::new_unchecked(consensus_tx, victim_address)` without verifying the signature belongs to `victim_address`, and inserts it into the pool as coming from `victim_address` — as confirmed by the passing integration test `test_insert_validated_eip1559_tx` (`crates/builder/core/tests/rpc.rs:135-148`), which succeeds using only a `sender`/`raw` pair with no real signer proof.

/// RPC interface for submitting pre-validated transactions to a block builder.
///
/// `E` is the wire extension payload; see [`ValidatedTransactionExtensions`].
#[rpc(server, namespace = "base")]
pub trait BuilderApi<E> {
    /// Inserts a single pre-validated transaction into the builder's pool.
    ///
    /// The transaction is EIP-2718 encoded with its sender address pre-recovered,
    /// allowing the builder to skip signature verification.

    /// Returns an error if decoding or pool insertion fails.
    /// Use JSON-RPC batch requests for efficient bulk submission.
    #[method(name = "insertValidatedTransaction")]
    async fn insert_validated_transaction(&self, tx: ValidatedTransaction<E>) -> RpcResult<()>;
}
