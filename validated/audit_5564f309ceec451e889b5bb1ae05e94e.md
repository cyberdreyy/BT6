### Title
Miner signature malleability lets a single miner mint two distinct `signer_signature_hash` values for one identical block, bypassing the signer's per-height double-sign guard - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoBlockHeader::signer_signature_hash_inner` folds `miner_signature` into the preimage that signers sign over, while `miner_signature_hash_inner` (what the miner signs) excludes it. Because secp256k1 ECDSA signatures are malleable (`(r,s)` and `(r, n-s)` both verify against the same public key and message), a single miner — with no cooperation from any other party — can produce two byte-distinct, both cryptographically valid `miner_signature` values for the *exact same* block content (same txs, same state transition, same `miner_signature_hash`). Each variant hashes to a different `signer_signature_hash`, so the signer set's entire conflict-tracking machinery, which is keyed by `signer_signature_hash`, sees these as two unrelated blocks rather than one.

### Finding Description
- `signer_signature_hash_inner` explicitly commits to `miner_signature`: `write_next(fd, &self.miner_signature)?;` [1](#0-0) , whereas `miner_signature_hash_inner`, the digest the miner actually signs, omits it entirely [2](#0-1) .
- The codebase itself documents and exercises this malleability: `malleablize_signature` flips a `MessageSignature`'s `s` to `n - s` (and the recovery-id parity bit), explicitly noting "It recovers to the same public key, so the signature remains valid, but its bytes (and any hash committing to them) change. Used to construct malleablized blocks: flipping the miner signature changes a block's id without changing its execution." [3](#0-2) 
- A test (`test_with_negated_s`) confirms both signature encodings recover to the identical public key for the identical message [4](#0-3) .
- All signer-side conflict detection, pre-commit tallying, and vote storage are keyed strictly by `signer_signature_hash` (e.g. `block_lookup_by_reward_cycle`, `get_signed_conflicts`, `handle_block_pre_commit`, `store_and_process_block_signature`), never by the block's underlying execution/content equality [5](#0-4) [6](#0-5) .

The equality broken: the signer set's "one signature per height/tenure" invariant assumes `signer_signature_hash` uniquely identifies a block's content, so that a fresh signature over hash H at height N blocks a signature over any different content at height N via `get_signed_conflicts`. Miner-signature malleability breaks that assumption: hash H1 and hash H2 can both correspond to the *same* semantic block. A signer that already validated and pre-committed to variant H1 (submitted to the node for validation and stored as `Unprocessed`/`PreCommitted`, not yet crossing the 70% pre-commit threshold) sees a later-arriving H2 as an entirely unrelated, never-before-seen proposal (`block_lookup_by_reward_cycle` misses), goes through the full fresh-evaluation path (`FRESH` in the flow), and can pre-commit/sign it independently, because `get_signed_conflicts` only returns rows for blocks that already carry a *signature*, and content-identity between H1 and H2 is invisible to it.

### Impact Explanation
This does not by itself let a miner get an invalid or non-canonical block signed (the content is identical, so it passes the same chainstate checks either way), so it falls short of the "signing an invalid/non-canonical block" critical bar. Its consequence is instead **doubled signer traffic/state per height** (two parallel `BlockInfo` rows, two pre-commit tallies, two signature-aggregation trees for what is one block) and it undermines the documented invariant that `signer_signature_hash` conflict tracking (`get_signed_conflicts`, `has_committed`, `block_lookup_by_reward_cycle`) is a faithful proxy for "have I already endorsed this content at this height." Different signers could converge their weight onto different variants (H1 vs H2) of the same block, splitting the 70% threshold across two hashes instead of one, which can stall the node's `verify_signer_signatures` (which needs ≥70% weight over *one* specific `signer_signature_hash`) even though a supermajority of signers actually endorsed the same underlying block content. That is a liveness degradation rather than a safety break, and requires no cooperation beyond the block-producing miner itself.

### Likelihood Explanation
Trivial and always available to whichever address currently holds the miner slot: computing `n - s` and flipping one bit is a few lines of arithmetic, requires no additional signing operation, and can be done for every block a miner produces. No signer key, majority, or StackerDB manipulation is needed — the test helper `malleablize_signature` in this very repo demonstrates it is already a known, mechanically simple operation. The main mitigating factor is that in the "happy path" a miner has no incentive to fragment its own block's votes; the bug is latent and would need a miner to deliberately publish both variants (e.g. via gossip to different subsets of signers) to actually split weight.

### Recommendation
Exclude `miner_signature` from the `signer_signature_hash` preimage (mirroring `miner_signature_hash`), or normalize `miner_signature` to its canonical low-S form before computing `signer_signature_hash`, so that signature malleability of the miner's own signature cannot change the block's identity as seen by the signer set. If removing the field outright is not epoch-compatible, at minimum normalize (`normalize_s`) `miner_signature` prior to hashing, consistently across `consensus_serialize`/`consensus_deserialize`, so H1 and H2 collapse to one canonical hash.

### Proof of Concept
1. Miner builds a Nakamoto block body and computes `miner_signature_hash` (excludes `miner_signature`), signs it to get `sig`.
2. Miner computes `sig' = malleablize_signature(&sig)` — same `(r, message, pubkey)`, negated `s`, flipped recovery-id parity bit, per `malleablize_signature` [7](#0-6) ; `sig'` still recovers to the miner's pubkey (`test_with_negated_s`).
3. Assemble two headers identical except `miner_signature = sig` vs `miner_signature = sig'`. Each has a distinct `signer_signature_hash` (which includes `miner_signature` in its preimage) despite identical `chain_length`, `consensus_hash`, `tx_merkle_root`, etc.
4. Broadcast variant A to signers 1..k and variant B to signers k+1..n via `.miners` StackerDB / direct proposal channels.
5. Each subset validates and pre-commits/signs its own variant independently — `block_lookup_by_reward_cycle`/`get_signed_conflicts` never correlate the two hashes — splitting pre-commit/signature weight across A and B instead of consolidating on one signature set, potentially preventing either from reaching the 70% `compute_voting_weight_threshold` even though the same block content was, in aggregate, endorsed by a supermajority.

/// high-S/low-S complement `s' = n - s`, with the recovery id's parity bit
/// flipped. It recovers to the same public key, so the signature remains valid,
/// but its bytes (and any hash committing to them) change. Used to construct
/// malleablized blocks: flipping the miner signature changes a block's id
/// without changing its execution.
fn malleablize_signature(sig: &MessageSignature) -> MessageSignature {
    // secp256k1 group order `n`, big-endian.
    const SECP256K1_ORDER_BE: [u8; 32] = [
        0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF,
        0xFE, 0xBA, 0xAE, 0xDC, 0xE6, 0xAF, 0x48, 0xA0, 0x3B, 0xBF, 0xD2, 0x5E, 0x8C, 0xD0, 0x36,
        0x41, 0x41,
    ];
    // MessageSignature layout: [recovery_id (1)][r (32)][s (32)].
    let mut bytes = sig.0;
    // s' = n - s, as a 32-byte big-endian subtraction.
    let mut borrow = 0i16;
    for i in (0..32).rev() {
        let diff = SECP256K1_ORDER_BE[i] as i16 - bytes[33 + i] as i16 - borrow;
        let (val, next_borrow) = if diff < 0 { (diff + 256, 1) } else { (diff, 0) };
        bytes[33 + i] = val as u8;
        borrow = next_borrow;
    }
    // Negating s flips the parity of R, so flip the recovery id's low bit.
    bytes[0] ^= 0x01;
    MessageSignature(bytes)
}
