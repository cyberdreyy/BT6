### Title
Cross-user response delivery due to `MessageId`-only keyed callback map in Gateway `WebAPIHandler` - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Gateway's `WebAPIHandler` (`capabilities` package) stores the caller's response callback in a map keyed **only** by the client-supplied `MessageId`, with no binding to the caller's identity and no collision check on insert. Because `MessageId` is fully attacker/user-controlled and only length-validated, two different unprivileged callers can cause their callback registrations to collide, resulting in one user's HTTP-trigger response being delivered to a different, unrelated caller — the same "response sent to the wrong identity" bug class as the referenced `PoolCommitter._uncommit` finding (funds/response routed using the wrong owner reference).

### Finding Description
`HandleLegacyUserMessage` registers the caller's callback like this: [1](#0-0) 

Note this is an unconditional map write — if an entry already exists under the same key, it is silently overwritten (no "already exists" check).

When a DON node later responds, the gateway looks the callback up **solely by `MessageId`** and deletes/dispatches it: [2](#0-1) 

The `MessageId` that becomes the map key is taken directly from the untrusted request body and is only checked for length/null-suffix — it is never required to be unique per sender: [3](#0-2) 

By contrast, the sibling `RequestCache` abstraction used elsewhere in the same gateway package deliberately scopes cache keys by `{sender, id}` and rejects duplicate keys, showing the intended safe pattern that `WebAPIHandler.savedCallbacks` fails to follow: [4](#0-3) 

**Attack scenario:**
1. User A sends a legacy `web_api_trigger` request with `MessageId = "X"` (e.g. via `ProcessRequest` → `HandleLegacyUserMessage`, reachable by any unprivileged client hitting the gateway's user-facing HTTP port).
2. `h.savedCallbacks["X"]` is set to A's callback; the request is forwarded to DON nodes.
3. Before a node responds, User B (a different unprivileged tenant, potentially malicious) sends a request also using `MessageId = "X"`.
4. `h.savedCallbacks["X"]` is overwritten with B's callback.
5. When a DON node responds to A's original request (still carrying `MessageId = "X"`), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's response data to B.
6. A's HTTP client instead times out waiting for a response (or later receives B's response if B's own request completes afterward), and B receives data that was never meant for them.

This is a cross-user response confusion analogous to `_uncommit` sending tokens to `msg.sender` (the pool) instead of `_commit.owner`: the wrong "owner" reference (here, the wrong caller's saved callback) is used to route sensitive output.

### Impact Explanation
The `Response` payload delivered to the wrong user can contain HTTP response bodies/headers from an external endpoint invoked on behalf of another tenant (`sendHTTPMessageToClient`), which may include sensitive data, workflow output, or execution results scoped to a different workflow/DON job. This is a confidentiality and correctness violation reachable by any unprivileged caller of the gateway's user-facing endpoint, requiring only the ability to choose an arbitrary `MessageId` and race message delivery timing.

### Likelihood Explanation
`MessageId` collision is trivial to induce: it is fully client-supplied (`MessageBody.MessageId`), validated only for length (`MessageIdMaxLen = 128`) and trailing-null-byte rules — never checked against in-flight IDs from other senders. An attacker only needs to guess or observe another in-flight request's `MessageId` (or brute-force/collide over the ID space, especially if calling clients use predictable IDs) and send a competing request before the legitimate response arrives. No special network position, node compromise, or elevated privileges are required — the endpoint is reached through the standard unprivileged user-facing gateway request path (`gateway.ProcessRequest` → `handlers.Handler.HandleLegacyUserMessage`).

### Recommendation
Scope `savedCallbacks` by a composite key that includes the authenticated/derived caller identity (or a server-generated unique nonce bound to the caller), not just the client-supplied `MessageId`, mirroring the `{sender, id}` pattern already used in `RequestCache`. Additionally, reject registration if a key collision occurs, and validate that the response's associated request context (message ID) is only ever resolved against the specific request that created it, rather than trusting the latest map entry.

### Proof of Concept
1. Configure a gateway with the legacy `web_api_trigger` handler enabled.
2. As User A, POST a legacy JSON message with `Body.MessageId = "collide-1"`, `Method = "web_api_trigger"`, targeting a DON that is slow to respond (e.g., add artificial latency or use a target the node takes time to reach).
3. Before the DON node replies, as User B, POST another legacy message with the same `Body.MessageId = "collide-1"` (different sender/signature, same MessageId).
4. Observe in `handleWebAPITriggerMessage` (`core/services/gateway/handlers/capabilities/handler.go:148-162`) that when the DON node finally sends its response for `MessageId="collide-1"` (intended for A's request), the lookup `h.savedCallbacks[msg.Body.MessageId]` returns User B's callback (since B's registration in `HandleLegacyUserMessage` overwrote A's), and A's response payload is sent back over User B's HTTP connection instead of A's.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
