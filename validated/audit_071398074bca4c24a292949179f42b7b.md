### Title
Post-default withdraw requests pay 1:1 from the fixed recovery reserve, stealing recovery owed to defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` mints an unbounded post-default receipt (`postDefaultRequests`) after `defaultRecoveryFinalized`, and `_claimPostDefaultWithdrawRequest` pays it 1:1 out of `defaultRecoveryReserve` — the same fixed reserve sized at default finalization to cover only the haircutted claims of defaulted-epoch receipt holders. No underlying is deposited to back these new receipts; they are pure dilution of other users' recovery.

### Finding Description
The kernel bug is a UAF: a connection object is looked up and then dereferenced outside the lock that guarantees it is still valid — the object may have been freed between lookup and use. The analog here is a claim paid against a resource whose backing was fixed at finalization and then silently re-purposed.

In `requestWithdraw` (lines 247–257), once `defaultRecoveryFinalized` is set, any tranche-token holder can call `requestWithdraw(_amount, _user, _principal)` through the CDO. The function burns `_amount` of the CDO's strategy tokens, mints `_amount` receipt tokens to the user, and sets `postDefaultRequests[_user] = _amount`. Critically, **no underlying ever enters the vault to back this claim** — the only transfers are strategy-token burn/mint.

`_claimPostDefaultWithdrawRequest` (lines 760–767) then pays `amount` at par via `_transferDefaultRecovery`, which unconditionally decrements `defaultRecoveryReserve` (lines 912–917):

```solidity
defaultRecoveryReserve -= _amount;
underlyingToken.safeTransfer(_user, _amount);
```

The comment says post-default receipts "are paid 1:1 because the haircut was applied when the request was made" — but the haircut was applied to `virtualPrice` inside the CDO, leaving the recovered value in the pool; nothing earmarks or replenishes the vault's recovery reserve for these new claims. Meanwhile the reserve was sized at `finalizeDefaultRecovery` to exactly cover the defaulted-epoch claims (`_claimDefaultedWithdrawRequest` pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the same reserve, lines 772–784, and `_claimDefaultedInstantWithdrawRequest` does the same, lines 842–855).

There is also no cap on post-default creation: the guard at line 249 only checks that *this user* has no pending requests — it does not limit aggregate post-default issuance relative to the reserve.

### Impact Explanation
Direct theft of unclaimed yield / permanent freezing of unclaimed recovery. Every unit of post-default request claims one unit of the recovery reserve at par. An attacker (any tranche-token holder — no privileged role needed) front-runs legitimate defaulted-epoch claimants: they `requestWithdraw` after `defaultRecoveryFinalized`, then `claimWithdrawRequest`, draining `defaultRecoveryReserve` down to near zero. When the actual defaulted-epoch victims later call `claimWithdrawRequest`, `_claimDefaultedWithdrawRequest` computes their haircutted payout, but `defaultRecoveryReserve -= _amount` underflows (Solidity 0.8 checked arithmetic) and the transfer reverts — their recovery is permanently frozen. Quantified loss: up to the entire `defaultRecoveryReserve` balance, i.e., the full realized recovery of the default event.

### Likelihood Explanation
- Phase: defaulted + finalized (`defaultRecoveryFinalized == true`), which persists indefinitely after `finalizeDefaultRecovery`.
- Attacker requirements: hold tranche tokens (or acquire dust), be KYC-allowed — the same unprivileged surface as any lender.
- No timing race needed: post-default requests can be created at any point after finalization, and claims are processed first (`claimWithdrawRequest` lines 303–310 checks post-default before defaulted-epoch claims).
- Existing guards do not stop it: `_hasWithdrawRequest`/`postDefaultRequests[_user] != 0` check is per-user only (an attacker can split across many addresses); `_ensureDefaultRecoveryInitialized`, the closed-pool check, and `_transferFundedClaim`'s reserve guard (lines 899–905) do not apply — the reserve guard exists only on the *funded* path, never on the reserve path itself.
- Caveat I could not fully verify within the index: whether `finalizeDefaultRecovery` in the CDO transfers additional underlying into the vault earmarked for post-default claims. From the strategy-side code, `requestWithdraw` performs no underlying transfer and `collectWithdrawFunds`/`collectInstantWithdrawFunds` are the only funding entry points, neither of which is invoked on the post-default path — so the reserve appears to be a fixed, non-replenished pool.

### Recommendation
- Track a separate `postDefaultReserve` credited by an explicit funding call (`collectWithdrawFunds`-style pull from the CDO for the haircut proceeds), and pay post-default claims exclusively from it.
- Alternatively, cap cumulative `postDefaultRequests` issuance at the reserve headroom explicitly reserved for post-default claims at finalization, and make `_transferDefaultRecovery` take the reserve bucket as a parameter.
- At minimum, add an invariant check in `_transferDefaultRecovery` that `defaultRecoveryReserve` never falls below the sum of outstanding defaulted-epoch claim bases (`defaultPendingClaimBasis`), so post-default claims cannot consume other users' finalized recovery.

### Proof of Concept
Foundry fork sketch (mainnet fork, existing vault deployment; assuming the standard epoch CDO wiring):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.17;
import "forge-std/Test.sol";

contract PostDefaultReserveDrainTest is Test {
    // wire: idleCDO (IdleCDOEpochVariant), strategy (IdleCreditVault), underlying (e.g. USDC)

    function testPostDefaultClaimsDrainRecoveryReserve() public {
        // --- Phase: epoch running, then borrower defaults ---
        // 1. victim deposits AA, requests withdraw in the defaulted epoch
        // 2. borrower underpays at stopEpoch -> defaulted() == true
        // 3. manager calls finalizeDefault / finalizeDefaultRecovery
        //    -> defaultRecoveryPrice and defaultRecoveryReserve fixed
        uint256 reserve = strategy.defaultRecoveryReserve();
        assertGt(reserve, 0);

        // --- Attacker: unprivileged tranche holder ---
        address attacker = makeAddr("attacker");
        // attacker acquires tranche tokens via deposit pre-default or secondary market;
        // post-finalization attacker calls:
        vm.startPrank(attacker);
        cdo.requestWithdraw(attackerTrancheBalance, address(aaTranche));
        // creates postDefaultRequests[attacker] = haircut-less amount, no funding
        cdo.claimWithdrawRequest();
        vm.stopPrank();

        // _claimPostDefaultWithdrawRequest pays 1:1 from defaultRecoveryReserve
        assertEq(strategy.defaultRecoveryReserve(), reserve - attackerPayout);

        // --- Victim claim now reverts / is frozen ---
        vm.prank(victim);
        vm.expectRevert(); // underflow in defaultRecoveryReserve -= _amount
        cdo.claimWithdrawRequest();
    }
}
```

PoC steps concretely: deposit as victim, request withdraw, run an epoch stop with shortfall so `defaulted()` is set, call `finalizeDefaultRecovery` (honest manager path), then as attacker call `requestWithdraw` + `claimWithdrawRequest` repeatedly (or via sybil addresses) until `defaultRecoveryReserve` approaches zero; the victim's `claimWithdrawRequest` then reverts on the reserve decrement, proving theft/permanent freezing of their defaulted-epoch recovery.
