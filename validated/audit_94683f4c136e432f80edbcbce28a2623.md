### Title
IdleCreditVault mints strategy tokens on the requested `_amount` instead of the actual received balance, breaking solvency for fee-on-transfer underlyings - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.deposit` pulls `_amount` of `underlyingToken` from the IdleCDO and mints `_amount` strategy tokens 1:1, without measuring the balance delta. For fee-on-transfer tokens (e.g., USDT with its togglable fee enabled, or any ERC20 with transfer fees), the vault receives less than `_amount` but mints the full `_amount`, inflating strategy-token supply beyond real backing. This is the same bug class as the Surge `addCollateral` report: crediting deposits by nominal amount rather than actual amount received.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`, `deposit` does:

```solidity
if (_amount > 0) {
  underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
  _mint(msg.sender, _amount);
}
```

(lines 602–605). The minted strategy tokens are denominated 1:1 in underlyings (per the doc comment "strategy tokens (1:1 with underlyings)") and back the CDO's NAV via `getContractValue`/`balanceOf(idleCDO)` accounting (lines 674–677).

The CDO itself correctly credits the depositor only for tokens actually received: `IdleCDO._deposit` computes `_contractTokenBalance(_token) - _preBal` before minting tranche shares (`IdleCDO.sol:250-253`), and `IdleCDOCreditVault._deposit` does the same at lines 203–206. However, `IdleCDOCreditVault._deposit` then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the nominal `_amount` (line 211). Two failures result:

1. **Double fee / NAV inflation**: the CDO only received `_amount - fee1` from the user, then the vault's `safeTransferFrom` pulls `_amount` and itself loses `fee2`, so the vault holds `_amount - fee1 - fee2` tokens but mints `_amount` strategy tokens to the CDO. NAV overstates real backing by `fee1 + fee2`.
2. **Silent draining of prior liquidity**: to pull `_amount`, the vault draws on the CDO's existing token balance (idle liquidity from earlier deposits), so the shortfall is covered by other depositors' funds — a direct transfer of value to the new depositor's share class.

The fee amount becomes unbacked strategy-token supply. Because strategy tokens redeem against real vault/epoch liquidity (`sendInterestAndDeposits`, withdraw-request claims at `pendingWithdraws`/`instantWithdrawClaimsByEpoch`), the last withdrawers or defaulted-epoch claimants absorb the shortfall. No guard stops this: `_onlyIdleCDO` passes (the CDO initiates the call), `_checkDefault`/`skipDefaultCheck` only inspect `strategyPrice`, and there is no skim/donation check on the mint path.

### Impact Explanation
Each deposit of a fee-on-transfer underlying inflates strategy-token supply by `fee1 + fee2` (twice the transfer-fee percentage of `_amount`) relative to real backing. Since `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over a basis that includes these inflated tokens, and pending/normal withdraw claims are paid from real underlying, the shortfall is socialized: honest lenders and tranche holders suffer a permanent loss equal to the cumulative unbacked minted amount, and terminal withdrawals can freeze when claims exceed real tokens.

### Likelihood Explanation
Medium. The attack requires the credit vault's underlying to be a fee-on-transfer token and an unprivileged lender (KYC-passing in whitelisted vaults, or anyone otherwise) to call `depositAA`/`depositBB`. USDT's fee is currently 0 but togglable, and multiple fee-on-transfer tokens exist. The vault has no allowlist on `token`, so a deployment using such an underlying is fully exposed on every deposit.

### Recommendation
Measure the balance delta in `deposit` and mint only what was received, mirroring the CDO's own pattern:

```solidity
uint256 balBefore = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - balBefore;
_mint(msg.sender, received);
```

and have `IdleCDOCreditVault._deposit`/`depositDuringEpoch` propagate the actual received amount (instead of nominal `_amount`) to `strategy.deposit`, or revert if `received < _amount`.

### Proof of Concept
Foundry fork sketch (fork mainnet, use a fee-on-transfer token or a mock with a 1% transfer fee as `token`):

```solidity
function testFeeOnTransferInflation() public {
    // token = FoTToken with 1% fee; vault already holds prior deposits (NAV > 0)
    uint256 amount = 1_000_000e6;
    FoT(token).mint(attacker, amount);
    vm.prank(attacker);
    FoT(token).approve(address(cdo), amount);

    uint256 vaultBalBefore = FoT(token).balanceOf(address(vault));
    uint256 stratSupplyBefore = vault.totalSupply();

    vm.prank(attacker);
    cdo.depositAA(amount);

    uint256 received = FoT(token).balanceOf(address(vault)) - vaultBalBefore;
    uint256 minted = vault.totalSupply() - stratSupplyBefore;

    // vault minted `amount` strategy tokens but received < amount net of both fees
    assertGt(minted, received);            // insolvency: minted - received
    // attacker was only credited amount*0.99 tranche shares, yet the CDO's
    // strategy-token NAV grew by `amount`, diluting all existing depositors.
}
```

The assertion `minted > received` demonstrates the broken solvency invariant; a subsequent `withdrawAA`/`claimWithdrawRequest` by earlier depositors will find claims exceeding real underlying.
