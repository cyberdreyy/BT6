### Title
Claimed instant-withdraw receipts stay on the per-epoch pending lists, corrupting default recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a funded instant-withdraw receipt and clears only the aggregate `instantWithdrawsRequests[_user]`, but never removes the same receipt from the two per-epoch structures `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. This mirrors the IOPF double-listing UAF: the receipt is "freed" through one path (par claim) while remaining linked on the generic pending list that default finalization later walks (`defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, `_claimDefaultedInstantWithdrawRequest`). If the borrower defaults in the same epoch while some instant requests remain unfunded, the stale entries inflate the recovery basis and the phantom prefunded reserve, so legitimate claimants are underpaid and part of `defaultRecoveryReserve` becomes stranded dust.

### Finding Description
In `requestInstantWithdraw`, a receipt is recorded in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) . The normal claim path clears only the aggregate: it burns `amount`, sets `instantWithdrawsRequests[_user] = 0`, and transfers underlying [2](#0-1) . Neither per-epoch map is touched — nothing else ever decrements `instantWithdrawClaimsByEpoch` except the default path [3](#0-2) .

During `finalizeDefaultRecovery`, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve` counts `instantBasis - pendingInstant` as already-held recovery funds [5](#0-4) . Both consume the stale entries of already-claimed receipts, since both are keyed to `epochNumber`, which equals `defaultRecoveryEpoch` when default is finalized in the same epoch.

### Impact Explanation
Two concrete impacts, both with direct fund loss:

1. **Recovery dilution / stranded reserve.** Already-paid instant claims are counted in `pendingBasis`, so `recoveryPrice = reserveAmount / totalBasis` is depressed. Legitimate defaulted and post-default claimants receive less than their entitlement per unit of recovered funds, and the reserve portion notionally allocated to stale claims can never be withdrawn — it is permanently frozen in the contract (theft/permanent freezing of unclaimed yield for the other victims).
2. **Phantom reserve inflates the price.** `_defaultPrefundedInstantReserve` treats `instantWithdrawClaimsByEpoch - pendingInstantWithdraws` as underlying already held by the strategy. Stale claims inflate this term, adding phantom funds to `defaultRecoveryReserve` without a matching balance. `recoveryPrice` is therefore also overstated on this component, and `_transferDefaultRecovery` transfers will fail for the last claimants (`balanceOf < reserve` bookkeeping aside, the ERC20 transfer itself reverts on insufficient balance), permanently freezing remaining recovery funds [6](#0-5) .

Quantified example: epoch N, user A instantly withdraws 100 USDC (funded and claimed at par). User B's 100 USDC instant request remains unfunded (`pendingInstantWithdraws = 100`). Borrower defaults; recovery source supplies 100. `defaultPendingClaimBasis` = 0 + `instantWithdrawClaimsByEpoch[N]` = 200, and `_defaultPrefundedInstantReserve` = 200 − 100 = 100 (phantom — A's 100 was already paid out). `reserveAmount` = 200, `recoveryPrice` = 200·1e18/200 = 1.0, but only 100 USDC actually backs it. B claims 100·1.0 = 100 and drains everything; any other claimant's `_transferDefaultRecovery` reverts, and the true entitlement B should have shared is distorted. With real pending normal receipts mixed in, the mispricing splits arbitrarily between dilution and insolvency.

### Likelihood Explanation
Requires the standard-epoch variant with instant withdrawals enabled, an instant claim completed earlier in the same epoch, and default finalization (`finalizeDefaultRecovery`) executed while `epochNumber` is unchanged and `pendingInstantWithdraws != 0`. All attacker-facing steps (`requestInstantWithdraw` → `claimInstantWithdrawRequest` after funding) are unprivileged user actions; only the honest manager/borrower default sequence positions the epoch. No guard clears the per-epoch maps, and no existing check rejects the stale basis — `_ensureDefaultRecoveryInitialized` only gates on `pendingInstantWithdraws`, which is legitimately nonzero in this scenario [7](#0-6) . Likelihood is moderate: it needs a same-epoch default after instant claims, a configuration the instant-withdraw feature explicitly supports.

### Recommendation
Mirror the upstream fix — dequeue the receipt from every pending list when it is completed. In `claimInstantWithdrawRequest`, after computing `amount`, also clear the per-epoch membership:

```solidity
uint256 epoch = /* request epoch, e.g. track via lastInstantRequestEpoch[user] */;
instantWithdrawsRequestsByEpoch[_user][epoch] = 0;   // or subtract amount for the correct epoch
instantWithdrawClaimsByEpoch[epoch] -= amount;
```

Because the aggregate mixes epochs, store the request epoch per user (or iterate/cap the decrement to the epochs that contributed), then decrement `instantWithdrawClaimsByEpoch` and `instantWithdrawsRequestsByEpoch` by the claimed amount so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever see still-unclaimed receipts.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testStaleInstantClaimCorruptsDefault() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);

    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address userA = makeAddr('userA');
    address userB = makeAddr('userB');
    uint256 tranchesA = _depositWithUser(userA, 100e6);
    uint256 tranchesB = _depositWithUser(userB, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    _requestInstantWithdrawWithUser(userA, tranchesA);
    _requestInstantWithdrawWithUser(userB, tranchesB);

    // Fund only A's instant request so pendingInstantWithdraws stays > 0
    vm.prank(manager);
    cdoEpoch.collectInstantWithdrawFunds(100e6); // borrower/CDO funds A only

    uint256 epoch = strategy.epochNumber();
    skip(101);
    vm.prank(userA);
    cdoEpoch.claimInstantWithdrawRequest();      // A paid at par
    // stale: instantWithdrawClaimsByEpoch[epoch] still 200e6
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 200e6); // BUG: never cleared

    // borrower defaults in the same epoch; recovery supplies 100e6
    _handleBorrowerDefaultAndFinalize(100e6);

    // basis counted 200e6 + phantom prefunded 100e6 -> mispriced recovery;
    // B's claim consumes the entire real 100e6 and further claims revert on
    // insufficient balance inside _transferDefaultRecovery.
}
```

Expected: `instantWithdrawClaimsByEpoch[epoch]` should be `100e6` after A's claim; with the bug it remains `200e6`, inflating `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` during `finalizeDefaultRecovery` [8](#0-7) .
