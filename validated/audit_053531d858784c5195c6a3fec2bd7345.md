### Title
External ERC4626 liquidity withdrawal blocks epoch settlement and freezes pending withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In programmable-borrower mode, `IdleCDOEpochVariant.stopEpoch` must call `ProgrammableBorrower.onStopEpoch` before it can fund normal withdrawal requests. [1](#0-0)  If the programmable borrower lacks enough idle cash, `onStopEpoch` synchronously withdraws the shortfall from the configured ERC4626 vault and deliberately reverts when that withdrawal fails. [2](#0-1)  A permissionless user of that ERC4626 vault can exhaust its currently withdrawable liquidity before the honest manager calls `stopEpoch`, causing `StopEpochVaultLiquidityUnavailable` to bubble up and leaving the epoch active and pending withdrawals unfunded. [3](#0-2) 

### Finding Description
`ProgrammableBorrower.onStartEpoch` parks all on-hand underlying in the configured ERC4626 vault and activates epoch accounting. [4](#0-3)  At epoch end, `IdleCDOEpochVariant._stopEpoch` calculates the amount needed for epoch interest and `IdleCreditVault.pendingWithdraws`, then invokes `onStopEpoch` on the borrower adapter. [5](#0-4) 

The adapter calculates the cash shortfall, checks only that the vault share valuation economically covers the shortfall, and then calls `vault.withdraw(shortfall, address(this), address(this))`. [6](#0-5)  The catch block converts any ERC4626 withdrawal failure into `StopEpochVaultLiquidityUnavailable`, and because the hook is invoked directly rather than behind a `try/catch`, the entire `stopEpoch` call reverts. [3](#0-2) [7](#0-6) 

This creates the same resource-contention pattern as the external report: an unprivileged actor consumes a shared liquidity resource needed by a critical settlement path, while the protected transaction itself fails before reaching the borrower-default fallback. [1](#0-0)  The repository’s own regression test demonstrates this state transition: the stop call reverts, `defaulted` remains false, `isEpochRunning` remains true, borrower accounting remains active, and `pendingWithdraws` remains unchanged. [8](#0-7) 

### Impact Explanation
An unprivileged ERC4626 vault shareholder can temporarily freeze settlement of the credit-vault epoch and the full `pendingWithdraws` amount by withdrawing enough vault liquidity immediately before the manager’s stop transaction. [9](#0-8)  The frozen amount is at least `IdleCreditVault(strategy).pendingWithdraws()`, plus any cash interest that must be pulled in non-minted mode, because those funds cannot be collected while the vault withdrawal reverts. [10](#0-9) 

The attack does not require a malicious owner, manager, guardian, borrower, or queue. [11](#0-10)  It is temporary rather than permanent: once the external vault again has withdrawable liquidity, the manager can retry `stopEpoch`, but the borrower is not marked defaulted during the freeze. [12](#0-11) 

### Likelihood Explanation
The attacker only needs to be a normal shareholder/user of the external ERC4626 vault and to redeem enough shares to make `vault.withdraw(shortfall, ...)` exceed the vault’s available liquidity. [2](#0-1)  The attack is timing-sensitive because it must occur between the epoch’s maturity and the honest manager’s `stopEpoch` transaction, but the epoch end and the pending-withdrawal obligation are public on-chain state. [13](#0-12) 

The current code intentionally makes this failure retryable rather than treating unavailable external-vault liquidity as borrower insolvency. [14](#0-13)  Consequently, no existing guard converts the condition into a default or provides an alternative settlement route while the vault remains liquidity-constrained. [1](#0-0) 

### Recommendation
Avoid making the epoch state transition atomically dependent on immediate ERC4626 cash availability. [1](#0-0)  A safer design should record that settlement is awaiting vault liquidity and provide a permissionless or operator-controlled asynchronous completion path that funds `pendingWithdraws` once liquidity returns, while still bounding how long withdrawals can remain unsettled. [15](#0-14) 

If an ERC4626 withdrawal can legitimately fail despite share coverage, `onStopEpoch` should distinguish economic insolvency from temporary illiquidity and return a retryable status that allows `IdleCDOEpochVariant` to enter an explicit settlement-pending state rather than reverting the entire state transition. [16](#0-15)  That state should expose a `completeStopEpoch`-style function, prevent new borrowing against the reserved amount, and optionally define an escalation/default deadline based on product requirements. [17](#0-16)

// test/foundry/ProgrammableBorrowerCreditVault.t.sol
function testUnprivilegedVaultWithdrawalFreezesStopEpochSettlement() external {
    // Existing production fork setup uses a live MetaMorpho ERC4626 vault.
    _setUpProgrammableBorrowerCreditVault(FORK_BLOCK, STEAKHOUSE_USDC);

    uint256 amount = 10_000 * oneScale;
    address vaultUser = makeAddr("external-vault-user");

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // Honest LP deposits and creates a normal withdrawal receipt for the next epoch.
    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );

    // Honest manager starts the epoch; idle cash is parked in the external ERC4626.
    _startEpochAndCheckPrices(0);

    uint256 pending = strategy.pendingWithdraws();
    assertGt(pending, 0, "pending withdrawal required");

    // Give an unprivileged vault user vault shares and redeem enough vault liquidity
    // before the manager's stopEpoch transaction. On a live fork this can also be an
    // existing shareholder redeeming their position.
    deal(
        address(morphoVault),
        vaultUser,
        morphoVault.totalSupply() / 10
    );

    vm.prank(vaultUser);
    morphoVault.redeem(
        morphoVault.balanceOf(vaultUser),
        vaultUser,
        vaultUser
    );

    // The programmable borrower position remains economically covered, so
    // onStopEpoch enters the withdraw path instead of the insolvency/default path.
    uint256 borrowerAssets = morphoVault.convertToAssets(
        morphoVault.balanceOf(address(programmableBorrower))
    );
    assertGe(borrowerAssets, pending, "position still covers withdrawal");

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.expectRevert(
        abi.encodeWithSelector(StopEpochVaultLiquidityUnavailable.selector)
    );
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Settlement is frozen: no default, epoch remains active, and the same
    // pending withdrawals remain unfunded.
    assertFalse(cdoEpoch.defaulted());
    assertTrue(cdoEpoch.isEpochRunning());
    assertTrue(programmableBorrower.epochAccountingActive());
    assertEq(strategy.pendingWithdraws(), pending);
}

  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
    emit EpochAccountingStarted(startAssets);

  /// @notice Hook called by IdleCDOEpochVariant before stopping an epoch.
  /// Withdraws enough liquidity from the vault so IdleCDO can pull funds.
  /// @param _amountRequired total amount IdleCDO will pull via transferFrom.
  /// @param _isRequestingAllFunds whether IdleCDO is closing the pool and recalling all funds.
  /// @return success false when the borrower ledger makes close-pool settlement a real default.
  function onStopEpoch(uint256 _amountRequired, bool _isRequestingAllFunds) external nonReentrant returns (bool success) {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // if we want to close the pool and the borrower still owes any amount, consider it a failure and let IdleCDO handle it as a default instead of a close. 
    if (_isRequestingAllFunds && (borrowerPrincipal != 0 || borrowerInterestDebt != 0 || borrowerInterestAccrued != 0)) {
      return false;
    }

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (_amountRequired > onHand) {
      uint256 shortfall = _amountRequired - onHand;
      // If the vault shares do not economically cover the shortfall, let IdleCDO's later
      // transferFrom fail and use the existing default path. Only an otherwise-covered ERC4626
      // withdrawal failure should make stopEpoch retryable.
      if (shortfall > _currentVaultAssets()) return true;
      try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        if (epochAccountingActive) {
          epochWithdrawnFromVault += shortfall;
        }
        emit WithdrawnFromVault(shortfall, shares, address(this));
      } catch {
        revert StopEpochVaultLiquidityUnavailable();
      }
    }

    // `totalInterestDueNow()` was already read by IdleCDO before calling this hook, so once the
    // stop flow begins we can clear the previous carry and snapshot the remaining vault sleeve
    // as the baseline for measuring buffer-period vault PnL before the next epoch starts.
    bufferedVaultDelta = 0;
    bufferInterest = 0;
    bufferStartVaultAssets = _currentVaultAssets();

    // Stop reserving epoch-end withdraw liquidity once IdleCDO has started the stop flow.
    epochPendingWithdraws = 0;
    epochAccountingActive = false;
    emit EpochAccountingStopped();
    success = true;
  }
