### Title
Overlong `instantWithdrawDelay` permanently gates `stopEpoch` while an epoch is running - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`instantWithdrawDelay` and `epochDuration` are independently configurable, but `stopEpoch` cannot execute while `pendingInstantWithdraws` is nonzero and `getInstantWithdrawFunds` cannot clear them before `instantWithdrawDeadline`. If `instantWithdrawDelay > epochDuration`, an ordinary instant-withdraw request creates a running epoch that cannot be stopped at `epochEndDate`; because the parameter setter is disabled while the epoch pauses the pool, the lock cannot be corrected until the misconfigured deadline expires. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`setInstantWithdrawParams` accepts any `_delay` and does not compare it with `epochDuration`. [1](#0-0)  During the buffer phase, a lender’s `requestWithdraw` is routed to `requestInstantWithdraw` when the new unscaled APR falls by more than `instantWithdrawAprDelta`. [4](#0-3)  The strategy then records the receipt and increases global `pendingInstantWithdraws`. [5](#0-4) 

`startEpoch` sets `instantWithdrawDeadline = start + instantWithdrawDelay`, while `epochEndDate = start + epochDuration`. [6](#0-5)  At `epochEndDate`, `stopEpoch` rejects every call while `_pendingInstant() != 0`. [2](#0-1)  The only normal funding path, `getInstantWithdrawFunds`, rejects until `instantWithdrawDeadline`, creating the unsatisfiable window `epochEndDate <= now < instantWithdrawDeadline`. [7](#0-6) 

### Impact Explanation
A lender can turn the misconfiguration into a live freeze with one unprivileged instant-withdraw request. Once the epoch starts, all active principal remains with the borrower, pending normal withdrawals cannot be funded, and tranche holders cannot enter the next withdrawal cycle until `instantWithdrawDelay - epochDuration` after maturity. For example, a 30-day epoch configured with a 395-day instant delay freezes epoch settlement for approximately 365 additional days. The lock is not merely operational because the same paused state prevents the owner or manager from reducing the delay through `setInstantWithdrawParams`. [1](#0-0) [8](#0-7) 

### Likelihood Explanation
The trigger requires an honest owner or manager to configure an instant delay longer than the epoch and leave instant withdrawals enabled, matching the accidental-configuration bug class. An unprivileged KYC-passing tranche holder can then create the blocking `pendingInstantWithdraws` balance during the buffer period after an APR reduction. Existing guards do not prevent it: the request is intentionally allowed, `startEpoch` does not validate `instantWithdrawDelay <= epochDuration`, and `stopEpoch` correctly enforces the pending-instant invariant. [9](#0-8) [10](#0-9) 

### Recommendation
Enforce `instantWithdrawDelay <= epochDuration` whenever either parameter is updated, or allow instant funding to be requested no later than `epochEndDate`. Alternatively, make `stopEpoch` able to pull and settle pending instant withdrawals after `epochEndDate` even when `instantWithdrawDeadline` has not elapsed. At minimum, `stopEpochWithDuration` should atomically validate the next duration against the configured instant delay before committing epoch state. [11](#0-10)

pragma solidity 0.8.10;

import "./TestIdleCDOBase.sol";

contract InstantDelayBlocksStopEpochTest is TestIdleCDOBase {
  function testInstantDelayLongerThanEpochBlocksStop() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Honest manager: 30-day epoch, 395-day instant deadline, instant requests enabled.
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(30 days, 5 days);
    cdoEpoch.setInstantWithdrawParams(395 days, 1, false);
    vm.stopPrank();

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Finish epoch 0 with a lower next APR so the next request is instant.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Unprivileged lender creates pendingInstantWithdraws.
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), 0);

    // Epoch 1 starts normally.
    _startEpochAndCheckPrices(1);

    // At maturity, neither funding path nor stopEpoch can proceed.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    assertLt(block.timestamp, cdoEpoch.instantWithdrawDeadline());

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.getInstantWithdrawFunds();

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr / 2, 0);

    // The pause also prevents correcting the bad delay while funds remain locked.
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.setInstantWithdrawParams(1 days, 1, false);

    // Settlement remains blocked for delay - duration after epoch maturity.
    vm.warp(cdoEpoch.instantWithdrawDeadline() - 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.getInstantWithdrawFunds();

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr / 2, 0);
  }
}

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
