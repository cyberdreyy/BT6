### Title
Stale rejection weight is never retracted when a signer later re-evaluates and accepts the same block, letting a validly-signed block be counted as globally rejected - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`should_reevaluate_reject_reason` (`stacks-signer/src/v0/signer.rs`) explicitly permits a signer that previously rejected a block (e.g. for `ConnectivityIssues`, `NoSignerConsensus`, `NoSortitionView`, `ConsensusHashMismatch`, `TestingDirective`, `InvalidTenureExtend`, `NotRejected`, or `Unknown`) to re-evaluate the exact same `BlockProposal` and, if conditions have changed, send a fresh `BlockAccepted` for it. On the node side, `StackerDBListener::run_loop` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`) tallies these two response kinds using two different "already counted" guards: rejections are gated on `block.responded_signers.insert(slot_id)`, while acceptances are gated on `!block.gathered_signatures.contains_key(&slot_id)`. Because these two guards are independent, a signer that first rejects and later accepts the *same* block has its weight added to **both** `total_weight_rejected` and `total_weight_approved`, and the stale rejection weight is never removed. This breaks the invariant that `total_weight_approved + total_weight_rejected` should never exceed `total_weight` for votes on a single block, and — because the rejection branch is evaluated before the approval branch in `SigningCoordinator::wait_for_signer_blocks_or_timeout` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) — can cause a block that has actually reached the legitimate 70% acceptance threshold to instead be declared globally rejected (`NakamotoNodeError::SignersRejected`) due to leftover, stale rejection weight.

### Finding Description
`stackerdb_listener.rs` maintains, per proposed block (`BlockStatus`, keyed by `signer_signature_hash`), `total_weight_approved`, `total_weight_rejected`, `gathered_signatures` (accept-only) and `responded_signers` (any response).

3. This time validation succeeds and the signer sends `BlockAccepted` for the **same** `H`. Node: `gathered_signatures.contains_key(slot)` is `false` (never inserted before) → `total_weight_approved += w` is added *in addition to* the already-recorded `total_weight_rejected += w` from step 1. Nothing ever subtracts the stale rejection weight.

The result: for this one block, `total_weight_approved + total_weight_rejected` now exceeds `total_weight` by `w`. If enough signers independently go through this reject→accept sequence (each on their own, no collusion or majority-signer compromise needed — only a single flip-flopping honest signer is required to create *some* skew, and every additional signer that legitimately reconsiders adds more), the rejected tally can spuriously cross the blocking-minority threshold at the exact same time the approved tally legitimately crosses 70%.

`SigningCoordinator::wait_for_signer_blocks_or_timeout` checks rejection before approval:
```rust
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ...
    return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    ...
    return Ok(...)
}
``` [4](#0-3) 
Because rejection is checked first, stale rejection weight left over from signers who have since accepted the very same block can cause the node to treat a block as globally rejected even though the current, up-to-date signer votes show it crossed the 70% approval threshold. This directly breaks the "aggregated weight vs. verified accepts" equality the report's bug class targets: the node's rejection tally no longer reflects the signers' current (verified) opinions — it is polluted by stale, superseded votes that were never retracted.

### Impact Explanation
This is a liveness break with safety-adjacent consequences: a block that legitimately reached the 70% signature threshold from currently-valid signer opinions can be discarded as `SignersRejected`, wedging tenure progress and forcing the miner to fail the block-commit / re-propose, even though no majority of signers actually oppose the block at evaluation time. It maps to the report's impact class "a rejection recounted as an accept" (here, inverted: an accept fails to retract the earlier stale rejection, corrupting the rejection tally) and to the "aggregated weight vs. verified-accepts" equality break explicitly called out in scope. It requires only ordinary protocol-sanctioned re-evaluation behavior (driven by proposal re-broadcast/gossip and possibly transient connectivity conditions the miner can influence by timing its re-proposals) rather than a majority of colluding signers.

### Likelihood Explanation
The reject→accept path for the same block is a normal, designed feature of the signer (`should_reevaluate_reject_reason` explicitly whitelists several reject reasons, including transient `ConnectivityIssues` and `NoSignerConsensus`, for re-consideration), so a single miner re-proposing an already-once-rejected block after some signers hit a transient rejection is a realistic and repeatable trigger, not a contrived edge case. The severity of the resulting corruption scales with how many signers went through the reject→accept cycle for that block, so the practical likelihood of it flipping the *outcome* of a specific block (rather than merely skewing the tallies by a small margin) depends on timing and how many signers experienced the transient condition — but even a partial skew degrades the correctness of the tally the node relies on to decide the fate of the block.

### Recommendation
Track approve/reject state per signer slot in a single map (e.g. `HashMap<slot_id, ResponseKind>`) instead of two independently-gated structures (`gathered_signatures` vs `responded_signers`). When a signer's response kind changes from reject to accept (or vice versa), retract the previously-tallied weight from the old bucket before adding it to the new one, so `total_weight_approved + total_weight_rejected` never exceeds `total_weight` for a single signer set.

### Proof of Concept
Not exploitable as a standalone PoC without a running signer/node harness, but the trigger sequence is deterministic given the code above:
1. Miner proposes block `H`.
2. Signer S evaluates `H`, hits a re-evaluable rejection reason (e.g. `RejectReason::ConnectivityIssues` or `NoSignerConsensus`) and broadcasts `BlockRejected(H)`. Node increments `total_weight_rejected` by S's weight via `stackerdb_listener.rs:515-518`.
3. Miner (or any relay) re-broadcasts the identical proposal `H`. Signer S's `should_reevaluate_block` → `should_reevaluate_reject_reason` returns `true` (`stacks-signer/src/v0/signer.rs:1505,1560-1571`), so S re-evaluates from scratch.
4. This time S's validation succeeds; S broadcasts `BlockAccepted(H)`. Node increments `total_weight_approved` by S's weight via `stackerdb_listener.rs:443-446`, because `gathered_signatures` never contained S's slot.
5. `total_weight_rejected` (from step 2) is never decremented, so `total_weight_approved + total_weight_rejected > total_weight` for block `H`, and depending on other signers' weights, `SigningCoordinator::wait_for_signer_blocks_or_timeout` (`signer_coordinator.rs:509-545`) may return `SignersRejected` for a block that in fact has ≥70% current approval weight.
