### Title
Multi-epoch withdraw receipts escape `stopEpochWithDuration` loss haircut and overdraw funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a partially-initialized variable: only part of `le_tmp64` is written, yet the whole 8-byte value is consumed as valid. The vault analog is `lossRecoveryPriceByEpoch` accounting in `IdleCreditVault`: `pendingWithdraws` is an aggregate across *all* user receipt epochs and is haircut in full by `collectWithdrawFunds`, but the loss-adjusted claim path only clears the basis of the single epoch stored in `lastWithdrawRequest[_user]`. Receipt basis recorded in earlier epochs is silently treated as fully funded and paid at par, so a user holding receipts from two epochs claims strictly more than the reserve funded for them.

### Finding Description
`requestWithdraw` lets a user stack receipts across epochs without claiming. The guard at `requestWithdraw` only blocks a new request when a loss price already exists for `lastWithdrawRequest[_user]`; when no loss has occurred yet, a user with an unclaimed epoch-N receipt can request again during the next buffer, moving `lastWithdrawRequest` to epoch N+1 while `withdrawsRequestsByEpoch[_user][N]` and `withdrawsRequestsByEpoch[_user][N+1]` both retain basis. `pendingWithdraws` accumulates both.

When the epoch-N+1 `stopEpoch` realizes a partial loss, `collectWithdrawFunds` funds only `pendingBasis * lossRecoveryPrice / 1e18` and stores `lossRecoveryPriceByEpoch[epochNumber]` once.

On claim, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which uses `lastWithdrawRequest[_user]` (N+1) and clears only `withdrawsRequestsByEpoch[_user][N+1]` via `_clearWithdrawClaimForEpoch`. The remaining `withdrawsRequests[_user]` balance — still containing the epoch-N basis — falls through to `_claimFundedWithdrawRequest`, which pays it **at par**. The correct payout was `(basis_N + basis_N+1) * price`; the actual payout is `basis_N + basis_N+1 * price`. The excess `basis_N * (1 - price)` is paid out of the same funded reserve that was sized only for the haircutted total, draining funds owed to other claimants (last claimers' `safeTransfer` underflows/reverts or the strategy is left short against `defaultRecoveryReserve`-style accounting).

### Impact Explanation
Direct theft / insolvency. With a 50% loss recovery price and an attacker holding an epoch-N receipt of X plus any epoch-N+1 dust receipt, the attacker extracts an extra `X * (1 - price)` underlying from the reserve. Since `collectWithdrawFunds` pulled exactly `pendingBasis * price`, every wei's worth of unhaircutted earlier-epoch basis is borne by other pending-receipt holders, whose claims then revert or are paid from strategy funds backing unrelated parties. Loss scales with the attacker's earlier-epoch receipt size, which the attacker fully controls by sizing their epoch-N request.

### Likelihood Explanation
Fully attacker-controllable sequence with honest privileged actors: deposit, request withdraw in epoch N, do not claim (explicitly supported — comment at line 323-324 documents re-requesting without claiming), request again in epoch N+1 buffer. Then any `stopEpochWithDuration`-style partial loss (borrower underfunding, which is a designed flow per `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds`) triggers the bug. The only external precondition is a partial-loss stopEpoch, a routine code path. No guard prevents it: the `lossRecoveryPrice` revert in `requestWithdraw` only fires if a loss already happened before the second request; the claim path has no check that the user has basis in other loss-marked epochs.

### Recommendation
Either force claim/settlement of all prior receipt epochs before allowing a new `requestWithdraw` (not only when a loss price exists for the last epoch), or make the loss claim iterate/aggregate all `withdrawsRequestsByEpoch` entries rather than only `lastWithdrawRequest`. Concretely, `_claimLossAdjustedWithdrawRequest` should haircut the user's *entire* outstanding `withdrawsRequests`/`apr0Users` basis when the funded pool was haircut on the aggregate, or `collectWithdrawFunds` should store the price per contributing epoch and the funded-claim path must exclude basis from any epoch whose receipts were included in the haircutted `pendingBasis`.

### Proof of Concept
```solidity
// Foundry fork-style PoC sketch (setup mirrors test/foundry/IdleCreditVault.t.sol)
function testLossHaircutSkippedForEarlierEpochReceipt() external {
    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                       // attacker deposits AA
    _transferBurnedTrancheTokens(address(this), true);

    // Epoch N buffer: request withdraw #1, do not claim
    uint256 req1 = cdoEpoch.requestWithdraw(half, address(AAtranche));

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, apr, fullyFunded);   // no loss; receipt still unclaimed

    // Epoch N+1 buffer: request again (allowed; no lossRecoveryPrice exists)
    cdoEpoch.requestWithdraw(remaining, address(AAtranche));
    // lastWithdrawRequest[this] = N+1, withdrawsRequestsByEpoch has basis in N and N+1

    _startEpochAndCheckPrices(1);
    // borrower underfunds -> partial loss -> collectWithdrawFunds sets
    // lossRecoveryPriceByEpoch[N+1] = e.g. 0.5e18 and funds pendingBasis * 0.5
    deal(defaultUnderlying, borrower, fundedAmount);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(...);             // loss path

    uint256 pre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - pre;

    // got == req1 + req2*price  >  (req1+req2)*price  == amount actually funded
    assertGt(got, fundedShare, "epoch-N basis paid at par despite aggregate haircut");
    // subsequent claimant's claimWithdrawRequest now reverts on insufficient reserve
}
```
