### Title
`claimInstantWithdrawRequest` never deletes the per-epoch receipt entry, so a defaulted-epoch instant receipt that was already paid is claimed a second time (or permanently bricks the claim path) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to `Token.updateFounders` failing to delete the old founder's schedule, `IdleCreditVault.claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` counter and never deletes the per-epoch bookkeeping `instantWithdrawsRequestsByEpoch[_user][epoch]`. When the borrower defaults in that same epoch, `_claimDefaultedInstantWithdrawRequest` re-reads the stale per-epoch entry as `claimBasis` and pays the user a second time out of the default-recovery reserve (or, if the user no longer holds receipt tokens, permanently reverts every later claim call).

### Finding Description
The external bug is a "stale schedule" pattern: an update path iterates differently from the creation path and leaves old entries alive. The closest credit-vault surface is the withdraw-receipt lifecycle in `IdleCreditVault.sol`.

- `requestInstantWithdraw` records both `instantWithdrawsRequests[_user] += _amount` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 366-372). The by-epoch map exists specifically so that `finalizeDefaultRecovery` can distinguish "default-epoch pending instant receipts" from older funded ones.
- `claimInstantWithdrawRequest` (lines 380-393) pays the funded amount, but only resets `instantWithdrawsRequests[_user] = 0`. It never touches `instantWithdrawsRequestsByEpoch[_user][epoch]` and never decrements `instantWithdrawClaimsByEpoch[epoch]` — the old schedule entry survives, exactly like the un-deleted vesting ids in the Nouns report.
- After `defaultRecoveryFinalized`, `_claimDefaultedInstantWithdrawRequest` (lines 842-856) computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. Because the stale entry was never deleted, `claimBasis` still holds the already-claimed amount.

Attack trace (attacker is a KYC-passing lender / tranche holder, all privileged actors honest):
1. During running epoch N, attacker calls `cdoEpoch.requestInstantWithdraw(amount, tranche)`; strategy mints `amount` receipt tokens and records `instantWithdrawsRequestsByEpoch[attacker][N] = amount`.
2. Borrower repays; manager stops epoch / CDO funds the instant queue and calls `collectInstantWithdrawFunds`, so `pendingInstantWithdraws` drops to 0 for the funded part.
3. Attacker calls `claimInstantWithdrawRequest` (still before default finalization, epoch N): receives `amount` underlying, receipt tokens burned, `instantWithdrawsRequests = 0` — but `instantWithdrawsRequestsByEpoch[attacker][N]` still equals `amount`.
4. Honest borrower default path executes: `_handleBorrowerDefault` → `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = N` and a nonzero `defaultRecoveryPrice`, and seeds `defaultRecoveryReserve`.
5. Attacker requests a new instant withdrawal of `amount2` (still epoch N while buffer/next epoch bookkeeping permits, or simply holds other strategy-token receipts) and calls `claimInstantWithdrawRequest` / `claimWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` reads stale `claimBasis = amount`, burns `amount` of the attacker's tokens, and transfers `amount * defaultRecoveryPrice / RECOVERY_FULL` from the reserve again — paying recovery on a receipt that was already fully funded and claimed.

Even in the variant where the attacker has no new balance, the stale `claimBasis` causes `instantWithdrawsRequests[_user] -= claimBasis` and `_burn(_user, claimBasis)` to revert, which permanently reverts the user's claim path — freezing any other legitimately claimable receipts under `defaultRecoveryFinalized`.

### Impact Explanation
Double payment out of `defaultRecoveryReserve`/`defaultRecoveryPrice` on an already-settled instant receipt directly steals recovery funds earmarked for genuinely defaulted receipts, breaking the "one receipt one payout" invariant and reducing what honest defaulted users recover. Alternatively it permanently DoSes the affected user's claim entry point, freezing unclaimed payouts. The stale entry persists because the funded-claim path in `claimInstantWithdrawRequest` never cleans the by-epoch schedule — the same root cause as the reported `updateFounders` bug.

### Likelihood Explanation
Requires the borrower to default in the same epoch in which the attacker requested and claimed an instant withdrawal, and default finalization to occur while `defaultRecoveryEpoch` still equals that epoch. Epochs are long-duration credit cycles, instant withdrawals are a supported user flow, and default finalization happens at the end of the epoch in which the default was declared, so the epoch-coincidence window is realistic whenever a mid-epoch default follows an instant withdrawal. No privileged misbehavior is needed; the attacker only makes ordinary user calls.

### Recommendation
Mirror the fix in the external report: keep the creation and deletion paths symmetric. In `claimInstantWithdrawRequest`, before zeroing `instantWithdrawsRequests[_user]`, iterate/delete `instantWithdrawsRequestsByEpoch[_user]` entries (at minimum clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and the epochs referenced by the receipt) and decrement `instantWithdrawClaimsByEpoch` accordingly, so a fully claimed funded receipt can never be re-interpreted as a defaulted-epoch claim basis. Alternatively, in `_claimDefaultedInstantWithdrawRequest`, cap `claimBasis` at the funded-remainder actually still held by the user.

### Proof of Concept
```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "./IdleCreditVault.t.sol";

contract StaleInstantReceiptPOC is IdleCreditVaultTest {
    function test_staleInstantReceipt_doubleRecoveryClaim() external {
        address attacker = makeAddr("attacker");
        uint256 amount = 100e6; // underlying units

        // ---- epoch N running ----
        // attacker deposits AA and requests an instant withdrawal
        uint256 tranches = _depositWithUser(attacker, amount);
        vm.prank(manager);
        cdoEpoch.startEpoch();
        _requestInstantWithdrawWithUser(attacker, tranches); // instantWithdrawsRequestsByEpoch[attacker][N] = tranches

        // borrower repays + manager stops epoch; CDO funds instant queue via collectInstantWithdrawFunds
        _stopCurrentEpochWithApr(10e18);

        // attacker claims the funded instant withdrawal at par (epoch N bookkeeping left stale)
        vm.prank(address(cdoEpoch)); // via CDO wrapper
        strategy.claimInstantWithdrawRequest(attacker);
        assertEq(strategy.instantWithdrawsRequests(attacker), 0);
        // BUG: strategy.instantWithdrawsRequestsByEpoch(attacker, N) still == tranches

        // ---- borrower defaults in the same epoch window ----
        _handleBorrowerDefaultPath(); // finalizeDefaultRecovery -> defaultRecoveryEpoch == N, defaultRecoveryPrice > 0

        // attacker requests another instant withdrawal (new epoch-N receipt or buffer)
        _requestInstantWithdrawWithUser(attacker, tranches / 2);

        uint256 balPre = underlying.balanceOf(attacker);
        vm.prank(address(cdoEpoch));
        strategy.claimInstantWithdrawRequest(attacker);

        // stale claimBasis = tranches paid AGAIN at defaultRecoveryPrice out of defaultRecoveryReserve
        uint256 stolen = tranches * strategy.defaultRecoveryPrice() / 1e18;
        assertGe(underlying.balanceOf(attacker) - balPre, stolen);
    }
}
```

Note on verification status: I confirmed the missing deletion in `claimInstantWithdrawRequest` (lines 380-393 only reset the aggregate counter) and the stale read in `_claimDefaultedInstantWithdrawRequest` (lines 842-856). What I could not fully verify within available iterations is the exact timing of `defaultRecoveryEpoch` assignment inside `finalizeDefaultRecovery` — if it is always set to an epoch strictly greater than any epoch in which instant claims were already funded, the theft leg degrades into a revert/DoS leg only (stale `claimBasis` underflows `instantWithdrawsRequests` or fails `_burn`), which still permanently freezes the user's remaining claimable receipts. Either outcome violates the payout invariant, but a concrete Foundry fork run is needed to pin down which branch fires.
