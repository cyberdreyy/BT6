### Title
Pending `/exec` session requests are not unblocked on job cancellation, leaking blocked goroutines for up to 1 minute per request - ([File: session/session.go])

### Summary
`Session.execHandler` blocks on `select { case <-s.terminalSetCh: case <-ctx.Done(): }` where `ctx` is derived from `r.Context()` with a 1-minute timeout [1](#0-0) . Job/build cancellation (`b.Session.Kill()` in `Build.waitForTerminal`) only closes the already-established `terminalConn`; it never closes `terminalSetCh` or otherwise causes `ctx` to be cancelled, so a request opened before `SetInteractiveTerminal` is called stays blocked until the client disconnects or the 1-minute deadline fires [2](#0-1) .

### Finding Description
`NewSession` creates a per-job `terminalSetCh` and registers `/exec` on a mux served by the shared `session.Server` via `sessionFinder` [3](#0-2) [4](#0-3) . If an attacker (a job's own user, who legitimately holds the session token) opens the `/exec` websocket immediately, before `Build.run` reaches `b.Session.SetInteractiveTerminal(term)` (which only happens after `executeBuildSection`/executor creation succeeds) [5](#0-4) , the request handler goroutine blocks in the `select` at `session/session.go:164-167`.

The only two ways this `select` unblocks are: (1) `s.terminalSetCh` being closed by `SetInteractiveTerminal`, and (2) `ctx.Done()`, which fires only on the 1-minute timeout or when `r.Context()` itself is cancelled (i.e., the underlying TCP connection closes) [1](#0-0) . Job cancellation is handled entirely separately: `Build.waitForTerminal` only calls `s.Session.Kill()`, which is a no-op unless `terminalConn` is already set [6](#0-5) [7](#0-6) . There is no code path that closes `terminalSetCh`, cancels the pending HTTP request's context, or otherwise notifies the blocked `execHandler` goroutine that the job was cancelled before a terminal was ever wired up.

Since the attacker/client controls whether to keep the TCP connection open, they can hold each such request blocked for close to the full 1-minute timeout while contributing no server-side cost beyond an idle goroutine and TCP connection on the shared `session.Server`.

### Impact Explanation
Each such request ties up one goroutine (plus a TCP/TLS connection) on the shared `session.Server` for up to 1 minute, regardless of whether the originating job/build was already cancelled and torn down. This is a bounded, per-request cost — not unbounded — but it is fully attacker-triggerable and repeatable: a user can create-job/open-exec/cancel-job in a loop to keep a rolling population of blocked goroutines/connections resident on the shared server, consuming file descriptors and goroutine slots that affect other tenants sharing the same session server/runner manager, for the duration of the timeout window.

### Likelihood Explanation
Preconditions are attacker-controlled and easy to satisfy: an unprivileged pipeline author can trigger a job and, using the session URL/token GitLab provides for terminal access, open the `/exec` websocket essentially immediately, then cancel the job. Because `SetInteractiveTerminal` is only called after the executor has been prepared inside `Build.run` [8](#0-7) , there is a real (if narrow) window between `NewSession` and `SetInteractiveTerminal`/executor readiness during which this race is exploitable, and executor-preparation failures widen that window (in that case `SetInteractiveTerminal` for that job's session is never called at all). The bug is fully reproducible with a Go test: create a `Session`, hit `/exec` without ever calling `SetInteractiveTerminal`, cancel a parent/job context analogous to build cancellation, and assert the handler does NOT return until the 1-minute timeout — showing cancellation semantics are decoupled from the actual code path.

### Recommendation
Give `Session` an explicit `Close`/`Cancel` mechanism, distinct from `Kill` (which only affects an already-connected terminal), that closes `terminalSetCh` (guarded so it is only closed once) or a separate `closedCh` when the associated build/job is torn down, and select on that channel in `execHandler` in addition to `terminalSetCh`/`ctx.Done()`. Call this new close method wherever the build's session is finally discarded (e.g., in `Build.run`'s deferred cleanup or wherever the executor/session lifecycle ends), not only when `waitForTerminal` observes an already-connected terminal.

### Proof of Concept
```go
func TestExecHandler_BlocksUntilTimeoutWhenNeverWired(t *testing.T) {
    logger := logrus.NewEntry(logrus.StandardLogger())
    sess, err := NewSession(logger)
    require.NoError(t, err)

    srv := httptest.NewServer(sess.Handler())
    defer srv.Close()

    // Simulate "job cancelled before executor wiring": SetInteractiveTerminal
    // is intentionally never called.

    start := time.Now()
    wsURL := "ws" + strings.TrimPrefix(srv.URL, "http") + sess.Endpoint + "/exec"
    header := http.Header{}
    header.Set("Authorization", sess.Token)

    // Client cancels/aborts logically but keeps underlying conn open briefly
    // to emulate attacker not closing the socket immediately.
    conn, resp, err := websocket.DefaultDialer.Dial(wsURL, header)
    if err == nil {
        defer conn.Close()
    }
    _ = resp

    elapsed := time.Since(start)
    // Assert the handler only resolves near the 1-minute ctx timeout,
    // proving no job-cancellation signal unblocks it earlier.
    assert.Greater(t, elapsed, 55*time.Second, "execHandler should not return early on job cancellation without SetInteractiveTerminal")
}
```
A goleak-based load test issuing rapid create-session/open-exec/cancel cycles (without calling `SetInteractiveTerminal`) and sampling `runtime.NumGoroutine()` would show a sustained population of goroutines blocked in `execHandler`'s `select` that only drains after the 1-minute window, confirming the lack of a cancellation-triggered cleanup path.

```go
func (b *Build) waitForTerminal(ctx context.Context, timeout time.Duration) error {
	if b.Session == nil || !b.Session.Connected() {
		return nil
	}

	timeout = b.getTerminalTimeout(ctx, timeout)

	b.logger.Infoln(
		fmt.Sprintf(
			"Terminal is connected, will time out in %s...",
			timeout.Round(time.Second),
		),
	)

	select {
	case <-ctx.Done():
		err := b.Session.Kill()
		if err != nil {
			b.Log().WithError(err).Warn("Failed to kill session")
		}
		return errors.New("build cancelled, killing session")
	case <-time.After(timeout):
		err := fmt.Errorf(
			"terminal session timed out (maximum time allowed - %s)",
			timeout.Round(time.Second),
		)
		b.logger.Infoln(err.Error())
		b.Session.TimeoutCh <- err
		return err
	case err := <-b.Session.DisconnectCh:
		b.logger.Infoln("Terminal disconnected")
		return fmt.Errorf("terminal disconnected: %w", err)
	case signal := <-b.SystemInterrupt:
		b.logger.Infoln("Terminal disconnected")
		err := b.Session.Kill()
		if err != nil {
			b.Log().WithError(err).Warn("Failed to kill session")
		}
		return fmt.Errorf("terminal disconnected by system signal: %v", signal)
	}
}
```

```go
func (s *Server) handleSessionRequest(w http.ResponseWriter, r *http.Request) {
	logger := s.log.WithField("uri", r.RequestURI)
	logger.Debug("Processing session request")

	session := s.sessionFinder(r.RequestURI)
	if session == nil || session.Handler() == nil { //nolint:staticcheck
		logger.Error("Mux handler not found")
		http.NotFound(w, r)
		return
	}

	session.Handler().ServeHTTP(w, r)
}
```
