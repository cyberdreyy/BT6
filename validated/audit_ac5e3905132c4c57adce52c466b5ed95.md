### Title
Inconsistent balance validation in `EVMTransfersController.Create` allows `ValidateEthBalanceForTransfer` bypass via relayer dispatch path - ([File: core/web/evm_transfer_controller.go])

### Summary
`EVMTransfersController.Create` dispatches to either `CreateEVMLegacy` or `CreateWithRelayer` depending on whether `tr.EVMChainID` resolves in `LegacyEVMChains()`. Only `CreateEVMLegacy` calls `ValidateEthBalanceForTransfer`; `CreateWithRelayer` calls `relayer.Transact` directly with no balance check at all, regardless of the `AllowHigherAmounts` flag.

### Finding Description
`Create` first attempts `getChain(tc.App.GetRelayers().LegacyEVMChains(), tr.EVMChainID.String())` [1](#0-0) . If that lookup fails (i.e., the requested `EVMChainID` is not present in the legacy chain set but is resolvable through `tc.App.GetRelayers().Get(...)`), execution falls into `CreateWithRelayer` instead of `CreateEVMLegacy`.

`CreateEVMLegacy` enforces the balance check: `if !tr.AllowHigherAmounts { err := ValidateEthBalanceForTransfer(...) }` [2](#0-1) .

`CreateWithRelayer`, however, never references `ValidateEthBalanceForTransfer` or any balance concept at all — it only fetches chain info and calls `relayer.Transact(c.Request.Context(), tr.FromAddress.String(), tr.DestinationAddress.String(), tr.Amount.ToInt(), !tr.AllowHigherAmounts)` [3](#0-2) . The last boolean argument (`!tr.AllowHigherAmounts`) is passed into the relayer's own `Transact` implementation, which lives outside this repository (in the `chainlink-evm`/loop relayer module) and is not visible/verifiable here — it is not guaranteed, and in this code path there is no local call to `ValidateEthBalanceForTransfer` at all.

Thus, for any `EVMChainID` that is absent from the legacy chain registry but present via the relayer registry, the request is routed to `CreateWithRelayer`, and the explicit balance-vs-fee check implemented in `ValidateEthBalanceForTransfer` (checking `chain.BalanceMonitor()`/`chain.Client().BalanceAt` against `amountWithFees`) is never executed in `core/web` — that logic is entirely bypassed at this layer [4](#0-3) .

### Impact Explanation
This is a real, code-level inconsistency: the financial safety check (`ValidateEthBalanceForTransfer`) exists on only one of the two dispatch branches of the same endpoint. An operator-facing transfer request routed to the relayer path skips node-side balance validation entirely, and whether any equivalent check happens downstream depends on relayer/`Transact` semantics not present in this repository. This matches the "unauthorized/oversized on-chain transfer bypassing balance validation" impact class for a financial-safety control that is supposed to apply uniformly.

### Likelihood Explanation
Exploitability requires only that the attacker (with credentials sufficient to reach `/v2/transfers`, as stated in the precondition) supply an `EVMChainID` that resolves via the relayer registry but not via `LegacyEVMChains()` — a configuration that is a normal/expected state during the documented legacy-to-relayer migration ("once we fully deprecate LegacyEVMChains we will switch to the relayer only" per the code comment) [5](#0-4) . No special exploit trickery is needed beyond selecting the right chain ID; this is reachable by any caller with adequate route authorization to `/v2/transfers` (as scoped by the question's stated precondition).

### Recommendation
Move the balance validation out of `CreateEVMLegacy` and perform it uniformly in `Create` (or in `CreateWithRelayer`) before dispatching to either transfer implementation, using relayer-agnostic balance retrieval (e.g., via `relayer`/chain client balance query) so the `AllowHigherAmounts`-gated check applies identically on both code paths.

### Proof of Concept
Table-driven test in `core/web/evm_transfer_controller_test.go`:
1. Configure `tc.App.GetRelayers()` such that `LegacyEVMChains()` lookup for a given `EVMChainID` fails, but `Get(types.RelayID{...})` succeeds with a mock relayer.
2. Mock relayer `Transact` to succeed unconditionally (simulate a relayer that does not itself enforce a balance check).
3. POST to the transfer endpoint with `Amount` far exceeding any funded balance and `AllowHigherAmounts=false`.
4. Assert that `CreateEVMLegacy`'s branch (using a legacy chain with insufficient balance) returns HTTP 422 via `ValidateEthBalanceForTransfer`, while the relayer-dispatched branch (same insufficient-balance scenario) currently returns success (200) — demonstrating the divergence and lack of a uniform check.

// ValidateEthBalanceForTransfer validates that the current balance can cover the transaction amount
func ValidateEthBalanceForTransfer(c *gin.Context, chain legacyevm.Chain, fromAddr common.Address, amount assets.Eth, toAddr common.Address) error {
	var err error
	var balance *big.Int

	balanceMonitor := chain.BalanceMonitor()

	if balanceMonitor != nil {
		balance = balanceMonitor.GetEthBalance(fromAddr).ToInt()
	} else {
		balance, err = chain.Client().BalanceAt(c, fromAddr, nil)
		if err != nil {
			return err
		}
	}

	zero := big.NewInt(0)

	if balance == nil || balance.Cmp(zero) == 0 {
		return fmt.Errorf("balance is too low for this transaction to be executed: %v", balance)
	}

	gasLimit := chain.Config().EVM().GasEstimator().LimitTransfer()
	estimator := chain.GasEstimator()

	amountWithFees, err := estimator.GetMaxCost(c, amount, nil, gasLimit, chain.Config().EVM().GasEstimator().PriceMaxKey(fromAddr), &fromAddr, &toAddr)
	if err != nil {
		return err
	}
	if balance.Cmp(amountWithFees) < 0 {
		// ETH balance is less than the sent amount + fees
		return fmt.Errorf("balance is too low for this transaction to be executed: %v", balance)
	}

	return nil
}
