### Title
Instant-withdraw receipts from epochs older than the default epoch are excluded from recovery accounting and permanently frozen - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` mirrors the CVE-2021-47602 bug class: like `mac80211` applying admission-control accounting only to "QoS data frames" while leaving other frame types in an untracked state, `finalizeDefaultRecovery` admits only *current-epoch* instant-withdraw receipts (`instantWithdrawClaimsByEpoch[epochNumber]`) into `defaultPendingClaimBasis`. Instant receipts created in an earlier epoch that are still unfunded when the borrower defaults are silently skipped by both the recovery path and the funded-claim path, so their holders can never claim.

### Finding Description
- `requestInstantWithdraw` records receipts per epoch in `instantWithdrawsRequestsByEpoch[user][epoch]` and aggregates them in `instantWithdrawClaimsByEpoch[epoch]`, while `pendingInstantWithdraws` tracks only the still-unfunded remainder.
- `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — when `pendingInstantWithdraws != 0`. Receipts requested in epoch N that remain unfunded after the epoch rolls to N+1 contribute nothing to the recovery basis.
- `finalizeDefaultRecovery` computes `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over that incomplete basis and sets `defaultInstantWithdrawsFinalized = true`.
- On claim, `_claimDefaultedInstantWithdrawRequest` reads only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`; it returns 0 for a receipt from an older epoch, clearing nothing.
- `claimInstantWithdrawRequest` then falls through to `instantWithdrawsRequests[user]` and calls `_transferFundedClaim`, whose guard `balance < reserve || balance - reserve < amount` reverts because after finalization the contract balance is dominated by `defaultRecoveryReserve`. There is no path that burns the stale receipt or pays a haircut.

Relevant code:
- `defaultPendingClaimBasis` — `IdleCreditVault.sol:644-649`
- `finalizeDefaultRecovery` / `defaultInstantWithdrawsFinalized` — `IdleCreditVault.sol:661-696`
- `_claimDefaultedInstantWithdrawRequest` (current-epoch only) — `IdleCreditVault.sol:842-856`
- `claimInstantWithdrawRequest` fallthrough and `_transferFundedClaim` reserve guard — `IdleCreditVault.sol:380-393`, `897-907`

### Impact Explanation
An unprivileged lender holding an instant-withdraw receipt from a pre-default epoch permanently loses the entire claim: no recovery payout (they were excluded from `totalBasis`, so no reserve was provisioned), and every `claimInstantWithdrawRequest` reverts via the reserve guard. The recovery reserve is also mispriced — `defaultRecoveryPrice` is inflated for admitted claimants because the old-epoch receipts were dropped from `totalBasis` while their collected funds remain stranded in the contract forever. Broken invariants: "one receipt one payout" and fair recovery distribution.

### Likelihood Explanation
Requires a specific sequence, but all steps are normal protocol operations by honest privileged roles plus one unprivileged attacker/victim action: (1) user calls `requestInstantWithdraw` in epoch N; (2) `startEpoch` moves only part of the instant queue's cash, leaving `pendingInstantWithdraws > 0` (the code explicitly documents this partial-funding case in `_defaultPrefundedInstantReserve`); (3) epoch rolls to N+1; (4) borrower defaults and the CDO finalizes recovery. No malicious privileged role is needed. The deterministic outcome once sequenced is permanent freezing of the receipt.

### Recommendation
Track instant-withdraw claim basis across all outstanding epochs, not only `epochNumber`. E.g., maintain a global `instantWithdrawClaims` aggregate (incremented in `requestInstantWithdraw`, decremented in `claimInstantWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`) and use it in `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`; correspondingly, `_claimDefaultedInstantWithdrawRequest` should iterate or fold all per-epoch receipts for the user, not just `defaultRecoveryEpoch`. Alternatively, block epoch rollover while `pendingInstantWithdraws != 0`.

// Foundry fork PoC sketch (test/foundry/)
// Setup: deploy IdleCDOEpochVariant + IdleCreditVault, AA deposit by user.
function test_StaleInstantReceiptFrozenOnDefault() external {
    // Epoch 0 running: user requests instant withdraw of X underlying.
    idleCDO.depositAA(10000e18);
    _startEpoch();                       // epochNumber = 0
    cdoEpoch.requestInstantWithdraw(X);  // instantWithdrawsRequestsByEpoch[user][0] = X
    // Honest manager funds only part of the instant queue at next startEpoch,
    // so pendingInstantWithdraws > 0 remains.
    _startEpochPartialInstantFunding();  // epochNumber = 1, pendingInstantWithdraws > 0
    // Borrower defaults during epoch 1; CDO finalizes recovery.
    cdoEpoch.stopEpochWithDuration(/* loss */);
    cdoEpoch._handleBorrowerDefault();
    strategy.finalizeDefaultRecovery(recovered, source);
    // defaultPendingClaimBasis used instantWithdrawClaimsByEpoch[1] only:
    // user's epoch-0 receipt contributed zero basis and got zero reserve share.
    // Claim path:
    //  - _claimDefaultedInstantWithdrawRequest: instantWithdrawsRequestsByEpoch[user][1] == 0 → no-op
    //  - funded path: _transferFundedClaim sees balance ~ defaultRecoveryReserve → revert
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();   // permanently bricked; receipt never burnable
}
