## Confirmed: cross-workflow / cross-owner cache key collision in `responseCache`

The full flow confirms this is real and directly reachable. `gatewayHandler.makeOutgoingRequest` unmarshals an `OutboundHTTPRequest` directly from a node's JSON-RPC response payload (attacker/node-controlled fields, only gated by per-node/global rate limiting, no per-workflow ownership check) and passes it straight to `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)` [1](#0-0) . The cache key used by `Fetch`, `Set`, and `isExpiredOrNotCached` is exactly `req.Hash()` with no workflow-scoping prefix added by the caller [2](#0-1) [3](#0-2) .

`OutboundHTTPRequest.Hash()` (in the `chainlink-common` dependency, not present as source in this repo's index) is proven by the existing unit test to omit `WorkflowID` from the hash while including `WorkflowOwner`: `TestRequestHash/having_different_workflowID_results_in_same_Hash` explicitly asserts `hash1 == hash2` for two requests differing only in `WorkflowID` [4](#0-3) . This directly contradicts the module's own documented design/security invariant: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [5](#0-4) .

However, `WorkflowOwner` *is* included in the hash and does differentiate cache entries (`TestRequestHash/having_different_workflowOwner_results_in_different_Hash`) [6](#0-5) . Since distinct workflows can share the same `WorkflowOwner` (an owner can deploy many workflows), the isolation gap is real: two different workflows belonging to the same owner (or, per the raw `Hash()` semantics, any two requests that happen to produce identical Method/URL/Headers/Body/WorkflowOwner but different WorkflowID) will collide in the cache, and workflow B's cached response is returned to workflow A's node via `Fetch`'s fast-path (`rc.cache[cacheKey]`) or singleflight path [2](#0-1) .

### Title
Cross-workflow response-cache key collision due to `OutboundHTTPRequest.Hash()` omitting `WorkflowID` - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The gateway's outbound HTTP response cache keys entries solely by `req.Hash()`, which per existing tests does not include `WorkflowID` (only `WorkflowOwner`, Method, URL, Headers, Body). Two distinct workflows under the same owner (or otherwise producing identical hash inputs) that issue outbound HTTP action requests with identical Method/URL/Headers/Body will share a single cache entry, allowing one workflow's cached HTTP response to be served to another workflow.

### Finding Description
`gatewayHandler.makeOutgoingRequest` deserializes an `OutboundHTTPRequest` from a node message and, when `CacheSettings.MaxAgeMs > 0`, calls `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)` with no additional workflow-scoping key [1](#0-0) . `responseCache.Fetch`/`Set`/`isExpiredOrNotCached` all key the internal `map[string]*cachedResponse` purely by `req.Hash()` [7](#0-6) [2](#0-1) [3](#0-2) . The confirmed test `having different workflowID results in same Hash` shows `WorkflowID` is excluded from the hash computation [4](#0-3) , while README documentation asserts the opposite guarantee (workflow-scoped cache isolation) [5](#0-4) . Because `WorkflowOwner` is included in the hash, full cross-owner leakage is prevented, but same-owner, cross-workflow leakage is not — an owner running multiple workflows (or a caller that can set an arbitrary/empty `WorkflowOwner` matching another workflow's owner value) that issue identical Method/URL/Headers/Body requests will collide on the same cache entry.

### Impact Explanation
This is a scoped confidentiality/integrity issue: workflow A can receive a cached HTTP response fetched for workflow B (data leakage across workflow boundaries) or, conversely, poison the cache for workflow B by causing its own request to be served under workflow B's key (response spoofing), as long as Method/URL/Headers/Body/WorkflowOwner line up. This matches a "cross-user response confusion" / broken workflow isolation impact class, scoped to workflows sharing the same owner (single-tenant isolation break, not full multi-tenant compromise, since `WorkflowOwner` is still checked).

### Likelihood Explanation
Preconditions: attacker needs only a valid node/gateway session capable of issuing `MethodHTTPAction` requests for a workflow it controls (an owner running two workflows performing outbound HTTP actions to the same URL, or a workflow whose fields can be crafted to collide with another's). No elevated privileges, DON quorum, or operator access needed — the request path goes through standard per-node rate limiting only [8](#0-7) . This is trivially and repeatably reproducible via unit test.

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`) in `OutboundHTTPRequest.Hash()`, or have `responseCache` derive its cache key from `WorkflowID + req.Hash()` instead of `req.Hash()` alone, restoring the documented workflow-scoped isolation.

### Proof of Concept
1. Unit test in `response_cache_test.go`: build two `OutboundHTTPRequest`s with identical Method/URL/Headers/Body/WorkflowOwner but different `WorkflowID`; assert `req1.Hash() == req2.Hash()` (already demonstrated by existing test at lines 139–149).
2. Handler-level integration test: call `cache.Set(req1, respA)` then `cache.Fetch(ctx, req2, fetchFnB, true)` and assert the fast path returns `respA` (workflow A's cached response) for workflow B's request instead of invoking `fetchFnB`, proving cross-workflow leakage via the shared cache key.

	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)

func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
