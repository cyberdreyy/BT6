### Title
Single-vault pending instant withdrawal reverts the atomic cluster-wide `stopEpochWithDuration` batch, freezing epoch settlement for all vaults - ([File: contracts/IdleCreditVaultManagerOrchestrator.sol](contracts/IdleCreditVaultManagerOrchestrator.sol))

### Summary
`IdleCreditVaultManagerOrchestrator.stopEpochWithDuration` iterates a list of credit vaults and calls `IdleCDOEpochVariant.stopEpochWithDuration` on each inside one atomic transaction, with no per-vault error isolation [1](#0-0) . `_stopEpoch` reverts whenever `_pendingInstant() != 0`, i.e. whenever unfunded instant-withdrawal receipts exist on that vault [2](#0-1) . Any KYC-passing lender holding tranche tokens can create such receipts via `requestWithdraw`, so one unprivileged user of one vault in the cluster can revert the whole batch and leave every other vault's epoch unstopped, even though those vaults are fully healthy and their borrowers funded.

### Finding Description
The analog to the Carapace `DefaultStateManager.assessStates` DoS (one pool's revert bricks the shared state-assessment loop) is the orchestrator's cluster batch:

- `startEpoch(address[])` and `stopEpochWithDuration(StopEpochWithDurationAction[])` are the cron-style maintenance entry points for the whole vault cluster. Both loop over vaults and let any inner revert bubble up, reverting the entire transaction [3](#0-2) .
- In `_stopEpoch`, the gate `_pendingInstant() != 0` forces a revert when instant-withdrawal requests were not funded by a prior `getInstantWithdrawFunds` call [4](#0-3) .
- Instant-withdrawal receipts are created by ordinary lenders through `requestWithdraw` during the buffer phase when the operator lowers the APR beyond `instantWithdrawAprDelta`; funding them requires a separate `getInstantWithdrawFunds` call which itself is only callable after `instantWithdrawDeadline` [5](#0-4) .

Attack sequence (running epoch, fixed-APR mode):

1. Operator stops epoch N of vault A with a lower `newApr`, opening the instant-withdraw window during the buffer.
2. Attacker (whitelisted lender) calls `requestWithdraw` on vault A, creating a pending instant-withdraw receipt.
3. Operator starts epoch N+1 and later calls `getInstantWithdrawFunds` — but if the borrower has not yet returned enough, or the operator's batch runs before `instantWithdrawDeadline` passes for the next cycle, `_pendingInstant()` stays non-zero. More importantly, the attacker can keep a receipt pending into the next stop: instant requests can be re-opened each cycle the APR is lowered.
4. When the operator calls `orchestrator.stopEpochWithDuration([A, B, C, ...])`, `cdo.stopEpochWithDuration` on vault A reverts with `NotAllowed`, and the whole transaction reverts — vaults B, C, ... keep `isEpochRunning = true` past `epochEndDate`, their pending normal-withdrawal receipts remain unfunded in `IdleCreditVault.pendingWithdraws`, and no lender on any vault can claim.

The invariant broken is availability of the shared epoch-settlement path: a per-vault, user-controllable precondition (`_pendingInstant() != 0`) poisons a cluster-wide atomic loop. Note the same revert applies to the `startEpoch` batch via `OrchestratorStartFailed` if any vault fails its post-checks [6](#0-5) .

### Impact Explanation
Temporary freezing of funds across the entire vault cluster: every vault in the batch has its epoch settlement blocked until the offending vault's instant-withdraw receipts are funded (operator must call `getInstantWithdrawFunds` after `instantWithdrawDeadline` and only if the borrower has liquidity) or removed from the batch. During the freeze, pending normal-withdrawal receipts on healthy vaults cannot be fulfilled and tranche holders cannot exit. Quantified loss = all `IdleCreditVault.pendingWithdraws` plus all active tranche NAV across the non-offending vaults for the duration of the freeze, i.e. effectively the whole cluster TVL is locked for at least one additional operator round-trip, and repeatedly re-lockable each time the APR is lowered. In the programmable-borrower mode this specific vector does not apply (instant withdrawals are disabled), but the atomicity flaw remains for any other per-vault revert such as `StopEpochVaultLiquidityUnavailable` from `onStopEpoch` [7](#0-6) .

### Likelihood Explanation
Requires only a KYC-passing lender with a tranche balance and an APR decrease (a routine operator action when rates fall — exactly when instant withdrawals exist by design). No privileged collusion needed. The mitigation exists (operator can pre-call `getInstantWithdrawFunds` and split batches), so this is a temporary rather than permanent freeze, matching Medium/High rather than Critical. Caveat: I could not fully confirm within the search budget whether `requestWithdraw` instant-receipt creation is additionally gated by `allowInstantWithdraw`/`disableInstantWithdraw` in a way that would narrow the window — the revert path in `_stopEpoch` is confirmed, but the exact set of epochs in which a lender can hold a pending instant receipt into `stopEpoch` should be verified in a PoC.

### Recommendation
Make the batch loops fault-isolated: wrap each `cdo.stopEpochWithDuration(...)` / `cdo.startEpoch()` in `try/catch`, emit a per-vault failure event, and continue (optionally with a strict mode flag). Additionally, have the orchestrator call `getInstantWithdrawFunds` for each vault before stopping, or reorder `_stopEpoch` so the pending-instant check is a skip rather than a hard revert for cluster operations.

pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract OrchestratorBatchDoSTest is Test {
    // reuse IdleCreditVault.t.sol harness: cdoA, cdoB registered in orchestrator,
    // operator == manager of both vaults, this contract = whitelisted lender on cdoA

    function testSingleVaultPendingInstantBlocksClusterStop() external {
        // 1. deposits + epoch running on cdoA and cdoB
        // 2. operator stops cdoA epoch with LOWER apr -> instant window opens
        // 3. attacker (this) calls cdoA.requestInstantWithdraw / requestWithdraw
        //    leaving pendingInstant > 0 into the next cycle
        // 4. warp past epochEndDate for both vaults
        IdleCreditVaultManagerOrchestrator.StopEpochWithDurationAction[] memory ops =
            new IdleCreditVaultManagerOrchestrator.StopEpochWithDurationAction[](2);
        ops[0] = _action(address(cdoA));
        ops[1] = _action(address(cdoB));

        vm.prank(operator);
        vm.expectRevert(NotAllowed.selector); // from cdoA _stopEpoch _pendingInstant() != 0
        orchestrator.stopEpochWithDuration(ops);

        // cdoB is healthy and funded, yet remains unstopped
        assertTrue(cdoB.isEpochRunning(), "healthy vault frozen by batch revert");
        assertGt(strategyB.pendingWithdraws(), 0, "pending withdraws unfunded");
    }
}
