### Title
Loss-adjusted withdrawal haircut is keyed to the user's *last* request epoch, so multi-epoch pending receipts escape `lossRecoveryPriceByEpoch` and are paid at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.collectWithdrawFunds` stores a stop-epoch loss haircut under `lossRecoveryPriceByEpoch[epochNumber]` (the epoch being stopped), while `_claimLossAdjustedWithdrawRequest` looks the haircut up via `lastWithdrawRequest[_user]` — a single-slot pointer that only holds the user's *most recent* request epoch. Because `pendingWithdraws` is a global aggregate of *all* pending receipts, a partial funding loss is priced against receipts from multiple epochs, but only the receipts whose basis sits in `lastWithdrawRequest[_user]`'s epoch are ever haircut. Receipts from earlier epochs — or the entire receipt when the pointer misses the loss epoch — fall through to `_claimFundedWithdrawRequest` and are paid 1:1, overpaying the attacker relative to the funded reserve and leaving later claimants unpayable. This mirrors the Tomcat bug class: a receipt is settled under terms associated with a different request/epoch than the one that actually priced it.

### Finding Description
Relevant code:

- `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`): on a shortfall (`_amount < pendingBasis`) it sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`. `epochNumber` here is the epoch whose `stopEpochWithDuration` realized the loss, and `pendingBasis` aggregates receipts requested in *any* prior epoch.
- `requestWithdraw` (`IdleCreditVault.sol:259-294`): updates `lastWithdrawRequest[_user] = currentEpoch` on every request and records basis per-epoch in `withdrawsRequestsByEpoch[_user][currentEpoch]`. The guard at lines 263-271 only blocks a *new* request when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` — i.e., it only detects a haircut on the single most recent epoch.
- `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`): reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and clears only that epoch's basis via `_clearWithdrawClaimForEpoch` (`IdleCreditVault.sol:811-837`), which zeroes `withdrawsRequestsByEpoch[_user][_claimEpoch]` but deliberately leaves older basis in `withdrawsRequests[_user]`.
- `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-350`): once `epochNumber > lastWithdrawRequest[_user]`, pays the full remaining `withdrawsRequests[_user]` plus APR0 buckets at par via `_transferFundedClaim`.

Attack trace (running pool, `stopEpochWithDuration` loss mode):

1. Epoch 5 buffer: attacker calls `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw` records basis under epoch 5; `lastWithdrawRequest = 5`.
2. Epoch 5 `stopEpoch` succeeds fully (no loss); `epochNumber` bumps. The attacker does not claim (claiming is optional; nothing forces it).
3. Epoch 6 buffer: attacker requests again. The loss check at lines 263-271 uses `lossEpoch = 5`, `lossRecoveryPriceByEpoch[5] == 0`, so it passes; `lastWithdrawRequest` is overwritten to 6. `pendingWithdraws` now aggregates epochs 5 + 6.
4. Epoch 6 `stopEpochWithDuration(_lossAmount)` realizes a loss. `previewLossAdjustedWithdrawFunds` splits the loss pro-rata across `pendingBasis` (which includes the epoch-5 receipt); the borrower funds `pendingToFund < pendingBasis`; `collectWithdrawFunds` stores the haircut at `lossRecoveryPriceByEpoch[6]` and zeroes `pendingWithdraws`.
5. Attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` uses `lossEpoch = lastWithdrawRequest = 6`, clears **only** `withdrawsRequestsByEpoch[6]` and pays it at the haircut price.
   - `_claimFundedWithdrawRequest` then passes (`epochNumber > lastWithdrawRequest`, which `_clearWithdrawClaimForEpoch` reset to 0 at line 832-836) and pays the **epoch-5 basis at par**, even though the epoch-5 basis was part of the loss-bearing `pendingBasis` and the strategy only collected the haircut amount for it.

A second, worse variant: if the attacker's *last* request epoch differs from the loss epoch entirely (e.g., requests in epochs 5 and 6, loss realized at the epoch-7 stop while `lastWithdrawRequest == 6`), then `lossRecoveryPriceByEpoch[6] == 0`, `_claimLossAdjustedWithdrawRequest` returns 0, and the **entire** aggregate claim is paid at par by `_claimFundedWithdrawRequest`.

The only payout guard, `_transferFundedClaim` (`IdleCreditVault.sol:897-907`), checks `balance - defaultRecoveryReserve >= _amount` — and only when `defaultRecoveryReserve != 0`. In the loss-adjusted (non-default) path the reserve is 0, so the overpayment succeeds and drains underlying collected for other users' receipts; subsequent claimants hit `safeTransfer` failures on an empty balance.

### Impact Explanation
The haircut funded by the borrower is `pendingBasis - pendingLoss` for the *aggregate* bucket, but the attacker is paid `haircut(epoch-6 part) + par(epoch-5 part)` — more than the reserve holds for those receipts once other users also claim. Concretely, with `pendingBasis = 200` split evenly between the attacker's epoch-5 receipt (100) and epoch-6 receipt (100) and a 20% loss, the strategy collects 160, but the attacker receives `100*0.8 + 100 = 180` — a 20-unit overpayment taken directly from underlying earmarked for other users' funded claims. Those users' `claimWithdrawRequest` calls then revert on insufficient balance: permanent freezing/theft of their unclaimed withdrawals. Broken invariants: fair burn/payout (one receipt one correctly-priced payout) and solvency of the funded-withdrawal reserve.

### Likelihood Explanation
Likelihood is moderate. It requires a `stopEpochWithDuration` partial-loss event, which is an honest manager/owner action used precisely when the borrower underpays — a realistic scenario in a credit vault. The attacker needs only to be a KYC-passing tranche holder who makes withdraw requests in two different epochs without claiming — behavior the code explicitly permits ("if a user does not claim... he will have to wait for another epoch to claim both requests", comment at `IdleCreditVault.sol:323-324`). No privileged role, no oracle manipulation, no reentrancy is needed. The loss magnitude scales with the older-epoch basis the attacker can accumulate, bounded only by their tranche holdings and the number of elapsed epochs.

### Recommendation
Do not key the loss haircut to a per-user `lastWithdrawRequest` pointer. Either:

- Iterate all epochs with nonzero `withdrawsRequestsByEpoch[_user][*]` when applying `lossRecoveryPriceByEpoch`, applying the haircut to every basis that contributed to the lossed `pendingBasis` (e.g., track which epochs' receipts were pending at each `collectWithdrawFunds` call, or store a per-user list of request epochs); or
- Make `collectWithdrawFunds` stamp the haircut onto each contributing epoch (requires tracking per-epoch pending totals, e.g., `pendingWithdrawsByEpoch`), and have the claim path check *every* epoch basis against its own recovery price before allowing the par claim; and
- Strengthen the `requestWithdraw` guard so that a new request is blocked while *any* prior epoch basis of the user carries an unclaimed loss haircut, not only the epoch referenced by `lastWithdrawRequest`.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_requestWithdrawWithUser`):

```solidity
function testMultiEpochReceiptEscapesLossHaircut() external {
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Epoch 5: request withdraw #1 (buffer), then run a clean stopEpoch
    _startEpochAndCheckPrices(0);
    uint256 req1 = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 4, address(AAtranche));
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Epoch 6: request withdraw #2 WITHOUT claiming req1 -> lastWithdrawRequest overwritten to 6
    uint256 req2 = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 4, address(AAtranche));

    // Epoch 6 stop realizes a loss: borrower underpays pendingWithdraws
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws(); // = req1 + req2
    uint256 loss = pending * 20 / 100;                                     // 20% loss on pending bucket
    deal(defaultUnderlying, borrower, /* active interest + */ pending - loss);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, /* interest */, /* duration */, loss); // stores lossRecoveryPriceByEpoch[6]

    // Claim: epoch-6 basis is haircut, epoch-5 basis is paid AT PAR
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    uint256 haircutPrice = IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(6);
    uint256 expected = req1 * haircutPrice / 1e18 + req2 * haircutPrice / 1e18; // correct payout
    assertGt(paid, expected, 'attacker overpaid: epoch-5 receipt escaped haircut');
    // paid == req1 + req2 * haircutPrice / 1e18  ->  overpay == req1 * (1 - haircutPrice/1e18)
}
```

Expected result: `paid` exceeds the loss-adjusted entitlement by `req1 * (RECOVERY_FULL - haircutPrice) / RECOVERY_FULL`; a second claimant's `claimWithdrawRequest` then reverts or underpays because the strategy's underlying was drained.

Uncertainty noted: exact helper names/`stopEpochWithDuration` signature in `IdleCDOEpochVariant` were not fully re-verified within the search budget, but the vulnerable data flow — haircut stored under `epochNumber` (line 421), looked up via `lastWithdrawRequest` (line 790), and only that epoch's basis cleared (lines 815-820) while the par claim path pays the remainder (lines 338-349) — is directly confirmed in `IdleCreditVault.sol`.
