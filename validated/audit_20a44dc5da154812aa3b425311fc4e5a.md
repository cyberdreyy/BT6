### Title
Gloas `apply_withdrawals()` mints unbacked Gwei when a builder's committed withdrawal amount exceeds its current balance - ([File: specs/gloas/beacon-chain.md])

### Summary
The bug pattern described in the Magnetar report — a withdrawal request derived from a *requested/committed amount* that can silently diverge from the amount actually available to withdraw — has a direct analog in the Gloas builder-withdrawal pipeline. `get_builder_withdrawals()` copies the *requested* `BuilderPendingWithdrawal.amount` verbatim into the `Withdrawal.amount` field that is committed to `state.payload_expected_withdrawals` (and thus must be honored exactly by the execution layer), while `apply_withdrawals()` only deducts `min(withdrawal.amount, builder_balance)` from the builder's consensus-layer balance. When the requested amount exceeds the builder's current balance, the execution layer is instructed to pay the *full requested amount* to `fee_recipient`, but the beacon state only burns the (smaller, capped) available balance — creating Gwei that is paid to a party without a corresponding decrease anywhere in state.

### Finding Description
`get_builder_withdrawals` builds each `Withdrawal` straight from the queued amount, without capping to the builder's balance: [1](#0-0) 

That withdrawal list becomes `state.payload_expected_withdrawals`, which the execution layer is required to honor byte-for-byte (per Engine API semantics, each `Withdrawal.amount` is credited directly to `Withdrawal.address`): [2](#0-1) 

But the *balance deduction* applied on the consensus side caps at the builder's current balance instead of using the full committed amount: [3](#0-2) 

This is exactly the same defect class as the Magnetar report: one code path computes/commits an amount (`removeAndRepayData.collateralAmount` / here, `BuilderPendingWithdrawal.amount` propagated into `Withdrawal.amount`), while a second, related deduction path derives a *different, potentially smaller* value (`collateralShare` via `toShare()` / here, `min(withdrawal.amount, builder_balance)`). In Magnetar the mismatch caused a revert (a safe failure); in the beacon spec there is no revert path at all — the smaller value is silently substituted only for the state mutation, while the larger, uncapped value continues on to be paid out via the execution payload. This breaks the invariant the spec itself calls out just above this code ("deferring the deduction ... would break the total supply invariant") — the invariant is violated exactly when `amount > balance`, since the payment (in the EL) and the burn (in the CL) diverge.

Reachability without any malicious/faulty peer: `builder_pending_withdrawals` entries are appended by `settle_builder_payment()` from previously-accepted bids, and by the "evicted payment" fallback path in `apply_parent_execution_payload()` when a bid's payment epoch has already rotated out of `builder_pending_payments`: [4](#0-3) [5](#0-4) 

Multiple bids from the same builder across different slots can each independently pass balance-sufficiency checks *at bid-acceptance time*, but all queue their withdrawals into `state.builder_pending_withdrawals`. Because `get_builder_withdrawals` can batch several entries for the *same* builder into a single block's withdrawal list (confirmed by the spec's own test coverage of duplicate-builder-index processing) without ever re-checking the builder's balance against the cumulative sum of amounts before emitting each `Withdrawal`, an honest builder whose balance is drawn down by earlier withdrawals in the same batch (or by a builder exit sweep withdrawing full balance concurrently) will have later withdrawals in the list still carry their full, uncapped requested amount into `payload_expected_withdrawals`, while `apply_withdrawals` deducts `min(amount, balance)` = 0 (or a small remainder) from an already-drained balance.

The repository's own test suite documents this exact effect as expected/intended behavior rather than flagging it as a bug: [6](#0-5) [7](#0-6) 

### Impact Explanation
This breaks the equality "Gwei paid out to an address == Gwei burned from the paying party's balance." When `withdrawal.amount > builder_balance`, the execution layer credits `fee_recipient` with the full `withdrawal.amount`, while the consensus layer only debits the smaller `builder_balance`. The difference is Gwei created out of thin air and paid to a non-owner (the fee_recipient), directly matching the Critical-impact category "Gwei created, destroyed or paid to a non-owner." This also is precisely the invariant the spec's own commentary on `apply_withdrawals` warns must not be broken.

### Likelihood Explanation
Medium-to-High: no malicious peer, coalition, or client bug is required — only ordinary sequencing of multiple honest builder payments/withdrawals for the same builder across slots/epochs such that the balance is insufficient by the time all queued withdrawals for that builder are drained in a single block's `get_builder_withdrawals` batch. The existing test suite already exercises and asserts this exact "insufficient balance → capped deduction but full requested amount in the withdrawal" behavior, indicating it is a real, reachable code path rather than a purely theoretical one.

### Recommendation
`get_builder_withdrawals` (or `apply_withdrawals`) should cap the `Withdrawal.amount` placed into `payload_expected_withdrawals` to `min(requested_amount, builder.balance)` at withdrawal-construction time (mirroring how `get_pending_partial_withdrawals` already caps validator partial withdrawals via `min(balance - MIN_ACTIVATION_BALANCE, amount)`), so the amount committed to the execution layer always equals the amount actually burned from the builder's balance in `apply_withdrawals`.

### Proof of Concept
1. Builder `B` submits two winning bids in consecutive slots, each for `10 ETH`, with `B.balance = 12 ETH` at bid-acceptance time for both (each individually passes any balance-sufficiency check at bid time).
2. Both payments settle into `state.builder_pending_withdrawals` as two `BuilderPendingWithdrawal(amount=10 ETH)` entries for builder `B` (via `settle_builder_payment` / the evicted-payment fallback), while `B.balance` remains `12 ETH` (no interim deduction happens at payment-queueing time).
3. In a subsequent block, `get_builder_withdrawals` processes both entries and emits two `Withdrawal` objects, each with `amount = 10 ETH` (20 ETH total), into `state.payload_expected_withdrawals` — this is what the execution layer will pay out to `fee_recipient`.
4. `apply_withdrawals` runs sequentially: first withdrawal deducts `min(10 ETH, 12 ETH) = 10 ETH`, leaving `B.balance = 2 ETH`; second withdrawal deducts `min(10 ETH, 2 ETH) = 2 ETH`, leaving `B.balance = 0`.
5. Net result: execution layer pays out `20 ETH` total to `fee_recipient` addresses, while the beacon state only burned `12 ETH` from builder `B`. `8 ETH` was created and paid out with no corresponding consensus-layer balance decrease anywhere in the system.

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()
