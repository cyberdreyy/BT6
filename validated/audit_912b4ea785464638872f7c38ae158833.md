### Title
Older-epoch pending withdraw receipts escape the `stopEpochWithDuration` loss haircut, over-claiming funded underlyings and insolventing same-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to a second-order injection (a benign-looking value stored under low privilege is later "executed" in a different trust context), an attacker can store a withdraw receipt in an earlier epoch and let it be paid out under a later epoch's context. When a subsequent `stopEpochWithDuration(_lossAmount)` applies a loss to the aggregate `pendingWithdraws`, `IdleCreditVault` only applies the stored `lossRecoveryPriceByEpoch` haircut to the user's **latest** request epoch. Any older still-pending receipts in the `withdrawsRequests` aggregate fall through to `_claimFundedWithdrawRequest` and are paid **at par**, so the attacker extracts more than their pro-rata share of the loss-adjusted pool, leaving the strategy underfunded for other claimants and active LPs.

### Finding Description
`requestWithdraw` records receipts both in the aggregate `withdrawsRequests[_user]` and per-epoch in `withdrawsRequestsByEpoch[_user][currentEpoch]`, and lets a user stack receipts across epochs as long as their `lastWithdrawRequest` epoch has no `lossRecoveryPriceByEpoch` set (the guard only inspects the *last* request epoch): [1](#0-0) 

On a lossy stop, `collectWithdrawFunds` funds only `_amount < pendingBasis` and records a single `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, i.e. the haircut is computed over **all** pending receipts including earlier-epoch ones: [2](#0-1) 

At claim time, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and clears **only** that epoch's per-epoch amount via `_clearWithdrawClaimForEpoch` (`withdrawsRequests[_user] -= normalAmount` for `_claimEpoch` only): [3](#0-2) 

It then calls `_claimFundedWithdrawRequest`, which pays out the *remaining* aggregate `withdrawsRequests[_user]` — including the earlier-epoch receipt — at par with no haircut, because that path performs no per-epoch loss check beyond `epochNumber > lastWithdrawRequest[_user]`: [4](#0-3) 

The guard that would prevent mixing (lines 263–271) only blocks when the *previous* `lastWithdrawRequest` epoch already has a stored `lossRecoveryPrice` — it does not anticipate a *future* loss landing on a later epoch that aggregates older receipts. So the stored earlier receipt silently "executes" at par inside the loss-funded pool.

### Impact Explanation
Let the attacker hold pending receipts `A` (epoch N) and `B` (epoch N+1). On the lossy stop of epoch N+1, the strategy receives `(A + B + others) * price` in underlying, where `price < RECOVERY_FULL` is meant to haircut every pending receipt. The attacker claims `B * price / RECOVERY_FULL` via `_claimLossAdjustedWithdrawRequest` **plus `A` at par** via `_claimFundedWithdrawRequest`, extracting `A * (1 - price)` more than their fair share. Those extra underlyings come out of the same funded pool/strategy balance, so either (a) other same-epoch claimants find the reserve short and their claims revert (temporary/permanent freezing of unclaimed funds), or (b) the deficit is absorbed by strategy-held underlying backing active tranche positions — direct theft/solvency breakage of the loss-waterfall invariant ("all pending receipts share the loss pro rata", per `previewLossAdjustedWithdrawFunds`). No privileged action is required: only `deposit`/`requestWithdraw`/epoch transitions around honest manager `stopEpochWithDuration` calls. The attacker's earlier stored request is the injected payload; the lossy stop is the second-order execution context.

### Likelihood Explanation
Requires: a `stopEpochWithDuration` loss event (a supported, intentional code path for partial borrower default at epoch end), the ability to keep an unclaimed receipt across one epoch boundary (explicitly supported — the code comments note a user "will have to wait for another epoch to claim both requests"), and another user or active NAV in the same pending bucket to absorb the shortfall. Likelihood is moderate: lossy stops are rare events, but no privileged misbehavior, timing race, or oracle dependence is needed — the accounting path is deterministic once a loss occurs while a user holds multi-epoch pending receipts.

### Recommendation
Apply the loss haircut to the user's **entire** pending claim basis, not just the last epoch's slice. Concretely, in `_claimLossAdjustedWithdrawRequest`, compute the claim basis over all of the user's pending receipts that were inside `pendingBasis` when the loss was booked (e.g., sum `withdrawsRequestsByEpoch` entries created before or at the loss epoch, or track a per-user "pending-at-loss" snapshot), and burn/pay accordingly. Alternatively, disallow stacking a new `requestWithdraw` while any unclaimed receipt exists (extend the `lossRecoveryPrice` guard to `withdrawsRequests[_user] != 0`), forcing claims before re-requesting so `pendingBasis` never mixes epochs. Regression-test: two sequential unclaimed requests + `stopEpochWithDuration(loss)` must yield each user exactly `receipt * lossRecoveryPrice / RECOVERY_FULL`.

```solidity
pragma solidity 0.8.17;

import "./IdleCreditVault.t.sol"; // reuse existing vault/CDO fixture

contract LossHaircutEscapePoC is IdleCreditVaultTest {
    // Attacker: KYC'd LP. Honest manager/borrower sequence.
    function test_OlderReceiptEscapesLossHaircut() external {
        // --- Epoch N (running): attacker deposits and requests withdraw of A ---
        uint256 A = 100_000e6;
        _depositAA(attacker, A);               // mint AA tranches
        vm.prank(attacker);
        cdo.requestWithdraw(A, AA);            // receipt A -> pendingWithdraws += A

        _stopCurrentEpochFullyFunded();        // manager stopEpoch: receipt A funded at par
        // attacker does NOT claim -> withdrawsRequests[attacker] == A still pending in aggregate

        // --- Epoch N+1: attacker deposits again, requests second withdraw B ---
        uint256 B = 50_000e6;
        _depositAA(attacker, B);
        vm.prank(attacker);
        cdo.requestWithdraw(B, AA);            // lastWithdrawRequest -> N+1; pendingWithdraws = A + B

        // --- Epoch N+1 ends with partial loss ---
        uint256 loss = (A + B) / 2;            // 50% loss on the pending bucket
        uint256 basisPre = strategy.pendingWithdraws();
        _stopCurrentEpochWithLoss(loss);       // collectWithdrawFunds -> lossRecoveryPrice = funded/basisPre
        uint256 price = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber() - 1);
        assertLt(price, strategy.RECOVERY_FULL());

        // --- Attacker claims ---
        uint256 balPre = underlying.balanceOf(attacker);
        vm.prank(attacker);
        cdo.claimWithdrawRequest(address(trancheAA));

        uint256 got = underlying.balanceOf(attacker) - balPre;
        uint256 fair = (A + B) * price / strategy.RECOVERY_FULL();   // what the funded pool assumes
        // BUG: _claimFundedWithdrawRequest pays the older receipt A at par
        assertGt(got, fair);                                        // got ≈ A + B*price > (A+B)*price
        // The excess A*(1-price) is drained from the same funded pool/strategy balance,
        // shortchanging other N+1 claimants or active LP backing.
    }
}
```

Expected result: `got == A + B * price / RECOVERY_FULL > fair`; the strategy's post-claim underlying balance is insufficient to honor remaining claimants at their advertised `lossRecoveryPrice`, breaking solvency/fair-burn for the loss epoch.

```text
  function claimWithdrawRequest(address _user) external returns (uint256 amount) {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized) {
      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);
      if (amount != 0) return amount;
      // Only receipts created in the defaulted epoch are haircutted here; old fulfilled
      // receipts are handled below at par if they were already funded before default.
      amount = _claimDefaultedWithdrawRequest(_user);
    }
    amount += _claimLossAdjustedWithdrawRequest(_user);
    return amount + _claimFundedWithdrawRequest(_user);
  }

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  /// @notice Clear a normal/APR0 withdraw receipt for one request epoch.
  /// @dev This does not move funds or burn receipt tokens. Default claims also decrease
  /// `apr0TotalPrincipal`; loss-adjusted claims do not because stopEpoch already closed that bucket.
  /// @param _user address of the user
  /// @param _claimEpoch epoch whose receipt should be cleared
  /// @param _isClearingApr0 true when clearing an open APR0 default claim
  /// @return claimBasis claim amount before applying the recovery ratio
  /// @return burnAmount strategy-token receipt amount to burn
  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
```
