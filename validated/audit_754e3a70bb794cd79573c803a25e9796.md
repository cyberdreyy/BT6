### Title
External Initiator credential can trigger runs for **any** job ID via `/v2/jobs/:ID/runs`, bypassing job-to-initiator binding - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` authenticates any registered External Initiator (EI) credential and unconditionally injects a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` into the gin context, with no binding to the specific job the EI is associated with. Because `PipelineRunsController.Create` treats *any* context holding a `SessionUserKey` (real or synthetic) as `isUser`, an authenticated EI can invoke `POST /v2/jobs/:ID/runs` for arbitrary integer job IDs, not just the job it was registered for.

### Finding Description
The route is registered without any per-job authorization check: [1](#0-0) 

`auth.AuthenticateExternalInitiator` validates only the EI credential pair (access key/secret) against the stored `ExternalInitiator` row — it never checks which job that EI is bound to — and then sets the same context key used for real user sessions: [2](#0-1) 

`auth.RequiresRunRole` only checks `user.Role`, never distinguishing a genuine session/token user from this synthetic EI-injected user: [3](#0-2) 

In `PipelineRunsController.Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed", and gates on `isUser := auth.GetAuthenticatedUser(c)`. However, since `AuthenticateExternalInitiator` also populates `SessionUserKey`, `GetAuthenticatedUser` returns `true` for EI-authenticated requests too — the intended EI exclusion is dead code: [4](#0-3) 

`GetAuthenticatedExternalInitiator` (which could reveal which EI is in play, enabling a job-binding check) is defined but never consulted by `PipelineRunsController.Create` or any other run-triggering code path — it is unused outside `auth.go` itself. As a result, there is no code anywhere that verifies the authenticated EI is actually the initiator configured on job `:ID` before calling `prc.App.RunJobV2(ctx, jobID, nil)`.

### Impact Explanation
Any holder of a valid, registered EI credential (access key + secret) — which is a comparatively low-privilege credential intended to trigger only its own bound webhook job — can call `POST /v2/jobs/:ID/runs` for **any** job ID on the node and force a pipeline execution. This is an authorization/role-binding bypass leading to unauthorized triggering of job runs belonging to unrelated jobs/initiators, potentially causing unwanted external-adapter calls, unwanted on-chain transactions (for jobs with transmit/write tasks), rate-limit exhaustion, or unexpected chain-state changes attributable to jobs the attacker does not own.

### Likelihood Explanation
The only precondition is possession of one legitimately-registered EI access key/secret pair (which the EI operator itself holds, and which per the security model should only allow running its own designated job). No admin/session/token privileges needed beyond that. The bypass is trivially and repeatably exploitable: authenticate with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers and POST to `/v2/jobs/<any-int-ID>/runs`.

### Recommendation
Bind the EI identity to the target job before allowing a run:
- In `PipelineRunsController.Create`, use `auth.GetAuthenticatedExternalInitiator(c)` to detect EI-originated requests explicitly (instead of relying on `GetAuthenticatedUser`, which EI auth also populates).
- Look up the job's configured `ExternalInitiatorWebHookSpec`/initiator association for `:ID` and reject the request (403) unless the authenticated EI matches the one bound to that job.
- Alternatively, stop `AuthenticateExternalInitiator` from writing to `SessionUserKey` and instead require all run-triggering handlers to explicitly check `GetAuthenticatedExternalInitiator` plus job binding, so EI and User authentication are never conflated.

### Proof of Concept
Handler-level integration test plan (Go, using `httptest`/`gin` test harness as used in `core/web/pipeline_runs_controller_test.go`):
1. Create Job-A with a webhook/EI spec bound to `ExternalInitiator EI-A`, and Job-B (any job type accepting a run) unrelated to EI-A.
2. Register `EI-A` credentials via the external initiators API/ORM.
3. Send `POST /v2/jobs/<Job-B integer ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-A's credentials, through the router chain (`auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` → `auth.RequiresRunRole(prc.Create)`).
4. Assert current (vulnerable) behavior: response is `200 OK` with a `pipelineRun` resource for Job-B, proving EI-A triggered a run for a job it is not bound to.
5. After fix: assert response is `403 Forbidden`/`401 Unauthorized` for Job-B, and `200 OK` only when the target job ID equals the one bound to EI-A.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
