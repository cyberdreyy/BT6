## Analog Found

### Title
Stale cross-tenure signature conflicts are never re-validated before signing, letting a signer double-sign at one height - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The Salty.IO report describes a check ("minimum collateral") that is only enforced at one mutating action (borrow) and silently skipped at a later mutating action (withdraw) on the same position, letting an attacker walk the position outside the invariant the check was meant to guarantee. The stacks-signer analog is the pre-commit→signature guard in `handle_block_pre_commit`: the "no signature at a conflicting height" invariant is fully enforced only while a competing signature is *fresh*; once it goes *stale*, the guard degrades to checking only the proposed block's **own tenure**, silently dropping the canonicity check for conflicts that live in any other tenure.

### Finding Description
`handle_block_pre_commit` re-validates chainstate and conflicts right before placing a signature [1](#0-0) . It first re-runs `check_block_against_signer_db_state`, which only checks the proposed block's **own** tenure (or, for tenure-change blocks, its **parent** tenure) via `check_latest_block_in_tenure` [2](#0-1) ; it never inspects an unrelated third tenure.

It then loads all signed/accepted conflicts at height ≥ h across *any* tenure via `get_signed_conflicts` [3](#0-2) . For conflicts still *fresh* (`last_endorsed > freshness_cutoff`), the code asks the node whether the conflicting tenure/block is still canonical via `conflict_still_blocks`/`reorg_permit_stands`, and refuses to sign if it is [4](#0-3) . But once a conflict goes **stale**, the only remaining guard checks conflicts whose `consensus_hash` equals the *proposed block's own tenure* [5](#0-4) . A stale conflict that lives in a tenure that is neither the proposed block's own tenure nor its parent tenure is not checked against the node at all — it is treated as if it never existed, and the code proceeds straight to `mark_locally_accepted`/signing [6](#0-5) .

The design comment explicitly assumes this gap is "settled by the chainstate checks above" [7](#0-6) , but the chainstate check (`check_latest_block_in_tenure`) only ever examines the block's own-or-parent tenure — never an arbitrary unrelated tenure that happens to hold the stale conflicting signature, exactly as `docs/signer-flows.md` itself documents: "Which tenure it is asked about depends on the block... never both" [8](#0-7) .

This is structurally identical to the collateral bug: the strong check (fresh-conflict canonicity verification) is enforced at the "natural" moment, but the equivalent verification silently disappears once time passes (analogous to withdrawing after borrowing), and no other code path reintroduces it for the cross-tenure case.

### Impact Explanation
If exploited, a signer can end up placing its signature on two different blocks at the same stacks height in two unrelated tenures — one already globally accepted, one newly proposed — because the stale-conflict guard never asks the node whether the other tenure/block is still canonical. This is a Critical-class outcome per the rules: "a signer signing an invalid, non-canonical, or conflicting block" and a loss of the "equivocation guard," since the one-signature-per-height invariant that the pre-commit re-check is designed to enforce is bypassed once `tenure_last_block_proposal_timeout` has elapsed for the older signature.

### Likelihood Explanation
Reachable by a single miner (plus normal gossip) without needing a majority of signers or any private keys: the miner only needs to (1) get an earlier block A signed/globally accepted, (2) let `tenure_last_block_proposal_timeout` elapse, then (3) propose a second, unrelated-tenure block C at the same height that independently passes `check_proposal`/`check_latest_block_in_tenure` on its own tenure (trivial if C's own tenure has no signed blocks at that height) and gathers the normal 70% pre-commit weight from honest signers validating C on its own merits. No signer needs to detect anything wrong with C in isolation — the bug is that the *cross-tenure* conflict with A is dropped once stale.

### Recommendation
In the stale-conflict branch of `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs`, lines ~1422-1457), do not restrict the canonicity re-check to conflicts sharing the proposed block's own `consensus_hash`. For every stale conflict, still ask the node (`get_tenure_tip`/`conflict_still_blocks`-style logic) whether the conflicting tenure/block is still canonical at or above the proposed height, regardless of which tenure it lives in, before signing.

### Proof of Concept
1. Miner tenure A produces block A at height h; it gathers ≥70% pre-commit weight and the signer signs it (`mark_locally_accepted`), later globally accepted.
2. Wait longer than `tenure_last_block_proposal_timeout` (so A's `last_endorsed` becomes stale relative to `freshness_cutoff`) [9](#0-8) .
3. Miner proposes block C, in an unrelated tenure X (not A's tenure, not A's parent tenure), also targeting height h; C passes `check_proposal`/`check_latest_block_in_tenure` on X because X has no signed blocks yet at that height.
4. Signers pre-commit to C normally (its own-tenure checks pass); once pre-commit weight ≥70%, `handle_block_pre_commit` re-runs the chainstate check (passes, since it only looks at X) [10](#0-9) , then `get_signed_conflicts` returns A as a conflict, but since A's `last_endorsed` is stale and `A.consensus_hash != X`, neither the fresh-conflict branch nor the same-tenure-stale branch fires [11](#0-10) .
5. The signer proceeds to `mark_locally_accepted`/sign C, producing a second signature at height h despite A already being signed/globally accepted — the cross-tenure canonicity of A relative to X is never checked.

```markdown
`check_latest_block_in_tenure` answers "does this block confirm the tip we
expect?" and it runs in three places: at proposal arrival (inside
`check_proposal`), at validate-ok, and at the moment of signing. _Which_ tenure
it is asked about depends on the block: a tenure-change block is checked against
its **parent** tenure, every other block against its **own**. Never both. The
pivotal helper is `get_tenure_last_block_info`, which considers only blocks that
carry a signature (`get_last_signed_block`): a pre-commit never vetoes anything,
it only counts as miner activity.
```
