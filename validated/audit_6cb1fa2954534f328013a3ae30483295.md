### Title
Cross-user response confusion via MessageId collision in webAPITrigger callback map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores pending user callbacks in `h.savedCallbacks` keyed **only** by the attacker-controlled `msg.Body.MessageId` string, with no binding to the requester's signer/sender address. Two different, mutually untrusted users can choose the same `MessageId`, causing the second request to silently overwrite the first request's saved callback, so the DON's response for user A's request is delivered to user B's callback.

### Finding Description
`MessageId` is a free-form field on `api.MessageBody` whose only validation is a length/null-byte check in `Message.Validate()` [1](#0-0) ; it is never required to be unique, and it is chosen entirely by the client before signing [2](#0-1) . The signature only authenticates that the sender who signed produced that exact `MessageId`/payload — it does nothing to prevent two independent signers from picking the identical `MessageId` value.

In `HandleLegacyUserMessage`, the callback is stored with:
```go
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [3](#0-2) 
This is a plain map write with no existence check and no `Sender` component in the key, unlike the newer/parallel `RequestCache` abstraction used by other handlers (e.g. `vault`, `confidentialrelay`) which keys entries by `globalId{sender, id}` specifically to avoid this class of bug: [4](#0-3) [5](#0-4) 

When a DON node later responds with `MethodWebAPITrigger` and the same `MessageId`, `handleWebAPITriggerMessage` looks the entry up by `MessageId` alone and delivers the response to whichever callback is currently stored:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
``` [6](#0-5) 

Exploit flow: attacker (any client capable of signing a gateway message with any private key — no privileged role required) sends message A with `MessageId=X`. Before the DON responds, a second (or the same) attacker sends message B, also with `MessageId=X`, signed by a different key. `HandleLegacyUserMessage` overwrites `savedCallbacks[X]` with B's callback and re-forwards a request with id X to all DON members. When the DON node's response to A's original request (still carrying id X) arrives, `handleWebAPITriggerMessage` delivers it to B's stored callback, not A's — user isolation between the two callback channels is broken. No existing check (`Validate()`, signature check, or the handler logic) verifies that the resolver of a `MessageId` matches the sender that originally registered it.

### Impact Explanation
This breaks the ISOLATION invariant between concurrent gateway users: one user's HTTP response (potentially containing sensitive data returned by the external endpoint through the DON's `web_api_trigger` flow) can be delivered to a different, unrelated user's callback/session. Depending on what the triggered HTTP response contains, this is a confidentiality/response-leak class issue (cross-user response confusion), matching the "unauthorized disclosure of another user's data" bounty class rather than fund loss or node compromise.

### Likelihood Explanation
Feasibility is high for anyone who can reach `HandleLegacyUserMessage` with a signed message: the attacker only needs to control an ECDSA keypair to sign requests (no operator/admin access, no special role) and to pick a `MessageId` value used concurrently by another in-flight request. Since `MessageId` has no uniqueness enforcement, and gateway request volume/latency creates natural windows of concurrent in-flight requests, collisions are entirely attacker-choosable (deterministic) rather than requiring luck if the attacker can predict or observe another user's chosen `MessageId` (or simply race with their own two identities). Repeatable via unit test.

### Recommendation
Key `h.savedCallbacks` by `(Sender, MessageId)` (mirroring `common.RequestCache`'s `globalId{sender, id}` pattern) instead of `MessageId` alone, and reject/overwrite-protect duplicate keys the same way `requestCache.NewRequest` does (`"request already exists"`). When resolving a node response in `handleWebAPITriggerMessage`, look up using the same composite key (sender must be derivable from `msg.Body.Receiver`/original request context) so a response can only be routed back to the callback that registered the identical `(Sender, MessageId)` pair. Ideally, migrate `capabilities.handler` to use the shared `common.RequestCache` implementation instead of the ad hoc `savedCallbacks` map.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler `h` via `NewHandler` with mock `don` and mock `httpClient`.
2. Create `msgA` signed by key A and `msgB` signed by key B, both with `Body.MessageId = "X"` and `Method = MethodWebAPITrigger`, valid `Timestamp`.
3. Create two distinct `handlers.Callback` mocks, `callbackA` and `callbackB`, each expecting `SendResponse` to be called at most once with a payload argument matcher checking origin data.
4. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` then immediately `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` (simulating message B arriving before A's response).
5. Simulate a DON node response for A's original request: build an `api.Message` with `Body.MessageId = "X"`, `Method = MethodWebAPITrigger`, and a payload distinguishable as "response for A" (e.g. embed a marker in `Response.Body`), sign it as coming from a legitimate node, and call `h.HandleNodeMessage(ctx, resp, nodeAddr)`.
6. Assert: `callbackB.SendResponse` is invoked with the "response for A" payload (demonstrating the bug), while `callbackA.SendResponse` is never called — i.e., `mock.AssertNotCalled(t, "SendResponse", ...)` for `callbackA` and `mock.AssertCalled` for `callbackB` with A's payload content.
7. Expected (buggy) result confirming the vulnerability: `callbackB` receives node data intended for user A's request, proving cross-user response confusion due to the shared `MessageId`-only key in `h.savedCallbacks`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {

	c.mu.Lock()
	defer c.mu.Unlock()
