### Title
Stale Confirmations From Revoked Multisig Keys Are Still Counted Toward Execution Threshold - ([File: multisig/src/lib.rs])

### Summary
The `MultiSigContract::confirm` function in `multisig/src/lib.rs` authorizes and executes a request once the number of *recorded* confirmations reaches `num_confirmations`, without verifying that each confirming public key is still a live/valid access key on the account at execution time. When a key is removed via `DeleteKey`, the contract only purges requests that key *itself created*, but does not scrub that key's confirmations recorded on other still-pending requests. This produces a divergence between "confirmations counted" and "confirmations from currently live members" — directly analogous to the report's core bug class (a count that no longer reflects ground truth being used to gate a critical threshold).

### Finding Description
`add_request`/`confirm` record confirmations per `PublicKey` in a `HashSet<PublicKey>` keyed by `request_id`: [1](#0-0) 

The threshold check is purely `confirmations.len() as u32 + 1 >= self.num_confirmations` — a raw count comparison against the set of public keys that have ever confirmed, with no re-validation that those keys are still authorized signers on the account: [2](#0-1) 

When a key is deleted, the `DeleteKey` action removes only *requests created by* that key (matched via `signer_pk`), plus its `num_requests_pk` entry — it does not walk other pending requests' `confirmations` sets to strip that key's earlier confirmation: [3](#0-2) 

Consequence: if key `C` confirms request `R` (created by `A`) and is later revoked (e.g., suspected compromise, key rotation) via a separate `DeleteKey{C}` request that only targets requests *C created*, `R`'s confirmation set still contains `C`. A subsequent confirmation by any other still-valid key can push `confirmations.len() + 1 >= num_confirmations` to true and trigger `execute_request`, even though the actual number of currently-live keys that approved `R` is one less than `num_confirmations`. This is the "confirmations counted versus live members" binding break called out in scope: the recorded confirmation tally no longer equals the number of currently authorized signers who approved the action, yet it is trusted as if it did.

### Impact Explanation
This allows a multisig request (e.g., `Transfer`, `AddKey`, `FunctionCall`) to execute with fewer genuinely live/authorized confirmations than the configured `num_confirmations` threshold — i.e., a K-of-N multisig executing below its real threshold. Per the scope's Critical impact category ("a multisig request executed below threshold"), this can result in unauthorized fund transfers or unauthorized key/permission changes on the multisig account.

### Likelihood Explanation
Exploitation requires no privileged party beyond normal multisig key-management operations that already happen in practice: a request pending confirmation, and a *separate, unrelated* `DeleteKey` action revoking one of the confirming keys (a routine security/rotation action, not itself malicious). No attacker collusion with contract owners is needed to trigger the underlying flaw — the stale-confirmation bookkeeping bug is triggered by ordinary key-rotation combined with an in-flight request, which is a realistic operational sequence for any active multisig.

### Recommendation
When executing `DeleteKey`, also remove the deleted public key from the `confirmations` set of every other pending request (not just requests it created), and re-validate on `confirm`/execution that all counted confirmations still belong to currently-authorized keys before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig initialized with `num_confirmations = 3` and keys `A`, `B`, `C` all holding full-access keys on the account.
2. Key `A` calls `add_request` creating request `R1` (e.g., `Transfer{amount}` to some receiver).
3. Key `B` calls `confirm(R1)` → confirmations = `{B}` (1/3, added since `B != A`, only creator implicit... in this contract creator confirmation is added only via `add_request_and_confirm`; assume `A` used `add_request_and_confirm` so confirmations = `{A}`).
4. Key `C` calls `confirm(R1)` → confirmations = `{A, C}` (2/3), not yet executed.
5. Separately, key `A` (or governance) submits and confirms a `DeleteKey{public_key: C}` request `R2` to revoke `C` (e.g., due to suspected compromise). Per `execute_request`'s `DeleteKey` branch (`multisig/src/lib.rs:198-216`), this only removes requests *created by* `C` — `R1` was created by `A`, so it is untouched, and `C`'s confirmation entry inside `R1`'s `confirmations` set is never scrubbed.
6. `C`'s access key is now deleted from the account (no longer a live signer), but `R1.confirmations` still logically counts `C`.
7. Key `B` calls `confirm(R1)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request(R1)` runs and transfers funds, even though only 2 currently-live keys (`A`, `B`) actually authorized it — one fewer than the configured 3-of-3 threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
