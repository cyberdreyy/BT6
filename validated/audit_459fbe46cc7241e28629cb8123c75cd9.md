### Title
Loss-epoch withdraw receipt escapes haircut when a second `requestWithdraw` overwrites `lastWithdrawRequest`, paying the stale receipt at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a use-after-free: `blk_mq_tag_to_rq` dereferences a request already freed by `blk_mq_complete_request` — a stale pointer to an object whose state was already consumed. The credit-vault analog is a stale-epoch claim: `IdleCreditVault.claimWithdrawRequest` resolves which epoch a loss-adjusted receipt belongs to through the single mutable slot `lastWithdrawRequest[_user]`. A second `requestWithdraw` in a later epoch "frees" (overwrites) that pointer while the per-epoch basis in `withdrawsRequestsByEpoch[_user][lossEpoch]` and the aggregate `withdrawsRequests[_user]` still exist, so the loss-adjusted payout path never runs and the funded path pays the stale basis at par.

### Finding Description
`requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and appends `_amount` to `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]`, without blocking on an existing pending receipt — the code comments explicitly allow stacking a new request on top of an unclaimed one. [1](#0-0) 

On claim, `_claimLossAdjustedWithdrawRequest` looks up the recovery price only for `lastWithdrawRequest[_user]`: [2](#0-1) 

If the user requested in the loss epoch `L` and then requested again in epoch `M > L` before claiming, `lastWithdrawRequest[_user] == M`, `lossRecoveryPriceByEpoch[M] == 0`, and the function returns 0 — the epoch-`L` haircut is never applied. `_clearWithdrawClaimForEpoch` for epoch `L` is never invoked because the loss-adjusted path only ever checks that one epoch. [3](#0-2) 

Control then falls into `_claimFundedWithdrawRequest`, which settles `normalAmount = withdrawsRequests[_user]` — still containing the full, un-haircutted epoch-`L` basis — and pays it at par via `_transferFundedClaim`, burning the receipt 1:1. [4](#0-3) 

The borrower only funded `claimBasis * lossRecoveryPrice` for epoch `L` at `stopEpochWithDuration(_lossAmount)`; the strategy therefore holds less underlying than the par payout, and `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve`, not other claimants' funded liquidity. [5](#0-4) 

The broken invariant is the loss waterfall ("one receipt one payout at its epoch price"): a haircutted receipt is paid twice-over — once implicitly at par through the aggregate ledger — consuming underlyings owed to other withdrawers.

### Impact Explanation
Direct theft / insolvency. An attacker holding a haircutted receipt of size `B` in epoch `L` (recovery price `p < 1`) makes a dust-size `requestWithdraw` (e.g., 1 wei of tranche tokens) in epoch `L+1` and claims `B + dust` at par instead of `B * p / RECOVERY_FULL`. Profit = `B * (1 - p)`. On a 50% loss epoch this doubles the attacker's recovery, draining the funded-claim liquidity that honest epoch-`L` claimants and later withdrawers rely on; the last claimants' `claimWithdrawRequest` reverts on insufficient balance, permanently freezing their payouts.

### Likelihood Explanation
High feasibility, unprivileged-only, and timing-controlled rather than racy:

1. Attacker is a KYC-passed tranche holder. Epoch `N` runs; attacker calls `cdoEpoch.requestWithdraw(trancheAmount, tranche)` (running phase, fixed-APR mode).
2. Manager calls `stopEpochWithDuration` with `_lossAmount > 0` (borrower shortfall) → `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` is recorded. Epoch `N+1` buffer begins; `epochNumber` increments.
3. Before claiming, attacker calls `requestWithdraw(dust, tranche)` again — permitted because the strategy never checks `_hasWithdrawRequest` on new requests — overwriting `lastWithdrawRequest` to `N+1`.
4. Epoch `N+1` ends (honest manager `stopEpoch`); `epochNumber > lastWithdrawRequest` gate passes, `lossRecoveryPriceByEpoch[N+1] == 0` skips the haircut, and `_claimFundedWithdrawRequest` pays the full aggregate.

No privileged misbehavior is required: honest manager `stopEpoch`/`stopEpochWithDuration` calls are just sequenced around. The existing guards (epoch gating at line 326, reserve guard in `_transferFundedClaim`, `_onlyIdleCDO`) do not stop it — they are precisely what makes the payout path succeed.

Uncertainty: I could not fully trace `stopEpochWithDuration`'s handling of `withdrawsRequestsByEpoch` inside `IdleCDOEpochVariant` (grep returned only hit counts, not the source lines). If that path zeroes `withdrawsRequestsByEpoch[user][L]` at stop time, the exploit window would narrow; the claim-side code shown does not clear it, and `_clearWithdrawClaimForEpoch` exists specifically because the per-epoch entry survives until claim, which supports the attack working as described. A fork PoC would settle this conclusively.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate or track all epochs with a nonzero `lossRecoveryPriceByEpoch` for the user rather than only `lastWithdrawRequest[_user]` — e.g., maintain a `firstLossEpoch[_user]` / epoch list, or set a separate `lossClaimEpoch[_user]` when the request is made in an epoch that ends with a loss. Alternatively, in `requestWithdraw`, revert if the user has an unclaimed receipt in an epoch with a pending loss price (reuse `_hasWithdrawRequest` plus a `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` check), forcing claim-before-re-request. Also have `_claimFundedWithdrawRequest` exclude any `withdrawsRequestsByEpoch` entry whose epoch has a nonzero `lossRecoveryPriceByEpoch`.

function testPocLossHaircutEscape() external {
    uint256 amt = 100_000 * ONE_SCALE;
    // attacker + honest user deposit AA
    idleCDO.depositAA(amt); // attacker (this contract)
    vm.prank(user1); idleCDO.depositAA(amt);

    _startEpochAndCheckPrices(0);
    // attacker requests withdraw of full balance in epoch that will end with loss
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // full balance

    // epoch ends with loss: borrower repays less than owed -> stopEpochWithDuration(_lossAmount>0)
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch() / 2); // 50% loss
    // now lossRecoveryPriceByEpoch[lossEpoch] == RECOVERY_FULL/2, epochNumber rolled

    _startEpochAndCheckPrices(1);
    // attacker makes dust re-request, overwriting lastWithdrawRequest
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balPre;

    uint256 parPayout = withdrawBasis; // full receipt amount incl. interest
    uint256 expected = parPayout * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL + 1;
    // BUG: got == parPayout + dust, not expected haircutted amount
    assertGt(got, expected, 'loss haircut bypassed via stale lastWithdrawRequest');
    // subsequent honest claim reverts NotAllowed / underflow -> frozen funds
}

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;

    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
