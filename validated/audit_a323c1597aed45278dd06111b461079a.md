## Analysis

The Linea report's core bug class — an unpermissioned/unprotected `initialize()` function that can be front-run to seize control of the contract before the legitimate deployer's initialization transaction lands — has a direct and reachable analog in the marginfi-v2 Solana program.

### Root Cause

`init_global_fee_state` initializes the program-wide `FeeState` singleton PDA. The instruction's account context has **no admin/authority check at all** — only a generic `payer: Signer`: [1](#0-0) 

The `admin_key` and `fee_wallet` values that become `FeeState.global_fee_admin` / `FeeState.global_fee_wallet` are taken directly from **caller-supplied instruction arguments**, not derived from any signer or program-authority check: [2](#0-1) 

Because the `fee_state` account uses Anchor's `#[account(init, seeds=[FEE_STATE_SEED])]`, it can be created exactly once, and this PDA has program-wide scope (not per-group). This is functionally identical to the Linea `initialize() external initializer` pattern: whoever's transaction lands first "wins" the privileged role permanently, and there is no way to re-run it.

The intended deployment flow (seen in test fixtures) treats `init_global_fee_state` as a *separate* transaction from program deployment/upgrade, not atomically bundled with it: [3](#0-2) [4](#0-3) 

This is exactly Scenario (a) from the Linea report: `[deploy program] ---window of opportunity--- [init_global_fee_state]`. Since Solana program deploys/upgrades and subsequent instruction calls are inherently separate transactions (unlike a single atomic `upgradeToAndCall`), and there is no mechanism (e.g., embedding the intended admin key in program-derived data, or checking `program_data.upgrade_authority`) restricting who may call this instruction, any observer of the mempool/leader schedule can submit `init_global_fee_state` first with themselves as `admin_key` and an attacker-controlled `fee_wallet`.

### Impact

`global_fee_admin` is a powerful, protocol-wide role. Once seized, the attacker can call `edit_global_fee_state` (gated only by `has_one = global_fee_admin`) to: [5](#0-4) 

- Redirect `global_fee_wallet` — the destination of **all program-fee revenue across every bank/group in the protocol** — to an attacker-controlled wallet, permanently diverting program fees (confirmed impact of the wallet field per `guides/ADMIN/PERMISSIONS_AND_ROLES.md` and `collect_bank_fees.rs`'s use of `global_fee_wallet`'s canonical ATA): [6](#0-5) 

- Set `program_fee_fixed` / `program_fee_rate` to the max allowed value, adversarially increasing borrower costs protocol-wide.
- Set/clear `pause_delegate_admin` and panic-pause the entire protocol.

This satisfies the "unprivileged-user analog" bar: the attacker starts with zero privilege and, purely by front-running an unauthenticated one-time initializer, obtains a durable, protocol-wide privileged role with direct financial-redirection capability — the same root cause (unauthenticated/non-atomic initialization) as the reported Linea `RollupRevenueVault` issue.

### Title
Front-runnable, unauthenticated `init_global_fee_state` instruction allows any signer to seize permanent global fee-admin control - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
`init_global_fee_state` creates the program-wide `FeeState` PDA and sets `global_fee_admin`/`global_fee_wallet` from caller-supplied arguments with no authorization check on who may call it. Since this instruction runs in a separate transaction from program deploy/upgrade (not atomically bundled), any party can front-run the legitimate initialization and permanently seize the `global_fee_admin` role and redirect protocol-wide fee revenue.

### Finding Description
The `InitFeeState` account context only requires a generic fee-paying `Signer`; there is no check that the caller is the program's upgrade authority, deployer, or any other pre-established authority: [7](#0-6) 
The handler blindly writes attacker-controlled `admin_key` and `fee_wallet` parameters into the `FeeState` PDA: [8](#0-7) 
Because `fee_state` is created via `#[account(init, seeds=[FEE_STATE_SEED])]`, this can only succeed once per program deployment — whichever transaction lands first wins irrevocably.

### Impact Explanation
Successful front-running grants the attacker the `global_fee_admin` role, allowing them to call `edit_global_fee_state` and redirect `global_fee_wallet` (destination of all protocol-wide program fees) to their own wallet, arbitrarily raise `program_fee_fixed`/`program_fee_rate`, and control the protocol's panic-pause delegate — a durable, protocol-wide value-redirection and governance-takeover with direct financial effect.

### Likelihood Explanation
High. No special permission, timing precision beyond normal transaction-landing races, or capital is required — any party monitoring new/upgraded program deployments (which are public on-chain events) can submit a competing `init_global_fee_state` transaction. The instruction is discoverable directly from the IDL/program interface.

### Recommendation
Restrict `init_global_fee_state` to a hard-coded/known authority (e.g., validate the caller against the program's `ProgramData.upgrade_authority`, or require a signer matching a compile-time constant), or bundle it atomically with program deployment tooling so the window cannot be front-run. Consider deriving `admin_key` from the upgrade authority rather than accepting it as an arbitrary instruction argument.

### Proof of Concept
1. Observe (via RPC or explorer) that the `marginfi` program has just been deployed/upgraded and the `FeeState` PDA (`seeds=[b"feestate"]`) does not yet exist.
2. Before the legitimate admin's transaction lands, submit a transaction calling `init_global_fee_state(admin_key=attacker, fee_wallet=attacker_wallet, ...)` with any funded signer as `payer`.
3. Anchor's `init` constraint succeeds since the PDA is unoccupied; `FeeState.global_fee_admin` and `FeeState.global_fee_wallet` are now permanently attacker-controlled.
4. The legitimate admin's subsequent `init_global_fee_state` call fails ("account already in use"), leaving the attacker in permanent control.
5. Attacker calls `edit_global_fee_state` to redirect `global_fee_wallet` and raise fee rates, diverting all future protocol program fees.

// Runs once per program to init the global fee state.
use anchor_lang::prelude::*;
use marginfi_type_crate::{
    constants::FEE_STATE_SEED,
    types::{FeeState, WrappedI80F48},
};

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}

#[derive(Accounts)]
pub struct InitFeeState<'info> {
    /// Pays the init fee
    #[account(mut)]
    pub payer: Signer<'info>,

    #[account(
        init,
        seeds = [
            FEE_STATE_SEED.as_bytes()
        ],
        bump,
        payer = payer,
        space = 8 + FeeState::LEN,
    )]
    pub fee_state: AccountLoader<'info, FeeState>,

    pub system_program: Program<'info, System>,
}
