### Title
Attached NEAR deposit becomes permanently stuck in `MultisigFactory` when sub-account creation fails, unlike sibling factories which refund on failure - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` is a `#[payable]` function that attaches the caller's entire deposit into a single promise batch that creates a new sub-account, deploys the multisig contract, transfers the deposit, and calls `new`. Unlike the sibling factory contracts in the same repository (`lockup-factory`, `staking-pool-factory`), it has no `.then()` callback to detect failure of the batch and refund the deposit. If the batch fails for any reason, the attached NEAR is left stranded on the factory contract with no method anywhere in the contract to move it back out.

### Finding Description
`create` builds a single `Promise` batch on the newly derived `account_id` (`"{name}.{current_account_id}"`): [1](#0-0) 

This is structurally identical to `lockup-factory::create` and `staking-pool-factory::create_staking_pool`, both of which attach a `.then(ext_self::on_..._create(...))` callback that checks `is_promise_success()` and, on failure, executes `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` to return the funds to the caller: [2](#0-1) [3](#0-2) 

`multisig-factory/src/lib.rs` has no equivalent callback and no other public method capable of transferring funds out of the factory account — the entire contract consists solely of the `create` function: [4](#0-3) 

The custody binding that should hold is: `attached_deposit == amount_transferred_to_new_sub_account OR amount_refunded_to_predecessor`. If the promise batch fails (e.g., the derived sub-account name already exists, is otherwise invalid, or `deploy_contract`/`function_call` fails for any reason), none of the batch's actions (including the `.transfer()`) execute, so the attached deposit remains on the `MultisigFactory` contract's own balance. Because the contract exposes no withdraw/refund/owner-controlled recovery function, that NEAR is now permanently unreachable by any account — it breaks the binding and is not recoverable by the depositor, the factory, or anyone else.

### Impact Explanation
This meets the Critical bar of "funds permanently frozen": any unprivileged caller who calls `create` with a name that collides with an existing account (including a griefing front-run, since account names are public/predictable — `sha256`/derived subaccount naming isn't even used here, it's a raw user-supplied `name`) or otherwise triggers batch failure loses their attached deposit with no recovery path, since the deposit becomes trapped on the factory contract with zero methods able to move funds out.

### Likelihood Explanation
Likelihood is elevated compared to the report's Solidity analog because:
- The sub-account name is directly attacker/user-controlled (`name`), so account-already-exists collisions are trivial to cause (self-inflicted by mistake, or deliberately by a third party front-running/pre-creating the target name to grief a specific depositor).
- No special privileges are required — any account can call `create` and attach a deposit.
- The two sibling factory contracts in the very same repository demonstrate the maintainers are aware this failure mode exists and normally mitigate it with a refund callback, confirming `multisig-factory` is missing that safeguard.

### Recommendation
Add a `.then()` callback to `create` (analogous to `on_lockup_create` / `on_staking_pool_create`) that checks `is_promise_success()` and, on failure, transfers the attached deposit back to `env::predecessor_account_id()`.

### Proof of Concept
1. Pre-create (or have already existing) an account named `alice.multisig_factory.near` on-chain (e.g. attacker front-runs, or it's simply a name collision).
2. Victim calls `multisig_factory.near::create({"name": "alice", "members": [...], "num_confirmations": 1})` attaching `X` NEAR.
3. The batched `create_account()` action fails because the account already exists; the entire receipt (including `.transfer(X)`) fails as a unit.
4. `X` NEAR remains credited to `multisig_factory.near`'s own account balance.
5. No method in `multisig-factory/src/lib.rs` can move that `X` NEAR back to the victim or anywhere else — the funds are permanently frozen.

const CODE: &[u8] = include_bytes!("../../multisig2/res/multisig2.wasm");

/// This gas spent on the call & account creation, the rest goes to the `new` call.
const CREATE_CALL_GAS: u64 = 50_000_000_000_000;

#[derive(Serialize, Deserialize)]
#[serde(crate = "near_sdk::serde", untagged)]
pub enum MultisigMember {
    AccessKey { public_key: Base58PublicKey },
    Account { account_id: AccountId },
}

#[near_bindgen]
#[derive(BorshSerialize, BorshDeserialize, Default)]
pub struct MultisigFactory {}

#[near_bindgen]
impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
}

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,

    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();
