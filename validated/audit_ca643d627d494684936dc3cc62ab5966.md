### Title
Early depositor can inflate tranche price via donated strategy tokens, stealing funds from later depositors - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
`IdleCDOCreditVault` mints tranche tokens as `_amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)`, where the price derives from NAV measured as the CDO's `strategyToken` balance (`_managedContractValue`). `_skimDonatedAssets` only sweeps raw `token` donations — donated `strategyToken` is not skimmed and is counted as NAV. An unprivileged first depositor can mint dust tranche shares at the fixed `oneToken` zero-supply price, donate `strategyToken` (obtainable unprivileged as instant-withdraw receipts minted to `msg.sender` by `IdleCreditVault.requestInstantWithdraw`) to inflate `priceAA`, and cause the next depositor to mint near-zero shares — the classic ERC4626 share-inflation/first-depositor attack from the Knox finding, transposed onto the tranche NAV surface.

### Finding Description
- On a never-initialized tranche, `_virtualPriceAux` returns `(oneToken, 0)` when `trancheSupply == 0` (`contracts/IdleCDOCreditVault.sol:296-298`), so the first `depositAA(1 wei)` mints `1 * 1e18 / oneToken` shares (e.g. `1e12` for 6-decimals USDC).
- `virtualPrice`/`_updateAccounting` use `_managedContractValue() = strategyToken.balanceOf(CDO) - unclaimedFees` (`contracts/IdleCDOCreditVault.sol:133-137`, `:172-180`). Raw `token` donations are neutralized by `_skimDonatedAssets()` (`contracts/IdleCDOEpochVariant.sol:794-796`), but nothing skims `strategyToken` donations, and `IdleCreditVault` strategy tokens are transferable ERC20 receipts minted to users in `requestInstantWithdraw` (`contracts/IdleCDOEpochVariant.sol:761-765`).
- Attack sequence (buffer phase, `isEpochRunning == false`, pool open):
  1. Attacker (KYC'd) deposits `1 wei` AA → holds ~all AA supply at price `oneToken`.
  2. Attacker obtains `D` underlying worth of `IdleCreditVault` strategy tokens as an instant-withdraw receipt in a prior epoch cycle (or via any legitimate holder flow), then `transfer`s them to the CDO.
  3. `_updateAccounting` (triggered inside the next `_deposit`) computes `totalGain = nav - lastNAV = D`, splits it per `trancheAPRSplitRatio`, and sets `priceAA ≈ D * 1e18 / 1e12` — massively inflated (`contracts/IdleCDOCreditVault.sol:306-336`).
  4. Victim `depositAA(V)` mints `V * 1e18 / priceAA ≈ 0` shares; its underlying is converted to strategy tokens and accrues to NAV.
  5. Attacker redeems all AA shares and captures `D + V` worth of NAV, profiting ~`V` minus unrecovered donation remainder.

### Impact Explanation
Direct theft: later depositors receive ~0 tranche tokens for real underlying, and the attacker redeems the inflated NAV. Loss is bounded by victim deposit size vs donation cost — with dust initial supply the attacker profitably captures deposits up to roughly the donated amount. Broken invariant: fair mint/burn — NAV is manipulable by an unprivileged direct `strategyToken` transfer.

### Likelihood Explanation
Requires the attacker to be the first (or near-exclusive) AA holder and to hold transferable `strategyToken` receipts, both achievable by an unprivileged KYC'd wallet without any privileged call. No existing guard stops it: `_skimDonatedAssets` covers only `token`; `depositDuringEpoch`'s `supply == 0` check does not apply to normal `_deposit`; `_checkDefault`/`Default` revert only fires on losses, not gains; the BB-first waterfall does not block NAV inflation.

### Recommendation
- Exclude unsolicited `strategyToken` from NAV by tracking managed strategy-token balance internally (incremented on `deposit`/`mintStrategyTokens`, decremented on burns/withdrawals) instead of `balanceOf(this)`, or skim `strategyToken` donations to `feeReceiver` analogously to `_skimDonatedAssets`.
- Alternatively seed a minimum initial mint (dead shares / reserve address) at first deposit so price cannot be inflated against a dust supply.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
function testShareInflationViaStrategyTokenDonation() external {
    // 1. Buffer phase: attacker is first AA depositor with dust
    vm.startPrank(attacker); // KYC'd wallet
    underlying.approve(address(cdoEpoch), type(uint256).max);
    idleCDO.depositAA(1); // mints ~1e12 shares at price == oneToken
    vm.stopPrank();

    // 2. Attacker holds strategyToken receipts (e.g. from a prior
    //    requestInstantWithdraw) and donates them to the CDO
    uint256 donation = 2_000 * ONE_SCALE;
    deal(address(strategyToken), attacker, donation); // stands in for legit receipt
    vm.prank(attacker);
    IERC20(address(strategyToken)).transfer(address(cdoEpoch), donation);

    // priceAA now reflects donated NAV
    uint256 inflated = cdoEpoch.virtualPrice(address(AAtranche));
    assertGt(inflated, cdoEpoch.oneToken());

    // 3. Victim deposits ~half the donation amount
    uint256 victimAmt = 1_900 * ONE_SCALE;
    deal(defaultUnderlying, victim, victimAmt);
    vm.startPrank(victim);
    underlying.approve(address(cdoEpoch), victimAmt);
    uint256 minted = idleCDO.depositAA(victimAmt);
    vm.stopPrank();
    assertLt(minted, ONE_TRANCHE_TOKEN); // victim gets dust shares

    // 4. Attacker requests withdraw of all shares and captures NAV
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    // after funding/claim, attacker underlying > victimAmt - remainder
}
```

Uncertainty note: the exact `strategyToken` receipt source (instant-withdraw receipt vs another legitimate holder) depends on epoch configuration, and I could not fully verify that `_updateAccounting` consumes `_managedContractValue` on every path rather than `getContractValue` (which also includes raw `token`). The core mechanism — NAV counting `balanceOf(strategyToken)` with no skim, plus dust-supply minting at `oneToken` — is confirmed in the cited code. A Devin session can finalize and run the PoC.
