### Title
Unauthenticated `clearMfa({userId})` accepts an arbitrary target user ID, allowing MFA state to be cleared for a user other than the caller - ([File: src/dist/cjs/index.js])

### Summary
The `mfa.clearMfa` method exposed on the `Privy` client (implemented by the `Zt` class in `src/dist/cjs/index.js`) forwards a caller-supplied `{userId}` object directly to the embedded-wallet iframe proxy without first resolving or verifying an access token for the calling session, unlike every other MFA method on the same class. This mirrors the `assertGovernanceApproved` bug class: a state-mutating operation that trusts a caller-supplied identifier instead of binding the action to the authenticated caller's own identity, enabling an attacker who can reach the SDK instance to trigger a security-relevant state change against an arbitrary account.

### Finding Description
Every other MFA-affecting method on `Zt` (the class assigned to `Privy.mfa`) requires and attaches the caller's own access token before performing a privileged action:

```
async verifyMfa(){...accessToken:await this.getAccessTokenInternal()}
async unenrollMfa(e){...accessToken:await this.getAccessTokenInternal()}
async unlinkPasskey({...}){...accessToken:await this.getAccessTokenInternal()}
``` [1](#0-0) 

In contrast, `clearMfa` takes an arbitrary object `e` (containing `userId`) and passes it straight through to the proxy with no token resolution and no comparison against the caller's own authenticated session:

```
async clearMfa(e){if(!this.proxy)throw new C({error:`Embedded wallet proxy not initialized`,code:`embedded_wallet_webview_not_loaded`});return await this.proxy.clearMfa(e)}
``` [1](#0-0) 

The proxy-level implementation simply posts a message to the embedded-wallet iframe with whatever payload it receives, again with no access-token binding:

```
clearMfa(e){return I(this.waitForReady().then(()=>this.invoke(`privy:mfa:clear`,e)),{msg:`Operation reached timeout: mfa:clear`})}
``` [1](#0-0) 

The only in-repo call sites pass the *current* session's own `userId` (e.g., inside `unenrollMfa`, `submitEnrollMfa`, `unlinkPasskey`, and `logout`):

```
logout(e){...e?.userId&&this._mfa.clearMfa({userId:e.userId})...}
``` [1](#0-0) 

However, `mfa` is a public property of the `Privy` client (`this.mfa=new Zt(this._privyInternal)` in the `tn`/`Privy` constructor), so `clearMfa` is a directly callable public API. Nothing in `Zt.clearMfa` or `$e.clearMfa` enforces that the supplied `userId` corresponds to the currently authenticated session — the function has no access-control check binding the action to the caller's own identity, exactly the missing-authorization pattern described in the report (a privileged/sensitive action reachable with an attacker-supplied target identifier instead of `msg.sender`/the caller's own session). [1](#0-0) 

### Impact Explanation
If the iframe-side handler for `privy:mfa:clear` trusts the `userId` field from this message without independently re-deriving it from a verified access token, any code path with access to the `Privy` instance (e.g., a malicious/compromised script sharing the page context, or a caller who obtains a `userId` value from elsewhere, such as a public profile or shared link) can request that a target user's MFA methods be cleared. This is an MFA/recovery-gating bypass: removing MFA protection on an account lowers the bar for subsequent account takeover of embedded wallet operations that are otherwise gated behind `invokeWithMfa`. This falls squarely within the accepted impact category of "MFA or recovery bypass."

### Likelihood Explanation
Exploitability depends on whether the iframe/back-end that receives the `privy:mfa:clear` postMessage independently validates the `userId` against a signed/verified access token rather than trusting the field verbatim. The SDK itself provides no such binding, and it is the only MFA-mutating method in the class that omits the `accessToken` parameter that all sibling methods explicitly attach. This inconsistency is a concrete, code-visible violation of the defense-in-depth pattern used everywhere else in this class, making it a realistic candidate for a broken trust boundary if the iframe does not perform out-of-band verification.

### Recommendation
Remove the caller-supplied `userId` parameter from `Zt.clearMfa` / `$e.clearMfa` (and the underlying `privy:mfa:clear` message) and instead have the SDK derive the target user strictly from the currently authenticated session's access token (as done in `unenrollMfa`, `verifyMfa`, and `unlinkPasskey`), so the iframe/back-end can bind the clear-MFA action to the token's subject rather than an attacker-controllable identifier.

### Proof of Concept
1. Obtain a reference to a `Privy` client instance in a context where `privy.mfa.clearMfa` is reachable (e.g., a script running in the same page/context as an integrator's app, or any caller with knowledge of a victim's Privy `userId`).
2. Call `await privy.mfa.clearMfa({ userId: '<victim-user-id>' })`.
3. Observe that the call proceeds directly to `this.proxy.clearMfa(e)` → `invoke('privy:mfa:clear', {userId: '<victim-user-id>'})` without any access-token check tying the request to the current session, unlike `unenrollMfa`/`verifyMfa`/`unlinkPasskey`, which all require `await this.getAccessTokenInternal()`.
4. If the iframe/back-end honors the `userId` field without independently re-verifying the caller's identity via a signed token, the victim's MFA methods are cleared, weakening their account's protection without their consent — analogous to the original report's unauthorized state-locking action performed against an arbitrary target.
