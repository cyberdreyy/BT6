### Title
Front-runnable `InitializeNonceAccount` allows unauthorized takeover and draining of durable-nonce accounts - ([File: programs/system/src/system_instruction.rs])

### Summary
The System Program's nonce-account initialization step is not access-controlled and is not bound to the account creation step, mirroring the Ramses V3 "unprotected `initialize` after separate deploy" bug class. An attacker who observes a `CreateAccount` transaction for a soon-to-be nonce account can race the legitimate owner's `InitializeNonceAccount` transaction, setting themselves as the nonce authority, and subsequently drain the account's lamports via `WithdrawNonceAccount`.

### Finding Description
`initialize_nonce_account` performs no signer or ownership check on either the target account or the caller — it only validates that the account is writable, holds enough lamports for rent-exemption, and is currently `State::Uninitialized`, before unconditionally writing the caller-supplied `nonce_authority` into the account state: [1](#0-0) 

The instruction dispatcher confirms no signature requirement is enforced for account index 0 (the nonce account) beyond what the runtime's generic account-writability rules provide; the handler simply borrows the account and forwards to `initialize_nonce_account`: [2](#0-1) 

Because Solana account creation (`CreateAccount`, signed by the new keypair) and nonce initialization (`InitializeNonceAccount`, which requires no signature tied to that keypair) are commonly issued as two separate instructions/transactions, an attacker who sees the `CreateAccount` transaction land (the new account's pubkey and its "Uninitialized" nonce-shaped data are now public) can submit their own `InitializeNonceAccount` naming themselves as `authorized`, before the legitimate initializer's transaction executes. Whoever's `InitializeNonceAccount` transaction is processed first wins — no authority tied to account creation is checked.

Once the attacker's transaction sets `data.authority` to their own pubkey, they gain full withdrawal rights: `withdraw_nonce_account` for an `Initialized` nonce checks only `check_signer(&data.authority)`, which is now attacker-controlled, letting them withdraw the account's lamports (including the funds the legitimate creator deposited for rent-exemption): [3](#0-2) 

This is structurally the same bug class as the Ramses report: a critical binding step ("who owns/controls this freshly-created resource") is exposed as a permissionless instruction that is expected — but not enforced — to run atomically with account creation.

### Impact Explanation
Unlike the Ramses case (pure griefing/wasted deployment), the Agave analog allows concrete unauthorized state mutation and fund loss: an attacker can seize the `authority` field of another user's nonce account and subsequently withdraw its lamports, which fits the "unauthorized fund/state mutation" impact bar via the fee/rent/nonce accounting path.

### Likelihood Explanation
Exploitability depends on the victim submitting `CreateAccount` and `InitializeNonceAccount` as separate, non-atomic transactions (rather than the conventional single-transaction pattern most wallets/CLIs use, e.g. `solana create-nonce-account` bundles both in one transaction). If that convention is followed, the race window does not exist. The vulnerability is real but its practical likelihood is bounded by whether callers deviate from the standard atomic construction pattern — this exactly parallels the Ramses report's own conclusion that the risk is eliminated by atomic execution.

### Recommendation
Documented as a known risk mitigated by convention (atomic `CreateAccount` + `InitializeNonceAccount`, as already used by the standard SDK helper). No code defect independent of caller-side atomicity was found; this is a design-level caveat, not an implementation bug enforceable purely within `system_processor.rs`/`system_instruction.rs`.

### Proof of Concept
1. Victim submits `CreateAccount` for pubkey `N` (signed by `N`'s keypair) with `owner = system_program`, `space = nonce::State::size()`, and sufficient lamports.
2. Attacker observes this transaction land and immediately submits `InitializeNonceAccount(attacker_pubkey)` referencing account `N` — no signature from `N` or from the intended authority is required by `initialize_nonce_account`.
3. If the attacker's transaction lands first, `N`'s nonce authority becomes `attacker_pubkey` per [4](#0-3) .
4. Attacker submits `WithdrawNonceAccount` signed by their own key, passing the `check_signer(&data.authority)` check, and drains `N`'s lamports per [3](#0-2) .

**Note:** I could not fully verify from indexed code whether the standard SDK/CLI nonce-account creation helper (`system_instruction::create_nonce_account` or similar) is always invoked atomically in a single transaction in every code path across this repo, since the client-side instruction builder for nonce accounts was not found in the indexed portion of this repository (it may live in an SDK crate outside the indexed scope). This affects confidence in the practical likelihood; a Devin session with full repository access could confirm whether any first-party caller (CLI, RPC helper, validator tooling) ever splits these into separate transactions.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
