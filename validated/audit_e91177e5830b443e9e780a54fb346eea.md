### Title
Response cache key ignores `WorkflowID`, causing cross-workflow cached HTTP response reuse in the CRE Gateway HTTP Action handler - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The Gateway's HTTP Action response cache (`responseCache`) keys cached responses using `req.Hash()`, and the handler's own documentation states caching is "scoped by workflow ID to prevent cross-workflow data leakage." However, the request `Hash()` implementation does not actually incorporate `WorkflowID` (only `WorkflowOwner`, method, URL, headers, and body), so two different workflows owned by the same address that issue functionally identical HTTP action requests will collide on the same cache key and receive each other's cached response, similar in class to the reported vault-withdrawal bug where an accounting/gating value diverges from the actual value used to satisfy the request.

### Finding Description
`responseCache.Fetch`/`Set`/`isExpiredOrNotCached` all use `req.Hash()` as the sole cache key [1](#0-0) . The package README explicitly documents the intended isolation guarantee: "**Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [2](#0-1) .

The test suite for the hash function proves this guarantee does not hold in the implementation: it explicitly asserts that requests with *different* `WorkflowID` values produce the *same* hash, while only differing `WorkflowOwner` values change the hash [3](#0-2) . This is the direct analog of the reported bug class: a value that is supposed to gate/scope an operation (the workflow identity used for cache isolation, akin to the "amount" that should have matched what was actually transferred) diverges from what the code actually enforces — the isolation boundary that is documented and expected does not match what the hashing code implements, since `WorkflowID` is silently dropped from the key while only `WorkflowOwner` is retained.

Cache entries are written from responses to outbound HTTP requests originating from workflow nodes reachable through the gateway's `HandleNodeMessage` path (`handleWebAPIOutgoingMessage` → cache → `sendHTTPMessageToClient`) and are looked up per subsequent request [4](#0-3) . Since workflow owners can typically run multiple distinct workflows (different `WorkflowID`s) under the same `WorkflowOwner`, and the gateway is the internet-facing component brokering these HTTP Action requests/responses on behalf of DON nodes, one workflow's cached HTTP response (which may contain owner/workflow-specific data returned by an external endpoint) can be served to a different, unrelated workflow that happens to issue a request with the same method/URL/headers/body and owner.

### Impact Explanation
This is a cross-workflow response confusion bug: a workflow can receive another workflow's cached HTTP action response merely because both share the same `WorkflowOwner` and issue byte-identical outbound HTTP requests. Depending on what the external HTTP endpoint returns (e.g., data keyed by request parameters embedded in headers/body that legitimately differ per workflow but happen to coincide, or endpoints whose responses vary by caller context tracked server-side out of band), this can leak data intended for one workflow into another workflow's execution, or cause a workflow to act on stale/foreign data. This falls squarely within the flagged category of "cross-user response confusion" in an internet-facing gateway cache.

### Likelihood Explanation
Likelihood is high for any deployment where a single workflow owner runs multiple workflows that call the same external HTTP endpoint with identical parameters (a common pattern, e.g., periodic price/data fetches with fixed URLs) — the collision requires no malicious action, only the documented-but-unenforced isolation assumption to be relied upon. The bug is directly demonstrated by the codebase's own test file, confirming it is a reachable, un-mitigated implementation gap rather than a theoretical possibility.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the `Hash()` computation for `gateway.OutboundHTTPRequest` used as the response cache key, so that cache entries are truly scoped per workflow as documented. Add/adjust the hash test to assert different `WorkflowID` values with otherwise identical fields produce different hashes, matching the "Workflow Isolation" guarantee in the README.

### Proof of Concept
The existing test in the repository already demonstrates the flaw: [5](#0-4) 
This shows `req1` and `req2` with different `WorkflowID` ("workflow-123" vs "workflow-456") but otherwise-identical fields produce `hash1 == hash2`. Given `responseCache.Fetch` keys strictly on this hash [6](#0-5) , workflow-123's cached response would be served to workflow-456's identical outbound request (or vice versa), violating the documented workflow isolation guarantee.

Note: I could not fully trace how `WorkflowOwner`/`WorkflowID` are populated on `gateway.OutboundHTTPRequest` at request-construction time (the `gateway.OutboundHTTPRequest.Hash()` implementation itself lives in an external `chainlink-common` package not indexed in this repo), so I was unable to inspect the exact field composition of the hash beyond what the test file demonstrates. This is sufficient to establish the root cause and its confirmed behavior via the test assertions, but a full walkthrough of the hash source code was not available in this index.

func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

// Fetch fetches a response from the cache if it exists and
// the age of cached response is less than the max age of the request.
// If the cached response is expired or not cached, it fetches a new response from the fetchFn
// and caches the response if it is cacheable and storeOnFetch is true.
//
// The mutex is only held during cache map access (microseconds), not during fetchFn execution.
// Singleflight deduplicates concurrent requests to the same cache key so only one fetchFn
// runs per key, while requests to different keys execute in parallel.
// Cache read and write happen inside the singleflight callback to ensure the key remains
// in-flight until the result is stored, preventing duplicate fetches.
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

func (h *handler) handleWebAPIOutgoingMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.lggr.Debugw("handling webAPI outgoing message", "messageId", msg.Body.MessageId, "nodeAddr", nodeAddr)
	if !h.nodeRateLimiter.Allow(nodeAddr) {
		return fmt.Errorf("rate limit exceeded for node %s", nodeAddr)
	}
	var payload Request
	err := json.Unmarshal(msg.Body.Payload, &payload)
	if err != nil {
		return err
	}

	timeout := time.Duration(payload.TimeoutMs) * time.Millisecond
	req := network.HTTPRequest{
		Method:           payload.Method,
		URL:              payload.URL,
		Headers:          payload.Headers,
		Body:             payload.Body,
		MaxResponseBytes: payload.MaxResponseBytes,
		Timeout:          timeout,
	}
