### Title
APR0 withdraw requests permanently brick `stopEpoch` once APR is set non-zero — missing check on `unscaledApr` vs open `apr0TotalPrincipal` freezes all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts unconditionally when `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged lender can open an APR0 withdraw receipt (`requestWithdraw` while APR is 0); if the honest manager later raises the APR — a normal, expected operation — every subsequent `stopEpoch` call reverts before `apr0TotalPrincipal` is cleared. Since `epochNumber` only advances inside `stopEpoch`/`deposit`, the APR0 principal can never settle, creating a permanent deadlock that freezes the entire pool's funds.

### Finding Description
The bug class of CVE-2018-13301 — a missing check of a value before using it, causing a hard failure — maps to `IdleCreditVault.sol`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:499-508
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

- Any KYC-passing lender calls `IdleCDOEpochVariant.requestWithdraw` while `unscaledApr == 0`. `IdleCreditVault.requestWithdraw` routes to `_requestWithdrawApr0`, which sets `apr0Users[user].principal` and increments `apr0TotalPrincipal` (lines 567-577).
- The honest manager/owner later raises the pool APR (`unscaledApr != 0`). This is a routine, permitted admin action; there is no guard preventing it while an APR0 bucket is open, and nothing settles or migrates the bucket on the APR change.
- `apr0TotalPrincipal` can only be zeroed inside `prepareStopEpochWithApr0` at line 540 — but that line is unreachable whenever `unscaledApr != 0` and `_principal != 0`, because line 507 reverts first.
- `_settleApr0` (lines 545-565) only settles user receipts after `epochNumber` advances past `principalEpoch`, and `epochNumber` only increments inside `deposit()` during `stopEpoch` (lines 607-610). So no user action can unblock it either.
- Result: `stopEpoch` reverts with `NotAllowed()` forever. The epoch cannot close, `epochEndDate` has already passed, withdrawal claims gated on `epochNumber <= lastWithdrawRequest` (line 326) never mature for new requests, and all borrower/strategy funds remain locked.

### Impact Explanation
Permanent freezing of all funds in the vault. The epoch is running, `block.timestamp >= epochEndDate`, yet `stopEpoch` always reverts. LPs cannot withdraw (claims require the epoch to finalize), deposits during epoch are disabled, and the only theoretical escape — forcing a default — requires the borrower (honest per scope) to actually fail repayment. Quantified loss: the full pool NAV (`getContractValue()` plus pending withdraws) is frozen indefinitely, triggered by one ordinary unprivileged withdraw request plus a routine APR change.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only (a) an epoch where `unscaledApr == 0` (a supported configuration — the APR0 flow exists precisely for this), (b) any user request in that epoch, and (c) the manager raising APR before the epoch ends — a plausible operational sequence, since APR changes between epochs are the mechanism that normally drives instant-withdraw APR deltas. The attacker needs no special role; a standard KYC'd lender suffices. Note: this assessment assumes no separate owner action (e.g., a setter that force-clears `apr0TotalPrincipal`) exists to escape the deadlock — I was not able to fully verify all recovery/admin paths within the exploration budget, which is the main uncertainty in this finding.

### Recommendation
Handle an open APR0 bucket on the APR-change path instead of reverting in `prepareStopEpochWithApr0`: either (a) settle APR0 principal at the zero rate and clear `apr0TotalPrincipal` when `unscaledApr` changes away from 0 (treating the bucket as matured with no interest), or (b) in `prepareStopEpochWithApr0`, when `unscaledApr != 0`, close the bucket (`apr0TotalPrincipal = 0`) and skip APR0 interest allocation rather than reverting. Alternatively, revert APR-updating admin calls while `apr0TotalPrincipal != 0` so the inconsistent state is never entered.

```solidity

vm.warp(cdoEpoch.epochEndDate() + 1);
```
