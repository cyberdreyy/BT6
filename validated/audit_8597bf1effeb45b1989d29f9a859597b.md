### Title
A single dust-sized queued withdrawal permanently freezes all withdrawal processing for the epoch via `Is0` revert - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external report (CVE-2022-21365) is a low-cost, unauthenticated partial denial of service triggered by crafted input to a parser. The analog in idle-tranches is a dust-input DoS on the epoch withdrawal pipeline: an unprivileged KYC'd tranche holder can enqueue a withdrawal request so small that the implied epoch withdraw price rounds to zero, causing `processWithdrawRequests()` to revert with `Is0()` forever and freezing every other user's queued withdrawal for that epoch.

### Finding Description
`IdleCDOEpochQueue.requestWithdraw` accepts any `amount` of tranche tokens with no minimum, crediting `userWithdrawalsEpochs[msg.sender][nextEpoch]` and `epochPendingWithdrawals[nextEpoch]` [1](#0-0) .

During the buffer period, the manager calls `processWithdrawRequests()`, which forwards the aggregate `_pending` to `IdleCDOEpochVariant.requestWithdraw` and computes `_epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending`. If `_underlyingsRequested` rounds to 0 (a dust request whose tranche value is below 1 unit of underlying at current `virtualPrice`), `_epochPrice == 0` and the function reverts with `Is0()` [2](#0-1) . Because the whole call reverts, `epochPendingWithdrawals[_epoch]` is never cleared, so every subsequent call reverts identically — the state is unrecoverable by the manager.

This is not hypothetical: `testProcessWithdrawRequestsWith0Price` demonstrates that a 100-wei tranche request makes `processWithdrawRequests` revert with `Is0` [3](#0-2) .

The only escape is `deleteWithdrawRequest`, which refunds tranche tokens — but it can only be called by the attacker for their own entry (`userWithdrawalsEpochs[msg.sender]`), and it is only blocked *after* a price is set, which never happens [4](#0-3) . Honest users cannot delete the attacker's dust entry, and their own entries remain locked in `epochPendingWithdrawals` aggregation.

### Impact Explanation
Permanent freezing of funds: all tranche tokens queued for withdrawal in that epoch by every user are stuck — they can neither be processed into claims nor individually refunded (a victim's `deleteWithdrawRequest` only refunds their own `amount`, which is fine for them, but the epoch can still never be processed, and any user who doesn't delete loses the withdrawal path entirely; more importantly each non-attacker user must individually discover and execute a delete, and users who already had claims pending rely on `pendingClaims`/`epochPendingClaims` bookkeeping that can never advance). At minimum, all users' queued withdrawals for the epoch are frozen indefinitely unless each one individually exits via `deleteWithdrawRequest`, and the queue's withdrawal pipeline for that epoch is permanently bricked. Attacker cost: ~100 wei of tranche tokens plus gas.

### Likelihood Explanation
High. Requires only a KYC-passing wallet and a dust tranche balance (1 wei of underlying deposited is sufficient). No privileged role, no timing race — the request just has to sit in `epochPendingWithdrawals[nextEpoch]` when the manager processes it. There is no minimum-request check anywhere in `requestWithdraw`, and `Is0` explicitly hard-reverts instead of skipping or flagging dust (contrast with `isEpochWithdrawZero` handling added for the claim side [5](#0-4) ).

### Recommendation
Enforce a minimum withdrawal size in `requestWithdraw`/`processWithdrawRequests` (e.g., revert at request time if `amount < minWithdrawal`, or skip dust entries), or handle the `_epochPrice == 0` case the same way zero-rounded claims are handled — record a zero-price epoch marker instead of reverting, so processing completes and other users can proceed (attacker's dust then simply claims 0).

### Proof of Concept
Foundry fork PoC sketch (mirroring `testProcessWithdrawRequestsWith0Price`, test/foundry/IdleCDOEpochQueue.t.sol:1431):

```solidity
// epoch running; attacker (KYC'd) holds >= ~100 wei of AA tranche
uint256 dust = 100;
vm.prank(attacker);
tranche.approve(address(queue), dust);
vm.prank(attacker);
queue.requestWithdraw(dust);          // added to epochPendingWithdrawals[nextEpoch]

// honest user also queues a real withdrawal in the same epoch
vm.prank(victim);
queue.requestWithdraw(victimTrancheBal);

_stopCurrentEpoch();                   // buffer period

// manager tries to process — always reverts
vm.prank(manager);
vm.expectRevert(Is0.selector);
queue.processWithdrawRequests();       // _epochPrice == 0 -> Is0

// retrying never helps; victim's funds are frozen unless victim
// independently calls deleteWithdrawRequest; epoch is bricked
```

```text
  function deleteWithdrawRequest(uint256 _requestEpoch) external {
    // if the epoch withdraw price is already set, withdrawal requests were already processed so
    // the withdraw request can't be deleted. Withdraw requests can be deleted even if the epoch is running
    _checkNotAllowed(epochWithdrawPrice[_requestEpoch] != 0 || isEpochWithdrawZero[_requestEpoch]);

    uint256 amount = userWithdrawalsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request for the epoch
    userWithdrawalsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending withdraw requests
    epochPendingWithdrawals[_requestEpoch] -= amount;
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, amount);
```
