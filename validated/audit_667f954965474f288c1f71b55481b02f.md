### Title
Reorg permit granted on one block's timing is applied tenure-wide, excluding *other*, never-checked signed blocks from the double-sign conflict guard - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a new tenure is allowed to reorg a prior tenure by inspecting only that prior tenure's **first** approved block (`get_first_approved_block_in_tenure`) and its timing relative to the next sortition. If that single block qualifies (poorly-timed / close to the burn-block transition) and the tenure has at most one globally-accepted block, the *entire* tenure is marked superseded (`mark_tenure_superseded`), keyed only by `consensus_hash`. Downstream, `SignerDb::get_signed_conflicts` / `Signer::reorg_permit_stands` exclude **any** signed block belonging to that superseded tenure from the double-sign conflict guard, not just the specific block whose timing was actually evaluated. This lets a signature over a second, well-timed, never-globally-accepted block in the reorged tenure lose its equivocation protection, even though that block was never individually vetted for reorg eligibility.

### Finding Description
The permit-granting logic in `check_parent_tenure_choice` looks only at the tenure's first approved block: [1](#0-0) 

If `globally_accepted_blocks <= 1` and the *first* block's approval-to-sortition timing is short enough, the tenure is pushed into `superseded_tenures` and later recorded wholesale: [2](#0-1) 

The record itself is keyed only by the reorged tenure's `consensus_hash`, with no reference to which specific block was checked: [3](#0-2) 

`get_signed_conflicts` joins on `consensus_hash` alone, so *every* row (i.e., every block ever signed in that tenure) inherits the `superseded_by` annotation: [4](#0-3) 

And at pre-commit time, `reorg_permit_stands` unconditionally excludes a conflict from blocking as long as the permitting sortition is canonical - this check is applied *before*, and independent of, `conflict_still_blocks` (the node-derived "is this block actually dead" check that would otherwise protect an un-globally-accepted sibling): [5](#0-4) [6](#0-5) 

This mirrors the H-3 pattern precisely: the "check" is performed against one narrow instance (the geometric pool's marginal price / here, the tenure's *first* block's timing), but the resulting exemption is applied to the aggregate/whole (the whole liquidity pool / here, the whole tenure's set of signed blocks), letting an attacker realize an effect (bypassing a price band / bypassing the equivocation guard) for something that was never itself checked.

Concretely: tenure A's first block A1 is proposed and approved very close to the burn-block transition (satisfying the "poorly timed" reorg-permission condition). Before or shortly after that, a signer separately signs a second block A2 in the same tenure A (e.g., through the normal `LocallyAccepted`/`PreCommitted` flow, at a normal, unhurried time), which never reaches global acceptance (e.g. because the group threshold stalls, a race with the next sortition, or the signer set is split). When tenure B's proposal is evaluated in `check_parent_tenure_choice`, only A1's timing is inspected (`get_first_approved_block_in_tenure` returns the first block, and `globally_accepted_blocks` counts only global acceptances, which A2 lacks), so the reorg is permitted and tenure A is marked wholly superseded. From this point on, any signer who separately signed A2 will find that `reorg_permit_stands` excludes A2 from `get_signed_conflicts()` filtering as long as B's sortition is canonical - even though `conflict_still_blocks` would otherwise correctly keep blocking on an un-globally-accepted sibling at the same height. That signer can then go on to sign B's conflicting block at the same (or higher) height as A2, producing two signatures over conflicting blocks at the same height in different tenures from the same signer - the exact double-sign the whole freshness/conflict machinery in section 5 of the signer flow exists to prevent.

### Impact Explanation
This breaks the "one-per-height" equivocation guard for a signer: a signature legitimately placed over block A2 no longer blocks a later signature over a conflicting block B at the same/higher height, purely because a *different, unrelated* block (A1) in the same tenure happened to qualify for a reorg permit. If both A2 and B accumulate enough signatures via other signers exhibiting the same gap, this can allow two mutually conflicting blocks to both approach (or reach) the acceptance threshold, a critical safety violation ("a signer signing... a conflicting block").

### Likelihood Explanation
This requires a specific but reachable sequencing: a tenure whose first block is proposed close to the sortition boundary (the miner or network timing already needs to be near the edge, which is a fairly common non-adversarial occurrence near tenure changes) plus a second block in that same tenure being signed by at least one signer without reaching global acceptance before the next sortition. Both conditions are plausible during normal tenure-boundary races and do not require a majority of signers or possession of another signer's key - only the natural occurrence (or miner-induced occurrence, since a one-slot miner controls when and how it proposes blocks within its tenure) of a second block proposal in the outgoing tenure.

### Recommendation
Scope the reorg permit to the specific block(s) that were actually evaluated for reorg-timing eligibility, not the whole tenure. Either: (a) record superseded status per-block (keyed by `signer_signature_hash`, not just `consensus_hash`), so only the block whose timing was checked is exempted from `get_signed_conflicts`; or (b) re-validate every block claimed to be superseded (not only the first) against the same timing rule before excluding it, e.g. by having `check_parent_tenure_choice` enumerate *all* locally/pre-committed blocks in the tenure (not just the first-approved one) and require every one of them to satisfy the "poorly timed" condition before granting the permit.

### Proof of Concept
No executable PoC was built (analog/code-review finding derived from static analysis of the referenced functions); a full PoC would require constructing a `SignerDb` fixture with two `BlockInfo` rows in the same tenure (one meeting the reorg-timing exemption, one only locally-accepted with different timing), driving `check_parent_tenure_choice` to permit the reorg, and then exercising `handle_block_pre_commit`/`reorg_permit_stands` to show the second block's conflict is excluded despite `conflict_still_blocks` returning `true` for it in isolation.

    /// Record that we permitted the tenure identified by `superseded_by_*` to reorg this one
    /// under the reorg-timing rules (`first_proposal_burn_block_timing`).
    ///
    /// Having sanctioned the replacement, our own signature over what this tenure built must not
    /// then block it: its blocks stop counting as conflicts (see
    /// [`SignerDb::get_signed_conflicts`]). Recorded when the reorg is permitted rather than
    /// derived at signing time, because by the time a replacement reaches the pre-commit
    /// threshold the sortition view that sanctioned the reorg may be long gone.
    ///
    /// The permit is only honored while the permitting tenure's sortition is still canonical
    /// (checked against the node when the record is applied): if a burnchain fork orphans it,
    /// the reorg we sanctioned can no longer happen, so the record must not keep suppressing
    /// this tenure's conflicts. A re-permit by a different tenure replaces the record, so the
    /// latest permitting sortition is the one checked. Records age out via
    /// [`SignerDb::prune_superseded_tenures`].
    pub fn mark_tenure_superseded(
        &mut self,
        consensus_hash: &ConsensusHash,
        burn_block_height: u64,
        superseded_by_consensus_hash: &ConsensusHash,
        superseded_by_burn_block_hash: &BurnchainHeaderHash,
    ) -> Result<(), DBError> {
        self.db.execute(
            "INSERT OR REPLACE INTO superseded_tenures (consensus_hash, burn_block_height, superseded_by_consensus_hash, superseded_by_burn_block_hash, superseded_at) VALUES (?1, ?2, ?3, ?4, ?5)",
            params![
                consensus_hash,
                u64_to_sql(burn_block_height)?,
                superseded_by_consensus_hash,
                superseded_by_burn_block_hash,
                u64_to_sql(get_epoch_time_secs())?
            ],
        )?;
        Ok(())
    }

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
