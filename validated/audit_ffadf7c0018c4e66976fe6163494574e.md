### Title
Post-close withdraw requests mint unbacked receipts that drain the funded claim reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The analog of CVE-2025-55661 — a parser accepting a crafted input that corrupts a bounded buffer — is `IdleCreditVault.requestWithdraw` accepting a withdraw request while the pool is closed (`epochEndDate == 0`). The function explicitly skips adding the request to `pendingWithdraws` "because a closed pool has no later stopEpoch to fund it", yet still mints the user a 1:1 strategy-token receipt and records `withdrawsRequestsByEpoch` / `lastWithdrawRequest`. On the claim side, `_claimFundedWithdrawRequest` waives the one-epoch wait precisely when `epochEndDate() == 0`, so the unbacked receipt is immediately redeemable at par from underlying held by the strategy — funds that were transferred there by `collectWithdrawFunds` to back legitimate pre-close receipts. One crafted request in the closed phase therefore pays out other users' funded claims.

### Finding Description
In `requestWithdraw`, when the pool is closed, the code burns the CDO's principal tokens and mints `_amount` receipt tokens to the user, but deliberately does not increase `pendingWithdraws` (`isClosed` check at lines 259-280). No funding will ever arrive for this receipt. The same request is still recorded in `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]`.

In `_claimFundedWithdrawRequest`, the epoch-wait guard `epochNumber <= lastWithdrawRequest[_user]` is bypassed entirely when `IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` (line 326). The claim then burns the receipt and calls `_transferFundedClaim(_user, amount)`, which pays underlying out of the strategy's token balance — the same balance that `collectWithdrawFunds` funded at the final stopEpoch for the pre-close pending receipts.

The broken invariant is "one receipt, one payout": a post-close receipt has zero backing reserved, but claims against the shared funded pot at 1:1. The guards do not stop it: `_onlyIdleCDO` is satisfied because `IdleCDOEpochVariant.requestWithdraw` (lines 739-791) has no closed-pool check — it only checks `allowAAWithdrawRequest`/`allowBBWithdrawRequest` flags and `isWalletAllowed`, which remain enabled. `_skimDonatedAssets` and `_updateAccounting` do not prevent the call. The `lossRecoveryPriceByEpoch` early-revert in `requestWithdraw` only applies to users with prior haircutted receipts, not a fresh attacker.

Uncertain detail: whether the honest owner leaves the allow-flags on after closing the pool. `stopEpochWithDuration`/`_interest == 1` close-pool flow does not appear to force `allowAAWithdrawRequest = false`, and keeping claims open requires the flag anyway, so the attack surface is realistic in the closed state.

### Impact Explanation
Direct theft plus freezing. After the pool closes and `collectWithdrawFunds` deposits the funded amount for pre-close receipts, any tranche holder (KYC-passed lender or anyone who acquired tranche tokens) can call `cdoEpoch.requestWithdraw(amount, tranche)`, then immediately `claimWithdrawRequest`, and withdraw underlying at par up to the strategy's funded balance. Each unbacked claim reduces the balance available to legitimate receipt holders, whose later claims revert on insufficient balance — permanent freezing/theft of their unclaimed withdrawals. Attacker loss bounded only by their tranche balance converted at `tranchePrice`; gain is up to the entire funded reserve held by the strategy.

### Likelihood Explanation
Requires only: (a) the pool reaches closed state via the `_interest == 1` recall path, (b) at least one funded pending receipt sits unclaimed in the strategy (common — users routinely delay claims across epochs), and (c) withdraw-request flags remain enabled (needed for normal operation). The attacker needs tranche tokens but not the borrower's or manager's cooperation; all transactions are unprivileged. Likelihood is moderate: it needs the closed-pool phase and residual unclaimed funded receipts.

### Recommendation
In `IdleCreditVault.requestWithdraw`, revert when `IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` (no funded epoch will ever arrive), or alternatively still increment `pendingWithdraws` and have the close flow fund it. Symmetrically, block `requestInstantWithdraw` post-close if reachable. Add a regression test that a post-close request cannot mint a claimable receipt.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Foundry fork PoC: post-close request mints an unbacked receipt that pays at par.
function testPostCloseRequestDrainsFundedReceipts() external {
    uint256 amountWei = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amountWei);          // victim LP (test contract)
    _depositWithUser(attacker, amountWei, true); // KYC'd attacker LP

    _startEpochAndCheckPrices(0);

    // Victim requests withdraw during the epoch; basis enters pendingWithdraws.
    vm.prank(victim);
    uint256 victimBasis = cdoEpoch.requestWithdraw(victimTrancheBal, address(AAtranche));

    // Honest manager closes the pool: stopEpoch(…, _interest = 1) recalls all
    // funds and collectWithdrawFunds moves victimBasis underlying into the vault.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 1); // close-pool sentinel
    assertEq(cdoEpoch.epochEndDate(), 0);

    uint256 vaultCash = underlying.balanceOf(address(strategy));
    assertGe(vaultCash, victimBasis); // funded reserve for victim's receipt

    // Attacker (still holding tranche tokens) requests AFTER close.
    uint256 pendingBefore = strategy.pendingWithdraws();
    vm.prank(attacker);
    uint256 attackerBasis = cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche));
    assertEq(strategy.pendingWithdraws(), pendingBefore); // no funding will ever come

    // Epoch-wait guard is skipped because epochEndDate == 0: immediate claim pays at par.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, attackerBasis); // paid from vaultCash

    // Victim's funded receipt now reverts / underpays on claim.
    vm.prank(victim);
    vm.expectRevert(); // ERC20: transfer amount exceeds balance (or shortfall)
    cdoEpoch.claimWithdrawRequest();
}
```

Key trace: `requestWithdraw` mints the receipt but skips `pendingWithdraws += _amount` when `epochEndDate() == 0` (lines 259-280), while `_claimFundedWithdrawRequest` skips the epoch-wait check under the same condition (line 326) and pays from the strategy's funded underlying via `_transferFundedClaim`.
