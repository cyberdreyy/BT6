### Title
Stale rejection weight is never cleared when a signer flips to acceptance, corrupting the aggregated-weight vs. verified-accepts equality in the miner's signature tally - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` maintains a per-block `BlockStatus` (`total_weight_approved`, `total_weight_rejected`, `responded_signers`, `gathered_signatures`) that the `SignerCoordinator` uses to decide whether a block/transaction set has reached the 70% approval threshold or the >30% blocking-rejection threshold. When a signer first rejects a block and later legitimately changes its mind and sends a valid `Accepted` response for the same block (a state transition explicitly permitted by the signer's own `BlockInfo::check_state`, `LocallyRejected -> LocallyAccepted`), the acceptance path increments `total_weight_approved` but nothing ever decrements the earlier `total_weight_rejected` contribution from that same signer.

### Finding Description
The rejection handler only guards against double counting a rejection from the same signer: [1](#0-0) 
It records the signer in `responded_signers` and adds their weight to `total_weight_rejected` if this is the first time that slot has been marked "responded."

The acceptance handler, however, checks a *different* set (`gathered_signatures`) to decide whether to add weight: [2](#0-1) 
Because `gathered_signatures` is disjoint from `responded_signers`/rejection bookkeeping, a signer who previously rejected (and thus is already in `responded_signers`, with their weight already folded into `total_weight_rejected`) will still pass the `!block.gathered_signatures.contains_key(&slot_id)` check when they later accept, so `total_weight_approved` is incremented too — with `total_weight_rejected` never reduced.

The `BlockStatus` struct holds these two weight totals as independent running counters with no cross-reset logic: [3](#0-2) 

This is the direct analog of the Ribbon `vaultState.totalPending` bug: `total_weight_rejected` is a monotonically-increasing tally that is supposed to represent "verified, currently-standing rejections," but the code never retracts a signer's contribution when the underlying vote it was derived from is superseded. The result is the same class of defect — an aggregate counter that drifts away from the true, current state it is meant to summarize.

The coordinator then consumes this drifted value as ground truth: [4](#0-3) 
and separately for permanently/temporarily banning txids based on the same stale per-txid rejection weight: [5](#0-4) 

I was not able to locate any code path (including `reset_rejections`, which I could only confirm exists but could not fully inspect before running out of tool calls) that decrements `total_weight_rejected` when a rejecting signer's vote is superseded by a later acceptance for the same block hash. This is a real gap: `reset_rejections` is only invoked on a coordinator-side timeout (`stacks-node/src/nakamoto_node/signer_coordinator.rs:555`), not on a signer's individual vote flip, so it does not address this specific drift.

### Impact Explanation
`total_weight_approved + total_weight_rejected` can exceed `self.total_weight` (the sum of all signer weights), breaking the "aggregated-weight vs. verified-accepts/rejects" equality the coordinator relies on. Concretely:
- A single ordinary signer that legitimately re-evaluates (rejects, then later accepts the same block after a re-proposal or reconsideration allowed by `should_reevaluate_reject_reason`/`BlockInfo::check_state`) leaves a phantom rejection weight behind.
- If enough such stale rejections accumulate from different signers across the block's lifetime, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can become true even though the *current* set of standing rejections is well under the 30% blocking minority and real acceptances have (or would) reach 70%.
- This causes the miner to declare the block rejected (`NakamotoNodeError::SignersRejected`) and to permanently/temporarily exclude transactions based on stale weight, even though a legitimate signer majority currently supports the block. This is a liveness wedge on block production driven purely by ordinary vote re-evaluation, not by malicious behavior or a majority of colluding signers — it matches the "wedged into never signing/reaching valid outcomes due to stale aggregated weight" impact class.

### Likelihood Explanation
The trigger condition — a signer rejecting and later accepting the very same block (identified by `signer_signature_hash`) — is explicitly modeled as a valid transition in the signer's own local state machine (`LocallyRejected -> LocallyAccepted`, "re-evaluated") and is reachable via normal re-proposal/re-evaluation flows (`should_reevaluate_block`, `should_reevaluate_reject_reason`) without requiring a majority of signers, another signer's key, or any privileged access — only a single signer's ordinary, protocol-sanctioned change of mind on one block.

### Recommendation
Track rejection/acceptance weight from a single canonical per-signer "current vote" state instead of two independently-incrementing counters. When a signer's response for a given block hash transitions from `Rejected` to `Accepted` (or vice versa), subtract the previously-counted weight for the old vote before adding the weight for the new one, e.g. maintain a `HashMap<u32, VoteWeight>` per block and recompute `total_weight_approved`/`total_weight_rejected` from that map, or explicitly decrement `total_weight_rejected` when `gathered_signatures` gains an entry for a slot already present in `responded_signers`/rejection tracking.

### Proof of Concept
1. Node proposes block B; `StackerDBListener` creates a fresh `BlockStatus` for B (`total_weight_approved = 0`, `total_weight_rejected = 0`).
2. Signer S (weight w) sends `BlockResponse::Rejected` for B → `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
3. B is re-proposed/re-evaluated by the signer set (a normal, allowed occurrence per `BlockInfo::check_state`'s `LocallyRejected -> LocallyAccepted` transition), and S now sends `BlockResponse::Accepted` with a valid signature for the same `signer_signature_hash`.
4. Handler at `stackerdb_listener.rs:443-465` checks `!gathered_signatures.contains_key(S)` → true → `total_weight_approved += w`; `total_weight_rejected` is left at its old value (still includes `w`).
5. Now `total_weight_approved + total_weight_rejected > total_weight` by `w`. Repeat with enough distinct signers rejecting-then-accepting across the block's evaluation window and `signer_coordinator.rs`'s rejection-threshold check (`total_weight_rejected + weight_threshold > total_weight`) can fire and reject the block/txids even though every signer currently on record actually accepts.
