### Title
Post-default withdraw requests drain the isolated recovery reserve at 1:1 without contributing collateral - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After `finalizeDefaultRecovery` crystallizes a hard default, all defaulted claimants share a fixed `defaultRecoveryReserve` at `defaultRecoveryPrice < 1`. However, a lender who still holds tranche tokens can call `requestWithdraw` on `IdleCDOEpochVariant`, which routes into `IdleCreditVault.requestWithdraw`'s post-default branch. That branch mints the user a receipt recorded in `postDefaultRequests` that is later paid **1:1** out of `defaultRecoveryReserve`, while the strategy tokens burned from the CDO only freed `amount * recoveryPrice` worth of claim basis. Each post-default request therefore extracts `amount * (1 - recoveryPrice)` more than its fair share, directly stealing from defaulted-epoch receipt holders and remaining active LPs.

### Finding Description
`finalizeDefault` → `IdleCreditVault.finalizeDefaultRecovery` computes a single `reserveAmount` and `recoveryPrice = reserveAmount * 1e18 / totalBasis` over active LP basis plus pending receipts (`contracts/strategies/idle/IdleCreditVault.sol:661-710`). The reserve is intentionally isolated: funded claims must not touch it (`_transferFundedClaim`, lines 897-907), and only default claims may draw it (`_transferDefaultRecovery`, lines 912-917).

In the post-default branch of `requestWithdraw` (lines 247-257):
```solidity
_burn(msg.sender, _amount);        // removes `_amount` of CDO active basis (claim worth _amount * recoveryPrice)
_mint(_user, _amount);             // mints receipt
postDefaultRequests[_user] = _amount;  // payable 1:1 from reserve
```
No underlying is added to `defaultRecoveryReserve`, yet `_claimPostDefaultWithdrawRequest` (lines 760-767) calls `_transferDefaultRecovery(_user, amount)`, decrementing the reserve by the full `_amount`. The comment claims these requests are "already backed by the reserve", but the reserve was sized only for claimants existing at finalization. The burned CDO strategy tokens released only `_amount * recoveryPrice` of reserve entitlement; the difference `_amount * (1 - recoveryPrice)` is extracted from other claimants' recovery.

### Impact Explanation
Direct theft of recovery funds. With `recoveryPrice = 0.5e18`, every 1 unit of post-default withdraw steals 0.5 units of underlying belonging to defaulted-epoch withdraw requesters and active LPs, and can leave the last claimants' claims unbacked (insolvency: `defaultRecoveryReserve` underflows or their `safeTransfer` reverts on insufficient balance). The loss scales linearly with `1 - recoveryPrice`, i.e., the worse the default, the larger the theft per withdrawal.

### Likelihood Explanation
Requires a finalized default with `recoveryPrice < 1` — precisely the scenario the recovery machinery exists for. Any KYC-passed lender holding tranche tokens after finalization is a valid attacker (tranche tokens remain transferable and `requestWithdraw` is still callable; nothing disables it post-default). The CDO's `requestWithdraw` path has no guard on `defaultRecoveryFinalized`, and the vault's only check is that the user has no pre-existing unclaimed requests — trivially satisfied by claiming first, or by using a second account that bought tranche tokens post-default.

### Recommendation
When taking the post-default branch in `requestWithdraw`, either (a) fund the request atomically — increase `defaultRecoveryReserve` by the underlying backing released — or more precisely (b) mint the receipt at `recoveryPrice`-adjusted value and keep it inside the same pro-rata recovery accounting instead of paying 1:1. Concretely, `postDefaultRequests` should store a claim basis that is settled at `defaultRecoveryPrice`, or the burned CDO basis should add `amount * defaultRecoveryPrice / RECOVERY_FULL` equivalent value back to the reserve before paying out.

### Proof of Concept
```solidity
// Foundry fork PoC (test/foundry/IdleCreditVault.t.sol harness)
function testPostDefaultRequestDrainsRecoveryReserve() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);            // attacker LP
    _depositWithUser(user1, amount, true); // victim LP with withdraw request

    // victim requests withdraw pre-default
    vm.prank(user1);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);
    // borrower repays only 50% -> default
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch() / 2);
    _checkDefault();

    // finalize: recoveryPrice = 0.5e18 over total basis
    vm.prank(manager);
    cdoEpoch.finalizeDefault(recovered, recoverySource);

    // attacker, still holding tranche tokens, requests post-default withdraw
    uint256 underlyingBefore = creditVault.defaultRecoveryReserve();
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    cdoEpoch.claimWithdrawRequest(); // paid 1:1 from reserve

    // reserve decreased by full receipt amount while only price*amount of basis was burned
    assertLt(
        creditVault.defaultRecoveryReserve(),
        underlyingBefore - drained, // drained > fair share
        'post-default claim over-drew the recovery reserve'
    );
    // victim's subsequent claim now reverts / underpays
}
```

Existing guards do not stop it: `_skimDonatedAssets` is irrelevant (no raw donation involved), `_transferFundedClaim`'s reserve guard is bypassed because payment goes through `_transferDefaultRecovery`, and the `defaultRecoveryFinalized` branch explicitly authorizes the mint-then-pay-1:1 flow.
