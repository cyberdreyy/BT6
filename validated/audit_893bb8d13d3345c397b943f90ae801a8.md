### Title
Native precompile dispatch has no panic-isolation boundary, allowing a single transaction to crash block execution - (File: `crates/common/precompiles/src/macros.rs`)

### Summary
The Stellar advisory fixes a bug where a native (host-implemented) contract's Rust panic during `try_call` was not caught and would abort/corrupt the host instead of being turned into a catchable error. Base's native precompiles (`B20Factory`, `B20AssetToken`, `B20StablecoinToken`, `PolicyRegistry`, `ActivationRegistry`, `TxContext`, `NonceManager`) are the direct architectural analog: they are Rust code invoked in-process from EVM `CALL`/`STATICCALL` the same way Soroban's native contracts are invoked from `try_call`, and there is no equivalent panic-catching boundary around that invocation.

### Finding Description
Every Base native precompile is wired into the EVM through the `base_precompile!` macro, which builds a `DynPrecompile::new_stateful` closure that directly calls into the precompile's `dispatch`/`route` logic: [1](#0-0) 

This closure is executed synchronously inside `PrecompilesMap`'s EVM call dispatch (`BaseZkvmPrecompiles`/`PrecompilesMap::run`), with no `std::panic::catch_unwind` (or `AssertUnwindSafe`) around the precompile body: [2](#0-1) 

By contrast, every other place in this codebase that runs code whose panics must not be allowed to bring down a critical loop (async task prefetchers, the proving pipeline, test harnesses) explicitly wraps that code in `catch_unwind`: [3](#0-2) [4](#0-3) 

No such wrapper exists for the EVM's precompile-call path. The precompile dispatch/route code paths (`b20_asset/dispatch.rs`, `b20_stablecoin/dispatch.rs`, `b20_factory/dispatch.rs`, `policy/dispatch.rs`, `activation/dispatch.rs`) are large, deeply nested ABI decode/dispatch trees driven entirely by attacker-controlled calldata, and the repository's own engineering guidance flags exactly this class of bug as high-risk: [5](#0-4) [6](#0-5) 

The codebase also shows the maintainers are aware this exact hazard is only one refactor away from being live: `FactoryAbi::abi_decode_validate` documents that `dispatch` unwraps a decoded ABI enum with `expect`, and that this is *only* safe because the decode is validating — i.e., a single future change to a non-validating decode "would turn an out-of-range variant byte from a revert into a node panic": [7](#0-6) 

Because there is no `catch_unwind` boundary at the precompile-call site, that invariant is the *only* thing standing between attacker-supplied calldata and a process-level panic; it is not defense-in-depth, it is the sole mitigation, and it depends on every current and future precompile handler (across `b20_asset`, `b20_stablecoin`, `b20_factory`, `policy`, `activation`, `tx_context`, `nonce`) never regressing a decode/unwrap/index/arithmetic invariant. This mirrors precisely the Soroban root cause: native/host contract code that can panic is invoked without a panic-catching boundary at the call frame.

### Impact Explanation
If any reachable precompile dispatch/route/logic function panics on attacker-controlled calldata (e.g. via `unwrap`/`expect`/indexing/arithmetic overflow reintroduced in any future change, or present today in an unreviewed code path), the panic unwinds straight out of the EVM interpreter's `run` call with no catch, since there is no `catch_unwind` wrapper at any level between `DynPrecompile` and the block-building/validation call stack. Per Rust's default panic behavior in a `panic=unwind` binary this would abort the enclosing thread; in the sequencer/builder or a validating full node executing untrusted transactions, this can crash the block-production/execution thread for every node that processes the transaction, i.e., a single crafted transaction can halt the sequencer or stall/crash validating nodes — a node halt / consensus-availability impact, the same class the referenced Stellar advisory addresses (a malicious call into native/host contract code crashing/corrupting the host).

### Likelihood Explanation
Reachability is unprivileged and trivial: any address can call `B20Factory`, `B20AssetToken`, `B20StablecoinToken`, `PolicyRegistry`, `ActivationRegistry`, `TxContext`, or `NonceManager` directly with arbitrary calldata (subject only to normal EVM call rules), since these are always-installed precompiles at fixed addresses from Beryl onward. The likelihood of an actual panic today depends on whether every decode/unwrap invariant across all dispatch/route/logic files currently holds — I could not exhaustively verify every `unwrap()`/`expect()` occurrence in every version/logic module within the available context (there are 30+ files with such calls across `crates/common/precompiles/src`), so I cannot confirm a currently-exploitable concrete panic input. What is confirmed is the structural gap: there is no panic-isolation boundary at all, so the security of the entire native-precompile subsystem rests entirely on invariant-by-convention rather than a defensive catch, which is the same anti-pattern the cited Stellar fix eliminated.

### Recommendation
Add a `catch_unwind`-based panic boundary around native precompile execution at the single choke point where all native precompiles are invoked (the `base_precompile!` macro's inner closure in `crates/common/precompiles/src/macros.rs`, and/or the `PrecompilesMap`/`BaseZkvmPrecompiles::run` call site), converting any caught panic into a deterministic `PrecompileError::Fatal`/halt result rather than letting it propagate into the EVM interpreter and the block-building/validation thread. This should be paired with CI-level auditing (e.g., `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::indexing_slicing)]` in the precompile dispatch crates) so the "one unwrap keeps this safe" invariant documented in `b20_factory/versions.rs` is enforced structurally instead of by convention.

### Proof of Concept
Not concretely constructed: I was unable to identify, within the available indexed context, one specific attacker-controlled calldata payload that currently trips an `unwrap()`/`expect()`/index/overflow panic in a shipped precompile handler (the b20_factory `expect` on `B20Variant::from_abi` is explicitly guarded by a validating decode today). The finding is the structural absence of a panic-catching boundary around native precompile execution — the same root cause class as the cited advisory — combined with the maintainers' own documentation acknowledging that a single future decode/validation regression in any of the several precompile dispatch modules turns a revert into a node-crashing panic reachable from an ordinary unprivileged transaction.

    pub fn abi_decode_validate(
        self,
        calldata: &[u8],
        selector: [u8; 4],
    ) -> Result<IB20Factory::IB20FactoryCalls> {
        match self {
            // Canonical aliases the V1 surface, so the frozen decode already yields the canonical
            // call type. A later surface adds its own arm, re-decoding against canonical.
            Self::V1 => IB20FactoryV1::IB20FactoryCalls::abi_decode_validate(calldata),
        }
        .map_err(|error| BasePrecompileError::AbiDecodeFailed {
            selector,
            error: error.to_string(),
        })
    }

    /// Selector-gates `calldata` against this wire surface, then decodes it into a routable call.
    ///
    /// Selectors a later fork introduced are absent from an older surface, so they fail the gate
    /// as [`BasePrecompileError::UnknownFunctionSelector`] rather than needing a hand-written arm.
    pub fn decode(self, calldata: &[u8]) -> Result<IB20Factory::IB20FactoryCalls> {
        let Some(selector) = calldata.first_chunk::<4>().copied() else {
            return Err(BasePrecompileError::UnknownFunctionSelector([0u8; 4]));
        };
        if !self.valid_selector(selector) {
            return Err(BasePrecompileError::UnknownFunctionSelector(selector));
        }
        self.abi_decode_validate(calldata, selector)
