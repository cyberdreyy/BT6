### Title
Front-runnable, permissionless initialization of the global `FeeState` singleton allows takeover of the protocol's global fee admin - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
The `init_global_fee_state` instruction initializes `FeeState`, a program-wide singleton PDA (seeded only by the constant `FEE_STATE_SEED`, with no group- or deployer-specific component), and accepts the `admin_key` and `fee_wallet` as free-form instruction arguments with no check that the caller is the deploying/authorized party.

### Finding Description
`InitFeeState` derives the `fee_state` PDA solely from `[FEE_STATE_SEED.as_bytes()]`, so its address is fully deterministic and identical for anyone interacting with the program - there is exactly one such account for the whole deployment: [1](#0-0) 

The handler blindly writes the caller-supplied `admin_key` into `fee_state.global_fee_admin` and `fee_wallet` into `fee_state.global_fee_wallet`, with no signer-identity check (e.g. against a known deployer key or upgrade authority) beyond requiring *some* signer to pay for the account: [2](#0-1) 

This is exactly the bug class described in the external report: an `init`-only instruction (no re-entrant protection needed since Anchor's `init` prevents re-initialization, but the *first* caller wins) that sets a sensitive admin key, with no verification that the caller is the intended deployer. Since `init_global_fee_state` is invoked as an explicit, standalone instruction (not something that runs atomically as part of program deployment), it is race-able: any transaction submitted before the legitimate operator's initialization transaction lands will permanently claim `global_fee_admin`.

The privilege is significant once claimed, since it is reused with `has_one` checks by other admin-only instructions:
- `EditFeeState` allows the `global_fee_admin` to freely change `global_fee_wallet`, `program_fee_fixed`, `program_fee_rate`, `bank_init_flat_sol_fee`, `liquidation_flat_sol_fee`, `order_init_flat_sol_fee`, `liquidation_max_fee`, `order_execution_max_fee`, and even reassign `global_fee_admin` itself and `pause_delegate_admin`: [3](#0-2) 
- `PanicUnpause` similarly gates on `has_one = global_fee_admin`, meaning the attacker-controlled admin also gains control of the protocol's manual pause/unpause mechanism: [4](#0-3) 
- Every new `MarginfiGroup` created afterward copies its `fee_state_cache` (global fee wallet, program fee fixed/rate) from this singleton `FeeState`, so an attacker-set `global_fee_wallet` becomes the destination for program fees on every group created after the takeover: [5](#0-4) 

The `init_global_fee_state` instruction is exposed as an unrestricted, permissionless program entrypoint: [6](#0-5) 

I could not find any deployer/upgrade-authority verification (e.g., comparison against `ProgramData.upgrade_authority_address`) anywhere in `init_global_fee_state.rs`, `lib.rs`, or elsewhere in the searched codebase — no `upgrade_authority` or `program_data` handling exists in the production program code (only found in unrelated build scripts).

### Impact Explanation
If an attacker's `init_global_fee_state` transaction lands before the operator's own initialization transaction (a realistic race on public mempools/RPCs immediately after program deployment, or after any event that requires re-deployment/re-initialization), the attacker permanently becomes `global_fee_admin` for the entire program. From there they can:
- Redirect all future protocol program fees (`global_fee_wallet`) to an address they control, for every marginfi group created thereafter.
- Set arbitrary `program_fee_fixed`/`program_fee_rate`, `bank_init_flat_sol_fee`, `liquidation_flat_sol_fee`, `order_init_flat_sol_fee`, `liquidation_max_fee`, `order_execution_max_fee` values across the whole protocol.
- Seize control of the manual pause/unpause circuit breaker (`panic_unpause`), a protocol-wide availability control.
- Because `FeeState` is a PDA and cannot be `init`'d twice, the legitimate operator cannot simply retry — the account must be abandoned and the program likely redeployed to a new program ID, or some other costly remediation performed, matching the report's described outcome ("attacker gaining privileges to the program" / forced redeployment).

This is a protocol-wide, financially-impactful authorization bypass, not merely a theoretical or admin-only concern, since it affects fee revenue routing for every group on the deployment.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to detect a fresh/un-initialized deployment (e.g., by observing that the deterministic `FeeState` PDA does not yet exist) and to win a race to submit `init_global_fee_state` before the operator's own transaction confirms. This is a known, common pattern of attack against uninitialized Solana program singletons, and PDA addresses are trivially derivable from the constant seed and public program ID, so no privileged information is needed to attempt the front-run.

### Recommendation
Add an explicit authorization check to `InitFeeState`/`initialize_fee_state`, verifying the payer/caller against a known, immutable value — e.g. compare the signer to the program's `upgrade_authority_address` (as recommended by Anchor docs) via the `ProgramData` account, or hardcode/embed an expected deployer pubkey checked with a `constraint`. Apply the same pattern to any other singleton-PDA `init` instructions in the codebase (e.g. `init_global_fee_state_v2`) that similarly lack a caller-identity check.

### Proof of Concept
1. Deploy (or observe a freshly deployed) marginfi program; derive the deterministic PDA `fee_state = find_program_address(["feestate"], marginfi::ID)` — this address does not depend on any signer, so anyone can compute it in advance.
2. Before the legitimate operator submits their `init_global_fee_state` transaction, an attacker submits their own transaction calling `init_global_fee_state(admin = attacker_key, fee_wallet = attacker_wallet, ...)` targeting the same derived `fee_state` PDA: [1](#0-0) 
3. Because `fee_state` uses Anchor's `init` constraint (fails if the account already exists) but has no check on *who* is allowed to call it first, the attacker's transaction succeeds and permanently sets `fee_state.global_fee_admin = attacker_key` and `fee_state.global_fee_wallet = attacker_wallet`: [2](#0-1) 
4. The legitimate operator's subsequent `init_global_fee_state` transaction fails (account already initialized).
5. The attacker now calls `edit_fee_state` (passing the `has_one = global_fee_admin` check with their own key) to redirect fees, and/or `panic_unpause` to control the protocol pause state, for as long as the compromised `FeeState` PDA remains in use by newly created groups: [3](#0-2)

pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
