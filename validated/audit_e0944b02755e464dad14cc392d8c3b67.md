## Title
Kamino harvest-reward fee-sweep uses a claim-only balance delta, permanently stranding rewards deposited by direct/front-run calls to the underlying Kamino Farms `harvest_reward` instruction - (File: `programs/marginfi/src/instructions/kamino/harvest_reward.rs`)

### Summary
Marginfi's `kamino_harvest_reward` instruction computes the amount of reward tokens to sweep to the protocol's `global_fee_wallet` by taking a balance snapshot of `user_reward_ata` immediately before its own CPI call to Kamino Farms' `harvest_reward`, then subtracting that from the post-CPI balance. Because Kamino Farms' `harvest_reward` is itself permissionless and can be invoked by anyone directly (not only through marginfi's wrapper), an attacker can pre-harvest rewards into the same ATA before marginfi's instruction runs. Those pre-existing tokens are excluded from the `received` delta computed by marginfi and are never swept to the destination account, mirroring the H-06 root cause: an unprivileged actor calling the underlying claim/reward instruction directly bypasses the wrapper's accounting logic that only reacts to balances it itself observes moving during its own call.

### Finding Description
`kamino_harvest_reward` is documented and implemented as permissionless: [1](#0-0) 

Its logic: [2](#0-1) 

`user_reward_ata` is a plain associated token account owned by the bank's `liquidity_vault_authority` PDA (not a marginfi-signature-gated custom account): [3](#0-2) 

The underlying Kamino Farms `harvest_reward` instruction (per its IDL) requires only a `payer` signer; `user_state`, `farm_state`, and `user_reward_token_account` are unsigned/writable accounts, meaning any unprivileged caller can invoke it directly against the same `user_state` (marginfi's `bank.integration_acc_2`) and the same `user_reward_ata`, causing Kamino to transfer accrued rewards straight into that ATA: [4](#0-3) 

Marginfi's own guide confirms this is expected/known to be externally triggerable: "Emissions can be harvested permissionlessly, and are sent to the global fee admin," referring to marginfi's wrapper — but nothing prevents a third party from calling Kamino's native instruction directly instead of marginfi's wrapper: [5](#0-4) 

If this happens, `user_reward_ata`'s balance rises outside of any marginfi instruction call. The next time someone calls marginfi's `kamino_harvest_reward`, `pre_transfer_balance` already includes that stranded amount, so `received = post_transfer_balance - pre_transfer_balance` only reflects rewards accrued after that point — the pre-existing stranded balance is never included in the `transfer_checked` call to `destination_token_account`: [6](#0-5) 

Because the ATA is owned by a bump-seeded PDA (`liquidity_vault_authority`) that only signs via `bank_signer!` inside marginfi's own instructions, and no other marginfi instruction sweeps the *full* balance of this specific reward ATA (contrast with the Drift analog below, which explicitly sweeps the entire intermediary balance rather than a delta), the stranded tokens become permanently stuck.

For comparison, the Drift equivalent instruction correctly avoids this bug class by transferring the *entire* balance of the intermediary account rather than a claim-time delta, making it immune to front-run/direct-call griefing: [7](#0-6) 

### Impact Explanation
Reward tokens intended for `global_fee_wallet` (and, per the roadmap, to eventually be redistributed to mrgn users of the bank) can become permanently locked in a PDA-owned token account with no sweep path other than the delta-based transfer, which will never again account for the stranded balance since each subsequent legitimate harvest resets `pre_transfer_balance` to include it. This is a durable freeze of funds with financial effect (lost protocol fee revenue / lost future reward redistribution), matching the accepted impact class of value redirection/durable freeze with financial effect.

### Likelihood Explanation
Exploitation requires only a permissionless call to the real Kamino Farms program's `harvest_reward` instruction using publicly-known/derivable accounts (`bank.integration_acc_2` as `user_state`, the farm's `farm_state`, and the canonical ATA of `liquidity_vault_authority` for the reward mint) — no marginfi authority, signature, or privileged role is needed. Any user or bot front-running/racing marginfi's own harvest calls can trigger this, making likelihood high once a Kamino-integrated bank with reward-bearing farms exists.

### Recommendation
Change `kamino_harvest_reward` to sweep the entire post-CPI balance of `user_reward_ata` (as Drift's `cpi_transfer_to_destination` already does), rather than only the delta computed from a pre/post snapshot taken within the same instruction call. This ensures any rewards deposited into the ATA by direct/external calls to Kamino Farms' `harvest_reward` are still captured and forwarded to the fee destination.

### Proof of Concept
1. Marginfi's bank has a Kamino Farm attached at `farm_state`, with obligation `user_state = bank.integration_acc_2`, and `user_reward_ata` = canonical ATA of `liquidity_vault_authority` for the reward mint.
2. Attacker builds and sends a transaction calling the real Kamino Farms program's `harvest_reward(reward_index)` instruction directly (not via marginfi), passing `payer = attacker`, `user_state`, `farm_state`, `global_config`, `reward_mint`, `user_reward_token_account = user_reward_ata`, `rewards_vault`, `rewards_treasury_vault`, `farm_vaults_authority`, `scope_prices`, `token_program` — all publicly derivable/readable accounts, none requiring marginfi's signature.
3. Kamino transfers the currently-accrued reward amount into `user_reward_ata`.
4. Anyone later calls marginfi's `kamino_harvest_reward` instruction: `pre_transfer_balance` now equals the attacker-deposited amount plus whatever accrues afterward; the CPI harvests only newly-accrued rewards since step 3; `received = post - pre` excludes the attacker-deposited amount.
5. `cpi_transfer_obligation_owner_to_destination(received)` moves only the newly-accrued delta to `destination_token_account`; the originally-deposited (attacker-triggered) balance remains in `user_reward_ata` indefinitely, since no other instruction sweeps its full balance. [2](#0-1)

```rust
pub fn kamino_harvest_reward(
    ctx: Context<KaminoHarvestReward>,
    reward_index: u64,
) -> MarginfiResult {
    let pre_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    ctx.accounts.cpi_harvest_rewards(reward_index)?;
    let post_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    let received = post_transfer_balance - pre_transfer_balance;
    ctx.accounts
        .cpi_transfer_obligation_owner_to_destination(received)?;
    Ok(())
}
```

```rust
    pub fn cpi_transfer_obligation_owner_to_destination(&self, amount: u64) -> MarginfiResult {
        let program = self.token_program.to_account_info();
        let accounts = TransferChecked {
            from: self.user_reward_ata.to_account_info(),
            to: self.destination_token_account.to_account_info(),
            authority: self.liquidity_vault_authority.to_account_info(),
            mint: self.reward_mint.to_account_info(),
        };
        let bump = self.bank.load()?.liquidity_vault_authority_bump;
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(program.key(), accounts, signer_seeds);
        let decimals = self.reward_mint.decimals;
        transfer_checked(cpi_ctx, amount, decimals)?;
        Ok(())
    }
```
