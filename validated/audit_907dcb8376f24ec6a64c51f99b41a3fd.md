Based on my investigation, the strongest analog to this bug class exists in `getProgramAccounts` and related token-account RPC handlers in `rpc/src/rpc.rs`, where a single account's encoding failure aborts the entire batch response instead of degrading gracefully.

### Title
`getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` fail entirely when a single matching account's data exceeds the base58 size limit - (File: rpc/src/rpc.rs)

### Summary
`JsonRpcRequestProcessor::get_program_accounts` iterates over all accounts matched by a program-id/filter scan and calls `encode_account` on each one, collecting results with `.collect::<Result<Vec<_>>>()?` [1](#0-0) . If `encode_account` returns an `Err` for even one account in the set — which happens whenever the requested encoding is `Binary`/`Base58` and that one account's (possibly data-sliced) data exceeds `MAX_BASE58_BYTES` (128 bytes) — the error propagates via `?` and the whole request fails, discarding all other accounts that could have been successfully encoded [2](#0-1) . The same pattern exists in `get_token_accounts_by_delegate` (and analogously `get_token_accounts_by_owner`) [3](#0-2) .

### Finding Description
This mirrors the Bond `findMarketFor` bug class: a loop aggregating results over many independent items calls a per-item function that can fail based on that item's own data, and a single failure aborts processing of the entire collection rather than being handled per-item. Here, an unprivileged RPC caller controls the `encoding` parameter (e.g., choosing `base58`) while having no control over which accounts happen to match a given `programId`/filter set on-chain. Any third party (or the caller's own prior actions) can create an account under that program whose data (after optional `dataSlice`) exceeds 128 bytes, which is trivial and common. Once such an account exists in the result set, `encode_account` returns `Err(error::Error{ code: InvalidRequest, ... })` [4](#0-3) , and the whole `getProgramAccounts` call returns an error instead of the accounts that could have been legitimately encoded.

### Impact Explanation
This causes `getProgramAccounts`, `getTokenAccountsByOwner`, and `getTokenAccountsByDelegate` (when called with `base58`/`binary` encoding) to become entirely unusable for any program/owner/delegate whose account set includes even one oversized account, denying legitimate callers all results. This falls under "wrong data returned" style query-availability breakage caused by unfiltered, uncontrollable third-party account data, in the same spirit as the Bond report's `findMarketFor` being broken by one market's `payoutFor` revert.

### Likelihood Explanation
Likelihood is moderate: it requires the caller to use `base58`/`binary` encoding for a program/owner query where the result set includes an account larger than 128 bytes, which is a fairly common condition for real on-chain data. It's arguably closer to expected/documented behavior (there's an explicit error message telling the caller to use base64) rather than an unintended crash, so severity is limited to a usability/DoS-of-availability issue with an easy mitigation (use `base64` encoding), not a crash or state-corruption bug.

### Recommendation
Change `get_program_accounts` and the token-accounts-by-owner/delegate handlers to skip or gracefully mark individual accounts that fail to encode (e.g., return `null`/error variant per item or filter them out with the same "won't fit" convention used elsewhere) instead of short-circuiting the entire response with `.collect::<Result<Vec<_>>>()?`.

### Proof of Concept
1. Store an account owned by `program_id` with `data.len() > 128` bytes on a local/test validator.
2. Store a second, small account under the same `program_id`.
3. Call `getProgramAccounts(program_id, { encoding: "base58" })`.
4. Observe the RPC call returns a JSON-RPC error ("Encoded binary (base 58) data should be less than 128 bytes...") for the whole request, even though the small account could have been encoded successfully [5](#0-4) .

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
