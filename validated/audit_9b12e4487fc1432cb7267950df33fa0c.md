### Title
Unprivileged job can force cache-volume "protected" status via cache key suffix, bypassing protected-ref isolation - ([File: executors/docker/volume.go])

### Summary
`createVolumesManager` computes `config.Protected` as `e.Build.IsProtected() || protectedKeyIdx >= 0`, where `protectedKeyIdx` is found by checking if any attacker-controlled `cache.key` from `.gitlab-ci.yml` ends with `-protected` (and not `-non_protected`). Since the underlying volume name is otherwise deterministic and independent of the branch/ref (based only on runner token, system ID, project ID, and project-runner ID via `ProjectRealUniqueName`), an unprivileged job on an unprotected branch can craft a cache key ending in `-protected` to make its build resolve to the exact same volume name that protected-ref jobs for the same project use.

### Finding Description
In `executors/docker/volume.go`, `createVolumesManager` derives `Protected` from two sources: the actual ref protection state `e.Build.IsProtected()`, and a heuristic scan of the job's own cache keys for a `-protected` suffix: [1](#0-0) 

The `cache.key` value comes directly from `.gitlab-ci.yml`, which any pipeline author (including on unprotected branches or in some setups, merge request pipelines from forks) fully controls. There is no server-side/authorization check tying the `-protected` suffix to actual ref-protection status here in the runner; the string match is the only gate.

Once `config.Protected` is `true`, `manager.go`'s `withProtected` appends the literal `-protected` suffix to the deterministic volume name derived from `ProjectRealUniqueName` (a hash of runner token, system ID, project ID, and project-runner ID — none of which depend on branch/ref): [2](#0-1) [3](#0-2) [4](#0-3) 

Because the volume name for a given project/destination is identical regardless of which ref triggered the build (only the `-protected` suffix differs, and that suffix is exactly what the attacker controls), an unprotected-branch job that sets `cache.key: "foo-protected"` will mount the **same persistent Docker volume** that legitimate protected-ref jobs for that project use. This defeats the purpose of the protected/non-protected volume separation described in the referenced GitLab work item 494478, whose entire premise is to keep untrusted (unprotected-ref) build state from mixing with trusted (protected-ref) build state.

The integration test `Test_CacheVolumeProtected` in `docker_command_integration_test.go` explicitly documents and asserts this exact behavior: a non-protected ref with cache key `"blammo-protected"` produces a volume with the `-protected` suffix and `protected: "true"` label, identical to what a protected ref would produce: [5](#0-4) 

### Impact Explanation
An unprivileged job/pipeline author on an unprotected branch can gain read/write access to the docker cache volume namespace intended exclusively for protected-ref builds of the same project (same runner). This allows:
- Cache poisoning: injecting malicious files/binaries into the "protected" cache volume that a later protected-branch job (e.g., a release/deploy pipeline) will consume, potentially leading to code execution in a higher-trust pipeline context.
- Read access to any data a protected-ref job placed in that persistent volume (build caches, downloaded dependencies, potentially sensitive intermediate artifacts), from an unprotected/untrusted job.

Impact is scoped to cross-job/cross-trust-boundary cache contamination and information exposure within the same project, consistent with the invariant that "a normal job must not... access another project's workload" being effectively extended here to "another trust tier's workload" within the same project.

### Likelihood Explanation
Fully feasible and reproducible: any pipeline author who can edit `.gitlab-ci.yml` on an unprotected branch (a very common privilege — feature branches, and often MR pipelines from forks) can set `cache: { key: "anything-protected" }`. No special GitLab permissions, admin access, or runner misconfiguration is required. The behavior is deterministic and repeatable on every build for that project/runner combination.

### Recommendation
Do not let the cache key content alone toggle the `Protected` volume flag on the runner side. Either:
1. Remove the `protectedKeyIdx` heuristic override entirely and derive `Protected` solely from the trusted, server-provided `e.Build.IsProtected()` value, or
2. If the "opt-in protected cache" feature from work item 494478 must be kept, only honor the cache-key suffix as an *additional restriction* (i.e., allow a protected-ref job to explicitly request non-shared caching) rather than as a way to *upgrade* an unprotected build into the protected volume namespace. In other words, the suffix should never be able to force `Protected = true` when `e.Build.IsProtected()` is `false`; at most it should be able to force isolation to a *separate, uniquely-named* volume that is still namespaced away from the real protected-ref volume.

### Proof of Concept
Extend `Test_CacheVolumeProtected` (or write a focused unit test on `createVolumesManager`) with an explicit assertion that the resulting volume for an unprotected ref with a "-protected" cache key is **not** the same volume name/hash that a protected ref would produce for the identical `BasePath`/`UniqueName`:

```go
func TestCreateVolumesManager_UnprotectedRefCannotForgeProtectedVolume(t *testing.T) {
    // Build A: protected ref, ordinary cache key
    buildA := newTestExecutorBuild(t, protected(true), cacheKey("blammo"))
    cfgA := createVolumesManagerConfig(t, buildA)
    require.True(t, cfgA.Protected)

    // Build B: unprotected ref, attacker-crafted cache key
    buildB := newTestExecutorBuild(t, protected(false), cacheKey("blammo-protected"))
    cfgB := createVolumesManagerConfig(t, buildB)

    // Bug: today cfgB.Protected == true even though the ref is unprotected,
    // producing the identical volume name as cfgA for the same project/runner.
    assert.False(t, cfgB.Protected,
        "an unprotected-ref job must not be able to force Protected=true via cache key suffix")
}
```

Expected (post-fix) assertion: `cfgB.Protected` is `false`, so the unprotected job's cache volume name diverges from the protected job's volume name, preventing cross-trust-tier cache sharing.

var createVolumesManager = func(e *executor) (volumes.Manager, error) {
	// Note if any of the cache keys includes the `-protected` suffix (but not the `-non_protected` suffix).
	// See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
	protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
		return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
	})

	config := volumes.ManagerConfig{
		CacheDir:      e.Config.Docker.CacheDir,
		BasePath:      e.Build.FullProjectDir(),
		UniqueName:    e.Build.ProjectRealUniqueName(),
		TemporaryName: e.getProjectUniqRandomizedName(),
		DisableCache:  e.Config.Docker.DisableCache,
		Driver:        e.Config.Docker.VolumeDriver,
		DriverOpts:    e.Config.Docker.VolumeDriverOps,
		// the volume should be protected if the ref is protected OR if any of the cache volumes have the protected
		// suffix. See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
		Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,

func (b *Build) ProjectRealUniqueName() string {
	const byteLen = 16

	data := fmt.Sprintf("%s-%s-%d-%d",
		b.Runner.GetToken(),
		b.Runner.GetSystemID(),
		b.JobInfo.ProjectID,
		b.ProjectRunnerID,
	)

	sum := sha256.Sum256([]byte(data))
	return "runner-" + hex.EncodeToString(sum[:byteLen])
}
