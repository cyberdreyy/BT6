### Title
Masker leaks unmatched partial secret bytes on stream `Close()`, bypassing trace masking on early process termination - ([File: common/buildlogger/internal/masker/masker.go])

### Summary
The `masker` type buffers matched-but-incomplete phrase bytes in `m.matching` and only replaces them with `[MASKED]` once the *entire* phrase is matched inside `Write()`. If the underlying stream is closed while a match is still in progress, `masker.Close()` explicitly flushes `m.phrase[:m.matching]` — i.e. all but the trailing unmatched bytes of the secret — to the job trace unredacted. This is reachable whenever a job process's stdout/stderr is closed before the last byte of a matched secret is written, which is the normal shutdown path after job cancellation/timeout (`KillAndWait` → `Terminate`/`ForceKill` → deferred `stdout.Close()`/`stderr.Close()` in `executors/shell/shell.go`).

### Finding Description
`masker.Write()` tracks a running match count `m.matching` per phrase and only calls `m.next.Write(mask)` once `m.matching == len(m.phrase)` [1](#0-0) . When the stream ends, `masker.Close()` is invoked:

```go
func (m *masker) Close() error {
	var werr error
	if m.matching == len(m.phrase) {
		_, werr = m.next.Write(mask)
	} else {
		_, werr = m.next.Write(m.phrase[:m.matching])
	}
	...
``` [2](#0-1) 

In the `else` branch, any bytes already recognized as matching the beginning of the secret (`m.phrase[:m.matching]`) are written **unmodified** to the next writer (ultimately the job trace) instead of being discarded or masked. If `m.matching == len(m.phrase)-1`, this flushes the secret minus its last byte in plaintext.

This masker sits directly in the trace pipeline built by `Logger.wrap()`: `masker.New(w, l.maskPhrases)` wraps the base trace writer for stdout/stderr of the running job command [3](#0-2) . The shell executor's `Run()` obtains these streams and passes them as `cmd.Stdout`/`cmd.Stderr`, always deferring `Close()` on them regardless of how the process ends [4](#0-3) . When the job context is canceled/times out, `newProcessKillWaiter(...).KillAndWait(c, waitCh)` is invoked, which calls `Terminate()`/`ForceKill()` on Unix via `syscall.Kill` on the negative process-group PID from `unixKiller.getPID()` [5](#0-4) , and the goroutine unwinds through the deferred `stdout.Close()`/`stderr.Close()` — which chains down to `masker.Close()`.

Since the pipeline author fully controls their job script, they can:
1. Use a masked CI/CD variable they have permission to *use* but not to *view* (e.g. a masked group/project variable) in a script that emits it one character (or small chunk) at a time with a `sleep` between each chunk, without needing to know the variable's actual value.
2. Predict, from the sleep cadence and elapsed time, the moment at which exactly all but the last byte of the secret has been written to the pipe/masker.
3. Trigger job cancellation or configure a job timeout to land at that moment, causing `ForceKill`/`Terminate` → stdout close → `masker.Close()` to flush `m.phrase[:m.matching]` (secret minus last byte) into the trace, which the attacker (and anyone else with trace-read access) can then read.

No existing check mitigates this: masking here is purely a streaming best-effort replace; there is no fallback that discards or fully redacts an in-flight partial match on abnormal/early close.

### Impact Explanation
An attacker with only the ability to *use* (not *view*) a masked/protected CI/CD variable can, through timing manipulation of their own job's output and job cancellation/timeout, cause the runner to write nearly the entirety of that secret value in cleartext into the job trace. This defeats the core guarantee of GitLab Runner's log masking feature and results in exposure of masked variables to project/job trace viewers who are not supposed to see them.

### Likelihood Explanation
This requires the attacker to control job script content (defining pipeline stage, always true for a pipeline author), to know the masked secret's approximate length or just always chunk single bytes (feasible without knowing content), and to time job cancellation relative to their own controlled `sleep` cadence. It is not a one-shot deterministic hit but is a repeatable process: the attacker can retry across multiple job runs, tuning the delay/cancellation timing until they observe a partial (n-1 byte) leak in the trace, since job cancellation/timeout timing is coarse-grained (seconds) relative to their own scripted write intervals, making convergence practical over a handful of attempts.

### Recommendation
`masker.Close()` should never write unflushed/partial phrase bytes verbatim to the trace. Options:
- On `Close()`, only flush partially-matched bytes if they cannot possibly be part of a mask (e.g., replace ambiguous partial matches with a generic redaction marker, or withhold/drop them entirely), rather than writing `m.phrase[:m.matching]` unmodified.
- Alternatively, ensure any partial in-flight match is masked (or at minimum truncated to a safe, non-identifying prefix length) instead of emitting the full unmatched prefix on stream teardown, including during forced/early termination paths (`Terminate`/`ForceKill` in `helpers/process/killer_unix.go`).

### Proof of Concept
Go unit test in `common/buildlogger/internal/masker/masker_test.go` style:
```go
func TestMasking_PartialMatchLeaksOnClose(t *testing.T) {
    secret := "supersecretvalue"
    buf := new(bytes.Buffer)
    m := New(internal.NewNopCloser(buf), internal.Unique([]string{secret}))

    // simulate chunked writes where the stream is closed
    // after all but the last byte of the secret has been written
    n, err := m.Write([]byte(secret[:len(secret)-1]))
    require.NoError(t, err)
    assert.Equal(t, len(secret)-1, n)

    // simulate premature Close() (as happens via KillAndWait -> ForceKill -> stdout.Close())
    require.NoError(t, m.Close())

    // Assertion: the trace must never contain len(secret)-1 contiguous bytes of the secret
    assert.NotContains(t, buf.String(), secret[:len(secret)-1],
        "masker.Close() leaked near-complete secret to trace: %q", buf.String())
}
```
Expected current behavior: the assertion fails — `buf.String()` contains `secret[:len(secret)-1]` verbatim, confirming the leak. An integration-level PoC job can reproduce the same effect end-to-end by using a masked CI/CD variable in a script that `printf`s it one character at a time with `sleep 1` between characters, combined with a CI job timeout set to expire mid-loop, and inspecting the resulting job trace for the leaked prefix.

func (m *masker) Close() error {
	var werr error

	if m.matching == len(m.phrase) {
		// this mask is added to avoid a potential undiscovered edge-case:
		// this should be unreachable as we replace full matches immediately in
		// Write().
		_, werr = m.next.Write(mask)
	} else {
		_, werr = m.next.Write(m.phrase[:m.matching])
	}

	err := m.next.Close()
	if err == nil {
		return werr
	}

	return err

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}
