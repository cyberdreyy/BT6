### Title
`DeployGlobalContract` with `GlobalContractDeployMode::AccountId` does not enforce `predecessor_id == receiver_id`, allowing an attacker to register a global contract under a victim account's identity and bill the victim for the storage cost - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`action_deploy_global_contract` binds the `GlobalContractIdentifier::AccountId` to the `account_id` of the account the receipt executes against (the receipt's `receiver_id`), and charges the storage burn to that same account's balance, but neither the action-execution code nor the action-validation code checks that the receipt's `predecessor_id` equals its `receiver_id`. An attacker can therefore submit a transaction/receipt whose `receiver_id` is any victim account and attach a `DeployGlobalContract(deploy_mode: AccountId)` action with attacker-chosen wasm bytecode, forcing that global contract to be registered under the victim's account identifier and forcing the victim's balance to pay the deploy storage fee.

### Finding Description
`action_deploy_global_contract` receives `account_id` (the execution-context account, i.e. the receipt's `receiver_id` as dispatched from `apply_action` in `runtime/runtime/src/lib.rs`) and, for `GlobalContractDeployMode::AccountId`, uses that same `account_id` as the `GlobalContractIdentifier`: [1](#0-0) 

The storage cost of the deploy is deducted from that account's own `amount()` — i.e. the receiver's balance, not the sender's: [2](#0-1) 

Unlike `CreateAccount`, which is explicitly passed an `actor_id` for self-vs-other authorization checks, `DeployGlobalContract` is dispatched with only `account_id` (`= receiver_id`) and no `actor_id`/`predecessor_id` comparison: [3](#0-2) 

The action-validation layer for `DeployGlobalContract` only checks the wasm size limit — it never compares `predecessor_id` to `receiver_id`: [4](#0-3) 

The protocol documentation explicitly enumerates the actions that require `predecessor_id == receiver_id` (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`) and `DeployGlobalContract` is conspicuously absent from that list: [5](#0-4) 

Because receipts can target any `receiver_id` regardless of who the `predecessor_id` is (this is normal/expected for actions like `Transfer` or `FunctionCall`), an attacker can craft a transaction with `signer_id = attacker`, `receiver_id = victim`, `actions = [DeployGlobalContract{ code: <attacker wasm>, deploy_mode: AccountId }]`. When this receipt is applied, `account_id` passed into `action_deploy_global_contract` is `victim`, so:
1. The storage burn (`global_contract_storage_amount_per_byte * code.len()`) is deducted from the victim's own account balance, without the victim's consent.
2. `GlobalContractIdentifier::AccountId(victim)` is registered globally, permanently binding the victim's account identity to arbitrary bytecode chosen by the attacker.

Any other account that later does `UseGlobalContract(GlobalContractIdentifier::AccountId(victim))` (trusting that "victim.near"'s global contract is authored/controlled by the victim, since the NEP-591 design intent of the `AccountId` mode is "the owner can update the contract for its users") will unknowingly run attacker-supplied bytecode. Since the identifier mode is meant to convey update authority to the account holder, this violates authorization exactness: the entity actually authorizing the deploy (attacker, as `predecessor_id`) is not the entity whose identity is bound (victim, as `receiver_id`/`account_id`).

### Impact Explanation
This is an authorization-escalation-across-accounts bug: an unprivileged attacker can (a) force any account with a positive balance to be billed for a deploy it never authorized (fund loss to the victim bounded by `global_contract_storage_amount_per_byte * code_len`), and (b) spoof a global-contract "owner" identifier that other unrelated accounts (and end users trusting `GlobalContractIdentifier::AccountId`) may reference, effectively giving the attacker control of code served under the victim's account identity. This matches the "authorization escalation across accounts" bounty category, plus incidental fund loss to the victim through unauthorized storage-fee debits.

### Likelihood Explanation
No special privileges are required beyond normal client capability: sign and submit a transaction (or relay a `DelegateAction`) whose `receiver_id` is the victim and whose action list contains a single `DeployGlobalContract` action with `deploy_mode: AccountId`. The victim account merely needs to exist and hold enough balance to cover the storage fee for the code size chosen by the attacker (attacker can pick a minimal-size wasm to minimize the fee needed, maximizing repeatability against many victim accounts cheaply). This is fully repeatable against any account on the network.

### Recommendation
Enforce the same self-action invariant documented for `DeployContract`/`AddKey`/etc. for `DeployGlobalContract` when `deploy_mode == GlobalContractDeployMode::AccountId`: reject the action (e.g. with a new `ActionsValidationError`) unless `receipt.predecessor_id() == receipt.receiver_id()` (or `actor_id == receiver_id` after a `CreateAccount` in the same receipt). This check should be added either in `validate_deploy_global_contract_action` (passing `receiver`/`predecessor` into the validation call, mirroring `validate_deterministic_state_init`'s receiver check) or in `action_deploy_global_contract` prior to charging storage/registering the identifier.

### Proof of Concept
Add an integration-style test (e.g. in a runtime-crate `apply_action`/receipt-processing test, or a test-loop test alongside `test-loop-tests/src/tests/global_contracts.rs`):
1. Set up two funded accounts: `attacker.test.near` (predecessor) and `victim.test.near` (receiver), both existing with sufficient balance.
2. Construct/execute an `ActionReceipt` with `predecessor_id = attacker.test.near`, `receiver_id = victim.test.near`, `actions = [Action::DeployGlobalContract(DeployGlobalContractAction { code: attacker_wasm, deploy_mode: GlobalContractDeployMode::AccountId })]`.
3. Apply the receipt through the runtime and assert:
   - Before the fix: the action succeeds, `victim.test.near`'s balance is reduced by the storage fee, and `GlobalContractIdentifier::AccountId("victim.test.near")` is stored with `attacker_wasm` content (readable via `state_update`/`TrieKey::GlobalContractCode`).
   - After the fix: the action is rejected with a new validation error (e.g. `GlobalContractAccountIdDeployRequiresSelf` or similar) because `predecessor_id != receiver_id`, and no state/balance change occurs.
4. Add a companion positive test where `predecessor_id == receiver_id == "owner.test.near"` and assert the deploy still succeeds normally, confirming the fix doesn't break legitimate self-deploys (as exercised in `test-loop-tests/src/tests/global_contracts.rs`).
