### Title
Honest borrower can be forced into default by a mid-epoch instant-withdraw request when `instantWithdrawDeadline` precedes the borrower's repayment schedule - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
`getInstantWithdrawFunds` pulls instant-withdraw liquidity directly from the borrower via `transferFrom` and routes any failure into `_handleBorrowerDefault`, which permanently flags the pool as defaulted, pauses it and stops the epoch. An unprivileged KYC'd user can create this liquidity demand mid-epoch by requesting an instant withdraw, while the honest borrower's repayment obligation (and token allowance) is only calibrated to the end-of-epoch amount. If the borrower has not provisioned mid-epoch liquidity, the pull fails and the borrower is marked defaulted even though nothing was yet due — the same bug class as a default duration shorter than the payment cycle.

### Finding Description
Two facts combine:

1. An attacker (any whitelisted/KYC'd tranche holder) can request an instant withdraw during a running epoch, creating a non-zero `pendingInstantWithdraws` balance in `IdleCreditVault`.
2. `_stopEpoch` reverts while `_pendingInstant() != 0` (`contracts/IdleCDOEpochVariant.sol` L340-345), so the honest manager cannot close the epoch normally and must call `getInstantWithdrawFunds`. That function performs `getFundsFromBorrower(_instantWithdraws)` — a `transferFrom` on the borrower — and on *any* failure calls `_handleBorrowerDefault` (L566-573).

`_handleBorrowerDefault` unconditionally sets `defaulted = true`, pauses the contract, stops the epoch and disables withdraw requests (L577-599). There is no grace check, no comparison of what the borrower actually owes at that point in time, and no distinction between "borrower insolvent" and "borrower only provisioned funds for the scheduled epoch-end repayment".

The borrower's scheduled liability is defined at epoch end (`_expectedInterest + _pendingWithdraws` pulled in `stopEpoch`). The instant-withdraw mechanism imposes an *additional, earlier* liquidity obligation whose size the attacker controls (up to their tranche balance), while the default decision ignores that this liability was not part of the expected repayment schedule. This mirrors the external bug: the default test does not account for the payment-cycle timing.

### Impact Explanation
- The borrower is marked `defaulted` despite having committed to repay at epoch end; the pool enters the hard-default recovery path (`finalizeDefault`, `DefaultDistributor`), socializing a fabricated "loss" across AA/BB tranche holders instead of normal repayment.
- Tranche holders suffer the default waterfall and recovery-haircut flow even though the borrower would have paid in full at `epochEndDate`.
- Permanent freezing of withdrawals: `_beforeUnpause` reverts while `defaulted` (L636), and `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are cleared, so user funds are locked until `finalizeDefault`/`finalizeDefaultRecovery` runs.

### Likelihood Explanation
Medium-low, gated by configuration and borrower behavior:

- Requires `instantWithdrawDeadline` to be set inside the running epoch and instant withdrawals enabled (`disableInstantWithdraw == false`, non-programmable borrower). The deadline is owner-set and honest, but nothing enforces that it is compatible with the borrower's funding schedule — analogous to `bidDefaultDuration < paymentCycle` being a market-owner misconfiguration, not an attacker action.
- Requires the borrower to have approved/held only the expected epoch-end repayment. A borrower that maintains a standing large allowance neutralizes the attack (the pull succeeds, though the borrower is still forced to fund an unscheduled early outflow — itself a cash-flow violation).
- The attacker bears no cost beyond requesting a withdraw they are entitled to make anyway.

This is partially mitigated in practice if borrowers keep full allowances, so the finding is a Medium severity misconfiguration/timing-mismatch rather than a guaranteed exploit.

### Recommendation
- Do not route `getInstantWithdrawFunds` pull failures into `_handleBorrowerDefault` when the epoch is otherwise healthy; instead revert and let the request remain pending until the borrower funds it or the epoch ends normally.
- Alternatively, treat instant-withdraw liabilities as already-due obligations only after a grace period aligned with the borrower's payment cycle (e.g. only default if unfunded past `epochEndDate + grace`), mirroring the recommendation to measure default from when payment was *due*.
- Optionally enforce `instantWithdrawDeadline + gracePeriod <= epochEndDate` in `setEpochParams`, or fund instant withdrawals from a CDO-side buffer rather than an ad-hoc borrower pull.

### Proof of Concept
Foundry sketch (base it on `test/foundry/IdleCreditVault.t.sol` helpers such as `_startEpochAndCheckPrices`):

```solidity
function testHonestBorrowerDefaultedByInstantWithdraw() external {
    // user = KYC'd AA holder; borrower honest, approved only epoch-end amount
    idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0); // epoch running, instantWithdrawDeadline set < epochEndDate

    // Attacker requests instant withdraw after the deadline passes
    vm.warp(cdoEpoch.instantWithdrawDeadline() + 1);
    vm.prank(attacker);
    IdleCreditVault(address(strategy)).requestInstantWithdraw(attackAmount, address(AAtranche));

    // Borrower has provisioned only expected epoch-end interest, not instant withdraws
    uint256 expected = _expectedFundsEndEpoch();
    deal(defaultUnderlying, borrower, expected);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), expected);

    // Honest manager must fulfill instant withdraws before stopping the epoch
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(); // transferFrom fails -> _handleBorrowerDefault

    assertTrue(cdoEpoch.defaulted(), "honest borrower defaulted mid-cycle");
    assertFalse(cdoEpoch.isEpochRunning(), "epoch stopped by default");
}
```

Key check: `borrower` never missed a *due* payment — the default was triggered solely by an unscheduled mid-epoch liquidity demand created by an unprivileged withdraw request.
