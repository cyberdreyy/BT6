### Title
Feeds-manager-managed jobs can be manually triggered via the `runJob` GraphQL mutation, bypassing the `IsJobManaged` guard that protects them from `deleteJob` - ([File: core/web/resolver/mutation.go])

### Summary
The `Resolver.RunJob` mutation resolver parses the numeric job ID from `args.ID` and immediately calls `r.App.RunJobV2(ctx, jobID, nil)` without checking whether the target job is managed by the Feeds Manager. This is inconsistent with `Resolver.DeleteJob`, which explicitly calls `app.FeedsService().IsJobManaged(...)` and rejects the operation for feeds-managed jobs.

### Finding Description
`core/web/resolver/mutation.go` implements two job-mutating resolvers reachable by any authenticated GraphQL session with at least the `run` role: `DeleteJob` and `RunJob`. `DeleteJob` looks up the job, calls the feeds service's `IsJobManaged` check [1](#0-0) -backed guard, and refuses to delete the job if it is under feeds-manager control, returning an error instructing the caller to use the job-proposal workflow instead. `RunJob`, by contrast, converts `args.ID` with `stringutils.ToInt32` and forwards it directly to `RunJobV2` with no equivalent `IsJobManaged` lookup or feeds-manager guard. Because `IsJobManaged` is referenced from `core/services/chainlink/application.go` (the `FeedsService` accessor) and from the feeds package itself, but never from the `RunJob` code path in `mutation.go`, a run-role session can supply the numeric ID of any job — including a bootstrap OCR peer job or a job under active feeds-manager management/job-proposal lifecycle — and force a manual pipeline execution that the node's own authorization model says should be blocked.

### Impact Explanation
A run-role user (or any credential scoped to that role) can force execution of a feeds-manager-governed job's pipeline outside the feeds-manager-controlled workflow. For OCR/FM-managed jobs this can trigger unintended pipeline runs and, depending on job type, unintended on-chain transmissions or reports, circumventing the intentional restriction enforced on the deletion path. This falls under "unauthorized job run / fund movement" impact category.

### Likelihood Explanation
Preconditions are modest: the attacker needs only a run-role (or higher) authenticated GraphQL session and the numeric job ID, which is a small sequential integer and can be enumerated/brute-forced via repeated `runJob` calls (each attempt is low-cost and the mutation returns distinguishable success/error responses per ID). No special network position, admin credentials, or DON/oracle compromise is required, making this practically reproducible by any operator-level session that is not supposed to control feeds-managed jobs directly.

### Recommendation
Add the same `IsJobManaged` (or equivalent feeds-manager ownership) check to `Resolver.RunJob` that already exists in `Resolver.DeleteJob`, rejecting manual `runJob` calls against feeds-manager-managed jobs (or requiring an explicit elevated permission/override flag for that specific case).

### Proof of Concept
1. Unit/integration test in `core/web/resolver/mutation_test.go` style: create a job via the feeds service (or mark an existing job as managed via `feeds.ORM.IsJobManaged` fixture) so `IsJobManaged(ctx, jobID)` returns `true`.
2. As a run-role authenticated GraphQL client, call `mutation { deleteJob(id: "<id>") { ... } }` and assert it is rejected with the "job is managed" error (existing behavior).
3. As the same run-role client, call `mutation { runJob(id: "<id>") { ... } }` and assert whether execution proceeds (calls `RunJobV2`) despite the job being feeds-managed.
4. Expected (secure) behavior: `runJob` should return an authorization/managed-job error analogous to `deleteJob`; current behavior (per code trace) is that it proceeds to `RunJobV2` without the check, confirming the gap.
