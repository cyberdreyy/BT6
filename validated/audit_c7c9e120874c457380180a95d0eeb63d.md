### Title
Stale rejection weight is never retracted when a signer flips from reject to accept for the same block, corrupting the coordinator's aggregated-weight tally - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` maintains a `BlockStatus` per block hash with two independent counters, `total_weight_approved` and `total_weight_rejected`, each guarded by its own de-duplication set. The `Accepted` branch de-duplicates using `gathered_signatures` (a map keyed by `slot_id`), while the `Rejected` branch de-duplicates using the shared `responded_signers` set. Because `responded_signers` is written by both branches but the branches check different sets to decide whether to add weight, a signer who first rejects and later legitimately accepts the very same block (a state transition the signer-side state machine explicitly allows) causes its weight to be added to `total_weight_approved` while the earlier contribution to `total_weight_rejected` is never removed. This is structurally the same class of bug as the audit report's `balanceBefore`/`balanceAfter` miscalculation: a delta/tally is computed against a companion value (`reservedFunds` there, `responded_signers`/rejected-weight here) that itself can change between the two measurement points, and the code never re-derives or reconciles it, producing an incorrect aggregate.

### Finding Description
`docs/signer-flows.md` (section 2, `BlockState`) documents that a signer can legitimately move `LocallyRejected --> LocallyAccepted` on re-evaluation: [1](#0-0) 

On the node side, `StackerDBListener::run` tracks this per-block state in a `BlockStatus`: [2](#0-1) 

For `BlockResponse::Accepted`, the weight is only added if the *signature* map doesn't already contain the slot: [3](#0-2) 

For `BlockResponse::Rejected`, the weight is added if `responded_signers.insert(slot_id)` (a *shared* set touched by both branches) returns `true`: [4](#0-3) 

The two branches thus use different keys to decide whether a signer's weight has "already been counted": `Accepted` checks `gathered_signatures`, `Rejected` checks/writes `responded_signers`. Sequence:
1. Signer A's initial view causes it to reject block B (same `signer_signature_hash`, e.g. re-sent unchanged after the coordinator's rejection-timeout resend path in `signer_coordinator.rs`). `responded_signers = {A}`, `total_weight_rejected += wA`.
2. Signer A re-evaluates (per the documented `LocallyRejected --> LocallyAccepted` transition) and now signs/accepts B.
3. The `Accepted` branch checks `gathered_signatures.contains_key(&A)` — false, since A never accepted before — so it adds `wA` to `total_weight_approved` and inserts A into both `gathered_signatures` and `responded_signers` (already present, no-op).
4. Result: `total_weight_rejected` still contains `wA` from step 1 (never decremented) *and* `total_weight_approved` now also contains `wA`. A single signer's weight is now double-booked across two supposedly disjoint tallies for the same block.

This breaks the intended invariant that "aggregated-weight" bookkeeping mirrors the *current, verified set of accepts/rejects" for a block — the exact equality class this scan is meant to catch (aggregated-weight vs. verified-accepts).

### Impact Explanation
The corrupted `total_weight_rejected` is used directly by `SignerCoordinator::get_block_status` to decide the block is definitively and permanently rejected: [5](#0-4) 
A stale, never-retracted rejection weight can push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` even though the real, current distinct-signer view no longer rejects the block (the rejecting signer switched to accept). This causes the miner to treat the block as `SignersRejected` and abandon it / exclude its transactions, even though a supermajority by weight currently endorses it — a liveness fault that can stall block production on a proposal that should have succeeded. Because the mistracked counters are also logged and used to reset resend timeouts (`rejections != block_status.total_weight_rejected` branch), the coordinator's retry/timeout behavior is likewise driven by stale, uncorrected data.

### Likelihood Explanation
This requires only one signer (plus the ordinary node/signer message flow) re-evaluating its own vote on an unchanged, re-proposed block — a state transition (`LocallyRejected → LocallyAccepted`) that the signer implementation explicitly supports and exercises. No malicious signer, no majority coordination, and no forged signature are needed; it is triggered by completely legitimate signer behavior combined with the coordinator's own resend-on-timeout mechanic. This makes the bug straightforwardly reachable in normal operation whenever a signer changes its mind about a stale/resent proposal.

### Recommendation
Track weight for `BlockStatus` from a single source of truth. Either:
- Use one `responded_signers`-keyed map that stores each signer's current verdict, and derive `total_weight_approved`/`total_weight_rejected` by summing over that map on each update rather than incrementally on both branches; or
- On the `Accepted` path, if the slot is already present in `responded_signers` with a prior rejection recorded, subtract that signer's weight from `total_weight_rejected` before adding it to `total_weight_approved` (and symmetrically for a flip from accept to reject).

This ensures a signer's weight is attributed to exactly one bucket at any time, matching the actual, current verdict set.

### Proof of Concept
1. Configure a reward set with signer A (weight `wA`) such that `wA` alone is not enough to cross either threshold by itself, but is comparable to `blocking_minority` margins in a test setup.
2. Node proposes block B; signer A's local chainstate view causes it to reject B; the rejection is relayed and processed by `StackerDBListener`, incrementing `total_weight_rejected` by `wA` and inserting A into `responded_signers`.
3. Trigger the coordinator's rejection-timeout resend path (`signer_coordinator.rs`, "Timed out while waiting for responses from signers, resending proposal") so the identical block (same `signer_signature_hash`) is resent.
4. Have signer A re-evaluate and accept B this time (exercising the documented `LocallyRejected --> LocallyAccepted` re-evaluation path in `stacks-signer/src/v0/signer.rs`).
5. Observe in `StackerDBListener` that `block.total_weight_approved` now includes `wA` while `block.total_weight_rejected` still includes `wA` from step 2, never decremented — demonstrating the stale/duplicated weight tally.
