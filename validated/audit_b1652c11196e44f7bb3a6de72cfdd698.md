### Title
Permissionless `lending_pool_emissions_deposit` allows first-depositor share-price inflation that mints near-zero shares for later depositors - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
The XDeFi bug class is a permissionless "distribution update" function that recomputes a per-unit accumulator by dividing a new deposit by the *current total units*, letting a first user with a dust-sized position inflate the per-unit value arbitrarily and break the arithmetic for later users. marginfi-v2 has a structurally identical pattern in `lending_pool_emissions_deposit`, which recomputes `bank.asset_share_value` as `updated_total_assets / total_asset_shares` and can be called by anyone with any `total_asset_shares` denominator, including a denominator left artificially tiny by a first depositor.

### Finding Description
`lending_pool_emissions_deposit` is explicitly documented and implemented as **permissionless**: [1](#0-0) 

It recomputes the bank's `asset_share_value` by dividing the new total asset amount by `total_asset_shares`: [2](#0-1) 

The only guard against a tiny/zero denominator is `total_asset_shares > 0`, not a minimum size: [3](#0-2) 

A newly created bank issues shares 1:1 to its first depositor (confirmed by test comments/assertions: "the first deposit issues shares 1:1"), so an attacker can be the sole depositor with `total_asset_shares` set to a tiny raw value (e.g. `1`): [4](#0-3) 

With `total_asset_shares = 1`, the attacker (or anyone) calls `lending_pool_emissions_deposit` with a large `amount`, driving `asset_share_value = (1 + amount) / 1` to an extreme value. All subsequent deposits go through `get_asset_shares`, which divides the deposited value by `asset_share_value`: [5](#0-4) 

Because `asset_share_value` is now huge, any legitimate depositor whose native deposit amount is smaller than `asset_share_value * 2^-48` (the I80F48 fractional resolution) will be minted **zero (or negligible) shares** while their tokens are transferred into the shared liquidity vault — a classic first-depositor/inflation-attack outcome. Their principal becomes value that accrues to the attacker's pre-existing shares rather than to their own account.

### Impact Explanation
This is a durable, permissionless, unprivileged-user-triggerable state manipulation of a core lending-accounting primitive (`asset_share_value`) that determines every depositor's claim on a bank's liquidity vault. Depending on how large the attacker inflates `asset_share_value`, a wide range of subsequent "normal" deposit sizes can be rounded down to zero shares, silently redirecting depositor funds to the attacker's shares. Because `asset_share_value` is monotonic on the asset side (see fuzz invariant that treats it as non-decreasing outside of bankruptcy), this state is durable and cannot be organically corrected — it can only be fixed via admin intervention (e.g., bankruptcy socialization or a manual haircut), constituting a financial-impact bug reachable without any privileged role. [6](#0-5) 

Compared to the original XDeFi report, the Solana/I80F48 fixed-point representation (80 integer / 48 fractional bits, all `checked_*` arithmetic) is far more resistant to the specific *overflow-that-reverts-and-freezes* scenario described in the report — legitimate deposit/withdraw calls are unlikely to literally overflow given I80F48's wide range versus u64 token amounts. The concretely reachable, in-scope harm here is the rounding/inflation-attack variant (value misdirection to the attacker), not a hard freeze via overflow.

### Likelihood Explanation
The attack requires only: (1) creating/being first depositor of a bank (bank creation is permissionless per `lending_pool_add_bank_permissionless`, consistent with the "New Instructions" changelog referencing permissionless bank additions), (2) depositing a dust amount as the sole depositor, and (3) calling the permissionless `lending_pool_emissions_deposit` with real capital equal to the desired inflation amount. The last step requires the attacker to actually own and irrevocably transfer that capital into the vault (it is not a free "wei donation" like the original report), and since the attacker holds 100% of shares before the emissions deposit, they do not "lose" that capital economically — but it functions as the capital needed to move the share price. This makes the attack financially non-trivial to execute at scale (the attacker must front real capital equal to the desired inflation factor) but is technically always available to any user on any bank they can appear as sole/first depositor of, particularly for a bank that is freshly created and not yet publicly known/used.

### Recommendation
- Require a minimum `total_asset_shares` (or minimum total deposited value) before `lending_pool_emissions_deposit` is permitted, or scale the minimum permitted `amount` relative to `total_asset_shares` so the multiplier per call is bounded.
- Alternatively, mint a fixed "dead" minimum number of shares to a burn address on bank initialization (Uniswap V2-style), similar to the recommendation in the original report, so `total_asset_shares` can never be attacker-controlled at a dust level.
- Add a check in `lending_pool_emissions_deposit` (and any other codepath that divides by `total_asset_shares`) rejecting share-price growth beyond a bounded multiplier per call, and/or require that the resulting minted-share precision for a "typical" deposit size (e.g. `10**mint_decimals`) remains above a sane threshold.

### Proof of Concept
1. Permissionlessly create a new bank for mint `X` (per `lending_pool_add_bank_permissionless`).
2. Attacker deposits the smallest possible amount (e.g., `1` native unit) as the bank's first depositor → `total_asset_shares = 1`, `asset_share_value = 1` (1:1 issuance confirmed by `tests/specs/basic/07_deposit.spec.ts:151-153`).
3. Attacker (or any signer) calls `lending_pool_emissions_deposit(amount = N)` funding `N` native tokens of mint `X` into the liquidity vault. Per `configure_bank.rs:138-146`, `asset_share_value` becomes `(1 + N) / 1 = 1 + N`.
4. A legitimate user deposits `M` native tokens where `M < (1 + N) * 2^-48`. Per `bank.rs:249-256` (`get_asset_shares`), `shares_minted = M / asset_share_value ≈ 0`.
5. The legitimate depositor's `M` tokens are now in the liquidity vault, but their credited asset shares are effectively zero, transferring the economic value of their deposit to the attacker's pre-existing shares.

```rust
pub fn lending_pool_emissions_deposit(
```

```rust
    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```
