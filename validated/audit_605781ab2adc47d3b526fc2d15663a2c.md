### Title
Builder withdrawal amount committed to the execution payload can exceed the builder's actual balance, minting Gwei on withdrawal - (specs/gloas/beacon-chain.md)

### Summary
`apply_withdrawals` in the Gloas fork caps the *beacon-state* balance deduction for a builder withdrawal to `min(withdrawal.amount, builder_balance)`, but the `Withdrawal` object placed into `state.payload_expected_withdrawals` — the object the execution layer is required to honor in full — still carries the original, **uncapped** `withdrawal.amount`. If a builder's balance is smaller than the amount recorded in a pending withdrawal, the beacon chain only debits what the builder actually has, while the execution layer credits the `fee_recipient` the full, larger amount, creating Gwei that was never backed by any balance.

### Finding Description
`get_builder_withdrawals` builds `Withdrawal` entries directly from `state.builder_pending_withdrawals[i].amount` (the pending withdrawal's requested amount), independent of the builder's current balance. When these withdrawals are applied: [1](#0-0) 

```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        # [Modified in Gloas:EIP7732]
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
```

the *state-side* deduction is capped (`min(withdrawal.amount, builder_balance)`), but `withdrawal.amount` itself — the value that is placed unmodified into `state.payload_expected_withdrawals` and that the execution layer must apply as an EL balance increase to `fee_recipient` — is never capped. This is confirmed by the test suite, which explicitly documents that the *withdrawal* keeps the full requested amount while the *builder balance* is only reduced by what is available: [2](#0-1) 

The spec itself documents that this withdrawal list is a binding commitment that the execution layer "is required to honor": [3](#0-2) 

This is structurally the same equality-break the Sandclock report describes (an amount recorded/committed doesn't match the amount actually moved) — except that here it produces value creation rather than a revert: `Withdrawal.amount` (what the EL pays out) ≠ `min(withdrawal.amount, builder_balance)` (what the beacon state actually had and removed).

### Impact Explanation
This breaks the fundamental invariant that a withdrawal executed on the execution layer must be fully backed by a corresponding balance decrease on the consensus layer. If any accepted pending builder withdrawal's `amount` exceeds the builder's `balance` at settlement time, the difference is Gwei created out of nothing and paid to `fee_recipient` (which the withdrawal-generator, i.e., the builder, can freely choose). This is a Critical-severity issue under the given rubric: "Gwei created ... paid to a non-owner" / a payment applied that is not actually backed by the committed balance.

### Likelihood Explanation
Whether this is reachable in practice depends on whether any code path can cause `builder_pending_withdrawals[i].amount` to exceed `builders[builder_index].balance` by the time `apply_withdrawals` runs. `can_builder_cover_bid` is intended to prevent a builder from bidding more than it can cover, accounting for existing pending withdrawals: [4](#0-3) 

However, this check is only performed at bid-submission time (`process_execution_payload_bid`), not re-verified when the payment is finally settled via `settle_builder_payment`, which can occur one or two epochs later, after other pending payments/withdrawals for the same builder may have already been queued or partially swept. I was not able to fully trace, within the tool budget available, a concrete unprivileged sequence of operations across epochs that provably drives a builder's balance below the sum of its already-queued pending withdrawals before settlement (this would require tracing `process_builder_pending_payments`, `get_pending_balance_to_withdraw_for_builder`, and the eviction/quorum logic across several epoch boundaries in detail). The capped-vs-uncapped mismatch in `apply_withdrawals` itself is a confirmed root cause in the spec text and test suite, but whether the surrounding admission-control logic (`can_builder_cover_bid`, payment settlement ordering, quorum eviction) fully prevents the triggering precondition is unverified with the evidence gathered.

### Recommendation
Cap `withdrawal.amount` itself (not just the beacon-state deduction) to `min(requested_amount, builder_balance)` when constructing the `Withdrawal` object in `get_builder_withdrawals`, so that the amount committed to `state.payload_expected_withdrawals` (and thus executed on the EL) can never exceed what `apply_withdrawals` actually removes from the builder's balance. Additionally, re-validate that the sum of all pending/queued builder withdrawals never exceeds the builder's balance at every point a new payment/withdrawal is queued, not only at initial bid-submission time.

### Proof of Concept
Cannot be fully constructed from the indexed spec text alone: it requires demonstrating a concrete multi-epoch sequence of bids/settlements (via `process_execution_payload_bid`, `settle_builder_payment`, `process_builder_pending_payments`) that leaves `builder.balance < sum(pending withdrawal amounts for that builder)` at the moment `apply_withdrawals` runs. The mismatch mechanism itself (`min()`-capped balance deduction vs. uncapped `Withdrawal.amount` committed to the payload) is directly demonstrated by the existing test `test_builder_withdrawal_insufficient_balance` [2](#0-1) , which shows a withdrawal of 5 ETH being emitted with `withdrawal.amount = 5 ETH` while the builder balance (1 ETH) is reduced only to 0 — confirming the state/payload amount divergence, though that specific test scenario is an intentionally-constructed test fixture rather than a proven reachable adversarial path through the state-transition function.
