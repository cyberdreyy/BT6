### Title
Silent authority/proof-context slot misalignment in `parse_permissioned_burn_instruction` `ConfidentialBurn` arm - ([File: transaction-status/src/parse_token/extension/permissioned_burn.rs])

### Summary
In the `PermissionedBurnInstruction::ConfidentialBurn` arm, the sequential `offset < account_indexes.len().saturating_sub(2)` guards for the sysvar/equality/validity/range optional accounts all check against the same fixed threshold (`account_indexes.len() - 2`) rather than tracking how many optional slots the attacker-declared offsets actually require. When `account_indexes` is shorter than what the encoded offsets imply, one or more "needs context account" branches are silently skipped (the account/label is dropped), but the walking `offset` counter is not adjusted to compensate, so the subsequent `permissionedBurnAuthority` assignment reads an account index that — per the instruction's own offset semantics — should have been labeled a proof-context-state account, not the authority. All three offset fields and `account_indexes` are attacker-controlled raw instruction bytes, so this misassignment is fully reproducible without any privileged access.

### Finding Description
The relevant logic is: [1](#0-0) [2](#0-1) 

Each of the four optional-account branches (`instructionsSysvar`, `equalityProofContextStateAccount`, `ciphertextValidityProofContextStateAccount`, `rangeProofContextStateAccount`) is gated by `offset < account_indexes.len().saturating_sub(2)` — the *same* bound in every branch, reserving only 2 trailing slots for authority + owner/delegate, regardless of how many of the optional accounts the encoded `equality_proof_instruction_offset`, `ciphertext_validity_proof_instruction_offset`, and `range_proof_instruction_offset` actually declare as needed (offset == 0 ⇒ a context-state account slot is expected; offset != 0 ⇒ only the shared sysvar slot is expected).

Because `account_indexes` and all three offset fields come directly from attacker-supplied instruction data/accounts (`decode_instruction_data`, `check_num_token_accounts(account_indexes, 4)` only guarantees a minimum of 4), an attacker can pick a combination where:
- at least one offset is non-zero (`has_sysvar = true`, consuming the sysvar slot and advancing `offset`), and
- at least one other offset is `0` (declaring a context-state account is expected),

but choose `account_indexes.len()` just large enough to pass `check_num_token_accounts(4)` yet too small to hold all the declared optional accounts. The bound check for the context-account branch then fails (`offset < len - 2` is false), so that context account is silently omitted from the JSON output, but `offset` is **not incremented** to skip past it. The final block: [3](#0-2) 

then reads `account_indexes[offset]` — the very slot that, per the instruction's own offset semantics, should have carried the dropped context-state account — and labels it `"permissionedBurnAuthority"` instead.

Concrete trace (fully self-contained, no on-chain execution needed since `getTransaction(jsonParsed)` parses raw instruction bytes regardless of transaction success/failure):
- `account_indexes.len() == 5` (minimum+1, passes `check_num_token_accounts(4)`)
- `equality_proof_instruction_offset == 0` (declares an equality context account is expected)
- `ciphertext_validity_proof_instruction_offset == 7` (non-zero ⇒ `has_sysvar = true`)
- `range_proof_instruction_offset == 0` (declares a range context account is expected)

Walk: `offset` starts at 2 → sysvar branch fires (`2 < 5-2=3`), assigns `account_keys[account_indexes[2]]` to `instructionsSysvar`, `offset = 3` → equality-context branch: `3 < 3` is false, so it is skipped and `equalityProofContextStateAccount` is never added, `offset` stays `3` → validity branch: offset field non-zero, skipped by condition → range-context branch: `3 < 3` false, skipped, `rangeProofContextStateAccount` never added → final block: `3 < 5-1=4` true, so `account_keys[account_indexes[3]]` is labeled `"permissionedBurnAuthority"`, even though the instruction's own offset fields declare that two context-state accounts (equality and range) are needed before the true authority slot. The account at `account_indexes[3]` is exactly the slot that should have been `equalityProofContextStateAccount` in a self-consistent 7-account layout.

No check exists anywhere in this arm that cross-validates the number of declared optional accounts (derived from the three offsets) against `account_indexes.len()` before doing the walk; the guards only prevent index-out-of-bounds panics, not semantic misalignment.

### Impact Explanation
This is a decoder misreporting bug (`getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding): the RPC-parsed instruction JSON can attribute the `"permissionedBurnAuthority"` role to an account index that is not the true authority under the instruction's own declared offset semantics, but rather a slot that should represent a proof-context-state account. Any downstream consumer of `jsonParsed` output (block explorers, indexers, compliance/monitoring tooling) that trusts this field for a landed (including failed) transaction can be misled about which account acted as the permissioned burn authority. This falls under the explicitly accepted "decoder ... misreporting" / "wrong ... account data returned" bounty category. Impact is limited to the parsed display data; it does not affect consensus, runtime execution, or actual on-chain token accounting.

### Likelihood Explanation
Fully attacker-controlled and reproducible with a single crafted instruction: the attacker builds their own `ConfidentialBurn` instruction with adversarial offset triples and an `account_indexes` length near the `check_num_token_accounts(4)` boundary, submits it via a normal transaction (it may or may not succeed on-chain — `jsonParsed` parsing runs regardless of `meta.err`), and then issues a single `getTransaction` RPC call to observe the misreported field. No privileged access, staked node, or multiple calls are required, satisfying the "single client, single call" constraint.

### Recommendation
Track the number of optional accounts actually required by the three offset fields (sysvar presence + count of offsets equal to 0) before walking `account_indexes`, and validate `account_indexes.len()` against that expected total up front (returning `ParseInstructionError` on mismatch) rather than using a fixed `saturating_sub(2)` threshold per branch. Alternatively, increment `offset` (or track a separate "reserved" counter) even when a branch is skipped due to insufficient length, and refuse to emit `permissionedBurnAuthority`/`authority` when the account layout is inconsistent with the declared offsets, rather than silently reassigning slots.

### Proof of Concept
Rust unit test to add to `transaction-status/src/parse_token/extension/permissioned_burn.rs`:

```rust
#[test]
fn test_confidential_burn_offset_misalignment() {
    use spl_token_2022_interface::extension::confidential_mint_burn::instruction::BurnInstructionData;

    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    // This account_indexes[2] should represent instructionsSysvar,
    // and account_indexes[3] should represent equalityProofContextStateAccount
    // per the declared offsets below, NOT permissionedBurnAuthority.
    let would_be_eq_ctx = Pubkey::new_unique();
    let real_authority = Pubkey::new_unique();
    let owner = Pubkey::new_unique();

    let account_keys = vec![account, mint, Pubkey::new_unique() /*sysvar*/, would_be_eq_ctx, real_authority, owner];
    let account_indexes: Vec<u8> = vec![0, 1, 2, 3, 4]; // len == 5, minimum+1

    let burn_data = BurnInstructionData {
        new_decryptable_available_balance: Default::default(),
        equality_proof_instruction_offset: 0,   // declares equality context account needed
        ciphertext_validity_proof_instruction_offset: 7, // non-zero => has_sysvar = true
        range_proof_instruction_offset: 0,      // declares range context account needed
    };
    let instruction_data = encode_confidential_burn_instruction(&burn_data); // helper to build raw bytes

    let parsed = parse_permissioned_burn_instruction(
        &instruction_data,
        &account_indexes,
        &AccountKeys::new(&account_keys, None),
    )
    .unwrap();

    // BUG: authority field aliases the slot that should be equalityProofContextStateAccount.
    assert_eq!(
        parsed.info["permissionedBurnAuthority"],
        json!(would_be_eq_ctx.to_string()), // wrongly reports proof-context account as authority
    );
    // equalityProofContextStateAccount and rangeProofContextStateAccount are silently dropped
    assert!(parsed.info.get("equalityProofContextStateAccount").is_none());
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());
}
```

Expected (buggy) result: `permissionedBurnAuthority` resolves to `would_be_eq_ctx`, not `real_authority`, confirming the offset-declared context-account slot is misreported as the authority. A fixed implementation should either reject this account/offset combination or correctly track the reserved slot so `permissionedBurnAuthority` never aliases an account that the instruction's own offsets designate as a proof-context account.
