Based on my investigation, I found a concrete unchecked-arithmetic issue in the gateway's message-freshness check that is a direct analog to the reported "not using SafeMath" bug class — raw arithmetic performed on attacker-influenced values without any bounds/overflow protection, undermining a security check.

### Title
Unchecked unsigned-integer arithmetic in gateway stale-message check allows anti-replay bypass - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`HandleLegacyUserMessage` validates message freshness using raw, unchecked `uint` subtraction/comparison between the current time and a client-supplied timestamp, instead of using a safe, bounds-checked time comparison. This mirrors the reported bug class of using plain arithmetic operators instead of protected math operations, and it results in a real staleness/anti-replay check that can be defeated by unprivileged client input.

### Finding Description
The handler computes freshness as: [1](#0-0) 

specifically: [2](#0-1) 

`uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` performs a raw `uint` subtraction and comparison with no protection against wraparound. `payload.Timestamp` originates directly from the untrusted, client-supplied `TriggerRequestPayload` decoded from the message body [3](#0-2) , i.e., an unprivileged workflow/user-originated request reaching the internet-facing gateway. Only a check that `payload.Timestamp == 0` is rejected exists before this comparison; there is no validation that the timestamp is within a sane range, nor any protection against integer conversion/wraparound of an out-of-range or malformed value, which is exactly the class of defect the referenced report calls out (plain operators instead of protected/overflow-safe arithmetic). This same pattern is also visible in the related test for stale-message handling, confirming this is the only staleness gate in the path: [4](#0-3) .

Additionally, the check only rejects timestamps that are too *old* (`now - maxAge > timestamp`); it never rejects timestamps that are far in the *future*, so a crafted timestamp value can always satisfy the freshness check regardless of actual staleness, compounding the impact of the unchecked-arithmetic issue.

### Impact Explanation
This check exists specifically to prevent processing of stale/replayed messages from unprivileged clients through the gateway's node-message dispatch path — the same message is subsequently forwarded to all DON members [5](#0-4) . Bypassing it via unchecked arithmetic/type-conversion behavior undermines the anti-replay/staleness guarantee that downstream node handlers rely on, potentially enabling replay or improperly-timed trigger requests to reach worker DON nodes.

### Likelihood Explanation
The `HandleLegacyUserMessage` path is reachable directly from unprivileged/external gateway clients submitting trigger requests (no special privilege is required beyond normal request submission), and the `Timestamp` field is fully attacker-controlled JSON input, making this a straightforward, remotely reachable path to trigger the flawed check.

### Recommendation
Replace the raw `uint` subtraction/comparison with time-safe comparisons (e.g., convert to `time.Time`/`time.Duration` and use `time.Since`/`Sub` with explicit bounds checks), and add explicit validation rejecting timestamps that are unreasonably far in the future as well as the past, rather than relying on unchecked integer arithmetic on client-supplied values.

### Proof of Concept
A client submits a `web_api_trigger` legacy message whose JSON payload's `Timestamp` field is set to a very large or otherwise out-of-normal-range numeric value (e.g., a value that, depending on the underlying numeric type of `TriggerRequestPayload.Timestamp`, converts unexpectedly under `uint(payload.Timestamp)`), then observes that `HandleLegacyUserMessage` does not reject the message as stale and forwards it to the DON, as exercised by the existing stale-message test at [4](#0-3)  — modifying the timestamp value used there to a boundary/overflow-inducing value demonstrates the check no longer functions as intended.

**Note on verification limits:** I was unable to fully confirm the exact declared Go type (`int64` vs `uint64`) of `TriggerRequestPayload.Timestamp` in `core/capabilities/webapi/webapicap/event_trigger_generated.go` before running out of tool iterations, which affects whether a negative-timestamp wraparound scenario is directly exploitable versus only the "future timestamp is never rejected" gap being exploitable. Both sub-issues stem from the same root cause (unchecked/unsafe arithmetic and missing bounds validation on attacker-controlled time input) and should be fixed together; a Devin session with full file access should confirm the exact field type before finalizing remediation.

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body

	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)

				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
