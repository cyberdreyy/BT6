### Title
`BlockRejection` / `BlockAccepted` signature does not bind `reason_code` / `response_data` - gossip-level tampering can recast a rejection's reason without invalidating the signer's signature ([File: libsigner/src/v0/messages.rs])

### Summary
The external report's bug class is "the wrong/incomplete data is used to compute a value that is supposed to represent the whole message" (fee estimated over 3 of 4 fields instead of all 4, so the estimate silently diverges from the real committed value). The direct analog in this codebase is `BlockRejection::hash()`/`sign()`/`verify()`/`recover_public_key()` in `libsigner/src/v0/messages.rs`: the signature is computed only over `self.signer_signature_hash` (plus the domain triple which bakes in `chain_id`), while `reason`, `reason_code`, `metadata`, and `response_data` (which carries `reject_reason: RejectReasonPrefix`, `failed_txid`, and the tenure/read-count extension timestamps) are transmitted unsigned. Any party that can rewrite the StackerDB chunk in transit (gossip layer) can alter these unsigned fields on an otherwise validly-signed rejection, and the signature will still verify.

### Finding Description
`BlockRejection::hash()`: [1](#0-0) 
only folds `signer_signature_hash` into the structured-data hash that gets signed: [2](#0-1) 
`verify()` and `recover_public_key()` re-derive the exact same hash from `self.hash()`, so they only ever authenticate the tuple (`domain(chain_id)`, `signer_signature_hash`): [3](#0-2) 

But the struct carries several other semantically significant, *unsigned* fields that downstream signer logic trusts as if they were part of the authenticated message: [4](#0-3) 

Notably `reason_code` / `response_data.reject_reason` (a `RejectReasonPrefix`) is used by peers to bucket rejection weight for reorg-protection logic: [5](#0-4) 
and specifically to decide whether to mark a miner's sortition as invalid: [6](#0-5) 

Because `reason_code`/`response_data` are not covered by the signature, any relay/gossip participant that forwards `BlockRejection` StackerDB chunks can flip a signer's rejection reason (e.g. from an ordinary validation failure to `ReorgNotAllowed`, or vice versa) while leaving `signature` and `signer_signature_hash` untouched — the modified chunk still authenticates successfully via `verify()`/`recover_public_key()` on every receiving signer and node-side consumer that checks this message type. `failed_txid` inside `response_data` is likewise unauthenticated and feeds into `FailedTxInfo`/problematic-tx bookkeeping on the node side (`stackerdb_listener.rs`).

This is precisely analogous to the LayerZero report: the "fee" (here, the signature) is computed over a strict subset of the fields that make up the real semantic message, so the two representations (what was signed vs. what is trusted/acted upon) can diverge whenever an intermediary edits the un-covered fields.

### Impact Explanation
An attacker who controls message relay for the `.signers` StackerDB contract (a gossip-layer position explicitly in scope per the rules) can, without holding any signer key or a majority of signers, retag a legitimately-signed rejection's `reason_code`/`response_data.reject_reason`:
- Turning an ordinary rejection into `ReorgNotAllowed` from enough (real) rejecting signers can push `total_reorg_reject_weight` over threshold and cause `sortition_state.cur_sortition.miner_status` to be set to `InvalidatedBeforeFirstBlock`, wedging that miner out of producing further blocks in the tenure even though no signer actually voted "reorg not allowed." This is a liveness wedge on an otherwise-valid miner/tenure.
- Conversely, stripping/mutating away a `ReorgNotAllowed` code could suppress the miner-invalidation safety mechanism that is supposed to stop a disallowed reorg from proceeding.
- Tampering with `failed_txid` in `response_data` can mislead per-txid problematic-transaction weight bookkeeping on the node side without invalidating the signer's authenticity.

This does not directly let a single relay forge a block acceptance or a valid-block signature (the `signer_signature_hash` itself, which anchors identity to a specific block, IS signed), so it falls short of "signing an invalid/non-canonical block" or a full "rejection recounted as acceptance." Its concrete, provable effect is corruption of the *reason* classification used by the reorg-protection state machine — a High-severity liveness/safety wedge on the miner-invalidation path, not a Critical block-signing forgery.

### Likelihood Explanation
Likelihood is comparable to the original report's "high": no signer key, no majority, and no cryptographic break are required — only the ability to intercept/relay a `.signers` StackerDB chunk (miner/relay/gossip position), which the analog-scan rules explicitly treat as in-scope ("a one-slot miner (plus gossip) can trigger"). The mutation is a straightforward re-serialization of the unsigned trailing fields of `BlockRejection` before re-publishing the chunk (chunk-level version bumps aside, this is a message-content change, not a StackerDB-protocol-level attack).

### Recommendation
Include `reason_code` (or the derived `RejectReasonPrefix`) and the security-relevant contents of `response_data` (at minimum `reject_reason` and `failed_txid`) inside the structured-data tuple hashed in `BlockRejection::hash()`, mirroring how `signer_signature_hash` is already folded in. Apply the same audit to `BlockAccepted`/`MockSignature`/other `v0` message types to ensure every field that downstream consensus-relevant logic reads is covered by the signer's signature, not just the fields chosen when the type was first introduced.

### Proof of Concept
1. A signer emits a valid `BlockRejection` for `signer_signature_hash = H` with `reason_code = ValidationFailed(SomeBenignCode)` and `response_data.reject_reason = RejectReasonPrefix::ValidationFailed`, signed via `BlockRejection::sign` (`libsigner/src/v0/messages.rs:1809-1814`).
2. A relay intercepting the `.signers` StackerDB chunk deserializes the message, sets `reason_code = RejectCode::??? ` / `response_data.reject_reason = RejectReasonPrefix::ReorgNotAllowed` (or edits `response_data.failed_txid`), and re-serializes it, leaving `signature` and `signer_signature_hash` unchanged.
3. Any peer signer/node calling `rejection.verify(pubkey)` or `rejection.recover_public_key()` (`libsigner/src/v0/messages.rs:1817-1837`) still succeeds, because `hash()` never included the tampered fields.
4. The tampered `reject_reason` is then folded into `compute_reject_code_signing_weight(..., RejectReasonPrefix::ReorgNotAllowed)` (`stacks-signer/src/v0/signer.rs:2186-2199`, `2354-2368`), potentially crossing the reorg-invalidation threshold and flipping `sortition_state.cur_sortition.miner_status` for a miner that no signer actually voted to block.

    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
