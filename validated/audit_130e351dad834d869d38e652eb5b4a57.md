## Title
Stale confirmations from removed multisig members are not purged from pending requests, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
When a multisig member is removed via `DeleteMember` (in `multisig2`) or a key is removed via `DeleteKey` (in `multisig`), the contract only deletes requests *originated* by that member/key. It does not scan and purge that member's confirmations from requests that were *added by other members*. Because `confirm()` tallies confirmations purely by set size without re-validating that every entry in the stored confirmation set still belongs to a current, live member, a confirmation cast by a member before their removal remains valid and counted forever afterward, effectively lowering the number of live confirmations actually required to execute a request below `num_confirmations`.

### Finding Description
The binding that should hold is:

`executed_request.confirmations.count(live_members) == num_confirmations`

i.e., a request should only execute once `num_confirmations` *currently authorized* members have approved it.

In `multisig2/src/lib.rs`, `confirm()` simply checks the size of the stored confirmations set: [1](#0-0) 

Membership is validated only when a *new* confirmation is being added (via `current_member()` inside `confirm`), never when tallying pre-existing entries in the `confirmations` set: [2](#0-1) 

When a member is removed, `delete_member` only clears confirmations for requests where that member was the *original requester* (`r.member == member`). It does not iterate over `self.confirmations` to strip that member's entries from requests raised by other members: [3](#0-2) 

The same pattern exists in the legacy `multisig` contract: `DeleteKey` only removes requests signed (added) by the deleted `pk`, and clears confirmations only for those specific requests, leaving that key's confirmations on other outstanding requests intact: [4](#0-3) [5](#0-4) 

This is directly analogous to the Astaria bug class: a previously-recorded value (a confirmation, analogous to accrued principal) is silently carried forward and reused to satisfy a later check (the execution threshold), even though the real-world state backing it (the confirming member's authorization) has since changed. Just as `stack.point.amount` kept stale, compounded interest baked into the "principal" for future comparisons, the confirmations set keeps a stale, no-longer-authorized approval baked into the count used for the "have we reached threshold" comparison.

### Impact Explanation
An attacker who is (or was) a legitimate multisig member — including one whose access key/membership is later revoked because it was compromised, an employee departed, or a rotation policy required removal — can confirm one or more pending requests before removal. After removal, those confirmations remain counted. If the remaining live members later confirm the same request, the multisig will execute it once `confirmations.len() + 1 >= num_confirmations` is reached, even though fewer than `num_confirmations` *currently live* members actually approved it. This directly matches the Critical impact category: "a multisig request executed below threshold." Since `execute_request` can perform `Transfer`, `AddKey`/`FunctionCallPermission`, `DeployContract`, or arbitrary `FunctionCall` actions on the multisig's own account, this can result in unauthorized movement of NEAR held by the multisig or unauthorized privilege escalation (e.g., adding a new full access key), which is exactly the kind of "NEAR moved by a party not entitled to it" scenario the rules call out.

### Likelihood Explanation
This requires no special access beyond what a legitimate multisig member already had at some point in time: any member removal event (routine key rotation, compromise response, employee offboarding) creates the exact window described. There is no additional permission needed beyond confirming a request while still a member — a completely ordinary action — and the flaw is purely in the missing cleanup during `DeleteMember`/`DeleteKey`. Because requests can remain open (subject only to the `active_requests_limit` and no forced expiration other than manual `delete_request` after `REQUEST_COOLDOWN`), the stale confirmation can persist for as long as the request stays open, giving ample opportunity for it to be "topped up" by the remaining members without anyone noticing the count already includes an invalid entry.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all `confirmations` entries (not only requests raised by that member) and remove that member/key from any confirmation sets it participated in. Alternatively, re-validate every entry in a request's confirmation set against current membership at the time `confirm()` tallies the count (i.e., only count members that `self.members.contains(...)` at execution time), rather than trusting historically stored strings/keys.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 2` and members `{A, B, M}`.
2. `A` calls `add_request` to create a `Transfer` request to attacker-controlled account `X` (request_id = 0).
3. `M` calls `confirm(0)` → `confirmations = {M}`, size 1 < 2, request stays open. [6](#0-5) 
4. The organization removes `M` from the multisig via `DeleteMember { member: M }` (e.g., because `M`'s key was compromised). `delete_member` only purges requests where `r.member == M` (i.e., requests *added* by `M`); request 0 was added by `A`, so its confirmation set `{M}` is left untouched. [7](#0-6) 
5. `B` (a legitimate, currently-live member) calls `confirm(0)`. `confirmations.len() as u32 + 1 == 2 >= num_confirmations`, so `execute_request` runs and transfers funds to `X`.
6. Result: the transfer executed with only one live-member confirmation (`B`) plus one stale confirmation from a removed member (`M`), instead of the required two live-member confirmations — funds moved below the intended authorization threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()

            }

                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
