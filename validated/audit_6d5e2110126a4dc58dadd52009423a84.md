## Finding: Operator commission is paid to the old operator instead of their configured beneficiary after `switch_operator` [1](#0-0) 

### Title
Stale operator commission distribution bypasses `beneficiary_for_operator` after `switch_operator`, paying commission to the old operator's own address instead of their designated beneficiary - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` decides whether to redirect a payout to an operator's beneficiary by comparing the recorded distribution `recipient` to the *current* `operator` parameter passed into the function. When a staker calls `switch_operator` while the old operator still has an outstanding, unlocked-but-not-yet-distributed commission entry in the `distribution_pool`, that entry's `recipient` remains the old operator's address, but all subsequent `distribute()` calls on that staking contract pass the *new* operator's address as `operator`. Because `recipient == operator` is false, `beneficiary_for_operator(operator)` is never applied to the stale entry, so the old operator's commission is paid directly to the old operator's own account instead of the beneficiary address they configured via `set_beneficiary_for_operator`.

### Finding Description
`request_commission_internal` records a pending distribution keyed by the operator's own address without resolving the beneficiary at record time: [2](#0-1) 

`switch_operator` can be called by the staker at any time to move a `StakingContract` from `old_operator` to `new_operator`. It flushes already-inactive stake and calls `request_commission_internal` for `old_operator` (which may only *unlock*, not yet distribute, the commission if the pool's lockup hasn't expired), then re-inserts the same `StakingContract` (carrying its `distribution_pool`) under the `new_operator` key: [3](#0-2) 

The beneficiary redirection logic in `distribute_internal` only triggers when the stored `recipient` equals the `operator` argument passed into the *current* call: [4](#0-3) 

Once the switch has happened, every future call to `distribute(staker, new_operator)` passes `operator = new_operator`. The stale distribution entry recorded under `old_operator`'s address never matches `new_operator`, so `beneficiary_for_operator` is skipped for that entry and the coins are sent straight to `old_operator`, silently bypassing the beneficiary the old operator had configured with `set_beneficiary_for_operator`.

The existing regression test only exercises the case where `distribute()` is called to fully flush old_operator's pending commission *before* `switch_operator` runs, which is why the beneficiary path appears to work correctly in that test: [5](#0-4) 

It does not cover the case where `request_commission` was called (unlocking commission) but the lockup has not yet expired (so `distribute()` cannot flush it) at the time `switch_operator` is invoked — leaving a stale, unresolved `recipient == old_operator` entry sitting in the pool that only gets paid out later, under the new operator's context.

### Impact Explanation
This corrupts operator-commission accounting by crediting the wrong account: funds intended for the operator's beneficiary (e.g., a custodial/cold-storage/split-revenue address the operator explicitly configured) are instead sent to the old operator's own address. This matches the required impact class "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account." Any staker holding a `staking_contract` can unprivilegedly trigger this by calling `switch_operator` while a `request_commission` unlock is in flight, and anyone can permissionlessly call `distribute` to complete the mis-routed payout.

### Likelihood Explanation
Moderate-to-high: `switch_operator`/`switch_operator_with_same_commission` and `request_commission` are both regular, unprivileged, permissionless-adjacent entry points used in normal staking-contract lifecycle management (vesting contracts also call `switch_operator` via `vesting::update_operator`). The only precondition is that a commission request has been unlocked but not yet distributed (i.e., the stake pool's lockup has not expired) when the staker decides to switch operators — a realistic and easily reachable timing window that does not require any privileged role beyond the staker's own existing rights.

### Recommendation
Resolve the beneficiary at distribution time based on the `recipient` address itself rather than comparing it to the `operator` parameter, e.g. change the check in `distribute_internal` to something like: if `recipient` has an associated `BeneficiaryForOperator` entry (`exists<BeneficiaryForOperator>(recipient)`), redirect to `beneficiary_for_operator(recipient)`, regardless of whether `recipient` equals the currently active `operator`. Alternatively, force a full `distribute_internal` flush of any old operator's pending distributions inside `switch_operator` before re-keying the `StakingContract`, ensuring no stale recipient entries survive the operator switch.

### Proof of Concept
1. Staker creates a staking contract with `operator1` and 10% commission via `create_staking_contract`.
2. `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary1)`.
3. Stake pool earns rewards; `operator1` (or staker) calls `request_commission(operator1, staker, operator1)`. This unlocks commission and records `add_distribution(operator1, staking_contract, recipient=operator1, commission_amount)` in the pool — but the stake pool's lockup has not yet expired, so the amount is still `pending_inactive`, not `inactive`, and cannot yet be distributed.
4. Staker calls `switch_operator(staker, operator1, operator2, new_commission)` before the lockup expires. The `StakingContract` (with the pending `recipient=operator1` distribution entry) is now stored under `operator2`.
5. Time passes; the lockup expires, making the previously-unlocked commission `inactive`/withdrawable.
6. Anyone calls `distribute(staker, operator2)`. `distribute_internal` runs with `operator = operator2`; the stale entry has `recipient = operator1`, so `recipient == operator` is false, `beneficiary_for_operator` is never applied, and the commission is deposited directly to `operator1`'s account instead of `beneficiary1`.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

    public entry fun switch_operator(
        staker: &signer,
        old_operator: address,
        new_operator: address,
        new_commission_percentage: u64
    ) acquires Store, BeneficiaryForOperator {
        let staker_address = signer::address_of(staker);
        assert_staking_contract_exists(staker_address, old_operator);

        assert!(
            new_commission_percentage <= 100,
            error::invalid_argument(EINVALID_COMMISSION_PERCENTAGE)
        );
        // Merging two existing staking contracts is too complex as we'd need to merge two separate stake pools.
        let store = borrow_global_mut<Store>(staker_address);
        let staking_contracts = &mut store.staking_contracts;
        assert!(
            !staking_contracts.contains_key(&new_operator),
            error::invalid_state(ECANT_MERGE_STAKING_CONTRACTS)
        );

        let (_, staking_contract) = staking_contracts.remove(&old_operator);
        // Force distribution of any already inactive stake.
        distribute_internal(
            staker_address,
            old_operator,
            &mut staking_contract,
        );

        // For simplicity, we request commission to be paid out first. This avoids having to ensure to staker doesn't
        // withdraw into the commission portion.
        request_commission_internal(
            old_operator,
            &mut staking_contract,
        );

        // Update the staking contract's commission rate and stake pool's operator.
        stake::set_operator_with_cap(&staking_contract.owner_cap, new_operator);
        staking_contract.commission_percentage = new_commission_percentage;

        let pool_address = staking_contract.pool_address;
        staking_contracts.add(new_operator, staking_contract);
        emit(SwitchOperator { pool_address, old_operator, new_operator });
    }

    /// Add a new distribution for `recipient` and `amount` to the staking contract's distributions list.
    fun add_distribution(
        operator: address,
        staking_contract: &mut StakingContract,
        recipient: address,
        coins_amount: u64,
    ) {
        let distribution_pool = &mut staking_contract.distribution_pool;
        let (_, _, _, total_distribution_amount) =
            stake::get_stake(staking_contract.pool_address);
        update_distribution_pool(
            distribution_pool,
            total_distribution_amount,
            operator,
            staking_contract.commission_percentage
        );

        distribution_pool.buy_in(recipient, coins_amount);
        let pool_address = staking_contract.pool_address;
        emit(AddDistribution { operator, pool_address, amount: coins_amount });
    }
