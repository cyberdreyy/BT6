### Title
Stale confirmations from removed multisig members allow request execution below the live confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`delete_member` (multisig2) / the `DeleteKey` action (multisig) only purge outstanding **requests that the removed member created**, but never scrub that member's **confirmations** left on *other* still-pending requests they had merely confirmed (not created). Since `confirm()` tallies confirmations purely by `confirmations.len()`, a confirmation cast by a member who has since been removed still counts toward `num_confirmations`, letting a request execute with fewer *live* member confirmations than the configured threshold.

### Finding Description
In `multisig2/src/lib.rs`, confirmations are stored independently of membership, in a `LookupMap<RequestId, HashSet<String>>` keyed by the confirmer's member string [1](#0-0) . When a member is removed, `delete_member` removes only the requests **created** by that member (matched via `r.member == member`, where `member` is the request's original *signer*, not its confirmers), and clears `num_requests_pk` — but does nothing to strip that member's entry out of the `confirmations` set of any *other* request they had confirmed: [2](#0-1) 

`confirm()` then checks the threshold purely against the stored confirmation count, without re-validating that every entry in the set still belongs to a current member: [3](#0-2) 

`current_member()` is only used to validate the *caller* of the current `confirm` call, not to filter the pre-existing `confirmations` set [4](#0-3) .

The equality that should hold is:
```
confirmations.len() (live members only) >= num_confirmations
```
but the actual code enforces:
```
confirmations.len() (live + stale members) >= num_confirmations
```
This is the same class of bug as the reported issue: a value used to authorize an action (confirmation count) is not re-synchronized against the current state of the entitled set (live members) before that action is authorized — analogous to rebalancing shares before withdrawal.

The original v1 `multisig` contract has the identical pattern: `DeleteKey` only removes requests where `r.signer_pk == pk` (i.e., requests created by that key), leaving that key's confirmations on other requests intact [5](#0-4) , and `confirm()` counts `confirmations.len()` without re-validating membership [6](#0-5) .

### Impact Explanation
This allows a multisig request (e.g., a `Transfer` of funds, a `FunctionCall`, or an `AddKey`) to be executed once the raw confirmation count reaches `num_confirmations`, even though one or more of those confirmations belong to accounts/keys that have since been removed from the multisig. Effectively, the request executes below the intended live-member threshold, which is a "multisig request executed below threshold" — a Critical-severity outcome per the funds-authorization boundary the multisig is meant to enforce.

### Likelihood Explanation
This requires no privileged access beyond normal multisig operation: any member can confirm a request; membership changes (`DeleteMember`/`DeleteKey`) are a standard, expected multisig operation (e.g., removing a compromised or departing signer). The scenario — a pending request confirmed by a member later removed, then completed by remaining members — is a realistic operational sequence, not a contrived edge case, making likelihood moderate-to-high in any multisig with member turnover.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over **all** pending requests' `confirmations` sets (not just those where the member is the original signer) and remove the member's entry from each. Alternatively, when tallying confirmations in `confirm()`, filter the stored confirmation set against `self.members` (or valid keys) before comparing against `num_confirmations`, so only confirmations from currently-live members count toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R1)` for a `Transfer` — `R1.confirmations = {A}`.
3. `B` calls `confirm(R1)` — `R1.confirmations = {A, B}` (2 < 3, still pending).
4. Members `A, C, D` execute a separate request `DeleteMember { member: B }`, removing `B` from `members`. Per `delete_member`, only requests created by `B` are purged; `R1` (created by `A`) is untouched, so `R1.confirmations` still contains `B`.
5. `C` calls `confirm(R1)`: `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `R1` executes the `Transfer`, even though only `A` and `C` are actual live confirmers (2 live confirmations against a nominal threshold of 3). [3](#0-2) [2](#0-1)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
