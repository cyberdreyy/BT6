### Title
Reward-token swaps use execution-time deadline (`block.timestamp` / `block.timestamp + 100`), giving no protection against delayed or sandwiched harvest transactions - (contracts/IdleCDO.sol)

### Summary
`IdleCDO._sellReward()` (and the identical overrides in `IdleCDOArbitrum`, `IdleCDOAvax`, `IdleCDOBase`, `IdleCDOOptimism`, `IdleCDOPolygon`, `IdleCDOPolygonZK`) hardcodes the Uniswap V3 `deadline` as `block.timestamp + 100`, evaluated inside the same transaction that performs the swap. The deadline therefore always passes — it is computed at the moment of execution, so it cannot expire a stale transaction. The same defect appears verbatim in strategy-level reward swaps that pass `block.timestamp` as the V2 router deadline (`ConvexBaseStrategy.redeemRewards`, `IdleMStableStrategy`, `IdleMStableStrategyPolygon`), matching the reported Tokemak `UniV3Swap` bug class exactly. ### Finding Description
`_sellReward` is invoked from `_sellAllRewards` during `harvest()`, which swaps accrued reward tokens for the underlying via `ISwapRouter.exactInput`:

```solidity
// contracts/IdleCDO.sol:622
ISwapRouter.ExactInputParams memory params = ISwapRouter.ExactInputParams({
  path: _path,
  recipient: address(this),
  deadline: block.timestamp + 100,   // evaluated at execution time
  amountIn: _amount,
  amountOutMinimum: _minAmount
});
return (_amount, _swapRouter.exactInput(params));
```

The Uniswap router checks `block.timestamp <= deadline`. Since `deadline` is set to the *current* block timestamp (+100s), the check can never fail — the deadline parameter is dead code. A harvest transaction sitting in the mempool can be delayed arbitrarily (within builder/sequencer discretion or via transaction replacement/censorship patterns) and still execute at the price prevailing at execution time, not at the time the harvester signed it. On the L2 variants (`IdleCDOBase`, `IdleCDOOptimism`, `IdleCDOArbitrum`, `IdleCDOAvax`, `IdleCDOPolygon*`), sequencer re-ordering or delayed inclusion has the same effect. The only residual protection is `amountOutMinimum = _minAmount`, which is supplied off-chain in `_extraData` based on a price quoted at signing time — a quote that is stale exactly when the delay matters.

Broken invariant: the protocol's reward-accounting assumes the swap realizes roughly the oracle-quoted price used to derive `_minAmount`; with no effective deadline, there is no on-chain bound tying execution time to the quote. Slippage is only bounded by `_minAmount`, which a keeper sets once and which may embed a wide tolerance for multi-hop paths (`_paths` is attacker-influencable caller data on permissionless harvests).

### Impact Explanation
If the harvest caller (or a permissionless caller, where `harvest` is open) uses a generous `_minAmount` — e.g., a stale quote from minutes earlier, or `0`/low values commonly used for dust rewards — the reward swap executes at whatever price the pool shows when the tx lands, and the protocol books the loss as reduced `harvestedRewards`/NAV, i.e., a direct loss of unclaimed yield accruing to tranche holders. The impact equals `quotedOut - actualOut` within the slippage band, which on thin multi-hop reward pools (e.g., CRV/CVX-type rewards routed through WETH) can be a substantial fraction of the reward amount. This is theft of yield via MEV rather than core-principal theft, so severity is medium-low, but the defect is the identical bug class: the deadline parameter provides zero protection.

### Likelihood Explanation
Requires either (a) a permissionless `harvest`/`redeemRewards` call with a stale or lax `_extraData` minOut combined with an adversarial mempool/sequencer environment, or (b) a legitimately-submitted harvest held in the mempool through a volatile window. On mainnet, builders can reorder but cannot hold transactions indefinitely; on L2s with centralized sequencers, ordering discretion is real. Sandwich profit is capped by `_minAmount`, so exploitation requires harvesters to pass loose minOuts — empirically common for small reward sells. The flaw is latent in every chain variant because the pattern is copy-pasted across all `_sellReward` overrides and in `ConvexBaseStrategy`/`IdleMStableStrategy*` where the deadline is literally `block.timestamp`.

### Recommendation
- Accept a deadline (or a max-staleness parameter) as part of `_extraData`/`redeemRewards` calldata and pass it through to `ExactInputParams.deadline`, reverting if `block.timestamp` exceeds the signed deadline.
- Alternatively validate `_minAmount` on-chain against a spot/TWAP check (`_minAmount >= oraclePrice * (1 - maxSlippage)`) so that execution-time price drift beyond a bound reverts regardless of deadline.
- Apply the fix uniformly: `contracts/IdleCDO.sol` `_sellReward`, and all overrides in `contracts/arbitrum/IdleCDOArbitrum.sol`, `contracts/avax/IdleCDOAvax.sol`, `contracts/base/IdleCDOBase.sol`, `contracts/optimism/IdleCDOOptimism.sol`, `contracts/polygon/IdleCDOPolygon.sol`, `contracts/polygon-zk/IdleCDOPolygonZK.sol`, plus the `block.timestamp` deadlines in `ConvexBaseStrategy.sol` and both `IdleMStableStrategy*` files.

### Proof of Concept
Fork-based PoC sketch (Foundry, mainnet fork):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract DeadlineAlwaysPassesPoC is Test {
    // Shows the deadline check in _sellReward can never fail:
    // simulate a "stale" harvest submitted at t0 but executed at t0 + 1 hour.

    function testDeadlineIsExecutionTime() public {
        uint256 t0 = block.timestamp;

        // Advance time far beyond any reasonable deadline
        vm.warp(t0 + 1 hours);

        // _sellReward computes deadline = block.timestamp + 100 *at this block*.
        // Emulate the router's check:
        uint256 deadline = block.timestamp + 100; // what IdleCDO._sellReward does
        assertTrue(block.timestamp <= deadline);  // always true -> check never reverts

        // For ConvexBaseStrategy / IdleMStableStrategy the deadline is literally
        // block.timestamp, so block.timestamp <= block.timestamp holds too.
        uint256 v2Deadline = block.timestamp;
        assertTrue(block.timestamp <= v2Deadline);
    }

    // Full exploit path (mainnet fork):
    // 1. Quote reward->WETH->underlying price at t0; build harvest _extraData
    //    with _minAmount based on that quote.
    // 2. Move the pool (large swap on the reward/WETH pool) so execution at t1
    //    yields less than the t0 quote.
    // 3. Call IdleCDO.harvest(...) (or strategy.redeemRewards) at t1.
    //    The swap still executes despite the quote being stale: no deadline binds
    //    it to t0. harvestedRewards reflect the worse price; assert
    //    contractValue after harvest < expected(t0 quote).
}
```

The structural assertion (execution-time deadline can never revert) holds for all six `_sellReward` overrides and the three strategy swap sites cited. Note: the practical fund loss is bounded by the `_minAmount` supplied by the harvester, so the strongest framing is "deadline parameter is dead code providing zero MEV/staleness protection," identical in class to the reported Tokemak issue, with the caveat that whether `harvest` is permissionless (which determines whether an unprivileged attacker can supply `_extraData` directly) could not be fully confirmed within the available search iterations.
