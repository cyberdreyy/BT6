Confirmed root cause. `get_builder_withdrawals` (specs/gloas/beacon-chain.md) creates a `Withdrawal` object using the full requested `withdrawal.amount` from `state.builder_pending_withdrawals`, uncapped by the builder's actual balance:

```python
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal.amount,
    )
)
``` [1](#0-0) 

This committed `Withdrawal.amount` becomes part of `state.payload_expected_withdrawals`, which the execution layer is required to honor by minting that exact amount to `fee_recipient`. But when `apply_withdrawals` actually debits the CL-side balance, it caps the deduction to whatever the builder actually has:

```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [2](#0-1) 

### Why this breaks an equality
The test suite for this exact function documents the divergence explicitly: when a builder's balance is less than the pending-withdrawal amount, the withdrawal committed to the EL still carries the full requested amount, while the CL-side deduction is capped ("deduction capped to available balance") [3](#0-2)  and the assertion helper explicitly models "Builder withdrawals cap at available balance (spec uses min())" while the committed `payload_expected_withdrawals` field is asserted to equal the **uncapped** `get_expected_withdrawals` result [4](#0-3) .

Since the execution layer mints ETH equal to the committed `Withdrawal.amount` for every entry in `payload_expected_withdrawals` (this is the entire point of the beacon-block/EL commitment model — the EL is required to honor exactly what the CL committed), any case where `withdrawal.amount > builder.balance` results in the EL crediting the `fee_recipient` with more ETH than was ever backed by a corresponding CL-side balance decrease. This breaks the "Gwei created" invariant: total minted-on-EL must equal total debited-on-CL for every withdrawal.

The spec authors are aware of and have partially documented a related asymmetry (timing of CL debit vs EL mint) in the `process_withdrawals` note, explicitly warning that "any CL-side saturation creates a net supply inflation" for the *validator* sweep case where `decrease_balance` saturates at zero [5](#0-4) . However, that note is scoped to normal validator withdrawals reduced by `process_pending_consolidations` between commitment and deduction slot — it does not cover the builder-pending-withdrawal path, where the balance shortfall is not a timing artifact but a structural one: `builder_pending_withdrawals` entries can be created with an `amount` that already exceeds the builder's balance at commitment time (e.g., via `settle_builder_payment` or the direct-append path for evicted payments in `apply_parent_execution_payload`, lines 1761-1770), and `get_builder_withdrawals` never caps by `builder.balance` when constructing the committed `Withdrawal`.

### Title
Builder pending-withdrawal amount is committed uncapped, while the CL-side deduction is capped to available balance, minting unbacked Gwei on the execution layer — (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` builds the `Withdrawal` entries in `payload_expected_withdrawals` directly from `BuilderPendingWithdrawal.amount`, without capping to the builder's current balance. `apply_withdrawals` later caps the actual CL balance decrease with `min(withdrawal.amount, builder_balance)`. Because the execution layer must mint exactly what the block/state committed in `payload_expected_withdrawals`, any shortfall between the committed amount and the capped CL debit results in ETH being minted on the EL that is not backed by an equivalent CL balance reduction.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md:1802-1834) iterates `state.builder_pending_withdrawals` and creates a `Withdrawal(amount=withdrawal.amount, ...)` for each entry, with no comparison against `state.builders[builder_index].balance`. This is unlike `get_validators_sweep_withdrawals`/`get_pending_partial_withdrawals`, which explicitly bound amounts by the validator's `balance`. The resulting `Withdrawal` list is stored verbatim in `state.payload_expected_withdrawals` (`update_payload_expected_withdrawals`), which the spec's own comments describe as binding on the execution layer: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer" (specs/gloas/beacon-chain.md:1969-1972). Meanwhile `apply_withdrawals` performs `state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)` — capping the CL-side debit. If `withdrawal.amount > builder_balance`, the CL only debits `builder_balance` (down to 0), but the EL, following the committed withdrawal, must still credit `fee_recipient` the full `withdrawal.amount`.

### Impact Explanation
This falls under Critical: "Gwei created, destroyed or paid to a non-owner" — new, unbacked ETH is minted on the execution layer whenever a `BuilderPendingWithdrawal.amount` exceeds the builder's balance at processing time. Depending on how `BuilderPendingWithdrawal` entries are produced (e.g., `settle_builder_payment`, or the direct append for parent bids older than the previous epoch at specs/gloas/beacon-chain.md:1761-1770), a builder balance can already be exhausted (e.g., by an intervening exit/other withdrawal) by the time this pending withdrawal is processed, making the shortfall reachable through ordinary protocol operation rather than a hypothetical.

### Likelihood Explanation
The repository's own test (`test_builder_withdrawal_insufficient_balance_realistic_bounds`) constructs exactly this scenario — a `builder_pending_withdrawals` entry requesting more than the builder's balance — and asserts the capped-balance/uncapped-committed-amount behavior as expected, confirming this is a real, currently-specified code path and not a purely theoretical edge case. [6](#0-5) 

### Recommendation
Cap the amount used when constructing the `Withdrawal` in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)`, mirroring the capping already done in `apply_withdrawals`, so the committed `payload_expected_withdrawals` amount and the actual CL balance debit are always equal — preserving the supply invariant between CL and EL.

### Proof of Concept
1. Create a builder with `balance = B`.
2. Enqueue a `BuilderPendingWithdrawal(builder_index=i, amount=A, fee_recipient=addr)` with `A > B` (reachable e.g. if the builder's balance is reduced by another withdrawal/exit path between when the pending withdrawal amount was fixed and when it is processed).
3. Call `get_expected_withdrawals(state)` → returns `Withdrawal(amount=A, ...)` unchanged from the queued amount (specs/gloas/beacon-chain.md:1822-1829).
4. This is committed into `state.payload_expected_withdrawals` (specs/gloas/beacon-chain.md:2003-2011), which the execution layer must honor by minting `A` to `fee_recipient`.
5. `apply_withdrawals` then only debits `min(A, B) = B` from `builder.balance`, leaving `A - B` Gwei minted on the EL with no corresponding CL-side debit. [7](#0-6)

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
