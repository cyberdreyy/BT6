### Title
Underfunded instant-withdraw bucket pays first claimants at par, draining other claimants' funded share - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a heap buffer over-write: a request writes past its own boundary into adjacent allocations. The vault analog is `claimInstantWithdrawRequest`: an instant-withdraw receipt always pays the caller's full requested amount from the strategy's shared underlying balance, with no per-receipt funded/underfunded tracking. When the instant-withdraw queue is only partially funded — a state the code itself acknowledges and handles at default finalization — the first claimant consumes the funding belonging to all other instant claimants, exactly like a write that spills into neighboring claimants' buffers.

### Finding Description
`requestInstantWithdraw` records `instantWithdrawsRequests[_user]` and bumps `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). `collectInstantWithdrawFunds` later decrements `pendingInstantWithdraws` by whatever amount the CDO actually transferred in (IdleCreditVault.sol:398-403). There is no check that the collected amount covers all instant requests: the code explicitly models a partially funded instant queue in `_defaultPrefundedInstantReserve`, where `instantBasis > pendingInstant` means part of the instant claims are already backed by strategy-held underlyings (IdleCreditVault.sol:716-723), and the comment on `defaultPendingClaimBasis` states this happens when "startEpoch moved the CDO's available cash to the strategy but that cash covered only part of the instant queue" (IdleCreditVault.sol:637-648).

`claimInstantWithdrawRequest` ignores all of this: it pays `instantWithdrawsRequests[_user]` in full via `_transferFundedClaim` (IdleCreditVault.sol:380-393), and `_transferFundedClaim` only protects `defaultRecoveryReserve` — which is zero until `finalizeDefaultRecovery` runs (IdleCreditVault.sol:897-907). So during the window between partial instant funding and default finalization, any instant withdrawer can claim 100% of their receipt at par, spending the pooled funding that should have been shared pro-rata. The protocol's own design confirms pro-rata is the intent: `_claimDefaultedInstantWithdrawRequest` pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL`, i.e., a haircut, for unfunded instant receipts (IdleCreditVault.sol:842-856) — but only for whatever basis remains after early claimants have already drained it at par.

### Impact Explanation
Direct theft with a quantified loss. If the instant queue has total basis B and the strategy holds only F < B in instant funding, the first claimant(s) can extract up to their full `instantWithdrawsRequests` amount while later claimants either revert on insufficient balance or receive a recovery price computed on a reserve the early claimant already depleted. The stolen amount is `claimedAmount - claimBasis * F / B` per early claimant, taken directly from other instant withdraw requesters and from the eventual default recovery reserve. Since `_transferDefaultRecovery` decrements `defaultRecoveryReserve` (IdleCreditVault.sol:912-917) for post-finalization claims, the loss is permanently socialized onto remaining claimants and active tranche holders.

### Likelihood Explanation
The attacker only needs to be a tranche holder who calls `requestInstantWithdraw` and then `claimInstantWithdrawRequest` first via the public CDO path — both unprivileged, KYC-gated user actions. The enabling condition (partial instant funding) is reached through honest borrower/manager sequences: a stop or epoch roll where the CDO's available cash covers only part of the instant queue, or the run-up to a borrower default, which the contract explicitly anticipates. No privileged misbehavior is required; the borrower defaulting is an ordinary protocol event, not attacker control.

### Recommendation
Track funded vs unfunded instant-withdraw basis per user or per epoch. Either (a) gate `claimInstantWithdrawRequest` so a receipt can only claim once its epoch's instant funding is complete (e.g., `pendingInstantWithdraws` no longer covers that epoch's claims, or store an `instantFundedAmountByEpoch` and pay pro-rata `claimBasis * funded / instantWithdrawClaimsByEpoch[epoch]`), or (b) route all underfunded instant receipts through the same recovery-price mechanism used post-default so no claimant can take par while the bucket is short. At minimum, `_transferFundedClaim` should exclude `pendingInstantWithdraws`-backed underlyings the way it excludes `defaultRecoveryReserve`.

### Proof of Concept
Foundry fork scenario (sketch):

```solidity
// Epoch N running; two users hold AA tranche receipts.
// 1. userA and userB each call cdoEpoch.requestInstantWithdraw(amount, AAtranche)
//    => instantWithdrawsRequests[A] = instantWithdrawsRequests[B] = X
//    => pendingInstantWithdraws = 2X, instantWithdrawClaimsByEpoch[N] = 2X
// 2. Honest sequence: manager calls cdoEpoch.stopEpoch/startEpoch; the CDO only
//    has X of cash available, so it calls
//    strategy.collectInstantWithdrawFunds(X)  // funds only half the queue
//    => pendingInstantWithdraws = X; vault balance for instant claims = X
// 3. Attacker (userA, unprivileged) immediately calls
//    cdoEpoch.claimInstantWithdrawRequest()
//    => _burn(A, X); _transferFundedClaim(A, X) pays A the FULL X at par,
//       draining the entire instant funding pool.
// 4. Borrower defaults; manager finalizes via finalizeDefaultRecovery.
//    userB's receipt (basis X) is haircut by defaultRecoveryPrice on a
//    reserve that no longer contains the X userA already took.
// 5. assert userB payout < X * F/(2X); assert userA payout == X (overpaid).
```

The broken invariant is "one receipt, one fair payout": `claimInstantWithdrawRequest` performs a write/payment that overruns the funded boundary of the instant-claim buffer, corrupting (consuming) adjacent claimants' allocations, in direct analogy to the heap buffer over-write where data written past a buffer boundary destroys neighboring allocations.
