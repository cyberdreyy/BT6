### Title
Late acceptance from a pre-commit-less peer can permanently skip the signature-threshold re-check, wedging a fully-signed block from ever being pushed - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`store_and_process_block_signature` stores every incoming `BlockResponse::Accepted` signature to `SignerDb`, but only *tallies* the accumulated signature weight against the group threshold when the message does **not** come from a peer that skipped the pre-commit step. If it does, the function unconditionally redirects to `handle_block_pre_commit` and returns before the tally runs. When the receiving signer has already signed the block itself, `handle_block_pre_commit` no-ops on that redirect, so the newly-stored signature is never checked against the threshold by anyone that already self-signed — mirroring the reported bug class where a balance-affecting event (a new deposit / here, a late signature) is folded into an accounting step that silently absorbs it without re-triggering the equality check that should follow.

### Finding Description
`store_and_process_block_signature` in `stacks-signer/src/v0/signer.rs` (lines 2442-2538) does the following on every `Accepted` `BlockResponse`:

1. It writes the signature to `SignerDb` via `add_block_signature` [1](#0-0) .
2. If the sender never sent a pre-commit for this block, it treats the acceptance as an implicit pre-commit and returns immediately, *before* computing `total_signature_weight` or comparing it to `min_weight`: [2](#0-1) .
3. Only if the sender had already pre-committed does the function proceed to recompute `total_signature_weight` from every signature in the DB and compare it to `min_weight`, broadcasting the block once the threshold is crossed: [3](#0-2) .

The redirect target, `handle_block_pre_commit`, exists to let this signer decide whether *it* should sign, based on the pre-commit weight of `get_block_pre_committers`. But if this signer has already signed (`block_info.signed_self.is_some()`), it does nothing at all and returns: [4](#0-3) .

So the sequence "signature persisted to DB, but the acceptance-weight vs. threshold comparison is skipped" happens whenever:
- the sender of the `Accepted` response never pre-committed (a legitimate, documented case for mixed-version fleets — see `docs/signer-flows.md` section 6: "an acceptance from a peer that never sent a pre-commit is routed into the pre-commit path instead" [5](#0-4) ), and
- the receiving signer has already signed the block itself.

If this straggler's weight is exactly what was missing to cross `min_weight`, no code path re-runs the comparison for any signer who has already self-signed. Every already-signed signer treats the message as a no-op after persisting it, so `broadcast_signed_block`/`handle_post_block` is never invoked by them for this block. A not-yet-signed signer that later reaches its own pre-commit threshold would sign and correctly re-tally (because signing itself invokes `store_and_process_block_signature` for its own signature, which is not from a pre-commit-less sender), but if every signer has already self-signed by the time the straggler's late acceptance lands — plausible given per-signer asynchronous StackerDB polling and no synchronized message ordering — the recheck is dropped by all of them simultaneously.

This breaks the equality the design intends to hold: "signature persisted ⇔ signature counted toward the push threshold." Just like the reported vault bug counted a fresh deposit into a reward-accrual step that should have excluded it, here a late, ordering-dependent message is absorbed into a control-flow branch (`handle_block_pre_commit`) that silently discards the accounting step that normally follows a stored signature.

### Impact Explanation
This is a liveness wedge on block finalization: a block that has, in aggregate, actually reached the ≥70% signature-weight threshold can end up with no signer ever performing the check that would trigger `broadcast_signed_block`/push to the node, stalling that specific block indefinitely absent some external trigger (e.g. a fresh proposal or timeout-driven retry) to force a re-evaluation. This falls under the "signer wedged" / liveness-wedge impact class, since the state machine equality "stored signature weight ≥ threshold ⇒ push happens" is broken.

### Likelihood Explanation
No majority coordination, malicious key, or `auth_token`/local access is required — only ordinary network conditions: one peer whose acceptance arrives after it never broadcast (or was never observed to broadcast) a pre-commit, combined with normal asynchronous propagation causing every currently-informed signer to have already self-signed by the time that acceptance lands. The code comment and docs explicitly acknowledge this "outdated peer" path exists for mixed-version fleets, confirming it is a reachable, non-theoretical branch, not an edge case requiring adversarial control.

### Recommendation
In `store_and_process_block_signature`, do not unconditionally `return` after redirecting a pre-commit-less acceptance to `handle_block_pre_commit`. Instead, after persisting the signature, always recompute `total_signature_weight` from the DB and compare against `min_weight` regardless of whether the sender had previously pre-committed, so a late straggler's stored signature is guaranteed to be re-tallied by every signer that receives it — even ones that have already self-signed and thus get a no-op from `handle_block_pre_commit`.

### Proof of Concept
1. Signer set of weight-threshold `min_weight`, where `total_weight - w_L == min_weight` (i.e., signer `L` holds exactly the marginal weight needed to cross the threshold).
2. All signers except `L` pre-commit and, upon reaching their local pre-commit threshold (using pre-commit weight, which can cross threshold before all signature broadcasts have propagated), sign and call `store_and_process_block_signature` for their own signature — each of these signers ends up with `signed_self.is_some() == true`, while the network-wide *signature* weight is still below `min_weight` because `L`'s signature has not arrived yet.
3. `L` runs an outdated/slow client that skips the pre-commit broadcast and sends only `BlockResponse::Accepted` directly, arriving late.
4. Each already-signed signer processes `L`'s acceptance in `store_and_process_block_signature`: the signature is stored via `add_block_signature` [1](#0-0) , then routed to `handle_block_pre_commit` [2](#0-1) , which no-ops because `signed_self.is_some()` [4](#0-3) .
5. No signer ever re-executes the `total_signature_weight >= min_weight` comparison at lines 2503-2537 for this event, so `broadcast_signed_block` is never called by anyone, even though the DB now holds signatures summing to ≥ `min_weight`. The block is wedged.
