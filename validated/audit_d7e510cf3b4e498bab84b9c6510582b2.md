### Title
Late-arriving signatures still broadcast an already `GloballyRejected` block because a failed `mark_locally_accepted` is silently swallowed - ([File: stacks-signer/src/v0/signer.rs])

### Summary
This is an analog of the reported liquidity bug's "the liquidity provider can take ALL the funds after the lock, not just their own" pattern: a guard exists to stop an action once a terminal/expired state has been reached, but the code path after the guard executes the action anyway. In `store_and_process_block_signature`, once a block has already reached the `GloballyRejected` state (≥30% weight rejected, the network's rejection consensus), a late-arriving batch of acceptance signatures that crosses the 70% threshold still causes the signer to call `broadcast_signed_block`, even though `mark_locally_accepted` failed because the state machine blocks the `GloballyRejected → LocallyAccepted` transition.

### Finding Description
`store_and_process_block_signature` tallies acceptance signatures and, once ≥70% weight is reached, is supposed to transition the block to `LocallyAccepted` and then push it to the node: [1](#0-0) 

The guard `if !block_info.has_reached_consensus() { warn!(...) }` is written so that a failure to `mark_locally_accepted` is only logged when consensus hasn't already been reached - implying the intent was "if consensus was already reached (e.g. `GloballyRejected`), do nothing further." However, there is no early `return` in either branch: execution falls through unconditionally to `self.signer_db.insert_block(block_info)` and `self.broadcast_signed_block(...)`, regardless of whether the state transition to `LocallyAccepted` actually succeeded.

Per the documented state machine, `PreCommitted`/local states are reachable "from anything not yet global," and each global state (`GloballyAccepted`, `GloballyRejected`) is terminal/unreachable from the other: [2](#0-1) 

So once this signer has already recorded the block as `GloballyRejected` (via `add_block_rejection_signer_addr`/`mark_globally_rejected` reaching the ≥30% rejection threshold, in `handle_block_rejection`): [3](#0-2) 

any subsequent flow of ≥70%-weight acceptance signatures for that same block (e.g. late/stale acceptances from signers who validated the block as OK before observing the rejection majority, or acceptances reinterpreted from the "treat foreign signature as pre-commit" compatibility fallback) will still hit the code at lines 2525-2538, silently fail to move the `BlockInfo` to `LocallyAccepted`, but proceed to gather all stored signatures and call `broadcast_signed_block` anyway.

The "treat as pre-commit" fallback that can feed this path is itself worth noting as the delivery mechanism: any signature received from a peer for a tracked block is first checked only against `has_committed`, not against whether the block has already reached a terminal rejected state: [4](#0-3) 

### Impact Explanation
This breaks the "rejection recounted as an accept" invariant explicitly called out as a Critical class in scope: a block the signer set has already declared dead via `GloballyRejected` (over 30% weight rejection, the guard meant to make 70% acceptance impossible) can still be pushed to the stacks-node as an accepted/signed block once a stale batch of acceptances arrives, because the failure of the state transition is swallowed instead of aborting the broadcast. This can cause a signer to push a block the network has already rejected, contradicting the coordinator's/peer's view of consensus and risking a fork/miner-invalidation mismatch, since the miner-invalid marking logic (`ReorgNotAllowed` handling) already ran on the assumption the block was dead.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires timing where a signer receives its own or peers' `GloballyRejected`-triggering rejections before it has received all outstanding acceptances for the same block, plus enough surviving/replayed acceptance weight (≥70%) to still cross the threshold afterward - a scenario made easier by the "treat signature as pre-commit" outdated-peer fallback and by the fact that pre-commits/acceptances are still counted and replayed even after local state changes (`process_pending_responses_for_block`, `drain_pending_block_responses`). No majority-signer collusion or key compromise is required; this is triggerable by ordinary message-timing/network conditions (or a byzantine minority delaying its rejection broadcast) combined with a miner or gossip-timed re-proposal/resend.

### Recommendation
In `store_and_process_block_signature`, return immediately (without calling `insert_block`/`broadcast_signed_block`) whenever `mark_locally_accepted` fails, regardless of the `has_reached_consensus()` value, e.g.:
```rust
if let Err(e) = block_info.mark_locally_accepted(true) {
    warn!("{self}: Failed to mark block as locally accepted: {e:?}");
    return;
}
```
This restores the intended invariant that a block already resolved to a terminal state (`GloballyRejected`/`GloballyAccepted`) can never be re-broadcast under a different verdict.

### Proof of Concept
1. Miner proposes block `B`. Signers S1..S10 (equal weight) validate it as OK and are ready to sign.
2. Due to network delay, S1-S4 (40% weight) broadcast rejections (e.g., `ReorgNotAllowed` or a transient `SortitionViewMismatch`) that reach the local signer under test first; once ≥30% rejection weight is recorded, `handle_block_rejection` calls `mark_globally_rejected` on the local `BlockInfo` for `B` (`stacks-signer/src/v0/signer.rs:2335`).
3. Shortly after, the delayed acceptance signatures/signatures-treated-as-pre-commits from S5-S10 (60%) plus the local signer's earlier local acceptance arrive and are stored via `add_block_signature`/`store_and_process_block_signature`, pushing `total_signature_weight` to ≥70%.
4. `mark_locally_accepted(true)` is invoked on the already-`GloballyRejected` `BlockInfo`, fails per the state machine's terminal-global-state rule, but the `if let Err(e) = ...` branch only logs a warning (suppressed here since `has_reached_consensus()` is true) and does not return.
5. `insert_block` and `broadcast_signed_block` execute unconditionally, pushing the previously `GloballyRejected` block `B` to the stacks-node as though it had reached signer consensus.
