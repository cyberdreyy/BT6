### Title
Unauthenticated `create()` lets anyone deploy a victim's lockup with attacker-chosen `lockup_duration`, `release_duration`, `vesting_schedule` and `whitelist_account_id` - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` is a public, `#[payable]` method callable by any account that attaches `MIN_ATTACHED_BALANCE`, and it derives the lockup's account id deterministically from `owner_account_id` alone: `sha256(owner_account_id)[..20] + "." + factory`. Because there is no check that the caller is the NEAR Foundation, a grantor, or `owner_account_id` itself, and no per-owner nonce/salt in the derivation, an attacker can call `create()` first for a chosen victim `owner_account_id` and supply arbitrary `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`, permanently squatting that deterministic address with terms the rightful grantor never authorized.

### Finding Description
The broken binding: `lockup_account_terms(owner_account_id) == grantor_intended_terms(owner_account_id)` should always hold, i.e. the schedule fields deployed for a given beneficiary must equal the schedule the grantor (NEAR Foundation) actually chose. Instead, `create()` accepts these fields verbatim from `env::predecessor_account_id()`, which can be anyone: [1](#0-0) 

- `owner_account_id`, `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, `whitelist_account_id` are all attacker-controlled call arguments.
- The only gate is `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` — a purely monetary check that any unprivileged account can satisfy.
- The target contract account id is computed purely as a function of `owner_account_id`: `format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id())`, with `byte_slice = sha256(owner_account_id)`. There is no dependency on caller identity, nonce, or any grantor-issued authorization token.

Because NEAR account creation is a one-time, first-come event (`Promise::new(lockup_account_id).create_account()` fails if the account already exists), whoever calls `create()` first for a given `owner_account_id` permanently determines the lockup contract deployed at that address, including:
- `vesting_schedule`: attacker may pass `VestingScheduleOrHash::VestingSchedule(...)` directly (not only the hashed variant), fully attacker-chosen start/cliff/end timestamps.
- `release_duration` / `lockup_duration` / `lockup_timestamp`: fully attacker-chosen release schedule.
- `whitelist_account_id`: if omitted defaults to the factory's configured whitelist, but the attacker may instead supply their own deployed contract id here, which the lockup contract will subsequently trust as the staking-pool whitelist oracle: [2](#0-1) 

The rollback path only refunds a *failed* creation to the caller who paid for it; it performs no validation that the parameters matched anything the true grantor intended: [3](#0-2) 

Exploit flow: the attacker observes (or predicts) that `owner_account_id = victim.near` is slated to receive a grant lockup. Before the Foundation calls `create()`, the attacker calls `create(victim.near, malicious_duration, malicious_timestamp, malicious_vesting_schedule, malicious_release_duration, Some(attacker_whitelist.near))` with the minimum `3.5 NEAR` deposit. This deploys and initializes the lockup contract at the deterministic address `sha256("victim.near")[..20].factory`, with the attacker's chosen release schedule and an attacker-deployed whitelist contract that will approve any staking pool (including one the attacker controls). When the Foundation later attempts the legitimate `create()` call for `victim.near` with the real grant amount, the `create_account()` sub-action fails (account already exists), the whole promise batch fails, and `on_lockup_create` simply refunds the Foundation's deposit — no error surfaces indicating *why* creation failed unless it is specifically checked. If the Foundation (or anyone relying on the precomputed address) subsequently transfers real grant funds to that address believing it to be the correctly parameterized lockup, or if `victim.near` (the legitimate owner, who does control that account name) later selects a staking pool, the lockup's staking-pool check consults the attacker's `whitelist_account_id` — which the protocol treats as trusted — potentially approving an attacker-controlled staking pool as a valid destination.

None of the existing guards prevent this: `assert_self()` only protects the callback from external callers, `is_promise_success()` only detects promise failure, and there is no `assert_owner`/`assert_called_by_foundation` guard on `create()` at all.

### Impact Explanation
This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker permanently claims the deterministic contract address intended for a specific beneficiary and dictates its `release_duration`, `lockup_duration`, `vesting_schedule`, and trusted `whitelist_account_id`. Concretely: real grant funds could later be steered toward, or a legitimate owner's staking flow could be tricked into trusting, an attacker-controlled whitelist/pool contract, and legitimate grant creation for that beneficiary is permanently blocked at that address. The attack is repeatable across every distinct `owner_account_id` the attacker wishes to squat, at a cost of `3.5 NEAR` per attempt (refundable only if their own creation fails, not recoverable once it succeeds since the account now exists with attacker's chosen terms).

### Likelihood Explanation
No privileged role is required — any account able to send a transaction with `≥3.5 NEAR` attached can call `create()`. The attacker only needs to know or predict the `owner_account_id` string of an intended grant recipient (typically public/known ahead of the grant, e.g. a named investor/employee account) and race the Foundation's transaction. This is inexpensive, fully automatable, and works against any future or currently-unclaimed lockup address, making it a low-cost, high-feasibility, repeatable attack.

### Recommendation
Restrict `create()` to a trusted caller (e.g. `assert_eq!(env::predecessor_account_id(), self.foundation_account_id)` or an owner-signed allowlist), or incorporate an authorization mechanism (e.g., only the `owner_account_id` itself, or a Foundation-issued signed grant ticket) before allowing lockup deployment for a given beneficiary, so that schedule fields provably originate from the grantor rather than an arbitrary caller. Additionally, consider making the derived lockup account id depend on a Foundation-issued nonce/salt rather than solely on `owner_account_id`, removing the ability to squat future beneficiary addresses.

### Proof of Concept
```rust
// lockup-factory/src/tests (conceptual addition, cargo test)
#[test]
fn test_attacker_can_squat_victim_lockup_with_malicious_terms() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker (not the Foundation, not the owner) calls create() naming the victim
    // as owner_account_id, with attacker-chosen malicious schedule and whitelist.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near"); // unprivileged
    context.attached_deposit = ntoy(4); // just above MIN_ATTACHED_BALANCE
    testing_env!(context.clone());

    let malicious_release_duration: WrappedDuration = 1u64.into(); // near-instant release
    let malicious_whitelist = ValidAccountId::try_from("attacker-whitelist.near").unwrap();

    contract.create(
        account_tokens_owner(), // == victim.near, chosen by attacker not by grantor
        63036000000000000u64.into(),
        None,
        None,
        Some(malicious_release_duration),
        Some(malicious_whitelist),
    );

    // Simulate successful account creation (attacker wins the race).
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(lockup_account(), ntoy(4).into(), String::from("attacker.near"));

    // Assert: the deterministic address for account_tokens_owner() is now permanently
    // deployed with attacker-chosen release_duration / whitelist_account_id, not the
    // Foundation's intended terms. A subsequent legitimate create() call for the same
    // owner_account_id must now fail (account already exists), proving the grantor's
    // real terms can never be applied to that address:
    //
    //   assert_ne!(deployed_release_duration, intended_release_duration);
    //   assert_ne!(deployed_whitelist_account_id, foundation_whitelist_account_id);
}
```
This demonstrates, within the existing test harness (`testing_env!`/`PromiseResult`), that `create()` allows an unprivileged predecessor to permanently fix the schedule and whitelist for a victim's deterministic lockup address, violating the binding that these fields must originate from the grantor.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
