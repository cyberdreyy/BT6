### Title
Loss-adjusted withdraw receipts keyed under the wrong epoch index let users claim unhaircutted funds — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.requestWithdraw` tags each receipt with the request-time `epochNumber` via `lastWithdrawRequest[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` (`IdleCreditVault.sol:260-293`). The loss haircut, however, is stored under `lossRecoveryPriceByEpoch[epochNumber]` inside `collectWithdrawFunds` (`IdleCreditVault.sol:421`), which runs during `stopEpochWithDuration` — after `deposit()` has already incremented `epochNumber` (`IdleCreditVault.sol:607-611`, which bumps `epochNumber += 1` when `isEpochRunning()` is still true, i.e. mid-stopEpoch). The two code paths therefore index the same receipt with different epoch keys: write under `N+1`, read under `N`.

### Finding Description
The Kerberos CVE bug class — a case-type index resolved to the wrong slot, producing a null/empty lookup where a real entry exists — maps directly onto this epoch-indexed recovery ledger:

- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` at request time (`IdleCreditVault.sol:260,282`) and adds basis to `withdrawsRequestsByEpoch[_user][currentEpoch]` (`IdleCreditVault.sol:293`).
- At epoch end, the strategy's `deposit()` increments `epochNumber` while the epoch is still flagged running (`IdleCreditVault.sol:607-611`). `collectWithdrawFunds` then stores the haircut as `lossRecoveryPriceByEpoch[epochNumber]` (`IdleCreditVault.sol:421`) — i.e. under the *post-increment* epoch `N+1`, while every affected receipt is tagged `N`.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns early (`IdleCreditVault.sol:789-792`).
- The receipt then falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` at par (`IdleCreditVault.sol:319-330`). The strategy only collected `pendingToFund < pendingBasis` from the borrower, so the full par payout drains funds belonging to other receipt holders / reserve.
- The same mis-indexed read disables the safety guard in `requestWithdraw` (`IdleCreditVault.sol:261-271`): it checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]` = index `N` = 0, so an unclaimed loss receipt does not block a follow-up request either.

I could not fully confirm the call ordering inside `IdleCDOEpochVariant.stopEpochWithDuration` (whether the `epochNumber`-bumping `deposit` precedes `collectWithdrawFunds`) — the index search returned match counts only for that file. If `collectWithdrawFunds` runs before the increment, the keys line up and the bug collapses; the code comments ("buffer + epochDuration is 1 epoch", `IdleCreditVault.sol:281`) and the increment-in-`deposit` design strongly suggest it runs after.

### Impact Explanation
Direct insolvency/theft: every holder of a loss-adjusted receipt claims 100% of basis while the strategy holds only `pendingBasis * lossRecoveryPrice`. The first claimers are made whole at the expense of later claimers and the default-recovery reserve, breaking the loss-socialization invariant that `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` are designed to enforce. Quantified: attacker-held receipt × (1 − lossRecoveryPrice), bounded only by their share of `pendingWithdraws`.

### Likelihood Explanation
Requires an epoch ending via `stopEpochWithDuration` with `_lossAmount > 0` while pending withdraws exist — a normal, honest-manager code path, no privileged misbehavior needed. Any unprivileged tranche holder who filed a withdraw request that epoch is an affected claimant. The only precondition that needs on-chain verification is the stopEpoch call ordering noted above.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the same epoch marker used for receipts: capture `epochNumber` before the mid-stopEpoch increment, or store receipts under `epochNumber + 1` (the epoch at which they become claimable, matching `claimEpoch = strategy.epochNumber() + 1` semantics in the queue tests). Alternatively, make `_claimLossAdjustedWithdrawRequest` iterate/verify the receipt's actual `withdrawsRequestsByEpoch` key rather than trusting `lastWithdrawRequest`. Add a regression test asserting a loss-adjusted receipt claims exactly `basis * lossRecoveryPrice`.

### Proof of Concept
Foundry fork PoC sketch:
1. Deposit as `victim` and `attacker`; `requestWithdraw` both tranches during epoch N (`strategy.epochNumber() == N`, `lastWithdrawRequest == N`).
2. `vm.prank(manager) cdoEpoch.startEpoch()`; warp past `epochEndDate`.
3. Borrower funds `expectedEpochInterest + pendingToFund` where `pendingToFund` comes from `previewLossAdjustedWithdrawFunds(lossAmount)` with `lossAmount > 0`.
4. `cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount)` — inside, `deposit()` bumps `epochNumber` to N+1, `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[N+1]`.
5. Assert `strategy.lossRecoveryPriceByEpoch(N) == 0` and `lossRecoveryPriceByEpoch(N+1) < 1e18`.
6. `attacker` calls `claimWithdrawRequest` via CDO: `_claimLossAdjustedWithdrawRequest` returns 0, `_claimFundedWithdrawRequest` pays full `withdrawsRequests[attacker]`. Assert attacker received `basis` instead of `basis * lossRecoveryPrice`, and strategy underlying is short by the haircut total.

Confidence caveat: the exact sequencing inside `stopEpochWithDuration` was not readable in this index; if `collectWithdrawFunds` executes before the `epochNumber` increment, the keys align and this is not exploitable — that ordering must be verified first.
