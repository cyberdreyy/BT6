### Title
Missing `reject_reason` update in `handle_block_validate_ok`'s DB-state-recheck rejection path permanently wedges a signer against re-validating a still-valid block - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
When a block passes `/v3/block_proposal` validation but fails the signer's own re-check (`check_block_against_signer_db_state`), `handle_block_validate_ok` marks the block `LocallyRejected` via `mark_locally_rejected()` but never sets `block_info.reject_reason`. The sibling function `handle_block_validate_reject` does set `reject_reason` on the same kind of transition. This is the same class of bug as the referenced report: one state-mutating path updates the primary flag (here, `valid`/`state`) but forgets to update a companion field (`reject_reason`) that other logic relies on to decide future behavior, so the two pieces of state fall out of sync.

### Finding Description
`BlockInfo::mark_locally_rejected` only sets `self.valid = Some(false)` and moves `state` to `LocallyRejected`; it does not touch `reject_reason` (`stacks-signer/src/signerdb.rs:297-301`). Callers are expected to set `reject_reason` themselves, and `handle_block_validate_reject` does so at `stacks-signer/src/v0/signer.rs:2045` right after calling `mark_locally_rejected()`.

However, in `handle_block_validate_ok`, when `check_block_against_signer_db_state` finds that the signer's local DB state has since changed and returns a `block_rejection` (e.g. `RejectReason::ConnectivityIssues(..)` from `check_block_against_signer_db_state`, `stacks-signer/src/v0/signer.rs:1832-1837` and `1872-1877`, or `RejectReason::SortitionViewMismatch`), the code does:

```rust
if let Some(block_rejection) =
    self.check_block_against_signer_db_state(stacks_client, &block_info.block)
{
    if let Err(e) = block_info.mark_locally_rejected() { ... }
    self.signer_db.insert_block(&block_info)...;
    self.handle_block_rejection(&block_rejection, sortition_state);
    self.send_block_response(&block_info.block, block_rejection.into());
}
```
(`stacks-signer/src/v0/signer.rs:1946-1959`)

`block_info.reject_reason` is never assigned here, so it stays `None` (the default from `BlockInfo::from(BlockProposal)`, `stacks-signer/src/signerdb.rs:239`), even though the concrete `block_rejection` computed just above carries a real `RejectReason`.

This `reject_reason` field is the sole input to `should_reevaluate_reject_reason` (`stacks-signer/src/v0/signer.rs:2706-2739`), which drives `should_reevaluate_block` (`stacks-signer/src/v0/signer.rs:1483-1572`) on every re-proposal of the same block hash:
- If `reject_reason` is `Some(RejectReason::ConnectivityIssues(_))` (a transient-failure reason explicitly whitelisted as re-evaluable, `signer.rs:2712`), the signer performs a fresh `FRESH` evaluation of the re-proposed block, per `docs/signer-flows.md:180-186` (`REASON -- yes --> FRESH`).
- If `reject_reason` is `None` (our bug), `should_reevaluate_reject_reason` falls into the `else` branch and returns `false` (`signer.rs:2736-2738`), so `should_reevaluate_block` treats the rejection as terminal, skips `FRESH` re-validation, and simply calls `determine_response`, which resends a cached `RejectReason::RejectedInPriorRound` rejection forever (`signer.rs:462-471`, `1530-1532`).

So a transient condition (temporary stacks-node connectivity blip, or a stale sortition/tenure view at the moment `check_block_against_signer_db_state` was run) permanently converts what should have been a retriable rejection into a terminal one for that specific block hash on that signer, because the field that "remembers" the reason is silently dropped.

### Impact Explanation
This is a High-severity liveness defect: it wedges an individual signer into never (re-)signing a specific still-valid block, matching the explicitly in-scope High-impact category "a signer wedged into never signing valid blocks." The affected signer will keep re-sending a generic `RejectedInPriorRound` rejection for that block hash even after the underlying transient condition (e.g. node connectivity, stale local sortition/tenure view) that caused `check_block_against_signer_db_state` to reject it has cleared, because `should_reevaluate_reject_reason` can never see the real, re-evaluable reason again. If a miner keeps re-proposing the exact same block (same `signer_signature_hash`, which regular miner retry loops commonly do when a block isn't signed in time), this signer's weight is durably lost for that block, which contributes to reducing the effective signing weight available toward the 70% signature threshold, and, combined with other signers experiencing the same or different transient failures, reduces the safety margin against a >30% rejection bloc making the block globally rejected via `store_and_process_block_rejection` (`stacks-signer/src/v0/signer.rs:2267-2341`).

### Likelihood Explanation
This requires no signer collusion, no majority, and no private key/auth token access — it is triggered purely by ordinary node-side transient conditions (a connectivity error or a momentarily-stale local view at the exact moment `check_block_against_signer_db_state` runs during `handle_block_validate_ok`) that any single signer can hit independently during normal operation, combined with a miner that re-proposes the same block content (a common, unremarkable retry pattern). No special miner malice is needed, only a normal repeated proposal of the same block.

### Recommendation
In the rejection branch of `handle_block_validate_ok` (`stacks-signer/src/v0/signer.rs:1946-1959`), set `block_info.reject_reason` from the computed `block_rejection` before inserting the block, mirroring what `handle_block_validate_reject` already does at `stacks-signer/src/v0/signer.rs:2045`:
```rust
block_info.reject_reason = Some(block_rejection.response_data.reject_reason.clone());
```
so that `should_reevaluate_reject_reason` always evaluates the real reason and re-evaluable rejections (e.g. `ConnectivityIssues`) are retried once conditions change.

### Proof of Concept
1. A signer receives a `BlockProposal` and submits it for validation; the stacks-node returns `Ok` (`BlockValidateOk`), routed to `handle_block_validate_ok`.
2. `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs:1803-1880`) hits a transient error (e.g. `get_tenure_tip`/`get_peer_info` RPC failure) and returns `Some(block_rejection)` with `RejectReason::ConnectivityIssues(..)`.
3. `handle_block_validate_ok` calls `block_info.mark_locally_rejected()` (state -> `LocallyRejected`, `valid = Some(false)`) but never sets `block_info.reject_reason`; the block is persisted with `reject_reason = None` (`signer.rs:1946-1959`).
4. The connectivity issue resolves. The miner re-proposes the identical block (same `signer_signature_hash`).
5. `handle_block_proposal` -> `should_reevaluate_block` -> `should_reevaluate_reject_reason(block_info)` reads `reject_reason == None`, returns `false` (`signer.rs:2706-2739`).
6. Since `state != PreCommitted`, `should_reevaluate_block` calls `determine_response(block_info)`, which — because `valid == Some(false)` — returns `create_block_rejection(RejectReason::RejectedInPriorRound, ..)` and resends it, permanently, without ever re-running `check_block_against_signer_db_state` (`signer.rs:458-471`, `1530-1532`). The signer never signs this block again, regardless of how many times it is re-proposed. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
