## Finding: Silent, unretried block-validation submission failure can permanently strand a proposal, wedging a signer out of ever voting on it

### Title
Non-transient `submit_block_for_validation` errors are silently dropped with no retry, permanently stranding a block proposal in an undecided state — ([File: stacks-signer/src/v0/signer.rs])

### Summary
The external report's bug class is: an external call in a token-bridge callback is not wrapped in error handling, so any failure of that call (even non-fatal, transient-looking ones) permanently freezes funds because nothing re-drives the operation. The reachable analog in this signer is `Signer::submit_block_for_validation`, which asks the stacks-node (an external dependency, analogous to the bridge's downstream `deposit()` call) to validate a proposed block. When that call fails with anything other than a `429 Too Many Requests`, the signer only logs a warning and takes no further action — it neither retries, nor re-queues the block for a later attempt, nor rejects it.

### Finding Description
`submit_block_for_validation` handles exactly two outcomes explicitly and treats everything else as a dead end: [1](#0-0) 

- `Ok(_)` → tracks the submission via `submitted_block_proposal` so a later `BlockValidationResponse` (or a timeout in `check_submitted_block_proposal`) can progress it.
- `Err(ClientError::RequestFailure(429))` → re-inserted into the pending-validation table via `insert_pending_block_validation`, so `check_pending_block_validations` will retry it later.
- **Any other `Err(e)`** (connection refused, timeout, 5xx, TLS error, etc.) → only `warn!(...)`. `submitted_block_proposal` stays `None`, and the block is **not** re-inserted into the pending table.

The call site in `handle_block_proposal` stores the block (`insert_block`) with `valid = None` regardless of the submission outcome: [2](#0-1) 

Because the block is already present in `SignerDb` under this exact `signer_signature_hash`, `handle_block_proposal`'s dedupe path — `should_reevaluate_block` — governs whether a later resend of the same proposal is ever re-driven through validation again, rather than being answered from cached state. If the miner does not resend the identical proposal (Stacks miners generally do not re-broadcast an unchanged, already-accepted proposal), no other code path calls `submit_block_for_validation` for that hash again: `check_pending_block_validations` only drains entries actually present in the pending table, and this failure path never puts one there.

The result: the block sits forever with `valid == None`, `state == Unprocessed`. This signer never produces a rejection or an acceptance for it — it simply stops participating on that specific block, indistinguishable (from the rest of the signer set's perspective) from an offline signer for that vote.

### Impact Explanation
This is a liveness wedge for a single block, not a majority-signer requirement: it is triggered by a plain, one-off networking failure between the signer and its own stacks-node (a condition any signer operator's environment can hit — proxy hiccup, node restart mid-request, transient DNS failure, etc.), with no attacker action needed. If enough signers experience this independently on the same proposal (or if it recurs across every proposal from a struggling node), the affected signer(s) contribute neither accept nor reject weight for that block, which can slow or, if it compounds with borderline weight distributions, block the network from reaching the 70% signing threshold — a liveness degradation matching "a signer wedged into never signing valid blocks" per the rubric's High-impact category. It does not by itself cause an invalid/non-canonical signature or a miscount, so it is bounded to the High tier, not Critical.

### Likelihood Explanation
Likely to occur incidentally in production: any transient error from the stacks-client that is not specifically a `429` (the only branch with retry logic) falls into the silent-drop branch. `ClientError` covers a wide variety of causes (deserialization errors, generic reqwest errors, IO errors) beyond `RequestFailure`, all of which hit the same unhandled branch. No malicious action or coordination is required — a single restart or blip of the signer's own stacks-node while a proposal is in flight is sufficient.

### Recommendation
Treat every submission failure the same way `429` is treated: re-insert the block into the pending-validation table (or otherwise schedule a bounded retry) instead of silently dropping it on non-`429` errors. At minimum, fall back to `insert_pending_block_validation` in the generic `Err(e)` branch of `submit_block_for_validation`, and ensure `check_submitted_block_proposal`'s timeout logic (or an equivalent watchdog) also covers blocks that failed to even reach "submitted" state, so a stuck `Unprocessed` block is guaranteed to eventually resolve to either a retried validation or an explicit `ConnectivityIssues` rejection rather than being ignored indefinitely.

### Proof of Concept
1. A block proposal arrives; `handle_block_proposal` passes proposal-time checks and calls `submit_block_for_validation`.
2. The stacks-node's `/v3/block_proposal` endpoint is momentarily unreachable (e.g., connection reset), causing `stacks_client.submit_block_for_validation` to return `Err(ClientError::RequestFailure(x))` with `x != 429`, or any non-`RequestFailure` `ClientError` variant.
3. Execution enters the final `Err(e) => { warn!(...) }` arm in `submit_block_for_validation` (lines 2641–2643) — no retry scheduled, `submitted_block_proposal` remains `None`.
4. The block was already persisted via `insert_block` with `valid = None` (line 1717–1719).
5. No later event re-drives validation for this exact `signer_signature_hash`: `check_pending_block_validations` finds nothing in the pending table for it, and the miner does not resend an identical proposal.
6. The signer never emits an accept or reject for this block, indefinitely. [3](#0-2) [4](#0-3)

    /// Submit a block for validation, and mark it as pending if the node
    /// is busy with a previous request.
    fn submit_block_for_validation(
        &mut self,
        stacks_client: &StacksClient,
        block: &NakamotoBlock,
        added_epoch_time: u64,
    ) {
        let signer_signature_hash = block.header.signer_signature_hash();
        if !self.maybe_processed_parent(stacks_client, block) {
            let time_elapsed = get_epoch_time_secs().saturating_sub(added_epoch_time);
            if Duration::from_secs(time_elapsed)
                < self.proposal_config.proposal_wait_for_parent_time
            {
                info!("{self}: Have not processed parent of block proposal yet, inserting pending block validation and will try again later";
                        "signer_signature_hash" => %signer_signature_hash,
                        "parent_block_id" => %block.header.parent_block_id,
                );
                self.signer_db
                    .insert_pending_block_validation(&signer_signature_hash, added_epoch_time)
                    .unwrap_or_else(|e| {
                        warn!("{self}: Failed to insert pending block validation: {e:?}")
                    });
                return;
            } else {
                debug!("{self}: Cannot confirm that we have processed parent, but we've waited proposal_wait_for_parent_time, will submit proposal");
            }
        }
        match stacks_client.submit_block_for_validation(
            block.clone(),
            if self.validate_with_replay_tx {
                self.global_state_evaluator
                    .get_global_tx_replay_set()
                    .unwrap_or_default()
                    .clone_as_optional()
            } else {
                None
            },
        ) {
            Ok(_) => {
                self.submitted_block_proposal = Some((signer_signature_hash, Instant::now()));
            }
            Err(ClientError::RequestFailure(status)) => {
                if status.as_u16() == TOO_MANY_REQUESTS_STATUS {
                    info!("{self}: Received 429 from stacks node for block validation request. Inserting pending block validation...";
                        "signer_signature_hash" => %signer_signature_hash,
                    );
                    self.signer_db
                        .insert_pending_block_validation(&signer_signature_hash, added_epoch_time)
                        .unwrap_or_else(|e| {
                            warn!("{self}: Failed to insert pending block validation: {e:?}")
                        });
                } else {
                    warn!("{self}: Received non-429 status from stacks node: {status}");
                }
            }
            Err(e) => {
                warn!("{self}: Failed to submit block for validation: {e:?}");
            }
        }
    }
