### Title
Stale rejection weight is never cleared when a signer flips from `Rejected` to `Accepted` for the same block, letting `total_weight_rejected` outlive a signer's reversed vote and spuriously trip the block-rejection threshold - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` keeps two independent running counters per proposed block, `total_weight_approved` and `total_weight_rejected`, meant to represent the *current* weight of signers who accepted vs. rejected a given block. A signer is allowed by design to change its vote from `LocallyRejected` back to `LocallyAccepted` after re-evaluation (documented state transition `LocallyRejected --> LocallyAccepted: re-evaluated`), and when it does, its acceptance is correctly added to `total_weight_approved`. However, the weight it earlier contributed to `total_weight_rejected` is never removed, because nothing in the `Accepted` handling path touches `total_weight_rejected` or clears the signer's slot from the bookkeeping that feeds it.

### Finding Description
`BlockStatus` tracks per-block signer responses with `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected`. [1](#0-0) 

When a `BlockResponse::Accepted` arrives, weight is added to `total_weight_approved` only if the signer's slot is not yet in `gathered_signatures`; `responded_signers` is unconditionally updated as well, but no check or reversal happens against `total_weight_rejected`: [2](#0-1) 

When a `BlockResponse::Rejected` arrives, weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` succeeds (i.e., the signer hasn't responded before at all): [3](#0-2) 

This makes the two directions asymmetric:
- Accept → Reject (same signer): `responded_signers` already contains the slot from the earlier accept, so `insert()` returns `false` and `total_weight_rejected` is correctly *not* incremented — no double count here.
- Reject → Accept (same signer, the documented re-evaluation path): `gathered_signatures` does not yet contain the slot (only `responded_signers` does, from the earlier reject), so the accept branch's guard `!block.gathered_signatures.contains_key(&slot_id)` is true and `total_weight_approved` is incremented — but the signer's earlier contribution to `total_weight_rejected` is left in place forever. There is no code path that decrements `total_weight_rejected` for an individual signer; the only way to clear it is `reset_rejections`, which zeroes it for *everyone* and only fires on a full proposal timeout: [4](#0-3) 

This breaks the intended invariant "`total_weight_rejected` == sum of weights of signers whose *current* vote is Reject" the same way the referenced report's `userTotalStaked` invariant was broken by updating one side of dual-tracked accounting (`selfStakes[...].amount`) without updating the other (`userTotalStaked`) in `release()`.

### Impact Explanation
`SignerCoordinator::get_block_status` uses exactly these two stale/live counters to decide whether to declare the proposal `SignersRejected` or accepted: [5](#0-4) 

The rejection check (`total_weight_rejected + weight_threshold > total_weight`) is evaluated *before* the approval check in the same loop iteration. Because `total_weight_rejected` can retain a signer's weight after that signer has legitimately reversed its vote to `Accepted` (a supported, documented flow — re-evaluation after a reject reason becomes stale, e.g. `should_reevaluate_reject_reason`), the coordinator can observe a rejected-weight tally that is stuck above the blocking-minority threshold even though the true, current signer-set opinion no longer blocks the block. The miner then declares `NakamotoNodeError::SignersRejected` for a block that in reality has (or is about to have) sufficient real acceptance weight, forcing it to abandon/resend the proposal. This is a liveness wedge reachable by a single signer's normal vote-reversal (no majority collusion, no key compromise) propagated only via ordinary StackerDB gossip that the miner's coordinator consumes — matching the "signer wedged / stale state acted upon" class of impact (a rejection improperly continuing to count after being superseded by an acceptance).

### Likelihood Explanation
Vote reversal from `Rejected` to `Accepted` is an explicitly supported and even expected behavior in this codebase (see `docs/signer-flows.md` §2 state diagram: `LocallyRejected --> LocallyAccepted: re-evaluated`, and §3 `should_reevaluate_reject_reason`). It happens whenever the reason a signer rejected a proposal (e.g., a stale conflicting block, a transient chainstate check failure) resolves before the miner's rejection-collection window elapses — a routine occurrence during forks/timeouts, not a contrived edge case. Any single such signer is sufficient to leave a stale weight entry in `total_weight_rejected`; no majority or privileged access is required.

### Recommendation
Track, per slot, the signer's *current* vote state (e.g. an enum keyed by `slot_id` instead of two separately-mutated running sums), and when processing an `Accepted` message for a signer whose slot is already present in `responded_signers` due to a prior `Rejected`, subtract that signer's weight from `total_weight_rejected` (and vice versa for the reverse transition) before/while adding it to `total_weight_approved`. Equivalently, recompute both totals each time from a `HashMap<slot_id, Vote>` rather than maintaining two independently-mutated `u32` accumulators, so the two counters can never drift out of sync with the actual latest-vote-per-signer set.

### Proof of Concept
1. Miner proposes block `B`; `SignerCoordinator::propose_block` inserts it via `insert_block`, initializing `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer `S` (weight `w`) initially rejects `B` (e.g., due to a transient chainstate re-check failure). The listener processes `BlockResponse::Rejected`: `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
3. Enough other signers also reject `B`, bringing `total_weight_rejected` close to, but under, the blocking-minority threshold (`total_weight - weight_threshold`).
4. `S` re-evaluates `B` (per `should_reevaluate_reject_reason`) and now legitimately accepts it, broadcasting `BlockResponse::Accepted`. The listener processes this: `gathered_signatures` doesn't contain `S`'s slot yet, so `total_weight_approved += w`. `total_weight_rejected` is left untouched at its previous (already elevated) value including `w`.
5. If a few more genuinely-rejecting signers' weight arrives (independent of `S`), `total_weight_rejected` — still counting `S`'s stale contribution — crosses the blocking-minority threshold in `SignerCoordinator::get_block_status`, causing `NakamotoNodeError::SignersRejected` to be returned even though `S`'s real, current vote is `Accepted` and should have reduced the effective rejection tally by `w`.
6. The miner abandons or has to retry the proposal based on this inflated, stale rejection count, even though the live vote tally (correctly interpreted) may not actually block the block.

No test in the repository exercises this reject→accept transition for `BlockStatus`, and there is no code path that decrements `total_weight_rejected` on a per-signer basis outside of the全-clearing `reset_rejections`, confirming the gap.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
