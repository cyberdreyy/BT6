### Title
EI credential holder can trigger a run on any job by integer ID, bypassing EI-job binding - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `POST /v2/jobs/:ID/runs` route is reachable by either a session/token user or an authenticated External Initiator (EI), since `auth.AuthenticateExternalInitiator` stores a synthetic `*clsessions.User{Role: UserRoleRun}` under the same `SessionUserKey` used by real users. `PipelineRunsController.Create` only checks `isUser := auth.GetAuthenticatedUser(c)` and, if true, calls `prc.App.RunJobV2(ctx, jobID, nil)` directly with the raw `:ID` path parameter — there is no lookup or check that the authenticated EI is bound to that specific job.

### Finding Description
The route is registered as: [1](#0-0) 

`auth.AuthenticateExternalInitiator` authenticates the EI credential (AccessKey/Secret) against the `external_initiators` table, and on success sets both `SessionExternalInitiatorKey` and `SessionUserKey`: [2](#0-1) 

In `PipelineRunsController.Create`, the code does:
```go
_, isUser := auth.GetAuthenticatedUser(c)
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [3](#0-2) 

Because `GetAuthenticatedUser` simply reads `SessionUserKey` from context, and `AuthenticateExternalInitiator` populates that same key with a `UserRoleRun` user object, `isUser` evaluates to `true` for EI-authenticated requests too — despite the code comment claiming "only users are allowed to run jobs using int IDs - EIs not allowed." There is no code anywhere in this path (nor in `ChainlinkApplication.RunJobV2`) that looks up `GetAuthenticatedExternalInitiator(c)` and validates that the EI is associated with the target job ID. `RunJobV2` (`core/services/chainlink/application.go:1126-1189`) simply does `app.jobORM.FindJob(ctx, jobID)` and executes the pipeline — no initiator/job binding check exists there either.

However, this specific code path is gated: `RunJobV2` immediately returns an error when running in production builds:
```go
if build.IsProd() {
    return 0, errors.New("manual job runs not supported on secure builds")
}
``` [4](#0-3) 
The `build` package (`IsProd`/`IsDev`) is part of the standard Chainlink build-tag mechanism and could not be located/confirmed in this index (index size limits may exclude it), so I could not verify with certainty whether this guard is compiled into production release binaries or is dev/test-only. If `IsProd()` returns `true` for the shipped node binaries, then this endpoint is unreachable in production and the vulnerability is not exploitable against a real deployed node.

### Impact Explanation
If the `build.IsProd()` guard does not apply to the actual shipped/production binary (e.g., it's a test-mode flag not set in default builds, or the reachable deployment doesn't set the prod build tag), an attacker who possesses valid EI credentials for their own integration could trigger a pipeline run of *any* job on the node by ID, including VRF or keeper jobs belonging to a different integration, potentially causing unauthorized on-chain transactions/fund movement. This would match the "unauthorized job run" / "unauthorized state-changing action" bounty class. Given the explicit `build.IsProd()` denial and the code comment `// Only used for local testing, not supported by the UI`, this functionality appears intended strictly for local/dev testing rather than a reachable production attack surface.

### Likelihood Explanation
Precondition: attacker only needs valid EI AccessKey/Secret for any initiator registered on the node (a low-privilege credential type). No job/initiator binding check exists in the vulnerable code, so exploitation would be a single POST request if reachable. However, exploitability hinges entirely on whether the node's production build sets `build.IsProd() == true`; I could not verify this constant/build-tag definition in the indexed codebase.

### Recommendation
- Correct the `isUser` check in `PipelineRunsController.Create` to explicitly exclude EI-authenticated sessions (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject, rather than relying on `GetAuthenticatedUser` which is polluted by EI auth).
- Independently of build-tag gating, do not rely solely on `build.IsProd()` to prevent an authorization bypass — enforce EI-to-job authorization checks (or fully disable EI use of this endpoint) regardless of build mode.

### Proof of Concept
Go handler-level integration test plan:
1. Build a test `chainlink.Application` (or mock) in a *non-prod* build context so `RunJobV2` does not short-circuit.
2. Create two `ExternalInitiator`s (`EI-A`, `EI-B`) via `bridges.NewExternalInitiator` and insert into the bridge ORM.
3. Create a job `job-B` (e.g., simple webhook/cron-independent int-ID job) unrelated to `EI-A`.
4. Authenticate as `EI-A` (set `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers matching `EI-A`).
5. `POST /v2/jobs/<job-B.ID>/runs` with `EI-A`'s headers.
6. Assert: request is NOT rejected with 401/403, and `prc.App.RunJobV2` is invoked, and a `pipelineRun` resource for `job-B` is returned — despite `EI-A` having no relationship to `job-B`.
7. Compare against expected/fixed behavior: an authorization check should reject the request with 401/403 because `EI-A` is not bound to `job-B`.

Note: this PoC is only meaningful if the test harness compiles without `build.IsProd()` returning true; verifying the exact build-tag semantics requires access to files not present in the current index — a full Devin session with codebase access would be needed to confirm production reachability.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func (prc *PipelineRunsController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	respondWithPipelineRun := func(jobRunID int64) {
		pipelineRun, err := prc.App.PipelineORM().FindRun(ctx, jobRunID)
		if err != nil {
			jsonAPIError(c, http.StatusInternalServerError, err)
			return
		}
		res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
		jsonAPIResponse(c, res, "pipelineRun")
	}

	idStr := c.Param("ID")

	// Webhook runs used external job UUIDs; that job type has been removed.
	if _, err := uuid.Parse(idStr); err == nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, fmt.Errorf("cannot run job of type %q: %w", job.Webhook, job.ErrJobTypeRemoved))
		return
	}

	_, isUser := auth.GetAuthenticatedUser(c)
	// only users are allowed to run jobs using int IDs - EIs not allowed
	if isUser {
		// Is it an int32? Then process it regardless of type
		var jobID int32
		jobID64, err := strconv.ParseInt(idStr, 10, 32)
		if err == nil {
			jobID = int32(jobID64)
			jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
			if err != nil {
				jsonAPIError(c, http.StatusInternalServerError, err)
				return
			}
			respondWithPipelineRun(jobRunID)
			return
		}
	}

	jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("bad job ID"))
}
