### Title
Stale per-epoch instant-withdraw receipts inflate default claim basis and corrupt the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` counter but never deletes the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` written at request time. If a borrower default is later finalized while `pendingInstantWithdraws != 0` in that same epoch number, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` count receipts that were already claimed and paid out, inflating `defaultRecoveryReserve` beyond the strategy's real balance and depressing `defaultRecoveryPrice`. This is the credit-vault analog of CVE-2020-19469's invalid write: a state write that is never corrected corrupts unrelated accounting.

### Finding Description
`requestInstantWithdraw` records three pieces of state: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . The normal claim path zeroes only the aggregate and pays out funded cash; the two per-epoch mappings remain permanently non-zero [2](#0-1) .

At default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [3](#0-2) , and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as cash already held for those claims [4](#0-3) . `finalizeDefaultRecovery` then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + priorReserve` and prices recovery off the inflated `totalBasis` [5](#0-4) .

Attack sequence (running epoch N, `instantWithdrawDelay` elapsed so instant receipts are funded and claimable):

1. Attacker (any KYC'd tranche holder) calls `requestWithdraw`, triggering `requestInstantWithdraw`, which writes `instantWithdrawClaimsByEpoch[N] += amount` [6](#0-5) .
2. `collectInstantWithdrawFunds` funds the queue, decrementing `pendingInstantWithdraws`, but a second user's receipt remains unfunded so `pendingInstantWithdraws != 0` still [7](#0-6) .
3. Attacker calls `claimInstantWithdrawRequest` and receives the funded cash; `instantWithdrawClaimsByEpoch[N]` is untouched [2](#0-1) .
4. Borrower defaults; manager calls `finalizeDefault`. `epochNumber` is still N, so the already-claimed amount re-enters `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` reports phantom "already held" cash.

### Impact Explanation
- `recoveryPrice` is computed against a `totalBasis` that includes the attacker's already-paid claim, so every legitimate defaulted receipt and active LP is underpaid pro rata — direct loss proportional to the claimed instant amount over total basis.
- `defaultRecoveryReserve` is credited with prefunded cash that was already transferred out, so the reserve exceeds the strategy's real underlying balance. Late claimants' `_transferDefaultRecovery` calls either drain funds belonging to funded receipts or revert on insufficient balance — permanent freezing/theft of unclaimed recovery [8](#0-7) . `_claimDefaultedInstantWithdrawRequest` also decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` against a claimed receipt, worsening counter skew [9](#0-8) .

### Likelihood Explanation
Requires an epoch where instant withdrawals are enabled, the queue is only partially funded (`pendingInstantWithdraws > 0` after `getInstantWithdrawFunds`), at least one user claims before `stopEpoch`, and the borrower then defaults in that same epoch — a plausible sequence since funding is allowed to be partial and default is decided by borrower repayment at epoch end. No privileged misbehavior is needed; the attacker is an ordinary tranche holder. The guards do not stop it: `_onlyIdleCDO` is satisfied via `cdoEpoch.claimInstantWithdrawRequest`, and no code path decrements the per-epoch instant counters outside of default claims.

### Recommendation
In `claimInstantWithdrawRequest` (and `_claimDefaultedInstantWithdrawRequest`), also clear `instantWithdrawsRequestsByEpoch[_user][<request epoch>]` and decrement `instantWithdrawClaimsByEpoch[<epoch>]` symmetrically, the same way `_clearWithdrawClaimForEpoch` clears `withdrawsRequestsByEpoch` for normal receipts [10](#0-9) . Alternatively, compute the default-epoch instant basis as `pendingInstantWithdraws` plus per-user unfunded amounts rather than the lifetime `instantWithdrawClaimsByEpoch` aggregate.

### Proof of Concept
```solidity
// Foundry fork test sketch against test/foundry/IdleCreditVault.t.sol harness
function testStaleInstantReceiptInflatesDefaultBasis() external {
    // enable instant withdraws and deposit
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, aprDelta, false);
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    // epoch 0 running; attacker requests instant withdraw via APR drop path
    _startEpochAndCheckPrices(0);
    _forceAprDrop(); // lastEpochApr > unscaledApr + instantWithdrawAprDelta
    uint256 bal = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(bal, address(AAtranche));

    // borrower partially funds instant queue; attacker claims funded cash
    _warpPast(instantDeadline);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(); // funds only part -> pendingInstantWithdraws > 0
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    // stale per-epoch entry remains
    assertGt(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0);

    // borrower defaults at stopEpoch; manager finalizes recovery
    _stopEpochWithDefault();
    uint256 basis = strategy.defaultPendingClaimBasis();
    // basis wrongly includes attacker's already-paid instant claim
    vm.prank(manager);
    cdoEpoch.finalizeDefault(recovered, manager);

    // recovery price diluted and reserve over-credited vs real balance
    assertGt(strategy.defaultRecoveryReserve(), underlying.balanceOf(address(strategy)));
}
```
