### Title
Permanent `Busy` freeze via malformed `#[callback]` deserialization in `on_get_account_total_balance` - ([File: lockup/src/owner_callbacks.rs])

### Summary
`refresh_staking_pool_balance` sets `staking_information.status = Busy` and schedules a cross-contract call to the (owner-selected) staking pool's `get_account_total_balance`, chained to `on_get_account_total_balance`. Because that callback declares its argument as `#[callback] total_balance: WrappedBalance`, near-sdk's generated wrapper deserializes the promise result into `WrappedBalance` (`U128`) *before* the function body (and thus `set_staking_pool_status(Idle)`) ever runs. A malicious/misbehaving pool contract can return a value that fails to deserialize as `U128`, causing the callback receipt to panic with `status` stuck at `Busy` forever.

### Finding Description
Binding claimed broken: `staking_information.status == TransactionStatus::Idle` after the promise resolves, for all possible return shapes from `get_account_total_balance`.

Code path:
- `refresh_staking_pool_balance` (owner-only) sets `Busy` and commits that state, then schedules `ext_staking_pool::get_account_total_balance(...).then(ext_self_owner::on_get_account_total_balance(...))` [1](#0-0) .
- `on_get_account_total_balance` is: `pub fn on_get_account_total_balance(&mut self, #[callback] total_balance: WrappedBalance)`, with `assert_self()` and `self.set_staking_pool_status(Idle)` as the first two body statements [2](#0-1) .
- Unlike `on_staking_pool_deposit`/`on_staking_pool_withdraw`/etc., which use `is_promise_success()` and never deserialize the callback payload, this method uses `#[callback]`, meaning near-sdk's `near_bindgen` macro generates deserialization of the promise result into `WrappedBalance` (`type WrappedBalance = U128`) as part of the method dispatch wrapper, prior to invoking the user-written function body [3](#0-2) .
- If the attacker-controlled pool contract (`staking_information.staking_pool_account_id`) returns anything that doesn't deserialize into `U128` (e.g., a bare number instead of a numeric string, an object, an array, or `null`), the macro-generated deserialization panics before `assert_self()` / `set_staking_pool_status(Idle)` execute.
- Since the panic occurs in the callback receipt, NEAR reverts state changes made *within that receipt* (i.e., none), but does not undo the `Busy` status set in the earlier `refresh_staking_pool_balance` receipt, which was already committed. Result: `status` remains `Busy` permanently, with no code path in the contract to reset it back to `Idle` (there is no explicit recovery/retry method).
- `assert_staking_pool_is_idle` then perpetually blocks `deposit_to_staking_pool`, `deposit_and_stake`, `withdraw_from_staking_pool`, `withdraw_all_from_staking_pool`, `stake`, `unstake`, `unstake_all`, `refresh_staking_pool_balance`, and `unselect_staking_pool` [4](#0-3) ; `transfer` is also blocked via `assert_no_staking_or_idle` since it treats `Busy` as blocking regardless of transfer-enablement [5](#0-4) .

Existing guards do not help: `assert_owner`, `assert_no_termination`, and `assert_staking_pool_is_idle` only gate entry into the *next* operation; none of them, nor any other method, can reset `status` back to `Idle` once stuck. `is_promise_success()` isn't used here so a successful-but-malformed response bypasses that check entirely.

### Impact Explanation
This freezes the lockup contract's staking-related functionality and the `transfer` method permanently (no retry path exists in the contract to clear `Busy`), which matches the "funds permanently frozen" Critical category: the owner can no longer deposit, withdraw, (un)stake, or transfer liquid NEAR out of the lockup contract. The attacker needs only to control the staking pool account referenced by `staking_information.staking_pool_account_id` and respond to a single `get_account_total_balance` call with a malformed value — a one-shot, repeatable-per-victim attack against any lockup contract that has selected (or been tricked into interacting with) that pool.

### Likelihood Explanation
Preconditions: the lockup's `staking_information.staking_pool_account_id` must already point to the attacker's contract, and the owner must call `refresh_staking_pool_balance()`. Getting a pool selected normally requires passing the whitelist check in `select_staking_pool` (gated by `staking_pool_whitelist_account_id`, which the audit rules state is Foundation-controlled, not attacker-controlled) — so the attacker cannot unilaterally place their contract there. This significantly reduces likelihood: it requires either (a) a pool that was whitelisted and selected in good faith later being deployed/redeployed maliciously by its operator, or (b) some other means of getting a non-whitelisted account into `staking_information` (not found in the reviewed code). If precondition (a) holds, the attack costs the pool operator nothing beyond writing a non-conforming `get_account_total_balance` view/handler, and it is trivially repeatable across any lockup contract pointed at that pool.

### Recommendation
Change `on_get_account_total_balance` to accept the raw/untyped callback result (or use `#[callback_result]`/`Result<...>` pattern if supported by the near-sdk version in use) so deserialization failures are handled gracefully inside the function body — e.g., treat a failed/unparseable result the same as a failed promise, log it, and unconditionally call `self.set_staking_pool_status(TransactionStatus::Idle)` before attempting to read/parse `total_balance`. At minimum, guarantee that `set_staking_pool_status(Idle)` executes regardless of whether the callback payload can be parsed, mirroring the `is_promise_success()`-based pattern already used in the other `on_staking_pool_*` callbacks.

### Proof of Concept
`cargo test` plan (unit test in `lockup/src` using `testing_env!` and mocked promise results, or `near-sdk-sim`):
1. Set up a `LockupContract` with `staking_information = Some(StakingInformation { staking_pool_account_id: "attacker.pool".into(), status: TransactionStatus::Busy, deposit_amount: 0.into() })` to simulate the state right after `refresh_staking_pool_balance` executed.
2. Inject a callback result via the mocked runtime that is *not* a valid `U128`/`WrappedBalance` JSON value (e.g., raw `42` instead of `"42"`, or `{}`).
3. Invoke `on_get_account_total_balance` and assert that it panics (as near-sdk's macro-generated deserialization will fail).
4. In a follow-up call using a fresh contract instance restored from storage (simulating what happens on-chain after the panicked receipt), assert `contract.staking_information.as_ref().unwrap().status == TransactionStatus::Busy` (LHS of the binding) while the required invariant is `TransactionStatus::Idle` (RHS) — demonstrating `Busy != Idle`, i.e., the binding is broken.
5. Additionally assert that `contract.assert_staking_pool_is_idle()` panics with `"Contract is currently busy with another operation"`, proving `deposit_to_staking_pool`/`unstake`/`transfer`/etc. remain permanently blocked.
