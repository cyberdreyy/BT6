Now I have the key evidence to evaluate idempotency of `ResumeRun`/`UpdateTaskRunResult`.

The critical query is in `core/services/pipeline/orm.go` `UpdateTaskRunResult`:### Title
Unauthenticated Pipeline Resume endpoint allows replay of a completed task run to re-trigger pipeline execution - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `PATCH /v2/resume/:runID` route is registered without authentication [1](#0-0) , and its idempotency guard in `orm.UpdateTaskRunResult` is scoped to the overall pipeline run's state (`running`/`suspended`), not to whether the specific task (identified by the `runID`/taskID in the URL) has already been completed. An attacker who has observed a valid task UUID can replay the same PATCH request and, whenever the parent pipeline run is still in `running` or `suspended` state (e.g., because a sibling async task is still pending), cause the already-finished task row to be overwritten and the run's `start` signal to fire again, spawning an additional `r.Run()` goroutine for the same run.

### Finding Description
`PipelineRunsController.Resume` parses the `runID` path parameter as a task UUID and forwards it, unauthenticated, straight to `app.ResumeJobV2` → `pipelineRunner.ResumeRun` → `orm.UpdateTaskRunResult`: [2](#0-1) [1](#0-0) 

`UpdateTaskRunResult`'s only replay guard is a join condition on the *pipeline run's* state, not on whether the individual `pipeline_task_runs` row is already finished:
```
WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
```
and the subsequent `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1` has no `AND finished_at IS NULL` clause, so it unconditionally overwrites an already-completed task row. [3](#0-2) 

For a pipeline containing multiple async/suspending tasks, once the first task (`taskID`) is resumed, the run transitions to `running` and eventually may suspend again while waiting on a second async task. At that point `pipeline_runs.state = 'suspended'` again. Replaying the original PATCH for the *first* (already-finished) `taskID` will still satisfy the `WHERE ... state in ('running','suspended')` predicate, will overwrite the already-processed task's output/error/finished_at, and — because the code only checks `run.State == RunStatusSuspended` (true again) — will set `start = true` and flip `pipeline_runs.state` back to `running`, triggering `ResumeRun`'s goroutine to invoke `r.Run(ctx, &run, ...)` a second time concurrently: [4](#0-3) 

This produces a second, concurrent execution pass over the pipeline DAG for the same run, racing with any other in-flight run goroutine and writing to `pipeline_runs`/`pipeline_task_runs` from two goroutines simultaneously. The audit log call further confirms this endpoint is explicitly labeled as unauthenticated (`audit.UnauthedRunResumed`). [5](#0-4) 

Note: I could not fully verify within the available context whether `r.run()` re-executes already-completed downstream tasks (e.g., a second on-chain `ETHTx` task submission) when a run is resumed a second time via this race, versus purely skipping already-finished nodes and only re-checking pending ones — this would require reading the DAG execution logic in `runner.go`'s `run` method (not fully retrieved). What is confirmed is that the endpoint is unauthenticated, the per-task idempotency check is missing, and a duplicate `start=true` signal (hence duplicate `r.Run()` goroutine) is reachable via replay while the run is mid-flight with multiple pending async tasks.

### Impact Explanation
This affects request idempotency/isolation of a financial-adjacent endpoint: a replayed resume request for a completed task can flip run state and spawn a second concurrent pipeline execution goroutine for the same run. Depending on downstream DAG behavior (unverified above), this could range from harmless duplicate DB writes/races to duplicate on-chain transaction submission by an `ETHTx` task, which would match Chainlink's "unauthorized job run / fund movement" bounty impact class if downstream tasks are indeed re-executed rather than skipped.

### Likelihood Explanation
No credentials or roles are required — the route is fully unauthenticated (`unauthedv2` group). The only precondition is knowledge of a task UUID (leaked via a bridge/external-adapter callback URL, logs, or observation), which the question's threat model explicitly grants. The exploit window (run still `running`/`suspended` due to other pending async tasks) is timing-dependent, making this a plausible but not universally-reproducible race — it requires jobs with multiple async/bridge tasks in one DAG and a replay timed while the run has not yet fully completed.

### Recommendation
- Scope the idempotency check in `UpdateTaskRunResult` to the specific task row: add `AND pipeline_task_runs.finished_at IS NULL` to both the `SELECT ... FOR UPDATE` and the subsequent `UPDATE pipeline_task_runs` statement, so a second call for an already-finished task is a no-op (return a "task already resumed" error) instead of overwriting data and re-arming the `start` signal.
- Ensure `start` is only set when this specific task transitioned from pending to finished, not merely because `run.State == RunStatusSuspended`.

### Proof of Concept
Go handler/integration test plan (`core/services/pipeline/orm_test.go` or `core/web/pipeline_runs_controller_test.go`):
1. Create a pipeline spec with two independent async/bridge tasks (`ds1`, `ds2`) feeding a final task.
2. Run the pipeline so it suspends waiting on both `ds1` and `ds2` (`pipeline_runs.state = 'suspended'`).
3. Call `orm.UpdateTaskRunResult(ctx, ds1_id, result)` — assert `start == true`, run transitions to `running`, then (simulating async continuation) let it suspend again waiting on `ds2` only.
4. Replay `orm.UpdateTaskRunResult(ctx, ds1_id, result2)` (same `ds1_id`, already finished) while `pipeline_runs.state == 'suspended'` — current code will match the WHERE clause, overwrite `ds1`'s `finished_at`/`output`, and return `start == true` again.
5. Assert (post-fix) that `err` is a "task run already finished" error and `start == false`; assert (pre-fix, to prove the bug) that the row is overwritten and `start == true`, then show via a mocked `Runner.Run` counter that `r.Run()` is invoked twice concurrently for the same `run.ID`, evidencing the double-execution path.

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
			}
		}

		return loadAssociations(ctx, tx.ds, []*Run{&run})
	})

	return run, start, err
}

		Error: err,
	})

	// TODO: Should probably replace this with a listener to update events

			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
