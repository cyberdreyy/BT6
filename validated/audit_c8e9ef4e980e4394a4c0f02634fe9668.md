### Title
Unfunded instant-withdraw receipts from a prior epoch are dropped from default-recovery accounting (stale-epoch uninitialized claim basis) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog of CVE-2018-10115 (uninitialized objects used in decode logic): in `IdleCreditVault`, instant-withdraw receipts are tracked per request epoch in `instantWithdrawClaimsByEpoch[epoch]` / `instantWithdrawsRequestsByEpoch[user][epoch]`, but the default-finalization path only ever reads the **current** `epochNumber`. If `pendingInstantWithdraws` is non-zero when an epoch rolls over — i.e. receipts requested in epoch N were only partially funded via `collectInstantWithdrawFunds` — those receipts keep their basis under key N while `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` read only key N+1. The result is stale-epoch receipts that are "uninitialized" w.r.t. recovery: they are neither counted in `totalBasis` nor backed by `defaultRecoveryReserve`, yet `defaultInstantWithdrawsFinalized` is set to true based solely on `pendingInstantWithdraws != 0` [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
- `requestInstantWithdraw` records basis under `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` [4](#0-3) .
- `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws`; it never moves per-epoch claim basis, so a partially funded queue leaves a remainder whose basis stays keyed to the *request* epoch [5](#0-4) .
- On `stopEpoch`, `deposit` increments `epochNumber` [6](#0-5) . Stale-epoch instant basis is never rolled forward.
- At `finalizeDefaultRecovery`, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — only current-epoch claims — and `_defaultPrefundedInstantReserve` computes prefunded backing from the same current-epoch key [7](#0-6) [8](#0-7) .
- After finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` = 0 for the stale receipt, then falls through to the funded path, paying `instantWithdrawsRequests[_user]` **at par** via `_transferFundedClaim` [9](#0-8) [10](#0-9) .

### Impact Explanation
Broken invariant: "one receipt one haircutted payout" and reserve isolation. Two outcomes depending on vault balance:

1. **Theft / unhaircutted payout**: if the strategy holds underlying ≥ `defaultRecoveryReserve + claim` (e.g. prefunded instant cash counted in `reserveAmount` but attributed only to current-epoch basis, or stray repayments), the stale-epoch receipt is paid 1:1 while all other defaulted claims take `defaultRecoveryPrice` haircut — the claimant extracts basis that was never haircutted, diluting/stealing the recovery reserve and funded balances of other users.
2. **Permanent freeze**: if balance < reserve + claim, `_transferFundedClaim` reverts `NotAllowed()` forever — the user's receipt tokens remain minted but unclaimable, permanently freezing funds that were partially prefunded [11](#0-10) .

Loss is quantified by the stale receipt amount × (1 − defaultRecoveryPrice) in the theft case, or the full prefunded portion in the freeze case.

### Likelihood Explanation
Requires: (a) an instant-withdraw request left only partially funded across an epoch boundary (`collectInstantWithdrawFunds` called for less than `pendingInstantWithdraws`), and (b) a subsequent borrower default finalized via `finalizeDefaultRecovery`. Both are sequencing of honest privileged calls around an unprivileged user's request — within the threat model. The code explicitly contemplates `pendingInstantWithdraws != 0` at finalization but only aggregates current-epoch basis, so the gap is structural rather than guarded.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, aggregate `instantWithdrawClaimsByEpoch` over all epochs with outstanding claims (or maintain a global `instantWithdrawClaimsTotal` counter updated on request/claim), and in `_claimDefaultedInstantWithdrawRequest` iterate/accumulate per-epoch user basis rather than only `defaultRecoveryEpoch`. Alternatively, prohibit unfunded instant receipts from surviving an epoch transition.

### Proof of Concept
Foundry fork PoC sketch (mode: instant-withdraw, epoch running → stopped → defaulted → finalized):

```solidity
// test/foundry/IdleCreditVaultStaleInstant.t.sol
function testStaleEpochInstantReceiptDroppedFromRecovery() external {
    // Epoch N running: user requests instant withdraw of 1000e6
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(1000 * ONE_SCALE, AAtranche); // via CDO

    // CDO partially funds: only 400 collected -> pendingInstantWithdraws = 600
    // basis stays under instantWithdrawClaimsByEpoch[N] = 1000
    // ... manager stops epoch N (epochNumber -> N+1), borrower underfunds -> defaulted
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, loss); // triggers _handleBorrowerDefault

    // finalizeDefaultRecovery: defaultPendingClaimBasis reads
    // instantWithdrawClaimsByEpoch[N+1] == 0 -> 600 unfunded basis excluded;
    // _defaultPrefundedInstantReserve uses key N+1 -> 400 prefunded misattributed
    cdoEpoch.finalizeDefaultRecovery(recovered, source);

    // user claims: _claimDefaultedInstantWithdrawRequest reads key [user][N+1] = 0,
    // falls through to funded path paying 1000 at par (steal) or reverting (freeze)
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest();
    // assert either payout > recovered * price (dilution) or revert NotAllowed
}
```

Caveat: I could not fully execute the CDO-side sequencing (`getInstantWithdrawFunds`/`collectInstantWithdrawFunds` call sites in `IdleCDOEpochVariant`) within the available iterations; the PoC assumes the CDO permits partial funding of the instant queue at `stopEpoch`/`startEpoch`, which the remainder-tracking design of `pendingInstantWithdraws` implies.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
