### Title
Unauthenticated MessageId collision causes silent overwrite/hijack of another user's pending callback in `savedCallbacks` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending web_api_trigger callback keyed only by the caller-supplied `MessageId`, with no check for whether that key is already in use by another in-flight request. Because `MessageId` is attacker-controlled input from an unauthenticated HTTP request (only length-limited to 200 chars in `gateway.go`), an attacker who can predict or observe a victim's `MessageId` can submit a second request with the same ID and silently replace the victim's saved callback, causing the eventual node response for that ID to be delivered to the attacker instead of the legitimate caller.

### Finding Description
In `core/services/gateway/gateway.go` `ProcessRequest`, the `MessageId` for a legacy request comes straight from `jsonRequest.ID`, which is fully attacker-controlled and only bounded by length (`len(jsonRequest.ID) > 200`) — there is no uniqueness, format, or ownership check. [3](#0-2) 

This value is passed into `HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`, which does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [2](#0-1) 

There is no `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { ... }` guard, so a second request bearing the same `MessageId` as an already-pending legitimate request simply replaces the map entry — the original caller's `callback` reference is dropped from the map with no notification, and any node response for that `MessageId` will be routed via `handleWebAPITriggerMessage` to the attacker's callback instead: [4](#0-3) 

The `MaxSavedCallbacks`/`CallbackMaxAgeSec` pruning in `pruneCallbacks()` is unrelated to this specific collision path — it only evicts oldest/expired entries during periodic sweeps and does not protect against a same-key overwrite happening synchronously within `HandleLegacyUserMessage`. [5](#0-4) 

Access requires no privilege: `msg.Validate()` only checks signature format/length and recovers a signer address via `ExtractSigner()`, but does not check that signer against any allowlist before storing the callback — the code even has a `// TODO: apply allowlist and rate-limiting here` comment confirming no such check exists at this stage. [6](#0-5)  Any party capable of generating an ECDSA signature (trivial, unauthenticated) can submit a request.

### Impact Explanation
Root cause: **overwrite without collision check**, not eviction from `MaxSavedCallbacks` capacity pressure as originally hypothesized. If an attacker learns/predicts a victim's `MessageId` (e.g., if the calling client uses low-entropy or predictable IDs, or the ID is otherwise observable/guessable), the attacker can hijack that pending request: the victim's original `callback` is discarded from the map, and the eventual DON response for that `MessageId` is delivered into the attacker's callback via `handleWebAPITriggerMessage`, causing cross-user response confusion — the attacker receives the DON's trigger response payload intended for the victim, and the victim never receives their response (silent drop). This matches the "attacker-controlled data returned to another user" / cross-user response confusion impact class.

### Likelihood Explanation
Precondition is knowledge of the victim's exact `MessageId`, which is not enforced to be high-entropy or hidden anywhere in this code path; if the calling client (e.g., a workflow node's web-API-trigger client) uses sequential, timestamp-based, or otherwise low-entropy MessageIds, this is straightforward to exploit by an unauthenticated attacker. No credentials beyond the ability to send a signed gateway JSON-RPC request are needed (self-signed keys are accepted since there's no allowlist check here). The primary uncertainty is whether `MessageId` generation elsewhere in the codebase (client side) is high-entropy/unpredictable enough to make guessing infeasible in practice — that generation logic was not found in this handler and is out of scope of this file.

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check for an existing entry under the same `MessageId` and reject the new request (return a collision error to the caller) rather than silently overwriting it. Additionally, consider deriving the map key from `(sender, MessageId)` rather than `MessageId` alone, since `msg.Body.Sender` is already populated from the verified signature in `Validate()`, which would prevent one signer from colliding with another signer's in-flight request even if `MessageId`s coincide.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two distinct `triggerRequest` messages signed by two different keys (`victimKey`, `attackerKey`) but with identical `MessageId` (e.g., `"colliding-id"`).
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`; assert `savedCallbacks["colliding-id"]` points to `victimCallback`.
3. Call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` with the same `MessageId` before the victim's response arrives.
4. Simulate a node response for `MessageId = "colliding-id"` via `handler.HandleNodeMessage`.
5. Assert that `attackerCallback.Wait(ctx)` receives the response (demonstrating hijack) while `victimCallback.Wait(ctx)` times out/never resolves — proving the victim's pending callback was silently dropped and misrouted to the attacker.

		// Arbitrary limit to prevent abuse

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
