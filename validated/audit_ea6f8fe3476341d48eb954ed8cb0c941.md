### Title
Vault DKG result export endpoint requires only Edit role instead of Admin role, unlike all other key-export routes - ([File: core/web/router.go])

### Summary
The route `POST /vault/dkg_results/export` is wrapped with `auth.RequiresEditRole` rather than `auth.RequiresAdminRole`, while every other export-type endpoint in the same router (CSA, ETH/EVM, OCR, OCR2, P2P, VRF, and the generic multi-chain keys loop) is wrapped with `auth.RequiresAdminRole`. This creates an inconsistent, lower authorization bar for a sensitive vault/DKG export operation.

### Finding Description
In `core/web/router.go`, the `v2Routes` function registers all key-export routes with `auth.RequiresAdminRole`, e.g.: [1](#0-0) [2](#0-1) [3](#0-2) 

However, the vault DKG routes are registered differently: [4](#0-3) 

Both `/vault/dkg_results/verify` and `/vault/dkg_results/export` use `auth.RequiresEditRole`, the same role tier used for lower-risk create/update operations (e.g., creating bridges, jobs, external initiators). The `VerifyDKGResult`/`ExportDKGResult` handlers are implemented in `core/web/vault_controller.go`, and the export path clearly returns DKG result/vault material to the caller (mirrored by presenter logic in `core/web/presenters/vault.go`). Since the authv2 group is reachable by any authenticated user holding session or API-token credentials with Edit role (a lower privilege tier than Admin), such a user can call this export endpoint even though they are not authorized to export any other key material (CSA, ETH, OCR, OCR2, P2P, VRF, multi-chain keys) which all require Admin role. The middleware chain does perform authentication (`auth.Authenticate` with token/session) before reaching the role check, but the role check itself (`RequiresEditRole`) does not raise the bar to Admin as it does for all comparable export operations, so no control stops the low-privileged Edit-role user from completing the export.

### Impact Explanation
An Edit-role user (not Admin) can export DKG result/vault material through `/vault/dkg_results/export`, an operation that — by the established convention in this very router file — should be gated behind Admin-only access identical to all other key export endpoints. This is a role/authorization-bar inconsistency, allowing a lower-privileged principal to extract sensitive vault-related secret material, matching the "Key or secret disclosure" / "role or authorization bypass" bounty impact class.

### Likelihood Explanation
The precondition is minimal: only a valid session or API token with Edit role is required — no Admin credentials needed. This is directly reachable via HTTP with a single POST request and is fully repeatable, requiring no race conditions or special node state beyond a valid DKG result ID.

### Recommendation
Change both vault DKG routes, and specifically `/vault/dkg_results/export`, to use `auth.RequiresAdminRole` to match the authorization bar of all other export-type key/secret endpoints in `core/web/router.go`.

### Proof of Concept
1. In a `core/web` handler-level test (similar to existing `vault_controller_test.go` and other `*_controller_test.go` files that set up `cltest.NewTestApp` and authenticate with a specific role), create a session/token with role `EDIT` (not `ADMIN`).
2. Seed a DKG result (or use the same setup used in `TestVaultController_ExportDKGResult` if present) with a known DKG result ID.
3. Issue `POST /v2/vault/dkg_results/export` with the Edit-role credentials and a valid DKG result ID in the request body.
4. Assert the response status: expected/desired behavior is `403 Forbidden` (matching `RequiresAdminRole` behavior seen in `TestETHKeysController_Export`-style tests when called with Edit role); current code will return `200 OK` with exported DKG/vault data, confirming the vulnerability.
5. As a control, repeat the same request with an Admin-role session and confirm `200 OK`, demonstrating that only the Edit-role bar is the anomaly relative to `keys/*/export` endpoints.
