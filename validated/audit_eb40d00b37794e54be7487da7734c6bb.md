This confirms the design: `SrcEscrowCreated` is emitted purely for off-chain reconstruction — nothing on-chain binds the `DstImmutablesComplement.parameters` (fee split) emitted on the source chain to the actual `dstImmutables.parameters` a caller later supplies to `createDstEscrow`. The comment explicitly says the event exists "to recreate EscrowSrc and EscrowDst immutables off-chain," confirming the cross-chain fee binding is an off-chain/trust assumption by design, not an on-chain invariant.

Given this, the destination-side fee split is inherently self-declared by whoever calls `createDstEscrow` (any unprivileged public caller — the interface imposes no restriction on `msg.sender`), and `EscrowDst._withdraw` blindly trusts `immutables.parameters` to route `protocolFeeAmount`/`integratorFeeAmount` away from the maker's payout.### Title
Unvalidated destination-side fee parameters in `createDstEscrow` let any caller zero out or redirect protocol/integrator fees - ([File: contracts/BaseEscrowFactory.sol])

### Summary
`BaseEscrowFactory.createDstEscrow` accepts a full `IBaseEscrow.Immutables` struct — including an opaque `parameters` field that encodes `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, and `integratorFeeRecipient` — directly from `msg.sender` with no cross-check against the fee split that was computed and emitted on the source chain. `EscrowDst._withdraw` later trusts these self-declared values verbatim to route "fee" transfers before paying the maker the remainder. This is the same root cause as the referenced `CreditManager.paths[i]` bug: an unprivileged caller supplies an untrusted parameter that directly determines how much value flows to the fee-collecting party, and no invariant checks the resulting split against the pre-agreed amount.

### Finding Description
On the source chain, `_postInteraction` in `contracts/BaseEscrowFactory.sol` (lines 67-160) computes `integratorFeeAmount`/`protocolFeeAmount` via `FeeTaker._getFeeAmounts` from the maker-signed order/extension, and only *emits* them inside `DstImmutablesComplement.parameters` as part of the `SrcEscrowCreated` event: [1](#0-0) 

The interface documentation confirms this event exists purely for off-chain reconstruction, not on-chain enforcement: [2](#0-1) 

However, `createDstEscrow` — the function that actually deploys the destination escrow and is reachable by any unprivileged address (no whitelist/access-token gate, unlike `_postInteraction`) — takes `dstImmutables` (including `parameters`) entirely as caller-supplied calldata, with the only checks being on `msg.value`/native amount and the cancellation timing: [3](#0-2) 

Nothing here recomputes or validates `dstImmutables.parameters` against the `DstImmutablesComplement.parameters` that was committed on the source chain. `EscrowDst._withdraw` then blindly extracts fee amounts and recipients from this attacker-controlled field and uses them to split the payout: [4](#0-3) [5](#0-4) 

Because `immutables.amount - integratorFeeAmount - protocolFeeAmount` is what the maker receives, and `protocolFeeAmount`/`integratorFeeAmount` (plus their recipients) come straight from the un-validated `parameters` bytes, a caller of `createDstEscrow` can set `protocolFeeAmount = 0` and `integratorFeeAmount = 0` (or redirect the recipients to an address they control) while still funding the escrow with the same total `amount` the maker expects to see. The maker's off-chain check (per the documented lifecycle, "Once the Maker sees the funded EscrowDst, they reveal the secret") is only likely to verify the total `amount`/`token`/`hashlock`/timelocks match — not the opaque `parameters` bytes — so the swap proceeds normally while the protocol/integrator fee is silently stripped or hijacked.

### Impact Explanation
This matches the "High: theft or permanent loss of unclaimed fee-like value" category in the bounty scope. The protocol/integrator fee that should be collected on withdrawal from `EscrowDst` can be reduced to zero or redirected to an attacker-chosen address by any caller of `createDstEscrow`, without needing any privileged role — `createDstEscrow` has no whitelist or access-token restriction, unlike the source-side `_postInteraction`.

### Likelihood Explanation
High. `createDstEscrow` is a standard, always-reachable public entry point in the live swap lifecycle (explicitly called out in the audit pivots as in-scope: "Destination path: `createDstEscrow` -> timelock binding -> native/ERC20 funding -> destination withdraw/cancel flow"). No signature, whitelist, or on-chain cross-check ties `dstImmutables.parameters` to the source-chain commitment, so exploiting it requires nothing beyond calling the function with crafted calldata and funding the same total `amount`/`safetyDeposit` that a legitimate deployment would require.

### Recommendation
Bind the destination-side fee parameters to the source-chain commitment on-chain instead of trusting caller-supplied `parameters`. Options:
- Have `_postInteraction` store (or hash-commit) the computed `protocolFeeAmount`/`integratorFeeAmount`/recipients keyed by `orderHash`, and require `createDstEscrow` to look up and use that committed data rather than accepting it as free-form calldata.
- Alternatively, hash `DstImmutablesComplement` at `_postInteraction` time and require `createDstEscrow` to pass/prove data matching that hash before deployment.
- At minimum, revert if the caller-declared `protocolFeeAmount + integratorFeeAmount` deviates from a value independently derivable/verifiable on the destination chain.

### Proof of Concept
1. A resolver/taker (or any address) observes a `SrcEscrowCreated` event with `dstImmutablesComplement.parameters` encoding `protocolFeeAmount = X`, `integratorFeeAmount = Y`, recipients `P`/`I`.
2. Instead of reusing those exact `parameters`, the caller invokes `createDstEscrow` with the same `amount`, `token`, `hashlock`, `maker`, `taker`, `safetyDeposit`, and `timelocks` (so the maker's visual/automatic checks pass), but with `parameters = abi.encode(0, 0, P, I)` (or with `P`/`I` replaced by the caller's own address).
3. `createDstEscrow` deploys `EscrowDst` using this self-declared `dstImmutables`, funding `immutables.amount` from `msg.sender` as usual — the check `msg.value != nativeAmount` and `IERC20.safeTransferFrom(msg.sender, escrow, immutables.amount)` both pass because total amount is unchanged: [6](#0-5) 
4. The maker, seeing the escrow funded with the expected total `amount`, reveals the secret.
5. On `withdraw`, `EscrowDst._withdraw` sends `0` to the protocol/integrator fee recipients and the *full* `immutables.amount` to the maker, per the un-validated `parameters`: [7](#0-6)  — the protocol/integrator fee that should have been collected is never paid, and if `parameters` instead redirects the recipient addresses to the caller's own address, the fee is stolen outright.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
