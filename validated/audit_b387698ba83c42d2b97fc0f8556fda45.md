## Analysis

The claimed invariant is: `for every request_id, confirmations[request_id] ⊆ {public keys that currently exist on the account}` — i.e., no key that has been removed from the account should still contribute a vote toward `num_confirmations`.

Tracing `confirm` and the `DeleteKey` handling in `execute_request` shows this invariant is **not maintained**.

`confirm` only checks that the calling account is the multisig itself and that the signer hasn't already voted on *this* request; it has no notion of "is this pk still a live key" beyond what NEAR's runtime enforces for the *current* call: [1](#0-0) 

When a `DeleteKey` action is executed, the contract purges pending requests and `num_requests_pk` only for requests that the deleted key itself *originated* — it does **not** scan every other pending request's `confirmations` `HashSet<PublicKey>` to strip out the deleted key from votes it cast on requests originated by someone else: [2](#0-1) 

Concretely:
1. Key `K1` calls `add_request` to create request `R` (some other signer).
2. Key `K2` calls `confirm(R)`, inserting `K2` into `confirmations[R]` (below threshold, so nothing executes yet): [3](#0-2) 
3. Later, `K2` is removed from the account via a legitimate `DeleteKey { public_key: K2 }` multisig request. `execute_request`'s `DeleteKey` branch only deletes requests where `r.signer_pk == K2` (i.e., requests *added* by `K2`) — it never touches `confirmations[R]`, so `K2`'s vote on `R` (which it did not originate) remains in the set.
4. `R` is still pending. When enough *other, currently-live* keys later call `confirm(R)`, the count check `confirmations.len() as u32 + 1 >= self.num_confirmations` at [4](#0-3)  includes `K2`'s stale vote, so `R` can execute with fewer live/current keys than `num_confirmations` actually requires.

None of the existing guards catch this: `assert_valid_request` only checks predecessor/request existence [5](#0-4) , and there is no mechanism anywhere in the contract that revalidates confirmation-set membership against currently-live keys at execution time.

This is a genuine implementation gap: **key removal does not retroactively invalidate that key's prior votes on requests it didn't originate**, so a request can execute below the "true" live-signer quorum, satisfying the Critical impact bullet "a multisig request executed below `num_confirmations` live members." It requires the request to remain pending across the key-rotation event and requires the attacker/former-member's stale vote to be one of the counted confirmations — it does not depend on the `num_requests_pk`/`active_requests_limit` mechanism mentioned in the question (that part is a red herring; `num_requests_pk` only throttles request creation, it plays no role in the confirmation-counting bug).

Note that this bug is about **stale votes from since-removed keys**, not about an outsider with no key ever being able to call `confirm`/`add_request` — those still require `predecessor_account_id == current_account_id`, meaning the caller must sign with a key currently valid on the account, which the NEAR runtime enforces independently of the multisig contract's own bookkeeping.

### Title
Stale confirmations from removed multisig keys still count toward quorum — (`multisig/src/lib.rs`)

### Summary
`execute_request`'s `DeleteKey` branch only clears pending requests *originated* by the deleted key and removes its `num_requests_pk` entry, but never purges that key's public key from the `confirmations` `HashSet` of other pending requests it had already voted on. A request that received a vote from a key later removed can still execute once enough additional votes accumulate, counting the removed key's stale vote toward `num_confirmations`.

### Finding Description
Broken binding: `confirmations[request_id] ⊆ live_keys(account)` should hold at all times, but is violated because `DeleteKey` handling at [2](#0-1)  filters `self.requests` by `r.signer_pk == pk` (the request *originator*) and never inspects/updates `self.confirmations` entries where `pk` appears merely as a *confirmer*. Consequently `confirm`'s threshold check at [6](#0-5)  can count a vote from a key that no longer exists on the account, letting `execute_request` run with fewer genuinely-live confirmations than `num_confirmations`.

### Impact Explanation
A multisig request (e.g., `Transfer`, `FunctionCall`, `AddKey`) can execute with fewer live-key confirmations than the configured `num_confirmations`, moving NEAR out of the account or granting access without full authorization from current members — matching the Critical category "a multisig request executed below `num_confirmations` live members." This is repeatable any time a key is rotated/removed while a request is left pending with an existing vote from that key.

### Likelihood Explanation
Requires: (1) a request pending below quorum with a confirmation from a key, (2) that key subsequently removed via a legitimate `DeleteKey` action while the request stays open, (3) later confirmations from other live keys push the count to/above `num_confirmations`. This is a normal-looking sequence (key rotation is routine on long-lived multisig accounts) and needs no special privilege beyond being able to eventually add/confirm requests on the account — no gas/storage exhaustion or off-chain dependency is required.

### Recommendation
On `DeleteKey` execution, iterate over `self.confirmations` for all pending requests and remove the deleted `pk` from each `HashSet<PublicKey>`, not just the requests originated by that key (mirroring what is already done for `self.requests`/`num_requests_pk`).

### Proof of Concept
`cargo test` in `multisig/src/lib.rs` test module:
1. Init `MultiSigContract::new(3)` with keys `K1`, `K2`, `K3` as access keys of `alice`.
2. As `K1`, `add_request` a `Transfer` request `R` (receiver `bob`).
3. As `K2`, `confirm(R)` — assert `confirmations[R].len() == 1` (contains `K2`).
4. As `K1`, `add_request_and_confirm` a `DeleteKey { public_key: K2 }` request, and confirm with `K3` to reach 3 confirmations, deleting `K2` — assert `K2` removed from `num_requests_pk` but `confirmations[R]` still contains `K2` (assert length still 1 after deletion — demonstrating the bug).
5. As `K3` then a new key `K4` (added to replace `K2`), call `confirm(R)` twice — request executes on the second confirm because count reaches `3` (`K2`(stale) + `K3` + `K4`), even though only 2 currently-live keys ever approved `R`.
6. Assert `c.requests.len() == 0` (executed) while only `K1`(originator, not counted as confirmation)/`K3`/`K4` are live signers who explicitly confirmed — proving execution occurred with a stale, removed key's vote counted.

        self.assert_valid_request(request_id);

        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
