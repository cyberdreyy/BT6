### Title
Post-default withdraw receipts pay 1:1 out of the fixed `defaultRecoveryReserve`, letting any tranche holder drain the recovery pot before defaulted claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE maps a use-after-free/race bug class (a resource continues to be used after its accounting context is gone) onto the vault's default-recovery lifecycle: after `finalizeDefaultRecovery` sizes and freezes `defaultRecoveryReserve` to exactly cover haircutted claims, `requestWithdraw` keeps minting new post-default receipts whose claims are paid **at par** out of that same, already-fully-allocated reserve — a "freed" (already-earmarked) balance being reused.

### Finding Description
When the borrower defaults and `finalizeDefaultRecovery` runs, the reserve is crystallized as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, then stored in `defaultRecoveryReserve`. Every settled claim consumes it via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` by the payout. At `recoveryPrice < RECOVERY_FULL`, the reserve exactly equals the sum of all haircutted claims — there is no slack.

After finalization, `requestWithdraw` takes a post-default path that burns `_amount` strategy tokens from the CDO, mints `_amount` to the user, and records `postDefaultRequests[_user] = _amount` — without adding any underlying to the reserve and without increasing `pendingWithdraws` (deliberately, per the comment "without increasing borrower-facing pendingWithdraws"). `claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest`, which burns the receipt and calls `_transferDefaultRecovery(_user, amount)` — paying `amount` 1:1 straight out of `defaultRecoveryReserve`.

The receipt is nominally fair to the requester (the CDO passed an already-haircut amount because `virtualPrice` dropped), but the funding source is wrong: the reserve was sized to pay defaulted claimants `claimBasis * recoveryPrice`, not to also fund new par-denominated claims minted out of thin air. Nothing replenishes the reserve for post-default requests — the burned CDO strategy tokens only shrink the CDO's own claim, which is settled through a different pot.

### Impact Explanation
Any tranche holder (explicitly an allowed unprivileged attacker) can, immediately after `finalizeDefaultRecovery`, call `requestWithdraw` on the CDO and then `claimWithdrawRequest` to pull `postDefaultRequests` face value from `defaultRecoveryReserve`. Since the reserve is fully earmarked (`reserve = recoveryPrice * totalBasis` with `recoveryPrice < 1`), each post-default claim directly steals from unsettled defaulted receipt claims. Claims processed later in `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` revert on the underflow in `defaultRecoveryReserve -= _amount`, permanently freezing other users' recovery. Quantified loss: up to the entire `defaultRecoveryReserve` for post-default withdrawals, i.e. all not-yet-claimed defaulted receipts.

### Likelihood Explanation
The trigger requires only a default that finalizes at a sub-par recovery (the scenario the whole recovery machinery exists for) plus an attacker holding any tranche tokens post-finalization. No privileged action is needed: `requestWithdraw` is callable by the honest CDO on behalf of any user, and the post-default path only reverts if the same user already has an open receipt — a fresh attacker address is unrestricted. One transaction pair (request + claim) executes the theft atomically.

### Recommendation
- Fund post-default receipts from a source other than `defaultRecoveryReserve`: either pull the corresponding underlying from the CDO/strategy balance at request time, or add `postDefaultRequests` claims to a separately tracked bucket paid only from post-finalization borrower repayments.
- Alternatively, keep reserve accounting honest by decrementing the claimable basis of the CDO's remaining active tokens (or crediting the reserve) when minting `postDefaultRequests`, so the payout is offset rather than net-new.
- Add a solvency invariant/test: `sum(all outstanding recovery claims) <= defaultRecoveryReserve` must hold after every `requestWithdraw`/`claimWithdrawRequest` post-finalization.

### Proof of Concept
A Foundry fork test would: (1) deposit into AA/BB, run an epoch, have some users request normal and instant withdrawals; (2) default the borrower and call `finalizeDefault`/`finalizeDefaultRecovery` with `recovered < totalBasis` so `recoveryPrice < RECOVERY_FULL`; (3) from a fresh attacker holding tranche tokens, call `cdoEpoch.requestWithdraw(amount, tranche)` then `cdoEpoch.claimWithdrawRequest()` — observe attacker receives `postDefaultRequests` face value while `defaultRecoveryReserve` shrinks; (4) have a legitimate defaulted claimant call `claimWithdrawRequest` and observe revert on `defaultRecoveryReserve -= _amount`, demonstrating stolen/permanently frozen recovery. The exact revert path is `claimWithdrawRequest → _claimPostDefaultWithdrawRequest → _transferDefaultRecovery` at `contracts/strategies/idle/IdleCreditVault.sol:760-766, 912-916`.

Caveat: I could not fully verify whether `IdleCDOEpochVariant` compensates the reserve elsewhere (e.g., by forwarding underlying during post-default `requestWithdraw`). If the CDO transfers matching underlying into the strategy at request time, the reserve stays solvent and this is not exploitable; the strategy-side code shows no such credit inside `requestWithdraw`/`postDefaultRequests` handling, but that caller-side flow should be confirmed in a live-session trace before reporting.
