### Title
Freshness-cutoff bypass of `conflict_still_blocks` lets a stale-but-still-canonical signed block be overridden by a conflicting sibling in another tenure - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit` decides whether a signed conflicting block still "blocks" a new pre-commit by first gating on a fixed wall-clock value, `tenure_last_block_proposal_timeout` (default 30s), rather than on verified chain state. If a prior signed block's `last_endorsed` timestamp falls outside this window, the node-derived liveness check (`conflict_still_blocks`) is *never invoked* for cross-tenure conflicts, and the signer will sign a second, conflicting block at the same height — exactly the class of bug described in the referenced report: a fixed/hard-coded value standing in for a value that should be derived from live, verified state, leading to an under-protected security check.

### Finding Description
In `handle_block_pre_commit`, once pre-commit weight reaches the 70% threshold, the signer looks for signed conflicts at or above the proposed height across *all* tenures via `get_signed_conflicts` [1](#0-0) . It then computes a `freshness_cutoff` purely from `tenure_last_block_proposal_timeout` (a static, operator-configured duration, default 30s) [2](#0-1)  and only calls the node-verifying `conflict_still_blocks` (which checks whether the conflicting tenure's sortition and block are still canonical) when the conflict is "fresh" — `last_endorsed > freshness_cutoff` — due to short-circuit `&&` evaluation:

```
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(stacks_client, conflict)
        && self.conflict_still_blocks(stacks_client, conflict, block_info.block.header.chain_length)
}) { ... return; }
``` [3](#0-2) 

If the conflict is stale (older than the timeout), the subsequent logic checks only the **same-tenure** case:
```
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash && ...
}) { ... }
``` [4](#0-3) 

A stale conflict belonging to a **different** tenure hits neither branch and is dropped entirely — the signer proceeds straight to `mark_locally_accepted` and signs [5](#0-4) . This mirrors the documented design intent in `docs/signer-flows.md`: "FRESH -- no — all stale --> OWN{'a conflict in this block's OWN tenure?'}" and "OWN -- no --> SIGN" [6](#0-5) . The design explicitly substitutes a fixed timer for the actual, verifiable fact of whether the earlier signed block is still reachable on the canonical chain — precisely the "hard-coded value standing in for a value that should be computed/verified live" bug class from the report (there, a constant LTC ratio stood in for a live price feed; here, a constant timeout stands in for a live canonicality check).

`conflict_still_blocks` itself is the correct oracle for "is this conflict still alive" — it queries `/v3/sortitions/burn/:hash` and `/v3/tenure/tip` to determine if the tenure/block is still canonical [7](#0-6) . The freshness gate bypasses this oracle for cross-tenure conflicts once the fixed timeout elapses, even though the block in question may still be entirely live and reachable on the node's canonical chain.

### Impact Explanation
This breaks the "one signed block per height" invariant (equivocation): the signer can be induced to place a valid signature over two different blocks at the same Stacks height in two different tenures, where the first block is still canonically live. If enough signers hit this path for both blocks, both blocks can independently reach the 70% signing threshold, producing two competing, signer-endorsed blocks at the same height — a critical safety violation matching the "signer signing a conflicting block" impact category, achievable without a majority of signers, their keys, or the `auth_token`. A miner (or two competing miners across tenures) can trivially trigger the elapsed-timeout condition by simply waiting past `tenure_last_block_proposal_timeout` (30s by default) before causing the second, competing block to reach pre-commit — well within normal tenure-extend/reorg timing already present in the protocol (`reorg_attempts_activity_timeout` is 200s by default, larger than the 30s freshness window, so this is easily achievable during ordinary reorg-timing scenarios) [8](#0-7) .

### Likelihood Explanation
The timing constants make this readily reachable: `tenure_last_block_proposal_timeout` defaults to only 30 seconds [9](#0-8) , while normal reorg/tenure-extend activity windows (`reorg_attempts_activity_timeout` = 200s) routinely exceed it. Any delay of >30s between the first sibling's endorsement and the second sibling's pre-commit threshold being reached — plausible during ordinary tenure changes, network delay, or a miner deliberately timing a competing tenure's block proposal — is sufficient to place the earlier conflict outside the freshness window and skip the node-verified liveness check entirely for the cross-tenure branch.

### Recommendation
Do not let a fixed wall-clock timeout alone determine whether a conflicting signed block can be overridden. For conflicts in tenures other than the proposed block's own tenure, always invoke `conflict_still_blocks` (or an equivalent canonical-liveness check against the node) regardless of freshness, and only exempt the check when the conflict has been *proven* dead (orphaned tenure or a reorg past a globally-accepted block) rather than merely "not recently endorsed." If a node-derived staleness signal is required for liveness (to avoid getting stuck when the node cannot answer), that signal should itself be derived from chain state (e.g., "N confirmations since the conflicting tenure's burn view," or an explicit query proving the conflicting block is unreachable) rather than a purely local, operator-configured timer.

### Proof of Concept
1. Miner A starts tenure 1 and proposes block X at height H; the signer set pre-commits and signs X (`signed_self`/`last_endorsed = T0`), and X remains fully canonical on the node (no reorg).
2. Wait more than `tenure_last_block_proposal_timeout` (default 30s) — well within the existing `reorg_attempts_activity_timeout` window (200s) already tolerated by the protocol for tenure-extend/reorg scenarios.
3. Miner B (a different tenure 2, sibling to tenure 1) proposes a conflicting block Y also at height H and drives pre-commit weight to ≥70%.
4. In `handle_block_pre_commit`, `get_signed_conflicts` returns X as a conflict at height H [1](#0-0) . Because `T0` is now older than `freshness_cutoff`, the predicate `conflict.last_endorsed > freshness_cutoff` is false, so `conflict_still_blocks` — which would otherwise confirm X's tenure/block are still canonical — is never called [3](#0-2) .
5. Since X's `consensus_hash` differs from Y's, the same-tenure fallback check also does not apply [4](#0-3) , so the signer proceeds to sign Y at the same height H, while X is still live on-chain — producing two signer-endorsed, conflicting blocks at height H.

Note: I could not execute this scenario against a running signer/node in this environment; the analysis is based on static code and inline documentation review (`docs/signer-flows.md`) confirming the intended control-flow described above. A Devin session with test infrastructure (e.g. `stacks-signer/src/v0/tests.rs`, which already contains sibling-conflict fixtures like `run_sibling_scenario`) would be needed to empirically confirm the double-sign outcome.

    fn conflict_still_blocks(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
        proposed_height: u64,
    ) -> bool {
        if let Ok(burn_block) = self
            .signer_db
            .get_burn_block_by_ch(&conflict.consensus_hash)
        {
            match stacks_client.get_sortition_by_burn_hash(&burn_block.block_hash) {
                Ok(_) => {
                    // The tenure's sortition is still canonical: the conflict is live at the
                    // burn chain level, so fall through to the block-level questions.
                }
                Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                    // A 404 only proves the sortition was orphaned if the node's burnchain
                    // view actually covers the burn block's height: a node still catching up
                    // 404s canonical burn blocks it hasn't processed yet (and the
                    // endpoint also 404s on internal data misses). Only trust it once the
                    // node's burnchain tip is at or past the stored burn block.
                    match stacks_client.get_peer_info() {
                        Ok(peer_info) if peer_info.burn_block_height >= burn_block.block_height => {
                            info!("{self}: A conflicting block's tenure was orphaned by a burnchain fork. The conflict no longer blocks.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                                "conflicting_block_height" => conflict.stacks_height,
                                "burn_block_hash" => %burn_block.block_hash,
                            );
                            return false;
                        }
                        Ok(peer_info) => {
                            info!("{self}: The node does not know a conflicting block's burn block, but its burnchain tip has not reached that height, so this does not prove the tenure was orphaned. Leaving the conflict in place.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                                "burn_block_hash" => %burn_block.block_hash,
                                "burn_block_height" => burn_block.block_height,
                                "node_burn_block_height" => peer_info.burn_block_height,
                            );
                            return true;
                        }
                        Err(e) => {
                            warn!("{self}: Failed to fetch the node's burnchain tip while checking a conflicting block's tenure: {e:?}. Leaving the conflict in place.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                            );
                            return true;
                        }
                    }
                }
                Err(e) => {
                    warn!("{self}: Failed to check whether a conflicting block's tenure is still canonical: {e:?}. Leaving the conflict in place.";
                        "conflicting_consensus_hash" => %conflict.consensus_hash,
                    );
                    return true;
                }
            }
        }
        let node_reaches_conflict = match stacks_client.get_tenure_tip(&conflict.consensus_hash) {
            Ok(tip) => tip.anchored_header.height() >= conflict.stacks_height,
            // A 404 is an answer, not a failure: the node has no blocks in that tenure at all.
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => false,
            Err(e) => {
                warn!("{self}: Failed to fetch the canonical tip of a conflicting block's tenure: {e:?}. Leaving the conflict in place.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "conflicting_block_height" => conflict.stacks_height,
                );
                return true;
            }
        };
        node_reaches_conflict
            || (!conflict.globally_accepted && conflict.stacks_height <= proposed_height)
    }
