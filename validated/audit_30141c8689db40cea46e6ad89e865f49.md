### Title
`DefaultDistributor.claim` lacks `address(0)` check on payout recipient `_to` — ([File: contracts/DefaultDistributor.sol](contracts/DefaultDistributor.sol))

### Summary
After a borrower default, tranche holders redeem their recovery payout via `DefaultDistributor.claim(address _to)`. The function pulls the caller's entire tranche balance into the distributor and transfers the pro-rata underlying payout to caller-supplied `_to` with no `address(0)` validation. A holder passing `address(0)` irreversibly loses their payout — the same bug class as `UToken.borrow`'s unchecked `to`.

### Finding Description
`claim` at `contracts/DefaultDistributor.sol:35` performs:

```solidity
function claim(address _to) external {
    require(isActive, '!ACTIVE');
    IERC20 tranche = IERC20(trancheToken);
    uint256 trancheBal = tranche.balanceOf(msg.sender);
    tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
    IERC20(token).safeTransfer(_to, trancheBal * rate / ONE_TRANCHE);
}
```

The only check is `isActive`. `_to` is fully attacker/user controlled. Once the tranche tokens are transferred to the distributor and the underlying `safeTransfer(_to, ...)` executes, the payout is gone: `rate` is fixed at activation (`setIsActive`, line 49) against the distributor's underlying balance, and there is no mechanism for a user to re-claim — their tranche balance is already zero. The tranche tokens sent in are effectively captured/burned from circulation while the corresponding underlying ends up at `address(0)`, permanently unrecoverable for underlyings that do not revert on zero-address transfers (e.g., USDC, which is the deployment asset for these vaults).

By contrast, comparable periphery in the same codebase does guard this: `IdleCreditVaultWriteOffEscrow.emergencyWithdraw` reverts `Is0()` when `_to == address(0)` (`contracts/IdleCreditVaultWriteOffEscrow.sol:176-177`), and `ProgrammableBorrower.rescueTokens` reverts `InvalidAddress()` (`contracts/strategies/idle/ProgrammableBorrower.sol:602-604`), showing the zero-recipient hazard is recognized elsewhere but missed here.

### Impact Explanation
A defaulted-tranche holder calling `claim(address(0))` (or any typo'd/unset recipient) permanently burns their entire recovery entitlement. Loss equals `trancheBal * rate / ONE_TRANCHE` — up to the holder's full share of the post-default recovery pool — with zero recourse, since their tranche tokens are already escrowed in the distributor. Broken invariant: one receipt one payout / fair redemption. This is a direct, quantified loss of user funds, identical in consequence to the referenced `UToken.borrow` finding.

### Likelihood Explanation
Low-to-medium: requires user error rather than an exploitable adversarial path, but the blast radius is the entire claim balance, the window is one-shot (post-default redemption is a single call per holder), and integrations/aggregators that parameterize the recipient amplify the risk. No privileged role is needed; any tranche holder triggers it.

### Recommendation
Revert on zero recipient:

```solidity
function claim(address _to) external {
    require(isActive, '!ACTIVE');
    require(_to != address(0), 'TO_0');
    ...
}
```

Consider also defaulting to `msg.sender` when `_to == address(0)` for UX parity with typical `claim()` APIs.

### Proof of Concept
Foundry test sketch (fork or local mock with a token that permits zero-address transfers, e.g., a plain ERC20 without OZ's zero-recipient guard, or mainnet USDC):

```solidity
function test_claim_toAddressZero_losesPayout() public {
    // arrange: distributor funded post-default
    DefaultDistributor dist = new DefaultDistributor(address(token), address(tranche), owner);
    deal(address(token), address(dist), 1000e6);
    deal(address(tranche), alice, 500 ether);
    vm.prank(owner);
    dist.setIsActive(true); // rate = 2 USDC per tranche

    uint256 balBefore = token.balanceOf(alice);
    vm.prank(alice);
    dist.claim(address(0));

    // alice's tranches are captured, payout went to address(0)
    assertEq(tranche.balanceOf(alice), 0);
    assertEq(token.balanceOf(alice), balBefore);          // no gain
    assertEq(token.balanceOf(address(0)), 1000e6);        // burned payout
    // re-claim impossible: tranche balance is zero
    vm.prank(alice);
    dist.claim(alice); // transfers 0
}
```

**Note:** impact is conditional on the underlying not reverting on `transfer(address(0))`; USDC's `transfer` does not enforce this, so the loss is real for the intended deployment asset.
