### Title
Integer overflow panic in `RecentLeaderSlots::estimate_current_slot` from attacker-controlled slot values on `slotsUpdates` websocket - (File: tpu-client-next/src/node_address_service/recent_leader_slots.rs)

### Summary
`WebsocketNodeAddressService` feeds raw `slot` values from a subscribed `slotsUpdates` pubsub stream directly into `RecentLeaderSlots::record`, with no upper-bound validation on the slot value. [1](#0-0)  `estimate_current_slot` then performs unchecked arithmetic (`median_recent_slot + (max_index - median_index) as u64` and `expected_current_slot + MAX_SLOT_SKIP_DISTANCE`) that can overflow `u64` if the buffer's median entry is a maliciously large slot value, causing a panic in overflow-checked builds. [2](#0-1) 

### Finding Description
`websocket_slot_event_stream` connects to an arbitrary `websocket_url` via `PubsubClient::slot_updates_subscribe`, and maps each incoming `SlotUpdate::FirstShredReceived`/`Completed` message directly into a `SlotEvent::Start`/`End` carrying whatever `slot` value the remote endpoint supplied, with no range or sanity check. [3](#0-2)  These events are pushed unmodified into `RecentLeaderSlots` via `record`, which maintains a bounded ring buffer (capacity 48). [4](#0-3) 

`estimate_current_slot` sorts the buffered events, picks the median entry, then computes `expected_current_slot = median_recent_slot + (max_index - median_index) as u64` and `max_reasonable_current_slot = expected_current_slot + MAX_SLOT_SKIP_DISTANCE` using plain `+` (only clippy's lint is suppressed via `#[allow(clippy::arithmetic_side_effects)]`, which does not disable Rust's runtime overflow checks). [5](#0-4)  If a malicious `slotsUpdates` source repeatedly sends `SlotEvent::Start`/`End` with slot values near `u64::MAX`, enough of these entries eventually fill the 48-entry buffer so that the sorted median lands on one of the attacker-supplied huge values (e.g., two events with slot `u64::MAX` alone: buffer `[Start(MAX), End(MAX)]`, `median_index = 0`, `median_recent_slot = MAX`, so `median_recent_slot + 1` overflows immediately). This overflow panics the async task in a debug/overflow-checked build, and even without immediate overflow at line 51, the subsequent `+ MAX_SLOT_SKIP_DISTANCE` at line 52 can overflow once `expected_current_slot` is close to `u64::MAX`.

No guard exists between the raw pubsub-derived slot value and this arithmetic: `record` performs no bounds check, and `estimate_current_slot` assumes slot values are "reasonable" only for the purpose of filtering the *result*, not for protecting its own internal addition.

### Impact Explanation
This causes a panic (task/thread crash) in the process consuming the `WebsocketNodeAddressService`/`SlotUpdateService` (used by TPU-client-next callers, e.g., transaction-forwarding tooling that tracks leader schedule) driven purely by content received over a single, rate-limited `slotsUpdates` subscription to an untrusted/attacker-controlled endpoint. This matches the "single RPC/pubsub-driven input causes a process panic → denial of service" bounty category, scoped to this component of the repo.

### Likelihood Explanation
The precondition is straightforward: at least one prior normal `record()` call must have occurred (which happens naturally after the service starts and receives its first legitimate slot update), after which the attacker-controlled `slotsUpdates` source needs only to emit a handful of `Start`/`End` events with slot values near `u64::MAX` (within the stated one-message-per-`CLUSTER_SLOT_TIME_TARGET/2` rate limit, sent over an extended subscription session) to dominate the median of the 48-entry ring buffer and trigger the overflow. This is fully reproducible and deterministic given control of the websocket stream content.

### Recommendation
Use saturating (or checked) arithmetic for `expected_current_slot` and `max_reasonable_current_slot` computations (e.g., `saturating_add`), and/or clamp/reject incoming slot values that are implausibly large (e.g., far beyond any plausible cluster slot) before they are recorded in `RecentLeaderSlots`.

fn websocket_slot_event_stream(
    websocket_url: String,
) -> (impl Stream<Item = SlotEvent>, JoinHandle<Result<(), Error>>) {
    const SEND_TIMEOUT: Duration = Duration::from_millis(100);
    let (tx, rx) = mpsc::channel::<SlotEvent>(256);

    let handle: JoinHandle<Result<(), Error>> = tokio::spawn(async move {
        let pubsub_client = PubsubClient::new(websocket_url).await?;
        let (mut notifications, unsubscribe) = pubsub_client.slot_updates_subscribe().await?;

        while let Some(event) = notifications.next().await {
            let Some(event) = map_websocket_update_to_slot_event(event) else {
                continue;
            };
            let Err(send_error) = tx.send_timeout(event, SEND_TIMEOUT).await else {
                continue;
            };
            match send_error {
                SendTimeoutError::Closed(_) => {
                    info!("Slot event receiver dropped, exiting websocket slot event stream.");
                    break;
                }
                SendTimeoutError::Timeout(_) => {
                    info!(
                        "Timed out sending slot event: stream is not consumed fast enough, \
                         continuing."
                    );
                }
            }
        }
        // `notifications` requires a valid reference to `pubsub_client`, so
        // `notifications` must be dropped before moving `pubsub_client` via
        // `shutdown()`.
        drop(notifications);
        unsubscribe().await;
        pubsub_client.shutdown().await?;
        Ok(())
    });

    (ReceiverStream::new(rx), handle)
}

fn map_websocket_update_to_slot_event(update: SlotUpdate) -> Option<SlotEvent> {
    match update {
        SlotUpdate::FirstShredReceived { slot, .. } => Some(SlotEvent::Start(slot)),
        SlotUpdate::Completed { slot, .. } => Some(SlotEvent::End(slot)),
        _ => None,
    }
}

    // Estimate the current slot from recent slot notifications.
    #[allow(clippy::arithmetic_side_effects)]
    pub fn estimate_current_slot(&self) -> Slot {
        let mut recent_slots: Vec<SlotEvent> = self.0.iter().cloned().collect();
        assert!(
            !recent_slots.is_empty(),
            "method must be called after at least one record."
        );
        recent_slots.sort_by(|a, b| {
            a.slot()
                .cmp(&b.slot())
                .then_with(|| b.is_start().cmp(&a.is_start())) // true before false
        });

        // Validators can broadcast invalid blocks that are far in the future so check if the
        // current slot is in line with the recent progression.
        let max_index = recent_slots.len() - 1;
        let median_index = max_index / 2;
        let median_recent_slot = recent_slots[median_index].slot();
        let expected_current_slot = median_recent_slot + (max_index - median_index) as u64;
        let max_reasonable_current_slot = expected_current_slot + MAX_SLOT_SKIP_DISTANCE;
