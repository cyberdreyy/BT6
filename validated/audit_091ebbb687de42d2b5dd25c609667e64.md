The README explicitly confirms the relevant invariant:

> "NOTE: Guarantees are based on the no-slashing condition. Once slashing is introduced, the contract will no longer provide some guarantees."

This directly addresses the mechanism the question relies on.

## Analysis

The claimed vulnerability requires that after a failed `on_stake_action` restake, the actual on-chain `env::account_locked_balance()` can drop below the value recorded in `self.last_total_balance` purely from the failed-stake/corrective-unstake sequence, causing `internal_ping`'s assert at [1](#0-0)  to permanently trip.

Tracing the actual mechanics:
- `internal_restake` issues a `stake()` action followed by a callback `on_stake_action` [2](#0-1) .
- If the stake action fails and locked balance is still positive, `on_stake_action` issues a corrective `stake(0, ...)` (unstake everything) [3](#0-2) .
- Neither `internal_restake` nor `on_stake_action` write to `last_total_balance`, `total_staked_balance`, or any account row — they only submit promises. This is a `Promise::stake` action on the **same account** (`env::current_account_id()`), and NEAR's protocol conserves an account's `account_locked_balance() + account_balance()` sum across stake/unstake transitions on that account absent slashing: staking only reclassifies funds already inside the account from unlocked to locked and vice versa, it does not move funds out of the account.
- Therefore, whether the corrective unstake(0) has fully "unwound" by the time `withdraw_all`'s `internal_ping` runs is irrelevant to the sum `env::account_locked_balance() + env::account_balance()`: that sum stays constant through the whole stake/fail/unstake sequence, so `total_balance` in `internal_ping` cannot fall below `last_total_balance` from this cause alone.
- The only way the sum genuinely decreases is validator slashing, which the contract's own README explicitly excludes from its guarantees: "Guarantees are based on the no-slashing condition." [4](#0-3) 

The question's proof idea relies on the test-only `Emulator` helper (`skip_epochs`, which independently mutates `self.locked_amount` without modeling protocol conservation) to artificially fabricate a lower locked balance — that emulator behavior is a simplification for reward-simulation tests, not a model of real protocol semantics, and is explicitly out of scope (`**/tests.rs`, `#[cfg(test)]` blocks, `test_utils.rs`). No unprivileged attacker action (deposit, stake, unstake, or triggering a promise failure) can, under real NEAR runtime semantics, cause `account_locked_balance() + account_balance()` to fall below the pool's own prior recorded balance without an actual slashing event, which is outside this repo's control and outside the threat model (rejecting "malicious validators, nodes" and infra-level causes).

```rust
    pub fn on_stake_action(&mut self) {
        assert_eq!(
            env::current_account_id(),
            env::predecessor_account_id(),
            "Can be called only as a callback"
        );

        assert_eq!(
            env::promise_results_count(),
            1,
            "Contract expected a result on the callback"
        );
        let stake_action_succeeded = match env::promise_result(0) {
            PromiseResult::Successful(_) => true,
            _ => false,
        };

        // If the stake action failed and the current locked amount is positive, then the contract
        // has to unstake.
        if !stake_action_succeeded && env::account_locked_balance() > 0 {
            Promise::new(env::current_account_id()).stake(0, self.stake_public_key.clone());
        }
    }
```
