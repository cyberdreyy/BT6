### Title
View-role users can read all bridge OutgoingToken secrets via /v2/bridge_types Index - ([File: core/web/router.go])

### Summary
The `GET /v2/bridge_types` route only requires generic authentication (any session/token role) via `paginatedRequest(bt.Index)`, unlike the mutating bridge routes which use `auth.RequiresEditRole`. `BridgeTypesController.Index` builds its response with `presenters.NewBridgeResource`, which unconditionally includes the bridge's `OutgoingToken` field, so any authenticated low-privileged (view-role) user can enumerate all bridges' outgoing tokens.

### Finding Description
`v2Routes` registers the bridge index endpoint without a role check: `authv2.GET("/bridge_types", paginatedRequest(bt.Index))`, while `Create`, `Update`, and `Destroy` are wrapped with `auth.RequiresEditRole` [1](#0-0) . The `authv2` group itself only requires successful authentication (token or session), not a specific role [2](#0-1) .

`BridgeTypesController.Index` fetches bridges from the ORM and maps each one through `presenters.NewBridgeResource` before returning them in the paginated response [3](#0-2) .

`presenters.BridgeResource` and `NewBridgeResource` include `OutgoingToken` as a plain, non-redacted field for every bridge, with no role-based filtering or redaction logic — only `IncomingToken` is commented as "only provided when creating a Bridge" (and even that comment isn't actually enforced by any conditional code, though `Index`/`Show` don't set it since `bta.IncomingToken` is separate from the persisted `BridgeType`) [4](#0-3) .

Since the endpoint lacks a `RequiresEditRole`/`RequiresAdminRole` wrapper, a view-role user's valid session or API token passes `Authenticate` and reaches `Index` unimpeded, receiving `OutgoingToken` for every bridge in the paginated page (e.g., `?size=50`).

### Impact Explanation
This is a credential/secret disclosure vulnerability: `OutgoingToken` is the credential a bridge adapter uses to authenticate outgoing job-run callbacks back into the Chainlink node. A view-role (read-only) user, who should not be able to perform any bridge-related actions, can harvest every bridge's `OutgoingToken` in bulk through simple pagination, then use those tokens to submit forged/unauthorized bridge task results into node job pipelines — impersonating any external adapter and potentially manipulating job outcomes or fund-moving OCR/VRF/keeper flows fed by those bridges. This matches the "unauthorized secret/key disclosure leading to request impersonation" bounty class.

### Likelihood Explanation
Very high likelihood/trivial to exploit: it only requires a legitimately provisioned view-role session or API token (the lowest privilege tier that can still authenticate to `/v2/*`), and a single `GET /v2/bridge_types?size=<N>` request per page. No timing, race conditions, or special setup needed; it is fully repeatable and works for as many bridges as exist by paging through results.

### Recommendation
Wrap the bridge index and show routes with an appropriate role check (at minimum `auth.RequiresEditRole`, matching the mutating routes), or strip `OutgoingToken` from the `BridgeResource` returned by `Index`/`Show` for non-privileged roles (e.g., add a redacted presenter variant analogous to how `IncomingToken` is only populated on `Create`). The safest fix is to never include `OutgoingToken` in read responses at all and instead expose it only once at creation/rotation time, consistent with the existing `IncomingToken` handling pattern in `core/web/bridge_types_controller.go`.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/bridge_types_controller_test.go`):
1. Start `cltest.NewApplication`, seed 2+ `bridges.BridgeType` rows via `orm.CreateBridgeType` with distinct `OutgoingToken` values (as in `setupBridgeControllerIndex`).
2. Create an HTTP client authenticated with a **view**-role session/API token instead of the default admin client (`app.NewHTTPClient` with a view-role user, mirroring patterns in other role-based tests in the repo, e.g. `cltest` helpers for view role users).
3. Call `client.Get("/v2/bridge_types?size=50")`.
4. Assert `resp.StatusCode == http.StatusOK` (not `403 Forbidden`).
5. Parse the paginated response into `[]presenters.BridgeResource` via `web.ParsePaginatedResponse`.
6. Assert that `resources[i].OutgoingToken` equals the seeded `bt[i].OutgoingToken` values for every bridge — demonstrating that a view-role user received unredacted outgoing credentials for all bridges.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}
