## Analysis

The finding is valid. `EscapeForAnsiC` hex-escapes every byte `<0x20`, `==0x7F`, or `>0x7F` [1](#0-0) , but `EscapeForPosix` only special-cases a fixed set of shell metacharacters (`` ` " \ $ `` plus a handful of whitespace/glob characters) and otherwise writes every other rune through unmodified via `default: buf.WriteRune(r)` [2](#0-1) , meaning ESC (0x1B) and other control bytes pass through untouched.

`CommandFormatter.FormatLogLine` builds the trace "echo" line by wrapping the (possibly attacker-influenced, first-line-truncated) display command in ANSI-green color codes, then dispatches to `EscapeForPosix` when `posixMode` is true or `EscapeForAnsiC` otherwise [3](#0-2) . This is reachable via `NewScriptGenerator(ScriptGeneratorConfig{PosixEscape:true}).GenerateScript(...)` → `CommandProcessor.writeNormalCommand` → `formatter.FormatLogLine` [4](#0-3) , and `PosixEscape` is wired directly from a job-controllable step input (`posix_escape`) in `script_legacy.go` [5](#0-4) [6](#0-5) .

The existing test suite confirms the divergence is intentional/known for `EscapeForAnsiC` (explicit ESC/CSI hex-escape assertions) [7](#0-6) , but there is no equivalent assertion for `EscapeForPosix`, and the existing `TestGenerateScript_PosixEscape_*` tests in `script_generator_test.go` never test embedded ESC bytes at all [8](#0-7) , so this gap is untested and unmitigated at this layer.

However, I could not find any downstream sanitizer in the trace-processing pipeline (`common/buildlogger`, `helpers/trace`, `network/trace.go`) that strips raw ANSI/control bytes from job stdout generically — the wrap chain there only does token/URL/phrase masking and timestamping, not ANSI stripping [9](#0-8) . GitLab's web trace viewer does sanitize/interpret ANSI codes for rendering rather than executing raw terminal control sequences, but this specific escaping layer is documented by its own comments as the defense against "clearing the screen or rewriting logs using ANSI escape sequences" [10](#0-9) , so the omission in the POSIX path is a real inconsistency, not something covered elsewhere in this codebase.

### Title
EscapeForPosix fails to neutralize raw ESC/control bytes, unlike EscapeForAnsiC - (File: functions/script_legacy/internal/escape.go)

### Summary
`EscapeForAnsiC` hex-escapes all control bytes (0x00–0x1F, 0x7F, >0x7F) to block terminal manipulation, but `EscapeForPosix` only escapes a small fixed set of shell metacharacters and lets ESC (0x1B) and other control bytes pass through raw. When a step is run with `PosixEscape`/`posix_escape` enabled, a command whose text (or first line, since multi-line commands are truncated for display) contains embedded ANSI/CSI escape sequences will have those raw bytes `echo`ed verbatim into the trace stream.

### Finding Description
`FormatLogLine` produces the `echo`-based trace log line and picks the escaper based on `posixMode` [11](#0-10) . `EscapeForPosix`'s `default` branch performs no filtering of non-listed runes, including control characters like ESC [12](#0-11) , whereas `EscapeForAnsiC` explicitly hex-escapes them for exactly this purpose [1](#0-0) . The command text used in the log line comes from the job's own script/step content (`getDisplayCommand`, which shows the full command or the truncated first line for multi-line commands) [13](#0-12) , which is attacker-controlled input (the CI job author supplies the `script` input array in `script_legacy.go`) [14](#0-13) . Since `posix_escape` is a job-facing step input with no privilege restriction [5](#0-4) , an attacker fully controls both the escaping mode and the payload content, and no other layer in the traced pipeline strips raw ANSI/control bytes from stdout before it's shipped as trace content [9](#0-8) .

### Impact Explanation
When `posix_escape` is enabled, a job can embed ESC-prefixed CSI sequences (e.g., `\x1b[2K` clear-line, `\x1b[nA` cursor-up) in a command string. The generated script `echo`s these raw bytes as part of the "$ <command>" trace line before executing the actual command, so a terminal or renderer that interprets ANSI codes could have that echoed line manipulate/overwrite prior trace content — potentially obscuring what command was actually about to run, undermining audit/log integrity for reviewers relying on the trace.

### Likelihood Explanation
Feasible and fully reproducible by any job author: set `posix_escape: true` on the `scriptv2`/`script_legacy` step and include a command string containing literal ESC bytes (e.g. via `printf`-embedded escapes or direct YAML control characters). No special runner privileges are required beyond normal job authoring, and the divergent behavior is deterministic and 100% repeatable given the code path shown.

### Recommendation
Make `EscapeForPosix` hex-escape (or strip) all bytes `<0x20`, `==0x7F`, and non-ASCII bytes the same way `EscapeForAnsiC` does, in addition to its existing metacharacter escaping, so both escaping modes uniformly neutralize control characters before they reach `echo`.

// wrap wraps the underlying writer with "filters". Order here somewhat
// matters, and the order they're instantiated in is the reverse order in which
// writes are processed, e.g. last added filter is the first to process data.
//
// order:
// - sync writer to ensure that multiple writes cannot happen concurrently
// - mask phrases (masker.New)
// - mask sensitive URL parameters (urlsanitizer.New)
// - mask secrets with a prefixed token (tokentanitizer.New)
// - split log lines and add timestamps (timestamper.New)
func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}
