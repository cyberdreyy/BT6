### Title
Attacker inflates `trancheAPRSplitRatio` via a same-buffer AA deposit to mint an over-priced BB (and AA) withdrawal receipt, draining fixed epoch interest from other claimants - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
In the Smilee bug, a single shared metric (utilization) priced two asymmetric products, letting an attacker cheaply push the metric and capture a disproportionate price on the expensive side. The credit-vault analog is `trancheAPRSplitRatio`: when Adaptive Yield Split is active, `_updateSplitRatio` recomputes the AA interest share quadratically from the AA/BB TVL ratio on every deposit and withdraw. `requestWithdraw` then prices the fixed withdrawal receipt (`_underlyings = principal + interest - fees`) using that ratio. Because deposits remain open during the buffer window while withdraw requests are also allowed, a KYC'd lender can deposit into the AA tranche to push the ratio up, then request a BB withdrawal whose per-NAV interest scales with the manipulated ratio, locking an oversized claim against a fixed borrower-interest budget.

### Finding Description
- `_updateSplitRatio` sets `trancheAPRSplitRatio = aux * tvlAARatio / FULL_ALLOC` (≈ `r²`, capped by `AA_RATIO_LIM_UP`/`minAprSplitAYS`) and is invoked by `_deposit` → `_updateSplitRatio(_getAARatio(true))` [1](#0-0)  and `_withdrawOps` [2](#0-1) .
- `requestWithdraw` computes receipt interest as `_amount * totTrancheInterest / _trancheBal`, where `totTrancheInterest = totInterest * (FULL_ALLOC - splitRatio)` for BB [3](#0-2) . BB per-NAV interest is therefore `totInterest * (1 − r·min(r,U)) / ((1−r)·NAV)`, which is monotonically increasing in the AA TVL ratio `r` (equal to `(1+r)·totInterest/NAV` in the uncapped region).
- During the buffer phase both `_deposit` (unpaused, `isEpochRunning == false`) and `requestWithdraw` (`allowBBWithdrawRequest`) are live [4](#0-3) , so the attacker can move `r` with a fresh AA deposit in the same window and immediately lock a BB receipt at the inflated share.
- The receipt is a fixed claim (`creditVault.requestWithdraw(_underlyings, msg.sender, principal)`), but the pool's actual interest income is the fixed `expectedEpochInterest` owed by the borrower. The `interestForOverUnderPerformance += diff` bookkeeping only adjusts *next-epoch* expectations; it does not reduce the current receipt, and pooled claims can exceed collectible interest, so the excess is socialized onto later claimants.

### Impact Explanation
An attacker holding BB tranche tokens (or acquiring them at par) deposits a large AA amount (capital or flash-sourced within the buffer) to drive `r` toward `AA_RATIO_LIM_UP`, roughly doubling BB interest per NAV (`1 + r` factor). They then `requestWithdraw` the BB position, fixing an inflated `principal + interest − fees` claim, and also queue their AA deposit for withdrawal. Since total receipt interest is capped only by the manipulated formula while real income is fixed, other withdrawers of the same epoch are underpaid or the vault/queue becomes insolvent for the difference. Bounded but quantifiable theft of yield: up to `~totInterest × (U − r0)` per epoch, repeatable each epoch.

### Likelihood Explanation
Requires an `isAYSActive` vault (AA/BB TVL-driven split enabled, which is the standard configuration for non-fixed credit vaults) and a KYC-passing lender — both within the allowed attacker profile. No privileged action is needed; the only cost is temporarily parking AA capital through one epoch plus management fees. Guards like `_skimDonatedAssets`, `_guarded`, and `_updateAccounting` do not prevent it because the manipulated deposit is a legitimate, accounted deposit.

### Recommendation
Price withdrawal-request interest using the `trancheAPRSplitRatio` snapshotted at `stopEpoch`/epoch start rather than a ratio mutable by same-window deposits, or gate deposits during the buffer once withdraw requests open (or compute the split ratio for interest attribution from balances excluding deposits made after `epochEndDate`).

### Proof of Concept
Foundry fork test against an AYS-enabled `IdleCDOEpochVariant` + `IdleCreditVault` deployment:

```solidity
// setup: vault with AYS active, epoch stopped, in buffer period
// attacker already holds BB tranche tokens worth navBB_user

// 1. During buffer: deposit large AA position to push AA ratio r up
deal(underlying, attacker, aaDeposit); // sized so r -> AA_RATIO_LIM_UP
vm.startPrank(attacker);
IERC20(underlying).approve(address(cdo), aaDeposit);
cdo.depositAA(aaDeposit);                       // _updateSplitRatio bumps trancheAPRSplitRatio

// 2. Request BB withdraw at inflated per-NAV interest
uint256 bb = IERC20(BBTranche).balanceOf(attacker);
uint256 claimed = cdo.requestWithdraw(bb, BBTranche); // receipt priced off inflated ratio

// 3. Baseline: same flow without step 1 yields claimedBase < claimed
assertGt(claimed, claimedBase); // excess comes from fixed expectedEpochInterest

// 4. Queue AA deposit withdraw as well; attacker exits fully next epoch
cdo.requestWithdraw(IERC20(AATranche).balanceOf(attacker), AATranche);

// 5. After next stopEpoch + borrower repayment, attacker claims;
//    sum of all receipts > NAV + real interest -> last honest claimant underpaid
vm.stopPrank();
```

  function _updateSplitRatio(uint256 tvlAARatio) internal virtual {
    uint256 _minSplit = minAprSplitAYS;
    _minSplit = _minSplit == 0 ? AA_RATIO_LIM_DOWN : _minSplit;

    if (isAYSActive) {
      uint256 aux;
      if (tvlAARatio >= AA_RATIO_LIM_UP) {
        aux = tvlAARatio == FULL_ALLOC ? FULL_ALLOC : AA_RATIO_LIM_UP;
      } else if (tvlAARatio > _minSplit) {
        aux = tvlAARatio;
      } else {
        aux = _minSplit;
      }
      trancheAPRSplitRatio = aux * tvlAARatio / FULL_ALLOC;
    }

  function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);
  }

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
