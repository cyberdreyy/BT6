### Title
v1's `validate_tenure_change_payload` uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, letting a v1 signer sign a duplicate tenure-start block during mixed v1/v2 rollout - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionStateV1::validate_tenure_change_payload` guards against a signer re-signing a competing tenure-start block by calling `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, whereas the newer `SortitionStateV2::validate_tenure_change_payload` calls the strictly broader `signer_db.get_last_signed_block(...)`, which also captures locally-accepted-but-not-yet-globally-accepted blocks. During a mixed-version rollout window, a signer still on v1 that has locally signed a block A in tenure T (but that block has not yet crossed the global-acceptance threshold) will not see `get_last_globally_accepted_block` return `Some(A)`, so the `DuplicateBlockFound` guard is bypassed and the signer can go on to validate and sign a second, conflicting tenure-start block B for the same tenure.

### Finding Description
The uniqueness invariant this check enforces is: *for a given signer, at most one tenure-start (`TenureChange`) block may be signed per tenure*. `SortitionStateV1::validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505-518`) implements this by querying only globally accepted state: [1](#0-0) 
`SortitionStateV2::validate_tenure_change_payload` (`stacks-signer/src/chainstate/v2.rs:340-357`) implements the same guard but deliberately widens it to also cover locally-signed-but-not-yet-globally-accepted blocks, per its own comment ("Only blocks we have signed (locally or globally accepted) count here"): [2](#0-1) 

The version each signer runs is derived purely from that signer's own configured protocol version via `SortitionStateVersion::from_protocol_version`, gated by `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`: [3](#0-2) 
This means during a rollout where some signers have not yet upgraded past `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`, those signers keep running the v1 check.

Exploit flow: an attacker who wins a single miner sortition slot for tenure T proposes block A (a normal `TenureChange` block starting T) which an honest v1-population signer locally accepts/signs, but before A reaches the global-acceptance threshold (e.g., other signers are slow or the attacker/miner simply proposes the fork before enough signatures accumulate), the attacker gossips a second, competing `BlockProposal` B — also a `TenureChange` block for the same tenure T, e.g., a different parent choice or reorg of the mempool contents — to the same signer set. For the v1 signer, `get_last_globally_accepted_block` still returns `None` (A never reached that threshold), so the `DuplicateBlockFound` check at `stacks-signer/src/chainstate/v1.rs:510-518` is skipped and validation proceeds to `Ok(())`. If the rest of validation for B passes, the v1 signer signs both A and B as tenure-start candidates for the same (tenure, height) — violating the intended uniqueness guarantee. A v2 signer, receiving the identical DB state and proposal B, would call `get_last_signed_block` at `stacks-signer/src/chainstate/v2.rs:344-345`, find A (which is locally signed even though not yet globally accepted), and correctly reject B with `DuplicateBlockFound`.

No node-side, StackerDB, or auth-token guard closes this gap: the discrepancy is purely a signer-local decision based on which of the two DB query functions it consults, and this is chosen by the signer's own configured protocol version, not something the node or the message content can constrain.

### Impact Explanation
This breaks the uniqueness/safety property that a signer should sign at most one candidate block per (tenure, height): a fraction of the signer population (v1 stragglers) can be induced to co-sign a second, conflicting tenure-start block for the same tenure that other signers already partially endorsed. If enough v1-population signers are induced this way, block B can also gather a quorum of signatures, producing two conflicting, both-signed tenure-start blocks for the same tenure — a chain split precisely matching the Critical "signer signing a conflicting block" impact category. Because the condition (a locally-but-not-globally accepted block existing for a tenure) is a routine race that occurs during normal mining/signing (any first proposal that has not yet reached full threshold), this is trivially repeatable for any tenure during the rollout window by any single-slot miner who also relays two competing block proposals.

### Likelihood Explanation
Preconditions are: (1) the network is in the mixed-signer rollout window around `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`, with at least one honest signer still running v1 logic; (2) that v1 signer has already locally signed a block A for the current tenure that has not yet reached global acceptance — an ordinary occurrence any time the group signing round hasn't finished; (3) the attacker holds a single miner slot (needed to win sortition and be recognized as the tenure's miner) and can gossip a competing `BlockProposal`/`TenureChange` block to the same signer set. All of this is within the stated unprivileged-attacker capability (one miner slot plus gossip, no signer key, no majority, no auth_token). The rollout window is transient but not rare — it exists for the duration of any staged protocol-version upgrade across the signer set, making the attack readily repeatable during that period.

### Recommendation
Align `SortitionStateV1::validate_tenure_change_payload` with v2 by having it also check `signer_db.get_last_signed_block` (or explicitly OR the results of `get_last_signed_block` and `get_last_globally_accepted_block`) before permitting a second tenure-start block to be validated, so the duplicate-block guard is consistent regardless of which protocol-version branch a signer is running during a mixed-version rollout.

### Proof of Concept
Rust test plan (to be added under `stacks-signer/src/chainstate/tests/v1.rs`, mirroring the existing `stacks-signer/src/chainstate/tests/v2.rs` structure):
1. Construct a `SignerDb` and insert a `BlockInfo` for block A in tenure T with state `LocallyAccepted`/`SelfSigned` such that `get_last_signed_block(&T)` returns `Some(A)` but `get_last_globally_accepted_block(&T)` returns `None` (i.e., do not mark A globally accepted).
2. Build a `TenureChangePayload`/`NakamotoBlock` B that also targets tenure T (same `prev_tenure_consensus_hash`/parent tenure), satisfying all the other preconditions of `validate_tenure_change_payload` (matching parent tenure, `check_tenure_change_confirms_parent` == true, `check_parent_tenure_choice` == true).
3. Call `SortitionStateV1::validate_tenure_change_payload(...)` on this DB/proposal state and assert it returns `Ok(())` — demonstrating the missed duplicate.
4. Call `SortitionStateV2::validate_tenure_change_payload(...)` with an identical DB state (same A record) and assert it returns `Err(RejectReason::DuplicateBlockFound)`, confirming the asymmetry and that v2's broader check is the design fix that v1 lacks.
