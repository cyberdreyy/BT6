### Title
Withdraw requests made before the first epoch are silently excluded from `pendingWithdraws` because `epochEndDate == 0` is conflated with "pool closed" - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.requestWithdraw` treats `IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` as "the pool was successfully closed and all funds were recalled". But `epochEndDate` is also `0` before the very first `startEpoch` — the sentinel is overloaded. The same misclassification of a zero/uninitialized timestamp is the analog of the Carapace bug, where `termEndTime == 0` (borrower hasn't drawn yet) was treated as "expired". Requests recorded in this state skip `pendingWithdraws` accounting and the APR0 path, so the borrower is never asked to fund those receipts at `stopEpoch`, leaving users with unredeemable receipt tokens.

### Finding Description
At `IdleCreditVault.sol:259`:

```solidity
bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0;
```

When `isClosed` is true, the function mints the user a receipt (`_mint(_user, _amount)`, line 275) and burns the CDO's strategy tokens, but deliberately does **not** add `_amount` to `pendingWithdraws` (lines 277–280) and does **not** run the APR0 accounting branch (line 285 checks `unscaledApr == 0 && !isClosed`). The rationale in the comment — "A successfully closed pool already recalled all funds" — is only valid when an epoch actually ran and `stopEpoch(0, 1)` cleared `epochEndDate` to 0.

Before the first `startEpoch`, `epochEndDate` is `0` by initialization, not by closure. A KYC-passed lender can deposit in the initial buffer (`depositAA`/`depositBB` are enabled while `isEpochRunning == false`, per `restoreOperations`/`_afterStopEpoch` flag handling in `IdleCDOEpochVariant.sol:619-630`) and then call `requestWithdraw`. The withdrawal is recorded in `withdrawsRequests`/`withdrawsRequestsByEpoch` (lines 289–293) but never enters `pendingWithdraws`.

At the subsequent `stopEpoch`, the CDO only pulls `pendingWithdraws` (plus interest/principal it accounts for) from the borrower via `collectWithdrawFunds` (lines 411–430). Since this receipt was never added, the borrower is not obligated for it and the strategy holds no funding earmarked for it. When the user later calls `claimWithdrawRequest`, `_transferFundedClaim` (lines 897–907) attempts `underlyingToken.safeTransfer(_user, _amount)` against a strategy balance that was forwarded to the borrower at `startEpoch` — the transfer reverts, permanently freezing the claim, unless the honest borrower voluntarily over-repays.

Additional inconsistency: the request epoch is recorded (`lastWithdrawRequest[_user] = currentEpoch`, line 282), so the user is still forced to wait a full epoch cycle before claiming (line 326) — they bear the delay cost of a normal request while receiving none of its funding guarantee. This also produces cross-request inconsistency: two identical requests made before vs. after the first `startEpoch` get different funding treatment, mirroring the report's "inconsistent lending pool status" impact.

### Impact Explanation
A lender who requests a withdrawal during the initial buffer (or any state where `epochEndDate` is 0 without a true close) permanently loses access to their requested funds: the receipt cannot be claimed because the strategy was never funded for it. The loss is the full request amount, up to the entire deposited TVL if all early depositors request withdrawals before epoch 0 starts. This is a broken "one receipt one payout" invariant caused purely by unprivileged sequencing around honest owner/manager calls.

### Likelihood Explanation
Requires only a normal user depositing and requesting withdrawal before the first epoch — a routine action during the buffer period the protocol explicitly supports. No malicious privileged actor, oracle manipulation, or exotic timing is needed. The freeze persists until pool closure/recovery, and even `finalizeDefaultRecovery` accounting (`defaultPendingClaimBasis`, lines 644–649) will misprice this user's basis because `pendingWithdraws` understates the true borrower obligation.

### Recommendation
Distinguish "closed pool" from "never-started/buffer" state instead of relying on `epochEndDate == 0`. Options:

- Track an explicit `isClosed`/`hasEverRun` flag on the CDO and read that instead of the timestamp sentinel.
- Only skip `pendingWithdraws` accounting when the pool actually ran and was closed via the `_interest == 1` path (e.g., require `epochNumber > 0 || isEpochRunning`-adjacent evidence of a completed lifecycle before treating `epochEndDate == 0` as closed).
- Alternatively, always increment `pendingWithdraws` and let `collectWithdrawFunds` zero it at stop; a closed pool simply never calls it again.

### Proof of Concept
Foundry fork test outline (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
function testPreFirstEpochWithdrawRequestNeverFunded() external {
    // Buffer phase: no epoch has ever run, epochEndDate() == 0
    assertEq(cdoEpoch.epochEndDate(), 0);

    // user1 deposits AA and requests withdraw before first startEpoch
    vm.prank(user1);
    idleCDO.depositAA(10_000 * ONE_SCALE);
    uint256 mintedAA = AAtranche.balanceOf(user1);

    vm.prank(user1);
    cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // BUG: request recorded but pendingWithdraws is still 0
    assertGt(strategy.withdrawsRequests(user1), 0);
    assertEq(strategy.pendingWithdraws(), 0); // <- misclassification

    // Manager starts epoch 0; funds (incl. user1's) go to borrower,
    // borrower is only obligated for pendingWithdraws + interest at stop.
    _startEpochAndCheckPrices(0);
    uint256 owed = strategyToken.balanceOf(address(cdoEpoch)) + cdoEpoch.expectedEpochInterest();
    deal(defaultUnderlying, borrower, owed);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), owed);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // user1's claim reverts/strategy lacks the funded amount
    vm.prank(user1);
    vm.expectRevert(); // safeTransfer fails: strategy balance < claim
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I was unable to fully trace `IdleCDOEpochVariant.startEpoch`/`stopEpoch` fund-pull internals in this pass (the grep returned only match counts), so the exact revert point (`_transferFundedClaim` vs. `collectWithdrawFunds` bookkeeping) should be confirmed in the PoC; the misclassification at `IdleCreditVault.sol:259` and the skipped `pendingWithdraws` increment at lines 277–280 are directly verified.
