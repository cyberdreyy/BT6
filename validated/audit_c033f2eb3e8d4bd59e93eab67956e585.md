### Title
Settled APR0 withdraw receipts escape the default-recovery haircut and are paid at par, draining value owed to other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Reverb bug is a use-after-free: memory is freed/overwritten but the object's methods still run with attacker-controlled state. The analog in `IdleCreditVault` is a withdraw receipt that has been "freed" from the default-claim accounting (moved out of `apr0Users[user].principal` into `settledPrincipal`/`settledInterest`) yet remains fully payable. `_withdrawClaimAmountsForEpoch` only counts `apr0User.principal` matching `defaultRecoveryEpoch`, so a settled APR0 position contributes zero `claimBasis` to `_claimDefaultedWithdrawRequest`, is never cleared, and is then paid **at par** by `_claimFundedWithdrawRequest` — even though `finalizeDefaultRecovery` already counted that same principal inside `pendingWithdraws`/`totalBasis` and priced it at `defaultRecoveryPrice`.

### Finding Description
- `requestWithdraw` in APR0 mode calls `_requestWithdrawApr0`, which calls `_settleApr0` first (`IdleCreditVault.sol:567-577`). A user who made an APR0 request in epoch N, lets `stopEpoch` bump `epochNumber` to N+1 (which settles the rate via `prepareStopEpochWithApr0` / `apr0RateByEpoch`), and then files a *second* `requestWithdraw` gets their epoch-N receipt moved to `settledPrincipal`/`settledInterest` (`_settleApr0`, lines 545-565) while the new request occupies `principal`/`principalEpoch = N+1`. The aggregate `pendingWithdraws` still includes both amounts (line 279).
- If the borrower defaults during epoch N+1 and the CDO calls `finalizeDefaultRecovery`, `defaultPendingClaimBasis` returns all of `pendingWithdraws` (lines 644-649), so the settled P1 is inside `totalBasis` and `recoveryPrice = reserve/totalBasis` assumes P1 gets only `price`-proportional payment.
- On `claimWithdrawRequest` → `_claimDefaultedWithdrawRequest` → `_withdrawClaimAmountsForEpoch(user, defaultRecoveryEpoch)` (lines 862-881): `normalAmount` is 0 in APR0 mode and `apr0User.principal` is P2 with `principalEpoch == N+1`, so `claimBasis = P2 + rate-interest` only. `settledPrincipal`/`settledInterest` are invisible to the clear.
- `_clearWithdrawClaimForEpoch` then zeroes `principal` and sets `lastWithdrawRequest[user] = 0` (lines 829-836).
- Execution falls through to `_claimFundedWithdrawRequest` (lines 319-350): the epoch gate `epochNumber <= lastWithdrawRequest` passes (0), and `amount = normalAmount(0) + settledPrincipal(P1) + principal(0) + settledInterest(I1)`. The strategy burns the receipt and calls `_transferFundedClaim` for `P1 + I1` at **full value**, while every other defaulted claimant receives only `claimBasis * defaultRecoveryPrice`.

Broken invariant: loss socialization / one-receipt-one-payout. The settled receipt was "freed" from the default-epoch tracking yet its claim still executes at par — the exact UAF shape of the report (stale object surviving after its accounting was cleared).

Guard check: `_transferFundedClaim` (lines 897-907) only protects `defaultRecoveryReserve`; the epoch-1 stopEpoch already collected P1's funding via `collectWithdrawFunds`/`sendInterestAndDeposits`, so non-reserve balance covers the par payout and no revert occurs. The `requestWithdraw` "claim-loss-receipt-first" guard (lines 263-270) only applies when `lossRecoveryPriceByEpoch` is set, not to pending defaults.

### Impact Explanation
The attacker extracts `P1 + I1` at par instead of `(P1 + I1) * recoveryPrice`. The shortfall `= (P1 + I1) * (1 - recoveryPrice)` is socialized onto the remaining defaulted receipt holders and active tranche holders whose NAV was burned to `activeBasis * recoveryPrice` — or it leaves unclaimable reserve dust, making the recovery distribution permanently underpaid relative to the priced basis. With a severe default (e.g., 30% recovery), a user can route the majority of their position through a settled APR0 receipt and recover 100% while others recover 30%.

### Likelihood Explanation
Requires: APR0 mode (`unscaledApr == 0`), two sequential `requestWithdraw` calls in consecutive epochs (the second auto-settles the first), and a borrower default in the second epoch followed by `finalizeDefaultRecovery` and a haircut below par. All attacker actions are unprivileged user calls (`requestWithdraw`, `claimWithdrawRequest` via the CDO); the default and finalization are performed by the honest borrower/manager/owner. Sequencing is fully attacker-controlled; the only external dependency is a default occurring after setup.

### Recommendation
In `_withdrawClaimAmountsForEpoch` (or `_claimDefaultedWithdrawRequest`), include `apr0User.settledPrincipal` and `apr0User.settledInterest` in the defaulted `claimBasis`/`burnAmount`, and clear them in `_clearWithdrawClaimForEpoch` so a settled APR0 receipt is haircut exactly once and cannot be repaid at par by `_claimFundedWithdrawRequest`.
