## Title
Job-controlled `credHelpers` registry keys let a job query the shared runner host's native credential store for arbitrary secrets - (File: `helpers/docker/auth/auth.go`)

## Summary
`readConfigsFromCredentialsHelper` iterates over `config.CredentialHelpers`, a map fully derived from the job-supplied `DOCKER_AUTH_CONFIG` CI/CD variable, and for every `registry` key calls `credentials.NewNativeStore(config, helper).Get(registry)`. Only the helper *binary name* is validated against path traversal; the `registry` lookup key is never validated against the job's own registries, so a job can query the host's native OS credential store (keychain/wincred/secretservice/pass) for arbitrary key strings.

## Finding Description
`readConfigsFromCredentialsHelper` is reached from `readConfigsFromReader` → `getUserConfiguration(dockerAuthConfig)` → `Resolver.AllConfigs`/`ConfigForImage`, which are invoked by `executors/docker/internal/pull/manager.go`'s `resolveAuthConfigForImage` using `m.config.AuthConfig`, i.e. the job-provided `DOCKER_AUTH_CONFIG` string. [1](#0-0) [2](#0-1) 

The only protection applied is:
```
if helper != filepath.Base(helper) {
    return nil, errPathTraversal
}
```
which stops path traversal on the helper binary name, but does nothing to restrict the `registry` value used as the lookup key passed to `store.Get(registry)`. [3](#0-2) 

`credentials.NewNativeStore(config, helper)` invokes an OS-level `docker-credential-<helper>` binary from the runner host's `PATH`, in the context of the runner process/user, and `Get(registry)` queries that binary's backing store (macOS Keychain, Windows Credential Manager, Secret Service, `pass`, etc.) for whatever is stored under the literal `registry` string — this is a live query against host state, not something scoped to the job's own project. Because the key is fully attacker-chosen, a job can enumerate any registry name it likes (e.g., other tenants' registry hostnames, or well-known hostnames like `docker.io`, `registry.gitlab.com`, an internal mirror) and retrieve whatever credentials the host-level helper happens to have stored for that key — including entries left over from another job's `docker login`, or from the runner administrator's own configuration, on a shared runner host.

This differs from the documented `~/.docker/config.json` sharing path (where every job legitimately sees every plain `auths` entry in the runner's home dir config, a documented precedence behavior) in that here the job supplies its own arbitrary `credHelpers` map and helper name via `DOCKER_AUTH_CONFIG`, actively triggering subprocess calls into the host's native secret store with attacker-chosen keys, rather than passively reading a fixed admin-provisioned file.

## Impact Explanation
On shared runners that reuse the same host/VM across jobs from different projects/tenants (any executor where the parsing code runs in the runner's own host process — this includes docker executor's control-plane process, plus shell/ssh/virtualbox/parallels executors), an attacker's job can retrieve any credential the host's native credential-helper backing store holds under a guessed/known key, even if that credential was never intended for the attacker's project. This is a concrete cross-tenant credential-exfiltration vector limited to environments where such a native credential helper is configured and populated on the shared host.

## Likelihood Explanation
Exploitability requires: (1) the runner host has a native credential-helper binary available (e.g., `docker-credential-pass`, `-wincred`, `-osxkeychain`, `-secretservice`, or a cloud helper) that other jobs/administrators have populated with entries, and (2) the attacker can set `DOCKER_AUTH_CONFIG` (a standard CI/CD variable any pipeline author can set unless restricted). No path traversal or other bypass is needed — the attack is a direct, repeatable dictionary/guessing attack over registry hostnames, requiring no privileged access.

## Recommendation
Restrict the credential-helper lookup so a job can only obtain credentials for registries it actually needs (e.g., only query `store.Get(registry)` for registries that also appear as `image`/`services` references in that job, or require an explicit allow-list), and/or disallow job-supplied `credHelpers`/`credsStore` entirely for `DOCKER_AUTH_CONFIG`, restricting that field to the runner administrator's `config.toml`-provided value instead of the job-scoped CI/CD variable. At minimum, treat native-credential-helper invocation from job-supplied `DOCKER_AUTH_CONFIG` as high-risk and document/gate it behind an explicit runner opt-in.

## Proof of Concept
Go unit test idea in `helpers/docker/auth/auth_test.go`:
1. Pre-populate a fake/native credential helper (as already stubbed in tests via `getValidCredentialHelperSuffix`) with an entry for `"victim-registry.internal"` unrelated to the test job.
2. Set `DOCKER_AUTH_CONFIG` = `{"credHelpers": {"victim-registry.internal": "<helper>"}}`.
3. Call `Resolver.AllConfigs`/`readConfigsFromCredentialsHelper` and assert that credentials for `"victim-registry.internal"` are returned even though the job's own image/service list never references that registry — proving the function returns credentials for **any** job-chosen registry key rather than only those explicitly authorized for the current job/project.

```go
func readConfigsFromCredentialsHelper(config *configfile.ConfigFile) (map[string]types.AuthConfig, error) {
	helpersAuths := make(map[string]types.AuthConfig)

	for registry, helper := range config.CredentialHelpers {
		if helper != filepath.Base(helper) {
			// Fail processing if credential helpers attempting path traversal are detected
			return nil, errPathTraversal
		}

		store := credentials.NewNativeStore(config, helper)

		newAuths, err := store.Get(registry)
		if err != nil {
			return nil, err
		}

		helpersAuths[registry] = newAuths
	}

	return helpersAuths, nil
}
```
