### Title
Signer broadcasts a fresh block-acceptance signature after `mark_locally_accepted` is rejected by the terminal-state guard - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit` in `stacks-signer/src/v0/signer.rs` always signs and broadcasts an acceptance once the pre-commit threshold and conflict checks pass, even when `BlockInfo::mark_locally_accepted` fails because the block has already reached a terminal state (`GloballyRejected`/`GloballyAccepted`). Unlike the sibling code path in `handle_block_validate_ok`, which explicitly `return`s when the equivalent `mark_pre_committed` call fails and the block is not already resolved, `handle_block_pre_commit` only logs the failure and falls through to create and send a signature.

### Finding Description
`BlockInfo::check_state` (invoked by `move_to`, which backs `mark_locally_accepted`) is the guard meant to make terminal states ("archived") immutable: [1](#0-0) 
It correctly forbids `LocallyAccepted` from `GloballyRejected` or `GloballyAccepted`.

In `handle_block_pre_commit`, once pre-commit weight crosses threshold, the chainstate re-check and conflict checks run, and then: [2](#0-1) 
If `mark_locally_accepted(false)` returns `Err` (i.e., the state transition was rejected because the block is already `GloballyRejected`), the error is only conditionally logged via `if !block_info.has_reached_consensus() { warn!(...) }` — there is **no `return`**. Execution falls through unconditionally to `create_block_acceptance`, `handle_block_signature`, and `send_block_response`, producing and broadcasting a fresh signed `Accepted` response for a block the signer's own DB already considers terminally, globally rejected.

Contrast this with the sibling handler `handle_block_validate_ok`, which performs the exact same "failed to mark, but consensus may have already been reached" check and explicitly bails out: [3](#0-2) 
That code path returns early (`return;`) unless the block is already `LocallyAccepted`. `handle_block_pre_commit` has no analogous `return`, so it is the one path in the block lifecycle where a "command" (issuing a signature) is not restricted after the "channel" (the block's consensus record) has been archived.

This is directly analogous to the reported bug class: an action (signing/broadcasting) that should be blocked once the entity (block) is in a terminal/archived state (`GloballyRejected`) is not actually blocked — the guard exists (`check_state`) but its failure is swallowed instead of stopping the action.

### Impact Explanation
This breaks the "signed vs. terminal-state" equality the signer relies on: a signer that has already recorded a block as globally rejected can still emit and broadcast a fresh signature/acceptance for that same block if a late-arriving pre-commit crosses the threshold after the rejection was recorded (e.g., pre-commits that arrive out of order, or a delayed threshold crossing that lands after 30%+ rejection weight already flipped the block to `GloballyRejected` via `handle_block_rejection`). That produces a valid signer signature over a block the signer set has already collectively rejected — a "rejection recounted as acceptance" scenario, and it also risks contributing a stray, cryptographically valid signature toward a block that should be dead, potentially helping it cross the signing (not rejection) threshold on the node side against the signer's own recorded verdict. This falls in the Critical impact bucket described (a rejection recounted as an accept / a signer signing a block it has already determined is invalid).

### Likelihood Explanation
This requires only ordinary asynchronous message arrival that the protocol already anticipates (the code comments acknowledge pre-commits/threshold crossings can race with a `mark_globally_rejected` transition — this is exactly why `has_reached_consensus()` is checked at all). No malicious majority or key compromise is needed: a single miner/proposer plus normal gossip timing (fast-arriving late pre-commits, or a slow validation causing a delayed `handle_block_pre_commit` re-evaluation via `should_reevaluate_block`'s `PreCommitted` path) is sufficient to hit the fallthrough. The bug is a missing `return`, not a logic error requiring adversarial control, making it plausibly triggerable by any one-slot miner racing rejection and pre-commit messages.

### Recommendation
In `handle_block_pre_commit`, mirror the pattern used in `handle_block_validate_ok`: when `mark_locally_accepted` fails, check whether the block has already reached consensus (or is otherwise terminally resolved) and `return` immediately instead of falling through to `create_block_acceptance` / `handle_block_signature` / `send_block_response`. Only proceed to sign and broadcast when the state transition actually succeeded.

### Proof of Concept
1. A block `B` is pre-committed to and gathers rejection weight until `handle_block_rejection` calls `block_info.mark_globally_rejected()`, transitioning `B` to `BlockState::GloballyRejected` (see `handle_block_rejection`, `stacks-signer/src/v0/signer.rs` lines 2274-2341, and `mark_globally_rejected` in `stacks-signer/src/signerdb.rs`).
2. A late pre-commit message for `B` (already in flight before the rejection threshold was reached, or replayed via `should_reevaluate_block`'s `PreCommitted` branch) is then delivered to `handle_block_pre_commit`.
3. `signed_self` is still `None` and `valid` is still `true` (set during validation before rejection), so neither early-return guard fires; weight now also crosses the pre-commit threshold (it was already at/above the rejection threshold, so likely also above the accept threshold if some signers pre-committed before flipping to reject).
4. `check_block_against_signer_db_state` may pass (rejection was driven by vote-count, not necessarily chainstate re-check failure), and no fresh conflicting signed block exists, so the conflict guard passes.
5. `block_info.mark_locally_accepted(false)` returns `Err` because `check_state` disallows `GloballyRejected -> LocallyAccepted`. The error is only logged, execution falls through to line 1475-1478, and the signer creates and broadcasts a signed `Accepted` block response for `B`, despite `B` being recorded as `GloballyRejected` in `signer_db`.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
