### Title
Non-`ErrorAuthFailed` errors from `AuthenticateExternalInitiator` short-circuit the `Authenticate` chain and can lock out legitimate session/token users - (core/web/auth/auth.go)

### Summary
`Authenticate` iterates over `authMethod`s and only continues to the next method when the current one returns `auth.ErrorAuthFailed`; any other error (e.g. a wrapped DB error from `FindExternalInitiator`) causes an immediate `break`, so subsequent methods such as `AuthenticateBySession`/`AuthenticateByToken` are never attempted [1](#0-0) . `AuthenticateExternalInitiator` wraps any non-`sql.ErrNoRows` error from `store.FindExternalInitiator` and returns it unchanged as `errors.Wrap(err, "finding external initiator")`, which is not `auth.ErrorAuthFailed` [2](#0-1) .

### Finding Description
The `Authenticate` middleware is designed to try multiple auth strategies in sequence and only fall through to the next strategy on a normalized "auth failed" sentinel (`auth.ErrorAuthFailed`) [3](#0-2) . `AuthenticateBySession` and `AuthenticateByToken` correctly normalize `sql.ErrNoRows`/session-expired conditions to `auth.ErrorAuthFailed` before returning [4](#0-3) , but `AuthenticateExternalInitiator` only normalizes `sql.ErrNoRows`; any other error from `FindExternalInitiator` (e.g. a connection/timeout/driver error) is wrapped and returned as-is [5](#0-4) . Because `Authenticate`'s loop condition is `if !errors.Is(err, auth.ErrorAuthFailed) { break }`, this wrapped error causes the loop to stop before ever invoking the remaining methods in the chain (e.g. `AuthenticateByToken`, `AuthenticateBySession`) if `AuthenticateExternalInitiator` is placed earlier in the method list for a shared route [6](#0-5) . The test file's `authError`/`authSuccess`/`TestRequireAuth_Error` case confirms this exact behavior already exists and is asserted in-repo (a generic error from one method prevents a later successful method from running) [7](#0-6) .

However, I could not confirm from the available code/schema that an attacker-supplied "oversized AccessKey" header actually forces a non-`sql.ErrNoRows` database error out of `FindExternalInitiator` (e.g., whether the underlying column is a fixed-length/constrained type that would reject oversized input at the driver level, as opposed to a `TEXT`/unconstrained column that would just yield zero rows). I was not able to inspect the `external_initiators` table schema or the `FindExternalInitiator` SQL query implementation within the available tool budget to verify this precondition. This is a real gap in my verification, not a confirmed non-issue.

### Impact Explanation
If the precondition holds (an attacker can force `FindExternalInitiator` to return a non-`ErrNoRows`, non-nil error on a route where `AuthenticateExternalInitiator` is chained before session/token auth, e.g. job-run endpoints), the concrete impact is denial of legitimate authentication (availability impact on auth) for other users/tokens on that shared endpoint, and the error text may propagate into the 401 response body depending on `jsonAPIError`'s formatting, which is a potential internal-error/information-disclosure concern. Without confirming the exact `jsonAPIError` implementation and the EI table schema I could not fully verify the information-disclosure sub-claim.

### Likelihood Explanation
The control-flow bug in `Authenticate`/`AuthenticateExternalInitiator` is real and reachable by an unauthenticated/EI-header-holding requester on any route where EI auth is chained with session/token auth. However, the specific attacker-triggerable precondition (crafting a header value that produces a genuine DB-level error rather than a normal no-match `sql.ErrNoRows`) is unconfirmed with the evidence gathered; ordinary primary-key/text lookups by access key typically just miss and return `ErrNoRows`, not a driver error, so likelihood is uncertain and possibly low absent a specific schema constraint (e.g., a fixed-length or typed column) that I could not verify.

### Recommendation
Normalize all `authMethod` implementations, including `AuthenticateExternalInitiator`, to only return `auth.ErrorAuthFailed` for authentication-relevant failures and to return the sentinel (not the wrapped DB error) so that `Authenticate` continues trying the remaining methods regardless of one method's internal failure; log the underlying error server-side but do not let it affect chain control flow or leak into the client response, and ensure `jsonAPIError` for 401s never echoes wrapped internal error strings.

### Proof of Concept
Add a unit test in `core/web/auth/auth_test.go` modeled on `TestRequireAuth_Error`: define a stub `authMethod` (e.g. simulating `AuthenticateExternalInitiator`) that returns a generic wrapped error (not `auth.ErrorAuthFailed`), chain it with `authSuccess` in `webauth.Authenticate(authr, stubEIError, authSuccess)`, and assert that the downstream handler is still invoked (`called == true`) or, if the intended behavior requires a 401, assert the response body does not contain the raw wrapped error string. Additionally, add an integration-level test hitting a real chained route (e.g. `/v2/jobs/:id/runs`) with a stub `Authenticator.FindExternalInitiator` returning a non-`ErrNoRows` error, and a valid session cookie/API token in the same request, asserting the request still succeeds via the session/token path instead of returning 401.

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}
```

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```
