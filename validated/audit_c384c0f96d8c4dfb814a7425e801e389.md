Based on my research, the closest analog to the Balancer pool-token caching bug (a value cached once, later required to exactly match a mutable source of truth, causing permanent operational failure) is in Base's dispute-game anchor-advancement logic.

### Title
Anchor advancement permanently stalls when the `DisputeGameFactory` implementation pair changes after a successor game already exists - (File: `crates/proof/challenge/src/anchor.rs`)

### Summary
`AnchorUpdater::next_game` derives a keyed lookup (`game_lookup_key`) for the successor dispute game using the block-interval/intermediate-interval "pair" resolved from the factory's *current* implementation at query time, then searches the factory for a game whose UUID matches that key. If the factory's implementation (and its pair) is later changed via `setImplementation` after a successor game was already created with the old pair, the keyed lookup permanently stops matching that game.

### Finding Description
`next_game` resolves `(block_interval, intermediate_block_interval)` from the *current* factory implementation via `resolve_intervals`, then computes a deterministic `game_lookup_key` and does a keyed factory search for a game with that UUID: [1](#0-0) 

The code explicitly documents this as an unresolved caching/consistency defect: the pair used to derive the lookup key is a function of "current" factory state rather than the state at the time the target game was actually created, so once the factory's implementation pair diverges from what was used to create an already-existing successor game, the keyed lookup can never match it again: [2](#0-1) 

This mirrors the reported bug class exactly: a value that is expected to remain stable (the pool-tokens set in the original report; here, the factory-implementation-derived interval "pair") is re-derived from a mutable source of truth (`resolve_intervals` reading the live factory) and then required to exactly reproduce a value baked into an already-existing artifact (a previously created dispute game's UUID). Once the source of truth changes, the reproduction can never match again, and the code has no fallback scan path — it is described as "a restart no longer clears" the stall.

`poll` further caches `(anchor, address)` in `self.cached_next_game`, short-circuiting subsequent calls to `next_game` while the anchor is unchanged, so the failure to find the successor game repeats on every poll cycle with no self-healing: [3](#0-2) 

### Impact Explanation
If a legitimate `setImplementation` call on the `DisputeGameFactory` changes the game-type's implementation (and therefore its interval pair) after a successor game already exists under the old pair, `AnchorUpdater::poll` permanently fails to locate that successor game. The anchor root then never advances past the stale anchor, which halts progress of the anchor-state pipeline that downstream dispute resolution and proof recovery depend on (`crates/proof/proposer/src/proof_recovery.rs` walks forward from the anchor). This is a durable halt of a core proving/output-root-finalization component, not a resource-only or transient issue — it requires manual/code intervention to unstick per the author's own note.

### Likelihood Explanation
The trigger is a normal governance/operational action (updating the dispute game implementation), which is an expected, periodically-occurring event in a live OP-Stack-style deployment (e.g., during an upgrade). Any successor game created before that implementation update, combined with the update landing before the challenger processes it, deterministically reproduces the stall — the code comment itself confirms this is a known, reachable limitation rather than a hypothetical edge case.

### Recommendation
Do not derive the lookup pair solely from the factory's current implementation. Either (a) persist/derive the pair actually used at game-creation time (e.g., read it from the game's own on-chain parameters rather than recomputing it), or (b) fall back to scanning factory indices from the anchor forward when the keyed lookup misses, so an implementation-pair change cannot permanently orphan an already-created successor game.

### Proof of Concept
1. Dispute games are created and resolved normally under interval pair `P1`.
2. `DisputeGameFactory.setImplementation()` changes the game type's implementation, and the interval pair for new games becomes `P2`, but a successor game to the current anchor was already created under `P1` before the change (or is created after using `P1`-derived timing while the factory now reports `P2`).
3. `AnchorUpdater::next_game` resolves the *current* (`P2`) pair via `resolve_intervals`, builds `game_lookup_key` with `P2`, and searches the factory — the search never matches the `P1`-keyed game.
4. `poll` repeatedly returns `None` from `next_game`; `cached_next_game` stays `None`; the anchor is never advanced, confirmed by the existing test demonstrating the pre-activation/post-activation cadence mismatch: [4](#0-3) .

    /// Finds the next game after the anchor game and advances the anchor root if it is ready.
    pub async fn poll<T: TxManager>(
        &mut self,
        verifier_client: &dyn AggregateVerifierClient,
        submitter: &ChallengeSubmitter<T>,
    ) {
        let anchor = match self.anchor_registry_client.anchor_snapshot().await {
            Ok(anchor) => anchor,
            Err(e) => {
                warn!(error = %e, "failed to read anchor snapshot for anchor update");
                return;
            }
        };

        let game_address = match self.cached_next_game {
            Some((cached_anchor, address)) if cached_anchor == anchor => address,
            _ => {
                self.cached_next_game = None;
                let Some(address) =
                    self.next_game(verifier_client, anchor.anchor_root, anchor.anchor_game).await
                else {
                    return;
                };
                self.cached_next_game = Some((anchor, address));
                address
            }
        };

    async fn next_game(
        &self,
        verifier_client: &dyn AggregateVerifierClient,
        anchor_root: AnchorRoot,
        anchor_game: Address,
    ) -> Option<Address> {
        // Resolved from the anchor block, which is where the next game's range starts:
        // the verifier switches to a shorter cadence at the Denim activation block, so a
        // pair cached at startup silently stops matching any game past the boundary.
        //
        // Known limitation: this reads the factory's *current* implementation, but the
        // successor game may already exist and have been created with an older pair. Across a
        // `setImplementation` that changes the pair the keyed lookup never matches and the
        // anchor stalls at "next anchor game not found", which a restart no longer clears.
        // Denim itself does not trigger it (the pair is a function of the starting block,
        // not of which implementation is current). Fix by scanning the factory from the
        // anchor index when the keyed lookup misses, if it ever bites.
        let (block_interval, intermediate_block_interval) = match resolve_intervals(
            self.factory_client.as_ref(),
            verifier_client,
            self.game_type,
            anchor_root.l2_block_number,
        )
        .await
        {
            Ok(intervals) => intervals,
            Err(e) => {
                warn!(error = %e, "failed to resolve anchor update intervals");
                return None;
            }
        };

        let blocks = match game_lookup_blocks(
            anchor_root.l2_block_number,
            block_interval,
            intermediate_block_interval,
        ) {
            Ok(blocks) => blocks,
            Err(e) => {
                warn!(error = %e, "invalid anchor update lookup blocks");
                return None;
            }
        };

    async fn poll_finds_next_game_built_with_fast_intervals() {
        // The anchor sits exactly at the Denim activation block, so the next game
        // spans FAST_BLOCK_INTERVAL and carries two intermediate roots instead of
        // one. Its UUID is only reproducible with the post-activation pair.
        let game = addr(1);
        let tx_hash = B256::repeat_byte(0xDD);
        let factory = Arc::new(MockDisputeGameFactory::new(vec![]));
        let anchor_registry = Arc::new(MockAnchorStateRegistry::new(Address::ZERO));
        anchor_registry.snapshot.lock().unwrap().anchor_root.l2_block_number =
            FAST_ACTIVATION_BLOCK;

        let mut l2 = MockL2Provider::default();
        let roots: Vec<B256> = (1..=FAST_BLOCK_INTERVAL / FAST_INTERMEDIATE_BLOCK_INTERVAL)
            .map(|i| {
                insert_l2_block(
                    &mut l2,
                    FAST_ACTIVATION_BLOCK + i * FAST_INTERMEDIATE_BLOCK_INTERVAL,
                )
            })
            .collect();
        // Present so the slow-cadence run fails on a UUID mismatch rather than on a
        // missing output root.
        insert_l2_block(&mut l2, FAST_ACTIVATION_BLOCK + BLOCK_INTERVAL);
        let l2 = Arc::new(l2);

        let extra_data = game_lookup_key(
            FAST_ACTIVATION_BLOCK,
            ASR_ADDRESS,
            FAST_BLOCK_INTERVAL,
            FAST_INTERMEDIATE_BLOCK_INTERVAL,
            &roots,
        )
        .unwrap()
        .extra_data;
        factory.insert_uuid_game(GAME_TYPE, *roots.last().unwrap(), extra_data, game);

        let mut state = mock_state(
            GameStatus::DefenderWins,
            Address::ZERO,
            FAST_ACTIVATION_BLOCK + FAST_BLOCK_INTERVAL,
        );
        state.anchor_state_registry = ASR_ADDRESS;
        let games = HashMap::from([(game, state)]);

        let denim_verifier = verifier(games.clone()).with_fast_intervals(
            FAST_ACTIVATION_BLOCK,
            FAST_BLOCK_INTERVAL,
            FAST_INTERMEDIATE_BLOCK_INTERVAL,
        );
        let (denim_submitter, tx_manager) = submitter(vec![tx_success(tx_hash)]);
        let mut denim_updater =
            updater(Arc::clone(&factory), Arc::clone(&anchor_registry), Arc::clone(&l2));
        denim_updater.poll(&denim_verifier, &denim_submitter).await;

        let calls = tx_manager.recorded_calls();
        assert_eq!(calls.len(), 1, "anchor should advance to the post-activation game");
        assert_eq!(calls[0].tx_data, encode_set_anchor_state_calldata(game));

        // Same fixture against a verifier that never switches cadence — the pair the
        // old startup-cached updater would have used. It must not find the game.
        let (stale_submitter, tx_manager) = submitter(vec![tx_success(tx_hash)]);
        let mut stale_updater = updater(factory, anchor_registry, l2);
        stale_updater.poll(&verifier(games), &stale_submitter).await;

        assert!(
            tx_manager.recorded_calls().is_empty(),
            "slow-cadence intervals build a different UUID, so no game is found"
        );
