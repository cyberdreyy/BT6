### Title
Signer weight is double-tallied into both `total_weight_rejected` and `total_weight_approved` for the same block, letting a single equivocating signer trigger a premature/false global-rejection (or spurious acceptance race) - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` tallies each signer's weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, gated by two *different* "already counted" sets (`gathered_signatures` vs `responded_signers`). A single signer that sends a `Rejected` response and later a valid `Accepted` response for the same block (or vice versa) has its weight counted in **both** tallies, breaking the invariant that a signer's weight should count toward at most one side of the accept/reject tally for a given block.

### Finding Description
In the `Accepted` branch, the "already counted" guard is `!block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

In the `Rejected` branch, the "already counted" guard is a *different* set, `block.responded_signers.insert(slot_id)`: [2](#0-1) 

Both branches unconditionally add the entry to `responded_signers` (`block.responded_signers.insert(slot_id)` appears in the accept branch too, at line 465), but the accept branch's weight-add condition checks `gathered_signatures`, not `responded_signers`. Consequently:

- Slot `X` sends `BlockResponse::Rejected` first → `responded_signers.insert(X)` succeeds → `total_weight_rejected += weight(X)`.
- Slot `X` later sends `BlockResponse::Accepted` (a validly recoverable signature) for the *same* block → since `gathered_signatures` does not yet contain `X`, the code adds `weight(X)` to `total_weight_approved` as well, and inserts `X` into `gathered_signatures`.

Now `weight(X)` is present in both `total_weight_rejected` and `total_weight_approved` simultaneously for the same `block_sighash`. Nothing in either branch removes a slot's weight from the opposite tally when it flips its vote, so `total_weight_rejected + total_weight_approved` can exceed `total_weight` (or, more importantly, both the 70% approval threshold and the 30%-blocking-minority rejection threshold can be crossed based on overlapping, non-disjoint weight).

These aggregated counters are read directly by the miner's `SignerCoordinator::get_block_status` loop to decide "signers rejected" vs "block accepted," with no re-derivation from the underlying per-signer verdict sets: [3](#0-2) 

This is precisely the "aggregated-weight vs verified-accepts" equality the scan is looking for: `total_weight_rejected` no longer represents the weight of signers who still hold that verdict — it retains weight from a signer who has since produced a valid, verified signature accepting the block. A signer flip-flopping (equivocating) between reject and accept for one block therefore corrupts the global tally without needing majority collusion; only the flipping signer's own message pair is required.

### Impact Explanation
Because the miner's decision in `get_block_status` treats `total_weight_rejected.saturating_add(weight_threshold) > total_weight` as proof that "70% is now impossible" and immediately returns `SignersRejected` (aborting the proposal and excluding transactions as "problematic"/"temporarily excluded"), a stale rejection weight that is simultaneously backed by a real, valid acceptance signature can push the miner into declaring the block dead and discarding transactions, even though enough weight (including the double-counted signer, now actually signing) may in fact have legitimately signed. This is a liveness/miscount defect: the aggregated rejection count is no longer a faithful representation of "signers who currently reject this block," which can wedge or stall block finalization and cause transactions to be needlessly excluded from future proposals (`temporarily_excluded_txids`/`permanently_excluded_txids`), a real disruption of an active session comparable to the report's "unauthorized sender disrupts active session" bug class — except here the disruption comes from a single signer's own conflicting-but-individually-valid messages bypassing the intended one-verdict-per-signer accounting.

### Likelihood Explanation
Reaching this requires only one signer (not a majority) sending two legitimate, correctly-signed StackerDB chunks for the same `signer_signature_hash`: first a `BlockResponse::Rejected`, then later a `BlockResponse::Accepted` (both are messages a normal signer client can legitimately produce, e.g., a signer that rejects due to a transient reason and re-evaluates and signs afterward, per the "re-evaluate a prior rejection" flow described in `should_reevaluate_reject_reason`/`determine_response`). No StackerDB or slot-authorization bypass is needed — this is purely a bookkeeping bug in how the two verdict tallies interact once the same slot appears in both categories. It is realistically triggerable in normal signer operation (a signer that legitimately reconsiders and changes its verdict), not just via an actively malicious signer.

### Recommendation
Use a single per-slot verdict-tracking structure (e.g., an enum `{Accepted(sig), Rejected}` keyed by `slot_id`) instead of two independently-gated sets (`gathered_signatures` and `responded_signers`). When a signer's verdict changes from Rejected to Accepted (or vice versa), atomically move its weight from one tally to the other rather than additively contributing to both. Add a test asserting that `total_weight_approved + total_weight_rejected <= total_weight` at all times for a given block.

### Proof of Concept
1. Set up a signer set and a proposed block with `signer_signature_hash = H`.
2. Have signer slot `X` (weight `w`) submit `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `H`. Observe `block.total_weight_rejected += w`.
3. Have the same signer slot `X` submit `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `H`, with a valid signature recoverable to `X`'s registered signing key. Observe `block.total_weight_approved += w` as well (since `gathered_signatures` did not yet contain slot `X`).
4. Confirm via the listener's in-memory `BlockStatus` for `H` that both `total_weight_approved` and `total_weight_rejected` now include `w`, i.e. `total_weight_approved + total_weight_rejected > total_weight_of_participating_signers_excluding_X`, violating the disjointness invariant consumed by `SignerCoordinator::get_block_status`.

Note: This finding was derived from `stackerdb_listener.rs` and `signer_coordinator.rs`; I was not able to independently trace whether `stacks-signer/src/v0/signer.rs` (signer-side) has an equivalent double-counting bug in its own local tallies (e.g. pre-commit weight tracking), since exhaustive review of `signer_state.rs`'s pre-commit accounting was not completed within the available iterations — this should be verified separately if a full-severity assessment is required.
