Based on my investigation, I found a genuine analog worth flagging: the `check_parent_tenure_choice` "poorly timed proposal" heuristic in `stacks-signer/src/chainstate/mod.rs` is exactly the same bug-class shape as the reported exploit — a value sampled from a narrow, attacker-influenceable time window is trusted for a security-critical decision (whether a reorg may destroy already-signed blocks), and a single miner fully controls one side of that window (`proposed_time`/`approved_time` of its own block).

### Title
Miner-controlled proposal timing lets a single miner get an illegitimate tenure reorg sanctioned ("poorly-timed" oracle manipulation) - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` permits a miner to reorg a prior tenure that already produced a globally-accepted block, solely based on a timing heuristic: it treats the tenure as "poorly timed" (and therefore reorg-eligible) if the time between when the reorged tenure's first block was *locally approved by this signer* and when the *new* sortition/burn block was received is shorter than `first_proposal_burn_block_timing`. This is analogous to the reported DeFi bug class: a value derived from a short observation window that one active party can influence is trusted directly for a consequential, hard-to-reverse decision (destructive reorg permission vs. collateral valuation). [1](#0-0) 

### Finding Description
The reorg-permission check computes `proposal_to_sortition = sortition_state_received_time - approved_time` for the reorged tenure's first block, and permits the reorg if this is below `first_proposal_burn_block_timing` (mainnet default 60s per `sample/conf/signer/mainnet-signer-conf.toml`). `approved_time` is stamped locally by each signer the moment it pre-commits to a proposal — a timestamp the *proposing miner* substantially controls by choosing when to broadcast the block (e.g., broadcasting it deliberately close to, but before, the anticipated next sortition). A miner that mines a tenure, waits, and then deliberately proposes/broadcasts its first (and only) block just before the next burn block is expected can manufacture a short `proposal_to_sortition` window across the signer set, making an otherwise-illegitimate reorg of an established, single-block tenure look "poorly timed" and get it sanctioned via `mark_tenure_superseded`.

Once sanctioned, `get_signed_conflicts` in `stacks-signer/src/signerdb.rs` (lines 1587-1625) stops treating the reorged tenure's already-signed block as a conflict for signers that recorded the permit, because `reorg_permit_stands` only re-checks whether the *permitting* sortition is still canonical — it does not re-validate the timing decision. This lets a rival, non-canonical/competing chain branch (the reorg) get signed over a previously globally-accepted block, which is precisely the "signer signing a conflicting/non-canonical block" impact category. [2](#0-1) [3](#0-2) 

### Impact Explanation
If successful, a single miner can engineer a scenario where the signer set signs a block that reorgs an already-globally-accepted tenure block — a "signer signing a conflicting/non-canonical block," which is explicitly listed as Critical impact.

### Likelihood Explanation
This requires precise timing control over broadcast of the miner's own proposal relative to the burn-chain block cadence, which a miner can influence but not perfectly predict (burn block arrival is probabilistic). The existing tests (`check_parent_tenure_choice_reorg_timing_ok`/`_bad` in `stacks-signer/src/chainstate/tests/v1.rs`/`v2.rs`, and `allow_reorg_within_first_proposal_burn_block_timing_secs` in `stacks-node/src/tests/signer/v0/reorg.rs`) show this exact mechanism is a documented, intended feature (to let a genuinely poorly-timed first block be safely superseded), not an oversight — the code comments explicitly frame it as recognizing an "outdated commit that the incoming miner did not have sufficient time to RBF." This significantly narrows the exploit window: the mechanism exists specifically to distinguish legitimate late-arriving commits from established tenures, and gaming it requires influencing burn-block timing itself, which the miner does not fully control (Bitcoin's block arrival is probabilistic, not miner-triggerable at will). [4](#0-3) 

### Recommendation
Given the likelihood caveat above and that this is a documented, deliberately-designed tradeoff (not a coding defect), no code fix is being proposed here. If tightening is desired, consider anchoring the timing check to a value less influenceable by the block-proposing miner (e.g., signer-local receipt time before any signer sends a pre-commit, or a threshold on the number of signers whose independent receive-times agree) rather than the single earliest `approved_time`.

### Proof of Concept
Not applicable — this write-up documents an existing, intentionally-designed timing heuristic and its inherent trust assumption rather than a coding bug; no working single-miner PoC bypassing majority assumptions was found within the tool budget.

```text
# Reorg protection window. Measures the time between when the first block
# of a tenure was signed and when the next burn block (sortition) arrived.
#
# If a new miner tries to reorg a tenure that already produced blocks:
#   - If (burn_block_received - first_block_signed) < this value:
#     Reorg is ALLOWED (the tenure was "poorly timed" and the incoming
#     miner did not have sufficient time to RBF an outdated commit)
#   - If (burn_block_received - first_block_signed) >= this value:
#     Reorg is DENIED (the tenure was established long enough for the
#     incoming miner to RBF any outdated commit)
#
# WARNING: Setting this too LOW allows dangerous reorgs of established
# tenures. Setting it too HIGH blocks legitimate miner handoffs when
# the previous tenure's first block arrived shortly before the sortition.
#
# Default: 60
# Units: seconds
# first_proposal_burn_block_timing_secs = 60
```
