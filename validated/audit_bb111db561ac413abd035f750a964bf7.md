### Title
Reorg-permission window uses a single fixed, locally-timestamped threshold (`first_proposal_burn_block_timing`) causing signers to reach conflicting verdicts on the same reorg - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a new miner is allowed to "reorg" (replace) a prior tenure's already-mined block by comparing a single, globally-configured constant, `first_proposal_burn_block_timing`, against a value computed from each signer's own locally-recorded wall-clock timestamps (`sortition_state_received_time` and `approved_time`). This mirrors the Chainlink analog: one fixed "heartbeat"-like threshold is applied uniformly to an event whose real-world timing is not uniform (network propagation delay, per-signer clock skew, per-signer message ordering). Because the inputs to the comparison are purely local rather than consensus data, different honest signers computing the same boolean predicate can land on opposite sides of the threshold and reach opposite verdicts on whether the same reorg is valid.

### Finding Description
`check_parent_tenure_choice` at [1](#0-0)  permits a reorg unconditionally only when the parent tenure equals the prior sortition. Otherwise, for each reorged tenure it computes:

```
proposal_to_sortition = sortition_state_received_time - approved_at
if Duration::from_secs(proposal_to_sortition) < first_proposal_burn_block_timing { allow reorg }
``` [2](#0-1) 

`sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time`, i.e., the *local* time this particular signer process observed/stored the new burn block, and `approved_at` is this signer's own locally recorded time when it (locally) approved the first block of the tenure being reorged. Neither value is embedded in the block, signed, or otherwise synchronized across the signer set — it is derived independently by each of the N signers based on when their own process received the relevant StackerDB/RPC events.

`first_proposal_burn_block_timing` is a single fixed `Duration` taken uniformly from `ProposalEvalConfig` for every signer, every tenure, and every network condition [3](#0-2) , and is invoked from `is_tenure_valid` on every block-proposal evaluation path [4](#0-3) .

Because the comparison mixes a single fixed constant with genuinely non-synchronized, per-signer clock/network-dependent measurements, a miner (a single sortition winner) can craft the timing of its tenure's first block and the following sortition so that the `proposal_to_sortition` value straddles the `first_proposal_burn_block_timing` boundary across the signer population: signers who received the burn-block event slightly earlier (or recorded `approved_at` slightly later, due to ordinary network jitter) will compute a value **below** the threshold and permit the reorg (superseding the old tenure and signing the new miner's competing block), while signers who received the burn-block event slightly later will compute a value **above** the threshold and refuse the reorg (continuing to endorse/extend the old tenure). This directly breaks the "approved-parent vs canonical" equality that the whole signer set is supposed to agree on: some signers end up signing over one branch (the old tenure) while others sign over the new, reorging tenure — a split that produces two sets of validly-collected signer signatures for mutually conflicting blocks at overlapping heights, exactly the class of issue called out as Critical ("a signer signing an invalid, non-canonical, or conflicting block").

This is the direct analog of the Chainlink M-1 bug: instead of one heartbeat value being wrong for many price feeds with different real update cadences, one timing threshold is wrong for many signers with different real local-clock/propagation cadences, and the mismatch is exploitable by whoever controls the timing of the tenure transition (the single winning miner), not by a majority of signers.

### Impact Explanation
If the signer population splits on `check_parent_tenure_choice`'s verdict, part of the signer set will sign/endorse the superseded (non-canonical) tenure's blocks while the rest sign/endorse the reorging tenure's blocks. Depending on the split and the per-signer weight distribution, this can (a) let a non-canonical/conflicting block accumulate enough weight to be treated as accepted by the stacks-node coordinator (`stacks-node/src/nakamoto_node/signer_coordinator.rs` totals weight purely from whichever responses arrive, per [5](#0-4) ), producing a signed conflicting/non-canonical block, or (b) wedge the network in a state where neither branch reaches threshold weight, stalling block production (liveness wedge) until the timeout logic elsewhere resolves it. Both outcomes map to explicit in-scope Critical/High impacts.

### Likelihood Explanation
Triggering the split requires only the ordinary timing precision available to the single sortition-winning miner (choosing when to broadcast its first block relative to the coming burn block) plus naturally occurring propagation/clock skew across the signer set — no majority collusion, no key compromise, and no StackerDB-sync-mechanics exploit is needed. The comment in the code itself acknowledges timing is measured from local, non-authoritative sources and that "this value *should* always be some, but try to do the best we can if it isn't" [6](#0-5) , indicating the authors were aware this is a best-effort/approximate check rather than a deterministic, consensus-safe one.

### Recommendation
Replace the purely local, single-fixed-threshold comparison with either (a) a value anchored to consensus data (e.g., the burn header timestamp already available on `SortitionData.burn_header_timestamp`, compared against a block's own signed proposal timestamp) so all signers derive the same input deterministically, or (b) widen the decision with a safety margin/consensus round so that a signer only permits a reorg once it can confirm (via node RPC or a majority-agreed value) that other signers computed the same side of the threshold, rather than trusting its own local receive/approve timestamps unilaterally.

### Proof of Concept
Conceptual PoC (cannot fully execute without live multi-signer harness, but derivable directly from the code path):
1. Miner A mines the first (and only) block of tenure T at burn height H.
2. Miner B wins the next sortition at H+1 and proposes a competing tenure T' that does not build on T (a reorg).
3. Miner B times its proposal/broadcast so that, across the 5 signers, the locally recorded `sortition_state_received_time` for H+1 and `approved_time` for T's block differ by an amount close to `first_proposal_burn_block_timing` (default 60s, see `DEFAULT_FIRST_PROPOSAL_BURN_BLOCK_TIMING_SECS` in `stacks-signer/src/config.rs`).
4. Signers whose `sortition_state_received_time - approved_time < 60s` call `check_parent_tenure_choice` → `Ok(true)` and sign T' (see lines 259-274 of `chainstate/mod.rs`).
5. Signers whose measured delta is `>= 60s` call the same function → `Ok(false)` and refuse T', continuing to endorse T.
6. Both partial signature sets are gathered independently by the node's `StackerDBListener`/`SignerCoordinator` weight tally (`stacks-node/src/nakamoto_node/stackerdb_listener.rs` lines ~443-470), which has no cross-check that all contributing signers agreed on the *same* parent-tenure choice before counting weight toward `total_weight_approved`.
