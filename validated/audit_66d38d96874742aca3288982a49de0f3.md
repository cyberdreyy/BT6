### Title
`grantRole` on B-20 Asset/Stablecoin precompiles accepts `account == address(0)`, letting the sole admin permanently orphan `DEFAULT_ADMIN_ROLE` and lock all role-gated operations - (File: `crates/common/precompiles/src/b20_asset/logic/v1.rs`, `crates/common/precompiles/src/b20_asset/logic/v2.rs`, `crates/common/precompiles/src/b20_stablecoin/logic/v1.rs`, `crates/common/precompiles/src/b20_stablecoin/logic/v2.rs`)

### Summary
The B-20 asset and stablecoin precompile role-management path (`grantRole` → `grant_role` → `grant_role_unchecked`) never validates that `account != address(0)`, unlike every value-moving operation in the same contracts (`transfer`, `transferFrom`, `mint`, `approve`), which explicitly reject `Address::ZERO`. This asymmetry lets the sole `DEFAULT_ADMIN_ROLE` holder grant that role to the zero address, after which the real admin can renounce/be revoked without tripping the "last admin" guard, permanently orphaning all admin-gated token operations.

### Finding Description
`grant_role_unchecked` in both asset and stablecoin logic (v1 and v2) performs no zero-address check before granting a role: [1](#0-0) 

Compare this to `transfer_inner`, `mint`, and `approve` in the very same files, which explicitly guard against `Address::ZERO` for `to`/`from`/`spender`/`caller`: [2](#0-1) [3](#0-2) 

The `DEFAULT_ADMIN_ROLE` "last admin" protection only fires when the role's member count is exactly `1`: [4](#0-3) [5](#0-4) 

Because `grant_role_unchecked` increments `role_member_count` for `DEFAULT_ADMIN_ROLE` regardless of whether `account` is the zero address: [6](#0-5) 

a sole admin can call `grantRole(DEFAULT_ADMIN_ROLE, address(0))`. This bumps the member count from 1 to 2 while granting the role to an address that can never originate a transaction. The genuine admin can then call `renounceRole`/be `revokeRole`'d, and since the member count is now 2 (not 1), the `LastAdminCannotRenounce` check does not trigger: [5](#0-4) 

The result: `DEFAULT_ADMIN_ROLE` membership count reports `1`, "held" solely by `address(0)`, which can never sign a transaction. All admin-gated mutations dispatched through `dispatch.rs` — `grantRole`, `revokeRole`, `setRoleAdmin`, `updatePolicy`, and any role whose admin role resolves to `DEFAULT_ADMIN_ROLE` (including `MINT_ROLE`, `Metadata`, pause/unpause-related roles, etc., depending on deployment config) — become permanently unreachable, since `ensure_role_admin_mutations_available`/`ensure_role` can never be satisfied by any real caller again: [7](#0-6) [8](#0-7) 

This is the exact bug class from the report: a reachable state-mutating role/position-assignment function with no `address(0)` guard, whose accidental (or malicious self-inflicted) use permanently and irrecoverably locks the position/role.

### Impact Explanation
Once `DEFAULT_ADMIN_ROLE` is orphaned to `address(0)`, the token contract's governance is permanently frozen: no future role grants/revocations, no policy updates, and no recovery path exists (there is no "rescue" mechanism for a role held by the zero address). Any token functionality gated behind `DEFAULT_ADMIN_ROLE`-managed roles — including pause/unpause, mint authorization changes, and policy configuration — is permanently locked, which for regulated/whitelisted B-20 assets (transfer policies, mint policies) can effectively freeze legitimate token operations for all holders. This matches "permanent freezing of funds"/functionality at High severity, matching the referenced report's classification.

### Likelihood Explanation
This requires the current sole `DEFAULT_ADMIN_ROLE` holder to call `grantRole(DEFAULT_ADMIN_ROLE, address(0))` and then renounce/be revoked — the same "operator error" scenario called out in the original report ("if called by error with this value, position would be permanently lost"). No special privilege beyond already holding `DEFAULT_ADMIN_ROLE` is needed, and nothing in the ABI, dispatch, or logic layers rejects the zero address for `grantRole`, so the mistake is directly reachable through the standard, publicly documented `grantRole` selector.

### Recommendation
Add a zero-address check to `grant_role`/`grant_role_unchecked` (and any equivalent "grant"-style mutation) mirroring the existing `transfer`/`mint`/`approve` guards, e.g. reject `account == Address::ZERO` with a dedicated revert (or reuse `InvalidReceiver`), for both `b20_asset` and `b20_stablecoin`, v1 and v2 logic implementations.

### Proof of Concept
1. Deploy a B-20 asset/stablecoin token; `ADMIN` holds the sole `DEFAULT_ADMIN_ROLE` (`role_member_count == 1`).
2. `ADMIN` calls `grantRole(DEFAULT_ADMIN_ROLE, address(0))` — succeeds, `role_member_count` becomes `2`, `address(0)` now "holds" `DEFAULT_ADMIN_ROLE`.
3. `ADMIN` calls `renounceRole(DEFAULT_ADMIN_ROLE, ADMIN)` (or another admin calls `revokeRole`) — succeeds because `role_member_count != 1`, so `LastAdminCannotRenounce` never triggers.
4. `DEFAULT_ADMIN_ROLE` is now solely "held" by `address(0)`; no real account can ever satisfy `ensure_role`/`ensure_role_admin_mutations_available` for that role again. All `DEFAULT_ADMIN_ROLE`-gated operations (`grantRole`, `revokeRole`, `setRoleAdmin`, `updatePolicy`, and roles administered by it) are permanently locked.

    /// Ensures role-admin mutations are still reachable.
    fn ensure_role_admin_mutations_available<S: AssetAccounting, A: PolicyAccounting>(
        &self,
        token: &B20AssetToken<S, A>,
        caller: Address,
    ) -> Result<()> {
        let admin_role = B20TokenRole::DefaultAdmin.id();
        if token.accounting().role_member_count(admin_role)? == U256::ZERO {
            return Err(BasePrecompileError::revert(IB20::AccessControlUnauthorizedAccount {
                account: caller,
                neededRole: admin_role,
            }));
        }
        Ok(())
    }

    fn grant_role_unchecked(
        &self,
        token: &mut B20AssetToken<S, A>,
        role: B256,
        account: Address,
        sender: Address,
    ) -> Result<()> {
        if token.accounting().has_role(role, account)? {
            return Ok(());
        }
        token.accounting_mut().set_role(role, account, true)?;
        if role == B20TokenRole::DefaultAdmin.id() {
            let current = token.accounting().role_member_count(role)?;
            let next =
                current.checked_add(U256::ONE).ok_or_else(BasePrecompileError::under_overflow)?;
            token.accounting_mut().set_role_member_count(role, next)?;
        }
        token
            .accounting_mut()
            .emit_event(IB20::RoleGranted { role, account, sender }.encode_log_data())
    }
