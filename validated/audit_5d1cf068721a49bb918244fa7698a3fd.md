## Finding [1](#0-0) 

### Title
Stale confirmations from deleted multisig members are still counted toward the execution threshold, allowing a request to execute below quorum - (File: multisig2/src/lib.rs)

### Summary
The multisig contract's `confirm()` method authorizes execution of a request purely by comparing the *size* of the stored confirmations set to `num_confirmations`, without verifying that every account/key in that set is still a current member. `delete_member()` only purges pending requests that were *originated* by the removed member; it never scans other pending requests' confirmation sets to strip the removed member's stale confirmation. As a result, a confirmation given by a member before removal keeps counting toward quorum even after that member has been deleted from `self.members`.

### Finding Description
`confirm()` computes the go/no-go decision as:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    ... execute_request(...)
}
``` [2](#0-1) 

This purely counts entries previously inserted into the `confirmations: LookupMap<RequestId, HashSet<String>>` map, without cross-checking membership in `self.members` at execution time.

`delete_member()` only cleans up requests whose `MultiSigRequestWithSigner.member == member` (i.e., requests the removed member *authored*):
```
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [3](#0-2) 

It never iterates over `self.confirmations` to remove the deleted member's string entry from *other* pending requests it merely confirmed but did not create. The equality that should hold — `confirmations recorded == confirmations from accounts still in self.members` — is broken the moment a confirming member is deleted while other requests they confirmed remain pending.

The equivalent legacy `multisig/src/lib.rs` contract has the same pattern with `DeleteKey`, which also only purges requests signed by the removed public key, not confirmations it placed elsewhere. [4](#0-3) 

### Impact Explanation
This directly breaks the "confirmations counted versus live members" custody binding and matches the Critical impact category "a multisig request executed below threshold." A multisig protecting NEAR funds, keys, or contract upgrades can be tricked into executing a `Transfer`, `AddKey`/`FunctionCall`, or `DeployContract` action with fewer live-member confirmations than the configured `num_confirmations`, because a stale confirmation from an already-removed member is silently counted. This can result in unauthorized transfer of NEAR held by the multisig account, or unauthorized privilege escalation (e.g., adding a full-access key) using less real authorization than intended.

### Likelihood Explanation
This requires no special node access, redeploy, or social engineering: any member who is later removed (e.g., because their key/account is discovered to be compromised or malicious — precisely the scenario `DeleteMember`/`DeleteKey` exists to remedy) can pre-confirm one or more malicious pending requests before removal. The removal action itself does not neutralize those confirmations. This is a realistic and directly reachable state-machine flaw in the core `confirm`/`delete_member` logic, not a theoretical edge case.

### Recommendation
When executing `DeleteMember` (or `DeleteKey` in `multisig/src/lib.rs`), iterate all pending requests' confirmation sets and remove the deleted member's identity from every one of them (not just requests they authored). Alternatively, validate confirmations against `self.members` at the moment of counting in `confirm()`, e.g. filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = {A, B, C}`, `num_confirmations = 2`.
2. Member `B` (later found to be compromised) calls `add_request_and_confirm` with a malicious `MultiSigRequest` `R` (e.g., `Transfer` of the full balance to an attacker-controlled account). `confirmations[R] = {B}` (1 of 2).
3. The team detects `B` is compromised and submits/executes a `DeleteMember{B}` request with confirmations from `A` and `C`, removing `B` from `self.members`. `delete_member()` only removes requests *authored* by `B`; request `R` (authored by `B` but that's irrelevant here — assume `B` merely confirmed a request authored by `A`) keeps `confirmations[R] = {B}` untouched.
4. Any single remaining member, e.g. `C`, calls `confirm(R)`. `confirmations.len() (1, from B) + 1 (C) = 2 >= num_confirmations (2)` → `execute_request(R)` runs, transferring funds to the attacker, even though only one currently-live member (`C`) actually authorized it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
