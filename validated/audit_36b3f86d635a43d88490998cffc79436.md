Based on my investigation, this is a legitimate access control finding, though the specific "impersonation" exploit mechanism requires an important caveat.

### Title
Missing role check on GET /v2/external_initiators discloses OutgoingToken to any authenticated user regardless of role - ([File: core/web/router.go])

### Summary
The `/v2/external_initiators` `Index` route is registered with only session/token authentication and no `RequiresEditRole`/`RequiresAdminRole` wrapper, unlike `Create` and `Destroy` on the same resource. `presenters.ExternalInitiatorResource`, the JSON representation returned by `Index`, includes the plaintext `OutgoingToken` field, meaning any authenticated user (including a view-role user or a restricted token holder) can enumerate every ExternalInitiator's outgoing credential.

### Finding Description
`v2Routes` wires the external-initiator endpoints as: [1](#0-0) 

`Create` and `Destroy` require `auth.RequiresEditRole`, but `Index` is wrapped only by `paginatedRequest`, with no role gate — any principal that passes `auth.Authenticate` (session cookie or API token, any role) can call it.

`Index` builds its response from `presenters.NewExternalInitiatorResource`, which copies `OutgoingToken` unredacted into the JSON payload: [2](#0-1) 

The existing test suite confirms the field is returned as-is over the wire rather than redacted: [3](#0-2) 

By contrast, `OutgoingSecret`, `Salt`, and `HashedSecret` are **not** included in `ExternalInitiatorResource` — only `OutgoingToken` and the (non-secret) `AccessKey` are exposed, so the disclosure is partial: `OutgoingSecret` is only ever returned once, at creation time, via `ExternalInitiatorAuthentication`.

### Impact Explanation
This is a genuine broken-access-control / credential-disclosure bug: the `Index` handler does not apply the same `RequiresEditRole`/`RequiresAdminRole` gate that `Create`/`Destroy` use, so lower-privileged authenticated users (view or run role) can read `OutgoingToken` values belonging to ExternalInitiators they did not create. That said, I was unable to find any code path within this repository that actually **consumes** `OutgoingToken`/`OutgoingSecret` to sign, authenticate, or verify outgoing HTTP requests from the node to an external initiator's callback URL — the fields are generated in `bridges.NewExternalInitiator` and persisted, but grep across `core/services/pipeline`, `core/services/webhook`, and related packages shows no reference to `OutgoingToken`/`OutgoingSecret` being attached to outgoing requests or checked anywhere in this codebase. Verification of those credentials (if any) would have to occur on the external initiator's own server, which is out of scope/not present in this repository. Because the "impersonate the node when responding to bridge callbacks" mechanism cannot be substantiated with concrete code in this repo, the confirmed, provable impact is limited to unauthorized disclosure of a stored secret token to an under-privileged authenticated user — not a demonstrated live impersonation/authentication-bypass exploit.

### Likelihood Explanation
Any authenticated user with a valid session or API token of *any* role (view, run, edit) can call `GET /v2/external_initiators` today, since the route lacks a role wrapper. No special preconditions are needed beyond having any valid credential to the node's API — this is trivially and repeatably reproducible.

### Recommendation
Wrap `Index` with `auth.RequiresEditRole` (or `RequiresAdminRole`) to match `Create`/`Destroy`, and/or redact `OutgoingToken` from `presenters.ExternalInitiatorResource` (return only non-sensitive metadata like `Name`, `URL`, `AccessKey`, timestamps), exposing outgoing credentials only once, at creation time, as is already done for `OutgoingSecret`.

### Proof of Concept
Go handler-level integration test plan:
1. Start app with `ExternalInitiatorsEnabled = true`, create a user/API token with **run** role only (not admin/edit).
2. Insert an `ExternalInitiator` via `bridges.ORM.CreateExternalInitiator` with a known `OutgoingToken`.
3. Authenticate an HTTP client as the run-role user and call `GET /v2/external_initiators`.
4. Assert the response is `200 OK` (not `403 Forbidden`) and that `presenters.ExternalInitiatorResource.OutgoingToken` in the parsed JSON equals the known plaintext value — demonstrating disclosure to a role that cannot itself create/manage external initiators.
5. (To validate the impersonation claim specifically) attempt to locate and exercise any code path that uses the disclosed `OutgoingToken`/`OutgoingSecret` to authenticate an outgoing node request — no such path currently exists in this repo, so this step cannot be completed against current code.

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {

		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),

		URL:           ei.URL,
		AccessKey:     ei.AccessKey,

}
