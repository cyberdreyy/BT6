### Title
Loss-adjusted withdraw receipt escapes its haircut when a later request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a use-after-free: a pointer to a driver-owned object is kept after the object is replaced/freed, and a later reader copies from the stale pointer. The vault analog lives in `IdleCreditVault.claimWithdrawRequest`: the per-epoch loss haircut recorded in `lossRecoveryPriceByEpoch[epoch]` is looked up only through the *single* mutable marker `lastWithdrawRequest[_user]`. A subsequent `requestWithdraw` overwrites that marker, orphaning the old haircut record — the stale epoch reference is "freed" — while the underlying debt survives in the aggregate `withdrawsRequests[_user]` ledger and is later paid out **at par** by `_claimFundedWithdrawRequest`.

### Finding Description
- `requestWithdraw` writes `lastWithdrawRequest[_user] = currentEpoch` on every call and accumulates into both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) .
- On a `stopEpochWithDuration` partial loss, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws`, collecting only the funded (post-haircut) amount [2](#0-1) .
- `_claimLossAdjustedWithdrawRequest` retrieves the haircut **only** via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [3](#0-2) . If the user makes a second request in a later epoch M, `lastWithdrawRequest` is overwritten to M; `lossRecoveryPriceByEpoch[M] == 0`, so the loss path returns 0 and `withdrawsRequestsByEpoch[_user][N]` is never cleared.
- `_claimFundedWithdrawRequest` then pays the aggregate `withdrawsRequests[_user]` — which still contains the epoch-N basis — at 1:1 par via `_transferFundedClaim`, and burns the receipt [4](#0-3) .
- Existing guards do not stop it: the epoch gate `epochNumber <= lastWithdrawRequest[_user]` only enforces waiting one epoch after the *latest* request; once epoch M ends, the full aggregate (including the haircutted epoch-N basis) is claimable at par.

### Impact Explanation
Direct theft / insolvency. The vault collected only `pendingBasis * lossRecoveryPrice` for epoch-N receipts, yet pays the epoch-N basis in full. The excess `claimBasis_N * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` is drained from the funded reserve, so other withdraw claimants (or the borrower-funded reserve for subsequent epochs) are short by exactly the haircut the attacker dodged. If `lossRecoveryPrice` is small (large loss), nearly the entire epoch-N basis is stolen.

### Likelihood Explanation
Medium-high. Requirements are all unprivileged and market-driven: (1) hold a withdraw receipt in an epoch where `stopEpochWithDuration` realizes a partial loss (`_amount < pendingBasis`); (2) submit any second `requestWithdraw` in a later epoch — a normal user action that even adds value to the pool; (3) wait one epoch and call `claimWithdrawRequest`. No privileged cooperation needed beyond honest manager stop/start calls.

### Recommendation
Make the loss-adjusted claim path not depend on `lastWithdrawRequest` being the loss epoch. Either iterate/record all epochs with pending loss-adjusted receipts per user (e.g., a `lossEpochs[_user]` enumerable set or checking `withdrawsRequestsByEpoch` against epochs with a non-zero `lossRecoveryPriceByEpoch`), or proactively settle the pending epoch-N receipt at haircut inside `requestWithdraw` before overwriting `lastWithdrawRequest`, so the aggregate ledger never mixes haircutted and unhaircutted basis.

### Proof of Concept
Foundry fork sketch (mainnet fork of an existing IdleCreditVault deployment, or the repo's own harness):

```solidity
// Epoch N: user deposits, requests withdraw of T tranche tokens.
vm.prank(user);
cdoEpoch.requestWithdraw(T, AAtranche);          // lastWithdrawRequest[user] = N

// Manager stops epoch N with a realized loss: borrower funds only part of pendingWithdraws.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(apr, duration, lossAmount); // sets lossRecoveryPriceByEpoch[N] < RECOVERY_FULL

// Epoch M = N+1: user submits a second withdraw -> lastWithdrawRequest[user] = M,
// lossRecoveryPriceByEpoch[M] == 0, epoch-N basis stays in withdrawsRequests[user].
vm.prank(user);
cdoEpoch.requestWithdraw(dust, AAtranche);

// Let epoch M end normally.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, interest);

// Claim: _claimLossAdjustedWithdrawRequest sees lossRecoveryPriceByEpoch[M]==0 and returns 0;
// _claimFundedWithdrawRequest pays the FULL aggregate (epoch-N basis + dust) at par.
uint256 balPre = underlying.balanceOf(user);
vm.prank(user);
cdoEpoch.claimWithdrawRequest();

uint256 claimed = underlying.balanceOf(user) - balPre;
uint256 expectedHaircutted = T * lossRecoveryPriceByEpoch[N] / RECOVERY_FULL + dust;
assertGt(claimed, expectedHaircutted); // theft: haircut bypassed
```

The invariant violated is "one receipt, haircut-adjusted payout": the stale `lastWithdrawRequest` reference frees the epoch-N haircut record while the aggregate ledger still pays it at par.

```text
    uint256 pendingBasis = pendingWithdraws;

      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
