### Title
Non-minted `stopEpoch` funds "borrower interest" from pool principal while the borrower ledger still shows it owed, double-counting debt and inflating tranche NAV - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
Analogous to the Gearbox report (pool-level `totalBorrowed` diverging from the sum of per-account debt), `IdleCDOEpochVariant._stopEpoch` in programmable-borrower mode with `isInterestMinted == false` pulls `totalInterestDueNow()` in cash from `ProgrammableBorrower`, but that cash is drawn from the facility's own vault principal — not from the real borrower — while `borrowerInterestAccrued` is never cleared. `settleBorrowerInterest()` is invoked only on the minted path, so the same borrower interest is recorded as still owed and is counted again in every subsequent `totalInterestDueNow()`/pull.

### Finding Description
In `_stopEpoch` (`contracts/IdleCDOEpochVariant.sol:330-466`):

- `_interest` is resolved via `_resolveStopEpochInterest` → `IProgrammableBorrower.totalInterestDueNow()`, which includes `borrowerInterestAccruedNow()` — the real borrower's contractual, not-yet-paid interest (`ProgrammableBorrower.sol:330-334`).
- `_amountToPullFromBorrower = _expectedInterest` when `isInterestMinted == false` (line 376). `getFundsFromBorrower` then `transferFrom`s that amount out of `ProgrammableBorrower`, and `onStopEpoch` (`ProgrammableBorrower.sol:231-268`) satisfies it from on-hand cash or by withdrawing from the ERC4626 vault — i.e., from LP principal, since the real borrower has not repaid anything.
- `settleBorrowerInterest()` is only called when `_mintInterest && isProgrammableBorrower` (lines 413-415). In the non-minted path `borrowerInterestAccrued` is left untouched.

Result: `_updateAccounting` raises tranche prices by `_grossInterest` backed by cash that already belonged to the pool (net system assets unchanged), and the borrower's ledger still shows the same interest outstanding. On the next epoch stop, `totalInterestDueNow()` includes that still-recorded `borrowerInterestAccrued` plus further accrual on `borrowerPrincipal`, so the pool pulls and books the same debt again — exactly the "pool `totalBorrowed` exceeds the real sum of account debt" mismatch from the Gearbox report, in reverse attribution but identical insolvency direction.

### Impact Explanation
Each non-minted epoch stop mints NAV against phantom interest. Withdraw-request fulfillers (`collectWithdrawFunds`) and LPs redeeming at `virtualPrice` between the stop and the borrower's actual repayment extract real underlying against yield that was only self-funded. If the borrower delays or under-repays relative to the repeated pulls, cumulative booked interest exceeds real assets and late withdrawers/claimants are left unbacked — protocol insolvency equal to the accrued borrower interest re-counted per epoch. A tranche holder (unprivileged) can time `requestWithdraw`/`claimWithdrawRequest` or instant claims across a stop to capture the inflated price.

### Likelihood Explanation
Requires a pool running in programmable-borrower mode with `isInterestMinted == false` and a nonzero draw at nonzero `borrowerApr`. The minted path is tested extensively, but the code explicitly branches on `_mintInterest` for both the pull amount and the settle call, indicating non-minted operation is a supported configuration rather than dead code. No attacker privileged action is needed beyond holding tranche tokens or withdraw receipts; the owner/manager performs only honest `stopEpoch` calls. One uncertainty I could not fully verify is whether `_checkProgrammableBorrowerMode` (line 333) independently forces `isInterestMinted` — if it does, this surface is unreachable and the finding collapses; the visible code does not show such a constraint.

### Recommendation
In the non-minted programmable path, either (a) call `settleBorrowerInterest()` as well so the pulled-vs-owed accounting stays coherent and the pulled amount is treated as an advance against recorded debt, or (b) exclude `borrowerInterestAccruedNow()` from the cash-pull computation and only realize borrower interest into pool NAV when the real borrower actually repays (e.g., via the existing `bufferInterest` carry in `_repay`). The invariant to enforce: booked epoch interest must equal interest actually funded by the borrower, not interest funded by the facility's own principal.

### Proof of Concept
Foundry fork test sketch (real MetaMorpho vault, as in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testNonMintedStopEpochDoubleCountsBorrowerInterest() external {
    uint256 amount = 10_000 * oneScale;
    uint256 drawAmount = 5_000 * oneScale;

    // do NOT call setIsInterestMinted(true) -> cash-pull mode
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(drawAmount);

    vm.warp(block.timestamp + 30 days);
    _accrueMorphoVaultInterest();

    uint256 accrued = programmableBorrower.borrowerInterestAccruedNow();
    uint256 vaultGain = programmableBorrower.vaultInterestAccrued();
    uint256 borrowerAssetsBefore = programmableBorrower.totalUnderlying();

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Pool booked totalInterestDueNow (vaultGain + accrued) as interest,
    // but borrowerInterestAccrued was never settled:
    assertEq(
        programmableBorrower.borrowerInterestAccruedNow(),
        accrued,
        "accrued borrower interest not cleared after cash pull"
    );
    // The pull was funded by the facility's own assets:
    assertLe(
        programmableBorrower.totalUnderlying(),
        borrowerAssetsBefore - (accrued + vaultGain),
        "interest pull drained pool principal"
    );

    // Next epoch: the same accrued amount is counted again by totalInterestDueNow
    _startEpochAndCheckPrices(1);
    assertGe(
        programmableBorrower.totalInterestDueNow(),
        accrued,
        "same borrower interest double-counted into next stop"
    );
}
```

Run against the existing harness with `isInterestMinted` left `false` and `borrowerApr = 365e18`.
