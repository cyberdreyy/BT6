### Title
Stale or zero-priced write-off asks let any EOA seize escrowed tranche tokens for free or below fair value - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow` escrows a lender's tranche tokens in `createWriteOffRequest` and lets **any** wallet settle the trade via `fullfillWriteOffRequest`. Because requests are updated by *additional* `createWriteOffRequest` calls rather than replaced atomically, a request temporarily sits in the escrow with `underlyings == 0` (or a stale lower ask). During that window any attacker can fulfill it, paying zero underlying and receiving the full tranche balance — the on-chain equivalent of the NFT God incident, where assets sitting in an "unsealed" state (hot wallet) were drained by anyone who reached them first.

### Finding Description
`createWriteOffRequest` escrows tranches and records `userRequests[msg.sender]` with whatever `underlyingsRequested` was passed — there is no lower bound on the ask (only `amount == 0` reverts) [1](#0-0) . `fullfillWriteOffRequest` is callable by `any wallet` and only enforces `_underlyings >= currentRequest.underlyings` and exact `_tranches` equality before deleting the request and paying out [2](#0-1) . Two consequences:

1. **Zero-ask window**: if a lender deposits tranches with `underlyingsRequested = 0` (intending to set the price in a follow-up call — which the additive design at lines 95–101 invites), anyone can immediately call `fullfillWriteOffRequest(user, tranches, 0)`, transfer 0 underlying, and receive all escrowed tranche tokens.
2. **Stale-ask front-running**: a lender who wants to *raise* the ask (market moved, or initial ask too low) must send a second `createWriteOffRequest` which only *adds* `underlyings`. An attacker can front-run that update and settle at the old, lower price — or sandwich a legitimate borrower fulfilment. There is no "ask change locks fulfillment" mechanism and no fulfiller whitelist.

### Impact Explanation
Direct theft of lender funds by an unprivileged EOA. In the zero-ask case the attacker acquires the full escrowed tranche position (e.g., 10,000 AA tranche tokens) for 0 underlying — total loss equals the tranche tokens' redemption value at `tranchePrice`. In the stale-ask case the loss is the delta between intended ask and stale ask. Both bypass the `EpochNotRunning` guard on creation (fulfill is ungated by epoch phase) and the `WrongRequest` check does not protect a zero or stale ask [3](#0-2) .

### Likelihood Explanation
The attack requires only a normal EOA and token approval; no privileged role is involved, satisfying the honest-privileged-role constraint. The zero-ask path depends on a user error (interim `underlyingsRequested = 0`), but the additive-update design makes a two-transaction setup a natural usage pattern, and searchers monitor mempools for exactly this class of mispriced escrow orders — the same class of opportunistic theft as the referenced incident. The stale-ask front-run is fully deterministic: any ask increase is exploitable by definition.

### Recommendation
- Revert in `createWriteOffRequest` when `underlyingsRequested == 0`, and/or require the ask to be set only once (`currentRequest.underlyings == 0` on first call) so a deposit is never fulfillable at zero.
- On any update to the ask, add a timelock or require the request to be deleted and recreated, so front-runners cannot settle at the stale price.
- Alternatively, let `fullfillWriteOffRequest` pull the agreed price from the stored request and pay exactly `currentRequest.underlyings`, removing attacker-chosen underpayment entirely.

### Proof of Concept
Foundry fork test (mainnet, block ~23032567, same setup as `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`):

```solidity
function testFulfillZeroAskStealsTranches() external {
    // LP creates a request but has not set the ask yet (or set it to 0)
    vm.prank(LP);
    escrow.createWriteOffRequest(10000e18, 0);

    // any unprivileged attacker fulfills with 0 underlying
    address attacker = makeAddr("attacker");
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, 10000e18, 0); // transfers 0 underlying

    assertEq(tranche.balanceOf(attacker), 10000e18, "attacker stole all escrowed tranches");
    assertEq(underlying.balanceOf(LP), 0, "seller received nothing");
}

function testFulfillAtStaleAskFrontrun() external {
    vm.prank(LP);
    escrow.createWriteOffRequest(10000e18, 1e6); // ask set, then LP wants to raise it

    // attacker front-runs LP's createWriteOffRequest(0, 9999e6) update
    deal(address(underlying), attacker, 1e6);
    vm.startPrank(attacker);
    underlying.approve(address(escrow), 1e6);
    escrow.fullfillWriteOffRequest(LP, 10000e18, 1e6); // settles at stale low ask
    vm.stopPrank();

    assertEq(tranche.balanceOf(attacker), 10000e18, "attacker bought tranches far below intended ask");
}
```

Both run in a running-epoch phase with honest owner/borrower; no existing guard (epoch gating, `WrongRequest`, reentrancy, KYC) blocks either path.

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
