### Title
Default finalization ignores unfunded instant-withdraw receipts from prior epochs, permanently freezing their recovery and bricking the user's entire `claimInstantWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the iwlwifi bug — where reading `txq->read_ptr` once and then reclaiming a *different* range frees/misses entries — `IdleCreditVault` snapshots the instant-withdraw recovery basis only for `epochNumber` at default-finalization time. Unfunded instant receipts recorded under *earlier* epochs in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` are neither added to `defaultPendingClaimBasis()` nor backed by `defaultRecoveryReserve`, yet they remain in `instantWithdrawsRequests[user]`. Post-default, `claimInstantWithdrawRequest` tries to pay the leftover aggregate at par via `_transferFundedClaim`, which reverts because the strategy balance is fully absorbed by `defaultRecoveryReserve` — permanently freezing both the stale receipt and the user's current-epoch recovery in a single always-reverting call.

### Finding Description
`defaultPendingClaimBasis()` only adds `instantWithdrawClaimsByEpoch[epochNumber]` (current epoch) when `pendingInstantWithdraws != 0`: [1](#0-0) 

`_defaultPrefundedInstantReserve()` likewise only credits `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`, i.e. current-epoch prefunding: [2](#0-1) 

So `finalizeDefaultRecovery` computes `defaultRecoveryPrice` over a `totalBasis` that excludes older-epoch instant receipts, and `defaultRecoveryReserve` holds no backing for them.

Post-default, `claimInstantWithdrawRequest` first clears only the `defaultRecoveryEpoch` basis, then pays the *entire remaining* `instantWithdrawsRequests[user]` at par: [3](#0-2) 

`_claimDefaultedInstantWithdrawRequest` reads only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`: [4](#0-3) 

`_transferFundedClaim` reverts whenever `balance - defaultRecoveryReserve < amount`: [5](#0-4) 

An old unfunded instant receipt has no funded balance outside the reserve, so the transfer always reverts and — because the defaulted-epoch claim happens in the same transaction — the user's recovery payout for the default epoch is frozen too. This mirrors the CVE pattern: an index/pointer (`epochNumber`) read at one point decides the reclaim range, while state accumulated under other indices is silently skipped and then mishandled.

### Impact Explanation
Any user holding an instant-withdraw receipt that went unfunded in an epoch *before* the default epoch permanently loses that underlying, and additionally cannot claim their defaulted-epoch instant recovery at all (the combined call reverts). Loss = full unfunded prior-epoch instant amount + locked default-epoch instant recovery share. Since `claimInstantWithdrawRequest` is the only redemption path for instant receipts, this is permanent freezing/theft of unclaimed yield, not a DoS-by-gas.

### Likelihood Explanation
Requires a specific but plausible sequence: an unprivileged lender requests an instant withdraw, the epoch starts with insufficient strategy liquidity, the manager/borrower never calls `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` for it (requests remain pending across later epochs — the test suite itself shows unfunded instant requests persisting and reverting on claim), and a later epoch ends in borrower default with `pendingInstantWithdraws != 0`. All steps use honest privileged roles; the attacker is just an ordinary KYC'd lender.

### Recommendation
In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, aggregate `instantWithdrawClaimsByEpoch` across all epochs with outstanding receipts (e.g., track a cumulative `totalInstantWithdrawClaims` incremented in `requestInstantWithdraw` and decremented on claim/collect) instead of only `instantWithdrawClaimsByEpoch[epochNumber]`. Alternatively, let `_claimDefaultedInstantWithdrawRequest` iterate/settle all per-epoch bases ≤ `defaultRecoveryEpoch`, and add an explicit `defaultRecoveryFinalized` check to `requestInstantWithdraw` to prevent post-default receipts polluting the aggregate.

```solidity
// test/foundry/IdleCreditVault.DefaultInstantFreeze.t.sol
function testOldUnfundedInstantReceiptFrozenAfterDefault() external {
    // epoch 0: deposit, run, stop -> buffer
    uint256 minted = idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // attacker/user requests instant withdraw
    uint256 req = cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));
    IdleCreditVault strat = IdleCreditVault(address(strategy));

    // epoch 1 starts with no free liquidity; borrower never funds the instant request
    _startEpochAndCheckPrices(1);
    assertEq(strat.pendingInstantWithdraws(), req);          // stays unfunded
    assertEq(strat.instantWithdrawsRequestsByEpoch(address(this), 1), req); // recorded under epoch 1

    // epoch 1 ends, epoch 2 runs, borrower defaults -> finalizeDefaultRecovery
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());
    _startEpochAndCheckPrices(2);
    _defaultBorrowerAndFinalize(); // helper: stopEpochWithDuration(_loss), finalizeDefaultRecovery

    // epoch-1 receipt was never added to defaultPendingClaimBasis -> no reserve backing
    // claim reverts inside _transferFundedClaim (balance == reserve)
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest(); // frozen forever: old receipt + any epoch-2 recovery
}
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
