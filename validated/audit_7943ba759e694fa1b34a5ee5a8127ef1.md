### Title
Unclaimed loss-adjusted withdraw receipt escapes its haircut and is paid at par after a second request - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The AppArmor bug is a use-after-free: a "handle" (open inode) survives while the referenced `aa_loaddata` is freed because refcounting assumed the profile's reference would keep it alive. The credit-vault analog is a stale receipt reference: `IdleCreditVault` keeps each user's claim bookkeeping keyed by the single slot `lastWithdrawRequest[_user]`, while per-epoch receipt data lives in `withdrawsRequestsByEpoch` / `lossRecoveryPriceByEpoch`. When a user holds an unclaimed loss-adjusted receipt from epoch E1 and files a new `requestWithdraw` in epoch E2, `lastWithdrawRequest` is overwritten — the "pointer" to the loss epoch is dropped even though the receipt itself is still alive — and the haircut claim path can never run again. The receipt is then redeemed at par through the funded-claim path, even though the strategy was only funded `amount * lossRecoveryPrice`.

### Finding Description
In `requestWithdraw`, every request unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds `_amount` to the aggregate `withdrawsRequests[_user]` and the per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) . When a `stopEpochWithDuration`-style stop funds less than `pendingWithdraws`, `collectWithdrawFunds` stores the haircut as `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` [2](#0-1) . From then on the only path that pays the receipt at the haircut is `_claimLossAdjustedWithdrawRequest`, which looks up the loss epoch exclusively via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [3](#0-2) .

If the user files a second `requestWithdraw` before claiming, `lastWithdrawRequest[_user]` becomes the new epoch E2, whose `lossRecoveryPriceByEpoch` is 0, so the loss-adjusted path silently returns 0 and `withdrawsRequestsByEpoch[_user][E1]` is never cleared [4](#0-3) . After epoch E2 is funded, `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` — which still includes the un-cleared E1 basis — at par, and burns the full receipt [5](#0-4) . The doc comments even confirm a user may request again without claiming [6](#0-5) . The invariant "a loss-adjusted receipt is paid at `lossRecoveryPrice`" is broken; no guard (epoch gating, `_ensureDefaultRecoveryInitialized`, reserve checks) stops this because the funded path sees a valid, funded aggregate.

### Impact Explanation
The strategy only collected `E1_amount * lossRecoveryPrice / RECOVERY_FULL` for the E1 receipt, but the attacker receives `E1_amount` at par. The shortfall `(1 - lossRecoveryPrice) * E1_amount` is paid out of underlyings belonging to other claimants and active LPs: later `claimWithdrawRequest` calls revert on insufficient balance, or — post-default — the funded-claim guard `balance - reserve < _amount` makes honest defaulted/post-default claims unpayable [7](#0-6) . This is direct theft of funds plus vault insolvency for remaining claimants, proportional to the loss haircut size (with a large realized loss the overpayment is nearly the full receipt).

### Likelihood Explanation
Fully attacker-controlled, unprivileged flow: deposit (KYC'd lender), `requestWithdraw` before a loss epoch, wait for `stopEpochWithDuration`/`collectWithdrawFunds` to record a haircut (honest manager/queue sequencing, not attacker-controlled behavior), then issue one more `requestWithdraw` in the next epoch and claim once funded. No privileged collusion, timing-only assumption is an epoch ending with a realized loss, which is a normal operating mode (`stopEpochWithDuration(_lossAmount)` is an in-scope surface). The attacker can even create the second request with a dust amount to minimize cost.

### Recommendation
Do not key the loss-adjusted claim solely off the mutable `lastWithdrawRequest`. Either iterate/record the user's loss epochs explicitly (e.g., a per-user set or scanning `withdrawsRequestsByEpoch` epochs with non-zero `lossRecoveryPriceByEpoch`), or in `requestWithdraw` settle/claim any pending loss-adjusted receipt for the user before overwriting `lastWithdrawRequest`. At minimum, revert a new request while `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` and the E1 receipt remains unclaimed.

### Proof of Concept
Foundry fork sketch against `IdleCDOEpochVariant` + `IdleCreditVault`:

```solidity
// setup: user deposits, epoch running
uint256 amt = 100_000e6;
_depositWithUser(attacker, amt);          // KYC'd lender
vm.prank(manager); cdoEpoch.startEpoch();

// epoch E1: attacker requests withdraw of all tranches
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // -> withdrawsRequestsByEpoch[attacker][E1], lastWithdrawRequest = E1

// honest manager stops epoch E1 with a loss: borrower funds only half of pendingWithdraws
uint256 pending = strategy.pendingWithdraws();
uint256 funded  = pending / 2;            // lossRecoveryPriceByEpoch[E1] = 0.5e18
... warp, borrower approves, manager calls stopEpochWithDuration(_lossAmount) ...
// strategy now holds only `funded` underlying for E1 receipts

// epoch E2 starts; attacker files a tiny second request -> lastWithdrawRequest = E2
vm.prank(manager); cdoEpoch.startEpoch();
vm.prank(attacker);
cdoEpoch.requestWithdraw(1, address(AAtranche)); // overwrites lastWithdrawRequest, E1 receipt stays in withdrawsRequests

// epoch E2 ends fully funded
... manager stopEpoch with full funding of pendingWithdraws ...

// attacker claims: loss-adjusted path skipped (lossRecoveryPriceByEpoch[E2] == 0),
// funded path pays withdrawsRequests[attacker] = E1_basis + dust AT PAR
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();

// assert attacker received ~amt instead of funded (~amt/2) + dust
assertGt(underlying.balanceOf(attacker), funded);
// subsequent honest claimants revert / strategy balance < aggregate claims -> insolvency
```

The PoC shows `withdrawsRequestsByEpoch[attacker][E1]` and its `lossRecoveryPriceByEpoch[E1]` haircut are orphaned by the `lastWithdrawRequest` overwrite, paying the stale receipt at par and leaving the vault short exactly `E1_basis * (1 - lossRecoveryPrice)`.

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
```
