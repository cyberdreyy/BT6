Based on my analysis, the delete-secrets path in the Vault gateway handler does not enforce that the `Owner` field inside the deleted `SecretIdentifier` matches the authorized/authenticated owner, unlike the list path which explicitly overrides it. However, I was unable to fully confirm within tool budget whether the JWT-based authorizer (`core/capabilities/vault/jwt_based_auth.go`) independently binds `DeleteSecretsRequest.Ids[].Owner` to the derived JWT owner before this point, which would close the gap. Given this open question, I cannot assert with certainty that this is an unauthenticated/exploitable owner-mismatch bug versus a defense-in-depth gap.

Given the uncertainty on that missing piece, and following the validation rule that root cause must be proven with exact file/function support, I'll report only what I can concretely support: `handleSecretsDelete` in `core/capabilities/vault/gw_handler.go` passes the client-supplied `Owner` field straight to `secretsService.DeleteSecrets` without re-stamping it to the authorized owner, in contrast to `handleSecretsList` which does `r.Owner = authResult.AuthorizedOwner()`.

### Title
Missing owner re-stamping on delete-secrets path allows cross-owner secret deletion if authorization binding is bypassed - (File: core/capabilities/vault/gw_handler.go)

### Summary
`GatewayHandler.handleSecretsList` explicitly overwrites the request's `Owner` field with the cryptographically authorized owner (`r.Owner = authResult.AuthorizedOwner()`) before calling into the secrets service [1](#0-0) . The sibling `handleSecretsDelete` handler performs no equivalent re-stamping: it unmarshals the client-controlled `DeleteSecretsRequest` and forwards its `Ids` (each carrying its own `Owner` field) directly to `secretsService.DeleteSecrets` [2](#0-1) .

### Finding Description
`ValidateDeleteSecretsRequest` in `core/capabilities/vault/validator.go` validates structural correctness of each `SecretIdentifier` (key/owner/namespace format and length) but never compares `id.Owner` against the authorized principal [3](#0-2) . The authorization step (`authorizeAndStamp` in `gateway_vault_request_processor.go`) computes a digest over the whole raw request and checks it against an allowlisted entry, then prefixes the request ID with the authorized owner — but it does not rewrite or validate the `Owner` fields embedded inside `DeleteSecretsRequest.Ids` [4](#0-3) . This is the same bug class as the reported Astaria issue: an action that operates on an owned resource (secret / NFT) is executed based on attacker-suppliable target identifiers without a positive check that the identifiers belong to the authenticated caller — the check is only implicit and only holds if every authorization path binds owner-to-digest equally.

### Impact Explanation
If the digest-based allowlist authorization is the only binding between authorized owner and the `Ids[].Owner` values (as is the case for `AllowListBasedAuth`), tampering with `Owner` would change the digest and fail authorization — so under that path this is not exploitable. This finding is only a real vulnerability if there exists an authorization path (e.g., a JWT-based authorizer path, `core/capabilities/vault/jwt_based_auth.go`) that authorizes the request as belonging to `AuthorizedOwner()` without cryptographically binding that owner to every `SecretIdentifier.Owner` inside `Ids`. I could not confirm or rule out this binding for the JWT path within the available investigation, so the concrete cross-owner deletion impact is unproven.

### Likelihood Explanation
Low/uncertain: exploitability depends entirely on whether any enabled authorizer path fails to bind `Ids[].Owner` to the caller identity the way `AllowListBasedAuth`'s full-request digest implicitly does. This could not be fully verified.

### Recommendation
As defense-in-depth (matching the pattern already used in `handleSecretsList`), explicitly enforce/re-stamp `id.Owner == authResult.AuthorizedOwner()` for every `SecretIdentifier` in `DeleteSecretsRequest.Ids` inside `handleSecretsDelete` (or in `ValidateDeleteSecretsRequest`/`authorizeAndStamp`), rather than relying solely on digest equality to implicitly guarantee owner binding across all current and future authorizer implementations.

### Proof of Concept
Not established — a concrete PoC would require confirming that a specific authorizer implementation (e.g. JWT-based) accepts a `DeleteSecretsRequest` whose `Ids[].Owner` differs from the JWT-derived owner. This was not verified within the scope of this investigation.

func (r *RequestValidator) ValidateDeleteSecretsRequest(ctx context.Context, request *vaultcommon.DeleteSecretsRequest) error {
	if request.RequestId == "" {
		return errors.New("request ID must not be empty")
	}
	if err := r.MaxRequestBatchSizeLimiter.Check(ctx, len(request.Ids)); err != nil {
		if errBoundLimited, ok := errors.AsType[limits.ErrorBoundLimited[int]](err); ok {
			return fmt.Errorf("request batch size exceeds maximum of %d: %w", errBoundLimited.Limit, err)
		}
		return fmt.Errorf("failed to check request batch size limit: %w", err)
	}
	if len(request.Ids) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}

	uniqueIDs := map[string]bool{}
	for idx, id := range request.Ids {
		if id == nil {
			return errors.New("secret ID must not be nil at index " + strconv.Itoa(idx))
		}
		if err := r.ValidateSecretIdentifier(ctx, id.Key, id.Owner, id.Namespace); err != nil {
			return fmt.Errorf("invalid secret identifier at index %d: %w", idx, err)
		}

		_, ok := uniqueIDs[vaulttypes.KeyFor(id)]
		if ok {
			return errors.New("duplicate secret ID found at index " + strconv.Itoa(idx) + ": " + id.String())
		}

		uniqueIDs[vaulttypes.KeyFor(id)] = true
	}
	return nil
}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil
}
