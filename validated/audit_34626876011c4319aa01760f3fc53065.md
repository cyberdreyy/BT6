### Title
First-depositor donation inflates tranche price so subsequent depositors mint ~0 shares - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
The credit vault's accounting (`_updateAccounting`) values NAV via `getContractValue()`, which includes the **raw underlying token balance** of the contract. An unprivileged KYC-passing lender can therefore perform a classic first-depositor/donation attack: deposit 1 wei to become the sole tranche holder, then directly `transfer` underlying tokens to the CDO. On the next interaction the donation is booked as `totalGain`, and because the attacker's tranche is the only one with saved NAV (`_lastNAV == _lastTrancheNAV`), the entire donation accrues to their single share, inflating `priceAA`. Subsequent depositors receive `_amount * ONE_TRANCHE_TOKEN / priceAA` shares, which rounds to ~0 while their NAV is recorded in `lastNAVAA` and attributed to the attacker.

### Finding Description
- `getContractValue()` (IdleCDOCreditVault.sol:125-128) returns `strategyTokenBalance + rawTokenBalance - unclaimedFees`, so a direct `ERC20.transfer` of `token` to the vault inflates `nav`.
- `_updateAccounting()` (line 227) uses that `nav`; the gain is passed to `_virtualPriceAux`.
- In `_virtualPriceAux` (lines 319-336), when only the AA tranche has NAV (`_lastNAV == _lastTrancheNAV`), the whole `totalGain` goes to AA, and `_virtualPrice = (_lastTrancheNAV + gain) * ONE_TRANCHE_TOKEN / trancheSupply`. With `trancheSupply = 1`, the price becomes astronomical.
- `_mintSharesAtCurrPrice` (lines 344-348) computes `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` with no minimum-mint check, so a victim depositing less than the donation mints 0 shares but `lastNAVAA += _amount` still credits their deposit to tranche NAV, which the attacker's share now claims.

The `trancheSupply == 0 → return (oneToken, 0)` guard (line 297) only prevents the literal zero-price mint from the reference report; it does not prevent donation-driven price inflation, and the `_managedContractValue()` exclusion of raw underlyings is used only by `virtualPrice`/`_accrueManagementFee`, not by `_updateAccounting`/`getContractValue`.

### Impact Explanation
High. The attacker can steal (nearly) the full value of all subsequent AA deposits: victims mint 0 or dust shares while their principal is added to tranche NAV, redeemable by the attacker's single share via the normal withdraw/epoch-claim path. Loss ≈ victim deposits minus the donation, approaching 100% for the first victim and proportional dilution thereafter.

### Likelihood Explanation
Medium. Requires being the first (or sole) holder of a tranche class — feasible on a freshly deployed vault or a tranche whose supply was fully redeemed — plus an underlying donation roughly equal to the target deposit size. Attacker needs only to pass the same wallet-allowlist gate as any lender (`isWalletAllowed`/KYC), which the threat model permits as "a KYC-passing lender." No privileged action is required; the donation path uses a plain `transfer`.

### Recommendation
Exclude unsolicited underlying from accounting — use `_managedContractValue()` (strategy-token-backed NAV) inside `_updateAccounting` instead of `getContractValue()`, or skim donated `token` into a non-accounting reserve before computing `nav`. Additionally, mint dead/initial shares at initialization or revert in `_mintSharesAtCurrPrice` when `_minted == 0 && _amount > 0`.

### Proof of Concept
```solidity
// Foundry fork-style PoC (contracts in scope: IdleCDOCreditVault)
function test_firstDepositorDonationInflation() public {
    // vault: initialized IdleCDOCreditVault, AA deposits open, attacker is allowlisted
    vm.startPrank(attacker);
    token.approve(address(cdo), type(uint256).max);
    cdo.depositAA(1);                       // mints 1 share at price == oneToken
    token.transfer(address(cdo), 1_000_000e6); // donation: raw underlying counted by getContractValue()
    vm.stopPrank();

    vm.startPrank(victim);
    token.approve(address(cdo), type(uint256).max);
    uint256 minted = cdo.depositAA(500_000e6);
    vm.stopPrank();

    assertEq(minted, 0);                    // victim receives 0 shares
    // attacker 1 share now claims ~all lastNAVAA -> redeem via epoch/instant withdraw path
}
```

Caveat: I verified `IdleCDOCreditVault` directly. `IdleCDOEpochVariant` (the epoch-mode wrapper used by live credit vaults) contains numerous "skim" references I could not fully inspect before the tool limit; if it overrides `_updateAccounting`/`getContractValue` to strip raw underlyings, the attack surface may be narrowed to the non-epoch `IdleCDOCreditVault`/`IdleCDO` path. A confirmation run of the PoC against the concrete deployed variant is advised.
