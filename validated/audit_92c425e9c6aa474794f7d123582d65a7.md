### Title
Loss-adjusted withdraw receipts are paid at par after a second `requestWithdraw` overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores a haircut in `lossRecoveryPriceByEpoch[epochNumber]` and the affected receipts are meant to be paid pro-rata through `_claimLossAdjustedWithdrawRequest`. That function derives the claim epoch solely from `lastWithdrawRequest[_user]`. If the same user makes a second `requestWithdraw` before claiming, `lastWithdrawRequest` is overwritten with the newer epoch, the loss-adjusted path returns 0, and `_claimFundedWithdrawRequest` pays the user's **entire aggregate** `withdrawsRequests[_user]` at par — including the haircutted receipt. The realized loss is silently escaped, draining the strategy at the expense of other claimants and LPs.

### Finding Description
Relevant code, `contracts/strategies/idle/IdleCreditVault.sol`:

1. On each request, the marker is overwritten and amounts accumulate in a single aggregate:
   - `lastWithdrawRequest[_user] = currentEpoch;` (line 282)
   - `withdrawsRequests[_user] += _amount;` (line 292)

2. On a lossy stop, the CDO calls `collectWithdrawFunds` with `_amount < pendingBasis`, which zeroes `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber]` (lines 414–421). Only `lossBasis * lossRecoveryPrice / RECOVERY_FULL` was actually funded into the strategy.

3. Claim order in `claimWithdrawRequest` (lines 301–313): defaulted paths first, then `_claimLossAdjustedWithdrawRequest`, then `_claimFundedWithdrawRequest`.

4. `_claimLossAdjustedWithdrawRequest` (lines 789–801) reads `lossEpoch = lastWithdrawRequest[_user]` and looks up `lossRecoveryPriceByEpoch[lossEpoch]`. It never iterates `withdrawsRequestsByEpoch` for older epochs, even though `_withdrawClaimAmountsForEpoch`/`_clearWithdrawClaimForEpoch` are epoch-keyed (lines 811–837).

5. `_claimFundedWithdrawRequest` (lines 319–350) gates only on `epochNumber > lastWithdrawRequest[_user]` and then pays `withdrawsRequests[_user]` (the whole aggregate, across all epochs) at par via `_transferFundedClaim`.

Attack trace (normal fixed-APR mode, non-prefunded variant):

- Epoch N running: attacker `requestWithdraw(X)`. `withdrawsRequestsByEpoch[A][N] = X`, `lastWithdrawRequest[A] = N`, `pendingWithdraws = X`.
- `stopEpochWithDuration` realizes loss L; `collectWithdrawFunds` funds `X * price / 1e18` and sets `lossRecoveryPriceByEpoch[N] = price < RECOVERY_FULL`, `pendingWithdraws = 0`. `epochNumber` becomes N+1.
- Before claiming, attacker `requestWithdraw(Y)` in epoch N+1 buffer. Now `lastWithdrawRequest[A] = N+1`, `withdrawsRequests[A] = X + Y` (the epoch-N receipt `X` was never removed — `requestWithdraw` only adds; the loss-adjusted clearing only happens on claim).
- Epoch N+1 stops normally, funding `Y`. Attacker calls `claimWithdrawRequest`:
  - `_claimDefaultedWithdrawRequest`: skipped (no default).
  - `_claimLossAdjustedWithdrawRequest`: `lossRecoveryPriceByEpoch[N+1] == 0` → returns 0. The epoch-N haircut is never applied.
  - `_claimFundedWithdrawRequest`: `epochNumber (N+2) > lastWithdrawRequest (N+1)` → burns and pays `X + Y` at par.

Result: the strategy pays out `X` in full while it only received `X * price` for that receipt. The shortfall `X * (1 - price)` is taken from funds belonging to other pending/funded claims or active LP backing in the strategy.

### Impact Explanation
Direct insolvency/theft: any user can convert a haircutted loss receipt into a par claim for the cost of one extra withdraw request and one epoch of waiting. The escaped loss amount `X * (RECOVERY_FULL - price) / RECOVERY_FULL` is paid out of strategy reserves earmarked for other users' claims (funded claims are transferred from the strategy's own underlying balance), breaking the loss-socialization invariant that `collectWithdrawFunds`/`previewLossAdjustedWithdrawFunds` are designed to enforce. With repeated requests a large share of a realized loss can be externalized onto remaining claimants and LPs, potentially leaving the last claimants unable to withdraw (permanent freezing of their funds).

### Likelihood Explanation
- Attacker is a plain tranche-token holder (unprivileged, possibly KYC'd lender). No privileged role needed.
- Precondition is a `stopEpochWithDuration`/`collectWithdrawFunds` partial funding, i.e., an honest borrower loss event — exactly the scenario `lossRecoveryPriceByEpoch` exists for, so it is within the intended operating envelope, not an edge state.
- The trigger (a second `requestWithdraw`) is cheap and routine; any user who happens to re-request before claiming hits it even accidentally.
- Existing guards do not stop it: `_claimLossAdjustedWithdrawRequest` self-silences because it keys only off `lastWithdrawRequest`; `_claimFundedWithdrawRequest`'s epoch gate passes legitimately once the newer epoch ends; `_clearWithdrawClaimForEpoch` is never reached for epoch N. There is no check that `withdrawsRequests[_user]` contains amounts from epochs with an outstanding `lossRecoveryPriceByEpoch`.

### Recommendation
Iterate or track all epochs with pending claims instead of keying off `lastWithdrawRequest`. Concretely:
- Keep a per-user set/list of epochs in `withdrawsRequestsByEpoch`, or track `firstPendingEpoch`/`earliest loss epoch` separately from `lastWithdrawRequest`, and have `claimWithdrawRequest` clear **every** epoch that has a non-zero `lossRecoveryPriceByEpoch` before the funded path runs.
- Alternatively, in `requestWithdraw`, eagerly settle any existing loss-adjusted receipts for prior epochs (apply the haircut to the stored amounts) before overwriting `lastWithdrawRequest`.
- Add an invariant check in `_claimFundedWithdrawRequest` that no `lossRecoveryPriceByEpoch[e]` exists for epochs contributing to `withdrawsRequests[_user]`.

### Proof of Concept
Foundry fork PoC sketch (mirror `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossReceiptPaidAtParAfterSecondRequest() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());

    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);

    // Epoch N request
    uint256 tranches = IERC20(AAtranche).balanceOf(address(this)) / 2;
    uint256 req1 = cdoEpoch.requestWithdraw(tranches, address(AAtranche));

    // Lossy stop: borrower returns only part of pending basis
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 funded = pending / 2; // 50% recovery
    deal(defaultUnderlying, borrower, funded + amount);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, pending - funded); // loss on pending bucket

    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber() - 1), 0);

    // Epoch N+1: attacker requests again before claiming
    _startEpochAndCheckPrices(1);
    uint256 tranches2 = IERC20(AAtranche).balanceOf(address(this)) / 2;
    cdoEpoch.requestWithdraw(tranches2, address(AAtranche));

    // Epoch N+1 ends normally, fully funded
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending2 = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, pending2 + amount);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    _startEpochAndCheckPrices(2);

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(address(this)) - balPre;

    // BUG: claimed == req1 + req2 at par; expected req1 * lossPrice / 1e18 + req2
    assertEq(claimed, req1 + req2, 'loss receipt escaped haircut');
}
```

Key assertion: `strategy.lossRecoveryPriceByEpoch(N) > 0` yet the payout equals the full un-haircutted `req1`, demonstrating the haircut was bypassed via `lastWithdrawRequest` overwrite at `IdleCreditVault.sol:282` and the single-epoch lookup at `IdleCreditVault.sol:790-791`.
