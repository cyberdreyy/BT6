### Title
External Initiator credentials bypass "EIs not allowed" restriction and can trigger runs on ANY integer job ID - ([File: core/web/pipeline_runs_controller.go], [File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` sets a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` into the same Gin context key (`SessionUserKey`) used for real session/token users. `PipelineRunsController.Create` relies solely on `auth.GetAuthenticatedUser(c)` returning `ok=true` to decide "is this a real user allowed to run jobs by integer ID," explicitly intending to block EIs ("EIs not allowed" per the code comment), but since the check cannot distinguish a synthetic EI-derived user from a genuine user/token session, any EI credential holder can call `POST /v2/jobs/:ID/runs` with an arbitrary integer job ID and trigger a run.

### Finding Description
In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` (lines 119-151) authenticates the EI token and then does: [1](#0-0) 
This places a fabricated `User` object (Role `UserRoleRun`) under `SessionUserKey`, the exact same key `AuthenticateBySession`/`AuthenticateByToken` use for genuine users.

`GetAuthenticatedUser` simply reads that key with no way to tell the origin apart: [2](#0-1) 

In `PipelineRunsController.Create`, the code comment states the intent explicitly ("only users are allowed to run jobs using int IDs - EIs not allowed"), but the check used to enforce that intent is only presence-based: [3](#0-2) 

Because `isUser` is `true` for the EI's synthetic user too, an EI-authenticated request with an integer job ID passes the `isUser` gate and calls `prc.App.RunJobV2(ctx, jobID, nil)` for whatever `jobID` the attacker supplies — there is no check anywhere in this path that ties the request to a specific job the EI is bound to. Additionally, `bridges.ExternalInitiator` (`core/bridges/external_initiator.go`) has no job-binding field at all; job binding for EIs is only established elsewhere via a webhook spec's `ExternalInitiatorWebhookSpec`, which this endpoint never consults.

### Impact Explanation
An external-initiator credential holder — a low-privilege, restricted credential class explicitly listed as an acceptable "unprivileged attacker" — can trigger pipeline runs (`RunJobV2`) for any job on the node by integer ID, not limited to the job the EI is intended to serve. Depending on job task graphs, this is unauthorized triggering of another user's/job-owner's job runs, which can cause unwanted on-chain transactions, spend node funds/gas, exhaust rate-limited external resources, or otherwise misuse jobs the EI has no legitimate relationship to. This matches the "unauthorized job run" bounty impact class from a role/authorization bypass.

### Likelihood Explanation
Exploitation requires only valid EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) for any single external initiator registered on the node — no special job binding, no elevated role, and no other precondition. The request is a single `POST /v2/jobs/<integer-jobID>/runs`, fully reproducible and repeatable, and the developer's own comment shows this was an unintended gap rather than accepted behavior.

### Recommendation
Distinguish EI-derived synthetic users from real session/token users. Options:
- Set a distinct context key (e.g., `SessionExternalInitiatorKey` already exists) and have `PipelineRunsController.Create` check `auth.GetAuthenticatedExternalInitiator(c)` is absent (not just `GetAuthenticatedUser` presence) before allowing integer-ID job runs.
- Alternatively, add an explicit flag/type on the synthetic user (or a separate principal type) so `isUser` truly reflects "authenticated as a real user," and re-add job-to-EI binding enforcement if EI-triggered runs by ID are still supported.

### Proof of Concept
Handler/integration test plan (in `core/web/pipeline_runs_controller_test.go` or `external_initiators_controller_test.go` style):
1. Create two jobs, Job A and Job B, via the app's job ORM/pipeline test helpers.
2. Register one External Initiator `EI1` (no job-specific binding exists in the `ExternalInitiator` model).
3. Build an authenticated HTTP client using `EI1`'s access key/secret headers (`static.ExternalInitiatorAccessKeyHeader` / `static.ExternalInitiatorSecretHeader`), routed through the same middleware chain used for `/v2/jobs/:ID/runs` (`auth.Authenticate(..., auth.AuthenticateExternalInitiator, ...)`).
4. Send `POST /v2/jobs/<Job B integer ID>/runs` using `EI1`'s credentials.
5. Assert: expected behavior is `401/403` (EIs should not be permitted to run any job by integer ID per the code comment); actual behavior observed is `200 OK` with a `pipelineRun` resource created for Job B, proving `isUser` at `pipeline_runs_controller.go:109` incorrectly treats the EI's synthetic role-forced user as a legitimate user and grants an unauthorized run.
