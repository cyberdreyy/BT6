### Title
`total_send_fees` DeployGlobalContract branch overflows on `byte_fee.checked_mul(num_bytes).unwrap()` while DeployContract does not, causing a deterministic panic - ([File: runtime/runtime/src/config.rs])

### Summary
`validate_deploy_contract_action` and `validate_deploy_global_contract_action` both bound the contract size against the *same* `limit_config.max_contract_size` field, so there is no separate/larger limit for global contracts that would explain a divergence. [1](#0-0)  However, the `deploy_global_contract_byte` fee constant shipped in the base `RuntimeConfigStore` parameters (`action_deploy_global_contract_per_byte: 999_999_999_999_999`) is roughly 8 orders of magnitude larger than the `deploy_contract_byte` fee (`~6.8M`–`64.5M`), so multiplying it by `max_contract_size` (`4_194_304`) in the `DeployGlobalContract` arm of `total_send_fees` overflows `u64` for any code size above ~18.4 KB, well under the 4 MiB ceiling that `validate_deploy_global_contract_action` allows.

### Finding Description
`total_send_fees` computes, for every `DeployGlobalContract` action, `byte_fee.checked_mul(num_bytes).unwrap()` where `num_bytes` is the deployed code length and `byte_fee` is `fees.fee(ActionCosts::deploy_global_contract_byte).send_fee(sender_is_receiver)`. [2](#0-1) 

The base parameters file defines this fee as a flat, un-costed placeholder value:
```
action_deploy_global_contract_per_byte: {
  send_sir: 999_999_999_999_999,
  send_not_sir: 999_999_999_999_999,
  execution: 999_999_999_999_999,
}
``` [3](#0-2) 

`u64::MAX` is `18_446_744_073_709_551_615`. With `byte_fee = 999_999_999_999_999`, the multiplication overflows once `num_bytes > u64::MAX / byte_fee ≈ 18_446`. The only gate standing between the attacker and this code path is `validate_deploy_global_contract_action`, which only rejects code larger than `limit_config.max_contract_size` (`4_194_304` bytes at PROTOCOL_VERSION 87). [4](#0-3)  That leaves an enormous window (~18.4 KB to 4 MiB) of contract sizes that pass validation but overflow the fee multiplication.

By contrast, the `DeployContract` byte fee is `6_812_999`/`47_683_715`/`64_572_944` (per the PROTOCOL_VERSION 87 config snapshot), which multiplied by the same `4_194_304` byte ceiling yields at most ≈`2.7×10^14`, comfortably inside `u64` range. [5](#0-4)  So the two branches are asymmetric not because of a different size limit (they share `max_contract_size`), but because the `deploy_global_contract_byte` fee constant is far too large relative to that shared limit.

Exploit flow: an ordinary account signs and submits a single `DeployGlobalContract` transaction (or wraps it in a `SignedDelegateAction`/`DelegateV2`) with code (real or arbitrary bytes — no wasm validity is required before this arithmetic runs) of, e.g., 20 KB. `validate_deploy_global_contract_action` passes because 20 KB < 4 MiB. `total_send_fees` is invoked during transaction admission/receipt creation to compute gas fees; the `.unwrap()` panics deterministically on every node that processes this transaction/receipt because the computation is a pure function of the transaction bytes.

### Impact Explanation
This is a `METERING_TOTALITY` violation causing a deterministic-abort panic reachable by an ordinary user's transaction. Since `total_send_fees` executes identically and deterministically on every node applying the same transaction/receipt, this triggers a shard/chain-halting panic rather than a mere metering inaccuracy — it maps to the "shard-halting panic" / consensus-divergence-via-crash bounty category. Because a `checked_mul` deliberately returns `Err`/`None` (not `panic!`) on overflow, an `.unwrap()` immediately following it converts a benign, unavoidable configuration/limit mismatch into a runtime panic on every replica.

### Likelihood Explanation
- Preconditions: none beyond a funded account and the ability to submit a `DeployGlobalContract` (or delegated) transaction — ordinary unprivileged capabilities.
- Cost: trivial; a ~20 KB payload is cheap to construct and well under the enforced 4 MiB ceiling, so it is guaranteed to pass `validate_deploy_global_contract_action`.
- Feasibility: fully deterministic and repeatable — the same transaction bytes will overflow on every node running the same protocol version/config.
- The only uncertainty is whether the exact numeric fee value (`999_999_999_999_999`) from the base `parameters.yaml` is still the live, un-overridden value at `PROTOCOL_VERSION 87` in the actual `RuntimeConfigStore`, since diff files for later versions can override individual parameters. This must be confirmed by resolving `RuntimeConfigStore::get_config(87)` directly (as the question's proof idea suggests) rather than relying solely on the base YAML.

### Recommendation
- Re-derive `action_deploy_global_contract_per_byte` (and `action_deploy_global_contract`) to a value consistent with `max_contract_size`, i.e., choose `byte_fee` such that `byte_fee * max_contract_size` cannot exceed `u64::MAX` for any protocol version where the `GlobalContract` feature is enabled.
- Replace the `.unwrap()` calls in `total_send_fees` (and the mirrored ones in `total_prepaid_send_fees`/execution-fee equivalents) with `checked_mul`/`checked_add` propagated as `IntegerOverflowError`, so that a fee-constant/limit mismatch degrades to a rejected transaction instead of a node panic.
- Add a config-invariant test that, for every protocol version in `RuntimeConfigStore`, asserts `fees.fee(ActionCosts::deploy_global_contract_byte).send_fee(_).checked_mul(limit_config.max_contract_size)` (and the equivalent for `deploy_contract_byte`) does not overflow.

### Proof of Concept
Rust unit test in `runtime/runtime/src/config.rs` (or `action_validation.rs`):
```rust
#[test]
fn deploy_global_contract_byte_fee_overflow() {
    let store = near_parameters::RuntimeConfigStore::new(None); // or ::test()/mainnet store
    let config = store.get_config(87);
    let max_size = config.wasm_config.limit_config.max_contract_size;
    let byte_fee = config.fees.fee(ActionCosts::deploy_global_contract_byte).send_fee(false);
    // Expect this to overflow given byte_fee ~ 999_999_999_999_999 and max_size = 4_194_304
    assert!(byte_fee.checked_mul(max_size).is_none());
}
```
Additionally, an integration/test-loop reproduction: submit a `DeployGlobalContract` transaction with `code.len() == 20_000` from a funded test account and assert the runtime returns a graceful error instead of panicking inside `total_send_fees`.

/// Validates `DeployContractAction`. Checks that the given contract size doesn't exceed the limit.
fn validate_deploy_contract_action(
    limit_config: &LimitConfig,
    action: &DeployContractAction,
) -> Result<(), ActionsValidationError> {
    if action.code.len() as u64 > limit_config.max_contract_size {
        return Err(ActionsValidationError::ContractSizeExceeded {
            size: action.code.len() as u64,
            limit: limit_config.max_contract_size,
        });
    }

    Ok(())
}

/// Validates `DeployGlobalContractAction`. Checks that the given contract size doesn't exceed the limit.
fn validate_deploy_global_contract_action(
    limit_config: &LimitConfig,
    action: &DeployGlobalContractAction,

    if action.code.len() as u64 > limit_config.max_contract_size {
        return Err(ActionsValidationError::ContractSizeExceeded {
            size: action.code.len() as u64,
            limit: limit_config.max_contract_size,
        });
    }

    Ok(())
}
