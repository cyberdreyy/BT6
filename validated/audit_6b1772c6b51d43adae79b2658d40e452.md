### Title
`setRewardsDuration` is permanently uncallable because `depositReward` continuously pushes `periodFinish` forward - (File: contracts/StakingRewards.sol)

### Summary
The credit-vault repo contains the exact same bug class as the external report, verbatim: `StakingRewards.setRewardsDuration` (and its sibling `DelegateStakingRewardsIDLE.setRewardsDuration`) requires `block.timestamp > periodFinish`, while `depositReward` sets `periodFinish = block.timestamp + rewardsDuration` on every call. Since `depositReward` is invoked by `rewardsDistribution` each time the IdleCDO forwards rewards/fees for staking, `periodFinish` is perpetually re-extended by `rewardsDuration` (default 7 days), leaving no gap in which the owner can ever update `rewardsDuration`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`StakingRewards.sol` is wired into the credit vault via `stakeFor`, which lets the IdleCDO (as `rewardsDistribution`) stake tranche tokens received as fees for `feeReceiver`, and `depositReward`, which notifies new reward amounts. [5](#0-4) 

The owner-only setter is gated on the reward period being over:

```solidity
function setRewardsDuration(uint256 _rewardsDuration) external onlyOwner {
    require(
        block.timestamp > periodFinish,
        "Previous rewards period must be complete before changing the duration for the new period"
    );
    rewardsDuration = _rewardsDuration;
    emit RewardsDurationUpdated(rewardsDuration);
}
```

But `depositReward` unconditionally rolls the window forward:

```solidity
lastUpdateTime = block.timestamp;
periodFinish = block.timestamp + rewardsDuration;
```

So each reward notification — the routine, honest operation of the system — resets a `rewardsDuration`-long timer. Because the notifier interval is far shorter than `rewardsDuration` (fees accrue and are forwarded every epoch/interaction, versus a 7-day duration), there is effectively never a timestamp where `block.timestamp > periodFinish`. The owner can only succeed if reward deposits cease entirely for more than `rewardsDuration`, which is outside the owner's control. [1](#0-0) [6](#0-5) 

Note: unlike the Berachain version, no unprivileged attacker action is required — the permanent gate is produced by the honest `rewardsDistribution` caller's own regular `depositReward` calls. An unprivileged user cannot make the situation worse, but also nothing an unprivileged user does is needed to trigger it; the invariant "owner can reconfigure rewardsDuration" is broken by design.

### Impact Explanation
Permanent freezing of a governance parameter: `rewardsDuration` can never be changed while rewards are being deposited. If the emission rate needs to be adjusted (e.g., rewards are dripping too fast, the pool's reward economics need reconfiguration, or `rewardRate` must be slowed), the owner's only recourse is for `rewardsDistribution` to stop calling `depositReward` for >7 days — i.e., halt reward deposits entirely — which stalls stakers' yield. No direct theft of user funds, but reward-distribution configuration is bricked under normal operation, matching the medium-risk classification of the source report.

### Likelihood Explanation
Certain under normal operation. `depositReward` is called on the schedule of the rewardsDistribution/IdleCDO fee flow — far more frequently than the 7-day `rewardsDuration` — so `periodFinish` stays strictly in the future indefinitely. The revert path is the only reachable path for `setRewardsDuration` unless rewards stop entirely. The same defect exists in `DelegateStakingRewardsIDLE.sol` lines 182-189. [3](#0-2) 

### Recommendation
Remove the `block.timestamp > periodFinish` requirement (as Berachain did in the referenced fix) and allow `rewardsDuration` to be updated at any time. To keep accounting correct for stakers mid-period, roll up accrued rewards first — e.g., apply the `updateReward(address(0))` modifier or snapshot `rewardPerTokenStored`/`lastUpdateTime` before mutating `rewardsDuration`, and optionally roll `leftover` into `rewardRate` the same way `depositReward` does when `block.timestamp < periodFinish`. Apply the identical fix to `DelegateStakingRewardsIDLE.setRewardsDuration`.

### Proof of Concept
Foundry fork test sketch:

```solidity
function testSetRewardsDurationAlwaysReverts() external {
    // stakingRewards deployed with rewardsDuration = 7 days, rewardsDistribution = IdleCDO
    // 1. Simulate normal operation: rewardsDistribution deposits rewards
    vm.startPrank(rewardsDistribution);
    rewardsToken.approve(address(stakingRewards), 100e18);
    stakingRewards.depositReward(address(0), 100e18);
    vm.stopPrank();

    // 2. Owner attempts to shorten duration repeatedly over time
    for (uint256 i = 0; i < 10; i++) {
        vm.warp(block.timestamp + 1 days); // less than 7-day rewardsDuration
        // honest depositReward keeps arriving from rewardsDistribution
        vm.startPrank(rewardsDistribution);
        rewardsToken.approve(address(stakingRewards), 1e18);
        stakingRewards.depositReward(address(0), 1e18); // re-extends periodFinish
        vm.stopPrank();

        vm.prank(owner);
        vm.expectRevert("Previous rewards period must be complete before changing the duration for the new period");
        stakingRewards.setRewardsDuration(3 days);
    }
    // setRewardsDuration never succeeds while deposits continue
}
```

Each iteration shows `periodFinish` being pushed `block.timestamp + 7 days` into the future again, so the owner's call reverts at every point in time.

```text
  function depositReward(address, uint256 reward) external onlyRewardsDistribution updateReward(address(0)) {
    if (shouldTransfer) {
      rewardsToken.safeTransferFrom(msg.sender, address(this), reward);
    }

    if (block.timestamp >= periodFinish) {
      rewardRate = reward / rewardsDuration;
    } else {
      uint256 remaining = periodFinish - block.timestamp;
      uint256 leftover = remaining * rewardRate;
      rewardRate = (reward + leftover) / rewardsDuration;
    }

    // Ensure the provided reward amount is not more than the balance in the contract.
    // This keeps the reward rate in the right range, preventing overflows due to
    // very high values of rewardRate in the earned and rewardsPerToken functions;
    // Reward + leftover must be less than 2^256 / 10^18 to avoid overflow.
    uint balance = rewardsToken.balanceOf(address(this));
    require(rewardRate <= balance / rewardsDuration, "Provided reward too high");

    lastUpdateTime = block.timestamp;
    periodFinish = block.timestamp + rewardsDuration;

    emit RewardAdded(reward);
```
