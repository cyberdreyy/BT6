### Title
Fee recipient rotation causes permanent loss of previously accrued fees for the outgoing recipient - ([File: v3/src/core/FeeVault.sol])

### Summary
`FeeVault.claimFees()` is gated by an `onlyFeeRecipient` modifier that checks `msg.sender == feeRecipient` (the *current* recipient) [1](#0-0) , while fee accrual in `BaseFeeCalculator`/`DelayedFeeCalculator` is tracked per-vault, not per-recipient, via `_vaultAccruals[vault].accruedFees` [2](#0-1) . When the vault owner calls `setFeeRecipient` to rotate the recipient [3](#0-2) , no claim/flush of previously earned fees is performed for the outgoing recipient. Because the accrued balance is keyed by vault address rather than by recipient, the new recipient can later call `claimFees()` and sweep the entire outstanding balance — including fees earned while the previous recipient held the role — permanently locking the prior recipient out of yield they already earned.

### Finding Description
This mirrors the M-8 pattern exactly: an access-control modifier (`onlyFeeRecipient`, analogous to `onlyStaker`) ties the ability to claim previously accrued rewards to a *current* role assignment rather than to the entity that actually earned them. Once that role is reassigned by an ordinary admin action (`setFeeRecipient`, analogous to unstaking/forced removal), the prior holder permanently loses access to funds already attributable to them, and the invariant "earned fees are eventually claimable by the earner" is broken.

Concretely:
1. `feeCalculator.claimFees()` accrues and decrements `vaultAccruals.accruedFees` keyed by `msg.sender` (the vault) — it has no concept of "who was feeRecipient when this fee accrued" [2](#0-1) .
2. `DelayedFeeCalculator._accrueFees` similarly only tracks state per vault (`vaultAccruals.accruedFees += ...`), with no snapshot of which recipient address is entitled to which slice [4](#0-3) .
3. `FeeVault.claimFees()` is restricted with `onlyFeeRecipient`, i.e. only whoever `feeRecipient` currently points to can pull the pooled balance out [5](#0-4) .
4. `setFeeRecipient(newRecipient)` (owner-only, `requiresAuth`) simply overwrites `feeRecipient` with no interaction with the fee calculator to settle/flush the outgoing recipient's share first [3](#0-2) .

Result: if recipient A has accrued fees but hasn't called `claimFees()` yet, and the owner rotates to recipient B (a routine, non-malicious operational action — e.g., a strategy migrating fee payout address), A can never claim those fees again (the `onlyFeeRecipient` check now fails for A), and B will receive them instead when B later calls `claimFees()`.

This differs from the `AeraVaultV2.claim()` design, which correctly avoids this exact bug: there, `fees[msg.sender]` is a balance keyed by the historical recipient address itself, not gated by a current-role check, so a former fee recipient retains permanent access to their already-reserved balance [6](#0-5) . The v3 `FeeVault`/`BaseFeeCalculator` design regressed from that pattern by keying accrual state to the vault and gating the claim by current role.

### Impact Explanation
Loss/freezing of already-earned, unclaimed protocol/vault fee yield for the outgoing fee recipient — the exact class of impact described in the M-8 report (loss of previously accrued, legitimately earned rewards due to a role-based access-control check that doesn't survive role reassignment). Funds are not burned but are effectively redirected to the new recipient, i.e., theft of the old recipient's yield.

### Likelihood Explanation
Requires only a normal, expected operational action: the vault owner calling `setFeeRecipient` to rotate the fee payout address (no exploit, no attacker collusion needed — this is a documented, intended admin function). Any vault deployed via `SingleDepositorVaultFactory` / `MultiDepositorVaultFactory` using `FeeVault` + `BaseFeeCalculator`/`DelayedFeeCalculator` is affected whenever there is a nonzero unclaimed `accruedFees` balance at the time of rotation. This is highly likely to occur in practice (e.g., fee recipient address migration, key rotation, or replacing a departing party) since nothing in the code path prompts or forces settlement before reassignment.

### Recommendation
Before changing `feeRecipient` in `setFeeVault.sol::setFeeRecipient`, force a settlement: call into the fee calculator's claim path for the outgoing recipient and transfer the currently accrued balance to the old recipient (or explicitly snapshot per-recipient accrued balances similar to the `fees[msg.sender]` pattern used in `AeraVaultV2`), so that historical accrual is not silently transferred to whoever the `feeRecipient` slot happens to point to at claim time. Alternatively, drop the `onlyFeeRecipient` gate and instead track a claimable balance per address (as in v2), so any address that has funds owed to it can call the claim function regardless of the current `feeRecipient` value.

### Proof of Concept
1. Deploy a vault via `SingleDepositorVaultFactory`/`MultiDepositorVaultFactory` wired to `DelayedFeeCalculator`, with `feeRecipient = A`.
2. Advance time / submit snapshots so that `DelayedFeeCalculator.accrueFees(vault)` accrues a nonzero `accruedFees` for the vault (verify via `previewFees(vault, type(uint256).max)`).
3. As the vault owner, call `setFeeRecipient(B)`.
4. As `A`, call `vault.claimFees()` → reverts with `Aera__CallerIsNotFeeRecipient` (assert revert).
5. As `B`, call `vault.claimFees()` → succeeds and transfers the full `accruedFees` balance (including the portion earned while `A` was recipient) to `B` (assert `FEE_TOKEN.balanceOf(B)` increased by the pre-rotation accrued amount, and `A`'s balance remains 0).
6. This demonstrates permanent, unrecoverable loss of A's earned fees and their reassignment to B without any consent or compensation mechanism.

    function claimFees(uint256 feeTokenBalance) external virtual returns (uint256, uint256, address) {
        // Effects: hook called before claiming fees
        _beforeClaimFees();

        VaultAccruals storage vaultAccruals = _vaultAccruals[msg.sender];

        uint256 vaultEarnedFees = vaultAccruals.accruedFees;
        uint256 protocolEarnedFees = vaultAccruals.accruedProtocolFees;
        uint256 claimableProtocolFee = Math.min(feeTokenBalance, protocolEarnedFees);

            vaultAccruals.accruedFees = uint112(vaultEarnedFees - claimableVaultFee);
        }

    function _accrueFees(
        VaultSnapshot storage vaultSnapshot,
        VaultAccruals storage vaultAccruals,
        uint256 lastFeeAccrualCached
    ) internal returns (uint256 protocolFeesEarned, uint256 vaultFeesEarned) {
        uint256 snapshotTimestamp = vaultSnapshot.timestamp;
        if (lastFeeAccrualCached >= snapshotTimestamp || vaultSnapshot.finalizedAt > block.timestamp) {
            // nothing to accrue
            return (0, 0);
        }

        // pending snapshot has become active, accrue fees
        (uint256 vaultPerformanceFeeEarned, uint256 protocolPerformanceFeeEarned) = _calculatePerformanceFees(
            vaultAccruals.fees.performance, vaultSnapshot.highestProfit, vaultSnapshot.lastHighestProfit
        );

        (uint256 vaultTvlFeeEarned, uint256 protocolTvlFeeEarned) = _calculateTvlFees(
            vaultAccruals.fees.tvl, vaultSnapshot.averageValue, snapshotTimestamp, lastFeeAccrualCached
        );

        // Effects: update the vault's state
        vaultSnapshot.lastHighestProfit = vaultSnapshot.highestProfit;
        vaultSnapshot.lastFeeAccrual = uint32(snapshotTimestamp);
        vaultAccruals.accruedFees += (vaultPerformanceFeeEarned + vaultTvlFeeEarned).toUint112();
        vaultAccruals.accruedProtocolFees += (protocolPerformanceFeeEarned + protocolTvlFeeEarned).toUint112();

        // Effects: delete the pending snapshot
        vaultSnapshot.averageValue = 0;
        vaultSnapshot.highestProfit = 0;
        vaultSnapshot.timestamp = 0;
        vaultSnapshot.finalizedAt = 0;

        protocolFeesEarned = protocolPerformanceFeeEarned + protocolTvlFeeEarned;
        vaultFeesEarned = vaultPerformanceFeeEarned + vaultTvlFeeEarned;
    }

    function claim() external override nonReentrant reserveFees {
        uint256 reservedFee = fees[msg.sender];

        // Requirements: check that there are fees to claim.
        if (reservedFee == 0) {
            revert Aera__NoClaimableFeesForCaller(msg.sender);
        }

        uint256 availableFee =
            Math.min(_feeToken.balanceOf(address(this)), reservedFee);

        // Requirements: check that fees are available to claim.
        if (availableFee == 0) {
            revert Aera__NoAvailableFeesForCaller(msg.sender);
        }

        // Effects: update fee total.
        feeTotal -= availableFee;
        reservedFee -= availableFee;

        // Effects: update leftover fee.
        fees[msg.sender] = reservedFee;

        // Interactions: transfer fee to caller.
        _feeToken.safeTransfer(msg.sender, availableFee);

        // Log the claim.
        emit Claimed(msg.sender, availableFee, reservedFee, feeTotal);
    }
