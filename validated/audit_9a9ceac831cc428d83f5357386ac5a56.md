### Title
Retroactive tranche APR split reconfiguration lets a tranche holder steal accrued yield - ([File: contracts/IdleCDO.sol](contracts/IdleCDO.sol))

### Summary

`setTrancheAPRSplitRatio` changes the yield-split parameter without first crystallizing accrued NAV. The next deposit or withdrawal calls `_updateAccounting`, which applies the new ratio to the entire NAV delta accumulated since `lastNAVAA` and `lastNAVBB` were last checkpointed, not only to yield earned after the change. [1](#0-0) [2](#0-1) 

### Finding Description

`setTrancheAPRSplitRatio` only validates the new value and writes it to storage; it does not call `_updateAccounting`. [1](#0-0) 

Deposits call `_updateAccounting` before minting new shares, and withdrawals do the same before calculating the redemption amount. Consequently, the first unprivileged user transaction after an owner reconfiguration forces all pending yield or loss to be allocated with the new ratio. [3](#0-2) [4](#0-3) 

`_updateAccounting` computes `totalGain = nav - lastNAV`, where `lastNAV` is the previous checkpoint rather than the owner transaction timestamp or block. It then supplies the currently stored `trancheAPRSplitRatio` to `_virtualPriceAux`. [2](#0-1) [5](#0-4) 

For example, a vault can accrue yield while the ratio allocates it to BB. If the owner later changes the ratio to 100% AA, an existing AA holder can submit a dust deposit or withdrawal and crystallize all historical accrued yield into the AA NAV and price. [6](#0-5) 

The credit-vault implementation has the same accounting pattern: it reads the current `trancheAPRSplitRatio` and applies it to `nav - lastNAV` before updating `priceAA`, `priceBB`, `lastNAVAA`, and `lastNAVBB`. [7](#0-6) 

### Impact Explanation

The broken invariant is fair yield allocation between AA and BB tranche holders. A ratio intended to govern future yield is instead applied to yield that accrued before the configuration change. [5](#0-4) 

An attacker who already holds the favored tranche can wait for an honest owner ratio update, immediately trigger `_updateAccounting`, and withdraw the misallocated yield. The loss is bounded by the uncheckpointed NAV delta multiplied by the effective change in the other tranche’s allocation; in the extreme, changing from 0% AA to 100% AA transfers the entire pending gain to AA holders. [6](#0-5) [1](#0-0) 

### Likelihood Explanation

The attack requires three ordinary events: tranche positions exist, NAV has changed since the last checkpoint, and the owner changes `trancheAPRSplitRatio` before any user accounting transaction. The attacker is only an existing tranche holder and does not need privileged access; being the first depositor or withdrawer after the owner transaction is sufficient. [8](#0-7) [1](#0-0) 

No existing guard prevents this sequence. `_updateAccounting` intentionally accepts pending NAV movement, and the setter performs only an upper-bound check without checkpointing that movement first. [2](#0-1) [1](#0-0) 

### Recommendation

Checkpoint accounting before applying configuration values that affect pending NAV. At minimum, `setTrancheAPRSplitRatio`, `setMinAprSplitAYS`, and performance-fee configuration should call `_updateAccounting` under the old parameters before writing the new parameters, subject to the existing default-handling rules. [2](#0-1) [9](#0-8) 

If a checkpoint cannot safely be performed inside the setter because loss handling could trigger a default path, require an explicit owner-controlled checkpoint in the same transaction and document that ordering in the setter, or atomically bundle the checkpoint and configuration change through a dedicated guarded function. [10](#0-9) [11](#0-10) 

### Proof of Concept

The following test can be added to a Foundry suite derived from `test/foundry/TestIdleCDOBase.sol`. The direct underlying balance increase models a realized but not-yet-checkpointed strategy gain.

```solidity
function testRetroactiveAprSplitStealsPendingYield() external {
    address attacker = makeAddr("attacker");
    address victim = makeAddr("victim");

    uint256 attackerPrincipal = 1;
    uint256 victimPrincipal = 1_000 * ONE_SCALE;
    uint256 pendingGain = 100 * ONE_SCALE;

    deal(address(underlying), attacker, attackerPrincipal + 1);
    deal(address(underlying), victim, victimPrincipal);

    vm.startPrank(owner);
    idleCDO.setIsAYSActive(false);
    idleCDO.setFeeParams(owner, 0);
    idleCDO.setTrancheAPRSplitRatio(0); // all yield allocated to BB
    vm.stopPrank();

    vm.startPrank(attacker);
    underlying.safeApprove(address(idleCDO), type(uint256).max);
    idleCDO.depositAARef(attackerPrincipal, address(0));
    vm.stopPrank();

    vm.startPrank(victim);
    underlying.safeApprove(address(idleCDO), type(uint256).max);
    idleCDO.depositBBRef(victimPrincipal, address(0));
    vm.stopPrank();

    // Realized NAV increase has not been checkpointed yet.
    deal(
        address(underlying),
        address(idleCDO),
        underlying.balanceOf(address(idleCDO)) + pendingGain
    );

    uint256 attackerUnderlyingBefore = underlying.balanceOf(attacker);

    // Honest owner changes the ratio without checkpointing pending gain.
    vm.prank(owner);
    idleCDO.setTrancheAPRSplitRatio(FULL_ALLOC); // all yield now allocated to AA

    // The attacker is the first unprivileged caller after the configuration.
    vm.startPrank(attacker);
    idleCDO.depositAARef(1, address(0));
    uint256 attackerShares = AAtranche.balanceOf(attacker);
    idleCDO.withdrawAA(attackerShares);
    vm.stopPrank();

    uint256 attackerUnderlyingAfter = underlying.balanceOf(attacker);

    // The attacker receives the pending gain that accrued while BB held the 100% allocation.
    assertApproxEqAbs(
        attackerUnderlyingAfter - attackerUnderlyingBefore,
        attackerPrincipal + pendingGain,
        2,
        "pending yield was retroactively reassigned to AA"
    );
}
```

The decisive step is the attacker’s dust `depositAARef`: it invokes `_updateAccounting` before minting, so the new ratio is applied to the previously accumulated NAV delta and only afterward prices the dust deposit. [12](#0-11)

  function _updateAccounting() internal virtual {
    uint256 _lastNAVAA = lastNAVAA;
    uint256 _lastNAVBB = lastNAVBB;
    uint256 _lastNAV = _lastNAVAA + _lastNAVBB;
    uint256 nav = getContractValue();
    uint256 _aprSplitRatio = trancheAPRSplitRatio;
    // If gain is > 0, then collect some fees in `unclaimedFees`
    if (nav > _lastNAV) {
      unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
    }
    (uint256 _priceAA, int256 _totalAAGain) = _virtualPriceAux(AATranche, nav, _lastNAV, _lastNAVAA, _aprSplitRatio);
    (uint256 _priceBB, int256 _totalBBGain) = _virtualPriceAux(BBTranche, nav, _lastNAV, _lastNAVBB, _aprSplitRatio);
    lastNAVAA = uint256(int256(_lastNAVAA) + _totalAAGain);

    // if we have a loss and it's gte last junior NAV we trigger a default
    if (_totalBBGain < 0 && -_totalBBGain >= int256(_lastNAVBB)) {
      // revert with 'default' error (4) if skipDefaultCheck is false, as seniors will have a loss too not covered. 
      // `updateAccounting` should be manually called to distribute loss
      if (!skipDefaultCheck) revert Default();
      // This path will be called when a default happens and guardian calls
      // `updateAccounting` after setting skipDefaultCheck or when skipDefaultCheck is already set to true
      lastNAVBB = 0;
      // if skipDefaultCheck is set to true prior a default (eg because AA is used as collateral and needs to be liquid), 
      // emergencyShutdown won't prevent the current deposit/redeem (the one that called this _updateAccounting) and is 
      // still correct because:
      // - depositBB will revert as priceBB is 0
      // - depositAA won't revert (unless the loss is 100% of TVL) and user will get 
      //   correct number of share at a priceAA already post junior default
      // - withdrawBB will redeem 0 and burn BB tokens because priceBB is 0
      // - withdrawAA will redeem the correct amount of underlyings post junior default
      // We pass true as we still want AA to be redeemable in any case even after a junior default
      _emergencyShutdown(true);
    } else {
      // we add the gain to last saved NAV
      lastNAVBB = uint256(int256(_lastNAVBB) + _totalBBGain);
    }
    priceAA = _priceAA;
    priceBB = _priceBB;
