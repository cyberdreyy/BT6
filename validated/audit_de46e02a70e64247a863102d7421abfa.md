### Title
Attacker-crafted all-zero source buffer causes panic in `SourceBuffer::new_checked_with_verified_build_hash` during core-BPF migration - ([File: runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs])

### Summary
`new_checked_with_verified_build_hash` computes `end_offset` by taking the last non-zero byte index across the *entire* buffer account data (including the metadata region), not just the ELF region after `offset`. If the metadata region contains a non-zero byte (e.g., the `Buffer` enum discriminant) but the entire ELF payload written by the attacker is all zero, `end_offset` can end up smaller than `offset`, causing `&data[offset..end_offset]` to panic with a slice-index violation. This function runs on every validator's replay path when a scheduled core-BPF migration with a verified build hash is triggered by feature activation.

### Finding Description
The vulnerable logic is: [1](#0-0) 

`offset` is `UpgradeableLoaderState::size_of_buffer_metadata()`. `end_offset` is computed via `data.iter().rposition(|&x| x != 0)`, which searches the **whole** `data` slice (metadata bytes included), not just `data[offset..]`. `UpgradeableLoaderState::Buffer { authority_address }` is a bincode-serialized enum; the variant discriminant itself is a non-zero value written at the start of the metadata region, while the rest of the fixed-size metadata region (e.g., an absent authority `Option::None` tag, or unused padding) can be zero. If the attacker writes an ELF/program-data region that is entirely zero bytes (e.g., via `InitializeBuffer` then `Write` with an all-zero payload, or simply never writing anything past a large zero-initialized buffer), the last non-zero byte in `data` is the discriminant byte located *inside* the metadata region, at some index `i < offset`. Then `end_offset = i + 1 <= offset`, and since it's strictly less than `offset` in general (the discriminant is not immediately before `offset`), the slice `&data[offset..end_offset]` has `end_offset < offset`, which panics with "slice index starts at X but ends at Y" (Rust panics whenever a slice's start > end, even for otherwise in-bounds indices).

The reachable path is:
- Attacker calls `SystemProgram::CreateAccount` on the hardcoded `source_buffer_address` used by an upcoming `CoreBpfMigrationConfig` (these addresses are public constants in `solana_builtins::core_bpf_migration`).
- Attacker calls `bpf_loader_upgradeable::InitializeBuffer` and `Write` (or simply never writes any non-zero bytes past the metadata) to produce a `Buffer` account whose data after `size_of_buffer_metadata()` is entirely zero.
- `new_checked` (called first inside `new_checked_with_verified_build_hash`) only validates that the leading `size_of_buffer_metadata()` bytes deserialize to `UpgradeableLoaderState::Buffer`, it does not validate anything about the data following it: [2](#0-1) 
- When the feature-activation slot arrives, `Bank::migrate_builtin_to_core_bpf` (in `runtime/src/bank.rs`) invokes `new_checked_with_verified_build_hash` for build-hash-verified migrations, executing the vulnerable slicing logic on attacker-controlled account bytes on every validator processing that block, since this runs in the replay/bank-freeze path rather than inside a transaction (so normal instruction-level panic-catching/`InstructionError` machinery does not protect it).

No existing check constrains the byte content of the region after the metadata (only that the account is owned by the upgradeable loader and that the first `size_of_buffer_metadata()` bytes deserialize as `UpgradeableLoaderState::Buffer`), so the attacker fully controls whether the ELF-region bytes are all zero.

### Impact Explanation
This is a replay-path panic reachable by an unprivileged attacker who merely owns/writes an account at a publicly known, hardcoded address ahead of a scheduled feature activation. Because `migrate_builtin_to_core_bpf` runs identically and deterministically on every validator during block/feature-activation processing, the panic occurs simultaneously across the entire validator set, halting the cluster — a liveness-kill via a single pre-positioned (non-privileged) transaction sequence. This matches the "replay-path panic causing validator crash/cluster halt" bounty category.

### Likelihood Explanation
Feasibility is high for an attacker who knows in advance which migration is scheduled and its `source_buffer_address` (public in `solana_builtins::core_bpf_migration`). All the attacker needs is:
1. Fund a keypair, `CreateAccount` at the target address before the feature-activation slot.
2. Call `InitializeBuffer` + (optionally) `Write` with all-zero bytes, or simply create the account with all-zero data beyond the metadata (the buffer only needs to be large enough and pass the `Buffer` state check).
3. Wait for the feature to activate — the crash happens automatically for every validator processing that slot.

No signature bypass, no race condition beyond timing the account creation before the scheduled activation, fully repeatable in a local test harness.

### Recommendation
Restrict the `rposition` search to the ELF region only, and treat "trim trailing zeros" defensively so `end_offset` can never fall below `offset`:
```rust
let offset = UpgradeableLoaderState::size_of_buffer_metadata();
let elf_bytes = data.get(offset..).unwrap_or(&[]);
let end_offset = elf_bytes
    .iter()
    .rposition(|&x| x != 0)
    .map_or(offset, |i| offset + i + 1);
let buffer_program_data = &data[offset..end_offset];
```
This guarantees `end_offset >= offset` unconditionally, eliminating the panic regardless of metadata byte content.

### Proof of Concept
```rust
#[test]
fn test_source_buffer_all_zero_elf_panics() {
    let bank = create_simple_test_bank(0);
    let buffer_address = Pubkey::new_unique();

    let buffer_metadata_size = UpgradeableLoaderState::size_of_buffer_metadata();
    let elf_len = 200;
    let data_len = buffer_metadata_size + elf_len;
    let mut data = vec![0u8; data_len];
    // Metadata: Buffer { authority_address: None } -> discriminant byte(s) nonzero,
    // rest of metadata region (and all ELF bytes) left as zero.
    bincode::serialize_into(
        &mut data[..buffer_metadata_size],
        &UpgradeableLoaderState::Buffer { authority_address: None },
    )
    .unwrap();
    // ELF region intentionally left all-zero (attacker writes no non-zero bytes).

    let lamports = bank.get_minimum_balance_for_rent_exemption(data_len);
    let mut account = AccountSharedData::new(lamports, data_len, &bpf_loader_upgradeable::id());
    account.data_as_mut_slice().copy_from_slice(&data);
    bank.store_account_and_update_capitalization(&buffer_address, &account);

    // Expected (buggy) behavior: this call panics with
    // "slice index starts at <offset> but ends at <end_offset>"
    // instead of returning Err(CoreBpfMigrationError::BuildHashMismatch(..)).
    let _ = SourceBuffer::new_checked_with_verified_build_hash(
        &bank,
        &buffer_address,
        Hash::default(),
    );
}
```
Running this test on the current code panics inside `new_checked_with_verified_build_hash` rather than returning a `BuildHashMismatch` error, confirming the reachable panic.
