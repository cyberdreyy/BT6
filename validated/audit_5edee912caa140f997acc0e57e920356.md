### Title
Stale confirmations from removed multisig members are not purged, allowing a request to execute below the live-member confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
When a multisig member/key is removed via `MultiSigRequestAction::DeleteKey` (`multisig/src/lib.rs`) or `MultiSigRequestAction::DeleteMember` (`multisig2/src/lib.rs`), the contract only purges *requests originated by* the removed signer, but never purges *confirmations that signer previously cast on requests created by other members*. Those stale confirmations remain in the `confirmations` map and continue to count toward `num_confirmations` in `confirm()`, letting a request execute with fewer live-member approvals than the configured threshold. This is the same bug class as the Flayer `relist` finding: a state-mutating path (`delete_key`/`delete_member`) fails to apply the invariant-preserving cleanup that sibling paths (`remove_request`, `delete_request`) already perform, breaking a trust binding — here, "confirmations counted" vs. "confirmations from currently live members."

### Finding Description
`confirm()` in both contracts simply checks the size of the `confirmations` `HashSet` against `num_confirmations`: [1](#0-0) [2](#0-1) 

The set contains public keys / member identifiers previously inserted whenever a member confirmed a request, with no validation at confirm-time that all entries in the set still correspond to current members.

When a key/member is removed, cleanup only targets requests that member *authored*, not confirmations they gave on other members' requests: [3](#0-2) [4](#0-3) 

Compare this to `remove_request`, which is invoked for a specific request during deletion/execution and correctly clears that request's confirmations: [5](#0-4) 

But `delete_member`/`DeleteKey` never call `remove_request`-equivalent cleanup for requests they did **not** author, meaning any confirmation they already cast on a still-pending request from another member survives their removal.

The equality that should hold is:
`confirmations_counted_for_request(R) == confirmations_from_currently_live_members(R)`

After a member is removed, this equality is violated: `confirmations_counted_for_request(R)` still includes the departed member, while `confirmations_from_currently_live_members(R)` does not.

### Impact Explanation
This falls under the explicit Critical impact category "a multisig request executed below threshold." A pending request only needs one *fewer* live confirmation than `num_confirmations` to execute once a prior confirmer is removed, because their stale confirmation is still tallied. Since `execute_request` can perform `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, etc., this allows movement of NEAR or authorization changes with less real-time consensus than the multisig was configured to require — undermining the fundamental custody guarantee of the contract (funds/authority changes require `num_confirmations` concurring *current* signers).

### Likelihood Explanation
The trigger sequence relies only on ordinary multisig lifecycle operations, not on any single privileged bypass or external contract flaw:
1. Member A confirms a pending request R created by another member (a normal partial confirmation, common in any k-of-n workflow where confirmations arrive over time).
2. Members later remove A as part of routine key rotation/offboarding (a legitimate `DeleteKey`/`DeleteMember` action, itself requiring its own threshold — but this is independent of R and is a common operational event, not an attack).
3. A remaining live member confirms R, and R executes using A's now-stale confirmation to reach threshold.

No malicious input is needed to trigger the state divergence — it is a missing invariant in the removal path. Any multisig relying on periodic key rotation while having outstanding requests is exposed.

### Recommendation
When removing a member/key (`DeleteKey` in `multisig/src/lib.rs`, `DeleteMember` in `multisig2/src/lib.rs`), iterate over `confirmations` for **all** pending requests (not just requests authored by the removed member) and strip the removed identity from each confirmation set, re-checking the removal doesn't retroactively make the entry inconsistent. Alternatively, validate at `confirm()`/execution time that every entry in a request's confirmation set still corresponds to a current member of `self.members`, discarding stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 3 members `M1, M2, M3` and `num_confirmations = 2` (`multisig2/src/lib.rs::new`).
2. `M1` calls `add_request` to create request `R` (e.g. `Transfer` of funds) — confirmations for `R` = `{}`.
3. `M2` calls `confirm(R)` — confirmations for `R` = `{M2}`; `1 < 2`, so `R` stays pending (`multisig2/src/lib.rs:294-315`).
4. Independently, the group runs a separate multisig flow that removes `M2` via `DeleteMember` (e.g., key rotation). `delete_member` only purges requests *created by* `M2`; `R` (created by `M1`) is untouched, so confirmations for `R` still contain `M2` (`multisig2/src/lib.rs:355-379`).
5. `M3` calls `confirm(R)`. Check: `confirmations.len() (=1, containing removed M2) + 1 = 2 >= num_confirmations (2)` → `R` executes.
6. Result: `R` executes having received only one confirmation from a currently valid member (`M3`), with the second "confirmation" coming from `M2`, who is no longer a member and no longer holds signing authority — the transfer moves funds below the intended 2-of-3 live-member threshold.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
