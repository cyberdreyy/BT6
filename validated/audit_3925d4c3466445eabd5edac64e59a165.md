### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether a request is ready to execute purely by comparing the *size* of the `confirmations` set to `self.num_confirmations`, without checking that every entry in that set still corresponds to a current member. `delete_member` only purges confirmations/requests that were *created* by the removed member, leaving any confirmation that member previously cast on requests created by someone else stranded in the `confirmations` map. A request can therefore reach the required confirmation count using a mix of live and already-removed members, letting it execute with fewer than `num_confirmations` currently-trusted signers.

### Finding Description
`confirm` reads the stored confirmation set and executes the request once its length plus the new confirmer reaches the threshold: [1](#0-0) 

It never re-validates that the pre-existing entries in `confirmations` belong to accounts/keys still present in `self.members`.

`delete_member` removes a departing member from `self.members`, and cleans up only the requests *that member itself created* (`r.member == member`), plus that member's `num_requests_pk` entry: [2](#0-1) 

Crucially, it never scans `self.confirmations` to strip the removed member's confirmation string out of requests created by *other* members. If member `A` confirmed a request created by member `B`, and `A` is later removed via `DeleteMember`, `A`'s confirmation entry survives inside that request's `confirmations` HashSet forever, and `A`'s deleted access key can never be replayed to confirm again — but the stale count remains and still counts toward the threshold in `confirm`.

This breaks the intended invariant "confirmations counted == live members who confirmed." The multisig's core guarantee — that `num_confirmations` *current* members must approve an action — is not actually enforced once membership changes while requests are outstanding.

### Impact Explanation
This falls under the explicit Critical impact category "a multisig request executed below threshold." An attacker (or any legitimate member acting in the ordinary flow, without needing special privileges beyond being a member at some point) can arrange for a request to execute with genuine assent from fewer than `num_confirmations` still-trusted members, because one or more of the counted confirmations come from an account/key that has since been deleted from the multisig. This can be used to push through a `Transfer`, `AddKey`, `FunctionCall`, or `AddMember`/`DeleteMember` action that should have required more live approvals — directly undermining the K-of-N security model the contract advertises.

### Likelihood Explanation
No special access is required beyond being any member of the multisig at the time a request is pending, which is the contract's normal operating mode. Membership changes (`DeleteMember`) are a routine, documented multisig operation (e.g., rotating out a compromised or departing signer) documented in `multisig2/README.md`. Any request left pending across such a member-removal event is silently exposed to this issue — it does not require any unusual sequencing beyond leaving a request unconfirmed while the removal request is processed, which is a common real-world scenario (removals are frequently used precisely because a member is untrusted, while other requests may still be in flight).

### Recommendation
When executing `DeleteMember`, iterate over all pending requests' `confirmations` sets (not just the ones the removed member authored) and remove the departing member's entry from each. Alternatively/additionally, in `confirm`, filter `confirmations` against `self.members` before counting (`confirmations.iter().filter(|m| self.members.contains(m)).count()`), so stale confirmations from removed members never contribute toward the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C], num_confirmations = 2)`.
2. `B` calls `add_request(transfer_request)` → request created with `member = B`, `confirmations = {}`.
3. `A` calls `confirm(request_id)` → `confirmations = {A}`, count 1 < 2, request stays pending (see `confirm`, `multisig2/src/lib.rs:292-315`).
4. Through the normal multisig flow, `B` and `C` jointly confirm a separate `DeleteMember { member: A }` request; it executes, calling `delete_member(promise, A)` (`multisig2/src/lib.rs:356-379`). Because the pending transfer request's `member` field is `B` (not `A`), it is not among the requests cleaned up, so `confirmations = {A}` remains attached to it, and `A`'s access key is now deleted from the account.
5. `C` calls `confirm(request_id)` on the still-pending transfer request. `confirmations.len() (1) + 1 == 2 >= num_confirmations (2)` → the request executes (`multisig2/src/lib.rs:304-309`), even though only one currently-live member (`C`) actually approved it live; the other "confirmation" belongs to `A`, who has already been removed from the multisig and cannot even be a signer anymore.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
