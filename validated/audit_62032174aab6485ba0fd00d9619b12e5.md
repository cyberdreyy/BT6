### Title
`IdleCreditVault.claimInstantWithdrawRequest()` clears the aggregate receipt but never clears `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`, letting an already-paid instant receipt be claimed again from the default-recovery reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The reported Knox bug is a removal path that fails to update a bookkeeping index correctly (`index.length` set to `1` instead of `0` when the last element is removed), leaving a stale non-zero counter that later reads treat as a real entry. The same bug class exists in `IdleCreditVault.claimInstantWithdrawRequest`: the per-user aggregate `instantWithdrawsRequests[_user]` is zeroed, but the per-epoch index entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are never decremented. After that epoch defaults, `_claimDefaultedInstantWithdrawRequest` treats the stale per-epoch entry as an unfunded defaulted receipt and pays it out again from `defaultRecoveryReserve`.

### Finding Description
In `requestInstantWithdraw` the vault records three counters for the same receipt:

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
``` [1](#0-0) 

When the claim is later executed, only the aggregate is cleared — the per-epoch index is left non-zero:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

This is the exact analog of `index.length = index.length > 0 ? index.length - 1 : 1;`: the removal path leaves a stale positive value in an index that other code trusts. If the epoch in which the instant request was recorded subsequently ends in a borrower default, `defaultRecoveryEpoch` is set to that same epoch and `defaultInstantWithdrawsFinalized` is set during finalization. On the next `claimInstantWithdrawRequest` call, `_claimDefaultedInstantWithdrawRequest` runs first and reads the stale entry:

```solidity
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
if (claimBasis == 0) return claimBasis;
instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
instantWithdrawsRequests[_user] -= claimBasis;
pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
_burn(_user, claimBasis);
_transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
``` [3](#0-2) 

An attacker who already claimed the receipt at par can register a fresh instant request after finalization so that `instantWithdrawsRequests[_user]` and their strategy-token receipt balance are again ≥ `claimBasis`. The subtraction and `_burn` then succeed, and `_transferDefaultRecovery` pays `claimBasis * defaultRecoveryPrice / 1e18` out of `defaultRecoveryReserve` for a receipt that was already fully paid in the funded epoch.

Additionally, `instantWithdrawClaimsByEpoch` is never reduced on a normal claim, so at default finalization the aggregate per-epoch pending basis used for recovery accounting (`defaultPendingClaimBasis`) is inflated by already-paid claims, distorting `defaultRecoveryPrice` / the reserve computation.

### Impact Explanation
Direct theft plus insolvency of the default-recovery reserve. The attacker's stale per-epoch receipt is paid a second time from `defaultRecoveryReserve`, which is denominated in underlying reserved for legitimate defaulted-epoch claimants (normal, APR0, and instant receipts plus post-default requests). Each duplicated claim drains the reserve, so honest users' recovery claims either underflow/revert or receive less than their entitlement — a solvency break of the reserve invariant (`sum of recovery payouts ≤ defaultRecoveryReserve`). The inflated `instantWithdrawClaimsByEpoch` can also cause the finalizer's accounting to over-reserve pending claims, mispricing `defaultRecoveryPrice` for everyone.

### Likelihood Explanation
The sequence requires no privileged misbehavior and a common ordering:

1. During a running epoch N the attacker requests an instant withdraw via `IdleCDOEpochVariant.requestWithdraw` (unprivileged, KYC'd lender path).
2. The manager calls `getInstantWithdrawFunds` after the instant delay; the attacker claims at par via `claimInstantWithdrawRequest`. The per-epoch index entries remain non-zero.
3. At `stopEpoch` of the same epoch N the borrower honestly repays short → default path; manager later calls `finalizeDefault`, setting `defaultRecoveryEpoch = N` and `defaultInstantWithdrawsFinalized = true`.
4. The attacker submits a new instant request (still unprivileged; `requestInstantWithdraw` has no post-default guard) large enough to cover the stale `claimBasis`, then calls `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` consumes the stale entry and pays recovery on an already-settled receipt.

Likelihood is moderate: it needs an instant withdrawal that is both requested and funded inside an epoch that later defaults — a plausible but not guaranteed market event. Once it occurs, exploitation is a single additional request+claim by the same unprivileged user.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch bookkeeping alongside the aggregate: track the request epoch(s) for the user (or store the epoch on the receipt) and decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, mirroring how `_clearWithdrawClaimForEpoch` keeps `withdrawsRequestsByEpoch` consistent with `withdrawsRequests`. Alternatively, make `_claimDefaultedInstantWithdrawRequest` clamp `claimBasis` to `min(staleEntry, instantWithdrawsRequests[_user])` and cross-check against `instantWithdrawClaimsByEpoch` so a stale index can never produce a payout exceeding outstanding receipts.

Note: exact assertions for step "finalizeDefault" mirror `testFundedInstantWithdrawRemainsClaimableAfterStopEpochDefault` and `test...instant...default` cases in `test/foundry/IdleCreditVault.t.sol` (lines ~2699–2752, ~4501–4551), which already exercise funded-then-defaulted instant receipts; those tests only assert the funded path, not the stale per-epoch index left behind. One residual uncertainty: whether `requestInstantWithdraw` remains callable through the CDO after `defaultRecoveryFinalized` in every configuration — if a guard blocks it, the impact reduces to a permanent revert (freezing) of the attacker's subsequent instant claims rather than reserve theft; either outcome still violates the "one receipt, one payout" invariant.
