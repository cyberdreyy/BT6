### Title
Missing role restriction on `GET /v2/external_initiators` discloses AccessKey and OutgoingToken of all External Initiators to any authenticated (including view-role) user - ([File: core/web/router.go], [File: core/web/external_initiators_controller.go], [File: core/web/presenters/external_initiators.go])

### Summary
`GET /v2/external_initiators` is registered with only `paginatedRequest(eia.Index)` while the sibling `POST`/`DELETE` routes require `auth.RequiresEditRole`. This lets any authenticated user in the `authv2` group — including a default/view-role session or a restricted API token — enumerate every External Initiator's `Name`, `URL`, `AccessKey`, and `OutgoingToken`.

### Finding Description
In `v2Routes` in `core/web/router.go`, the External Initiators routes are: [1](#0-0) 
`authv2.GET("/external_initiators", paginatedRequest(eia.Index))` has no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, while `POST` and `DELETE` do. The `authv2` group only requires successful token or session authentication (`auth.Authenticate(..., AuthenticateByToken, AuthenticateBySession)`), with no minimum role check — that check is delegated per-route to the `auth.Requires*Role` wrappers, which `Index` lacks.

`ExternalInitiatorsController.Index` (`core/web/external_initiators_controller.go:50-59`) fetches all external initiators from the ORM and maps them through `presenters.NewExternalInitiatorResource`, which returns: [2](#0-1) 
This resource includes `Name`, `URL`, `AccessKey`, and `OutgoingToken` for every stored `bridges.ExternalInitiator` record, sourced from the model at `core/bridges/external_initiator.go:22-34` (`AccessKey`, `Salt`, `HashedSecret`, `OutgoingSecret`, `OutgoingToken`). While `Salt`, `HashedSecret`, and `OutgoingSecret` are correctly excluded from the response DTO, `AccessKey` and `OutgoingToken` are not redacted and are returned in full, in bulk, across all pages, to any caller who merely passes authentication — regardless of role.

The existing integration test confirms this behavior is by design/unguarded: [3](#0-2) 
which asserts `AccessKey` and `OutgoingToken` are returned as-is, with no role-based test variation (unlike other admin-only endpoints in this codebase that have `_NoAdmin` test variants).

### Impact Explanation
`AccessKey` is the credential an external service presents to Chainlink to authenticate inbound webhook/job-run requests, and `OutgoingToken` (paired with `OutgoingSecret`, which is only used for the outbound direction and stays private) is part of the outbound HMAC-style scheme Chainlink uses when calling out to the external initiator's endpoint. Disclosure of `AccessKey` for another integration's External Initiator allows a low-privileged authenticated user to impersonate that external system by presenting the stolen `AccessKey` (though full authentication with `AccessKey`+`Secret` requires `Secret`, which is never stored/returned — only `HashedSecret`/`Salt`). Disclosure of `OutgoingToken` alone provides partial internal credential exposure for that EI's outbound channel. This is a genuine cross-tenant/cross-integration credential disclosure due to an authorization gap (missing role gate consistent with the CRUD siblings), matching Chainlink's "sensitive information disclosure via authorization bypass" bounty class, though the practical impersonation impact is partially mitigated because `Secret` (needed to complete inbound auth) is never exposed.

### Likelihood Explanation
Any principal capable of authenticating to the node's API — a session login with the lowest available role, or an API token scoped to view/run — can immediately call `GET /v2/external_initiators` with no additional privilege. The route is paginated and trivially scriptable to enumerate all records. This is fully repeatable and requires no race conditions, timing, or special preconditions beyond holding any valid credential.

### Recommendation
Wrap the `Index` route with the same role requirement as `Create`/`Destroy` (`auth.RequiresEditRole` or `auth.RequiresAdminRole`, matching the sensitivity of the AccessKey material), e.g.:
```go
authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))
```
Additionally, consider whether `AccessKey`/`OutgoingToken` need to be present at all in the list resource, or if they should be redacted/omitted for non-admin roles, consistent with how `Salt`/`HashedSecret`/`OutgoingSecret` are already excluded.

### Proof of Concept
Add a handler-level integration test analogous to existing `_NoAdmin` tests in the repo (e.g. patterned after `TestBridgeTypesController_Create_NoAdmin`-style tests):
1. Start app with `ExternalInitiatorsEnabled = true`.
2. Insert one `bridges.ExternalInitiator` via `cltest.MustInsertExternalInitiatorWithOpts`.
3. Create an HTTP client authenticated with a **view-role** user/session (`app.NewHTTPClient(&cltest.User{Role: view-role})` or equivalent lowest-privilege client helper used elsewhere in the test suite for negative-role checks).
4. Call `client.Get("/v2/external_initiators")`.
5. Assert `http.StatusOK` is currently returned (expected fix: `http.StatusUnauthorized`/`http.StatusForbidden`).
6. Parse the response and assert it currently contains the seeded initiator's `AccessKey` and `OutgoingToken` (expected fix: request rejected before reaching the controller).
