### Title
Fee-on-transfer underlying causes over-minting and NAV inflation in `depositDuringEpoch` / mid-epoch deposits - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The Allo bug class is "accounting credits the nominal transfer amount instead of the actual amount received" for fee-on-transfer (FoT) tokens. The main deposit paths in this codebase are already protected: `IdleCDO._deposit` and `IdleCDOCreditVault._deposit` mint shares from the measured balance delta (`_contractTokenBalance(_token) - _preBal`). However, `IdleCDOEpochVariant.depositDuringEpoch` performs the pull, the share mint, the `expectedEpochInterest` accrual and the onward transfer to the borrower all using the nominal `_amount`, never measuring what actually arrived. If the vault's underlying token ever charges a fee on transfer (e.g., USDT with fees enabled, or any FoT stable chosen as `token`), the vault credits and forwards value it never received.

### Finding Description
In `depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:656-733):

1. `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` pulls `_amount` from the depositor. With an FoT token, the vault receives only `_amount - fee`.
2. `interest` is computed from the nominal `_amount` (`_calcInterest(_amount)`), and `expectedEpochInterest += interest` inflates the epoch's promised yield by the full amount.
3. Shares are minted as `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` — again on nominal `_amount`.
4. `IdleCreditVault(strategy).mintStrategyTokens(_amount)` mints claim tokens for the full `_amount`.
5. `_transferUnderlyings(_borrower(), _amount)` pushes `_amount` to the borrower.

The borrower's debt and the tranche-holder claims are denominated in the gross `_amount`, while only `_amount - fee` was contributed. The shortfall is silently drawn from whatever token balance the vault held at the time (residual liquidity, funds sent by a write-off fulfiller via `writeOffDeposit`, or pending liquidity not yet skimmed — `_skimDonatedAssets` only sweeps amounts above accounted NAV). If the vault balance is zero the call reverts, so the attack requires an epoch in which the vault carries residual balance during a running epoch, which does occur in the prefunded variant (`IdleCDOEpochVariantPrefunded`) and when escrow/write-off funds sit in the contract.

The same nominal-amount assumption exists in `IdleCDOCreditVault._deposit`, which mints correctly on the delta but then calls `IIdleCDOStrategy(strategy).deposit(_amount)` (IdleCDOCreditVault.sol:211), pulling the gross `_amount` out of the CDO into the strategy — draining more than was deposited if the vault carried any residual balance.

### Impact Explanation
Each mid-epoch deposit mints tranche shares and borrower-debt claims backed by less underlying than accounted. The deficit is socialized: existing tranche holders' NAV is diluted and the vault can end up unable to honor withdrawals at epoch end, i.e., an accounting-driven insolvency / theft of residual funds, quantified as the cumulative FoT fee on every such deposit. This is the exact broken invariant of the source report — internal claim balance exceeds actual token balance.

### Likelihood Explanation
Conditional: it requires (a) an underlying token with non-zero transfer fee (USDT supports an optional fee and is a plausible credit-vault underlying), and (b) the vault holding any residual token balance while an epoch is running so the `_transferUnderlyings(_borrower(), _amount)` doesn't revert. If either fails, the deposit reverts (DoS only, no fund impact). An attacker only needs to be a KYC-passed lender (`isWalletAllowed`) calling `depositDuringEpoch` — an unprivileged action.

Uncertainty I could not fully resolve within the iteration budget: whether a running epoch realistically leaves spendable residual balance in this vault depends on the prefunded/write-off flows; the code paths exist (`IdleCDOEpochVariantPrefunded`, `WriteOffEscrow`), but a deployed-vault configuration with an FoT token is a deployment-time condition rather than guaranteed.

### Recommendation
Measure actual received amount and use it for all accounting, mirroring the already-safe `_deposit` pattern:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
```

Then compute `interest`, `trancheInterest`, `_minted`, `mintStrategyTokens` and the borrower transfer on `_received` instead of `_amount`. Apply the same fix to `IdleCDOCreditVault._deposit`'s `strategy.deposit(_amount)` call (pass the received delta), or skip the strategy deposit and forward only what arrived.

### Proof of Concept
Foundry-style fork test sketch:

```solidity
function testFoTDepositDuringEpoch() public {
    // Assume vault deployed with FoT token (e.g. USDT with fee enabled)
    feeToken.setFee(100); // 1%

    // epoch already started, AA tranche seeded, vault holds residual balance R >= fee shortfall
    // attacker is KYC-allowed
    uint256 amount = 1_000_000e6;
    feeToken.approve(address(cdo), amount);

    uint256 vaultBalBefore = feeToken.balanceOf(address(cdo));
    uint256 shares = cdo.depositDuringEpoch(amount, AATranche);

    // vault forwarded `amount` to borrower but only received `amount * 99/100`
    // shares minted are worth ~amount + interest while only 0.99*amount contributed
    // => vault balance decreased by ~fee, shares over-collateralized claim remains
    assertLt(feeToken.balanceOf(address(cdo)), vaultBalBefore);
    // solvency: tranche NAV claims now exceed recoverable underlying
}
```

The PoC requires a vault instance configured with an FoT underlying and a running epoch — reproducible on a mainnet fork by enabling USDT's transfer fee or by substituting an FoT test token at vault creation.
