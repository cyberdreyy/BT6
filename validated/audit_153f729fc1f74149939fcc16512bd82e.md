### Title
Missing validation of `underlyingsRequested` in `createWriteOffRequest` lets a fulfiller seize escrowed tranche tokens for zero payment - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
The external report's bug class — a function that accepts attacker/user-supplied inputs without validating them, producing unexpected value transfers — maps directly onto `IdleCreditVaultWriteOffEscrow.createWriteOffRequest` / `fullfillWriteOffRequest`. `createWriteOffRequest` validates `amount != 0` and epoch state but never validates `underlyingsRequested`. A request stored with `underlyings == 0` can then be fulfilled by any unprivileged EOA with `_underlyings == 0`, because `fullfillWriteOffRequest` only enforces `_underlyings >= currentRequest.underlyings`. The fulfiller receives the escrowed tranche tokens for free, and the lender receives nothing.

### Finding Description
`createWriteOffRequest` escrows tranche tokens and records the ask:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol
if (amount == 0) revert NotAllowed();              // tranches validated
// underlyingsRequested is NOT validated
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
```

`fullfillWriteOffRequest` then checks:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

If `currentRequest.underlyings == 0`, passing `_underlyings = 0` satisfies the check. The fulfiller pays 0 underlying (0 exit fee is computed), the lender gets `_underlyings - _totFee = 0`, and `IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches)` hands the full escrowed tranche balance to the fulfiller. Note also that `createWriteOffRequest` allows *adding* to an existing request: a second call with `underlyingsRequested = 0` lets a lender accidentally dilute an existing ask — and even with a nonzero ask, a lender can lower their own effective price, but the exploitable case is the zero/degenerate ask.

### Impact Explanation
Direct theft of escrowed tranche tokens by an unprivileged fulfiller: any lender whose stored request has `underlyings == 0` (or an ask far below market because the field is unchecked) loses the full `tranches` amount for zero underlying compensation. Tranche tokens represent a claim on the credit vault's NAV, so the loss equals `virtualPrice * tranches`. Additionally, because `deleteWriteOffRequest` clamps `pendingUnderlyings` with `pendingUnderlyings >= currentRequest.underlyings ? ... : pendingUnderlyings`, the accounting stays consistent and the theft is silent.

### Likelihood Explanation
Requires a lender (KYC'd, unprivileged) to submit a request with `underlyingsRequested = 0` or a mispriced value — no input validation stops this, and there is no UI-level guarantee on-chain. Once such a request exists, fulfillment is permissionless (`fullfillWriteOffRequest` is callable by "any wallet" per its natspec), so a bot can monitor `userRequests` and fulfill degenerate requests atomically in the same block they appear. Cost to the attacker is only gas plus the token approval.

### Recommendation
In `createWriteOffRequest`, revert when `underlyingsRequested == 0` (mirroring the existing `amount == 0` check):

```solidity
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

Optionally add a sanity bound relating the ask to the current tranche `virtualPrice` (e.g., reject asks that imply a price above a configurable multiple of par), since the field is otherwise unconstrained.

### Proof of Concept
Foundry fork-style PoC sketch (credit vault with a running epoch):

```solidity
// setup: vault = IdleCDOEpochVariant with IdleCreditVault strategy,
// escrow = deployed IdleCreditVaultWriteOffEscrow (isAATranche = true),
// lender holds AA tranche tokens, epoch is running.

address fulfiller = makeAddr("fulfiller");
uint256 trancheAmt = 100e18;

// lender creates a request with zero underlying ask (no validation stops this)
vm.startPrank(lender);
tranche.approve(address(escrow), trancheAmt);
escrow.createWriteOffRequest(trancheAmt, 0); // underlyingsRequested = 0 accepted
vm.stopPrank();

// fulfiller atomically takes the tranches for free
vm.prank(fulfiller);
escrow.fullfillWriteOffRequest(lender, trancheAmt, 0);

assertEq(tranche.balanceOf(fulfiller), trancheAmt);   // fulfiller got the tranches
assertEq(underlying.balanceOf(lender), 0);            // lender got nothing
```

Uncertain: whether existing deployment tooling/frontends already prevent zero asks; on-chain, nothing does. Related but weaker analogs exist in `harvest`/`_sellAllRewards` (caller-supplied `_minAmount`/paths with no validation), but the caller there only harms themselves or creates MEV, which falls under excluded classes.
