### Title
Instant-withdraw receipts recorded in a prior epoch are orphaned by default finalization, inflating the recovery price and permanently freezing user funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` keys a user's receipt to `epochNumber` at request time (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`), but `epochNumber` is incremented inside `deposit()` when `stopEpoch` runs. If an instant-withdraw request stays partially unfunded across an epoch boundary (`pendingInstantWithdraws != 0`), a later `finalizeDefaultRecovery` computes the claim basis and prefunded reserve using `instantWithdrawClaimsByEpoch[epochNumber]` of the *new* epoch, which excludes the orphaned receipts. The recovery price is therefore computed over a too-small basis, already-held instant funding is not reserved, and the stale receipts revert on claim — permanently freezing them. This is the exact analog of `split --line-bytes`: a fixed "line buffer" (`instantWithdrawClaimsByEpoch[epochNumber]`) is sized for one epoch's worth of data, while user-controlled request amounts written under an older epoch key overflow the accounting bucket.

### Finding Description
- `requestInstantWithdraw` stores claims under `currentEpoch = epochNumber` read at request time (lines 367–372).
- `epochNumber += 1` occurs in `deposit()` during `stopEpoch` when `isEpochRunning()` is still true (lines 607–610).
- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` only at finalization time (lines 644–649), and `_defaultPrefundedInstantReserve()` uses the same current-epoch key (lines 716–723).
- `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` (line 693), so `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (lines 843–845).
- `claimInstantWithdrawRequest` then burns the *aggregate* `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim` for the full amount (lines 387–392), which reverts when `balance - defaultRecoveryReserve < amount` (lines 897–907).

Concretely: a lender calls `requestWithdraw` while `_isInstantWithdrawEnabled()` and the APR drop exceeds `instantWithdrawAprDelta`, minting an instant receipt in epoch E. At `startEpoch`, `collectInstantWithdrawFunds` only partially collects (`pendingInstantWithdraws` remains > 0). `stopEpoch` bumps `epochNumber` to E+1. If the borrower then defaults and `finalizeDefaultRecovery` runs in E+1, the epoch-E instant claims are invisible to both `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`.

Two broken invariants result:
1. **Loss-distribution / reserve integrity**: `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed without the orphaned instant basis, so defaulted claimants are paid an inflated `defaultRecoveryPrice`, and the already-collected instant funding is not added to `defaultRecoveryReserve`.
2. **One receipt one payout**: `_claimDefaultedInstantWithdrawRequest` reads epoch E+1 entries (zero) and returns without clearing; the subsequent `_transferFundedClaim` must pay the entire aggregate at par. When free balance is insufficient (it is — part of the receipt was never funded), the whole claim reverts, permanently freezing the receipt including its funded portion.

### Impact Explanation
The receipt amount is fully user-controlled (any KYC'd lender with a tranche balance can trigger `requestInstantWithdraw` during a qualifying APR drop). The loss equals the unfunded instant-receipt amount plus the funded portion that becomes unclaimable because the burn-and-transfer is atomic over the aggregate. Other defaulted claimants are simultaneously overpaid through the understated `totalBasis`, so the recovery reserve drains faster than accounted — a direct redistribution of recovery funds plus permanent freezing of unclaimed withdrawal proceeds. This is not a privileged-role attack: the only honest-actor sequencing needed is a partial instant funding at `startEpoch` and a later borrower default, both of which are normal protocol states.

### Likelihood Explanation
Requires (a) an instant-withdraw-enabled deployment, (b) a pending instant queue that survives underfunded across a `stopEpoch` (borrower under-funds or funds late), and (c) default finalization in a later epoch. Each condition is reachable through ordinary protocol flows (`requestWithdraw`, `startEpoch`/`collectInstantWithdrawFunds`, `stopEpoch`, `_handleBorrowerDefault`/`finalizeDefaultRecovery`). The guards do not stop it: `_ensureDefaultRecoveryInitialized` is already set, the request is a legitimate receipt, and the epoch-key mismatch is invisible to every check.

### Recommendation
Key instant-claim accounting to the pending bucket rather than a single epoch: maintain a global `pendingInstantClaims` (or iterate/merge per-user epochs) so `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest` account for all unfunded instant receipts regardless of which epoch they were created in. Alternatively, record `instantWithdrawClaimsByEpoch` under the epoch in which the request will be funded, or roll stale epoch entries forward when `epochNumber` increments while `pendingInstantWithdraws != 0`.

```solidity
// test/foundry/InstantWithdrawDefaultEpochMismatch.t.sol
function testOrphanedInstantReceiptFrozen() external {
    // 1. Enable instant withdraws; deposit AA as lender.
    uint256 amount = 100_000 * ONE_SCALE;
    uint256 minted = idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // 2. Drop unscaledApr so requestWithdraw routes into requestInstantWithdraw.
    //    (lastEpochApr > unscaledApr + instantWithdrawAprDelta)
    vm.prank(manager);
    strategy.setAprsWithBuffer(lowApr, epochDuration, bufferPeriod);

    cdoEpoch.requestWithdraw(0, address(AAtranche)); // -> requestInstantWithdraw in epoch E
    uint256 receipt = strategy.instantWithdrawsRequests(address(this));
    assertGt(receipt, 0);

    // 3. startEpoch: borrower under-funds the instant queue.
    //    deal borrower only partial instant amount; getInstantWithdrawFunds
    //    collects less than pendingInstantWithdraws.
    deal(defaultUnderlying, borrower, partialInstant);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertGt(strategy.pendingInstantWithdraws(), 0); // still unfunded remainder

    // 4. stopEpoch runs -> deposit() bumps epochNumber to E+1.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // or borrower default path leading to epochNumber+1

    // 5. Borrower default finalized in epoch E+1.
    cdoEpoch.finalizeDefault(recovered, recoverySource); // calls strategy.finalizeDefaultRecovery
    // instant claims for this user were recorded under epoch E, but
    // defaultPendingClaimBasis used instantWithdrawClaimsByEpoch[E+1] == 0.

    // 6. User tries to claim the instant receipt -> reverts.
    vm.expectRevert(); // _transferFundedClaim: balance - reserve < amount
    cdoEpoch.claimInstantWithdrawRequest();
    // receipt permanently frozen; other defaulted claimants were overpaid
    // because totalBasis excluded this user's instant claim.
}
```
