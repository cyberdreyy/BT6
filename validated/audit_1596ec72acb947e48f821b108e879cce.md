### Title
Unprivileged ERC4626 vault liquidity drain forces `stopEpoch` to revert indefinitely, freezing all epoch settlements and withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The MongoDB advisory describes a binary that trusts an environment-controlled resource (a shared library resolved from a relative path), letting an unprivileged host actor hijack execution. The credit-vault analog is `ProgrammableBorrower.onStopEpoch`: the epoch state machine delegates its settlement to an external, permissionlessly shared ERC4626 vault. Any unprivileged user of that vault can drain or borrow its liquid assets so that `vault.withdraw` reverts, which makes `onStopEpoch` revert with `StopEpochVaultLiquidityUnavailable` and bubbles up through `IdleCDOEpochVariant.stopEpoch`. Because the revert happens before `_updateAccounting` and before the epoch is marked stopped, every settlement attempt fails while the epoch remains "running", freezing all queued withdraw-request claims and trapping tranche holders' funds until third-party liquidity returns — an environment the attacker controls but the protocol does not.

### Finding Description
`IdleCDOEpochVariant.stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)` and lets hook reverts bubble (`IdleCDOEpochVariant.sol` ~L395-404). Inside `onStopEpoch` (`ProgrammableBorrower.sol` L239-253):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The vault shares may *economically* cover the shortfall (`shortfall <= _currentVaultAssets()`, so the `return true` escape does not fire), yet the underlying ERC4626 vault can have zero withdrawable liquidity because its assets are lent out or withdrawn by other users (e.g., a Morpho-style vault where `totalAssets` counts outstanding loans but `withdraw` is capped by idle liquidity — exactly the case exercised by `setVaultWithdrawLimit` in `test/foundry/ProgrammableBorrowerEpochInvariant.t.sol` L300-304). The `catch` then reverts, the whole `stopEpoch` reverts, `isEpochRunning()` stays true, `epochAccountingActive` stays true, and neither the AA/BB price settlement nor `withdrawsRequestsByEpoch` claims can proceed. The invariant test itself encodes this: on revert it asserts `cdoEpoch.isEpochRunning()` remains true, i.e., the freeze is by design, not a guard that eventually resolves it.

Broken invariant: settlement liveness / one-receipt-one-payout. No skim, flag, or epoch gate bounds how long this lasts; `maxApr` checks, KYC, and `only-CDO` guards are irrelevant. The only unwind paths are privileged (`_emergencyShutdown`) or the attacker voluntarily restoring liquidity.

### Impact Explanation
Any unprivileged actor who can withdraw or borrow from the shared ERC4626 vault (per the threat model, "a user of the programmable borrower's ERC4626 vault" is an allowed attacker) can repeatedly force `stopEpoch` to revert. Consequences:

- All pending withdraw requests (`requestWithdraw` receipts for the epoch) cannot be claimed via `claimWithdrawRequest`, since the epoch never stops and `withdrawsRequestsByEpoch` is never settled — temporary freezing of user funds equal to `_pendingWithdraws`.
- Tranche holders cannot redeem at post-epoch prices; the entire pool NAV (potentially the full `getContractValue()`) is frozen for the duration of the liquidity drought.
- The attacker can time this around epochs where they hold no receipts, purely to grief, or to keep a favorable epoch running (e.g., delay loss realization `stopEpochWithDuration(_lossAmount)` after observing adverse vault PnL cannot be front-run either, though managers are honest).

Cost to the attacker: only the opportunity cost of borrowing/withdrawing vault liquidity, which is fully reversible — they can repay/return liquidity later. Loss to users: time-value of the entire pool plus missed settlement, and indefinite freeze in vaults whose liquidity is structurally thin.

### Likelihood Explanation
- Requirements: `isProgrammableBorrower == true` (an existing deployed mode per `setIsProgrammableBorrower`), an epoch with `_amountRequired > onHand` (typical: funds are parked in the vault by `onStartEpoch`, so `onHand` is usually ~0), and vault idle liquidity < shortfall.
- The vault is external and permissionless; for lending-vault backends (Morpho/Euler-style), utilization near 100% is a routine market condition, not an exotic state — the protocol explicitly anticipates it with `StopEpochVaultLiquidityUnavailable`.
- An attacker can create the condition atomically: borrow/withdraw the vault's idle assets in the same block the manager calls `stopEpoch`, or simply wait for organic high utilization and keep it that way cheaply if borrow rates are low.
- No privileged action is needed and nothing in the code rate-limits retries or provides a fallback withdrawal path; even honest market conditions (not just malice) trigger the freeze.

Severity is capped at temporary freezing (no direct theft), matching Medium.

### Recommendation
- In `onStopEpoch`, treat covered-but-illiquid vault withdrawals as a graceful path instead of reverting: e.g., withdraw what is available (`vault.maxWithdraw(address(this))`), return `true` for the covered portion, and let IdleCDO's `transferFrom` pull whatever is on hand — or return `false` to route through the existing `_handleBorrowerDefault`/loss-adjusted flow rather than an unbounded retry.
- Alternatively, have `stopEpoch` catch `StopEpochVaultLiquidityUnavailable` and settle the epoch partially (realize pending withdraws pro rata against received funds) instead of leaving the epoch in a permanently "running" state.
- Add a permissionless `redeem`-based fallback or a max-liquidity-aware `previewLossAdjustedWithdrawFunds` so settlement degrades rather than halts.

### Proof of Concept
Foundry fork-style test against the existing harness in `test/foundry/ProgrammableBorrowerCreditVault.t.sol` (sketch):

```solidity
function testStopEpochFrozenByVaultLiquidityDrain() external {
    uint256 amount = 10_000 * oneScale;
    idleCDO.depositAA(amount);                       // KYC'd lender
    _startEpochAndCheckPrices(0);                    // funds parked in Morpho vault

    // user requests withdrawal; creates pendingWithdraws > 0
    vm.prank(user);
    cdoEpoch.requestWithdraw(amount / 2, address(aaTranche)); // epoch N request

    // ATTACKER (unprivileged vault user): drain vault idle liquidity
    address attacker = makeAddr("vaultUser");
    deal(USDC, attacker, 1);
    vm.startPrank(attacker);
    morphoVault.withdraw(morphoVault.maxWithdraw(address(morphoVault)) , attacker, attacker); // or borrow max from market
    vm.stopPrank();
    // vault now: shares cover assets economically, but withdraw() reverts on liquidity

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // freeze assertions (mirror invariant test expectations)
    assertTrue(cdoEpoch.isEpochRunning());
    assertTrue(programmableBorrower.epochAccountingActive());
    vm.expectRevert(); // epoch not settled
    cdoEpoch.claimWithdrawRequest(/* receipt */, /* epoch N */);

    // repeat: attacker keeps liquidity drained; every stopEpoch reverts
    vm.warp(block.timestamp + 30 days);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);
}
```

The mock-vault equivalent already exists via `setVaultWithdrawLimit` in `ProgrammableBorrowerEpochInvariant.t.sol` L300-304; capping `withdrawLimit` below the shortfall reproduces the revert deterministically, and the handler at L318-323 confirms the protocol's own expected post-revert state is "epoch keeps running" — i.e., the freeze.
