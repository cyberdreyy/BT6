### Title
Unbounded concurrent WebSocket connections in RPC PubSub service enable memory-exhaustion DoS - (File: `rpc/src/rpc_pubsub_service.rs`)

### Summary
The `rpc_pubsub` service, which handles WebSocket-based subscriptions on the JSON-RPC PubSub port, accepts an unlimited number of concurrent TCP connections and spawns an unbounded number of `tokio::spawn` tasks with no admission control or connection cap, mirroring the "unlimited concurrent requests" DoS class described in the Staking API report.

### Finding Description
The `listen` function's accept loop unconditionally spawns a new async task for every incoming TCP connection with no bound on the total number of concurrent connections: [1](#0-0) 

The only per-connection bookkeeping is a `TokenCounter` used purely for metrics reporting, not for enforcing a limit: [2](#0-1) 

Each spawned task runs `handle_connection`, which performs a WebSocket handshake and allocates buffers/state for the connection's lifetime (subscription tracking, broadcast receiver, framed buffers), meaning memory and file-descriptor cost scale linearly with attacker-controlled connection count. While `PubSubConfig` has a `max_active_subscriptions` cap (`DEFAULT_MAX_ACTIVE_SUBSCRIPTIONS = 1_000_000`) governing subscription state: [3](#0-2) 

this limit governs subscriptions *after* a WebSocket connection is established, not the number of raw TCP connections or handshake attempts the listener will accept. There is no equivalent to Chi's `Throttle` middleware, no `max_connections`, and no backpressure/queueing on the accept loop itself.

By contrast, the separate `banks-server` TCP service explicitly caps concurrency with `.max_channels_per_key(1, ...)` and `.buffer_unordered(10)`: [4](#0-3) 

showing this class of protection is a known/available pattern in the codebase but is absent from `rpc_pubsub_service.rs`'s `listen()`.

### Impact Explanation
An externally reachable RPC node (any validator/RPC operator exposing `--full-rpc-api` with PubSub enabled) can be driven to exhaust memory or file descriptors by an attacker opening a very large number of TCP/WebSocket connections to the pubsub port, each of which is accepted and given its own task/state regardless of system load. On typical OS behavior this can trigger an OOM kill of the validator process, taking down both RPC service and, if co-located, block-production/voting functionality — a denial of service against a publicly-known endpoint, exactly the bug class in the reference report.

### Likelihood Explanation
High for any node/cluster operator running `full_rpc_api` with the PubSub service enabled and reachable from the public internet. No authentication or per-IP/global connection cap exists to block a straightforward "open many sockets" attack; it requires only knowledge of the RPC PubSub host:port, which is typically public for RPC providers.

### Recommendation
Add explicit admission control to the `listen()` accept loop in `rpc/src/rpc_pubsub_service.rs`: enforce a configurable maximum number of concurrent accepted connections (e.g., via a semaphore acquired before spawning `handle_connection` and released on completion), and/or apply per-IP connection limits and accept-rate limiting. This mirrors the `max_channels_per_key`/`buffer_unordered` pattern already used in `banks-server/src/banks_server.rs`. This should be paired with documentation guidance (as Babylon's own conclusion noted) that internet-facing RPC/PubSub deployments should sit behind a reverse proxy/CDN providing connection-level DoS protection.

### Proof of Concept
1. Start a validator/RPC node with `--full-rpc-api` and a `rpc-pubsub` port exposed.
2. From an attacker host, open a very large number (tens of thousands) of raw TCP connections to the pubsub port in a tight loop without completing/closing the WebSocket handshake or sending minimal handshake bytes to keep connections alive.
3. Observe `listen()` accepting every connection and spawning a task per connection with no limit, causing steadily increasing memory/file-descriptor usage on the RPC node until the process is OOM-killed or connection limits are exhausted, denying legitimate RPC/PubSub clients service.
