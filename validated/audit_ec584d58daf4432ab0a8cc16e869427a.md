### Title
`check_parent_tenure_choice` records a reorg permit as a side effect even when the enclosing tenure-change validation ultimately rejects the proposal - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary

### Finding Description
`SortitionData::check_parent_tenure_choice` is a sub-check invoked from within `validate_tenure_change_payload` in both `stacks-signer/src/chainstate/v1.rs` and `stacks-signer/src/chainstate/v2.rs`, itself called from `check_proposal` while evaluating a miner's block proposal. [1](#0-0) [2](#0-1) 

Its docstring makes the side effect explicit: "A permitted reorg is recorded once the whole reorg is permitted: each tenure whose blocks this one is allowed to replace is marked superseded ... Nothing is recorded for a refused reorg." However, that promise only covers a refusal detected *inside `check_parent_tenure_choice` itself*. When the function determines the reorg is legitimate, it eagerly persists the permit via `record_superseded_tenure` → `signer_db.mark_tenure_superseded(...)`, and returns `Ok(true)` **before** validation of the same proposal is complete: [3](#0-2) 

In `validate_tenure_change_payload` (v1), the call order is:
1. parent-tenure-id mismatch check → early `Err(InvalidParentBlock)`
2. `check_tenure_change_confirms_parent` → early `Err(InvalidParentBlock)`
3. `check_parent_tenure_choice` → **writes `mark_tenure_superseded` to signerdb and returns `Ok(true)`**
4. `get_last_signed_block` duplicate-block check → `Err(DuplicateBlockFound)` if the signer already signed a block in the (unrelated) current tenure [4](#0-3) 

Step 4 (and the v2 equivalent, plus the bitvec / tenure-extend / consensus-hash checks that run elsewhere in `check_proposal`) can still reject the overall proposal *after* step 3 has already committed the superseded-tenure record to the database. The v1 `check_proposal` also runs a tenure-extend-cause check and other validations after `validate_tenure_change_payload` returns successfully but the overall proposal may still be rejected downstream (e.g. `check_block_against_signer_db_state` re-validation at validate-ok time, or a later `DuplicateBlockFound`/`InvalidTenureExtend`). [5](#0-4) 

This is structurally the same bug class as the TSPortal advisory: a validation helper performs a database write (a "found or create"-style mutation — here, "found legitimate, so mark superseded") as a side effect of an intermediate check, and that mutation is not contingent on the overall validation actually succeeding.

### Impact Explanation
`mark_tenure_superseded` / `is_tenure_superseded` feed directly into the pre-commit-to-signature path's conflict guard (`reorg_permit_stands`, documented in `docs/signer-flows.md` section 5): a signed block in a tenure marked "superseded" is excluded from blocking a new signature on a competing block in ANY tenure ("our signature must not block a replacement we sanctioned"). If a permit is recorded for a tenure-change proposal that is ultimately rejected for an independent reason (duplicate block already signed in the *current* tenure, unsupported tenure-extend cause, bitvec/consensus-hash mismatch found later in `check_proposal`, etc.), the signer's conflict guard is weakened for a proposal that never validated. A subsequent conflicting/reorging proposal that the signer would otherwise refuse to sign (because it conflicts with an existing fresh signature) can instead be signed, because the stale/invalid permit lets `reorg_permit_stands` return true. This is a Critical-class safety concern: it can lead the signer to place a signature on a competing/reorging block that should have been blocked by the same-height/any-tenure conflict check, undermining the append-only "approved-parent vs canonical" guarantee the reorg-permit mechanism is meant to protect.

### Likelihood Explanation
Reachable by a single miner (the only actor that produces block proposals) with no majority-signer collusion required. The miner needs to submit a tenure-change proposal whose parent-tenure choice legitimately satisfies `check_parent_tenure_choice` (a check based on timing/burn-block data the miner can arrange), while some other independent field of the same proposal (or a later revalidation) causes final rejection. Because `check_parent_tenure_choice` runs early relative to several later-failing checks (`DuplicateBlockFound`, bitvec, unsupported tenure-extend, and any re-validation at `handle_block_validate_ok`/pre-commit time via `check_block_against_signer_db_state`), the ordering makes the side-effect-before-final-outcome window realistically reachable, though it depends on specific field combinations a miner must carefully craft. I was not able to execute the flow end-to-end to fully confirm exploitability of the downstream sign path in this pass; further test-based confirmation (e.g., a `#[cfg(test)]` reproduction feeding a proposal that trips `check_parent_tenure_choice`'s `Ok(true)` branch but later fails a different check) would be needed to convert this into a fully proven exploit chain.

### Recommendation
Defer the call to `record_superseded_tenure` (the DB write) until the *entire* proposal has passed all validation steps in `check_proposal`/`validate_tenure_change_payload`, not just the parent-tenure-choice sub-check. Concretely: have `check_parent_tenure_choice` return the list of tenures that would be superseded (without writing them), and only invoke `signer_db.mark_tenure_superseded` for that list after `validate_tenure_change_payload` and any remaining checks in `check_proposal` return `Ok`. Alternatively, wrap the whole tenure-change validation flow so that permit-recording happens transactionally with the final accept decision.

### Proof of Concept
1. Set up a signer with an existing globally/locally accepted block signed in the current tenure (so the later `get_last_signed_block`/`DuplicateBlockFound` check in `validate_tenure_change_payload` will fail).
2. Craft a tenure-change block proposal whose `parent_tenure_id` differs from `prior_sortition`, but whose reorged tenures satisfy `check_parent_tenure_choice`'s "poorly-timed proposal" leniency (`Duration::from_secs(proposal_to_sortition) < first_proposal_burn_block_timing`), causing it to push tenures onto `superseded_tenures` and return `Ok(true)`, per `stacks-signer/src/chainstate/mod.rs` lines 247–294.
3. Ensure the *same* tenure-change block also confirms a tenure in which the signer already signed a block (`get_last_signed_block(&block.header.consensus_hash)` returns `Some`), so `validate_tenure_change_payload` subsequently returns `Err(RejectReason::DuplicateBlockFound)` per `stacks-signer/src/chainstate/v1.rs` lines 505-518.
4. Observe (via `SignerDb::is_tenure_superseded`) that the earlier tenure was marked superseded in signerdb despite the overall proposal being rejected.
5. Propose a second, competing block conflicting with a block the signer previously signed in the now-"superseded" tenure; the pre-commit/signing conflict guard (`reorg_permit_stands`) will treat the conflict as excluded, potentially allowing the signer to sign it.

*Note: steps 2 and 4 were verified in the code (`check_parent_tenure_choice` and `mark_tenure_superseded`); full end-to-end confirmation of step 5's exploitability against `reorg_permit_stands` was not directly traced/executed in this review and should be validated with a targeted unit/integration test.*

    fn validate_tenure_change_payload(
        &self,
        proposed_by: &ProposedBy,
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            self.config.tenure_last_block_proposal_timeout,
            self.config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // now, we have to check if the parent tenure was a valid choice.
        let is_valid_parent_tenure = proposed_by.state().data.check_parent_tenure_choice(
            signer_db,
            client,
            &self.config.first_proposal_burn_block_timing,
        )?;
        if !is_valid_parent_tenure {
            return Err(RejectReason::ReorgNotAllowed);
        }
        let last_in_current_tenure = signer_db
            .get_last_globally_accepted_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }
