### Title
`deposit()` merges new funds into `account.unstaked`, causing `withdraw()` to re-lock never-staked liquid NEAR behind a stale `unstaked_available_epoch_height` from a prior `unstake()` - (File: staking-pool/src/internal.rs)

### Summary
`inner_unstake` sets `account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK` and adds the unstaked amount to the single `account.unstaked` field. `internal_deposit`, called later (even in a later transaction, not just the same batch), adds the freshly attached deposit into the very same `account.unstaked` field without touching or resetting `unstaked_available_epoch_height`. `internal_withdraw` then gates the entire `account.unstaked` balance behind that one epoch height check, so liquid, never-locked deposited NEAR becomes temporarily frozen for up to `NUM_EPOCHS_TO_UNLOCK` epochs it was never subject to.

### Finding Description
The binding that should hold is: **only NEAR whose lock originated from `unstake()` should be gated by `unstaked_available_epoch_height`; NEAR arriving via `deposit()` should be immediately withdrawable** (`withdrawable_liquid_amount == deposited_amount` regardless of `unstaked_available_epoch_height`). The actual code enforces a coarser binding: **all of `account.unstaked` is gated by the single `unstaked_available_epoch_height <= env::epoch_height()` check**, with no separate accounting for the liquid vs. locked-until-epoch portions.

Code path:
- `inner_unstake` (staking-pool/src/internal.rs:124-181): converts shares to NEAR, does `account.unstaked += receive_amount;` and unconditionally sets `account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;`, then `internal_save_account`.
- `internal_deposit` (staking-pool/src/internal.rs:24-40): reads the account via `internal_get_account`, does `account.unstaked += amount;` (the attached deposit), and saves — it never inspects or resets `unstaked_available_epoch_height`.
- `internal_withdraw` (staking-pool/src/internal.rs:42-68): checks only `account.unstaked >= amount` and `account.unstaked_available_epoch_height <= env::epoch_height()` before allowing withdrawal of `amount` from the merged `account.unstaked` pool.

Exploit flow: an unprivileged delegator calls `unstake(X)` at epoch `T`, setting `unstaked_available_epoch_height = T + NUM_EPOCHS_TO_UNLOCK`. Before that epoch height is reached, the same delegator calls `deposit()` (or `deposit_and_stake` followed by a partial `unstake`/deposit combo) attaching `Y` NEAR. `internal_get_account` in `internal_deposit` reads the account that already carries the future `unstaked_available_epoch_height`, and merges `Y` into `account.unstaked` alongside `X`. A subsequent `withdraw(Y)` call — attempting to pull out only the just-deposited, never-staked liquid portion — fails the `unstaked_available_epoch_height <= env::epoch_height()` assertion, even though `Y` was never staked or subject to any unlock schedule.

No existing guard mitigates this: `assert_owner`, `assert_self()`, `is_promise_success()`, `internal_ping`'s balance assertion, and the U256 rounding pairs are unrelated to this check; the only relevant guard is the epoch-height assert itself, and it is applied indiscriminately to the entire `unstaked` balance rather than to only the portion that originated from `unstake()`.

### Impact Explanation
The delegator's own already-liquid, freshly deposited NEAR becomes frozen inside the staking-pool contract for up to `NUM_EPOCHS_TO_UNLOCK` epochs that it was never supposed to be subject to. The funds are not lost — once the stale `unstaked_available_epoch_height` epoch passes, `withdraw()` succeeds normally — so this is "funds frozen for at least one epoch but recoverable," matching the **High** severity category in the rubric. This is repeatable by any delegator against their own account, on any staking pool instance built from this contract, every time they interleave `unstake()` and `deposit()` calls before the unlock epoch is reached. It does not let anyone extract funds beyond entitlement, attribute rewards incorrectly, or affect other delegators' accounts — the blast radius is confined to the caller's own liquid balance being temporarily inaccessible.

### Likelihood Explanation
No special preconditions beyond normal delegator activity: any account with a nonzero staked balance can call `unstake()` and then `deposit()` before `NUM_EPOCHS_TO_UNLOCK` epochs elapse — a common, easily reachable usage pattern (e.g., a user unstaking part of their stake and then also depositing new NEAR intending to stake it). Attacker cost is just gas and the deposit amount (which they get back after the freeze). This is fully repeatable across every epoch cycle and every staking-pool deployment of this codebase.

### Recommendation
Separate liquid deposited balance from unstaking-locked balance in the account structure (e.g., track `unstaked` amounts per unlock-epoch bucket, or add a distinct `available_for_withdraw` liquid balance that is not touched by the unstake epoch gate), and have `internal_withdraw` allow immediate withdrawal of the liquid portion while still gating only the portion whose lock has not yet expired. At minimum, `internal_deposit` should not merge new deposits into `account.unstaked` if `unstaked_available_epoch_height > env::epoch_height()`; instead it should track them separately until the existing lock clears.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }

    pub(crate) fn internal_get_account(&self, account_id: &AccountId) -> Account {
        self.accounts.get(account_id).unwrap_or_default()
    }

    /// Inner method to save the given account for a given account ID.
    /// If the account balances are 0, the account is deleted instead to release storage.
    pub(crate) fn internal_save_account(&mut self, account_id: &AccountId, account: &Account) {
        if account.unstaked > 0 || account.stake_shares > 0 {
            self.accounts.insert(account_id, &account);
        } else {
            self.accounts.remove(account_id);
        }
    }
