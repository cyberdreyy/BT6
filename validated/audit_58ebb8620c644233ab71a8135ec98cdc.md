### Title
Node coordinator never marks off a stale rejection once a signer flips to acceptance, allowing a signable block to be spuriously killed as globally rejected - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
This is a direct analog of the "bad debt not marked off" class of bug: a quantity that must be corrected the moment the underlying fact changes (bad debt / a retracted vote) is instead left stale forever, and downstream logic (redemption ordering / block-kill decision) keeps using the inflated, no-longer-true total. In the lending report, `totalAssets.amount` is never decremented for bad debt, so early redeemers get paid based on a false balance while late redeemers absorb the loss. Here, `BlockStatus.total_weight_rejected`, accumulated in `StackerDBListener::handle_signer_messages` (`stackerdb_listener.rs`), is only ever incremented and is never decremented when the same signer later reconsiders and sends an `Accepted` response for the same block.

### Finding Description
The miner-side coordinator tracks two independent running totals per proposed block in `BlockStatus`: [1](#0-0) 

On a `BlockResponse::Rejected` from a signer, the coordinator adds that signer's weight to `total_weight_rejected`, gated only by `block.responded_signers.insert(slot_id)` (first-response-wins bookkeeping, not a correction mechanism): [2](#0-1) 

On a subsequent `BlockResponse::Accepted` from that *same* signer for the *same* block (e.g. because the signer re-evaluated the proposal — the signer's own local state machine explicitly supports "LocallyRejected → LocallyAccepted: re-evaluated" and even clears the signer-local DB record of the rejection, per `stacks-signer/src/signerdb.rs`'s `reject_then_accept` test and the CHANGELOG entry "Do not count both a block acceptance and a block rejection for the same signer/block"), the coordinator only checks `gathered_signatures.contains_key(&slot_id)` — not `responded_signers` and not whether this signer previously contributed to `total_weight_rejected` — before adding the weight to `total_weight_approved`: [3](#0-2) 

Nowhere in this branch (or anywhere else in the file) is `total_weight_rejected` decremented for that signer's slot. The signer-local DB (`signerdb.rs`) correctly "marks off" the stale rejection when a later signature arrives, but the miner-side `BlockStatus` aggregate — the value actually used to decide whether a block is dead — never receives that correction. This is exactly the bad-debt pattern: the local/individual ledger is fixed, but the aggregate/global ledger that decisions are made from is not.

The aggregate is then used to make a terminal, safety/liveness-relevant decision in `SignerCoordinator`: [4](#0-3) 
and the reject-branch is evaluated ahead of the accept-branch (rejected check first, approved check second) in the same loop, so a stale/double-counted rejection weight can trip the `SignersRejected` branch even when the true, current signer-set opinion (after retractions) would clear the ≥70% approval threshold.

### Impact Explanation
This breaks the "aggregated-weight vs. verified/actual votes" equality that the >30%-rejection / ≥70%-approval thresholds are supposed to enforce. A signer who initially rejects a block for a transient reason (chain reorg, timing, stale proposal, sortition-view mismatch — several of which are explicitly documented as reconsiderable in `should_reevaluate_reject_reason`) and later legitimately signs it still has their earlier "no" permanently counted toward `total_weight_rejected`. If enough such retractions occur, `total_weight_rejected` can cross `total_weight - weight_threshold` purely from stale weight, causing the miner to declare the block `SignersRejected` and abandon it — even though the live signer set would have supplied enough valid signatures to reach consensus. This is a liveness wedge on block production (the miner incorrectly kills a signable block and must re-mine/exclude transactions), matching the "High — a signer wedged... acting on a stale... threshold" impact class.

### Likelihood Explanation
This requires no majority collusion and no key compromise — it is triggered purely by ordinary, permitted signer behavior: a `Rejected` response followed later by a legitimate `Accepted` response for the same block from the same signer, which the codebase's own tests (`signers_do_not_reconsider_globally_accepted_and_responded_blocks`, `locally_rejected_blocks_overriden_by_global_acceptance`, `reject_then_accept`) show is an expected, normal occurrence (reconsideration after stale proposals, timing races, or reorg resolution). A single gossip-timing race or a handful of signers reconsidering is sufficient to poison the aggregate; no privileged access is needed.

### Recommendation
When processing a `BlockResponse::Accepted` for a slot that is already present in `responded_signers` (i.e., previously rejected), subtract that signer's weight from `total_weight_rejected` (and remove any per-txid `failed_txids` weight attributed to that signer) before adding it to `total_weight_approved`, mirroring the correction that `signerdb.rs` already performs for the signer-local record. Symmetrically, guard the `Rejected` branch so a signer's earlier acceptance weight is retracted if they now reject (or make the transition irreversible once one type of terminal vote is recorded, consistent with the "approvals are sticky" invariant documented in `proposal_replication_void.rs`).

### Proof of Concept
1. Start a signer set where `weight_threshold` requires ≥70% of `total_weight`, and identify a signer S whose weight, combined with existing genuine rejections, is enough to push `total_weight_rejected` over `total_weight - weight_threshold` (the blocking-minority threshold).
2. Propose block B. Signer S is briefly forced to reject B (e.g., via a transient `SortitionViewMismatch`/stale-proposal condition), triggering `SignerMessageV0::BlockResponse(BlockResponse::Rejected(..))`; the coordinator adds S's weight to `block.total_weight_rejected` (`stackerdb_listener.rs:515-519`).
3. The transient condition clears; S re-evaluates B (as `should_reevaluate_block`/`should_reevaluate_reject_reason` in `signer.rs` permit) and sends `BlockResponse::Accepted`. The coordinator adds S's weight to `total_weight_approved` (`stackerdb_listener.rs:443-446`) but never subtracts it from `total_weight_rejected`.
4. Have enough other signers behave the same way (reject-then-accept) so that the sum of stale rejection weights alone exceeds `total_weight - weight_threshold`, while the live/final tally of accepted signers is actually ≥ `weight_threshold`.
5. Observe `SignerCoordinator::` wait loop (`signer_coordinator.rs:509-540`) hit the `total_weight_rejected.saturating_add(weight_threshold) > total_weight` branch and return `NakamotoNodeError::SignersRejected`, discarding a block that the current, corrected signer opinions would have approved — confirming the stale-rejection-weight liveness wedge.
