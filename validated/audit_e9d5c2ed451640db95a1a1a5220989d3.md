### Title
`GET /v2/external_initiators` Index route lacks role check, leaking `AccessKey`/`OutgoingToken` to any authenticated (View-role) user - ([File: core/web/router.go])

### Summary
The `authv2` group requires only `Authenticate` (session or API token, no minimum role) as its base middleware. `Index` is wired with `paginatedRequest(eia.Index)` alone, with no `RequiresEditRole`/`RequiresAdminRole` wrapper, unlike `Create`/`Destroy` which use `auth.RequiresEditRole`. This means any authenticated user, including one with the lowest "view" role, can call `GET /v2/external_initiators` and receive `AccessKey` and `OutgoingToken` for every registered external initiator.

### Finding Description
The `authv2` group is created with just `auth.Authenticate(...)` (token or session), imposing no minimum role: [2](#0-1) . Within that group, `Create` and `Destroy` are explicitly gated with `auth.RequiresEditRole`, but `Index` is not: [1](#0-0) .

`ExternalInitiatorsController.Index` fetches all external initiators from the ORM and serializes them with `presenters.NewExternalInitiatorResource`, which includes the initiator's `AccessKey` and `OutgoingToken` fields in the JSON response: [3](#0-2) [4](#0-3) . There is no redaction of these credential-like fields in the presenter, unlike `ExternalInitiatorAuthentication` which is only returned once on `Create`. `AccessKey` is the incoming HMAC key identifier used by the EI to authenticate to the node (paired with a secret not present here, but still a sensitive identifier), and `OutgoingToken` is the token the node uses to call back into the EI service — both are credential material that should be admin/edit-role gated, matching the intent already applied to `Create`/`Destroy`.

Any principal that can obtain a valid session cookie or API token (including a low-privileged "view" role user) can call `Index` and enumerate `AccessKey`/`OutgoingToken` for every configured external initiator, none of which they are supposed to access if they only hold view-level privileges intended for read-only operational visibility, not credential material.

### Impact Explanation
This is a role/authorization bypass leading to disclosure of external-initiator credentials (`AccessKey`, `OutgoingToken`) to any authenticated user regardless of role, rather than being restricted to edit/admin roles as `Create`/`Destroy` are. An attacker with only view-role credentials (e.g., a compromised low-privilege API token) could harvest these tokens to impersonate the external initiator's outgoing calls or replay/query its incoming access identifiers, expanding their foothold beyond their granted role. This matches a role-based authorization bypass / sensitive-credential-disclosure impact class.

### Likelihood Explanation
Precondition is minimal: any valid authenticated session or API token, without any specific "edit" or "admin" role, is sufficient — this is directly reachable and inconsistent with the sibling `Create`/`Destroy` routes' explicit `RequiresEditRole` gating in the same file, strongly suggesting an authorization omission rather than an intentional design. The exploit is a single unauthenticated-role GET request and is fully repeatable.

### Recommendation
Wrap the `Index` route with the same role check used by `Create`/`Destroy` (e.g., `auth.RequiresEditRole(paginatedRequest(eia.Index))` or `RequiresAdminRole`), or alternatively strip `AccessKey`/`OutgoingToken` from `ExternalInitiatorResource` used by `Index` so that only names/URLs/timestamps are exposed to lower-privileged roles, keeping secret fields exclusive to the one-time `Create` response.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/external_initiators_controller_test.go`):
1. Create an app/test client, register two external initiators via `Create` (admin/edit role), capturing their `AccessKey`/`OutgoingToken` from the ORM.
2. Create a session/API token with the lowest role (`user_role.View` or equivalent) and no edit/admin scope.
3. Call `GET /v2/external_initiators` authenticated as the view-role user.
4. Assert: request currently returns `200 OK` (expected: should be `401`/`403` unless role is edit/admin).
5. Parse the JSON:API response body and assert that `data[].attributes.accessKey` and `data[].attributes.outgoingToken` are present and match the values captured in step 1, demonstrating credential leakage.
6. After applying the fix (adding `auth.RequiresEditRole`/`RequiresAdminRole` or presenter redaction), re-run and assert `403` for the view-role caller, and/or absence of `accessKey`/`outgoingToken` fields for any role below edit.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
