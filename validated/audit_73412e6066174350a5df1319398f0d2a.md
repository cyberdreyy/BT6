### Title
APR0 withdraw receipts escape `stopEpochWithDuration` loss haircut and claim at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`collectWithdrawFunds` haircuts the aggregate `pendingWithdraws` bucket (which includes APR0 principal) by storing `lossRecoveryPriceByEpoch[epochNumber]`, but the loss-adjusted claim path can only recover a receipt through `withdrawsRequestsByEpoch` or an *open* `apr0Users` entry. APR0 requests never populate `withdrawsRequestsByEpoch`, and `_settleApr0` zeroes `principal` before the claim, so the per-epoch lookup "misses" (the analog of `find_cc()` returning NULL) and the APR0 user falls through to `_claimFundedWithdrawRequest`, which pays 100% at par from the already-haircutted funded pool.

### Finding Description
- `requestWithdraw` routes `unscaledApr == 0` requests into `_requestWithdrawApr0`, which only fills `apr0Users[_user]` and `apr0TotalPrincipal`; `withdrawsRequestsByEpoch[_user][epoch]` is left empty even though `pendingWithdraws += _amount` was already applied for both branches. [1](#0-0) 
- On a lossy `stopEpochWithDuration`, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` using a `pendingBasis` that still contains APR0 principal, then zeroes `pendingWithdraws`. [2](#0-1) 
- In `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` looks up the claim under `lastWithdrawRequest[_user]`, but `_withdrawClaimAmountsForEpoch` returns a nonzero APR0 basis only when `apr0Users[_user].principal != 0 && principalEpoch == _claimEpoch`. `_claimFundedWithdrawRequest` calls `_settleApr0(_user)` first — after the wait epoch `_settleApr0` moves `principal` to `settledPrincipal` and zeroes it — so by the time the loss lookup runs, the APR0 receipt is invisible and `claimBasis == 0`. [3](#0-2) [4](#0-3) [5](#0-4) 
- The funded claim then pays `settledPrincipal + settledInterest` (plus `principal` if still open) at par via `_transferFundedClaim`, burning the full receipt while normal requesters of the same epoch only receive `claimBasis * lossRecoveryPrice / 1e18`. [6](#0-5) 

### Impact Explanation
In an APR0 (`unscaledApr == 0`) epoch where `stopEpochWithDuration` realizes a loss, every APR0 withdrawer redeems `principal * (1 - lossRecoveryPrice)` more than their fair share, paid out of the underlyings funded for all pending receipts. The excess is stolen from the remaining claimants: once the strategy's balance is drained, later claimants revert in `_transferFundedClaim`/`safeTransfer`, so the last normal/APR0 claimant's payout is permanently frozen. Loss equals the sum of escaped haircuts on APR0 principal, bounded only by `apr0TotalPrincipal` share of `pendingWithdraws`.

### Likelihood Explanation
Requires a vault configured in APR0 mode and a `stopEpochWithDuration` loss in an epoch with pending APR0 requests — both are first-class supported modes (APR0 flow and loss-adjusted funding are explicitly implemented), and any lender can hold an APR0 receipt. The attacker is an ordinary unprivileged requester; no privileged cooperation is needed.

### Recommendation
Apply the epoch haircut to APR0 receipts as well: record APR0 request basis per epoch (or keep `principal`/`principalEpoch` keyed until claim), let `_withdrawClaimAmountsForEpoch` match settled APR0 principal to its request epoch, and route APR0 loss-epoch claims through `_claimLossAdjustedWithdrawRequest` so `settledPrincipal`/`principal` is paid at `lossRecoveryPrice`, not at par.

### Proof of Concept
```solidity
// test/foundry/PoC.t.sol — fork test sketch
// Setup: APR0 vault (unscaledApr == 0), epoch running.
// 1. Alice (normal) and Bob each requestWithdraw(1000e6) in epoch N.
//    pendingWithdraws == 2000e6; Bob's principal went to apr0Users, Alice's to withdrawsRequestsByEpoch[N].
// 2. Borrower repays only 1500e6 at stopEpochWithDuration(0, interest, duration, loss=500e6).
//    collectWithdrawFunds(1500e6) -> lossRecoveryPriceByEpoch[N] = 0.75e18, pendingWithdraws = 0.
// 3. After epochNumber bumps, Bob calls claimWithdrawRequest:
//    _settleApr0 moves Bob.principal -> settledPrincipal (principal = 0).
//    _claimLossAdjustedWithdrawRequest: withdrawsRequestsByEpoch[Bob][N] == 0 &&
//    apr0Users[Bob].principal == 0 -> claimBasis == 0 (lookup "NULL").
//    _claimFundedWithdrawRequest pays Bob 1000e6 at par.
// 4. Alice claims: only ~500e6 left but she is owed 750e6 -> revert / frozen.
assertEq(strategy.balanceOf(payout), 1500e6); // funded pool
// bob received 1000e6 instead of 750e6; alice's 750e6 is unpayable.
```

```text
  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
