### Title
Unprivileged instant-withdraw request front-runs borrower funding and forces a spurious pool default - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In non-programmable (fixed-APR) credit vaults, users can open instant-withdraw requests while an epoch is running. The manager later calls `getInstantWithdrawFunds()` to pull the *current* aggregate `pendingInstantWithdraws` from the borrower in a single `transferFrom`. Because the pulled amount is read fresh at execution time and the whole pull is wrapped in `try/catch`, an attacker can front-run the funding transaction with a dust instant-withdraw request, making the borrower pull exceed the repaid/approved amount. The revert is caught and routed into `_handleBorrowerDefault`, permanently flagging the pool as defaulted even though the borrower fully repaid.

### Finding Description
`getInstantWithdrawFunds` computes the liability inside the transaction:

- `IdleCDOEpochVariant.sol:564` reads `uint256 _instantWithdraws = _pendingInstant()` (the strategy's live `pendingInstantWithdraws`), then `try this.getFundsFromBorrower(_instantWithdraws)` performs `transferFrom(_borrower(), address(this), _amount)` at `IdleCDOEpochVariant.sol:550-553`.
- Any failure of that pull is caught and funneled to `_handleBorrowerDefault(_instantWithdraws)` at `IdleCDOEpochVariant.sol:571-573`, which sets `defaulted = true`, pauses the contract, stops the epoch, and disables `allowAAWithdrawRequest`/`allowBBWithdrawRequest` (`IdleCDOEpochVariant.sol:577-599`).

Meanwhile `requestInstantWithdraw` in `IdleCreditVault` (called via the CDO's instant-request path while the epoch is running, before `instantWithdrawDeadline` funding) burns the user's receipt tokens and increments `pendingInstantWithdraws` / `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` (`IdleCreditVault.sol:356-360` and following). There is no check that the request does not exceed the liquidity the borrower has already returned for the current instant queue — analogous to JOJO's `deposit` missing the `_isAccountSafe` check that `withdraw` has.

Attack sequence:

1. Epoch is running; `instantWithdrawDeadline` has passed. Borrower (honest) has returned/approved exactly the funds needed for the current instant queue `P`.
2. Attacker (any tranche holder) front-runs the manager's `getInstantWithdrawFunds()` with `requestInstantWithdraw(1 wei)` — or a minimal tranche amount — so `pendingInstantWithdraws` becomes `P + ε`.
3. `getFundsFromBorrower(P + ε)` reverts on insufficient borrower balance/allowance.
4. The `catch` arm invokes `_handleBorrowerDefault`, setting `defaulted = true`, pausing deposits/requests, and freezing the epoch.

The pool is now hard-defaulted despite a solvent, honest borrower: `startEpoch` reverts on `defaulted` (`IdleCDOEpochVariant.sol:239`), `unpause`/`restoreOperations` revert, and all pending/active claims can only be resolved through `finalizeDefault`, which applies a single aggregate recovery multiplier (`IdleCreditVault.sol:661-710`), waives all accrued fees (`fee`, `managementFee`, `unclaimedFees` zeroed at `IdleCDOEpochVariant.sol:202-204`), and forces every LP and pending redeemer through the haircut claim path.

### Impact Explanation
A 1-wei request converts a fully-funded epoch into a borrower default. Consequences: (a) all LP funds are frozen until owner/manager execute `finalizeDefault` with real recovery capital; (b) fees legitimately accrued (`unclaimedFees`, `pendingWithdrawFees`) are permanently waived; (c) pending receipts and active NAV are forced through the loss-recovery multiplier machinery even at 100% recovery, and if no recovery is sourced the pool can be finalized at price zero, socializing a phantom loss onto all LPs. This is a permanent freezing / insolvency-impact path triggered entirely by an unprivileged user, matching the report's "attacker adds an entry that makes the debt-removal transaction revert" bug class.

### Likelihood Explanation
Only requires: a fixed-APR credit vault with instant withdrawals enabled and at least one pending instant request (or the borrower having topped up exact liquidity), and the attacker holding any tranche balance (KYC-passing lender or even a minimal holder). The grief costs dust. It must be timed against the manager's `getInstantWithdrawFunds` call, but instant funding is a routine every-epoch operation, giving repeated windows each epoch.

### Recommendation
Do not let the instant-funding amount float at execution time, and do not treat a funding-shortfall revert in `getInstantWithdrawFunds` as borrower default attributable to liabilities created after the deadline. Concretely:
- Snapshot the instant queue at `instantWithdrawDeadline` (e.g., `instantWithdrawClaimsByEpoch[epochNumber]` frozen at deadline) and pull exactly that amount; route post-deadline requests to the next epoch, or
- Revert (without defaulting) when `pendingInstantWithdraws` differs from the amount being funded, letting the manager retry after accounting for new requests, and/or
- Only enter `_handleBorrowerDefault` if the borrower failed to cover the snapshotted liability, not a newly inflated one.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (fixed-APR IdleCreditVault, instant withdraws enabled)
// Pre: epoch running, user A has an instant request of amount P,
//      borrower has approved/returned exactly P.
vm.warp(cdoEpoch.instantWithdrawDeadline() + 1);

// Attacker front-runs manager's getInstantWithdrawFunds with a dust request
vm.startPrank(attacker); // attacker holds >= 1 wei of AA tranche (KYC'd lender)
trancheAA.approve(address(cdoEpoch), type(uint256).max);
cdoEpoch.requestInstantWithdraw(1, address(AAtranche)); // pendingInstantWithdraws = P + 1
vm.stopPrank();

// Manager's routine funding tx pulls _pendingInstant() = P + 1 -> transferFrom fails -> catch -> default
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();

assertTrue(cdoEpoch.defaulted());              // spurious default
assertFalse(cdoEpoch.allowAAWithdrawRequest());
assertTrue(cdoEpoch.paused());
vm.expectRevert();                             // pool cannot restart
vm.prank(manager);
cdoEpoch.startEpoch();
```

Note: I verified the pull-then-default flow in `getInstantWithdrawFunds`/`_handleBorrowerDefault` and the unguarded increment of `pendingInstantWithdraws` in `requestInstantWithdraw`; the exact CDO-side gating of the instant-request entrypoint was not fully re-read line-by-line, but the feature is documented as a user-facing mid-epoch request path (manager fulfills after `instantWithdrawDeadline`), which is the surface this attack needs.
