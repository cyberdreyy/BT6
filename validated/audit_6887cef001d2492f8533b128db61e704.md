### Title
Single uncooperative shareholder can permanently block payout distribution to all other shareholders - ([File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
`vesting::distribute()` iterates over every shareholder in a vesting pool and pays them out with `aptos_account::deposit_coins` inside one atomic transaction. `deposit_coins` aborts if the recipient's `CoinStore` is not yet registered and the recipient has opted out of "direct coin transfers" (`EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`), or if the recipient's `CoinStore` is frozen. Because Move transactions are all-or-nothing, one unregistered/opted-out shareholder causes the whole `distribute()` call to abort every time it is invoked, permanently blocking payout to all of the other (innocent) shareholders in the same vesting pool. This is the on-chain analog of the reported `transfer()`-based push-payment DoS: a single recipient can indefinitely grief every other claimant sharing the same distribution loop.

### Finding Description
`vesting::distribute()` withdraws all currently unlocked stake and then loops through every shareholder of the pool, calling `aptos_account::deposit_coins(recipient_address, share_of_coins)` for each one: [1](#0-0) 

`aptos_account::deposit_coins` will register a `CoinStore` and create the account if needed, but for an *existing* account that has not registered `AptosCoin`, it requires `can_receive_direct_coin_transfers(to)` to be true, otherwise it aborts: [2](#0-1) 

This "opt out of arbitrary/unregistered coin transfers" and CoinStore-frozen abort behavior is formally documented in the module's spec (requirement #3, #6, and the `frozen` abort condition): [3](#0-2) 

A shareholder (or, since `set_beneficiary` is admin-controlled but a shareholder's own account is always a valid deposit target if no beneficiary is set) is fully unprivileged with respect to their own account and can, by simply never registering a `CoinStore<AptosCoin>` and calling the self-service opt-out (`set_allow_direct_coin_transfers(false)`), make any deposit to their own address abort forever. Since `distribute()` has no per-recipient error handling or skip-on-failure logic — it processes `grant_pool.shareholders()` in a single loop inside one atomic entry function — a single such account among up to `MAXIMUM_SHAREHOLDERS` (30) shareholders in the pool will cause `distribute()`, and therefore `terminate_vesting_contract()` and `admin_withdraw()` (both of which call `distribute()` internally), to abort on every call. [4](#0-3) [5](#0-4) 

The exact same accounting pattern exists in `staking_contract::distribute_internal`, which loops over `distribution_pool.shareholders()` (staker, prior operators with unpaid commission, and the current operator's beneficiary) and calls `aptos_account::deposit_coins` for each recipient without any per-recipient fallback: [6](#0-5) 

### Impact Explanation
Once withdrawable stake/rewards are unlocked and staged for `distribute()`, they cannot be redirected to a different address — the payout targets are fixed (`get_beneficiary`/shareholder address). If any single shareholder is unregistered and has opted out of direct transfers (or their `CoinStore` becomes frozen), `distribute()` reverts unconditionally and permanently, since the underlying stake pool state (already unlocked/inactive) doesn't change between retries. This traps the vested/reward stake of every *other* shareholder in the pool — funds that should be withdrawable become permanently non-recoverable through the normal `distribute`/`distribute_many`/`terminate_vesting_contract`/`admin_withdraw` paths, matching the "permanent lock or non-recoverable loss of claim rights in vesting flows" impact class.

### Likelihood Explanation
The precondition (an account that exists but is not registered for `AptosCoin` and has explicitly opted out of unregistered/direct transfers) is entirely self-inflicted and requires no privileged role — any of up to 30 shareholders in a vesting pool, or any staker/operator/beneficiary in a `staking_contract` distribution, can trigger it against themselves at any time. Because pool membership (shareholders) is fixed at pool creation by the admin, a shareholder wanting to grief the rest of the pool (e.g., to extort the admin, or out of malice/dispute) only needs to configure their own account this way once. However, the impact is confined to a specific pool the griefer must already be a member of, and cannot redirect or steal other shareholders' funds, only strand them — so I rate confidence in exploitability as reasonably high but the "attacker" gains no direct financial benefit beyond denial-of-service on their co-shareholders.

### Recommendation
In both `vesting::distribute()` and `staking_contract::distribute_internal`, avoid aborting the entire batch payout on a single recipient's transfer failure. Wrap each `aptos_account::deposit_coins` call so a failure for one recipient does not prevent payment to the rest (e.g., use a fallback/pull-based claim mechanism per recipient, or catch failures and re-queue that shareholder's share instead of reverting the whole transaction). This mirrors the recommended fix for the reported `transfer()`/`.call()` issue: isolate per-recipient failures so no single account can block payouts to everyone else in the batch.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `[S1, S2]` via `vesting::create_vesting_contract`, where `S2`'s account exists but has never called `coin::register<AptosCoin>` (e.g., account created via a raw `account::create_account_for_test`/multisig flow rather than `aptos_account::create_account`).
2. `S2` calls `aptos_account::set_allow_direct_coin_transfers(false)` (self-service, unprivileged) to opt out of unregistered/direct coin transfers to their address.
3. Vesting proceeds normally; `vest()`/`unlock_rewards()` unlock stake for both `S1` and `S2`, and stake lockup expires.
4. Anyone calls `vesting::distribute(contract_address)` — see loop at [1](#0-0) 
   — when the loop reaches `S2`, `aptos_account::deposit_coins` hits the `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` abort path, reverting the entire transaction.
5. `S1`'s already-vested/unlocked stake, together with `S2`'s, remains locked in the vesting contract's resource account indefinitely: every subsequent call to `distribute`, `distribute_many`, `terminate_vesting_contract`, or `admin_withdraw` for this pool aborts the same way, since `S2`'s configuration does not change between calls.

Note: I could not fully inspect the body of `set_allow_direct_coin_transfers`/`can_receive_direct_coin_transfers` in this pass due to index/tool limitations on that specific file range; their abort semantics are corroborated by the formally-verified spec module (`aptos_account.spec.move`, requirements #3 and #6) rather than direct inspection of the Move source body. A Devin session with full repository access would be needed to confirm the exact implementation details of that opt-out function.

    public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
        distribute(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);
        assert!(pending_active_stake == 0, error::invalid_state(EPENDING_STAKE_FOUND));

        // Unlock all remaining active stake.
        vesting_contract.state = VESTING_POOL_TERMINATED;
        vesting_contract.remaining_grant = 0;
        unlock_stake(vesting_contract, active_stake);

        emit(
            Terminate {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
            },
        );
    }
