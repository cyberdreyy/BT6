## Finding

### Title
Fee/insurance transfers with amounts rounded down to zero can revert via Token-2022 Transfer Hook, freezing permissionless fee collection and third-party liquidation - (File: `programs/marginfi/src/instructions/marginfi_account/liquidate.rs`, `programs/marginfi/src/instructions/marginfi_group/collect_bank_fees.rs`)

### Summary
Marginfi allows banks to be created on Token-2022 mints that carry an active `TransferHook` extension — this is explicitly exercised and passed as a valid configuration for the standard liquidation flow in the test suite (`marginfi_account_liquidation_success_with_extension` with `SupportedExtension::TransferHook`), unlike the emissions-deposit path which explicitly rejects hooked mints via `has_transfer_hook` checks in `lending_pool_emissions_deposit` [1](#0-0) . Any Token-2022 transfer that goes through `withdraw_spl_transfer` invokes `spl_token_2022::onchain::invoke_transfer_checked`, which performs a CPI into the mint's registered transfer-hook program for every transfer, including zero-amount transfers [2](#0-1) .

Several fee/insurance computations in the protocol truncate an `I80F48` fixed-point value to an integer `u64` before performing this transfer, and none of them guard against the truncated amount being zero before invoking the transfer.

### Finding Description
In `lending_account_liquidate`, the insurance-fund fee is computed as the difference between the amount paid by the liquidator and the amount received by the liquidatee, then truncated to `u64` and unconditionally transferred to the insurance vault: [3](#0-2) [4](#0-3) 

For small liquidation amounts (e.g. tiny debt positions, dust-sized liquidations, or low-decimal/low-value liability tokens), `insurance_fund_fee` can be `< 1` in native units, so `insurance_fee_to_transfer` truncates to `0`. The code calls `liab_bank.withdraw_spl_transfer(insurance_fee_to_transfer, ...)` regardless, which — for a Token-2022 mint with an active transfer hook — triggers a CPI into the hook program with `amount = 0`.

The same pattern exists in the permissionless `lending_pool_collect_bank_fees` instruction, where `insurance_fee_transfer_amount`, `group_fee_transfer_amount`, and `program_fee_transfer_amount` are each computed via `min(outstanding, available_liquidity).int()` (floor) and unconditionally passed to `bank.withdraw_spl_transfer(...)`, with no zero-amount guard: [5](#0-4) [6](#0-5) 

If the transfer-hook program associated with the bank's mint contains logic that rejects zero-value transfers (a legitimate design choice a hook author might make, directly analogous to the ERC-20 "revert on zero transfer" behavior described in the source report), then:
- Any liquidation of an account holding that bank's liability that rounds the insurance fee to zero will revert, and
- Any permissionless fee-collection call that rounds any of the three fee buckets to zero will revert.

Both instructions are otherwise unprivileged/permissionless — `lending_account_liquidate` is callable by any third-party liquidator, and `lending_pool_collect_bank_fees` is explicitly documented and designed to be callable by anyone [7](#0-6) .

### Impact Explanation
A reverting zero-amount transfer inside `lending_account_liquidate` means an unhealthy account cannot be liquidated at all as long as the computed insurance fee for that liquidation attempt truncates to zero — this is a durable, protocol-level denial-of-service on the risk-mitigation mechanism (liquidation) for banks backed by such Token-2022 mints, directly threatening solvency since bad debt cannot be cleared. Similarly, blocking `lending_pool_collect_bank_fees` freezes fee/insurance accrual from flowing out of the liquidity vault into the fee/insurance vaults, which can also block subsequent `lending_pool_withdraw_fees`/`lending_pool_withdraw_insurance` flows that depend on this step having run.

### Likelihood Explanation
Likelihood depends on a bank being created for a Token-2022 mint with an active transfer hook that specifically rejects zero-amount transfers — the protocol does not prohibit such mints for standard bank instructions (only for emissions deposits), and the test suite confirms hooked mints are accepted for the deposit/borrow/liquidate flow. Given marginfi's stated support for Token-2022 extensions and permissionless integration of external mints, this is a realistic configuration, though it requires a specific class of hook implementation to trigger.

### Recommendation
Before invoking `withdraw_spl_transfer` (or any SPL transfer) with a fee/insurance amount derived from rounding/truncation, skip the transfer entirely when the amount is zero, mirroring the pattern already used elsewhere in the codebase (e.g., `lending_pool_emissions_deposit` returns early when `amount == 0`, and `super_admin_withdraw` also short-circuits on `amount == 0`). Specifically:
- In `liquidate.rs`, guard the insurance-fund transfer with `if insurance_fee_to_transfer > 0 { ... }`.
- In `collect_bank_fees.rs`, guard each of the three `withdraw_spl_transfer` calls with a zero-amount check.

### Proof of Concept
1. Create a bank whose mint is Token-2022 with an active `TransferHook` extension, where the hook program enforces `require(amount != 0)` (a valid, spec-compliant hook implementation).
2. Have a borrower open a very small liability position in that bank (or engineer a liquidation where `q_a * p_a * f_i` truncates to `< 1` native unit).
3. Have a liquidator call `lending_account_liquidate` targeting this unhealthy position.
4. `insurance_fund_fee.checked_to_num::<u64>()` truncates to `0`; `liab_bank.withdraw_spl_transfer(0, ...)` invokes the transfer hook via CPI with `amount = 0`, which the hook rejects, reverting the entire liquidation transaction — the account remains unliquidated.
5. Analogously, call `lending_pool_collect_bank_fees` on a bank where `collected_insurance_fees_outstanding` (or group/program fees) is nonzero but below `1` native unit; the truncated `0` transfer to the corresponding vault reverts under the same hook logic.
