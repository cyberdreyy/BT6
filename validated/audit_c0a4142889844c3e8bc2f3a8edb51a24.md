### Title
Donation to pool account counted as staking reward via `internal_ping` - ([File: staking-pool/src/internal.rs])

### Summary
`internal_ping` computes `total_reward` as `total_balance - self.last_total_balance`, where `total_balance` is derived from `env::account_locked_balance() + env::account_balance()`. Any NEAR sent directly to the pool account via a bare transfer increases `env::account_balance()` with no corresponding accounting entry, so the first `ping` (or `deposit`/`stake`/`unstake`/`withdraw`, all of which call `internal_ping` first) in a new epoch will misattribute the donated amount as a staking reward, splitting it between the owner fee and existing stakers' share price.

### Finding Description
The invariant that should hold is: `total_reward == NEAR credited by the validator staking mechanism only`, i.e. `total_balance - last_total_balance` should equal only the validator rewards accrued since the last ping, not arbitrary incoming transfers. In `internal_ping` (`staking-pool/src/internal.rs`, lines 194-250), the code does: [1](#0-0) 

`env::account_balance()` reflects the *entire* NEAR balance of the account, including any plain transfers received by the contract — there is no way for the contract to distinguish "reward NEAR" from "donated NEAR." Since `self.last_total_balance` is only updated inside `internal_ping` (and adjusted in `internal_deposit`/`internal_withdraw` for tracked user flows), any bare `Promise`-less transfer sent to the account via a normal NEAR transaction bypasses those bookkeeping updates entirely and simply raises `env::account_balance()`.

`internal_ping` only runs once per epoch (guarded by `self.last_epoch_height == epoch_height` check at lines 196-198), so the attacker's exact exploit is:
1. Wait for (or race to be) the first transaction touching the pool in a new epoch.
2. Send a plain NEAR transfer to the pool account (no method call, so no `internal_ping` is triggered by that transfer itself).
3. Call `ping()` (or any of `deposit`, `stake`, `unstake`, `withdraw`, all of which invoke `internal_ping` at the top) before anyone else does.
4. `total_balance` now includes the donated NEAR; `total_reward` is computed as if it were a validator reward, and split via `reward_fee_fraction` between the owner (as new stake shares) and the existing pool stakers (via increased `total_staked_balance`, raising the share price for everyone holding shares at that moment) — see lines 213-234.

None of the existing guards catch this: `assert_owner` is not required (`ping` is intentionally public), `assert_self()` doesn't apply here, and the only balance assertion is `total_balance >= self.last_total_balance` (line 208-211), which is satisfied trivially since donations only increase the balance. There is no check that the increase in balance actually originated from staking rewards versus a direct transfer.

### Impact Explanation
The donated NEAR is absorbed into `total_staked_balance` and distributed as if it were validator reward:
- A portion becomes `owners_fee`, minted as new stake shares for `self.owner_id` — the owner receives value they are not entitled to, funded by the attacker's own transfer (this part is merely a wasteful donation to the owner, not itself a theft from other parties).
- The remaining `remaining_reward` is added directly to `self.total_staked_balance` without minting new shares, which increases the "stake" share price for **all existing shareholders instantly**, retroactively crediting anyone who already held shares before the donation and diluting/crediting future price calculations.

This breaks the accounting invariant that `total_reward` should reflect only real staking rewards. The primary externally verifiable damage is to the internal reward/fee attribution bookkeeping (a value diverging from reality that other parties — the owner and all delegators — settle on), rather than making NEAR leave the contract to an unauthorized party (the attacker gains nothing directly; they are giving NEAR to the pool, and that NEAR mostly benefits the owner and other existing stakers). This most closely resembles the **High** severity category ("rewards or owner fees attributed to the wrong party ... an accounting value diverging from reality where another party settles on it"), but note the attacker does not personally profit from this action — they burn their own NEAR to (mis)inflate other parties' stake price and the owner's fee shares. This is a genuine accounting integrity bug but does not constitute "theft" benefiting the attacker; it's closer to a griefing/donation misattribution than a direct extraction of value by the attacker.

### Likelihood Explanation
Trivial to execute: any account can send a plain transfer to a public pool account and then call `ping()` in the same or next transaction. No special privileges, deposits requirements, or races beyond being first in a new epoch are required (and if the attacker is not first, another party's incidental action would trigger `internal_ping` anyway, absorbing the donation the same way — so it doesn't strictly need to be the attacker who is first, weakening the "attacker-controlled first ping" framing but not the underlying donation-becomes-reward bug). Cost is only the amount of NEAR donated plus gas; the "gain" is not to the attacker (they lose the donated NEAR to third parties), so the practical incentive for a purely profit-seeking attacker is limited to griefing/miscrediting scenarios (e.g., inflating a competitor's or their own colluding account's share value, or forcing extra owner fee).

### Recommendation
Track balance deltas explicitly tied to staking mechanics rather than relying on raw `env::account_balance()` deltas, or explicitly document/accept that this "donation-becomes-reward" behavior is intended (many NEAR staking-pool forks treat this as accepted behavior since it only benefits existing stakers/owner, not the depositor). If unintended, consider snapshotting/ignoring balance increases that are not accompanied by locked-balance change from the protocol, though full mitigation is likely impractical since NEAR's account model has no way to distinguish transfer sources.
