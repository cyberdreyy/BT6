### Title
Already-claimed instant-withdraw receipts remain in `instantWithdrawClaimsByEpoch`, inflating default-recovery basis and prefunded reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When an instant-withdraw receipt is normally claimed via `claimInstantWithdrawRequest`, only the aggregate `instantWithdrawsRequests[_user]` is cleared. The per-epoch basis (`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`) is never decremented. If the borrower later defaults in that same epoch while other instant receipts remain unfunded (`pendingInstantWithdraws != 0`), `finalizeDefaultRecovery` counts the already-paid-out receipts both as outstanding claim basis and as "prefunded" strategy-held reserve, minting phantom recovery backing. Recovery price is diluted for all claimants and `defaultRecoveryReserve` ends up larger than the real token balance, so the last defaulted/instant claimants' transfers revert permanently.

### Finding Description
The analog of the report's "stale/uninitialized state reused after it was already consumed" is the missing per-epoch cleanup in `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393):

- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (lines 371-372).
- `claimInstantWithdrawRequest` burns the receipt and pays out, but only resets `instantWithdrawsRequests[_user]` (lines 387-392). Neither the per-user per-epoch entry nor the global `instantWithdrawClaimsByEpoch` is reduced. Compare with the normal withdraw path, which clears `withdrawsRequestsByEpoch` in `_clearWithdrawClaimForEpoch` (lines 815-820).
- On default, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644-649), and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held by the strategy (lines 716-723).

The stale basis therefore double-counts paid receipts: once as claim basis (lowering `defaultRecoveryPrice` at line 688) and once as reserve (inflating `defaultRecoveryReserve` at line 691 with funds that were already transferred to the claiming user).

### Impact Explanation
Concrete sequence in a running epoch with instant withdraws enabled:

1. Honest user U2 and attacker U1 each request an instant withdraw (e.g. 100 underlying each). `instantWithdrawClaimsByEpoch[E] = 200`, `pendingInstantWithdraws = 200`.
2. Borrower funds only 100; `collectInstantWithdrawFunds(100)` leaves `pendingInstantWithdraws = 100`.
3. U1 calls `claimInstantWithdrawRequest` (via `IdleCDOEpochVariant.claimInstantWithdrawRequest`) and receives the 100 funded underlying. Per-epoch entries stay 200.
4. Borrower defaults; manager finalizes via `finalizeDefaultRecovery`. `defaultPendingClaimBasis` includes 200 instead of 100, and `_defaultPrefundedInstantReserve` returns 100 that no longer exists in the strategy balance.
5. `defaultRecoveryReserve` is set 100 higher than the real balance. U2's defaulted instant claim and other defaulted withdraw claims consume reserve pro-rata; the diluted `defaultRecoveryPrice` underpays every claimant, and once the reserve bookkeeping exceeds the actual balance, `_transferDefaultRecovery` (line 916) reverts for the last claimants — permanent freezing of their unclaimed recovery.

Broken invariants: one receipt one payout (U1's receipt is paid once at par and then counted again as reserved basis) and solvency of the isolated recovery reserve (reserve > actual balance). Existing guards do not stop it: the `_transferFundedClaim` reserve check (lines 899-905) only protects the reserve during funded claims, not the overstatement at finalization; `defaultInstantWithdrawsFinalized` legitimately enables the defaulted-epoch path whenever `pendingInstantWithdraws != 0`.

Quantified loss: an attacker who requests an instant withdraw equal to X, gets funded and claims it, inflates the recovery basis by X and creates X phantom reserve. All other claimants lose `X / totalBasis` of their recovery each, and claimants totaling up to X of reserve can never withdraw. Attacker cost is only their already-returned principal.

### Likelihood Explanation
Requires only unprivileged actions: a KYC-passing lender requests an instant withdraw in a running epoch with `allowInstantWithdraw`, gets funded before other requesters, claims, and the epoch later ends in borrower default while some instant requests remain unfunded. No privileged misbehavior is needed — partial funding of instant withdraws followed by default is a normal failure mode the code explicitly handles (`pendingInstantWithdraws` remainder, `_defaultPrefundedInstantReserve`). Likelihood is moderate: it needs an epoch with instant-withdraw demand exceeding funded liquidity followed by default, but the trigger is entirely within honest-actor sequencing around attacker transactions.

### Recommendation
In `claimInstantWithdrawRequest`, clear the claimed amount from the per-epoch buckets for the epoch(s) it belongs to, mirroring `_clearWithdrawClaimForEpoch`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol, in claimInstantWithdrawRequest
uint256 amount = instantWithdrawsRequests[_user];
uint256 reqEpoch = /* epoch the receipt belongs to */;
instantWithdrawsRequestsByEpoch[_user][reqEpoch] -= amount;
instantWithdrawClaimsByEpoch[reqEpoch] -= amount;
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
```

If receipts can span epochs, store the request epoch per user (e.g. a `lastInstantWithdrawRequest` marker) or iterate/record it at request time so the correct `instantWithdrawClaimsByEpoch` bucket is decremented. Additionally, consider making `_defaultPrefundedInstantReserve` recompute prefunded amounts from live per-epoch user data rather than the global counter, and add an invariant check in `finalizeDefaultRecovery` that `defaultRecoveryReserve <= underlyingToken.balanceOf(address(this))`.

### Proof of Concept
Foundry fork test sketch (setup mirrors `test/foundry/IdleCDOEpochQueue.t.sol` `testClaimInstantWithdrawRequest`):

```solidity
function testStaleInstantBasisInflatesRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);

    uint256 instantDelay = 100;
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 1e18, false);

    address u1 = makeAddr('u1');
    address u2 = makeAddr('u2');
    uint256 t1 = _depositWithUser(u1, 100e6);
    uint256 t2 = _depositWithUser(u2, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();
    skip(instantDelay + 1);

    // both request instant withdraws in epoch E
    _requestInstantWithdrawWithUser(u1, t1); // requestInstantWithdraw via cdo
    _requestInstantWithdrawWithUser(u2, t2);
    uint256 epoch = strategy.epochNumber();
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 200e6);
    assertEq(strategy.pendingInstantWithdraws(), 200e6);

    // borrower/manager funds only u1's share through the normal instant-funding flow
    _fundInstantWithdraws(100e6);            // collectInstantWithdrawFunds(100e6)
    assertEq(strategy.pendingInstantWithdraws(), 100e6);

    // u1 claims fully; per-epoch basis is NOT cleared
    vm.prank(u1);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequests(u1), 0);
    // BUG: stale basis remains
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 200e6); // expected 100e6

    // borrower defaults; manager finalizes recovery
    _defaultAndFinalize(recoveredAmount);

    // inflated basis diluted the price, and reserve exceeds real balance by 100e6
    uint256 reserve = strategy.defaultRecoveryReserve();
    assertGt(reserve, underlying.balanceOf(address(strategy))); // phantom reserve

    // last claimant's transfer reverts -> permanent freeze
    vm.prank(u2);
    vm.expectRevert(); // underflow / ERC20 transfer fail in _transferDefaultRecovery
    cdoEpoch.claimInstantWithdrawRequest();
}
```
