## Title
Removed multisig member's stale confirmation can push an unconfirmed request past the confirmation threshold - (`File: multisig2/src/lib.rs`)

### Summary
When a member is removed from the multisig via `DeleteMember`, the contract only purges *requests created by* that member and its `num_requests_pk` counter, but it never scans the `confirmations` map to strip that member's votes from *other members' still-open requests*. Because `confirm()` only compares the size of the cached `confirmations` set to `num_confirmations` — without validating that every entry in that set still corresponds to a current member — a request can accumulate a confirmation from a member that has since been removed, and later execute once enough *additional* confirmations arrive, even though the number of currently-live approving members never reached `num_confirmations`.

This is structurally the same bug class as the Raydium AMM report: a mutating "cancel"-style action (`DeleteKey`/`DeleteMember`) fails to refresh a cached count (`confirmations`) that a subsequent check (`confirm`'s threshold comparison) relies on, letting a stale value stand in for live state.

### Finding Description
`confirm()` decides whether to execute a request purely by counting entries in the cached `confirmations` set: [1](#0-0) 

`delete_member()` is the only cleanup routine invoked when a member is removed (via `execute_request`'s `DeleteMember` branch), and it explicitly filters requests by `r.member == member` — i.e., requests *authored* by the removed member — while leaving `self.confirmations` for every *other* request untouched: [2](#0-1) 

The `DeleteMember` action is dispatched from `execute_request`: [3](#0-2) 

Consequence: if member `A` confirms a request `R` created by member `B`, and afterwards `A` is removed from the multisig (a separate, independently-confirmed `DeleteMember` request), `R`'s confirmation set still contains `A`. `A`'s vote never gets scrubbed because `delete_member` only touches requests *authored* by `A`, not requests `A` merely confirmed. `confirm()` will then count `A`'s stale vote toward `num_confirmations`, letting `R` execute with fewer live, authorized approvals than the configured threshold requires.

The near-identical v1 contract has the same gap: `DeleteKey`'s cleanup in `execute_request` only removes requests where `r.signer_pk == pk` (i.e., requests created by that key), not requests merely confirmed by that key: [4](#0-3) 

### Impact Explanation
This breaks the custody binding "confirmations counted versus live members." The multisig's entire security model rests on `num_confirmations` distinct *live* members approving a request before funds move, keys are added, or contracts are deployed/called on the account's behalf. With this bug, a request can execute using a confirmation cast by a member who no longer has any authority, so the request executes with fewer real, current approvals than the configured threshold. Given the multisig can transfer NEAR, add/delete keys, or deploy/call contracts, this is a **Critical** impact per the rules ("a multisig request executed below threshold").

### Likelihood Explanation
No attacker key, foundation, or validator is required beyond the normal multisig membership churn that this contract is designed to support (adding/removing members is a core documented feature). Any workflow where a member confirms a pending request and is later removed before that request reaches quorum reproduces the stale-confirmation state; a colluding or compromised (former) member scenario makes this directly exploitable.

### Recommendation
When removing a member (`delete_member` in multisig2, `DeleteKey` cleanup in multisig v1), iterate `self.confirmations` for all open requests and strip the removed member's/key's entry, or alternatively re-validate on every `confirm()` call that all existing entries in the confirmations set still correspond to current members before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `B` calls `add_request` to create request `R` (e.g., a `Transfer`).
3. `A` calls `confirm(R)` → `confirmations[R] = {A}`.
4. Separately, members confirm a `DeleteMember{member: A}` request to threshold and it executes — `A` is removed from `members`, but `confirmations[R]` still contains `A` because `delete_member` only cleans requests *authored* by `A` (`r.member == member`), not `R` which `A` merely confirmed (`multisig2/src/lib.rs:355-379`).
5. `C` calls `confirm(R)` → `confirmations[R] = {A, C}`, size 2, still below threshold.
6. `D` calls `confirm(R)` → size check `2 + 1 >= 3` passes → `execute_request(R)` runs (`multisig2/src/lib.rs:304-309`).
7. `R` executes with only `C` and `D` as live, currently-authorized confirmers — one fewer live approval than `num_confirmations = 3` requires, because `A`'s stale vote was counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
