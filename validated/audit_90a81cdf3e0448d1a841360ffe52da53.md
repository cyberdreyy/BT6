### Title
OutgoingToken secret disclosed to any view-role user via GET /v2/external_initiators - ([File: core/web/presenters/external_initiators.go])

### Finding Description
`ExternalInitiatorResource` includes `OutgoingToken` as a plain, non-`omitempty` JSON field [1](#0-0) , and `NewExternalInitiatorResource` copies `ei.OutgoingToken` directly from the DB-loaded `bridges.ExternalInitiator` into the response resource with no redaction [2](#0-1) . The `Index` handler for `GET /v2/external_initiators` retrieves **all** external initiators in the system (paginated, ordered by name) without any per-user/ownership filter and maps each one through `NewExternalInitiatorResource` [3](#0-2) . The underlying ORM query `SELECT * FROM external_initiators ORDER BY name asc LIMIT $1 OFFSET $2` has no `WHERE` clause tying rows to a creating user [4](#0-3) , and the `external_initiators` schema has no owner/user column at all — external initiators are a node-wide (not per-user) resource. `OutgoingToken` is the credential the node sends as a bearer token when calling out to the initiator's registered URL, so its disclosure allows an attacker to impersonate the node's outbound call to that third-party endpoint.

### Impact Explanation
This matches the "sensitive credential disclosure" impact class: an authenticated but low-privileged (view-role) API user can read the `OutgoingToken` for external initiators created by other operators of the same node, and use it to make requests to the initiator's callback URL that appear to originate from the Chainlink node.

### Likelihood Explanation
Exploitation only requires a valid view-role session and a preexisting external initiator (created by anyone via `POST /v2/external_initiators`). No additional bypass of auth/role middleware is needed since the endpoint's own presenter/ORM logic returns the secret to any caller permitted to hit `Index`. However, I could not fully confirm the exact role gate applied to `GET /v2/external_initiators` in `core/web/router.go` (the grep found matches but I was unable to inspect the surrounding route-registration code, e.g., which `authorizedUserGuard`/`RequiresAuth` role level wraps `externalInitiatorsController.Index`) before running out of iterations. This is material because if the route is actually restricted to `admin`-only role (not `view`), the "unprivileged view-role user" precondition in the question would not hold, and the finding would reduce to intra-role information disclosure rather than a privilege-boundary violation. This should be verified directly in `core/web/router.go` before treating this as fully confirmed for the view-role threat model.

### Recommendation
- Redact `OutgoingToken` (and any other outbound secret) from the `Index`/list presenter entirely, or only return it once at creation time (as is already done via `ExternalInitiatorAuthentication` in `Create`) [5](#0-4) .
- If per-user attribution is desired, add an owner/user column to `external_initiators` and filter `Index` results, or restrict the listing endpoint to admin-only role.
- At minimum, remove `OutgoingToken` from `ExternalInitiatorResource` used by `Index`/`Show` and keep it only in the one-time creation response.

### Proof of Concept
Go handler-level integration test plan:
1. Using `cltest` test app, create two users: `admin` (or whichever role can create external initiators) and a `view`-role user.
2. As the initiator-creating user, `POST /v2/external_initiators` with a name/URL, capture the returned `outgoingToken` from `ExternalInitiatorAuthentication`.
3. As the `view`-role user, call `GET /v2/external_initiators`.
4. Assert the response body for that initiator's resource contains a non-empty `outgoingToken` field matching the value captured in step 2 (confirms disclosure), or, after the fix, assert `outgoingToken` is omitted/empty in the list response for all callers except at creation time.

Note: Before filing, confirm in `core/web/router.go` that the `Index` route for external initiators is indeed reachable by `view`-role sessions rather than restricted to `admin` role, since this determines whether the impact crosses a genuine unprivileged/privileged boundary.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

// ExternalInitiators returns a list of external initiators sorted by name
func (o *orm) ExternalInitiators(ctx context.Context, offset int, limit int) (initiators []ExternalInitiator, count int, err error) {
	err = o.transact(ctx, true, func(tx *orm) error {
		if err = tx.ds.GetContext(ctx, &count, "SELECT COUNT(*) FROM external_initiators"); err != nil {
			return pkgerrors.Wrap(err, "ExternalInitiators failed to get count")
		}

		sql := `SELECT * FROM external_initiators ORDER BY name asc LIMIT $1 OFFSET $2;`
		if err = tx.ds.SelectContext(ctx, &initiators, sql, limit, offset); err != nil {
			return pkgerrors.Wrap(err, "ExternalInitiators failed to load external_initiators")
		}
		return nil
	})
	return
}
