### Title
Instant-withdraw claims are not bound to the epoch that funded them — aggregate payout replays later, unfunded receipts into an earlier epoch's claim - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external bug (CVE-2026-12704) is a skipped response-to-request binding (`InResponseTo`), which turns a one-shot credential into a replayable one. The analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: instant-withdraw receipts are recorded per epoch (`instantWithdrawsRequestsByEpoch[user][epoch]`), but the claim path pays and clears the *aggregate* `instantWithdrawsRequests[user]` with no check that the paid amount corresponds to the epoch whose funds were actually collected. A claim processed for epoch N therefore also consumes receipts created in later epochs whose underlying was never collected via `collectInstantWithdrawFunds`, letting earlier claimants be paid for unfunded requests and permanently stripping later claimants' entitlements. [1](#0-0) [2](#0-1) 

### Finding Description

Instant withdraws are tracked two ways:

- Per-epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` in `requestInstantWithdraw` (lines 367–374).
- Aggregate: `instantWithdrawsRequests[_user] += _amount` (line 366).

Funding is also aggregate: `collectInstantWithdrawFunds(_amount)` decrements `pendingInstantWithdraws` and pulls underlying, with no epoch attribution (lines 398–403).

The claim, however, ignores epochs entirely:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:380-393
function claimInstantWithdrawRequest(address _user) external {
  _onlyIdleCDO();
  if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);
  }
  uint256 amount = instantWithdrawsRequests[_user];   // ALL epochs lumped together
  _burn(_user, amount);
  instantWithdrawsRequests[_user] = 0;
  _transferFundedClaim(_user, amount);
}
```

There is no equivalent of the funded-claim gating used for normal withdrawals — no epoch check, no verification that `amount <=` underlying actually collected for instant receipts, and no decrement of `instantWithdrawsRequestsByEpoch` outside the defaulted-epoch path (`_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`). [3](#0-2) 

The caller amplifies the mismatch: `IdleCDOEpochQueue.processWithdrawalClaims(_epoch)` is explicitly parameterized by epoch and measures `_received` vs `epochPendingClaims[_epoch]`, but for instant epochs it calls `claimInstantWithdrawRequest()` which returns the queue's *entire* aggregate instant balance — including receipts whose underlying was never collected. [4](#0-3) 

### Impact Explanation

Concretely, in a running epoch with instant withdrawals enabled:

1. Queue user A requests instant withdrawal in epoch N; `collectInstantWithdrawFunds` collects backing for it and `pendingInstantWithdraws` rises.
2. Before the epoch-N claim is processed, the queue (or the CDO directly for user A's later request) records *another* instant request in epoch N+1 which is *not* funded — e.g., instant withdrawals get disabled or there is no liquidity, so `collectInstantWithdrawFunds` is never called for it. `instantWithdrawsRequests[user]` now covers both epochs.
3. Any claim executed for epoch N (`processWithdrawalClaims(N)` via the queue, or the CDO's instant-claim path) pays the full aggregate at par via `_transferFundedClaim`, zeroing `instantWithdrawsRequests[user]` and burning the receipt tokens — including the unfunded N+1 portion. [5](#0-4) 

Result: the epoch-N claim is overpaid by exactly the unfunded later-epoch amount, paid out of the strategy's underlying balance that belongs to funded normal/instant claimants (only the `defaultRecoveryReserve` is ring-fenced, and only when nonzero). [6](#0-5)  Through the queue, the extra `_received` is folded into `epochWithdrawPrice[N]` (lines 353–357), so epoch-N claimants split a payout larger than their entitlement — direct theft from the pool — while the N+1 requesters' accounting (`instantWithdrawsRequestsByEpoch[user][N+1]`, `instantWithdrawClaimsByEpoch[N+1]`, `pendingInstantWithdraws`) still says they are owed, but their claimable balance was already burned and zeroed: their receipts are permanently unclaimable. This is the same shape as the advisory: a replay/authorization valid only for a specific context is accepted globally because the binding check is skipped.

### Likelihood Explanation

- Attacker surface is unprivileged: any user who can request instant withdrawals through the CDO or the queue (KYC'd lenders / tranche holders) triggers the accounting; the attacker just needs an unfunded instant request outstanding when an earlier-epoch claim executes.
- Trigger conditions are normal operations: instant withdrawals being toggled off (`setInstantWithdrawParams` with `disableInstantWithdraw`), liquidity shortfalls, or simply ordering where a second request lands in a later epoch before the first is claimed — all driven by honest manager/owner calls.
- The queue path is the worst case because `processWithdrawalClaims` is epoch-scoped and explicitly re-bases price on received amounts, so the overpayment is automatically distributed to epoch-N claimants.
- Caveat: exploitation requires an instant receipt to remain unfunded at claim time while the aggregate still contains it; whether `claimInstantWithdrawRequest` can be invoked by the CDO while `pendingInstantWithdraws` > 0 unfunded needs confirmation on the CDO side (`IdleCDOEpochVariant.sol` claim orchestration was not fully traced). If the CDO strictly collects before every claim, the residual risk is limited to partial collections and the defaulted-instant path.

### Recommendation

Bind instant-withdraw claims to the epoch(s) they settle:

- Track a funded instant balance separately from requested (`instantWithdrawsFunded[user]`), incremented in `collectInstantWithdrawFunds` proportionally or per-epoch, and pay only the funded portion.
- Alternatively, make `claimInstantWithdrawRequest` iterate `instantWithdrawsRequestsByEpoch` and pay only epochs whose `instantWithdrawClaimsByEpoch` was fully collected, clearing those entries — mirroring the per-epoch clearing already implemented for defaulted instant receipts in `_claimDefaultedInstantWithdrawRequest`. [3](#0-2) 
- Revert or cap the claim when `amount >` collected instant funds rather than silently paying unfunded receipts at par.

### Proof of Concept

Foundry fork sketch (build on `test/foundry/IdleCDOEpochQueue.t.sol` / `IdleCreditVault.t.sol` harness):

```solidity
// Setup: standard epoch variant, instant withdrawals enabled (delay=100, aprDiff=1e18)
// 1. Epoch N buffer: user via queue requests instant withdraw amountA.
//    Borrower/manager funds only amountA via collectInstantWithdrawFunds -> pendingInstantWithdraws = amountA (funded).
// 2. Epoch N+1: same queue requests instant withdraw amountB; manager disables instant
//    withdrawals (setInstantWithdrawParams(delay, bigDiff, true)) or provides no liquidity,
//    so collectInstantWithdrawFunds is never called for amountB.
//    instantWithdrawsRequests[queue] == amountA + amountB, only amountA funded.
// 3. manager calls queue.processWithdrawalClaims(epochN) -> _cdo.claimInstantWithdrawRequest()
//    transfers amountA + amountB to the queue and zeroes the aggregate.
// 4. epochWithdrawPrice[N] is re-based upward; epoch-N claimants each receive > entitlement.
// 5. Any attempt to claim the epoch N+1 instant receipt reverts or pays 0 even though
//    instantWithdrawsRequestsByEpoch[queue][N+1] == amountB and
//    pendingInstantWithdraws still includes amountB -> permanent loss for those claimants.

assertEq(underlying.balanceOf(address(queue)), amountA + amountB); // overpaid claim
assertEq(strategy.instantWithdrawsRequests(address(queue)), 0);    // N+1 receipt consumed
assertGt(strategy.instantWithdrawsRequestsByEpoch(address(queue), N+1), 0); // orphaned basis
```

Note: I could not fully verify the `IdleCDOEpochVariant.sol` orchestration (whether the CDO guarantees `collectInstantWithdrawFunds` covers the full `instantWithdrawsRequests[user]` before permitting a claim); if it does, the same defect still applies to partial collections and to the queue path where the epoch-scoped claim contractually expects an epoch-bound payout.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
