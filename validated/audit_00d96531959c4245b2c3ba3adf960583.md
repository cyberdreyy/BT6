### Title
Loss-adjusted and default-recovery claim math rounds down per-claimant payouts, permanently stranding funded underlyings in `IdleCreditVault` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
This is the same bug class as `rewardRate * duration < reward`: a fixed-point ratio is computed once by integer division, and every claimant's payout is `claimBasis * ratio / SCALE`. Since each multiplication rounds down, the sum of all payouts is strictly less than the amount actually funded, and the residual has no distribution path — `pendingWithdraws` is zeroed at funding time and `defaultRecoveryReserve` is only decremented by claims. The dust is permanently locked in the vault.

### Finding Description
Two sites implement the pattern:

1. `collectWithdrawFunds` stores `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` (floor division) and then zeroes `pendingWithdraws` (`IdleCreditVault.sol:417-421`). Each user later claims `claimBasis * lossRecoveryPrice / RECOVERY_FULL` via `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:799`). Because `lossRecoveryPrice * pendingBasis <= _amount * RECOVERY_FULL` and each per-claim multiply also rounds down, `Σ payouts <= _amount`, with the difference left in the strategy's underlying balance forever — `collectWithdrawFunds` cannot be called again for that epoch's receipts since `pendingWithdraws` is already 0, and the epoch key in `lossRecoveryPriceByEpoch` is never reused.

2. `finalizeDefaultRecovery` computes `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (`IdleCreditVault.sol:688`) and sets `defaultRecoveryReserve = reserveAmount`. All recovery claims (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`, plus active-side NAV repriced via `activeBasis * recoveryPrice / RECOVERY_FULL`) round down, so the reserve can never be fully drained; the code itself acknowledges "any positive reserve too small to represent at `RECOVERY_FULL` precision remains isolated as recovery dust" (`IdleCreditVault.sol:655-657`), but the bound is actually per-claim rounding, not just subprecision reserves.

The same shape exists for APR0 interest: `apr0RateByEpoch[epochNumber] = _apr0NetInterest * 1e18 / _principal` rounds down, so `_apr0NetInterest` added to `pendingWithdraws` exceeds what `Σ principal * rate / 1e18` pays out (`IdleCreditVault.sol:537,561`).

### Impact Explanation
Permanent freezing of unclaimed yield. Per loss-adjusted epoch, up to `N_claimants + 1` wei of already-borrower-funded underlyings are stranded; per default finalization, up to `N_claimants + active` wei of recovered funds are stranded inside `defaultRecoveryReserve`. For low-decimals/high-value underlyings (e.g., WBTC-like pools or future integrations), per-epoch dust across repeated `stopEpochWithDuration(_lossAmount)` calls accumulates, matching the original report's "more damaging if token precision is low or calls are frequent" argument. `_transferFundedClaim` explicitly forbids spending the reserve, and `pendingWithdraws`/`lossRecoveryPriceByEpoch` provide no re-distribution path; only the privileged `transferToken` rescue can recover it.

### Likelihood Explanation
No attacker action is required — this is an accounting invariant, identical to the reference finding. It triggers on any `stopEpochWithDuration` with `_lossAmount > 0` while pending receipts exist, or any borrower default followed by `finalizeDefaultRecovery`. Rounding to zero is guarded (`lossRecoveryPrice == 0` reverts), but nonzero dust is unguarded and deterministic whenever `_amount * RECOVERY_FULL` is not a multiple of `pendingBasis` or individual `claimBasis` values don't divide evenly.

### Recommendation
Track the remainder and route it deterministically: e.g., in `collectWithdrawFunds`/`finalizeDefaultRecovery` leave `pendingWithdraws`/`defaultRecoveryReserve` consistent with `ceil`-priced aggregate payout, or let the last claimant receive the residual (`amount = min(computed, remaining reserve)`), or add a sweep that forwards post-finalization dust to `feeReceiver`. Alternatively compute `lossRecoveryPrice` with `ceil` division and cap each claim at the remaining funded balance.

### Proof of Concept
Foundry fork-style sketch (against an existing epoch vault on `mainnet`):

```solidity
// Epoch running; two lenders requested withdrawals: pendingBasis = 1001 units.
// Manager calls stopEpochWithDuration(newApr, 0, duration, lossAmount) such that
// previewLossAdjustedWithdrawFunds returns pendingToFund = 500, activeLoss = rest.
// IdleCDO calls collectWithdrawFunds(500):
//   lossRecoveryPrice = 500 * 1e18 / 1001 = 499500499500499500 (floor)
//   pendingWithdraws = 0
// After buffer, both users claim via IdleCDO.claimWithdrawRequest:
//   userA basis 1   -> 1 * price / 1e18   = 0
//   userB basis 1000-> 1000 * price / 1e18 = 499
// Strategy retains 500 - 499 = 1 unit of funded underlying with pendingWithdraws == 0;
// no subsequent call can redistribute it.
```

Analogous default case: call `finalizeDefaultRecovery(recovered, source)` with `reserveAmount` not divisible by `totalBasis`; after all `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` calls, `defaultRecoveryReserve > 0` with every claim mapping cleared — the residual is unreachable.
