### Title
Public ERC4626 liquidity withdrawal can repeatedly block epoch settlement and freeze withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

In programmable-borrower mode, `IdleCDOEpochVariant._stopEpoch()` calls `ProgrammableBorrower.onStopEpoch()` before pulling funds. When the borrower does not hold enough underlying, `onStopEpoch()` attempts `vault.withdraw(shortfall)` and converts any failure into `StopEpochVaultLiquidityUnavailable`, reverting the entire epoch stop. An unprivileged user of the configured ERC4626 vault can consume its available liquidity so the borrower’s shares remain economically sufficient but their liquidity is temporarily unavailable. Every honest `stopEpoch()` call can then be made to revert, keeping the epoch running and delaying pending withdrawal funding.

### Finding Description

`startEpoch()` pauses deposits and disables new withdrawal requests while marking the epoch as running. [1](#0-0) 

At epoch end, `_stopEpoch()` requires the programmable borrower hook to succeed before it calls `getFundsFromBorrower()`, funds pending withdrawals, accrues accounting, and reopens requests. [2](#0-1) 

`ProgrammableBorrower.onStopEpoch()` compares the cash shortfall to `_currentVaultAssets()`. If the borrower’s vault shares cover the shortfall, it calls `vault.withdraw(shortfall, address(this), address(this))`; any ERC4626 withdrawal failure is caught and deliberately rethrown as `StopEpochVaultLiquidityUnavailable`. [3](#0-2) 

A public vault participant can therefore put the vault into a state where:

```solidity
vault.convertToAssets(programmableBorrower.vaultSharesBalance()) >= shortfall
vault.maxWithdraw(address(programmableBorrower)) < shortfall
```

For example, in a lending-style ERC4626 vault, the attacker supplies collateral and borrows the vault’s idle underlying, leaving the borrower’s share valuation intact while removing withdrawable cash. Alternatively, an existing vault shareholder with sufficient claim over idle liquidity can redeem before the stop transaction.

Because the hook reverts before `_stopEpoch()` reaches its `try/catch` borrower-default path, the transaction does not finalize as a default. [4](#0-3)  The epoch remains `isEpochRunning`, normal withdrawal requests remain unfunded, and the CDO remains in its no-deposit/no-new-request state. Users also cannot claim a newly created request while `epochNumber <= lastWithdrawRequest[user]` and the epoch is still open. [5](#0-4) 

The attacker can repeat the liquidity consumption whenever the vault regains idle liquidity, extending the freeze across successive honest `stopEpoch()` attempts.

### Impact Explanation

This is a temporary freezing vulnerability affecting the amount required to settle the epoch:

```text
frozen amount = expectedInterest + pendingWithdraws
```

or, when the manager uses close-pool mode (`_interest == 1`), substantially all recalled principal plus pending withdrawals.

The frozen value can be quantified onchain as:

```solidity
uint256 frozen = strategy.pendingWithdraws() + programmableBorrower.totalInterestDueNow();
```

For a 10,000 USDC pool with a 5,000 USDC pending request, draining the ERC4626 vault’s available cash below `5,000 USDC` while preserving share valuation blocks the 5,000 USDC withdrawal funding and leaves the epoch unclosed. In close-pool mode, the same condition can delay the pool’s entire strategy-token principal.

The issue does not directly steal assets or create insolvency. Its impact is sustained settlement delay and withdrawal freezing for as long as public vault liquidity can be kept below the required recall amount.

### Likelihood Explanation

Likelihood is medium for deployments whose configured ERC4626 vault exposes idle liquidity to unprivileged borrowers or redeemers. No IdleCDO privileged role is required: the attacker only needs to perform ordinary vault-side liquidity consumption after `epochEndDate`, around the honest manager’s `stopEpoch()` transaction.

The production code explicitly treats this condition as retryable rather than defaulting, so existing guards do not prevent repetition. [3](#0-2) 

The attack requires enough vault-side borrowing power or share ownership to consume the relevant idle liquidity. That capital requirement reduces likelihood, but the attacker does not need to keep capital in IdleCDO and can repeatedly target subsequent retry attempts.

### Recommendation

Do not let an otherwise solvent ERC4626 liquidity failure indefinitely restart the same stop-epoch flow without a bounded resolution path.

Recommended changes:

1. Preflight `vault.maxWithdraw(address(this))` or `maxRedeem(address(this))` separately from `convertToAssets`.
2. Persist a settlement snapshot and expose a permissionless retry path that does not recalculate epoch obligations on each attempt.
3. Add a bounded liquidity-recovery deadline or retry policy, after which owner/manager can choose an explicit insolvency/default path rather than leaving the epoch permanently open.
4. Consider a fallback `redeem()` path where `withdraw()` is unavailable but share redemption is supported.
5. Emit the vault-reported `maxWithdraw`, share backing, and shortfall to distinguish transient liquidity exhaustion from real borrower insolvency.

### Proof of Concept

Add this test to `test/foundry/ProgrammableBorrowerCreditVault.t.sol`. The existing `MockStopEpochLiquidityVault.setWithdrawLimit()` models the state reached after a public vault user consumes idle ERC4626 liquidity while share valuation remains sufficient.

```solidity
function testPublicVaultLiquidityDrainBlocksStopEpochAndWithdrawal() external {
    MockStopEpochLiquidityVault limitedVault =
        new MockStopEpochLiquidityVault(USDC);
    address liquidityAttacker = makeAddr("liquidityAttacker");
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    vm.prank(manager);
    programmableBorrower.setVault(address(limitedVault));

    idleCDO.depositAA(amount);

    uint256 requested = aaTranche.balanceOf(address(this)) / 2;
    cdoEpoch.requestWithdraw(requested, address(aaTranche));
    uint256 claimBasis = strategy.pendingWithdraws();

    _startEpochAndCheckPrices(0);

    assertGt(
        limitedVault.convertToAssets(
            limitedVault.balanceOf(address(programmableBorrower))
        ),
        claimBasis,
        "borrower shares should economically cover the recall"
    );

    // Models a public ERC4626 borrower/redeemer consuming the vault's idle cash.
    vm.prank(liquidityAttacker);
    limitedVault.setWithdrawLimit(claimBasis - 1);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.expectRevert(
        abi.encodeWithSelector(
            StopEpochVaultLiquidityUnavailable.selector
        )
    );
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning(), "epoch was not settled");
    assertFalse(cdoEpoch.defaulted(), "liquidity failure did not default");
    assertEq(strategy.pendingWithdraws(), claimBasis, "request remains unfunded");

    // The same public liquidity condition can be recreated before each retry.
    vm.warp(block.timestamp + 1 days);
    vm.prank(liquidityAttacker);
    limitedVault.setWithdrawLimit(claimBasis - 1);

    vm.expectRevert(
        abi.encodeWithSelector(
            StopEpochVaultLiquidityUnavailable.selector
        )
    );
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning(), "second settlement attempt blocked");
    assertEq(strategy.pendingWithdraws(), claimBasis, "withdrawal still frozen");
}
```
