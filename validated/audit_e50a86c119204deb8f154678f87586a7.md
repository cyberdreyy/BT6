### Title
Vault liquidity squeeze forces `onStopEpoch` to revert, freezing LP funds instead of defaulting - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable` whenever the ERC4626 vault's *redeemable* liquidity is insufficient to cover the stop-epoch shortfall, even though the borrower's vault shares still have positive `convertToAssets` value. A user of the external ERC4626 vault (an in-scope unprivileged attacker) can drain the vault's free liquidity right before `stopEpoch`, causing `IdleCDOEpochVariant.stopEpoch` to revert permanently/temporarily instead of falling through to the borrower-default path.

### Finding Description
In `onStopEpoch`, when on-hand underlying is less than `_amountRequired`, the code computes `shortfall` and only allows the "graceful" path (`return true`, letting the CDO's `transferFrom` fail → `_handleBorrowerDefault`) if `shortfall > _currentVaultAssets()` (i.e., shares can't economically cover it). Otherwise it attempts `vault.withdraw(shortfall, ...)` and **reverts** on failure:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:240-253
if (_amountRequired > onHand) {
    uint256 shortfall = _amountRequired - onHand;
    if (shortfall > _currentVaultAssets()) return true;
    try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        ...
    } catch {
        revert StopEpochVaultLiquidityUnavailable();
    }
}
```

The crash (NULL-deref → revert) analog: `_currentVaultAssets()` uses `convertToAssets`, which prices shares against the vault's *total* assets — including assets lent out / illiquid. `vault.withdraw`, however, fails when the vault's *free* balance is below `shortfall`. So the two conditions diverge exactly when the vault is illiquid but shares remain valuable — a state any vault depositor can create by withdrawing all available liquidity (standard ERC4626 behavior when the vault lends funds onward).

Because `onStopEpoch` is called inside `IdleCDOEpochVariant._stopEpoch` before `getFundsFromBorrower`/`sendFundsToBorrower` try/catch blocks, the revert propagates out of `stopEpoch` entirely: the honest manager cannot close the epoch, and `_handleBorrowerDefault` is never reached.

### Impact Explanation
All LP funds (AA + BB tranches) parked in the borrower facility remain locked: `isEpochRunning` stays true, deposits stay paused, and `allowAAWithdrawRequest`/`allowBBWithdrawRequest` stay false. If the attacker keeps the vault drained (or the vault's assets are durably illiquid), the freeze is permanent — every call to `stopEpoch`/`stopEpochWithDuration` reverts with `StopEpochVaultLiquidityUnavailable`. The attacker profits by effectively borrowing vault liquidity while the CDO is forced to keep extending the facility. Quantified loss: the entire shortfall amount (`_amountRequired - onHand`), up to the full vault share value held by `ProgrammableBorrower`, is frozen/unrecoverable via the normal path (only `emergencyExitVault`/`rescueTokens` remain, and `emergencyExitVault` also reverts when the vault can't pay out).

### Likelihood Explanation
Requires a programmable-borrower deployment and an ERC4626 vault whose liquidity can be withdrawn by third parties — explicitly an allowed attacker class ("a user of the programmable borrower's ERC4626 vault"). The attack needs no privileged role, is cheap (withdraw vault liquidity before epoch end), and is repeatable: any retry of `stopEpoch` reverts until liquidity returns. The existing guards don't help: `shortfall > _currentVaultAssets()` is false precisely because shares still carry value, so the `catch → revert` branch is hit every time.

### Recommendation
Treat a failed vault withdrawal the same as an economically uncovered shortfall: let `onStopEpoch` return `true` (or `false`) so the CDO's `transferFrom` failure triggers `_handleBorrowerDefault` and the established default/finalizeDefault flow, rather than reverting. If a retryable stop is desired, gate the revert behind an explicit manager call instead of blocking the default path — e.g., `try vault.withdraw(...) { ... } catch { return true; }` so `transferFrom` fails cleanly into default handling.

### Proof of Concept
Foundry fork test sketch:

```solidity
// Assume programmable deployment: IdleCDOEpochVariant (cdoEpoch) with
// ProgrammableBorrower (pb) whose `vault` is a real/permissionless ERC4626.

// 1. LPs deposit, epoch runs, pending interest exists.
idleCDO.depositAA(10_000e6);
cdoEpoch.startEpoch();

// 2. Attacker (any ERC4626 vault user) drains free liquidity so that
//    vault.withdraw(shortfall) reverts while pb's shares still price > 0.
vault.redeem(vault.balanceOf(attacker), attacker, attacker); // or withdraw max
// vault now holds ~0 free asset but pb.convertToAssets(shares) > shortfall

// 3. Borrower keeps funds; manager tries to close the epoch.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// 4. Retry forever: still reverts, default is never declared.
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 1);
assertFalse(cdoEpoch.defaulted());   // no default path reached
// LP funds frozen: requestWithdraw/claim paths remain disabled while
// isEpochRunning == true and borrower retains the drawn assets.
```
