### Title
Gross `_amount` is used for minting, forwarding, and accounting instead of the net amount actually received - (contracts/IdleCDOEpochVariant.sol, contracts/IdleCDOCreditVault.sol)

### Summary
In the external report, `stake.amount` stored the pre-fee `_amount` rather than the post-fee `stakedAmount`. The same bug class exists in the credit-vault deposit paths: `depositDuringEpoch` (and the base `_deposit`'s strategy push) use the caller-supplied gross `_amount` for share minting, `expectedEpochInterest`, `mintStrategyTokens`, and the onward transfer to the borrower, even though only the net received balance may have arrived (fee-on-transfer underlying). The base `_deposit` correctly mints on the balance delta (`_contractTokenBalance(_token) - _preBal`), proving the codebase intends to support tokens that deliver less than `_amount` — but it then pushes the gross `_amount` into the strategy, and `depositDuringEpoch` never measures a delta at all.

### Finding Description
`IdleCDOEpochVariant.depositDuringEpoch` pulls `_amount` from the depositor (`_transferUnderlyingsFrom(msg.sender, address(this), _amount)`) and then:

- mints tranche tokens priced off gross `_amount`: `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` [1](#0-0) 
- increases `expectedEpochInterest` and mints strategy tokens via `IdleCreditVault(strategy).mintStrategyTokens(_amount)` for the gross amount [2](#0-1) 
- forwards the gross `_amount` to the borrower: `_transferUnderlyings(_borrower(), _amount)` [3](#0-2) 

No balance-delta is measured, so if the underlying takes a transfer fee (e.g., a fee-on-transfer or rebasing-style pool currency), the vault receives `received < _amount` yet credits the depositor and disburses the borrower as if `received == _amount`. The shortfall is paid out of the CDO's existing token balance, i.e., out of other depositors' principal. The same discrepancy exists in `IdleCDOCreditVault._deposit`: shares are minted on the true delta, but `IIdleCDOStrategy(strategy).deposit(_amount)` pulls the gross amount out of the CDO, silently drawing the fee gap from funds belonging to existing tranche holders [4](#0-3) .

The invariant broken is fair mint/burn plus solvency: credited claim > assets actually contributed, with the difference socialized across all LPs.

### Impact Explanation
An unprivileged, KYC-passing lender can repeatedly deposit with a fee-on-transfer underlying (or arrange the underlying to deduct on transfer). Each deposit mints them tranche tokens and epoch interest entitlement for the full `_amount` while the pool only received `_amount - fee`, and the pool simultaneously pays the full `_amount` onward to the borrower or strategy. The attacker then exits (via `requestWithdraw`/claims at epoch end, or by selling tranche tokens) having been credited more than they contributed; the residual deficit is insolvency borne by remaining depositors — quantified as `fee` per deposit, unbounded across repeated deposits. Note this only applies if the configured `token` can deliver less than the transferred amount; for plain USDC-like underlyings there is no gap. The balance-delta logic already present in `_deposit` shows fee-on-transfer handling was an intended property, so deployments with such tokens are realistically affected.

### Likelihood Explanation
Conditional: it requires the vault's underlying `token` to charge on transfer (or any path where received < sent). Where that holds, any whitelisted depositor can trigger it in the buffer phase (`_deposit`/strategy push) or mid-epoch (`depositDuringEpoch`, which additionally skips balance-delta minting entirely and inflates `expectedEpochInterest`/`mintStrategyTokens`). No privileged cooperation is needed; `isWalletAllowed` only gates the caller, not the token behavior. Likelihood is therefore deployment-dependent: high for fee-charging pool currencies, nil for pure feeless tokens.

### Recommendation
Measure the net received amount everywhere and use it consistently:

- In `depositDuringEpoch`: record `received = _contractTokenBalance(token) - preBal` after `_transferUnderlyingsFrom`, and use `received` for `_calcInterest`, `trancheInterest`, the `_minted` formula, `expectedEpochInterest += interest`, `mintStrategyTokens(received)`, and `_transferUnderlyings(_borrower(), received)`.
- In `IdleCDOCreditVault._deposit`: pass the measured delta (`_contractTokenBalance(_token) - _preBal`, already computed for minting) to `IIdleCDOStrategy(strategy).deposit(...)` instead of `_amount`.
- Optionally `require(received == _amount)` if fee-on-transfer underlyings are not supported, or whitelist the underlying at factory level.

### Proof of Concept
Foundry sketch (deploy vault with a mock fee-on-transfer ERC20 as `token`):

```solidity
// MockFoT burns `feeBps` on every transferFrom.
contract DepositFeeInflationTest is Test {
    function testDepositDuringEpochGrossAmount() public {
        // setup: epoch running, isDepositDuringEpochDisabled=false, AA supply seeded
        uint256 amount = 1000e6;
        deal(address(fot), attacker, amount);

        vm.startPrank(attacker);
        fot.approve(address(cdoEpoch), amount);
        uint256 minted = cdoEpoch.depositDuringEpoch(amount, address(AAtranche));
        vm.stopPrank();

        // fot took 1% on the inbound transfer: vault got 990, but
        // borrower was sent 1000 and tranche tokens/interest were minted for 1000.
        uint256 received = amount * (BPS - feeBps) / BPS;
        assertLt(fot.balanceOf(address(cdoEpoch)) + received, amount);
        // deficit: minted claim + borrower disbursement exceed received by `fee`
        // -> drain over repeated deposits leaves insolvency for other LPs.
    }
}
```

I was not able to confirm the exact implementation of `_transferUnderlyings`/`_transferUnderlyingsFrom` or whether the factory restricts `token` to feeless assets within the remaining exploration budget; if `token` is hard-restricted to a known feeless asset (e.g., USDC) at deploy time, the practical exploitability is limited to `depositDuringEpoch`'s accounting inconsistency rather than a live theft path.
