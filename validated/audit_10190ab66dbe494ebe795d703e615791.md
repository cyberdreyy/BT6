The kernel bug is a stale/NULLed "saved" pointer read by a concurrent path. The closest analog in this codebase is `IdleCreditVault._claimLossAdjustedWithdrawRequest`, which looks up the loss-adjusted epoch exclusively through `lastWithdrawRequest[_user]` — a single mutable pointer that gets overwritten by every new `requestWithdraw`.

Let me confirm the interaction.### Title
Loss-adjusted withdraw haircut is bypassed when `lastWithdrawRequest` is overwritten by a later request — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` applies a stop-epoch loss to pending withdraw receipts by storing a recovery price under `lossRecoveryPriceByEpoch[epochNumber]` in `collectWithdrawFunds`. At claim time, `_claimLossAdjustedWithdrawRequest` looks up that price using only `lastWithdrawRequest[_user]` — a single mutable per-user pointer that `requestWithdraw` overwrites on every new request. A lender whose receipt was haircutted in epoch N can file a new withdraw request in epoch N+1, shifting the pointer so the loss-adjusted path returns zero, and the funded-claim path then pays the full aggregate `withdrawsRequests[_user]` — including the epoch-N haircutted basis — at par.

### Finding Description
In `collectWithdrawFunds`, when the borrower underfunds pending receipts, the vault records `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and clears `pendingWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:411–430). The per-user claimable basis stays inside the aggregate `withdrawsRequests[_user]` plus per-epoch `withdrawsRequestsByEpoch[_user][epoch]` — it is only removed by `_clearWithdrawClaimForEpoch` (IdleCreditVault.sol:811–837).

At claim time (`claimWithdrawRequest`, IdleCreditVault.sol:301–314), the order is:
1. `_claimLossAdjustedWithdrawRequest(_user)` — computes `lossEpoch = lastWithdrawRequest[_user]` and reads `lossRecoveryPriceByEpoch[lossEpoch]` (IdleCreditVault.sol:789–801). If the user's *latest* request epoch has no stored recovery price, this returns 0 and **the older haircutted epoch is never consulted**.
2. `_claimFundedWithdrawRequest(_user)` — once `epochNumber > lastWithdrawRequest[_user]`, pays `withdrawsRequests[_user] + apr0 buckets` in full via `_transferFundedClaim` (IdleCreditVault.sol:319–350).

`requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds to `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch[_user][currentEpoch]` (IdleCreditVault.sol:282–293). The code's own comments confirm a user may request again before claiming ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests").

This mirrors CVE-2024-26731: a saved pointer (`saved_data_ready` / `lastWithdrawRequest`) is dereferenced to pick a handler, but a concurrent/later teardown path (`sk_psock_stop_verdict` / a new `requestWithdraw`) can leave the pointer referring to a state where the special-case handling silently disappears.

### Impact Explanation
A KYC-passing lender escapes the socialized loss entirely and is paid 100% on a receipt that should pay `recoveryPrice`. The overpayment `(claimBasis_N * (1 - lossRecoveryPriceByEpoch[N]) / RECOVERY_FULL)` comes directly from vault-held underlyings meant for other claimants and active LPs, breaking both the loss-waterfall invariant and "one receipt, one haircut" fairness. Every lender with a haircutted receipt is incentivized to do this (it's free — just re-request a dust withdraw after the loss epoch and wait one more epoch), so the aggregate theft can equal the entire pending-receipt loss amount, potentially rendering later claims insolvent.

### Likelihood Explanation
Likelihood is high once any loss-adjusted stopEpoch occurs: the trigger is a normal `requestWithdraw` by an unprivileged lender, requires no privileged cooperation, no flash loans, and no timing precision — just requesting in a later running epoch and waiting for `epochNumber` to advance. The only precondition is a partial `collectWithdrawFunds`, which is exactly the scenario the feature exists for. Note: whether a second `requestWithdraw` is accepted while a loss-adjusted receipt is still pending is allowed by the code path shown; if any upstream CDO gate blocked re-requesting while `defaulted`, this could narrow — I could not fully verify every `IdleCDOEpochVariant` entry guard within the iteration budget, but `requestWithdraw` itself performs no such check.

### Recommendation
Do not derive the claim route from `lastWithdrawRequest`. Iterate/check `withdrawsRequestsByEpoch[_user]` across epochs, or record a per-user `lossAdjustedEpoch`/bitmap when the request is made, or block new `requestWithdraw` while the user has an unclaimed receipt in an epoch with `lossRecoveryPriceByEpoch[epoch] != 0`. Alternatively, apply the haircut eagerly at `collectWithdrawFunds` time by scaling down `withdrawsRequestsByEpoch`/`withdrawsRequests` for that epoch.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
