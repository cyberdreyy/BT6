### Title
Rejection weight is never rescinded on a later Accept, letting a signer's stale rejection wedge a valid block into a false `SignersRejected` — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The external report's bug class is: an eligibility/threshold check is computed from a stale or wrong input component, letting an actor exploit the mismatch between what "should" be counted and what "is" counted. The reachable analog here is in the miner-side tally that a `SignerCoordinator` uses to decide whether a block proposal has crossed the 70% signing threshold or the 30% blocking-rejection threshold: `total_weight_approved` and `total_weight_rejected` are two independent running sums that are never reconciled against each other when the *same* signer's vote changes from Reject to Accept.

### Finding Description
`StackerDBListener`'s per-block tally keeps two counters, `total_weight_approved` and `total_weight_rejected`, updated by two separate branches of the same match statement:

- On `BlockResponse::Accepted`, weight is added to `total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)` [1](#0-0) .
- On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` guarded by `block.responded_signers.insert(slot_id)` [2](#0-1) .

These two guards are independent sets (`gathered_signatures` keyed by signature payload, `responded_signers` a generic "have we counted this slot" set). Nothing here deletes or decrements a signer's prior contribution to `total_weight_rejected` when that same signer later sends an `Accepted` message for the same block, or vice versa. A signer legitimately *can* switch its vote from Reject to Accept for the same block hash: the signer's own event loop explicitly re-evaluates and can flip a rejection to acceptance once "the reject reason allows us to reconsider" (e.g. transient `ConnectivityIssues`/`NoSortitionView`), as documented for `should_reevaluate_reject_reason` / `check_block_against_state` [3](#0-2) .

This is precisely the case the signer's own database layer (`SignerDb::add_block_signature`) was built to guard against: before recording a new signature it explicitly deletes any prior rejection entry for that signer/block pair so the two tallies stay mutually exclusive: [4](#0-3) 

The miner-side `stackerdb_listener.rs` tally has no equivalent reconciliation step, so a signer's weight can remain permanently counted in `total_weight_rejected` even after that same signer later accepts and is (correctly) added to `total_weight_approved`.

The consumer of these two counters, `SignerCoordinator::get_block_status`, checks the rejection condition first and unconditionally aborts once it holds: [5](#0-4) 

So if enough signers' *stale* (superseded) rejection weight, combined with a few genuinely-still-rejecting signers, pushes `total_weight_rejected + weight_threshold` past `total_weight`, the coordinator returns `NakamotoNodeError::SignersRejected` and the miner gives up on the block — even though the *current* opinion of the signer set (with the flipped votes correctly counted as accepts) may in fact be ≥70% in favor and fully signable.

### Impact Explanation
This is a liveness wedge on the miner/coordinator side: it can make the block-production pipeline (`signer_coordinator.rs`, explicitly in scope) declare a proposal permanently, incorrectly rejected and abandon it, even though a real supermajority of current signer opinion supports signing it. It does not itself let an invalid/non-canonical block get signed (the signatures placed in `gathered_signatures` are real, verified signer signatures over the real block hash — signature verification at lines 411–426 is unaffected), so this does not rise to a Critical safety break. It matches the High-severity liveness category ("a signer wedged into never signing valid blocks") but manifested in the coordinator's tally rather than in an individual signer's state machine.

### Likelihood Explanation
No majority collusion is required: this can be triggered by ordinary, permitted behavior of a small number of signers (or gossip-observed messages) that reject a proposal for a transient/reconsiderable reason and then correctly flip to Accept once the transient condition clears — a scenario the signer's own re-evaluation logic (`should_reevaluate_reject_reason`) exists specifically to handle. No auth token, private key, or majority weight beyond the signers whose own messages are involved is needed; the flaw is purely in how the coordinator aggregates already-valid, already-authenticated messages.

### Recommendation
When applying a `BlockResponse::Accepted` for a `slot_id` that is already present in `responded_signers` as a rejection (or vice versa), first subtract that signer's weight from `total_weight_rejected` (or `total_weight_approved`) before adding it to the new bucket — mirroring the reconciliation `SignerDb::add_block_signature` already performs by deleting the corresponding `block_rejection_signer_addrs` row before inserting a new signature. Alternately, maintain a single per-slot "current vote" map instead of two independently-incremented saturating counters, and recompute `total_weight_approved`/`total_weight_rejected` as sums over that map's current state.

### Proof of Concept
1. Coordinator tracks a block proposal with `total_weight = 100`, `weight_threshold = 70` (so blocking minority weight is `30`).
2. Signers A (weight 15), B (weight 15) send `BlockResponse::Rejected` early (e.g., due to `ConnectivityIssues`/`NoSortitionView` before validation settles) → `total_weight_rejected = 30` [2](#0-1) . This alone does not yet cross `total_weight_rejected + weight_threshold > total_weight` (30+70=100, not >100).
3. One more signer C (weight 1) rejects for the same transient reason → `total_weight_rejected = 31`, crossing `31 + 70 > 100` → but suppose the coordinator hasn't polled yet.
4. Signers A and B re-evaluate (their reject reason is reconsiderable) and now send `BlockResponse::Accepted` for the same block. Because the Accepted branch's guard (`gathered_signatures.contains_key`) is independent of `responded_signers`, their weight is added to `total_weight_approved` (`+30`) [1](#0-0)  while their earlier contribution to `total_weight_rejected` (`30`) is never removed.
5. `total_weight_rejected` remains at 31 (stale, includes A+B's superseded rejections), so the very next poll in `get_block_status` still satisfies `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (31+70=101>100) and returns `Err(SignersRejected)` [5](#0-4) , even though the current, correct opinion tally (excluding stale votes) has only signer C (weight 1) rejecting and A+B+others potentially reaching the 70% acceptance threshold.
