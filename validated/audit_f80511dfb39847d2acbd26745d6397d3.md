This confirms the vulnerability: `MessageId` is a fully user-supplied field (`m.Body.MessageId`, JSON field `message_id`), and only its length/suffix are validated in `Message.Validate()`. It is the sender's ECDSA signature (`Sign`/`ExtractSigner`) that produces `m.Body.Sender`, but `Sender` is never mixed into the `MessageId`.

### Title
In-flight web-API-trigger callback map keyed only by attacker-controlled `MessageId`, allowing cross-sender callback hijack/eviction - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `capabilities` gateway handler's `savedCallbacks` map, used to correlate DON node responses back to the originating HTTP user for `MethodWebAPITrigger`, is keyed solely by `msg.Body.MessageId` in `HandleLegacyUserMessage` [1](#0-0) , unlike the sibling `common.RequestCache` abstraction used by `vault`/`confidentialrelay` handlers, which explicitly namespaces entries by `globalId{sender, id}` [2](#0-1) . Because `MessageId` is fully attacker-chosen and only length/suffix-validated in `Message.Validate()` [3](#0-2) , any signed client can submit a request whose `MessageId` collides with a victim's currently in-flight `MessageId`, silently overwriting the victim's callback entry.

### Finding Description
1. A user submits a `web_api_trigger` request through `HandleLegacyUserMessage`. The gateway validates signature/timestamp/method but does not enforce any relationship between `MessageId` and `Sender`, and stores the callback keyed only by `MessageId`: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` [1](#0-0) .
2. An attacker (any address able to sign a gateway message, per `Message.Sign`/`SignKS` [4](#0-3) ) crafts and submits their own `web_api_trigger` message using the exact same `MessageId` as a currently pending victim request. Because the signature only covers `MessageId`, `Method`, `DonId`, `Receiver`, `Payload` (not any uniqueness/nonce tied to sender+time server-side), this is trivial to do once the attacker learns or guesses the victim's in-flight `MessageId` (e.g., by triggering their own request to the same DON/receiver and observing timing, or if `MessageId`s are predictable/sequential from a caller's own client).
3. The attacker's call overwrites `h.savedCallbacks[messageId]`, replacing the victim's `Callback` with the attacker's own.
4. When the DON node subsequently responds to the *victim's* forwarded request (correlated purely by `msg.Body.MessageId` in `handleWebAPITriggerMessage` [5](#0-4) ), the gateway looks up `h.savedCallbacks[msg.Body.MessageId]`, finds the attacker's callback (since it overwrote the victim's), deletes the entry, and delivers the victim's response — potentially containing decrypted secrets/results intended for the victim — to the attacker's HTTP connection.
5. No check ties the found `savedCb` back to the sender of the *node's* response message vs. the sender who registered the callback, so cross-sender confusion is not detected or blocked anywhere in this path.

This differs from the `common.RequestCache` pattern deliberately used elsewhere in the same package tree specifically to prevent this class of bug, confirming the capabilities handler's `savedCallbacks` map is the unguarded outlier.

### Impact Explanation
An attacker can cause another user's `web_api_trigger` response — which can include secret/decrypted payloads depending on the capability behind the DON (e.g., vault/DKG-style secret retrieval flows routed through this generic trigger path) — to be delivered to the attacker's own callback instead of the legitimate requester's. This is a cross-user response confusion / unauthorized disclosure vulnerability, matching a "server credential theft" / secret-disclosure class impact if the underlying capability payload contains sensitive data. At minimum it is a reliable denial-of-service/response-hijack against arbitrary users of the shared DON gateway trigger endpoint.

### Likelihood Explanation
The attacker needs only the ability to sign and submit gateway messages (any EOA capable of using the public gateway client — explicitly the assumed unprivileged threat actor). The only obstacle is learning/guessing the victim's exact `MessageId` string before the DON response returns (a ~2 minute window per `defaultCallbackMaxAgeSec`/`CallbackMaxAgeSec`, and message TTL is also gated by `MaxAllowedMessageAgeSec`). If client libraries generate `MessageId`s predictably (e.g., counters, timestamps, or derived from public request content) this is straightforward to win the race repeatably; the vulnerability is a real, reproducible logic bug in the handler regardless of exact `MessageId` generation strategy on the client side, since the server performs zero sender-based isolation of the map key.

### Recommendation
Key `savedCallbacks` by a composite `(Sender, MessageId)` value, mirroring `common.RequestCache`'s `globalId{sender, id}` pattern, in both the write path (`HandleLegacyUserMessage`) and the lookup path (`handleWebAPITriggerMessage`), which requires correlating the DON node's response with the original sender who requested it (e.g., by embedding/tracking the requester's address alongside the outbound `SendToNode` calls, or storing the sender when saving the callback and matching against it when the DON's response is later validated). Consider migrating the `capabilities` handler to reuse `common.RequestCache[T]` entirely instead of maintaining a separate ad hoc `savedCallbacks` map.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct two signed `api.Message` values, `msgVictim` and `msgAttacker`, from two different ECDSA keys, both with `Method = MethodWebAPITrigger` and identical `Body.MessageId = "collide-id"`.
2. Call `handler.HandleLegacyUserMessage(ctx, msgVictim, victimCallback)` — assert it stores callback under `"collide-id"`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgAttacker, attackerCallback)` with the same ID — assert (post-fix) this either fails/collides safely, but pre-fix silently overwrites `h.savedCallbacks["collide-id"]`.
4. Simulate a DON node response for the *victim's* forwarded request (`msg.Body.MessageId = "collide-id"`, `Sender = nodeAddr`) via `handler.HandleNodeMessage`.
5. Assert (fast validation / cross-sender isolation invariant): `victimCallback.SendResponse` is called with the correct data and `attackerCallback.SendResponse` is never called. On the current code, the test fails because `attackerCallback.SendResponse` receives the victim's response data instead.
