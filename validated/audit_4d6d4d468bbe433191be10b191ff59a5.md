### Title
Post-finalization instant-withdraw receipts are classified into the defaulted epoch and paid from a fixed recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The MinIO JWT algorithm-confusion bug class maps to claim-type confusion: a credential (here, a withdraw receipt) is validated/paid under a verification regime it was never issued under. `IdleCreditVault.requestInstantWithdraw` has no `defaultRecoveryFinalized` branch, unlike `requestWithdraw`, which forces post-default requests into the separately-priced `postDefaultRequests` bucket. An attacker who files an instant-withdraw request after `finalizeDefault` has it recorded in `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, which equals `defaultRecoveryEpoch`, so `claimInstantWithdrawRequest` pays it from `defaultRecoveryReserve` — a pot sized only for claims that existed at finalization.

### Finding Description
`requestWithdraw` contains an explicit post-default path: if `defaultRecoveryFinalized` is set, the caller must have no open requests and the receipt is routed to `postDefaultRequests[_user]`, paid 1:1 because the haircut was already applied to the virtual price [1](#0-0) .

`requestInstantWithdraw` contains no such branch. After `_ensureDefaultRecoveryInitialized`, it unconditionally writes `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` with `currentEpoch = epochNumber` and mints the receipt to the user [2](#0-1) .

On claim, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` [3](#0-2) . That function reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of `defaultRecoveryReserve` [4](#0-3) . Since `defaultRecoveryEpoch` is set to `epochNumber` at finalization and `epochNumber` does not advance after default, a receipt created after the reserve was fixed lands in exactly the bucket that spends it.

`defaultRecoveryReserve` is funded once by the manager's `recovered` contribution in `finalizeDefault`, sized to `defaultPendingClaimBasis` (pre-finalization pending claims). Claims consume it via `defaultRecoveryReserve -= _amount` [5](#0-4) . The funded-claim fallback cannot rescue other claimants because `_transferFundedClaim` explicitly refuses to touch the reserve [6](#0-5) .

### Impact Explanation
The attacker deposits/redeems normally to obtain tranche tokens before or around default, waits for `finalizeDefault`, then calls `requestInstantWithdraw` on the CDO. The receipt is minted at the already-haircut virtual price, yet `_claimDefaultedInstantWithdrawRequest` pays `amount * defaultRecoveryPrice` from a reserve that never accounted for this claim. Each token the attacker extracts is a token of recovery owed to legitimate defaulted-epoch claimants; once the reserve underflows, their claims revert permanently (`defaultRecoveryReserve -= _amount` underflows), converting the theft into permanent freezing of the remaining recovery. Quantified loss is up to the attacker's instant request size times `defaultRecoveryPrice`, bounded only by the reserve.

### Likelihood Explanation
Requirements: instant-withdraw mode enabled on the pool, a finalized default, and the CDO path `requestInstantWithdraw` remaining callable while `defaulted()` — the strategy itself imposes no default check, so exploitability hinges on CDO-side gating, which the vault code does not enforce (the vault clearly assumed instant requests are impossible post-finalization, mirroring the symmetric guard added to `requestWithdraw`). The attacker needs only tranche tokens (any KYC-passing lender), no privileged role, and a single transaction after `finalizeDefault`. If the CDO does gate defaulted requests, the issue degrades to defense-in-depth, but the vault-level classification asymmetry is still a latent vulnerability for any CDO variant that permits it (e.g., prefunded variants where instant requests bypass `allowInstantWithdraw` timing checks).

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert outright or route the haircut-adjusted amount into `postDefaultRequests` (funded from free balance, not `defaultRecoveryReserve`), and reject the request if the user has open receipts. Additionally, in `_claimDefaultedInstantWithdrawRequest`, only clear receipts whose request was recorded before finalization (e.g., snapshot a per-epoch closed flag or compare against a stored `defaultFinalizedAtEpoch` bound), and consider rejecting `requestInstantWithdraw` whenever `defaulted()` is true.

### Proof of Concept
Foundry fork sketch (instant-withdraw enabled pool, e.g. via `setInstantWithdrawParams`):

```solidity
// Setup: AA deposit by attacker and victim; epoch runs; borrower defaults.
// Manager calls finalizeDefault(recovered, manager) where recovered is sized to
// defaultPendingClaimBasis() (victim's pending claims only).
// Post-condition: defaultRecoveryFinalized == true, defaultRecoveryEpoch == epochNumber.

// Attacker holds AA tranches (bought pre-default or already held).
uint256 attackerTranche = AAtranche.balanceOf(attacker);

// No defaulted() / defaultRecoveryFinalized guard inside IdleCreditVault.requestInstantWithdraw.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackerTranche, address(AAtranche)); // or requestWithdraw instant path

// Receipt lands in instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch].
uint256 reservePre = strategy.defaultRecoveryReserve();

vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();

// Attacker receives amount * defaultRecoveryPrice paid out of the fixed reserve.
assertLt(strategy.defaultRecoveryReserve(), reservePre);

// Victim's legitimate defaulted-epoch claim now reverts (reserve underflow) or pays less.
vm.expectRevert();
vm.prank(victim);
cdoEpoch.claimInstantWithdrawRequest();
```

Caveat: I verified the strategy-side classification gap and reserve accounting directly in `IdleCreditVault.sol` (lines 356–374, 380–393, 842–856, 897–917), but within the iteration budget I could not fully confirm the CDO-side gating (`IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` behavior while `defaulted()`). If the CDO already blocks instant requests after default, this remains a missing defense-in-depth guard rather than a live exploit; the vault's own code assumes but does not enforce the invariant.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
