### Title
Deactivated/removed LDAP users retain full transaction ability via existing sessions and API tokens until the next background sync - (File: core/sessions/ldapauth/ldap.go / core/sessions/ldapauth/sync.go)

### Summary
When using the LDAP `AuthenticationProvider`, revoking a user's access upstream (removing them from an authorized LDAP group, or marking them inactive) is analogous to "blacklisting" that account. However, the request-time authorization checks (`AuthorizedUserWithSession` and `FindUserByAPIToken`) never re-validate the user's current upstream group membership or active status — they trust a locally cached `ldap_sessions` / `ldap_user_api_tokens` row until it naturally expires or until a separate, interval-based background sync (`LDAPServerStateSyncer.Work`) runs and purges it. This mirrors the Telcoin bug class where an administratively "blacklisted" actor can continue to transact because the enforcement point never re-checks the ban at request time.

### Finding Description
The per-request authorization paths only check local, cached state: [1](#0-0) 

`AuthorizedUserWithSession` looks up `user_email`, `user_role`, and only validates the session against the *local* `SessionTimeout` — there is no call back to LDAP or to `validateUsersActive` to check whether the user is still a member of an authorized group or still marked active.

Similarly, `FindUserByAPIToken` only checks the cached `ldap_user_api_tokens` row and expiry: [2](#0-1) 

The only mechanism that removes access for a deactivated/removed user is the separate `LDAPServerStateSyncer.Work` background job, which:
1. Fetches the current upstream group membership and active-flag state.
2. Builds `upstreamUserStateMap`, removing users who are inactive.
3. Purges `ldap_sessions`/`ldap_user_api_tokens` rows for emails no longer present in that map. [3](#0-2) 

This sync is explicitly interval- and rate-limit-gated (`UpstreamSyncInterval`, `UpstreamSyncRateLimit`), and if `UpstreamSyncInterval` is non-zero it only runs on a ticker in a background goroutine, not synchronously with each authenticated request: [4](#0-3) 

Consequently, between the moment an operator revokes a user (removes their LDAP group membership, disables their account, or sets `ActiveAttribute` to false) and the next sync tick (or the configured rate limit interval), the revoked user's existing session cookie and/or API token remain fully valid and can be used to call any node API endpoint permitted by their previously cached role — including job/run creation (`RequiresRunRole`), edit-level actions (`RequiresEditRole`), or even admin actions if they held that role, exactly as in `core/web/router.go`'s route wiring: [5](#0-4) 

### Impact Explanation
This is a failure of a manually/administratively enforced access-revocation control, directly analogous to the blacklist bypass in the referenced report. A node operator who intends to immediately cut off a compromised or malicious user's node-API access (e.g., a departing employee, a compromised account, or a user under active exploitation) cannot actually do so instantly when using the LDAP authentication provider — the user retains full session/API-token-based access to run jobs, view secrets/configuration, or (if privileged) perform admin actions until the periodic sync removes the cached row. The severity depends on the configured `UpstreamSyncInterval`/`UpstreamSyncRateLimit`, which can be set to a large duration, extending the exposure window.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the node to be configured for LDAP authentication (`LDAPAuth`), and (b) an administrator to revoke a user upstream expecting immediate effect, while the user (or an attacker holding their credentials/session/API token) continues issuing requests. This is a realistic operational scenario for enterprise deployments using LDAP, and does not require any malicious node/peer/network-layer behavior — it is purely an unprivileged client continuing to use a previously-issued, still "locally valid" session/token via the internet-facing node API.

### Recommendation
- Re-validate the user's upstream active/group-membership status synchronously on each `AuthorizedUserWithSession` and `FindUserByAPIToken` call (or at minimum on a much shorter cache TTL than the full sync interval), rather than relying solely on the periodic `LDAPServerStateSyncer.Work` job.
- Alternatively, provide an explicit "revoke now" admin action that synchronously purges `ldap_sessions`/`ldap_user_api_tokens` for a given user, decoupled from the interval-based `UpstreamSyncInterval`/`UpstreamSyncRateLimit` timer.
- Document/enforce a maximum safe value for `UpstreamSyncInterval` so operators are aware of the real-world revocation delay.

### Proof of Concept
1. Configure the node with `LDAPAuth` and a non-trivial `UpstreamSyncInterval` (e.g., 15 minutes) as permitted by config.
2. User `alice@example.com` is a member of the Run group; log in to create a valid session (`ldap_sessions` row) and/or generate an API token (`ldap_user_api_tokens` row).
3. Administrator removes `alice` from the LDAP Run group (or flips her `ActiveAttribute` to inactive) to immediately revoke access.
4. Before the next `LDAPServerStateSyncer.Work` tick, `alice` continues sending authenticated requests using her existing session cookie or API token headers.
5. `AuthorizedUserWithSession`/`FindUserByAPIToken` return her cached role from `ldap_sessions`/`ldap_user_api_tokens` without re-checking upstream state, and requests to run-role-gated endpoints (e.g., `POST /v2/jobs/:ID/runs`) succeed despite the revocation.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field. The state of the upstream LDAP server
// is polled and synced at the defined interval via a SleeperTask
func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

func (l *LDAPServerStateSyncer) Close() error {
	close(l.stopCh)
	<-l.done
	return nil
}

func (l *LDAPServerStateSyncer) run() {
	defer close(l.done)
	ctx, cancel := l.stopCh.NewCtx()
	defer cancel()
	ticker := time.NewTicker(l.config.UpstreamSyncInterval().Duration())
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			l.Work(ctx)
		}
	}
}

func (l *LDAPServerStateSyncer) Work(ctx context.Context) {
	// Purge expired ldap_sessions and ldap_user_api_tokens
	recordCreationStaleThreshold := l.config.SessionTimeout().Before(time.Now())
	err := l.deleteStaleSessions(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire local LDAP sessions: ", err)
	}
	recordCreationStaleThreshold = l.config.UserAPITokenDuration().Before(time.Now())
	err = l.deleteStaleAPITokens(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire user API tokens: ", err)
	}

	// Optional rate limiting check to limit the amount of upstream LDAP server queries performed
	if !l.config.UpstreamSyncRateLimit().IsInstant() {
		if !time.Now().After(l.nextSyncTime) {
			return
		}

		// Enough time has elapsed to sync again, store the time for when next sync is allowed and begin sync
		l.nextSyncTime = time.Now().Add(l.config.UpstreamSyncRateLimit().Duration())
	}
