### Title
Single getTransaction call for a signature triggers full-block protobuf decode regardless of block size - ([File: storage-bigtable/src/lib.rs])

### Summary
`LedgerStorage::get_confirmed_transaction` resolves a signature to `(slot, index)` via a cheap single-row lookup in `TX_TABLE_NAME`, but then unconditionally fetches and fully decodes the *entire* block at that slot via `get_confirmed_block(slot)` before indexing into `block.transactions` for the single requested transaction. This means the cost of a single-transaction `getTransaction` RPC call scales with the size of the whole block that contains it, not with the size of the requested transaction.

### Finding Description
The RPC entrypoint for `getTransaction` (in `rpc/src/rpc.rs`) falls back to the bigtable path via `bigtable_ledger_storage`, which ultimately calls `LedgerStorage::get_confirmed_transaction`: [1](#0-0) 

The implementation:
1. Looks up `TransactionInfo { slot, index, .. }` from the `tx` table by signature — an O(1)/cheap single-row fetch.
2. Calls `self.get_confirmed_block(slot)`, which fetches and fully protobuf/bincode-decodes the **entire block** for that slot: [2](#0-1) 
3. Only after materializing the entire `ConfirmedBlock` (all transactions, all metadata, all instructions/accounts referenced in every transaction of the block) does it index with `.nth(index as usize)` to extract the one transaction requested.

There is no fast path that reads only the target transaction's bytes out of BigTable or decodes only a slice of the stored protobuf block; the full row (the entire serialized block) must be fetched from BigTable and fully deserialized before the single transaction is sliced out. `get_confirmed_signatures_for_address`/`get_confirmed_transactions` and even `ledger-tool`'s `transaction_history` explicitly note this behavior as a deliberate trade-off ("fetch the entire block and keep it around... reduce BigTable query traffic"), confirming that block-granularity fetching is the designed access pattern rather than an oversight limited to one function: [3](#0-2) 

No parameter-limit, commitment, or length-check guard bounds the size of the block being decoded per single-transaction request; the guard checks earlier in the RPC path (`check_transaction_history_enabled`, commitment resolution) only gate whether bigtable is queried at all, not how much data is materialized once it is.

An attacker who can get a transaction included in a very large block (maximal instructions/accounts, up to `max_entry_bytes_per_slot`, e.g. `DEFAULT_MAX_ENTRY_BYTES_PER_SLOT = 20 MiB` or the slot-time-scaled variants such as 18.35 MiB/15.7 MiB/13.1 MiB/10.5 MiB depending on active slot-time feature) can cause any single `getTransaction(signature)` lookup for that transaction to force decode of the full multi-megabyte block: [4](#0-3) 

### Impact Explanation
This is an unbounded-cost-per-single-request issue: one unprivileged JSON-RPC call (`getTransaction`) can force the RPC/bigtable-storage backend to fetch and fully protobuf-decode up to the maximum on-chain block size (multi-megabyte) rather than doing work proportional to the single transaction requested. Repeated at the maximum permitted rate (one call per `CLUSTER_SLOT_TIME_TARGET / 2`), this creates disproportionate CPU/memory/network cost on the RPC node compared to a normal single-transaction fetch, matching the "unbounded cost for a single low-rate call" impact category in scope.

### Likelihood Explanation
Feasible and fully attacker-controlled: the attacker only needs `bigtable_ledger_storage` enabled on the target RPC node (a common production configuration) and needs their own transaction to land in a large block, which they can help construct (e.g., issuing/paying for large transactions themselves in the same slot, or simply picking a naturally large historical block on cluster that already contains many packed transactions and issuing `getTransaction` for any signature in it — no attacker cooperation with block producers is even required since any historically large block works). The exploit requires no elevated privileges and repeats deterministically every time `getTransaction` is called for a signature in a large block.

### Recommendation
Avoid materializing the whole block for a single-transaction lookup:
- Store per-transaction data (or an index enabling partial decode) separately from the full block row so `get_confirmed_transaction` can retrieve/decode only the target transaction's bytes.
- Alternatively, cache decoded blocks with a size-aware LRU and impose a hard ceiling on decode cost per request, rejecting/streaming instead of fully materializing oversized blocks in memory for a single-transaction query.
- Add BigTable column-level fetch qualifiers or split large blocks into transaction-addressable cells to make the underlying read itself proportional to one transaction, not the entire block.

    let maximal_sig = upload_block_with_n_transactions(&ledger_storage, maximal_slot, MAX_TXS_PER_BLOCK).await;

    let (t0, mem0) = time_and_peak_mem(|| async {
        ledger_storage.get_confirmed_transaction(&minimal_sig).await.unwrap()
    }).await;

    let (t1, mem1) = time_and_peak_mem(|| async {
        ledger_storage.get_confirmed_transaction(&maximal_sig).await.unwrap()
    }).await;

    // Expected (bug present): t1 >> t0 and mem1 >> mem0, scaling with block size.
    // Desired invariant (fix): t1 and mem1 bounded within a small constant factor of t0/mem0,
    // independent of block size, e.g.:
    assert!(t1 < t0 * 3, "single-tx fetch cost should not scale with block size");
    assert!(mem1 < mem0 * 3, "single-tx fetch memory should not scale with block size");

    /// Fetch a confirmed transaction
    pub async fn get_confirmed_transaction(
        &self,
        signature: &Signature,
    ) -> Result<Option<ConfirmedTransactionWithStatusMeta>> {
        trace!("LedgerStorage::get_confirmed_transaction request received: {signature:?}");
        self.stats.increment_num_tx_table_reads();
        let mut bigtable = self.connection.client();

        // Figure out which block the transaction is located in
        let TransactionInfo { slot, index, .. } = bigtable
            .get_bincode_cell(TX_TABLE_NAME, signature.to_string())
            .await
            .map_err(|err| match err {
                bigtable::Error::RowNotFound => Error::SignatureNotFound(*signature),
                _ => err.into(),
            })?;

        // Load the block and return the transaction
        let block = self.get_confirmed_block(slot).await?;
        match block.transactions.into_iter().nth(index as usize) {
            None => {
                // report this somewhere actionable?
                warn!("Transaction info for {signature} is corrupt");
                Ok(None)
            }
            Some(tx_with_meta) => {
                if tx_with_meta.transaction_signature() != signature {
                    warn!("Transaction info or confirmed block for {signature} is corrupt");
                    Ok(None)
                } else {
                    Ok(Some(ConfirmedTransactionWithStatusMeta {
                        slot,
                        tx_with_meta,
                        block_time: block.block_time,
                        index,
                    }))
                }
            }
        }
    }
