### Title
Zip extraction path traversal allows `os.Lchown` (and file writes) outside the job workspace - (File: helpers/archives/zip_extract.go, helpers/archives/zip_extra_unix.go)

### Summary
`ExtractZipArchive`/`extractZipFile` in `helpers/archives/zip_extract.go` use `file.Name` from the `zip.File` header directly, with no validation that it stays within the extraction root, before calling `os.MkdirAll`, `os.OpenFile`/`os.Symlink`, and later `os.Lchown` in `processZipUIDGidField` (`helpers/archives/zip_extra_unix.go`). If a `zip.File.Name` contains `../` traversal segments, both file creation and the subsequent `os.Lchown` will operate on a path outside the intended cache/artifact/build directory.

### Finding Description
`extractZipFile` computes the parent directory with `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and then creates/writes/symlinks at `file.Name` verbatim [1](#0-0) . `ExtractZipArchive` then iterates the same files and calls `lchmod(file.Name, ...)` and `processZipExtra(&file.FileHeader)` [2](#0-1) . `processZipExtra` parses the zip "Info-ZIP New Unix Extra Field" (`ZipUIDGidFieldType = 0x7875`) and, when present, calls `processZipUIDGidField(data, file)` [3](#0-2) , which does `os.Lchown(file.Name, int(ugField.UID), int(ugField.Gid))` [4](#0-3) . None of these functions call `filepath.Clean`, reject `..` segments, or verify the resolved path stays under the extraction directory (`ziplegacy` extractor's `dir` field, `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`, is never even passed to `archives.ExtractZipArchive` — it's ignored) [5](#0-4) . So a crafted zip entry named e.g. `../../shared-cache/lib/foo` reaches `extractZipFile` and `os.Lchown` unmodified, i.e. a classic "Zip Slip" plus an additional chown-based corruption primitive.

The unresolved question for this specific scenario is *how* an unprivileged pipeline author gets such a raw, hand-crafted zip byte stream into the extraction path reachable via `CacheExtractorCommand.Execute`. Cache/artifact zip archives consumed by `CacheExtractorCommand` are normally produced by GitLab Runner's own `CacheArchiverCommand` (`helpers/archives/zip_create.go`), which walks the job's own `cache:paths`/`artifacts:paths` on disk and writes relative filenames computed from that walk — not attacker-supplied raw zip bytes. To inject a truly adversarial `file.Name` (with literal `../` in the zip central directory entry, independent of any real filesystem path), the attacker would need to control the raw archive bytes fetched by `CacheExtractorCommand` — e.g. by controlling/uploading directly to the cache storage backend (S3/GCS bucket, self-hosted cache server) bypassing the runner's own archiver, or through a compromised/malicious shared cache server. That is outside the "unprivileged pipeline author only, via CI-accepted inputs" threat model unless the runner's cache/artifact storage endpoint itself is reachable by ordinary users independent of GitLab's authorization (not established here).

### Impact Explanation
If reached, the impact is exactly as described: `os.Lchown`/`os.MkdirAll`/`os.OpenFile` on `../../shared-cache/lib` would corrupt ownership/contents of a path outside the intended job/cache root, potentially a shared runner directory used by other projects' jobs, causing persistent, cross-job disruption that survives the triggering job's completion or cancellation (the corruption is on-disk state, not tied to the process).

### Likelihood Explanation
The code-level bug (no path sanitization in `extractZipFile`/`processZipExtra`/`processZipUIDGidField`) is real and confirmed in the current code. However, the *reachability* claimed in the question — an ordinary pipeline author supplying a raw crafted zip with malicious entry names via a normal "job cache/artifact" upload — is not substantiated by the code I reviewed: `CacheArchiverCommand` builds the zip from real on-disk paths under the runner's control, so it is not obvious an unprivileged user can inject an arbitrary `zip.File.Name` string (as opposed to real filesystem structure, which the OS itself would refuse to create with `..` as a literal path component). Without evidence that the cache/artifact upload flow accepts attacker-supplied raw archive bytes that bypass the runner's own archiver, the "unprivileged pipeline author" precondition for this exact exploit chain is unproven from the available code.

### Recommendation
Regardless of the exact reachability question, harden `extractZipFile` in `helpers/archives/zip_extract.go` to reject or clean any `file.Name` that, after `filepath.Clean`, is absolute or contains a `..` segment escaping the destination root (standard Zip Slip mitigation: compute `target := filepath.Join(destRoot, file.Name)` and verify `strings.HasPrefix(target, destRoot+string(os.PathSeparator))`). Apply the same root-confinement check before `processZipExtra`/`processZipUIDGidField` calls `os.Lchown`, and thread the actual extraction root (`dir` in `ziplegacy.extractor`, currently unused) through `ExtractZipArchive` so it can enforce this boundary.

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go`:
1. Build an in-memory `zip.Writer`, add a `zip.FileHeader` with `Name: "../outside/evil.txt"` and craft an `Extra` field of type `ZipUIDGidFieldType` (`0x7875`) with `Version=1, UIDSize=4, UID=<attacker-chosen uid>, GIDSize=4, GID=<attacker-chosen gid>`.
2. In a temp dir, `os.Mkdir` a subdirectory `extract-root`, `os.Chdir` into it (mirroring how extraction currently ignores the destination root), and call `archives.ExtractZipArchive(&zr.Reader)`.
3. Assert `../outside/evil.txt` (i.e., a sibling of `extract-root`) was created, and assert (as root, or via `os.Lstat` + checking `Sys().(*syscall.Stat_t).Uid/Gid`) that its ownership matches the attacker-supplied UID/GID rather than the process's own uid/gid — proving `os.Lchown` executed outside the intended root.
This test would need to run as root (or in a container/CI runner with `CAP_CHOWN`) since `os.Lchown` to an arbitrary UID/GID normally requires privilege; alternatively assert only that the *file* was created outside the root (sufficient to prove the traversal) and separately unit-test `processZipUIDGidField` in isolation with a `file.Name` containing `..` to show it is passed through to `os.Lchown` without any path-confinement check.

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}

func ExtractZipArchive(archive *zip.Reader) error {
	tracker := newPathErrorTracker()

	for _, file := range archive.File {
		if err := errorIfGitDirectory(file.Name); tracker.actionable(err) {
			printGitArchiveWarning("extract")
		}

		if err := extractZipFile(file); tracker.actionable(err) {
			logrus.Warningf("%s: %s (suppressing repeats)", file.Name, err)
		}
	}

	for _, file := range archive.File {
		if err := lchmod(file.Name, file.Mode()); tracker.actionable(err) {
			logrus.Warningf("%s: %s (suppressing repeats)", file.Name, err)
		}

		// Process zip metadata
		if err := processZipExtra(&file.FileHeader); tracker.actionable(err) {
			logrus.Warningf("%s: %s (suppressing repeats)", file.Name, err)
		}
	}

	return nil
}

func processZipExtra(file *zip.FileHeader) error {
	if len(file.Extra) == 0 {
		return nil
	}

	r := bytes.NewReader(file.Extra)
	for {
		field, data, err := readZipExtraField(r)
		if err == io.EOF {
			break
		} else if err != nil {
			return err
		}

		switch field.Type {
		case ZipUIDGidFieldType:
			err = processZipUIDGidField(data, file)
		case ZipTimestampFieldType:
			err = processZipTimestampField(data, file)
		}
		if err != nil {
			return err
		}
	}

	return nil
}
```

func processZipUIDGidField(data []byte, file *zip.FileHeader) error {
	var ugField ZipUIDGidField
	err := binary.Read(bytes.NewReader(data), binary.LittleEndian, &ugField)
	if err != nil {
		return err
	}

	if !(ugField.Version == 1 && ugField.UIDSize == 4 && ugField.GIDSize == 4) {
		return errors.New("uid/gid data not supported")
	}

	return os.Lchown(file.Name, int(ugField.UID), int(ugField.Gid))
```
