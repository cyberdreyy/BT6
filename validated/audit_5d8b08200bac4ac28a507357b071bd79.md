Confirmed: `createDstEscrow` (contracts/BaseEscrowFactory.sol:165-185) accepts `dstImmutables` fully supplied by `msg.sender`, including the arbitrary `parameters` bytes (encoding `protocolFeeAmount`, `integratorFeeAmount`) that are only decoded later inside `EscrowDst._withdraw`. No check in `createDstEscrow` validates that `protocolFeeAmount + integratorFeeAmount < immutables.amount`, unlike the analogous source-side check `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();` in `_postInteraction` (contracts/BaseEscrowFactory.sol:92), which only guards the emitted `SrcEscrowCreated` event data, not the actual dst escrow deployment.

### Title
Unvalidated fee parameters in `createDstEscrow` cause guaranteed underflow revert in `EscrowDst._withdraw`, permanently freezing/redirecting maker funds - (File: contracts/BaseEscrowFactory.sol, contracts/EscrowDst.sol)

### Summary
`EscrowDst._withdraw` computes `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` [1](#0-0)  without any bound on `integratorFeeAmount`/`protocolFeeAmount` relative to `immutables.amount`. These fee values come from the arbitrary `parameters` bytes field of `Immutables`, decoded via `ImmutablesLib.integratorFeeAmountCd`/`protocolFeeAmountCd` [2](#0-1) . Unlike the source-chain path, where `_postInteraction` enforces `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();` [3](#0-2) , the destination-chain deployment path `createDstEscrow` performs no such validation on the caller-supplied `dstImmutables.parameters` [4](#0-3) .

### Finding Description
`createDstEscrow` is a public, unprivileged entry point — any caller (the taker/resolver funding the destination escrow) supplies the full `Immutables` struct, including the opaque `parameters` bytes that later decode into `protocolFeeAmount` and `integratorFeeAmount`. The function only validates that `msg.value`/token transfer matches `dstImmutables.amount` and `safetyDeposit`; it never checks that `protocolFeeAmount + integratorFeeAmount < amount`. Because the fee-sum check present on the source path (`InvalidFeeAmounts`) only fires inside `_postInteraction`, which builds a *separate*, independently-encoded `parameters` blob for the `SrcEscrowCreated` event's `DstImmutablesComplement` — it has no binding effect on what is actually passed to `createDstEscrow`. A taker can call `createDstEscrow` with legitimate `amount`/`safetyDeposit` funding (satisfying the balance checks) but with `parameters` encoding fees whose sum is `>= amount`. Every subsequent call to `withdraw`/`publicWithdraw` on that `EscrowDst` clone will underflow at `immutables.amount - integratorFeeAmount - protocolFeeAmount` and revert unconditionally, regardless of whether the correct secret is supplied.

### Impact Explanation
Since `withdraw`/`publicWithdraw` can never succeed, the maker can never receive their destination-chain tokens through the intended atomic-swap flow. The escrow can only be resolved via `cancel`, which returns the full `immutables.amount` and safety deposit back to the taker who created the escrow [5](#0-4) . If the taker has already (or subsequently) withdrawn the corresponding source-chain funds using the revealed secret via the independent `EscrowSrc.withdraw` flow, the maker's source funds are transferred to the taker while the taker reclaims their own destination-chain deposit in full — resulting in the maker never receiving the destination assets they were owed. This fits the Critical bounty tier (theft of user funds) as well as, at minimum, the High tier (temporary/permanent freezing of funds during the live swap lifecycle), triggered entirely by an unprivileged caller through the "destination escrow creation" entry point.

### Likelihood Explanation
This requires no privileged role, no reentrancy, and no race condition — it is a simple malformed-input call to a public factory function (`createDstEscrow`) available to any address funding a destination escrow. The only precondition is that the maker/relayer's off-chain verification of the destination escrow's `parameters` field is not exhaustive enough to reject this specific configuration before the secret is disclosed, which is plausible since the protocol's on-chain contracts provide no such guard themselves.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`: revert if `ImmutablesLib.protocolFeeAmount(immutables) + ImmutablesLib.integratorFeeAmount(immutables) >= immutables.amount` (handling the case where `parameters` is empty as "no fee") before deploying the clone, so a malicious/malformed destination escrow can never be created in a state that guarantees `withdraw` will underflow.

### Proof of Concept
1. Taker calls `EscrowFactory.createDstEscrow{value: amount + safetyDeposit}(dstImmutables, srcCancellationTimestamp)` where `dstImmutables.amount = 100` and `dstImmutables.parameters = abi.encode(protocolFeeAmount = 60, integratorFeeAmount = 50, protocolFeeRecipient, integratorFeeRecipient)` (sum 110 > 100). The call succeeds because `createDstEscrow` only checks `msg.value == nativeAmount` and never inspects `parameters` [4](#0-3) .
2. Maker/anyone later calls `withdraw(secret, dstImmutables)` with the correct secret during the withdrawal window; `_withdraw` reverts on `immutables.amount - integratorFeeAmount - protocolFeeAmount` (100 - 50 - 60 underflows) [6](#0-5) .
3. After the cancellation timelock, the taker calls `cancel(dstImmutables)`, reclaiming the full `amount` (100) and `safetyDeposit` back to themselves [5](#0-4) , while having already (or still being able to) withdraw the maker's source-chain funds via `EscrowSrc.withdraw` using the same secret.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
