### Title
Missing `oracle_max_age` lower-bound validation in `StakedSettings`/`lending_pool_add_bank_permissionless` allows creation of staked-collateral banks with `oracle_max_age = 0` - ([File: programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs])

### Summary
`BankConfigImpl::validate()` enforces `oracle_max_age >= ORACLE_MIN_AGE` (10 seconds) whenever a bank config is validated [1](#0-0) . However, `StakedSettingsImpl::validate()`, which is the validation routine called by `init_staked_settings` and `edit_staked_settings`, never checks `oracle_max_age` at all [2](#0-1) . The permissionless instruction `lending_pool_add_bank_permissionless` copies `settings.oracle_max_age` directly into the new `Bank`'s `BankConfig` and never calls `bank.config.validate()` afterward [3](#0-2) . This mirrors the reported bug class: a timeout/threshold-like parameter (`oracle_max_age`) can be set to `0` without any validation, unlike the analogous `BankConfig` path which does enforce a minimum.

### Finding Description
`oracle_max_age` controls how long an oracle price is considered live before being treated as stale [4](#0-3) . The `BankConfig::validate()` used by admin-driven `lending_pool_configure_bank` explicitly rejects values below `ORACLE_MIN_AGE` (10s) [1](#0-0) , and this is exercised by `configure_bank_oracle_min_age_validation` test which rejects `9` and accepts `10` [5](#0-4) .

`StakedSettings` — the group-level defaults used to create/propagate staked-collateral banks — carries its own `oracle_max_age: u16` field [6](#0-5)  but `StakedSettingsImpl::validate()` only checks the asset weights and risk tier; it has no check on `oracle_max_age` whatsoever [2](#0-1) . Both `init_staked_settings` and `edit_staked_settings` call only `staked_settings.validate()` [7](#0-6) [8](#0-7) , so a group admin can set `oracle_max_age: Some(0)` and it will be accepted.

The permissionless bank-creation flow `lending_pool_add_bank_permissionless` then copies `settings.oracle_max_age` straight into the new bank's `BankConfigCompact`/`BankConfig` (`oracle_max_age: settings.oracle_max_age`) [9](#0-8)  and constructs the `Bank` via `Bank::new(...)` [10](#0-9)  without ever invoking `bank.config.validate()` — unlike `propagate_staked_settings`, which does call `bank.config.validate()` after copying the same fields [11](#0-10) . This means the `ORACLE_MIN_AGE` guard is bypassed on the bank-creation path specifically.

Because these staked banks use `OracleSetup::StakedWithPythPush` (not `OracleSetup::PythPushOracle`), `get_oracle_max_age()`'s special-case fallback (`(0, OracleSetup::PythPushOracle) => MAX_PYTH_ORACLE_AGE`) does not apply [12](#0-11) , so an `oracle_max_age` of `0` would flow through to the staleness check as a literal zero-second allowance, exactly analogous to the DIA report's concern that a zero `timeoutSeconds`/`threshold` value disrupts normal `getValue()`-style operation.

### Impact Explanation
If `oracle_max_age = 0` reaches a live bank's staleness check, virtually any oracle read for that staked bank will be treated as stale (since a price can essentially never be "younger" than 0 seconds in practice, or the check logic could behave unexpectedly at the zero boundary). This would durably block all deposit/borrow/liquidation health checks that rely on that bank's price feed, effectively freezing usage of that staked-collateral bank — a durable operational DoS with financial effect (frozen collateral, blocked borrowing/liquidation) for any accounts depending on it. This requires the group admin (who controls `StakedSettings`) to set the zero value, so it is not a fully permissionless bug, but it demonstrates a real gap versus the equivalent, better-guarded `BankConfig::validate()` path, and the actual bank creation (`lending_pool_add_bank_permissionless`) is a permissionless instruction that anyone can invoke once `StakedSettings.oracle_max_age` is misconfigured.

### Likelihood Explanation
Requires the group admin to misconfigure `StakedSettings.oracle_max_age` to `0` (or an operator error/typo), which is plausible since there is no explicit rejection and no test coverage analogous to `configure_bank_oracle_min_age_validation` exists for the staked-settings/permissionless-add-bank path. Once misconfigured, exploitation of the resulting frozen bank requires no special privilege — any user's interaction with that bank would be affected, and the permissionless `lending_pool_add_bank_permissionless`/`propagate_staked_settings` instructions can be called by anyone to materialize the bad config into a live bank state (for `add_pool_permissionless`, since no `validate()` call exists there at all).

### Recommendation
- Add an explicit `oracle_max_age >= ORACLE_MIN_AGE` check (and ideally a sane upper bound) inside `StakedSettingsImpl::validate()` in `programs/marginfi/src/state/staked_settings.rs`, mirroring `BankConfigImpl::validate()`.
- Call `bank.config.validate()` (or at minimum re-use the same oracle-age check) at the end of `lending_pool_add_bank_permissionless` in `programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs`, consistent with `propagate_staked_settings`, to guarantee the invariant holds regardless of code path.

### Proof of Concept
1. Group admin calls `init_staked_settings` (or `edit_staked_settings`) with `oracle_max_age: 0`. `StakedSettingsImpl::validate()` does not check this field, so the transaction succeeds and `StakedSettings.oracle_max_age = 0` is persisted [2](#0-1) .
2. Any user calls the permissionless `lending_pool_add_bank_permissionless` to create a new staked-collateral bank. The resulting `BankConfig.oracle_max_age` is copied from `settings.oracle_max_age` (`0`) with no subsequent `validate()` call [13](#0-12) .
3. Because `oracle_setup == OracleSetup::StakedWithPythPush`, `get_oracle_max_age()` returns the literal `0` rather than falling back to `MAX_PYTH_ORACLE_AGE` [12](#0-11) , causing all subsequent staleness checks against this bank's oracle to fail/behave incorrectly, freezing deposits/borrows/liquidations that depend on this bank.

Note: I was unable to fully trace the exact staleness-comparison arithmetic in `programs/marginfi/src/state/price.rs` (the file appears large/only partially indexed) to confirm whether `oracle_max_age = 0` manifests as "always stale" (DoS) versus a different edge-case comparison outcome; a Devin session with full file access would be needed to pin down the precise runtime behavior at the `= 0` boundary.

    fn validate(&self) -> MarginfiResult {
        let asset_init_w = I80F48::from(self.asset_weight_init);
        let asset_maint_w = I80F48::from(self.asset_weight_maint);

        check!(
            asset_init_w >= I80F48::ZERO && asset_init_w <= I80F48::ONE,
            MarginfiError::InvalidConfig
        );
        check!(asset_maint_w >= asset_init_w, MarginfiError::InvalidConfig);
        check!(
            asset_maint_w <= (I80F48::ONE + I80F48::ONE),
            MarginfiError::InvalidConfig
        );
        if self.risk_tier == RiskTier::Isolated {
            check!(asset_init_w == I80F48::ZERO, MarginfiError::InvalidConfig);
            check!(asset_maint_w == I80F48::ZERO, MarginfiError::InvalidConfig);
        }

        Ok(())
    }
