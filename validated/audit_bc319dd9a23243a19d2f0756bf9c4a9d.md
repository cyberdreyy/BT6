### Title
Pre-Commit Weight Counted Toward Consensus Can Be Silently Reversed to a Rejection After the Threshold Is Already Relied Upon — (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/signerdb.rs`)

### Summary
The signer's pre-commit consensus mechanism tallies a signer's weight as soon as it pre-commits to a block, and lets peer signers act on that aggregated weight before the pre-committing signer's final signature is ever produced. The `BlockInfo` state machine explicitly permits a block that has already been marked `PreCommitted` (i.e., `valid = Some(true)`, weight already contributed to `commit_weight`) to later transition to `LocallyRejected`. This mirrors the reported vesting bug's root cause: a value (weight) is added to a running tally and relied upon by others, but the final, "true" state used to actually credit that value can change afterward, producing an accounting mismatch between the aggregated tally and the actually-verified outcome.

### Finding Description
When a signer receives enough `BlockPreCommit` messages to cross the voting-weight threshold, it treats that as the trigger to sign the block: [1](#0-0) 

The weight used for this decision (`commit_weight`) is derived purely from the set of `committers` recorded in the signer DB — i.e., signers who sent a pre-commit and were marked valid — not from confirmed final signatures: [2](#0-1) 

Once threshold is reached, the code explicitly re-validates chainstate "since this block passed proposal-time checks," and states it will respond with a rejection if the checks no longer pass "just as the block validation response handler does": [3](#0-2) 

Crucially, the underlying `BlockInfo` state machine permits this reversal: a block that reached `BlockState::PreCommitted` (which required `valid = Some(true)` via `mark_pre_committed`) is allowed to transition into `BlockState::LocallyRejected` (which sets `valid = Some(false)`), because `check_state` only forbids `LocallyAccepted`/`LocallyRejected` transitions when the *previous* state was `GloballyRejected` or `GloballyAccepted` — `PreCommitted` is not in that exclusion list: [4](#0-3) [5](#0-4) 

Because a miner can trigger a reorg/conflicting-proposal condition between the time a signer pre-commits (and its weight is durably recorded via `add_block_pre_commit`/`get_block_pre_committers`) and the time the aggregate threshold is reached and re-validation runs, the same signer's weight can be:
1. Counted by every peer signer's `compute_signature_signing_weight(committers.iter())` call as contributing toward the pre-commit threshold (an "aggregated-weight" credit), while
2. Never actually materializing as a verified signature, because the local re-validation converts it into `LocallyRejected`.

This breaks the equality between "aggregated (pre-commit) weight" and "verified accepts," which is exactly the class of equality this scan is scoped to check. Other signers who already crossed the threshold using the now-stale pre-commit weight will proceed to sign, while the signer count on which they relied is not honored by all contributors.

### Impact Explanation
This does not directly forge a signature over an invalid block, but it undermines the assumption that pre-commit weight (used as the internal trigger for a signer to add its own signature) reflects committed, final validity. In a reorg/conflicting-proposal scenario triggered by a single miner, it can cause:
- A signer set to believe consensus threshold was crossed based on weight that later flips to rejection, potentially stalling the round (liveness wedge — signers waiting on a weight that will never convert to real signatures), or
- Divergent local views across signers about whether the pre-commit round succeeded, since the underlying weight backing the "reached consensus" decision is not immutable once counted.

This aligns with the High-impact category: "a signer wedged into never signing valid blocks" due to relying on a stale/reversible weight snapshot rather than verified accepts.

### Likelihood Explanation
Reachable by a single miner: a block producer can submit a proposal, allow signers to pre-commit, and then submit a conflicting/reorg proposal (or otherwise change chainstate) before the pre-commit threshold's re-validation runs, causing some pre-committing signers to flip to rejection after their weight was already counted by peers. No majority of signers or extra keys are required — only ordinary gossip-visible proposal timing that a miner naturally controls.

### Recommendation
Do not allow a block that has reached `BlockState::PreCommitted` to transition to `LocallyRejected` on the same evaluation path that other signers use to tally consensus weight. Instead, either:
1. Freeze/exclude a signer's pre-commit weight from peers' threshold calculations once local re-validation invalidates it (and require a subsequent gossip message informing peers so they can re-tally), or
2. Perform the "since-passed-proposal-time" re-validation *before* pre-commit weight is recorded/counted at all, so `PreCommitted` state can only ever be reached once the signer's final validity determination is stable, removing the `PreCommitted -> LocallyRejected` transition entirely from `check_state`.

### Proof of Concept
1. Miner proposes Block A; Signers S1..Sn validate it as valid and pre-commit (`mark_pre_committed`, `add_block_pre_commit`), each pre-commit persisted and counted via `get_block_pre_committers`/`compute_signature_signing_weight`.
2. Enough signers (crossing `compute_voting_weight_threshold`) pre-commit; peer signers observe `commit_weight >= min_weight` in `handle_block_pre_commit` and begin the "about to sign" path.
3. Miner or gossip introduces a conflicting/reorg condition affecting chainstate checks for one of the pre-committing signers (e.g., a competing block for the same tenure), so that signer's mandatory re-validation ("re-run the chainstate checks…respond with rejection if they no longer pass") fails.
4. That signer calls `mark_locally_rejected` on the same block hash — permitted by `check_state` since `PreCommitted` is not excluded — flipping `valid` to `false` despite its weight already being counted by peers toward the threshold in step 2.
5. Peers that already progressed based on the stale `commit_weight` now have an inconsistent view: the aggregated pre-commit weight they relied upon no longer equals the weight of signers who will actually produce final signatures, potentially stalling consensus for that block round.

            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
