## #ValidVulnerability found for this question.

### Title
Stale rejection weight is never reconciled when a signer later accepts the same block, letting a phantom "blocking-minority" trip a validly-signed block into `SignersRejected` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies signer votes for a block into two independent counters, `total_weight_approved` and `total_weight_rejected`, using two *different* de-duplication keys (`gathered_signatures` for accepts, `responded_signers` for rejects). When a signer first sends a `Rejected` response and later sends an `Accepted`/`BlockAccepted` response for the very same block (`signer_signature_hash`), its weight is added to `total_weight_rejected` on the first message and then, because the accept-path checks a *different* map, added a second time to `total_weight_approved` on the second message. The earlier rejection weight is never removed. This lets a single signer's stale, superseded rejection permanently inflate `total_weight_rejected`, which the miner's `SignerCoordinator` checks *before* the approval threshold, potentially causing it to declare `SignersRejected` on a block that has, in fact, reached full signer approval.

### Finding Description
The two tally paths are:

Accept path [1](#0-0) 

Reject path [2](#0-1) 

`gathered_signatures` (a `BTreeMap<u32, MessageSignature>`) is only ever populated by the accept path, and `responded_signers` (a `HashSet<u32>`) is checked/inserted independently by each path. Consider a single signer at `slot_id`:

1. It sends `BlockResponse::Rejected` first. `responded_signers.insert(slot_id)` returns `true` (new), so `total_weight_rejected` is incremented by `signer_entry.weight`, and `slot_id` is now recorded in `responded_signers`.
2. The same signer later sends `BlockAccepted` for the identical `signer_signature_hash` (e.g. after a later validation, a resend, a race against a pre-commit, or gossip re-delivery/re-ordering). The accept path's guard is `!block.gathered_signatures.contains_key(&slot_id)` — this is `true`, because the reject path never touches `gathered_signatures`. So `total_weight_approved` is incremented by the *same* signer's weight, in addition to the weight already counted in `total_weight_rejected`.

The signer's weight is now counted in both buckets simultaneously, and the stale rejection weight is never retracted. (Note the reverse ordering — accept then reject — is correctly guarded, because the reject path's `responded_signers.insert(slot_id)` returns `false` once the accept path has already inserted that slot, so a late reject after an accept is properly dropped. Only the reject-then-accept ordering breaks the invariant.)

This corrupted tally is consumed directly by the miner-side coordinator, which checks rejection *before* approval: [3](#0-2) 

Because the rejection check `total_weight_rejected.saturating_add(weight_threshold) > total_weight` is evaluated first and returns early with `NakamotoNodeError::SignersRejected`, a block that has since collected `total_weight_approved >= weight_threshold` (i.e., is validly, fully signed) can still be thrown away by the miner if enough signers had *earlier* rejected before flipping to accept — the accept never cancels the earlier reject weight.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that the reward-set threshold protocol depends on: `total_weight_rejected` is supposed to represent the current weight of signers who reject the block, but the code lets it silently retain weight from signers who have since accepted it. In the worst case a properly, fully-signed block (⟶ `total_weight_approved >= weight_threshold`) is discarded by the miner as `SignersRejected` due to phantom, un-retracted rejection weight from an earlier vote by the same signers. This is a liveness wedge on block production: valid, canonical-quality blocks can be spuriously abandoned/retried by the miner, and (per the coordinator's failed-txid banning logic that runs inside the same `SignersRejected` branch) can even cause transactions to be temporarily or permanently excluded from future proposals based on this corrupted tally.

### Likelihood Explanation
Triggering this requires only a single signer (using its own key) to emit a `Rejected` response followed later by an `Accepted`/`BlockAccepted` response for the same block hash — no majority collusion, no other signer's key, and no auth token access is needed. This can happen either through ordinary vote reconsideration/resubmission by one signer, through network/gossip re-ordering of messages that were sent in the opposite order, or deliberately by one byzantine signer. Given that block proposal handling already anticipates out-of-order and duplicate signer responses (hence the existence of `responded_signers`/`gathered_signatures` de-dup logic in the first place), this is a realistically reachable code path, not merely a theoretical one.

### Recommendation
Use a single, unified per-slot vote record (e.g. an enum `Accepted(weight)`/`Rejected(weight)` keyed by `slot_id`) instead of two independently-guarded structures. On a vote change for the same `slot_id`, subtract the previously-tallied weight from whichever bucket held it before adding it to the new bucket, so `total_weight_approved + total_weight_rejected` for any `slot_id` never exceeds that signer's declared weight and always reflects only the signer's most recent vote.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`.
2. Signer `S` (slot `k`, weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `H`. `stackerdb_listener.rs` runs `responded_signers.insert(k)` → `true`; `total_weight_rejected += w`.
3. Enough other signers approve such that, together with a hypothetical retry, `total_weight_approved` for `H` eventually reaches `weight_threshold` while `total_weight_rejected` (boosted by `w` from step 2) already satisfies `total_weight_rejected.saturating_add(weight_threshold) > total_weight`.
4. Signer `S` later sends `SignerMessageV0::BlockAccepted(...)` for the same `H` (e.g., after reconsidering, or its earlier reject was network-delayed relative to its accept intention). The accept-path in `stackerdb_listener.rs` checks `!gathered_signatures.contains_key(k)` → `true`, so `total_weight_approved += w` a second time for the same signer, and `S`'s stale reject weight from step 2 is never removed from `total_weight_rejected`.
5. `SignerCoordinator::get_block_status`'s polling loop (`stacks-node/src/nakamoto_node/signer_coordinator.rs`, lines 509-545) evaluates the rejection branch first; since `total_weight_rejected.saturating_add(weight_threshold) > total_weight` already held from step 3, the miner returns `NakamotoNodeError::SignersRejected` for block `B`, even though `total_weight_approved` (including `S`'s corrected vote) meets or exceeds `weight_threshold`.
