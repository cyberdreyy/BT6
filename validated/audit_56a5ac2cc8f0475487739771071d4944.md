### Title
Missing mint-account ownership validation when parsing SPL token accounts for `jsonParsed` RPC responses lets a foreign-owned account spoof `decimals`/extension data and corrupt returned token balances - (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
The external report's bug class is: code trusts data at a caller-supplied/derived address without first confirming that address is actually backed by the expected program, allowing spoofed data to poison downstream logic. In agave, the JSON-RPC layer that renders SPL token accounts with `jsonParsed` encoding resolves the token account's embedded `mint` pubkey and unpacks whatever account lives at that address as an SPL `Mint`, without ever checking that the account is actually owned by a recognized SPL Token program.

### Finding Description
`get_mint_owner_and_additional_data` in [1](#0-0)  fetches the account at the `mint` pubkey taken directly from the token account's raw data (via `get_token_account_mint`, which just reads bytes `[0..32]` of the account, see [2](#0-1) ) and passes its data straight into `get_additional_mint_data`, which only attempts `StateWithExtensions::<Mint>::unpack(data)` — it never checks `mint_account.owner()` against `is_known_spl_token_id` before trusting the unpacked `decimals`/extension configs: [3](#0-2) .

This is a real, in-repo inconsistency, not a hypothetical: elsewhere in the very same RPC module, `get_token_supply` explicitly validates `is_known_spl_token_id(mint_account.owner())` before unpacking a `Mint` [4](#0-3) , and the SVM's own token-balance computation for transaction metadata explicitly checks `*mint_account.owner() != program_id` before trusting the mint's `decimals` [5](#0-4) . The parsed-token-account path used for RPC/pubsub output omits this same check that the codebase applies correctly in two other places, confirming the omission is a genuine defect rather than intentional design.

This helper is reached from every unprivileged path that renders `jsonParsed` SPL token accounts:
- `get_encoded_account` → `getAccountInfo` / `getMultipleAccounts` [6](#0-5) 
- `get_parsed_token_accounts` → `getProgramAccounts` / `getTokenAccountsByOwner` [7](#0-6) 
- `get_token_account_balance` (`getTokenAccountBalance`) [8](#0-7) 
- account-change pubsub notifications [9](#0-8) 

### Impact Explanation
If the account referenced by a token account's `mint` field is not actually owned by the SPL Token/Token-2022 program but its raw data happens to unpack as a valid `Mint` (i.e., the fixed-size `Mint::LEN` layout with `is_initialized = true`), the RPC layer will silently accept attacker-controlled `decimals` and extension configuration (`InterestBearingConfig`, `ScaledUiAmountConfig`) for that mint. This directly falsifies the `uiAmount`/`uiAmountString` computed by `token_amount_to_ui_amount_v3` and returned to any RPC/pubsub client for `getAccountInfo`, `getMultipleAccounts`, `getProgramAccounts`, `getTokenAccountsByOwner`, `getTokenAccountBalance`, and account subscriptions — i.e., wrong account data returned from a query, which matches an accepted impact category for this scan.

### Likelihood Explanation
The check is cheap (a single `is_known_spl_token_id` comparison already used correctly by sibling functions `get_token_supply` and `get_token_program_id_and_mint`), and its absence is purely an oversight in `get_additional_mint_data`/`get_mint_owner_and_additional_data`. Every affected RPC method is a single, unprivileged, unauthenticated read call, so any client capable of causing (directly or indirectly) a token account whose `mint` bytes reference a foreign-owned-but-Mint-shaped account can trigger incorrect decimal/ui-amount reporting for that account in one request.

### Recommendation
In `get_mint_owner_and_additional_data` / `get_additional_mint_data` (`rpc/src/parsed_token_accounts.rs`), require `is_known_spl_token_id(mint_account.owner())` before calling `StateWithExtensions::<Mint>::unpack`, mirroring the check already performed in `get_token_supply` (`rpc/src/rpc.rs`) and in `SvmTokenInfo::unpack_token_account` (`svm/src/transaction_balances.rs`). If the owner check fails, treat the account the same as "mint not found" (fall back to no additional data / raw amount) rather than trusting its parsed contents.

### Proof of Concept
1. Craft or locate a token account (owned by the SPL Token/Token-2022 program) whose stored `mint` field (bytes `0..32`) points to an account `X` that is not owned by a known SPL token program id but whose data happens to satisfy the fixed `Mint` packing (`is_initialized = true` at the correct offset, arbitrary `decimals` byte).
2. Call `getAccountInfo`/`getTokenAccountBalance` (or subscribe via `accountSubscribe`) on the legitimate token account with `encoding: "jsonParsed"`.
3. Observe the RPC layer calls `get_mint_owner_and_additional_data(bank, &mint_pubkey_of_X)` → `get_additional_mint_data` (`rpc/src/parsed_token_accounts.rs:92-130`), which unpacks `X`'s data as a `Mint` without verifying `X.owner()`, and returns the attacker-chosen `decimals`, which is then used to compute `uiAmount`/`uiAmountString` in the response — an incorrect account/balance representation returned to any unprivileged RPC caller.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}

fn filter_account_result(
    result: Option<(AccountSharedData, Slot)>,
    params: &AccountSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (Option<UiAccount>, Slot) {
    // If the account is not found, `last_modified_slot` will default to zero and
    // we will notify clients that the account no longer exists if we haven't already
    let (account, last_modified_slot) = result.unwrap_or_default();

    // If last_modified_slot < last_notified_slot this means that we last notified for a fork
    // and should notify that the account state has been reverted.
    let account = (last_modified_slot != last_notified_slot).then(|| {
        if is_known_spl_token_id(account.owner())
            && params.encoding == UiAccountEncoding::JsonParsed
        {
            get_parsed_token_account(&bank, &params.pubkey, account, None)
        } else {
            encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
        }
    });
    (account, last_modified_slot)
}
