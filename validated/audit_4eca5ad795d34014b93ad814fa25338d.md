### Title
External Initiator credentials bypass the "EIs not allowed" integer-ID check in `PipelineRunsController.Create`, allowing any job to be run via `POST /v2/jobs/:ID/runs` - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`PipelineRunsController.Create` intends to restrict integer-ID job triggering to authenticated users only, explicitly excluding external initiators (EIs): `_, isUser := auth.GetAuthenticatedUser(c) // only users are allowed to run jobs using int IDs - EIs not allowed` [1](#0-0) . However, `isUser` is derived solely from the presence of a `*clsessions.User` object in the gin context under `SessionUserKey`, via `auth.GetAuthenticatedUser` [2](#0-1) .

The `AuthenticateExternalInitiator` auth method, upon successfully validating EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers against `bridges.AuthenticateExternalInitiator`), explicitly sets the same `SessionUserKey` with a synthetic user object: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [3](#0-2) . This means `GetAuthenticatedUser` returns `ok == true` for EI-authenticated requests exactly the same as for real user sessions/tokens — the comment's assumed distinction ("EIs not allowed") does not hold, because the code path meant to gate this behavior (`isUser`) cannot actually distinguish an EI from a real user.

As a result, an attacker holding only valid EI credentials (registered via `ExternalInitiatorsController.Create`, intended only to trigger the specific webhook job it was created for) can:
1. Authenticate as an EI against any route in the `authv2` group that accepts `AuthenticateExternalInitiator` as one of its auth methods (confirmed present in `core/web/router.go`, paired with `AuthenticateByToken`).
2. `POST /v2/jobs/<any-integer-ID>/runs` for **any** job ID in the node — OCR, VRF, direct-request, keeper, etc. — not just a job bound to that EI.
3. `PipelineRunsController.Create` sees `isUser == true`, parses the ID as int32, and calls `prc.App.RunJobV2(ctx, jobID, nil)` unconditionally, with no check that the job is associated with the calling EI via `external_initiator_webhook_specs` [4](#0-3) .

The route/permission model provides no additional binding-check between an EI's identity and a job's ID before invoking `RunJobV2`.

### Impact Explanation
This is an authorization-bypass leading to unauthorized job execution: an attacker with only EI-level credentials for one job can trigger execution of any job on the node by numeric ID, including jobs that may perform on-chain transactions (e.g., DirectRequest/Keeper/VRF fulfillment jobs), potentially causing unwanted fund movement, gas expenditure, or unintended contract interactions — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitation requires only valid EI credentials, which are a low-privilege, commonly-issued credential type (created via `POST /v2/external_initiators`). No admin/user session or edit-role token is needed. The exploit is deterministic and repeatable — every EI-authenticated request to `/v2/jobs/:ID/runs` with a numeric ID will succeed regardless of which job the EI was created for.

### Recommendation
Distinguish real users from EIs explicitly, e.g., check `auth.GetAuthenticatedExternalInitiator(c)` first and reject/branch differently, rather than relying on `GetAuthenticatedUser`'s boolean presence (which is now always true after `AuthenticateExternalInitiator` runs). If EIs must still be allowed to trigger runs, validate that the requested job ID is bound to that specific EI's registered webhook spec before calling `RunJobV2`.

### Proof of Concept
1. Create a webhook/EI via `POST /v2/external_initiators` to obtain `AccessKey`/`Secret`.
2. Create Job A (e.g., an OCR/VRF job) not associated with this EI; capture Job A's integer ID.
3. Send `POST /v2/jobs/<JobA-ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI credentials (no session cookie, no API token).
4. Assert current (vulnerable) behavior: response is `200 OK` with a `pipelineRun` resource, and `prc.App.RunJobV2` was invoked — i.e., the run was created despite the EI having no relationship to Job A.
5. Expected/fixed behavior: response should be `401/403` (EI not authorized to run this job).
