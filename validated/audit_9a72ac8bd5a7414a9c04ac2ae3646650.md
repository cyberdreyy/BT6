### Title
Classic liquidation permits state changes on a frozen (compliance-held) liquidatee account without checking `ACCOUNT_FROZEN` - (File: `programs/marginfi/src/instructions/marginfi_account/liquidate.rs`)

### Summary
The external report describes `ComplianceServiceGlobalWhitelisted::newPreTransferCheck`/`preTransferCheck` checking the blacklist status of only the recipient (`_to`) and not the sender (`_from`), letting a blacklisted party bypass the control on the unchecked side of a two-party transfer. The analogous bug class — enforcing a state/authorization gate on only one side of a two-account operation — is reachable in marginfi-v2's permissionless liquidation path, where the `liquidator_marginfi_account` is checked against `ACCOUNT_FROZEN` but the `liquidatee_marginfi_account` is not, even though the instruction mutates the liquidatee's balances.

### Finding Description
`LendingAccountLiquidate` requires `account_not_frozen_for_authority` and `is_signer_authorized` constraints on `liquidator_marginfi_account`, but the `liquidatee_marginfi_account` account struct only checks `!a.get_flag(ACCOUNT_IN_RECEIVERSHIP)`: [1](#0-0) 

Per the project's own documentation, `ACCOUNT_FROZEN` is meant to make an account fully locked to third parties: "Only the group admin can operate on the account (e.g. to withdraw or rebalance)... This is used for compliance, investigations, or protecting accounts in unusual situations." [2](#0-1) 

However `account_not_frozen_for_authority` is only invoked for the signer's own account (the liquidator), never for the liquidatee: [3](#0-2) 

Because liquidation is explicitly permissionless — "Any signer can liquidate an unhealthy account" — and directly mutates the liquidatee's `lending_account` balances (repaying its liability, removing its collateral) inside `lending_account_liquidate`, a frozen liquidatee's state is still mutated by unrelated third parties despite the freeze being documented as blocking all operations except by the group admin. [4](#0-3) [5](#0-4) 

By contrast, other instructions such as `LendingAccountWithdraw` explicitly gate on both `ACCOUNT_DISABLED` and `ACCOUNT_FROZEN` for the account being acted upon: [6](#0-5) 

This asymmetry mirrors the reported bug class: a value-affecting state transition enforces the gating condition on one side of the interaction (liquidator authority/frozen) but omits it on the counterparty (liquidatee) whose balances are the ones actually being changed.

### Impact Explanation
If a group admin freezes an account for compliance/investigation reasons (e.g., a court order, fraud investigation, or sanctioned wallet), the documentation implies the account should be inert to everyone but the admin. Under the current code, if that frozen account also happens to be unhealthy, any permissionless liquidator can still call `lending_account_liquidate` against it, repaying its debt and seizing its collateral — bypassing the "compliance hold" intent of the freeze entirely for this specific interaction. This is a state-change/financial-effect bypass of an access-control gate that the protocol documents as exclusive to the admin, though it is worth noting liquidation itself is intentionally permissionless for unhealthy accounts in the normal (unfrozen) case, so the practical exposure is narrower than the generic blacklist-bypass in the report — it only matters for accounts that are simultaneously frozen and liquidatable.

### Likelihood Explanation
Requires: (1) an account to be frozen by the admin, and (2) that same account to be unhealthy/liquidatable at the same time. Both conditions are plausible in an investigation scenario (e.g., freeze happens after health has already deteriorated, or health deteriorates naturally while frozen since interest continues to accrue per the docs — "A frozen account's positions continue to accrue interest and can still be liquidated if unhealthy" is explicitly called out in `ACCOUNT_LIFECYCLE.md`, line 73). Given that the docs already state frozen accounts "can still be liquidated if unhealthy," this appears to be a deliberate design decision rather than an oversight, which weakens confidence that this is an unintended vulnerability. [7](#0-6) 

### Recommendation
If frozen-but-liquidatable is intended behavior (as the documentation suggests), no code change is needed — this is a documented design choice, not a defect. If it is not intended, add an explicit `ACCOUNT_FROZEN` constraint check to `liquidatee_marginfi_account` in `LendingAccountLiquidate`, or route liquidation of frozen accounts exclusively through an admin-only path, consistent with the freeze semantics described for other instructions like `LendingAccountWithdraw`.

### Proof of Concept
Not applicable as a concrete exploit — the codebase's own documentation (`ACCOUNT_LIFECYCLE.md` line 73) states that frozen accounts "can still be liquidated if unhealthy," indicating this is intended behavior rather than a flaw. Given this explicit confirmation, I cannot assert with confidence that this constitutes an unintended vulnerability analogous to the reported blacklist bypass; it is presented here only because it is the closest structural analog to the reported bug class (asymmetric enforcement of a state gate across the two parties of a value-transferring operation) found in the reachable, unprivileged-liquidation code path.

/// Checks if the account authority is allowed to act on their account based on frozen status.
///
/// Returns `true` if the action is allowed, `false` if blocked.
///
/// Returns `false` when both conditions are met:
/// - The account is frozen
/// - The signer is the account authority
///
/// This is intentionally separate from [`is_signer_authorized`] to return a distinct
/// `AccountFrozen` error in the instruction context  rather than `Unauthorized`.
pub fn account_not_frozen_for_authority(
    marginfi_account: &MarginfiAccount,
    signer: Pubkey,
) -> bool {
    !(marginfi_account.get_flag(ACCOUNT_FROZEN) && marginfi_account.authority == signer)
}
