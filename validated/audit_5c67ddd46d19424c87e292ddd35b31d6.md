### Title
`determine_response` re-signs a block already marked `GloballyRejected` in the signer's own bookkeeping, bypassing `BlockInfo::check_state`'s terminal-state guard - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`should_reevaluate_block` re-sends a signer's "decision" for a re-proposed block by calling `determine_response`, which decides Accept/Reject purely from `BlockInfo::valid`, never from `BlockInfo::state`. This lets a signer produce and broadcast a fresh, valid acceptance signature for a block whose own `signerdb` record already sits in the terminal `GloballyRejected` state, which the intended state machine (`BlockInfo::check_state`) is supposed to make unreachable from `GloballyRejected`.

### Finding Description
The claimed equality — "a rejection (even a local `GloballyRejected` marking) must never be recounted as an acceptance for the same `signer_signature_hash`" — is enforced only at the `move_to`/`check_state` layer: [1](#0-0) 

`check_state` correctly forbids `GloballyRejected -> LocallyAccepted`. But this guard is bypassed entirely by a second code path that never calls `move_to`.

`store_and_process_block_rejection` tallies rejection weight from OTHER signers and, once >30% weight is reached, calls `mark_globally_rejected()` on the *victim signer's own* `BlockInfo` — regardless of whether that signer had itself signed, only pre-committed, or done nothing yet with the block: [2](#0-1) 

Because `check_state`'s `GloballyRejected` arm only excludes `GloballyAccepted` as a predecessor, this transition succeeds from `Unprocessed`, `PreCommitted`, `LocallyAccepted`, or `LocallyRejected` alike: [3](#0-2) 

Critically, `mark_globally_rejected` never touches the `valid` field: [4](#0-3) 

So if the signer had earlier validated the block as `valid = Some(true)` (e.g. it reached `PreCommitted` after a node validate-OK, before ever signing), that flag survives the flip to `GloballyRejected`.

Now the attacker (a single miner slot) re-broadcasts the identical `BlockProposal` for hash `H`. `handle_block_proposal` looks up the stored (now `GloballyRejected`) `BlockInfo` and calls `should_reevaluate_block`: [5](#0-4) 

- `globally_approved_and_responded()` only matches `GloballyAccepted`, so it does **not** short-circuit for `GloballyRejected`: [6](#0-5) 
- `should_reevaluate_reject_reason` returns `false` because this signer's own `reject_reason` field is `None` (it never itself rejected the block — the rejection weight came from peers): [7](#0-6) 
- The `state == PreCommitted` special-case no longer applies, because the state is now `GloballyRejected`, not `PreCommitted`.
- Control falls into `determine_response(block_info)`: [8](#0-7) 

`determine_response` reads only `block_info.valid` (`Some(true)`) and unconditionally calls `create_block_acceptance`, which signs the block hash with the signer's private key and returns a fresh `BlockAccepted` response. This response is sent to the network via `send_block_response`, all without ever invoking `mark_locally_accepted`/`move_to`, so `check_state`'s terminal-state protection is never consulted.

### Impact Explanation
This breaks the fail-closed safety property: a block this signer's own database has already declared dead (`GloballyRejected`) gets a brand-new, valid, network-broadcast acceptance signature from that signer. If this signer had not yet signed (only reached `PreCommitted`/`valid=true` before the rejection tally crossed 30%), this signature is genuinely novel weight that other signers can aggregate toward the 70% acceptance threshold for a block that was supposed to be terminally and irrevocably rejected — a rejection recounted as acceptance. This matches the Critical category: a rejection recounted as acceptance / a signer signing a block its own state machine marks as invalid.

### Likelihood Explanation
Preconditions: the victim signer must have validated the block as `valid = true` (via node validate-OK, e.g. reached `PreCommitted`) before rejection weight from other signers crosses the >30% threshold and this signer's own `store_and_process_block_rejection` calls `mark_globally_rejected`. The attacker only needs to (1) win a miner slot to craft/re-propose the `BlockProposal`, and (2) rely on network conditions (any mix of legitimately differing peer votes, timing, or a competing proposal) driving rejection weight for `H` above 30% at the victim signer before the victim signs. No forged signer identity or majority control is required by the attacker; only re-delivery of the identical `BlockProposal` message, which is within the stated threat model (craft BlockProposals + gossip). This is repeatable per proposal/hash and requires no privileged access.

### Recommendation
Make `determine_response` (and the re-send branch of `should_reevaluate_block`) state-aware: it must refuse to produce/re-send an `Accepted` response when `block_info.state` is `GloballyRejected` (or any other state where `check_state` would forbid `LocallyAccepted`). Concretely, before calling `create_block_acceptance`, re-check `block_info.state != BlockState::GloballyRejected` (and ideally route the re-send decision through `mark_locally_accepted`/`move_to` so `check_state` is authoritative for every acceptance path, not just the "fresh evaluation" path).

### Proof of Concept
Rust test plan for `stacks-signer/src/v0/signer.rs` / `signerdb.rs`:
1. Construct a `BlockInfo` for block `H`, set `valid = Some(true)`, `state = BlockState::PreCommitted` (simulating a validate-OK signer that has not yet signed).
2. Call `store_and_process_block_rejection` (or directly `block_info.mark_globally_rejected()`) enough times/with enough synthetic peer weight to cross the 30% rejection threshold; assert `block_info.state == BlockState::GloballyRejected` after `insert_block`.
3. Re-deliver the identical `BlockProposal` for `H` via `handle_block_proposal` (mirroring `prior_block_info = Some(block_info)`).
4. Assert that `should_reevaluate_block` → `determine_response` does **not** return `Some(BlockResponse::Accepted(_))`, and that no `create_block_acceptance`/signature is produced/broadcast for `H`.
5. Contrast with current behavior: without the fix, `determine_response` returns `Some(Accepted(...))` because it only checks `block_info.valid`, proving the state guard is bypassed on this path.

        // We will only have the valid field set if we have already validated this block

        let valid = block_info.valid?;

            debug!("{self}: Accepting block {}", block_info.block.block_id());

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
