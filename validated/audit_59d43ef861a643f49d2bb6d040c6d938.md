### Title
Mid-epoch deposit credits nominal `_amount` instead of actual received, enabling share inflation on fee-on-transfer or non-standard underlying - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`depositDuringEpoch` in `IdleCDOEpochVariant` pulls underlyings from the depositor but never measures the balance delta. It mints tranche shares priced on the nominal `_amount`, mints `_amount` strategy tokens 1:1, adds interest computed on `_amount` to `expectedEpochInterest`, and pushes `_amount` to the borrower. The ordinary `_deposit` path correctly mints on `balanceAfter - balanceBefore` (`IdleCDOCreditVault._deposit`, lines 203-206), so this mid-epoch path is the inconsistent one — the same bug class as the external report (credit the declared amount, not the received amount).

### Finding Description
In `IdleCDOEpochVariant.depositDuringEpoch` (lines 656-733):

1. `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` pulls tokens with no pre/post balance check (line 685).
2. `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` mints shares against the declared `_amount` (line 724), and `_mintShares(..., _amount)` bumps `lastNAV*` by the full `_amount`.
3. `IdleCreditVault(strategy).mintStrategyTokens(_amount)` mints `_amount` receipt tokens (line 730) — `mintStrategyTokens` mints 1:1 with no backing check (IdleCreditVault.sol lines 621-624).
4. `_transferUnderlyings(_borrower(), _amount)` forwards the full `_amount` to the borrower (line 732), and `expectedEpochInterest += interest` is computed on the full `_amount`.

If the vault's underlying token charges a transfer fee (or otherwise delivers less than `_amount`), the CDO receives `_amount - fee` but books `_amount` of NAV, strategy tokens, expected interest, and borrower disbursement. The gap is either (a) covered by other funds already sitting in the CDO (e.g., buffer-period residual liquidity or pending instant-withdraw funding), which is a direct transfer of value from other LPs to the depositor/borrower, or (b) the borrower transfer reverts. Case (a) inflates the attacker's shares at the expense of the pool; every holder's `virtualPrice` is propped up by assets that were never delivered, and the deficit is socialized at `stopEpoch`/claim time.

Note the same nominal-crediting pattern exists in `IdleCreditVault.deposit` (lines 596-604: `safeTransferFrom` then `_mint(msg.sender, _amount)`), but that path is `onlyIdleCDO` and sourced from the CDO's own balance-delta-verified `_deposit`, so it is not attacker-reachable.

### Impact Explanation
A KYC-passing wallet (the required caller class for `depositDuringEpoch`) deposits a fee-on-transfer underlying mid-epoch and is minted tranche shares for the gross `_amount` while delivering only `_amount - fee`. The vault simultaneously mints `_amount` strategy tokens and raises `expectedEpochInterest` on the gross amount. If the CDO holds any residual underlying balance (buffer leftovers, prefunded amounts), the borrower receives the full `_amount`, creating a permanent NAV hole equal to the fee (plus the phantom interest accrual). This breaks the fair-mint/solvency invariant: new shares are issued against undelivered assets and the loss is socialized across existing AA/BB holders at epoch settlement.

### Likelihood Explanation
Moderate-low. It requires (1) the credit vault's underlying token to be a fee-on-transfer or rebate-decrementing token — deployments target stablecoins like USDC, so this is a configuration/asset-selection hazard rather than a current-deployment exploit; (2) `isDepositDuringEpochDisabled` turned off by the owner (it is a gated, opt-in feature); (3) the CDO holding residual underlying during a running epoch to absorb the fee (otherwise the borrower transfer reverts and the deposit fails atomically, limiting it to a DoS). No existing guard stops it: `_skimDonatedAssets` only skims *excess* above accounted NAV and runs *before* the pull, `isWalletAllowed`/KYC only restricts who calls, and `mintStrategyTokens` performs no backing verification.

### Recommendation
Mirror the `_deposit` pattern in `depositDuringEpoch`: record `balanceBefore = token.balanceOf(address(this))` before `_transferUnderlyingsFrom`, then use `received = token.balanceOf(address(this)) - balanceBefore` for the interest calc, `_mintShares`, `mintStrategyTokens`, and the borrower transfer (or revert if `received != _amount`). Apply the same fix or an explicit fee-token rejection comment in `IdleCreditVault.deposit`/`mintStrategyTokens` for defense-in-depth.

### Proof of Concept
Foundry test extending `test/foundry/IdleCreditVault.t.sol` patterns. Deploy a fee-charging variant of the test underlying (`TestnetERC20TokenWithFee` taking a 10% fee on `transfer`/`transferFrom`, as in the external PoC), wire it as the CDO's `token`, then:

```solidity
function testDepositDuringEpochFeeOnTransfer() public {
    // setup: fee token as underlying, seed vault with residual liquidity
    idleCDO.depositAA(10_000 * ONE_SCALE);
    vm.prank(owner); cdoEpoch.setIsAYSActive(false);
    _startEpochAndCheckPrices(0);
    vm.prank(owner); cdoEpoch.setIsDepositDuringEpochDisabled(false);

    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);

    address attacker = makeAddr('midEpochFoT');
    uint256 amount = 1_000 * ONE_SCALE;
    deal(feeToken, attacker, amount);

    vm.startPrank(attacker);
    IERC20Detailed(feeToken).approve(address(cdoEpoch), amount);
    uint256 minted = cdoEpoch.depositDuringEpoch(amount, address(AAtranche));
    vm.stopPrank();

    // vault only received amount - fee, but lastNAVAA/strategy tokens/expectedEpochInterest
    // were credited the full `amount` -> shares minted against undelivered assets
    uint256 fee = amount / 10;
    assertLt(IERC20Detailed(feeToken).balanceOf(address(cdoEpoch)), amount);
    // insolvency: getContractValue reflects strategy tokens minted 1:1 with `amount`
    // while true backing is amount - fee (or borrower was overpaid from pool residual)
}
```

Run: `forge test --match-test testDepositDuringEpochFeeOnTransfer -vvvv`. Caveat: I verified the code paths via the index but did not confirm line-by-line whether `_transferUnderlyings`/`_mintShares` contain additional internal delta checks; if the underlying is strictly standard ERC20 in all deployments, the practical severity reduces to zero until a fee-bearing asset is onboarded.
