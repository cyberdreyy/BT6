### Title
Deterministic lockup account address allows front-running/squatting of a victim's lockup, permanently blocking legitimate creation with attacker-chosen parameters funded - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the new lockup account ID deterministically as `sha256(owner_account_id)[..20].<factory>` with no uniqueness salt tied to the caller, and `create` is callable by anyone with `MIN_ATTACHED_BALANCE`. An attacker can pre-create this address for a victim `owner_account_id`, after which the legitimate grantor's later `create` call for the same victim fails at `create_account` (account already exists), triggers the refund path in `on_lockup_create`, and permanently leaves the victim's lockup account populated with attacker-chosen parameters and attacker's deposit.

### Finding Description
The claimed binding "refund (Y) + NEAR left in the account (X) == a single creator's `env::attached_deposit()`" does not actually break any accounting invariant inside `on_lockup_create`: each `create` call has its own independent `attached_deposit`, and the callback correctly refunds exactly the deposit associated with the failing call to its own `predecessor_account_id`: [1](#0-0) 
When `is_promise_success()` is false, `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` refunds the caller's own `attached_deposit`, not some combined X+Y value — so the real grantor's `Y` is fully and correctly returned. No NEAR is misappropriated in the refund step itself.

The actual defect is upstream: the lockup account ID is fully deterministic from `owner_account_id` alone, with no dependency on the caller or a nonce/salt: [2](#0-1) 
Since `create` is `#[payable]` and open to any unprivileged caller (only `env::attached_deposit() >= MIN_ATTACHED_BALANCE` is checked, with no `assert_called_by_foundation` or owner check), an attacker can call `create(owner_account_id=<victim>, ...)` with attacker-chosen `lockup_duration`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`, attaching `X = MIN_ATTACHED_BALANCE`. This succeeds and deploys a lockup contract at the deterministic address, owned by `<victim>` but funded and configured entirely on the attacker's terms.

When the legitimate grantor later calls `create(owner_account_id=<victim>, ...)` with the intended deposit `Y` and intended terms, the `Promise::new(lockup_account_id).create_account()...` action chain fails on NEAR's runtime because the account already exists at that address (account creation actions fail if the target account ID is already taken). `is_promise_success()` returns `false` in `on_lockup_create`, and the grantor's `Y` is refunded to them — correctly, but the intended, properly-funded/properly-parameterized lockup for `<victim>` can never be created at that address again. `assert_self()` only ensures the callback is called by the contract itself, and does nothing to prevent or detect this squatting; there is no check anywhere in `create`/`on_lockup_create` for pre-existing accounts, and none is even possible synchronously (existence is only discovered via the failed promise).

### Impact Explanation
This matches the Critical category "a lockup deployed with parameters its rightful creator never chose." The victim's lockup account is permanently occupied by a lockup with an attacker-chosen `lockup_duration`, `vesting_schedule`/`release_duration`, and `staking_pool_whitelist_account_id`, funded with attacker's own `X` (attacker's own money, so no direct fund theft from a third party), while the legitimate grantor (e.g., a company or the foundation intending to grant `Y` NEAR to `<victim>` under specific vesting terms) can never deploy the intended lockup at that deterministic address — their attempt always fails and their deposit is refunded, but the intended grant is permanently blocked/frozen at that address. This is a one-shot, repeatable-per-victim griefing/squatting primitive: an attacker can pre-emptively squat any `owner_account_id` they can predict is about to receive a lockup grant, for the cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per victim, which they get to keep control of (as the account creator/funder, though not as `owner_account_id`).

### Likelihood Explanation
Feasible for any unprivileged attacker: the account address is a pure deterministic function of `owner_account_id`, publicly computable off-chain before the real grantor's call lands. Cost is `MIN_ATTACHED_BALANCE` per victim address squatted, fully recoverable is not — the attacker's own deposit is locked into the squatted lockup (it becomes owned by `<victim>`, not the attacker), so this is more a griefing/DoS-of-legitimate-grant attack than a direct profit vector for the attacker, though it does block/freeze the intended grant. Requires the attacker to know or guess the victim's `owner_account_id` before the legitimate `create` call executes (e.g., via mempool observation or public announcement of upcoming grants).

### Recommendation
Bind the lockup account address to the caller's intent uniquely, e.g., include a nonce/salt or the funding transaction's unique identifier in the account ID derivation, or require `create` to be restricted to a privileged caller (foundation/whitelisted issuer) via `assert_called_by_foundation`-style check, or check for account existence up front (e.g., via a registry mapping `owner_account_id -> lockup_account_id` already created) and reject/no-op the transaction with a refund before attempting `create_account`, rather than relying on the async create_account failure as the only signal.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
