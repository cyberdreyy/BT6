Based on my research, I found a concrete Aptos-native analog of this bug class in the `vesting` module's `distribute()` flow.

### Title
Any shareholder can permanently block `vesting::distribute` for an entire vesting pool by disabling direct coin transfers, stranding other shareholders' vested funds - (File: aptos-move/framework/aptos-framework/sources/vesting.move)

### Summary
`vesting::distribute` is a permissionless `public entry fun` that iterates over every shareholder in a `VestingContract`'s `grant_pool` and pushes coins to each one via `aptos_account::deposit_coins`, with no removal mechanism for problematic shareholders — mirroring the reported `configureFeeRecipient`/`distributeProtocolAssetReward` pattern where a poisoned or invalid recipient blocks the whole distribution loop.

### Finding Description
`create_vesting_contract` adds up to `MAXIMUM_SHAREHOLDERS` (30) arbitrary addresses to `grant_pool` [1](#0-0) , and there is no function anywhere in `vesting.move` to remove a shareholder from `grant_pool` — only `set_beneficiary`/`reset_beneficiary`, which merely redirect that shareholder's own future payouts and don't affect the loop membership [2](#0-1) .

`distribute()` is callable by anyone (no auth check) and unconditionally loops over `shareholders()` from `grant_pool`, calling `aptos_account::deposit_coins(recipient_address, share_of_coins)` for each one [3](#0-2) . `aptos_account` exposes a self-service, fully unprivileged `set_allow_direct_coin_transfers` (opt-out toggle) that any shareholder can call on their own account at any time, gated by the `DirectTransferConfig` resource [4](#0-3) . If that same shareholder address is not yet registered for `AptosCoin` (nothing in `create_vesting_contract` requires or registers shareholder addresses for APT — only `withdrawal_address` is checked, via `assert_account_is_registered_for_apt(withdrawal_address)` [5](#0-4) ), `aptos_account::deposit_coins` will abort on that recipient because it refuses to auto-register/deposit to unregistered accounts that have opted out of arbitrary transfers.

Because Move aborts unwind the entire transaction, a single malicious/self-poisoned shareholder in the shared `grant_pool` causes `distribute()` to revert for the whole vesting contract — blocking payout to *every other* shareholder sharing that pool, exactly as in the external report where any single invalid fee recipient blocks the entire `distributeProtocolAssetReward` loop.

### Impact Explanation
This traps vested/reward funds for all co-shareholders of a vesting pool that includes the malicious account, with no admin-side recovery path (no `remove_shareholder`, and `distribute()`'s loop is unconditional). This satisfies "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows," since honest shareholders lose their ability to actually withdraw distributed value even though their accounting entitlement (`grant_pool` shares) remains intact — the value is functionally stranded in the vesting contract's resource account.

### Likelihood Explanation
The attacker needs zero privilege: they only need to (1) be one of the (up to 30) shareholders of a shared vesting contract set up by an admin, and (2) call the standard, publicly available `set_allow_direct_coin_transfers(false)` on their own account while remaining unregistered for `AptosCoin`. Both actions are ordinary, unprivileged, self-directed operations reachable by any account, making this a straightforward, low-cost griefing vector whenever a vesting contract has multiple independent shareholders.

### Recommendation
In `distribute()`, wrap each per-shareholder payout so a failed deposit does not abort the whole transaction (e.g., retain undistributed shares/coins for that shareholder and skip to the next, similar to a "pull" pattern), or add an explicit remove/skip mechanism for shareholders whose accounts cannot receive direct transfers, analogous to removing a zero-share fee recipient in the external report's suggested fix.

### Proof of Concept
1. Admin creates a vesting contract via `create_vesting_contract` with shareholders `[Alice, Bob]`, where `Bob` is a freshly generated address never registered for `AptosCoin`.
2. `Bob` calls `aptos_account::set_allow_direct_coin_transfers(false)` on his own account (fully permissionless, ordinary user action).
3. Time passes; rewards/vesting accrue and become withdrawable (`stake::fast_forward_to_unlock`, etc.).
4. Anyone calls `vesting::distribute(contract_address)`.
5. The loop reaches `Bob`, calls `aptos_account::deposit_coins(Bob, share_of_coins)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` since `Bob` is unregistered and opted out.
6. The whole `distribute()` transaction reverts — `Alice` (and all other shareholders) receive nothing, and there is no way for the admin to remove `Bob` from `grant_pool` to unblock future distributions.

Note: I was unable to directly view the full source of `aptos_account::deposit_coins`/`can_receive_direct_coin_transfers` or `terminate_vesting_contract` within the indexed context (grep did not surface `deposit_coins`'s body in this repo snapshot), so the exact abort semantics and whether `terminate_vesting_contract` also calls `distribute_internal` (and would thus also be blockable) should be verified directly in a full checkout before treating this as fully proven; if `deposit_coins` behaves differently in this specific codebase revision (e.g., always auto-registers regardless of opt-out), the vulnerability would not hold as described.

    /// Distribute any withdrawable stake from the stake pool.
    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

    public entry fun set_beneficiary(
        admin: &signer,
        contract_address: address,
        shareholder: address,
        new_beneficiary: address,
    ) acquires VestingContract {
        // Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't
        // fail and block all other accounts from receiving APT if one beneficiary is not registered.
        assert_account_is_registered_for_apt(new_beneficiary);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);

        let old_beneficiary = get_beneficiary(vesting_contract, shareholder);
        let beneficiaries = &mut vesting_contract.beneficiaries;
        if (beneficiaries.contains_key(&shareholder)) {
            let beneficiary = beneficiaries.borrow_mut(&shareholder);
            *beneficiary = new_beneficiary;
        } else {
            beneficiaries.add(shareholder, new_beneficiary);
        };

        emit(
            SetBeneficiary {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
                shareholder,
                old_beneficiary,
                new_beneficiary,
            },
        );
    }
