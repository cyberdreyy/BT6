No vulnerability found for this question.

Investigation confirms this exact behavior is intentional, documented, and tested. `SignerDb::add_block_rejection_signer_addr` explicitly refuses to record a rejection when a signature already exists for that signer/block, returning `Ok(false)` without modifying the stored signature [1](#0-0) . This is verified by the existing unit test `accept_then_reject`, which asserts that after `add_block_signature` succeeds, a subsequent `add_block_rejection_signer_addr` call for the same signer/block returns `false` and leaves both the signature table and rejection table unchanged [2](#0-1) . The symmetric case (`reject_then_accept`) confirms a signature *does* clear a prior rejection [3](#0-2) , and `add_block_signature` itself deletes any rejection row before inserting the signature [4](#0-3) .

This asymmetry is deliberate and documented directly in the codebase: a signature is treated as a bearer instrument that, once made public, can be aggregated by anyone toward the 70% threshold, so a later "rejection" is only a revocable local opinion that cannot retroactively unwind an already-broadcast signature [5](#0-4) . `docs/signer-flows.md` reiterates the same design intent: signing is "the one irreversible act," and a signer commits to a tenure once it signs regardless of any later state it falls to [6](#0-5) .

Additionally, `store_and_process_block_rejection` in the state machine explicitly bails out once `block_info.has_reached_consensus()`, meaning any terminal decision (accepted or rejected) is final and later opposing messages are audit-only, never re-tallied [7](#0-6) .

Finally, `get_account_entry` (the nominated target) is an unrelated read-only RPC helper used only for balance/nonce/monitoring purposes [8](#0-7) ; it has no role in block-response aggregation, signature storage, or the accept/reject tally described in this question, so there is no code path connecting the claimed entrypoint (BlockProposal + gossiped signer messages) to this function or to the alleged "stale accept counted" impact.

Since the guard is present, intentional, and covered by existing tests on both sides of the claimed equality, there is no vulnerability here.

                "signer_address" => %signer_addr,
