### Title
EI-authenticated requests bypass "no EI job runs" restriction and RequiresRunRole enforces role-only check with no EI-to-job binding, enabling cross-job run triggering - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` regardless of which job the EI credential is registered for. `auth.RequiresRunRole` only inspects `user.Role`, and `PipelineRunsController.Create`'s `isUser` gate (`auth.GetAuthenticatedUser`) cannot distinguish this synthetic EI-derived user from a genuine session/token user, so an EI credential scoped to job A can trigger `RunJobV2` for any integer job ID, including job B, with no check that the EI is associated with that job.

### Finding Description
The route is registered as: [1](#0-0) 

`userOrEI` accepts `AuthenticateExternalInitiator` before `AuthenticateByToken`/`AuthenticateBySession`. On success, `AuthenticateExternalInitiator` stores the EI object under `SessionExternalInitiatorKey` and, critically, also injects a fabricated `User` object with Run role into `SessionUserKey`: [2](#0-1) 

`RequiresRunRole` then only checks `user.Role != UserRoleView`, with no notion of which EI/job pair is bound to the request: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and gates this via `isUser, _ := auth.GetAuthenticatedUser(c)`: [4](#0-3) 

However, `GetAuthenticatedUser` simply reads whatever object is under `SessionUserKey`: [5](#0-4) 

Since `AuthenticateExternalInitiator` places a `User` object there too, `isUser` evaluates to `true` for EI-authenticated requests exactly as it would for a real user — the intended EI exclusion for integer-ID job runs does not function. The handler then calls `prc.App.RunJobV2(ctx, jobID, nil)` using only the path-param `jobID` from `:ID`, with **no lookup or check** that the authenticated `ExternalInitiator` (obtainable via `GetAuthenticatedExternalInitiator`) is actually linked to that job through `external_initiator_webhook_specs`. Any successfully authenticated EI credential (registered for job A) can thus submit `POST /v2/jobs/<jobB_int_ID>/runs` and trigger job B's pipeline run, since the binding between an EI and its authorized job is never verified in this code path — it's checked nowhere between authentication and `RunJobV2` invocation.

Note: webhook-type jobs (the ones actually associated with EIs) use UUID job IDs, and `Create` explicitly rejects UUID IDs with `job.ErrJobTypeRemoved`. But `Create` does not reject *integer* IDs for EI-authenticated callers as its own comment claims it should — the `isUser` check is a no-op distinguishing mechanism against `SessionUserKey`, so an EI credential can address integer-ID jobs (e.g., OCR, Cron, VRF, Flux Monitor, DirectRequest specs) it was never meant to trigger, and there is no job-ownership check tying the specific EI to the specific integer job ID at all.

### Impact Explanation
An external initiator credential holder authorized only for job A (a webhook job) can force execution of an arbitrary job B (any non-webhook job addressable by integer ID) by simply calling `POST /v2/jobs/<jobB_ID>/runs` with job A's EI access key/secret. This is unauthorized job-run triggering across job boundaries — matches the "unauthorized job run" bounty impact class, since it lets a lower-privileged/narrowly-scoped credential holder cause execution of arbitrary pipelines (potential fund movement, external HTTP/bridge calls, on-chain transactions depending on job type) outside its intended scope.

### Likelihood Explanation
Preconditions are minimal: any valid EI access key/secret registered for any job (job A) suffices; the attacker needs no further privilege. The request is a single unauthenticated-relative-to-target-job HTTP POST with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to job A's EI credentials and the target `:ID` set to job B's integer ID. This is trivially repeatable and requires no race condition or timing dependency.

### Recommendation
In `PipelineRunsController.Create`, distinguish EI-derived sessions explicitly (e.g., check `auth.GetAuthenticatedExternalInitiator` presence, not just `GetAuthenticatedUser`) and reject EI-authenticated requests for integer job IDs entirely, per the existing code comment's intent. Additionally, for any EI-triggered run, look up the job's `external_initiator_webhook_specs` and verify the authenticated `ExternalInitiator.ID` is bound to the target `WebhookSpec`/`Job` before calling `RunJobV2`/`RunJobV2` for webhook UUID paths, closing the gap where role-only checks (`RequiresRunRole`) allow no distinction between which EI is calling for which job.

### Proof of Concept
Handler/integration test plan:
1. Create job A as a webhook job with EI `eiA` (via `cltest.MustInsertExternalInitiator` + webhook spec linking) and job B as a non-webhook job (e.g., Cron or a second job) with integer ID `jobB.ID`.
2. Build an authenticated `*http.Client`-less raw HTTP request: `POST /v2/jobs/<jobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to `eiA`'s credentials (not any credential tied to job B).
3. Assert the response is `403`/`404` (expected secure behavior) — currently, the request reaches `prc.App.RunJobV2(ctx, jobB.ID, nil)` and returns `200` with a `pipelineRun` resource, because `isUser` is true and no EI-to-job binding check exists.
4. Assert `pipeline_runs` table gained an entry for `jobB.ID` triggered by `eiA` credentials, confirming cross-job unauthorized triggering.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
