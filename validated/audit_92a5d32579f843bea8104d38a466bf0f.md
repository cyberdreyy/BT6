### Title
Instant-withdraw receipt counters are never cleared on a successful claim, inflating `defaultPendingClaimBasis` and permanently stranding default-recovery funds - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
Analogous to the external `totalStaked`/`totalClaimed` bug, `IdleCreditVault` increments two instant-withdraw counters on request — `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` — but the normal claim path `claimInstantWithdrawRequest` never decrements them. Only the default-recovery claim path `_claimDefaultedInstantWithdrawRequest` clears them. If a borrower default is finalized in the same epoch in which instant receipts were already claimed, `defaultPendingClaimBasis()` re-counts those already-paid claims, deflating `defaultRecoveryPrice` for all honest claimants and permanently locking the excess inside `defaultRecoveryReserve`.

### Finding Description
`requestInstantWithdraw` records the receipt basis twice: per user/epoch and as an epoch aggregate:

- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;`
- `instantWithdrawClaimsByEpoch[currentEpoch] += _amount;` [1](#0-0) 

The funded claim path burns the user's receipt tokens and zeroes only `instantWithdrawsRequests[_user]` — the per-epoch basis and the epoch aggregate survive:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

By contrast, the defaulted-receipt claim correctly clears both `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and `instantWithdrawClaimsByEpoch[defaultEpoch]`. [3](#0-2) 

At default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`. [4](#0-3)  That value is then used to compute `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` in `finalizeDefaultRecovery`. [5](#0-4) 

So the "live" claim basis is `instantWithdrawClaimsByEpoch - alreadyClaimed`, exactly as the external report's real managed amount is `totalStaked - totalClaimed` — but the contract uses the raw cumulative figure.

### Impact Explanation
When `finalizeDefaultRecovery` runs in the same epoch where instant claims were already paid:

- `totalBasis` is overstated by the claimed amount `X`, so `defaultRecoveryPrice` is set to `reserve / (basis + X)` instead of `reserve / basis`.
- Every honest defaulted and post-default claimant (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`, `_claimPostDefaultWithdrawRequest`) receives `claimBasis * price / 1e18`, i.e. a proportional haircut larger than the real loss.
- The surplus `reserve - Σ realBasis·price ≈ reserve·X/(basis+X)` can never be withdrawn: `defaultRecoveryReserve` is only decremented by `_transferDefaultRecovery` on claims [6](#0-5) , and the stale entry cannot even be drained by the user who already claimed — `instantWithdrawsRequests[_user] -= claimBasis` underflows (0 minus a nonzero amount) and reverts. [7](#0-6) 

Result: direct loss to defaulted claimants plus permanent freezing of part of the recovery reserve. Loss magnitude scales with instant-withdraw volume claimed before the default.

### Likelihood Explanation
Requirements: an epoch with instant withdrawals enabled (non-prefunded `IdleCDOEpochVariant`), at least one user claiming an instant withdrawal mid-epoch, another instant/pending receipt still unfunded (`pendingInstantWithdraws != 0`), and a borrower default finalized before `stopEpoch` bumps `epochNumber` (default finalization reads `instantWithdrawClaimsByEpoch[epochNumber]` for the same epoch). Instant-withdraw windows (e.g. a few days after epoch start) overlapping a mid-epoch borrower default are a plausible operational scenario, and no privileged misbehavior is needed — an unprivileged lender claiming their instant withdrawal early is enough to poison the basis. No existing guard (`_ensureDefaultRecoveryInitialized`, `defaultRecoveryFinalized` checks) prevents it, since `pendingInstantWithdraws` legitimately remains nonzero.

### Recommendation
Mirror the external fix — track the live basis instead of the cumulative one. In `claimInstantWithdrawRequest`, clear the per-epoch and epoch-aggregate counters for the request epoch, e.g.:

```solidity
uint256 currentEpochBasis = instantWithdrawsRequestsByEpoch[_user][epochNumber_of_request];
instantWithdrawsRequestsByEpoch[_user][reqEpoch] = 0;
instantWithdrawClaimsByEpoch[reqEpoch] -= currentEpochBasis;
```

This requires storing (or deriving) the request epoch for instant receipts, since `instantWithdrawsRequests` is an aggregate across epochs — e.g. add a `lastInstantWithdrawRequest` epoch marker per user, or decrement `instantWithdrawClaimsByEpoch` for each epoch the claimed amount was booked under.

### Proof of Concept
Foundry fork-style sequence on an `IdleCDOEpochVariant` + `IdleCreditVault` deployment with instant withdrawals enabled:

1. `startEpoch` — epoch E running, `epochNumber == E`.
2. Alice (KYC'd lender) deposits, then calls `CDO.requestInstantWithdraw(100)` → `instantWithdrawsRequestsByEpoch[Alice][E] = 100`, `instantWithdrawClaimsByEpoch[E] = 100`, `pendingInstantWithdraws = 100`.
3. Owner/manager calls `collectInstantWithdrawFunds(60)` (partial funding) → `pendingInstantWithdraws = 40`. Bob also has an unfunded instant/normal receipt so `pendingInstantWithdraws` stays nonzero (or Bob requested 40 more; net: `instantWithdrawClaimsByEpoch[E] = 140`, `pendingInstantWithdraws = 40`, funded reserve 100 sits in strategy).
4. After the instant delay, Alice calls `claimInstantWithdrawRequest` → receives 100 underlying. Assert: `instantWithdrawsRequests[Alice] == 0` but `instantWithdrawsRequestsByEpoch[Alice][E] == 100` and `instantWithdrawClaimsByEpoch[E] == 140` (stale).
5. Borrower defaults mid-epoch; owner calls `finalizeDefaultRecovery(recovered, source)`.
6. Assert: `defaultPendingClaimBasis()` includes the already-paid 100 → `defaultRecoveryPrice` equals `reserve * 1e18 / (realBasis + 100)` instead of `reserve * 1e18 / realBasis`.
7. Honest claimant Carol calls `claimWithdrawRequest` → payout is lower than `realBasis * reserve / realBasis`; the difference stays in `defaultRecoveryReserve`.
8. Alice calls `claimInstantWithdrawRequest` again → reverts on `instantWithdrawsRequests[Alice] -= 100` underflow → the surplus share of the reserve is stranded permanently.

(Note: exact feasibility of step 4 depends on the instant-delay vs. epoch-boundary timing; the stale counters are directly observable from the code since `claimInstantWithdrawRequest` never writes `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, which I verified by reading every site that mutates them.)
