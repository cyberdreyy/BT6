### Title
Permanent `stopEpoch` DoS via APR0 withdraw request followed by APR change - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` unconditionally reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged tranche holder can permanently trap the vault in a running epoch by placing a dust-sized `requestWithdraw` while the configured APR is 0. Once the honest manager or CDO later sets a non-zero APR — a routine configuration call — every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts, because `apr0TotalPrincipal` can only be decremented inside the very function that now always reverts. This mirrors the CVE-2022-22719 bug class: a small crafted input creates a latent state that makes all later processing crash (revert).

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` the request is routed to `_requestWithdrawApr0`, which increments the global bucket `apr0TotalPrincipal` by `_amount` (`IdleCreditVault.sol:285-286`, `567-577`). There is no minimum amount, so 1 wei suffices.

At epoch stop, the CDO calls `prepareStopEpochWithApr0` (`IdleCreditVault.sol:490-541`):

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`apr0TotalPrincipal` is only cleared in two places:
- `prepareStopEpochWithApr0` itself (`apr0TotalPrincipal = 0`, line 540) — unreachable once it reverts;
- `_clearWithdrawClaimForEpoch` with `_isClearingApr0 = true`, which is only reached through `_claimDefaultedWithdrawRequest`, i.e., only after `defaultRecoveryFinalized` — which requires the honest manager to push the vault through a borrower default flow.

There is no user-facing or admin-facing path to reduce `apr0TotalPrincipal` otherwise. The attacker's own `requestWithdraw` while `unscaledApr != 0` goes to the normal bucket (line 287-294) and never touches `apr0TotalPrincipal`. So once the guard trips, the revert is permanent: `stopEpoch` can never succeed, `epochNumber` never increments, `lastWithdrawRequest` gating keeps all pending withdrawals unclaimable (`_claimFundedWithdrawRequest` reverts when `epochNumber <= lastWithdrawRequest[_user]`, line 326), and the borrower's funds plus all pending receipts are frozen.

Existing guards do not stop this: KYC/`isWalletAllowed` admits the attacker (a normal lender), `_onlyIdleCDO` is satisfied because the request flows through the CDO, and the `setApr`/`setAprsWithBuffer` call that triggers the condition is a legitimate manager/CDO action, not attacker-controlled abuse of a privileged role.

### Impact Explanation
Permanent freezing of all vault funds and unclaimed yield: the epoch can never be stopped, no new epoch can start, pending withdraw and instant-withdraw receipts can never be claimed (their epoch-wait check can never be satisfied), and scheduled borrower repayment accounting halts. The attacker spends only a dust withdraw request (near-zero cost); the frozen amount equals the entire pool NAV plus pending receipts. This satisfies the "permanent freezing" acceptance criterion with quantified loss equal to full vault TVL until owner intervention (owner rescue via `transferToken`/`_emergencyShutdown` would still strand receipt accounting).

### Likelihood Explanation
High, conditional on an APR0-configured epoch. Preconditions: (1) the vault is configured with `unscaledApr == 0` for an epoch (APR0 mode is a supported configuration per `prepareStopEpochWithApr0`), (2) the attacker is a KYC-passing lender holding tranche tokens, which is explicitly in scope. The attacker calls the CDO's withdraw-request path for 1 wei during the APR0 epoch. Later, the manager/CDO updates APR to a non-zero value (a routine action between or within epochs, via `setAprs`/`setAprsWithBuffer`). The very next `stopEpoch` reverts forever. The attacker needs no cooperation from any privileged role beyond a routine APR update that honest managers perform anyway.

### Recommendation
Remove or relax the `unscaledApr != 0` revert in `prepareStopEpochWithApr0`. Options: (a) skip the APR0 pro-rata interest split when `unscaledApr != 0` but still close the bucket (`apr0TotalPrincipal = 0`) so stale APR0 principal cannot wedge the epoch; (b) provide an admin/permissionless escape that migrates `apr0TotalPrincipal` into the normal `pendingWithdraws`/`withdrawsRequests` bucket when APR changes; (c) convert `apr0Users` principal into `withdrawsRequests` at the moment `setApr`/`setAprs` sets a non-zero `unscaledApr`. Any fix must guarantee `apr0TotalPrincipal` is always reclaimable/clearable regardless of the current APR.

### Proof of Concept
Sketch for a Foundry fork test (`test/foundry/`); exact CDO wiring follows existing `IdleCreditVault*` test fixtures:

```solidity
function test_Apr0RevertLocksStopEpoch() public {
    // Setup: IdleCDOEpochVariant + IdleCreditVault, epoch running, unscaledApr == 0.
    // attacker = KYC-passed AA lender holding tranche tokens.

    // 1) Attacker places dust withdraw request during APR0 epoch.
    vm.prank(attacker);
    idleCDO.withdrawAA(1); // routes to IdleCreditVault.requestWithdraw -> _requestWithdrawApr0
    assertEq(creditVault.apr0TotalPrincipal(), 1);

    // 2) Honest manager sets a non-zero APR (routine config call).
    vm.prank(manager);
    creditVault.setAprs(5e17, 5e17 * (epochDur + buffer) / epochDur);

    // 3) Every subsequent stopEpoch reverts -> permanent freeze.
    vm.warp(epochEndDate + 1);
    vm.prank(borrower);
    underlying.approve(address(idleCDO), type(uint256).max);
    vm.expectRevert(); // NotAllowed() inside prepareStopEpochWithApr0
    idleCDO.stopEpoch();

    // 4) No non-default path clears apr0TotalPrincipal; receipts stay locked.
    assertEq(creditVault.apr0TotalPrincipal(), 1); // wedged
}
```

Caveat: I verified the revert logic and clearing paths in `IdleCreditVault.sol` directly; I did not read the exact `stopEpoch` call site in `IdleCDOEpochVariant.sol` within the tool budget (grep confirmed `prepareStopEpochWithApr0` is invoked from it), so the PoC must be run to confirm `stopEpoch` calls it unconditionally in the non-prefunded epoch variant.
