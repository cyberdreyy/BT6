### Title
Miner-signature (ECDSA) malleability lets the same block content produce two distinct `signer_signature_hash` values, breaking the "one signed block per (miner, tenure)" equality signers rely on - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`NakamotoBlockHeader::signer_signature_hash_inner()` includes the miner's `miner_signature` bytes in the data that signers sign over, while `miner_signature_hash_inner()` (what the miner itself signs) does **not** depend on the signer signature. Because ECDSA signatures are malleable and the codebase's own recovery routine `recover_to_pubkey_without_validating_low_s` does not reject high-S signatures for miner signatures (confirmed by the test `check_proposal_accepts_high_s_miner_sign` in `stacks-signer/src/chainstate/tests/v2.rs`), a single miner keypair can produce two syntactically different, but semantically identical, valid `miner_signature` values (low-S and its negated/high-S counterpart) for the exact same block body. Since `signer_signature_hash` folds `miner_signature` into its preimage, these two miner-signature variants yield **two different `signer_signature_hash` / `block_id` values for what is otherwise the same block** (same `consensus_hash`, `chain_length`, `parent_block_id`, `tx_merkle_root`, `state_index_root`, `timestamp`, `pox_treatment`).

### Finding Description
`stackslib/src/chainstate/nakamoto/mod.rs`: [1](#0-0) 
shows `signer_signature_hash_inner` explicitly serializes `self.miner_signature` into the preimage that signers sign (`write_next(fd, &self.miner_signature)?;`), whereas `miner_signature_hash_inner` (lines 1008-1024) excludes it (and excludes the signer signature vector entirely). `block_hash()`/`block_id()` are derived from `signer_signature_hash_inner`, so the block's on-chain identity depends on the exact bytes of `miner_signature`.

ECDSA allows two valid signatures `(r, s)` and `(r, n-s)` for the same message and key. Native recovery in `stacks-common/src/util/secp256k1/native.rs`: [2](#0-1) 
only checks low-S when a `verify_low_s` flag is set; `recover_to_pubkey_without_validating_low_s` (used for miner signature recovery in `recover_miner_pk`) does not enforce it. The signer-side test explicitly documents this asymmetry: [3](#0-2) 
"We no longer accept transaction signatures with high S ... but in miner signatures they're still allowed" and shows `check_proposal` returning `Ok(())` for a block whose `miner_signature` was negated (`with_negated_s()`).

A single-slot miner can therefore build two block proposals, `B1` and `B2`, with identical block bodies except that `B1.header.miner_signature` and `B2.header.miner_signature` are the low-S/high-S malleated pair of the same underlying signature. Both `recover_miner_pk()` calls (used in `GlobalStateView::check_proposal`, `stacks-signer/src/chainstate/v2.rs` lines 146-152, and in `v1.rs` lines 221-238) succeed and recover the same, correct `miner_pk`/`miner_pkh`, so both proposals pass the "was this signed by the expected miner" check equally. But `B1.header.signer_signature_hash() != B2.header.signer_signature_hash()` because the differing `miner_signature` bytes are folded into that hash, so they are treated by the signer state machine as **two entirely distinct blocks/proposals** (different `signer_signature_hash`, different `block_id`), even though they represent the same tenure content and the same miner intent.

This breaks the equality that the signer set (and downstream `verify_signer_signatures` weight aggregation in `stackslib/src/chainstate/nakamoto/mod.rs` lines 1096-1190) relies on: that a given miner/tenure/height has *one* canonical block that signers converge on and sign once. A malicious or buggy miner can submit both variants to the signer set (or to different signers/at different times), and standard duplicate/conflict detection in the signer (`Signer::handle_block_signature`, proposal caching keyed by `block_hash`/`signer_signature_hash` in `stacks-signer/src/signerdb.rs`) will not recognize `B1` and `B2` as conflicting/duplicate proposals for the same miner because their signature hashes differ. Each variant can independently accumulate signer weight toward the 70% threshold (`verify_signer_signatures`), risking two independently-signed, fully-valid Nakamoto blocks for the same tenure position — a signing/acceptance equivocation that the one-block-per-height invariant is supposed to prevent.

### Impact Explanation
This qualifies as **Critical** under the stated rubric ("a signer signing an invalid, non-canonical, or conflicting block"): the same underlying tenure content can be independently signed twice by (potentially disjoint) sets of signers because the conflict-detection keys (`signer_signature_hash`) diverge for cosmetically different but semantically identical miner signatures. This can be triggered unilaterally by the one-slot miner (as required by scope) using only standard ECDSA signature malleability (negating `s`), requiring no majority of signers and no key compromise.

### Likelihood Explanation
Likelihood is high given the scope constraints: the miner already controls its own signing key and can trivially compute the malleated (`n - s`) counterpart of any ECDSA signature it produces, with no additional cryptographic difficulty. The codebase's own regression test (`check_proposal_accepts_high_s_miner_sign`) proves the acceptance path for high-S miner signatures is intentionally permitted and exercised, confirming this path is reachable in production logic, not merely theoretical.

### Recommendation
Either (a) exclude `miner_signature` from the `signer_signature_hash` preimage so the signer-facing block identity is invariant to miner-signature malleability, or (b) enforce low-S normalization/canonicalization on `miner_signature` at proposal-ingestion time (the same way transaction signatures already reject high-S), so only one canonical `miner_signature` byte encoding is ever accepted for a given block body, collapsing `B1`/`B2` back into a single canonical `signer_signature_hash`.

### Proof of Concept
1. Miner builds a valid `NakamotoBlock` body and computes `miner_signature = sign(miner_signature_hash())`.
2. Miner computes the malleated counterpart `miner_signature' = (r, n-s)` (equivalent to `with_negated_s()` as shown in the existing test `check_proposal_accepts_high_s_miner_sign`).
3. Miner creates `B1` with `miner_signature` and `B2` (otherwise-identical body) with `miner_signature'`.
4. Both `B1.header.recover_miner_pk()` and `B2.header.recover_miner_pk()` return the same, correct miner public key, so `GlobalStateView::check_proposal` (`stacks-signer/src/chainstate/v2.rs:111-152`) accepts both as valid proposals from the legitimate miner.
5. `B1.header.signer_signature_hash() != B2.header.signer_signature_hash()` (proved by the `signer_signature_hash_inner` implementation embedding `miner_signature` — `stackslib/src/chainstate/nakamoto/mod.rs:1026-1045`), so the two proposals are tracked as independent, non-conflicting entries by the signer, allowing both to independently collect signer weight toward `verify_signer_signatures`'s 70% threshold.         msg: &[u8],
        sig: &MessageSignature,

    ) -> Result<Secp256k1PublicKey, &'static str> {
        _secp256k1.with(|ctx| {
            let msg = LibSecp256k1Message::from_slice(msg).map_err(|_e| {

            })?;

            let secp256k1_sig = sig
                .to_secp256k1_recoverable()
                .ok_or("Invalid signature: failed to decode recoverable signature")?;

            if verify_low_s {
                let secp256k1_sig_standard = secp256k1_sig.to_standard();
                let mut secp256k1_sig_low_s = secp256k1_sig_standard;
                secp256k1_sig_low_s.normalize_s();
                if secp256k1_sig_low_s != secp256k1_sig_standard {
                    return Err("Invalid signature: high-S");
                }
            }

            let recovered_pubkey = ctx
                .recover_ecdsa(&msg, &secp256k1_sig)
                .map_err(|_e| "Invalid signature: failed to recover public key")?;

            Ok(Secp256k1PublicKey {
                key: recovered_pubkey,
                compressed: true,
            })
        })

/// We no longer accept *transaction* signatures with high S (because they cause
/// txid malleability), but in *miner* signatures they're still allowed.

        setup_test_environment(function_name!());
    block.header.consensus_hash = current_sortition.data.consensus_hash;

    block.header.miner_signature = miner_sk
        .sign(block.header.miner_signature_hash().as_bytes())
        .unwrap()
        .with_negated_s();
    assert_eq!(
        sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block),
        Ok(()),
        "should validate"
    );
}
