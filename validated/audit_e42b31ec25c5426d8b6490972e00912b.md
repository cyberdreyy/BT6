### Title
Stale `lastWithdrawRequest` epoch marker: a defaulted-epoch claim erases the pointer to an older loss-adjusted receipt, which is then paid at par instead of the loss price - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.claimWithdrawRequest` processes three receipt classes in sequence (post-default, defaulted-epoch, loss-adjusted, funded-at-par). The loss-adjusted path locates the user's haircutted receipt solely via `lastWithdrawRequest[_user]`, but the defaulted-epoch clearing path (`_clearWithdrawClaimForEpoch`) resets `lastWithdrawRequest[_user]` to 0 whenever it clears the latest epoch's receipt. A user holding both an older loss-adjusted receipt (epoch L) and a newer defaulted receipt (epoch D > L) loses the epoch-L pointer during the same claim call, so the loss receipt falls through to `_claimFundedWithdrawRequest` and is paid at full face value from funded underlyings, stealing `claimBasis * (1 - lossRecoveryPrice)`.

### Finding Description
`requestWithdraw` records per-epoch ownership in `withdrawsRequestsByEpoch[_user][currentEpoch]` and always overwrites the scalar `lastWithdrawRequest[_user] = currentEpoch` (lines 282-293). When a `stopEpoch` underfunds pending receipts, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` (lines 411-421), leaving users to claim `claimBasis * lossRecoveryPrice / RECOVERY_FULL` later via `_claimLossAdjustedWithdrawRequest` (lines 789-800), which keys on `lastWithdrawRequest[_user]`.

On a subsequent default, `finalizeDefaultRecovery` pins `defaultRecoveryEpoch` (line 693). At claim time (lines 301-313):

1. `_claimDefaultedWithdrawRequest` calls `_clearWithdrawClaimForEpoch(_user, defaultEpoch, true)`, which zeroes `withdrawsRequestsByEpoch[user][D]` and decrements the aggregate `withdrawsRequests[user]` — but crucially sets `lastWithdrawRequest[user] = 0` because `lastWithdrawRequest[user] == D` (lines 832-836).
2. `_claimLossAdjustedWithdrawRequest` then reads `lossEpoch = lastWithdrawRequest[user] = 0`; `lossRecoveryPriceByEpoch[0]` is unset (or belongs to a different epoch), so it returns 0 without clearing `withdrawsRequestsByEpoch[user][L]`.
3. `_claimFundedWithdrawRequest` sees `lastWithdrawRequest[user] == 0`, so the epoch-wait guard `epochNumber <= lastWithdrawRequest` passes. `normalAmount = withdrawsRequests[user]` still contains the full epoch-L basis, so the user is paid the entire pre-loss amount at par by `_transferFundedClaim` and burns the receipt 1:1 (lines 338-349).

The mirror of CVE-2021-46958 is exact: a stale snapshot of mutable state (`lastWithdrawRequest`) is invalidated by one ordering path (default-epoch clearing) and then consumed by another (loss-adjusted/funded claim), producing an out-of-invariant payout — the receipt that should be haircut is paid whole.

### Impact Explanation
Direct theft of funded underlyings. The vault only received `claimBasis_L * lossRecoveryPrice` for epoch-L receipts at `collectWithdrawFunds`; paying `claimBasis_L` at par overdraws the strategy balance by `claimBasis_L * (1 - lossRecoveryPrice)`. The `_transferFundedClaim` reserve guard (lines 897-906) only protects `defaultRecoveryReserve`, not other claimants' funded pool or active-LP underlyings, so the excess comes out of other funded receipts/active LP backing — a solvency/fair-payout invariant break. With a 50% loss price and a 100k USDC receipt, the attacker extracts ~50k USDC extra.

### Likelihood Explanation
Requires only an unprivileged KYC'd lender who (a) holds a loss-adjusted receipt from an earlier `stopEpochWithDuration`/partial-funding epoch and deliberately does not claim it, then (b) deposits/requests again so a new request lands in a later epoch that ends in borrower default, then (c) calls `claimWithdrawRequest` after `finalizeDefault`. No privileged misbehavior, no reentrancy, no timing race — one ordinary user transaction order. The only precondition is a partial-loss epoch followed by a default epoch, both plausible credit-vault states.

### Recommendation
In `_claimFundedWithdrawRequest`, iterate/verify each remaining `withdrawsRequestsByEpoch` entry against `lossRecoveryPriceByEpoch` rather than paying the aggregate at par; or, in `_clearWithdrawClaimForEpoch`, only reset `lastWithdrawRequest` when the cleared epoch was the user's *only* outstanding receipt epoch — otherwise leave the oldest outstanding epoch marker. Alternatively make `requestWithdraw` revert when an unclaimed loss-adjusted receipt exists (same policy already enforced post-default via `_hasWithdrawRequest`-style gating).

### Proof of Concept
```solidity
// test/foundry/IdleCreditVaultStaleLossReceipt.t.sol  (fork test sketch)
function testStaleLossReceiptPaidAtParAfterDefault() external {
    address user = makeAddr('attacker');
    uint256 amount = 100_000 * ONE_SCALE;

    // 1) deposit and request withdraw in epoch 0 buffer
    _depositWithUser(user, amount, true);
    vm.prank(user);
    uint256 lossBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 2) epoch 0 ends with partial funding -> lossRecoveryPriceByEpoch[0] = 50%
    _startEpochAndCheckPrices(0);
    uint256 funded = lossBasis / 2;
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpoch(funded, initialProvidedApr);   // loss-adjusted stop
    // user does NOT claim: withdrawsRequestsByEpoch[user][0] stays set

    // 3) deposit again and request withdraw in epoch 1 buffer -> lastWithdrawRequest = 1
    _depositWithUser(user, amount, true);
    vm.prank(user);
    uint256 defaultBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 4) epoch 1 ends in borrower default, recovery finalized
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    _checkDefault();
    uint256 recovered = /* defaultPendingClaimBasis-scaled recovery */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // 5) single claim: epoch-1 receipt cleared (lastWithdrawRequest -> 0),
    //    loss path sees epoch 0 pointer erased, funded path pays epoch-0
    //    receipt at PAR instead of at 50% loss price.
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = IERC20Detailed(defaultUnderlying).balanceOf(user) - balPre;

    // Expected fair payout:
    uint256 fair = lossBasis / 2
                 + defaultBasis * strategy.defaultRecoveryPrice() / strategy.RECOVERY_FULL();
    assertGt(got, fair + lossBasis / 4);   // user stole the loss share
}
```
