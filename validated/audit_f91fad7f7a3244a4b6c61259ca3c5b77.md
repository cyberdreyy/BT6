### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` only compares the size of a request's stored `confirmations` set to `num_confirmations`; it never checks that the accounts/keys recorded in that set are still current members. `delete_member()` only purges requests *created by* the removed member, not confirmations that member previously cast on *other* members' requests. A confirmation cast by a member before removal therefore keeps counting toward the approval threshold after that member is no longer part of the multisig, exactly mirroring the reported class of bug where a previously-recorded value is trusted without re-validating it against the current, live source of truth.

### Finding Description
`confirm()` computes eligibility purely from set cardinality: [1](#0-0) 

`delete_member()` only cleans up requests where the removed member is the request's creator (`r.member == member`); it does not scan `self.confirmations` for entries elsewhere that include the removed member's identity: [2](#0-1) 

`assert_valid_request()` similarly never re-validates the confirmers stored in `self.confirmations`, only that the caller is currently a member and that the request/confirmation records exist: [3](#0-2) 

Sequence:
1. Members Alice, Bob, Carol, `num_confirmations = 2`.
2. Bob creates request `R1` (e.g. `Transfer` funds to some receiver) via `add_request`.
3. Alice confirms `R1` (`confirmations(R1) = {Alice}`), which is below threshold, so it stays pending: [4](#0-3) 
4. The multisig later executes a separate `DeleteMember { member: Alice }` request to remove Alice (e.g., because her key is rotated/compromised or she leaves). `delete_member` removes Alice from `self.members` but does not touch `confirmations(R1)`, which still contains Alice's identity.
5. Bob confirms `R1`. `confirmations.len()==1 (stale Alice) + 1 (Bob) == 2 >= num_confirmations`, so `R1` executes — even though only one *currently live* member (Bob) actually approved it after Alice's removal.

This breaks the equality the contract is supposed to enforce: `count(confirmations that are current members) == num_confirmations` before execution. Instead it enforces `count(confirmations ever recorded, including now-removed members) == num_confirmations`, which is the same class of flaw as the reported issue — trusting stored data that was never re-bound/re-verified against the authoritative present-state before being used to authorize a privileged action.

### Impact Explanation
This is a Critical-tier break under the stated rules: "a multisig request executed below threshold." Any privileged action reachable via a `MultiSigRequest` (`Transfer`, `DeployContract`, `AddKey`, `AddMember`, `DeleteMember`, `FunctionCall`, etc.) can be executed with fewer currently-authorized approvers than `num_confirmations` mandates, as long as a pending request happens to carry a confirmation from a member who is later removed. In the worst case this allows fund transfers or full-access key additions to be pushed through with effectively one fewer live approver than the configured threshold, undermining the entire purpose of the multisig's k-of-n authorization model.

### Likelihood Explanation
No privileged capability beyond normal, already-supported multisig operations is required: creating requests, confirming them, and removing members via `DeleteMember` are all standard flows of this contract. Any organization that rotates or removes multisig members while requests are in flight (a routine operational event, e.g., an employee offboarding or key rotation) is exposed. No victim key compromise, redeploy, or social engineering is needed — only ordinary sequencing of pending requests around a member-removal event.

### Recommendation
When counting confirmations in `confirm()` (and when deciding execution eligibility generally), filter `confirmations` against the current `self.members` set, e.g. `confirmations.iter().filter(|m| self.members.contains(m)).count()`, or proactively purge a departing member's confirmations from *all* pending requests (not just requests they created) inside `delete_member()`.

### Proof of Concept
```
// members: Alice, Bob, Carol; num_confirmations = 2
let request_id = contract.add_request(transfer_to_attacker); // created by Bob
// Alice confirms while still a member
set_signer(alice_key); contract.confirm(request_id); // confirmations = {Alice}, 1 < 2, pending

// Multisig later removes Alice via a separate DeleteMember request/confirm flow
set_signer(bob_key); contract.confirm(delete_alice_request_id); // Alice removed from self.members
// self.confirmations[request_id] still contains "Alice" — delete_member() never purged it

// Bob confirms the original transfer request
set_signer(bob_key); contract.confirm(request_id);
// confirmations.len() (1, stale Alice) + 1 (Bob) == 2 >= num_confirmations(2) -> executes
// Result: funds transferred with only 1 live-member approval instead of the required 2

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
