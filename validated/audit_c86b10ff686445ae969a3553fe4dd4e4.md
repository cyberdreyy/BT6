### Title
Equivocation-guard freshness check uses strict `>` at the exact timeout boundary, allowing a signer to sign a conflicting block one second early - (File: stacks-signer/src/v0/signer.rs)

### Summary
When a signer reaches the pre-commit threshold for a block, it re-checks whether it has recently signed/accepted a *conflicting* block at the same or higher chain height before actually placing its signature. "Recently" is defined by a `freshness_cutoff = now - tenure_last_block_proposal_timeout`, and a prior conflicting signature only still blocks if `conflict.last_endorsed > freshness_cutoff`. Because this is a strict inequality, a conflict whose `last_endorsed` timestamp is *exactly equal* to `freshness_cutoff` (i.e. exactly `tenure_last_block_proposal_timeout` seconds old, which happens at the natural second-granularity boundary of the timeout) is treated as stale and no longer blocks, even though the timeout window as configured/intended should still cover it.

The comment at lines 1368-1382 explicitly documents the intent: "a signature must not be superseded while it's still 'fresh'". The freshness test is `conflict.last_endorsed > freshness_cutoff`. Since both `get_epoch_time_secs()` and the stored `last_endorsed` are second-granularity, the case `conflict.last_endorsed == freshness_cutoff` — i.e. a previously signed conflicting block whose endorsement is exactly `tenure_last_block_proposal_timeout` seconds old — falls outside the "fresh" bucket due to the strict `>`. This is the same class of bug as the referenced report: a boundary value that should still count as valid/blocking is excluded because of a strict rather than inclusive comparison.

If this equality case is hit, the `find` in lines 1403-1411 returns `None` for that conflict, the early return at line 1420 is skipped, and execution falls through to the second conflict-resolution block (lines 1432 onward), which only re-blocks signing if the *node's* canonical tenure tip is already at or above the proposed height. If the node hasn't yet incorporated the previously-signed conflicting block (plausible, since it may still be propagating/being validated), the signer proceeds to sign the new, conflicting block — i.e., the signer ends up holding two live signatures over conflicting blocks at the same/higher chain height, directly undermining the one-signature-per-height equivocation guard that this exact code path exists to enforce.

### Impact Explanation
This breaks a core signer safety invariant: it can cause "a signer signing an invalid, non-canonical, or conflicting block" (the report's Critical impact category). The guard's entire purpose (per the code's own comments) is to prevent a signer from ratifying two competing blocks at the same height; a boundary miscomparison directly defeats that purpose for conflicts landing exactly on the second boundary of the timeout window.

### Likelihood Explanation
The trigger condition only requires natural timing (or an adversarial miner/proposer racing a second competing proposal to land at the precise second boundary of `tenure_last_block_proposal_timeout` after the first was endorsed) — no majority of signers, no other signer's key, and no privileged access is required. Because timestamps here are second-granularity rather than sub-second, hitting the exact equality is a realistic, narrow-but-reachable timing window rather than a probability-zero edge case, and a motivated single miner has some influence over proposal timing to attempt to land in this window.

### Recommendation
Change the comparison from `conflict.last_endorsed > freshness_cutoff` to `conflict.last_endorsed >= freshness_cutoff` (equivalently, treat the conflict as fresh when its age is `<= tenure_last_block_proposal_timeout`) so blocks exactly at the timeout boundary remain covered by the equivocation guard, consistent with the documented intent.

### Proof of Concept
1. Signer S validates and signs block `B1` at height `H` in tenure `T1`; the corresponding `last_endorsed` is recorded in `signerdb` at time `t0`.
2. A competing block `B2` at height `H` (different tenure or same tenure) is proposed and reaches the pre-commit threshold at time `t0 + tenure_last_block_proposal_timeout` exactly (attacker/miner can bias proposal timing toward this).
3. At `check_block_against_signer_db_state`/pre-commit handling time, `freshness_cutoff = now - tenure_last_block_proposal_timeout = t0`, and `conflict.last_endorsed == t0`, so `conflict.last_endorsed > freshness_cutoff` is `false`.
4. The conflict is excluded from the "fresh" set; if the node's tenure tip for `B1`'s tenure has not yet reached height `H` (e.g., `B1` hasn't finished propagating/validation on the node), the second check at lines 1432-1457 also does not block, and signer S proceeds to sign `B2`, producing two valid signatures over conflicting blocks at height `H`.
