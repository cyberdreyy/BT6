## Summary

`staking_contract.move`'s `distribute_internal` pays out **all** shareholders of a staking contract's `distribution_pool` (the staker and the operator/beneficiary) in a single atomic loop that calls `aptos_account::deposit_coins` for each recipient in turn [1](#0-0) . `aptos_account::deposit_coins` can abort for a recipient that has opted out of unregistered/direct coin transfers via `DirectTransferConfig` [2](#0-1) [3](#0-2) . Because `distribute_internal` is a single Move transaction, one recipient toggling this unprivileged, self-controlled setting causes the **entire distribution to revert every time**, permanently blocking the counterparty's (the other party in the 2-party staking contract) payout — a direct structural analog to the Cardex nonce-blocking bug: one participant's own inaction/action prevents another legitimate participant from ever completing their claim.

## Finding Description

`distribute_internal` is invoked not only by the permissionless `distribute()` entry function [4](#0-3) , but is also forced to run first inside `unlock_stake` and `request_commission`-triggering flows, meaning the staker cannot withdraw and the operator cannot claim commission without going through the same shared payout loop [5](#0-4) .

Inside `distribute_internal`, the function withdraws all inactive/pending_inactive stake up front, then iterates `distribution_pool.shareholders()` and calls `aptos_account::deposit_coins` for each shareholder, sending the operator's commission to `beneficiary_for_operator(operator)`:

```
while (distribution_pool.shareholders_count() > 0) {
    let recipients = distribution_pool.shareholders();
    let recipient = recipients[0];
    ...
    aptos_account::deposit_coins(recipient, coin::extract(&mut coins, amount_to_distribute));
    ...
};
``` [1](#0-0) 

`aptos_account::deposit_coins` will abort with a permission-denied error if the target account has not registered the coin type and has disabled arbitrary/direct coin transfers, a setting any account owner can toggle for themselves at will via the `DirectTransferConfig` resource [6](#0-5) . Because the whole loop runs inside one atomic transaction, an abort at any single recipient rolls back the entire `distribute_internal` call — including the withdrawal that had already unlocked stake from the stake pool.

Since a `StakingContract` (and its `distribution_pool`) only ever has two possible payees — the staker and the operator/beneficiary — either side can unilaterally and permanently prevent the other side from ever collecting funds already unlocked and waiting in the distribution pool, simply by disabling direct coin transfers on their own account (or never registering for `AptosCoin`, though `AptosCoin` is typically auto-registered; the same mechanism applies more generally to any account that becomes unable to accept the deposit, e.g. is deleted/reset). This mirrors the report's root cause exactly: a party who controls only their own state (the "next in line" position) can indefinitely halt a shared, sequential payout process affecting a different party's already-earned claim.

## Impact Explanation

This breaks the "Accounting across active/pending_inactive/inactive/rewards/commission state must preserve value and withdrawal rights" invariant and the "beneficiary-update paths must not... strand it permanently" pivot. A staker (or operator) can grief the counterparty out of already-unlocked commission or stake withdrawal by disabling direct coin transfers on their own account, since `distribute()`, `unlock_stake()`, and commission-request flows will perpetually abort for both parties until the offending account re-enables transfers or registers the coin. This is a permanent, non-recoverable stranding of a **legitimate counterparty's claim right** (operator commission or staker withdrawal) — matching the required impact category "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows."

## Likelihood Explanation

Likelihood is Medium: toggling `DirectTransferConfig` is a normal, unprivileged, single-transaction action any account holder can perform on themselves, requiring no special setup, and can be done either maliciously (to grief a counterparty during a dispute over commission) or accidentally (a user who disabled unregistered transfers for wallet-hygiene reasons, unaware they had an active `StakingContract`).

## Recommendation

`distribute_internal` should not let one recipient's deposit failure block the payout to all other recipients: iterate defensively (e.g., skip failed deposits and re-buy failed amounts back into the distribution pool, or push to a per-recipient escrow) rather than aborting the whole function, and/or use a transfer path that always succeeds without requiring `DirectTransferConfig` opt-in (e.g., register the coin store for the recipient inside `distribute_internal` unconditionally rather than deferring to `aptos_account::deposit_coins`'s opt-in check), so that one party's account configuration cannot hold another party's already-earned funds hostage.

## Proof of Concept

1. Staker `S` creates a staking contract with operator `O` via `create_staking_contract`, stake accrues rewards.
2. `O` calls `disable_direct_coin_transfers` (implemented on top of `DirectTransferConfig`) on their own beneficiary/operator account (or the `BeneficiaryForOperator` address is never registered for `AptosCoin`) — an entirely unprivileged, self-directed action.
3. `S` calls `unlock_stake` to withdraw part of their principal; internally this calls `distribute_internal`, which withdraws inactive stake and then attempts `aptos_account::deposit_coins` to `O`'s beneficiary for the pending commission share, which aborts.
4. The entire transaction reverts: `S`'s own withdrawal (already unlocked/inactive stake sitting in the distribution pool) can never be distributed either, since every future call to `distribute()`, `unlock_stake()`, or `request_commission()` re-enters the same failing loop.
5. Both `S`'s and `O`'s already-unlocked funds remain permanently stuck in the `distribution_pool` until `O` reverses their `DirectTransferConfig` setting — something `S` cannot force.

Note: I was not able to fully view the remainder of `aptos_account::deposit_coins` (the file's initial lines and the exact abort code path are truncated in the indexed content), so the exact revert condition (opt-out via `DirectTransferConfig` vs. un-registered coin store) should be re-verified directly against the full `aptos_account.move` source before treating this as final; the core structural flaw — a single shared atomic payout loop with no per-recipient failure isolation in `staking_contract::distribute_internal` — is confirmed from the visible code.

    ) acquires Store, BeneficiaryForOperator {
        // Short-circuit if amount is 0.
        if (amount == 0) return;

        let staker_address = signer::address_of(staker);
        assert_staking_contract_exists(staker_address, operator);

        let store = borrow_global_mut<Store>(staker_address);
        let staking_contract = store.staking_contracts.borrow_mut(&operator);
