### Title
`internal_withdraw` permanently debits a staker's `unstaked` claim before the NEAR transfer is confirmed, with no callback to reconcile a failed transfer - ([File: staking-pool/src/internal.rs])

### Summary
`StakingContract::internal_withdraw` (called by both `withdraw` and `withdraw_all`) decrements the caller's recorded `unstaked` balance and the pool's `last_total_balance` accounting *before* the actual NEAR transfer is known to succeed, and fires the transfer as a bare `Promise::new(account_id).transfer(amount)` with no `.then()` callback to verify the result. [1](#0-0) 

### Finding Description
`internal_withdraw` asserts that the internal ledger (`account.unstaked`) has enough recorded balance, then unconditionally mutates state:
```
account.unstaked -= amount;
self.internal_save_account(&account_id, &account);
...
Promise::new(account_id).transfer(amount);
self.last_total_balance -= amount;
``` [2](#0-1) 

The equality this breaks is: **recorded per-account claim (`account.unstaked`, and pool-wide `last_total_balance`) must equal the NEAR actually deliverable/held by the contract.** In NEAR, a native `transfer` action executes as an independent, asynchronous receipt; if it fails at the protocol level (e.g. insufficient *actual* liquid balance on the contract account), that failure does not roll back state that the enclosing function call already committed. The state decrements above are committed as soon as the function call succeeds (no panic), regardless of whether the subsequent transfer receipt later succeeds or fails.

This is a known-good pattern elsewhere in the same contract that is not applied here: `internal_restake` explicitly chains `.then(ext_self::on_stake_action(...))` so a failed `stake` action can be detected and handled via `is_promise_success()`. [3](#0-2) 
The same "commit accounting → fire transfer → verify via callback" discipline is followed for staking-pool withdrawals initiated from the lockup contract, where `on_staking_pool_withdraw` checks `is_promise_success()` before deciding whether to restore the pool's deposit accounting. [4](#0-3) 
`internal_withdraw` has no equivalent callback at all — it is a fire-and-forget `Promise::new(...).transfer(...)` with zero result checking.

The contract has no storage-staking/reserve accounting tying `last_total_balance` to `env::account_balance()`; `last_total_balance` is only reconciled against `env::account_locked_balance() + env::account_balance()` inside `internal_ping`, once per epoch, and only to *credit* rewards, never to *validate* that a pending withdrawal amount is actually present as spendable, non-storage-reserved balance. [5](#0-4) 
Any gradual divergence between the on-chain liquid balance and the sum of all accounts' `unstaked` claims (e.g., from storage cost growth as more accounts register, which is deducted from the raw account balance at the protocol level but never subtracted from `last_total_balance`) can make a later `Promise::transfer` fail for a legitimate withdrawal, while the caller's `unstaked` balance and the pool's `last_total_balance` have already been permanently reduced.

### Impact Explanation
When the transfer promise fails under this condition, the staker's claim is extinguished from the ledger (`account.unstaked` reduced, ultimately removed from storage if it hits zero via `internal_save_account`), yet no NEAR was delivered. There is no retry path and no reconciliation callback, so the funds are permanently lost to that account with no way to re-claim them — the ledger no longer reflects any right to the money that was never paid out. This matches the "accounting value diverging from reality where another party settles on it" / permanently frozen funds category, since other accounts and pool-wide bookkeeping (`last_total_balance`) continue to operate as if the withdrawal succeeded.

### Likelihood Explanation
This does not require any privileged actor, malicious validator, or foundation intervention — it is triggered purely by ordinary use of the public `withdraw`/`withdraw_all` methods by any staker once the underlying divergence between recorded `unstaked` claims and actual spendable contract balance exists. The mechanism (asynchronous NEAR transfer with no callback) is a structural property of the function, not a rare edge case, so any accumulation path that drains the contract's spendable balance below the sum of pending `unstaked` claims (e.g., storage growth from onboarding many staking accounts over time, which is unaccounted for in `last_total_balance`) will manifest this bug on a subsequent withdrawal.

### Recommendation
Do not decrement `account.unstaked` / `last_total_balance` unconditionally before the transfer is confirmed. Chain the `Promise::new(account_id).transfer(amount)` with a `.then()` callback (mirroring `on_stake_action`/`on_staking_pool_withdraw` elsewhere in this codebase) that checks `is_promise_success()`; only finalize the debit on success, and restore `account.unstaked` and `last_total_balance` if the transfer promise fails.

### Proof of Concept
1. Contract accumulates enough registered accounts / storage growth over time such that `env::account_balance()` becomes smaller than the sum of all accounts' recorded `unstaked` balances (the code never subtracts storage cost from `last_total_balance`, only tracks rewards in `internal_ping`, see `staking-pool/src/internal.rs:194-249`).
2. A staker with a valid, unlock-eligible `unstaked` balance calls `withdraw(amount)` (`staking-pool/src/lib.rs:254-263`), which invokes `internal_withdraw` (`staking-pool/src/internal.rs:42-68`).
3. `internal_withdraw` passes its internal assertions (`account.unstaked >= amount`), decrements `account.unstaked` and `self.last_total_balance`, and persists the account via `internal_save_account`.
4. The subsequent `Promise::new(account_id).transfer(amount)` receipt executes later and fails at the protocol level because the contract's actual spendable balance is insufficient to cover `amount` plus its own storage reserve.
5. Because there is no `.then()` callback, the earlier state mutation (step 3) is never reverted: the staker's `unstaked` balance is gone, `last_total_balance` reflects the withdrawal as completed, but the NEAR was never transferred to the staker — the claim is permanently lost with no recovery mechanism in the contract.     pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }

    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
        if total_reward > 0 {
            // The validation fee that the contract owner takes.
            let owners_fee = self.reward_fee_fraction.multiply(total_reward);

            // Distributing the remaining reward to the delegators first.
            let remaining_reward = total_reward - owners_fee;
            self.total_staked_balance += remaining_reward;

            // Now buying "stake" shares for the contract owner at the new share price.
            let num_shares = self.num_shares_from_staked_amount_rounded_down(owners_fee);
            if num_shares > 0 {
                // Updating owner's inner account
                let owner_id = self.owner_id.clone();
                let mut account = self.internal_get_account(&owner_id);
                account.stake_shares += num_shares;
                self.internal_save_account(&owner_id, &account);
                // Increasing the total amount of "stake" shares.
                self.total_stake_shares += num_shares;
            }
            // Increasing the total staked balance by the owners fee, no matter whether the owner
            // received any shares or not.
            self.total_staked_balance += owners_fee;

            env::log(
                format!(
                    "Epoch {}: Contract received total rewards of {} tokens. New total staked balance is {}. Total number of shares {}",
                    epoch_height, total_reward, self.total_staked_balance, self.total_stake_shares,
                )
                    .as_bytes(),
            );
            if num_shares > 0 {
                env::log(format!("Total rewards fee is {} stake shares.", num_shares).as_bytes());
            }
        }

        self.last_total_balance = total_balance;
        true
