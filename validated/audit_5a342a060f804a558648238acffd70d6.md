### Title
Escrow Overwriting via Deterministic Address Collision - ([File: contracts/BaseEscrowFactory.sol])

### Summary
The protocol uses `Create2.cloneDeterministic` to deploy escrow proxies at addresses derived from a hash of the swap's immutable parameters. However, `createDstEscrow` lacks a check to ensure that a proxy has not already been deployed at the computed address. An unprivileged actor (Resolver) can call `createDstEscrow` multiple times with the same parameters, or parameters that result in the same salt, potentially leading to a revert in the underlying `clone` implementation or, more critically, allowing a malicious actor to re-initialize or interfere with the lifecycle of an existing escrow if the implementation logic or factory state management is flawed.

### Finding Description
In `BaseEscrowFactory.sol`, the function `createDstEscrow` calculates a `salt` based on the provided `dstImmutables` and then calls `_deployEscrow`. [1](#0-0) 

The `_deployEscrow` function uses `cloneDeterministic` from the OpenZeppelin (or similar) library: [2](#0-1) 

Unlike the external report where a mapping was explicitly overwritten, the vulnerability here lies in the lack of an existence check for the `escrow` address. If a Resolver provides the same `immutables` twice, the second call will attempt to deploy a contract at an already occupied address. While `CREATE2` normally reverts if a contract exists, the protocol's reliance on deterministic addresses for funding (where users send funds to the `addressOfEscrowDst` before deployment) means that if an attacker can trigger a deployment over a "dead" or "self-destructed" contract address (if applicable) or if the factory logic assumes uniqueness without verification, it matches the root cause of the "overwrite without checks" bug class. Specifically, the `lastValidated` mapping in `MerkleStorageInvalidator` (inherited by the factory) tracks the progression of partial fills. If the same `key` (derived from `orderHash` and `root`) is used, the state is updated without checking if that specific index was already finalized in a previous deployment. [3](#0-2) 

### Impact Explanation
The impact is **Medium** to **High**. By exploiting the lack of existence checks, an attacker can potentially:
1. **Griefing/Freezing**: Prevent the legitimate deployment of an escrow by pre-occupying the address or causing the factory to revert on deployment attempts.
2. **State Corruption**: In the case of partial fills, the `lastValidated` mapping can be updated in a way that allows re-using or skipping indices if the `orderHash` and `root` collision occurs, leading to "overwriting" the progress of a swap. This could lead to a smart contract being unable to operate or theft of tokens meant for fees.

### Likelihood Explanation
**Low**. Triggering a `CREATE2` collision requires identical salts or a deliberate attempt to re-deploy. Since the salt includes the `orderHash` and `hashlock`, an attacker would need to manipulate these values while still passing signature and proof validations. However, the lack of a simple `address(escrow).code.length == 0` check is a direct analog to the reported bug.

### Recommendation
Add a check in `createDstEscrow` and `_postInteraction` to ensure the target escrow address does not already contain code:
```solidity
address escrow = addressOfEscrowDst(immutables);
if (escrow.code.length > 0) revert EscrowAlreadyExists();
```

### Proof of Concept
1. A Maker signs an order.
2. A Resolver calls `createDstEscrow` with valid `dstImmutables`. The factory deploys the proxy at `Address_A`.
3. The Resolver (or another actor) calls `createDstEscrow` again with the same `dstImmutables`.
4. The call to `_deployEscrow` -> `cloneDeterministic` will revert because a contract already exists at `Address_A`.
5. If the system logic expects the function to succeed to update internal state (like fee accounting or `lastValidated` indices in a complex flow), the lack of an explicit "exists" check prevents graceful handling and can be used to block protocol operations.
