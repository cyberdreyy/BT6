### Title
Direct underlying donation inflates tranche price and steals subsequent depositors' funds via first-depositor attack - (File: contracts/IdleCDO.sol)

### Summary
`IdleCDO._deposit` mints tranche tokens at the stored tranche price after `_updateAccounting()` folds the contract's *entire* raw underlying balance into NAV via `getContractValue()`. An attacker who is the first depositor can seed the pool with 1 wei, donate a large amount of `token` directly to the CDO, let the donation be crystallized as a gain on their single share, and cause the next depositor to mint ~0 shares while their deposited funds accrue to the attacker. This is the same donation-based share-inflation class as the ClaggAaveAdapter report. The `_skimDonatedAssets()` guard exists only on the privileged `updateAccounting()`/`finalizeDefault()` paths in `IdleCDOEpochVariant.sol`, not on the user-facing `_deposit` path, so the attack is unmitigated.

### Finding Description
`getContractValue()` computes NAV as `strategyTokens * price + _contractTokenBalance(token) - lockedRewards - unclaimedFees` (`IdleCDO.sol:183-186`), so any underlying token directly transferred to the CDO is counted as NAV. In `_deposit`, `_updateAccounting()` runs *before* minting and records `nav - lastNAV` as tranche gain, updating `lastNAVAA`/`lastNAVBB` and `priceAA`/`priceBB` (`IdleCDO.sol:273-311`). Shares are then minted at the now-inflated saved price: `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` (`IdleCDO.sol:437-440`), with no minimum-shares check and no dead-share offset. There is no ERC4626-style virtual-share defense and no donation skimming on the deposit path; `_skimDonatedAssets()` is only invoked in the owner/guardian `updateAccounting()` and `finalizeDefault()` (`IdleCDOEpochVariant.sol:157-161, 194-199`). In `IdleCDOCreditVault`, when a tranche has `trancheSupply == 0` the price is `oneToken`, so the attacker's first 1-wei deposit always mints at 1:1 regardless of donations; the donation must therefore be crystallized *after* the attacker already holds shares, i.e., on the victim's deposit call.

### Impact Explanation
Direct theft of user deposits. On a fresh or empty tranche (e.g., buffer phase before `startEpoch`, or after all holders withdrew):

1. Attacker (a KYC-passing lender — `isWalletAllowed` only gates *who* can deposit, not first-deposit size) calls `depositAA(1 wei)`; `priceAA == oneToken`, so they get 1 tranche token and `lastNAVAA = 1`.
2. Attacker `transfer`s `100e18` underlying directly to the CDO contract.
3. Victim calls `depositAA(10e18)`. `_updateAccounting()` sees `nav = 100e18 + 1` vs `lastNAV = 1`, books `~100e18` as gain (minus `fee`), sets `lastNAVAA ≈ 100e18+1` and `priceAA ≈ 100e18 * ONE_TRANCHE_TOKEN`.
4. The victim mints `10e18 * ONE / priceAA` → rounds down to ~0 shares, while `_mintShares` adds their `10e18` to `lastNAVAA` (`IdleCDO.sol:448-456`). The victim's deposit is owned by the attacker's single share.
5. Attacker calls `withdrawAA(0)` and redeems `~110e18` for 1 share, profiting `~10e18` minus the donation cost basis, repeatable per victim.

Broken invariant: fair mint/burn — shares no longer represent pro-rata NAV claims.

### Likelihood Explanation
Requires being the first (or only) depositor of a tranche and a capital-intensive donation (~10× the victim deposit to zero out minted shares). Epoch-based credit vaults (`IdleCDOCreditVault`) reset conditions each pool lifecycle and allow deposits during buffer phase, so fresh deployments are a realistic window; Lender deposits are KYC-gated but attackers are permitted to be KYC'd lenders per scope rules. The donation costs the attacker roughly the victim's deposit amount (they recover it plus the victim's funds), so net profitability exists whenever a victim deposit arrives before anyone else re-deposits at the inflated price — the attack is self-profiting rather than purely griefing since the attacker captures nearly all deposited value, and the donation itself is recoverable through their share. High capital requirement but deterministic payoff; medium likelihood.

### Recommendation
Apply the standard defense on the minting path:
- Mint a minimum amount of "dead" shares (e.g., burn `1e4–1e6` tranche tokens to `address(0)`/`address(1)` and add equivalent NAV) on the first deposit of each tranche, or track an internal `totalAssets`/virtual offset instead of deriving NAV from raw `_contractTokenBalance(token)`.
- Additionally, skim donated underlying in `_deposit`/`_updateAccounting` (extend `_skimDonatedAssets()` to the user-facing path), or track an internal `unlentBalance` counter incremented only through `deposit`/`withdraw`/`harvest` flows rather than using the raw token balance.
- Revert deposits that would mint 0 shares (`_checkIs0(_minted)`).

### Proof of Concept
Foundry fork PoC outline (concrete deploy code depends on repo test harness; not fully verified end-to-end):

```solidity
// Setup: deploy IdleCDOCreditVault (or IdleCDO) with attacker as KYC'd lender
address attacker; address victim; // both pass isWalletAllowed

// 1. Buffer phase (epoch not started): attacker first deposit of 1 wei
underlying.mint(attacker, 1);
vm.prank(attacker);
cdo.depositAA(1); // mints 1 tranche token, priceAA = 1e18

// 2. Donation
uint256 donation = 100e18;
underlying.mint(attacker, donation);
vm.prank(attacker);
underlying.transfer(address(cdo), donation); // raw donation, counts in getContractValue()

// 3. Victim deposit — _updateAccounting crystallizes donation as AA gain
underlying.mint(victim, 10e18);
vm.prank(victim);
uint256 minted = cdo.depositAA(10e18);
assertLt(minted, 1); // ~0 shares minted

// 4. Attacker redeems everything
vm.prank(attacker);
cdo.withdrawAA(0); // redeems ~110e18 - fees for 1 share
```

Uncertainty note: I could not fully verify within the iteration budget whether `IdleCDOCreditVault` overrides `_deposit`/`depositAA` with additional guards (e.g., a skim call or min-shares check) or whether deposits during the buffer phase route underlying to the strategy immediately (`directDeposit`), which would weaken the attack by moving donated tokens out of `_contractTokenBalance(token)` scope — if `directDeposit` pushes the victim's funds (but not the donation, which arrives before) into the strategy, the donation accounting still holds since the donation itself sits in the contract's raw balance until the next deposit. If a deployment path auto-skims donations on every deposit, this finding would reduce to a no-vuln; the `_skimDonatedAssets` calls I confirmed are restricted to privileged functions only.
