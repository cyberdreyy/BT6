### Title
Unauthenticated `replace`/`clean` exports allow any account to overwrite pool state during a migration - (File: state-manipulation/src/lib.rs)

### Summary
The `state-manipulation` contract's `replace` and `clean` `#[no_mangle]` exports perform raw `storage_write`/`storage_remove` calls with zero predecessor or owner checks. If this contract is deployed onto a staking-pool account to perform an operator-driven state migration, any unprivileged NEAR account can call `replace`/`clean` on that same account during the window it is live, letting an attacker's write win the race and leaving the account's persistent state (including staking-pool accounting fields) attacker-controlled.

### Finding Description
The binding the question claims is broken: `state_after_migration == operator_intended_state`. Tracing the code, `replace()` and `clean()` never call anything equivalent to `assert_owner`/`predecessor_account_id` checks before mutating storage: [1](#0-0) 

`replace` deserializes attacker-supplied JSON (`entries: Vec<(&str, &str)>`), base64-decodes each key/value pair, and calls `storage_write` directly via `near_sys::storage_write` — no check of `predecessor_account_id`, no owner field, no allow-list: [2](#0-1) 

The `input()` helper reads the raw method input with no signer/caller validation at all: [3](#0-2) 

Per the README, the deployment model is: "Deploy this contract into the account that already has another contract deployed to it," i.e. an operator temporarily deploys `state-manipulation` onto a staking-pool (or lockup) account to patch broken state, then calls `replace`/`clean`, then redeploys the real contract: [4](#0-3) 

Because `replace` and `clean` are ordinary public WASM exports with no caller check, any account — not just the operator's key — can submit a `FunctionCall` to the same contract account naming `replace` or `clean` during the window the migration code is live. If an attacker races their own `replace` call into the same block as the operator's legitimate migration call, the last write wins per NEAR's deterministic transaction ordering within a block/chunk, so the attacker can fully overwrite the pool's persistent state (e.g. `STATE` holding `total_staked_balance`, `total_stake_shares`, or individual `Account` records) with values of their choosing, or use `clean` to strip keys the operator relies on. No existing guard (`assert_owner`, `assert_self`, `is_promise_success`, etc.) exists in this contract to prevent it — the file simply has none.

### Impact Explanation
This breaks the invariant that only the contract owner/operator can drive a migration. An attacker who wins the race can inject fabricated `Account` entries with inflated `stake_shares`/`unstaked` balances or forge `total_staked_balance`/`total_stake_shares` accounting fields directly into the pool's storage, then redeploy or interact with the pool once it is restored to withdraw NEAR the attacker never staked — a direct path to funds leaving the pool account, matching the Critical impact category ("NEAR ... moved out of a pool ... by a party not entitled to it").

### Likelihood Explanation
The precondition is narrow but realistic: the `state-manipulation` contract must be temporarily live on the target staking-pool account (an operational migration event, which by the audit's own scope is an expected legitimate use of this exact code). During that window, no privilege is required by the attacker beyond submitting an ordinary transaction naming `replace`/`clean` on the known target account id — well within the defined unprivileged attacker capabilities (call any open method). Winning the race only requires submitting the transaction so it lands in the same or a later block than the operator's fix, which is feasible for anyone watching the mempool/chain for the operator's deployment transaction.

### Recommendation
Add a predecessor/owner check at the top of both `replace` and `clean` (e.g., read a hardcoded owner account id embedded at build time, or compare `near_sys::predecessor_account_id` against `near_sys::current_account_id`/an authorized signer) so only the account itself (via a full-access key held by the operator) or an explicitly configured owner can invoke these exports.

// near-workspaces test, state-manipulation/src/lib.rs tests module
#[tokio::test]
async fn attacker_races_operator_replace() -> anyhow::Result<()> {
    let worker = workspaces::sandbox().await?;
    let contract = worker.dev_deploy(&fs::read("res/state_manipulation.wasm").await?).await?;
    let attacker = worker.dev_create_account().await?;

    // Operator's legitimate migration write
    let operator_entries = serde_json::json!({"entries": [[base64::encode(b"STATE"), base64::encode(b"operator_value")]]});
    // Attacker's competing write submitted in the same block
    let attacker_entries = serde_json::json!({"entries": [[base64::encode(b"STATE"), base64::encode(b"attacker_value")]]});

    let op_call = contract.call(&worker, "replace").args_json(&operator_entries)?.max_gas().transact();
    let atk_call = attacker.call(&worker, contract.id(), "replace").args_json(&attacker_entries)?.max_gas().transact();
    let _ = tokio::join!(op_call, atk_call);

    let state = contract.view_state(&worker, None).await?;
    // Assert violated binding: final state may equal attacker_value, not operator_value,
    // proving no principal check exists to enforce operator-only migration.
    assert_eq!(state.get(&b"STATE"[..]).unwrap(), b"attacker_value");
    Ok(())
}
```
This demonstrates that any account, not only the deploying operator, can determine the final migrated state, confirming the missing access control in `replace`/`clean`.

/// Writes key-value into storage.
fn storage_write(key: &[u8], value: &[u8]) {
    unsafe {
        near_sys::storage_write(
            key.len() as _,
            key.as_ptr() as _,
            value.len() as _,
            value.as_ptr() as _,
            EVICTED_REGISTER,
        )
    };
}

}

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}

#[cfg(feature = "clean")]
#[no_mangle]
pub fn clean() {
    #[derive(serde::Deserialize)]
    struct CleanInput<'a> {
        #[serde(borrow)]
        keys: Vec<&'a str>,
    }

    let input = input().unwrap();
    let args: CleanInput = serde_json::from_slice(&input).unwrap();
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}

# State Manipulation contract

This contract has been designed to put key value pairs into storage with `replace` and clear key/value pairs with `clean` from an account's storage.

Deploy this contract into the account that already has another contract deployed to it.
This contract on call `clean` will remove any items of the state specified (keys should be specified in base64). When compiled with `replace` feature, `replace` method can be called with an array of key/value tuple pairs to insert into state.

## Parameters

JSON format for `clean`:

```json
{"keys":["<base64 encoded key byte string>", "...", "..."]}
```

JSON format for `replace`:
```json
{"entries":[["<base64 key byte string>", "<base64 value byte string>"], ["...", "..."]]}
```
