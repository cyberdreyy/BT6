## Finding: Lockup factory lets the caller override the trusted staking‑pool whitelist, letting a lockup owner stake (and thereby release) locked/unvested NEAR through a self‑controlled fake pool

### Summary
The `lockup-factory` contract's `create()` method accepts an optional `whitelist_account_id` parameter supplied by whoever pays to create the lockup, and bakes it into the deployed lockup contract as `staking_pool_whitelist_account_id` instead of always using the factory's own vetted whitelist. Because the lockup contract's `select_staking_pool`/`deposit_and_stake` flow blindly trusts whatever account is configured as the whitelist, and gates staking only on `get_account_balance()` (not on vested/released amount), an attacker can substitute a fake, always‑true whitelist and a self‑controlled fake "staking pool," then move the entire locked/unvested principal into that pool and withdraw it immediately — bypassing the lockup timestamp, release duration and vesting schedule entirely.

### Finding Description
`LockupFactory::create()` is callable by anyone with sufficient attached deposit, and lets the caller choose the whitelist that the newly deployed lockup will trust: [1](#0-0) 

If the caller omits `whitelist_account_id`, the factory's own trusted address is used; if supplied, the attacker‑chosen address is baked verbatim into the lockup's `staking_pool_whitelist_account_id` field with no further validation. This is not an accident of test code — it is an explicitly supported feature, exercised by `test_create_lockup_with_custom_whitelist_success`: [2](#0-1) 

Inside the deployed lockup contract, `select_staking_pool` unconditionally trusts `self.staking_pool_whitelist_account_id` (fixed once at `new()`/init and never re-validated against any canonical NEAR Foundation whitelist): [3](#0-2) 

The callback `on_whitelist_is_whitelisted` accepts the boolean returned by whatever contract sits at that address and immediately records the staking pool as trusted: [4](#0-3) 

Once a pool is "selected," `deposit_to_staking_pool`/`deposit_and_stake`/`stake` only check that `get_account_balance().0 >= amount.0` — i.e., that the lockup account physically holds the NEAR — with no check against the vesting/release schedule (`get_locked_amount`), so the *entire* locked/unvested balance can be transferred out to the "pool": [5](#0-4) 

The binding that should hold is:
`staking_pool_whitelist_account_id == <NEAR Foundation‑controlled whitelist that only lists vetted, non‑custodial staking pool contracts>`

Because `create()` lets the funding caller supply an arbitrary address for this field, the equality is broken: any account can play the role of "the whitelist," and by extension any account can play the role of "a whitelisted staking pool," even though the whole design (see `whitelist/src/lib.rs`, restricted to foundation/whitelisted factories) assumes the whitelist is trustworthy and gate-kept.

### Impact Explanation
This directly maps to the Critical impact class "locked or unvested tokens released early." A lockup contract's entire purpose is to keep NEAR inaccessible until `lockup_timestamp`/`release_duration`/vesting conditions are met. By deploying (or colluding with whoever deploys) the lockup with a malicious whitelist address, the owner can whitelist a staking pool contract they fully control, then `deposit_and_stake` up to the full locked/unvested balance into it. Since the "pool" is attacker code, it can allow instant, unrestricted withdrawal (no unbonding, no fee, no epoch delay), letting the owner recover the funds as liquid NEAR immediately — completely defeating the lockup/vesting schedule that a third party (e.g., an employer or the NEAR Foundation funding an employee grant) relied on when creating the lockup.

### Likelihood Explanation
`create()` has no access control beyond attaching the minimum deposit, and `whitelist_account_id` is an ordinary, publicly documented optional argument — no special privilege, redeploy, or foundation cooperation is required to exploit this. Any party able to call `create()` (which is explicitly designed to be permissionless — "No need to have access to the foundation keys to create lockup," per the factory's own README) can set this parameter.

### Recommendation
Remove the caller‑supplied `whitelist_account_id` override from `LockupFactory::create()` (or restrict it to be settable only by the factory's foundation account), and always deploy new lockups with the factory's own trusted `whitelist_account_id`. If per‑deployment overrides are truly required, require them to be signed off by the `foundation_account_id`, and consider having the lockup contract cross-check the pool against a canonical, foundation‑controlled whitelist address that cannot be substituted at deploy time.

### Proof of Concept
1. Deploy a fake whitelist contract exposing `is_whitelisted(staking_pool_account_id) -> bool` that always returns `true`.
2. Deploy a fake "staking pool" contract you control that accepts `deposit`/`deposit_and_stake` and lets you `withdraw`/`unstake` instantly without restriction.
3. Call `lockup-factory.create` with attached deposit equal to the intended lockup principal, `owner_account_id = <yourself>`, a normal `lockup_duration`/`vesting_schedule`, and `whitelist_account_id = Some(<fake whitelist>)`:
   `lockup-factory/src/lib.rs` lines 107-166 show this parameter flows straight into the deployed lockup's `staking_pool_whitelist_account_id`.
4. As owner, call `select_staking_pool(<fake pool>)`. The lockup calls `is_whitelisted` on the fake whitelist (`lockup/src/owner.rs` lines 12-41), gets `true`, and `on_whitelist_is_whitelisted` (`lockup/src/owner_callbacks.rs` lines 6-25) records the fake pool as the selected staking pool — despite it never having been vetted by the real NEAR Foundation whitelist.
5. Call `deposit_and_stake(<full locked balance>)`. `lockup/src/owner.rs` lines 127-166 only check `get_account_balance() >= amount`, not the vested/released amount, so the whole locked principal is transferred to the fake pool.
6. From the fake pool, immediately call your own `withdraw`/`unstake` logic to return the funds to yourself as liquid NEAR — before `lockup_timestamp`, `release_duration`, or the vesting schedule would have permitted any transfer. [1](#0-0) [3](#0-2) [4](#0-3) [5](#0-4)

    /// Called after a given `staking_pool_account_id` was checked in the whitelist.
    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
        });
        true
    }
