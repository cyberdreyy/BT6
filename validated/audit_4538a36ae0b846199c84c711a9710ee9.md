### Title
Instant-withdraw receipts pay out at par from vault balance without verifying the corresponding borrower funding arrived - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2021-20271 is a "trusted header / unverified payload" bug: RPM accepts a package whose *signature header* verifies while the *package body* was altered, so integrity-critical code executes on data that was never actually validated. The credit-vault analog is `claimInstantWithdrawRequest` in `IdleCreditVault.sol`. The strategy mints a receipt (`instantWithdrawsRequests[_user]`) that functions like a "verified claim header," but the claim path pays out that amount from the contract's underlying balance without checking that the borrower actually funded that specific request. `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` when the CDO pulls money in, but the claim path never compares funded amounts against the receipt being paid — it blindly transfers `instantWithdrawsRequests[_user]` worth of underlying.

### Finding Description
In `requestInstantWithdraw` (lines 356-375), strategy tokens are burned from the CDO and minted 1:1 to the user as a receipt, and `instantWithdrawsRequests[_user]` / `pendingInstantWithdraws` are incremented. Separately, the CDO calls `collectInstantWithdrawFunds` (lines 398-403) to pull funded underlyings from the borrower side into the vault, decrementing `pendingInstantWithdraws`.

`claimInstantWithdrawRequest` (lines 380-393) then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` (lines 897-907) only protects `defaultRecoveryReserve`. There is no check that the borrower's funding leg for this receipt was actually collected — the payout is satisfied from whatever underlying balance the contract currently holds. That balance can legitimately contain funded *normal* withdraw receipts (funded via `collectWithdrawFunds`, line 428), because those are held in the same balance until users call `claimWithdrawRequest`.

So an attacker who holds tranche tokens (a KYC-passing lender) can:
1. Wait until the vault holds funded underlying for normal-receipt claimants after `stopEpoch` (receipts not yet claimed).
2. During `startEpoch` of the next epoch, call `requestWithdraw`/`requestInstantWithdraw` via `IdleCDOEpochVariant`, minting an instant receipt.
3. Call `claimInstantWithdrawRequest()` immediately, before `getInstantWithdrawFunds`/borrower funding for that new request has been collected. The claim pays out the receipt amount from the *previous epoch's* funded reserve meant for other users' normal claims.

The "signature header" (receipt accounting asserting entitlement) is honored while the "payload" (actual borrower funding behind this receipt) was never verified. The guard that would stop this — checking that `pendingInstantWithdraws`-corresponding funding was collected before paying — does not exist; `instantWithdrawsRequests` is zeroed and paid in the same call.

### Impact Explanation
Direct theft of other users' funded withdraw proceeds: an attacker-sized instant claim paid from the funded normal-withdraw balance reduces the vault's balance below what later `claimWithdrawRequest`/`_claimFundedWithdrawRequest` users are owed. Those users' claims then revert on insufficient balance or, after `defaultRecoveryFinalized`, on the reserve guard — a permanent loss of up to the attacker's instant-request size for honest claimants, and a theft for the attacker equal to that amount (bounded by the attacker's tranche NAV).

### Likelihood Explanation
Requires: a running epoch with `allowInstantWithdraw` enabled, funded-but-unclaimed normal receipts in the vault balance, and an attacker with tranche tokens. All are reachable by an unprivileged KYC'd lender; no privileged role is needed. The borrower's honest sequencing (funding instant requests promptly) reduces but does not eliminate the race, since the attacker can claim in the same transaction window as `startEpoch` before funding lands.

### Recommendation
Track funded instant-withdraw amounts explicitly. Either gate `claimInstantWithdrawRequest` so it pays only up to the amount actually collected for that epoch's instant bucket (e.g., decrement a funded counter in `collectInstantWithdrawFunds` and cap claims at `instantWithdrawsRequests[_user]` funded portion), or hold instant-request underlyings in a segregated balance that cannot satisfy claims of a different bucket. At minimum, revert in `claimInstantWithdrawRequest` when `pendingInstantWithdraws` still covers the user's request, so receipts can never be paid from another epoch's funded reserve.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// epoch N: user deposits AA, requests normal withdraw, stopEpoch funds it
uint256 minted = idleCDO.depositAA(10_000e6);
uint256 reqVictim = cdoEpoch.requestWithdraw(0, address(AAtranche));
_startEpochAndCheckPrices(N);
_stopEpochAndCheckPrices(N, apr, expectedFunds); // funds pulled into vault for reqVictim
// victim does NOT claim yet; vault holds underlying >= reqVictim

// epoch N+1 starts; attacker is also a tranche holder
_startEpochAndCheckPrices(N + 1);
// attacker requests instant withdraw of full tranche NAV, then claims in the same block,
// BEFORE manager calls getInstantWithdrawFunds / borrower funds the request
uint256 reqAtk = cdoEpoch.requestInstantWithdraw(0, address(BBtranche));
cdoEpoch.claimInstantWithdrawRequest();
// assertion: attacker received reqAtk underlying drawn from victim's funded balance
assertGt(underlying.balanceOf(attacker) - pre, 0);
// victim's claim now reverts or pays less than reqVictim
```

Caveat: I verified the claim path pays `instantWithdrawsRequests` unconditionally and that funded normal receipts share the same underlying balance; I did not fully trace whether `allowInstantWithdraw` / epoch gating in `IdleCDOEpochVariant` always forces borrower funding before the first claim window — if the CDO collects instant funds atomically inside `startEpoch`, the window shrinks to same-tx ordering around that call. The missing funded-vs-owed check on the claim path remains the concrete gap regardless of how narrow the race is.
