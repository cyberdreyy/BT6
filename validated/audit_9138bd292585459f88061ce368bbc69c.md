### Title
Unvalidated fee parameters in `createDstEscrow` cause guaranteed arithmetic-underflow revert in `EscrowDst._withdraw`, permanently blocking destination withdrawal - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
This is the same root cause as the reported `DVGToken._moveDelegates` bug: a subtraction is performed on values that are not guaranteed to satisfy `minuend >= subtrahend`, with no `require`/`if` guard, so it reverts (in Solidity 0.8, underflow reverts rather than wraps, but the practical effect — an operation that can never succeed — is identical to the reported issue). In `EscrowDst._withdraw`, `immutables.amount - integratorFeeAmount - protocolFeeAmount` (contracts/EscrowDst.sol:92) is computed from fee values taken directly from `immutables.parameters`, which for a destination escrow is fully attacker-controlled calldata supplied to the permissionless `createDstEscrow` entrypoint.

### Finding Description
On the source-escrow path, `BaseEscrowFactory._postInteraction` validates fee amounts before they are ever used: `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();` [1](#0-0) . That check only guards the values encoded into the `DstImmutablesComplement.parameters` emitted in the `SrcEscrowCreated` event — it is off-chain-informational and is never enforced on-chain against the actual destination escrow.

The actual on-chain destination-escrow creation path, `createDstEscrow`, takes the full `dstImmutables` struct — including the `parameters` bytes that encode `protocolFeeAmount`/`integratorFeeAmount`/recipients — directly from the caller with no whitelist and no validation of the fee values against `immutables.amount`: [2](#0-1) .

When withdrawal is later attempted, `EscrowDst._withdraw` decodes these unchecked fee values and subtracts them from `immutables.amount`: [3](#0-2) 

If `integratorFeeAmount + protocolFeeAmount > immutables.amount`, line 92 underflows. Because the contract compiles with checked arithmetic (`pragma solidity 0.8.23`), this reverts unconditionally for every call to `withdraw` and `publicWithdraw`, for the entire lifetime of the escrow up to the `DstCancellation` timelock — there is no `if`/`revert` guard at deployment time to reject such a malformed escrow, exactly the missing-guard pattern described in the external report.

### Impact Explanation
Any unprivileged caller of `createDstEscrow` (an explicitly in-scope entry point per the audit pivots — "destination escrow creation") can lock in fee parameters that make `_withdraw` permanently unreachable for that escrow. This is a public trigger, not a privileged-resolver-only assumption: `createDstEscrow` has no access control beyond depositing the correct native/token amount. The consequence is that the maker can never receive the destination-chain funds during the entire withdrawal window (`withdraw`/`publicWithdraw` both call the same broken `_withdraw`), and thus the secret is never revealed on the destination chain — which in turn blocks the linked `EscrowSrc` withdrawal on the source chain until its own cancellation timelock elapses. This matches the "temporary freezing of funds during the live swap lifecycle" High-severity bucket in the bounty scope: no admin/governance/privileged-resolver-off-chain-trust assumption is needed — the flaw lives entirely in the on-chain lack of validation in `createDstEscrow`.

### Likelihood Explanation
High likelihood: triggering it requires only a single permissionless call to `createDstEscrow` with a `parameters` payload where the encoded fee sum exceeds `amount` — no race condition, no privileged role, and no interaction with off-chain infrastructure is needed. The existing check in `_postInteraction` (`InvalidFeeAmounts`) proves the developers are aware such invariant must hold, but the guard was not replicated on the `createDstEscrow` code path that actually constructs the immutables `_withdraw` relies on.

### Recommendation
Add the same validation performed in `_postInteraction` to `createDstEscrow`: decode `protocolFeeAmount`/`integratorFeeAmount` from `dstImmutables.parameters` and `revert InvalidFeeAmounts()` if `integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount` before deploying the escrow clone, mirroring the existing check at [4](#0-3) .

### Proof of Concept
1. Attacker (any unprivileged address, playing the taker role) calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.amount = 100` and `dstImmutables.parameters = abi.encode(protocolFeeAmount = 60, integratorFeeAmount = 60, protocolFeeRecipient, integratorFeeRecipient)`, sending the correct `msg.value`/token amount so the deployment succeeds (contracts/BaseEscrowFactory.sol:165-185).
2. Once the `DstWithdrawal` timelock stage is reached, the taker (or any access-token holder via `publicWithdraw`) calls `withdraw(secret, immutables)`.
3. Execution reaches `contracts/EscrowDst.sol:92`: `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` → `100 - 60 - 60` underflows and reverts under Solidity 0.8 checked arithmetic.
4. Every subsequent call to `withdraw`/`publicWithdraw` with the same immutables reverts identically — the maker can never receive destination funds; the only remaining path is `cancel()` after `DstCancellation`, which returns the funds only to the taker, freezing the swap and the linked source escrow for its full lifecycle.     function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);

    }
