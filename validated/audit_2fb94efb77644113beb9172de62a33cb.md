### Title
Legacy trigger `MessageId` collision allows cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each user's `Callback` in `h.savedCallbacks` keyed purely by the attacker-supplied `msg.Body.MessageId`, with no check for an existing entry before overwriting it. Because `MessageId` is fully attacker-controlled (bounded only by `MessageIdMaxLen`) and uniqueness is never enforced or namespaced per-sender, a second unprivileged client can submit a request with the same `MessageId` as a still-pending request from a different client, silently discarding the first client's callback and causing the DON's eventual response to be delivered only to the second (attacker) client while the first client's response is dropped/orphaned.

### Finding Description
In `HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421), the message is validated (signature, timestamp, method) but `msg.Body.MessageId` itself is never checked against existing entries in `h.savedCallbacks`. The save happens unconditionally: [1](#0-0) 

`Message.Validate()` (core/services/gateway/api/message.go:54-88) only checks length/format of `MessageId` (non-empty, ≤ `MessageIdMaxLen`, no trailing null byte) — it does not bind `MessageId` to the sender or enforce any uniqueness: [2](#0-1) 

When the DON later responds via `HandleNodeMessage` → `handleWebAPITriggerMessage`, the handler looks up and deletes the callback purely by `MessageId` and invokes whichever callback is currently stored — it has no way to know or verify which original sender that callback belongs to: [3](#0-2) 

Exploit flow: Client A sends a signed `Message{MessageId:"X", DonId:"D"}`; the handler stores A's callback under key `"X"`. Before the DON responds, Client B (a different, unauthenticated signer) sends a signed `Message{MessageId:"X", DonId:"D"}`; the handler overwrites `h.savedCallbacks["X"]` with B's callback, discarding A's without notification. When the DON responds once for MessageId `"X"`, only B's callback fires; A's HTTP request hangs until whatever outer timeout applies and never receives a response (or, if B constructs the request such that its own trigger job produces attacker-influenced payload timing, B could effectively suppress A's flow). This breaks the isolation invariant between unrelated unauthenticated users since nothing binds the stored callback to the sender identity established via signature verification.

### Impact Explanation
This is a cross-user response confusion / request hijacking issue: a low-privilege, unauthenticated caller can cause another unrelated caller's legacy web API trigger response to be dropped and effectively "steal" the response slot for the shared `MessageId`. Impact is availability/integrity of the gateway's HTTP response delivery to legitimate clients (denial of response / hijacked capability response channel), not disclosure of the DON's payload to the attacker (the attacker cannot read victim's payload, only intercept the response intended for the victim's own request keyed on the ID it chose). This is a moderate-severity node-availability/response-hijacking bug appropriate for a "Denial of Service" or "Broken Access Control between users" bounty category depending on classification.

### Likelihood Explanation
The precondition is minimal: any unauthenticated actor able to sign gateway `Message`s (any address holding an ECDSA key valid for signing, no allowlist enforced at this validation stage per the `// TODO: apply allowlist and rate-limiting here` comment at handler.go:384) and able to choose an arbitrary `MessageId` string can trigger the collision. Guessing/predicting another client's in-flight `MessageId` requires the attacker to know or guess the victim's chosen ID; if the ID is generated with sufficient entropy client-side, exploitation requires either coordination or ID enumeration, lowering practical likelihood, but the code contains no defense-in-depth (e.g., no uniqueness check, no per-sender namespacing) even for a lucky/aware attacker.

### Recommendation
Reject (or fail-safe queue) `HandleLegacyUserMessage` requests whose `MessageId` already has a live, unexpired entry in `h.savedCallbacks`, returning an explicit "duplicate message id" error to the second caller instead of overwriting the first entry. Additionally, consider namespacing the map key by `(sender, MessageId)` or by a gateway-generated unique correlation ID rather than trusting a purely client-supplied identifier for callback storage.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct `handler` with a mocked `handlers.DON` (`don.SendToNode` no-op) per existing test helpers in this file.
2. Create two mock `handlers.Callback` instances (`callbackA`, `callbackB`) with `SendResponse` expectations set to detect which one is invoked.
3. Sign `msgA := api.Message{Body: api.MessageBody{MessageId: "X", DonId: donID, Method: MethodWebAPITrigger, Payload: validPayload}}` with key A, and `msgB` identically but with `MessageId: "X"` signed by key B.
4. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)`, then `h.HandleLegacyUserMessage(ctx, msgB, callbackB)`.
5. Assert `len(h.savedCallbacks) == 1` and `h.savedCallbacks["X"].Callback == callbackB` (A's entry silently overwritten).
6. Construct a JSON-RPC response for `MessageId "X"` from a DON node and call `h.HandleNodeMessage(ctx, resp, nodeAddr)`.
7. Assert `callbackB.SendResponse` was invoked and `callbackA.SendResponse` was never called — demonstrating A's request is orphaned while B receives the (potentially unrelated) response for its own overwritten slot.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response

	}
	return nil
}
