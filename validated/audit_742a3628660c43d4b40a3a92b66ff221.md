### Title
Loss-adjusted APR0 receipt can be bypassed via a later normal-mode request, paying a haircutted epoch's principal at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` guards against opening a new request while the user still holds a loss-adjusted receipt, but it derives the "receipt epoch" solely from the single-slot `lastWithdrawRequest`. The external advisory's bug class — a distinct repeated value silently dropped because membership is tested against only one imprecise key — maps onto this: a user's APR0 principal recorded under an earlier `principalEpoch` is effectively invisible once `lastWithdrawRequest` is overwritten by a later request. A user can then claim APR0 principal that suffered a `stopEpochWithDuration` haircut at full par.

### Finding Description
In `requestWithdraw` (lines 261–270):

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (
  lossRecoveryPrice != 0 &&
  (withdrawsRequestsByEpoch[_user][lossEpoch] != 0 ||
  (apr0Users[_user].principal != 0 && apr0Users[_user].principalEpoch == lossEpoch))
) { revert NotAllowed(); }
```

The guard inspects only `lossRecoveryPriceByEpoch[lastWithdrawRequest]`. It then unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch` (line 282). Two modes write different books:

- APR0 mode (`unscaledApr == 0`): request goes to `apr0Users[_user].principal/principalEpoch`; `withdrawsRequestsByEpoch` is *not* written.
- Normal mode: `withdrawsRequestsByEpoch[_user][epoch]` is written.

So if a user makes an APR0 request in epoch A (recorded under `apr0Users.principalEpoch == A`, `lastWithdrawRequest == A`), epoch A ends with a loss (`lossRecoveryPriceByEpoch[A] = p < 1e18`), and then the (honest) manager raises the APR so `unscaledApr != 0` for epoch B, the user's new normal request sets `lastWithdrawRequest = B`. The guard now evaluates `lossRecoveryPriceByEpoch[B]` (zero) and `apr0Users.principalEpoch == B` (false — it is A). The still-unclaimed, haircutted epoch-A APR0 receipt is "dropped" from the dedup check exactly like the advisory's substring-dropped header value.

On claim, `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` (line 789) also uses `lastWithdrawRequest` (= B), finds no loss price, and returns 0; `_claimFundedWithdrawRequest` (lines 319–350) then settles the APR0 principal via `_settleApr0` and pays `settledPrincipal + principal + settledInterest` **at par** via `_transferFundedClaim`. The haircut portion of epoch A's APR0 principal was never funded by the borrower (only `claimBasis * lossRecoveryPrice` was delivered at `stopEpochWithDuration`), so the excess payout is sourced from underlyings belonging to other claimants/LPs.

### Impact Explanation
Direct theft / insolvency: the attacker receives `apr0Principal * (1 - lossRecoveryPriceByEpoch[A])` in underlying that was never funded. `_transferFundedClaim` only guards against spending `defaultRecoveryReserve`, not other users' funded balances, so the delta is silently taken from the vault, impairing later legitimate claims. One receipt (the epoch-A APR0 principal) escapes the loss waterfall while still being paid — a broken "one receipt, haircut-adjusted payout" invariant.

### Likelihood Explanation
Requires: a vault running APR0 mode (`unscaledApr == 0`), a `stopEpochWithDuration` that crystallizes a partial loss on the request epoch, and a subsequent epoch where `unscaledApr != 0` so the attacker can file a normal-mode request that rewrites `lastWithdrawRequest`. The APR flip is an honest manager action (`setAprsWithBuffer`/`setAprs`), entirely consistent with normal vault operation (e.g., re-enabling yield after a loss epoch). The attacker is any KYC'd lender; no privileged cooperation is needed beyond the manager changing APR, which is routine. Any unclaimed APR0 principal in the loss epoch is exploitable, bounded only by the attacker's deposited principal.

### Recommendation
Track per-epoch receipt obligations rather than a single latest epoch, or make the guard comprehensive: revert if *any* epoch for the user has `lossRecoveryPriceByEpoch[e] != 0` together with `withdrawsRequestsByEpoch[user][e] != 0` or `apr0Users[user].principalEpoch == e && principal != 0` — e.g., iterate the user's outstanding request epochs, or additionally check `apr0Users[_user].principalEpoch`'s loss price independently of `lastWithdrawRequest` before overwriting it. A minimal fix is to also evaluate `lossRecoveryPriceByEpoch[apr0Users[_user].principalEpoch]` when `principal != 0`, and symmetrically to keep a record of any earlier funded-loss epoch rather than collapsing everything onto `lastWithdrawRequest`.

### Proof of Concept
```solidity
// Foundry fork test sketch, mirroring test/foundry/IdleCreditVault.t.sol helpers
function testApr0LossReceiptBypassedByLaterNormalRequest() external {
    // APR0 mode, no fees
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);           // attacker = this contract
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _forceLastEpochAprToZero();

    uint256 epochA = IdleCreditVault(address(strategy)).epochNumber();
    uint256 principal = cdoEpoch.requestWithdraw(
        IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));

    _startEpochAndCheckPrices(1);

    // Epoch ends with partial loss -> lossRecoveryPriceByEpoch[epochA] < 1e18
    uint256 shortfall = principal / 2; // borrower repays only half of receipts
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, pending - shortfall);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(epochDuration, pending - shortfall, 0);
    uint256 price = IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(epochA);
    assertLt(price, 1e18);

    // Honest manager raises APR for next epoch -> normal mode
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(1e18, 1e18);

    // Attacker does NOT claim the loss-adjusted receipt; files new request in epoch B.
    // Guard checks only lastWithdrawRequest == epochB -> passes despite unpaid haircut.
    _startEpochAndCheckPrices(2);
    cdoEpoch.requestWithdraw(
        IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));

    _startEpochAndCheckPrices(3);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, /* normal funding */);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    // CLAIMED: epoch-A APR0 principal paid at PAR; expected: principal * price
    assertApproxEqAbs(
        underlying.balanceOf(address(this)) - balPre,
        /* includes */ principal, // haircut never applied
        1);
}
```

Key assertions the PoC demonstrates: `lossRecoveryPriceByEpoch[epochA] < 1e18` yet the attacker's epoch-A APR0 principal is paid in full, because both `requestWithdraw` (line 261) and `_claimLossAdjustedWithdrawRequest` (line 790) resolve the loss epoch exclusively through the overwritten `lastWithdrawRequest` slot.
