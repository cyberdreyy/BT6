### Title
Unfunded instant-withdraw receipts can claim at par against the vault's general balance, escaping the funded-bucket restriction and stealing reserves earmarked for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays the full `instantWithdrawsRequests[_user]` balance through `_transferFundedClaim`, which only protects `defaultRecoveryReserve` — and that reserve is zero until `finalizeDefaultRecovery` runs. When the borrower fails to fund instant withdrawals (`getInstantWithdrawFunds` triggers a default), the instant receipts are *unfunded* (`pendingInstantWithdraws` remains > 0), yet their holders can still withdraw at par from any underlying sitting in the strategy — including borrower-funded reserves held for normal (`claimWithdrawRequest`) receipts. This is the credit-vault analog of CWE-22: the payout path fails to confine the claim to its funded scope and "traverses" into balances belonging to other claimants. [1](#0-0) [2](#0-1) 

### Finding Description
Flow trace:

1. Epoch running, `allowInstantWithdraw = true`. Attacker (a KYC'd lender holding tranche tokens) calls `requestWithdraw` on `IdleCDOEpochVariant`, which routes to `requestInstantWithdraw`: `_amount` of strategy tokens are burned from the CDO and minted to the attacker as a receipt; `instantWithdrawsRequests[attacker] += amount`, `instantWithdrawsRequestsByEpoch[attacker][epoch] += amount`, `pendingInstantWithdraws += amount`. [3](#0-2) 
2. After `instantWithdrawDelay`, manager calls `getInstantWithdrawFunds`; the borrower does not send funds, so nothing is collected via `collectInstantWithdrawFunds` and the pool is marked defaulted. `pendingInstantWithdraws` stays > 0 — the attacker's receipt is unfunded.
3. Meanwhile the strategy holds underlying previously pulled via `collectWithdrawFunds` to back *funded* normal withdraw receipts of honest users (transferred at a prior `stopEpoch`). [4](#0-3) 
4. Before manager calls `finalizeDefault`/`finalizeDefaultRecovery` (which would set `defaultRecoveryFinalized` and haircut the attacker's receipt via `_claimDefaultedInstantWithdrawRequest` at `defaultRecoveryPrice`), the attacker calls `claimInstantWithdrawRequest`.
5. In `claimInstantWithdrawRequest`, because `defaultRecoveryFinalized` is still `false`, the defaulted-epoch branch is skipped entirely. `amount = instantWithdrawsRequests[attacker]` is paid at full par by `_transferFundedClaim`. [1](#0-0) 
6. `_transferFundedClaim`'s only guard is `balance - defaultRecoveryReserve >= amount`; with `defaultRecoveryReserve == 0` pre-finalization, the check is vacuous and the transfer spends the funded normal-receipt reserve. [2](#0-1) 

The same `claimInstantWithdrawRequest` wrapper on the CDO side only checks `!allowInstantWithdraw` — no `defaulted()` or pending-funding gate. [5](#0-4) 

Broken invariant: **one receipt one payout / donation-reserve isolation**. An unfunded instant receipt is worth `claimBasis * defaultRecoveryPrice` post-finalization, but is redeemed for `claimBasis` pre-finalization out of funds that do not belong to it.

### Impact Explanation
Direct theft / insolvency with quantified loss: an attacker holding an unfunded instant receipt of `X` underlying extracts `X` at par, while honest users' funded normal withdraw receipts (`withdrawsRequests`, already paid for by the borrower and sitting in the strategy) are drained. Those users' subsequent `claimWithdrawRequest` calls revert or are underpaid because the strategy balance no longer covers `withdrawsRequests`. Additionally, the stolen amount reduces what `finalizeDefaultRecovery` later counts as `_defaultPrefundedInstantReserve`, lowering `defaultRecoveryPrice` for all defaulted claimants. Loss ≈ min(instant receipt, strategy balance excluding reserve) — bounded only by the attacker's deposit size. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
Requires only an unprivileged KYC'd tranche holder and an honest-manager sequence: request instant withdraw during a running epoch → borrower fails to fund → attacker claims before recovery finalization. Borrower default is an expected protocol event (the whole `defaultRecovery*` machinery exists for it), and there is a real window — finalization is a separate privileged transaction. The attacker can also force the race by requesting instant withdraws and immediately claiming in the same block the default is recorded, front-running `finalizeDefaultRecovery`. No malicious privileged role is needed.

### Recommendation
Restrict the instant-claim payout to its funded scope: in `claimInstantWithdrawRequest`, either
- revert when `IIdleCDOEpochVariant(idleCDO).defaulted()` is true and `defaultRecoveryFinalized` is false (route users through the recovery path once finalized), or
- cap the par payout at the funded portion, e.g. require `amount <= fundedInstant` where fundedInstant tracks underlying actually collected via `collectInstantWithdrawFunds` for the current epoch (`instantWithdrawClaimsByEpoch[epoch] - pendingInstantWithdraws`), so unfunded receipts can never traverse into normal-receipt reserves.

### Proof of Concept
Foundry fork PoC (sketch, against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// setup: depositAA by attacker and honest user; run epoch 0; stop epoch 0
// honest user requestWithdraw -> funded at next stopEpoch (borrower repays pendingWithdraws)
// -> strategy now holds underlying reserved for honest user's claim

// epoch 1 starts; attacker requests instant withdraw of X
cdoEpoch.requestInstantWithdraw-like path via requestWithdraw during running epoch
// -> instantWithdrawsRequests[attacker] = X; pendingInstantWithdraws = X; strategy received nothing

// after instantWithdrawDelay, borrower does NOT fund
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds(); // pool defaults, nothing collected

// BEFORE manager can call finalizeDefaultRecovery:
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// attacker received X at par from strategy balance reserved for honest user

// honest user now claims -> reverts NotAllowed or receives less
vm.prank(honestUser);
cdoEpoch.claimWithdrawRequest(); // underfunded / revert
```

Assert `underlying.balanceOf(attacker)` increased by `X` while `strategy` balance reserved for `withdrawsRequests[honestUser]` decreased, demonstrating the escape.

Caveat: I verified the absence of a `defaulted()`/funding gate in `IdleCreditVault.claimInstantWithdrawRequest` and the CDO-side wrapper, but I was not able to read `IdleCDOEpochVariant.getInstantWithdrawFunds`/`finalizeDefault` in full within the available iterations; the PoC assumes (consistent with `testClaimWithdrawRequestWithInstantDefault`) that the strategy retains claimable underlying after an instant-funding default and that instant claims remain callable pre-finalization.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
