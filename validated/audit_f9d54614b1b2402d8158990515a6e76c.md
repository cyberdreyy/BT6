### Title
Stale confirmations from removed multisig members can be counted toward the approval threshold, letting a request execute with fewer than K currently-authorized signers - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges requests and confirmations that were *created* by the member being removed; it never scans other active requests to strip confirmations that the removed member previously cast as a *confirmer*. `confirm()` counts confirmation-set size against `num_confirmations` without checking that every entry in the set still corresponds to a current member. This is the same class of bug as the Symbiotic `Settlement` finding: a party's "vote"/stake-derived authority persists in state and is counted toward a security threshold after that party has been stripped of standing, letting the threshold be satisfied with fewer genuinely-authorized approvers than `K`.

### Finding Description
The multisig's security invariant is: an action executes only when at least `num_confirmations` *current* members approve it — i.e. `len(confirmations ∩ live_members) == num_confirmations` should hold at execution time. The code instead enforces `len(confirmations) >= num_confirmations` [1](#0-0) , where `confirmations` is a raw set of member-string entries that is never reconciled against the current `members` set except at the moment each individual confirmer calls `confirm`.

When a member is removed via `DeleteMember`, `delete_member` only cleans up:
- requests where `r.member == member` (i.e., requests *authored* by that member), and
- that member's `num_requests_pk` counter.

It does **not** iterate over `self.confirmations` to remove the departing member's account/key string from confirmation sets of requests they merely *confirmed* (but did not author): [2](#0-1) 

Consequently, if member M confirms request X (created by someone else) and is later removed from the multisig (e.g., because a key was compromised, an employee left, or the group intentionally shrank membership), M's confirmation string remains permanently embedded in `confirmations[X]`. Any subsequent `confirm()` call by a different, still-legitimate member will count M's stale confirmation toward `num_confirmations`, potentially executing the request with fewer than `K` currently-live approvers — e.g., 2 live confirmations + 1 stale confirmation reaching a threshold of 3.

Contrast with `remove_request`/normal completion flow, which only clears `confirmations` for the request being executed or deleted — there is no per-membership-change invalidation of confirmations recorded on *other, still-pending* requests [3](#0-2) .

### Impact Explanation
This breaks the authorisation boundary the contract is built to enforce: "confirmations counted versus live members." A stale confirmation from a de-authorized member can substitute for a required live approval, allowing a `Transfer`, `FunctionCall`, `AddKey`, `AddMember`, or `DeployContract` request to execute with fewer than `num_confirmations` currently-trusted signers agreeing. Since `multisig2` custodies NEAR/access and is meant to gate `Transfer` and key/deploy actions behind a K-of-N threshold, this is a threshold bypass that can move NEAR or grant access below the configured quorum — matching the "Critical: a multisig request executed below threshold" impact category.

### Likelihood Explanation
Exploitation requires only ordinary, in-scope multisig usage, no privileged foundation/owner role, no redeploy, and no social engineering:
1. Any member (not necessarily malicious) confirms a pending request they didn't author.
2. Later, that member is removed from the multisig through the normal `DeleteMember` flow (a routine operational event — compromised key, employee offboarding, membership rebalancing).
3. The stale confirmation silently remains attached to any other request that was pending (or is created and left unconfirmed) at removal time.
4. A remaining member — potentially the attacker, if they control enough of the remaining live members or exploit an already-borderline threshold — calls `confirm` on that request and it executes counting the departed member's stale approval.

This is realistic because request lifetimes can span the `REQUEST_COOLDOWN` window and beyond (no expiry is enforced other than manual `delete_request`), so a request confirmed by soon-to-be-removed members can remain "confirmed" indefinitely, waiting to be combined with fewer live confirmations than intended.

### Recommendation
In `delete_member`, iterate all entries in `self.confirmations` (not just requests authored by the removed member) and strip the departing member's identifier from every confirmation set, re-persisting the updated sets. Alternatively, redesign `confirm`/execution to recompute confirmation counts by intersecting the stored confirmation set with `self.members` at execution time, so removed members' historical approvals never count toward `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members, 3)` with members `[A, B, C, D]`.
2. `A` calls `add_request(request)` (creates request X, not self-confirmed).
3. `B` calls `confirm(X)` → confirmations = `{B}`.
4. `C` calls `confirm(X)` → confirmations = `{B, C}` (2/3, not yet executed) [4](#0-3) .
5. Separately, members execute a `DeleteMember{member: B}` request (requires 3 confirmations from currently-live members, satisfiable using A, C, D) — this succeeds and removes B from `self.members`, but request X's confirmation set `{B, C}` is left untouched because X was authored by A, not B [5](#0-4) .
6. `D` (a live member) calls `confirm(X)`. `confirmations.len() + 1 = 3 >= num_confirmations (3)` → request X executes, even though only `C` and `D` are still current members approving it — B's stale confirmation supplied the third "vote" despite B no longer being a member [6](#0-5) .

This demonstrates the request executed with only 2 genuinely live-member confirmations against a nominal 3-of-N threshold, using a departed member's stale approval to make up the difference.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
