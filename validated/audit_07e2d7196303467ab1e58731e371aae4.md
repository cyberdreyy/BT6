### Title
Zip Legacy Extractor bypasses path-root confinement, enabling zip-slip path traversal - (File: helpers/archives/zip_extract.go, reached via commands/helpers/archive/ziplegacy/zip_legacy_extractor.go: Extract)

### Summary
The `Extract` method in `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go` receives an extraction root directory `e.dir` at construction time but never uses it — it calls `archives.ExtractZipArchive(zr)` which extracts every zip entry using the raw, attacker-controlled `file.Name` with no root confinement, no `..`-segment rejection, and no absolute-path rejection. This is a classic zip-slip: an attacker who controls artifact/cache archive content can craft entry names such as `../../../../etc/foo` or absolute paths to write files outside the intended extraction root.

### Finding Description
`extractor.Extract` in `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go` (lines 26-33) stores `dir` on construction but the field is completely unused inside `Extract`: [1](#0-0) 

It forwards the parsed `*zip.Reader` directly to `archives.ExtractZipArchive`, which has no `dir` parameter at all: [2](#0-1) 

Inside, each entry is written using `file.Name` unmodified/unchecked:
- Directory entries: `os.Mkdir(file.Name, ...)` [3](#0-2) 
- Symlink entries: `os.Symlink(string(data), file.Name)`, where the link target and the link path are both attacker-controlled [4](#0-3) 
- Regular file entries: `os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, ...)` [5](#0-4) 
- Parent directories are created via `os.MkdirAll(filepath.Dir(file.Name), 0o777)` with no confinement check [6](#0-5) 

Contrast this with `tarzstd_extractor.go`, which does correctly join the entry name to `e.dir`, resolves the absolute path, and rejects any path escaping the root: [7](#0-6) 

The only path-related check present in the zip-legacy code path is `errorIfGitDirectory`, which only guards against `.git` directory entries (a different, unrelated protection) — it performs no `..`-segment or absolute-path validation: [8](#0-7) 

Because `os.Mkdir`/`os.OpenFile`/`os.Symlink` are called with the entry name exactly as it appears in the archive, a crafted zip with entries like `../../../home/user/.ssh/authorized_keys` or `/tmp/evil` will write to those absolute/traversed paths relative to whatever the process current working directory happens to be (since no `dir` is joined), completely escaping any extraction root the Runner intended (build directory, cache directory, artifacts directory).

I could not fully verify from static reading alone whether the `zip` (legacy) format is still registered/reachable via `commands/helpers/archiver.go` in current builds (as opposed to the modern `fastzip` extractor being the default), since the registration site could not be retrieved within the tool budget. However, the code exists, compiles, is exported (`ziplegacy.NewExtractor`), implements the shared `archive.Extractor` interface, and is wired for the `Zip` format constant. Regardless of whether `fastzip` is the default for new zip archives, if the `zip` format extractor path used by cache/artifact restoration (`commands/helpers/cache_extractor.go` / `commands/helpers/artifacts_extractor.go` equivalents) can select the legacy implementation (e.g., via feature flag, fallback, or explicit format value), this bug is directly reachable by an attacker who controls artifact/cache zip content for a job.

### Impact Explanation
An attacker-controlled zip archive (submitted as a job artifact or cache blob that another job later restores) can overwrite arbitrary files on the runner's filesystem outside the intended checkout/cache directory, up to the privileges of the runner/job process. This includes tampering with checkout state for a protected-ref pipeline, corrupting shared cache/helper state, or planting files (e.g., in shell profile, cron, or SSH authorized_keys locations) leading to code execution or persistence outside job sandbox boundaries — directly matching the scoped impact of protected-ref escalation or cross-job state tampering via path-root escape.

### Likelihood Explanation
Feasibility is high if the legacy zip extractor is reachable: the attacker only needs to control the bytes of a zip file consumed by `Extract` (a cache or artifact archive), a capability normal, unprivileged CI job authors already have (via `artifacts:paths`, cache config, or direct upload of a crafted archive as a cache/artifact blob later downloaded and extracted). No special executor privileges or admin action are required — only that the vulnerable `ziplegacy` code path is invoked instead of, or in addition to, the safer `fastzip` path. This is a repeatable, deterministic bug (100% reproducible with a single crafted zip) with no existing runtime checks that stop it in `ExtractZipArchive`.

### Recommendation
Fix `helpers/archives/zip_extract.go` (`ExtractZipArchive`/`extractZipFile`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry`/`extractZipFileEntry`) to accept and enforce the destination root directory, mirroring the confinement logic already present in `tarzstd_extractor.go`:
1. Thread `dir` through from `ziplegacy.extractor.Extract` into `archives.ExtractZipArchive(zr, e.dir)`.
2. For every `file.Name`, compute `path := filepath.Join(dir, file.Name)`, resolve to an absolute path, and reject (return error / skip with warning) any entry where the resolved path is not equal to or a descendant of `dir` (reject `..` traversal and absolute paths).
3. Apply the same validation to symlink targets (`file.Symlink` link value) to prevent symlink-based escapes on subsequent writes through the link.
4. Add a regression test asserting that a zip containing `../../outside.txt` and an absolute-path entry produces an error (or is skipped) and creates no file outside the extraction root.

### Proof of Concept
Go unit test to add to `helpers/archives/zip_extract_test.go`:
```go
func TestExtractZipArchive_PathTraversal(t *testing.T) {
    tmpRoot := t.TempDir()
    extractDir := filepath.Join(tmpRoot, "extract")
    require.NoError(t, os.MkdirAll(extractDir, 0o755))

    outsideTarget := filepath.Join(tmpRoot, "escaped.txt")

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    w, _ := zw.Create("../escaped.txt")
    _, _ = w.Write([]byte("pwned"))
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    // Simulate correct fixed signature: ExtractZipArchive(zr, extractDir)
    err = ExtractZipArchive(zr) // current signature ignores dir entirely
    _ = err

    // Assertion for the fix: file must not exist outside extractDir
    _, statErr := os.Stat(outsideTarget)
    assert.True(t, os.IsNotExist(statErr), "zip-slip: file was created outside extraction root at %s", outsideTarget)
}
```
Expected result on the current (vulnerable) code: the test fails because `escaped.txt` is created relative to the process's current working directory (outside `extractDir`), demonstrating the escape. After applying the recommended fix (joining against `dir` and validating the resolved path stays within it), the test passes.

}
