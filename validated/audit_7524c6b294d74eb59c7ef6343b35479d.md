### Title
Job-writable `RUNNER_TEMP_PROJECT_DIR` allows deleting the derived key file to permanently break `proxy-exec` masking bootstrap for the shared build/tmp directory - ([File: commands/helpers/internal/store/store.go])

### Summary
`store.Open` derives its encryption key by XOR-ing a random half stored inside `masking.db` with a second half stored in a **predictable, deterministic filename** (`"runner"+hex(sha256(pathname))`) placed directly inside the job's own `RUNNER_TEMP_PROJECT_DIR`/`TmpProjectDir`. A pipeline job has full read/write/delete access to this directory (it is the job's own temp workspace), so it can compute the same key path and delete it, permanently breaking `deriveEncryptionKey` for any later `proxy-exec` invocation that reuses `masking.db` without regenerating the key.

### Finding Description
- `store.Open(dir)` computes `pathname := filepath.Join(dir, "masking.db")` and `keyPath := filepath.Join(dir, "runner"+hex.EncodeToString(sha256(pathname)))`, both fully deterministic from `dir` alone. [1](#0-0) 
- The key is only (re)generated when `masking.db` does **not yet exist** (`os.Stat(pathname)` fails). If `masking.db` already exists, `keyPath` is expected to still hold its half of the key, and `deriveEncryptionKey` unconditionally does `os.ReadFile(keyPath)`, returning a hard error (`"deriving key"`) if the file is missing. [2](#0-1) 
- `dir` passed into `store.Open` is `RUNNER_TEMP_PROJECT_DIR` / `Build.TmpProjectDir()`, which is exposed directly to job scripts and is used by `proxy-exec` on every wrapped shell invocation (pre_build, build, after_script, etc.): [3](#0-2) [4](#0-3) 
- `TmpProjectDir()` is simply `BuildDir + ".tmp"`, and `BuildDir` is derived from the deterministic `ProjectUniqueDir()` (project slug/ID based), **not** the per-build `BuildID`. It is therefore the same path across the build's stages within a job, and — because it is not build-ID-scoped — is reused across separate job runs on the same runner/project unless the workspace is wiped by `GIT_CLEAN_FLAGS`/`GIT_STRATEGY: none` semantics or executor ephemerality do not apply. [5](#0-4) 
- Because the job script executes inside this directory with normal filesystem permissions, it can trivially reconstruct `keyPath` with the exact same `sha256(filepath.Join(dir,"masking.db"))` formula and `os.Remove()` it, while leaving `masking.db` untouched.
- On the very next `proxy-exec` invocation (next stage in the same job, or a subsequent job reusing the directory before cleanup), `Open()` sees `masking.db` exists → skips key regeneration → `deriveEncryptionKey` fails on `os.ReadFile(keyPath)` → `Open` returns `fmt.Errorf("deriving key: %w", err)` → `NewProxy` propagates it → `ProxyExecCommand.Execute` calls `logrus.Fatalln("creating exec proxy", err)`, killing the wrapped process entirely. [6](#0-5) 
- There is no self-healing path: `Open` never regenerates `keyPath` when `masking.db` exists but `keyPath` is missing; it only regenerates when `masking.db` itself is absent. No permission/ownership check, no locking, and no separation between the "job-writable" build directory and the "runner-private" key material exists to stop this.

### Impact Explanation
Within a single job, any stage after the deletion (e.g., `after_script`, or a subsequent step) that also goes through `ProxyExecShell`/`proxy-exec` will hard-fail with a fatal error, terminating that helper invocation rather than degrading gracefully. If the build/tmp directory is reused across job runs for the same project/runner slot (its path is deterministic and not build-ID scoped), the corruption persists and **every subsequent job on that project/runner combination using `ProxyExec=true` will fail identically** until an operator manually removes `masking.db`/the tmp directory or a full workspace wipe occurs. This matches the scoped impact: persistent proxy-exec/masking bootstrap breakage surviving the triggering job, affecting future pipelines sharing that workspace — a job-triggered, cross-job denial-of-service against the masking/exec-proxy feature.

### Likelihood Explanation
Fully feasible with only ordinary pipeline-author privileges: the attacker needs no special permission beyond writing a job script, and `RUNNER_TEMP_PROJECT_DIR` is documented/exposed as a normal, writable job variable. The key-path formula is deterministic and computable client-side (`sha256` over a constant string plus the known directory), so no information disclosure or race is needed. The main precondition — that the temp/build directory is not always deleted between jobs — depends on runner configuration (`GIT_STRATEGY`, custom build dirs, non-Docker/ephemeral executors, `builds_dir` reuse), which is common for shell/SSH executors and long-lived autoscaler instances, making this repeatable in realistic deployments.

### Recommendation
Do not store the second key half as a job-writable file inside the job's own temp/build directory. Options:
1. Store `keyPath`'s content (or the whole key) outside the job-writable tree, e.g., in a runner-owned, per-build-ID-scoped location not exposed via `RUNNER_TEMP_PROJECT_DIR`.
2. Detect and self-heal: if `masking.db` exists but `keyPath` is missing/corrupt, either fail closed with a clear, recoverable action (auto re-key by truncating/regenerating `masking.db` too) instead of a fatal, unrecoverable state, and make sure this doesn't silently decrypt old entries with a mismatched key.
3. Set the key file's permissions/ownership so the job's build user cannot delete or modify it (though on POSIX, delete rights depend on directory permissions, not just the file — so directory separation is the real fix), or verify integrity (e.g., HMAC of `keyPath` contents recorded elsewhere) and fail with a distinct, cleanup-safe error/state rather than global fatal failure blocking future jobs indefinitely.

### Proof of Concept
```go
func TestStore_Open_KeyFileDeletionBreaksReuse(t *testing.T) {
    dir := t.TempDir()

    // First Open+Add: creates masking.db and the derived key file.
    s, err := store.Open(dir)
    require.NoError(t, err)
    require.NoError(t, s.Add("secret-phrase"))
    s.Close()

    // Attacker (job script) computes the same deterministic keyPath and deletes it,
    // leaving masking.db intact.
    pathname := filepath.Join(dir, "masking.db")
    sum := sha256.Sum256([]byte(pathname))
    keyPath := filepath.Join(dir, "runner"+hex.EncodeToString(sum[:]))
    require.FileExists(t, keyPath)
    require.NoError(t, os.Remove(keyPath))

    // Subsequent proxy-exec / Open call on the same dir must fail deterministically
    // and must NOT self-heal (masking.db is untouched, so it isn't regenerated).
    _, err = store.Open(dir)
    require.Error(t, err)
    require.Contains(t, err.Error(), "deriving key")

    // Confirm it stays broken (no self-heal on repeated attempts).
    _, err2 := store.Open(dir)
    require.Error(t, err2)
}
```
This test demonstrates: (1) job-controllable deletion of a deterministically-named file, (2) permanent, non-self-healing failure of `store.Open` for the same directory, matching the described `proxy-exec` fatal failure path in `commands/helpers/proxy_exec.go`.

func deriveEncryptionKey(f *os.File, keyPath string) ([]byte, error) {
	var key1 [32]byte
	if _, err := io.ReadFull(f, key1[:]); err != nil {
		return nil, err
	}

	key2, err := os.ReadFile(keyPath)
	if err != nil {
		return nil, err
	}

	if len(key2) < len(key1) {
		return nil, fmt.Errorf("key1 and key2 not the same size")
	}

	for i := 0; i < len(key1); i++ {
		key1[i] ^= key2[i]
	}

	return key1[:], nil
}

func (b *Build) ProjectUniqueDir(sharedDir bool) string {
	dir, err := b.ProjectSlug()
	if err != nil {
		dir = fmt.Sprintf("project-%d", b.JobInfo.ProjectID)
	}

	// for shared dirs path is constructed like this:
	// <some-path>/runner-short-id/concurrent-project-id/group-name/project-name/
	// ex.<some-path>/01234567/0/group/repo/
	if sharedDir {
		dir = path.Join(
			b.Runner.ShortDescription(),
			fmt.Sprintf("%d", b.ProjectRunnerID),
			dir,
		)
	}

	if b.GetGitStrategy() == GitEmpty {
		dir += "-empty"
	}

	return dir
}
