### Title
Removing a multisig key does not purge its existing confirmations on other pending requests, allowing requests to execute below the live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
When a multisig key is removed via `MultiSigRequestAction::DeleteKey`, the contract only deletes requests that were *originally submitted* by that key. It never scans the `confirmations` map to strip that key's vote from other, still-pending requests that it had already confirmed. Because `confirm()` counts `confirmations.len()` against `num_confirmations` without verifying that each confirming public key is still a live access key on the account, a request can later be pushed over the threshold and executed using a mix of live signers plus a "ghost" confirmation from a key that has already been removed.

### Finding Description
`execute_request`'s `DeleteKey` branch removes only requests whose `signer_pk` (the original submitter) equals the deleted key: [1](#0-0) 

It does not touch `self.confirmations` entries for *other* requests that the deleted key had already confirmed. `confirm()` itself never re-validates that previously recorded confirming keys are still authorized signers on the account — it just compares set size to `num_confirmations`: [2](#0-1) 

`remove_request` (invoked from `confirm` and `delete_request`) only clears confirmations for the request being finalized/deleted, not for confirmations by a key elsewhere in the system that gets deleted later: [3](#0-2) 

So the equality that should hold — `confirmations counted on a request == confirmations from keys currently authorized on the account` — is violated once a key is deleted while it still has an outstanding, unconsumed confirmation on some other pending request.

### Impact Explanation
This directly matches the "multisig request executed below threshold" critical-impact category. Concretely:

1. Key `K2` submits `add_request` for request `B` (e.g., a `Transfer` to some receiver). `signer_pk` of `B` is `K2`.
2. Key `K1` calls `confirm(B)`. Since `confirmations.len() + 1 < num_confirmations` (e.g. 1 < 2), it just records `K1` in `confirmations[B]` and returns.
3. Members later remove `K1` (normal key rotation / offboarding) via a `DeleteKey{K1}` request, executed with confirmations from other live keys. `execute_request`'s `DeleteKey` branch only drops requests where `signer_pk == K1` — `B` was submitted by `K2`, so it is untouched, and `confirmations[B]` still contains `K1`.
4. Key `K3` (a live key) calls `confirm(B)`. `confirmations.len() + 1 == 2 >= num_confirmations(2)`, so `B` executes — approved by only one currently-live key (`K3`) plus a stale vote from the now-deleted `K1`.

The transfer/`FunctionCall`/`AddKey` action in `B` executes with an effective live-signer count below the configured `num_confirmations`, i.e., NEAR (or key/permission changes) move on authority that the account owners no longer collectively hold.

### Likelihood Explanation
Key rotation/removal (offboarding a signer, replacing a compromised key) is a normal, expected multisig operation, not a contrived edge case. Any pending request that a soon-to-be-removed key had already confirmed — but that hasn't reached threshold — will silently retain that confirmation forever, until enough remaining keys confirm it. No special privilege beyond being a former (now non-member) key-holder is needed to have contributed the residual confirmation; the requirement is only ordinary multisig usage combined with a key-removal event, making this readily reachable in production multisig accounts that periodically rotate signers.

### Recommendation
When executing `DeleteKey`, iterate over `self.confirmations` for *all* pending requests and remove the deleted public key from each confirmation set (not just requests it submitted). Alternatively, have `confirm()`/execution re-validate, at execution time, that every public key recorded in `confirmations[request_id]` is still present among the account's current access keys before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(2)` with keys `K1, K2, K3`.
2. As `K2`, call `add_request(Transfer{...})` → `request_id = B`.
3. As `K1`, call `confirm(B)` → `confirmations[B] = {K1}` (threshold not met, no execution).
4. As `K2`/`K3` (any 2 keys reaching threshold), submit and confirm `DeleteKey{K1}` on `alice()` (self) → `K1` is removed from the account's access keys; `execute_request`'s `DeleteKey` branch only removes requests whose `signer_pk == K1` (none here, since `B.signer_pk == K2`), so `confirmations[B]` is untouched.
5. As `K3`, call `confirm(B)` → `confirmations[B].len() + 1 == 2 >= num_confirmations(2)`, so `execute_request` runs the `Transfer` in `B`, even though only `K3` is a currently live, authorized key confirming it — one below the configured threshold of live signers.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .expect("Failed to remove existing element");
        // decrement num_requests for original request signer
        let original_signer_pk = request_with_signer.signer_pk;
        let mut num_requests = self.num_requests_pk.get(&original_signer_pk).unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_signer_pk, &num_requests);
        // return request
        request_with_signer.request
    }
