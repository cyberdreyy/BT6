### Title
Mempool leak of `stopEpochWithDuration` loss parameter lets a tranche holder escape the loss waterfall via a par-valued instant withdrawal - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The external report is an information-leak bug (CVE-2024-6747 in mknotifyd). In this codebase the strongest analog of "leaked sensitive data enables exploitation" is the public mempool visibility of the manager's `stopEpochWithDuration(_newApr, _interest, _duration, _lossAmount)` call. `_lossAmount` is an explicit, pre-computed realized loss that will be socialized across active LPs (BB-first) and pending normal receipts. An unprivileged tranche holder who observes this transaction can front-run it with `requestWithdraw`, converting their position into an instant-withdraw receipt that `getInstantWithdrawFunds` must fund at par before the loss burn, escaping the haircut entirely while the same absolute `_lossAmount` is absorbed by the remaining, smaller active basis.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch` the check `_pendingInstant() != 0` (contracts/IdleCDOEpochVariant.sol:345) forces the manager to call `getInstantWithdrawFunds()` before any stop. That function pulls the full `pendingInstantWithdraws` amount from the borrower at par and sets `allowInstantWithdraw = true` (lines 558-574). Instant receipts are minted to the user at request time in `IdleCreditVault.requestInstantWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:362-375): the CDO's strategy tokens are burned and the user gets a fixed `_amount` claim denominated in underlyings.

The loss path (`previewLossAdjustedWithdrawFunds`, contracts/strategies/idle/IdleCreditVault.sol:440-460) splits `_lossAmount` only between `activeBasis` and normal `pendingWithdraws`. Because requesting an instant withdrawal already burned the CDO-side strategy-token principal, the attacker's position is excluded from `activeBasis` (`_lossActiveBasis` reads `balanceOf(idleCDO)` / `getContractValue` post-burn), and instant receipts are not part of `pendingBasis`. The attacker therefore redeems at 100% while the unchanged `_lossAmount` is concentrated onto fewer remaining LP tokens, and the `totalBasis` revert check is computed on the shrunken basis, so it does not protect them.

The exploit sequence, in a running epoch with instant withdrawals enabled (`setInstantWithdrawParams` configured with a low `minAprDelta`, and lower next-epoch APR so `requestWithdraw` routes to the instant path — per test/foundry/IdleCDOEpochQueue.t.sol:1141-1178):

1. Attacker (KYC-passed AA/BB tranche holder) monitors the mempool after `epochEndDate` passes.
2. Manager broadcasts `stopEpochWithDuration(newApr, interest, duration, lossAmount)` with `lossAmount > 0` — leaking the exact realized loss and its basis split (also publicly computable via `previewLossAdjustedWithdrawFunds`).
3. Attacker front-runs with `requestWithdraw(amount, tranche)`, creating an instant receipt at the pre-loss price.
4. `stopEpoch` now reverts on `_pendingInstant() != 0`; manager must call `getInstantWithdrawFunds()`, which pulls the attacker's full claim from the borrower at par.
5. `stopEpochWithDuration` then succeeds and applies `lossAmount` to the remaining active LPs and normal pending receipts only.

### Impact Explanation
Direct harm with quantified loss: the attacker exits at par for their entire position while the fixed `lossAmount` is socialized over a strictly smaller basis, increasing the per-token haircut of every other LP and pending receipt. Example: NAV 1,000,000 units, `lossAmount = 100,000` (10%). An attacker holding 200,000 (20% of TVL) who escapes loses 0 instead of ~20,000; the remaining 800,000 of LPs absorb the full 100,000 (12.5% instead of 10%). The attacker's avoided loss equals funds effectively transferred from other LPs. The borrower is honest and solvent here — the attack does not require default, and it fails only if funding the instant request itself triggers `_handleBorrowerDefault` (which would haircut the attacker via `defaultRecoveryPrice`).

### Likelihood Explanation
Requires: (a) a loss epoch where the manager uses the `_lossAmount` parameter, (b) instant withdrawals enabled for that epoch (low `minAprDiff` config and a declining APR regime — a supported configuration), (c) a public-mempool chain or observable pending manager transaction. All attacker capabilities (tranche holding, `requestWithdraw`) are unprivileged. The leak is inherent: `_lossAmount` is plaintext calldata and `previewLossAdjustedWithdrawFunds` is a public view exposing the exact split before execution.

### Recommendation
Do not let in-flight instant requests sidestep a same-stop loss. Options: compute the loss basis *before* burning CDO strategy tokens for same-block instant requests (i.e., include pending instant receipts in `totalBasis` and haircut `pendingInstantWithdraws` via a `lossRecoveryPriceByEpoch`-style price), or apply the loss atomically to the pre-request basis so that instant receipts minted between end-of-epoch and stop are haircut pro rata. At minimum, gate `requestInstantWithdraw` once `block.timestamp >= epochEndDate` so the loss parameter cannot be front-run at the epoch boundary.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testFrontRunStopLossViaInstantWithdraw() external {
    uint256 amountWei = 10_000 * ONE_SCALE;
    // victim (test contract) + attacker each deposit AA
    uint256 victimShares = idleCDO.depositAA(amountWei);
    address attacker = makeAddr('attacker');
    uint256 attackerShares = _depositWithUser(attacker, amountWei, true);
    idleCDO.depositBB(amountWei);

    _startEpochAndCheckPrices(0);
    // configure instant withdraws enabled for next epoch (low apr diff)
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(cdoEpoch.instantWithdrawDelay(), 1e18, false);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());
    _startEpochAndCheckPrices(1); // epoch running, instant requests enabled

    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 loss = cdoEpoch.getContractValue() / 10; // manager's mempool tx: stopEpochWithDuration(..., loss)
    // front-run: attacker converts entire position to instant receipt at par
    vm.prank(attacker);
    uint256 attackerClaim = cdoEpoch.requestWithdraw(attackerShares, address(AAtranche));

    // manager must fund instant requests at par before stop
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();
    deal(defaultUnderlying, strategy.borrower(), cdoEpoch.getContractValue() + loss, true);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), type(uint256).max);
    uint256 priceBBPre = cdoEpoch.virtualPrice(address(BBtranche));
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), loss);

    // attacker claims full amount, unaffected by loss
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker), attackerClaim, 'attacker escaped loss at par');
    // remaining LPs absorbed the whole loss on a smaller basis
    assertLt(cdoEpoch.virtualPrice(address(BBtranche)), priceBBPre, 'BB absorbed concentrated loss');
}
```

Caveat: I could not fully trace the CDO-side `requestWithdraw` instant-vs-normal routing condition (exact `minAprDiff`/APR-comparison gating) in the available iterations; the PoC assumes instant requests are enabled in epoch 1 as demonstrated by the existing tests. If the epoch's configuration makes instant withdrawals unavailable, the same front-run via a *normal* request is still partially effective (pending receipts share only `pendingBasis/totalBasis` of the loss pro rata), but the par-escape vector via instant withdrawals is the stronger instance.
