### Title
Blacklisted lenders cannot redirect funded withdrawal claims and can permanently freeze receipt payouts - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary

Credit-vault withdrawal receipts are minted to, tracked by, and paid only to the requester address. If the underlying token contract later blacklists that requester, every claim path reverts while sending underlying to the same immutable beneficiary. Because the receipt tokens are address-bound and user transfers are disabled, the requester cannot migrate the claim to an unblacklisted address.

### Finding Description

`requestWithdraw` mints the receipt strategy tokens directly to `_user` and stores the pending claim under `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][epoch]`. [1](#0-0) 

Once the withdrawal is funded, `claimWithdrawRequest` reaches `_claimFundedWithdrawRequest`, burns the requester’s receipt, clears the requester’s accounting, and calls `_transferFundedClaim(_user, amount)`. [2](#0-1) 

`_transferFundedClaim` has no recipient parameter and always sends underlying to `_user`. [3](#0-2) 

The same fixed-recipient issue exists for instant withdrawals, loss-adjusted claims, post-default claims, and default-recovery claims because all of them eventually call `_transferFundedClaim` or `_transferDefaultRecovery` with the recorded `_user` address. [4](#0-3) [5](#0-4) [6](#0-5) 

The user cannot work around this by transferring the receipt: `IdleCreditVault._transfer` reverts unless `msg.sender == idleCDO`, so ordinary holders cannot move strategy-token receipts to a clean account. [7](#0-6) 

The atomic revert protects accounting, but it also makes the failure repeatable: burning and request clearing are rolled back when the underlying-token transfer reverts, while the payout remains permanently claimable only by the blacklisted address. [8](#0-7) 

### Impact Explanation

A lender can permanently lose access to the full funded withdrawal amount, including principal and accrued withdrawal interest. For loss-adjusted or default-recovery claims, the affected amount is the user’s corresponding recovery payout.

This is direct permanent freezing of otherwise withdrawable protocol funds. The funds remain isolated in `IdleCreditVault`; other users cannot claim them, and the rightful claimant cannot redirect them.

### Likelihood Explanation

Likelihood is low because it requires a centralized underlying token, such as a stablecoin, to blacklist the claimant after the withdrawal receipt is created. However, no privileged Idle role is required to trigger the impact: it is caused solely by the token contract’s transfer restriction combined with the fixed `_user` payout.

### Recommendation

Add a recipient parameter to the externally callable claim entry points and pass it through to `_transferFundedClaim` and `_transferDefaultRecovery`.

For example, introduce a CDO-to-strategy API equivalent to:

```solidity
function claimWithdrawRequest(address user, address receiver)
```

Then replace:

```solidity
_transferFundedClaim(_user, amount);
```

with:

```solidity
_transferFundedClaim(receiver, amount);
```

The claim authorization and receipt burn must remain bound to `_user`; only the underlying payout destination should be configurable. Apply the same recipient routing to funded normal claims, instant claims, post-default claims, loss-adjusted claims, and default-recovery claims.

### Proof of Concept

A reproducible Foundry PoC can use a forked credit-vault deployment or the existing vault test harness with a blacklistable ERC20 underlying:

```solidity
function test_blacklistedWithdrawRecipient_freezesClaim() public {
    // Lender deposits and receives tranche tokens.
    underlying.mint(lender, depositAmount);
    vm.prank(lender);
    underlying.approve(address(cdo), depositAmount);
    vm.prank(lender);
    cdo.depositAA(depositAmount);

    // During the buffer period, lender requests the withdrawal.
    vm.prank(lender);
    cdo.requestWithdrawAA(requestAmount);

    // Manager starts and later stops the epoch so the request is funded.
    vm.prank(manager);
    cdo.startEpoch();
    vm.warp(epochEnd + 1);
    vm.prank(manager);
    cdo.stopEpoch(apr, interest);

    // The underlying token contract blacklists the original beneficiary.
    vm.prank(underlyingOwner);
    underlying.addToBlackList(lender);

    // The claim reverts even though the request is funded.
    vm.prank(lender);
    vm.expectRevert(); // blacklistable token transfer revert
    cdo.claimWithdrawRequest();

    // The receipt remains owned by the blacklisted lender and cannot be
    // transferred to a clean beneficiary because strategy-token transfers
    // are permitted only from idleCDO.
    assertEq(strategy.withdrawsRequests(lender), requestAmount);
    assertEq(strategy.balanceOf(lender), requestAmount);
    vm.prank(lender);
    vm.expectRevert();
    strategy.transfer(cleanReceiver, requestAmount);
}
```

The sequence demonstrates that the invariant “one funded receipt has one payable beneficiary” is broken in practice when that sole beneficiary cannot receive the underlying token. The user cannot choose a clean receiver or transfer the receipt claim, so the funded withdrawal remains permanently unclaimable. [9](#0-8) [10](#0-9)

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }

  /// @notice Claim a defaulted normal withdraw receipt with the finalized recovery haircut.
  /// @param _user address of the user
  /// @return amount amount paid from default recovery reserve
  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  /// @notice Claim a stopEpochWithDuration loss-adjusted withdraw receipt.
  /// @param _user address of the user
  /// @return amount amount paid from funded strategy underlyings
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  /// @notice Transfer a funded claim without spending default recovery reserve.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @inheritdoc ERC20Upgradeable
  /// @dev Receipt claims are address-bound, so only the IdleCDO can move strategy tokens.
  function _transfer(address sender, address recipient, uint256 amount) internal virtual override {
    if (msg.sender != idleCDO) revert NotAllowed();
    super._transfer(sender, recipient, amount);
  }

  /// @notice Clear the deprecated receipt-token transfer flag.
  /// @dev Kept for upgrade compatibility. Enabling transfers is permanently disabled because
  /// receipt claims are address-bound; the manager may only clear a legacy `true` value.
  /// @param _canTransfer must be false
  function setCanTransfer(bool _canTransfer) external {
    if (msg.sender != manager || _canTransfer) revert NotAllowed();
    canTransfer = false;
  }
