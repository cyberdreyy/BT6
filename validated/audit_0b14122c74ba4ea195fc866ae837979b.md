Based on my analysis, I found a concrete, in-scope analog: the `batchMint` operation in Base's B20 precompile.

### Title
All-or-nothing `batchMint` reverts the entire batch when any single recipient is blocked by `MintReceiver` policy or the token is paused, letting one unauthorized/blocked address deny mint delivery to every other unrelated recipient - (File: crates/common/precompiles/src/b20_asset/logic/v1.rs and v2.rs)

### Summary
The B20 asset/stablecoin precompile exposes `batchMint(address[] recipients, uint256[] amounts)`, documented as "All-or-nothing", which loops over `recipients` and calls the same privileged `mint` path for every entry [1](#0-0) . Each iteration re-enforces `B20Guards::ensure_policy_type(token, B20PolicyType::MintReceiver, to)` and the pause check inside `mint` [2](#0-1) . If any single recipient in the batch is denied by the `MintReceiver` policy (or the token is paused for `MINT`), the whole `batch_mint` call returns `Err`, aborting the transaction and reverting every state change already staged for the other, unrelated, unblocked recipients in the same call [3](#0-2) . This mirrors the reported bug class in `CrabNetting.sol`: a batch operation intended to serve many independent parties is fully blocked by policy/pause state tied to just one of them.

### Finding Description
`batchMint` is implemented identically in `AssetV1`/`AssetV2` and the B20 stablecoin equivalents: it validates lengths, rejects an empty batch, then iterates `recipients.into_iter().zip(amounts)` calling `self.mint(token, caller, recipient, amount, true)` for each pair [4](#0-3) . Because `mint` is called with `privileged = true`, the `MINT_ROLE` check is skipped, but `B20Guards::ensure_policy_type(token, B20PolicyType::MintReceiver, to)` is still enforced per-recipient and is not bypassed by the caller's privilege [5](#0-4) . There is no per-recipient catch/skip: `self.mint(...)?` short-circuits the whole loop on the first `Err`, which is exactly the "reverts as a whole on the failing element" pattern the external report describes for `netAtPrice()`/`withdrawAuction()`. A `MintReceiver` policy can be set to `ALWAYS_BLOCK` or a custom blocklist via `updatePolicy`, as demonstrated in the harness test `b20_always_block_mint_receiver_policy_blocks_mint_recipient` [6](#0-5) , and the same block also applies inside a `batchMint` call because the guard runs unconditionally on `privileged`.

### Impact Explanation
Any operator (e.g., an exchange, payroll system, or airdrop tool) that batches many independent recipients into one `batchMint` call can have the entire batch fail because of a single address that is currently policy-blocked or because the token's `MINT` feature is paused. Time-sensitive batched mint operations (e.g., scheduled payouts) are denied for all legitimate recipients whenever one recipient in the same call is on a blocklist or the feature is paused, causing operational disruption/denial of service for the batch caller until the offending recipient is removed from the request or unblocked. This does not enable theft of funds and is bounded to the caller's own batch, so severity is Medium rather than High/Critical — it is a availability/DoS issue on an intentional "all-or-nothing" primitive rather than a permanent freeze of already-held user funds (contrast with the CrabNetting case, where funds already escrowed in the contract get stuck).

### Likelihood Explanation
Any account holding `MINT_ROLE` (or calling through the privileged factory path) that constructs a `batchMint` with recipients it does not fully control (e.g., a third-party allowlist or user-submitted address list) can trivially trigger this by including one blocked/paused address, whether accidentally or via griefing from outside if the recipient list is derived from external input.

### Recommendation
Given the doc comment already declares `batchMint` "All-or-nothing" as an intentional design choice, the primary mitigation is documentation/API-level: callers should pre-filter recipients against policy state (e.g., via a read-only `isAuthorized`-style check) before submitting the batch, or the precompile could expose an alternative batched entry point that skips/report per-recipient failures instead of aborting the whole call, analogous to the try-catch mitigation suggested in the original report.

### Proof of Concept
1. Grant `MINT_ROLE` to `ALICE` and set `B20PolicyType::MintReceiver` to `PolicyRegistryStorage::ALWAYS_BLOCK_ID` (or a custom blocklist policy containing one target address), as done in `b20_always_block_mint_receiver_policy_blocks_mint_recipient` [7](#0-6) .
2. Call `batchMint([BOB, BLOCKED_ADDR, CAROL], [amt1, amt2, amt3])` from `ALICE`.
3. `batch_mint` iterates and calls `mint` for `BOB` (succeeds, staged), then for `BLOCKED_ADDR`, `B20Guards::ensure_policy_type` returns `PolicyForbids`, propagating `Err` out of the loop [8](#0-7) .
4. The precompile dispatcher surfaces this as a revert for the entire `batchMint` transaction, so `BOB`'s and `CAROL`'s legitimate mints never land, even though only `BLOCKED_ADDR` was invalid.

```rust
    fn batch_mint(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        recipients: Vec<Address>,
        amounts: Vec<U256>,
        privileged: bool,
    ) -> Result<()> {
        // The pause and role guards below are the sole authorization gate for the batch: the inner
        // mints run privileged to avoid re-checking per recipient. Do not remove or conditionalize
        // these guards. Check order: PAUSE -> ROLE -> INPUT -> BUSINESS.
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::MINT)?;
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::Mint)?;
        }
        if recipients.len() != amounts.len() {
            return Err(BasePrecompileError::revert(IB20Asset::LengthMismatch {
                leftLen: U256::from(recipients.len()),
                rightLen: U256::from(amounts.len()),
            }));
        }
        if recipients.is_empty() {
            return Err(BasePrecompileError::revert(IB20Asset::EmptyBatch {}));
        }
        for (recipient, amount) in recipients.into_iter().zip(amounts) {
            self.mint(token, caller, recipient, amount, true)?;
        }
        Ok(())
    }
```

```rust
/// `MINT_RECEIVER_POLICY` gates the recipient for direct mint calls.
#[tokio::test]
async fn b20_always_block_mint_receiver_policy_blocks_mint_recipient() {
    let mut scenario = B20PolicyScenario::new().await;

    let grant_mint_role = scenario.token_tx(IB20::grantRoleCall {
        role: B20TokenRole::Mint.id(),
        account: BerylTestEnv::alice(),
    });
    let block = scenario.build_block(vec![grant_mint_role]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "MINT_ROLE grant must succeed");

    let mint_allowed =
        scenario.token_tx(IB20::mintCall { to: BerylTestEnv::bob(), amount: TRANSFER_AMOUNT });
    let block = scenario.build_block(vec![mint_allowed]).await;
    assert!(
        scenario.env.user_tx_succeeded(&block, 0),
        "mint must succeed before policy is blocked"
    );
    scenario.assert_balance(BerylTestEnv::bob(), 1);

    let wire_mint_receiver = scenario.token_tx(IB20::updatePolicyCall {
        policyScope: B20PolicyType::MintReceiver.id(),
        newPolicyId: PolicyRegistryStorage::ALWAYS_BLOCK_ID,
    });
    let block = scenario.build_block(vec![wire_mint_receiver]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "mint receiver updatePolicy must succeed");

    let blocked =
        scenario.token_tx(IB20::mintCall { to: BerylTestEnv::carol(), amount: TRANSFER_AMOUNT });
    let block = scenario.build_block(vec![blocked]).await;
    assert!(
        !scenario.env.user_tx_succeeded(&block, 0),
        "mint must revert when recipient is blocked by MINT_RECEIVER_POLICY"
    );
    scenario.assert_balance(BerylTestEnv::bob(), 1);
    scenario.assert_balance(BerylTestEnv::carol(), 0);

    scenario.derive().await;
}
```
