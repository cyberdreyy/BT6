### Title
Rejection Recounted as Acceptance via Unchecked `mark_locally_accepted` Result — ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_signature` ignores the failure of `BlockInfo::mark_locally_accepted`, and that failure occurs exactly when a block has already reached a terminal `GloballyRejected` state — yet the side effect of stamping `signed_group` still happens, and the function unconditionally persists the block and broadcasts it to the node regardless of the error. This mirrors the reported analog class: "the `approve`-like function may return an error and the caller does not process the result," here allowing a signer to push a block it has already recorded as globally rejected.

### Finding Description
`BlockInfo::mark_locally_accepted` in `stacks-signer/src/signerdb.rs` (~lines 279–289) is: [1](#0-0) 
```rust
pub fn mark_locally_accepted(&mut self, group_signed: bool) -> Result<(), String> {
    if group_signed {
        self.signed_group.get_or_insert(get_epoch_time_secs());
    } else {
        ...
    }
    self.move_to(BlockState::LocallyAccepted)
}
```
The `signed_group` timestamp is stamped **unconditionally, before** the state-transition check `move_to(BlockState::LocallyAccepted)` runs. `move_to`/`check_state` explicitly forbid this transition when the block's current state is `GloballyRejected` or `GloballyAccepted` [2](#0-1) , i.e. these are meant to be terminal states ("Global states are terminal against each other," per `docs/signer-flows.md`).

The caller, `store_and_process_block_signature`, does: [3](#0-2) 
```rust
if let Err(e) = block_info.mark_locally_accepted(true) {
    if !block_info.has_reached_consensus() {
        warn!("{self}: Failed to mark block as locally accepted: {e:?}");
    }
}
let _ = self.signer_db.insert_block(block_info).map_err(...);
self.broadcast_signed_block(stacks_client, block_info.block.clone(), &addrs_to_sigs);
```
The only case in which `mark_locally_accepted` returns `Err` is precisely the case where `block_info.has_reached_consensus()` is `true` (block already `GloballyRejected`/`GloballyAccepted`), so the `warn!` never fires and the `Err` is completely swallowed. Execution falls through unconditionally to `insert_block` (persisting the now-tainted `signed_group` field even though `state` is still `GloballyRejected`) and to `broadcast_signed_block` → `handle_post_block` → `stacks_client.post_block(block)` [4](#0-3) , i.e. the signer actively pushes a "signed" block to its own node even though its local signer DB still records that block as globally rejected.

This is reachable without collusion of a majority of signers: `add_block_signature` and `add_block_rejection_signer_addr` are independent tables that both persist entries "for auditing purposes... even on consensus reached blocks" [5](#0-4) , and a signer can legitimately re-evaluate and flip its vote (the state diagram explicitly allows `LocallyRejected --> LocallyAccepted : re-evaluated`). If enough weight in the rejection table crosses the 30% blocking-minority threshold (marking the block `GloballyRejected` via `store_and_process_block_rejection`, lines 2335–2341) while gossip continues to deliver `Accepted` `BlockResponse`s from signers who flip their vote (triggered by a miner re-proposing the block, causing `should_reevaluate_block`/re-evaluation on other signers), the signature table can independently cross the 70% acceptance weight later. When that happens on this signer, `store_and_process_block_signature` runs the buggy branch above.

### Impact Explanation
This falls under "Critical – a rejection recounted as an accept." A block that this signer's own state machine considers terminally, globally rejected gets `signed_group` set and is broadcast/pushed to the node as if group-accepted, defeating the terminal/sticky guarantee of `GloballyRejected` that `check_state` was designed to enforce. It can help finalize a block that was already correctly identified and rejected by the local signer, corrupting the audit trail (`signed_group`) that other logic (e.g. `has_signed_block_in_tenure`) relies on for miner-inactivity and liveness decisions.

### Likelihood Explanation
No majority collusion or key compromise is required — only ordinary flip-flopping of votes by some already-known signers (a supported protocol re-evaluation flow) combined with normal gossip propagation and a miner re-proposing the block. The exact conditional (`if !block_info.has_reached_consensus()`) that guards the warning is tautologically false in the one case the error occurs, so the bug is guaranteed to be silent whenever triggered, and the code path (`insert_block` + `broadcast_signed_block`) always executes regardless.

### Recommendation
- In `mark_locally_accepted` (and the analogous `mark_pre_committed`/`mark_globally_accepted`/`mark_globally_rejected`), only mutate `signed_group`/`approved_time`/etc. *after* `move_to` succeeds, not before, so a rejected state transition has no side effects.
- In `store_and_process_block_signature`, propagate the `Err` from `mark_locally_accepted` unconditionally (return early on any error, not just when `!has_reached_consensus()`), so `insert_block` and `broadcast_signed_block` never run against a block whose state transition was refused.

### Proof of Concept
1. Signer S receives enough `BlockResponse::Rejected` messages for block `B` to cross the 30% blocking-minority weight; `store_and_process_block_rejection` calls `block_info.mark_globally_rejected()` and persists `state = GloballyRejected` [6](#0-5) .
2. The miner re-proposes / signers re-evaluate, and a set of signers whose combined weight (added to any other already-accepting signers) crosses 70% send `BlockResponse::Accepted` for the same `signer_signature_hash`, propagated over StackerDB gossip.
3. S's `handle_block_signature` → `store_and_process_block_signature` runs; `add_block_signature` records each new signature (allowed post-consensus, per the "auditing purposes" comment) [7](#0-6) ; total weight crosses `min_weight`.
4. `mark_locally_accepted(true)` sets `signed_group` unconditionally, then fails `move_to` because `state == GloballyRejected`; the `Err` is silently dropped because `has_reached_consensus()` is true [8](#0-7) .
5. `insert_block` persists the tainted `signed_group`, and `broadcast_signed_block`/`handle_post_block` submits the block to the node via `post_block` [9](#0-8)  — a block S's own signer DB marks `GloballyRejected` is pushed as accepted.
