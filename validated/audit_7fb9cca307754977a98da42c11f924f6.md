### Title
Repair-response token bucket permanently loses tokens when the outbound send channel is full, causing accumulating bandwidth-throttle starvation - (File: `core/src/repair/serve_repair.rs`)

### Summary
`ServeRepairService::handle_requests` mirrors the `batchContributeFor` bug pattern: it optimistically debits a shared "budget" (`data_budget: &TokenBucket`) before knowing whether the operation will ultimately succeed, and only some of the failure paths refund the debited amount. When `packet_batch_sender.try_send(rsp)` fails, the tokens already spent on `actually_used_cost` are never returned to the bucket.

### Finding Description
In `handle_requests` [1](#0-0) , `max_response_cost` is speculatively consumed from `data_budget` before the request is actually served:

```
// we deliberately consume early assuming that request succeeds,
// if it does we will refund the unused tokens
let max_response_cost = request.max_response_bytes() * byte_cost_multiplier;
if data_budget.consume_tokens(max_response_cost as u64).is_err() { ... continue; }
```

Two failure paths correctly refund the full `max_response_cost` (ping-cache check failure, `handle_repair` returning `None`) [2](#0-1) . After a response is actually built, only the *unused portion* (`max_response_cost - actually_used_cost`) is refunded before the send attempt [3](#0-2) . The code then attempts `packet_batch_sender.try_send(rsp)`, and on failure only updates drop statistics — it never calls `data_budget.add_tokens(actually_used_cost)`:

```
if packet_batch_sender.try_send(rsp).is_ok() {
    ...
} else {
    stats.dropped_requests_outbound_bandwidth += 1;
    stats.total_dropped_response_packets += num_response_packets;
}
``` [4](#0-3) 

The comment at line 1598-1600 explicitly acknowledges this drop path is "not accounted for" and dismisses it as unlikely "unless we are severely overloaded" — which is exactly the scenario in which this leak matters most, since it is self-reinforcing: as the node gets more overloaded, `try_send` fails more often, tokens leak faster, `data_budget` depletes, and `consume_tokens` starts rejecting good repair requests via the early-exit path at line 1567-1573, worsening the overload the node is trying to survive under.

`TokenBucket::consume_tokens`/`add_tokens` [5](#0-4)  confirm there is no automatic reconciliation — tokens removed via `consume_tokens` are gone unless explicitly returned via `add_tokens`; the bucket only naturally regenerates at `new_tokens_per_us`.

### Impact Explanation
This is a self-amplifying denial-of-service against the node's own repair-serving capacity (ingest/serving starvation), analogous to the Solidity bug's silent loss of ETH: a shared accounting resource (`data_budget`) is debited on the optimistic path and never restored on one of the realistic failure branches, permanently shrinking the effective bandwidth budget available to serve legitimate repair requests from other validators. Under load, this degrades cluster-wide repair service, which can slow catch-up/replay for lagging nodes — a valid unprivileged network-facing effect reachable by any peer sending enough concurrent repair requests to fill `packet_batch_sender`'s channel.

### Likelihood Explanation
Likelihood is moderate-to-high specifically under load or congestion — the exact condition the report's failure mode (`revertOnFailure=false`, or here, "outbound channel full") is designed to trigger. An external actor cannot directly force `try_send` to fail (it depends on internal channel capacity and the validator's own send-thread scheduling), but during genuinely high repair traffic (e.g., after a fork/restart storm, or an attacker flooding a validator with valid-looking repair requests to legitimately fill its `max_response_bytes` budget and outbound queue), the drop path is reachable without any authentication bypass, matching the code's own acknowledgment that this happens "unless we are severely overloaded."

### Recommendation
Refund `actually_used_cost` tokens to `data_budget` in the `else` branch of the `try_send` result at `core/src/repair/serve_repair.rs:1610-1613`, e.g.:
```rust
} else {
    data_budget.add_tokens(actually_used_cost as u64);
    stats.dropped_requests_outbound_bandwidth += 1;
    stats.total_dropped_response_packets += num_response_packets;
}
```
Apply the same fix to the `pending_pings` batch send at lines 1616-1624 if pings are also charged against the budget elsewhere.

### Proof of Concept
Conceptual trace (cannot execute in this environment, but derivable directly from the code):
1. Attacker (or organic load) sends enough valid repair requests so that `packet_batch_sender`'s bounded channel becomes full (e.g., a slow/backed-up socket-send thread).
2. For each such request, `handle_requests` consumes `max_response_cost` tokens (line 1568), passes ping-cache check, builds a valid response `rsp` via `handle_repair`, and refunds only `max_response_cost - actually_used_cost` (line 1601).
3. `packet_batch_sender.try_send(rsp)` returns `Err` because the channel is full (line 1604); the `else` branch (lines 1610-1613) records drop stats but does not call `data_budget.add_tokens(actually_used_cost)`.
4. Repeating this N times permanently removes `N * actually_used_cost` tokens from `data_budget` that were never used to actually serve any peer, shrinking the effective throughput budget for future genuine repair responses until the bucket's slow natural refill (`new_tokens_per_us`) catches up — during which legitimate repair requests get dropped at line 1571 (`dropped_requests_outbound_bandwidth`).

    pub fn consume_tokens(&self, request_size: u64) -> Result<u64, u64> {
        let now = self.time_us();
        self.update_state(now);
        match self.tokens.fetch_update(
            Ordering::AcqRel,  // winner publishes new amount
            Ordering::Acquire, // everyone observed correct number
            |tokens| {
                if tokens >= request_size {
                    Some(tokens.saturating_sub(request_size))
                } else {
                    None
                }
            },
        ) {
            Ok(prev) => Ok(prev.saturating_sub(request_size)),
            Err(prev) => Err(request_size.saturating_sub(prev)),
        }
    }

    /// Consumes up to `request_size` tokens from the bucket, draining whatever
    /// is available without requiring the full amount.
    ///
    /// Returns the number of tokens actually consumed (0..=request_size).
    /// Unlike [`consume_tokens`](Self::consume_tokens) this never fails — if
    /// fewer tokens are available than requested, all available tokens are
    /// taken and the consumed count reflects that.
    #[inline]
    pub fn consume_tokens_saturating(&self, request_size: u64) -> u64 {
        let now = self.time_us();
        self.update_state(now);
        let mut consumed = 0u64;
        let _ = self.tokens.fetch_update(
            Ordering::AcqRel,  // winner publishes new amount
            Ordering::Acquire, // everyone observed correct number
            |tokens| {
                consumed = tokens.min(request_size);
                Some(tokens.saturating_sub(consumed))
            },
        );
        consumed
    }

    /// Adds given amount of tokens, up to a maximum of self.max_tokens.
    #[inline]
    pub fn add_tokens(&self, new_tokens: u64) {
        let _ = self.tokens.fetch_update(
            Ordering::AcqRel,  // writer publishes new amount
            Ordering::Acquire, //we fetch the correct amount
            |tokens| Some(tokens.saturating_add(new_tokens).min(self.max_tokens)),
        );
    }
