### Title
Cross-user callback hijack via MessageId collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `handler.HandleLegacyUserMessage` and `handler.handleWebAPITriggerMessage` functions key the `savedCallbacks` map solely by `msg.Body.MessageId`, with no binding to the caller's identity (signer/sender). An attacker who submits a request with the same `MessageId` as a victim's in-flight request overwrites the victim's saved callback, causing the eventual node response (correlated only by `MessageId`) to be delivered to the attacker's callback channel instead of the victim's.

### Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` (lines 264–276) accepts a user-supplied JSON-RPC request, calls `msg.Validate()` (which only checks length/format and derives `Sender` from the signature, `api/message.go` lines 54–88), and then calls `h.HandleLegacyUserMessage(ctx, msg, callback)`. Crucially, `Message.Body.MessageId` is entirely attacker-controlled (any string ≤128 bytes not ending in a null byte) — there is no per-sender namespacing or uniqueness enforcement against other users' IDs.

In `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:411-414`):
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
```
this unconditionally overwrites any existing entry for the same `MessageId`, regardless of who created it. There is no check for `Sender` prior to insertion, and no rejection when a `MessageId` is already active in the map.

Later, when a node response for the *original* (victim's) request arrives, `HandleNodeMessage` (line 248) validates only that `msg.Body.Sender == nodeAddr` (the responding node's address) — not that the correlated `MessageId` still belongs to the original callback owner. It routes into `handleWebAPITriggerMessage` (lines 148-162), which does:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
```
Because the map is keyed only by `MessageId`, if attacker A's `HandleLegacyUserMessage` call with the same `MessageId` executed after victim B's, A's callback object now occupies the slot. The node's response to B's original request is looked up by that same `MessageId` and delivered to A's callback — B never receives a response (timeout) and A receives a response body that was never intended for them.

Nothing in the request path (gateway HTTP entrypoint, `msg.Validate()`, or the handler) enforces per-sender uniqueness of `MessageId`, and the signature check only proves who signed *that particular* message, not that the `MessageId` slot is exclusively owned by that signer.

### Impact Explanation
This is a cross-user response confusion vulnerability: an unprivileged/unauthenticated gateway client can intercept another user's in-flight web API trigger response by colliding on `MessageId`. Depending on payload content, this could leak information intended for another user's workflow trigger response (data disclosure) and/or cause denial of service for the victim's request (which silently times out because its callback slot is stolen). This matches Chainlink's "unauthorized action on another user's job/request" / "cross-user response confusion" bounty impact class.

### Likelihood Explanation
Exploitation requires only sending two ordinary, validly-signed HTTP/JSON-RPC gateway requests to the public user-facing gateway endpoint (`gateway.ProcessRequest`) with an attacker-chosen `MessageId` that matches (or is guessed/observed for) a victim's request, timed so the attacker's call lands after the victim's `HandleLegacyUserMessage` call but before the node responds. No special credentials beyond normal gateway API access are needed, and the race window is on the order of the node round-trip time, making it feasible for an attacker who can predict or observe MessageIds (e.g., low-entropy or client-supplied sequential IDs) or simply flood many candidate MessageIds to increase collision probability, though a targeted attack requires knowledge/prediction of victim's chosen MessageId which may reduce practical likelihood if MessageId is a client-generated random value.

### Recommendation
Bind `savedCallbacks` entries and lookups to `(Sender, MessageId)` or a server-generated unique correlation ID (not attacker-supplied) instead of `MessageId` alone. When inserting into `savedCallbacks`, reject or fail the request if an active, non-expired entry already exists for that key rather than silently overwriting it. Ensure `handleWebAPITriggerMessage`/`HandleNodeMessage` correlate node responses using the same composite key so a differing sender cannot hijack another user's slot.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Create two distinct signers (victim key, attacker key) and two `triggerRequest` messages both using the identical `MessageId` (e.g., "collide-1") but different payload/topics, each signed by its own key.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`.
3. Call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` — this overwrites `handler.savedCallbacks["collide-1"]`.
4. Construct a node response correlated to the victim's original message (`hc.ValidatedResponseFromMessage(victimMsg)`), and call `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
5. Assert that `attackerCallback.Wait(ctx)` returns the victim's response payload (`codec.EncodeLegacyResponse(victimMsg)`), while `victimCallback.Wait(ctx)` times out / never receives a response — proving cross-user callback delivery confusion.
