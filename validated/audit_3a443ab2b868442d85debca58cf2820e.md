### Title
Loss-adjusted withdraw receipts escape their haircut when a later request overwrites `lastWithdrawRequest`, letting the user claim the defaulted epoch receipt at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Cilium bug class — a broad policy shadowing a more specific one so stricter enforcement never runs — maps directly onto `IdleCreditVault.claimWithdrawRequest`: the per-epoch loss-haircut path (`_claimLossAdjustedWithdrawRequest`) is keyed only to the user's *latest* request epoch via `lastWithdrawRequest[_user]`. If a user re-requests a withdrawal after a loss-adjusted epoch, the earlier haircutted receipt falls through to the general funded path `_claimFundedWithdrawRequest`, which pays the full aggregate `withdrawsRequests[_user]` at par. The stricter per-epoch rule exists but is never consulted for the old epoch.

### Finding Description
In `claimWithdrawRequest` (IdleCreditVault.sol:301-314) the claim waterfall is:

1. `_claimPostDefaultWithdrawRequest` / `_claimDefaultedWithdrawRequest` (only when `defaultRecoveryFinalized`)
2. `_claimLossAdjustedWithdrawRequest` — looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only (lines 789-792)
3. `_claimFundedWithdrawRequest` — pays `withdrawsRequests[_user]` (the aggregate across all epochs) at par via `_transferFundedClaim` (lines 338-349)

`collectWithdrawFunds` (lines 411-430) records a partial funding loss as `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`, so the strategy only holds `claimBasis * lossRecoveryPrice` for that epoch's receipts.

Attack sequence:

1. Epoch N (buffer): attacker calls `requestWithdraw(X)` → `withdrawsRequestsByEpoch[user][N] = X`, `lastWithdrawRequest[user] = N`, `pendingWithdraws += X` (lines 271-294).
2. Epoch N `stopEpoch` is underfunded: borrower returns less than pending → `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL` and `pendingWithdraws = 0`. The strategy now holds only `X * p` for that receipt.
3. Epoch N+1 (buffer): attacker calls `requestWithdraw(Y)` again (allowed — the comment at line 323 explicitly notes re-requesting merges receipts). Now `lastWithdrawRequest[user] = N+1` and `withdrawsRequests[user] = X + Y`.
4. Epoch N+1 `stopEpoch` funds Y fully (`pendingWithdraws` returns to 0, no entry in `lossRecoveryPriceByEpoch[N+1]`).
5. After epoch N+1 ends, attacker calls `claimWithdrawRequest`. The gate `epochNumber <= lastWithdrawRequest` passes. `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0 — the epoch-N haircut is never found. `_claimFundedWithdrawRequest` then burns `X + Y` receipt tokens and transfers `X + Y` underlying at par.

The attacker receives `X` instead of `X * p / RECOVERY_FULL`. The excess `(X * (1 - p))` comes out of underlyings held for other epochs' loss-adjusted claimants and the funded reserve, i.e. direct theft plus insolvency for honest users whose claims now exceed the strategy balance.

### Impact Explanation
Direct theft / insolvency: a user with a loss-adjusted receipt can withdraw it at par, extracting `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` more than entitled. Since the strategy only received the haircutted amount, the payout drains funds reserved for other users' claims in the same loss epoch, leaving the last claimants unpaid. Broken invariant: fair burn (one receipt, haircutted payout) and loss-waterfall isolation per epoch.

### Likelihood Explanation
Requires a `stopEpochWithDuration` underfunded stop (a realized borrower shortfall, not necessarily a full default), followed by the attacker re-requesting in a subsequent epoch — both normal, unprivileged user flows documented in the code's own NOTE comments. Any unprivileged tranche holder can do this; no privileged cooperation needed beyond honest manager stop calls.

### Recommendation
Track loss-adjusted claims per epoch rather than via a single `lastWithdrawRequest` pointer: iterate the user's epochs with non-zero `lossRecoveryPriceByEpoch`, or store a per-user set of loss epochs. At minimum, `_claimLossAdjustedWithdrawRequest` should check all epochs with entries in `withdrawsRequestsByEpoch[_user]`, not only `lastWithdrawRequest[_user]`. Alternatively, settle/clear any prior loss-adjusted receipt inside `requestWithdraw` when a new request is made.

### Proof of Concept
Foundry fork test sketch (modeled on `test/foundry/IdleCreditVault.t.sol` `testClaimWithdrawRequest*`):

```solidity
// setup: deposit, run epoch N-1, stopEpoch fully funded
uint256 mintedAA = idleCDO.depositAA(amountWei);

// epoch N buffer: attacker requests withdraw X
cdoEpoch.requestWithdraw(X, address(AAtranche));

// epoch N runs; borrower returns only partial pending -> loss epoch
_startEpochAndCheckPrices(N);
uint256 pending = strategy.pendingWithdraws();
deal(underlying, borrower, partialAmount); // partialAmount < total owed
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpochWithDuration(lossAmount, ...); // triggers collectWithdrawFunds(_amount < pendingBasis)
assertGt(strategy.lossRecoveryPriceByEpoch(N), 0);
assertLt(strategy.lossRecoveryPriceByEpoch(N), RECOVERY_FULL);

// epoch N+1 buffer: attacker re-requests Y
cdoEpoch.requestWithdraw(Y, address(AAtranche));
assertEq(strategy.lastWithdrawRequest(attacker), N + 1);

// epoch N+1 stop fully funded
_startEpochAndCheckPrices(N + 1);
_stopEpochAndCheckPrices(N + 1, apr, expectedFullFunds);

// claim: haircutted receipt X paid at par
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
assertEq(underlying.balanceOf(attacker) - balPre, X + Y); // should be X*p/FULL + Y
```
