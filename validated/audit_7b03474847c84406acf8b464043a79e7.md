## Finding: `distribute_internal` selects the commission-beneficiary recipient using the *caller-supplied* `operator` argument, not the address that actually earned the distribution share, allowing stale post-`switch_operator` commission entries to bypass beneficiary routing

### Summary
`distribute_internal` iterates the `distribution_pool` shareholders and redirects a share to `beneficiary_for_operator(operator)` only `if (recipient == operator)`, where `operator` is the parameter passed by the caller of the public, permissionless `distribute(staker, operator)` entry function. After `switch_operator` moves a `StakingContract` from the `old_operator` key to the `new_operator` key while leaving an unredeemed distribution share still keyed at `old_operator` (the newly-unlocked commission requested via `request_commission_internal` right before the key swap), any later call to `distribute(staker, new_operator)` will find that stale `old_operator` share, but the equality check `recipient == operator` compares it against `new_operator`, not `old_operator`. The beneficiary redirection therefore never fires for that share, and the funds are paid directly to `old_operator`'s raw account instead of the beneficiary `old_operator` had configured via `set_beneficiary_for_operator`.

### Finding Description
- `distribute` is `public entry`, callable by anyone with any `(staker, operator)` pair that has an existing staking contract — no signer/role check is required beyond the pair existing. [1](#0-0) 
- `switch_operator` removes the `StakingContract` from the map under `old_operator`, calls `distribute_internal(staker, old_operator, ...)` to flush already-inactive funds, then calls `request_commission_internal(old_operator, ...)`, which adds a **new**, not-yet-redeemed distribution share keyed at `old_operator` for the newly-unlocked (still `pending_inactive`) commission, and only *after that* re-inserts the struct into the map under `new_operator`. [2](#0-1) [3](#0-2) 
- The commission recipient-selection logic in `distribute_internal` only redirects to the beneficiary when the share's recorded `recipient` equals the `operator` value passed into the *current* call: [4](#0-3) 
- Once the lockup expires and the pending commission becomes `inactive`, anyone can call `distribute(staker, new_operator)`. `distribute_internal` is invoked with `operator = new_operator`, but the stale share's `recipient` is still `old_operator`. Since `old_operator != new_operator`, the `beneficiary_for_operator` lookup is skipped, and the payout goes straight to `old_operator`'s account instead of whatever beneficiary `old_operator` had set via `set_beneficiary_for_operator`.

### Impact Explanation
This breaks the invariant claimed in the module's own spec documentation — "unlocked funds are correctly distributed to recipients based on their distribution shares... Operator commission is recorded under the operator address ... but may ultimately be paid to a separate beneficiary address during distribution" — for the specific window of commission requested immediately before a `switch_operator` call. The value is not stolen by an attacker's own address; it still reaches the entity that actually earned it (`old_operator`), but it is diverted away from the address that operator explicitly configured to receive their commission. If an operator relies on a beneficiary address for operational reasons (e.g., a compromised or deprecated signing key for the operator address, or a multisig/treasury beneficiary), this stale-share bug silently reroutes their commission to the address they intended to stop using, which is exactly the kind of "beneficiary-update paths must not redirect value" break called out in the review scope.

### Likelihood Explanation
Any unprivileged account can trigger the vulnerable code path simply by calling `distribute(staker, new_operator)` after a legitimate `switch_operator`/`switch_operator_with_same_commission` transaction has occurred and the previously-pending commission has become withdrawable — no special privileges are required for the trigger itself. However, the vulnerable *state* (a stale distribution share surviving a key change in `staking_contracts`) only arises through the staker's own legitimate `switch_operator` action, so the "attacker" role here is limited to permissionless observers who race to call `distribute` before the affected operator does so themselves; it is not an attacker-orchestrated state-corruption exploit.

### Recommendation
In `distribute_internal`, resolve the beneficiary using the address that actually earned each share rather than the `operator` argument passed into the call — e.g., store the commission-earning operator's address alongside each distribution entry (or resolve beneficiary lookups at `request_commission_internal`/`add_distribution` time, before the operator key changes), so that stale shares created under a prior operator are still routed through that prior operator's beneficiary when eventually redeemed.

### Proof of Concept
1. `staker` creates a staking contract with `operator_1`; `operator_1` calls `set_beneficiary_for_operator(operator_1, beneficiary)`.
2. Let rewards accrue so unpaid commission exists.
3. `staker` calls `switch_operator(staker, operator_1, operator_2, new_commission_pct)`. Internally this calls `request_commission_internal(operator_1, ...)`, which does `add_distribution(operator_1, staking_contract, operator_1, commission_amount)` — creating a distribution share keyed at `operator_1` — and then moves the `StakingContract` under key `operator_2`. [2](#0-1) 
4. Advance epochs until the lockup expires and the pending commission becomes `inactive`.
5. Anyone calls `distribute(staker, operator_2)`. Inside `distribute_internal`, `operator = operator_2`, but the pool's stale shareholder is `operator_1`; `recipient == operator` (`operator_1 == operator_2`) is false, so `beneficiary_for_operator` is never consulted, and the commission is paid directly to `operator_1` instead of `beneficiary`. [5](#0-4) 

A unit test analogous to the existing `test_update_commission`/`switch_operator` tests in this file can assert that after step 5, `beneficiary`'s coin balance is unchanged while `operator_1`'s balance increased by the commission amount, demonstrating the beneficiary-routing invariant is violated. [6](#0-5)

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );
