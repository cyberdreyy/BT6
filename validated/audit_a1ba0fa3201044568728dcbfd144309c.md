## Title
`BlockRejection` signature does not bind `reason_code` / `response_data` (reorg-reject reason, `failed_txid`), letting the signed content be detached from its meaning - ([File: libsigner/src/v0/messages.rs])

## Summary
This is the same bug class as the pico `read_write` finding: a signature/lookup commits to only a *subset* of the semantically meaningful fields, while the rest are consumed downstream as if they were equally authenticated. In `BlockRejection`, the cryptographic signature covers only `signer_signature_hash` (plus `chain_id` via the domain tuple), but `reason`, `reason_code`, and the entire `response_data` (`reject_reason`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`, `failed_txid`) are left unauthenticated by that signature, even though signer.rs and the miner's `stackerdb_listener.rs` both treat these fields as if they carried the same authenticity as the recovered public key.

## Finding Description
`BlockRejection::hash()` and `verify()`/`recover_public_key()` compute the signed digest from only the block's `signer_signature_hash` and `chain_id`: [1](#0-0) 

Yet the struct carries several additional fields that are *not* part of that digest: [2](#0-1) 

On the consuming side, both other signers and the block-proposing node recover the public key using only `hash()`/hash-equivalent verification, and then unconditionally trust the un-signed `reason_code` / `response_data` fields for consensus-relevant bookkeeping:

- `stacks-signer/src/v0/signer.rs::handle_block_rejection` recovers the pubkey from `rejection.recover_public_key()` (i.e., only over `signer_signature_hash`), then forwards `rejection.response_data.reject_reason` into `store_and_process_block_rejection` as if it were an authenticated part of the message: [3](#0-2) 

- That reason is then used to compute reorg-specific rejection weight and can flip the miner to `InvalidatedBeforeFirstBlock`: [4](#0-3) 

- On the node/miner side, `stackerdb_listener.rs` similarly only checks `rejected_data.recover_public_key() == signer_pubkey` and then trusts `rejected_data.response_data.failed_txid` / `reason_code` to accumulate "problematic transaction" weight per txid: [5](#0-4) 

Because `reason_code`/`response_data` (including `failed_txid` and `reject_reason`) fall outside the signed digest, any two `BlockRejection` payloads that share the same `signer_signature_hash`, `chain_id`, and `signature` bytes verify as equally authentic regardless of what `reason`/`reason_code`/`response_data` say. This is structurally identical to the pico `read_write` chip bug: the "opcode selector and flags" (`reason_code`, `reject_reason`, `failed_txid`) are not constrained by the lookup/signature that is supposed to authenticate the whole instruction/message.

## Impact Explanation
In principle this allows the *reason* attached to an already-signed rejection to be swapped without invalidating the signature: for example, changing an unrelated `ValidationFailed` rejection into a `ReorgNotAllowed` rejection (to push weight toward marking the current miner `InvalidatedBeforeFirstBlock`, a liveness-affecting state transition), or attaching an arbitrary `failed_txid` to mark an unrelated transaction as "problematic" on the node side, biasing which transactions future block templates exclude.

However, I was not able to confirm within this repo that this is independently reachable by a non-majority attacker without the signer's key: both StackerDB writes (from a signer to its own slot) and the node's StackerDB listener are gated by slot-ownership and chunk-level signature verification that is expected to cover the *entire* posted chunk bytes (the full serialized `SignerMessage`, including `response_data`). I located `StackerDBChunkData` only by name (`libstackerdb/src/libstackerdb.rs`) and could not retrieve its `sign`/`verify` implementation in this session to confirm whether that outer chunk-level signature actually binds the full byte payload (which would foreclose this attack, since forging a new chunk without the signer's key would fail chunk verification) or whether it too only covers a partial digest (which would make this directly exploitable by anyone relaying StackerDB traffic, satisfying the "plus gossip" scope). This is a genuine gap in my verification, not a confirmed non-issue.

## Likelihood Explanation
If the StackerDB chunk-level signature (verified on write and on read replication) covers the full serialized message bytes — which is the typical StackerDB design — then this is not independently exploitable by a lone miner or gossip peer without the target signer's private key, since any attempt to swap `reason_code`/`response_data` would require re-signing the entire chunk. In that case this finding is a defense-in-depth gap (the inner application-level signature should also bind the full semantic content) rather than an immediately exploitable safety/liveness break under the stated rules. I could not fully confirm the chunk-signing scope in this session.

## Recommendation
Include `reason_code`, `chain_id`, and the full `response_data` (or at least `reject_reason` and `failed_txid`) in the digest computed by `BlockRejection::hash()`, mirroring the pico fix of constraining the whole "instruction" (opcode + all relevant flags) rather than a subset. This removes any possibility — now or if a future refactor changes StackerDB's chunk-signing scope — that the reason/consequence-bearing fields of a rejection can be detached from the authenticated part of the message.

## Proof of Concept
Not executable here: exploitability hinges on unverified transport-layer behavior of `StackerDBChunkData::sign`/verification, which I could not confirm reaches only a partial digest (in which case a gossip-level tamper of `reason_code`/`response_data` while preserving `signer_signature_hash`+`signature` would pass `BlockRejection::verify()` in both `stacks-signer/src/v0/signer.rs::handle_block_rejection` and `stacks-node/src/nakamoto_node/stackerdb_listener.rs`).

        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
