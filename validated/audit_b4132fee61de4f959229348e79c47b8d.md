### Title
Loss-adjusted withdraw receipt can be upgraded to a full-par claim by filing a second withdraw request in a later epoch — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The MariaDB bug is a crash in `update_depend_map_for_order` — dependency resolution driven by the *order* in which items were processed. The analog in `IdleCreditVault` is the ordering-dependent claim resolution in `claimWithdrawRequest`: the loss-adjusted receipt lookup is keyed **only** by `lastWithdrawRequest[_user]`, i.e. by the *latest* request epoch, not by the epoch that actually carried the haircut. A user who holds a haircutted receipt from a `stopEpochWithDuration` loss epoch can file a second `requestWithdraw` in a later epoch, which overwrites `lastWithdrawRequest[_user]`. The loss-adjusted branch then finds `lossRecoveryPriceByEpoch[newEpoch] == 0` and skips it, so the old haircutted receipt falls through to `_claimFundedWithdrawRequest` and is paid **at par**.

### Finding Description
- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user] += _amount` plus `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 282–293). The receipt tokens are minted 1:1 with the *full* requested amount.
- On a loss stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` (lines 414–421). Only `pendingToFund` underlyings are pulled in.
- In `claimWithdrawRequest` (lines 301–314), `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = lastWithdrawRequest[_user]` (line 790) and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch] == 0`. Because only the single latest epoch is consulted, an older haircutted receipt from epoch `E` is never cleared when `lastWithdrawRequest[_user] == F > E`.
- `_claimFundedWithdrawRequest` (lines 319–350) then pays `withdrawsRequests[_user]` — which still includes the untouched epoch-`E` basis — at full par once `epochNumber > lastWithdrawRequest[_user]`, and burns the full receipt balance. There is no per-epoch check that each component of `withdrawsRequests[_user]` was actually funded at par.
- Nothing else stops this: a second `requestWithdraw` while a pending receipt exists is explicitly permitted (the NatSpec note at lines 323–324 only says the user must wait another epoch); `pendingWithdraws` was already zeroed by the loss stop, so solvency checks do not fire.

The broken invariant is the loss waterfall: a receipt that should settle at `lossRecoveryPriceByEpoch[E] < 1e18` is settled at `RECOVERY_FULL`, and the shortfall is paid out of strategy underlyings that belong to the epoch-`F` receipt funding and other claimants/LPs.

### Impact Explanation
Quantified theft of `receiptE * (1 - lossRecoveryPriceByEpoch[E] / 1e18)` underlying tokens per exploit. The vault only holds `pendingToFund + fundedF` underlyings, so the attacker extracts more than was funded; whoever claims last (other withdrawers or the CDO/LPs via the active side) is left insolvent by the same amount. With a 50% haircut on a large first receipt, up to half of that receipt is stolen.

### Likelihood Explanation
Requires only an unprivileged KYC-passed lender holding tranche tokens and a loss epoch (manager-driven `stopEpochWithDuration`, honest actor). The attacker merely calls `requestWithdraw` twice across two epochs and claims once — no privileged cooperation, no timing race beyond waiting one extra epoch, which the code explicitly documents as normal behavior.

### Recommendation
Resolve loss-adjusted claims per request epoch instead of via the single `lastWithdrawRequest` pointer: iterate/check `withdrawsRequestsByEpoch[_user][e]` against `lossRecoveryPriceByEpoch[e]`, or maintain a per-user set of epochs with non-zero haircut prices and clear each at its own price in `claimWithdrawRequest` before the funded-path payout. At minimum, `_claimFundedWithdrawRequest` should subtract (or reject while present) any epoch basis whose `lossRecoveryPriceByEpoch` is non-zero and unclaimed.

### Proof of Concept
Foundry fork sketch (extends `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossReceiptUpgradedBySecondRequest() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('attacker');

    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    uint256 trancheBal = IERC20(AAtranche).balanceOf(attacker);

    // Receipt 1 in epoch E, then loss-stop epoch E
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));
    _startEpochAndCheckPrices(0);
    uint256 lossEpoch = vault.epochNumber(); // key used by collectWithdrawFunds
    // borrower underfunds -> stopEpochWithDuration(_lossAmount) sets
    // lossRecoveryPriceByEpoch[lossEpoch] = p < 1e18, pendingWithdraws = 0
    _stopEpochWithLoss(...); // as in IdleCDOEpochQueue.t.sol:817-830

    // Receipt 2 in epoch F = lossEpoch + 1 (after next stopEpoch bumps epochNumber)
    _startEpochAndCheckPrices(1);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche)); // lastWithdrawRequest = F
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Now epochNumber > lastWithdrawRequest == F.
    // _claimLossAdjustedWithdrawRequest uses lossEpoch = F -> price 0 -> skipped.
    // _claimFundedWithdrawRequest pays the full withdrawsRequests (E + F basis) at par.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    uint256 expectedHaircutted = trancheBal / 2 * vault.lossRecoveryPriceByEpoch(lossEpoch) / 1e18;
    uint256 expected = expectedHaircutted + trancheBal / 2;
    // actual payout is full par for both receipts -> strictly greater than `expected`
    assertGt(underlying.balanceOf(attacker) - balPre, expected);
}
```
