### Title
`ProgrammableBorrower` vault-replacement and unwind paths depend on the old vault's `balanceOf`/`redeem` succeeding, so a misbehaving vault permanently freezes pool funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` (the revolving-credit adapter used by `IdleCDOEpochVariant`) exposes `setVault` as the escape hatch to migrate idle capital away from a broken ERC4626 vault, and `emergencyExitVault` as the way to unwind shares first. Both functions — plus the epoch-critical views `totalInterestDueNow`/`vaultLoss`/`availableToBorrow` — unconditionally call into the *old* vault (`vault.balanceOf`, `vault.redeem`, `vault.convertToAssets`). If the old vault's view or redeem path reverts (the exact scenario these functions exist for), the migration itself reverts, `stopEpoch` reverts, and all lender capital held through the adapter is permanently frozen.

### Finding Description
In `setVault` (lines 158–170):

```solidity
if (epochAccountingActive || vault.balanceOf(address(this)) != 0) revert NotAllowed();
underlyingToken.safeApprove(address(vault), 0);
vault = IERC4626(_vault);
```

- `vault.balanceOf(address(this))` is an external call to the **old** vault. If it reverts, `setVault` always reverts — the owner can never repoint the facility to a healthy vault.
- Even when `balanceOf` works but returns non-zero, the owner must unwind via `emergencyExitVault` (lines 361–372), which itself calls `vault.balanceOf` and `vault.redeem` with no `try/catch`. A vault that reverts on `redeem` (or on `balanceOf` while `redeem` via a different path would still pay out) makes both the unwind and the replacement permanently unusable.

The damage is amplified because the *same* old-vault calls sit on the epoch hot path: `_currentVaultAssets()` feeds `totalInterestDueNow()`, `vaultLoss()`, `availableToBorrow()` and `onStopEpoch`'s `vault.withdraw`/`convertToAssets` (lines 231–268, 337–355). `IdleCDOEpochVariant.stopEpoch` calls `onStopEpoch` inside a `try/catch` that falls back to `_handleBorrowerDefault`, but the pre-stop reads (`totalInterestDueNow`) and the post-default state still depend on the vault, so a vault whose views revert blocks both the normal stop path and the vault replacement meant to rescue it.

### Impact Explanation
All pool underlying parked in the vault sleeve (`underlyingToken.balanceOf` + vault shares) becomes permanently frozen: deposits can't be redeployed (`_depositToVault` calls `vault.deposit`), the epoch can't be stopped (`stopEpoch` reads vault views / `onStopEpoch` withdraws), the default path leaves funds stranded, and the owner cannot switch vaults because `setVault` reverts on the old vault's `balanceOf`. For an `IdleCDOEpochVariant` running in programmable-borrower mode, this is a permanent freeze of all AA/BB lender capital routed through the adapter — a direct analog of `_setToken` being bricked by the old token's `approve`.

### Likelihood Explanation
Requires the configured ERC4626 vault to revert on `balanceOf`, `redeem`, `withdraw`, or `convertToAssets` — e.g., a vault that pauses/blacklists the adapter, a vault upgrade that breaks its view, or selfdestruct/implementation failure. This is precisely the "old component starts behaving incorrectly" condition `setVault`/`emergencyExitVault` exist to handle, and no unprivileged attacker action is required beyond the external dependency failing; the contract offers no fallback path once it does.

### Recommendation
Wrap interactions with the old vault in `try/catch`: in `setVault`, attempt `vault.balanceOf` inside a `try` and only enforce the zero-balance check when the call succeeds (or let the owner force the switch with an explicit flag acknowledging stranded shares). Similarly, make `emergencyExitVault` tolerate a reverting `balanceOf` (e.g., accept an explicit `_shares` amount without the view call), and consider a `try/catch` around `convertToAssets` in `_currentVaultAssets` returning a conservative value so `stopEpoch` can still settle.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Mock broken ERC4626: underlying transfers work, but views/redeem revert.
contract BrokenVault {
    IERC20 asset_;
    mapping(address => uint256) public shares;
    bool public broken;
    constructor(IERC20 a) { asset_ = a; }
    function deposit(uint256 a, address r) external returns (uint256) {
        asset_.transferFrom(msg.sender, address(this), a); shares[r] += a; return a;
    }
    function balanceOf(address r) external view returns (uint256) {
        require(!broken, "broken"); return shares[r];
    }
    function redeem(uint256 s, address r, address o) external returns (uint256) {
        require(!broken, "broken"); /* would still pay out if called directly */
    }
    function convertToAssets(uint256 s) external view returns (uint256) {
        require(!broken, "broken"); return s;
    }
    function asset() external view returns (address) { return address(asset_); }
    function breakIt() external { broken = true; }
}

function testSetVaultBrickedWhenOldVaultReverts() external {
    // setup: ProgrammableBorrower initialized with BrokenVault, epoch started,
    // pool underlying deposited into the vault via onStartEpoch/_depositToVault
    brokenVault.breakIt();

    // 1. Owner cannot unwind
    vm.expectRevert(bytes("broken"));
    borrowerAdapter.emergencyExitVault(0);

    // 2. Owner cannot migrate to a healthy vault
    vm.expectRevert(bytes("broken"));
    borrowerAdapter.setVault(address(healthyVault));

    // 3. Epoch cannot be stopped: totalInterestDueNow()/onStopEpoch revert on vault views
    vm.expectRevert();
    idleCDOEpochVariant.stopEpoch(apr, 0);

    // Result: all lender funds routed through the adapter are permanently frozen.
}
```

Note: I could not fully verify the exact revert propagation of `stopEpoch`'s pre-reads inside `IdleCDOEpochVariant` within the available iterations; the PoC should confirm whether `stopEpoch` reverts outright or falls through to `_handleBorrowerDefault` — in both cases funds remain frozen because the default path cannot recover vault-held assets either.
