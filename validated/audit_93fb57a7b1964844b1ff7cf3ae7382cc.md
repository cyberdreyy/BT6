### Title
Rejected-then-Accepted response ordering double-counts a signer's weight in both `total_weight_approved` and `total_weight_rejected` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The `BlockResponse::Accepted` handler gates its weight addition on `gathered_signatures.contains_key(&slot_id)` while the `BlockResponse::Rejected` handler gates on `responded_signers.insert(slot_id)`, using two different, non-mutually-exclusive membership tests. If a signer's `Rejected` message for a given `signer_signature_hash` is processed before its `Accepted` message for that same hash, the same slot's weight is added to `total_weight_rejected` and later also to `total_weight_approved`, breaking the invariant that a slot's weight should be attributed to exactly one bucket.

### Finding Description
`BlockStatus` tracks `responded_signers: HashSet<u32>`, `gathered_signatures: BTreeMap<u32, MessageSignature>`, `total_weight_approved: u32`, and `total_weight_rejected: u32` [1](#0-0) .

In the `Accepted` branch, the weight is added only if the slot is not yet in `gathered_signatures`, then `gathered_signatures` and `responded_signers` are both unconditionally updated: [2](#0-1) 

In the `Rejected` branch, the weight is added only if `responded_signers.insert(slot_id)` returns `true` (i.e., slot not previously present in `responded_signers`): [3](#0-2) 

Trace for the Reject-then-Accept ordering:
1. `Rejected` arrives first for `slot_id`. `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected += weight`; `responded_signers` now contains `slot_id`.
2. `Accepted` arrives second for the same hash/slot. The Accepted branch checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (Reject never touched `gathered_signatures`) → `total_weight_approved += weight` is executed. `gathered_signatures.insert(slot_id, signature)` and `responded_signers.insert(slot_id)` (no-op, already present) follow.

Result: the same slot's weight is now counted in both `total_weight_rejected` and `total_weight_approved` simultaneously, violating the intended equality that a signer's weight belongs to exactly one of the two buckets for a given block hash. Note the asymmetric case (Accept-then-Reject) does *not* double count, because the Rejected branch's `responded_signers.insert` returns `false` once `Accepted` has already inserted the slot — so the bug is specifically order-dependent (Reject observed strictly before Accept for the same hash).

This aggregation state (`total_weight_approved`, `total_weight_rejected`) is consumed by `signer_coordinator.rs`'s block-status waiting/threshold logic (`get_block_status`/`wait_for_block_status`) to decide when a block has crossed `weight_threshold` for acceptance versus rejection. With inflated `total_weight_approved`, the threshold can be reached using weight that is simultaneously recorded as rejecting weight, corrupting the accept/reject race the miner relies on to decide whether to broadcast the block.

There is no equivocation guard in this file that prevents processing a `Rejected` followed later by an `Accepted` for the same `slot_id`/hash pair — the code only guards `gathered_signatures` re-insertion (to avoid re-adding weight for a duplicate Accept) and `responded_signers` re-insertion (to avoid re-adding weight for a duplicate Reject), but does not cross-check between the two branches.

### Impact Explanation
This corrupts the miner-side vote aggregation used to gate block broadcast (`total_weight_approved >= weight_threshold` at line 467, and the parallel rejection-threshold check at lines 567-571). If enough double-counted weight accumulates, `total_weight_approved` can cross `weight_threshold` while the same weight is simultaneously recorded against `total_weight_rejected`, potentially causing the miner to treat a block as approved when a genuine majority did not actually approve it net of rejections. This falls under "a rejection recounted as acceptance," matching the Critical severity category defined in the rules, since it corrupts the accept/reject aggregation that gates whether a signed block is finalized and broadcast.

### Likelihood Explanation
The bug is purely a code-logic defect in the miner's `StackerDBListener::run` message-processing loop and requires only that, for the same block hash, a `BlockResponse::Rejected` message from a given `slot_id` be processed before a `BlockResponse::Accepted` message from that same `slot_id`. This can occur naturally through message reordering, retries, or re-relay of a block proposal causing an honest signer to re-evaluate and change its vote (the local signer-side reasoning for why the vote flips is out of scope per the prompt, but the ordering itself is a realistic possibility in an asynchronous StackerDB delivery/gossip system where messages are not guaranteed to be delivered or processed in send order). No majority of signers, no compromised keys, and no auth_token are needed — this is purely an aggregation bug on the miner side triggered by ordinary message ordering for a single legitimate signer's slot weight.

### Recommendation
Make the two branches mutually exclusive using a single source of truth for "has this slot already been counted, and in which bucket." Concretely: track a per-slot `HashMap<u32, ResponseKind>` (Accepted/Rejected) instead of the disjoint `HashSet`/`BTreeMap` checks, and when processing an `Accepted` or `Rejected` message, only add weight for a slot if it has no matching bucket entry yet; if the slot already has an entry in the opposite bucket, either ignore the new (conflicting) message, or explicitly move the weight from the old bucket to the new one (subtracting from the previous bucket before adding to the new one) so that `total_weight_approved + total_weight_rejected` never exceeds a slot's own weight and never exceeds `self.total_weight` in aggregate.
