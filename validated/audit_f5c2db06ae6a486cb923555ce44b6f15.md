### No vulnerability found for this question.

`get_last_set_cycle` in `stacks-signer/src/client/stacks_client.rs` is a read-only contract call wrapper that queries the `.signers` boot contract's `get-last-set-cycle` function to retrieve the last reward cycle for which the StackerDB signer slots were calculated [1](#0-0) . Its only caller is `RunLoop::get_signer_config`, which uses it purely as a gate to decide whether the StackerDB has been updated for a given reward cycle before the signer registers/configures itself for that cycle [2](#0-1) . The underlying contract state (`last-set-cycle`) is written only by `stackerdb-set-signer-slots`, an internal, node-only Clarity function that is not attacker-reachable [3](#0-2) .

This function has no involvement whatsoever in block-signature computation. The signature hash (`signer_signature_hash`) used for BlockProposal/BlockResponse signing and validation is computed and checked entirely within `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/signerdb.rs`, and `stacks-signer/src/chainstate/{v1,v2}.rs`, none of which call or depend on `get_last_set_cycle` [1](#0-0) . There is no code path by which a crafted BlockProposal, gossiped signer message, or StackerDB write can influence the value returned by `get_last_set_cycle`, nor any path by which that value feeds into the tenure-binding of a signature. The premise that "the signed hash omits the tenure" because of this function is not supported by any reachable code — `get_last_set_cycle` is not part of the signing/validation logic at all, only of the signer's own registration bookkeeping.

Since the target function is unreachable from the described attacker capabilities (a single miner slot plus gossiped signer/StackerDB messages) in any way that affects block signature production or validation, and it has no relationship to tenure binding of signatures, the claimed vulnerability does not exist.
