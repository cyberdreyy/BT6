### Title
ERC4626 inflation/donation attack on `ProgrammableBorrower._depositToVault` lets a first depositor steal pooled lender funds at `onStartEpoch` - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
Analogous to the Jenkins plugin blindly trusting an unauthenticated TLS endpoint, `ProgrammableBorrower` blindly trusts the external ERC4626 vault's reported share price: it deposits pool assets via `vault.deposit()` and withdraws via `vault.withdraw()`/`convertToAssets()` with no minimum-shares bound, no price sanity check, and no verification that the received shares are economically worth the deposited assets. An unprivileged attacker who is a user of the configured ERC4626 vault can run the classic first-depositor inflation attack against `_depositToVault` so the facility receives ~0 shares for its entire deposit, then redeem the inflated shares to steal the funds.

### Finding Description
- `onStartEpoch` parks all idle lender capital into the vault via `_depositToVault(underlyingToken.balanceOf(address(this)), 0)` [1](#0-0) 
- `_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and accepts whatever `shares` come back; there is no `minShares`/slippage parameter and no check that `vault.convertToAssets(shares) ≈ _assetAmount` [2](#0-1) 
- All accounting (`_vaultNetInterest`, `totalInterestDueNow`, `availableToBorrow`, the `shortfall > _currentVaultAssets()` coverage check in `onStopEpoch`) is derived from `vault.convertToAssets(vault.balanceOf(this))`, i.e., the same manipulable price [3](#0-2) [4](#0-3) 
- The same unverified trust applies to `vault.withdraw` in `_borrow` and `onStopEpoch` [5](#0-4) 

Attack path (epoch buffer → start):
1. Attacker is first depositor into the shared ERC4626 vault: deposits 1 wei for 1 share, then direct-transfers `D` underlying to the vault, inflating price-per-share to ≈ `D` (the "MitM": the price signal the borrower consumes is forged, not authenticated).
2. Manager calls `startEpoch` on the CDO; `onStartEpoch` fires and `_depositToVault` deposits the pooled lender assets `A` into the vault.
3. With `A < D`, the vault mints `floor(A / (D+1))` shares — 0 or dust — while the transfer of `A` succeeded. The code records `epochStartVaultAssets = A` but holds ~no shares.
4. Attacker redeems their single share for `≈ A + D`, profit `A`. `_vaultNetInterest` reports the loss to the pool, but the funds are already extracted, not recoverable.

### Impact Explanation
Direct theft of the full undrawn facility balance parked via `_depositToVault`. Loss magnitude = pooled idle assets `A` at epoch start (everything not already in the vault), bounded only by the attacker's donation `D > A`. Tranche holders (AA/BB) absorb the loss through the normal `vaultLoss`/`totalInterestDueNow` accounting while the attacker extracts real tokens from the vault. This also corrupts the `onStopEpoch` coverage check (`shortfall > _currentVaultAssets()`), which can be flipped the other way: deflating the vault price mid-epoch makes the pool look insolvent and pushes honest `stopEpoch` flows toward forced default.

### Likelihood Explanation
Requires the configured ERC4626 vault to accept arbitrary depositors (a permissionless vault), which is precisely the attacker model ("a user of the programmable borrower's ERC4626 vault"). No privileged role is needed: the donation and first-deposit are ordinary unprivileged transactions, and `onStartEpoch` deterministically deposits the full balance in one call, giving a reliable execution window. Guard check: none of the existing protections cover it — there is no skim of donated vault assets, no min-shares bound, no price oracle cross-check, and KYC/only-CDO gating only constrains IdleCDO entry points, not the external vault's share price.

### Recommendation
- Require a minimum-shares bound on every vault interaction: pass/verify `shares >= _assetAmount * maxSharePrice` inside `_depositToVault`, or check `vault.convertToAssets(shares)` against the deposited amount and revert on deviation beyond a small tolerance.
- Prefer vault integrations that are donation/inflation resistant (virtual shares offset à la OZ ERC4626) or use dedicated, access-controlled vaults where share price cannot be forged by arbitrary depositors.
- Track the facility's own share balance and deposited-cost basis so `vaultLoss`/`vaultInterestAccrued` reflect realized positions rather than trusting `convertToAssets` spot prices alone.

### Proof of Concept
Reproducible Foundry PoC (fork/mock vault with standard ERC4626 math):

```solidity
// test setup: Vault = standard OpenZeppelin ERC4626 over `underlying`
// ProgrammableBorrower pb initialized with vault, borrower, apr

function testFirstDepositorInflationStealsEpochDeposit() external {
    // 1) Attacker becomes first vault depositor and inflates share price
    address attacker = makeAddr("attacker");
    underlying.mint(attacker, DONATION + 1);
    vm.startPrank(attacker);
    underlying.approve(address(vault), 1);
    vault.deposit(1, attacker);                    // 1 share
    underlying.transfer(address(vault), DONATION); // price/share ~= DONATION
    vm.stopPrank();

    // 2) Lenders fund pool; manager starts epoch -> onStartEpoch -> _depositToVault
    uint256 pooled = 1_000_000e6;                  // e.g. USDC, DONATION > pooled
    underlying.mint(address(pb), pooled);
    vm.prank(address(cdo));
    pb.onStartEpoch(0);

    // 3) Facility holds ~0 vault shares but believes it has `pooled` principal
    assertEq(pb.epochStartVaultAssets(), pooled);
    assertLt(vault.balanceOf(address(pb)), 10);    // dust shares

    // 4) Attacker redeems their single share for donation + stolen pooled funds
    vm.prank(attacker);
    uint256 stolen = vault.redeem(1, attacker, attacker);
    assertGe(stolen, pooled + DONATION - 1);
}
```

The test demonstrates that `_depositToVault` performs no verification of the shares it receives (exactly the "improper verification → forged data source" class of the Jenkins MitM advisory) and that lender principal is transferred to an attacker-controlled vault position in a single `startEpoch` call.
