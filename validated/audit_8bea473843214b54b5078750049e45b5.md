### Title
Cross-user denial-of-service via shared per-node rate limiter in `HandleNodeMessage` - ([File: core/services/gateway/handlers/vault/handler.go])

### Finding Description
`(*handler).HandleNodeMessage` in the vault gateway handler gates every incoming node response with a single quota keyed only by `nodeAddr`: [1](#0-0) 

`h.nodeRateLimiter.Allow(nodeAddr)` does not take the request ID, requester identity, or `activeRequest` into account — it is a per-node token bucket shared by every user whose vault request is routed through that DON node (mirroring the `PerSenderRPS`/`PerSenderBurst` per-sender rate limiter construction pattern seen in the sibling capabilities handler config [2](#0-1)  and identically implemented in the confidentialrelay handler [3](#0-2) ).

Each user request forwarded to a node produces one node response for that node's key. An unprivileged, authenticated vault client can legitimately issue a burst of `vault.secretsList`/`vault.create` requests (each creates a distinct `activeRequest` via `newActiveRequest`, `core/services/gateway/handlers/vault/handler.go:466-481`). Because all responses from a given node consume the *same* rate-limit bucket regardless of which user's `activeRequest` they belong to, once the attacker's own traffic exhausts `nodeRateLimiter` for that `nodeAddr`, subsequent legitimate responses for *other* users' in-flight `activeRequests` to the same node are silently dropped at line 493-496 (`l.Debugw("node is rate limited", ...); return nil`). No error is surfaced to the affected victim's request — it simply never receives a response from that node, and (depending on the aggregator's quorum requirements) may stall until the request's timeout/cleanup logic fires and returns `api.RequestTimeoutError`, or fail quorum entirely if enough nodes are throttled.

This is confirmed by the exact analogous behavior test written for the sibling `confidentialrelay` handler, which explicitly asserts a second, unrelated request's callback is silently starved once the shared per-node limiter is exhausted: [4](#0-3) 

Nothing in the reachable path — JSON-RPC auth, message signature verification (`common.ValidatedMessageFromResp`), or the aggregator — restores per-user isolation; the check happens before `getActiveRequest` is even consulted, so it cannot distinguish which user's request the throttled response belongs to.

### Impact Explanation
An unprivileged vault client can, through ordinary (non-malicious-node, non-privileged) high-volume legitimate usage, deny service to other tenants sharing the same DON node by exhausting the shared `nodeRateLimiter` bucket. Victim requests silently lose their node responses, causing degraded quorum, delayed responses, or outright request timeout (`api.RequestTimeoutError`) — a cross-tenant availability impact on vault operations (secret create/list), matching the "Denial of Service" class in the DON/Gateway components.

### Likelihood Explanation
Feasibility is high: the attacker needs only a valid credential to submit vault requests (no operator/admin access) and the ability to send requests at a rate exceeding the per-node burst/RPS configured for `nodeRateLimiter`. Because the limiter has no per-sender/per-user dimension, no signature forgery or node compromise is required — ordinary retries or automated tooling routed to the same DON node are sufficient, and the attack is fully repeatable.

### Recommendation
Scope the node-response rate limiter so it cannot be exhausted by one user's traffic to starve another's: e.g., key the limiter (or an additional layer) by `(nodeAddr, requestID owner / requester identity)`, apply a fairness/priority scheme so in-flight `activeRequests` are guaranteed at least one accounted response per node regardless of global node throughput, or move the throttle to the inbound user-request path (already rate-limited per-sender elsewhere) rather than dropping already-solicited node responses indiscriminately. At minimum, log at a level that identifies the affected `requestID`/owner when a response is dropped due to rate limiting, so cross-user starvation is detectable.

### Proof of Concept
Extend `TestConfidentialRelayHandler_RateLimitedNode`-style test to the vault handler (`core/services/gateway/handlers/vault/handler_test.go`):
1. Configure `handler` with a single DON node and a `nodeRateLimiter` with burst=1 (simulating exhaustion under load).
2. Simulate "attacker": call `HandleJSONRPCUserMessage` to create `activeRequest` A, then call `HandleNodeMessage` for node A's response — consumes the sole token, callback A resolves successfully.
3. Simulate "victim": call `HandleJSONRPCUserMessage` to create a second, unrelated `activeRequest` B (different requester context/ID), then call `HandleNodeMessage` with node's response for B before the limiter refills.
4. Assert: `HandleNodeMessage` returns `nil` (no error surfaced) yet victim's callback `cb.Wait(ctx)` with a bounded timeout returns an error (never delivered) — demonstrating the victim's legitimate in-flight response was silently dropped solely due to the attacker's earlier consumption of the shared per-node quota.
5. Optionally extend cleanup/timeout logic assertions to show the victim's request eventually surfaces `api.RequestTimeoutError` from the periodic cleanup routine, confirming no distinguishable error path exists for the victim beyond a generic timeout.

```go
func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	if !h.nodeRateLimiter.Allow(nodeAddr) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}

	ar := h.getActiveRequest(resp.ID)
	if ar == nil {
		// Request is not found, so we don't need to send a response to the user
		// This can happen if a slow node responds after the request has already been completed
		l.Debugw("no pending request found for ID")
		return nil
	}
```

```go
func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		l.Debug("global relay rate limit exceeded")
		return nil
	}
```
