### Title
Front-runnable `approve()` allows allowance double-spend in B20 precompile tokens - ([File: crates/common/precompiles/src/b20_asset/logic/v1.rs])

### Summary
The B20 precompile's `approve()` implementation for both the asset and stablecoin token variants (v1 and v2 logic) unconditionally overwrites `allowance[owner][spender]` with the new value, exactly matching the classic ERC20 approve-front-running race condition described in the external report.

### Finding Description
`approve()` in `AssetV1`/`AssetV2` and `StablecoinV1`/`StablecoinV2` sets the allowance directly to the new `amount` with no dependency on, or check against, the previous allowance value: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

Because `approve()` sets the allowance to an absolute value rather than an incremental delta, an owner who wants to change a spender's allowance from A to B (e.g., decrease it) cannot do so atomically. If the spender observes the pending `approve` transaction in the mempool, it can front-run it with a `transferFrom` consuming the old allowance A (decremented via `set_allowance` in `transfer_from`), and then, once the owner's new `approve(B)` transaction lands, spend the fresh allowance B as well — consuming A+B in total instead of the owner's intended A or B: [5](#0-4) [6](#0-5) 

There is no `increaseAllowance`/`decreaseAllowance` mitigation present anywhere in the codebase, confirming the absolute-set `approve()` is the only allowance-mutation path exposed via the B20 precompile's ABI (`crates/common/precompiles/src/common/abi/v2.rs:104`).

### Impact Explanation
A spender that is granted an allowance and later has it reduced by the owner can, by front-running the owner's `approve` transaction, extract both the old and new allowance amounts — i.e. transfer more B-20 tokens out of the owner's balance than the owner ever intended to authorize at any single point in time. This is an unauthorized transfer of funds beyond the owner's most recent, intended authorization, affecting any B-20 asset or stablecoin token deployed via the precompile and any unprivileged holder who uses `approve`/`transferFrom`.

### Likelihood Explanation
The precondition is narrow: it requires an owner to actively change (typically decrease) an existing non-zero allowance to a spender who is malicious or colluding, and that spender must be able to observe the pending `approve` transaction and front-run it with `transferFrom` before the new approval lands. This is a well-known race that requires active exploitation timing (mempool visibility and fast inclusion), limiting likelihood to scenarios where allowances are actively adjusted downward for spenders that are not fully trusted.

### Recommendation
Add `increaseAllowance`/`decreaseAllowance` (delta-based) entry points to the B20 precompile interface (`IB20` in `crates/common/precompiles/src/common/abi/v2.rs`) and corresponding logic in `AssetV1`/`AssetV2`/`StablecoinV1`/`StablecoinV2`'s `approve` handling, so owners can atomically adjust allowances relative to the current on-chain value instead of unconditionally overwriting it, mirroring the mitigation recommended in the referenced Sherlock report.

### Proof of Concept
1. Alice calls `approve(Bob, 100)` on a B20 token via the precompile, setting `allowance[Alice][Bob] = 100` (`crates/common/precompiles/src/b20_asset/logic/v1.rs:247-264`).
2. Alice decides to reduce Bob's allowance and submits `approve(Bob, 50)`.
3. Bob observes this pending transaction and front-runs it with `transferFrom(Alice, Bob, 100)`, which succeeds because `allowance` is still 100, decrementing it to 0 (`crates/common/precompiles/src/b20_asset/logic/v1.rs:212-245`).
4. Alice's `approve(Bob, 50)` transaction then executes, setting `allowance[Alice][Bob] = 50` (overwriting rather than adding).
5. Bob calls `transferFrom(Alice, Bob, 50)` again, succeeding and extracting an additional 50 tokens.
6. Net result: Bob has transferred 150 tokens total, exceeding both the original (100) and updated (50) allowances Alice ever intended to be valid at once.

    fn transfer_from(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        from: Address,
        to: Address,
        amount: U256,
        privileged: bool,
    ) -> Result<()> {
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::TRANSFER)?;
        if to == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        if from == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSender { sender: from }));
        }
        let allowance = token.accounting().allowance(from, caller)?;
        let is_infinite = allowance == U256::MAX;
        if !is_infinite && allowance < amount {
            return Err(BasePrecompileError::revert(IB20::InsufficientAllowance {
                spender: caller,
                allowance,
                needed: amount,
            }));
        }
        if !privileged && caller != from {
            B20Guards::ensure_policy_type(token, B20PolicyType::TransferExecutor, caller)?;
        }
        self.transfer_inner(token, from, to, amount, privileged)?;
        if is_infinite {
            return Ok(());
        }
        token.accounting_mut().set_allowance(from, caller, allowance - amount)
    }

    fn transfer_from(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        from: Address,
        to: Address,
        amount: U256,
        privileged: bool,
    ) -> Result<()> {
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::TRANSFER)?;
        // Validate before allowance / transfer-policy-id SLOADs.
        let to = NonZeroAddress::new(to)
            .map_err(|_| BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }))?;
        let from = NonZeroAddress::new(from)
            .map_err(|_| BasePrecompileError::revert(IB20::InvalidSender { sender: from }))?;
        let allowance = token.accounting().allowance(from.get(), caller)?;
        let is_infinite = allowance == U256::MAX;
        if !is_infinite && allowance < amount {
            return Err(BasePrecompileError::revert(IB20::InsufficientAllowance {
                spender: caller,
                allowance,
                needed: amount,
            }));
        }
        if privileged {
            self.transfer_inner(token, from, to, amount, None)?;
        } else {
            // One SLOAD fetches all transfer policy ids, reused for the executor and
            // sender/receiver checks.
            let policies = token.accounting().transfer_policy_ids()?;
            if caller != from.get() {
                B20Guards::ensure_authorized_by_id(
                    token,
                    B20PolicyType::TransferExecutor.id(),
                    policies.executor,
                    caller,
                )?;
            }
            self.transfer_inner(token, from, to, amount, Some(&policies))?;
        }
        if is_infinite {
            return Ok(());
        }
        token.accounting_mut().set_allowance(from.get(), caller, allowance - amount)
    }
