### Title
Stale Confirmations from Removed Multisig Members Are Still Counted Toward Execution Threshold - (File: `multisig2/src/lib.rs`)

### Summary
The external report describes a scenario where authorization data (router signatures bound to a `transferId`) can be "replayed" outside the context in which it was originally granted, because the verification does not re-validate that the authorizing party is still a valid signer for the destination it is being used against. The analogous defect exists in `multisig2/src/lib.rs`: once a member confirms a pending request, that confirmation is permanently counted toward the `num_confirmations` threshold even after the confirming member is removed from the multisig via `DeleteMember`. `delete_member` only purges requests *originated* by the removed member, not confirmations that member gave to requests originated by *other* members. This lets a request execute using a stale confirmation from a member who is no longer part of the trusted set — i.e., `confirmations recorded == num_confirmations` while `confirmations from live members < num_confirmations`.

### Finding Description
`confirm()` counts confirmations purely by set length, without checking that every confirming identity is still present in `self.members`: [1](#0-0) 

`delete_member()` is the only place that reacts to a member being removed, and it explicitly filters requests by `r.member == member` — i.e., only requests the removed member *originated* — leaving intact any confirmations that member previously added to requests originated by someone else: [2](#0-1) 

Because `self.confirmations` is a `LookupMap<RequestId, HashSet<String>>` keyed by request, and is only cleaned up when the *request itself* is removed (via `remove_request` on execution/deletion, or via the request-origin filter in `delete_member`), a confirmation added by a member to someone else's still-pending request survives that member's removal. `assert_valid_request()` also does not re-validate the confirmations set against current membership: [3](#0-2) 

This breaks the intended custody binding: `confirmations counted toward threshold == confirmations from currently authorized (live) members`. A request can reach `num_confirmations` using one or more confirmations that were cast by a member who has since been removed (e.g., because their key was compromised or they left the organization), even though the remaining live membership never actually reached consensus.

The equivalent design flaw also exists in the v1 `multisig/src/lib.rs::DeleteKey` handling, which likewise only removes requests originated by the removed key and does not scrub that key's confirmations from other pending requests: [4](#0-3) 

### Impact Explanation
This maps directly to the Critical impact category "a multisig request executed below threshold." Funds (`Transfer` action), key additions (`AddKey`), or arbitrary `FunctionCall`/`DeployContract` actions on the multisig account can be executed with fewer genuinely-authorized (live) confirmations than `num_confirmations` requires, because a stale confirmation from a removed/untrusted member still counts. This is a real threshold-bypass, not a griefing or DoS issue, and does not require redeploying the contract, admin/owner privileges beyond the normal multisig membership, or any deviation from documented initialization.

### Likelihood Explanation
The precondition is realistic and even encouraged by normal multisig operations: members regularly confirm requests over time, and membership changes (e.g., removing a departing employee or a member whose key may be compromised) are a documented, expected action (`DeleteMember`). Any time a member is removed while they have outstanding confirmations on requests they did not originate, the remaining members are silently exposed to executing that request with less real consensus than intended. No attacker action beyond normal usage patterns (confirm, then get removed) is required to create the exposure, and any remaining member (or the removed member's residual confirmation) can complete the threshold.

### Recommendation
When removing a member via `DeleteMember`/`DeleteKey`, iterate over **all** pending requests (not just those the member originated) and strip that member's entry from each request's confirmation set, decrementing effectively toward the (possibly newly lowered) threshold. Alternatively, validate at `confirm()`/execution time that every entry in the confirmations set still corresponds to a current member of `self.members`, discarding/ignoring confirmations from members no longer present, before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 5 members `[A, B, C, D, E]` and `num_confirmations = 3`.
2. Member `A` calls `add_request` to create request `R` (e.g., `Transfer { amount }` to an account `A` or a colluding party controls).
3. Member `B` calls `confirm(R)` → confirmations = `{B}`.
4. Member `C` calls `confirm(R)` → confirmations = `{B, C}` (not yet executed, count 2 < 3).
5. The group later discovers member `C`'s key is compromised and submits/confirms a separate `DeleteMember { member: C }` request, which executes via `delete_member`. This only removes requests where `r.member == C` (requests `C` created) — request `R` (created by `A`) is untouched, and `C`'s confirmation entry inside `R`'s confirmation set is never scrubbed. Members set is now `[A, B, D, E]` (size 4, still ≥ `num_confirmations` so the removal succeeds).
6. Member `D` calls `confirm(R)` → confirmations = `{B, C, D}`, length 3 ≥ `num_confirmations` (3) → `execute_request` runs and the `Transfer` is sent.
7. Result: `R` executed using only 2 confirmations from members currently in the multisig (`B`, `D`) plus 1 stale confirmation from a member (`C`) who was removed specifically because they were no longer trusted — i.e., the request executed below the real live-member threshold, matching the Critical impact "a multisig request executed below threshold."

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
