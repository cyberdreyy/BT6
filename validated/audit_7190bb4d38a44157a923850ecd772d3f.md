### Title
`depositDuringEpoch()` under-charges management fees by excluding the buffer period, letting mid-epoch depositors mint excess tranche shares - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
`depositDuringEpoch()` credits mid-epoch depositors with interest for both the remaining epoch and the full buffer period, but calculates projected management fees using only the remaining epoch. [1](#0-0)  When a non-zero management fee and buffer period are configured, a KYC-passing lender can mint shares based on under-charged fees, diluting existing tranche holders. [2](#0-1) 

### Finding Description
The contract explicitly prorates mid-epoch deposit interest over `remaining + buffer` because the strategy APR is scaled to include the full buffer. [3](#0-2)  However, both projected management-fee deductions use only `remaining`: one for existing NAV and one for the new deposit. [4](#0-3) 

Management fees are linear in the supplied duration, so omitting `buffer` under-charges every mid-epoch deposit by `managementFee * buffer / 365 days` on its principal. [5](#0-4)  The resulting inflated `trancheInterest` is passed directly into the mint formula, producing more tranche shares than the depositor should receive. [2](#0-1) 

For example, with a 365-day epoch, 365-day buffer, 10% unscaled APR, 10% management fee, no performance fee, and a deposit halfway through the epoch, a 1,000-token deposit receives approximately `997.73` shares instead of the approximately `992.56` shares justified after charging fees for the full 1.5-year participation period. [6](#0-5) 

### Impact Explanation
This is a fair-mint invariant violation and direct value transfer from existing tranche holders to the mid-epoch depositor. [2](#0-1)  The omitted buffer-period fee increases the depositor’s projected net interest, while the same principal-backed NAV is shared across the inflated tranche supply. [7](#0-6) 

The same omission also understates the future fee burden in `expectedFinal`, but it does not fully offset the depositor-side undercharge; for profitable configurations the depositor-side effect can dominate and produce excess shares. [8](#0-7)  The loss scales with `depositAmount`, `managementFee`, and `bufferPeriod`. [9](#0-8) 

### Likelihood Explanation
The attack requires the honest owner or manager to enable mid-epoch deposits, configure a non-zero management fee, and use a non-zero buffer period. [10](#0-9)  Once enabled, any wallet satisfying `isWalletAllowed` can call `depositDuringEpoch()` during a running epoch, so no privileged role or borrower misbehavior is required. [11](#0-10) 

Existing donation skimming and accounting calls do not prevent the issue because they checkpoint already-elapsed fees but do not correct the projected fee duration used by the mint calculation. [12](#0-11) 

### Recommendation
Use the same participation duration for projected management fees that is used for projected interest:

```solidity
uint256 feeDuration = remaining + buffer;
uint256 existingMgmtFee = _calculateManagementFee(
  lastNAVAA + lastNAVBB,
  feeDuration
);
uint256 depositMgmtFee = _calculateManagementFee(_amount, feeDuration);
```

Then pass those values to `_netGainAfterFees()` instead of calculating both fees over only `remaining`. [4](#0-3) 

### Proof of Concept
Insert this test into `test/foundry/IdleCreditVault.t.sol`; it uses the existing fixture and demonstrates that the implementation mints more shares than the fair value after charging the omitted buffer-period management fee:

```solidity
function testDepositDuringEpochUnderchargesBufferManagementFee() external {
  uint256 one = ONE_SCALE;
  uint256 depositAmount = 1_000 * one;
  uint256 mgmtFee = 10_000; // 10% annualized

  _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, mgmtFee);

  vm.startPrank(manager);
  cdoEpoch.setEpochParams(365 days, 365 days);
  IdleCreditVault(address(strategy)).setAprs(10e18, 20e18);
  vm.stopPrank();

  idleCDO.depositAA(depositAmount);
  _transferBurnedTrancheTokens(address(this), true);

  vm.prank(owner);
  cdoEpoch.setIsAYSActive(false);

  _startEpochAndCheckPrices(0);

  uint256 remaining = cdoEpoch.epochDuration() / 2;
  vm.warp(cdoEpoch.epochEndDate() - remaining);

  vm.prank(owner);
  cdoEpoch.setIsDepositDuringEpochDisabled(false);

  address attacker = makeAddr("attacker");
  deal(defaultUnderlying, attacker, depositAmount);

  vm.startPrank(attacker);
  IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), depositAmount);
  uint256 minted = cdoEpoch.depositDuringEpoch(depositAmount, address(AAtranche));
  vm.stopPrank();

  uint256 navAfterCheckpoint = depositAmount -
    _calcManagementFee(depositAmount, mgmtFee, remaining);

  uint256 actualProjectedExistingFee =
    _calcManagementFee(navAfterCheckpoint, mgmtFee, remaining);
  uint256 actualExpectedFinal =
    navAfterCheckpoint + cdoEpoch.expectedEpochInterest() - actualProjectedExistingFee -
    _calcManagementFee(depositAmount, mgmtFee, remaining) -
    (cdoEpoch.expectedEpochInterest() - actualProjectedExistingFee) -
    _calcManagementFee(depositAmount, mgmtFee, remaining);

  uint256 fullDuration = remaining + cdoEpoch.bufferPeriod();
  uint256 fairExistingFee =
    _calcManagementFee(navAfterCheckpoint, mgmtFee, fullDuration);
  uint256 fairExpectedFinal =
    navAfterCheckpoint + cdoEpoch.expectedEpochInterest() - fairExistingFee;
  uint256 fairDepositInterest = _calcInterest(depositAmount) *
    fullDuration / (cdoEpoch.epochDuration() + cdoEpoch.bufferPeriod());
  uint256 fairDepositFee =
    _calcManagementFee(depositAmount, mgmtFee, fullDuration);
  uint256 fairDepositNetInterest =
    fairDepositFee >= fairDepositInterest ? 0 : fairDepositInterest - fairDepositFee;

  uint256 fairMinted = (depositAmount + fairDepositNetInterest) *
    IERC20(address(AAtranche)).totalSupply() / fairExpectedFinal;

  assertGt(minted, fairMinted, "mid-epoch deposit omitted buffer management fee");
}
```
