### Title
Panic-inducing `u16` overflow in Holocene frame-pruning during batch derivation - (File: crates/consensus/derive/src/stages/frame_queue.rs)

### Summary
The CVE-2020-28349 bug class is an inaccurate deduplication routine that a network participant can drive into an unhandled edge case, crashing the node processing untrusted input. The analogous code in Base is `FrameQueue::prune` in `crates/consensus/derive/src/stages/frame_queue.rs`, which deduplicates/prunes channel frames derived from L1 batch-inbox data once Holocene is active. This routine performs unchecked arithmetic on attacker-controlled `u16` frame numbers.

### Finding Description
`FrameQueue::prune` walks the frame queue and, for two adjacent frames belonging to the same channel, checks sequentiality with: [1](#0-0) 

```rust
if extends_channel && prev_frame.number + 1 != next_frame.number {
```

`Frame::number` is a `u16` field fully controlled by whoever posts calldata/blob data to the batch inbox address (this data is `L1Retrieval`-sourced, and the frame-number field is read directly off the wire in `Frame::decode`/`Frame::parse_frames`, with no range restriction other than the raw `u16` domain, per `crates/consensus/protocol/src/frame.rs`): [2](#0-1) 

If `prev_frame.number == u16::MAX` (65535) and the next frame in the queue shares the same channel ID, the expression `prev_frame.number + 1` overflows the `u16` type. This is the same root-cause pattern the CVE describes: an entity untrusted at the protocol layer (any L1 account can send calldata to the batch-inbox address — batcher-sender authorization is not enforced by matching the L1 tx `from` field in the derivation pipeline stages examined) supplies malformed/edge-case values into a "deduplication/ordering" comparison, and the implementation does not defensively bound the arithmetic.

In Rust, whether this triggers a hard panic or a silent wrap depends on whether overflow-checks are enabled for the build profile. No `overflow-checks = true` (or `= false`) override was found in the workspace configuration, so release builds use the Rust default (`overflow-checks = false` in `[profile.release]` unless the workspace opts in), while debug/test builds panic. This means the reachability of a hard node crash is build-profile dependent; where overflow checks are enabled (debug builds, or any release profile that has opted into `overflow-checks = true`, which many production Rust services do for safety), the comparison panics and unwinds the derivation task, halting L1 data ingestion for that node.

### Impact Explanation
`FrameQueue::prune` runs on every derivation step once Holocene is active, on every full node/verifier processing L1 batch data (this is not a builder/sequencer-only code path — it runs for any node deriving the canonical L2 chain from L1). A panic here breaks the derivation pipeline task, which:
- Halts safe/canonical-head progression for the affected node (node halt / persistent derivation failure), and
- If overflow checks are enabled in the deployed binary, can be triggered repeatedly by any single L1 transaction that posts two adjacent same-channel frames where the first has `number = 65535`, causing a denial of service against derivation for every node that ingests that L1 block.

This matches the "node halt" impact category in scope. It does not, however, cause loss of funds, unbacked supply, or incorrect provable output — it is a liveness/DoS issue analogous to the CVE.

### Likelihood Explanation
Likelihood is **conditional and not fully confirmed**:
- Reaching the vulnerable comparison only requires posting ordinary calldata/blob data to the batch-inbox address with a crafted frame (`channel_id`, `number = 0xFFFF`, `is_last = false`) followed by a second frame with the same `channel_id` — an operation any L1 account can perform economically (pay L1 gas for a calldata/blob tx).
- I was **unable to verify from the available index** whether the workspace's `Cargo.toml` `[profile.release]` enables `overflow-checks`. No `overflow-checks` setting was found via search, which typically means the Rust/Cargo default applies: `overflow-checks = false` for `--release` builds and `true` for debug/test builds. If Base's production binaries are built in `--release` mode without an explicit override (the common case), the overflow **silently wraps** instead of panicking, and the practical impact would only be an incorrect prune decision (frame retained/dropped incorrectly) rather than a crash — this would still cause a channel-completion mismatch but is a much lower-severity issue than a panic-based node halt, and may not meet the "concrete node halt" bar required by the validation rules.
- I could not fully confirm (given the truncated context) whether an upstream length check on `Frame::number` (e.g., a maximum frame count bound derived from `MAX_RLP_BYTES`/`FJORD_MAX_RLP_BYTES`) already makes `number == 65535` unreachable in practice for any channel that could actually complete, though the field itself has no such bound at decode time and Holocene's `prune()` operates before channel completion is checked.

Given this uncertainty around build profile and effective reachability of the exact boundary value, I flag this as a plausible but **not conclusively proven** finding — see recommendation below to confirm at the code level.

### Recommendation
- Replace the unchecked `+` with `prev_frame.number.checked_add(1)` (or `saturating_add`), returning a definitive "not sequential" result when the addition would overflow, matching the rest of the sequentiality logic's intent.
- Explicitly enable `overflow-checks = true` for release profiles workspace-wide (or confirm it is already set) so that arithmetic bugs like this fail safely/are caught in CI rather than silently corrupting derivation logic in production.
- Add a unit test in `crates/consensus/derive/src/stages/frame_queue.rs` with `prev_frame.number = u16::MAX` and a same-channel `next_frame` to lock in the fixed behavior.

### Proof of Concept
1. Deploy/observe a Base node with Holocene active.
2. Craft two frames sharing the same 16-byte channel ID:
   - Frame A: `number = 65535 (0xFFFF)`, `is_last = false`.
   - Frame B: `number` = any value, same channel ID, arriving immediately after Frame A in the `FrameQueue`'s internal `VecDeque` (e.g., in the same L1 calldata/blob payload via `Frame::parse_frames`).
3. Submit this payload as calldata (or packed into a blob) to the configured batch-inbox address from any L1 account — no special role/allowlist enforcement on the sender was found in the reviewed derivation stages.
4. When the node's `FrameQueue::load_frames` → `FrameQueue::prune` executes the same-channel branch, it evaluates `prev_frame.number + 1 != next_frame.number` with `prev_frame.number == 65535`, triggering an arithmetic overflow. In a build with overflow checks enabled, this panics and unwinds the derivation pipeline task, halting safe-head progression for that node until restarted/patched.

    /// Parse the on-chain serialization of frame(s) in an L1 transaction. Currently
    /// only version 0 of the serialization format is supported. All frames must be parsed
    /// without error, there must not be any leftover data, and there must be at least one
    /// frame.
    ///
    /// Frames are stored in L1 transactions with the following format:
    /// * `data = DerivationVersion0 ++ Frame(s)` Where there is one or more frames concatenated
    ///   together.
    pub fn parse_frames(encoded: &[u8]) -> Result<Vec<Self>, FrameParseError> {
        if encoded.is_empty() {
            return Err(FrameParseError::NoFrames);
        }
        if encoded[0] != DERIVATION_VERSION_0 {
            return Err(FrameParseError::UnsupportedVersion);
        }

        let data = &encoded[1..];
        let mut frames = Vec::new();
        let mut offset = 0;
        while offset < data.len() {
            let (frame_length, frame) =
                Self::decode(&data[offset..]).map_err(FrameParseError::FrameDecodingError)?;
            frames.push(frame);
            offset += frame_length;
        }

        if offset != data.len() {
            return Err(FrameParseError::DataLengthMismatch);
        }
        if frames.is_empty() {
            return Err(FrameParseError::NoFramesDecoded);
        }

        Ok(frames)
    }
