Analogous vulnerability found in `multisig2` (and equally present in `multisig`): stale confirmations from a removed member remain counted toward the K-of-N threshold on pending requests they did not originate, allowing a request to execute with fewer *live* member confirmations than the configured threshold — the same "value expected vs value validated" mismatch as the Gravity.sol report, translated to the "confirmations counted versus live members" custody binding.

### Title
Stale confirmations from a deleted multisig member remain counted toward the confirmation threshold, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`DeleteMember` in the multisig contract only removes requests that were *originated* by the removed member; it does not scan the `confirmations` map to strip that member's confirmations from requests originated by *other* members. Because `confirm()` simply counts entries in the `confirmations` set without re-validating that each confirmer is still a current member, a stale confirmation from a removed member continues to count toward `num_confirmations` forever, letting a request execute with fewer genuinely live confirmations than the configured K-of-N threshold.

### Finding Description
`confirm()` decides whether to execute a request purely by counting set membership: [1](#0-0) 

`delete_member()`, invoked when a `DeleteMember` request executes, cleans up only the requests where the removed member is the *originating signer* (`r.member == member`); confirmations left by that member on requests created by other members are left untouched in the `confirmations` map: [2](#0-1) 

The confirmations are stored as a `HashSet<String>` keyed by `request_id` with no back-reference from member to the requests they confirmed, so there is no mechanism to purge a removed member's stale confirmation from unrelated pending requests: [3](#0-2) 

The custody binding that should hold is: *confirmations counted toward the threshold == confirmations from currently live members*. This binding is broken because a stale confirmation from an already-removed member is never purged and is still summed in `confirmations.len()`.

### Impact Explanation
This is a Critical-tier finding under "a multisig request executed below threshold." The K-of-N guarantee — that any authorized action (fund transfer, key/contract deployment, member management) requires K *currently trusted* signers — is violated. In the realistic and intended use case of `DeleteMember` (removing a member whose key is believed compromised or who should no longer be trusted), that very member's prior confirmation on any pending request continues to count. Concretely with N=4 members {A,B,C,D} and num_confirmations=3: member D confirms pending Transfer request R (1/3). The remaining members subsequently execute a `DeleteMember` request removing D (a completely legitimate, expected multisig action). R still shows `confirmations = {D}`. If A and B now confirm R, `confirmations.len()` reaches 3 (D, A, B) and the transfer executes — even though D is no longer a member and only two currently-live members (A, B) actually approved it. The multisig has effectively been reduced to a 2-of-3 (or worse) scheme without ever changing `num_confirmations`, and an untrusted (removed/compromised) signature permanently retains its weight on any request it touched before removal.

### Likelihood Explanation
No attacker privilege beyond already being one of the K signers is required to trigger the loss of guarantee — the bug is triggered by completely ordinary multisig lifecycle operations (a pending request plus a subsequent, routine member removal), which is exactly the scenario `DeleteMember` exists to handle safely. Any multisig that ever rotates or revokes a member while a request is outstanding is exposed, making this a realistic, low-effort trigger rather than a contrived edge case.

### Recommendation
When executing `DeleteMember`, iterate over `confirmations` for *all* active requests (not just those originated by the removed member) and remove the deleted member's entry from each set; alternatively, validate at `confirm()` time and at threshold-check time that every account/key in a request's `confirmations` set is still present in `self.members`, discounting entries that are not.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `A` calls `add_request` to create Transfer request `R` (receiver gets funds), `request_id = 0`.
3. `D` calls `confirm(0)` → `confirmations(0) = {D}`, count 1 < 3, request stays pending.
4. Members create and confirm a separate `DeleteMember { member: D }` request (a normal, expected recovery/rotation action) with 3 confirmations from A, B, C; it executes via `delete_member`, which — per [4](#0-3)  — only removes requests where `r.member == D` (i.e. requests D originated), not `R`, which D merely confirmed. `confirmations(0)` remains `{D}`, `members = {A, B, C}`.
5. `B` calls `confirm(0)` → `confirmations(0) = {D, B}`, count 2 < 3, still pending.
6. `C` calls `confirm(0)` → `confirmations(0) = {D, B, C}`, count 3 >= `num_confirmations` (3) → `execute_request(R)` fires per [5](#0-4) , transferring funds even though only B and C are current live members who actually approved it; D's stale, no-longer-valid confirmation supplied the third vote.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
