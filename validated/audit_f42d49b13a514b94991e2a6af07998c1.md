### Title
Front-runnable multisig sub-account creation with attacker-chosen members - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` lets any caller deploy a multisig at `<name>.<factory>` with an arbitrary `members` list and `num_confirmations` chosen entirely by the caller, with no check that `name` is reserved for or restricted to a particular caller. An attacker can observe a pending legitimate creation transaction (or simply predict a commonly-expected name) and submit their own `create(name, attacker_members, attacker_num_confirmations)` one block earlier, permanently claiming `<name>.<factory>` with attacker-controlled signer set before the intended owner's transaction lands.

### Finding Description
The invariant being violated: `deployed_multisig_at(name.factory).members == intended_owner.chosen_members`. In `create`: [1](#0-0) 
the account id is deterministically derived as `format!("{}.{}", name, env::current_account_id())`, and the promise chain does `create_account().deploy_contract(CODE).transfer(deposit).function_call("new", {members, num_confirmations})` with no signer/name binding, no reservation mechanism, and no owner allowlist check.

Because NEAR account creation is first-come-first-served, whoever's `create` transaction is included first for a given `name` wins that sub-account permanently; NEAR itself will reject the second `create_account()` for an already-existing account (it fails atomically as part of that promise), so the legitimate creator's later transaction simply fails while the attacker's multisig - with attacker-chosen `members` and `num_confirmations` - now permanently occupies the trusted-looking `<name>.<factory>` address. Any downstream party (users, other contracts, or off-chain systems) that trusts `<name>.<factory>` as "the multisig belonging to `name`" is actually interacting with a contract whose signer set the attacker fully controls. There is no `assert_owner`, `assert_called_by_foundation`, or any name-reservation/commit-reveal check in this function that would prevent this.

### Impact Explanation
Since the multisig's whole security model is "N of `members` must approve," attacker-controlled `members`/`num_confirmations` means any subsequent request sent to the squatted account is signed and approved entirely by the attacker. Any NEAR or wNEAR that legitimate users, DAOs, or other contracts later send to `<name>.<factory>` in the belief it is owned by the intended party can be withdrawn solely by the attacker. This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" (here, a multisig deployed with parameters its rightful creator never chose), and can cascade to "NEAR moved out of a multisig by a party not entitled to it" once funds are deposited under the false trust assumption.

### Likelihood Explanation
The attack requires no privilege beyond the ability to submit an ordinary NEAR transaction with a small deposit for account creation and gas - well within the defined "unprivileged attacker" capability set. The only timing requirement is submitting a transaction for the same `name` before the legitimate creator's transaction is included, which is straightforward via mempool observation or by predicting well-known/expected names (e.g., DAO or protocol names about to be onboarded). It is fully repeatable across any `name` not yet claimed under the factory.

### Recommendation
Bind sub-account creation to an authorized principal, e.g. require `predecessor_account_id() == name` (so only the account named `name` can create `name.factory`) as is done in the lockup/staking-pool factories' whitelist checks, or require a signed commitment/allowlist entry created in advance by a trusted party before `create` is permitted for that `name`.

### Proof of Concept
Using `near-workspaces` (or `near-sdk-sim`):
1. Deploy `MultisigFactory` to `factory.test.near`.
2. Attacker account `eve.test.near` calls `factory.create("dao", [MultisigMember::Account{eve.test.near}], 1)` in block N.
3. Legitimate owner `alice.test.near` calls `factory.create("dao", [MultisigMember::Account{alice.test.near}, ...], 2)` in block N+1, targeting the same `name = "dao"`.
4. Assert: `dao.factory.test.near` exists and its `list_members()`/state shows `[eve.test.near]` and `num_confirmations == 1` (attacker's values), not Alice's; assert Alice's `create` call fails (promise batch fails on `create_account` because the account already exists).
5. This demonstrates `deployed_multisig.members != alice.chosen_members`, proving the binding is broken and the account is squattable by an unprivileged front-runner.

```rust
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
```
