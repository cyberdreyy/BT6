### Title
Multisig confirmations from removed members still count toward the execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges requests that a removed member *created*, but never scans the `confirmations` map to strip that member's prior confirmations from other requests they had merely *approved*. As a result, a confirmation cast by a member who is later removed from the multisig continues to count toward `num_confirmations` when `confirm()` totals up approvals, allowing a request to execute with fewer live, currently-authorized signers than the configured threshold `K`.

### Finding Description
The invariant the multisig is supposed to enforce is: `confirmations counted == confirmations from currently live members`. `confirm()` reaches the execution threshold purely by set cardinality: [1](#0-0) 

Confirmations are stored as raw strings in a `HashSet<String>` keyed by `request_id`, independent of whether the confirming member is still part of `self.members`: [2](#0-1) 

When a member is removed via `DeleteMember` (itself an action requiring `K` confirmations), `delete_member` only cleans up:
1. `self.num_requests_pk` for that member.
2. Requests where `r.member == member`, i.e., requests the removed member *authored* (`MultiSigRequestWithSigner.member`). [3](#0-2) 

It never inspects or trims entries inside `self.confirmations` for requests authored by *other* members that the removed member had confirmed. Those stale string entries remain in the `HashSet<String>` and are still counted by `confirm()`'s `confirmations.len() as u32 + 1 >= self.num_confirmations` check.

Concretely: with `num_confirmations = K` and `N` members, member `M` confirms request `R` (authored by someone else). Before `R` reaches `K` confirmations, the remaining live members vote to remove `M` via a separate `DeleteMember` request. `M`'s confirmation on `R` is untouched. Live members then only need to supply `K - 1` additional live confirmations for `R` to execute, because `M`'s stale confirmation is still counted — the recorded confirmation count no longer equals the number of *live* members who approved.

### Impact Explanation
This breaks the core multisig custody guarantee that any privileged action (fund transfer, key/member management, function calls) requires `K` confirmations *from currently authorized members*. An attacker (or a soon-to-be-removed compromised key) can pre-confirm a malicious `Transfer` or `AddKey`/`FunctionCall` request, get removed from the multisig (e.g., because their key was known to be compromised and the remaining members intentionally revoke it), and the request can still execute later with only `K-1` live approvals. This is a "multisig request executed below threshold" scenario, i.e., Critical impact per the rules — funds can be moved or membership/authorization changed with fewer genuinely authorized signers than configured.

### Likelihood Explanation
The scenario requires normal, expected multisig operations: a member confirms a pending request, and later that member is removed (a routine key-rotation/incident-response action any active multisig would perform). No exploit of cryptography or out-of-scope privileged access is needed — only ordinary usage of `confirm`, `add_request`, and `DeleteMember`, all reachable by legitimate multisig members using the public interface. The bug is deterministic, not probabilistic.

### Recommendation
When deleting a member in `delete_member`, iterate over all outstanding requests' `confirmations` sets (not just ones authored by that member) and remove the member's identity string from each. Alternatively, revalidate at execution time in `confirm()`/`execute_request()` that every entry in the confirmations set still belongs to `self.members` before counting it toward `num_confirmations`, discarding stale confirmations from removed members.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account).
3. `B` calls `confirm(R)` → confirmations for `R` = `{A, B}` (size 2, `add_request_and_confirm` counts creator too).
4. Separately, `C` and `D` (plus `A`) approve a `DeleteMember { member: B }` request and it executes, removing `B` from `self.members`. `delete_member` only scans requests authored by `B` (`request.member == B`) — `R` (authored by `A`) is untouched, so `R`'s confirmation set still contains `B`.
5. `C` calls `confirm(R)` → `confirmations.len() as u32 + 1 == 3 >= num_confirmations (3)` → `R` executes, even though only `A` and `C` are *live* members who approved (`B`'s confirmation is stale). The transfer/action executes with 2 live approvals instead of the required 3. [4](#0-3) [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
