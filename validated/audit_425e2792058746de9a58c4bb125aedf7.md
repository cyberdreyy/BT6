### Title
First-depositor donation attack: attacker inflates tranche price via direct token transfer, causing subsequent depositors to mint zero/near-zero shares - (File: contracts/IdleCDO.sol)

### Summary
`IdleCDO._deposit` (and the credit-vault override `IdleCDOCreditVault._deposit`) mint tranche shares purely as `amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)`, where the price is derived from `getContractValue()` / `_managedContractValue()`, which counts the raw ERC20 balance of the contract. There is no minimum-liquidity lock, no dead-share seed, and no cap on the minted-share/price ratio. An attacker who is the first depositor of a tranche class can deposit 1 wei, donate a large amount of `token` directly to the CDO, inflate the tranche price arbitrarily, and cause the next depositor to receive 0 shares while their underlying is credited to `lastNAV*`. The attacker then redeems their single share for the entire NAV.

### Finding Description
Bug class of the external report (heap overflow via attacker-controlled input corrupting adjacent accounting) maps to donation/rounding corruption of the share-accounting invariant.

Mechanics:

1. **Buffer phase / fresh vault** (or first deposit into an empty tranche class): attacker (a KYC-passing lender) calls `depositAA(1 wei)`/`depositBB(1 wei)`. In `_mintSharesAtCurrPrice` the price returned by `_virtualPriceAux` is `oneToken` when `trancheSupply == 0` or `lastNAV == 0`, so the attacker mints shares at 1:1 and `lastNAVAA += 1`. [1](#0-0) [2](#0-1) 

2. Attacker transfers `D` tokens directly to the CDO contract (plain ERC20 `transfer` — no access control). `getContractValue()` includes the contract's token balance, so `nav = lastNAV + D` on the next accounting call. [3](#0-2) 

3. The donation is treated as gain inside `_virtualPriceAux`: `totalGain = nav - lastNAV = D - epsilon`; since only one tranche class has supply, the whole gain accrues to that class and `_virtualPrice = (lastTrancheNAV + D) * ONE_TRANCHE_TOKEN / trancheSupply` — i.e., price ≈ `D` per wei-share (times 1e18 scaling). [4](#0-3) 

4. Victim calls `depositAA(X)`. `_updateAccounting()` runs first, crystallizing the inflated price into `priceAA`/`lastNAVAA`. Shares minted = `X * ONE_TRANCHE_TOKEN / inflatedPrice`. With `D` chosen so that `inflatedPrice > X * 1e18`, the victim mints **0 shares** while `_mintShares` still increments `lastNAVAA += X`. [5](#0-4) 

5. Attacker calls `withdrawAA(1 wei share)`; `_withdraw`/`_withdrawOps` burns their share and pays out `shares * price / ONE_TRANCHE_TOKEN` ≈ the full NAV including the victim's `X` and (minus performance fee) most of their own donation.

The credit-vault variant has identical mechanics (`_deposit` → `_updateAccounting` → `_mintSharesAtCurrPrice` at `contracts/IdleCDOCreditVault.sol:191-212` and `344-348`; `_virtualPriceAux` at `287-337`). The `_managedContractValue()` used in `virtualPrice` likewise exposes managed NAV to balance-delta donations.

**Guards that do not stop it:**
- `_skimDonatedAssets`/balance-delta accounting is only applied *inside* `_deposit` (`_contractTokenBalance(_token) - _preBal`); tokens sitting in the contract *before* the deposit are folded into `nav` as gain, not skimmed. [6](#0-5) 
- `unclaimedFees` siphons only `fee/FULL_ALLOC` of the donation; the rest inflates the attacker's share.
- `lossToleranceBps`, `skipDefaultCheck`, `Default()` revert: the manipulation is a *gain*, not a loss, so no default path triggers.
- KYC/`isWalletAllowed` restricts who deposits but the attacker is a legitimate KYC'd lender — the rules' in-scope attacker set.
- No minimum deposit, no `MIN_LIQUIDITY`-style dead shares, and `_tranchePrice` falls back to `oneToken` at zero supply with no first-deposit dilution check.

### Impact Explanation
Direct theft of the next depositor's entire principal `X` (bounded by choosing `D > X`): the victim receives 0 (or dust) shares, their underlying joins the tranche NAV, and the sole pre-existing share redeems nearly the whole pool. Net attacker profit = `X - fee portion of D` ≈ `X` for any chosen donation, since the donation is recoverable through redemption. Solvency and fair mint/burn invariants are broken: NAV credited ≠ shares outstanding.

### Likelihood Explanation
Requires being the first depositor of a tranche class — trivially satisfiable on any freshly deployed/factory-cloned CDO or credit vault, or after a full exit wipes a tranche's supply while `epochEndDate == 0`. Cost is gas plus a recoverable donation; detection surface is a single early transaction. KYC does not mitigate since any whitelisted lender qualifies. Likelihood is high whenever a vault launches with public deposits.

### Recommendation
- Seed each tranche with a minimum-liquidity amount of dead shares at initialization (mint to `address(0)`/`0xdead`) or enforce a minimum first deposit.
- Reject deposits that would mint 0 shares: `require(_minted > 0, "0 shares")` in `_mintSharesAtCurrPrice`.
- Skim contract-balance donations out of `nav`: track `lastNAV` versus internal accounting and exclude unsolicited balance deltas in `getContractValue()`/`_managedContractValue()` (route them to `unclaimedFees` or a sweepable reserve) so donations cannot move `_virtualPrice`.
- Alternatively compute price from `lastNAV* / supply` rather than live `getContractValue()` for the mint step.

### Proof of Concept
Foundry fork test sketch (solidity):

```solidity
// assume: fresh IdleCDO clone, attacker + victim are whitelisted, token = USDC
uint256 D = 200_000e6;      // donation, recovered on redeem
uint256 X = 100_000e6;      // victim deposit

vm.startPrank(attacker);
usdc.approve(address(cdo), 1);
cdo.depositAA(1);                          // mints shares at price = oneToken
usdc.transfer(address(cdo), D);            // donation inflates nav
vm.stopPrank();

vm.startPrank(victim);
usdc.approve(address(cdo), X);
cdo.depositAA(X);                          // _updateAccounting crystallizes inflated priceAA
vm.stopPrank();
assertEq(AA.balanceOf(victim), 0);         // victim minted 0 shares

vm.startPrank(attacker);
AA.approve(address(cdo), AA.balanceOf(attacker));
cdo.withdrawAA(AA.balanceOf(attacker));    // redeems ~ lastNAVAA incl. victim's X
vm.stopPrank();

// attacker.balance ≈ X + D - fee(D)  => net profit ≈ X
```

Uncertainty noted: the `test/` suite may already cover a minted-0 revert or a first-deposit guard in a variant not fully indexed (e.g., `IdleCDOEpochVariant`/`IdleCDOCreditVault` epoch gating may restrict *when* deposits occur, narrowing the window to the pre-epoch buffer phase). The core gap — donations entering `nav` through `getContractValue()` and 0-share mints not being reverted — is visible in the indexed code above.

  function _mintSharesAtCurrPrice(uint256 _amount, address _to, address _tranche) internal virtual returns (uint256 _minted) {
    // calculate # of tranche token to mint based on current tranche price: _amount / tranchePrice
    _minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche);
    _mintShares(_tranche, _to, _minted, _amount);
  }

  /// @notice mint tranche tokens and updates tranche last NAV
  /// @param _tranche tranche address
  /// @param _to receiver address of the newly minted tranche tokens
  /// @param _shares number of tranche tokens to mint
  /// @param _underlyings amount of underlyings added to the tranche
  function _mintShares(address _tranche, address _to, uint256 _shares, uint256 _underlyings) internal {
    IdleCDOTranche(_tranche).mint(_to, _shares);
    // update NAV with the _amount of underlyings added
    if (_tranche == AATranche) {
      lastNAVAA += _underlyings;
    } else {
      lastNAVBB += _underlyings;
    }
  }
