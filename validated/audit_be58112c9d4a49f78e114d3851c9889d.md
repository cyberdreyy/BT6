### Title
External-initiator credentials trigger arbitrary job runs with no job/EI binding check - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` authenticates an EI credential globally (by access key only) and always injects a synthetic `Run`-role `SessionUserKey`, which is indistinguishable from a real user session downstream. `RequiresRunRole` only checks the role level, and `PipelineRunsController.Create` gates the integer-ID run path on `auth.GetAuthenticatedUser(c)` returning `ok`, which is now also true for EI-authenticated requests, defeating the code's own "EIs not allowed" comment and allowing any valid EI credential to trigger a run for any job ID, unrelated to the EI's intended association.

### Finding Description
The route is wired as: [1](#0-0) 

`AuthenticateExternalInitiator` looks up the EI purely by access key/secret and never associates it to a specific job. On success it sets a **synthetic** session user object identical in shape to a real logged-in user: [2](#0-1) 

`RequiresRunRole` only inspects `user.Role`, with no notion of which job/EI pair is authorized: [3](#0-2) 

`GetAuthenticatedExternalInitiator` (which retrieves the actual `*bridges.ExternalInitiator` set by `AuthenticateExternalInitiator`) is defined but never consulted anywhere outside `auth.go` — confirmed by grep showing zero usages in any controller or job-running code path.

In `PipelineRunsController.Create`, the UUID-based branch (which historically was the job/EI-scoped webhook path) is now hard-rejected because the webhook job type has been removed: [4](#0-3) 

The remaining branch gates on `isUser`, intending to block EI callers from the int-ID path ("only users are allowed to run jobs using int IDs - EIs not allowed"), but because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `auth.GetAuthenticatedUser(c)` returns `ok=true` for EI-authenticated requests too: [5](#0-4) 

As a result, an EI credential passes `isUser` and directly invokes `prc.App.RunJobV2(ctx, jobID, nil)` for any integer job ID supplied in the URL, with zero verification that this EI is registered against that job at all.

### Impact Explanation
Any holder of a valid external-initiator access key/secret pair (registered for any purpose) can trigger a pipeline run for an arbitrary job by supplying its integer ID in `POST /v2/jobs/:ID/runs`, regardless of whether that job has any relationship to the EI. This is unauthorized action on another user's/job's resource — cross-job/cross-subscription run triggering — matching the "unauthorized job run" bounty impact class. Depending on job type/pipeline tasks, this could cause unwanted on-chain transactions, resource exhaustion, or unintended external HTTP calls from the node.

### Likelihood Explanation
Preconditions are minimal: possession of any single valid, currently-registered EI access key + secret (the attacker archetype explicitly includes "external-initiator credential holder"). No job-specific relationship is required. The exploit is a single unauthenticated-by-session HTTP POST with EI headers and a guessable/enumerable integer job ID — highly repeatable and trivial to automate.

### Recommendation
- Bind the EI-authenticated identity to the specific job before allowing a run: in `PipelineRunsController.Create`, when the caller is authenticated via `auth.GetAuthenticatedExternalInitiator(c)`, look up the target job's registered external initiator(s) and reject unless the authenticated EI matches.
- Stop conflating EI authentication with `SessionUserKey`/`isUser`; use a distinct context key/check so downstream authorization code can differentiate "real user session" from "EI request" instead of relying on a synthetic `User{Role: UserRoleRun}`.
- Since the webhook/EI job type is deprecated, consider removing the EI authentication method from this route entirely if no legitimate job type still requires EI-triggered runs, or enforce the association check for whatever mechanism replaces it.

### Proof of Concept
1. Register an external initiator via `/v2/external_initiators` to obtain `AccessKey`/`Secret` (per `external_initiators_controller_test.go` pattern).
2. Create/insert a non-webhook job (e.g., Cron/VRF) not associated with the EI, and note its integer job ID.
3. Send `POST /v2/jobs/<jobID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI credentials from step 1 (no session/API token).
4. Assert the response is `200 OK` with a created pipeline run (via `respondWithPipelineRun`) rather than `401 Unauthorized` — demonstrating that an EI credential unrelated to the job can trigger it.
5. Compare against expected behavior: assert should be `401`/`403` unless the EI is verified via `GetAuthenticatedExternalInitiator` to be associated with that specific job ID.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
