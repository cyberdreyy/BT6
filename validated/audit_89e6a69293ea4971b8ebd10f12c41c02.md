## Finding: v1 protocol's tenure-duplicate check uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, permitting equivocation once the earlier signature's freshness window lapses

### Title
Signer can sign two conflicting tenure-start blocks under the v1 protocol because `validate_tenure_change_payload` only detects a *globally accepted* prior block, not a merely *signed* one — ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (v1 protocol) rejects a tenure-change proposal with `DuplicateBlockFound` only if it finds an existing **globally accepted** block in the same tenure, via `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0) . The v2 protocol's equivalent check was hardened to use `signer_db.get_last_signed_block`, which additionally matches `LocallyAccepted` blocks, with an explicit comment explaining why: "Only blocks we have signed (locally or globally accepted) count here" [2](#0-1) . A dedicated regression test confirms this exact class of bug was found and fixed for v2 [3](#0-2) , but the v1 code path was left with the weaker, pre-fix condition.

### Finding Description
The equality the signer must never violate is "have I already signed a block in this tenure?" — this is what prevents equivocation on a tenure-start (`TenureChange`) block. This check runs exactly once, at proposal arrival, inside `validate_tenure_change_payload`, and — as documented — is **never re-run** at validate-ok or pre-commit time for the block's own tenure: `check_block_against_signer_db_state` only re-checks the tenure-change block against its **parent** tenure via `check_tenure_change_confirms_parent`, not its own tenure [4](#0-3) .

For v1, the one-shot duplicate check only consults `get_last_globally_accepted_block`, i.e. a block that has already been signed by the whole 70% threshold *and* handed to and processed by the node [1](#0-0) . It ignores a block this same signer has already put its own signature on (`LocallyAccepted`) if that block never collected enough weight from the rest of the signer set to become globally accepted. The pre-commit-time backstop (`get_signed_conflicts` + `conflict_still_blocks`) is the only remaining guard, but it is explicitly time-bound: a conflict only unconditionally blocks while it is "fresh" (`last_endorsed > freshness_cutoff`, i.e. within `tenure_last_block_proposal_timeout`) [5](#0-4) . Once that window elapses, the fallback for same-tenure conflicts only refuses to sign if the **node's own tip already confirms** the tenure at or above the proposed height [6](#0-5)  — which is precisely the case that does not hold when the earlier block was never globally accepted/pushed to the node. This blind spot is explicitly acknowledged in code comments: "The chainstate checks don't cover this for tenure-change blocks: those check the parent tenure instead of their own" [7](#0-6) .

Consequently, under the v1 (non-global-state) signer protocol: if a signer locally signs tenure-start block A, but A never reaches the 70% network-wide threshold within `tenure_last_block_proposal_timeout`, a later, conflicting tenure-start block B (same tenure/parent, different content — e.g. a miner re-proposal after a stall) will (1) pass the proposal-time `DuplicateBlockFound` check because A is not globally accepted, and (2) pass the pre-commit-time stale-conflict fallback because the node has no record of A. The signer will then sign B — producing two valid signatures from the same signer over two different blocks for the same tenure, i.e. equivocation.

### Impact Explanation
This breaks the "one-per-tenure/no double signing" invariant for a single signer under the v1 protocol: a one-slot miner (by simply re-proposing a competing tenure-start block after a network hiccup delays the first block's threshold) can induce a signer to sign a second, conflicting block in the same tenure. This matches the Critical impact category: "a signer signing an invalid, non-canonical, or conflicting block." No majority of signers or other signer's key is required — only the timing gap between local signing and global threshold, which is realistic (`tenure_last_block_proposal_timeout` is a bounded config value, not infinite).

### Likelihood Explanation
Exploitation requires only ordinary conditions: a delayed or dropped set of peer pre-commits/signatures for block A (e.g., transient network partition or slow signer set convergence) that outlasts the freshness window, followed by a legitimate-looking re-proposal B for the same tenure. This is a plausible operational condition rather than requiring privileged access, and it is entirely triggerable by the block-proposing miner and ordinary gossip — no majority collusion needed.

### Recommendation
Change `SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (matching both `LocallyAccepted` and `GloballyAccepted`) instead of `get_last_globally_accepted_block`, mirroring the fix already applied to v2 [8](#0-7) . Additionally, consider making the pre-commit-time own-tenure stale-conflict fallback in `stacks-signer/src/v0/signer.rs` treat "node has not yet seen the tenure" as blocking (rather than permissive) when the stale conflict itself was never globally accepted, closing the timing blind spot regardless of protocol version.

### Proof of Concept
1. Boot a v1-protocol signer set (pre-global-state activation).
2. Miner proposes tenure-start block A for tenure T; signer S locally validates and signs A (`mark_locally_accepted`), but the rest of the signer set is slow/partitioned so A never reaches the 70% global threshold within `tenure_last_block_proposal_timeout`.
3. After the freshness window elapses, miner proposes a different tenure-start block B for the same tenure T (same `parent_tenure_id`/`prev_tenure_consensus_hash`, different content/timestamp).
4. At proposal time, `validate_tenure_change_payload` calls `get_last_globally_accepted_block(T)` — returns `None` (A is only locally accepted) — proposal passes, unlike v2 which would reject with `DuplicateBlockFound` via `get_last_signed_block`.
5. B is validated by the node and reaches the pre-commit threshold; `handle_block_pre_commit`'s fresh-conflict check skips A (stale), and the same-tenure fallback queries `get_tenure_tip(T)`, which the node cannot answer beyond A's height since A was never pushed — so the check passes and S signs B.
6. Signer S has now signed two different blocks (A and B) for the same tenure T — an equivocation.
