### Title
Unbounded per-call cost in `get_vote_accounts` scales with attacker-inflatable total on-chain vote-account count - ([File: rpc/src/rpc.rs])

### Summary
`RpcSol::get_vote_accounts` (`rpc/src/rpc.rs:1155`) iterates every entry returned by `bank.vote_accounts()` (backed by `Stakes::vote_accounts()` / `VoteAccounts::iter()` in `vote/src/vote_account.rs`) and performs per-account decoding work (`vote_state_view()`, `epoch_credits_iter()`, pubkey-to-string formatting, `Vec` allocation) for every account before any stake-based filtering is applied. Because zero-stake vote accounts remain in this map and are only dropped from the *delinquent* output list afterward, an attacker who creates many low-cost vote accounts on-chain forces every future `getVoteAccounts` call (including the attacker's own single call) to pay CPU/allocation cost proportional to the total number of vote accounts, not a fixed cap.

### Finding Description
`get_vote_accounts` fetches `bank.vote_accounts()` and, for every `(vote_pubkey, (activated_stake, account))` pair, unconditionally calls `account.vote_state_view()`, `vote_state_view.epoch_credits_iter().skip(...).map(Into::into).collect()`, and builds a full `RpcVoteAccountInfo` (with `to_string()` conversions) inside the `filter_map` closure: [1](#0-0) 

Only *after* this per-account work is done does the code `.partition(...)` into current/delinquent, and only then optionally strips zero-stake delinquent entries via the `keep_unstaked_delinquents` filter: [2](#0-1) 

Crucially, `VoteAccounts` (the type backing `bank.vote_accounts()`) tracks *every* vote-program account regardless of delegated stake — `VoteAccounts::insert` stores whatever `calculate_stake()` returns (which is `0` for an account with no delegation), and the entry is retained in the underlying `HashMap` until explicitly removed: [3](#0-2) 

`VoteAccounts::iter()` returns all entries with no size cap: [4](#0-3) 

This is directly confirmed by the existing test `test_get_vote_accounts`, where creating a single no-stake vote account (via normal `CreateAccount` + vote-program `InitializeAccount`-style flow, simulated here by `rpc.store_vote_account`) increases `bank.vote_accounts().len()` from `1` to `2`: [5](#0-4) 

and that account is only excluded from the *delinquent* output list, not from the iteration/decoding cost incurred inside `get_vote_accounts`: [6](#0-5) 

There is no limit, pagination, or cap anywhere in `get_vote_accounts` on the number of accounts processed — the only filters (`filter_by_vote_pubkey`, `keep_unstaked_delinquents`) either narrow to a single account or run after the expensive per-account decode/format step. An unprivileged attacker with sufficient lamports can call the vote program's normal `CreateAccount` + `InitializeAccount` instructions repeatedly (one-time on-chain writes, no special privilege required) to create N vote accounts at rent-exempt-minimum balance with zero stake. Every subsequent `getVoteAccounts` call by any client — including a single call from the attacker itself — then does O(N) decode/allocation work where N is fully attacker-controlled and grows without bound, rather than being capped by an explicit RPC-side limit.

### Impact Explanation
This is an unbounded-cost-for-a-single-low-rate-call issue: CPU and memory cost of one `getVoteAccounts` JSON-RPC request scales linearly with the total number of vote-program accounts ever created on-chain, a quantity an unprivileged actor can inflate arbitrarily (bounded only by their own lamports, paid once). This matches the in-scope Agave bounty category for RPC DoS caused by a single call rather than requiring multiple clients or unfiltered `getProgramAccounts`. Repeated legitimate `getVoteAccounts` calls (used by validators, the CLI `agave-validator wait-for-restart-window`, and staking tools) become progressively more expensive for the life of the chain, since the attacker's polluting accounts are never removed by this code path.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs enough lamports to fund N rent-exempt vote accounts once (no special stake amount, no delegation required, since `calculate_stake()` legitimately returns 0 for undelegated accounts). No validator/leader/gossip control, no leaked keys, and no more than the normal vote-program `CreateAccount`/`InitializeAccount` instruction sequence are required. The cost is paid every time afterward by any caller of `getVoteAccounts`, including the attacker's own single subsequent call, satisfying the "single call" precondition in the rules.

### Recommendation
Move stake-based filtering (and any account-count limiting) ahead of the expensive per-account decode step, or introduce an explicit bound/cap: e.g., iterate `bank.vote_accounts()` and short-circuit accounts with `activated_stake == 0` (unless `keep_unstaked_delinquents` is requested) before calling `vote_state_view()`/`epoch_credits_iter()`, and/or enforce a maximum number of vote accounts processed per `getVoteAccounts` request analogous to limits already used elsewhere in RPC (e.g., `getProgramAccounts` filter/response caps).

### Proof of Concept
Rust unit/bench test plan (extends the existing `test_get_vote_accounts` in `rpc/src/rpc.rs`):
1. Start `RpcHandler` as in `test_get_vote_accounts`.
2. In a loop, create and `store_vote_account` N zero-stake vote accounts (N = 1_000, 10_000, 100_000), each with a unique `VoteStateV4` and populated `epoch_credits` history to maximize per-account decode cost.
3. Assert `bank.vote_accounts().len() == N + 1` (bootstrap leader account included) to confirm all attacker accounts remain tracked.
4. Time a single `io.handle_request_sync(getVoteAccounts request, ...)` call for each N and assert wall-clock time / allocation count grows sub-linearly or is capped (expected to fail today, showing linear/unbounded growth with N), demonstrating the absence of any cap independent of attacker-controlled on-chain state.

    pub fn insert(
        &mut self,
        pubkey: Pubkey,
        new_vote_account: VoteAccount,
        calculate_stake: impl FnOnce() -> u64,
    ) -> Option<VoteAccount> {
        let vote_accounts = Arc::make_mut(&mut self.vote_accounts);
        match vote_accounts.entry(pubkey) {
            Entry::Occupied(mut entry) => {
                // This is an upsert, we need to update the vote state and move the stake if needed.
                let (stake, old_vote_account) = entry.get_mut();

                if let Some(staked_nodes) = self.staked_nodes.get_mut() {
                    let old_node_pubkey = old_vote_account.node_pubkey();
                    let new_node_pubkey = new_vote_account.node_pubkey();
                    if new_node_pubkey != old_node_pubkey {
                        // The node keys have changed, we move the stake from the old node to the
                        // new one
                        Self::do_sub_node_stake(staked_nodes, *stake, old_node_pubkey);
                        Self::do_add_node_stake(staked_nodes, *stake, *new_node_pubkey);
                    }
                }

                // Update the vote state
                Some(mem::replace(old_vote_account, new_vote_account))
            }
            Entry::Vacant(entry) => {
                // This is a new vote account. Use the caller-provided stake for the initial
                // cache entry.
                let (stake, vote_account) = entry.insert((calculate_stake(), new_vote_account));
                if let Some(staked_nodes) = self.staked_nodes.get_mut() {
                    Self::do_add_node_stake(staked_nodes, *stake, *vote_account.node_pubkey());
                }
                None
            }
        }
    }
