### Title
Stale Confirmations From Removed Multisig Members Are Counted Toward the Approval Threshold, Allowing Requests To Execute Below Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges the confirmations of requests *authored by* the removed member, but never scans or removes that member's *confirmations on other members' pending requests*. Because `confirm()` counts raw entries in the `confirmations` set without verifying the confirmer is still a current member, a stale confirmation left behind by a removed member continues to count toward `num_confirmations`, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
`confirm()` decides whether to execute a request purely by set size: [1](#0-0) 

It never re-validates that each entry in `confirmations` still corresponds to a current member of `self.members`.

`delete_member()` only cleans up requests where the removed member is the *request author* (`r.member == member`); it does not walk `self.confirmations` to strip that member's approval from requests authored by *other* members: [2](#0-1) 

Because the `confirmations: LookupMap<RequestId, HashSet<String>>` has no reverse index from member → confirmed request IDs, there is no way for `delete_member` to find and purge those stale entries even if it tried.

The intended invariant is:
```
confirmations(request) counted toward threshold == confirmations from accounts currently in self.members
```
After a member is removed, this equality breaks: `confirmations(request)` can contain identifiers of accounts no longer in `self.members`, yet `confirm()` still counts them.

### Impact Explanation
This directly matches the "multisig request executed below threshold" critical impact: a request can be executed after being approved by fewer *live* members than `num_confirmations` requires, because a stale confirmation from a removed (e.g., compromised/offboarded) member is counted as if it were still valid. This is precisely the accounting-binding failure targeted by the report's bug class (a recorded claim/count diverging from the actual, current state it's supposed to represent) — here applied to "confirmations counted versus live members" instead of "fees charged versus finalized sale."

Concrete scenario:
1. Multisig has 4 members `{A,B,C,D}`, `num_confirmations = 3`.
2. `D` confirms a pending `Transfer` request `X` authored by `A`. `confirmations(X) = {D}`.
3. Separately, members vote to remove `D` (e.g., because `D`'s key was compromised) via `DeleteMember`. `delete_member` checks `members.len() - 1 >= num_confirmations` (3 >= 3, OK), removes `D` from `members`, and only cleans up requests *authored* by `D` — request `X` (authored by `A`) and its stored confirmation set `{D}` are untouched.
4. Now only `A, B, C` are members. `A` confirms `X`: `confirmations(X) = {D, A}`, size 2, `2+1 >= 3` not yet met.
5. `B` confirms `X`: before insertion, `confirmations.len() == 2` (`D`,`A`), so `2 + 1 >= 3` is true and `execute_request` fires — even though only `A` and `B` are actually current, live members who approved. `D`'s stale confirmation substituted for a live approval.

The request (e.g., a `Transfer` of funds, `AddKey`, or `DeployContract`) executes with only 2 of 3 required *live* approvals, i.e., the multisig's security threshold is effectively bypassed by one confirmation for every request that a since-removed member had confirmed before being removed.

### Likelihood Explanation
This requires no privileged attacker action beyond the normal, expected lifecycle of a multisig: a member confirming a request and later being removed (a routine security practice, e.g. rotating out a compromised key or a departing member) while that request is still pending. It requires no protocol violation, no owner/attacker collusion, and no exploitation of `near-sdk` — it is a pure logic gap in `delete_member`/`confirm` in this repository. Any multisig that ever removes a member who had confirmed an outstanding request is exposed.

### Recommendation
When removing a member, also purge that member's identifier from the `confirmations` set of every other outstanding request (requires either an additional reverse index from member → confirmed request IDs, or iterating all `requests`/`confirmations` entries on `delete_member`). Alternatively, have `confirm()` (and the execution check) filter `confirmations` against `self.members` before comparing against `num_confirmations`, so only confirmations from currently-live members count.

### Proof of Concept
```rust
// members: {A, B, C, D}, num_confirmations = 3
let request_x = MultiSigRequest { receiver_id: victim, actions: vec![Transfer{ amount }] };
// authored by A
let request_id = contract.add_request(request_x); // as A

// D confirms it
// as D:
contract.confirm(request_id); // confirmations(request_id) = {D}

// Members vote to remove D (separate self-request, reaches num_confirmations via A, B, C)
contract.add_request_and_confirm(MultiSigRequest {
    receiver_id: current_account_id,
    actions: vec![DeleteMember { member: D }],
}); // executes, D removed from `members`; request_id's confirmations set still = {D}

// as A:
contract.confirm(request_id); // confirmations(request_id) = {D, A}, size 2, 2+1 < 3 -> not executed yet

// as B:
contract.confirm(request_id); // before insert: len=2 ({D,A}), 2+1 >= 3 -> execute_request fires!
// Transfer executes with only A and B as live confirmers, D's stale confirmation
// counted toward the threshold despite D no longer being a member.
```

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
