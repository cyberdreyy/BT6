This confirms the pattern: elsewhere in the same package tree, `requestCache` (used by other handlers like `vault`, `confidentialrelay`) explicitly keys pending requests by `globalId{sender, id}` and rejects duplicates with `"request already exists"`, as shown in [1](#0-0) . The legacy `capabilities.handler`, however, keys `savedCallbacks` purely by the attacker-controlled `msg.Body.MessageId` string with no sender binding and no existence check, unconditionally overwriting any prior entry.

### Title
Cross-user response hijack/DoS via unauthenticated MessageId collision in savedCallbacks map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` stores pending user callbacks keyed solely by the caller-supplied `msg.Body.MessageId`, with no binding to the sender's address and no check for an existing entry, so a second request reusing the same MessageId silently overwrites the first user's callback. Since the DON's asynchronous trigger response is later looked up and delivered by the same unauthenticated MessageId key in `handleWebAPITriggerMessage`, this allows response misdelivery (DoS on the original request) and potential cross-user response confusion.

### Finding Description
`MessageId` is fully attacker-controlled: it originates either directly from `MessageBody.MessageId` set by the client or from the JSON-RPC request `ID` field copied verbatim in `ValidatedMessageFromReq` ( [2](#0-1) ). `Message.Validate()` only checks length/format of `MessageId`, and derives `Body.Sender` from signature verification, but never ties `MessageId` uniqueness to `Sender` ( [3](#0-2) ).

In `HandleLegacyUserMessage`, after validating the message, the handler does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [4](#0-3) 

There is no `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { reject }` guard, and the key is a plain `string` (the raw MessageId), not a `(sender, id)` tuple. Contrast this with the codebase's own `requestCache` abstraction used by other gateway handlers (`vault`, `confidentialrelay`), which keys pending requests by `globalId{sender, id}` and explicitly rejects duplicate `(sender, id)` pairs with `"request already exists"` ( [1](#0-0) ) — demonstrating this is a recognized correctness requirement that the legacy capabilities handler fails to implement.

Later, when a DON node responds with `MethodWebAPITrigger`, the gateway resolves and clears the callback purely by `MessageId`:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    ... return savedCb.SendResponse(...)
}
``` [5](#0-4) 

Exploit flow: Attacker A signs and sends a valid request with `MessageId = "X"`. Legitimate user B, using an unrelated key, independently (or by coincidence/predictable ID scheme) sends a request also with `MessageId = "X"` shortly after. B's `savedCallbacks["X"]` entry overwrites A's. Both requests are forwarded to DON nodes with their own distinct payloads/signatures (each request's `req` is separately validated and signed by its own sender via `ValidatedRequestFromMessage`, so per-request signature checks pass for each independently — the collision is only in the gateway's in-memory bookkeeping, not in message authentication). Whichever DON response for MessageId `"X"` arrives first at `handleWebAPITriggerMessage` is delivered to whatever callback currently occupies the map slot — potentially B's callback receiving a response tied to A's originally-triggered workflow execution, and A's original HTTP-waiting client receiving no response until timeout/never (since the entry was deleted after delivering to B).

### Impact Explanation
This is a cross-user response confusion / minor denial-of-service inside the gateway's legacy web API trigger flow: an unprivileged party can (a) cause another concurrently pending user's request to silently hang/fail (never receive its DON response, or receive a spurious timeout), and (b) potentially receive a DON-generated payload responding to a workflow trigger that was not their own request, if response content differs based on which request triggered it. It does not directly leak secrets, bypass key material, or move funds; the tangible harm is disruption/confusion of concurrent legacy-handler users, not full account takeover.

### Likelihood Explanation
Exploitability requires only the ability to send a normal signed gateway trigger request (any external, unprivileged holder of a signing key that the DON accepts as a valid sender per its config) and knowledge/guessing of another pending request's `MessageId` at the same moment — since `MessageId` is attacker/client chosen and not a server-issued random nonce, it is straightforward to intentionally collide with a predictable/observed ID (e.g., using the JSON-RPC request `id` scheme many clients set to simple counters), and no special timing beyond issuing the request while the ID is still pending (within `CallbackMaxAgeSec`, default 120s) is needed. This is repeatable in a Go handler test by directly invoking `HandleLegacyUserMessage` twice with the same `MessageId` from two callbacks and observing overwrite.

### Recommendation
Key `savedCallbacks` by a composite of `(msg.Body.Sender, msg.Body.MessageId)` instead of `MessageId` alone (mirroring `common.requestCache`'s `globalId{sender, id}` pattern), and reject/no-op on collision within the same sender key instead of silently overwriting. Alternatively, replace the legacy map with the existing `common.RequestCache` abstraction, which already enforces this invariant.

### Proof of Concept
Go handler-level test (add to `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a stub `handlers.DON` (no-op `SendToNode`).
2. Create two distinct `handlers.Callback` mocks (`cbA`, `cbB`) each recording the `UserCallbackPayload` passed to `SendResponse`.
3. Build `msgA` signed by key A with `Body.MessageId = "X"`, and `msgB` signed by an unrelated key B with `Body.MessageId = "X"` (both pass `Validate()` independently — distinct signers/senders).
4. Call `h.HandleLegacyUserMessage(ctx, msgA, cbA)` then `h.HandleLegacyUserMessage(ctx, msgB, cbB)`.
5. Assert `h.savedCallbacks["X"].Callback == cbB` (overwrite occurred, `cbA` reference lost) — i.e., `require.NotEqual(t, cbA, h.savedCallbacks["X"].Callback)` and length of `savedCallbacks` is 1 despite two distinct senders.
6. Simulate a DON node response with `MethodWebAPITrigger` and `MessageId = "X"` via `h.HandleNodeMessage`; assert only `cbB.SendResponse` is invoked and `cbA.SendResponse` is never called, demonstrating user A's request is silently dropped/never resolved.
7. (Optional stronger assertion) If the map instead correctly used `(sender, id)` keys, both `cbA` and `cbB` entries should coexist and each would be resolved independently by their respective sender-scoped node responses.
