### Title
Claimed instant-withdraw receipts are replayed into default-recovery accounting, inflating the claim basis and phantom prefunded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` clears the aggregate receipt counters (`instantWithdrawsRequests[_user]`, strategy tokens burned, underlying paid) but never clears the per-epoch receipt markers `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` (IdleCreditVault.sol:380-393). Those per-epoch values are the exact replay surface used later by `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` at `finalizeDefaultRecovery` and by `_claimDefaultedInstantWithdrawRequest` at claim time. A receipt that was already paid at par is therefore "replayed" into the default-epoch basis, the same class of bug as CVE-2015-7973 (consumed messages re-accepted by the protocol).

### Finding Description
The vulnerable sequence, all inside one strategy epoch (`epochNumber` only increments in `deposit()` at `stopEpoch`, IdleCreditVault.sol:607-614):

1. During the buffer, attacker requests an instant withdraw of `A` via `requestInstantWithdraw` (IdleCreditVault.sol:356-375). This sets `instantWithdrawsRequests[attacker] += A`, `instantWithdrawsRequestsByEpoch[attacker][E] += A`, `instantWithdrawClaimsByEpoch[E] += A`, `pendingInstantWithdraws += A`.
2. The CDO funds it through `collectInstantWithdrawFunds` (`pendingInstantWithdraws` back to 0) and the attacker calls `claimInstantWithdrawRequest` → receipt tokens burned, `A` paid at par. `instantWithdrawsRequestsByEpoch[attacker][E]` and `instantWithdrawClaimsByEpoch[E]` stay at `A` — the consumed receipt is still "live" in per-epoch accounting.
3. Another instant request `B` arrives in the same epoch and remains unfunded (`pendingInstantWithdraws = B`, `instantWithdrawClaimsByEpoch[E] = A + B`).
4. The honest borrower defaults and the CDO calls `finalizeDefaultRecovery` (IdleCreditVault.sol:661-710) while `epochNumber == E`:
   - `defaultPendingClaimBasis` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[E]` = basis includes the already-paid `A` (IdleCreditVault.sol:644-649).
   - `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant = (A + B) - B = A` and adds this *phantom* `A` to `reserveAmount` (IdleCreditVault.sol:685-686, 716-723). No underlying backs that `A` — it was already transferred out in step 2.
   - `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore computed with `A` in both numerator and denominator, but only the denominator corresponds to real claims. The reserve pays out `recoveryPrice` on `A` of claims whose funds no longer exist.
5. At claim time, `_claimDefaultedInstantWithdrawRequest` (IdleCreditVault.sol:842-856) reads the stale `instantWithdrawsRequestsByEpoch[attacker][E] = A` and tries `instantWithdrawsRequests[attacker] -= A`, which underflows (aggregate was zeroed in step 2) — the attacker cannot be paid twice, but every *other* claimant's payout is priced against an inflated reserve/basis, so the recovery reserve is drained early and the last claimants' `safeTransfer` in `_transferDefaultRecovery` reverts for lack of underlying.

### Impact Explanation
Direct insolvency of `defaultRecoveryReserve`: defaulted-epoch receipt holders and active LPs (via the minted/burned `activeFinalNAV` adjustment that uses the same `recoveryPrice`, IdleCreditVault.sol:699-705) are paid from a reserve whose price was computed on non-existent prefunded funds. Quantified loss: up to the full amount `A` of every instant withdraw claimed earlier in the default epoch, socialized as a shortfall for whoever claims last — permanent loss of underlying for honest receipt holders. Broken invariant: one receipt one payout / recovery price must divide only real funds over real claims.

### Likelihood Explanation
Requires only unprivileged actions: an instant withdraw request, its claim, and another user's (or the same attacker's) instant request staying unfunded in the same strategy epoch when the honest borrower defaults. Instant withdraws and claims during the buffer are normal user flows; no privileged misbehavior is needed. The guard that blocks repeat normal requests after loss (`lastWithdrawRequest`/`lossRecoveryPriceByEpoch` check at IdleCreditVault.sol:261-271) has no equivalent for the instant path, and no code path ever clears `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` outside `_claimDefaultedInstantWithdrawRequest`, so the stale entry deterministically reaches finalization.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch markers for the request's epoch alongside the aggregate (i.e., decrement `instantWithdrawClaimsByEpoch` for each epoch covered and zero `instantWithdrawsRequestsByEpoch[_user][epoch]`), or record per-user funded status so `_defaultPrefundedInstantReserve`/`defaultPendingClaimBasis` only count still-unclaimed receipts. Alternatively track a `instantWithdrawFundedByEpoch` counter so claimed-and-funded receipts are excluded from the default-epoch basis.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (test/foundry/), on a credit-vault CDO with instant withdraws enabled
// Assumes helpers _depositWithUser / _startEpochAndCheckPrices / _stopCurrentEpochWithApr
// from IdleCreditVault.t.sol and an instant-enabled epoch variant.

function testClaimedInstantReceiptReplaysIntoDefaultBasis() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    address alice = makeAddr('alice');
    address bob   = makeAddr('bob');
    uint256 A = 5_000 * ONE_SCALE;
    uint256 B = 5_000 * ONE_SCALE;

    // buffer phase: alice deposits, requests instant withdraw of A
    _depositWithUser(alice, 100_000 * ONE_SCALE, true);
    vm.prank(alice);
    cdoEpoch.requestInstantWithdraw(A, address(AAtranche)); // or AA/BB instant entry point
    uint256 epochE = vault.epochNumber();

    // CDO funds alice's request; she claims at par
    vm.prank(manager); // or the honest queue/CDO path that calls collectInstantWithdrawFunds
    // collectInstantWithdrawFunds(A) is invoked by the CDO during its funding flow
    vm.prank(alice);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(vault.instantWithdrawsRequests(alice), 0);
    // BUG: per-epoch markers still hold A
    assertEq(vault.instantWithdrawsRequestsByEpoch(alice, epochE), A);
    assertEq(vault.instantWithdrawClaimsByEpoch(epochE), A);

    // bob requests instant withdraw B in the same epoch; it stays unfunded
    _depositWithUser(bob, 50_000 * ONE_SCALE, true);
    vm.prank(bob);
    cdoEpoch.requestInstantWithdraw(B, address(AAtranche));
    assertEq(vault.pendingInstantWithdraws(), B);
    assertEq(vault.epochNumber(), epochE); // no stopEpoch in between

    // honest borrower defaults; CDO calls finalizeDefaultRecovery with real recovered funds R
    // basis is inflated by phantom A:
    assertEq(vault.defaultPendingClaimBasis(), vault.pendingWithdraws() + A + B);
    // and _defaultPrefundedInstantReserve reports A that no longer exists in the vault
    // -> recoveryPrice computed on A phantom reserve; last claimant's transfer reverts.
}
```

The assertion on `instantWithdrawsRequestsByEpoch(alice, epochE)` and `instantWithdrawClaimsByEpoch(epochE)` after the claim is the minimal deterministic proof of the replay: consumed receipts remain counted in the epoch basis used by `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest`. The full PoC would then finalize the default with `R = B` recovered and show the reserve paying out at a price that assumes `A + B` of backing, leaving the final claimant's `_transferDefaultRecovery` reverting on insufficient underlying.

Caveat: exact CDO entry-point names for instant requests/claims (`requestInstantWithdraw`/`claimInstantWithdrawRequest` on `IdleCDOEpochVariant`) and the funding path via `collectInstantWithdrawFunds` should be confirmed against `IdleCDOEpochVariant.sol` when writing the PoC; the strategy-side accounting flaw itself is fully visible in `IdleCreditVault.sol`.
