### Title
Signer's cross-tenure sibling-conflict guard misses blocks adopted via `NewBlock` without a locally recorded signature, letting the signer sign a conflicting block at an already-adopted height - ([File: stacks-signer/src/v0/signer.rs], [File: stacks-signer/src/signerdb.rs])

### Summary
The Beanstalk report is about a tracking array (`depositIdList`) that is not updated when a deposit is added through an alternate code path (migration), so a later invariant check (removal) that trusts the array silently breaks. The direct analog here is `SignerDb::get_signed_conflicts`, the "is there already a signed sibling at this height" backstop used before a signer places a fresh signature. That query only considers a block a "signed conflict" if `signed_self` or `signed_group` is set. But a block can reach `BlockState::GloballyAccepted` through the `NewBlock` event path in `stacks-signer/src/v0/signer.rs` without either of those columns ever being populated, i.e. the "tracking column" for conflict detection is never updated on this alternate path to global acceptance.

### Finding Description
`get_signed_conflicts` is explicitly documented as the backstop for cross-tenure siblings that the tenure-scoped chainstate re-check cannot see: [1](#0-0) 

Its SQL filter requires a signature timestamp: [2](#0-1) 

However, when the local signer observes the node adopting a block via a `NewBlock` event, it marks the block `GloballyAccepted` directly, without ever calling `add_block_signature` and without setting `signed_self`/`signed_group`: [3](#0-2) 

`check_state` permits this transition to `GloballyAccepted` from essentially any non-terminal prior state (`Unprocessed`, `LocallyRejected`, `PreCommitted`, etc.): [4](#0-3) 

So a block this local signer never signed (e.g. it locally rejected the proposal, or it was simply offline for the gossip round while the rest of the set signed and the node processed the block) can still land in this signer's DB as `GloballyAccepted` with `signed_self = NULL` and `signed_group = NULL`. When a competing sibling block at the same Stacks height, in a *different* tenure, later reaches the pre-commit threshold at this signer, the pre-commit path runs `get_signed_conflicts` as the last line of defense before signing: [5](#0-4) 

Because the already-adopted sibling has no `signed_self`/`signed_group`, the SQL predicate `(b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)` excludes it from the conflict result set, exactly mirroring the Beanstalk bug where an item added through an alternate path is invisible to the array/query that a later safety check depends on. The own-tenure `DuplicateBlockFound` check only fires at proposal time and only within one tenure, and the chainstate re-check at pre-commit time is also single-tenure-scoped, so this query is the *only* guard covering the cross-tenure sibling case: [6](#0-5) 

With the guard blind to the already-chain-adopted block, the signer proceeds to sign the sibling.

### Impact Explanation
This breaks the "signed/adopted vs. conflicting" equality the guard exists to enforce: the signer ends up signing a non-canonical block at a Stacks height for which the node has already processed and adopted a different, competing block in a different tenure. Per the rules, this is Critical: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
The trigger requires only a one-slot miner proposing two sibling tenure-competing blocks at the same height (one that wins global signature/adoption on the network broadly, one presented to a specific target signer), combined with that target signer missing the `BlockResponse` gossip for the winning block (offline signer, network partition, or the signer itself locally rejecting it) before later receiving the `NewBlock` announcement. No signer majority or key compromise is required, satisfying the "one slot miner plus gossip" bound in scope.

### Recommendation
Update `get_signed_conflicts` (or the state transition path in `mark_globally_accepted`/`NewBlock` handling) so that reaching `GloballyAccepted` also counts as "signed" for conflict-detection purposes, e.g. by stamping `signed_group` (or an equivalent adoption timestamp) whenever a block transitions to `GloballyAccepted` via the `NewBlock`/tenure-tip path, mirroring the deposit-list fix of always updating the tracking structure whenever state is added through any path, not just the primary one.

### Proof of Concept
1. Signer S is disconnected/delayed during gossip for block A (tenure T1, height H); the rest of the signer set signs A and the node processes it.
2. S receives the `NewBlock` event for A and calls the code at `stacks-signer/src/v0/signer.rs:710-726`, marking A `GloballyAccepted` in its DB with `signed_self = NULL`, `signed_group = NULL`.
3. Miner proposes sibling block B at height H in a different tenure T2. B reaches the pre-commit threshold at S.
4. S calls `get_signed_conflicts(H, B_hash)`; because A has no `signed_self`/`signed_group`, the row for A is excluded.
5. Absent a returned conflict, S proceeds through `handle_block_pre_commit` and signs B, producing a signer signature over a block conflicting with the already-adopted canonical block A at the same height.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
