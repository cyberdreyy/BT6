### Title
Stale confirmations from removed multisig members are counted toward the confirmation threshold, allowing request execution below the effective live-member quorum - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` (and the analogous `DeleteKey` handler in `multisig/src/lib.rs`) only purges pending requests and confirmations for requests **created by** the removed member. It never scrubs the removed member's `confirmations` entries on requests created by *other* members. Because `confirm()` counts set membership in `self.confirmations.get(&request_id)` without re-validating that every entry in that set is still a current member of `self.members`, a confirmation cast by a member before their removal remains valid "weight" toward `num_confirmations` forever. This breaks the equality the contract is supposed to guarantee: `confirmations counted == confirmations from currently live members`.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` (and `multisig/src/lib.rs`) computes quorum purely from the size of the stored `HashSet<String>` of confirming members for a request: [1](#0-0) 

The set is only cleaned up when a request is deleted, executed, or when the *request's creator* is removed via `delete_member`: [2](#0-1) 

Notice the filter `if r.member == member` only matches requests where the removed member is the **creator** (`r.member`, i.e. `MultiSigRequestWithSigner.member`). It does nothing about `self.confirmations` entries belonging to that member on requests created by someone else. `assert_valid_request()` also never re-checks that stored confirmers are still members: [3](#0-2) 

So the following sequence is possible with only ordinary multisig operations (no owner/foundation/redeploy required):
1. Members are `{A, B, C, D}`, `num_confirmations = 3`.
2. `D` (or anyone) creates request `X` (e.g. `Transfer` of contract funds to an attacker-controlled account).
3. `C` confirms `X` → `confirmations(X) = {C}`.
4. Through a separate, legitimate `DeleteMember{C}` request (itself requiring 3 confirmations from the then-current membership), `C` is removed. `delete_member` only cleans requests `C` created; `X` (created by `D`) is untouched, so `confirmations(X)` still contains `C`.
5. Members are now `{A, B, D}`, `num_confirmations` unchanged at 3 (the `assert!` in `delete_member` only checks `members.len()-1 >= num_confirmations`, it never lowers `num_confirmations`).
6. `A` confirms `X` → `confirmations(X) = {C, A}`, len = 2.
7. `B` confirms `X` → `len + 1 = 3 >= num_confirmations (3)` → **`execute_request` fires**, even though only 2 of the 3 currently-live members (`A`, `B`) actually approved it.

The stale confirmation from a since-removed member is silently counted as live quorum weight. The identical pattern exists in the v1 `multisig/src/lib.rs` via `DeleteKey`, which likewise only clears confirmations for requests the departing key itself created.

### Impact Explanation
This is a threshold-authorization bypass: a multisig request (including `Transfer` of NEAR, `FunctionCall`, `AddKey`, `DeployContract`, etc.) is executed below the number of confirmations from currently-authorized members that the contract is supposed to require. This directly matches the Critical category "a multisig request executed below threshold," since funds or privileged operations can move with fewer live signers than `num_confirmations` mandates.

### Likelihood Explanation
No foundation, victim key, redeploy, or off-chain access is needed — only the normal lifecycle of adding/removing members that every multisig account goes through. Membership turnover (offboarding an employee/key, rotating a compromised key) is a routine multisig operation, and any request left pending with a confirmation from the departing member at the time of their removal becomes a latent phantom vote. Colluding minority members can deliberately engineer this (get a soon-to-be-removed member to confirm a request, then push through the member's removal, then supply only `num_confirmations - 1` fresh confirmations) to execute an unauthorized transfer.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over **all** active requests' confirmation sets and strip the removed member's entry (not just requests the member created), or alternatively re-validate at `confirm()`/`execute_request` time that every entry in the stored confirmation set still belongs to `self.members` before counting it toward quorum.

### Proof of Concept
Given `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`:
1. `D` (as a member) calls `add_request({receiver_id: multisig_account, actions: [Transfer{amount}]})` → `request_id = X`.
2. `C` calls `confirm(X)` → 1 confirmation stored (`{C}`).
3. Members collectively execute a `DeleteMember{C}` request through the normal 3-of-4 process (unrelated request, reaches quorum honestly with A, B, D confirming) — `C` is removed; `X`'s stored confirmation set still contains `C`.
4. `A` calls `confirm(X)` → `{C, A}`, len 2.
5. `B` calls `confirm(X)` → `len(2)+1 >= num_confirmations(3)` → `execute_request(X)` fires and the transfer executes, having received live confirmations only from `A` and `B` — one short of the mandated 3-of-3 (post-removal) or 3-of-4 (pre-removal) quorum. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
