### Title
An unprivileged APR0 withdraw request can permanently wedge `stopEpoch` once the manager sets a non-zero APR, freezing all pending withdrawals - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`prepareStopEpochWithApr0` hard-reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` (lines 502–508). Any KYC-passing user can populate `apr0TotalPrincipal` by calling `requestWithdraw` while the vault is in APR=0 mode. If the honest manager later raises the APR (a routine operational action), every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts until APR is forced back to 0, freezing pending withdraw receipts and halting the epoch state machine — the analog of a malformed input crashing the service and it "not restarting" on its own.

### Finding Description
The fluent-bit bug is a crash on attacker-supplied input (invalid `x-www-form-urlencoded` payload → NULL deref → process dies and does not restart). The credit-vault analog is a persistent protocol state wedge triggered by an unprivileged transaction: `requestWithdraw` with `unscaledApr == 0` records attacker-controlled `apr0TotalPrincipal` (`_requestWithdrawApr0`, lines 567–577). That state is a latent landmine: `prepareStopEpochWithApr0` (lines 490–508) returns early only when `_principal == 0`; otherwise it reverts with `NotAllowed` when `unscaledApr != 0`. Since `stopEpoch` in `IdleCDOEpochVariant` routes through this hook, the epoch cannot close, `epochNumber` cannot advance, `lossRecoveryPriceByEpoch`/`collectWithdrawFunds` never run, and `claimWithdrawRequest` keeps reverting at the `epochNumber <= lastWithdrawRequest` gate (line 326). The revert is not a one-off: it repeats on every `stopEpoch` attempt while `unscaledApr != 0`.

### Impact Explanation
Temporary freezing of all funds gated on epoch closure: pending withdraw receipts cannot be claimed, new depositors' funds are locked mid-epoch, and borrower repayments cannot be settled. The freeze persists until the manager notices and calls `setAprs`/`setApr` to restore `unscaledApr = 0` — matching the "crashes and does not restart" semantics, since recovery requires manual intervention rather than happening automatically. Quantified loss: time-value and missed yield on the entire vault NAV for the frozen duration; if the wedge coincides with borrower distress, the delay also delays loss socialization.

### Likelihood Explanation
Requires two conditions: (1) the vault operates in APR=0 mode (a supported configuration — `unscaledApr == 0` is a first-class branch in `requestWithdraw`, line 285), and (2) an attacker submits any nonzero `requestWithdraw` in that mode — cheap, KYC-gated only. The trigger (manager later setting a nonzero APR) is an honest, routine action, not attacker collusion. Whether `setAprs` itself guards against `apr0TotalPrincipal != 0` could not be fully verified in the available code; if it does not, the wedge is straightforward to land. Recovery requires only restoring APR 0, so the impact is temporary freezing rather than permanent loss — appropriate to Medium/Low likelihood of material harm but a real invariant break (liveness of the epoch state machine depends on a user-controllable counter).

### Recommendation
Remove the revert and make APR0 settlement tolerant of APR changes: either (a) settle APR0 principal at the rate captured in `apr0RateByEpoch` for its request epoch and treat later epochs under the new APR, or (b) snapshot-and-close the APR0 bucket inside `setAprs`/`setApr` when `unscaledApr` transitions away from 0 (equivalently, revert the *APR change* when `apr0TotalPrincipal != 0`, forcing an explicit `settleApr0` step), or (c) in `prepareStopEpochWithApr0`, skip the interest allocation but still close the bucket (`apr0TotalPrincipal = 0`) and record a zero rate instead of reverting. Option (c) is the minimal fix: APR0 users forfeit pro-rata interest for an epoch whose APR changed — economically correct, since interest was never accrued at a nonzero APR during their request epoch.

### Proof of Concept
Foundry fork sequence (mode: APR0 vault, non-instant withdraws):

```solidity
// 1. Vault configured with unscaledApr == 0 (existing APR0 test setup).
// 2. Attacker (KYC-passing user) deposits and requests a withdraw.
vm.prank(attacker);
cdoEpoch.requestWithdraw(attackerTrancheBalance, address(AAtranche));
// apr0TotalPrincipal > 0 now (IdleCreditVault._requestWithdrawApr0)

// 3. Honest manager raises APR for the next epoch.
vm.prank(manager);
IdleCreditVault(strategy).setAprs(500, 500); // unscaledApr != 0

// 4. Next stopEpoch reverts — epoch can never close at nonzero APR.
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(0, 0);
// prepareStopEpochWithApr0 hits `if (unscaledApr != 0) revert NotAllowed()`
// because apr0TotalPrincipal != 0 (lines 502-508).

// 5. Attacker's (and every user's) withdraw stays unclaimable:
vm.prank(attacker);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimWithdrawRequest(); // epochNumber <= lastWithdrawRequest gate

// 6. Only recovery: manager must set APR back to 0 — manual restart, not automatic.
```

Invariant broken: epoch state-machine liveness must not depend on a counter any unprivileged user can set.
