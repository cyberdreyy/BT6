### Title
Panic-based DoS in `Bank::simulate_transaction` invariant check reachable via `simulateTransaction` RPC — ([File: runtime/src/bank.rs])

### Summary
The MobileCoin report describes a class of bug where a state-machine invariant is enforced with a hard `assert!`/`assert_eq!` that is not guaranteed to hold along every code path that can reach it, so a single externally-triggerable input can violate the assertion and crash the process. Agave has a direct analog: `Bank::simulate_transaction` asserts the bank is frozen before running simulation, but this invariant depends on which bank object the RPC layer hands it, and the assertion is not re-verified/enforced independently of that caller context.

### Finding Description
`Bank::simulate_transaction` enforces a hard runtime invariant that the bank must be frozen: [1](#0-0) 

This function is called directly from the `simulateTransaction` JSON-RPC handler in `rpc/src/rpc.rs`, using whatever bank object `meta.get_bank_with_config(...)` resolves to for the requested commitment level: [2](#0-1) 

The test suite explicitly documents that calling this code path against an **unfrozen** bank causes an `assert!` panic: [3](#0-2) 

This is structurally identical to the MobileCoin finding: the phase/state invariant (`is_frozen()` here, `Phase::NominatePrepare`/`Phase::Prepare` in SCP) is checked with a hard assertion inside the state-transition function, but the invariant is established by *other* code (whichever code path selects/produces the bank passed in) rather than being locally guaranteed by the function itself. Any caller that reaches `simulate_transaction` with a bank object that has not yet been frozen — e.g., a bank corresponding to `commitment: "processed"` for a slot that is still being actively built/replayed — hits the same `assert!` panic path demonstrated by the test.

### Impact Explanation
A `panic!`/`assert!` firing on an RPC worker thread is a validator-process crash if the runtime is built with `panic = "abort"` (the conventional configuration for consensus-critical Rust services, to avoid continuing with inconsistent process state after a failed invariant), or at minimum reliably fails a request/thread. Since `simulateTransaction` is an unprivileged, publicly exposed RPC method taking a single crafted transaction and commitment parameter, this matches the report's "Eve sends a crafted transaction… causing an assertion violation followed by a crash" exploit scenario precisely, mapped onto the agave RPC surface instead of MobileCoin's SCP consensus module.

### Likelihood Explanation
Reaching `simulate_transaction` with a bank object is trivial for any RPC user (single call, no elevated privileges, no special config). Reaching it with a bank that is *not frozen* depends on the internal timing/behavior of `get_bank_with_config` for lower commitment levels (e.g. `processed`) — I was not able to fully verify, within the available tooling, whether `get_bank_with_config` in this codebase always guarantees a frozen bank before returning it for every commitment level, or whether there exists a window (e.g., while the working bank for the current slot is actively being replayed/built) where an unfrozen bank can be returned. This is the key uncertainty in this analog: if `get_bank_with_config` unconditionally freezes/clones a frozen bank for all commitment levels, this path is unreachable in practice and the assertion is dead code from an attacker's perspective; if it can return the live working bank, the bug is directly and trivially triggerable.

### Recommendation
- Make `Bank::simulate_transaction` defensively return a `Result`/`TransactionError` instead of `assert!`ing when the bank is not frozen, mirroring the report's short-term recommendation to eliminate hard phase/invariant assertions in favor of graceful error handling on paths reachable from untrusted input.
- Audit `get_bank_with_config` and all callers of `simulate_transaction` (and any other function guarded by a bank-frozen assertion) to guarantee, at the type or call-site level, that only frozen banks can ever reach these assertions — rather than relying on caller discipline.
- As the MobileCoin report's long-term recommendation states, add fuzzing (e.g., fuzzing the JSON-RPC surface with randomized commitment/config combinations and transactions) to catch equivalent invariant-violation panics elsewhere in the RPC-reachable codebase.

### Proof of Concept
The existing unit test already demonstrates the crash condition end-to-end through the RPC handler: [3](#0-2) 
Conceptually: issue a `simulateTransaction` JSON-RPC request with `commitment: "processed"` (or whichever commitment resolves to the not-yet-frozen working bank) against a validator whose current-slot bank has not been frozen yet, causing `Bank::simulate_transaction`'s `assert!(self.is_frozen(), "simulation bank must be frozen")` to fire on the RPC-serving thread.

**Note on confidence:** I could not, within the tool budget, trace `get_bank_with_config`'s implementation to conclusively confirm whether an unfrozen bank can actually be returned for any commitment level in production operation. This is the load-bearing assumption of the finding; if `get_bank_with_config` always freezes/clones before returning, this specific analog is not exploitable and would need to be reclassified as a defense-in-depth issue rather than a triggerable vulnerability.
