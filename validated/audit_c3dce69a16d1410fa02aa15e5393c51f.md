### Title
Node RPC failure in own-tenure conflict check causes signer to sign a conflicting block at the same height — fail-open analog of unguarded oracle dependency ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit`'s own-tenure conflict guard depends on a single external RPC call, `stacks_client.get_tenure_tip`, to decide whether a same-tenure conflicting block that has already been signed still blocks the currently-thresholded proposal. When that call fails for any reason (node busy, timeout, connection reset, node temporarily unavailable), the code does not refuse to sign (fail-safe) — it logs a warning and falls through to sign the block anyway, exactly mirroring the reported bug class: an external dependency whose unavailability is not defensively handled, except here failure opens the signing gate instead of just reverting a price read.

### Finding Description
In `Signer::handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs`), once a block crosses the pre-commit weight threshold, the signer must verify it does not conflict with a previously signed block in the *same* tenure at the same or higher height (a duplicate/double-sign guard, since the standard proposal-time `DuplicateBlockFound` check runs only once, at initial proposal arrival, per `docs/signer-flows.md` section 7): [1](#0-0) 

If `get_tenure_tip` returns `Ok`, the code correctly `return`s (refuses to sign) when the node's canonical tip for that tenure is already at or above the proposed height. But if the RPC call errors (`Err(e)`), the warning is merely logged ("Treating the tenure as unconfirmed") and execution *continues* into the unconditional signing path: [2](#0-1) 

This is a fail-open dependency on the stacks-node RPC endpoint: unlike the earlier `conflict_still_blocks` guard (used for cross-tenure/other conflicts), which explicitly treats "could not ask the node" as "leave the conflict in place" (see `conflict_still_blocks`, `stacks-signer/src/v0/signer.rs:1176-1189,1196-1202` — every `Err` branch there `return`s `true`, i.e., keeps blocking), the own-tenure branch inverts that safety posture: an RPC failure here is treated as "unconfirmed, proceed to sign." The documentation for this branch even confirms the design choice explicitly: *"node unreachable" --> SIGN* (`docs/signer-flows.md:267`), justified only for the "never confirmed" case but coded identically for genuine RPC failures.

### Impact Explanation
If a node RPC call transiently fails (timeout, connection reset, node under load, restart, or a temporary network partition between the signer and its own node) at the exact moment a same-tenure conflicting proposal crosses the pre-commit threshold, the signer will produce a signature for a block that duplicates or conflicts with state the node has already built — the very double-sign scenario this guard exists to prevent (see the guard's own preamble comment about the "own-tenure" conflict at lines 1423-1431). This falls squarely under the Critical class defined in scope: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
No malicious majority or key compromise is required. Two competing block proposals can legitimately arise in the same tenure (e.g., a re-proposed tenure-start block after the first failed to reach consensus, as called out in the code comment at line 1369-1372), and pre-commit crossing threshold happens via ordinary gossip once enough honest signers weigh in. All that's additionally needed is a single transient RPC error to the local stacks-node at the moment of that specific check — a routine occurrence in any long-running node (timeouts, restarts, load spikes), not an adversarial precondition.

### Recommendation
Make the own-tenure conflict branch fail closed like `conflict_still_blocks` does for cross-tenure conflicts: on `get_tenure_tip` error, treat the conflict as still blocking (refuse to sign for now, allowing a later re-evaluation once the node is reachable again) rather than falling through to `mark_locally_accepted`/`handle_block_signature`. This preserves liveness (the block can still be signed once the node answers) while removing the fail-open path that allows a wrongly-issued, unrevocable signature.

### Proof of Concept
1. Two tenure-start blocks, A and B, are proposed at the same height H in the same tenure (e.g., B is a re-proposal after A stalls), each already tracked/signed against by different subsets of signers such that `get_signed_conflicts` for B returns A as a same-tenure conflict.
2. Enough peers pre-commit to B to cross the 70% weight threshold on this signer (`handle_block_pre_commit`, `stacks-signer/src/v0/signer.rs:1250-1338`).
3. Chainstate re-check and freshness/`conflict_still_blocks` checks (lines 1345-1421) do not veto (e.g., A's conflict is stale, or excluded via `reorg_permit_stands`), reaching the own-tenure branch at line 1432.
4. The signer's call to `stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash)` fails (simulate via a dropped connection, timeout, or node restart at that instant).
5. Execution falls into the `Err(e)` arm (line 1449-1456), logs the warning, and continues to line 1467 onward, producing and broadcasting a signature for block B even though the node's tenure tip may already be at or above H because of block A — a signed conflicting block.
