### Title
ProgrammableBorrower trusts unbounded ERC4626-reported assets for epoch interest, letting a vault user inflate `totalInterestDueNow()` and mint unbacked strategy tokens — (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The kernel bug reads a buffer location from loaded firmware and performs R/W without checking it fits inside L2TCM. The idle-tranches analog is `ProgrammableBorrower._vaultNetInterest()`/`totalInterestDueNow()`: the contract reads `vault.convertToAssets(shares)` — a value an unprivileged user of the same ERC4626 vault can manipulate via a direct underlying donation (share-price inflation) — and feeds it, with no upper bound, into `totalInterestDueNow()`. `IdleCDOEpochVariant._stopEpoch` then consumes that value as `_expectedInterest` and, because programmable mode requires `isInterestMinted`, calls `mintStrategyTokens(_grossInterest)`, minting unbacked strategy tokens that inflate tranche `virtualPrice`. An attacker holding tranche tokens then redeems at the inflated price and steals other LPs' principal.

### Finding Description
- `ProgrammableBorrower.totalInterestDueNow()` returns `vaultInterest + borrowerInterestAccruedNow() + bufferInterest - loss`, where `vaultInterest` derives from `_currentVaultAssets()` = `vault.convertToAssets(vault.balanceOf(this))` at [1](#0-0) . `convertToAssets` is a manipulable exchange rate: any ERC4626 user can donate underlying to the vault, inflating assets-per-share.
- `IdleCDOEpochVariant._stopEpoch` resolves `_interest` (for programmable borrowers this is `totalInterestDueNow()`, confirmed by the comment "totalInterestDueNow() was already read by IdleCDO before calling this hook" at [2](#0-1) ) and in minted mode calls `_strategy.mintStrategyTokens(_grossInterest)` at [3](#0-2) , creating strategy tokens with zero underlying backing, then `_updateAccounting()` raises `virtualPrice`.
- The only sanity bound is the `maxApr` check at [4](#0-3) , which is a no-op when `maxApr == 0` (`_maxApr != 0` short-circuits) and only applies to the `_interest > 1` override path anyway. `setMaxApr(0)` is the documented "disable the cap" configuration at [5](#0-4) .
- `_skimDonatedAssets()` at [6](#0-5)  only removes donations sent to the CDO itself; it cannot see donations made to the external vault, so the donation-isolation guard does not cover this path.
- Epoch mode constraints are satisfied: programmable mode forces minted interest via `_checkProgrammableBorrowerMode` ( [7](#0-6) ), so the unbacked-mint path is mandatory, not optional.

### Impact Explanation
Broken invariant: fair mint/burn and solvency — strategy tokens are minted against interest that exists only as inflated vault share value, not as borrower-paid assets. After `stopEpoch`, `virtualPrice` rises for all tranches; the attacker (a KYC'd tranche holder) submits a normal withdraw request and claims underlying at the inflated price. Since `mintStrategyTokens` added no backing, early claimants drain real principal while later claimants are left with unbacked receipts — direct theft quantified by `(inflatedInterest × attackerShareOfSupply) - donationCost`. In a 1:1 vault-share donation the attacker recaptures most of the donation through their vault-independent tranche claim, so net cost is bounded by the share of vault interest attributable to other vault depositors.

### Likelihood Explanation
Requires: a programmable-borrower vault in minted mode, `maxApr == 0` (explicitly supported), an attacker who is both a tranche holder and a depositor/donor into the same ERC4626 vault (an explicitly allowed attacker class), and an honest manager calling `stopEpoch` afterward. No privileged collusion is needed; the attacker only sequences around honest `startEpoch`/`stopEpoch` calls. If `maxApr` is set, the same unchecked input instead lets the attacker force `stopEpoch` to revert via over-cap inflation, temporarily freezing epoch settlement until the manager intervenes.

### Recommendation
Bound the externally sourced component before it is minted: in `_vaultNetInterest`/`totalInterestDueNow`, cap recognized `interest` (e.g., at a configurable `maxVaultInterestBps` of `principalAssets`, or require `maxApr != 0` for programmable borrowers), or measure vault PnL only on realized `vault.withdraw`/`redeem` proceeds rather than live `convertToAssets`. Alternatively, apply the existing `maxApr` cap check to the resolved programmable interest unconditionally and treat an over-cap report as a default instead of minting.

```solidity
function testVaultDonationInflatesMintedInterest() external {
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    vm.prank(owner);
    strategy.setMaxApr(0); // uncapped, as permitted by setMaxApr docs

    uint256 deposit = 100_000 * oneScale;
    deal(USDC, attacker, deposit);
    vm.startPrank(attacker);
    IERC20(USDC).approve(address(idleCDO), deposit);

    idleCDO.depositAA(victimDeposit);     // honest LP

    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 donation = 50_000 * oneScale;

    vm.prank(attacker);
    IERC20(USDC).transfer(address(morphoVault), donation);

    uint256 inflated = programmableBorrower.totalInterestDueNow();
    assertGt(inflated, /* honest accrued */ borrowerInterestOnly);

    vm.prank(manager);

    uint256 priceNow = cdoEpoch.virtualPrice(address(aaTranche));

    // assert attackerUnderlyingOut > attackerDeposit + attributable share of donation
    // assert remaining LP claim basis < strategy underlying balance (insolvency)
```

Caveat: I verified the consumption path (`totalInterestDueNow` → `stopEpoch` → `mintStrategyTokens`) and the missing bound, but did not confirm `_resolveStopEpochInterest` line-by-line or the exact vault-donation economics on a specific fork vault; the PoC needs a run to quantify the net extraction precisely.

```text
  function totalInterestDueNow() external view returns (uint256) {
    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();
    uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;
    return totalGain > loss ? totalGain - loss : 0;
  }

  /// @notice Compute the net vault delta split into interest and loss (mutually exclusive).
  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
  }
```
