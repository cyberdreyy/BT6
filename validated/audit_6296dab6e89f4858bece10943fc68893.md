### Title
Stale confirmations from removed multisig members remain counted toward `num_confirmations`, allowing request execution below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
This is a structural analog of the reported bug class: a binding between "confirmations counted" and "live/trusted members" is silently broken when a member's own confirmation on someone else's request is not purged when that member is deleted from the multisig. The Fei report's core defect is that a trust relationship (FlywheelCore ↔ FlywheelRewards) established at one point in time is not re-validated/kept consistent when the trusted party's identity changes, letting stale state be used against current holders. Here, the `confirmations` set recorded for a pending request is never re-validated against the *current* member set, and `delete_member`/`DeleteKey` only clean up confirmations for requests a departing member *created*, not confirmations they merely *cast* on someone else's request.

### Finding Description
`confirm()` counts confirmations purely by set size and compares against `self.num_confirmations`, without re-checking that every entry in the `confirmations` set still corresponds to a current member: [1](#0-0) 

Membership removal (`DeleteMember`/`delete_member`) only purges requests and confirmations for requests where the departing member was the **original requester** (`r.member == member`), not requests where the departing member merely added a confirmation to another member's request: [2](#0-1) 

The equality that should hold is:
`confirmations.len()` (as counted in `confirm()`) == `count of distinct entries in confirmations that are still in self.members`

But after a `DeleteMember` action removes a member who had confirmed (not created) some other pending request, that request's `confirmations` set still contains the removed member's entry, so:
`confirmations.len()` > `count of live members who actually confirmed`

If the multisig later reaches `confirmations.len() + 1 >= num_confirmations` on a stale request whose set includes the removed member's entry, `execute_request` runs with fewer live-member confirmations than `num_confirmations` actually requires.

The same defect exists in the older `multisig/src/lib.rs`: `DeleteKey` handling only removes requests keyed by `r.signer_pk == pk` (the requester), leaving that key's confirmations on other requests intact: [3](#0-2) 

### Impact Explanation
This crosses the exact boundary called out in scope: "confirmations counted versus live members." A request can be executed (moving NEAR, adding/deleting keys, deploying code, calling arbitrary functions) with effectively fewer live, currently-trusted confirmers than the configured `num_confirmations` threshold, because a since-removed member's stale confirmation still counts. This matches the Critical impact category "a multisig request executed below threshold." Removing a member is precisely the security action an operator takes when a key is believed compromised or a member should lose authority; this defect means that member's prior confirmation continues to exert authority after removal, undermining the entire K-of-N custody guarantee for both `multisig` and `multisig2`.

### Likelihood Explanation
This requires only normal multisig usage: (1) member A creates a request, (2) member B (not the creator) confirms it but the request doesn't yet reach threshold, (3) the multisig (via unrelated, legitimate governance action) removes member B, (4) confirmations from other live members subsequently push the stale set's length to `num_confirmations - 1`, causing the final confirming call to execute the request while counting B's phantom confirmation. No malicious key, redeploy, or foundation action is needed — it is a latent bug reachable through the documented `add_request` → `confirm` → `DeleteMember` → `confirm` flow.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate all pending requests and remove the departing member's entry from every request's `confirmations` set (not only requests they created), or alternatively re-validate at `confirm()` time that every entry in `confirmations` is still contained in `self.members` before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 3 members (A, B, C) and `num_confirmations = 2`.
2. A calls `add_request` (request R) — 0 confirmations.
3. B calls `confirm(R)` — `confirmations = {B}`, still below threshold (1 < 2), so it doesn't execute yet.
4. Multisig executes a separate confirmed `DeleteMember{member: B}` request, reducing membership to {A, C}. `delete_member` only clears requests where `r.member == B` (i.e., requests B created); R was created by A, so R's confirmations entry `{B}` is untouched.
5. A calls `confirm(R)` as the second confirmer: `confirmations.len() (1) + 1 >= num_confirmations (2)` → true, so `execute_request` runs.
6. Result: request R executes with only one live member (A) actually confirming at execution time — B's stale, post-removal confirmation was used to satisfy the 2-of-N threshold, violating the intended custody guarantee. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
