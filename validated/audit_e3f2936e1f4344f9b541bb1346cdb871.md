### Title
Miner-controlled conflicting-block spam resets `last_activity_time` and permanently suppresses the signer's inactivity fallback - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
The signer's inactivity watchdog (`SortitionState::is_timed_out`) decides whether to abandon an unresponsive/misbehaving tenure miner and fall back to the prior sortition's miner based on `last_activity_time`, a value stored per-tenure in `SignerDb`. That value is refreshed not only by legitimate block progress, but also by `SortitionData::check_latest_block_in_tenure`, which counts *rejected, non-advancing* block proposals from the current miner as "activity" as long as they conflict with a recently-signed or pre-committed block. Because the current tenure's miner is the only party who can submit proposals for that tenure, this lets that single miner refresh the cooldown indefinitely with junk proposals, exactly analogous to the reported `distributeGold` front-running pattern (an unprivileged/low-trust caller resets a cooldown timestamp that gates a privileged, time-based state transition).

### Finding Description
`update_last_activity_time` is invoked from `SortitionData::check_latest_block_in_tenure` whenever a proposal is rejected for not confirming enough blocks, provided the conflict is still "fresh": [1](#0-0) 
and again for conflicts against a merely pre-committed (never signed) block: [2](#0-1) 

This timestamp is later read by `SortitionState::is_timed_out` (both v1 and v2 chainstate) to decide whether the current miner has gone idle long enough that the signer should stop waiting on it: [3](#0-2) [4](#0-3) 

`check_miner_inactivity` uses this result to decide whether to fall back to the last sortition's miner: [5](#0-4) 

The equality/wedge broken: the signer is supposed to enforce "if the active miner has been inactive for longer than `block_proposal_timeout`, stop trusting it and fall back to the prior miner." Activity is meant to mean *forward chain progress*, but the code also treats *conflicting, rejected* proposals as activity (this is deliberate for genuine reorg-timing edge cases, gated by `reorg_attempts_activity_timeout`/pre-commit freshness). The current tenure's miner is the only actor who can produce syntactically valid proposals for that tenure (correct consensus hash, correct miner pubkey-hash, valid bitvec — enforced in `check_proposal`, e.g. `stacks-signer/src/chainstate/v2.rs:133-163`), so it is a single, low-trust, one-slot actor that fully controls this refresh path. By periodically re-proposing a block at or below the already-signed/pre-committed height (varying the header timestamp so each proposal has a distinct hash and is processed anew), the miner can call `update_last_activity_time` on a schedule faster than `block_proposal_timeout`, keeping `elapsed > block_proposal_timeout` permanently false. This mirrors the reported bug precisely: an unprivileged/low-trust caller (holder of one "slot", the current miner) repeatedly touches a shared cooldown timestamp used to gate a distinct, privileged state transition (fallback to a different miner), preventing that transition from ever firing.

### Impact Explanation
This is a liveness wedge matching the report's "signer wedged into never signing valid blocks" category (High). If a tenure's miner becomes unable or unwilling to produce a valid, advancing block (e.g., it is stalled, censoring transactions, or deliberately withholding progress) but keeps emitting rejected, non-advancing proposals at/below the last signed/pre-committed height, the signer's own state machine never marks it as timed out and never reverts to the prior, legitimate miner. Combined with the fact that this same `is_timed_out`/fallback logic gates whether the signer will consider the prior tenure's proposals valid, this can stall the signer set's forward progress within the tenure indefinitely, without needing cooperation from a majority of signers — a single tenure miner suffices.

### Likelihood Explanation
Reaching this path requires only:
1. Winning (or otherwise legitimately holding) the current sortition, so `check_proposal`'s pubkey/tenure checks pass.
2. Submitting proposals that are syntactically valid but do not advance the chain height beyond what has already been signed/pre-committed, timed to land inside `reorg_attempts_activity_timeout` of the last signature, or inside `tenure_last_block_proposal_timeout` of the last pre-commit, and repeated more frequently than `block_proposal_timeout`.
Both mechanisms already exist in the codebase specifically to treat such proposals as "activity" (to avoid punishing a legitimately slow miner), so no exploit of memory-safety or novel protocol violation is needed — only repeated, well-timed, cheap network messages from the single actor who already controls the tenure.

### Recommendation
Separate "the miner is submitting request traffic" from "the miner is producing progress that should reset the inactivity clock." Concretely:
- Do not let repeatedly-rejected/non-advancing proposals refresh `last_activity_time` indefinitely; cap the number of times, or the total duration, that "conflict-based" freshness can extend the window, independent of new proposals arriving.
- Alternatively, track two distinct timestamps as the original TempleDAO fix did: one that only privileged/canonical progress (a newly signed or globally-accepted block) can update, used exclusively by `is_timed_out`, and a separate best-effort activity signal used purely for logging/diagnostics.
- Bound the freshness window(`reorg_attempts_activity_timeout`, pre-commit freshness) to a fixed real-time deadline anchored to the *first* observed conflict for that tenure, rather than resettable on every subsequent conflicting proposal.

### Proof of Concept
Conceptual PoC (integration-test level, following the pattern of existing tests in `stacks-node/src/tests/signer/v0/reorg.rs` and `stacks-signer/src/chainstate/tests/v2.rs::pre_committed_block_does_not_veto_replacement`):
1. Boot a `SignerTest` past epoch 3 with a short `block_proposal_timeout` (e.g. 20s) and default `reorg_attempts_activity_timeout`/`tenure_last_block_proposal_timeout`.
2. Have the miner mine and get one block globally signed in a tenure (establishes `info.block.header.chain_length` and `signed_group` time).
3. Instead of producing a new higher block, have the miner repeatedly re-propose blocks at the *same* `chain_length` (varying `header.timestamp` to generate a fresh `signer_signature_hash` each time), spaced at an interval shorter than `block_proposal_timeout` but within `reorg_attempts_activity_timeout` of the last signature.
4. Assert via `signer_db.get_last_activity_time(&tenure_id)` (as exercised in `stacks-signer/src/chainstate/tests/v2.rs:1012-1016`) that the timestamp keeps advancing with each rejected proposal.
5. Assert that `SortitionState::is_timed_out` never returns `true` for the tenure even after the nominal `block_proposal_timeout` has elapsed, and that `check_miner_inactivity` never switches `current_miner` to the prior sortition's miner, confirming the fallback is permanently suppressed by miner-controlled traffic.
