### Title
`/v2` pprof debug routes reachable by any authenticated 'view'-role user with no role check - ([File: core/web/router.go])

### Summary
The `metricRoutes` function registers Go's `net/http/pprof` handlers (`cmdline`, `profile`, `heap`, `goroutine`, `trace`, etc.) under the `authv2` route group, which only requires session/token authentication via `auth.Authenticate` but applies no role-based authorization wrapper (`auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole`) unlike virtually every other sensitive endpoint registered in the same block.

### Finding Description
In [1](#0-0) , the `authv2` group is created with only `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)`, which validates that *a* session or token exists but does not check the user's role. Every sensitive action registered on `authv2` (key export/import/delete, job create/update, transfers, admin user management) is explicitly wrapped with `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole`, e.g.: [2](#0-1) 
However, at the end of the block: [3](#0-2) 
`metricRoutes(authv2)` registers the pprof debug group directly onto `authv2` with no additional role wrapper: [4](#0-3) 
This means `/v2/debug/pprof/cmdline`, `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/profile`, `/v2/debug/pprof/trace`, `/v2/debug/pprof/allocs`, `/v2/debug/pprof/block`, `/v2/debug/pprof/mutex`, and `/v2/debug/pprof/threadcreate` are reachable by any authenticated user regardless of role — including a user holding only the lowest 'view' role, who is barred from every other privileged action in the router.

The `paginatedRequest` helper itself in [5](#0-4)  performs no authorization; it is a generic pagination wrapper used across many `authv2` routes (e.g. `/jobs`, `/chains`, `/nodes`) that rely on the surrounding route registration to apply the correct role check — which the debug/pprof registration fails to do.

### Impact Explanation
`/debug/pprof/cmdline` returns the full process command line, which can include secrets passed as CLI flags (e.g., `-password`, keystore passwords, API secrets) depending on how the node was launched. `/debug/pprof/heap` and `/debug/pprof/goroutine` dumps can expose in-memory secrets, private keys, decrypted key material, or other sensitive runtime state held in Go heap objects. This matches Chainlink's "Critical - server credential/key theft" bounty class: an attacker with only a low-privileged authenticated ('view' role) session can extract sensitive node internals without any operator/admin privilege.

### Likelihood Explanation
The only precondition is holding any valid authenticated session or API token for the node — the lowest privilege level ('view' role) is sufficient, since no role check is present on this route group. This is trivially and repeatably exploitable: an attacker simply issues `GET /v2/debug/pprof/cmdline` (or `/heap`, `/goroutine`, etc.) with a valid session cookie/token of a view-only user.

### Recommendation
Wrap the debug/pprof routes with the same privilege level as other sensitive operational endpoints, e.g. `auth.RequiresAdminRole`, before registering them:
```go
authv2Admin := authv2.Group("", auth.RequiresAdminRole)
metricRoutes(authv2Admin)
```
or add an explicit role check inside `metricRoutes`/`ginHandlerFromHTTP` wrapper so pprof handlers reject non-admin roles.

### Proof of Concept
1. Create a test node with two users: one with `Admin` role (or default) and one with `View` role, similar to existing tests in `core/web/router_test.go`/`auth_test.go`.
2. Authenticate as the 'view'-role user (session cookie) and issue `GET /v2/debug/pprof/cmdline` and `GET /v2/debug/pprof/heap`.
3. Assert HTTP status `200 OK` and non-empty response body is returned (proving the debug data leaks), instead of the expected `403 Forbidden` that other privileged routes return for `view`-role users (validate by comparing to `GET /v2/keys/eth/export/:address` under the same session, which correctly returns 403).
4. Repeat for an unauthenticated (no session) request to confirm `auth.Authenticate` at least blocks fully anonymous access, isolating the bug to missing role enforcement rather than missing authentication.
