### Title
Unchecked ERC20 `transfer` return in `MerkleClaim.claim`/`sweep` permanently bricks claims for false-returning tokens - (File: contracts/MerkleClaim.sol)

### Summary
`MerkleClaim.claim` sets `hasClaimed[to] = true` and then performs a raw `IERC20Upgradeable(token).transfer(to, amount)` without checking the return value. For ERC20 tokens that return `false` instead of reverting on failure (e.g., STASIS EURO-style implementations), the transfer silently fails while the claim is permanently marked as consumed. The same pattern exists in `sweep`, which would silently report a successful sweep to the multisig while tokens remain locked.

### Finding Description
In `contracts/MerkleClaim.sol`:

```solidity
// L63-66
hasClaimed[to] = true;
IERC20Upgradeable(token).transfer(to, amount);
```

```solidity
// L74 (sweep)
IERC20Upgradeable(_token).transfer(to, IERC20Upgradeable(_token).balanceOf(address(this)));
```

The raw `.transfer()` discards the boolean return value. Per `IERC20Upgradeable`, a `false` return is a valid failure signal for non-reverting tokens. Because `hasClaimed[to]` is written before the transfer and there is no way to reset it (no admin function clears `hasClaimed`), a single failed claim permanently blocks the claimee from ever claiming again. `sweep` is similarly fire-and-forget: after 60 days the multisig could believe leftover tokens were recovered while they remain in the contract — a false positive identical in spirit to the Telcoin `rescueERC20` bug.

For comparison, all other token movements in scope use `SafeERC20`: `IdleCreditVaultWriteOffEscrow` uses `safeTransfer`/`safeTransferFrom` in `createWriteOffRequest`, `deleteWriteOffRequest`, `fullfillWriteOffRequest`, and `emergencyWithdraw` (`contracts/IdleCreditVaultWriteOffEscrow.sol:93,115,139,146,149,151,179`), and `DefaultDistributor.claim` uses `safeTransferFrom`/`safeTransfer` (`contracts/DefaultDistributor.sol:39-40`). `MerkleClaim` is the outlier.

### Impact Explanation
Permanent freezing of unclaimed tokens: a claimee whose `claim` transaction hits a `false`-returning transfer (frozen flag, blacklist flag, insufficient fee headroom, etc., in tokens like EURS) loses the claim irrevocably — the tokens stay in `MerkleClaim` while `hasClaimed[to]` is `true`. Loss equals the full Merkle-allotted `amount` for that leaf. In `sweep`, the full contract balance can be reported as recovered while still locked (only recoverable via a later `sweep` call once the token unfreezes, but the false success misleads operations during an incident — the exact "rescue false positive" amplification from the source finding).

### Likelihood Explanation
Low-to-medium. It requires the distributed `token` (set at `initialize`) to be a false-returning ERC20, and a transient failure condition (blacklist/frozen flags) at claim time. Merkle trees are typically built for a known reward token, but nothing in the contract constrains `token`, and the contract is a reusable cloneable claim utility. No guard checks the token's behavior, and once triggered the state corruption is irreversible.

### Recommendation
Use `SafeERC20Upgradeable.safeTransfer` (or explicitly `require(IERC20Upgradeable(token).transfer(to, amount))`) in both `claim` and `sweep`. Alternatively, set `hasClaimed[to] = true` only after a verified successful transfer.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {MerkleClaim} from "../contracts/MerkleClaim.sol";
import {IERC20Upgradeable} from "@openzeppelin/contracts-upgradeable/token/ERC20/IERC20Upgradeable.sol";

contract FalseToken is IERC20Upgradeable {
    mapping(address => uint256) public override balanceOf;
    uint256 public override totalSupply;
    mapping(address => mapping(address => uint256)) public override allowance;
    function transfer(address, uint256) external override returns (bool) { return false; } // never moves funds
    function transferFrom(address, address, uint256) external override returns (bool) { return false; }
    function approve(address, uint256) external override returns (bool) { return true; }
    function mint(address to, uint256 amt) external { balanceOf[to] += amt; totalSupply += amt; }
}

contract MerkleClaimFalsePositiveTest is Test {
    using stdStorage for StdStorage;

    MerkleClaim claim;
    FalseToken token;
    address alice = address(0xA11CE);
    uint256 amount = 100e18;

    function setUp() public {
        claim = new MerkleClaim();
        token = new FalseToken();
        // leaf = keccak256(bytes.concat(keccak256(abi.encode(alice, amount))))
        bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(alice, amount))));
        claim.initialize(leaf, address(token));
        token.mint(address(claim), amount);
    }

    function testClaimFalsePositive() public {
        bytes32[] memory proof = new bytes32[](0); // single-leaf tree
        claim.claim(alice, amount, proof);

        // BUG: transfer returned false, alice got nothing,
        // but the claim is permanently consumed.
        assertEq(token.balanceOf(alice), 0);
        assertTrue(claim.hasClaimed(alice));
        // Any retry reverts with AlreadyClaimed() -> funds permanently locked
        vm.expectRevert(MerkleClaim.AlreadyClaimed.selector);
        claim.claim(alice, amount, proof);
        assertEq(token.balanceOf(address(claim)), amount);
    }
}
