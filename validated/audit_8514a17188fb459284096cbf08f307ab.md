## Title
`apply_withdrawals` in Gloas caps builder balance deduction to `min(amount, balance)` while the committed `Withdrawal.amount` sent to the execution layer is the uncapped requested amount — creating Gwei not backed by any deducted stake - ([File: specs/gloas/beacon-chain.md])

### Summary
This is the same "residual/uncapped-amount accounting mismatch" bug class as the `AgentPolice.distributeLiquidatedFunds` report, but inverted in effect: instead of leftover funds getting stuck, the consensus layer *commits* to paying out a `Withdrawal.amount` that is *larger* than what actually gets removed from the payer's accounted balance. In the Solidity report the pool refused to transfer more than it needed and the excess was stranded; here the beacon chain does the opposite — it instructs the execution layer to unconditionally credit the full requested `amount`, while only deducting `min(amount, builder.balance)` from the builder's own ledger. Any shortfall is fabricated Gwei rather than being reconciled or dropped.

### Finding Description
`get_builder_withdrawals` (processing `state.builder_pending_withdrawals`) builds each `Withdrawal` using the raw requested amount, with no cap against the builder's actual balance: [1](#0-0) 

```python
for withdrawal in state.builder_pending_withdrawals:
    ...
    withdrawals.append(
        Withdrawal(
            index=withdrawal_index,
            validator_index=convert_builder_index_to_validator_index(builder_index),
            address=withdrawal.fee_recipient,
            amount=withdrawal.amount,   # <-- uncapped, raw requested amount
        )
    )
```

That `Withdrawal.amount` is placed into `state.payload_expected_withdrawals`, which per spec commentary is a binding instruction to the execution layer: [2](#0-1) 

However, `apply_withdrawals` — which updates the CL-side accounting that is supposed to back that instruction — only deducts the *capped* amount from the builder's balance: [3](#0-2) 

```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
```

So if `withdrawal.amount > builder.balance`, the committed `Withdrawal` (which the EL is required to honor and pay to `fee_recipient` in full) exceeds what is actually removed from the builder's stake. This is confirmed directly by the spec's own test suite, which documents this as expected behavior: [4](#0-3) 

```python
def test_builder_withdrawal_insufficient_balance(spec, state):
    """
    ...
    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
    """
    builder_index = 0
    withdrawal_amount = spec.Gwei(5_000_000_000)
    available_balance = spec.Gwei(1_000_000_000)
    ...
    assert_process_withdrawals(
        ...,
        builder_balances={builder_index: 0},
        withdrawal_amounts_builders={builder_index: withdrawal_amount},
    )
```

Here the builder only had 1 ETH but the committed `Withdrawal.amount` sent to the execution layer is 5 ETH — a 4 ETH shortfall between what is deducted (accounted-for stake destroyed) and what the execution layer is required to pay out (Gwei created for the `fee_recipient`).

The auto-generated report for `process_withdrawals` also documents this explicitly as the intended semantics rather than an edge-case oversight: [5](#0-4) 

```
- **Builder pending**:
    `actual_amount = min(requested_amount, builder.balance)` (builder balance
    can go to zero)
```

The mismatch is between the *committed* withdrawal amount (`state.payload_expected_withdrawals[*].amount`, which the EL must credit unconditionally) and the *actual* balance decrease applied on the CL side (`min(amount, balance)`). This breaks the equality: total Gwei removed from the sender must equal total Gwei credited to the recipient.

### Impact Explanation
If exploitable, this breaks the "Gwei created" invariant: a builder (or a validator/party controlling `builder_pending_withdrawals` insertion via `process_builder_pending_payments` or `apply_parent_execution_payload`) could queue a withdrawal request for far more than their actual balance and have the execution layer credit the full requested amount to an arbitrary `fee_recipient`, while the consensus layer only deducts the builder's much smaller actual balance. This is a Critical-class issue per the rubric (Gwei created / paid to a non-owner) if the requested `amount` value in `BuilderPendingWithdrawal`/bid settlement can be set by the builder or proposer to exceed their real balance and reach `get_builder_withdrawals` unchecked.

### Likelihood Explanation
This requires confirming whether any upstream code path that populates `builder_pending_withdrawals` (`settle_builder_payment`, `process_builder_pending_payments`, `apply_parent_execution_payload`'s direct-append fallback) ever validates `amount <= builder.balance` at insertion time. From what was found, `process_builder_pending_payments` copies `payment.withdrawal` (already containing `amount`) directly into `builder_pending_withdrawals` based only on `weight >= quorum`, with no balance check visible in the retrieved code: [6](#0-5) 

and the `apply_parent_execution_payload`/EIP8205 fallback path appends `amount=parent_bid.value` directly with no balance check either: [7](#0-6) 

I was not able to fully trace whether `settle_builder_payment` (the normal path) enforces `bid.value <= builder.balance` before it ever reaches `builder_pending_payments`/`builder_pending_withdrawals` — that function's body was not retrieved in this session. If it does enforce sufficiency, the shortfall could only arise from balance decreasing *between* bid settlement and withdrawal processing (e.g. via slashing-adjacent operations, other pending withdrawals draining the same builder, or the direct-append fallback for stale parents), which the test suite explicitly exercises and treats as the documented "capped deduction, uncapped payout" behavior — i.e. this is very likely a known/intended-but-under-specified design choice rather than an accidental gap, since it is explicitly unit-tested with matching semantics description ("deduction capped to available balance" while "withdrawal.amount: requested amount").

### Recommendation
Cap the `Withdrawal.amount` produced by `get_builder_withdrawals` to `min(withdrawal.amount, builder.balance)` at construction time (mirroring what `get_pending_partial_withdrawals`/`get_validators_sweep_withdrawals` already do for validators — those compute the *committed* amount as `min(...)` up front, rather than committing the raw request and separately capping the deduction). This ensures the amount instructed to the execution layer for payout always equals the amount actually removed from the builder's balance, preserving the Gwei conservation invariant.

### Proof of Concept
Using the existing spec test as a concrete demonstration of the divergence (not a new PoC, but the exact code path that manifests the bug):
1. Set `state.builders[0].balance = 1_000_000_000` (1 ETH).
2. Insert `BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=X)` into `state.builder_pending_withdrawals`.
3. Call `process_withdrawals(state)`.
4. Result: `state.payload_expected_withdrawals[0].amount == 5_000_000_000` (committed to the EL, to be paid to `X`), while `state.builders[0].balance == 0` (only 1 ETH actually removed) — see the spec test `test_builder_withdrawal_insufficient_balance` at [4](#0-3) , which asserts exactly this outcome as expected. This 4 ETH gap between what is committed for EL payout and what is actually deducted from the builder's stake is unbacked Gwei.
