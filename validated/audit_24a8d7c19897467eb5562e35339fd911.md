### Title
A dust APR=0 withdraw request permanently bricks `stopEpoch` once APR is raised, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. `apr0TotalPrincipal` is incremented on every APR0 withdraw request (`_requestWithdrawApr0`) and is only ever reset inside `prepareStopEpochWithApr0` itself — after the revert check — or partially decremented on default-epoch clearing. A lender can therefore leave a tiny APR0 withdraw receipt open; if the manager later sets a non-zero APR (a normal, honest re-pricing between epochs), every subsequent `stopEpoch` call reverts, and the epoch state machine is deadlocked with all NAV stuck at the borrower.

### Finding Description
The relevant code path:

- `requestWithdraw` (non-closed pool, `unscaledApr == 0`) calls `_requestWithdrawApr0`, which does `apr0TotalPrincipal += _amount` (IdleCreditVault.sol:285-286, 567-577).
- `prepareStopEpochWithApr0`, invoked by the CDO during `stopEpoch`, reverts with `NotAllowed()` when `unscaledApr != 0` while `apr0TotalPrincipal != 0` (IdleCreditVault.sol:505-508).
- `apr0TotalPrincipal = 0` is only assigned at IdleCreditVault.sol:540, which is unreachable once the function starts reverting.
- `_settleApr0`/`_claimFundedWithdrawRequest` move the user's principal to `settledPrincipal` but never decrement `apr0TotalPrincipal`, and settlement cannot run anyway because it requires `epochNumber` to have advanced past the request epoch — which requires a successful `stopEpoch`.

This is the direct analog of CVE-2019-5062: an attacker establishes a minimal "session" (a dust APR0 withdrawal receipt) whose lingering state causes the protocol to deauthenticate/kill service for all legitimate participants. The attacker's cost is one dust withdrawal request (tranche tokens burned, small upfront management fee) during an APR=0 epoch.

### Impact Explanation
Once triggered, `stopEpoch` reverts unconditionally: borrower repayments cannot be booked, `epochNumber` never advances, pending withdraw receipts can never be claimed (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest`), and deposits/NAV remain frozen. The freeze is recoverable only if the manager sets `unscaledApr` back to 0 to let one `stopEpoch` through — i.e., the vault's pricing policy is held hostage by a dust receipt, a temporary/permanent freezing of the entire TVL with a quantifiable loss equal to all funds under management plus accrued interest.

### Likelihood Explanation
Requirements: a vault running an epoch with `unscaledApr == 0` (a supported mode with dedicated accounting), and the manager subsequently changing the APR — a routine honest action. Any KYC-passed tranche holder can open the dust request. No privileged or malicious role is needed; the existing guards (`_onlyIdleCDO`, epoch gating) do not prevent it because the receipt itself is legitimate state.

### Recommendation
In `prepareStopEpochWithApr0`, when `unscaledApr != 0` treat the outstanding `apr0TotalPrincipal` as settled at zero interest (pay principal, skip interest split, clear `apr0TotalPrincipal`) instead of reverting; or allow per-user settlement to decrement `apr0TotalPrincipal` so a later claim removes the blocker. The APR0 bucket should be closed unconditionally at each `stopEpoch` regardless of the current APR.

// Foundry fork test sketch on an APR0-mode IdleCreditVault deployment
function test_Apr0DustRequestBricksStopEpoch() public {
    // epoch N running, unscaledApr == 0
    // 1. attacker (KYC'd AA holder) requests a dust withdraw
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, AAtranche); // creates apr0TotalPrincipal > 0

    // 2. manager honestly re-prices the vault: new epoch terms with APR > 0
    vm.prank(manager);
    strategy.setAprsWithBuffer(5e18, epochDuration, bufferDuration); // unscaledApr != 0

    // 3. every stopEpoch reverts at IdleCreditVault.prepareStopEpochWithApr0
    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch();

    // 4. epochNumber stuck => withdraw claims revert, NAV frozen at borrower
    vm.expectRevert(NotAllowed.selector);
    vm.prank(victim);
    cdoEpoch.withdrawAA(0); // claimWithdrawRequest reverts, epochNumber <= lastWithdrawRequest
}
