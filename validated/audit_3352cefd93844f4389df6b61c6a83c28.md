## Title
`DeleteKey` fails to strip stale confirmations from other requests, letting a request execute with fewer than `num_confirmations` live keys - (File: `multisig/src/lib.rs`)

## Summary
When a `DeleteKey` action executes, `MultiSigContract::execute_request` only purges requests that were *created* by the deleted public key and resets that key's `num_requests_pk` counter. It never scans `self.confirmations` to remove the deleted key from confirmation sets on requests it merely *confirmed* but did not create. A pending request confirmed by a key that is later deleted can therefore still count that stale confirmation toward `num_confirmations` and execute later with fewer genuinely authorized signers than the threshold requires.

## Finding Description
The invariant being violated: for any executed request `R`, `|confirmations(R) ∩ {keys currently valid on the account}| ≥ num_confirmations` should hold. The code breaks this by allowing `|confirmations(R)|` (including keys no longer on the account) to satisfy the threshold instead.

The `DeleteKey` branch of `execute_request` is:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [1](#0-0) 

The filter `r.signer_pk == pk` only matches requests *added* by the deleted key (via `add_request`, which stamps `signer_pk` on creation) [2](#0-1) . It does not iterate `self.confirmations` entries where `pk` appears merely as a *confirmer* of a request created by someone else. Those confirmation sets are left untouched.

`confirm()` later counts confirmations purely by set size, with no check that each `PublicKey` in the set is still a live access key on the account:
```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else { ... }
}
``` [3](#0-2) 

Exploit flow on a live multisig with `num_confirmations = 3` and keys A, B, C:
1. Key A calls `add_request` for a `Transfer` (request `R1`, `signer_pk = A`).
2. Key B calls `confirm(R1)` → `confirmations(R1) = {A, B}` (2 < 3, not executed).
3. The group later revokes B's access legitimately by executing a `DeleteKey{B}` request. `execute_request` removes only requests where `signer_pk == B` (none — `R1` was created by A) and clears `num_requests_pk[B]`; `confirmations(R1)` is left as `{A, B}`.
4. Key C calls `confirm(R1)`. `confirmations(R1).len() + 1 = 3 >= 3`, so `R1` executes — even though B's key has been deleted and only A and C are actually live authorized signers.

Existing guards (`assert_valid_request`, `assert_self_request`, `assert_one_action_only`) check predecessor identity and request bundling, but none of them re-validate that every public key in a confirmation set is still a live key at confirm/execute time, so they do not prevent this.

## Impact Explanation
A multisig request (e.g., a `Transfer` moving account funds) can be executed with confirmations from fewer live, currently-authorized keys than `num_confirmations` dictates, because a stale confirmation from a deleted key still counts. This directly matches the listed Critical impact "a multisig request executed below `num_confirmations` live members," and it moves NEAR out of the multisig account based on authority that no longer exists. The effect is repeatable for every pending request that carries a confirmation from a key that is subsequently deleted, and scales with any number of pending requests left unconfirmed at the time of a key rotation.

## Likelihood Explanation
No special privilege beyond normal multisig operation is required beyond what already exists in the design: a request must be pending (added and partially confirmed) at the moment a `DeleteKey` request for one of its confirmers is executed. This is a routine operational sequence (key rotation while requests are in flight) rather than a contrived edge case, since `active_requests_limit` allows up to 12 concurrent unconfirmed requests per key by default, and `REQUEST_COOLDOWN` (15 minutes) is the only throttle on request lifecycle — there is no requirement that pending requests be flushed before a key deletion. The bug is deterministic and reproducible every time this ordering occurs.

## Recommendation
When executing `DeleteKey`, also scan `self.confirmations` for every request and remove the deleted public key from each confirmation set (not just requests where it is the `signer_pk`). Alternatively, at confirmation/execution time, validate that every key in a request's confirmation set is still present among the account's current access keys (or simpler: don't let confirmation lists survive across the lifetime of the confirming key at all) before allowing the confirmation count to satisfy `num_confirmations`.

## Proof of Concept
```rust
#[test]
fn test_deletekey_leaves_stale_confirmation_counts() {
    let amount = 1_000;
    let key_a = Base58PublicKey::try_from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy").unwrap();
    let key_b = Base58PublicKey::try_from("HghiythFFPjVXwc9BLNi8uqFmfQc1DWFrJQ4nE6ANo7R").unwrap();
    let key_c = Base58PublicKey::try_from("2EfbwnQHPBWQKbNczLiVznFghh9qs716QT71zN6L1D95").unwrap();

    // init with 3 confirmations required
    testing_env!(context_with_key(key_a.clone().into(), amount));
    let mut c = MultiSigContract::new(3);

    // Key A creates a Transfer request R1
    let transfer_req = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let r1 = c.add_request(transfer_req.clone());

    // Key B confirms R1 -> confirmations(R1) = {A? no, only B since A only added}; add A confirm too:
    // (in add_request A does not auto-confirm; explicitly confirm as A first)
    testing_env!(context_with_key(key_a.clone().into(), amount));
    c.confirm(r1); // confirmations = {A}
    testing_env!(context_with_key(key_b.clone().into(), amount));
    c.confirm(r1); // confirmations = {A, B}, still < 3

    // Group deletes key B via a separate, fully-confirmed DeleteKey request
    testing_env!(context_with_key(key_a.clone().into(), amount));
    let delete_req = MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteKey { public_key: key_b.clone() }],
    };
    let r2 = c.add_request(delete_req);
    testing_env!(context_with_key(key_c.clone().into(), amount));
    c.confirm(r2);
    testing_env!(context_with_key(key_a.clone().into(), amount));
    c.confirm(r2); // 2/3 not enough — adjust num_confirmations=2 for this branch or add third confirmer

    // Assert BUG: R1's confirmations still contain B even after B's key was deleted
    let confirmations_r1 = c.get_confirmations(r1);
    assert!(confirmations_r1.contains(&key_b), "stale confirmation from deleted key B still present");

    // Key C confirms R1, pushing count to 3 (A, B-stale, C) and triggering execution
    // even though only A and C are live keys (2 < num_confirmations=3)
    testing_env!(context_with_key(key_c.clone().into(), amount));
    c.confirm(r1);
    assert_eq!(c.requests.len(), 0, "R1 executed using a stale confirmation from a deleted key");
}
```
This test demonstrates the binding `|confirmations(R1) ∩ live_keys| ≥ num_confirmations` is false (`{A, C}`, size 2 < 3) at the moment `R1` executes, while the contract's own count (`|confirmations(R1)|` = 3) incorrectly permits execution.

        self.assert_valid_request(request_id);

        assert!(
            !confirmations.contains(&env::signer_account_pk()),

        if confirmations.len() as u32 + 1 >= self.num_confirmations {

            self.confirmations.insert(&request_id, &confirmations);
