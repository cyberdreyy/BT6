### No vulnerability found for this question.

Analysis: `lending_pool_configure_bank_emode` accounts are validated via Anchor's declarative constraints on `LendingPoolConfigureBankEmode`: `group` requires `has_one = emode_admin` (checked against the signer) and `bank` requires `has_one = group @ MarginfiError::InvalidGroup` (checked against the provided group account) [1](#0-0) . Anchor evaluates these `has_one` constraints during account deserialization/validation, which completes before the instruction handler body executes, so there is no window in which `bank.emode.emode_tag`, `bank.emode.emode_config.entries`, or `bank.emode.timestamp` can be mutated prior to an authorization failure [2](#0-1) .

Duplicate/aliased account metas do not defeat `has_one`, since the constraint compares the stored pubkey field in the account data (`group.emode_admin` or `bank.group`) against the actual key of the account passed at that position — this check is independent of whether other accounts in the transaction happen to be duplicates or aliases. An unprivileged attacker without a signer matching `group.emode_admin`, or a `bank` whose `group` field does not match the supplied `group` account, cannot pass validation regardless of how metas are duplicated or reordered.

There is no sibling-role confusion here: the instruction only references `emode_admin` (not the general group `admin`), and the accounts list contains exactly `group`, `emode_admin`, and `bank` — no delegate/curve/limit/flow role accounts are present that could be substituted via metas to redirect the target bank or admin role. No protected field mutation occurs before or independent of the constraint checks, and no late-binding/rollback issue exists in this handler.

pub fn lending_pool_configure_bank_emode(
    ctx: Context<LendingPoolConfigureBankEmode>,
    emode_tag: u16,
    entries: [EmodeEntry; MAX_EMODE_ENTRIES],
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    let mut sorted_entries = entries;
    sorted_entries.sort_by_key(|e| e.collateral_bank_emode_tag);

    // Prevent footguns from passing data in padding, which could interfere with future values in
    // that assumed-empty space. Yes, we could simply take a struct without padding as input, but
    // having a separate config type has proved to be more of a pain than dealing with padding.
    for entry in sorted_entries.iter_mut() {
        entry.pad0 = [0; 5];
    }

    bank.emode.emode_tag = emode_tag;
    bank.emode.emode_config.entries = sorted_entries;
    bank.emode.timestamp = Clock::get()?.unix_timestamp;

    bank.emode.validate_entries_with_liability_weights(
        &bank.config,
        group.emode_max_init_leverage,
        group.emode_max_maint_leverage,
    )?;
