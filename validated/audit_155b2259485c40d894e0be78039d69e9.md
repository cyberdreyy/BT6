## Analysis Result

### Title
Re-proposal of a block that reached group-signature threshold without local validation wipes `signed_group`/state, defeating the same-tenure conflict guard - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
A signer can accumulate enough peer pre-commits/signatures to cross the 70% weight threshold and mark a block `LocallyAccepted` with `signed_group` set, **without ever having validated that block itself** (`valid` still `None`). If the block is then re-proposed (trivially triggered by a single miner, e.g. on a retry), `should_reevaluate_block` fails to recognize the block as already decided, and `handle_block_proposal` builds a brand-new `BlockInfo` via `BlockInfo::from(block_proposal)`, discarding `signed_group`, `state`, and `vote`, and persists it with `insert_block`, overwriting the previously-recorded consensus progress. This is the direct analog of the reported `auctionStorage` overwrite bug: state that represents an in-flight/committed consensus outcome is clobbered because the code does not check "is there already an active/settled decision here?" before writing a fresh record.

### Finding Description
`BlockInfo::from(BlockProposal)` always resets `vote`, `valid`, `signed_self`, `signed_group`, `approved_time`, and `state` to their initial `Unprocessed` values: [1](#0-0) 

`mark_locally_accepted(group_signed)` only sets `valid`/`approved_time`/`signed_self` when `group_signed == false`; when a signer reaches local acceptance purely because the **group** (peer) signature weight crossed the threshold, only `signed_group` is stamped — `valid` is left untouched: [2](#0-1) 

This `group_signed = true` path is reached in `store_and_process_block_signature` once peer signature weight (not necessarily including our own validation) crosses the threshold: [3](#0-2) 

When the same block is proposed again, `handle_block_proposal` consults `should_reevaluate_block` to decide whether to keep the existing verdict. That function only short-circuits re-evaluation when `determine_response` returns `Some(...)`: [4](#0-3) 

but `determine_response` returns `None` whenever `block_info.valid` is `None`: [5](#0-4) 

Since the block is not `PreCommitted` (it's `LocallyAccepted`) and there is no pending validation, `should_reevaluate_block` falls through and returns `true`, and `handle_block_proposal` proceeds to build a fresh `BlockInfo` and overwrite the DB record: [6](#0-5) [7](#0-6) 

The comment at line 1653 ("Creating a new proposal will overwrite any prior proposal info on the block if it exists, e.g. validity, signed_timestamps, etc.") shows the overwrite is an acknowledged general mechanism, but it is only supposed to fire for blocks whose prior verdict is *not yet decided* — the `group_signed`-only path is a decided state (crossed the 70% threshold) that this guard fails to recognize as decided, exactly mirroring the audited bug where a new state object is written without checking whether the existing slot already holds a live/settled entry.

### Impact Explanation
The tenure-level same-height conflict guard (`get_signed_conflicts`/`get_last_signed_block`/`has_signed_block_in_tenure`) relies on the persisted `state`/`signed_self`/`signed_group` fields to determine whether a block is already "signed" for a tenure, as shown by this state contract: [8](#0-7) 

Once the overwrite resets this block's `state` to `Unprocessed` and clears `signed_group`, the record no longer counts as "signed" for its tenure. A conflicting sibling proposal at the same height that arrives afterward will not see this block as a blocking conflict, so the signer can go on to pre-commit and sign the sibling. Later, if/when the original block is (re)validated and reaches the threshold again, the signer may end up having produced pre-commits/signatures over **two conflicting blocks at the same height**, breaking the one-per-height / conflicting-signature invariant the pre-commit flow (section 5 of `docs/signer-flows.md`) is specifically designed to prevent. This is a Critical-class outcome (a signer contributing a signature toward a conflicting block), or at minimum a High-class loss of the equivocation guard for that block/tenure.

### Likelihood Explanation
This requires only a single miner (or any peer able to gossip the same `BlockProposal` twice) plus normal peer traffic — no majority collusion, no key compromise. Reaching `group_signed=true` while `valid` is `None` needs this signer to be slow/behind on its own validation (busy with another in-flight submission, or a delayed pending validation) while enough other signers already pre-committed/signed — a state directly acknowledged and exercised by existing tests such as `signers_reprocess_late_block_proposals_pre_commits` and the `reproposal_signs_replacement_after_conflict_times_out` family, which already show the codebase re-processing re-proposed blocks after timeouts/retries as normal operation. Re-proposals of the same block are a first-class, expected event in this signer implementation (miner retries on timeout), making the trigger realistically reachable, though it depends on the timing window where `valid` has not yet been set locally.

### Recommendation
`should_reevaluate_block` (and, more fundamentally, `handle_block_proposal`'s decision to construct a fresh `BlockInfo`) must treat `signed_group.is_some()` (and any `is_locally_finalized()`/`has_reached_consensus()` state) as an already-decided outcome, just like `globally_approved_and_responded()` and the `PreCommitted` branch are treated. Concretely:
- In `should_reevaluate_block`, add an explicit early-return for blocks whose `state == BlockState::LocallyAccepted` (whether via `signed_self` or `signed_group`), re-sending the prior acceptance/response instead of falling through to a fresh evaluation.
- In `handle_block_proposal`, before overwriting with `BlockInfo::from(block_proposal)`, check whether an existing record for this hash already carries `signed_group` or `signed_self` and, if so, preserve those fields (or refuse to overwrite) rather than resetting `state` to `Unprocessed`.

### Proof of Concept
1. Signer S receives `BlockProposal` for block X and stores it (`state = Unprocessed`, `valid = None`), but its own validation submission to the node stalls (e.g., `submitted_block_proposal` is occupied by another block, so X is queued via `insert_pending_block_validation`).
2. Peers P1..P5 pre-commit and then sign X; their accumulated signature weight crosses the 70% threshold at S via `store_and_process_block_signature`, which calls `mark_locally_accepted(true)` — `signed_group` is set, `state = LocallyAccepted`, but `valid` stays `None` because S never validated X itself.
3. The miner (or any relaying peer) re-broadcasts the identical `BlockProposal` for X (a routine event on any timeout/retry).
4. `handle_block_proposal` → `should_reevaluate_block` finds `globally_approved_and_responded() == false`, `state != PreCommitted`, `determine_response` returns `None` (since `valid.is_none()`), no pending validation is recorded (or it's stale) → returns `true`.
5. `handle_block_proposal` builds `BlockInfo::from(block_proposal)` and calls `insert_block`, overwriting the DB record: `state` back to `Unprocessed`, `signed_group` cleared.
6. A conflicting sibling block Y at the same height/tenure is proposed; the tenure conflict/`get_signed_conflicts` check no longer finds X as a signed block, so S proceeds to pre-commit/sign Y.
7. X's original validation eventually returns from the node and/or the group threshold is retallied, and S ends up having signed both X and Y at the same height — a conflicting-signature outcome that the pre-commit conflict guard exists to prevent.

    pub fn mark_locally_accepted(&mut self, group_signed: bool) -> Result<(), String> {
        if group_signed {
            self.signed_group.get_or_insert(get_epoch_time_secs());
        } else {
            self.valid = Some(true);
            self.approved_time.get_or_insert(get_epoch_time_secs());
            self.signed_self.get_or_insert(get_epoch_time_secs());
        }
        self.move_to(BlockState::LocallyAccepted)

        block_info.mark_locally_accepted(false).unwrap();

        block_info.block.header.consensus_hash = consensus_hash_2.clone();

        block_info.signed_group = None;

    /// Determine this signers response to a proposed block
    /// Returns a BlockResponse if we have already validated the block
    /// Returns None otherwise
    fn determine_response(&mut self, block_info: &BlockInfo) -> Option<BlockResponse> {
        // We will only have the valid field set if we have already validated this block
        // against our stacks-node/local state.
        let valid = block_info.valid?;
        let response = if valid {
            debug!("{self}: Accepting block {}", block_info.block.block_id());
            self.create_block_acceptance(&block_info.block).into()
        } else {
            debug!("{self}: Rejecting block {}", block_info.block.block_id());
            self.create_block_rejection(RejectReason::RejectedInPriorRound, &block_info.block)
                .into()
        };
        Some(response)
    }

    /// Returns true if the block should be re-evaluated, false if it should be ignored.
    fn should_reevaluate_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &BlockInfo,
        block_proposal: &BlockProposal,
    ) -> bool {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        if block_info.globally_approved_and_responded() {
            info!("{self}: received a block proposal for a globally accepted block to which we have already responded. Ignoring.";
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "block_height" => block_info.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_info.block.header.consensus_hash,
                "timestamp" => block_info.block.header.timestamp,
                "signed_group" => block_info.signed_group,
                "signed_self" => block_info.signed_self,
                "valid" => ?block_info.valid
            );
            return false;
        }
        if !should_reevaluate_reject_reason(block_info) {
            if block_info.state == BlockState::PreCommitted {
                // We validated this block but haven't signed it. Signing requires the
                // pre-commit threshold and the conflict checks in `handle_block_pre_commit`.
                // Re-broadcast our pre-commit and re-run that evaluation instead of
                // responding with a signature directly, so a re-proposed block can't
                // bypass those checks.
                info!(
                    "{self}: received a block proposal for a block we have pre-committed to but not signed. Re-evaluating the pre-commit.";
                    "signer_signature_hash" => %signer_signature_hash,
                    "block_id" => %block_info.block.block_id(),
                    "block_height" => block_info.block.header.chain_length,
                    "burn_height" => block_proposal.burn_height,
                    "consensus_hash" => %block_info.block.header.consensus_hash
                );
                self.send_block_pre_commit(signer_signature_hash.clone());
                let address = self.stacks_address.clone();
                self.handle_block_pre_commit(
                    stacks_client,
                    sortition_state,
                    &address,
                    &signer_signature_hash,
                );
                return false;
            }
            if let Some(block_response) = self.determine_response(block_info) {
                self.send_block_response(&block_info.block, block_response);
                return false;
            } else {
                let is_pending = self
                    .signer_db
                    .has_pending_block_validation(&signer_signature_hash)
                    .unwrap_or_else(|e| {
                        warn!("{self}: Failed to load pending block validations: {e:?}");
                        false
                    });
                if is_pending {
                    debug!(
                        "{self}: received a block proposal for a block for which we is already pending validation. Do nothing.";
                        "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                        "block_id" => %block_info.block.block_id()
                    );
                    return false;
                } else {
                    info!(
                        "{self}: received a block proposal for this block before, but we do not have a pending validation for it.";
                        "reject_reason" => ?block_info.reject_reason,
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %block_info.block.block_id(),
                        "block_height" => block_info.block.header.chain_length,
                        "burn_height" => block_proposal.burn_height,
                        "consensus_hash" => %block_info.block.header.consensus_hash

                }

                "block_id" => %block_proposal.block.block_id(),

                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_proposal.block.header.consensus_hash
            );
        }
