### Title
Confirmations from deleted multisig keys still count toward execution quorum - ([File: multisig/src/lib.rs])

### Summary
In `MultiSigContract`, deleting an access key (`DeleteKey` action) only removes requests that were *originated* by that key, but does not scrub that key's public key from the `confirmations` set of *other* pending requests it previously confirmed. Because `confirm()` never re-validates that stored confirming keys are still live members, a request can reach `num_confirmations` and execute using a mix of confirmations from a currently-revoked key and live keys, breaking the intended binding "confirmations counted == confirmations from currently authorized members."

### Finding Description
`add_request` stores a new `MultiSigRequestWithSigner { signer_pk, ... }` and an empty `confirmations: HashSet<PublicKey>` entry keyed by `request_id`. [1](#0-0) 

`confirm()` inserts `env::signer_account_pk()` into the `confirmations` set for the request and executes the request once the set size reaches `num_confirmations`: [2](#0-1) 

When a `DeleteKey` action executes, the contract only purges requests whose *original signer* (`r.signer_pk`) equals the deleted key. It never scans other requests' `confirmations` sets to remove the deleted key from them:
```
MultiSigRequestAction::DeleteKey { public_key } => {
    ...
    let request_ids: Vec<u32> = self.requests.iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [3](#0-2) 

This is the same root-cause pattern as the reported `emergencyUpdatequestPeriod()` issue: mutable state that grants "credit" toward a threshold/claim (there: bitmap bit tied to merkle index; here: a `PublicKey` entry tied to quorum) is not invalidated/reset when the underlying authorization set changes (there: merkle tree re-issued; here: key deleted). The stale entry keeps counting toward the binding it was originally tied to, even though the real-world authorization has changed.

The equality that should hold is:
```
confirmations_recorded(request_id) ⊆ currently_authorized_keys
```
After a `DeleteKey` action removes a member key that had previously confirmed (but not created) some other pending request `R`, this invariant breaks: `R`'s `confirmations` set still contains the removed key, while the account's actual live key set no longer does.

### Impact Explanation
This is a multisig quorum-bypass: a request can execute with fewer than `num_confirmations` *currently valid* signatures. For example, with `num_confirmations = 2`:
1. Key `K1` calls `add_request(R)` (no auto-confirm) → `confirmations(R) = {}`.
2. Key `K2` calls `confirm(R)` → `confirmations(R) = {K2}` (1 < 2, not yet executed).
3. Some other quorum of live keys executes a `DeleteKey { public_key: K2 }` request. Because `R`'s `signer_pk == K1 ≠ K2`, `R` and its stale `confirmations = {K2}` are **not** cleared. `K2` is now removed from the account and has no further access.
4. Key `K3` (a currently live key) calls `confirm(R)`. `confirmations(R).len() + 1 = 2 >= num_confirmations`, so `R` executes — a `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. — using confirmation weight from a key that had already been revoked at execution time.

This falls under the "Critical" impact bucket described in scope: a multisig request executed below the *effective* threshold of live-member approval, potentially moving NEAR out of the account without the actually-required number of currently-authorized signers agreeing.

### Likelihood Explanation
This requires no attacker privilege escalation beyond normal multisig usage: any key with legitimate access can create/confirm requests, and key rotation via `DeleteKey` is a normal operational action supported by the contract itself (e.g., an employee offboarding scenario). No foundation/owner/redeploy assumption is needed — it is triggered purely through the documented `add_request` → `confirm` → `DeleteKey` → `confirm` sequence, all unprivileged-relative-to-each-other multisig member actions. The scenario is realistic whenever a pending, unconfirmed/partially-confirmed request exists at the time a member key is rotated out, which is a routine occurrence for any actively used multisig wallet.

### Recommendation
- When executing `DeleteKey` (or `DeleteMember` in `multisig2`), iterate over **all** pending requests' `confirmations` sets (not just those the key originated) and remove the deleted key/member from each, re-checking whether removal now under-fills quorum.
- Alternatively, validate at `confirm()`-execution time (the moment the threshold is reached) that every public key present in `confirmations` still corresponds to a currently active access key/member on the account before allowing `execute_request` to proceed.
- Consider recomputing effective confirmation count as `confirmations ∩ live_keys` rather than trusting the persisted set unconditionally.

### Proof of Concept
1. Deploy `MultiSigContract::new(num_confirmations = 2)` with keys `K1, K2, K3` as full-access keys on the account.
2. As `K1`: `add_request(R = Transfer{ amount })` → `confirmations(R) = {}`.
3. As `K2`: `confirm(R)` → `confirmations(R) = {K2}`, request not yet executed (1 < 2).
4. As `K1` + `K3` (2 confirmations), create and confirm a separate request `D = DeleteKey{ public_key: K2 }` until it executes, removing `K2`'s on-chain access key. Because `D.signer_pk` (say `K1`) `≠ K2`, this does not touch `R`'s stored confirmations (`{K2}` persists) since the filter `r.signer_pk == pk` only matches `D` itself, not `R`. [3](#0-2) 
5. As `K3` (still live): `confirm(R)`. Since `confirmations(R).len() (=1) + 1 >= num_confirmations (2)`, the contract calls `remove_request` and `execute_request(R)`, transferring funds — despite `K2` no longer being an authorized key at the moment of execution. [2](#0-1)

    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        assert_eq!(
            env::current_account_id(),
            env::predecessor_account_id(),
            "Predecessor account must much current account"
        );
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&env::signer_account_pk())
            .unwrap_or(0)
            + 1;
        assert!(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some."
        );
        self.num_requests_pk
            .insert(&env::signer_account_pk(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            signer_pk: env::signer_account_pk(),
            added_timestamp: env::block_timestamp(),
            request: request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
