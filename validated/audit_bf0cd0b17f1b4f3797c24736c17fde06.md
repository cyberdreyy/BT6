### Title
RunRole-gated `/v2/execute_capability` endpoint permits execution of any registered capability with attacker-forged workflow metadata, bypassing DON/quorum authorization checks - ([File: core/web/capability_controller.go])

### Summary
`CapabilityController.ExecuteCapability`, mounted at `POST /v2/execute_capability` and guarded only by `auth.RequiresRunRole` when `build.IsDev()` is true, lets any run-role-authenticated caller invoke **any** capability registered in the node's `CapabilitiesRegistry` by name, with a fully attacker-controlled `CapabilityRequest` (including `Metadata.WorkflowID`/`WorkflowExecutionID`). Unlike the DON-to-DON execution path, this HTTP path performs no binding/quorum/attestation checks before calling `capability.Execute`.

### Finding Description
The route is registered as: [1](#0-0) 

`RequiresRunRole` only checks that the user's role is not `view`; `run` and above pass through: [2](#0-1) 

Notably, `run` role is not exclusively an interactive-admin-granted role: `AuthenticateExternalInitiator` automatically assigns `UserRoleRun` to any valid external-initiator credential, i.e. an external-initiator token holder — a fairly low-trust, job-trigger-only credential — is treated as sufficient here: [3](#0-2) 

The handler itself looks up an arbitrary capability by attacker-supplied `CapabilityName`, unmarshals an attacker-supplied `CapabilityRequest` (including `Metadata.WorkflowID`, `WorkflowExecutionID`, `Config`, `Inputs`), and executes it directly with no ownership/ACL/binding checks: [4](#0-3) 

Contrast this with the legitimate DON-to-DON capability execution path (`core/capabilities/remote/executable/request/server_request.go`), which enforces that the caller's DON ID matches `Metadata.WorkflowDonID` via `workflowDONBindingGate` before executing: [5](#0-4) 

The web endpoint has none of these bindings — the `WorkflowID`/`WorkflowExecutionID`/`WorkflowDonID` fields in the request metadata are taken at face value from the HTTP caller, meaning a run-role caller can impersonate any workflow when invoking a capability, and can target capabilities whose real-world effects (e.g., "write"/"target" capabilities that submit on-chain transactions, or capabilities that read/handle secrets) are far beyond what a "run" role is intended to authorize elsewhere in the router (compare `/v2/replay_from_block`, `/v2/find_lca`, `/v2/lp_skip_to_block`, which are read/replay-only operations, not arbitrary-capability invocation).

### Impact Explanation
A run-role credential (including an auto-granted external-initiator credential) can trigger execution of any capability registered in the node's registry, with forged workflow identity metadata and attacker-controlled `Inputs`/`Config`. Depending on which capabilities are registered (e.g., write/target capabilities that move funds or submit transactions, or capabilities that access secrets/vault data), this constitutes unauthorized state-mutating action performed under a "run"-only credential — a role/authorization-scope violation matching Chainlink's "unauthorized job run or fund movement" / role-bypass impact class. This is gated behind `build.IsDev()`, whose default (unless explicitly overridden via a production build flag) evaluates true, so default/staging builds are exposed.

### Likelihood Explanation
Preconditions: (1) node built without the explicit non-dev/production build flag so `build.IsDev()` is true (the default), (2) attacker holds any credential with role ≥ `run` (a run-role API token, or an external-initiator credential which is automatically treated as run-role), (3) at least one capability with state-mutating or sensitive effects is registered. Given `run` is the second-lowest role and external-initiator tokens are trivially run-role, and the endpoint is enabled by default in non-production-flagged builds, this is straightforward to reproduce with only network access and a low-privilege token.

### Recommendation
- Require `auth.RequiresEditRole` (or `RequiresAdminRole`) instead of `RequiresRunRole` for `/v2/execute_capability`, since it allows invocation of arbitrary capabilities with side effects beyond job-triggering.
- Validate/bind `CapabilityRequest.Metadata` (WorkflowID/WorkflowExecutionID/WorkflowDonID) against the authenticated caller's actual authorization scope instead of trusting attacker-supplied values, mirroring the `workflowDONBindingGate` check used in the DON-to-DON path.
- Maintain an explicit allowlist of capabilities safe for external/manual invocation via this debug endpoint, rather than allowing any registered capability by name.
- Reconsider defaulting `build.IsDev()` to true; invert so production-safety is the default and dev-mode must be explicitly opted into via build tags/ldflags, reducing accidental exposure in default/staging builds.

### Proof of Concept
Go handler-level integration test (extending `core/web/capability_controller_test.go` patterns):
1. Build a `gin.Engine` with `/v2/execute_capability` wired as in `router.go`, using `auth.Authenticate` + `auth.RequiresRunRole(controller.ExecuteCapability)`.
2. Seed context/session with a `clsessions.User{Role: clsessions.UserRoleRun}` (simulating a run-role token or an external-initiator-derived session).
3. Register a mock `ExecutableCapability` in the app's `CapabilitiesRegistry` that records the `Metadata.WorkflowID` it received and simulates a state-mutating side effect (e.g., a counter representing "funds moved" or "secret accessed").
4. POST to `/v2/execute_capability` with `CapabilityRequestOuter{CapabilityName: "mock-write-cap", CapabilityRequest: <marshaled CapabilityRequest with Metadata.WorkflowID = "victim-workflow-id">}`.
5. Assert: HTTP 200, `capabilityResponse` returned, and the mock capability recorded execution under the forged `WorkflowID` — proving a run-role caller executed an arbitrary capability while impersonating an unrelated workflow, with no binding/ownership check rejecting the request (unlike `executeCapabilityRequest` in `server_request.go`).

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```

```go
func (cc *CapabilityController) ExecuteCapability(c *gin.Context) {
	body := c.Request.Body
	if body == nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("missing request body"))
		return
	}

	capabilityRegistry := cc.App.GetCapabilitiesRegistry()
	if capabilityRegistry == nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("capability registry not initialized"))
		return
	}
	var capabilityRequestOuter CapabilityRequestOuter
	if err := c.BindJSON(&capabilityRequestOuter); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	capability, err := capabilityRegistry.GetExecutable(c.Request.Context(), capabilityRequestOuter.CapabilityName)
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	capabilityRequest, err := pb.UnmarshalCapabilityRequest(capabilityRequestOuter.CapabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	resp, err := capability.Execute(c.Request.Context(), capabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
```
