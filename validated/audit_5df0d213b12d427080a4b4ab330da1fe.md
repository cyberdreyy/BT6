## Finding

The reported bug class (shared, capacity-bounded resource that an unprivileged actor can exhaust/collide to deny or hijack service for other users) has a genuine analog in the Chainlink gateway's legacy WebAPI capability handler.

### Title
Missing request-ID uniqueness check and rate limiting in the legacy WebAPI gateway handler allows callback-slot exhaustion and cross-user response hijacking - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`handler.HandleLegacyUserMessage` stores each incoming (client-controlled) request under `h.savedCallbacks[msg.Body.MessageId]` with **no check that the ID is not already in use**, and with **no rate limiting** on the ingress path itself (only on the DON→gateway egress path). [1](#0-0)  The code even contains an explicit TODO acknowledging this: `// TODO: apply allowlist and rate-limiting here`. [2](#0-1) 

### Finding Description
`gateway.ProcessRequest` routes any client JSON-RPC request that carries a `DonId` to `HandleLegacyUserMessage(ctx, msg, callback)`, where `msg.Body.MessageId` is derived from client-supplied fields (e.g. the JSON-RPC `ID`, as shown in `dummyHandler.HandleJSONRPCUserMessage`, which sets `msg.Body.MessageId = jsonRequest.ID` before delegating to the same legacy path). [3](#0-2) [4](#0-3) 

Inside `HandleLegacyUserMessage`, the handler unconditionally overwrites the map entry:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [5](#0-4) 

There is no uniqueness/conflict check comparable to what exists in the newer confidential-relay and HTTP-trigger handlers. The `confidentialrelay` handler explicitly rejects duplicate IDs with `"request ID already exists"`, [6](#0-5)  and the v2 HTTP trigger handler's `setupCallback` returns `jsonrpc.ErrConflict` when a `requestID` is already in flight. [7](#0-6)  The legacy `handler.go` path lacks this safeguard.

When a node later responds, `handleWebAPITriggerMessage` looks the response up purely by `msg.Body.MessageId` and delivers it to whatever callback is currently stored there:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
``` [8](#0-7) 

Because there is no per-user/per-session binding of the ID and no ownership check, an unprivileged client that submits a request using the same `MessageId` as a concurrently pending, unrelated legitimate request overwrites that legitimate request's callback entry. Whichever response arrives first for that ID is delivered to whichever caller's callback is currently stored — either denying the original user their expected response (their callback silently disappears, eventually timing out) or, depending on timing, delivering a mismatched response to the wrong caller (`cross-user response confusion`).

Separately, the `savedCallbacks` map has a bounded capacity (`defaultMaxSavedCallbacks = 20000`) enforced by periodic `pruneCallbacks()`, which evicts the oldest entries once the map exceeds this size. [9](#0-8) [10](#0-9)  Since there is no rate limiting on the ingress side (only `nodeRateLimiter`, which throttles DON→gateway egress messages, not client requests), an unprivileged client can flood unique `MessageId`s to fill this shared, capacity-bounded resource, causing eviction of other users' pending callbacks — directly analogous to the reported PSM rate-limit exhaustion DoS, where a single actor exhausts a shared, capacity-bounded resource and denies service to everyone else.

### Impact Explanation
- An unprivileged client can deny other users their expected trigger response (their saved callback is silently overwritten or evicted, causing their request to eventually time out).
- Under specific timing, a client-controlled ID collision can cause the wrong caller's callback to receive another user's node response (`cross-user response confusion`).
- Because the handler entry point performs no rate limiting on this ingress path (per the code's own acknowledged TODO), a single client can also flood the bounded `savedCallbacks` map to force eviction of unrelated in-flight requests.

### Likelihood Explanation
The vulnerable path (`HandleLegacyUserMessage`) is reachable directly by any client capable of sending a JSON-RPC request to the gateway's `ProcessRequest` entry point with a `DonId` set, requiring no special privilege. [3](#0-2)  No authentication beyond normal gateway message validation (`msg.Validate()`) is required to control the `MessageId`, and the code contains no defense against ID reuse or flooding, unlike parallel handlers in the same codebase (`confidentialrelay`, v2 `http_trigger_handler`) that already implement this exact protection.

### Recommendation
- Add a conflict check in `HandleLegacyUserMessage` (mirroring `confidentialrelay`'s "request ID already exists" check and `http_trigger_handler.setupCallback`'s `ErrConflict` handling) before inserting into `h.savedCallbacks`.
- Apply the rate limiting/allowlist noted in the existing TODO comment to the ingress (client) side of this handler, not just the DON egress side.
- Consider binding saved callback ownership to session/connection identity so a colliding ID from a different caller cannot silently replace another user's pending callback.

### Proof of Concept
1. User A sends a legacy request with `MessageId = "X"` to a given `DonId`; the gateway stores A's callback under `savedCallbacks["X"]` and forwards the request to DON nodes.
2. Before A's response arrives, attacker sends their own legacy request also using `MessageId = "X"` to the same `DonId`. This overwrites `savedCallbacks["X"]` with the attacker's callback (no conflict check exists in `HandleLegacyUserMessage`).
3. When a DON node responds with `MessageId = "X"` (in response to either A's or attacker's forwarded request), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback, and delivers the response there — user A's original request is starved and eventually times out, or, depending on which request the DON is actually answering, response data intended for A is delivered to the attacker.
4. Repeating step 2 rapidly with many distinct IDs (no rate limit exists on this path) also allows filling `savedCallbacks` to its `MaxSavedCallbacks` cap, triggering `pruneCallbacks()` to evict legitimate in-flight entries from unrelated users.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
```

func (d *dummyHandler) HandleJSONRPCUserMessage(ctx context.Context, jsonRequest jsonrpc.Request[json.RawMessage], callback Callback) error {
	var msg api.Message
	if jsonRequest.Params != nil {
		if err := json.Unmarshal(*jsonRequest.Params, &msg); err != nil {
			return err
		}
	}
	msg.Body.MessageId = jsonRequest.ID
	if msg.Body.Method == "" {
		msg.Body.Method = jsonRequest.Method
	}
	if msg.Body.DonId == "" {
		msg.Body.DonId = d.donConfig.DonId
	}
	return d.HandleLegacyUserMessage(ctx, &msg, callback)
```
