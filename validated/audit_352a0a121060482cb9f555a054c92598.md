### Title
Stale acceptance signature is not invalidated when a signer later rejects the same block, allowing double-counted weight across the accept/reject tallies - ([File: stacks-signer/src/signerdb.rs], [File: stacks-signer/src/v0/signer.rs])

### Summary
The `express-mock-middleware` advisory is about an exported function letting caller-controlled path/attribute data mutate object state it shouldn't (dynamically-determined attribute writes with no reciprocal guard). The reachable analog here is an asymmetric cross-table mutation in the signer's vote-tallying logic: the "accept a block" code path explicitly cleans up ("mutates") the rejection table when a signer's weight moves to the accept side, but the "reject a block" code path has no symmetric cleanup of the signature table. This lets one signer's weight be counted on both sides of the accept/reject equality for the same block at the same time.

### Finding Description
When a signer's acceptance signature for a block is recorded, `SignerDb::add_block_signature` first removes any earlier stored rejection row for that `(signer_signature_hash, signer_addr)` pair before inserting the new signature: [1](#0-0) 

This is a deliberate design: accepting after having rejected must retract the earlier rejection so the reject-weight tally in `store_and_process_block_rejection` doesn't still count that signer.

The reverse direction, however, has no equivalent cleanup. `handle_block_rejection` → `store_and_process_block_rejection` simply calls `add_block_rejection_signer_addr` to record the rejection and then recomputes the reject tally; it never touches the `block_signatures` table to retract a signer's earlier acceptance signature for the same `signer_signature_hash`: [2](#0-1) 

Meanwhile, the accept-side tally in `store_and_process_block_signature` computes `total_signature_weight` purely from whatever rows remain in `block_signatures` via `get_block_signatures`/`addrs_to_sigs`, with no cross-check against `block_rejection_signer_addrs`: [3](#0-2) 

Concretely: if a signer first observes/produces an acceptance signature for a block (stored in `block_signatures`), and then later — after re-evaluation, a reorg attempt, or a crafted/duplicated gossip message — sends a rejection for the *same* `signer_signature_hash`, `store_and_process_block_rejection` will add that signer's weight to the reject tally while the earlier acceptance signature (and its weight) is still present and still counted by `store_and_process_block_signature`'s tally the next time an acceptance message triggers recomputation. Both `total_signature_weight` (accept side) and `total_reject_weight` (reject side) can therefore include the same signer's weight simultaneously, for the same block, breaking the implicit invariant that the accept-weight and reject-weight partitions are mutually exclusive within the "70% accept / 30%+1 reject" threshold arithmetic (`NakamotoBlockHeader::compute_voting_weight_threshold`, referenced at both tally sites).

### Impact Explanation
This is an aggregated-weight-vs-verified-accepts equality break: the signer's own bookkeeping allows one signer's weight to be double-attributed across the accept and reject tallies for a single block. In the presence of gossip replay or a re-proposal/re-evaluation cycle (both of which are normal, in-scope signer behaviors described in `docs/signer-flows.md`'s `should_reevaluate_block`/`should_reevaluate_reject_reason` flow), this asymmetry can let a stale, already-superseded acceptance signature continue to count toward the 70% signing threshold used to broadcast a block, even though the signer who produced it has since broadcast a rejection for that exact hash. This does not itself require a signature forgery or another signer's key — it only requires the local one-slot signer's own vote to flip on a message it already saw once, which is fully within the trust model of "what a one-slot miner/signer or gossip can trigger."

### Likelihood Explanation
Reaching this state does not require a majority of signers or any cryptographic break — only that a single signer transitions from accept → reject for the same block hash after its acceptance signature has already been persisted, which can happen via normal re-evaluation paths (`should_reevaluate_block`) or duplicate/late-arriving StackerDB chunks. The reject-side cleanup gap is a straightforward code-path omission (compare directly to the explicit, commented cleanup that exists for the opposite direction), making this a structural rather than probabilistic issue.

### Recommendation
Make cleanup symmetric: when `store_and_process_block_rejection`/`add_block_rejection_signer_addr` records a new rejection for a `(signer_signature_hash, signer_addr)`, also delete (or otherwise invalidate) any existing row in `block_signatures` for that same signer and hash before recomputing `total_reject_weight`, mirroring the `DELETE FROM block_rejection_signer_addrs ...` step already present in `add_block_signature`. Additionally, `total_signature_weight` and `total_reject_weight` computations should explicitly exclude any signer address present in the *other* table for the same block, rather than trusting that inserts/deletes on both tables stay in sync.

### Proof of Concept
1. Signer S produces (or receives and stores via `add_block_signature`) an acceptance signature for block B (`signer_signature_hash = H`). `block_signatures` now has a row for `(H, S)`.
2. Before B reaches either threshold, S (or a replayed/duplicated message purportedly from S that passes `is_valid_signer`/pubkey-recovery checks in `handle_block_rejection`) sends a `BlockRejection` for `H`.
3. `store_and_process_block_rejection` calls `add_block_rejection_signer_addr(H, S, reason)`, adding `(H, S)` to `block_rejection_signer_addrs`. It does not delete the row `(H, S)` from `block_signatures`.
4. A subsequent acceptance signature from a *different* signer arrives, triggering `store_and_process_block_signature` to recompute `total_signature_weight` via `get_block_signatures(H)`; S's stale signature row is still included, contributing S's weight toward the 70% accept threshold.
5. Simultaneously, `total_reject_weight` computed from `get_block_rejection_signer_addrs(H)` also includes S's weight toward the reject threshold.
6. S's weight is now counted on both sides of the tally for block B, letting the two thresholds be reached with fewer genuinely-distinct-and-still-committed signers than the protocol assumes.

Note: the body of `add_block_rejection_signer_addr` itself was not directly inspected in this pass (tool budget exhausted before reaching its definition in `signerdb.rs`); the asymmetry is inferred from (a) the explicit, commented-only-on-one-side cleanup logic in `add_block_signature`, and (b) the absence of any call to delete/invalidate `block_signatures` rows in the `store_and_process_block_rejection` call path shown above. If `add_block_rejection_signer_addr` is confirmed to perform equivalent cleanup internally, this finding would need to be retracted; verifying that function's full body is the immediate next step for confirming or disproving this analog.
