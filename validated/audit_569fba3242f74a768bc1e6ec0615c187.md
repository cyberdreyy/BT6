### Title
Performance-fee changes retroactively reduce already-accrued epoch yield - ([File: `contracts/IdleCDOCreditVault.sol`])

### Summary
`setFeeParams` updates the global performance `fee` without checkpointing the gain accrued under the previous fee configuration. The next accounting checkpoint applies the newly configured fee to the entire NAV increase since the previous interaction, including epoch yield that economically accrued before the fee change.

### Finding Description
`setFeeParams` checkpoints only the time-based management fee through `_accrueManagementFee`, then immediately replaces `fee`, `feeSplit`, and `managementFee`. [1](#0-0) 

Performance-fee accounting is instead deferred until `_updateAccounting`, where the complete gain between `lastNAVAA + lastNAVBB` and the current NAV is charged using the newly stored `fee`. [2](#0-1) 

`_virtualPriceAux` likewise subtracts the current `fee` from the entire `totalGain`, with no fee-rate checkpoint or per-period breakdown. [3](#0-2) 

For an active epoch, `startEpoch` precomputes `expectedEpochInterest`, while the borrower's interest payment is not represented in CDO NAV until `stopEpoch` pulls the funds. [4](#0-3) 

`stopEpoch` pulls the expected interest and only afterwards calls `_updateAccounting`, so a fee changed at any point during the epoch is applied to the full epoch interest payment. [5](#0-4) 

The resulting `unclaimedFees` are then paid to `feeReceiver` and the owner, while the remaining interest is distributed to tranche holders. [6](#0-5) 

### Impact Explanation
AA and BB holders lose a portion of yield that accrued under the old fee schedule. For example, changing `fee` from 0% to 10% immediately before `stopEpoch` redirects 10% of the entire epoch's expected interest to the configured fee recipients rather than charging 10% only on post-change gains.

The loss is directly quantifiable as:

```solidity
retroactiveFeeLoss = expectedEpochInterest * newFee / FULL_ALLOC;
```

The issue affects realized NAV and eventual withdrawal value, not merely an off-chain estimate. Lenders cannot independently checkpoint accounting because `updateAccounting` is restricted to the owner or guardian, and normal deposits are paused while an epoch is running. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
This requires only a routine owner fee update while a yield-bearing epoch is active or while other unrealized gains remain uncheckpointed. No malicious privileged actor or unprivileged attacker transaction is required; the accounting design itself applies the updated rate to pre-change yield.

The likelihood is highest for long epochs because the accrued-but-uncrystallized amount grows until `stopEpoch`, and the vulnerable window is the complete epoch duration. Mid-epoch deposits are disabled by default, further reducing the chance that accounting is checkpointed before a parameter change. [9](#0-8) 

### Recommendation
Snapshot the performance-fee rate when an epoch starts and use that snapshotted rate when accounting for that epoch's interest. Apply a newly configured `fee` only to gains realized after the configuration change.

For non-epoch realized gains, `setFeeParams` should checkpoint the existing NAV gain under the old fee before assigning the new value. If fixed-rate epoch interest remains off-book until settlement, merely calling `_forceUpdateAccounting` inside `setFeeParams` is insufficient because the unpaid borrower interest is not yet included in `getContractValue`; an `epochFee` value selected at `startEpoch` is therefore the more complete fix.

### Proof of Concept
Add this test to `test/foundry/IdleCreditVault.t.sol`; it uses the existing mainnet fork fixture at block `18678289` and the existing `manager`, `owner`, `TL_MULTISIG`, `underlying`, and `_toggleEpoch` helpers:

```solidity
function testFeeChangeRetroactivelyTaxesEpochYield() external {
    uint256 amount = 10_000 * ONE_SCALE;

    idleCDO.depositAA(amount / 2);
    idleCDO.depositBB(amount / 2);

    // Start a normal epoch under the existing 0% performance fee.
    _toggleEpoch(true, 0, 0);

    uint256 expectedInterest = cdoEpoch.expectedEpochInterest();
    assertGt(expectedInterest, 0);

    deal(defaultUnderlying, borrower, expectedInterest);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 snapshotId = vm.snapshot();

    // Baseline: settle the epoch without changing the fee.
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    uint256 navWithoutChange = cdoEpoch.lastNAVAA() + cdoEpoch.lastNAVBB();
    uint256 receiverWithoutChange = underlying.balanceOf(TL_MULTISIG);

    vm.revertTo(snapshotId);

    // Change the performance fee only after the epoch yield has accrued.
    vm.prank(owner);
    cdoEpoch.setFeeParams(
        TL_MULTISIG,
        10_000, // 10%
        FULL_ALLOC,
        cdoEpoch.managementFee()
    );

    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    uint256 navWithChange = cdoEpoch.lastNAVAA() + cdoEpoch.lastNAVBB();
    uint256 receiverWithChange = underlying.balanceOf(TL_MULTISIG);
    uint256 expectedRetroactiveFee = expectedInterest * 10_000 / FULL_ALLOC;

    // The full epoch yield is charged at the new 10% rate.
    assertApproxEqAbs(
        navWithoutChange - navWithChange,
        expectedRetroactiveFee,
        2,
        "new fee should have taxed only post-change yield"
    );

    assertApproxEqAbs(
        receiverWithChange - receiverWithoutChange,
        expectedRetroactiveFee,
        2,
        "fee recipients received yield accrued before the fee update"
    );

    assertLt(navWithChange, navWithoutChange);
}
```

Run with:

```bash
forge test --match-test testFeeChangeRetroactivelyTaxesEpochYield -vvv
```
