### Title
User/email enumeration via response message and timing discrepancy in login flow - ([File: core/sessions/localauth/orm.go])

### Summary
`orm.CreateSession` (`core/sessions/localauth/orm.go:144-162`) returns a distinct, low-cost error immediately when `FindUser` fails to locate an email, but performs an expensive bcrypt comparison (`utils.CheckPasswordHash`) and returns a different message ("Invalid password") when the email exists. This creates an observable timing and message discrepancy that lets an unauthenticated caller determine whether an email is registered. MFA status, however, is only revealed after a correct password is supplied, so it is not disclosed pre-auth as the question hypothesizes.

### Finding Description
`SessionsController.Create` (`core/web/sessions_controller.go:29-68`) binds the POST `/sessions` body and calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`, forwarding any returned error verbatim as the HTTP 401 body via `jsonAPIError`.

Inside `orm.CreateSession` (`core/sessions/localauth/orm.go:144-162`):
1. `o.FindUser(ctx, sr.Email)` runs a single indexed lookup (`SELECT * FROM users WHERE lower(email)=lower($1)`). For a non-existent email this fails fast and the function returns immediately with the raw DB error (e.g. `sql: no rows in result set`) — no bcrypt work is performed [1](#0-0) .
2. For an existing email, execution proceeds to `constantTimeEmailCompare` (line 154, effectively always true here since the SQL already matched case-insensitively) and then `utils.CheckPasswordHash(sr.Password, ...)` (line 159), which performs a bcrypt hash comparison — a deliberately slow operation — before returning `"Invalid password"` on mismatch [2](#0-1) .

Because bcrypt is only invoked on the "email exists" path, response latency and the returned error string both differ measurably between a random/unregistered email and a registered one with a wrong password, letting an attacker enumerate valid accounts by observing the `/sessions` POST response.

The MFA-challenge branch (`GetUserWebAuthn` at line 165, challenge JSON at lines 184-199) is only reached *after* a correct password has already been verified at line 159 [3](#0-2) . Consequently, MFA-enabled status is **not** disclosed to an attacker who does not already know the correct password — a wrong-password attempt against an MFA account returns the identical `"Invalid password"` message/timing as a wrong-password attempt against a non-MFA account. The pre-auth call to `GetUserWebAuthn` in `SessionsController.Create` (line 42) also does not leak this, since its result only conditionally sets internal fields and is never echoed to the client before authentication succeeds [4](#0-3) . So the "MFA status disclosure pre-auth" portion of the hypothesis does not hold.

### Impact Explanation
This is a user-enumeration issue (CWE-203/CWE-204 class): an unauthenticated attacker can determine which emails are registered admin/API-user accounts on a node by comparing the `/sessions` response body/timing, aiding targeted credential-stuffing or phishing against real node operators. It does not by itself allow authentication bypass, session forgery, or MFA downgrade, since password-protected and MFA-protected paths remain gated behind a correct password check.

### Likelihood Explanation
Fully unauthenticated and trivially repeatable: an attacker only needs network access to POST `/sessions` with arbitrary emails and measure response time/content — no credentials or prior access required. Feasibility depends on network jitter versus the bcrypt cost delta, but is a well-known, reliably exploitable class of timing side channel.

### Recommendation
Perform a dummy/constant-cost password hash comparison (e.g., against a fixed dummy hash) when `FindUser` fails, so the code path timing is equalized regardless of whether the email exists, and return the same generic error message (e.g., `"invalid credentials"`) for both "unknown email" and "wrong password" cases.

### Proof of Concept
Table-driven Go test in `core/sessions/localauth/orm_test.go` (or handler test in `core/web/sessions_controller_test.go`):
1. Seed DB with one non-MFA user and one MFA-enabled user.
2. POST `/sessions` with: (a) random unregistered email, (b) known non-MFA email + wrong password, (c) known MFA email + wrong password.
3. Assert response error strings for (a) differ from (b)/(c) (e.g., raw SQL error vs `"Invalid password"`), demonstrating enumeration.
4. Assert (b) and (c) produce identical error text (`"Invalid password"`), confirming MFA status is not leaked without a correct password.
5. Measure wall-clock latency across N repeated requests for (a) vs (b)/(c) and assert (a) is consistently faster (no bcrypt executed), demonstrating the timing side channel.
