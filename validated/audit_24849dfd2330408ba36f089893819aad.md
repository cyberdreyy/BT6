### Title
Attacker can block `stopEpoch` indefinitely by draining the ERC4626 vault's available liquidity, freezing all tranche funds - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower` parks the pool's undrawn capital in an external ERC4626 vault (e.g., a MetaMorpho vault) and, at epoch stop, must withdraw any shortfall between what `IdleCDOEpochVariant` pulls and on-hand cash. If the vault's `withdraw` reverts for an otherwise-covered amount, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable` rather than degrading. Any unprivileged user of that third-party vault can withdraw/borrow-out its liquid assets in the same block the manager calls `stopEpoch`, making the stop (and therefore all queued withdrawals) fail until liquidity returns. The SwissBorg analog is dependence on a third-party component whose failure propagates into the vault's solvency/liveness — here it is a liveness failure of the epoch state machine rather than a direct API compromise.

### Finding Description
At stop time, `ProgrammableBorrower.onStopEpoch` computes the shortfall and forces a vault withdrawal:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol
uint256 shortfall = _amountRequired - onHand;
if (shortfall > _currentVaultAssets()) return true;      // covered-by-default path
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
} catch {
    revert StopEpochVaultLiquidityUnavailable();
}
``` [1](#0-0) 

The guard only distinguishes "shares don't cover the shortfall" (return true → IdleCDO default path) from "shares cover it" (must withdraw). It does not distinguish a withdrawal failure caused by insufficient vault liquidity from a permanent failure: in both cases `stopEpoch` reverts and must be retried. Liquidity available to `vault.withdraw` is fully controlled by third-party vault users: any depositor can redeem, and in lending vaults the liquid buffer can be borrowed out, leaving `convertToAssets` high (accounting says covered) while `withdraw` reverts.

Because `availableToBorrow()`/`epochPendingWithdraws` reserve only covers the facility borrower, there is no protection against the external vault's liquidity being consumed by unrelated users. The default path (`return true`) never triggers because `_currentVaultAssets()` still reports full share value — the shares exist; they are just not currently redeemable.

### Impact Explanation
Every tranche holder's exit depends on the epoch state machine: `requestWithdraw` payouts and `collectWithdrawFunds` settle only after `stopEpoch`/`stopEpochWithDuration` completes and the next epoch's funds are distributed. An attacker who times a large vault redemption/borrow to coincide with the manager's `stopEpoch` call forces `StopEpochVaultLiquidityUnavailable`, and can repeat it each retry while the vault's liquidity remains exhausted. In a MetaMorpho-style vault, liquidity is only restored when external borrowers repay — outside the protocol's control — so withdrawal funds, pending epoch interest, and the entire tranche principal are frozen for the duration of the liquidity shortage. This is temporary freezing of user funds with a quantifiable bound equal to the full TVL parked in the vault sleeve (`epochStartVaultAssets + epochDepositedToVault`), matching the accepted impact class. It does not require any privileged role: the attacker is merely a user of the third-party ERC4626 vault.

### Likelihood Explanation
- The attacker needs no position in the Idle vault and no privileged role; only capital to drain the external vault's free liquidity, which is returned when they re-deposit (cost ≈ gas + opportunity cost).
- The timing window is favorable: `stopEpoch` is called by the manager/orchestrator at a publicly known `epochEndDate`, so the transaction ordering is predictable.
- The same revert can arise organically whenever the lending vault is fully utilized, so griefing is cheap to blend in with normal market conditions.
- Mitigating factors: the freeze is temporary (funds are not stolen), the honest manager can retry, and the code comments acknowledge retryability — but "covered but unwithdrawable" is precisely the case the retry cannot self-resolve, since nothing inside the protocol restores vault liquidity.

### Recommendation
- On `vault.withdraw` catch, do not hard-revert: fall back to withdrawing whatever the vault can serve (e.g., `vault.maxWithdraw(address(this))`), or return `true` so the pool's existing default/partial path runs rather than blocking the state machine.
- Alternatively, track a `vault.maxWithdraw`-aware expectation before `stopEpoch` so the interest/shortfall accounting can proceed on the redeemable portion and mark the remainder as defaulted/recoverable instead of freezing the epoch transition.
- Consider `redeem`ing shares pro-rata or holding a minimum liquid buffer (`underlyingToken.balanceOf(this)` floor) sized to `epochPendingWithdraws` so third-party vault liquidity cycles cannot stall settlement.

### Proof of Concept
Reproducible on the existing fork harness in `test/foundry/ProgrammableBorrowerCreditVault.t.sol` (which already runs against the live MetaMorpho USDC vault):

```solidity
// Fork test sketch — extends ProgrammableBorrowerCreditVault.t.sol
function testStopEpochFrozenByVaultLiquidityDrain() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // Attacker (any third-party vault user) drains the Morpho vault's free
    // liquidity right before epochEndDate, e.g. redeem/borrow via the vault's
    // own entry points so that morphoVault.maxWithdraw(programmableBorrower) < shortfall.
    // On a fork this is done by borrowing out the vault's markets or redeeming
    // with whale shares, leaving convertToAssets (accounting) unchanged.
    _drainMorphoVaultLiquidity(); // helper: leave shares intact, zero free liquidity

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);           // epoch cannot settle

    // Queued withdraw requests remain unclaimable; retried stopEpoch keeps
    // reverting until external vault borrowers repay.
    assertGt(cdoEpoch.epochEndDate(), 0);
    // all tranche principal + pending withdraws frozen for the liquidity gap
}
```

Key assertion: `vault.convertToAssets(shares) >= shortfall` (default path skipped) while `vault.maxWithdraw(address(this)) < shortfall`, which is exactly the gap the `if (shortfall > _currentVaultAssets())` check fails to cover.

Caveat I could not fully verify within the index: the exact `IdleCDOEpochVariant.stopEpoch` call site and whether a defaulted-partial-stop alternative exists that would downgrade this from a freeze to a loss-accounting issue; the exploit still stands on `ProgrammableBorrower.onStopEpoch` lines 241–253, which self-evidently propagate the external revert.
