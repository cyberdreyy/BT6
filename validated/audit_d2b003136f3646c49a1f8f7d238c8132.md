### Title
View/run-role users can read a bridge's `outgoingToken` via GET /v2/bridge_types/:BridgeName - ([File: core/web/bridge_types_controller.go])

### Finding Description
`BridgeTypesController.Show` looks up the bridge and directly returns `presenters.NewBridgeResource(bt)` with no role check and no field redaction: [1](#0-0) 

`presenters.NewBridgeResource` unconditionally copies `b.OutgoingToken` into the resource and serializes it as `outgoingToken` (no `omitempty`, unlike `IncomingToken` which is explicitly commented as "only provided when creating a Bridge"): [2](#0-1) [3](#0-2) 

`OutgoingToken` on `bridges.BridgeType` is the outbound authentication secret sent to the external adapter/bridge, so its confidentiality matters — it is meant to authenticate the node to the bridge, not to be handed to arbitrary authenticated users. In the router's `v2Routes`, the mutating bridge endpoints (`Create`, `Update`, `Destroy`) are wrapped with `auth.RequiresEditRole()`/`auth.RequiresAdminRole()`, but the `GET /v2/bridge_types/:BridgeName` route registering `bt.Show` has no such role wrapper — it only sits behind the general session/API-token authentication middleware applied to the `v2Routes` group, which accepts any authenticated role (`view`, `run`, `edit`, `admin`).

### Impact Explanation
Any authenticated user, even one restricted to `view` or `run` role (the lowest privilege tiers, intended to be unable to read/write sensitive configuration), can call `GET /v2/bridge_types/:BridgeName` and receive the bridge's `outgoingToken` in the JSON response. This token is a credential used to authenticate the Chainlink node's outbound requests to the external adapter; disclosure lets an unprivileged user impersonate the node to that adapter or use the credential outside the node's control. This maps to the "credential/secret disclosure" bounty class.

### Likelihood Explanation
Exploitation requires only a valid `view`- or `run`-role session or API token — the lowest privilege level grantable in a Chainlink node — and a single unauthenticated-in-role GET request once a bridge exists. No timing races, no admin cooperation beyond the pre-existing bridge creation, fully repeatable.

### Recommendation
Wrap the `GET /v2/bridge_types/:BridgeName` (and `Index`) routes with `auth.RequiresEditRole()` (or higher), matching the mutating routes, or strip `OutgoingToken` from the presenter in `Show`/`Index` responses (return it only on `Create`, similar to how `IncomingToken` is handled) so it is never returned to `view`/`run` role callers.

### Proof of Concept
1. As an `admin`-role session, `POST /v2/bridge_types` to create a bridge and capture its `outgoingToken`.
2. Create a session/API token with `view` (or `run`) role only.
3. As that low-privilege session, `GET /v2/bridge_types/<BridgeName>`.
4. Assert the response is `200 OK` (not `401`/`403`) and that `data.attributes.outgoingToken` equals the token captured in step 1 — proving credential leakage to an unprivileged role.
5. Compare against `Create`/`Update`/`Destroy` handler tests, which already assert `403` for non-edit/admin roles, to show the asymmetry with `Show`.

```go
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```
