### Title
Stale Confirmations From Deleted Keys Allow Multisig Requests To Execute Below The Configured Threshold - (File: multisig/src/lib.rs)

### Summary
The `MultiSigContract` in `multisig/src/lib.rs` counts confirmations recorded in the `confirmations` map without verifying that the public keys that produced them are still valid access keys on the account. When a key is removed via a `DeleteKey` request, the contract only purges confirmations/requests that key *originated* (`signer_pk == pk`), not confirmations that key cast on *other* pending requests. A request that a since-deleted key already confirmed keeps that stale confirmation counted toward `num_confirmations`, letting a request execute with fewer live-key approvals than the configured `K` threshold.

### Finding Description
`confirm()` performs the threshold check purely against the stored `HashSet<PublicKey>` for a request: [1](#0-0) 

There is no re-validation that each `PublicKey` already present in `confirmations` still exists as an access key on the multisig account at the time of the check.

When a `DeleteKey` action executes, the contract cleans up only requests *created by* the deleted key, and removes that key's own tracking counter — it does **not** scrub that key's confirmations from other, still-pending requests: [2](#0-1) 

Sequence that breaks the "confirmations counted vs. live members" binding:
1. Key `A` creates and self-confirms request `R` (a `Transfer`). `confirmations(R) = {A}`, `len = 1`.
2. Key `B` confirms `R`. Check: `len(1)+1 = 2 < num_confirmations(3)` → insert. `confirmations(R) = {A, B}`, `len = 2`.
3. A separate request to `DeleteKey(B)` is created and reaches `num_confirmations` using other live keys (e.g. `A`, `C`, `D`), and executes. `B`'s key is now removed from the account. This path only removes requests whose `signer_pk == B` and clears `num_requests_pk[B]`; it leaves `confirmations(R) = {A, B}` untouched.
4. Key `C` (a live key) confirms `R`. Check: `len(2)+1 = 3 >= num_confirmations(3)` → `execute_request(R)` runs the `Transfer`.

The transfer executes counting `A`, the now-nonexistent `B`, and `C` as three confirmations, while only `A` and `C` are actually live signers who approved it — one fewer live approval than the configured `K`. The equality that should hold, `confirmations_counted == live_members_who_approved`, is broken: `confirmations_counted (3) != live_approvals (2)`.

### Impact Explanation
This directly matches the report's impact category of "a multisig request executed below threshold." Any request type is affected — `Transfer`, `FunctionCall`, `AddKey`, further `DeleteKey`s, or `DeployContract` — so an attacker who controls or colludes with fewer than `K` live keys can get an arbitrary NEAR transfer or account-mutating action (including adding a new full-access key) executed by engineering a scenario where a stale confirmation from a legitimately-removed key remains attached to a pending request. This is a systemic accounting flaw in the confirmation-counting mechanism, not a one-off configuration error, and can result in outright loss of the funds/authority controlled by the multisig account.

### Likelihood Explanation
Key rotation (removing a compromised or departing signer's key) is a normal, expected multisig operation explicitly supported by the `DeleteKey` action. Any keyholder can leave a confirmation on a request and then have their key removed through routine key management; no owner/foundation/redeploy/social-engineering step is required beyond standard multisig usage. The bug is triggered by ordinary operational flows, making it readily reachable, not merely theoretical.

### Recommendation
When executing `DeleteKey` (or any member/key removal action), scrub the deleted key from the `confirmations` set of *every* pending request, not just requests it originated:
```rust
for (request_id, mut confirmations) in self.confirmations.iter() {
    if confirmations.remove(&pk) {
        self.confirmations.insert(&request_id, &confirmations);
    }
}
```
Alternatively (more robust), validate at `confirm()` time that all `PublicKey`s already recorded in a request's confirmation set are still valid access keys on `env::current_account_id()` before counting them toward the threshold, since NEAR does not currently expose enumerable access keys, it is preferable to actively re-verify liveness on any key/member removal, as recommended above.

### Proof of Concept
1. Initialize multisig with `num_confirmations = 3` and keys `A`, `B`, `C`, `D`.
2. `A` calls `add_request_and_confirm` with a `Transfer { amount }` request `R` targeting an external receiver → `confirmations(R) = {A}`.
3. `B` calls `confirm(R)` → `confirmations(R) = {A, B}` (2 < 3, no execution yet).
4. `A`, `C`, `D` confirm a separate request `R2 = DeleteKey(B)` targeting the multisig account itself, reaching 3 confirmations and executing — `B`'s access key is removed from the account.
5. `C` calls `confirm(R)` → `execute_request` runs because `len(confirmations(R))=2, +1 = 3 >= num_confirmations`, even though the only currently valid keys that approved `R` are `A` and `C`.
6. The `Transfer` executes with a live-approval count of 2 despite `num_confirmations = 3`, demonstrated by tracing `confirmations` state and the `on-chain` access key list at steps 3–5 in `multisig/src/lib.rs` lines [3](#0-2)  and [2](#0-1) .

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
