### Title
Loss-adjusted withdraw receipt escapes its haircut when the user re-requests before claiming, paying the full basis at par and draining the funded-claim pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` locates a haircutted receipt by dereferencing `lastWithdrawRequest[_user]` — an indirect "pointer" to the epoch that suffered a `stopEpochWithDuration` loss — instead of tracking which epoch actually owns the loss haircut. When a user submits a new `requestWithdraw` after the loss epoch but before claiming, `requestWithdraw` overwrites `lastWithdrawRequest[_user]` with the new epoch (`IdleCreditVault.sol:282`). The subsequent `claimWithdrawRequest` then looks up `lossRecoveryPriceByEpoch` under the wrong epoch, finds 0, skips the haircut clearing entirely, and the funded path pays the still-intact aggregate `withdrawsRequests[_user]` at par. The strategy only ever received the haircutted `pendingToFund` from `collectWithdrawFunds`, so the par payout is over-collateralized by other claimants' funded underlyings.

### Finding Description
Bug class: incorrect unref / dangling-pointer dereference (CVE-2016-9810 analog) — a claim is resolved through a stale/mutable epoch reference, so the loss-adjustment bookkeeping for the real loss epoch is never applied and the same basis is later "freed" a second time at full value.

Relevant code:

- `requestWithdraw` unconditionally overwrites the epoch marker: `lastWithdrawRequest[_user] = currentEpoch;` and adds to the aggregate `withdrawsRequests[_user] += _amount;` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;` [1](#0-0) 
- On a partially-funded `stopEpochWithDuration`, `collectWithdrawFunds` zeroes `pendingWithdraws` and records `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`, transferring only the haircutted `_amount` into the strategy [2](#0-1) .
- `claimWithdrawRequest` chains `_claimLossAdjustedWithdrawRequest` then `_claimFundedWithdrawRequest` [3](#0-2) .
- `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]`; if `lossRecoveryPriceByEpoch[lossEpoch] == 0` it returns without clearing anything [4](#0-3) .
- `_claimFundedWithdrawRequest` only checks `epochNumber <= lastWithdrawRequest[_user]` and then pays the whole `withdrawsRequests[_user]` aggregate at par via `_transferFundedClaim` [5](#0-4) .

Attack sequence (running epoch E, `stopEpochWithDuration` realized loss):

1. Attacker (any tranche-token holder / queued user) calls `requestWithdraw` in epoch E, recording basis B into `withdrawsRequests[attacker]` and `withdrawsRequestsByEpoch[attacker][E]`.
2. Epoch E is stopped via `stopEpochWithDuration(..., _lossAmount)`; the borrower funds only `pendingToFund < pendingBasis`. `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[E] < 1e18` and the strategy holds only the haircutted funds for that receipt.
3. In the next buffer (epoch E+1, before claiming), the attacker calls `requestWithdraw` again with any small amount (or the same tranche balance). `lastWithdrawRequest[attacker]` is overwritten to E+1.
4. After epoch E+1 ends, `epochNumber > lastWithdrawRequest[attacker]`, so the funded-claim guard passes. `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = E+1`, `lossRecoveryPriceByEpoch[E+1] == 0`, returns 0 — the epoch-E haircut is silently skipped.
5. `_claimFundedWithdrawRequest` pays `withdrawsRequests[attacker]` (which still contains the full un-haircutted epoch-E basis B plus the new request) at par through `_transferFundedClaim`.

The broken invariant is the loss waterfall: `pendingBasis * lossRecoveryPrice` was collected but `pendingBasis` is paid. The excess `B * (1 - lossRecoveryPrice)` is stolen from underlying held for other funded receipts, making the strategy insolvent for the last claimant.

No existing guard stops it: `_checkNotAllowed` in the queue, the `epochEndDate`/epoch-gating check, and `_transferFundedClaim`'s reserve guard only protect `defaultRecoveryReserve`, not the funded-claim pool.

Caveat: `lossRecoveryPriceByEpoch` is keyed by `epochNumber` at `collectWithdrawFunds` time (line 421); whether the stored key equals the request epoch E or E+1 depends on whether `deposit()`'s `epochNumber += 1` (line 610) runs before the collect call inside `stopEpochWithDuration`. I could not fully verify that ordering in `IdleCDOEpochVariant.sol`. If the key is E+1, the same dereference mismatch means the haircut is unreachable even without a second request — which only strengthens the finding, but the exact epoch key should be confirmed during PoC development.

### Impact Explanation
Direct theft / insolvency. The attacker receives `B * (1 - lossRecoveryPriceByEpoch[E])` underlying more than the strategy collected for that receipt. Loss is bounded by the attacker's share of the pending-receipt bucket but is fully quantifiable: with a 50% loss haircut on a receipt of 1000 tokens, the attacker extracts 500 tokens of other claimants' funded underlyings; the last legitimate claimant's `claimWithdrawRequest` reverts on insufficient balance, permanently freezing their payout.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only (a) a realized-loss epoch (`stopEpochWithDuration` with `_lossAmount > 0` and partial pending funding — an honest manager/borrower flow), and (b) the attacker making any second `requestWithdraw` before claiming, which is an unprivileged action available to any tranche holder in any buffer phase. No privileged role, no default, and no oracle manipulation is needed. The overwrite of `lastWithdrawRequest` on every request makes the trigger trivially repeatable by design.

### Recommendation
Do not derive the loss-adjusted claim epoch from the mutable `lastWithdrawRequest` marker. Either:

- Record per-request-epoch loss participation explicitly: when `collectWithdrawFunds` applies a haircut, persist the affected epoch and have `_claimLossAdjustedWithdrawRequest` iterate or look up `lossRecoveryPriceByEpoch` against each epoch present in `withdrawsRequestsByEpoch[_user]` (e.g., track the earliest unsettled epoch per user), clearing each basis at its own recovery price before the funded path runs; or
- In `requestWithdraw`, refuse (or first force-claim) when the user's outstanding receipt spans an epoch with `lossRecoveryPriceByEpoch != 0`, so a new request can never overwrite a pending haircutted epoch's marker; or
- Subtract the haircutted basis from `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch` at `collectWithdrawFunds` time (pro-rata is impossible without per-user iteration, so per-epoch claim tracking is preferable).

### Proof of Concept
Foundry fork/in-repo test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
// test/foundry/IdleCreditVault.t.sol
function testLossHaircutBypassedByLaterRequest() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);      // attacker deposit
    uint256 mintedBB = idleCDO.depositBB(amountWei);      // other liquidity

    _startEpochAndCheckPrices(0);

    // 1) attacker requests withdraw of tranches worth B in epoch 0
    uint256 req = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
    // plus a second honest user request so pendingWithdraws > 0
    cdoEpoch.requestWithdraw(mintedBB / 2, address(BBtranche));

    // 2) borrower partially funds; stop epoch with a realized loss
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 loss = pendingBasis / 2; // 50% haircut on pending receipts
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
    _stopEpochWithLossAndFunding(loss, pendingToFund);   // helper: borrower approves, manager calls stopEpochWithDuration
    // now lossRecoveryPriceByEpoch[lossEpoch] == ~0.5e18 and strategy holds only pendingToFund

    // 3) buffer of epoch 1: attacker re-requests, overwriting lastWithdrawRequest
    cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));

    // 4) finish epoch 1 normally
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // 5) attacker claims: loss-adjusted lookup hits epoch of lastWithdrawRequest (no price),
    //    funded path pays the full aggregate at par
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre;

    // attacker received full basis incl. the haircutted epoch-0 receipt
    assertGt(paid, req / 2, 'haircut was not applied to epoch-0 receipt');

    // insolvency: remaining claimants' funded pool is short
    // the other requester's claimWithdrawRequest reverts / underpays
}
```

Assertions to confirm: `strategy.withdrawsRequests(attacker)` paid at par exceeds `pendingToFund` pro-rata share, and the residual strategy balance is insufficient for the remaining claimants — demonstrating theft/insolvency caused by the stale epoch dereference.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
