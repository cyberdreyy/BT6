### Title
Unauthenticated MethodPublicKeyGet requests bypass authorization and trigger unbounded fan-out amplification before cache warms - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
`HandleJSONRPCUserMessage` special-cases `vaulttypes.MethodPublicKeyGet` at handler.go:413-429 to skip `requestProcessor.ProcessRequest`/`authorizer` entirely, and when the in-memory cache (`h.cachedPublicKeyGetResponse`) is empty it calls `newActiveRequest` + `fanOutToVaultNodes`, which sends one `don.SendToNode` call per DON member for every distinct `req.ID`. Because there is no per-request-ID deduplication other than the `req.ID` uniqueness check in `newActiveRequest`, and no auth/quota is tied to unauthenticated public-key requests, an attacker sending N requests with unique IDs before the cache is populated (or during any window where the cache is stale/empty) causes `N × len(donConfig.Members)` node sends.

### Finding Description
`HandleJSONRPCUserMessage` (handler.go:413-429) checks `req.Method == vaulttypes.MethodPublicKeyGet` before any authorization step and comments that this is intentional ("Public key requests don't require authorization... Note we cache this value quite aggressively so don't need to worry about DoS"). If `h.getCachedPublicKey()` returns `nil` (cache empty — true at cold start, after handler restart, or any time before the 1-minute `tickerVaultPublicKeyRefresh` populates it, or if `tryCachePublicKeyResponse` fails to parse a response), the handler calls `h.newActiveRequest(req, callback)` and `h.handlePublicKeyGet` → `h.fanOutToVaultNodes`, which iterates `h.donConfig.Members` and calls `don.SendToNode` for each member (handler.go:726-734).

`newActiveRequest` only rejects requests that reuse an already-active `req.ID` (handler.go:466-481); it does not rate-limit distinct IDs. The only inbound gating is a request-ID length check (`req.ID` ≤ 200 chars) and the generic top-level `gateway.ProcessRequest` path, which does not appear to apply any per-caller/global rate limiter before invoking `HandleJSONRPCUserMessage` (confirmed by reading `core/services/gateway/gateway.go` ProcessRequest, which only validates message shape/ID length and dispatches to the handler — no rate limiter call). The vault handler's own `nodeRateLimiter` (`ratelimit.RateLimiter`) throttles inbound *node* responses per node address in `HandleNodeMessage` (handler.go:493-496), not inbound user requests, so it does nothing to stop the fan-out from being triggered on the ingress side.

Since `MethodPublicKeyGet` requires no `Auth`/signature and no owner concept, a caller can generate arbitrarily many unique `req.ID` values (e.g., UUIDs) and fire concurrent `HandleJSONRPCUserMessage` calls, each of which is a cache miss until the periodic ticker (every 1 minute, or until a successful response is cached) fills `h.cachedPublicKeyGetResponse`. Each such call fans out to every DON member node, so node-facing traffic scales linearly with attacker request volume, unbounded by any per-caller quota.

### Impact Explanation
This is a request-amplification / DoS vector against DON member nodes reachable via the gateway: an unauthenticated caller can force the gateway to multiply a single cheap HTTP request into `len(donConfig.Members)` outbound node requests, repeated per unique `req.ID`, well before the aggressive cache the code comments rely on has had a chance to populate (cold start, restart, or any failure to cache a response keeps the miss path open indefinitely). This matches a node-availability/resource-exhaustion impact class (amplified request flood against DON nodes) rather than a direct funds/secrets compromise; it does not by itself leak keys or bypass write-path authorization, since public-key data is not itself sensitive, but it does provide an unauthenticated amplification primitive with no attacker-specific throttle in this code path.

### Likelihood Explanation
Preconditions: no credential, signature, or role is required — this is the "no requestProcessor/authorizer" path by design. Feasibility is high: the attacker only needs network access to the gateway's user-facing HTTP endpoint and the ability to generate unique JSON-RPC request IDs (trivial, e.g., UUIDs), and to send requests concurrently before the cache is warm or repeatedly during any gap when the cache is empty (handler restart, first minute after start, or if `fetchVaultPublicKey`/`tryCachePublicKeyResponse` fails). It is repeatable indefinitely against any DON that exposes this handler through a gateway with no external per-caller rate limiting in front of it (rate limiting existence at the HTTP ingress layer for this specific handler was not found in `core/services/gateway/network/httpserver.go`/`gateway.go` in the code paths reviewed; only node-response rate limiting and a request-ID-length check were found).

### Recommendation
- Deduplicate/coalesce concurrent public-key cache-miss requests instead of fanning out per distinct `req.ID` (e.g., use a single in-flight "refresh" request/singleflight pattern so multiple concurrent misses share one fan-out and await the same result).
- Apply a rate limiter (global and/or per-caller/IP) specifically to unauthenticated `MethodPublicKeyGet` requests before invoking `newActiveRequest`/`fanOutToVaultNodes`, consistent with the `nodeRateLimiter` pattern already used for node responses.
- Consider serving a stale cached key (with a short grace period) rather than triggering a fresh node fan-out on every miss, to eliminate repeated node traffic during cache-empty windows.

### Proof of Concept
Go handler-level test (extending `core/services/gateway/handlers/vault/handler_test.go`):
1. Construct a `handler` via `newHandlerWithAuthorizer` with a DON config of, e.g., 4 members, and a mocked `don` (`mocks.NewDON(t)`) with `don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)`.
2. Ensure the public-key cache is empty (`h.cachedPublicKeyGetResponse == nil`, default state — do not call `tryCachePublicKeyResponse`/`fetchVaultPublicKey`).
3. Loop N times (e.g., N=50), each iteration constructing a `jsonrpc.Request[json.RawMessage]{ID: uuid.New().String(), Method: vaulttypes.MethodPublicKeyGet}` and a fresh `handlerscommon.NewCallback()`, then call `h.HandleJSONRPCUserMessage(ctx, req, cb)` — do not wait for a node response so the cache stays empty throughout.
4. Assert `don.AssertNumberOfCalls(t, "SendToNode", N*len(donConfig.Members))` (or equivalent call-count assertion via `mock.Calls`), demonstrating fan-out scales linearly with N.
5. Assert that no rate-limit error is returned from any of the N calls, and that no authorization/authorizer mock method (`AuthorizeRequest`) was ever invoked for these calls, confirming the bypass.
