### Title
Missing per-instance authorization check in `VaultController.ExportDKGResult` allows any edit-role authenticated user to exfiltrate DKG result secret material for arbitrary DON/workflow instances - (File: core/web/vault_controller.go)

### Summary
`VaultController.ExportDKGResult` takes an attacker-supplied `instanceId` and directly returns the hex-encoded DKG result package (`HexDKGResultPackage`) for that instance without verifying that the requesting authenticated user/session is associated with that DON/workflow instance. Any user holding a session or API token sufficient to reach this route can retrieve DKG secret material for any instance ID that exists in the `dkg_results` table, not just instances belonging to their own workflow.

### Finding Description
`ExportDKGResult` in `core/web/vault_controller.go` parses `ExportDKGResultRequest{InstanceID}` from the request body, validates only that it is non-empty, and then calls: [1](#0-0) 

`orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))` performs a lookup keyed purely by `instanceId` with no join/filter against the requesting principal's identity, role scope, or any DON/workflow membership table. The retrieved `v.ReportWithResultPackage` (the raw DKG result package containing key-share/secret material) is hex-encoded and returned verbatim in `presenters.ExportDKGResultResource.HexDKGResultPackage`: [2](#0-1) 

There is no code anywhere in this handler, in `VaultORM.ReadResultPackage`, or in the presenter that checks whether the authenticated caller is a participant/owner of the given `instanceId`. The sibling `VerifyDKGResult` handler has the identical pattern — lookup by attacker-supplied `instanceId` with no ownership check: [3](#0-2) 

Standard Chainlink node authentication middleware (session cookie or API token) only establishes *that* a user is authenticated and *what role* (view/edit/admin) they hold — it does not (and cannot generically) know about per-instance DON/workflow ownership, so it cannot stop this. As long as the route is reachable by any session/token with edit-role privileges (the minimum role gate typically applied to non-admin mutating vault endpoints), the endpoint returns another instance's secret package.

### Impact Explanation
This is a secret/credential disclosure vulnerability: DKG result packages contain key-share material tied to a specific DON/workflow instance and are meant to be confined to the owning DON's participants. Any edit-role authenticated caller (not just admins) can enumerate/guess or otherwise obtain `instanceId` values and pull the corresponding `HexDKGResultPackage` for workflows/DONs they do not participate in, violating the secret-confinement invariant and enabling cross-tenant/cross-DON key material exposure. This maps to Chainlink's "secret/key material disclosure" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: an authenticated session or API token with edit role (no admin needed), and knowledge of a valid `instanceId` for a package created by `vault.ORM.WriteResultPackage` under a different instance/DON. `instanceId` values are not treated as secrets in this code path (they are user-suppliable plain strings in the request body), so this is trivially repeatable via a single POST request once a target `instanceId` is known or discovered.

### Recommendation
Add an authorization check in `ExportDKGResult` (and `VerifyDKGResult`) that verifies the authenticated caller/node is an authorized participant of the given `instanceId`'s DON/workflow before returning `ReportWithResultPackage`. This could be implemented by cross-referencing the `instanceId` against the caller's owned DON/workflow instances (e.g., via a workflow registry or DON-membership table) and returning 403/404 if the caller does not own/participate in that instance. Alternatively, scope the export endpoint to a system-internal/admin-only capability rather than session/token edit-role users.

### Proof of Concept
Go handler-level integration test in `core/web/vault_controller_test.go`:
1. Seed two DKG result packages via `vault.ORM.WriteResultPackage` under `instanceId = "A"` (belongs to test DON X) and `instanceId = "B"` (belongs to different DON Y).
2. Create an authenticated test client with `UserRoleEdit` associated only with DON X (no association/membership with DON Y — using whatever fixture the test harness uses to represent DON/workflow scoping, if any exists; note the current code has none).
3. POST `/v2/vault/dkg_results/export` with body `{"instanceId": "B"}` using the edit-role session/token.
4. Assert response is `200 OK` and `hexDKGResultPackage` field in the JSON body is non-empty and matches the seeded package B's `ReportWithResultPackage` hex encoding — demonstrating the edit user retrieved secret material for an instance/DON they are not associated with, with no ownership check performed by `ReadResultPackage`/`ExportDKGResult`.
