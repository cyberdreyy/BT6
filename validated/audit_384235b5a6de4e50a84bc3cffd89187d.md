### Title
Malicious users can spoof the name/symbol of an existing B-20 token to impersonate its issuer - ([File: crates/common/precompiles/src/b20_factory/logic/v1.rs])

### Summary
The `B20Factory` precompile lets any caller mint a new B-20 token with an arbitrary `name`/`symbol` string via `createB20`, with no check that the chosen identifier is unique or tied to any registered issuer. Because the on-chain token address is derived only from `(variant, msg.sender, salt)` and not from `name`/`symbol`, and no ownership/allowlist check is performed on these fields, a malicious user can create a token that presents itself under the identity of a legitimate, well-known asset (e.g. reusing `name: "USD Coin"`, `symbol: "USDC"`), exactly mirroring the OpenQ report's "pretend to be another organization" bug class where an unvalidated off-chain-identity string (there, `_organization`; here, token `name`/`symbol`) is fully attacker-controlled.

### Finding Description
`FactoryV1::create_b20` decodes caller-supplied `TokenCreateParams` (containing `name`/`symbol`) and only validates version, decimals (asset) or currency (stablecoin) — never uniqueness of `name`/`symbol`: [1](#0-0) 

`validate_asset`/`validate_stablecoin` check only `decimals` and delegate currency checks to storage; there is no check that `name`/`symbol` are unique or reserved: [2](#0-1) 

The token's on-chain address is derived from `variant.compute_address_from_hash(address_hash)`, which depends on `(variant, msg.sender, salt)`, not on `name`/`symbol`, so name/symbol collisions across different creators are unconstrained and undetectable by address alone: [3](#0-2) 

A dedicated regression test even confirms that empty (and by extension any) `name`/`symbol` values are accepted without validation, demonstrating there is no identity check on these fields at all: [4](#0-3) 

The `B20AssetCreateParams`/`B20StablecoinCreateParams` ABI surface exposes `name`, `symbol`, and `currency` as fully attacker-chosen strings with no on-chain registry binding them to a specific issuer: [5](#0-4) 

This is the direct analog of the OpenQ finding: there, `_organization` was a caller-chosen UUID with no on-chain binding to the real organization, enabling impersonation for phishing. Here, `name`/`symbol` (the human-facing identity of a B-20 asset that wallets, exchanges, and bridges display and often key off of) are equally unbound caller-chosen strings.

### Impact Explanation
Any unprivileged transaction sender (a "B20 token creator", explicitly a reachable persona for Base) can deploy a token whose displayed `name`/`symbol` — and even `currency` for stablecoins — is indistinguishable from a legitimate, already-deployed or well-known token. Downstream systems (wallets, off-chain indexers, bridges, integrators) that resolve tokens by symbol/name rather than by canonical address can be tricked into treating the attacker's token as the genuine asset, leading users to acquire, trade, or deposit into the fake token believing it to be the real one — a direct vector for theft of user funds via impersonation/phishing, matching the original report's stated impact category.

### Likelihood Explanation
Likelihood is high: `createB20` is a completely public, unprivileged precompile entry point once the relevant `ActivationFeature` (B20Asset/B20Stablecoin) is enabled, requires only a single signed L2 transaction, and the attacker has full control over `name`/`symbol`/`currency` with zero uniqueness enforcement or registry lookup blocking the spoof.

### Recommendation
Add an on-chain uniqueness/reservation mechanism for `name`/`symbol` (and `currency` for stablecoins) analogous to the reporter's suggestion of an oracle-backed mapping — e.g., a case-insensitive registry keyed by normalized `symbol` (and optionally `name`) that `create_b20` consults and updates atomically, rejecting creation if the identifier is already claimed, or require an authorization/permit step (similar to `associateExternalIdToAddress` in the referenced report) before a caller can mint a token under a given `symbol`/`name`.

### Proof of Concept
1. Attacker activates `ActivationFeature::B20Asset` (or it is already active).
2. Attacker calls `createB20(ASSET, salt, B20AssetCreateParams{ name: "USD Coin", symbol: "USDC", initialAdmin: attacker, decimals: 6 }, [])` from their own EOA.
3. `FactoryV1::create_b20` performs no uniqueness check on `name`/`symbol`, deploys the token at `compute_address_from_hash(variant, attacker, salt)`, and emits `B20Created` with `name = "USD Coin"`, `symbol = "USDC"`, as validated by the golden/unit tests showing arbitrary (including empty) `name`/`symbol` values are accepted unmodified: [6](#0-5) 
4. Any off-chain consumer resolving "USDC" by symbol/name instead of canonical address will treat the attacker's token as genuine, enabling phishing-driven fund theft.

impl Factory for FactoryV1 {
    fn create_b20(
        &self,
        storage: &mut B20FactoryStorage<'_>,
        call: IB20Factory::createB20Call,
        address_hash: B256,
        upgrade: BaseUpgrade,
    ) -> Result<Address> {
        let variant = B20Variant::from_abi(call.variant)
            .ok_or_else(|| BasePrecompileError::revert(IB20Factory::InvalidVariant {}))?;
        ActivationRegistryStorage::new(storage.storage())
            .ensure_activated(variant.activation_feature().id())?;
        let params = TokenCreateParams::decode(variant, &call.params)?;
        Self::check_version(params.version(), variant)?;
        params.validate()?;
        let (token_address, _) = variant.compute_address_from_hash(address_hash);

        let already_deployed = storage
            .storage()
            .with_account_info(token_address, |info| Ok(!info.is_empty_code_hash()))?;
        if already_deployed {
            return Err(BasePrecompileError::revert(IB20Factory::TokenAlreadyExists {
                token: token_address,
            }));
        }

        let checkpoint = storage.storage().checkpoint();
        let stub = Bytecode::new_legacy(Bytes::from_static(&[0xef]));
        storage.storage().set_code(token_address, stub)?;

        let init_calls = call.initCalls;
        match params {
            TokenCreateParams::Stablecoin { common, init } => {
                self.init_stablecoin(storage, token_address, common, init, init_calls, upgrade)?;
            }
            TokenCreateParams::Asset { common, init } => {
                self.init_asset_token(storage, token_address, common, init, init_calls, upgrade)?;
            }
        }

        checkpoint.commit();
        Ok(token_address)
    }

    /// Validates variant-specific invariants after the shared version check.
    ///
    /// Each arm owns its own rules. Version is checked first by the caller (`check_version`)
    /// so that version errors always take precedence over field-level errors.
    pub fn validate(&self) -> Result<()> {
        match self {
            Self::Stablecoin { init, .. } => Self::validate_stablecoin(init),
            Self::Asset { init, .. } => Self::validate_asset(init),
        }
    }

    /// Validates stablecoin initialization fields.
    pub const fn validate_stablecoin(_init: &B20StablecoinInit) -> Result<()> {
        // Currency validation is delegated to `B20StablecoinStorage::initialize`, which rejects
        // empty values with `MissingRequiredField` and non-A-Z values with `InvalidCurrency`.
        Ok(())
    }

    /// Validates asset-token initialization fields.
    pub fn validate_asset(init: &B20AssetInit) -> Result<()> {
        if init.decimals < B20AssetStorage::MIN_DECIMALS
            || init.decimals > B20AssetStorage::MAX_DECIMALS
        {
            return Err(BasePrecompileError::revert(IB20Factory::InvalidDecimals {
                decimals: init.decimals,
            }));
        }
        Ok(())
    }
