### Title
`epochEndDate == 0` sentinel misclassifies pre-first-epoch withdraw requests as "closed pool", skipping `pendingWithdraws` funding - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to CVE-2023-45539, where HAProxy treats `#` as a valid URI character while downstream `path_end` rules treat it as a delimiter — causing one component to misclassify a request another component routed differently — `IdleCreditVault.requestWithdraw` uses `idleCDO.epochEndDate() == 0` as the "pool is closed" signal. But `epochEndDate == 0` is an overloaded sentinel: it is true (a) after a successful pool close, and (b) before the very first `startEpoch()` has ever run (initial buffer, `epochEndDate` never set). Requests made in state (b) take the closed-pool branch: the receipt is minted but `pendingWithdraws` is never incremented, so the borrower is never asked to fund it at `stopEpoch`. The same sentinel also disables the one-epoch wait in `_claimFundedWithdrawRequest` (`IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && ...` short-circuits to false), so the receipt is claimable immediately, paying out of strategy underlyings that were never reserved for it.

### Finding Description
In `IdleCreditVault.requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:259-294):

```solidity
bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0;
...
if (!isClosed) {
  pendingWithdraws += _amount;
}
lastWithdrawRequest[_user] = currentEpoch;   // = 0 on first epoch
```

Before the first `startEpoch()`, `epochEndDate` is `0` (it is only set at `startEpoch`, IdleCDOEpochVariant.sol:266, and reset to `0` on pool close/default, IdleCDOEpochVariant.sol:223). The CDO-side `requestWithdraw` (IdleCDOEpochVariant.sol:739-791) is callable in this buffer phase whenever `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are enabled. Two misinterpretations result:

1. **Funding skip**: the receipt minted via `_mint(_user, _amount)` is never added to `pendingWithdraws`, so the first `stopEpoch` only sources borrower repayment for the *other* receipts. The attacker's receipt is structurally unfunded.
2. **Epoch-wait bypass**: `_claimFundedWithdrawRequest` (IdleCreditVault.sol:326) requires `epochEndDate() != 0` to enforce `epochNumber <= lastWithdrawRequest`. With `epochEndDate == 0` the check is skipped entirely, so the attacker can call `claimWithdrawRequest` in the *same* transaction/phase as `requestWithdraw` and pull underlyings immediately via `_transferFundedClaim` — i.e., an instant withdrawal with no epoch delay and no reserving, paid from whatever underlyings the strategy holds (including funds belonging to other pending receipts or residual liquidity). `lastWithdrawRequest[_user]` is also recorded as `0`, which is indistinguishable from "no request" for the loss-adjusted recovery bookkeeping (`lossRecoveryPriceByEpoch[0]` lookup at :261-262).

### Impact Explanation
Any unprivileged KYC-passed lender can, during the initial buffer period before the first epoch, deposit, call `requestWithdraw`, and immediately call `claimWithdrawRequest`. Because `epochEndDate == 0` skips both the `pendingWithdraws` accounting and the one-epoch wait, the claim is paid at par from strategy-held underlyings without the borrower ever being debited for it — a direct under-collateralized payout. If the strategy holds insufficient underlyings at claim time, the receipt instead remains minted but permanently unfunded after `stopEpoch` (borrower repayment only covered `pendingWithdraws`), causing insolvency/frozen-funds for the holder or dilution of other claimants when recovery reserves are tapped by `_transferFundedClaim`/`_transferDefaultRecovery`. Loss is bounded only by the attacker's deposit size; invariant broken is "one receipt one funded payout" and fair burn.

### Likelihood Explanation
Requires only that withdrawals be requestable during the pre-first-epoch buffer (the normal `allowAAWithdrawRequest`/`allowBBWithdrawRequest` gating, which is enabled for buffer-phase withdrawals in subsequent epochs and is not gated on `epochNumber > 0`). No privileged cooperation, no oracle manipulation, no donation is needed — a single user transaction pair in the deployment window. The window closes permanently once the first `startEpoch` sets `epochEndDate`, so it is a one-shot deployment-time issue per vault, but the vault lifetime begins exactly in this state.

### Recommendation
Distinguish "never started" from "closed" instead of overloading `epochEndDate == 0`. Options: (a) treat `epochNumber == 0 && epochEndDate == 0` as not-closed so pre-first-epoch requests increment `pendingWithdraws` normally; (b) gate `requestWithdraw` on a dedicated `poolClosed` flag set only by the successful close path rather than deriving it from `epochEndDate`; (c) enforce the epoch-wait in `_claimFundedWithdrawRequest` whenever `withdrawsRequests[_user] != 0`, not conditioned on `epochEndDate != 0`. Also reject `requestWithdraw` while `epochNumber == 0` if the intended design is that withdrawals only exist once an epoch has run.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCDOEpochVariant` + `IdleCreditVault` deployment, before any `startEpoch`):

```solidity
function testPreFirstEpochWithdrawSkipsPendingAndClaimsInstantly() external {
    // Fresh vault: epochEndDate == 0, epochNumber == 0, buffer phase
    assertEq(cdoEpoch.epochEndDate(), 0);
    assertEq(strategy.epochNumber(), 0);

    uint256 amount = 100_000 * ONE_SCALE;
    deal(defaultUnderlying, attacker, amount);
    _depositWithUser(attacker, amount);              // KYC'd lender deposit in buffer

    vm.startPrank(attacker);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(strategy.pendingWithdraws(), 0,         // BUG: not reserved for borrower funding
        "request misclassified as closed-pool");
    assertEq(strategy.withdrawsRequests(attacker), requested);

    // BUG: epochEndDate == 0 bypasses the one-epoch wait -> immediate claim
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();                 // pays at par from strategy underlyings
    assertGt(underlying.balanceOf(attacker) - balPre, 0);
    vm.stopPrank();
}
```

If strategy underlyings are insufficient at claim time, run the variant where the epoch then starts/stops normally and show `stopEpoch` funds only `pendingWithdraws` (excluding the attacker's receipt), leaving the minted receipt unfunded — a subsequent `claimWithdrawRequest` either reverts on transfer or drains reserves meant for other epochs' receipts.
