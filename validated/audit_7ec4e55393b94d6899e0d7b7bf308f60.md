### Title
Unsequenced (JIT) EIP-8130 account-change batches are intentionally replayable until the local epoch is bumped, permitting repeated re-application of a single signed authorization - (File: crates/execution/eip8130/src/config.rs)

### Summary
The bug class in CVE-2020-14302 is a signed authorization artifact (the OAuth "state" value) that can be replayed across multiple invocations because the server does not invalidate it after first use. The closest reachable analog in this codebase is the EIP-8130 `Local` channel's "unsequenced" (JIT) batch mode, whose sequence gate is explicitly skipped for replay purposes.

### Finding Description
`ConfigChangeAuthorizer::check_channel_sequence` enforces a monotonic `sequence` counter for `AccountChangeChannel::Local` batches, but explicitly exempts the sentinel value `UNSEQUENCED` (`u32::MAX`) from that check: [1](#0-0) 

The constant table documents this as deliberate: an unsequenced batch "consumes no sequence and stays replayable until the local epoch moves": [2](#0-1) 

Because the digest bound into the signature (`changes_digest`) commits only to `account`, `chainId`, `sequence`, and the changes payload — not to any per-transaction or per-inclusion nonce — a signed `SignedAccountChanges` batch with `sequence == UNSEQUENCED` remains valid and can be authenticated and applied by `ConfigChangeAuthorizer::authorize`/`authorize_with_account_state` repeatedly, in as many separate EIP-8130 transactions as an attacker (or observer who captured the signed batch) chooses to submit, as long as `local_epoch` has not changed: [3](#0-2) 

This mirrors the Keycloak flaw's structure: a signed/authenticated credential intended for single use is accepted on unlimited repeated invocations because the only invalidation mechanism (the sequence counter / Keycloak's session-state check) is bypassed by design for this mode.

### Impact Explanation
Repeated replay of a JIT-authorized `AuthorizeActor`/`RevokeActor`/`Lock`/`Unlock` batch lets anyone holding the signed bytes (which travel in plaintext inside transaction `account_changes` data) resubmit the exact same authorization change indefinitely. If the JIT batch grants scope (e.g., `AUTHORIZE_ACTOR` with a broad `SCOPE_OPERATOR`/`SCOPE_SPONSOR_PAYER` grant) intended to be a single ephemeral just-in-time authorization, an observer can re-apply it repeatedly, effectively turning a supposedly single-use session grant into a standing, indefinitely re-invocable authorization — an unauthorized-operation class impact on the account's actor configuration (theft-adjacent: an attacker-controlled actor can be kept perpetually re-authorized even if the account owner attempts to reason about it as one-shot).

### Likelihood Explanation
This requires only that a JIT-mode signed batch exists and is observable on-chain (transactions are public), and that the account's `local_epoch` has not been bumped since — both are ordinary conditions, not privileged capabilities. However, this is a documented, intentional design tradeoff (the comment explicitly states JIT batches "stay replayable until the local epoch moves"), not an unintended flaw. The severity of any misuse is therefore governed entirely by whether callers treat the epoch bump as the required single-use invalidation step; if any legitimate flow signs a JIT batch expecting single-use semantics without immediately bumping `local_epoch`, the replay window is real and unbounded in time.

### Recommendation
Confirm whether any current or planned issuance flow signs `UNSEQUENCED` batches under an assumption of single use without pairing them with an immediate epoch bump. If so, either (a) require every JIT batch to be paired atomically with a `CHANGE_TYPE_INCREMENT_LOCAL_EPOCH` op in the same `account_changes` list so it self-invalidates on first application, or (b) bind the JIT digest to an additional single-use nonce (e.g., the enclosing transaction hash or nonce) so the same signature cannot be reapplied in a different transaction.

### Proof of Concept
1. Account owner signs a `SignedAccountChanges` batch on the `Local` channel with `sequence = UNSEQUENCED (u32::MAX)`, containing an `AUTHORIZE_ACTOR` op granting a broad scope to some actor, intending it as a one-time just-in-time grant.
2. The batch (calldata) is submitted once via an EIP-8130 transaction; `check_channel_sequence` allows it because `seq == UNSEQUENCED` skips the sequence-match check, and it is applied.
3. Anyone who observed the transaction's calldata (public) re-submits the identical signed batch bytes in a new EIP-8130 transaction. `check_channel_sequence` again allows it (still `seq == UNSEQUENCED`, `local_epoch` unchanged), and `ActorAuthorizer` re-authenticates the same signature successfully, re-applying the authorization grant.
4. Step 3 can be repeated indefinitely as long as `local_epoch` is not incremented, demonstrating unbounded replay of what was intended as a single-use authorization. [4](#0-3)

    /// Enforces the channel's epoch/sequence gate against `state`. Mirrors the
    /// epoch/sequence block at the top of `applySignedAccountChanges`.
    fn check_channel_sequence(
        change: &SignedAccountChanges,
        state: &AccountState,
    ) -> Result<(), TxAuthError> {
        match change.channel {
            AccountChangeChannel::Local => {
                let epoch = u64::from((change.sequence >> 32) as u32);
                let seq = change.sequence as u32;
                if epoch != state.local_epoch {
                    return Err(TxAuthError::StaleEpoch {
                        expected: state.local_epoch,
                        got: epoch,
                    });
                }
                // An unsequenced (JIT) batch consumes no counter; any other value
                // must match the account's current local sequence.
                if seq != Eip8130Constants::UNSEQUENCED {
                    if u64::from(seq) != state.local_sequence {
                        return Err(TxAuthError::BadSequence {
                            expected: state.local_sequence,
                            got: u64::from(seq),
                        });
                    }
                    if seq >= Eip8130Constants::UNSEQUENCED - 1 {
                        return Err(TxAuthError::SequenceSaturated);
                    }
                }
            }
            AccountChangeChannel::Multichain => {
                if change.sequence != state.multichain_sequence {
                    return Err(TxAuthError::BadSequence {
                        expected: state.multichain_sequence,
                        got: change.sequence,
                    });
                }
                if change.sequence == u64::MAX {
                    return Err(TxAuthError::SequenceSaturated);
                }
            }
        }
        Ok(())
    }
