### Title
Signer vote flip-flop (Reject → Accept) double-counts weight in the miner's StackerDB tally, letting stale rejection weight and approval weight coexist past `total_weight` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` event loop tallies `BlockResponse::Accepted` and `BlockResponse::Rejected` messages from signers into `BlockStatus.total_weight_approved` / `total_weight_rejected`, guarding against double-counting a single vote *of the same kind* twice, but never against a signer switching sides. A signer that first rejects a block (weight added to `total_weight_rejected`, slot recorded in `responded_signers`) and later legitimately re-evaluates and accepts the very same block (a flow explicitly supported by the signer's own state machine, `LocallyRejected --> LocallyAccepted : re-evaluated`, see `docs/signer-flows.md` §2) has its weight added a second time to `total_weight_approved`, with no corresponding subtraction from `total_weight_rejected`. The two totals are supposed to be mutually exclusive per signer (each signer counts once, toward either accept or reject) so that `total_weight_approved + total_weight_rejected <= total_weight`; this invariant is what the coordinator's decision logic in `stacks-node/src/nakamoto_node/signer_coordinator.rs` relies on. That invariant is broken here.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the event-processing loop handles two message kinds per signer slot:

- `BlockResponse::Accepted`: bumps `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, then unconditionally does `block.responded_signers.insert(slot_id)` [1](#0-0) .
- `BlockResponse::Rejected`: bumps `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first response ever from that slot) [2](#0-1) .

The `Accepted` branch's gating check is against `gathered_signatures` (a signature map), not against `responded_signers`. So the sequence:
1. Signer S rejects block B → `responded_signers.insert(S)` succeeds, `total_weight_rejected += weight(S)`.
2. Signer S later re-evaluates and legitimately signs/accepts B (a normal, documented path in `stacks-signer/src/v0/signer.rs`'s `should_reevaluate_block`/`should_reevaluate_reject_reason`, which explicitly allows moving from a rejected state back to accepted once the rejection reason is no longer valid) → `Accepted` branch checks `gathered_signatures.contains_key(&S)`, which is `false` (S never signed before), so `total_weight_approved += weight(S)` is executed.

Nothing in the `Accepted` branch clears or decrements `total_weight_rejected`, and nothing in `Rejected` prevents this because it only fires once per slot via `responded_signers`. The result: signer S's weight is now counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously, and it stays that way for the lifetime of the `BlockStatus` entry. This directly breaks the "aggregated-weight vs verified-accepts" equality that `signer_coordinator.rs` depends on when it evaluates:

```
if total_weight_rejected + weight_threshold > total_weight { ... SignersRejected ... }
else if total_weight_approved >= weight_threshold { ... accept ... }
``` [3](#0-2) 

Because `total_weight_rejected` is a monotonically non-decreasing, "sticky" tally (never cleared when a signer flips to accept), a single equivocating/re-evaluating signer permanently inflates the reject side while simultaneously being credited on the accept side. Over multiple legitimate reject→accept flips from different signers (e.g., during a contested sibling-block scenario described in `docs/signer-flows.md` §5, where the signer set is explicitly expected to flip votes as conflicts go stale), the sum `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, i.e., the two "mutually exclusive" categories are no longer mutually exclusive.

### Impact Explanation
This is a coordinator-side liveness wedge, matching the "acting on a stale reward set/threshold" category: the miner's `SignCoordinator`/`StackerDBListener` can reach a state where `total_weight_rejected` alone (inflated with stale weight from signers who have since flipped to Accepted) crosses the `> total_weight - weight_threshold` line and forces `NakamotoNodeError::SignersRejected`, killing a block proposal that the *current* (post-flip) signer set would actually approve with ≥70% weight. Because the mechanism that resets rejection weight (`StackerDBListenerComms::reset_rejections`, called on `SignatureTimeout`) only fires on a timeout and does not run on every accept, and because `total_weight_rejected` is never decremented on an accept, a block can be starved indefinitely by weight that logically no longer represents any signer's live stance. This is a real correctness gap in the miner's vote aggregation that a normal signer-set re-evaluation flow (not even malicious behavior) can trigger, wedging block production for the current tenure.

### Likelihood Explanation
This requires no special privileges beyond a single signer slot's votes reaching the miner via StackerDB (gossip), and the underlying trigger — a signer rejecting then later accepting the same block after a conflict/timeout resolves — is an intended, documented signer-side behavior (`should_reevaluate_reject_reason`, `LocallyRejected --> LocallyAccepted`). It requires no majority and no other signer's key; a lone signer flipping its own vote is sufficient to desynchronize the two weight tallies. The severity of the resulting wedge scales with how many signers flip during contested proposals (e.g., sibling-block/reorg scenarios that the codebase's own tests exercise, such as `stacks-node/src/tests/signer/v0/reorg.rs`), making this readily reachable under ordinary network conditions rather than a purely theoretical edge case.

### Recommendation
Gate the `Accepted` branch's weight bump on the same `responded_signers` semantics used for `Rejected`, and when a slot transitions from rejected to accepted (or vice versa), explicitly subtract the stale weight from the previous category before adding it to the new one — e.g., track each slot's current disposition (`Approved`/`Rejected`) in a single map keyed by `slot_id`, and recompute `total_weight_approved`/`total_weight_rejected` from that map (or explicitly decrement the old bucket) instead of using two independently-incrementing counters gated by different keys (`gathered_signatures` vs `responded_signers`).

### Proof of Concept
1. Miner proposes block B; `StackerDBListenerComms::insert_block` initializes `BlockStatus` with zeroed weights [4](#0-3) .
2. Signer S (weight `w_S`) observes a stale/fresh sibling conflict and sends `BlockResponse::Rejected` for B. The listener does `responded_signers.insert(S)` (succeeds) and `total_weight_rejected += w_S`.
3. The conflict goes stale / re-evaluation criteria change (per `stacks-signer/src/v0/signer.rs`'s `should_reevaluate_reject_reason`), and S legitimately signs and sends `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. The listener's `Accepted` handler checks `gathered_signatures.contains_key(&S)` → false (first-time signature) → `total_weight_approved += w_S`. `total_weight_rejected` is left untouched at `w_S`.
5. Now `total_weight_approved + total_weight_rejected` includes `w_S` twice; repeating with enough flipping signers makes `total_weight_rejected` alone exceed `total_weight - weight_threshold` even though every signer currently on record would approve, causing `signer_coordinator.rs`'s wait loop to return `NakamotoNodeError::SignersRejected` and abort a block that should have been accepted.
