### Title
Front-runnable deterministic lockup address lets an attacker deploy a lockup for a victim with attacker-chosen parameters - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the lockup account id deterministically from `owner_account_id` alone (`sha256(owner_account_id)[..20].<factory>`) and only checks `env::attached_deposit() >= MIN_ATTACHED_BALANCE` before dispatching `Promise::new(lockup_account_id).create_account()...`, with no check that the address is still free. Anyone can pre-empt a known/expected grant to `owner_account_id` by calling `create()` first with their own `lockup_duration`/`vesting_schedule`/`whitelist_account_id`, permanently occupying that address before the legitimate issuer's transaction executes.

### Finding Description
The binding that should hold is: `LockupArgs persisted at lockup_account_id == sha256(owner_account_id)[..20].<factory>` must equal the `LockupArgs` submitted by the party the intended recipient (and the ecosystem) expects to fund that grant. In `LockupFactory::create` (lockup-factory/src/lib.rs:107-166), the only gating check is [1](#0-0) 
before the deterministic `lockup_account_id` is computed and a `Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(...).function_call("new", LockupArgs{...})` is dispatched [2](#0-1) .
There is no `env::state_exists()` (or equivalent) check against the target `lockup_account_id`. Because `owner_account_id` is a public identifier, anyone can compute the exact address a future grant to that account will be deployed to, and can race a call to `create(owner_account_id=<victim>, ...)` with attacker-chosen `lockup_duration`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`, attaching only `MIN_ATTACHED_BALANCE` (3.5 NEAR). If this transaction is included before the legitimate issuer's transaction, NEAR's `create_account` action succeeds for the attacker and persists the attacker's `LockupArgs` at that address. The legitimate issuer's subsequent `create()` call for the same `owner_account_id` will have its `create_account` action fail on-chain (the account already exists), causing `on_lockup_create` to detect failure via `is_promise_success()` and refund the issuer's deposit back to `predecessor_account_id` [3](#0-2) .
No guard such as `assert_self`, `assert_owner`, or a pre-flight existence check protects against this front-run; `assert_self()` in `on_lockup_create` only ensures the callback is invoked by the factory itself, not that the address was unclaimed at dispatch time.

### Impact Explanation
The `owner_account_id` field itself is not altered (it remains the victim, since it is passed by whoever calls `create`), but every other economically meaningful term of the lockup - `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, `staking_pool_whitelist_account_id`, `foundation_account_id` presence - is chosen entirely by whichever caller wins the race, not by the intended/legitimate grant issuer. This matches the explicitly listed Critical category "a lockup deployed with parameters its rightful creator never chose." The address is permanently squatted (deterministic derivation from `owner_account_id` gives no alternative), so the legitimate issuer cannot retry at that same address; their deposit is refunded, but the intended grant terms are lost/overridden. No victim private keys or foundation funds are directly drained by this specific path (the attacker's own `MIN_ATTACHED_BALANCE` funds the squatted contract, and the legitimate issuer's deposit is refunded rather than stolen), but the address-squatting with attacker-chosen lockup terms is a real, repeatable griefing/parameter-substitution vector against any specific `owner_account_id` the attacker can anticipate.

### Likelihood Explanation
Preconditions: the attacker must know or predict that a lockup grant for a specific `owner_account_id` is imminent (e.g., observed in mempool or publicly announced), and must be able to get their transaction included before the legitimate one - feasible via standard NEAR transaction submission/gas-price competition, no special privilege needed. Cost to the attacker is `MIN_ATTACHED_BALANCE` (3.5 NEAR) locked into the squatted contract, which is cheap relative to typical grant sizes. This is repeatable across any distinct `owner_account_id` the attacker can predict in advance.

### Recommendation
Before dispatching the `create_account` promise, add an explicit check that the deterministic `lockup_account_id` does not already exist (e.g., via a cross-contract view/promise pattern to check state, or restrict `create` calls for a given `owner_account_id` to be authorized/rate-limited, or salt the derived address with a value chosen by the trusted issuer rather than a value derivable purely from `owner_account_id`) so that address occupancy cannot be won by an unrelated party racing a legitimate grant.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
