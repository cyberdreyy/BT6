### Title
JWT replay protection has a TOCTOU race allowing double-use of a single-use token - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and only later, after several unsynchronized operations, calls `h.jwtCache.recordUsage(claims.ID)`. Because the check-then-act sequence is not performed atomically (no lock spans both operations), two concurrent calls to `Authorize` with the same JWT `jti` can both pass the replay check before either records usage, allowing the single-use token to authorize two trigger executions.

### Finding Description
In `Authorize`, the read of the replay cache and the write happen as two independent, separately-locked operations: [1](#0-0) 

`isReplay` takes an `RLock`, checks map membership, and releases the lock: [2](#0-1) 

`recordUsage` is called separately, much later in `Authorize`, after workflow-ID lookup and signer authorization checks, taking its own `Lock`: [3](#0-2) 

Since `isReplay` and `recordUsage` are not covered by a single critical section (e.g., no mutex held across both, and no atomic check-and-insert like `LoadOrStore`), two goroutines calling `Authorize` concurrently with the same JWT (`claims.ID`) can each independently observe `isReplay == false` before either calls `recordUsage`. Both would then pass the subsequent authorized-key lookup (which is read-only and doesn't consume the JWT) and both would return a valid `*gateway.AuthorizedKey`, allowing the caller to execute the workflow trigger twice with what should be a single-use, signed JWT.

### Impact Explanation
This breaks the single-use replay protection intended to enforce rate limiting / at-most-once execution of a user-triggered workflow capability via a signed JWT. An attacker holding one valid (possibly leaked but legitimate) single-use JWT can race two `Authorize` calls to obtain two successful authorizations from one token, resulting in duplicate workflow trigger execution — this maps to Chainlink's "unauthorized job run" / duplicate paid-capability execution impact class, and can cause resource exhaustion or duplicate side effects (e.g., double payment triggers, double capability invocation) for a single authorized action.

### Likelihood Explanation
The attacker only needs one valid JWT they are authorized to use once (a normal run-role/holder credential) and the ability to fire two requests concurrently to the gateway/API endpoint that calls `Authorize` — a trivial precondition requiring no elevated privileges. The race window is realistic: `isReplay` and `recordUsage` are separated by a map lookup and comparison (`authorizedKeys[workflowID]`, `keys[key]`), which is enough wall-clock time in a concurrent Go server for two simultaneous requests to both pass the check. This is reliably reproducible with two goroutines invoking `Authorize` in parallel.

### Recommendation
Make the check-and-record operation atomic under a single lock (or use `sync.Map.LoadOrStore` semantics), e.g., add a combined `checkAndRecord(jti string) bool` method on `jwtReplayCache` that acquires the write lock once, checks for existence, and if not present inserts the entry, returning whether it was already present — all under one critical section. Call this atomic method at the top of `Authorize` before doing the authorized-key checks, rather than calling `isReplay` and `recordUsage` as two separate calls.

### Proof of Concept
Go concurrent test in `workflow_metadata_handler_test.go`:
1. Construct a `WorkflowMetadataHandler` with a registered `workflowID` and authorized signer key, matching an actual signed JWT with a fixed `claims.ID` (`jti`).
2. Launch two goroutines that both call `handler.Authorize(workflowID, token, req)` with the same JWT/token concurrently (use a `sync.WaitGroup` and a shared start barrier/channel to maximize overlap).
3. Collect both `(key, err)` results.
4. Assert that only one of the two calls returns `err == nil` (success) and the other returns the "JWT token has already been used" error; run the test in a loop (e.g., 100 iterations, or with `-race` and higher `GOMAXPROCS`) to demonstrate that, prior to a fix, both calls sometimes return `err == nil`, proving the replay protection can be bypassed.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}
```

```go
func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```
