### Title
Global thread-local `Eip8130PhaseStatuses` handoff can misattribute phase-status data across concurrently executing EIP-8130 transactions - (File: `crates/common/evm/src/eip8130_phase_statuses.rs`)

### Summary
`Eip8130PhaseStatuses` is a single global mutable slot (a `thread_local!` `RefCell<Vec<u8>>`) used to hand off the EIP-8130 per-phase call status array from the executor to the receipt builder [1](#0-0) . This is structurally the same bug class as the reported oracle issue: a single shared "last value" variable is written by a producer step (`set`) and consumed later by a separate step (`take`), with correctness depending entirely on strict, uninterleaved ordering between the two for one logical unit of work (there, an oracle request/fulfillment; here, one transaction's execute→receipt-build sequence).

### Finding Description
The module's own documentation identifies the precise risk: it is "sound because block execution drives each transaction strictly as `execute → commit` on a single thread: the executor `set`s the statuses while running the transaction and the receipt builder `take`s them immediately afterward, with no other EIP-8130 transaction executing in between" [2](#0-1) . The panic-safety note goes further, explicitly acknowledging that "a panic between `set` and `take` (for instance, one caught by a `catch_unwind` in a parallel-execution context) could otherwise leave one transaction's statuses behind for the next transaction on the same worker thread to misattribute" [3](#0-2) .

The mitigation implemented — calling `clear()` at the start of every `execute` [4](#0-3)  — only protects against a *stale* leftover value from an earlier transaction being picked up by a later one on the same thread. It does **not** protect against the same failure mode as the oracle report: if the assumed strict `set → take` adjacency is ever violated for two transactions that are genuinely in flight concurrently on the same thread (e.g., under a parallel/async block-execution scheme, a panic path, or receipt building deferred relative to execution), a second `set()` call from transaction B can silently overwrite transaction A's not-yet-`take`n phase-status vector, exactly mirroring `lastHouseId` being overwritten by a second oracle request before the first fulfillment reads it.

This mechanism feeds `BaseReceiptBuilder`, which is used both in normal block execution (`crates/execution/evm/src/receipts.rs`) and in the flashblocks pending-state receipt builder (`crates/execution/flashblocks/src/receipt_builder.rs`) — both confirmed call sites of `Eip8130PhaseStatuses`.

### Impact Explanation
If the single-thread, non-interleaved assumption is ever broken (via a panic/`catch_unwind` recovery path in a parallel-execution context, as the code's own doc anticipates, or via any future change that makes execute/receipt-build asynchronous or reorderable), the wrong EIP-8130 transaction's per-phase status array would be attached to a receipt, or a transaction's receipt would silently get an empty status array belonging to no execution. Since EIP-8130 `phaseStatuses` communicate per-phase (all-or-nothing call-batch) execution outcomes in the transaction receipt, this would corrupt receipt/transaction encoding served to clients (`eth_getTransactionReceipt`) — an in-scope RPC surface — potentially misrepresenting which phases of a sponsored/account-abstraction transaction succeeded or reverted.

### Likelihood Explanation
Low-to-medium. Under the current, purely sequential single-block execution model this is not reachable by an ordinary unprivileged sender, because reth drives `execute → commit` synchronously per transaction with no interleaving. The vulnerability class only manifests if the "no other EIP-8130 transaction executing in between" invariant is violated — a scenario the code's authors themselves flag as a live concern ("a parallel-execution context") but do not fully close. I was not able to trace, within the available tool budget, whether `crates/execution/evm/src/receipts.rs` or `crates/execution/flashblocks/src/receipt_builder.rs` ever call `take()` from a different call frame/thread than the one that ran `set()` (e.g., via async scheduling, catch_unwind recovery, or flashblocks re-execution/caching paths), so I cannot confirm today's build is actually exploitable versus merely fragile-by-design. This should be treated as an unconfirmed, code-acknowledged latent race rather than a proven, directly triggerable bug.

### Recommendation
Replace the ambient global/thread-local handoff with an explicit, keyed structure (e.g., pass the phase-status vector directly through the `ExecutionResult`/receipt-building call chain, or key the handoff slot by transaction hash/index the way the report recommended keying `RAACHousePriceOracle` by `requestId`), removing any dependence on implicit thread/ordering invariants for correctness.

### Proof of Concept
No working PoC was constructed against this Base repository within the available time/tool budget. The finding is derived directly from the module's own documented risk model rather than from a demonstrated exploit trace through `crates/execution/evm/src/receipts.rs` / `crates/execution/flashblocks/src/receipt_builder.rs`, which I was unable to fully inspect in this session.

```rust
use alloc::vec::Vec;

#[cfg(feature = "std")]
std::thread_local! {
    /// Per-thread slot holding the most recently executed EIP-8130 transaction's
    /// per-phase statuses, awaiting consumption by the receipt builder.
    static PHASE_STATUSES: core::cell::RefCell<Vec<u8>> = const { core::cell::RefCell::new(Vec::new()) };
}
```

```rust
    /// Clears any statuses left in the slot, called at the start of `execute` so a
    /// value leaked by an earlier transaction (e.g. a panic caught between a prior
    /// [`Self::set`] and its [`Self::take`]) can never be misattributed to the
    /// current transaction's receipt. No-op in `no_std` builds.
    #[cfg(feature = "std")]
    pub fn clear() {
        PHASE_STATUSES.with(|cell| cell.borrow_mut().clear());
    }
```
