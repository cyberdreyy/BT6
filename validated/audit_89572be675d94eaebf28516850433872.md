### Title
Cross-user callback confusion via colliding attacker-controlled `MessageId` in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each user's response callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no uniqueness check before insertion. Because `MessageId` is fully attacker-controlled (bounded only by a max-length check in `Message.Validate`), a malicious client can submit a request with a `MessageId` identical to a victim's concurrently in-flight request, overwriting the victim's saved callback and hijacking the DON node's response.

### Finding Description
`HandleLegacyUserMessage` unconditionally does: [1](#0-0) 
This line assigns `h.savedCallbacks[msg.Body.MessageId]` without checking whether an entry already exists for that key. `MessageId` comes straight from the client-submitted message body and is validated only for length and null-byte suffix: [2](#0-1) 
There is no requirement that `MessageId` be globally unique, randomly generated, or namespaced per sender — it is attacker-chosen. Consequently, if attacker A submits a legacy request with `MessageId = "X"` after (or racing with) victim B's request also using `MessageId = "X"`, A's callback overwrites B's entry in `savedCallbacks[X]` under the same mutex `h.mu` (line 412 in `handler.go`).

When a node's response for method `web_api_trigger` arrives, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId`, with no sender/requester binding check: [3](#0-2) 
Whichever callback is currently stored under that key — attacker's or victim's — receives the node's response. This is a genuine violation of the "one user's request/response cannot be read by another" isolation invariant, and the fix belongs entirely to the gateway handler logic (not to a malicious node/DON, misconfiguration, or an out-of-scope actor) since it is exploitable purely by an unprivileged external client issuing well-formed, correctly-signed legacy messages with a colliding `MessageId`.

### Impact Explanation
If the attacker's callback overwrites the victim's, the attacker's HTTP client receives the private trigger response payload intended for the victim (secrets/data returned via `EncodeLegacyResponse` from the DON node) — a cross-user information disclosure. Symmetrically, the victim could receive an attacker-crafted response body, since the router has no way to tell whose entry is legitimate. This matches the "cross-user response confusion" impact class in scope, since exploitation is a straightforward race and requires no elevated privileges — only the ability to send `HandleLegacyUserMessage` requests with a chosen `MessageId`.

### Likelihood Explanation
Exploitability requires: (1) the attacker can submit `web_api_trigger` requests to the gateway with an arbitrary, valid-length `MessageId` (a normal capability of any external client of the legacy Gateway API — signature validity is required but does not constrain `MessageId` choice), and (2) the attacker can guess or observe a victim's in-flight `MessageId`. If `MessageId`s are generated predictably or are otherwise observable/guessable by the workflow/client tooling calling the gateway (e.g., sequential/derivable IDs, or IDs echoed elsewhere), the race is straightforward to win by submitting concurrently. Even without observing the exact victim ID, an attacker submitting a high-volume flood of requests using a small set of `MessageId`s could opportunistically collide with legitimate in-flight IDs, given the DON's node-response turnaround window (bounded by `CallbackMaxAgeSec`, default 120s) provides ample race window. This is a repeatable server-side flaw, not dependent on network timing tricks beyond ordinary concurrent HTTP requests.

### Recommendation
Do not key `savedCallbacks` solely by client-supplied `MessageId`. Options:
1. Reject insertion into `savedCallbacks` if the key already exists (return an error to the second submitter instead of silently overwriting), closing the race window.
2. Generate the map key server-side (e.g., a gateway-generated UUID or a hash of `MessageId + Sender address`) so that two different senders can never collide even with identical `MessageId` values, and use that composite/generated key for both storing and looking up the callback.
3. Additionally bind the stored callback to the expected sender/DON member and validate on response delivery that the response is being routed to the callback that corresponds to the original request context.

### Proof of Concept
Go unit/handler-level test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler `h` as in existing tests (mock `don`, `httpClient`).
2. Create two signed `api.Message`s, `msgA` (attacker) and `msgB` (victim), both with `Body.MessageId = "collide-id"`, method `web_api_trigger`, but different payloads/signers.
3. Register two distinct callback mocks, `cbA` (records what it receives) and `cbB`.
4. Call `h.HandleLegacyUserMessage(ctx, msgB, cbB)` then immediately `h.HandleLegacyUserMessage(ctx, msgA, cbA)` (simulating attacker's request overwriting victim's saved callback under `h.mu`).
5. Simulate the DON node's response for `MessageId = "collide-id"` intended for the victim's trigger via `h.HandleNodeMessage` (or directly `handleWebAPITriggerMessage`).
6. Assert: `cbA.SendResponse` is called with the response payload (bug reproduced — attacker receives victim's response) while `cbB.SendResponse` is never called.
7. Expected secure behavior (post-fix): either the second `HandleLegacyUserMessage` call returns an error/collision rejection, or each callback is keyed uniquely such that `cbB` (and only `cbB`) receives the correct response regardless of `MessageId` collision.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

}
