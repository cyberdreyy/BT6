### Title
Unbounded growth of the Vault gateway's replay-protection cache causes O(n) per-request scan DoS - (File: core/capabilities/vault/request_replay_guard.go)

### Summary
The Splitter bug is a class of "ever-growing state that is iterated in full on every call, reachable by an unprivileged/attacker-controlled action, with no upper bound on growth." The closest analog I could locate in this codebase is `RequestReplayGuard` in the Vault gateway handler, which stores every processed request digest in an in-memory map with no maximum size, and does a full linear scan of that map on **every single call** to expire old entries.

### Finding Description
`RequestReplayGuard` is documented as being used by both the `AllowListBasedAuth` and `JWTBasedAuth` flows in the Vault capability's gateway handler to ensure a request digest is only accepted once: [1](#0-0) 

Every call to `CheckAndRecord` performs `clearExpiredLocked()`, which iterates the *entire* `seen` map to find and delete expired entries, before inserting the new digest unconditionally (no cap on map size, `len(c.cache)` is never checked here unlike the unrelated `requestCache[T]` in the gateway `common` package): [2](#0-1) 

This is reached from `GatewayHandler.HandleGatewayMessage`, which processes `MethodSecretsCreate`, `MethodSecretsUpdate`, `MethodSecretsDelete`, and `MethodSecretsList` requests arriving from the internet-facing gateway via `h.requestProcessor.ProcessRequest`: [3](#0-2) 

The structural parallel to the `Splitter.claimForAllWindows()` bug is: (1) a data structure only grows via calls triggered externally, (2) every subsequent invocation pays a cost proportional to the *current total size* of that structure rather than to the individual request, and (3) there is no independent, size-based backstop — only time-based expiry, whose effectiveness depends on parameters I was not able to fully verify (see below).

### Impact Explanation
If the expiry timestamp passed into `CheckAndRecord` can be influenced or kept far enough in the future relative to the arrival rate of unique digests, the `seen` map grows without an upper bound, and the per-request cost of `clearExpiredLocked` grows linearly with it. Under sustained request volume this degrades (and in the limit could exhaust CPU/memory on) the node process handling Vault gateway traffic for *all* tenants/workflows, not just the attacker's own requests — a shared-resource DoS analogous to `claimForAllWindows()` becoming unusable for every claimant once `currentWindow` grows too large.

### Likelihood Explanation
I was unable to complete verification of two facts that determine whether this is truly exploitable versus already effectively mitigated:
- The exact call site and the source of the `expiresAtUnix` parameter in `core/capabilities/vault/authorizer.go` (3 references were found via `grep_search`, but I ran out of iterations before reading the file). If `expiresAtUnix` is derived from a short, non-attacker-controlled window (e.g., request TTL enforced elsewhere), then entries self-expire quickly and the practical growth is bounded by request rate × TTL, which would substantially reduce (though not eliminate) the risk.
- Whether requests reaching `HandleGatewayMessage`/`CheckAndRecord` are gated by an existing rate limiter (`limits.Factory`/`NewRequestValidatorFromLimitsFactory` appear in `NewGatewayHandler`) that would throttle the rate of unique digests an attacker could inject.

Because of these open questions, I cannot assert with confidence that this rises to the same "must-fix, high-severity, unbounded-forever" class as the Splitter bug — it may be a bounded, lower-severity, or already-mitigated pattern.

### Recommendation
Cannot be stated with full confidence without confirming the two points above. If confirmed to be attacker-influenced/unbounded, the general Splitter-style mitigation applies: cap the maximum size of `RequestReplayGuard.seen` (reject/evict when full, similar to how `requestCache[T].maxCacheSize` is enforced in `core/services/gateway/handlers/common/requestcache.go`), and/or move cleanup to a periodic background ticker instead of doing a full scan on the hot path of every request.

### Proof of Concept
Not able to construct a verified end-to-end PoC within the available tool budget — this would require confirming the `expiresAtUnix` source and any upstream rate limiting in `core/capabilities/vault/authorizer.go`, which I could not read before the iteration limit was reached.

Treat this as a lead requiring further investigation rather than a confirmed finding.**

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

// ClearExpired removes all entries whose expiry timestamp is in the past.
// Call this to eagerly reclaim memory even when CheckAndRecord is not invoked.
func (g *RequestReplayGuard) ClearExpired() {
	g.mu.Lock()
	defer g.mu.Unlock()
	g.clearExpiredLocked()
}

func (g *RequestReplayGuard) clearExpiredLocked() {
	now := g.nowFunc().UTC().Unix()
	for digest, expiry := range g.seen {
		if now > expiry {
			delete(g.seen, digest)
		}
	}
}
```

```go
func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}
```
