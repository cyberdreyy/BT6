### Title
Unauthenticated cross-user response hijacking via unvalidated `MessageId` reuse in legacy WebAPI Gateway handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `HoneyPot` report shows how a value freely chosen and set by one actor (`referralFeeDestination`), which is then unconditionally consumed on a shared code path affecting *other* users' transactions, can be weaponized because nothing enforces that the value is unique/owned/consistent before being relied upon later. The Chainlink Gateway's legacy `web_api_trigger` handler has a structurally similar issue: the `MessageId` used as the sole key into a shared `savedCallbacks` map is fully attacker/client-chosen and is stored **without checking whether an entry already exists**, unlike its v2 counterpart which explicitly rejects duplicates.

### Finding Description
In the legacy capabilities handler, `HandleLegacyUserMessage` blindly overwrites the shared callback map keyed only by the client-supplied `MessageId`: [1](#0-0) 

There is no check for an existing in-flight entry with the same key (contrast with the v2 `httpTriggerHandler.setupCallback`, which explicitly rejects duplicate `requestID`s): [2](#0-1) 

`MessageId` is validated only for length/format, not for uniqueness or binding to the sender's identity in any way that prevents collision with another party's in-flight request: [3](#0-2) 

When a node's response later arrives, it is matched and delivered purely by `MessageId` lookup, with no verification that the response's original requester is the same party who ends up holding the callback in the map: [4](#0-3) 

Because any unprivileged client hitting the gateway's `/user` endpoint can choose the `MessageId` value in the message they sign and submit, a malicious client can submit a request using the same `MessageId` as a legitimate victim's still-pending request. This overwrites the victim's entry in `savedCallbacks` with the attacker's own callback. When the DON's response for the victim's original request eventually arrives keyed by that `MessageId`, `handleWebAPITriggerMessage` will deliver it to whichever callback is currently stored under that key — the attacker's — not the victim's.

### Impact Explanation
This is a cross-user response confusion bug: an unprivileged/unauthenticated actor interacting with the internet-facing Gateway can intercept another user's workflow trigger response (or cause the victim's original caller to simply hang until timeout, a DoS on that specific request) simply by reusing a `MessageId`. Depending on the payload contents the leaked response body could include workflow-run details not belonging to the attacker, and legitimate callers would silently receive no response (their callback slot was stolen). This mirrors the underlying report's root cause — a caller-controlled identifier being trusted and relied upon by later shared logic without ownership/uniqueness checks, enabling denial-of-service or misdirected results for other users, exactly the class of "cross-user response confusion" called out as acceptable impact.

### Likelihood Explanation
The legacy path is exercised whenever `msg.Body.DonId != ""` is used (`isLegacyRequest`) in `gateway.ProcessRequest`, i.e., it is a supported production entry point for unprivileged HTTP clients hitting the gateway's user-facing endpoint, not merely a test/dummy scaffold — the same weakness also literally exists in the standalone `dummyHandler` reference implementation, which duplicates the exact pattern. An attacker needs only to guess or observe a legitimate `MessageId` and race the request submission before the real node response arrives — low-cost condition to satisfy compared to more complex attacks, though it does require some knowledge/timing of a target's in-flight `MessageId`, which is not inherently secret in these systems (workflow request IDs are often visible or predictable within the same client integration, or via existing race windows).

### Recommendation
Reject/atomically guard against `MessageId` collisions on the legacy path exactly as done in v2's `setupCallback`: check `savedCallbacks[msg.Body.MessageId]` for an existing entry under the same lock and return an explicit conflict error rather than overwriting silently. Additionally consider binding stored callbacks to the authenticated sender (verified via `ExtractSigner`) so that even if IDs collide, a mismatched sender on the eventual node response cannot be paired with someone else's callback.

### Proof of Concept
1. Victim submits a legacy `web_api_trigger` message signed with `MessageId = "abc123"` to the gateway; `HandleLegacyUserMessage` stores `savedCallbacks["abc123"] = victimCallback` and forwards the signed request to DON members.
2. Before the DON responds, attacker submits their own signed legacy message also using `MessageId = "abc123"` (message IDs are attacker-chosen and validated only for length: `core/services/gateway/api/message.go` lines 61-66). `HandleLegacyUserMessage` overwrites `savedCallbacks["abc123"] = attackerCallback` with no conflict check (`core/services/gateway/handlers/capabilities/handler.go` lines 411-414).
3. DON responds to `MessageId = "abc123"` for the victim's original request. `handleWebAPITriggerMessage` looks up `savedCallbacks["abc123"]`, finds the attacker's callback, deletes the entry, and delivers the victim's response payload to the attacker (`core/services/gateway/handlers/capabilities/handler.go` lines 148-161).
4. The victim's original caller never receives a response (hangs until gateway-side timeout), while the attacker receives data intended for the victim.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
