### Title
Loss-adjusted withdrawal haircut applied to the wrong epoch lets an attacker claim an old receipt at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The OOB-read bug class (attacker-controlled index reading the wrong slot) maps to `IdleCreditVault`'s epoch-indexed receipt accounting. `collectWithdrawFunds` stores a single `lossRecoveryPriceByEpoch[epochNumber]` for the *aggregate* `pendingWithdraws` bucket, but `_claimLossAdjustedWithdrawRequest` looks up the haircut via `lastWithdrawRequest[_user]`, which only points to the user's *latest* request epoch. A user holding an older, already-funded receipt plus a new receipt in the loss epoch claims the old one at par even though the funded pool assumed a haircut on it — a direct over-claim.

### Finding Description
- `requestWithdraw` records receipts per epoch in `withdrawsRequestsByEpoch[_user][currentEpoch]` and lumps them into the global `pendingWithdraws`, updating `lastWithdrawRequest[_user] = currentEpoch` (lines 259–294). The guard at lines 263–271 only blocks a new request when a loss price *already exists* for the previous `lastWithdrawRequest` epoch — it does not stop a user from stacking receipts across two epochs before any loss occurs.
- On a lossy stop, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the *whole* `pendingWithdraws` aggregate (which includes both epochs' receipts), zeroes `pendingWithdraws`, and stores the price under the *current* `epochNumber` only (lines 411–421).
- At claim time, `claimWithdrawRequest` first runs `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and calls `_clearWithdrawClaimForEpoch`, clearing only the latest epoch's `withdrawsRequestsByEpoch` entry and decrementing `withdrawsRequests[_user]` by that slice (lines 789–800, 811–820). The older epoch's receipt remains in the `withdrawsRequests` aggregate.
- `_claimFundedWithdrawRequest` then pays the residual `withdrawsRequests[_user]` at par (line 338–349), backed by a pool that only received `(W1 + W2) * lossRecoveryPrice`.

Broken invariant: loss waterfall / solvency — the haircut is priced on the aggregate but applied per latest-epoch slot, i.e., the contract "reads" the wrong per-epoch slot for older receipts.

### Impact Explanation
Direct theft / insolvency. The attacker receives `W1 + W2*price` instead of `(W1 + W2)*price`, an excess of `W1 * (1 - lossRecoveryPrice)` taken from the strategy's funded balance. Other users' loss-adjusted claims then underflow the funded pool — the last claimants' `safeTransfer` reverts (temporary freezing of funded claims) or the vault is drained. Loss is quantified by the attacker's pre-loss receipt size times the haircut fraction; with a 50% recovery price the attacker extracts half of `W1` in excess.

### Likelihood Explanation
Fully attacker-driven in normal modes (fixed-APR or APR0, any non-defaulted vault):
1. During running epoch N, KYC'd attacker calls CDO `requestWithdraw(W1)` → receipt recorded in `withdrawsRequestsByEpoch[attacker][N]`.
2. Epoch N stops and is funded normally (no loss); attacker does not claim.
3. During running epoch N+1, attacker calls `requestWithdraw(W2)` → `lastWithdrawRequest = N+1`; `pendingWithdraws` now aggregates both receipts. The guard at line 263 does not fire because `lossRecoveryPriceByEpoch[N] == 0`.
4. Epoch N+1 stops via `stopEpochWithDuration` with a partial loss; `lossRecoveryPriceByEpoch[N+1] < 1e18` and funded amount covers only the haircut on `W1+W2`.
5. Attacker calls `claimWithdrawRequest`: epoch N+1 slice is haircut, the epoch N slice pays at par → over-claim.

No privileged misbehavior required; the borrower/manager merely executes a documented loss path (`stopEpochWithDuration`), which is an honest, expected operation.

### Recommendation
Track per-user multi-epoch receipts when applying `lossRecoveryPriceByEpoch`: either (a) apply the loss price to all of a user's unfunded `withdrawsRequestsByEpoch` entries at collect time, or (b) at request time, snapshot whether the user still has unclaimed receipts included in `pendingWithdraws` and revert (extend the line-263 check to cover any unfunded prior receipt, not only ones whose epoch already has a stored price), or (c) split `pendingWithdraws`/funding per request epoch so each epoch's price is applied to exactly the receipts that epoch contains.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry` harness that already provides `_depositWithUser`, `_requestWithdrawWithUser`, `_stopCurrentEpoch*`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;
// In the existing IdleCreditVault/IdleCDOEpochVariant test fixture:

function testLossHaircutBypassAcrossEpochs() external {
    uint256 W1 = 100e6;  // attacker receipt in epoch N
    uint256 W2 = 100e6;  // attacker receipt in epoch N+1
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");

    // --- epoch N running ---
    uint256 tA = _depositWithUser(attacker, W1 + W2);
    uint256 tV = _depositWithUser(victim, 100e6);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(W1 * 1e18 / strategyPrice, address(tranche)); // request epoch N

    _stopCurrentEpochWithApr(apr);   // epoch N funded normally (no loss)
    // attacker intentionally does NOT claim

    // --- epoch N+1 running ---
    vm.prank(manager); cdoEpoch.startEpoch();
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(W2 * 1e18 / strategyPrice, address(tranche)); // lastWithdrawRequest = N+1
    vm.prank(victim);
    cdoEpoch.requestWithdraw(tV, address(tranche));                        // victim pending too

    // --- epoch N+1 stops with partial loss (honest manager flow) ---
    _stopCurrentEpochWithLoss(/* lossAmount such that lossRecoveryPrice = 0.5e18 */);

    // attacker claims: epoch N+1 slice haircut, epoch N slice paid at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();  // -> strategy.claimWithdrawRequest(attacker)
    uint256 attackerGot = underlying.balanceOf(attacker) - balPre;

    uint256 fair = (W1 + W2) * strategy.lossRecoveryPriceByEpoch(epochN1) / 1e18;
    assertGt(attackerGot, fair);      // attacker over-claimed by W1 * (1 - price)

    // victim's loss-adjusted claim now underflows the funded pool -> revert/insolvency
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertion: `attackerGot == W1 + W2 * price > (W1 + W2) * price`, and the vault's remaining balance is insufficient for the victim's claim. Uncertainty: exact helper names/`stopEpochWithDuration` invocation depend on fixture internals, but the state transitions (`requestWithdraw` → funded stop → second `requestWithdraw` → lossy stop → `claimWithdrawRequest`) follow directly from the cited lines.
