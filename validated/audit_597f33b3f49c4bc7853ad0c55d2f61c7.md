**Analysis:** The premise of the question is factually incorrect based on the code. `VMContext.storage_usage` is indeed a pre-execution snapshot [1](#0-0) , but it seeds a **running counter** `ExecutionResultState.current_storage_usage` [2](#0-1)  that is incrementally updated by **every** `storage_write`/`storage_remove` call within the same `FunctionCall`, not just the first one. Each `storage_write` invocation does `checked_add`/`checked_sub` against the current value of `current_storage_usage` (which already reflects any prior writes in the same execution), not against the frame-start snapshot [3](#0-2) .

At the end of execution, `compute_outcome` builds `VMOutcome.storage_usage` from this fully-accumulated `current_storage_usage` [4](#0-3) , and the runtime writes that final value onto the account via `account.set_storage_usage(outcome.storage_usage)` [5](#0-4) . The storage-staking exhaustion check (`check_storage_stake`) is then run against this fully-updated account state after the whole receipt executes [6](#0-5) , using `required = storage_amount_per_byte * account.storage_usage()` [7](#0-6) .

Existing unit tests (`test_storage_write_counter`, `test_storage_remove`) already confirm this incremental/cumulative accounting behavior [8](#0-7) . There is no code path where a delta is computed only against the frame-start snapshot while ignoring intermediate writes within the same call — every write mutates the same running total that is used for both the final `storage_usage` field and the subsequent staking check. No under-priced storage cost or bypass of storage-staking exhaustion checks is possible via this mechanism.
