**Analysis:** The scenario described is speculative and does not correspond to any actual code path in the repository.

`ShardChunkHeaderV1` and `ShardChunkHeaderV2` are legacy chunk header types whose `inner` field is statically typed as the bare `ShardChunkHeaderInnerV1` struct (no discriminant), while `ShardChunkHeaderV3` is statically typed to hold the tagged `ShardChunkHeaderInner` enum [1](#0-0) . These are three distinct, fixed Rust types — there is no code anywhere in the codebase that extracts an inner value out of a `ShardChunkHeaderInner::V1` enum variant and then re-hashes it via the untagged `ShardChunkHeaderInnerV1::compute_hash`/`ShardChunkHeaderV1::compute_hash`/`ShardChunkHeaderV2::compute_hash` paths. The dispatch in `ShardChunkHeader::compute_hash` strictly matches header version to its own fixed compute_hash function [2](#0-1) , and `inner_version_number` explicitly documents/enforces that `ShardChunkHeaderV1`/`V2` only ever contain `ShardChunkHeaderInnerV1` [3](#0-2) .

Additionally, chunk headers are produced exclusively by chunk producers (validators) as part of block/chunk production, not by ordinary unprivileged clients submitting transactions to an RPC endpoint. The threat model in this audit excludes validator/chunk-producer access, so even if a "tag-stripping" code path existed, it would require chunk-production-time control, which is out of scope. No concrete, reachable exploit path from an unprivileged attacker's transaction into this alleged flaw exists in the current code.
