### Title
Denial-of-Service via dust-lamport pre-funding of `SystemInstruction::CreateAccount` target accounts - (File: `programs/system/src/system_processor.rs`)

### Summary
The System Program's `create_account` handler rejects account creation whenever the destination account already holds any lamports, even a single lamport. Because any unprivileged party can transfer arbitrary lamports to an arbitrary `Pubkey` (including deterministically-derivable PDAs) via an ordinary `system_instruction::transfer`, an attacker can pre-fund a target address with 1 lamport before the legitimate owner's `CreateAccount` transaction lands, permanently forcing that legitimate transaction to fail with `SystemError::AccountAlreadyInUse`. This mirrors the LeXscrow report's root cause: a strict/optimistic balance check (`> 0` / `!= totalWithFee`) that can be poisoned by an unrelated, unprivileged deposit, causing legitimate operations to revert.

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` bails out if the destination account's lamport balance is nonzero: [1](#0-0) 

Since lamports can be sent to any `Pubkey` via a plain `SystemInstruction::Transfer` regardless of that account's ownership/existence, an attacker who knows (or can predict, e.g. a PDA derived with `create_program_address`/`create_with_seed`) the address a victim intends to `CreateAccount` at can front-run with a dust transfer. The subsequent legitimate `CreateAccount` instruction then unconditionally fails at this check, well before any of the account's data/owner is touched.

Tellingly, Agave engineers already recognized this exact class of bug and added a dedicated escape hatch, `create_account_allow_prefund`, which explicitly skips the `lamports > 0` check: [2](#0-1) 

This new path is exposed only through the separate `SystemInstruction::CreateAccountAllowPrefund` instruction and is gated behind the `create_account_allow_prefund` feature flag: [3](#0-2) 

The original `SystemInstruction::CreateAccount` instruction — which is what the vast majority of on-chain programs and client SDKs invoke via CPI (e.g., for PDAs, associated accounts, escrow vaults) — is unaffected by this fix and remains vulnerable to the dust pre-funding DoS.

### Impact Explanation
Any unprivileged actor observing a program's deterministic account-derivation scheme (PDAs, seeded addresses) can send 1 lamport to that address ahead of time. When the victim program or user later attempts `CreateAccount` at that same address (directly or via CPI), the instruction — and therefore the entire enclosing transaction — reverts with `AccountAlreadyInUse`. This is a reliable, cheap (single lamport + one signature fee), and repeatable denial-of-service primitive against any protocol that relies on `CreateAccount` succeeding at a specific, predictable address, matching the report's "small deposits causing legitimate deposits/operations to revert" bug class.

### Likelihood Explanation
High. No special privileges are required — only the ability to submit an ordinary `system_instruction::transfer` to a known/predictable target pubkey, something every ordinary user's transaction can do. Predictable target addresses (PDAs, seeded accounts) are extremely common in Solana program design, making this broadly exploitable wherever a victim program doesn't use `CreateAccountAllowPrefund` (which is a new, non-default, feature-gated instruction).

### Recommendation
Widen the `create_account_allow_prefund` behavior (or an equivalent relaxation) to the standard `SystemInstruction::CreateAccount` path itself, rather than requiring callers to opt into a brand-new instruction, since existing programs and SDKs overwhelmingly still call `CreateAccount`. At minimum, ensure the fix is activated by default/via feature-set rollout, and encourage/require program authors deriving PDAs to use `create_account_allow_prefund`-style semantics instead of the strict `lamports == 0` gate.

### Proof of Concept
1. Attacker computes the victim's future PDA/seeded account address `X` off-chain (deterministic derivation is public).
2. Attacker submits `system_instruction::transfer(attacker, X, 1)` — a normal, permissionless transaction.
3. Victim's program later issues a CPI to `SystemInstruction::CreateAccount { lamports, space, owner }` targeting `X`.
4. In `create_account` (`programs/system/src/system_processor.rs:160-171`), `to.get_lamports() > 0` is true (equals 1), so the instruction returns `SystemError::AccountAlreadyInUse`, aborting the victim's transaction — indefinitely, until the victim reworks their flow to use `CreateAccountAllowPrefund` (requires the feature to be active) or manually reclaims/handles the dust.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
