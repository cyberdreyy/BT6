### Title
Missing per-request ownership binding in `savedCallbacks` map allows MessageId collision to hijack another caller's Gateway response - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each pending user callback in `h.savedCallbacks` keyed **only** by the client-supplied `api.MessageBody.MessageId`, with no uniqueness check and no binding to the caller's signing address. Any signed request with a colliding `MessageId` silently overwrites a pending entry, so when the DON responds, `handleWebAPITriggerMessage` delivers the response to whichever caller registered last.

### Finding Description
`gateway.ProcessRequest` decodes the JSON-RPC/legacy envelope and assigns `msg.Body.MessageId` directly from the client-controlled request/JSON-RPC ID (`m.Body.MessageId = req.ID` in `common.ValidatedMessageFromReq`, `core/services/gateway/handlers/common/message_util.go:34-58`), then invokes `h.HandleLegacyUserMessage(ctx, msg, callback)` [1](#0-0) . The only requirement to reach this path is a validly signed envelope; `msg.Validate()` checks the signature format/recoverability but does not verify sender authorization for the method (confirmed by the `// TODO: apply allowlist and rate-limiting here` comment) [2](#0-1) .

Inside `HandleLegacyUserMessage`, after validation, the handler unconditionally overwrites the map entry:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

There is no check for an existing, still-pending entry under the same `MessageId` before overwrite, and the key space is not namespaced by sender address. When the DON later responds, `handleWebAPITriggerMessage` looks the response up purely by `msg.Body.MessageId` and delivers it to whichever callback is currently stored:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [4](#0-3) 

Because an attacker only needs their own valid keypair to sign an envelope (`msg.Sign(key)`), and can freely choose `MessageId` (proven by tests using arbitrary literal IDs like `"abc"`, `"abcd"`, `"12345"`) [5](#0-4) , they can submit a second `web_api_trigger` request reusing a `MessageId` that is currently pending for another caller. The second `HandleLegacyUserMessage` call silently replaces the first caller's `savedCallback` entry. The original caller's request is still forwarded to the DON with the original `MessageId`, so when the DON responds, the response is routed to the attacker's callback instead of the legitimate caller's — and the legitimate caller's HTTP request stalls until `RequestTimeoutError`.

### Impact Explanation
This is a cross-user response confusion / request hijacking bug: the attacker (using only their own signing key, no DON/gateway privilege) can capture a response payload addressed to another caller's in-flight `web_api_trigger` request, and simultaneously deny that caller the response (denial of service via silent overwrite). If the colliding `MessageId` belongs to a caller with higher-value data (e.g., proprietary trigger payload/results), the attacker gains unauthorized access to that data, matching Chainlink bounty classes for unauthorized data disclosure and request impersonation/response misdirection between unprivileged users.

### Likelihood Explanation
The only precondition is possessing any keypair to produce a validly signed gateway envelope — no DON, gateway operator, or admin role required, and no allowlist currently gates `web_api_trigger` senders (explicitly marked `TODO` in code). Actual exploitation likelihood depends on the attacker's ability to know/predict a victim's in-flight `MessageId` (e.g., deterministic IDs generated by known integrations, workflow IDs, or client software that is not randomizing IDs); regardless of that external factor, the core protection that should exist — rejecting or namespacing on collision — is completely absent in the code, so the collision itself is 100% reproducible in a unit/integration test.

### Recommendation
Bind `savedCallbacks` entries to the requester's identity, not merely to `MessageId`: derive the map key from `(sender, MessageId)` (sender recovered from the message signature) or reject/aggregate a `HandleLegacyUserMessage` call whose `MessageId` already has a live, non-expired entry (return a `HandlerError`/`UserMessageParseError` instead of silently overwriting). At minimum, add a `found` check before writing to `h.savedCallbacks` in `HandleLegacyUserMessage` and fail the request if an active entry already exists for that ID.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. `setupHandler(t)` to construct handler with mocked DON (`don.On("SendToNode", ...)` returns nil for all calls).
2. Build `msgVictim := triggerRequest(t, victimKey, topics, "", "", "")` with `messageID := "shared-id"` (adjust the `triggerRequest` helper or manually construct the message with `MessageId: "shared-id"` signed by `victimKey`).
3. Call `cbVictim := hc.NewCallback(); err := handler.HandleLegacyUserMessage(ctx, msgVictim, cbVictim)`; assert `err == nil` and `handler.savedCallbacks["shared-id"].Callback == cbVictim` (via exported test hook or `require.Same`).
4. Build `msgAttacker` — same `MessageId: "shared-id"`, but signed by `attackerKey`, different `Topics`/payload.
5. Call `cbAttacker := hc.NewCallback(); err = handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)`; assert `err == nil`.
6. Assert `handler.savedCallbacks["shared-id"].Callback == cbAttacker` — i.e., the victim's callback was silently overwritten (isolation invariant violated).
7. Simulate the DON response for `MessageId: "shared-id"` via `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)` using `hc.ValidatedResponseFromMessage(msgVictim)` (the DON is echoing the original request `MessageId`).
8. Assert `cbAttacker.Wait(...)` returns the response payload (attacker receives it), while `cbVictim.Wait(...)` with a short timeout returns a timeout/no-response error, proving the victim never receives their own response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

// newSignedLegacyRequest creates a signed legacy request message for testing purposes.
// Legacy requests embed
func newSignedLegacyRequest(t *testing.T, messageID string, method string, donID string, payload []byte) []byte {
	msg := &api.Message{
		Body: api.MessageBody{
			MessageId: messageID,
			Method:    method,
			DonId:     donID,
			Payload:   payload,
		},
	}
	privateKey, err := crypto.GenerateKey()
	require.NoError(t, err)
	require.NoError(t, msg.Sign(privateKey))
	codec := api.JsonRPCCodec{}
	rawRequest, err := codec.EncodeLegacyRequest(msg)
	require.NoError(t, err)
	return rawRequest
}
