### Title
Stale LDAP Session/API Token Retains Revoked Role Because Upstream Sync Only Runs Once At Startup By Default - (File: `core/sessions/ldapauth/sync.go`, `core/sessions/ldapauth/ldap.go`)

### Summary
The Chainlink node's LDAP authentication provider caches a user's role locally in the `ldap_sessions` and `ldap_user_api_tokens` tables at login time, and every subsequent request is authorized purely from this cached copy rather than the upstream LDAP directory [1](#0-0) . Reconciliation with the upstream LDAP server (which would remove or downgrade a user who has been de-provisioned or demoted) is only guaranteed to run once, at node startup, when `UpstreamSyncInterval` is left at its default `'0s'` value [2](#0-1) . This is the same bug class as the Mento report: a privilege-granting state (veMENTO voting power / here, the cached session role) is not revoked when the underlying entitlement (locked MENTO / here, LDAP group membership) is removed, because the code path that would clear it is not guaranteed to run on the relevant trigger.

### Finding Description
`LDAPServerStateSyncer.Start()` only spawns the recurring background sync goroutine (`l.run()`) if `UpstreamSyncInterval` is non-zero; otherwise it calls `l.Work(ctx)` exactly once, at application startup [2](#0-1) . The documented and shipped default for `UpstreamSyncInterval` is `'0s'` [3](#0-2) , meaning the periodic re-validation against the upstream directory is disabled out of the box.

Per-request authorization (`AuthorizedUserWithSession` and `FindUserByAPIToken`) never queries LDAP directly — it trusts the `user_role`/`user_email` fields cached in the local `ldap_sessions` / `ldap_user_api_tokens` tables and only checks a time-based expiry, not upstream group membership [1](#0-0) [4](#0-3) . The package's own doc comment confirms the design intent was that sync "happens for every auth endpoint hit, and via the defined sync interval" [5](#0-4) , but the actual per-request auth functions (`AuthorizedUserWithSession`, `FindUserByAPIToken`) do not call `Work()` or otherwise trigger a re-sync — they only read the cached row.

The only other place that can trigger a reconciliation via `WakeSessionReaper()` is the session `Destroy` (logout) handler [6](#0-5) , which is a voluntary client action, not something an administrator can force on a compromised or demoted account.

Consequently, if an LDAP administrator removes a user from a privileged group (e.g., `NodeAdmins`) or deactivates the account upstream, any browser session cookie or API token that user already obtained continues to authenticate with the old, cached role for as long as the session/token remains within its expiry window (`SessionTimeout` / `UserAPITokenDuration`, default up to `240h`) — because the local cache is never invalidated except at the one-time startup sync or on that specific user's own logout. This mirrors the Mento report exactly: revocation of the underlying entitlement (group membership / locked MENTO) does not clear the derived privilege (cached role / veMENTO) unless a specific, easily-missed code path executes.

### Impact Explanation
A de-provisioned or demoted LDAP user (or an admin downgrading a user's role for security reasons, e.g., after suspected compromise) retains their prior elevated role (Admin/Edit/Run) against the Chainlink node's HTTP API for the full remaining lifetime of any session or API token they already hold, potentially up to the configured `SessionTimeout`/`UserAPITokenDuration`. This allows continued unauthorized administrative actions (job creation/deletion, key management, bridge/external-initiator management) after the operator believed access had been revoked — a stale-authorization/role-bypass condition directly analogous to the accepted Sherlock finding.

### Likelihood Explanation
This requires no special network position and is entirely a function of default configuration: because `UpstreamSyncInterval` defaults to `'0s'`, every node deployed with LDAP auth and left at defaults is affected — the periodic reconciliation simply never runs after the initial startup sync. The only way to force re-validation of a specific compromised/demoted account is for that account holder to voluntarily log out. This is a realistic, easily reachable scenario for any operator relying on default settings, which the config docs do not warn is effectively "sync-once."

### Recommendation
- Change the default behavior so the reconciliation with the upstream LDAP directory runs on a safe periodic interval by default (do not let `'0s'` fully disable background sync), or explicitly document/warn that `'0s'` means "sync only at node startup and at that user's logout."
- Additionally, revalidate role/membership (or at minimum, check a "deactivated" flag) directly against LDAP on each `AuthorizedUserWithSession` / `FindUserByAPIToken` call, or reduce `SessionTimeout`/`UserAPITokenDuration` bound tightly to the sync interval so cached privileges cannot outlive intended revocation windows.
- Provide an explicit operator action (e.g., a CLI/API command) to force-purge/re-sync a specific user's sessions and tokens immediately upon a role change, rather than relying on the user's own logout.

### Proof of Concept
1. Deploy a Chainlink node with `WebServer.AuthenticationMethod = "ldap"` and leave `WebServer.LDAP.UpstreamSyncInterval` at its default `'0s'`.
2. A user in the `NodeAdmins` LDAP group logs in, and `CreateSession` inserts a row with `user_role = 'admin'` into `ldap_sessions` [7](#0-6) .
3. The LDAP administrator removes this user from the `NodeAdmins` group (or deactivates the account) directly on the upstream LDAP server.
4. Because `UpstreamSyncInterval` is `'0s'`, `LDAPServerStateSyncer.Start()` never schedules `l.run()`'s ticker loop, so no further reconciliation occurs after the node's initial startup sync [2](#0-1) .
5. The user continues issuing authenticated admin-level requests using their existing session cookie; `AuthorizedUserWithSession` returns the stale cached `admin` role from `ldap_sessions` without contacting the LDAP server, succeeding until the session naturally expires or the user calls `Destroy` (logout) themselves [1](#0-0) .

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

// Destroy removes the specified session ID from the database.
func (sc *SessionsController) Destroy(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()

	session := sessions.Default(c)
	defer session.Clear()
	sessionID, ok := session.Get(auth.SessionIDKey).(string)
	if !ok {
		jsonAPIResponse(c, Session{Authenticated: false}, "session")
		return
	}
	if err := sc.App.AuthenticationProvider().DeleteUserSession(ctx, sessionID); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	sc.App.GetAuditLogger().Audit(audit.AuthSessionDeleted, map[string]any{"sessionID": sessionID})
	jsonAPIResponse(c, Session{Authenticated: false}, "session")
}
