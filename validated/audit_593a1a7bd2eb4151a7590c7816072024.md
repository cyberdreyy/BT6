## Analysis

Confirmed root cause in `BlockStatus` tallying on the node-side coordinator (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`). `BlockStatus` keeps a single shared `responded_signers: HashSet<u32>` gate together with two independent monotonic counters, `total_weight_approved` and `total_weight_rejected`, and a separate `gathered_signatures` map used only to gate double-adding *approve* weight. [1](#0-0) 

- Accept path gates on `gathered_signatures.contains_key(&slot_id)` and, if absent, adds to `total_weight_approved`, then always inserts into both `gathered_signatures` and `responded_signers`: [2](#0-1) 
- Reject path gates on `responded_signers.insert(slot_id)` and, only on first insertion, adds to `total_weight_rejected`: [3](#0-2) 

Neither path ever decrements the *other* counter or clears the other path's gate. A signer who first rejects the block, then legitimately flips to accept the *same* `signer_signature_hash` (this is a normal, protocol-sanctioned flow — a signer re-evaluates and revises its vote on the same proposal once the reject reason becomes re-evaluable, per the signer's own `should_reevaluate_reject_reason`/`should_reevaluate_block` logic) will:
1. First register in `responded_signers` and bump `total_weight_rejected` (Reject path).
2. Later register in `gathered_signatures` (still absent) and bump `total_weight_approved` too (Accept path), because the accept-path gate (`gathered_signatures`) is independent of the reject-path gate (`responded_signers`).

The result: that signer's weight is counted in **both** `total_weight_rejected` and `total_weight_approved` simultaneously, and `total_weight_rejected` is never rolled back after the flip. [4](#0-3)  shows the consumer of these tallies: on every wakeup it checks rejection-crosses-blocking-threshold **first**, and only checks acceptance second. Because `total_weight_rejected` is sticky and never cleared on a later flip-to-accept, a scenario is reachable where, after enough signers flip reject→accept for the same block hash, `total_weight_approved` legitimately reaches the 70% threshold while the stale `total_weight_rejected` tally (from the earlier, now-superseded rejections of the very same flipping signers) still exceeds the 30% blocking minority. Since the reject check is evaluated first in the loop, the coordinator will call `NakamotoNodeError::SignersRejected` and discard a block that has, at that moment, actually reached real 70% signer approval — a liveness wedge on a validly-signed block. This directly breaks the "aggregated-weight vs verified-accepts" equality the rules call out: the aggregated `total_weight_rejected` figure no longer reflects the verified/live set of current rejecters once votes flip.

Contrast this with the signer-client side, `stacks-signer/src/signerdb.rs`'s `add_block_signature`, which explicitly deletes any prior rejection row for the same signer/block before inserting the acceptance — i.e., the signer-side storage correctly treats accept/reject as mutually exclusive per signer per block: [5](#0-4) . The node-side coordinator's in-memory `BlockStatus` tally has no equivalent reconciliation, which is the asymmetry causing the bug.

I was not able to fully trace, within the remaining budget, the exact upstream conditions in the doc-described re-evaluation flow (`docs/signer-flows.md` section 3, "prior reject reason re-evaluable?") that make a signer flip from Rejected to Accepted for the *identical* `signer_signature_hash` in a live mining round, nor did I confirm whether `reset_rejections` (called on timeout) is ever invoked in a way that would mask this before the reject-threshold check fires in practice. That would need runtime/integration verification (e.g. via a Devin session) to fully confirm exploitability timing.

### Title
Stale, never-cleared rejection weight lets a node coordinator discard an already-70%-approved block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`BlockStatus.total_weight_rejected` and `total_weight_approved` are updated by two independently-gated code paths (`responded_signers` vs `gathered_signatures`). A signer that legitimately flips its vote for the same block hash from Rejected to Accepted (a protocol-sanctioned re-evaluation) has its weight counted in *both* tallies, and the reject tally is never rolled back.

### Finding Description
- Reject path gate: `block.responded_signers.insert(slot_id)` — sets weight into `total_weight_rejected` only once, permanently. [3](#0-2) 
- Accept path gate: `block.gathered_signatures.contains_key(&slot_id)` — independent map, so a later Accepted message from the same signer still adds to `total_weight_approved`. [2](#0-1) 
- Neither branch clears the other counter/gate when a signer's vote changes, so `total_weight_rejected` remains permanently inflated by since-superseded rejections.
- `SignCoordinator::wait_for_block_response`-style loop checks the reject-threshold condition before the accept-threshold condition on every wakeup: [4](#0-3) 

### Impact Explanation
If enough signers who initially rejected a proposal (e.g., because their local chainstate view was stale) later flip to Accept for the identical `signer_signature_hash` once the block re-evaluates favorably, `total_weight_approved` can reach the real 70% quorum while `total_weight_rejected` — never decremented — still exceeds the 30% blocking minority from the stale rejections. Because the coordinator evaluates the rejection condition first, it discards a validly, currently-approved block as `SignersRejected`, a liveness wedge: a properly-signed block that should be broadcast is dropped.

### Likelihood Explanation
This requires no majority collusion or externally privileged access: it only needs the mining round's own signer set to exhibit the protocol-sanctioned reject→accept flip on the same proposal, which the codebase's own docs describe as expected behavior (`should_reevaluate_reject_reason` / re-evaluation flow). A single slow/late-informed signer combined with ordinary gossip timing could trigger the double count; the miner does not need any extra capability beyond normal proposal broadcasting/timing.

### Recommendation
When a signer's Accepted message supersedes a previously recorded Rejected vote (or vice versa) for the same `signer_signature_hash`/slot, `BlockStatus` should reconcile the tallies atomically — e.g. use a single `HashMap<u32, Vote>` keyed by slot id recording the signer's *current* vote, and recompute `total_weight_approved`/`total_weight_rejected` from that map, mirroring the signer-side `add_block_signature`'s deletion of the stale opposite-vote row.

### Proof of Concept
1. Node proposes block B (`signer_signature_hash = H`).
2. Signer S (weight w) sends `BlockResponse::Rejected(H)` — `responded_signers` gains S's slot, `total_weight_rejected += w`.
3. State changes (e.g. new burn block/read-count) make S's earlier reject reason re-evaluable; S locally re-evaluates the same block B and now signs it, sending `BlockResponse::Accepted(H)` with its signature.
4. In `stackerdb_listener.rs`, since S's slot is absent from `gathered_signatures`, `total_weight_approved += w` is applied — S's weight now counted in both tallies.
5. If, at this point, `total_weight_approved >= weight_threshold` (70%) is now satisfied by the actual live vote set, but `total_weight_rejected` (still containing S's and possibly other flippers' stale weight) also satisfies `total_weight_rejected + weight_threshold > total_weight` (>30% blocking), the coordinator's `if`-`else if` ordering in `signer_coordinator.rs` returns `SignersRejected` first, discarding a block that in reality has already reached quorum approval.
