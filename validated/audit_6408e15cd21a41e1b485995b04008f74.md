## Title
Non-atomic JWT replay check allows duplicate authorization/execution of the same signed workflow trigger request via TOCTOU race - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
The Gateway's HTTP Trigger authorization path checks a JWT's `jti` for replay and then separately records it as used, with no atomicity between the check and the record. Two concurrent requests bearing the identical signed JWT can both pass the "already used" check before either marks it used, letting an unprivileged caller get the same single-use authorized request accepted and executed twice — the same bug class as the reported "double voting": a value meant to be spendable/countable exactly once (a delegated stake / a JWT authorization) is consumed via one path while a race window lets it be reused via another.

### Finding Description
`WorkflowMetadataHandler.Authorize` is the sole authorization gate for the internet-facing HTTP Trigger endpoint (`workflows.execute`), reachable directly from any external, unauthenticated-at-the-network-layer client that holds a valid signer key for a workflow: [1](#0-0) 

The replay protection is implemented as two independent, separately-locked operations on `jwtReplayCache`: [2](#0-1) 

`isReplay` takes an `RLock`, checks membership, and releases the lock; `recordUsage` is only called afterward, near the end of `Authorize`, after the signature has been verified and the signer looked up in `authorizedKeys`. Between the `isReplay` check and the `recordUsage` call there is no lock held across both operations — this is a classic check-then-act race. If two requests carrying the same signed JWT (same `jti`) arrive concurrently, both can observe `isReplay() == false` before either calls `recordUsage`, so both succeed authorization and are both dispatched to the DON as valid, distinct workflow executions.

This authorization result feeds directly into request dispatch: `httpTriggerHandler.authorizeRequest` calls `Authorize` and, on success, proceeds to rate-limit, mark the request ID in-flight, and fan the trigger out to the workflow DON: [3](#0-2) [4](#0-3) 

Note the request-ID uniqueness check (`setupCallback`, line ~402) only dedupes by the outer JSON-RPC request `id`, not by JWT `jti` — so an attacker can send two requests with different outer request IDs but the same JWT/`Auth` token, sidestepping that separate dedup mechanism entirely and relying purely on the racy `jwtReplayCache`.

### Impact Explanation
A single "single-use" signed authorization (JWT) can be replayed to trigger duplicate executions of a workflow. For workflows that perform state-changing or fund-moving actions upon each trigger, this allows an external caller (or even a legitimate signer intentionally racing their own token) to cause the workflow to execute more than once from what should be one authorized invocation — directly analogous to "double voting" with a single credential. This also undermines the very JWT replay guarantee the code explicitly claims to provide ("JWT token has already been used" error), which callers and workflow authors rely on for exactly-once semantics.

### Likelihood Explanation
The race window is small but real and trivially triggerable by an external, unprivileged client: simply fire two requests with an identical `Auth` JWT at (near-)the same time. No special network position or privileged access is required — only knowledge of one valid signed JWT for a workflow (which is by design something the workflow owner/consumer already possesses to trigger it once). Under load or with automation, exploiting a microsecond-scale TOCTOU window is a standard and reliable technique.

### Recommendation
Make the check-and-record atomic: hold a single lock across the `isReplay` check and the `recordUsage` write (e.g., merge them into one `CheckAndRecord`-style method under one critical section, similar to the pattern already used in `core/capabilities/vault/request_replay_guard.go`'s `RequestReplayGuard.CheckAndRecord`, which correctly performs the seen-check and the record under one `mu.Lock()`). Additionally, consider recording the `jti` as used immediately upon signature verification success (before proceeding to authorized-key lookup and dispatch) rather than only after the full authorization completes, to shrink or eliminate any window where a valid signature can be reused.

### Proof of Concept
1. Obtain a valid signed JWT (`req.Auth`) for `workflows.execute` against a registered workflow's authorized signer key.
2. Construct two `jsonrpc.Request[json.RawMessage]` payloads with the same `Auth` token but different outer JSON-RPC `id` values (to bypass the `setupCallback` in-flight `requestID` dedupe).
3. Send both requests concurrently to the gateway's HTTP Trigger endpoint.
4. Both requests call `WorkflowMetadataHandler.Authorize` concurrently; if both reach `isReplay(claims.ID)` before either reaches `recordUsage(claims.ID)`, both are authorized and forwarded to the DON, resulting in two workflow executions from one JWT — contrast with the existing sequential test `TestWorkflowMetadataHandler_Authorize/JWT replay protection`, which only exercises the non-concurrent case and therefore does not catch the race: [5](#0-4)

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```

```go
func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
```
