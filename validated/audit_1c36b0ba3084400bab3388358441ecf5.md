### Title
Instant-withdraw receipts bypass the epoch-loss haircut and are always paid at par, letting losses be socialized onto active LPs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`stopEpochWithDuration`-style partial funding writes a per-epoch haircut into `lossRecoveryPriceByEpoch`, and normal withdraw receipts are forced through `_claimLossAdjustedWithdrawRequest` which pays `claimBasis * lossRecoveryPrice / 1e18`. Instant-withdraw receipts have no equivalent path: `claimInstantWithdrawRequest` burns the full `instantWithdrawsRequests[_user]` balance and pays it 1:1 via `_transferFundedClaim`, regardless of the epoch the receipt belongs to or whether a loss was realized in it. An unprivileged user who routes a withdrawal through the instant path (available when `lastEpochApr > currentApr + instantWithdrawAprDelta` in `IdleCDOEpochVariant.requestWithdraw`, `contracts/IdleCDOEpochVariant.sol:761-769`) escapes any loss haircut that pending normal receipts and active LPs must absorb. This is the vault analog of an out-of-bounds read: the claim reads the aggregate receipt balance with no epoch bounds check, paying out state that should have been truncated by the epoch's recovery price.

### Finding Description
In `IdleCreditVault`, pending normal withdraws are haircutted at funding time: `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = funded * 1e18 / pendingBasis` when the borrower underfunds (`IdleCreditVault.sol:411-421`), and `_claimLossAdjustedWithdrawRequest` applies that price (`IdleCreditVault.sol:789-801`).

Instant receipts are tracked separately in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`), but the claim path is flat:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```
(`IdleCreditVault.sol:387-392`)

There is no `lossRecoveryPriceByEpoch` lookup, no per-epoch bound on what is claimable, and `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` by whatever amount the CDO actually pulls in (`IdleCreditVault.sol:398-403`). Meanwhile `previewLossAdjustedWithdrawFunds` splits `_lossAmount` only between `pendingWithdraws` and the active basis (`IdleCreditVault.sol:440-459`) — the instant bucket is excluded from `pendingBasis`, so instant receipt holders are treated as fully funded senior claimants while the entire realized loss is pushed onto normal pending receipts and active tranche holders.

Additionally, `requestInstantWithdraw` has none of the `requestWithdraw` guards that force a user to claim a stale loss-adjusted receipt before opening a new one (`IdleCreditVault.sol:261-271`), so the epoch-marker protection that exists for normal receipts does not apply to the instant bucket either.

### Impact Explanation
Invariant broken: loss waterfall / fair haircut across receipt holders of the same epoch.

Scenario: APR drops sharply between epochs (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`), enabling instant mode. Attacker calls `IdleCDOEpochVariant.requestWithdraw` during the buffer; the CDO routes it to `creditVault.requestInstantWithdraw`, burning tranche tokens at the pre-loss price. The epoch then stops with a realized loss via `stopEpochWithDuration(_lossAmount)`. Normal pending receipts claim at `lossRecoveryPrice`; active AA/BB LPs take the residual `activeLoss` through the BB-first waterfall. The attacker's instant receipt still claims 100 cents on the dollar. Quantified loss: up to the attacker's full instant receipt amount times `(1 - lossRecoveryPrice)` is shifted onto remaining LPs — e.g. on a 10% epoch loss, a 100k USDC instant request extracts ~10k USDC that should have been haircutted. If the vault is underfunded, early instant claimants drain the balance and later claimants' transfers revert (temporary freezing until the borrower tops up).

### Likelihood Explanation
Likelihood is gated by two conditions: (1) instant-withdraw mode must be enabled (`disableInstantWithdraw == false`, not a programmable borrower) and triggered by an APR decrease exceeding `instantWithdrawAprDelta`; (2) the epoch must settle with a partial funding / realized loss. The attacker needs only a KYC-passing wallet and tranche tokens, and the APR drop that opens the instant window is set by the honest manager/borrower via `setAprs`. The code asymmetry (loss-adjusted path exists for normal receipts, none for instant) makes the payout gap deterministic whenever both conditions hold; the residual uncertainty is whether off-chain operators always fully fund `pendingInstantWithdraws` before claims, which the contracts do not enforce.

### Recommendation
Mirror the normal-receipt flow for instant withdrawals: store an `instantLossRecoveryPriceByEpoch` (or reuse `lossRecoveryPriceByEpoch`) when instant receipts are underfunded at epoch stop, record each user's instant basis per epoch, and have `claimInstantWithdrawRequest` apply the epoch's recovery price instead of paying `instantWithdrawsRequests[_user]` at par. Also port the `requestWithdraw` guard so a user cannot open a new instant request while an unclaimed loss-adjusted instant receipt exists.
