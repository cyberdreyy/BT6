### Title
Front-runnable global policy-ID counter lets an attacker have their own policy silently substituted into a victim's composite policy - ([File: crates/common/precompiles/src/policy/logic/v2.rs])

### Summary
`PolicyRegistryV2` (and `PolicyRegistryV1`) assigns every new policy an ID derived from a single global, shared `next_counter` that any unprivileged caller can advance simply by calling `createPolicy`/`createPolicyWithAccounts`/`createCompositePolicy`. A caller who plans a multi-transaction flow — create one or more child policies, then reference their *predicted* IDs in a follow-up `createCompositePolicy` call — has no guarantee that the predicted ID still belongs to their own policy by the time the composite-creation transaction lands, because any other address can front-run the counter in between.

### Finding Description
`create_policy_inner` reads the registry-wide counter, uses it (unchanged by caller identity) to derive the new policy's ID, and increments it for the next caller: [1](#0-0) 

`createPolicy` and `createPolicyWithAccounts` have no access control — any address can call them and thereby increment the shared counter: [2](#0-1) 

`createCompositePolicy` takes a caller-supplied `child_policy_ids` array and only checks that each referenced ID *exists*, is a *simple* (non-builtin, non-composite) policy — it never checks that the caller (or the composite's `admin`) actually created/owns that child policy: [3](#0-2) [4](#0-3) 

This mirrors the CidNFT `mint`/`add` bug exactly: a client predicts a soon-to-be-assigned sequential ID off-chain (there `_cidNFTID`, here a policy ID from `next_counter`), then submits a follow-up transaction that operates against that predicted ID. Because the ID space is a single monotonically-incrementing counter shared by every caller in the mempool, anyone can front-run the victim's `createPolicy` call, shifting the counter so the victim's actual new policy lands at `predicted_id + 1` while `predicted_id` now belongs to the attacker's own (adversarially-configured) policy.

### Impact Explanation
Unlike the original CidNFT report (which only causes a revert), here the outcome can be a **silent misconfiguration of access control** rather than a revert:
1. Victim submits `createPolicy` for child A, expecting ID `N`.
2. Attacker front-runs with their own `createPolicy` call, taking ID `N` for an attacker-controlled ALLOWLIST/BLOCKLIST policy (e.g. one that authorizes every address, or blocks none).
3. Victim's child policy is actually created at ID `N+1`.
4. Victim's already-prepared `createCompositePolicy(admin, UNION/INTERSECT, [N, ...])` transaction executes; `validate_composite_child_policies` finds ID `N` exists and is a simple policy, so it happily accepts the *attacker's* policy as a child of the victim's composite gate.
5. The resulting composite — used to gate B-20 token transfers/mints via `isAuthorized` — now silently includes an attacker-chosen authorization rule (e.g. a UNION composite that now authorizes everyone because the attacker's substituted child allows all), defeating the intended access-control policy for whatever B-20 asset or feature relies on it.

This is a genuine unauthorized-operation / broken-access-control outcome (medium severity), not merely griefing, since anyone reachable from an unprivileged transaction can corrupt another user's composite policy semantics without reverting.

### Likelihood Explanation
`createPolicy`/`createPolicyWithAccounts`/`createCompositePolicy` are unauthenticated precompile calls reachable by any EOA sending an ordinary transaction, so front-running the shared counter requires no special privilege — only observing the victim's pending transaction and paying a higher fee, exactly as in the original report's PoC. Any workflow that predicts a policy ID client-side before broadcasting a dependent transaction (a natural pattern given `createPolicy` returns the ID only in its return value/event) is exposed.

### Recommendation
Do not let composite creation (or any downstream consumer) trust caller-predicted policy IDs computed off-chain against a shared counter. Options:
- Require `createCompositePolicy`/`updateComposite` to verify the caller (or `admin`) is the admin of each referenced child policy, closing the "wrong owner substituted" class of exploit even under counter front-running.
- Or make ID assignment scoped per-creator (e.g. derive from `(creator, nonce)`) instead of a single global monotonic counter, matching the CidNFT fix pattern of decoupling the assigned ID from execution order.

### Proof of Concept
1. Alice sends `createPolicy(ALICE, ALLOWLIST)` intending to later reference the resulting ID (predicted as `next_counter` read off-chain) inside a follow-up `createCompositePolicy(ALICE, UNION, [predicted_id, otherChild])`.
2. Attacker observes Alice's pending `createPolicy` tx and front-runs it with their own `createPolicy(ATTACKER, ALLOWLIST)` call, consuming `predicted_id` for a policy they control (e.g. one they later populate to allow every address via `updateAllowlist`).
3. Alice's `createPolicy` mines afterward, actually creating her policy at `predicted_id + 1`.
4. Alice's already-signed `createCompositePolicy([predicted_id, otherChild])` mines; `validate_composite_child_policies` (crates/common/precompiles/src/policy/logic/v2.rs:130-150) only checks existence/type, so it accepts the attacker's policy as `predicted_id`'s referent.
5. Alice's UNION composite policy now silently includes the attacker's policy, which the attacker can update via `updateAllowlist` at will (since they are its admin) to make the composite always-authorize, undermining whatever gate Alice intended (e.g. a B-20 token transfer restriction).

    /// Requires every composite child to be a created, custom, simple policy. Two passes so
    /// `PolicyNotFound` (any non-existent child) takes precedence over `InvalidChildPolicy`
    /// (a built-in sentinel or a composite) across the whole set — the canonical revert order.
    fn validate_composite_child_policies<S: PolicyAccounting>(
        &self,
        storage: &S,
        child_policy_ids: &[u64],
    ) -> Result<()> {
        for &child in child_policy_ids {
            // Reverts PolicyNotFound when the child does not exist.
            self.require_existing_policy(storage, child)?;
        }
        for &child in child_policy_ids {
            if Self::is_builtin(child) || Self::is_composite(child) {
                return Err(BasePrecompileError::revert(IPolicyRegistry::InvalidChildPolicy {
                    childPolicyId: child,
                }));
            }
        }
        Ok(())
    }

    /// Shared creation core after inputs have been validated.
    fn create_policy_inner<S: PolicyAccounting>(
        &self,
        storage: &mut S,
        admin: Address,
        policy_type: PolicyType,
        policy_type_u8: u8,
    ) -> Result<u64> {
        let counter = self.ensure_initialized_and_get_counter(storage)?;
        let is_counter_overflowed = counter >= Self::COUNTER_MASK;
        if is_counter_overflowed {
            return Err(BasePrecompileError::under_overflow());
        }
        storage.write_next_counter(counter + 1)?;
        let policy_id = Self::make_id(policy_type_u8, counter);
        storage.write_policy_word(policy_id, PackedPolicy::new(admin).into_u256())?;

    fn create_composite_policy(
        &self,
        storage: &mut S,
        admin: Address,
        policy_type: PolicyType,
        child_policy_ids: Vec<u64>,
    ) -> Result<u64> {
        if admin == Address::ZERO {
            return Err(BasePrecompileError::revert(IPolicyRegistry::ZeroAddress {}));
        }
        if !matches!(policy_type, PolicyType::UNION | PolicyType::INTERSECT) {
            return Err(BasePrecompileError::revert(IPolicyRegistry::IncompatiblePolicyType {}));
        }
        Self::require_child_policy_in_range(&child_policy_ids)?;
        self.validate_composite_child_policies(storage, &child_policy_ids)?;

        // Reuse the simple create core for counter/ID/PolicyCreated+PolicyAdminUpdated events.
        let policy_id =
            self.create_policy_inner(storage, admin, policy_type, policy_type.as_discriminant())?;
        storage.write_children(policy_id, &child_policy_ids)?;
        storage.emit_event(
            IPolicyRegistry::CompositePolicyUpdated {
                policyId: policy_id,
                updater: storage.caller(),
                childPolicyIds: child_policy_ids,
            }
            .encode_log_data(),
        )?;
        Ok(policy_id)
    }
