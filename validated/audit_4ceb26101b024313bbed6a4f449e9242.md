### Title
Front-runnable `CreateAccount` on eth-implicit-shaped top-level ids permanently prevents (or hijacks) eth-implicit wallet-contract installation - (File: runtime/runtime/src/actions.rs)

### Summary
`action_create_account` only checks `AccountId::is_top_level()` / `is_sub_account_of()`, never `get_account_type()`, so an ordinary attacker can submit an explicit `CreateAccount` action naming an id that has the exact eth-implicit shape (`0x` + 40 lowercase hex, 42 chars total). Because `min_allowed_top_level_account_length` (32 on mainnet) is smaller than 42, this passes as an ordinary top-level named account creation with no registrar requirement, pre-empting the legitimate secp256k1 keyholder's implicit-account-creation-transfer path.

### Finding Description
`action_create_account` (`runtime/runtime/src/actions.rs:167-210`) validates an account id purely on `is_top_level()` (no `.` and not `system`) and, for short top-level ids, on `predecessor_id == registrar_account_id`. It never calls `get_account_type()`, so it cannot distinguish a normal named id from one that is structurally an eth-implicit id (`0x` + 40 hex, checked by `is_eth_implicit`, priority-ordered ahead of "Named" in `get_account_type`). [1](#0-0) 

Because eth-implicit ids are 42 characters, they exceed `min_allowed_top_level_account_length` (32 on mainnet), so the registrar-only branch is skipped entirely and the id is accepted as an ordinary top-level account: [2](#0-1) 

By contrast, the legitimate path for such an id is `action_implicit_account_creation_transfer`, which branches on `account_id.get_account_type()` and, for `AccountType::EthImplicitAccount`, installs `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))`: [3](#0-2) 

This implicit-creation path is only taken when the account does not yet exist (per `check_account_existence`/`account_is_implicit`, `core/primitives/src/utils.rs:471-477`). If an attacker submits `CreateAccount{account_id: "0x...40hex"}` (optionally followed, in the same receipt, by `AddKey` with the attacker's own key, since the first `CreateAccount` action makes the attacker the acting predecessor for subsequent actions in the receipt), the account is materialized with `AccountContract::None` and either no keys or an attacker-controlled key. When the real secp256k1 keyholder later sends `Transfer` to that same derived address, the account already exists, so it is treated as a plain transfer into an existing account rather than triggering `action_implicit_account_creation_transfer` — the eth-wallet Global contract is never attached, and if the attacker added their own key, the attacker (not the eth keyholder) now controls the deposited funds. [4](#0-3) 

No existing check stops this: `is_top_level()`/`is_sub_account_of()` are purely structural (no-dot check), and there is no explicit rejection of implicit/deterministic-shaped ids at the `CreateAccount` call site.

### Impact Explanation
This breaks the authorization-exactness invariant of eth-implicit accounts: an unprivileged attacker can pre-empt or hijack an address that is supposed to be exclusively controllable by the corresponding secp256k1 key. In the minimal case, the attacker only griefs (permanently freezes) subsequent deposits to that address, since the resulting bare account has neither the wallet contract nor a usable key. In the aggravated case (attacker adds their own key via a follow-up `AddKey` action in the same receipt), the attacker gains outright custody of any future deposit sent to the derived eth address, i.e. theft of funds. This matches the NEAR bounty categories of "permanent freezing of user funds" and "theft of user funds" via authorization escalation.

### Likelihood Explanation
Preconditions are minimal and mainnet-realistic: `min_allowed_top_level_account_length = 32 < 42`, so no registrar involvement is needed for the eth-implicit-shaped id; the attacker only needs any funded account able to pay gas for a `CreateAccount` (+ optional `AddKey`) transaction, and needs to know/guess the target eth-implicit address in advance (e.g., a publicly advertised deposit address). This is fully repeatable and requires no validator/node access, no leaked keys.

### Recommendation
In `action_create_account`, reject account ids whose `get_account_type()` is not `AccountType::NamedAccount` (i.e., reject `EthImplicitAccount`, `NearImplicitAccount`, `NearDeterministicAccount` shapes) regardless of `is_top_level()`/length, so these ids can only be created through the dedicated implicit-account-creation-transfer path.

### Proof of Concept
Integration/apply-level test:
1. Genesis with mainnet-like `min_allowed_top_level_account_length = 32`.
2. Attacker account submits a receipt with actions `[CreateAccount, AddKey(attacker_pubkey)]` targeting `account_id = "0x" + 40 lowercase hex` (a valid eth-implicit shape not derived from any real key).
3. Apply the receipt; assert the account now exists with `AccountContract::None` and an access key controlled by the attacker.
4. Simulate the legitimate eth keyholder sending `Transfer` to the same `account_id` (implicit-account-creation-transfer path).
5. Assert `account.contract() != AccountContract::Global(eth_wallet_global_contract_hash(chain_id))` and that the attacker's `AddKey` still has full access — demonstrating the deposited funds are now under attacker control / the wallet contract is never installed.

pub(crate) fn action_implicit_account_creation_transfer(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    fee_config: &RuntimeFeesConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    deposit: Balance,
    block_height: BlockHeight,
    epoch_info_provider: &dyn EpochInfoProvider,
) {
    *actor_id = account_id.clone();
    match account_id.get_account_type() {
        AccountType::NearImplicitAccount => {
            let mut access_key = AccessKey::full_access();
            access_key.nonce = initial_nonce_value(block_height);

            // unwrap: here it's safe because the `account_id` has already been determined to be implicit by `get_account_type`
            let public_key = PublicKey::from_near_implicit_account(account_id).unwrap();

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,
                AccountContract::None,
                fee_config.storage_usage_config.num_bytes_account
                    + public_key.trie_id_len() as u64
                    + borsh::object_length(&access_key).unwrap() as u64
                    + fee_config.storage_usage_config.num_extra_bytes_record,
            ));

            set_access_key(state_update, account_id.clone(), public_key, &access_key);
        }
        // Invariant: The `account_id` is implicit.
        // It holds because in the only calling site, we've checked the permissions before.
        AccountType::EthImplicitAccount => {
            let chain_id = epoch_info_provider.chain_id();

            // Use a deployed global contract for ETH implicit accounts.
            let global_contract_hash = eth_wallet_global_contract_hash(&chain_id);
            let storage_usage = fee_config.storage_usage_config.num_bytes_account
                + global_contract_hash.as_bytes().len() as u64;

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,

pub fn account_is_implicit(account_id: &AccountId, eth_implicit_accounts_enabled: bool) -> bool {
    if eth_implicit_accounts_enabled {
        account_id.get_account_type().is_implicit()
    } else {
        account_id.get_account_type() == AccountType::NearImplicitAccount
    }
}

/// Returns hex-encoded copy of the public key.
/// This is a NEAR-implicit account ID which can be controlled by the corresponding ED25519 private key.
pub fn derive_near_implicit_account_id(public_key: &ED25519PublicKey) -> AccountId {
    hex::encode(public_key).parse().unwrap()
}

/// Returns '0x' + keccak256(public_key)[12:32].hex().
/// This is an ETH-implicit account ID which can be controlled by the corresponding Secp256K1 private key.
pub fn derive_eth_implicit_account_id(public_key: &Secp256K1PublicKey) -> AccountId {
    use sha3::Digest;
    let pk_hash = sha3::Keccak256::digest(&public_key);
    format!("0x{}", hex::encode(&pk_hash[12..32])).parse().unwrap()
}
