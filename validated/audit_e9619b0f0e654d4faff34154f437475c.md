### Title
Harvested-reward vesting and same-block protection rely on `block.number` as a time source, which misprices tranche redemptions on non-Ethereum chains - (File: contracts/strategies/BaseStrategy.sol, contracts/IdleCDO.sol)

### Summary
`BaseStrategy` and the `IdleCDO` harvest/withdrawal path measure elapsed time in **blocks** (`latestHarvestBlock`, `releaseBlocksPeriod`, `_lastCallerBlock`) rather than seconds. The repo explicitly ships chain-specific deployments (`contracts/optimism/`, `contracts/arbitrum/`, `contracts/polygon/`, `contracts/polygon-zk/`, `contracts/avax/`, `contracts/base/`). On chains like Optimism where `block.number` advances once per transaction and does not map to wall-clock time, the reward-release window and the mint/redeem same-block guard deviate from design, letting an unprivileged user mint tranche tokens at a price that excludes locked rewards and redeem them after release, capturing yield belonging to existing holders.

### Finding Description
Strategies record the block of the last reward swap and linearly unlock the harvested LP tokens over `releaseBlocksPeriod` blocks:

```solidity
// contracts/strategies/mstable/IdleMStableStrategy.sol:316-324 (same pattern in
// contracts/polygon/strategies/mstable/IdleMStableStrategyPolygon.sol:315-323 and BaseStrategy)
function _lockedLpTokens() internal view returns (uint256 _locked) {
    uint256 _releaseBlocksPeriod = releaseBlocksPeriod;
    uint256 _blocksSinceLastHarvest = block.number - latestHarvestBlock;
    uint256 _totalLockedLpTokens = totalLpTokensLocked;
    if (_totalLockedLpTokens > 0 && _blocksSinceLastHarvest < _releaseBlocksPeriod) {
        _locked = _totalLockedLpTokens * (_releaseBlocksPeriod - _blocksSinceLastHarvest) / _releaseBlocksPeriod;
    }
}

Locked rewards are subtracted from the strategy/CDO NAV, so the tranche price during the vesting window is intentionally understated. `releaseBlocksPeriod` is configured assuming a constant block time (~12s on mainnet). The same flawed assumption protects the CDO itself:

```solidity
// contracts/IdleCDO.sol:1015-1023
function _updateCallerBlock() internal {
    _lastCallerBlock = keccak256(abi.encodePacked(tx.origin, block.number));
}
function _checkSameBlock() internal view {
    if (keccak256(abi.encodePacked(tx.origin, block.number)) == _lastCallerBlock) revert SameBlock();
}
``` [3](#0-2) 

On Optimism-style L2s every transaction is its own block, so `block.number - latestHarvestBlock` grows with transaction count, not time; the vesting period can elapse in far less real time than intended, or stretch arbitrarily when sequencer activity is low. The minted-interest variants (`isInterestMinted` flows) and epoch variants inheriting `IdleCDO` share the same harvest/NAV accounting, so credit vaults deployed on these chains inherit the mispriced window.

### Impact Explanation
The invariant broken is fair mint/burn around harvested yield. When `block.number` advances slower than assumed relative to real time (low-activity L2 periods, chains anchoring `block.number` to L1), rewards stay locked longer than the intended duration: users who withdraw during the extended window redeem at a price excluding the locked rewards, forfeiting their share. An attacker (any KYC-passed lender / tranche holder) who remains deposited until `_lockedLpTokens()` returns 0 captures the forfeited portion — direct theft of unclaimed yield proportional to `totalLpTokensLocked` and the amount withdrawn during the lock. When `block.number` advances faster than assumed, the anti-dilution smoothing collapses, and the `_checkSameBlock`/`_minterBlock` protection (which assumes "same block" ≈ "same instant") no longer reflects the real-time window it was designed for on per-tx blockchains.

Quantified loss: up to the full `totalLpTokensLocked` harvested amount per harvest, split among withdrawers during the miscalibrated lock window and capturable by an attacker who times entry/exit around the release boundary.

### Likelihood Explanation
The contracts are explicitly multi-chain (dedicated `optimism/` and `arbitrum/` subtrees), and `releaseBlocksPeriod` is set via `setReleaseBlocksPeriod` in block units regardless of chain. The attacker is unprivileged: deposit before/inside the lock window, wait for `block.number - latestHarvestBlock >= releaseBlocksPeriod`, redeem. No privileged misbehavior is needed; the miscalculation is inherent to using block deltas as a clock on chains without constant block times. Likelihood is medium: it requires a harvest with nonzero `totalLpTokensLocked` plus predictable relative block progression, but requires no exploit primitives beyond normal `depositAA/BB`/`withdrawAA/BB` calls.

### Recommendation
Replace block-based time measurement with `block.timestamp`:
- Store `latestHarvestTimestamp` and compute release progress as `block.timestamp - latestHarvestTimestamp` over a `releasePeriod` expressed in seconds.
- In `IdleCreditVaultImpliedPrice._accruedGain`, the code already mixes units (`block.timestamp - cdo.latestHarvestBlock()` at contracts/IdleCreditVaultImpliedPrice.sol:71) — ensure the stored value is a timestamp consistently across all variants.
- Keep `_checkSameBlock` as an anti-atomicity check if desired, but do not rely on block deltas for any duration-sensitive accounting on L2 deployments.

### Proof of Concept
Foundry fork test sketch (mainnet-style CDO with an mstable/BaseStrategy-derived strategy, simulating an L2-style block cadence via `vm.roll`/`vm.warp` divergence):

```solidity
// test/foundry/BlockNumberVesting.t.sol — sketch
// 1. Seed the CDO: victim deposits 1000e18 via depositAA (KYC'd lender).
// 2. Owner harvests: strategy swaps rewards, sets latestHarvestBlock = block.number,
//    totalLpTokensLocked = harvested balance. Price now excludes locked rewards.
// 3. Simulate slow-block chain: vm.warp(+intended seconds) but vm.roll(block.number + k)
//    with k < releaseBlocksPeriod — rewards remain locked despite the intended
//    time having elapsed. Victim withdraws all AA; receives NAV minus locked share.
// 4. Attacker (fresh EOA, no privilege) stays deposited, vm.roll past
//    releaseBlocksPeriod so _lockedLpTokens() == 0, then withdraws — captures the
//    victim's forfeited reward share. Assert attackerEndBalance > attackerFairShare.
// Symmetric case: vm.roll(block.number + releaseBlocksPeriod) with vm.warp(+1s)
// shows the full vesting completing in ~1 real second, voiding the smoothing window
// and the _checkSameBlock timing assumption on per-tx-block chains.
```
