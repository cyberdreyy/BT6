## Analysis

The reported Solidity bug pattern is: a reward-accounting accumulator (`totalTokenRewardsPerStake`) is incremented when funds enter the reward pool, but a code path that moves funds back out (`migrateToken`) never decrements/reconciles that accumulator, so the pool's bookkeeping becomes permanently out of sync with real balances, causing stakers to be over/under credited.

The closest analog in this agave codebase is the `pending_delegator_rewards` field on `VoteStateV4`, used for SIMD-0123 block-revenue delegator rewards.

### Root cause

- `deposit_delegator_rewards` transfers lamports into a vote account and *increments* `pending_delegator_rewards` via `add_pending_delegator_rewards`: [1](#0-0) 
- The only mutator exposed on the vote-state handler for this field is the adder; there is no corresponding subtractor/decrementer anywhere in the handler: [2](#0-1) 
- A repository-wide search for any decrement of `pending_delegator_rewards` (`sub_...`, `-=`, `checked_sub`, `set_pending_delegator_rewards`) returns no matches, confirming the field is write-once-increment-only.
- `calculate_block_reward`, used every epoch during partitioned reward calculation, reads the *current* (undiminished) `pending_delegator_rewards` value and distributes a proportional share of it to every active delegator based on `stake / total_active_stake`: [3](#0-2) 
- Those block rewards are then minted directly into stake accounts via `checked_add_lamports`, with no corresponding debit against the vote account or against `pending_delegator_rewards`: [4](#0-3) 

Because `pending_delegator_rewards` is never reduced after being paid out, the *same* deposited amount is used as the numerator for `calculate_block_reward` again in the next epoch (and every epoch thereafter), so delegators are paid the same reward pool repeatedly — this is functionally identical to `totalTokenRewardsPerStake` not being updated on a token movement: the accounting value that should shrink as funds are distributed never does, permanently desynchronizing the "amount owed" bookkeeping from the "amount actually paid" reality.

### Reachability

This is reachable by any ordinary user/validator withdrawer through the standard `DepositDelegatorRewards` vote instruction (guarded only by feature flags `commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`), followed by the automatic, non-privileged, per-epoch reward-distribution path that every validator's bank executes.

### Confidence / caveats

I was not able to fully trace whether `pending_delegator_rewards` is reset elsewhere (e.g., at epoch-boundary snapshot time, inside `EpochInflationAccountState`, or via a mechanism outside the files I inspected) due to the size of the reward-distribution code and my search budget. The `calculate_block_reward` docstring itself acknowledges recomputation across "recalculation" without resetting the source value, which supports the finding, but I could not exhaustively rule out an offsetting mechanism elsewhere in `runtime/src/bank/partitioned_epoch_rewards/` or `runtime/src/inflation_rewards/`. Given the ask-only scope and search-tool limits, I recommend a Devin session with full repository access to confirm whether any epoch-boundary reset of `pending_delegator_rewards` exists before treating this as a confirmed, exploitable finding.

### Title
Vote account `pending_delegator_rewards` is incremented on deposit but never decremented after block-reward distribution, causing repeated over-distribution of delegator rewards - (File: `programs/vote/src/vote_state/handler.rs`, `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`VoteStateV4::pending_delegator_rewards` tracks lamports deposited via `DepositDelegatorRewards` (SIMD-0123) that are owed to delegators as block-revenue rewards. The vote-state handler only exposes an incrementer (`add_pending_delegator_rewards`); no decrementer exists anywhere in the codebase. The per-epoch `calculate_block_reward` function computes each delegator's share directly from this field without ever reducing it once rewards are paid, so the same deposited pool is redistributed every subsequent epoch.

### Finding Description [5](#0-4)  shows the only write path for `pending_delegator_rewards` is additive. `deposit_delegator_rewards` [6](#0-5)  calls this adder after transferring lamports in. `calculate_block_reward` [3](#0-2)  reads `vote_state.pending_delegator_rewards()` fresh every epoch to compute the amount owed per stake account, and `build_updated_stake_reward` mints that amount directly into stake accounts [4](#0-3)  without any corresponding write back to the vote account's `pending_delegator_rewards`.

### Impact Explanation
A single `DepositDelegatorRewards` deposit is treated as still fully "pending" in every subsequent epoch's reward calculation, so the same funds get paid out to stakers repeatedly. This both inflates SOL paid to stakers beyond what was actually deposited (fund creation / unauthorized state mutation) and keeps the vote account's withdrawal floor (`withdraw` checks `pending_delegator_rewards` before allowing withdrawal, `programs/vote/src/vote_state/mod.rs:1079-1121`) permanently and incorrectly elevated, potentially blocking legitimate withdrawer operations indefinitely.

### Likelihood Explanation
High, if no offsetting reset exists elsewhere: any validator that ever calls `DepositDelegatorRewards` (a normal, unprivileged, feature-gated instruction) will trigger this every epoch thereafter with no additional attacker action required.

### Recommendation
Decrement `pending_delegator_rewards` by the amount actually distributed as block reward at partition-distribution time (or at epoch-boundary calculation time), mirroring how `stake_reward_lamports_minted`/`distributed_rewards` are tracked and subtracted from the `EpochRewards` sysvar elsewhere in this same module.

### Proof of Concept
1. Enable `commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing` features.
2. Call `DepositDelegatorRewards` on a vote account with amount `D`, setting `pending_delegator_rewards = D`.
3. Advance one epoch; verify (via the harness in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` tests, e.g. `get_block_reward_for_test`) that stake accounts are paid `~D` in block rewards.
4. Advance a second epoch without any further deposit; observe `pending_delegator_rewards` is still `D` (no test in the codebase asserts it is reduced), and stake accounts are paid `~D` again, doubling the total payout relative to the single deposit.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
