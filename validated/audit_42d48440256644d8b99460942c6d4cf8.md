## Finding confirmed

### Title
`Busy` status can be wedged permanently because `#[callback]`-typed callbacks panic on promise failure before clearing status - (File: `lockup/src/owner_callbacks.rs`)

### Summary
`refresh_staking_pool_balance` and `withdraw_all_from_staking_pool` set `TransactionStatus::Busy` and then schedule a cross-contract call whose result is consumed by `on_get_account_total_balance` / `on_get_account_unstaked_balance_to_withdraw_by_owner`. Both callbacks take their result via a `#[callback]`-annotated argument rather than checking `is_promise_success()`, so when the inner staking-pool call fails, near-sdk's generated wrapper panics while decoding the failed promise result *before* the function body runs, meaning `self.set_staking_pool_status(TransactionStatus::Idle)` is never reached. `Busy` is left set forever, and every subsequent staking method plus `unselect_staking_pool` panics via `assert_staking_pool_is_idle` / `assert_no_staking_or_idle`.

### Finding Description
The claimed invariant is: for every call that does `set_staking_pool_status(Busy)` before a `Promise`, the attached callback *always* executes and eventually sets status back to `Idle` — i.e. `Busy_transitions == Idle_transitions` should hold after the callback fires, regardless of the outer promise's success or failure.

Compare the two callback styles in `lockup/src/owner_callbacks.rs`:
- Deposit/stake/unstake/withdraw callbacks (`on_staking_pool_deposit`, `on_staking_pool_stake`, etc.) take the amount as a plain argument and call `is_promise_success()` internally, so they run and clear `Busy` regardless of whether the inner call succeeded or failed: [1](#0-0) 
- `on_get_account_total_balance`, called from `refresh_staking_pool_balance`, instead takes `#[callback] total_balance: WrappedBalance` and only sets `Idle` inside the body: [2](#0-1) 
- Likewise `on_get_account_unstaked_balance_to_withdraw_by_owner`, called from `withdraw_all_from_staking_pool`, takes `#[callback] unstaked_balance: WrappedBalance` and only sets `Idle` in the "no balance to withdraw" branch: [3](#0-2) 

Both are preceded by `self.set_staking_pool_status(TransactionStatus::Busy)` before the promise is scheduled: [4](#0-3)  and [5](#0-4) .

Under near-sdk's `#[callback]` codegen (used here, `near-sdk 3.1.0`), if the awaited promise result is `PromiseResult::Failed`, the generated method wrapper panics while trying to decode the (non-existent) successful payload — this happens *before* `assert_self()` or any of the method body executes. So if the staking pool the owner selected (an account the owner/attacker fully controls, since `LockupFactory::create` is open and payable to anyone: `select_staking_pool` only requires the target be present on `staking_pool_whitelist_account_id`, not that it behaves correctly) makes `get_account_total_balance` or `get_account_unstaked_balance` fail, the corresponding callback never runs its body and `Busy` is never reset.

Once stuck, every guard downstream keeps rejecting further calls: [6](#0-5)  is used by `deposit_to_staking_pool`, `deposit_and_stake`, `withdraw_from_staking_pool`, `refresh_staking_pool_balance`, `stake`, `unstake`, `unstake_all`, and `unselect_staking_pool`, so all of them permanently panic with "Contract is currently busy with another operation" once `Busy` is wedged.

None of the existing guards (`assert_owner`, `assert_self()`, `is_promise_success()`, `assert_staking_pool_is_idle`) prevent this, because the panic happens in the SDK-generated wrapper before `assert_self()` is even reached — the method body, including any assertion, is skipped entirely.

The `release_duration ~ u64::MAX` detail mentioned in the question is not actually a precondition for this bug: the wedge occurs purely from the `#[callback]` vs. `is_promise_success()` inconsistency between callbacks and is independent of the lockup's release schedule parameters.

### Impact Explanation
Once `Busy` is wedged, the affected lockup account can never again call any staking method or `unselect_staking_pool`. If the owner already has funds deposited/staked on the (now unreachable, or intentionally reverting) staking pool, those funds — and the remaining liquid balance controlled through this lockup — become permanently inaccessible through the contract's owner interface, since `assert_no_staking_or_idle` also blocks `transfer` and `add_full_access_key`. This matches the "Critical - funds permanently frozen" category. The affected party is the lockup owner (who could be the attacker's own account, or, if a real vesting recipient ever selects an unreliable/misbehaving pool, an innocent user relying on a Foundation-issued lockup). The condition is repeatable per-lockup: any owner who deploys or selects a pool that fails `get_account_total_balance`/`get_account_unstaked_balance` triggers it, and it cannot be reversed once triggered — there is no method in `owner.rs`/`foundation.rs` that resets `staking_information.status` back to `Idle` without going through the vulnerable callback path.

### Likelihood Explanation
Any account holder can call `LockupFactory::create` to become the owner of their own lockup, and `select_staking_pool` only checks the target against the whitelist contract, not that it behaves correctly — an attacker who also controls (or has whitelisted) a pool account can make it revert on `get_account_total_balance`/`get_account_unstaked_balance` calls. Triggering `refresh_staking_pool_balance` or `withdraw_all_from_staking_pool` against such a pool costs a single low-gas transaction. This is deterministic and reproducible on any lockup, at any time after a staking pool is selected, with no special privileges required beyond being the lockup owner (a position anyone can hold via the open factory).

### Recommendation
Change `on_get_account_total_balance` and `on_get_account_unstaked_balance_to_withdraw_by_owner` to consume the promise result via `is_promise_success()` / `env::promise_result(0)` instead of a `#[callback]`-typed argument, mirroring the pattern already used in `on_staking_pool_deposit`, `on_staking_pool_stake`, etc., so that `set_staking_pool_status(TransactionStatus::Idle)` executes unconditionally regardless of whether the inner promise succeeded or failed.

// lockup/src/owner_callbacks.rs (unit test style, near-sdk testing_env!)
#[test]
fn test_busy_wedged_on_refresh_balance_failure() {
    let (mut context, mut contract) = lockup_only_setup();
    context.predecessor_account_id = account_owner();
    testing_env!(context.clone());

    // select + whitelist pool as in test_staking_pool_success
    contract.select_staking_pool("staking_pool".to_string());
    context.predecessor_account_id = lockup_account();
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(b"true".to_vec()));
    contract.on_whitelist_is_whitelisted(true, "staking_pool".to_string());

    // refresh_staking_pool_balance sets Busy
    context.predecessor_account_id = account_owner();
    testing_env!(context.clone());
    contract.refresh_staking_pool_balance();

    // Binding to test: Busy_set == true here.
    // Simulate the staking pool call FAILING.
    context.predecessor_account_id = lockup_account();
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);

    // This call panics inside the near-sdk `#[callback]` wrapper
    // BEFORE assert_self()/set_staking_pool_status(Idle) runs.
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        contract.on_get_account_total_balance(0.into());
    }));
    assert!(result.is_err()); // panics: "Callback computation failed"

    // Binding check: status is STILL Busy (never reset to Idle).
    context.predecessor_account_id = account_owner();
    testing_env!(context.clone());
    let result2 = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        contract.unselect_staking_pool();
    }));
    assert!(result2.is_err()); // panics: "Contract is currently busy with another operation"
    // Repeat for deposit_to_staking_pool / stake / unstake / withdraw_from_staking_pool -> all panic forever.
}

    pub fn assert_no_staking_or_idle(&self) {
        if let Some(staking_information) = &self.staking_information {

                TransactionStatus::Idle => (),
                TransactionStatus::Busy => {
                    env::panic(b"Contract is currently busy with another operation")
                }
            };
        }
    }
