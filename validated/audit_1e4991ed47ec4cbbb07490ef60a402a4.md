### Title
Loss-adjusted withdraw receipt is paid at par when the user files a second request — `lastWithdrawRequest` overwrite orphans the haircut epoch (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The expat bug is a shared structure (DTD) destroyed while a second parser still references it. The credit-vault analog is the per-user withdraw ledger: `_claimLossAdjustedWithdrawRequest` can only locate a loss-adjusted receipt through the single shared marker `lastWithdrawRequest[_user]`. A second `requestWithdraw` overwrites that marker, so the haircut epoch's entry in `withdrawsRequestsByEpoch` is never cleared through the loss path; instead the full (un-haircutted) amount remains inside the aggregate `withdrawsRequests[_user]` and is paid at par by `_claimFundedWithdrawRequest`, even though `collectWithdrawFunds` only pulled `amount * lossRecoveryPrice / RECOVERY_FULL` from the CDO.

### Finding Description
- `requestWithdraw` accrues into `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) .
- On a realized loss, `collectWithdrawFunds` receives only `pendingBasis * price`, zeroes `pendingWithdraws`, and stores `lossRecoveryPriceByEpoch[epochNumber]` — but the per-user basis stays inside `withdrawsRequests`/`withdrawsRequestsByEpoch` [2](#0-1) .
- The recovery path `_claimLossAdjustedWithdrawRequest` looks up the loss epoch solely via `lastWithdrawRequest[_user]`; if that epoch has no stored price it returns 0 and never iterates older epochs [3](#0-2) .
- `_claimFundedWithdrawRequest` then pays the entire `withdrawsRequests[_user]` aggregate at par once `epochNumber > lastWithdrawRequest[_user]`, burning the same amount of receipt tokens [4](#0-3) .
- Nothing in `requestWithdraw` or `claimWithdrawRequest` checks for a still-unclaimed loss-adjusted epoch before overwriting the marker or paying the aggregate. The stale `withdrawsRequestsByEpoch[user][lossEpoch]` entry remains non-zero forever, which is the "freed" state that is still referenced by the aggregate counter.

### Impact Explanation
Direct theft / insolvency: a user whose epoch-N receipt was haircut to price `p < RECOVERY_FULL` recovers the full par amount `X` instead of `X*p`. The strategy only holds `X*p` of borrower funding for that receipt, so the excess `(1-p)*X` is paid out of underlyings belonging to other funded claimants and the default-recovery reserve guard in `_transferFundedClaim` does not help — the balance check passes as long as other users' money is present [5](#0-4) . Loss scales with the receipt size and haircut: e.g. a 1M USDC receipt at a 50% recovery price yields a ~500k USDC overpayment.

### Likelihood Explanation
Requirements are all unprivileged and ordinary: (1) the attacker holds tranche tokens and files `requestWithdraw`, (2) an epoch ends with a realized loss via `stopEpochWithDuration`/`collectWithdrawFunds` partial funding — a normal, expected vault event, not an attacker-controlled precondition, (3) the attacker files a second small `requestWithdraw` in the next buffer period and waits one epoch. No privileged cooperation, no timing race, and no existing guard (`_onlyIdleCDO`, `NotAllowed` epoch gate, reserve check) blocks it; the funded-claim path is explicitly designed to pay `withdrawsRequests[_user]` in full.

### Recommendation
In `requestWithdraw`, revert or route through the loss-claim path when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` (i.e., force the user to settle the haircutted receipt before opening a new one), or track loss-adjusted claims in a per-epoch structure independent of the single `lastWithdrawRequest` marker so `_claimLossAdjustedWithdrawRequest` can iterate all epochs with `withdrawsRequestsByEpoch[_user][e] != 0` and a non-zero `lossRecoveryPriceByEpoch[e]`.

### Proof of Concept
Foundry fork sketch against `IdleCreditVault` + `IdleCDOEpochVariant`:

```solidity
// epoch 0 running; attacker holds AA tranches worth X underlying
cdoEpoch.requestWithdraw(X, address(AAtranche));      // lastWithdrawRequest[att] = 0
// manager stops epoch with a realized loss; borrower funds only X*p
cdoEpoch.stopEpochWithDuration(lossApr, lossAmount);  // collectWithdrawFunds(X*p)
// strategy state: pendingWithdraws = 0, lossRecoveryPriceByEpoch[0] = p < RECOVERY_FULL,
// but withdrawsRequests[att] = X and withdrawsRequestsByEpoch[att][0] = X still set

// next buffer period: attacker files a dust request, overwriting the marker
cdoEpoch.requestWithdraw(1, address(AAtranche));      // lastWithdrawRequest[att] = 1

// epoch 1 stops normally; epochNumber becomes 2
cdoEpoch.stopEpoch(apr, 0);

// claimWithdrawRequest: loss path reads lastWithdrawRequest=1 -> price 0 -> returns 0
// funded path pays withdrawsRequests[att] = X + 1 AT PAR
uint256 pre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
assertEq(underlying.balanceOf(attacker) - pre, X + 1); // expected X*p + 1
// invariant broken: strategy paid X+1 but only received X*p + 1 of funding;
// shortfall (1-p)*X drained from other funded claims / reserve
assertEq(strategy.withdrawsRequestsByEpoch(attacker, 0), X); // orphaned entry remains
```

Caveat: I was unable to fully trace `IdleCDOEpochVariant.stopEpochWithDuration`/`_beforeStopEpoch` sequencing to confirm that a new `requestWithdraw` is permitted in the buffer period immediately following a loss-adjusted stop; the claim ordering and marker overwrite in `IdleCreditVault` itself are as described.

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
