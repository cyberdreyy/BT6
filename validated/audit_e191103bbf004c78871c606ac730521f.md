### Title
Absolute Staleness Not Checked in `get_latest_data` / `add_simple_oracle` — (`File: crates/sui-oracle/move/oracle/sources/meta_oracle.move`, `crates/sui-oracle/move/oracle/sources/simple_oracle.move`)

---

### Summary

The Sui oracle framework's `simple_oracle::get_latest_data()` and `meta_oracle::add_simple_oracle()` never compare stored data timestamps against the current on-chain clock. The only staleness filter in `meta_oracle::combine()` is relative — it checks whether each feed's timestamp falls within `time_window_ms` of `max_timestamp` — but `max_timestamp` itself is never validated against the current time. If the oracle operator stops submitting updates, all feeds age together and every feed continues to pass the relative window check indefinitely, delivering arbitrarily old prices as "trusted" data.

---

### Finding Description

`simple_oracle::get_latest_data()` returns whatever `StoredData` is stored in the dynamic field, with no `Clock` argument and no freshness assertion:

```move
public fun get_latest_data<T: store + copy>(oracle: &SimpleOracle, ticker: String): Option<Data<T>> {
    if (!df::exists_(&oracle.id, ticker)) { return option::none() };
    let data: &StoredData<T> = df::borrow(&oracle.id, ticker);
    let StoredData { value, sequence_number, timestamp, identifier } = *data;
    option::some(data::new(value, ticker, sequence_number, timestamp, oracle.address, identifier))
}

Because `max_timestamp` is never compared against `clock::timestamp_ms(clock)`, the entire window slides with the data. If all three oracle operators stop submitting at time T, then one hour later `max_timestamp` is still T, `min_timestamp` is `T - time_window_ms`, and every feed still passes the filter. The `median()` call returns a price that is one hour stale with no error or warning.

The `submit_data()` function correctly records `clock::timestamp_ms(clock)` as the timestamp on write: [4](#0-3) 

but the read path (`get_latest_data`, `add_simple_oracle`, `combine`) never uses the `Clock` to validate freshness.

The intended consumer pattern, shown in the test module, calls `meta_oracle::median()` and immediately uses the returned price for a financial conversion with no staleness guard:

```move
let trusted_data = meta_oracle::median(meta_oracle);
let value = meta_oracle::value(&trusted_data);
...
let amount = mist_amount * value;
``` [5](#0-4) 

---

### Impact Explanation

Any Move package that calls `simple_oracle::get_latest_data()` or `meta_oracle::median()` — the two public APIs the framework exposes for consuming prices — will silently receive arbitrarily old price data if oracle operators stop updating. Financial applications (FX conversion, margin valuation, liquidation triggers) built on this framework will compute incorrect amounts, potentially enabling users to exploit stale-high or stale-low prices to extract value or avoid liquidation. This matches the "harmful smart-contract behavior" class in the allowed impact gate (High/Medium).

---

### Likelihood Explanation

The `Clock` object is already used correctly on the write path (`submit_data`), demonstrating that the framework authors are aware of on-chain time. The omission on the read path is a design gap, not an intentional choice. Any network disruption, oracle operator outage, or deliberate withholding of updates leaves consumers with no on-chain protection. An ordinary SUI holder can trigger the vulnerable path by calling any public entry that internally reads from a `SimpleOracle` after the oracle has gone stale.

---

### Recommendation

1. Add a `max_age_ms: u64` parameter and a `clock: &Clock` argument to `get_latest_data()`. Assert `clock::timestamp_ms(clock) - timestamp <= max_age_ms` before returning data, or return `option::none()` if the data is too old.

2. Add the same `clock: &Clock` argument to `add_simple_oracle()` and pass it through to `get_latest_data()`.

3. In `combine()`, additionally assert that `max_timestamp` itself is recent: `assert!(clock::timestamp_ms(clock) - max_timestamp <= acceptable_lag, EDataTooStale)`.

4. Note the secondary arithmetic issue: if no oracle has data, `max_timestamp` remains `0` and `let min_timestamp = max_timestamp - time_window_ms` will abort with a u64 underflow. Guard with `if (max_timestamp >= time_window_ms)` or initialize `max_timestamp` to a sentinel that makes the subtraction safe.

---

### Proof of Concept

1. Deploy the `oracle` package and create three `SimpleOracle` objects.
2. Call `submit_data` on each at time T (e.g., T = 1_000_000 ms).
3. Wait (or advance the clock) so that the current time is T + 3_600_000 ms (1 hour later). Do **not** call `submit_data` again.
4. Call `trusted_fx(oracle1, oracle2, oracle3, mist_amount, ctx)`:
   - `add_simple_oracle` loads each feed; all have `timestamp = T`.
   - `max_timestamp = T` (set by the last oracle added).
   - `min_timestamp = T - 60_000` (60-second window).
   - All three feeds have `timestamp T > T - 60_000`, so all pass.
   - `median()` returns the 1-hour-old price.
   - `amount = mist_amount * stale_price` is computed and a `MockUSD` object is transferred to the caller.
5. The transaction succeeds with a price that is 1 hour stale, with no revert or warning.
