### Title
Missing Zero-Address Validation on B20 `grantRole(account)` Lets a Token's Sole DefaultAdmin Be Bricked to `Address::ZERO` - (File: crates/common/precompiles/src/b20_asset/logic/v1.rs, crates/common/precompiles/src/b20_asset/logic/v2.rs, crates/common/precompiles/src/b20_stablecoin/logic/v1.rs, crates/common/precompiles/src/b20_stablecoin/logic/v2.rs)

### Summary
The B-20 factory bootstrap path explicitly refuses to grant `DefaultAdmin` to `Address::ZERO` (`if !common.initial_admin.is_zero() { grant_role_unchecked(...) }`), showing the code owners recognize zero-address admin as unsafe. However, the ongoing, publicly reachable `grantRole` surface on both B20 Asset and B20 Stablecoin precompiles (V1 and V2 logic) performs no such check on the `account` parameter, allowing an existing admin to grant `DefaultAdmin` (or any role) to `Address::ZERO`.

### Finding Description
`grantRole` is dispatched from user transactions via `crates/common/precompiles/src/b20_asset/dispatch.rs` (`C::grantRole(c) => logic.grant_role(self, caller, c.role, c.account, privileged)`), with no zero-address check on `c.account`. [1](#0-0) 

`grant_role` and `grant_role_unchecked` in the token logic implementations use `account` directly to set the role bit and, for `DefaultAdmin`, bump `role_member_count` — with no `account.is_zero()` guard anywhere in the path: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

This contrasts with the factory bootstrap path, which is careful to skip the same mutation for a zero admin: [6](#0-5) 

The `revoke_role`/`renounce_role` guard only blocks removing the *last* `DefaultAdmin` when `role_member_count == 1`: [7](#0-6) 

If a real admin grants `DefaultAdmin` to `Address::ZERO` (e.g., by mistake, or as an intermediate step in an admin-rotation script that fails to validate its input, mirroring the exact bug class in the referenced report), `role_member_count(DefaultAdmin)` becomes 2. The real admin can then revoke/renounce their own `DefaultAdmin` role without tripping the `LastAdminCannotRenounce` check (count != 1), leaving `Address::ZERO` as the sole `DefaultAdmin` holder. Because no real signed transaction can ever originate from `msg.sender == Address::ZERO` (this repo's B20 authorization checks are role-membership based, and the token has no privileged/factory bypass for post-creation role administration), the token becomes permanently locked out of all `DefaultAdmin`-gated operations (role administration, and any other functions gated behind the admin role for that token), with no recovery path.

### Impact Explanation
This is a self-inflicted-but-realistic operational bug (same class as the referenced Sherlock finding: a privileged setter with no zero-address validation on an address parameter that controls critical authorization state). The result is a permanent, irrecoverable loss of administrative control for the affected B-20 token: role management functions gated by `DefaultAdmin` become permanently unreachable once `Address::ZERO` is left as the sole admin, since `Address::ZERO` can never be the caller of a valid transaction/precompile call. Depending on the token's role wiring, this can permanently freeze the ability to manage compliance/policy roles, pause, or seize functionality tied to `DefaultAdmin`, which qualifies as a permanent freezing-of-capability impact under the accepted rules (Medium severity, matching the referenced report's severity).

### Likelihood Explanation
The likelihood is moderate: it requires an existing `DefaultAdmin` (an authorized signer) to call `grantRole(DefaultAdmin, Address::ZERO)`, whether through operator error, a buggy automation script, or a compromised/malicious front-end supplying a zero address. This mirrors exactly the misuse scenario described in the original report (an admin calling a setter with a zero address that should have been rejected) — the difference is only which admin-controlled setter is affected (Base's B20 `grantRole` instead of Ubiquity's `setCollateralChainLinkPriceFeed`).

### Recommendation
Add an explicit zero-address check on `account` in `grant_role`/`grant_role_unchecked` for both `B20Asset` and `B20Stablecoin` (V1 and V2), reverting with a dedicated error (mirroring the existing `InvalidReceiver`/`InvalidSender`/`ZeroAdminAddress` pattern already used elsewhere in the codebase, e.g. `NonZeroAddress` in `crates/common/precompiles/src/common/ops/non_zero_address.rs` and `ActivationRegistryStorage::set_admin`'s `ZeroAdminAddress` check) before writing role state, so the reachable `grantRole` entry point enforces the same invariant the factory bootstrap path already enforces.

### Proof of Concept
1. Deploy a B20 asset/stablecoin token via the factory with a non-zero `initialAdmin` (`ADMIN`).
2. `ADMIN` calls `grantRole(role: DefaultAdmin, account: Address::ZERO)` — succeeds, no revert; `role_member_count(DefaultAdmin)` becomes 2 (see `grant_role_unchecked` incrementing `role_member_count`, `crates/common/precompiles/src/b20_asset/logic/v1.rs:490-495`).
3. `ADMIN` calls `renounceRole(DefaultAdmin, ADMIN)` (or `revokeRole`) — succeeds because `role_member_count(DefaultAdmin) == 2 != 1`, so the `LastAdminCannotRenounce` guard at `crates/common/precompiles/src/b20_asset/logic/v1.rs:514-519` does not trigger.
4. `Address::ZERO` is now the sole `DefaultAdmin`. No subsequent transaction can ever be sent with `msg.sender == Address::ZERO`, so all `DefaultAdmin`-gated functionality on this token is permanently unreachable.

Note: I was unable to fully trace every downstream function gated by `DefaultAdmin` (e.g., pause/seize/policy-admin wiring) within the available index; a Devin session with full repository access is recommended to confirm the complete blast radius of functions gated behind `DefaultAdmin` for both Asset and Stablecoin variants before treating this as launch-blocking.

    fn grant_role(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        role: B256,
        account: Address,
        privileged: bool,
    ) -> Result<()> {
        if role == B20TokenRole::DefaultAdmin.id() || !privileged {
            self.ensure_role_admin_mutations_available(token, caller)?;
        }
        if !privileged {
            let admin = token.accounting().role_admin(role)?;
            B20Guards::ensure_role(token, caller, admin)?;
        }
        self.grant_role_unchecked(token, role, account, caller)
    }

    fn grant_role_unchecked(
        &self,
        token: &mut B20AssetToken<S, A>,
        role: B256,
        account: Address,
        sender: Address,
    ) -> Result<()> {
        if token.accounting().has_role(role, account)? {
            return Ok(());
        }
        token.accounting_mut().set_role(role, account, true)?;
        if role == B20TokenRole::DefaultAdmin.id() {
            let current = token.accounting().role_member_count(role)?;
            let next =
                current.checked_add(U256::ONE).ok_or_else(BasePrecompileError::under_overflow)?;
            token.accounting_mut().set_role_member_count(role, next)?;
        }
        token
            .accounting_mut()
            .emit_event(IB20::RoleGranted { role, account, sender }.encode_log_data())
    }

    fn revoke_role(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        role: B256,
        account: Address,
        privileged: bool,
    ) -> Result<()> {
        if !privileged {
            self.ensure_role_admin_mutations_available(token, caller)?;
            let admin = token.accounting().role_admin(role)?;
            B20Guards::ensure_role(token, caller, admin)?;
        }
        if role == B20TokenRole::DefaultAdmin.id()
            && token.accounting().has_role(role, account)?
            && token.accounting().role_member_count(role)? == U256::ONE
        {
            return Err(BasePrecompileError::revert(IB20::LastAdminCannotRenounce {}));
        }
        self.revoke_role_unchecked(token, role, account, caller)
    }
