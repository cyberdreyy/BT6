## Analysis

The external report describes a **race condition between a check (proof verification) and an action (fund release)** — a classic TOCTOU (time-of-check-to-time-of-use) bug that permits a single credential/authorization to be used more than once.

Searching for an analogous unprivileged-actor-reachable pattern in Chainlink's internet-facing gateway, I found two implementations of JWT replay protection that should be functionally equivalent, but only one of them is safe:

**Safe pattern** — `RequestReplayGuard.CheckAndRecord` performs the "seen?" check and the "record as seen" write atomically under a single mutex acquisition: [1](#0-0) 

**Unsafe pattern** — `WorkflowMetadataHandler.Authorize` (used to authorize inbound HTTP-trigger workflow-execution requests from unprivileged external clients) performs the check and the record as two *separate* calls into the `jwtReplayCache`, with authorization/signer-lookup logic executed in between: [2](#0-1) 

```go
if h.jwtCache.isReplay(claims.ID) {          // check
    return nil, errors.New(...)
}
...                                            // signer/authorized-key lookup happens here
h.jwtCache.recordUsage(claims.ID)             // record — happens only at the very end
```

If two requests carrying the same single-use JWT (`jti`) arrive concurrently, both can pass the `isReplay` check before either one reaches `recordUsage`, because the "already used" state is not written until authorization fully succeeds. The `jwtReplayCache` struct guards its map with its own mutex per-call, but that only makes each individual method call atomic — it does not make the check-then-record sequence atomic.

### Title
Non-atomic Check-then-Record in JWT Replay Guard Allows Duplicate Authorization of HTTP Trigger Requests - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize`, which authenticates inbound HTTP-trigger requests from unprivileged external clients before dispatching a workflow execution, checks JWT replay status and marks the JWT as used in two separate, non-atomic steps.

### Finding Description
Chainlink's HTTP trigger gateway path authorizes each inbound request by verifying a JWT and rejecting reused JWT IDs (`jti`) via `jwtReplayCache`. The intended design is "single-use JWT, one workflow execution." However, the check (`isReplay`) and the mark-as-used (`recordUsage`) are invoked as two independent calls separated by signer/authorized-key validation logic: [2](#0-1) 

Compare this to the vault capability's `RequestReplayGuard`, which combines the identical check-and-record operation into one atomic, mutex-protected method (`CheckAndRecord`) specifically to avoid this class of race: [3](#0-2) [4](#0-3) 

Because `Authorize` does not follow the same atomic pattern, two goroutines processing near-simultaneous requests that reuse the same signed JWT can both observe `isReplay(claims.ID) == false` before either calls `recordUsage`, both pass the signer/authorized-key check, and both are granted authorization — defeating the single-use guarantee.

### Impact Explanation
An unprivileged external caller who obtains or replays a single valid signed JWT for an HTTP trigger request can, by sending it concurrently (e.g., two near-simultaneous HTTP requests), get more than one workflow execution authorized from what was intended to be a one-time-use token. Depending on what the triggered workflow does downstream (e.g., initiating on-chain actions, capability calls, or state changes gated on "one execution per token"), this can result in duplicate/unauthorized execution — the same class of impact as the double-spend risk in the external report, where a check meant to gate a single fund-releasing action is bypassed by concurrency.

### Likelihood Explanation
Exploitation requires only sending the same signed JWT/request twice in quick succession, network-level concurrency (no special privileges, no cryptographic break), and does not require compromising the workflow's DON, node keys, or gateway itself. This is reachable directly from an unprivileged HTTP client hitting the gateway's HTTP-trigger capability endpoint.

### Recommendation
Refactor `WorkflowMetadataHandler.Authorize` to record JWT usage atomically with the replay check, mirroring `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go` — i.e., combine the "already seen?" check and the "mark seen" write into a single critical section (ideally the very first step, before any further authorization work), so that concurrent requests bearing the same `jti` cannot both pass.

### Proof of Concept
1. Craft a valid signed JWT for a registered workflow signer, with a fixed `jti`, targeting `MethodWorkflowExecute`.
2. Fire two requests carrying this identical JWT to the gateway's HTTP trigger handler at (nearly) the same time, e.g. via two goroutines/parallel HTTP clients.
3. Under the current implementation, both can pass `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`, since the two calls are separated by signer lookup logic: [2](#0-1) 
4. Both requests are authorized and dispatched, resulting in two workflow executions from one intended single-use token — contrast with the existing sequential-replay test which only demonstrates that *sequential* (non-concurrent) reuse is blocked: [5](#0-4) 

**Caveat:** I was unable to retrieve the exact source of `jwtReplayCache.isReplay`/`recordUsage` (tool access ended before I could pull it), so I cannot fully confirm whether the per-map mutex inside `jwtReplayCache` might incidentally serialize enough to prevent this in all cases, or whether there's an outer lock elsewhere in `Authorize`'s caller that I did not observe. Based on the visible code, `Authorize` itself does not hold a single lock across the check-and-record sequence, which is the root-cause pattern being flagged. Given the residual uncertainty about `jwtReplayCache`'s internals, I'd recommend starting a Devin session to inspect the full `jwtReplayCache` implementation and add a concurrency test before treating this as fully confirmed.

```go
// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```
