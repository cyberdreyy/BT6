### Title
Post-default withdraw claims drain `defaultRecoveryReserve` without replenishment, stealing haircutted default-epoch recovery funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug is a lookup-then-use race: a pointer (`hci_conn`) is looked up under one lock, the lock is released, and the stale pointer is used while another path frees it. The closest analog in this codebase is `IdleCreditVault`'s post-default claim accounting: recovery funds are sized once at `finalizeDefaultRecovery` into an isolated reserve (`defaultRecoveryReserve` / `defaultRecoveryPrice`), but claims made *after* finalization (`postDefaultRequests`) are paid 1:1 out of that same fixed reserve even though their basis was never included in `totalBasis` and their funding never enters the reserve.

### Finding Description
At `finalizeDefaultRecovery` (lines 661-710), `defaultRecoveryReserve` is set to `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, and `defaultRecoveryPrice = reserveAmount * 1e18 / totalBasis`, where `totalBasis = activeBasis + pendingBasis`. Every unit of the reserve is therefore spoken for by default-epoch claims.

After finalization, `requestWithdraw` (lines 247-257) mints a receipt to the user and records `postDefaultRequests[_user] = _amount`. `_claimPostDefaultWithdrawRequest` (lines 760-767) pays this at par via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` (lines 912-917). The reserve is strictly decremented — there is no symmetric path that adds post-default funding into it: `collectWithdrawFunds` only `safeTransferFrom`s underlying to the strategy, and `reserveDefaultRecovery` reverts once `defaultRecoveryFinalized` is true (line 631).

Meanwhile the guard in `_transferFundedClaim` (lines 897-907) explicitly forbids funded claims from touching the reserve (`balance - reserve < _amount` reverts), so underlying delivered later by the borrower for post-default receipts sits as *non-reserve* balance that the reserve-accounting layer never credits.

The "concurrent modification" analog: the reserve is a fixed-size object whose consumers are determined at finalization, but a post-finalization code path (`postDefaultRequests` claims) consumes the same object as if it were sized for them — a UAF-by-accounting.

### Impact Explanation
- **Direct theft of recovery funds**: post-default requesters receive 100% of their claim (the haircut was already applied to their receipt amount at request time, and the haircut was *already delivered by reducing `virtualPrice`*). Paying them from the reserve gives each unit of post-default basis a full unit of recovery, diluting the `defaultRecoveryPrice` pie that was sized only for default-epoch claimants.
- **Permanent freezing / insolvency**: `defaultRecoveryReserve -= _amount` (line 915) will underflow-revert (Solidity checked arithmetic) once post-default claims exhaust the reserve, permanently blocking default-epoch claimants (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`, `DefaultDistributor.claim`) from receiving their haircutted payouts.
- Quantified loss: every token of post-default claims consumes `defaultRecoveryPrice`-priced reserve it was never budgeted for; with reserve fully claimed by post-default users, remaining defaulted claims revert → loss equals `min(postDefaultRequests_total, defaultRecoveryReserve)` for default-epoch claimants.

### Likelihood Explanation
High. Triggering requires only:
1. Borrower defaults and `finalizeDefaultRecovery` runs (honest manager/borrower actions — allowed per rules).
2. Any KYC-passing lender calls `requestWithdraw` post-default (allowed: `postDefaultRequests` path is unprivileged through the CDO) and then `claimWithdrawRequest` once funded.
No privileged misbehavior, no oracle manipulation, no DoS speculation — the reserve accounting mismatch executes deterministically on the normal post-default claim path.

### Recommendation
Pay post-default claims via `_transferFundedClaim` (or a dedicated post-default bucket credited by `collectWithdrawFunds`), not `_transferDefaultRecovery`. Equivalently, increment `defaultRecoveryReserve` when post-default funding arrives (a `reserveDefaultRecovery`-like entry point that works after finalization), so the reserve only ever covers the basis it was priced against.

### Proof of Concept
Not reproduced as a runnable Foundry fork test within this analysis — the claim rests on a storage-level trace: `postDefaultRequests` payouts decrement `defaultRecoveryReserve` (lines 765-766, 915) while the only reserve-funding paths (`finalizeDefaultRecovery` line 691, `reserveDefaultRecovery` line 632 gated by `!defaultRecoveryFinalized`) are unreachable post-finalization. A PoC would: deposit, run an epoch, default the borrower, call `finalizeDefaultRecovery` with partial recovery (e.g., 50%), then have a second user `requestWithdraw` + get funded via `collectWithdrawFunds` + `claimWithdrawRequest`, and show the reserve underflows before the first user's `_claimDefaultedWithdrawRequest` executes.

I could not fully verify `IdleCDOEpochVariant`'s post-default funding path (whether it routes post-default collections through `reserveDefaultRecovery` — which would revert, strengthening the finding, or adds reserve elsewhere). If the CDO does top up `defaultRecoveryReserve` for post-default funding, this finding collapses; that path should be confirmed before reporting.
