### Title
Underfunded instant-withdraw payouts let early claimants drain later claimants' receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Node.js bug class is "state not cleared after an operation, causing later operations on the same thread to see false/misleading state." The analog in this codebase is the instant-withdraw accounting in `IdleCreditVault`: `pendingInstantWithdraws` is a global aggregate that is only *partially* decremented by whatever `collectInstantWithdrawFunds` manages to pull from the CDO, while `claimInstantWithdrawRequest` pays each user their full `instantWithdrawsRequests[_user]` balance from the vault's aggregate underlying balance with no per-epoch/per-user funding check. When `startEpoch` underfunds instant requests (the normal case, since most assets are lent to the borrower), the vault's underlying balance covers only part of the outstanding receipts, yet each claim pays out in full — early claimants are paid from funds earmarked for later claimants.

### Finding Description
`requestInstantWithdraw` mints the user a strategy-token receipt and increments both `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375). At `startEpoch`, the CDO calls `collectInstantWithdrawFunds(min(pendingInstant, totUnderlyings))` (contracts/IdleCDOEpochVariant.sol:279-290); if `pendingInstant > totUnderlyings` the function returns early, the surplus stays in `pendingInstantWithdraws`, but no additional funding is ever scheduled for those receipts.

`claimInstantWithdrawRequest` then does:

```
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

(contracts/strategies/idle/IdleCreditVault.sol:387-392). `_transferFundedClaim` only guards the `defaultRecoveryReserve` (lines 897-907); it does not verify the claim was actually funded. So while `pendingInstantWithdraws` still records an unfunded remainder, the vault's whole underlying balance — which includes funding belonging to *other* users' receipts — is fair game.

### Impact Explanation
Broken invariant: "one receipt, one funded payout." With pendingInstant > available underlying at epoch start, the vault holds less underlying than the sum of outstanding instant receipts. Each claim pays 1:1 anyway, so the first claimants receive full payment while the last claimants' receipts become permanently unpayable (their share was never re-funded: `stopEpoch` funds `pendingWithdraws`, not the stale `pendingInstantWithdraws` remainder). Result: theft/permanent freezing of later claimants' unclaimed principal, quantified as `pendingInstantWithdraws_funded - instantWithdrawsRequests_outstanding` — up to the entire unfunded remainder.

### Likelihood Explanation
Reachable by any unprivileged tranche holder in any epoch where aggregate instant-withdraw requests exceed the underlying held by the CDO at `startEpoch` — which is the common case since most TVL is with the borrower. No privileged misbehavior is needed: `startEpoch` itself deterministically creates the underfunded state when `pendingInstant > totUnderlyings` (IdleCDOEpochVariant.sol:286-290). The attacker simply calls `claimInstantWithdrawRequest` before other claimants.

### Recommendation
Track per-epoch instant-withdraw funding (as is already done for normal receipts via `lossRecoveryPriceByEpoch`) or gate `claimInstantWithdrawRequest` so a user can only claim the funded portion of `instantWithdrawsRequests[_user]`; alternatively persist an `instantFundingShortfall`/`instantRecoveryPrice` at `collectInstantWithdrawFunds` time and haircut claims accordingly, instead of letting the unfunded remainder sit in `pendingInstantWithdraws` while claims pay at par.

### Proof of Concept
Foundry fork test (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantWithdrawUnderfundedDrainsLaterClaimants() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address alice = makeAddr('alice');
    address bob = makeAddr('bob');
    uint256 amt = 10_000 * ONE_SCALE;

    // two users deposit and request instant withdraw during buffer (APR drop)
    _depositWithUser(alice, amt, true);
    _depositWithUser(bob, amt, true);

    // set APR delta so requestWithdraw takes the instant path
    // ... set lastEpochApr > unscaledApr + instantWithdrawAprDelta ...
    vm.prank(alice); cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(bob);   cdoEpoch.requestWithdraw(0, address(AAtranche));

    uint256 pending = creditVault.pendingInstantWithdraws();
    assertEq(pending, 2 * amt - feeAdjust);

    // at startEpoch, CDO holds less underlying than pending instant requests
    // (rest of TVL is with the borrower) -> underfunding
    _startEpochAndCheckPrices(0);
    assertGt(creditVault.pendingInstantWithdraws(), 0, 'unfunded remainder');

    // alice claims first and is paid in full from the shared balance
    vm.prank(alice);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(alice), amt);

    // bob's receipt is now unpayable: vault balance < his receipt
    vm.prank(bob);
    vm.expectRevert(); // SafeERC20: transfer amount exceeds balance
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Setup note: reproduce the `pendingInstant > totUnderlyings` branch of `startEpoch` (IdleCDOEpochVariant.sol:286) by keeping buffer liquidity below total instant requests; the revert on Bob's claim demonstrates permanent loss/freezing of his funded receipt.
