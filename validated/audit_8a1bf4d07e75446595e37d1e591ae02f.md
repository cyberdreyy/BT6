### Title
BlockRejection Signature Does Not Bind `reason`, `reason_code`, or `response_data` — Field-Splicing Forges Signer Metadata Without the Signer's Key - (File: libsigner/src/v0/messages.rs)

### Summary
`BlockRejection::hash()` computes the digest that is signed and later re-verified using **only** the block's `signer_signature_hash`. The struct's other fields — `reason` (free text), `reason_code`/`response_data.reject_reason`, and the versioned `response_data` payload (which carries `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`, `failed_txid`) — are never included in the signed preimage. Any party that can observe a signer's rejection message on StackerDB (a public, read-by-everyone channel) can therefore splice a different `reason`, `reject_reason` code, or `response_data` timing fields onto the untouched, still-valid signature and hash, and the recipient's `verify()` call will accept it as an authentic, unmodified message from that signer.

The `BlockRejection` struct itself, however, carries much more state that is delivered to and trusted by downstream consumers: [2](#0-1) 

`reason`, `reason_code`, and `response_data` (containing `reject_reason`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`, `failed_txid`) are all part of the wire message but are excluded from the cryptographic binding — exactly the ALTCHA-class flaw: the signature authenticates only a subset of the semantically meaningful parameters (`signer_signature_hash`), leaving the remaining parameters (`reason`/`reason_code`/`response_data`) unauthenticated and freely re-attachable to the valid `(hash, signature)` pair. This is the "challenge splicing" pattern from the report, applied to `BlockRejection` instead of an ALTCHA challenge: an attacker doesn't need to forge a new signature, only reassemble a validly-signed envelope around different payload bytes.

Because signer-to-signer/miner traffic travels over StackerDB — a public gossip channel readable and relayable by anyone, including non-signers — this is reachable without any signer key, a majority, or auth_token, consistent with the in-scope threat model (gossip-level tampering).

### Impact Explanation
`response_data` (in particular `tenure_extend_timestamp` / `tenure_extend_read_count_timestamp`) is read out of `BlockResponse`/`BlockRejection` messages and fed into tenure-extension timing logic consumed by the node (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`, which references these fields extensively) and by other signers (`stacks-signer/src/v0/signer.rs`, which also consumes `tenure_extend_timestamp`/`response_data`). Because these values are not bound by the signature, an on-path relayer can attribute forged extension timestamps, a forged `reject_reason`, or a forged `failed_txid` to an honest signer's otherwise-genuine, validly-signed rejection — without possessing that signer's key. Depending on how aggressively these unauthenticated fields are trusted downstream (median/threshold computation for tenure-extend windows, or re-evaluation logic keyed off `reject_reason`, cf. `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`), this can desynchronize tenure-extend timing consensus across signers and the miner, producing a liveness wedge (mistimed or blocked tenure extension) attributable to a signer who never actually reported those values.

I was not able to fully trace, within the available iterations, the exact aggregation function that consumes `tenure_extend_timestamp` from other signers' `BlockResponse` messages on the miner/node side to confirm the precise blast radius (e.g., whether it's a simple max/median across all signers, which would bound the damage, or whether a single forged value can flip a threshold decision). This should be verified directly against `stacks-node/src/nakamoto_node/stackerdb_listener.rs` before rating final severity, but the root-cause binding gap in `BlockRejection::hash()` is proven directly from the code above.

### Likelihood Explanation
High reachability: StackerDB traffic for signer messages is broadcast/gossip and observable by any network participant; no signer key, majority, or privileged access is required to intercept a validly-signed `BlockRejection` and re-attach different `reason`/`reason_code`/`response_data` bytes before relaying it onward, since `verify()` never re-derives those fields.

### Recommendation
Include the full semantically-relevant payload — `reason`, `reason_code` (or `response_data.reject_reason`), and the entire `response_data` blob (or its own hash) — inside the structured-data tuple hashed in `BlockRejection::hash()`, so the signature unambiguously commits to every field the recipient will act on, not just `signer_signature_hash`.

### Proof of Concept
1. Signer `S` rejects block `B` for reason `NoSortitionView` with `tenure_extend_timestamp = T1`, producing `BlockRejection { signer_signature_hash: H(B), reason_code, response_data{tenure_extend_timestamp: T1, ...}, signature: Sig }` where `Sig = Sign(sk_S, hash())` and `hash()` only covers `H(B)` [3](#0-2) .
2. A network relayer intercepts this message on StackerDB (public), and constructs a new `BlockRejection` with the same `signer_signature_hash` and `signature`, but a different `reason`, `reason_code`, or `response_data` (e.g., `tenure_extend_timestamp = T2`, or a different `reject_reason`/`failed_txid`).
3. Any recipient calling `BlockRejection::verify(pubkey_S)` recomputes `hash()` — which is identical to step 1 since it only depends on `signer_signature_hash` — and the forged message verifies successfully as an authentic message from `S`, even though `S` never produced those `reason`/`response_data` values [4](#0-3) .

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)

    }
