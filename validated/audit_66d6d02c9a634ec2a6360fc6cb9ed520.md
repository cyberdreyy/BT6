### Title
Unprivileged client can block another user's confidential relay request by pre-registering the same JSON-RPC request ID - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
The `HandleJSONRPCUserMessage` entry point of the gateway's confidential relay handler keys pending requests solely by the client-supplied, unauthenticated `req.ID` field, with no per-caller or per-owner scoping. Any client can submit a JSON-RPC request with a request ID equal to one another user intends to use, permanently occupying that ID and causing the legitimate user's subsequent request with the same ID to be rejected — mirroring the `TunnlTwitterOffers.createOffer` front-running pattern where a user-chosen identifier is globally unique and unauthenticated at time of reservation.

### Finding Description
`HandleJSONRPCUserMessage` performs only trivial structural checks (non-empty ID, length ≤ 200) and then immediately calls `newActiveRequest`, which stores the request in a single, global `activeRequests` map keyed by the raw `req.ID`: [1](#0-0) 

`newActiveRequest` rejects the request outright if any entry already exists for that ID, before any authentication, authorization, or ownership check is performed: [2](#0-1) 

There is no per-caller namespacing of the ID at this layer (unlike the sibling vault gateway handler, whose `GatewayVaultRequestProcessor.authorizeAndStamp` explicitly prefixes the request ID with the *authorized owner* — derived from a verified auth result — before it is used as a dedup/routing key): [3](#0-2) 

Because the confidential relay handler skips that owner-prefixing step, any unprivileged caller who knows or predicts a victim's intended request ID (e.g. via a fixed/incrementing ID scheme, disclosure elsewhere, or race conditions against the public gateway endpoint) can submit a bogus request with that same ID first. The victim's real request will then be rejected with `"request ID already exists"`, exactly the analog of the `TunnlTwitterOffers.createOffer` bug where `s_offers[offerId].creationDate == 0` is checked and a pre-existing, attacker-created record blocks legitimate use of a chosen identifier. The handler is directly reachable from the gateway's public request path with no scoping applied beforehand: [4](#0-3) 

### Impact Explanation
An attacker with only unprivileged access to the gateway's public JSON-RPC endpoint can deny service to a specific confidential-relay request (`MethodSecretsGet` / `MethodCapabilityExec`) by squatting on its ID before the legitimate caller's request arrives. This blocks a specific user's capability execution/secret retrieval flow through the DON, without needing any credentials, matching the "unauthorized... request" / availability-denial class called out as acceptable in the rules. It does not directly disclose secrets or move funds, so impact is best characterized as medium — a targeted denial of a legitimate request.

### Likelihood Explanation
Exploitation requires the attacker to know or predict the victim's request ID and win a race to submit it first at the gateway before the legitimate request. If IDs are non-random/predictable (e.g. deterministic per workflow/session), or observable through client-side behavior/timing, this is straightforward and cheap for an unprivileged caller to attempt against the exposed gateway HTTP endpoint. If IDs are always cryptographically random per request, likelihood drops significantly; this cannot be confirmed from the reachable code because ID generation is caller-controlled and not standardized/validated within this handler.

### Recommendation
Scope `activeRequests` keys by an authenticated identity (e.g., prefix the ID by an authorization result / caller identity as already done in `GatewayVaultRequestProcessor.authorizeAndStamp`) rather than trusting the raw, unauthenticated client-supplied `req.ID` as a global dedup key. Alternatively, perform authentication/authorization before ID registration and derive the dedup key from verified caller identity plus request ID.

### Proof of Concept
1. Attacker sends a JSON-RPC request to the gateway's confidential relay endpoint with `Method: MethodCapabilityExec` and `ID: "victim-id"`.
2. `newActiveRequest` succeeds and stores `activeRequests["victim-id"]`.
3. Victim later submits their legitimate request with the same `ID: "victim-id"`.
4. `newActiveRequest` returns `"request ID already exists: victim-id"`, and `HandleJSONRPCUserMessage` returns this error to the victim, denying their request — directly analogous to `TunnlTwitterOffers.createOffer`'s `require(s_offers[offerId].creationDate == 0, "Offer already exists")` front-running scenario.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil
