### Title
Truncating `uint64` cast of `idx` in `MerkleStorageInvalidator.takerInteraction` allows storage corruption that permanently DoSes future partial fills - (File: `contracts/MerkleStorageInvalidator.sol`)

### Summary
`MerkleStorageInvalidator.takerInteraction` verifies a Merkle proof using a **truncated** `uint64(takerData.idx)` inside the leaf hash, but then persists the **full, untruncated** `uint256 idx + 1` value into the `lastValidated` mapping used later to gate escrow creation. An unprivileged taker filling a multi-fill order can supply `idx = 2**64 + N` (any real, valid index `N` plus a multiple of `2**64`), which still verifies against the real Merkle proof for leaf `N` (since the hash uses the truncated value) but stores a corrupted, astronomically large `index` in `lastValidated`. This is the same unsafe-narrowing-cast root cause as the referenced Sushi finding: a value is validated against one width but consumed/persisted at a different width, letting the caller desynchronize the two.

### Finding Description
In `takerInteraction`: [1](#0-0) 

The Merkle leaf is computed with `uint64(takerData.idx)`, but the value written to storage is the raw `takerData.idx + 1` (a `uint256`), with no bound/equality check that the two representations match. Because `takerData.idx` is taken directly from calldata (attacker-controlled `extraData` supplied by the taker calling `fillOrderArgs`), a taker can choose `idx = 2**64 + N` for any legitimate part index `N` whose proof/secret they possess. The proof check `uint240(uint256(rootCalculated)) != rootShortened` still passes because `uint64(idx) == N`, so the correct leaf is reconstructed and the Merkle proof validates. However, `lastValidated[key] = ValidationData(takerData.idx + 1, secretHash)` now stores `index = 2**64 + N + 1`, a value with no real relationship to the actual fill progress.

This corrupted `validated.index` is later consumed in `BaseEscrowFactory._postInteraction` and `_isValidPartialFill`: [2](#0-1) [3](#0-2) 

`_isValidPartialFill` computes a small `calculatedIndex` bounded by `partsAmount` (realistically at most a few hundred/thousand parts) and compares it with `validatedIndex`. Once `validatedIndex` has been corrupted to `2**64 + N + 1`, no legitimate future `calculatedIndex + 1` (or `+2`) can ever equal it again, so `InvalidPartialFill` reverts for every subsequent fill attempt on that order.

### Impact Explanation
Any unprivileged taker participating in a legitimate multi-fill order fill can, in the course of an otherwise-valid partial fill, permanently corrupt `lastValidated[key]` for that order's Merkle root, making all subsequent partial fills of the order impossible (`_postInteraction` always reverts with `InvalidPartialFill`). This breaks the smart contract's ability to operate for that order going forward — the order can never be completed via the Merkle multi-fill mechanism, and the maker's remaining making amount can no longer be swapped through this path. This matches the Medium-severity bucket: "smart contract unable to operate because required token/native balances can be broken by an unprivileged actor." It is a griefing/DoS vector reachable purely from the public order-fill entry point, requiring no privileged role.

### Likelihood Explanation
Likelihood is high for any order using `allowMultipleFills`: the attacker only needs to be a legitimate (or malicious) taker able to call `fillOrderArgs` with crafted `extraData`/`interaction` bytes containing an inflated `idx`. No special permissions, races, or capital are required beyond executing one real partial fill with a manipulated `idx` value.

### Recommendation
Do not let the value written to storage differ in width/semantics from the value verified in the proof. Either:
- Declare `TakerData.idx` as `uint64` (or another fixed-width type matching the proof encoding) so calldata decoding reverts (or is properly masked) for out-of-range values, or
- Explicitly require `takerData.idx == uint64(takerData.idx)` (i.e., `idx <= type(uint64).max`) before using it, reverting otherwise, or
- Store the truncated `uint64` value (consistently used elsewhere) instead of the raw `uint256 idx + 1`.

### Proof of Concept
1. Order created with `allowMultipleFills` and `partsAmount = P`; Merkle tree built over leaves `keccak256(uint64(i), secretHash_i)` for `i in [0, P]`.
2. A legitimate taker calls `fillOrderArgs` for a partial amount corresponding to real index `N`, but crafts `extraData`/`interaction` so `TakerData.idx = 2**64 + N` instead of `N`, using the genuine Merkle proof and `secretHash_N`.
3. In `MerkleStorageInvalidator.takerInteraction` at [1](#0-0) , `uint64(takerData.idx) == N`, so `rootCalculated` matches `rootShortened` and the proof validates. `lastValidated[key]` is now set to `ValidationData(2**64 + N + 1, secretHash_N)`.
4. `BaseEscrowFactory._postInteraction` proceeds to create the escrow for this fill using `validated.leaf = secretHash_N` (this fill still succeeds).
5. For any subsequent partial fill of the same order, `_isValidPartialFill` at [3](#0-2)  computes a small `calculatedIndex` (bounded by `partsAmount`) that can never equal the corrupted `validatedIndex = 2**64 + N + 1`, so `InvalidPartialFill` reverts permanently — the order can never be filled further.

    function _isValidPartialFill(
        uint256 makingAmount,
        uint256 remainingMakingAmount,
        uint256 orderMakingAmount,
        uint256 partsAmount,
        uint256 validatedIndex
    ) internal pure returns (bool) {
        uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;

        if (remainingMakingAmount == makingAmount) {
            // If the order is filled to completion, a secret with index i + 1 must be used
            // where i is the index of the secret for the last part.
            return (calculatedIndex + 2 == validatedIndex);
        } else if (orderMakingAmount != remainingMakingAmount) {
            // Calculate the previous fill index only if this is not the first fill.
            uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
            if (calculatedIndex == prevCalculatedIndex) return false;
        }

        return calculatedIndex + 1 == validatedIndex;
    }
