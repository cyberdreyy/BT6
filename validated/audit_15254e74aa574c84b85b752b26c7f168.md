### Title
Malicious maker with a native-token-rejecting address can permanently block `EscrowDst.withdraw`/`publicWithdraw`, freezing resolver's principal and safety deposit until the cancellation window - (File: contracts/EscrowDst.sol, contracts/BaseEscrow.sol)

### Summary
`EscrowDst._withdraw` and `EscrowSrc._cancel`/`_withdrawTo` use a push-transfer pattern (`_ethTransfer`/`_uniTransfer`) that reverts the whole call if the native-token recipient cannot accept ETH, exactly the root cause described in the GoGoPool `cancelMinipoolByMultisig` report.

### Finding Description
`BaseEscrow._ethTransfer` performs a low-level `call` and reverts with `NativeTokenSendingFailure` if the transfer fails [1](#0-0) . `EscrowDst._withdraw` uses this to push the destination amount to `immutables.maker.get()` (which can be native token when `token == address(0)`) before crediting the caller's safety deposit [2](#0-1) . The `maker` address is an immutable value fixed at order-fill time and is fully controlled by the swap's maker/user (an unprivileged party), not by the resolver calling `withdraw`/`publicWithdraw`. If the maker is a contract that rejects plain ETH transfers, every call to `withdraw` (private, by the taker) and `publicWithdraw` (public, by any access-token holder/resolver) reverts, since the maker-bound transfer happens before the caller's safety-deposit transfer and the whole transaction reverts atomically. This is functionally identical to the GoGoPool scenario, where a malicious minipool owner blocked `cancelMinipoolByMultisig` by refusing AVAX.

The repository's own test suite documents this exact revert behavior for `EscrowDst`: `test_NoFailedNativeTokenTransferWithdrawalDst` and `test_NoFailedNativeTokenTransferWithdrawalDstNative` both show `withdraw`/`publicWithdraw` reverting with `NativeTokenSendingFailure` when the maker/recipient (`nativeTokenRejector`) cannot receive native tokens [3](#0-2) .

### Impact Explanation
Unlike `EscrowSrc.cancel`, which returns funds to the taker itself and safety deposit to `msg.sender` (self-inflicted risk only), `EscrowDst._withdraw` forces a push to a third-party-controlled address (`maker`) as a mandatory step of a function callable by other, honest resolvers via `publicWithdraw`. Because the maker's address and its rejecting behavior are fixed for the whole life of the destination escrow, no resolver — private or public — can ever complete a withdrawal. The only remaining path is `EscrowDst.cancel`, which is gated behind `DstCancellation` and sends funds back to the taker only, `onlyCaller(immutables.taker.get())` [4](#0-3) . This bounds the impact to a temporary freeze of the resolver's deposited destination tokens and safety deposit for the duration of the withdrawal window, matching the "temporary freezing of funds during the live swap lifecycle" High-severity category in the bounty scope — but it does not cause permanent loss, since cancellation always succeeds afterward.

### Likelihood Explanation
The attack requires only that the maker (an unprivileged party who signs the source-chain order) use a contract address as `maker` that rejects bare ETH transfers, and that the destination token for the swap be native (`token == address(0)`), a supported and tested configuration in this repo (`test_CancelDstWithNativeToken`, `test_WithdrawByResolverDstNative`) [5](#0-4) . No privileged access is needed, and the griefing condition is set up entirely before the resolver deploys the destination escrow and deposits funds, so likelihood is high whenever a resolver accepts a native-token destination swap from an unvetted maker.

### Recommendation
Adopt a pull-over-push pattern for the maker-bound native transfer in `EscrowDst._withdraw` (and consider the same for the fee-recipient transfers): record the maker's owed native amount in storage and let the maker claim it separately, so that a maker unable/unwilling to receive ETH cannot block the resolver's withdrawal or public-withdraw path. Alternatively, wrap failed native transfers to the maker into WETH or an internal credit balance instead of reverting the whole withdrawal.

### Proof of Concept
The existing repository test already demonstrates the revert: deploying a `EscrowDst` with `token = address(0)` and `maker = address(nativeTokenRejector)`, then calling `dstClone.withdraw(SECRET, immutables)` during the withdrawal window reverts with `NativeTokenSendingFailure`, and the resolver's `bob.addr` balance and escrow balance remain unchanged (funds locked) [6](#0-5) . The equivalent `publicWithdraw` case is shown at [7](#0-6) , confirming that neither the private taker nor any public resolver can withdraw once the maker is set to a rejecting contract; only `cancel` (returning funds to the taker after `DstCancellation`) can unlock the escrow.

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
