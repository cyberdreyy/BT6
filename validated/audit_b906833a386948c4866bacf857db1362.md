### Title
External initiator credentials for one job can trigger `POST /v2/jobs/:ID/runs` on any other job by integer ID with no identity/job binding check - (File: core/web/pipeline_runs_controller.go)

### Summary
`AuthenticateExternalInitiator` grants any valid EI credential holder a generic `UserRoleRun` session identity, and `PipelineRunsController.Create` only checks whether *some* authenticated identity is present (`auth.GetAuthenticatedUser`) before running a job by raw integer ID — it never checks that the specific external initiator (`auth.GetAuthenticatedExternalInitiator`) is associated with that job. This lets an EI credential for job A trigger runs on job B.

### Finding Description
The route is registered as: [1](#0-0) 

`auth.AuthenticateExternalInitiator` validates the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers against the `external_initiators` table and, on success, sets `SessionExternalInitiatorKey` **and** a generic `SessionUserKey` with `Role: UserRoleRun` — the exact same context key used for real session/token-authenticated users: [2](#0-1) 

`auth.RequiresRunRole` (wrapping `prc.Create`) only checks that `user.Role != UserRoleView`; it does not distinguish an EI-derived "user" from a real DB user, and it never inspects `SessionExternalInitiatorKey`: [3](#0-2) 

`PipelineRunsController.Create` then does the actual authorization/dispatch: [4](#0-3) 

It rejects UUID-format IDs (the legacy webhook-by-external-job-UUID path was removed, returning `job.ErrJobTypeRemoved`), then checks only `_, isUser := auth.GetAuthenticatedUser(c)` — which is `true` for an EI-authenticated request too, since `AuthenticateExternalInitiator` populated `SessionUserKey`. If `idStr` parses as an `int32`, it calls `prc.App.RunJobV2(ctx, jobID, nil)` directly, with **no lookup of `GetAuthenticatedExternalInitiator(c)` and no check that this EI's registered job/bridge matches `jobID`**.

Thus an attacker holding valid EI credentials for job A can send `POST /v2/jobs/{jobB_ID}/runs` (where `jobB_ID` is any job's numeric ID on the node) and the request is accepted at `RequiresRunRole` and executed at `PipelineRunsController.Create` without any binding check between the authenticated initiator identity and the target job.

### Impact Explanation
This is an authorization/request-binding bypass: possession of a single external-initiator credential (intended to be scoped to one specific job/bridge integration) becomes equivalent to holding a generic "Run role" credential for the entire node, allowing the attacker to trigger pipeline runs on arbitrary jobs by numeric ID. This matches Chainlink's "unauthorized job run" / authorization bypass impact class, potentially causing unwanted external calls, resource consumption, bridge invocations, or (depending on job task graph) fund-moving transactions on jobs the initiator was never registered for.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs one legitimate external-initiator AccessKey/Secret pair (the lowest-privilege credential type in the system, explicitly scoped to a single job/bridge by design), and knowledge or guessing of another job's integer ID (which is often sequential/discoverable via `GET /v2/jobs`, which is not scoped by EI role either). No admin, operator, or additional secrets are required, and the exploit is fully reproducible via a single HTTP request.

### Recommendation
In `PipelineRunsController.Create`, when the request was authenticated via `AuthenticateExternalInitiator`, retrieve the external initiator via `auth.GetAuthenticatedExternalInitiator(c)` and verify that the target `jobID`'s job is actually associated with that specific initiator (e.g., via its `ExternalJobID`/bridge/name mapping) before calling `RunJobV2`. Do not treat EI-derived `SessionUserKey` identically to real user sessions/tokens for authorization purposes in job-run-triggering endpoints; use a distinct context flag/type so `isUser` in `Create` reflects a real user versus an EI, and add an explicit initiator-to-job binding check for the EI case.

### Proof of Concept
Handler-level integration test plan (Go, using existing `cltest` helpers similar to `TestRunner_WebhookJobRemoved`):
1. Start an app with `ExternalInitiatorsEnabled = true`.
2. Create external initiator "ei-A" via `POST /v2/external_initiators` → obtain `AccessKey`/`Secret` A.
3. Create Job A (any job type with an integer `job.ID`) intended to be run by EI-A.
4. Create Job B (a distinct job with a different integer `job.ID`) that is NOT associated with EI-A in any way.
5. Send `POST /v2/jobs/{jobB.ID}/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-A's credentials, no session/token.
6. Assert: current behavior returns `200`/`201` and a `pipeline_runs` row is created for Job B (`SELECT COUNT(*) FROM pipeline_runs WHERE pipeline_spec_id = jobB.PipelineSpec.ID` increments) — demonstrating the bypass.
7. Expected fixed behavior: response should be `401`/`403` (unauthorized), and `cltest.AssertCountStays(t, app.GetDB(), "pipeline_runs", 0)` for Job B when triggered by an unrelated EI credential.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (prc *PipelineRunsController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	respondWithPipelineRun := func(jobRunID int64) {
		pipelineRun, err := prc.App.PipelineORM().FindRun(ctx, jobRunID)
		if err != nil {
			jsonAPIError(c, http.StatusInternalServerError, err)
			return
		}
		res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
		jsonAPIResponse(c, res, "pipelineRun")
	}

	idStr := c.Param("ID")

	// Webhook runs used external job UUIDs; that job type has been removed.
	if _, err := uuid.Parse(idStr); err == nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, fmt.Errorf("cannot run job of type %q: %w", job.Webhook, job.ErrJobTypeRemoved))
		return
	}

	_, isUser := auth.GetAuthenticatedUser(c)
	// only users are allowed to run jobs using int IDs - EIs not allowed
	if isUser {
		// Is it an int32? Then process it regardless of type
		var jobID int32
		jobID64, err := strconv.ParseInt(idStr, 10, 32)
		if err == nil {
			jobID = int32(jobID64)
			jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
			if err != nil {
				jsonAPIError(c, http.StatusInternalServerError, err)
				return
			}
			respondWithPipelineRun(jobRunID)
			return
		}
	}

	jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("bad job ID"))
}
