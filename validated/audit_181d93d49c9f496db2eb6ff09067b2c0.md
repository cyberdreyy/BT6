### Title
Multisig requests execute using confirmations from removed members, letting stale approvals satisfy the live threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether a request has "enough" approvals purely by counting entries in a per-request `HashSet<String>` of confirmations, comparing that count against `self.num_confirmations`. Nothing in this comparison re-checks that every account/key that previously confirmed is still a current member of `self.members` at the moment the request executes. This is the exact binding class the review scope calls out: "confirmations counted versus live members."

### Finding Description
`add_request`/`add_request_and_confirm` create a request together with an empty (or 1-entry) `confirmations: HashSet<String>` keyed on the confirming member's string representation [1](#0-0) . Each subsequent call to `confirm` validates only that the *current caller* is a live member via `current_member()`, inserts that caller into the set if the count is still below threshold, and — critically — decides to execute as soon as `confirmations.len() as u32 + 1 >= self.num_confirmations`, without walking the existing entries in the set to confirm they are still members [2](#0-1) .

The multisig membership set (`self.members: UnorderedSet<MultisigMember>`) is designed to be mutable: `MultiSigRequestAction::AddMember` / `DeleteMember` are first-class request actions [3](#0-2) , meaning K-of-N membership can legitimately shrink or rotate between the time a member confirms request A and the time request A finally reaches its (K)-th confirmation. Because confirmations are stored per-request as opaque strings and never revalidated against the live `members` set on the execute path, a member who confirmed request A and was later removed (e.g., because their key was compromised, or as part of routine key rotation) still counts toward that request's threshold. This lets a request execute with fewer than K *currently authorized* signers — the same "locked parameter counted at approval-time, not enforced against present authority" pattern as the reported Manager-editable-deadline bug, applied to multisig custody.

Binding that should hold: `count(confirmations that are current members) >= num_confirmations` at execution time. What the code actually enforces: `count(all recorded confirmations, live or not) >= num_confirmations`.

### Impact Explanation
This crosses an authorization threshold boundary for a custody contract: a `Transfer`, `AddKey`, or `DeployContract` request can be executed by the multisig account while backed by fewer than `num_confirmations` accounts that are actually members at execution time. This directly matches the Critical impact category "a multisig request executed below threshold," since NEAR funds held by the multisig account can move (via `Transfer` action) or control of the account can be altered (via `AddKey`/`DeployContract`) without the intended live quorum.

### Likelihood Explanation
The precondition — a membership change (`DeleteMember`) occurring while a request from a since-removed member is still pending confirmation — is an ordinary operational event for any long-lived multisig (key rotation, offboarding a signer, responding to a suspected key compromise). No attacker collusion beyond normal multisig usage patterns is required: a stale confirmation from an already-removed member simply remains valid weight forever unless the request is explicitly deleted by a current member first.

### Recommendation
When counting confirmations in `confirm` (and in any other threshold check), filter `confirmations` down to entries that are still present in `self.members` before comparing against `self.num_confirmations`, or proactively purge/invalidate stored confirmations belonging to a member removed via `DeleteMember`.

### Proof of Concept
1. Multisig initialized with 3 members A, B, C and `num_confirmations = 2` [4](#0-3) .
2. Member A calls `add_request_and_confirm` for a `Transfer` request, adding A's confirmation (set = {A}) [1](#0-0) .
3. A legitimate governance action removes A via `DeleteMember` (e.g., A's key is suspected compromised, replaced with D). The pending request's `confirmations` set still contains "A" — nothing purges it.
4. Member B calls `confirm` on the same `request_id`. `confirm` checks `confirmations.len() as u32 + 1 >= num_confirmations` → `1 + 1 >= 2` → true, and the request executes using confirmations from A (no longer a member) and B — i.e., only 1 live member actually approved, but the request executes as if 2 did [2](#0-1) .

Note: I was unable to inspect the `DeleteMember`/`remove_member` handler implementation directly within the available iterations to confirm it does not itself scan and purge in-flight `confirmations` entries; this PoC assumes (based on the per-request, string-keyed storage model and absence of any cross-referencing logic in `confirm`) that no such purge occurs. This should be verified against the full `remove_member` implementation in `multisig2/src/lib.rs` before treating this as fully confirmed.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
