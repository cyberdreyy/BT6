### Title
Aggregated approve/reject weight can double-count a single signer's weight in the node's `StackerDBListener`, letting a stale rejection be recounted as an acceptance (or vice-versa depending on order) - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side StackerDB listener that aggregates `BlockAccepted`/`BlockResponse::Rejected` messages into `total_weight_approved` / `total_weight_rejected` uses two different, inconsistent de-duplication keys for the two message types. The `Accepted` handler gates on `gathered_signatures` (keyed by signature), while the `Rejected` handler gates on `responded_signers` (keyed by signer). A single signer who first rejects and later accepts the same block has their weight added to `total_weight_rejected` and then also added to `total_weight_approved`, because the Accept path never checks `responded_signers`.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the `Accepted` branch only skips re-adding weight if the slot already has an entry in `gathered_signatures`: [1](#0-0) 

but the `Rejected` branch gates purely on `responded_signers`: [2](#0-1) 

Sequence that breaks the invariant:
1. Signer `S` (holding its own valid key, no majority/collusion required) sends `BlockResponse::Rejected` for block `B`. `responded_signers.insert(slot_id)` succeeds, and `S`'s weight is added to `total_weight_rejected`.
2. `S` later sends `BlockResponse::Accepted` for the same `B` (e.g. after re-evaluating, or a malicious signer deliberately flip-flopping). The Accept path only checks `gathered_signatures.contains_key(&slot_id)`, which is still false (no signature was ever recorded for this slot), so `S`'s weight is *also* added to `total_weight_approved`.

The reverse order (`Accepted` then `Rejected`) is safe, because `Accepted` also inserts into `responded_signers` (line 465), so the subsequent `Rejected` branch's `responded_signers.insert(slot_id)` returns `false` and the reject weight is never added. This asymmetry means the aggregated-weight bookkeeping no longer reflects "verified distinct accepts" vs "verified distinct rejects" — the same signer's weight can land in both buckets depending purely on message arrival order, which an adversarial or buggy signer fully controls.

### Impact Explanation
`total_weight_approved` and `total_weight_rejected` are used by the coordinator to decide when a block has reached the approval threshold, when a blocking minority has rejected it, and which txids to permanently/temporarily exclude: [3](#0-2) 

Because a rejecting signer's weight is retained in `total_weight_rejected` even after that same signer later accepts, the "blocking minority" (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`) and per-txid exclusion checks can fire using stale/duplicated weight that no longer corresponds to an actual rejecting signer. This lets a single signer's earlier rejection be "recounted" alongside its own later acceptance, corrupting the aggregated-weight-vs-verified-accepts equality the coordinator relies on to decide whether to keep waiting, broadcast, or abandon/exclude txids from the block — a liveness-affecting miscount reachable by any one signer without collusion.

### Likelihood Explanation
Any single signer can trivially trigger this by sending a `Rejected` response followed by an `Accepted` response for the same block hash — both are normal, protocol-legal messages a signer can emit with its own key (e.g. a signer re-evaluating a proposal, or a byzantine signer deliberately flip-flopping to poison the miner's bookkeeping). No majority, no other signer's key, and no auth token are required.

### Recommendation
Use a single, consistent per-signer de-duplication key for both `Accepted` and `Rejected` handling in `stackerdb_listener.rs` — gate both branches on `responded_signers` (or otherwise ensure a signer's weight is attributed to exactly one of `total_weight_approved`/`total_weight_rejected` for a given block, with later messages either ignored or explicitly reconciled by removing the stale contribution from the prior bucket).

### Proof of Concept
1. Miner proposes block `B`; `BlockStatus` for `B` is initialized with empty `responded_signers`/`gathered_signatures` and zero weights.
2. Signer `S` (weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(..))` for `B`. `responded_signers.insert(slot_id)` succeeds ⇒ `total_weight_rejected += w`.
3. Signer `S` then sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(..))` for the same `B` with a validly-signed signature. `gathered_signatures.contains_key(&slot_id)` is `false` (untouched by step 2) ⇒ `total_weight_approved += w` as well.
4. Now `total_weight_approved + (weight of any other distinct approvers)` and `total_weight_rejected` both include `w`, so `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and stale rejection weight `w` can persist in `total_weight_rejected` (and in `failed_txids` per-txid tallies) even though `S` has since accepted — corrupting the coordinator's threshold/blocking-minority decisions in `signer_coordinator.rs`.
