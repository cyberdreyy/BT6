### Title
Reorg-permit unconditionally voids a signer's own signature guard for tenures with no *node-visible* blocks, enabling the signer to double-sign at the same height - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner may reorg a prior tenure and, if so, calls `record_superseded_tenure` → `SignerDb::mark_tenure_superseded` to void this signer's own conflict guard over that tenure's blocks. For a tenure whose only block never reached the stacks-node (i.e. it was only *locally* signed by this signer, not yet globally accepted), the code takes an unconditional "no blocks mined" branch that marks the tenure superseded **without checking `first_proposal_burn_block_timing` at all** and regardless of whether this signer already put its own signature on that block. This lets the signer sign a second, conflicting block at the same height in the replacement tenure, breaking the one-signature-per-height guarantee the rest of the codebase (`get_signed_conflicts`, `conflict_still_blocks`) is deliberately built to preserve.

### Finding Description
`check_parent_tenure_choice` in `stacks-signer/src/chainstate/mod.rs` iterates the tenures a new proposal would reorg and decides, per tenure, whether the reorg is permitted: [1](#0-0) 

```
// disallow reorg if more than one block has already been signed

    signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
if globally_accepted_blocks > 1 { ... return Ok(false); }

let Some(first_block_mined) = &tenure.first_block_mined else {
    // The node saw no blocks in this tenure, so the reorg takes nothing away from
    // the canonical chain. We may still hold a signature over a block in it that
    // the node has never seen (a block we accept locally is not handed to the node
    // until the whole signer set has signed it), so the reorg must still be
    // recorded if it is permitted.
    superseded_tenures.push(tenure);
    continue;
};
```

Two facts combine here:

1. `globally_accepted_blocks` only counts blocks in state `GloballyAccepted` (70%+ signature weight observed). A block this very signer locally accepted and signed (`signed_self` set, state `LocallyAccepted`) but which never reached the 70% threshold contributes **zero** to this count, so the "more than one globally-accepted block" guard never fires for it.
2. `tenure.first_block_mined` (from `client.get_tenure_forking_info`) reflects what the **stacks node** has actually processed. A locally-accepted-but-not-globally-accepted block is never handed to the node (per the code's own comment), so `first_block_mined` is `None` for that tenure.

The combination routes straight into the `else` branch, which the comment explicitly acknowledges may be voiding a live signature ("We may still hold a signature over a block in it that the node has never seen") — yet it still unconditionally pushes the tenure onto `superseded_tenures` with **no timing check** (`first_proposal_burn_block_timing` is bypassed entirely for this branch, unlike the sibling branch a few lines below that gates on `proposal_to_sortition < first_proposal_burn_block_timing`).

Once permitted, `record_superseded_tenure` calls `SignerDb::mark_tenure_superseded`: [2](#0-1) 

which stores a per-*tenure* record (not per-block). Every block this signer already signed in the superseded tenure is subsequently excluded from the conflict guard via `reorg_permit_stands`: [3](#0-2) 

```
fn reorg_permit_stands(&self, stacks_client: &StacksClient, conflict: &SignedConflictInfo) -> bool {
    let Some(superseded_by) = &conflict.superseded_by else { return false; };
    match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
        Ok(_) => true,   // permit stands: the conflict is excluded outright
        ...
    }
}
```

and per the flow described in the design doc, `PERM -- yes --> EXCL` skips straight past the freshness/liveness checks (`conflict_still_blocks`) that would otherwise refuse to sign a fresh sibling at the same height: [4](#0-3) 

So the signer proceeds to sign the new tenure's block at the same height where it already holds a live, un-superseded-by-consensus signature.

The rest of the codebase treats a signature as a bearer instrument that must never be silently invalidated ("Only staleness or node-derived death... clears a conflict" — `docs/signer-flows.md` lines 322-327; `get_signed_conflicts` doc comment, `stacks-signer/src/signerdb.rs` lines 1587-1605). This one branch is the sole exception, and it clears the conflict purely because the node hasn't seen the block yet — which is exactly the state a signature is in while it is still trying to reach 70% (i.e., still potentially live and gatherable by peers who haven't heard of the reorg).

### Impact Explanation
This lets a single signer place two valid signatures over two different, conflicting blocks at the same Stacks height in different tenures:
- Block B1 in tenure T (already signed locally by this signer, stalled below the 70% threshold, e.g. due to a slow/partial signer-set split or network delay).
- Block B2 in a fast-following tenure that reorgs T (signed once the permit clears the B1 conflict).

If straggling peer signatures for B1 (broadcast earlier, independent of this signer's later decision) still arrive and push B1 over 70% before or after B2 also reaches 70% via other peers, two conflicting blocks at the same height each carry a quorum-worthy signature set — precisely the "signer signing a conflicting block" scenario the equality guard (`get_signed_conflicts` + freshness + `conflict_still_blocks`) exists to prevent. This is a Critical-class break of the "one canonical block per height" invariant that the pre-commit/conflict machinery is designed to uphold everywhere else in the codebase.

### Likelihood Explanation
- Triggerable by a single miner (a "one-slot miner"): win tenure T, get partial signer support that stalls at less than 70% (naturally occurring during network partitions, slow signer restarts, or an intentionally slow proposal), then win the next sortition quickly and propose a tenure-change block reorging T.
- Requires no majority of signers, no other signer's key, and no access to the local signer beyond normal gossip — only that this signer itself previously signed a block that never reached global acceptance, which is an ordinary, frequently-occurring network condition (the codebase's own tests exercise 50/50 signature splits, e.g. `pre_commit_50_50_split_agrees_on_node_tip`, confirming this state is reachable in practice).
- The vulnerable branch is explicit in the code with no timing gate, unlike the sibling branch that does check `first_proposal_burn_block_timing`, making this a straightforward, deterministic trigger once the precondition (a stalled locally-signed block) exists.

### Recommendation
In `check_parent_tenure_choice`'s "no node-visible blocks" branch (`stacks-signer/src/chainstate/mod.rs`), do not unconditionally supersede the tenure. Instead:
- Check whether this signer itself has a live signature (`signed_self`/`has_signed_block_in_tenure`) over a block in the tenure being reorged, and apply the same `first_proposal_burn_block_timing` freshness check used in the sibling branch before permitting the supersession.
- Alternatively, make `mark_tenure_superseded`/`get_signed_conflicts` record the permit per-block (keyed by `signer_signature_hash`) rather than per-tenure, so a permit granted based on the node's view cannot retroactively clear a signature the node never had a chance to evaluate.

### Proof of Concept
1. Signer S signs block B1 (tenure T, height H) locally; B1 stalls below 70% group signature (e.g. two signers are network-partitioned), so B1's state stays `LocallyAccepted` and the node never receives it (`first_block_mined = None` for T when queried later).
2. A new sortition occurs quickly; the winning miner proposes a tenure-change block B2 at height H that reorgs T.
3. `check_parent_tenure_choice` evaluates T: `get_globally_accepted_block_count_in_tenure(T) == 0` (passes the ≤1 check), `tenure.first_block_mined == None` → unconditionally `superseded_tenures.push(T)`, no timing check applied.
4. `mark_tenure_superseded(T, ..., superseded_by = new tenure)` is recorded.
5. B2 crosses the pre-commit threshold; `get_signed_conflicts` finds B1 as a conflict at height H, but `reorg_permit_stands` returns true (new tenure's sortition still canonical) → conflict excluded → S signs B2.
6. S has now signed both B1 (height H, tenure T) and B2 (height H, reorg tenure) — a double signature over the same height, contingent only on B1's earlier, independently-broadcast signature still being gatherable by other signers.
