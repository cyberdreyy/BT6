## Finding

### Title
Reorg-timing bypass when a signer's local record lacks `approved_time` — signer signs a non-canonical reorg it should reject - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` is the gate that decides whether a miner may build off something other than the prior sortition (a tenure reorg). It is only supposed to permit the reorg when the tenure being displaced produced its first block suspiciously close to the sortition boundary (`first_proposal_burn_block_timing`) — a race condition, not a deliberate multi-block takeover. When the local signer has no `approved_time` recorded for that block, the code silently treats the elapsed time as `0`, which always satisfies the "poorly timed" condition and unconditionally permits the reorg.

`local_block_info` comes from [2](#0-1)  `get_first_approved_block_in_tenure`, whose query matches on `signed_self IS NOT NULL OR signed_group IS NOT NULL OR approved_time IS NOT NULL`. This means the returned record can be one this signer never locally pre-committed/signed — e.g. one it only learned about via `signed_group` (global acceptance observed from the network/node) after a restart, after being newly added to a running network, or after the local signer_db was reset. In every such case `approved_time` is `None`, and the code substitutes `0` for "time between proposal and sortition," which is always less than `first_proposal_burn_block_timing` (any nonzero config), so `checked_proposal_timing`'s branch always fires and the reorg is granted — regardless of how long the displaced tenure's block had actually been live and confirmed.

This function is the sole gate against `RejectReason::ReorgNotAllowed` both at proposal time (`check_proposal`, [3](#0-2) ) and in tenure-change validation ( [4](#0-3) , and the v2 equivalent). A signer whose local record for the displaced tenure lacks `approved_time` will therefore validate, pre-commit, and sign a tenure-change block that illegitimately reorgs an already-canonical tenure it should have rejected.

Worse, granting the reorg also calls `record_superseded_tenure` ( [5](#0-4) ), which marks the displaced tenure as sanctioned-superseded. Per `reorg_permit_stands`/`conflict_still_blocks` ( [6](#0-5) ), that record subsequently excludes the signer's own prior conflicting signature from blocking further signing — compounding the mistaken permit rather than just being a one-off error.

### Impact Explanation
This is exactly the "a signer signing an invalid/non-canonical/conflicting block" class: the reorg-timing rule exists specifically to stop a miner from replacing a tenure that legitimately mined blocks, unless the timing genuinely indicates a race. An affected signer's endorsement of an illegitimate reorg is a real signature over a conflicting/non-canonical block — and per the codebase's own documented model, "a signature is a bearer instrument that can still be aggregated toward the 70% threshold if rejecting signers change their minds" (see docs/signer-flows.md commentary around `get_signed_conflicts`), so even a single such wrongly-produced signature is treated by the design as consequential, not inert.

### Likelihood Explanation
The precondition — a signer's local DB missing `approved_time` for an older tenure's first block while that block is nonetheless known (via `signed_group`/global acceptance) — is reachable through ordinary, non-adversarial signer lifecycle events explicitly acknowledged elsewhere in this codebase: a signer added to an already-running network, a signer restart, or "a node error [that] can wipe the local state machine" (docs/signer-flows.md, section 5 commentary). A miner does not need to compromise any signer; it only needs to attempt a reorg while one or more signers are in this ordinary state, and the existing test suite (`stacks-signer/src/chainstate/tests/v2.rs`, `check_parent_tenure_choice_reorg_timing_*`) only exercises the `Some(approved_at)` branch, never the `None` fallback, so this path is untested.

### Recommendation
Do not default the elapsed time to `0` when `approved_time` is missing. A missing local timestamp should be treated as "cannot verify timing" and refuse the reorg (return `Ok(false)`) rather than "verify it as instantly poorly-timed." At minimum, fall back to a value derived from `tenure.burn_block_height`/`proposed_time` recorded elsewhere, or from the node's own record of when the block was mined, rather than assuming zero elapsed time.

### Proof of Concept
1. A signer is newly added to the network, or restarts and loses/rebuilds its local signer_db, after tenure T's first block B has already been globally accepted by the rest of the signer set (this signer only observes `signed_group` for B, never calling `mark_pre_committed`/`mark_locally_accepted` itself, so `approved_time` is `None`).
2. A miner mines a competing tenure T' that reorgs T, arbitrarily long after B was confirmed (not a genuine race).
3. On this signer, `check_parent_tenure_choice` evaluates T as a reorged tenure: `tenure.first_block_mined = Some(B)`, `get_first_approved_block_in_tenure(T)` returns B's info with `approved_time = None`.
4. `proposal_to_sortition` becomes `0`, `Duration::from_secs(0) < first_proposal_burn_block_timing` is true, so the code logs "the block was poorly timed, allowing the reorg," pushes T into `superseded_tenures`, and ultimately returns `Ok(true)`.
5. The signer proceeds to pre-commit/sign T''s tenure-change block, rejecting the correct `ReorgNotAllowed` outcome that a signer with an intact local record would have produced.

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
