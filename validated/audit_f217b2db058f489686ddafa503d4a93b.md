### Title
`parse_permissioned_burn_instruction` (ConfidentialBurn branch) mislabels accounts when proof-offset flags are inconsistent with account count - ([File: transaction-status/src/parse_token/extension/permissioned_burn.rs])

### Summary
The `ConfidentialBurn` arm of `parse_permissioned_burn_instruction` decides which optional accounts (`instructionsSysvar`, three proof context accounts) are present using a heuristic based purely on remaining account-index slots (`account_indexes.len().saturating_sub(2)`), rather than deriving the exact count from the combination of `equality_proof_instruction_offset`, `ciphertext_validity_proof_instruction_offset`, and `range_proof_instruction_offset`. Since both `instruction_data` (the three offsets) and `account_indexes` (the account list length) are independently attacker-controlled fields of a single crafted instruction, an attacker can produce a byte layout where the heuristic's account-count "budget" runs out before all semantically-required optional accounts are consumed, causing later accounts (including the true `permissionedBurnAuthority` and trailing signer) to be shifted and mislabeled.

### Finding Description
In `permissioned_burn.rs`, the `ConfidentialBurn` branch of `parse_permissioned_burn_instruction` [1](#0-0)  only requires `check_num_token_accounts(account_indexes, 4)`, i.e. at least 4 accounts, before decoding `ConfidentialBurnInstructionData` and walking a manually tracked `offset` variable to attribute `instructionsSysvar`, `equalityProofContextStateAccount`, `ciphertextValidityProofContextStateAccount`, `rangeProofContextStateAccount`, `permissionedBurnAuthority`, and finally the trailing signer/multisig fields via `parse_signers` [2](#0-1) .

Each optional field is gated by two independent, attacker-controlled conditions:
1. Whether the corresponding proof offset field is zero/non-zero (from raw `instruction_data`).
2. Whether `offset < account_indexes.len().saturating_sub(2)` (derived purely from the number of accounts attached to the instruction).

Because `instruction_data` and `account_indexes` are supplied together in one attacker-crafted instruction with no cross-validation that the two agree with each other, an attacker can set, e.g., `equality_proof_instruction_offset != 0` (offset-based, no context account expected) while `ciphertext_validity_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0` (both context-account-based, each semantically requiring one dedicated account), but only supply enough accounts for one of the two context accounts. The `saturating_sub(2)`-based length check will silently stop adding fields once slots run out, without regard to which specific proof still needs an account. The result is that the account meant to be the range-proof context account gets labeled `permissionedBurnAuthority`, and the actual owner/delegate account is mislabeled through `parse_signers` at the wrong `offset`.

This is possible because:
- `check_num_token_accounts` only enforces a minimum count (`>= 4`), not an exact count tied to the offset combination.
- The three offset booleans and the account count are never cross-checked for internal consistency anywhere in this function.
- `getTransaction` (jsonParsed) parses instructions independent of on-chain execution success, so a transaction need not even succeed for its `parsed` info to be returned this way.

### Impact Explanation
This is a decoder misreporting bug in `transaction-status`: RPC clients calling `getTransaction`/`getBlock` with `jsonParsed` for a crafted permissioned-confidential-burn instruction can be given a `permissionedBurnAuthority` field (and/or `authority`/`multisigAuthority`) that points to the wrong account (e.g., a proof context-state account) instead of the real authority, or omit the real authority entirely. Downstream integrators/indexers/wallets that trust the `parsed` JSON for display, accounting, or authority-verification purposes would show a materially wrong burn authority for the instruction — matching the "decoder misreporting" scoped impact in the question.

### Likelihood Explanation
The attacker only needs to submit one crafted transaction (or have one accepted, even if it later fails execution) containing a `spl_token_2022_interface` permissioned-burn `ConfidentialBurn` instruction with `>=4` accounts and adversarially chosen offset fields whose implied account-count does not match the account list length. This requires no privileged access — any client can build and submit such a transaction, or simply have it observed via websocket/RPC once landed (or even simulated). It is fully repeatable and deterministic given the same crafted bytes.

### Recommendation
Compute the expected number of optional accounts explicitly from the three offset fields (count of proofs using `ContextStateAccount`, plus 1 for the sysvar if any proof uses `InstructionOffset`) and validate that `account_indexes.len()` exactly equals `2 (account, mint) + <computed optional count> + 2 (authority, owner/delegate account or its trailing signers)` before assigning any field. If the count does not match, return `ParseInstructionError::InstructionNotParsable` rather than guessing via a length-remaining heuristic.

### Proof of Concept
Add a test that crafts `account_indexes` inconsistent with the offset flags, e.g. for `len == 6` with `equality_proof_instruction_offset = 1` (offset-based), `ciphertext_validity_proof_instruction_offset = 0`, `range_proof_instruction_offset = 0` (both context-based, needing 2 context accounts + 1 sysvar account = 3 optional accounts, for a correct total of `2 + 3 + 2 = 7` accounts):

```rust
#[test]
fn test_confidential_burn_offset_account_count_mismatch() {
    // Craft raw ConfidentialBurnInstructionData bytes with:
    // equality_proof_instruction_offset = 1 (InstructionOffset)
    // ciphertext_validity_proof_instruction_offset = 0 (ContextStateAccount)
    // range_proof_instruction_offset = 0 (ContextStateAccount)
    // but only supply 6 accounts (one short of the semantically correct 7).
    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let sysvar_acc = Pubkey::new_unique(); // for the offset-based eq proof
    let range_ctx = Pubkey::new_unique();  // should be labeled rangeProofContextStateAccount
    let permissioned_burn_authority = Pubkey::new_unique();
    let authority = Pubkey::new_unique();

    // account_indexes (6 total, missing the val_ctx account that a correct
    // 7-account layout would require):
    // [account, mint, sysvar, range_ctx, permissioned_burn_authority, authority]
    let account_indexes: Vec<u8> = vec![0, 1, 2, 3, 4, 5];

    // ... build instruction_data bytes for ConfidentialBurn with the above offsets ...

    let parsed_info = parse_permissioned_burn_instruction(
        &instruction_data,
        &account_indexes,
        &account_keys, // maps 0..6 to the pubkeys above in order
    ).unwrap();

    // BUG: the parser labels account_indexes[4] (permissioned_burn_authority's
    // slot) using its length-based heuristic, but because ciphertext_validity's
    // context account was never assigned a slot, `range_ctx` ends up under
    // "permissionedBurnAuthority" instead of "rangeProofContextStateAccount",
    // and the true authority/owner accounts are shifted by one.
    assert_ne!(
        parsed_info.info["permissionedBurnAuthority"],
        json!(permissioned_burn_authority.to_string())
    );
}
```

Running this against the current implementation demonstrates that `permissionedBurnAuthority` in the parsed output does not correspond to the intended authority account once the offset flags and account count diverge, confirming the index-confusion/misreporting described above.
