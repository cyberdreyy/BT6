### Title
Stale rejection weight is never retracted when a signer changes its vote from Reject to Accept, corrupting the coordinator's rejection tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
This is a direct analog of the `recoverEther`/`currentWithheldETH` bug: a state counter (`total_weight_rejected`) is incremented under one de-duplication guard but is never decremented/corrected when the underlying vote it represents becomes stale, so a later legitimate action (accepting the same block) leaves the counter permanently out of sync with the signer's actual current opinion.

### Finding Description
The node-side `StackerDBListener` tallies both acceptance and rejection weight for a proposed block in a shared `BlockInfoStatus`-like struct, but it uses **two different de-duplication mechanisms** for the two branches:

- On `BlockResponse::Accepted`, the guard is `!block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

- On `BlockResponse::Rejected`, the guard is `block.responded_signers.insert(slot_id)`: [2](#0-1) 

The signer protocol itself explicitly allows a signer to reject a block and later accept the very same block, via the documented re-evaluation/capitulation path `LocallyRejected --> LocallyAccepted : re-evaluated`: [3](#0-2) 

When this legitimate sequence happens (signer S first rejects block B, then re-evaluates and signs/accepts B):
1. `BlockResponse::Rejected` arrives first: `responded_signers.insert(slot_id)` returns `true` (first time), so `total_weight_rejected += weight(S)`.
2. `BlockResponse::Accepted` arrives later for the *same* block: the guard checks `gathered_signatures.contains_key(&slot_id)`, which is still empty for S, so it evaluates to `true` and `total_weight_approved += weight(S)` is added as well. `responded_signers.insert(slot_id)` at line 465 is a no-op since it is already present.

The result is that signer S's weight is counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously, and the earlier rejection is never retracted — exactly like `currentWithheldETH` never being decremented in `recoverEther`, leaving a permanent offset between the tracked counter and the true state.

### Impact Explanation
This breaks the equality between "aggregated rejected weight" and "signers who currently reject the block." The rejection-threshold check in `signer_coordinator.rs` relies purely on the (now-corrupted) `total_weight_rejected`: [4](#0-3) 

Because a signer's weight remains permanently booked as "rejected" even after that same signer legitimately capitulates and accepts the block, `total_weight_rejected` can cross the `>30%`-of-weight "blocking minority" threshold from stale votes alone, even while a genuine supermajority has since accepted the block. This causes the miner/coordinator to treat a validly, supermajority-signed block as globally rejected (`SignersRejected`), a liveness wedge: a legitimately-approved block is discarded and the miner is forced to abandon it, stalling block production for that tenure. This does not require a majority of colluding signers — it is triggered by the ordinary reevaluation behavior of a single signer.

### Likelihood Explanation
Reject→accept re-evaluation of the same block by one signer is a documented, normal part of the state machine (`should_reevaluate_reject_reason`, `capitulate_viewpoint`, `LocallyRejected → LocallyAccepted`), not an edge case requiring malice or a majority — it can occur any time a transient rejection reason (e.g., a stale conflict) resolves before the pre-commit/signature threshold is reached. Because network delivery ordering and processing timing are not controlled, this reject-then-accept sequence from a normal, honest signer is readily reachable in practice.

### Recommendation
Use a single, consistent per-signer state (e.g., one `HashMap<slot_id, Vote>`) to track each signer's current vote for a given block, and when a signer's vote transitions (e.g., from Rejected to Accepted), subtract the weight from `total_weight_rejected` before/while adding it to `total_weight_approved` (and vice versa), so the two tallies always reflect only the *current* vote of each signer, never a superposition of both.

### Proof of Concept
1. Coordinator/listener tracks a proposed block B with `total_weight_approved = 0`, `total_weight_rejected = 0`, `responded_signers = {}`, `gathered_signatures = {}`.
2. Signer S (weight `w`) sends `BlockResponse::Rejected(B)` — `responded_signers.insert(S)` → true, `total_weight_rejected += w`. (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-518`)
3. Signer S later re-evaluates (per the documented `LocallyRejected → LocallyAccepted` transition) and sends `BlockResponse::Accepted(B)` for the identical block hash.
4. The accept-branch guard `!gathered_signatures.contains_key(S)` is true (S was never in `gathered_signatures`), so `total_weight_approved += w` also executes. (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-465`)
5. Now `total_weight_rejected` still includes `w` from step 2 even though S has since accepted; if enough other signers likewise reject-then-accept (or if S's weight alone tips the balance combined with real rejecters), `total_weight_rejected` can cross the 30%-blocking-minority threshold in `signer_coordinator.rs` and cause the coordinator to declare the block `SignersRejected` despite a genuine supermajority of current votes being `Accepted`.
