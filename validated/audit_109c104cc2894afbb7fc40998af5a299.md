### Title
Stale loss-adjusted withdraw receipt is re-paid at par after a new `requestWithdraw`, draining funded claim reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` looks up a haircutted receipt exclusively through `lastWithdrawRequest[_user]` (the *latest* request epoch). When an attacker makes a new withdraw request in a later epoch before claiming, the pointer is overwritten, the loss-adjusted claim path becomes unreachable, and `_claimFundedWithdrawRequest` pays the aggregated `withdrawsRequests[_user]` — including the already-haircutted old receipt — at 100% par. This mirrors the CVE class: a credential (receipt) issued for one context (a loss epoch, priced at `lossRecoveryPriceByEpoch`) is accepted in another context (a fully-funded epoch) because the claim path never validates which epoch/price each receipt belongs to.

### Finding Description
- On a loss stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` and zeroes `pendingWithdraws`; the strategy holds only the haircut-funded amount for that epoch's receipts [1](#0-0) .
- `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and only applies the haircut if `lossRecoveryPriceByEpoch[lossEpoch] != 0` [2](#0-1) .
- `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` while *accumulating* `withdrawsRequests[_user] += _amount` — the old haircutted basis stays in the aggregate [3](#0-2) .
- `_claimFundedWithdrawRequest` then pays `normalAmount + apr0...` at par with no per-epoch price check; only `withdrawsRequestsByEpoch` retains per-epoch data, and it is never consulted on the funded path [4](#0-3) .

Broken invariant: one receipt one (correctly-priced) payout. A receipt whose funded backing is `basis * lossRecoveryPrice / 1e18` is redeemed for `basis`.

### Impact Explanation
The attacker withdraws more underlying than the strategy reserved for them. The excess `(basis - basis*price)` is paid from the strategy's funded-claim reserve, directly stealing from other users' matured withdraw claims (or rendering later claims unpayable → insolvency). Quantified loss: up to the full unrealized-loss portion of the attacker's prior receipt, i.e. `oldBasis * (1 - lossRecoveryPrice)`, which can be an arbitrarily large fraction of the pool's pending-withdraw bucket in a heavy-loss epoch.

### Likelihood Explanation
Attacker is an ordinary KYC'd lender/tranche holder (in-scope unprivileged role). Requirements: (1) an epoch stopped via `stopEpochWithDuration`/`collectWithdrawFunds` with `_amount < pendingBasis` (manager action, honest, routine loss path); (2) attacker holds a pending receipt in that epoch; (3) attacker calls `requestWithdraw` again in any later epoch, waits for it to mature, then calls `claimWithdrawRequest`. No privileged collusion, no timing race beyond one extra epoch wait. Receipt strategy tokens are minted 1:1 at each request, so the `_burn(_user, ...)` always succeeds.

### Recommendation
Track and claim receipts strictly per epoch: in `claimWithdrawRequest`, iterate/aggregate each outstanding `withdrawsRequestsByEpoch[_user][e]` applying `lossRecoveryPriceByEpoch[e]` (or `defaultRecoveryPrice` for `defaultRecoveryEpoch`) per epoch instead of keying the loss claim off `lastWithdrawRequest`. Alternatively, prevent a new `requestWithdraw` while the user has an unclaimed loss-adjusted receipt, or settle (`_claimLossAdjustedWithdrawRequest`) inside `requestWithdraw` before overwriting `lastWithdrawRequest`.

function testLossReceiptRepaidAtPar() external {
    // epoch 1: user deposits AA, starts epoch, requests withdraw of X
    uint256 x = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
    _startEpochAndCheckPrices(1);

    // epoch 1 stops with a loss: borrower funds only pendingToFund < pendingBasis
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    _repayBorrower(expectedInterest + pendingToFund);
    cdoEpoch.stopEpochWithDuration(apr, expectedInterest, duration, lossAmount);
    // lossRecoveryPriceByEpoch[2] = pendingToFund/pendingBasis < 1e18

    // attacker does NOT claim; instead requests again in next epoch
    cdoEpoch.requestWithdraw(remaining, address(AAtranche)); // lastWithdrawRequest -> epoch3
    _startEpochAndCheckPrices(3);
    _stopEpochAndCheckPrices(3, apr, _expectedFundsEndEpoch()); // funds only new request

    // claim: loss path skipped (lastWithdrawRequest=3, no price), funded path pays old+new at par
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, x + newAmount);
    // strategy paid x instead of x*lossRecoveryPrice/1e18 -> reserve shortfall = x*(1-price)
}
```

Key assertions: `strategy.lossRecoveryPriceByEpoch(lossEpoch) != 0` is set, `lastWithdrawRequest` is later overwritten, and the payout equals the un-haircutted sum while the strategy only held `pendingToFund` for the old receipt.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
