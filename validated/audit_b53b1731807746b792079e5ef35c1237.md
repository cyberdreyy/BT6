### Title
Blocking QUIC connection close while holding `ConnectionCache` write lock can stall/deadlock TPU send path - (File: quic-client/src/lib.rs)

### Summary
Like the nano-node fix (avoid holding `tcp_channels::mutex` while blocking on `io_context` shutdown during channel close), Agave's `ConnectionCache::create_connection_internal` evicts pooled `QuicPool` entries while holding the cache's `map: Arc<RwLock<IndexMap<SocketAddr, QuicPool>>>` **write** lock. Dropping the evicted `QuicPool` synchronously invokes `close_quic_connection`, which — outside of a Tokio worker context — calls `RUNTIME.block_on(connection.close())`, a blocking wait on an async runtime task, executed while the synchronous `RwLock` write guard is still held.

### Finding Description
`ConnectionCache::create_connection_internal` performs LRU-style eviction under the write lock: `map.swap_remove_index(n)` [4](#0-3) . `swap_remove_index` drops the removed `QuicPool` value in place, and `QuicPool`'s `Drop` implementation iterates over its connections and calls `close_quic_connection(connection.0.clone())` for each [2](#0-1) .

`close_quic_connection` explicitly blocks the calling thread on the global QUIC runtime when not already inside a Tokio worker: `RUNTIME.block_on(connection.close())` [3](#0-2) . This blocking call happens while the caller (`create_connection_internal`) is holding `map`, a `std::sync::RwLock` write guard passed by `&mut` reference from `create_connection` [5](#0-4) .

This is structurally the same hazard the nano-node commit addresses: a synchronous lock is held across a blocking/async-runtime-dependent close operation. If the dedicated `RUNTIME` (used for all QUIC client connection closes) becomes saturated or if any other code path attempts to acquire `ConnectionCache::map`'s read/write lock from within a task running on that same runtime (e.g. the async connection-creation thread also reads `map`: `create_connection_async_thread` takes `map.read().unwrap()` [6](#0-5) ), the thread holding the write lock in `create_connection_internal` can block indefinitely waiting for the `RUNTIME.block_on` to complete, while other callers (e.g. `get_or_add_connection`'s read-lock acquisitions in the TPU client send path) queue up behind the writer, starving new connection creation cluster-wide for that `ConnectionCache` instance (used for TPU/vote/forwarding sends).

### Impact Explanation
If the blocking close stalls (e.g. due to `RUNTIME` executor contention or a slow/unresponsive quinn shutdown), every thread needing to send transactions/votes through this `ConnectionCache` (validator's TPU client, vote sending, forwarding) blocks on the write/read lock, effectively stalling outbound transaction/vote submission for that cache instance — a liveness/availability degradation on the sending path, not a memory-safety or fund-theft bug.

### Likelihood Explanation
This path triggers routinely under normal validator operation whenever the connection cache reaches `max_connections` and must evict an entry to add a new peer connection (common under high peer churn, e.g. leader schedule changes) — `create_connection_internal`'s eviction loop runs on every cache-full insertion [7](#0-6) . The severity of an actual deadlock depends on the `RUNTIME`'s thread pool being saturated at the same moment, which is plausible under load but not guaranteed on every eviction — this is a latent stall risk rather than a guaranteed deadlock on every call.

### Recommendation
Mirror the nano-node fix: swap/take the evicted `QuicPool` entries out of the `map` while holding the lock only long enough to update the `IndexMap`, then drop the lock before running any code that can block (i.e., before the evicted `QuicPool`'s `Drop`/`close_quic_connection` executes). Concretely, collect evicted pool values into a `Vec` inside the write-lock critical section, release the lock, and drop the vector (triggering the blocking closes) afterward — analogous to swapping the channel set out from under `tcp_channels::mutex` before closing entries.

### Proof of Concept
Not independently verified against a live deadlock reproduction (would require driving `RUNTIME` to saturation while forcing eviction); the report is based on static code-path analysis showing the write lock in `create_connection_internal` is held across a call chain that can synchronously block on the async runtime (`swap_remove_index` → `QuicPool::drop` → `close_quic_connection` → `RUNTIME.block_on`).

pub(crate) fn close_quic_connection(connection: Arc<QuicClient>) {
    // Close the connection and release resources
    trace!("Closing QUIC connection to {}", connection.server_addr());
    // Connection caches can be dropped by async callers, such as admin RPC set-identity;
    // blocking on RUNTIME from a Tokio worker would panic.
    if tokio::runtime::Handle::try_current().is_ok() {
        let _handle = RUNTIME.spawn(async move {
            connection.close().await;
        });
    } else {
        RUNTIME.block_on(connection.close());
    }
}
