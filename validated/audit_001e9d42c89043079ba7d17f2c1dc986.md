## #ValidVulnerability found for this question.

### Title
Confirmations from removed multisig members are never purged from pending requests, allowing execution below the true live-member threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
When a multisig member is removed (`DeleteKey` in `multisig`, `DeleteMember` in `multisig2`), the contract only deletes pending requests that were *authored* by the removed member. It does not purge that member's *confirmations* on other still-pending requests. Because the confirmation-threshold check only compares the size of the stored `confirmations` set to `num_confirmations`, a stale confirmation from a since-removed member still counts toward the threshold, letting a request execute with fewer live, currently-authorized confirmations than the configured threshold requires.

### Finding Description
The confirmation counting binding that must hold is: `confirmations recorded for a request == confirmations from members who are still live/authorized when the request is executed`. This binding is broken because removal only cleans up requests keyed by authorship, not confirmation membership.

In `multisig2/src/lib.rs`, `delete_member` only removes requests where the removed member is the *author* (`r.member == member`), and clears `confirmations` for *those* requests only: [1](#0-0) 

Any other pending request that the removed member had already *confirmed* (but did not author) keeps that member's identifier in its `confirmations: LookupMap<RequestId, HashSet<String>>` entry untouched.

The threshold check in `confirm` only counts the size of this (possibly stale) set: [2](#0-1) 

The same pattern exists in the original `multisig` contract: `DeleteKey` only removes requests authored by (`signer_pk == pk`) the deleted key: [3](#0-2) 

and `confirm` again only checks the raw set size against `num_confirmations`: [4](#0-3) 

This is structurally the same class of bug as the DKIM report: an identifier/record meant to gate a privileged action (`identifier` in the recoveries mapping / `confirmations` set in the multisig) is derived from state that is not re-validated against the currently valid set (validated `SignatureMeta` fields / currently live members) at the time the gated action executes.

### Impact Explanation
This crosses the "multisig request executed below threshold" boundary explicitly called out as Critical impact. A request can execute a `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, or `DeployContract` action with strictly fewer *currently authorized* confirmations than `num_confirmations`, because a phantom confirmation from a removed member is still tallied. This allows funds to move or account control to change without the intended quorum of currently-trusted keyholders actually agreeing.

### Likelihood Explanation
Medium: it requires (a) a request pending with partial confirmations, (b) one of the confirmers being removed from the multisig (e.g., due to key rotation/compromise/offboarding) without that specific request being deleted, and (c) the remaining live members topping up confirmations to reach the threshold, unaware a stale one is being counted. This is a realistic operational sequence for any multisig that rotates members over its lifetime while requests are in flight.

### Recommendation
When deleting a member/key, iterate all pending requests' `confirmations` sets (not just those authored by the removed member) and strip the removed member's identifier from each. Alternatively, when tallying confirmations in `confirm`, filter the stored confirmation set to only those entries that are still present in `self.members` before comparing against `num_confirmations`, so removed members' confirmations never count.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` for a `Transfer` action → confirmations = `{A}`.
3. `B` calls `confirm` on the same request → confirmations = `{A, B}` (still below 3, request stays pending).
4. Via a separate fully-confirmed request, the group executes `DeleteMember { member: B }` (e.g., because B's key was compromised). `delete_member` only removes requests authored by `B`; the pending Transfer request (authored by `A`) is untouched, so its `confirmations` set still contains `B`.
5. `C` (a live member) calls `confirm` on the pending Transfer request → `confirmations.len() == 3 >= num_confirmations`, so `execute_request` runs and the transfer executes — even though only `A` and `C` are actually live members who confirmed; `D` never confirmed and `B` was no longer authorized. The request executed with 2 genuine live confirmations instead of the required 3. [1](#0-0) [2](#0-1)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

        );

            let request = self.remove_request(request_id);

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
