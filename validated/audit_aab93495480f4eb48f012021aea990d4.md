### Title
Inconsistent/ambiguous cache-scoping semantics in `responseCache` allow cross-workflow-owner response reuse and cache-poisoning across differing `CacheSettings` - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The `applyInterest` finding is a bug class about a function whose return semantics (delta vs. absolute value) are used inconsistently by different callers, leading to miscalculated balances. The `chainlink--007` gateway HTTP-capability response cache exhibits the same class of bug: the cache key (`req.Hash()`) is documented to scope by `workflow ID` for isolation, but the implementation and its own tests show the hash intentionally ignores `WorkflowID` and `CacheSettings` (`MaxAgeMs`, `Store`), while different call sites (`Fetch` vs `Set`) apply these fields inconsistently to decide whether to read/write the cache.

### Finding Description
`responseCache.Fetch` and `responseCache.Set` both use `req.Hash()` as the cache key [1](#0-0) . The package comment claims the key is derived from "method, URL, headers, body, workflowOwner" [2](#0-1) , but the accompanying test suite confirms the hash is explicitly independent of `WorkflowID` and `CacheSettings` (only `WorkflowOwner` differentiates the hash) [3](#0-2) . Meanwhile, the README explicitly states "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [4](#0-3) , which directly contradicts the implementation (isolation is actually keyed on `WorkflowOwner`, not `WorkflowID`).

Separately, the two write paths for populating the cache are inconsistent, mirroring the `applyInterest` "some callers add, some don't" problem: `makeOutgoingRequest` decides between `Fetch` (read+write) and `Set` (write only) based on `req.CacheSettings.MaxAgeMs > 0`, and independently gates writing on `req.CacheSettings.Store` [5](#0-4) . Because `CacheSettings` is not part of the hash, one workflow node can request with `MaxAgeMs=0, Store=true` (write-only, via `Set`), and another can request with `MaxAgeMs>0` (read via `Fetch`) for the same `Method+URL+Headers+Body+WorkflowOwner` — since the key collides regardless of caller intent, a response written under one node/workflow request's caching policy can be served to a different request that never intended to consult a shared cache for that endpoint, and requests from different workflows under the same `WorkflowOwner` can read each other's cached HTTP responses.

### Impact Explanation
Unprivileged workflow owners (or any workflow issuing outbound HTTP capability requests under the gateway) can have HTTP responses (including any secrets embedded in headers/body from a first-party endpoint, or 4xx/2xx error content) served across workflows sharing the same `WorkflowOwner`, since `WorkflowID` is not part of the cache key despite the documented "workflow ID" isolation guarantee. This is cross-user/cross-workflow response confusion — data from one workflow's outbound HTTP action can leak into another workflow's response for that owner, without any privileged or malicious-node action required, purely because of the mismatch between the intended workflow-scoped design and the actual owner-scoped hash implementation.

### Likelihood Explanation
Any workflow can set `CacheSettings.Store = true` on its `OutboundHTTPRequest`, and any other workflow belonging to the same owner and hitting the same URL/method/headers/body combination with `MaxAgeMs > 0` will transparently receive the cached (possibly stale or unintended) response via `Fetch` [6](#0-5) . This requires no privileged access — it is reachable purely through normal workflow-node-originated `OutboundHTTPRequest` traffic passed through the gateway.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the cache key hash so isolation matches the documented behavior, and make the cache write/read decision path consistent — i.e., derive both `Fetch`'s "should read" and `Set`'s "should write" strictly from the same `CacheSettings` semantics, ideally binding `CacheSettings` into the key or validating it consistently in one place instead of splitting the check between `MaxAgeMs > 0` in `makeOutgoingRequest` and `Store` in two different call sites.

### Proof of Concept
1. Workflow A (owner `0xabc`, workflow ID `wf-1`) issues an `OutboundHTTPRequest` to `GET https://api.example.com/data` with `CacheSettings{Store:true, MaxAgeMs:0}` — this is fetched fresh and written to cache via `Set` (`http_handler.go:436-440`), because `MaxAgeMs==0` takes the `else` branch.
2. Workflow B (same owner `0xabc`, but different workflow ID `wf-2`) issues the same `GET https://api.example.com/data` request with `CacheSettings{MaxAgeMs: 600000}` — this hits `Fetch` (`http_handler.go:433-435`), computes the same `req.Hash()` (since `WorkflowID` and `CacheSettings` are excluded per `response_cache_test.go:139-149`), and receives Workflow A's cached response without ever calling the HTTP client, confirming cross-workflow leakage under a shared owner.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
