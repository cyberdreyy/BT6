### Title
Fail-open tenure-conflict check lets a signer sign a duplicate/conflicting tenure-start block on a transient node-RPC error - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The report's core pattern — a value that is checked once, then trusted through an unguarded window where an adversarial or transient condition can invalidate it — reappears in `handle_block_pre_commit`'s own-tenure conflict guard. `validate_tenure_change_payload`'s `DuplicateBlockFound` check runs only at proposal time and is documented as **not** re-run at signing (`docs/signer-flows.md:425-437`). The only remaining defense against signing two conflicting tenure-start blocks in the same tenure, once the pre-commit threshold is crossed, is the guard at `stacks-signer/src/v0/signer.rs:1432-1457`, and that guard fails open when the node RPC call it depends on errors.

### Finding Description
`check_latest_block_in_tenure`/`validate_tenure_change_payload` enforce "no second signed tenure-start block per tenure" only at proposal arrival [1](#0-0) . At the moment the signer actually signs (crossing the 70% pre-commit weight threshold), `handle_block_pre_commit` re-derives whether an existing signed conflict in the block's **own tenure** should still block signing by asking the node for that tenure's canonical tip: [2](#0-1) 

If `stacks_client.get_tenure_tip(...)` returns `Err(e)`, the code logs a warning that it is "Treating the tenure as unconfirmed" and simply falls through — the `return` that would refuse to sign is only inside the `Ok` branch when `tip_height >= chain_length`. Falling through past this block leads directly to `mark_locally_accepted` and a broadcast signature a few lines later: [3](#0-2) 

Because the duplicate-tenure-start check is a proposal-time-only guard and this is the sole re-derivation of that invariant at sign time, a single query failure at exactly the wrong moment converts the "still blocks" branch into "does not block," and the signer signs a tenure-start block it should have refused, in a tenure where it already holds a conflicting signed block.

### Impact Explanation
This breaks the "one signed tenure-start block per tenure" equality the whole conflict-checking machinery (sections 5 and 7 of the flow doc) exists to enforce: a signer ends up putting its signature on a **conflicting** block, which is one of the explicitly listed Critical impacts (signer signing a conflicting block). Two tenure-start blocks signed by overlapping signer weight for the same tenure is exactly the kind of split-brain condition the pre-commit/conflict design is meant to prevent.

### Likelihood Explanation
This requires no majority of signers and no key compromise — a single signer instance experiencing a transient RPC hiccup to its own node (timeout, connection reset, or a load/latency spike around the very moment its pre-commit tally crosses threshold) is enough to trigger the fail-open branch for that signer. Because pre-commit weight tallying happens repeatedly as commits stream in, and the erroring branch is only reached on the specific race where a stale-but-not-fresh conflict already exists in the same tenure, the precondition (an existing signed sibling in the same tenure) does require some prior forking/timing already occurring — but no adversary control over other signers is needed, matching the "one-slot miner plus gossip/timing" threat model.

### Recommendation
Do not fail open on `get_tenure_tip` error inside the same-tenure conflict guard. On a lookup failure, the safe default is to refuse to sign (return, as in the `HOLD1`/`ConnectivityIssues` treatment used elsewhere in the flow), not to treat the tenure as unconfirmed and proceed toward a signature. Alternatively, re-run the full `validate_tenure_change_payload`/`DuplicateBlockFound` check at signing time instead of relying solely on this node-tip lookup as the last line of defense.

### Proof of Concept
1. A miner proposes tenure-start block `A` for tenure `T`; it collects enough signed acceptances to become the tenure's tip.
2. The same miner (or a colluding miner after a fork) proposes a second tenure-start block `B` for tenure `T`, which does not hit the proposal-time `DuplicateBlockFound` check because of timing (e.g. it was queued before `A`'s signature landed, or the check's own freshness/consensus-visible state hadn't caught up — the "stale" branch discussed in the flow doc's section 5).
3. `B` accumulates pre-commit weight past threshold. `handle_block_pre_commit` finds the conflict with `A` at `consensus_hash == B.consensus_hash` (same tenure) and calls `stacks_client.get_tenure_tip(&B.header.consensus_hash)`.
4. If that RPC call errors for this signer at this instant (network blip, node busy), the code takes the `Err(e)` branch, logs and "treats the tenure as unconfirmed," and does **not** return.
5. Execution falls through the `if !conflicts.is_empty() { info!(...) }` log and reaches `mark_locally_accepted` / `handle_block_signature`, producing a signature over `B` even though `A` already exists as the tenure's signed tip — a conflicting/duplicate signature [4](#0-3) .
