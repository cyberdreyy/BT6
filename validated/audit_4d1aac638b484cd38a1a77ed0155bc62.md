### Title
Multisig request can execute below threshold using a stale confirmation from a removed member/key - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
Both NEAR multisig contracts (`multisig/src/lib.rs` and `multisig2/src/lib.rs`) determine whether a pending request has "enough" approvals purely by counting the size of the `confirmations` set stored for that `request_id`, without re-validating that every entry in that set still belongs to a live/current member at the moment the count is checked. When a member (or access key) is removed via `DeleteMember`/`DeleteKey`, the cleanup logic only purges confirmations for requests that the removed member *originally created*, not confirmations that member gave to *other* still-pending requests created by someone else. Those stale confirmations remain counted toward `num_confirmations`, allowing a request to execute with fewer live, currently-authorized approvals than the configured threshold.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides whether to execute a request purely from the cached confirmation-set size: [1](#0-0) 

The membership check (`current_member()`) is only applied to the *caller* of `confirm`, not retroactively to the *already stored* entries in `confirmations`. Those entries are `String` representations of members captured at the time they called `confirm`, with no re-validation of liveness when the set is later re-read to decide whether the threshold is reached.

When a member is removed, `delete_member()` only removes confirmations/requests for requests that member itself originated (`r.member == member`), not requests it merely confirmed: [2](#0-1) 

So if member `A` confirms a request `R` that was created by member `B` (i.e. `R`'s stored `member` field is `B`, not `A`), and afterward the multisig removes `A` via a `DeleteMember` request, `delete_member` iterates `self.requests` filtering `r.member == A` — this does **not** match `R` (whose `member` is `B`), so `R`'s confirmation set (still containing `A`) is left untouched. `A`'s stale confirmation continues to count toward `R`'s threshold even though `A` is no longer `self.members`-resident and can no longer legitimately confirm anything going forward.

The exact same root cause exists in the older public-key based contract, `multisig/src/lib.rs`: `DeleteKey` only purges requests originated by the deleted key (`r.signer_pk == pk`), not confirmations that key gave to other pending requests: [3](#0-2) [4](#0-3) 

This is the direct NEAR analog of the reported Safe/HatsSignerGate issue: the binding that should hold is `confirmations counted == confirmations from currently-live/authorized signers`. In both the Safe/HSG bug and this contract, the code that *tallies* approvals toward a threshold does not use the same, live set of authorized parties that governs whether a party is currently allowed to approve — a party that was valid when it signed/confirmed, but is no longer valid at execution time, is still counted.

### Impact Explanation
This breaks the core multisig custody guarantee that a request can only execute once `num_confirmations` *currently authorized* members have approved it. An attacker scenario:
1. Multisig has members `{A, B, C, D}`, `num_confirmations = 2`.
2. `B` creates request `R` (e.g. `Transfer` draining funds) via `add_request` (not auto-confirmed).
3. `A` calls `confirm(R)` — `confirmations(R) = {A}` (1 < 2, not yet executed).
4. Separately, `C` and `D` create and confirm a `DeleteMember{member: A}` request, removing `A` from `self.members` (this is a legitimate, in-scope multisig operation requiring only the existing threshold, not a compromise).
5. `delete_member(A)` only purges requests whose `r.member == A`; `R`'s `member` is `B`, so `R` and its confirmation set `{A}` survive untouched.
6. `B` now calls `confirm(R)` — `confirmations.len() + 1 == 2 >= num_confirmations`, so `R` executes immediately, funded by only one currently-live approval (`B`) plus one stale/invalid approval (`A`, no longer a member).

This is exactly the "multisig request executed below threshold" Critical impact: NEAR (or any action requiring the threshold, including adding a full-access key or changing `num_confirmations` again) can be pushed through with fewer than the intended number of live, authorized approvers, letting funds move or privileged state changes occur without genuine threshold consensus.

### Likelihood Explanation
This does not require any privileged position beyond being one of the existing members (an "unprivileged" party relative to the funds/threshold-boundary itself, since a minority of members below threshold cannot otherwise act alone). It requires: (a) at least one pending, unconfirmed-to-completion request created by someone other than the confirmer, (b) a legitimate, in-scope member-removal request executed later. Given human/organizational multisig turnover (removing departing members/keys) is an expected, documented operation, and the contract explicitly supports `DeleteMember`/`DeleteKey` as normal actions, this stale-confirmation scenario is readily triggerable in normal operational flow, not a contrived edge case.

### Recommendation
When counting confirmations in `confirm()` (and in `get_confirmations()`), filter the stored confirmation set against the *current* `self.members` (or `num_requests_pk`/live-key set in `multisig/src/lib.rs`) before comparing against `num_confirmations`, e.g.:
```rust
let live_count = confirmations.iter().filter(|m| self.members.contains(...)).count();
if live_count as u32 + 1 >= self.num_confirmations { ... }
```
Alternatively, when a member/key is removed, iterate over **all** requests and prune the removed member's entry from every confirmation set (not only requests it originated), ensuring `confirmations` never contains stale, no-longer-authorized entries.

### Proof of Concept
See the step-by-step scenario in **Impact Explanation**: with members `{A,B,C,D}` and `num_confirmations=2`,
1. `B.add_request(Transfer)` → `request_id=R`, `confirmations[R] = {}`.
2. `A.confirm(R)` → `confirmations[R] = {A}` (not executed, 1<2).
3. `C.add_request_and_confirm(DeleteMember{A})`, `D.confirm(...)` → executes, removing `A` from `members`; `delete_member` only checks `r.member == A` (true only for requests A itself created), so `confirmations[R] = {A}` remains.
4. `B.confirm(R)` → `confirmations[R].len() + 1 == 2 >= num_confirmations` → `R` (the `Transfer`) executes using `A`'s stale, now-unauthorized confirmation, i.e. with only one live member's actual approval instead of the required two. [5](#0-4) [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
