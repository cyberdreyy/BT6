### Title
Unauthenticated `/proposal_response` HTTP endpoint lets a network attacker spoof `BlockValidateOk` and make a signer sign an unvalidated block - (File: `libsigner/src/events.rs`)

### Summary
The `stacks-signer`'s inbound event-observer HTTP server (`SignerEventReceiver`) accepts POST requests on `/proposal_response` (and the other event routes) from **any TCP client**, with no authentication, no source-address check, and no binding of the response to an outstanding request. Any payload that deserializes as `BlockValidateResponse` is treated as authoritative and fed directly into `Signer::handle_block_validate_response`, which — on an `Ok` verdict — drives the signer straight to `mark_pre_committed`/signing without the block ever having been checked by the trusted `stacks-node`'s `/v3/block_proposal` validator. This mirrors the RADIUS bug class: a party that should only trust responses from one authenticated peer instead accepts the first matching message from anyone, with no signature or request/response binding.

### Finding Description
The signer's proposal-validation flow is a two-hop request/response over plain, unauthenticated HTTP:

1. The signer submits a block for validation to its own trusted node via `StacksClient::submit_block_for_validation`, which authenticates *outbound* to the node with an `Authorization` header [1](#0-0) .
2. The node validates asynchronously and POSTs the verdict back to the signer's configured `events_observer` endpoint at `/proposal_response` [2](#0-1) .
3. That inbound POST is handled by `SignerEventReceiver::next_event`, which dispatches purely on `request.url()`, with **no authentication check at all** — no `Authorization` header, no shared secret, no source IP restriction: [3](#0-2) 
4. `process_event` merely reads the HTTP body, JSON-deserializes it into a `BlockValidateResponse`, and converts it into a `SignerEvent::BlockValidationResponse` — again with no verification of provenance: [4](#0-3) 
5. `handle_block_validate_ok` only checks that the `signer_signature_hash` matches a block the signer is already tracking (`block_lookup_by_reward_cycle`) and that it hasn't already been decided; it performs **no check that the message actually originated from the local stacks-node it submitted the block to**: [5](#0-4) 
6. If accepted, the signer proceeds to `mark_pre_committed`, broadcasts `send_block_pre_commit`, and ultimately signs the block once its own pre-commit weight check passes — all triggered by a message an attacker forged: [6](#0-5) 

Contrast this with the node-side `/v3/block_proposal` endpoint, which explicitly requires a matching `Authorization` header before accepting a request from the miner/signer direction: [7](#0-6) . There is no analogous protection on the signer's receiving side, and the reference configuration binds this listener to `0.0.0.0`, i.e., all interfaces, not loopback-only: [8](#0-7) [9](#0-8) .

`check_block_against_signer_db_state`, which runs after receiving the "Ok" verdict, only re-checks the block against the signer's own local DB state (tenure-change confirmation, "last block in tenure") — it does **not** redo the node's chainstate/transaction/cost/tenure-canonicality validation that `postblock_proposal.rs::validate` performs. So a forged `Ok` response is not caught by this re-check; it only guards against races with other locally-known blocks, not against the response being fabricated. [10](#0-9) 

This exactly matches the RADIUS advisory's root cause: "the receive path does not check the source IP/port, does not match the response identifier to the outstanding request, and does not verify ... any non-Reject/non-Challenge packet is treated as success." Here, the "packet" is an HTTP POST to `/proposal_response`, and "success" is a fabricated `BlockValidateOk`.

### Impact Explanation
This breaks the **signed-vs-validated equality**: the signer is designed to only sign a block after the trusted node's chainstate validator (`NakamotoBlockProposal::validate`) approves it (checking tenure canonicality, parent linkage, burn amounts, tx execution, timestamps, etc., in `stackslib/src/net/api/postblock_proposal.rs`). By spoofing the `Ok` verdict on the unauthenticated `/proposal_response` port, a network attacker (a one-slot miner, or anyone who can route packets to the signer's listening address/port — which per the reference config is `0.0.0.0`, not loopback) can make an individual signer produce a valid Schnorr/secp256k1 signature over a block it never actually had validated. This is a single-signer, no-majority-required action: the attacker only needs to know the `signer_signature_hash` of a block already circulating as a `BlockProposal` (which is broadcast in the clear over StackerDB to all miners and signers), craft a `BlockValidateOk` JSON body with that hash, and POST it to the signer's event port before/instead of the real node's response arrives. If several signers' ports are reachable this way, this could contribute forged signatures toward the aggregate threshold for a block that was never truly chainstate-validated — i.e., a **signer signing an invalid/non-canonical block**, which the rules classify as Critical.

### Likelihood Explanation
Reachability depends on network exposure: if a signer's `events_observer`/`endpoint` HTTP port is reachable from outside the loopback interface (the sample/reference configs literally set `endpoint = "0.0.0.0:30000"`), any attacker with network access to that port can exploit this without needing any signer key, majority collusion, or the node's `auth_token` (that token only protects the *signer→node* submission path, not the *node→signer* response path). No cryptographic forgery is required at all — this is strictly weaker for the attacker than RADIUS spoofing, since there isn't even a shared-secret/Response-Authenticator concept on this channel to begin with.

### Recommendation
Add authentication and provenance binding to the signer's inbound event HTTP server, symmetric to what already protects the node's `/v3/block_proposal` endpoint:
- Require the same `auth_password`/`auth_token` (already configured, but currently unused for validating inbound requests) as an `Authorization` header check inside `SignerEventReceiver::next_event`/`process_event` before accepting `/proposal_response`, `/stackerdb_chunks`, `/new_block`, `/new_burn_block`.
- Restrict the listener to loopback by default, or explicitly document/enforce that it must not be exposed beyond a trusted network boundary, similar to the loopback-only guidance for `/v3/block_proposal`.
- Bind validation responses to the specific outstanding request (e.g., verify the response was solicited by comparing against `submitted_block_proposal` state and, ideally, verify the response came over an authenticated channel to the specific configured `node_host`) rather than accepting any JSON body matching a locally-tracked hash.

### Proof of Concept
1. Attacker observes a `BlockProposal` broadcast over the `.miners`/signer StackerDB contract (visible to any network participant) and extracts `signer_signature_hash` for a block that has not yet been (or will never be) validated by the real node.
2. Attacker sends: `POST http://<signer-endpoint>:30000/proposal_response` with body `{"result":"Ok","signer_signature_hash":"<hash>","cost":{...zero...},"size":..., ...}` matching the `BlockValidateOk` JSON schema, with no `Authorization` header (none is required — see `libsigner/src/events.rs:413-440`).
3. `SignerEventReceiver` accepts it via `process_event::<T, BlockValidateResponse>` and forwards `SignerEvent::BlockValidationResponse(Ok(...))`.
4. `Signer::handle_block_validate_ok` finds the locally-tracked `block_info` for that hash, passes the local-DB-only re-check (`check_block_against_signer_db_state`), calls `mark_pre_committed`, and proceeds toward `send_block_pre_commit`/signing — even though the real node never validated the block.

Note: I could not fully trace every downstream consumer of `SignerEvent::BlockValidationResponse` for defense-in-depth mitigations elsewhere in the codebase (e.g., whether some deployments wrap this HTTP listener in a reverse proxy with auth by convention); this assessment is based solely on the in-repo code path and the reference configuration files shown above.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}

    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }

        // Ensure that the block is the last block in the chain of its current tenure.
        match SortitionData::check_latest_block_in_tenure(
            &proposed_block.header.consensus_hash,
            proposed_block,
            &mut self.signer_db,
            stacks_client,
            self.proposal_config.tenure_last_block_proposal_timeout,
            self.proposal_config.reorg_attempts_activity_timeout,
        ) {
            Ok(is_latest) => {
                if !is_latest {
                    warn!(
                        "Miner's block proposal does not confirm as many blocks as we expect";
                        "proposed_block_consensus_hash" => %proposed_block.header.consensus_hash,
                        "proposed_block_signer_signature_hash" => %signer_signature_hash,
                        "proposed_chain_length" => proposed_block.header.chain_length,
                    );
                    Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                } else {
                    None
                }
            }
            Err(e) => {
                warn!("{self}: Failed to check block against signer db: {e}";
                    "signer_signature_hash" => %signer_signature_hash,
                    "block_id" => %proposed_block.block_id()
                );
                Some(self.create_block_rejection(
                    RejectReason::ConnectivityIssues(
                        "failed to check block against signer db".to_string(),
                    ),
                    proposed_block,
                ))
            }
        }
