## Title
Permissionless `distribute()` in vesting and staking_contract can be indefinitely griefed by any single shareholder opting out of direct coin transfers, freezing payouts for all co-shareholders - ([File: aptos-move/framework/aptos-framework/sources/vesting.move], [File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

## Summary
The external report describes a controller-controlled external call that can be made to always revert, permanently blocking `release()`/withdrawal for every user sharing that call path. The Aptos-native analog is the shared, permissionless distribution loops in `vesting::distribute` and `staking_contract::distribute_internal`, which iterate over *multiple* shareholders/recipients in a single atomic transaction and call `aptos_account::deposit_coins` for each. If any single recipient in that shared pool is configured to always make `deposit_coins` abort, the whole transaction reverts every time `distribute()`/`distribute_internal()` is called, permanently blocking payouts of principal, rewards, and commission to every *other* legitimate shareholder in that same pool — not just the attacker's own funds.

## Finding Description
`aptos_account::deposit_coins` aborts (rather than silently forwarding or skipping) when the recipient is not yet registered for the coin type and has opted out of arbitrary transfers: [1](#0-0) 

An account controls its own "accept arbitrary coin transfers" flag and its own coin registration; both are pre-conditions the account itself decides. Any address that is (a) added as a vesting shareholder, or (b) a party in a `staking_contract` (staker, current operator, or a *former* operator left in the shared `distribution_pool` after `switch_operator`) can deliberately keep itself unregistered for `AptosCoin` and disable direct transfers, so that any attempted deposit into it always aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.

`vesting::distribute` loops over **every** shareholder in the vesting contract's `grant_pool` inside a single transaction, extracting each shareholder's proportional share and calling `deposit_coins` in sequence: [2](#0-1) 

If iteration reaches a malicious/griefing shareholder before finishing, the abort unwinds the *entire* transaction, so none of the other shareholders (who did nothing wrong) receive their vested funds either. Since `distribute` is a plain `public entry fun` callable by anyone, and shares/withdrawal amounts keep accruing on-chain regardless (`vest`, `unlock_stake`), this becomes a **permanent** DoS: every future call to `distribute` for that vesting contract will hit the same poisoned recipient and abort, locking the stake of all co-shareholders indefinitely (barring an admin resetting the beneficiary of that one address, which requires already-privileged admin/resetter action and does not solve the underlying default-shareholder case).

The framework authors were aware of exactly this DoS vector for the *admin-set beneficiary* path, and added a defensive check there: [3](#0-2) 
```
// Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't
// fail and block all other accounts from receiving APT if one beneficiary is not registered.
assert_account_is_registered_for_apt(new_beneficiary);
```
However, this guard only fires when an admin explicitly calls `set_beneficiary`. It does **not** cover the default case where `get_beneficiary` simply returns the shareholder address itself (no beneficiary override set) — the shareholder can independently drive their own account into the "unregistered + opted-out" state at any time after the vesting contract is created, bypassing the mitigation entirely.

The identical pattern exists in `staking_contract::distribute_internal`, which loops over all shareholders of the staking contract's `distribution_pool` (staker, current operator via beneficiary, and any former operators still owed a distribution) and calls `deposit_coins` for each: [4](#0-3) 

Because `switch_operator` forces a distribution of already-inactive stake and adds the outgoing operator into the pool as a shareholder before proceeding, a malicious/former operator can retain a permanent unpaid commission entry and later poison their own account, freezing the staker's own unlock/withdrawal path together with any subsequent operator's distributions that route through the same `StakingContract.distribution_pool`.

## Impact Explanation
This breaks the "Unlock, reactivate, withdraw ... paths must not redirect value or strand it permanently" and "must preserve value and withdrawal rights" invariants for stake/vesting flows. A single unprivileged party sharing a distribution pool (a vesting shareholder, staker, or ex-operator) can strand the withdrawal rights of every other party in that pool with no privileged remediation available except (for vesting) an admin/resetter re-pointing the *poisoned account's own* beneficiary — which does not exist for `staking_contract`'s staker/operator distribution pool at all, since there is no equivalent "reset the offending recipient's payout target" function for that module. This is a high-impact, non-recoverable loss of claim/withdrawal rights for uninvolved third parties, directly matching the "Required Impacts" criterion of permanent lock/non-recoverable loss of claim rights in stake/vesting flows.

## Likelihood Explanation
Likelihood is high: `set_allow_direct_coin_transfers`-style opt-out and simply not registering a `CoinStore<AptosCoin>` are both ordinary, permissionless, self-serve account actions requiring no special capability, gas griefing, or privileged role — any of the co-shareholders, the staker, or a disgruntled ex-operator can trigger it unilaterally at any time after being added to the shared pool. `distribute()` and `distribute_internal()` are permissionless entry points ("Allow anyone to distribute already unlocked funds") explicitly designed to be callable by any account, so the attack does not even require the attacker to submit the triggering transaction.

## Recommendation
Make the distribution loops resilient to a single failing recipient instead of aborting the whole batch:
- Wrap each `aptos_account::deposit_coins` call in a way that cannot cause the entire loop to revert (e.g., pre-check `coin::is_account_registered` / `can_receive_direct_coin_transfers` per recipient and, if the target cannot currently accept the coin, retain/re-buy their shares in the pool or route the funds to an escrow/claimable balance instead of aborting).
- Alternatively, require and enforce coin-transfer-acceptance registration for every party at the moment they are added as a shareholder/staker/operator to a distribution pool (not just for admin-set beneficiaries via `set_beneficiary`), and prevent that "coin cannot be received" state from becoming untrue afterward for as long as pending distributions exist.

## Proof of Concept
1. Admin creates a vesting contract with shareholders `[S1, S2]`, `S2` being the attacker's account (freshly generated, no `CoinStore<AptosCoin>` yet). Uses `vesting::create_vesting_contract`/`setup_vesting_contract`.
2. `S2` calls `aptos_account::set_allow_direct_coin_transfers(&S2_signer, false)` from their own key (no privileges required), while never calling `coin::register<AptosCoin>` for their account.
3. Vesting periods pass; `vesting::vest` unlocks stake for both `S1` and `S2` proportionally into the shared `grant_pool`.
4. Anyone calls `vesting::distribute(contract_address)`. The loop reaches `S2`'s share, calls `aptos_account::deposit_coins(S2, ...)`, which hits `!coin::is_account_registered<AptosCoin>(S2)` and `can_receive_direct_coin_transfers(S2) == false`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The whole `distribute` transaction reverts. `S1` never receives their vested funds on this or any future call, since `S2`'s state persists and every subsequent `distribute` call reaches the same abort. Because `set_beneficiary`'s registration check only applies to admin-driven overrides (`aptos-move/framework/aptos-framework/sources/vesting.move:915-935`), there is no way for `S1` or the admin to unblock the pool without the attacker's cooperation.
6. The same construction applies to `staking_contract::distribute_internal` using a malicious/former operator left in the `distribution_pool` after `switch_operator`, blocking the staker's own unlock/withdraw path.

Note: I was not able to trace `create_vesting_contract`'s full body (only matched by name) to confirm whether shareholder addresses are validated/registered for APT at creation time; if such a check already exists there, it would need to be bypassed post-creation (e.g., a shareholder registers, then later unregisters — Move's `CoinStore` cannot be removed once created, so this specific bypass may not be possible for *pre-registered* shareholders, but it remains fully exploitable for addresses without a `CoinStore<AptosCoin>` at the time distribution is attempted). This should be verified against the full `create_vesting_contract`/`add_shareholder` code path in a live Devin session before treating the PoC as fully verified end-to-end.

    /// Distribute any withdrawable stake from the stake pool.
    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

        // Send any remaining "dust" (leftover due to rounding error) to the withdrawal address.
        if (coin::value(&coins) > 0) {
            aptos_account::deposit_coins(vesting_contract.withdrawal_address, coins);
        } else {
            coin::destroy_zero(coins);
        };
