### Title
V1 `validate_tenure_change_payload` duplicate-block guard checks only globally-accepted blocks, missing locally-accepted equivocation - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in the v1 chainstate module guards against signing a second tenure-start block for a tenure by querying `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0)  instead of a signature-inclusive lookup that also covers locally-accepted (self-signed but not yet 70%-threshold) blocks. If the signer has only locally accepted a tenure-start block for a given `consensus_hash`, this guard returns `None` and lets a second, conflicting tenure-start proposal for the same tenure pass the `DuplicateBlockFound` check.

### Finding Description
The intended safety equality is: "a block has already been signed in this tenure" should be true whenever the signer has produced ANY signature for a block in that tenure — whether the block is only locally accepted (signer's own signature, pre-threshold) or globally accepted (70%-signed). The v1 code narrows this to only the globally-accepted case: [1](#0-0) 

Root cause: `get_last_globally_accepted_block` is keyed to the globally-accepted status, which by definition requires the 70% threshold to have been reached across signers. A block that this signer has locally accepted (i.e., already signed and durably recorded) but that has not yet reached global threshold is invisible to this lookup, so the duplicate check silently passes.

Exploit flow (attacker holds a single miner slot for the sortition tied to `consensus_hash` CH1, so `proposed_by`/pubkey checks pass legitimately):
1. Miner (attacker) proposes tenure-start block `B1` for tenure `CH1`. The v1 signer runs `check_proposal` → `validate_tenure_change_payload`, finds no prior globally- or locally-accepted block, approves, and the signer locally accepts/signs `B1` (persisted in signerdb as locally-accepted, not yet globally accepted since it doesn't yet have 70% of the signer set).
2. Before `B1` reaches global 70% threshold, the same miner crafts and gossips a second, conflicting tenure-start block `B2` for the *same* `consensus_hash` CH1 (same `prev_tenure_consensus_hash`, satisfying `check_tenure_change_confirms_parent` and `check_parent_tenure_choice`, but a different block body/tx set).
3. `validate_tenure_change_payload` for `B2` calls `get_last_globally_accepted_block(CH1)`, which still returns `None` because `B1` has not crossed the global threshold. The `DuplicateBlockFound` rejection never fires.
4. The v1 signer proceeds to validate and potentially locally sign `B2` as well, resulting in the same signer having signed two conflicting tenure-start blocks (`B1` and `B2`) for the same tenure.

This bypasses the guard using only a single miner slot and standard block-proposal gossip — no majority of signers, no node operator access, no auth_token needed.

### Impact Explanation
This breaks the UNIQUENESS safety property: a single v1-configured signer can be induced to produce signatures for two conflicting tenure-start blocks in the same tenure. If enough signers are independently tricked this way (each is a self-contained equivocation, requiring no coordination with other signers), it directly threatens chain safety per the stated Critical category ("a signer signing an invalid, non-canonical, or conflicting block"). It is repeatable per tenure whenever a block sits in the locally-accepted-but-not-globally-accepted window, which is a normal transient state during signing rounds.

### Likelihood Explanation
Preconditions are realistic and cheap: the attacker only needs to win one sortition slot (their own BTC) and race a second conflicting tenure-start block into gossip before the first one reaches the 70% global-acceptance threshold — a window that exists in every tenure-start signing round. No majority-signer collusion, no compromised keys, and no local host access are required, matching the allowed unprivileged-attacker model.

### Recommendation
Change the duplicate-block guard in `validate_tenure_change_payload` (stacks-signer/src/chainstate/v1.rs) to use a lookup that considers any signed state (local or global) for the tenure's `consensus_hash`, analogous to v2's `get_last_signed_block`, rather than `get_last_globally_accepted_block` alone.

### Proof of Concept
Rust test plan (to be placed alongside `stacks-signer/src/chainstate/tests/v1.rs`):
1. Seed `SignerDb` with a `NakamotoBlock` `B1` containing a `TenureChangePayload` for `consensus_hash = CH1`, marked as locally accepted (signed) via the signerdb API used for local acceptance, but NOT globally accepted.
2. Construct `SortitionsView` with `cur_sortition.data.consensus_hash == CH1` and matching `parent_tenure_id`/miner pubkey hash so pubkey/parent checks pass.
3. Build a second block `B2` with the same `consensus_hash = CH1`, a valid `TenureChangePayload` with the same `prev_tenure_consensus_hash`, but different block content/signer_signature_hash than `B1`.
4. Call `view.validate_tenure_change_payload(&proposed_by, &tenure_change_b2, &b2, &mut signer_db, &client)`.
5. Assert the result is `Ok(())` (i.e., does NOT return `Err(RejectReason::DuplicateBlockFound)`), proving the guard fails to detect the locally-accepted `B1` as "already signed" — contrast with an assertion that `signer_db.get_last_globally_accepted_block(&CH1)` is `None` while a signature for `B1` already exists in the db, demonstrating the broken equality.

Note: I was not able to fully read `stacks-signer/src/signerdb.rs` or `chainstate/v2.rs` within the available tool budget to confirm the exact semantics of `get_last_signed_block` or rule out an additional outer-layer equivocation guard in `stacks-signer/src/v0/signer.rs`; this should be verified before finalizing the fix.
