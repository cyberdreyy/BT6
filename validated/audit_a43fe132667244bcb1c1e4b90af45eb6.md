### Title
Default recovery ignores unfunded instant-withdraw receipts from earlier epochs — multi-epoch receipts share one `pendingInstantWithdraws` counter but only the default epoch gets a recovery basis - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class is "a single aggregate marker cannot represent multiple same-kind items." In `IdleCreditVault`, `pendingInstantWithdraws` is a single global counter that aggregates unfunded instant-withdraw receipts across *all* epochs, while `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` track per-epoch basis. Default finalization (`finalizeDefaultRecovery` / `defaultPendingClaimBasis` / `_defaultPrefundedInstantReserve`) only credits `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — as claimable basis. Any instant receipt requested in an earlier epoch that was never fully collected via `collectInstantWithdrawFunds` stays inside `pendingInstantWithdraws`, flips on `defaultInstantWithdrawsFinalized`, but receives no recovery basis and no reserve.

### Finding Description
- `requestInstantWithdraw` adds to the flat aggregates `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`, plus per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` / `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366–374).
- `collectInstantWithdrawFunds` decrements only `pendingInstantWithdraws`; a partial collection leaves a stale remainder from prior epochs (lines 398–403).
- At default, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` only when `pendingInstantWithdraws != 0` — the per-epoch map for *old* epochs is never included in `basis` (lines 644–649).
- `_defaultPrefundedInstantReserve` compares the *aggregate* `pendingInstantWithdraws` against only the *current-epoch* basis, so stale prior-epoch pending amounts corrupt the prefunded-reserve calculation in both directions (lines 716–723).
- After finalization, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`; the leftover pre-default-epoch receipt remains in `instantWithdrawsRequests[_user]` and falls through to `_transferFundedClaim`, which reverts whenever `balance - defaultRecoveryReserve < amount` — i.e., always, since no funds were ever collected for it (lines 842–856, 897–907).

Two broken invariants follow: (a) the excluded basis inflates `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, letting current-epoch/default-epoch claimants over-recover (price can exceed par, draining underlying that should have covered the old receipt); (b) the old-epoch instant receipt is permanently unclaimable — `claimInstantWithdrawRequest` cannot pay it at par (reserve guard reverts) and cannot pay it haircut (not in `defaultRecoveryEpoch`).

### Impact Explanation
An unprivileged lender whose instant-withdraw request was only partially funded in epoch N loses that claim permanently when the borrower defaults in a later epoch: the receipt can never be claimed at par (insufficient funded balance due to the `defaultRecoveryReserve` guard in `_transferFundedClaim`) and is never given a recovery price (excluded from `defaultPendingClaimBasis`). Meanwhile other claimants' recovery price is computed against a smaller `totalBasis`, so they recover strictly more than fair share — a direct redistribution of the frozen user's funds. Quantified loss: up to the full stale `pendingInstantWithdraws` remainder, which equals the old unfunded instant-withdraw basis.

### Likelihood Explanation
Requires (1) an instant-withdraw request that remains partially unfunded across an epoch boundary — possible whenever `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` collects less than `pendingInstantWithdraws` (e.g., thin liquidity at `startEpoch`), and (2) a subsequent borrower default finalized via `finalizeDefaultRecovery`. Both events are reachable with honest privileged roles; the unprivileged user only needs to leave an unfunded instant receipt open, which is normal protocol usage.

### Recommendation
Track instant-withdraw basis per epoch through finalization: `defaultPendingClaimBasis` should include all epochs' `instantWithdrawClaimsByEpoch` entries that remain inside `pendingInstantWithdraws` (or maintain an aggregate `instantPendingBasis` alongside the per-epoch maps), and `_defaultPrefundedInstantReserve` / `_claimDefaultedInstantWithdrawRequest` should iterate or fold every pending instant epoch rather than keying exclusively on `defaultRecoveryEpoch`.
