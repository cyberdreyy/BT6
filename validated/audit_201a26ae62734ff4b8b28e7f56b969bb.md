### Title
Response cache in gateway HTTP capability handler ignores WorkflowID when scoping cache keys, enabling cross-workflow response reuse - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
### Finding Description
The bug class in the external report is that a piece of shared state (`StakerVault._poolTotalStaked`/`strategiesTotalStaked`) is not updated to reflect a change in the caller's category (strategy vs. non-strategy) when a transfer occurs, so a later accounting computation (`LpGauge.poolStakedIntegral`) is computed using an entitlement scope that does not actually match the requester, letting one actor benefit from state intended for a different, disjoint scope.

The same class of bug exists in the `responseCache` used by the HTTP capability's gateway handler. The cache is documented as being "scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) , but the actual cache key, `OutboundHTTPRequest.Hash()`, is built only from method, URL, headers, body, and `WorkflowOwner` — the code comment itself states `keyed by a hash of the request (method, URL, headers, body, workflowOwner)` [2](#0-1) , and `WorkflowID` is explicitly excluded from the hash, confirmed by the test asserting that two requests differing only by `WorkflowID` produce the **same** hash [3](#0-2) .

`Fetch()` and `Set()` both use this `req.Hash()` as the sole cache key when storing/serving cached HTTP responses for outbound HTTP-action requests coming from workflow nodes [4](#0-3) , and the gateway handler drives this from every unprivileged, node-originated `OutboundHTTPRequest` in `makeOutgoingRequest` based on that request's own `CacheSettings` [5](#0-4) .

This mirrors the StakerVault bug exactly: the intended isolation boundary (per-workflow, analogous to per-strategy accounting) is not actually enforced by the underlying state key (cache map keyed by hash, analogous to `_poolTotalStaked`), only the coarser boundary (per-owner, analogous to per-pool) is enforced.

### Impact Explanation
Because the cache is only scoped by `WorkflowOwner` (and method/URL/headers/body), two *different* workflows belonging to the same owner that issue functionally identical HTTP requests (same URL/method/headers/body) will share the same cache entry. A workflow with `CacheSettings.MaxAgeMs > 0` can be served a cached response that was originally produced/paid-for on behalf of a different workflow. This is a cross-user/cross-workflow response confusion: a workflow can receive a response it never independently triggered (potentially stale, produced under a different trigger context, or containing information intended only for the originating workflow's execution), and it also lets a workflow effectively free-ride on another workflow's outbound HTTP call/cache population, defeating the "Workflow Isolation" guarantee documented for the cache and any per-workflow cost/quota assumptions built on that isolation.

### Likelihood Explanation
Reachable directly by any workflow owner who controls two or more workflows: no special privilege is needed beyond having (or being able to have) multiple workflows under the same owner that call the same external endpoint with the same request shape and non-zero `CacheSettings.MaxAgeMs`. This is a self-contained node-side capability path, not a network/consensus attack, and is triggerable purely through normal HTTP Action capability usage.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in `OutboundHTTPRequest.Hash()` so cache entries are scoped per-workflow as documented, matching Method 2 of the original recommendation (make the tracked scoping key consistent with the accounting/isolation boundary that is actually enforced elsewhere in the system).

### Proof of Concept
1. Workflow A (WorkflowID = "wf-A", WorkflowOwner = "0xOwner") issues an `OutboundHTTPRequest` to `GET https://example.com/api` with `CacheSettings{Store:true, MaxAgeMs:600000}`. The gateway handler calls `responseCache.Fetch`, which executes the real HTTP call and stores the result keyed by `req.Hash()` [6](#0-5) .
2. Workflow B (WorkflowID = "wf-B", same WorkflowOwner = "0xOwner") issues an identical `OutboundHTTPRequest` (same method/URL/headers/body) with the same cache settings.
3. As shown by the unit test verifying identical hashes across differing `WorkflowID` values [3](#0-2) , `req.Hash()` for workflow B collides with workflow A's cache entry, so `Fetch` returns workflow A's cached response to workflow B without ever making a new outbound HTTP call.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)

			if req.CacheSettings.Store {
