### Title
Authorization escalation via chained Transfer+AddKey on a not-yet-existing implicit account - ([File: runtime/runtime/src/actions.rs])

### Finding Description
`action_implicit_account_creation_transfer` unconditionally mutates the shared `actor_id` to `account_id` whenever a `Transfer` action creates a new implicit account: `*actor_id = account_id.clone();` [1](#0-0)  This mirrors the same pattern used for explicit `CreateAccount`, `*actor_id = account_id.clone();` [2](#0-1) .

`actor_id` is a mutable variable threaded through the sequential actions of a single receipt. `check_actor_permissions` treats `Action::Transfer` (and `CreateAccount`, `FunctionCall`, `TransferToGasKey`) as always permitted (no `actor_id == account_id` check), while `Action::AddKey`/`DeleteAccount` require `actor_id == account_id` or else return `ActorNoPermission`: [3](#0-2)  and [4](#0-3) .

Since `actor_id` starts as `predecessor_id` and gets overwritten to `account_id` as a *side effect* of the first `Transfer` action creating the implicit account, any subsequent `AddKey` (or `DeleteAccount`) action in the same receipt trivially satisfies `actor_id == account_id`, regardless of whether the original `predecessor_id` (the attacker) had any legitimate relationship to the target implicit address. Unlike explicit `CreateAccount`, which is gated by `account_id.is_sub_account_of(predecessor_id)` (i.e., the creator must own the naming rights), implicit-account creation via `Transfer` has no such relationship requirement — any account can transfer to any not-yet-existing implicit address to trigger creation. This means an ordinary attacker who knows/predicts a target implicit address (an address is just the hex of a public key someone else generated off-chain and has not yet used on-chain) can submit a single receipt with actions `[Transfer(1 yocto), AddKey(attacker_pubkey, FullAccess)]` targeting that address. The `Transfer` implicitly creates the account and grants the address-embedded key (belonging to the "true" owner), but also flips `actor_id` to `account_id`, letting the attacker's `AddKey` pass the permission check and inject an additional, attacker-controlled `FullAccess` key into the same account — without the true owner ever signing anything.

### Impact Explanation
This is an authorization-escalation bug: an unprivileged attacker gains permanent `FullAccess` control over an account belonging to another party, purely as a side effect of ordering actions within one receipt. If the true owner later deposits significant funds into that implicit address (expecting it to be exclusively theirs, since its address is derived from a keypair they generated), the attacker's injected key allows them to transfer out or drain those funds — a concrete theft-of-user-funds scenario, matching the "authorization escalation across accounts" / "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions: the target implicit address must not yet exist on-chain (precondition explicitly noted in the question, and realistic since implicit addresses are typically generated off-chain by wallets before first use). Cost to attacker: negligible (1 yoctoNEAR deposit plus base gas fees for two actions in one receipt). Feasibility: the attacker needs only to learn of the target address before its legitimate owner performs their first on-chain action against it (e.g., observing a shared/published address, a QR code, or racing a pending transfer) — no validator, node, or peer privileges are required, satisfying the "ordinary client" attacker model. The attack is repeatable against any implicit address that hasn't yet been touched on-chain.

### Recommendation
Do not let `actor_id` mutations caused by implicit-account creation via `Transfer` (or by `CreateAccount`) leak into permission checks for unrelated, security-sensitive actions like `AddKey`/`DeleteAccount` within the same receipt unless the receipt's `signer_id`/`predecessor_id` is provably the account itself or an authorized creator. Specifically, either (a) restrict `action_implicit_account_creation_transfer` from mutating `actor_id` at all (implicit accounts don't need this since their ownership is defined by the embedded public key, not by whoever funds them), or (b) explicitly forbid batching `AddKey`/`DeleteAccount` after a `Transfer` that performs implicit account creation in the same receipt, or (c) require that `AddKey` actions targeting a newly implicit-created account use the account's own derived public key check rather than trusting the `actor_id` short-circuit.

### Proof of Concept
Add a runtime `apply`-level integration test (in `runtime/runtime/src/tests/apply.rs`) that:
1. Constructs a receipt with `receiver_id` = a fresh near-implicit account address (hex of a locally generated keypair `K_owner`) that does not yet exist in state.
2. Sets the receipt's actions to `[Transfer(1 yocto), AddKey(K_attacker, FullAccess)]`, signed/originated by an attacker-controlled account.
3. Applies the receipt via the runtime and asserts:
   - The account now exists with the implicit key matching `K_owner` (added by `action_implicit_account_creation_transfer`).
   - AND the `AddKey` action succeeded (no `ActorNoPermission` error), so an access key for `K_attacker` (controlled solely by the attacker, unrelated to `K_owner`) is also present on the account.
   - Assert both keys are `FullAccess`, demonstrating that the attacker, who never held `K_owner`'s private key nor any relation to the target account, obtained full control over an account it does not own.
