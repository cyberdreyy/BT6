### Title
Loss-adjusted withdraw receipts are keyed by funding epoch but looked up by request epoch, letting requesters claim at par and push the whole stopEpoch loss onto remaining LPs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the haircut as `lossRecoveryPriceByEpoch[epochNumber]` (the epoch in which the borrower funded the shortfall, i.e. after `stopEpoch` bumped `epochNumber`). `_claimLossAdjustedWithdrawRequest` instead reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, the epoch in which the user called `requestWithdraw`. These two keys differ by exactly one epoch, so the lookup always returns 0, the loss-adjusted branch is skipped, and `_claimFundedWithdrawRequest` pays the full unhaircutted `withdrawsRequests` amount at par.

### Finding Description
- `requestWithdraw` records the receipt under the *request* epoch: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (`IdleCreditVault.sol:282-293`).
- When the borrower underfunds the stop, `collectWithdrawFunds` writes the haircut under the *funding* epoch: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (`IdleCreditVault.sol:411-421`). Per the comment at `IdleCreditVault.sol:322`, "Epoch number is increased at stopEpoch", so at this point `epochNumber == requestEpoch + 1`.
- On claim, `_claimLossAdjustedWithdrawRequest` does `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:790-791`) — the request epoch — gets 0, and returns early.
- Control then falls into `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-349`). The wait check `epochNumber <= lastWithdrawRequest[_user]` passes because `epochNumber` was already incremented, `_settleApr0` runs, and the user is paid `withdrawsRequests[_user]` at par via `_transferFundedClaim`.

The attacker only needs to be a KYC-passing lender: deposit, `requestWithdraw`, wait for a stop that funds less than `pendingWithdraws` (a `stopEpochWithDuration` loss — an honest-manager flow), then call `claimWithdrawRequest` and receive 100% while the stored `lossRecoveryPriceByEpoch` entry is never consumed by anyone.

### Impact Explanation
Direct theft/insolvency: every user with a pending receipt in a loss epoch escapes the pro-rata haircut that `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` explicitly designed (`IdleCreditVault.sol:405-421`). The vault pays out more underlying than was funded (`_transferFundedClaim` draws on vault reserves meant to back active strategy tokens), so the loss is silently socialized onto active AA/BB LPs instead of being split per the documented waterfall. Quantified: a claimer receives `claimBasis` instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL`; with a 50% haircut the excess equals half of all pending receipts.

### Likelihood Explanation
Triggers deterministically on the first `collectWithdrawFunds` call with `_amount < pendingWithdraws` — i.e. any `stopEpochWithDuration` loss while receipts are pending. No privileged misbehavior is required; the manager calling `stopEpoch` with a partial repayment is within the honest-role model. The only precondition is an attacker-held pending withdraw receipt in that epoch.

### Recommendation
Key `lossRecoveryPriceByEpoch` consistently: either store under the request epoch(s) covered by the pending bucket, or look up by the funding epoch. Since pending receipts can span epochs, the cleaner fix is to record the loss epoch separately (e.g. `lossRecoveryEpochOf[_user]` or a global `latestLossRecoveryEpoch` plus per-epoch claim basis) rather than reusing `lastWithdrawRequest[_user]` as the index.

### Proof of Concept
Not executed (read-only analysis). Reproduction sketch for a Foundry fork test:

```solidity
// Setup: deposit, startEpoch, requestWithdraw(amount) in epoch N.
cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));
assertEq(strategy.lastWithdrawRequest(user), N);          // request epoch

// Honest manager stops epoch with a partial loss:
// previewLossAdjustedWithdrawFunds(loss) -> pendingToFund < pendingWithdraws
cdoEpoch.stopEpochWithDuration(duration, interest, loss); // epochNumber -> N+1
// inside stopEpoch -> strategy.collectWithdrawFunds(pendingToFund)
assertGt(strategy.lossRecoveryPriceByEpoch(N + 1), 0);    // haircut keyed at N+1
assertEq(strategy.lossRecoveryPriceByEpoch(N), 0);        // lookup key is empty

// Attacker claim: loss-adjusted branch returns 0, funded path pays at par
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(user) - balPre;
assertGt(paid, trancheAmount * strategy.lossRecoveryPriceByEpoch(N + 1) / 1e18);
// paid == full claimBasis, no haircut applied
```

Caveat: I could not fully trace the `stopEpoch`/`collectWithdrawFunds` call ordering inside `IdleCDOEpochVariant.sol` within the available iterations; the finding rests on `epochNumber` being incremented before `collectWithdrawFunds` (consistent with the "epoch number is increased at stopEpoch" invariant at `IdleCreditVault.sol:322`). If the increment instead happens after funding, the keys coincide and this specific path is safe — verification of `stopEpoch` ordering is required before reporting.
