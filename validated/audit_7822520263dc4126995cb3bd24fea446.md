### Title
`getSupply` RPC handler subtracts a stale non-circulating-lamport scan result from capitalization without saturation, causing an arithmetic-underflow panic - (File: rpc/src/rpc.rs)

### Summary
`JsonRpcRequestProcessor::get_supply` computes `circulating = total_supply - non_circulating_supply.lamports` using a plain, non-saturating subtraction on two values that are read from the bank at two different points in time separated by a full accounts-db scan. [1](#0-0)  This mirrors the `Basket.sol#auctionBurn` bug class: a ratio/derived value (`ibRatio`, here `circulating`) is computed from a component (`startSupply`, here `non_circulating_supply.lamports`) that is captured before a state-changing operation (`handleFees`, here ongoing bank transaction processing / inflation-reward crediting) completes, so the two operands used in the final arithmetic are inconsistent with each other.

### Finding Description
In `get_supply`, the non-circulating supply is computed first via `calculate_non_circulating_supply`, which performs a full scan of all stake-program accounts (`get_filtered_indexed_accounts` / `get_program_accounts`) and sums their lamport balances at the time each account is read. [2](#0-1)  Only *after* this scan completes does the handler read `bank.capitalization()` for `total_supply`. [3](#0-2) 

If the bank used is the live/working bank (non-finalized commitment), it can continue to mutate concurrently while the scan is in progress — e.g., stake accounts locked/non-circulating may receive additional lamports (inflation rewards) during the scan, or `capitalization()` may drop afterward due to fee/rent burns unrelated to those specific accounts. The two reads (`non_circulating_supply.lamports` captured mid-scan, `total_supply` captured after) are therefore not guaranteed to be a matched, monotonic snapshot pair.

The final line then performs `total_supply - non_circulating_supply.lamports` with the default `-` operator instead of `saturating_sub`. [4](#0-3)  This is the same root-cause pattern as the external report: a value computed from a stale/mismatched intermediate is fed directly into arithmetic that assumes consistency, and here that arithmetic is unchecked/non-saturating on `u64`.

Notably, the sibling REST implementation `calculate_circulating_supply_async` (used for `/v0/circulating-supply`) performs the identical computation but explicitly uses `saturating_sub`, indicating the JSON-RPC path is the outlier and the "correct" mitigation pattern already exists elsewhere in the codebase: [5](#0-4) 

### Impact Explanation
`getSupply` is a standard, unauthenticated JSON-RPC method reachable by any client with one request. [6](#0-5)  If `total_supply < non_circulating_supply.lamports` at the moment of subtraction, `u64` underflow occurs. Depending on whether the RPC-node binary is built with overflow-checks enabled (release builds in agave frequently enable `overflow-checks = true` in the workspace profile), this either:
- panics the JSON-RPC processing thread, causing the request to fail loudly and potentially crashing/aborting the validator process if the panic propagates out of a critical thread, or
- silently wraps to a huge circulating-supply value near `u64::MAX`, returning grossly incorrect data to every RPC consumer of `getSupply` (and to `getLargestAccounts` with a `filter`, which shares `calculate_non_circulating_supply`).

Either outcome maps to the accepted validator-process-crash or wrong-data-returned categories from a single unprivileged JSON-RPC call.

### Likelihood Explanation
Likelihood is moderate: it requires the scan-vs-capitalization window to close on a specific bank state where the non-circulating locked accounts' lamports transiently exceed the later-read total capitalization (e.g., due to concurrently-applied inflation rewards to locked/withdraw-authority-restricted stake accounts during the scan, or a capitalization decrease from unrelated burns after the scan completes). This is most exploitable when the RPC node's `bank` for `getSupply` is not a frozen/rooted bank (i.e., default/processed commitment), since scanning a live, mutating bank increases the chance of an inconsistent pair of reads. No special privileges or multiple calls are needed — the race is inherent to a single `getSupply` invocation against the live bank.

### Recommendation
Change `total_supply - non_circulating_supply.lamports` to `total_supply.saturating_sub(non_circulating_supply.lamports)`, matching the existing, correct pattern already used in `calculate_circulating_supply_async` in `rpc/src/rpc_service.rs`. [5](#0-4)  Additionally, consider reading `bank.capitalization()` before or atomically with the non-circulating scan (or requiring a frozen/rooted bank for `getSupply`) so the two values represent a consistent snapshot rather than being captured across a scan window.

### Proof of Concept
1. Start a validator/RPC node and let it run through several epochs so partitioned reward distribution is active, ensuring some non-circulating (lockup/withdraw-restricted) stake accounts are actively receiving inflation rewards.
2. Issue a `getSupply` JSON-RPC request against a node configured to use the default (`processed`/working) commitment so the scan target bank is still live. [7](#0-6) 
3. While `calculate_non_circulating_supply` performs its multi-account scan over the stake program (`runtime/src/non_circulating_supply.rs`), the bank continues normal transaction processing and reward crediting. [2](#0-1) 
4. If the resulting `non_circulating_supply.lamports` (captured mid-scan) ends up greater than `bank.capitalization()` (captured immediately after, at line 1133), the subtraction at line 1148 underflows a `u64`, either panicking the RPC thread or wrapping to a near-`u64::MAX` circulating-supply figure returned to the caller. [8](#0-7) 

Note: I was unable to fully confirm from the index whether the workspace's release `Cargo.toml` profile enables `overflow-checks = true` (grep found `[profile.*]`/`overflow` references but the index did not surface the exact profile block contents), so the precise choice between "panic" vs "silent wraparound" outcome could not be definitively verified and should be checked directly in a full clone of the repository.

                circulating: total_supply - non_circulating_supply.lamports,
                non_circulating: non_circulating_supply.lamports,

        ))

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
    let total_supply = bank.capitalization();
    let bank = Arc::clone(bank);
    let non_circulating_supply =
        tokio::task::spawn_blocking(move || calculate_non_circulating_supply(&bank))
            .await
            .expect("Failed to spawn blocking task")
            .map_err(|e| SupplyCalcError::Scan(e.to_string()))?;

    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
}
