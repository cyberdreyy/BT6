### Title
APR0 withdraw requests classified by request-time `unscaledApr` permanently revert `stopEpoch` if APR is later raised, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the Envoy TLS-inspector bypass — where a connection was classified using only a partial inspection and then bound to the wrong filter chain — `IdleCreditVault.requestWithdraw` classifies a withdrawal as an "APR0 request" by inspecting only the *current* `unscaledApr == 0` ( [1](#0-0) ). That classification is then enforced at a later lifecycle stage: `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` ( [2](#0-1) ). A dust-size request made during an APR-0 epoch therefore wedges every subsequent `stopEpoch` as soon as the honest manager/borrower raises the APR, freezing all LP funds and pending withdrawal receipts.

### Finding Description
- `requestWithdraw` routes a request into the APR0 bucket solely on `unscaledApr == 0` at request time ( [1](#0-0) ), accumulating `apr0Users[_user].principal` and the global `apr0TotalPrincipal` ( [3](#0-2) ).
- At `stopEpoch`, `prepareStopEpochWithApr0` takes the fast path only when `_principal == 0` ( [4](#0-3) ); otherwise it hard-reverts if `unscaledApr != 0` ( [5](#0-4) ).
- `apr0TotalPrincipal` has no independent escape hatch: it is only zeroed inside `prepareStopEpochWithApr0` itself ( [6](#0-5) ) or inside the default-claim path `_clearWithdrawClaimForEpoch` ( [7](#0-6) ), neither of which runs while `stopEpoch` reverts.
- Like the Envoy connection that was never recognized as TLS because only some extensions were inspected, the request is stamped with a classification valid only for the instant of inspection; the invariant it encodes ("APR stays 0 for the whole request lifecycle") is never enforced at request time and is instead enforced at the worst possible point — the epoch transition all funds depend on.

### Impact Explanation
An unprivileged tranche holder calls `cdoEpoch.requestWithdraw(1 wei tranche, ...)` during any epoch where the borrower operates at `unscaledApr == 0`. When the manager/borrower later sets any positive APR — routine pool operation — every `stopEpoch`/`stopEpochWithDuration` call reverts in `prepareStopEpochWithApr0`. Consequences:

- **Temporary freezing of the entire vault TVL**: no LP can be paid out, no pending withdrawal receipt can be funded, and `claimWithdrawRequest` remains blocked by the epoch gating in `_claimFundedWithdrawRequest` ( [8](#0-7) ), because `epochNumber` can never advance past `lastWithdrawRequest`.
- The only recovery is the manager setting APR back to 0 to un-wedge `stopEpoch`; if `apr0TotalPrincipal` is recreated each epoch (an attacker can re-request every APR-0 epoch), the vault is effectively pinned to zero-yield operation or indefinite freeze. Loss = interest denied to all LPs plus illiquidity of all queued receipts for the frozen duration.

### Likelihood Explanation
Low-to-medium likelihood, high blast radius: it requires a vault operating at `unscaledApr == 0` (a supported mode — the APR0 flow exists precisely for it) followed by any APR increase, both within normal honest operation. The attacker action itself is a dust withdrawal request costing gas only. The code comments indicate the APR-0 lifecycle constraint is known, but nothing prevents an attacker from re-arming `apr0TotalPrincipal` each time it clears, and no guard blocks `setAprs` while APR0 principal is outstanding.

### Recommendation
Resolve the misclassification at request/epoch boundaries rather than at `stopEpoch`:
1. In `prepareStopEpochWithApr0`, treat outstanding `apr0TotalPrincipal` under a nonzero `unscaledApr` as ordinary pending principal (fold it into `pendingWithdraws` / `withdrawsRequests` and clear `apr0TotalPrincipal`) instead of reverting, so a stale APR0 bucket cannot brick the epoch machine.
2. Alternatively, revalidate the classification when it is consumed: give `setApr`/`setAprs` a guard that either blocks APR transitions while `apr0TotalPrincipal != 0` or force-settles APR0 requests into the normal bucket on transition.

### Proof of Concept
```solidity
// Foundry fork test — sketch against test/foundry/IdleCreditVault.t.sol helpers
function testApr0RequestBricksStopAfterAprRaise() external {
    // 1. Vault running at unscaledApr == 0; LP deposits AA and gets tranches.
    uint256 shares = _depositWithUser(attacker, 1e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();
    _stopCurrentEpochWithApr(0);          // epoch ends with APR still 0

    // 2. During buffer with unscaledApr == 0, attacker files a dust request.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));   // routed into apr0Users bucket
    assertGt(strategy.apr0TotalPrincipal(), 0);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // 3. Borrower/manager (honest) raises APR for the next epoch.
    vm.prank(manager);
    strategy.setAprs(10e18, 10e18);       // unscaledApr != 0

    // 4. Every stopEpoch now reverts in prepareStopEpochWithApr0.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // 5. No claim path advances: epochNumber cannot increase, all receipts frozen.
    assertEq(strategy.epochNumber(), requestEpoch);
}
```

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
