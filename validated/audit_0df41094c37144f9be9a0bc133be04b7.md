### Title
Vault secret path traversal via unsanitized `path.Join` in secret engine `fullPath`/`dataPath` - ([File: helpers/vault/secret_engines/generic/engine.go], [File: helpers/vault/secret_engines/kv_v2/engine.go])

### Summary
The job-controlled `secrets.VAULT.path` value (`spec.VaultSecret.Path`) is fully variable-expandable and flows unsanitized into `engine.fullPath`/`engine.dataPath`, which build the Vault request path with `path.Join(e.path, p)`. Because Go's `path.Join`/`path.Clean` lexically collapses `..` segments without any boundary check, a crafted `SecretPath()` such as `../../other-project-engine/service-account-token` can make the resulting path resolve outside the admin-configured `Engine.Path` prefix.

### Finding Description
The call chain is: `spec.VaultSecret.expandVariables` ( [1](#0-0) ) expands `s.Path` via CI variables with no validation, `spec.VaultSecret.SecretPath()` returns that raw string ( [2](#0-1) ), which is passed into `defaultVault.GetField` → `getSecretEngine(engineDetails).Get(secretDetails.SecretPath())` ( [3](#0-2) ). The engine constructor is created with the admin-configured `Engine.Path` ( [4](#0-3) ). Inside the generic engine, `Get` calls `e.fullPath(path)`, defined as `path.Join(e.path, p)` ( [5](#0-4) ); the kv-v2 engine's `dataPath` does the same (`path.Join(e.path, "data", p)`) ( [6](#0-5) ).

`path.Join` internally calls `path.Clean`, which lexically collapses `..` segments regardless of whether they escape the base prefix — there is no check that the resulting path remains a descendant of `e.path`. For example, if `e.path = "team-a"` and the job sets `secrets.VAULT.path: "../team-b/token"`, `path.Join("team-a", "../team-b/token")` yields `"team-b/token"`, completely outside the `team-a` prefix. With enough `../` segments an attacker can also produce a path with a leading `..` component, sent verbatim to Vault's HTTP read/write API.

No sanitization, canonicalization-then-prefix-check, or rejection of `..` exists anywhere in this path (confirmed via repo-wide search for traversal guards in `helpers/vault/**`, none found). The only isolation relied upon is the JWT auth role's Vault-side policy scoping, which per the question's precondition uses path-prefix/wildcard string matching on the *pre-collapsed* prefix string — a purely string-based ACL does not protect against a runner-side path built by naive `Join`+`Clean` if the resulting concrete path string no longer starts with the intended prefix.

### Impact Explanation
If Vault ACL policies are configured with path-based/wildcard trust anchored on the configured engine path prefix (a common real-world configuration, not a documented insecure choice), an unprivileged pipeline author can retrieve secrets stored under sibling paths outside their assigned prefix — for example another project's/team's Kubernetes service-account bearer token — by simply setting the CI-side `secrets.VAULT.path` field to a traversal string. This is a genuine identity/permission escalation: the job obtains a credential stronger or different than what the runner administrator intended to scope to it, matching the requested scoped impact exactly.

### Likelihood Explanation
- Preconditions are realistic and commonly seen: runner administrators scope Vault access per project/team by giving each JWT role a distinct `Engine.Path`, and rely on that path prefix (directly or via glob) in Vault ACL policy definitions.
- `secrets.VAULT.path` (`spec.VaultSecret.Path`) is fully attacker-controlled and expandable through ordinary CI/CD variables — no special runner privileges are needed, only the ability to define `.gitlab-ci.yml` `secrets:` config or set a variable, which is standard unprivileged pipeline-author capability.
- The exploit is deterministic and repeatable: any job can set the same traversal path every run.
- The vulnerable code path is directly reachable in the described call sequence with no intervening validation.

### Recommendation
After computing the joined path in `fullPath`/`dataPath`/`metadataPath`, verify that the cleaned result is still contained within `e.path` (e.g., compare that the joined path equals `e.path` or has `e.path + "/"` as a prefix after `path.Clean`), and reject/error out otherwise. Alternatively, reject any `SecretPath()` value containing `..` path segments before it reaches `path.Join`, at the point where `spec.VaultSecret` is validated/expanded (`common/spec/spec.go`), so untrusted job input cannot manipulate engine-relative paths at all.

### Proof of Concept
```go
// helpers/vault/secret_engines/generic/engine_traversal_test.go
func TestEngine_FullPath_NoTraversalOutsidePrefix(t *testing.T) {
    e := &engine{path: "team-a", name: "generic"}

    cases := []string{
        "../team-b/service-account-token",
        "../../shared/root-token",
        "..%2f..%2fteam-b/token", // if any decoding happens upstream
    }

    for _, p := range cases {
        got := e.fullPath(p)
        assert.True(t, strings.HasPrefix(got, "team-a/"),
            "fullPath(%q) = %q escaped configured engine prefix", p, got)
    }
}
```
Expected (current, vulnerable) behavior: assertion fails, e.g. `fullPath("../team-b/service-account-token")` returns `"team-b/service-account-token"`, demonstrating the path escapes the `team-a` prefix. A fix should make this test pass by rejecting or safely containing traversal segments.

func (v *defaultVault) GetField(engineDetails Engine, secretDetails Secret) (interface{}, error) {
	engine, err := v.getSecretEngine(engineDetails)
	if err != nil {
		return nil, err
	}

	secret, err := engine.Get(secretDetails.SecretPath())
	if err != nil {
		return nil, fmt.Errorf("reading secret: %w", err)
	}

	field := secretDetails.SecretField()
	for key, data := range secret {
		if key != field {
			continue
		}

		return data, nil
	}

	return nil, nil
}

func (e *engine) Get(path string) (map[string]interface{}, error) {
	secret, err := e.client.Read(e.dataPath(path))
	if err != nil {
		return nil, fmt.Errorf("reading from Vault: %w", err)
	}

	if secret == nil {
		return nil, nil
	}

	data := secret.Data()
	if data == nil {
		return nil, nil
	}

	if raw, ok := data["data"]; !ok || raw == nil {
		return nil, nil
	}

	result, ok := data["data"].(map[string]interface{})
	if !ok {
		return nil, fmt.Errorf("data for key %s cannot be coerced to 'map[string]any'", path)
	}
	return result, nil
}

func (e *engine) dataPath(p string) string {
	return path.Join(e.path, "data", p)
}
