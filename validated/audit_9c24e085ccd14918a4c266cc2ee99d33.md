## Finding: Valid (with corrected mechanism)

The premise in the submitted question — that funds might get redirected to the *new* operator's beneficiary — doesn't hold. But tracing the code reveals a real, related bug: after `switch_operator`, a stale commission-distribution share recorded for the **old operator** bypasses beneficiary routing entirely and pays out to the old operator's raw address instead of `beneficiary_for_operator(old_operator)`.

### Title
Stale distribution-pool shares for a removed operator bypass beneficiary routing after `switch_operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` calls `distribute_internal` (to flush existing inactive stake) and then `request_commission_internal` (to book final commission owed to the old operator) *before* re-keying the `StakingContract` map entry from `old_operator` to `new_operator`. The commission booked by `request_commission_internal` is added as a new share in `distribution_pool` keyed by the `old_operator` address, but this share is never paid out during `switch_operator` itself — it is left pending. Once anyone later calls `distribute(staker, new_operator)` (the only reachable key, since the map entry no longer exists under `old_operator`), `distribute_internal` runs with `operator = new_operator`. Its beneficiary substitution check `if (recipient == operator) { recipient = beneficiary_for_operator(operator) }` compares the pending shareholder address (`old_operator`) against the wrong operator identity (`new_operator`), so the check never fires for the old operator's stale share, and the payout goes directly to the raw `old_operator` address instead of through `beneficiary_for_operator(old_operator)`.

### Finding Description
Relevant code: [1](#0-0) 

`request_commission_internal` books the pending commission under `recipient = old_operator` via `add_distribution`/`buy_in`: [2](#0-1) 

The permissionless `distribute` entry function looks up the contract only by its *current* map key (post-switch, that's `new_operator`), then calls `distribute_internal` with that same `new_operator` as the `operator` parameter: [3](#0-2) 

Inside `distribute_internal`, the beneficiary substitution only triggers for the shareholder whose address equals the `operator` parameter passed in: [4](#0-3) 

Because the leftover shareholder is `old_operator` but the `operator` parameter is now `new_operator`, `recipient == operator` is false, so `beneficiary_for_operator(old_operator)` is never consulted, and the funds are deposited straight to the `old_operator` account address.

### Impact Explanation
This is an unprivileged-input-triggerable accounting/beneficiary-routing corruption: any caller invoking `distribute(staker, new_operator)` after a `switch_operator` causes the old operator's still-pending commission share to be paid to the old operator's own wallet rather than to the beneficiary address that operator had configured via `set_beneficiary_for_operator`. This matches the "Operator commission, beneficiary payout... credits the wrong account" impact category — the beneficiary redirection contract is silently broken for any commission left pending across a `switch_operator` boundary. It is not fund loss to a third party/attacker (the money still lands in an account the old operator controls), but it does violate the beneficiary-routing invariant that operators rely on for payout automation/custody separation.

### Likelihood Explanation
High reachability: `switch_operator` is a normal staker action, `distribute` is `public entry` and callable by anyone with no privilege, and the bug triggers deterministically whenever there is nonzero unpaid commission for the old operator at the moment of the switch (a common real-world sequence: operator has beneficiary set, staker rotates to a new operator mid-lockup).

### Recommendation
In `distribute_internal`, decouple the beneficiary substitution from the currently-passed `operator` parameter. Instead, look up whether the shareholder recipient itself corresponds to *some* operator with a registered beneficiary (e.g., check `exists<BeneficiaryForOperator>(recipient)` directly) rather than comparing `recipient == operator`. Alternatively, ensure `switch_operator` fully distributes (drains) the `distribution_pool` after `request_commission_internal` runs, so no operator-owned share ever survives the re-keying from `old_operator` to `new_operator`.

### Proof of Concept
1. Staker creates a staking contract with `operator` and sets `set_beneficiary_for_operator(operator, beneficiary)`.
2. Stake pool accrues rewards; staker calls `switch_operator(staker, operator, new_operator, new_commission_pct)`. This internally calls `request_commission_internal(operator, ...)`, booking a commission share for `operator` in `distribution_pool`, then re-keys the `StakingContract` to `new_operator`.
3. Any unprivileged account calls `distribute(staker_address, new_operator)`.
4. Assert: the commission amount is deposited to `operator`'s address directly, not to `beneficiary` (i.e., `coin::balance(beneficiary)` unchanged, `coin::balance(operator)` increased) — demonstrating the beneficiary-routing bypass introduced by the operator-key mismatch inside `distribute_internal`.

        operator: address,
        staking_contract: &mut StakingContract,

            get_staking_contract_amounts_internal(staking_contract);

        };

        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
