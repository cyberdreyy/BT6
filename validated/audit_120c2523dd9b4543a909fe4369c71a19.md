### Title
Missing verification of actual received token amount on deposit paths allows Token-2022 TransferHook mints to break deposit accounting - ([File: programs/marginfi/src/instructions/marginfi_account/deposit.rs])

### Summary
Marginfi's core `lending_account_deposit` instruction (and the analogous Kamino/Solend/JupLend/Drift integration deposit instructions) credit the user's bank-share balance using a *requested/pre-computed* amount rather than verifying the actual balance change in the bank's liquidity vault after the CPI transfer completes. Marginfi does compute a deterministic pre-fee adjustment for the standard Token-2022 `TransferFeeConfig` extension, but it does not defend against the `TransferHook` extension, whose actual token movement is controlled by arbitrary third-party program logic (analogous to the "malicious or rebalancing tokens" cited in the Sudoswap/Spearbit report).

### Finding Description
In `lending_account_deposit`, the flow is:
1. `bank_account.deposit(I80F48::from_num(deposit_amount))` credits shares based on the caller-specified `deposit_amount`. [1](#0-0) 
2. `amount_pre_fee` is computed only to compensate for `TransferFeeConfig`, a deterministic SPL extension. [2](#0-1) 
3. The transfer is performed via `bank.deposit_spl_transfer(...)`, which invokes `spl_token_2022::onchain::invoke_transfer_checked` (or a manual `transfer_checked` instruction) — this CPI call will also invoke any active `TransferHook` program attached to the mint. [3](#0-2) 
4. No before/after balance check on the liquidity vault is performed to confirm that `deposit_amount` (or the fee-adjusted equivalent) tokens actually landed in the vault.

Critically, marginfi already recognizes `TransferHook` as a distinct risk elsewhere: `has_transfer_hook()` is defined and used to reject Token-2022 mints with an active transfer hook — but only in the permissionless `lending_pool_emissions_deposit` instruction. [4](#0-3) [5](#0-4) 

This same `has_transfer_hook` guard is not invoked in `lending_account_deposit`, nor in the Kamino/Solend/JupLend deposit paths, all of which perform `transfer_checked` CPIs and then credit shares/balances based on the nominal `amount` rather than a measured balance delta. [6](#0-5) [7](#0-6) 

This is a structural analog to the Sudoswap `_validateTokenInput()` finding: the "safe" direct-transfer path trusts the requested amount rather than confirming what was actually received, and a hook-bearing token (fully attacker-controlled logic on transfer, capable of siphoning, minting, or burning during transfer) can desynchronize real vault balance from the internal share accounting.

### Impact Explanation
If a bank were ever configured against a Token-2022 mint with an active `TransferHook`, a malicious hook could cause less value to actually land in the liquidity vault than the shares issued to the depositor, or could redirect value to a third party during the CPI. Because marginfi's internal accounting (`asset_share_value`, `total_asset_shares`) is derived from the requested `amount`/`deposit_amount` and not a verified balance delta, this would create a durable mismatch between the vault's real token balance and marginfi's internal solvency accounting — enabling other users to withdraw against phantom collateral, i.e., an exploitable misvaluation with direct financial effect.

### Likelihood Explanation
Exploitability strictly depends on whether marginfi's bank-creation process (`add_bank` / permissionless pool add flows) forbids listing Token-2022 mints carrying an active `TransferHook` extension. I could not find such a bank-creation-time allowlist/denylist for mint extensions in the paths I was able to inspect (`add_pool_permissionless.rs`, `configure_bank.rs`, etc. were only found by filename, not fully read). The existence of `has_transfer_hook()` used defensively in one instruction (`lending_pool_emissions_deposit`) but not in the main deposit paths suggests the omission may be intentional-but-incomplete rather than deliberate — i.e., an inconsistent application of an otherwise-known mitigation. Given marginfi supports permissionless bank/pool addition in some configurations, this raises the likelihood that an untrusted mint could be onboarded.

### Recommendation
Apply the existing `has_transfer_hook` (and ideally a broader "verify received amount via pre/post balance diff") check consistently across all deposit entry points (`lending_account_deposit`, `kamino_deposit`, `solend_init_obligation`/`deposit`, `juplend_deposit`, `drift_deposit`), either by:
1. Rejecting bank creation/mint registration for any Token-2022 mint with an active `TransferHook` extension, matching the restriction already applied in `lending_pool_emissions_deposit`, or
2. Measuring the liquidity vault's actual balance before and after the transfer CPI and crediting shares based on the observed delta rather than the nominal `amount`.

### Proof of Concept
Not independently reproducible from static analysis alone — a concrete PoC would require confirming (via a Devin session with full repo/test access) whether `add_bank`/`add_pool_permissionless` currently permit registering a Token-2022 mint with a `TransferHook` extension. If permitted, the PoC path is:
1. Create a bank backed by a T22 mint with an attacker-controlled `TransferHook` program that transfers `amount - k` tokens to the vault instead of `amount` (or reroutes `k` tokens elsewhere) while the CPI itself still reports success.
2. Call `lending_account_deposit` with `amount`; observe `bank_account.deposit(amount)` credits full shares while the vault balance increased by less than `amount`.
3. Repeat/scale to accumulate a share/vault-balance mismatch, then withdraw more value than was ever actually deposited, at other depositors' expense.

**Caveat:** This finding's validity hinges on an unverified assumption (that TransferHook mints are not already blocked at bank-creation time). I was not able to conclusively confirm or rule this out with the available tools/time, so this should be treated as a lead requiring direct code confirmation of the bank-creation allowlist logic before being treated as a fully proven, exploitable vulnerability.

/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
