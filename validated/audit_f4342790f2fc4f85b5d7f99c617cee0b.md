### Title
Global-state-machine agreement threshold uses floor division while chainstate signature verification uses ceiling division, creating a mismatched approval boundary - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::reached_agreement()` in `libsigner/src/v0/signer_state.rs` computes the approval threshold with plain integer (floor) division, while the consensus-critical `NakamotoBlockHeader::compute_voting_weight_threshold()` in `stackslib/src/chainstate/nakamoto/mod.rs` deliberately adds a ceiling correction. When `total_weight * NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` is not an exact multiple of 10, these two computations diverge by 1 weight unit, exactly analogous to the reported `convert_to_yang_helper()` premature-division precision loss: an integer division performed too early (and without the compensating rounding step) yields a threshold that is off by one compared to the "true"/canonical value used elsewhere in the same protocol.

### Finding Description
`compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs` explicitly computes a ceiling: [1](#0-0) 
```rust
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
```
This is the threshold that `verify_signer_signatures` (chainstate, node-side, consensus critical) and every signer-side call (`store_and_process_block_signature`, `handle_block_pre_commit`, `handle_block_rejection`) in `stacks-signer/src/v0/signer.rs` uses to decide whether a block has enough weight to be signed/accepted.

By contrast, `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` in `libsigner/src/v0/signer_state.rs` performs the same multiply-then-divide-by-10 operation **without** the ceiling correction: [2](#0-1) 
```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}

pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```
The signer-set test's own regression suite confirms the ceiling behavior is intentional and load-bearing for `compute_voting_weight_threshold`: for `total_weight = 511`, the threshold is `358` (`511*7=3577`, `3577/10=357` + ceil `1` = `358`), not `357`. [3](#0-2) 

`GlobalStateEvaluator::reached_agreement` (floor division) would treat `357` as sufficient for the same `total_weight = 511`, one weight-unit below what the canonical `compute_voting_weight_threshold` (and hence `verify_signer_signatures` / the node) requires. This is the direct analog of the report's bug: the "hidden" division inside the global-state agreement check truncates precision, producing a threshold value that disagrees with the value computed the "correct"/ceiling way elsewhere in the same codebase for the same conceptual quantity (approval threshold as a fraction of total signer weight).

### Impact Explanation
`GlobalStateEvaluator` drives the v0/v1 global signer-protocol-version state machine's determination of whether a supermajority of signers agree on a piece of global state (e.g. active signer protocol version, tx replay set) — see `determine_global_state`/`get_global_tx_replay_set` in the same file. If the off-by-one threshold causes `reached_agreement` to return `true` one weight unit earlier than the canonical `compute_voting_weight_threshold` would, a signer can conclude "global agreement reached" on a value (protocol version, replay set) that a majority using the canonical threshold would not yet recognize as agreed. This breaks the equality between "what the global state machine believes is agreed" and "what the canonical 70% threshold requires," which can cause signers to act on a state (e.g. switch signing behavior, apply a tx replay set) that other, more conservative signers/nodes do not yet consider settled — a state-machine equality break of the class called out in the rules ("aggregated-weight vs verified-accepts").

Because this only manifests when `total_weight * 7` is not an exact multiple of 10 (i.e., most `total_weight` values not divisible by 10), the boundary condition is common, not a corner case.

### Likelihood Explanation
This requires no majority collusion and no privileged access: it is triggered purely by the natural arithmetic of `total_weight`, which is set by the reward-set stacking distribution and is essentially never a multiple of 10. Any single signer's own state-machine evaluation is affected deterministically whenever `total_weight` is not a multiple of 10, so the divergence is reachable on essentially every reward cycle without any attacker action — likelihood is high in terms of triggering, though the downstream consequence depends on how `GlobalStateEvaluator`'s agreement result feeds into signer behavior in the specific caller path (which was not fully traced in this pass).

### Recommendation
Make `reached_agreement`/`reached_disagreement` use the same ceiling-division semantics as `NakamotoBlockHeader::compute_voting_weight_threshold`, e.g. by calling `compute_voting_weight_threshold` directly or replicating its `ceil` correction, so that the global state machine's notion of "threshold reached" is always consistent with the canonical, consensus-critical threshold used by chainstate and by `stacks-signer/src/v0/signer.rs`.

### Proof of Concept
For `total_weight = 511`:
- `compute_voting_weight_threshold(511) = 358` (verified by existing test `test_compute_voting_weight_threshold`) [4](#0-3) 
- `reached_agreement(357)` on a `GlobalStateEvaluator` with `total_weight = 511` evaluates `357 >= (511*7)/10 = 357` → `true`, one unit below the canonical `358` threshold. [5](#0-4) 

This demonstrates the two threshold computations disagree by exactly one weight unit whenever `total_weight * 7 % 10 != 0`, mirroring the reported bug's premature-division truncation.
