### Title
External Initiator credentials can trigger integer-ID job runs, bypassing the "EIs not allowed" restriction - ([File: core/web/pipeline_runs_controller.go])

### Summary
The route `POST /v2/jobs/:ID/runs` is authenticated by `auth.Authenticate` with `AuthenticateExternalInitiator` as an accepted method [1](#0-0) . `AuthenticateExternalInitiator` sets `SessionUserKey` to `&clsessions.User{Role: clsessions.UserRoleRun}` for a successfully-authenticated EI [2](#0-1) , so `PipelineRunsController.Create`'s check `_, isUser := auth.GetAuthenticatedUser(c)` cannot distinguish an EI-derived identity from a real user [3](#0-2) , allowing EI credentials to run jobs by integer ID despite the comment stating this is disallowed.

### Finding Description
`GetAuthenticatedUser` simply reads whatever `*clsessions.User` object is stored under `SessionUserKey` in the gin context [4](#0-3) . Both real user auth (`AuthenticateBySession`, `AuthenticateByToken`) and `AuthenticateExternalInitiator` populate this same key [5](#0-4) [6](#0-5) [7](#0-6) . There is no separate marker distinguishing "this User struct was synthesized for an EI" from "this is a genuine authenticated user".

The route wiring confirms EIs reach `Create`: `userOrEI` group is authenticated via `AuthenticateExternalInitiator, AuthenticateByToken, AuthenticateBySession` (in that order, first success wins) and then wrapped only with `auth.RequiresRunRole(prc.Create)` [1](#0-0) . `RequiresRunRole` only checks `user.Role != clsessions.UserRoleView` [8](#0-7) , which the EI's synthetic `UserRoleRun` object satisfies.

Inside `Create`, the code explicitly relies on `isUser` (derived from `GetAuthenticatedUser`) to gate integer-ID job runs, with the comment "only users are allowed to run jobs using int IDs - EIs not allowed" [9](#0-8) . Since an EI request also produces `isUser == true`, this gate is ineffective — it only actually blocks fully unauthenticated requests (which would never reach here at all, since `Authenticate` middleware already rejects them). The intended distinction between "EI-triggered run" (normally only permitted for webhook/UUID jobs) and "user-triggered run" (permitted for both UUID and int32 job IDs) is not enforced by this code.

### Impact Explanation
An attacker who only holds valid EI credentials (not a node user session/API token) can trigger arbitrary integer-ID job runs (e.g., OCR/direct-request/keeper jobs addressed by int32 ID), which the code intends to restrict to authenticated node users only. This is an authorization-boundary bypass: EI credentials are meant to be scoped to legacy webhook-style job triggering, not general job execution by numeric ID. Concrete impact is unauthorized triggering of job runs, which could cause unwanted on-chain transactions, oracle report submissions, or resource exhaustion depending on job type — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: attacker only needs a valid External Initiator access key/secret (which is a lower-privilege credential explicitly intended only for enabling job-trigger webhooks, not general API access) [10](#0-9) . The request is a simple `POST /v2/jobs/<int32-ID>/runs` with the EI headers `static.ExternalInitiatorAccessKeyHeader`/`static.ExternalInitiatorSecretHeader` instead of session/API-token headers. No additional exploitation complexity or race conditions are required; the bypass is deterministic and repeatable for any int32 job ID that exists on the node.

### Recommendation
Distinguish EI-derived authentication from genuine user authentication instead of overloading `SessionUserKey`/`GetAuthenticatedUser` for both. Options:
- Do not set `SessionUserKey` in `AuthenticateExternalInitiator`; instead rely solely on `SessionExternalInitiatorKey` for EI identity, and update `RequiresRunRole` (or add a new role check) to accept either a real `run`+ role or a valid EI, without polluting `GetAuthenticatedUser`.
- In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or restrict-appropriately) when the request originated from an EI, rather than only checking `GetAuthenticatedUser`.

### Proof of Concept
Go handler-level integration test plan (added to `core/web/pipeline_runs_controller_test.go`):
1. Set up an app with a job that has an int32 ID (e.g., reuse `setupPipelineRunsControllerTests`).
2. Create an External Initiator via `ExternalInitiatorsController.Create` (or directly via ORM) to obtain `AccessKey`/`Secret`.
3. Build an HTTP client that sends `POST /v2/jobs/<jobID>/runs` with headers `static.ExternalInitiatorAccessKeyHeader` and `static.ExternalInitiatorSecretHeader` set to the EI credentials, and no session cookie/API token.
4. Assert the expected behavior is `http.StatusUnauthorized` or `http.StatusForbidden` (per the code comment's intent that EIs cannot trigger int-ID runs).
5. Run the test against the current code: it will instead return `http.StatusOK` with a `pipelineRun` resource, confirming the run was successfully triggered by EI credentials — demonstrating the bypass.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
