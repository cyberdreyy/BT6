### Title
`TransactionStatus::Busy` can be wedged permanently via a failing `#[callback]`-based staking-pool query, freezing the lockup and blocking Foundation clawback - (File: `lockup/src/owner.rs`, `lockup/src/owner_callbacks.rs`, `lockup/src/foundation.rs`, `lockup/src/foundation_callbacks.rs`)

### Summary
`refresh_staking_pool_balance` and `withdraw_all_from_staking_pool` set `TransactionStatus::Busy` and then chain a callback whose single argument is annotated with `#[callback]` (`on_get_account_total_balance`, `on_get_account_unstaked_balance_to_withdraw_by_owner`). The near-sdk-generated wrapper for a `#[callback]` parameter panics while deserializing the promise result **before** the function body runs whenever the awaited cross-contract call fails, so the `self.set_staking_pool_status(TransactionStatus::Idle)` statement inside the body is never reached. Because the lockup owner is free to create and whitelist their own staking pool through the public `staking-pool-factory`, they can deliberately make that pool's queried method fail, permanently wedging `Busy` on their own lockup and, if a Foundation vesting-termination deficit is outstanding, blocking `termination_prepare_to_withdraw` forever.

### Finding Description
Binding claimed by the invariant: for any lockup, `staking_information.status == Busy` at time T implies `∃ T' > T` where a callback runs and sets `status == Idle`. The code path breaks this equality:

- `refresh_staking_pool_balance` (`lockup/src/owner.rs:176-209`) sets `Busy`, calls `ext_staking_pool::get_account_total_balance`, and chains `on_get_account_total_balance`, whose signature is `fn on_get_account_total_balance(&mut self, #[callback] total_balance: WrappedBalance)` (`lockup/src/lib.rs:88`). Because the argument is `#[callback]`, near-sdk's generated wrapper extracts the promise's `Successful` payload; on `PromiseResult::Failed` it panics inside the wrapper, and the body (`lockup/src/owner_callbacks.rs:281-294`, which contains the only `set_staking_pool_status(TransactionStatus::Idle)` for this path) never executes.
- The same pattern applies to `withdraw_all_from_staking_pool` → `on_get_account_unstaked_balance_to_withdraw_by_owner` (`lockup/src/owner.rs:259-294`, `lockup/src/owner_callbacks.rs:298-339`), and to the Foundation-side termination flow `termination_prepare_to_withdraw` → `on_get_account_staked_balance_to_unstake` / `on_get_account_unstaked_balance_to_withdraw` (`lockup/src/foundation.rs:58-127`, `lockup/src/foundation_callbacks.rs:9-53,95-139`).

By contrast, every other staking callback (`on_staking_pool_deposit`, `on_staking_pool_stake`, `on_staking_pool_unstake`, `on_staking_pool_withdraw`, `on_staking_pool_unstake_all`, and their termination equivalents) deliberately avoids `#[callback]` and instead uses `is_promise_success()` [1](#0-0)  so the body always runs and always clears `Busy`, e.g. [2](#0-1) . The two view-style query callbacks were not written this way, which is the root cause.

Attacker path: the attacker is entitled to be a lockup owner (`LockupFactory::create` is payable and open to anyone) and is entitled to create/whitelist a staking pool through the public `staking-pool-factory`, whose `on_staking_pool_create` self-whitelists on success with no Foundation involvement [3](#0-2) . The attacker then:
1. Deploys a pool contract they control, named/whitelisted via the factory.
2. Calls `select_staking_pool` on their lockup to pick that pool (passes the whitelist check because it is self-whitelisted).
3. Calls `deposit_and_stake`/`deposit_to_staking_pool` normally (these use `is_promise_success()`, so they complete and correctly update `deposit_amount`).
4. Calls `refresh_staking_pool_balance()`, which sets `Busy` [4](#0-3)  and calls into the attacker-controlled pool's `get_account_total_balance`.
5. The attacker's pool contract panics (or is undeployed/returns malformed data) in `get_account_total_balance`, so the promise fails.
6. `on_get_account_total_balance`'s `#[callback]` wrapper panics before the body runs, leaving `status == Busy` forever.

From then on, `assert_staking_pool_is_idle()` [5](#0-4)  panics unconditionally, so `deposit_to_staking_pool`, `deposit_and_stake`, `withdraw_from_staking_pool`, `stake`, `unstake`, `unstake_all`, `refresh_staking_pool_balance`, `withdraw_all_from_staking_pool`, and `unselect_staking_pool` (which also asserts idle at `lockup/src/owner.rs:51`) all panic permanently. Crucially, `termination_prepare_to_withdraw` also calls `self.assert_staking_pool_is_idle()` at the very start [6](#0-5) , so once `Busy` is wedged, the NEAR Foundation can never advance a `VestingTerminatedWithDeficit` termination past the unstake/withdraw step, permanently blocking recovery of the unvested-but-staked deficit that legitimately belongs to the Foundation after `terminate_vesting`.

None of the existing guards prevent this: `assert_self()` only restricts who may invoke the callback, not whether the wrapper panics before reaching it; `is_promise_success()` is not used on the queried-balance callbacks; there is no `assert_valid_request`/timeout/retry mechanism to un-stick `Busy`.

### Impact Explanation
- The owner's own lockup becomes permanently unusable for any staking operation — funds already staked/deposited on the attacker-controlled pool are stuck as far as this contract's accounting is concerned (matches "funds permanently frozen").
- More significantly, in a real vesting lockup, an owner (employee) facing eventual `terminate_vesting` by the Foundation can pre-emptively wedge `Busy` while a deficit exists on a staking pool they control, permanently preventing `termination_prepare_to_withdraw` from completing. This blocks the Foundation from ever reclaiming the unvested/terminated NEAR that is sitting staked — i.e., "locked or unvested tokens released early" / indefinitely withheld from the rightful party (the Foundation), which is a Critical-category impact under the stated rubric.
- Repeatable per-lockup: any lockup owner can do this once against their own contract; the freeze is permanent and not tied to gas/rate limits, so it is not a DoS/griefing issue with "no gain" — the gain is denial of legitimate clawback.

### Likelihood Explanation
- Preconditions: attacker must be a lockup owner (trivial via public `LockupFactory::create`) and must control a staking pool that is whitelisted (trivial via public `staking-pool-factory`, which self-whitelists on success).
- Cost: only the `MIN_ATTACHED_BALANCE` for the factory calls and normal deposit/stake gas; fully within an unprivileged actor's normal toolset per the threat model.
- Feasibility: causing a cross-contract call from the attacker's own pool contract to fail is entirely within the attacker's control (the pool is their own code).
- Repeatable across any lockup the attacker owns; for the Foundation-blocking variant, it requires the owner to have an active vesting schedule and a Foundation-initiated termination with a deficit, which is a realistic real-world condition for terminated employees.

### Recommendation
Do not use `#[callback]`-typed parameters for `on_get_account_total_balance`, `on_get_account_unstaked_balance_to_withdraw_by_owner`, `on_get_account_staked_balance_to_unstake`, and `on_get_account_unstaked_balance_to_withdraw`. Instead, use `#[callback_result]` (or manually inspect `env::promise_result(0)` via `is_promise_success()`/pattern matching) so the function body always executes, unconditionally resets `TransactionStatus`/`TerminationStatus` to a safe/idle state on failure (mirroring the pattern already used in `on_staking_pool_deposit` etc.), and only proceeds to use the deserialized value on success.

### Proof of Concept
```rust
// lockup/src/lib.rs (test module) - cargo test wedge_busy_forever
#[test]
fn wedge_busy_forever_on_failed_total_balance_query() {
    let (mut context, mut contract) = lockup_only_setup();
    context.predecessor_account_id = account_owner();
    context.signer_account_pk = public_key(2).try_into().unwrap();

    let staking_pool = "malicious_pool".to_string();
    testing_env!(context.clone());
    contract.select_staking_pool(staking_pool.clone());

    context.predecessor_account_id = lockup_account();
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(b"true".to_vec()));
    contract.on_whitelist_is_whitelisted(true, staking_pool.clone());

    // deposit/stake succeed normally (is_promise_success-based callbacks)
    let amount = to_yocto(LOCKUP_NEAR - 100);
    context.predecessor_account_id = account_owner();
    testing_env!(context.clone());
    contract.deposit_and_stake(amount.into());
    context.predecessor_account_id = lockup_account();
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_staking_pool_deposit_and_stake(amount.into());

    // owner triggers refresh_staking_pool_balance -> sets Busy
    context.predecessor_account_id = account_owner();
    testing_env!(context.clone());
    contract.refresh_staking_pool_balance();

    // BINDING CHECK (before): status must be Busy right now
    context.is_view = true;
    testing_env!(context.clone());
    // (assert via internal state or a getter exposing status, if available)
    context.is_view = false;

    // simulate the malicious pool's get_account_total_balance call failing
    context.predecessor_account_id = lockup_account();
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);

    // In real near-sdk execution, calling the #[near_bindgen]-generated wrapper for
    // on_get_account_total_balance with a Failed promise result panics INSIDE the
    // wrapper before the body runs -- so Idle is never set. This is best proven with
    // near-workspaces / near-sdk-sim driving an actual failing cross-contract call
    // rather than the unit-test helper (which bypasses the wrapper), asserting:
    //   - the outer transaction (refresh_staking_pool_balance's receipt chain) fails,
    //   - status is STILL Busy afterward,
    //   - any subsequent call to deposit_to_staking_pool / unselect_staking_pool panics
    //     with "Contract is currently busy with another operation" forever.

    // BINDING CHECK (after): status == Busy still, contradicting the invariant that
    // Busy is always eventually cleared.
    context.predecessor_account_id = account_owner();
    testing_env!(context.clone());
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        contract.unselect_staking_pool();
    }));
    assert!(result.is_err(), "unselect_staking_pool should panic forever once Busy is wedged");
}
```

Full end-to-end confirmation (including the actual wrapper-panic-before-body semantics of `#[callback]`) requires a `near-workspaces`/`near-sdk-sim` test with a real malicious pool contract whose `get_account_total_balance` panics, driving `refresh_staking_pool_balance` through an actual cross-contract call and asserting the lockup's staking methods remain permanently unusable afterward.
