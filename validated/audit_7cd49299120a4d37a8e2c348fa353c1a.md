### Title
Unpersisted `tx_replay_scope` causes replay-guard/liveness wedge on signer restart - (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/v0/signer_state.rs`)

### Summary
The signer's transaction-replay scope (`tx_replay_scope: ReplayScopeOpt`) is held only as a transient, in-memory field on the `Signer` struct rather than being persisted to `SignerDb`. This is structurally analogous to the Blast bug: state that must be "configured"/maintained on the actual long-lived object (the proxy / the on-disk `SignerDb`) is instead only ever set on a short-lived, in-memory container (the implementation / the process's `Signer` instance). When the process restarts, the scope resets to `None` while the replay transaction set (`tx_replay_set`, which *is* persisted via `SignerStateMachine`/`StateMachineUpdate`) can still be non-empty, producing an inconsistent state.

### Finding Description
`Signer` stores replay-tracking state split across two places with different persistence guarantees:
- `tx_replay_set: ReplayTransactionSet` is embedded in `SignerStateMachine`, which is serialized into `StateMachineUpdate`s and persisted/gossiped through `SignerDb`/StackerDB.
- `tx_replay_scope: ReplayScopeOpt` is a bare field on `Signer` [1](#0-0) , initialized fresh to `None` on every construction of `Signer::new` [2](#0-1) , and never written to or read back from `SignerDb`.

`ReplayState::infer_state` explicitly documents this design flaw: it notes that `None` is returned "Possibly caused by the scope being a local state in the `Signer` struct, which is not persisted." [3](#0-2) 

When `bitcoin_block_arrival` runs with a non-empty `tx_replay_set` (loaded from the persisted `SignerStateMachine`) but `tx_replay_scope` is `None` (because the process just (re)started), `ReplayState::infer_state` returns `None`, and the code path explicitly fails closed:
```
let replay_state = match ReplayState::infer_state(&tx_replay_set, tx_replay_scope) {
    Some(valid_state) => valid_state,
    None => {
        warn!("Tx Replay: Invalid state due to scope being not set while in replay mode!");
        return Err(SignerChainstateError::LocalStateMachineNotReady);
    }
};
``` [4](#0-3) 

Because `bitcoin_block_arrival` sets `self` to `Self::Uninitialized` at the top (to guarantee a fail-safe on error) and only replaces it with `Self::Initialized(...)` at the very end if no error occurs [5](#0-4) [6](#0-5) , this early `Err` return leaves `LocalStateMachine::Uninitialized` for this signer instance after every subsequent burn-block arrival, as long as a non-empty replay set was in effect and the scope is unrecoverable.

This wedge is caused purely by a normal signer restart (a one-slot operation any single signer can trigger simply by restarting its own process, or by an operator applying a routine restart) while a chain reorg/transaction replay is in progress — no majority collusion or malicious peer input is required. `LocalStateMachine::new` calls `bitcoin_block_arrival` on startup [7](#0-6) , meaning this failure occurs immediately at boot, and any error is swallowed into `LocalStateMachine::Uninitialized` by the caller: `Signer::new` catches the error and falls back to `Uninitialized` [8](#0-7) . An `Uninitialized` local state machine cannot participate in validating/rejecting proposals normally (per test comments elsewhere, "an uninitialized local state cannot be modified").

### Impact Explanation
This matches the High-impact category: "a signer wedged into never signing valid blocks... or losing the equivocation guard on restart." Specifically:
- The replay-transaction-set / replay-scope mechanism exists precisely to prevent re-signing/re-accepting stale transactions across a bitcoin fork (an equivocation-adjacent guard). Because the scope component of that guard is not persisted while the set component is, a signer restart during an active replay window desynchronizes the two, and the signer's own logic recognizes this as an invalid state and refuses to proceed, wedging its local state machine into `Uninitialized`.
- A single signer being wedged into `Uninitialized` does not by itself stop the network (validation may fall back to global-state checks), but it degrades that signer's liveness/participation exactly during fork/replay conditions — the highest-risk period for equivocation — which is the scenario the guard is meant to protect.

### Likelihood Explanation
Any signer operator restarting their signer process (upgrade, crash-recovery, redeploy) while a bitcoin fork replay is in progress (`tx_replay_set` non-empty, i.e., `ReplayState::InProgress`) will hit this on the very next `bitcoin_block_arrival` call, which is invoked immediately during `LocalStateMachine::new` at startup. This requires no coordination with other signers and no malicious behavior — a completely ordinary single-node restart during a real (or test-simulated) chain reorg triggers it deterministically.

### Recommendation
Persist `tx_replay_scope` (or equivalently, derive it deterministically) in `SignerDb` alongside `tx_replay_set`, analogous to how `SignerStateMachine`/`StateMachineUpdate` already persist the replay set. On `Signer::new`/`LocalStateMachine::new`, the scope should be reloaded from durable storage rather than defaulting to `None`, so that a process restart mid-replay does not desynchronize the scope from the set. Alternatively, treat "non-empty replay set with unknown scope after restart" as a state to reconstruct/re-derive (e.g., by re-deriving `fork_origin`/`past_tip` from chain state) rather than an unrecoverable error.

### Proof of Concept
Not executable in this ask-only context, but the wedge is reproducible on paper as follows:
1. Signer observes a bitcoin fork; `bitcoin_block_arrival` sets `tx_replay_set` to a non-empty set and `tx_replay_scope` to `Some(ReplayScope{..})` in-memory (persisted set is written to `SignerDb` via the `SignerStateMachine`/`StateMachineUpdate` path; the scope stays only in `Signer.tx_replay_scope`).
2. Operator restarts the signer process before the replay resolves (`ReplayState` still `InProgress`).
3. On restart, `Signer::new` builds a fresh `Signer` with `tx_replay_scope: None` [2](#0-1)  and calls `LocalStateMachine::new` → `bitcoin_block_arrival`, which loads `tx_replay_set` (non-empty) from the persisted state machine but is handed `tx_replay_scope = None`.
4. `ReplayState::infer_state` returns `None` because the set is non-empty but no scope was supplied [9](#0-8) , causing `bitcoin_block_arrival` to return `Err(SignerChainstateError::LocalStateMachineNotReady)` [4](#0-3) .
5. `Signer::new` swallows this error into `LocalStateMachine::Uninitialized` [10](#0-9) , wedging the signer.

I was not able to execute this in a live test harness (no filesystem/terminal access in ask-only mode); the trace above is based on static analysis of the referenced functions and the explicit code comment acknowledging the non-persistence of the scope.

impl ReplayState {
    /// Infers the appropriate `ReplayState` based on the contents of the replay transaction set
    /// and the optional scope.
    ///
    /// # Arguments
    ///
    /// * `replay_set` - A reference to a set of transactions intended for replay.
    /// * `scope_opt` - An optional scope defining the boundaries or context for the replay.
    ///
    /// # Returns
    ///
    /// * `Some(ReplayState::Unset)` if the `replay_set` is empty.
    /// * `Some(ReplayState::InProgress)` if the `replay_set` is non-empty and a `scope` is provided.
    /// * `None` if the `replay_set` is non-empty but no `scope` is provided.
    ///   - Possibly caused by the scope being a local state in the `Signer` struct, which is not persisted.
    fn infer_state(replay_set: &ReplayTransactionSet, scope_opt: &ReplayScopeOpt) -> Option<Self> {
        if replay_set.is_empty() {
            return Some(Self::Unset);
        }

        scope_opt
            .as_ref()
            .map(|scope| Self::InProgress(replay_set.clone(), scope.clone()))
    }
```
