### Title
Raw internal error details from `finding external initiator` DB error wrap can leak to unauthenticated API caller - ([File: core/web/auth/auth.go])

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) calls `store.FindExternalInitiator(ctx, eia)` using an unauthenticated request's `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers. If the lookup fails with anything other than `sql.ErrNoRows`, the code does:
```go
return errors.Wrap(err, "finding external initiator")
``` [1](#0-0) 

This is a plain wrapped `error`, not a `*models.JSONAPIErrors`. The shared `jsonAPIError` helper only special-cases `*models.JSONAPIErrors`; for any other error type it serializes `err.Error()` verbatim into the JSON response body:
```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
``` [2](#0-1) 

Because `FindExternalInitiator` implementations run a raw SQL query (`SELECT * FROM external_initiators WHERE access_key = $1`) directly against the datastore [3](#0-2) , any non-`ErrNoRows` failure (e.g., a transient DB/connection error, a malformed/oversized header causing a driver-level error, statement timeout, etc.) is wrapped with the prefix `"finding external initiator"` while preserving the full underlying `error.Error()` text (which for `database/sql`/`pq`/`sqlx` errors can include driver-level detail).

I was not able to fully confirm, within the tool budget available, the exact code path of the outer middleware wrapper that invokes `AuthenticateExternalInitiator` and turns its returned `error` into the final HTTP response (i.e., whether it calls `jsonAPIError(c, http.StatusUnauthorized, err)` with this specific `err`, or substitutes a generic `auth.ErrorAuthFailed` message before the JSON response is written). This is the missing link required to make the leak concretely reachable, and it needs verification (likely in `core/web/router.go` around the `RequireAuth`/`Authenticate` gin middleware construction).

### Impact Explanation
If the wrapped error is indeed passed unchanged into `jsonAPIError`, an unauthenticated attacker probing endpoints protected by `AuthenticateExternalInitiator` (e.g., `/v2/jobs/:ID/runs`) with malformed EI headers could trigger a non-`ErrNoRows` datastore error and receive it verbatim in the response body. This is an information-disclosure issue (internal error text / possible query or driver detail exposure), not a direct authentication bypass, fund movement, or credential leak — it does not defeat the `subtle.ConstantTimeCompare` secret check or reveal `HashedSecret`/`OutgoingSecret`. It maps to a low-severity "sensitive data exposure via error message" class rather than a critical node-compromise finding.

### Likelihood Explanation
Triggering a non-`ErrNoRows` error from `FindExternalInitiator` in normal operation is difficult for an external, unprivileged, unauthenticated caller — it generally requires abnormal DB conditions (connection failures, timeouts) rather than attacker-controlled input, since the query is parameterized and access_key is just a string comparison. Reliable exploitation to leak sensitive internals is therefore low-likelihood absent an underlying DB availability issue.

### Recommendation
Do not propagate raw wrapped datastore errors to the HTTP layer. In `AuthenticateExternalInitiator`, log the wrapped error server-side and return a generic sentinel (e.g., `auth.ErrorAuthFailed` or a new `auth.ErrorInternal`) to the caller so `jsonAPIError` never serializes internal error text for unauthenticated requests. Alternatively, harden `jsonAPIError`/the auth middleware to never echo raw `err.Error()` for non-2xx auth failures and instead use fixed messages for all outward-facing 401/500 responses on unauthenticated routes.

### Proof of Concept
1. Unit test in `core/web/auth`: construct a fake `Authenticator` whose `FindExternalInitiator` returns `nil, fmt.Errorf("pq: connection refused to db host 10.0.0.5:5432")`.
2. Call `AuthenticateExternalInitiator(c, fakeStore)` and assert the returned error's `Error()` string contains the raw injected message (confirms wrapping preserves internal detail) — this part is confirmed by code inspection.
3. Handler-level integration test: hit a route guarded by the actual gin middleware chain that uses `AuthenticateExternalInitiator` with headers causing this DB error, then assert on the resulting HTTP response body via `models.NewJSONAPIErrorsWith` — check whether `err.Error()` (containing "connection refused to db host 10.0.0.5:5432") appears in the JSON payload. This step needs to be run against the actual middleware setup (`core/web/router.go`) to confirm whether the generic `auth.ErrorAuthFailed` is substituted before reaching `jsonAPIError`, which determines whether this is exploitable in practice.
