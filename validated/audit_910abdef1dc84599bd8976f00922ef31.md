### Title
Unprotected ERC4626 deposit in `ProgrammableBorrower._depositToVault` enables share-price inflation theft of pooled lender funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The HtmlUnit report is an injection flaw: attacker-supplied content enters a trusted pipeline and is executed/valued as if it were benign input. The idle-tranches analog is injected value entering the facility's accounting pipeline: `ProgrammableBorrower` parks the credit pool's idle underlying in an external ERC4626 vault via raw `vault.deposit()` with no minimum-shares check, no dead-share seeding, and no pre/post share-price validation. Any unprivileged user of that ERC4626 vault can front-run the facility's first deposit, inflate the vault's price per share (the classic donation/first-depositor inflation), and cause the pool's deposit to mint zero or near-zero shares — the donation (injected assets) is then redeemed back together with the stolen deposit. The pool books the theft as a vault loss through `totalInterestDueNow()`/`vaultLoss()`, socializing it to AA/BB tranche holders at `stopEpoch`.

### Finding Description
`onStartEpoch` (called by `IdleCDOEpochVariant._startEpochProgrammableBorrower` at `contracts/IdleCDOEpochVariant.sol:288-297`) deposits the contract's entire idle underlying balance into the configured ERC4626 vault:

`contracts/strategies/idle/ProgrammableBorrower.sol:214-216`
```solidity
uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
// Any idle balance left on the contract between epochs is parked immediately into the vault.
_depositToVault(underlyingToken.balanceOf(address(this)), 0);
```

`contracts/strategies/idle/ProgrammableBorrower.sol:378-385`
```solidity
function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
  if (_assetAmount == 0) return;
  uint256 shares = vault.deposit(_assetAmount, address(this));
  ...
}
```

There is no check that `shares > 0` or that minted shares approximate the deposited value. `_borrow` (line 452) and `onStopEpoch` (line 246) similarly call `vault.withdraw` trusting `convertToAssets`. The same raw-deposit pattern exists in `ERC4626Strategy` (`contracts/strategies/ERC4626Strategy.sol`), which also lacks a min-shares guard, but the programmable-borrower path is the in-scope credit surface and the prompt explicitly lists "a user of the programmable borrower's ERC4626 vault" as an allowed attacker.

Sequence (buffer phase → `startEpoch`, programmable/minted-interest mode):
1. Owner configures a fresh or near-empty ERC4626 vault via `initialize`/`setVault` (`setVault` actually requires `vault.balanceOf(address(this)) == 0`, so a switch lands the facility on a vault where it holds no position; an attacker can hold the entire existing supply cheaply, or be first depositor on a brand-new vault).
2. Attacker deposits 1 wei (minting 1 share) and donates `D ≥ X` underlying directly to the vault, where `X` is the pool's idle balance awaiting `startEpoch`.
3. Manager calls `startEpoch`; `onStartEpoch` → `_depositToVault(X)` mints `X * 1 / (1 + D) = 0` shares. No revert — the deposit silently succeeds.
4. Attacker redeems its 1 share for `D + X`, profiting `X` (minus dust).
5. `_currentVaultAssets()` / `_vaultNetInterest()` (`ProgrammableBorrower.sol:337-347, 546-549`) now report the loss; at `stopEpoch` the missing amount flows into `totalInterestDueNow()` and, via `IdleCDOEpochVariant._stopEpoch` (`contracts/IdleCDOEpochVariant.sol:357-505`), into the tranche waterfall — BB-first loss socialization or a `_handleBorrowerDefault` the honest borrower did not cause.

Invariant broken: fair mint/burn — deposited principal must be recoverable; instead attacker-injected vault assets convert the pool's deposit into attacker-redeemable shares. No existing guard stops it: `_skimDonatedAssets` only sweeps raw underlying on the CDO contract itself (it cannot see donations inside the external vault), the self-call try/catch only catches reverts (the deposit succeeds), and `onlyIdleCDO`/KYC gating does not apply to the third-party vault's deposit entry point.

### Impact Explanation
Direct theft of pooled lender principal: up to the full idle balance deposited at `startEpoch` (attacker cost ≈ the stolen amount, net profit ≈ deposit size in the zero-shares case; for the partial-shares case, ~deposit/2 classically). Loss is quantified exactly by `X - recoveredSharesValue`. The theft is then crystallized into tranche prices via `_updateAccounting`'s BB-first waterfall or triggers a spurious borrower default and permanent freezing pending `finalizeDefault`.

### Likelihood Explanation
Conditions: programmable-borrower deployment whose configured ERC4626 vault has low/zero total supply at the moment the facility first deposits (fresh `setVault`, brand-new vault, or vault drained by other users). The attacker needs only to be a depositor in that public vault and hold capital on the order of the deposit — no privileged role, no borrower cooperation. This is the standard, well-known ERC4626 inflation attack applied at the facility's deposit entry point.

### Recommendation
- In `_depositToVault`, compute expected shares via `vault.previewDeposit(_assetAmount)` and require `shares >= expected * (1 - maxSlippage)` and `shares > 0`.
- Alternatively enforce a minimum share price bound or seed a dead-share position on first deposit, and record the pre-deposit `convertToAssets` price to detect injected-value dilution.
- Apply the same guard in `ERC4626Strategy._deposit` and to `vault.withdraw`/`redeem` return-value checks in `_borrow`/`onStopEpoch`.

### Proof of Concept
Foundry fork test sketch (pseudo, to be placed under `test/foundry/`):

```solidity
// Vault: real ERC4626 (e.g., OZ ERC4626 impl) or forked target vault, initially empty.
// Setup: IdleCDOEpochVariant + ProgrammableBorrower with isProgrammableBorrower=true,
// isInterestMinted=true; lender deposits X via depositAA during buffer.

// 1. Attacker seeds vault inflation
underlying.mint(attacker, X + 1);
vm.startPrank(attacker);
underlying.approve(address(vault), 1);
vault.deposit(1, attacker);                       // 1 share
underlying.transfer(address(vault), X);           // donate >= pool idle balance
vm.stopPrank();

// 2. Pool idle balance X sits on ProgrammableBorrower (from sendFundsToBorrower
//    or repayment during buffer). Manager calls startEpoch:
vm.prank(manager);
cdo.startEpoch();                                  // onStartEpoch -> _depositToVault(X)

// 3. ProgrammableBorrower minted 0 shares
assertEq(vault.balanceOf(address(pb)), 0);
assertEq(pb.totalUnderlying(), 0);                 // X effectively gone from ledger

// 4. Attacker redeems everything
vm.prank(attacker);
vault.redeem(1, attacker, attacker);
assertGt(underlying.balanceOf(attacker), 2 * X);   // profit ~X

// 5. Loss is socialized to tranche holders at stopEpoch via _updateAccounting,
//    or forces _handleBorrowerDefault on an honest borrower.
```

Caveat: the PoC depends on the configured vault's rounding behavior; it is reproducible against any ERC4626 that mints shares as `assets * supply / totalAssets` without zero-share revert (e.g., OpenZeppelin `ERC4626` prior to virtual-shares versions, or a vault with negligible supply).
