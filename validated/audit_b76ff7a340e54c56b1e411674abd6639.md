### Title
Unfunded instant-withdraw receipts are paid at par from the strategy's funded-claim pool - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out the caller's entire `instantWithdrawsRequests` balance without checking that the corresponding funds were ever collected via `collectInstantWithdrawFunds`. Unlike normal withdraw claims, which are gated by `epochNumber <= lastWithdrawRequest` so a full epoch (and thus a funding `stopEpoch`) must pass first, the instant path has no "was this request funded" binding. An unprivileged KYC'd lender can mint an unfunded instant receipt mid-epoch and immediately withdraw underlying that was collected for other users' pending claims, stealing funded liquidity.

The external report (gnark GHSA-7p92-x423-vwj6) fixed a missing check on the *number of public inputs* — a verifier accepted a proof whose declared inputs did not match what was actually bound. The analog here is identical in shape: the claim verifies that a receipt *exists* (`instantWithdrawsRequests[_user] != 0`) but never verifies the receipt's *funding inputs* — i.e., that `collectInstantWithdrawFunds` actually moved underlying into the strategy for that epoch's instant bucket (`instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` are tracked but unused as a claim gate).

### Finding Description
Flow, all within a running epoch with instant withdrawals enabled (`allowInstantWithdraw == true`):

1. Honest users' instant requests are funded at `startEpoch`/`getInstantWithdrawFunds`: the CDO transfers underlying and `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`). That underlying sits in the strategy until each user claims.
2. Attacker (a KYC-passed lender holding tranche tokens) calls `IdleCDOEpochVariant.requestInstantWithdraw`. `requestInstantWithdraw` burns the CDO's strategy tokens, mints the attacker a 1:1 receipt, increments `instantWithdrawsRequests[attacker]`, `instantWithdrawsRequestsByEpoch[attacker][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`).
3. Attacker immediately calls `claimInstantWithdrawRequest`. The function only checks `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, then pays `instantWithdrawsRequests[attacker]` in full via `_transferFundedClaim` (`IdleCreditVault.sol:380-393`). There is no check that `pendingInstantWithdraws` was funded for the attacker's epoch — the "public input count" (funded vs. declared receipts) is never verified.
4. `_transferFundedClaim` transfers underlying from the strategy balance, excluding only `defaultRecoveryReserve` (`IdleCreditVault.sol:897-900`). The attacker's unfunded receipt is paid from underlying that was collected for earlier, legitimate instant-withdraw receipts (and matured normal-request funds still held in the strategy).
5. When honest users later call `claimInstantWithdrawRequest`, the strategy balance is short and their transfers revert or underpay — direct theft plus temporary/permanent freezing of their claims.

The existing guards do not stop this: `_onlyIdleCDO` is satisfied (the CDO exposes `claimInstantWithdrawRequest` to anyone, gated only by `allowInstantWithdraw` at `IdleCDOEpochVariant.sol:975-978`); KYC/`isWalletAllowed` is satisfied because a lender is allowed; the epoch gating at `IdleCreditVault.sol:326` applies only to `_claimFundedWithdrawRequest`, not the instant path; and the per-epoch funding counters (`instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`) are written but never read on the claim path.

### Impact Explanation
Direct theft of underlying held by the strategy for other users' funded instant/normal withdrawal claims, up to `underlyingToken.balanceOf(strategy) - defaultRecoveryReserve`, proportional to the attacker's tranche holdings (they get back their own principal plus drain the funded pool). Second-order: honest claimants' transactions revert or pay short — temporary freezing that becomes permanent if the shortfall exceeds what later epochs refund.

### Likelihood Explanation
Requires an epoch-running phase with instant withdrawals enabled and a nonzero funded-but-unclaimed balance in the strategy — a routine state whenever any user's instant withdrawal was funded at `startEpoch` and has not yet claimed. The attacker needs only to hold tranche tokens (KYC-passed lender). No privileged cooperation, no default, no timing race beyond "attack before the honest user claims," which is front-runnable.

### Recommendation
Bind instant claims to collected funding, mirroring the funded-vs-declared check the gnark fix added. Concretely: gate `claimInstantWithdrawRequest` on the request's epoch having been funded — e.g., record `instantFundedByEpoch[epoch]` in `collectInstantWithdrawFunds` and require `instantWithdrawsRequestsByEpoch[_user][fundedEpoch] != 0` (or decrement a per-user unfunded counter), rather than paying the bare `instantWithdrawsRequests[_user]` aggregate. Alternatively, deduct claims from `pendingInstantWithdraws` and revert if the user's receipt exceeds the funded remainder.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_stopCurrentEpoch`, `_startEpochAndCheckPrices`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract InstantClaimUnfundedPoC is Test {
    // reuse suite fixtures: cdoEpoch, proxiedStrategy (IdleCreditVault),
    // idleCDO, underlying, borrower, manager, AAtranche, ONE_SCALE

    function testUnfundedInstantClaimDrainsFundedPool() external {
        address victim = makeAddr("victim");
        address attacker = makeAddr("attacker");

        // --- buffer phase: victim and attacker deposit (KYC'd lenders) ---
        uint256 victimTranches  = _depositWithUser(victim, 10_000 * ONE_SCALE);
        uint256 attackerTranches = _depositWithUser(attacker, 10_000 * ONE_SCALE);

        // enable instant withdraws
        vm.prank(manager);
        cdoEpoch.setInstantWithdrawParams(0, type(uint256).max, true);

        // victim requests instant withdraw during buffer so it is funded at startEpoch
        _requestInstantWithdrawWithUser(victim, victimTranches);

        // --- startEpoch: CDO funds pending instant requests ---
        // getInstantWithdrawFunds -> strategy.collectInstantWithdrawFunds
        // strategy now holds `victimAmount` underlying, pendingInstantWithdraws == 0
        vm.prank(manager);
        cdoEpoch.startEpoch();
        assertGt(underlying.balanceOf(address(strategy)), 0, "funded pool empty");

        // --- running epoch: attacker requests a NEW instant withdraw ---
        // receipt minted, pendingInstantWithdraws incremented, but no funds collected
        _requestInstantWithdrawWithUser(attacker, attackerTranches);

        // attacker claims immediately: pays aggregate receipt at par
        uint256 balPre = underlying.balanceOf(attacker);
        vm.prank(attacker);
        cdoEpoch.claimInstantWithdrawRequest();
        uint256 stolen = underlying.balanceOf(attacker) - balPre;
        assertGt(stolen, 0, "unfunded claim paid");
        // attacker recovered principal AND drained victim's funded share

        // victim's funded claim now reverts/underpays: strategy is short
        vm.prank(victim);
        vm.expectRevert(); // ERC20 transfer amount exceeds balance (or pays < owed)
        cdoEpoch.claimInstantWithdrawRequest();
    }
}
```

Key invariant broken: one funded receipt — one payout. `claimInstantWithdrawRequest` (line ~380-393) burns `instantWithdrawsRequests[_user]` and transfers that amount without verifying the request epoch was funded via `collectInstantWithdrawFunds`/`instantWithdrawClaimsByEpoch`, so an unfunded receipt spends funded underlying reserved for other users.

Caveat: I did not fully trace `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` call ordering inside `IdleCDOEpochVariant.startEpoch`, so the exact helper names in the PoC may need adjustment; the missing-funding check in `claimInstantWithdrawRequest` itself is confirmed from the source above.
