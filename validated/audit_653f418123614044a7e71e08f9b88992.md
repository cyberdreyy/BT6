### Title
`BlockRejection` and `BlockAccepted` sign the same bare `signer_signature_hash` with no message-type binding, allowing a gossiped rejection signature to be replayed as an acceptance - (File: `libsigner/src/v0/messages.rs`, consumed in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`BlockAccepted` signs the raw 32-byte `signer_signature_hash` directly with no domain separator: [1](#0-0)  and the node verifies an "Accepted" message purely by `signer_pubkey.verify(block_sighash.bits(), &signature)` [2](#0-1) . `BlockRejection::new` produces its signature by calling `rejection.sign(private_key)` over the same `signer_signature_hash` field [3](#0-2) , and `BlockRejection` is verified on the node side via `rejected_data.recover_public_key()` [4](#0-3) . Because neither construction binds a message-type tag (Accepted vs. Rejected) into the signed digest, a signature that is valid for a rejection over hash `H` under pubkey `P` is also a valid ECDSA signature for `H` under `P` in general, so it can be re-wrapped into a `BlockAccepted{signer_signature_hash: H, signature: S}` payload and replayed to a listener that only checks `P.verify(H.bits(), S)`.

### Finding Description
The invariant that should hold is: *a signed response's meaning (accept vs. reject) is cryptographically bound to what the signer intended*, i.e. `verify(P, S, H) == true` should only be possible for the exact message type the signer produced. Tracing the code:

- `Signer::create_block_acceptance` signs `block.header.signer_signature_hash().bits()` directly with the signer's private key, with no prefix distinguishing this from any other signed payload over the same hash [5](#0-4) .
- `BlockRejection::new`/`from_validate_rejection` construct a `BlockRejection` whose `signer_signature_hash` field is the identical block hash, then call `self.sign(private_key)` [3](#0-2) .
- On the consuming side (`stackerdb_listener.rs`), an `Accepted` message is validated only by checking the ECDSA signature against the bare `block_sighash.bits()` [2](#0-1) , and a successful check causes the sighash's `total_weight_approved` to be incremented and `gathered_signatures` to record the signer's vote [6](#0-5) .
- A `Rejected` message is validated via `rejected_data.recover_public_key()` [4](#0-3) , which recovers a pubkey from the *same* `(signer_signature_hash, signature)` pair.

Since ECDSA signature verification and recoverable-signature-derived-pubkey verification are mathematically equivalent operations over the same message digest, if `BlockRejection`'s signing digest is exactly `signer_signature_hash.bits()` (as its field layout and the recovery-based verification strongly suggest, since no other canonical "signable" quantity is defined per-rejection), then the signature `S` a victim signer produces when rejecting block `H` is *also* a valid signature over `H` for that signer's key under the bare-hash-verify used for acceptances. An attacker who is any single signer (or simply observes gossiped StackerDB traffic) can take a victim's legitimately broadcast `BlockRejection{signer_signature_hash: H, signature: S, ...}` and re-emit `BlockResponse::Accepted(BlockAccepted{signer_signature_hash: H, signature: S, ...})` attributed to the same slot/pubkey. Any listener (miner counting weight, or another signer's `determine_response`) that checks only `pubkey.verify(H.bits(), S)` will treat the victim as having accepted the block, when the victim actually rejected it.

No existing guard breaks this chain: there is no type-prefix, no domain-separation tag, and no chain-id/round/context binding mixed into the signed digest that would make an Accepted-signature computation diverge from a Rejected-signature computation over the same hash.

### Impact Explanation
This breaks the safety property that "a rejection recounted as acceptance" is impossible - explicitly listed as a Critical severity outcome. If enough replayed/relabeled rejection signatures are counted as acceptances, a block that should have been rejected by threshold weight can instead cross the `weight_threshold` for `total_weight_approved` [6](#0-5) , causing an invalid/non-canonical block to obtain a valid aggregate signature and be finalized. This is repeatable for any rejection message the attacker can observe on the gossip stream, requiring no majority signer weight and no compromise of any private key.

### Likelihood Explanation
The attacker only needs: (1) their own miner slot (to be able to craft/propose a block, which is a normal precondition for a BlockProposal to exist), and (2) the ability to observe/gossip StackerDB signer messages, which any signer or network observer can do. No majority weight, no auth_token, and no victim key material are required - only observation of a broadcast rejection and re-emission of a repackaged Accepted payload with the identical `(hash, signature)` pair. This is fully repeatable per rejected block/tenure.

### Recommendation
Bind the message type into the signed digest. Concretely, change `BlockAccepted`/`BlockRejection` signing to sign over a domain-separated digest, e.g. `sign(hash(type_prefix || signer_signature_hash || other fields))` where `type_prefix` differs between `BlockResponseTypePrefix::Accepted` and `BlockResponseTypePrefix::Rejected` (this prefix already exists at [7](#0-6)  but is not mixed into the signed payload). Update all verifiers (`stackerdb_listener.rs` and any signer-side aggregation logic) to recompute and check against the same domain-separated digest.

### Proof of Concept
```rust
// Pseudo-outline for a Rust test in stacks-signer / stacks-node test harness

#[test]
fn rejection_signature_replays_as_acceptance() {
    let victim_key = StacksPrivateKey::new();
    let victim_pubkey = StacksPublicKey::from_private(&victim_key);
    let block_sighash = Sha512Trunc256Sum::from_data(b"attacker-crafted-block");

    // Victim legitimately rejects the block.
    let rejection = BlockRejection::new(
        block_sighash,
        RejectReason::RejectedInPriorRound,
        &victim_key,
        false,
        0,
        0,
    );

    // Attacker lifts (hash, signature) from the rejection and repackages as Accepted.
    let forged_accept = BlockAccepted::new(
        rejection.signer_signature_hash,
        rejection.signature,
        0,
        0,
    );

    // Assert the forged acceptance verifies under the victim's pubkey using
    // the exact check performed in stackerdb_listener.rs.
    let valid = victim_pubkey
        .verify(forged_accept.signer_signature_hash.bits(), &forged_accept.signature)
        .unwrap();
    assert!(valid, "forged Accepted signature should verify -- confirms type confusion");

    // And confirm the original message really was a rejection, i.e. the two
    // interpretations diverge in intended meaning:
    assert_ne!(
        BlockResponse::Rejected(rejection.clone()),
        BlockResponse::Accepted(forged_accept.clone())
    );
}
```
If `valid == true`, the equality `signed_response.meaning == signer_intended_meaning` is broken: the same `(hash, signature)` pair verifies as both an acceptance and (via `recover_public_key`) a rejection, confirming the replay.

**Note on verification gap:** I was unable to retrieve within the available tool budget the exact byte-level implementation of `BlockRejection::sign`/`recover_public_key` (the `Signable`-style trait implementation) to give a byte-for-byte proof that its digest is *identical* to the bare `signer_signature_hash.bits()` used by `BlockAccepted`. The finding rests on strong circumstantial evidence (field layout, the recovery-based verification pattern, and the absence of any visible type/domain tag), but a Devin session with full file access should confirm the exact `sign`/`recover_public_key` byte content in `libsigner/src/v0/messages.rs` before treating this as fully validated.
