### Title
User enumeration and MFA-status disclosure via distinguishable login error messages - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` returns different, attacker-visible error strings depending on whether the account exists, whether the password is wrong, and whether MFA is configured for the account. These distinct messages are forwarded verbatim to the unauthenticated HTTP client by `SessionsController.Create`, allowing an unauthenticated caller to enumerate valid emails and identify which accounts lack MFA.

### Finding Description
The unauthenticated route `POST /sessions` is wired to `SessionsController.Create` [1](#0-0) , which calls `AuthenticationProvider().CreateSession(ctx, sr)` and forwards any returned error directly to the client via `jsonAPIError(c, http.StatusUnauthorized, err)` [2](#0-1) .

In `orm.CreateSession`:
- If the email does not exist in the `users` table, `o.FindUser` returns the raw DB lookup error (e.g. "sql: no rows in result set") immediately, before any constant-time comparison is performed [3](#0-2) .
- If the email exists but the (already-known-equal) email fails the redundant `constantTimeEmailCompare` check, it returns `"Invalid email"` [4](#0-3) .
- If the email is correct but the password is wrong, it returns `"Invalid password"` [5](#0-4) .
- If the credentials are valid and the account has WebAuthn/MFA registered, the function returns the full WebAuthn challenge JSON as the error body (`pkgerrors.New(string(j))`) — this response itself proves MFA is enabled and contains credential descriptor data — or `"MFA Error"` on failed attestation [6](#0-5) [7](#0-6) .
- If credentials are valid and no MFA is configured, a session is created successfully (200 OK) [8](#0-7) .

The code comment claims the ordering "prevent[s] extra database look up for MFA tokens leaking," but this only avoids one timing side-channel; it does not address the far more direct leak of **message content**. An attacker submitting `POST /sessions` with `{"email": X, "password": "wrongpwd"}` receives one of three distinguishable outcomes: a raw SQL "no rows" style error (email doesn't exist), `"Invalid password"` (email exists, no valid credentials supplied), or a JSON WebAuthn challenge (email exists, account has MFA enabled). This is sufficient to enumerate valid accounts and separate MFA-protected accounts from non-MFA accounts without any authentication, purely from response bodies — no timing analysis needed. `constantTimeEmailCompare` is irrelevant to this path since it is a self-comparison of an already-fetched record and never actually gates on DB lookup failure timing (that happens earlier in `FindUser`).

### Impact Explanation
This maps to a **user enumeration / information disclosure** class issue (not authentication bypass or secret disclosure by itself). It concretely reveals: (1) which emails have registered admin/API accounts, and (2) which of those accounts have MFA disabled, which are the accounts most susceptible to credential-stuffing/brute-force since they lack a second factor. The chained scenario described in the prompt (using this to eventually reach config/secret endpoints via credential stuffing on non-MFA accounts) is a downstream, non-guaranteed consequence — it requires the attacker to separately guess/obtain a valid password, which this bug does not provide. The directly provable impact is limited to account/MFA-status disclosure, which is a lower-severity finding than key/secret exposure or auth bypass.

### Likelihood Explanation
Fully unauthenticated and trivially repeatable: a single `POST /sessions` per candidate email, with no privileged access or preconditions required. The `unauthenticated` rate limiter on `/sessions` [9](#0-8)  throttles but does not prevent this enumeration; the confirmed rate-limit test only checks HTTP status codes eventually return 429, not that content leakage is blocked [10](#0-9) .

### Recommendation
- Return a single, generic, identical error message and identical HTTP status (e.g., "Invalid email or password") for all pre-MFA-challenge failure cases (account not found, email mismatch, wrong password), and ensure `FindUser`/`findUser` failures are folded into that same generic message before reaching the controller.
- Do not return the WebAuthn challenge JSON as an `error`; only return it for confirmed valid credentials, and consider using a uniform response shape/timing regardless of MFA registration state.
- Add a constant amount of dummy work (e.g., hash comparison against a fixed dummy hash) when the account does not exist, so response timing is also equalized.
- Audit `jsonAPIError` usage in `sessions_controller.go` to ensure internal error details are never echoed to unauthenticated clients.

### Proof of Concept
Handler-level integration test (extending `TestSessionsController_Create` in `core/web/sessions_controller_test.go`):
1. Create user A with no MFA and user B with WebAuthn/MFA registered.
2. POST `/sessions` with `{"email": "nonexistent@test.net", "password": "x"}` — capture response body/detail.
3. POST `/sessions` with `{"email": A.Email, "password": "wrong"}` — capture response body/detail.
4. POST `/sessions` with `{"email": B.Email, "password": B.Password}` (no `webAuthnData`) — capture response body/detail.
5. Assert: steps 2–4 currently produce three distinct response bodies (raw DB error vs `"Invalid password"` vs WebAuthn challenge JSON), proving enumeration; after the fix, assert all three produce an identical generic message/status.

func TestSessions_RateLimited(t *testing.T) {
	t.Parallel()

	ctx := t.Context()
	app := cltest.NewApplicationEVMDisabled(t)
	require.NoError(t, app.Start(ctx))

	router := web.Router(t, app, nil)
	ts := httptest.NewServer(router)
	defer ts.Close()

	client := clhttptest.NewTestLocalOnlyHTTPClient()
	input := `{"email":"brute@force.com", "password": "wrongpassword"}`

	for range 5 {
		request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
		require.NoError(t, err)

		resp, err := client.Do(request)
		require.NoError(t, err)
		assert.Equal(t, http.StatusUnauthorized, resp.StatusCode)
	}

	request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
	require.NoError(t, err)

	resp, err := client.Do(request)
	require.NoError(t, err)
	assert.Equal(t, 429, resp.StatusCode)
}
