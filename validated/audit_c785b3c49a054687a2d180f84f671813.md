### Title
Decimal Conversion Rounding in `bridgeERC20`/`bridgeETH` Permanently Locks Dust in `BridgeVault` — (`bridge/evm/contracts/SuiBridge.sol`)

### Summary

`BridgeUtils.convertERC20ToSuiDecimal` performs integer division that silently truncates sub-precision wei. The full ERC20 amount (including the truncated remainder) is transferred into `BridgeVault`, but only the rounded-down `suiAdjustedAmount` is recorded in the `TokensDeposited` event. Because the vault has no sweep or recovery function, the truncated dust is permanently locked with no on-chain path to reclaim it.

### Finding Description

In `SuiBridge.bridgeERC20` and `SuiBridge.bridgeETH`, the deposit flow is:

1. Transfer the full user-supplied `amount` into `BridgeVault`.
2. Compute `suiAdjustedAmount = BridgeUtils.convertERC20ToSuiDecimal(erc20Decimal, suiDecimal, amountTransfered)`.
3. Emit `TokensDeposited` with `suiAdjustedAmount`.

`convertERC20ToSuiDecimal` performs:

```solidity
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
amount = amount / factor;          // integer division — truncates remainder
return uint64(amount);
```

For ETH (18 EVM decimals → 8 Sui decimals), `factor = 10^10`. Any deposit whose wei value is not a multiple of `10^10` leaves up to `10^10 − 1` wei (≈ 10 Gwei) in the vault that is never represented in any bridge message.

The existing test explicitly demonstrates this:

```solidity
// 2_000_000_011_000_000_888 is rounded to 2.00000001 eth
bridge.bridgeERC20(BridgeUtils.ETH, 2_000_000_011_000_000_888, ...);
assertEq(IERC20(wETH).balanceOf(address(vault)), 3_000_000_011_000_000_888);
// suiAdjustedAmount = 200_000_001 → represents only 2_000_000_010_000_000_000 wei
// dust locked: 1_000_000_888 wei
```

`BridgeVault` exposes only `transferERC20` and `transferETH`, both `onlyOwner` (the `SuiBridge` contract). `SuiBridge` calls these only inside `_transferTokensFromVault`, which is only reachable via `transferBridgedTokensWithSignatures` — a path that requires a committee-signed bridge message. No such message is ever created for the dust, so it is permanently unclaimable.

The same issue exists in `SuiBridgeV2.bridgeERC20V2` and `SuiBridgeV2.bridgeETHV2`.

### Impact Explanation

Every `bridgeERC20` or `bridgeETH` call whose amount is not an exact multiple of `10^(erc20Decimal − suiDecimal)` permanently locks the remainder in `BridgeVault`. There is no admin sweep, no refund path, and no bridge message that can ever release the dust. This is a **permanent fund lock** triggered by any ordinary bridge user.

### Likelihood Explanation

Any user who calls `bridgeERC20` or `bridgeETH` with a non-aligned amount (e.g., any ETH amount that is not a multiple of 10 Gwei) triggers the lock. This is the common case for ETH transfers. The attacker model is an ordinary bridge user — no privilege required.

### Recommendation

Before transferring tokens to the vault, align the amount to the precision boundary and refund the remainder to the caller:

```solidity
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
uint256 alignedAmount = (amount / factor) * factor;
uint256 dust = amount - alignedAmount;
// transfer only alignedAmount to vault
// if (dust > 0) refund dust to msg.sender
```

Alternatively, revert if `amount % factor != 0`, forcing callers to supply aligned amounts.

### Proof of Concept

1. Alice calls `SuiBridge.bridgeERC20(ETH, 2_000_000_011_000_000_888, recipientSuiAddr, suiChainId)`.
2. `2_000_000_011_000_000_888` wei is transferred from Alice to `BridgeVault`.
3. `convertERC20ToSuiDecimal(18, 8, 2_000_000_011_000_000_888)` → `factor = 10^10`, `amount / factor = 200_000_001`, returns `200_000_001`.
4. `TokensDeposited` is emitted with `suiAdjustedAmount = 200_000_001` (representing `2_000_000_010_000_000_000` wei).
5. Bridge nodes mint `200_000_001` Sui-side ETH for Alice.
6. `BridgeVault` holds `1_000_000_888` wei of dust that no bridge message will ever claim.
7. `BridgeVault.transferERC20` is `onlyOwner`; `SuiBridge` never calls it for amounts not backed by a signed message. Dust is permanently locked.
