### Title
Unauthenticated caller can set vault APR while `idleCDO` is unset - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Strapi bug class is a privileged state-changing action executed without the credential that is supposed to gate it (a password reset accepted without a valid reset token). The closest analog in this repo is `IdleCreditVault.setApr` / `setAprs` / `setAprsWithBuffer`, which deliberately skip the `only CDO or manager` authorization check whenever `idleCDO == address(0)`. Any unprivileged EOA can therefore rewrite `lastApr` and `unscaledApr` during the window between strategy initialization and `setWhitelistedCDO`, an action intended to be restricted to privileged roles.

### Finding Description
In `setApr`, the caller check is conditional on the CDO already being configured:

```solidity
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

`setAprs` and `setAprsWithBuffer` are also unauthenticated entry points; they write `unscaledApr` with no bound at all and then route into `setApr`. `unscaledApr` is never capped — it controls the APR0 request flow (`requestWithdraw` branches on `unscaledApr == 0`) and is the raw borrower-facing rate, while `lastApr` (capped only at `maxApr = 20e18`) drives epoch interest expectations via `IIdleCDOEpochVariant.expectedEpochInterest` consumers such as `prepareStopEpochWithApr0`, `_lossActiveBasis`, and `_defaultActiveInterestBasis`.

The broken invariant is access control on a privileged parameter: the code comments state "only cdo and manager can set the apr", but the check is bypassable by any caller during setup. This mirrors CVE-2019-18818, where the "valid reset token" check was bypassable, letting an unauthenticated party perform an admin-only action.

### Impact Explanation
Two concrete attacker paths exist during the setup window:

1. **Yield theft / interest manipulation**: set `unscaledApr` and `lastApr` to an arbitrary value (including near the 20e18 cap or 0). If the first epoch runs before the manager/CDO overwrites the APR, the borrower-facing rate and the epoch interest expectations are wrong in either direction — inflating expected interest so `stopEpoch` reverts on insufficient borrower repayment (freezing all lender funds in the vault until the honest manager intervenes), or zeroing it so an epoch completes with no yield owed (permanent loss of that epoch's unclaimed yield, which belongs to lenders).
2. **APR0 accounting corruption**: flipping `unscaledApr` to or from 0 mid-setup changes which request branch `requestWithdraw` takes (APR0 bucket vs normal `withdrawsRequests`), corrupting `apr0TotalPrincipal` / `apr0RateByEpoch` accounting for the first epoch and causing pro-rata interest misallocation at `prepareStopEpochWithApr0`.

Loss is bounded by one epoch of pool yield or temporary freezing of full TVL, whichever the misconfiguration produces; quantified worst case is the entire vault TVL frozen until owner/manager correction, or 100% of the first epoch's interest.

### Likelihood Explanation
The vulnerability requires a real deployment/upgrade ordering gap: `initialize` must complete while `setWhitelistedCDO` is pending (factory flows that deploy the strategy, then deploy/configure the CDO, then wire `idleCDO` create exactly this window, which can span multiple blocks and is front-runnable). Attacker cost is a single transaction; no privileged role is needed, matching the "unauthenticated" severity of the source bug. Likelihood is limited by the window's duration and by whether the honest manager resets the APR before the first `startEpoch`, but nothing on-chain prevents the write.

### Recommendation
Remove the conditional bypass: enforce `msg.sender == idleCDO || msg.sender == manager` unconditionally in `setApr`, and either set `idleCDO` inside `initialize` or require a separate owner-only one-time bootstrap function for pre-CDO configuration. Also apply a cap to `unscaledApr` in `setAprs`/`setAprsWithBuffer`, since it is currently written unchecked.

### Proof of Concept
Foundry fork PoC (assumes a deployed `IdleCreditVault` proxy where `initialize` has run but `setWhitelistedCDO` has not):

```solidity
function test_UnauthenticatedAprSet() public {
    IdleCreditVault vault = IdleCreditVault(strategyProxy);
    assertEq(vault.idleCDO(), address(0));

    address attacker = makeAddr("attacker");
    vm.prank(attacker);
    // any EOA: sets borrower-facing APR and scaled APR with no authorization
    vault.setAprs(0, 0); // or type(uint256).max unscaled / up to maxApr scaled

    assertEq(vault.unscaledApr(), 0);
    assertEq(vault.getApr(), 0);
    // subsequent epoch accrues zero borrower interest -> lender yield lost,
    // or a max APR causes stopEpoch to expect interest the borrower never owes -> revert/freeze
}
```

Caveat: I was unable to fully trace `IdleCDOEpochVariant.startEpoch`/`stopEpoch` within the available iterations to confirm whether the manager/CDO unconditionally rewrites the APR at epoch start (which would narrow the impact to a revert/freeze rather than yield loss). The missing authorization itself is confirmed directly in `IdleCreditVault.sol:225-235`.
