### Title
Multisig `DeleteKey`/`DeleteMember` does not purge stale confirmations from other pending requests, allowing a request to execute with fewer live signers than `num_confirmations` - ([File: multisig/src/lib.rs], [File: multisig2/src/lib.rs])

### Summary
When a multisig member/key is removed via `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`), the contract only purges requests that the removed key **created**, and clears `num_requests_pk`/`num_requests_per_member` for that key. It never scans `confirmations` for *other* pending requests where the removed key/member had already cast a confirmation. That stale confirmation entry remains counted toward `num_confirmations` in `confirm()`, so a request can later be pushed over the threshold and executed even though one of the "confirming" identities is no longer a member of the multisig.

### Finding Description
`confirm()` in both contracts only checks the raw size of the `confirmations` set/hashmap entry against `num_confirmations`, without re-validating that every public key/member still present in that set is a current member: [1](#0-0) 

The removal logic for a key, `MultiSigRequestAction::DeleteKey`, only removes requests where the removed key was the *original creator* (`r.signer_pk == pk`); it does not touch the `confirmations` map for any other outstanding request the same key may have already confirmed: [2](#0-1) 

The same gap exists in `multisig2`'s `delete_member`, which only removes requests created by the removed member (`r.member == member`) and never scans other requests' `confirmations` sets for stale entries from that member: [3](#0-2) 

and its `confirm()` similarly just compares set size to `num_confirmations`: [4](#0-3) 

The intended invariant is: `confirmations counted == confirmations from members that are still live`. Because removal only cleans up requests *authored* by the removed identity, not confirmations it *gave* on other requests, this equality is broken — a stale confirmation from a deleted key/member is silently retained and still counts toward the threshold.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold": once a key/member is removed, any pending request it previously confirmed still carries that confirmation weight. If the remaining live members later add enough confirmations to reach `num_confirmations` (counting the stale one), `execute_request` will fire actions (including `Transfer`, `AddKey`, `FunctionCall`, etc.) with effectively fewer live, currently-authorized signers than the multisig's own security parameter requires. This directly undermines the core guarantee of the multisig (`k`-of-`n` current members must approve).

### Likelihood Explanation
This requires only ordinary, unprivileged multisig operations already exposed by the contract's interface: creating a request, confirming it, and later executing a `DeleteKey`/`DeleteMember` request that removes one of the confirmers (not the requester) of a still-pending, not-yet-executed request. No owner/foundation privilege beyond being an existing multisig signer is needed, and no redeploy or malicious validator assumption is required — it is a straightforward ordering-of-operations issue reachable by any member set through normal contract usage.

### Recommendation
When executing `DeleteKey` (`multisig`) / `DeleteMember` (`multisig2`), iterate over all outstanding `requests` and remove the deleted key/member's entry from each associated `confirmations` set, not just the requests it authored. Alternatively, when `confirm()` computes the count, re-validate each stored key/member against the current member set (or `access_key`/`members` set) and discard invalid entries before comparing to `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(3)` (or `multisig2` with 3 members) with keys/members `A`, `B`, `C`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R1)` for some `Transfer` request → `confirmations[R1] = {A}` (count 1).
3. `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}` (count 2, below threshold, not yet executed).
4. Separately, `A`, `B`, `C` collectively pass a `DeleteKey { public_key: B }` request (requires all 3 confirmations, since none of them were removed yet) — this removes `B` as a valid multisig key/member.
   - Per [2](#0-1) , this only deletes requests *created by* `B`; `R1` was created by `A`, so it is untouched and `confirmations[R1]` still contains `B`.
5. `C` calls `confirm(R1)` → `confirmations.len() == 2`, so `2 + 1 >= 3` is true, and `execute_request` fires the transfer — even though `B` is no longer a valid signer, meaning only `A` and `C` (2 live members) truly authorized a request gated at a 3-confirmation threshold.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
