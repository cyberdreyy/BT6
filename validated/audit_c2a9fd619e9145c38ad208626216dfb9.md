### Title
Removed multisig member's stale confirmations remain counted toward quorum, allowing request execution below the live-member threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The multisig contracts allow a request to execute once `confirmations.len() + 1 >= num_confirmations`. When a member/key is removed via a `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`) request, the code only purges requests *authored by* that member/key and their own confirmation set — it does not scan `confirmations` for *other* still-pending requests that the removed member had already confirmed. Those stale confirmations remain in the `confirmations` set and continue to count toward `num_confirmations`, letting a request execute even though fewer than `num_confirmations` currently-authorized members actually approved it.

### Finding Description
In `execute_request`, the `DeleteKey` action (multisig) only cleans requests it created: [1](#0-0) 

Similarly in multisig2, `delete_member` only removes requests authored by (`r.member == member`) the deleted member: [2](#0-1) 

Neither routine iterates the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` / `LookupMap<RequestId, HashSet<String>>` structure to strip the removed key/member's entry from confirmation sets belonging to requests *authored by other members*. `confirm()` treats the raw cardinality of that set as proof of live-member approval: [3](#0-2) [4](#0-3) 

This breaks the intended custody binding: `confirmations counted == confirmations by currently-live members`. After removal, `confirmations counted > confirmations by live members`, because a stale entry from a revoked key/member is still present and still adds to the count.

### Impact Explanation
This is a Critical-class finding under the stated impact rules: "a multisig request executed below threshold." A pending `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` request can reach and execute quorum with strictly fewer than `num_confirmations` *currently authorized* signers, because a since-revoked signer's earlier confirmation is never invalidated. Funds can be moved, or new access keys/members added, by a coalition smaller than the multisig's advertised security threshold.

### Likelihood Explanation
This requires only actions available to legitimate multisig members/administrators through normal contract usage (no owner/foundation privilege beyond what the multisig grants its own members, and no assumption of a misconfigured deployment): a member confirms a pending request, is later removed via a separate `DeleteKey`/`DeleteMember` request (e.g., because their key is believed compromised or they leave the organization), and the remaining members confirm the same still-open request. No special timing or race condition is needed — the request simply needs to remain in the `active_requests_limit` / not yet be deleted (past `REQUEST_COOLDOWN`) window, which is the normal lifetime of an unconfirmed request.

### Recommendation
When executing `DeleteKey` (multisig) / `DeleteMember` (multisig2), iterate all entries in `confirmations` (not just those for requests the removed key authored) and remove the deleted key/member's entry from every confirmation set; equivalently, recompute `confirmations.len()` at confirm-time by intersecting with the current live-member set instead of trusting the raw stored `HashSet` cardinality.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 3`. [5](#0-4) 
2. `B` calls `add_request` to create request `R` (e.g., `Transfer` of the contract's balance to an attacker-controlled `receiver_id`), then confirms it. `confirmations(R) = {B}` (1/3). [6](#0-5) 
3. `A` confirms `R` too. `confirmations(R) = {A, B}` (2/3) — still below quorum, request stays pending.
4. Separately, the remaining members submit and pass a `DeleteMember { member: A }` request to revoke `A` (e.g., because `A`'s key was suspected compromised). This calls `delete_member`, which removes `A`'s access key and any requests *A authored*, but `R` was authored by `B`, so `R` and its confirmation set (still containing `A`) are untouched. [2](#0-1) 
5. `C` confirms `R`. `confirmations(R) = {A, B, C}` → `len()+1 >= 3` is satisfied by the code's count, so `execute_request` fires and the transfer executes — even though `A` is no longer a live member and only `B` and `C` (2 live members) actually approved at execution time. [7](#0-6) 

This demonstrates a multisig transfer executed with confirmations below the intended live-member threshold, matching the Critical impact criterion.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Add request for multisig.
    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// Add request for multisig and confirm with the pk that added.
    pub fn add_request_and_confirm(&mut self, request: MultiSigRequest) -> RequestId {
        let request_id = self.add_request(request);
        self.confirm(request_id);
        request_id
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
