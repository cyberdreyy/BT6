### Title
Incomplete secret-redaction blacklist in HTTP request logging exposes credentials in debug logs - (File: core/web/router.go)

### Summary
Chainlink's web server logs every incoming HTTP request body and query string via `loggerFunc` when running at debug log level. Before logging, it attempts to redact sensitive fields using `readSanitizedJSON` (for the body) and `redact` (for the query string), both of which rely on `isBlacklisted` to decide what to mask. This mirrors the exact remediation item raised against `in3-server`: *"Do not leak credentials and key material in debug-mode, to local log-output or external log aggregators."*

### Finding Description
The redaction logic only recognizes field names equal to or containing the substring `"password"`: [1](#0-0) 

Any other secret-bearing field name — API secrets/tokens, external-initiator secrets, bridge outgoing/incoming authentication tokens, mnemonic/seed values, or raw/keystore JSON key material submitted to key-management endpoints — is **not** matched by this blacklist and is logged verbatim by `readSanitizedJSON`/`redact`: [2](#0-1) 

This is invoked unconditionally for every request through the debug-level logging middleware: [3](#0-2) 

Because the blacklist is a hardcoded, narrow allowlist-by-name approach (`password`, `newpassword`, `oldpassword`, `current_password`, `new_account_password`) rather than a broader secret-detection strategy, any endpoint whose JSON body or query parameters carry credential material under a differently-named field (e.g. `secret`, `token`, `apiKey`, `mnemonic`, key JSON payloads for key import/export flows) will have that material written to the node's structured logs whenever `Log.Level = 'debug'` is set — the same log stream that is commonly shipped to external log aggregators (as explicitly called out in the in3-server report regarding Sentry/log aggregation).

### Impact Explanation
If an operator runs the Chainlink node at debug log level (a supported, documented configuration, not an exotic edge case) and the node exposes credential-bearing fields that aren't literally named `*password*`, those secrets end up in plaintext in local log files and any configured external log shipping/aggregation pipeline. This can lead to compromise of external-initiator secrets, bridge authentication tokens, or key material submitted through admin key-management endpoints, potentially enabling request impersonation or unauthorized job triggering downstream.

### Likelihood Explanation
The logging middleware runs on every request path unconditionally; the only gating factor is the configured log level (`debug`), which is a normal operational setting, not an attacker-controlled toggle. The likelihood of exposure is therefore driven entirely by naming mismatches between actual secret field names in various API request bodies and the fixed 5-entry blacklist — a maintenance gap rather than a rare edge case, since the blacklist has not evolved alongside new secret-bearing fields added to the API surface.

### Recommendation
- Replace the name-based blacklist with an explicit allowlist of loggable fields, or a broader pattern match (`secret`, `token`, `apikey`, `key`, `mnemonic`, `credential`, etc.) in `isBlacklisted`.
- Avoid logging raw request bodies for endpoints known to carry key material (key import/export, external initiator creation, bridge creation) regardless of log level.
- Apply the same redaction rules (or stronger ones) to `secrets.toml`-style value redaction already implemented elsewhere in the codebase, e.g. the pattern used for `core/services/chainlink/testdata/secrets-full-redacted.toml`, so that redaction coverage is consistent across configuration files and HTTP logging.

### Proof of Concept
1. Configure the node with `Log.Level = 'debug'`.
2. Send an authenticated `POST` request to an endpoint whose JSON body contains a credential field not literally named with `password` (for example a bridge/external-initiator creation payload carrying an outgoing/incoming token, or a key-import payload carrying keystore JSON).
3. Observe the node's structured debug log output produced by `loggerFunc` — the `body`/`query` fields will contain the full unredacted value, since `isBlacklisted` only matches on `password`-related keys. [4](#0-3) 
4. If the deployment forwards logs to an external aggregator (Loki, Papertrail, Sentry, etc.), the secret is now persisted outside the node's trust boundary.

func loggerFunc(lggr logger.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		buf, err := io.ReadAll(c.Request.Body)
		if err != nil {
			lggr.Error("Web request log error: ", err.Error())
			// Implicitly relies on limits.RequestSizeLimiter
			// overriding of c.Request.Body to abort gin's Context
			// inside io.ReadAll.
			// Functions as we would like, but horrible from an architecture
			// and design pattern perspective.
			if !c.IsAborted() {
				c.AbortWithStatus(http.StatusBadRequest)
			}
			return
		}
		rdr := bytes.NewBuffer(buf)
		c.Request.Body = io.NopCloser(bytes.NewBuffer(buf))

		start := time.Now()
		c.Next()
		end := time.Now()

		lggr.Debugw(fmt.Sprintf("%s %s", c.Request.Method, c.Request.URL.Path),

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
