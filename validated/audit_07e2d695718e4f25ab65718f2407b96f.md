### Title
User enumeration via distinguishable error messages/timing in login flow - ([File: core/sessions/localauth/orm.go])

### Summary
`(o *orm) CreateSession` returns a distinct, raw database error (e.g. "sql: no rows in result set") when the submitted email does not match any user, versus a generic "Invalid password" when the email exists but the password is wrong. Because `SessionsController.Create` forwards `err.Error()` verbatim to the HTTP response, an unauthenticated attacker can distinguish "email exists" from "email does not exist" by comparing response bodies, independent of the `constantTimeEmailCompare` timing-safe check (which never actually protects this path, since a non-existent email fails before that check is even reached).

### Finding Description
The login flow is: `POST /sessions` → `SessionsController.Create` → `AuthenticationProvider().CreateSession(ctx, sr)` [2](#0-1) . Inside `CreateSession`, the first step is `o.FindUser(ctx, sr.Email)` which runs `SELECT * FROM users WHERE lower(email) = lower($1)` [3](#0-2) . If no row exists, this call errors immediately and `CreateSession` returns that raw DB error with no audit-safe wrapping [4](#0-3) .

If the email *does* exist, execution proceeds past `FindUser` to the `constantTimeEmailCompare` check (which is effectively a no-op since the SQL query already guarantees `lower(user.Email) == lower(sr.Email)` for any returned row) and then to `utils.CheckPasswordHash`, returning the distinct string `"Invalid password"` on mismatch [5](#0-4) .

These two error values — a raw SQL "no rows" error vs. the literal string "Invalid password" — are different in both content and (since one path does an extra bcrypt hash comparison) latency. `jsonAPIError` copies `err.Error()` straight into the JSON response body [1](#0-0) , so the attacker directly observes which case occurred. The `constantTimeEmailCompare`/`mathutil.Max(constantTimeEmailLength,...)` padding logic referenced in the question only guards a constant-time comparison of two already-matched, lowercased strings — it does nothing to normalize the "user not found" vs. "wrong password" divergence that happens before it, so it does not actually close the enumeration channel.

### Impact Explanation
This matches the "user enumeration" class of impact: an unauthenticated caller can determine whether a given email address is registered as a node API user (including likely admin accounts), which is a reconnaissance primitive that materially aids targeted credential-stuffing/brute-force/phishing against confirmed valid accounts. It does not by itself grant authentication bypass, privilege escalation, or credential disclosure, so the impact is bounded to information disclosure/enumeration rather than direct account compromise.

### Likelihood Explanation
No credentials or privileges are required — the `/sessions` endpoint is explicitly unauthenticated (`unauth.POST("/sessions", sc.Create)`) [6](#0-5) , gated only by a rate limiter, not by authentication. Rate limiting throttles volume but does not prevent the enumeration technique itself — an attacker with time/multiple source IPs or a slow drip can still fully enumerate. The behavior is deterministic and repeatable per request (message differs every time; not merely a subtle timing side-channel), making exploitation straightforward rather than probabilistic.

### Recommendation
Normalize the error path so `CreateSession` returns the same generic error value/message (e.g. `"Invalid email or password"`) and performs equivalent work (a dummy `CheckPasswordHash` call against a fixed hash) regardless of whether `FindUser` found a row, so that neither the message nor the timing distinguishes "no such user" from "wrong password." This should be done at the top of `CreateSession` before branching on `FindUser`'s error, not only in the already-vestigial `constantTimeEmailCompare` check.

### Proof of Concept
Go handler-level integration test in `core/web/sessions_controller_test.go`:
1. Create one known user via `app.AuthenticationProvider().CreateUser`.
2. Send `POST /sessions` with `{"email": "<existing>@test.net", "password": "wrongpassword"}` and capture response body/status.
3. Send `POST /sessions` with `{"email": "doesnotexist@test.net", "password": "wrongpassword"}` and capture response body/status.
4. Assert both requests return `401` — but currently the response bodies differ: case (2) contains `"Invalid password"` while case (3) contains a raw driver error string (e.g. containing `"no rows"`), demonstrating the enumeration oracle. A stronger PoC additionally measures wall-clock latency of both requests over N repetitions and asserts they are statistically indistinguishable (currently they are not, since the "no such user" path skips the bcrypt `CheckPasswordHash` call entirely).
