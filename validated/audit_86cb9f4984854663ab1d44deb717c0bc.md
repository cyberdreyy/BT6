### Title
Unbounded zstd compression + base64 re-encode of attacker-grown accounts in `encode_ui_account` - (File: account-decoder/src/lib.rs)

### Summary
`encode_ui_account`'s `UiAccountEncoding::Base64Zstd` branch always compresses and base64-encodes the *entire* (post-`slice_data`) account buffer with no upper bound check before doing the work, and `getAccountInfo`/`getMultipleAccounts` do not require or default to a `dataSlice` for this encoding. An attacker can grow an owned account to `MAX_ACCOUNT_DATA_LEN` (10 MiB) via on-chain reallocation and then have any client's single `getAccountInfo` call with `base64+zstd` encoding force a ~10 MB zstd compression pass and a full base64 re-encode on the RPC's blocking thread pool.

### Finding Description
`encode_ui_account` in `account-decoder/src/lib.rs` (lines 67-79) builds a `zstd::stream::write::Encoder` and writes `slice_data(account.data(), data_slice_config)` into it unconditionally, then base64-encodes the compressed output: [1](#0-0) 
There is no size guard analogous to the `MAX_BASE58_BYTES` check that `encode_account` in `rpc/src/rpc.rs` performs for `Binary`/`Base58` encodings: [2](#0-1) 
That guard only fires for `Binary`/`Base58`; `Base64Zstd` falls into the `else` branch and calls `encode_ui_account` directly with whatever `data_slice` the client supplied (which can be `None`).

`get_account_info` in `rpc/src/rpc.rs` (lines 534-560) accepts the client-supplied `encoding` and `data_slice` and dispatches to `get_encoded_account` on a `spawn_blocking` thread, with no minimum/maximum data-slice enforcement tied to encoding cost: [3](#0-2) 

An account owner can grow an account they own via CPI/realloc up to `MAX_ACCOUNT_DATA_LEN` (10 MiB) — the on-chain growth path enforces `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` and caps the final size at `MAX_ACCOUNT_DATA_LEN`, but does not stop the account from persisting at 10 MiB once grown: [4](#0-3) [5](#0-4) 

Once the account is stored at 10 MiB, any single `getAccountInfo` call with `encoding: "base64+zstd"` and no `dataSlice` triggers the full-buffer compression and base64 re-encode path shown above, on the RPC's blocking-task pool, with cost proportional to the attacker-authored account size rather than any RPC-imposed limit.

### Impact Explanation
This is a single-request, unbounded-cost RPC operation: one `getAccountInfo` call (within the rate limit of one call per `CLUSTER_SLOT_TIME_TARGET / 2`) forces the RPC-serving thread to allocate and process ~10 MB of data through a zstd encoder and then a base64 encoder, producing multiple large heap allocations and a compression pass whose cost is fully attacker-controlled (both size and content — low-entropy/adversarial data can be chosen to maximize CPU time in the compressor). This matches the "unbounded cost for a single low-rate call" category in scope, causing CPU/memory pressure on the RPC node proportional to `MAX_ACCOUNT_DATA_LEN` rather than any RPC-side cost bound.

### Likelihood Explanation
Fully feasible with only unprivileged capabilities: the attacker needs to own a program/account and grow its data to 10 MiB using ordinary realloc/CPI operations (bounded by existing per-transaction growth limits, so this may take multiple transactions but no special privilege), then issue a single `getAccountInfo` RPC call with `base64+zstd` encoding and no `dataSlice`. This is fully repeatable against any RPC node that serves the account and supports `Base64Zstd` encoding (the `zstd` feature is enabled by default in most deployments). No multiple clients or elevated rate are required.

### Recommendation
Add an explicit size/cost guard for `Base64Zstd` (and other whole-buffer transforms) in `encode_account`/`encode_ui_account`, mirroring the existing `MAX_BASE58_BYTES` check for `Binary`/`Base58`: require a `dataSlice` (or reject/cap) when the (post-slice) length exceeds a bounded threshold, so a single request's compression/encoding cost is bounded independent of the attacker-authored account size.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
