### Title
Missing role check on `GET /v2/bridge_types` (and `GET /v2/bridge_types/:BridgeName`) discloses `OutgoingToken` to Run/View-role principals - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Index` (and `Show`) are registered in `router.go` without any `auth.RequiresXRole` wrapper, unlike the sibling mutation routes (`Create`, `Update`, `Destroy`) which are guarded by `auth.RequiresEditRole`. Any authenticated principal — including a `run`-role or `view`-role user whose intended privilege is limited to invoking job runs / read-only dashboards — can call `GET /v2/bridge_types` and receive every bridge's `OutgoingToken` in the JSON:API response.

### Finding Description
The route table wires the read endpoints with only the generic authentication middleware, no role check: [1](#0-0) 

Compare this to the mutating routes on the same resource, which are explicitly wrapped with `auth.RequiresEditRole`, showing the developers intended write operations (and, implicitly, secret-bearing operations) to require a minimum role — but forgot to apply an equivalent guard to `Index`/`Show`.

`Index` fetches all bridges and serializes them via `presenters.NewBridgeResource`, which copies `OutgoingToken` unconditionally into the response (`omitempty` is only applied to `IncomingToken`, not `OutgoingToken`): [2](#0-1) [3](#0-2) 

The role hierarchy defined in `core/web/auth/auth.go` is View < Run < Edit < Admin: [4](#0-3) 

Because `Index`/`Show` have no role predicate at all, a `view`-role user (whose entire purpose is read-only monitoring with no secret access) or a `run`-role user (intended only to invoke `/v2/jobs/:ID/runs`, per the comment on `AuthenticateExternalInitiator` at lines 145-148) can retrieve the `OutgoingToken` for every bridge configured on the node. `OutgoingToken` is the credential the node presents to the external adapter when it delivers job-run requests; harvesting it lets the attacker impersonate the node to the bridge/adapter or replay authenticated requests against it.

### Impact Explanation
This is a credential/secret-disclosure issue: an under-privileged, legitimately-provisioned account (view or run role) can exfiltrate the `OutgoingToken` secret for all bridges node-wide, which is scoped to be accessible only to edit/admin roles for mutation and arguably should be similarly restricted for read access, since it is a live credential rather than just a name/URL. This matches the Chainlink bounty "sensitive credential/secret disclosure via authorization bypass" impact class — it does not directly move funds or execute unauthorized job runs, but it grants a lower-privileged principal a secret whose possession exceeds their documented role, enabling further impersonation of the node to third-party bridge/adapter services.

### Likelihood Explanation
Highly likely and trivially reproducible: it only requires a valid `view` or `run` role API token or session — a credential level explicitly intended to be more restricted than `edit`/`admin`. No additional bypass, timing, or race condition is needed; a single authenticated `GET /v2/bridge_types` call from a run/view session/token returns the data. This is a static authorization-matrix omission, not a probabilistic exploit.

### Recommendation
Wrap `bt.Index` and `bt.Show` with `auth.RequiresEditRole` (or a dedicated `RequiresViewSecretsRole`) so that only accounts with at least the same privilege level as bridge creation/mutation can read `OutgoingToken`. Alternatively, keep `Index`/`Show` open to all authenticated roles but redact `OutgoingToken` from the presenter unless the caller has `edit`/`admin` role.

### Proof of Concept
Go handler-level integration test plan (extends existing `TestBridgeTypesController_Index` in `core/web/bridge_types_controller_test.go`):
1. Create an `app` via `cltest.NewApplication`, insert a bridge via `setupBridgeControllerIndex` and capture its `OutgoingToken`.
2. For each role in `{clsessions.UserRoleView, clsessions.UserRoleRun, clsessions.UserRoleEdit, clsessions.UserRoleAdmin}`, create a user/session with that role and call `client.Get("/v2/bridge_types")`.
3. Assert current behavior: all four roles receive `http.StatusOK` and the response body's `resources[0].OutgoingToken` equals the bridge's real outgoing token — demonstrating `view`/`run` roles obtain the secret.
4. After applying the fix (wrapping with `auth.RequiresEditRole`), assert `view`/`run` roles now get `http.StatusUnauthorized`, while `edit`/`admin` still get `http.StatusOK` with the token present (or redacted per chosen fix), proving the role matrix is enforced.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))

	paginatedResponse(c, "Bridges", size, page, resources, count, err)

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
