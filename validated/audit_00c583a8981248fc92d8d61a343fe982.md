### Title
`distribute_internal` can be permanently DoS'd by a single unresponsive shareholder, freezing commission and stake withdrawals for every other party - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::distribute` is a permissionless entry function (callable by anyone, per its own doc comment "Allow anyone to distribute already unlocked funds") that iterates over *every* shareholder in the `distribution_pool` and pushes funds to each one via `aptos_account::deposit_coins`. Because `deposit_coins` can abort for a single recipient, and Move transactions are atomic, one blocked recipient reverts the entire distribution for all other shareholders (staker, operator/beneficiary, and any other stakers who unlocked funds into the same pool).

### Finding Description
`distribute_internal` withdraws the total withdrawable stake from the pool and then loops over all shareholders of the `distribution_pool`, redeeming their shares and calling `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` will `assert!(can_receive_direct_coin_transfers(to), ...)` and abort if the target account already exists but is not yet registered for `AptosCoin` and has explicitly disabled direct coin transfers via `set_allow_direct_coin_transfers(false)`: [2](#0-1) 

`set_allow_direct_coin_transfers` is a fully permissionless, unprivileged call any account can invoke on itself: [3](#0-2) 

This is functionally identical to the Union `AssetManager.rebalance` bug: a single "market" (here, a single shareholder in the distribution pool) can cause the whole batch operation to fail, because the loop is all-or-nothing and there is no per-recipient fallback or skip logic. Since `distribute_internal` is atomic (a Move transaction either fully commits or fully reverts), the `redeem_shares` calls already executed for earlier shareholders in the loop are also rolled back, so the entire distribution — including the operator's commission and every other staker's unlocked stake — is permanently blocked as long as the blocking shareholder remains registered in the pool and unregistered for `AptosCoin` with direct transfers disabled.

The same shareholder loop pattern with the same `aptos_account::deposit_coins` call exists in `vesting::distribute`: [4](#0-3) 

There is no mechanism in `staking_contract.move` to remove/skip an unresponsive recipient from `distribution_pool` short of the shareholder itself re-enabling direct transfers or registering the coin store — actions the malicious/griefing party fully controls and has no incentive to do (they can leave commission/stake indefinitely locked for other stakers on the same operator/pool).

### Impact Explanation
This falls squarely in "Permanent lock or non-recoverable loss of claim rights in stake ... commission, beneficiary, or vesting flows" and "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value." A single delegator/beneficiary who becomes part of a shared `distribution_pool` (staking_contract or vesting) can, by simply calling `set_allow_direct_coin_transfers(false)` on their own account (and never registering for `AptosCoin`), indefinitely block:
- The operator's commission payout.
- Every other staker/shareholder's unlocked/withdrawn stake in that same staking contract or vesting contract, since they all share the same `distribution_pool` and the same atomic `distribute_internal`/`distribute` call.

This is high severity because it strands value belonging to unrelated, honest parties, with no recovery path in the given code paths.

### Likelihood Explanation
Likelihood is high: `set_allow_direct_coin_transfers` is a normal, unprivileged, unrestricted user action (intended for opting out of unsolicited token transfers), and any account that has never paid gas in APT (e.g., freshly created via `create_account` without funding, or an object/resource account added as a beneficiary) would not yet be registered for `AptosCoin`. No special privilege or race condition is needed — a single delegator/beneficiary can trigger this unintentionally or maliciously (griefing) at any time before a distribution is attempted.

### Recommendation
Do not let a single recipient's deposit failure abort the whole distribution loop. Options:
- Wrap each `aptos_account::deposit_coins` call so that a failing deposit routes the recipient's share into an escrow/claimable balance instead of aborting the whole transaction, allowing other shareholders' distributions to proceed.
- Alternatively, use `coin::deposit` directly to a pre-registered internal escrow keyed by recipient address that the recipient can withdraw from later, decoupling one recipient's registration status from the batch operation's success.
- At minimum, allow the staker/admin to permissionlessly skip or defer a distribution to any shareholder that fails deposit, and retry only that one out-of-band.

### Proof of Concept
1. Staker creates a staking contract with an operator (`staking_contract::create_staking_contract`) and unlocks stake at some point, adding themselves and possibly other stakers to `distribution_pool` via `add_distribution` (`aptos-move/framework/aptos-framework/sources/staking_contract.move` lines 937-957).
2. A delegator/beneficiary account `X` that has never registered for `AptosCoin` (e.g. an account created solely to receive a beneficiary designation, never having paid gas or received APT) calls `aptos_account::set_allow_direct_coin_transfers(false)` on itself — a fully permissionless call.
3. Once `X` is (or becomes) a shareholder of the `distribution_pool` (e.g., set as `beneficiary_for_operator`, or as a co-staker whose unlocked stake was added via `add_distribution`), any subsequent call to `staking_contract::distribute(staker, operator)` reaches `X` in the `while (distribution_pool.shareholders_count() > 0)` loop (`staking_contract.move` lines 889-911) and calls `aptos_account::deposit_coins(X, ...)`.
4. Because `X` exists, is not registered for `AptosCoin`, and disallows direct transfers, `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` (`aptos_account.move` lines 123-127).
5. The entire `distribute` transaction reverts — the operator's commission and every other shareholder's unlocked stake in the pool remain permanently unwithdrawable as long as `X` keeps direct transfers disabled and unregistered, with no code path in `staking_contract.move` to exclude `X` from the loop.

**Uncertainty**: I was not able to fully trace every caller-path by which an arbitrary attacker-controlled address becomes a `distribution_pool` shareholder beyond the staker/operator/beneficiary roles shown in the read code (e.g., whether the `staker` role itself could be attacker-controlled in a shared/pooled operator scenario); this would need runtime/test verification (e.g., building a Move unit test exercising `distribute` with a shareholder that has disabled direct transfers) to be conclusively confirmed as reproducible, which I could not execute in this read-only environment.

    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }

    /// Distribute any withdrawable stake from the stake pool.
    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

        // Send any remaining "dust" (leftover due to rounding error) to the withdrawal address.
        if (coin::value(&coins) > 0) {
            aptos_account::deposit_coins(vesting_contract.withdrawal_address, coins);
        } else {
            coin::destroy_zero(coins);
        };

        emit(
            Distribute {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
                amount: total_distribution_amount,
            },
        );
    }
