### Title
Closed-pool `requestWithdraw` mints unfunded receipts that `claimWithdrawRequest` pays from other users' funded reserve — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
When the pool is closed (`epochEndDate() == 0`), `IdleCreditVault.requestWithdraw` deliberately skips `pendingWithdraws += _amount` — a "stopped" flag check that decides whether the receipt must be borrower-funded — yet it still mints the user a strategy-token receipt, increments `withdrawsRequests[_user]`, and sets `lastWithdrawRequest[_user]`. Because `_claimFundedWithdrawRequest` treats `epochEndDate() == 0` as "claims are immediately allowed," the same user can claim the full receipt at par in the same transaction window, paid from underlyings the strategy holds to back other users' already-funded claims. The kcm analog holds exactly: a missing state check on the teardown path lets work (a payable receipt) be created against an object (the closed pending bucket) that is never funded.

### Finding Description
The bug is in `requestWithdraw` at `contracts/strategies/idle/IdleCreditVault.sol:259-294` and the claim gate at `contracts/strategies/idle/IdleCreditVault.sol:326`.

```solidity
// requestWithdraw
bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0;
...
_burn(msg.sender, _principal);
_mint(_user, _amount);              // full receipt minted
if (!isClosed) {
  pendingWithdraws += _amount;      // skipped when closed
}
lastWithdrawRequest[_user] = currentEpoch;
...
withdrawsRequests[_user] += _amount;
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

```solidity
// _claimFundedWithdrawRequest gate — passes instantly when closed
if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
  revert NotAllowed();
}
```

So once the pool closes (manager calls the close/`_interest == 1` path in `IdleCDOEpochVariant`), an unprivileged tranche-token holder can:

1. Call `cdoEpoch.requestWithdraw(trancheAmount, tranche)` — receipt minted, `withdrawsRequests` incremented, `pendingWithdraws` untouched.
2. Call `cdoEpoch.claimWithdrawRequest()` — gate passes because `epochEndDate() == 0`, `_burn` consumes the receipt, and `_transferFundedClaim` pays `amount` at par from strategy-held underlyings.

The only funded source for that payout is the strategy's underlying balance, which exists to satisfy other users' funded withdraw receipts and instant-withdraw claims collected via `collectWithdrawFunds`/`collectInstantWithdrawFunds`. The closed-pool receipt is never funded by the borrower, so each closed-pool claim is a direct 1:1 draw on someone else's reserve.

Guards that do not stop it: the `lossRecoveryPrice != 0` check at `IdleCreditVault.sol:263-271` only gates users with a prior loss-adjusted epoch; the `defaultRecoveryFinalized` branch is bypassed pre-default; `requestWithdraw` has no `isClosed` revert, and the claim gate explicitly whitelists the closed state. The "wait one epoch" protection is disabled precisely when `isClosed` is true.

### Impact Explanation
Direct theft of unclaimed, already-funded withdraw proceeds. Each wei requested post-close is paid from the funded reserve until the strategy's underlying balance is exhausted, after which legitimate funded claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on the ERC20 transfer — permanent freezing/theft of their funded payouts. Loss is bounded by the strategy's funded underlying balance and quantified exactly as the attacker's withdrawn amount.

### Likelihood Explanation
Requires the pool to reach closed mode (`epochEndDate == 0`), a reachable terminal state by design ("A successfully closed pool already recalled all funds"). After that, any KYC-passed tranche holder can execute the request+claim in a single buffer window with no privileged cooperation; first mover drains the shared reserve. Likelihood is moderate (conditional on pool close), impact is high.

Uncertain: I could not fully verify (a) whether `IdleCDOEpochVariant.requestWithdraw` adds an upstream revert when closed, and (b) the exact reserve-accounting inside `_transferFundedClaim` (grep located the function but the body was not retrieved before the iteration limit). The asymmetry shown above — receipt minted and claimable while the funding bucket is skipped — is confirmed in the cited lines.

### Recommendation
In `requestWithdraw`, either revert when `isClosed` (no new receipts after close), or keep the receipt out of the funded-claim path — e.g., record closed-pool requests in a separate map (`postDefaultRequests`-style) funded by a reserve accounted for at close time, so they cannot draw on other users' funded claims. Mirror the kernel fix's principle: replace the implicit `isClosed` skip with an explicit guard that prevents requeueing claims against a finalized funding bucket.

// setup: deposit userA + attacker, epochs advance normally

The assertion that `pendingWithdraws` is unchanged across the attacker's `requestWithdraw` while `withdrawsRequests[attacker]` increases, combined with the successful immediate claim, demonstrates the unfunded-payout invariant break.
