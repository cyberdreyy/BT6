### Title
APR0 withdraw requests can brick `stopEpoch` if APR is raised before epoch close, freezing all pool funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The InnoDB DoS class maps to the epoch state machine: an unprivileged lender can leave a pending APR0 withdraw request in `apr0TotalPrincipal`; if the (honest) manager updates the vault APR to a non-zero value before `stopEpoch` runs — a documented, legitimate operation via `setAprs`/`setAprsWithBuffer` — `prepareStopEpochWithApr0` reverts on every `stopEpoch` call, so the epoch cannot close and all lent funds plus pending withdraw receipts remain locked until the manager discovers that APR must be reset to 0.

### Finding Description
`prepareStopEpochWithApr0` hard-reverts whenever an open APR0 principal bucket exists while `unscaledApr != 0`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:499-508
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

A request created while `unscaledApr == 0` populates `apr0TotalPrincipal` via `_requestWithdrawApr0` (`IdleCreditVault.sol:285-286`, `567-577`). `setAprs`/`setAprsWithBuffer` let the manager change `unscaledApr` at any time (`IdleCreditVault.sol:206-220`), and there is no guard preventing an APR change while an APR0 bucket is open, nor a stopEpoch path that settles the bucket under a non-zero APR. In `stopEpoch` the new-epoch APR is applied through `_setScaledApr(_newApr)` only after accounting (`IdleCDOEpochVariant.sol:469-471`), but a routine mid-epoch manager APR update (e.g. repricing for the next epoch ahead of time) is enough to enter the poisoned state.

### Impact Explanation
Temporary freezing of all pool funds: while `apr0TotalPrincipal > 0` and `unscaledApr > 0`, every `stopEpoch` reverts. The epoch never ends, `epochNumber` never advances, so `_claimFundedWithdrawRequest` keeps reverting (`epochNumber <= lastWithdrawRequest`) and pending receipt holders, the borrower's repayment, and the AA/BB NAV accounting are all stalled. Recovery requires the manager to reset `unscaledApr` to 0 and re-run stop, after which the attacker's dust-sized request can be renewed, repeating the freeze each time APR is raised early. The attacker's cost is a minimal deposit plus one withdraw request; the frozen value is the entire pool TVL plus pending withdraw basis.

### Likelihood Explanation
Requires (a) a 0-APR epoch so the request lands in the APR0 bucket, and (b) the honest manager setting a non-zero APR before the epoch closes rather than passing it through `stopEpoch`. `setAprs` is explicitly exposed for direct manager use ("If manager manually set apr from here it will not be scaled"), so this sequencing is within normal operations, but it is an edge rather than the default path — hence medium-low likelihood. The revert has no in-contract fallback, so once triggered it deterministically blocks epoch finalization.

### Recommendation
In `prepareStopEpochWithApr0`, settle the open APR0 bucket at the realized rate instead of reverting when `unscaledApr != 0` (e.g. treat accrued interest as 0 for the closing bucket, or settle with the last stored `apr0RateByEpoch`), or alternatively block `setAprs`/`setAprsWithBuffer`/`setApr` from raising `unscaledApr` while `apr0TotalPrincipal != 0` so the poisoned state is unreachable.

### Proof of Concept
```solidity
// Foundry fork PoC (test/foundry/IdleCreditVault.t.sol harness style)
// Setup: pool running, unscaledApr == 0 for current epoch.
address attacker = makeAddr('attacker');
_depositWithUser(attacker, 1 * ONE_SCALE, true);          // dust AA deposit

// Attacker opens an APR0 withdraw request during the 0-APR epoch
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche));
assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

// Honest manager reprices the vault before stopEpoch (legitimate op)
vm.prank(manager);
IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, initialProvidedApr);

// stopEpoch now reverts forever while the APR0 bucket is open
vm.warp(cdoEpoch.epochEndDate() + 1);
deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
vm.prank(manager);
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
cdoEpoch.stopEpoch(initialProvidedApr, 0);

// All lender funds and pending withdraw receipts remain frozen;
// only resetting unscaledApr to 0 unblocks the epoch close.
```
