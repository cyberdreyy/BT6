### Title
Missing allowlist enforcement in legacy WebAPI trigger handler allows any signer to trigger DON-wide message dispatch - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(*handler).HandleLegacyUserMessage` validates payload structure, timestamp freshness, and method name, but performs no check that `msg.Body.Sender` is an allowlisted/subscribed identity before dispatching the message to every DON member via `don.SendToNode`. The `TODO: apply allowlist and rate-limiting here` comment at line 384 sits directly above the dispatch path with no enforcement logic anywhere in the function or its callers (`multiHandler.HandleLegacyUserMessage` simply forwards to this handler with no additional authz).

### Finding Description
The flow is: request payload is JSON-unmarshalled into `webapicap.TriggerRequestPayload` [1](#0-0) ; timestamp is checked for staleness [2](#0-1) ; then, right after the `TODO` comment, only the method name is checked before converting the message to a JSON-RPC request and sending it to **every** member of the DON [3](#0-2) . No call exists in this function, in `multiHandler.HandleLegacyUserMessage` [4](#0-3) , or in `common.ValidatedRequestFromMessage`/message validation helpers [5](#0-4)  that checks `msg.Body.Sender` against a per-workflow/topic allowlist or subscription registry. Message-level `Validate()` (referenced in `ValidatedMessageFromReq`) performs structural/signature validation but is not an authorization/allowlist check tied to workflow subscription. As a result, any holder of a fresh ECDSA keypair who can produce a well-formed, validly-signed `TriggerRequestPayload` with a current timestamp will have it fully dispatched to all DON nodes, regardless of whether that sender is subscribed/allowlisted for any topic.

### Impact Explanation
This matches the "unauthorized job run" / resource-exhaustion class of impact: an anonymous, unprivileged internet-reachable attacker can force DON-wide processing of arbitrary `web_api_trigger` payloads, consuming DON compute/network resources and potentially triggering downstream workflow executions that should be gated by subscription/allowlist. This is a capability/resource-consumption and authorization-bypass issue rather than fund theft or secret disclosure, but it directly negates the intended access control the TODO acknowledges is missing.

### Likelihood Explanation
Very high likelihood/feasibility: the only precondition is generating an ECDSA keypair (`crypto.GenerateKey()`), which requires no registration, subscription, or credentials. The attacker just signs a payload with a current timestamp and sends it through the standard legacy user-message gateway path — this is trivially repeatable and scriptable, and matches the exact reachable path from an unauthenticated gateway client into `HandleLegacyUserMessage`.

### Recommendation
Implement the allowlist/subscription check explicitly called out by the TODO before dispatching to `don.SendToNode`: after signature/timestamp validation, look up `msg.Body.Sender` (the recovered/verified signer) against the DON's configured allowlist or the specific workflow/topic subscription registry for the requested trigger, and reject with an authorization error (e.g., a new `api.UnauthorizedError` JSON-RPC error) if the sender is not registered. Additionally apply per-sender rate-limiting (the existing `nodeRateLimiter` construct used elsewhere in this file for node-side messages could be mirrored for user-side messages) to bound resource consumption from repeated unauthorized/authorized submissions alike.

### Proof of Concept
Go test plan (extends `handler_test.go`'s existing `TestHandlerReceiveHTTPMessageFromClient`-style tests):
1. Instantiate the `handler` via `NewHandler` with a `donConfig` containing a fixed set of DON members and a mocked `handlers.DON` whose `SendToNode` is asserted via `mock.On("SendToNode", ...)`.
2. Generate a fresh keypair with `crypto.GenerateKey()` that is **not** present in any allowlist/subscription structure known to the handler (note: as verified, no such structure is even referenced in `HandleLegacyUserMessage`, so any signer will pass).
3. Build a `webapicap.TriggerRequestPayload` with `Timestamp: uint32(time.Now().Unix())` and arbitrary trigger/topic fields, marshal it into `api.MessageBody.Payload`, set `Method: MethodWebAPITrigger`, sign the message body with the throwaway key, and populate `msg.Signature`.
4. Call `handler.HandleLegacyUserMessage(ctx, msg, mockCallback)`.
5. Assert `don.SendToNode` was called once per DON member (i.e., `len(donConfig.Members)` times) and that no error/`api.UnauthorizedError` response was sent back via `callback.SendResponse`.
6. This demonstrates that dispatch occurs unconditionally for any validly-signed, fresh-timestamp message regardless of sender identity, confirming the absence of allowlist enforcement described by the TODO.

// ValidatedRequestFromMessage converts a legacy Gateway Message to a JSON-RPC request
func ValidatedRequestFromMessage(msg *api.Message) (*jsonrpc.Request[json.RawMessage], error) {
	if msg == nil {
		return nil, errors.New("nil message")
	}
	if msg.Body.MessageId == "" {
		return nil, errors.New("message ID is empty")
	}
	if msg.Body.Method == "" {
		return nil, errors.New("method is empty")
	}
	params, err := json.Marshal(msg)
	if err != nil {
		return nil, fmt.Errorf("failed to marshal message: %w", err)
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageId,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	return req, nil
}
