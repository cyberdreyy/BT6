### Title
`claimInstantWithdrawRequest` never clears per-epoch instant receipt accounting, inflating default-recovery basis and enabling a double claim - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records three pieces of accounting per request: the aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][epoch]`, and the per-epoch total `instantWithdrawClaimsByEpoch[epoch]` (lines 366–374). The normal claim path `claimInstantWithdrawRequest` (lines 380–393) burns and clears only the aggregate, leaving the two per-epoch entries permanently stale — the same bug class as the referenced kernel leak (acquire a tracked resource, never release it). Those stale entries are later consumed by `defaultPendingClaimBasis` (lines 644–649), `_defaultPrefundedInstantReserve` (lines 716–723), and `_claimDefaultedInstantWithdrawRequest` (lines 842–856) during default finalization, so an already-paid instant receipt is counted a second time in the recovery waterfall.

### Finding Description
- `claimInstantWithdrawRequest` clears `instantWithdrawsRequests[_user]` but does not decrement `instantWithdrawsRequestsByEpoch[_user][*]` or `instantWithdrawClaimsByEpoch[*]` (lines 387–392). Contrast with `_claimDefaultedInstantWithdrawRequest`, which does clear both (lines 847–853) — proving the per-epoch entries are intended to track outstanding (not historical) claims.
- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` (lines 645–648). If an attacker claimed an instant receipt in the same `epochNumber` in which a new unfunded instant request exists at default time, the already-paid amount is counted again, inflating `totalBasis` in `finalizeDefaultRecovery` (lines 679–688).
- Worse, `_claimDefaultedInstantWithdrawRequest` pays out `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch] * defaultRecoveryPrice` (lines 844–855). Because the stale per-epoch entry was never cleared, the same user can claim the same instant receipt twice: once at par pre-default, once haircut from the recovery reserve.

Attack sequence (running epoch `E`, instant withdrawals enabled by honest manager):
1. Attacker deposits, requests instant withdraw `X` → `instantWithdrawsRequestsByEpoch[attacker][E] += X`, `instantWithdrawClaimsByEpoch[E] += X`.
2. After `instantWithdrawDelay`, manager calls `getInstantWithdrawFunds` → `collectInstantWithdrawFunds` funds `X`, `pendingInstantWithdraws` returns to 0.
3. Attacker calls `claimInstantWithdrawRequest`, receives `X` at par. `instantWithdrawClaimsByEpoch[E]` and `instantWithdrawsRequestsByEpoch[attacker][E]` still equal `X`.
4. Attacker (or another user) requests a second instant withdraw `Y` in the same epoch `E` → `pendingInstantWithdraws = Y`, `instantWithdrawClaimsByEpoch[E] = X + Y`.
5. Borrower fails to fund; honest `finalizeDefault`/`finalizeDefaultRecovery` runs. `defaultPendingClaimBasis` returns `pendingWithdraws + X + Y` — phantom `X` inflates both the basis and `_defaultPrefundedInstantReserve` (`instantBasis - pendingInstant = X`), so `defaultRecoveryReserve` is credited with `X` tokens that do not exist.
6. Attacker calls `claimInstantWithdrawRequest` again; `_claimDefaultedInstantWithdrawRequest` pays `(X + Y_basis) * recoveryPrice`, including a second payout on the already-claimed `X`.

### Impact Explanation
Double payout of the same instant-withdraw receipt: the attacker extracts `X * defaultRecoveryPrice` a second time, draining `defaultRecoveryReserve` ahead of honest defaulted-epoch claimants. Because the phantom `X` inflates `reserveAmount` in `finalizeDefaultRecovery` without real backing, the last claimants' `_transferDefaultRecovery` calls fail on insufficient balance — theft of recovery proceeds plus permanent freezing of the remaining honest claims. Broken invariants: one receipt one payout, and solvency of the default recovery reserve.

### Likelihood Explanation
Requires instant withdrawals enabled (normal manager configuration), two instant requests within the same `epochNumber` (the second can be dust-sized — the attacker only needs `pendingInstantWithdraws != 0` at default to activate `defaultInstantWithdrawsFinalized`), and a borrower default in that epoch. All attacker steps are unprivileged user calls; the default itself is an honest protocol event the attacker merely sequences around. One caveat I could not fully verify in the available index: whether the queue/CDO path can complete `collectInstantWithdrawFunds` and a second `requestInstantWithdraw` within a single `epochNumber` before epoch end — the instant-withdraw delay must fit inside the epoch, which the configurable `instantWithdrawDelay` allows.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting the same way `_claimDefaultedInstantWithdrawRequest` does: decrement `instantWithdrawsRequestsByEpoch[_user][<claimEpoch>]` and `instantWithdrawClaimsByEpoch[<claimEpoch>]` by the claimed amount. Since claims aggregate across epochs, iterate or track the user's request epoch (analogous to `lastWithdrawRequest`) so each funded receipt releases its per-epoch reservation exactly once — i.e., always `dput()` what `requestInstantWithdraw` "looked up."

### Proof of Concept
```solidity
// Foundry fork test sketch, modeled on testRequestWithdraw during running epoch
function testInstantReceiptDoubleCountedAfterClaim() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18); // epoch 1
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address attacker = makeAddr("attacker");
    uint256 tranchesAtk = _depositWithUser(attacker, 100e6);
    _depositWithUser(makeAddr("victim"), 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();           // epoch running, epochNumber = N

    // 1) attacker instant request X
    vm.prank(attacker);
    uint256 reqX = cdoEpoch.requestWithdraw(tranchesAtk, address(AAtranche)); // instant path via APR drop
    uint256 epochN = strategy.epochNumber();

    // 2) fund instant queue, pendingInstantWithdraws -> 0
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    deal(defaultUnderlying, borrower, reqX);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();

    // 3) attacker claims at par -- per-epoch entries stay stale
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequests(attacker), 0);
    assertEq(strategy.instantWithdrawClaimsByEpoch(epochN), reqX); // STALE

    // 4) dust instant request Y in same epoch N -> pendingInstantWithdraws != 0
    address dust = makeAddr("dust");
    uint256 tranchesDust = _depositWithUser(dust, 1e6);
    vm.prank(dust);
    cdoEpoch.requestWithdraw(tranchesDust, address(AAtranche));
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // 5) borrower defaults in epoch N; honest finalization
    //    (do not fund borrower; trigger default + finalizeDefaultRecovery)
    _triggerDefaultAndFinalize();

    // basis included phantom reqX -> reserve mispriced
    // 6) attacker claims defaulted instant receipt AGAIN
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 secondPayout = underlying.balanceOf(attacker) - balPre;
    assertGt(secondPayout, 0); // double claim on the same receipt
    // victim's subsequent claim reverts / is underpaid: reserve drained
}
```
