Confirmed. The vulnerability is a real accounting asymmetry in `stackerdb_listener.rs` that mirrors the WiseLending bad-debt bug class: an aggregate tally is incremented on one side without ever being reconciled/decremented when the same signer's per-slot state legitimately flips.

### Title
Node-side vote tally double-counts a signer's weight across `total_weight_approved` and `total_weight_rejected` when a signer legitimately flips from Reject to Accept — miscounted aggregate can wedge a valid block from ever being signed - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` maintains, per proposed block, a `BlockStatus` with two independently-accumulated weight counters: `total_weight_approved` and `total_weight_rejected` [1](#0-0) . The dedup guard used to decide whether to add a signer's weight differs between the two branches: the `Accepted` branch gates on `gathered_signatures.contains_key(&slot_id)` [2](#0-1) , while the `Rejected` branch gates on `responded_signers.insert(slot_id)` [3](#0-2) . Because the `Accepted` branch also unconditionally inserts into `responded_signers` [4](#0-3) , a signer who rejects first and later accepts the *same* block gets counted in `total_weight_rejected` (from the reject) **and again** in `total_weight_approved` (from the later accept) — with the reject contribution never removed. This is the exact "increment aggregate / never reconcile per-entity state change" pattern from the WiseLending `totalBadDebtETH` bug: a per-actor value legitimately changes (reject → accept, analogous to `badDebtPosition` being paid down), but the global aggregate that was bumped for the old state is never adjusted, permanently polluting the aggregate.

### Finding Description
The signer protocol explicitly permits a `LocallyRejected → LocallyAccepted` re-evaluation transition — it is a documented, legitimate state change (`docs/signer-flows.md`, "Block lifecycle" state diagram: `LocallyRejected --> LocallyAccepted : re-evaluated`), reachable any time a signer's earlier rejection reason no longer applies (e.g., `check_block_against_signer_db_state` now passes, or the pre-commit/signature threshold path re-validates and signs). When such a signer later broadcasts a `BlockResponse::Accepted` for the *same* block:

- The reject that was previously recorded already incremented `total_weight_rejected` by `signer_entry.weight` and set `responded_signers.insert(slot_id)` = true.
- On the later Accept, the code only checks `gathered_signatures.contains_key(&slot_id)`, which is false (this signer never accepted before), so it adds the same signer's weight to `total_weight_approved` as well.
- Nothing in the codebase ever subtracts this signer's weight back out of `total_weight_rejected`.

The result: `total_weight_approved + total_weight_rejected` can now exceed `total_weight` for a single signer's flip, and `total_weight_rejected` is permanently inflated with weight belonging to a signer who no longer rejects the block. This breaks the aggregated-weight ↔ verified-current-accepts equality that `signer_coordinator.rs` relies on to decide the fate of the block.

### Impact Explanation
`SignerCoordinator::wait_for_block_acceptance` polls this exact `BlockStatus` and checks the rejection condition **before** the acceptance condition on each iteration [5](#0-4) :
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected ...)
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(...) // enough signatures, accept block
}
```
Because the phantom rejected weight is never cleared out, it can push `total_weight_rejected` over the `>30%` blocking-minority line even though the signer whose weight is stuck there has *actually* moved to accept. This causes the coordinator to declare the block rejected (`SignersRejected`, including permanently/temporarily excluding transactions based on polluted `failed_txids` weight [6](#0-5) ) even in scenarios where legitimate signer support for the block has actually reached (or would reach) the 70% signing threshold. This is a liveness wedge on that block/tenure attempt — the miner is prevented from finalizing a block that legitimately has enough support, purely due to stale double-counted weight from a superseded verdict.

### Likelihood Explanation
No majority collusion, secret keys, or malicious behavior is required. This is triggered by a single signer performing a state transition the protocol explicitly supports and expects to happen in the normal course of chain-tip reconciliation (`should_reevaluate_block`/`should_reevaluate_reject_reason`, `mark_locally_rejected` → `mark_locally_accepted` re-evaluation flows described in `docs/signer-flows.md`). Any legitimate reject-then-accept flip by even one signer during a block's validation/signing window will corrupt the tally for that block.

### Recommendation
Track a single canonical per-slot verdict (e.g., an enum `Accepted(weight)`/`Rejected(weight)` keyed by `slot_id`) instead of two independently-accumulated counters guarded by different membership sets. On any transition, remove the previous contribution before adding the new one — analogous to the recommended WiseLending fix of computing `totalBadDebtETH` as a delta against the position's current recorded debt rather than blindly incrementing. Concretely, before adding weight in the `Accepted` branch, check whether `slot_id` is present in `responded_signers` due to an earlier rejection and, if so, subtract that signer's weight from `total_weight_rejected` first (and symmetrically for the `Rejected` branch relative to `gathered_signatures`).

### Proof of Concept
1. Node proposes block `B`; `StackerDBListener` creates `BlockStatus{total_weight_approved:0, total_weight_rejected:0, responded_signers:{}, gathered_signatures:{}}` for `B`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `B` (e.g., transient chainstate check failure). Handler: `responded_signers.insert(slot_S)` → true → `total_weight_rejected += w`.
3. `S` re-evaluates (per the documented `LocallyRejected → LocallyAccepted` transition) and now signs/accepts `B`, sending `BlockResponse::Accepted`.
4. Handler checks `gathered_signatures.contains_key(&slot_S)` → false → `total_weight_approved += w`; then unconditionally does `gathered_signatures.insert(slot_S, sig)` and `responded_signers.insert(slot_S)` (already true, no-op).
5. Now `BlockStatus{total_weight_approved: w, total_weight_rejected: w, ...}` — `S`'s weight is counted on both sides simultaneously, and `total_weight_rejected` can never be reduced back down for `S`.
6. If enough other signers are near the rejection/acceptance boundary, this phantom `w` in `total_weight_rejected` can push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` to true in `signer_coordinator.rs`, causing `SignersRejected` to be returned even though the *actual* current verdicts (recomputed from `gathered_signatures` alone) would show the block has legitimate accepting weight and no signer currently opposes it.
