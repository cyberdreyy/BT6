### Title
Unfunded instant-withdraw receipts persist across epochs and are paid at par from the next epoch's funded claims — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays a user's aggregate `instantWithdrawsRequests[_user]` balance at par, without checking which epoch each receipt belongs to or whether that epoch was actually funded. Receipt accounting is tracked per-epoch in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, but the claim path ignores the per-epoch split. A user whose instant request went unfunded in epoch N can wait for epoch N+1 funding (collected for *other* users' requests) and drain it — the same underlying is effectively counted against two different epochs' claim bases with no deduplication between funded and unfunded receipts.

### Finding Description
At `startEpoch`, the CDO calls `collectInstantWithdrawFunds(min(pendingInstant, totUnderlyings))` (`IdleCDOEpochVariant.sol:279-282`). If the CDO holds less underlying than `pendingInstantWithdraws`, the strategy receives only a partial transfer and `pendingInstantWithdraws -= _amount` retains the unfunded remainder (`IdleCreditVault.sol:398-403`).

Later, `claimInstantWithdrawRequest` does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

(`IdleCreditVault.sol:387-392`)

There is no check that the receipt's request epoch was funded. The per-epoch structures (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) are only consulted on the default-recovery path (`_claimDefaultedInstantWithdrawRequest`), which requires `defaultRecoveryFinalized`. Outside of a finalized default, all historical receipts are fungible against whatever underlying the strategy currently holds — including funds collected at a later `startEpoch` that were earmarked for that epoch's instant queue.

Sequence:
1. Epoch N (running): attacker calls `requestInstantWithdraw(A)` via the CDO; `instantWithdrawsRequests[attacker] += A`, `instantWithdrawsRequestsByEpoch[attacker][N] += A`.
2. `startEpoch` for the next cycle: `pendingInstant > totUnderlyings`, so all CDO cash is sent but the attacker's receipt remains partially/fully unfunded (this also occurs when the early-return branch at `IdleCDOEpochVariant.sol:286-290` is taken).
3. Epoch N+1 buffer/running: honest users file new instant requests; the next `startEpoch` collects `pendingInstant` worth of underlying into the strategy.
4. Attacker calls `claimInstantWithdrawRequest` → receives the full `A` at par from funds reserved for epoch N+1 claimants. Later N+1 claimants' `_transferFundedClaim` transfers fail or are shorted.

### Impact Explanation
Direct theft of funded instant-withdraw liquidity: an unprivileged tranche holder converts an unfunded receipt into a par claim on other users' money. Loss equals the attacker's unfunded receipt amount, capped by the next epoch's collected instant funds. No privileged misbehavior, default, or oracle input is required — only the normal condition where instant demand exceeds available CDO cash.

### Likelihood Explanation
Requires an epoch boundary where `pendingInstantWithdraws` exceeds the CDO's token balance, which happens organically under liquidity stress (exactly when instant withdrawals matter most). The attacker only needs one instant request before the shortfall and one claim after the next funding event. The `_onlyIdleCDO` gating is satisfied because claims route through the CDO's user-facing redeem path.

### Recommendation
Track funded vs unfunded instant receipts per epoch. Concretely: on `collectInstantWithdrawFunds`, record a per-epoch funded ratio (analogous to `lossRecoveryPriceByEpoch`); in `claimInstantWithdrawRequest`, iterate the user's `instantWithdrawsRequestsByEpoch` entries and pay each epoch at min(1, fundedRatio) rather than paying the aggregate at par. Alternatively, revert/cancel unfunded instant receipts at `startEpoch` instead of carrying them forward as silently fungible claims.
