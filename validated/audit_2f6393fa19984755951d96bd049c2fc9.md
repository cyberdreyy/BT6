### Title
Unfunded instant-withdraw receipts are paid from other users' funded claims in `IdleCreditVault.claimInstantWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` conflates two different "types" of instant-withdraw receipts — funded ones (for which `IdleCDOEpochVariant` already pulled underlying via `collectInstantWithdrawFunds`) and freshly requested, still-unfunded ones that are only tracked in `pendingInstantWithdraws`. The claim path pays out the aggregate `instantWithdrawsRequests[_user]` at par with no check that the request epoch was ever funded, which is the same class of bug as the reported type confusion in `SIccCalcOp::ArgsPushed()`: an aggregate value is interpreted as a different semantic type (funded claim vs pending request) without validation.

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens, mints a receipt to the user, and immediately increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws` [1](#0-0) . Underlying for these requests only arrives later, when the CDO calls `collectInstantWithdrawFunds`, which decreases `pendingInstantWithdraws` and pulls tokens from the CDO [2](#0-1) .

`claimInstantWithdrawRequest`, however, pays `instantWithdrawsRequests[_user]` in full without consulting `pendingInstantWithdraws`, `instantWithdrawsRequestsByEpoch`, or `instantWithdrawClaimsByEpoch` — the per-epoch fields exist and are only used on the default path via `_claimDefaultedInstantWithdrawRequest` [3](#0-2) [4](#0-3) . The payout goes through `_transferFundedClaim`, whose only guard protects `defaultRecoveryReserve`, not funded-but-unclaimed balances of other users [5](#0-4) .

So an attacker who holds an unfunded instant receipt can claim it in the same epoch it was requested, paid out of underlying that the strategy is holding for earlier funded claimants (normal withdraw claims funded by `collectWithdrawFunds` or earlier instant claims). The attacker's receipt was never funded — the borrower still owes it via `pendingInstantWithdraws` — so the payout is effectively taken from someone else's reserve.

### Impact Explanation
Direct theft / temporary freezing of other users' funded withdraw claims. Each attack moves up to the full `instantWithdrawsRequests[attacker]` amount out of the strategy's non-reserve balance; the legitimate claimants whose funding was drained revert on `_transferFundedClaim` (insufficient balance) until the borrower funds the pending queue at the next `collectInstantWithdrawFunds` — and if that funding never materializes (e.g., pool closed or defaulted), the loss becomes permanent for the earlier claimant. Loss is bounded by the strategy's unclaimed funded balance, which can equal the whole pending-claims bucket.

### Likelihood Explanation
Requires only a KYC-passed lender holding tranche tokens in a pool with instant withdrawals enabled. The attacker performs `requestInstantWithdraw` followed by `claimInstantWithdrawRequest` (via the CDO) in a window where the strategy holds funded claim liquidity — i.e., after a `stopEpoch`/`startEpoch` collected funds for prior claimants. The attack is only blocked if `IdleCDOEpochVariant.claimInstantWithdrawRequest` enforces epoch/funding gating before calling the strategy; the strategy itself exposes no such check, and the presence of `instantWithdrawsRequestsByEpoch` used solely for defaults shows the funded/unfunded distinction was recognized but not enforced on the normal claim path. I was unable to fully verify the CDO-side gating within the available iterations, so if the CDO already forbids claiming before funding, this degrades to defense-in-depth rather than an exploitable bug.

### Recommendation
In `claimInstantWithdrawRequest`, deduct only funded receipts: track the funded vs pending split per user (e.g., subtract `instantWithdrawsRequestsByEpoch[_user][epochNumber]` while that epoch's share of `pendingInstantWithdraws` is still unfunded), or gate claims on the request epoch being fully collected. Mirror the per-epoch clearing used by `_claimDefaultedInstantWithdrawRequest` so a current-epoch unfunded receipt can never be paid at par.

### Proof of Concept
Foundry fork PoC sketch against an `IdleCDOEpochVariant` + `IdleCreditVault` deployment with instant withdrawals enabled:

```solidity
// Epoch N: user1 (honest) requests instant withdraw; startEpoch collects funds.
// Strategy now holds `amount1` underlying reserved for user1's claim.
// Same epoch (buffer/running), attacker requests instant withdraw:
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(amountAtk, address(tranche));
// instantWithdrawsRequests[attacker] == amountAtk, pendingInstantWithdraws += amountAtk,
// but no underlying was collected for it yet.

// Attacker claims immediately — no funded/pending check in the strategy:
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// attacker received amountAtk underlying taken from user1's funded claim.

// user1's legitimate claim now reverts or is unpaid:
vm.prank(user1);
vm.expectRevert(); // _transferFundedClaim: balance - reserve < amount
cdoEpoch.claimInstantWithdrawRequest();
```

Expected assertion: `underlying.balanceOf(attacker)` increases by `amountAtk` while `strategy.balance` was only sufficient for user1's funded claim; `pendingInstantWithdraws` still counts the attacker's receipt as borrower-owed.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
