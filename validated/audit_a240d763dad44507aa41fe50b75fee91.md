### Title
Cross-epoch receipt pollution: a new unfunded instant-withdraw request inflates the aggregate `instantWithdrawsRequests` receipt and lets a user claim other users' funded withdraw money — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`merge-recursive` prototype pollution lets attacker-controlled keys corrupt a shared aggregate. The in-scope analog is `IdleCreditVault.requestInstantWithdraw`: every new request is merged into the single per-user aggregate `instantWithdrawsRequests[_user]`, while funding is tracked separately via `pendingInstantWithdraws` and per-epoch maps. `claimInstantWithdrawRequest` pays the whole aggregate in one shot with no per-epoch isolation and no check that the latest request was actually funded, so an unfunded "polluting" request drains underlying that was collected for other users' funded claims.

### Finding Description
- `requestInstantWithdraw` (IdleCreditVault.sol:356-375) burns the CDO-held principal, mints the user a receipt, and does `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount`, `instantWithdrawClaimsByEpoch[epochNumber] += _amount`, `pendingInstantWithdraws += _amount`. There is no guard requiring prior receipts to be claimed first (unlike `requestWithdraw`, which reverts if an unclaimed loss-adjusted receipt exists, lines 263-271), and no guard that the vault actually holds liquidity for the new request.
- `claimInstantWithdrawRequest` (lines 380-393) reads `amount = instantWithdrawsRequests[_user]` — the polluted aggregate across all epochs — burns it and calls `_transferFundedClaim(_user, amount)`, which transfers underlying from the strategy balance, only skipping the `defaultRecoveryReserve` portion (lines 897-900).
- Funding is strictly per-amount, not per-request: `collectInstantWithdrawFunds(_amount)` (lines 398-403) only decrements `pendingInstantWithdraws` and pulls whatever the CDO sends. `_defaultPrefundedInstantReserve` (lines 716-723) explicitly treats `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as the funded share, confirming that the contract itself models instant claims as only partially funded.
- Therefore: user request I₁ is funded (CDO calls `collectInstantWithdrawFunds`, `pendingInstantWithdraws` reduced, strategy now holds I₁). Before claiming, the same user submits I₂ in a later epoch/buffer where no instant liquidity is collected (e.g., APR-drop instant path during a running epoch, or a request larger than available cash). `instantWithdrawsRequests[user] = I₁ + I₂`. `claimInstantWithdrawRequest` pays `I₁ + I₂` but only `I₁` was funded — the excess is taken from underlying reserved for other users' funded normal/instant withdraw claims held in the strategy.

### Impact Explanation
Direct theft of other users' funded withdraw proceeds. The strategy's underlying balance is a shared pool backing all `withdrawsRequests`/instant claims that the borrower already funded through `collectWithdrawFunds`/`collectInstantWithdrawFunds`. Paying an unfunded receipt from that pool permanently steals the delta from legitimate claimants (their later `_transferFundedClaim` reverts on insufficient balance → their funded claims freeze). Loss is bounded only by the unfunded amount the attacker can register, i.e., up to their deposited principal.

### Likelihood Explanation
Requires only a KYC-passed lender (unprivileged per scope). Steps: deposit AA, request an instant withdraw that gets funded during a buffer, then — before claiming — submit a second `requestInstantWithdraw` in a phase where the strategy holds no spare instant liquidity (running epoch after the funded cash was redeployed/`sendInterestAndDeposits` forwarded, or amount exceeding on-hand cash). No privileged cooperation needed beyond the honest scheduled `startEpoch`/`stopEpoch`/`collectInstantWithdrawFunds` calls. The missing same-user "claim-before-new-request" guard that exists for `requestWithdraw` is absent here, and nothing in `requestInstantWithdraw` verifies incremental funding.

### Recommendation
Mirror the normal-withdraw fix: either (a) revert in `requestInstantWithdraw` when `instantWithdrawsRequests[_user] != 0` until claimed, or (b) make `claimInstantWithdrawRequest` pay per funded epoch only — e.g., cap the payout at `instantWithdrawsRequests[_user] - pendingInstantShare` using per-epoch data, or track a per-user `fundedInstantAmount` incremented in `collectInstantWithdrawFunds` pro-rata. Also gate `claimInstantWithdrawRequest` so unfunded receipts (`pendingInstantWithdraws` share) cannot be burned and paid.

### Proof of Concept
```solidity
// Foundry fork test against deployed IdleCDOEpochVariant + IdleCreditVault
function testInstantWithdrawAggregatePollution() external {
    // setup: attacker is KYC'd lender; pool in buffer with instant-withdraw mode active
    uint256 I1 = 10_000e6;
    cdo.requestWithdraw(attackerBal, address(AAtranche)); // -> requestInstantWithdraw(I1)
    // honest manager collects funds for I1 (stopEpoch/startEpoch collects via collectInstantWithdrawFunds)
    vm.prank(manager); cdo.stopEpoch(0, 0); // strategy receives I1 underlying, pendingInstantWithdraws -> 0

    // pollution: attacker submits second instant request while strategy has no spare cash
    uint256 I2 = 10_000e6;
    cdo.requestInstantWithdraw(I2, address(AAtranche)); // aggregate = I1+I2, pendingInstantWithdraws = I2 (unfunded)

    // claim pays aggregate from shared strategy balance
    uint256 before = underlying.balanceOf(attacker);
    cdo.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - before, I1 + I2); // I2 stolen from other users' funded claims
}
```
