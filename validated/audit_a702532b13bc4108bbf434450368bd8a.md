### Title
View-role users can harvest all bridge `OutgoingToken` credentials via unredacted `BridgeResource` on `GET /v2/bridge_types` - ([File: core/web/bridge_types_controller.go] / [File: core/web/presenters/bridges.go])

### Summary
`BridgeTypesController.Index` and `.Show` build responses via `presenters.NewBridgeResource`, which always serializes the bridge's `OutgoingToken` field with no role-based redaction. Since `Index` supports pagination (`size`/`page`/`offset`), any caller authorized to hit these read routes can enumerate every page and reconstruct the full bridge catalog, including every bridge's `OutgoingToken`.

### Finding Description
`BridgeTypesController.Index` fetches bridges from `btc.App.BridgeORM().BridgeTypes(ctx, offset, size)` and converts each to a `presenters.BridgeResource` via `presenters.NewBridgeResource(bridge)` before passing them to `paginatedResponse` [1](#0-0) . `Show` performs the equivalent single-record lookup and returns the same resource type [2](#0-1) .

`presenters.NewBridgeResource` copies `b.OutgoingToken` into the response's `OutgoingToken` field unconditionally, with no `omitempty` and no gating on the caller's role — unlike `IncomingToken`, which the code comment explicitly says is "only provided when creating a Bridge" and which callers are expected to treat as sensitive [3](#0-2) . `OutgoingToken` is the credential the node itself presents to the external adapter when calling out to the bridge's URL, so its disclosure lets a holder impersonate the node to that adapter or otherwise abuse the bridge's outbound trust relationship.

Because `Index` is paginated (`size`, `page`, `offset` parameters flow to `paginatedResponse`), a caller only needs read access to the route to walk every page and collect the `OutgoingToken` for every bridge configured on the node — this scales the exposure from "a few visible bridges" to "the complete bridge secret set" with a handful of sequential requests.

I was not able to fully verify the exact role requirement (`View` vs `Edit`/`Admin`) enforced by the router middleware for `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` in `core/web/router.go` within the available tool budget — the file contains role/auth wiring but I could not confirm from what I retrieved whether the `View` role specifically is permitted on these GET routes. This is the load-bearing precondition for the "unprivileged attacker" framing in the question: if these routes require `Edit`/`Admin` role, then the exposure is scoped to already-privileged bridge managers and is not a privilege boundary violation; if `View` role is sufficient (as the question's precondition assumes and as is architecturally typical for read endpoints in this codebase, since `View` is the designated read-only monitoring role), the finding is a genuine authorization/redaction bug — the presenter fails to distinguish "read access to bridge metadata" from "read access to bridge secrets."

### Impact Explanation
If `View` role (or any role below `Edit`/`Admin`) can call `Index`/`Show`, this is credential disclosure: it discloses `OutgoingToken` secrets for every bridge on the node to a role that the UI/product model intends only to browse, not to obtain outbound-authentication secrets. An attacker holding these tokens can impersonate the node when calling the corresponding external adapter/bridge endpoints, or use the token to access whatever the adapter gates behind it. This matches Chainlink's "key/secret disclosure" bounty impact class, scoped to the bridge subsystem rather than the OCR/consensus core.

### Likelihood Explanation
Preconditions: an authenticated node API token/session with at minimum the role authorized for `GET /v2/bridge_types` (the question presumes `View` role suffices). If so, the attack requires only a handful of authenticated GET requests varying `page`/`size`, no timing races, and no special node state — fully repeatable. The severity of the finding is entirely contingent on the unconfirmed role gate; without confirming `View` role is accepted on these routes, this cannot be treated as a confirmed privilege-boundary violation.

### Recommendation
- Redact `OutgoingToken` (and any other bridge secret) from `BridgeResource` for reads, mirroring the existing `IncomingToken` treatment ("only provided when creating"), or only include it for callers with `Edit`/`Admin` role.
- Explicitly verify and, if necessary, tighten `core/web/router.go` so `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` require `Edit`/`Admin` role rather than `View`, since bridge tokens are operational secrets, not read-only metadata.
- Add a presenter-level test asserting `OutgoingToken` is empty/omitted in list/show responses regardless of caller role.

### Proof of Concept
Go handler-level integration test plan (`core/web/bridge_types_controller_test.go`):
1. Seed N bridges (e.g., 15) via `BridgeORM().CreateBridgeType`, each with a distinct known `OutgoingToken`.
2. Create an API session/token with the minimal role that the router actually allows on `GET /v2/bridge_types` (confirm this role first by inspecting `core/web/router.go`'s route group for `bridge_types`).
3. Issue sequential `GET /v2/bridge_types?size=5&page=1..3` requests as that role.
4. Assert: (a) all N bridges are returned across pages via `paginatedResponse`'s `meta.count`; (b) every returned `BridgeResource.OutgoingToken` matches the seeded value (i.e., not redacted); (c) if the confirmed minimal role is `View`, assert this constitutes a role boundary violation relative to `Edit`-gated mutation endpoints (`Create`/`Update`/`Destroy` on the same controller).
5. Fail the test if `OutgoingToken` is empty/redacted for the tested role, or if the role is confirmed to require `Edit`/`Admin` (in which case the finding should be downgraded/rejected).

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
