### Title
Timing side-channel in `localLoginFallback` allows local-admin email enumeration - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` unconditionally invokes `localLoginFallback` whenever the LDAP `Bind` or `FindUser` step returns any error, which includes ordinary failed LDAP logins (wrong password, non-existent upstream user) as well as LDAP search/timeout errors. Inside `localLoginFallback`, the "email not found" branch returns immediately after a DB lookup miss, while the "wrong password" branch additionally executes `utils.CheckPasswordHash` (bcrypt), producing an observable response-time difference that lets an unauthenticated caller infer whether a given email exists in the local `users` table.

### Finding Description
In `core/sessions/ldapauth/ldap.go`, `CreateSession` (lines 396-433) always sets `returnErr` on any `conn.Bind` or `FindUser` failure and then calls `l.localLoginFallback(ctx, sr)` [1](#0-0) . Note this fallback path is reached for *any* failed LDAP login (e.g., an email simply not present upstream, or a wrong LDAP password), not only for a "genuinely local" account — so an attacker does not need to craft anything special to reach it; a normal failed login already routes here.

`localLoginFallback` performs:
```go
err := l.ds.GetContext(ctx, &user, sql, sr.Email)
if err != nil {
    return user, err                       // fast path: no such local user
}
if !constantTimeEmailCompare(...) { ... }  // effectively unreachable given the WHERE lower(email)=lower($1) query
if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) { ... } // slow bcrypt path
``` [2](#0-1) 

Since the SQL query already filters by `lower(email) = lower($1)`, a matching row is only returned when the email exists, making `constantTimeEmailCompare` here largely redundant/dead code for its stated timing-safety purpose — the actual branching that leaks information is the DB "no rows" fast return versus the bcrypt `CheckPasswordHash` call, which is deliberately expensive. This produces a measurable timing difference between "email unknown" and "email known, wrong password," letting an attacker enumerate valid local admin emails without any credentials.

### Impact Explanation
The scoped impact is limited to **account/email enumeration** of local admin users — it does not itself bypass authentication or expose secrets, since `CheckPasswordHash` still uses bcrypt with fixed-cost hashing, giving no further leak about password correctness beyond right/wrong. This maps to a low-severity information-disclosure/enumeration class rather than authentication bypass, credential disclosure, or unauthorized fund movement.

### Likelihood Explanation
No authentication or special network access is required — any client can POST to `/sessions` with arbitrary emails and observe response latency. However, exploitation is affected by real-world network jitter, and reaching `localLoginFallback` doesn't require "forcing" an LDAP search error via oversized/malformed input as hypothesized in the question — it is trivially reached by any normal failed LDAP login (nonexistent upstream user or wrong password), which is expected day-to-day behavior, not a bypass of any control.

### Recommendation
Ensure constant-time behavior regardless of whether the email exists: always perform a dummy bcrypt comparison (against a fixed/precomputed hash) when no user row is found, so both branches take comparable time before returning "invalid email"/"invalid password" (ideally a single generic "invalid credentials" error to avoid distinguishing the two failure reasons altogether).

### Proof of Concept
Go table test plan for `localLoginFallback`:
1. Seed a `users` table with one known email/hashed password.
2. Case A: call `localLoginFallback` with an email not in the table; measure elapsed time.
3. Case B: call `localLoginFallback` with the known email and a wrong password; measure elapsed time.
4. Assert Case B takes measurably longer (bcrypt cost) than Case A across repeated trials, demonstrating the oracle; then apply the fix (dummy hash comparison for unknown emails) and assert timings converge within a small tolerance.

Note: this issue is limited to enumeration and does not meet the stricter "authentication bypass / credential disclosure / unauthorized action" bar defined in the audit rules; it is reported here as the closest supported finding to the question's premise, but the described "attacker forces LDAP error via crafted email" precondition is not actually required, as documented above.

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
