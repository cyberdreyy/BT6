### Title
`simulateTransaction` panics the RPC service when serving requests against an unfrozen ("processed") bank - ([File: rpc/src/rpc.rs])

### Summary
The `simulate_transaction` handler in `rpc/src/rpc.rs` fetches a bank via `meta.get_bank_with_config(...)` using the caller-supplied `commitment` and then unconditionally calls `bank.simulate_transaction(&transaction, enable_cpi_recording)`. `Bank::simulate_transaction` in `runtime/src/bank.rs` asserts the bank is frozen ("simulation bank must be frozen") before proceeding, and this is enforced with an `assert!`/`expect`-style panic rather than a recoverable `Result`. Since a client can request `commitment: "processed"`, which routes to the actively-building (unfrozen) working bank, a single crafted `simulateTransaction` request can trigger this panic.

### Finding Description
`simulate_transaction` in `rpc/src/rpc.rs` (around lines 4010-4072) resolves the bank with: [1](#0-0) 
which calls `JsonRpcRequestProcessor::get_bank_with_config`, which in turn calls `self.bank(commitment)`: [2](#0-1) 

The `bank()` helper resolves `CommitmentLevel::Processed` to the "heaviest slot" from `block_commitment_cache`, which can be the currently-active/unrooted working bank rather than a rooted/frozen bank: [3](#0-2) 

`simulate_transaction` then unconditionally calls `bank.simulate_transaction(...)`: [4](#0-3) 

The existing repo test suite confirms this exact panic path is real and reachable purely through the public RPC interface — `test_rpc_simulate_transaction_panic_on_unfrozen_bank` deliberately keeps the bank unfrozen, submits a `simulateTransaction` JSON-RPC request, and asserts a panic with message "simulation bank must be frozen": [5](#0-4) 

Unlike `send_transaction`'s preflight path, which explicitly comments "Freeze bank 0 to prevent a panic in `run_transaction_simulation()`" and freezes the bank before use in its own test setup: [6](#0-5) 
the `simulate_transaction` RPC method itself performs no such freeze check or guard before calling into `bank.simulate_transaction`. There is no `Result`-returning check for "is the bank frozen" in `simulate_transaction`; the panic is the only enforcement mechanism, and it happens inside the shared RPC handler thread, which — depending on how request handling is scheduled — can propagate up and crash/degrade the RPC service since no single request is supposed to be able to panic the shared service.

### Impact Explanation
A successful trigger causes a panic inside the RPC request-handling call stack from a single unprivileged JSON-RPC request (`simulateTransaction` with `commitment: "processed"`, no funds or signed transaction required beyond a well-formed transaction blob). This matches the "RPC DoS/Crash" category: an attacker-controlled single request panics code invoked directly by the RPC service, violating the invariant that no single request should be able to crash the shared RPC service.

### Likelihood Explanation
- Preconditions: an unprivileged client only needs network access to the node's JSON-RPC endpoint (no special config, no privileged actor).
- Attacker capability: crafting a JSON-RPC `simulateTransaction` request with `params: [<any validly-encoded transaction>, {"commitment": "processed"}]`. No signature validity or funds are required if `sigVerify` defaults/`skip`s appropriately (the test that reproduces this in the repo uses `sigVerify: true` with a normally signed transfer transaction and an explicitly-unfrozen bank).
- Feasibility/repeatability: the repository's own unit test (`test_rpc_simulate_transaction_panic_on_unfrozen_bank`) demonstrates the panic deterministically via the public JSON-RPC entrypoint (`io.handle_request_sync`), i.e., exactly the client-facing dispatch path, not an internal-only API. The main open uncertainty is the precise timing window in a live validator during which the "processed"/heaviest-slot bank returned by `bank()` is guaranteed unfrozen versus already frozen by the time an RPC thread observes it; this depends on scheduling/timing between bank creation, work in the current slot, and RPC read paths, which I could not fully verify from the indexed code alone (the `runtime/src/bank.rs` assert body and full freezing lifecycle were not retrievable in this session due to index limits).

### Recommendation
In `simulate_transaction` (and any other method reaching `Bank::simulate_transaction`), explicitly check `bank.is_frozen()` before calling `simulate_transaction`, and return a proper JSON-RPC error (e.g., `RpcCustomError`) instead of relying on the internal `assert!`/panic inside `Bank::simulate_transaction`. Alternatively, change `get_bank_with_config`/`bank()` to never return an unfrozen working bank for simulation-oriented RPC methods, or make `Bank::simulate_transaction` itself return a `Result` rather than panicking on an unfrozen bank.

### Proof of Concept
The existing repo test is a direct, minimal PoC of the reachable panic via the JSON-RPC surface: [5](#0-4) 

This test issues:
```json
{"jsonrpc":"2.0","id":1,"method":"simulateTransaction","params":["<serialized-tx>", {"sigVerify": true}]}
```
via `io.handle_request_sync(&req, meta)` against an unfrozen working bank, and asserts a panic with message "simulation bank must be frozen" — demonstrating that the exact RPC-facing code path can panic the request-handling thread from a single crafted request. A production fast-validation test should additionally send `commitment: "processed"` explicitly and confirm whether the "heaviest slot" bank returned during active slot production is unfrozen at the moment the request is served, and assert that no panic occurs (i.e., the fix returns a graceful RPC error instead).

impl JsonRpcRequestProcessor {
    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }

    #[allow(deprecated)]
    fn bank(&self, commitment: Option<CommitmentConfig>) -> Arc<Bank> {
        debug!("RPC commitment_config: {commitment:?}");

        let commitment = commitment.unwrap_or_default();
        if commitment.is_confirmed() {
            let bank = self
                .optimistically_confirmed_bank
                .read()
                .unwrap()
                .bank
                .clone();
            debug!("RPC using optimistically confirmed slot: {:?}", bank.slot());
            return bank;
        }

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
