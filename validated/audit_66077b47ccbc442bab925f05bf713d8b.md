### Title
Deleted multisig member's stale confirmation still counted toward quorum, allowing requests to execute below the effective live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
The `delete_member` helper in `multisig2/src/lib.rs` only purges pending requests *authored* by the removed member, but never scrubs that member's existing `confirmations` entries on requests authored by *other* members. Because `confirm()` counts confirmations purely by set size against `self.num_confirmations` without re-validating that each confirming identity is still a current member, a request can reach quorum and execute using a confirmation cast by an account/key that has since been removed from the multisig. This mirrors the report's bug class: an action is authorized based on a "trusted identity/state" (a live member) recorded at confirmation time, but that trust binding is not re-checked at execution time, and it can change (member deleted) between the confirmation and the moment quorum is reached and the request executes.

### Finding Description
`confirm()` adds the caller to the request's confirmation `HashSet<String>` and, once `confirmations.len() + 1 >= self.num_confirmations`, immediately executes the request: [1](#0-0) 

`delete_member()` is the only place that mutates state when a member is removed. It removes the member from `self.members`, deletes the member's own `num_requests_pk` entry, and deletes any *requests the member itself authored* (along with those requests' confirmations) — but it does not iterate over all other outstanding requests to strip the deleted member's confirmation from their `confirmations` sets: [2](#0-1) 

`assert_valid_request()`, used by both `confirm` and `delete_request`, only checks that the *current caller* is a member and that the request/confirmations exist — it never re-validates the identities already present in a request's `confirmations` set: [3](#0-2) 

The binding that should hold is:
`num_confirmations from live members who confirmed == self.num_confirmations` (threshold met only by currently authorized members).

Instead, the actual state after a member deletion is:
`confirmations.len() (including stale, now-removed members) >= self.num_confirmations`, even though the count of *live* members who confirmed can be strictly less than `self.num_confirmations`.

### Impact Explanation
This breaks the multisig's core authorization guarantee: a `MultiSigRequest` (which can be a `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc.) can be executed with fewer live, currently-authorized confirmations than `num_confirmations` requires. This is squarely a "multisig request executed below threshold" condition, which can result in unauthorized transfers of NEAR held by the multisig account, unauthorized key additions, or unauthorized contract deployment/upgrade — all Critical-impact outcomes for this contract.

### Likelihood Explanation
Likelihood is Medium: it requires a request to be left pending (unconfirmed to completion) while a `DeleteMember` request executes for one of the confirmers — a realistic operational sequence (e.g., rotating out a compromised or departing key-holder) rather than an attacker-crafted edge case. No privileged access beyond normal multisig operation (adding/confirming requests, which any member can already do) is needed to trigger it; it can occur through ordinary member turnover combined with in-flight requests, and the remaining members have no way to detect that a stale confirmation from a removed member is silently counted toward quorum.

### Recommendation
When executing `DeleteMember`, iterate over all outstanding `requests`/`confirmations` and remove the deleted member's identity string from every request's confirmation set (not just requests the member authored), recomputing whether any request now falls back below threshold. Alternatively, revalidate at `confirm()`/execution time that every identity present in the confirmations set is still contained in `self.members` before comparing the count against `self.num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)` (`num_confirmations = 3`). [4](#0-3) 
2. Member `B` calls `add_request` with a `Transfer` action to attacker/receiver — request `R` created, 0 confirmations. [5](#0-4) 
3. Member `A` calls `confirm(R)` — `confirmations(R) = {A}` (1/3). [1](#0-0) 
4. Separately, an already-confirmed `DeleteMember { member: A }` request executes (e.g., because the team is rotating out `A`'s key). `delete_member` removes `A` from `self.members` but request `R`'s confirmations still contain `A`. [2](#0-1) 
5. Members `B` and `C` (both legitimately live) call `confirm(R)`. `confirmations(R).len()` reaches 3 (`{A, B, C}`) which is `>= num_confirmations (3)`, so `execute_request` runs the `Transfer` — even though only 2 currently-live members (`B`, `C`) actually authorized it, one short of the required 3. [6](#0-5) 

This demonstrates a Critical-impact "multisig request executed below threshold" outcome achievable without compromising any live key, purely through normal request/member-management ordering.

    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
