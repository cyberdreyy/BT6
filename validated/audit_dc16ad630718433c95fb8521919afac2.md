### Title
Unanchored `NamespaceOverwriteAllowed` regex allows namespace-restriction bypass via substring match - (File: executors/kubernetes/overwrites.go)

### Summary
`createOverwrites` validates `KUBERNETES_NAMESPACE_OVERWRITE` against the admin-configured `NamespaceOverwriteAllowed` regex through `evaluateOverwrite` → `overwriteRegexCheck`, which uses Go's `regexp.MatchString`. Since `MatchString` reports whether the pattern matches *anywhere* in the string (not a full-string match), an operator-configured pattern such as `ci-.*` (without `^...$` anchors) can be satisfied by a value that merely contains that pattern as a substring, e.g. `kube-system-ci-x`.

### Finding Description
The validation chain is:
- `commands/multi.go` `RunCommand.processBuildOnRunner` → executor `Prepare` → `createOverwrites` (`executors/kubernetes/overwrites.go:147`), which reads `KUBERNETES_NAMESPACE_OVERWRITE` and calls `o.evaluateOverwrite("Namespace", config.Namespace, config.NamespaceOverwriteAllowed, namespaceOverwrite, logger)` at `executors/kubernetes/overwrites.go:158-164`.
- `evaluateOverwrite` (`executors/kubernetes/overwrites.go:593-618`) delegates the regex check to `overwriteRegexCheck` (`executors/kubernetes/overwrites.go:620-630`), which compiles the admin regex and calls `r.MatchString(value)`.

Go's `regexp.MatchString`/`(*Regexp).MatchString` performs an unanchored search — it returns `true` if the pattern matches *any substring* of the input, not the entire input. If an admin configures `namespace_overwrite_allowed = "ci-.*"` intending to restrict overwrites to namespaces beginning with `ci-`, a value like `kube-system-ci-x` will still match, because the substring `ci-x` (starting mid-string) satisfies `ci-.*`. The full value is never required to match from start to end unless the admin explicitly anchors the pattern with `^` and `$`. There is no additional anchoring, prefix check, or full-match enforcement anywhere in `overwriteRegexCheck` or its callers to compensate for this.

This is a genuine root cause: a real Go regex semantics gap in a security-relevant validation function that a normal Runner operator, following the documented pattern-based configuration model, could reasonably not anticipate — many users assume "regex must match" implies "the whole value must match the pattern," which is not how `MatchString` works.

### Impact Explanation
If an unprivileged CI job author sets `KUBERNETES_NAMESPACE_OVERWRITE=kube-system-ci-x` (or any string containing the substring pattern), `evaluateOverwrite` returns this value as the accepted namespace override rather than rejecting it, and the job pod is scheduled in that namespace instead of being confined to the intended `ci-*` pool. This is a concrete Runner-enforced-restriction bypass: the job attacker gains the ability to place their pod in a namespace outside the admin's intended boundary, which can carry different RBAC/service-account bindings, network policies, or resource quotas — i.e., stronger/different identity or permissions than intended, matching the scoped impact exactly. The same bug also affects `ServiceAccountOverwriteAllowed`, `PodLabelsOverwriteAllowed`, `PodAnnotationsOverwriteAllowed`, `NodeSelectorOverwriteAllowed`, and `NodeTolerationsOverwriteAllowed`, since they all funnel through the same `overwriteRegexCheck` helper.

### Likelihood Explanation
This requires only that the admin configure a non-fully-anchored regex for `namespace_overwrite_allowed` — a very plausible, commonly-seen misconfiguration (e.g. copying `ci-.*` from documentation examples without realizing anchoring is required), since nothing in the code or an unanchored pattern makes this obviously wrong at configuration time. The attacker only needs to be a normal CI job author able to set job/pipeline variables. No cluster-admin or GitLab-admin compromise is needed. It is fully reproducible and deterministic given the regex configuration.

### Recommendation
Enforce full-string matching in `overwriteRegexCheck` regardless of whether the admin's pattern is anchored, e.g. by wrapping the compiled pattern (`^(?:` + regex + `)$`) before calling `MatchString`, or by using `regexp.MustCompile` output with a full-match helper that checks `loc := r.FindStringIndex(value); loc[0] == 0 && loc[1] == len(value)`. Additionally, update documentation to clarify that supplied regexes are auto-anchored (or explicitly warn admins to anchor them if that behavior is intentionally left to configuration).

func (o *overwrites) evaluateOverwrite(
	fieldName, value, regex, overwriteValue string,
	logger buildlogger.Logger,
) (string, error) {
	if regex == "" {
		logger.Debugln("Regex allowing overrides for", fieldName, "is empty, disabling override.")
		return value, nil
	}

	if overwriteValue == "" {
		return value, nil
	}

	if err := overwriteRegexCheck(regex, overwriteValue); err != nil {
		return value, err
	}

	logValue := overwriteValue
	if fieldName == "BearerToken" {
		logValue = "XXXXXXXX..."
	}

	logger.Println(fmt.Sprintf("%q overwritten with %q", fieldName, logValue))

	return overwriteValue, nil
}

func overwriteRegexCheck(regex, value string) error {
	var err error
	var r *regexp.Regexp
	if r, err = regexp.Compile(regex); err != nil {
		return err
	}
	if match := r.MatchString(value); !match {
		return &malformedOverwriteError{value: value, pattern: regex}
	}
	return nil
}
