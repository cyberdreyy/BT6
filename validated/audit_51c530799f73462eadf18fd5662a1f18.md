### Title
`check_latest_block_in_tenure` treats an unreachable node's tenure-tip as "proposal is higher," letting a miner's stale/conflicting block pass the tip-confirmation check - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The external report's bug class is: a fetch that fails is signaled with a "safe-looking" sentinel value instead of a hard failure, and the caller treats that sentinel as if it were a real, verified result, corrupting a downstream calculation/decision. In the Reserve report this is `price()` returning `(0, FIX_MAX)` on fetch failure, silently consumed by `collateralShortfall()`.

The same pattern occurs in `SortitionData::check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs`. When the signer cannot reach the stacks-node to fetch the tenure tip (`client.get_tenure_tip(tenure_id)` errors), the code does not fail closed. It logs a warning and returns `Ok(true)` — i.e., it *assumes* the proposed block is higher than (confirms) the tenure tip, exactly the affirmative answer needed to pass the "does this block confirm the expected tip" check. [1](#0-0) 

### Finding Description
`check_latest_block_in_tenure` is the shared helper used by `check_tenure_change_confirms_parent` and `confirms_latest_block_in_same_tenure`, which in turn are invoked from `check_block_against_signer_db_state` at three critical points: proposal arrival, block-validate-OK, and immediately before a signature is placed (per `docs/signer-flows.md` section 7). Its purpose is to prevent a signer from signing a block that fails to confirm the freshest known tip of its tenure (or parent tenure, for tenure-change blocks). [2](#0-1) 

After the local DB checks (last signed block, last pre-committed block) pass or are inconclusive, the function asks the node directly for the tenure tip: [3](#0-2) 

If `get_tenure_tip` fails (RPC unreachable, timeout, or any client-side error), the function returns `Ok(true)` unconditionally — the same code path that is taken when the node genuinely confirms the proposal is higher than the tip. The caller has no way to distinguish "verified higher" from "could not verify, so assumed higher." This is structurally identical to `price()` returning `(0, FIX_MAX)` on failure and the caller not checking for that sentinel before using it in `collateralShortfall()`: an error condition is silently converted into "no problem detected."

The comment in the code rationalizes this by saying the block still has to pass the `stacks-node`'s own `/v3/block_proposal` validation, so this local check is just a backstop. That reasoning holds for the *proposal-time* call site, where an independent node-side validation gate still exists downstream. But `check_block_against_signer_db_state` also runs this same check at the **pre-commit → signature** boundary (section 5 of `docs/signer-flows.md`), i.e., immediately before the signer's signature is actually produced, well after the node's one-time `/v3/block_proposal` validation already happened. At that later point, a transient RPC failure to the local node (which a miner cannot directly cause, but which is plausible under normal operational noise — restart, load, network blip) makes the "confirms tip" check vacuously pass, when the correct fail-safe behavior for a check whose entire job is to prevent double-signing/reorg blocking would be to reject or hold, not silently approve.

### Impact Explanation
If this check spuriously returns `true` due to an RPC error at the pre-commit-to-signature transition, a signer can place its signature on a block that does not, in fact, confirm the tenure's actual latest tip — i.e., a signature over a stale or conflicting block relative to what the signer's own local state (or the network) has already progressed past. Because `check_latest_block_in_tenure` is one of only two gates (`get_tenure_last_block_info` local check and this node-tip check) protecting the signer from signing over a reorg/duplicate at the same height, defeating the second gate via an inconclusive RPC removes half of the fail-safe defense at exactly the highest-consequence moment (right before a signature that will be broadcast and potentially reach the 70% threshold). This matches the "signer signing an invalid/non-canonical/conflicting block" Critical bucket, since the effect is the safety equality "signature only placed after tip is verified" is broken and replaced with "signature placed whenever verification could not be completed."

### Likelihood Explanation
This does not need a majority of signers or any privileged access — a single signer's own transient connectivity/latency issue with its own stacks-node (which is common in normal operation: node restarts, RPC timeouts, `block_proposal_validation_timeout`-adjacent load) is sufficient to hit the `Err(e)` branch. No attacker action against other signers is required; the miner does not even need to be malicious for the race window to appear, though a miner racing a reorg attempt against a signer whose node RPC is briefly degraded increases the chance of exploiting it.

### Recommendation
Do not treat an RPC/node failure at `get_tenure_tip` as equivalent to a verified "proposal is higher" answer. At minimum, distinguish the site: for the proposal-time call (where the node's own `/v3/block_proposal` validation is still pending and acts as backstop), the current assume-true behavior may be acceptable; for the check invoked from `check_block_against_signer_db_state` immediately preceding pre-commit/signature (the last check before a signature leaves the signer), a failure to fetch the tip should cause the signer to hold/reject rather than default to `true`, consistent with how `get_signed_conflicts`/`reorg_permit_stands` in the surrounding code correctly choose to "hold" rather than "sign" when a node query cannot be completed.

### Proof of Concept
Not independently reproduced in a live cluster; based on static analysis of `stacks-signer/src/chainstate/mod.rs:450-461` and its call chain via `check_tenure_change_confirms_parent` / `confirms_latest_block_in_same_tenure` → `check_block_against_signer_db_state`, which per `docs/signer-flows.md` section 5/7 is re-run immediately before `mark_pre_committed`/signature. Reproducing this concretely would require injecting an RPC failure against `get_tenure_tip` on a signer at the moment its pre-commit weight crosses threshold, which was not verified end-to-end here.
