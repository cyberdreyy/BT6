## Finding

The `multihandler.HandleLegacyUserMessage` in [1](#0-0)  is a stateless router with no ID tracking of its own — it just looks up the handler by `msg.Body.Method` and delegates. The actual message-id bookkeeping happens downstream, and its safety differs by handler:

- **Vault / confidential-relay handlers do not support `HandleLegacyUserMessage` at all** — they explicitly reject legacy messages: [2](#0-1) . Their JSON-RPC path (`HandleJSONRPCUserMessage`) tracks active requests keyed only by `req.ID` (no sender), but **rejects** duplicate IDs outright rather than silently overwriting: [3](#0-2)  and [4](#0-3) . So the "vault/DKG secret shares disclosed" impact claimed in the question is **not reachable** through this path — the vault handler cannot even receive legacy messages, and its JSON-RPC path fails closed on ID collision (confirmed by `TestConfidentialRelayHandler_DuplicateRequestID`, [5](#0-4) ).

- **The legacy WebAPI capabilities handler**, which is what `HandleLegacyUserMessage` actually reaches for `MethodWebAPITrigger`, stores pending callbacks in `savedCallbacks map[string]*savedCallback` keyed solely by `msg.Body.MessageId` — with **no sender binding and no existence check before overwrite**: [6](#0-5) . Compare this to `common.RequestCache`, which correctly scopes pending requests by `globalId{sender, id}` and rejects duplicates: [7](#0-6) . When the node responds, `handleWebAPITriggerMessage` looks the callback up purely by `msg.Body.MessageId`, again with no sender check, and delivers the response to whatever callback currently occupies that key: [8](#0-7) .

This means two different senders (any signed EOA) submitting `web_api_trigger` requests with the same `MessageId` will have the second one silently clobber the first's saved callback, so the response destined for the victim gets delivered to the attacker's callback instead. This is a genuine cross-user response confusion bug, but the scope of information disclosed is limited to whatever payload the legacy WebAPI trigger handler returns (HTTP trigger response contents), not vault/DKG secrets.

### Title
Message-ID collision causes cross-user response delivery in legacy WebAPI trigger handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`multihandler.HandleLegacyUserMessage` routes `web_api_trigger` requests to the capabilities handler, whose `savedCallbacks` map is keyed only by the caller-supplied `MessageId`, without binding to the authenticated sender or rejecting duplicates. A second signed request from any address reusing an in-flight victim's `MessageId` silently overwrites the stored callback, so the node's eventual response for that `MessageId` is delivered to the attacker instead of the original requester.

### Finding Description
`HandleLegacyUserMessage` in `handlers/capabilities/handler.go` stores `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` with no check for an existing entry and no sender component in the key [6](#0-5) . `handleWebAPITriggerMessage`, invoked when a node responds, looks up and deletes the callback purely by `msg.Body.MessageId` and forwards the raw node response to whichever callback is registered [8](#0-7) . Since `MessageId` is attacker-chosen and unconstrained (only timestamp/method/signature are validated in `HandleLegacyUserMessage`, [9](#0-8) ), any signed sender can submit a colliding ID to hijack the callback slot for that ID.

### Impact Explanation
This enables cross-user response confusion — an unprivileged attacker with any valid signing key can cause another user's web-api-trigger response (e.g., HTTP trigger execution result) to be delivered to the attacker's callback instead. This does **not** reach vault/DKG secret material, since the vault and confidential-relay handlers do not support `HandleLegacyUserMessage` and reject duplicate IDs on their JSON-RPC path [2](#0-1) [3](#0-2) . The realistic impact is limited to unauthorized disclosure of another user's legacy WebAPI trigger response payload, not Critical-tier server credential/secret theft.

### Likelihood Explanation
Any internet client with a signing key can trigger this without special privileges; the only requirement is guessing or observing the victim's `MessageId` (which may be predictable, e.g., derived from workflow ID/execution ID) before the victim's request completes.

### Recommendation
Bind `savedCallbacks` (and any other legacy-message pending-request maps) to `{sender, messageId}` similar to `common.RequestCache`'s `globalId` key [10](#0-9) , and reject registration if an entry already exists instead of silently overwriting.

### Proof of Concept
Go test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two signed `api.Message`s from different private keys (different `Sender`) but identical `MessageId` and `Method: MethodWebAPITrigger`.
2. Call `handler.HandleLegacyUserMessage` for sender A with callback A, then for sender B with callback B (same `MessageId`).
3. Simulate a node response for sender A's original message (`msg.Body.MessageId` unchanged) via `handleWebAPITriggerMessage`/`HandleNodeMessage`.
4. Assert that callback B (attacker) receives the response intended for sender A, and callback A never receives a response — demonstrating cross-user response delivery.

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if payload.Timestamp == 0 {
		h.lggr.Errorw(ErrDecodingPayload)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload,
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
		h.lggr.Errorw("stale message")
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.HandlerError),
				"stale message",
				nil,
			),
			ErrorCode: api.HandlerError,
		})
	}
	// TODO: apply allowlist and rate-limiting here
	if msg.Body.Method != MethodWebAPITrigger {
		h.lggr.Errorw("unsupported method", "method", body.Method)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UnsupportedMethodError),
				"invalid method "+msg.Body.Method,
				nil,
			),
			ErrorCode: api.UnsupportedMethodError,
		})
	}
	req, err := common.ValidatedRequestFromMessage(msg)
	if err != nil {
		h.lggr.Errorw(ErrTransformingMessageToRequest)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrTransformingMessageToRequest,
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	h.mu.Lock()
	h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
	don := h.don
	h.mu.Unlock()

	// Send original request to all nodes
	for _, member := range h.donConfig.Members {
		err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
	}
	return err

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
