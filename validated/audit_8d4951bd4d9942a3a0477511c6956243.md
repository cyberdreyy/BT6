### Title
Stale confirmations from removed/deleted multisig members can execute a request below the effective live-member threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
The `confirm` flow in both `multisig` and `multisig2` counts a `request_id`'s stored confirmations set purely by size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without re-validating, at the moment of execution, that every account/key that previously confirmed is still a current, live member/key of the contract. [1](#0-0) [2](#0-1) 

### Finding Description
The intended custody binding for a K-of-N multisig is: **confirmations counted == confirmations from currently live members**. A request should only execute once `num_confirmations` *live* members have approved it.

In both implementations, `confirm()` looks up the stored `confirmations` set for a `request_id` and simply checks its cardinality against `self.num_confirmations`:

```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    ...
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), "Already confirmed this request with this key");
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
``` [1](#0-0) 

There is no step that iterates the stored confirmations and asserts each confirmer is still contained in `self.members` (multisig2) or still has a live access key (multisig v1). A member can be confirmed on request R, then later be removed via an `AddMember`/`DeleteMember` or `AddKey`/`DeleteKey` request that itself reaches the required threshold (a separate, legitimately-approved action). Once removed, R's confirmation set on disk still contains that now-invalid member's confirmation. When a later, still-current member calls `confirm(R)`, the size check counts the stale (now-invalid) confirmation toward the threshold, allowing `execute_request` to fire with fewer *live* approvals than `num_confirmations` actually requires among current members.

This directly breaks the "confirmations counted versus live members" custody binding called out for this class of finding: the recorded confirmation count no longer equals the count of confirmations that current members actually granted.

### Impact Explanation
This can allow an arbitrary request (`Transfer`, `FunctionCall`, `DeployContract`, `AddKey`, etc.) to execute with fewer effective/live confirmations than the configured `num_confirmations` threshold, i.e. "a multisig request executed below threshold" — explicitly listed as a Critical impact for this analysis. Since `MultiSigRequestAction::Transfer` can move NEAR out of the multisig account, and `DeployContract`/`AddKey` can grant further unauthorized control, this can lead to unauthorized fund movement or account takeover using confirmations from a member who has since been legitimately revoked.

### Likelihood Explanation
Requires: (1) a pending request with partial confirmations from a member who is later removed, and (2) any remaining confirmations to complete the threshold afterward. Both are ordinary contract usage patterns (creating a request, gathering confirmations over time, and separately rotating members/keys) rather than privileged or out-of-scope actions — no redeploy, foundation, or victim key is required, only the ordinary multisig members/keys operating the contract as documented. The likelihood is moderate: it depends on timing (request left pending across a membership change), which is plausible in real key-rotation workflows (e.g., revoking a compromised or departing signer) but not guaranteed to occur every time.

### Recommendation
- Short term: In `confirm()`/`execute_request()`, before counting confirmations toward `num_confirmations`, filter the stored confirmation set to only those confirmers still present in `self.members` (multisig2) or still holding a valid access key (multisig v1), and use that filtered count for the threshold check.
- Alternatively, on every `AddMember`/`DeleteMember` (or `AddKey`/`DeleteKey`) execution, prune stale confirmations from all pending requests whose confirmer is no longer a member/key holder.
- Long term: Add an invariant check that revalidates confirmer membership at the moment `execute_request` is invoked, not just at the moment each individual `confirm` call was made.

### Proof of Concept
1. Deploy `multisig2` with 5 members (`m1..m5`) and `num_confirmations = 3`.
2. `m1` calls `add_request_and_confirm(Transfer{...})` → request `R` has 1 confirmation (`m1`).
3. `m2` calls `confirm(R)` → `R` has 2 confirmations (`m1`, `m2`), below threshold of 3, so it is not yet executed (see the `else` branch in `confirm`, storing the pending confirmations). [3](#0-2) 
4. Separately, `m3`, `m4`, `m5` create and confirm a `DeleteMember{member: m1}` request that reaches the threshold of 3 and executes, removing `m1` from `self.members`.
5. `m2` calls `confirm(R)` again — wait, `m2` already confirmed; instead a third *still-valid* member, e.g. `m3`, calls `confirm(R)`.
6. In `confirm`, `confirmations.len()` is 2 (`m1`, `m2`) so `2 + 1 >= 3` is true, and `execute_request(request)` fires — even though `m1` is no longer a member, meaning only 2 of the 3 confirmations (`m2`, `m3`) came from currently valid members. [4](#0-3) 
7. The `Transfer` request executes with only 2 live-member confirmations against a configured 3-of-N policy, demonstrating a request executed below the effective threshold.
