## Confirmations counted despite deleted member/key ("stale confirmation") — ([File: multisig2/src/lib.rs])

### Summary
The reported vulnerability class ("failed proposal can be committed/replayed again, breaking a custody binding between what was authorized and what actually executes") maps onto the `multisig`/`multisig2` contracts as a **binding break between confirmations counted and members actually live**. `confirm()` treats `num_confirmations` <= `confirmations.len()` as sufficient authorization, but `delete_member` (v2) / `DeleteKey` (v1) only purge confirmations/requests that were *created* by the removed member — they do not purge confirmations that removed member gave on *other* still-pending requests created by someone else. A stale confirmation from an already-removed member therefore still counts toward the execution threshold.

### Finding Description
`confirm()` counts entries in `self.confirmations` against `self.num_confirmations` and, once satisfied, executes the request via `execute_request` [1](#0-0) . Membership removal is implemented in `delete_member`, which is only invoked as part of executing a `DeleteMember` request action [2](#0-1) . `delete_member` cleans up:
- requests where `r.member == member` (i.e., requests *created* by the removed member), and
- the `num_requests_pk` entry for that member,

but it never scans other pending requests' `confirmations` sets to strip out the removed member's identity string [3](#0-2) .

Consequently: if member `B` confirms a pending request `R` created by member `A` (so `R.confirmations = {A, B}` after `A`'s implicit confirm via `add_request_and_confirm` and `B`'s `confirm`), and afterward the multisig executes a separate request that deletes member `B` via `DeleteMember`, `B`'s access key/account is removed from `self.members` and its key is revoked on-chain — but `R.confirmations` still contains `B`'s entry. If a third member `C` later calls `confirm(R)`, the count `{A, B, C}.len() == 3` may reach `num_confirmations` even though only `A` and `C` are *currently live* members, i.e. **confirmations counted diverges from live members actually entitled to authorize**. The equality the contract is supposed to maintain — `count(confirmations that belong to live members) >= num_confirmations` — is violated because stale, no-longer-authorized confirmations are never purged from other requests.

The identical pattern exists in the original `multisig` (v1) contract: `DeleteKey`'s cleanup loop filters only `r.signer_pk == pk` (i.e. requests created by that key) before removing confirmations, and never removes the deleted `pk` from `confirmations` sets belonging to requests created by other keys [4](#0-3) .

### Impact Explanation
This crosses an authorization/threshold boundary explicitly called out as Critical: "a multisig request executed below threshold." A request can be executed with fewer *currently authorized* confirmations than `num_confirmations` requires, because a stale confirmation from a member whose key/account access was already revoked is still tallied. Since `execute_request` can perform `Transfer`, `FunctionCall`, `AddKey`, etc. [5](#0-4) , this can lead to unauthorized movement of NEAR held by the multisig account, or unauthorized privilege changes (adding new full-access keys), executed with effectively fewer live signers than the configured threshold.

### Likelihood Explanation
This does not require compromising the foundation, a redeploy, or any off-chain compromise — it only requires the ordinary, documented multisig workflow: a member is removed (e.g., due to key rotation, offboarding, or compromise response) while there exists an unrelated pending request that member had previously confirmed. This is a routine and expectable sequence of unprivileged-from-the-attacker's-perspective multisig operations (the "attacker" here is simply a remaining/removed member exploiting an existing stale confirmation, or the situation arises unintentionally and is exploited by a member who realizes a removed co-signer's confirmation is still "banked"). The bug is purely a missing cleanup step in `delete_member`/`DeleteKey`, present in both `multisig` and `multisig2`.

### Recommendation
When removing a member (`delete_member` in v2, `DeleteKey` handling in v1), iterate over all pending `requests`/`confirmations` and strip the removed member's identity from every confirmations set, not only from requests that member itself created. Alternatively, re-validate at `confirm()`/execution time that every entry in a request's confirmations set still corresponds to a current member of `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)`.
2. `A` calls `add_request_and_confirm(R)` for some `Transfer`/`FunctionCall` request — `R.confirmations = {A}`.
3. `B` calls `confirm(R)` — `R.confirmations = {A, B}` (below threshold 3, so not yet executed).
4. Members `A, C, D` (or any 3-of-4) submit and confirm a separate request `R2 = DeleteMember{member: B}`, which executes and calls `delete_member(B)` — this removes `B` from `self.members`, deletes `B`'s access key on-chain, but does **not** touch `R.confirmations`, which still contains `B` [6](#0-5) .
5. `C` calls `confirm(R)`. `confirmations.len() + 1 == 3 >= num_confirmations (3)`, so `execute_request(R)` runs [7](#0-6) , even though only `A` and `C` are currently live members that actually authorized it — `B`'s revoked confirmation was counted.

**Note on confidence:** I verified the missing-cleanup logic directly in `multisig2/src/lib.rs` (`delete_member`, `remove_request`, `confirm`) and the analogous `DeleteKey` handler in `multisig/src/lib.rs`. I was not able to find any additional runtime check elsewhere in the confirm/execute path that re-validates confirmation identities against current membership before tallying, but given the size of the indexed codebase there may be test files or other guard code not surfaced by my searches; a full Devin session with complete file access could confirm there is no such secondary guard.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
