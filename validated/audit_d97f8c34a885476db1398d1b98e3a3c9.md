This is a genuine, provable bug. `createDstEscrow` accepts a fully attacker/taker-controlled `Immutables` struct — including the `parameters` bytes blob — with no validation of its length or content: [1](#0-0) 

That blob is baked immutably into the CREATE2 salt (`immutables.hashMem()`), so it can never be altered after deployment. `EscrowDst._withdraw` (used by both `withdraw` and `publicWithdraw`) unconditionally decodes fee fields from `parameters`: [2](#0-1) 

`integratorFeeAmountCd` enforces `parameters.length >= 0x40` regardless of the actual fee *value* — a length-only check, not a value check: [3](#0-2) 

So if the taker funds a destination escrow with a 32-byte `parameters` blob (satisfying `protocolFeeAmountCd`'s `>= 0x20` check but failing `integratorFeeAmountCd`'s `>= 0x40` check), `_withdraw` reverts with `IndexOutOfRange` unconditionally — for both the private `withdraw()` (`contracts/EscrowDst.sol:36-43`) and the public `publicWithdraw()` (`contracts/EscrowDst.sol:50-57`) paths, since both funnel into the same `_withdraw`. This holds no matter what secret is supplied, because the revert happens before the secret/hashlock check would even matter for the fee-decoding step. [4](#0-3) 

Because the immutables (including the malformed `parameters`) are permanently bound to the escrow's deterministic address/hash via `onlyValidImmutables(immutables.hash())`, this cannot be fixed post-deployment — the maker can never successfully withdraw regardless of who calls or when. The only way to move funds out is `cancel()`, which sends the destination token amount back to the **taker** (not the maker) after `DstCancellation`, or `rescueFunds` (also taker-only, after `RESCUE_DELAY`): [5](#0-4) 

Since the taker already knows the secret off-chain (required to call the private `withdraw`) and can still redeem the maker's original funds on the source chain with that same secret via `EscrowSrc.withdraw`, this is not merely a temporary freeze — the maker's destination-side payout is permanently unrecoverable by the maker, while the taker keeps both the source funds and reclaims the destination deposit/tokens via `cancel()`.

### Title
Malicious taker can brick `EscrowDst._withdraw` (both private and public paths) with a short `parameters` blob, permanently denying the maker's destination payout - (File: `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`createDstEscrow` does not validate the length or consistency of the caller-supplied `Immutables.parameters` field. `ImmutablesLib.integratorFeeAmountCd`/`protocolFeeRecipientCd`/`integratorFeeRecipientCd` enforce strict minimum-length checks unconditionally, independent of the encoded fee value. A taker can fund a destination escrow with `parameters` set to exactly 32 bytes (passing the 0x20-byte `protocolFeeAmountCd` check but failing the 0x40-byte `integratorFeeAmountCd` check used unconditionally in `_withdraw`), causing every call to `withdraw()` and `publicWithdraw()` to revert with `IndexOutOfRange`, for the lifetime of that escrow.

### Impact Explanation
Because `parameters` is hashed into the immutable salt used for `onlyValidImmutables`, the corrupted parameters cannot be corrected after deployment. The maker can never successfully withdraw their destination-chain payout, even with a valid secret and during the public-withdrawal window intended as the safety-net path. The only exits are `cancel()`/`rescueFunds`, both of which return the token amount to the taker, not the maker — so the maker's destination funds are permanently lost to them, while the taker (who already possesses the secret needed to unlock the source escrow) can still claim the maker's source-chain funds. This satisfies the Critical bar of permanent freezing/loss of user funds caused by unprivileged-taker-supplied input in production contracts.

### Likelihood Explanation
High. `createDstEscrow` is a public, unrestricted entrypoint that fully trusts caller-supplied `Immutables`, including `parameters`; no cross-checks tie it to any source-chain fee data. Any resolver/taker acting as an unprivileged destination-escrow creator can trivially construct a 32-byte `parameters` blob instead of the expected 128-byte (4×32) fee-metadata encoding.

### Recommendation
Validate `dstImmutables.parameters` length/format inside `createDstEscrow` (e.g., require it be exactly the expected 0x80-byte fee-metadata size, or empty only if fees are genuinely disabled via a distinct code path), and/or make `ImmutablesLib`'s fee getters treat a short/empty `parameters` as "no fees" rather than reverting, so that `_withdraw` can still complete when fee amounts are legitimately zero.

### Proof of Concept
1. Taker calls `escrowFactory.createDstEscrow{value: safetyDeposit (+amount if native)}(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.parameters = abi.encode(uint256(0))` (32 bytes) instead of the full 4-field encoding.
2. Escrow deploys and gets funded normally (`IERC20.safeTransferFrom` for ERC20, or native value check passes).
3. Maker learns the secret is valid; at `DstWithdrawal` stage taker calls `withdraw(secret, dstImmutables)` — reverts with `ImmutablesLib.IndexOutOfRange` at `integratorFeeAmountCd` (`parameters.length` = 32 < 64).
4. At `DstPublicWithdrawal` stage, an access-token holder calls `publicWithdraw(secret, dstImmutables)` — same revert, confirming the public safety-net path is equally bricked.
5. After `DstCancellation`, taker calls `cancel(dstImmutables)`, reclaiming the destination token amount and safety deposit for themselves; the maker never receives the destination payout.

        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;

        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;

        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    /**
     * @notice Returns the integrator fee amount from the immutables (calldata version).
     * @param immutables The immutables to extract the fee from.
     * @return ret The integrator fee amount.
     */
    function integratorFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x40) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(add(parameters.offset, 0x20))
        }
    }
