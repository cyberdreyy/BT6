### Title
Settled APR0 withdraw receipts survive default-claim clearing and permanently brick `claimWithdrawRequest` — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
CVE-2022-23034 is a double-accounting bug: Xen's grant-mapping refcount was decremented twice when two mapping forms coexisted, and the underflow check then wedged the hypervisor. The analog in `IdleCreditVault` is the opposite half of the same bug class — one accounting form is decremented while a coexisting second form is *not*. A user holding both a **settled** APR0 receipt and an **open** APR0 receipt has only the open bucket cleared by `_clearWithdrawClaimForEpoch` during default finalization. The settled bucket then falls through to `_claimFundedWithdrawRequest`, which tries to pay it at par out of non-reserve balance. After finalization essentially all strategy balance *is* `defaultRecoveryReserve`, so `_transferFundedClaim`'s reserve-protection guard reverts and the entire claim transaction reverts — permanently freezing that user's defaulted claim, their reserve share, and any future post-default requests.

### Finding Description
`requestWithdraw` keeps two simultaneous accounting forms for APR0-mode receipts (contracts/strategies/idle/IdleCreditVault.sol:567-577): the "open" bucket `apr0Users[_user].principal/principalEpoch` plus `apr0TotalPrincipal`, and — after `_settleApr0` migrates it on the next epoch's request (lines 545-565) — the "settled" bucket `settledPrincipal/settledInterest`. Both forms were funded through the same `pendingWithdraws` liability (line 279, 535) and are both included in `defaultPendingClaimBasis` (line 645) when `finalizeDefaultRecovery` computes the recovery haircut (lines 679-688).

On claim, `_claimDefaultedWithdrawRequest` → `_clearWithdrawClaimForEpoch` (lines 811-837) clears only the form whose `principalEpoch == defaultEpoch` and `principal != 0`. A settled bucket (`principal == 0`, `settledPrincipal != 0`) produces `claimBasis == 0` for itself: it is never removed from `withdrawsRequests`, never decrements `pendingWithdraws`, and its `apr0Users` entry is untouched.

`claimWithdrawRequest` then unconditionally calls `_claimFundedWithdrawRequest` (line 313), which computes `amount = normalAmount + settledPrincipal + principal + settledInterest` (lines 338-341) — the settled receipt is counted a second time under the *other* accounting form — burns the receipt tokens, deletes `apr0Users`, and calls `_transferFundedClaim`. There `_transferFundedClaim` reverts with `NotAllowed` whenever `balance - defaultRecoveryReserve < amount` (lines 899-905), which is always the case post-finalization because `defaultRecoveryReserve` absorbs prefunded instant funds and all recovered cash (line 686, 691). The revert rolls back the already-executed `_claimDefaultedWithdrawRequest` payment, so the user receives nothing at all.

### Impact Explanation
- The user's defaulted-epoch claim is permanently frozen: every call to `IdleCDOEpochVariant.claimWithdrawRequest()` for them hits the same revert in `_transferFundedClaim`. Their haircut share stays locked inside `defaultRecoveryReserve` forever.
- The freeze is sticky: `requestWithdraw` post-default reverts because `_hasWithdrawRequest` returns true while `settledPrincipal/settledInterest != 0` (lines 247-251, 886-891), so the user can never open a `postDefaultRequests` claim either.
- `pendingWithdraws` is left permanently overstated by the settled basis, corrupting any accounting that still reads it.
- Quantified loss: the full recovery payout owed to any APR0 user who requested in two consecutive APR0 epochs (`settledPrincipal + settledInterest`, scaled by `defaultRecoveryPrice`), e.g. ~$X recovered share of their principal, frozen with no unprivileged path to release (only `transferToken` owner rescue exists).

### Likelihood Explanation
Requires a specific but plausible sequence: `unscaledApr == 0` across two consecutive epochs (APR0 mode is a supported configuration, see `prepareStopEpochWithApr0` and the apr0 test flows), a user making withdraw requests in both epochs (or claiming once then re-requesting), then a borrower default finalized via `finalizeDefaultRecovery`. All attacker actions (`requestWithdraw`, `claimWithdrawRequest`) are unprivileged; borrower default is an environmental trigger, not a malicious action. No existing guard stops it: `_ensureDefaultRecoveryInitialized`, the epoch gating in `_claimFundedWithdrawRequest`, and the KYC/`_onlyIdleCDO` checks all pass; the reserve guard that causes the revert is itself working as intended — the defect is the leaked second ledger entry reaching it. If stray non-reserve balance ever exceeds `settledPrincipal + settledInterest`, the same bug instead pays the settled receipt *at par* (haircut escape), though the post-finalization balance profile makes the freeze outcome the realistic one.

### Recommendation
In `_clearWithdrawClaimForEpoch`, also consume `apr0User.settledPrincipal`/`settledInterest` (adding them to `claimBasis`/`burnAmount` and decrementing `pendingWithdraws` accordingly) when they belong to the defaulted epoch's liability — or store the settled bucket's epoch so defaulted claims can price it. Alternatively, when `defaultRecoveryFinalized` is true, exclude already-recovered APR0 buckets from the funded-claim path in `_claimFundedWithdrawRequest` so the aggregate `withdrawsRequests + settled*` payout cannot double-count basis that was already folded into the recovery reserve. A regression test should cover two consecutive APR0 requests followed by default finalization and a single `claimWithdrawRequest` call.

// Foundry fork-style PoC against IdleCreditVault default-recovery flow.
function test_SettledApr0ClaimFrozenAfterDefault() external {
    // --- Epoch N (APR0 mode): user requests withdraw #1 ---
    _setApr0Mode();                                  // unscaledApr == 0
    uint256 amt1 = 10_000 * ONE_SCALE;
    _depositWithUser(user, amt1 * 2, true);
    vm.prank(user);
    cdoEpoch.requestWithdraw(amt1, address(AAtranche));   // open APR0 bucket, epoch N

    // --- Epoch N+1 (still APR0): request #2 settles #1 ---
    _startEpochAndCheckPrices(0);                    // stop N: apr0RateByEpoch[N] set,
    // prepareStopEpochWithApr0 -> pendingWithdraws += apr0 net interest
    vm.prank(user);
    cdoEpoch.requestWithdraw(amt1, address(AAtranche));
    // _requestWithdrawApr0 -> _settleApr0: principal -> settledPrincipal (+settledInterest)
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    (,, uint256 settledP, uint256 settledI,,) = vault.apr0Users(user);
    assertGt(settledP, 0);

    // --- Default during epoch N+1, then finalize ---
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    _checkDefault();

    uint256 recovered = /* basis * recoveryRatio */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // --- Claim: defaulted bucket pays, then funded path reverts -> whole tx reverts ---
    vm.prank(user);
    vm.expectRevert(IdleCreditVault.NotAllowed.selector); // _transferFundedClaim reserve guard
    cdoEpoch.claimWithdrawRequest();

    // Reserve share owed to user stays locked; new post-default requests also revert
    vm.prank(user);
    vm.expectRevert(IdleCreditVault.NotAllowed.selector);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
}
