### Title
`BlockRejection`/`BlockAccepted` signatures don't bind `reason_code`/`response_data`, letting anyone with a valid observed rejection forge a different reason and response payload - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` computes the signed digest over **only** `signer_signature_hash` and `chain_id`, not over `reason`, `reason_code`, or `response_data` (which includes `failed_txid`, `reject_reason`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`). Any party who can observe a validly-signed `BlockRejection` from a signer can splice its signature onto a new message with an arbitrary `reason_code`/`response_data`/`reason`, and `BlockRejection::verify()`/`recover_public_key()` will still succeed because they hash-check the same restricted digest.

### Finding Description
`BlockRejection::hash()` at [1](#0-0)  builds the structured-data digest from only `self.signer_signature_hash` (plus a `chain_id`-derived domain separator). `sign()` and `verify()`/`recover_public_key()` all operate over this same restricted digest [2](#0-1) .

The `BlockRejection` struct, however, carries several fields that are *not* part of that digest: `reason` (free text), `reason_code` (`RejectCode`), and the entire `response_data` (`BlockResponseData`, containing `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`) [3](#0-2) . Because none of these fields feed into the signed hash, a valid `(signer_signature_hash, signature)` pair produced once by a genuine signer for one rejection can be reused verbatim in a *different* `BlockRejection` object with attacker-chosen `reason_code`/`response_data`, and it will still pass `verify()`/`recover_public_key()` — the check only confirms the signature matches the `(signer_signature_hash, chain_id)` pair, never the rest of the payload.

Consumers trust these unauthenticated fields as if they came from the signer:
- `stackerdb_listener.rs` uses `rejected_data.reason_code` to decide whether to bucket a `failed_txid` as `BadTransaction`/`ProblematicTransaction` and accumulate signer weight against that transaction [4](#0-3) .
- The same handler feeds `response_data.tenure_extend_timestamp` and `response_data.tenure_extend_read_count_timestamp` directly into `update_idle_timestamp`/`update_read_count_timestamp` [5](#0-4) , which drive tenure-extension/idle-timeout logic for the miner coordinator.

Since none of `reason_code`, `failed_txid`, `reject_reason`, or the two timestamp fields are covered by the signature, a message carrying a legitimately-signed `signer_signature_hash`/`signature` pair (observable on the public StackerDB or via gossip) can be re-wrapped with forged values for all of these fields by anyone relaying/observing traffic — no signer key, no majority, and no auth token is required. This is the direct structural analog of the reported bug class: the code authenticates one attribute (here, the block hash identity via the signature) but then trusts a set of adjacent, unauthenticated attributes (here, `reason_code`/`response_data`) as if they had the same trust level, exactly as `getRealIpAddr()` trusts unauthenticated headers alongside `REMOTE_ADDR`.

### Impact Explanation
This does not itself forge a *new* valid rejection from a signer who never rejected (the underlying `signer_signature_hash`/`signature` pair is still a genuine signer artifact), but it lets a non-majority relayer/miner rewrite the *metadata* of an existing genuine rejection to:
- Misattribute a rejection to `RejectCode::ValidationFailed(ProblematicTransaction)` against an arbitrary `failed_txid`, feeding false weight into the miner-side problematic-transaction bookkeeping that influences which transactions get excluded from future blocks — a liveness/censorship effect against a chosen transaction, achievable by any single relayer.
- Rewrite `tenure_extend_timestamp` / `tenure_extend_read_count_timestamp` to attacker-chosen values, corrupting the idle-timeout/tenure-extension bookkeeping the coordinator maintains per signer, which can wedge or distort tenure-extension liveness decisions.

I could not fully trace, within the available context, whether the StackerDB chunk-level signature (`StackerDBChunkData.sig`, which does cover the full serialized payload bytes via `auth_digest()` over `slot_id/slot_version/data_hash`) is verified on every consumption path before these fields are read, or whether there exists a path (e.g. buffered/pending storage, cross-context relay, or a node-side ingestion route) that accepts the inner `BlockRejection` object independent of a fresh chunk-signature check. If chunk-level signing is always re-verified end-to-end for every code path that reads `reason_code`/`response_data`, exploitation is restricted to the original signer re-signing their own message with a fresh chunk signature (self-inconsistency, low value); if any path trusts the inner object once chunk-authenticity was checked earlier in its lifecycle (e.g., replay/re-serialization through `signerdb.rs` pending-response tables) without re-validating that the specific `reason_code`/`response_data` combination was part of the originally-chunk-signed bytes, the forgeable-metadata issue becomes directly exploitable by any relayer. This gap should be confirmed with a full trace of `drain_pending_block_responses`/`add_pending_block_signature_response` and all StackerDB ingestion call sites.

### Likelihood Explanation
Likelihood is high for the message-malleability primitive itself (no majority, no keys, no auth token needed — just observing one legitimately signed rejection on the wire), but the exploitability of the *consequence* depends on whether any consumer trusts `reason_code`/`response_data` without the accompanying chunk-level signature having been fully verified against that exact byte-for-byte content at the time of use.

### Recommendation
Include `reason_code`, `reason`, and the full `response_data` (or at minimum a hash/commitment of them) inside the digest signed in `BlockRejection::hash()`, mirroring the structured-data approach already used for `signer_signature_hash`. Apply the same fix to `BlockAccepted`/`BlockResponseData` if its `response_data` is similarly excluded from any signed digest. Audit every consumer (`stackerdb_listener.rs`, `signerdb.rs` pending-response persistence, `v0/signer.rs` handlers) to ensure they only act on `reason_code`/`response_data` after verifying a signature that covers those exact fields.

### Proof of Concept
1. Observe a genuine, validly signed `BlockRejection` message `M1` broadcast by signer `S` for block hash `H` with `reason_code = ConnectivityIssues` and `response_data.failed_txid = None`.
2. Construct a new `BlockRejection` `M2` with the same `signer_signature_hash = H`, same `chain_id`, and the exact same `signature` bytes from `M1`, but set `reason_code = ValidationFailed(ProblematicTransaction)` and `response_data.failed_txid = Some(victim_txid)`, and/or set `response_data.tenure_extend_timestamp` to an attacker-chosen value.
3. Call `M2.verify(&S_pubkey)` / `M2.recover_public_key()` — per `BlockRejection::hash()` [1](#0-0) , verification succeeds because the digest only depends on `signer_signature_hash` and `chain_id`, both unchanged.
4. If `M2` (re-wrapped in a chunk that still needs its own valid StackerDB chunk signature — this is the open point noted above) reaches `stackerdb_listener.rs`, `rejected_data.reason_code`/`response_data.failed_txid`/`response_data.tenure_extend_timestamp` are consumed as authentic [6](#0-5) , corrupting problematic-transaction weight tracking and tenure-idle-timeout bookkeeping attributed to signer `S`.

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
