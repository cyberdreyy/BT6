### Title
No exploitable vulnerability found - inner_receiver protocol-version gating in validate_delegate_action

### Summary
`validate_delegate_action` in `runtime/runtime/src/action_validation.rs` selects `inner_receiver` based on `ProtocolFeature::FixDelegatedDeterministicStateInit`. At `PROTOCOL_VERSION` 87 (a `StableProtocolVersion`), this feature is stable and always enabled, so `delegate_action.receiver_id()` is always used — the pre-fix `receiver` branch is dead code at this protocol version. The comment in the source explicitly documents that even the old buggy behavior could not be abused, because the final receipt-level check in `validate_deterministic_state_init` (invoked when the inner receipt is actually processed) independently re-derives and re-validates the receiver against the deterministic state init contents.

### Finding Description [1](#0-0) 
shows the gated selection: post-fix uses `delegate_action.receiver_id()`; pre-fix used the outer `receiver`. Since this is a `ProtocolFeature`, whether the branch is reachable depends solely on `current_protocol_version` at the time `validate_delegate_action` executes — not on any caller-controlled data. At stable `PROTOCOL_VERSION = 87`, `FixDelegatedDeterministicStateInit.enabled(87)` evaluates true unconditionally (this is standard nearcore protocol-versioning: a stabilized feature is enabled for all versions ≥ its stabilization version, and `PROTOCOL_VERSION` never regresses below a stabilized feature at runtime). Thus the `receiver` branch is unreachable in production at PV 87.

Regarding the "bypass via apply_delegate_action" concern: even hypothetically, if a receipt were constructed with a mismatched `inner_receiver` during validation, the actual execution path (`validate_deterministic_state_init`, called for the actual receipt receiver when the DeterministicStateInit action is applied) independently recomputes `derive_near_deterministic_account_id` and compares it to the real receiver_id of the receipt being executed — see [2](#0-1) . This means the authorization for "against which account can this DeterministicStateInit run" is not actually delegated to `validate_delegate_action`'s pre-check; it is enforced again, deterministically, at the point the action is executed against a concrete receiver. So even a validation-side receiver mismatch cannot let an attacker execute a signed `DeterministicStateInit` against an account it wasn't derived for — the derived-id check at execution time would reject it regardless of what happened during pre-validation.

I was unable to fully trace every call site of `apply_delegate_action` inside `actions.rs` within the available tool budget (file is large and truncated in some views), so I cannot exhaustively enumerate all invocation contexts. However, no evidence was found of any code path that constructs/executes a `DeterministicStateInit` receipt while skipping the `validate_deterministic_state_init` receiver-derivation check.

### Impact Explanation
No concrete, reachable fund-theft, freezing, double-spend, or authorization-escalation impact was identified. The described gated branch is provably dead code at stable PV 87, and even in a counterfactual reachability scenario, the redundant execution-time check in `validate_deterministic_state_init` prevents the described bypass.

### Likelihood Explanation
Not applicable — no viable attacker-triggerable path was found.

### Recommendation
No fix required for this specific concern. If defense-in-depth is desired, the dead pre-fix branch and the `ProtocolFeature::FixDelegatedDeterministicStateInit` gate could eventually be removed once the feature has been stable long enough that no historical replay/resharding logic depends on the old behavior, but this is a code-cleanliness consideration, not a security requirement.

Not applicable — no exploitable condition was identified requiring a PoC.

fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }
