### Title
Multisig factory `create` has no failure callback and silently keeps attacker's deposit on failed deployment - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` builds a single promise chain (`create_account` → `deploy_contract` → `transfer` → `function_call("new", ...)`) and returns it directly with no `.then()` callback to the factory itself. If any step of the chain fails (e.g., account already exists, `name` collides, or `new` panics due to invalid `members`/`num_confirmations` per `multisig2`'s own validation), the attached deposit is transferred into a doomed/failed account creation and is never returned to the caller, unlike the sibling `staking-pool-factory` and `lockup-factory` contracts which both refund via an `on_*_create` callback checking `is_promise_success()`.

### Finding Description
The invariant that should hold: `balance_before(predecessor) - deposit == balance_after(predecessor)` only if deployment succeeds; if deployment fails, `balance_after(predecessor) == balance_before(predecessor)` (deposit refunded). In `multisig-factory/src/lib.rs`: [1](#0-0) 

`create` attaches `env::attached_deposit()` directly inside the promise chain via `.transfer(env::attached_deposit())`, then calls `.function_call("new", ...)` on the newly created account, and the resulting `Promise` is returned to the runtime with no `.then(ext_self::...)` callback. There is no `assert_self()`, no `is_promise_success()` check, and no rollback `Promise::new(predecessor_account_id).transfer(...)` anywhere in this file (confirmed absent by searching for `callback`, `on_create`, `is_promise_success` in `multisig-factory`, in contrast to `staking-pool-factory/src/lib.rs` which implements `on_staking_pool_create` at lines 200-239 doing exactly this rollback).

Compare to `staking-pool-factory/src/lib.rs::create_staking_pool` / `on_staking_pool_create`: [2](#0-1) 

That contract explicitly refunds `attached_deposit` to `predecessor_account_id` when `is_promise_success()` is false. The `multisig-factory` has no equivalent structure — the deposit is transferred unconditionally as part of the promise chain and is never returned if `create_account`, `deploy_contract`, or the `new` function call fails (e.g. due to name collision producing `AccountAlreadyExists`, or `multisig2::new`'s internal `assert!` on member/confirmation validity panicking).

Any unprivileged caller can trigger this by: (1) attaching the minimum meaningful deposit for a multisig account (enough to cover storage, e.g. equivalent to what's needed for account creation/contract deployment), (2) choosing a `name` that either collides with an existing account or is otherwise guaranteed to fail (or supplying `members`/`num_confirmations` that the `multisig2::new` constructor will reject), and (3) letting the transaction execute — the deposit is consumed with no refund path, and no callback ever fires to return funds.

### Impact Explanation
NEAR sent by the caller is consumed by a failed deployment and is not returned to the sender; the funds do not move to any legitimate destination — they are effectively stuck/lost inside the failed promise chain since no refund promise ever gets scheduled. This matches "an accounting value diverging from reality where another party settles on it" (High) — the caller's expectation (refund on failure) is broken, and the factory has no bookkeeping or state to reconcile this loss. This is repeatable by any account any number of times, each attempt losing the deposit for that specific attempt; it does not steal from other users' funds nor break protocol-wide accounting invariants beyond the caller's own lost deposit, but it is a systemic missing-refund defect affecting every failed `create` call.

### Likelihood Explanation
Trivial to trigger: an unprivileged attacker (or an unwitting normal user) just needs to call `create` with a `name` that collides with an existing account, or with `members`/`num_confirmations` combinations that `multisig2::new` rejects, while attaching a deposit. No special permissions, keys, or preconditions are required beyond a NEAR account with enough balance to attach a deposit and pay gas — cost is exactly the deposit and gas of one failed transaction, and it's repeatable indefinitely.

### Recommendation
Add an `ext_self` callback (mirroring `staking-pool-factory`'s `on_staking_pool_create` / `lockup-factory`'s pattern): chain `.then(ext_self::on_create(predecessor_account_id, attached_deposit, &env::current_account_id(), NO_DEPOSIT, gas::CALLBACK))` after the `function_call`, and in that callback use `assert_self()` + `is_promise_success()` to refund `attached_deposit` to `predecessor_account_id` via `Promise::new(predecessor_account_id).transfer(attached_deposit)` when the deployment fails.

### Proof of Concept
Using `near-sdk-sim`/`testing_env!` similar to `staking-pool-factory`'s `test_create_staking_pool_rollback`:
1. Set up `MultisigFactory`, set `predecessor_account_id` to an attacker account, set `attached_deposit` to a chosen minimum value.
2. Call `create(name, members, num_confirmations)` where `name` is engineered to collide with an existing sub-account (or `members`/`num_confirmations` invalid so `multisig2::new` panics).
3. Simulate `PromiseResult::Failed` for the created promise chain (since there is no callback in the actual code, this step demonstrates that — unlike `staking-pool-factory` — there is no `on_create` function to even invoke).
4. Assert: `predecessor_account_id`'s balance after the failed call equals `balance_before - attached_deposit` (deposit not refunded), i.e., `assert_eq!(balance_after, balance_before - attached_deposit)`, directly contradicting the required invariant `balance_after == balance_before`. Contrast with `staking-pool-factory/src/lib.rs`'s `test_create_staking_pool_rollback` test (lines 326-374) which asserts the deposit *is* returned in the analogous failure scenario — no equivalent test or code path exists for `multisig-factory`.
