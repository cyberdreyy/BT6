## Finding

### Title
Signer weight double-counted across `total_weight_approved` and `total_weight_rejected` when a signer switches vote — coordinator can wrongly kill a passing block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener`'s `BlockStatus` is supposed to count each signer's weight exactly once toward either the approval or the rejection tally, gated by the single `responded_signers` set [1](#0-0) . In practice the `Accepted` branch guards its weight addition with a *different* map (`gathered_signatures`) instead of `responded_signers` [2](#0-1) , while the `Rejected` branch guards on `responded_signers` [3](#0-2) . This mismatch lets one signer's weight land in *both* `total_weight_rejected` and `total_weight_approved` when it first rejects and later switches to accepting the same block (a legitimate, gossip-only sequence any single signer can produce, e.g. rejecting under stale chainstate and then signing once the chain re-checks pass per `handle_block_pre_commit`'s re-check flow) [4](#0-3) .

### Finding Description
`BlockStatus` documents `responded_signers` as "the set of slot ids of signers who have responded," intended as the single gate ensuring one signer contributes weight to at most one of the two tallies [5](#0-4) .

- In the `Accepted` handling path, the weight add to `total_weight_approved` is gated by `!block.gathered_signatures.contains_key(&slot_id)`, not by `responded_signers`: [2](#0-1) 
- Only afterward is `slot_id` unconditionally inserted into both `gathered_signatures` and `responded_signers` [6](#0-5) .
- In the `Rejected` handling path, the weight add to `total_weight_rejected` is gated by `block.responded_signers.insert(slot_id)` (true only the first time this slot_id appears in the set) [3](#0-2) .

Because these two paths check different collections, the sequence **Reject → Accept** by the same signer for the same block causes:
1. `Rejected` fires first: `responded_signers.insert(slot_id)` returns `true` (first time) → `total_weight_rejected` gets the signer's weight added.
2. `Accepted` fires later with a valid signature: `gathered_signatures.contains_key(&slot_id)` is `false` (this map was never touched by the rejection path) → `total_weight_approved` also gets the signer's weight added.

The same signer's weight is now counted in **both** `total_weight_rejected` and `total_weight_approved`, even though `self.total_weight` (the sum of all distinct signer weights) is used as the fixed denominator for both threshold checks in `SignerCoordinator::wait_for_signer_blocks_responses` (or equivalent gather loop) [7](#0-6) . This breaks the intended invariant that `total_weight_approved` and `total_weight_rejected` are disjoint partitions bounded by `total_weight`.

The rejection check runs first and unconditionally uses the stale/inflated `total_weight_rejected`:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { .. })
}
``` [8](#0-7) 

There is no code path that removes or decrements a signer's weight from `total_weight_rejected` once that signer later accepts — the rejection tally is permanently sticky regardless of the signer's later, valid signature. So a set of signers who initially reject (e.g., due to a transient chainstate mismatch such as the sibling/reorg races the doc describes in the pre-commit flow) and then legitimately sign after the re-check passes will have their weight counted twice: once stuck in `total_weight_rejected` forever, and once correctly in `total_weight_approved`. If enough signers follow this reject→accept sequence, `total_weight_rejected + weight_threshold` can exceed `total_weight` purely from stale/duplicated weight, even while `total_weight_approved` is simultaneously climbing toward (or has reached) `weight_threshold` from the very same signers' genuine, still-valid signatures.

### Impact Explanation
This is a liveness wedge on the miner/coordinator side: a block that is in fact receiving legitimate, valid signatures toward the 70% threshold can be declared `SignersRejected` (dead) by the coordinator because the same signers' earlier (superseded) rejections are permanently double-counted in `total_weight_rejected`, which is never reconciled against their later acceptance. This can stall block production/tenure progress even though a real supermajority of current, valid signatures exists — matching the "wedge the state machine" / liveness-wedge class called out in scope. It requires no majority collusion: a single signer switching its vote once (a normal, protocol-sanctioned event per the pre-commit re-check design) contributes to the miscount, and the effect compounds as more signers do the same during a contested tenure/reorg window.

### Likelihood Explanation
Reject→accept vote flips by an individual signer are an expected, protocol-sanctioned occurrence: the signer state machine explicitly re-runs chainstate checks and can reject a block at validate-ok time or pre-commit time and later sign a re-proposed/still-fresh version of essentially the same contested slot once conflicts go stale [4](#0-3) . Any single signer (or the miner's own gossip relay of such messages) can trigger the sequence without needing cooperation from a majority, satisfying the "one slot miner plus gossip" threat model.

### Recommendation
Gate both the `Accepted` and `Rejected` weight additions on the same `responded_signers` set (or otherwise track, per slot_id, which single bucket a signer's weight has been counted into, and move it — rather than duplicate it — when the signer's vote changes). Concretely, before adding weight in the `Accepted` branch, check `responded_signers.contains(&slot_id)`; if the signer previously contributed weight to `total_weight_rejected`, subtract that weight before adding it to `total_weight_approved` (and symmetrically for the reverse direction), ensuring a signer's weight is always counted in at most one tally at a time.

### Proof of Concept
1. Signer S (slot `k`, weight `w`) sends `BlockResponse::Rejected` for block `B`. `responded_signers.insert(k)` → `true`; `total_weight_rejected += w` [9](#0-8) .
2. The same signer S later sends `BlockResponse::Accepted` with a valid signature for the same `B` (e.g., after its own pre-commit re-check passes) [10](#0-9) .
3. `gathered_signatures.contains_key(&k)` is `false` (never touched in step 1) → `total_weight_approved += w` [2](#0-1) .
4. Now `w` is counted in both `total_weight_rejected` and `total_weight_approved`. Repeating this with enough signers whose combined `w` satisfies `total_weight_rejected + weight_threshold > total_weight` causes `SignerCoordinator` to return `NakamotoNodeError::SignersRejected` [8](#0-7) , discarding a block that is concurrently amassing genuine, valid signatures toward `total_weight_approved >= weight_threshold`.
