### Title
Unbounded zstd compression cost for `getAccountInfo`/`getMultipleAccounts` with `base64+zstd` encoding on large accounts - (File: account-decoder/src/lib.rs)

### Summary
`encode_ui_account`'s `Base64Zstd` branch compresses the full (post-slice) account data with `zstd::stream::write::Encoder` without any size cap, unlike the `Binary`/`Base58` paths which reject payloads over `MAX_BASE58_BYTES`. Since on-chain accounts can be up to `MAX_ACCOUNT_DATA_LEN` (10 MiB), a single `getAccountInfo` call against an attacker-populated large account forces the RPC thread to allocate and zstd-compress up to 10 MiB of data per request.

### Finding Description
`get_account_info` in `rpc/src/rpc.rs` (lines 534-560) resolves the bank, then does `self.runtime.spawn_blocking(... get_encoded_account(&bank, &pubkey, encoding, data_slice, None))`, which ultimately calls `encode_account` (rpc/src/rpc.rs:2575-2601) and then `encode_ui_account` (account-decoder/src/lib.rs:46-101). `encode_account` only enforces a `MAX_BASE58_BYTES` size check for `Binary`/`Base58` encodings; no equivalent check exists for `Base64Zstd`. In `encode_ui_account`, the `Base64Zstd` arm (account-decoder/src/lib.rs:67-79) creates a `zstd::stream::write::Encoder` and calls `write_all`/`finish` on `slice_data(account.data(), data_slice_config)` with no upper bound on the slice length beyond what `data_slice_config` (if supplied by the client) restricts — and `data_slice_config` is optional, so a client can simply omit it to request the full account. Accounts can be written on-chain up to `MAX_ACCOUNT_DATA_LEN = 10 * 1024 * 1024` bytes (`transaction-context/src/lib.rs:19`), reachable via ordinary `CreateAccount`/`Allocate`+`Assign` and realloc instructions subject to `MAX_PERMITTED_DATA_LENGTH`/`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` limits enforced in `programs/system/src/system_processor.rs` and `transaction-context/src/transaction_accounts.rs:309-326` — these limits cap transaction-level growth per instruction/transaction but not the final resting size of an account, which can reach the full 10 MiB over multiple (attacker's own) transactions before the victim RPC node is queried.

### Impact Explanation
A single `getAccountInfo` (or `getMultipleAccounts`) call with `encoding: base64+zstd` against a 10 MiB attacker-controlled account forces the RPC's blocking thread pool to allocate a `Vec` buffer and run zstd compression over up to 10 MiB of arbitrary data, with cost proportional to attacker-chosen data (e.g., incompressible/random data maximizes CPU time) rather than being bounded by a per-request cost/size limit. This matches the "unbounded cost for a single low-rate call" category: a low-rate (≤ 1 per `CLUSTER_SLOT_TIME_TARGET/2`) unprivileged request causes disproportionate CPU/memory consumption on the RPC thread pool, though it is bounded to `spawn_blocking` (not consensus-affecting) and capped by the fixed maximum account size (10 MiB), so it is a resource-amplification/DoS-adjacent issue on the RPC service rather than a crash or consensus violation.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs (1) to fund/write one account up to close to 10 MiB via ordinary permitted system-program instructions (no special privileges), and (2) issue a single `getAccountInfo` call with `base64+zstd` encoding against that pubkey, satisfying the "single request ≤ 1 per CLUSTER_SLOT_TIME_TARGET/2" constraint. No commitment, quota, or length-check guard currently prevents requesting `Base64Zstd` encoding of an arbitrarily large account, since the `MAX_BASE58_BYTES` guard in `encode_account` (rpc/src/rpc.rs:2581-2586) only applies to `Binary`/`Base58`.

### Recommendation
Add an explicit upper bound on the input length used for the `Base64Zstd` (and general non-base58) encode path in `encode_ui_account`/`encode_account` — e.g., reject or clamp requests where the sliced account data exceeds a configurable maximum (similar in spirit to `MAX_BASE58_BYTES` but sized appropriately for base64/zstd, such as the RPC response size limit), and/or apply a compression-time/CPU budget or streaming size cap when constructing the `zstd::stream::write::Encoder`.

### Proof of Concept
```rust
// account-decoder/src/lib.rs (test module)
#[test]
fn test_base64_zstd_large_account_unbounded_cost() {
    use {
        solana_account::AccountSharedData,
        std::time::Instant,
    };

    // Simulate the maximum permitted on-chain account size (10 MiB),
    // filled with incompressible (random-like) data to maximize zstd CPU cost.
    let data = vec![0xAAu8; 10 * 1024 * 1024];
    let account = AccountSharedData::new(1, data.len(), &Pubkey::default());
    // (populate account.data_as_mut_slice() with pseudo-random bytes in a real test)

    let start = Instant::now();
    let ui_account = encode_ui_account(
        &Pubkey::default(),
        &account,
        UiAccountEncoding::Base64Zstd,
        None,
        None, // no data_slice_config supplied by client
    );
    let elapsed = start.elapsed();

    // Assertion: a single request's cost should be bounded independent of
    // the size of attacker-controlled account data. This currently fails
    // because encode time/memory scale linearly with account size (up to 10MB)
    // with no cap enforced in the Base64Zstd branch.
    assert!(elapsed.as_millis() < 50, "single request took too long: {elapsed:?}");
    let _ = ui_account;
}
```
Expected result on current code: the assertion fails (or, run as a benchmark, shows compression time/memory scaling linearly up to the full 10 MiB with no enforced cap), confirming the missing size bound. An integration-level PoC would additionally exercise `rpc/src/rpc.rs::get_account_info` against a bank containing a 10 MiB account and measure `spawn_blocking` thread wall time per single `getAccountInfo` call with `encoding=base64+zstd`.
