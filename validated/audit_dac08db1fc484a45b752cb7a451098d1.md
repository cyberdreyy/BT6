### Title
ProgrammableBorrower deposits the full idle balance in a single `vault.deposit` without respecting `maxDeposit`, letting any ERC4626 vault user freeze `startEpoch` - (contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStartEpoch()` parks all idle underlying into the configured ERC4626 vault via a single `_depositToVault(underlyingToken.balanceOf(address(this)), 0)` call, which invokes `vault.deposit` for the entire amount. The ERC4626 spec allows vaults to enforce a per-call `maxDeposit`/`maxMint` limit; `ProgrammableBorrower` never queries or splits against that limit (the exact analog of the kernel fix: large BIOs must be split to zoned-device limits *before* reaching the target, rather than relying on the target to partially accept). When idle balance exceeds the vault's remaining deposit capacity, `startEpoch` reverts and the pool is stuck in the buffer phase — all lender funds frozen — for as long as any third-party vault user keeps the deposit cap saturated.

### Finding Description
In `ProgrammableBorrower.sol`:

- `onStartEpoch` calls `_depositToVault(underlyingToken.balanceOf(address(this)), 0)` at `contracts/strategies/idle/ProgrammableBorrower.sol:216`, and `_depositToVault` performs a single unbounded `vault.deposit(_assetAmount, address(this))` at line 380. There is no `vault.maxDeposit(address(this))` check and no chunked-deposit loop.
- The same pattern exists in `_repay` (`_depositToVault(totalRepaidAssets, ...)` at line 527) and in `_borrow` where `vault.withdraw(shortfall, ...)` at line 452 ignores `maxWithdraw` — but the start-epoch path is the exploitable one because it is on the critical epoch-state-machine path.

In `IdleCDOEpochVariant.startEpoch()`:

- `_startEpochProgrammableBorrower(_pendingWithdraws)` is invoked at `contracts/IdleCDOEpochVariant.sol:288` and `:297`. Unlike `sendFundsToBorrower`, which is wrapped in `try/catch` (lines 295–303), the programmable-borrower hook is called bare — a revert in `onStartEpoch` propagates and reverts the whole `startEpoch`. Compare with `onStopEpoch`, which does wrap `vault.withdraw` in `try/catch` and surfaces a retryable `StopEpochVaultLiquidityUnavailable` (lines 246–253). No equivalent guard exists for the deposit side.
- `startEpoch` sets `isEpochRunning = true` and `_pause()` *before* the hook, so a revert rolls everything back cleanly, but the revert is repeatable: every subsequent `startEpoch` call fails while `idle balance > vault.maxDeposit(...)`.

### Impact Explanation
Temporary freezing of all pool funds. While `startEpoch` reverts, deposits are still open (buffer phase) but no epoch can run, so withdraw requests cannot be processed and no yield accrues through the intended facility. An attacker who is merely "a user of the programmable borrower's ERC4626 vault" — an explicitly in-scope unprivileged actor — can deposit into the underlying ERC4626 vault to saturate its deposit cap (or keep a cap-limited vault perpetually saturated with flash-sized deposits each time room opens). Because the deposit is attempted atomically for the entire idle balance rather than split to `maxDeposit`, even partial cap availability reverts the whole call. Loss magnitude: the entire pool TVL is frozen for the duration of the griefing; unlike the stop-epoch path there is no retryable-degrade, no default, and no escape hatch short of the honest owner calling `setVault` — which itself reverts while `vault.balanceOf(address(this)) != 0` if the position is non-empty (line 165), and only helps when the position is zero.

Broken invariant: operations crossing into the external vault must be split to the vault's per-call limits before submission (deposit analog of `bio_split_to_limits`), so a partially-available cap cannot deadlock the epoch state machine.

### Likelihood Explanation
Requires the programmable-borrower mode (a first-class supported configuration, per `isProgrammableBorrower`/`_checkProgrammableBorrowerMode`) wired to an ERC4626 vault with a finite `maxDeposit` (common for capped vaults, e.g. MetaMorpho-style caps — the repo already integrates `MetaMorphoStrategy`). The attacker needs only to be an ordinary depositor of that vault; no privileged role is needed. Cost to sustain the grief is low since the cap can be re-saturated whenever it frees. Severity is bounded by "temporary freezing" (funds recoverable once cap pressure clears or owner migrates vault), not permanent loss.

### Recommendation
Mirror the kernel fix: split before submitting. In `_depositToVault`, loop `vault.deposit` in chunks bounded by `vault.maxDeposit(address(this))` (and treat remaining undeposited balance as on-hand rather than reverting), and similarly bound `vault.withdraw` calls in `_borrow`/`onStopEpoch` by `vault.maxWithdraw`. Optionally wrap the `onStartEpoch` hook call in `IdleCDOEpochVariant.startEpoch` in `try/catch` with a graceful fallback, matching the retryable-degrade design already used for `onStopEpoch`.

### Proof of Concept
Foundry fork-style PoC (pseudo-test, using the repo's harness conventions):

```solidity
// test/foundry/ProgrammableBorrowerSplitLimits.t.sol
contract CappedVault is ERC4626Mock {
    uint256 public cap; // maxDeposit returns cap - totalAssets
    function maxDeposit(address) public view override returns (uint256) {
        return totalAssets() >= cap ? 0 : cap - totalAssets();
    }
}

function testStartEpochFrozenByVaultDepositCap() external {
    // Setup: cdoEpoch with isProgrammableBorrower = true, borrower = ProgrammableBorrower
    // wired to CappedVault with cap = 15_000e6.
    idleCDO.depositAA(10_000 * ONE_SCALE);          // pool TVL
    _startEpochAndCheckPrices(0);                    // epoch 0 runs, funds parked in vault
    _stopEpochAndCheckPrices(0, initialApr, expected); // back to buffer; idle cash sits on ProgrammableBorrower

    // Attacker: ordinary vault user fills remaining cap headroom.
    // vault.cap = 15_000, vault holds ~10_000 => headroom ~5_000; attacker deposits 5_000
    // or, after PB holds shares, deposits enough that maxDeposit < idle balance.
    vm.prank(attacker);
    vault.deposit(headroom, attacker);               // maxDeposit(PB) now < PB idle balance

    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
    vm.prank(manager);
    vm.expectRevert();                               // vault.deposit exceeds maxDeposit
    cdoEpoch.startEpoch();                           // reverts inside onStartEpoch->_depositToVault

    assertFalse(cdoEpoch.isEpochRunning());          // stuck in buffer; repeat as long as cap saturated
}
```

Note: exact vault-cap mechanics depend on the chosen ERC4626 (the finding holds for any vault where `maxDeposit < idleBalance`), and the equivalent `maxWithdraw` gap in `_borrow`/`onStopEpoch` follow-up calls should be verified against the production vault's limit surface.
