### Title
APR0 dust withdraw request permanently bricks `stopEpoch` once a nonzero APR is set, freezing the entire vault - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. An unprivileged lender can open a 1-wei `requestWithdraw` during an APR=0 epoch, populating `apr0TotalPrincipal`. When the manager later configures a normal nonzero APR for a subsequent epoch, every `stopEpoch` call reverts inside the strategy before any borrower-funding logic runs, so the epoch can never close and no default can be triggered. All LP funds are frozen until governance manually resets `unscaledApr` back to 0. This is the direct analog of the CVE's "repeatable crash / hang" class mapped onto the epoch state machine.

### Finding Description
`requestWithdraw` routes to `_requestWithdrawApr0` whenever `unscaledApr == 0` and the pool is not closed, incrementing the global `apr0TotalPrincipal` by the request amount [1](#0-0) . The bucket is only closed inside `prepareStopEpochWithApr0`, which first enforces `if (unscaledApr != 0) revert NotAllowed()` while `_principal != 0` [2](#0-1) .

The sequencing flaw is that `unscaledApr` reflects the *upcoming* epoch's APR, set by `_setScaledApr` → `setAprsWithBuffer` at the end of a previous `stopEpoch` [3](#0-2) . So the lifecycle is:

1. Epoch N runs at `unscaledApr == 0` (zero-APR credit line, a supported mode: `_requestWithdrawApr0` and `apr0RateByEpoch` exist for it).
2. Attacker calls `cdoEpoch.requestWithdraw(dustAmount, tranche)` — any KYC'd lender or tranche holder. `apr0TotalPrincipal` becomes `dustAmount > 0`.
3. Epoch N stops fine; the bucket settles (`apr0TotalPrincipal = 0`). The attacker's receipt sits as `apr0Users[attacker].settledPrincipal`.
4. Epoch N+1: manager sets a normal nonzero APR via `stopEpoch(_newApr, ...)`, so `unscaledApr != 0`. Attacker deposits/receives tranches and calls `requestWithdraw` again — now routed through the *normal* path since `unscaledApr != 0`. **Or**, more simply, the attacker's `apr0Users.principal` from a request made while APR was 0 remains in `apr0TotalPrincipal` entering the epoch where the manager raises the APR.
5. Next `stopEpoch` calls `prepareStopEpochWithApr0`, which reads `apr0TotalPrincipal != 0` and `unscaledApr != 0` and reverts at `IdleCreditVault.sol:506-508`. This revert occurs before `getFundsFromBorrower`, `_handleBorrowerDefault`, `collectWithdrawFunds`, or `_updateAccounting` [4](#0-3) .

Because the revert happens on every `stopEpoch` invocation and `_handleBorrowerDefault` is unreachable, the protocol's own default-recovery path cannot fire. `withdrawsRequests`-backed claims also cannot proceed because `_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest` while the pool is open [5](#0-4) . No guard prevents this: there is no check in `setAprsWithBuffer`/`setApr` against a live `apr0TotalPrincipal`, and `requestWithdraw` happily accepts dust amounts (`if (_amount == 0) return` only rejects zero) [6](#0-5) .

### Impact Explanation
Temporary freezing of the entire pool TVL (all AA + BB principal plus borrower-held funds) for the duration between the APR change and remediation. `stopEpoch` and `stopEpochWithDuration` are permanently bricked while the condition holds; `startEpoch`, default handling, loss accounting, and all withdrawal claims are transitively blocked. The borrower continues to hold loaned funds with no protocol-side mechanism to force recall. Recovery requires the honest manager to notice and call `setAprsWithBuffer(0, ...)` to restore `unscaledApr == 0`, then run `stopEpoch` — a manual operational intervention the attacker can re-arm each time APR transitions from 0 to nonzero while they hold an open APR0 receipt. Attacker cost is a dust withdraw request plus gas; frozen value is unbounded (full NAV).

### Likelihood Explanation
Medium. Requires a zero-APR epoch configuration, which is an explicitly supported mode (dedicated `apr0Users`, `apr0RateByEpoch`, `apr0TotalPrincipal` accounting). Any whitelisted tranche holder can execute it with negligible cost and no collusion; the trigger is a routine manager APR change, not an exotic privileged action. The freeze is recoverable, so the impact is temporary rather than permanent loss, matching a Medium-severity DoS.

### Recommendation
In `prepareStopEpochWithApr0`, settle the APR0 bucket at zero interest when `unscaledApr != 0` (store `apr0RateByEpoch[epochNumber] = 0` and clear `apr0TotalPrincipal`) instead of reverting — APR0 users simply forgo interest they could not have accrued. Alternatively, prevent the inconsistent state: revert in `setApr`/`setAprsWithBuffer` when `apr0TotalPrincipal != 0` and the new `unscaledApr` is nonzero, or reject new APR0-flagged requests when a pending APR transition exists. Add a regression test covering APR0-request → APR-raise → `stopEpoch` sequencing.

### Proof of Concept
```solidity
// Foundry fork test against a live epoch vault configured at 0% APR.
function testApr0DustRequestBricksStopEpoch() external {
    // Epoch N: unscaledApr == 0 (APR0 mode). Attacker is a normal KYC'd lender.
    uint256 tranches = _depositWithUser(attacker, 1e6); // dust-scale deposit
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(tranches, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // Manager ends epoch N and sets a normal APR for epoch N+1.
    _stopCurrentEpochWithApr(10e18); // sets unscaledApr != 0

    // Attacker (or any prior APR0 holder whose principal was still open)
    // re-opens an APR0-flagged receipt before the APR change lands, or simply
    // relies on a still-open principal bucket. Then next stopEpoch:
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Every subsequent attempt reverts identically; borrower cannot be marked
    // defaulted, claims cannot advance (epochNumber never bumps). TVL frozen
    // until manager calls strategy.setAprsWithBuffer(0, ...) to unbrick.
}
```
