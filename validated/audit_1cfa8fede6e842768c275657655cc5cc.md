### Title
Changing `idleCDO` via `setWhitelistedCDO` permanently freezes pending withdraw claims and strategy-token receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` binds every claim/transfer path to a single mutable `idleCDO` address. The owner can rotate it at any time via `setWhitelistedCDO()` with no check that pending withdraw receipts, APR0 receipts, or in-flight epoch flows are settled. All privileged entry points into the vault — deposits, receipt-token transfers, and CDO-driven claim plumbing — are gated by `msg.sender == idleCDO`, so pointing `idleCDO` at a new CDO strands every claim that still lives on the old CDO, exactly like the `bribeVault` rotation that orphaned ETH rewards in RewardDistributor.

### Finding Description
The vault stores `idleCDO` as a plain state variable and exposes `setWhitelistedCDO(address _cdo)` (`contracts/strategies/idle/IdleCreditVault.sol:954-957`), which only checks `_cdo != address(0)` before overwriting. Several critical paths then hard-require `msg.sender == idleCDO`:

- `_transfer` reverts `NotAllowed` unless the caller is `idleCDO` (lines 939-942), so strategy/receipt tokens become non-movable by the previous CDO the moment the pointer flips.
- `_onlyIdleCDO` (lines 968-972) guards the deposit/epoch callbacks; the old CDO can no longer settle its outstanding epoch state.
- `_ensureDefaultRecoveryInitialized` reads `epochEndDate()` and `defaulted()` from `IIdleCDOEpochVariant(idleCDO)` (lines 927-929). After rotation it queries the new CDO's epoch state, which does not reflect the epoch in which users' `withdrawsRequests`, `withdrawsRequestsByEpoch`, `instantWithdrawsRequestsByEpoch`, and `apr0Users` receipts were created, and reverts `NotAllowed` if the new CDO reports a running epoch or default — blocking initialization and any claim path that depends on it.

There is no equivalent of the external report's "all funds withdrawn" check: `setWhitelistedCDO` does not verify `pendingWithdraws == 0`, `pendingInstantWithdraws == 0`, or `apr0TotalPrincipal == 0`, and does not verify that `defaultRecoveryReserve` claims are drained.

### Impact Explanation
Users holding pending normal/APR0/instant withdraw receipts created under the previous CDO can lose the ability to claim funded underlyings: receipt transfers revert (`_transfer` guard), epoch-state reads hit the wrong contract, and recovery initialization can permanently revert. Because receipt claims are address-bound (`canTransfer` can never be re-enabled per lines 944-951), users cannot work around the freeze by transferring receipts. Result is permanent freezing of unclaimed yield/principal for all pending receipts at the time of rotation — quantified as `pendingWithdraws + pendingInstantWithdraws + apr0TotalPrincipal + postDefaultRequests` underlyings.

### Likelihood Explanation
The trigger is a routine privileged action (migrating a vault to a new CDO implementation — a realistic upgrade path, since `setWhitelistedCDO` exists precisely for that purpose) executed while any receipt is pending, which is the normal state of an epoch vault. No attacker action is required beyond holding an unclaimed receipt; the bug class is identical to the confirmed M-07, where a legitimate setter stranded existing claims.

### Recommendation
Block rotation while claims are outstanding: require `pendingWithdraws == 0 && pendingInstantWithdraws == 0 && apr0TotalPrincipal == 0 && postDefaultRequests == 0` (and the vault's underlying balance covers no unclaimed reserve) in `setWhitelistedCDO`, or make `idleCDO` immutable after the first non-zero set. Alternatively, snapshot the epoch state needed by `_ensureDefaultRecoveryInitialized` rather than reading it live from the rotated CDO.
