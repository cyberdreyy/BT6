### Title
Already-paid instant-withdraw receipts stay in per-epoch claim accounting, inflating default-recovery basis and stranding the reserve - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the CVE (a "user buffer" written to/cleared with the wrong primitive), `IdleCreditVault` never clears the per-epoch instant-withdraw ledgers when a funded receipt is paid out. `claimInstantWithdrawRequest` only zeroes the aggregate `instantWithdrawsRequests[_user]` [1](#0-0) , while `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (credited at request time [2](#0-1) ) keep counting already-paid underlyings. On a same-epoch borrower default, `defaultPendingClaimBasis` re-adds those ghost receipts to the recovery basis [3](#0-2)  and `_defaultPrefundedInstantReserve` treats them as still-held backing [4](#0-3) .

### Finding Description
1. During a running epoch `E` (instant mode), user A calls `requestInstantWithdraw`; the CDO funds the queue via `collectInstantWithdrawFunds`, which only decrements `pendingInstantWithdraws` [5](#0-4) .
2. A claims via `claimInstantWithdrawRequest`: the strategy tokens are burned and `instantWithdrawsRequests[A]` is reset, but `instantWithdrawsRequestsByEpoch[A][E]` and `instantWithdrawClaimsByEpoch[E]` are never decremented.
3. Other users (B) request instant withdrawals in the same epoch that remain partially unfunded (`pendingInstantWithdraws != 0`).
4. The borrower defaults in epoch `E`; `finalizeDefaultRecovery` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[E]`, which still includes A's already-paid `X`. `prefundedReserve = instantBasis - pendingInstant` counts `X` as underlying held by the strategy even though it was transferred to A.
5. `defaultRecoveryReserve` is therefore overstated by `X` relative to the actual token balance, and `defaultRecoveryPrice` is diluted across the phantom basis.
6. When claimants call `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` → `_transferDefaultRecovery` [6](#0-5) , the last `X` worth of claims reverts on insufficient balance and the phantom `X` is stranded in the strategy forever (only recoverable by owner `transferToken`).

### Impact Explanation
Every underyling paid to an instant-withdraw claimant during an epoch that later defaults is double-counted into the default-recovery basis. This permanently dilutes `defaultRecoveryPrice` for all defaulted-epoch claimants and leaves the tail claimants unpayable — a quantified loss equal to the total instant claims already paid in the default epoch, with residual funds frozen as unreachable "recovery dust".

### Likelihood Explanation
Requires only ordinary unprivileged users: an instant-withdraw request that is funded and claimed during a running epoch, plus a same-epoch borrower default with a partially unfunded instant queue — a normal configuration (instant withdrawals are an explicitly supported mode). No malicious privileged role, oracle manipulation, or timing beyond honest manager calls is needed.

### Recommendation
When a funded instant receipt is claimed in `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` (and symmetrically ensure paid receipts are excluded from `defaultPendingClaimBasis` / `_defaultPrefundedInstantReserve`), mirroring how `_claimDefaultedInstantWithdrawRequest` already clears both ledgers [7](#0-6) .

### Proof of Concept
Foundry fork PoC (sketch, modeled on `test/foundry/IdleCDOEpochQueue.t.sol` instant-withdraw tests):

```solidity
function testStaleInstantReceiptInflatesDefaultBasis() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);          // epoch #1 buffer
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    uint256 amountA = 100e6;
    address userA = makeAddr('userA');
    _depositWithUser(userA, amountA);
    address userB = makeAddr('userB');
    _depositWithUser(userB, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();                    // epoch #1 running

    // userA requests instant withdraw; CDO funds it; userA claims
    _requestInstantWithdraw(userA, amountA);  // instantWithdrawClaimsByEpoch[1] += amountA
    _fundInstantWithdraws(amountA);           // collectInstantWithdrawFunds, pendingInstantWithdraws -> 0
    skip(101);
    vm.prank(userA);
    cdoEpoch.claimInstantWithdrawRequest();   // paid; per-epoch ledgers NOT cleared

    // userB requests instant withdraw, only partially funded
    _requestInstantWithdraw(userB, 100e6);    // claimsByEpoch[1] = amountA + amountB
    // borrower defaults in same epoch; finalizeDefaultRecovery()
    _defaultAndFinalize();                    // basis includes userA's ghost amountA

    // defaultRecoveryReserve recorded > strategy underlying balance by amountA
    assertGt(strategy.defaultRecoveryReserve(), underlying.balanceOf(address(strategy)),
        'reserve overstated by paid instant claim');

    // userB's defaulted claim reverts / underpays; tail of reserve stranded
    vm.prank(userB);
    cdoEpoch.claimInstantWithdrawRequest();   // short by ~amountA or reverts
}
```

Uncertainty: exact CDO entry points (`requestInstantWithdraw`, default flow helpers) follow the existing test helpers; the core defect — per-epoch instant ledgers never cleared on funded claim while `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` still read them — is confirmed in the source cited above.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
