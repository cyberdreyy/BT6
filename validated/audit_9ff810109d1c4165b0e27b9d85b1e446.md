### Title
Loss-adjusted withdrawal receipts are keyed to the wrong epoch, letting defaulted/impaired receipts claim at par while later healthy receipts absorb the haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The ImageMagick bug is a short-decompression flaw: the PSD handler reads a buffer that was only partially filled, leaking data the caller never supplied. The credit-vault analog is an epoch-index mismatch in `IdleCreditVault`: withdraw receipts are stored under the *request* epoch (`withdrawsRequestsByEpoch[user][epochNumber]` at request time), while `collectWithdrawFunds` records the funded haircut under the *post-increment* epoch (`lossRecoveryPriceByEpoch[epochNumber]` at stop time, after `prepareStopEpochWithApr0` has advanced `epochNumber`). Claims therefore read a stale/zero slot — the "uninitialized" data — and fall through to the par-paying funded path, while the stored haircut lands on the next epoch's innocent requesters.

### Finding Description
In `requestWithdraw`, a user's receipt is recorded under the current epoch and `lastWithdrawRequest[_user] = currentEpoch`. Requests are only possible during the buffer period, so `currentEpoch` is the epoch that is *about to run*. [1](#0-0) 

In `IdleCDOEpochVariant._stopEpoch`, the strategy's `prepareStopEpochWithApr0` runs first (this is where `epochNumber` advances — confirmed by tests asserting `epochNumber()` equals the pre-stop value + 1 after `stopEpoch`), and only later does `collectWithdrawFunds(_pendingWithdraws)` execute inside the `getFundsFromBorrower` try block. `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]`, i.e. under the *new* epoch number, not the epoch under which the receipts were stored. [2](#0-1) [3](#0-2) 

At claim time, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the request epoch — finds 0 (the haircut was stored one slot higher), and returns 0. The claim then falls through to `_claimFundedWithdrawRequest`, whose only gate is `epochNumber > lastWithdrawRequest[_user]`, which is satisfied. The user is paid the **full un-haircutted** `claimBasis` from strategy underlyings even though the borrower only funded `claimBasis * lossRecoveryPrice`. [4](#0-3) [5](#0-4) 

Symmetrically, the non-zero `lossRecoveryPriceByEpoch[E+1]` left behind matches the epoch under which *next-buffer* requesters' receipts are stored, so an unrelated user requesting in the following buffer inherits a haircut meant for the previous epoch and is underpaid. The `requestWithdraw` guard that is supposed to force claiming a loss-adjusted receipt before opening a new one also reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]` (the wrong, zero slot) and never triggers. [6](#0-5) 

### Impact Explanation
Direct theft / insolvency. When `stopEpochWithDuration` (or any loss-path stop where `collectWithdrawFunds` receives less than `pendingBasis`) is used, every pending withdrawer claims 100% of their receipt while the strategy only received the haircutted amount. The difference is paid out of underlyings belonging to the default recovery reserve, instant-withdraw claimants, or other funded receipts — whichever balance is present. Quantified loss per receipt: `claimBasis * (1 - lossRecoveryPrice)`. Additionally, next-epoch requesters are permanently underpaid by the orphaned haircut entry, which is theft of unclaimed yield with no recovery path since there is no mechanism to rewrite `lossRecoveryPriceByEpoch`.

### Likelihood Explanation
Requires only that owner/manager call `stopEpochWithDuration` with `_lossAmount > 0` while `pendingWithdraws > 0` — an explicitly supported honest-manager flow (manager is honest, not the attacker). The attacker is an ordinary KYC'd tranche holder who calls `requestWithdraw` during the buffer and `claimWithdrawRequest` after the stop. No privileged misbehavior, no oracle manipulation, no timing race needed; the miskeying is deterministic on every loss-adjusted stop.

### Recommendation
Key the loss record to the epoch the receipts were filed under. Either write `lossRecoveryPriceByEpoch[epochNumber - 1]` in `collectWithdrawFunds` (the epoch that was running when the receipts matured), or store the funding epoch on each receipt. Add a regression test: request in buffer, `stopEpochWithDuration` with a partial loss, assert the claim pays exactly `claimBasis * lossRecoveryPrice` and that a new request in the following epoch is not haircutted.

### Proof of Concept
Reproducible Foundry fork PoC sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossHaircutKeyedToWrongEpoch() external {
    uint256 amount = 100_000 * ONE_SCALE;
    address victim = makeAddr('victim');
    _depositWithUser(victim, amount, true);

    // buffer of epoch 0: request withdraw, receipt stored under epochNumber == 0
    vm.prank(victim);
    uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);

    // borrower funds only 50% of pendingWithdraws via loss path
    uint256 loss = cdoEpoch.getContractValue() / 2; // partial loss
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, epochDuration, loss);

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    // haircut was recorded under the NEW epoch, not the request epoch
    assertEq(vault.lossRecoveryPriceByEpoch(0), 0);
    assertGt(vault.lossRecoveryPriceByEpoch(1), 0);
    assertLt(vault.lossRecoveryPriceByEpoch(1), 1e18);

    // victim claims at PAR instead of haircut: overpayment drained from strategy
    uint256 balPre = underlying.balanceOf(victim);
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(victim) - balPre, basis, 'claimed un-haircutted');
}
```

Note: I could not read `prepareStopEpochWithApr0` directly to confirm it is where `epochNumber` increments (only two `epochNumber =` assignments exist in `IdleCreditVault.sol`, and the test at `IdleCreditVault.t.sol:921` confirms the increment happens inside `_stopEpoch` before `claimEpoch` is usable). If the increment were instead located after `collectWithdrawFunds`, the keys would match and this finding would not hold — that single line ordering is the load-bearing assumption to verify.

    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
