### Title
Post-default instant-withdraw receipts bypass recovery routing and can drain the default recovery reserve - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The jsonwebtoken bug is a classic "present but unrecognized state is treated as absent": a malformed `nbf` claim deserializes to `FailedToParse`, and the validator's `matches!(claims.nbf, TryParse::Parsed(_))` check silently skips it, so `validate_nbf = true` is bypassed. The closest analog in idle-tranches is in `IdleCreditVault.requestInstantWithdraw`: the `defaultRecoveryFinalized` state exists on-chain but is never matched in this function, so a post-default instant request is processed as if it were a normal, funded receipt. `requestWithdraw` explicitly routes post-default requests into `postDefaultRequests` at lines 247-257; `requestInstantWithdraw` at lines 356-375 skips that branch entirely.

### Finding Description
When the CDO finalizes a borrower default via `finalizeDefaultRecovery` (lines 661-710), the strategy holds `defaultRecoveryReserve` and pays claims through `defaultRecoveryPrice`. `requestWithdraw` correctly treats the post-default state as a distinct case: it requires the user to have no outstanding receipts and routes the request into `postDefaultRequests`, paid 1:1 from the reserve without increasing `pendingWithdraws` (lines 247-258).

`requestInstantWithdraw` (lines 356-375) performs no such check. It burns the CDO's strategy tokens, mints a full receipt to the user, increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` — exactly as during a healthy epoch. `claimInstantWithdrawRequest` (lines 380-393) then burns the aggregate receipt and calls `_transferFundedClaim(_user, amount)`, which pays at par from the strategy's underlying balance — the same balance that backs `defaultRecoveryReserve`.

An attacker who holds tranche tokens after default finalization can call `IdleCDOEpochVariant.requestWithdraw`, which takes the instant path when `lastEpochApr > currentApr + instantWithdrawAprDelta` (IdleCDOEpochVariant.sol lines 761-770; post-default `unscaledApr` is typically 0/lowered, so the delta condition is satisfiable), mint a receipt, then call `claimInstantWithdrawRequest` (IdleCDOEpochVariant.sol lines 975-979) and withdraw un-haircut underlying directly out of the recovery reserve.

### Impact Explanation
Direct theft: each post-default instant receipt converts defaulted tranche tokens — which should only be worth `defaultRecoveryPrice` — into a par claim on the strategy's underlying. The attacker extracts up to their full pre-haircut basis per request, drawn from `defaultRecoveryReserve` that belongs to honest defaulted-epoch claimants, leaving them with unbacked recovery claims (insolvency of the reserve). Loss is bounded by the attacker's tranche balance and the reserve size, but requires no privileged role. Caveat: severity depends on whether `_transferFundedClaim` isolates `defaultRecoveryReserve` (its body was not fully inspected — if it subtracts the reserve, impact collapses to a revert), and on `allowInstantWithdraw`/`isInterestMinted` remaining enabled post-default.

### Likelihood Explanation
Reachable by any KYC-passed tranche holder with unprivileged calls only: deposit → default occurs (borrower behavior is honest; a real default scenario suffices, e.g., stopEpochWithDuration or repayment shortfall) → `finalizeDefaultRecovery` → `requestWithdraw` taking the instant path → `claimInstantWithdrawRequest`. The missing guard is a clear asymmetry with `requestWithdraw`'s post-default branch, indicating the state was overlooked rather than intentionally skipped. Main uncertainty is whether a post-default epoch continues far enough for the claim path and whether the funded-claim transfer draws on the reserve.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert or route the amount into `postDefaultRequests`-style reserve-backed accounting, and prevent `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` from growing after finalization. Additionally, ensure `_transferFundedClaim` can never pay out `defaultRecoveryReserve` for unfunded receipts (track funded vs. unfunded instant receipts per epoch post-default).

### Proof of Concept
```solidity
// Foundry fork test sketch (contracts: IdleCDOEpochVariant + IdleCreditVault)
function test_PostDefaultInstantWithdrawDrainsRecovery() external {
    // 1. Deposit as AA lender, start epoch, borrower defaults.
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);
    // borrower fails to repay; manager stops epoch -> defaulted
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // repayment shortfall path -> defaulted()
    // 2. Finalize default recovery (reserve funded at recoveryPrice < 1)
    vm.prank(manager);
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);
    assertTrue(strategy.defaultRecoveryFinalized());
    uint256 reserveBefore = strategy.defaultRecoveryReserve();

    // 3. Attacker tranche holder requests withdraw; APR dropped -> instant path
    uint256 trancheBal = AAtranche.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
    // receipt minted at par into instantWithdrawsRequests, pendingInstantWithdraws grew
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // 4. Attacker claims: burns receipt, _transferFundedClaim pays from strategy balance
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = underlying.balanceOf(attacker) - balPre;

    // 5. Reserve drained for honest claimants
    assertGt(stolen, 0);
    assertLt(strategy.defaultRecoveryReserve() + /* spent */ stolen, reserveBefore + stolen);
}
```
Expected: `claimInstantWithdrawRequest` pays `amount` at par even though no borrower funding ever backed the post-default receipt, transferring default recovery reserve to the attacker.
