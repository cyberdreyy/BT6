### Title
`claimInstantWithdrawRequest` never clears per-epoch instant-receipt counters, inflating the default-recovery basis and price - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analog of the refcount-leak bug class (a counter is incremented on acquisition but never decremented on release): `requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`, but the normal funded claim path `claimInstantWithdrawRequest` only clears the aggregate `instantWithdrawsRequests[_user]` — the per-epoch counters leak. If a default is later finalized in the same epoch while another user's instant request is still unfunded (`pendingInstantWithdraws != 0`), `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` read the stale counters, overstating both `totalBasis` and `reserveAmount`. `defaultRecoveryPrice` is then computed against phantom funds, overpaying early recovery claimants and leaving the reserve unable to pay later legitimate claims.

### Finding Description
Relevant code:

- `requestInstantWithdraw` writes three ledgers per request (`IdleCreditVault.sol:366-374`):
  - `instantWithdrawsRequests[_user] += _amount`
  - `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount`
  - `instantWithdrawClaimsByEpoch[epochNumber] += _amount`
- `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) clears only `instantWithdrawsRequests[_user] = 0` and burns receipt tokens. It never touches `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`. Compare with `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`), which decrements all three.
- On default finalization (`finalizeDefaultRecovery`, `IdleCreditVault.sol:661-710`):
  - `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (`:646-648`).
  - `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` using the same stale `instantWithdrawClaimsByEpoch` (`:716-723`), counting already-paid-out funds as reserve held by the strategy.
  - `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (`:688`) is computed against a reserve that includes tokens already transferred to users, and `defaultRecoveryReserve` is set to that inflated `reserveAmount` (`:691`).

Broken invariant: one receipt one payout / reserve solvency. The per-epoch claim counters double-count instant receipts that were already funded and claimed at par, so the recovery price implicitly treats paid-out underlying as still reserved.

Attack sequence (instant mode, running epoch N):
1. Epoch N is running with instant withdrawals enabled (`setInstantWithdrawParams`).
2. Attacker (KYC'd lender) requests instant withdraw; `instantWithdrawClaimsByEpoch[N] += A`.
3. CDO collects funds via `collectInstantWithdrawFunds` (drops `pendingInstantWithdraws`), attacker calls `claimInstantWithdrawRequest` and is paid in full. `instantWithdrawClaimsByEpoch[N]` still equals `A` (leak).
4. Victim requests instant withdraw in the same epoch N (`instantWithdrawClaimsByEpoch[N] += V`, `pendingInstantWithdraws += V`) but it is only partially/never funded before epoch end.
5. Borrower defaults; manager calls `finalizeDefault`. In `finalizeDefaultRecovery`, `pendingInstantWithdraws != 0`, so basis includes `A + V` and prefunded reserve includes `(A + V) - pendingInstant`, i.e. `A` phantom tokens plus the legitimately prefunded part.
6. `defaultRecoveryPrice` is computed using reserve that does not exist. Early `_claimDefaultedInstantWithdrawRequest` / `_claimDefaultedWithdrawRequest` claimants are paid at the inflated price; once the strategy's real `underlyingToken` balance is exhausted, subsequent `_transferDefaultRecovery` calls revert — permanently freezing the remaining claimants' recovery.

Guards do not stop this: `defaultInstantWithdrawsFinalized` is correctly set from `pendingInstantWithdraws != 0` (`:696`), and the revert in `_claimDefaultedInstantWithdrawRequest` for the already-claimed attacker (`_burn` on a zeroed receipt balance, `:854`) does not prevent the reserve from being overcommitted to other users. The attacker profits indirectly only through dilution mechanics; the primary impact is inflated recovery price causing insolvency of `defaultRecoveryReserve` — last claimants lose their recovery payout entirely.

### Impact Explanation
Permanent loss of default-recovery funds for claimants whose claims are processed after the reserve's real balance is drained. The overpayment equals the stale, already-paid instant claim amount `A` times `defaultRecoveryPrice / RECOVERY_FULL`. Any unprivileged lender able to perform an instant withdrawal in the default epoch can create this stale basis; no privileged role required.

### Likelihood Explanation
Requires (a) instant withdrawals enabled, (b) a funded-then-claimed instant request in the same epoch in which (c) another instant request remains unfunded at epoch end and (d) the borrower defaults and `finalizeDefaultRecovery` runs with `pendingInstantWithdraws != 0`. This is a specific but plausible configuration (prefunded/partial-funding instant mode is an explicit feature), and the leak is unconditional — every normal instant claim leaves stale epoch counters.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers symmetrically with `_claimDefaultedInstantWithdrawRequest`: decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount (using the user's recorded request epoch, not necessarily the current `epochNumber`). Alternatively, have `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` derive the instant basis from live receipts rather than the cumulative `instantWithdrawClaimsByEpoch` counter.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style
function testInstantClaimLeakInflatesRecoveryPrice() external {
    _useStandardEpochVariant();              // instant-capable variant
    _stopCurrentEpochWithApr(10e18);
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false); // 100s delay

    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    uint256 depA = 50e6, depV = 50e6;
    uint256 tA = _depositWithUser(attacker, depA);
    uint256 tV = _depositWithUser(victim,   depV);

    vm.prank(manager);
    cdoEpoch.startEpoch();                   // epoch N running

    // Attacker requests instant withdraw; CDO funds it fully
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tA, address(AAtranche));
    uint256 aAmt = strategy.instantWithdrawsRequests(attacker);
    deal(defaultUnderlying, address(cdoEpoch), aAmt);
    vm.prank(address(cdoEpoch));
    strategy.collectInstantWithdrawFunds(aAmt);
    vm.warp(block.timestamp + 101);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();  // paid in full

    // BUG: per-epoch counters not cleared
    uint256 epoch = strategy.epochNumber();
    assertGt(strategy.instantWithdrawClaimsByEpoch(epoch), 0);

    // Victim requests instant withdraw in same epoch, left unfunded
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(tV, address(AAtranche));

    // Borrower defaults; finalize recovery
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                // triggers default path
    _checkDefault();
    uint256 recovered = /* partial recovery */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // defaultRecoveryPrice is inflated by attacker's already-paid A:
    // reserveAmount counts A as "prefunded" though tokens were paid out.
    // Early claimants drain real underlying; later _transferDefaultRecovery
    // reverts, freezing remaining recovery claims.
    uint256 price = strategy.defaultRecoveryPrice();
    uint256 realReserve = IERC20Detailed(defaultUnderlying).balanceOf(address(strategy));
    assertGt(strategy.defaultRecoveryReserve(), realReserve); // overcommitted reserve
}
```
The key assertion — `instantWithdrawClaimsByEpoch(epoch) != 0` after a fully claimed and paid instant withdrawal — is the refcount-leak analog, and it propagates into `defaultRecoveryReserve > actual balance`, producing overpayment of early claims and permanent freezing of later ones.
