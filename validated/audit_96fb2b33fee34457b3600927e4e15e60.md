### Title
Client-controlled `message_id` collision in gateway legacy WebAPI handler enables cross-user response hijacking and response denial - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway's legacy WebAPI trigger handler stores pending user callbacks in a shared map keyed solely by the `message_id` supplied inside the client's own signed request payload. Because this ID is fully attacker-controlled and never checked for uniqueness/ownership against other in-flight requests, one unprivileged user can pick a `message_id` already in use by another in-flight request, silently overwrite that pending callback slot, and either (a) cause the victim's request to receive no response (its callback is discarded/orphaned), or (b) receive the response intended for the victim's request when the DON eventually replies. This is the same bug class as the DittoETH finding: a reusable/attacker-influenced identifier is trusted to reference a specific stateful resource without verifying that the caller legitimately "owns" that identifier slot, letting an unprivileged actor manipulate or hijack another user's pending state.

### Finding Description
When the gateway receives a legacy (DON-ID-based) JSON-RPC user request, `gateway.ProcessRequest` decodes it via `JsonRPCCodec.DecodeJSONRequest`, which sets: [1](#0-0) 

Here `msg.Body.MessageId = request.ID` is taken verbatim from the client-supplied JSON-RPC `id` field, with only a length check (`<= 200` chars) applied in `gateway.ProcessRequest`: [2](#0-1) 

The message is signed by the caller (`Message.Validate()` recovers the signer of the message body via `ExtractSigner`), but this signature only proves *some* keypair authored the message — any unprivileged client requesting a workflow trigger controls their own key and thus fully controls the `message_id` value they submit. Validation does not check that the `message_id` is unique or "owned" by the requester relative to other pending requests: [3](#0-2) 

The legacy handler then stores the callback for this request directly under the attacker-controlled key, unconditionally overwriting whatever was previously stored there: [4](#0-3) 

When a DON node later responds to a `web_api_trigger` message, the handler looks up and deletes the callback purely by `message_id` and forwards the response to whichever callback is currently occupying that slot: [5](#0-4) 

This mirrors the DittoETH root cause exactly: a reused/attacker-supplied identifier (`shortOrderId` → here `message_id`) is used to reference a resource slot (a short order → here a pending HTTP callback) without verifying that the party currently acting via that ID actually owns/created the current occupant of that slot.

### Impact Explanation
- **Response denial (censorship analog to "cancel")**: If Attacker A submits a request reusing Victim B's still-pending `message_id`, B's `savedCallback` entry is overwritten. When the DON eventually responds to B's original request, `handleWebAPITriggerMessage` finds A's callback (or nothing, if A's own request already completed) instead of B's — B's caller HTTP connection will hang until any recovery/timeout expires without ever getting a legitimate reply, exactly like the referenced report canceling another user's order.
- **Cross-user response confusion**: Conversely, if the DON responds to what it believes is B's trigger message, but the map slot has been overwritten with A's callback, A can receive the DON's response payload intended to correlate with B's original request/trigger context.
- Both are explicitly allowed impact categories ("cross-user response confusion", "allowlist/handler" bug in the internet-facing gateway).

### Likelihood Explanation
Requires only submitting a normal, validly-self-signed workflow trigger HTTP request to the gateway's user-facing endpoint (unprivileged, unauthenticated beyond having any workflow keypair) with a chosen/guessed `message_id`. Because message IDs are supplied by the requester and only bounded to ≤200 characters with no uniqueness enforcement, an attacker who can predict or observe a victim's in-flight `message_id` (e.g., low-entropy IDs, or a race where the attacker races the same well-known/short ID) can trigger the collision. The severity is bounded to whatever transits this legacy DON-ID handler (still reachable via `isLegacyRequest` branch in `ProcessRequest`), while the newer JSON-RPC v2 path uses JWT nonce/jti-based replay protection (`ErrRequestAlreadySeen`, "token has already been used") that this legacy path lacks.

### Recommendation
1. Scope the `savedCallbacks` map key by `(sender, message_id)` (or DON/service + verified signer address) rather than by `message_id` alone, so that one signer cannot collide with another's pending request slot.
2. On insertion, reject (rather than silently overwrite) the request if an entry already exists under the resulting key, returning an explicit "duplicate/in-flight request" error, similar to the `ErrRequestAlreadySeen` / "token has already been used" protection already implemented for the v2 JSON-RPC trigger handler.
3. Consider migrating the legacy WebAPI handler off the same replay/duplicate-protection mechanism used by the v2 HTTP trigger handler (`workflow_metadata_handler`/JWT `jti` tracking) for consistency.

### Proof of Concept
1. Victim submits a legacy `web_api_trigger` request to the gateway's user HTTP endpoint with `message_id = "shared-id-123"`, signed with their own key; `handler.HandleLegacyUserMessage` stores `savedCallbacks["shared-id-123"] = victimCallback` and forwards to DON nodes.
2. Before the DON responds, Attacker sends their own legacy `web_api_trigger` request also using `message_id = "shared-id-123"` (self-signed with attacker's own key — no restriction prevents choosing this value). `handler.HandleLegacyUserMessage` overwrites `savedCallbacks["shared-id-123"] = attackerCallback`, discarding the victim's callback reference.
3. When a DON node responds to either message with `message_id = "shared-id-123"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["shared-id-123"]`, finds the attacker's callback, deletes the entry, and delivers the response to the attacker's HTTP connection — the victim's original HTTP request never receives a legitimate response (denial), while the attacker may receive a response correlated with the victim's triggered workflow execution (cross-user confusion).

func (*JsonRPCCodec) DecodeJSONRequest(request jsonrpc2.Request[json.RawMessage]) (*Message, error) {
	var msg Message
	err := json.Unmarshal(*request.Params, &msg)
	if err != nil {
		return nil, err
	}
	msg.Body.MessageId = request.ID
	msg.Body.Method = request.Method
	return &msg, nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
