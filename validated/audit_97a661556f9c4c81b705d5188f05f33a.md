### Title
Signer block-acceptance signatures omit chain ID / domain separation, enabling cross-network signature reuse - (File: `libsigner/src/v0/messages.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
`BlockAccepted` (a signer's affirmative vote on a block, which is also the exact signature embedded on-chain in `NakamotoBlockHeader.signer_signature`) is produced by signing the raw `signer_signature_hash` with no chain ID or domain-separation tag. This is inconsistent with `BlockRejection`, which explicitly binds `chain_id` into its signed digest via a structured-data domain. Because the digest that signers actually sign for block *approval* commits to none of {chain_id, mainnet/testnet flag, reward-cycle}, a signature produced by a signer key for one network's block can be a valid signature for a byte-identical header on a different network/context that shares the same key — the exact "verification not taking into account chain ID" bug class from the Tendermint advisory.

### Finding Description
The message a signer actually signs to accept a block is computed by: [1](#0-0) 

which calls `block.header.signer_signature_hash()`. That hash is computed purely from header fields — version, chain_length, burn_spent, consensus_hash, parent_block_id, tx_merkle_root, state_index_root, timestamp, miner_signature, pox_treatment, and (in Epoch 4.0+) problematic_txs: [2](#0-1) 

Notice `chain_id` (mainnet vs testnet, or any distinct network identifier) is **not** part of this preimage at all. This same raw signature is what the node ultimately checks when it validates the block header's `signer_signature` vector against a `RewardSet`: [3](#0-2) 

`verify_signer_signatures` takes only `reward_set` and `epoch_id` — no `chain_id` parameter — so the on-chain consensus check for signer approval is likewise chain-ID-agnostic; the only place chain_id is actually checked is in the `NakamotoBlockProposal::validate` RPC path (`postblock_proposal.rs`), which is a local sanity check on the block proposal that a compromised/misconfigured signer or node could bypass, not something enforced by the signature primitive itself: [4](#0-3) 

By contrast, the sibling message type `BlockRejection` explicitly recognizes the need for domain separation and binds `chain_id` into what is signed: [5](#0-4) 

This asymmetry shows the codebase is aware that raw hash-signing needs domain separation to prevent cross-context signature validity, yet the *acceptance* signature — the one that actually counts toward the 70% weight threshold and gets embedded into the canonical block header — was left unprotected.

### Impact Explanation
If the same signer's Stacks private key is used to participate in more than one network/context that shares this codebase (e.g., mainnet and a testnet/subnet/fork sharing the same signer registration key, or two chains that briefly diverge only in `chain_id`), a signature a signer produces for a block on one network is a byte-for-byte valid ECDSA signature recoverable to that signer's public key for any other block with an identical `signer_signature_hash` preimage on the other network. This is a cross-context-valid signature: gossiped `BlockAccepted` messages (and the equivalent bytes embedded in `NakamotoBlockHeader.signer_signature`) carry no cryptographic commitment to which network/chain they were produced for. This falls under the "cross-context-valid signature" critical-impact category, since it breaks the fundamental equality that a signer's signature attests specifically to acceptance of a block *on a particular chain*.

### Likelihood Explanation
Exploitation requires that a signer's key material and its acceptance signature be replayable across two distinguishable contexts where the header bytes can be made to coincide (or nearly coincide, since `consensus_hash`/`parent_block_id`/`tx_merkle_root` are attacker/miner-influenced fields that a single block-producing entity does control). This is most directly a concern for any deployment reusing signer keys across a mainnet/testnet pair or a mainnet/appchain pair — a configuration the codebase does not appear to forbid, and one for which no other in-repo defense-in-depth compensates, since neither `signer_signature_hash()` nor `verify_signer_signatures()` incorporate chain identity. It is a lower-likelihood, structural weakness rather than a trivially exploitable one on a single canonical network, but it precisely mirrors the reported bug class (a verification path lacking chain-ID binding) and is reachable purely through the in-scope signer gossip/signing code.

### Recommendation
Bind chain identity into the digest that signers actually sign for block acceptance, matching what was already done for `BlockRejection`:
- Compute `signer_signature_hash()` (or a wrapper used specifically for the gossip/on-chain signature) using a structured-data domain that includes `chain_id`/mainnet flag, analogous to `make_structured_data_domain("block-rejection", "1.0.0", chain_id)`.
- Thread `chain_id` through `NakamotoBlockHeader::verify_signer_signatures` so the on-chain acceptance check also verifies the signature was produced against the correct network context, not just against the correct reward set.
- Audit any other raw-hash-and-sign call sites in `stacks-signer`/`libsigner` for the same missing domain separation.

### Proof of Concept
Conceptual (not directly runnable without a second deployed network sharing signer keys):
1. Operate signer key `K` registered in the reward set of both Network A (`chain_id = X`) and Network B (`chain_id = Y`), which is not prevented anywhere in the reviewed code.
2. Construct (or have a cooperating miner construct) a `NakamotoBlockHeader` on Network A whose `signer_signature_hash()` preimage fields (`version, chain_length, burn_spent, consensus_hash, parent_block_id, tx_merkle_root, state_index_root, timestamp, miner_signature, pox_treatment[, problematic_txs]`) are made to be byte-identical to a header proposed on Network B.
3. Signer `K` signs the block on Network A via `create_block_acceptance` (`stacks-signer/src/v0/signer.rs:474-497`), producing signature `S = sign(signer_signature_hash)`.
4. `S` is a valid signature recoverable to `K` for the Network B header as well, because `verify_signer_signatures` (`stackslib/src/chainstate/nakamoto/mod.rs:1097-1190`) only checks that the recovered public key is in Network B's reward set — it performs no chain-ID check — so `S` can be inserted into Network B's block's `signer_signature` vector and counted toward its approval weight, even though `K` never intended to endorse that Network B block.
