### Title
Settled APR0 receipt escapes `stopEpochWithDuration` loss haircut and is paid at par, draining other claimants' funded withdrawals - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `collectWithdrawFunds` records a loss via `lossRecoveryPriceByEpoch[epochNumber]`, pending receipts of that epoch must be claimed through `_claimLossAdjustedWithdrawRequest`, which pays `claimBasis * lossRecoveryPrice / RECOVERY_FULL`. The protection in `requestWithdraw` that forces a user to claim a loss-adjusted receipt before opening a new request only checks `withdrawsRequestsByEpoch[user][lossEpoch]` and the still-open `apr0Users[user].principal` bucket. However, `_settleApr0` moves APR0 principal into `settledPrincipal`/`settledInterest` at `stopEpoch`, clearing `principal`/`principalEpoch`. A user whose only epoch-N receipt was an already-settled APR0 receipt therefore passes the guard, opens a new request in epoch N+1, and `lastWithdrawRequest` is overwritten to N+1. The loss-adjusted claim path then looks only at `lossRecoveryPriceByEpoch[N+1]` (zero), and the funded claim path pays the settled APR0 principal + interest at par from the strategy's underlying balance, even though the borrower only funded `amount * lossRecoveryPrice` for that epoch. The excess is taken from underlyings reserved for other users' funded/default-recovery claims, breaking the loss-waterfall invariant and causing insolvency for later claimants (use-after-free analog: the receipt's loss bookkeeping is "freed" by settlement while the payout token remains live).

### Finding Description
`requestWithdraw` guards a new request with a check on `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` combined with `withdrawsRequestsByEpoch[user][lossEpoch] != 0 || (apr0Users[user].principal != 0 && principalEpoch == lossEpoch)` (IdleCreditVault.sol:261-271). APR0 receipts are never written to `withdrawsRequestsByEpoch` (IdleCreditVault.sol:285-294), and once `prepareStopEpochWithApr0`/`_settleApr0` settles them, `apr0Users[user].principal` and `principalEpoch` are zeroed (IdleCreditVault.sol:563-564). After a lossy `stopEpoch` for epoch N, the attacker requests a new withdraw in epoch N+1: the guard sees a zero `principal` and zero `withdrawsRequestsByEpoch[N]`, so it does not revert, and `lastWithdrawRequest[user]` becomes N+1 (IdleCreditVault.sol:282). On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]` = `lossRecoveryPriceByEpoch[N+1]` = 0 and returns 0 (IdleCreditVault.sol:789-795), so the N-epoch haircut is skipped. `_claimFundedWithdrawRequest` then pays `settledPrincipal + settledInterest` in full via `_transferFundedClaim` (IdleCreditVault.sol:338-349, 897-906). The strategy only received `claimBasis * lossRecoveryPrice` for epoch N, so the difference is paid out of funds backing other users' receipts or the `defaultRecoveryReserve`-adjacent balance (the reserve guard only protects `defaultRecoveryReserve`, not funded claims of other epochs).

### Impact Explanation
Direct theft / insolvency: the attacker redeems a haircut receipt at par, extracting `settledClaim * (1 - lossRecoveryPrice)` of underlying that belongs to other pending-receipt holders. Later legitimate claimants' `_transferFundedClaim` calls revert or are underpaid, i.e., permanent loss of unclaimed yield equal to the haircut the attacker skipped. The broken invariant is the loss waterfall / "one receipt one haircut-adjusted payout".

### Likelihood Explanation
Requires: unscaledApr == 0 (APR0 mode), an attacker withdraw request outstanding in the epoch, and the epoch ending via a lossy `stopEpoch` where `collectWithdrawFunds` is called with `_amount < pendingWithdraws` (borrower underfunds, honest manager sequence per threat model). The attacker is an ordinary KYC'd tranche holder performing only `requestWithdraw` twice and `claimWithdrawRequest`. No privileged action needed. The main uncertainty is the exact ordering of `_settleApr0` vs. `collectWithdrawFunds` inside `stopEpoch` in `IdleCDOEpochVariant` (not fully verified here); the bug requires settlement to occur in the same stop that records the loss, or that the settled bucket persist into a subsequent lossy epoch.

### Recommendation
In `requestWithdraw`'s loss guard, also treat `apr0Users[user].settledPrincipal != 0` (and `settledInterest`) for the loss epoch as blocking, or persist the settled bucket's originating epoch so `_claimLossAdjustedWithdrawRequest` can apply `lossRecoveryPriceByEpoch` to settled APR0 claims. Alternatively, store the loss-adjusted payout per user/epoch at settlement time so the haircut survives `lastWithdrawRequest` being overwritten.

function testApr0SettledReceiptSkipsLossHaircut() external {
    // APR0 mode: force apr to 0, disable AYS
    _forceLastEpochAprToZero();

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);          // attacker deposit
    idleCDO.depositAA(amount);          // victim deposit (second user)

    _startEpochAndCheckPrices(0);

    // attacker requests full withdraw in epoch 0 (APR0 bucket)
    uint256 atkPrincipal = cdoEpoch.requestWithdraw(0, address(AAtranche));
    // victim also requests, sharing the same pendingWithdraws bucket
    // ...

    // epoch 0 ends with a loss: borrower underfunds pendingWithdraws
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 funded = pending / 2; // 50% recovery -> lossRecoveryPriceByEpoch[0] = 0.5e18
    deal(defaultUnderlying, borrower, funded + cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // settles apr0 -> settledPrincipal, then collectWithdrawFunds(funded)

    // attacker opens a new request in epoch 1; guard passes because
    // apr0Users.principal == 0 and withdrawsRequestsByEpoch[attacker][0] == 0
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // fund epoch 1 normally, then claim
    // ...
    cdoEpoch.claimWithdrawRequest();

    // attacker received settledPrincipal + settledInterest at PAR,
    // while lossRecoveryPriceByEpoch[0] was 0.5 -> excess drained victim's funded share
}

Expected result: attacker's payout exceeds `claimBasis * lossRecoveryPriceByEpoch[0] / RECOVERY_FULL`, and the victim's subsequent `claimWithdrawRequest` underpays or reverts in `_transferFundedClaim`.
