### Title
Unbounded, Instant Commission Rate Increase on Vote Accounts (No Delay/Cap Protection) — Delegator Reward Front-Run Analog ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The `UpdateCommissionBps` vote instruction lets a vote account's authorized withdrawer change `inflation_rewards_commission_bps` and `block_revenue_commission_bps` to any value in `[0, 10000]` (0–100%) with no timing restriction whatsoever, unlike the legacy `update_commission` path. This mirrors the reported spl-stake-pool "front-run deposits" bug class: a pool/vote manager can spike their cut of a value distribution (stake pool deposit vs. vote-account reward commission) right before value is realized, then roll it back, with no on-chain delay and no way for the counterparty to bound their minimum expected payout.

### Finding Description
`update_commission` (legacy, percent-based) enforces `is_commission_update_allowed`, blocking commission *increases* outside the first half of an epoch specifically "to prevent last minute commission rugs" [1](#0-0) .

The newer basis-points path, `update_commission_bps` (SIMD-0291, gated behind `commission_rate_in_basis_points` + `delay_commission_updates`), explicitly drops this restriction — the code comment reads "No commission update rule, per SIMD-0249 and SIMD-0291" — and only checks the withdrawer's signature before writing the new commission directly into vote state: [2](#0-1) 

This is invoked unconditionally (once the relevant features are active) via `VoteInstruction::UpdateCommissionBps` in the vote processor, with no per-transaction slot/epoch gating beyond feature checks: [3](#0-2) 

For *inflation* rewards, the protocol compensates for this by having `redeem_delegation_rewards` read commission from a **cached, ~1-2 epoch-old** vote-account snapshot (`snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`) instead of the live value when `delay_commission_updates` is active: [4](#0-3) [5](#0-4) 

However, `calculate_block_reward` (SIMD-0123 block-revenue sharing) reads `pending_delegator_rewards` directly from the **current** `distribution_epoch_vote_accounts` view rather than a delayed snapshot, and performs no commission-delay lookup at all: [6](#0-5) 

Commission for block-revenue distribution appears to be applied at the point rewards are deposited (`VoteInstruction::DepositDelegatorRewards`), which reads the live `block_revenue_commission_bps` from vote state at call time: [7](#0-6) 

I was not able to fully trace the `DepositDelegatorRewards` handler body within the available tool budget to confirm exactly how/when the commission split is computed relative to the deposit; this is the primary unverified link in the chain and should be reviewed directly in `programs/vote/src/vote_processor.rs` / `vote_state/mod.rs` around the `DepositDelegatorRewards` implementation.

### Impact Explanation
If block-revenue commission is applied synchronously at deposit time (as the code structure suggests, since `calculate_block_reward` performs no delay), a vote account's authorized withdrawer can:
1. Wait for a block/deposit event carrying substantial `pending_delegator_rewards`.
2. Call `UpdateCommissionBps` to spike `block_revenue_commission_bps` toward 10000 (100%) immediately before/alongside the `DepositDelegatorRewards` call.
3. Collect nearly the entire block-revenue reward as "commission," then lower the rate back down.

Delegated stakers have no analog to `DepositStakeWithSlippage`/minimum-received-amount protection to guard against this instantaneous commission spike — this is structurally the same primitive as the reported stake-pool deposit-fee front-run, but for validator commission on delegator rewards, and would constitute unauthorized diversion of delegator funds if confirmed.

### Likelihood Explanation
Moderate-to-low confidence without full trace of `DepositDelegatorRewards`. The design intentionally protects the far larger inflation-reward stream via the 1-2 epoch cached-snapshot delay, and SIMD-0249/0291's removal of the instruction-level rule appears deliberate given that mitigation exists elsewhere for inflation rewards. Whether the same protection applies to block-revenue commission is the open question — if `DepositDelegatorRewards` also reads from a delayed/cached commission value (rather than live vote state), this finding would not hold. This requires direct code review of the deposit handler, which was not retrievable in the current session.

### Recommendation
Confirm whether `DepositDelegatorRewards`/block-revenue commission distribution consults a delayed (cached) commission rate analogous to `redeem_delegation_rewards`'s inflation-reward path. If it uses the live `block_revenue_commission_bps` at call time, apply the same epoch-delay mechanism used for inflation rewards, or introduce an explicit cap/rate-of-change limit on `UpdateCommissionBps` for the `BlockRevenue` kind.

### Proof of Concept
Conceptual (pending confirmation of `DepositDelegatorRewards` semantics):
1. Attacker controls vote account's authorized withdrawer.
2. Vote account accrues `pending_delegator_rewards` from block revenue.
3. Attacker submits `UpdateCommissionBps { commission_bps: 10000, kind: BlockRevenue }` via `programs/vote/src/vote_processor.rs:362-382` → `update_commission_bps` at `programs/vote/src/vote_state/mod.rs:827-859` (no delay check).
4. `DepositDelegatorRewards` is processed, splitting `pending_delegator_rewards` using the now-100% commission rate.
5. Attacker sets commission back down afterward — delegators received ~0 of the block revenue owed to them for that distribution, with no way to have specified a minimum acceptable amount.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }
