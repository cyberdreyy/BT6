### Title
Fallback-miner (`ProposedBy::LastSortition`) tenure-change validation only rejects duplicates via `get_last_globally_accepted_block`, permitting a second conflicting tenure-change block to be signed - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
When `cur_sortition.miner_status == InvalidatedBeforeFirstBlock`, `check_proposal` routes tenure-change proposals whose `consensus_hash` matches `last_sortition` through `validate_tenure_change_payload`, whose only duplicate-block guard is `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`. This lookup is scoped to *globally* accepted blocks, so a block this signer has already locally signed (but which has not reached the global 70% threshold) is invisible to the check, letting a second, conflicting tenure-change block for the same consensus hash pass validation.

### Finding Description
In `SortitionsView::check_proposal` (`stacks-signer/src/chainstate/v1.rs:301-317`), once `cur_sortition.miner_status == SortitionMinerStatus::InvalidatedBeforeFirstBlock`, a proposal whose `consensus_hash` matches `last_sortition.data.consensus_hash` is accepted into the `ProposedBy::LastSortition` branch, gated only by the `miner_pkh` equality check at line 276 against `last_sortition.data.miner_pkh` (cached once at `fetch_view`/`reset_view` time, `v1.rs:522-563`).

If the proposal carries a tenure-change payload, `validate_tenure_change_payload` (`v1.rs:461-520`) is invoked. Its only anti-duplication check is: [1](#0-0) 
which calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`. This function is explicitly scoped to blocks that have reached *global* acceptance (i.e., signed by enough signer weight to be broadcast/accepted network-wide), not blocks this individual signer has merely locally signed. If this signer previously signed BlockProposal A for the fallback tenure but A has not yet crossed the global-acceptance threshold, this lookup returns `None`, and a second, structurally distinct BlockProposal B for the same `consensus_hash`/height passes this check as long as it independently satisfies `check_tenure_change_confirms_parent` and `check_parent_tenure_choice`.

The root cause is that the duplicate-block guard is defined in terms of network-wide state (`get_last_globally_accepted_block`) rather than this signer's own local commitment record for the tenure, and the `ProposedBy::LastSortition` path has no additional local-history check beyond this.

### Impact Explanation
This breaks the **uniqueness** safety property: a single signer would produce two valid signatures over two different `signer_signature_hash` values for the same tenure/height under the fallback-miner path. If a byzantine miner (who won the last sortition) collects such conflicting signatures from a sufficient set of otherwise-honest signers via this same code gap, it creates a genuine chain-safety hazard (conflicting blocks each accumulating signer weight), which matches the "Critical: signer signing... conflicting block" category.

### Likelihood Explanation
Preconditions are narrow but not implausible under normal chain operation: `cur_sortition` must be `InvalidatedBeforeFirstBlock` (a fairly common occurrence — happens whenever the current miner times out or picks an invalid parent tenure, per `v1.rs:144-203`), `last_sortition` must still be `Valid`, and the signer must have already locally signed (but not yet seen global acceptance for) one block in the fallback tenure. A miner who won the *last* sortition slot can then submit a second, differently-constructed tenure-change block for that same consensus hash; per-signer, this requires no privileges beyond normal block-proposal gossip and the fact that they legitimately won that sortition slot.

### Recommendation
Change the duplicate-block guard in `validate_tenure_change_payload` (and any equivalent path for non-tenure-change confirms-latest-block checks) to also consult this signer's own local signing record for the tenure — e.g. check `SignerDb` for *any* locally-signed/locally-accepted block for `block.header.consensus_hash`, not only globally-accepted ones — and reject a second, differing `signer_signature_hash` for the same tenure/height regardless of global-acceptance status.

**Caveat:** I was unable, within the available tool budget, to fully verify whether `stacks-signer/src/v0/signer.rs`'s higher-level proposal-handling state machine applies an additional, independent local-equivocation guard (e.g. checking `SignerDb` for any prior local block at the same height/tenure) before invoking `check_proposal`. If such a guard exists in the calling code, it may prevent the second signature from being produced despite `validate_tenure_change_payload` itself lacking the check. This should be verified against the full `stacks-signer/src/v0/signer.rs` and `stacks-signer/src/signerdb.rs` contents before treating this as fully confirmed exploitable end-to-end.
