### Title
Permanent stuck-slot growth in `blockSubscribe` notifications once a slot is purged by `BlockstoreCleanupService` - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
The `blockSubscribe` notification path tracks per-subscription progress with `last_notified_slot` and only advances it when `Blockstore::get_complete_block` succeeds for a slot. If that call ever fails for a slot (most plausibly because `BlockstoreCleanupService` has already purged it), the cursor is never advanced, and every subsequent bank-commitment notification re-attempts and re-accumulates the same stuck slot plus every new slot since, unboundedly, for the lifetime of the subscription — the same structural pattern as the referenced report: a single external event makes a piece of cached/retryable state permanently unresolvable, and the retry logic can only ever replay the same doomed input.

### Finding Description
`RpcSubscriptions::notify_watchers` handles `SubscriptionParams::Block` like this [1](#0-0) :
- `w_last_unnotified_slot` is read/written from `subscription.last_notified_slot`.
- `slots_to_notify` is built as the range `*w_last_unnotified_slot..slot`, filtered to proper ancestors, then `slot` is appended.
- For each slot `s`, `blockstore.get_complete_block(s, false)` is called.
  - On success, `*w_last_unnotified_slot = s + 1` (cursor advances).
  - On error, the comment explicitly states: *"we don't advance `w_last_unnotified_slot` so that it'll retry on the next notification trigger"* — an error notification is sent, but the cursor stays put [2](#0-1) .

This retry design assumes failures are transient. But `Blockstore::get_complete_block` (and the internal getters it uses) is gated by `check_lowest_cleanup_slot`, which returns `BlockstoreError::SlotCleanedUp` for any slot at or below `lowest_cleanup_slot` [3](#0-2) . `lowest_cleanup_slot` is a monotonically non-decreasing watermark maintained by `BlockstoreCleanupService`, which periodically purges older slots based on shred-count thresholds — this is normal, continuous validator operation, not an attacker action [4](#0-3) .

Consequently, if a `blockSubscribe` subscriber's cursor (`w_last_unnotified_slot`) ever falls behind `lowest_cleanup_slot` — e.g., a slow/backpressured websocket consumer, a `finalized`-commitment subscription during a period where rooting lags behind cleanup, or simply a long-lived idle subscription during heavy ledger churn — the failing slot can never succeed again, since `lowest_cleanup_slot` only grows. From that point on, on every single bank-commitment notification (which fires roughly every slot, i.e., far more often than once per `CLUSTER_SLOT_TIME_TARGET / 2`), `notify_watchers`:
1. Recomputes `slots_to_notify` as the ever-widening range from the stuck slot to the current slot (this range grows by one on every tick, forever).
2. Calls `blockstore.get_complete_block` for every slot in that growing range, each doing RocksDB lookups (`meta`, transaction/entry reads) that all fail with `SlotCleanedUp`.
3. Sends an `Err` `RpcBlockUpdate` notification through the pubsub channel for every one of those slots, every time.

This is triggered purely by opening one `blockSubscribe` subscription (feature is opt-in via `--rpc-pubsub-enable-block-subscription`, but once enabled it is reachable by any unprivileged RPC client) and letting/forcing the cursor to fall behind cleanup — no malicious payload or privileged access needed on the validator side.

### Impact Explanation
Once triggered, a single subscription causes unbounded, ever-increasing per-notification CPU/I/O work (blockstore reads for a growing slot range) and unbounded outbound notification traffic, indefinitely, from one client action. This matches the reachable-analog criteria: unbounded cost for a single low-rate call, driven by a JSON-RPC/pubsub subscription path rather than validator/peer/operator logic. It does not by itself corrupt consensus state or crash the process, but it is a self-inflicted, non-recoverable resource-consumption bug directly parallel to the referenced report's "funds permanently stuck because the only available retry replays stale, forever-failing data."

### Likelihood Explanation
Requires: (1) `--rpc-pubsub-enable-block-subscription` enabled (an operator choice, common on RPC-serving nodes), and (2) the subscriber's tracked cursor falling behind the blockstore's cleanup watermark. This can happen organically (slow consumer, network hiccups, deliberately not reading the socket, or subscribing with `finalized` commitment on a node with aggressive `--limit-ledger-size`/cleanup settings) and can also be deliberately induced by an unprivileged client that simply opens the subscription and stalls reading responses while normal cleanup proceeds. No special privileges or crafted payloads beyond a standard subscribe call are needed, making the trigger realistically reachable, though it does depend on the operator having block subscriptions enabled.

### Recommendation
In the `SubscriptionParams::Block` handling of `notify_watchers`, detect when a target slot's `get_complete_block` failure is due to permanent purge (`BlockstoreError::SlotCleanedUp` or slot `< blockstore.lowest_cleanup_slot()`), and in that case skip/advance `w_last_unnotified_slot` past the unrecoverable slot(s) instead of leaving the cursor stuck. Additionally, cap the maximum span of `slots_to_notify` processed per notification cycle (or resync the cursor to a bounded window, e.g. `max(last_unnotified_slot, slot - N)`) so that a lagging/stuck subscription cannot cause an unbounded, ever-growing range of blockstore lookups and notifications per tick.

### Proof of Concept
Not independently executable within this analysis (no filesystem/terminal access), but the mechanism is fully traceable in-code:
1. Open a `blockSubscribe` websocket subscription with `commitment: finalized` (or any commitment) on a node with `--rpc-pubsub-enable-block-subscription` and an active `BlockstoreCleanupService`/`--limit-ledger-size`.
2. Stop reading from the websocket (or otherwise let the subscription's `last_notified_slot` lag) long enough that `BlockstoreCleanupService::cleanup_ledger` purges slots at or below the subscriber's current `last_notified_slot`, setting `lowest_cleanup_slot` past it [5](#0-4) .
3. Resume reading (or simply observe server-side CPU/notification volume): every subsequent `notify_watchers` invocation for this subscription recomputes `slots_to_notify` starting at the now-permanently-purged slot [1](#0-0) , and `get_complete_block` fails with `SlotCleanedUp` for that slot forever [3](#0-2) , so `w_last_unnotified_slot` never advances and the range grows by one slot every subsequent bank-commitment tick, indefinitely.

    /// Acquires the `lowest_cleanup_slot` lock and returns a tuple of the held lock
    /// and lowest available slot.
    ///
    /// The function will return BlockstoreError::SlotCleanedUp if the input
    /// `slot` has already been cleaned-up.
    fn check_lowest_cleanup_slot(
        &self,
        slot: Slot,
    ) -> Result<std::sync::RwLockReadGuard<'_, Slot>> {
        // lowest_cleanup_slot is the last slot that was not cleaned up by LedgerCleanupService
        let lowest_cleanup_slot = self.lowest_cleanup_slot.read().unwrap();
        if *lowest_cleanup_slot > 0 && *lowest_cleanup_slot >= slot {
            return Err(BlockstoreError::SlotCleanedUp);
        }
        // Make caller hold this lock properly; otherwise LedgerCleanupService can purge/compact
        // needed slots here at any given moment
        Ok(lowest_cleanup_slot)
    }

    /// Cleanup the ledger if a cleanup request is present. Cleanup requests may
    /// be automatically created given the configuration options, or they may
    /// come from an external caller who holds a Blockstore
    pub fn cleanup_ledger(
        blockstore: &Blockstore,
        cleanup_request_sender: &Sender<Slot>,
        cleanup_request_receiver: &Receiver<Slot>,
        cleanup_strategy: BlockstoreCleanupStrategy,
        last_purge_slot: &mut u64,
        purge_interval: u64,
    ) {
        Self::maybe_generate_automatic_cleanup_request(
            blockstore,
            cleanup_request_sender,
            cleanup_strategy,
            last_purge_slot,
            purge_interval,
        );

        // `Receiver::try_recv()` will error if the channel is disconnected or
        // empty. Both sides of the channel are passed in so it is impossible
        // for the channel to be disconnected. If the channel is empty, there
        // is nothing to do and `ok()` will convert to an `Option` for us
        let lowest_cleanup_slot = cleanup_request_receiver.try_recv().ok();

        if let Some(lowest_cleanup_slot) = lowest_cleanup_slot {
            *blockstore.lowest_cleanup_slot.write().unwrap() = lowest_cleanup_slot;

            let mut purge_time = Measure::start("purge_slots()");
            // purge any slots older than lowest_cleanup_slot.
            let _ = blockstore
                .purge_slots(0, lowest_cleanup_slot, PurgeType::CompactionFilter)
                .inspect_err(|e| {
                    error!("Purge failed when cleaning ledger to {lowest_cleanup_slot}: {e:?}")
                });
            // Update only after purge operation.
            // Safety: This value can be used by compaction_filters shared via Arc<AtomicU64>.
            // Compactions are async and run as a multi-threaded background job. However, this
            // shouldn't cause consistency issues for iterators and getters because we have
            // already expired all affected keys (older than or equal to lowest_cleanup_slot)
            // by the above `purge_slots`. According to the general RocksDB design where SST
            // files are immutable, even running iterators aren't affected; the database grabs
            // a snapshot of the live set of sst files at iterator's creation.
            // Also, we passed the PurgeType::CompactionFilter, meaning no delete_range for
            // transaction_status and address_signatures CFs. These are fine because they
            // don't require strong consistent view for their operation.
            blockstore.set_max_expired_slot(lowest_cleanup_slot);
            purge_time.stop();
            info!("Cleaned up Blockstore data older than slot {lowest_cleanup_slot}. {purge_time}");
        }
