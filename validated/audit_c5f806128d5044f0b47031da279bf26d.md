### Title
Unfunded instant-withdraw receipts from epochs prior to the default epoch escape the recovery haircut and are paid at par, draining the recovery reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` only account for instant-withdraw receipts tagged to the *current* `epochNumber` bucket (`instantWithdrawClaimsByEpoch[epochNumber]`). However, `pendingInstantWithdraws` is a global aggregate that can span multiple epochs. An unprivileged lender can leave an unfunded instant-withdraw receipt in an older epoch bucket; when a later epoch defaults and is finalized, that stale receipt is excluded from the haircut basis yet is still paid 1:1 through `_transferFundedClaim`, consuming underlying that either belongs to the recovery reserve or to other claimants. This mirrors the CVE bug class: a buffer (recovery reserve) sized to the "expected" input (current-epoch claims) is over-run by a single call contributing more than accounted for (multi-epoch pending claims).

### Finding Description
- `requestInstantWithdraw` records claims per epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`, while `pendingInstantWithdraws` is a single global counter [1](#0-0) .
- Epochs can start and stop while `pendingInstantWithdraws > 0` (partial funding by the borrower via `collectInstantWithdrawFunds`, which only decrements the counter [2](#0-1) ), and `epochNumber` is incremented on the deposit done at `stopEpoch` [3](#0-2) . So instant receipts requested in epoch N remain pending while the bucket index advances to N+1.
- At default finalization, the claim basis only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *single current* bucket — conditioned on the *aggregate* `pendingInstantWithdraws != 0` [4](#0-3) . The prefunded reserve is similarly computed only against the current bucket [5](#0-4) .
- At claim time, `_claimDefaultedInstantWithdrawRequest` only haircuts the `defaultRecoveryEpoch` bucket; any remainder in `instantWithdrawsRequests[_user]` (the old-epoch unfunded receipt) is then paid at par by `_transferFundedClaim` [6](#0-5) . `_transferFundedClaim` only requires `balance - reserve >= amount`, so it happily spends any non-reserve underlying — including funds backing other users' funded claims — or reverts if only reserve remains [7](#0-6) .

Broken invariant: one receipt, one haircut-adjusted payout. The stale unfunded receipt was never funded and never included in `totalBasis`, so paying it at par is pure dilution of the recovery reserve / funded-claim pool.

### Impact Explanation
A lender holding an old unfunded instant receipt receives 100% while all genuinely defaulted claimants receive `recoveryPrice`. The excess comes out of strategy underlying reserved for other claimants or for funded receipts: either earlier claimants are overpaid at the expense of later ones whose claims then revert on `defaultRecoveryReserve -= _amount` underflow or the `_transferFundedClaim` balance guard (permanent freeze of remaining claims), or the attacker directly extracts funded-claim underlying. Loss is bounded by the stale unfunded instant amount, which the attacker fully controls (they choose the request size).

### Likelihood Explanation
Requires no privileged misbehavior: the borrower simply underfunds `getInstantWithdrawFunds` once (partial funding is an explicitly supported path — `pendingInstantWithdraws -= _amount` with any `_amount`), the next epoch runs, and a subsequent epoch defaults. The attacker is an ordinary KYC'd lender calling `requestWithdraw`/instant claim flows. Sequence: epoch N instant request → partial prefund → epoch N+1 runs → borrower default → `finalizeDefault` → attacker claims. The existing `_ensureDefaultRecoveryInitialized` guard only fires for uninitialized legacy strategies and does not stop this [8](#0-7) .

### Recommendation
In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, account for the *aggregate* pending instant exposure rather than only `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., iterate/track all epoch buckets contributing to `pendingInstantWithdraws`, or store a global `instantWithdrawClaimsTotal` alongside the per-epoch map so every unfunded instant receipt joins the haircut basis regardless of request epoch. Symmetrically, `_claimDefaultedInstantWithdrawRequest` should haircut every instant receipt epoch that was unfunded at finalization, not only `defaultRecoveryEpoch`.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testStaleInstantReceiptEscapesDefaultHaircut() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 recoveryRatio = 7e17;
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));

    // attacker deposits, epoch 0 runs and stops normally
    _depositWithUser(attacker, amount, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // attacker requests instant withdraw in epoch-1 buffer
    vm.prank(attacker);
    uint256 staleClaim = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch 1 starts; borrower only PARTIALLY funds instant queue
    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    // fund only half of pendingInstantWithdraws via collectInstantWithdrawFunds
    _getInstantFundsPartial(creditVault.pendingInstantWithdraws() / 2);
    assertGt(creditVault.pendingInstantWithdraws(), 0, 'stale instant still unfunded');

    // epoch 2 runs; borrower defaults at stop
    _startEpochAndCheckPrices(2);
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees();
    _stopEpochAndCheckPrices(2, initialProvidedApr / 4, 0);
    _checkDefault();

    // finalize: stale epoch-1 bucket is NOT in defaultPendingClaimBasis (only epochNumber bucket is)
    uint256 basisCounted = creditVault.defaultPendingClaimBasis();
    assertLt(basisCounted, staleClaim, 'stale instant bucket excluded from basis');

    uint256 recovered = (activeBasis + basisCounted) * recoveryRatio / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // attacker claims: stale receipt paid 1:1 via _transferFundedClaim,
    // overpaid vs the ~70% haircut every honest claimant gets
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;
    assertGt(paid, staleClaim * recoveryRatio / ONE_TRANCHE, 'unfunded receipt paid above recovery price');
    // reserve now short => subsequent _claimDefaulted* claims revert on defaultRecoveryReserve underflow
}
```

`_getInstantFundsPartial` mirrors the existing `_getInstantFunds` helper but has the borrower return only part of `pendingInstantWithdraws` to the CDO before `collectInstantWithdrawFunds`.

    if (_amount == 0) return;

      uint256 balance = underlyingToken.balanceOf(address(this));

      // receipts can never spend underlyings reserved for default recovery claimants.
