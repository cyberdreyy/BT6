## Analysis: Analog to CVE-2023-30798 in stacks-signer

The bug class in the report (`MultipartParser` accepting an unbounded number of parts, causing high CPU/memory from processing each one) maps to the `StateMachineUpdate` / `ReplayTransactionSet` handling in the v0 signer.

### Finding Description

`StateMachineUpdate::consensus_deserialize` caps the *serialized byte size* of the content at `STATE_MACHINE_UPDATE_MAX_SIZE`, but places no cap on the **number of items** in `replay_transactions: Vec<StacksTransaction>`: [1](#0-0) 

Any signer (or a gossiping peer) can craft a `StateMachineUpdate` whose `V1`/`V2` content carries a very large number of minimal `StacksTransaction`s — bounded only by total bytes, not item count — the same "no cap on parts" pattern as the advisory.

This flows into `GlobalStateEvaluator::determine_global_state`, called on every `handle_state_machine_update` / event-loop pass: [2](#0-1) 

Inside it, `find_majority_prefix_replay_set` performs an unbounded, per-candidate-truncation scan: for a replay set of length *n* it repeatedly calls `.starts_with(&candidate_prefix)` over every stored set while popping one element at a time — an O(n²) operation over attacker-controlled *n*: [3](#0-2) 

Additionally, `replay_txids()` maps over the full vector computing a `txid()` (a hash) for every transaction on every log line of every received update: [4](#0-3) 

### Impact Explanation

This is a **liveness** issue, not a signing-safety break: a single crafted `StateMachineUpdate` message with a huge `replay_transactions` list forces every receiving signer to spend disproportionate CPU (txid hashing over all items, plus O(n²) prefix-matching in `determine_global_state`) each time the message is (re-)evaluated in the event loop. Because `determine_global_state` is invoked repeatedly as part of ordinary per-event housekeeping (not just once), a single such message can repeatedly burn CPU on every signer that ingests it via StackerDB, potentially delaying block validation/signing responses and stalling the pre-commit → signature pipeline described in the signer flow docs. This matches the "High: signer wedged into never signing valid blocks" category insofar as it degrades timely processing, though I could not fully confirm the degree of wedging (e.g., whether it is severe enough to miss the block-proposal timeout window) without load-testing, and I could not locate the exact numeric value of `STATE_MACHINE_UPDATE_MAX_SIZE` to compute a worst-case transaction count in this pass — this constant's value wasn't returned by the searches, only its usage sites.

### Likelihood Explanation

Any signer's private key can produce and broadcast a `StateMachineUpdate` over its own `.signers-*` StackerDB slot; there is no majority requirement — a single misbehaving/compromised signer or slot suffices to reach every peer signer through the normal `handle_state_machine_update` path. The item-count is unchecked at both serialization/deserialization time and consumption time.

### Recommendation

Cap `replay_transactions.len()` (e.g., to a small fixed maximum tied to reasonable tenure replay-set sizes) at deserialization time in `StateMachineUpdateContent::deserialize`, independent of the byte-size cap, mirroring Starlette's `max_fields`/`max_files` fix. Additionally bound the cost of `find_majority_prefix_replay_set` by rejecting/truncating oversized replay sets before they enter the evaluator, and consider memoizing/limiting `replay_txids()` computation.

### Proof of Concept

Not independently verified with a live cluster; based on static code analysis of `libsigner/src/v0/messages.rs` (`StateMachineUpdateContent::deserialize`) and `libsigner/src/v0/signer_state.rs` (`find_majority_prefix_replay_set`), which shows only a total-byte-size cap and no per-item-count cap on `replay_transactions`, and a quadratic algorithm operating over that unbounded vector.

**Confidence caveat:** I was unable to retrieve the concrete numeric value of `STATE_MACHINE_UPDATE_MAX_SIZE` or fully trace whether `determine_global_state`/`find_majority_prefix_replay_set` execute on a hot path frequently enough (vs. only on state changes) to constitute a severe wedge versus a minor, self-limiting CPU spike. This should be verified with a live Devin session (running the signer test suite / instrumenting `determine_global_state`) before treating this as a confirmed High-severity liveness bug rather than a lower-severity performance concern.

        &mut self,
        signer_public_key: &Secp256k1PublicKey,
        update: &StateMachineUpdate,

    ) {
        let replay_txids = update.content.replay_txids();
        let pubkey = signer_public_key.to_hex();
        info!(
            "{self}: Received state machine update from signer {pubkey}: {update}";
            "replay_txids" => ?replay_txids
        );
        let address = StacksAddress::p2pkh(self.mainnet, signer_public_key);
        // Store the state machine update so we can reload it if we crash
        if let Err(e) = self.signer_db.insert_state_machine_update(
            self.reward_cycle,
            &address,
            update,
            received_time,
        ) {
            warn!("{self}: Failed to update global state in signerdb: {e}");
        }
        self.global_state_evaluator
            .insert_update(address, update.clone());
    }
