### Title
Confirmations from removed multisig members are never purged, letting a request execute below the intended live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only removes requests *authored by* the member being deleted; it never scans the `confirmations` map to strip that member's confirmation entries from *other* pending requests. Because `confirm()` counts raw entries in the `confirmations` HashSet against `num_confirmations` without checking that each confirming identity is still in `self.members`, a confirmation cast by a member before their removal continues to count toward the K-of-N threshold after they have been removed. This breaks the intended equality `confirmations counted == confirmations from currently-live members`.

### Finding Description
`confirm()` looks up the confirmations already recorded for a request and executes it once `confirmations.len() + 1 >= num_confirmations`: [1](#0-0) 

Membership is only checked for the *caller* of `confirm`/`add_request` via `current_member()`, which validates against `self.members`: [2](#0-1) 

When a member is removed, `delete_member` removes the member from `self.members`, deletes their access key if applicable, and cleans up only the requests that member itself created (and the confirmation sets for those requests). It does not touch `confirmations` entries the removed member left on requests created by other members: [3](#0-2) 

Consequently, for any request `R` that was not authored by the removed member but was confirmed by them before removal, the string key representing that member remains inside `self.confirmations.get(&R)`'s `HashSet`. That stale entry is still summed in the `>= num_confirmations` check the next time anyone confirms `R`, effectively letting a former (now-untrusted) member's vote count toward execution.

### Impact Explanation
This crosses the exact authorization/threshold boundary the contract is designed to enforce: "K live members must agree". A request (e.g., `Transfer`, `AddKey`/full-access-key grant, `DeployContract`, or a further `DeleteMember`/`AddMember`) can be executed with fewer than `num_confirmations` *currently trusted* signers, because one of the counted confirmations belongs to someone who has already been removed from the multisig (e.g., an employee who left, a compromised key that was intentionally revoked, or a member removed specifically because they were no longer trusted). This is a Critical-impact issue per the custody-binding class: "a multisig request executed below threshold." Concretely, funds can be transferred out of the account, or a full-access key can be granted to an attacker-controlled key, using confirmations that should no longer be valid.

### Likelihood Explanation
No privileged access is required beyond being (or having been) an ordinary multisig member — the same trust level any member already has. The only preconditions are: (1) a request exists that has partial confirmations from a member, and (2) that member is later removed (a routine operation, e.g. off-boarding a team member or replacing a compromised key) before the request is deleted/expired. Given `REQUEST_COOLDOWN` only prevents deletion within 15 minutes and there is no automatic expiry tied to membership changes, this is straightforward to trigger, whether accidentally (stale pending requests sitting around during a membership change) or as a deliberate move by a soon-to-be-removed member who front-loads confirmations on a malicious request before their own removal is finalized.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests authored by that member) and remove the member's identity string from every confirmation set. Alternatively, when counting confirmations in `confirm()`, filter the stored confirmation set to only identities still present in `self.members` before comparing against `num_confirmations`, so stale confirmations from removed members never count.

### Proof of Concept
1. Initialize `MultiSigContract::new` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R1)` where `R1` is a malicious `Transfer` (or `AddKey` with full access) request — confirmations for `R1` = `{A}` (1/3).
3. `B` calls `confirm(R1)` — confirmations for `R1` = `{A, B}` (2/3, not yet executed).
4. Separately, members legitimately reach 3 confirmations (e.g. `A`, `C`, `D`) to execute a `DeleteMember { member: B }` request, removing `B` from `self.members` and deleting `B`'s access key. `delete_member` only cleans up requests *created by* `B`; `R1` (created by `A`) is untouched, so `R1`'s confirmation set still contains `B`.
5. `C` calls `confirm(R1)`. `confirmations.len()` for `R1` is 2 (`A`, `B`) `+ 1` (`C`) `= 3 >= num_confirmations`, so `R1` executes — even though `B` is no longer a member and only two currently-live members (`A`, `C`) actually authorized it.

This demonstrates a request executing with fewer than the required number of *live* member confirmations, i.e., a multisig request executed below the intended threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()
                    .unwrap_or_else(|_| env::panic_str("Failed to deserialize public key")),
            }
        } else {
            MultisigMember::Account {
                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
