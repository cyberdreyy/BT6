### Title
MessageId is not sender-scoped, allowing cross-user callback/response collision in the legacy Gateway path - ([File: core/services/gateway/api/message.go], [File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`Message.Validate` / `Message.ExtractSigner` correctly recovers the true signer of a message from its signature and stores it in `Body.Sender`, so a signature cannot be forged to claim someone else's address. However, neither `Validate` nor any caller binds `Body.MessageId` to the recovered `Body.Sender`: any signer can choose an arbitrary `MessageId` (only length/`NullChar` constraints are enforced), and downstream legacy handler state is keyed purely by `MessageId` (not by `MessageId`+`Sender`), which allows request/response state belonging to one user to be looked up or overwritten by another user's message sharing the same `MessageId`.

### Finding Description
`Message.Validate` (core/services/gateway/api/message.go:54-88) only validates format constraints on `MessageId`, `Method`, `DonId`, and `Receiver`, then calls `ExtractSigner` (line 82) and sets `m.Body.Sender = utils.StringToHex(string(signerBytes))` (line 86). `ExtractSigner` (lines 124-134) recovers the signer strictly from the ECDSA signature over the aligned `(MessageId, Method, DonId, Receiver, Payload)` tuple via `gw_common.ExtractSigner`. This means `Sender` cannot be spoofed to another address — it is cryptographically tied to whichever private key signed the tuple — but `MessageId` itself is fully attacker-chosen and is never required to be unique per sender or to encode/derive from the sender.

`ValidatedMessageFromReq` (core/services/gateway/handlers/common/message_util.go:36-58) sets `m.Body.MessageId = req.ID` directly from the client-supplied JSON-RPC ID, with no per-sender namespacing, and `gateway.ProcessRequest` (core/services/gateway/gateway.go:250-262) routes purely by `DonId`/`MessageId`/`Method` after `msg.Validate()` succeeds — again with no sender-scoping check.

Downstream, the legacy WebAPI capability handler stores pending callbacks in a single map keyed only by `MessageId`: `savedCallbacks map[string]*savedCallback` (core/services/gateway/handlers/capabilities/handler.go:53), and `handleWebAPITriggerMessage` looks up and deletes an entry using only `msg.Body.MessageId` (lines 148-161), with no sender check. Because two different, differently-signed messages (from two different `Sender`s) can carry the same `MessageId`, whichever message currently occupies the `savedCallbacks[MessageId]` slot will receive the delivered response — enabling response/callback collisions across users sharing a DON.

This is in contrast to the newer vault gateway flow, which explicitly guards against exactly this class of ID collision by namespacing request IDs per owner (`owner + vaulttypes.RequestIDSeparator + requestID`, see core/capabilities/vault/gateway_vault_request_processor.go and the "duplicate requestId" rejection test in core/services/gateway/handlers/vault/handler_test.go:682-725), confirming that ID-collision-across-senders is a recognized concern that the legacy `api.Message` path does not address.

### Impact Explanation
An unprivileged, unauthenticated caller of the gateway API (any address that can produce a validly-signed message) can pick a `MessageId` matching one used concurrently by another legitimate user targeting the same DON. Because the legacy handler's callback bookkeeping is keyed solely by `MessageId`, this can cause cross-user response mixup: a victim's response (potentially containing sensitive payload data intended for them) can be delivered to, or overwritten/dropped by, the attacker's request, or vice versa. This matches the "cross-user response confusion" bounty impact class. It does not by itself grant fund movement, key disclosure, or authorization bypass — `Sender` values themselves remain correctly and unforgeably bound to signatures.

### Likelihood Explanation
No special privilege is required — any client able to send a signed gateway message can pick its own `MessageId`. The main practical constraint is a race/timing requirement: the attacker's message must be in flight (registered) at the same time as the victim's message with the same `MessageId` targeting the same DON, so this is a collision/race condition rather than a deterministic one-shot exploit. Guessing or predicting another user's `MessageId` in real time is the limiting factor, but a malicious/curious user of the same gateway/DON could intentionally reuse observed or predictable IDs (e.g., sequential or externally-visible request IDs) to trigger the collision.

### Recommendation
Scope all request-correlation state (the `savedCallbacks` map key, and any other MessageId-based lookup/dedup) to `(Sender, MessageId)` or `(DonId, Sender, MessageId)` rather than `MessageId` alone, mirroring the owner-prefixing approach already used in the vault gateway flow (`owner + RequestIDSeparator + requestID`). Additionally, consider enforcing uniqueness of `MessageId` per sender at `Message.Validate` time (or generating an internal composite key immediately after `ExtractSigner` resolves `Sender`) so that no downstream code path can be reached with only the raw, sender-agnostic `MessageId`.

### Proof of Concept
1. In `core/services/gateway/api/message_test.go` (or similar), construct two `api.Message` values with an identical `Body.MessageId`, `Method`, `DonId`, but signed with two different `ecdsa.PrivateKey`s via `Message.Sign`.
2. Call `Validate()` on both messages and assert `err == nil` for both, and that `Body.Sender` differs between them — demonstrating `MessageId` collision is accepted regardless of sender.
3. At the handler level (`core/services/gateway/handlers/capabilities/handler_test.go`), simulate two concurrent `HandleLegacyUserMessage`/HTTP-trigger flows that both populate `savedCallbacks` under the same `MessageId` (from different signers), then simulate a single `HandleWebAPITriggerMessage`/node response with that `MessageId` and assert which callback receives the response — showing the second registration silently replaces/intercepts the first's pending callback, i.e., cross-user response delivery.

Note: full confirmation of the exact write-site that populates `savedCallbacks` (the HTTP trigger registration handler) was not completely traced within this investigation; a Devin session with full repo access would be needed to pin down that code path precisely and finalize the PoC. func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}

func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
