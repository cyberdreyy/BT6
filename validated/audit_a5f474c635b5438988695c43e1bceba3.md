### Title
Missing role check on `GET /v2/config` and `/v2/config/v2` allows any authenticated user (including view-role) to read full effective node configuration - ([File: core/web/router.go])

### Summary
The routes `authv2.GET("/config", cc.Show)` and `authv2.GET("/config/v2", cc.Show)` are registered only behind `auth.Authenticate(...)`, without any `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, unlike nearly every other sensitive route in the same group. Any session-authenticated user, including one with the lowest `view` role, can call `ConfigController.Show` and receive the full `effective` TOML configuration via `cfg.ConfigTOML()`.

### Finding Description
`v2Routes` registers the config endpoints inside `authv2`, which is gated only by `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0) . This middleware validates that the requester has any valid session cookie or API token, but does not check the user's role. By contrast, comparable/adjacent routes explicitly wrap their handlers with `auth.RequiresEditRole` or `auth.RequiresAdminRole` (e.g. bridge types, external initiators, keys, jobs) [2](#0-1) .

`ConfigController.Show` unconditionally calls `cc.App.GetConfig()` and `cfg.ConfigTOML()`, which returns the `user` (input) and `effective` (fully resolved, defaults-applied) configuration TOML, and serializes it into the JSON API response with no role-based redaction or field scoping: [3](#0-2) . `ConfigTOML()` is implemented as `return g.inputTOML, g.effectiveTOML`, i.e., the entire generated configuration document [4](#0-3) .

Because `auth.RequiresEditRole` and `auth.RequiresAdminRole` are the mechanisms that actually check `user.Role` against `UserRoleView`/`UserRoleRun` [5](#0-4) , and this route never invokes either, `GetAuthenticatedUser`'s role check is simply skipped for `/v2/config` and `/v2/config/v2`. Any authenticated principal — including a `view`-role user with only a session cookie, or an API token — is able to fetch the full effective node config.

### Impact Explanation
This causes full node configuration disclosure to a low-privilege (`view`-role) authenticated user: chain RPC endpoint URLs, feature flags, timeouts, gas/finality parameters, and overall node topology contained in the effective TOML config. This maps to the Chainlink bounty impact class of "sensitive information disclosure via authorization bypass" — a view-role/read-only account gains access to data that should require at least `edit`/`admin` privilege, violating the exact-role invariant intended by the router's design (evidenced by the pervasive use of `RequiresEditRole`/`RequiresAdminRole` on comparably sensitive endpoints).

### Likelihood Explanation
Any user with a valid session or API token — including the lowest privilege `view` role, which is commonly issued to read-only/monitoring accounts — can trigger this with a single unauthenticated-role-check GET request. No special conditions, timing, or race are needed; it is trivially and repeatably reproducible on any running node with a view-role account.

### Recommendation
Wrap the config routes with a role restriction consistent with their sensitivity, e.g.:
```go
authv2.GET("/config", auth.RequiresEditRole(cc.Show))
authv2.GET("/config/v2", auth.RequiresEditRole(cc.Show))
```
in `core/web/router.go`. Alternatively, redact sensitive fields (RPC URLs/secrets) from `ConfigTOML()`'s effective output for lower-privileged roles at the `ConfigController.Show` level.

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, similar to existing controller tests using `cltest.NewTestGeneralConfig`/`cltest.NewApplicationWithConfigAndKey` and `cltest.CreateUserWithRoleAndCookie`/`AuthenticateWithSession` helpers):
1. Set up a test app with `httptest` server registering `v2Routes` (or the full router) using `cltest.NewApplication`.
2. Create a user with `sessions.UserRoleView` and obtain a valid session cookie via the sessions controller (`POST /sessions`) or `cltest` session-creation helper.
3. Issue `GET /v2/config` and `GET /v2/config/v2` with only the view-role session cookie attached (no admin/edit role).
4. Assert the response status is `200 OK` (not `401`/`403`).
5. Decode the JSON:API body into `ConfigV2Resource` and assert `Config` contains effective configuration content (e.g. contains chain RPC URL substrings or other fields configured in the test config), proving disclosure to a view-role principal.
6. Contrast with a call to an edit-gated route (e.g. `POST /v2/bridge_types`) using the same view-role session, expecting `401/403`, to demonstrate the inconsistency/missing role check specific to `ConfigController.Show`.

```go
func (cc *ConfigController) Show(c *gin.Context) {
	cfg := cc.App.GetConfig()
	var userOnly bool
	if s, has := c.GetQuery("userOnly"); has {
		var err error
		userOnly, err = strconv.ParseBool(s)
		if err != nil {
			jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("invalid bool for userOnly: %w", err))
			return
		}
	}
	var toml string
	user, effective := cfg.ConfigTOML()
	if userOnly {
		toml = user
	} else {
		toml = effective
	}
	jsonAPIResponse(c, ConfigV2Resource{toml}, "config")
}
```

```go
// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
