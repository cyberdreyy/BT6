### Title
Login handler leaks distinguishable error message for nonexistent user vs. wrong password, enabling email enumeration - ([File: core/web/sessions_controller.go])

### Summary
`SessionsController.Create` forwards the raw error from `AuthenticationProvider().CreateSession` directly to the client as a JSON body via `jsonAPIError`, and the underlying `orm.CreateSession` implementation returns different, identifiable errors for "user not found" (`FindUser` error, e.g. `sql: no rows in result set`) versus "wrong password" (`"Invalid password"`). This lets an unauthenticated attacker enumerate valid emails by comparing the login error text, and also introduces a timing side-channel since bcrypt comparison only runs when the email exists.

### Finding Description
`SessionsController.Create` calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and on any error simply does `jsonAPIError(c, http.StatusUnauthorized, err)` [1](#0-0) . `jsonAPIError` places `err.Error()` verbatim into the JSON response body: `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))` [2](#0-1) .

In the default local-auth provider, `orm.CreateSession` first calls `o.FindUser(ctx, sr.Email)` and, if the user does not exist, returns that error (a DB-layer not-found error) immediately without an audit-log-friendly wrapper: `user, err := o.FindUser(ctx, sr.Email); if err != nil { return "", err }` [3](#0-2) . If the user is found but the password is wrong, it instead returns a distinct, hardcoded error: `pkgerrors.New("Invalid password")` [4](#0-3) .

Because these two error values differ in text and are passed unmodified through `jsonAPIError`, an attacker can send `POST /sessions` with an arbitrary email/password and distinguish "email does not exist" (DB not-found style message) from "email exists but wrong password" (`"Invalid password"`) purely from the response body — no timing analysis required, though a timing difference also exists since `utils.CheckPasswordHash` (bcrypt) is only invoked when a user record is found, adding measurable latency for valid emails. There is no generic/normalized error message or constant-time response injected at the controller or ORM boundary to unify these two outcomes; the existing `constantTimeEmailCompare` helper in the ORM only guards against timing differences in the email-string comparison itself, not the invalid-password vs. user-not-found branch distinction [5](#0-4) .

### Impact Explanation
This maps to Chainlink's user/account enumeration weakness class rather than a direct compromise: it does not grant unauthorized session or key access itself, but it lets an unauthenticated attacker cheaply build a list of valid operator emails on the node, which can then be targeted with credential stuffing or brute force against accounts holding admin/key-export privileges (e.g., via `/keys/eth/export` or similar endpoints reachable only after a successful login).

### Likelihood Explanation
No preconditions or credentials are required — the endpoint `POST /sessions` is reachable pre-authentication by design. The distinguishing signal (differing error body text) is directly observable in a single request/response round trip and is fully repeatable and scriptable, making enumeration trivial once an attacker has a candidate email list.

### Recommendation
Normalize the error returned to the client for both "user not found" and "wrong password" cases in `orm.CreateSession` (and the LDAP/OIDC equivalents) to an identical generic message (e.g., `"invalid credentials"`), and ensure `SessionsController.Create` does not leak internal error text differences. Additionally, always perform a dummy/constant-cost password hash comparison even when the user is not found, to remove the timing side channel.

### Proof of Concept
Go handler-level test plan:
1. Seed one known user via `orm.CreateUser`.
2. Call `POST /sessions` with `{"email": "nonexistent@x.com", "password": "whatever"}` and capture status code + response body + elapsed time.
3. Call `POST /sessions` with `{"email": "<seeded-user-email>", "password": "wrongpassword"}` and capture status code + response body + elapsed time.
4. Assert both currently produce **different** body text (`sql: no rows in result set`-style vs. `"Invalid password"`) — demonstrating the enumeration vector — and that the fix requires both to produce an identical status/body, with comparable elapsed time (e.g., asserting overlap within a fixed tolerance after adding constant-time hashing for the not-found branch).

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
