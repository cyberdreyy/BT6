### Title
Missing re-initialization guard allows takeover of an already-funded Lockup contract - (File: lockup/src/lib.rs)

### Summary
The `LockupContract::new` initializer lacks the `assert!(!env::state_exists(), ...)` guard that every sibling contract in this repo (`staking-pool`, `staking-pool-factory`, `whitelist`, and by convention `multisig`/`voting`) uses to make `#[init]` a one-time operation. Without this check, `new` can be called again after the lockup account already holds funds, letting a caller overwrite `owner_account_id`, `vesting_information`, `staking_information`, and `foundation_account_id`, i.e. re-point custody of all NEAR already locked in the account to an attacker-chosen owner.

### Finding Description
`LockupContract::new` is marked `#[init]` but does not verify that state does not already exist before writing a fresh `Self`: [1](#0-0) 

Compare this to the equivalent initializers in the sibling contracts in scope, which all explicitly guard against re-initialization: [2](#0-1) [3](#0-2) [4](#0-3) 

The `Default` impl for `LockupContract` only prevents non-init methods from being called before state exists (`env::panic` on missing state); it does not prevent `new` itself from being called a second time once state exists: [5](#0-4) 

Because `new` unconditionally computes `lockup_information.lockup_amount: env::account_balance()` and rebuilds the whole struct — including `owner_account_id`, `vesting_information`, `staking_information` (reset to `None`), `staking_pool_whitelist_account_id`, and `foundation_account_id` — a second call to `new` (by anyone, since there is no access-control modifier on `#[init]` methods, only the account signing the function call needs to be a valid caller of the contract) fully replaces the contract state after the first, legitimate initialization funded the account. This breaks the custody binding: "account trusted as the lockup owner versus the code/arguments that trust was granted for."

### Impact Explanation
The lockup contract account is deployed with the intent that only the account specified in the *first* `new` call has owner rights over the funds locked in it (`owner_account_id`), including the ability to invoke owner-only methods in `lockup/src/owner.rs` to withdraw, stake, or transfer once conditions are met. If `new` can be re-invoked after the account is already funded (e.g. after the initial deposit/transfer completed in the deployment batch, or after the account otherwise received funds), an attacker who manages to call `new` again can set themselves as `owner_account_id` and clear `staking_information`/`vesting_information`, effectively seizing control of all NEAR already held by the lockup account. This is a Critical-class impact: NEAR moved (via subsequent owner withdrawal) by a party not entitled to it.

### Likelihood Explanation
This is High/uncertain in practice: within the atomic deployment batch used by `lockup-factory` (`create_account` + `transfer` + `deploy_contract` + `function_call("new")` in one Promise/transaction), there is no window for an outside caller to race the initial `new` call, since all actions execute as one receipt. However, this repository also documents manual, multi-step deployment via `near-shell`/`near repl` scripts (see `scripts/deploy_lockup.sh`), and the contract's own initializer provides no defense-in-depth if `new` is ever invoked a second time through any other path (redeploy without wiping state, manual re-run of the init script, or a future integration that calls `new` outside a single atomic batch). Given every other contract in this codebase treats double-init prevention as mandatory and lockup is the one that holds the actual custody-bearing NEAR balance, the missing guard is a real code defect rather than a merely theoretical one, even though the most probable operational deployment path (atomic batched transaction) is not exploitable by an external front-runner.

### Recommendation
Add `assert!(!env::state_exists(), "Already initialized");` as the first line of `LockupContract::new` in `lockup/src/lib.rs`, mirroring the guard already present in `staking-pool/src/lib.rs`, `staking-pool-factory/src/lib.rs`, and `whitelist/src/lib.rs`, so that `new` can only ever succeed once for a given account.

### Proof of Concept
1. Lockup account `lockup1` is deployed and initialized once with `owner_account_id = "owner1"` via the documented flow (`lockup/README.md` initialization example), and receives NEAR (attached deposit / subsequent transfers).
2. Because `LockupContract::new` (`lockup/src/lib.rs:180-243`) never checks `env::state_exists()`, any account able to issue a `function_call` to `lockup1` (e.g. by reusing/adding an access key, or via any deployment/integration path that re-invokes `new` outside the original single atomic batch) can call:
```
near call lockup1 new '{"owner_account_id": "attacker", ...}' --accountId=attacker
```
3. This overwrites `owner_account_id` to `"attacker"` and resets `staking_information`/`vesting_information`, while `lockup_information.lockup_amount` is recomputed from the *current* `env::account_balance()` (which now includes all previously locked funds).
4. `attacker` can now call the owner-only methods in `lockup/src/owner.rs` to withdraw/transfer the funds that were previously locked for `owner1`. [6](#0-5)

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
