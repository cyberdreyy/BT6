### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing a request to execute below the live-member quorum - (File: multisig2/src/lib.rs)

### Summary
In `multisig2/src/lib.rs`, the `confirm()` function counts entries in a per-request `HashSet<String>` of confirmations against `num_confirmations` without verifying that each confirming principal is still a current member. `delete_member()` only purges requests that were *created* by the removed member; it does not scan and remove that member's confirmations recorded on requests created by other members. As a result, a member who confirms a request and is later removed from the multisig continues to count toward that request's threshold, allowing the request to execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` decides whether to execute a request purely based on the size of the stored confirmation set plus one: [1](#0-0) 

There is no re-validation that every account/key already present in `confirmations` is still in `self.members` at execution time.

`delete_member()` is the only cleanup path invoked when a member is removed (via a separately-confirmed `DeleteMember` request): [2](#0-1) 

It filters `self.requests` for entries whose `r.member == member` (i.e., requests the removed member *authored*) and clears confirmations only for those. It does not iterate over `self.confirmations` for requests authored by *other* members to strip out a confirmation previously cast by the now-removed member.

Binding broken: `confirmations counted (|confirmations| ) == live members who approved`. After a member is deleted, a request they previously confirmed still contains their entry in the `confirmations` set, so `|confirmations|` no longer equals the number of members currently in `self.members` who approved it. Since `confirm()` only checks `|confirmations| + 1 >= num_confirmations`, an execution can proceed with fewer live approvals than the configured threshold.

### Impact Explanation
This crosses the "confirmations counted versus live members" custody boundary explicitly called out as in-scope: a multisig request can be executed with fewer than the intended `K` live signers, effectively lowering the K-of-N threshold to K-1 (or fewer, if multiple stale confirmations accumulate across membership churn) without ever executing a `SetNumConfirmations` request. This is a Critical-class impact per the stated impact categories ("a multisig request executed below threshold"), since it allows a `Transfer`, `AddKey`, `DeployContract`, `AddMember`/`DeleteMember`, or `FunctionCall` action to be authorized and moved out of the account by fewer distinct, currently-authorized members than the multisig's security model guarantees.

### Likelihood Explanation
The bug requires a normal, expected multisig lifecycle event — a pending request that has been partially confirmed, followed by a routine `DeleteMember` action to rotate a signer — which is a common operational action (e.g. offboarding a departing signer or replacing a compromised key) rather than a contrived or privileged attacker. No foundation, owner, or victim key is required; only cooperation among enough of the existing members to pass the `DeleteMember` action and later confirmations by remaining members, which is entirely within the standard workflow of the contract. This makes the scenario realistic rather than purely theoretical.

### Recommendation
When executing `delete_member()`, iterate all entries in `self.confirmations` (not just requests authored by the removed member) and remove the deleted member's string key from every confirmation set; if removing that confirmation drops any request below its recorded threshold, leave it pending. Alternatively, revalidate at `confirm()` time (and before scheduling execution) that every principal in the stored `confirmations` set is still contained in `self.members`, discarding stale entries (and recomputing the live count) before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. Member `A` calls `add_request(R1)` (e.g., `Transfer` to an attacker-controlled receiver). `confirmations[R1] = {}`.
3. Member `D` calls `confirm(R1)`. Now `confirmations[R1] = {D}` (size 1, `< 3`, so it stays pending) — see `confirm()` logic at [3](#0-2) .
4. Separately, `A`, `B`, and `C` create and confirm a `DeleteMember { member: D }` request (3 confirmations satisfy `num_confirmations = 3`). This calls `delete_member()` [4](#0-3) , which removes `D` from `self.members` and deletes `D`'s access key, but only clears requests where `r.member == D` — `R1` (authored by `A`) is untouched, so `confirmations[R1]` still contains `D`.
5. Members remaining: `{A, B, C}`, `num_confirmations` unchanged at `3`.
6. `A` calls `confirm(R1)` — this is rejected by the "already confirmed" check only if `A` had confirmed before; assume `A` had not, so `confirmations[R1] = {D, A}` (size 2, `2+1=3 not >= 3`... actually with size 2, `+1=3 >= 3` triggers execution) — meaning after just two *live* members (`D`'s removed stale entry plus one live confirmation from `A`) the request executes, even though only 1 currently-authorized member besides the original proposer approved it, not the required 3 live signers.
7. `execute_request(R1)` runs, transferring funds out of the multisig account, despite the quorum of live, currently-authorized members never reaching `num_confirmations = 3`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
