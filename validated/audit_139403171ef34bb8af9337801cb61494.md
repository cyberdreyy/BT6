### Title
Withdrawal requests are charged a full-epoch management fee even when no epoch will run (closed pool / instant redemption path) — ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The referenced Lyra finding concerns a valuation function that unconditionally applies a withdrawal fee which the underlying protocol only charges conditionally, leaving users systematically under-paid. The analog in this codebase is the upfront management fee charged in `requestWithdraw`. The fee duration is computed by `_withdrawRequestManagementFeeDuration` as `epochDuration + remaining buffer`, on the rationale that receipts sit outside live NAV until the next epoch settles. But there are states where no next epoch will ever run — the pool has been closed via `stopEpoch(_, 1)` (`_interest == 1` recalls all principal and ends the epoch machine) — yet `requestWithdraw` still charges a full `epochDuration` of management fee, which is booked into `pendingWithdrawFees` and paid out to `feeReceiver`. Users redeeming from a closed pool are thus charged a "time in queue" fee for a queue that no longer exists.

### Finding Description
In `requestWithdraw`, every non-instant withdrawal receipt is haircut by `_totalWithdrawFees(principal, interest)` (`contracts/IdleCDOEpochVariant.sol:774-776`), and the deducted amount is accumulated into `pendingWithdrawFees` (line 778), which is later paid to `feeReceiver`/owner in `_stopEpoch` (lines 418-419, 452-456).

The fee covers the period the receipt must wait for the next epoch: `_withdrawRequestManagementFeeDuration` returns `epochDuration` plus the remaining buffer `epochEndDate + bufferPeriod - block.timestamp` (lines 925-931).

However, when the pool is in the closed/terminal state — after `stopEpoch(0, 1)` requests all principal back (`_isRequestingAllFunds`, lines 332, 367-372), or equivalently when `epochEndDate` is left at 0 and the buffer has long passed — the code still charges `epochDuration` of management fee. There is no next epoch for the receipt to wait through; the recalled principal pays the receipt directly. The same unconditional fee is applied regardless of whether the external "waiting period" exists, which is precisely the bug class of the Lyra report (fee applied in valuation where the underlying mechanics would not charge it). The instant-withdraw path (lines 761-769) already demonstrates that the codebase itself recognizes redemptions should not bear this fee when no epoch wait occurs — it bypasses `_totalWithdrawFees` entirely.

### Impact Explanation
Every lender requesting withdrawal from a closed pool (or in any state where the receipt can be settled without waiting `epochDuration`) permanently loses `principal * managementFee * epochDuration / 365 days` to `feeReceiver`/owner. For a 1% annualized management fee and a 90-day epoch this is ~0.25% of principal; the loss scales linearly with `epochDuration`, which is owner-set and can be large (tests use 365 days). This is a direct, quantified transfer of user funds, not a rounding artifact, and there is no guard preventing `requestWithdraw` in the closed state — `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are re-enabled after `stopEpoch` returns to the buffer phase.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires the pool to be closed or for a user to request withdrawal in a phase where no next epoch will run, and the fee rate must be non-zero. However, pool closure is a normal, expected lifecycle event (the `stopEpoch(0, 1)` path is explicitly supported and tested), and a lender exiting a closed pool is the canonical action in that state — so the overcharge hits the most common withdrawal flow in that state rather than an edge case. There is no economic dependence on privileged misbehavior; owner/manager act honestly, the fee simply accrues to `feeReceiver` by design. Caveat: this may be argued as intended "exit fee" behavior — the tests intentionally assert upfront management fees on requests — but no test covers the closed-pool state, and the code's own comments justify the fee solely by the epoch wait, which is absent post-closure.

### Recommendation
In `requestWithdraw` / `_withdrawRequestManagementFeeDuration`, return a zero (or minimal) management-fee duration when the pool is closed / will not start another epoch — e.g., when `epochEndDate == 0` or when a flag recording the close-pool `stopEpoch(_, 1)` call is set. Alternatively, charge the fee only on the interest component (which is zero in the closed state) rather than on principal.

### Proof of Concept
```solidity
// Foundry fork/unit PoC sketch (extends test/foundry/IdleCreditVault.t.sol helpers)
function testClosedPoolOverchargesManagementFee() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mgmtFeeRate = 1_000; // 1% annualized
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    _setManagementFee(mgmtFeeRate);

    uint256 trancheAmount = idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Run and then CLOSE the pool: stopEpoch(newApr = 0, _interest = 1)
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1); // close-pool sentinel: recalls all principal, no next epoch

    // Buffer period elapses; there is no next epoch to wait through.
    vm.warp(block.timestamp + cdoEpoch.bufferPeriod() + 1);

    uint256 principal = trancheAmount * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;
    uint256 requested = cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));

    // BUG: a full epochDuration of management fee was still charged on principal
    uint256 chargedFee = principal - requested;
    assertGt(chargedFee, 0, "fee charged despite no epoch wait");
    assertEq(
        chargedFee,
        _calcManagementFee(principal, mgmtFeeRate, cdoEpoch.epochDuration()),
        "full epoch fee charged on closed pool"
    );
    // chargedFee is booked to pendingWithdrawFees and later paid to feeReceiver,
    // even though the receipt is settled directly from recalled principal.
}
```
