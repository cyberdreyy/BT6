Based on my investigation, I found a direct analog to the external report's "missing zero-address check" bug class in the Aptos staking beneficiary-setting functions.

### Title
Missing zero-address validation in `set_beneficiary_for_operator` permanently strands operator commission - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move` and `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
Both `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` accept an arbitrary `new_beneficiary: address` and store it without any validation, including no check against the zero address (`@0x0`). [1](#0-0) [2](#0-1) 

### Finding Description
`set_beneficiary_for_operator` writes `new_beneficiary` directly into the `BeneficiaryForOperator` resource with no `assert!(new_beneficiary != @0x0, ...)` guard, unlike other address-accepting flows in the framework (e.g. `vesting::set_beneficiary` requires `account::spec_exists_at(new_beneficiary)` per its spec). [3](#0-2) 

Once a zero (or otherwise unowned) beneficiary is set, every future commission distribution routes operator payouts to that address. In `distribute_internal`, when the shareholder being paid out equals `operator`, the recipient is swapped for `beneficiary_for_operator(operator)` and the commission coins are sent via `aptos_account::deposit_coins`: [4](#0-3) 

Because `beneficiary_for_operator` simply returns whatever was last stored (including `@0x0`) with no re-validation at payout time, commission funds intended for the operator are silently redirected to the zero address on every subsequent `distribute`/`request_commission`/`unlock_stake` call. [5](#0-4) 

The identical pattern exists in the `delegation_pool` module, where `set_beneficiary_for_operator` is used for delegation-pool commission distribution. [6](#0-5) 

### Impact Explanation
This maps directly to the Stake-And-Lockup Gate's "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows." If an operator mistakenly (or is tricked/scripted into) calling `set_beneficiary_for_operator(operator, @0x0)`, all subsequent operator commission across both `staking_contract` and `delegation_pool` flows becomes unrecoverable — there is no un-set/reset function analogous to `vesting::reset_beneficiary` for operator beneficiaries in either module. The only recovery is calling `set_beneficiary_for_operator` again with a valid address, but any commission already paid out to `@0x0` in the interim is permanently lost, since no private key exists for that address.

### Likelihood Explanation
The function is `public entry`, callable directly by any operator with no elevated privilege beyond controlling their own operator key — the same self-inflicted-but-unprivileged pattern used in the external report's exploit scenario (Bob deploying `AaveV2Strategy` with a zero `aaveLmReceiver`). Since no address validation, no zero-check, and no confirmation step exists, a single mistaken transaction (or malicious frontend/dApp encouraging it) is sufficient to trigger permanent fund loss.

### Recommendation
Add `assert!(new_beneficiary != @0x0, error::invalid_argument(EINVALID_BENEFICIARY))` in both `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` before storing the value, and consider adding a `reset_beneficiary_for_operator` recovery path analogous to `vesting::reset_beneficiary`.

### Proof of Concept
1. Operator calls `staking_contract::set_beneficiary_for_operator(operator_signer, @0x0)` (or the `delegation_pool` equivalent). No abort occurs. [1](#0-0) 
2. Rewards accrue and staker/anyone calls `request_commission` / `distribute` / `unlock_stake`, which invoke `distribute_internal`. [7](#0-6) 
3. Inside `distribute_internal`, the operator's commission share is redirected to `beneficiary_for_operator(operator)` == `@0x0` and deposited there via `aptos_account::deposit_coins`. [4](#0-3) 
4. The commission is now controlled by an address with no corresponding private key, permanently stranding operator commission funds.

**Note on residual uncertainty:** I could not fully verify the exact runtime behavior of `aptos_account::deposit_coins` when targeting `@0x0` (whether it silently succeeds and creates an account resource, or aborts) because that function's implementation was not retrieved in this session — a Devin session with full repo access would be needed to confirm whether the deposit itself reverts or whether it succeeds and truly strands the funds.
