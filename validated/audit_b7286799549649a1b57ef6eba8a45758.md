## Analysis

The external report's core invariant is: **a single unvalidated/uncontrollable piece of state, once embedded in a shared account, permanently blocks an otherwise-legitimate operation for everyone sharing that state** (bad `asset_type` → all swaps against the pool permanently fail).

The Aptos-native analog I found is in `aptos_framework::staking_contract`'s **shared distribution pool payout loop**.

### Finding Description

`staking_contract::distribute_internal` iterates over *every* shareholder currently owed funds in a single `StakingContract.distribution_pool` and pays them all out in one atomic loop: [1](#0-0) 

Both the staker's unlocked stake and any pending, unpaid operator commission live in the **same** `distribution_pool`. This is by design — the module doc explains commissions and staker withdrawals share the same shares-based pool: [2](#0-1) .

`switch_operator` explicitly leaves the **old operator's unredeemed commission shares** inside the same `distribution_pool` that keeps being used for the staker's future unlocks, since it force-triggers `distribute_internal` and `request_commission_internal` on the pool before moving the `StakingContract` struct to the new operator key: [3](#0-2) . `add_distribution` (called from `unlock_stake`) adds the staker's own new distribution into that exact same pool object: [4](#0-3) .

`distribute()` is explicitly permissionless — "Allow anyone to distribute already unlocked funds" — and pays out the entire pool atomically: [5](#0-4) .

Each recipient in the loop is paid via `aptos_account::deposit_coins`, which — per the standard Aptos framework `aptos_account` module semantics — aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has not registered a `CoinStore<AptosCoin>` **and** has disabled direct coin transfers via `coin::set_allow_direct_coin_transfers(false)` (a normal, unprivileged, self-service call any account can make). I could not re-verify `aptos_account.move`'s exact source in this session (tool budget exhausted), but this is the documented and well-known behavior of that function; a background agent should confirm it directly against `aptos_account.move` in this repo before filing.

### Impact Explanation

Because the payout loop is atomic and unconditional (no per-recipient try/skip logic — see the `while` loop at lines 889–911), if **any single shareholder in the shared pool** — most easily a **former operator** who was switched away from via `switch_operator` before their commission became fully withdrawable — has disabled direct coin transfers and lacks a registered `CoinStore<AptosCoin>`, then every future call to `distribute()` on that `StakingContract` reverts forever. Since the staker's own unlocked/inactive stake sits in the very same `distribution_pool`, this permanently traps the staker's stake withdrawal alongside the poisoned operator entry. There is no way to remove or skip a single bad shareholder from the shared pool. This is a permanent, non-recoverable loss of withdrawal rights for the staker (and vesting shareholders relying on `vesting::distribute`, which delegates into this same code path), caused entirely by an unprivileged actor (the former operator) acting on their own account.

### Likelihood Explanation

- Setting `allow_direct_coin_transfers = false` on one's own account is a normal, unprivileged, publicly documented operation.
- `switch_operator`/`switch_operator_with_same_commission` are staker-initiated but the *former* operator does not need to cooperate or be notified — they can pre-emptively disable transfers on their own account at any time before being switched away from, as a griefing setup.
- Once the old operator has any unredeemed commission share left in the pool at switch time (a very common case — commission that is unlocked but not yet past the stake pool's lockup, hence not yet distributed), the DoS is unconditionally triggered on the next `distribute()` call.
- No special privilege, and no cooperation from the staker, is required from the attacker.

### Recommendation
- In `distribute_internal`, wrap each recipient's `aptos_account::deposit_coins` call so that a failing/ineligible recipient's payout is skipped or diverted (e.g., held in an escrow entry) rather than aborting the whole loop, so unrelated shareholders (especially the staker) are never blocked.
- Alternatively, disallow removing/blocking direct-transfer eligibility for addresses that hold outstanding shares in an active `distribution_pool`, or force-register/verify recipients' eligibility at the time shares are bought into the pool (`add_distribution`/`request_commission_internal`) rather than at redemption time.

### Proof of Concept
1. Staker `S` creates a staking contract with operator `O1`, `commission_percentage = 10`.
2. `O1` calls `coin::set_allow_direct_coin_transfers(false)` on their own account, and never registers `CoinStore<AptosCoin>` (fresh account).
3. `O1` operates the validator; rewards accrue. `S` calls `staking_contract::switch_operator(S, O1, O2, ...)`, which internally calls `request_commission_internal` for `O1`, buying `O1` shares into the shared `distribution_pool` for the still-locked commission (not yet withdrawable because stake pool lockup hasn't expired).
4. Time passes; the lockup expires, making the pool's inactive/pending_inactive stake (including `O1`'s commission and any of `S`'s own newly unlocked stake) withdrawable.
5. `S` (or anyone) calls `staking_contract::distribute(S, O2)`. `distribute_internal` iterates the `distribution_pool`, reaches `O1`'s entry, and `aptos_account::deposit_coins(O1, ...)` aborts because `O1` cannot receive direct transfers and has no registered coin store.
6. The entire transaction reverts. `S`'s own withdrawable stake in the same pool can never be distributed as long as `O1`'s entry remains and `O1` keeps direct transfers disabled — permanently locking `S`'s funds.

**Uncertainty / unverified**: I could not re-confirm the exact abort condition inside `aptos_account::deposit_coins` and `coin::set_allow_direct_coin_transfers` in this repository within the available tool budget — this should be verified against `aptos-move/framework/aptos-framework/sources/aptos_account.move` and `coin.move` before treating this as fully proven.

        let distribution_pool = &mut staking_contract.distribution_pool;
