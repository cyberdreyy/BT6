### Title
Meta-transaction (`DelegateAction`/`DelegateActionV2`) signing payload omits any chain-binding data, allowing a `SignedDelegateAction` created under a `FunctionCall`-restricted key on one network to execute with `FullAccess` authority on another network sharing the same `account_id`/`public_key` — ([File: runtime/runtime/src/actions.rs])

### Summary
`validate_delegate_action_key` derives the permission check purely from the *executing* chain's current on-chain `AccessKey` state for `(sender_id, public_key)`, looking up `access_key.permission.function_call_permission()` at execution time. Because the NEP-461 signable payload for `DelegateAction`/`DelegateActionV2` (`get_nep461_hash`, `SignableMessage`) contains no chain identifier, the exact same signed bytes are valid on any NEAR-protocol chain where that account/key pair exists, and the authority granted to the relayed action is determined entirely by that chain's local key state rather than the signer's intent at signing time.

### Finding Description
`DelegateAction`/`DelegateActionV2` (`core/primitives/src/action/delegate.rs`) contain only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` — there is no `chain_id`/`genesis_hash` field. The signature is computed over `SignableMessage::new(&delegate_action, SignableMessageType::DelegateAction[/V2])` and hashed with `get_nep461_hash()` [1](#0-0) , none of which mix in any chain-identifying data [2](#0-1) .

On execution, `validate_delegate_action_key` fetches the access key that currently exists for `(sender_id, public_key)` on the chain processing the receipt via `get_access_key(state_update, sender_id, public_key)`, and only then inspects `access_key.permission.function_call_permission()` to decide whether to enforce the receiver/method-name/no-deposit restrictions [3](#0-2) . If that lookup returns `None` (i.e., the key is `FullAccess` on this chain), the entire receiver-id/method-name/deposit gating block is skipped [4](#0-3) , and the delegate's inner actions are dispatched with full authority.

Exploit flow: a victim signs a `SignedDelegateAction` intended for chain A, using a key that is registered there as `FunctionCall`-restricted to receiver `R1`/method `M1`. If the same `account_id` and `public_key` also exist on chain B (e.g., a shared-seed/HD-derived key registered independently as `FullAccess` on B — a plausible real-world setup since key material and account naming conventions are often reused across NEAR networks/forks), an attacker who intercepts or is otherwise handed the relayed bytes (e.g., a malicious or compromised relayer, or simply anyone who can see the meta-transaction payload before/after being relayed) can resubmit the identical borsh bytes to chain B's RPC. `SignedDelegateAction::verify()`/`VersionedSignedDelegateAction::verify()` will succeed on B because signature verification only checks the ed25519 signature over the (chain-agnostic) NEP-461 hash [5](#0-4) , and `validate_delegate_action_key` on B will resolve the `FullAccess` permission, bypassing the `R1`/`M1` scoping the signer explicitly encoded into the delegate action for A.

No existing check closes this gap: nonce validation is scoped to the local access key's nonce (`current_nonce`/`delegate_nonce`), which is chain-local state and does not encode or bind to a chain identity [6](#0-5) ; `max_block_height` is likewise a chain-local block height with no chain-identity semantics.

### Impact Explanation
This is authorization escalation across the trust boundary the signer intended: an action explicitly scoped by the signer to a specific receiver/method under `FunctionCallPermission` executes instead with `FullAccess` authority (arbitrary actions, including `Transfer`, `DeployContract`, `AddKey`/`DeleteKey`, `Stake`, etc.) on a different network, purely because that other network's independent access-key state happens to grant broader permission to the same public key. Where the reused account also holds funds/authority on chain B, this can lead to unauthorized transactions and potential loss/misuse of funds under an authority level the signer never granted for that chain — matching NEP-366/meta-transaction "authorization escalation across accounts or promises" impact category.

### Likelihood Explanation
This requires the specific precondition that the same `(account_id, public_key)` exists on two NEAR-protocol-compatible networks with differing access-key permissions (e.g., testnet/mainnet, or a fork/appchain sharing the same account-naming and key-derivation conventions) — a realistic but non-default configuration (shared HD wallets/seed reuse across networks, or identical account bootstrap on multiple chains). Given that precondition, the attack is a pure replay: capture the signed bytes once (as the relayer role in NEP-366, which any unprivileged party can act as) and resubmit to the other chain's public RPC; no cryptographic break, no privileged access, and it is fully repeatable for any number of such delegate actions.

### Recommendation
Include a chain-binding value (e.g., `genesis_hash` or a `chain_id`) inside the signed `DelegateAction`/`DelegateActionV2` payload (part of the NEP-461 `SignableMessage`), and have `validate_delegate_action_key` (or an earlier validation stage) reject delegate actions whose embedded chain identifier does not match the executing chain's own identifier, mirroring how ordinary `Transaction`s are implicitly scoped to a single chain's mempool/state by convention.

### Proof of Concept
1. Unit test in `runtime/runtime/src/actions.rs` extending the existing `test_delegate_action_key_permissions_*` harness:
   - Build a `DelegateAction`/`DelegateActionV2` signed once with `sender_id`/`public_key` fixed, targeting `receiver_id = R1` with a single `FunctionCall` action for method `M1`.
   - Chain-A state: set up `AccessKey { permission: AccessKeyPermission::FunctionCall(FunctionCallPermission { receiver_id: R1, method_names: [M1], .. }), .. }` for `(sender_id, public_key)`; call `validate_delegate_action_key`; assert it succeeds only when receiver/method match, and fails (`ReceiverMismatch`/`MethodNameMismatch`) for a different receiver/method — establishing the intended restriction.
   - Chain-B state: using the identical `SignedDelegateAction` bytes (same signature), set up `AccessKey { permission: AccessKeyPermission::FullAccess }` for the same `(sender_id, public_key)`, then replace the single `FunctionCall` action with an arbitrary/unrelated action list (e.g., `Transfer` or `AddKey`) that would have been rejected under A's restriction; call `validate_delegate_action_key`; assert `result.result.is_ok()` — demonstrating identical signed bytes produce a permissive outcome purely due to chain-B's local key state.
2. Confirm via `SignedDelegateAction::verify()`/`VersionedSignedDelegateAction::verify()` that the same signature validates in both "chain" contexts (no chain-specific data is checked), completing the PoC that signature validity and permission scoping are decoupled from chain identity.

    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
        let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
        hash(&bytes)
    }

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
