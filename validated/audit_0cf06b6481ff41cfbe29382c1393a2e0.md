### Title
Missing chain-id domain separation on `BlockAccepted` signatures enables cross-network/cross-environment replay of signer acceptances - (File: `libsigner/src/v0/messages.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
`BlockAccepted` (the signer's block-acceptance vote) is signed over the raw `signer_signature_hash` with no chain/network binding, while `BlockRejection` — created in the same code path — explicitly binds its signature to `chain_id` via SIP-018 structured data. This asymmetry means an acceptance signature is not scoped to the network/environment it was produced for, unlike a rejection.

### Finding Description
`Signer::create_block_acceptance` signs only the bare block header hash: [1](#0-0) 
```
pub fn create_block_acceptance(&self, block: &NakamotoBlock) -> BlockAccepted {
    let signature = self
        .private_key
        .sign(block.header.signer_signature_hash().bits())
        ...
```
There is no `chain_id`, network flag, or any other domain separator mixed into the signed payload.

By contrast, `BlockRejection::hash()` explicitly builds a SIP-018 structured-data domain that includes `self.chain_id`: [2](#0-1) 
```
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
```
and `BlockRejection` carries a `chain_id` field precisely for this reason: [3](#0-2) 

On the verification side (both the peer-signer path and the miner/coordinator path), the acceptance signature is checked purely against `signer_signature_hash.bits()`/`.as_bytes()` with no chain-id check: [4](#0-3) [5](#0-4) 

`signer_signature_hash` is derived purely from the Nakamoto block header fields (`consensus_hash`, `parent_block_id`, `tx_merkle_root`, `state_index_root`, `timestamp`, etc.) — `chain_id` is not itself part of the header and is only checked by the node's HTTP validation endpoint (`postblock_proposal.rs`) against the local chainstate's configured `chain_id`, not baked into the hash that signers sign over: [6](#0-5) 

Because the acceptance signature is not bound to `chain_id`/network, an acceptance signature is portable across any two deployments that (a) share overlapping signer keys and (b) can produce (or already share) a block header with the identical `signer_signature_hash` — this is exactly the deployment topology the external report's replay-attack scenario anticipates (staging vs. mainnet, or any two environments intentionally kept close so their state/hashes can be compared/verified against each other). The team's own stated design goal — "It's actually necessary to have the environment NOT baked into releaseHash... a testnet may have a particular releaseHash, and the mainnet proposal will necessarily want to propose the identical releaseHash" — describes precisely a scenario where identical artifacts (and by extension, potentially identical or attacker-crafted-identical block headers/hashes) are expected to exist across environments that reuse operator/signer keys. In that topology, a `BlockAccepted` vote collected in one environment is a bit-for-bit valid `BlockAccepted` vote in the other, silently inflating the acceptance-weight tally counted by `store_and_process_block_signature` / the node's `signer_coordinator`.

### Impact Explanation
This is a cross-context-valid signature: the same bytes that constitute a valid `BlockAccepted` signature in environment/network A also validate as a `BlockAccepted` signature in environment/network B, because the signed payload carries no chain identifier. If a signer's key is shared or reused across a testnet/mainnet pair (or any two networks that a single custodial signer operator runs), acceptance votes harvested from one network can be replayed into the other network's tally, contributing toward the 70% signing-weight threshold without that signer having actually validated or accepted the specific proposal in that network's context — directly matching the "Critical" impact class: a rejection/acceptance vote miscounted / a cross-context-valid signature.

### Likelihood Explanation
Exploitability depends entirely on operational key reuse across networks/environments and on being able to produce (or already possess) two blocks whose headers hash identically across those environments — a condition explicitly discussed as plausible by the project's own reasoning about environment parity in the external report excerpt. Given `BlockRejection` was deliberately hardened with `chain_id` domain separation while `BlockAccepted` was not, this looks like an oversight in an otherwise-recognized threat model rather than a hypothetical concern.

### Recommendation
Bind `BlockAccepted` signatures to `chain_id` (and ideally to the signer's own reward-cycle/protocol version) using the same SIP-018 structured-data domain approach already used for `BlockRejection`, and have peers verify the acceptance signature against the expected chain-id domain rather than the raw hash. Apply the same audit to `BlockPreCommit` and any other signer-vote message type that currently signs the bare `signer_signature_hash`.

### Proof of Concept
Not independently reproducible from the indexed code alone without also confirming whether `BlockPreCommit`'s serialization/signing routine (`libsigner/src/v0/messages.rs`) similarly omits chain-id binding — the search only confirmed 9 references to `BlockPreCommit` in that file but did not resolve its `sign`/`hash` implementation details before the tool budget ended. Given the codebase index's size limits, if a full trace of `BlockPreCommit`'s signing code is needed, a Devin session with full file access would be required to confirm whether the same gap extends to pre-commit votes.
