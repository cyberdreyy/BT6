### Title
Single non-conforming shareholder can permanently brick a vesting contract's `distribute` path, stranding all shareholders' and the admin's funds - ([File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
The Optimism report's root cause is a shared payout path that lets a single unprivileged actor's failure condition abort the *entire* atomic operation, destroying a recoverable state that other, uninvolved parties depended on. The Aptos analog is `vesting::distribute()` at [1](#0-0) , which loops over **all** shareholders in a single transaction and calls `aptos_account::deposit_coins` for each one unconditionally. If any single shareholder address is unregistered for `AptosCoin` and has opted out of direct coin transfers, that one call aborts, and because Move transactions are atomic, the abort reverts the *whole* `distribute()` call — permanently blocking payouts to every other shareholder and the admin, with no recovery path.

### Finding Description
`aptos_account::deposit_coins` only auto-registers a recipient and proceeds if the recipient either is already registered for the coin type or has not opted out of direct coin transfers: [2](#0-1) 

Any account holder can, without any privilege, call the public entry function that disables `allow_arbitrary_coin_transfers` on their own account (the `DirectTransferConfig` resource), and simply never register a `CoinStore<AptosCoin>`. Once that account is one of the shareholders of a vesting pool, any call to `distribute()` will hit `aptos_account::deposit_coins(recipient_address, share_of_coins)` for that shareholder inside the `for_each_ref` loop: [1](#0-0) 

Since `coin::is_account_registered` is false and `can_receive_direct_coin_transfers` is false for that address, the `assert!` inside `deposit_coins` aborts. Move's transaction atomicity means this single failure reverts the entire `distribute()` call, including deposits already computed for all other well-behaved shareholders and the dust transfer to the withdrawal address.

Crucially, `distribute()` is not an isolated, optional call — it is invoked from every meaningful exit path of the vesting contract:
- `vest()` calls `unlock_rewards()` then unlocks vested stake, and eventually payouts flow through `distribute()`.
- `terminate_vesting_contract()` explicitly calls `distribute(contract_address)` as its first step before the admin can even mark the contract terminated: [3](#0-2) 
- `admin_withdraw()` requires `state == VESTING_POOL_TERMINATED` (only reachable via `terminate_vesting_contract`) and also calls `withdraw_stake` → `distribute`-adjacent flows: [4](#0-3) 

The vesting module explicitly acknowledges this exact class of bug for the *beneficiary* path — `set_beneficiary` requires `assert_account_is_registered_for_apt(new_beneficiary)` specifically "so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered": [5](#0-4) 

However, this guard is applied only when an admin explicitly reassigns a beneficiary via `set_beneficiary`. It is **not** applied to the raw shareholder addresses supplied at `create_vesting_contract` time, nor is there any function to remove/replace a poisoned shareholder afterward. A shareholder that never gets a beneficiary override (the common case) is paid directly via `get_beneficiary` returning the shareholder address itself, with no registration check ever performed on that address.

### Impact Explanation
Because `terminate_vesting_contract` and `admin_withdraw` both depend on a successful `distribute()`, a single malicious or careless shareholder (an inherently unprivileged role — shareholders have no admin control over the contract) can:
1. Permanently block reward/vesting distribution to every other shareholder in the same pool.
2. Permanently block the admin from ever terminating the vesting contract (since `terminate_vesting_contract` calls `distribute` first and will always abort).
3. Permanently block `admin_withdraw` (unreachable state), stranding the entire remaining grant and accumulated rewards for all parties, including the withdrawal address, indefinitely.

This is a full denial of the vesting flow's core value-recovery mechanisms with no mitigation — a non-recoverable stranding of stake/vesting funds for uninvolved third parties, matching the "Permanent lock or non-recoverable loss of claim rights ... in vesting flows" impact class.

### Likelihood Explanation
The precondition is trivial and fully unprivileged: any address can be created, immediately call `set_allow_direct_coin_transfers(false)`, and never register `AptosCoin`. The only external dependency is that a vesting admin adds this address as one of the (up to 30) shareholders — plausible in any multi-employee/DAO vesting arrangement where the admin does not control every shareholder's on-chain behavior, or where a shareholder is deliberately malicious/griefing. No governance or privileged access is needed to trigger the abort once included.

### Recommendation
- Validate that every shareholder address passed to `create_vesting_contract` is registered for `AptosCoin` (mirroring the existing `assert_account_is_registered_for_apt` check used in `set_beneficiary`), or
- Make the per-recipient payout in `distribute()` defensive: wrap each `aptos_account::deposit_coins` call so a failure for one recipient does not abort the whole distribution (e.g., skip failing recipients and accumulate their share into a separately claimable/dust pool, or use `coin::is_account_registered`/`can_receive_direct_coin_transfers` pre-checks per recipient to redirect unpayable amounts to the withdrawal address instead of aborting the entire loop).

### Proof of Concept
1. Attacker creates a fresh account `A` and calls `aptos_account::set_allow_direct_coin_transfers(A, false)`; `A` never registers a `CoinStore<AptosCoin>`.
2. A vesting admin calls `vesting::create_vesting_contract(..., shareholders = [honest_1, honest_2, A], ...)` including `A` as one of several shareholders.
3. Time passes; rewards/vesting accrue and become withdrawable (`stake::fast_forward_to_unlock`).
4. Anyone calls `vesting::distribute(contract_address)` (permissionless, no signer argument). The loop reaches shareholder `A`, calls `aptos_account::deposit_coins(A, share_of_coins)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` because `A` is unregistered and has opted out.
5. The entire `distribute()` transaction aborts — `honest_1` and `honest_2` receive nothing despite being fully entitled, and the operation can never succeed as long as `A` remains a shareholder in that state.
6. The admin's attempt to call `terminate_vesting_contract` also aborts (it calls `distribute` first), permanently preventing termination and `admin_withdraw`, stranding all remaining grant funds in the vesting contract's resource account.
