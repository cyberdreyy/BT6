Confirmations from a deleted multisig member remain counted toward `num_confirmations`, allowing execution below the intended live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` decides whether a request is ready to execute purely by counting the size of the `confirmations` set for that request. `delete_member` removes a departing member from `self.members`, but only purges `confirmations`/`requests` for requests that member *originally created* — it never scans other requests' `confirmations` sets to strip votes the departing member cast as a *confirmer*. A stale confirmation from a removed member therefore keeps counting toward the execution threshold, letting a request execute with fewer live-member confirmations than `num_confirmations` requires.

### Finding Description
The custody/authorization binding this contract must maintain is: **confirmations counted == confirmations from currently live members**. That equality is broken.

- `confirm()` (multisig2/src/lib.rs:294-315) checks only `confirmations.len() as u32 + 1 >= self.num_confirmations` — it never re-validates that every account/key already present in the `confirmations` set is still in `self.members`.
- `delete_member()` (multisig2/src/lib.rs:356-379) removes the member from `self.members`, deletes its access key, and cleans up `num_requests_pk`. It only clears `confirmations`/`requests` for requests where `r.member == member`, i.e., requests the removed member itself *authored* (line 362-371, `filter_map(|(k, r)| if r.member == member ...)`). It does **not** iterate `self.confirmations` to remove the departing member's vote from requests authored by *other* members that the departing member had merely confirmed.
- `current_member()` (multisig2/src/lib.rs:322-339) is only used to validate the *caller* of `add_request`/`confirm`/`delete_request`; it plays no role in re-validating the historical contents of a `confirmations` set.

This exactly mirrors the ENS `NameWrapper` bug class: an indirect/partial check (`ens.owner(node) != address(this)`, here: "is this the request the removed member created?") is used as a proxy for a stronger invariant ("does the DB/confirmation-set correctly reflect current trusted state?"), letting stale/forged entries persist and be relied upon later.

### Impact Explanation
This crosses the "confirmations counted versus live members" boundary explicitly called out as in-scope. A malicious or subsequently-compromised member can confirm a high-value request (e.g., `Transfer`, `AddKey` with a full-access key, or `FunctionCall`) that has not yet reached quorum, then be removed from the multisig via a legitimate `DeleteMember` request. The stale confirmation from the now-removed member is never purged from that other request's `confirmations` set. When the remaining live members later confirm it, the count (including the ghost vote) reaches `num_confirmations` even though the number of currently-authorized signers who approved it is one less than intended. This can result in unauthorized execution of a `Transfer` (NEAR moved by a party — the ghost voter — no longer entitled to authorize it) or an `AddKey`/`FunctionCall` action executed below the configured threshold, i.e. **a multisig request executed below threshold**, which is explicitly listed as a Critical-severity impact category.

### Likelihood Explanation
The attack requires the attacker to be (or have been) a multisig member — a member removed via governance is not a privileged/foundation actor and is exactly the kind of "unprivileged former-insider" scenario allowed by the rules (it does not require the foundation, a contract owner, a victim key, or a redeploy). The sequence — confirm, then get removed via a routine `DeleteMember` request (e.g., key rotation, offboarding), then have others push the request past quorum — is a plausible and reproducible operational sequence, not a theoretical edge case, since nothing in the code prevents it.

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` (not just requests authored by the removed member) and remove the removed member's `to_string()` key from every confirmation set. Alternatively, when counting confirmations in `confirm()`, filter the stored `confirmations` set against `self.members` before comparing against `num_confirmations`, so stale votes from removed members never count toward the threshold.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. Member `D` calls `add_request` (as some other member, e.g. A) then `D` calls `confirm(request_id)` — `confirmations = {D}` (size 1, below 3).
3. Members submit and confirm a separate `DeleteMember { member: D }` request (self-request, needs 3 confirmations from A/B/C — unrelated to the first request), which executes and removes `D` from `self.members`. Per `delete_member`, since the pending request was authored by `A` (not `D`), it is **not** cleaned up; `D`'s confirmation entry remains in `confirmations` for that request.
4. Members `A` and `B` confirm the original request: `confirmations.len() + 1 >= 3` becomes true (1 stale `D` vote + A + B = 3), and `execute_request` runs — even though only 2 currently-live members (A, B) actually approved it, one fewer than the configured `num_confirmations = 3`.
