### Title
Miner-Controlled Activity-Timer Refresh Lets a Single Miner Indefinitely Suppress the `block_proposal_timeout` Inactivity Check - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
The signer's miner-inactivity detection (`SortitionState::is_timed_out`) is gated on a `last_activity_time` value that is refreshed every time `SortitionData::check_latest_block_in_tenure` observes *any* conflicting/low block proposal for a tenure whose last known block has not yet been globally signed. Because this refresh condition (`info.signed_group.is_none_or(...)`) is satisfied unconditionally whenever the tenure's last-known block is still only locally/pre-committed, a single miner can keep resubmitting stale, invalid, or non-canonical proposals faster than `block_proposal_timeout` to perpetually reset its own activity clock — exactly mirroring the referenced bug class where an outcome (there: compounding APY; here: the inactivity/timeout decision) depends on the *frequency* of a triggerable action rather than a fixed, frequency-independent condition.

### Finding Description
`SortitionState::is_timed_out` (both `v1.rs` and `v2.rs`) computes elapsed time as `now - last_activity_time` (falling back to burn-block receive time) and compares it against `block_proposal_timeout`: [1](#0-0) 

`last_activity_time` is written by `SignerDb::update_last_activity_time`, which is invoked from `SortitionData::check_latest_block_in_tenure` whenever a proposed block conflicts with (is not higher than) the tenure's currently known last block: [2](#0-1) 

The refresh condition is `info.signed_group.is_none_or(|signed_time| signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs())`. When the tenure's last known block has not yet reached `signed_group` (globally-signed) state — a routine condition whenever the miner is slow, or whenever the signer's local view of the tenure has only a locally/pre-committed block — this evaluates to `true` unconditionally, with **no bound on how many times or how quickly it can be triggered**. The same unconditional refresh also occurs for the "fresh pre-commit" branch: [3](#0-2) 

This function is the sole activity-writer feeding `is_timed_out`, which `SortitionsView::check_proposal` uses to decide whether to mark the current or prior sortition's miner `InvalidatedBeforeFirstBlock` (the mechanism that lets the signer set fall back to a different miner): [4](#0-3) 

Because `update_last_activity_time` is keyed by `block.header.consensus_hash` — the tenure of the *newly proposed* block — a miner can submit a rapid stream of otherwise-rejected proposals (e.g., stale chain-length values, or blocks that just barely fail the `chain_length` check) that are still cheap for the signer to receive and process. Each such submission refreshes the very activity clock that `is_timed_out` reads for that miner's own tenure, so as long as the miner submits at least one such proposal per `block_proposal_timeout` window, `is_timed_out` never returns `true` for it — a wedge fully controlled by the frequency of proposals the miner chooses to send, not by whether it is actually producing valid blocks.

### Impact Explanation
This breaks the liveness guarantee `block_proposal_timeout` is meant to provide: it is supposed to be an absolute deadline after which an unresponsive/malicious miner is marked invalid so the signer set falls back to the previous miner or otherwise recovers. By controlling the *frequency* of low-cost, rejected proposal submissions, a single miner can hold that deadline open indefinitely, preventing the signer set from ever invalidating it (`InvalidatedBeforeFirstBlock`) even though it never produces a signable block. This matches the specified High-impact bucket: "a signer wedged into never signing valid blocks... or acting on a stale reward set/threshold" — here the signer set is wedged waiting on a miner that is never declared inactive, stalling chain progress for as long as the miner keeps sending cheap conflicting proposals.

### Likelihood Explanation
This requires no signer collusion, no majority, and no cryptographic material beyond what any sortition winner already has: any miner that wins a sortition slot can simply keep re-submitting proposals (even ones that will be locally rejected for chain-length mismatch) at a rate faster than `block_proposal_timeout`. The relevant refresh branch (`signed_group.is_none_or(...)`) is the common case whenever the tenure hasn't yet reached global signature, which is frequent in normal operation (slow validation, network partitions, or an intentionally slow/uncooperative miner), making the attack easy to trigger without any unusual preconditions.

### Recommendation
Decouple the inactivity deadline from the frequency of externally-triggered refresh events. Options: (1) bound `update_last_activity_time` refreshes to a fixed number of occurrences or to only the very first observed conflicting proposal per tenure, rather than allowing every subsequent conflicting proposal to reset the timer; (2) base `is_timed_out` on the tenure's original burn-block receive time only (not a repeatedly-resettable activity clock) except where a signature was genuinely produced; or (3) rate-limit how often `check_latest_block_in_tenure`'s activity-refresh branch may extend the deadline within a single tenure.

### Proof of Concept
1. A miner wins sortition for tenure T and becomes `cur_sortition`/`last_sortition` under `SortitionsView`.
2. Instead of producing a valid, higher block, the miner repeatedly proposes blocks whose `chain_length` does not exceed the tenure's currently known last block (trivial to construct, and cheap since these are rejected before full node validation in many cases).
3. Each such proposal reaches `SortitionData::check_latest_block_in_tenure`, hits `info.signed_group.is_none_or(...)` (true because the tenure's last block has no `signed_group` timestamp yet), and calls `signer_db.update_last_activity_time(&block.header.consensus_hash, now)`. [5](#0-4) 
4. As long as step 2–3 repeats at an interval shorter than `block_proposal_timeout`, `SortitionState::is_timed_out` for that tenure's consensus hash never observes `elapsed > block_proposal_timeout`, so `check_proposal` never sets `miner_status = InvalidatedBeforeFirstBlock`. [6](#0-5) 
5. The signer set therefore never falls back to a prior miner for this tenure, stalling block production while the malicious/unresponsive miner produces no valid, signable block — a liveness wedge sustained purely by the frequency of low-cost proposal submissions rather than by any legitimate mining activity.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
