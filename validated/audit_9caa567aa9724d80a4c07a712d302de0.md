### Title
Non-alphabet byte inside a token value truncates masking and leaks the real secret suffix unmasked - ([File: common/buildlogger/internal/tokensanitizer/token_masker.go])

### Summary
`tokenSanitizer.Write` stops masking the moment it hits a byte that is not in the hardcoded `alphabet` table, flushes `[MASKED]` for the portion matched so far, and then treats everything after that byte as ordinary, unrelated data. If the true secret value (or attacker-influenced data immediately following a real secret in the same buffer) contains such a byte, every remaining byte of the real secret is written to the underlying writer (the job trace) completely unmasked.

### Finding Description
In `tokenSanitizer.Write` (`common/buildlogger/internal/tokensanitizer/token_masker.go:104-203`), once the configured prefix (e.g. `glpat-`) is fully matched (`m.matching == len(m.prefix)`), the code enters a scan loop: [1](#0-0) 

For every byte in `alphabet`, it keeps advancing `last`/`n` and setting `m.masked = true`, treating the token as still being masked. The instant it encounters a byte that is *not* in `alphabet`, it:
1. Emits `mask` (`[MASKED]`) for the bytes matched so far.
2. Sets `m.matching = 0` and `m.masked = false`.
3. Falls straight through into the "look for the next prefix occurrence" branch (`bytes.IndexByte(p[n:], m.prefix[0])`), *without re-masking or skipping* the offending byte and everything after it.

Because `last` was pinned at the position right before the offending byte, and no code path advances `last` again unless a brand-new full prefix match is later found, the eventual `m.next.Write(p[last:n])` at the end of the function (or on the next loop's flush) sends the offending byte **and all subsequent bytes — including the true remainder of the secret — to the next writer completely unmasked**.

The masking boundary is therefore not "end of this occurrence of the secret," but "first byte not in `alphabet`." Any of the covered token types (`glpat-`, `gloas-`, `gldt-`, `glrt-`, `glcbt-`, `glrtr-`, `glptt-`, `glft-`, `glimt-`, `glagent-`, `glsoat-`, `glffct-`, `_gitlab_session=`, `gltok-`) whose actual value contains a byte outside `-, ., 0-9, A-Z, _, a-z, =` (e.g. `+`, `/`, `:`, `~`, whitespace) will have everything after that byte leak in cleartext into the build log/trace, even though the writer believes (via the `[MASKED]` emission) that it has hidden the token.

No other check in this file compensates for this: there is no fallback re-scan for the prefix starting mid-buffer at the offending byte, and `Close()` (`token_masker.go:206-225`) only handles the case where masking is still in progress at end-of-stream — it does not protect the mid-stream truncation case described here.

### Impact Explanation
Partial secret exfiltration via the job trace: the prefix and leading alphabet-conformant portion of a real token are masked, but any trailing bytes after a single non-alphabet character are written verbatim to the trace output that is stored/displayed by GitLab (job log). This directly violates the core invariant that "Secrets, tokens, and masked values must not leak across jobs, projects, logs, traces, caches, artifacts, or sessions."

### Likelihood Explanation
Requires only that a value beginning with one of the masked prefixes, followed by at least one alphabet-conforming byte then a byte outside `alphabet`, then more real secret bytes, reaches `Write()` in a single logical token stream — e.g., any secret whose format is not strictly limited to the assumed alphabet, or any log line built by concatenating a masked-prefixed value with other attacker/job-controlled text without a separator recognized as terminating the token (which is exactly the runtime behavior here since ANY non-alphabet byte is treated as terminal). This is fully deterministic and reproducible with a simple unit test; no privilege escalation or admin compromise is needed.

### Recommendation
Change the boundary-detection semantics so hitting a non-alphabet byte only ends the *masked run* but resumes normal unmasked forwarding strictly at that boundary — this already happens correctly for the boundary byte itself, but the fix should ensure the scanning/prefix-search logic advances `last` past the boundary byte immediately (rather than leaving `last` fixed and relying on finding a fresh prefix occurrence) and continues writing subsequent bytes through the normal masked/unmasked write path byte-by-byte rather than only being able to resume masking after another full prefix match. Concretely, after emitting `mask` for the non-alphabet break, immediately flush the boundary byte (and continue byte-by-byte processing from `n+1`), rather than falling into the `IndexByte` prefix-search branch which silently treats the remaining buffer, including real secret bytes, as pass-through data.

### Proof of Concept
Go unit test in `common/buildlogger/internal/tokensanitizer`:
```go
func TestMaskingStopsAtNonAlphabetByte(t *testing.T) {
    var out bytes.Buffer
    m := New(&nopCloser{&out}, [][]byte{[]byte("glpat-")})
    secret := "glpat-abc123+REALSECRETSUFFIX"
    _, err := m.Write([]byte(secret))
    require.NoError(t, err)
    require.NoError(t, m.Close())
    result := out.String()
    // Expect: masked prefix, but must NOT contain the real suffix
    require.NotContains(t, result, "REALSECRETSUFFIX")
}
```
Expected (buggy) result: `result` contains `[MASKED]+REALSECRETSUFFIX`, i.e. the assertion fails, proving `REALSECRETSUFFIX` leaks unmasked after the `+` character. A fuzz test can be built by generating random alphabet-prefix strings, injecting a random byte outside `alphabet` at a random position, and asserting no substring of the original secret after the injected byte appears unmasked in the writer output.
