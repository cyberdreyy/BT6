### Title
Signer weight double-counted when a signer flips from Rejected to Accepted for the same block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener`'s block-status tally in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` uses two different, mutually inconsistent gates to decide whether a signer's weight has "already been counted": the `Accepted` branch gates on `gathered_signatures.contains_key(&slot_id)`, while the `Rejected` branch gates on `responded_signers.insert(slot_id)`. Because these are two different membership checks over two different sets, a single signer that first rejects and later accepts the *same* block gets its weight added to both `total_weight_rejected` *and* `total_weight_approved`, exactly the "double counting because a status/predicate doesn't track the other side's history" bug class described in the external report (there: a validator flips `WithdrawalDone → WithdrawalPossible` and gets counted twice by an incomplete predicate; here: a signer flips `Rejected → Accepted` and gets counted twice by two incompatible gates).

### Finding Description
In the `Accepted` handling branch: [1](#0-0) 

the weight is only added `if !block.gathered_signatures.contains_key(&slot_id)`, and then, unconditionally, `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)` are both performed.

In the `Rejected` handling branch: [2](#0-1) 

the weight is only added `if block.responded_signers.insert(slot_id)` (i.e. only the first time this slot appears in `responded_signers` at all, regardless of source).

The intended invariant is that a signer's weight should be counted exactly once total, on whichever side it last (or first) responds. But the two branches don't share a single check:

- If a signer votes **Accept first, then Reject**: the accept path inserts `slot_id` into both `gathered_signatures` and `responded_signers`. When the later `Reject` message arrives, `responded_signers.insert(slot_id)` returns `false` (already present), so the reject weight is *not* added — this ordering is safe.
- If a signer votes **Reject first, then Accept**: the reject path inserts `slot_id` into `responded_signers` only (not into `gathered_signatures`), and adds the signer's weight to `total_weight_rejected`. When the later `Accept` message arrives, the accept path checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (that map was never touched by the reject path) — so the accept path adds the *same* signer's weight to `total_weight_approved` as well.

The net effect: a single signer's weight ends up counted in **both** `total_weight_rejected` and `total_weight_approved` for the same block, when it flips from reject to accept. This breaks the accounting invariant `Σ(unique signer weight approved) == total_weight_approved` that the miner-side coordinator relies on to decide whether the 70% signing threshold has genuinely been reached by distinct signer weight.

### Impact Explanation
This is the "aggregated-weight vs verified-accepts" equality break called out in scope. `stacks-node/src/nakamoto_node/signer_coordinator.rs` treats `total_weight_approved >= self.weight_threshold` as proof that a supermajority of distinct signer weight has genuinely signed the block, and pushes/broadcasts it as approved: [3](#0-2) 

Because a rejecting signer's weight can be silently re-added to `total_weight_approved` once it flips to accept, the approved tally can be inflated by up to that signer's own weight beyond the true distinct-signer support. In a scenario where genuine, distinct-signer approval weight is below the 70% threshold, one additional signer (of any weight) that first rejects and then accepts contributes its weight twice — once to `total_weight_rejected`, once to `total_weight_approved` — potentially pushing `total_weight_approved` over the threshold even though the real number of distinct signers backing the block never reached the required weight. This is a concrete instance of a "rejection recounted as acceptance," matching the Critical-tier impact category in scope: the miner can conclude a block has reached the 70% signing threshold and gather/broadcast a signature set (`return Ok(block_status.gathered_signatures.values().cloned().collect())`) when the true supporting weight is lower than required.

### Likelihood Explanation
No majority collusion and no other signer's key are required — a single signer legitimately using its own key can produce this sequence, e.g. a signer that rejects a proposal (stale chainstate view, timeout, transient validation error) and later — after its own state re-evaluation — accepts the same block once it validates. The node-side StackerDB listener processes both messages from that signer's own slot as they are relayed over StackerDB gossip, with no cross-check preventing the flip from inflating both counters. This requires only ordinary signer behavior (a legitimate accept-after-reject transition is explicitly part of the signer's local retry/re-evaluation logic, per the docs describing repeat/PRIOR answers and capitulation flows) plus message delivery in the vulnerable order, which is entirely plausible given gossip/StackerDB polling timing.

### Recommendation
Use a single, shared gate for "has this signer's weight already been counted for this block," independent of which side it counted toward. Concretely, track one `HashMap<slot_id, Vote>` (or a single `responded_signers: HashSet<Slot>` checked identically by both branches) and only ever add weight once per slot for the lifetime of the block record, e.g.:
- On `Accepted`: only add to `total_weight_approved` if `slot_id` is not already present in the unified "responded" tracking structure; then record the slot as responded (as accepted).
- On `Rejected`: only add to `total_weight_rejected` under that same unified check.
- If a later message for an already-responded slot arrives with a different verdict, either ignore it (matching current one-vote-per-signer semantics implied elsewhere in the codebase, e.g. the CHANGELOG entry "Do not count both a block acceptance and a block rejection for the same signer/block") or explicitly move the weight from one bucket to the other (subtract-then-add) so no double counting occurs in either direction.

### Proof of Concept
1. Node/coordinator has `weight_threshold` computed for 70% of `total_weight`; suppose real distinct-signer approval weight for a block reaches only slightly below threshold (say 65%), and one signer S (weight 10%, bringing hypothetical total past 70% only if double counted) is part of the remaining signers.
2. Signer S sends `BlockResponse::Rejected` for the block first (e.g., due to a transient local chainstate mismatch). `stackerdb_listener.rs` processes it: `responded_signers.insert(S.slot_id)` succeeds, `total_weight_rejected += S.weight`.
3. Signer S re-evaluates and later sends `BlockResponse::Accepted` for the same block (e.g., after its own state catches up). `stackerdb_listener.rs` processes it: `gathered_signatures.contains_key(&S.slot_id)` is `false` (never touched by the reject path), so `total_weight_approved += S.weight` executes, and `gathered_signatures`/`responded_signers` are updated.
4. `total_weight_approved` now includes S's weight a second time relative to the true distinct-signer support, potentially crossing `self.weight_threshold` in `get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs:541`) even though genuine distinct approving weight never reached 70%, causing the coordinator to treat the block as validly signed and push it.
