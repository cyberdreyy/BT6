### Title
Unbounded pending-callback map with no rate limiting in Legacy Gateway user message handler enables mempool-style DoS - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Monad report describes a mempool DoS where unprivileged senders can hog a capacity-limited resource (`MAX_ADDRESSES`) because the pool lacks a proper eviction/limit strategy and blindly accepts entries keyed by sender-controlled identifiers. The Chainlink Gateway's legacy capabilities handler exhibits an analogous pattern: `HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` accepts any unauthenticated `WebAPITrigger` message and unconditionally inserts an entry into the in-memory `h.savedCallbacks` map keyed by the attacker-supplied `msg.Body.MessageId`, with no allowlist or rate-limiting check performed before the write.

### Finding Description
In `HandleLegacyUserMessage` [1](#0-0) , request validation is limited to payload decoding, timestamp presence, staleness checking, and method matching. Critically, the code contains an explicit acknowledgement that authorization/throttling controls are missing: [2](#0-1) 

Immediately after this comment, the handler unconditionally stores the callback in a shared map under lock, without any check on current map size or the sender's identity/quota, before dispatching the request to every DON member: [3](#0-2) 

This mirrors the two core defects from the Monad report:
1. **No eviction/capacity strategy across distinct keys** — like the tracked pool dropping new transactions once `MAX_ADDRESSES` is reached instead of evicting the lowest-value entry, `savedCallbacks` grows per unique `MessageId` with no visible admission control gating unprivileged, unauthenticated callers before insertion.
2. **Sender-controlled key stuffing** — just as a tracked address can submit nonce-gapped transactions to occupy a permanent slot, an external caller can submit arbitrarily many `WebAPITrigger` messages with distinct, self-chosen `MessageId` values to inflate the map indefinitely, since the ID is attacker-supplied and not scoped to a per-sender quota.

I was not able to fully verify within the available tool budget whether `pruneCallbacks` (referenced elsewhere in the same file) enforces a hard cap on `savedCallbacks` size or purely does time-based expiry; this affects the exact severity, since a time-based reaper without a size cap only bounds outstanding requests by time-window request rate, not by attacker cost.

### Impact Explanation
If `savedCallbacks` has no hard capacity bound (only time-based pruning), an unauthenticated actor able to reach the gateway's legacy `WebAPITrigger` HTTP endpoint could flood it with distinct `MessageId` values faster than the prune interval reclaims them, growing the in-memory map without bound and exhausting gateway node memory — a resource-exhaustion Denial of Service against the DON's gateway ingress path, potentially blocking legitimate workflow trigger requests from being processed, similar in effect to the mempool being hogged and denying transaction admission to legitimate senders.

### Likelihood Explanation
The `TODO: apply allowlist and rate-limiting here` comment directly acknowledges the control gap is unimplemented, and the code path is reachable by any unprivileged caller hitting the gateway's legacy JSON message handler with a `WebAPITrigger` payload — no signature verification or authorization occurs prior to the map insertion in the code I could confirm. However, without confirming whether `pruneCallbacks` also enforces a maximum map size (which would cap and mitigate the issue), I cannot assert this rises to a definitively unmitigated production DoS with full confidence.

### Recommendation
- Implement the allowlist/rate-limiting referenced in the `TODO` comment before requests are admitted into `savedCallbacks`, scoping quotas per sender/API key rather than relying on attacker-supplied `MessageId`.
- Enforce a hard maximum size on `savedCallbacks` (reject new entries once the cap is reached, similar to `requestCache.maxCacheSize` in `core/services/gateway/handlers/common/requestcache.go`), and/or evict the oldest/lowest-priority pending entry when full instead of accepting unbounded growth.
- Confirm and, if necessary, add a size-bound check in `pruneCallbacks` in addition to time-based expiry.

### Proof of Concept
Not executed (no filesystem/runtime access in this mode). Conceptually: an external, unauthenticated client repeatedly POSTs legacy JSON-RPC `WebAPITrigger` messages to the gateway HTTP endpoint, each with a unique `MessageId` and valid-looking payload/timestamp, at a rate exceeding the `pruneCallbacks` reclamation rate, causing `h.savedCallbacks` to grow unbounded in memory.

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if payload.Timestamp == 0 {
		h.lggr.Errorw(ErrDecodingPayload)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload,
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
		h.lggr.Errorw("stale message")
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.HandlerError),
				"stale message",
				nil,
			),
			ErrorCode: api.HandlerError,
		})
	}
