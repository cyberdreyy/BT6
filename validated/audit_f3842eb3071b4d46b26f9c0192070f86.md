This confirms the analysis. The shell executor uses local process groups (`Setpgid: true`) and sends `SIGTERM`/`SIGKILL` to the entire negative PID (process group) via `helpers/process/killer_unix.go`'s `getPID()`, ensuring child processes are also terminated. The SSH executor has no equivalent mechanism — it only signals/closes the SSH *session* (the single remote command channel), with no process-group tracking or remote `pkill`/`kill -TERM -$(pgid)` logic.

### Title
Cancelled SSH executor jobs leave detached child processes running on the shared SSH host - ([File: executors/ssh/ssh.go], [File: helpers/ssh/ssh_command.go])

### Summary
The SSH executor's `Client.Run` in `helpers/ssh/ssh_command.go` only sends `ssh.SIGKILL` to the session and closes it on cancellation, but never targets the process group of the remote command. A job script that detaches via `setsid ... & disown` escapes the session's process tree entirely, so cancellation/timeout leaves the detached process running indefinitely on the shared SSH host, consuming resources that affect all future jobs routed to that host.

### Finding Description
`(*executor).Run` in `executors/ssh/ssh.go` (lines 55-73) delegates to `s.sshCommand.Run(cmd.Context, ...)`, which is implemented in `helpers/ssh/ssh_command.go` `Client.Run` (lines 141-178). The remote command is started with `session.Start(cmd.Command)`, and on `ctx.Done()` the only cleanup performed is:
```go
case <-ctx.Done():
    _ = session.Signal(ssh.SIGKILL)
    _ = session.Close()
    return <-waitCh
``` [1](#0-0) 

This only attempts to signal the single foreground process associated with the SSH channel (and only if the remote `sshd` implements the SSH "signal" channel request, which is not universal for OpenSSH exec channels). It does not enumerate or kill a process group, and it has no awareness of any processes the script explicitly detached from its own session/process group (e.g., via `setsid ... & disown`). Compare this with the shell executor's cancellation path, which sets `Setpgid: true` on the local process (`helpers/process/job_unix.go` lines 36-40) and kills the negative PID/process group via `syscall.Kill(pk.getPID(), ...)` in `helpers/process/killer_unix.go` (lines 46-52), guaranteeing all descendants are reaped. The SSH executor has no analog of this process-group tracking on the remote host — `Cleanup()` (`executors/ssh/ssh.go` lines 75-78) merely calls `s.sshCommand.Cleanup()`, which just closes the outer SSH TCP connection (`helpers/ssh/ssh_command.go` lines 180-184), and does not run any remote `pkill`/`kill -- -$pgid` to reap orphaned children.

Attacker input: the job's `script`/`before_script`/`after_script` (fully attacker-controlled CI YAML content) executed via `s.BuildShell.CmdLine` and `cmd.Script` as `Stdin`. A one-line script like `setsid nohup sleep infinity </dev/null &>/dev/null & disown; exit 0` immediately detaches a long-lived process from the SSH session's process group before the parent shell exits.

### Impact Explanation
Once detached, the process is no longer a child of (or in the same process group as) the SSH session's shell, so `session.Signal`/`session.Close`/TCP disconnect cannot reach it. It survives job cancellation, timeout, and `Cleanup()`, persisting on the shared SSH host and consuming CPU/memory/network ports/disk indefinitely, degrading or disrupting subsequent jobs from any project assigned to that same SSH host — a real cross-tenant resource-exhaustion/persistence issue scoped to hosts shared across projects.

### Likelihood Explanation
High feasibility for any user able to submit a `.gitlab-ci.yml` job routed to an SSH executor runner: no special permissions beyond normal CI authorship are needed, the detach primitive (`setsid`/`nohup`/`disown`) is standard POSIX shell tooling present on virtually any SSH target, and the exploit is fully repeatable on every job run since the runner performs no process-group-based cleanup on the remote host at any point (`Run`, `Cleanup`, timeout, or cancellation).

### Recommendation
Track the PID/process-group of the remote command (e.g., wrap the script to `echo $$` first, or explicitly `setsid`/`setpgid` the launched shell server-side) and, on cancellation/timeout/`Cleanup`, issue an explicit remote kill of the whole process group (e.g., `kill -- -$PGID` or `pkill -g $PGID`) via a separate SSH exec, rather than relying solely on `session.Signal`/`session.Close`. Additionally, document/detect that `session.Signal` support is optional per-`sshd` and should not be the sole termination mechanism.

### Proof of Concept
Integration test outline (extending existing SSH executor test infra, which already contains `helpers/ssh/stub_ssh_server_unix.go`):
```go

// 5. Open an independent second SSH connection/session to the same host and run:

```
