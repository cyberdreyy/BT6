Confirmed. In both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, when a key/member is removed via `DeleteKey` (multisig) or `DeleteMember` (multisig2), the cleanup only purges requests that were *created* by that key/member — it does not purge that key/member's *confirmations* recorded on other still-pending requests created by someone else.

### Title
Stale confirmations from removed multisig members still count toward quorum, allowing execution below the live-member threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
`confirm()` tallies quorum purely from the size of the `confirmations` set attached to a request; it never re-validates that each entry in that set still corresponds to a current member of the multisig. `delete_member`/`DeleteKey` only deletes requests *authored* by the removed member/key, and only clears confirmations tied to those self-authored requests — it never scans other pending requests to strip out confirmations the removed member had already cast on them.

### Finding Description
The binding that should hold is: `distinct_live_member_confirmations(request) == num_confirmations` before a request executes. Instead the code checks `confirmations.len() + 1 >= num_confirmations`, where `confirmations` is a `HashSet<String>` of member identifiers gathered over the request's lifetime [1](#0-0) .

`delete_member` removes the member from `self.members` and deletes any *requests* filed by that member, but does not touch `self.confirmations` entries for requests filed by *other* members that the removed member had already confirmed [2](#0-1) . The identical pattern exists in the legacy `multisig` contract's `DeleteKey` handling inside `execute_request`, which purges only requests where `r.signer_pk == pk`, leaving that key's confirmations on other pending requests intact [3](#0-2) .

Because `confirm()` never cross-checks `self.members`/live keys against the stored confirmation identifiers [4](#0-3) , a confirmation cast by a member who is later removed remains permanently counted toward that pending request's quorum.

### Impact Explanation
This breaks the core custody guarantee of a "K out of N" multisig: that any state-changing action (in particular `Transfer`, `AddKey`/`AddMember`, `DeployContract`) requires `K` *currently authorized* signers. With a stale confirmation retained, only `K-1` (or fewer, if multiple members were removed after confirming pending requests) truly live members are needed to push a pending request past the quorum check and execute it — including moving NEAR out of the account. This matches Critical impact: "NEAR ... moved by a party not entitled to it" / "a multisig request executed below threshold", since a removed member's prior confirmation is being spent as if it were a live signer's authorization.

### Likelihood Explanation
This requires no privileged access beyond normal multisig usage: any member can create a `Transfer` (or other) request and get it partially confirmed by other members in the ordinary course of operation. It only takes one of the confirming members to later be removed (e.g. because their key was rotated out, they left the organization, or their access was revoked for being compromised) for the stale confirmation to persist. This is a realistic and even routine operational sequence (member confirms, then is later removed) rather than a contrived edge case, and it silently reduces the effective threshold with no error, warning, or view method to detect it before execution.

### Recommendation
When removing a member/key (`delete_member` in multisig2, `DeleteKey` handling in multisig), iterate over **all** `confirmations` entries (not just requests authored by that member) and strip out the removed member's identifier from each set. Alternatively, have `confirm()` re-validate, at tally time, that every identifier in the stored `confirmations` set still corresponds to a current entry in `self.members` (multisig2) or a currently active access key (multisig), and only count live members toward the `num_confirmations` threshold.

### Proof of Concept
1. Initialize a `multisig2` contract with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request` to create a `Transfer` request `R1` to some receiver — `R1` now has 0 confirmations.
3. `B` calls `confirm(R1)` — `R1.confirmations = {B}` (1 of 2), not yet executed [5](#0-4) .
4. Separately, members reach quorum on a `DeleteMember { member: B }` request and it executes, removing `B` from `self.members` — but `R1`'s confirmations set is untouched because `R1` was authored by `A`, not `B` [6](#0-5) .
5. `C` (the only other live member besides `A`) calls `confirm(R1)`. `confirmations.len() + 1 = 2 >= num_confirmations (2)`, so `R1` executes the `Transfer` — even though only `A` (author) and `C` are still live members and `B`'s confirmation, now stale, was decisive in reaching quorum.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
