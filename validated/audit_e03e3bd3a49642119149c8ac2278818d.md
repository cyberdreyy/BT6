Based on my investigation, I found a plausible analog to the Ajna `isEpochClaimed` bug class in Base's dual-EVM-engine handling of EIP-8130 nonce-free (`NONCE_KEY_MAX`) transaction replay protection, but I was **unable to fully confirm the exact call site** before running out of tool iterations. I'm presenting what I found with explicit caveats.

### Title
Missing replay-marking write for nonce-free EIP-8130 transactions in the evm2 execution engine - (File: crates/common/evm2/src/nonce_manager.rs)

### Summary
Base runs two execution engines for EIP-8130 account-abstraction transactions: the revm-based engine (`crates/common/evm/src/eip8130.rs`) and a second engine, `evm2` (`crates/common/evm2/`). Both must apply identical state transitions for consensus to hold. For nonce-free transactions (`nonce_key == NONCE_KEY_MAX`), the revm engine both validates and *records* the replay hash in the same atomic step via `NonceManagerStorage::check_and_mark_expiring_nonce`, which reads-then-writes the `expiring_nonce_seen` mapping and ring buffer [1](#0-0) , mirroring the precompile's own read+write implementation [2](#0-1) .

By contrast, evm2's `NonceManager` type — the access layer the second engine uses to read/write this same storage — exposes only `get_nonce` (read), `is_expiring_nonce_seen` (read-only check), and `increment_nonce` (write, but only for sequence channels, not the nonce-free ring buffer/seen-set) [3](#0-2) . There is no method in this file analogous to `check_and_mark_expiring_nonce` that would persist the replay hash for a nonce-free transaction.

### Finding Description
This is structurally the same bug class as the Ajna finding: a "claimed"/"seen" check exists (`isEpochClaimed` in Ajna, `is_expiring_nonce_seen` in Base), but a path that consumes the corresponding privileged action does not perform the state-mutating "mark as claimed/seen" step, so the guard has no persistent effect. In the Ajna case, `moveStakedLiquidity` called `_claimRewards` without the `isEpochClaimed` revert check that `claimRewards` had. Here, if `evm2`'s EIP-8130 transaction handler validates a nonce-free transaction using `NonceManager::is_expiring_nonce_seen` but has no corresponding write-back call (because none exists on `NonceManager`), the replay hash is never recorded, so the exact same signed nonce-free transaction could be resubmitted and executed repeatedly on the `evm2` engine within (and potentially beyond) its `valid_before` window, since the "seen" state controlling that check-only path never toggles.

### Impact Explanation
If confirmed, this would allow unbounded replay of any single valid EIP-8130 nonce-free transaction on nodes running the `evm2` engine — an unauthorized repeated-execution / double-spend primitive reachable by any signer of a nonce-free transaction (an unprivileged transaction sender), and it would also produce a state/consensus divergence between the revm engine (which marks-and-blocks replay) and `evm2` (which would not), a chain-split-class defect.

### Likelihood Explanation
**Low-to-uncertain confidence** — I was not able to inspect `crates/common/evm2/src/transaction.rs`, the actual EIP-8130 transaction handler in evm2, before running out of tool budget, so I cannot confirm (a) whether evm2 currently supports nonce-free transaction execution at all, or (b) whether it calls `is_expiring_nonce_seen` in a way that assumes marking happens elsewhere (e.g., via a shared/generic write helper I did not find). The asymmetry in the `NonceManager` API surface between the two engines is the strongest evidence, but it is not conclusive proof of an exploitable path.

### Recommendation
Verify in `crates/common/evm2/src/transaction.rs` whether nonce-free (`NONCE_KEY_MAX`) EIP-8130 transactions are handled, and if so, confirm that after `is_expiring_nonce_seen` returns `false`, the replay hash and its ring-buffer slot are actually persisted (mirroring `NonceManagerStorage::check_and_mark_expiring_nonce`) before or as part of transaction finalization. If no such write exists, add a `mark_expiring_nonce_seen` (or equivalent) method to `evm2`'s `NonceManager` and call it from the nonce-free branch of the evm2 transaction handler, keeping its slot-derivation and ring-buffer semantics identical to `crates/common/precompiles/src/nonce/storage.rs::check_and_mark_expiring_nonce` to preserve cross-engine consensus.

### Proof of Concept
Not constructed — this requires confirming the evm2 nonce-free transaction dispatch path (`crates/common/evm2/src/transaction.rs`), which I did not get to examine before exhausting my tool-call budget. A concrete PoC would submit the same signed nonce-free EIP-8130 transaction twice to an `evm2`-based node within its `valid_before` window and observe whether the second submission executes successfully instead of reverting with `ExpiringNonceReplay`.

        &mut self,
        expiring_nonce_hash: B256,
        valid_before: u64,
    ) -> Result<()> {
        // Both `valid_before` and this `now` are Unix milliseconds; the EIP
        // evaluates the window against `block.timestamp * 1000`.
        let now: u64 = self.storage.timestamp().saturating_to::<u64>().saturating_mul(1_000);

        // 1. Validate the expiry window: must be in (now, now + MAX_EXPIRY_MS].
        if valid_before <= now || valid_before > now.saturating_add(Self::NONCE_FREE_EXPIRY_WINDOW)

impl NonceManager {
    /// Returns the current 2D nonce for `account` at `nonce_key`, or `None` for the reserved
    /// protocol nonce key (`0`). Reads storage untracked, so it does not perturb execution.
    pub fn get_nonce(
        evm: &mut Evm<'_, BaseEvmTypes>,
        account: Address,
        nonce_key: U256,
    ) -> HandlerResult<Option<u64>> {
        let Some(slot) = NonceManagerSlots::nonce_slot(account, nonce_key) else {
            return Ok(None);
        };
        let value = evm
            .state_mut()
            .storage_slot_untracked(&NonceManagerSlots::ADDRESS, &slot)
            .map_err(HandlerError::Fatal)?;
        Ok(Some(value.saturating_to::<u64>()))
    }

    /// Returns whether `replay_id` has been recorded and has not yet expired relative to `now`
    /// (Unix milliseconds) — the nonce-free replay check. Reads storage untracked.
    pub fn is_expiring_nonce_seen(
        evm: &mut Evm<'_, BaseEvmTypes>,
        replay_id: B256,
        now: u64,
    ) -> HandlerResult<bool> {
        let slot = NonceManagerSlots::expiring_nonce_seen_slot(replay_id);
        let expiry = evm
            .state_mut()
            .storage_slot_untracked(&NonceManagerSlots::ADDRESS, &slot)
            .map_err(HandlerError::Fatal)?
            .saturating_to::<u64>();
        Ok(expiry != 0 && expiry > now)
    }

    /// Increments the 2D channel nonce for `account` at `nonce_key`, returning the new value, or
    /// `None` for the reserved protocol nonce key (`0`). Writes to the transaction state overlay
    /// (the increment commits with the transaction), mirroring the reference's in-execution write.
    pub fn increment_nonce(
        evm: &mut Evm<'_, BaseEvmTypes>,
        account: Address,
        nonce_key: U256,
    ) -> HandlerResult<Option<u64>> {
        let Some(slot) = NonceManagerSlots::nonce_slot(account, nonce_key) else {
            return Ok(None);
        };
        let mut handle = evm
            .state_mut()
            .storage_slot(&NonceManagerSlots::ADDRESS, slot, false)
            .map_err(HandlerError::Fatal)?;
        let current = handle.current().saturating_to::<u64>();
        let new_nonce =
            current.checked_add(1).ok_or_else(|| HandlerError::external(NonceOverflow))?;
        handle.set(U256::from(new_nonce));
        Ok(Some(new_nonce))
    }
}
