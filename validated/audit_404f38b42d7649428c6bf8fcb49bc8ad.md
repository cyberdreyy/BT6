### Title
V1 tenure-change duplicate-block guard checks only globally-accepted state, allowing double-signing of conflicting tenure-change blocks - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`v1.rs::validate_tenure_change_payload`'s "already signed a block in this tenure" guard queries `signer_db.get_last_globally_accepted_block`, which only matches blocks in `BlockState::GloballyAccepted`. `v2.rs`'s equivalent guard queries `get_last_signed_block`, which matches any block the signer has cryptographically signed (`signed_self`/`signed_group`), whether locally or globally accepted. This means a signer still evaluating proposals on the V1 code path can sign a second, competing tenure-change block for a tenure where it already signed (but has not yet seen global acceptance for) a prior block.

### Finding Description
The intended equality is: *the set of blocks the "duplicate tenure-change" guard treats as "already signed by me for this tenure" == the true set of blocks this signer has cryptographically signed for this tenure*. `v2.rs` enforces this explicitly and states the rationale in its own comment: [1](#0-0) 

`v1.rs`, by contrast, queries only globally-accepted state: [2](#0-1) 

`get_last_globally_accepted_block` filters strictly on `BlockState::GloballyAccepted`, while `get_last_signed_block` matches any block bearing this signer's own signature timestamp, regardless of global-acceptance status — confirmed by the `signerdb.rs` implementations of both accessors and by the `SortitionData::get_tenure_last_block_info` helper (used elsewhere in `mod.rs`) which explicitly measures endorsement via `signed_self`/`signed_group`, not global state: [3](#0-2) 

The protocol-version dispatch that selects which of these code paths a given signer runs is in `SortitionStateVersion::uses_global_state`/`from_protocol_version`, confirming this is a genuine version-dependent branch reachable during a mixed-version fleet (e.g., a rolling upgrade where some signers have not yet crossed `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`): [4](#0-3) 

Exploit flow: a malicious miner (single BTC slot) proposes a tenure-change block A for tenure T; the V1 victim signer locally accepts/signs it (`signed_self` set, state not yet `GloballyAccepted` because the rest of the fleet hasn't converged). The miner then proposes a second, conflicting tenure-change block B for the same tenure T (different `signer_signature_hash`, same `consensus_hash`). When the V1 signer evaluates B, `get_last_globally_accepted_block(&B.header.consensus_hash)` returns `None` (block A is not globally accepted), so the "already signed a block in this tenure" branch is skipped and `Ok(())` is returned instead of `Err(RejectReason::DuplicateBlockFound)`. The signer proceeds to also sign B, thereby signing two conflicting tenure-change blocks for the same tenure — exactly the case `v2.rs`'s comment says must be prevented for any block the signer has signed, "locally or globally accepted."

None of the other checks in `validate_tenure_change_payload` (parent-tenure-consensus-hash match, `check_tenure_change_confirms_parent`, `check_parent_tenure_choice`) inspect the *current* tenure for prior signer activity — they only validate the relationship to the *parent* tenure/reorg rules, so they do not catch this case.

### Impact Explanation
This breaks the uniqueness/equivocation-avoidance property for a V1-evaluating signer: it can be induced to place its signature on two mutually conflicting tenure-change blocks for the same tenure. If that signer's weight combines with other signers' signatures on both competing blocks (a realistic scenario in a fleet mid-upgrade, where more than one signer may transiently be on V1 and hit the same local-accept-not-yet-global window), this materially increases the chance of a chain split / conflicting-block finalization — a Critical, chain-safety-affecting outcome (a signer signing a conflicting block).

### Likelihood Explanation
Preconditions are the ones already declared in the question and consistent with the code: a mixed-version fleet with at least one signer still running the V1 evaluation path (`uses_global_state()==false`), and a tenure where that signer has locally accepted/signed a block that hasn't yet reached global acceptance. The attacker needs only a single won block-commit slot (their own BTC) plus the ability to gossip a second competing tenure-change `BlockProposal` — no majority-signer collusion, no compromised key, and no local/node access are required. This is repeatable each time the timing window (local-accept pending global-accept) occurs on a V1 signer, which is a normal, recurring race during tenure transitions, not a rare edge case.

### Recommendation
Change `v1.rs::validate_tenure_change_payload`'s duplicate-block guard (line 505-518) to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the semantics already implemented and documented in `v2.rs`, so that any block the signer has signed for the current tenure — locally or globally accepted — blocks a second, conflicting tenure-change proposal.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/v1.rs`:
1. Construct a `SignerDb` and a `SortitionState::V1` fixture for tenure `T` (consensus_hash `CH`) with a parent tenure that legitimately satisfies `check_parent_tenure_choice`.
2. Build tenure-change block `A` for tenure `CH`; insert it into `signer_db` with `BlockState::LocallyAccepted`/`Accepted` (not `GloballyAccepted`) and set `signed_self` to a timestamp (simulating that this signer already signed it), matching how `SortitionData::get_tenure_last_block_info` treats "signed" state.
3. Build a second, conflicting tenure-change block `B` for the same `CH` (different `signer_signature_hash`, satisfying `check_tenure_change_confirms_parent`/`check_parent_tenure_choice` against the same parent tenure).
4. Call `v1_state.validate_tenure_change_payload(&proposed_by, &tenure_change_payload_for_B, &B, &mut signer_db, &client)`.
5. Assert (bug): result is `Ok(())`.
   Assert (expected/fixed behavior): result should be `Err(RejectReason::DuplicateBlockFound)`.
6. Repeat the same setup against `v2.rs::validate_tenure_change_payload` and assert it correctly returns `Err(RejectReason::DuplicateBlockFound)`, demonstrating the version-dependent gap.
