### Title
Pending APR0 withdraw requests permanently brick `stopEpoch` once APR is set non-zero, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
A KYC-passing lender who calls `requestWithdraw` while the vault is in APR0 mode (`unscaledApr == 0`) populates `apr0TotalPrincipal`. `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`, and `apr0TotalPrincipal` is only cleared inside that same reverting function. Once the (honest) manager sets a non-zero APR for the next epoch, every `stopEpoch` call reverts, so no withdraw request can ever be claimed.

### Finding Description
The bug-class analog of CVE-2018-2766 (an InnoDB state that causes a repeatable crash/hang, i.e. permanent availability loss) maps to the credit-vault surface as a reproducible state-machine stall that freezes all user funds.

`requestWithdraw` routes APR0 requests into `_requestWithdrawApr0`, which adds the amount to the global `apr0TotalPrincipal` bucket [1](#0-0) [2](#0-1) .

`prepareStopEpochWithApr0`, invoked by the CDO during `stopEpoch`, reverts if the bucket is non-empty while `unscaledApr` has moved off zero [3](#0-2) . The only place `apr0TotalPrincipal` is reset is at the end of that same function, after the revert check [4](#0-3) . There is no alternative path that drains the bucket: `_settleApr0` only moves per-user data, and `_clearWithdrawClaimForEpoch` only touches `apr0TotalPrincipal` inside the default-finalization flow.

Sequence:

1. Epoch N runs with `unscaledApr == 0` (APR0 mode is a supported vault mode; `requestWithdraw` explicitly branches on it at line 285).
2. Attacker — any KYC-passing lender holding tranche tokens — calls the CDO's withdraw path, which calls `requestWithdraw(amount, attacker, principal)`. `apr0TotalPrincipal += amount`; the attacker's principal is now receipt-backed, so they risk nothing extra.
3. Honest manager calls `setAprsWithBuffer`/`setAprs` to set a normal APR for epoch N+1 (`unscaledApr != 0`). This is a routine, expected privileged action, not an attacker-controlled one.
4. Borrower repays; manager calls `stopEpoch`. `prepareStopEpochWithApr0` reverts with `NotAllowed` because `apr0TotalPrincipal != 0 && unscaledApr != 0`.
5. `epochNumber` never increments, `lossRecoveryPriceByEpoch`/`collectWithdrawFunds` never run, and `claimWithdrawRequest` keeps reverting on `epochNumber <= lastWithdrawRequest[user]` [5](#0-4) . Every pending withdraw, plus new deposits routed through the epoch path, is frozen.

The freeze persists until the manager manually sets `unscaledApr` back to 0 and successfully stops an epoch — i.e. all lenders' funds are locked for at least one full additional epoch duration, and indefinitely if the honest operational sequence keeps APR non-zero (e.g. APR is updated per epoch by an orchestrator). No existing guard prevents this: `requestWithdraw` has no check that APR0 principal must be claimable before APR changes, and `setApr`/`setAprs` do not check `apr0TotalPrincipal`.

### Impact Explanation
Temporary-to-permanent freezing of all vault funds. The borrower repaid in full, so the underlying sits between CDO/strategy but is unreachable: `stopEpoch` cannot complete, `epochEndDate` stays non-zero, and every funded/unfunded withdraw claim reverts. Loss quantification = entire vault TVL locked for at least one extra epoch cycle (plus gas/ops to recover), matching the "complete DOS / hang" availability impact of the CVE class with direct fund impact.

### Likelihood Explanation
Requires an APR0 epoch (a first-class vault mode), one lender withdraw request during it (the attacker pays nothing — their own principal was already deposited), and a subsequent honest APR change, which is the normal epoch-rollover flow. All attacker actions are unprivileged and unconditional; the only dependencies are honest-role actions that occur in ordinary operation.

### Recommendation
- In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0` with a pending bucket; instead settle the APR0 bucket at the rate applicable to its request epoch (or at 0 interest) and clear `apr0TotalPrincipal` before the revert path can trigger.
- Alternatively, block the transition at the source: revert `setApr`/`setAprs`/`setAprsWithBuffer` when `apr0TotalPrincipal != 0` and the new `unscaledApr != 0`, or force-claim/settle APR0 receipts inside `requestWithdraw` when the APR regime changes.

### Proof of Concept
Foundry fork PoC (against the repo's existing `IdleCreditVault`/`IdleCDOEpochVariant` harness used in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function test_apr0_pending_request_bricks_stopEpoch() public {
    // setup: vault in APR0 mode
    vm.prank(manager);
    strategy.setAprs(0, 0); // unscaledApr = 0

    // attacker: KYC lender deposits then requests withdraw during APR0 epoch
    _depositAsLender(attacker, 100e18);
    vm.prank(attacker);
    cdo.requestWithdraw(50e18); // -> IdleCreditVault.requestWithdraw, APR0 path
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // honest manager sets normal APR for next epoch
    vm.prank(manager);
    strategy.setAprsWithBuffer(5e18, epochDuration, bufferDuration); // unscaledApr != 0

    // borrower repays interest; honest stopEpoch now always reverts
    _repayBorrower();
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdo.stopEpoch();

    // all claims frozen
    vm.prank(attacker);
    vm.expectRevert(NotAllowed.selector);
    cdo.claimWithdrawRequest(); // epochNumber never advanced
}
```

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
