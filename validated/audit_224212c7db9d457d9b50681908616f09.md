## No Vulnerability found for this question.

**Analysis supporting this conclusion:**

The image name only reaches two kinds of consumers, neither of which involves shell/`exec.Command` interpretation of the raw string:

1. **Docker daemon API calls (structured, not shell)** — `expandAndGetDockerImage` passes the user-supplied name into `e.pullManager.GetDockerImage(imageName, ...)` and ultimately into `e.dockerConn.ContainerCreate(...)` [1](#0-0) . The actual `container.Config.Image` field set at container-creation time is not even the raw job-supplied string — it's `imageReferenceForCreate(image)`, which uses the *resolved* image object's `RepoDigests`/`ID` returned by the Docker daemon after inspect/pull, not the attacker's literal text [2](#0-1) [3](#0-2) . All of this goes over the Docker Engine HTTP/JSON API via the `docker` client SDK — never through `exec.Command` or a shell.

2. **`exec.Command` usage in this package is confined to integration test helpers** (`docker_command_integration_test.go`, `docker_podman_integration_test.go`, `docker_pull_retry_integration_test.go`), which are test-only setup code invoked with fixed, hardcoded arguments — not runtime paths reachable by job-controlled image strings [4](#0-3) .

Before any of this, `VerifyAllowedImage` at `common/allowed_images.go:20-54` only does a `doublestar.Match` glob check against the configured allow-list; it does not sanitize or escape anything, but it also is not the layer responsible for preventing injection — because there is no downstream shell/`exec.Command` sink for the image string in the production path (`executors/docker/docker.go`, `executors/docker/services.go`) [5](#0-4) .

Additionally, service names go through `services.SplitNameAndVersion`, which uses `github.com/distribution/reference`'s `ReferenceRegexp` to parse the string as a Docker reference [6](#0-5) . Reference strings containing shell metacharacters like `;`, `$()`, backticks, or newlines are not valid Docker image reference syntax, so they either fail this regex match (falling back to being treated as a literal, non-matching image name) or get rejected by the Docker daemon itself as an invalid reference when passed to `ContainerCreate`/`ImagePull`. Either way, they never get concatenated into a shell command string.

The premise that "the docker executor's `createContainer`/`getContainerServicesHostname`-adjacent code paths" build shell/exec command strings from raw image names is not supported by the code — `createContainer` and `createService` build strongly-typed `container.Config`/`container.HostConfig` structs consumed by the Docker SDK's JSON API client, and hostname/alias generation (`SplitNameAndVersion`, `createServicesHostAlias`) produces DNS-validated strings (`dns.ValidateDNS1123Subdomain`) rather than shell-interpolated ones [7](#0-6) .

// imageReferenceForCreate returns the reference to use as a container's
// Image field. When the same tag has been pulled locally for more than one
// platform, image.ID is the ID of that specific platform's manifest, which
// the daemon can't resolve on its own for container creation - only the
// image's repo digest (or its tag) can. Fall back to the ID when there's no
// repo digest (for example, a locally built image that was never pushed).
func imageReferenceForCreate(image *image.InspectResponse) string {
	if len(image.RepoDigests) > 0 {
		return image.RepoDigests[0]
	}

	return image.ID
}
