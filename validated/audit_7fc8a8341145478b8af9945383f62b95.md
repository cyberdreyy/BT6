### Title
Unclamped utilization ratio in `calc_interest_rate` lets `lending_rate_apr` exceed `borrowing_rate_apr` once a bank's liabilities exceed its assets - ([File: programs/marginfi/src/state/interest_rate.rs])

### Summary
`InterestRateCalc::calc_interest_rate` derives the borrow-side curve rate (`base_rate_apr`) from a utilization ratio that is internally clamped to `[0, 1]`, but it computes the lend-side rate (`lending_rate_apr`) by multiplying `base_rate_apr` by the **raw, unclamped** utilization ratio passed in by the caller. When a bank's `total_liabilities_amount` exceeds its `total_assets_amount` (a state the protocol explicitly supports and names "bank super-bankruptcy"), the utilization ratio exceeds `1.0` and `lending_rate_apr` is inflated above what `borrowing_rate_apr` actually pays in, breaking the invariant that lenders can never be paid more than borrowers pay. This mirrors the Compound-fork bug in the report, where `reserves` pushed utilization above `1e18` and the supply rate was multiplied by the unclamped utilization rate while the borrow rate had its own separate cap.

`calc_interest_rate` receives `utilization_ratio` and uses it in two different ways:

That clamp does **not** propagate back to the outer `utilization_ratio`, which is still used unclamped to compute `lending_rate_apr`:

The only sanity checks performed are lower-bound-only assertions; there is no check that `lending_rate_apr <= borrowing_rate_apr`, and no check that `utilization_ratio <= 1`:
<cite repo="EzraCole/marginfi-v2--005" path="programs/marginfi/src/state/interest_rate.rs" start="227-232" />

Both `Bank::accrue_interest` and `Bank::update_bank_cache` compute this ratio as a plain division with no clamping before calling into `calc_interest_rate`:

Marginfi already documents and tests the exact precondition needed to push this ratio above `1.0`: a "bank super-bankruptcy" state where bad debt exceeds bank assets before `handle_bankruptcy` is executed.

A test explicitly reaches this state (`bankValues.liability > bankValues.asset`) and shows that `withdraw` is blocked with `IllegalUtilizationRatio` (error `6026`), while `deposit` and `repay` continue to succeed in that same window:
<cite repo="EzraCole/marginfi-v2--005" path="tests/specs/bankruptcy/zb01_bankruptcy.spec.ts" start="556-586" />

Because `IllegalUtilizationRatio` is only enforced on the withdraw path (not inside `accrue_interest`/`update_bank_cache`), every deposit/repay call in this window - as well as the dedicated permissionless `accrue_bank_interest` instruction - re-runs interest accrual with `utilization_ratio > 1`, feeding the unclamped multiplication in `lending_rate_apr` described above.

### Impact Explanation
`lending_rate_apr` directly drives `asset_share_value` growth via `calc_accrued_interest_payment_per_period`:
<cite repo="EzraCole/marginfi-v2--005" path="programs/marginfi/src/state/interest_rate.rs" start="369-381" />
<cite repo="EzraCole/marginfi-v2--005" path="programs/marginfi/src/state/interest_rate.rs" start="454-460" />

When `utilization_ratio > 1`, `lending_rate_apr` (= `base_rate_apr * utilization_ratio`, unclamped) can exceed `borrowing_rate_apr` (≈ `base_rate_apr * (1 + fee_ir) + fee_fixed`, whose `base_rate_apr` factor *is* clamped to the curve's 100%-UR rate). This means the bank credits depositors' `asset_share_value` with more value than is actually being generated by borrowers, worsening the shortfall that must eventually be absorbed via `socialize_loss`/insurance during `handle_bankruptcy`. Anyone who deposits during this window (deposits remain permitted per the test above) captures a disproportionate, unbacked share-value gain relative to what borrowers are paying, at the expense of the group's insurance fund and remaining depositors who bear the enlarged socialized loss.

### Likelihood Explanation
This requires a bank to already be in the documented "super-bankrupt" state (liabilities > assets, i.e. bad debt not yet resolved via `handle_bankruptcy`) — a rare but explicitly supported and tested protocol state, not a contrived or out-of-scope one. Reaching this state does not require any privileged action; it can occur organically after a large, fast price move outpaces liquidators (as `BANKRUPTCY.md` describes), or could plausibly be nudged into existence by a user maximizing bad debt before triggering their own bankruptcy. Once in that state, exploitation only requires calling the permissionless `accrue_bank_interest` instruction (or any deposit/repay, both shown to succeed in this state) and letting time pass, which is easily attacker-triggerable and requires no special permissions.

### Recommendation
Clamp the utilization ratio used for `lending_rate_apr` (and any other utilization-scaled quantity) to `[0, 1]` at the same point it's clamped for the base curve lookup, rather than only clamping the local copy inside `interest_rate_multipoint_curve`. Additionally, add an explicit invariant check, e.g. `assert!(lending_rate_apr <= borrowing_rate_apr)` (or clamp `utilization_ratio` once, up front, in `calc_interest_rate` before it is used anywhere), so a `total_liabilities_amount > total_assets_amount` condition can never inflate lender payouts beyond what borrowers actually pay.

### Proof of Concept
1. Create a bank and drive it into the documented "super-bankruptcy" state (liabilities > assets), exactly as reproduced in the existing test suite: <cite repo="EzraCole/marginfi-v2--005" path="tests/specs/bankruptcy/zb01_bankruptcy.spec.ts" start="351-442" />, culminating in the observed state where `bankValues.liability > bankValues.asset` <cite repo="EzraCole/marginfi-v2--005" path="tests/specs/bankruptcy/zb01_bankruptcy.spec.ts" start="556-560" />.
2. Before `lending_pool_handle_bankruptcy` is invoked, deposit into the bank (already shown to succeed in this state) <cite repo="EzraCole/marginfi-v2--005" path="tests/specs/bankruptcy/zb01_bankruptcy.spec.ts" start="592-611" />.
3. Trigger interest accrual (via the permissionless `accrue_bank_interest` instruction, or any subsequent deposit/repay call) so that `Bank::update_bank_cache`/`accrue_interest` runs `calc_interest_rate` with `utilization_ratio = total_liabilities_amount / total_assets_amount > 1` <cite repo="EzraCole/marginfi-v2--005" path="programs/marginfi/src/state/bank.rs" start="649-652" />.
4. Observe that `lending_rate_apr = base_rate_apr * utilization_ratio` (unclamped) is computed and applied to inflate `asset_share_value` beyond what `borrowing_rate_apr` (whose base rate is internally clamped to 100% UR) actually funds <cite repo="EzraCole/marginfi-v2--005" path="programs/marginfi/src/state/interest_rate.rs" start="205-216" />.
5. Once the bank's utilization drops back under 1 (e.g., after the admin/rescue deposit shown in the test), withdraw the inflated deposit, realizing a value gain not backed by actual borrower interest payments, at the expense of the insurance fund/remaining depositors who must cover the now-larger shortfall in `lending_pool_handle_bankruptcy`.
