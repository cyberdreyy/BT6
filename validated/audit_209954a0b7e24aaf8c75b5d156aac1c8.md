### Title
Unbounded O(N) cost in `getVoteAccounts` RPC handler scales with attacker-created on-chain vote-account count - ([File: rpc/src/rpc.rs])

### Summary
The `get_vote_accounts` handler iterates over the entire `bank.vote_accounts()` map and builds a full `RpcVoteAccountInfo` (including per-account epoch-credits history) for every entry, with no cap on the number of entries processed or returned when no `vote_pubkey` filter is supplied. Since vote-account creation is permissionless, an attacker can create many vote accounts on-chain and force each unfiltered `getVoteAccounts` call to do work proportional to the total number of on-chain vote accounts.

### Finding Description
`JsonRpcRequestProcessor::get_vote_accounts` in `rpc/src/rpc.rs` fetches `bank.vote_accounts()` and, absent a `vote_pubkey` filter, iterates every `(vote_pubkey, (activated_stake, account))` pair in the map, decoding the vote state and building an `RpcVoteAccountInfo` per entry: [1](#0-0) 
For each entry it calls `account.vote_state_view()`, walks `epoch_credits_iter()`, and allocates a `Vec<RpcVoteAccountInfo>` before partitioning into `current`/`delinquent`: [2](#0-1) 
There is no limit on the number of vote accounts processed or serialized — the only bound present is `MAX_RPC_VOTE_ACCOUNT_INFO_EPOCH_CREDITS_HISTORY`, which caps the per-account epoch-credits list, not the account count. The `filter_by_vote_pubkey` check only helps when the caller supplies `vote_pubkey`, which is optional; the default (unfiltered) code path is exactly what the question specifies. Because creating a vote account via the vote program is a permissionless action (any keypair can be used as the vote/node identity with `CreateAccount` + `InitializeAccount`), an attacker can pre-populate the chain with many zero/low-stake vote accounts, then issue a single unfiltered `getVoteAccounts` call, forcing the validator to allocate and serialize `O(N)` `RpcVoteAccountInfo` structures for a single request.

### Impact Explanation
This falls under the "RPC/validator resource exhaustion from a single low-rate call" category: a single JSON-RPC call's CPU/memory/allocation cost scales linearly with total on-chain vote-account count rather than being bounded by a fixed limit, so the cost of one request is attacker-influenced and unbounded over time as more vote accounts accumulate on-chain. Repeated at the allowed low rate (≤ 1 per `CLUSTER_SLOT_TIME_TARGET/2`), this can produce a sustained CPU/memory burden on any RPC-serving node processing `getVoteAccounts`, though it does not affect consensus, cause a crash, or return incorrect data.

### Likelihood Explanation
The precondition (creating many vote accounts) is fully permissionless and requires no special privileges — only the rent-exempt-minimum lamports and a small transaction per vote account. No commitment, subscription-quota, or vote-count guard blocks this in `get_vote_accounts`. The attack is straightforward to reproduce: create N vote accounts, then call `getVoteAccounts` with no `vote_pubkey` filter.

### Recommendation
Add a configurable/hard cap on the number of vote accounts scanned/returned per `getVoteAccounts` call when no `vote_pubkey` filter is provided (e.g., pagination, a maximum result count, or requiring a minimum-stake threshold to be included by default), and/or avoid doing the more expensive `vote_state_view()`/`epoch_credits_iter()` work for accounts that will ultimately be filtered out or that fall below a stake threshold.

### Proof of Concept
Rust integration test plan (extending the existing `test_get_vote_accounts` test in `rpc/src/rpc.rs`, e.g. around [3](#0-2) ):
1. Using `RpcHandler::start()`, programmatically create N (e.g. 10,000 and 100,000) zero-stake `VoteStateV4` accounts via `rpc.store_vote_account` (or actual `CreateAccount`+`InitializeAccount` vote-program transactions to model the on-chain permissionless path) with distinct random pubkeys.
2. Issue a single `{"jsonrpc":"2.0","id":1,"method":"getVoteAccounts"}` request (no `vote_pubkey` filter) via `io.handle_request_sync`.
3. Measure wall-clock time and allocation count of the handler call for each N, and assert the observed cost grows linearly (or worse) with N and exceeds an expected fixed-cost bound (e.g., > constant-time threshold), demonstrating the absence of any pagination/limit.
4. As an invariant assertion, add a test that fails if `get_vote_accounts` ever returns more than a defined `MAX_VOTE_ACCOUNTS_PER_RESPONSE` (currently no such constant exists), confirming the missing cap.

    fn test_get_vote_accounts() {
        let rpc = RpcHandler::start();
        let mut bank = rpc.working_bank();
        let RpcHandler {
            ref io,
            ref meta,
            ref mint_keypair,
            ref leader_vote_keypair,
            ..
        } = rpc;

        assert_eq!(bank.vote_accounts().len(), 1);

        // Create a vote account with no stake.
        let alice_vote_keypair = Keypair::new();
        let alice_vote_state = VoteStateV4::new_with_defaults(
            &alice_vote_keypair.pubkey(),
            &VoteInit {
                node_pubkey: mint_keypair.pubkey(),
                authorized_voter: alice_vote_keypair.pubkey(),
                authorized_withdrawer: alice_vote_keypair.pubkey(),
                commission: 0,
            },
            &bank.get_sysvar_cache_for_tests().get_clock().unwrap(),
        );
        rpc.store_vote_account(&alice_vote_keypair.pubkey(), alice_vote_state);
        assert_eq!(bank.vote_accounts().len(), 2);

        // Check getVoteAccounts: the bootstrap validator vote account will be delinquent as it has
        // stake but has never voted, and the vote account with no stake should not be present.
        {
            let req = r#"{"jsonrpc":"2.0","id":1,"method":"getVoteAccounts"}"#;
            let res = io.handle_request_sync(req, meta.clone());
            let result: Value = serde_json::from_str(&res.expect("actual response"))
                .expect("actual response deserialization");

            let vote_account_status: RpcVoteAccountStatus =
                serde_json::from_value(result["result"].clone()).unwrap();

            assert!(vote_account_status.current.is_empty());
            assert_eq!(vote_account_status.delinquent.len(), 1);
            for vote_account_info in vote_account_status.delinquent {
                assert_ne!(vote_account_info.activated_stake, 0);
            }
        }
