### Title
Prefunded instant-withdraw receipts are double-counted into the default recovery reserve and remain claimable at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` maps cleanly onto a use-after-free: when instant withdraws are prefunded (the CDO already collected the underlying via `collectInstantWithdrawFunds`, so `pendingInstantWithdraws` drops), the physical cash backing those receipts is "freed" — at `finalizeDefaultRecovery` it is swept into `defaultRecoveryReserve` via `_defaultPrefundedInstantReserve` and counted in `reserveAmount` to compute `defaultRecoveryPrice` — yet the stale "pointer" (`instantWithdrawsRequests[_user]` / `instantWithdrawsRequestsByEpoch[_user][epoch]`) remains live and `claimInstantWithdrawRequest` still pays the full receipt at par from the same strategy balance. The same underlying is spent twice: once as recovery backing, once as a funded claim.

### Finding Description
- `requestInstantWithdraw` mints a receipt and records `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (`IdleCreditVault.sol:356-375`).
- During `startEpoch`/epoch processing the CDO calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls the underlying into the strategy (`IdleCreditVault.sol:398-403`). The receipt itself is not cleared; only the pending counter is.
- `defaultPendingClaimBasis` adds the current-epoch instant claim basis **only when `pendingInstantWithdraws != 0`** (`IdleCreditVault.sol:644-649`). A fully prefunded instant queue therefore contributes `reserveAmount` but zero `basis`.
- `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` (`IdleCreditVault.sol:685-692`). Including prefunded instant cash in the numerator with no matching basis inflates `defaultRecoveryPrice` and `activeFinalNAV`/`defaultBBNav` (`IdleCreditVault.sol:699-700`), letting active tranche prices stay above their true recovery value.
- `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (`IdleCreditVault.sol:696`), so in `claimInstantWithdrawRequest` the defaulted-epoch clearing path `_claimDefaultedInstantWithdrawRequest` is skipped (`IdleCreditVault.sol:382-386`), and the full `instantWithdrawsRequests[_user]` is burned and paid at par via `_transferFundedClaim` (`IdleCreditVault.sol:387-392`) — out of the same balance that was just booked into `defaultRecoveryReserve`.

### Impact Explanation
One receipt, two payouts: the prefunded instant cash simultaneously (a) raises `defaultRecoveryPrice` for every defaulted claimant and active tranche holder, and (b) remains withdrawable in full by the receipt holder. The reserve is drained below what `defaultRecoveryPrice` promises, so the last claimants (normal withdraw receipts via `_transferDefaultRecovery`, defaulted instant receipts, or tranche holders redeeming through the CDO) are underpaid or cannot be paid — direct insolvency/permanent freezing of other users' claims equal to the total prefunded instant amount. Conversely, if prefunded cash were intended as recovery backing only, the receipt holder steals it by claiming at par. Either way the "one receipt one payout" and solvency invariants break.

### Likelihood Explanation
Requires only unprivileged actions: an attacker (or any user) requests an instant withdraw during the buffer; honest manager/borrower sequence provides `startEpoch` prefunding and a subsequent borrower default finalized via `finalizeDefaultRecovery`. The attacker then calls `claimInstantWithdrawRequest`. No privileged collusion, no oracle manipulation, no timing beyond the normal epoch state machine (buffer → running → defaulted → finalized). The bug triggers whenever instant requests are fully prefunded before a default.

### Recommendation
In `finalizeDefaultRecovery`/`_defaultPrefundedInstantReserve`, either (a) exclude prefunded instant cash that still backs live `instantWithdrawsRequests`/`instantWithdrawsRequestsByEpoch` receipts from `reserveAmount`, or (b) include those receipts in `defaultPendingClaimBasis` and route them through `_claimDefaultedInstantWithdrawRequest` so each unit of prefunded cash has exactly one claim basis. Additionally, in `claimInstantWithdrawRequest`, clear current-epoch instant receipts through the defaulted path whenever `defaultRecoveryFinalized`, not only when `defaultInstantWithdrawsFinalized`.

### Proof of Concept
```solidity
// Foundry fork PoC (test/foundry/) — sketch, against the harness in
// test/foundry/IdleCreditVault.t.sol
function testPrefundedInstantReceiptDoubleCounted() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                          // buffer phase
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);

    // epoch ends; borrower returns funds, user requests instant withdraw
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, amount);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    uint256 req = cdoEpoch.requestInstantWithdraw(amount / 4, address(AAtranche));

    // new epoch: manager prefunds the instant queue via collectInstantWithdrawFunds
    _startEpochAndCheckPrices(1);                       // pendingInstantWithdraws -> 0, cash in strategy

    // borrower defaults; owner/guardian finalize recovery
    _handleDefaultAndFinalize();                        // finalizeDefaultRecovery runs:
                                                        // prefundedReserve counted in reserveAmount,
                                                        // instant basis == 0 (pendingInstantWithdraws == 0)

    uint256 reserveBefore = strategy.defaultRecoveryReserve();
    uint256 balBefore     = underlying.balanceOf(address(this));

    // stale receipt still pays at par out of the recovery reserve
    cdoEpoch.claimInstantWithdrawRequest();

    assertEq(underlying.balanceOf(address(this)) - balBefore, req);
    assertLt(strategy.defaultRecoveryReserve() + strategyUnderlyingBalance(),
             reserveBefore + req, 'same cash paid as recovery backing AND as funded claim');
}
```

Note: I could not fully read `_defaultPrefundedInstantReserve`'s body (iteration limit). The finding holds if it returns the collected-but-unclaimed instant amount when `pendingInstantWithdraws == 0`; if it already excludes that case, the analogous double-spend applies to the *partially* prefunded portion, since `instantWithdrawClaimsByEpoch[epochNumber]` is added to basis at its full value while the prefunded slice is simultaneously swept into the reserve.
