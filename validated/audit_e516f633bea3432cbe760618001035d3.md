### Title
Unclaimed funded instant-withdraw receipts are double-counted when a user opens a second instant request, letting the new unfunded claim be paid out of other users' funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` aggregates a user's claim in `instantWithdrawsRequests[_user]` and mints a full receipt immediately, but `claimInstantWithdrawRequest` pays the aggregate balance with no check that the newly requested portion has actually been funded by the borrower via `collectInstantWithdrawFunds`. A user who lets an already-funded instant request sit unclaimed and then files a second instant request can claim both at once, spending underlying reserved for other claimants — the same memory-corruption shape as the reported heap overflow (one buffer region consumed twice / past its allocation).

### Finding Description
Bug-class mapping: heap-based buffer overflow (reading/writing past the boundary of an allocated region) maps to the withdraw-receipt accounting boundary in the credit vault — each instant receipt is only "allocated" backing when `collectInstantWithdrawFunds` pulls underlying into the strategy at `stopEpoch`, yet claims are settled against the *aggregate* per-user counter.

Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:
- `requestInstantWithdraw` (lines 356–375) burns CDO strategy tokens, mints the user a receipt, and does `instantWithdrawsRequests[_user] += _amount` plus `pendingInstantWithdraws += _amount`. There is no check for a pre-existing unfunded-or-unclaimed request, unlike the loss-epoch guard added to `requestWithdraw` (lines 263–271) which explicitly reverts when a stale receipt would corrupt epoch bookkeeping.
- `claimInstantWithdrawRequest` (lines 380–393) reads `amount = instantWithdrawsRequests[_user]` (the full aggregate), burns it, zeroes the counter, and calls `_transferFundedClaim(_user, amount)`. There is no epoch-wait gate and no per-epoch funding check — the analogous `claimWithdrawRequest` path enforces `epochNumber > lastWithdrawRequest[_user]` (line 326) so a request can never be claimed before its funding event.
- `collectInstantWithdrawFunds` (lines 398–403) funds `pendingInstantWithdraws` only at epoch stop, so between a user's second request and the next stop, the strategy's underlying balance only covers the first request.

Attack trace (buffer phase, fixed-APR mode, instant-withdraw enabled i.e. `lastEpochApr > unscaledApr + instantWithdrawAprDelta`):
1. Attacker (KYC'd wallet) calls `IdleCDOEpochVariant.requestWithdraw`, takes the instant path (lines 761–769 of `IdleCDOEpochVariant.sol`), gets receipt for amount A.
2. Manager stops the epoch; `collectInstantWithdrawFunds(A)` moves A underlying into the vault.
3. Instead of claiming, the attacker deposits again and calls `requestWithdraw` → instant path for amount B. Now `instantWithdrawsRequests[attacker] = A + B`, but the vault only holds A (+ other users' funded instant amounts).
4. Attacker calls `claimInstantWithdrawRequest` (via the CDO): it burns A+B receipt tokens and transfers A+B underlying. Since `_transferFundedClaim`'s reserve guard (lines 897–907) only activates when `defaultRecoveryReserve != 0`, the transfer succeeds by consuming underlying belonging to other funded instant claimants.

### Impact Explanation
Direct theft of up to B underlying from the strategy's funded-receipt pool. Other users' `claimInstantWithdrawRequest` calls will then revert on insufficient balance — permanent freezing of their unclaimed yield unless recapitalized. The invariant broken is "one receipt, one funded payout": a receipt minted before its funding event is settled against backing allocated to earlier receipts. Loss is bounded by the attacker's second deposit size but repeats across users and epochs.

### Likelihood Explanation
Requirements: instant-withdraw path active (APR decrease epoch-over-epoch beyond `instantWithdrawAprDelta`), an attacker wallet passing `isWalletAllowed`, and at least one other claimant's funded balance (or timing the claim before `collectInstantWithdrawFunds` of the second request while other funded funds sit in the vault). All are reachable by an unprivileged user in normal epoch flow; no privileged misbehavior required. The asymmetry is telling: the normal-request path was hardened with a stale-epoch revert (lines 263–271) while the instant path has no equivalent guard.

### Recommendation
Mirror the normal-request protection on the instant path: in `requestInstantWithdraw`, revert if `instantWithdrawsRequests[_user] != 0` (forcing users to claim their funded receipt before opening a new one), or track funded vs. unfunded portions per epoch and have `claimInstantWithdrawRequest` pay only the funded portion, clearing `instantWithdrawsRequestsByEpoch[_user][epoch]` per epoch instead of the aggregate.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantWithdrawDoubleSpendFundedReserves() external {
  // setup: depositAA, epoch with apr drop so _isInstantWithdrawEnabled() path is taken
  idleCDO.depositAA(10_000 * ONE_SCALE);          // attacker
  // victim deposits and requests instant withdraw of V
  // epoch stops; collectInstantWithdrawFunds funds V + attacker A receipts
  // attacker does NOT claim; deposits again and requests instant withdraw B
  // before second stopEpoch:
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest();         // CDO -> vault.claimInstantWithdrawRequest(attacker)
  // assert attacker received A + B while vault only ever funded A (+ victim's V)
  assertEq(underlying.balanceOf(attacker), expectedA + B);
  // victim claim now reverts / underfunded
  vm.expectRevert();
  vm.prank(victim);
  cdoEpoch.claimInstantWithdrawRequest();
}
```

Uncertainty: I verified the aggregate-claim path and the absence of a stale-request guard in `requestInstantWithdraw`, but did not fully trace the CDO-side `claimInstantWithdrawRequest` wrapper in `IdleCDOEpochVariant.sol` for additional gating (e.g. a per-epoch instant claim lock) — if such a guard exists there, this finding reduces to the residual case where a second instant request is made in a later epoch before claiming.
