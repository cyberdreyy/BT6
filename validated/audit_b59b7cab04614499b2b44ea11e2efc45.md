### Title
Single-client subscription flooding on distinct max-size accounts causes unbounded per-tick notification cost with no per-client cap - ([File: rpc/src/rpc_subscription_tracker.rs])

### Summary
`SubscriptionControl::subscribe` and `SubscriberCountGuard::try_reserve` enforce only a single global cap, `max_active_subscriptions` (default 1,000,000), on the total number of live subscriber tokens across the entire node; there is no per-client, per-connection, or per-IP quota. A single client operating within the allowed cadence (one call per `CLUSTER_SLOT_TIME_TARGET/2`) can open a large number of `accountSubscribe`/`programSubscribe`/`logsSubscribe` subscriptions, each targeting a distinct attacker-controlled max-size account, and force the notification pipeline to repeatedly encode/serialize all of that attacker data on every bank update that touches those accounts.

### Finding Description
`SubscriptionControlInner` tracks a single global `subscriber_count: AtomicUsize` bounded by `max_active_subscriptions`, checked in `SubscriberCountGuard::try_reserve` via a `fetch_update` comparing against `max` [1](#0-0) [2](#0-1) . This cap is enforced per live token holder regardless of which client/connection created it — there is no accounting keyed by client identity, IP, or connection anywhere in `SubscriptionControl::subscribe` [3](#0-2) , nor in `RpcSolPubSubImpl::subscribe` which simply forwards to `subscription_control.subscribe(params)` [4](#0-3) . The default value of `max_active_subscriptions` is `DEFAULT_MAX_ACTIVE_SUBSCRIPTIONS = 1_000_000` [5](#0-4) , meaning a single connection can legally hold a very large fraction (or, absent operator-side reconfiguration, effectively unlimited relative to what one client should reasonably need) of that global budget.

Each account/program subscription entry (`SubscriptionInfo`, `last_notified_slot`) has fixed per-entry bookkeeping overhead, but the *notification* work triggered on each bank update is proportional to the underlying account data size: the notifier path encodes account data via `encode_ui_account`, which serializes the full (or sliced, if configured) account bytes for each subscribed account on each relevant bank update [6](#0-5) . Because the global cap treats all subscriber slots identically irrespective of origin, one client can reserve many of those slots on distinct attacker-owned accounts sized up to the network's maximum account size, and pay the encoding/serialization cost once per relevant bank update per open subscription — with the aggregate cost scaling with the number of subscriptions times the size of the attacker-controlled data, entirely from a single client issuing calls no faster than the allowed cadence.

### Impact Explanation
This falls under the "unbounded cost for a single low-rate call"-style RPC resource-exhaustion category, except here the aggregate cost accrues from a bounded sequence of low-rate calls from one client rather than a single call. Since there is no explicit per-client cap distinct from the global `max_active_subscriptions`, one client can cause the RPC pubsub notification thread pool to do CPU work (account encoding) and hold memory proportional to `(number of open subscriptions from this client) × (attacker account size)` on every bank update, degrading pubsub service for all clients sharing that node.

### Likelihood Explanation
Feasibility depends heavily on operator configuration of `max_active_subscriptions`, `queue_capacity_items`/`queue_capacity_bytes`, and the fact that the default value is extremely large (1,000,000), and Agave's own guidance is that public RPC nodes should be placed behind rate-limiting proxies for exactly this class of concern. The code itself only implements a single global counter with no per-client subdivision, so the described disproportionate-resource-consumption behavior is real and reproducible in-process, though whether it rises to a "vulnerability" versus a known operational-hardening gap (mitigated by front-end rate limiting/connection caps, which are standard practice for public validators) is a judgment call — the repository does not implement any additional internal safeguard beyond the single global cap.

### Recommendation
Add a per-connection (or per-`SocketAddr`) subscription quota in `PubSubService`/`RpcSolPubSubImpl` that is checked in addition to the global `max_active_subscriptions`, so a single client cannot claim more than a configurable fraction of the total subscription budget. Consider also weighting the per-client budget by expected notification cost (e.g., account data size) rather than purely counting subscription slots.

### Proof of Concept
```rust
// rpc/src/rpc_subscription_tracker.rs (extend existing tests module)
#[test]
fn single_client_can_exhaust_global_cap_with_distinct_params() {
    let (sender, _receiver) = bounded(1024);
    let (broadcast_sender, _broadcast_receiver) = broadcast::channel(42);
    let max = 1000; // stand-in for DEFAULT_MAX_ACTIVE_SUBSCRIPTIONS
    let control = SubscriptionControl::new(max, sender, broadcast_sender);

    // One "client" opens `max` distinct account subscriptions itself.
    let mut tokens = Vec::new();
    for i in 0..max {
        let params = SubscriptionParams::Account(AccountSubscriptionParams {
            pubkey: Pubkey::new_unique(),
            encoding: UiAccountEncoding::Base64,
            data_slice: None,
            commitment: CommitmentConfig::finalized(),
        });
        tokens.push(control.subscribe(params).unwrap());
    }
    // Single client alone has consumed the entire global budget; a distinct,
    // legitimate client is now refused regardless of it being a separate origin.
    assert!(matches!(
        control.subscribe(SubscriptionParams::Slot),
        Err(Error::TooManySubscriptions)
    ));
    assert_eq!(control.subscriber_total(), max);
}
```
Expected assertion demonstrates no per-client isolation exists: a single caller can consume the entire configured `max_active_subscriptions` budget, and each of those subscriptions, once populated with attacker-controlled max-size account data, adds proportional encoding cost to every subsequent bank-update notification tick handled by `RpcSubscriptions::process_notifications`.

impl SubscriberCountGuard {
    fn try_reserve(control: &Arc<SubscriptionControlInner>) -> Option<Self> {
        let max = control.max_active_subscriptions;
        control
            .subscriber_count
            .fetch_update(Ordering::Relaxed, Ordering::Relaxed, |current| {
                (current < max).then_some(current + 1)
            })
            .ok()?;
        Some(Self(Arc::clone(control)))
    }
}
