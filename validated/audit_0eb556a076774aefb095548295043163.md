### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing request execution below live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges requests and confirmations *created* by the member being removed; it does not scrub confirmations that member had already cast on requests created by *other* members. Because `confirm()` counts entries in the `confirmations` set to decide whether the `num_confirmations` threshold is met, a confirmation cast by a now-removed member continues to count toward that threshold forever, letting a request execute with fewer live-member approvals than the configured policy requires.

### Finding Description
`confirm()` looks up the confirmation set for a request and executes it once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

The confirmation set is a plain `HashSet<String>` keyed by the confirming member's serialized identity, with no cross-check against current membership at count time—only that the *current* caller (`member`) is checked against `self.members` in `current_member()`: [2](#0-1) 

When a member is removed via `DeleteMember`, `delete_member` clears confirmations only for requests whose *creator* (`r.member`) equals the removed member: [3](#0-2) 

It does not scan the `confirmations` map for entries where the removed member's serialized identity appears as a *confirmer* of a request created by someone else. Those stale confirmations remain in storage and are still summed by `confirm()`'s threshold check, `self.members` no longer contains that member, but their earlier vote is still credited.

Binding broken: `confirmations counted == confirmations from members that were live members at the moment of counting`. After a `DeleteMember` execution, this becomes `confirmations counted > live-member confirmations`, because stale votes from departed members persist in the set.

### Impact Explanation
This directly maps to the in-scope Critical category "a multisig request executed below threshold." A request can reach `num_confirmations` and trigger `execute_request` (which can transfer NEAR, deploy contracts, add full-access keys, or call arbitrary functions with `deposit`) using fewer genuinely-live approvals than the contract's policy mandates. Any high-value action gated by the multisig (transfers, `AddKey` with a full-access key, `DeployContract`, `SetNumConfirmations`) can be pushed through with an artificially inflated confirmation count, effectively lowering the real security threshold without governance approving that change.

### Likelihood Explanation
Exploitation requires membership turnover, which is a normal, expected multisig operation (rotating signers/access keys) rather than an edge case—every `DeleteMember` execution leaves behind any confirmations that member previously cast on still-open requests created by other members. Any request that received a confirmation from a member before that member was removed is permanently one confirmation "ahead" of its true live-member support. No privileged access beyond ordinary participation as one of the (former) multisig members/keys is needed to have contributed the stale vote; a colluding or compromised former signer's earlier confirmation continues to count indefinitely.

### Recommendation
When removing a member in `delete_member`, iterate over `self.confirmations` for all outstanding requests (not just those the member created) and strip the removed member's identity string from each confirmation set, decrementing effective counts accordingly. Alternatively, re-validate at confirm-time that every entry in the stored confirmation set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new` with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` of funds to an external account) — created by `A`, zero confirmations yet.
3. `B` calls `confirm(R)`. Confirmation set for `R` is now `{B}` (1 confirmation, below threshold of 2, so it's queued).
4. The multisig itself executes a separate, properly-confirmed `DeleteMember { member: B }` request (a normal governance action). `delete_member` removes `B` from `self.members`, and only clears confirmations/requests where `r.member == B` (i.e., requests `B` created) — it does **not** touch `R`, which was created by `A`. `R`'s confirmation set remains `{B}` even though `B` is no longer a member.
5. `C` calls `confirm(R)`. `confirmations.len() (1, stale "B") + 1 ("C") = 2 >= num_confirmations (2)` → `execute_request(R)` runs and the transfer executes.
6. Result: `R` executed with only one live-member confirmation (`C`), even though policy requires 2 live confirmations — the removed member `B`'s stale vote substituted for a genuine second signer. [1](#0-0) [3](#0-2)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
