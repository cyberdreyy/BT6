### Title
Global AssumeRole credential LRU cache lacks per-tenant partitioning, allowing cache-key fan-out to evict other projects' cached AWS credentials - ([File: cache/s3v2/s3.go])

### Summary
`assumeRoleCredCache` is a single process-wide `expirable.LRU` shared by every project/job served by the runner manager, capped at `assumeRoleCredCacheSize` (1000) entries and keyed by `roleARN + bucketName + objectName + upload`, where `objectName` embeds the job-controlled cache key. A pipeline author can generate many distinct cache keys (e.g. via a matrix/parallel strategy or successive pipelines) to insert enough unique entries to evict other tenants' cached credentials, forcing them back onto the `AssumeRole` (STS) path.

### Finding Description
`assumeRoleCredCache` is declared as a package-level global shared across all `s3Client` instances/projects: [1](#0-0) . The cache key is computed purely from `roleARN`, `bucketName`, `objectName`, and `upload` with no per-project or per-runner partitioning: [2](#0-1) . `objectName` is passed straight through from the adapter's `objectName` field into `FetchCredentialsForRole`, and that value is derived from the job's cache key (sanitized by `cachekey.Sanitize`, but still attacker/pipeline-author-chosen content) [3](#0-2) [4](#0-3) . Each unique `(roleARN, bucketName, objectName, upload)` tuple produces a distinct cache entry that consumes one LRU slot: [5](#0-4) . Since the LRU is fixed at 1000 entries with no fairness or per-tenant reservation, inserting enough unique keys evicts the least-recently-used entries regardless of which project or job they belong to, and eviction persists in the shared long-lived process state (it is not scoped to or reversible by cancelling the attacker's job).

### Impact Explanation
When a victim's previously-cached credential entry is evicted, the victim's next `FetchCredentialsForRole` call misses the cache (`cachedCreds` returns `false`) and must issue a fresh `AssumeRole` call to AWS STS: [6](#0-5) [7](#0-6) . This is bounded to extra latency/STS calls and potential AWS STS throttling for unrelated projects sharing the same runner manager — an availability/performance degradation of the shared cache resource, not a credential leak, sandbox escape, or auth bypass. The `assumeRoleSem` concurrency semaphore limits concurrent STS calls but does not prevent this cache-poisoning-by-cardinality effect since eviction happens on `Add`, independent of the semaphore.

### Likelihood Explanation
The attacker needs only to be a pipeline author on a project served by an instance/shared runner using the `s3v2` cache backend with `RoleARN`/`UploadRoleARN` configured. Generating 1000+ distinct cache keys is straightforward (parallel/matrix jobs, or varying `cache:key` with `CI_JOB_ID`/`CI_PIPELINE_ID` across many jobs over time) — no elevated privileges or special config are required beyond normal cache usage. However, the code comment explicitly documents this as an accepted capacity tradeoff ("1,000 entries ... sufficient for instance runners serving hundreds of projects with multiple cache keys each"), indicating the sizing/lack-of-partitioning is a known design choice rather than an overlooked check, which lowers this to a resource-planning/availability concern rather than a strict security-boundary violation.

### Recommendation
Consider partitioning the credential cache per role/bucket namespace with per-tenant quotas (e.g., limit how many entries a single `roleARN`/project can hold), or size the cache/TTL based on operator-configured expected tenant count rather than a fixed global constant, so that one tenant's cache-key cardinality cannot starve others' cache slots.

### Proof of Concept
Go unit test in `cache/s3v2/s3_test.go`:
1. Construct an `s3Client` with `disableCredCache=false` and a fake/mock `sts` client (as existing tests already do) so `AssumeRole` succeeds cheaply.
2. Call `FetchCredentialsForRole` once for a "victim" `objectName` and confirm `cachedCreds` returns `ok=true`.
3. Loop 1000+ times calling `FetchCredentialsForRole` with distinct `objectName` values (simulating attacker cache-key fan-out) via a cancellable `context.Context`, then cancel that context.
4. Assert `assumeRoleCredCache.Len() == assumeRoleCredCacheSize` and that `c.cachedCreds(victimKey, ...)` now returns `ok=false`, proving eviction of the victim entry persists after the attacker's context is canceled.

// assumeRoleCacheKey returns a cache key for a set of AssumeRole parameters.
func assumeRoleCacheKey(roleARN, bucketName, objectName string, upload bool) string {
	uploadStr := "0"
	if upload {
		uploadStr = "1"
	}
	return roleARN + "\x00" + bucketName + "\x00" + objectName + "\x00" + uploadStr
}

func (c *s3Client) cachedCreds(credKey string, minValidity time.Duration) (map[string]string, bool) {
	if c.disableCredCache {
		return nil, false
	}
	cached, ok := assumeRoleCredCache.Get(credKey)
	if !ok || time.Until(cached.expiresAt) < minValidity {
		return nil, false
	}
	assumeRoleCredCacheHits.Inc()
	return cached.creds, true
}

func Sanitize(cacheKey string) (string, error) {
	if cacheKey == "" {
		return "", nil
	}

	// Decode percent-encoded chars and normalise separators, then
	// resolve traversals against a virtual root so ".." can never
	// escape beyond the root.
	cleaned := path.Clean("/" + normaliser.Replace(cacheKey))

	// Strip the leading "/" we added, split into segments, then walk
	// backwards trimming trailing whitespace from the rightmost
	// segments—dropping any that become empty.
	parts := strings.Split(cleaned[1:], "/")
	n := len(parts)
	for n > 0 {
		parts[n-1] = strings.TrimRightFunc(parts[n-1], unicode.IsSpace)
		if parts[n-1] != "" {
			break
		}
		n--
	}

	key := strings.Join(parts[:n], "/")

	if key == "" {
		return "", fmt.Errorf("cache key %q could not be sanitized", cacheKey)
	}

	return key, nil
