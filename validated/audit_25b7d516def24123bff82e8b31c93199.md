### Title
Hardcoded EIP-8130 CREATE2 addresses/init-code-hashes can silently desync from deployed contract bytecode, bricking counterfactual account creation and authenticator admission - (File: crates/common/consensus/src/transaction/eip8130/addresses.rs)

### Summary
`Eip8130Contracts` in `addresses.rs` hardcodes the CREATE2 `Address`, `salt`, and `init_code_hash` triples for the Account Configuration system contract, the default/high-rate-payer account implementations, and the P256/WebAuthn/delegate authenticators [1](#0-0) . These constants are consumed directly by consensus/execution logic — most critically `AccountChangeApplier::compute_address`, which builds the CREATE2 preimage using `Eip8130Contracts::ACCOUNT_CONFIG` as the "factory" byte and a freshly computed `code_hash` [2](#0-1) , and by the canonical-authenticator allowlist (`CANONICAL_AUTHENTICATORS` / `is_canonical_authenticator`) used on the block-validation and txpool admission paths. This is the exact bug class from the report: a hardcoded init-code-hash/derived-address baked into code that must be kept in lockstep with the actual deployed contract bytecode, where any bytecode change without re-pinning all coupled constants produces a wrong, non-existent (or wrong-but-existent) address.

### Finding Description
The module's own documentation states the risk plainly: "Because each address is derived from the contract init code, **any change to the contract bytecode changes its address**, and the account-implementation and delegate-authenticator addresses additionally cascade off the Account Configuration address" [3](#0-2) . The only safeguard is a unit test that checks internal self-consistency of each `(address, salt, init_code_hash)` triple via `Eip8130Contracts::CREATE2_FACTORY.create2(salt, init_code_hash) == address` [4](#0-3) . This test cannot detect the actual failure mode described in the report: it only proves the three hardcoded numbers are consistent *with each other*, not that `ACCOUNT_CONFIG_INIT_CODE_HASH` (or any of the authenticator/account-implementation hashes) still matches the *real* deployed contract's init code. If the reference `AccountConfiguration`/`DefaultAccount`/authenticator Solidity contracts are patched (as happened to `UniswapV2Pair` in the referenced report) and only some of the three coupled constants are re-pinned — or the off-chain mined-salt/hash values are transcribed incorrectly — the test still passes while the address is wrong.

Because `Eip8130Contracts::ACCOUNT_CONFIG` is used as the CREATE2 "factory" address inside `compute_address` for every counterfactual `CreateEntry` [5](#0-4) , and this same address is checked against `sender` for EIP-8130 create transactions (`apply_create`) [6](#0-5) , a stale `ACCOUNT_CONFIG` constant would make every legitimately-signed counterfactual create transaction fail the sender/derived-address match, or (worse) allow a different, attacker-influenced address to be treated as the canonical system contract address for CREATE2 derivation. Likewise `DEFAULT_ACCOUNT` and `DELEGATE_AUTHENTICATOR` explicitly embed `ACCOUNT_CONFIG` as a constructor argument, so any drift in `ACCOUNT_CONFIG` cascades into wrong addresses for those too.

### Impact Explanation
This is reachable by any unprivileged transaction sender submitting a standard EIP-8130 counterfactual-create transaction (the primary entry point exercised throughout `crates/execution/eip8130/src/transaction.rs` and `crates/execution/txpool/src/validator.rs`) [7](#0-6) . If the hardcoded constants desync from the real deployed bytecode:
- Every EIP-8130 counterfactual account-creation transaction would derive a different address than the actually reachable/expected system contract, causing systematic rejection (`AlreadyInitialized`/mismatch errors) or misdirected state writes — a node-wide malfunction of the entire EIP-8130 account-creation and authenticator-admission surface, analogous to the "total bricking of swapping functionality" impact in the source report.
- Because the authenticator allowlist (`CANONICAL_AUTHENTICATORS`) gates the block-validation path, a stale entry could cause valid blocks/transactions signed against the real (correctly redeployed) authenticator to be rejected by conforming nodes, or — depending on which side of the drift occurs — could cause a canonical-vs-actual mismatch that is a consensus-relevant divergence between nodes running different pinned constants.

### Likelihood Explanation
This is not an unconditional, already-triggered bug in the current snapshot — the existing self-consistency test passes for the current constants. The vulnerability is a *maintenance-time* class: it will only manifest if/when the underlying `AccountConfiguration`, `DefaultAccount`, or authenticator contract bytecode is patched and the three coupled constants (`ADDRESS`, `SALT`, `INIT_CODE_HASH`) are not correctly re-derived and re-pinned together, exactly the failure mode the source report demonstrated (init code changed, hash constant left stale). Given there is no on-chain cross-check (e.g., an extcodehash assertion against the live chain at startup) and the guard test only validates internal arithmetic self-consistency rather than the true init code, this is a plausible and easy-to-miss regression path for future redeployments/upgrades.

### Recommendation
- In addition to the existing `create2` self-consistency test, add a runtime or CI check that recomputes `keccak256` of the actual compiled contract artifacts' init code for `ACCOUNT_CONFIG`, `DEFAULT_ACCOUNT`, `CANONICAL_HIGH_RATE_PAYER_ACCOUNT`, `P256_AUTHENTICATOR`, `WEBAUTHN_AUTHENTICATOR`, and `DELEGATE_AUTHENTICATOR` and asserts it equals the corresponding `*_INIT_CODE_HASH` constant, so drift is caught at build/CI time rather than only checked for internal arithmetic consistency.
- Consider verifying `extcodehash` of the deployed addresses against the pinned constants at node startup (or via a governance/monitoring job) so a bytecode/constant mismatch is detected before it silently breaks account creation or authenticator admission in production.
- Document and enforce (e.g., via a single source-of-truth build script) that all three values per contract are regenerated together from the compiled artifact, never hand-edited independently.

### Proof of Concept
Not applicable as a live exploit against the current pinned constants (they currently pass the self-consistency test). The vulnerability class is demonstrated structurally:
1. `compute_address` derives every counterfactual EIP-8130 account address using `Eip8130Contracts::ACCOUNT_CONFIG` as the CREATE2 base [8](#0-7) .
2. The only protection, `addresses_match_create2_derivation`, checks `create2(salt, init_code_hash) == address` — a tautological check that cannot detect a wrong-but-internally-consistent hash trio if the underlying contract bytecode changed [9](#0-8) .
3. If any redeploy updates the contract bytecode without correctly regenerating and re-pinning `ADDRESS`/`SALT`/`INIT_CODE_HASH` together, every subsequent counterfactual `Create` transaction submitted by ordinary senders (as constructed in `create_tx_and_signed`/`counterfactual_create_signed`) will derive an address that either fails the sender-match check in `apply_create`, or targets a contract not actually holding the intended EIP-8130 code, breaking account creation network-wide.

    pub fn apply_create(

        entry: &CreateEntry,

        // admission and block inclusion) rejects the same set of malformed
        // runtimes at the shared choke point, matching the reference contract's
        // CREATE2 deploy (EIP-170 size, EIP-3541 leading-byte).
        Self::validate_create_runtime(&entry.code)?;
        let address = Self::compute_address(entry.user_salt, &entry.code, &entry.initial_actors)?;

        // `local_sequence` doubles as the created/imported flag; `local_epoch`
        // covers an account whose sequence was reset to 0 by `IncrementLocalEpoch`;
        // and `multichain_sequence` guards an account that established state via a

        // initial actor (mirrors `createAccount`'s guard).

    /// Computes the counterfactual CREATE2 address for a created account. Mirrors
    /// `computeAddress`.
    pub fn compute_address(
        user_salt: B256,
        code: &[u8],
        initial_actors: &[InitialActor],
    ) -> Result<Address, ApplyError> {
        let effective_salt = Self::effective_salt(user_salt, initial_actors);
        let code_hash = keccak256(Self::build_deployment_code(code)?);
        let mut buf = Vec::with_capacity(1 + 20 + 32 + 32);
        buf.push(0xff);
        buf.extend_from_slice(Eip8130Contracts::ACCOUNT_CONFIG.as_slice());
        buf.extend_from_slice(effective_salt.as_slice());
        buf.extend_from_slice(code_hash.as_slice());
        Ok(Address::from_word(keccak256(buf)))
    }
