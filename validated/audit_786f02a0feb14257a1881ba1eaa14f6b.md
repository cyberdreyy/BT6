### Title
Unauthenticated-role-gate on GET /v2/bridge_types/:BridgeName discloses bridge OutgoingToken credential to view-role users - ([File: core/web/router.go])

### Summary
The route `authv2.GET("/bridge_types/:BridgeName", bt.Show)` has no `auth.RequiresEditRole`/`RequiresRunRole` wrapper (unlike `Create`/`Update`/`Destroy`), so any authenticated user—including `view` role or a restricted API token—can call `BridgeTypesController.Show`. The handler serializes the full `bridges.BridgeType` via `presenters.NewBridgeResource`, which unconditionally copies `OutgoingToken` into the JSON response, exposing this bridge credential to low-privileged callers.

### Finding Description
`v2Routes` registers `authv2.GET("/bridge_types/:BridgeName", bt.Show)` [1](#0-0)  with no role gate, in contrast to the sibling routes for `Create`, `Update`, and `Destroy` which are wrapped in `auth.RequiresEditRole`. The only guard applied group-wide is `auth.Authenticate(..., AuthenticateByToken, AuthenticateBySession)` [2](#0-1) , which only checks that the caller is *some* authenticated user/token — it does not check role. `RequiresEditRole`/`RequiresRunRole` are separate, opt-in wrapper functions [3](#0-2) , and `Show` never uses either.

`BridgeTypesController.Show` looks up the bridge by name and renders it via `presenters.NewBridgeResource(bt)` [4](#0-3) . The `bridges.BridgeType` DB model stores `OutgoingToken` in plaintext (not hashed, unlike `IncomingTokenHash`) [5](#0-4) , and `NewBridgeResource` copies it directly into the `BridgeResource.OutgoingToken` field with no `omitempty` and no redaction [6](#0-5) . This is confirmed by the presenter unit test, which shows `outgoingToken` always present in the serialized JSON, unlike `incomingToken` which is `omitempty` and only present when explicitly set by `Create` [7](#0-6) .

The existing controller test `TestBridgeController_Show` only asserts `Name`, `URL`, and `Confirmations` fields match, and never checks/asserts that `OutgoingToken` is absent from the response — it does not catch this issue [8](#0-7) .

Note: `IncomingToken` is not persisted server-side at all (only its salted hash, `IncomingTokenHash`, is stored) [5](#0-4) , so it cannot leak via `Show`. The concrete disclosure is limited to `OutgoingToken`, plus non-secret `Confirmations`/`MinimumContractPayment`/`URL` metadata which are not considered sensitive credentials.

### Impact Explanation
Any authenticated `view`-role user or a restricted API token can retrieve a bridge's `OutgoingToken` — a credential meant to authenticate the node to the external adapter (or used by the external adapter to push results back) — without requiring `edit`/`run`/`admin` privileges. This matches the bounty scope of "job spec contents including bridge credentials" being disclosed to a low-privileged party, since bridge names are frequently reused across job specs and the token grants adapter-side capabilities tied to that bridge.

### Likelihood Explanation
Trivially reproducible: only requires one authenticated session or API token of any role (including the lowest, `view`), and a single `GET /v2/bridge_types/<name>` request with a known/guessable bridge name. No race conditions, no admin access, no additional exploitation steps required.

### Recommendation
Wrap the `Show` route with `auth.RequiresEditRole` (matching `Create`/`Update`/`Destroy`), or, if view-level read access to bridge metadata is intentionally allowed, strip `OutgoingToken` from the presenter output for non-privileged roles (e.g., add a redacted variant of `BridgeResource` for `Show`/`Index`, keeping `OutgoingToken` only in the `Create` response, similar to how `IncomingToken` is already `omitempty` and only populated on creation).

### Proof of Concept
1. In `core/web/bridge_types_controller_test.go`, extend `TestBridgeController_Show` (or add a new test) to:
   - Create an app with a `view`-role user/session (see how other tests construct restricted-role clients, e.g. via `app.NewHTTPClient` with a specific role or an API token of `view` role).
   - Create a bridge via `app.BridgeORM().CreateBridgeType` with a known `OutgoingToken`.
   - As the `view`-role client, call `GET /v2/bridge_types/<name>`.
   - Assert `resp.StatusCode == http.StatusOK` (expected to succeed, proving no role gate blocks it).
   - Unmarshal into `presenters.BridgeResource` and assert `resource.OutgoingToken != ""` and equals the bridge's stored token — demonstrating credential disclosure to an under-privileged caller.
2. Contrast with a similar test against `PATCH`/`DELETE`/`POST /v2/bridge_types` as the same `view`-role client, expecting `401 Unauthorized` due to `RequiresEditRole`, to show the inconsistency.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

func TestBridgeController_Show(t *testing.T) {
	t.Parallel()

	app := cltest.NewApplication(t)
	require.NoError(t, app.Start(t.Context()))

	client := app.NewHTTPClient(nil)

	bt := &bridges.BridgeType{
		Name:          bridges.MustParseBridgeName(testutils.RandomizeName("showbridge")),
		URL:           cltest.WebURL(t, "https://testing.com/bridges"),
		Confirmations: 0,
	}
	ctx := t.Context()
	require.NoError(t, app.BridgeORM().CreateBridgeType(ctx, bt))

	resp, cleanup := client.Get("/v2/bridge_types/" + bt.Name.String())
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusOK, resp.StatusCode, "Response should be successful")

	var resource presenters.BridgeResource
	cltest.ParseJSONAPIResponse(t, resp, &resource)
	assert.Equal(t, bt.Name.String(), resource.Name, "should have the same name")
	assert.Equal(t, bt.URL.String(), resource.URL, "should have the same URL")
	assert.Equal(t, bt.Confirmations, resource.Confirmations, "should have the same Confirmations")

	resp, cleanup = client.Get("/v2/bridge_types/nosuchbridge")
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusNotFound, resp.StatusCode, "Response should be 404")
}
