### Title
Incomplete validation of optional proof-account offsets causes misattributed account data in SPL-Token-2022 confidential instruction parsing - (File: transaction-status/src/parse_token/extension/confidential_transfer.rs)

### Summary
The confidential-transfer/confidential-mint-burn/confidential-transfer-fee/permissioned-burn instruction parsers in `transaction-status` compute an `offset` into `account_indexes` to decide which optional "proof context state account" or "instructions sysvar" fields are present, then feed the *same accumulated* `offset` into `parse_signers` to resolve the trailing `owner`/`multisigOwner` accounts. Like the `getMultiplier` bug class, each individual guard (`offset < account_indexes.len().saturating_sub(N)`) is locally "safe" (no panic), but the checks are done independently per optional field rather than validating the *combination* of proof-offset flags against the actual account list length. This lets a value that "looks valid" for one guard silently diverge from what the instruction data actually implies, so the function never fails but returns internally inconsistent (wrong) parsed output.

### Finding Description
In `parse_confidential_transfer_instruction` (`ConfidentialTransferInstruction::Transfer`), the number of optional accounts (`instructionsSysvar`, `equalityProofContextStateAccount`, `ciphertextValidityProofContextStateAccount`, `rangeProofContextStateAccount`) that must be present depends on the *values* of `equality_proof_instruction_offset`, `ciphertext_validity_proof_instruction_offset`, and `range_proof_instruction_offset` decoded from `instruction_data`: [1](#0-0) 

Each `if` block only checks `offset < account_indexes.len().saturating_sub(1)` — a generic remaining-length check — not whether the *specific number of accounts required by this particular combination of offsets* actually exists. `check_num_token_accounts(account_indexes, 4)` only enforces a fixed minimum unrelated to how many optional accounts a given offset-combination needs.

Because the guards are independent, `account_indexes.len()` being "just barely enough" for some fields but not others causes some optional slots to be silently skipped (no panic, since each guard is safe on its own) while `offset` keeps incrementing only when a field actually gets inserted. This same pattern repeats for `TransferWithFee` [2](#0-1) , for `Mint`/`Burn` in confidential_mint_burn.rs [3](#0-2) , for `WithdrawWithheldTokensFromMint` in confidential_transfer_fee.rs [4](#0-3) , and for `ConfidentialBurn` in permissioned_burn.rs [5](#0-4) .

The final `offset` value — whose correctness silently depends on this incomplete combination check — is then passed straight into `parse_signers`, which uses it to index `account_indexes` for the `owner`/`multisigOwner` fields: [6](#0-5) 

If a crafted (but structurally-valid, i.e., passing `check_num_token_accounts`) transaction supplies an `account_indexes` list whose length matches the *minimum* required accounts but sets `*_proof_instruction_offset` fields to combinations that this code does not exhaustively cover (only a handful of combinations are exercised by the accompanying tests, e.g. `confidential_transfer.rs:1019-1039` "All Contexts / All Offsets / Mixed C-I-C / Mixed I-C-I"), the accumulated `offset` reaching `parse_signers` can point at an account that is not the actual owner/multisig-owner account — for example, an account that is actually a mint or a proof context-state account gets labeled `"owner"` in the parsed JSON, or vice versa. This is analogous to `getMultiplier` returning a superficially "valid" (`0`) result for the boundary case while still producing an incorrect result for internally inconsistent inputs — here the parser never panics but silently misreports account/field associations.

### Impact Explanation
This is a decoder misreporting bug in `transaction-status`, which backs `getTransaction`/`getConfirmedTransaction` JSON-RPC responses with `encoding: jsonParsed`. Any unprivileged user can submit or replay such a transaction (it does not need to succeed on-chain — parsing happens on the raw instruction/account list from a message, independent of execution success) and cause the RPC node to return a parsed instruction whose `"owner"`, `"multisigOwner"`, `"proofContextStateAccount"`, or `"instructionsSysvar"` field is bound to the wrong `Pubkey`. Consumers (wallets, explorers, indexers) that trust this parsed output for auditing/ownership decisions receive incorrect data. This falls under the accepted category "decoder panic and misreporting" for instruction parsing in the validate rules.

### Likelihood Explanation
Likelihood is limited by the fact that: (1) an attacker must construct a transaction whose SPL-Token-2022 confidential-extension instruction accounts/offsets fall exactly into one of the un-covered combinations (only 3–4 of many possible C/I combinations are tested), and (2) I was unable to fully confirm the exact minimum values enforced by `check_num_token_accounts` for each variant, nor definitively construct a concrete offset/account-count combination that produces a wrong-but-non-panicking result, due to running out of tool iterations. This should be verified with a Devin session that has file-system/test access to enumerate all offset/account-count combinations against `check_num_token_accounts`'s actual minimums.

### Recommendation
Rather than gating each optional account insertion independently on `offset < account_indexes.len().saturating_sub(N)`, compute the total number of accounts required by the specific combination of proof-offset values up front (mirroring the "return valid value for every case" recommendation from the report) and validate it against `account_indexes.len()` before beginning to assign any offsets, returning a parse error if inconsistent, rather than silently proceeding with a partially-filled, internally-inconsistent `offset`.

### Proof of Concept
Not independently reproduced within the available tool budget. Conceptually: construct an SPL-Token-2022 `Transfer` (or `TransferWithFee`, `Mint`, `Burn`, `WithdrawWithheldTokensFromMint`, permissioned `ConfidentialBurn`) instruction with `account_indexes.len()` equal to the minimum enforced by `check_num_token_accounts`, but with a combination of `*_proof_instruction_offset` fields not covered by the existing tests (`confidential_transfer.rs` test cases only cover "All Contexts / All Offsets / Mixed C-I-C / Mixed I-C-I"), such that the independent per-field guards allow the running `offset` to diverge from the actual owner-account index, then call `parse_token` on the resulting `CompiledInstruction` and inspect the `"owner"`/`"multisigOwner"` fields of the returned JSON for misattribution. This needs to be confirmed with the actual `check_num_token_accounts` minimums and a test harness, which was not available in this session.
