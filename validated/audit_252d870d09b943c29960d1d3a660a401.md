I have enough evidence to finalize the finding. The `multisig2` contract (`multisig2/src/lib.rs`) has confirmations counted against a stale membership snapshot rather than live members, directly matching the "confirmations counted versus live members" binding.

### Title
Stale confirmations from removed multisig members still count toward execution threshold, allowing sub-quorum execution - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` removes a member from the `members` set but only purges requests that member *created*; it never removes that member's *confirmations* on requests created by other members. `confirm()` then compares `confirmations.len()` against `num_confirmations` without checking that each recorded confirmer is still a current member. This lets a stale confirmation from an account no longer part of the multisig count toward the threshold, allowing a request to execute with fewer live, currently-trusted confirmers than `num_confirmations` requires.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` decides whether to execute a request purely from the *count* of entries in the request's confirmations `HashSet<String>`: [1](#0-0) 

Membership removal is implemented in `delete_member`: [2](#0-1) 

This function only scans `self.requests` for entries where `r.member == member` (i.e., requests *created by* the removed member) and clears those. It does not scan `self.confirmations` for *other* pending requests that the removed member had already confirmed. Because `confirmations` is a separate `LookupMap<RequestId, HashSet<String>>` keyed independently from `members`, a member's confirmation string persists in any request they confirmed before being removed.

Binding broken: `confirmations counted in confirm() == confirmations from members currently in self.members` is assumed but not enforced. After a `DeleteMember` action executes, this equality no longer holds for any request the removed member had confirmed but did not create.

Concretely, with members `{A, B, C, D}` and `num_confirmations = 3`:
1. A creates request `R1` (e.g., `Transfer`). `B` confirms (`confirmations = {B}`), `C` confirms (`confirmations = {B, C}`, still short of 3).
2. Separately, members confirm and execute a `DeleteMember { C }` request, removing `C` from `self.members`. `delete_member` clears only requests *authored* by `C`; `R1`'s confirmation set `{B, C}` is untouched.
3. `A` now confirms `R1`: `confirmations.len() (2) + 1 >= num_confirmations (3)` → `R1` executes, using `C`'s now-stale confirmation as one of the three "votes," even though only `A` and `B` are still live members who actually authorized this specific request.

### Impact Explanation
This is a threshold-bypass on the multisig's core custody guarantee: a request (including `Transfer`, `AddKey`, `FunctionCall`, or another `DeleteMember`/`AddMember`) can be executed while backed by fewer *live* confirming members than `num_confirmations` mandates. This matches the Critical impact category "a multisig request executed below threshold," since NEAR (or access/permissions on the account) can move based on authorization that includes a party no longer entrusted with signing rights.

### Likelihood Explanation
This does not require any external attacker privilege beyond normal multisig operation: membership changes (onboarding/offboarding signers) are an expected multisig lifecycle event, and it is entirely plausible for a request to be pending confirmation at the time a member is removed. No malicious insider collusion beyond ordinary confirm/delete-member usage is needed to trigger the stale-vote condition; only the *interpretation* of the stale confirmation as valid is the bug.

### Recommendation
When executing `DeleteMember`, iterate over all entries in `self.confirmations` (not just `self.requests` filtered by author) and remove the deleted member's confirmation string from every request's confirmation set. Alternatively, validate at `confirm()` time that each entry in the confirmations set still belongs to `self.members` (e.g., filter the set to only members still present in `self.members` before comparing its length to `num_confirmations`).

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)`.
2. `A` calls `add_request` with `MultiSigRequest { receiver_id: contract, actions: [Transfer{amount}] }` → `request_id = R1`.
3. `B` calls `confirm(R1)` → confirmations `{B}`.
4. `C` calls `confirm(R1)` → confirmations `{B, C}` (2 < 3, not yet executed).
5. In parallel, `A`, `B`, `D` add and confirm a `DeleteMember { member: C }` request (3 confirmations, passes `self.members.len() - 1 >= num_confirmations` check since 3 members remain) → `C` removed from `self.members`; `R1`'s confirmations set is untouched because `R1` was authored by `A`, not `C`.
6. `A` calls `confirm(R1)`: `confirmations.len() (2) + 1 == num_confirmations (3)` → `execute_request` runs the `Transfer`, even though only `A` and `B` are current members who confirmed it — one fewer live confirmer than the configured 3-of-N threshold. [3](#0-2) [4](#0-3)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
