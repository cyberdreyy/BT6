### Title
JWT replay-protection check-then-record race in `WorkflowMetadataHandler.Authorize` allows duplicate workflow triggers - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
The Bootfinance airdrop bug (`claimExact`/`validate` check-then-write race) allowed re-claiming funds because the "already claimed" check and the state mutation that finalizes the claim were not atomic. The Chainlink HTTP-trigger gateway has the same class of bug: the JWT replay-protection check (`isReplay`) and the write that marks a JWT as consumed (`recordUsage`) are two independent, separately-locked operations rather than one atomic check-and-set, so two concurrent requests carrying the same signed JWT can both pass the replay check before either records usage.

### Finding Description
`WorkflowMetadataHandler.Authorize` is the function that authenticates unprivileged, internet-facing HTTP trigger requests before they are fanned out to workflow nodes to execute a workflow run: [1](#0-0) 

The anti-replay check and the "consume" step are implemented as two distinct calls into `jwtReplayCache`, each taking its own lock independently: [2](#0-1) 

`isReplay` takes an `RLock`, checks map membership, and releases the lock. Only later — after the (unrelated) authorized-key lookup — does `recordUsage` take a separate `Lock` and insert the jti into the map. There is no single critical section covering "check jti unused" + "mark jti used", exactly mirroring the airdrop bug where `validate()`'s zero-check and the state overwrite that resets `claimed` were not atomic.

`Authorize` is invoked from `httpTriggerHandler.HandleUserTriggerRequest` via `authorizeRequest`, before the per-request in-flight dedup (`setupCallback`, keyed by `req.ID`) is set up: [3](#0-2) 

Because the in-flight/duplicate-ID guard is only established after `authorizeRequest` returns, two goroutines processing the same (or replayed) signed JWT request concurrently can both execute `isReplay(claims.ID)` and see "not yet used" before either calls `recordUsage(claims.ID)`. Both requests then proceed to be authorized and dispatched to the workflow DON.

### Impact Explanation
This breaks the JWT replay-protection guarantee that is the sole mechanism (besides signature verification) preventing a captured/duplicated signed trigger request from executing a workflow more than once. Successful exploitation causes an unauthorized/duplicate workflow execution from a single signed authorization, which is a concrete "unauthorized job run" per the accepted impact classes — the same class of harm as duplicate/double-claim in the original finding, just applied to workflow executions instead of token transfers.

### Likelihood Explanation
The race window is narrow (two lock acquisitions separated by a map lookup) but is triggerable by any unprivileged client capable of sending the same HTTP trigger request (or a replayed copy of a legitimately-observed one) twice in rapid succession/concurrently to the internet-facing gateway — no special privilege or node compromise is required. Likelihood is moderate: exploitation requires precise timing to land both requests inside the check-then-record window, but this is achievable with standard request racing techniques (e.g., HTTP/2 multiplexed simultaneous requests).

### Recommendation
Make the replay check-and-mark atomic: hold a single lock (or use a `sync.Map`/`LoadOrStore`-style compare-and-set) across "is jti already used" and "mark jti used," e.g., replace `isReplay`+`recordUsage` with a single `checkAndRecord(jti) bool` method that atomically inserts the jti and returns whether it was already present, and use that as the sole gate in `Authorize`.

### Proof of Concept
1. Register a workflow with an authorized signer.
2. Sign one HTTP trigger request (fixed `req.ID`, fixed JWT `jti`).
3. Fire the same signed request concurrently (e.g., two goroutines calling `HandleUserTriggerRequest`/`Authorize` at the same time, or two near-simultaneous HTTP POSTs before the in-flight callback map is populated).
4. Both calls can observe `jwtCache.isReplay(claims.ID) == false` before either calls `recordUsage`, so both requests pass authorization and are dispatched to the DON, causing the workflow to run twice from one JWT — contrary to the "token has already been used" guarantee demonstrated in the sequential test case at `core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go:357-394`.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
