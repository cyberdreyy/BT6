### Title
`getRecentPrioritizationFees` can return fee data for a dumped/non-canonical slot with no cache invalidation mechanism - (File: `runtime/src/prioritization_fee_cache.rs`)

### Summary
`PrioritizationFeeCache` finalizes a slot's fee entry into `cache` as soon as `finalize_priority_fee(slot, bank_id)` is called from `OptimisticallyConfirmedBankTracker::notify_or_defer`, and that entry is never removed except by FIFO eviction (`cache.pop_first()`) once `cache_max_size` (`MAX_NUM_RECENT_BLOCKS` = 150) is exceeded. If the fork containing that slot is later dumped/purged (e.g. via duplicate-slot repair / `dump_then_repair_correct_slots`), there is no code path in `prioritization_fee_cache.rs` that removes or marks the slot as invalid, so `get_prioritization_fees` (backing `getRecentPrioritizationFees`) keeps returning it as if it were part of the canonical chain.

### Finding Description
`finalize_priority_fee` is invoked from `notify_or_defer` in `rpc/src/optimistically_confirmed_bank_tracker.rs:216-218` whenever a bank is frozen and optimistic-confirmation notification fires; it enqueues `CacheServiceUpdate::BankFinalized { slot, bank_id }` [1](#0-0) . The service loop's `finalize_slot` then permanently moves the `PrioritizationFee` entry for that `bank_id` into the shared `cache: RwLock<BTreeMap<Slot, PrioritizationFee>>`, with the only bound being size-based FIFO eviction: [2](#0-1) 

There is no code in `runtime/src/prioritization_fee_cache.rs` referencing `purge`, `dump`, root-set intersection, or `BankForks`/blockstore state — a grep over the file confirms no invalidation logic exists at all. Once inserted, an entry is queryable via `get_prioritization_fees` regardless of whether its slot subsequently gets dumped from blockstore/BankForks due to duplicate-block resolution (`dump_then_repair_correct_slots`). Optimistic confirmation is a probabilistic/soft guarantee, not an absolute one — Agave's own duplicate-slot handling can still discard an OC'd fork in rare cases — yet `finalize_priority_fee` treats OC as final and irrevocable.

### Impact Explanation
A regular RPC client calling `getRecentPrioritizationFees` (or specifying a set of accounts) can receive prioritization-fee data attributed to a slot number that is no longer part of the canonical/rooted chain, i.e., wrong-slot/fork data returned by a single unprivileged call — this matches the "wrong-slot/fork/account data returned" bounty category. It does not cause a crash or consensus mutation, but it violates the invariant that RPC "finalized" answers should never derive from unrooted/dumped forks.

### Likelihood Explanation
Preconditions: a slot must be optimistically confirmed and its prioritization-fee finalize signal delivered to `PrioritizationFeeCache`, then the corresponding fork must later be dumped by the normal duplicate-block-resolution path. This dump/repair path is a routine part of Agave consensus operation (not something the RPC caller needs privileged control over) and occurs during ordinary network operation. Once it happens, any single unprivileged `getRecentPrioritizationFees` call will observe the stale/non-canonical entry until the cache naturally FIFO-evicts it up to 150 blocks later. This is not attacker-triggerable on demand, but it's a real, reproducible correctness gap tied to existing consensus behavior.

### Recommendation
Have `PrioritizationFeeCache` subscribe to fork-dump/purge notifications (e.g., via the same channel or a new one signaled from `dump_then_repair_correct_slots` / blockstore's `clear_unconfirmed_slot` path) and remove the corresponding entry from `cache` when a previously-finalized slot is dumped. Alternatively, gate `finalize_priority_fee` behind root confirmation instead of optimistic confirmation, or have `get_prioritization_fees` cross-check candidate slots against `BankForks`'s current fork/root set before returning them.
