### Title
Unauthorized low-privilege access to `/v2/debug/pprof/*` endpoints exposes process memory/CPU profiles - (File: core/web/router.go)

### Summary
The pprof debug routes registered via `metricRoutes(authv2)` in `core/web/router.go` are only gated by `auth.Authenticate` (any valid session or token), with no role check applied, unlike every other sensitive endpoint in the router which uses `auth.RequiresEditRole` or `auth.RequiresAdminRole`. A user who only holds a view or run role session/token can therefore dump full heap, goroutine, profile, and trace data from the running node process.

### Finding Description
In `v2Routes`, `authv2` is created with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0)  which only verifies that the caller has valid credentials, setting the authenticated user in context without any role restriction, as implemented in `auth.Authenticate` [2](#0-1) . Nearly all sensitive handlers registered on `authv2` are wrapped with `auth.RequiresEditRole` or `auth.RequiresAdminRole` (e.g. key management, job creation, user management) [3](#0-2) . However, `metricRoutes(authv2)` is called unwrapped at the end of the `authv2` block [4](#0-3) , and inside `metricRoutes`, every `/debug/pprof/*` handler (`heap`, `profile`, `goroutine`, `trace`, `allocs`, `block`, `mutex`, `threadcreate`, `cmdline`, `symbol`, index) is registered directly with no role wrapper at all [5](#0-4) . Since the role check functions (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) are the only place role is enforced [6](#0-5) , and they are never invoked for these routes, any authenticated identity — including a session created with `UserRoleView` via `POST /sessions`, or an API token belonging to a view-role user — can call `GET /v2/debug/pprof/heap?debug=1`, `GET /v2/debug/pprof/profile`, etc., and receive a 200 response with full pprof output.

### Impact Explanation
Heap and goroutine profiles from a Go process routinely include in-memory copies of secrets, private keys, unencrypted key material buffers, database credentials, and other sensitive state currently referenced on the heap or in goroutine stacks. A low-privilege "view" role user (the lowest privilege tier, intended for read-only dashboards) or a run-role external-initiator-equivalent identity can extract this data, constituting unauthorized information disclosure of process secrets — matching a "sensitive data exposure" / broken access control bounty impact class.

### Likelihood Explanation
The only precondition is possessing any valid authv2 identity — a view-role user session (created via `POST /sessions` with view credentials) or a view/run-role API token — which is the lowest privilege level supported by the system. No additional exploitation complexity, timing, or race condition is required; the request is a single unauthenticated-by-role `GET` to a fixed, always-registered path, making this fully deterministic and repeatable.

### Recommendation
Wrap all handlers registered in `metricRoutes` with at least `auth.RequiresAdminRole` (consistent with the sensitivity of process-memory/CPU data), e.g. change each `pprofGroup.GET(...)` registration in `core/web/router.go` to pass the handler through `auth.RequiresAdminRole(...)`, matching the pattern already used for `/keys/*` and `/users` routes.

### Proof of Concept
Go handler-level integration test plan (in `core/web/router_test.go` or a new `core/web/pprof_test.go`):
1. Set up a test app via existing test harness (`cltest.NewApplication`/`setupWebServer`).
2. Create a session/user with `clsessions.UserRoleView` using existing test session helpers (e.g. `cltest.MustRandomUser` with `Role: UserRoleView`), and log in via `POST /sessions` to obtain a session cookie.
3. Issue `GET /v2/debug/pprof/heap?debug=1` (and separately `/v2/debug/pprof/profile?seconds=1`) using the view-role session cookie.
4. Assert current (buggy) behavior returns `http.StatusOK` with pprof body content.
5. After applying the fix (wrapping routes with `auth.RequiresAdminRole`), assert the same request returns `http.StatusForbidden`.
6. Repeat with an admin-role session and assert `http.StatusOK` is preserved, confirming no regression for legitimate admin access.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)

	}

	}
