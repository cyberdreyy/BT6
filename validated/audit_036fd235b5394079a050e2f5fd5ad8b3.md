## Finding: Unbounded concurrent WebSocket handshakes in the flashblocks publisher listener (Slowloris-style DoS)

### Title
Unbounded concurrent handshake spawning in flashblocks WebSocket `Listener` enables slow-loris denial of service - (File: `crates/builder/publish/src/listener.rs`)

### Summary
The flashblocks pending-state publisher's connection acceptor spawns one Tokio task per accepted TCP connection with no bound on the number of connections concurrently awaiting the WebSocket handshake. This mirrors the reported `tls-listener` defect: a fixed per-connection handshake timeout exists, but there is no cap on how many handshakes may be in flight simultaneously, so an unauthenticated remote client can exhaust listener resources by opening many connections and never completing (or slowly trickling) the handshake.

### Finding Description
`Listener::run` accepts a connection and unconditionally calls `tokio::spawn` for every accepted socket, before any handshake or rate limiting occurs: [1](#0-0) 

The only protection against a stalled peer is a fixed 10-second timeout (`HANDSHAKE_TIMEOUT`) applied per-connection: [2](#0-1) [3](#0-2) 

There is no semaphore, connection-count limit, or per-IP throttling anywhere in this code path — `WebSocketPublisher::with_capacity` simply binds the listener and spawns the `Listener::run` loop with no additional guard: [4](#0-3) 

This is the same root cause as CVE-2024-28854: a fixed handshake timeout without a concurrency cap. In contrast, the sibling `crates/infra/websocket-proxy` server explicitly acquires a rate-limit ticket (`state.rate_limiter.try_acquire(client_addr)`) before upgrading any connection, demonstrating that the codebase's own pattern for public listeners is to bound concurrent/per-IP connections — a control absent from `crates/builder/publish/src/listener.rs`: [5](#0-4) 

Because the flashblocks publisher's socket is meant to serve pending-state subscribers publicly, an attacker can open many raw TCP connections (never sending the WebSocket upgrade request, or sending it byte-by-byte) to keep tasks alive for up to 10 seconds each, and continuously reopen them faster than they expire.

### Impact Explanation
Each accepted socket holds a live Tokio task, an open file descriptor, and (per test wiring) resources tied to `BroadcastLoop`/ring buffer subscription for up to 10 seconds. With unbounded concurrent acceptance, an attacker can drive file-descriptor and task-count exhaustion on the node process hosting the flashblocks publisher, denying new legitimate subscribers (builders/relayers/RPC consumers relying on flashblocks pending state) from connecting — a node halt/service-availability impact scoped to the flashblocks pending-state distribution path.

### Likelihood Explanation
The attack requires only unauthenticated TCP connections to the publicly-exposed flashblocks WebSocket port; no authentication, valid handshake, or payload is required to consume a listener slot for the full `HANDSHAKE_TIMEOUT` window, matching the low-cost PoC described in the advisory (opening streams and sending 0 bytes).

### Recommendation
Bound the number of concurrent in-flight (pre-handshake) connections in `Listener::run`, e.g., via a `tokio::sync::Semaphore` acquired before `tokio::spawn`, and/or apply per-IP connection limits analogous to `crates/infra/websocket-proxy/src/rate_limit.rs`, rejecting or delaying accepts once a configurable `max_handshakes` threshold is reached.

### Proof of Concept
Analogous to the referenced advisory's PoC: repeatedly open raw TCP connections to the flashblocks publisher's bound address (as returned by `WebSocketPublisher::new`/`with_capacity`) without completing the WebSocket upgrade, and hold each open up to just under 10 seconds while opening new ones faster than the timeout expires. Since `Listener::run` accepts and spawns without any concurrency cap, this can occupy an unbounded number of tasks/file descriptors, starving legitimate subscribers.
