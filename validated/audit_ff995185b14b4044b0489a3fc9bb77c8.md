### Title
`RoleNotPermittedError` leaks the caller's actual role string and is distinguishable from `unauthorizedError`, enabling privileged-mutation/role enumeration - ([File: core/web/resolver/auth.go])

### Summary
`RoleNotPermittedError.Error()` embeds the session user's exact `sessions.UserRole` value in the returned GraphQL error message, and unlike `unauthorizedError` it does not implement an `Extensions()` method to normalize the error to a generic `UNAUTHORIZED`/`FORBIDDEN` code. This makes "no session" and "wrong role" errors trivially distinguishable to any authenticated caller, and reveals role information in plaintext error text.

### Finding Description
`core/web/resolver/auth.go` defines two gate helpers used by mutation resolvers (`authenticateUserCanRun`, `authenticateUserCanEdit`, `authenticateUserIsAdmin`) called from `core/web/resolver/mutation.go` for every admin/edit/run-gated GraphQL mutation. [1](#0-0) 

`unauthorizedError` (returned when there is no authenticated session) implements both `Error()` and `Extensions()`, normalizing the response to `code: "UNAUTHORIZED"` with the generic message "Unauthorized": [2](#0-1) 

`RoleNotPermittedError` (returned when a session exists but the role is insufficient) only implements `Error()`, which formats the caller's own role directly into the message: `fmt.Sprintf("Not permitted with current role: %s", e.Role)`, and has no `Extensions()` method at all: [3](#0-2) 

Because `Extensions()` is absent on `RoleNotPermittedError`, it does not satisfy gqlgen's extended-error interface the way `unauthorizedError` does, so the two error types produce structurally/textually distinguishable GraphQL responses (different message text, and likely a different/default error `code`, e.g. no `code` extension vs. `UNAUTHORIZED`). An attacker who already holds a valid session (any role, including the lowest `view` role) can call every edit/admin mutation and, from the response, learn: (1) that the mutation exists and requires a role above their own (via the distinct `RoleNotPermittedError` shape vs. session-invalid errors), and (2) their own exact role name echoed back — though the more significant leak is the systematic distinguishability itself, letting an attacker map which mutations require `run`, `edit`, or `admin` without needing to guess via side channels.

### Impact Explanation
This is an information-disclosure / reconnaissance issue, not a privilege-escalation or authentication-bypass bug: the underlying authorization decision (deny access) is enforced correctly in all three gate functions. Impact is limited to: (a) confirming the existence and required-role tier of privileged mutations, and (b) echoing the caller's own already-known role string back to them (not another user's role, since `session.User` refers to the caller's own session). This maps to Chainlink's "minor information disclosure" bounty class rather than a fund-movement, key-disclosure, or auth-bypass class impact.

### Likelihood Explanation
Trivially reachable by any authenticated user regardless of role — precondition is only "any authenticated session, any role" as stated in the question. An attacker with a `view`-role session can call any GraphQL mutation gated by `authenticateUserCanRun`/`authenticateUserCanEdit`/`authenticateUserIsAdmin` in `core/web/resolver/mutation.go` and observe the differing error text/shape versus what an unauthenticated (no-session) request returns. This requires no special network position or credential beyond a low-privilege login, making it fully repeatable.

### Recommendation
Make `RoleNotPermittedError` implement `Extensions()` returning a generic, non-role-leaking code (e.g., `"FORBIDDEN"`), and change `Error()` to return a generic message such as `"Not permitted with current role"` without interpolating `e.Role`, so the error surface matches `unauthorizedError`'s normalized shape and does not disclose per-mutation role requirements or the caller's role string in the message body.

### Proof of Concept
Add a resolver-level Go test in `core/web/resolver/auth_test.go` (or extend existing mutation tests, e.g. patterns used in `core/web/resolver/user_test.go`) that:
1. Constructs a GraphQL test client authenticated as a `view`-role user.
2. Calls a representative `edit`-gated mutation (e.g. one guarded by `authenticateUserCanEdit`) and a representative `admin`-gated mutation.
3. Asserts the returned error's `message` field equals a generic string with no role name interpolated, and asserts `extensions.code == "FORBIDDEN"` (not absent, not different from the `unauthorizedError` code shape).
4. Compares this against a request made with no session at all, asserting both paths now return the same normalized `code` value (only the message differs by "no session" vs "insufficient role" at most, with no role names or mutation-specific leakage). [3](#0-2) [2](#0-1)

// Authenticates the user from the session cookie and asserts at least 'run' role.
func authenticateUserCanRun(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role == sessions.UserRoleView {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'edit' role.
func authenticateUserCanEdit(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	switch session.User.Role {
	case sessions.UserRoleView, sessions.UserRoleRun:
		return RoleNotPermittedError{session.User.Role}
	default:
	}
	return nil
}

// Authenticates the user from the session cookie and asserts has 'admin' role
func authenticateUserIsAdmin(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role != sessions.UserRoleAdmin {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}
