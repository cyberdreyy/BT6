### Title
Signer Event-Receiver HTTP Endpoint Accepts Unauthenticated, Content-Type-Agnostic POSTs — Cross-Origin/Local Injection of Fabricated Block Validation Responses - ([File: libsigner/src/events.rs])

### Summary
The signer's local event-receiver HTTP server (`SignerEventReceiver`) — which is the exact functional analog of the go-sdk's Streamable HTTP transport in the advisory — accepts `POST` requests on `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` with **no authentication check, no `Content-Type` validation, and no `Origin` validation**. Any request body reaching this port is deserialized via `serde_json::from_slice` regardless of its declared content type or origin, and fed directly into the signer's state machine as a `SignerEvent`, including as a spoofed `BlockValidateResponse` for `/proposal_response`.

### Finding Description
`SignerEventReceiver::next_event` (`libsigner/src/events.rs:413-459`) dispatches based solely on URL path and HTTP method: [1](#0-0) 

`process_event` (`libsigner/src/events.rs:519-542`) reads the raw body and deserializes it as JSON with no check of the `Content-Type` header and no authentication/authorization of the sender: [2](#0-1) 

This is unlike the node-side `/v3/block_proposal` endpoint (`stackslib/src/net/api/postblock_proposal.rs:1128-1179`), which strictly requires a matching `Authorization` header and an exact `application/json` `Content-Type` before accepting a body: [3](#0-2) 

The signer's own inbound listener has no equivalent of either control. A successfully parsed `/proposal_response` body becomes `SignerEvent::BlockValidationResponse`, which is fed into `handle_event_match` → `handle_block_validate_response` (`stacks-signer/src/v0/signer.rs:511-518`), directly influencing the signer's block acceptance/rejection state: [4](#0-3) 

The signer runbook explicitly warns that the endpoint can be bound to a non-loopback address (`endpoint = "0.0.0.0:30000"` in `docs/signing.md`), and `SpawnedSigner::new` prints a runtime warning acknowledging the risk of exposing this port beyond a trusted local node: [5](#0-4) [6](#0-5) 

Because there is no per-request authentication (unlike `auth_token`/`Authorization` used on the node's `/v3/block_proposal` side) and no validation that the sender is the paired stacks-node, any process (browser via simple/CORS-safelisted cross-origin POST if reachable, or any local/network process able to reach the bound port) that can deliver a raw HTTP POST to this listener can inject a fabricated `BlockValidateResponse` (Ok or Reject) for an arbitrary `signer_signature_hash`, exactly mirroring the CVE's "arbitrary request reaches message handling without a CORS/auth barrier" pattern.

### Impact Explanation
An attacker who can reach the signer's event-receiver port (which per the sample/docs may be bound to `0.0.0.0`, or reachable cross-origin from a co-hosted browser context) can forge a `BlockValidateResponse::Ok` for a block hash of their choosing without that block ever having been legitimately validated by the paired stacks-node. This breaks the equality the signer relies upon — "block was validated by *my* node" vs. "a POST claiming validation arrived at my listener" — potentially causing the signer to treat an unvalidated/invalid block as validated and sign it (a signer signing an invalid/non-canonical block), or to spoof a `Reject` for a legitimately valid block, wedging the signer out of accepting a valid proposal (liveness impact). This satisfies the Critical/High impact bar in scope (signer signing on a forged validation result; liveness wedge from forged rejects).

### Likelihood Explanation
Likelihood depends on network exposure of the signer's `endpoint`. Where operators bind to `0.0.0.0` (documented as a supported configuration) or where the signer's listener is reachable from other same-host/co-tenant processes (or a browser via a CORS-safelisted cross-origin POST, per the advisory's bug class), no signing key, majority collusion, or `auth_token` is required — only network reachability to the bound port. This is a single-actor-triggerable analog, consistent with the "one-slot miner plus gossip" threat model in scope, since forging a `/proposal_response` requires no cooperation from other signers.

### Recommendation
- Require an authentication token/shared secret (mirroring the node's `auth_token`/`Authorization` scheme used for `/v3/block_proposal`) on all inbound signer event-receiver requests, validated in `next_event`/`process_event` before deserialization.
- Enforce and validate `Content-Type: application/json` strictly (reject anything else, matching the node-side handler's behavior) to close the CORS-safelisted `text/plain` bypass class described in the advisory.
- Optionally validate the sender's origin/source (e.g., restrict to loopback by default, and require explicit configuration + authentication to bind non-loopback).

### Proof of Concept
1. Configure a signer with `endpoint = "0.0.0.0:30000"` (a documented supported configuration) or otherwise ensure the signer's event port is reachable from the attacker's context.
2. Craft a raw HTTP POST to `http://<signer-host>:30000/proposal_response` with body:
```json
{
  "result": "Ok",
  "block": "<attacker-chosen serialized block/signature hash>",
  "cost": {"read_count":0,"read_length":0,"runtime":0,"write_count":0,"write_length":0},
  "size": 0
}
```
No `Authorization` header or specific `Content-Type` is required — `RPCBlockProposalRequestHandler`-style validation is absent here (contrast with `stackslib/src/net/api/postblock_proposal.rs:1136-1168`).
3. `SignerEventReceiver::next_event` (`libsigner/src/events.rs:439-440`) routes this to `process_event::<T, BlockValidateResponse>`, which deserializes it without any sender verification (`libsigner/src/events.rs:519-542`) and forwards it as `SignerEvent::BlockValidationResponse` into `handle_block_validate_response` (`stacks-signer/src/v0/signer.rs:511-518`), influencing the signer's block acceptance/rejection decision based on the forged response rather than a genuine validation performed by the paired stacks-node.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
