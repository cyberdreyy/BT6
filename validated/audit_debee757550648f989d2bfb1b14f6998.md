### Title
Withdraw-request interest is priced on current TVL but historical NAV, so mid-epoch deposits retroactively inflate earlier withdrawers' receipts - (File: contracts/IdleCDOEpochVariant.sol)

### Summary

`requestWithdraw` prices the epoch interest embedded in a withdraw receipt via `_calcInterestWithdrawRequest`, which multiplies a *historical* basis (`_lastSavedNAV(_tranche)`, fixed at the last epoch boundary) by interest computed on the *current* managed contract value (`_managedContractValue()`), which already includes mid-epoch deposits made after the NAV snapshot. This is the same bug class as the external report: a "current rate/state" value is applied where a historical rate belongs, so a user's entitlement for a period changes retroactively when unrelated deposits occur.

### Finding Description

In `contracts/IdleCDOEpochVariant.sol:856-878`:

```solidity
uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
uint256 _trancheBal = _lastSavedNAV(_tranche);
_interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
```

- Numerator: `_calcInterest(_managedContractValue())` uses live TVL, which grows with every mid-epoch deposit (`depositDuringEpoch`/`mintStrategyTokens` path mints shares at current price and adds `interest` to `expectedEpochInterest`, `IdleCDOEpochVariant.sol:721-732`).
- Denominator: `_trancheBal` is `lastNAVAA`/`lastNAVBB`, which is only refreshed at epoch boundaries and does **not** include the new deposit.

So the per-unit interest rate `totTrancheInterest / _trancheBal` increases whenever a deposit lands mid-epoch. A lender who calls `requestWithdraw` *after* a large deposit gets a bigger receipt (principal + inflated interest, minted as strategy tokens in `IdleCreditVault.requestWithdraw`, lines 272-294) than a lender who requested *before* the deposit — even though both were exposed for the same epoch. The deposited principal itself contributes zero to `_trancheBal`, so its interest share is redistributed to whoever requests a withdraw while the NAV snapshot is stale.

The parallel to the EYWA PoC is exact: there, a deposit changed the *past* votes; here, a deposit changes the interest embedded in withdraw receipts computed for the *current/past* epoch window, because live TVL is mixed with a stale NAV base.

### Impact Explanation

The inflated receipt is funded out of `expectedEpochInterest`/`pendingWithdraws` at `stopEpoch`. Since `pendingWithdraws` is funded before active tranche interest is distributed, every unit of excess interest captured by the withdrawer is a unit of yield not received by the LPs who remain active (including the mid-epoch depositor, whose deposit's interest is partially diverted). This is theft of unclaimed yield from other lenders, quantified roughly as:

`excess ≈ _amount * (trancheShare of APR interest on the new deposit) / lastNAV(_tranche)`

i.e. the withdrawer skims a pro-rata share of interest generated by capital that arrived after the NAV snapshot. With a large victim deposit relative to `lastNAV`, a withdrawer holding a big tranche position can capture a meaningful fraction of the new deposit's epoch interest. The attacker only needs to be a KYC-passed tranche holder and to order their `requestWithdraw` after a victim's mid-epoch deposit (e.g., via mempool observation during a running epoch).

### Likelihood Explanation

- Requires mid-epoch deposits to be enabled (the `depositDuringEpoch`/minted-interest mode exists precisely for this) and a running epoch — both normal operating conditions.
- The attacker must hold tranche tokens and be `isWalletAllowed`-KYC'd, which is a standard lender, in scope.
- No privileged misbehavior is required; the mispricing is deterministic given the ordering deposit → requestWithdraw.
- Caveat: severity scales with the ratio `newDeposit / lastNAV`; in pools where mid-epoch deposits are small or absent the effect is negligible. Also note the same stale/live mixing is reused by `writeOffDeposit` (borrower-only, out of scope) and `maxWithdrawable` (view only).

### Recommendation

Use a consistent basis in `_calcInterestWithdrawRequest`: either compute `totInterest` on the NAV snapshot that matches `_trancheBal` (e.g., `lastNAVAA + lastNAVBB` rather than `_managedContractValue()`), or accrue mid-epoch deposits into the saved NAV used for the ratio. The goal is that the interest rate embedded in a receipt depends only on state fixed at epoch start, so later deposits cannot change already-computable entitlements — the direct analog of "accurately account for past rate changes."

### Proof of Concept

Reproducible Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testRequestWithdrawInterestInflatedByMidEpochDeposit() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0); // no fees, isolate interest math

    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);   // attacker LP
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);                   // epoch running

    // Baseline: interest embedded in a receipt requested now
    uint256 principal = mintedAA * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;
    (uint256 interestBefore,) = _calcInterestForTranche(address(AAtranche), mintedAA);

    // Victim deposits mid-epoch (depositDuringEpoch / mintStrategyTokens path)
    address victim = makeAddr("victim");
    _depositWithUser(victim, amount, true);         // live TVL doubles, lastNAVAA unchanged

    // Attacker requests withdraw AFTER the deposit
    (uint256 interestAfter,) = _calcInterestForTranche(address(AAtranche), mintedAA);
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // Same epoch, same position, larger receipt purely because a deposit landed
    assertGt(interestAfter, interestBefore, "receipt interest inflated by later deposit");
    assertApproxEqAbs(interestAfter, 2 * interestBefore, 1e6, "interest roughly doubles");
}
```

Expected behavior mirrors the external PoC: `getPastVotes`-like value (here the receipt's embedded interest) changes after an unrelated deposit, when it should be fixed by the epoch-start rate/NAV. Note I could not fully verify within available iterations whether `_managedContractValue()` also includes other live components (e.g., `unclaimedFees`) that further skew the ratio, or whether prefunded/programmable variants override `_calcInterestWithdrawRequest`; a Devin session with full file access should confirm those details before finalizing the PoC.
