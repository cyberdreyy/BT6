### Title
Claimed instant-withdraw receipts are never cleared per-epoch, allowing a second payout from the default-recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` burns the user's aggregate instant receipt and zeroes `instantWithdrawsRequests[_user]`, but it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]` / the per-epoch markers that the default-recovery path relies on. The stale per-epoch ledger entry is the analog of the kernel memory leak in CVE-2022-3619 (state allocated for a processed object is never freed): the "consumed" receipt remains visible to `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` at `contracts/strategies/idle/IdleCreditVault.sol:842-855`.

### Finding Description
The funded-claim path clears only the aggregate mapping:

```solidity
// IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (set at line 371) and `instantWithdrawClaimsByEpoch[currentEpoch]` (line 372) are left populated. If the pool subsequently defaults in the same epoch while `pendingInstantWithdraws != 0` (i.e., other users' instant receipts were unfunded), `finalizeDefaultRecovery` sets `defaultInstantWithdrawsFinalized = true` (line 696) and `defaultRecoveryEpoch = epochNumber`. A later `claimInstantWithdrawRequest(_user)` call then executes `_claimDefaultedInstantWithdrawRequest`, which reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — still equal to the already-paid amount — computes `claimBasis`, and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve`.

The only repayment guard is `_burn(_user, claimBasis)` on the user's receipt-token balance. Because instant receipts are ordinary ERC20 strategy tokens (`_mint(_user, _amount)` at line 363), an attacker can satisfy the burn by holding enough strategy tokens from a separate position — e.g., a concurrent normal `requestWithdraw` receipt (minted at line 275), a `postDefaultRequests` receipt, or tokens received via transfer from another holder.

Additionally, even without a second claim, the stale `instantWithdrawClaimsByEpoch[epoch]` inflates `defaultPendingClaimBasis()` (lines 644-649), diluting `defaultRecoveryPrice` for all honest claimants.

### Impact Explanation
Direct theft of the default-recovery reserve: the attacker is paid a second time for a receipt already settled at par, draining `defaultRecoveryReserve` that is owed to other defaulted-epoch receipt holders and active LPs. The stolen amount is `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`, i.e., proportional to the attacker's already-claimed instant position — bounded only by how large an instant request they could fund pre-default. Every double-claimed unit is a direct loss to remaining claimants since recovery is a fixed pool.

### Likelihood Explanation
Requires a specific sequence but all unprivileged actions: (1) attacker requests an instant withdraw during an epoch where the APR drops (instant mode auto-triggers in `IdleCDOEpochVariant.requestWithdraw` when `lastEpochApr > currentApr + instantWithdrawAprDelta`); (2) epoch starts and the CDO funds the attacker's receipt via `collectInstantWithdrawFunds` while at least one other user's instant receipt stays unfunded (`pendingInstantWithdraws != 0`); (3) borrower defaults and `finalizeDefault` runs in the same `epochNumber`; (4) attacker calls `claimInstantWithdrawRequest` again holding enough strategy tokens to cover the burn. Steps 1-2 and 4 are normal user actions; step 3 is an honest-manager action. No malicious privileged role is needed.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch entries alongside the aggregate: zero `instantWithdrawsRequestsByEpoch[_user][epoch]` for the funding epoch (or iterate/track the request epoch per user, mirroring `lastWithdrawRequest`), and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. Alternatively, snapshot the funded epoch in a `lastInstantWithdrawRequest[_user]` marker and clear it on claim, as `_clearWithdrawClaimForEpoch` does for normal receipts.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (against a fork with instant-withdraw enabled pool)
function testInstantWithdrawDoubleClaim() external {
    // --- Epoch N running, APR drops so requestWithdraw routes to instant ---
    // attacker deposits, then requests withdraw -> requestInstantWithdraw mints receipt
    uint256 receipt = strategy.balanceOf(attacker);          // == instant amount
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epochN), receipt);

    // --- startEpoch: CDO funds attacker's receipt only ---
    // collectInstantWithdrawFunds(attackerAmount) -> pendingInstantWithdraws stays > 0 (victim unfunded)
    cdoEpoch.claimInstantWithdrawRequest(attacker);          // first claim: paid at par
    assertEq(strategy.instantWithdrawsRequests(attacker), 0);
    // BUG: per-epoch entry survives
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epochN), receipt);

    // --- borrower defaults, finalizeDefault in same epochNumber ---
    cdoEpoch.finalizeDefault(recovered, manager);            // honest manager
    assertTrue(strategy.defaultRecoveryFinalized());
    assertTrue(strategy.defaultInstantWithdrawsFinalized());

    // --- attacker holds strategy tokens from a separate normal withdraw receipt ---
    // (or receives them via ERC20 transfer) so _burn succeeds
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimInstantWithdrawRequest(attacker);          // second payout from reserve
    uint256 stolen = underlying.balanceOf(attacker) - balPre;
    assertEq(stolen, receipt * strategy.defaultRecoveryPrice() / strategy.RECOVERY_FULL());
}
```

Note: I was unable to fully verify within this pass whether the strategy token's `_transfer`/`_burn` hooks restrict receipt-token transfers or whether `claimInstantWithdrawRequest` on the CDO side applies additional gating (e.g., `allowInstantWithdraw` checks in `IdleCDOEpochVariant`). If strategy tokens are non-transferable, the attacker would instead need a second pending receipt of equal size in the same epoch to cover the burn; the stale-accounting inflation of `defaultPendingClaimBasis` (recovery dilution) remains unconditionally exploitable.
