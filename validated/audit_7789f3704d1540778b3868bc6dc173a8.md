### Title
`depositDuringEpoch` mints shares/strategy tokens and forwards the requested `_amount` instead of the actual received balance, so a fee-on-transfer underlying dilutes tranche holders and drains the difference to the borrower - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report describes accounting updated with *intended* amounts rather than the *actual* amounts an external transfer/mint settled for. `IdleCDOEpochVariant.depositDuringEpoch` has the same defect class: unlike the normal `_deposit` path, which computes shares from the post-transfer balance delta (`_contractTokenBalance(_token) - _preBal`), `depositDuringEpoch` uses the nominal `_amount` parameter for share minting, NAV accounting, strategy-token minting, and the onward transfer to the borrower. If the underlying token charges a transfer fee (e.g. USDT with fees enabled), the CDO books more assets than it received and pays the shortfall out of existing depositors' funds.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol` `depositDuringEpoch` (lines 656-733):

```solidity
_transferUnderlyingsFrom(msg.sender, address(this), _amount);   // line 685: actual received may be < _amount
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;  // line 724: priced on _amount
_mintShares(_tranche, msg.sender, _minted, _amount);            // line 725: NAV += _amount
IdleCreditVault(strategy).mintStrategyTokens(_amount);          // line 730: 1:1 strategy tokens for _amount
_transferUnderlyings(_borrower(), _amount);                     // line 732: sends full _amount out
```

Compare with `IdleCDOCreditVault._deposit` (lines 203-206) and `IdleCDO._deposit` (lines 250-253), which measure the real inflow:

```solidity
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
```

The discrepancy matters because `_transferUnderlyingsFrom` uses `safeTransferFrom` with no balance check, so a deflationary token delivers `_amount - fee`. The CDO then:

1. Credits the depositor's tranche NAV (`lastNAVAA`/`lastNAVBB`) by the full `_amount` via `_mintShares`.
2. Mints `_amount` strategy tokens via `IdleCreditVault.mintStrategyTokens`, inflating `getContractValue()` (which counts strategy-token balance 1:1).
3. Sends the full `_amount` to the borrower, funding the un-received fee portion from pre-existing contract balance (other depositors' idle buffer / uninstant-withdrawn cash).

No existing guard stops this: `_skimDonatedAssets` only removes *excess* balance, `_guarded` checks limits, and `_updateAccounting` runs before the transfer. The strategy's `mintStrategyTokens` trusts the CDO's amount blindly.

### Impact Explanation
Each mid-epoch deposit with a fee-charging underlying mints tranche shares worth `fee%` more than the capital actually contributed (unfair mint / share inflation) and simultaneously transfers `fee%` of `_amount` out of other users' funds to the borrower. The loss is `depositAmount * tokenFeeBps` per call and is repeatable; once forwarded to the borrower it is only recoverable through borrower repayment, so it is a direct, permanent loss to tranche holders. Broken invariant: fair mint/burn and NAV solvency.

### Likelihood Explanation
Requires the pool's underlying to charge or enable a transfer fee — e.g. USDT, whose fee switch is controlled by Tether and has been exercised historically, or any rebasing/FOT pool currency. It also requires the manager to run `startEpoch` (epoch must be running, `isEpochRunning && block.timestamp < epochEndDate`) and the attacker to pass `isWalletAllowed` KYC. Both are plausible operational conditions; the attacker needs only an ordinary allowed-depositor wallet calling `depositDuringEpoch` — the deposit is even self-funded, so the attacker recaptures most of the fee as over-minted shares, profiting at other holders' expense.

### Recommendation
Mirror the `_deposit` pattern: measure the actual received amount and use it for all downstream accounting.

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
// use _received (not _amount) in the _minted formula, _mintShares NAV update,
// mintStrategyTokens(_received), and _transferUnderlyings(_borrower(), _received)
```

Alternatively, explicitly document and enforce that only non-FOT underlyings are supported, consistent with the balance-delta pattern already used in `_deposit`.

### Proof of Concept
Foundry-style PoC (fork or mock a fee-on-transfer underlying with e.g. 1% fee):

```solidity
function testDepositDuringEpochFot() public {
    // setup: AA tranche initialized, epoch started, running, wallet KYC'd
    uint256 amount = 1_000_000e6; // USDT-like token, feeBps = 100

    fotToken.mint(attacker, amount);
    vm.prank(attacker);
    fotToken.approve(address(cdo), amount);

    uint256 balBefore = fotToken.balanceOf(address(cdo));
    uint256 navBefore = cdo.lastNAVAA();

    vm.prank(attacker);
    uint256 minted = cdo.depositDuringEpoch(amount, AATranche);

    // actual received is 99% of amount
    uint256 received = fotToken.balanceOf(address(cdo)) - balBefore;
    assertEq(received, amount * 99 / 100);

    // NAV and strategy tokens were credited the full amount -> over-mint
    assertEq(cdo.lastNAVAA() - navBefore, amount);          // books 100%
    assertEq(strategy.balanceOf(address(cdo)), amount);     // mints 100%

    // borrower received full amount, i.e. 1% came from other depositors' balance
    assertEq(fotToken.balanceOf(borrower), amount);

    // depositor's minted shares redeem for more than the capital contributed
    // (minted * priceAA > received), extracting value from existing LPs.
}
```

Expected: `received < amount` while NAV/strategy-token/borrower accounting all use `amount`, demonstrating both share inflation and an outflow exceeding the inflow.
