### Title
Multisig `confirm()` counts stale confirmations from deleted members, allowing execution below the live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
The bug report describes governance actions in veRAACToken relying on voting-power/authorization state that can become stale (during emergency states) yet is still counted toward decision thresholds. The same class of bug — an authorization tally (confirmations) that is not re-validated against the *current* set of authorized parties (members) — exists in this repository's multisig contracts. `DeleteMember`/`DeleteKey` only purges requests and confirmations *created by* the removed member, but leaves that member's confirmations on *other, still-pending* requests intact. Those stale confirmations still count toward `num_confirmations`, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` checks the threshold purely by counting entries in the `confirmations` set for a request: [1](#0-0) 

Confirmations are stored as plain strings (`member.to_string()`) with no re-validation that the confirming member is still part of `self.members` at confirm/execution time — only the *current* caller is checked via `current_member()`; prior confirmers are never re-checked.

When a member is removed via `DeleteMember`, `delete_member()` only cleans up requests/confirmations that member *originally created* (`r.member == member`), not confirmations that member cast on requests created by *other* members: [2](#0-1) 

The same gap exists in the legacy `multisig` contract's `DeleteKey` handling, which likewise only removes requests where `r.signer_pk == pk`, not confirmations that key gave elsewhere: [3](#0-2) 

Binding broken (as an equality): `confirmations counted toward num_confirmations` should equal `confirmations from members present in the current self.members set`. After a `DeleteMember`/`DeleteKey` execution, this equality is violated: a removed member's stale confirmation on an unrelated pending request remains counted.

### Impact Explanation
This falls under the explicitly in-scope "Critical" impact: *"a multisig request executed below threshold."* A request configured to require `K` confirmations from currently-authorized members can execute with only `K-1` (or fewer) live confirmations plus one or more confirmations from accounts that have since been removed as members (and whose access key/account authority has been revoked). This lets a request (e.g., `Transfer`, `AddKey`, `FunctionCall`) execute with less real authorization than the multisig's security model promises, directly compromising the custody guarantee of the K-of-N scheme.

### Likelihood Explanation
This requires only normal multisig operation, not a compromised key or foundation privilege:
1. A member confirms a pending request without pushing it over threshold (e.g., 1 of 2 needed).
2. Independently, that member is later removed via a legitimate `DeleteMember`/`DeleteKey` request (a routine membership-rotation action).
3. Any remaining member then confirms the still-pending request; the stale confirmation is still tallied, and the request executes despite only one live member having actually approved it in this instance.
No malicious code, redeploy, or key theft is required — merely ordinary sequencing of legitimate multisig actions (add request → partial confirm → remove that confirmer → complete confirm on the original request), so likelihood is meaningful in active multisigs with membership churn.

### Recommendation
When executing `DeleteMember` (or `DeleteKey` in the v1 contract), iterate over **all** pending requests' confirmation sets (not just requests originally created by that member) and strip the removed member's entry from each. Alternatively, when tallying confirmations in `confirm()`, filter the confirmations set against `self.members` (i.e., only count confirmations still held by current members) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 2`.
2. `A` calls `add_request` to create request `R1` (e.g., `Transfer` to an external account) — no confirmation yet.
3. `B` calls `confirm(R1)` — `confirmations[R1] = {B}` (1 of 2, not executed).
4. `A` and `C` create+confirm a `DeleteMember { member: B }` self-request; it executes, removing `B` from `members` and revoking B's key/account access. Per `delete_member()`, this only purges requests where `r.member == B` — `R1` was created by `A`, so it is untouched and `confirmations[R1]` still contains `B`.
5. `A` calls `confirm(R1)`. In `confirm()`, `confirmations.len() as u32 + 1 >= num_confirmations` evaluates `1 + 1 >= 2` → true, so `R1` executes with the `Transfer` action, even though only `A` (one live member) actually approved it after `B`'s removal — the threshold of 2 live-member confirmations was never truly met.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
