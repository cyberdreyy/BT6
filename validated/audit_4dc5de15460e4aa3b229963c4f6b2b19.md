## Title
Stale confirmations from removed multisig members are never purged from pending requests, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` implement a K-of-N confirmation scheme where a pending `MultiSigRequest` executes once `confirmations.len() + 1 >= num_confirmations`. When a member/key is removed via `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`), the removal logic only purges requests that member *created*, not confirmations that member cast on other still-pending requests created by someone else. That member's earlier confirmation therefore remains counted toward the threshold forever, even though the member is no longer part of the multisig, letting a request execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
In `confirm()`, a request executes as soon as the stored confirmation count reaches `num_confirmations`: [1](#0-0) 

The confirmations for a request are a `HashSet<String>` of member identifiers, stored independently of the current `members` set: [2](#0-1) 

When a member is removed, `delete_member` only removes *requests created by that member* and their confirmations. It does not scan `confirmations` for other requests that this member had already confirmed: [3](#0-2) 

The same pattern exists in the legacy `multisig` contract's `DeleteKey` handling inside `execute_request`, which likewise filters only by `r.signer_pk == pk` (the request creator) and ignores confirmer-only relationships: [4](#0-3) 

Consequently, a confirmation cast by a member while that member was still trusted continues to be counted as a valid vote toward `num_confirmations` on any request created by a different member, even after that member has been deleted from `members` (or, for `multisig`, has had its key deleted). This is the same class of bug as H-7 in the external report: the code that grants "confirmation" trust (cast while the signer was valid) is checked differently from the code that revokes membership (which only cleans up requests keyed by the departing member as creator), so a stale approval survives and is later combined with fresh approvals to cross the threshold — "confirmations counted versus live members" is broken.

### Impact Explanation
This allows a `MultiSigRequest` (e.g. `Transfer`, `FunctionCall`, `AddKey`/`AddMember`) to execute with strictly fewer live, currently-trusted-member confirmations than `num_confirmations` mandates, because one of the counted "confirmations" belongs to a member who has since been removed. This is a multisig request executed below threshold — funds (`Transfer`) can be moved, or a new full-access key/member can be added, by a set of live members smaller than the configured quorum. This falls squarely under the Critical impact category: "a multisig request executed below threshold."

### Likelihood Explanation
This requires no attacker key compromise beyond normal multisig operation: any legitimate member who confirms a request, and is subsequently removed for entirely unrelated reasons (rotation, compromise, off-boarding), leaves a "ghost" confirmation on any request they confirmed before their removal that has not yet reached the threshold or been separately deleted. Given `REQUEST_COOLDOWN` intentionally keeps requests alive for a period, and active-request limits allow multiple concurrent pending requests per member, this is a realistic and easily triggered situation in normal multisig lifecycle management, not a contrived edge case.

### Recommendation
When removing a member (`delete_member` in `multisig2`, `DeleteKey` handling in `multisig`), iterate over *all* pending requests' `confirmations` sets and remove the departing member's/key's entry from each, not just from requests the member created. Alternatively, re-validate at confirm-time / execute-time that every entry in a request's `confirmations` set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
Using `multisig2` semantics (analogous PoC applies to `multisig` with `DeleteKey`):
1. Initialize multisig with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R)` (R created by `A`, not by `B`). `confirmations(R) = {A}`.
3. `B` calls `confirm(R)`. `confirmations.len() = 1`, `1+1=2 < 3`, so `B` is added: `confirmations(R) = {A, B}`.
4. Separately, members legitimately execute a fully-confirmed `DeleteMember{member: B}` request. `delete_member` only scans requests created by `B` (there are none matching `R`, since `R.member == A`), so `confirmations(R) = {A, B}` is left untouched even though `B` is no longer a member.
5. `C` calls `confirm(R)`. `confirmations.len() = 2` (`{A, B}`), `2+1=3 >= num_confirmations(3)` → `R` executes.
6. `R` executed with only 2 confirmations from currently live members (`A`, `C`); `B`'s stale confirmation completed the quorum despite `B` having been removed, bypassing the intended 3-confirmation threshold among the now-3 live members (`A`, `C`, `D`).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
