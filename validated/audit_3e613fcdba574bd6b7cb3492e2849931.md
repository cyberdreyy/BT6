### Title
Fee-on-transfer underlying breaks the two-step deposit pull in `IdleCDOCreditVault._deposit` / `IdleCreditVault.deposit`, draining the CDO's withdrawal liquidity reserve - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault._deposit` correctly mints tranche shares based on the *actual* received amount (balance delta at lines 203–206), but then forwards the *nominal* `_amount` to `IIdleCDOStrategy(strategy).deposit(_amount)` at line 211. `IdleCreditVault.deposit` (contracts/strategies/idle/IdleCreditVault.sol:603–604) pulls the full `_amount` from the CDO via `safeTransferFrom` and mints `_amount` strategy tokens 1:1. With a fee-on-transfer underlying (e.g. USDT with its fee toggled on), the CDO only received `_amount - fee`, so the strategy's pull of `_amount` silently takes the missing `fee` from whatever other underlying the CDO holds — the liquid balance earmarked for pending withdrawal claims and funds returned by `sendInterestAndDeposits`. If no such reserve exists, deposits revert entirely.

### Finding Description
The external bug (nominal amount used for a second-hop transfer after a fee-on-transfer `transferFrom`) maps directly onto this codebase's two-hop deposit path:

1. User calls `depositAA(_amount)` → `_deposit` → `_transferUnderlyingsFrom(user, CDO, _amount)`. With a FoT token the CDO receives `_amount - f`.
2. `_mintSharesAtCurrPrice(balanceDelta, ...)` mints the user shares for `A - f` only — NAV accounting (`lastNAVxx += A - f`) stays internally consistent.
3. `IdleCreditVault.deposit(_amount)` then pulls the full `_amount` from the CDO and mints `_amount` strategy tokens.

Net effect per deposit: the strategy receives `A`, the user contributed `A - f`, and the extra `f` is extracted from the CDO's pre-existing `token` balance. `getContractValue()` (line 127) counts both strategy-token balance and raw `token` balance, so total NAV is unchanged — the loss is a *reallocation*: `f` moves out of the CDO's liquid reserve (which backs pending `claimWithdrawRequest`/`claimInstantWithdrawRequest` payouts and borrower repayments parked at the CDO) and into strategy-held NAV belonging to all tranche holders. Pending withdrawal claims become underfunded by `f` per deposit and their payout transactions revert on insufficient balance — temporary freezing of unclaimed yield/withdrawals, quantified as `f × n` deposits, up to the full liquid reserve. Alternatively, if the CDO holds no surplus, `strategy.deposit` reverts and deposits are bricked while the token fee is enabled.

The existing balance-delta mint (line 206) is exactly the half-fix the original report recommended; the second hop was not fixed. No skim or reserve check guards the discrepancy.

### Impact Explanation
Each deposit with a fee-bearing underlying extracts `fee` underlying from the CDO's liquid balance into the strategy, where it is attributed to NAV rather than to the depositor. This both underfunds pending withdrawal/instant-withdraw claims (freezing payouts until the borrower repays or the fee is disabled) and, when the depositor holds tranche shares, lets an attacker convert illiquid pending-claim liquidity into NAV they partially own. Loss per deposit equals the token's transfer fee; repeatability scales it to the entire CDO reserve.

### Likelihood Explanation
Requires the vault's `token` to charge transfer fees. USDT — a supported-style 6-decimal stablecoin underlying — can enable fees at any time via a Tether governance toggle, matching the external report's scenario. The attacker is an ordinary KYC'd lender depositing during a buffer/running epoch; no privileged role is needed. Severity is bounded by the fee magnitude and the reserve size, consistent with Medium.

### Recommendation
In `IdleCDOCreditVault._deposit`, forward the measured received amount to the strategy instead of the nominal amount: capture `uint256 received = _contractTokenBalance(_token) - _preBal` (already computed for minting) and call `IIdleCDOStrategy(strategy).deposit(received)`. Defense-in-depth: in `IdleCreditVault.deposit`, compute `balanceOf` delta after `safeTransferFrom` and mint strategy tokens for the actual received amount.

### Proof of Concept
Assumption (not fully re-verified in this pass): pending withdrawal payouts are funded from the CDO's `token` balance via `sendInterestAndDeposits`/claim paths, so draining that balance freezes claims.

```solidity
// test/foundry/FeeOnTransferDeposit.t.sol — fork test sketch
contract FoTUSDT is ERC20 {
    uint256 public feeBps = 30; // 0.3% toggleable like USDT
    function _transfer(address f, address t, uint256 a) internal override {
        uint256 fee = a * feeBps / 10_000;
        super._transfer(f, t, a - fee);
        super._transfer(f, feeSink, fee);
    }
}

function testDepositDrainsCdoReserve() public {
    // Setup: vault with FoT token; prior epoch leaves W underlying at the CDO
    // earmarked for pending withdraw claims (sendInterestAndDeposits already called).
    uint256 reserve = token.balanceOf(address(cdo));          // W backing pending claims
    uint256 depositAmt = 100_000e6;

    token.approve(address(cdo), depositAmt);
    uint256 minted = cdo.depositAA(depositAmt);               // user = attacker lender

    uint256 received = depositAmt - depositAmt * 30 / 10_000; // CDO received less
    // User minted shares only for `received`, but strategy holds `depositAmt`
    assertEq(strategyToken.balanceOf(address(cdo)), depositAmt);
    // The `fee` difference was pulled out of the withdrawal reserve
    assertEq(token.balanceOf(address(cdo)), reserve - (depositAmt - received));
    // A pending claim of `reserve` now reverts on insufficient balance
    vm.expectRevert();
    vault.claimWithdrawRequest(/* ... */);
}
```
