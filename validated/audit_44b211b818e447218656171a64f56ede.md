### Title
Client-supplied request ID containing the literal `::` owner separator is incorrectly stripped in `errorResponse` for pre-authorization errors, causing response ID to not match the original request ID - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`errorResponse` unconditionally looks for `vaulttypes.RequestIDSeparator` (`"::"`) anywhere in `req.ID` and strips everything up to and including it, assuming the ID was previously owner-prefixed by `authorizeAndStamp`. For error paths that occur *before* authorization/prefixing happens (e.g. `InvalidParamsError` from `vaultcap.IsInvalidVaultParamsError` in `HandleJSONRPCUserMessage`, or `UnsupportedMethodError`), the ID passed to `errorResponse` is still the raw, client-supplied ID that was never prefixed. If a client chooses an ID containing the literal `::` substring, the substring before it gets erroneously truncated off.

### Finding Description
The prefixing pipeline is in [1](#0-0) : `authorizeAndStamp` only sets `req.ID = authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` *after* `p.authorizer.AuthorizeRequest` succeeds. Validation errors returned earlier in `processCreateSecretsRequest`/`processUpdateSecretsRequest`/etc. (via `p.validationError(req, err)`) happen before `authorizeAndStamp` is ever invoked, so `req.ID` is still the unprefixed client value at that point [2](#0-1) .

Back in the gateway handler, `HandleJSONRPCUserMessage` calls `ProcessRequest(ctx, &req, cachedPublicKey)`; if it returns an `InvalidVaultParamsError`, it calls `sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)` with the still-unprefixed `req` [3](#0-2) , which in turn calls `h.errorResponse(req, errorCode, err, nil)` [4](#0-3) .

`errorResponse` then does:
```go
index := strings.Index(req.ID, vaulttypes.RequestIDSeparator)
if index != -1 {
    req.ID = req.ID[index+2:]
}
``` [5](#0-4) 

Since this code has no way to distinguish "an ID that was actually owner-prefixed by `authorizeAndStamp`" from "a client-chosen ID that merely happens to contain `::`", any client sending `ID = "a::b"` on a request that fails validation before authorization (e.g., malformed `SecretsCreate` params) will have the returned error envelope's `id` field become `"b"` instead of `"a::b"`, violating the JSON-RPC 2.0 requirement that response `id` match request `id`.

### Impact Explanation
This is a request/response correlation bug, not a privilege escalation or secret-disclosure issue. A client that uses `::` in its own chosen IDs will see error responses whose `id` does not match what it sent, potentially causing the client (or any client-side dispatcher keyed on exact ID match) to fail to correlate the error to the correct pending call, or to misattribute it to a different in-flight request if that literal truncated ID happens to collide with another concurrent request's ID. This does not expose secrets, bypass authorization, or allow cross-user access to another user's data — the mismatch only affects the ID label in the error's own response, sent back to the same client that made the request. This matches, at most, a minor/informational protocol-conformance bug rather than a security-impact class recognized by Chainlink's bounty program (no auth bypass, no key/secret exposure, no unauthorized action, no cross-user data leak).

### Likelihood Explanation
Trivial to trigger: any unprivileged caller can submit a `SecretsCreate`/`SecretsUpdate`/`SecretsDelete`/`SecretsList` request with a self-chosen ID containing `::` and invalid params (e.g., missing required fields) to hit `InvalidParamsError` before authorization runs, or hit `UnsupportedMethodError`/`UserMessageParseError` paths, all of which pass an unprefixed `req.ID` to `errorResponse`. No special role or credential is needed.

### Recommendation
Track whether the ID has actually been owner-prefixed (e.g., via a boolean/flag on the request or activeRequest, or by threading through the original client ID separately) instead of inferring prefixing from the presence of the separator substring in the ID text. Alternatively, always store/pass the pristine client-supplied ID alongside the internal prefixed ID and use the pristine one when building `errorResponse`/`sendSuccessResponse`, rather than attempting to parse it back out heuristically.

### Proof of Concept
Go table test in `core/services/gateway/handlers/vault/handler_test.go`:
1. Construct a `jsonrpc.Request[json.RawMessage]{ID: "a::b", Method: vaulttypes.MethodSecretsCreate, Params: <invalid/malformed params>}`.
2. Call `handler.HandleJSONRPCUserMessage` (or directly `h.errorResponse(req, api.InvalidParamsError, someErr, nil)` for a unit-level test) without ever going through `authorizeAndStamp`.
3. Decode the resulting `UserCallbackPayload.RawResponse` JSON-RPC error envelope and assert `resp.ID == "a::b"`.
4. Observe actual result is `resp.ID == "b"`, demonstrating the ID is mangled even though no owner-prefixing occurred, confirming the mismatch against the JSONRPC id-echo invariant.

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

func (h *handler) sendImmediateUserResponse(
	ctx context.Context,
	req jsonrpc.Request[json.RawMessage],
	callback gwhandlers.Callback,
	errorCode api.ErrorCode,
	err error,
) error {
	switch errorCode {
	case api.InvalidParamsError, api.UnsupportedMethodError, api.UserMessageParseError:
		h.metrics.requestUserError.Add(ctx, 1, metric.WithAttributes(
			attribute.String("don_id", h.donConfig.DonId),
		))
	default:
	}
	return callback.SendResponse(h.errorResponse(req, errorCode, err, nil))
}
