## Missing Beneficiary Validation Enables Operator‑Griefed Denial‑of‑Withdrawal in `staking_contract` and `delegation_pool` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`, `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
`staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` store an operator-supplied `new_beneficiary` address with no validation whatsoever, unlike the analogous `vesting::set_beneficiary`, which explicitly calls `assert_account_is_registered_for_apt(new_beneficiary)` before accepting the value. Because the unvalidated beneficiary address is later used as the recipient in a shared distribution loop that pays out **every** shareholder's unlocked stake in one transaction, an operator can set a "poison" beneficiary that makes the payout to itself revert — which aborts the whole `distribute` call and blocks all other stakers/delegators in the same pool from withdrawing their already-unlocked funds.

### Finding Description
`staking_contract::set_beneficiary_for_operator` [1](#0-0)  and `delegation_pool::set_beneficiary_for_operator` [2](#0-1)  both write `new_beneficiary` into storage without any check on the address. The comment even states "the operator does not need to be validated with respect to a staking pool", but no equivalent statement or check is made about `new_beneficiary` itself.

Contrast this with `vesting::set_beneficiary`, which explicitly guards against exactly this class of bug: [3](#0-2) 

The comment there is explicit about *why* the check exists: "so `distribute()` wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered."

That exact failure mode is reachable through `staking_contract::distribute_internal`, which iterates over *all* shareholders of the distribution pool and pays each one out in a single transaction, redirecting the operator's share to `beneficiary_for_operator(operator)`: [4](#0-3) 

`aptos_account::deposit_coins` will create an unregistered account automatically, but if the target address already exists and has disabled direct coin transfers (via `set_allow_direct_coin_transfers(account, false)`) while not being separately registered for `AptosCoin`, the deposit aborts: [5](#0-4) 

Because the `while (distribution_pool.shareholders_count() > 0)` loop processes recipients in a fixed order and only extracts/removes shares as it succeeds, an abort on the operator's (redirected) beneficiary payout reverts the entire `distribute`/`distribute_internal` call — including all other shareholders' payouts that would have preceded or followed it in that same transaction. The `delegation_pool` module's `BeneficiaryForOperator` is used identically for commission payout redirection, so it shares the same exposure.

The operator role itself is not a privileged/governance role — any staker can name any address (including one they control) as `operator` via `staking_contract::create_staking_contract`/`switch_operator`, or a delegation pool owner can call `delegation_pool::set_operator`. Thus a party who is only an operator (a role obtainable without any special privilege) can unilaterally set a beneficiary designed to revert on deposit.

### Impact Explanation
An operator (who does not own the underlying stake) can call `set_beneficiary_for_operator` with an address that:
1. Exists on-chain,
2. Has called `set_allow_direct_coin_transfers(false)`, and
3. Is not separately registered for `AptosCoin`.

Once set, every subsequent call to `staking_contract::distribute` / `distribute_internal` (also triggered internally from `switch_operator`, `update_commision`, and other flows) for that staking pool will abort, because the commission payout to the poisoned beneficiary always fails. This blocks distribution of the staker's own already-inactive/pending_inactive stake — funds that should be freely withdrawable — indefinitely, since `distribute_internal` processes all shareholders in one all-or-nothing transaction. This is a permanent, non-recoverable block on withdrawal rights (until/unless the malicious operator chooses to reset a valid beneficiary, which they have no incentive to do if griefing), matching the "Permanent lock or non-recoverable loss of claim rights in stake … flows" impact.

### Likelihood Explanation
No special privilege is required beyond being named `operator` — a role that is freely assignable and, in self-stake/self-operate setups or malicious-operator scenarios, can be held by an adversarial party from the outset. Setting a `DirectTransferConfig` to reject arbitrary transfers is a normal, permissionless user action, so constructing the poison beneficiary account requires no exceptional access.

### Recommendation
Add a check in both `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` mirroring `vesting::set_beneficiary`, e.g. `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` (and/or reject the zero address), before writing to `BeneficiaryForOperator`. Additionally, consider hardening `distribute_internal` so that a single failing recipient cannot block distribution to the rest of the shareholders (e.g., skip-and-retain-shares-on-failure semantics), independent of the beneficiary-address validation fix.

### Proof of Concept
1. Attacker/operator account `O` calls `aptos_account::set_allow_direct_coin_transfers(O, false)` and does not register for `AptosCoin`.
2. Staker `S` has an active `StakingContract`/delegation pool with operator `O` (or `O` self-delegates as its own operator).
3. `O` calls `staking_contract::set_beneficiary_for_operator(O, O)` (or any similarly configured address) — this succeeds with no validation per [6](#0-5) .
4. Once stake becomes `inactive`/`pending_inactive` and any party calls `staking_contract::distribute(S, O)`, `distribute_internal` reaches the loop at [4](#0-3)  and aborts on `aptos_account::deposit_coins(O's beneficiary, …)` per the guard in [7](#0-6) , reverting the whole transaction and leaving all withdrawable stake stuck.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
