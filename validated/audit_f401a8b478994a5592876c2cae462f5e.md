Loss-recovery price keyed under post-increment `epochNumber` while claims read the pre-increment request epoch, letting haircutted withdraw receipts claim at par and drain the reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analog of CVE-2024-9681 (a narrower-scoped cache entry overwriting/missing the broader parent entry): `IdleCreditVault.collectWithdrawFunds` stores a stop-epoch loss haircut under the **current** `epochNumber`, but `epochNumber` is incremented inside `deposit()` while `isEpochRunning()` is still true — i.e., during the same `stopEpoch` — so the haircut is written under epoch `N+1` while every affected receipt is looked up under its request epoch `N` via `lastWithdrawRequest`. The epoch-scoped entry misses its intended key, claims then fall through to the at-par path, and haircutted receipts are paid 1:1 from an underfunded reserve.

### Finding Description
Three pieces of state interact:

- `requestWithdraw` records the request epoch: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 260-294 of `contracts/strategies/idle/IdleCreditVault.sol`).
- `deposit()` bumps the epoch counter mid-`stopEpoch`: when called while `isEpochRunning()` is still true it does `epochNumber += 1` (lines 607-610).
- `collectWithdrawFunds(_amount)` computes the haircut on the aggregate `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (line 421).

In the normal `stopEpochWithDuration(_lossAmount)` flow, borrower repayments are pushed into the strategy via `deposit()` (incrementing `epochNumber` to `N+1`) before the CDO collects withdraw funds, so the haircut for receipts requested in epoch `N` is stored under key `N+1`.

On the claim side, `_claimLossAdjustedWithdrawRequest` resolves the loss epoch as `lossEpoch = lastWithdrawRequest[_user]` (= `N`) and reads `lossRecoveryPriceByEpoch[N]`, which is `0`, so it returns early without clearing anything (lines 789-801). Control reaches `_claimFundedWithdrawRequest`, whose only epoch gate is `epochNumber <= lastWithdrawRequest[_user]` — now `N+1 <= N` is false — so it pays `withdrawsRequests[_user]` **at par** (lines 319-349) even though only `pendingBasis * lossRecoveryPrice / RECOVERY_FULL` was ever collected into the strategy.

The same wrong key disables the guard in `requestWithdraw` (lines 263-271): `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` reads `0`, so new requests are not blocked and `lastWithdrawRequest` can be overwritten again, compounding the cross-epoch mix-up — exactly the "subdomain expiry bleeds over the parent entry" shape of the original bug.

### Impact Explanation
Broken invariant: one receipt, one correctly-priced payout; loss socialization. All receipts of the loss epoch redeem at 100% while the reserve holds only `pendingBasis * price`. Earlier claimers extract more than their haircut-adjusted entitlement; the reserve is exhausted and the remaining claimants' withdrawals are permanently unpayable (insolvency / effective theft of the shortfall, quantifiable as `pendingBasis * (1 - lossRecoveryPrice)`).

### Likelihood Explanation
Requires a `stopEpochWithDuration` with `_lossAmount > 0` while `pendingWithdraws > 0` — a real but not exotic event (partial borrower repayment at epoch end). It hinges on `deposit()` being invoked before `collectWithdrawFunds` inside the same stop, which matches the repay-then-collect ordering of the epoch flow; I could not fully confirm the exact call order inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` in this session, which is the main residual uncertainty. All involved roles are honest; the attacker is any unprivileged tranche holder with a pending withdraw request who claims early.

### Recommendation
Key the loss-recovery entry under the request epoch rather than the post-increment counter: store `lossRecoveryPriceByEpoch[epochNumber - 1]` (or capture the epoch before the deposit bump), and/or make `_claimLossAdjustedWithdrawRequest` resolve the loss epoch deterministically from the receipt's own epoch key rather than the mutable `lastWithdrawRequest` pointer. Additionally, revert in `collectWithdrawFunds` when `pendingBasis != 0` and the computed epoch key does not match any outstanding request epoch.

### Proof of Concept
Foundry fork sketch:

1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` (fixed-APR mode), whitelist two KYC'd LPs A and B.
2. `startEpoch()`; A and B `requestWithdraw` during epoch `N` → `lastWithdrawRequest[*] = N`, `pendingWithdraws = P`.
3. Manager calls `stopEpochWithDuration(loss)` with `0 < loss < P`; borrower repays partially → strategy `deposit()` runs while `isEpochRunning()` → `epochNumber = N+1`; then `collectWithdrawFunds(funded < P)` stores `lossRecoveryPriceByEpoch[N+1] = p < 1e18`.
4. A calls `claimWithdrawRequest`: `lossRecoveryPriceByEpoch[N] == 0` → loss path skipped; funded path pays A `P_A` at par.
5. B claims: receives `p*P_B` funded remainder at best, or reverts on insufficient balance once the reserve is drained.
6. Assert: `strategy underlying balance < outstanding funded claims`; `lossRecoveryPriceByEpoch[N] == 0` while `lossRecoveryPriceByEpoch[N+1] != 0` demonstrates the key mismatch.

If step 3's ordering instead collects before the epoch bump, the keys coincide and this finding collapses — that ordering should be confirmed against `stopEpoch`'s implementation before reporting.
