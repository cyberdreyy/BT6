### Title
Time-based staleness cutoff bypasses the node liveness check for cross-tenure signed conflicts, allowing a signer to sign two conflicting blocks at the same height (equivocation) - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The pre-commit → signature path in `stacks-signer/src/v0/signer.rs` guards against a signer double-signing at a given height by consulting `SignerDb::get_signed_conflicts` and then asking the node whether each conflict is still "live" (`conflict_still_blocks`). But this liveness re-verification is only performed for conflicts that are still *fresh* (`last_endorsed > freshness_cutoff`, where the cutoff is `now - tenure_last_block_proposal_timeout`, default 30s). A conflict that has merely aged past this local timeout is dropped from consideration with **no node query at all**, even for a conflicting block in a third tenure that the chainstate checks never look at. This substitutes a local wall-clock guess ("the earlier decision is stale, therefore dead") for the actual proof of liveness the design otherwise insists on, mirroring the reported bridge flaw where a locally-set unlock timer is trusted instead of verifying whether the underlying transaction proof still stands.

### Finding Description
`handle_block_pre_commit` in [1](#0-0)  computes `conflicts` via `get_signed_conflicts` (any block this signer signed or saw group-signed, at or above the proposed block's height, in *any* tenure), then only blocks the current signature if it finds a conflict that is simultaneously:
1. fresh (`last_endorsed > freshness_cutoff`), and
2. not covered by a standing reorg permit, and
3. still "live" per `conflict_still_blocks` (which asks the node whether the conflicting tenure's sortition is still canonical and whether the node's chain still reaches the conflicting block).

Immediately after, a second check at [2](#0-1)  only re-examines conflicts whose `consensus_hash` equals the *proposed block's own tenure* — it does not consider stale conflicts belonging to any other tenure.

The practical effect: a signed conflict from a *different* tenure that has simply aged past `tenure_last_block_proposal_timeout` (30s by default, see [3](#0-2)  and `get_tenure_last_block_info`'s freshness rule at [4](#0-3) ) is never checked against the node's actual canonical state before this signer signs a new, conflicting block at the same or higher height. The design doc itself calls out that this backstop exists precisely because `check_latest_block_in_tenure` "only ever looks at _one_ tenure ... so a signed sibling at the same height in a third tenure is invisible to it" [5](#0-4) , and explicitly states that only "staleness or node-derived death... clears a conflict" [6](#0-5)  — treating staleness alone as sufficient to clear a *third-tenure* conflict, without ever confirming node-derived death for it.

### Impact Explanation
If the earlier signed block's tenure is in fact still canonical and reachable on the node (e.g., the node or network was merely slow, or push/propagation of the earlier block was delayed beyond 30 seconds — well within realistic network variance), the signer will nonetheless sign a second, conflicting block at the same height once the local staleness clock expires. This is a genuine equivocation: the same signer places its signature over two blocks that cannot both be canonical at the same chain height, which is exactly the Critical-tier "a signer signing an invalid, non-canonical, or conflicting block" outcome called out in scope. If enough signers experience the same timing (all measuring staleness independently from their own `last_endorsed` clocks against the same `tenure_last_block_proposal_timeout` default), both blocks could separately accumulate the 70% signature weight required for the node to accept them, creating a fork/double-commit at the same height.

### Likelihood Explanation
No signer collusion or majority compromise is needed. A single miner (plus normal gossip propagation) can produce this race by: (1) getting a block signed in tenure A, (2) allowing normal network delay or a legitimate tenure boundary to intervene so that block A is not yet globally accepted/pushed by the time `tenure_last_block_proposal_timeout` elapses, and (3) proposing a conflicting block B in a different, still-canonical tenure at the same height. Honest signers, following the documented protocol exactly as written, will pre-commit and sign B once B's own pre-commit threshold is reached, because the stale A-conflict is dropped without a liveness check. The default timeout (30s) is short relative to realistic node/network delays and Bitcoin block timing, making the staleness window practically reachable during normal operation, not just under adversarial conditions.

### Recommendation
Do not use local `last_endorsed` age alone to exclude a cross-tenure conflict from consideration. Either (a) always run `conflict_still_blocks` (or an equivalent node-derived liveness check) for every returned conflict regardless of freshness, only using staleness as an optimization to skip the check when the underlying tenure is already known-dead from previously recorded state, or (b) extend the "own tenure" recheck at [2](#0-1)  to cover every tenure with a conflicting entry, not only the proposed block's own tenure, so a real node-tip check always gates the decision before an irreversible signature is produced.

### Proof of Concept
1. Configure default `tenure_last_block_proposal_timeout = 30s` (mainnet default, [3](#0-2) ).
2. Miner produces block A at height H in tenure X; signer set reaches pre-commit threshold and each signer sets `signed_self` (records `last_endorsed`), but delivery/push of A to the stacks node is delayed (e.g., node congestion, network partition) so A is not yet globally accepted.
3. Wait >30 seconds so `last_endorsed <= freshness_cutoff` for A in `get_signed_conflicts`, per the staleness math in [7](#0-6) .
4. Miner proposes conflicting block B at height H in tenure Y (Y ≠ X). B passes `check_latest_block_in_tenure` (which only inspects Y's own tenure history, not X), reaches pre-commit threshold.
5. In `handle_block_pre_commit`, `get_signed_conflicts` returns A as a conflict, but since `last_endorsed <= freshness_cutoff`, it fails the `find()` predicate at [8](#0-7)  and is never passed to `conflict_still_blocks`/node query. The second check only inspects same-tenure (Y) conflicts, so A (tenure X) is not caught there either.
6. The signer signs B, producing a signature over B even though A's tenure X may still be fully live/canonical on the node — an equivocating signature at the same height H.

    /// Get the last signed block from the given tenure if it has not timed out.
    /// Even globally accepted blocks are allowed to be timed out, as that
    /// triggers the signer to consult the Stacks node for the latest globally
    /// accepted block. This is needed to handle Bitcoin reorgs correctly.
    ///
    /// The timeout window is measured from the last time a signature actually covered the
    /// block: our own (`signed_self`) or the observed group/global acceptance
    /// (`signed_group`), whichever is later, matching how `get_signed_conflicts` measures
    /// endorsement freshness. `approved_time` is deliberately not used: it is stamped at
    /// pre-commit, which carries no signature, so it would close the window early. This also
    /// means a globally accepted block we never signed ourselves gets a full window from the
    /// time its acceptance was observed, rather than timing out instantly for lack of a
    /// timestamp.
    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
    }

Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
