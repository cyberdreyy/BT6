### Title
Attacker-controlled `RUNNER_TEMP_PROJECT_DIR` job variable overrides trusted `TmpProjectDir()` path used by `proxy-exec`, enabling path-controlled writes outside the build's temp dir - ([File: commands/helpers/proxy_exec.go])

### Summary
`ProxyExecCommand.Execute` resolves its working directory (`dst`) by first checking the OS environment variable `RUNNER_TEMP_PROJECT_DIR`, only falling back to the `--temp-dir` CLI flag that `shells.ProxyExecShell.GetConfiguration` computed from the trusted `info.Build.TmpProjectDir()`. Because `RUNNER_TEMP_PROJECT_DIR` is also the well-known internal job-variable key (`common/spec/variables.go:19`, `TempProjectDirVariableKey`) that gets exported into the job process environment, a pipeline author who defines a CI/CD variable with that same key can override the value the helper actually uses for `NewProxy`/`bootstrap`, decoupling it from the value the Runner computed and put on the trusted `--temp-dir` argument.

### Finding Description
`shells.ProxyExecShell.GetConfiguration` builds the proxy-exec command line using the Runner-computed, trusted path: [1](#0-0) 

`commands/helpers/proxy_exec.go`'s `Execute` then resolves `dst` with environment-variable precedence over the CLI flag it was just given: [2](#0-1) 

`RUNNER_TEMP_PROJECT_DIR` is the same key used elsewhere in the codebase as the canonical job-variable name for the build temp dir: [3](#0-2) 

Job variables (including any variable a pipeline author defines under a job's/`.gitlab-ci.yml` `variables:` block, or as an inline pipeline variable) are exported into the child process environment that runs the shell script and, transitively, the `gitlab-runner-helper proxy-exec` process spawned from it. Because `Variables.value()`/`Variables.Set()` resolve duplicate keys by taking the last-defined one, and predefined/internal variables are typically appended before user-supplied job variables, a job variable named `RUNNER_TEMP_PROJECT_DIR` set by the pipeline author can win and be the value actually present in `os.Getenv("RUNNER_TEMP_PROJECT_DIR")` inside the spawned helper process — independent of the `--temp-dir` value the shell layer computed from the trusted `Build.TmpProjectDir()`.

Since `Execute` prefers the environment variable, `dst` becomes attacker-controlled. That value flows into:
- `bootstrap(dst)`, which does `os.MkdirAll(dst, 0o777)` and then copies the running helper binary into `filepath.Join(dst, "gitlab-runner-helper")` via `os.CreateTemp(dst, "")` + `os.Rename` (`commands/helpers/proxy_exec.go:119-171`).
- `NewProxy(dst, ...)`, which opens a `store.Store` database rooted at `dst`.

Neither `Execute` nor `bootstrap` validates that `dst` still resides under the intended build/project temp root, so an attacker-supplied `RUNNER_TEMP_PROJECT_DIR` (e.g. an absolute path elsewhere in the container filesystem, or a path with `..` segments) redirects directory creation, database file creation, and the helper binary copy to that path instead of the sandboxed temp directory the Runner intended.

### Impact Explanation
Within the job's own execution context (container/shell), the attacker can force the Runner-helper's file operations (`MkdirAll`, temp-file creation, binary copy/rename, store DB creation) to target an arbitrary writable path of their choosing rather than the build-scoped temp directory. This breaks the "File operations must stay within intended build/cache/artifact roots" invariant. Depending on executor/container layout, this could let the pipeline author write/overwrite files in shared or unexpected locations (e.g. mounted volumes, other paths writable by the job's process) rather than being contained to the isolated per-build tmp directory, and it also causes the masking/store proxy (`addmask` store) — which underpins log-masking bookkeeping — to be initialized at an unintended location, potentially corrupting or misplacing masking state used to redact secrets in the trace.

### Likelihood Explanation
Precondition: `FF`/config enabling `IsProxyExec()` (proxy-exec mode) must be active for the build. Given that, an unprivileged pipeline author only needs to declare a job variable named `RUNNER_TEMP_PROJECT_DIR` in `.gitlab-ci.yml` or via pipeline/trigger variables — a standard, commonly available capability with no special privilege. No cluster/GitLab-admin compromise is required. The mechanism is fully within the attacker model described (job inputs controlled by a pipeline author).

### Recommendation
In `commands/helpers/proxy_exec.go`'s `Execute`, stop trusting the `RUNNER_TEMP_PROJECT_DIR` environment variable for path resolution; use only the `--temp-dir` CLI argument that the Runner controls and pass it explicitly rather than reading it back from the process environment (or, if the env var must remain for backward compatibility, validate that its value is byte-for-byte equal to the Runner-supplied `--temp-dir`, and reject/ignore mismatches). Additionally, canonicalize and validate `dst` (`filepath.Clean` + prefix check against the known build root) before use in `bootstrap` and `NewProxy`.

### Proof of Concept
Go test sketch for `commands/helpers`:
```go
func TestProxyExecCommand_EnvOverridesTempDirFlag(t *testing.T) {
    trusted := t.TempDir()
    attacker := t.TempDir() // simulate attacker-chosen path via job variable

    t.Setenv("RUNNER_TEMP_PROJECT_DIR", attacker)

    c := &ProxyExecCommand{TempDir: trusted}
    // Invoke the same dst-resolution logic as Execute():
    dst := os.Getenv("RUNNER_TEMP_PROJECT_DIR")
    if dst == "" {
        dst = c.TempDir
    }

    assert.Equal(t, attacker, dst, "attacker-controlled env var overrides Runner-trusted --temp-dir")
    assert.NotEqual(t, trusted, dst)
}
```
Expected assertion: `dst` resolves to the attacker-supplied `attacker` path rather than the Runner-computed `trusted` path passed via `--temp-dir`, confirming that a job-variable named `RUNNER_TEMP_PROJECT_DIR` can redirect `bootstrap`/`NewProxy` file operations away from the sandboxed build temp directory.

const TempProjectDirVariableKey = "RUNNER_TEMP_PROJECT_DIR"

// tmpFile will return a canonical temp file path by prepending the job
// variables Key with the value of `RUNNER_TEMP_PROJECT_DIR` (typically the
// build's temporary directory). The returned path must be further expanded
// by/for each shell that uses it.
func (b Variables) tmpFile(s string) string {
	return path.Join(b.Value(TempProjectDirVariableKey), s)
}
