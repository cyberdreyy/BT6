### Title
Post-default instant-withdraw receipts reuse the finalized default epoch bucket and drain the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` lacks the `defaultRecoveryFinalized` handling that `requestWithdraw` has. A receipt minted after `finalizeDefaultRecovery` is recorded under `instantWithdrawsRequestsByEpoch[user][epochNumber]`, where `epochNumber` still equals `defaultRecoveryEpoch`. On claim, `_claimDefaultedInstantWithdrawRequest` treats it as a defaulted-epoch receipt, pays it out of `defaultRecoveryReserve` at `defaultRecoveryPrice`, and decrements `defaultRecoveryReserve`, corrupting the reserve ledger and eventually freezing legitimate defaulted claims via underflow. This mirrors the kernel UAF-with-retry pattern: a stale (already-finalized, "freed") epoch slot is reused by a new request.

### Finding Description
- `requestWithdraw` explicitly branches on `defaultRecoveryFinalized` and routes post-default receipts into `postDefaultRequests` (IdleCreditVault.sol:247-257).
- `requestInstantWithdraw` performs no such check; it only calls `_ensureDefaultRecoveryInitialized`, which returns early once initialized (lines 356-375, 924-935).
- `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` and never bumps `epochNumber` afterward (line 693).
- A post-default instant request therefore writes into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` and `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` — slots that were already consumed by `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` during finalization (lines 644-649, 716-723).
- In `claimInstantWithdrawRequest`, `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` triggers `_claimDefaultedInstantWithdrawRequest`, which reads exactly that stale epoch bucket, reduces `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[defaultEpoch]`, burns the receipt, and pays `claimBasis * defaultRecoveryPrice` out of `defaultRecoveryReserve` (lines 380-393, 842-856).
- The reserve was sized at finalization only for the pre-existing basis (`reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, lines 685-691). New post-default claims draw from it without any new backing, so honest defaulted claimants hit `defaultRecoveryReserve -= _amount` underflow (line 915) and their recovery is permanently frozen.

### Impact Explanation
Unpriced claims are paid from an isolated, fixed-size recovery reserve. Either the attacker extracts payout at `defaultRecoveryPrice` (above zero, backed by honest claimants' recovery), or the reserve underflows and the remaining recovery funds are permanently locked (`_transferDefaultRecovery` reverts). Broken invariant: one receipt one payout / recovery-reserve isolation — the same epoch slot is claimed twice against a fixed reserve.

### Likelihood Explanation
Reachability depends on `IdleCDOEpochVariant.requestInstantWithdraw` still permitting instant requests while `defaulted()` / post-finalization (i.e., `allowInstantWithdrawRequest` and epoch-running gating not blocking). The strategy code itself — the layer responsible for recovery isolation — has no `defaultRecoveryFinalized` guard, in contrast to the explicitly guarded `requestWithdraw`, indicating the path was intended to be reachable or was overlooked. Even at `defaultRecoveryPrice` the payout is non-zero whenever any recovery was secured, so the drain is bounded only by the attacker's deposited liquidity.

### Recommendation
Add the same post-default branch to `requestInstantWithdraw` as in `requestWithdraw`: either revert when `defaultRecoveryFinalized` is set, or record the receipt in a fresh post-default bucket (e.g., `postDefaultRequests`-style accounting) instead of `instantWithdrawsRequestsByEpoch[user][epochNumber]`, so it cannot collide with `defaultRecoveryEpoch`.

### Proof of Concept

```solidity

// 2. During the allowed window A calls requestInstantWithdraw(X) -> epoch E receipt.
// 3. Borrower defaults; CDO calls _handleBorrowerDefault, then finalizeDefaultRecovery(R, source)

// 4. Attacker B (any KYC'd LP) deposits (if allowed post-default) or reuses balance and calls

// 5. B calls claimInstantWithdrawRequest -> _claimDefaultedInstantWithdrawRequest
//    pays Y * defaultRecoveryPrice / RECOVERY_FULL out of defaultRecoveryReserve.
// 6. Repeat with new requests until reserve is drained; A's subsequent
//    claimInstantWithdrawRequest reverts on `defaultRecoveryReserve -= amount` underflow.
// assert: B received un-backed recovery payout; A's legitimate defaulted claim is frozen.
```
