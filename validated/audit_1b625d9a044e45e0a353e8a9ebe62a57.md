### Title
Cheap repeated stale block proposals let a miner indefinitely suppress the `block_proposal_timeout` inactivity fallback, wedging signers against the prior miner - (File: `stacks-signer/src/chainstate/mod.rs`, `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionsView::check_proposal` in `stacks-signer/src/chainstate/v1.rs` decides whether the current sortition's miner should be marked `InvalidatedBeforeFirstBlock` (the safety-valve that lets signers fall back to signing blocks from the *previous* miner) purely by measuring elapsed time since `last_activity_time` versus `block_proposal_timeout`. [1](#0-0)  Separately, `SortitionData::check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs` refreshes that same `last_activity_time` whenever it sees *any* stale/conflicting/rejected block proposal for a tenure, as long as it arrives within `reorg_attempts_activity_timeout` of the last signed/pre-committed time. [2](#0-1) [3](#0-2)  A miner never has to produce a *valid* block to keep resetting this clock — a low-height/conflicting proposal that gets outright rejected still counts as "activity" and refreshes `last_activity_time`, exactly like GMX's `cooldownDuration` being refreshed by any cheap `_addLiquidity()` call regardless of intent.

### Finding Description
The equality being relied on by the signer set is: *"if the sortition winner has been silent for `block_proposal_timeout`, treat them as invalid and unblock the previous miner's ability to extend the tenure."* This is the exact mechanism documented in `sample/conf/signer/mainnet-signer-conf.toml`: `block_proposal_timeout_ms` is one of two required gates before a tenure-extend from the *previous* miner is accepted. [4](#0-3) 

`SortitionState::is_timed_out` computes `elapsed = now - last_activity`, where `last_activity` defaults to burn-block-receive time but is overridden by `SignerDb::get_last_activity_time` if set. [5](#0-4)  `last_activity_time` is written by `check_latest_block_in_tenure`, and crucially the write happens even when the proposal in question is *rejected* by the very next line (`return Ok(false)`):

```

and again for the pre-commit-conflict branch:
```
if is_fresh_pre_commit && block.header.chain_length <= info.block.header.chain_length {
    ...
    signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs());

``` [3](#0-2) 

Because `reorg_attempts_activity_timeout` defaults to 200s (`reorg_attempts_activity_timeout_ms = 200_000` default) [7](#0-6)  and `block_proposal_timeout` defaults to 120s (`block_proposal_timeout_ms = 120000`), [8](#0-7)  the activity window that resets the clock is wider than the timeout window that would otherwise mark the miner invalid. A single low-cost, guaranteed-to-be-rejected block proposal roughly every 120s (well within the 200s freshness window) is sufficient to keep re-arming `last_activity_time` and thereby prevent `elapsed > block_proposal_timeout` from ever becoming true in `is_timed_out`. [9](#0-8) 

This mirrors the GMX report precisely: a cheap, low-value action (`depositGlpETH` with 1 wei / here, a stale block proposal that is immediately rejected) is used solely to refresh a cooldown/activity timer and permanently block the alternate path (redeem / fallback-to-previous-miner) that depends on that timer expiring.

### Impact Explanation
If the current sortition's miner goes offline or stalls (equivocates, censors transactions, or is otherwise malicious) while continuing to broadcast cheap junk/rejected proposals for its own tenure, `SortitionMinerStatus` never transitions to `InvalidatedBeforeFirstBlock`, so signers never fall back and sign the previous miner's tenure-extend. This is a liveness wedge for block production driven entirely by the *current* one-slot miner's own broadcast, requiring no majority of signers and no key compromise — matching the "High: a signer wedged into never signing valid blocks" impact class.

### Likelihood Explanation
The action required (repeatedly broadcasting a stale/conflicting block proposal to a signer's block-proposal endpoint) is unauthenticated apart from the miner's own commitment for that sortition slot and is essentially free/cheap compared to producing a real, valid tenure — directly analogous to the sub-cent `depositGlpETH` calls in the GMX report. It requires only the current sortition-winning miner (a role any miner naturally holds once per won sortition) and no cooperation from other parties.

### Recommendation
Do not refresh `last_activity_time` (used to gate the `block_proposal_timeout` invalidation fallback) from proposals that are ultimately rejected/stale/conflicting. If "activity" credit is desired for legitimately slow-but-honest miners, bound it independently of the fallback-timeout window (e.g., require a validly-formed, non-conflicting, or actually-signed block to reset the clock), and ensure `reorg_attempts_activity_timeout` can never exceed `block_proposal_timeout`, closing the window in which cheap rejected proposals can outrun the invalidation check.

### Proof of Concept
1. Miner M wins the sortition for tenure T and never produces a fully valid, tip-confirming block.
2. Every ~110s (< `reorg_attempts_activity_timeout` = 200s, but before `block_proposal_timeout` = 120s would elapse without a reset), M broadcasts a trivially invalid/stale block proposal for tenure T (e.g., one with `chain_length` no higher than the last known block, or one conflicting with an existing pre-commit).
3. `SortitionData::check_latest_block_in_tenure` rejects the proposal (`Ok(false)`) but, per the freshness checks at `stacks-signer/src/chainstate/mod.rs:403-417` and `427-447`, calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` before returning.
4. On the next call to `SortitionsView::check_proposal`, `SortitionState::is_timed_out` computes `elapsed = now - last_activity` using the just-refreshed timestamp, which is always `< block_proposal_timeout`, so `miner_status` stays `Valid` and never becomes `InvalidatedBeforeFirstBlock`.
5. Because the gate at `stacks-signer/src/chainstate/v1.rs:301-315` only permits signing the previous miner's blocks once `cur_sortition.miner_status == InvalidatedBeforeFirstBlock`, the previous miner's tenure-extend is permanently rejected as long as M keeps sending its cheap junk proposals, wedging block production despite M contributing no valid chain progress.

impl SortitionState {
    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }

# How long to wait for the current sortition winner to propose a block
# before the signer marks that miner as inactive.
#
# When a new sortition happens, the signer gives the winning miner this
# much time to propose a block. If no proposal arrives, the signer marks
# the winner as InvalidatedBeforeFirstBlock. This is one of two gates
# that must be satisfied before the signer will accept a tenure extend
# from the PREVIOUS miner (the other gate is `tenure_idle_timeout_secs`).
#
# WARNING: Interacts with miner's `tenure_extend_wait_timeout_ms` (default 120_000ms).
# The miner waits `tenure_extend_wait_timeout_ms` before attempting to extend.
#
# If miner's value < this value:
#   Miner extends BEFORE signer invalidates the new winner -> REJECTED
# If miner's value >= this value:
#   Signer invalidates new winner first, then accepts extend -> OK
#
# Recommended: keep this <= miner's tenure_extend_wait_timeout_ms.
#
# Default: 120_000
# Units: milliseconds
# block_proposal_timeout_ms = 120000
