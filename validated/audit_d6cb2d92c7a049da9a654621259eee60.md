### Title
Missing workflow-ownership check in `capContr.ExecuteCapability` allows any run-role user to invoke arbitrary capabilities with forged workflow metadata - ([File: core/web/capability_controller.go])

### Summary
The dev-only `POST /v2/execute_capability` endpoint is protected only by `auth.RequiresRunRole`, a coarse role check that has no notion of "which workflow" the caller is authorized for. `CapabilityController.ExecuteCapability` takes a capability name and an attacker-supplied, opaque `CapabilityRequest` byte blob, looks up the capability from the global `capabilitiesRegistry`, and calls `Execute` directly with no validation that the request's embedded metadata (workflow ID/owner) matches the caller's identity.

### Finding Description
The route is registered as `authv2.POST("/execute_capability", auth.RequiresRunRole(capContr.ExecuteCapability))` [1](#0-0) , gated behind `build.IsDev()`. `RequiresRunRole` only checks `user.Role != clsessions.UserRoleView`, i.e., it enforces a global, per-node role (view/run/edit/admin) — there is no per-workflow scoping or "identity bound to workflow" concept anywhere in this authorization layer [2](#0-1) .

Inside the handler, `ExecuteCapability` binds `CapabilityRequestOuter{CapabilityName, CapabilityRequest []byte}` from the JSON body, resolves any capability by name via `capabilityRegistry.GetExecutable`, unmarshals the caller-supplied bytes into a `pb.CapabilityRequest` (which includes its own `Metadata`, e.g. workflow ID/owner fields), and calls `capability.Execute(ctx, capabilityRequest)` directly [3](#0-2) . There is no code anywhere in this function that cross-checks the authenticated `clsessions.User` against the capability's owning workflow, DON, or any ACL — the entire request-to-workflow binding (`CapabilityRequest.Metadata.WorkflowID`/`WorkflowOwner`) is attacker-controlled input coming straight from the HTTP body.

### Impact Explanation
Any credential with run-role (the lowest privileged role capable of triggering actions) can invoke any capability registered in the node's `CapabilitiesRegistry`, and can forge the workflow-identifying metadata inside `CapabilityRequest`, causing the capability to execute "as" an arbitrary victim workflow. This is an authorization-bypass / action-impersonation issue that could result in unauthorized capability execution outside of the caller's authorized workflow context (matches Chainlink's "role/authorization bypass" and "unauthorized job run" impact classes).

### Likelihood Explanation
Preconditions are only a run-role credential (not edit/admin) and a dev build (`build.IsDev()==true`, which is the default in CI/dev images per the question). No other secrets, network position, or elevated privileges are required, and the request is a single unauthenticated-relative-to-workflow HTTP POST, making this trivially repeatable.

### Recommendation
Add an explicit ownership/authorization check in `CapabilityController.ExecuteCapability` that validates the authenticated user (or, in production, the workflow-scoped credential) is authorized for the specific `WorkflowID`/`WorkflowOwner` embedded in the `CapabilityRequest.Metadata` before calling `capability.Execute`. Alternatively, restrict this endpoint entirely to loopback/internal callers and remove the ability to set workflow metadata externally, deriving it server-side from the authenticated identity instead of trusting client-supplied bytes.

### Proof of Concept
1. Register two capabilities/executables in the `CapabilitiesRegistry`, one associated with "workflow A" and one with "workflow B" (or a single capability whose `Execute` behavior depends on `CapabilityRequest.Metadata.WorkflowID`).
2. Authenticate as a run-role user "owner A".
3. `POST /v2/execute_capability` with `capabilityName` set to the capability and `capabilityRequest` bytes containing `Metadata.WorkflowID = "B"` (owner B's workflow).
4. Assert that `capContr.ExecuteCapability` executes the request successfully with no error/403, proving no ownership check exists between the authenticated run-role identity and the workflow ID embedded in the request — i.e., `capability.Execute` is invoked without any binding validation, confirmed by tracing `core/web/capability_controller.go` lines 44-60 where no user/workflow correlation code exists.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (cc *CapabilityController) ExecuteCapability(c *gin.Context) {
	body := c.Request.Body
	if body == nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("missing request body"))
		return
	}

	capabilityRegistry := cc.App.GetCapabilitiesRegistry()
	if capabilityRegistry == nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("capability registry not initialized"))
		return
	}
	var capabilityRequestOuter CapabilityRequestOuter
	if err := c.BindJSON(&capabilityRequestOuter); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	capability, err := capabilityRegistry.GetExecutable(c.Request.Context(), capabilityRequestOuter.CapabilityName)
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	capabilityRequest, err := pb.UnmarshalCapabilityRequest(capabilityRequestOuter.CapabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	resp, err := capability.Execute(c.Request.Context(), capabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	responseBytes, err := pb.MarshalCapabilityResponse(resp)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	c.JSON(http.StatusOK, gin.H{"capabilityResponse": responseBytes})
