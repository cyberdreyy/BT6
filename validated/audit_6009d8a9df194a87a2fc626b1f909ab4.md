### Title
Session lifetime bounded only by idle timeout, not absolute age, allowing indefinite session renewal via authenticated activity - (File: core/sessions/localauth/orm.go, core/sessions/localauth/reaper.go)

### Summary
The session validity check in `findValidSession` and the reaper's `deleteStaleSessions` both key exclusively off the `last_used` column, with no absolute cap tied to `created_at`. Any authenticated request that touches `AuthorizedUserWithSession` bumps `last_used`, so a session can be kept alive forever by making a request at least once per `SessionTimeout` interval (default 15m), well within the `SessionReaperExpiration` window (default 240h) which itself is also computed relative to `last_used`, not session creation time.

### Finding Description
`findValidSession` only checks `last_used + sessionDuration >= now()` [1](#0-0) , and `AuthorizedUserWithSession` calls `updateSessionLastUsed` on every successful authenticated request, resetting the idle clock [2](#0-1) . The background reaper (`sessionReaper.Work`) also deletes sessions using a threshold computed purely from `last_used` (`SessionReaperExpiration` before `SessionTimeout` before now) [3](#0-2) , with no reference to `created_at` anywhere in the schema check. Consequently, there is no absolute session lifetime enforced anywhere in this authentication path — as long as a request is made at least once per `SessionTimeout` window, the session (and its `last_used`) is perpetually refreshed and the reaper's stale threshold is perpetually pushed forward, so the session never gets deleted regardless of how old it actually is.

However, I was unable to confirm the specific claim tying this to `UpdateRole` in `core/web/user_controller.go`. That handler modifies another user's role via `AuthenticationProvider().UpdateRole`, which explicitly purges all sessions belonging to the target user (`DELETE FROM sessions WHERE email = lower($1)`) [4](#0-3)  — it does not touch or refresh the *caller's own* session's `last_used`, and it forbids acting on one's own account (`sessionUser.Email == request.Email` is rejected) [5](#0-4) . The `last_used` bump comes from the generic `AuthenticateBySession` middleware (`AuthorizedUserWithSession`) that runs on *every* authenticated request regardless of which specific handler is hit [6](#0-5) , not specifically from `UpdateRole`. I could not verify from the available index which role level (`view`, `edit`, `admin`) is actually required to reach `/v2/users` `UpdateRole`, `/v2/user/password`, or `/v2/user/tokens`, because I was unable to load `core/web/router.go` route definitions before running out of investigation budget — this is necessary to confirm whether a 'view'-role user can even reach `UpdateRole` (which conventionally requires admin privileges in Chainlink) or only the self-service password/token endpoints.

### Impact Explanation
If confirmed, the underlying issue (idle-only expiry with no absolute cap) means a compromised or shared session credential (cookie or, separately, an API token subject to its own `UserAPITokenDuration`) can be kept alive indefinitely by an attacker who can issue any authenticated request roughly every `SessionTimeout` interval, regardless of the total elapsed time since login. This matches a "stale session past expiry" weakness, but the severity depends heavily on what role is required for the specific endpoints named (`UpdateRole`, password change, API token create/delete) — a low-privilege 'view' user renewing their own low-privilege session does not, by itself, grant escalation to admin. The Critical "node takeover" framing in the question presumes the attacker either already holds an admin session (in which case this is about persistence of stolen admin credentials, not escalation) or that `UpdateRole`/token endpoints are reachable by 'view'-role users, which is inconsistent with the `RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` wrappers defined in `core/web/auth/auth.go` [7](#0-6) .

### Likelihood Explanation
Not conclusively determinable without the router configuration confirming the role requirement per route. General idle-based-only session renewal is present in the code, but I cannot confirm this specific question's framing (a 'view' user reaching `UpdateRole` to renew a session and escalate to admin) is accurate given the visible admin/edit/run role gating and the fact `UpdateRole` purges the target's own sessions rather than refreshing the caller's.

### Recommendation
N/A — pending confirmation of route role requirements, this may not be a distinct vulnerability separate from the general idle-timeout-only session model already present in `localauth.orm`/`reaper.go`. If the general idle-only-expiry model is considered undesirable, an absolute lifetime cap keyed off `created_at` (independent of `last_used` renewal) would need to be added to `findValidSession` and `deleteStaleSessions`.

func (o *orm) AuthorizedUserWithSession(ctx context.Context, sessionID string) (user sessions.User, err error) {
	if len(sessionID) == 0 {
		return sessions.User{}, sessions.ErrEmptySessionID
	}

	email, err := o.findValidSession(ctx, sessionID)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	user, err = o.findUser(ctx, email)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	if err := o.updateSessionLastUsed(ctx, sessionID); err != nil {
		return sessions.User{}, err
	}

	return user, nil
}

func (sr *sessionReaper) Work(ctx context.Context) {
	recordCreationStaleThreshold := sr.config.SessionReaperExpiration().Before(
		sr.config.SessionTimeout().Before(time.Now()))
	err := sr.deleteStaleSessions(ctx, recordCreationStaleThreshold)
	if err != nil {
		sr.lggr.Error("unable to reap stale sessions: ", err)
	}
}

// DeleteStaleSessions deletes all sessions before the passed time.
func (sr *sessionReaper) deleteStaleSessions(ctx context.Context, before time.Time) error {
	_, err := sr.ds.ExecContext(ctx, "DELETE FROM sessions WHERE last_used < $1", before)
	return err
}
