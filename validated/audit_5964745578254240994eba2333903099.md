## Title
Stale confirmations from removed multisig members remain counted toward the confirmation threshold, allowing requests to execute below the required number of live signers - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

## Summary
When a multisig member (account or access key) is removed via `DeleteMember`/`DeleteKey`, the contract only purges *requests originally submitted by* that member. It does not scan and strip that member's *confirmations* recorded on other members' still-pending requests. Those stale confirmations remain in the `confirmations` set and continue to count toward `num_confirmations` when a later, still-valid member confirms the same request — letting a request execute with fewer currently-authorized signers than the configured threshold.

## Finding Description
`confirm()` compares the size of the stored confirmation set against `num_confirmations` without re-validating that every confirmer is still a current member: [1](#0-0) 

Membership removal (`delete_member`) only cleans up requests that were *added* by the removed member, and removes that member's `num_requests_pk` bookkeeping entry — it never walks other requests' `confirmations` sets to strip out entries belonging to the removed member: [2](#0-1) 

The same pattern exists in the v1 contract's `DeleteKey` action, which likewise filters only on `r.signer_pk == pk` (the request's original submitter) before removing associated requests, leaving that key's confirmations on *other* requests untouched: [3](#0-2) 

`assert_valid_request` (called from `confirm`) only checks that the *caller* is currently a member; it performs no validation over previously recorded confirmers: [4](#0-3) 

This breaks the intended custody binding: the number of confirmations *recorded* for a request should always equal the number of *currently authorized, live* members who confirmed it. Once a confirming member is removed, that equality is silently violated because the stale entry is never purged from requests it confirmed but did not submit.

## Impact Explanation
A request can be executed by `Promise`-driven actions (`Transfer`, `FunctionCall`, `AddKey`, `AddMember`, `DeleteMember`, etc.) once `confirmations.len() + 1 >= num_confirmations`. If one of the recorded confirmers has since been removed from the multisig, the effective number of currently-valid confirmers backing that execution is strictly less than `num_confirmations`. This is a multisig request executed below the intended threshold — e.g., a 2-of-3 multisig could end up executing a fund transfer or key/permission change with only 1 live, current signer's real consent, because a stale confirmation from a removed member is still counted.

## Likelihood Explanation
This requires only ordinary, legitimate multisig usage, no malicious collusion or external privilege beyond being one of the multisig's own members:
1. Member confirms a pending request (but not enough to trigger execution yet).
2. That member is later removed for any unrelated, legitimate reason (key rotation, member churn) via a separate, correctly-confirmed `DeleteMember`/`DeleteKey` request.
3. The original pending request is never touched by the removal logic (because it wasn't submitted by the removed member).
4. A remaining member confirms the still-pending request, and the stale confirmation is added to the live count, triggering execution below the true current threshold.

This is a realistic operational sequence for any long-lived multisig account with member turnover, not a contrived edge case.

## Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate over all `confirmations` entries (not just requests submitted by that member) and strip the removed member's entry from every request's confirmation set. Alternatively, when counting confirmations in `confirm()`, re-validate that each entry in the stored `confirmations` set still corresponds to a current member of `self.members` before counting it toward `num_confirmations`.

## Proof of Concept
1. Deploy multisig with `num_confirmations = 2`, members `{A, B, C}`.
2. `B` calls `add_request(R1)` (a `Transfer` request) — confirmations for `R1` = `{}`.
3. `A` calls `confirm(R1)` — confirmations for `R1` = `{A}` (1 < 2, not executed): [5](#0-4) 
4. `B` and `C` jointly confirm a separate `DeleteMember{member: A}` request (2 confirmations, legitimate operation) — `A` is removed from `self.members`; only requests submitted by `A` are purged, `R1` (submitted by `B`) is untouched: [2](#0-1) 
5. `C` calls `confirm(R1)` — `confirmations.len() (1, stale from A) + 1 >= 2` → `R1` executes, transferring funds, even though only `C` (one live member) actually authorized it at execution time. [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
