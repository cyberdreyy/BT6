### Title
Unverified NFT selection in `_withdraw` lets any tranche holder steal other users' PoLido claim NFTs - (File: contracts/IdleCDOPoLidoVariant.sol)

### Summary
`IdleCDOPoLidoVariant._withdraw` burns the caller's tranche tokens and then transfers the *last* PoLido NFT owned by the contract to the caller, without verifying that this NFT is the one minted by the caller's own `requestWithdraw` or that its MATIC value matches the redeemed amount. This is the same bug class as the reported `_withdrawNfts()` flaw: a withdrawal path transfers an asset from a pool without checking that the asset belongs to the withdrawer. Because deposits are permissionless, an attacker who burns a dust amount of tranche tokens can walk away with an NFT representing a much larger unstaking claim.

### Finding Description
In `IdleCDOPoLidoVariant._withdraw` (contracts/IdleCDOPoLidoVariant.sol:40-79):

- `toRedeem` is computed from the caller's burned tranche amount (`_liquidate` is invoked on that amount, which calls `stMatic.requestWithdraw` and mints a new PoLido NFT to this contract).
- The NFT to hand out is then selected as `tokenIds[tokenIds.length - 1]` from `poLidoNFT.getOwnedTokens(address(this))`, and transferred to `msg.sender` via `safeTransferFrom` — with no check that the NFT's claim amount equals `toRedeem` or that it was minted in this transaction.

The code itself acknowledges the assumption (`// NOTE: assume last token is the one we just minted` in `IdlePoLidoStrategy._redeem`, contracts/strategies/lido/IdlePoLidoStrategy.sol:133-135). ERC721Enumerable `getOwnedTokens` ordering is index-based, not mint-order-based: when a token is transferred out, `removeTokenFromOwnerEnumeration` swaps the *last* element into the removed slot. So "last" is not stable — an NFT minted earlier (from a previous withdrawal whose NFT was left in the contract, or from a direct `safeTransferFrom` donation of a PoLido NFT to the CDO) can end up as the last element.

Attack sequence (requires only a KYC-passed lender, no privileged role):
1. A pre-existing large PoLido NFT sits in the CDO contract (e.g., an NFT donated via `safeTransferFrom` — the contract accepts arbitrary ERC721s via `onERC721Received` — or a leftover from a failed/partial unstake flow).
2. Attacker deposits a dust amount via `depositAA`/`depositBB`, then calls `withdraw` for a tiny amount.
3. `_liquidate(toRedeem)` requests an unstake of only `toRedeem` MATIC, but `tokenIds[last]` resolves to the large NFT, which is transferred to the attacker.
4. Attacker claims the full stMATIC value from the PoLido contract — far exceeding their burned principal, draining value belonging to other LPs.

The broken invariant is "one receipt one payout" / fair burn: the payout asset is decoupled from the caller's entitlement. No existing guard stops this — `_checkDefault`, `_updateAccounting` and NAV accounting only track `toRedeem`, not which NFT leaves.

### Impact Explanation
Direct theft: the attacker receives a PoLido NFT redeemable for more MATIC than the underlying they burned. All value held by the contract in the form of PoLido NFTs (including donated or leftover claims, which the contract logic itself creates by sending the "last" NFT each time) can be extracted with dust deposits, at the expense of the remaining tranche holders whose NAV is debited by `lastNAVAA -= toRedeem`/`lastNAVBB -= toRedeem` while the real asset outflow is larger.

### Likelihood Explanation
Any unprivileged user can trigger it with a minimal deposit; the only precondition is that the contract holds at least one PoLido NFT whose claim exceeds the attacker's `toRedeem` — trivially satisfiable by NFT enumeration-order effects or a donation (NFTs sent to the contract are fully recoverable value in this design, analogous to the idle underlying handled by `_skimDonatedAssets` elsewhere).

### Recommendation
Verify ownership/correspondence before transferring: capture `tokenIds` length (or the tokenId returned by the unstake request) before calling `_liquidate`, require `getMaticFromTokenId(tokenId)` ≈ `toRedeem`, or compute `toRedeem` *from* the specific NFT being transferred rather than picking `tokenIds[last]` blindly. Follow Checks-Effects-Interactions as in the original report.

### Proof of Concept
Foundry fork test sketch (Polygon fork, stMATIC/PoLido live):

```solidity
function testStealPoLidoNFT() public {
    // seed: contract ends up holding a large NFT (e.g. donor safeTransfers a 1000-MATIC claim)
    vm.prank(donor);
    poLidoNFT.safeTransferFrom(donor, address(cdoPoLido), bigTokenId);

    // attacker deposits dust and withdraws
    uint256 dust = 1e6; // tiny stMATIC amount
    deal(STMATIC, attacker, dust);
    vm.startPrank(attacker);
    stm .approve(address(cdoPoLido), dust);
    cdoPoLido.depositAA(dust);
    cdoPoLido.withdrawAA(dust); // burns dust tranche tokens
    vm.stopPrank();

    // attacker now owns the large NFT instead of a dust-sized claim
    assertEq(poLidoNFT.ownerOf(bigTokenId), attacker);
    assertGt(stMatic.getMaticFromTokenId(bigTokenId), dust * 100);
}
```

Caveat: `IdleCDOPoLidoVariant`/`IdlePoLidoStrategy` are Polygon/stMATIC-era contracts and may be considered legacy relative to the `IdleCreditVault` credit-vault surface; if the program's scope excludes them, no equally direct NFT-withdrawal analog exists — `IdleCreditVault`'s receipt accounting (`withdrawsRequestsByEpoch`, `apr0Users`, `postDefaultRequests`) is consistently keyed by `_user` and cleared before payout, so the same missing-ownership pattern does not hold there.
