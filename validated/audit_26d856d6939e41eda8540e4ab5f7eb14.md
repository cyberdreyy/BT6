### Title
Accrued-but-undistributed yield and `unclaimedFees` are repriced and re-routed under new fee parameters by `setFeeParams()` — (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.setFeeParams()` updates `fee` (performance fee), `feeSplit`, `feeReceiver`, and `managementFee` in a single call while only checkpointing the management fee via `_accrueManagementFee()`. The performance-fee-bearing gain accumulated in `unclaimedFees`/`lastNAV` since the last accounting is not checkpointed, so on the next `_updateAccounting()`/`_depositFees()`/`stopEpoch()` the entire pending gain is charged at the new `fee` and split to the new `feeReceiver` at the new `feeSplit` — exactly the "pending fees distributed under updated rates" bug class of `updateFeeType()`.

### Finding Description
- `_updateAccounting()` computes the performance fee on *all* gain since the last checkpoint using the *current* `fee`: `unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC` [1](#0-0) .
- `setFeeParams()` snapshots only the management fee (`_accrueManagementFee()`) before overwriting `fee`, `feeSplit`, `managementFee` and `feeReceiver`, leaving the pending performance-fee-bearing gain uncheckpointed [2](#0-1) .
- Distribution happens later against the *new* routing params: `_transferFeeUnderlyings`/`_feeReceiverAmount` split the whole `unclaimedFees` balance at the current `feeSplit` to the current `feeReceiver` [3](#0-2) , and in the epoch variant `stopEpoch` splits accrued `unclaimedFees` plus `pendingWithdrawFees` (computed under old rates at `requestWithdraw` time) using the new `feeSplit`/`feeReceiver` [4](#0-3) .
- `_depositFees()` likewise mints AA shares for `unclaimedFees` to whatever `feeReceiver` is set at harvest time [5](#0-4) .
- The asymmetry is telling: the code already checkpoints `managementFee` before update (`_accrueManagementFee()` at line 466) but performs no equivalent checkpoint for the performance `fee`, `feeSplit`, or `feeReceiver`, so pending yield accrued under the old parameters is re-priced and re-routed under the new ones.

### Impact Explanation
If `fee` is raised mid-interval, tranche holders pay the higher rate on yield that accrued while the lower rate was promised — direct overcharge of user yield, crystallized into `unclaimedFees` at the next deposit/withdraw/`stopEpoch` (in `IdleCDOEpochVariant`, `_updateAccounting` may not run for an entire epoch, so a whole epoch's gain is repriced). If `feeSplit`/`feeReceiver` change, all previously accrued `unclaimedFees` and `pendingWithdrawFees` are delivered to the new receiver/split rather than the one in effect at accrual, permanently diverting accrued fees. Loss is bounded by `(newFee - oldFee) * pendingGain / FULL_ALLOC` for users and `unclaimedFees * ΔfeeSplit / FULL_ALLOC` for the routing error — material when NAV gain is large.

### Likelihood Explanation
Fee-parameter updates are routine operations (the factory task `tasks/cdo-factory.js` calls `setFeeParams` post-deployment to reconcile config drift), and in the epoch variant the interval between `_updateAccounting` checkpoints spans a full running epoch, so any `setFeeParams` call during a running epoch reprices the entire epoch's pending gain. No privileged malice is required — an honest owner's normal parameter update triggers the mispricing; unprivileged users trigger the (mis-)distribution via the next deposit/withdraw or epoch stop.

### Recommendation
In `setFeeParams()`, call `_updateAccounting()` (or at minimum settle `unclaimedFees`/`pendingWithdrawFees` under the old `fee`/`feeSplit`/`feeReceiver`) before overwriting the parameters, mirroring how `_accrueManagementFee()` already checkpoints `managementFee`. Alternatively snapshot the receiver/split applicable to each accrued fee bucket.

### Proof of Concept
Foundry fork test against the repo's existing harness (`test/foundry/IdleCreditVault.t.sol` patterns):

```solidity
function testPendingFeesRepricedBySetFeeParams() external {
    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);          // seed NAV
    _transferBurnedTrancheTokens(address(this), true);

    _setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, 0); // 10% perf fee, all to feeReceiver

    // accrue pending gain (e.g. harvest bumping strategy price, or epoch interest)
    vm.prank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setApr(initialProvidedApr);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.warp(cdoEpoch.epochEndDate());

    // owner raises fee to 50% and reroutes split mid-epoch (honest update)
    address newReceiver = makeAddr("newReceiver");
    _setFeeParams(newReceiver, 50_000, 50_000, 0);

    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // entire epoch gain was charged at 50% instead of the 10% in force during accrual,
    // and the accrued balance was split 50/50 to newReceiver instead of 100% to TL_MULTISIG
    uint256 gain = cdoEpoch.lastEpochInterest(); // net of overcharged fees
    assertLt(gain, expectedNetAt10pct);          // users overcharged on pending gain
    assertGt(IERC20Detailed(defaultUnderlying).balanceOf(newReceiver), 0); // rerouted fees
}
```

Assertions: (1) `unclaimedFees` after `stopEpoch` reflects `newFee` applied to gain accrued under `oldFee`; (2) the pre-update accrued fee balance is delivered to `newReceiver`/`newFeeSplit` rather than the recipients in force at accrual time.

  function setFeeParams(address _feeReceiver, uint256 _fee, uint256 _feeSplit, uint256 _managementFee) external {
    _checkOnlyOwner();
    _checkAmountTooHigh(_fee > MAX_FEE || _feeSplit > FULL_ALLOC || _managementFee > MAX_FEE / 10);
    _checkIs0((feeReceiver = _feeReceiver) == address(0));

    _accrueManagementFee();
    fee = _fee;
    feeSplit = _feeSplit;
    managementFee = _managementFee;
  }

  function _transferFeeUnderlyings(uint256 _amount) internal {
    uint256 feeReceiverAmount = _feeReceiverAmount(_amount);
    _transferUnderlyings(feeReceiver, feeReceiverAmount);
    _transferUnderlyings(owner(), _amount - feeReceiverAmount);
  }

  /// @notice calculates the amount to transfer to feeReceiver based on the feeSplit
  /// @dev `setFeeParams` guarantees a nonzero receiver; a zero split naturally returns zero.
  /// @param _amount total fee amount to split
  function _feeReceiverAmount(uint256 _amount) internal view returns (uint256) {
    return _amount * feeSplit / FULL_ALLOC;
  }
