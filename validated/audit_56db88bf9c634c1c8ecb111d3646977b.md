## Title
Unprivileged front-running of deterministic lockup address lets an attacker squat a victim owner's lockup with attacker-chosen terms - (File: `lockup-factory/src/lib.rs`)

## Summary
`LockupFactory::create` derives the lockup account id purely from `owner_account_id` via `hex::encode(&env::sha256(owner_account_id.as_bytes())[..20])`, and is callable by any account that attaches `MIN_ATTACHED_BALANCE`, with no check that the caller is the owner, the grantor, or the foundation, and no check that the derived account does not already exist. An attacker can therefore call `create` first for a victim's `owner_account_id` with attacker-chosen `lockup_duration`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`, permanently occupying the address the legitimate grantor would later target.

## Finding Description
The broken binding is: `terms(lockup_account_id) == terms_chosen_by(owner_account_id's_grantor)`. This holds only if the grantor is the first (and only) party able to deploy to `lockup_account_id`.

`create` computes the address deterministically and unconditionally: [1](#0-0) 

There is no `assert_called_by_foundation`, no `assert_eq!(env::predecessor_account_id(), owner_account_id)`, and no pre-check that `lockup_account_id` is unoccupied - the only guard is the deposit-size assertion: [2](#0-1) 

The promise batch then unconditionally does `create_account().deploy_contract(...).transfer(...).function_call("new", LockupArgs{...})` using whatever `lockup_duration`, `vesting_schedule`, `release_duration`, `whitelist_account_id` the caller supplied: [3](#0-2) 

Exploit flow:
1. Attacker learns/guesses the victim's future `owner_account_id` (the intended lockup beneficiary) before the real grantor calls `create`.
2. Attacker calls `create(owner_account_id = victim, lockup_duration = <attacker-chosen>, vesting_schedule = <attacker-chosen or None>, release_duration = <attacker-chosen>, whitelist_account_id = <attacker-controlled pool>)` with `MIN_ATTACHED_BALANCE`. `create_account()` on NEAR succeeds because the account does not yet exist, so attacker's version deploys first at `hex::encode(sha256(victim)[..20]).<factory>`.
3. When the legitimate grantor later calls `create` with the same `owner_account_id`, it computes the identical `lockup_account_id` and `Promise::new(lockup_account_id).create_account()` fails (account already exists), so the whole promise batch fails.
4. `on_lockup_create` sees `is_promise_success() == false` and simply refunds the legitimate caller's deposit; it does not detect or report that the address is squatted: [4](#0-3) 
5. The victim's canonical lockup address now permanently hosts attacker-chosen `lockup_duration`, `vesting_schedule`/`release_duration`, and `staking_pool_whitelist_account_id` (e.g. pointing at an attacker-controlled staking pool as the "whitelisted" delegation target), while `owner_account_id` in the deployed lockup is still the real victim account (attacker must pass the victim's account id to get the desired collision address). The protocol/UI, expecting terms chosen by the grantor, instead treats attacker-parameterised terms as authoritative.

None of the existing guards (`assert_self`, `is_promise_success`, `assert_one_yocto`, etc.) address this, because they only govern the callback bookkeeping, not who may initiate `create` or whether the target address is already taken.

## Impact Explanation
Funds subsequently sent to fund the lockup (attached deposit plus any later foundation/grantor top-up attempts, and NEAR eventually delegated per the attacker-chosen `whitelist_account_id`) are governed by lockup terms the victim's rightful grantor never chose - matching the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." Since the whitelist/staking pool is attacker-controlled, delegated NEAR can be routed through a pool the attacker fully controls, and the real vesting/lockup schedule intended for the victim is replaced, which can also enable early release (short/zero `lockup_duration`, no `vesting_schedule`) or permanent freezing (excessive duration), and the legitimate deposit gets refunded to the grantor instead of funding the real lockup - a denial of the intended vesting/lockup for that owner account entirely. This is repeatable against every distinct `owner_account_id` that has not yet had its lockup created, i.e., against any future grant.

## Likelihood Explanation
The only precondition is attaching `MIN_ATTACHED_BALANCE` (3.5 NEAR) and knowing/predicting the target `owner_account_id` before the legitimate grantor calls `create` for it - both are realistic (grant recipients are often publicly known in advance, e.g. team/investor account names, or the attacker can race a public mempool transaction). No privileged role, key, or contract ownership is required; this is directly callable by the "unprivileged attacker" persona defined in scope.

## Recommendation
Restrict `create` so that the derived `lockup_account_id` can only be deployed once for a given `owner_account_id` under authorized control, e.g.:
- Require `env::predecessor_account_id() == owner_account_id` or `== foundation_account_id`, so only the owner or the foundation can create a lockup for that owner, and/or
- Have `on_lockup_create`/`create` detect an already-existing target account before attempting creation and reject/refund immediately with a clear "lockup already exists for this owner" error rather than silently allowing whichever caller wins the race to fix the terms.

## Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module (near-sdk testing_env)
#[test]
fn test_attacker_squats_victim_lockup_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker-chosen malicious terms
    let attacker_duration: WrappedTimestamp = 0u64.into(); // e.g. zero lockup duration
    let attacker_whitelist = Some(custom_whitelist_account_id()); // attacker-controlled pool

    // 1. Attacker calls create() for the *victim's* owner_account_id first.
    context.predecessor_account_id = String::from("attacker"); // NOT account_tokens_owner()
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // victim's owner_account_id -> derives victim's address
        attacker_duration,
        None,
        None,
        None,
        attacker_whitelist,
    );
    // Assert: no panic occurred -- attacker is not the owner and is not
    // rejected, proving predecessor is never checked against owner_account_id.

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(lockup_account(), ntoy(30).into(), String::from("attacker"));
    // lockup_account() (deterministic from owner_account_id) is now deployed
    // with attacker's terms.

    // 2. Legitimate grantor later tries to create the *real* lockup for the same owner.
    const LEGIT_DURATION: u64 = 63036000000000000; // 24 months, the intended real term
    let legit_duration: WrappedTimestamp = LEGIT_DURATION.into();
    context.predecessor_account_id = String::from("legit_grantor");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), legit_duration, None, None, None, None);
    // Same lockup_account_id is computed (assert equality with step 1's target).

    // Simulate NEAR runtime rejecting create_account() on an already-existing account.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from("legit_grantor"),
    );

    // Legitimate creation fails and deposit is refunded to legit_grantor,
    // while the address permanently retains attacker's terms (zero duration,
    // attacker-controlled whitelist) instead of the grantor's intended 24-month term.
    assert_eq!(res, false);
}
```
This demonstrates: (a) `create` never validates `predecessor_account_id` against `owner_account_id` or any privileged role, (b) the address is derived solely from `owner_account_id` and thus is identical and predictable for both attacker and legitimate calls, and (c) the second (legitimate) call fails and refunds while the first (attacker) call's terms remain live at the victim's canonical lockup address - proving the terms-authority invariant is broken.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
