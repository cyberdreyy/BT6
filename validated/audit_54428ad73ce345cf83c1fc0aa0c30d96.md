### Title
Default finalization undercounts the claim basis by only reading current-epoch instant receipts, inflating `defaultRecoveryPrice` and permanently freezing late claimants' recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — i.e., only receipts recorded under the *current* epoch — whenever `pendingInstantWithdraws != 0`. But `pendingInstantWithdraws` is an aggregate that also includes instant-withdraw receipts created in *earlier* epochs that were never fully funded by `collectInstantWithdrawFunds`. Those stale-epoch receipts are real outstanding claims yet are excluded from `totalBasis` in `finalizeDefaultRecovery`, so `recoveryPrice = reserve / totalBasis` is computed against a too-small denominator. Early claimants are overpaid; once the reserve is exhausted, later `_claimDefaultedWithdrawRequest` / `_claimPostDefaultWithdrawRequest` calls revert on `defaultRecoveryReserve -= _amount` underflow, permanently freezing their recovery.

### Finding Description
The bug class of CVE-2020-27845 is an out-of-bounds/stale-index read: untrusted input drives a read at an index outside the intended range. The analog lives in the epoch-indexed claim accounting:

- `requestInstantWithdraw` records receipts under the *current* `epochNumber` (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) and bumps the aggregate `pendingInstantWithdraws`. [1](#0-0) 
- `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` when the CDO fronts cash, but never touches the per-epoch mappings. A partially funded instant queue leaves `pendingInstantWithdraws > 0` while `instantWithdrawClaimsByEpoch[oldEpoch]` keeps the stale basis. [2](#0-1) 
- At finalization, `defaultPendingClaimBasis` reads only `instantWithdrawClaimsByEpoch[epochNumber]` (the default epoch), so any unfunded instant receipt from a prior epoch contributes to `pendingInstantWithdraws != 0` (which gates `defaultInstantWithdrawsFinalized`) but is missing from `basis`. [3](#0-2) 
- `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` with `totalBasis` missing the stale-epoch instant claims. [4](#0-3) 
- `_defaultPrefundedInstantReserve` makes the same single-epoch assumption: it treats `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as already-held backing, which can revert via underflow (`instantBasis < pendingInstant` is guarded, but an old-epoch claim inflates `pendingInstant` beyond the current basis, silently reducing `prefundedReserve` to 0 and understating `reserveAmount` is *not* the failure — the failure is the *basis* side). Net effect: `totalBasis` is understated → `recoveryPrice` overstated. [5](#0-4) 

Additionally, the old-epoch instant receipt itself is never claimable through `_claimDefaultedInstantWithdrawRequest` (it only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`), and its par claim via `claimInstantWithdrawRequest` → `_transferFundedClaim` is blocked by the reserve guard — yet it was never counted as a liability. [6](#0-5) 

### Impact Explanation
The reserve is sized for `totalBasis` claims at `recoveryPrice`, but the real claim set is larger. Every defaulted-epoch claimant and post-default claimant draws `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` (`_transferDefaultRecovery`). Because the price is inflated by the missing basis, the reserve drains early; subsequent claims hit `defaultRecoveryReserve -= _amount` underflow and revert permanently — direct theft by early claimants plus permanent freezing of the remaining recovery. The stale instant receipt holder's own funds are also permanently frozen (claim path reverts on the reserve guard since no non-reserve balance was ever funded for them). [7](#0-6) 

### Likelihood Explanation
Requires only unprivileged sequencing: an attacker (or any lender) calls `requestInstantWithdraw` in epoch N; the epoch's instant funding is only partially collected by the honest manager/CDO flow (e.g., borrower liquidity shortfall, or `getInstantWithdrawFunds` covering less than the queue), leaving `pendingInstantWithdraws > 0` into epoch N+1. A borrower default then triggers `finalizeDefaultRecovery`. No privileged misbehavior is needed — partial instant funding and borrower default are both honest-role events. The payout-order race favors whoever claims first, including the attacker holding a defaulted-epoch receipt.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, account for all outstanding instant claims, not just `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., track a global `totalInstantClaimBasis` incremented on request and decremented on claim, or iterate/track epochs with nonzero instant claims. Symmetrically, `_claimDefaultedInstantWithdrawRequest` should clear a user's full `instantWithdrawsRequests[_user]` basis (all epochs) at the recovery price, not only the default-epoch slice, so every unfunded instant receipt is both counted in the basis and paid at the same haircut.

### Proof of Concept
Foundry fork sketch:

```solidity
// Epoch N: attacker (or any user) requests instant withdraw of X.
cdo.requestInstantWithdraw(X, user) // via IdleCDO; pendingInstantWithdraws = X, claimsByEpoch[N] = X

// Honest flow only partially funds instant queue: collectInstantWithdrawFunds(k), k < X
// => pendingInstantWithdraws = X - k > 0, claimsByEpoch[N] still = X

// Epoch N+1 starts (manager.startEpoch), other users request normal withdraws (basis P)
// Borrower defaults; guardian/owner finalize:
strategy.finalizeDefaultRecovery(recovered, source)
// totalBasis = activeBasis + pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]  (== 0!)
// The X-k unfunded instant basis is missing => defaultRecoveryPrice too high.

// First defaulted-epoch claimant drains reserve:
cdo.claimWithdrawRequest(userA) // paid inflated amount from reserve
// Later claimant / post-default claimant reverts:
vm.expectRevert(); // underflow on defaultRecoveryReserve
cdo.claimWithdrawRequest(userB)
```

Key assertions: `strategy.pendingInstantWithdraws() > 0` at finalization while `strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()) == 0`; `defaultRecoveryPrice * trueTotalBasis > reserveAmount * 1e18`; final claim reverts.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
