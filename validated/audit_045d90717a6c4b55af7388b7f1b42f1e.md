### Title
Unauthenticated `InitializeBuffer` allows frontrunning to hijack buffer authority and drain lamports via `Close` - ([File: programs/bpf_loader/src/lib.rs])

### Summary
The `UpgradeableLoaderInstruction::InitializeBuffer` handler in `process_loader_upgradeable_instruction` sets the buffer account's `authority_address` from whatever pubkey is supplied as instruction account 1, without requiring that account (or the buffer account itself) to be a signer. Any account that is merely `Uninitialized` and owned by `bpf_loader_upgradeable` can be claimed by an attacker who races the legitimate owner's `InitializeBuffer` transaction. This is structurally the same bug class as the reported `prepareCondition` issue: a permissionless, first-writer-wins initialization step that sets critical authority/state and can be frontrun between account creation and initialization.

### Finding Description
`InitializeBuffer` only checks that the target account's current state is `Uninitialized`, then unconditionally records instruction account 1's key as the new buffer authority: [1](#0-0) 

No signature is required from the buffer account (index 0) or from the new authority (index 1). Compare this to `SetAuthorityChecked`, which explicitly requires the present authority and new authority to sign: [2](#0-1) 

Buffer accounts are typically created by a `CreateAccount` (or similarly funded) instruction in one transaction, then initialized by a follow-up `InitializeBuffer` call, exactly the same two-step pattern the external report describes for `prepareCondition`/pricing setup. Once a buffer account exists on-chain (funded, owned by `bpf_loader_upgradeable`, data all-zero i.e. `Uninitialized`), it is publicly visible, and an attacker can submit their own `InitializeBuffer` instruction naming themselves as `authority_address` before the legitimate owner's initialize transaction lands (via mempool observation, priority fee, or reorg). Because `payoutNumerators`/state-setting in the original bug and `authority_address` here are both "only settable once, first caller wins, no signature required," the race condition is directly analogous.

Once the attacker becomes the recorded authority, they can later call `Close`, which properly checks that the *stored* `authority_address` signs — but since the stored value is the attacker's own key, this check passes trivially: [3](#0-2) [4](#0-3) 

This lets the attacker sweep all lamports funded into the victim's buffer account to a recipient address of their choosing.

### Impact Explanation
This results in concrete unsigned/unauthorized fund movement: an attacker can steal the lamports deposited into a buffer account intended for legitimate program deployment, by hijacking its authority through a race condition and later draining it via a signature check that is satisfied only because the attacker corrupted the initial authority. It also enables denial-of-service against program deployment pipelines (the legitimate deployer's later `Write`/`DeployWithMaxDataLen` calls will fail with `IncorrectAuthority` since the stored authority no longer matches theirs).

### Likelihood Explanation
Likelihood is moderate: it requires monitoring the mempool/chain for `CreateAccount` transactions that create loader-owned, uninitialized buffer accounts and winning a race (via priority fee, colocated leader, or short-window reorg) to submit `InitializeBuffer` before the legitimate follow-up transaction. This is a realistic MEV/frontrunning scenario reachable by any unprivileged transaction sender, matching the exact bug class (frontrunning corrupting a permissionless initialization step) described in the external report.

### Recommendation
Require that `InitializeBuffer`'s account 0 (the buffer being initialized) is a signer, so only the party that controls the buffer's own keypair (i.e., the one who created it) can initialize it — mirroring the signature requirements already present in `SetAuthorityChecked` and `common_close_account`. Alternatively, require the buffer account to have been created in the same transaction/atomic sequence as its `InitializeBuffer` call, and reject standalone `InitializeBuffer` calls on accounts not freshly created in the same instruction set.

### Proof of Concept
1. Victim submits a transaction: `SystemInstruction::CreateAccount` to create `buffer_pubkey` (funded, owned by `bpf_loader_upgradeable`, `Uninitialized` state), signed by the victim's ephemeral buffer keypair and payer.
2. Victim intends to follow up with `UpgradeableLoaderInstruction::InitializeBuffer` naming themself (`victim_authority`) as buffer authority, but this second transaction has not yet landed.
3. Attacker observes the on-chain `buffer_pubkey` (now `Uninitialized`, owned by loader, funded) and submits their own transaction calling `InitializeBuffer` with account 0 = `buffer_pubkey`, account 1 = `attacker_pubkey`, per `programs/bpf_loader/src/lib.rs:158-172` — no signature is required for either account, and the instruction succeeds because state is still `Uninitialized`.
4. Victim's original `InitializeBuffer` transaction now fails with `InstructionError::AccountAlreadyInitialized` (state check at line 162-165).
5. Attacker calls `UpgradeableLoaderInstruction::Close` (`programs/bpf_loader/src/lib.rs:686-716`, `common_close_account` at 1003-1027), signing with `attacker_pubkey` as authority, and receives all lamports that were funded into `buffer_pubkey`. [1](#0-0) [3](#0-2)

fn common_close_account(
    authority_address: &Option<Pubkey>,
    instruction_context: &InstructionContext,
    log_collector: &Option<Rc<RefCell<LogCollector>>>,
) -> Result<(), InstructionError> {
    if authority_address.is_none() {
        ic_logger_msg!(log_collector, "Account is immutable");
        return Err(InstructionError::Immutable);
    }
    if *authority_address != Some(*instruction_context.get_key_of_instruction_account(2)?) {
        ic_logger_msg!(log_collector, "Incorrect authority provided");
        return Err(InstructionError::IncorrectAuthority);
    }
    if !instruction_context.is_instruction_account_signer(2)? {
        ic_logger_msg!(log_collector, "Authority did not sign");
        return Err(InstructionError::MissingRequiredSignature);
    }

    let mut close_account = instruction_context.try_borrow_instruction_account(0)?;
    let mut recipient_account = instruction_context.try_borrow_instruction_account(1)?;

    recipient_account.checked_add_lamports(close_account.get_lamports())?;
    close_account.set_lamports(0)?;
    close_account.set_state(&UpgradeableLoaderState::Uninitialized)?;
    Ok(())
