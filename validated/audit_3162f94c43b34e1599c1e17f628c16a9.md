### Title
Builder payments settle without verifying PTC/attestation quorum, bypassing the required authorization check - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas fork (EIP-7732), a builder is only supposed to be paid for a slot once enough attesters/PTC weight have confirmed the payload was actually delivered — this is enforced by comparing `payment.weight` against `get_builder_payment_quorum_threshold(state)` in `process_builder_pending_payments`. However, the block-processing path `settle_builder_payment`, called from `apply_parent_execution_payload` on almost every block, moves the same `BuilderPendingPayment` into `state.builder_pending_withdrawals` based solely on `payment.withdrawal.amount > 0`, with **no weight/quorum check at all**. Because this block-processing settlement fires before the epoch-boundary quorum check ever gets a chance to run (and clears the payment slot to empty as a side effect), the quorum gate is effectively bypassed for essentially every builder payment.

### Finding Description
Two independent code paths can move a queued `BuilderPendingPayment` into `state.builder_pending_withdrawals` (which is later paid out to `fee_recipient` via `apply_withdrawals`):

1. **Epoch-level, authorized path** — `process_builder_pending_payments`, run once per epoch, correctly gates the payment on quorum: [1](#0-0) 

2. **Block-level, unauthorized path** — `settle_builder_payment`, called every block via `apply_parent_execution_payload` whenever the parent block's payload was `FULL`, unconditionally appends the withdrawal with no weight check: [2](#0-1) 

`apply_parent_execution_payload` calls `settle_builder_payment` for the payment slot corresponding to the parent block's slot as soon as the very next block is processed (`parent_epoch == get_current_epoch(state)` or `== get_previous_epoch(state)`), i.e., in slot N+1 following the payload slot N: [3](#0-2) 

The `payment.weight` field that the quorum check depends on is only incremented inside `process_attestation` when PTC/attesters vote for the same slot with `is_attestation_same_slot`: [4](#0-3) 

Since attestations for slot N are processed in blocks at slot N+1 (or later, within `MIN_ATTESTATION_INCLUSION_DELAY` bounds) and `settle_builder_payment` for slot N's payment already runs during the processing of block N+1 (as part of `apply_parent_execution_payload`, invoked before `process_operations`/`process_attestation` of block N+1's own attestations complete their weight accumulation), the payment is settled — unconditionally, ignoring `payment.weight` — essentially immediately, well before the epoch-boundary `process_builder_pending_payments` quorum sweep ever executes on it. `settle_builder_payment` also always resets the entry to `BuilderPendingPayment.empty()`, so by the time epoch processing runs, there is nothing left in that slot for the quorum check to act on.

This breaks the intended equality that the design establishes: **a Gwei payment to the builder's `fee_recipient` should only occur if the payload attestation weight for that slot reaches quorum** (i.e., a sufficient fraction of stake confirmed the payload was actually delivered on time). Because `settle_builder_payment` performs no such authorization/threshold check, a builder is paid even when the PTC/attester weight never reached (or even started accumulating toward) the quorum threshold — the entire quorum mechanism becomes dead code for the normal, non-degenerate case (block N+1 proposed within the same or following epoch, which is virtually always true).

### Impact Explanation
This is a Critical-severity class of bug per the rules: **Gwei paid to a party (the builder/fee_recipient) without the authorization check (quorum) the protocol requires**, i.e., "a payload executed or paid that the block did not commit to" in the sense that payment happens without the network's committee-based confirmation that the payload was actually delivered/available. It effectively grants the builder guaranteed payment regardless of whether their payload passed the PTC/attestation-weight authorization gate, which is precisely the "incorrect authorization" bug class the Mattermost report describes (a privileged action executed without validating the permission/threshold that should gate it).

### Likelihood Explanation
This triggers under completely normal chain operation — no malicious peer, coalition, or special stake concentration is required. Any time a block is proposed on top of a FULL parent payload within the same or previous epoch (the overwhelmingly common case), `settle_builder_payment` executes and pays the builder unconditionally. The quorum-gated path (`process_builder_pending_payments`) can only ever act on entries that survive to the epoch boundary without being touched by `settle_builder_payment`, which in practice is essentially never for slots that had a proposed follow-on block.

### Recommendation
`settle_builder_payment` should apply the same quorum check as `process_builder_pending_payments` before appending `payment.withdrawal` to `state.builder_pending_withdrawals` — e.g., only settle if `payment.weight >= get_builder_payment_quorum_threshold(state)`, and otherwise leave the payment queued for the appropriate epoch-boundary reconciliation. Alternatively, the design should ensure the same payment entry cannot be resolved through two independent code paths with inconsistent authorization criteria; the two settlement mechanisms need to be reconciled to always require quorum before any builder payment is queued for withdrawal.

### Proof of Concept
Given a state where a builder submits a nonzero-value bid for slot `N` (`process_execution_payload_bid` records the pending payment in `state.builder_pending_payments[slot_index]` with `weight=0`):
1. No attester or an insufficient (<quorum) subset of attesters attest to slot `N`'s payload as timely/available — `payment.weight` remains `0` or below `get_builder_payment_quorum_threshold(state)`.
2. A block is proposed at slot `N+1` whose parent (`block N`) was FULL. During its processing, `process_parent_execution_payload` → `apply_parent_execution_payload` is invoked, which calls `settle_builder_payment(state, payment_index)` for slot `N`'s entry.
3. `settle_builder_payment` checks only `payment.withdrawal.amount > 0` (true, since the builder's bid was nonzero) and unconditionally appends `payment.withdrawal` to `state.builder_pending_withdrawals`, then clears the payment slot — despite `payment.weight` never reaching quorum.
4. On the next withdrawal sweep, `get_builder_withdrawals`/`apply_withdrawals` pays out `payment.withdrawal.amount` to `fee_recipient`, even though the required PTC/attestation-weight quorum confirming payload delivery was never met. [2](#0-1) [5](#0-4)

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
