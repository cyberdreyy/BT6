## Analog Found

### Title
Permissionless SOL "donation" to the SVSP on-ramp/stake account can artificially inflate the cached price of `StakedWithPythPush` banks - (File: `programs/marginfi/src/state/price.rs`)

### Summary
Similar to the HydraDX finding, where direct token transfers to a StableSwap pool bypass the hooks that keep the EMA oracle in sync with the pool's real state, marginfi's `StakedWithPythPush` oracle computes the LST exchange rate directly from the raw lamport balances of the SVSP stake account and on-ramp account instead of going through any protected accounting path. Because Solana allows anyone to credit lamports to an arbitrary account via a plain System Program transfer, a user can inflate these balances at will and then permissionlessly refresh the bank's cached price to reflect the manipulated value.

### Finding Description
For `OracleSetup::StakedWithPythPush`, the price/NAV multiplier is derived directly from the raw lamport balances of the stake account (`ais[2]`) and, once the on-ramp migration flag is set, the on-ramp account (`ais[3]`): [1](#0-0) 

The unit test confirms the NAV is computed as `stake_nav + onramp_nav`, i.e. the sum of both accounts' lamport balances (minus rent-exempt reserve), with no verification that this balance was accrued through any legitimate stake-pool deposit/mint flow: [2](#0-1) 

This NAV is then divided by the LST mint's total supply to compute a `multiplier`, which is applied to the Pyth SOL price to produce the adjusted collateral price: [3](#0-2) 

Unlike a legitimate stake-pool deposit (which mints new LST tokens proportional to the SOL deposited, keeping NAV/supply constant), a bare lamport transfer to the stake account or on-ramp account increases the numerator (`sol_pool_adjusted_balance`) without any corresponding increase to `lst_supply`. Anyone can perform such a transfer using the System Program, since crediting lamports to an account does not require invoking or being authorized by that account's owning program.

The resulting inflated price is not applied lazily — it is picked up as soon as the permissionless `lending_pool_pulse_bank_price_cache` instruction is called, which recomputes and overwrites `bank.cache` with whatever price the current (attacker-manipulated) account state yields: [4](#0-3) 

The test suite documents this exact mechanic in `tests/specs/staked/s02_addBank.spec.ts`, showing that pulsing the staked bank price recomputes `priceMultiplier` directly from on-ramp/stake balances after a deposit changes them: [5](#0-4) 

### Impact Explanation
An attacker (or a borrower about to be liquidated) can:
1. Identify their `StakedWithPythPush` bank's `sol_pool` (stake account) or `pool_onramp` account (both are public keys stored in `bank.config.oracle_keys`).
2. Transfer SOL directly to that account via a plain System Program transfer, instantly inflating the raw balance used in the NAV calculation.
3. Call the permissionless `lending_pool_pulse_bank_price_cache` instruction to force the bank's cached price to reflect the inflated NAV, artificially raising the reported collateral value of that bank for every account holding a balance in it — including the attacker's own unhealthy position.

This lets a borrower defeat an otherwise-legitimate liquidation or unlock additional borrowing capacity on demand, entirely outside of the intended Pyth-price and stake-pool-deposit flow — directly mirroring the original report's concern that direct transfers "interfere with necessary liquidations." Because the multiplier computation has no floor/ceiling sanity check against the previous cached value or against expected deposit flows, the manipulation is accepted at face value by the risk engine on the next health check.

### Likelihood Explanation
The action requires no privileged access: any wallet can send lamports to a public account and call the permissionless pulse instruction, both are single-instruction, atomic operations executable in the same transaction as the health-check-dependent action (e.g., a withdraw or borrow that would otherwise fail health checks). The manipulation is bounded only by the attacker's willingness to spend SOL, and for a borrower trying to avoid a liquidation penalty larger than the donation cost, this is directly economically rational, matching the "confirmed... impact on external protocols/lending" upgrade rationale used in the original C4 finding.

### Recommendation
Do not derive the staked-collateral NAV from raw lamport balances of externally-writable accounts. Instead, source the exchange rate from the SPL Single Validator Stake Pool program's own tracked accounting (or add a rate-of-change/sanity bound comparing the new multiplier to the previously cached multiplier, rejecting price jumps that exceed a reasonable per-refresh threshold unless corroborated by an actual mint/burn of the LST supply).

### Proof of Concept
1. Group admin creates a `StakedWithPythPush` bank for validator V, with `oracle_keys = [pyth_oracle, lst_mint, sol_pool, pool_onramp]`.
2. Attacker (or an existing borrower with an unhealthy staked-collateral position) sends a plain `SystemProgram::transfer` of N SOL to `pool_onramp` (or `sol_pool`).
3. Attacker calls `lending_pool_pulse_bank_price_cache` (permissionless, see `programs/marginfi/src/instructions/marginfi_group/pulse_bank_price_cache.rs`), passing `[pyth_oracle, lst_mint, sol_pool, pool_onramp]` as `remaining_accounts`.
4. `OraclePriceFeedAdapter::load_oracle_context` recomputes `sol_pool_adjusted_balance = stake_nav + onramp_nav` (now inflated by N SOL) and divides by the unchanged `lst_supply`, producing an inflated `multiplier` and hence an inflated adjusted price, which is written into `bank.cache`.
5. Attacker immediately performs a withdraw/borrow (or simply avoids a liquidation) that is evaluated against the now-inflated cached/adjusted collateral price for their staked-SOL bank balance.

```rust
/// (permissionless) Refresh the cached oracle price for a bank.
pub fn lending_pool_pulse_bank_price_cache<'info>(
    ctx: Context<'info, LendingPoolPulseBankPriceCache<'info>>,
) -> MarginfiResult {
    let clock = Clock::get()?;

    let mut bank = ctx.accounts.bank.load_mut()?;

    let price_for_cache = OraclePriceFeedAdapter::get_price_and_confidence_for_cache(
        &bank,
        ctx.remaining_accounts,
        &clock,
    )?;

    bank.update_cache_price(Some(price_for_cache))?;

    Ok(())
}
```
