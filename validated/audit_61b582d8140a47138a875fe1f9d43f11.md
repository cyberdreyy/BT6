### Title
Dust queued deposit left past the prefunding window permanently reverts `stopEpochWithDuration` and bricks prefunded settlement - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
Analogous to the Stakehouse "stake 1 gwei to break the fixed 12 ETH `mintDerivatives` call" bug, an unprivileged (only KYC'd) attacker can make a dust `requestDeposit` in `IdleCDOEpochQueue` and let the prefunding cutoff window lapse. From that point, `epochPendingDeposits[nextEpoch] != 0` can never be cleared by anyone but the attacker, while both `prefundedDepositsToProcess`/`processPrefundedDeposits` hard-revert on `epochPendingDeposits[_epoch] != 0`. On `IdleCDOEpochVariantPrefunded`, the direct `stopEpoch` selector is blocked once a queue is configured and prefunded settlement is executed atomically inside `stopEpochWithDuration`, so a single dust deposit permanently bricks epoch settlement — and with it any already-prefunded principal.

### Finding Description
In the prefunded flow:

1. `requestDeposit(amount)` during a running epoch adds `amount` to `epochPendingDeposits[epochNumber + 1]` ([IdleCDOEpochQueue.sol:103-127](contracts/IdleCDOEpochQueue.sol)). Once the cutoff is reached (`block.timestamp + prefundedDepositWindow >= epochEndDate`), new deposits are blocked and `processDepositsToBorrower` also reverts (`_checkNotAllowed(_prefundedWindow == 0 || block.timestamp + _prefundedWindow < _cdo.epochEndDate())`, lines 164-168).

2. `deleteRequest` can only be called by the depositor himself (line 184-198); there is no manager sweep for leftover pending deposits.

3. Settlement reverts whenever pending deposits remain: `prefundedDepositsToProcess` reverts on `epochPendingDeposits[_epoch] != 0` (line 281) and `processPrefundedDeposits` reverts on `epochPendingDeposits[_epoch] != 0 || _prefunded == 0` (line 265).

4. On the prefunded CDO variant, `_beforeStopEpoch` blocks the plain `stopEpoch` selector when `epochQueue` is set ([IdleCDOEpochVariantPrefunded.sol:39-48](contracts/IdleCDOEpochVariantPrefunded.sol)), and queue settlement is driven atomically from `stopEpochWithDuration` (confirmed by `testStopEpochProcessesPrefundedQueueAtomically`). Because the revert happens inside the stop call, the whole `stopEpochWithDuration` tx reverts — `isEpochRunning` stays true, borrower repayment is never pulled, and no claims can be processed.

Attack sequence:

1. Epoch N is running; attacker (any KYC-passing lender) calls `queue.requestDeposit(1)` costing 1 wei of underlying.
2. Attacker waits until `block.timestamp + prefundedDepositWindow >= epochEndDate`. From here `processDepositsToBorrower` reverts (line 164), so the pending 1 wei can never be forwarded, and only the attacker can remove it via `deleteRequest`.
3. Manager calls `cdoEpoch.stopEpochWithDuration(...)`. The prefunded settlement path hits `epochPendingDeposits[N+1] != 0` → `NotAllowed()` revert. The only other selector, `stopEpoch`, is blocked by `_beforeStopEpoch` (`msg.sig == this.stopEpoch.selector` → revert) while the queue is set.

Epoch N can never be stopped while the queue remains configured.

### Impact Explanation
Broken invariant: epoch state machine liveness — a required privileged transition (`stopEpochWithDuration`) becomes permanently uncallable due to an unprivileged dust action, exactly mirroring M-12's "1 gwei stake reverts the fixed 12 ETH stake".

- **Temporary → permanent freezing of all pool funds**: borrower repayment, pending withdraw fulfillment, and new-epoch start are all gated behind a successful epoch stop. The freeze persists until owner intervention.
- **Permanent freezing of prefunded principal**: the only escape hatch is `setEpochQueue(address(0))`, which skips `processPrefundedDeposits`. Any honest prefunded deposits then keep `epochPrefundedDeposits[epoch] != 0` with `epochPrice[epoch] == 0` forever — `deleteRequest` reverts (line 187) and `claimDepositRequest` reverts (lines 375-379), so those funds are permanently stranded in the queue/borrower.
- Quantified loss: entire prefunded amount forwarded to the borrower (arbitrarily large) plus indefinite freeze of vault NAV, for an attack cost of 1 wei + KYC.

### Likelihood Explanation
Requires only a KYC-passing lender (explicitly an allowed attacker class) and one transaction before the window closes. No privileged collusion needed; the manager cannot prevent it since `requestDeposit` is open to all allowed wallets until the cutoff, and `processDepositsToBorrower` is optional. The bug triggers deterministically once the window lapses with dust still pending.

### Recommendation
Sweep leftover pending deposits into prefunded settlement instead of reverting: in `processPrefundedDeposits`, treat `epochPendingDeposits[_epoch]` as additional prefunded principal (transfer to borrower or refund pro-rata at `virtualPrice`), or allow anyone to permissionlessly flush pending deposits to the borrower before stop. Alternatively, let the manager force-refund pending deposits (a `deleteRequest`-style sweep) and/or make `stopEpochWithDuration` settle-and-clear `epochPendingDeposits` rather than revert.

```solidity
// Fork-style Foundry PoC (setup mirrors test/foundry/IdleCDOEpochVariantPrefunded.t.sol)
function testDustPendingDepositBricksStopEpoch() external {
    // manager configures prefunded queue + window, epoch N is running
    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    vm.prank(manager);
    queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);

    // honest lender prefunds
    _requestDepositWithUser(honestUser, 1e6);
    _enterPrefundedWindow(PREFUNDED_DEPOSIT_WINDOW); // still before cutoff
    vm.prank(manager);
    queue.processDepositsToBorrower(); // prefunded[N+1] = 1e6

    // NOTE: after prefunding, requestDeposit is blocked, so attacker must act
    // BEFORE prefunding instead: redo with attacker depositing 1 wei first.
}

function testDustPendingDepositBricksStopEpoch_v2() external {
    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    vm.prank(manager);
    queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);

    // attacker: any KYC'd wallet, deposits 1 wei for epoch N+1
    address attacker = makeAddr("attacker");
    deal(address(underlying), attacker, 1);
    vm.startPrank(attacker);
    underlying.approve(address(queue), 1);
    queue.requestDeposit(1);                 // epochPendingDeposits[N+1] = 1
    vm.stopPrank();

    // warp inside the prefunding cutoff window
    vm.warp(cdoEpoch.epochEndDate() - PREFUNDED_DEPOSIT_WINDOW + 1);

    // manager can no longer forward the dust
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    queue.processDepositsToBorrower();

    // epoch end: stopEpochWithDuration reverts on leftover pending deposits
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(newApr, interest, duration, 0);

    // direct stopEpoch selector is also blocked while queue is set
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(newApr, interest);

    assertTrue(cdoEpoch.isEpochRunning());   // epoch permanently stuck
}
```

**Uncertainty note**: the exact call site where `IdleCDOEpochVariantPrefunded` invokes `prefundedDepositsToProcess`/`processPrefundedDeposits` (likely its `_afterStopEpochWithDuration` override) was not fully readable in the index (file truncated), but `processPrefundedDeposits` requires `msg.sender == idleCDOEpoch` and the test `testStopEpochProcessesPrefundedQueueAtomically` confirms settlement is executed atomically inside the stop flow, so the revert propagating into `stopEpochWithDuration` is established.
