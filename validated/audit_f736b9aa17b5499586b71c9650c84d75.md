### Title
Node-side signer coordinator double-counts a single signer's weight in both `total_weight_approved` and `total_weight_rejected` for the same block, letting a single signer's flip‑flop inflate the aggregated-vs-verified tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run` maintains a per-block `BlockStatus` with two independent gating sets: `gathered_signatures` (gates weight addition on `BlockResponse::Accepted`) and `responded_signers` (gates weight addition on `BlockResponse::Rejected`). Because these are two different collections, a single signer that first rejects and later accepts (or the reverse, in a more limited way) the same `signer_signature_hash` can have its weight counted into *both* `total_weight_approved` and `total_weight_rejected` simultaneously, breaking the invariant that the tallied "aggregated weight" reflects distinct, verified per-signer decisions.

### Finding Description
In `StackerDBListener::run` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`), the `Rejected` branch only adds weight to `total_weight_rejected` guarded by insertion into `responded_signers`: [1](#0-0) 

It does **not** touch `gathered_signatures`.

The `Accepted` branch, however, gates its weight addition to `total_weight_approved` on `gathered_signatures`, not on `responded_signers`: [2](#0-1) 

Sequence of events for a single signer S with weight w, targeting one block hash H:
1. S sends `BlockResponse::Rejected` for H first. `responded_signers.insert(slot_id)` succeeds (returns true) → `total_weight_rejected += w`.
2. S later sends `BlockResponse::Accepted` for the same H (this is a normal, reachable path in the signer's own state machine — a signer can locally reject a proposal and, after further evaluation such as `check_block_against_signer_db_state`/pre-commit tracking in `stacks-signer/src/v0/signer.rs`, later re-evaluate and sign/accept the same hash if state changes, or a byzantine/buggy signer can simply emit both responses over StackerDB gossip).
3. On processing the Accept, `gathered_signatures.contains_key(&slot_id)` is `false` (that map was never touched by the earlier Reject), so the `if` branch is entered and `total_weight_approved += w` is added — even though this same signer's weight is already counted in `total_weight_rejected`.

Result: `BlockStatus.total_weight_approved + total_weight_rejected` can exceed the true distinct-signer weight, and a single signer's weight can appear on both sides of the approve/reject equality checked at `stacks-node/src/nakamoto_node/signer_coordinator.rs` (the `total_weight_approved >= self.weight_threshold` / `total_weight_rejected + weight_threshold > total_weight` checks): [3](#0-2) 

This is exactly the "rejection recounted as an accept" class of bug: the coordinator's aggregated-weight bookkeeping no longer equals the set of verified, distinct accepting signers.

### Impact Explanation
This directly breaks the aggregated-weight vs. verified-accepts equality that the mining coordinator relies on to decide whether a block has enough signer weight to broadcast, or has been rejected by a blocking minority. A single signer (one StackerDB slot) can inflate `total_weight_approved` toward `weight_threshold` with weight that should not count as a clean, exclusive "accept" (since that same weight is simultaneously counted as a rejection), or symmetrically pad `total_weight_rejected`. In marginal-weight scenarios (weight close to the 70% threshold), this double counting can let the miner believe it has gathered sufficient approving weight from distinct honest signers when part of that counted weight actually belongs to a signer who also rejected the block, undermining the safety guarantee that a block is only broadcast once it has genuinely reached the required distinct-signer weight threshold.

### Likelihood Explanation
Reachable by a single node — no majority collusion or admin/authtoken access is required. It only requires one signer (or a compromised/buggy signer, or one that legitimately flip-flops its decision through gossip'd StackerDB writes) to publish two different `BlockResponse` messages for the same `signer_signature_hash`. Because `gathered_signatures` and `responded_signers` are separate bookkeeping structures with no cross-check, the double count is deterministic once the two message types are received in the reject→accept order.

### Recommendation
Use a single per-slot decision record (e.g., one `HashMap<u32, BlockResponse>` or an enum tracking each signer's current accept/reject state) instead of two independently-gated collections. When a new response for the same slot arrives, subtract the previously counted weight from whichever bucket it was in before adding it to the new bucket, ensuring `total_weight_approved` and `total_weight_rejected` are always mutually exclusive per-signer weight tallies.

### Proof of Concept
1. Coordinator receives `BlockResponse::Rejected` from signer slot `k` (weight `w`) for hash `H`: `responded_signers = {k}`, `total_weight_rejected = w`.
2. Coordinator later receives `BlockResponse::Accepted` from the same slot `k` for the same hash `H` (crafted/gossiped signer message, or a legitimate later re-evaluation by the same signer).
3. Because `gathered_signatures` is still empty for slot `k`, the accept branch's `if !block.gathered_signatures.contains_key(&slot_id)` is true, so `total_weight_approved += w`.
4. Now `total_weight_approved == w` and `total_weight_rejected == w` for the same signer's weight `w`, violating the expectation that a signer's weight belongs exclusively to one bucket — demonstrable purely via the state transitions in [4](#0-3) .
