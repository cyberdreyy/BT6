## Analog Found: Stale Confirmations From Deleted Multisig Keys Allow Request Execution Below Live-Signer Threshold

### Title
Multisig request execution counts confirmations from already-deleted keys, letting requests execute below the intended live-signer threshold - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` checks whether the number of confirming public keys stored in `self.confirmations` has reached `num_confirmations` [1](#0-0) . When a key is revoked via the `DeleteKey` action, the contract only removes requests that were *originated* by that key, and clears `num_requests_pk` for it — it never scans other pending requests' `confirmations` sets to strip out that key's prior confirmation [2](#0-1) . The threshold check therefore counts a confirmation from a key that is no longer a member of the multisig.

### Finding Description
The intended binding is: `confirmations counted for a request == confirmations from currently live (non-deleted) signer keys`. The code breaks this equality:

- `confirm(request_id)` inserts `env::signer_account_pk()` into the `HashSet<PublicKey>` stored per request, and once `confirmations.len() + 1 >= self.num_confirmations`, it calls `execute_request` [3](#0-2) .
- `execute_request`'s `DeleteKey` branch removes only the *requests originated by* the deleted key (`r.signer_pk == pk`) and the per-key request counter, but does not touch `self.confirmations` entries belonging to *other* requests that the deleted key had already confirmed [2](#0-1) .
- Consequently, a pending request X (created by key A, previously confirmed by key B) keeps key B in its confirmation set even after key B is deleted from the multisig via a completed `DeleteKey` request.

So if `num_confirmations = 3` and key B had already confirmed request X before being revoked, only 2 more *live* keys are needed to reach the threshold of 3 — the third "confirmation" is really from a revoked identity. The recorded confirmation count no longer reflects the set of currently-trusted keys.

### Impact Explanation
This directly matches the "Critical" impact class: "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`, or `DeleteKey` action can be executed with fewer genuinely live/authorized confirmations than `num_confirmations` mandates, because a stale confirmation from a removed key is silently counted. This weakens the custody guarantee that funds/actions require `num_confirmations` *current* signers to agree.

### Likelihood Explanation
This requires no special privilege beyond being (or having been) one of the multisig's keys — a normal operational event (rotating out a compromised or departing signer via `DeleteKey`) is sufficient to create the stale state. Any request that was confirmed by the soon-to-be-deleted key before deletion, and left pending, silently retains that confirmation weight indefinitely. No malicious node, redeploy, or social engineering is needed — it is a straightforward consequence of normal `DeleteKey` usage combined with pre-existing pending requests.

### Recommendation
When executing `DeleteKey`, iterate over all entries in `self.confirmations` (not just requests originated by the deleted key) and remove the deleted public key from every confirmation set, re-checking whether affected requests still meet quorum. Alternatively, validate at `confirm`-time / `execute_request`-time that every public key in a request's confirmation set is still a valid multisig key before counting it toward the threshold.

### Proof of Concept
1. Initialize multisig with `num_confirmations = 3` and keys A, B, C, D attached to the account.
2. Key A calls `add_request` for `Transfer{amount}` to an attacker-controlled receiver → `request_id = X`.
3. Key B calls `confirm(X)` → confirmations = {B} (1/3).
4. Separately, a quorum (A, C, D) submits and confirms a `DeleteKey{public_key: B}` request, which executes and calls `promise.delete_key(B)`. Per `execute_request`'s `DeleteKey` branch [2](#0-1) , only requests where `signer_pk == B` are purged; request X (signed/originated by A) is untouched, and confirmations for X still contain B.
5. Key B's on-chain access key is now removed — B is no longer a legitimate signer.
6. Key C calls `confirm(X)` → confirmations = {B, C} (2/3).
7. Key D calls `confirm(X)` → confirmations = {B, C, D} (3/3) → `execute_request` runs the `Transfer`, even though B's access was revoked in step 4 and only 2 genuinely live keys (C, D) plus A's original request actually authorized it.

This demonstrates the transfer executes using a stale confirmation from a deleted key, i.e., below the real live-signer threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
