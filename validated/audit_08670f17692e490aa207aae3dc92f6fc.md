Based on my investigation, I found a genuine analog to the FUXA bug class (an unauthenticated/error state being converted into a permissive default) in the signer's chainstate tenure-tip check.

### Title
Signer's tenure-height check fails open when the node is unreachable, letting a lower/conflicting block pass the "confirms latest tip" gate - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs` is the shared gate that answers "does this proposed block confirm the highest known tip of its tenure?" It runs at proposal arrival, at validate-ok, and again at the pre-commit → signature moment via `check_block_against_signer_db_state`. When the signer's own local records (`get_tenure_last_block_info`, `get_last_accepted_block`) don't veto the block, the function falls back to asking the stacks-node for the tenure tip with `client.get_tenure_tip(tenure_id)`. If that RPC call errors (timeout, connection refused, node busy, etc.), the code does not reject or hold the block — it returns `Ok(true)`, i.e. treats the proposal as confirmed-higher-than-tip by default. [1](#0-0) 

### Finding Description
The equality being protected here is: *"a proposed/competing block must only be treated as extending the tenure's tip if it is verifiably higher than the last known tip."* The function's own doc comment states the assumption is "safe" because the block still has to clear the `stacks-node`'s own `/v3/block_proposal` endpoint. That is true for the **first** call site (proposal arrival, before submission to the node), but this same function is reused, unmodified, at two later call sites that do **not** go through node validation again:

- `handle_block_validate_ok` re-invokes `check_block_against_signer_db_state` → `check_latest_block_in_tenure` after the node already validated the block, purely to catch state that changed since submission. [2](#0-1) 
- `handle_block_pre_commit`'s pre-commit→signature threshold re-check calls the same `check_block_against_signer_db_state` immediately before the signer actually signs, with no further node round-trip in between. [3](#0-2) 

At both of these later points, a transient RPC failure to the local stacks-node (which a miner cannot directly control the timing of, but which is a very common/likely condition — restarts, load, network hiccups) causes the "does it confirm the tip" check to *fail open* rather than fail closed. Because this is the check that would reject a block that does not confirm the tenure's already-signed/accepted tip, a node hiccup at exactly the wrong moment removes this equivocation guard, and the signer proceeds to mark the block pre-committed/signed as if it had passed the check honestly.

This mirrors the FUXA class of bug precisely: an error/unavailable state (`Err(e)` from the RPC, analogous to "invalid token") is silently converted into the permissive/accepted branch (`Ok(true)`, analogous to "guest access granted") instead of being converted into a rejection or a stall. [4](#0-3) 

### Impact Explanation
This weakens (does not fully break by itself) the one-per-tenure/conflict guard: it removes one of the layers that would otherwise reject a block that fails to confirm the tenure's tip. Combined with the pre-commit conflict logic in `handle_block_pre_commit` (documented in `docs/signer-flows.md` sections 5 and 7), an unreachable node at the specific instant of the pre-commit-threshold recheck means the signer signs off the tracked `valid`/pre-commit path without the tip confirmation actually having been verified for that call. This is a High-severity concern under the given taxonomy (a signer potentially acting on unverified state right at the signing boundary) rather than an outright Critical break, because the local db checks (`get_tenure_last_block_info`, `get_last_accepted_block`) still run first and can independently veto obviously-conflicting blocks; the RPC fallback is only reached when those checks don't already block it.

### Likelihood Explanation
This does not require a majority of signers or another signer's key — it only requires the *victim signer's own* stacks-node RPC connection to be momentarily unavailable at the moment `check_latest_block_in_tenure` is called (a condition a single miner/attacker could plausibly try to induce or simply race against, e.g. by proposing a competing block while the target signer's node is restarting or under load). It is a one-slot-miner/gossip-triggerable condition, matching the "single miner plus gossip" constraint in scope.

### Recommendation
Change the RPC-failure branch of `check_latest_block_in_tenure` to distinguish call sites: for the pre-node-validation proposal-arrival path, the current "assume higher, let the node's `/v3/block_proposal` be the backstop" logic is fine since the node still validates. For the two post-validation call sites (`handle_block_validate_ok`'s re-check and the pre-commit→signature re-check in `handle_block_pre_commit`), an RPC failure to `get_tenure_tip` should not be silently treated as `Ok(true)`; it should instead surface as a `ConnectivityIssues`/retry-able condition so the signer holds off signing until it can positively confirm the tip check, consistent with how other connectivity failures in this same code path (e.g. in `check_block_against_signer_db_state`) are already converted into `RejectReason::ConnectivityIssues` rather than a silent pass. [5](#0-4) 

### Proof of Concept
1. Signer A has already signed/accepted block `B1` at height `h` in tenure `T` (recorded via `get_last_signed_block`/`get_last_accepted_block`).
2. A miner proposes a conflicting/lower block `B2` at height `h` (or one that otherwise should fail the tip check) in a way that reaches the point where `check_latest_block_in_tenure`'s local-db checks (`info.block.header.chain_length <= ...`, pre-commit freshness) do not veto it — e.g. because the local record has just timed out per `tenure_last_block_proposal_timeout`, or because it's a fresh proposal not yet reflected locally.
3. At the exact moment Signer A's runloop calls `client.get_tenure_tip(tenure_id)` inside `check_latest_block_in_tenure` (from either `handle_block_validate_ok`'s re-check, or the pre-commit-threshold recheck in `handle_block_pre_commit`), Signer A's connection to its own stacks-node RPC endpoint is disrupted (e.g. node restart/timeout).
4. `client.get_tenure_tip` returns `Err(e)`; the function logs a warning and returns `Ok(true)` (line 459 of `chainstate/mod.rs`), i.e., "assume proposal is higher."
5. The tip-confirmation check is bypassed for this evaluation, and the caller proceeds down the accept path (pre-commit/sign) without a genuine tip confirmation having occurred at that call. [1](#0-0)
