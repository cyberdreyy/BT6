### Title
Lockup owners can bypass the Foundation-controlled staking-pool whitelist by supplying a forged `whitelist_account_id` at creation, permanently diverting unvested tokens — (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` lets the caller of `create()` override the canonical, Foundation-owned staking-pool whitelist with an arbitrary account ID, which is then baked into the deployed lockup as its trust anchor for staking-pool selection. This is the NEAR analog of the reported Solidity bug: an address that is supposed to be an immutable, trust-establishing reference (there, the voting-adaptor/factory pointer used in a `delegatecall`; here, the whitelist contract used to gate which staking pool a lockup may delegate to) is instead attacker-suppliable "calldata"/constructor argument, letting the attacker substitute a value they fully control for the value the security model assumes is trusted.

### Finding Description
`LockupFactory::create()` accepts an optional `whitelist_account_id` parameter and, if provided, uses it verbatim as the new lockup's `staking_pool_whitelist_account_id` instead of enforcing the factory's own Foundation-configured `self.whitelist_account_id`: [1](#0-0) 

That value is passed straight into the deployed lockup's `new()` args: [2](#0-1) 

The deployed lockup then trusts this attacker-chosen contract completely when deciding which staking pool is safe to delegate to: [3](#0-2) 

The design intent of the whitelist, as documented, is to guarantee that a staking pool "can not be lost or locked, such as the lockup contract should be able to recover delegated tokens back to the lockup from a staking pool," and that only Foundation-approved pools/factories are added to it: [4](#0-3) 

By pointing `staking_pool_whitelist_account_id` at a whitelist contract the owner controls, the owner (the vesting recipient) can make `is_whitelisted` return `true` for a malicious "staking pool" they also control, then stake the account's full liquid balance — vested or not — into it: [5](#0-4) 

`deposit_and_stake` only checks the lockup's own liquid NEAR balance, not whether the amount is vested, so unvested tokens (which should remain recoverable by the Foundation) can be moved out through the same path. The Foundation's only recourse — `terminate_vesting` / `termination_prepare_to_withdraw` — depends entirely on cross-contract calls to the selected staking pool cooperating truthfully (`get_account_staked_balance`, `unstake`, `get_account_unstaked_balance`, `withdraw`): [6](#0-5) 

Since the "staking pool" is attacker-controlled, it can answer these calls with fabricated success responses (or simply never surrender funds), so this recovery mechanism can be defeated entirely, exactly mirroring the reported pattern where an attacker substitutes a fake, trust-bearing contract for the genuine one the protocol assumed was fixed/immutable.

### Impact Explanation
This breaks the custody binding the rules describe as "an account trusted as a pool or whitelist versus the code and arguments that trust was granted for." The Foundation's unvested-token custody is meant to be enforced by delegating only to whitelist-approved, honest staking pools. Because `create()` lets the deployer/owner substitute their own whitelist, the owner can:
1. Deploy (or have deployed) a lockup with an owner-controlled `staking_pool_whitelist_account_id`.
2. `select_staking_pool()` to a self-controlled malicious pool that the fake whitelist approves.
3. `deposit_and_stake()` the full account balance (including still-unvested tokens) into that malicious pool, which simply keeps the NEAR.
4. When the Foundation later calls `terminate_vesting`/`termination_prepare_to_withdraw`, the malicious pool can lie about balances or refuse withdrawal, leaving the lockup permanently unable to recover the unvested amount.

This matches the Critical category "locked or unvested tokens released early" / funds permanently frozen — real NEAR is diverted from the Foundation's reach by an unprivileged token recipient using only functionality the factory/lockup expose by design.

### Likelihood Explanation
Any account that can call `LockupFactory::create()` with the minimum attached deposit can trigger this — no special privilege beyond being the future lockup owner/recipient is required, and the vulnerable code path (`create()` → `select_staking_pool()` → `deposit_and_stake()`) is part of normal, documented lockup usage. The only extra work required of the attacker is deploying two contracts they already control (a fake whitelist and a fake staking pool).

### Recommendation
Do not allow `create()` callers to override the whitelist account with an arbitrary value. Either remove the `whitelist_account_id` override parameter entirely and always use the factory's own Foundation-configured `self.whitelist_account_id`, or restrict use of a custom whitelist to callers authorized by the Foundation (e.g., only when `predecessor_account_id == foundation_account_id`), and separately ensure any custom whitelist used for vesting lockups is itself an approved value rather than an unrestricted argument.

### Proof of Concept
1. Attacker (future lockup owner) deploys `FakeWhitelist` (always returns `true` from `is_whitelisted`) and `FakePool` (implements the staking-pool interface but never returns deposited NEAR, and fabricates `get_account_staked_balance`/`get_account_unstaked_balance` responses).
2. Attacker calls `LockupFactory::create(owner_account_id = attacker, vesting_schedule = Some(...), whitelist_account_id = Some(FakeWhitelist))` (`lockup-factory/src/lib.rs:108-134`), which is deployed with `staking_pool_whitelist_account_id = FakeWhitelist`.
3. Foundation funds the lockup with vesting NEAR as usual (out of scope of this PoC — assume standard onboarding flow).
4. Attacker calls `select_staking_pool(FakePool)` (`lockup/src/owner.rs:12-41`); the lockup asks `FakeWhitelist.is_whitelisted(FakePool)`, which returns `true`.
5. Attacker calls `deposit_and_stake(full_balance)` (`lockup/src/owner.rs:127-166`), moving all NEAR — including unvested — into `FakePool`.
6. Foundation calls `terminate_vesting` then `termination_prepare_to_withdraw` (`lockup/src/foundation.rs:58-127`); `FakePool` reports fabricated balances/never releases funds, so the unvested NEAR is never recovered by the Foundation while the attacker's `FakePool` retains the actual tokens.

            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

# Whitelist contract for staking pools

The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved
by NEAR Foundation.

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
able to recover delegated tokens back to the lockup from a staking pool. In order to enforce this, only approved (whitelisted)
accounts of staking pool contracts can receive delegated tokens from lockup contracts.

If NEAR Foundation has to approve every single staking pool account it might lead to a bottleneck and centralization
To address this NEAR Foundation can whitelist the account IDs of staking pool factory contracts.

The whitelisted staking pool factory contract will be able to whitelist accounts of staking pool contracts.
A factory contract creates and initializes a staking pool contract in a secure and permissionless way.
This allows anyone on the network to be able to create a staking pool contract for themselves without needing approval from the NEAR
Foundation. This is important to maintain the decentralization of the decision making and network governance.

To be able to address mistakes, NEAR Foundation has the ability to remove staking pools and staking pool factories from the whitelists.

    pub fn termination_prepare_to_withdraw(&mut self) -> Promise {
        self.assert_called_by_foundation();
        self.assert_staking_pool_is_idle();

        let status = self.get_termination_status();

        match status {
            None => {
                env::panic(b"There is no termination in progress");
            }
            Some(TerminationStatus::UnstakingInProgress)
            | Some(TerminationStatus::WithdrawingFromStakingPoolInProgress)
            | Some(TerminationStatus::WithdrawingFromAccountInProgress) => {
                env::panic(b"Another transaction is already in progress.");
            }
            Some(TerminationStatus::ReadyToWithdraw) => {
                env::panic(b"The account is ready to withdraw unvested balance.")
            }
            Some(TerminationStatus::VestingTerminatedWithDeficit) => {
                // Need to unstake
                self.set_termination_status(TerminationStatus::UnstakingInProgress);
                self.set_staking_pool_status(TransactionStatus::Busy);
                env::log(b"Termination Step: Going to unstake everything from the staking pool");

                ext_staking_pool::get_account_staked_balance(
                    env::current_account_id(),
                    &self
                        .staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id,
                    NO_DEPOSIT,
                    gas::staking_pool::GET_ACCOUNT_STAKED_BALANCE,
                )
                .then(
                    ext_self_foundation::on_get_account_staked_balance_to_unstake(
                        &env::current_account_id(),
                        NO_DEPOSIT,
                        gas::foundation_callbacks::ON_GET_ACCOUNT_STAKED_BALANCE_TO_UNSTAKE,
                    ),
                )
            }
            Some(TerminationStatus::EverythingUnstaked) => {
                // Need to withdraw everything
                self.set_termination_status(
                    TerminationStatus::WithdrawingFromStakingPoolInProgress,
                );
                self.set_staking_pool_status(TransactionStatus::Busy);
                env::log(b"Termination Step: Going to withdraw everything from the staking pool");

                ext_staking_pool::get_account_unstaked_balance(
                    env::current_account_id(),
                    &self
                        .staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id,
                    NO_DEPOSIT,
                    gas::staking_pool::GET_ACCOUNT_UNSTAKED_BALANCE,
                )
                .then(
                    ext_self_foundation::on_get_account_unstaked_balance_to_withdraw(
                        &env::current_account_id(),
                        NO_DEPOSIT,
                        gas::foundation_callbacks::ON_GET_ACCOUNT_UNSTAKED_BALANCE_TO_WITHDRAW,
                    ),
                )
            }
        }
    }
