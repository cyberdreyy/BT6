### Title
Stale confirmations from removed multisig members allow request execution below the effective live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges pending requests that were *authored* by the removed member, but never removes that member's `confirmations` entries from requests they merely *confirmed*. As a result, a member's confirmation persists and continues to count toward `num_confirmations` even after that member has been removed from the multisig, letting a request be executed with fewer genuinely-current members backing it than the configured threshold requires.

### Finding Description
The binding the multisig is supposed to enforce is: `confirmations.len() >= num_confirmations` should equal *live, currently-authorized member approvals* ≥ `num_confirmations`. In `confirm()`, this equality is checked purely against the stored `HashSet<String>` of confirmer identifiers: [1](#0-0) 

However, `delete_member()` only cleans up requests where the removed member is the *original requester* (`r.member == member`), not requests that member merely confirmed: [2](#0-1) 

So if member `M` confirms request `R` (authored by someone else), then `M` is later removed via a separate `DeleteMember` request, `R`'s `confirmations` set still contains `M`'s identifier. `M` is no longer in `self.members`, so `M` could never confirm again — but the confirmation they already cast is never invalidated. When a subsequent `confirm()` call from a still-current member pushes the count to `num_confirmations`, `execute_request()` runs, treating the departed member's stale approval as valid: `Left = confirmations recorded (includes ex-member) ≥ num_confirmations` while `Right = approvals actually backed by live members < num_confirmations` — the equality the design depends on is broken.

### Impact Explanation
This lets a request (e.g., a `Transfer` moving NEAR out of the multisig account) execute while backed by fewer than `num_confirmations` *currently authorized* members. In a realistic scenario, a member whose key is later found compromised/malicious and is removed via `DeleteMember` may have already confirmed a self-serving `Transfer` request before removal; that confirmation is never invalidated, so the malicious request only needs `num_confirmations - 1` further honest confirmations (rather than the full quorum of live members) to execute and move funds. This matches the Critical impact class: "a multisig request executed below threshold" / NEAR moved by a party not entitled to it.

### Likelihood Explanation
This requires no special privilege beyond being (or having been) a multisig member/key holder — any member can confirm a pending request and later be removed through the normal `DeleteMember` governance flow used for compromised or offboarded members, which is a routine operation in a long-lived multisig. No malicious redeploy, foundation action, or out-of-scope trust is needed; it purely exploits the accounting gap between `confirmations` (a `HashSet<String>` keyed by member string) and `members` (`UnorderedSet<MultisigMember>`).

### Recommendation
When `delete_member()` removes a member, also scan `confirmations` for **all** active requests (not only ones the member authored) and strip that member's confirmation entry from each `HashSet`. Alternatively, validate at `confirm()`/`execute_request()` time that every entry in a request's `confirmations` set still corresponds to a member currently present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `D` (about to be flagged as compromised) calls `add_request` to create malicious `Transfer` request `R` to an attacker-controlled account, then calls `confirm(R)` — `confirmations[R] = {D}` (1 of 3).
3. Legitimate members detect `D`'s compromise and submit/confirm a `DeleteMember{member: D}` request to remove `D`. `delete_member()` runs its cleanup, but since `D` did not author `R` (`r.member != D`), `R`'s entry in `confirmations` is left untouched — `confirmations[R]` still equals `{D}`.
4. `D` is now removed from `self.members` and can no longer call `confirm`.
5. An honest member `A` confirms `R` → `confirmations[R] = {D, A}` (2). Member `B` confirms `R` → `{D, A, B}` reaches 3 == `num_confirmations`, and `execute_request(R)` fires the `Transfer`, moving funds out — even though only 2 of the 3 *current* members (`A`, `B`) actually approved it, with the third "confirmation" coming from a member already expelled from the multisig. [2](#0-1)  shows the incomplete cleanup, and [3](#0-2)  shows the unconditional trust placed in the stored `confirmations` set when reaching the threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
