Confirmed: `LendingAccountBorrow.group` (and the equivalent accounts in withdraw and the integration withdraws) is a non-`mut` `AccountLoader<MarginfiGroup>` [1](#0-0) , and `effective_remaining_capacity` is an explicitly non-mutating read that only simulates window advancement without writing state back [2](#0-1) .

### Title
Group-Level Rate Limiter Is a Per-Instruction Cap With No Real-Time Accumulation, Allowing Unlimited Bypass via Multiple Outflow Instructions - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
The group-level rate limiter (`configure_group_rate_limits` / hourly and daily USD outflow caps) is enforced only as a read-only check against a stale, admin-settled counter on every individual withdraw/borrow instruction. The check never mutates the `MarginfiGroup` account during the user instruction, so any number of outflow instructions — whether issued across separate transactions before the off-chain admin settlement runs, or packed into a single atomic transaction — each see the exact same starting counter and each pass the "single instruction under the cap" check independently. This is architecturally identical to the reported `MaviaToken.sol` bug class: a maximum-transfer cap enforced per single transfer with no accumulation logic, trivially bypassed via multiple transfers below the cap.

### Finding Description
`record_withdrawal_outflow` performs the group rate-limit check purely read-only: it compares the projected USD value of the current withdrawal/borrow against `group.rate_limiter.hourly/daily.effective_remaining_capacity(...)`, and if it passes, only emits a `RateLimitFlowEvent` for later off-chain aggregation — it never calls a mutating "record" method on the group's counters [3](#0-2) . The actual counter is only advanced later, out-of-band, when the delegate admin aggregates emitted events and submits `update_group_rate_limiter` [4](#0-3) .

Because the `group` account is loaded via a non-`mut` `AccountLoader` in `LendingAccountBorrow`/`LendingAccountWithdraw`/Kamino/Solend/JupLend/Drift withdraw contexts [1](#0-0) , no user instruction can durably decrement remaining capacity on-chain. The project's own test explicitly documents and asserts this: a user can borrow (or repay) any amount within the configured limit and the group's `curWindowOutflow` remains completely unchanged afterward [5](#0-4) . The design doc even states the admin only aggregates and settles "every ~10 minutes" in production [6](#0-5) .

Consequently, a user (or several colluding users) can issue N outflow instructions in immediate succession — including multiple `lending_account_borrow`/`lending_account_withdraw` instructions bundled in a single atomic Solana transaction — where each individual instruction is under the configured hourly/daily cap, and each is validated against the identical unmutated group state. All N instructions succeed atomically, producing a cumulative outflow of N× the configured group-wide cap, with no on-chain mechanism preventing it before the next admin settlement.

### Impact Explanation
The group rate limiter exists specifically as a risk-control backstop — the guide states the deleverage-limit variant "exists to cap how much USD value can be withdrawn from a group... as a defense if the risk workflow is abused or compromised" [7](#0-6) , and the general group rate limiter is meant to bound aggregate outflow across the whole group per hour/day. Bypassing it undermines a protocol-level safety control intended to contain fast, large-scale drains (e.g., from a compromised oracle, a mispriced bank, or a broader exploit) within a bounded window. Because settlement is off-chain and only periodic, an attacker can extract effectively unbounded outflow (bounded only by actual bank liquidity and per-bank/per-instruction limits, not the group cap) before the counter is ever updated, defeating the intended defense-in-depth purpose of the control during the exact type of event it exists to mitigate.

### Likelihood Explanation
Likelihood is high and requires no privileged access, no timing race with validators, and no mocked/idealized environment: any user with sufficient collateral can trivially construct a single transaction containing multiple borrow/withdraw instructions, each individually valid and under the cap, and the on-chain code will accept all of them because the check reads identical, unmutated group state every time within the transaction. This is directly reproducible and does not depend on off-chain worker latency at all (the atomic-transaction variant works even with an instantly-responsive admin), only on the fact that the write-back is admin-driven rather than done synchronously in the instruction.

### Recommendation
Track pending group-level outflow in-transaction (or fail closed) rather than relying purely on a stale off-chain-settled counter. Options: (1) make the group account mutable and increment an in-instruction "pending outflow" accumulator synchronously during the withdraw/borrow path (accepting the extra writable-account cost the design was trying to avoid), or (2) if the read-only/off-chain design must be kept, bound how many outflow instructions can be combined per transaction and/or enforce a stricter per-instruction cap so that worst-case atomic-transaction bypass cannot materially exceed the intended window cap, and reconcile aggressively (e.g., every block) rather than periodically.

### Proof of Concept
1. Admin configures group hourly rate limit via `configure_group_rate_limits`, e.g. cap = $10.
2. Attacker (or several colluding accounts) constructs a single Solana transaction containing 5 `lending_account_borrow` instructions of $8 each against sufficiently collateralized marginfi accounts/banks.
3. For each instruction, `record_withdrawal_outflow` reads `group.rate_limiter.hourly.effective_remaining_capacity()` — which is unchanged from the transaction's start because `group` is never written to by a prior instruction in the same transaction (non-`mut` `AccountLoader`) — and since $8 < $10 remaining, every instruction individually passes the check.
4. All 5 instructions succeed atomically, producing $40 of outflow in one transaction against a configured $10 hourly cap — a 4x bypass — with the group's on-chain counter still recording $0 of consumed capacity until the admin's later `update_group_rate_limiter` call. This mirrors the existing test `"(user 2) group rate limiter is read-only during user instructions"` [5](#0-4)  which already demonstrates that a single borrow leaves `curWindowOutflow` unchanged — the exploit is simply repeating that same successful, unmutating check N times before any settlement occurs.

```markdown
### 2. User transaction path

During a withdraw or borrow:

- The bank rate limiter is updated immediately on the writable bank account.
- The group rate limiter is only checked read-only.
- The protocol converts the flow to USD using the instruction price/oracle path.
- If the projected group hourly or daily capacity is exceeded, the user instruction fails.
- A `RateLimitFlowEvent` is emitted for off-chain aggregation.

Important details:

- Flashloans, liquidations, and deleverages skip the normal rate-limit accounting path.
- `RateLimitFlowEvent` is an indexing aid, not a source of truth. Solana log truncation can drop
  events, so the off-chain worker must reconcile gaps instead of assuming no event means no flow.
```
