### Title
Signer broadcasts a block signature without verifying the equivocation-guard DB write succeeded - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
In `handle_block_pre_commit`, the local state-machine transition that records "I signed this block" (`mark_locally_accepted`) and its persistence to SignerDB (`insert_block`) are both allowed to fail silently, yet the signer proceeds to compute and broadcast the actual cryptographic signature regardless. This mirrors the D3Vault bug class: a critical "debt/collateral" bookkeeping step (persisting the signed state that the conflict/equivocation checks depend on) is not gated on success, while the "payout" step (irreversibly broadcasting a signature over the network) happens unconditionally right after. [1](#0-0) 

### Finding Description
When the pre-commit weight threshold is reached and all conflict checks pass, the signer calls `block_info.mark_locally_accepted(false)`. If this returns an `Err` (e.g. because the block already reached global consensus in a way not anticipated), the code only logs a warning when `!block_info.has_reached_consensus()`, and otherwise takes no corrective action — it does not `return`. [2](#0-1) 

Immediately afterward, `self.signer_db.insert_block(&block_info)` is called with `.unwrap_or_else(|e| self.handle_insert_block_error(e))` — any DB persistence error is routed to a handler rather than aborting the signing flow. [3](#0-2) 

Right after that, regardless of whether the mark/insert succeeded, the code unconditionally creates the block acceptance signature and broadcasts it: [4](#0-3) 

The entire double-sign/equivocation defense in this codebase is built on the assumption that a successful `mark_locally_accepted` + `insert_block` durably records "signed_self" for this height/tenure in SignerDB, so that later pre-commit evaluations for a conflicting block at the same height can find it via `get_signed_conflicts` and refuse to sign. The doc comments describing this pre-commit flow explicitly rely on this: "a signature is a bearer instrument", so once the network-visible signature is out, the local bookkeeping absolutely must reflect it. [5](#0-4) 

The same unconditional-broadcast-after-possibly-failed-persist pattern appears again in `handle_block_validate_ok`, where `mark_pre_committed` errors are likewise only conditionally warned about (`if !block_info.has_reached_consensus() && block_info.state != BlockState::LocallyAccepted`) before continuing to send the pre-commit and drive the state machine forward. [6](#0-5) 

If a transient DB error occurs at exactly the moment of signing (disk I/O failure, lock contention, process being killed/restarted between the in-memory mutation and the SQLite write), the signature is still computed and broadcast over StackerDB, but the SignerDB row on disk does not reflect `signed_self`/`GloballyAccepted`/`LocallyAccepted` state for that block. `get_signed_conflicts`, which is the sole guard checked in `handle_block_pre_commit` before signing a would-be conflicting block at the same or higher height, queries exactly this persisted state. [7](#0-6) 

On the next restart (or even without a restart, if the in-memory `block_info` map entry itself is later evicted/replaced because the insert never committed), the signer has no record that it already signed a block at that height. A subsequent proposal at the same height — from the same miner after a fork, or from an attacker-influenced tenure-change — would then pass the conflict check and be signed again, producing two valid signer signatures over conflicting blocks at the same height: an equivocation.

### Impact Explanation
This breaks the equivocation guard that the whole pre-commit/conflict-detection design in section 5 of `docs/signer-flows.md` depends on. Per the rules, "a signer losing the equivocation guard on restart" is explicitly classified as High impact. A signer that equivocates undermines the safety assumption that each signer only ever backs one block per height, which downstream consumers (the coordinator's weight tally in `stackerdb_listener.rs`/`signer_coordinator.rs`) rely on to determine a globally accepted, canonical block. [8](#0-7) 

### Likelihood Explanation
This requires no attacker action beyond normal operation of the network — it is triggered purely by an ordinary transient failure (disk error, process kill/restart, DB lock timeout) occurring in the narrow window between marking the in-memory `BlockInfo` as accepted and durably persisting it, immediately before an unconditional broadcast of the signature. Such timing windows are realistic on any production node subject to restarts, OOM kills, or storage hiccups, and the code path is on every single block signing decision (`handle_block_pre_commit`), so it is a persistent, not one-off, risk. It does not require a malicious majority or another signer's key — it can be triggered on a single signer's own local failure.

### Recommendation
- Treat a failed `mark_locally_accepted`/`mark_pre_committed` or a failed `signer_db.insert_block` as fatal for the current attempt to sign: `return` immediately instead of only logging a conditional warning, so the signature is never computed/broadcast unless the durable equivocation-guard state was actually committed first.
- Ensure the ordering is: persist state guaranteeing conflict visibility → only then compute and broadcast the signature, and abort (not just log) on any persistence failure, mirroring the recommendation in the source report to check return values before proceeding with the "payout" step.
- Add a startup/recovery check that reconciles in-flight signing attempts against SignerDB so a crash mid-write cannot silently drop the equivocation record.

### Proof of Concept
1. A signer receives enough pre-commits to cross the 70% threshold for block `B1` at height `H`, tenure `T1`, and enters `handle_block_pre_commit`. [9](#0-8) 
2. `block_info.mark_locally_accepted(false)` succeeds in memory, but the subsequent `self.signer_db.insert_block(&block_info)` fails (e.g., simulate with a disk-full/locked DB) — the error is swallowed by `handle_insert_block_error` and execution continues. [3](#0-2) 
3. `create_block_acceptance` + `handle_block_signature` + `send_block_response` still run, and the signature for `B1` is broadcast to the network and counted by peers/the coordinator. [4](#0-3) 
4. The signer process restarts (or the DB write is retried later against a rebuilt/rolled-back store). SignerDB has no `signed_self` record for `B1` at height `H`.
5. A new proposal `B2` arrives for the same height `H` (different tenure or a re-org candidate). `handle_block_pre_commit` calls `get_signed_conflicts(H, hash(B2))`, which returns empty because `B1`'s signed state was never persisted. [10](#0-9) 
6. The signer signs `B2` as well, producing two signer signatures over conflicting blocks at height `H` — equivocation.
