### Title
Attacker-triggered `new` initialization failure lets a created lockup account keep the transferred NEAR while the factory refunds the same deposit again - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` batches `create_account`, `deploy_contract`, `transfer`, and `function_call("new", ...)` as actions on a single `Promise`, then attaches `on_lockup_create` as its callback. If the attacker supplies arguments that cause the `new` initialization call on the deployed lockup contract to panic, the preceding actions in that same receipt (account creation, code deployment, and the NEAR transfer) have already been applied and are not rolled back, yet the overall promise result is reported as failed, causing `on_lockup_create` to refund `attached_deposit` back to the caller. The predecessor thus recovers the full deposit while the newly created (attacker-named) account also retains the transferred NEAR, duplicating funds out of the factory.

### Finding Description
The binding the code implicitly relies on is:
`refunded_amount_to_predecessor + NEAR_left_in(lockup_account_id) == attached_deposit`

In `LockupFactory::create` (`lockup-factory/src/lib.rs:107-166`), a single `Promise::new(lockup_account_id)` chains `create_account()`, `deploy_contract(CODE.to_vec())`, `transfer(env::attached_deposit())`, and `function_call(b"new", ...)` [1](#0-0) . These are all actions scheduled on the *same* outgoing receipt. The chain is followed by `.then(ext_self::on_lockup_create(...))`, whose result depends only on whether that whole receipt executed successfully [2](#0-1) .

The callback `on_lockup_create` uses `is_promise_success()`, which just inspects `env::promise_result(0)` for `PromiseResult::Successful` [3](#0-2) . If that single boolean is `false`, the callback unconditionally refunds the full `attached_deposit` to `predecessor_account_id` via `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` [4](#0-3) .

Root cause: actions bundled into one receipt execute sequentially, and a later action's failure (the `new` function call panicking) does not undo the effects of earlier actions in the same receipt that already completed - the target account is created, the lockup WASM is deployed, and the `attached_deposit` NEAR has already been transferred into it before the `new` call runs and panics. The receipt is nonetheless reported to the callback as failed as a whole, so the factory believes lockup creation failed and refunds the deposit a second time from its own balance to the predecessor.

The attacker fully controls the inputs that reach the deployed lockup contract's `new` (e.g. `owner_account_id`, `vesting_schedule`/`VestingScheduleOrHash`, `release_duration`, `lockup_timestamp`, `whitelist_account_id`), so they can choose a combination that passes the factory's own (minimal) checks in `create` but causes `new` on the lockup contract to panic (invalid vesting schedule construction, invalid duration relationships, etc., as enforced inside `lockup/src/lib.rs::new`). None of the guards present - `assert_self()`, `is_promise_success()` - detect or compensate for the partial-execution state; they only gate whether the refund fires, not whether the deposit already delivered to the created account is reclaimed.

### Impact Explanation
NEAR leaves the factory's effective custody twice for one attached deposit: once as NEAR permanently held by the newly created (and now uninitialized, or attacker-influenced) lockup account, and once again as a refund transfer back to the predecessor. This duplicates funds that were never authorized to leave in that combined amount, and repeatable per attempt (each `create` call with the same failure-inducing pattern reproduces the double payout, limited only by `MIN_ATTACHED_BALANCE` cost per attempt). This matches the Critical impact category: NEAR moved out of a contract account by a party not entitled to it / a lockup-adjacent account created and funded outside its rightful accounting.

### Likelihood Explanation
The attacker needs only an unprivileged NEAR account and `MIN_ATTACHED_BALANCE` (3.5 NEAR) to call `create`, and needs to find (or already know) a parameter combination accepted by the factory's minimal validation but rejected by the lockup contract's `new` initializer. This is a low-cost, repeatable, self-service attack requiring no special privileges, keys, or foundation/owner involvement.

### Recommendation
Do not batch `transfer` (and ideally `deploy_contract`) together with the `function_call("new", ...)` in the same receipt as unconditional actions preceding the fallible initialization call. Instead, either: (1) create the account and deploy code first, verify success via a callback, and only transfer/initialize in a subsequent step so a failed `new` can be cleanly detected before funds move; or (2) have `on_lockup_create`, upon detecting failure, attempt to recover funds from the created account (e.g., via a follow-up transfer/self-destruct receipt) before refunding the predecessor, so the invariant `refunded + left_in_account == attached_deposit` holds under failure.

### Proof of Concept
Using the existing test harness in `lockup-factory/src/lib.rs` `#[cfg(test)] mod tests`:
1. Call `contract.create(...)` with `context.attached_deposit = ntoy(35)` as in `test_create_lockup_rollback`.
2. Simulate the receipt outcome as `PromiseResult::Failed` (representing the `new` call panicking after account creation/deploy/transfer already applied) as done in `test_create_lockup_rollback` at `lockup-factory/src/lib.rs:374-388`.
3. Assert `res == false` from `on_lockup_create` and that `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` was scheduled for the full `ntoy(35)`.
4. In an environment that models actual NEAR receipt semantics (e.g. `near-workspaces` sandbox), additionally assert that the created `lockup_account_id` account exists on-chain and holds a balance close to `ntoy(35)` (from the `transfer` action that ran before the panicking `function_call`).
5. Sum both sides: `refund_to_predecessor (ntoy(35)) + balance_left_in(lockup_account_id) (~ntoy(35)) != attached_deposit (ntoy(35))` - confirming the deposit was effectively duplicated rather than conserved.
