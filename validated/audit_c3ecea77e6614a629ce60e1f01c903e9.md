### Title
Unbounded per-call decode cost in `get_confirmed_signatures_for_address2` via `get_block_signatures_rev`/`get_complete_block` for attacker-chosen dense `before`/`until` slots - ([File: ledger/src/blockstore.rs])

### Summary
`Blockstore::get_confirmed_signatures_for_address2` resolves a `before` or `until` signature's position within its slot by calling `get_block_signatures_rev`, which fully decodes the entire block via `get_complete_block(slot, false)` and reverses all its transactions, rather than using an indexed/early-exit lookup. Because this full-block decode is invoked once for `before` and once (independently) for `until`, an attacker who controls signatures located in densely packed slots can force a single `getSignaturesForAddress` RPC call to fully decode and reverse up to two maximally-sized blocks.

### Finding Description
In `Blockstore::get_confirmed_signatures_for_address2` [1](#0-0) , resolving the `before` parameter calls `self.get_block_signatures_rev(slot)?` on the slot containing the `before` signature to determine its position and build an exclusion set [2](#0-1) . The same happens independently for `until`, on a potentially different slot [3](#0-2) .

`get_block_signatures_rev` itself calls `get_complete_block(slot, false)`, which reconstructs the full block (all entries, all transactions) from the blockstore, then reverses the transaction list to locate signature ordering [4](#0-3) . This is a full deserialization of the entire slot's transaction data regardless of how deep in the block the target signature is — there's no early-exit index lookup by signature within the slot; the cost is `O(transactions in slot)` for decode plus a linear scan/`position` call to find the target signature [5](#0-4) .

Since `before` and `until` are independent, attacker-supplied signatures (an unprivileged client only needs to know or have submitted transactions into two densely packed slots, then reference them as `before` and `until` in one `getSignaturesForAddress` call), a single RPC call can trigger two full-block decodes of two separately maximized slots — doubling the attacker-influenced cost within one request. No parameter or length check in `get_signatures_for_address` (rpc/src/rpc.rs, calling into this function [6](#0-5) ) bounds this cost by anything other than the natural protocol-level maximum block size (compute-unit/shred-count limits), which any validator would in any case need to process during normal block replay — but here the decode is redundant, additional work purely to service a read-only history query.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" category: a single JSON-RPC `getSignaturesForAddress` call's blockstore-side CPU/memory cost scales with the size (transaction count) of the on-chain block(s) that happen to contain the `before`/`until` signatures, which is influenced by the depth of attacker-created transactions in those blocks. The cost is not bounded by the RPC-level `limit` parameter at all — it's bounded only by however large a block can legitimately be, and it is paid twice (once for `before`, once for `until`) per call. Repeating this against many different addresses/signatures at the rate limit could meaningfully increase CPU load on the RPC-serving validator's blockstore-read path.

### Likelihood Explanation
Feasibility is straightforward: an unprivileged client can submit or observe transactions landing in densely packed slots (this is normal usage, not requiring any privileged access), record two signatures from two maximally-packed slots, and issue one `getSignaturesForAddress(before=sigA, until=sigB)` call at or below the permitted rate (one call per `CLUSTER_SLOT_TIME_TARGET / 2`). This is fully repeatable across different slot/address pairs.

### Recommendation
Avoid decoding the entire block merely to locate a single signature's position for exclusion-set purposes. Prefer an index-based lookup (e.g., using per-slot transaction index already stored via `write_transaction_status`/`transaction_index` in `AddressSignatures`, or a dedicated slot->ordered-signature index) rather than `get_complete_block` + linear scan + reverse. Alternatively, cache decoded blocks used for this purpose, or cap the cost by streaming/lazily decoding entries until the target signature is found instead of eagerly reconstructing and reversing the full transaction vector.

### Proof of Concept
Integration test plan (extends existing `test_get_confirmed_signatures_for_address2` in `ledger/src/blockstore/tests.rs`):
1. Insert one slot with a minimal number of transactions (e.g., 4) and record a signature `sig_sparse`.
2. Insert a second slot filled to the maximum practical transaction count for a single slot (e.g., as many entries/transactions as the test harness can construct, on the order of hundreds-to-thousands) and record a signature `sig_dense` placed early in program order (so lookup within `get_block_signatures_rev`'s reversed list is worst-case, i.e., near the end after `.rev()`).
3. Measure wall-clock time (via `std::time::Instant`) for `get_confirmed_signatures_for_address2(address, highest_slot, Some(sig_sparse), None, 1)` versus `get_confirmed_signatures_for_address2(address, highest_slot, Some(sig_dense), None, 1)`.
4. Assert that the dense-slot call's latency does not scale linearly/unboundedly with slot transaction count relative to the sparse-slot call (e.g., assert ratio below a fixed small bound), or that an early-exit lookup path exists that avoids full `get_complete_block` decode when only `before`/`until` position resolution is needed.
5. Repeat with both `before` and `until` pointing to two separate maximally-packed slots in a single call, asserting the total cost roughly doubles versus a single dense slot, demonstrating the doubling effect described.

Expected result under current code: latency scales with slot transaction count (no bound independent of block size), confirming the finding; a fix should show latency bounded by an explicit limit rather than block density.

            .transactions

            .filter_map(|transaction_with_meta| {
                transaction_with_meta
                    .transaction
                    .signatures
                    .into_iter()
                    .next()
            })
            .collect())
    }
