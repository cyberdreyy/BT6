This confirms v1.rs has no equivalent regression test for the LocallyAccepted duplicate check, unlike v2.rs which explicitly has `check_tenure_change_rejects_when_locally_accepted_block_exists`. The v1 path still uses `get_last_globally_accepted_block` at [1](#0-0) , confirming the asymmetric, unpatched duplicate-check logic.

### Title
v1 `validate_tenure_change_payload` misses LocallyAccepted sibling blocks, permitting a second signed tenure-start block per tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
Under the v1 chainstate protocol, `SortitionsView::validate_tenure_change_payload` checks for a duplicate tenure-start block using `SignerDb::get_last_globally_accepted_block`, which only matches blocks in `GloballyAccepted` state. A block the signer has locally accepted (signed_self set, i.e. `LocallyAccepted`) but that has not yet crossed the 70% global-acceptance threshold is invisible to this check, so a second, competing tenure-start proposal for the same tenure is not rejected with `DuplicateBlockFound` and can proceed to pre-commit and signing.

### Finding Description
The intended uniqueness property is: once a signer has put a signature over any block in a tenure (`LocallyAccepted` or `GloballyAccepted`, i.e. `has_signed_block_in_tenure`/`get_last_signed_block` semantics), no other tenure-start block for that same tenure should ever be signed by that signer. The v2 code path enforces exactly this — `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v2.rs` (lines 340-357) explicitly queries `signer_db.get_last_signed_block(&block.header.consensus_hash)`, with a comment stating "Only blocks we have signed (locally or globally accepted) count here." This was a deliberate regression fix, documented by the v2 test `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs` (lines 748-850), whose own comment says the check "previously ... used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change."

The v1 path, `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` (lines 461-519), still performs exactly that vulnerable check: it calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` (lines 505-509) and only raises `RejectReason::DuplicateBlockFound` if a `GloballyAccepted` block is found (lines 510-518). There is no corresponding regression test for v1 in `stacks-signer/src/chainstate/tests/v1.rs` — the fix and its test exist only on the v2 side, and `has_approved_block_in_tenure`/`get_last_signed_block` semantics were never wired into v1's duplicate check.

Exploit flow: an attacker who wins a sortition (single miner slot) proposes tenure-start block A for tenure T. A signer (the victim) locally accepts and signs A (`mark_locally_accepted`), setting `signed_self`, moving it to `LocallyAccepted` — but A has not yet reached global (70%) acceptance. The attacker (or another miner controlling the tenure) now crafts a second, competing tenure-start `BlockProposal` B for the same tenure T (same `consensus_hash`, different `signer_signature_hash`). On the v1-pinned victim signer, `validate_tenure_change_payload` runs `get_last_globally_accepted_block(T)`, which returns `None` because A is only `LocallyAccepted`. The duplicate check is skipped, `check_proposal` returns `Ok`, and B proceeds through the normal pipeline to pre-commit and, once it gathers enough pre-commits (or is otherwise driven to threshold, e.g. via other colluding/duplicate signer weight or activity from the attacker's own slot), `handle_block_pre_commit`/`mark_locally_accepted` signs B as well. The victim signer has now put its signature on two distinct tenure-start blocks (A and B) in the same tenure T.

### Impact Explanation
This breaks the uniqueness/safety guarantee that a signer signs at most one tenure-start block per tenure. Two signed sibling blocks in the same tenure is exactly the class of conflicting/equivocating signature the signer protocol is designed to prevent (the same property `has_signed_block_in_tenure`, `get_signed_conflicts`, and the v2 fix are built to protect). If enough signers are similarly v1-pinned or hit this same race, both A and B could separately accumulate the signatures needed for global acceptance, producing two canonical-looking tenure-start blocks for the same tenure — a chain-safety violation. This matches the Critical severity category: a signer signing a conflicting block within a tenure boundary.

### Likelihood Explanation
Preconditions: the signer must be running the v1 chainstate protocol (i.e., `chainstate::v1::SortitionsView` is the active code path rather than v2), and the tenure-start block must be at the `LocallyAccepted` stage (signed by this signer but not yet globally accepted) when the competing proposal arrives — a natural, commonly-occurring window in any tenure-start race since global acceptance is not instantaneous. The attacker needs only their own miner slot to craft the competing tenure-change block and gossip it as a normal `BlockProposal`/StackerDB message; no majority signer weight, no auth_token, and no other privileged access is required. This is repeatable on every tenure-start race under v1.

### Recommendation
Change v1's `validate_tenure_change_payload` duplicate check from `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` to `signer_db.get_last_signed_block(&block.header.consensus_hash)`, mirroring the v2 fix at `stacks-signer/src/chainstate/v2.rs` lines 344-345, so that any `LocallyAccepted` or `GloballyAccepted` block already signed in the tenure blocks a second tenure-start proposal from being signed. Add a v1-side regression test analogous to `check_tenure_change_rejects_when_locally_accepted_block_exists`.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/v1.rs`, adapted from `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs` (lines 756-850):
1. Use `setup_test_environment` from `v1.rs`'s test module to build a `SortitionsView` (v1) and `SignerDb`.
2. Insert an `existing_block_info` for the current tenure's `consensus_hash`, call `existing_block_info.mark_locally_accepted(false)` (sets `signed_self`, state `LocallyAccepted`, but not `GloballyAccepted`), and `signer_db.insert_block(&existing_block_info)`.
3. Build a second tenure-start `BlockProposal` `block` for the same `consensus_hash`, with `TenureChangePayload { cause: TenureChangeCause::BlockFound, .. }` plus a coinbase tx, signed by the miner key.
4. Call `sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block)` (v1's `check_proposal`, which dispatches to `validate_tenure_change_payload`).
5. Assert `matches!(result, Err(RejectReason::DuplicateBlockFound))`.
   - Before the fix: this assertion fails because `get_last_globally_accepted_block` returns `None` for the `LocallyAccepted` `existing_block_info`, so `result` is `Ok(())` — the equality (`has_signed_block_in_tenure`-equivalent duplicate protection) does not hold in v1.
   - After applying the recommended fix (switching to `get_last_signed_block`), the assertion passes, matching v2's already-fixed behavior.
