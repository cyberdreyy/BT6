## Answer

Based on the code reviewed, this is a valid finding: the script generator concatenates all commands (PreBuildScript, each job script line, PostBuildScript) into a single shell script buffer with no syntactic isolation between them, so an unterminated quote/heredoc in one command can swallow subsequent commands' text into its own syntax context.

### Title
Unisolated command concatenation allows attacker-controlled script line to swallow PostBuildScript/PreBuildScript into its own shell syntax context - (File: functions/script_legacy/internal/script_generator.go)

### Summary
`stepDispatch` builds a single `script` array as `[PreBuildScript, step.Script..., PostBuildScript]` [1](#0-0)  and hands it to `ScriptGenerator.GenerateScript`, which simply loops over the commands and writes each one's echo-trace line plus raw text into a single shared `strings.Builder`, with no per-command shell isolation (no subshell wrapping, no syntax validation, no separator beyond a newline) [2](#0-1)  and [3](#0-2) . Because all commands end up as literal text in one shell script executed as a whole, an attacker-controlled job script line containing an unbalanced quote or open heredoc marker can cause the runner-authored `PostBuildScript` (and its own trace/echo line) to be parsed as data within the attacker's open construct, rather than executed as an isolated command.

### Finding Description
`stepDispatch` (in `common/build_step_dispatch.go`) appends `shell.PreBuildScript`, then all `step.Script` lines from `build.Steps` (attacker-controlled via `.gitlab-ci.yml`'s `script:` array), then `shell.PostBuildScript`, into one flat `[]string` [1](#0-0) . This array is passed as the `script` input to the `builtin://script_legacy` step, which is consumed by `script_legacy.go`'s `Run` and fed into `internal.NewScriptGenerator(...).GenerateScript(commands)` [4](#0-3) .

`GenerateScript` writes a shebang/header, then iterates `commands` calling `ProcessCommand` for each, all writing into the *same* `strings.Builder` that becomes one shell script [5](#0-4) . `ProcessCommand`/`writeNormalCommand` simply writes an `echo` trace line for the command followed by the raw command text and a newline — there's no wrapping in `{ ... }`, no subshell, no `EOF`-style guaranteed termination between one command's text and the next command's echo/text [3](#0-2) .

Since bash parses the whole file as one contiguous script, any shell metacharacter imbalance in one array element (an unterminated `'`, `"`, backtick, or an open `<<EOF` heredoc with no matching terminator) causes everything textually following it — including the next command's `echo $'...'`/`echo "..."` trace line and the `PostBuildScript` command body — to be consumed as part of the open quoting/heredoc construct, changing from "isolated runner command" to "attacker-controlled string/heredoc body." This directly violates the stated invariant that "each command array element must be isolated by the script generator such that no element's syntax can span into the next" — no such isolation exists in `ProcessCommand`/`GenerateScript`.

There's no existing check that rejects or escapes commands for shell balance; `CommandFormatter.FormatLogLine` only escapes text for the `echo` trace line, not for the actual command execution, and no validation of quote/heredoc balance is performed anywhere in `command_processor.go` or `script_generator.go` [6](#0-5) .

### Impact Explanation
An attacker who controls the CI job's `script:` array (a normal, unprivileged pipeline author under `FF_USE_SCRIPT_TO_STEP_MIGRATION`) can craft a script line with, e.g., an open heredoc (`cat <<'EOF'`) with no terminating `EOF`. The runner's `PreBuildScript`/`PostBuildScript` text (used for git-checkout bookkeeping, cleanup, trace section markers, etc.) will then be consumed as heredoc *content* rather than executed as commands, or conversely the attacker's heredoc content will be extended to include text that was meant to be runner-injected commands, altering the intended pre/post script behavior. This matches the scoped impact: unintended commands executed under attacker-controlled shell state, and the runner's own injected pre/post-build commands potentially not running as isolated commands, but as swallowed/altered heredoc payload (e.g., cleanup commands are captured as heredoc data and never actually run, or their text becomes attacker-visible/attacker-influenced input to a command that consumes stdin).

### Likelihood Explanation
Requires: `FF_USE_SCRIPT_TO_STEP_MIGRATION` enabled (documented, opt-in-by-runner-operator feature flag) and an attacker who can define `.gitlab-ci.yml` script content for a job on that runner — both realistic for a normal pipeline author on a project targeting a runner with the flag on. The exploit is deterministic and trivially reproducible with a single crafted job script line (no timing/race conditions, no privilege escalation needed beyond normal CI authoring).

### Recommendation
Isolate each command in its own syntactic scope in `ProcessCommand`/`GenerateScript`, e.g., wrap each command in a subshell/braced block with an internally validated heredoc delimiter, or emit each command via a mechanism that cannot be affected by unbalanced quoting in a prior command (e.g., write each command to a temp file and `source`/execute it separately, or use `bash -c` per command with proper single-argument passing instead of literal concatenation). At minimum, validate/reject script lines containing unterminated heredoc markers or unbalanced quotes before concatenation in `stepDispatch`/`GenerateScript`.

### Proof of Concept
Go unit test in `functions/script_legacy/internal/script_generator_test.go`:
```go
func TestGenerateScript_UnterminatedHeredocSwallowsSubsequentCommands(t *testing.T) {
    gen := NewScriptGenerator(ScriptGeneratorConfig{ShellPath: "/bin/bash"})

    commands := []string{
        "pre_build_marker",
        "cat <<'EOF'\nattacker payload",   // unterminated heredoc
        "post_build_marker",
    }
    script := gen.GenerateScript(commands)

    // Execute script with bash and capture behavior: post_build_marker should
    // execute as an isolated command, not be swallowed into the heredoc.
    cmd := exec.Command("bash", "-c", script)
    out, _ := cmd.CombinedOutput()

    // Assert failure of invariant: post_build_marker output does not appear
    // as an executed command (it gets consumed as heredoc data instead).
    assert.NotContains(t, string(out), "post_build_marker: command not found") // or check exit status / that no isolation occurred
}
```
Expected observation confirming the bug: the script hangs waiting for heredoc terminator (or, if EOF is reached at end of file, `post_build_marker` text is consumed as heredoc content and never executed as a command), demonstrating no isolation between commands.

func (g *ScriptGenerator) GenerateScript(commands []string) string {
	var buf strings.Builder

	buf.WriteString(g.header.Generate())

	if g.gitLabEnvFile != "" {
		// Export GITLAB_ENV so user commands can append KEY=VALUE pairs to it,
		// then source any variables written by previous stages. This mirrors
		// what AbstractShell.writeExports does for the legacy shell path.
		fmt.Fprintf(&buf, "export GITLAB_ENV=%q\n", g.gitLabEnvFile)
		fmt.Fprintf(
			&buf,
			"if [ -f %q ]; then while read -r line; do export \"$line\" || true; done < %q; fi\n\n",
			g.gitLabEnvFile,
			g.gitLabEnvFile,
		)
	}

	for i, cmd := range commands {
		g.processor.ProcessCommand(&buf, i, cmd)
	}

	return buf.String()

// FormatLogLine generates the echo statement to log a command.
// Returns different formats based on POSIX mode setting.
func (f *CommandFormatter) FormatLogLine(command string) string {
	command = ansiGreen + commandPrefix + f.getDisplayCommand(command) + ansiReset

	if f.posixMode {
		return fmt.Sprintf("echo %s", EscapeForPosix(command))
	}

	return fmt.Sprintf("echo $'%s'", EscapeForAnsiC(command))
}
