### Title
Stale per-epoch instant-withdraw counters inflate `defaultPendingClaimBasis` and dilute default recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the FrankenDAO issue where `proposalsCreated` was incremented instead of `proposalsPassed` (one accounting counter updated where a sibling should have been, corrupting a later weighted calculation), `IdleCreditVault` maintains paired per-user/per-epoch instant-withdraw counters. `requestInstantWithdraw` increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` together, but `claimInstantWithdrawRequest` only clears `instantWithdrawsRequests[_user]` — the two per-epoch counters are never decremented. The stale `instantWithdrawClaimsByEpoch` total is later added to the default recovery claim basis whenever `pendingInstantWithdraws != 0`, diluting the recovery price for honest claimants.

### Finding Description
At `IdleCreditVault.sol:366-374`, an instant withdraw request updates three counters:

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

`pendingInstantWithdraws` is decremented by `collectInstantWithdrawFunds` (`:398-403`), but `claimInstantWithdrawRequest` (`:380-393`) burns the user's receipt and zeroes only `instantWithdrawsRequests[_user]`:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` retain the full basis of receipts that were already paid out.

`defaultPendingClaimBasis` (`:644-649`) then computes:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

So if the instant queue was only partially funded — `pendingInstantWithdraws` still non-zero because `collectInstantWithdrawFunds` was called for less than the total — while some users already claimed (i.e., already received underlying and had their receipts burned), the entire epoch claim total, including the already-paid claims, is added to the recovery basis. `finalizeDefaultRecovery` (`:679-688`) computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, so an inflated `totalBasis` lowers the price for every legitimate claimant, and the phantom share of the reserve is never claimable — it remains locked in the strategy as unclaimable recovery dust.

### Impact Explanation
Like the external report, this is a wrong/stale-counter accounting bug whose impact is conditional: it only materializes when an epoch's instant-withdraw queue is partially funded at default finalization. In that scenario, the recovery ratio is diluted by already-settled claims. Example: epoch instant claims total 1,000 (500 already claimed and paid, 500 still pending). `instantWithdrawClaimsByEpoch` still reports 1,000, so the reserve is split across 1,000 of basis instead of 500 — pending claimants recover half of what they should, and the remaining reserve is permanently stranded in the contract. That is a quantified loss to honest pending claimants plus permanently frozen recovery funds.

### Likelihood Explanation
Requires a specific but plausible sequence: instant withdraw requests in an epoch → partial funding via `collectInstantWithdrawFunds` (or funding where some users claim before the rest) → borrower default and `finalizeDefaultRecovery` while `pendingInstantWithdraws != 0`. All steps are reachable through normal epoch/default flows; no privileged misbehavior is needed beyond the honest manager/borrower actions that trigger default finalization. The trigger condition (partial instant funding at default time) is narrower than the generic path, which is why severity is Medium rather than High.

### Recommendation
Mirror the normal-withdraw per-epoch accounting: when `claimInstantWithdrawRequest` (and `_claimDefaultedInstantWithdrawRequest`) pays a receipt, decrement `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and `instantWithdrawClaimsByEpoch[requestEpoch]` by the claimed amount, so `defaultPendingClaimBasis` only counts still-outstanding claims. Alternatively, track per-epoch unfunded instant claims separately and subtract claimed amounts at claim time.

### Proof of Concept
Foundry fork test outline (deterministic, no external oracle):

```solidity
// Setup: epoch running, CDO has deposits, instant-withdraw enabled.
uint256 amount = 1000 * ONE_SCALE;

// 1. Two users request instant withdrawals in the same epoch.
cdoEpoch.requestInstantWithdraw(user1Shares, user1); // 500
cdoEpoch.requestInstantWithdraw(user2Shares, user2); // 500
// instantWithdrawClaimsByEpoch[epoch] == 1000; pendingInstantWithdraws == 1000

// 2. CDO collects only part of the instant queue.
strategy.collectInstantWithdrawFunds(500); // pendingInstantWithdraws == 500
// user1 claims and is paid in full.
strategy.claimInstantWithdrawRequest(user1);
// instantWithdrawsRequests[user1] == 0 but
// instantWithdrawClaimsByEpoch[epoch] is still 1000  <-- stale counter

// 3. Borrower defaults; manager finalizes recovery.
// defaultPendingClaimBasis() = pendingWithdraws + 1000
// instead of pendingWithdraws + 500.

uint256 basis = strategy.defaultPendingClaimBasis();
assertEq(basis, pendingWithdrawsExpected + 1000); // inflated by 500

// 4. finalizeDefaultRecovery computes recoveryPrice over the inflated basis:
// recoveryPrice is ~half of correct value; user2's defaulted instant claim
// recovers only ~50% of what it should, and the difference is stranded
// in the strategy as unclaimable recovery dust.
```

Key assertion: `instantWithdrawClaimsByEpoch[epochNumber]` remains 1000 after `user1` was fully paid, while only 500 of claims are still outstanding — the counter was incremented in `requestInstantWithdraw` but never decremented in `claimInstantWithdrawRequest`, directly mirroring the FrankenDAO "wrong variable accounting" bug class.

Note: verification of the exact CDO-side sequence that reaches `claimInstantWithdrawRequest` before full instant funding (whether the CDO permits a claim while `pendingInstantWithdraws` is still non-zero) could not be fully traced within the available context; if the CDO only allows claims after `pendingInstantWithdraws == 0`, the stale-counter path becomes unreachable and this reduces to incorrect-but-dormant accounting, same as the original report's "no current impact" caveat.
