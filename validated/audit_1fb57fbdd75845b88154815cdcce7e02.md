## Analysis

I traced the "seller != buyer not checked" bug class to the Aptos `staking_contract` module, where the analogous unchecked-distinctness invariant is **`staker != operator`**. `create_staking_contract_with_coins` never asserts this [1](#0-0) , so a staker can create a contract naming themselves as the operator.

The `distribution_pool` (a `pool_u64::Pool`) is keyed only by `address` [2](#0-1) . `unlock_stake` first calls `request_commission_internal`, which does `add_distribution(operator, staking_contract, operator, commission_amount)` [3](#0-2) , then calls `add_distribution(operator, staking_contract, staker_address, amount)` for the staker's own withdrawal [4](#0-3) . Since `pool_u64::buy_in`/`add_shares` merges shares under one key [5](#0-4) , if `staker == operator` both distributions collapse into a single shareholder entry.

In `distribute_internal`, the payout loop checks `if (recipient == operator) { recipient = beneficiary_for_operator(operator); }` [6](#0-5) . When staker == operator, this check is always true for the merged entry, so the **entire distribution (commission + the staker's own principal withdrawal) is redirected to whatever `beneficiary_for_operator` is set** via `set_beneficiary_for_operator` [7](#0-6) , instead of splitting commission-to-beneficiary and principal-to-staker.

### Title
Merged commission/principal distribution shares wrongly redirect staker's own stake withdrawal to `beneficiary_for_operator` when `staker == operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract` never enforces `staker != operator`. Because the internal `distribution_pool` is keyed by address, and `distribute_internal` redirects any distribution keyed by the `operator` address to `beneficiary_for_operator(operator)`, a self-staking user (staker == operator) who sets a beneficiary for commission collection will have their own principal stake withdrawals silently redirected to that beneficiary address as well, instead of returning to themselves.

### Finding Description
`create_staking_contract_with_coins` allows `operator == staker` with no distinctness check [8](#0-7) . `unlock_stake` calls `request_commission_internal` (which buys commission shares keyed by `operator`) and then `add_distribution` for the staker's principal keyed by `staker_address` [9](#0-8) . When `staker_address == operator`, both calls target the same shares-pool key, merging commission and principal into one balance. `distribute_internal`'s recipient-substitution logic `if (recipient == operator) { recipient = beneficiary_for_operator(operator) }` [10](#0-9)  cannot distinguish "this was the operator's commission" from "this was the staker's principal that happens to share the operator's address" — it redirects the whole merged amount.

### Impact Explanation
This corrupts share/recipient accounting: the staker's own principal stake gets non-consensually routed to a third-party beneficiary account instead of the staker, matching the "wrong account credited" impact category. Any legitimate use of `set_beneficiary_for_operator` for commission handling by a self-staking user will cause all subsequent principal withdrawals via `unlock_stake` to also go to the beneficiary rather than the staker, i.e., loss/misdirection of principal stake, not merely commission.

### Likelihood Explanation
Requires the unprivileged staker to create a staking contract naming themselves as the operator (permitted, no check blocks it) and to set a beneficiary via `set_beneficiary_for_operator`. This is a self-inflicted misconfiguration path rather than a cross-account attack by a third party, since operator role and beneficiary-setting rights are already held by the same actor who is harmed. This weakens the severity: it is not an external-attacker fund theft, but rather a state where the protocol's `distribute_internal` logic breaks its own accounting invariant (correctly split commission vs. principal payouts) under a configuration that the contract itself permits without warning.

### Recommendation
Enforce `staker != operator` in `create_staking_contract_with_coins`/`create_staking_contract`, or track distribution entries with a dedicated flag/type (commission vs. principal) instead of relying solely on `recipient == operator` to decide the beneficiary redirect.

### Proof of Concept
1. User A calls `staking_contract::create_staking_contract` with `operator = A` (self-staking), commission > 0.
2. A calls `set_beneficiary_for_operator(A, B)` to route commission to account B.
3. Stake pool earns rewards.
4. A calls `unlock_stake(A, A, amount)`: `request_commission_internal` buys commission shares keyed by `A`; then `add_distribution` buys principal-withdrawal shares also keyed by `A` — merged into one pool entry.
5. Lockup expires; `distribute` is called. In `distribute_internal`, the merged entry's `recipient == operator (A)` is true, so the entire merged amount (commission + principal) is deposited to B instead of splitting principal back to A.

I was unable to fully verify whether `staking_contract::create_staking_contract*` is reachable through `vesting.move`'s `create_vesting_contract` with `operator == admin_derived_staker` (the resource account signer), since the vesting flow's staker is always the vesting contract's own resource account rather than a plain user account, which would make the self-staker path less directly reachable there; this analysis is scoped to direct calls into `staking_contract` by an ordinary user.

        };

            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,

            }

    public fun buy_in(self: &mut Pool, shareholder: address, coins_amount: u64): u64 {
        if (coins_amount == 0) return 0;

        let new_shares = self.amount_to_shares(coins_amount);
        assert!(MAX_U64 - self.total_coins >= coins_amount, error::invalid_argument(EPOOL_TOTAL_COINS_OVERFLOW));
        assert!(MAX_U64 - self.total_shares >= new_shares, error::invalid_argument(EPOOL_TOTAL_COINS_OVERFLOW));

        self.total_coins += coins_amount;
        self.total_shares += new_shares;
        self.add_shares(shareholder, new_shares);
        new_shares
    }

    /// Add the number of shares directly for `shareholder` in `self`.
    /// This would dilute other shareholders if the pool's balance of coins didn't change.
    fun add_shares(self: &mut Pool, shareholder: address, new_shares: u64): u64 {
        if (self.contains(shareholder)) {
            let existing_shares = self.shares.borrow_mut(&shareholder);
            let current_shares = *existing_shares;
            assert!(MAX_U64 - current_shares >= new_shares, error::invalid_argument(ESHAREHOLDER_SHARES_OVERFLOW));

            *existing_shares = current_shares + new_shares;
            *existing_shares
        } else if (new_shares > 0) {
            assert!(
                self.shareholders.length() < self.shareholders_limit,
                error::invalid_state(ETOO_MANY_SHAREHOLDERS),
            );

            self.shareholders.push_back(shareholder);
            self.shares.add(shareholder, new_shares);
            new_shares
        } else {
            new_shares
        }
    }
