### Title
Attacker-controlled `decimals` field in SPL Token "Checked" instructions causes misreported token amounts in RPC-parsed transaction data - (File: `transaction-status/src/parse_token.rs`)

### Summary
The transaction-status crate's `parse_token` function, used to build `jsonParsed` instruction output for `getTransaction`, `getConfirmedTransaction`, `getBlock`, and transaction-subscription notifications, computes the human-readable `tokenAmount`/`feeAmount` fields directly from the `decimals` value embedded in the raw instruction data supplied by the transaction sender, without cross-checking it against the real decimals of the referenced mint account. This mirrors the DODO `GatewayTransferNative` bug class: a value that should be validated against a second, independent source of truth (the actual mint) is instead trusted blindly from user-controlled input, producing incorrect derived output.

### Finding Description
For every "Checked" SPL Token instruction variant, the parser builds a `SplTokenAdditionalDataV2` purely from the `decimals` field parsed out of the instruction bytes, and immediately uses it to compute the displayed `UiTokenAmount`: [1](#0-0) 

The same pattern repeats for `ApproveChecked`, `MintToChecked`, `BurnChecked`, and `TransferCheckedWithFee`: [2](#0-1) [3](#0-2) 

The conversion itself simply divides the raw `amount` by `10^decimals` (or applies interest/scaling configs) with no sanity check against the mint that is also present in the same instruction's account list: [4](#0-3) 

On-chain, the SPL Token / Token-2022 program does validate that the supplied `decimals` matches the target mint's actual decimals, and will fail execution if they don't match — but this validation only happens at execution time. The RPC-side instruction parser in `transaction-status` runs unconditionally on every instruction in every transaction returned by `getTransaction`/`getBlock`, regardless of whether that transaction succeeded or failed. Failed transactions are still stored and returned (with an `err` field populated), and their instructions are still parsed and displayed with the attacker-chosen `decimals`.

### Impact Explanation
An unprivileged user can submit (or simply construct, without needing it to land, since even a transaction that fails is retained and queryable) a `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked`/`TransferCheckedWithFee` instruction whose `decimals` field is arbitrary and unrelated to the real mint's decimals. When any client (block explorer, wallet, monitoring service, indexer) queries that transaction via `getTransaction`/`getBlock`/`getConfirmedTransaction`/pubsub with `encoding: jsonParsed`, the parsed `tokenAmount`/`uiAmount`/`uiAmountString` values shown will be arbitrarily wrong — e.g., a transfer of a small raw amount can be displayed as an enormous "UI amount" or vice versa. This is a decoder misreporting bug: the JSON-RPC response returns wrong derived data for a query, matching the accepted impact class of "decoder panic and misreporting."

### Likelihood Explanation
This is trivially reachable by any unprivileged user: they only need to submit or construct a transaction containing a Checked-variant SPL Token instruction with a mismatched `decimals` byte. No special privileges, validator/peer role, or multi-call sequencing is required, and the bad data is served to any caller of standard, single-call JSON-RPC methods (`getTransaction`, `getBlock`).

### Recommendation
When parsing "Checked" token instructions for display, cross-check the caller-supplied `decimals` against the actual decimals of the mint account referenced in the instruction (fetched from the ledger/bank state) before using it to compute `tokenAmount`, or clearly flag/skip UI-amount computation when parsing on a best-effort basis for failed transactions, so RPC consumers cannot be shown fabricated token amounts derived purely from unchecked user input.

### Proof of Concept
1. Construct a `spl_token_2022_interface::instruction::transfer_checked` instruction with `amount = 1_000_000` and `decimals = 0`, targeting a mint that actually has `decimals = 9`.
2. Submit the transaction (it will fail on-chain because the program validates decimals against the mint), or simply have it stored via any submission path.
3. Call `getTransaction` with `{"encoding": "jsonParsed"}` on the transaction signature.
4. Observe the returned `parsed.info.tokenAmount` reflects `decimals: 0` (i.e., displays as `1000000` tokens) rather than the true value implied by the mint's real 9 decimals, as computed in [1](#0-0)  and [4](#0-3) .

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
