## Analysis

The Superfluid incident's root cause was a trusted "forwarder" entry point (`callAgreement`/`ctx`) that faithfully validated the *outer* call but blindly re-dispatched attacker-controlled calldata to an inner target, letting the attacker redirect fund transfers to unauthorized recipients. The closest reachable analog on Base is the EIP-8130 **policy gate**, which enforces `call.to == policy_target` only at the outermost AA call dispatch and has no visibility into calls made *by* that target.

### Title
Policy-gated EIP-8130 session actors can fully bypass their intended call-target restriction via the enshrined `DEFAULT_ACCOUNT` forwarder - (File: `crates/common/evm/src/eip8130.rs`)

### Summary
An account owner grants a session actor `SCOPE_POLICY` and a `policy_target`, believing the actor is scoped to only interact with that one target contract. `Eip8130Executor::execute_calls` enforces this by rejecting any dispatched call whose `call.to` differs from `policy_target`. However, if `policy_target` is (or ever ends up being) the account's own enshrined smart-account address — `Eip8130Contracts::DEFAULT_ACCOUNT`, the code every code-less EOA auto-delegates to — the gate is satisfied by any call to that address, and `DEFAULT_ACCOUNT.execute(target, value, data)` / `executeBatch(...)` then forwards **arbitrary** `target`/`data` with the account's full authority. The protocol only checks the first hop; the actual arbitrary-call forwarding one level deeper is never constrained.

### Finding Description
The gate is implemented as a single equality check per call, purely on the top-level `call.to`: [1](#0-0) 

`policy_target` is resolved once from `policy_manager(sender, actorId)` and is meant to be *the specific contract the session actor is authorized to touch*: [2](#0-1) 

The enshrined `DEFAULT_ACCOUNT` implementation is a generic forwarder (`execute`/`executeBatch`) reachable by any code-less EOA that has not set an explicit delegation, since the executor auto-delegates it: [3](#0-2) [4](#0-3) 

Test fixtures show `set_policy` accepting an arbitrary `target` address and the gate accepting any call whose `to` equals that stored target, with no further constraint applied once the call reaches its destination: [5](#0-4) [6](#0-5) 

If `target` in `seed_gated_sender`/`set_policy` is the sender's own `DEFAULT_ACCOUNT`-delegated address (a natural configuration for "let this session key operate my wallet"), the gate degenerates to a no-op restriction: any `call.to == sender` passes, and the forwarded `execute(target, value, data)` inside that call is completely outside the protocol's policy check, exactly as `Minimal7702Account`-style forwarders demonstrate the pattern used in this codebase's own test fixtures for arbitrary target/calldata forwarding: [7](#0-6) 

This mirrors Superfluid precisely: the outer authorization surface (there, `callAgreement`; here, the EIP-8130 policy gate) validates only the entry point, while the entry point itself is a raw forwarder that executes attacker/session-key-chosen calldata against an arbitrary, unvalidated destination.

### Impact Explanation
A session actor intended to be scoped to a single dApp (e.g., "this key may only call the DEX router") instead obtains unrestricted call authority over the account whenever `policy_target` resolves to a generically-forwarding contract such as `DEFAULT_ACCOUNT`. Because `calls` are dispatched `from sender` with the account's real balance and approvals, a leaked or over-privileged session key can drain funds, revoke/modify unrelated approvals, or invoke any contract, defeating the entire security purpose of `SCOPE_POLICY`. This is a concrete unauthorized-operation/fund-theft primitive reachable purely from a single signed EIP-8130 transaction crafted by the session-key holder.

### Likelihood Explanation
Likelihood depends on how policy targets are chosen by wallet-provisioning tooling/dApps. If any first-party or third-party flow ever sets `policy_target` to the account's own smart-account address (a plausible pattern for "let this key manage my account"), the restriction silently collapses to `SCOPE_OPERATOR`-equivalent power without any signal to the granting party, since both grants look identical from a `set_policy` call except for the address argument. The protocol provides no safeguard (e.g., rejecting `policy_target == sender` or `policy_target` code that matches a known forwarder) to prevent this misconfiguration from becoming a full authority escalation.

### Recommendation
Either (a) forbid `policy_target == sender`/known-forwarder addresses at `set_policy` time, or (b) extend the policy gate semantics to also validate the selector/first-level `target` argument when the resolved `policy_target`'s code is a recognized generic-forwarder pattern (`DEFAULT_ACCOUNT`, ERC-1167 proxies matching `erc1167_proxy_code_hash`, etc.), so the gate's documented guarantee ("every `call.to` must equal this") cannot be satisfied by a contract whose only job is to relay arbitrary calldata onward.

### Proof of Concept
1. Account `A` (code-less EOA) is auto-delegated to `DEFAULT_ACCOUNT` on first EIP-8130 transaction, per `Self::auto_delegate_codeless_sender`.
2. Owner authorizes session actor `S` with `SCOPE_POLICY` and `policy_target = A` (intending "S may operate my account"), via `AccountConfigurationStorage::set_policy`.
3. `S` signs an EIP-8130 transaction with `calls = [[Call { to: A, data: executeCall{ target: VICTIM_TOKEN, value: 0, data: transferCall{to: attacker, amount: ALL} } }]]`.
4. In `execute_calls`, the gate check `call.to != outcome.policy_target` passes because `call.to == A == policy_target`.
5. The dispatched call executes `DEFAULT_ACCOUNT.execute(VICTIM_TOKEN, 0, transferCall)` in `A`'s context, which then calls `VICTIM_TOKEN.transfer(attacker, ALL)` with no further protocol-level validation — funds move to an address never authorized by the policy grant. [1](#0-0)

    /// Seeds a policy-gated k1 actor for `account`, authorized to the `signer`
    /// key and gated to `target`, then commits it. POLICY-only (plus payer/nonce
    /// grants): OPERATOR would override POLICY and leave the sender ungated.
    fn seed_gated_sender(
        evm: &mut BaseEvm<InMemoryDB, NoOpInspector, PrecompilesMap>,
        account: Address,
        signer_addr: Address,
        target: Address,
    ) {
        use base_precompile_storage::Handler as _;
        let actor_id = AccountConfigurationStorage::self_actor_id(signer_addr);
        {
            let ctx = evm.ctx_mut();
            let internals = EvmInternals::from_context(ctx);
            let mut provider = JournalStorageProvider::new(internals, Address::ZERO);
            StorageCtx::enter(&mut provider, |sctx| {
                let mut acc = AccountConfigurationStorage::new(sctx);
                acc.actors
                    .at_mut(&actor_id)
                    .at_mut(&account)
                    .write(pack_actor(
                        Eip8130Constants::K1_AUTHENTICATOR,
                        Eip8130Constants::SCOPE_POLICY
                            | Eip8130Constants::SCOPE_SELF_PAYER
                            | Eip8130Constants::SCOPE_NONCE,
                        0,
                    ))
                    .unwrap();
                acc.set_policy(account, actor_id, target, B256::ZERO).unwrap();
            });
        }
        let state = evm.ctx_mut().journal_mut().finalize();
        revm::DatabaseCommit::commit(evm.ctx_mut().journal_mut().db_mut(), state);
    }
