## Analysis

This repository's multisig contracts implement the "K of N" custody scheme central to the report's bug class: an operation is authorized only if a specific *quorum of currently-entitled signers* approves it. Just as the Sequence bug let a stale/foreign signature count toward authorization it was never meant to grant, these NEAR multisig contracts let a **removed member's prior confirmation continue to count toward the quorum** after that member has been revoked — breaking the binding `confirmations recorded == confirmations from currently-live members`.

### Root cause

In `multisig2/src/lib.rs`, `delete_member` only cleans up requests that the removed member *created*, not confirmations that member cast on *other* still-pending requests: [1](#0-0) 

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
```

This filters `self.requests` by `r.member == member` — i.e. requests *added* by the member being deleted — and wipes their confirmation sets. It never scans `self.confirmations` for entries elsewhere that contain the departing member's identity string as a *confirmer* of someone else's request.

`confirm` then blindly trusts the stored confirmation count toward the threshold, without re-validating that every confirming identity is still a current member: [2](#0-1) 

The identical pattern exists in the older `multisig` contract, where `DeleteKey` only purges requests whose `signer_pk` equals the removed key, leaving that key's confirmations on other requests intact: [3](#0-2) [4](#0-3) 

### Exploit path

1. Multisig has members `{A, B, C}`, `num_confirmations = 2`.
2. `A` adds a sensitive request `R` (e.g. `Transfer`, `AddKey`, or `FunctionCall`).
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1/2, not yet executed).
4. Members later approve a separate `DeleteMember{B}` request and it executes, removing `B` from `self.members`. `delete_member` only inspects requests *added by* `B`; `R` was added by `A`, so its confirmation set is untouched — `confirmations[R]` still contains `B`.
5. `A` (a legitimate, still-live member) calls `confirm(R)`. The check `confirmations.len() as u32 + 1 >= self.num_confirmations` becomes `1 + 1 >= 2` → **true**, and `R` executes with only one currently-authorized approval (`A`) plus a stale approval from an already-revoked member (`B`).

The result: a request executes below the real, live-member threshold — funds can be transferred, a full-access key added, or an arbitrary `FunctionCall` performed by the contract with fewer genuine approvals than `num_confirmations` requires.

### Why this matches the report's bug class

The Sequence report's core flaw was that an authorization artifact (a signature) was accepted without being bound to the identity/context it was actually meant to authorize (the specific wallet). Here, a confirmation artifact (a member's approval) is accepted without being re-validated against that member's *current* membership status, so it silently outlives the revocation event it should have been invalidated by.

### Title
Stale confirmations from removed multisig members count toward quorum, allowing execution below the live-member threshold - (`multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`delete_member` (multisig2) and the `DeleteKey` action (multisig) only remove confirmations for requests that the removed member/key *created*. Confirmations that member cast on *other* pending requests as a confirmer are never purged. `confirm` counts these stale entries toward `num_confirmations` without re-checking that every confirming identity is still a current member, allowing a request to execute with fewer genuinely live approvals than the configured threshold.

### Finding Description
`add_request`/`confirm` record approvals keyed by a member's stringified identity in `self.confirmations: LookupMap<RequestId, HashSet<String>>` ( [5](#0-4) ). When a member is removed via `MultiSigRequestAction::DeleteMember`, `delete_member` filters `self.requests` for entries added *by* that member and clears their confirmation sets ( [6](#0-5) ) — but it never inspects the `confirmations` map for other requests where the removed member appears merely as a confirmer, not as the requester. Those stale entries remain and are counted the next time `confirm` is called on that request, satisfying the threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` with a mix of live and revoked approvals.

The same defect exists in the original `multisig` contract's `DeleteKey` handling, which cleans up only requests whose `signer_pk` matches the deleted key ( [3](#0-2) ), leaving that key's confirmations on other requests intact for `confirm` to still tally ( [7](#0-6) ).

### Impact Explanation
This breaks the fundamental custody invariant of a K-of-N multisig: `confirmations counted == confirmations from currently-live members`. An attacker or colluding subset of members who no longer control `num_confirmations` live signers can still push through arbitrary `Transfer`, `AddKey` (full access key), `DeployContract`, or `FunctionCall` actions on the multisig-controlled account, because a revoked member's leftover approval papers over the missing live approval. Per the impact criteria, this is a multisig request executed below threshold — Critical.

### Likelihood Explanation
Requires no privileged access beyond being an ordinary current member of the multisig (which any of the N members inherently is) and relies only on the normal operational sequence of: add request → partial confirm → later member removal → completing confirmation. Multisig membership changes over time are an expected, common operation, so the sequence of events needed is entirely realistic and does not require the foundation, a redeploy, or any out-of-scope actor.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), scan all pending requests' confirmation sets and strip any entry corresponding to the removed member's identity, not just requests they authored. Alternatively, have `confirm` re-validate every entry in the stored confirmation set against `self.members` before counting it toward the threshold, discarding (or lazily purging) confirmations from identities that are no longer members.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As `A`, call `add_request` with a sensitive `MultiSigRequest` (e.g. `Transfer`) → `request_id = R`.
3. As `B`, call `confirm(R)` → `confirmations[R] = {B}` (not yet executed, 1 < 2).
4. Separately, get a `DeleteMember{member: B}` request created and confirmed by 2 members and executed, removing `B` from `self.members` (`delete_member` at [1](#0-0) ) — note `confirmations[R]` is untouched since `R` was added by `A`, not `B`.
5. As `A`, call `confirm(R)` → `confirmations.len() + 1 == 2 >= num_confirmations(2)` → `execute_request(R)` runs, moving funds/executing the action, despite `B` no longer being a valid member and only one live member (`A`) having actually approved.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
