One more targeted check on how instant-withdraw funding links to receipts, and the CDO-side gating.### Title
Unfunded instant-withdraw receipts are paid from the pooled vault balance reserved for matured normal-withdraw claims — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the zkSync bug — where a proof was verified without linkage to the committed blocks it was supposed to cover — `IdleCreditVault.claimInstantWithdrawRequest` pays out a recorded instant-withdraw receipt without checking that the funds earmarked for that receipt (`pendingInstantWithdraws` collected via `collectInstantWithdrawFunds`) were actually received. The receipt ("proof") is validated against the vault's whole underlying balance, which also contains underlying collected at `stopEpoch` via `collectWithdrawFunds` to back matured normal withdraw receipts. An unprivileged user can therefore claim an unfunded instant receipt and steal underlying reserved for honest claimants.

### Finding Description
`requestInstantWithdraw` mints a 1:1 strategy-token receipt and records it in `instantWithdrawsRequests[_user]` / `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and bumps `pendingInstantWithdraws` [1](#0-0) . Funding is asynchronous: after `startEpoch`, the manager calls `getInstantWithdrawFunds` (which invokes `collectInstantWithdrawFunds`, decreasing `pendingInstantWithdraws` and pulling underlying from the CDO) only once `instantWithdrawDelay` has passed [2](#0-1) .

`claimInstantWithdrawRequest` then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [3](#0-2) 

`_transferFundedClaim` only excludes `defaultRecoveryReserve` from the transferable balance; it does not check that the instant receipt being claimed was ever funded — i.e., it never inspects `pendingInstantWithdraws` or `instantWithdrawsRequestsByEpoch` [4](#0-3) . The CDO-side entry point checks only `allowInstantWithdraw` [5](#0-4) , which is a global availability flag, not a per-request funding check.

Meanwhile, `collectWithdrawFunds` pulls underlying into this same vault to back matured normal withdraw receipts (`pendingWithdraws`), where it sits until each user calls `claimWithdrawRequest` [6](#0-5) . There is no per-purpose bucket isolation — only the post-default `defaultRecoveryReserve` is ring-fenced.

Attack sequence (instant mode, running epoch):
1. Honest users' normal withdraw requests from the previous buffer are funded at `stopEpoch` via `collectWithdrawFunds`; the underlying now sits in the vault backing `withdrawsRequests`.
2. Attacker (a KYC'd AA holder) calls `cdoEpoch.requestWithdraw` during the buffer; the APR delta routes it to `requestInstantWithdraw`, minting a receipt and increasing `pendingInstantWithdraws`.
3. `startEpoch` runs; the CDO has insufficient idle liquidity to prefund the instant queue (or `getInstantWithdrawFunds` simply has not been called yet within `instantWithdrawDelay`).
4. Attacker immediately calls `cdoEpoch.claimInstantWithdrawRequest`. `allowInstantWithdraw` is true, the receipt exists, and the vault balance — made up of honest users' funded normal claims — is sufficient, so `_transferFundedClaim` pays out.
5. When honest claimants later call `claimWithdrawRequest`, `_transferFundedClaim` reverts on insufficient balance: their matured, already-funded receipts are unpayable.

The test suite implicitly confirms the only defense is balance sufficiency: `testClaimInstantWithdrawRequest` expects a revert purely because "there are no underlyings available" [7](#0-6)  — no accounting guard rejects an unfunded claim.

### Impact Explanation
Direct theft of underlying: the attacker receives up to `min(instant receipt, vault balance - defaultRecoveryReserve)`, paid out of funds committed to matured withdraw receipts. Honest claimants' `claimWithdrawRequest` calls then revert permanently until the borrower wires the instant funding (which may never arrive if the borrower later defaults, converting the theft into an unrecoverable loss borne by honest claimants). In a default, `finalizeDefaultRecovery` computes `defaultPendingClaimBasis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` [8](#0-7)  assuming funded claims still hold their backing — the drained balance silently reduces everyone's recovery.

### Likelihood Explanation
Requires only an unprivileged KYC'd tranche holder. Preconditions: instant withdrawals enabled (`allowInstantWithdraw`), a pending instant receipt created during a buffer, and vault balance ≥ the receipt — which is exactly the state after any `stopEpoch` that funded normal withdraw requests while the CDO lacks idle liquidity to prefund instant redemptions at `startEpoch`. The window is at least `instantWithdrawDelay` long every such epoch, and persists indefinitely if the manager delays `getInstantWithdrawFunds`. No privileged misbehavior is needed; sequencing around honest manager calls suffices.

### Recommendation
Bind each instant claim to its funding: track the funded portion per user/epoch (e.g., a `fundedInstantWithdraws` cumulative counter increased by `collectInstantWithdrawFunds` and consumed by claims), and in `claimInstantWithdrawRequest` pay only the funded remainder, reverting or capping when the receipt is still covered by `pendingInstantWithdraws`. Alternatively, segregate buckets: have `_transferFundedClaim` also exclude `pendingInstantWithdraws`-backed normal reserves, or settle instant claims from a dedicated balance tracked separately from normal-claim reserves.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (based on test/foundry/IdleCreditVault.t.sol harness)
function testUnfundedInstantClaimStealsFundedNormalReserve() external {
    // 1. Epoch 0: honest LP deposits AA, requests normal withdraw in buffer.
    _depositWithUser(honest, 100_000e6, true);
    _startEpochAndCheckPrices(0);
    vm.prank(honest);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    // stopEpoch funds pendingWithdraws -> vault now holds honest reserve
    _stopEpochAndCheckPrices(0, apr / 4, _expectedFundsEndEpoch());

    // 2. Buffer: attacker (KYC'd AA holder) requests instant withdraw.
    _depositWithUser(attacker, 10_000e6, true);
    vm.prank(attacker);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant path

    // 3. Epoch 1 starts; CDO idle liquidity < pendingInstantWithdraws,
    //    manager has NOT yet called getInstantWithdrawFunds (delay window).
    _startEpochAndCheckPrices(1);
    assertGt(strategy.pendingInstantWithdraws(), 0); // receipt is UNFUNDED

    // 4. Attacker claims anyway: paid from honest funded reserve.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, receipt); // stolen payout

    // 5. Honest matured claim now reverts on insufficient vault balance.
    vm.prank(honest);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I was unable to fully trace every `startEpoch`/`getInstantWithdrawFunds` code path in `IdleCDOEpochVariant.sol` within the available iterations; if some path atomically disables `allowInstantWithdraw` whenever `pendingInstantWithdraws != 0` at epoch start, this vector closes — but nothing in the inspected code (the CDO claim gate, the vault claim, and `_transferFundedClaim`) enforces per-receipt funding, and the test at `IdleCreditVault.t.sol:4801` shows the revert comes only from insufficient balance, not from an unfunded-receipt guard.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
