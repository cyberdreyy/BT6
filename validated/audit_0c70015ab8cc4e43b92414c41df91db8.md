### Title
Node-side signer-response tally double-counts a signer's weight in both `total_weight_approved` and `total_weight_rejected` when a signer legitimately flips from reject to accept - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::run` maintains one `BlockStatus` per proposed block with two independently-incrementing weight counters, `total_weight_approved` and `total_weight_rejected`. The guard used to prevent double counting differs by branch: the `Accepted` branch gates on `gathered_signatures.contains_key(&slot_id)` while the `Rejected` branch gates on `responded_signers.insert(&slot_id)`. Because signers are explicitly allowed by the signer's own design to reject a block first and later sign the same (or a re-proposed) block once a conflict goes stale, a signer's weight can end up added to both totals for the same block, with no mechanism ever removing it from the earlier tally. This is analogous to the reported InsuranceFund bug, where an exact, unreconciled state check (`balance == 0`) failed to account for a partial/residual state left behind by an earlier action, letting an attacker exploit the gap between two states that should have been mutually exclusive.

### Finding Description
On the signer side, `handle_block_pre_commit` documents and implements the exact scenario that creates the gap: a signer may reject a proposal (`mark_locally_rejected`, broadcasting `Rejected`), but the docs and code explicitly state "a rejection is a revocable opinion" and the signer "may sign later if the rival dies out" [2](#0-1)  - once the conflicting signature it saw becomes stale (`conflict_still_blocks`, freshness cutoff), the same signer can go on to sign a re-proposal of the same (or a new) block and broadcast `Accepted` for it.

On the miner/node side, `StackerDBListener::run` processes these two messages independently:
- For `Accepted`, weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)` [3](#0-2) .
- For `Rejected`, weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot is seen in `responded_signers`) [4](#0-3) .

Crucially, the `Accepted` branch also unconditionally inserts into `responded_signers` (`block.responded_signers.insert(slot_id);`, line 465) alongside `gathered_signatures`. So if a signer's `Rejected` message for a given block arrives first (adding its weight to `total_weight_rejected` and marking `responded_signers`), and its `Accepted` message for the same block arrives later, the `Accepted` branch's own guard (`gathered_signatures.contains_key`) is still `false` (this signer never signed before), so the weight is added again to `total_weight_approved`. Nothing in this code path ever subtracts the earlier weight from `total_weight_rejected`.

This breaks the implicit invariant the miner's decision logic depends on: that `total_weight_approved` and `total_weight_rejected` are drawn from disjoint sets of signer weight so that at most one of "70% approved" and ">30% rejected (making 70% impossible)" can become true. With the double count, both conditions can become true simultaneously purely because of the ordering of message arrival for a single flip-flopping (but legitimately behaving) signer, i.e. the aggregated weight tracked here diverges from what a genuine per-signer verified-accept tally would show.

### Impact Explanation
`SignerCoordinator::get_block_status` (stacks-node/src/nakamoto_node/signer_coordinator.rs) checks the rejection-impossible condition before the approval-threshold condition on every loop iteration [5](#0-4) . With the double-counted rejection weight, the coordinator can spuriously conclude `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` and return `NakamotoNodeError::SignersRejected`, aborting the block-proposal cycle, even though the actual, currently-valid signature set (as would be verified independently via `NakamotoBlockHeader::verify_signer_signatures`) has legitimately reached the 70% threshold. This is a liveness/availability break at the aggregated-weight-vs-verified-accepts boundary: the miner's own bookkeeping about "is this block dead" diverges from the ground truth that a real signature-weight check would show, causing the miner to unnecessarily abandon or retry proposals whenever a signer follows the documented reject-then-accept path (which the signer protocol explicitly allows and, per the docs, expects to happen during ordinary reorg/freshness handling).

### Likelihood Explanation
This does not require compromising a signer key or a majority of signers. It only requires the ordinary, protocol-sanctioned behavior of a single signer rejecting a block due to a (temporarily) fresh conflicting signature, and later signing the same or a re-proposed block once that conflict goes stale - a flow the codebase explicitly documents as expected (`docs/signer-flows.md`, "a rejection is a revocable opinion... can still be aggregated toward the 70% threshold"). A miner/tenure re-proposing a block after an initial split vote (a scenario already covered by existing tests such as `pre_commit_50_50_split_agrees_on_node_tip`) is enough to trigger the ordering that produces the double count, at the node's `StackerDBListener`, which is on the miner's coordination path used for every block.

### Recommendation
Track, per slot_id, a single authoritative vote state (e.g., an enum `Approved(weight)`/`Rejected(weight)`/`None`) instead of two independently-incrementing counters guarded by different sets. When a slot's vote transitions from Rejected to Accepted (or vice versa), subtract the weight from the old tally before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` are always computed over disjoint signer sets and can never both cross their respective thresholds for overlapping signer weight.

### Proof of Concept
1. Reward set with signers A (weight 40), B (weight 35), C (weight 25), `weight_threshold` = 70% (~70), blocking minority > 30 (~31).
2. Miner proposes block X. Signer A rejects X because it has a fresh conflicting signature over a sibling block. `StackerDBListener` records: `total_weight_rejected = 40`, `responded_signers = {A}`.
3. The conflicting sibling's signature goes stale (`last_endorsed <= freshness_cutoff`), and per `handle_block_pre_commit`'s documented behavior, signer A's later pre-commit/response for the same (or a re-proposed) block X can now succeed and it signs, broadcasting `Accepted`.
4. `StackerDBListener` Accepted-handler check: `gathered_signatures.contains_key(&A) == false` → adds A's weight to `total_weight_approved = 40`; `responded_signers.insert(A)` is a no-op (already present) - `total_weight_rejected` stays at 40.
5. Signers B and C both accept: `total_weight_approved = 40 + 35 + 25 = 100 ≥ 70` (threshold reached) while `total_weight_rejected = 40` is unchanged, still counted from step 2.
6. If B or C's acceptance is delayed relative to a coordinator poll where `total_weight_rejected` (40) is combined with a hypothetical additional rejecting signer weight ≥ 31 total, the coordinator's rejection-impossible check (`total_weight_rejected + weight_threshold > total_weight`) can fire and abort the round via `SignersRejected`, even though A's rejection was already revoked and superseded by a valid signature - demonstrating the tallies no longer reflect a disjoint, ground-truth partition of signer weight.
