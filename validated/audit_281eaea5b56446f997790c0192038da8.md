### Title
Unauthenticated `replace`/`clean` storage manipulation exports allow any caller to overwrite/delete an account's storage - (File: state-manipulation/src/lib.rs)

### Summary
The `replace` and `clean` `#[no_mangle]` exports in `state-manipulation/src/lib.rs` perform raw `storage_write`/`storage_remove` calls driven entirely by caller-supplied `input()` JSON, with no check of `predecessor_account_id()`, no owner check, and no `assert_self()` guard. Any account that can send a `FunctionCall` action to the account this contract is deployed on can invoke `replace` (or `clean`) and arbitrarily rewrite (or erase) that account's persistent storage, including keys such as `STATE` that other contracts (lockup, staking-pool, multisig, wNEAR) use to store balances and ownership.

### Finding Description
The invariant that should hold is: `predecessor_account_id() == current_account_id()` (or some equivalent owner/self check) before any `storage_write`/`storage_remove` call executes. In the actual code this equality is never asserted: [1](#0-0) 

`replace()` calls `input()` to read the raw call arguments, deserializes a list of base64 `(key, value)` pairs, and calls the local `storage_write` helper for every pair - unconditionally: [2](#0-1) 

There is no import or use of `env::predecessor_account_id`, `env::current_account_id`, or any authorization primitive anywhere in the file - not in `replace`, not in `clean`, and not in any shared helper. The `clean` export has the identical structural flaw: [3](#0-2) 

Per the project's own README, this contract is meant to be deployed temporarily onto an account that already runs another contract (lockup, staking pool, multisig, etc.), used once via `replace`/`clean` to patch state, then removed: [4](#0-3) 

Deploying the WASM code itself requires a full-access key on the target account (outside attacker capability), but once the account's rightful owner has deployed this contract (e.g., during an emergency state fix), the exported `replace`/`clean` methods become ordinary public change-methods with zero authorization. Any unprivileged account - not just the owner - can then call `replace` (or `clean`) on that account before the owner's own follow-up transaction executes, and completely rewrite or delete the account's storage: overwrite the `STATE` key with an attacker-chosen Borsh-serialized struct (e.g. setting themselves as `owner_id`, inflating an `unstaked`/`liquid` balance, or altering `vesting_information`/`termination_withdrawn_tokens`), or `clean` away keys entirely. There is no `assert_self()`, no `assert_owner`, no predecessor check of any kind guarding either export, so none of the standard guards (`assert_owner`, `assert_called_by_foundation`, `assert_self()`, `assert_one_yocto()`, etc.) apply here - the contract simply lacks them.

### Impact Explanation
Whoever wins the race to call `replace` (or `clean`) after deployment controls the account's entire persistent state. Against a lockup, staking-pool, multisig, or wNEAR-holding account, an attacker can fabricate `STATE` bytes that: set themselves as owner, inflate withdrawable/unstaked balances beyond what is actually held, mark vesting as fully vested, or zero out `termination_withdrawn_tokens` - any of which lets an unentitled party subsequently withdraw or transfer NEAR out of the account. This matches the Critical impact category: NEAR moved out of a lockup/pool/multisig by a party not entitled to it, or claims exceeding tokens actually held/unvested tokens released early. The attack is repeatable against any account onto which this contract is (even transiently) deployed, and a single successful call fully compromises that account's state.

### Likelihood Explanation
The precondition is that the state-manipulation contract must be deployed (by its rightful full-access-key holder) onto the target account - the attacker cannot deploy it themselves onto a victim-owned account. However, once deployed, exploitation costs nothing beyond a normal `FunctionCall` transaction with gas: no deposit, no special permission, no key compromise, and the call is indistinguishable from the intended maintenance call. Given the contract's own stated purpose (patch state, then remove), there is a real window between deployment and the owner's intended follow-up call/removal during which any observer of the deployment (mempool, block explorer, or state that a WASM upgrade just occurred) can race a `replace`/`clean` call in.

### Recommendation
Add a `predecessor_account_id() == current_account_id()` (self-call) or equivalent explicit owner check at the top of both `replace` and `clean` before performing any `storage_write`/`storage_remove`, e.g. via `near_sys::predecessor_account_id` compared against `near_sys::current_account_id`, panicking if they differ.

### Proof of Concept
```rust
// near-workspaces test (state-manipulation/... test module, illustrative)
#[tokio::test]
async fn unauthorized_replace_overwrites_state() -> anyhow::Result<()> {
    let worker = workspaces::sandbox().await?;
    let wasm = tokio::fs::read("res/state_manipulation.wasm").await?;

    // Simulate "owner" deploying the contract to their own account.
    let owner = worker.dev_create_account().await?;
    let contract = owner
        .deploy(&worker, &wasm)
        .await?
        .into_result()?;

    // Attacker is an unrelated account with no key on `contract`.
    let attacker = worker.dev_create_account().await?;

    // Attacker calls `replace` directly, no auth check stops them.
    attacker
        .call(&worker, contract.id(), "replace")
        .args_json(serde_json::json!({
            "entries": [[
                base64::encode(b"STATE"),
                base64::encode(b"attacker-controlled-bytes")
            ]]
        }))?
        .max_gas()
        .transact()
        .await?;

    // Binding check: predecessor (attacker) != current_account_id (contract owner)
    // yet the write succeeded -> invariant broken.
    let state_items = contract.view_state(&worker, None).await?;
    assert_eq!(
        state_items.get(b"STATE".as_ref()).unwrap(),
        b"attacker-controlled-bytes"
    );
    Ok(())
}
```
This demonstrates that `attacker`, holding no key on `contract`, successfully rewrites `contract`'s storage via `replace`, violating the binding `predecessor_account_id() == current_account_id()` that should gate any storage write.

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}

pub fn clean() {
    #[derive(serde::Deserialize)]
    struct CleanInput<'a> {
        #[serde(borrow)]
        keys: Vec<&'a str>,
    }

    let input = input().unwrap();
    let args: CleanInput = serde_json::from_slice(&input).unwrap();
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}

# State Manipulation contract

This contract has been designed to put key value pairs into storage with `replace` and clear key/value pairs with `clean` from an account's storage.

Deploy this contract into the account that already has another contract deployed to it.
This contract on call `clean` will remove any items of the state specified (keys should be specified in base64). When compiled with `replace` feature, `replace` method can be called with an array of key/value tuple pairs to insert into state.
