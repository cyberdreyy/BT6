### Title
Same-tenure reorg-permit re-signing check skips `conflict_still_blocks`, allowing a second signature for an already-signed block once `reorg_permit_stands` returns `false` on a transient error - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_pre_commit`'s own-tenure re-signing branch (the code guarding a return to a tenure whose reorg-permit has dissolved) decides whether to sign a *new* pre-committed candidate using only `reorg_permit_stands` plus a single `get_tenure_tip` height check, never calling `conflict_still_blocks`. Because `reorg_permit_stands` maps any error — a genuine 404 (orphaned permitting sortition) *and* a transient `ClientError` such as a timeout — to the same "permit does not stand" result, a fleeting node/network hiccup can make the signer treat a still-standing reorg permit as void and sign a brand-new sibling block in the resurrected tenure while an earlier, still-live signature for that tenure remains outstanding.

### Finding Description
The equality that must hold: once a signer has signed block A in tenure T1 under a valid reorg permit granted to T2, it must never also sign a distinct block C for the same tenure/height unless A is provably dead. `conflict_still_blocks` (stacks-signer/src/v0/signer.rs:1137-1206) is the function built to answer that "provably dead" question precisely, using two node-derived checks (sortition canonicity + chain reachability) with staleness/tip-height guards designed to fail closed.

`reorg_permit_stands` (stacks-signer/src/v0/signer.rs:1222-1248) instead answers a narrower question — "is the permitting sortition (T2) still canonical?" — and on *any* failure (404 **or** any other `ClientError`, e.g. a request timeout) it returns `false`: [1](#0-0) 

This function is used in two places in `handle_block_pre_commit`:

1. The cross-tenure freshness check (lines 1403-1421), which correctly pairs `!reorg_permit_stands` with `conflict_still_blocks` before refusing to sign a *competing* proposal. [2](#0-1) 

2. The own-tenure "fall back to the tenure whose permit dissolved" check (lines 1432-1457), which only checks `!reorg_permit_stands(...)` and a raw `get_tenure_tip` height comparison — it never calls `conflict_still_blocks`, and it is not gated by conflict freshness at all: [3](#0-2) 

Because `get_signed_conflicts` already excludes the candidate's own `block_hash` [4](#0-3) , any `conflict` reaching this branch is necessarily a *different*, already-signed block than the current pre-committed candidate. The `get_tenure_tip` guard only refuses to sign when the node's canonical chain has already advanced to or past the candidate's height — but a block that only the signer set has locally signed (not yet pushed to / adopted by the node) will not show up in `get_tenure_tip` at all. In that window, a transient `reorg_permit_stands` failure (timeout, 5xx, connection reset — anything besides a genuine 404) makes the guard fall through and sign the new candidate, producing a second live signature for the tenure alongside the still-outstanding one for the original block.

Attacker's exact path: the attacker holds one won miner slot. They (a) cause/observe a legitimate reorg-permit grant from T1 to T2 (via normal timing rules), (b) once T2's sortition is genuinely still canonical, craft/gossip a new BlockProposal C for T1 (the "resurrected" tenure) at the conflicting height, and (c) rely on an ordinary transient RPC failure between the signer and its node (no privileged access needed — any `Err(e)` branch of `get_sortition_by_burn_hash` other than clean success suffices) to occur exactly when `reorg_permit_stands` is evaluated for the pre-existing A/T1 conflict record. The signer then signs C without ever confirming that A (already signed, potentially in flight to the node from other signers) is dead.

### Impact Explanation
This breaks the UNIQUENESS/equivocation safety property: the state machine can produce two live signatures (A and C) for the same tenure/height without ever confirming A is dead, which is exactly the double-sign the whole conflict-guard machinery (`conflict_still_blocks`, freshness, reorg permits) exists to prevent. If enough other signers hit the same or a related timing race, a genuinely conflicting pair of blocks can each independently accumulate signer weight, matching the Critical category ("a signer signing an invalid, non-canonical, or conflicting block; chain safety").

### Likelihood Explanation
Preconditions: a prior legitimate reorg permit (T1 superseded by T2) whose conflict has gone through pre-commit re-evaluation; T2's sortition still canonical (no real orphan); and an ordinary transient RPC error on the `get_sortition_by_burn_hash` call used by `reorg_permit_stands` (timeouts, disconnects, and 5xx responses are commonp, unprivileged, and require no majority-signer collusion — a single unprivileged attacker with one miner slot only needs to gossip a competing BlockProposal C at the right moment). The race window is real but narrow (it needs the RPC failure to coincide with the pre-commit re-evaluation for tenure T1's stale conflict), so likelihood is non-trivial but not guaranteed on every attempt — it is repeatable across pre-commit re-evaluations, since `handle_block_pre_commit` re-runs this logic on every incoming pre-commit.

### Recommendation
Route the own-tenure re-signing branch (stacks-signer/src/v0/signer.rs:1432-1457) through the same `conflict_still_blocks` logic used for cross-tenure conflicts instead of a bare `get_tenure_tip` check, and/or make `reorg_permit_stands` distinguish a genuine `NOT_FOUND` (safe to void the permit) from any other `ClientError` (which should instead leave the permit's prior state unchanged / retry, consistent with the "blocking is the direction that can be taken back" principle already stated in its own doc comment but not honored for non-404 errors).

### Proof of Concept
Rust test plan (extending `stacks-signer/src/v0/tests.rs`, alongside `standing_reorg_permit_clears_conflict` / `orphaned_reorg_permit_restores_conflict`):
1. Run `run_cross_tenure_scenario` (or an extended variant) to get signer to sign block A in tenure T1, then sanction a reorg permitting T2 to supersede T1 (mirrors `TenureAFate::SupersededPermitCanonical` setup), producing a `SignedConflictInfo` for A with `superseded_by = T2`.
2. Mock `get_sortition_by_burn_hash(T2_burn_hash)` to return a non-404 `ClientError` (e.g. a transient failure) rather than 404, while keeping T2 genuinely canonical (i.e., a real `Ok` response would occur on retry) — asserting `reorg_permit_stands` returns `false` despite T2 still being canonical.
3. Mock `get_tenure_tip(T1_consensus_hash)` to return a tip below A's height (simulating A not yet globally accepted / pushed to the node).
4. Drive a second, distinct `BlockProposal` C for T1 at A's height/conflicting position through `handle_block_proposal` → pre-commit threshold → `handle_block_pre_commit`.
5. Assert that the signer does NOT sign C while A's signature is still outstanding and not proven dead: i.e. `info_c.signed_self.is_none()` (expected/fixed behavior) versus the current code's actual behavior of `info_c.signed_self.is_some()` (bug), while also asserting `info_a.signed_self.is_some()` throughout, demonstrating the state machine signing two conflicting blocks for the same tenure/height in a single test run.
