## Analysis Result

### Title
RPC token-account parsing trusts an attacker-controlled "mint" pubkey without verifying it is owned by an SPL Token program, allowing wrong decimals/`uiAmount` to be returned - ([File: rpc/src/parsed_token_accounts.rs])

### Summary
The external report concerns a `depositToken` function that accepts any ERC20 token without verifying its legitimacy, because there is no whitelist check on the token being deposited. The reachable analog in agave is in the JSON-RPC token-account decoding path: when computing the `decimals`/`uiAmount` fields for a parsed SPL token account, the RPC blindly trusts the 32-byte "mint" field embedded in the token-account data and fetches whatever account lives at that address, without ever checking that this account is actually owned by a legitimate SPL Token / Token-2022 program.

### Finding Description
`get_token_account_mint` simply extracts the first 32 bytes of the account data as a `Pubkey` once the data passes a generic length/state sanity check [1](#0-0) . This pubkey is fully attacker-controlled: any token account created with the correct `Account` layout (owned by `spl_token::id()` or `spl_token_2022::id()`, which anyone can do) may specify an arbitrary pubkey in the `mint` field, pointing to any account in the ledger.

That mint pubkey is then passed to `get_mint_owner_and_additional_data`, which fetches the account at that address and immediately tries to unpack it as a `Mint` struct via `get_additional_mint_data`/`StateWithExtensions::<Mint>::unpack`, with **no check that `mint_account.owner()` equals the SPL Token or Token-2022 program id** before treating its bytes as mint state: [2](#0-1) . The only owner check performed is on the resulting value returned as `(*mint_account.owner(), mint_data)`, which is used purely for caching/keying, not for validation.

This "additional data" (decimals, interest-bearing config, scaled-ui-amount config) is then fed into `token_amount_to_ui_amount_v3`/`parse_token_v3` to compute the displayed `uiAmount` and `uiAmountString` for the token account: [3](#0-2) . Both `get_parsed_token_account` (used for single-account lookups/simulation) and `get_parsed_token_accounts` (used for `getTokenAccountsByOwner` / `getProgramAccounts` with `jsonParsed` encoding) follow this same unchecked path: [4](#0-3) [5](#0-4) .

These helpers are invoked directly from the `getProgramAccounts` and `getTokenAccountsByOwner` RPC handlers whenever `jsonParsed` encoding is requested: [6](#0-5) [7](#0-6) .

### Impact Explanation
An attacker can craft:
1. A "fake mint" account (owned by any program, e.g. their own throwaway program or even the System program after allocation) whose raw bytes happen to satisfy the 82-byte `Mint` layout (`mint_authority: COption<Pubkey>`, `supply: u64`, `decimals: u8`, `is_initialized: bool`, `freeze_authority: COption<Pubkey>`), with an arbitrary `decimals` value (e.g. 0 or 255).
2. A legitimate SPL Token account (owned by the real `spl_token`/`spl_token_2022` program, so it passes the outer `PARSABLE_PROGRAM_IDS` owner check) whose `mint` field points at the fake mint account from step 1.

When any unprivileged client calls `getTokenAccountsByOwner`, `getProgramAccounts`, or `getAccountInfo`/`simulateTransaction` with `encoding: "jsonParsed"` against this account, the RPC node will report a completely wrong `decimals`/`uiAmount`/`uiAmountString` for the token account, since it trusts the crafted decimals from an account that is not actually a token mint. This is a decoder-misreporting bug: wrong account data is returned by a JSON-RPC query, which can mislead wallets, explorers, and downstream tooling that rely on the `jsonParsed` encoding for balance display, without requiring any validator/peer privilege.

### Likelihood Explanation
Any unprivileged user can create both the fake "mint" account and the associated token account with a single transaction using the SPL Token program's standard `InitializeAccount` instruction (setting an arbitrary `mint` pubkey is allowed at the instruction level; the runtime does not itself verify `mint` ownership at account-creation time — that check only happens on `Transfer`/`MintTo`, not on `InitializeAccount`). A single subsequent `getTokenAccountsByOwner`/`getProgramAccounts` RPC call with `jsonParsed` encoding triggers the bug, satisfying the "no more than one call" scope constraint.

### Recommendation
In `get_mint_owner_and_additional_data` (and the underlying `get_additional_mint_data`), verify that the fetched mint account's owner is `spl_token::id()` or `spl_token_2022::id()` before unpacking it as a `Mint` and before using its decimals/extension data to compute `uiAmount`. If the owner check fails, the RPC should fall back to omitting `uiAmount`/decimals (or returning an error/using raw `Binary` encoding) rather than trusting arbitrary account data as legitimate mint state — effectively adding the missing "is this really a token mint" whitelist-style check that the original report calls for.

### Proof of Concept
1. Allocate an account `fakeMint` (any owner, e.g. via `SystemProgram.createAccount`) and write 82 bytes into it matching `spl_token::state::Mint`'s packed layout, with `decimals = 0` and `is_initialized = true`.
2. Create a standard SPL token account `tokenAcct` via `spl_token::instruction::initialize_account`, passing `fakeMint` as the `mint` parameter (the instruction does not check that `fakeMint` is owned by the token program at creation time — see `SvmTokenInfo::unpack_token_account`'s `mint_account.owner() != program_id` check only occurring at transaction-processing/balance-reporting time inside `svm`, not at `InitializeAccount` time) [8](#0-7) .
3. Call `getTokenAccountsByOwner` (or `getProgramAccounts`) with `{"encoding": "jsonParsed"}` for the owner of `tokenAcct`.
4. Observe that the RPC response's `parsed.info.tokenAmount.decimals`/`uiAmount` reflects the attacker-chosen bytes at `fakeMint`, rather than an error or a legitimate token's decimals, confirming the missing ownership check in [9](#0-8) .

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
