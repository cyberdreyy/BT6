### Title
Threshold-crossing acceptance path bypasses the chainstate/conflict re-check that gates the pre-commit-threshold signing path, letting a stale/conflicting block get broadcast to the node without revalidation - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_signature` has two ways to reach "enough weight, broadcast the block": (1) route through `handle_block_pre_commit`, which re-runs `check_block_against_signer_db_state`, `get_signed_conflicts`, `conflict_still_blocks`, and `reorg_permit_stands` before signing/broadcasting, and (2) fall straight through to the signature-tally branch when the sender is already known to have pre-committed (`has_committed == true`) or is ourselves. Path (2) performs none of those re-checks before calling `broadcast_signed_block`.

### Finding Description
`handle_block_signature` → `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2371-2538`) stores every valid peer signature unconditionally via `add_block_signature` (line 2454-2457). It then branches: [1](#0-0) 

If the signer already has a recorded pre-commit for this block (`has_committed == true`) — which a single malicious/one-slot miner-adjacent peer can arrange simply by sending its own genuine pre-commit early — subsequent Accepted signatures from that same address skip the pre-commit re-evaluation entirely and go directly into the weight tally: [2](#0-1) 

Contrast this with the pre-commit-threshold path, `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1250-1479`), which explicitly re-validates chainstate and conflict state immediately before signing/broadcasting: [3](#0-2) 

The signer's own design doc explicitly documents *why* this re-check is necessary at the moment of crossing the threshold — "Between validation and threshold, we may have signed a different block at the same height... so the world must be re-checked before the signature leaves the box" — and states the guard's scope is "Pre-commits from peers (and our own)": [4](#0-3) 

The threshold-crossing branch inside `store_and_process_block_signature` (reached once `has_committed` is already true) is a *second* path that also crosses the 70% weight threshold and calls `broadcast_signed_block`, but it inherits none of the conflict/chainstate re-validation that `handle_block_pre_commit` performs. This breaks the "aggregated-weight vs verified-accepts" equality the rest of the design deliberately maintains: reaching threshold weight is supposed to imply a fresh re-check that the block still doesn't conflict with anything this signer has since (locally) accepted, but this path allows threshold-crossing purely from already-stored signatures with no such re-check.

Concretely: suppose the local signer earlier recorded a pre-commit from peer P for block A (satisfying `has_committed`), then later — before A reaches 70% — this signer locally signs a conflicting sibling block B at the same height (via the properly-guarded pre-commit path for B, which is allowed to proceed because A never reached threshold and its pre-commit is stale/dead per `conflict_still_blocks`). If P's real, valid `Accepted` signature for A now arrives (P having genuinely signed A before this signer switched to B), and enough analogous already-committed peers' accepted signatures arrive to cross 70% for A, `store_and_process_block_signature`'s direct branch will mark A locally accepted and call `broadcast_signed_block(stacks_client, block_info.block.clone(), &addrs_to_sigs)` — pushing A to the node — without re-running `get_signed_conflicts`/`conflict_still_blocks`/`reorg_permit_stands` against this signer's own now-conflicting state (having signed B). The pre-commit path would have caught and refused this; the signature-tally path does not.

### Impact Explanation
This lets the network push and adopt (`broadcast_signed_block` → `handle_post_block`) an aggregate-signed block that this specific signer's own current chainstate view considers conflicting/stale, purely because the last piece of weight arrived as an `Accepted` signature from an already-known committer rather than as a fresh pre-commit. This is exactly the "aggregated-weight vs verified-accepts" equality break called out in scope: the signer treats accumulated signature weight as sufficient proof of validity without re-verifying it against its own latest local state, which the codebase's own design explicitly says must be re-checked at the moment of crossing the threshold.

### Likelihood Explanation
Reaching this branch requires no forged signatures and no majority collusion: a single one-slot-adjacent miner/gossip actor only needs to arrange the *timing* of proposal/pre-commit/signature messages relative to this signer's own conflicting decision — which the pre-commit path (section 5 of the design) is explicitly built to defend against, but the signature-tally shortcut is not. Given that `has_committed` becomes true from routine, benign pre-commit traffic (including the documented "outdated peer" fallback that deliberately promotes bare Accepted messages into pre-commits), this state is easy to reach in normal operation, making the missing re-check a persistent gap rather than an edge case.

### Recommendation
Before broadcasting on the direct signature-tally path in `store_and_process_block_signature` (i.e., whenever `min_weight <= total_signature_weight` is about to trigger `mark_locally_accepted` + `broadcast_signed_block`), re-run the same `check_block_against_signer_db_state` / `get_signed_conflicts` / `conflict_still_blocks` / `reorg_permit_stands` sequence that `handle_block_pre_commit` performs, or route this branch through `handle_block_pre_commit` unconditionally so there is a single, always-re-checked path to crossing the signing/broadcast threshold.

### Proof of Concept
1. Signer S receives P's pre-commit for block A at height h in tenure T1 (`has_committed(A, P) == true`), but A's pre-commit weight never reaches 70%.
2. S later validates and signs conflicting sibling block B (height h, tenure T2) via the properly-guarded `handle_block_pre_commit` path for B (A's earlier pre-commit is stale/not live per `conflict_still_blocks`), so S is now locally accepted on B.
3. P's genuine, previously-issued `Accepted` signature for A (and other already-committed peers' genuine signatures for A) arrive/replay to S via `handle_block_response` → `handle_block_signature` → `store_and_process_block_signature`.
4. Because `has_committed(A, P)` is already true, the code skips `handle_block_pre_commit` and goes straight to the weight tally; once ≥70% weight for A is reached, S calls `broadcast_signed_block` for A — despite S itself already being locally accepted on the conflicting sibling B — because none of the conflict/chainstate re-checks that gate the pre-commit path were run.
