### Title
Pending withdraw requests cannot be funded when the ERC4626 vault's spot liquidity is drained, even though the position is fully backed - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The GMX bug is "position is backed but cannot be paid out because withdrawal requires spot liquidity in one specific token." The analog in idle-tranches is `ProgrammableBorrower.onStopEpoch`: when `IdleCDOEpochVariant.stopEpoch` needs to pull `_amountRequired` to fund `pendingWithdraws`, the borrower adapter must withdraw the shortfall from the external ERC4626 vault in the underlying token. If `vault.withdraw` reverts due to insufficient vault-side liquidity — even though the vault shares economically cover the shortfall (`shortfall <= _currentVaultAssets()`) — the whole `stopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, blocking funding of all pending withdraw requests.

### Finding Description
In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:239-253):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The coverage check uses `convertToAssets` (economic backing), but the actual payout uses `vault.withdraw` (spot liquidity). For ERC4626 vaults whose assets are deployed into lending markets (e.g., Morpho/Gauntlet vaults, as used in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`), `maxWithdraw`/`withdraw` can be far below `convertToAssets` when the underlying markets' idle liquidity is borrowed out. Any unprivileged actor can borrow the remaining liquidity from the vault's underlying markets (or wait for organic utilization), causing `vault.withdraw` to revert while shares remain fully backed.

The revert propagates out of `stopEpoch` (per `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`, the epoch remains running and `pendingWithdraws` stays nonzero). Withdrawal claimants holding receipts minted by `IdleCreditVault.requestWithdraw` cannot be paid, because claims are denominated in the underlying token and there is no alternative payout path (e.g., paying in vault shares) — exactly the GMX "must pay out in the same token, no fallback" shape.

Note the asymmetry: when `shortfall > _currentVaultAssets()` the hook returns `true` and lets the default path run, but when shares *cover* the shortfall yet liquidity is unavailable, the transaction reverts and the epoch is stuck until spot liquidity returns. There is no deadline, partial-fill, or share-payout fallback.

### Impact Explanation
Temporary freezing of all pending withdraw requests for the epoch, quantified by `pendingWithdraws` (the full amount `stopEpoch` must source). Duration is bounded only by when vault liquidity is replenished (borrower repayment, new deposits into the vault's markets), which is outside the pool's control. During the freeze, users holding funded-epoch receipts cannot claim despite full economic backing, and epoch rollover/interest settlement is stalled. An attacker with capital can deliberately sustain the freeze by keeping the vault's underlying markets fully borrowed.

### Likelihood Explanation
Requires the configured vault to have less spot liquidity than the stopEpoch shortfall. For lending-market-backed vaults this is a routine state (high utilization is the normal yield mechanism), not an edge case, and an unprivileged attacker can force it by borrowing available liquidity — no privileged role needed. The honest owner/manager can partially mitigate via `emergencyExitVault` (also subject to the same vault liquidity limits) or `rescueTokens`, so the freeze is temporary rather than permanent, matching the "temporary freezing" acceptance criterion.

### Recommendation
Mirror the GMX resolution ("pay profits in the backing token"): when `shortfall <= _currentVaultAssets()` but `vault.withdraw` reverts or `vault.maxWithdraw(address(this)) < shortfall`, either (a) transfer vault shares to IdleCDO as settlement in kind, (b) allow `stopEpoch` to proceed with a recorded `vaultLiquidityDeficit` that claims draw against as liquidity returns, or (c) bound the withdrawal to `vault.maxWithdraw` and socialize the residual shortfall across pending receipts rather than reverting the entire epoch stop. At minimum, add a deadline after which a covered-but-illiquid stop degrades to the funded-default accounting path instead of leaving `pendingWithdraws` unclaimable indefinitely.

### Proof of Concept
A Foundry PoC exists essentially already in `test/foundry/ProgrammableBorrowerCreditVault.t.sol:372-399` (`testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`), extended to show the user-level freeze:

```solidity
// Setup: programmable-borrower CDO, deposit AA, requestWithdraw, start epoch.
// All idle funds are now vault shares in `limitedVault`/Morpho vault.
uint256 pendingWithdraws = strategy.pendingWithdraws();
assertGt(pendingWithdraws, 1);

// Attacker action (unprivileged): borrow vault's market liquidity so
// maxWithdraw < shortfall while convertToAssets still covers it.
// In the mock this is simulated by:
limitedVault.setWithdrawLimit(pendingWithdraws - 1);
// In a live fork: attacker calls morpho.borrow(...) draining the vault's markets.

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// Consequence: epoch stays running, pendingWithdraws never funded,
// claimWithdrawRequest reverts/not allowed for all receipt holders.
assertTrue(cdoEpoch.isEpochRunning());
assertEq(strategy.pendingWithdraws(), pendingWithdraws);
```

Uncertainties: I verified the revert path in `ProgrammableBorrower.onStopEpoch` and the existing test asserting `stopEpoch` reverts while `pendingWithdraws` remains pending, but I could not re-check the exact `IdleCDOEpochVariant.stopEpoch` call ordering (the grep output was truncated to match counts). Whether `stopEpoch` fully reverts vs. catches the hook revert is inferred from the test asserting `isEpochRunning()` remains true after the expected revert — which confirms the epoch is left unsettled and withdraws unfunded.
