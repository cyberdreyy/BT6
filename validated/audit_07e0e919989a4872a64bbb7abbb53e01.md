### Title
Missing zero-address validation on `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permanently locks the migrated account's authority - (File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs)

### Summary
The Trail of Bits finding concerns `UniswapV3Factory` accepting an unvalidated `_owner` argument (including `address(0)`) in its constructor/`setOwner`, permanently locking the owner role. Marginfi has a directly analogous pattern: the account-authority-transfer instructions accept a completely unvalidated `new_authority` account and write it directly into the new `MarginfiAccount.authority` field, with no check against `Pubkey::default()` (Solana's analog of `address(0)`).

### Finding Description
`transfer_to_new_account` and `transfer_to_new_account_pda` let a `MarginfiAccount` owner (or authorized delegate) migrate their account to a brand-new account under a caller-supplied `new_authority`. The account is explicitly marked as unchecked: [1](#0-0) 

That `new_authority.key()` is passed straight into `initialize_migrated_account`, which sets the new account's `authority` field, and the old account is simultaneously disabled and permanently marked as migrated: [2](#0-1) [3](#0-2) 

There is no on-chain check preventing `new_authority == Pubkey::default()`. The only place this check exists is client-side, in the CLI tooling (`p0-cli`), which is not enforced by the program itself: [4](#0-3) 

Because the old account's `migrated_to` field is set once and guarded against re-migration (`check_eq!(old_account.migrated_to, Pubkey::default(), MarginfiError::AccountAlreadyMigrated)`), the migration is a one-way, irreversible operation: [5](#0-4) 

If `new_authority` is `Pubkey::default()` (or any key nobody controls a private key for), the new account — which now holds all the migrated lending positions/balances — becomes permanently unownable: no signer can ever satisfy `is_signer_authorized` checks (`authority.key() == group.admin` / delegate checks) for this account going forward, since the field is set to a key with no controlling keypair.

### Impact Explanation
Any user (via a buggy integration, malicious wallet/dApp front-end, or a simple mistake) who calls `transfer_to_new_account`/`transfer_to_new_account_pda` with `new_authority = Pubkey::default()` permanently and irrecoverably locks all assets/positions held in the resulting `MarginfiAccount`. This is a durable, unrecoverable freeze of user funds with direct financial effect — no admin function exists to reassign `authority` on an existing account, and the source account cannot be "un-migrated" (the `AccountAlreadyMigrated` check blocks retry). This is the same class of harm identified in the report: irrecoverable loss of a control role due to unvalidated `owner`/`authority` input.

### Likelihood Explanation
The action is fully permissionless from the perspective of the account authority — it requires only the account's own owner/delegate signature, exactly analogous to the report's "Alice deploys and mistakenly passes address(0)" scenario. Given that a client-side guard against `Pubkey::default()` already exists in the CLI (showing developers are aware this specific value is dangerous) but no equivalent guard exists in the on-chain program, any front-end bug, malformed integration, or user error bypassing the CLI can trigger this irreversibly. This is realistic and has a real precedent risk since the safety net is entirely off-chain.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` rejecting `new_authority.key() == Pubkey::default()` (and, ideally, verifying `new_authority` is not itself a PDA/program-owned/unspendable key when that can be determined), returning a dedicated error (e.g. `MarginfiError::InvalidAuthority`) instead of relying solely on client-side CLI validation.

### Proof of Concept
1. User owns `MarginfiAccount` A with an authority they control and has deposited collateral.
2. User (or a compromised/buggy front-end) submits `transfer_to_new_account` (or the PDA variant) with `new_authority = Pubkey::default()`.
3. Instruction succeeds: `old_marginfi_account` (A) is disabled and `migrated_to` is set to the new account; `new_marginfi_account` (B) is initialized with `authority = Pubkey::default()`, inheriting all of A's balances via `initialize_migrated_account`. [3](#0-2) 
4. A can no longer be used (disabled + migrated), and B can never be operated on because no wallet can produce a valid signature for `Pubkey::default()`, so `is_signer_authorized` can never succeed for account B. [6](#0-5) 
5. All assets tracked by B are permanently frozen with no recovery path on-chain.
