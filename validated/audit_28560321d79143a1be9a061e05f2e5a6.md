### Title
Divide-before-multiply truncation in `jovian_da_footprint` causes systematic DA-footprint gas undercounting - (File: `crates/common/l1-fees/src/params.rs`)

### Summary
`L1FeeParams::jovian_da_footprint` computes the Jovian DA-footprint gas by **dividing before multiplying**, the same rounding-order bug class flagged in the referenced report (chained integer division causing avoidable precision loss). Because Solidity/Rust integer division always truncates, performing the division first destroys the fractional remainder before it is ever multiplied by the scalar, systematically under-counting DA-footprint gas for every transaction whose estimated size is not an exact multiple of `1_000_000`.

### Finding Description
`tx_estimated_size_fjord` returns a FastLZ-estimated size pre-scaled by `1e6`. The correct order to preserve precision is `estimated_size * scalar / 1e6` (multiply first, then divide once). Instead, `jovian_da_footprint` divides by `1e6` first and multiplies by the scalar afterward: [1](#0-0) 

Compare this to the sibling function `data_gas`, which correctly multiplies before dividing: [2](#0-1) 

For any `estimated_size` value where `estimated_size % 1_000_000 != 0` (i.e., almost always, since `tx_estimated_size_fjord` is a scaled floating estimate, not a clean multiple of a million), the leading `wrapping_div` truncates the fractional compressed-byte count to zero before the scalar is ever applied. The result is a footprint value that is smaller than the mathematically correct `estimated_size * scalar / 1e6`, with the truncation error scaling with `scalar` (up to `scalar - 1` gas lost per transaction, not just a rounding-unit loss).

This value feeds directly into the block executor's `da_footprint_used` accumulator, which enforces the Jovian DA-footprint block limit: [3](#0-2) 

### Impact Explanation
Because `da_footprint_used` is systematically under-reported relative to the protocol-correct formula, a block builder/sequencer (or any transaction sender shaping calldata to land on truncation-favorable sizes) can pack more compressed calldata into a block than the Jovian DA-footprint limit is intended to allow, since the metered footprint understates real DA usage. This is a resource-metering correctness bug in block building: the enforced limit no longer matches the specified protocol formula, degrading DA-availability guarantees the limit exists to protect. This falls squarely in the allowed "block building and resource metering" category.

### Likelihood Explanation
The bug triggers on essentially every transaction post-Jovian activation whenever `estimated_size` is not an exact multiple of `1,000,000` — which is the common case given `tx_estimated_size_fjord`'s scaling — so the divergence from the spec formula is not an edge case but a systematic, always-on undercount. No special privileges are needed; it activates automatically for any transaction processed after the Jovian fork.

### Recommendation
Reorder the arithmetic to multiply before dividing, matching `data_gas`'s pattern and the reference "`jovian_da_footprint_estimation`" spec:
```rust
pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
    let Some(scalar) = self.da_footprint_gas_scalar else {
        return 0;
    };
    U256::from(tx_estimated_size_fjord(input))
        .saturating_mul(scalar)
        .wrapping_div(U256::from(1_000_000u64))
        .saturating_to::<u64>()
}
```
This preserves the fractional remainder through the multiplication step and only truncates once at the end, consistent with `L1FeeParams::data_gas` and `calculate_tx_l1_cost_fjord`.

### Proof of Concept
Given `da_footprint_gas_scalar = 7` and an estimated size (pre-scaled by 1e6) of `1_999_999` (i.e., ~2 compressed bytes minus 1 unit of scale):
- Correct order: `1_999_999 * 7 / 1_000_000 = 13` (rounded down from 13.999993).
- Buggy order (current code): `1_999_999 / 1_000_000 = 1`, then `1 * 7 = 7`.

The current implementation returns `7` instead of the spec-correct `13`, a ~46% undercount for this input — and the gap widens with larger `scalar` values, since the entire fractional part of `estimated_size / 1e6` is discarded before scaling. [4](#0-3)
