### Title
Tranche holders can race instant-withdraw requests while the pool is already insolvent but still marked "active", exiting at par before the borrower default is crystallized - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` tracks borrower health only through cached flags (`defaulted`, `isEpochRunning`, `allowInstantWithdraw`) that are updated exclusively inside `stopEpoch`/`getInstantWithdrawFunds` via the `getFundsFromBorrower` try/catch and `_handleBorrowerDefault`. Between the moment a borrower becomes unable to fully repay and the next `stopEpoch` call, the contract still treats the epoch as healthy. During that window an unprivileged tranche holder can call `requestWithdraw`/`requestInstantWithdraw`, and when the honest manager later calls `getInstantWithdrawFunds`, the borrower only needs to cover the instant-withdraw amount (not the full epoch liability) for the attacker to be funded 1:1. When `stopEpoch` subsequently fails to pull the remaining principal, `_handleBorrowerDefault` fires and everyone else's claim is haircut by `finalizeDefault`/`defaultRecoveryReserve`, while the attacker's already-funded receipt pays out at par.

### Finding Description
The analog to the Carapace "buy protection on a stale 'active' pool" bug is the instant-withdraw path:

- `requestInstantWithdraw` in `IdleCreditVault.sol:356-375` burns the CDO's strategy tokens and mints a receipt with no solvency check — it cannot have one, because `defaulted` is only set inside `_handleBorrowerDefault` (`IdleCDOEpochVariant.sol:577-599`), which runs only when a pull from the borrower reverts.
- `getInstantWithdrawFunds` (`IdleCDOEpochVariant.sol:558-574`) only requires `isEpochRunning` and `instantWithdrawDeadline` to have passed. Its try/catch pulls exactly `_pendingInstant()` from the borrower; a borrower that can cover the instant requests but not the full epoch debt lets this succeed, transfers the funds to the vault, and sets `allowInstantWithdraw = true`.
- When `stopEpoch`/`stopEpochWithDuration` later runs (`IdleCDOEpochVariant.sol:408`, `501-505`), the pull of `_amountToPullFromBorrower + _pendingWithdraws` fails, `_handleBorrowerDefault` pauses the pool, stops the epoch and disables new withdraw requests. But per the comment at `IdleCDOEpochVariant.sol:502-503` and `_claimFundedWithdrawRequest`'s "if borrower defaults, old withdraw requests can still be claimed" note (`IdleCreditVault.sol:325`), receipts already funded are deliberately honored at par, and `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) pays them out of the vault balance.
- The broken invariant is the loss waterfall / fair redemption: a default is a point-in-time solvency fact, but the protocol only learns it lazily. Anyone who exits through the funded instant path before `stopEpoch` receives 100 cents on the dollar; everyone remaining is paid `recoveryRatio` cents through `DefaultDistributor`/`_claimDefaultedWithdrawRequest`.

This is structurally identical to the Carapace finding: `_verifyLendingPoolIsActive` reads a cached `poolStatus` that lags the real late state; here `isEpochRunning`/`defaulted` lag the real insolvency state, and the privileged-but-honest manager's scheduled call is what front-runners exploit.

### Impact Explanation
The attacker redeems at par using borrower liquidity that economically belongs to all LPs pro-rata. Quantified: if the borrower can repay `X` of `X + Y` owed and an attacker holds instant receipts worth `X`, the attacker receives `X` in full, `stopEpoch` then defaults with zero additional funds, and all remaining NAV + pending receipts recover only `recovered / totalBasis` through `finalizeDefault`. The attacker's gain equals `receipt * (1 - recoveryRatio)` — direct theft of the loss-socialization shortfall, borne by passive AA/BB holders and pending receipt holders whose `defaultPendingClaimBasis` is haircut.

### Likelihood Explanation
Requires a specific but realistic setup: instant withdrawals must be enabled (non-programmable, non-`disableInstantWithdraw` pool), the epoch must be running past `instantWithdrawDeadline`, and the borrower must be able to partially cover instant requests while being insolvent on the full repayment — i.e., exactly the "already late but not yet recorded" scenario from the source report. The attacker needs only a tranche position (KYC-passing lender) and to submit `requestInstantWithdraw` before the manager's scheduled `getInstantWithdrawFunds`/`stopEpoch` calls; no privileged action is required and no existing guard (`whenNotPaused`, `allowAAWithdrawRequest`, `skipDefaultCheck`, KYC) blocks the request, because none of them can observe the not-yet-recorded default.

### Recommendation
- In `getInstantWithdrawFunds`, or in the `requestInstantWithdraw` path, assess total borrower coverage before funding partial claims: compare `pendingInstantWithdraws` against the borrower's full obligation (`_amountToPullFromBorrower + pendingWithdraws + pendingInstantWithdraws`), and trigger `_handleBorrowerDefault` (or skip funding) rather than funding a subset at par when total repayment will fail.
- Alternatively, make instant funding conditional on `borrower` having approved/balanced the full `stopEpoch` liability, so the "late" state is probed before any par payout, mirroring the recommendation to call `_assessState` before `_verifyLendingPoolIsActive`.
- Optionally add a permissionless `assessBorrower()`-style poke so anyone can crystallize a default the moment coverage is insufficient, shrinking the stale-state window.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (mode: fixed-APR, instant withdrawals enabled,
// epoch running, honest manager + honest-but-insolvent borrower)
function testInstantWithdrawRacesStaleDefault() external {
    // Setup: user deposits AA, manager starts epoch (buffer -> running)
    uint256 amount = 100_000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);
    _startEpochAndCheckPrices(0);

    // Borrower draws funds and becomes insolvent on the FULL repayment,
    // but keeps enough tokens+allowance to cover pending instant requests.
    // (State in CDO: isEpochRunning == true, defaulted == false — stale.)

    // Attacker requests instant withdraw for full tranche balance
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(trancheBal, address(AAtranche));

    // Past instantWithdrawDeadline: honest manager collects instant funds.
    // Borrower repays ONLY pendingInstantWithdraws.
    vm.warp(cdoEpoch.instantWithdrawDeadline() + 1);
    uint256 instant = IdleCreditVault(strategy).pendingInstantWithdraws();
    deal(underlying, borrower, instant);
    vm.prank(borrower);
    IERC20(underlying).approve(address(cdoEpoch), instant);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();          // succeeds, allowInstantWithdraw = true

    // Epoch end: borrower cannot repay principal -> stopEpoch defaults
    deal(underlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);
    assertTrue(cdoEpoch.defaulted());

    // Attacker claims funded instant receipt AT PAR
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - pre, instant); // 100%, not recoveryRatio

    // finalizeDefault later pays everyone else pro-rata on a drained base
}
```

Caveat: I did not fully trace the CDO-side gating for `requestInstantWithdraw` (request window/`disableInstantWithdraw`/`allowInstantWithdraw` ordering relative to `instantWithdrawDeadline`), so the exact call sequencing in the PoC may need adjustment against the request path in `IdleCDOEpochVariant.sol`; the core stale-state gap — no solvency probe between request and par funding — is confirmed by `IdleCDOEpochVariant.sol:558-574` and `:577-599`.
