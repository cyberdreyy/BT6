### Title
Runner-side logrus output (`internal.Tee.log`) emits unmasked secrets that are masked in the job trace - (File: common/buildlogger/internal/tee.go)

### Summary
`internal.Tee.log` writes the same `args` both to the build trace writer (`t.logFn`, which passes through the masker/tokensanitizer/urlsanitizer chain) and directly to `t.entry.Logln(level, args...)`, the runner's own logrus logger, with zero sanitization applied to the latter. Any code path that calls `Logger.Errorln`/`Warningln`/`SoftErrorln`/`Println`/`Infoln` with a message containing a masked phrase, private token, or signed-URL parameter will leak that secret verbatim into the runner's structured/host log even though it is correctly redacted in the job trace shown to the user.

### Finding Description
`Logger.wrap` (common/buildlogger/build_logger.go:213-224) builds the masking chain (`masker.New` → `urlsanitizer.New` → `tokensanitizer.New`) that only applies to `l.w`, the writer used for the job trace (`Stream`, `SendRawLog` at build_logger.go:238-246). `Logger.Errorln`, `Warningln`, `SoftErrorln`, `Println`, `Infoln` are inherited from the embedded `internal.Tee` (build_logger.go:39-40, 82). `Tee.log` (internal/tee.go:49-74) sends the formatted line to `t.logFn` (which is `SendRawLog`, going through `l.w` and thus the masking chain) **and separately** calls `t.entry.Logln(level, args...)` at line 73 with the raw, un-sanitized `args`. There is no masker/tokensanitizer/urlsanitizer call anywhere near `t.entry.Logln`.

This is directly demonstrated by the existing test `TestLogLineWithSecret` (common/buildlogger/build_logger_test.go:66-86): after calling `l.Errorln("... X-Amz-Signature=abcd1234&private_token=abcd1234")`, the assertions confirm `jt.Read()` (job trace) contains the masked string `[MASKED]`, while `output.String()` (the hijacked `logrus.StandardLogger().Out`, standing in for the runner's own log) contains the **unmasked** secret. The test itself proves the exploit works exactly as described — masking is asymmetric between the two sinks by design of `Tee.log`.

Whether this becomes attacker-exploitable depends on whether any Errorln/Warningln/etc. call site in the runner passes attacker-influenced content (e.g., masked CI/CD variable values, `private_token`/signed-URL query strings from a git/artifact/cache URL) into these log functions. Search across the codebase shows numerous callers of `Errorln`/`Warningln` (e.g., `common/build.go`, `executors/docker/docker.go`, `executors/kubernetes/kubernetes.go`, `network/gitlab.go`) that log error strings derived from external operations (HTTP failures, exec failures, git/artifact fetch errors), some of which can embed URLs with masked tokens (e.g., signed artifact/cache URLs, CI_JOB_TOKEN-embedded URLs) or masked variable values that end up in an error message. I was not able to fully trace every call site in this session to confirm a concrete production example with attacker-fully-controlled content reaching Errorln, but the sink itself is confirmed unconditionally unsafe: any code path that puts masked content into an Errorln/Warningln/Println argument bypasses masking en route to the runner log/logrus output.

Existing protections (masker, tokensanitizer, urlsanitizer) are wired only into `l.wrap()` for `l.w`/`l.base`, and are entirely absent from the `Tee.log` → `t.entry.Logln` path. There is no check or guard preventing this.

### Impact Explanation
Any secret/masked value that is placed into an argument to `Logger.Errorln`, `Warningln`, `SoftErrorln`, `Println`, or `Infoln` is exposed in cleartext in the runner's own logrus/host log stream, even though the same value is correctly masked in the job trace visible to the pipeline author. On a shared runner (fleet runner, GitLab.com shared runners, or any runner whose host logs are aggregated/exported to a support or logging platform), this creates cross-job/cross-tenant secret exposure to whoever has access to that log-aggregation surface — independent of any runner admin misconfiguration, since this is a design gap in the buildlogger's Tee, not a config option.

### Likelihood Explanation
The vulnerable code path is unconditionally reachable whenever `Logger.Errorln`/`Warningln`/etc. is invoked with a string containing masked content, and is not gated by any feature flag or admin option — `TeeOnly` opts *out* of teeing entirely but that's not the default. The precondition is that some caller places masked variable values, private tokens, or signed URLs into an error/warning log line rather than the raw trace writer. The provided unit test (`TestLogLineWithSecret`) already demonstrates the mechanism deterministically and repeatably with no special environment needed, confirming feasibility with 100% reproducibility of the "log the same content to trace and runner log" primitive. Concrete confirmation of a currently reachable attacker-controlled call site producing a masked secret in an `Errorln` argument was not fully enumerated in this pass, so likelihood should be treated as "mechanism confirmed, full attacker-reachability enumeration incomplete."

### Recommendation
Sanitize `args` before they're passed to `t.entry.Logln` in `internal.Tee.log` (internal/tee.go:73) — e.g., run the same masker/tokensanitizer/urlsanitizer transformations (or a shared masking function) over the formatted `logLine` string before logging it to `t.entry`, rather than only applying them to the trace-writer path. Alternatively, ensure `Logger.Errorln`/`Warningln`/etc. never receive raw un-masked secret material by having callers route sensitive content only through the trace writer (`l.w`) and never through the Tee's `t.entry` sink.

### Proof of Concept
Existing test `common/buildlogger/build_logger_test.go:66-86` (`TestLogLineWithSecret`) already serves as the PoC:
```go
l.Errorln("Get http://localhost/?id=123&X-Amz-Signature=abcd1234&private_token=abcd1234")
assert.Contains(t, jt.Read(), `X-Amz-Signature=[MASKED]&private_token=[MASKED]`) // trace: masked
assert.Contains(t, output.String(), `X-Amz-Signature=abcd1234&private_token=abcd1234`) // runner log: UNMASKED
```
Expected assertion for a fixed implementation: `output.String()` should also contain `[MASKED]` instead of the raw secret value — the current code path fails this stronger assertion, which is the bug.
