Based on the investigation, I found a genuine analog. Let me lay out the finding.

### Title
Pre-commit-threshold recheck omits sortition-canonicity re-validation, letting a signer sign a block whose tenure has been orphaned — ([File: stacks-signer/src/v0/signer.rs])

### Summary
The Lottery bug lets a state-changing action (claim) be raced ahead of a trade that was priced on stale state, breaking the buyer's assumed equality between "ticket held" and "reward claimable." The signer analog: a block's "is my tenure still canonical / still valid" fact is checked once, early (at proposal arrival and at node validate-ok), but the *narrower* recheck performed immediately before the signature is actually produced — `check_block_against_signer_db_state` — never re-asks that question. If the underlying fact changes (a Bitcoin reorg orphans the tenure) in the window between validate-ok and the pre-commit threshold being reached, and no rival block has yet been proposed/signed to trip the separate conflict guard, the signer proceeds straight to signing a now non-canonical block.

### Finding Description
`check_block_against_signer_db_state` is explicitly documented as incomplete and is the *only* re-check run both right after node validate-ok and again right before a signature is placed at the pre-commit threshold: [1](#0-0) 

It only re-derives tenure continuity (`check_tenure_change_confirms_parent` / `check_latest_block_in_tenure`) from signed blocks in the signer's own DB: [2](#0-1) 

It does **not** re-run the fuller `check_proposal` machinery that was used at proposal arrival, which is what actually verifies sortition canonicity, miner-invalidation status, and timeout state: [3](#0-2) 

At the pre-commit-threshold path, this same narrow recheck is invoked immediately before the signer signs: [4](#0-3) 

The only other safety net at signing time is the *signed-conflict* guard, which asks the node whether a conflicting signed block's tenure/sortition is still canonical — but this guard only fires when `get_signed_conflicts` returns something, i.e. when the signer already knows about a rival signed block: [5](#0-4) 

The documentation itself acknowledges this gap for a related check (`DuplicateBlockFound`) and states the own-tenure conflict branch is relied on to cover it — but that branch, too, is only reached when `conflicts` is non-empty: [6](#0-5) 

So the sequence is:
1. Miner proposes tenure-start block B for tenure T. Signer's full `check_proposal` passes (T's sortition is canonical at that instant).
2. Node validates B "Ok"; signer re-checks only via `check_block_against_signer_db_state` (tenure continuity), passes, `mark_pre_committed`, broadcasts pre-commit.
3. Before 70% pre-commit weight is reached, a Bitcoin reorg orphans T's sortition (no signer has yet proposed/observed a rival block at this height, so `get_signed_conflicts` is empty for every signer).
4. Once 70% pre-commit weight accumulates, each signer re-runs only `check_block_against_signer_db_state` — which still passes, because it never asks whether T's sortition is still on the canonical burn chain — and each signs B.

### Impact Explanation
This breaks the "signed vs. canonical" equality directly: a signer places a genuine signature over a block whose tenure is no longer on the canonical Bitcoin fork. This is a Critical-class outcome per the rules (a signer signing a non-canonical block), and it can occur across the honest signer set simultaneously since they all validated B before the reorg and share the same incomplete recheck — no collusion or majority of malicious signers is required, only the naturally-occurring race between reorg timing and pre-commit-threshold timing.

### Likelihood Explanation
The pre-commit round is explicitly designed to take time (waiting for 70% weight), which is exactly the window during which a reorg can land. The vulnerable path additionally requires that no rival block has yet reached the signer's local view (so the separate signed-conflict guard doesn't trigger) — a plausible condition for tenure-start blocks proposed promptly after a sortition, before the reorging chain's own tenure-start block propagates.

### Recommendation
Re-run (or fold into) `check_block_against_signer_db_state` an explicit re-verification that the block's own tenure sortition is still canonical (equivalent to the node-side `check_block_has_valid_tenure`/`NonCanonicalTenure` check, or the signer-side sortition-status checks in `check_proposal`), not just tenure-height continuity, immediately before a signature is emitted at the pre-commit threshold — mirroring the mitigation pattern the bug report recommends (re-validate immediately before the irreversible action, rather than relying on a stale earlier check).

### Proof of Concept
Conceptual reproduction using the existing test harness (`stacks-signer/src/v0/tests.rs` sibling-scenario helpers) or an integration test similar to those in `stacks-node/src/tests/nakamoto_integrations.rs`:
1. Propose tenure-start block B for tenure T; drive it through `handle_block_proposal` → node validate-ok → `mark_pre_committed` (as in `handle_block_validate_ok`, lines 1940-1984).
2. Before reaching pre-commit weight threshold, orphan T's sortition (simulate a reorg so that a subsequent `check_proposal`/node call for T would fail with `NonCanonicalTenure`/`ReorgNotAllowed`), while ensuring no rival block at T's height has been proposed to the signer yet (so `get_signed_conflicts` stays empty).
3. Deliver enough `BlockPreCommit` messages to cross the 70% weight threshold via `handle_block_pre_commit`.
4. Observe that `check_block_against_signer_db_state` still returns `None` (passes) and the signer proceeds to `mark_locally_accepted`/signs B, despite T no longer being canonical.

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we

  pox bitvec, and tenure-extend rules before delegating here.

Because the duplicate check never runs again, a block that crosses the pre-commit
threshold long after it was proposed relies on section 5's own-tenure conflict
guard to cover the same ground.
