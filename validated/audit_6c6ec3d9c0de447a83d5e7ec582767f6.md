### Title
Stale APR0 withdraw receipt makes `prepareStopEpochWithApr0` revert once APR is raised, freezing the epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Kerberos CVE is a reachable-assertion bug: an attacker who first acquires a "legacy-mode" credential (old enctype krbtgt ticket) can later crash the KDC through a normal request path (S4U2Self). The analog in `IdleCreditVault` is the APR0 accounting guard in `prepareStopEpochWithApr0`: an unprivileged lender who opens a withdraw request while `unscaledApr == 0` permanently plants an `apr0TotalPrincipal != 0` state that turns a later, perfectly honest `stopEpoch` into a guaranteed revert once the manager sets a nonzero APR. The attacker-held receipt acts like the weak-enctype ticket: it arms a fatal assertion inside a privileged flow the attacker never calls directly.

### Finding Description
`requestWithdraw` routes any request made while `unscaledApr == 0` (and pool not closed) into `_requestWithdrawApr0`, which grows `apr0TotalPrincipal` and stores per-user `apr0Users[_user].principal`/`principalEpoch` [1](#0-0) . The only place that bucket is closed is inside `prepareStopEpochWithApr0`, which is `_onlyIdleCDO` and is invoked during `stopEpoch`. Before closing the bucket it reverts whenever APR is no longer zero:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) return (...);
if (unscaledApr != 0) {
  revert NotAllowed();
}
``` [2](#0-1) 

The revert executes *before* `apr0TotalPrincipal = 0` is reached [3](#0-2) , so the revert does not self-heal. Nothing forces an APR0 requester to settle or claim: `_settleApr0` only runs lazily inside the user's own `claimWithdrawRequest`, and even it does not decrement `apr0TotalPrincipal` — only a successful `prepareStopEpochWithApr0` does [4](#0-3) . `requestWithdraw` has no guard preventing new APR0 requests while old ones are unsettled (the `lossRecoveryPriceByEpoch` check only blocks users with a *loss-adjusted* receipt) [5](#0-4) .

Attack sequence:
1. Manager runs an epoch with `setAprs(0, 0)` (APR0 mode is a supported configuration; the test suite sets it via manager) [6](#0-5) .
2. Attacker (any KYC-passing lender/tranche holder) calls `cdoEpoch.requestWithdraw(dustAmount, tranche)` in the buffer phase. `apr0TotalPrincipal` becomes nonzero and stays nonzero forever unless a stopEpoch succeeds while APR is 0.
3. Epoch runs; `stopEpoch` succeeds (APR still 0, so `prepareStopEpochWithApr0` settles and zeroes the bucket only if this stop happens while APR is 0 — if the attacker's request lands in an epoch whose *next* stop occurs after APR changed, skip to step 4 with bucket still armed; note the bucket survives across epochs because `apr0TotalPrincipal` is only closed on a *successful* stop, and an unsettled request epoch `< epochNumber` keeps `apr0Users` data intact).
4. Manager later calls `setAprs(x, y)` with `x != 0` for a new epoch — a routine, honest operation.
5. Attacker re-arms the bucket is unnecessary: if any request was made while APR was 0 and its `apr0TotalPrincipal` was never zeroed (e.g., request placed in buffer *after* the last APR0 stopEpoch settled, i.e., between `prepareStopEpochWithApr0` closing the bucket and the APR change taking effect), then every subsequent `stopEpoch` call hits `if (unscaledApr != 0) revert NotAllowed()` and reverts.

The critical ordering: `requestWithdraw` snapshots `unscaledApr == 0` at request time [7](#0-6) , but `prepareStopEpochWithApr0` re-evaluates `unscaledApr != 0` at stop time. During the buffer phase between `stopEpoch` (which set APR for the next epoch to 0) and a later APR change, an attacker can deposit APR0 principal that will explode on the next stop under nonzero APR.

### Impact Explanation
While `unscaledApr != 0 && apr0TotalPrincipal != 0`, every `stopEpoch`/`stopEpochWithDuration` reverts inside `prepareStopEpochWithApr0`. The running epoch can never be closed: borrower repayment cannot be booked, `epochNumber` cannot advance, pending withdraw receipts cannot be funded (`pendingWithdraws` is only drained via `collectWithdrawFunds` during stop) [8](#0-7) , and claimers remain blocked by the `epochNumber <= lastWithdrawRequest[_user]` gate [9](#0-8) . All LP and queued funds are frozen until the manager restores `unscaledApr = 0` to unstick the bucket. This is a temporary freezing of the entire vault's TVL (the full `getContractValue()` plus `pendingWithdraws`), quantified as the whole pool NAV for the duration of the freeze — matching the accepted "temporary freezing with quantified loss" impact class and mirroring the CVE's crash-the-KDC denial of service.

### Likelihood Explanation
The attacker needs only a KYC-passed wallet and a dust-sized tranche position (no minimum is enforced on `requestWithdraw` beyond `_amount == 0` early-return). The trigger requires two ordinary conditions: an APR0 epoch existing at request time (a supported, tested mode) and the manager later raising APR — a normal operation between epochs. No privileged misbehavior is needed, and no existing guard stops it: the `lossRecoveryPriceByEpoch` guard only covers haircut receipts, `isClosed` only covers pool-close, and there is no check forcing APR0 requesters to claim before APR changes. Residual uncertainty: if `setAprs` for the next epoch is only applied atomically inside `stopEpoch` after `prepareStopEpochWithApr0`, the freeze is temporary rather than permanent, since returning APR to 0 unsticks the bucket — but the DoS window is still fully attacker-caused from a dust position.

### Recommendation
Remove the `unscaledApr != 0` revert and instead settle/close the APR0 bucket unconditionally at stopEpoch (treat the pending APR0 principal as settled at `apr0RateByEpoch` = 0 if APR changed, or carry it with a per-request recorded APR snapshot). Alternatively, snapshot the APR into `apr0Users[_user]`/`apr0RateByEpoch` at request time and settle against the snapshot, so a later APR change cannot retroactively invalidate already-booked receipts. A defense-in-depth option is to sweep stale `apr0TotalPrincipal` into `apr0Users` settlement during `startEpoch` before any APR change can take effect.

### Proof of Concept
A Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol`, which already has `_startEpochAndCheckPrices`, `_depositWithUser`, `setAprs` via manager) would:

```solidity
function testApr0RequestBlocksStopEpochAfterAprRaise() external {
    // Epoch N runs at APR = 0
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    uint256 amount = 10000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true); // KYC'd lender

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch()); // APR0 stop OK; bucket zeroed

    // Buffer phase: attacker requests a dust withdraw while unscaledApr is still 0
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // arms apr0TotalPrincipal > 0

    // Honest manager raises APR for the next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());

    // Every stopEpoch now reverts inside prepareStopEpochWithApr0 -> epoch cannot close
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);
}
```

I could not fully verify within the iteration budget the exact call site ordering of `prepareStopEpochWithApr0` inside `IdleCDOEpochVariant.stopEpoch` and whether `setAprs` can be re-lowered to 0 to recover; the PoC assertion (revert on stop) follows directly from lines 499–508, but the "temporary vs. permanent" classification hinges on the manager being able to restore APR=0 — which `setAprs(0,0)` in the existing test demonstrates is permitted.
