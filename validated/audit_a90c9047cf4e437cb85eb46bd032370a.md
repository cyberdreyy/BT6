### Title
Missing ERC4626 deposit-availability check in `ProgrammableBorrower._depositToVault` reverts `startEpoch` and freezes queued deposits and pending withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.startEpochAccounting` unconditionally redeploys its entire idle underlying balance into the configured ERC4626 vault via `_depositToVault` (`vault.deposit`). There is no `maxDeposit`/`maxMint` availability check, no try/catch, and no alternative path — exactly the M-05 bug class: a single unconditional external deposit call whose revert bricks the whole `startEpoch` transaction. An unprivileged attacker who is also a user of the programmable borrower's ERC4626 vault can fill the vault's supply cap (or otherwise make `deposit` revert, e.g., deposit-asset pause on Morpho-style vaults), causing every `startEpoch` call to revert until the attacker unwinds.

### Finding Description
In `startEpochAccounting` (hooks into `IdleCDOEpochVariant.startEpoch` via `onStartEpoch`), idle underlying is parked in the vault:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol
uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
// Any idle balance left on the contract between epochs is parked immediately into the vault.
_depositToVault(underlyingToken.balanceOf(address(this)), 0);
```

`_depositToVault` calls `vault.deposit(_assetAmount, address(this))` directly with no guard:

```solidity
function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
    if (_assetAmount == 0) return;
    uint256 shares = vault.deposit(_assetAmount, address(this)); // reverts if cap reached / deposits paused
    ...
}
```

Contrast with the stop path, which was deliberately made resilient: `onStopEpoch` wraps `vault.withdraw` in try/catch and either returns `false` (triggering the default path) or reverts the retryable `StopEpochVaultLiquidityUnavailable`, and `sendFundsToBorrower` in `IdleCDOEpochVariant` is wrapped in a `try this.sendFundsToBorrower` self-call with a default-handling `catch`. The deposit path has no such fallback — any revert propagates and reverts the entire `startEpoch`, which is the same shape as the Asymmetry `stake()` → `Reth.deposit()` revert propagation.

### Impact Explanation
While `vault.deposit` reverts, the manager cannot start a new epoch. Buffer-period deposits (including `IdleCDOEpochQueue` pending deposits already transferred to the strategy) and any withdrawal receipts awaiting epoch processing remain locked: queued depositors cannot `claimDepositRequest` (epoch never priced) and withdraw receipts cannot be funded (no epoch runs, no borrower repayment cycle). This is temporary freezing of all vault user funds for the duration the attacker keeps the vault saturated, at the attacker's chosen cost of parking capital in the target ERC4626 vault — a griefing cost, not theft, but accepted impact under the "temporary freezing" criterion.

### Likelihood Explanation
Medium-low. It requires the programmable borrower to hold a nonzero idle underlying balance at epoch start (common: buffer deposits sent to the strategy land as on-hand balance before redeployment) and an ERC4626 vault with a saturatable deposit cap or pausable deposits. The attacker only needs an ordinary vault depositor position — no privileged role — and can hold the cap filled by depositing repeatedly as room frees. The borrower/owner have a partial mitigation (`emergencyExitVault` only redeems existing shares; it cannot skip the deposit), so there is no clean owner escape that avoids the revert on `startEpoch` while an idle balance exists.

### Recommendation
Mirror the availability-check pattern the original audit asked for: check `vault.maxDeposit(address(this))` (and/or `maxMint`) before calling `deposit`, deposit only up to the available amount, and leave the remainder on the contract (it is already covered by `startAssets` accounting). Optionally wrap `vault.deposit` in try/catch so a mid-transaction cap change cannot revert `startEpoch`.

### Proof of Concept
Foundry fork (Morpho/Gauntlet-style capped vault), skeleton:

```solidity
function testStartEpochRevertsWhenVaultDepositUnavailable() external {
    // setup: programmable borrower credit vault with ERC4626 `vault` that has a supply cap
    idleCDO.depositAA(amount);                 // buffer deposit
    // attacker: fill vault supply cap as an ordinary depositor
    deal(address(underlying), attacker, vault.maxDeposit(address(programmableBorrower)));
    vm.startPrank(attacker);
    underlying.approve(address(vault), type(uint256).max);
    vault.deposit(vault.maxDeposit(address(attacker)) > 0
        ? remainingCap : remainingCap, attacker); // saturate cap so deposit() reverts
    vm.stopPrank();

    vm.expectRevert(); // ERC4626ExceededMaxDeposit
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // deposits stay queued, epoch never starts while cap is saturated
    assertFalse(cdoEpoch.isEpochRunning());
}
```

Caveat: I did not have remaining iterations to confirm the exact wiring of `onStartEpoch`/`startEpochAccounting` inside `IdleCDOEpochVariant.startEpoch` or whether an owner-side path exists to skip vault redeposit entirely; the finding stands if, as the code shows, `_depositToVault` is reached unconditionally on the start-epoch path with a nonzero idle balance.
