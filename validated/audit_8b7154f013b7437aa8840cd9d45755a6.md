### Title
GET /v2/external_initiators leaks all External Initiators' AccessKey/OutgoingToken node-wide with no role check - ([File: core/web/router.go])

### Summary
The route `GET /v2/external_initiators` is registered without any role wrapper, requiring only session/API-token authentication, and `ExternalInitiatorsController.Index` returns every external initiator's `AccessKey` and `OutgoingToken` platform-wide via `presenters.ExternalInitiatorResource`, with no per-owner filtering or redaction.

### Finding Description
`v2Routes` registers the route as `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` [1](#0-0) , unlike sibling mutating routes on the same resource (`POST`/`DELETE`) which are wrapped with `auth.RequiresEditRole` [2](#0-1) . The enclosing `authv2` group only requires `AuthenticateByToken` or `AuthenticateBySession` [3](#0-2) , with no minimum role. This is inconsistent with most other sensitive list endpoints in the same file (e.g. `/users` is `RequiresAdminRole`) but consistent with several other `Index` routes that also lack role gating (e.g. `/keys/eth`, `/keys/csa`, `/jobs`), so the missing role check here is a genuine gap relative to the credential sensitivity of the data returned, not a unique anomaly in the router's general pattern.

`ExternalInitiatorsController.Index` fetches all external initiators via `eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)` and maps every record to `presenters.NewExternalInitiatorResource(initiator)` without any owner/session scoping [4](#0-3) . `ExternalInitiatorResource` includes `AccessKey` and `OutgoingToken` fields directly from the DB row [5](#0-4) . The existing integration test confirms this behavior: a generic authenticated `NewHTTPClient` retrieves both `eiFoo` and `eiBar`'s `AccessKey` and `OutgoingToken` values across pages, with no filtering by caller identity [6](#0-5) .

Because the entire admin GUI/API session model in Chainlink is single-tenant (all authenticated users manage the same node's resources — jobs, keys, bridges, etc.) rather than multi-tenant/per-caller isolated, there is no inherent per-owner concept for external initiators to filter against; "every EI belongs to the operator of this node." The only distinguishing factor is *role* (view/run/edit/admin), and this route imposes no role floor, meaning even the lowest role capable of session/token auth to `/v2/*` (which in this app model requires at least `view` role per the general auth middleware requirement) can retrieve `AccessKey`/`OutgoingToken` for all EIs. The write operations (`Create`/`Destroy`) are correctly gated to edit role, highlighting that Index was likely just overlooked by the same policy.

### Impact Explanation
Impact is credential/secret metadata disclosure: a caller who only needs baseline authenticated access (not edit/admin) can enumerate `AccessKey` and `OutgoingToken` for every external initiator configured on the node. The `OutgoingToken` is used by the node to authenticate itself when calling out to an external initiator's webhook; leaking it lets a low-privileged accountholder impersonate the node against that external initiator's endpoint, or use `AccessKey` values to correlate/replay against `/v2/jobs/:ID/runs` triggers if the corresponding EI's `IncomingSecret` is guessed or already known through other means. This aligns with a "sensitive data exposure" / "unauthorized information disclosure" class rather than direct fund loss, since the associated `Secret`/`IncomingSecret` values are not returned by this endpoint.

### Likelihood Explanation
Any principal that can obtain a valid session cookie or API token for the node (the minimal `view`-capable role, per the app's role hierarchy of view < run < edit < admin) can call `GET /v2/external_initiators?size=1000` and receive the full list in one paginated sweep — no special permission, timing, or race condition is needed, and the behavior is deterministic/repeatable as shown by the existing test. This makes it trivially and repeatably exploitable by the lowest role capable of reaching `/v2/*`.

### Recommendation
Wrap the `Index` route with the same minimum role required for `Create`/`Destroy` on this resource (`auth.RequiresEditRole` or stricter, e.g. `RequiresAdminRole` given it exposes long-lived outbound credentials), i.e. change `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` to `authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))` in `core/web/router.go`. Additionally, consider redacting `AccessKey`/`OutgoingToken` from the list presenter (`presenters.ExternalInitiatorResource`) and only exposing them at creation time (as is already done via `ExternalInitiatorAuthentication`) or via a dedicated admin-only "reveal" action, since list views are commonly used broadly and secrets should not round-trip through them repeatedly.

### Proof of Concept
1. In `core/web/external_initiators_controller_test.go`, extend `TestExternalInitiatorsController_Index` (or add a new test) to create an HTTP client scoped to a `view`-role (or `run`-role) session/API key instead of the default `NewHTTPClient(nil)` (which appears to default to admin in tests) — use `cltest.CreateUser`/session helpers analogous to those used in other role-gated controller tests (e.g. `csa_keys_controller_test.go`, `user_controller_test.go`) to build a client authenticated only as `view` or `run`.
2. Call `GET /v2/external_initiators?size=1000` with that client.
3. Assert current (vulnerable) behavior: HTTP 200 is returned (not 401/403), and the parsed `presenters.ExternalInitiatorResource` list contains non-empty `AccessKey` and `OutgoingToken` fields matching the DB-inserted `eiFoo`/`eiBar` values, as already demonstrated by the existing assertions at `core/web/external_initiators_controller_test.go:108-109,125-126`.
4. After applying the fix (adding `auth.RequiresEditRole` to the route), assert the same request from a `view`/`run` client now returns `403 Forbidden`, while an `edit`/`admin` client still returns `200` with the resource list.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
	URL           *models.WebURL `json:"url"`
	AccessKey     string         `json:"accessKey"`
	OutgoingToken string         `json:"outgoingToken"`
	CreatedAt     time.Time      `json:"createdAt"`
	UpdatedAt     time.Time      `json:"updatedAt"`

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
```
