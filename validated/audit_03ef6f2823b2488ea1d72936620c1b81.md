### Title
User enumeration and MFA/WebAuthn credential metadata leakage via distinguishable `SessionsController.Create` error responses - ([File: core/web/sessions_controller.go])

### Summary
`SessionsController.Create` forwards the raw error returned by `AuthenticationProvider().CreateSession` directly into the HTTP 401 body via `jsonAPIError(c, http.StatusUnauthorized, err)`, without normalizing or redacting it. The underlying `localauth.orm.CreateSession` implementation returns three distinguishable error strings/payloads depending on whether the email doesn't exist, exists with a wrong password, or exists and requires a WebAuthn/MFA challenge — allowing an unauthenticated attacker to enumerate valid accounts and, once account/password are known, to retrieve the raw WebAuthn challenge JSON.

### Finding Description
The handler: [1](#0-0) 
passes `err` from `CreateSession` straight to the client.

In `core/sessions/localauth/orm.go`, `CreateSession` has three distinct failure/response paths:
1. Unknown email → `FindUser` fails and the raw DB error (e.g. `sql: no rows in result set`) is returned unmodified: [2](#0-1) 
2. Known email, wrong password → a distinct literal string `"Invalid password"` is returned: [3](#0-2) 
3. Known email, correct password, MFA required → the WebAuthn challenge options are JSON-marshaled and returned as the error message itself, which is then serialized into the client-visible response body: [4](#0-3) 

Because the controller does not normalize these into one generic message, an unauthenticated attacker sending `POST /sessions` with different emails/passwords can trivially distinguish:
- "account does not exist" (raw SQL error, different string/format/length) vs.
- "account exists, wrong password" (`"Invalid password"`).

This is textbook credential-enumeration via error-message oracle, requiring no preconditions or credentials — any anonymous caller of `/sessions` can probe it repeatedly.

The MFA-challenge leak (case 3) is a separate, lower-severity issue since it requires the attacker to already possess a valid email+password pair; the JSON returned by `sessions.BeginWebAuthnLogin` is designed to be sent to the legitimate client per the WebAuthn spec (it contains only public challenge/allowCredential data, not secrets), so this alone does not constitute a secret disclosure, but it is exposed through an error field rather than a proper success-shaped API response, which is an API design flaw worth flagging alongside the enumeration issue.

No auth middleware exists to intercept this path since `/sessions` `Create` is intentionally public (pre-authentication endpoint), and there is no rate limiting or generic-error normalization visible in this file to prevent probing.

### Impact Explanation
Concrete impact: unauthenticated user enumeration of node operator/API accounts, which aids targeted credential-stuffing or phishing against confirmed accounts, and reveals whether MFA is enabled per case in the WebAuthn-required branch. This maps to a low/informational-to-low severity "sensitive information disclosure via error message" class rather than a direct authentication bypass or fund-movement issue — no session, token, or password is disclosed, only account-existence metadata and (post-password-knowledge) public WebAuthn challenge data.

### Likelihood Explanation
Fully unauthenticated, zero preconditions: any anonymous client can send repeated `POST /sessions` requests with different `email` values and observe response-body differences. Fully repeatable and scriptable (differencing engine trivially distinguishes `"Invalid email"`/DB-error text from `"Invalid password"`).

### Recommendation
Normalize all authentication failure branches in `orm.CreateSession` (unknown email, wrong password, and MFA errors that aren't specifically the challenge-required flow) to return one generic, identical error (e.g., `"invalid credentials"`), and ensure `SessionsController.Create` returns a generic message string rather than `err.Error()` verbatim for all non-2xx branches except the specific WebAuthn challenge-required flow, which should be returned via a distinct, well-typed response field/status (not embedded inside a generic error string) so its presence/absence isn't itself an oracle beyond what's necessary.

### Proof of Concept
Go handler-level integration test (`core/web/sessions_controller_test.go` style):
1. Seed one known user (`known@example.com` / correct hashed password), no WebAuthn tokens.
2. Case A: `POST /sessions {"email":"unknown@example.com","password":"x"}` → capture status (401) and body.
3. Case B: `POST /sessions {"email":"known@example.com","password":"wrongpass"}` → capture status (401) and body.
4. Assert `bodyA != bodyB` (currently true, proving enumeration) — the fix should assert `bodyA == bodyB` after remediation.
5. Additional case: seed user with WebAuthn token, POST with correct password and no `webAuthnData` → assert response body contains raw WebAuthn `options` JSON inside the `errors[].detail` field, confirming the challenge is exposed through the generic error channel rather than a structured field.
