So a signer that learns a tenure's first block reached the group threshold purely from peers' `BlockResponse::Accepted` messages (via `handle_block_signature` → `store_and_process_block_signature`, which calls `mark_locally_accepted(true)`), without ever pre-committing to it itself (no `mark_pre_committed` call, which is the only path that stamps `approved_time`), ends up with `approved_time == None` while `get_first_approved_block_in_tenure` still returns that block (its query matches on `signed_group IS NOT NULL`).

### Title
Reorg-timing bypass lets a signer sanction reorging a globally-accepted tenure it never locally timed - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` decides whether a miner may build off something other than the prior sortition (a reorg). For each reorged tenure with exactly one globally accepted block, it computes `proposal_to_sortition = sortition_state_received_time - local_block_info.approved_time` and allows the reorg only if that duration is under `first_proposal_burn_block_timing`. When `local_block_info.approved_time` is `None`, the code silently substitutes `0`, which is always "close enough" to trigger the permit path.

### Finding Description [1](#0-0)

`local_block_info` is fetched via `get_first_approved_block_in_tenure`, whose SQL predicate is `signed_self IS NOT NULL OR signed_group IS NOT NULL OR approved_time IS NOT NULL` [2](#0-1) . A block can satisfy this via `signed_group` alone while `approved_time` stays `None`, because `mark_locally_accepted(true)` (the group-signed path invoked from `store_and_process_block_signature` when peer signatures cross threshold) and `mark_globally_accepted` both only touch `signed_group`/state, never `approved_time` [3](#0-2) . `approved_time` is stamped only by `mark_pre_committed` or by the *self-signed* branch of `mark_locally_accepted(false)` [4](#0-3) .

So any signer that never personally pre-committed/self-signed a tenure's first block (e.g., it was busy validating a competing proposal, restarted mid-tenure, or simply lost the pre-commit race to peers and only later absorbed the peers' accepted signatures) but did observe enough peer signatures to record `signed_group`, will hit the `None` branch and treat that tenure's first block as a "late-arriving proposal" with `proposal_to_sortition = 0`. Since `0 < first_proposal_burn_block_timing` is true for any non-zero configured timeout (the docs describe this exact case as the one where a "poorly timed" tenure is legitimately reorgable — see `sample/conf/signer/mainnet-signer-conf.toml:151-166`), the check unconditionally falls into the "allow reorg" branch and calls `mark_tenure_superseded`, regardless of how long ago that tenure's block was actually confirmed.

This breaks the "approved-parent vs canonical" equality: the tenure being reorged already has a **globally accepted** (network-canonical) block — the very thing `check_parent_tenure_choice`'s `globally_accepted_blocks > 1` guard is meant to protect once there is more than one such block — but for exactly the boundary case of a single, long-settled globally accepted block, a signer with an incomplete local timing record will approve a `TenureChange`/`BlockFound` proposal from a different miner that reorgs it, and will additionally record the reorged tenure as `superseded` in its own `SignerDb` (`mark_tenure_superseded`), voiding its own earlier signature as a future conflict-guard entry (see `get_signed_conflicts` documentation: superseded tenures are excluded from blocking future signatures) [5](#0-4) . That signer then proceeds to sign the reorging block via the normal `validate_tenure_change_payload` → `check_parent_tenure_choice` → sign flow [6](#0-5) .

### Impact Explanation
This is a Critical-class break per the rules: it causes a signer to sign a block that reorgs a canonical (globally accepted) tenure it should have refused, i.e. a "signer signing a conflicting/non-canonical-parent block." Since the fault is purely a function of that one signer's local bookkeeping gap (missing `approved_time`), it does not require compromising a majority, another signer's key, or node access — only a scenario (achievable by ordinary network timing/gossip, or a signer restart) where a signer never pre-committed to a tenure's first block itself but still marked it globally accepted from peer gossip.

### Likelihood Explanation
The precondition — a signer observes/records `signed_group`/`GloballyAccepted` for a block without itself ever calling `mark_pre_committed` or self-signing it first — is a normal, frequently-occurring race in the existing pre-commit/signature-gossip design (explicitly acknowledged elsewhere in the flow docs, e.g. the "outdated peer" fallback in `handle_block_response`/`handle_block_signature` treats late peer acceptances specially precisely because peers can lag). A signer restarting mid-tenure and re-syncing state from the node/peers, or a signer that loses the pre-commit race but later ingests the group's accept messages, would trigger it. No attacker action beyond normal timing is strictly required, though a miner could also intentionally target signers known to be behind on pre-commits to increase the chance of exploiting this gap when attempting the reorg.

### Recommendation
`check_parent_tenure_choice` should not silently equate "no locally recorded `approved_time`" with "definitely late-arriving / always eligible for reorg." Options:
- If `local_block_info.approved_time` is `None` but the block reached `GloballyAccepted`/`signed_group`, treat the timing as unknown and require it to be resolved against `signed_group`'s timestamp or the node's canonical record instead of defaulting to `0`.
- Alternatively, fail closed (refuse the reorg, same as the "no local knowledge for that tenure's block timing" branch a few lines above) rather than fail open, whenever a reliable local timing basis is unavailable for a tenure that already has a confirmed, globally accepted block.

### Proof of Concept
1. Set up 2+ signers with `first_proposal_burn_block_timing` at its default (60s).
2. Have Signer A validate and pre-commit Tenure 1's first block, then reach group threshold and broadcast; Signer B is offline/restarting during this window and misses the pre-commit gossip but later ingests enough `BlockResponse::Accepted` peer messages (post-restart resync) to call `mark_locally_accepted(true)`/`mark_globally_accepted` on Tenure 1's block — leaving Signer B's local `approved_time` for that block `None`.
3. Well after `first_proposal_burn_block_timing` has elapsed (e.g., minutes later), have a new miner win a sortition and propose a `TenureChange`/`BlockFound` block whose `prev_tenure_consensus_hash` reorgs Tenure 1 (parent tenure ≠ prior sortition).
4. On Signer B, `check_parent_tenure_choice` computes `proposal_to_sortition = 0` (the `None`-approved_time branch) and permits the reorg, calling `mark_tenure_superseded` and voting to sign the reorging block — while Signer A (with a valid `approved_time`) correctly refuses it as the timing window has long passed. This produces a signer that signs a block conflicting with a tenure that had already reached global (canonical) acceptance according to that same signer's own DB.
