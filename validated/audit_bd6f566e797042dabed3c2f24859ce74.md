### Title
Deterministic lockup account address enables front-run squatting with attacker-chosen vesting hash - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the new lockup contract's account ID purely from `sha256(owner_account_id)` concatenated with the factory account, independent of the caller or any nonce. Any unprivileged account can precompute this address for a target `owner_account_id` and submit their own `create` call one block ahead of the legitimate grantor, permanently occupying the address with an attacker-chosen `VestingScheduleOrHash::VestingHash` whose preimage they control, while the legitimate creator's later call fails atomically (refunded) since NEAR account creation cannot target an already-existing account.

### Finding Description
The invariant the question is probing is: `vesting_information` stored in the deployed lockup contract at address `H = sha256(owner_account_id) || factory` == the commitment chosen by the legitimate grantor (e.g. NEAR Foundation) for that `owner_account_id`. This binding is broken because `create` computes the target address purely from public input the caller supplies: [2](#0-1) 

Nothing ties `lockup_account_id` to `env::predecessor_account_id()`, a commit-reveal step, or any registry lookup that would prevent re-use/pre-emption of a specific owner's lockup address. The only guard that fires on a naming collision is NEAR's own runtime: `create_account()` fails on an already-existing account, which fails the whole batched receipt, and the `on_lockup_create` callback then simply refunds the caller's deposit: [3](#0-2) 

This refund path protects the *funds* of whichever party's transaction lands second, but it does nothing to protect the *address*. Once the attacker's transaction is mined first, the address `H` is permanently claimed with the attacker's parameters — including `vesting_schedule = VestingScheduleOrHash::VestingHash(hash)` for a schedule/salt pair only the attacker knows — and the legitimate grantor's subsequent transaction for the same `owner_account_id` can never succeed at that address. Note `foundation_account_id` itself cannot be spoofed by the attacker (it's forced to `self.foundation_account_id` in `create`, `lockup-factory/src/lib.rs:123-126`), but the vesting *hash* — the load-bearing commitment referenced later by `terminate_vesting` (`lockup/src/lib.rs`, verified via `VestingScheduleWithSalt::hash()` in `lockup-factory/src/types.rs:191-194`) — is entirely attacker-supplied. Because the hash only commits to whatever the attacker chooses, the "vesting commitment is the grantor's" invariant is broken: the deployed lockup at the expected, canonical address for that owner now enforces vesting terms nobody but the attacker agreed to or can correctly reveal.

### Impact Explanation
This matches the Critical category "a lockup deployed with parameters its rightful creator never chose." The legitimate grantor's attempt is blocked (their deposit is refunded, so they lose no NEAR directly), but the canonical, deterministic address for that `owner_account_id` is permanently squatted with attacker-chosen vesting/whitelist parameters. Any subsequent off-chain process, UI, or automation that assumes "the lockup for owner X lives at `sha256(X)+factory`" and deposits funds or relies on the vesting hash there is now interacting with a contract whose commitment nobody but the attacker can honestly satisfy — e.g. the real grantor cannot later call `terminate_vesting` with the true agreed schedule because it won't match the squatted hash, while the attacker (as sole holder of the preimage) can supply a schedule that is maximally favorable to whoever holds `owner_account_id`. This is repeatable for any `owner_account_id` an attacker can predict is about to be used, at the cost of just the minimum attached deposit each time.

### Likelihood Explanation
The attacker needs only a funded NEAR account and `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus knowledge (from mempool observation or public announcement, e.g. a known list of employee accounts for mass lockup deployment) of the `owner_account_id` about to be used by a legitimate grantor. No privileged role, key, or foundation access is required — `create` is `#[payable]` and open to any caller. The only timing requirement is placing one transaction ahead of the legitimate one, which is straightforward given NEAR's public mempool and the deterministic address computation.

### Recommendation
Bind the deployed lockup account's uniqueness/ownership more strongly to the legitimate grantor: e.g., require the factory's `foundation_account_id` (or another privileged/registered creator) to co-sign or be the exclusive caller for lockups that carry a `VestingScheduleOrHash::VestingHash`, or include an unpredictable/creator-bound component (e.g. `predecessor_account_id` or a foundation-issued nonce) in the derivation of `lockup_account_id`, so a random account cannot pre-empt the canonical address for a given owner.

### Proof of Concept
Using `near-sdk-sim`/`near-workspaces` (unit `testing_env!` cannot express two competing cross-contract `create_account` receipts):
1. Deploy `LockupFactory` with `foundation_account_id = foundation`.
2. As `attacker`, call `create(owner_account_id = "victim", vesting_schedule = Some(VestingHash(hash_of_attacker_secret_schedule)), ...)` with `MIN_ATTACHED_BALANCE`; assert the resulting lockup account `sha256("victim")+factory` now exists and its `vesting_information` equals `VestingHash(hash_of_attacker_secret_schedule)`.
3. As `foundation`/legitimate deployer, call `create(owner_account_id = "victim", vesting_schedule = Some(VestingHash(hash_of_real_schedule)), ...)` in the next block; assert the promise fails (`create_account` on an existing account), `on_lockup_create` returns `false`, and the caller's deposit is refunded.
4. Assert the address `sha256("victim")+factory` still stores the attacker's `VestingHash`, demonstrating the address was captured with parameters the legitimate grantor never chose.

        &mut self,

        attached_deposit: U128,

        if lockup_account_created {

        }
