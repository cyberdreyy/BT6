Rejection weight is never retracted when the same signer later signs, letting a single minority signer inflate `total_weight_rejected` past the block-reject threshold on an otherwise valid block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s per-block tally in `stackerdb_listener.rs` accumulates `total_weight_approved` and `total_weight_rejected` from signer messages keyed by `slot_id`. The bookkeeping used to prevent double-counting (`gathered_signatures` / `responded_signers`) is asymmetric: once a signer's `Reject` is counted into `total_weight_rejected` (which inserts the slot into `responded_signers`), a *later, legitimately signed* `Accept` for the same block from the same signer is still counted into `total_weight_approved` because the accept path only checks `gathered_signatures`, not `responded_signers`. The signer's own weight ends up counted in both buckets simultaneously, breaking the invariant `total_weight_approved + total_weight_rejected <= total_weight`.

### Finding Description
In `handle_signer_messages` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`), the `Accepted` branch does: [1](#0-0) 
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```
and the `Rejected` branch does: [2](#0-1) 
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```
Each branch only guards against re-processing *its own* message kind (`gathered_signatures` for accepts, `responded_signers` for the very first message of any kind for rejects). There is no check that prevents a signer who has already contributed weight to `total_weight_rejected` from *also* contributing weight to `total_weight_approved`.

Concretely: a single signer whose weight is below the 30% blocking-minority threshold can (1) send a `Rejected` response for a block (incrementing `total_weight_rejected` and marking `responded_signers`), then (2) re-evaluate and send a genuine, validly signed `Accepted` response for the *same* block (which is an explicitly supported transition in the signer's own local state machine, `LocallyRejected -> LocallyAccepted`, documented in `docs/signer-flows.md` section 2: "LocallyRejected --> LocallyAccepted : re-evaluated"). Because the accept branch never consults `responded_signers`, step (2) unconditionally adds the same signer's weight into `total_weight_approved` as well, since `slot_id` is not yet in `gathered_signatures`.

The coordinator's decision loop in `signer_coordinator.rs` checks the rejection condition *before* the acceptance condition and returns early: [3](#0-2) 
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ...
    return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    ...
    return Ok(...)
}
```
Because a single signer's weight can be phantom-counted into `total_weight_rejected` even though that signer ultimately produced a valid accepting signature, the sum of the two buckets can exceed `total_weight`. This breaks the "aggregated-weight vs verified-accepts" equality the coordinator relies on: the rejection bucket no longer reflects the set of signers who currently, verifiably, oppose the block. If enough of the remaining, distinct signer weight legitimately approves the block (i.e., real accept weight would otherwise clear the 70% threshold), the phantom extra rejection weight contributed by the flip-flopping signer can independently push `total_weight_rejected` past the 30% blocking-minority mark first, causing the miner to abandon a block that a genuine supermajority (by real, current votes) would have signed.

### Impact Explanation
This is a liveness/safety-tally break in the signer_set/coordinator equality "aggregated-weight vs verified-accepts": a single minority-weight signer, using only its own valid key (no majority, no other signer's key, no auth_token), can manufacture a false "30%+ reject" state by contributing to both tallies with one signature. The practical effect is that the miner's coordinator (`NakamotoSigningCoordinator`) incorrectly returns `SignersRejected` and abandons a block proposal that, based on the *current* votes of all signers, actually has enough real support to cross the 70% signing threshold — a tenure-stalling / block-production denial that is triggerable by a single sub-threshold-weight signer flipping its vote, not requiring flooding or a majority.

### Likelihood Explanation
The trigger requires only: (1) a single signer under the attacker's control (own key, no collusion needed), and (2) sending a `Rejected` response followed later by a legitimately re-evaluated `Accepted` response for the same block — both of which are normal, protocol-supported behaviors (the local FSM explicitly allows `LocallyRejected -> LocallyAccepted` re-evaluation, and the coordinator has no defense against it). No cryptographic forgery, no majority collusion, and no flooding is required — only ordinary vote-order manipulation by one participant.

### Recommendation
Make the reject/accept bookkeeping mutually exclusive and idempotent per signer: before crediting `total_weight_rejected`, check (and clear, if present) any prior contribution to `total_weight_approved` for that `slot_id`, and vice versa — i.e., track a single "current vote" per slot (accept or reject) and recompute both totals from the live set of current votes rather than accumulating monotonically increasing counters across state transitions. Concretely, `responded_signers`/`gathered_signatures` bookkeeping in `stackerdb_listener.rs` should be replaced with a single `HashMap<u32, Vote>` per block where inserting/overwriting a vote also subtracts the old weight from whichever total it had contributed to, guaranteeing `total_weight_approved + total_weight_rejected <= total_weight` at all times.

### Proof of Concept
Conceptual sequence exercising the bug purely through the documented protocol:
1. Miner proposes block `B`. Coordinator tracks `BlockStatus` for `B` with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer `S` (weight `w`, `w` below the 30% blocking-minority weight on its own) initially rejects `B` (e.g. due to a transient state, such as a race with `check_block_against_signer_db_state`) and broadcasts `BlockResponse::Rejected`. The listener's `Rejected` branch inserts `slot(S)` into `responded_signers` and adds `w` to `total_weight_rejected`.
3. Enough honest signers whose combined weight (plus `S`, if it later approves) would clear 70% send `Accepted` for `B`, but their combined weight *excluding* `S` alone doesn't cross the 30% *rejected*-blocking margin unless `S`'s weight is also present in the rejected bucket.
4. Signer `S` subsequently re-evaluates `B` per `should_reevaluate_block` / the documented `LocallyRejected -> LocallyAccepted` transition, and legitimately signs and broadcasts `BlockResponse::Accepted` for the same `B`. The listener's `Accepted` branch sees `slot(S)` is not in `gathered_signatures` and adds `w` to `total_weight_approved` as well — with no removal of `w` from `total_weight_rejected`.
5. Now `total_weight_rejected` still includes `S`'s weight `w` from step 2 even though `S`'s current, live vote is Accept. If the sum `total_weight_rejected(includes stale w) + weight_threshold > total_weight`, the coordinator's loop in `signer_coordinator.rs` (lines 509-518) triggers `Err(SignersRejected)` before ever reaching the `total_weight_approved >= weight_threshold` branch, aborting a block that in fact has sufficient live approving weight.
