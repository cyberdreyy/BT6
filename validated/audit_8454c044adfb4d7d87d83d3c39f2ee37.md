I found a valid analog: the multisig contracts in this repo have the exact same class of bug — a value used to authorize a state transition (here, confirmation count) is not correctly synchronized with the actual set of trusted parties (live signing keys) at execution time. This mirrors the Ajna bug's core pattern of "recorded claim vs. what is actually still backing it."

### Title
Stale confirmations from removed multisig keys are still counted toward `num_confirmations`, allowing a request to execute below the intended live-signer threshold - ([File: multisig/src/lib.rs])

### Summary
`MultiSigContract::confirm` counts every public key ever recorded in a request's `confirmations` set toward the `num_confirmations` threshold, without verifying that those keys are still valid signers on the account. When a key is removed via `DeleteKey`, the contract only purges requests that key itself *created*; it does not purge confirmations that key previously *cast* on other still-pending requests. Those stale confirmations remain counted, so a request can execute once new confirmations plus stale ones from removed keys reach the threshold, even though fewer than `num_confirmations` currently-valid keys ever confirmed it.

### Finding Description
The `confirm` function only checks that the *current* signer hasn't already confirmed; it never re-validates the pre-existing entries in `confirmations`: [1](#0-0) 

The cleanup logic on `DeleteKey` only removes confirmations for requests where the deleted key is the *original requester* (`r.signer_pk == pk`), not requests where the deleted key merely *confirmed*: [2](#0-1) 

This breaks the intended custody/authorization binding:
```
count(live signer confirmations at execution time) == num_confirmations required
```
Instead, what actually holds is:
```
count(confirmations ever recorded, including from since-removed keys) >= num_confirmations
```
Before the attacker's action: request R (added by member B) has one confirmation from member A. A's key is then removed via a legitimate `DeleteKey` action (e.g., A is offboarded or a device is compromised). After removal, R's `confirmations` set still contains A's stale public key — untouched by the cleanup, since R was not "added by" A.

After the attacker's action: two more currently-valid members confirm R. `confirmations.len() as u32 + 1 >= num_confirmations` (1 stale + 2 live + 1 = 3) satisfies a 3-of-5 threshold, and `execute_request` fires the transfer/action — even though only 2 currently-authorized keys actually approved it, not 3.

### Impact Explanation
This directly matches the "Critical" impact category of a multisig request executed below its configured threshold. Once a key is revoked (the normal, expected security response to a suspected compromise or personnel change), the multisig's guarantee that any transfer/upgrade/key-management action requires `num_confirmations` currently-trusted signers no longer holds. Funds transfers, `AddKey`, `DeployContract`, or `SetNumConfirmations` actions can all be pushed through with fewer live approvals than configured, which can be leveraged to move funds or fully compromise the account (e.g., adding a full-access key) with less than the intended quorum.

### Likelihood Explanation
This requires no external/unauthorized actor — it happens through the normal, documented lifecycle of the contract: add request → partial confirmation → key rotation/removal (a routine security practice) → completion of confirmations by remaining members. Any multisig account that ever revokes a key while a request is still pending confirmation is exposed. Given that key rotation is a normal operational event for any long-lived multisig, likelihood is realistic rather than purely theoretical.

### Recommendation
When a key/member is removed (`DeleteKey` / `DeleteMember`), scan and strip that key from the `confirmations` set of *every* pending request, not just requests it created. Alternatively, validate at `confirm`-time (and at threshold-check time) that every public key in the stored `confirmations` set is still present among the account's/contract's current valid signer set before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with 5 members, `num_confirmations = 3`.
2. Member B calls `add_request_and_confirm` for a `Transfer` action (creates request R, 1 confirmation from B).
3. Member A calls `confirm(R)` — now R has confirmations `{B, A}` (2 of 3).
4. The group executes a separate, legitimate `DeleteKey` request removing A's key (e.g., A's device was compromised). Per [3](#0-2) , only requests *added by* A are purged — R (added by B) is untouched, and A's confirmation on R remains.
5. Member C calls `confirm(R)`. `confirmations.len() as u32 + 1` = `2 + 1` = `3 >= num_confirmations`, so `execute_request` fires the transfer — even though only B and C (2 live keys) ever confirmed R after A was revoked.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
