# No vulnerability found for this question.

Analysis: `whitelist::add_staking_pool` only checks that `env::predecessor_account_id()` is present in `factory_whitelist` (or is the foundation) before inserting the caller-supplied `staking_pool_account_id`, with no on-chain verification of what code lives at that id, and this call carries no deposit. [1](#0-0)  However, the only path that reaches this method from an unprivileged actor is through `StakingPoolFactory::create_staking_pool` → `on_staking_pool_create`, and the account id passed to `add_staking_pool` is not attacker-arbitrary:

- `create_staking_pool` rejects any `staking_pool_id` containing `.`, then derives `staking_pool_account_id = format!("{}.{}", staking_pool_id, env::current_account_id())`, forcing the id to always be a subaccount of the factory's own account. [2](#0-1) 
- That exact same `staking_pool_account_id` is used to `create_account()`, `deploy_contract()` with the factory's embedded `staking_pool.wasm`, and `function_call("new", ...)`, chained via `.then()` into the `on_staking_pool_create` callback with the identical id baked into the call arguments. [3](#0-2) 
- `on_staking_pool_create` is gated by `assert_self()` and only proceeds to call `ext_whitelist::add_staking_pool` if `is_promise_success()` is true, i.e. only after the account was actually created and the official pool wasm was actually deployed and initialized successfully at that exact id. [4](#0-3) 

Because NEAR's account model only permits creating subaccounts under the creator's own account, and because the id passed to `add_staking_pool` is fixed by the promise chain to be the very id that was just verified (via `is_promise_success()`) to hold the factory's own bundled `staking_pool.wasm`, an attacker calling `create_staking_pool` cannot cause an arbitrary, attacker-controlled contract (with attacker-chosen code) to be inserted into the whitelist — the whitelisted id is always `{chosen_prefix}.{factory_account_id}` running the official pool code deployed by the factory itself. The "zero deposit" observation is a red herring: the security boundary here is the predecessor-is-whitelisted-factory check plus the promise-success gate, not a deposit requirement. The invariant "a whitelisted id runs the pool code the whitelist implies" therefore holds for every reachable path from an unprivileged caller.

    pub fn add_staking_pool(&mut self, staking_pool_account_id: AccountId) -> bool {
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The given account ID is invalid"
        );
        // Can only be called by a whitelisted factory or by the foundation.
        if !self
            .factory_whitelist
            .contains(&env::predecessor_account_id())
        {
            self.assert_called_by_foundation();
        }
        self.whitelist.insert(&staking_pool_account_id)
    }
