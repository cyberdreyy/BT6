### Title
Shared `RequestCache` lacks per-sender quota, allowing one sender to exhaust `maxCacheSize` and deny service to other senders - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces only a single global size check (`len(c.cache) >= int(c.maxCacheSize)`) with no per-sender accounting, so any single authenticated sender can fill the entire shared cache with unique `MessageId`s and cause `NewRequest` calls from other senders to fail with "request cache is full".

### Finding Description
`NewRequest` computes a `globalId{sender, id}` key and only rejects duplicate `(sender, id)` pairs; the only capacity check is the aggregate `len(c.cache) >= maxCacheSize` comparison, with no limit on how many entries a single `sender` may hold concurrently: [1](#0-0) 
This cache is used by `gatewayHandler` in `core/services/gateway/handlers/capabilities/v2/http_handler.go`, which is a shared, multi-tenant structure serving requests from multiple workflow senders through a single DON/shard handler. Because entries persist until either a response arrives via `ProcessResponse` or the per-entry timeout fires, an attacker with one valid signed sender identity can submit `maxCacheSize` distinct `NewRequest` calls with unique `MessageId`s, filling the map before other legitimate senders' requests, at which point `NewRequest` will unconditionally return `"request cache is full"` for everyone until slots free up (bounded by `timeout`, e.g., minutes).

However, I was unable to confirm in this codebase snapshot that this `RequestCache` type is actually being instantiated/wired into a live gateway path — `grep` shows `requestcache.go` is only referenced by its own test file (`requestcache_test.go`) and mentioned in `http_handler.go`'s vocabulary (`ResponseCache` naming), but I could not locate an actual call site invoking `common.NewRequestCache(...)` or `.NewRequest(...)` in production handler code within the indexed portion of the repo. This limits certainty about the exact reachable attack surface (which gateway route/method maps to this exact cache, what `maxCacheSize` is configured to, and whether an upstream per-sender rate limiter is applied before `NewRequest` is reached).

### Impact Explanation
If reachable without an upstream per-sender gate, this is a cross-tenant Denial of Service: one low-privilege sender can starve the shared request cache, blocking new gateway requests (and thus callback delivery) for all other users of the same DON/handler until entries time out. This matches the "denial of service affecting multiple users" bounty class, but the severity is capped by uncertainty over whether this exact cache is deployed on a reachable path or whether existing per-sender rate limiters upstream (as seen for the `webapi` handler and `gatewayHandler` in `http_handler.go`) already throttle the rate at which any sender can call `NewRequest` before hitting `maxCacheSize`.

### Likelihood Explanation
Preconditions: attacker needs only one valid signed low-privilege sender identity, no special role. If the cache is reachable directly from gateway user requests without a per-sender submission quota gating entry into `NewRequest`, the exploit is straightforward and repeatable (loop of `maxCacheSize` unique-ID requests). However, other parts of this codebase consistently apply per-sender rate limiters (e.g., `limits.RateLimiter` per node/sender in `http_handler.go`, `ratelimiter.RateLimiter` with `PerSenderRPS`/`PerSenderBurst` in `core/services/workflows/ratelimiter/ratelimiter.go`) in front of similar caches/handlers, which — if present in front of this specific `RequestCache` instance — would throttle the rate of cache-filling requests and significantly reduce feasibility. Without confirming the actual instantiation site and its surrounding rate-limiting middleware, I cannot state with certainty that this DoS is currently exploitable end-to-end in a live handler.

### Recommendation
Add a per-sender quota to `requestCache`, e.g., track counts per `sender` (or reuse `globalId.sender` bucket) and reject `NewRequest` once a sender's own pending-entry count exceeds a configured `maxPerSenderCacheSize`, in addition to the existing global `maxCacheSize` check. Alternatively/additionally, ensure every call site that can reach `NewRequest` is preceded by a per-sender rate limiter (as already done elsewhere in the gateway codebase) sized so that a single sender cannot realistically fill `maxCacheSize` before legitimate traffic gets a fair share.

### Proof of Concept
Go unit test plan for `core/services/gateway/handlers/common/requestcache_test.go`:
1. Construct `requestCache` via `NewRequestCache[T](timeout, maxCacheSize)` with a small `maxCacheSize` (e.g., 3).
2. From `senderA`, call `NewRequest` `maxCacheSize` times with unique `MessageId`s and a valid callback/responseData; assert all succeed (`err == nil`).
3. From `senderB` (different sender), call `NewRequest` once with a distinct `MessageId`; assert it returns `errors.New("request cache is full")`.
4. This demonstrates the cache has no per-sender isolation and one sender can deny cache slots to another.

Note: this PoC validates the `requestcache.go` unit in isolation; confirming full exploitability requires identifying the concrete handler wiring (`NewRequestCache` call site with its configured `maxCacheSize`, and whether an upstream per-sender rate limiter already mitigates this) which I could not locate in the current index — starting a Devin session with full repo access would be needed to trace that wiring definitively.
