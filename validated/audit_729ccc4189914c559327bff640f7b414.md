### Title
Unbounded CPU cost from synchronous zstd compression of attacker-sized account data in `encode_ui_account` (Base64Zstd) - (File: account-decoder/src/lib.rs)

### Summary
`encode_ui_account`'s `UiAccountEncoding::Base64Zstd` branch performs synchronous zstd compression of the entire (post-slice) account data on the RPC handler thread, with no length check or cost-based limiting distinct from the general on-chain account size cap. [1](#0-0)  Since account data size can be attacker-controlled up to the protocol's maximum permitted account size, a single `getAccountInfo` call with `encoding=base64+zstd` on such an account forces the validator to synchronously compress up to that maximum amount of data per request.

### Finding Description
The `Base64Zstd` branch constructs a `zstd::stream::write::Encoder`, writes the sliced account data into it, and calls `finish()`, all inline in the request-handling call graph, with no bound tied to request cost other than the account's own on-chain data length. [1](#0-0)  The function receives `account.data()` directly from the loaded account and a `data_slice_config` that, if absent, results in the full account buffer being compressed via `slice_data`. [2](#0-1)  There is no explicit CPU-time or byte-count cap applied specifically before invoking the zstd encoder inside `encode_ui_account`; the only constraint present at this layer is whatever the account's actual persisted data size is. An attacker who owns/controls a program account (or any account they can grow, e.g., via `system_processor`'s allocate/extend paths) can pad the account up to the maximum permitted account data size with random, incompressible bytes, then issue a single `getAccountInfo` request with `base64+zstd` encoding. Random/incompressible data does not reduce zstd's CPU work — the encoder must still scan/hash the entire input — so the actual compression cost scales with the full account size regardless of the value's "reverse compressibility" framing in the prompt.

I was not able to find, within the indexed portion of `rpc/src/rpc.rs`, an explicit RPC-level pre-check that limits the *size of data passed into `encode_ui_account`* independent of the account's own size (e.g., a fixed max-bytes-to-compress cap or a data-slice enforcement specifically for the zstd path). The only related constant I located, `MAX_PERMITTED_DATA_LENGTH`, is defined and used in `transaction-context/src/lib.rs`, `programs/bpf_loader/src/lib.rs`, `program-runtime/src/serialization.rs`, and `accounts-db/src/append_vec.rs` as the general account-size ceiling enforced at account-realloc/creation time, not as an RPC response-cost gate. [3](#0-2)  I could not confirm or rule out whether a separate size/time budget exists elsewhere in `rpc/src/rpc.rs` around the `encode_ui_account` call sites due to index coverage limits; this would need direct file inspection of the call sites in a Devin session with full file access.

### Impact Explanation
A single legally-rate-limited RPC call (`getAccountInfo` with `base64+zstd`) can force the validator's RPC handler thread to perform zstd compression proportional to the maximum permitted account size, rather than a fixed, request-scoped budget. This matches the "unbounded cost for a single low-rate call" impact category: the cost of one request is governed by attacker-authored on-chain data size, not an explicit per-request limit.

### Likelihood Explanation
Preconditions are attacker-feasible without special privileges: the attacker needs only an account they can grow to near the maximum permitted size (achievable via ordinary system/program instructions available to any unprivileged user) and the ability to issue one `getAccountInfo(encoding=base64+zstd)` call at the standard allowed RPC rate. This is repeatable per qualifying account and does not require validator, leader, or peer control.

### Recommendation
Enforce an explicit, fixed cost/size cap in `encode_ui_account`'s `Base64Zstd` branch (and/or upstream in `rpc/src/rpc.rs` before calling it) that is independent of the account's on-chain data length — e.g., reject or fall back to `Base64` when `slice_data(...).len()` exceeds a configured maximum, or apply a lower zstd compression level with a bounded time budget, so the RPC-layer invariant "cost of one request bounded by explicit limits" is upheld regardless of attacker-authored account size.
