### Title
`getSupply` RPC handler uses unchecked subtraction between two independently-tracked accounting values, risking integer underflow / wrapped-supply data - ([File: rpc/src/rpc.rs])

### Summary
The `getSupply` JSON-RPC handler computes `circulating` supply as a plain, unchecked `total_supply - non_circulating_supply.lamports`, where `total_supply` comes from the incrementally-tracked `bank.capitalization()` counter and `non_circulating_supply.lamports` comes from an independent, on-demand account scan. This mirrors the reported bug class ("debts calculation is not accurate"): one aggregate value is maintained incrementally while a second, logically-related value is computed by a different code path, and the two are combined with an operation (bare subtraction) that assumes an invariant (`total_supply >= non_circulating_supply.lamports`) that is not defensively enforced at this call site — unlike the equivalent computation elsewhere in the same codebase.

### Finding Description
`JsonRpcRequestProcessor::get_supply` at [1](#0-0)  computes:

```rust
let total_supply = bank.capitalization();
...
circulating: total_supply - non_circulating_supply.lamports,
```

`bank.capitalization()` is an atomically-maintained running counter that is incremented/decremented across many independent code paths (fee burns/deposits, epoch reward distribution, commission burns to invalid collectors, VAT burns, etc.), for example in [2](#0-1)  and [3](#0-2) . `non_circulating_supply.lamports`, in contrast, is computed by `calculate_non_circulating_supply` via `bank.get_balance(pubkey)` summed over a live account scan at [4](#0-3) . These are two logically-coupled but structurally separate accounting mechanisms — exactly the pattern the external report flags: a counter incremented one way and decremented/compared another way, with no code-level guarantee that they stay consistent.

Critically, the codebase itself demonstrates awareness of this fragility: the nearly identical computation used for the `/v0/circulating-supply` REST endpoint explicitly guards against underflow with `saturating_sub`:

```rust
Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
``` [5](#0-4) 

The JSON-RPC `getSupply` path performs the same subtraction with a bare `-` operator instead, with no equivalent safeguard [6](#0-5) .

### Impact Explanation
If `capitalization` and the non-circulating account balance total ever diverge such that the scanned non-circulating sum exceeds the tracked capitalization (e.g., due to any drift in the many independent capitalization-adjusting code paths, similar in spirit to the reported `debts` drift), the unchecked `u64` subtraction will either:
- wrap around in a standard release build (no overflow checks), silently returning a wildly incorrect (near-`u64::MAX`) `circulating` value to any RPC caller — wrong data returned from a single `getSupply` call, or
- panic and crash the RPC-serving thread if overflow checks are enabled for the build.

Either outcome is caused entirely by a single, ordinary, unprivileged `getSupply` JSON-RPC call and requires no special client access.

### Likelihood Explanation
No `Cargo.toml` `overflow-checks` setting was found in this repo, so behavior depends on build profile; regardless of profile, the underlying correctness issue exists because `capitalization` is not proven to always dominate the non-circulating scan total across all historical/administrative code paths that touch capitalization, and the code path itself already acknowledges the need for a saturating guard in the parallel REST implementation. This is a reachable, low-effort, single-call condition (`getSupply`), not a theoretical-only concern, but confirming a concrete capitalization-drift trigger scenario was not possible from static analysis alone within scope of this review.

### Recommendation
Change the `getSupply` computation in `rpc/src/rpc.rs` to mirror the safer pattern already used in `rpc_service.rs`:

```rust
circulating: total_supply.saturating_sub(non_circulating_supply.lamports),
```

This removes the risk of both the underflow panic and the wrapped-value data-integrity issue for a widely-used public RPC method.

### Proof of Concept
1. Call `getSupply` via JSON-RPC on a node where `bank.capitalization()` momentarily reflects less lamports than the sum of currently non-circulating account balances (any drift between the two independently maintained totals, as acknowledged by the codebase's own defensive `saturating_sub` usage in the REST supply endpoint).
2. Observe the `circulating` field in the RPC response is either a near-`u64::MAX` wrapped value or the RPC-serving thread panics, depending on build overflow-check configuration — directly comparing `rpc/src/rpc.rs:1148` (bare `-`) against `rpc/src/rpc_service.rs:431` (`saturating_sub`) shows the inconsistency between the two nearly-identical implementations of the same conceptual calculation.

    async fn get_supply(
        &self,
        config: Option<RpcSupplyConfig>,
    ) -> RpcCustomResult<RpcResponse<RpcSupply>> {
        let config = config.unwrap_or_default();
        let bank = self.bank(config.commitment);
        let non_circulating_supply =
            self.calculate_non_circulating_supply(&bank)
                .await
                .map_err(|e| RpcCustomError::ScanError {
                    message: e.to_string(),
                })?;
        let total_supply = bank.capitalization();
        let non_circulating_accounts = if config.exclude_non_circulating_accounts_list {
            vec![]
        } else {
            non_circulating_supply
                .accounts
                .iter()
                .map(|pubkey| pubkey.to_string())
                .collect()
        };

        Ok(new_response(
            &bank,
            RpcSupply {
                total: total_supply,
                circulating: total_supply - non_circulating_supply.lamports,
                non_circulating: non_circulating_supply.lamports,
                non_circulating_accounts,
            },
        ))
    }

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
