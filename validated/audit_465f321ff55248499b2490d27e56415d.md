### Title
Instant-withdraw request congestion re-blocks `stopEpoch` and can force a false borrower default - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The EOS "transaction congestion" attack pattern — many cooperating accounts spamming a single shared queue to stall settlement — maps directly onto the instant-withdraw pipeline in `IdleCDOEpochVariant`. `stopEpoch` cannot execute while `pendingInstantWithdraws != 0`, and an unprivileged tranche holder can keep creating new instant-withdraw receipts mid-epoch as long as the APR dropped between epochs. Each new request re-blocks `stopEpoch`, forces another `getInstantWithdrawFunds` borrower recall, and if the borrower (honest, but finite liquidity) fails to fund the congested remainder, `_handleBorrowerDefault` fires even though the borrower never actually defaulted.

### Finding Description
The instant-withdraw flow has three coupled stages:

1. **Request.** In `requestWithdraw`, if `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, the request is routed to `IdleCreditVault.requestInstantWithdraw`, which increments `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws`. The only gates are `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed` (KYC). Withdraw-request flags stay enabled during a running epoch — they are only cleared inside `_handleBorrowerDefault` (lines 594-596) — so requests can be submitted throughout the epoch, not only in the buffer.

2. **Fund.** `getInstantWithdrawFunds` (manager/owner, after `instantWithdrawDeadline`) pulls `pendingInstantWithdraws` from the borrower via `getFundsFromBorrower`; on transfer failure it calls `_handleBorrowerDefault`, which sets `defaulted = true`, pauses deposits, stops the epoch, and disables further withdraw requests.

3. **Stop.** `_stopEpoch` reverts via `_checkNotAllowed(... _pendingInstant() != 0 ...)` — the epoch cannot close until the instant queue is empty.

The broken invariant is queue-finality: there is no cutoff that freezes the instant queue once funding begins. An attacker controlling multiple KYC'd accounts (the report's "multiple accounts to cooperate") can sequence requests around the honest manager's `getInstantWithdrawFunds`/`stopEpoch` calls — submit requests after each funding pull — so `_pendingInstant()` is non-zero every time `stopEpoch` is attempted. Worse, if the manager funds amount X, then the attacker adds a new instant request for Y where the borrower cannot immediately pull Y (e.g., funds deployed, borrower must unwind), the next `getInstantWithdrawFunds` transfer fails and `_handleBorrowerDefault` marks a solvent borrower defaulted.

### Impact Explanation
- **Temporary freezing of all user funds**: `stopEpoch` is permanently gated on an empty instant queue; each congestion request extends the freeze, locking both AA and BB NAV plus all funded withdraw claims.
- **False default / insolvency event**: a borrower that is honest and solvent on aggregate can be forced into `defaulted = true` because a fresh request arrived between funding calls and could not be pulled in that transaction. Post-default the pool is paused, epoch state is frozen, and NAV must go through `finalizeDefault`/`DefaultDistributor` recovery — permanently altering lender payouts even when fully recovered, and permanently freezing them if governance never finalizes.
- **Griefing amplification**: the attacker's cost is one tranche position split across N accounts (instant requests don't require extra capital beyond holding tranches), while each round imposes a full borrower recall on the protocol.

### Likelihood Explanation
- Requires a real APR decrease between epochs (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`), so it is conditional rather than always-available — this is why it is Medium-like rather than Critical.
- KYC gating raises the bar, but the attacker model explicitly includes a KYC-passing lender, and tranche positions can be split across multiple whitelisted wallets.
- No existing guard stops it: `_checkNotAllowed` in `requestWithdraw` doesn't check `isEpochRunning` vs. a request deadline, `allowInstantWithdraw` only controls *claims*, and `instantWithdrawDeadline` only gates the manager's funding call, not user requests.

### Recommendation
- Snapshot/freeze the instant-withdraw queue at `instantWithdrawDeadline` (or when `getInstantWithdrawFunds` first runs): requests submitted after the cutoff should fall back to the normal epoch-withdraw path instead of inflating `pendingInstantWithdraws`.
- Alternatively, gate `requestWithdraw`'s instant path on `block.timestamp < instantWithdrawDeadline`, matching the funding window.
- Do not escalate to `_handleBorrowerDefault` on a failed pull for requests created after the last funding snapshot; separate "queue snapshot funded" from "queue snapshot unfunded" so late requests cannot retroactively cause a default.

### Proof of Concept
Foundry fork PoC outline (environment mirrors `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_getInstantFunds`):

```solidity
function testInstantWithdrawCongestionBlocksStopEpoch() external {
    // Attacker controls K many KYC'd accounts, each holding AA tranches.
    address[] memory attackers = _makeAttackerAccounts(3);
    for (uint256 i; i < attackers.length; i++) {
        _depositWithUser(attackers[i], 10_000 * ONE_SCALE, true);
    }

    // Epoch 0 runs; manager lowers APR so instant path is enabled.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Epoch 1 starts; attacker[0] files an instant withdraw.
    _startEpochAndCheckPrices(1);
    vm.prank(attackers[0]);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Deadline passes; manager funds the current queue.
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds(); // pendingInstantWithdraws -> 0, allowInstantWithdraw = true

    // CONGESTION: attacker[1] files a NEW instant request mid-epoch,
    // re-inflating pendingInstantWithdraws after funding completed.
    vm.prank(attackers[1]);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // stopEpoch now reverts even though epochEndDate passed and borrower
    // already honored one recall.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr / 2, 0);

    // FALSE DEFAULT: borrower has just returned capital and cannot pull the
    // congested remainder in the same block; the failed transfer marks the
    // honest borrower defaulted.
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(); // transfer fails -> _handleBorrowerDefault
    _checkDefault();                    // defaulted == true, paused, epoch frozen
}
```

Caveat I could not fully verify within the iteration budget: whether `requestWithdraw`'s instant path is reachable for accounts whose *only* prior epoch was epoch 0 (i.e., `lastEpochApr` semantics at line 762 require an APR drop registered via `stopEpoch`/`stopEpochWithDuration` — the test suite does exercise instant requests mid-buffer repeatedly, e.g., `testClaimInstantWithdrawRequestAfterAnEpochWithInstantWithdraw`, which supports reachability). If an additional `isEpochRunning`-phase gate on requests exists elsewhere that I did not observe, the congestion window shrinks to the buffer period — but the same multi-account sequencing still applies across the funding/claim boundary since requests remain enabled until a default is declared.
