### Title
Missing precision-decimal division in the Jovian operator-fee formula amplifies fees charged on every post-Jovian transaction - (`crates/common/l1-fees/src/params.rs`)

### Summary
`L1FeeParams::operator_fee_charge_inner` computes the operator fee that every non-deposit L2 transaction pays. For pre-Jovian forks it divides `gas * operator_fee_scalar` by `OPERATOR_FEE_SCALAR_DECIMAL` (1,000,000, i.e. 6 decimals of fixed-point precision), matching the scalar's documented precision. For Jovian, the code instead multiplies by `OPERATOR_FEE_JOVIAN_MULTIPLIER` (100) and never re-applies any division by the scalar's fixed-point precision, so the Jovian branch is missing the `/ 1_000_000` normalization that the non-Jovian branch has. [1](#0-0) 

### Finding Description
`operator_fee_scalar` is documented as a fixed-point value with 6 decimal points of precision (`OPERATOR_FEE_SCALAR_DECIMAL = 1_000_000`), consistent with its usage in the Isthmus branch: `gas * operator_fee_scalar / OPERATOR_FEE_SCALAR_DECIMAL`. [2](#0-1) 

In the Jovian branch, the same `operator_fee_scalar` (still carrying the same on-chain 6-decimal precision, since it's read from the same `OPERATOR_FEE_SCALARS_SLOT`/offsets used pre-Jovian) is multiplied by `OPERATOR_FEE_JOVIAN_MULTIPLIER = 100` with no compensating division:

```rust
let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
    gas.saturating_mul(operator_fee_scalar)
        .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
} else {
    gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
};
``` [3](#0-2) 

This is exactly the bug class from the report: a per-unit rate (here `operator_fee_scalar`, precision 1e6) is combined with a raw quantity (`gas`) and a scaling multiplier, but the branch omits the divisor that normalizes the rate's fixed-point precision back down — leaving the result amplified by the full precision factor (1e6) instead of a small, intended multiplier. The test suite itself demonstrates the resulting magnitude: with `operator_fee_scalar = 1000`, `gas = 1000`, Isthmus yields `1000*1000/1e6 = 1` (+constant), while Jovian yields `1000*1000*100 = 100,000,000` (+constant) — an increase of 8 orders of magnitude for the same inputs. [4](#0-3) 

The `L1BlockInfo::operator_fee_charge_inner` wrapper in the revm integration simply forwards to this same engine-neutral function, so the bug is shared by both the revm and evm2 execution paths. [5](#0-4) 

### Impact Explanation
`operator_fee_charge_inner` is on the hot path for every non-deposit transaction post-Isthmus/Jovian:
- It is charged during block execution (via `operator_fee_charge`/`operator_fee_refund`) against the sender's balance for every ordinary transaction.
- It is used in the txpool admission check (`apply_base_checks`) to decide whether a transaction has sufficient balance to be admitted, including for EIP-8130 sponsored transactions. [6](#0-5) [7](#0-6) 

If the Jovian operator-fee scalar retains the same 1e6 fixed-point precision as pre-Jovian (which the shared decoding path and constant naming (`OPERATOR_FEE_SCALAR_DECIMAL`) strongly suggest), then every ordinary transaction submitted by any unprivileged sender after Jovian activation would be charged an operator fee inflated by roughly `OPERATOR_FEE_SCALAR_DECIMAL` (1,000,000×) relative to the value the sequencer/operator intends to configure. Consequences:
- Direct loss of funds to every transaction sender (fee vault over-collection) if scalars are configured assuming the normal 1e6 precision.
- Alternatively, mass transaction rejection/DoS in the txpool once senders can no longer afford the inflated fee, since `apply_base_checks` will reject transactions as `InsufficientFunds` for what should be affordable operator fees.
- Since this fee affects the block-execution charge/refund itself (`operator_fee_charge`/`operator_fee_refund`), a materially wrong fee also risks state-transition/consensus divergence between engines that don't share this exact formula (if any exist), or between-node disagreement about balances.

### Likelihood Explanation
The Jovian formula runs unconditionally for every standard transaction once Jovian activates, with no special preconditions — it is reachable by any unprivileged transaction sender who is EOA-signing a normal L2 transaction, i.e., the most common transaction path on the chain. It requires no attacker-controlled configuration; it is purely a function of whatever `operator_fee_scalar`/`operator_fee_constant` are configured post-Jovian and the transaction's gas usage.

### Recommendation
Restore precision normalization in the Jovian branch of `operator_fee_charge_inner`, dividing by the same fixed-point decimal denominator (or the correct Jovian-specific denominator if the Jovian scalar's precision was intentionally changed) instead of only multiplying by `OPERATOR_FEE_JOVIAN_MULTIPLIER`:

```rust
let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
    gas.saturating_mul(operator_fee_scalar)
        .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)   // <-- missing normalization
} else {
    gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
};
```
Add a regression test asserting the Jovian fee equals the Isthmus fee scaled by exactly `OPERATOR_FEE_JOVIAN_MULTIPLIER` (not by `OPERATOR_FEE_SCALAR_DECIMAL * OPERATOR_FEE_JOVIAN_MULTIPLIER`), and cross-check against the canonical op-stack/op-geth Jovian operator-fee reference implementation to confirm the intended scalar precision and multiplier semantics.

### Proof of Concept
Using the existing unit test as the reproduction (already present in the codebase, confirming the amplification is real and currently accepted by the test suite as "expected" behavior): [4](#0-3) 

With `operator_fee_scalar = 1000` (interpreted, per the scalar's documented 6-decimal fixed-point precision, as `0.001`) and `gas = 1000`:
- Isthmus: `1000 * 1000 / 1_000_000 + 10 = 11` — consistent with a 6-decimal fixed-point rate.
- Jovian: `1000 * 1000 * 100 + 10 = 100_000_010` — off by a factor of ~`9,090,910×` relative to the Isthmus result scaled only by the intended `100×` multiplier (`11 * 100 = 1100`, not `100_000_010`).

This demonstrates the missing `/ OPERATOR_FEE_SCALAR_DECIMAL` division in the Jovian branch produces an operator fee that is orders of magnitude larger than intended for identical inputs, directly mirroring the reported `_debt_interest_since_last_update` precision-mismatch bug class.

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }
```
