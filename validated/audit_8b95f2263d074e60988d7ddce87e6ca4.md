### Title
Run-role users (including External Initiators) can execute arbitrary registered node capabilities via POST /v2/execute_capability, exceeding intended job-run scope - ([File: core/web/router.go])

### Summary
`POST /v2/execute_capability` is gated only by `auth.RequiresRunRole` and a `build.IsDev()` compile-time flag, and `CapabilityController.ExecuteCapability` performs no authorization/filtering based on capability type before invoking `capability.Execute`. Any credential granted `UserRoleRun` — including External Initiator credentials, which `AuthenticateExternalInitiator` unconditionally maps to `UserRoleRun` — can invoke any capability registered in the node's `CapabilitiesRegistry` by name, including write/target capabilities (e.g. EVM `write_*` targets) that submit on-chain transactions.

### Finding Description
The route is registered with only run-role gating: [1](#0-0) 

`RequiresRunRole` only rejects `UserRoleView`; it permits `UserRoleRun`, `UserRoleEdit`, and `UserRoleAdmin` through: [2](#0-1) 

Critically, `AuthenticateExternalInitiator` explicitly sets the authenticated principal to `UserRoleRun` for any successfully-authenticated External Initiator credential: [3](#0-2) 

`CapabilityController.ExecuteCapability` then looks up any capability by attacker-supplied `capabilityName` from the global `CapabilitiesRegistry` and executes it with an attacker-supplied `capabilityRequest` payload, with no allowlist, no check of capability type (trigger/action/consensus/target), and no restriction tying the operation to a specific job the caller is authorized to run: [4](#0-3) 

The node's `CapabilitiesRegistry` can contain state-mutating/fund-moving "target" capabilities such as EVM write targets (`write_<chain>`) that submit on-chain transactions via the node's tx manager, as seen in the write-target capability and its registration definitions: [5](#0-4) [6](#0-5) 

Because `RequiresRunRole` treats run/edit/admin equivalently for this route, and EI credentials are hard-wired to `UserRoleRun`, this endpoint effectively grants any run-scoped credential the ability to trigger arbitrary registered capability executions — an action well beyond "trigger a job run," which is the intended scope of the run role (used elsewhere only for `/replay_from_block`, `/find_lca`, `/lp_skip_to_block` — read/ops-safe actions). There is no capability-level authorization check verifying that the calling identity is permitted to invoke the specific named capability, nor any scoping to a workflow/job the caller owns.

### Impact Explanation
If a node has an EVM `write_*` (or other target) capability registered in its `CapabilitiesRegistry` (a supported, documented configuration for CRE/Keystone workflow nodes), any holder of a run-role session/API token or External Initiator credential can call `POST /v2/execute_capability` with a crafted `capabilityRequest` to directly invoke that target capability's `Execute` method — triggering an on-chain transaction submission from the node's configured `Workflow.FromAddress`/forwarder, independent of the OCR3/workflow consensus path that normally gates target execution. This matches the "unauthorized job run or fund movement" bounty impact class: an unprivileged run-scoped credential can cause node-controlled funds/keys to be used for a transaction the operator did not intend, and can mutate other in-process capability state for any capability type, not just triggers.

### Likelihood Explanation
Preconditions are minimal: (1) the node is built with `build.IsDev()` true, (2) the attacker holds any credential mapped to `UserRoleRun` — this includes a run-scoped API token, a run-scoped session, or (critically) any valid External Initiator access key/secret pair, which are commonly distributed to lower-trust external bridge/adapter integrations, and (3) the target node has at least one non-trivial capability registered (e.g., an EVM write target, common in CRE/Keystone deployments). Given `build.IsDev()` gating, this depends on the specific build configuration and may not be present in all production binaries, but where enabled it is directly reachable over the authenticated API with no additional secrets, and the request is fully attacker-controlled (only `capabilityName` and marshaled `capabilityRequest` bytes are needed) — making it repeatable and low-effort once a target capability name is known (capability names/format for write targets are documented and predictable, e.g. `write_ethereum-mainnet`).

### Recommendation
Do not gate `/v2/execute_capability` on `RequiresRunRole` alone. At minimum:
- Restrict this endpoint to `RequiresAdminRole` (or a new dedicated debug/dev-only permission), since it allows invocation of arbitrary registered capabilities, not just job triggers.
- Alternatively/additionally, add capability-level authorization inside `CapabilityController.ExecuteCapability` that only permits execution of capabilities explicitly marked as "run-safe" (e.g., excluding `CapabilityType == target`/write capabilities), and reject execution of write/target capabilities via this ad hoc debug endpoint entirely.
- Ensure the `build.IsDev()` gate is enforced consistently in all release build configurations so this endpoint cannot be reachable in production builds.
- Do not allow `AuthenticateExternalInitiator`-derived identities (`UserRoleRun`) to reach this route at all, since EI credentials are meant only to trigger job runs, not arbitrary capability execution.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/capability_controller_test.go`):
1. Build a `gin` engine wiring the real route group as in `router.go`: `authv2.POST("/execute_capability", auth.RequiresRunRole(capContr.ExecuteCapability))`, with `auth.Authenticate` middleware ahead of it using `AuthenticateExternalInitiator`.
2. Register a mock/stub capability in the `CapabilitiesRegistry` that simulates a write/target capability whose `Execute` method records that it was invoked (e.g., using `capmock.NewExecutableCapability(t)` with an assertion that `Execute` is called).
3. Simulate an External-Initiator-authenticated request: set `c.Set(auth.SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` (mirroring `AuthenticateExternalInitiator`'s behavior) or actually authenticate via `AuthenticateExternalInitiator` with a valid EI token fixture.
4. POST to `/v2/execute_capability` with `CapabilityRequestOuter{CapabilityName: "write_ethereum-mainnet", CapabilityRequest: <marshaled request>}`.
5. Assert: HTTP 200 is returned and the mock capability's `Execute` was called — demonstrating that a run-role/EI-derived identity, which should only be able to trigger job runs, successfully invoked a write/target capability with no additional authorization check, `Execute` being called at all (regardless of the mocked business logic) proving the authorization gap. Compare against expected behavior: the request should have been rejected with 403/401 unless the capability is explicitly classified as run-safe.

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```

```go
func (cc *CapabilityController) ExecuteCapability(c *gin.Context) {
	body := c.Request.Body
	if body == nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("missing request body"))
		return
	}

	capabilityRegistry := cc.App.GetCapabilitiesRegistry()
	if capabilityRegistry == nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("capability registry not initialized"))
		return
	}
	var capabilityRequestOuter CapabilityRequestOuter
	if err := c.BindJSON(&capabilityRequestOuter); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	capability, err := capabilityRegistry.GetExecutable(c.Request.Context(), capabilityRequestOuter.CapabilityName)
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	capabilityRequest, err := pb.UnmarshalCapabilityRequest(capabilityRequestOuter.CapabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	resp, err := capability.Execute(c.Request.Context(), capabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	responseBytes, err := pb.MarshalCapabilityResponse(resp)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	c.JSON(http.StatusOK, gin.H{"capabilityResponse": responseBytes})
```
