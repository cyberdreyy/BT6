### Title
Unfunded instant-withdraw residue permanently bricks `stopEpoch`, freezing all LP and borrower funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2017-13141 is a resource leak: a counter is incremented but never released. The analog in `IdleCreditVault` is `pendingInstantWithdraws` — a liability that can be left permanently non-zero with no reachable code path to clear it. `stopEpoch` hard-reverts while `pendingInstantWithdraws() != 0` ( [1](#0-0) ), and the only decrement, `collectInstantWithdrawFunds`, can only pull underlying that the CDO already holds ( [2](#0-1) ). When `startEpoch` cannot fully cover the instant queue it forwards the entire CDO balance and returns early ( [3](#0-2) ); the residual `pendingInstantWithdraws` can then never be funded, because the borrower's only repayment route is `stopEpoch` itself, which is blocked by the very deficit it would repay.

### Finding Description
`requestInstantWithdraw` mints a receipt and increments `pendingInstantWithdraws` ( [4](#0-3) ). At `startEpoch`, the CDO computes `pendingInstant = _pendingInstant()` and calls `collectInstantWithdrawFunds(min(pendingInstant, totUnderlyings))`; if `pendingInstant > totUnderlyings`, it sends everything to the strategy and returns without funding the borrower ( [3](#0-2) ). The deficit `pendingInstant - totUnderlyings` stays in `pendingInstantWithdraws`.

During the epoch the CDO holds no underlying: deposits are paused (`_pause()` at startEpoch), `depositDuringEpoch` forwards tokens straight to the borrower ( [5](#0-4) ), and any direct token transfer to the CDO is swept to `feeReceiver` by `_skimDonatedAssets` ( [6](#0-5) ). So even an honest borrower trying to pre-fund the deficit via a direct transfer has it skimmed as a "donation" rather than credited to the instant queue.

At epoch end, `stopEpoch` reverts at the `_pendingInstant() != 0` check before reaching `getFundsFromBorrower`, `collectWithdrawFunds`, or `_handleBorrowerDefault`. Because `epochNumber` cannot advance and `defaulted` cannot be set, `finalizeDefaultRecovery` is also unreachable (it additionally requires `_ensureDefaultRecoveryInitialized`, which itself reverts on `pendingInstantWithdraws != 0` [7](#0-6) ). The state is terminal: no stop, no default declaration, no recovery, no pause release (`_beforeUnpause` blocks while `isEpochRunning` [8](#0-7) ).

### Impact Explanation
Permanent freezing of all funds. Every active LP's tranche tokens, all pending normal withdraw receipts, and the borrower's outstanding loan principal plus interest become unreachable. Loss equals the full vault TVL plus the borrower-held loan amount — arbitrarily large. The instant requester also loses their own unfunded receipt, so this is a griefing/leak class bug rather than theft, matching the CVE's resource-leak class.

### Likelihood Explanation
Medium. Triggering requires (a) instant withdrawals enabled (`instantWithdrawDelay` set, `disableInstantWithdraw == false`, non-programmable borrower), and (b) aggregate instant requests at `startEpoch` exceeding the CDO's liquid underlying balance — which happens naturally whenever queued instant exits exceed the buffer's un-lent residue, since the surplus was sent to the borrower in prior epochs. An unprivileged KYC'd lender can deliberately size their request to create the deficit; an honest borrower repaying through the normal `stopEpoch` `transferFrom` path never pre-funds the CDO, so no privileged misbehavior is needed. The only escape — borrower spontaneously sending tokens to the CDO — is defeated by `_skimDonatedAssets` or at minimum is outside the repayment protocol.

### Recommendation
Allow `stopEpoch` (or a dedicated path) to fund the instant deficit from borrower repayment: pull `_amountToPullFromBorrower + _pendingWithdraws + pendingInstant` first, then call `collectInstantWithdrawFunds` for the remainder before the `_pendingInstant() != 0` gate. Alternatively, cap `requestInstantWithdraw` at the CDO's available liquidity, and exempt borrower repayment transfers from `_skimDonatedAssets`.

### Proof of Concept
Foundry fork PoC sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testInstantDeficitBricksStopEpoch() external {
    // 1. Deposit, run one epoch so CDO balance is minimal at next startEpoch.
    idleCDO.depositAA(100_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);          // sends surplus to borrower; CDO holds ~0
    // 2. Enable instant withdrawals; user requests instant redeem > CDO balance.
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);
    // warp into a new buffer, deposit small buffer liquidity, request instant for full bal
    _depositWithUser(user1, 50_000 * ONE_SCALE, true);
    vm.prank(user1);
    cdoEpoch.requestWithdraw(type(uint256).max, address(AAtranche)); // instant path
    // 3. startEpoch: pendingInstant > CDO balance -> sends all to strategy, deficit remains
    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertGt(strategy.pendingInstantWithdraws(), 0);
    // 4. Borrower repays normally via approve + balance; stopEpoch still reverts
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    // 5. Any borrower pre-funding attempt is skimmed to feeReceiver
    //    finalizeDefaultRecovery also unreachable -> funds permanently frozen.
}
```

Caveat: this assumes no cap inside the CDO's instant-request path limiting requests to available liquidity, and that `getInstantWithdrawFunds` cannot source funds the CDO doesn't hold — both consistent with the skim/equilibrium design seen above, but the exact request-time liquidity check was not fully verified.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function _ensureDefaultRecoveryInitialized() internal {
    if (defaultRecoveryInitialized) return;
    if (pendingInstantWithdraws != 0) revert NotAllowed();
    if (pendingWithdraws != 0) {
      IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
      if (cdo.epochEndDate() != 0 || cdo.defaulted()) revert NotAllowed();
      pendingWithdraws = 0;
      apr0TotalPrincipal = 0;
    }
    defaultRecoveryInitialized = true;
    canTransfer = false;
  }
