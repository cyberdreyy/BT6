### Title
Unbounded recursive RLP decoding of `TrieNode` in the fault-proof MPT allows stack-exhaustion DoS on attacker-supplied preimages - (File: `crates/proof/mpt/src/node.rs`)

### Summary
The MPT node decoder used by Base's fault-proof program recursively decodes trie nodes with no depth limit, mirroring the CVE-2019-6245 pattern where an attacker-controlled recursive decoder (there, `agg::cell_aa::not_equal`; here, `TrieNode::decode`) can be driven to unbounded recursion depth by crafted input, exhausting the call stack.

### Finding Description
`TrieNode::decode` is implemented as a self-recursive `Decodable` for extension nodes: when it identifies an RLP list of length 2 with an "extension" path prefix, it calls `Self::try_decode_leaf_or_extension_payload`, which in turn calls `Self::decode(buf)` again on the remaining bytes to decode the child node [1](#0-0) , and the top-level `Decodable::decode` recursively decodes branch children via `Vec::<Self>::decode(buf)` [2](#0-1) . No maximum nesting/depth check bounds this recursion; the only constraints are RLP header validity and the surrounding buffer length. The crate's own README describes this as intentional: "A recursive, in-memory implementation of Ethereum's hexary Merkle Patricia Trie (MPT)" [3](#0-2) .

This decoder is fed directly from preimages retrieved via the fault-proof preimage oracle. In `OracleL1ChainProvider::trie_node_by_hash`, raw oracle bytes for a claimed keccak preimage are passed straight into `TrieNode::decode` with no depth or structural pre-validation: `TrieNode::decode(&mut self.oracle.get(PreimageKey::new(*key, PreimageKeyType::Keccak256)).await?.as_ref())` [4](#0-3) . The L2 chain provider and the in-memory `TrieDB` used by `base-proof-executor` follow the same pattern, fetching preimages by hash and decoding them without a depth guard [5](#0-4) .

In the dispute-game/fault-proof model, the preimage oracle is populated by a host serving data supplied to satisfy hints during trace execution; the party in the dispute (an unprivileged, potentially adversarial participant proposing/defending an output-root claim) controls which preimages are supplied for a given committed hash during off-chain execution of the program, and is incentivized to make honest verification/re-execution as expensive/impossible as possible. A hostile participant can craft a byte string that keccak-hashes to a hinted key and that RLP-decodes as a very deeply nested chain of two-item lists (extension-node shape: `[path, child]`), where each nesting level costs only a few bytes of overhead. A single preimage of a few hundred KB (well within permitted preimage sizes) can therefore encode tens of thousands of nested `Extension` levels, each level consuming a new stack frame in `TrieNode::decode` / `try_decode_leaf_or_extension_payload`.

This differs from a legitimate MPT, where real Ethereum tries never nest this deeply for a single storage/account key (bounded to 64 nibbles by keccak256 key length), so honest data can never trigger deep recursion — but there is no explicit code-level enforcement of that invariant in the decoder itself; it only holds because real state data is well-formed. Since preimages are attacker-suppliable data validated only by matching a keccak-preimage hash (not by any MPT well-formedness/depth check) before decoding, this invariant can be violated by a malicious/adversarial party in the dispute flow.

### Impact Explanation
A successful stack-overflow triggers a process crash of whatever consumes `TrieNode::decode` on that adversarial data — the fault-proof program executor (host or in-VM), or the ZK/TEE witness-generation pipeline that call into `base-proof-executor`/`base-proof-mpt` during re-execution of a disputed claim. If this can be triggered during host-side witness generation for a legitimate/opposing party's re-derivation, it prevents them from producing a valid counter-proof or witness within the dispute window, letting a fraudulent output-root claim go unchallenged — i.e., a wrong provable output root can stand, leading to theft/permanent freezing of funds tied to the incorrect state commitment. This satisfies the "wrong provable output root" / "node halt" impact bar.

### Likelihood Explanation
Likelihood depends on whether the preimage-serving host (or on-chain preimage oracle contracts) perform any independent bound on nesting depth/complexity before/while the client decodes it, which was not found in the reviewed MPT and provider code, only fetch/keccak-preimage validation. Constructing a keccak preimage of a chosen byte string is trivial (the attacker just supplies bytes and use its hash as the key — no preimage resistance to defeat), so the only barrier is submitting the resulting bytes through the standard preimage/hint flow used by any dispute-game participant, which is a normal capability of a "participant" in the fault-proof game. This is a moderate-effort, no-special-privilege construction.

### Recommendation
Add an explicit maximum recursion/nesting-depth counter (bounded, e.g., to 64–65, matching the maximum possible MPT path depth for 32-byte keccak keys) to `TrieNode::decode` / `try_decode_leaf_or_extension_payload`, returning a decode error once exceeded, mirroring hardened MPT/RLP decoders elsewhere in the ecosystem (e.g., `alloy-rlp`'s recommended nesting guards used in the CBOR decoder for Nitro attestation, which already enforces `MAX_CBOR_NESTING_DEPTH` [6](#0-5) ). Consider converting the recursive decode into an iterative/stack-based decode loop for defense-in-depth.

### Proof of Concept
Conceptually (cannot be executed without live infra):
1. Choose target hash `H` that the fault-proof program will request as a `PreimageKeyType::Keccak256` trie-node lookup during derivation of a disputed L2 block (via the normal hint mechanism in `OracleL1ChainProvider::trie_node_by_hash` [4](#0-3) ).
2. As the party controlling host-side preimage serving in the dispute game (i.e., the proposer of the malicious game), construct bytes `B` such that `keccak256(B) == H` and `B` RLP-decodes as `N` deeply nested 2-element lists shaped like extension nodes (`0xc2 <path> <nested>` repeated), with `N` in the tens of thousands, fitting within the preimage size limits.
3. Serve `B` for key `H` through the preimage oracle to any node attempting independent verification/witness generation.
4. `TrieNode::decode` recurses `N` times through `try_decode_leaf_or_extension_payload` → `Self::decode`, exhausting the call stack of the verifying process before it can produce a witness/proof outcome, causing SIGSEGV/crash and denying honest verification.

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }

# `base-proof-mpt`

A recursive, in-memory implementation of Ethereum's hexary Merkle Patricia Trie (MPT).

## Overview

Implements Ethereum's Merkle Patricia Trie with support for retrieval, insertion, deletion, and
root computation via RLP-encoded trie node encoding. Starting from a trie root hash, `TrieNode`
lazily fetches and caches node preimages via `TrieProvider`, enabling stateless block execution
without storing the full state. Designed as the trie backend for [`base-proof-executor`](../executor).

    type Error = OracleProviderError;

    fn trie_node_by_hash(&self, key: B256) -> Result<TrieNode, Self::Error> {
        // On L1, trie node preimages are stored as keccak preimage types in the oracle. We assume
        // that a hint for these preimages has already been sent, prior to this call.
        crate::block_on(async move {
            TrieNode::decode(
                &mut self
                    .oracle
                    .get(PreimageKey::new(*key, PreimageKeyType::Keccak256))
                    .await
                    .map_err(OracleProviderError::Preimage)?
                    .as_ref(),
            )
            .map_err(OracleProviderError::Rlp)
        })
    }
