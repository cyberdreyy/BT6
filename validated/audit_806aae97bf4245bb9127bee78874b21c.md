## Analysis

The external report's bug class is: **a cache/lookup key that omits an identity field that can change, causing stale routing of value to the wrong account after that identity changes.** In `widget-react`, the client cache keyed only by `chainId` (omitting wallet address) kept routing signed transactions to the old wallet after the user switched accounts.

The Aptos-native analog exists in `staking_contract.move`'s beneficiary-redirect logic, which keys the "is this a commission payout that should be redirected to a beneficiary" check by comparing a stored distribution recipient against the *current* `operator` parameter — not by the actual identity that owned the pending distribution at the time it was created.

### Title
Stale operator-keyed commission distribution bypasses `BeneficiaryForOperator` after `switch_operator`, misdirecting pending commission to the raw old-operator address - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` force-requests the outgoing operator's uncommitted commission and records it in the `distribution_pool` under the key `old_operator` [1](#0-0) . The `StakingContract` struct is then moved to a new map entry keyed by `new_operator` [2](#0-1) . Because the old operator's key no longer exists in `Store.staking_contracts`, the only way to later pay out that pending distribution is via `distribute(staker, new_operator)`, which invokes `distribute_internal` with `operator = new_operator` [3](#0-2) . Inside `distribute_internal`, the beneficiary-redirect check is `if (recipient == operator)` [4](#0-3) , where `recipient` is the stale `old_operator` address recorded before the switch and `operator` is now `new_operator`. The comparison fails, so the payout is **not** redirected through `beneficiary_for_operator(old_operator)` and instead is sent directly to the raw `old_operator` address.

### Finding Description
1. Staker creates a staking contract with `operator1`, who calls `set_beneficiary_for_operator` to route all commission payouts to a separate `beneficiary` account [5](#0-4) .
2. Staker calls `switch_operator`/`switch_operator_with_same_commission` to move the pool to `operator2` [6](#0-5) . Internally this calls `request_commission_internal(old_operator, ...)`, which records a new distribution share keyed by `old_operator` via `add_distribution(operator, staking_contract, operator, commission_amount)` [7](#0-6) . This unlocked amount is not yet withdrawable (still subject to stake pool lockup), so it cannot be distributed within the same call.
3. The `StakingContract` is then re-keyed from `old_operator` to `new_operator` in the `Store.staking_contracts` map [8](#0-7) . There is no longer any entry point that can call `distribute_internal` with `operator = old_operator`, since `assert_staking_contract_exists(staker, old_operator)` will now fail.
4. Once the lockup expires, anyone calls `distribute(staker, new_operator)`. In `distribute_internal`, the stale `old_operator`-keyed share is redeemed, but the redirect check `recipient == operator` (`old_operator == new_operator`) is false, so `beneficiary_for_operator(old_operator)` is never consulted and the funds go straight to the `old_operator` address [9](#0-8) .

This mirrors the report's flaw exactly: the routing decision is keyed on an identity (`operator` parameter at distribution time) that no longer matches the identity that was valid when the value was recorded (`old_operator` at request time), silently sending funds to the wrong account with no error.

### Impact Explanation
The operator-configured `beneficiary_for_operator` mapping exists specifically so that commission need not be custodied by the (often hot/validator-controlled) operator key [10](#0-9) . This bug silently breaks that guarantee for any commission that was requested-but-unresolved at the moment of an operator switch, permanently misdirecting that commission to the raw operator address instead of the beneficiary who was entitled to it. This matches the required impact class of "Operator commission, beneficiary payout ... corruption that credits the wrong account or trap value," and the beneficiary has no recovery path once the funds land in the wrong account.

### Likelihood Explanation
`switch_operator`/`switch_operator_with_same_commission` are unprivileged, staker-callable entry functions [11](#0-10) , and operator switches together with beneficiary configuration are both documented, expected usage patterns (see AIP-related `operator_beneficiary_change_enabled` feature gate [12](#0-11) ). The only condition required is that the operator has requested/pending commission not yet distributed at the time of the switch — a routine timing occurrence given the unlock lockup delay inherent to stake pools.

### Recommendation
Do not compare the recorded distribution `recipient` against the *current* operator parameter. Instead, either:
- Redirect through `beneficiary_for_operator` at `add_distribution`/`request_commission_internal` time (i.e., record the beneficiary address as the recipient at creation, not the operator address), or
- Track the original operator address alongside each distribution entry so `distribute_internal` can always resolve `beneficiary_for_operator(original_operator)` regardless of what operator key the `StakingContract` is later re-mapped under.

### Proof of Concept
1. `staker` creates a staking contract with `operator1`, `commission_percentage = 10`.
2. `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary)`.
3. Validator earns rewards; `staker` calls `switch_operator(staker, operator1, operator2, new_commission)`. Internally this force-calls `request_commission_internal(operator1, ...)`, creating a pending distribution entry keyed to `operator1` for the outstanding commission, then moves the `StakingContract` to be keyed by `operator2`.
4. Fast-forward past the stake pool lockup.
5. Anyone calls `distribute(staker, operator2)`.
6. Observe: the pending commission amount is paid directly to `operator1`'s account balance, not to `beneficiary`'s account balance — violating the beneficiary configuration set in step 2.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

    /// Allows staker to switch operator without going through the lenghthy process to unstake.
    public entry fun switch_operator(
        staker: &signer,
        old_operator: address,
        new_operator: address,
        new_commission_percentage: u64
    ) acquires Store, BeneficiaryForOperator {
        let staker_address = signer::address_of(staker);
        assert_staking_contract_exists(staker_address, old_operator);

        assert!(
            new_commission_percentage <= 100,
            error::invalid_argument(EINVALID_COMMISSION_PERCENTAGE)
        );
        // Merging two existing staking contracts is too complex as we'd need to merge two separate stake pools.
        let store = borrow_global_mut<Store>(staker_address);
        let staking_contracts = &mut store.staking_contracts;
        assert!(
            !staking_contracts.contains_key(&new_operator),
            error::invalid_state(ECANT_MERGE_STAKING_CONTRACTS)
        );

        let (_, staking_contract) = staking_contracts.remove(&old_operator);
        // Force distribution of any already inactive stake.
        distribute_internal(
            staker_address,
            old_operator,
            &mut staking_contract,
        );

        // For simplicity, we request commission to be paid out first. This avoids having to ensure to staker doesn't
        // withdraw into the commission portion.
        request_commission_internal(
            old_operator,
            &mut staking_contract,
        );

        // Update the staking contract's commission rate and stake pool's operator.
        stake::set_operator_with_cap(&staking_contract.owner_cap, new_operator);
        staking_contract.commission_percentage = new_commission_percentage;

        let pool_address = staking_contract.pool_address;
        staking_contracts.add(new_operator, staking_contract);
        emit(SwitchOperator { pool_address, old_operator, new_operator });
    }

        let old_beneficiary = beneficiary_for_operator(operator_addr);

            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;

            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(

                operator: operator_addr,
                old_beneficiary,

            }
