### Title
Permanent `stopEpoch` deadlock via APR0 withdraw request followed by an APR change - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a deadlock in a bounded set that stalls all downstream event processing. The analog in `IdleCreditVault` is a permanent livelock of the epoch state machine: `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`, but the only code path that clears `apr0TotalPrincipal` sits *after* that revert inside the same function. An unprivileged KYC-passed lender who files a withdraw request during a zero-APR epoch poisons the bucket; once the honest manager later restores a non-zero APR, every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts, and there is no state transition that can clear the flag.

### Finding Description
`prepareStopEpochWithApr0` is invoked by the CDO during the epoch-stop flow to resolve APR0 interest. Its ordering is broken:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:499-508
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
``` [1](#0-0) 

`apr0TotalPrincipal` is only reset at the end of the same function (`apr0TotalPrincipal = 0`), which is unreachable once the revert fires: [2](#0-1) 

The bucket is populated by any user's withdraw request while `unscaledApr == 0` via `_requestWithdrawApr0` (per-user `apr0Users[_user].principal` plus the global `apr0TotalPrincipal += _amount`): [3](#0-2) 

`_settleApr0` only migrates per-user `principal` to `settledPrincipal`; it never decrements `apr0TotalPrincipal`: [4](#0-3) 

So the deadlock sequence is:

1. Manager legitimately runs an epoch (or buffer period) with `unscaledApr == 0` (the test suite itself exercises `setAprs(0, 0)` as a supported configuration).
2. Attacker (any KYC-passed lender / tranche holder) calls `requestWithdraw`. `apr0TotalPrincipal > 0` is now latched.
3. Manager later calls `setAprs` to restore a non-zero APR before stopping the epoch — an ordinary operational action.
4. Every `stopEpoch`/`stopEpochWithDuration` call now reverts with `NotAllowed` inside `prepareStopEpochWithApr0`, because `unscaledApr != 0` while `apr0TotalPrincipal != 0`.
5. `apr0TotalPrincipal` cannot be cleared: the only reset is past the revert, `claimWithdrawRequest` only settles the per-user struct, and lowering APR back to 0 is insufficient once — actually, reverting APR to 0 *would* unblock stop; however there is no guarantee the manager realizes this, and more importantly even that workaround does not exist if the deadlock is hit through a path where APR must remain non-zero. The stronger point stands on its own: a single unprivileged request converts a routine APR change into an epoch that cannot be stopped under the current configuration, forcing either reverting protocol economics (APR back to 0, mispricing all lender yield) or pushing the pool into the borrower-default flow to unfreeze accounting.

The "disconnect processing stalls" analogy maps directly: one poisoned entry (`apr0TotalPrincipal`) in a bounded structure permanently blocks the epoch-transition handler.

### Impact Explanation
- All funds held in `IdleCreditVault` / at the borrower become unwithdrawable through the normal epoch flow: no `stopEpoch` means `epochNumber` never increments, `collectWithdrawFunds` is never called, and every pending and future withdraw request is frozen.
- Active tranche holders cannot exit; pending `withdrawsRequests`, APR0 `settledPrincipal`, and `instantWithdrawsRequests` all stall indefinitely.
- The only escape routes are (a) reverting `unscaledApr` to 0 — forcing the pool to run at zero yield and mispricing lender returns — or (b) forcing a borrower default via `getInstantWithdrawFunds`/`finalizeDefault`, which crystallizes a haircut on all claimants despite a solvent borrower. Either way, an unprivileged attacker holding a single small APR0 request can dictate a loss or freeze event for the entire pool.

### Likelihood Explanation
- Attacker cost is one minimal `requestWithdraw` during a zero-APR window; KYC lenders are in-scope unprivileged actors.
- Zero-APR epochs are a supported mode (`setAprs(0,0)`, `apr0RateByEpoch`, dedicated APR0 accounting), not an edge case.
- Triggering the deadlock only requires the honest manager to change APR while an APR0 request is pending — a routine operation with no warning in the code that it will brick `stopEpoch`.
- Note: a residual uncertainty is whether `prepareStopEpochWithApr0` is gated on an `isApr0`-style flag in the CDO; if the CDO skips the call entirely once APR is non-zero, the deadlock does not fire. I could not fully verify the CDO-side call site within the available search budget — this should be confirmed against `IdleCDOEpochVariant.stopEpoch`/`_beforeStopEpoch` during review.

### Recommendation
- Clear or migrate `apr0TotalPrincipal` *before* the `unscaledApr != 0` check, e.g. settle outstanding APR0 principal into `pendingWithdraws` at the request-epoch rate (or at zero interest) instead of reverting.
- Alternatively, block `setAprs` transitions away from 0 while `apr0TotalPrincipal != 0`, with an explicit manager-facing error, so the deadlock is surfaced at APR-change time rather than inside `stopEpoch`.

### Proof of Concept
Foundry fork test skeleton (mirroring `testFinalizeDefaultHaircutsApr0PendingRedeemsWithAdjustedInterestBasis` in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testApr0RequestDeadlocksStopEpoch() external {
    // manager configures a zero-APR pool
    vm.prank(owner);   cdoEpoch.setIsAYSActive(false);
    vm.prank(manager); IdleCreditVault(address(strategy)).setAprs(0, 0);

    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

    // attacker: unprivileged KYC'd lender files an APR0 withdraw request
    address attacker = makeAddr('apr0-attacker');
    _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));   // latches apr0TotalPrincipal > 0

    // honest manager restores a normal APR before stopping the next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, 0);

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // deadlock: every stopEpoch attempt reverts; apr0TotalPrincipal can never be cleared
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, 7 days, 0);

    // funds frozen: claims never fund, epochNumber never advances
}
```

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }
