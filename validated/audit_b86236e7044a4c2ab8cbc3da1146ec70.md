### Title
Masker (phrase) stage processing before tokensanitizer (prefix) stage lets an attacker-registered mask phrase break prefix-based token detection, leaking secret suffixes - (File: `common/buildlogger/build_logger.go`)

### Summary
The production wrap chain built in `Logger.wrap` runs the phrase masker (`masker.New`) **before** the prefix-based token sanitizer (`tokensanitizer.New`) [1](#0-0) . Because `masker` and `tokensanitizer` are independent stateful byte-scanners that don't share state, a mask phrase that is an exact prefix (or overlapping substring) of a real token prefix (e.g. `glpat-`, `gloas-`, `glcbt-`, etc.) gets consumed and replaced with the literal string `[MASKED]` by the masker stage before the tokensanitizer stage ever sees the contiguous prefix bytes, so the tokensanitizer's prefix-scan never fires and the token's secret suffix passes through unmasked.

### Finding Description
`Logger.wrap` instantiates writers in this order (last-instantiated processes first): `masker.New` (phrase masking) is the outermost/first stage, followed by `urlsanitizer.New`, then `tokensanitizer.New` (prefix masking), then `timestamper.New`, then the base trace writer [2](#0-1) .

`masker.masker.Write` scans byte-by-byte for an exact configured phrase; on a full match it synchronously writes the literal bytes `[MASKED]` to `m.next` (i.e., forwards to urlsanitizer→tokensanitizer) and only forwards the *remaining, unmatched* bytes afterward [3](#0-2) . Both `masker` and `tokensanitizer.tokenSanitizer` maintain their own independent `matching` state across `Write()` calls specifically to detect matches split across call boundaries [4](#0-3) , but that cross-call state machine only works on the *contiguous byte stream* it actually receives. If the masker stage has already spliced in the literal text `[MASKED]` in place of the token's prefix bytes, tokensanitizer's `IndexByte(p, prefix[0])` scan for the first prefix byte never finds a match — because the true prefix bytes were consumed and replaced upstream — so the alphabet run following the (now-missing) prefix is written straight through unmasked [5](#0-4) .

`MaskPhrases` is populated from `b.GetAllVariables().Masked()`, i.e., the values of CI/CD variables flagged `Masked: true` [6](#0-5) [7](#0-6) . Additionally, `common/buildtest/masking.go` demonstrates that the job script itself can register a phrase at runtime via `echo "::add-mask::VALUE"`, handled by `commands/helpers/proxy_exec.go` [8](#0-7) , confirming an unprivileged pipeline author can inject an arbitrary mask phrase into the running job's masking set without needing project-level "Masked variable" permissions.

An attacker who can define/register a masked value equal to (or matching as a prefix of) a well-known GitLab token prefix — e.g. `glpat-`, or any of the prefixes in `tokensanitizer.allTokenPrefixes` (`gloas-`, `gldt-`, `glrt-`, `glcbt-`, `glrtr-`, `glptt-`, `glft-`, `glimt-`, `glagent-`, `glsoat-`, `glffct-`, `gltok-`) [9](#0-8)  — causes the masker stage to consume and mask *only that prefix substring* wherever it appears in later trace output, before tokensanitizer's prefix+alphabet scan ever runs on the full token. Any subsequently emitted real token sharing that prefix (e.g. a leaked backend credential accidentally echoed by the job, error output containing a Bearer token, or a credential embedded in a URL that isn't caught by `urlsanitizer`) then has its prefix replaced by `[MASKED]` and its secret suffix (the actually sensitive part) written to the trace log in cleartext.

The fuzz harness in `internal/build_logger_fuzz.go` builds the chain in a *different* nesting order (`urlsanitizer(tokensanitizer(masker(base)))`, i.e. masker processes *last*) than the real production order in `build_logger.go` (`masker(urlsanitizer(tokensanitizer(base)))`, masker processes *first*) [10](#0-9) [1](#0-0) , so this fuzz target never exercises the actual production ordering and would not have caught this interaction.

### Impact Explanation
The masking pipeline is a core invariant of GitLab Runner: secrets/tokens must never leak into job logs. This ordering flaw allows an unprivileged pipeline author to neutralize the prefix-based defense-in-depth layer (`tokensanitizer`) for any GitLab-format token appearing later in the same job's trace, by simply masking the known constant prefix string as an ordinary mask phrase. Any backend auth token (personal access token, deploy token, runner token, CI job token, agent token, etc.) that happens to surface in the trace with that prefix will have only its prefix hidden while its secret suffix is printed in cleartext, enabling credential theft and downstream impersonation.

### Likelihood Explanation
Feasible and fully attacker-controlled: the attacker only needs to (1) get an arbitrary string equal to a known token prefix registered as a masked value — via a project "Masked" CI/CD variable they can set, or via the job-script-triggered `::add-mask::` trace command — and (2) have any real token with that prefix appear later in the job output (a realistic scenario for tokens surfaced by API error messages, misconfigured debug output, or environment dumps). No special executor privileges or admin access are required; this is deterministic given the write orderings shown in `masker.go` and `token_masker.go`.

### Recommendation
Do not rely on independent, order-sensitive masking stages that can consume each other's match anchors. Either: (1) reorder the wrap chain so `tokensanitizer` (prefix-based) processes before `masker` (phrase-based), and additionally reject/ignore any registered mask phrase that is itself a strict prefix of a configured/default token prefix, or (2) merge phrase and prefix masking into a single combined scanning pass that evaluates all candidate matches (phrases and prefixes) against the original unmodified byte stream before any substitution is emitted downstream, so a phrase match can never suppress bytes needed for a still-pending prefix match.

### Proof of Concept
Go unit test in `common/buildlogger` reproducing production ordering (not the fuzz harness's differing order):
```go
func TestMaskerBreaksTokenSanitizerPrefixDetection(t *testing.T) {
    buf := new(bytes.Buffer)
    w := io.WriteCloser(nopWriteCloser{buf})
    w = tokensanitizer.New(w, [][]byte{[]byte("glpat-")})
    w = urlsanitizer.New(w)
    w = masker.New(w, [][]byte{[]byte("glpat-")}) // attacker registers "glpat-" as a mask phrase

    _, err := w.Write([]byte("token leaked: glpat-REALSECRETVALUE\n"))
    require.NoError(t, err)
    require.NoError(t, w.Close())

    out := buf.String()
    // Expect full token masked, but bug produces "[MASKED]REALSECRETVALUE"
    assert.NotContains(t, out, "REALSECRETVALUE", "secret suffix leaked because masker consumed the prefix before tokensanitizer could match it")
}
```
Expected (buggy) result: the assertion fails, showing `REALSECRETVALUE` present in `out` even though `glpat-` was individually "masked" by each stage.

// wrap wraps the underlying writer with "filters". Order here somewhat
// matters, and the order they're instantiated in is the reverse order in which
// writes are processed, e.g. last added filter is the first to process data.
//
// order:
// - sync writer to ensure that multiple writes cannot happen concurrently
// - mask phrases (masker.New)
// - mask sensitive URL parameters (urlsanitizer.New)
// - mask secrets with a prefixed token (tokentanitizer.New)
// - split log lines and add timestamps (timestamper.New)
func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}

	prefix   []byte
	matching int
	masked   bool
	next     io.WriteCloser
}

//nolint:gocognit
func (m *tokenSanitizer) Write(p []byte) (n int, err error) {
	if len(p) == 0 {
		return 0, nil
	}

	// fast path: if the write is "[MASKED]" from an upper-level, don't bother
	// processing it, send it to the next writer.
	if bytes.Equal(p, mask) {
		return m.next.Write(p)
	}

	var last int
	for n < len(p) {
		if m.matching == len(m.prefix) {
			if alphabet[p[n]] {
				m.masked = true
				n++
				last = n
				continue
			}

			if m.masked {
				m.masked = false
				_, err := m.next.Write(mask)
				if err != nil {
					return n, err
				}
			}
			m.matching = 0
		}

		// optimization: use the faster IndexByte to jump to the start of a
		// potential prefix and if not found, advance the whole buffer.
		if m.matching == 0 {
			off := bytes.IndexByte(p[n:], m.prefix[0])
			if off < 0 {
				n += len(p[n:])
				break
			}
			if off > -1 {
				n += off
			}
		}
