### Title
De-KYC'd users bypass the Keyring whitelist gate through `claimWithdrawRequest` / `claimInstantWithdrawRequest` - (`contracts/IdleCDOEpochVariant.sol`)

### Summary
`IdleCDOEpochVariant` enforces the Keyring credential check (`isWalletAllowed`) on every entry/state-changing path — `_deposit`, `depositDuringEpoch`, and `requestWithdraw` — but neither `claimWithdrawRequest` nor `claimInstantWithdrawRequest` checks it. A user whose Keyring credential is revoked (or who acquired receipt-bearing status before revocation) can still pull underlying out of `IdleCreditVault`, so the compliance gate that blocks `requestWithdraw` does not block the payout leg of the same flow — the same bug class as the reported `safeBatchTransferFrom` missing the `NoBlacklist(from)` check.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol`:

- `_deposit` checks `!isWalletAllowed(msg.sender)` [1](#0-0) 
- `depositDuringEpoch` includes `!isWalletAllowed(msg.sender)` in its revert condition [2](#0-1) 
- `requestWithdraw` includes `!isWalletAllowed(msg.sender)` [3](#0-2) 
- `isWalletAllowed` queries the external Keyring credential contract [4](#0-3) 

But the two claim entry points have no check at all:

```solidity
function claimWithdrawRequest() external {
    IdleCreditVault(strategy).claimWithdrawRequest(msg.sender);   // no isWalletAllowed
}
function claimInstantWithdrawRequest() external {
    _checkNotAllowed(!allowInstantWithdraw);                       // only the flag
    IdleCreditVault(strategy).claimInstantWithdrawRequest(msg.sender);
}
``` [5](#0-4) 

The vault-side claim functions (`claimWithdrawRequest`, `claimInstantWithdrawRequest`, `_claimFundedWithdrawRequest`, `_transferFundedClaim`, `_transferDefaultRecovery`) are gated only by `_onlyIdleCDO` and epoch timing — they have no Keyring awareness, so the check cannot be delegated [6](#0-5) [7](#0-6) .

Sequence:

1. Epoch 0 running/buffer: an allowed wallet calls `requestWithdraw`, receives strategy-token receipts bound to its address (receipts are intentionally non-transferable via the `_transfer` override).
2. The epoch settles; the receipt is funded via `collectWithdrawFunds` / `collectInstantWithdrawFunds`.
3. Before the user claims, the Keyring admin revokes the user's credential — `isWalletAllowed(user)` now returns `false`. The user can no longer deposit or request withdrawals.
4. Despite revocation, the user calls `cdoEpoch.claimWithdrawRequest()` and receives the full funded underlying amount via `_transferFundedClaim`/`_transferDefaultRecovery`.

The same applies to instant-withdraw receipts (`claimInstantWithdrawRequest`), loss-adjusted claims (`_claimLossAdjustedWithdrawRequest`), defaulted-epoch claims (`_claimDefaultedWithdrawRequest`), and post-default requests (`_claimPostDefaultWithdrawRequest`) — all reachable through the unchecked `claimWithdrawRequest` wrapper [8](#0-7) .

Notably, the codebase already treats Keyring revocation as a meaningful gate: `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw` asserts that a non-Keyring holder of tranche tokens (acquired via `WriteOffEscrow.fullfillWriteOffRequest`) reverts on `requestWithdraw` — proving the intent that non-allowed wallets must not be able to redeem positions [9](#0-8) . The claim path violates that intent for pre-existing requests.

### Impact Explanation
Medium. A user flagged by Keyring policy (sanctions, compliance revocation) retains full ability to withdraw vault funds — including default-recovery reserve payouts that should arguably be restricted — through a path the protocol explicitly guards on the request side. Funds lost are the user's own claim, so there is no direct theft from other LPs; the impact is failure of the compliance/blacklist control itself, exactly analogous to the reported medium finding. If the vault design intends revocation to freeze a wallet's interaction, this is a complete bypass of the freeze for any matured receipt.

### Likelihood Explanation
Medium. Revocation of a Keyring credential between a `requestWithdraw` and the subsequent `claimWithdrawRequest` (which requires at least one full epoch wait) is a realistic operational event — that waiting window is precisely when a compliance flag would typically be raised. No privileged attacker is required; the honest Keyring admin revoking a credential is an expected, in-scope action.

### Recommendation
Add the wallet check to both claim functions, matching `requestWithdraw`:

```solidity
function claimWithdrawRequest() external {
    _checkNotAllowed(!isWalletAllowed(msg.sender));
    IdleCreditVault(strategy).claimWithdrawRequest(msg.sender);
}

function claimInstantWithdrawRequest() external {
    _checkNotAllowed(!allowInstantWithdraw || !isWalletAllowed(msg.sender));
    IdleCreditVault(strategy).claimInstantWithdrawRequest(msg.sender);
}
```

If the intent is instead that matured claims must remain redeemable even after revocation (exit-only mode), document that explicitly and consider whether the `requestWithdraw` check is then overly restrictive — but the two paths should be consistent. Also consider checking `isWalletAllowed` in `IdleCDOEpochQueue.claimDepositRequest`/`claimWithdrawRequest` for prefunded variants if the same invariant is meant to hold there.

### Proof of Concept
Foundry test (place in `test/foundry/IdleCreditVault.t.sol` harness, reusing `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testRevokedUserCanStillClaimWithdrawRequest() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    address user = makeAddr("user");
    address keyring = address(1);

    // enable keyring gate; user initially passes
    vm.prank(cdoEpoch.owner());
    cdoEpoch.setKeyringParams(keyring, 1);
    vm.mockCall(
        keyring,
        abi.encodeWithSelector(IKeyring.checkCredential.selector, 1, user),
        abi.encode(true)
    );

    // user deposits (allowed) and requests withdraw in buffer period
    _depositWithUser(user, amountWei, true);
    vm.prank(user);
    uint256 claimAmount = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch settles, receipt is funded
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Keyring revokes user's credential: requestWithdraw now reverts,
    // proving the gate treats revocation as blocking
    vm.mockCall(
        keyring,
        abi.encodeWithSelector(IKeyring.checkCredential.selector, 1, user),
        abi.encode(false)
    );
    assertFalse(cdoEpoch.isWalletAllowed(user));
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.requestWithdraw(1, address(AAtranche));

    // BUG: but the matured claim still pays out in full to the revoked wallet
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(user) - balPre, claimAmount, "revoked user claimed funded receipt");
}
```

The analogous PoC for `claimInstantWithdrawRequest` requests during an instant-eligible epoch (APR decreased beyond `instantWithdrawAprDelta`) and then calls `claimInstantWithdrawRequest` after revocation — same missing check.

      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);

    amount += _claimLossAdjustedWithdrawRequest(_user);
    return amount + _claimFundedWithdrawRequest(_user);
  }
