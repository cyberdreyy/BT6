### Title
Own-tenure conflict fail-open on RPC error lets a signer double-sign conflicting blocks - (File: `stacks-signer/src/v0/signer.rs`, function `handle_block_pre_commit`)

### Summary
The external report's bug class is: an assumption made about the deployment environment (gas price, gas limit, transaction execution success) that, if it silently fails to hold, causes an irrevocable, one-shot action (Nick's-method deployment) to not land at the intended address — with no retry path. The closest reachable analog in the signer is the own-tenure conflict re-check performed just before a signature is produced in `handle_block_pre_commit`: on a node RPC failure the signer treats the tenure as "unconfirmed" and proceeds to take the irrevocable action (signing), rather than refusing to sign. If the node's canonical tip actually *had* already reached or passed the proposed height (i.e., the earlier conflicting block is real chain state), a transient RPC error still results in a second, conflicting signature being produced.

### Finding Description
In `handle_block_pre_commit`, once pre-commit weight reaches the ≥70% threshold, the signer re-derives whether it is safe to sign by checking for signed conflicts at the same or higher height [1](#0-0) . Fresh conflicts (`last_endorsed > freshness_cutoff`) that are still "live" per `conflict_still_blocks`/`reorg_permit_stands` correctly block the signature [2](#0-1) .

However, for a **stale** conflict in the block's **own tenure**, the code queries the node's canonical tenure tip to decide whether the conflict still blocks:

```
match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) {
    Ok(tip) => { if tip_height >= block_info.block.header.chain_length { ... return; } }
    Err(e) => {
        warn!("... Treating the tenure as unconfirmed."); // falls through, does NOT return
    }
}
``` [3](#0-2) 

On `Err(e)` the function does not return; execution falls through to the signing path (`mark_locally_accepted`, `create_block_acceptance`, `handle_block_signature`, broadcast) [4](#0-3) . This is the same "own tenure, node unreachable → SIGN" branch documented in `docs/signer-flows.md` section 5 [5](#0-4) , and the design rationale explicitly states this trade-off is deliberate: "For the own-tenure question below, an unreachable node is instead treated as unconfirmed and the signature goes out." [6](#0-5) 

The equality being relied on is: *"node RPC failure implies the tenure tip has not actually reached the proposed height."* That equality does not hold — an RPC failure (timeout, connection reset, node restart, node momentarily overloaded by request volume/gossip) is orthogonal to the node's actual chain state. A single miner (who legitimately re-proposes a competing block B at the same height/tenure after A's pre-commit staled, which is an explicitly supported liveness path — see `stale_sibling_replaced_when_canonical_tip_below` [7](#0-6) ) combined with any transient failure of this signer's own `get_tenure_tip` RPC at the moment of pre-commit-threshold evaluation, is enough to trigger the fail-open branch even when the node had, in fact, already confirmed A at or above B's height.

Because a signature is a bearer instrument that is aggregated toward the 70% global threshold regardless of what the signer's local view later becomes (per the docs: "rejection... does not clear one: a rejection is a revocable opinion, while a signature is a bearer instrument" [8](#0-7) ), this signer would now have two live signatures over two conflicting blocks at the same height in the same tenure — precisely the equivocation the whole pre-commit/conflict-guard machinery in section 5 exists to prevent.

### Impact Explanation
This maps to the Critical bucket: "a signer signing an invalid, non-canonical, or conflicting block." A single signer signing two conflicting blocks at the same height contributes weight toward both forks reaching the 70% aggregation threshold, undermining the single-block-per-height safety property the whole `get_signed_conflicts`/`conflict_still_blocks` design is meant to guarantee, and can help a fork/equivocation get enough combined weight to be pushed to the node.

### Likelihood Explanation
This does not require a majority of signers or another signer's key — only:
1. A one-slot miner (or any actor able to cause miner behavior) re-proposing a second block B at the same height/tenure after the freshness window on the signer's earlier acceptance of A elapses — an explicitly supported, common scenario per the existing test suite.
2. A transient failure of the signer's own outbound RPC call to its own stacks-node's `/v3/tenures/.../tip` endpoint (`get_tenure_tip`) at the exact moment the pre-commit threshold for B is reached — network blips, node restart, node briefly overloaded, or general request timeout are all realistic and not attacker-controlled-signer-key events.

The window is per-signer and per-evaluation (it re-runs on every pre-commit re-check), so probability accumulates over the life of a stalled/contested tenure, and is elevated during exactly the periods (miner reorg attempts, node restarts) most associated with chain instability.

### Recommendation
Treat an RPC failure on the own-tenure tip check the same way `conflict_still_blocks` treats other RPC failures elsewhere in the same function: fail closed, i.e. keep the conflict blocking (do not sign) and let the next re-evaluation retry, rather than falling through to sign. This is consistent with the surrounding code's own stated principle: "Whenever the node cannot be asked, the conflict keeps blocking... That only delays the replacement until the signature goes stale, whereas wrongly signing cannot be taken back." [9](#0-8)  — the own-tenure branch is the one place that currently violates that stated principle.

### Proof of Concept
1. Signer signs block A (tenure T, height h) which is later superseded because A stalls past `tenure_last_block_proposal_timeout` (conflict becomes stale). Node's canonical tip for tenure T is actually confirmed at ≥ h (A landed).
2. Miner proposes block B, also in tenure T at height h (conflicting sibling). B reaches the local pre-commit threshold.
3. `handle_block_pre_commit` runs; the fresh-conflict branch is skipped because A is stale (`last_endorsed <= freshness_cutoff`) [2](#0-1) .
4. The own-tenure stale-conflict branch fires: it calls `stacks_client.get_tenure_tip(consensus_hash)` [10](#0-9) . Simulate/induce a transient error on this call (e.g., node briefly unavailable).
5. Execution falls through the `Err(e)` branch (only logs a warning) and proceeds to sign B: `mark_locally_accepted`, `create_block_acceptance`, `handle_block_signature`, broadcast [4](#0-3) .
6. The signer has now produced valid signatures over both A (already confirmed by the node) and B (a conflicting sibling at the same height), which can be aggregated by other signers/the coordinator toward opposing 70% thresholds.

This could not be fully exercised in a live environment from this analysis (no filesystem/test-execution access); the control-flow trace above is derived directly from reading `handle_block_pre_commit` and corroborated by the design doc's explicit acknowledgment of this exact fail-open trade-off.
