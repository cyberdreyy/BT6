### Title
BridgeResource.OutgoingToken credential disclosed to any authenticated user via GET /v2/bridge_types/:BridgeName - ([File: core/web/presenters/bridges.go], [File: core/web/router.go], [File: core/web/bridge_types_controller.go])

### Summary
The `Show` route for bridges (`GET /v2/bridge_types/:BridgeName`) has no role restriction wrapper, unlike `Create`/`Update`/`Destroy`, so any authenticated user (including the lowest-privilege view-role user) can call it. The response is built via `presenters.NewBridgeResource`, whose `BridgeResource.OutgoingToken` field lacks `omitempty` and is always populated from `bridges.BridgeType.OutgoingToken`, causing the bridge's outgoing-connection credential to be returned in plaintext to any caller who can reach the endpoint.

### Finding Description
In `core/web/router.go`, bridge routes are registered as:
```go
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
authv2.GET("/bridge_types/:BridgeName", bt.Show)
authv2.PATCH("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Update))
authv2.DELETE("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Destroy))
``` [1](#0-0) 
`Create`, `Update`, and `Destroy` are gated with `auth.RequiresEditRole`, but `Show` (and `Index`) are only wrapped in the base `authv2` group, which just requires successful authentication (session or API token) with no role check.

`BridgeTypesController.Show` fetches the full `bridges.BridgeType` record (including `OutgoingToken`) and renders it directly:
```go
bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
...
jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
``` [2](#0-1) 

`presenters.NewBridgeResource` copies `b.OutgoingToken` into the resource unconditionally, and the struct tag lacks `omitempty` (unlike `IncomingToken`, which is `omitempty` and only populated explicitly on `Create`):
```go
IncomingToken          string       `json:"incomingToken,omitempty"`
OutgoingToken          string       `json:"outgoingToken"`
...
func NewBridgeResource(b bridges.BridgeType) *BridgeResource {
	return &BridgeResource{
		...
		OutgoingToken:          b.OutgoingToken,
``` [3](#0-2) 

This is confirmed by the existing presenter test, which asserts `outgoingToken` is always present in the JSON, even before `IncomingToken` is set: [4](#0-3) 

`OutgoingToken` is a real credential stored per bridge on `bridges.BridgeType`, used to authenticate the node's outgoing connection to the bridge/external adapter manager: [5](#0-4) 

Because the `Show` route requires only authentication (not any specific role), any low-privilege authenticated principal — e.g., a view-role user or an API token restricted to view access — can call `GET /v2/bridge_types/:BridgeName` and receive `OutgoingToken` in the response body, since no presenter-level redaction or role gate exists to stop it.

### Impact Explanation
This is a credential/secret disclosure: the bridge's `OutgoingToken`, used to authenticate the node's outgoing connections to the external adapter/bridge manager, is exposed to any authenticated node user regardless of role. An attacker with only view privileges (e.g., a compromised low-privilege dashboard account or read-only API key) can enumerate bridge names via `GET /v2/bridge_types` (also unrestricted) and then retrieve each bridge's `OutgoingToken` via `Show`, enabling impersonation of the node's outgoing bridge connection to third-party adapter services.

### Likelihood Explanation
Fully feasible and repeatable with minimal privilege: any valid session or API token (no specific role required) can hit `GET /v2/bridge_types/:BridgeName`. No additional preconditions beyond authentication are needed, since the route bypasses the edit-role checks applied to mutating bridge endpoints, and the presenter serializes `OutgoingToken` unconditionally.

### Recommendation
Add `omitempty` to `OutgoingToken` in `presenters.BridgeResource` and only populate it in contexts where it is intended to be shown (analogous to how `IncomingToken` is only set on `Create`), or restrict `GET /v2/bridge_types/:BridgeName` and `GET /v2/bridge_types` with `auth.RequiresEditRole`/`RequiresAdminRole` consistent with the mutating endpoints. Also review `core/web/resolver/bridge.go`'s `OutgoingToken()` GraphQL resolver for the same issue.

### Proof of Concept
1. Unit test (presenter): call `presenters.NewBridgeResource` with a `bridges.BridgeType{OutgoingToken: "secret"}`, marshal with `jsonapi.Marshal`, assert the JSON contains `"outgoingToken":"secret"` — matches existing `TestBridgeResource` behavior in `core/web/presenters/bridges_test.go`.
2. Integration test (handler-level, in `core/web/bridge_types_controller_test.go` style):
   - Create an app/client with a user whose API token/session has only view role (not admin/edit).
   - Create a bridge via an admin/edit-role client with a known `OutgoingToken`.
   - As the view-role client, `GET /v2/bridge_types/<name>`.
   - Assert response status is `200 OK` (not `403 Forbidden`).
   - Parse the JSON response and assert `resource.OutgoingToken == "<known token>"`, proving disclosure to an unprivileged viewer.
