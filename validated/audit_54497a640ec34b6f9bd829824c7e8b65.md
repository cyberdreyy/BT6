Based on my investigation, this is a valid, if narrow, timing bug in commission-effectiveness gating, but it is not the scenario the question describes (an owner attacking someone else's pool) — rather it's a self-inflicted/derivative timing gap that mis-prices commission for the pool's own delegators for at most one epoch's worth of rewards. I'll report it as found, scoped correctly.

### Title
Premature commission-percentage flip due to `effective_after_secs` being decoupled from actual lockup renewal - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
`update_commission_percentage` sets `NextCommissionPercentage.effective_after_secs = stake::get_lockup_secs(pool_address)` [1](#0-0) , and `is_next_commission_percentage_effective` gates the flip purely on `timestamp::now_seconds() >= effective_after_secs` [2](#0-1) . However, `stake::get_lockup_secs` (`locked_until_secs`) is a value that only advances when an actual epoch reconfiguration renews it [3](#0-2) , and pending_inactive stake is only actually inactivated for the ending lockup cycle at that same reconfiguration point [4](#0-3) . Timestamp advancement and the actual lockup-renewal/inactivation event are two separate triggers: the timestamp check can be satisfied before the corresponding on-chain reconfiguration executes.

### Finding Description
`synchronize_delegation_pool` computes `commission_active`/`commission_pending_inactive` with the OLD `pool.operator_commission_percentage` first (correct), then, after distributing that commission, checks `is_next_commission_percentage_effective` and — if true — immediately overwrites `pool.operator_commission_percentage` with the new value [5](#0-4) . `lockup_cycle_ended` (which controls whether the delegation pool actually advances its observed lockup cycle, i.e. whether the pending_inactive shares pool for the just-ended OLC is truly closed) is separately derived from `stake::get_stake`'s `inactive` amount rising [6](#0-5) , which itself only changes at the same reconfiguration event.

Because `synchronize_delegation_pool` is a public entry function reachable from any unprivileged caller (indirectly via `add_stake`, `unlock`, `withdraw`, `set_operator`, `update_commission_percentage`, or directly) [7](#0-6) , there exists a window — bounded by the interval between the timestamp crossing the old `locked_until_secs` and the next actual reconfiguration — during which:
- `now_seconds() >= effective_after_secs` is true (so `is_next_commission_percentage_effective` returns true), but
- the stake pool has not yet inactivated the current lockup cycle's `pending_inactive` stake, and the delegation pool's `observed_lockup_cycle` has not advanced.

In that window, `pool.operator_commission_percentage` is switched to the new value while the current (still nominally "ongoing") lockup cycle's `active`/`pending_inactive` rewards continue to accrue. Any further reward distribution processed by `synchronize_delegation_pool` before the next reconfiguration will then commission those rewards — earned within what the code's own commentary treats as the still-open lockup cycle — at the new rate instead of the old rate.

### Impact Explanation
This does not let one party attack another party's pool or steal stake it doesn't own — the caller must already own the pool being modified (`get_owned_pool_address` requires `DelegationPoolOwnership`) [8](#0-7) . The affected unprivileged parties are the delegators of that same pool (and, symmetrically, the operator), whose commission split for the tail of a lockup cycle (bounded by roughly one epoch's worth of rewards, since lockup renewal happens at the next reconfiguration after the threshold is crossed) can be computed with the wrong (new instead of old) commission percentage. This corrupts the accounting invariant that a commission change only applies starting the next full lockup cycle, but the magnitude of value affected is capped by one epoch's rewards rather than unbounded value redirection.

### Likelihood Explanation
Triggering it requires no special access: any account can call `add_stake`/`unlock`/`withdraw` (or the owner calls `update_commission_percentage`/`set_operator`) at the right moment, and the owner controls exactly when to schedule the commission change relative to the lockup boundary. The `ETOO_LATE_COMMISSION_CHANGE` check only bounds how close to lockup expiry the *request* can be made [9](#0-8) ; it does not close the gap between timestamp-based `effective_after_secs` and the actual reconfiguration-driven lockup renewal, so the described window exists on every lockup boundary, not just under adversarial timing.

### Recommendation
Gate `is_next_commission_percentage_effective` (or the point at which `pool.operator_commission_percentage` is updated in `synchronize_delegation_pool`) on `lockup_cycle_ended` (the actual on-chain inactivation signal) rather than, or in addition to, the raw timestamp comparison against a captured `effective_after_secs`, so the commission-rate flip is synchronized with the real lockup-cycle boundary instead of a frozen snapshot of `locked_until_secs`.

### Proof of Concept
1. Initialize a delegation pool with commission `X%`, add delegator stake, activate the validator.
2. Shortly before the current lockup boundary (`stake::get_lockup_secs(pool_address)`), call `update_commission_percentage(owner, Y%)`; this sets `effective_after_secs = current locked_until_secs`.
3. Advance `timestamp` minimally past that `locked_until_secs` value WITHOUT calling `end_aptos_epoch()`/triggering reconfiguration (i.e., do not let `stake::on_new_epoch` run yet).
4. Call `synchronize_delegation_pool(pool_address)` (or trigger it via `add_stake`/`unlock`). Observe `is_next_commission_percentage_effective(pool_address) == true` and `pool.operator_commission_percentage` flips to `Y%`, while `stake::get_stake` shows `pending_inactive` unchanged (not yet inactivated) and `observed_lockup_cycle` unchanged — proving the flip preceded the real lockup-cycle end.
5. Produce further rewards before the next `end_aptos_epoch()`/reconfiguration and call `synchronize_delegation_pool` again; assert the commission taken for that reward slice used `Y%` instead of `X%`, even though it is still part of the pre-boundary lockup cycle.

    fun calculate_stake_pool_drift(pool: &DelegationPool): (bool, u64, u64, u64, u64) {
        let (active, inactive, pending_active, pending_inactive) = stake::get_stake(get_pool_address(pool));
        assert!(
            inactive >= pool.total_coins_inactive,
            error::invalid_state(ESLASHED_INACTIVE_STAKE_ON_PAST_OLC)
        );
        // determine whether a new lockup cycle has been ended on the stake pool and
        // inactivated SOME `pending_inactive` stake which should stop earning rewards now,
        // thus requiring separation of the `pending_inactive` stake on current observed lockup
        // and the future one on the newly started lockup
        let lockup_cycle_ended = inactive > pool.total_coins_inactive;

        // actual coins on stake pool belonging to the active shares pool
        active += pending_active;
        // actual coins on stake pool belonging to the shares pool hosting `pending_inactive` stake
        // at current observed lockup cycle, either pending: `pending_inactive` or already inactivated:
        if (lockup_cycle_ended) {
            // `inactive` on stake pool = any previous `inactive` stake +
            // any previous `pending_inactive` stake and its rewards (both inactivated)
            pending_inactive = inactive - pool.total_coins_inactive
        };
