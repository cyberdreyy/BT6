### Title
Stale APR0 principal bucket permanently bricks `stopEpoch` after an APR change, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts whenever the global `apr0TotalPrincipal` bucket is non-zero while `unscaledApr` is non-zero. The bucket is only cleared at the end of that same function (or on the default-recovery path), and `_settleApr0` / `claimWithdrawRequest` never decrement it. An unprivileged tranche holder can therefore park a dust APR0 withdraw request, wait for the honest manager to set a non-zero APR for a later epoch, and every subsequent `stopEpoch`/`stopEpochWithDuration` call permanently reverts — the epoch can never close, mirroring the Spring Retry bug where a poisoned shared stateful structure permanently rejects all further updates.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` → `_requestWithdrawApr0` adds the requester's principal to the global `apr0TotalPrincipal` (line ~576) whenever `unscaledApr == 0` at request time. Any KYC'd tranche holder can do this with 1 wei of tranche tokens via `IdleCDOEpochVariant.requestWithdraw`.
- `prepareStopEpochWithApr0` (called by the CDO inside `stopEpoch`) reverts `NotAllowed` at line ~506-508 when `apr0TotalPrincipal != 0 && unscaledApr != 0`. This check sits *before* the bucket is reset at line ~540 (`apr0TotalPrincipal = 0`).
- `_settleApr0` (lines ~545-565) moves the user's `principal` into `settledPrincipal` but never reduces `apr0TotalPrincipal`; `_claimFundedWithdrawRequest` clears the user entry but leaves the global bucket untouched. The only decrement is `_clearWithdrawClaimForEpoch` with `_isClearingApr0 = true`, reachable solely via the post-default claim path — i.e., only after the vault is already dead.
- Sequence: (1) vault runs an APR=0 epoch; attacker calls `requestWithdraw` for a dust amount → `apr0TotalPrincipal > 0`; (2) manager legitimately configures a non-zero APR for a subsequent epoch (a normal operation — the attacker just keeps a dust APR0 receipt alive); (3) every `stopEpoch`/`stopEpochWithDuration` from then on calls `prepareStopEpochWithApr0` and reverts, since the revert precedes the reset.
- Existing guards do not help: the `NotAllowed` check is the vulnerability itself; the attacker needs no privilege, no default, and the `lossRecoveryPriceByEpoch` early-revert in `requestWithdraw` does not apply to a fresh APR0 request.

### Impact Explanation
Permanent freezing of all vault funds. With `stopEpoch` permanently reverting, `epochNumber` never advances, `epochEndDate`-gated claims never mature, `pendingWithdraws` are never funded, and all deposited principal plus pending withdraw/instant receipts remain locked in the strategy/CDO. Quantified loss: the entire vault TVL plus all outstanding withdraw claims. This satisfies the "permanent freezing" impact class, not a mere gas/DoS issue.

### Likelihood Explanation
Medium. Requires an APR0-configured credit vault (the codebase explicitly supports this mode and the bucket only exists for it) and a subsequent honest-manager APR change or a single dust request placed during the last APR0 epoch before any APR-positive epoch. The attacker's cost is one dust-sized tranche position and one `requestWithdraw` call; no privileged cooperation is needed since APR reconfiguration between epochs is routine manager behavior.

### Recommendation
Decouple the bucket-lifecycle from the APR guard: either decrement `apr0TotalPrincipal` inside `_settleApr0` when an APR0 principal settles, or move the `unscaledApr != 0` revert so the bucket is still closed/reset (`apr0TotalPrincipal = 0`) rather than permanently latching. Alternatively, treat leftover `apr0TotalPrincipal` under a non-zero APR as a settle-at-zero-rate case instead of reverting, so an orphaned dust receipt cannot veto the epoch state machine.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCDOEpochQueue.t.sol`-style harness on an APR0 vault):

```solidity
// 1. Vault is in APR0 mode (unscaledApr == 0), epoch N running.
// 2. Attacker (KYC'd tranche holder) deposits dust and requests withdraw:
vm.prank(attacker);
cdoEpoch.requestWithdraw(1, address(AATranche));   // -> strategy.requestWithdraw -> _requestWithdrawApr0
assertGt(strategy.apr0TotalPrincipal(), 0);

// 3. Epoch N stops while APR is still 0: prepareStopEpochWithApr0 clears bucket.
//    Attacker instead times it so the request lands in the epoch where APR stays 0
//    but manager then configures APR > 0 for the next epoch before the bucket clears,
//    or re-requests each APR0 epoch to keep apr0TotalPrincipal non-zero.
vm.prank(manager);
cdoEpoch.setApr(10e18); // honest reconfiguration for next epoch

// 4. Every subsequent stopEpoch reverts forever:
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch();   // prepareStopEpochWithApr0: apr0TotalPrincipal != 0 && unscaledApr != 0
// Repeating after the attacker claims also reverts: claim never decrements apr0TotalPrincipal.
```

Note: exact feasibility of keeping `apr0TotalPrincipal` non-zero across the APR transition depends on how `IdleCDOEpochVariant.stopEpoch` orders the `setApr`/`prepareStopEpochWithApr0` calls — that call ordering in `IdleCDOEpochVariant.sol` was not fully verified within this pass and should be confirmed when writing the PoC (the attacker's ability to request a *new* APR0 withdraw in the buffer window before `unscaledApr` is updated is the key enabler).
