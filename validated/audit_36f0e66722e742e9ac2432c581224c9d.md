### Title
Global `PRIMARY KEY (signer_addr)` on `block_rejection_signer_addrs` lets a signer's rejection vote for one block silently clobber/collide with their rejection of any other block, deflating the on-disk rejection tally and wedging global-rejection finality - (File: `stacks-signer/src/signerdb.rs`)

### Summary
### Finding Description
`store_and_process_block_rejection` in `stacks-signer/src/v0/signer.rs` tallies rejection weight for a block by reading back every rejecting address from the `block_rejection_signer_addrs` table via `get_block_rejection_signer_addrs(block_hash)`, and compares the recovered weight against `min_weight` (70%/30% thresholds) before calling `mark_globally_rejected`: [1](#0-0) 

The persistence layer backing this tally is declared with the primary key scoped to `signer_addr` alone, not to `(signer_signature_hash, signer_addr)`: [2](#0-1) 

This is the exact shape of the vault bug: an identity-scoped counter (`req.totalRedemption` per owner in the report; here, "has this signer_addr rejected this block" per `signer_signature_hash`) is supposed to be keyed by *both* the actor and the object being voted on, but the schema only enforces uniqueness on the actor (`signer_addr`). Because a single signer legitimately rejects *different* block hashes over time (competing sibling proposals at the same height during a tenure fork, re-proposals, stale/timed-out blocks, etc. — all first-class, frequent flows per `docs/signer-flows.md` sections 3 and 7), the same `signer_addr` will need a row for more than one `signer_signature_hash`. With the PK scoped only to `signer_addr`, that is impossible: either the later insert for a second block silently overwrites/replaces the row recorded for the earlier block (losing that address's vote against the earlier block), or the later insert is rejected outright by the UNIQUE/PK constraint (permanently preventing that signer's rejection from ever being recorded again for *any subsequent* block, once they've rejected one block).

Either behavior breaks the aggregated-weight-vs-verified-votes equality that `store_and_process_block_rejection` depends on: `get_block_rejection_signer_addrs(block_hash)` can return fewer verified rejections than were actually cast and stored by `add_block_rejection_signer_addr`, so `total_reject_weight` computed from it under-represents the real rejecting weight for that block hash.

### Impact Explanation
This directly wedges the `mark_globally_rejected` path (`stacks-signer/src/v0/signer.rs:2335`) for any block whose rejecting signer set overlaps with signers who have (before or after) rejected a *different* block hash — a routine occurrence any time a miner produces sibling/competing proposals at a height, which `docs/signer-flows.md` describes as an expected, frequent flow (`signer_refuses_to_sign_second_sibling_tenure_start` and related tests in `stacks-signer/src/v0/tests.rs` confirm this scenario is exercised routinely). A rejected, non-canonical block can therefore be stuck indefinitely in `LocallyRejected` instead of transitioning to `GloballyRejected`, since the local weight tally never reliably reaches the >30% blocking-minority threshold once votes are lost/overwritten across block hashes. This is a liveness wedge on the signer's local block-finality bookkeeping: legitimate rejection consensus can never be locally recorded as reached for the affected block hash(es), even though the necessary rejecting weight was, in fact, broadcast and individually verified.

### Likelihood Explanation
Triggering this requires nothing more than a single miner (one-slot) proposing two or more competing/sibling blocks at the same height in the same tenure — an ordinary occurrence in the miner-proposal lifecycle already covered by existing sibling-block tests — causing honest signers to legitimately reject more than one distinct `signer_signature_hash` over time. No majority collusion, other signers' keys, or privileged access is needed; it is purely a consequence of the schema's under-scoped primary key colliding with the protocol's own normal branching/re-proposal behavior.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` (and the corresponding lookup/insert logic in `add_block_rejection_signer_addr` / `get_block_rejection_signer_addrs`) to the composite `(signer_signature_hash, signer_addr)`, mirroring how `block_signatures`/`block_pre_commits` are effectively scoped per block. This ensures a signer's rejection of one block can never overwrite or be blocked by their rejection of a different block, restoring the equality between verified rejections received and rejections counted toward the global-rejection threshold. A schema migration (as already done elsewhere in `signerdb.rs`, e.g. `MIGRATE_BLOCKS_DROP_SIGNED_OVER_ADD_APPROVED_TIME`) will be needed to correct existing databases.

### Proof of Concept
1. Miner proposes block `A` at height `h` in tenure `T`.
2. Signer `S` rejects `A` for a legitimate reason (e.g. `ReorgNotAllowed`); `add_block_rejection_signer_addr(A_hash, S, reason)` inserts a row `(A_hash, S)`.
3. Before 30%+ weight accumulates against `A`, the miner (or a fork) proposes a second block `B` at the same height `h` (a sibling), which is also invalid/conflicting from `S`'s perspective.
4. `S` rejects `B` as well; `add_block_rejection_signer_addr(B_hash, S, reason)` executes against a table whose primary key is `signer_addr` alone, so it either (a) overwrites `S`'s existing row from `(A_hash, S)` to `(B_hash, S)`, or (b) fails the insert entirely due to the PK constraint.
5. Any subsequent recomputation of `A`'s rejection tally via `get_block_rejection_signer_addrs(A_hash)` no longer includes `S`'s (previously verified and stored) rejection, permanently understating `total_reject_weight` for `A`.
6. If enough other signers behave the same way across sibling proposals at various heights, no single stale block ever accumulates enough recorded rejection weight to cross the >30% threshold, so `mark_globally_rejected` is never invoked for it, even though it was legitimately voted down by more than 30% of weight in aggregate — a liveness wedge on that block's finalization bookkeeping.

*(Note: I was unable to inspect the exact SQL body of `add_block_rejection_signer_addr`/`get_block_rejection_signer_addrs` in this session — only the table DDL — so I cannot definitively state whether the failure mode is silent overwrite or constraint-violation rejection; either is consistent with the schema shown and produces the described tally-deflation/liveness effect. A Devin session with full file access should verify the exact INSERT statement used before finalizing the fix.)*
