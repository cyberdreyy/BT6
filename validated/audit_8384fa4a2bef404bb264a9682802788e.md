### Title
View-role users can retrieve a bridge's plaintext `OutgoingToken` credential via `GET /v2/bridge_types/:BridgeName` - ([File: core/web/bridge_types_controller.go])

### Summary
The `Show` route for bridge types is registered with only generic authentication (any authenticated user) and no role gate, while `presenters.NewBridgeResource` unconditionally includes the bridge's plaintext `OutgoingToken` field in the JSON response. This lets any authenticated view-role user read a secret credential that is meant to be used only by the node to authenticate itself to the external adapter/bridge.

### Finding Description
The route is registered as: [1](#0-0) 
Unlike `Create`, `Update`, and `Destroy` on the same controller which are wrapped in `auth.RequiresEditRole(...)`, `GET /v2/bridge_types/:BridgeName` (`bt.Show`) is registered with no role wrapper at all — it only requires membership in the generic authenticated group (`authv2`), which is reachable by admin, edit, run, and view roles alike.

`BridgeTypesController.Show` fetches the bridge and serializes it directly via the presenter: [2](#0-1) 

`presenters.NewBridgeResource` copies `b.OutgoingToken` into the response struct, and the JSON tag for that field has no `omitempty`/redaction, unlike `IncomingToken` which is explicitly commented as "only provided when creating a Bridge": [3](#0-2) 

The underlying `BridgeType` model stores `OutgoingToken` in plaintext (only `IncomingTokenHash`/`Salt` are hashed, `IncomingToken` itself is never persisted post-creation): [4](#0-3) 

So while `IncomingToken` correctly never leaves the node after bridge creation, `OutgoingToken` — a secret the node presents to the external adapter — is returned in full on every subsequent `Show`, `Index`, `Update`, and `Destroy` response, and `Show`/`Index` are reachable by any authenticated role including the lowest-privileged "view" role, since neither has a `RequiresEditRole`/`RequiresAdminRole` wrapper.

### Impact Explanation
This is a credential/secret disclosure to a lower-privileged role: a "view" role user (who by design should only be able to read non-sensitive state) can retrieve the `OutgoingToken` used to authenticate the node to an external adapter/bridge. An attacker holding only a view-role API token or session can extract this token and use it to impersonate the Chainlink node when calling the bridge's URL (depending on how the adapter validates the outgoing token), or at minimum obtain a secret that was intended to be confined to edit/admin-privileged operators. This maps to the "sensitive data exposure to unauthorized user" / broken access-control class of the Chainlink bounty program.

### Likelihood Explanation
Trivial and fully reproducible: it requires only a valid, low-privileged ("view") authenticated session or API token for the node — no special conditions, race, or misconfiguration. Any bridge created on the node is affected immediately and repeatedly (every `Show`/`Index` call re-discloses the token).

### Recommendation
- Redact `OutgoingToken` from `BridgeResource` in `Show`/`Index`/`Update`/`Destroy` responses (e.g., mark it `omitempty` and don't populate it, or replace with a masked value), returning it in plaintext only from `Create`, consistent with how `IncomingToken` is already handled.
- Additionally, restrict `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` to `auth.RequiresEditRole` (or higher) in `core/web/router.go`, since bridge configuration (including URL and outgoing credential) is sensitive, matching the protection already given to `Create`/`Update`/`Destroy`.

### Proof of Concept
Go handler-level integration test (extends `core/web/bridge_types_controller_test.go`):
1. Use `cltest.NewApplication` and `cltest.MustCreateBridge` (or `app.BridgeORM().CreateBridgeType`) to create a bridge, capturing the `OutgoingToken` set on the `bridges.BridgeType` struct.
2. Create an HTTP client scoped to a view-only role (e.g., via `app.NewHTTPClient(&cltest.User{Role: "view"})` or equivalent test helper that issues a view-role session/API token).
3. Issue `client.Get("/v2/bridge_types/" + bt.Name.String())`.
4. Assert `resp.StatusCode == http.StatusOK` (showing no role check blocks the view user).
5. Parse the JSON-API response into `presenters.BridgeResource` and assert `resource.OutgoingToken == bt.OutgoingToken`, proving the secret is disclosed to a view-role caller.
6. Expected (fixed) behavior: either the request should be rejected with `403 Forbidden` for the view role, or `resource.OutgoingToken` should be empty/masked in the response.

```go
// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```
