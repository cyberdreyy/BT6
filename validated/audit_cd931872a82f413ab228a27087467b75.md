### Title
ETH sent along a withdrawal is forwarded to a throwaway `EthenaCooldownRequest` clone and locked — (File: contracts/IdleCDOEthenaVariant.sol)

### Summary
`IdleCDOEthenaVariant._withdraw` propagates `msg.value` into the per-request clone created via `ClonesWithImmutableArgs.clone(…, msg.value)`. The withdrawal path (`withdrawAA`/`withdrawBB` → `_withdraw`) does not need native ETH — USDe-denominated accounting burns tranche tokens and transfers sUSDe — so any ETH attached by the caller is forwarded to a freshly deployed, per-user cooldown contract and becomes unaccounted/locked, mirroring the DODO `externalSwap` `msg.value` bug class (native value silently accepted and stranded instead of being required to match an intended amount or rejected).

### Finding Description
In `IdleCDOEthenaVariant._withdraw`, after burning the user's tranche tokens and computing `SUSDeRedeemed`, the code creates a one-off `EthenaCooldownRequest` clone:

```solidity
// contracts/IdleCDOEthenaVariant.sol (lines 82-87)
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
  abi.encodePacked(address(this), msg.sender),
  msg.value
));
IERC20Detailed(strategyToken).safeTransfer(address(clone), SUSDeRedeemed);
```

There is no validation of `msg.value` anywhere in the withdraw path, and the clone receives whatever ETH the caller sent. The clone's immutable args are only `(cdo, user)` — the ETH is not part of its tracked state. The sUSDe cooldown/claim flow in `EthenaCooldownRequest` is denominated in sUSDe/USDe; nothing in the withdrawal accounting credits, refunds, or routes the ETH back to the user. The result: any ETH attached to `withdrawAA`/`withdrawBB` on this CDO variant is permanently locked in an ephemeral clone whose only intended role is to hold sUSDe during the Ethena cooldown and forward USDe to the user on claim.

The recommended fix in the source report (require `msg.value == 0` when the operation is not ETH-denominated) applies directly here: a USDe/sUSDe tranche withdrawal has no legitimate reason to carry native value.

### Impact Explanation
Users who attach ETH to a withdrawal transaction (wallet misconfiguration, aggregator sending `value` alongside a multicall, or a mistaken assumption that the cooldown request needs gas funding) permanently lose that ETH. The funds are locked in a clone with no ETH sweep path — a direct, permanent loss of user funds with no recovery mechanism, matching the medium-severity precedent. Loss is quantified per transaction as `msg.value` with no bound.

### Likelihood Explanation
Likelihood is moderate: the vulnerable path is user-inflicted rather than attacker-induced (an attacker cannot force a victim to send ETH), which is why the source report classed it Medium. However, the deploy-time `msg.value` forwarding is a strong signal the author intended payable withdrawals, and routers/aggregators composing calls on behalf of users commonly attach value. Every affected user loses 100% of attached ETH; the contract offers no rescue. Note: this requires `withdrawAA`/`withdrawBB` (or the CDO's `receive`/`fallback`) to accept value — the presence of `msg.value` in `clone(...)` indicates the variant was built for a payable call path; if the entry points were ever made non-payable the code becomes dead but harmless.

### Recommendation
Reject native value on the withdraw path:

```solidity
// in _withdraw (IdleCDOEthenaVariant.sol)
require(msg.value == 0, 'ETH not accepted');
```

Alternatively, if the clone genuinely needs ETH (e.g., to fund an operation), require an exact expected amount and refund the excess:

```solidity
require(msg.value == EXPECTED_FEE, 'bad msg.value');
```

and add a `sweep`/`rescue` function on `EthenaCooldownRequest` so only the `user` can recover any ETH balance after claiming.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEthenaVariant} from "../contracts/IdleCDOEthenaVariant.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract EthLockedOnWithdraw is Test {
    // mainnet fork against the deployed sUSDe CDO
    IdleCDOEthenaVariant cdo;
    IERC20Detailed aaTranche;
    IERC20Detailed susde;
    address user = makeAddr("user");

    function setUp() public {
        vm.createSelectFork(vm.envString("ETH_RPC_URL"));
        cdo = IdleCDOEthenaVariant(payable(<CDO_ADDRESS>));
        aaTranche = IERC20Detailed(cdo.AATranche());
        susde = IERC20Detailed(cdo.strategyToken());
        deal(address(aaTranche), user, 1000e18);
        vm.deal(user, 10 ether);
    }

    function test_ethLockedInCooldownClone() public {
        vm.startPrank(user);
        // user mistakenly attaches 1 ETH to the withdrawal
        cdo.withdrawAA{value: 1 ether}(1000e18);

        // the clone is deployed with msg.value as balance
        // grab the clone address from NewCooldownRequestContract event logs
        // then assert:
        //   address(clone).balance == 1 ether
        //   clone has no function to return ETH to `user`
        // => 1 ether permanently locked
        vm.stopPrank();
    }
}
```

Note on verification limits: I confirmed the `msg.value` propagation into the clone at `IdleCDOTrancheVariant.sol` lines 82–87 and that `receive()` guards elsewhere (e.g., `LidoCDOTrancheGateway.receive` restricted to WETH) prevent analogous stray-ETH locking in the gateway. I could not fully read `EthenaCooldownRequest.sol` or the `withdrawAA/withdrawBB` signatures to confirm the payable declaration and absence of an ETH rescue path before the iteration limit; if either already handles ETH recovery, the finding is void.
