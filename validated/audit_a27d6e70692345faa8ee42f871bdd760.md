### Title
Signer weight double-counted toward both `total_weight_approved` and `total_weight_rejected` due to mismatched dedup keys - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run` tallies each signer's vote weight exactly once per bucket by deduplicating on a per-message-kind key: the `Accepted` branch dedups on `block.gathered_signatures` (a `HashMap<slot_id, signature>`), while the `Rejected` branch dedups on the shared `block.responded_signers` set — which the `Accepted` branch *also* inserts into, but does not read from before adding weight. A signer who first rejects a block (crediting `total_weight_rejected` and populating `responded_signers`) and later sends an `Accepted` message for the *same* `signer_signature_hash` is **not** blocked by the accept path, because that path only checks `gathered_signatures`, which was never populated by the reject. The result is that the same signer's weight gets credited to both `total_weight_rejected` and `total_weight_approved` simultaneously for one block — the aggregated-weight invariant (each signer contributes its weight once, to at most one side) is broken.

### Finding Description
In the `Rejected` handling arm: [1](#0-0) 
weight is added to `total_weight_rejected` only `if block.responded_signers.insert(slot_id)` succeeds (i.e., first time this slot is seen).

In the `Accepted` handling arm, the dedup check uses a *different* set: [2](#0-1) 
`if !block.gathered_signatures.contains_key(&slot_id)` gates the `total_weight_approved` increment, and only *after* that increment does the code do `block.gathered_signatures.insert(slot_id, signature); block.responded_signers.insert(slot_id);`.

Because the reject path writes to `responded_signers` but the accept path's guard checks `gathered_signatures`, the two dedup domains are not the same set for the "already voted" question:
- Signer votes `Reject` first → `responded_signers` gains `slot_id`, `total_weight_rejected` += weight. `gathered_signatures` is untouched.
- Same signer later sends `Accepted` for the same block → the guard `!gathered_signatures.contains_key(&slot_id)` is still `true` (nothing was ever inserted there by the reject path), so `total_weight_approved` += weight is executed again for the *same* signer's weight.

The signer's weight is now counted in both `total_weight_approved` and `total_weight_rejected` for the same block, and `responded_signers`/`gathered_signatures` no longer agree on which signers have voted which way. This exactly mirrors the report's bug class: a piece of per-identity state (`lastProfit`/here, "has this signer already been credited") is tracked in a way that is not synchronized across the two code paths that mutate related but distinct maps, so the same underlying "credit" (token profit / signer weight) is granted twice through two different bookkeeping structures instead of once.

The threshold checks that read these values assume the invariant "each signer contributes weight to at most one bucket": [3](#0-2) [4](#0-3) 
Once the invariant is broken, `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, and a single signer's weight can simultaneously push the approval side toward the 70% threshold while its earlier rejection continues to count toward the 30% blocking-minority threshold.

### Impact Explanation
A single signer (no majority required) can, on its own, get its stake weight counted twice — once toward rejection, once toward approval — for the same block, by emitting a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash`. This inflates `total_weight_approved` beyond what genuinely-distinct accepting weight would produce, letting the coordinator believe the 70% approval threshold has been reached (and push/broadcast the block) using less real distinct endorsing weight than the protocol requires, while that signer's weight is still simultaneously recorded as blocking. This is the "aggregated-weight vs verified-accepts" equality break called out in scope — effectively a rejection's weight is silently recycled into an acceptance tally, which is functionally analogous to a "rejection recounted as an acceptance."

### Likelihood Explanation
Triggering this requires only a single signer to send two StackerDB messages (`Rejected` then `Accepted`) referencing the same block's `signer_signature_hash`, and nothing in `StackerDBListener::run` prevents a signer's own client from doing this (the "do not change votes on a rejected block unless re-proposed" convention lives only in the signer's local decision logic in `stacks-signer/src/v0/signer.rs`, not in the node-side listener that processes whatever arrives on StackerDB). A misbehaving or buggy signer implementation, or a deliberately byzantine one, can trigger it unilaterally with gossip alone — no other signer's key or majority control is needed.

### Recommendation
Use a single, unified per-slot "already voted" record (one map from `slot_id` to the vote kind actually counted) that both the `Accepted` and `Rejected` branches check and update, so a signer's weight can only ever be added to `total_weight_approved` XOR `total_weight_rejected`, never both. If a signer's vote changes, either ignore the later message or explicitly move the previously-tallied weight out of the old bucket before crediting the new one, rather than allowing an independent guard variable in the opposing branch.

### Proof of Concept
1. Node runs `StackerDBListener::run` for a proposed block with `signer_signature_hash = H`.
2. Signer S (weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `H`.
   - `block.responded_signers.insert(S_slot)` succeeds → `total_weight_rejected += w`.
3. Signer S later sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `H` (nothing on the node side prevents this).
   - Guard `!block.gathered_signatures.contains_key(&S_slot)` is `true` (never populated by step 2) → `total_weight_approved += w`.
4. Now `total_weight_approved` and `total_weight_rejected` both include `w` for the same signer S on block `H`, violating the invariant that a signer contributes its weight once; both thresholds in [3](#0-2) 
and [4](#0-3) 
can be reached using an inflated/duplicated weight contribution from a single signer.
