### Title
Unauthenticated Request-ID collision in `(*handler).HandleJSONRPCUserMessage` allows cross-subscriber Denial-of-Service - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`(*handler).HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 characters before inserting it into the shared `h.activeRequests` map keyed solely by the raw, attacker-supplied `req.ID` string, with no binding to sender identity or authentication check at that stage. Because the gateway (`gateway.go`'s `ProcessRequest`) forwards any client's request directly to this function without pre-associating the ID with the caller, any unprivileged client can race a legitimate subscriber by submitting a request with a colliding ID first, causing the victim's later, legitimate call to fail with "request ID already exists".

### Finding Description
`gateway.go`'s `ProcessRequest` decodes the raw JSON-RPC request (`jsonRequest.ID` is fully attacker-controlled) and immediately calls `h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)` for the relevant service handler [1](#0-0) , with no per-sender scoping of `req.ID`, and dispatches straight to the handler [2](#0-1) .

In `core/services/gateway/handlers/confidentialrelay/handler.go`, `HandleJSONRPCUserMessage` performs only the length/emptiness check on `req.ID` before calling `h.newActiveRequest`, and — unlike the `vault` handler — performs **no authentication/authorization check at all** prior to reserving the ID slot: [3](#0-2) .

`newActiveRequest` takes the global handler lock and rejects the request outright if `req.ID` is already present in `h.activeRequests`, returning "request ID already exists": [4](#0-3) .

This is confirmed as intentional single-slot behavior (not a bug in isolation) by the existing unit test `TestConfidentialRelayHandler_DuplicateRequestID`, which demonstrates exactly this collision/rejection mechanic using two different callbacks (simulating two different callers) sharing one ID: [5](#0-4) . The test's own structure — first caller succeeds, second caller with the same ID is rejected — is the exact DoS primitive: nothing in the code path checks whether the second caller is the "rightful" owner of that ID pattern; the map is a flat namespace shared by all callers of the DON/service.

The `vault` handler mitigates this specific risk by requiring `h.requestProcessor.ProcessRequest` (identity/signature-based authorization) to succeed *before* calling `newActiveRequest`, and additionally namespaces certain request IDs with `authorizedOwner + vaulttypes.RequestIDSeparator + requestID` [6](#0-5) , and its own duplicate-ID test error message differs ("request was already authorized previously") [7](#0-6) , suggesting the ID collision is checked against the *authorized* request in that handler. The `confidentialrelay` handler has no equivalent authorization gate or ID namespacing before `newActiveRequest`, so any caller — including one without valid credentials for the workflow/method in question — can occupy an ID slot that a legitimate subscriber is expected to use next, given that `req.ID` values elsewhere in the gateway follow predictable conventions (e.g., `<method>/<workflowID>/<uuid>`-style patterns as seen in `http_trigger_handler.go`'s `setupCallback` in-flight ID checks) [8](#0-7) .

### Impact Explanation
An unauthenticated/unprivileged attacker can perform a targeted Denial-of-Service against a specific subscriber's confidential-relay request by pre-empting a predictable or guessable `req.ID` before the legitimate request arrives, causing the legitimate request to be rejected with "request ID already exists" and never reach the DON. This blocks a specific victim's capability execution / secrets-get flow without requiring any credentials, matching a "Denial of Service" impact class against gateway request availability rather than fund loss or key disclosure.

### Likelihood Explanation
Exploitability requires only: (1) knowledge/predictability of the ID scheme the victim will use (feasible if IDs are constructed from public data such as workflow IDs or deterministic UUID generation, or if the attacker can observe/replay IDs from other channels), and (2) a race to submit before the victim, since the map only rejects a second use of an already-*active* ID and the winner is whoever submits first — no signature or role check gates this reservation. This is a straightforward, repeatable pre-emption; the existing `TestConfidentialRelayHandler_DuplicateRequestID` test already proves the mechanic works cleanly with two independent callers.

### Recommendation
Namespace `activeRequests` keys by an identity/session-bound value (e.g., verified sender/owner derived from `req.Auth`/signature) in addition to `req.ID`, similar to the vault handler's owner-prefixed request IDs, and/or require successful authentication/authorization before the ID reservation (`newActiveRequest`) is performed in the confidentialrelay handler, so an unauthenticated party cannot occupy or collide with another subscriber's request slot.

### Proof of Concept
1. In `core/services/gateway/handlers/confidentialrelay/handler_test.go`, extend `TestConfidentialRelayHandler_DuplicateRequestID`:
   - Simulate an "attacker" callback (`cbAttacker`) constructing a `req.ID` matching a known/predictable convention for a target workflow (e.g., `"exec/wf1/<uuid>"`).
   - Call `h.HandleJSONRPCUserMessage(ctx, attackerReq, cbAttacker)` first; assert `require.NoError`.
   - Have the "victim" call `h.HandleJSONRPCUserMessage(ctx, victimReq, cbVictim)` with the identical `ID` (simulating the predicted convention) and identical/target workflow; assert `require.ErrorContains(err, "request ID already exists")`.
   - Assert that `h.getActiveRequest(id)` still points to the attacker's `activeRequest` (i.e., the attacker's callback, not the victim's, will eventually receive/consume the DON's responses), demonstrating cross-subscriber denial and response misdirection risk.
2. Confirm no authorization step differentiates the two callers prior to `newActiveRequest`, by asserting the attacker's call succeeds without supplying any `req.Auth`/signature field.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	t.Parallel()
	h, cb, don, _ := setupHandler(t, 4)
	don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-dup",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
