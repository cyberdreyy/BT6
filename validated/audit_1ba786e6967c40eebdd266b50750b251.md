### Title
Group rate-limiter check-then-settle design allows unbounded outflow beyond configured caps via concurrent/rapid withdrawals before off-chain aggregation lands - ([File: programs/marginfi/src/utils/general.rs])

### Summary
The report's bug class is a check-then-act race: an action reads a shared "capacity/status" value, validates against it, and performs an irreversible transfer, while the authoritative state update that should have gated the second concurrent action happens later and out-of-band. Marginfi's group-level rate limiter is architected with exactly this pattern: the group outflow/inflow counters are validated read-only inside `record_withdrawal_outflow` during user withdraw/borrow instructions, but the actual counter mutation only happens later, out-of-band, when `delegate_flow_admin` calls `update_group_rate_limiter` with events aggregated off-chain.

### Finding Description
`record_withdrawal_outflow` in [1](#0-0)  performs the group-level cap check by calling `effective_remaining_capacity` against the group's *last admin-settled* counters, and only *emits* a `RateLimitFlowEvent` — it never mutates `group.rate_limiter` itself. The bank-level limiter is updated inline (synchronously, on the writable bank account), but the group-level limiter deliberately is not, as documented: "Group-level rate limiting is checked read-only during user actions, then settled later from aggregated events" [2](#0-1) .

The actual counter update only occurs when `delegate_flow_admin` submits a batched, sequence-numbered update via `update_group_rate_limiter` [3](#0-2) . Between the time capacity is "checked" (against stale, already-settled counters) and the time the admin's batch actually lands and consumes that capacity, every concurrent or rapid user withdraw/borrow observes the same stale `remaining` value and is permitted to proceed — mirroring the promo handler's "read pending → enqueue" TOCTOU, where multiple actors independently pass a check against data that has not yet been atomically reserved. The project's own test suite explicitly demonstrates and asserts this non-atomicity ("group rate limiter is read-only during user instructions" — the group counter does not change across multiple successive borrows until the admin update lands) [4](#0-3)  and [5](#0-4) . The same deliberate check-then-settle pattern is repeated for the deleverage withdrawal daily cap via `check_deleverage_withdraw_limit` inside `record_withdrawal_outflow`-style call sites (e.g. JupLend withdraw) [6](#0-5)  and its admin settlement counterpart `update_deleverage_withdrawals` [7](#0-6) .

Consequently, any number of ordinary, unprivileged withdraw/borrow instructions (`lending_account_withdraw`, `lending_account_borrow`, and the Kamino/Drift/Solend/JupLend withdraw variants) submitted before the off-chain worker's next aggregation cycle can each independently pass the group-level (or deleverage) capacity check against the same un-decremented "remaining capacity" figure, letting the aggregate outflow blow through the admin-configured hourly/daily USD cap — the exact risk control this mechanism exists to enforce is bypassable by the very actors it is meant to constrain, purely through timing, with no authorization bypass needed.

### Impact Explanation
This is a **defense-in-depth risk control**, not a fund-safety invariant enforced elsewhere (each individual withdraw/borrow still separately passes the normal health-engine and bank-level rate-limit checks). Its purpose per the guide is explicitly to be "a defense if the risk workflow is abused or compromised" (for the deleverage cap) and a general USD-denominated netflow limiter for the group. If bypassed by racing withdrawals within the settlement window, the practical effect is that the group can experience outflow well beyond the admin-configured limit within an hour/day — a durable, unrecoverable inconsistency between intended policy and actual on-chain outflow, with financial/risk-management effect (the whole point of the limiter — capping large USD-denominated drains — is defeated during exactly the period it's meant to matter, e.g. a black-swan/market-stress event with many withdrawals in quick succession).

### Likelihood Explanation
Medium. Exploitation requires only ordinary, permissionless withdraw/borrow calls, no special privileges or account state. The window of opportunity is bounded by the off-chain worker's aggregation cadence and the on-chain staleness bound (`MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` / `MAX_DELEVERAGE_WITHDRAW_LIMIT_UPDATE_LAG_SLOTS` = 1,500 slots, ~10 minutes) [8](#0-7) [9](#0-8) , so a user (or coordinated set of users) that submits many withdraws/borrows within that ~10 minute window, or precisely at moments right after an admin update but before the next one lands, can systematically exceed the intended cap. This is a documented, intentional design trade-off (to avoid making the group account writable on every user tx) rather than an oversight, which somewhat reduces "surprise" but does not change that the on-chain enforcement is genuinely non-atomic and race-able by unprivileged users.

### Recommendation
- If the group/deleverage rate limiter is meant to be a hard on-chain cap (not just an indexing/monitoring aid), it must not be purely read-only during the settlement gap: either make the group account mutable in the outflow path (accepting the extra write-lock contention) or introduce a bounded "provisional reservation" counter on a separate writable account that is atomically decremented at check time and reconciled by the admin batch, so concurrent user actions cannot all read the same unconsumed capacity.
- At minimum, tighten `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` / `MAX_DELEVERAGE_WITHDRAW_LIMIT_UPDATE_LAG_SLOTS` and require more frequent admin settlement, shrinking (but not eliminating) the exploitable race window.
- Document explicitly (if not already fully clear to integrators) that the group/deleverage rate limiter is a soft, eventually-consistent guard rather than a hard real-time cap, so downstream risk assumptions aren't miscalibrated — since based on the available documentation and tests this already appears to be an acknowledged design trade-off rather than an unknown defect.

### Proof of Concept
1. Admin configures `groupHourly` (or the deleverage daily cap) to a small limit, e.g. $10, via `configure_group_rate_limits` — as reproduced in the existing test setup [4](#0-3) .
2. Multiple unprivileged users (or a single user across several transactions/slots) each submit `lending_account_borrow` (or withdraw) for amounts individually under the limit, e.g. 4 separate borrows of $8 each ($32 total), all within the ~10 minute / 1,500-slot settlement window and before `delegate_flow_admin` calls `update_group_rate_limiter`.
3. Because `record_withdrawal_outflow` only compares each new instruction's projected value against `group.rate_limiter.hourly.effective_remaining_capacity` — which is not mutated by any of the preceding calls in the same window — every one of these borrows independently passes the check, exactly as shown by the existing test asserting the group counter is unchanged across multiple successive borrows/repays until an explicit admin update [5](#0-4) .
4. Aggregate group outflow of $32 has now occurred against a configured $10 hourly cap, before the admin's next `update_group_rate_limiter` call can retroactively record and enforce the breach (which, being after the fact, cannot claw back already-transferred funds).

/// Records withdrawal outflow on bank-level rate limiter and validates against
/// group-level rate limits (read-only). Emits a `RateLimitFlowEvent` for the
/// delegate flow admin to aggregate off-chain and update the group
/// rate limiter via
/// `update_group_rate_limiter`.
pub fn record_withdrawal_outflow(
    group_rate_limit_enabled: bool,
    native_amount: u64,
    balance_amount: u64,
    price: I80F48,
    bank: &mut Bank,
    group: &MarginfiGroup,
    group_key: Pubkey,
    bank_key: Pubkey,
    marginfi_account: &MarginfiAccount,
    clock: &Clock,
) -> MarginfiResult<()> {
    // Rate limiting tracks net outflow; skip for flashloan/liquidation/deleverage flows.
    if !should_skip_rate_limit(marginfi_account.account_flags) {
        if bank.rate_limiter.is_enabled() {
            bank.rate_limiter
                .try_record_outflow(native_amount, clock.unix_timestamp)?;
        }

        // Group-level rate limiting: read-only validation + event emission.
        // The admin aggregates events off-chain and calls update_group_rate_limiter.
        if group_rate_limit_enabled {
            check!(price > I80F48::ZERO, MarginfiError::InvalidRateLimitPrice);

            let value = calc_value(
                I80F48::from_num(balance_amount),
                price,
                bank.get_balance_decimals(),
                None,
            )?;
            if group.rate_limiter.hourly.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .hourly
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupHourlyRateLimitExceeded.into());
                }
            }
            if group.rate_limiter.daily.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .daily
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupDailyRateLimitExceeded.into());
                }
            }

            emit!(RateLimitFlowEvent {
                group: group_key,
                bank: bank_key,
                mint: bank.mint,
                flow_direction: 0, // outflow
                native_amount,
                mint_decimals: bank.mint_decimals,
                current_timestamp: clock.unix_timestamp,
            });
        }
    }
    Ok(())

## Why These Flows Exist

Both systems avoid making the group account writable in every user transaction.

- Bank-level rate limiting is updated inline because the bank account is already writable.
- Group-level rate limiting is checked read-only during user actions, then settled later from
  aggregated events.
- Deleverage withdraw limits are also checked read-only during the withdraw, then settled later from
  aggregated events.

This avoids serializing all activity in a group through one writable group account.

pub fn update_group_rate_limiter(
    ctx: Context<UpdateGroupRateLimiter>,
    outflow_usd: Option<u64>,
    inflow_usd: Option<u64>,
    update_seq: u64,
    event_start_slot: u64,
    event_end_slot: u64,
) -> MarginfiResult {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let clock = Clock::get()?;

    check!(
        outflow_usd.is_some() || inflow_usd.is_some(),
        MarginfiError::GroupRateLimiterUpdateEmpty
    );
    validate_event_slots(
        event_start_slot,
        event_end_slot,
        group.rate_limiter_last_admin_update_slot,
    )?;
    check!(
        event_end_slot <= clock.slot,
        MarginfiError::GroupRateLimiterUpdateFutureSlot
    );
    check!(
        clock.slot.saturating_sub(event_end_slot) <= MAX_RATE_LIMIT_UPDATE_LAG_SLOTS,
        MarginfiError::GroupRateLimiterUpdateStale
    );
    check!(
        update_seq == group.rate_limiter_last_admin_update_seq.saturating_add(1),
        MarginfiError::GroupRateLimiterUpdateOutOfOrderSeq
    );

    if let Some(inflow) = inflow_usd {
        check!(
            is_valid_rate_limit_amount(inflow),
            MarginfiError::InvalidConfig
        );
        group
            .rate_limiter
            .record_inflow(inflow, clock.unix_timestamp);
        msg!("Group rate limiter inflow recorded: {} USD", inflow);
    }

    if let Some(outflow) = outflow_usd {
        group
            .rate_limiter
            .try_record_outflow(outflow, clock.unix_timestamp)?;
        msg!("Group rate limiter outflow recorded: {} USD", outflow);
    }

    group.rate_limiter_last_admin_update_slot = event_end_slot;
    group.rate_limiter_last_admin_update_seq = update_seq;

    Ok(())
}

  it("(admin) batched event aggregation - multiple actions then single admin update", async () => {
    // Simulates production flow: multiple user actions happen over a period,
    // admin aggregates all emitted events and calls updateGroupRateLimiter once.
    await setRateLimits({
      bankHourly: usdcNative(1_000),
      bankDaily: new BN(0),
      groupHourly: new BN(10),
      groupDaily: new BN(0),
    });

    const allEvents: RateLimitFlowEvent[] = [];

    // Action 1: Borrow 3 USDC
    const events1 = await borrowUsdcWithEvents(usdcNative(3));
    allEvents.push(...events1);

    // Action 2: Borrow 2 USDC
    const events2 = await borrowUsdcWithEvents(usdcNative(2));
    allEvents.push(...events2);

    // Action 3: Repay 1 USDC
    const events3 = await repayUsdcWithEvents(usdcNative(1));
    allEvents.push(...events3);

    // Action 4: Borrow 1 USDC
    const events4 = await borrowUsdcWithEvents(usdcNative(1));
    allEvents.push(...events4);

    // Verify all events were captured
    assert.equal(allEvents.length, 4, "Should have 4 events total");

    // Admin aggregates all events at once (as would happen in production every ~10 minutes)
    const { totalOutflowUsd, totalInflowUsd } = aggregateFlowEvents(allEvents);
    assert.equal(totalOutflowUsd, 6, "3 + 2 + 1 = 6 USDC outflow");
    assert.equal(totalInflowUsd, 1, "1 USDC inflow");

    // Group state should still be unchanged (read-only during user instructions)
    const groupBeforeAdmin = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    assertBNEqual(groupBeforeAdmin.rateLimiter.hourly.curWindowOutflow, 0);

    // Admin submits both outflow and inflow in a single update
    await adminUpdateGroupRateLimiter({
      outflowUsd: new BN(totalOutflowUsd),
      inflowUsd: new BN(totalInflowUsd),
    });

    // Net outflow = 6 - 1 = 5
    const groupAfterAdmin = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    assertBNEqual(groupAfterAdmin.rateLimiter.hourly.curWindowOutflow, 5);

    // Borrow 2 more USDC and capture events for a second batch
    const events5 = await borrowUsdcWithEvents(usdcNative(2));
    const batch2 = aggregateFlowEvents(events5);
    assert.equal(batch2.totalOutflowUsd, 2);

    // Admin does second batch update
    await adminUpdateGroupRateLimiter({
      outflowUsd: new BN(batch2.totalOutflowUsd),
    });

    const groupAfterBatch2 = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    // 5 (previous) + 2 (new) = 7
    assertBNEqual(groupAfterBatch2.rateLimiter.hourly.curWindowOutflow, 7);

    // Borrow 4 more - should fail the read-only group capacity check (7 + 4 = 11 > 10)
    await expectFailedTxWithError(
      async () => {
        await borrowUsdc(usdcNative(4));
      },
      "GroupHourlyRateLimitExceeded",
      6117,
    );

pub fn update_deleverage_withdrawals(
    ctx: Context<UpdateDeleverageWithdrawals>,
    outflow_usd: u32,
    update_seq: u64,
    event_start_slot: u64,
    event_end_slot: u64,
) -> MarginfiResult {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let clock = Clock::get()?;

    check!(
        outflow_usd > 0,
        MarginfiError::DeleverageWithdrawalUpdateEmpty
    );
    validate_event_slots(
        event_start_slot,
        event_end_slot,
        group.deleverage_withdraw_last_admin_update_slot,
    )?;
    check!(
        event_end_slot <= clock.slot,
        MarginfiError::DeleverageWithdrawalUpdateFutureSlot
    );
    check!(
        clock.slot.saturating_sub(event_end_slot) <= MAX_DELEVERAGE_WITHDRAW_LIMIT_UPDATE_LAG_SLOTS,
        MarginfiError::DeleverageWithdrawalUpdateStale
    );
    check!(
        update_seq
            == group
                .deleverage_withdraw_last_admin_update_seq
                .saturating_add(1),
        MarginfiError::DeleverageWithdrawalUpdateOutOfOrderSeq
    );

    group.update_withdrawn_equity(I80F48::from_num(outflow_usd), clock.unix_timestamp)?;
    msg!(
        "Deleverage withdrawal outflow recorded: {} USD",
        outflow_usd
    );

    group.deleverage_withdraw_last_admin_update_slot = event_end_slot;
    group.deleverage_withdraw_last_admin_update_seq = update_seq;

    Ok(())
}
