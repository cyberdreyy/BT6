### Title
`LockupFactory::create` deploys a lockup at a deterministic address chosen only by `owner_account_id`, letting any unprivileged caller pick `lockup_duration`/`lockup_timestamp` for a victim - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` computes the lockup contract's account id solely from `sha256(owner_account_id)` and immediately deploys the contract with attacker-supplied `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`, with no assertion that `env::predecessor_account_id() == owner_account_id` (or the foundation). Because NEAR account creation is a one-shot operation, whoever calls `create` first for a given `owner_account_id` permanently fixes the schedule at that address.

### Finding Description
The claimed binding is: `LockupInformation.lockup_duration == value chosen by owner_account_id` and `LockupInformation.lockup_timestamp == value chosen by owner_account_id`. In the actual code: [1](#0-0) 

`lockup_account_id` is derived deterministically from `owner_account_id` alone via `sha256`, and the function accepts `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, and `release_duration` as caller-supplied parameters with no check that `env::predecessor_account_id()` matches `owner_account_id` or `self.foundation_account_id`: [2](#0-1) 

Any unprivileged account can call `create(owner_account_id = victim, lockup_duration = 63036000000000000, lockup_timestamp = Some(far_future_ts), vesting_schedule = None, release_duration = None, whitelist_account_id = None)` while attaching `MIN_ATTACHED_BALANCE`. This deploys and initializes the lockup contract at `sha256(victim)[..20].<factory>` with the attacker's chosen `lockup_duration`/`lockup_timestamp` written into `LockupArgs`, which becomes `LockupInformation` on `new`. Since the account name is a pure function of `owner_account_id`, this occupies the exact address the foundation/victim would later use; any subsequent legitimate `create` call for the same `owner_account_id` fails at `create_account` (account already exists), gets rolled back in `on_lockup_create`, and cannot overwrite the already-deployed contract. There is no `assert_owner`, `assert_called_by_foundation`, or equivalent guard in `create` to prevent this - only `assert_self()` guards the callback, which is irrelevant here.

### Impact Explanation
This is exactly the Critical category "a lockup deployed with parameters its rightful creator never chose." An attacker permanently locks a victim's future lockup contract address into a schedule (e.g., unfavorably long duration/far-future unlock timestamp) that the victim/foundation never authorized. Any NEAR tokens later sent to that deterministic address (e.g., by the foundation funding the real vesting) become subject to the attacker's chosen unlock terms instead of the intended ones. The attack is repeatable against any `owner_account_id` the attacker chooses to target, at the cost of one `MIN_ATTACHED_BALANCE` (3.5 NEAR) deposit per target account.

### Likelihood Explanation
The precondition is only that the attacker knows/predicts a target `owner_account_id` before the foundation calls `create` for it, and can afford `MIN_ATTACHED_BALANCE` (3.5 NEAR) — no special privilege, key, or role is required. Since lockup creation for a given owner account name is a one-time, race-to-create event, and `create` is a fully public method, this is straightforward to execute by any account holder.

### Recommendation
Add an authorization check in `create`, e.g. `assert!(env::predecessor_account_id() == owner_account_id.as_ref().to_string() || env::predecessor_account_id() == self.foundation_account_id, "Only the owner or the foundation can create a lockup for this account");` before building `LockupArgs`, ensuring the schedule parameters can only be set by the account entitled to choose them.

#[test]
fn test_attacker_frontrun_sets_victim_schedule() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const MALICIOUS_DURATION: u64 = 63036000000000000; // 24mo, attacker's choice
    let malicious_duration: WrappedTimestamp = MALICIOUS_DURATION.into();
    let far_future_ts: WrappedTimestamp = 4_102_444_800_000_000_000u64.into(); // year 2100

    // Attacker (not the victim, not the foundation) calls create for victim's account.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker"); // != account_tokens_owner()
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());

    let promise = contract.create(
        account_tokens_owner(), // owner_account_id = victim
        malicious_duration,
        Some(far_future_ts),
        None,
        None,
        None,
    );

    // Assert: the LockupArgs serialized into the deploy call reflect the
    // attacker-chosen duration/timestamp, for an owner_account_id that never
    // authorized them (predecessor != owner_account_id, no owner/foundation check fired).
    // In a full near-workspaces/near-sdk-sim test, decode the function_call
    // action's args and assert lockup_duration == MALICIOUS_DURATION and
    // lockup_timestamp == far_future_ts, then show a subsequent create() call
    // by account_tokens_owner() (the real owner) or the foundation for the
    // same owner_account_id fails because the deterministic account already exists.
}
