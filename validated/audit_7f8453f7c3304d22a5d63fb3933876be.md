### Title
Post-default withdraw requests drain the isolated default recovery reserve, freezing or stealing funds owed to defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to a directory-traversal flaw (attacker-controlled input reaching outside its intended namespace), `_claimPostDefaultWithdrawRequest` lets a receipt created *after* default finalization pay out from `defaultRecoveryReserve` — a pool that was sized at finalization only to cover the already-crystallized claim basis. Each post-default payout consumes reserve that was never allocated to it, so earlier claimants can extract more than their pro-rata recovery and later legitimate claimants' claims revert on underflow.

### Finding Description
`finalizeDefaultRecovery` computes `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` covers only pre-default active and pending claims [1](#0-0) . The reserve is therefore exactly enough to pay every finalized claim at `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`.

After finalization, `requestWithdraw` takes the post-default path: it burns the CDO's strategy tokens, mints a receipt to `_user`, and records `postDefaultRequests[_user] = _amount` [2](#0-1) . On claim, `_claimPostDefaultWithdrawRequest` pays this amount 1:1 by calling `_transferDefaultRecovery`, which unconditionally decrements `defaultRecoveryReserve` [3](#0-2) [4](#0-3) .

Because post-default requests were never part of `totalBasis` at finalization, no recovery budget was reserved for them. Every post-default payout is an unallocated draw on a reserve that is exactly funded for pre-default claims. Once post-default draws plus earlier finalized claims exhaust the reserve, `_transferDefaultRecovery` reverts via arithmetic underflow on `defaultRecoveryReserve -= _amount` for any remaining claimant — permanently freezing their recovery, since nothing replenishes the reserve post-finalization.

The traversal-shaped flaw: the `defaultRecoveryFinalized` branch in `claimWithdrawRequest` tries post-default first, letting a *new* attacker-supplied receipt reach into a payout namespace (`defaultRecoveryReserve`) reserved for a disjoint set of claims [5](#0-4) .

### Impact Explanation
Any tranche-token holder can, immediately after `finalizeDefaultRecovery`, call `requestWithdraw` and then `claimWithdrawRequest`, pulling underlying out of the recovery reserve at 1:1 for their (already haircut) receipt. Because the reserve is exactly sized, each such payout converts directly into a shortfall for defaulted-epoch or active-Basis claimants: either direct theft of their pro-rata recovery, or a permanent freeze when `defaultRecoveryReserve -= _amount` underflows. Loss is bounded by the attacker's post-default receipt size but scales with repeated/new post-default requests until the reserve is drained.

### Likelihood Explanation
Requirements: a borrower default followed by `finalizeDefaultRecovery` with `recoveryPrice < RECOVERY_FULL`, and a user who still holds tranche tokens (any unprivileged KYC'd tranche holder qualifies; the CDO's `requestWithdraw` is permissionless for holders). The attacker merely front-runs other claimants — no privileged action is needed. The ordering guarantee (post-default claims are attempted first in `claimWithdrawRequest`) makes the drain deterministic once any post-default receipt exists. Caveat I could not fully verify within this pass: whether the CDO-side mint/burn at the post-default `virtualPrice` was intended to offset the reserve draw economically — even if the *amount* is "fair," the *funding source* remains the non-replenished reserve, so the insolvency argument holds regardless of the haircut applied at request time.

### Recommendation
Fund post-default withdrawals from a source other than `defaultRecoveryReserve` — e.g., require new borrower funding collected via a dedicated counter (similar to `collectWithdrawFunds`) before `postDefaultRequests` become claimable, or route the payout through `_transferFundedClaim` (which already guards `balance - reserve < _amount`) so post-default claims can never spend the segregated recovery pool [6](#0-5) . Alternatively, account for anticipated post-default claims inside `totalBasis`/`reserveAmount` at finalization.

### Proof of Concept
Foundry fork outline (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

1. Deploy/attach `IdleCDOEpochVariant` + `IdleCreditVault`; users A (victim) and B (attacker) deposit AA; `startEpoch()`.
2. A calls `cdoEpoch.requestWithdraw(...)`, creating a pending receipt included in `pendingWithdraws`.
3. Warp past `epochEndDate`; `stopEpoch` with borrower underfunding → `defaulted()`. Finalize via `finalizeDefaultRecovery(R, source)` with `R < totalBasis` (recoveryPrice < 1).
4. B (still holding tranches) calls `cdoEpoch.requestWithdraw(amt, tranche)` → post-default branch mints B a receipt.
5. B calls `cdoEpoch.claimWithdrawRequest()` → `_claimPostDefaultWithdrawRequest` → `_transferDefaultRecovery` pays B 1:1 from the reserve.
6. A calls `cdoEpoch.claimWithdrawRequest()` → `_claimDefaultedWithdrawRequest` → `_transferDefaultRecovery` reverts (underflow) or pays less than `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`. Assert the shortfall equals B's payout.

State asserted: `strategy.defaultRecoveryReserve()` decreased by B's payout while A's finalized entitlement is unpaid — broken invariant is "one receipt, one (funded) payout" / isolation of the recovery reserve.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
