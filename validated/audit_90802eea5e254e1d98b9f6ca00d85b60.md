Based on my research, I found a genuine analog: the `UpdateCommissionCollector` instruction (SIMD-0232) in the vote program allows a vote account's authorized withdrawer to redirect where commission rewards are deposited, and the runtime's epoch-reward distribution path explicitly documents and tests scenarios where previously-earned/pending commission lamports tied to the old collector configuration get burned rather than delivered to the intended recipient — this is functionally the same bug class as `setTokenRewards`: changing a "payout address" field with no mechanism to safely flush/protect value already associated with the old configuration.

### Title
Vote account commission-collector reassignment permanently burns already-accrued commission rewards - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`UpdateCommissionCollector` lets a vote account's authorized withdrawer repoint `inflation_rewards_collector` (or `block_revenue_collector`) to a new address at any time, including mid-epoch, without any check on rewards that are already calculated/pending for the old collector configuration. The reward-commission accounting logic in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` explicitly handles — and burns — lamports in exactly the scenario the external report describes: an address change happens between reward calculation and distribution, and the funds tied to the old configuration are irrecoverably destroyed instead of delivered to any party.

### Finding Description
The vote program instruction handler for `UpdateCommissionCollector` calls `update_commission_collector`, which only validates the new collector and the authorized-withdrawer signature before overwriting the collector field — it performs no settlement of rewards accrued under the previous collector: [1](#0-0) 

Separately, and more concretely, the runtime's partitioned epoch-rewards distribution code computes commission payouts per collector address based on state captured at calculation time, then re-loads and validates the collector account at actual distribution time. The `accumulate_lamports` helper documents precisely the loss scenario: a vote account sets its inflation collector to a valid system account, and if that address later becomes an initialized vote account (or otherwise becomes invalid/reassigned) before distribution executes, the accrued commission lamports for the original collector configuration are burned rather than paid to anyone: [2](#0-1) 

The actual burn path is implemented in `load_and_reward_commission_accounts`, which re-validates the collector at distribution time via `collector_type_checked` and, on any failure (invalid owner, not rent-exempt, reserved account, or the address having since become a vote account with a mismatched role), adds the entire `commission_lamports` amount to `burned_lamports` instead of crediting any account: [3](#0-2) 

This is unit-tested and effectively acknowledged as expected behavior rather than prevented: [4](#0-3)  and [5](#0-4) 

### Impact Explanation
Commission lamports that would otherwise be paid to a validator operator (or the party they designated) are permanently burned with no path to recovery, mirroring the `setTokenRewards` bug class where changing a payout-destination field orphans funds already earmarked for payout. Because the reassignment (`UpdateCommissionCollector`) is a single ordinary signed transaction requiring only the authorized withdrawer's signature, and reward calculation vs. distribution happens over multiple blocks/slots within the runtime (`distribute_reward_commissions` / `load_and_reward_commission_accounts`), there is a window in which an operator's own commission — or, in the adversarial construction the code comments describe, another party's future collector configuration — can silently lose funds to the burn path with no compensating credit to the vote account, the withdrawer, or the incinerator's accounted total in a way that benefits any party.

### Likelihood Explanation
This requires no special privilege beyond being the authorized withdrawer of a vote account (a role any validator operator legitimately holds), and the SIMD-0232 collector-reassignment feature is a normal, unprivileged instruction path. The burn condition is explicitly anticipated and tested by the Agave developers themselves, indicating the scenario is reachable in production under ordinary reward-cycle timing (i.e., changing collector configuration between epoch-reward calculation and the multi-block partitioned distribution phase).

### Recommendation
Before or during `UpdateCommissionCollector`, the vote program (or the runtime commission-distribution path) should either (a) refuse to change the collector while there are pending/in-flight calculated-but-undistributed commission amounts still keyed to the old collector, or (b) settle/flush any already-calculated commission to the old collector configuration prior to accepting the new one, analogous to returning the old reward token before setting a new one in the reported bug. At minimum, the burn-on-reassignment behavior should be clearly flagged as a known, accepted design tradeoff (per SIMD-0232) rather than silently discovered by operators losing commission.

### Proof of Concept
1. Create a vote account with delegated stake and commission > 0.
2. During epoch N, set `inflation_rewards_collector` to system account `B` (a currently valid, rent-exempt, system-owned account) via `UpdateCommissionCollector`.
3. Allow reward calculation for epoch N to occur, capturing collector `B` as the destination for the accrued commission.
4. Before the partitioned distribution phase executes for that reward, initialize account `B` as a new vote account (or otherwise invalidate it, e.g. change owner) — this is achievable by any user via ordinary `CreateAccount`/`InitializeAccount` instructions targeting `B`, since `B` was just an arbitrary system account.
5. Observe, as demonstrated in `test_invalid_inflation_rewards_collector_burns_sysvar_rewards` and `test_inflation_collector_becomes_vote_account_burns_rewards`, that `load_and_reward_commission_accounts` fails `collector_type_checked` for `B` and adds the full `commission_lamports` to `burned_lamports`, permanently destroying the original vote account's earned commission for that epoch. [4](#0-3)

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

///
/// * a vote account A sets the inflation collector to valid system account B
/// * at some point in the future, that system account B gets allocated and
///   initialized as a vote account B
/// * vote account B sets itself as the inflation reward collector
///
/// In that situation, the rewards for vote account A will get burned, but the
/// rewards for vote account B will not. According to the rules of SIMD-0232,
/// a collector account must either be the vote account itself or a system
/// account that fulfills certain criteria. In the case of vote account A, we
/// are already sure that the collector account is invalid.
///
/// NOTE: if vote account B sets a system account as its inflation collector,
/// then the commission lamports for vote account A will NOT get burned here,
/// but will get burned during `load_and_reward_commission_accounts`
fn accumulate_lamports(src: &RewardCommission, dst: &mut RewardCommission) {
    match (src.is_vote_account, dst.is_vote_account) {
        (false, true) => {
            // Don't accumulate, burn everything in the source
            // reward commission entry.
            //
            // NOTE: There shouldn't be any burned lamports in the
            // source entry, but we're defensive
            dst.burned_lamports = dst
                .burned_lamports
                .saturating_add(src.commission_lamports)
                .saturating_add(src.burned_lamports);
        }
        (true, false) => {
            // The commission lamports on the source are the only
            // ones that get distributed, all others get burned.
            //
            // NOTE: There shouldn't be any burned lamports in the
            // destination entry, but we're defensive
            dst.is_vote_account = true;
            dst.burned_lamports = dst
                .burned_lamports
                .saturating_add(dst.commission_lamports)
                .saturating_add(src.burned_lamports);
            dst.commission_lamports = src.commission_lamports;
        }
        _ => {
            // Normal case, just accumulate both
            dst.commission_lamports = dst
                .commission_lamports
                .saturating_add(src.commission_lamports);
            dst.burned_lamports = dst.burned_lamports.saturating_add(src.burned_lamports);
        }
    }
}

        // boundary. Account is not credited, so the commission lamports are burned.
        let bank = apply_epoch_operations(

                epoch: 1,

                    VoteOperations {
                        earned_credits: Some(1000),
                        new_inflation_rewards_collector: Some(invalid_collector),
                        ..VoteOperations::default()
                    },
                )],
            },
        );

        // The burned commission lamports must be reflected in the epoch rewards
