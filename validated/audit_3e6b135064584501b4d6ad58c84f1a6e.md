### Title
Truncated index used for Merkle proof verification vs. full untruncated index stored in `lastValidated` permanently bricks multi-fill partial validation - (File: contracts/MerkleStorageInvalidator.sol)

### Summary
`MerkleStorageInvalidator.takerInteraction` verifies a taker-supplied Merkle proof against a leaf built from `uint64(takerData.idx)` (a 64-bit truncated view of the index), but then stores the *full, untruncated* `takerData.idx + 1` (a `uint256`) into `lastValidated[key].index`. Because only the low 64 bits of `idx` are checked by the proof, any value `idx = realIndex + n·2^64` produces an identical, valid leaf hash, yet the huge un-truncated value gets persisted as the "canonical" validated index. This is the same root-cause class as the reported Vyper bug — a single logical index has two inconsistent numeric representations (a truncated one used for the security check and a full one used for the persisted state), and the code never asserts they are equal.

### Finding Description
`takerInteraction` (called by anyone permissionlessly acting as `taker` in `LimitOrderProtocol.fillOrderArgs`, which then invokes the taker interaction/post-interaction hooks) decodes `TakerData` directly from taker-controlled calldata: [1](#0-0) 

`idx` is a full `uint256` field, entirely controlled by the taker who crafts the `extraData`/interaction bytes passed into `fillOrderArgs`: [2](#0-1) 

The proof-verification leaf is computed as `keccak256(abi.encodePacked(uint64(takerData.idx), takerData.secretHash))` — truncating `idx` to 64 bits — while the value persisted to storage is the full `takerData.idx + 1`: [3](#0-2) 

Since the off-chain Merkle tree leaves are built from `uint64` indices (as also assumed by tests, e.g. `keccak256(abi.encodePacked(i, hashedSecrets[i]))` with `i` declared `uint64`), any `idx` value congruent mod `2^64` to a real, valid leaf index will pass `processProofCalldata` verification. The attacker can thus pick `idx = realIndex + k·2^64` for any `k`, producing a fully valid proof while writing an astronomically large `index` into `lastValidated[key]`.

This corrupted `validated.index` is subsequently read by `_postInteraction` and checked against `_isValidPartialFill`: [4](#0-3) [5](#0-4) 

`calculatedIndex` in `_isValidPartialFill` is strictly bounded by `partsAmount` (extracted from a 16-bit field, `uint256(extraDataArgs.hashlockInfo) >> 240`), so it can never reach values anywhere near `2^64`. Once `lastValidated[key].index` is poisoned with a huge value, `calculatedIndex + 1 == validatedIndex` (or `+2`) can never be true again for that `key` (`orderHash` + Merkle-root-derived key), so every subsequent legitimate `postInteraction` call for that multi-fill order reverts with `InvalidPartialFill`.

### Impact Explanation
The attack permanently breaks the multiple-fills invariant for the affected order: after one malicious (but individually valid) partial fill with an inflated `idx`, no further resolver can complete any subsequent partial fill of the same order through the Merkle multi-fill path, because `_isValidPartialFill` will never match again. The maker's remaining, still-unfilled `makingAmount` becomes stuck — unable to be picked up by any other resolver — for the remainder of the order's life (until it expires or the maker cancels off-chain), i.e. temporary freezing of funds during the live swap lifecycle for the order's un-filled remainder. Note that the first, malicious fill itself proceeds normally and its own escrow is funded correctly; the damage is that the mapping's future usability is destroyed, denying the ability to complete the swap via additional partial fills.

### Likelihood Explanation
Any unprivileged address can be the `taker` filling a multiple-fills order via `LimitOrderProtocol.fillOrderArgs` (whitelisting only affects fee discount, not the ability to fill — confirmed by `testFuzz_DeployWithFullFeesForResolverNotInWhitelistWithAccessToken` in the test suite, showing non-whitelisted resolvers can still fill with full fees). Constructing a proof for `idx = realIndex + 2^64` requires no special access — the attacker only needs a legitimate leaf/proof pair for any position in the already-published Merkle tree (which is public data shared to enable multi-fills) and can add any multiple of `2^64` to the on-chain-supplied `idx` argument. This requires a single ordinary transaction with crafted calldata; no race condition or privileged role is needed.

### Recommendation
Do not silently truncate `idx` when hashing the leaf. Either:
- Require `idx <= type(uint64).max` (or whatever bit-width the leaf encoding uses) and revert otherwise, or
- Use the full, untruncated `idx` consistently when building the leaf hash (`keccak256(abi.encodePacked(idx, secretHash))` without truncation) so leaf verification and the value persisted to `lastValidated` always refer to the exact same integer, with no scope for the two representations to diverge.

### Proof of Concept
1. Maker creates a multi-fill order with `partsAmount = P`, publishing a Merkle tree over leaves `keccak256(abi.encodePacked(uint64(i), secretHash[i]))` for `i = 0..P`.
2. Attacker (any address acting as taker) calls `LimitOrderProtocol.fillOrderArgs` with `TakerData.idx = 0 + 2^64` (or any `realIndex + k·2^64`) and the genuine proof/secretHash for `realIndex`.
3. In `takerInteraction`, `uint64(takerData.idx) == realIndex`, so `processProofCalldata` succeeds and `InvalidProof` is not triggered — see [6](#0-5) .
4. `lastValidated[key] = ValidationData(takerData.idx + 1, secretHash)` stores `index = 2^64 + 1` instead of `realIndex + 1` — see [7](#0-6) .
5. Any subsequent resolver attempting to fill the remainder of the same order triggers `_postInteraction`, which reads `validated.index = 2^64 + 1` and calls `_isValidPartialFill(..., validatedIndex: 2^64+1)`; since `calculatedIndex` is bounded by `partsAmount` (a small number), the equality checks in `_isValidPartialFill` (lines 224/231 of `BaseEscrowFactory.sol`) never hold, and the call reverts with `InvalidPartialFill` for every future fill attempt on that order.

    function _isValidPartialFill(
        uint256 makingAmount,
        uint256 remainingMakingAmount,
        uint256 orderMakingAmount,
        uint256 partsAmount,
        uint256 validatedIndex
    ) internal pure returns (bool) {
        uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;

        if (remainingMakingAmount == makingAmount) {
            // If the order is filled to completion, a secret with index i + 1 must be used
            // where i is the index of the secret for the last part.
            return (calculatedIndex + 2 == validatedIndex);
        } else if (orderMakingAmount != remainingMakingAmount) {
            // Calculate the previous fill index only if this is not the first fill.
            uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
            if (calculatedIndex == prevCalculatedIndex) return false;
        }

        return calculatedIndex + 1 == validatedIndex;
    }
