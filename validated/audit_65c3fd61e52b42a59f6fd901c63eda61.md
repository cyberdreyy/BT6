### Title
Unsynchronized concurrent writes to shared `l.base` between `SendRawLog`/`Tee` log calls and `StepRunnerStream`/`Stream` writers can interleave trace bytes - (File: common/buildlogger/build_logger.go)

### Summary
`Logger.SendRawLog` is guarded by `l.mu` and the single `internal.NewSync` wrapper baked into `l.w`, but `Logger.Stream()` and `Logger.StepRunnerStream()` each construct brand-new, independent `internal.NewSync` writer instances (with their own private `sync.Mutex`) that also write directly to the same shared `l.base`. None of these independent mutexes are shared with each other or with `l.mu`, so concurrent writers reaching `l.base` through different call paths are not mutually excluded.

### Finding Description
`Logger.w` is built once in `New()` via `l.wrap(l.base, StreamExecutorLevel, Stdout)`, producing one `internal.syncWriter` instance ("syncA") that owns the only mutex protecting that particular pipeline down to `l.base`. `SendRawLog` (invoked by `Tee.Println`/`Errorln`/etc. via `l.logFn`) takes `l.mu` and then writes through `l.w` (syncA), so calls to `SendRawLog` are serialized both by `l.mu` and syncA's own mutex. [1](#0-0) 

However, `Logger.Stream()` and `Logger.StepRunnerStream()` each call `l.wrap(l.base, streamID, streamType)` (or `internal.NewSync(l.base)` for the passthrough case) on every invocation, creating a *new* `syncWriter` with its *own* mutex, unrelated to `l.mu` or to syncA: [2](#0-1) [3](#0-2) 

`internal.NewSync` only locks around the single writer instance it wraps; it provides no cross-instance exclusion: [4](#0-3) 

Since `l.base` (the `internal.NewNopCloser` around the raw `Trace`) is a bare, unlocked writer, all of these independently-mutexed pipelines ultimately call `l.base.Write` without any shared serialization: [5](#0-4) [6](#0-5) 

The struct comment states the intent that `l.mu` should protect all writes to the shared trace ("mu protects w, as Tee's Println, Debugln etc. funcs can be called throughout the runner from different go routines"), but this protection only covers the fixed `l.w` pipeline, not the dynamically-created `Stream()`/`StepRunnerStream()` pipelines: [7](#0-6) 

Job-triggered log lines (e.g. `build.Println`/`Errorln` calls made throughout job execution, reachable via normal job processing) execute on the executor/main build goroutine, while `StepRunnerStream` writers are driven concurrently by the step-runner integration streaming stdout/stderr from a separate goroutine. Both write to the same `l.base` at essentially the same time with no shared lock, so if the concrete `Trace` implementation behind `l.base` is not itself safe for concurrent, non-serialized `Write` calls, byte sequences from the two sources can interleave mid-write.

### Impact Explanation
If interleaving occurs, the resulting trace bytes seen by any trace consumer (job log viewer, or any downstream parser that treats trace content as structured, e.g. artifact/cache metadata embedded in trace output) could be corrupted — a partial write from one source spliced with a partial write from another. This is a data-integrity/log-corruption issue in the build trace stream. Whether it can be escalated to "misinterpreted as a different file path or archive header" depends entirely on whether any downstream component parses the *trace* stream itself as structured/executable data; standard GitLab Runner artifact/cache upload logic does not read paths or archive headers from the trace text, so the specific "archive header confusion" claim in the question is speculative and unverified. The concretely provable impact is limited to corrupted/interleaved bytes in the job trace output.

### Likelihood Explanation
Preconditions are realistic: `StepRunnerStream` is used whenever step-runner is invoked for a job step, and ordinary `Tee` log calls (`Println`, `Errorln`, etc.) can fire concurrently from other goroutines during the same job (e.g. executor-level logging, timeouts, cleanup). No special privilege is needed — this is triggered by normal job execution, not by malicious input. The actual manifestation depends on the concrete `Trace` implementation's own thread-safety, which was not verifiable from the buildlogger package alone; if the underlying `Trace.Write` (e.g., the network trace buffer) already serializes writes internally, this bug is masked at that layer. This uncertainty should be resolved by checking the concrete `Trace` implementation before treating this as fully exploitable.

### Recommendation
Share a single mutex (the existing `l.mu`, or a common one) across all writer chains that terminate at `l.base` — i.e., have `Stream()`, `StepRunnerStream()`'s `buildStripped`/`buildWrapped`/`passthrough`, and `SendRawLog`'s pipeline all synchronize through the same lock before calling into `l.base.Write`, rather than each constructing independent `internal.NewSync` instances with private mutexes.

### Proof of Concept
Go test using `-race` and a custom `Trace` implementation that records `Write` calls and detects overlap (e.g., using an atomic counter/mutex misuse detector or by writing distinguishable markers and checking for byte-level splicing):
1. Construct `Logger` via `buildlogger.New(trace, entry, opts)`.
2. In parallel: goroutine A repeatedly calls `logger.Println("AAAA...")`/`Errorln`; goroutine B repeatedly calls `logger.StepRunnerStream(id, Stdout).Write([]byte("BBBB..."))`.
3. Run with `go test -race`; assert the captured `Trace` buffer never contains a byte sequence that mixes an incomplete "A" run with an incomplete "B" run (e.g., regex-match that all "AAAA" and "BBBB" tokens appear as complete, non-interleaved runs of expected length).
4. Expect: without a shared lock, on a `Trace` backed by a plain non-atomic writer (e.g., `bytes.Buffer` without its own mutex — note `bytes.Buffer` is not concurrency-safe), interleaved/corrupted output can appear, demonstrating the missing cross-pipeline synchronization at the `buildlogger` layer.

```go
func (l *Logger) StepRunnerStream(streamID int, streamType StreamType) io.WriteCloser {
	if l.base == nil {
		return internal.NewNopCloser(io.Discard)
	}

	return &stepRunnerStream{
		timestamping: l.timestamping,
		passthrough:  internal.NewSync(l.base),
		buildStripped: func() io.WriteCloser {
			return newInnerStreamStripper(
				l.wrap(l.base, streamID, Stdout),
				l.wrap(l.base, streamID, Stderr),
			)
		},
		buildWrapped: func() io.WriteCloser {
			return l.wrap(l.base, streamID, streamType)
		},
	}
}
```

```go
func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}
```

```go
type syncWriter struct {
	mu sync.Mutex

	w io.WriteCloser
}

func NewSync(w io.WriteCloser) *syncWriter {
	return &syncWriter{w: w}
}

func (s *syncWriter) Write(p []byte) (int, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	return s.w.Write(p)
}
```
