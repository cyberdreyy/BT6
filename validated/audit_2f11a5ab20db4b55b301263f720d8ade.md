### Title
Allowed-image validation runs on unexpanded `Image.Name`, allowing CI variable expansion to substitute an unvalidated image at VM-tunnel creation - (File: executors/instance/instance.go / executors/internal/autoscaler/acquisition.go)

### Summary
`executor.Prepare` in `executors/instance/instance.go` validates `options.Build.Image.Name` against `AllowedImages` **without expanding CI/CD variables**, while the actual value used to create the nesting VM in `acquisitionRef.createVMTunnel` (`executors/internal/autoscaler/acquisition.go`) is the **variable-expanded** value (`options.Build.GetAllVariables().ExpandValue(image)`). Because the two calls operate on different strings for the same logical field, a job author can craft an `image:` value that is a bare variable reference matching the `allowed_images` glob pattern literally, then define a job-level variable that expands to an arbitrary, non-allowed image string, causing the nesting VM to be created with an image never actually checked by `VerifyAllowedImage`.

### Finding Description
`executors/instance/instance.go` Prepare validates the image before expansion: [1](#0-0) 

Note `options.Build.Image.Name` is passed directly to `common.VerifyAllowedImage` with no call to `ExpandValue`/`GetAllVariables().ExpandValue`, unlike the Docker executor which explicitly expands first and validates the expanded string: [2](#0-1) 

Later, in the same `Prepare` flow, `e.client, err = environment.Prepare(...)` invokes `acquisitionRef.Prepare`, which — when VM isolation is enabled — calls `createVMTunnel`: [3](#0-2) 

Here, `image` is taken from `options.Build.Image.Name` again (the *same, unmodified* raw field) but is now expanded with `options.Build.GetAllVariables().ExpandValue(image)` before being passed to `nc.Create(ctx, image, &slot)`, which actually provisions the nesting VM image.

`VerifyAllowedImage` performs literal `doublestar.Match` glob comparisons against `options.Image` as given — it has no variable-expansion awareness: [4](#0-3) 

Exploit flow:
1. Runner is configured with `vm_isolation.enabled = true` and some `allowed_images` pattern that matches single- or fixed-segment path shapes (e.g. `["*"]`, `["*/*"]`, etc. — this configuration is explicitly documented and expected to be used to allow "any nesting image").
2. Attacker (pipeline author) sets `image: "${JOB_VAR}"` (or a multi-segment pattern like `"${A}/${B}"` matching a `*/*`-style allow pattern) in `.gitlab-ci.yml`.
3. Attacker defines `variables: JOB_VAR: "<arbitrary/disallowed-image>:tag"` in the same `.gitlab-ci.yml` (fully attacker-controlled, ordinary CI variable, no special privilege required).
4. `instance.executor.Prepare` validates the **literal string** `"${JOB_VAR}"` against `AllowedImages`. Because the literal reference has the same segment/slash shape as the glob pattern (e.g., no slash for `*`, one slash for `*/*`), it passes validation even though it is not a real image name.
5. `createVMTunnel` then expands `"${JOB_VAR}"` via `options.Build.GetAllVariables().ExpandValue(image)`, producing the attacker's arbitrary image string, which was never checked by `VerifyAllowedImage`, and passes it straight to `nc.Create`.
6. The nesting daemon creates a VM using an image string that bypassed the `allowed_images` allowlist entirely.

Existing protections are insufficient because:
- `VerifyAllowedImage` has no mechanism to detect or reject variable-reference syntax (`$VAR`, `${VAR}`) in the image field.
- There is no re-validation of the image after expansion inside `createVMTunnel` before calling `nc.Create`.
- The docker executor's pattern (expand-then-validate) is the correct approach and is not mirrored in the instance/autoscaler VM-isolation path.

### Impact Explanation
This breaks the invariant that `allowed_images` restricts which nesting VM images an unprivileged pipeline author can request. An attacker can cause a nesting VM to be provisioned from an image the runner administrator did not intend to allow, defeating the primary control (`allowed_images`/`vm_isolation`) that is meant to constrain nested VM content on shared autoscaler fleets. This can lead to running pipelines inside arbitrary, potentially attacker-supplied or malicious VM images inside the isolated nesting VM.

### Likelihood Explanation
- Preconditions: Runner must be using the `instance`/`autoscaler` executor with `vm_isolation.enabled = true` and a non-empty `allowed_images` list containing pattern shapes an attacker can mimic with variable-reference literal text (glob patterns like `*`, `*/*`, `**/*`, etc. are common/documented examples, including the doc example `allowed_images = ["*"]`). [5](#0-4) 
- Attacker action requires only normal pipeline-author privileges (setting `image:` and `variables:` in `.gitlab-ci.yml`), no special access.
- Fully repeatable and deterministic — the bug is a straightforward missing-expansion-before-validation ordering issue in `instance.go`, contrasted with the correct expand-then-validate order already used in `docker.go`.

### Recommendation
In `executors/instance/instance.go` `Prepare`, expand `options.Build.Image.Name` via `options.Build.GetAllVariables().ExpandValue(...)` (or equivalent) **before** calling `common.VerifyAllowedImage`, mirroring the Docker executor's `expandImageName` pattern. Additionally, in `executors/internal/autoscaler/acquisition.go` `createVMTunnel`, re-validate the expanded `image` value against `nestingCfg`/`Instance.AllowedImages` immediately before calling `nc.Create`, so that the value actually used to provision the VM is the one that was checked, closing any remaining TOCTOU gap between the two Prepare stages.

func (e *executor) expandImageName(imageName string, allowedInternalImages []string) (string, error) {
	defaultDockerImage := e.ExpandValue(e.Config.Docker.Image)
	if imageName != "" {
		image := e.ExpandValue(imageName)
		allowedInternalImages = append(allowedInternalImages, defaultDockerImage)
		err := e.verifyAllowedImage(image, "images", e.Config.Docker.AllowedImages, allowedInternalImages)
		if err != nil {
			return "", err
		}
		return image, nil
	}

func VerifyAllowedImage(options VerifyAllowedImageOptions, logger buildlogger.Logger) error {
	for _, allowedImage := range options.AllowedImages {
		ok, _ := doublestar.Match(allowedImage, options.Image)
		if ok {
			return nil
		}
	}

		if internalImage == options.Image {
			return nil
		}
	}
