### Title
Missing Timeout on WebSocket Handshake in RPC PubSub Connection Handler Enables Ingest Starvation - ([File: rpc/src/rpc_pubsub_service.rs])

### Summary
The `iso-filecoin` report flags a missing timeout on an RPC `call` that could let a slow/unresponsive peer stall the caller indefinitely. The same bug class exists in agave's RPC pubsub (WebSocket) ingest path: `listen()` in `rpc/src/rpc_pubsub_service.rs` unconditionally accepts every incoming TCP connection and spawns `handle_connection` for it, but the WebSocket handshake (`server.receive_request().await`) and the subsequent `receiver.receive_data(&mut data)` calls have no timeout applied. A client that opens a TCP connection and never completes (or very slowly drips) the WebSocket handshake/frames can hold that spawned task open indefinitely.

### Finding Description
In `listen()` [1](#0-0) , every accepted TCP connection is immediately handed to `tokio::spawn(handle_connection(...))` with no per-connection accept-rate limiting or handshake deadline.

Inside `handle_connection`, the very first operation is:
```
let mut server = Server::new(socket.compat());
let request = server.receive_request().await?;
``` [2](#0-1) 

This `await` has no `tokio::time::timeout(...)` wrapper, unlike the resolved `iso-filecoin` issue where `fetch()` lacked a timeout. A client that opens the TCP socket and sends bytes at a trickle (or nothing at all) will keep `server.receive_request()` pending forever, and the spawned task (with its own stack, buffers, and a `TcpStream`) stays alive for the lifetime of that idle connection.

The main receive loop has the same property — `receiver.receive_data(&mut data)` inside the `select!` at [3](#0-2)  is not time-bounded either, so once past the handshake, a client can also hold the connection open indefinitely by never sending a complete frame.

Unlike the actual subscription layer, which is protected by `SubscriptionControl::subscribe`'s `SubscriberCountGuard::try_reserve` cap (`max_active_subscriptions`, default `DEFAULT_MAX_ACTIVE_SUBSCRIPTIONS = 1_000_000`) [4](#0-3) , this cap only limits *successful* subscriptions after a completed handshake and JSON-RPC request. It does nothing to bound the number of raw TCP connections sitting in the handshake/read phase, since there is no `max_connections` gate or accept throttling visible in `listen()`.

### Impact Explanation
An external, unauthenticated attacker can open a large number of TCP connections to the RPC pubsub port and either withhold the WebSocket handshake or send data byte-by-byte, causing `tokio::spawn`ed tasks to accumulate. Each task holds an open socket and buffer resources. Because the accept loop keeps spawning without regard to a connection or handshake timeout, this is a classic "slow-loris" resource exhaustion vector against the RPC pubsub service, denying service to legitimate `accountSubscribe`/`signatureSubscribe`/etc. clients (and consuming file descriptors / worker capacity on the node) — matching the "ingest starvation" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in deployments where the pubsub port is exposed to the public internet (a common configuration for RPC API nodes). No authentication, stake, or fee is required to open a TCP connection and stall the handshake; the attack requires only ordinary network access, consistent with "reachable from an ordinary user's RPC call."

### Recommendation
Wrap the handshake (`server.receive_request()`) and the per-message read (`receiver.receive_data`) in `tokio::time::timeout(...)`, closing/dropping connections that fail to progress within a bounded interval (e.g., a few seconds for handshake, an idle timeout for subsequent frames). Additionally, consider bounding the number of concurrently pending (pre-handshake) connections independent of `max_active_subscriptions`, mirroring the fix pattern used for `iso-filecoin`'s `call` method (adding an explicit timeout option to the network operation).

### Proof of Concept
1. Start a validator/RPC node with the pubsub service enabled and reachable.
2. From an attacker host, open N TCP connections to the pubsub port and, for each, either send nothing or send a partial HTTP Upgrade request one byte at a time with long delays.
3. Observe that each connection's `handle_connection` task remains alive indefinitely (visible via connection counters / task metrics), since `server.receive_request().await` in [5](#0-4)  never times out.
4. Repeating this with sufficient connections exhausts file descriptors/worker capacity, delaying or blocking legitimate subscription clients from completing their handshakes.

    listen_address: SocketAddr,
    config: PubSubConfig,
    subscription_control: SubscriptionControl,
    mut tripwire: Tripwire,
) -> io::Result<()> {
    let listener = match tokio::net::TcpListener::bind(&listen_address).await {
        Ok(listener) => {
            info!("rpc_pubsub listening on {listen_address:?}");
            listener
        }
        Err(e) => {
            error!(
                "failed to bind rpc_pubsub listener on {listen_address:?}: {e}. Hint: is the port \
                 already in use?"
            );
            return Err(e);
        }
    };
    let counter = TokenCounter::new("rpc_pubsub_connections");
    loop {
        select! {
            result = listener.accept() => match result {
                Ok((socket, addr)) => {
                    debug!("new client ({addr:?})");
                    let subscription_control = subscription_control.clone();
                    let config = config.clone();
                    let tripwire = tripwire.clone();
                    let counter_token = counter.create_token();

                        let handle = handle_connection(
                            socket, subscription_control, config, tripwire
                        );

                            Err(err) => warn!("connection handler error ({addr:?}): {err}"),
                        }

struct SubscriberCountGuard(Arc<SubscriptionControlInner>);

impl SubscriberCountGuard {
    fn try_reserve(control: &Arc<SubscriptionControlInner>) -> Option<Self> {
        let max = control.max_active_subscriptions;
        control
            .subscriber_count
            .fetch_update(Ordering::Relaxed, Ordering::Relaxed, |current| {
                (current < max).then_some(current + 1)
            })
            .ok()?;
        Some(Self(Arc::clone(control)))
    }
}
