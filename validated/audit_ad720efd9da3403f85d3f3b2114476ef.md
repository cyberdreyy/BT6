### Title
Instant-withdraw receipt is counted twice after borrower default: paid at par via `instantWithdrawsRequests` while still included in `defaultPendingClaimBasis` via `instantWithdrawClaimsByEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The analog to "one escaped token fans out into multiple filesystem matches" is a single instant-withdraw receipt that matches two independent payout/basis sources in `IdleCreditVault`: the aggregate `instantWithdrawsRequests[user]` paid at par by `claimInstantWithdrawRequest`, and the per-epoch `instantWithdrawClaimsByEpoch[epochNumber]` re-counted by `defaultPendingClaimBasis()` during `finalizeDefaultRecovery`. Nothing clears the per-epoch counter in the pre-finalization claim path, so one receipt can be paid once in full and then counted again into the recovery basis.

### Finding Description
`requestInstantWithdraw` records the same receipt in two places: `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` plus `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . The pre-finalization claim path burns only the aggregate and clears only `instantWithdrawsRequests[_user]`; it never touches `instantWithdrawClaimsByEpoch` [2](#0-1) . Only `_claimDefaultedInstantWithdrawRequest` (reachable solely after `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`) decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` [3](#0-2) .

Meanwhile `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the defaulted claim basis whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `finalizeDefaultRecovery` divides the recovery reserve by `activeBasis + pendingBasis` [5](#0-4) .

Sequence: epoch running, instant-withdraw mode enabled; attacker (any KYC'd lender) calls `requestInstantWithdraw`; borrower funding partially arrives via `collectInstantWithdrawFunds` (which only reduces `pendingInstantWithdraws`, not `instantWithdrawClaimsByEpoch`) [6](#0-5) ; `stopEpoch` borrower funding then fails and the CDO marks `defaulted()`. In the window where `defaulted()` is true but `defaultRecoveryFinalized` is still false, `claimInstantWithdrawRequest` takes the funded path and pays the full aggregate at par [7](#0-6) . Because `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws` are unchanged, the later honest `finalizeDefaultRecovery` still counts the already-claimed receipts in `pendingBasis`, inflating the denominator and cutting `recoveryPrice` for every other receipt holder and active LP [8](#0-7) .

### Impact Explanation
Two effects from one receipt (the "one match expands to many" analog): (1) the attacker exits an unfunded defaulted-epoch receipt at par, consuming funded strategy underlyings ahead of the haircut; (2) the stale `instantWithdrawClaimsByEpoch` basis dilutes `defaultRecoveryPrice`, so all remaining claimants and active tranche holders recover less than the true reserve share — a direct, quantifiable wealth transfer equal to `claimedAmount * (defaultRecoveryPrice_true - defaultRecoveryPrice_actual)` spread across the pool.

### Likelihood Explanation
Requires an epoch vault with instant withdrawals enabled, a partially or fully collected instant queue, and a borrower default in the same epoch — plus the CDO-side claim routing must remain callable while `defaulted()` is true but before `finalizeDefaultRecovery` executes. I could not fully verify the last guard: if `IdleCDOEpochVariant.claimInstantWithdrawRequest` reverts whenever `defaulted()` is set, the exploitable window closes and severity drops to a bookkeeping inconsistency only (stale basis still inflates `pendingBasis` if claims happened before default but after funding, which does not require the defaulted window at all — the user can claim the funded part at par legitimately, yet their receipt remains in `instantWithdrawClaimsByEpoch`, still double-counting basis). That second path needs no privileged misbehavior and is reachable whenever `collectInstantWithdrawFunds` funded part of the queue before default.

### Recommendation
Decrement `instantWithdrawClaimsByEpoch[epochNumber]` (or track a per-epoch claimed counter) inside `claimInstantWithdrawRequest` when clearing `instantWithdrawsRequests[_user]`, and gate the funded claim path on `!IIdleCDOEpochVariant(idleCDO).defaulted() || defaultRecoveryFinalized` so defaulted-epoch receipts cannot exit at par before `finalizeDefaultRecovery` fixes the haircut.

### Proof of Concept
Foundry fork PoC on an instant-withdraw-enabled `IdleCreditVault`/`IdleCDOEpochVariant` deployment:

1. Attacker deposits AA, epoch runs, calls `requestInstantWithdraw(amount)`.
2. CDO collects partial funding via `collectInstantWithdrawFunds(part)` → `pendingInstantWithdraws = amount - part`, `instantWithdrawClaimsByEpoch[E] = amount` unchanged.
3. `stopEpoch` fails borrower funding → `_handleBorrowerDefault` marks defaulted; `finalizeDefaultRecovery` not yet called.
4. Attacker calls `claimInstantWithdrawRequest` → receives full `amount` at par; `instantWithdrawClaimsByEpoch[E]` still `amount`.
5. Owner/manager finalizes recovery → `defaultPendingClaimBasis()` re-adds `amount` → assert `defaultRecoveryPrice` is strictly lower than the price computed without the stale basis, and other claimants' payouts are reduced proportionally.

Uncertainty noted in Likelihood: step 4 depends on the CDO not reverting claims while `defaulted()` is set pre-finalization; if it does, the stale-basis dilution in step 5 still reproduces for receipts that were claimed (legitimately) between funding and default.

    _onlyIdleCDO();

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
