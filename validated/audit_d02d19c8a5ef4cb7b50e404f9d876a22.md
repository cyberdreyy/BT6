### Title
Cross-user callback overwrite via colliding MessageId in `handler.HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each request's callback keyed solely by the client-controlled `msg.Body.MessageId`, without checking whether that key is already occupied by another in-flight request. Any unprivileged holder of an ECDSA key that can sign a valid gateway `Message` can pick an arbitrary `MessageId` (up to 128 bytes) and overwrite another user's pending callback slot, causing that victim's DON response to be silently dropped or delivered to the attacker.

### Finding Description
`Message.Validate()` only checks length/format constraints and derives `Body.Sender` from the signature [1](#0-0) ; it does not enforce that `MessageId` is unique per-sender or globally. In `HandleLegacyUserMessage`, after validating the message, the handler unconditionally writes into the shared map with no existence check:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [2](#0-1) 

If an attacker sends `msg.Body.MessageId = "V1"` (the same ID as a victim's pending `webAPITrigger` request), `h.savedCallbacks["V1"]` is silently overwritten with the attacker's own `callback`. When the DON later replies for `"V1"`, `handleWebAPITriggerMessage` looks up and deletes by `msg.Body.MessageId` only, with no sender/ownership check, and dispatches the response to whichever callback currently occupies that slot:

```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ...})
``` [3](#0-2) 

The `MessageId` is fully attacker-controlled: it flows from the JSON-RPC request ID directly into `Body.MessageId` in `ValidatedMessageFromReq` [4](#0-3) , and `gateway.ProcessRequest` only enforces a max length of 200 characters before routing to `HandleLegacyUserMessage`, with no per-node/per-sender allowlist applied at this stage (marked as a TODO in the handler itself) [5](#0-4) [6](#0-5) . Only a valid signature over the message body is required (`msg.Validate()`), which any ECDSA keyholder can produce — no allowlisting, roles, or MessageId ownership checks exist for the legacy path.

Notably, the newer v2 handler (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`) already implements protection against this exact class of bug — it rejects a duplicate/in-flight request ID with a conflict error, as shown by its test asserting `"in-flight request"` and `jsonrpc.ErrConflict` [7](#0-6) . The legacy handler under review lacks this equivalent safeguard, confirming the gap is a real, addressable deficiency rather than an inherent design constraint.

### Impact Explanation
This is a cross-user response confusion / request-isolation bypass: an attacker can either (a) cause denial-of-service on a targeted victim's pending webAPITrigger request (silently dropped, no response ever delivered, since the DON's genuine response is swallowed by the attacker's slot and the victim's own DON response, if it arrives later under the now-overwritten different callback, is delivered to the attacker instead), or (b) receive the DON's response payload intended for the victim, potentially exposing data scoped to the victim's request. Because trigger payloads can carry workflow-specific data, this could constitute unauthorized disclosure of another user's response data and denial of service of a legitimate request.

### Likelihood Explanation
Exploitability requires only: (1) an ECDSA keypair (freely generatable, no registration or on-chain requirement is enforced at this legacy code path), (2) knowledge or guess of the victim's `MessageId` value used for the concurrent in-flight request, and (3) timing the attacker's message to arrive after the victim's but before the DON responds. Guessing the exact `MessageId` may be nontrivial if the caller uses a random/unique value, lowering practical likelihood; however the vulnerability is fully reachable and reproducible in a unit-test/handler-level setting (as shown below) and requires no elevated privileges — the TODO comment in the code (`// TODO: apply allowlist and rate-limiting here`) confirms even sender-side allowlisting is not yet enforced at this stage.

### Recommendation
In `HandleLegacyUserMessage`, before storing into `h.savedCallbacks`, check whether an entry already exists for `msg.Body.MessageId` (optionally scoped by `msg.Body.Sender` for stronger isolation) and reject the request with a conflict error (mirroring the v2 handler's `"in-flight request"` / `ErrConflict` behavior) instead of silently overwriting. Consider keying the map by `(Sender, MessageId)` tuple rather than `MessageId` alone to prevent any cross-sender ID collision entirely.

### Proof of Concept
Handler-level Go test (analogous to existing `TestHandlerReceiveHTTPMessageFromClient` in `handler_test.go`):
1. Create victim message `msgV` signed with `nodes[0].PrivateKey` (or any key) with `MessageId = "V1"`; call `handler.HandleLegacyUserMessage(ctx, msgV, cbVictim)`.
2. Before dispatching the DON response, create attacker message `msgA` signed with a different, unrelated ECDSA key, but with the same `Body.MessageId = "V1"`; call `handler.HandleLegacyUserMessage(ctx, msgA, cbAttacker)`.
3. Assert `handler.savedCallbacks["V1"]` now holds the attacker's callback (`cbAttacker`), proving the victim's entry was overwritten.
4. Simulate the DON's response for `"V1"` (as if answering the victim's original request) via `handler.HandleNodeMessage(ctx, resp, nodeAddr)`.
5. Assert `cbAttacker.Wait(ctx)` receives the response (attacker gets victim-scoped data) while `cbVictim.Wait(ctx)` times out / never resolves (victim's request is silently dropped) — expected/desired behavior instead: the second `HandleLegacyUserMessage` call should return an error (e.g., conflict) and `cbVictim` should remain intact and receive the correct DON response.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
