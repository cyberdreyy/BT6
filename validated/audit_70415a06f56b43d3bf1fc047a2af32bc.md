Based on the codebase, there's a concrete analog in the gateway's legacy WebAPI handler where a client-controlled `MessageId` is used as the sole key into a shared callback map without any collision or ownership check, enabling cross-user response confusion.

### Title
Client-controlled `MessageId` collision in `handler.savedCallbacks` enables cross-user response hijacking - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`handler.HandleLegacyUserMessage` stores each incoming user request's callback in a shared map keyed only by the client-supplied `MessageId`, with no check for an existing entry and no binding to the requester's identity. Because `MessageId` is fully attacker-controlled (it is part of the signed message body but its *value* is chosen by the caller), an unprivileged actor can pick a `MessageId` that collides with another in-flight request. This silently overwrites the victim's saved callback, so when the DON node eventually replies with that `MessageId`, the response is delivered to the attacker's callback instead of the victim's — a cross-user response confusion analogous to the Venus `healAccount` bug class, where an operation clears/overwrites shared state without validating or preserving the effects owed to the original party.

There is no check for `_, exists := h.savedCallbacks[msg.Body.MessageId]` before overwriting. `MessageId` validation only enforces length/format, not uniqueness or ownership: [2](#0-1)

The same unconditional-overwrite pattern also exists in the dummy handler used as a reference implementation: [4](#0-3) .

By contrast, the newer v2 request-cache abstraction guards against this by keying on `(sender, messageId)` and rejecting duplicates: [5](#0-4) . The legacy `capabilities.handler` path does not have this protection, showing this is a regression/gap rather than an inherent design limitation.

### Impact Explanation
An unprivileged client can:
1. Observe or guess a victim's pending `MessageId` (or race to submit a request using the same `MessageId` before the victim's request completes, since the window is open until the DON node responds).
2. Submit their own signed `HandleLegacyUserMessage` request using that same `MessageId`, causing their callback to silently replace the victim's in `h.savedCallbacks`.
3. Receive the victim's trigger response payload when the DON node's reply arrives, since routing is solely by `MessageId`.

This results in cross-user response confusion / information disclosure, matching the "cross-user response confusion" impact category. Depending on payload content, this can leak external system responses or trigger data intended for another workflow/user.

### Likelihood Explanation
The attack requires only the ability to submit a signed legacy WebAPI trigger message with an attacker-chosen `MessageId`, which is achievable by any unprivileged client capable of interacting with the gateway (the message only needs to be validly signed by the attacker's own key — the `MessageId` value itself is not derived from or bound to the sender). The main constraint is timing (the attacker's overwrite must land before the legitimate node response arrives), which is feasible given typical request latencies and no rate limit gates this specific narrow window.

### Recommendation
Key `savedCallbacks` by `(Sender, MessageId)` similarly to the pattern in `core/services/gateway/handlers/common/requestcache.go`, and reject new registrations that would collide with an existing pending entry instead of overwriting it silently. Additionally, when delivering the response in `handleWebAPITriggerMessage`, validate that the response is destined for the same sender that registered the callback.

### Proof of Concept
1. Victim submits a legacy WebAPI trigger request with `MessageId = "X"`, is forwarded to DON nodes, and awaits response via `savedCallbacks["X"]`.
2. Before the DON node replies, attacker submits their own signed legacy request with `MessageId = "X"`; `h.savedCallbacks["X"]` is overwritten with the attacker's callback (`handler.go` lines 411-414).
3. DON node responds with `MessageId = "X"` (the victim's original trigger); `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback, and delivers the victim's response payload to the attacker.
