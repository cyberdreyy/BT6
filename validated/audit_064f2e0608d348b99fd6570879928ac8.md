### Title
Reward-cycle signer refresh overwrites a still-active previous-cycle `Signer` at the same HashMap parity slot before stale-check, dropping pending block-proposal state - (File: stacks-signer/src/runloop.rs)

### Summary
`RunLoop::refresh_runloop` calls `refresh_signer_config(next_reward_cycle)` — which does an unconditional `self.stacks_signers.insert(reward_index, new_signer_config)` — *before* calling `cleanup_stale_signers(current_reward_cycle)`. Because `stacks_signers` is keyed by `reward_cycle % 2`, cycle N-1 and cycle N+1 share the same map slot, so when the runloop enters the next prepare phase it can overwrite the live cycle N-1 `Signer` (still holding in-flight `submitted_block_proposal` bookkeeping) without ever checking `has_unprocessed_blocks()`.

### Finding Description
In `stacks-signer/src/runloop.rs`, `refresh_runloop` (lines 387-448) does the following in order:
1. `refresh_signer_config(current_reward_cycle)` if not configured for current cycle.
2. `refresh_signer_config(next_reward_cycle)` if in next prepare phase and not configured for next cycle — this unconditionally calls `self.stacks_signers.insert(reward_index, new_signer_config)` at [1](#0-0) .
3. Only *after* both of the above, `self.cleanup_stale_signers(current_reward_cycle)` runs, which is the only place that checks `has_unprocessed_blocks()` before removing a stale entry: [2](#0-1) .

Since `reward_index = reward_cycle % 2`, cycles N-1 and N+1 map to the identical HashMap key. If the signer for cycle N-1 is still resident in `stacks_signers[(N-1)%2]` (e.g., because its tenure has not yet been marked stale/cleaned up, or simply because cleanup for this pass hasn't run yet), and the runloop is now in the next-prepare-phase for cycle N+1, step 2 above (`refresh_signer_config(next_reward_cycle)`) will `insert` the new `ConfiguredSigner::RegisteredSigner` for N+1 directly into that slot, silently dropping the old N-1 `ConfiguredSigner` value — regardless of whether it still has `has_unprocessed_blocks() == true` — because that check only happens in `cleanup_stale_signers`, which runs strictly after the insert in the same function, and only when reward_cycle < current_reward_cycle (line 480 `if reward_cycle >= current_reward_cycle { continue; }`).

The dropped `Signer` struct is the only place holding transient, non-persisted decision state for an in-flight block validation/response (e.g., `submitted_block_proposal`). `SignerDb` records finalized block info/signatures but not this specific in-flight bookkeeping, so once the `ConfiguredSigner` value is dropped via `HashMap::insert` overwrite, that pending decision is lost — it will never be resolved (accepted or rejected), and the corresponding response to the node/miner for that tenure is never sent.

An attacker who can win a single miner slot can craft a `BlockProposal` for the tail of cycle N-1 that is expensive/slow to validate (e.g., crafted to maximize validation latency within permitted limits), increasing the odds that `submitted_block_proposal` is still `Some(..)` when the node's burn-height events push the runloop into the next-cycle prepare phase and `refresh_runloop` executes the ordering above. No majority of signers, no privileged access, and no auth token are required — only gossip of the proposal and control of one slot.

### Impact Explanation
This breaks a bounded-liveness guarantee: a valid, already-in-flight block proposal for cycle N-1 can be silently orphaned by the signer's own runloop bookkeeping, meaning the signer never completes processing/responding to that tenure's proposal. This matches the High-severity liveness category ("a signer wedged into never signing valid blocks / losing state needed to resolve a pending decision"). The bug is a structural ordering defect in `refresh_runloop`, so it is repeatable at every reward-cycle boundary where the timing/parity conditions line up, not a one-off race.

### Likelihood Explanation
Preconditions: (1) the affected signer must still hold a `ConfiguredSigner::RegisteredSigner` entry for cycle N-1 at time of the N+1 refresh (i.e., not yet cleaned up), (2) that entry must have an in-flight `submitted_block_proposal`, and (3) the runloop's next-prepare-phase computation for N+1 must fire in the same `refresh_runloop` invocation, before `cleanup_stale_signers` runs. This requires natural reward-cycle progression (burn-chain driven), which the attacker does not directly control, but the attacker can increase the likelihood of overlap by submitting proposals that take longer to validate near a cycle boundary. The attacker needs only one miner/signer slot and message gossip — no privileged role. Exploitability depends on timing alignment with the node's reward-cycle transition, making it probabilistic rather than deterministically attacker-triggered, but the underlying code defect (missing `cleanup_stale_signers`-before-`refresh_signer_config` ordering, or missing `has_unprocessed_blocks()` guard in `refresh_signer_config`'s insert) is present regardless.

### Recommendation
In `RunLoop::refresh_runloop`, call `self.cleanup_stale_signers(current_reward_cycle)` before `refresh_signer_config(next_reward_cycle)`, or have `refresh_signer_config` itself refuse to overwrite an existing `ConfiguredSigner::RegisteredSigner` entry at the target index if that entry's `reward_cycle()` differs from the new cycle and `has_unprocessed_blocks()` is still `true` (log/warn and defer the refresh in that case, similar to the `Err` branch at lines 355-358).

### Proof of Concept
Rust unit test in `stacks-signer/src/runloop.rs` (`#[cfg(test)] mod tests`):
1. Construct a `RunLoop` with a mock `Signer` implementation of the `SignerTrait` whose `has_unprocessed_blocks()` returns `true` (simulating an in-flight `submitted_block_proposal`).
2. Insert this mock signer into `stacks_signers` at index `(N-1) % 2` with `reward_cycle() == N-1`.
3. Directly call `self.refresh_signer_config(N+1)` (bypassing the normal `refresh_runloop` gate) and assert that `stacks_signers.get(&((N+1)%2))` is `Some(ConfiguredSigner::RegisteredSigner(_))` reflecting the new N+1 config — confirming the old N-1 entry (with `has_unprocessed_blocks() == true`) was silently dropped by `HashMap::insert` without any check.
4. Contrast with calling `cleanup_stale_signers(N)` first: assert the mock N-1 signer is retained (not removed) because `has_unprocessed_blocks()` is `true`, showing that had the correct ordering been used, the pending proposal would have been preserved instead of being overwritten. [3](#0-2)

    fn cleanup_stale_signers(&mut self, current_reward_cycle: u64) {
        #[cfg(any(test, feature = "testing"))]
        if TEST_SKIP_SIGNER_CLEANUP.get() {
            warn!("Skipping signer cleanup due to testing directive.");
            return;
        }
        let mut to_delete = Vec::new();
        for (idx, signer) in &mut self.stacks_signers {
            let reward_cycle = signer.reward_cycle();
            if reward_cycle >= current_reward_cycle {
                // We are either the current or a future reward cycle, so we are not stale.
                continue;
            }
            match signer {
                ConfiguredSigner::RegisteredSigner(signer) => {
                    if !signer.has_unprocessed_blocks() {
                        debug!("{signer}: Signer's tenure has completed.");
                        to_delete.push(*idx);
                    }
                }
                ConfiguredSigner::NotRegistered { .. } => {
                    debug!("{signer}: Unregistered signer's tenure has completed.");
                    to_delete.push(*idx);
                }
            }
        }
        for idx in to_delete {
            self.stacks_signers.remove(&idx);
        }
    }
