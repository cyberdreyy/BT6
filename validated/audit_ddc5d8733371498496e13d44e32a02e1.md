### Title
Front-runnable `SystemInstruction::InitializeNonceAccount` allows a malicious authority to be set on any funded, uninitialized nonce account - (File: `programs/system/src/system_instruction.rs`, `programs/system/src/system_processor.rs`)

### Summary
The bug class in the external report — an `initialize()` entry point that can be called by *anyone* because it lacks an authority/owner check, enabling a front-run of the intended initializer — has a direct analog in Agave's System Program nonce-account initialization path. `initialize_nonce_account()` and its dispatcher in `system_processor.rs` never verify that the nonce account itself (or any privileged party) is a transaction signer; the only requirements are that the account is writable, uninitialized, and rent-exempt.

### Finding Description
The dispatcher for `SystemInstruction::InitializeNonceAccount` only checks account count and pulls the `RecentBlockhashes`/`Rent` sysvars — it performs no signer check on account index 0 (the nonce account) before calling `initialize_nonce_account`: [1](#0-0) 

The underlying state-transition function itself only validates writability, `Uninitialized` state, and rent-exemption before writing the caller-supplied `nonce_authority` into the account — again with no signer/authority check: [2](#0-1) 

By contrast, `authorize_nonce_account` (which changes the authority on an *already initialized* nonce account) explicitly requires the current authority to be present in the `signers` set: [3](#0-2) 

This asymmetry is the analog of the reported bug: the "first call" transition (`Uninitialized -> Initialized`) is unprotected, while subsequent authority changes are protected. Because `SystemInstruction::CreateAccount` (funding + assigning the account to the System Program) and `SystemInstruction::InitializeNonceAccount` (writing the nonce authority) are ordinarily issued as separate instructions/transactions (e.g. by `solana_system_interface::instruction::create_nonce_account`), any observer who sees a freshly created, rent-exempt, system-owned, correctly-sized nonce account before it has been initialized can submit their own `InitializeNonceAccount` instruction naming themselves (or an arbitrary key) as `nonce_authority`, transitioning the account to `Initialized` first. Once initialized, the legitimate creator's subsequent `InitializeNonceAccount` call fails with `InstructionError::InvalidAccountData` (state is no longer `Uninitialized`), permanently locking the attacker in as the durable-nonce authority.

### Impact Explanation
A successful front-run gives the attacker sole control (`authorize_nonce_account`, `advance_nonce_account`, `withdraw_nonce_account`) over a nonce account that the victim funded with rent-exempt lamports, including the ability to withdraw those lamports once the account is drained back to `Uninitialized` (the account's lamports are recoverable only by the authority). This is an unauthorized state mutation of a live account reachable purely from ordinary, unprivileged transactions.

### Likelihood Explanation
Exploitation requires only that the two instructions (`CreateAccount` and `InitializeNonceAccount`) land as separate transactions/instructions and that an attacker can observe the intermediate, uninitialized state (e.g., via mempool/QUIC ingest monitoring or a delay between wallet-issued transactions) and race a competing `InitializeNonceAccount` transaction ahead of the legitimate one. Many wallets and CLI flows (e.g., `solana-cli`'s nonce creation helpers) combine both instructions into a single atomic transaction, which would not be vulnerable, but any client that separates account creation from initialization — or any case where a `CreateAccount` transaction confirms before the paired `InitializeNonceAccount` is submitted/confirmed — is exposed.

### Recommendation
Require a signer check in `initialize_nonce_account`/the `InitializeNonceAccount` processor arm analogous to `authorize_nonce_account`: either require the nonce account key itself to be a signer of the initializing transaction, or require the caller-supplied `nonce_authority` (or a designated creator key) to sign, so an unrelated third party cannot claim authority over an account they did not fund/create.

### Proof of Concept
1. Attacker monitors QUIC/mempool or account creation events for `SystemInstruction::CreateAccount` transactions targeting the System Program with `space == NonceState::size()`.
2. Once such an account is observed (funded, rent-exempt, owned by the System Program, and still `State::Uninitialized`), before the victim's paired `InitializeNonceAccount` transaction lands, the attacker submits their own transaction:
   `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` with account index 0 = victim's newly created nonce account (no signature from that account required per `system_processor.rs:448-466`).
3. `initialize_nonce_account` (`programs/system/src/system_instruction.rs:163-211`) succeeds because the account is writable, `Uninitialized`, and rent-exempt — the attacker's key is now `nonce_authority`.
4. The victim's original `InitializeNonceAccount` transaction now fails with `InstructionError::InvalidAccountData` since the account is already `Initialized`.
5. The attacker can now call `AdvanceNonceAccount`/`WithdrawNonceAccount` as the sole authority, ultimately withdrawing the victim's rent-exempt deposit.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
