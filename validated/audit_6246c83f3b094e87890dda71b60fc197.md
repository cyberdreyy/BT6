### Title
Post-default instant withdraw receipts bypass recovery-basis accounting and drain `defaultRecoveryReserve` at recovery price — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` lacks the `defaultRecoveryFinalized` routing that `requestWithdraw` has. A request made after `finalizeDefaultRecovery` is recorded under `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (since `epochNumber` no longer advances), and `_claimDefaultedInstantWithdrawRequest` then pays it at `defaultRecoveryPrice` from `defaultRecoveryReserve` — a reserve sized at finalization only for basis reported by `defaultPendingClaimBasis`, which did not include this new claim. The extra payout shrinks the reserve and freezes later legitimate claimants out of their recovery.

### Finding Description
After a borrower default, `finalizeDefaultRecovery` fixes `defaultRecoveryReserve` and `defaultRecoveryPrice` against `totalBasis = activeBasis + defaultPendingClaimBasis()`, where the pending basis includes `instantWithdrawClaimsByEpoch[epochNumber]` only as it existed at that moment [1](#0-0) . `requestWithdraw` contains an explicit post-default branch that mints an already-haircut receipt into `postDefaultRequests` [2](#0-1) , but `requestInstantWithdraw` has no `defaultRecoveryFinalized` check at all: it burns CDO strategy tokens, mints the user a receipt, and books it into `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` [3](#0-2) . Because `epochNumber` equals `defaultRecoveryEpoch` post-finalization, `claimInstantWithdrawRequest` routes the new receipt through `_claimDefaultedInstantWithdrawRequest`, which pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve` [4](#0-3) . The paid amount was never part of the finalized claim basis, so every post-default instant claim consumes recovery funds belonging to other defaulted receipt holders.

### Impact Explanation
Direct theft of defaulted recovery funds / insolvency of the recovery reserve. With recovery price `p < 1`, an attacker (any KYC-passed lender / tranche-token holder) who calls the CDO's instant-withdraw path after finalization receives `amount * p` from the reserve while contributing nothing to its basis. The reserve is finite: `defaultRecoveryReserve -= amount` in `_transferDefaultRecovery` [5](#0-4)  means legitimate pre-default claimants' later claims revert on underflow once the attacker extracts enough — a quantifiable loss equal to the attacker's payout, capped by the reserve. In the `defaultInstantWithdrawsFinalized == false` configuration, the same request instead reaches `_transferFundedClaim`, whose reserve-protection guard reverts when `balance - reserve < amount` [6](#0-5)  — so the user's already-burned tranche tokens become a permanently unpayable receipt (permanent freezing of funds).

### Likelihood Explanation
Requires only an unprivileged tranche holder requesting an instant withdraw through the (honest) CDO after `defaultRecoveryFinalized`; no privileged collusion needed. The gap exists precisely because the two request entry points were asymmetrically patched for post-default handling. Uncertainty: whether `IdleCDOEpochVariant`'s instant-withdraw entry (`requestInstantWithdraw` caller) remains reachable while `defaulted()` — the strategy side imposes no such gate, and the existence of the post-default `requestWithdraw` path shows post-default requests are an intended flow. If the CDO blocks instant requests when defaulted, the residual bug is the missing guard itself plus the frozen-receipt path.

### Recommendation
Mirror `requestWithdraw`'s post-default branch in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert, or mint a post-default receipt paid 1:1 from a separately tracked post-default bucket (never touching `defaultRecoveryReserve`), and skip `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` bookkeeping that feeds `defaultPendingClaimBasis`. Additionally, after finalization, write post-default instant receipts under a sentinel epoch (e.g. `defaultRecoveryEpoch + 1`) so `_claimDefaultedInstantWithdrawRequest` can never confuse them with finalized basis.

// test/foundry/IdleCreditVaultPostDefaultInstant.t.sol — fork of mainnet, existing harness
function testPostDefaultInstantDrainsRecoveryReserve() external {
    // buffer phase: attacker + victim deposit AA; epoch runs
    idleCDO.depositAA(10_000 * ONE_SCALE);          // attacker
    // ... victim deposits, startEpoch, borrower defaults via stopEpoch shortfall
    _vault.stopEpoch(0, 1);                          // manager, honest
    // recovery finalized: defaultRecoveryReserve = R, price = p < RECOVERY_FULL
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);

    uint256 reserveBefore = _vault.defaultRecoveryReserve();

    // Attacker requests instant withdraw AFTER finalization (unprivileged)
    cdoEpoch.requestInstantWithdraw(attackAmt);      // burns attacker's tranche receipt path
    // epochNumber == defaultRecoveryEpoch -> receipt lands in the defaulted-epoch bucket
    cdoEpoch.claimInstantWithdrawRequest(attacker);

    // attacker paid attackAmt * p / RECOVERY_FULL from reserve that never counted this basis
    assertLt(_vault.defaultRecoveryReserve(), reserveBefore);
    // now a legitimate defaulted receipt holder's claim underflows/reverts
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest(victim);    // or claimWithdrawRequest victim
}
```
Expected result: the attacker's post-finalization receipt is paid at `defaultRecoveryPrice` out of `defaultRecoveryReserve`, and the victim's pre-existing claim can no longer be fully funded, demonstrating reserve insolvency caused by uncounted post-default claim basis.

    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
