## Analog Found

### Title
Division-before-multiplication in `jovian_da_footprint` underestimates the DA footprint resource-metering value - (File: `crates/common/l1-fees/src/params.rs`)

### Summary
The reported bug is a classic "hidden division before multiplication" precision-loss pattern in Solidity integer math. The Base repo contains the same anti-pattern in `L1FeeParams::jovian_da_footprint`, which computes the DA-footprint gas used for Jovian's per-block resource-metering (DA footprint block limit).

### Finding Description
`tx_estimated_size_fjord` returns the FastLZ-estimated compressed transaction size **scaled by 1e6** (documented explicitly: "Calculates the estimated compressed transaction size in bytes, scaled by `1e6`"). [1](#0-0) 

`jovian_da_footprint` is supposed to unscale this value (divide by `1e6`) and then multiply by the configured `da_footprint_gas_scalar` to get the metered gas cost. Instead, it performs the division **first**, then the multiplication:
```rust
pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
    let Some(scalar) = self.da_footprint_gas_scalar else {
        return 0;
    };
    U256::from(tx_estimated_size_fjord(input))
        .wrapping_div(U256::from(1_000_000u64))
        .saturating_mul(scalar)
        .saturating_to::<u64>()
}
``` [2](#0-1) 

Because Solidity/Rust integer division truncates, `wrapping_div(1_000_000)` floors the estimated size down to the nearest whole "compressed byte" *before* the multiplication by `scalar` is applied. Any fractional remainder (up to just under 1 full byte, i.e. up to `999_999/1_000_000` of a unit) is discarded and never contributes to the final gas value, exactly mirroring the reported `Bonding.sol` defect where `k` was divided by `assetRate` before being multiplied back up, losing precision that a "multiply-then-divide" ordering would have preserved. This is the same class of hidden-division-before-multiplication rounding bug, just applied to `da_footprint_gas_scalar` instead of `assetRate`.

This value feeds directly into `da_footprint_used`, the block executor's per-block resource-metering counter for Jovian's [DA footprint block limit](https://github.com/ethereum-optimism/specs/blob/main/specs/protocol/jovian/exec-engine.md#da-footprint-block-limit): [3](#0-2) 

The metering computation is reached from `calculate_tx_l1_cost`/block execution and payload building code paths, and is exercised for every transaction included in a Jovian block by an unprivileged transaction sender's calldata size and the (attacker-influenced) `da_footprint_gas_scalar` set via L1 attributes.

### Impact Explanation
`da_footprint_used` is the resource-metering value used to enforce the protocol's DA-footprint block limit — a hard cap analogous to the gas limit, meant to bound how much L1 data-availability budget a block consumes. Systematically under-computing this value (by up to ~1_000_000 scaled units, i.e. up to nearly 1 unscaled byte, times `scalar` per transaction) means the block builder/executor can pack transactions whose *true* DA footprint exceeds the intended limit while the metered value stays under it. This is a resource-metering correctness bug in a consensus-relevant, protocol-defined limit (part of block building and resource metering, explicitly in-scope), and can permit an attacker-controlled sequence of transactions with sizes chosen to maximize truncation loss to force blocks whose actual DA footprint exceeds the protocol-intended cap.

### Likelihood Explanation
The precision loss triggers deterministically on essentially every transaction whose FastLZ-estimated compressed size (scaled by 1e6) is not an exact multiple of `1_000_000`, which in practice is virtually all transactions. A single unprivileged transaction sender fully controls the calldata (and thus the FastLZ-estimated size) that feeds this computation, so the bug is trivially and repeatedly reachable without any special privilege.

### Recommendation
Reorder the arithmetic to multiply before dividing, matching the correct pattern already used elsewhere in the same file (e.g. `calculate_tx_l1_cost_fjord`, which multiplies by `l1_fee_scaled` before dividing by `1_000_000_000_000`):
```rust
pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
    let Some(scalar) = self.da_footprint_gas_scalar else {
        return 0;
    };
    U256::from(tx_estimated_size_fjord(input))
        .saturating_mul(scalar)
        .wrapping_div(U256::from(1_000_000u64))
        .saturating_to::<u64>()
}
```

### Proof of Concept
Given `tx_estimated_size_fjord(input) = 100_999_999` (just under the next whole-byte boundary) and `da_footprint_gas_scalar = 400`:

- Current implementation: `100_999_999 / 1_000_000 = 100`, then `100 * 400 = 40_000`.
- Correct implementation: `100_999_999 * 400 = 40_399_999_600`, then `/ 1_000_000 = 40_399` (rounded down only at the very end).

The current implementation undercounts the metered DA footprint by `399` gas-equivalent units for this single transaction — reproducible and maximized by any attacker who crafts calldata whose FastLZ-estimated size sits just below a 1e6 boundary, repeated across many transactions in a block to widen the aggregate gap between metered `da_footprint_used` and the true DA footprint. /// Calculate the estimated compressed transaction size in bytes, scaled by 1e6.
/// This value is computed based on the following formula:

pub fn tx_estimated_size_fjord(input: &[u8]) -> u64 {
    let fastlz_size = flz_compress_len(input) as u64;

    fastlz_size
        .saturating_mul(L1_COST_FASTLZ_COEF)

}
