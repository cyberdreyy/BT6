Based on the investigation, I found a closely analogous pattern in the WebAuthn (2FA/MFA) registration flow, which mirrors the `CpiContextAccount` issue: a shared, mutable "context" object that persists across two separate requests, keyed by a value that isn't bound to the specific session/request that created it, allowing a mismatched actor to complete the flow with injected data.

### Title
WebAuthn Registration Challenge Context Lacks Per-Session Binding, Enabling Credential Injection - (File: core/sessions/webauthn.go)

### Summary
`WebAuthnSessionStore` stores in-progress WebAuthn registration challenges in a global map keyed only by `user.Email + "-registration"`, with no binding to the specific session, browser, or request that initiated the challenge. [1](#0-0)  Just as `CpiContextAccount` is a shared context spanning multiple transactions without access control, allowing a different proof to be injected into it, this `inProgressRegistrations` context spans the `BeginRegistration` → `FinishRegistration` request pair without any control tying the two requests together beyond the user's email. [2](#0-1) 

### Finding Description
`BeginRegistration` and `FinishRegistration` in `core/web/webauthn_controller.go` both require an authenticated user (via `auth.GetAuthenticatedUser`), and use that user's email to store/retrieve the registration challenge. [3](#0-2) [4](#0-3)  The challenge (`sessionData`) is written and later consumed via `store.put`/`store.take`, keyed solely by `user.Email + "-registration"` — not by session ID, CSRF token, or any nonce unique to the specific HTTP request/browser that started the flow. [5](#0-4) [6](#0-5) 

Because the context object is identified purely by the victim's identity rather than by an unguessable, request-scoped token, any request that carries the victim's session cookie (e.g., forced via CSRF, since cookie-based session auth is used per `AuthenticateBySession`) [7](#0-6)  can complete a `FinishRegistration` call using attacker-controlled WebAuthn response data (`c.Request`) against whatever challenge is currently stored for that email — regardless of which browser/session actually initiated `BeginRegistration`. This is structurally the same weakness as the audited `CpiContextAccount` bug: a shared context spanning multiple transactions/requests, resettable and fillable by whichever party gets there next, without verifying that the same actor/session owns both ends of the flow.

### Impact Explanation
If an attacker can trigger both steps of the flow riding on a victim admin's authenticated session (e.g., via CSRF, given no visible CSRF-token enforcement was found for these routes), the attacker's own WebAuthn credential (security key) could be registered as a valid persistent 2FA method on the victim's account via `AddCredentialToUser`. [8](#0-7)  This would grant the attacker a durable second factor for the victim's admin account, enabling account takeover / persistence — a concrete authentication/role bypass outcome.

### Likelihood Explanation
Exploitation requires the attacker to force two authenticated cross-site requests through a logged-in admin's browser (a CSRF-style scenario). I was not able to confirm from the available index whether CSRF protections or strict `SameSite` cookie settings are enforced by default for these endpoints — I found a `SameSite`-related reference in `core/services/chainlink/config_web_server.go` but could not verify its configured value/default within the tool budget available. This is a material uncertainty that affects likelihood and should be verified directly in a full checkout of the repo.

### Recommendation
Bind the in-progress WebAuthn registration/authentication challenge to a value unique to the initiating request/session (e.g., store it in the user's server-side session alongside the session ID, or generate and validate a per-flow random state token that must be echoed back in `FinishRegistration`), rather than keying solely by `user.Email`. Additionally, confirm and enforce CSRF protection (e.g., `SameSite=Strict`/`Lax` cookies plus anti-CSRF tokens) on all state-changing session/auth endpoints, including `/webauthn/begin` and `/webauthn/finish`. [9](#0-8) 

### Proof of Concept
1. Attacker begins their own WebAuthn registration challenge is not required; instead, the attacker crafts a hidden auto-submitting form/page that, when visited by an authenticated victim admin, issues an XHR to `POST /webauthn/begin` (using the victim's ambient session cookie) to create a fresh registration challenge for the victim's email in the shared `inProgressRegistrations` map.
2. The same malicious page immediately issues a second request `POST /webauthn/finish` with a WebAuthn attestation response generated using the attacker's own security key, again riding the victim's session cookie.
3. `FinishWebAuthnRegistration` looks up the challenge purely by `user.Email + "-registration"` — matching the one created in step 1 — and validates the attacker's attestation against it, succeeding because nothing ties the challenge to a specific session. [10](#0-9) 
4. The attacker's key is persisted as a valid credential for the victim's account via `AddCredentialToUser`, giving the attacker a working 2FA credential for the victim's admin account. [11](#0-10) 

**Note on confidence**: This finding is offered as the closest structural analog to the reported `CpiContextAccount` issue found via the available index (shared cross-request context lacking per-actor/session access control). I could not fully verify CSRF-protection posture for these specific routes within the tool budget — a full checkout via a Devin session would be needed to confirm cookie `SameSite` defaults and any CSRF middleware before treating this as a confirmed exploit path.

	if err != nil {
		return nil, err
	}

		credCreationOpts.CredentialExcludeList = waUser.CredentialExcludeList()
	}

	if err != nil {
		return nil, err
	}

	return options, nil
}

// WebAuthnSessionStore is a wrapper around an in memory key value store which provides some helper
// methods related to webauthn operations.
type WebAuthnSessionStore struct {
	inProgressRegistrations map[string]string
	mu                      sync.Mutex
}

// NewWebAuthnSessionStore returns a new session store.
func NewWebAuthnSessionStore() *WebAuthnSessionStore {
	return &WebAuthnSessionStore{
		inProgressRegistrations: map[string]string{},
	}
}

// SaveWebauthnSession marshals and saves the webauthn data to the provided
// key given the request and responsewriter
func (store *WebAuthnSessionStore) SaveWebauthnSession(key string, data *webauthn.SessionData) error {
	marshaledData, err := json.Marshal(data)
	if err != nil {
		return err
	}
	store.put(key, string(marshaledData))
	return nil
}

func (store *WebAuthnSessionStore) put(key, val string) {
	store.mu.Lock()
	defer store.mu.Unlock()
	store.inProgressRegistrations[key] = val
}

// take returns the val for key, as well as removing it.
func (store *WebAuthnSessionStore) take(key string) (val string, ok bool) {
	store.mu.Lock()
	defer store.mu.Unlock()
	val, ok = store.inProgressRegistrations[key]
	if ok {
		delete(store.inProgressRegistrations, key)
	}
	return
}

func (w *WebAuthnController) BeginRegistration(c *gin.Context) {
	ctx := c.Request.Context()
	user, ok := auth.GetAuthenticatedUser(c)
	if !ok {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("failed to obtain current user from context"))
		return
	}

	orm := w.App.AuthenticationProvider()
	uwas, err := orm.GetUserWebAuthn(ctx, user.Email)
	if err != nil {
		w.App.GetLogger().Errorf("failed to obtain current user MFA tokens: error in GetUserWebAuthn: %+v", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	webAuthnConfig := w.App.GetWebAuthnConfiguration()

	options, err := w.inProgressRegistrationsStore.BeginWebAuthnRegistration(*user, uwas, webAuthnConfig)
	if err != nil {
		w.App.GetLogger().Errorf("error in BeginWebAuthnRegistration: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	optionsp := presenters.NewRegistrationSettings(*options)

	jsonAPIResponse(c, optionsp, "settings")
}

func (w *WebAuthnController) FinishRegistration(c *gin.Context) {
	ctx := c.Request.Context()
	user, ok := auth.GetAuthenticatedUser(c)
	if !ok {
		logger.Sugared(w.App.GetLogger()).AssumptionViolationf("failed to obtain current user from context")
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	orm := w.App.AuthenticationProvider()
	uwas, err := orm.GetUserWebAuthn(ctx, user.Email)
	if err != nil {
		w.App.GetLogger().Errorf("failed to obtain current user MFA tokens: error in GetUserWebAuthn: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	webAuthnConfig := w.App.GetWebAuthnConfiguration()

	credential, err := w.inProgressRegistrationsStore.FinishWebAuthnRegistration(*user, uwas, c.Request, webAuthnConfig)
	if err != nil {
		w.App.GetLogger().Errorf("error in FinishWebAuthnRegistration: %s", err)
		jsonAPIError(c, http.StatusBadRequest, errors.New("registration was unsuccessful"))
		return
	}

	if sessions.AddCredentialToUser(ctx, w.App.AuthenticationProvider(), user.Email, credential) != nil {
		w.App.GetLogger().Errorf("Could not save WebAuthn credential to DB for user: %s", user.Email)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

// AuthenticateBySession authenticates the request by the session cookie.

// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
