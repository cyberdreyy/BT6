## Title
Stale confirmations from removed multisig members count toward execution threshold, allowing requests to execute below the current quorum - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the multisig contract only purges requests *authored by* the removed member; it never scrubs that member's confirmation entries from other requests they had previously confirmed as a co-signer. Because `confirm` counts raw entries in the `confirmations` set against `num_confirmations` without checking that each entry still belongs to a current member, a request can execute using confirmations that include one or more accounts/keys that have since been removed from the multisig, effectively executing a request approved by fewer live members than the configured threshold.

### Finding Description
`confirm` determines whether to execute a request purely by counting stored confirmation entries: [1](#0-0) 

The counted set, `self.confirmations.get(&request_id)`, is a `HashSet<String>` of member identifiers that were valid at the time they confirmed. When a member is removed via `DeleteMember`, `delete_member` only cleans up requests where that member was the *creator* (`r.member == member`); it does not scan `self.confirmations` for entries recorded elsewhere by the removed member: [2](#0-1) 

So if member `A` confirms request `X` (created by member `B`), and `A` is later removed by a legitimate `DeleteMember` governance action (which only checks that the *remaining* member count is still `>= num_confirmations`, not that outstanding confirmations remain valid): [3](#0-2) 

`A`'s stale confirmation on `X` is never removed. Any subsequent confirmations by current members on `X` are added to the same set that still contains `A`'s entry, so `confirmations.len() as u32 + 1 >= self.num_confirmations` can become true while the number of *currently valid* members who confirmed is one (or more) short of `num_confirmations`.

The equality this breaks is:
`confirmations recorded == confirmations from members currently in `self.members``
After a `DeleteMember`, this no longer holds for any request that a removed member had previously confirmed but that was not yet executed.

### Impact Explanation
This directly matches the "Critical" impact category of "a multisig request executed below threshold." An attacker (or a group of only `num_confirmations - 1` current members) can get a `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` request executed without reaching the actual configured quorum among live members, because a leftover confirmation from a member who no longer has authority is still tallied. This can be used to move NEAR out of the multisig account, add an unauthorized full-access key, or deploy new contract code, all while bypassing the intended K-of-N governance guarantee.

### Likelihood Explanation
The scenario requires: (1) a pending, unconfirmed-to-completion request that has at least one confirmation, and (2) a subsequent, otherwise-legitimate `DeleteMember` request that removes the confirming member while keeping `members.len() - 1 >= num_confirmations`. Both conditions are ordinary, expected multisig operations (member rotation is a normal governance action), so no special privilege beyond normal member turnover is needed for the stale confirmation to remain exploitable — it just requires that at least one active request is outstanding when a confirming member is later removed, which is a realistic operational sequence for any long-lived multisig with periodic membership changes.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests authored by that member) and strip the removed member's identifier from every confirmation set, or alternatively re-validate every entry in a `confirmations` set against `self.members` inside `confirm` before counting them toward the threshold.

### Proof of Concept
1. Deploy multisig with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `B` calls `add_request` to create request `X` (e.g., `Transfer`). `A` calls `confirm(X)` → `confirmations = {A}` (1 of 3, not yet executed).
3. A separate request `Y` (`DeleteMember { member: A }`) is created and confirmed by `B, C, D` (3 confirmations, satisfies quorum, and `members.len()-1 == 3 >= num_confirmations == 3` so `delete_member` succeeds). `A` is removed; `members = {B, C, D}`. Request `X`'s confirmation set still contains `A` because `delete_member` only purged requests created by `A`, not `A`'s confirmation entries elsewhere.
4. `C` calls `confirm(X)` → `confirmations = {A, C}` (2).
5. `D` calls `confirm(X)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → request `X` executes.
6. Result: request `X` executed with only 2 currently-valid confirmations (`C`, `D`) plus one stale, no-longer-authorized confirmation (`A`), bypassing the 3-of-4 threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
