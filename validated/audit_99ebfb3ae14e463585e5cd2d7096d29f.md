### Title
Unbounded, unmetered precompile signature loop lets an unfunded/failing transaction burn validator CPU disproportionate to any fee charged - ([File: precompiles/src/secp256k1.rs], [File: precompiles/src/secp256r1.rs], [File: precompiles/src/lib.rs])

### Summary
The external report describes a caller-supplied array (`shortHintArray`) that is looped over without a length/validity check, letting an attacker inflate gas costs paid by a third party (the TAPP) far beyond what is actually charged/expected. The closest reachable analog in Agave is the secp256k1/secp256r1 precompile `verify()` loops: the iteration count is taken directly from attacker-controlled instruction data (`count = data[0]`, up to 255), and for each iteration the validator performs an expensive elliptic-curve signature recovery/verification, driven by `verify_if_precompile` in `precompiles/src/lib.rs`, before the transaction's fee payer, compute budget, or execution outcome is finalized.

### Finding Description
`verify` in `precompiles/src/secp256k1.rs` reads an attacker-controlled `count` byte and loops `for i in 0..count { ... libsecp256k1::recover(...) ... }` [1](#0-0) [2](#0-1) . The equivalent secp256r1 path performs an even heavier OpenSSL ECDSA verification per iteration inside a similar unconditioned loop driven by `num_signatures` [3](#0-2) .

This verification is invoked generically via `verify_if_precompile`, which builds an `instruction_datas` vector from *all* instructions in the transaction and calls the matched precompile's `verify_fn` [4](#0-3) . The cost model separately estimates the signature cost purely from the same attacker-supplied count byte (`instruction.data.first()`), multiplying by a fixed per-signature constant (`SECP256K1_VERIFY_COST`, `SECP256R1_VERIFY_COST`) [5](#0-4) [6](#0-5) . Because the "hint"/count value is self-reported by the attacker and the CPU-expensive verification work (elliptic curve recovery/point operations) happens as part of transaction sanitization/verification — a step that can run before the fee payer's balance is validated and before the transaction is guaranteed to execute or even be included — a validator can be made to spend real, unbounded-per-instruction CPU cycles on transactions that will ultimately fail (e.g., bad signature, insufficient fee payer funds, or duplicate/garbage data), analogous to how the DeFi bug allowed unbounded, attacker-chosen loop iterations to consume resources paid for by a party other than the requester.

### Impact Explanation
Precompile signature counts are bounded to `u8::MAX` (255) per instruction, and a transaction may contain multiple such instructions up to the transaction size limit. Each verification (especially secp256r1's OpenSSL ECDSA path, or repeated secp256k1 recoveries) is CPU-intensive relative to normal instruction processing. Submitting many such transactions (via TPU/QUIC ingest) that are cheap to construct but expensive to verify — and that are designed to ultimately fail sanitization/fee-payer checks — allows an attacker to impose asymmetric CPU cost on validators during sigverify/precompile-verification stages relative to the fees actually collectable, which is the same "attacker forces unmetered, disproportionate work performed by someone else" bug class as the reported TAPP-drain issue. This is a resource-exhaustion/DoS class issue rather than a direct fund-drain, since Agave's TAPP-equivalent (fee payer paying gas) enforces fee payment before *execution*, but the precompile CPU work occurs during verification, ahead of that enforcement point.

### Likelihood Explanation
Reachable directly from an ordinary, unprivileged client: any transaction containing a secp256k1 or secp256r1 program instruction with a crafted count byte and instruction offsets is normal, permitted transaction construction; the loop bound is entirely attacker-controlled data, not derived from any privileged or validated source. No special access is required beyond submitting transactions through the normal ingest path.

### Recommendation
- Charge/verify compute costs for precompile signature verification prior to, or consistently gated with, doing the actual expensive cryptographic work, and ensure the reported `count`/`num_signatures` used for cost estimation cannot diverge from the actual work performed.
- Ensure precompile verification (particularly the CPU-heavy secp256r1 OpenSSL path) cannot be triggered for transactions whose fee payer would ultimately fail validation, or reduce/rate-limit per-packet precompile verification cost at the sigverify/ingest stage independent of final execution outcome.
- Confirm cost-model accounting for precompile signatures (`get_signature_cost`) is enforced as an early admission gate (e.g., against `MAX_BLOCK_UNITS`/per-packet limits) before the expensive cryptographic loop executes, not only after.

### Proof of Concept
Not independently verifiable within the scope of this analysis — the exact ordering of precompile verification relative to fee-payer/compute-budget validation in the ingest/banking pipeline (e.g., `bank.verify_transaction` call sites in `runtime/src/bank.rs`) could not be fully traced within tool budget. This should be confirmed by tracing `Bank::verify_transaction` / `TransactionVerificationMode::HashAndVerifyPrecompiles` call sites in `runtime/src/bank.rs` and the sigverify pipeline (`core/src/sigverify_stage.rs`) to determine precisely when precompile `verify()` executes relative to fee-payer balance checks, and by benchmarking worst-case secp256r1/secp256k1 verify() loops with maximal signature counts across multiple instructions in a single transaction.

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
