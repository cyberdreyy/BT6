### Title
Stale confirmations from a removed multisig member remain counted toward the approval threshold, allowing execution with fewer live-member approvals than required - (File: multisig2/src/lib.rs)

### Summary
This is the closest in-scope analog to the HackerOne report: a "banned" identity (here, a removed multisig `member`) retains functional privilege (a counted confirmation) after its access is supposed to be revoked, because the revocation path only scrubs *some* of that identity's state, not all of it.

### Finding Description
`MultiSigContract::confirm` (`multisig2/src/lib.rs:292-315`) counts a request as approved purely by the size of the `HashSet<String>` stored in `self.confirmations` for that `request_id`: [1](#0-0) 
It never re-validates that the account IDs/public keys already present in that set are still active `members` — it only validates the *caller* of `confirm`/`delete_request` via `assert_valid_request`: [2](#0-1) 

When a member is removed via `DeleteMember` → `delete_member`, the cleanup only removes:
1. `self.members` entry for that member,
2. requests that member itself *authored* (filtered by `r.member == member`),
3. that member's `num_requests_pk` counter. [3](#0-2) 

It does **not** scan `self.confirmations` to strip that member's prior confirmation entries from *other*, still-pending requests they did not author but had already confirmed. Those stale confirmations remain in the `HashSet<String>` and continue to count toward `num_confirmations` in the `confirm` function shown above.

### Impact Explanation
This breaks the equality that should hold for every executed request: `confirmations counted == confirmations from currently-live members`. Concretely:
- Members A, B, C with `num_confirmations = 2`.
- A calls `add_request` for request R (transfer, add key, etc.) without confirming.
- B calls `confirm(R)` → `confirmations = {B}` (1 < 2, not yet executed).
- Separately, the multisig (via a normal, properly-threshold-confirmed `DeleteMember` request) removes B — e.g., B is compromised/banned. `delete_member` clears requests authored by B, but request R (authored by A) is untouched, so `confirmations = {B}` for R survives.
- C, now the only other live member besides A, calls `confirm(R)` → `confirmations = {B, C}`, size 2 ≥ `num_confirmations` (2) → `execute_request` runs.

R executes with only one currently-live member (C) actually having approved it post-removal, while the multisig's own governance believed 2-of-N live members were required. This is exactly the "multisig request executed below threshold" impact called out as Critical: a `Transfer`, `AddKey`, `FunctionCall`, or `DeployContract` action can move funds or grant access with fewer live authorizations than the configured `num_confirmations`.

### Likelihood Explanation
No privileged/foundation action, redeploy, or victim key is required beyond the multisig's own normal governance flow (member removal, which is a standard, expected operation for banning a compromised or departing member) combined with an already-pending unconfirmed-but-partially-confirmed request — a realistic and easily reproducible sequence of ordinary calls (`add_request`, `confirm`, `DeleteMember` request, `confirm`).

### Recommendation
When executing `DeleteMember`, iterate over `self.confirmations` for all pending `requests` (not only ones authored by the removed member) and remove the deleted member's entry from each confirmation set, decrementing/re-evaluating pending approval counts accordingly. Alternatively, validate live membership of each entry in the confirmation set at `confirm`/execution time rather than trusting historically recorded strings.

### Proof of Concept
1. Deploy multisig with members `[A, B, C]`, `num_confirmations = 2`.
2. `A.add_request(R)` (e.g., `Transfer` to attacker-controlled or arbitrary account).
3. `B.confirm(R)` → `confirmations[R] = {B}`.
4. Multisig properly executes a `DeleteMember{member: B}` request (2-of-3 confirmed by A and C), removing B from `members`; `delete_member` does not touch `confirmations[R]`.
5. `C.confirm(R)` → `confirmations[R] = {B, C}`, length 2 ≥ `num_confirmations` → `execute_request(R)` runs the `Transfer`, executed with only C (1 live member) actually approving after B's removal.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Prevents access to calling requests and make sure request_id is valid - used in delete and confirm
    fn assert_valid_request(&mut self, request_id: RequestId) {
        // request must come from key added to contract account
        assert(
            self.current_member().is_some(),
            "Caller (predecessor or signer) is not a member of this multisig",
        );
        // request must exist
        assert(
            self.requests.get(&request_id).is_some(),
            "No such request: either wrong number or already confirmed",
        );
        // request must have
        assert(
            self.confirmations.get(&request_id).is_some(),
            "Internal error: confirmations mismatch requests",
        );
    }
