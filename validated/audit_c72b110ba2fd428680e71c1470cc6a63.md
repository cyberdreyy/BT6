### Title
Malformed slot ID in a single StackerDB signer message crashes the `StackerDBListener`, wedging block-signature collection for all subsequent blocks - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::run()` processes a batch of signer messages delivered in one StackerDB event and, for each message, looks up the sending slot's registration in `self.signer_entries`. If any single message's `slot_id` is not present in that map, the function immediately returns `Err(...)`, terminating the entire listener loop rather than skipping the one bad entry. This is structurally the same defect as the reported `PrimeStrategy.withdraw()` bug: one failing item inside a loop over independent items propagates an unhandled error that kills the whole operation, rather than being isolated.

### Finding Description
`StackerDBListener::run()` is a `loop { ... }` that repeatedly receives `StackerDBChunksEvent`s and, for signer-message events, iterates over every `(slot_id, _pk, message)` triple in the batch: [1](#0-0) 

For each message, it does:
```rust
let Some(signer_entry) = &self.signer_entries.get(&slot_id) else {
    return Err(NakamotoNodeError::SignerSignatureError(
        "Signer entry not found".into(),
    ));
};
```
This `return Err(...)` returns out of `run()` itself (the `loop` is the body of `run()`, not a helper called with `?`), so a single unresolved `slot_id` in a single message inside a batch that may contain many otherwise-valid messages from many signers aborts processing of the whole batch and exits the listener's event loop entirely — the equivalent of the strategy loop in the analog report reverting the entire withdrawal because one strategy failed.

The `slot_id`/`signer_entries` mismatch is reachable, not merely theoretical: `signer_entries` is built once from the registered reward-cycle signer set and keyed by slot id, while `messages` are decoded per-chunk from `modified_slots` on every event. The `signer_set != self.signer_set` parity filter only rejects messages from the *other* signer set's contract; it does nothing to guarantee that every slot id physically present in the StackerDB replica falls inside the range of slots the listener's `signer_entries` map actually has entries for (e.g., during a reward-cycle rotation window, a stale/late chunk write, or a slot assignment/signer-count discrepancy between the `InitialChunksLoader`'s view and the live registration). Any of these ordinary, adversary-influenceable timing conditions (a signer or gossip peer writing to StackerDB around a reward-cycle boundary) can produce a slot id absent from `self.signer_entries`, and the miner's own code path has no defensive skip-and-continue for that one entry — it kills the listener for every future block in the tenure.

### Impact Explanation
Because `run()` returns instead of `continue`-ing the loop on this error, the `StackerDBListener` thread exits. This is the miner-side channel that aggregates signer `BlockResponse::Accepted`/`Rejected` and `BlockPreCommit`/`StateMachineUpdate` messages used by `SigningCoordinator`/`signer_coordinator.rs` to compute `total_weight_approved`/`total_weight_rejected` against `weight_threshold`. Once the listener has died, no further signer votes for any subsequent block proposal are observed by the miner, so the miner can never again accumulate enough weight to conclude a block is signed — a liveness wedge for the mining/signing pipeline that matches the "signer wedged into never signing valid blocks ... acting on a stale reward set/threshold" category, since it stems from exactly the coordinator/signer-set machinery in scope (`stacks-node/src/nakamoto_node/signer_coordinator.rs`, `stackerdb_listener.rs`).

### Likelihood Explanation
The trigger does not require compromising a majority of signers or forging any signature — it only requires one message in a batch to arrive tagged with a `slot_id` the listener's `signer_entries` snapshot does not contain an entry for. This is plausible around any signer-set/reward-cycle transition, or wherever `InitialChunksLoader`'s `signer_count` and the live `signer_entries` map disagree, both of which are reachable from ordinary gossip/relay activity rather than needing majority collusion. However, I was not able to fully trace every path that populates `self.signer_entries` versus the exact set of slot ids the running StackerDB replica can emit chunks for within the scope of this review, so the precise reachability window (how often/easily a mismatched slot id can appear) is not fully confirmed.

### Recommendation
Replace the `return Err(...)` inside the per-message loop with a `continue` (skip that one malformed/unregistered-slot message and log a warning), so a single bad entry cannot terminate the listener for the entire batch or tenure. Apply the same treatment to the other early `return Err(...)` inside this loop (`StacksPublicKey::from_slice` failure) for consistency.

### Proof of Concept
1. A `StackerDBChunksEvent` for the signers contract arrives at the node containing multiple modified slots, one of which corresponds to a `slot_id` not present in `self.signer_entries` (e.g., because it was written just before/after a reward-cycle-boundary signer-set refresh, or the chunk is from a stale slot no longer tracked).
2. `StackerDBListener::run()` iterates the batch; on reaching that entry, `self.signer_entries.get(&slot_id)` is `None`.
3. `run()` executes `return Err(NakamotoNodeError::SignerSignatureError(...))`, exiting the loop and the thread.
4. All other, otherwise-valid messages in that same batch (and any future batches) are never processed; the miner stops receiving signer acceptances/rejections for the remainder of the run, freezing block-signature aggregation network-wide until the node/thread is manually restarted.     pub fn run(&mut self) -> Result<(), NakamotoNodeError> {
        info!("StackerDBListener: Starting up");

        let Some(receiver) = &self.receiver else {
            return Err(NakamotoNodeError::SigningCoordinatorFailure(
                "StackerDBListener: Failed to obtain the StackerDB event receiver".into(),
            ));
        };

        loop {
            // was the node asked to stop?
            if !self.node_keep_running.load(Ordering::SeqCst) {
                info!("StackerDBListener: received node exit request. Aborting");
                return Ok(());
            }

            // was the listener asked to stop?
            if !self.keep_running.load(Ordering::SeqCst) {
                info!("StackerDBListener: received listener exit request. Aborting");
                return Ok(());
            }

            let event = match receiver.recv_timeout(EVENT_RECEIVER_POLL) {
                Ok(event) => event,
                Err(std::sync::mpsc::RecvTimeoutError::Timeout) => {
                    debug!("StackerDBListener: No StackerDB event received. Checking flags and polling again.");
                    continue;
                }
                Err(std::sync::mpsc::RecvTimeoutError::Disconnected) => {
                    warn!("StackerDBListener: StackerDB event receiver disconnected");
                    return Err(NakamotoNodeError::SigningCoordinatorFailure(
                        "StackerDB event receiver disconnected".into(),
                    ));
                }
            };
