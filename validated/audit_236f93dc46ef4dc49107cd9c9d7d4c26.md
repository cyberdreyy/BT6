### Title
Stale confirmations from removed multisig members allow request execution below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set against `num_confirmations` without verifying that each confirming identity is still a current member. `delete_member` only purges requests *created by* the removed member; it never scans `confirmations` sets of other pending requests to strip entries belonging to the removed member. A member's earlier confirmation therefore continues to count toward the threshold on any request they didn't create, even after they are removed from `members`.

### Finding Description
`confirm()` executes the request once the stored confirmation count reaches `num_confirmations`: [1](#0-0) 

`delete_member()` only cleans up requests whose *creator* (`r.member`) equals the removed member, and removes that member from `self.members` and `num_requests_pk`. It does not iterate `self.confirmations` to strip the removed member's entries from confirmation sets of requests created by other members: [2](#0-1) 

The binding that should hold is:
`count(confirmations[request_id] ∩ current members) >= num_confirmations` before executing a request.

The actual code enforces only:
`count(confirmations[request_id]) >= num_confirmations`

Since `confirmations[request_id]` is a plain `HashSet<String>` populated at confirmation time and never revalidated against the live `members` set, a confirmation cast by an account/key that is later removed via a `DeleteMember` request still counts. This is the direct analog to the H-01 report's root cause: a critical trust decision (transfer/execution) is made from state (a recorded "success"/"confirmed" flag) that is not re-validated against present ground truth (still a member vs removed), exactly like relying on a boolean the receiving party doesn't actually enforce.

### Impact Explanation
This breaks the multisig's core custody guarantee: "a request requires `num_confirmations` confirmations from members currently trusted with signing power." A request (including `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc.) can be executed with fewer than `num_confirmations` *live* confirming members, because one or more confirming identities were removed (e.g., due to key compromise) after confirming but before the request reached quorum. This is exactly the Critical category "a multisig request executed below threshold" — funds or privileged actions can be pushed through by a coalition smaller than the configured security threshold.

### Likelihood Explanation
The scenario requires only normal, expected multisig operations, no code changes or unusual conditions:
1. Any member confirms a pending request (routine).
2. That member is later removed (the very security response the `DeleteMember` action exists for, e.g. because their key was compromised or they are no longer trusted).
3. The pending request they confirmed remains in `requests`/`confirmations` and can still reach quorum using their stale confirmation plus fewer remaining live members.

Removing a member specifically because their key is no longer trusted is a realistic and expected operational event, making this a practically reachable path, not a theoretical one.

### Recommendation
When executing `delete_member`, iterate all entries in `self.confirmations` and remove the deleted member's string from every confirmation set (not just requests they created), and re-check whether any request's already-executed condition changes. Alternatively, validate confirmers against `self.members` inside `confirm()` before counting toward `num_confirmations`, e.g. by filtering `confirmations.iter().filter(|c| self.members.contains(...))` at check time rather than trusting the raw set size.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `B` calls `add_request(R)` where `R` is e.g. `Transfer { amount }` to an attacker-controlled receiver. `confirmations[R] = {}`.
3. `A` calls `confirm(R)` → `confirmations[R] = {A}` (len 1 < 3, not executed) — see check at [3](#0-2) .
4. `A`'s key is compromised/flagged; `B, C, D` create and confirm a `DeleteMember { member: A }` request, which executes (3/3 confirmations from currently-live members) and removes `A` from `self.members` via `delete_member` — see [4](#0-3) . Note `confirmations[R]` (`{A}`) is untouched because `R.member == B`, not `A`.
5. `C` calls `confirm(R)` → `confirmations[R] = {A, C}` (len 2 < 3, not executed).
6. `D` calls `confirm(R)` → stored `confirmations[R]` length is 2 (`A`,`C`) before insert, so `2 + 1 >= 3` is true → `execute_request(R)` runs the `Transfer`.
7. Result: `R` executed with only `C` and `D` as genuinely current members confirming (2 live confirmations), while `A`'s stale confirmation (a removed/untrusted identity) was counted to satisfy the `num_confirmations = 3` threshold — the request was executed below the intended live-member threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
