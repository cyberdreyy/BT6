## Finding: Builder Withdrawal Amount Not Capped to Available Balance Before Being Committed to the Execution Payload

### Title
Builder withdrawals can commit an execution payment larger than the builder's actual balance, creating unbacked ETH — (File: `specs/gloas/beacon-chain.md`)

### Summary
The reported GMX issue is a class of bug where a claimable amount is not properly capped/synced to actual available balance before that amount is committed to an external system, causing an accounting mismatch. The same bug class exists in the Gloas (EIP-7732) builder-withdrawal path: the `Withdrawal` object that is committed to the execution payload (and thus actually paid out by the EL to `fee_recipient`) is built from the *raw requested* `amount` in `state.builder_pending_withdrawals`, while the *actual* deduction from the builder's tracked balance in `apply_withdrawals` is silently capped with `min(withdrawal.amount, builder_balance)`.

### Finding Description
`get_builder_withdrawals` constructs the withdrawal list straight from the queue without checking or capping against the builder's current balance: [1](#0-0) 

Contrast this with `get_builders_sweep_withdrawals`, which does gate on `builder.balance > 0` and uses the live `builder.balance` as the withdrawal amount: [2](#0-1) 

Later, `apply_withdrawals` finally caps the *state* balance decrease, but only for bookkeeping inside the beacon state — it does not (and cannot) retroactively shrink the `Withdrawal.amount` value that was already placed into `payload_expected_withdrawals` / the execution payload: [3](#0-2) 

Because `process_withdrawals` must be honored 1:1 by the execution layer (per the spec's own note that any EL block "is required to honor these withdrawals"), the EL will pay the fee-recipient address the full, uncapped `withdrawal.amount`, while the consensus layer only debits `min(withdrawal.amount, builder_balance)` from `state.builders[i].balance`. The difference between the two is Gwei that is created and paid to a non-owner (the `fee_recipient`) without being backed by any validator/builder balance — this breaks the equality "amount paid by EL == amount debited from builder stake," directly matching the report's underlying bug class (a claim/payment amount computed from a stale/unsynced balance).

This is confirmed by the project's own test, which asserts this exact behavior as expected: [4](#0-3)  — a 5 ETH withdrawal request against only 1 ETH of builder balance still produces `withdrawal.amount: 5 ETH` (i.e., what will be paid via the execution payload) while `builders[0].balance` is only reduced by the available 1 ETH.

### Impact Explanation
This is Critical: it creates Gwei that is paid to a non-owner. If `state.builder_pending_withdrawals` can ever contain entries whose amounts exceed the builder's true balance (e.g., a builder is slashed, or multiple withdrawal requests are queued against the same balance and the balance is reduced between enqueue and processing, or requests are enqueued without validating the current balance at enqueue time), the EL executes payments the beacon state never actually deducted — inflating total supply and misdirecting a builder payment, matching the "builder payment ... doubled or escaped" and "Gwei created ... paid to a non-owner" Critical/High categories explicitly called out in scope.

### Likelihood Explanation
Likelihood depends on whether `state.builder_pending_withdrawals` entries are always guaranteed (by the enqueue-time validation logic, which was not available for inspection) to never exceed the builder's balance at processing time. The `get_builders_sweep_withdrawals` function's explicit `builder.balance > 0` re-check, and the very existence of the `min()` clamp in `apply_withdrawals`, both imply the spec authors anticipated that a builder's balance can be lower than a previously-queued withdrawal amount by the time it is processed (e.g., two pending withdrawals racing against the same balance, or a slashing/other balance-reducing event occurring after the request was queued but before it is swept). This strongly suggests the scenario is reachable through ordinary spec-following state transitions rather than requiring a client bug.

### Recommendation
In `get_builder_withdrawals`, cap the amount placed into the `Withdrawal` object to the builder's *current, running* balance (accounting for any prior withdrawals already added to `withdrawals` in the same call), mirroring how `get_builders_sweep_withdrawals` and `get_pending_partial_withdrawals` derive amounts from live state rather than from a stale queued value. Ensure the amount ultimately included in the execution payload can never exceed what `apply_withdrawals` will actually debit from `state.builders[i].balance`.

### Proof of Concept
1. Builder `i` has `state.builders[i].balance = 1 ETH`.
2. `state.builder_pending_withdrawals` contains one entry `{builder_index: i, amount: 5 ETH, fee_recipient: X}` (enqueued while balance was higher, or balance was subsequently reduced by another operation).
3. During `get_expected_withdrawals` → `get_builder_withdrawals`, a `Withdrawal(validator_index=i, address=X, amount=5 ETH)` is added to `payload_expected_withdrawals` with no check against `state.builders[i].balance`.
4. `apply_withdrawals` executes `state.builders[i].balance -= min(5 ETH, 1 ETH)`, leaving `balance = 0`.
5. The execution payload still commits to paying `5 ETH` to address `X` (per `payload_expected_withdrawals`), which the EL must honor — 4 ETH is paid out with no corresponding balance ever having existed in the beacon state, exactly as demonstrated by `test_builder_withdrawal_insufficient_balance` [5](#0-4) .
