### Title
Confirmations from a removed multisig member are not purged from pending requests they did not originate, allowing a request to execute below the intended confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`GovValidators::vote/cancelVote` in the external report allow an already-expelled validator's stale, back-dated voting power to count toward outcomes on active proposals. The same class of bug exists in `MultiSigContract::delete_member`: when a member is removed, only the *requests that member originated* are purged; any confirmation that member cast on a request originated by someone else remains in the `confirmations` set and continues to count toward `num_confirmations` even though that member is no longer part of `self.members`.

### Finding Description
`confirm` decides whether a request is ready to execute purely by counting the size of the `confirmations` set: `if confirmations.len() as u32 + 1 >= self.num_confirmations { ... execute_request(...) }`. [1](#0-0) 

The only place confirmations are cleaned up for a removed member is inside `delete_member`, and the cleanup is scoped to requests that member *added*, not requests they merely *confirmed*:
```
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [2](#0-1) 

`r.member` is the `MultiSigRequestWithSigner.member`, i.e. the original requester recorded by `add_request`, not the set of confirmers. [3](#0-2)  Confirmations themselves are stored independently in `self.confirmations: LookupMap<RequestId, HashSet<String>>` keyed by request id, and are appended to in `confirm` without any tie to the current membership check being performed at confirm-time vs. later revocation. [4](#0-3) 

The intended invariant is: `confirmations.len() == number of currently-live members who have confirmed`. The actual state after a `DeleteMember` action executes is: `confirmations.len() == number of confirmations ever cast (including by now-removed members), for any request they did not personally originate`. This breaks the threshold binding the same way the report's `GovValidators::vote` breaks the "current validator" binding — a party that no longer belongs to the trusted set still has its past action counted toward a live authorization decision.

### Impact Explanation
Concretely: with `num_confirmations = K` and `N` members, suppose member A creates request R (a `Transfer`, `AddKey`, or `FunctionCall` request), member B confirms it (confirmations = {A, B} via `add_request_and_confirm`/`confirm`), then the remaining members execute a `DeleteMember { member: B }` request (a separate, already-confirmed action) to remove B (e.g., because B's key was compromised or B is being expelled). `delete_member` does not touch R's confirmations because `r.member == A`, not `B`. R's `confirmations` set still contains B. Any single additional live member C now confirming R makes `confirmations.len() == 3 >= K` (if `K` = 3, say), causing `execute_request` to run a transfer/add-key/function-call/deploy action that was only ever actively approved by 2 currently-live members (A, C) plus one now-expelled member (B) — i.e. a multisig request executed below the true live threshold. This matches the "Critical" impact category of a multisig request executed below threshold, since funds can move or keys/contracts can be changed with insufficient live authorization.

### Likelihood Explanation
This does not require any privileged action beyond the normal multisig flow that the contract itself exposes: any member can call `confirm`/`add_request_and_confirm` before being removed, and `DeleteMember` is a standard, documented action of the contract. [5](#0-4)  No malicious validator, redeploy, or out-of-repo actor is needed — it triggers purely from the ordinary lifecycle of members joining/leaving while requests are pending, which is a realistic operational scenario (the report's own motivating case — expelling a compromised or departing party — is exactly this scenario).

### Recommendation
In `confirm`, validate that every entry in the request's stored `confirmations` set still corresponds to a current member of `self.members` before counting length (or actively prune confirmations from `self.confirmations` for all pending requests, not just self-originated ones, inside `delete_member`). Concretely, `delete_member` should iterate all pending requests and remove the departing member's string from every `confirmations` entry (not only from requests where `r.member == member`), and/or `confirm`/quorum-check logic should re-verify live membership of each entry in the confirmation set at the time quorum is evaluated.

### Proof of Concept
1. Deploy `MultiSigContract::new` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. A calls `add_request_and_confirm(R)` where R is `{receiver_id: current_account_id, actions: [Transfer{...}]}` → `confirmations[R] = {A}`.
3. B calls `confirm(R)` → `confirmations[R] = {A, B}` (still below threshold of 3, so it doesn't execute).
4. Separately, C and D (plus B, before removal) confirm and execute a `DeleteMember{member: B}` request — this only cleans up requests where `r.member == B` (B has none), so R's confirmations set `{A, B}` is untouched; `self.members` becomes `{A, C, D}`.
5. C calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations (3)` → `execute_request(R)` runs the `Transfer`, even though only A and C are still live members who confirmed (2 of 3 required live confirmations), with B's stale confirmation making up the count. [1](#0-0) [2](#0-1)

    /// Add request for multisig.
    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
