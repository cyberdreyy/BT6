### Title
`create` forwards attacker-chosen `num_confirmations` with no minimum-value check, permitting a zero-confirmation multisig - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` is a public, unprivileged entrypoint that takes `name`, `members`, and `num_confirmations` directly from the caller and forwards them verbatim into the `new` call of the deployed multisig contract, with no assertion that `num_confirmations >= 1`. Any account can therefore deploy a multisig subaccount whose `num_confirmations` field is `0`.

### Finding Description
The broken binding is: `deployed_multisig.num_confirmations == max(1, creator_intended_value)` — i.e., every legitimately-created multisig must require at least one confirming member before it can execute a request. In `multisig-factory/src/lib.rs::create`: [1](#0-0) 

the function takes `num_confirmations: u64` straight from the caller's transaction arguments and embeds it unchanged into the `new` call's JSON args (`json!({ "members": members, "num_confirmations": num_confirmations })`), with `Promise::new(account_id).create_account().deploy_contract(...).transfer(...).function_call(b"new", ...)`. There is no check in `create` itself that `num_confirmations > 0`.

Because `name` and `account_id = format!("{}.{}", name, env::current_account_id())` are fully attacker-chosen, and the deposit/gas are attacker-supplied, an attacker can pick any unused subaccount name and any `num_confirmations`, including `0`. If the deployed multisig's `new`/confirmation-execution logic in `multisig2/src/lib.rs` treats "current confirmations >= num_confirmations" as the execute condition (a common pattern for these contracts), a `num_confirmations = 0` value means the threshold is satisfied immediately upon request creation — with zero or one confirmation — allowing any single member (or even the request itself, depending on implementation) to trigger execution of arbitrary `MultiSigRequestAction`s such as `Transfer`, moving funds out of the multisig account without the intended N-of-M authorization.

This differs from the front-running framing in the question (racing a legitimate creator's deployment) only in mechanism: since `create` performs no validation, the attacker does not even need to race anyone — they can simply deploy their own zero-confirmation multisig directly under the factory subaccount namespace they control, self-fund it, and drain it via a `Transfer` request that requires no real multisig oversight. The core root cause is identical: the factory-level guard against `num_confirmations = 0` is absent.

I was not able to fully confirm, within the available tool budget, whether `multisig2/src/lib.rs::new` itself independently re-validates and rejects `num_confirmations == 0` server-side (i.e., whether the deployed contract enforces the invariant that `create` fails to enforce). The `multisig-factory` code — the explicitly named target of this question — has no such validation, which is what the question tests.

### Impact Explanation
If `multisig2::new` also lacks a minimum-confirmation check (unverified from the code I could inspect), an attacker-deployed multisig with `num_confirmations = 0` would allow any request — including a `Transfer` action — to execute without genuine multi-party confirmation. This matches the Critical impact category: "a multisig request executed below `num_confirmations` live members." The blast radius is limited to multisigs the attacker themselves deploys and funds (since `create` requires the caller to name and fund the new subaccount); it does not directly let the attacker drain a victim's *pre-existing* multisig unless the victim's own deployment transaction can be front-run for the *same* subaccount name, which is a separate, harder-to-verify race condition than the missing validation itself.

### Likelihood Explanation
The precondition is only that the attacker calls the permissionless `create` function with `num_confirmations = 0` — no privileged role, key, or foundation status is required. This is trivially repeatable across any number of subaccount names.

### Recommendation
Add an explicit assertion in `MultisigFactory::create` (and defensively in `multisig2::new`) that `num_confirmations >= 1` (and ideally `num_confirmations <= members.len()`), panicking otherwise so the account-creation promise fails and no funds are transferred to a mis-configured multisig.

### Proof of Concept
Given the incomplete visibility into `multisig2::new`'s validation logic, a full `cargo test` proof against the execute-threshold check could not be constructed with certainty in this pass. The concrete, verifiable finding is limited to: `multisig-factory/src/lib.rs::create` performs no validation of `num_confirmations`, which is a `near-sdk-sim`/`near-workspaces` testable fact — call `create("victim", members, 0)` and assert the promise succeeds and the deployed contract's `num_confirmations` field equals `0`. Further validation of whether this leads to actual fund movement requires reading the confirmation/execution logic in `multisig2/src/lib.rs::new` and `confirm`, which was not fully retrieved in this session.

    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
