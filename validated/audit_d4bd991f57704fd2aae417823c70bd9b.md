### Title
Missing `return` after failed email claim extraction causes fail-open login and blank-identity session creation - (`core/sessions/oidcauth/oidc.go`)

### Summary
In `handleTokenExchange`, when the ID token's `email` claim is missing or not a string, the handler logs an error and writes a `500` response but does not `return`, so execution falls through and completes the login flow anyway. This results in a persisted `oidc_sessions` row, a set session cookie, and an audit log entry all keyed on an empty `user_email`, while the server still grants the role derived from the group claims.

### Finding Description
The relevant code is:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
``` [1](#0-0) 

Unlike every other error branch in `handleTokenExchange` (e.g. state mismatch, exchange failure, verify failure, claim extraction failure, role mapping failure), which all call `return` immediately after writing the error response, this branch omits `return`. Execution therefore continues past the `!ok` check into role mapping, session persistence, and cookie issuance:
```go
role, err := oi.IDClaimsToUserRole(idClaims, ...)
...
clSession := clsessions.NewSession()
_, err = oi.ds.ExecContext(ctx,
    "INSERT INTO oidc_sessions (id, user_email, user_role, created_at) VALUES ($1, $2, $3, now())",
    clSession.ID, strings.ToLower(email), role,
)
...
oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": email})
ginSession.Set(webauth.SessionIDKey, clSession.ID)
err = ginSession.Save()
...
c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})
``` [2](#0-1) 

Because `email` remains `""` (the zero value from the failed type assertion), the row inserted into `oidc_sessions` has `user_email = ''`. The role, however, is still correctly derived from the separate `idClaims` group claim, so a fully valid, working session cookie mapped to the user's real (or attacker-influenced) role is issued despite the handler having detected and reported a failure condition.

This blank-identity session is functional: `AuthorizedUserWithSession` looks sessions up purely by the random `sessionID`, so the empty email does not prevent authentication. [3](#0-2) 

The blank email does, however, poison the account-identity model used elsewhere: `ClearNonCurrentSessions` resolves the session's `user_email` and deletes every other `oidc_sessions` row sharing that same email:
```go
func (oi *oidcAuthenticator) ClearNonCurrentSessions(ctx context.Context, sessionID string) error {
	var email string
	if err := oi.ds.GetContext(ctx, &email, "SELECT user_email FROM oidc_sessions WHERE id = $1", sessionID); err != nil {
		return err
	}
	_, err := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE lower(user_email) = lower($1) AND id != $2", email, sessionID)
	return err
}
``` [4](#0-3) 

If any two authenticated users independently trip this bug (e.g. logging in via an OIDC identity whose token omits the `email` claim, which is plausible for service/machine accounts or providers where `email` is not always populated even with the `email` scope requested), both end up with `user_email = ''`. Any one of them invoking the "clear other sessions" flow will then delete the session belonging to the *other*, unrelated user — an unauthenticated/low-privileged actor forcibly terminating another authenticated user's session, which they have no authorization to affect. The response corruption (`c.String` followed later by `c.JSON`, both attempting to write the status/body) is a secondary symptom confirming the code did not intend to continue but does so anyway.

### Impact Explanation
This is a fail-open authentication/session-hygiene bug: an error path meant to abort the login instead silently completes it, producing a live, cookie-backed session bound to an empty subject identity. The audit trail (`audit.AuthLoginSuccessNo2FA`) is corrupted with an unidentifiable `email: ""`, breaking accountability. Combined with `ClearNonCurrentSessions`, this allows a low-privileged authenticated party (any user whose account trips the same missing-`email`-claim condition) to unilaterally terminate another user's active session — an unauthorized action against another user's session/account state performed without any role check tying the two identities together. This falls under Chainlink's "Authentication/Session Management" and "Broken Access Control" bounty impact classes.

### Likelihood Explanation
Exploitation requires: (1) the OIDC provider configuration/account type where the `email` claim is absent from the verified ID token for at least one legitimate login (plausible for service accounts, providers not always populating `email` even when scope requested, or accounts with unverified/hidden email), and (2) at least two distinct sessions falling into this state to enable the cross-user session-clear collision. The core defect itself (missing `return`) is deterministic and 100% reproducible whenever the `email` claim is absent — no attacker credential beyond a normal OIDC-authenticated session is required, and no admin/host access is needed.

### Recommendation
Add a `return` immediately after writing the error response in the `!ok` branch, mirroring every other failure branch in `handleTokenExchange`:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, consider rejecting session creation entirely (rather than persisting) when `email` is empty, since `user_email` is relied upon as a unique-ish identity key by `ClearNonCurrentSessions` and audit logging.

### Proof of Concept
Handler-level integration test plan (using `httptest` + `gin`):
1. Stand up a test `oidcAuthenticator` with a mock `oidc.Provider`/`Verifier` that returns a valid, signature-verified ID token whose claims include the configured group claim (e.g. `ReadClaim`) but omit the `email` field entirely.
2. Drive `handleSignIn` to populate session state, then POST to `/oidc-exchange` with a valid `code`/`state` pair.
3. Assert that:
   - The HTTP response is *not* a completed `200 Success: true` JSON body (expected/fixed behavior: `500` with no session cookie set).
   - Current (buggy) behavior: a session cookie (`webauth.SessionIDKey`) is set and a row is inserted into `oidc_sessions` with `user_email = ''`.
4. Repeat step 1-3 for a second distinct "user" (different group claims) to produce two `oidc_sessions` rows both with `user_email = ''`.
5. Call `ClearNonCurrentSessions(ctx, sessionA.ID)` and assert that `sessionB` (belonging to the unrelated second login) is deleted — demonstrating cross-user session termination caused by the shared blank `user_email`.
6. After applying the `return` fix, re-run steps 1-3 and assert the login is rejected with no cookie/session/audit row created, and step 4-5 is no longer reachable (no blank-email collision possible).

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
