Confirmed the bug mechanics: `confirmations` for a given `request_id` is only a `HashSet<PublicKey>` of keys that confirmed it, and the only place a public key's stale confirmation is purged is inside `execute_request`'s `DeleteKey` branch, which removes requests originally **created** by the deleted key (`r.signer_pk == pk`) — it does **not** scrub that key's `confirmations` entries from *other* live requests it had already confirmed [1](#0-0) . The threshold check in `confirm()` is purely `confirmations.len() as u32 + 1 >= self.num_confirmations` [2](#0-1) , i.e., it counts stored confirmations, not currently-valid keys.

### Title
Stale confirmations from deleted multisig keys still count toward `num_confirmations`, allowing execution below the live-key threshold - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes and executes a request once the number of entries in its `confirmations: HashSet<PublicKey>` reaches `num_confirmations`. When a key is removed via a `DeleteKey` request, the contract only purges requests *originated* by that key and the key's `num_requests_pk` counter — it never removes that key's already-recorded confirmations on other, still-pending requests [1](#0-0) . This breaks the intended equality `confirmations counted == currently authorized keys confirming`, letting a request execute with fewer live-key approvals than `num_confirmations` mandates.

### Finding Description
The `DeleteKey` execution branch is:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    // remove num_requests_pk entry for public_key
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [1](#0-0) 

Note the filter is `r.signer_pk == pk` — only requests **added** by the deleted key are dropped. Any other pending request that the deleted key had already `confirm`ed retains that key's public key inside its `confirmations` HashSet, because that set is only mutated by `confirm()` (add) or `remove_request()` (full removal on execution/deletion) [3](#0-2) [4](#0-3) .

`confirm()` itself only checks set membership and cardinality, never validating that recorded confirmers are still valid access keys on the account:
```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert!(
        !confirmations.contains(&env::signer_account_pk()),
        "Already confirmed this request with this key"
    );
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(env::signer_account_pk());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
``` [3](#0-2) 

Equality broken: intended binding is `confirmations recorded for request == confirmations from currently valid access keys`. After a `DeleteKey` action, this becomes `confirmations recorded ⊇ confirmations from valid keys`, i.e. stale/removed-key confirmations remain counted.

### Impact Explanation
This is a threshold-bypass: a `k`-of-`n` multisig can execute a `Transfer`, `AddKey`, `FunctionCall`, or arbitrary other action with effectively fewer than `k` currently-authorized keys approving, because a confirmation from an already-revoked key still counts toward `k`. Since `Transfer` actions move NEAR out of the account, this maps directly to "a multisig request executed below threshold" / funds moved by parties not currently entitled — the Critical impact class defined for this analysis.

### Likelihood Explanation
Exploitation requires no privileged party beyond an ordinary multisig key holder: any key that co-signs a pending request, and is later removed (a routine key-rotation action any confirming quorum can request), leaves its confirmation live on other pending requests. An attacker who is one of the remaining key holders can then complete execution of a stale pending request with one fewer live confirmation than `num_confirmations` requires, or deliberately orchestrate this by pre-confirming a request with a soon-to-be-revoked key before the revocation, then confirming with fewer of the remaining live keys than intended.

### Recommendation
When executing `DeleteKey`, scan and purge the deleted public key from **all** `confirmations` entries (not just requests it originated), or alternatively validate at `confirm()`/execution time that every public key present in a request's `confirmations` set still corresponds to a live access key on the account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` contract with `num_confirmations = 3` and keys `K1, K2, K3, K4`.
2. `K1` calls `add_request` to create request `R` (e.g., `Transfer` of funds to an attacker-controlled account).
3. `K2` calls `confirm(R)` → `confirmations = {K2}` (1/3).
4. `K3` calls `confirm(R)` → `confirmations = {K2, K3}` (2/3, not yet executed).
5. Separately, the group executes a `DeleteKey { public_key: K3 }` request (a normal, legitimate key-rotation action) — this only deletes requests where `signer_pk == K3` (there are none, since `K3` only confirmed, didn't originate) and clears `num_requests_pk` for `K3`; `R`'s `confirmations` set still contains `K3`.
6. Now only `K1, K2, K4` are valid keys on the account, and `num_confirmations` is still `3`, meaning a legitimate execution should require all three remaining keys or an updated threshold.
7. `K4` calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations (3)` → request executes, transferring funds, even though the confirming set `{K2 (stale membership still valid key), K3 (revoked), K4}` only contains 2 currently-valid keys' actual confirmations among the 3 counted.

    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .expect("Failed to remove existing element");
        // decrement num_requests for original request signer
        let original_signer_pk = request_with_signer.signer_pk;
        let mut num_requests = self.num_requests_pk.get(&original_signer_pk).unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_signer_pk, &num_requests);
        // return request
        request_with_signer.request
    }
