### Title
Blacklisted requester with default self-receiver cannot redirect escrowed deposit tokens on refund/cancel, permanently freezing funds - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.requestDeposit`/`requestRedeem` escrow the user's tokens/units in the contract and bind the withdrawal path to an immutable `request.receiver` and `request.user` pair set at request creation. When the refund/cancel flow eventually pays out via `_transferWithFallback`, if `receiver == requester` (the common default case where a user calls the overload that sets `receiver = msg.sender`), the function skips the `trySafeTransfer` attempt entirely and calls a non-try `safeTransfer` directly to that single address, exactly the pattern flagged in the referenced Beedle report where blacklisted borrowers/lenders have no way to specify an alternate recipient.

### Finding Description
`requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice)` (no receiver arg) forwards to the receiver-taking overload with `receiver = msg.sender` [4](#0-3) , pulling `tokensIn` into the Provisioner via `token.safeTransferFrom(msg.sender, address(this), tokensIn)` [5](#0-4) . `request.user` and `request.receiver` are both `msg.sender` and are fixed forever in the request hash.

If the token issuer later blacklists this address (e.g., USDC-style asset), the only recovery paths are `refundRequest` (post-deadline, callable by anyone but pays out via `requester = request.user`) and `cancelRequest` (`require(msg.sender == request.user, ...)`) [2](#0-1) [3](#0-2) . Both funnel into `_clearHashAndTransferRefund`, which calls `_transferWithFallback(token, requester, request.receiver, amount)` [6](#0-5) :

```solidity
function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
    if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
        token.safeTransfer(requester, amount);
    }
}
```

Because `receiver == requester` in the default single-address flow, the `trySafeTransfer` attempt to `receiver` is skipped entirely, and the code goes straight to the non-try `token.safeTransfer(requester, amount)`, which reverts unconditionally against a blacklisted address — there is no `recipient` parameter anywhere in `refundRequest` or `cancelRequest` to redirect the payout to a clean address the user controls. This is the exact root cause and broken invariant from the reference report: "no mechanics to move [escrowed funds] to another address or specify the recipient for the transfer."

### Impact Explanation
The user's full escrowed `tokensIn` (deposit case) or vault units (redeem case) become permanently stuck in `ProvisionerV2`, unrecoverable by the user through any public function. Recovery would require privileged `Sweepable` admin intervention [7](#0-6) , which is out of the ordinary-user threat model and not guaranteed. This matches a "temporary/permanent freezing of user funds" class of impact.

### Likelihood Explanation
Requires the depositor/redeemer's own address to become blacklisted by the underlying asset issuer (e.g., USDC) after submitting an async request but before it is solved or refunded/cancelled — a low-probability but externally-triggerable event outside the protocol's control, consistent with the "Medium" categorization in the referenced report.

### Recommendation
Add an explicit `recipient` parameter to `refundRequest` and `cancelRequest` (restricted to being settable only by `request.user`/`msg.sender` themselves) so users can redirect payout to a non-blacklisted address, decoupling it from the immutable `request.receiver`/`request.user` fields. Alternatively, always attempt `trySafeTransfer` to a caller-supplied fresh address rather than only reusing `receiver`/`requester`.

### Proof of Concept
1. Deploy `ProvisionerV2` with a mock ERC20 that supports a `blacklist(address)` function reverting on transfers to/from blacklisted addresses (mimicking USDC).
2. As `alice`, call `requestDeposit(token, 100e18, minUnitsOut, 0, deadline, maxPriceAge, false)` (no receiver arg) — confirm `request.user == request.receiver == alice`, and `100e18` tokens now sit in `ProvisionerV2`.
3. Call `token.blacklist(alice)` on the mock token.
4. As `alice`, call `cancelRequest(token, request)` (or wait for deadline and call `refundRequest`) — assert the call reverts inside `_transferWithFallback` because `receiver == requester == alice` skips the `trySafeTransfer` fallback and goes directly to `safeTransfer(alice, amount)`, which reverts due to blacklist.
5. Assert there is no alternate function/parameter allowing `alice` to redirect the refund to a different, non-blacklisted address; the `100e18` tokens remain permanently locked in `ProvisionerV2`.

    function cancelRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: self-cancel caller must be request user
        require(msg.sender == request.user, Aera__CallerIsNotRequestUser());

        if (_isRequestTypeDeposit(request.requestType)) {
            // Requirements: deposit cancellation toggle must be enabled
            require(_depositCancellationsEnabled, Aera__DepositRequestCancellationDisabled());

            uint256 refundAmount = request.tokens;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeDepositCancellationFeeTokens(token);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;
                    }
                    // Interactions: transfer cancellation fee to vault
                    token.safeTransfer(MULTI_DEPOSITOR_VAULT, cancellationFee);
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net token amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token);

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        require(asyncRequestHashes[requestHash], Aera__HashNotFound());
        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;
        // Interactions: transfer amount to receiver, fallback to requester on transfer failure
        _transferWithFallback(transferToken, requester, request.receiver, amount);

        // Log refund event
        if (_isRequestTypeDeposit(request.requestType)) {
            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }
