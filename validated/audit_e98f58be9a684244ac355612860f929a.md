Confirmed. Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` share the same flaw: removing a key/member only purges requests *originated* by that key/member, never scrubs that key's/member's existing **confirmations** recorded on other still-pending requests. The `confirm()` threshold check counts raw `confirmations.len()` with no re-validation that each confirming key/member is still live.

### Title
Stale confirmations from removed multisig keys/members count toward the confirmation threshold, allowing requests to execute below the live-signer threshold - ([File: multisig/src/lib.rs], [File: multisig2/src/lib.rs])

### Summary
`DeleteKey` (multisig) and `DeleteMember` (multisig2) remove a signer from the authorized set but never purge that signer's prior confirmations recorded on *other* still-pending requests. `confirm()` only compares the raw size of the stored `confirmations` set to `num_confirmations`, so a confirmation cast by a key/member that has since been revoked still counts toward reaching the threshold, letting a request execute after being approved by fewer currently-live signers than `num_confirmations` requires.

### Finding Description
The invariant the contract is supposed to enforce is: `confirmations from currently-live members >= num_confirmations`. Instead the code enforces: `confirmations.len() (including revoked signers) >= num_confirmations`.

In `multisig/src/lib.rs`, `DeleteKey` only removes requests whose `signer_pk` (the original *requester*) equals the deleted key, and clears `num_requests_pk` for that key: [1](#0-0) 
It never inspects `self.confirmations` for entries on *other* requests where the deleted key merely added a confirmation (not the original requester). Those stale confirmations remain stored: [2](#0-1) 
`confirm()` blindly trusts `confirmations.len()` without checking whether each confirming public key is still a valid key on the account.

The same pattern exists in `multisig2/src/lib.rs`, where `delete_member` removes requests originated by the removed member and removes them from `self.members`, but does not scrub the member's confirmations from other pending requests: [3](#0-2) 
and `confirm()` again just counts entries in the `HashSet<String>`: [4](#0-3) 

### Impact Explanation
This breaks the "confirmations counted versus live members" binding explicitly. A request (e.g., a `Transfer` draining the multisig-controlled account, or an `AddKey`/`AddMember` seizing control) can reach execution even though one or more of its counted confirmations came from a key/member that was subsequently revoked — meaning fewer truly live/authorized signers approved it than `num_confirmations` demands. This is a multisig request executed below threshold, a Critical-severity impact per the custody bindings this analysis targets (funds can move, or control of the account can be seized, without the intended quorum of currently-trusted signers).

### Likelihood Explanation
This requires no privileged bypass beyond ordinary multisig operations that are supported and expected in day-to-day use: creating/confirming a request, and later removing a key/member (a routine operational action, e.g. rotating a compromised key). The stale confirmation is never invalidated automatically, so the window in which this can be exploited persists as long as the original request stays pending (bounded only by `delete_request`'s 15-minute cooldown, i.e., it is not auto-expired).

### Recommendation
When a key/member is removed, iterate over all active `requests`/`confirmations` entries and strip the removed key/member's confirmation from each, decrementing recorded counts accordingly (not just from requests they originated). Alternatively, re-validate at `confirm()` time that every public key/member recorded in the `confirmations` set is still present in the current authorized set (`members` / valid access keys) before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` creates request `R` = `Transfer` to an attacker-controlled account via `add_request_and_confirm` → `confirmations(R) = {A}`.
3. `B` calls `confirm(R)` → `confirmations(R) = {A, B}` (2 < 3, request stays pending).
4. Separately, the team legitimately removes `A` (e.g., suspected compromised key) via a `DeleteMember{A}` (or `DeleteKey`) request confirmed by `B, C, D` → executes, removing `A` from `self.members` and revoking its access key. Per `delete_member`/`DeleteKey`, only requests *originated* by `A` are purged; `R` (originated by `A` too in this example — use a scenario where `A` is not the originator, e.g. `C` originates `R` and `A`/`B` merely confirm it, to show the request survives) remains with `confirmations(R) = {A, B}` untouched.
5. `C` calls `confirm(R)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `R` executes and the transfer is sent, even though only `B` and `C` are currently live, authorized signers; `A`'s stale, revoked confirmation was used to satisfy the threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
