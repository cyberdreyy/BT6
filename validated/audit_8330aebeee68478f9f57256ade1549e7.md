### Title
Reorg-permit exclusion in `get_signed_conflicts`/`reorg_permit_stands` is scoped to the permitting sortition's burnchain canonicity, not to the permitted successor chain — letting a signer sign two conflicting blocks at the same height - (File: `stacks-signer/src/chainstate/mod.rs`, `stacks-signer/src/signerdb.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
The pre-commit conflict guard that is supposed to stop a signer from putting a signature over two different blocks at the same height ("one-per-height"/equivocation guard) can be permanently defeated for a specific tenure once that tenure has ever been legitimately superseded by a reorg. The exclusion record (`superseded_tenures`) is only re-validated against whether the *permitting sortition* is still present on the canonical **burnchain**, not whether the block currently being signed actually descends from that permitting tenure. A second, unrelated reorg attempt that lands at the same height as the originally superseded block can therefore reuse a stale permit to bypass the conflict check and get signed, causing the signer to sign two conflicting blocks at the same height.

### Finding Description
When a miner's tenure does not build off the prior sortition, `SortitionData::check_parent_tenure_choice` decides whether the implied reorg is allowed (each reorged tenure must have ≤1 globally accepted block and be "poorly timed"). If sanctioned, every reorged tenure is recorded as superseded via `SignerDb::mark_tenure_superseded`, storing only the *permitting* tenure's consensus hash and burn-block hash: [1](#0-0) [2](#0-1) 

Later, when a new block reaches the pre-commit threshold, `handle_block_pre_commit` fetches every previously signed block at height ≥ the new block's height, in **any** tenure, via `get_signed_conflicts`: [3](#0-2) 

For a conflict whose own tenure was marked superseded, the exclusion is decided purely by `reorg_permit_stands`, which asks the node only whether the *permitting sortition's burn block* is still canonical — not whether the block currently under evaluation is actually descended from that permitting tenure: [4](#0-3) 

This is then used unconditionally in the fresh-conflict check: [5](#0-4) 

A tenure's Stacks-level reorg does not invalidate its own *sortition* on the burnchain (the sortition is a burnchain-level fact; only the Stacks tenure built from it can be reorged away by a later Stacks-level sanction). Consequently, once tenure `T1` is superseded by `T2` (a legitimate, sanctioned reorg), the permit keeps excluding `T1`'s signed block as a conflict for **any** future block that reaches height ≥ `T1`'s block height, as long as `T2`'s sortition remains on the canonical burnchain — even if that future block has nothing to do with `T2` at all (e.g., it is a second, independent reorg that skips both `T1` and `T2`).

### Impact Explanation
This breaks the "one signature per height" equivocation guard that section 5 of the signer flow (`handle_block_pre_commit`) exists to enforce. A sequence of two independently-sanctioned, "poorly timed" reorgs landing at the same chain position can cause the signer to place a valid, fresh signature over two different blocks at the same height in two unrelated tenures. This is exactly the Critical-impact category: a signer signing a conflicting block / losing the equivocation guard, which can produce a Stacks-chain split or double-spend opportunity across the two conflicting histories.

### Likelihood Explanation
No signer majority, key compromise, or auth-token access is required. The path requires only ordinary sortition wins by any miner(s) plus two Bitcoin-timing conditions (`first_proposal_burn_block_timing`) that `check_parent_tenure_choice` already treats as legitimate, sanctioned reorg triggers — i.e., a single miner (or a small number of consecutive miners) winning sortitions under realistic burn-timing jitter can reach this state without any protocol violation on their part. The window is bounded by `MAX_FORK_DEPTH` (100 burn blocks) before `prune_superseded_tenures` drops the record, which is a substantial amount of time.

### Recommendation
Scope the reorg-permit exclusion to the actual chain of the block being evaluated, not merely to the permitting sortition's burnchain canonicity. For example, when honoring a permit, additionally verify that the block currently reaching pre-commit is a descendant of the permitting tenure's chain (or, more conservatively, invalidate/replace a tenure's superseded record whenever the *permitting* tenure is itself later superseded, rather than leaving the original record to be checked only against burnchain canonicity of the now-stale permitting sortition).

### Proof of Concept
1. Miner wins sortition for tenure `T1`; its first (and only) block `B1` at height `H` is signed and globally accepted (only 1 globally accepted block — satisfies the reorg-eligibility bar in `check_parent_tenure_choice`, `stacks-signer/src/chainstate/mod.rs:210-223`).
2. A subsequent sortition produces tenure `T2`, which reorgs `T1` legitimately (Bitcoin timing makes `T1`'s only block "poorly timed", `stacks-signer/src/chainstate/mod.rs:247-274`). Signers record `mark_tenure_superseded(T1, superseded_by=T2)` (`stacks-signer/src/signerdb.rs:1642-1659`).
3. Shortly after, before `T2` accumulates more than one globally accepted block, a further sortition produces tenure `T3` whose miner also reorgs past `T2` back to the same point as `T1`'s parent (also satisfying the "poorly timed"/≤1-block bar for `T2`, since `T2` is likewise young) and proposes a new block `B3` at the same height `H`.
4. `T3`'s `B3` reaches the pre-commit threshold. `get_signed_conflicts(H, B3_hash)` returns `B1` (still signed, fresh) with `superseded_by = T2` (`stacks-signer/src/signerdb.rs:1606-1625`).
5. `reorg_permit_stands` asks only whether `T2`'s sortition/burn block is still canonical (`stacks-signer/src/v0/signer.rs:1222-1247`) — which it is, because `T2`'s Stacks-level reorg by `T3` does not affect `T2`'s own burnchain sortition. The permit is reported as standing, so `B1` is excluded from the conflict set even though `B3` (`T3`) has no relation to `T2` at all.
6. The signer proceeds to sign `B3` (`stacks-signer/src/v0/signer.rs:1403-1421`, `1466-1471`), resulting in the signer holding fresh signatures over two conflicting blocks (`B1` and `B3`) at the identical height `H` in unrelated tenures — the exact double-sign the guard was built to prevent.

        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,

                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2

        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)

    fn reorg_permit_stands(
        &self,

        conflict: &SignedConflictInfo,

        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
