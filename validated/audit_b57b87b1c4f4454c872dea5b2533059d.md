### Title
Unprivileged lamport-griefing can block vote account closing/full withdrawal via exact-amount balance check - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `withdraw` function used by `VoteInstruction::Withdraw` determines whether an operation is a "full close" of a vote account strictly by checking `remaining_balance == 0`, where `remaining_balance = vote_account.get_lamports() - lamports` and `lamports` is a fixed value chosen by the withdrawer ahead of time and baked into the signed transaction. Because any unprivileged account can send lamports to a vote account via a normal system transfer (vote accounts are not restricted recipients), an attacker can grief a pending "close the vote account" or "withdraw full balance" transaction by sending a small amount of lamports to the target vote account before it lands, changing `remaining_balance` from `0` to a nonzero value and forcing execution into the `else` branch, which imposes a stricter `min_balance` (rent-exempt minimum plus `pending_delegator_rewards`) requirement that the withdraw amount no longer satisfies.

### Finding Description
`withdraw()` computes: [1](#0-0) 
then branches on whether `remaining_balance == 0` to treat the request as a full account close (deinitializing state), versus the `else` branch that requires `remaining_balance >= min_rent_exempt_balance + pending_delegator_rewards`: [2](#0-1) 

The `lamports` parameter comes directly from the caller-supplied instruction data (`VoteInstruction::Withdraw(lamports)`), which is fixed at the time the withdrawer signs the transaction based on the vote account's balance observed at that time: [3](#0-2) 

Because a vote account's lamport balance can be increased by anyone via an ordinary system transfer (no signature/authority check on receiving lamports), an attacker who observes a pending withdraw/close transaction (e.g., in the mempool or by simply resubmitting whenever the withdrawer resubmits) can send even 1 lamport to the vote account so that, at execution time, `vote_account.get_lamports()` is higher than what the withdrawer accounted for. This makes `remaining_balance` nonzero even though the withdrawer intended a full close, pushing execution into the `else` branch. If the account is only barely rent-exempt (or the withdrawal was calculated to bring balance to exactly zero), the new stricter `min_balance` check fails and the instruction returns `InstructionError::InsufficientFunds`, so the withdraw/close does not execute at all. As documented in the code, this exact-equality "close" branch already interacts with `pending_delegator_rewards` and epoch-credits protections (SIMD-0123), and its state-dependent behavior (`==0` vs partial withdraw semantics) makes it directly susceptible to this class of dust/balance-manipulation griefing, mirroring the reported "prevent deletion by sending 1 wei" pattern.

### Impact Explanation
An unprivileged attacker can repeatedly and cheaply (cost of 1 lamport plus fee) block a validator/withdrawer from closing a vote account or withdrawing its full balance in one shot, since the fixed `lamports` value chosen ahead of time will consistently fail once the attacker perturbs the balance. This is a targeted denial-of-service against a legitimate, permissioned action (only the `authorized_withdrawer` can withdraw) performed by an entirely unrelated, unprivileged party, and can be repeated indefinitely to keep frustrating the withdrawer's attempts to close/fully drain the account in a single transaction.

### Likelihood Explanation
Likelihood is moderate: the attack requires the attacker to observe/predict a pending exact-amount close/withdraw transaction and race a small transfer ahead of it (or simply resubmit whenever the withdrawer retries with an updated fixed amount), which is feasible for any account since system transfers to arbitrary pubkeys are unrestricted and cheap.

### Recommendation
Avoid relying on an exact-equality (`remaining_balance == 0`) check to detect "full close" intent. Instead, accept an explicit close flag/sentinel value (e.g., `u64::MAX` meaning "withdraw entire current balance") so the amount to withdraw is computed from the live balance at execution time rather than a value fixed at signing time, eliminating the race window that lets a third party perturb the balance and flip which branch is taken.

### Proof of Concept
1. Vote account `V` has balance `B` (>= rent-exempt minimum) and `pending_delegator_rewards = 0`; the `authorized_withdrawer` observes balance `B` and signs `VoteInstruction::Withdraw(B)` intending a full close.
2. Before that transaction lands, an attacker submits a system transfer of `1` lamport to `V`, landing first in the same or an earlier slot, making `V`'s balance `B + 1`.
3. When the withdrawer's transaction executes, `remaining_balance = (B + 1) - B = 1`, which is not `0`, so `withdraw()` takes the `else` branch: [4](#0-3) 
4. The check `remaining_balance < min_balance` (where `min_balance` is at least the rent-exempt minimum) fails since `remaining_balance == 1`, and the instruction returns `InstructionError::InsufficientFunds`, aborting the close/full withdrawal despite the withdrawer being fully authorized and having accounted for the correct balance at signing time.
