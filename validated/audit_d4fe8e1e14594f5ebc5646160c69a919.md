### Title
Unsanitized cache `AlternateKey` under `FF_HASH_CACHE_KEYS` enables path traversal in `cacheArchivePath` - (File: functions/concrete/run/stages/cache_archive.go)

### Summary
When the `FF_HASH_CACHE_KEYS` feature flag is enabled, `builder.buildCacheArchive`/`cacheKey` leaves the human-readable cache key completely unsanitized and assigns it directly to `CacheArchive.AlternateKey`, while the primary `Key` is safely hashed with SHA-256. `cacheArchivePath` in `functions/concrete/run/stages/cache_archive.go` then joins this attacker-controlled, unsanitized key into `e.CacheDir` without any traversal check, letting a job's `cache:key` value (e.g. containing `../`) redirect the alternate cache archive write outside the job's own cache directory.

### Finding Description
`cacheArchivePath` blindly does `filepath.Join(e.CacheDir, key, "cache.zip")` and then makes it relative to `e.WorkingDir`, with no validation that the resulting path stays under `e.CacheDir`: [1](#0-0) 

For the primary key, `builder.cacheKey` guards against traversal in the non-hashed path by running `cachekey.Sanitize`, which resolves `..`/`.` against a virtual root so they can never escape it: [2](#0-1) 

But when `FF_HASH_CACHE_KEYS` is on, `cacheKey` skips sanitization entirely (`humanKey = rawKey`) and only the *primary* resolved key is hashed with SHA-256 (which is safe because hex digests can't contain path separators): [3](#0-2) 

The alternate key, however, is computed as `alternateResolved := humanKey` and is only re-hashed in the *opposite* case (`!HashCacheKeys`). When the flag is on, this branch is skipped, so `AlternateKey` is assigned the raw, unsanitized `humanKey` directly: [4](#0-3) 

This `AlternateKey` is then passed straight into `CacheArchive.Run`, and if it differs from `Key` (which it always does, since one is a raw string and the other a hex hash), `cacheArchivePath(e, s.AlternateKey)` is invoked to build the `--alternate-file` argument passed to `cache-archiver`: [5](#0-4) 

Since `key` here is fully attacker-controlled (from the job's `cache:key`, only variable-expanded, never sanitized) and `filepath.Join` cleans `..` segments, a key such as `../../otherproject/mykey` collapses `e.CacheDir/../../otherproject/mykey/cache.zip` into a path outside `e.CacheDir`. The `filepath.Rel(e.WorkingDir, absPath)` call does not reject this — it simply computes whatever relative path reaches that (now out-of-bounds) absolute location, and the cache-archiver helper subsequently writes `cache.zip` there.

The existing sanitization (`cachekey.Sanitize`) that would normally neutralize this is present in the codebase but is not applied to the alternate key computation in the `FF_HASH_CACHE_KEYS`-enabled branch — this is the missing check.

### Impact Explanation
On a runner with `FF_HASH_CACHE_KEYS` enabled, any pipeline author who controls `cache:key` can cause the cache-archiver to write `cache.zip` to a directory outside the job's own cache root, e.g., into another project's cache path if the on-disk cache layout is shared/predictable (`e.CacheDir` typically encodes a project/build-relative segment). This corrupts or overwrites another project's cache artifact, a persistent cross-project effect that outlives the job and does not require the shared-runner administrator to have made any explicitly documented insecure choice — it is a bypassed path-confinement check, not an accepted admin trust boundary.

### Likelihood Explanation
Requires `FF_HASH_CACHE_KEYS` to be enabled (an opt-in runner feature flag, not default-on) — this is the only real precondition, and once enabled, exploitation needs nothing more than an ordinary `.gitlab-ci.yml` `cache: key:` value containing `../` sequences, fully within reach of an unprivileged pipeline author. It is deterministic and repeatable every time the alternate cache path diverges from the primary path.

### Recommendation
Apply the same `cachekey.Sanitize` (or an equivalent traversal-safe canonicalization) to the alternate key computation in `builder.buildCacheArchive` regardless of `FF_HASH_CACHE_KEYS` state, and/or add a defense-in-depth check inside `cacheArchivePath` that verifies the resulting `absPath` is still contained within `e.CacheDir` (e.g., via `filepath.Rel(e.CacheDir, absPath)` and rejecting results starting with `..`), returning an error instead of silently emitting the escaped path.

### Proof of Concept
```go
// functions/concrete/run/stages/cache_archive_test.go
func TestCacheArchivePath_AlternateKeyTraversal(t *testing.T) {
    e := &env.Env{
        WorkingDir: "/builds/group/project",
        CacheDir:   "/cache/project-123",
    }
    s := CacheArchive{Key: "abc123hash", AlternateKey: "../../otherproject/mykey"}

    got := s.alternateArchivePath(e)
    abs := filepath.Join(e.WorkingDir, got)

    rel, err := filepath.Rel(e.CacheDir, abs)
    require.NoError(t, err)
    assert.False(t, strings.HasPrefix(rel, ".."),
        "alternate archive path escaped CacheDir: got %s (resolved %s)", got, abs)
}
```
Combined with a `builder_test.go` case asserting that with `FF_HASH_CACHE_KEYS=true` and `cache.Key = "../../otherproject/mykey"`, `config.CacheArchive[0].AlternateKey` is sanitized (e.g., normalized to `otherproject/mykey`) rather than left as the raw traversal string — currently it is not, confirming the bug at the builder layer that feeds the vulnerable path in `cacheArchivePath`.

func Sanitize(cacheKey string) (string, error) {
	if cacheKey == "" {
		return "", nil
	}

	// Decode percent-encoded chars and normalise separators, then
	// resolve traversals against a virtual root so ".." can never
	// escape beyond the root.
	cleaned := path.Clean("/" + normaliser.Replace(cacheKey))

	// Strip the leading "/" we added, split into segments, then walk
	// backwards trimming trailing whitespace from the rightmost
	// segments—dropping any that become empty.
	parts := strings.Split(cleaned[1:], "/")
	n := len(parts)
	for n > 0 {
		parts[n-1] = strings.TrimRightFunc(parts[n-1], unicode.IsSpace)
		if parts[n-1] != "" {
			break
		}
		n--
	}

	key := strings.Join(parts[:n], "/")

	if key == "" {
		return "", fmt.Errorf("cache key %q could not be sanitized", cacheKey)
	}

	return key, nil
}
