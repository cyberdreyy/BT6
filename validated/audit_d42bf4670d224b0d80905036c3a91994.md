### Title
`min_context_slot` restriction is silently ignored on `accountSubscribe`/`programSubscribe`, letting subscribers bypass the freshness guard enforced on the polling RPC equivalents - (File: `rpc/src/rpc_pubsub.rs`)

### Summary
`rpc/src/rpc.rs` enforces `min_context_slot` on all `getAccountInfo`/`getProgramAccounts`-style calls via `get_bank_with_config()`, rejecting requests with `MinContextSlotNotReached` when the node's bank hasn't caught up to the caller-specified slot. The pubsub equivalents (`accountSubscribe`, `programSubscribe`) accept the same `min_context_slot` field in their config but explicitly discard it, so a subscriber gets notified with stale/instantiated data from whatever slot the node happens to be on, without ever being told the node lagged behind the requested context.

### Finding Description
`JsonRpcRequestProcessor::get_bank_with_config` treats `min_context_slot` as a hard precondition for any RPC read: [1](#0-0) 
This same struct field is threaded through `get_blocks`, `get_signatures_for_address`, and account-info methods and is uniformly checked with `RpcCustomError::MinContextSlotNotReached`.

However, `RpcSolPubSubImpl::account_subscribe` destructures `RpcAccountInfoConfig` and drops `min_context_slot` on the floor: [2](#0-1) 
The comment `min_context_slot: _, // ignored` makes the omission explicit — no error is returned, and the subscription is created against whatever bank state exists when `notify_watchers` later runs. `program_subscribe` builds its `ProgramSubscriptionParams` from the same `RpcAccountInfoConfig` embedded in `RpcProgramAccountsConfig` and likewise never surfaces or checks `min_context_slot`: [3](#0-2) 

The actual notification path (`check_commitment_and_notify` / `filter_account_result` in `rpc_subscriptions.rs`) has no min-slot concept either — it just reads whatever bank is available for the requested commitment level: [4](#0-3) [5](#0-4) 

This mirrors the reported bug class exactly: a restriction (`emergency`/freshness guard) is properly enforced on the "main" mutation/read path but is silently skippable through a parallel/side entry point (transfer hook vs. pubsub subscribe) that shares the same config struct but drops the guard.

### Impact Explanation
A client relying on `min_context_slot` to ensure it never observes data from before a slot it has already seen elsewhere (e.g., after submitting a transaction and learning the slot it landed in) can be silently served stale account/program data through `accountSubscribe`/`programSubscribe`, even though the identical guard would have caused an explicit, actionable error via `getAccountInfo`. This is a "wrong-slot/account data returned" class issue: the caller receives account state from an earlier/inconsistent slot without any indication that the min-context guarantee was violated, which can lead to incorrect application logic (e.g., displaying unconfirmed/rolled-back balances as if freshness had been validated).

### Likelihood Explanation
Trivially reachable by any unprivileged JSON-RPC client — `min_context_slot` is a documented, publicly exposed config field on `accountSubscribe`/`programSubscribe`, and there is no special access control needed. The bypass is deterministic (the field is unconditionally discarded), not a race condition, so it will happen every time a client attempts to use this parameter on these subscription methods.

### Recommendation
Thread `min_context_slot` from `RpcAccountInfoConfig`/`RpcProgramAccountsConfig` into `AccountSubscriptionParams`/`ProgramSubscriptionParams`, and either (a) reject the subscribe call up front with `RpcCustomError::MinContextSlotNotReached` if the current bank hasn't reached that slot (mirroring `get_bank_with_config`), or (b) suppress notifications until the watched bank's slot is `>= min_context_slot`, consistent with how the polling RPC methods behave.

### Proof of Concept
1. Start a node whose working bank is behind slot `N`.
2. Call `accountSubscribe` (or `programSubscribe`) with `config.min_context_slot = N` for an account whose state differs between the current bank and slot `N`.
3. Observe that the subscription succeeds immediately (no `MinContextSlotNotReached` error) and delivers `accountNotification`s built from banks below slot `N`, unlike a `getAccountInfo` call with the same `min_context_slot`, which would instead return a `-32016 MinContextSlotNotReached` error until the node catches up — confirmed by the code paths cited above (`rpc.rs:273-289` enforcing it vs. `rpc_pubsub.rs:425-443` discarding it, with no min-slot check anywhere in `rpc_subscriptions.rs`'s notification pipeline).

impl JsonRpcRequestProcessor {
    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }

fn filter_account_result(
    result: Option<(AccountSharedData, Slot)>,
    params: &AccountSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (Option<UiAccount>, Slot) {
    // If the account is not found, `last_modified_slot` will default to zero and
    // we will notify clients that the account no longer exists if we haven't already
    let (account, last_modified_slot) = result.unwrap_or_default();

    // If last_modified_slot < last_notified_slot this means that we last notified for a fork
    // and should notify that the account state has been reverted.
    let account = (last_modified_slot != last_notified_slot).then(|| {
        if is_known_spl_token_id(account.owner())
            && params.encoding == UiAccountEncoding::JsonParsed
        {
            get_parsed_token_account(&bank, &params.pubkey, account, None)
        } else {
            encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
        }
    });
    (account, last_modified_slot)
}
