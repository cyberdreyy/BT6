### Title
External initiator credential can trigger job runs for arbitrary job IDs, not just its own bound job - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets `SessionUserKey` to a generic `clsessions.User{Role: UserRoleRun}` with no reference to which external initiator (EI) or job triggered the authentication. `PipelineRunsController.Create`, mounted at `POST /v2/jobs/:ID/runs` under the `userOrEI` group with `auth.RequiresRunRole`, only checks for the presence of *any* authenticated user object and then calls `RunJobV2` directly using the `:ID` path parameter, without ever checking the EI object retrieved by `GetAuthenticatedExternalInitiator` or its binding to the target job.

### Finding Description
The route is registered as: [1](#0-0) 

`AuthenticateExternalInitiator` authenticates using the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, looks up the `ExternalInitiator` record, and on success sets both the EI context value and a bare, unscoped run-role user: [2](#0-1) 

`RequiresRunRole` only rejects `UserRoleView`; it has no notion of "this session is scoped to EI X / job Y": [3](#0-2) 

`PipelineRunsController.Create` determines "isUser" purely from the presence of `SessionUserKey` (true for session/token users *and* for EI-authenticated requests, since `AuthenticateExternalInitiator` sets the same key), then parses the URL `:ID` as an arbitrary int32 job ID and calls `RunJobV2` with no cross-check against `GetAuthenticatedExternalInitiator(c)` or any stored mapping between the EI and the job: [4](#0-3) 

Because there is no lookup connecting the authenticated `ExternalInitiator` (available via `auth.GetAuthenticatedExternalInitiator(c)`) to the job identified by `:ID`, any successfully authenticated EI can submit `POST /v2/jobs/<any-int-job-ID>/runs` and have `RunJobV2` executed for that job — including jobs that were configured to be triggered by a *different* external initiator.

### Impact Explanation
This breaks request/credential binding: possession of one external initiator's AccessKey/Secret is sufficient to trigger job runs for any job on the node reachable by int ID, not just the job(s) the initiator was registered against. This can cause unauthorized pipeline execution, potentially consuming node resources, triggering unintended on-chain-adjacent side effects from job pipelines (e.g., HTTP calls, VRF/transmission-adjacent tasks depending on job type), and violates the intended "least privilege" scoping of external initiator credentials to their own job(s). This maps to a role/authorization-bypass / unauthorized-job-run Chainlink bounty impact class.

### Likelihood Explanation
Precondition is only a valid external initiator credential (AccessKey + Secret) — the lowest privilege credential type in the system, obtainable by any party the operator has registered as an EI. No admin/session/token access is needed. The exploit is a single unauthenticated (from the node's perspective, EI-authenticated) HTTP POST with attacker-chosen job ID, fully repeatable and requires no timing or race conditions.

### Recommendation
In `PipelineRunsController.Create`, when the request is authenticated via an external initiator (`auth.GetAuthenticatedExternalInitiator(c)` returns ok), verify that the target job at `:ID` is actually configured with that specific external initiator (e.g., look up the job's `externalInitiators`/webhook spec and confirm the authenticated EI's name/ID is present) before calling `RunJobV2`. Reject with 401/403 if the EI is not bound to the given job. Alternatively, encode the EI-job binding into the session object set by `AuthenticateExternalInitiator` so that `RequiresRunRole`/the controller can enforce it generically instead of relying on role alone.

### Proof of Concept
1. Register two external initiators EI_A and EI_B via `POST /v2/external_initiators` (admin/edit role), each returning `AccessKey`/`Secret`.
2. Create Job A configured with `externalInitiators = [{name = "EI_A", ...}]` and Job B configured with `externalInitiators = [{name = "EI_B", ...}]` via `POST /v2/jobs`.
3. Using EI_A's `AccessKey`/`Secret` headers (`X-Chainlink-EA-AccessKey`, `X-Chainlink-EA-Secret`), send `POST /v2/jobs/<Job B int ID>/runs`.
4. Assert the response: expected secure behavior is `401`/`403` because EI_A is not bound to Job B; current code path (per `PipelineRunsController.Create`, `core/web/pipeline_runs_controller.go:109-127`) is expected to return `200`/`201` and successfully create a pipeline run for Job B, since no EI-to-job binding check exists.
5. Confirm via `prc.App.PipelineORM()`/`pipeline_runs` table that a run was created for Job B using EI_A's credentials, proving cross-EI job-run triggering.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (prc *PipelineRunsController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	respondWithPipelineRun := func(jobRunID int64) {
		pipelineRun, err := prc.App.PipelineORM().FindRun(ctx, jobRunID)
		if err != nil {
			jsonAPIError(c, http.StatusInternalServerError, err)
			return
		}
		res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
		jsonAPIResponse(c, res, "pipelineRun")
	}

	idStr := c.Param("ID")

	// Webhook runs used external job UUIDs; that job type has been removed.
	if _, err := uuid.Parse(idStr); err == nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, fmt.Errorf("cannot run job of type %q: %w", job.Webhook, job.ErrJobTypeRemoved))
		return
	}

	_, isUser := auth.GetAuthenticatedUser(c)
	// only users are allowed to run jobs using int IDs - EIs not allowed
	if isUser {
		// Is it an int32? Then process it regardless of type
		var jobID int32
		jobID64, err := strconv.ParseInt(idStr, 10, 32)
		if err == nil {
			jobID = int32(jobID64)
			jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
			if err != nil {
				jsonAPIError(c, http.StatusInternalServerError, err)
				return
			}
			respondWithPipelineRun(jobRunID)
			return
		}
	}

	jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("bad job ID"))
