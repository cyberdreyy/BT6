### Title
Missing role check on GET /v2/external_initiators discloses AccessKey/OutgoingToken to any authenticated (view/run-role) token holder - ([File: core/web/router.go], [File: core/web/external_initiators_controller.go])

### Summary
`GET /v2/external_initiators` is registered as `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` with no `auth.RequiresEditRole`/`RequiresRunRole` wrapper, unlike `POST`/`DELETE` on the same resource which both require edit role. Any authenticated principal (session or API token, including view-role or run-role) can therefore call `Index` and receive every `ExternalInitiator`'s `AccessKey` and `OutgoingToken` via `presenters.ExternalInitiatorResource`.

### Finding Description
The route table shows the asymmetry directly: [1](#0-0) 

`ExternalInitiatorsController.Index` fetches all initiators from the ORM and maps them through `presenters.NewExternalInitiatorResource` with no additional authorization check inside the handler: [2](#0-1) 

The presenter used for `Index`, `ExternalInitiatorResource`, includes `AccessKey` and `OutgoingToken` in its JSON output: [3](#0-2) 

Note: contrary to the premise in the question, `Salt` and `HashedSecret` are **not** part of `ExternalInitiatorResource` and are never serialized by this presenter — only `ExternalInitiatorAuthentication` (returned solely on `Create`, one-time) includes the plaintext `Secret`, and that struct is not used by `Index`: [4](#0-3) [5](#0-4) 

So the actual disclosure is limited to `AccessKey` (the "username" half of incoming EI auth, not sufficient alone to pass `AuthenticateExternalInitiator` since the matching `Secret`/`HashedSecret`+`Salt` are never returned again) and `OutgoingToken` (a genuine secret the node uses to authenticate its own outbound calls to the external initiator's webhook endpoint). The authorization wrapper is inconsistent: `Create`/`Destroy` are gated by `auth.RequiresEditRole`, but `Index` is only wrapped by `paginatedRequest`, which does not perform any role check — it just does pagination parameter parsing (confirmed by the identical pattern used for `bt.Index`, `tas.Index`, etc., none of which apply role gates).

### Impact Explanation
An attacker holding a view-role or run-role API token/session — i.e., a legitimate but restricted-privilege user, not an admin — can enumerate all `ExternalInitiator` records and obtain each one's `OutgoingToken`. This falls under credential/secret disclosure: the `OutgoingToken` could be replayed by the attacker against the external initiator's own external endpoint to impersonate the Chainlink node's outbound webhook traffic. The `AccessKey` disclosure alone does not grant `AuthenticateExternalInitiator` bypass (the corresponding secret is never re-exposed and is only ever compared via its salted hash), so this is a partial secret-confinement/authorization-exactness violation rather than a full authentication bypass, matching the question's own caveat ("once secrets are also leaked or brute-forced").

### Likelihood Explanation
Precondition is only a valid low-privilege (view-role or run-role) API token or session — no admin/edit privileges required. The route is reachable directly over HTTP with no additional gating, making this trivially and repeatably exploitable by any authenticated non-admin user.

### Recommendation
Wrap `authv2.GET("/external_initiators", ...)` with the same `auth.RequiresEditRole` (or a dedicated `RequiresViewRole`-appropriate but explicitly reviewed) guard used for `Create`/`Destroy`, and/or strip `OutgoingToken` (and `AccessKey`, since it has no legitimate read use after creation) from `ExternalInitiatorResource` returned by `Index`/list endpoints, following the same one-time-disclosure pattern already used for `ExternalInitiatorAuthentication` on `Create`.

### Proof of Concept
Handler-level integration test plan (Go, using existing `core/web/external_initiators_controller_test.go` harness patterns):
1. Create an app/session with a **view-role** (non-edit, non-admin) API token via existing test helpers (e.g. `cltest.NewSession`/`cltest.MustSetup...` with `sessions.UserRoleView`).
2. Seed one or more `ExternalInitiator` records via `BridgeORM().CreateExternalInitiator`.
3. Issue `GET /v2/external_initiators` using the view-role credential.
4. Assert response status is `200 OK` (currently succeeds; expected fix: `401`/`403`).
5. Assert response body contains `accessKey` and `outgoingToken` fields populated with the real stored values (currently leaked; expected fix: fields absent or endpoint denied for non-edit roles).
6. Repeat with a run-role credential to show the same gap.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

type ExternalInitiatorAuthentication struct {
	Name           string        `json:"name,omitempty"`
	URL            models.WebURL `json:"url"`
	AccessKey      string        `json:"incomingAccessKey,omitempty"`
	Secret         string        `json:"incomingSecret,omitempty"`
	OutgoingToken  string        `json:"outgoingToken,omitempty"`
	OutgoingSecret string        `json:"outgoingSecret,omitempty"`
}

// NewExternalInitiatorAuthentication creates an instance of ExternalInitiatorAuthentication.
func NewExternalInitiatorAuthentication(
	ei bridges.ExternalInitiator,
	eia auth.Token,
) *ExternalInitiatorAuthentication {
	var result = &ExternalInitiatorAuthentication{
		Name:           ei.Name,
		AccessKey:      ei.AccessKey,
		Secret:         eia.Secret,
		OutgoingToken:  ei.OutgoingToken,
		OutgoingSecret: ei.OutgoingSecret,
	}
	if ei.URL != nil {
		result.URL = *ei.URL
	}
	return result
}
