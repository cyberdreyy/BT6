### Title
JWT replay-cache check-then-act race allows a single signed HTTP trigger request to bypass replay protection and execute twice - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The `WorkflowMetadataHandler.Authorize` function validates a JWT-signed HTTP trigger request and is supposed to guarantee "used-once" semantics via a `jwtReplayCache`, but the check (`isReplay`) and the write (`recordUsage`) are performed as two separate, non-atomic locked operations, allowing a race window in which the same signed request can pass authorization more than once — directly analogous to the referenced report's root cause: a validation gate that exists in source but doesn't actually enforce the invariant it claims to, letting stale/already-consumed state be accepted again.

### Finding Description
`Authorize` verifies the JWT, then checks for replay, then (only after other checks pass) records usage: [1](#0-0) 

The replay cache itself implements the check and the write as two independent critical sections: [2](#0-1) 

`isReplay` takes an `RLock`, reads, and releases; `recordUsage` separately takes a `Lock`, writes `cache[jti] = time.Now()`, and releases. There is no atomic "check-and-set" (e.g., a single locked `LoadOrStore`-style operation). If the gateway processes concurrent JSON-RPC requests bearing the identical `Auth` JWT (same `jti`) — which an unprivileged external client fully controls by sending the same signed request twice concurrently — both goroutines can call `isReplay(claims.ID)` before either calls `recordUsage(claims.ID)`, and both will see "not a replay" and proceed. This mirrors the class of bug in the external report: a freshness/consumed-state check exists, but is evaluated against data that can change between the check and the action, so the intended guard ("do not accept/act on this value twice / after it's stale") fails to hold under realistic conditions.

This function is reached directly from unprivileged, internet-facing input: `Authorize` is called by the gateway's HTTP-trigger processing path when handling `MethodWorkflowExecute` requests forwarded from external HTTP trigger callers through the gateway (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`), which is the externet-facing gateway envelope/handler path explicitly in scope.

### Impact Explanation
A successfully authorized JWT-signed trigger normally causes the gateway to fan the request out to DON members for execution (as described in the package's own flow docs: "Node Distribution: Sends request to all DON members with retry logic"). If the replay guard can be raced, an external caller can cause a single authorized workflow-execution intent to be dispatched/executed more than once. Depending on the workflow semantics this can translate into duplicate job runs, duplicate side effects, or duplicate consumption of any state gated by "one JWT = one execution," which is the "unauthorized job run" class of impact called out as an acceptable, concrete impact for this scan. Because the JWT's replay protection is the only mechanism preventing reuse of a single signed authorization (the JWT `exp`/`iat` window can be relatively long-lived, up to `maxJWTExpiryDuration`), losing that guarantee under concurrency removes the single de-duplication control for the entire expiry window.

### Likelihood Explanation
The race requires only that the same client (or a network intermediary/retry mechanism) send two (or more) copies of the identical signed JSON-RPC request to the gateway within the same short window before the first `recordUsage` write completes — this is trivially achievable by any unprivileged external client issuing two near-simultaneous HTTP POSTs with the same JWT. It requires no privileged access, no cryptographic break, and no node compromise; it purely exploits the non-atomic check-then-act pattern in `jwtReplayCache`. The primary uncertainty (which I could not fully confirm before running out of tool calls) is whether `HandleUserTriggerRequest`/`Authorize` calls are serialized behind some other lock further up the call stack in `http_trigger_handler.go`; if they are not (which is consistent with the `WorkflowMetadataHandler`'s own internal `sync.RWMutex`-per-map design elsewhere, suggesting the author intended fine-grained concurrent access), the race is directly exploitable.

### Recommendation
Make the replay check-and-record atomic under a single lock acquisition, e.g. add a `checkAndRecord(jti string) bool` method on `jwtReplayCache` that holds the write lock for the full duration of "check if present, then insert if absent," and use that single call in `Authorize` instead of separate `isReplay`/`recordUsage` calls. This closes the TOCTOU window regardless of how many goroutines call `Authorize` concurrently with the same `jti`.

### Proof of Concept
1. Client generates a valid signed JWT for a `MethodWorkflowExecute` request (`utils.CreateRequestJWT` + ECDSA signature), with a normal `exp`/`iat` window.
2. Client sends two copies of the exact same JSON-RPC request (same body, same `Auth` JWT, same `jti`) to the gateway's HTTP trigger endpoint at (near-)the same time, e.g. via two concurrent HTTP connections or a proxy that duplicates the request.
3. Both requests reach `WorkflowMetadataHandler.Authorize` concurrently on the gateway.
4. Goroutine A calls `h.jwtCache.isReplay(claims.ID)` → `false` (not yet recorded).
5. Before goroutine A calls `recordUsage`, goroutine B also calls `isReplay(claims.ID)` → `false`.
6. Both goroutines pass the replay check, both continue to signer/authorized-key validation, and both eventually call `recordUsage`, but by then both authorizations have already succeeded — the request has been effectively authorized (and forwarded to DON members) twice from a single signed JWT. func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func newJWTReplayCache(cleanupPeriod time.Duration) *jwtReplayCache {
	return &jwtReplayCache{
		cache:         make(map[string]time.Time),
		cleanupPeriod: cleanupPeriod,
	}
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
