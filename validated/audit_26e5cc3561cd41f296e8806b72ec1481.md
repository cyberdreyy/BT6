### Title
Unhandled `.unwrap()` on malformed reward-set signing key panics the signer runloop - (File: `stacks-signer/src/runloop.rs`)

### Summary
`RunLoop::get_parsed_reward_set` calls `SignerEntries::parse(...).unwrap()` on every reward-set refresh; `SignerEntries::parse` returns `Err(Error::BadSignerPublicKey)` whenever any `NakamotoSignerEntry.signing_key` bytes fail `StacksPublicKey::from_slice`. The chainstate's own PoX-4 tuple parser (`RawRewardSetEntry::from_pox_4_tuple`) can itself construct such a malformed all-zero key when the on-chain `signer` buffer is shorter than 33 bytes, so a genuinely malformed key can reach the reward set the signer must load.

### Finding Description
In `RunLoop::get_parsed_reward_set`, after fetching the reward set from the node, the code does: [1](#0-0) 
`SignerEntries::parse` iterates every entry and does `StacksPublicKey::from_slice(entry.signing_key.as_slice())`, returning `Err(Error::BadSignerPublicKey(..))` on any parse failure: [2](#0-1) 

The upstream chainstate code that builds `RawRewardSetEntry.signer` from the PoX-4 tuple explicitly acknowledges that Clarity's `(buff 33)` type only enforces a *maximum* length, not a minimum, and defensively substitutes an all-zero 33-byte array when the on-chain `signer` buffer is not exactly 33 bytes: [3](#0-2) 
This zero-filled `[0u8; 33]` array is not a valid compressed secp256k1 public key (compressed keys must start with `0x02`/`0x03`), so it will fail `StacksPublicKey::from_slice` and turn into a `BadSignerPublicKey` error downstream. `NakamotoSigners::make_signer_set` (in `stackslib/src/chainstate/stacks/boot/mod.rs`, `make_signer_set`) then happily wraps any such zero-key signer with weight `> 0` into the finalized `NakamotoSignerEntry` set that is later fed to the signer's stacks-client via `get_reward_set_signers`, with no further validation of the key bytes.

This defect is only reachable through `get_parsed_reward_set` at the point every signer must load a reward set for a new/refreshed cycle (`get_signer_config` → `refresh_signer_config` → `initialize_runloop`), so the `.unwrap()` will fire for every signer process attempting to service that cycle, not just one victim.

### Impact Explanation
The panic kills the signer process at the exact moment it tries to configure itself for the affected reward cycle. Because `refresh_signer_config`/`initialize_runloop` are re-executed on every restart, the signer enters a crash-loop and never reaches the point where it can evaluate or sign any block proposal for that cycle — a liveness break matching "signer wedged into never signing valid blocks" for the reward cycle in question. This is not confined to a single attacker-controlled signer slot; it hits every honest signer process that loads the same tainted reward set, so it is a global availability failure for the cycle, not a localized one.

### Likelihood Explanation
The precondition is that a malformed/short `signer` buffer for a PoX-4 stacking entry reaches the confirmed reward set with nonzero weight — a scenario the chainstate's own code comment (`stackslib/src/chainstate/nakamoto/signer_set.rs:310`) flags as a known gap in Clarity's `(buff 33)` max-length-only enforcement. Whether an attacker can actually get such a short-buffer stacking entry accepted end-to-end by `pox-4.clar`'s signer-key-authorization/signature-verification logic could not be fully confirmed with the available tool budget — I was unable to trace the exact `stack-stx`/`set-signer-key-authorization` Clarity call paths in `pox-4.clar` to verify whether a minimum-length or signature-ownership check there already blocks a sub-33-byte `signer-key` from ever being committed to the PoX contract state. This is the crux uncertainty: if `pox-4.clar` rejects any `signer-key` buffer shorter than 33 bytes before storage, this path is unreachable and the `.unwrap()` is dead code for realistic inputs.

### Recommendation
Regardless of whether the PoX-4 path is currently reachable by an attacker, `RunLoop::get_parsed_reward_set` should not use `.unwrap()` on `SignerEntries::parse`. Propagate the `Error::BadSignerPublicKey` as a recoverable `ClientError` (as is already done for the `get_reward_set_signers` call directly above it), log it, and either skip the malformed entry (excluding it from the parsed set) or return `Ok(None)`/an error that `get_signer_config`/`refresh_signer_config` already know how to handle without crashing the process, preserving liveness for the rest of the honest signer set.

### Proof of Concept
```rust
// stacks-signer/src/runloop.rs (test module)
#[test]
fn malformed_signing_key_should_not_panic_get_parsed_reward_set() {
    // Build a NakamotoSignerEntry with an all-zero / invalid signing_key,
    // mirroring RawRewardSetEntry::from_pox_4_tuple's fallback for a
    // short `signer` buffer.
    let bad_entry = NakamotoSignerEntry {
        signing_key: [0u8; 33], // invalid: prefix byte must be 0x02/0x03/0x04
        stacked_amt: 100_000_000_000,
        weight: 1,
    };

    // Mock/stub stacks_client.get_reward_set_signers to return vec![bad_entry]
    // (or directly call SignerEntries::parse to demonstrate the panic surface).
    let result = std::panic::catch_unwind(|| {
        SignerEntries::parse(false, &[bad_entry.clone()])
    });

    // Current behavior: parse() returns Err, but RunLoop::get_parsed_reward_set
    // unwraps it directly, which would panic here if invoked instead of parse():
    assert!(result.is_ok());
    assert!(matches!(result.unwrap(), Err(libsigner::Error::BadSignerPublicKey(_))));

    // Desired fix assertion (post-patch): get_parsed_reward_set(reward_cycle)
    // should return Ok(None) or a recoverable Err(ClientError), never panic,
    // preserving the runloop's liveness for the rest of the reward cycle.
}
```
