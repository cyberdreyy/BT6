### Title
Builder payment `fee_recipient` is never bound to the proposer's committed preference in consensus-layer state transition - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_execution_payload_bid`, the consensus state-transition function that admits a builder's `SignedExecutionPayloadBid` into the chain, never checks that `bid.fee_recipient` matches the proposer's `SignedProposerPreferences` for that slot. The only place this binding is checked is `validate_execution_payload_bid_gossip`, a non-authoritative, `IGNORE`-level (i.e., advisory, not block-validity-affecting) gossip filter. This mirrors the CVE-2025-4143 bug class: a security-critical destination check exists at a soft/non-binding layer instead of the authoritative one, so the "wrong redirect target" (here, `fee_recipient`) is accepted by every spec-following node as a fully valid state transition.

### Finding Description
In `specs/gloas/beacon-chain.md`, `process_execution_payload_bid` verifies signature, builder activity/version, balance coverage, blob-commitment limits, slot/parent/hash/prev_randao consistency — but it contains no assertion relating `bid.fee_recipient` to anything derived from the proposer's declared `ProposerPreferences`: [1](#0-0) 

The intended binding is described only as guidance for honest builders in `specs/gloas/builder.md`: [2](#0-1) 

and the validator guide explicitly states this address "will receive the builder payment": [3](#0-2) 

The only actual enforcement of `bid.fee_recipient == proposer_preferences.fee_recipient` in the entire spec is in the gossip validator, and it is an `IGNORE`, not a `REJECT`: [4](#0-3) 

`IGNORE` only affects local gossip propagation/scoring; it is explicitly not a block-validity rule, and the spec explicitly permits bids to be obtained "by other off-protocol means" (i.e., bypassing gossip validation entirely): [5](#0-4) 

Once a proposer includes a `signed_execution_payload_bid` with an arbitrary `fee_recipient` in their block, `process_execution_payload_bid` records the pending payment to that exact address with no cross-check: [6](#0-5) 

Because this state-transition function is run identically by every node to validate blocks, the equality broken is: the Gwei payment committed by the builder (`bid.value`) is paid to whatever `fee_recipient` the builder wrote into the bid, with no consensus-enforced guarantee that this equals the address the proposer actually authorized via their signed `ProposerPreferences` message. All spec-following nodes agree the block is valid regardless — there's no fork/split, but the payment destination itself is unauthenticated at the consensus layer.

### Impact Explanation
This falls under "a builder payment ... misdirected" (High) or "Gwei ... paid to a non-owner" (Critical), depending on trust assumptions:
- Builder payments are meant to go to the address in the proposer's signed `SignedProposerPreferences`. Since `process_execution_payload_bid` never checks this, any entity capable of getting a bid into a proposer's block (a relay, an off-protocol builder API, or a builder colluding with tooling that doesn't re-derive/re-check `fee_recipient` before signing) can redirect the entire builder payment for that slot to an arbitrary address instead of the proposer-designated one.
- Because bids can legitimately be delivered "by other off-protocol means" (bypassing gossip's `IGNORE` filter, which is the only place this check exists), the redirection is not something an honest, spec-only validator implementation can catch — the check simply doesn't exist in the authoritative execution path.

### Likelihood Explanation
Likelihood is non-trivial in realistic MEV-relay architectures: today's block-building pipelines (analogous to MEV-Boost) already deliver bids to proposers out-of-band rather than via p2p gossip, exactly the "off-protocol means" the spec calls out. Any relay/builder software bug or compromise that forwards a bid without re-validating `fee_recipient` against the proposer's own preference results in silent payment misdirection with no consensus-level safety net.

### Recommendation
Add an explicit consensus-level assertion inside `process_execution_payload_bid` binding `bid.fee_recipient` (and ideally `bid.gas_limit`) to the proposer's authenticated preference for `bid.slot`, mirroring the check currently only present in the gossip validator, so that the check is enforced by state transition and cannot be bypassed by off-protocol bid delivery.

### Proof of Concept
1. Proposer P for slot `S` broadcasts `SignedProposerPreferences{proposal_slot=S, fee_recipient=A}`.
2. A relay/builder delivers (off-protocol, not via gossip) `SignedExecutionPayloadBid{slot=S, fee_recipient=B, value=V, ...}` with a valid builder signature, `B != A`.
3. Proposer's node includes this bid in its block for slot `S` (gossip's `fee_recipient` `IGNORE` check was never invoked because the bid didn't arrive over gossip).
4. `process_execution_payload_bid` accepts the block: signature valid, builder active/covers balance, slot/parent/hash/randao all match — no check ever compares `bid.fee_recipient` to `A`.
5. `state.builder_pending_payments` (and later `builder_pending_withdrawals`) records `fee_recipient=B`, so value `V` gwei is ultimately paid to `B`, not `A`, even though every node in the network validates and accepts this block as fully spec-compliant.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
