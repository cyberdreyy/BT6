Found a concrete indexing vulnerability that matches the "decoder panic and misreporting from unprivileged input" impact category.

### Title
Out-of-bounds panic in SPL-Token `WithdrawWithheldTokensFromAccounts` / `HarvestWithheldTokensToMint` instruction parsing crashes RPC on `getTransaction`/`getBlock` - (File: transaction-status/src/parse_token/extension/transfer_fee.rs)

### Summary
The external report's core bug class is "trusting caller/attacker-controlled structured data without validating consistency between related fields before using it to index/act," which lets an unprivileged party trigger crashing or fund-losing logic. The closest reachable analog in Agave is in `parse_transfer_fee_instruction()`, where the number of "source accounts" to slice out of `account_indexes` is taken directly from attacker-controlled instruction data (`num_token_accounts`) and only loosely checked against the *total* account count, not validated for internal consistency, before indexing into `account_keys` with values from `account_indexes`.

### Finding Description
`parse_transfer_fee_instruction` in [1](#0-0)  handles `TransferFeeInstruction::WithdrawWithheldTokensFromAccounts { num_token_accounts }`. It calls `check_num_token_accounts(account_indexes, 3 + num_token_accounts as usize)` (a length check against `account_indexes.len()`), then does:
```rust
for i in account_indexes[first_source_account_index..].iter() {
    source_accounts.push(account_keys[*i as usize].to_string());
}
```
`account_keys[*i as usize]` indexes into `account_keys` (the transaction's static/loaded account list) using a raw `u8` value taken from `instruction.accounts` — a byte array that is part of the raw `CompiledInstruction` supplied by whoever crafted the transaction message. `check_num_token_accounts` (defined in [2](#0-1)  ) only validates the *count* of account indexes, not that each individual byte value in `account_indexes` is `< account_keys.len()`.

Similarly `HarvestWithheldTokensToMint` at [3](#0-2)  iterates `account_indexes.iter().skip(1)` and does the same unchecked `account_keys[*i as usize]` indexing.

Because `CompiledInstruction.accounts` is only required by the runtime to reference valid indices *at execution time for the top-level instruction actually executed*, and because this parsing path is invoked later, by the RPC layer, purely for **display purposes** against data already committed to the `Blockstore` (via `get_transaction`/`get_block`, calling into `transaction_status::parse_instruction::parse` → `parse_token` → `parse_transfer_fee_instruction`, see [4](#0-3)  and [5](#0-4) ), any user who can get a transaction containing a spl-token-2022 `TransferFeeExtension::WithdrawWithheldTokensFromAccounts` (or `HarvestWithheldTokensToMint`) instruction included in a block — even one whose top-level instruction ultimately fails at runtime, since the failing instruction's raw bytes are still stored in the transaction message — can supply an account-index byte that is out of range relative to `account_keys.len()` for that instruction's local account slice, if `account_indexes` (a `&[u8]` subslice from `instruction.accounts`) itself is not bounds-validated element-wise.

### Impact Explanation
An out-of-range index into `account_keys` (a `Vec<Pubkey>`-backed slice/`AccountKeys`) causes a Rust panic. Since `parse_token`/`parse_transfer_fee_instruction` executes inside the `solJsonRpcSvc` thread pool when serving `getTransaction`, `getBlock`, `getConfirmedTransaction` and similar RPC methods (see `rpc/src/rpc.rs`), a panic here crashes or poisons the serving thread, causing a decoder panic that can degrade or take down RPC service for a single, unprivileged, unauthenticated request — matching the allowed "decoder panic and misreporting" impact class.

### Likelihood Explanation
Reaching this code only requires that a transaction containing this instruction shape exist in a confirmed/rooted block (it does not need to succeed at runtime — the compiled instruction bytes are stored regardless of execution outcome) and that any client subsequently calls `getTransaction`/`getBlock` on it. This is achievable by any user submitting a normal transaction; no validator/peer/operator privilege is required.

### Recommendation
In `check_num_token_accounts` / `parse_transfer_fee_instruction` and `HarvestWithheldTokensToMint`, validate that every byte in the relevant `account_indexes` slice is `< account_keys.len()` before using it to index, returning `ParseInstructionError::InstructionKeyMismatch` instead of panicking (mirroring the pattern already used in `parse_system.rs`, see [6](#0-5) , which explicitly checks `instruction.accounts.iter().max()` against `account_keys.len()` before any indexing).

### Proof of Concept
1. Craft a transaction whose message includes an instruction targeting the SPL-Token-2022 program id, with instruction data encoding `TransferFeeInstruction::WithdrawWithheldTokensFromAccounts { num_token_accounts: N }`, and an `accounts` byte array of length `3+N` where at least one of the trailing `N` "source account" index bytes is `>= account_keys.len()` for that message.
2. Submit the transaction (it may fail at runtime harmlessly, e.g. due to missing/invalid accounts) so it is still included and its raw compiled instruction is committed to the ledger/blockstore with transaction status metadata.
3. Call `getTransaction`(signature) or `getBlock`(slot) via JSON-RPC.
4. The RPC thread invokes `parse_token` → `parse_transfer_fee_instruction`, which executes `account_keys[*i as usize]` with the out-of-range index and panics, crashing/poisoning the serving worker thread from a single unauthenticated RPC call.
