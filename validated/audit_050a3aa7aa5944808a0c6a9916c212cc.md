### Title
Mid-epoch depositor can immediately requestWithdraw to book full-epoch interest and dilute existing tranche holders - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` mints tranche tokens at a discounted price that credits the depositor only the *prorated* interest for the remaining epoch time, but `requestWithdraw` unconditionally books the *full-epoch* interest share for the requested amount via `_calcInterestWithdrawRequest`. There is no cooldown or holding-period check between the two calls, so a KYC'd lender can deposit mid-epoch (even seconds before `epochEndDate`) and atomically request a withdrawal that claims a full epoch of yield on capital that was deployed for only a fraction of it. The excess interest is not paid by the borrower (`expectedEpochInterest` was only increased by the prorated amount at line 728), so it is socialized across the remaining tranche holders at `stopEpoch`.

### Finding Description
In `depositDuringEpoch` the depositor's interest is deliberately prorated to the time they actually participate:

```solidity
uint256 interest = _calcInterest(_amount) *
  (remaining + buffer) /
  (epochDuration + buffer);
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
...
expectedEpochInterest += interest;   // only prorated interest added
``` [1](#0-0) 

`requestWithdraw` has no epoch-running check and no minimum holding time; it prices principal at current NAV (`_trancheToUnderlyings`) and computes interest as the amount's proportional share of **total tranche interest for the whole epoch**:

```solidity
uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
_interest = _amount * totTrancheInterest / _trancheBal;
``` [2](#0-1) 

Because the mint at line 724 barely moves the tranche price (NAV grows by `_amount`, supply by `minted ≈ (_amount + trancheInterest) / priceEnd`), the attacker's `principal` from `_trancheToUnderlyings` is ≈ their deposit, and the booked `_interest` is a **full-epoch** share regardless of when they deposited. The `_diff`/`interestForOverUnderPerformance` bookkeeping only reconciles the AA/BB split at the *next* `startEpoch`; it does not reduce the interest promised to the receipt this epoch. `creditVault.requestWithdraw(_underlyings, msg.sender, principal)` then fixes the receipt at `principal + interest - fees`.

Conditions that must hold (all owner/manager-side, honest): `isDepositDuringEpochDisabled == false`, `isAYSActive == false`, not programmable-borrower mode, tranche supply non-zero, and attacker passes `isWalletAllowed` (KYC) — all satisfiable by an unprivileged lender in a fixed-APR running epoch.

### Impact Explanation
Direct theft via yield dilution, quantifiable: on a 365-day epoch at 10% APR, depositing 1000 underlying on day 364 mints shares priced for ≈1 day of interest (≈0.27), but the same-block `requestWithdraw` books ≈100 of interest (minus management/performance fees — still ~90 net with 10% perf fee and zero mgmt fee). The borrower only owes the prorated ~0.27 extra (`expectedEpochInterest`), so ~99 of the claim is paid out of the epoch interest belonging to honest holders, lowering `virtualPrice` at `stopEpoch` for everyone else. Repeated or large-scale execution can push pending withdrawals beyond available repayment, causing partial insolvency for later claimants.

### Likelihood Explanation
Requires `depositDuringEpoch` to be enabled (it is an owner-gated feature that exists precisely to allow mid-epoch entry) and a running fixed-APR epoch. Any KYC-passing lender can execute deposit + withdraw-request atomically; profit scales with elapsed epoch fraction and APR, and is largest near `epochEndDate` where the prorated mint credit is smallest while the withdraw credit remains full-epoch. No privileged collusion, oracle, or timing-of-honest-call dependence beyond the epoch being in its running phase.

### Recommendation
Apply the same proration in `_calcInterestWithdrawRequest` that `depositDuringEpoch` uses for minting: track each holder's deposit timestamp (or an interest-vesting basis per tranche token), and scale the withdraw-request interest by `min(elapsed participation, epochDuration) / epochDuration`. Alternatively, enforce a cooldown so tranche tokens minted via `depositDuringEpoch` cannot be used in `requestWithdraw` until the following epoch, and exclude freshly minted supply from `_trancheBal` in the interest-share calculation.

### Proof of Concept
Foundry fork/invariant PoC sketch (based on `test/foundry/IdleCreditVault.t.sol` mid-epoch helpers):

```solidity
function testMidEpochDepositWithdrawSandwich() external {
    // 365-day epoch, 10% apr, fees enabled; honest holder deposits 1000, epoch starts
    idleCDO.depositAA(1000 * ONE_SCALE);
    vm.prank(owner); cdoEpoch.setIsAYSActive(false);
    _startEpochAndCheckPrices(0);

    // warp to day 364 of the epoch
    vm.warp(cdoEpoch.epochEndDate() - 1 days);
    vm.prank(owner); cdoEpoch.setIsDepositDuringEpochDisabled(false);

    // attacker: KYC'd lender
    address attacker = makeAddr("sandwich");
    deal(defaultUnderlying, attacker, 1000 * ONE_SCALE);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), 1000 * ONE_SCALE);
    uint256 minted = cdoEpoch.depositDuringEpoch(1000 * ONE_SCALE, address(AAtranche));
    // same-block withdraw request books full-epoch interest
    uint256 requested = cdoEpoch.requestWithdraw(minted, address(AAtranche));
    vm.stopPrank();

    // requested >> principal + prorated(1 day) interest; e.g. ~1090 vs ~1000.27 expected fair
    assertGt(requested, 1000 * ONE_SCALE + 0.3 * ONE_SCALE);
    // at stopEpoch the shortfall is socialized: honest holder's virtualPrice drops
}
```

Run the existing numerical harness: fair value of the receipt should be ≈1000.27 (1-day prorated) but the code books a proportional share of the full 100-unit epoch interest; assert `requested ≈ 1090` while `expectedEpochInterest` only increased by ≈0.27, demonstrating the dilution of the remaining AA holders at `stopEpoch`.

    if (expectedInt > pendingFees) {

        _netGainAfterFees(expectedInt - pendingFees, _calculateManagementFee(lastNAVAA + lastNAVBB, remaining)),
        _tranche
      );
    }
    // interest this deposit will earn for the tranche over the remaining time (net of fees)
    uint256 trancheInterest = _calcTrancheInterestShare(
      _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
      _tranche
    );
    // pre-deposit expected final NAV for existing holders.
    // This won't ever be zero as we checked _trancheTotSupply and we seed initial NAV at tranche creation
    uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;

    // mint at a discounted price so depositor gets principal + its prorated interest at epoch end
    // A mid‑epoch depositor should get _amount + trancheInterest at epoch end.
