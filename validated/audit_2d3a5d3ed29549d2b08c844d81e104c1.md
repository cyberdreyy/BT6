### Title
Malicious/laggy current-tenure miner can indefinitely reset the inactivity timer, blocking signer fallback to a valid prior miner - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs`, lines 376-478) stamps `tenure_activity.last_activity_time` for the *current* tenure every time it observes a conflicting or non-advancing block proposal from that tenure's miner — before that proposal has been validated, pre-committed, or signed. Both the V1 and V2 `is_timed_out` checks (`stacks-signer/src/chainstate/v1.rs:55-94` and `stacks-signer/src/chainstate/v2.rs:48-89`), which gate the fallback from an unresponsive/malicious miner to the previous valid miner, read exactly this timestamp. A miner that cannot or will not produce a valid, advancing block can keep re-proposing cheap, rejected, non-advancing blocks (each with a trivially different signature hash, e.g. differing timestamp) purely to keep resetting this timer, preventing the signer set from ever falling back and thereby stalling block production for that tenure.

### Finding Description
`check_latest_block_in_tenure` is the shared routine used by `check_block_against_signer_db_state` at proposal time, at validate-ok, and at signing time (see `docs/signer-flows.md:389-420`). When a proposed block does not advance beyond the tenure's last signed/committed block, the function does **not** just reject it — it also calls:

The current tenure's miner is the only entity that can produce a block whose `consensus_hash` matches the active tenure and whose miner signature is accepted by `check_proposal`/`recover_miner_pk` far enough to reach this check — so this is triggerable by exactly a "one-slot miner" (the currently active, sortition-winning miner), exactly as scoped. Each such proposal is cheap: it need not be valid, need not advance the chain, and need not ever reach pre-commit or signature — it only has to be a *distinct* signer-signature-hash (trivially achieved by varying the block timestamp) so that `handle_block_proposal`'s dedup-by-hash (`block_lookup_by_reward_cycle`) treats it as new and re-runs the chainstate check (`stacks-signer/src/v0/signer.rs:1591-1604`). [5](#0-4) 

This is structurally the same bug class as the report: a low-cost, attacker-controlled, repeatable action (there: `depositWeth(receiver, 1 wei)`; here: propose-a-non-advancing-block) resets a timestamp that gates a protective mechanism for someone else's benefit (there: the staker's reward accrual clock; here: the signer set's fallback-to-honest-miner clock), defeating the intended safeguard.

### Impact Explanation
This breaks the liveness guard documented in `docs/signer-flows.md:450-533`: "`check_miner_inactivity` ... asks whether the current miner has gone inactive ... measure[d as] time since the last activity ... against `block_proposal_timeout`." A miner that goes rogue (refuses/fails to build a valid, advancing block) but keeps broadcasting throwaway proposals never becomes "inactive" in the eyes of the signer set, because every rejected/non-advancing proposal it sends resets the same clock that is supposed to detect its unresponsiveness. The signer set is thus wedged: it will never revert to the prior, valid miner, and no new valid block can be produced for the tenure — this is a liveness wedge matching the in-scope impact category "a signer wedged into never signing valid blocks."

### Likelihood Explanation
The action requires no special privilege beyond being the currently active miner for a tenure (a normal, permitted role — the "one-slot miner" allowed by scope) and gossiping proposals over the miner→signer channel, which is standard traffic the signer set must process. No majority of signers, no other signer's key, and no auth token are needed. The cost per resend is a single trivially-crafted block proposal (a fresh signature hash via a timestamp bump), directly analogous to the "1 wei" cost in the original report.

### Recommendation
Do not let a non-advancing/rejected block proposal from the current tenure indefinitely refresh miner-activity for the purpose of suppressing `is_timed_out`. Specifically:
- Consider bounding how many times or how long a single tenure's `last_activity_time` may be refreshed purely by conflicting/non-advancing proposals (as distinct from genuinely useful signed/pre-committed progress), or
- Require that activity resets from `check_latest_block_in_tenure`'s "reorg attempt" and "pre-commit conflict" branches only count while there is independent evidence the tenure is still making forward progress (e.g., rate-limit by unique proposed chain length, not by wall-clock resend), so that a miner cannot manufacture indefinite "activity" from stalled or invalid proposals alone.

### Proof of Concept
1. Miner M wins the current tenure/sortition and is the `ActiveMiner` in the signer set's state machine.
2. M proposes and gets a first block signed (or pre-committed) — establishing a "last signed/pre-committed block" for the tenure.
3. M then repeatedly proposes new, non-advancing blocks at or below the same chain height (each with a bumped `timestamp` field to produce a distinct `signer_signature_hash`, so `handle_block_proposal` treats each as a fresh proposal rather than a resend).
4. Each such proposal reaches `check_block_against_signer_db_state` → `check_latest_block_in_tenure`, fails the height check, and — per lines 403-417 — calls `signer_db.update_last_activity_time(...)` with the current time before being rejected.
5. As long as M repeats step 3 faster than `block_proposal_timeout` (v1) / the configured timeout (v2), `is_timed_out` in `chainstate/v1.rs`/`v2.rs` never returns `true`.
6. `check_miner_inactivity` therefore never falls back to the prior sortition's miner, and the tenure never produces a new valid, signed block, stalling the chain for as long as M keeps sending throwaway proposals. [6](#0-5) [7](#0-6)

    pub fn check_latest_block_in_tenure(
        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }
        }

        // A block we have only pre-committed to must NOT veto this proposal, but, similar to above
        // this should still count as activity for the miner.
        let last_accepted_block = signer_db
            .get_last_accepted_block(tenure_id)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;
        if let Some(info) = last_accepted_block {
            let is_fresh_pre_commit = info.state == BlockState::PreCommitted
                && info.approved_time.is_some_and(|approved_time| {
                    approved_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
                        > get_epoch_time_secs()
                });
            if is_fresh_pre_commit && block.header.chain_length <= info.block.header.chain_length {
                info!(
                    "Miner's block proposal conflicts with a block we have only pre-committed to. Counting it as miner activity, but not rejecting the proposal.";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "pre_committed_signer_signature_hash" => %info.block.header.signer_signature_hash(),
                    "pre_committed_chain_length" => info.block.header.chain_length,
                );
                if let Err(e) = signer_db
                    .update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())
                {
                    warn!("Failed to update last activity time: {e}");
