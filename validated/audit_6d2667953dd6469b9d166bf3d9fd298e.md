### Title
External Initiator credentials satisfy `auth.GetAuthenticatedUser` and can trigger `RunJobV2` for arbitrary integer job IDs, bypassing the "EIs not allowed" restriction - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the integer-ID run path with `isUser` from `auth.GetAuthenticatedUser`, intending that only real dashboard/API-token users (not External Initiators) can trigger runs by numeric job ID. However, `auth.AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic `clsessions.User{Role: UserRoleRun}`, so `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests, defeating the intended restriction.

### Finding Description
In `core/web/pipeline_runs_controller.go` `Create` (lines 109-125), the code explicitly comments: "only users are allowed to run jobs using int IDs - EIs not allowed", and gates the `strconv.ParseInt`/`prc.App.RunJobV2` call behind `isUser`: [1](#0-0) 

The `isUser` flag comes from `auth.GetAuthenticatedUser(c)`, which merely checks presence of `SessionUserKey` in the gin context: [2](#0-1) 

But `auth.AuthenticateExternalInitiator` — the auth method invoked when a request presents valid `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers — sets *both* `SessionExternalInitiatorKey` and `SessionUserKey` (with a synthetic run-role user) after validating the EI's credentials: [3](#0-2) 

Because `SessionUserKey` is set for EI-authenticated requests too, `GetAuthenticatedUser` returns `(user, true)` for them, making `isUser == true` in `Create`. This means an EI credential holder passes the exact check meant to exclude EIs, reaches `strconv.ParseInt(idStr, 10, 32)`, and if the supplied `:ID` parses as an int32, `prc.App.RunJobV2(ctx, jobID, nil)` is invoked for that job ID — with no verification that the EI is associated with, or authorized for, that specific job. Any job ID in the system (webhook or otherwise) can be targeted this way, since `RunJobV2` performs no EI-to-job binding check either.

### Impact Explanation
This is an authorization-bypass / unauthorized-job-run vulnerability: a credential meant to be scoped to invoking a single externally-triggerable job (an External Initiator's bridge/webhook) can instead trigger `RunJobV2` for **any** job in the node by numeric ID, including jobs unrelated to the EI's registration. Depending on job type, `RunJobV2` executes the job's pipeline, which can lead to unauthorized on-chain transmissions, unwanted external HTTP calls, resource exhaustion, or triggering flux-monitor/OCR-style runs outside their intended trigger conditions — a violation of the "one gateway/EI credential bound to one authorized job" invariant.

### Likelihood Explanation
Exploitability requires only a valid External Initiator credential (`AccessKey`/`Secret` pair), which is a low-privilege credential explicitly designed to be restricted to specific webhook job(s) it was provisioned for. No admin/user session or special role is needed beyond having any EI registered on the node — the bypass works for *any* integer job ID guessable or enumerable via the API, not just the EI's own job. This is deterministic and repeatable on every request.

### Recommendation
Distinguish EI-originated sessions from true user sessions before applying the "only users allowed" restriction — e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or otherwise strictly bind) when set, rather than relying solely on `GetAuthenticatedUser`. Additionally, if EI-triggered runs by integer ID are ever intended to be supported, add an explicit authorization check binding the specific EI to the specific job (e.g., verify the job's bridge/webhook configuration references that EI) before calling `RunJobV2`.

### Proof of Concept
1. Handler/integration test in `core/web/pipeline_runs_controller_test.go`:
   - Create an application, register an `ExternalInitiator` (`bridges.NewExternalInitiator`) unrelated to any job.
   - Create an unrelated job (e.g., an OCR job as in `setupPipelineRunsControllerTests`) not associated with that EI.
   - Issue `POST /v2/jobs/<jobID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials (no session cookie, no API token).
   - Assert: current behavior returns `200 OK` and `RunJobV2` executes for the unrelated job (mock/spy on `app.RunJobV2` or assert a new `pipeline.Run` row exists for that job).
   - Expected fixed behavior: request should be rejected with `401`/`422` because the caller authenticated as an EI, not a real user, and/or because the EI has no authorization for that job.

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
```

```go
// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
```
