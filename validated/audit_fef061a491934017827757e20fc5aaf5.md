### Title
Post-default instant-withdraw receipts are paid from the default recovery reserve at the default-epoch haircut, even though their basis was never included in recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug frees a pool-owned object with `kfree()` — the wrong release path corrupts a shared pool. The analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: after `finalizeDefaultRecovery`, every instant receipt recorded under `defaultRecoveryEpoch` is released through `_transferDefaultRecovery` (the isolated recovery pool), while the amount of reserve was fixed at finalization by `defaultPendingClaimBasis()`. Instant requests made *after* finalization land in the same epoch bucket (`instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `epochNumber` never advances once the pool is defaulted), so they draw down a reserve they were never accounted for — a "free into the wrong pool" that corrupts `defaultRecoveryReserve` and can permanently freeze legitimate defaulted claims.

### Finding Description
- `finalizeDefaultRecovery` sizes the reserve once: `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount / totalBasis`, where `totalBasis` includes only `pendingWithdraws` and current-epoch instant claims that existed at finalization (`defaultPendingClaimBasis`, lines 644-649). It also sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (lines 686-696).
- `requestInstantWithdraw` has no default guard: it burns the CDO's strategy tokens, mints a receipt to the user, and records it under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` — which, post-finalization, is still `defaultRecoveryEpoch` (lines 356-375). Compare with `requestWithdraw`, which routes post-default requests into `postDefaultRequests` paid 1:1 (lines 247-257).
- On `claimInstantWithdrawRequest`, `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` triggers `_claimDefaultedInstantWithdrawRequest`, which reads exactly that epoch slot, zeroes it, decrements `pendingInstantWithdraws`, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery` — consuming `defaultRecoveryReserve` (lines 380-393, 842-856, 912-917).
- Because the attacker's post-default basis was never in `totalBasis`, the reserve is under-collateralized by exactly the attacker's claim. When enough legitimate claimants later call `_claimDefaulted*`, `defaultRecoveryReserve -= _amount` underflows and reverts, permanently freezing the remaining recovery funds (the pool is defaulted; there is no path to refill the reserve).

### Impact Explanation
An attacker holding tranche tokens (unprivileged lender) drains `recoveryPrice × A` from the isolated reserve for a request of size `A` that contributed zero recovery basis, and/or causes `defaultRecoveryReserve -= _amount` to revert for honest defaulted claimants — permanent freezing of unclaimed recovery equal to the reserve shortfall. Loss is bounded by the attacker's post-default instant request size; with `recoveryPrice` near par (over-recovery), it approaches the full request amount.

### Likelihood Explanation
Requires `defaultInstantWithdrawsFinalized == true` (i.e., `pendingInstantWithdraws != 0` at finalization — a partially funded instant queue at default), `recoveryPrice > 0`, and that `IdleCDOEpochVariant` still routes `requestInstantWithdraw`/`claimInstantWithdrawRequest` to the strategy after default (the strategy imposes no default check itself). I could not fully verify the CDO-side gating of instant requests post-default; if the CDO blocks them, this path is unreachable and the finding collapses.

### Recommendation
- In `requestInstantWithdraw`, revert (or route into `postDefaultRequests`-style par accounting) when `defaultRecoveryFinalized` is true, mirroring `requestWithdraw`.
- Alternatively, key `_claimDefaultedInstantWithdrawRequest` eligibility on receipts that existed at finalization (e.g., a per-user finalized snapshot) so post-finalization receipts cannot consume the reserve.
