### Title
Dust-Stake Sybil Identities Bypass Per-Peer QUIC Connection/Stream Limits in TPU Ingest - (File: `streamer/src/nonblocking/swqos.rs`)

### Summary
The go-ipfs CVE describes attackers generating cheap ephemeral identities to defeat a peer-based connection-management/reputation system. Agave's QUIC TPU ingest path (`SwQos`) has an analogous weakness: a peer whose self-asserted identity has *any* nonzero stake keeps a `Some(pubkey)` identity even when it is reclassified as `ConnectionPeerType::Unstaked` for being below the minimum stake ratio. Because the connection table key is chosen by identity presence rather than by the peer's *effective* class, such "dust-stake" peers are keyed by `Pubkey` instead of by `IP`, letting a single source IP register unlimited independent per-identity connection slots and independent per-identity stream token buckets in the unstaked pool — defeating the intended per-IP/per-peer ingest caps.

### Finding Description
Every QUIC client presents a self-signed X.509 certificate embedding an arbitrary Ed25519 pubkey; the server extracts it with no external validation beyond signature well-formedness: [1](#0-0) 

`get_connection_stake` looks this pubkey up against the current `staked_nodes` table: [2](#0-1) 

In `SwQos::build_connection_context`, if the pubkey has *any* stake, `remote_pubkey` is set to `Some(pubkey)` — but `peer_type` can still be downgraded to `ConnectionPeerType::Unstaked` when `stake_ratio < min_stake_ratio`: [3](#0-2) 

The connection table key is then derived purely from whether a pubkey exists, not from the resulting `peer_type`: [4](#0-3) [5](#0-4) 

So a "downgraded" dust-stake peer is inserted into the `unstaked_connection_table` (subject to unstaked global caps and pruning) but keyed by `Pubkey` rather than `IP`. `try_add_connection` enforces `max_connections_per_unstaked_peer` per *key*: [6](#0-5) 

and allocates a brand-new independent `ConnectionStreamCounter` (token bucket) per unique key via `stream_counter_factory`: [7](#0-6) 

Because each distinct dust-stake identity is a unique `ConnectionTableKey::Pubkey`, an attacker controlling many such identities from one IP address gets `N × max_connections_per_unstaked_peer` connections and `N` independent stream-rate buckets, instead of the single IP-scoped allotment a genuinely unstaked (no-stake) peer would receive (which is correctly keyed by `IP`, per `ConnectionTableKey::new`'s `None` branch).

### Impact Explanation
This allows resource-exhaustion/ingest-starvation of the validator's TPU QUIC listener from a single network location: connection-count and stream-rate limits that are meant to bound abuse per network peer are instead scoped per self-chosen identity, which is nearly free to mint (any pubkey with dust delegated stake). This can crowd out legitimate unstaked and low-stake traffic, degrade transaction ingestion, and consume server-side resources (connection table entries, token buckets, uni-stream slots) disproportionately — a direct analog of the IPFS Sybil-based routing/connection-table poisoning described in the report, but applied to Agave's TPU streamer connection admission control.

### Likelihood Explanation
Moderate-to-high. No leaked keys, MITM, or privileged access are required — any party can self-sign a certificate binding an arbitrary pubkey, and only needs to have *some* stake delegated to that pubkey (even a tiny/dust amount below the stake-ratio threshold) recorded in `staked_nodes`, which is realistically obtainable at low cost by delegating minimal stake to many identities. The bypass is triggered automatically by existing logic in `build_connection_context`/`cache_new_connection`; no race condition or complex timing is needed.

### Recommendation
Derive `ConnectionTableKey` from the *effective* `peer_type` after downgrade, not from raw pubkey presence: when `peer_type` resolves to `ConnectionPeerType::Unstaked` (including the low-stake-ratio downgrade path), key by IP instead of by pubkey, mirroring the no-stake case. Alternatively, apply a separate IP-scoped cap across all unstaked-classified connections (regardless of key) before/alongside the per-key cap in `try_add_connection`/`ConnectionTable::try_add_connection`.

### Proof of Concept
1. Set up a validator with `staked_nodes` containing many attacker-controlled pubkeys, each delegated a stake amount below `min_stake_ratio` (per `SwQos::build_connection_context`), all connecting from the same source IP.
2. Establish `N` QUIC connections, each presenting a distinct self-signed certificate for one of these dust-stake pubkeys.
3. Observe each connection is inserted into `unstaked_connection_table` keyed by its unique `Pubkey` (not by the shared IP), each receiving its own `max_connections_per_unstaked_peer` allotment and independent `ConnectionStreamCounter`, exceeding the connection/stream budget a single IP is normally permitted under the unstaked, no-stake path.

pub fn get_connection_stake(
    connection: &Connection,
    staked_nodes: &RwLock<StakedNodes>,
) -> Option<(Pubkey, u64, u64)> {
    let pubkey = get_remote_pubkey(connection)?;
    debug!("Peer public key is {pubkey:?}");
    let staked_nodes = staked_nodes.read().unwrap();
    Some((
        pubkey,
        staked_nodes.get_node_stake(&pubkey)?,
        staked_nodes.total_stake(),
    ))
}
