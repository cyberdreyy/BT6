### Title
`PipelineRunsController.Create` isUser check is bypassable by External Initiator auth, allowing an EI credential holder to trigger runs on arbitrary integer job IDs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` is meant to reject External-Initiator (EI) authenticated requests that use an integer job ID (the comment explicitly states "EIs not allowed" for int IDs, only UUID webhook jobs). However, the check `_, isUser := auth.GetAuthenticatedUser(c)` is satisfied for EI-authenticated requests too, because `AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic `run`-role user. This lets an EI credential holder call `prc.App.RunJobV2(ctx, jobID, nil)` for any numeric job ID, not just the job the EI is bound to.

### Finding Description
`auth.AuthenticateExternalInitiator` authenticates a request purely using the `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers, resolves the matching `ExternalInitiator` row, and then sets both the EI context key and a synthetic user object: [1](#0-0) 

Later, `GetAuthenticatedUser` simply reads back whatever was stored under `SessionUserKey`, without distinguishing whether it was set by a real session/token authentication or by the EI middleware's synthetic user: [2](#0-1) 

`PipelineRunsController.Create` uses exactly this ambiguous check to decide whether the caller is allowed to use an integer job ID (as opposed to the UUID-based webhook flow, which has been removed): [3](#0-2) 

The comment "only users are allowed to run jobs using int IDs - EIs not allowed" documents the intended restriction, but the code checks `isUser`, which is `true` for both a genuine session/token-authenticated user and an EI-authenticated request (since both populate `SessionUserKey`). There is no code path here that checks `auth.GetAuthenticatedExternalInitiator(c)` to reject EI-originated requests, nor any check that the numeric job ID corresponds to a job actually bound to the authenticated EI. Consequently, if the route serving `POST /v2/jobs/:ID/runs` accepts `AuthenticateExternalInitiator` as one of its auth methods (as the comment implies it must, otherwise the guard would be dead code), a valid EI credential holder can supply any integer job ID and have `RunJobV2` executed for that job — a job that may belong to a completely different tenant/EI.

I was not able to confirm from the available index whether `RunJobV2` performs any additional ownership/binding validation between the EI and the target job ID; the `Application.RunJobV2` implementation was not fully retrievable. However, the controller-level check that the code comment states is the intended safeguard is provably broken as written.

### Impact Explanation
An EI credential holder (a low-privilege, non-admin credential type) can trigger job runs (`RunJobV2`) on jobs it does not own by supplying an arbitrary integer job ID, instead of being confined to its own bound webhook job. This is a cross-tenant unauthorized job-run injection: unwanted/unauthorized execution of pipeline runs (potentially with real-world side effects such as external adapter calls, on-chain transactions in the pipeline, etc.) on jobs belonging to a different EI/tenant, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Precondition is only possession of a valid EI access key/secret pair (no admin/session/API token needed). If the route accepting `POST /v2/jobs/:ID/runs` includes `auth.AuthenticateExternalInitiator` in its authentication chain (which the explicit code comment strongly implies, since it exists solely to defend against this scenario), exploitation requires nothing more than sending a request with a different job's numeric ID — trivially repeatable and does not require any interaction with the legitimate job owner.

### Recommendation
In `PipelineRunsController.Create`, do not rely on the presence of `SessionUserKey` alone to gate the "int ID" path. Explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject the request (or route it through EI-specific, ownership-validated logic) if an EI principal is present, regardless of whether `SessionUserKey` also happens to be set. Alternatively, stop `AuthenticateExternalInitiator` from populating `SessionUserKey`, or tag the synthetic user distinctly (e.g., a dedicated context key) so `isUser` cannot be conflated with genuine user authentication.

### Proof of Concept
1. In `core/web/auth/auth_test.go` (or a new controller-level test), authenticate a `gin.Context` via `auth.AuthenticateExternalInitiator` using valid EI access/secret headers for `EI-A`, bound to `Job-A`.
2. Assert that `auth.GetAuthenticatedUser(c)` returns `ok == true` with `Role == clsessions.UserRoleRun` (confirming the synthetic user is indistinguishable from a real one at the `isUser` check).
3. Add a handler-level integration test for `PipelineRunsController.Create`: set up two jobs, `Job-A` (bound to `EI-A`) and `Job-B` (bound to `EI-B`, or a plain user-owned job). Send `POST /v2/jobs/:ID/runs` with `ID = Job-B`'s integer ID, authenticated using `EI-A`'s access key/secret headers.
4. Expected (secure) behavior: request should be rejected (403/422) because EI-A is not authorized for `Job-B`.
5. Observed (vulnerable) behavior: `isUser` evaluates `true`, `prc.App.RunJobV2(ctx, Job-B.ID, nil)` is invoked and a pipeline run resource for `Job-B` is returned, demonstrating cross-tenant run injection.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
