### Title
Predictable masking-store encryption key via pre-planted `masking.db`/key file in attacker-writable `RUNNER_TEMP_PROJECT_DIR` - (File: `commands/helpers/internal/store/store.go`)

### Summary
`Open()` decides whether to (re)generate encryption key material purely based on whether `masking.db` already exists and is non-empty, and derives the AEAD key by XOR-combining the first 32 bytes of `masking.db` with the contents of a companion key file whose name is a deterministic hash of the store path. Because the whole directory (`RUNNER_TEMP_PROJECT_DIR`/`.tmp` dir, i.e. `Build.TmpProjectDir()`) is writable by the job before proxy-exec ever runs, and both file names/paths are fully predictable, a job can pre-seed both files with known bytes and force the derived key to be attacker-known, defeating the masking store's confidentiality guarantee for any process that later opens the same store in that directory.

### Finding Description
`store.Open` at [1](#0-0)  only re-generates the companion key (`keyPath`) when `os.Stat(pathname)` reports the store file does not yet exist. `pathname` is always `filepath.Join(dir, "masking.db")` and `keyPath` is `filepath.Join(dir, "runner"+hex(sha256(pathname)))` — both fully deterministic and computable by anyone who knows `dir`, which for `proxy-exec` is `RUNNER_TEMP_PROJECT_DIR` set from `Build.TmpProjectDir()` [2](#0-1) , itself derived deterministically from the project slug/build dir [3](#0-2) .

If a job pre-creates `masking.db` with attacker-chosen bytes (size > 0) and also pre-creates the deterministically-named `keyPath` file with attacker-chosen bytes, then:
- `os.Stat(pathname)` succeeds, so the "regenerate key" branch is skipped [4](#0-3) .
- `openFile` opens the existing file without truncation (`O_APPEND|O_RDWR|O_CREATE`, no `O_EXCL`) [5](#0-4) .
- `info.Size() != 0`, so the "write new 32-byte key into store" branch is also skipped [6](#0-5) .
- `deriveEncryptionKey` reads `key1` from the attacker-controlled first 32 bytes of `masking.db` and `key2` from the attacker-controlled `keyPath` file, XORs them, and uses the result as the ChaCha20-Poly1305 key [7](#0-6) .

Since both inputs are fully attacker-known, the resulting AEAD key is fully attacker-known. No integrity check (HMAC/signature), no ownership/permission verification, and no atomic/exclusive creation exists to prevent this. Any subsequent `Add()`/`List()` call against that same store — e.g. a later `proxy-exec` invocation in the same directory (`NewProxy` → `store.Open` → `addmask.New`) [8](#0-7)  — will encrypt/decrypt masked secret phrases with a key the attacker already possesses.

The directory in question (`Build.TmpProjectDir()`) is a deterministic sibling of the build directory, constructed from the runner short id / concurrent-project-id / project slug, not per-job-run [9](#0-8) , so it is reused across sequential job executions in the same runner/concurrency slot for the same project — consistent with GitLab Runner's standard build-directory persistence model.

### Impact Explanation
Because the derived key is attacker-predictable, entries later written into the same `masking.db` (the plaintext phrases being masked, i.e. secret job variable values) via `Add()` can be decrypted by the attacker using the known key, and/or existing entries can be forged/replaced without detection (AEAD with a known key provides no protection against a party who knows the key). If the same `TmpProjectDir` is reused by a later job run in the same runner/project slot (standard build-dir reuse), an unprivileged job can poison the store ahead of time and later recover secret values recorded into that store by an intervening job — a scoped cross-job secret exfiltration.

### Likelihood Explanation
Feasible: the attacker only needs the ability to write into `RUNNER_TEMP_PROJECT_DIR`/`.tmp` before proxy-exec's first legitimate use, which is exactly the directory the question specifies the job controls, and only needs to know the fixed hashing scheme (`sha256` of `dir/masking.db`) to compute `keyPath`'s name — both derivable from public runner source code and a known, deterministic `dir`. The scenario requires build-directory reuse across sequential job runs (the default unless the runner/project is configured for fresh clones/ephemeral hosts each time), making it feasible but dependent on runner/project persistence configuration and job-scheduling timing to actually read back another job's ciphertext.

### Recommendation
- Use exclusive creation (`O_EXCL`) or a random, non-guessable per-invocation store/key filename instead of a name derived from a fixed hash of a predictable path.
- Bind the store to the current process/job (e.g., include a fresh, securely random nonce/salt generated and persisted only by `Open()` itself, verified via HMAC/AEAD tag, before trusting existing file contents).
- Reject or ignore pre-existing `masking.db`/key files that do not carry a verifiable marker proving they were created by the runner in the current job invocation (e.g., store a random session ID at creation time, checked with a MAC).
- Ensure `TmpProjectDir` (or at least the masking store) is not reused across separate job executions, or is wiped/recreated at the start of each job before proxy-exec first runs.

### Proof of Concept
Go unit test in `commands/helpers/internal/store/store_test.go` style:
```go
func TestOpen_PredictableKeyFromPreseededFiles(t *testing.T) {
    dir := t.TempDir()
    pathname := filepath.Join(dir, "masking.db")
    sum := sha256.Sum256([]byte(pathname))
    keyPath := filepath.Join(dir, "runner"+hex.EncodeToString(sum[:]))

    known32 := bytes.Repeat([]byte{0x41}, 32) // attacker-chosen "key1" material
    knownKey := bytes.Repeat([]byte{0x42}, 32) // attacker-chosen "key2" material
    require.NoError(t, os.WriteFile(pathname, known32, 0o666))
    require.NoError(t, os.WriteFile(keyPath, knownKey, 0o644))

    s, err := store.Open(dir)
    require.NoError(t, err)
    defer s.Close()

    require.NoError(t, s.Add("super-secret-value"))

    // attacker independently derives the same key and can decrypt the store
    expectedKey := make([]byte, 32)
    for i := range expectedKey {
        expectedKey[i] = known32[i] ^ knownKey[i]
    }
    c, err := chacha20poly1305.NewX(expectedKey)
    require.NoError(t, err)

    // read masking.db raw, skip 32-byte header, decode/decrypt line(s)
    // assert plaintext == "super-secret-value" using attacker-derived key
    // (asserts the runner's own derivation matches attacker prediction)
}
```
Assertions: the key computed purely from attacker-planted bytes matches the key actually used by `Store`, and decrypting the appended entry with that attacker-derived key succeeds and recovers the plaintext secret phrase.

```go
func deriveEncryptionKey(f *os.File, keyPath string) ([]byte, error) {
	var key1 [32]byte
	if _, err := io.ReadFull(f, key1[:]); err != nil {
		return nil, err
	}

	key2, err := os.ReadFile(keyPath)
	if err != nil {
		return nil, err
	}

	if len(key2) < len(key1) {
		return nil, fmt.Errorf("key1 and key2 not the same size")
	}

	for i := 0; i < len(key1); i++ {
		key1[i] ^= key2[i]
	}

	return key1[:], nil
}
```
