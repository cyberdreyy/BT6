## Title
`lending_pool_configure_bank` allows changing a bank's `asset_tag` while open integration positions exist, orphaning funds behind the wrong deposit/withdraw code path - (File: `programs/marginfi/src/state/bank.rs`)

### Summary
The Alchemix report's root cause is that `TransmuterBuffer::setAlchemist` swaps out a critical dependency (the Alchemist contract) without verifying that all exposure (open credit/positions) to the old dependency has been closed, so funds tied to the old Alchemist become unreachable. In marginfi, the analogous "swap a critical routing/typing field with no exposure check" pattern exists in `Bank::configure` (called by `lending_pool_configure_bank`), which lets the group admin change `bank.config.asset_tag` at any time, with no check that `lending_position_count`/`borrowing_position_count` (or total asset/liability shares) are zero for that bank.

### Finding Description
`Bank::configure` sets `asset_tag` unconditionally via `set_if_some!(self.config.asset_tag, config.asset_tag);` [1](#0-0) , with no guard analogous to the position-count/share checks used elsewhere (e.g. `lending_pool_close_bank` explicitly requires `lending_position_count == 0 && borrowing_position_count == 0` and zero shares before allowing a bank to be torn down) [2](#0-1) .

`asset_tag` is not cosmetic — it determines which instruction family (and which CPI/vault/reserve accounts) is valid for interacting with a bank's deposited funds: `lending_account_deposit`/`withdraw` only accept `ASSET_TAG_DEFAULT`/`ASSET_TAG_SOL`/`ASSET_TAG_STAKED`, while Kamino/Drift/Solend/JupLend deposits and withdrawals require their own dedicated instructions and validate the bank's `asset_tag` against the specific integration before proceeding [3](#0-2) . The repo's own test suite documents that flipping `asset_tag` on a live integration bank is accepted by the program with no positions/exposure check, explicitly noting the consequence: `"(admin) Configure wrong asset tag for Token A bank - happy path (but all Drift operations will now fail on it)"` [4](#0-3) .

This is the structural analog of `setAlchemist`: a single admin call reroutes which "integration"/type governs a bank's funds without first confirming the old integration's positions have been unwound, exactly mirroring the recommended Alchemix fix (require `getTotalCredit()==0`/`getAvailableFlow()==0` before switching). `configure_bank` has no equivalent `lending_position_count == 0 && borrowing_position_count == 0` requirement for `asset_tag` changes, even though such a check already exists (and is enforced) for the conceptually identical `close_bank` operation.

### Impact Explanation
If the admin (accidentally, via tooling error, or through a compromised/malicious multisig transaction) changes `asset_tag` on a bank that still has active Kamino/Drift/Solend/JupLend deposits or borrows outstanding, subsequent deposit/withdraw/repay/borrow calls for those existing balances will be routed to instruction handlers that reject the mismatched `asset_tag` (`AssetTagMismatch`/`WrongBankAssetTagForDriftOperation`, etc.), or to the generic default-bank path, which is not wired to the integration's reserve/vault/CPI accounts. Users' existing balances in that bank become practically unreachable through the correct instruction path, mirroring the "funds frozen with old Alchemist" scenario — deposits become durably stuck pending manual admin intervention (e.g., reverting `asset_tag`), and if the admin mistakenly believes the migration is safe and proceeds with other changes (e.g., pairing an incompatible new oracle setup with the new tag), recovery could require significant manual remediation.

Because this requires an admin-signed transaction, the severity is bounded (no attacker-controlled trigger for an unprivileged user), matching the original report's own characterization as "admin only... but impact is up to massive user fund freeze." The Alchemix judges themselves confirmed and rated this "admin footgun with financial freeze impact" pattern as valid despite being admin-gated.

### Likelihood Explanation
Likelihood is low-to-moderate: `configure_bank` is a routine, frequently-used admin operation (used to tweak deposit/borrow limits, risk tiers, weights, etc. — see `04_configureBank.spec.ts`), and `asset_tag` is bundled into the same `BankConfigOpt` struct as many benign fields [5](#0-4) , increasing the chance of an inadvertent or partially-scripted config update touching `asset_tag` on a live bank. The project's own test explicitly demonstrates this exact scenario is accepted without error ("happy path"), confirming there is no on-chain safeguard today.

### Recommendation
In `Bank::configure` (or in `lending_pool_configure_bank`), before allowing `config.asset_tag` to change the stored value, require that the bank currently has no open exposure — e.g.:
```rust
if let Some(new_tag) = config.asset_tag {
    if new_tag != self.config.asset_tag {
        check!(
            self.lending_position_count == 0 && self.borrowing_position_count == 0,
            MarginfiError::Unauthorized,
            "Cannot change asset_tag while bank has open positions"
        );
    }
}
```
This mirrors the check already used by `lending_pool_close_bank` and closes the same class of "swap dependency while exposure open" bug that the Alchemix report flagged for `setAlchemist`.

### Proof of Concept
1. Admin creates and configures a Drift-integration bank with `asset_tag = ASSET_TAG_DRIFT`, sets up the Drift spot market/oracle, and users deposit via `drift_deposit`, opening non-zero `lending_position_count`.
2. Admin calls `lending_pool_configure_bank` with `BankConfigOpt { asset_tag: Some(ASSET_TAG_KAMINO), .. }` (or any mismatched tag). This succeeds with no check on `lending_position_count`/`borrowing_position_count`, as demonstrated in the repo's own test `"(admin) Configure wrong asset tag for Token A bank - happy path (but all Drift operations will now fail on it)"` [4](#0-3) .
3. Users who deposited via `drift_deposit` can no longer withdraw via the Drift-specific withdraw path because the bank's `asset_tag` no longer matches Drift, nor can they use the standard withdraw path (which is gated to `ASSET_TAG_DEFAULT`/`ASSET_TAG_SOL`/`ASSET_TAG_STAKED`) or the newly-mismatched Kamino path (which expects Kamino-specific reserve accounts) [3](#0-2) .
4. Funds remain stuck in the bank's liquidity vault/underlying integration position until the admin manually reverts `asset_tag`, exactly analogous to funds being frozen in the old Alchemist after `setAlchemist` is called.

Note: due to indexing limits I could not directly inspect the full bodies of `drift/withdraw.rs`, `kamino/withdraw.rs`, and `marginfi_account/withdraw.rs` in this session to quote their exact `asset_tag` gating checks; the analysis above is based on the confirmed `AssetTagMismatch`/`WrongBankAssetTagForDriftOperation` error definitions and the explicit test comment demonstrating the vulnerable behavior. A Devin session with full repository access could confirm the precise assertion lines in those withdraw handlers.
