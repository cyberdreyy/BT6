I found a concrete instance of exactly this bug class: v1's `validate_tenure_change_payload` uses `get_last_globally_accepted_block` (a shallow/narrower check) to decide `DuplicateBlockFound`, while v2's equivalent function was hardened to use `get_last_signed_block` (checking both locally *and* globally accepted signatures). This mirrors the `SwapperCallbackValidation` pattern: a check that verifies a narrow condition ("is this a verified swapper" / "is this block globally accepted") while a broader capability ("execCalls can run anything" / "a locally-accepted, signed block is not covered") lets an attacker route around the intended guarantee.

### Title
V1 tenure-change duplicate-block guard checks only global acceptance, letting a signer double-sign a conflicting tenure-start block - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (v1 chainstate) guards against re-signing a second tenure-start block in the same tenure by querying `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`. This only detects a *global* acceptance (70% signed and confirmed) as evidence of "already signed a block in this tenure." A block this same signer has locally accepted (signed, but not yet globally accepted) is invisible to this check, so `DuplicateBlockFound` is never raised for it — the equivalent v2 function was fixed to use `get_last_signed_block`, which covers both locally and globally accepted/signed blocks.

### Finding Description
`validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` (lines ~505-518) is the only defense in `check_proposal` against a second tenure-start block for a tenure the signer already signed:
```rust
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)
    ...
if let Some(last_in_current_tenure) = last_in_current_tenure {
    return Err(RejectReason::DuplicateBlockFound);
}
```
`get_last_globally_accepted_block` returns `None` for a block this signer has already signed (`LocallyAccepted`) but which has not yet crossed the network-wide 70% threshold to become `GloballyAccepted`. In that intermediate window, a second tenure-start block for the *same* tenure — proposed either by the same miner retrying, or by a different sortition winner racing the change — passes `check_proposal` cleanly, because the equality being enforced ("have I already signed a tenure-start block here?") is checked against the wrong, narrower predicate (global acceptance) instead of the correct one (any signature this signer has placed, local or global).

This is exactly analogous to `SwapperCallbackValidation.verifyCallback()`: it checks a shallow, correctly-named-sounding condition (`isSwapper`/`globally accepted`) that looks like it implies the real invariant, but a legitimate, narrower state (`execCalls` being callable by the owner directly / a `LocallyAccepted`, signed-but-not-yet-global block) is not covered, breaking the intended guarantee.

The v2 (`stacks-signer/src/chainstate/v2.rs`) equivalent already fixes this by using `signer_db.get_last_signed_block(...)`, with an explicit code comment: "Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us...". The CHANGELOG.md entry for `[3.4.0.0.2.0]` even documents this exact fix ("When checking tenure change blocks, ensure there are no locally accepted blocks in the tenure, not just globally accepted blocks") — but the fix landed only in the v2 code path (`GlobalStateView::validate_tenure_change_payload`), while v1's `SortitionsView::validate_tenure_change_payload` still uses the old, narrower `get_last_globally_accepted_block` call.

### Impact Explanation
Because `check_proposal` is the gating function called from `stacks-signer/src/v0/signer.rs` before pre-commit/validation/signing proceeds, any signer still running the v1 chainstate path (`SortitionStateVersion::V1`, i.e. protocol version below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) will not reject a second tenure-start block in a tenure where it already has a `LocallyAccepted` (signed) block, as long as global acceptance hasn't yet been observed. This lets a single miner (with only ordinary, one-slot capabilities — no majority of signers required) present two competing tenure-start blocks for the same tenure and obtain a *second* valid signature from the same signer on a conflicting block, i.e. an equivocation: a signer signing a conflicting block for the same tenure/height. This breaks the "one signature per tenure-start" equality the guard exists to enforce, which is the Critical-class impact category ("a rejection recounted as an accept" / "a signer signing... a conflicting block").

### Likelihood Explanation
Any tenure normally spends time between a signer's local signature and global acceptance (waiting on the rest of the 70% threshold and/or the node observing the chain tip advance). A miner (or an equivocating/faulty miner racing with a rival tenure-start proposal) merely needs to get the signer to evaluate a second tenure-start block during that ordinary window — no majority of signers, no key compromise, and no StackerDB manipulation required. This is a naturally-occurring race in the block-lifecycle, making the likelihood high wherever V1 chainstate is still active.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` with `signer_db.get_last_signed_block(&block.header.consensus_hash)` (matching the v2 fix and its rationale), so that any block this signer has already signed — locally or globally accepted — is treated as a conflict, triggering `RejectReason::DuplicateBlockFound` and preventing a second signature on a competing tenure-start block for the same tenure.

### Proof of Concept
1. Signer is running under `SortitionStateVersion::V1` (protocol version < `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`).
2. Miner A proposes tenure-start block `B1` for consensus hash `CH`. Signer validates and signs it (`mark_locally_accepted`), storing `B1` as `LocallyAccepted` — but the network has not yet reached 70% weight, so it never becomes `GloballyAccepted`.
3. Before `B1` reaches global acceptance, a competing tenure-start block `B2` for the same consensus hash `CH` (from the same or a rival winning miner) is proposed.
4. `check_proposal` → `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(CH)`, which returns `None` (since `B1` is only `LocallyAccepted`), so `DuplicateBlockFound` is not raised.
5. `B2` proceeds through validation and, if it independently reaches its own pre-commit/threshold gates, the signer can also sign `B2`, producing two valid signatures from the same signer over two conflicting tenure-start blocks (`B1` and `B2`) for the same tenure — an equivocation that the guard was specifically designed to prevent (as evidenced by the identical, already-applied fix in `v2.rs` and the corresponding CHANGELOG entry).
