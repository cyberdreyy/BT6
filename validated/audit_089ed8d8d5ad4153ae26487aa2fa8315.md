### Title
Signer weight double-counted across accept/reject when a signer switches its vote - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` (the node-side coordinator that gathers signer votes for a proposed block) tracks two aggregate counters per block, `total_weight_approved` and `total_weight_rejected`, plus a single shared `responded_signers: HashSet<u32>` used to gate whether a slot's weight has already been tallied. The gating for the *rejection* path checks `responded_signers`, but the gating for the *acceptance* path checks a different, independent map (`gathered_signatures`). When a signer first rejects and later accepts the same block (a legitimate, single-signer, protocol-valid sequence — e.g. re-evaluating after a timeout or after seeing new information), its weight is added to `total_weight_rejected` on the rejection and then *also* added to `total_weight_approved` on the later acceptance, with the stale `total_weight_rejected` contribution never removed. This is the same "increment on entry recorded, but no matching decrement/reconciliation on state change" defect described in the Tapioca twTAP finding (`--totalParticipants` updated but `averageMagnitude` never adjusted on release), just instantiated on the two weight accumulators here.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- Acceptance path guards the increment with `gathered_signatures`: [1](#0-0) 

- Rejection path guards the increment with `responded_signers`: [2](#0-1) 

Both branches insert into `responded_signers` (line 465 for accept, line 515 for reject), but only the reject branch actually *uses* that set to decide whether to add weight. The accept branch instead checks `gathered_signatures.contains_key(&slot_id)`, which is unrelated to whether this signer already contributed to `total_weight_rejected`.

Sequence that breaks the invariant:
1. Signer `S` (weight `w`) sends `Rejected` for a block. `responded_signers.insert(S)` → true (first time) → `total_weight_rejected += w`.
2. `S` later sends `Accepted` for the same block (allowed — nothing in this coordinator rejects a "flip"). `gathered_signatures` does not yet contain `S`, so `total_weight_approved += w` and `gathered_signatures.insert(S, sig)`; `responded_signers.insert(S)` is a no-op since already true, so nothing decrements `total_weight_rejected`.

After this sequence, `S`'s weight `w` is counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously, and it stays counted in `total_weight_rejected` forever even though `S`'s current, valid vote is acceptance. This breaks the "aggregated-weight vs verified-accepts/rejects" equality the coordinator relies on: `total_weight_approved + total_weight_rejected` can now exceed `total_weight`, and the recorded rejection weight no longer corresponds to a live rejecting signer, exactly mirroring the twTAP bug where `averageMagnitude` kept accumulating without a matching decrement on `_releaseTap()`.

### Impact Explanation
The coordinator uses these two counters, compared against `self.weight_threshold`, to decide when to declare the block approved or rejected and to notify waiters via `cvar.notify_all()`: [3](#0-2) [4](#0-3) 

Because a single flipping signer's weight is never retracted from `total_weight_rejected`, the rejection tally is permanently inflated by stale, superseded rejections. This can cause the reject threshold to be crossed (and the miner to abandon/replace a block) using phantom rejection weight from a signer whose live vote is actually acceptance — i.e., a rejection is effectively "recounted" indefinitely even after the signer accepted, an aggregated-weight-vs-verified-accepts mismatch. Depending on timing this can either wedge legitimate blocks from reaching the accept threshold (liveness) or cause the miner to treat a block as rejected when the true, current signer opinions would not support that outcome (a miscounted response).

### Likelihood Explanation
This requires only a single signer to send a `Rejected` message and later a `Accepted` message for the same `signer_signature_hash` — no majority collusion, no key compromise, and no malicious behavior is needed; a signer legitimately re-evaluating a proposal (e.g., after a transient validation failure, after a pre-commit race, or after replaying a delayed StackerDB chunk) can trigger this in normal operation. Both branches are reachable via ordinary StackerDB message delivery, and message re-ordering/duplication over StackerDB is expected, not exotic.

### Recommendation
Use one authoritative "already tallied" gate shared by both branches (or reconcile the two maps), and — mirroring the correct fix in the twTAP case — when a signer's vote transitions from reject to accept (or vice versa), decrement the stale side's total weight (and remove/replace any per-signer accounting such as `failed_txids` weight) at the same time the new side is incremented, so `total_weight_approved` and `total_weight_rejected` always reflect only the signer's most recent vote.

### Proof of Concept
1. Configure a reward set including signer `S` with weight `w`.
2. Deliver a StackerDB chunk containing `BlockResponse::Rejected` from `S` for block `B`; observe `total_weight_rejected == w` (see rejection branch increment at [2](#0-1) ).
3. Deliver a subsequent StackerDB chunk containing `BlockResponse::Accepted` from the same `S` for the same block `B`; observe `total_weight_approved` also becomes `w` (increment guarded only by `gathered_signatures`, see [5](#0-4) ), while `total_weight_rejected` remains `w` — the same signer's weight is now counted on both sides, and the reject tally is never corrected.
