### Title
Unbounded, unpartitioned epoch-reward calculation over all stake delegations enables a permissionless-growth compute-exhaustion / cluster-halt at epoch boundaries - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
Solana's partitioned-rewards mechanism was built specifically to avoid doing all epoch-reward work in a single block by spreading the *distribution* (crediting) phase across many blocks. However, the *calculation* phase — which iterates over every stake delegation in the cluster to compute reward points and stake rewards — is still done synchronously, once, in a single epoch-boundary block. Because creating stake accounts and delegating stake is a fully permissionless (unprivileged) operation, the size of the `stake_delegations` collection that this calculation loop must process is attacker-influenceable and effectively unbounded, mirroring the reported "unbounded loop length DoS" bug class: an unprivileged, repeatable action (`createPair`) grows an array that a later, unskippable operation (`setPeriodSize`) must iterate over in full, with no way to do that iteration incrementally.

### Finding Description
`calculate_stake_rewards_and_commissions` and `calculate_reward_points_partitioned` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` iterate (in parallel via `rayon`, but still O(N) total work) over the *entire* `stake_delegations` vector for the whole cluster: [1](#0-0) [2](#0-1) 

This work happens inside `calculate_rewards_for_partitioning` → `calculate_validator_rewards`, invoked from `calculate_rewards`/`compute_new_epoch_caches_and_rewards`, which the code comments themselves state occurs once, synchronously, at the epoch boundary (guarded by a per-parent-hash cache so it only runs once per fork, not skippable or resumable): [3](#0-2) 

In contrast, the subsequent *distribution* phase (crediting the computed rewards to individual stake accounts) is explicitly chunked across multiple blocks using `get_reward_distribution_num_blocks`, precisely because doing all of it in one block/slot was recognized as infeasible at scale: [4](#0-3) [5](#0-4) 

No equivalent chunking/partitioning exists for the *calculation* step itself — the comment at line 804-812 even acknowledges that N (the number of stake delegations) can reach "way smaller number than 1,000,000" today but does not bound it going forward: [6](#0-5) 

The count of stake delegations that must be processed here is populated from `stakes_cache.stake_delegations_vec()`, which reflects every currently-delegated stake account on the network — an amount that grows any time an unprivileged user issues `CreateAccount` + `stake::Instruction::DelegateStake` (or similar) transactions: [7](#0-6) 

This is functionally identical to the reported bug class: a permissionless action pushes new entries into a collection (`allPairs`/`stake_delegations`) with no upper bound, and a subsequent required, non-skippable, single-pass loop (`setPeriodSize`/epoch-boundary reward calculation) must process that entire collection at once. If enough stake accounts are created, this single-pass, single-block calculation could grow to consume more wall-clock/CPU time than is available in the block-production/replay budget for the epoch-boundary slot.

### Impact Explanation
Because bank state transitions (including reward calculation) must be deterministic and identical across all validators, if the calculation step at the epoch boundary cannot complete within the time budget expected for producing/replaying that slot, every validator attempting to process the epoch-boundary block would be affected simultaneously (not just a single leader), potentially stalling block production/consensus cluster-wide at every epoch boundary going forward until the stake set shrinks — a transaction-triggered cluster halt scenario, which is one of the accepted impact categories for this analog scan.

### Likelihood Explanation
Likelihood is currently low-to-uncertain rather than confirmed:
- Creating a stake account and delegating requires funding it to at least the rent-exempt minimum plus the minimum stake delegation, so scaling `stake_delegations` to a size that meaningfully threatens block-time is economically costly (though, unlike the Canto report's "burn," these funds are not destroyed — they remain recoverable — so the true cost to an attacker is only the time-value of locked capital plus rent, not a permanent loss, arguably making this *cheaper* to attempt than the original finding assumed for its own analog).
- The `rayon` parallel iteration and `with_min_len(500)` batching in `calculate_stake_rewards_and_commissions` mitigate but do not eliminate O(N) scaling.
- I was not able to fully verify (due to running out of investigation budget) whether there is an existing implicit ceiling on the number of concurrently active stake accounts, or whether the compute/time budget for the epoch-boundary slot has independent safety margins (e.g., a generous slot-time allowance specifically for epoch-boundary processing) that would make this impractical in practice at realistic cluster stake-account counts. This should be verified against current mainnet stake-account counts and any documented safety margins before treating this as an urgent, confirmed vulnerability.

### Recommendation
- Bound or partition the reward *calculation* phase the same way the *distribution* phase already is, so that no single block/slot has to process an unbounded number of stake delegations synchronously.
- Alternatively/additionally, impose an explicit maximum on the number of active stake delegations counted per epoch (analogous to `MAX_ALPENGLOW_VOTE_ACCOUNTS` used for vote accounts) and/or increase minimum stake delegation requirements to keep worst-case N bounded relative to available block-processing time.
- Add monitoring/metrics and a hard assertion or fallback path if `calculate_rewards_for_partitioning` measured time exceeds a safe fraction of slot time, to detect this class of stall before it manifests as a live incident.

### Proof of Concept
A rigorous PoC would require large-scale simulation (creating an extremely large number of funded stake accounts, all delegated to active vote accounts, then measuring wall-clock time of `calculate_rewards_for_partitioning`/`calculate_stake_rewards_and_commissions` at the next epoch boundary against the slot-time budget) which is outside the scope of static code review. The code paths and lack of chunking identified above are the structural basis for this concern; I was unable to execute/benchmark this in the available time to confirm a concrete N at which this becomes practically exploitable on mainnet-scale hardware.

        // We hold the lock here for the epoch rewards calculation cache to prevent
        // rewards computation across multiple forks simultaneously. This aligns with
        // how banks are currently created- all banks are created sequentially.
        // As such, this lock does not actually introduce contention because bank
        // creation (and therefore reward calculation) is always done sequentially.
        //
        // However, if we plan to support creating banks in parallel in the future, this logic
        // would need to change to allow rewards computation on multiple forks concurrently.
        // That said, there's still a compelling reason to keep this lock even in a parallel
        // bank creation model: we want to avoid calculating rewards multiple times for the same
        // parent bank hash. This lock ensures that.
        //
        // Creating bank for multiple forks in parallel would also introduce contention for compute resources,
        // potentially slowing down the performance of both forks. This, in turn, could delay
        // vote propagation and consensus for the leading fork—the one most likely to become rooted.
        //
        // Therefore, it seems beneficial to continue processing forks sequentially at epoch
        // boundaries: acquire the lock for the first fork, compute rewards, and let other forks
        // wait until the computation is complete.
        let mut epoch_rewards_calculation_cache =
            self.epoch_rewards_calculation_cache.lock().unwrap();
        let rewards_calculation = epoch_rewards_calculation_cache
            .entry(self.parent_hash)
            .or_insert_with(|| {
                Arc::new(self.calculate_rewards_for_partitioning(
                    stake_history,
                    stake_delegations,
                    cached_vote_accounts,
                    rewarded_epoch,
                    reward_epoch_delegated_stakes,
                    reward_calc_tracer,
                    thread_pool,
                    metrics,
                ))

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),

impl Bank {
    /// Process reward distribution for the block if it is inside reward interval.
    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
        }
