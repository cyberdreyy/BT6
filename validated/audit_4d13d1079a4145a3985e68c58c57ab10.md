### Title
Stale vote weight from flip-flopping signer causes miner to act on a corrupted approval/rejection tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The stacks-signer state machine explicitly allows a signer's local verdict on a block to flip in either direction after re-evaluation (`LocallyRejected -> LocallyAccepted` and `LocallyAccepted -> LocallyRejected`), and it re-broadcasts a fresh `BlockResponse` each time [1](#0-0) . The miner-side `StackerDBListener`, which tallies these responses to decide when a block has reached the 70%/30% weight threshold, only guards against a *single* response type being double counted, but never removes a signer's earlier contribution from the opposite bucket when that signer later flips its vote. This is the same class of bug as the ERC20 `approve` race: the old "grant" (the earlier vote's weight) is never revoked before the new one is recorded, so both are live simultaneously.

### Finding Description
`handle_signer_messages` in `stackerdb_listener.rs` keeps two independent accumulators per block, `total_weight_approved` and `total_weight_rejected`, together with two bookkeeping sets, `gathered_signatures` (keyed by slot) and `responded_signers` (keyed by slot).

For an `Accepted` response, the code only prevents *re-adding* weight if this slot already has a gathered signature; it does not check whether the slot has already contributed to `total_weight_rejected`: [2](#0-1) 

For a `Rejected` response, weight is added only the first time `responded_signers.insert(slot_id)` succeeds, i.e., the first time this slot ever responds at all (accept or reject): [3](#0-2) 

Consider a signer that first rejects a block (e.g., because validation failed or a conflicting sibling was fresh), and later — per the documented `LocallyRejected -> LocallyAccepted` re-evaluation transition [1](#0-0)  — signs and accepts the same block once the blocking condition clears:

1. **Reject arrives first**: `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += weight`.
2. **Accept arrives later**: `gathered_signatures.contains_key(&slot_id)` is `false` (no signature was ever recorded for this slot) → `total_weight_approved += weight`. `responded_signers.insert(slot_id)` is now a no-op (already present) so nothing here re-checks or clears the earlier rejection tally.

The result: the same signer's weight is now counted in **both** `total_weight_approved` and `total_weight_rejected` at once, and `total_weight_rejected` is never decremented. The invariant that a signer's weight belongs to exactly one bucket at a time — the "equality" between an aggregated weight and a signer's currently valid answer — is broken. This is structurally identical to the ERC20 bug: the old approval (rejection) isn't atomically revoked when a new approval (acceptance) supersedes it, so both are counted.

### Impact Explanation
Because `total_weight_rejected` retains stale weight from signers who have since flipped to acceptance, the miner's "globally rejected" check can fire on stale data: [4](#0-3) 

This lets `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` trip prematurely/incorrectly even though the signer that previously rejected has already reversed course and signed. The miner ends up acting on a stale, double-counted threshold state rather than the signers' current live verdicts — the block can be judged (via `cvar.notify_all()`) as unreachable/dead while it may in fact still be able to reach 70% approval, or the sum of the two buckets can exceed `total_weight`, corrupting the bookkeeping the miner relies on to decide whether to keep waiting or give up on a proposal. This matches the "acting on a stale ... threshold" high-impact category: the coordinator's threshold accounting no longer reflects the actual current set of signer decisions.

### Likelihood Explanation
This requires only ordinary signer behavior already documented and tested in this codebase — no majority collusion or key compromise. The state machine explicitly supports and tests `LocallyRejected -> LocallyAccepted` (and the reverse) re-evaluation transitions [1](#0-0) , and scenarios such as a stale sibling-conflict rejection being replaced by a later signature are directly exercised in the test suite [5](#0-4) . Any single honest signer that legitimately changes its answer (e.g., a conflicting sibling times out, or a chainstate re-check now passes) triggers this miscount on the node side; a single one-slot miner/gossip relaying such ordinary two-round traffic is enough.

### Recommendation
On the miner/coordinator side (`stackerdb_listener.rs`), track the signer's *current* verdict per slot (accept/reject) in one place rather than two independently-gated accumulators. When a response updates an existing verdict for a slot, first subtract that slot's weight from whichever bucket it previously counted toward, then add it to the new bucket — mirroring the ERC20 fix pattern of never additively combining an old and new grant, but instead replacing the old value atomically before applying the new one.

### Proof of Concept
1. Miner submits `BlockProposal` for block `B`.
2. Signer `S` (weight `w`) initially rejects `B` (e.g. transient conflicting sibling) → `BlockResponse::Rejected` is relayed; listener sets `responded_signers.insert(S)` → `total_weight_rejected += w` (`stackerdb_listener.rs:515-518`).
3. The conflict later becomes stale and `S` re-evaluates per `LocallyRejected -> LocallyAccepted`, signs `B`, and broadcasts `BlockResponse::Accepted`.
4. Listener processes the acceptance: `gathered_signatures` does not yet contain `S`'s slot → `total_weight_approved += w` (`stackerdb_listener.rs:443-446`), while `total_weight_rejected` still includes `w` from step 2 (never cleared).
5. Now `total_weight_approved + total_weight_rejected > total_weight` by `w`, and the rejection-threshold check at `stackerdb_listener.rs:567-574` can fire using `S`'s stale rejection weight even after `S` has switched to accepting — corrupting the miner's decision on whether the block can still reach consensus.
