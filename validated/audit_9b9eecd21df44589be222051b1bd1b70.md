### Title
Missing duplicate-key check in `savedCallbacks` map allows cross-user response hijacking via MessageId collision - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores a user's response callback in `h.savedCallbacks` keyed solely by the caller-supplied `msg.Body.MessageId`, with no check for an existing entry and no binding to the original sender's identity. Because `MessageId` is fully attacker-controlled and unrelated to authentication (any self-signed message can carry any ID), an attacker can submit a message using the same `MessageId` as a victim's in-flight (or recently pruned/expired) trigger request, silently overwriting the victim's saved callback and causing the DON node's subsequent response for that ID to be delivered to the attacker instead of the victim.

### Finding Description
In `HandleLegacyUserMessage` [1](#0-0) , the callback is stored with:
```go
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
```
There is no `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { ... }` guard, and `MessageId` is a user-supplied string bounded only by `MessageIdMaxLen` (validated in `Message.Validate`) [2](#0-1) , with no cryptographic tie to the sender (the signature covers the whole body but the ID value itself is chosen by the caller).

The lookup path in `handleWebAPITriggerMessage` matches purely by `MessageId`:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [3](#0-2) 

Because the code explicitly documents that it takes the "first response from a node" and ignores the sender's origin, whichever caller most recently occupies the `MessageId` slot wins. An unauthenticated attacker can:
1. Observe/guess a victim's in-flight `MessageId` (predictable IDs, replay of a previously-observed ID, or an ID reused after `pruneCallbacks` expires it after `CallbackMaxAgeSec`, default 120s [4](#0-3) ).
2. Submit their own self-signed `web_api_trigger` message with that exact `MessageId` before the DON node's response arrives.
3. Their write overwrites the map entry, so when the node's response for that `MessageId` arrives, `handleWebAPITriggerMessage` delivers it into the attacker's `savedCallback.Callback` — not the victim's — while the victim's original request hangs until its own context timeout.

The explicit `// TODO: apply allowlist and rate-limiting here` comment [5](#0-4)  confirms there is no per-sender throttling to make guessing/flooding costly, and `pruneCallbacks` itself provides no reuse protection — it only removes entries based on age/count, with no mechanism preventing a fresh write from colliding with a still-active or just-pruned ID [6](#0-5) .

### Impact Explanation
This is a cross-user response/state confusion: the response intended for one caller's `web_api_trigger` message can be redirected to a different, attacker-controlled callback, while the legitimate caller's request silently stalls until timeout. This matches the "cross-user response confusion" impact class described in the audit prompt. The severity is bounded by the fact that the trigger ACK payload (`ACCEPTED`/`ERROR` status from `trigger.go`'s `sendResponse`) is not itself highly sensitive, but the underlying primitive — an attacker overwriting another caller's pending map slot with no identity check — is a genuine isolation/authorization flaw in the callback dispatch logic, and increases risk if this pattern is reused elsewhere.

### Likelihood Explanation
Exploitability requires only: (1) the ability to submit self-signed gateway messages (any keypair, no privileged credential needed), and (2) knowledge or a good guess of a victim's `MessageId` at the right time, or simply racing many requests against expected `pruneCallbacks` expirations. There is no allowlist or rate limiting on this path (as flagged by the existing TODO), so an attacker can flood attempts cheaply and repeatedly to win races, making this feasible and repeatable, though it depends on `MessageId` predictability/observability which is not itself hardened by this code.

### Recommendation
- Reject new `savedCallbacks` writes if the `MessageId` already has a live entry (return an explicit "duplicate message ID" error to the caller) instead of silently overwriting.
- Bind the callback entry (and lookup) to both `MessageId` and sender identity (e.g., key by `MessageId + Sender`), so a different signer cannot hijack another sender's pending slot.
- Add per-sender rate limiting/allowlisting on `HandleLegacyUserMessage` as already flagged by the TODO comment, to make MessageId flooding/racing costly.

### Proof of Concept
Go handler-level test plan (extending `handler_test.go`):
1. Build `msgVictim := triggerRequest(t, victimKey, ..., "")` and `msgAttacker` with the **same** `MessageId` but signed by a different key (`attackerKey`), each with distinct payload content.
2. Call `handler.HandleLegacyUserMessage(ctx, msgVictim, cbVictim)`, then before any node responds, call `handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)`.
3. Assert `handler.savedCallbacks[messageID].Callback == cbAttacker` (victim's callback silently evicted).
4. Simulate one DON node response via `handler.HandleNodeMessage(ctx, resp, nodeAddr)` using the shared `MessageId`.
5. Assert `cbAttacker.Wait(ctx)` receives the response while `cbVictim.Wait(ctx)` times out/never resolves — demonstrating the response was diverted to the attacker's callback instead of being delivered to, or an error returned to, the original victim caller.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
```
