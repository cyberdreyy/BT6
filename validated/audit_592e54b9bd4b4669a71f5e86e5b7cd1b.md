### Title
Claimed instant-withdraw receipts remain in the per-epoch claim ledger, corrupting default-recovery basis and prefunded-reserve accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks instant-withdraw receipts in two parallel ledgers: the aggregate `instantWithdrawsRequests[user]` and the per-epoch pair `instantWithdrawsRequestsByEpoch[user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`. The normal withdrawal flow clears both (`_clearWithdrawClaimForEpoch` at lines 811-837 zeroes the per-epoch entry when a claim is released), but `claimInstantWithdrawRequest` clears only the aggregate ledger and leaves the per-epoch entries populated. Default finalization later reads only the per-epoch ledger, so a receipt that was already paid at par is counted again as an outstanding claim — the same "release operates on only one of two lists" shape as CVE-2018-18559.

### Finding Description
In `claimInstantWithdrawRequest` (lines 380-393):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (written in `requestInstantWithdraw`, lines 371-372) are never decremented. The stale per-epoch data is consumed in two places during `finalizeDefaultRecovery` when the borrower defaults in the same epoch and `pendingInstantWithdraws != 0` (i.e. at least one later instant request is unfunded):

1. `defaultPendingClaimBasis` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery `totalBasis`, inflating it by already-paid amounts and diluting `defaultRecoveryPrice` for every honest claimant and active LP.
2. `_defaultPrefundedInstantReserve` (lines 716-723) computes `instantBasis - pendingInstant` and treats that difference as underlying already held by the strategy. Because the claimed user's funds were already transferred out via `_transferFundedClaim`, this counts phantom balance that does not exist, inflating `reserveAmount` and pushing `recoveryPrice` above what real holdings support (line 688: `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`).

Additionally, `_claimDefaultedInstantWithdrawRequest` (lines 842-856) later reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, computes a non-zero `claimBasis` for the already-claimed user, then executes `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed aggregate, underflowing and reverting — so the dust accounting can never be repaired through the claim path.

### Impact Explanation
Direct loss / permanent freezing with a quantified bound:

- If the stale claim dominates `instantBasis - pendingInstant`, the phantom prefunded reserve raises `defaultRecoveryPrice` beyond real backing. Claims are paid pro-rata from `defaultRecoveryReserve` (lines 782-783, 855), so early claimants over-draw the actual token balance and later claims (including `_claimDefaultedWithdrawRequest` and `DefaultDistributor` payouts) revert on insufficient balance — permanent freezing of unclaimed recovery for honest users.
- In the opposite configuration the inflated `totalBasis` lowers `recoveryPrice`, so every active LP (whose `activeFinalNAV` is minted at lines 699-705 using the same price) and every defaulted-epoch redeemer crystallizes a larger loss than realized; the unclaimable remainder stays locked in the strategy as recovery dust.

Loss is bounded by the attacker's stale claimed amount, which scales linearly with repeat deposit → requestInstantWithdraw → claim cycles within the epoch before the default.

### Likelihood Explanation
Requires: instant withdraws enabled (`allowInstantWithdraw`), an epoch where the attacker's instant request is funded at `startEpoch` and claimed, a second unfunded instant request in the same epoch so `pendingInstantWithdraws != 0`, and a borrower default in that epoch (`stopEpoch(0,0)` → `finalizeDefaultRecovery`). The attacker is an ordinary KYC-passing lender; the default is an honest-borrower event, not attacker-caused. The attacker can keep stale claims primed every epoch at near-zero cost (request size can be minimal or maximal — larger claims cause larger distortion) and simply wait for any default, making this a persistent latent accounting error rather than a one-shot race.

### Recommendation
Mirror the normal-withdraw path: in `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user]` for the request epoch(s) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. If the epoch tracking a receipt is needed, store the request epoch per user (analogous to `lastWithdrawRequest`) at request time, or iterate and zero all non-zero per-epoch entries for the user. Add a regression test that claims an instant withdrawal mid-epoch, defaults the same epoch with a second pending instant request, and asserts `defaultPendingClaimBasis` excludes the claimed amount.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCDOEpochQueue.t.sol` helpers `_depositWithUser`, `_stopCurrentEpochWithApr`):

```solidity
function testStaleInstantClaimCorruptsDefaultBasis() external {
    _useStandardEpochVariant();
    // enable instant withdrawals
    vm.prank(manager);
    cdoEpoch.setAllowInstantWithdraw(true, 100); // manager helper per test harness

    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    uint256 tA = _depositWithUser(attacker, 100e6);
    uint256 tV = _depositWithUser(victim,   100e6);

    uint256 epoch = strategy.epochNumber();
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // attacker requests + claims instant withdraw (funded at startEpoch)
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tA, address(tranche));
    // borrower funds instant queue via collectInstantWithdrawFunds path
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequests(attacker), 0);
    // BUG: per-epoch ledger still counts the paid receipt
    assertGt(strategy.instantWithdrawsRequestsByEpoch(attacker, epoch), 0);
    assertGt(strategy.instantWithdrawClaimsByEpoch(epoch), tV);

    // victim requests instant withdraw later in same epoch; left unfunded
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(tV, address(tranche));
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // honest borrower defaults this epoch
    deal(address(underlying), strategy.borrower(), 0, true);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(cdoEpoch.owner());
    cdoEpoch.stopEpoch(0, 0);

    uint256 basis = strategy.defaultPendingClaimBasis();
    // basis includes attacker's already-claimed amount -> inflated
    assertGt(basis, strategy.pendingWithdraws() + tV);
    // finalizeDefaultRecovery then computes a recoveryPrice that either
    // dilutes all claimants or over-promises vs actual held balance,
    // and _claimDefaultedInstantWithdrawRequest(attacker) reverts on
    // instantWithdrawsRequests[attacker] -= staleClaimBasis underflow.
}
```

Note: exact helper names (`setAllowInstantWithdraw`, `requestInstantWithdraw` signature on the CDO) should be matched to the deployed `IdleCDOEpochVariant` test harness; the core assertions on the stale per-epoch ledgers hold directly against `IdleCreditVault` state shown above.
