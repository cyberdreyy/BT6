### Title
Instant-withdraw receipts from epochs before the default epoch are omitted from default-recovery basis and can never be claimed - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Tomcat bug class is "special roles and empty authorization constraints silently dropped when the effective configuration is summarized". The analog in `IdleCreditVault` is `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()`: both only ever look at `instantWithdrawClaimsByEpoch[epochNumber]` / `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — i.e. only the *current* epoch's bucket. Instant-withdraw receipts recorded under any earlier epoch (an "empty" current-epoch bucket) are omitted from the recovery basis and can never be cleared, while their aggregate `instantWithdrawsRequests[user]` and `pendingInstantWithdraws` still count them.

### Finding Description
`requestInstantWithdraw` records receipts per request epoch (`instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`) and increments the global `pendingInstantWithdraws` (`IdleCreditVault.sol:367-374`). `pendingInstantWithdraws` is only decremented by `collectInstantWithdrawFunds` (`:398-403`), so when a startEpoch/stopEpoch only partially funds the instant queue, the unfunded remainder — which may carry claims from multiple past epochs — persists while `epochNumber` advances.

At default finalization:

- `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — claims requested in earlier epochs are excluded from `totalBasis` even though they are real, unfunded claims (`:644-649`).
- `_defaultPrefundedInstantReserve()` computes the prefunded portion as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`, using only the current-epoch bucket, so already-collected funds backing *old-epoch* instant claims are not counted as reserve (`:716-723`).
- `defaultInstantWithdrawsFinalized` is set from `pendingInstantWithdraws != 0` (`:696`), and `_claimDefaultedInstantWithdrawRequest` only reads/clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (`:842-856`). An old-epoch instant receipt returns `claimBasis == 0`, leaving `instantWithdrawsRequests[user]` nonzero; the call then falls through to the funded path which burns it and calls `_transferFundedClaim` — which pays at par (100%) if stray non-reserve balance exists, or reverts via the `balance - reserve < _amount` guard (`:897-907`), permanently freezing the receipt.

Two symmetric breakages result from omitting the "empty" (non-current-epoch) entries:

1. Omitted basis inflates `defaultRecoveryPrice` (`reserveAmount / totalBasis` with a too-small denominator, `:688`), over-paying default-epoch claimants and draining `defaultRecoveryReserve` so later claimants' `_transferDefaultRecovery` underflows and reverts — permanent freeze.
2. Old-epoch instant claimants are either paid at par from funds that were not reserved for them, or are bricked entirely.

### Impact Explanation
Direct loss / permanent freezing: included default-epoch claimants recover more than the intended haircut while old-epoch instant receipt holders and tail claimants get zero (reserve exhausted or guard revert). Broken invariants: one-receipt-one-payout at the finalized recovery ratio, and fair loss socialization.

### Likelihood Explanation
Requires a default while `pendingInstantWithdraws > 0` spans more than one epoch — i.e. the instant queue was only partially funded across an epoch boundary. Partial funding is an explicitly supported state per the in-code comments (`pendingInstantWithdraws` is "the still-unfunded remainder"), so this is an edge-but-real configuration rather than a hypothetical. Uncertainty: whether `IdleCDOEpochVariant.startEpoch`/`stopEpoch` always fully drains `pendingInstantWithdraws` before advancing `epochNumber` was not fully verified in the CDO code; if it does, the multi-epoch window cannot occur and severity drops.

### Recommendation
Track instant-withdraw basis globally rather than per current epoch: e.g. keep a `totalInstantClaims` aggregate (or iterate/clear all epochs in `instantWithdrawClaimsByEpoch`), include all outstanding instant claims in `defaultPendingClaimBasis`, and make `_claimDefaultedInstantWithdrawRequest` clear a user's aggregate receipt (`instantWithdrawsRequests[user]`) rather than only the `defaultRecoveryEpoch` entry.

Foundry sketch (against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. depositAA, _startEpochAndCheckPrices(0)
// 2. user1: cdoEpoch.requestInstantWithdraw(X)   // recorded under epoch E0
// 3. partially fund instant queue: borrower repays < X so
//    strategy.collectInstantWithdrawFunds(partial) leaves pendingInstantWithdraws > 0
// 4. _startEpochAndCheckPrices(1)                 // epochNumber -> E1, old basis stays in E0
// 5. user2: requestWithdraw(...)                  // normal pending receipt in E1
// 6. borrower defaults -> cdoEpoch.finalizeDefaultRecovery(...)
// assert: instantWithdrawClaimsByEpoch[E0] > 0 was excluded from totalBasis,
//         user1's claim either reverts (balance < reserve) or is paid at par,
//         and defaultRecoveryPrice is inflated vs the all-claims denominator.
```

Note: step 3's feasibility depends on whether `IdleCDOEpochVariant` permits partial instant-queue funding across `startEpoch`; that call path should be confirmed when writing the PoC.
