### Title
User enumeration and MFA-status disclosure via distinguishable `/sessions` error bodies - ([File: core/sessions/localauth/orm.go])

### Summary
`orm.CreateSession` returns distinct, verbatim error strings ("Invalid email", "Invalid password", "MFA Error", or a full WebAuthn challenge JSON containing the RPID) that are propagated unmodified into the HTTP response body by `jsonAPIError`. This lets an unauthenticated caller distinguish nonexistent accounts, existing accounts without MFA, and existing accounts with MFA enabled, despite the code comment claiming this is prevented.

### Finding Description
`SessionsController.Create` (`core/web/sessions_controller.go:29-68`) binds the request, then unconditionally calls `GetUserWebAuthn(ctx, sr.Email)` *before* any password check, and calls `CreateSession`, forwarding any error straight to `jsonAPIError(c, http.StatusUnauthorized, err)`. [3](#0-2) 

Inside `orm.CreateSession` (`core/sessions/localauth/orm.go:144-230`):
- Wrong email → `pkgerrors.New("Invalid email")` [4](#0-3) 
- Correct email, wrong password → `pkgerrors.New("Invalid password")` [5](#0-4) 
- Correct email/password, no MFA → session created successfully (200, cookie issued) [6](#0-5) 
- Correct email/password, MFA enabled, no WebAuthn data → serialized WebAuthn challenge JSON (including RPID) returned as the error body [7](#0-6) 

`jsonAPIError` places `err.Error()` directly into the JSON `detail` field of the response, so all four cases produce distinguishable, differently-shaped bodies while sharing (mostly) the same 401 status code. [1](#0-0) 

The code comment at `orm.go:152-153` claims the email/password ordering "prevent[s] extra database look up for MFA tokens leaking if an account has MFA tokens or not," but this protection is undermined in two ways:
1. `SessionsController.Create` itself queries `GetUserWebAuthn` unconditionally before calling `CreateSession` at all — the DB lookup timing difference the comment tries to avoid inside `orm.go` already happens one layer up in the controller, for every request regardless of email/password validity. [8](#0-7) 
2. Even ignoring timing, the returned error text/body content itself differs: "Invalid email" vs "Invalid password" already leaks account existence, and, for a valid email with a wrong password guessed against an MFA-enabled account, an attacker who eventually finds the correct password receives a WebAuthn challenge JSON (revealing RPID/credential IDs) instead of an immediate session — a content-based signal of MFA enrollment status distinct from the non-MFA path.

Neither the auth middleware nor any redaction layer intervenes here since `/sessions` is deliberately unauthenticated (`unauth.POST("/sessions", sc.Create)`), and no additional generic-error normalization exists between `CreateSession` and `jsonAPIError`. [9](#0-8) 

### Impact Explanation
This maps to a user-enumeration / information-disclosure impact (not a direct authentication bypass or credential leak). An attacker can distinguish valid vs. invalid emails and detect MFA enrollment via content shape, enabling targeted credential-stuffing or social-engineering campaigns against known, MFA-lacking accounts. This is a low/medium severity issue: no secrets, keys, or session material are exposed, and it does not by itself allow account takeover or fund movement.

### Likelihood Explanation
Precondition: unauthenticated network access to the node's `/sessions` endpoint only, matching the given attacker model. The attack is trivially repeatable — a scripted client can iterate emails and inspect the JSON `detail` field or body shape/length. Rate limiting exists (`sessionRoutes` unauthenticated rate limiter, and `TestSessions_RateLimited` confirms 429 after repeated attempts) which reduces but does not eliminate feasibility. [10](#0-9) [11](#0-10) 

### Recommendation
- Return a single generic error message/status (e.g., "Invalid email or password") for all pre-MFA failure branches (email not found, password mismatch) instead of distinct strings.
- Move/guard the `GetUserWebAuthn` call in `SessionsController.Create` so it does not run (or its result does not affect response shape/timing) until after credentials are validated, or make its cost/response uniform regardless of match.
- Ensure the WebAuthn-challenge-required response and the "no MFA, invalid password" response are indistinguishable to an unauthenticated caller who hasn't yet supplied correct credentials — e.g., only emit the WebAuthn challenge after password validation succeeds (already done) but normalize the *type/status code* of failure responses so pre-credential-validation errors don't reveal existence/MFA status through content difference.

### Proof of Concept
Table-driven `httptest` integration test against `SessionsController.Create` (extending `core/web/sessions_controller_test.go`):
1. Seed one user with no MFA, one user with MFA enrolled (`SaveWebAuthn`), and use a nonexistent email.
2. For each of the three emails, POST `/sessions` with an intentionally wrong password.
3. Capture status code and raw response body for each case.
4. Assert (currently failing) that all three bodies are textually identical (e.g., all say `"Invalid email or password"`) and same length class — today the test would show `"Invalid email"` vs `"Invalid password"` differing bodies, demonstrating enumeration.
5. Separately, for the MFA user with a *correct* password and no `WebAuthnData`, assert the response is a large WebAuthn-challenge JSON, vs. for a non-MFA correct-credential user, assert a 200 session response — showing the content-based MFA-status signal (this occurs only post-credential-validation, so document it as a secondary, credential-gated leak rather than pre-auth).

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}

func TestSessions_RateLimited(t *testing.T) {
	t.Parallel()

	ctx := t.Context()
	app := cltest.NewApplicationEVMDisabled(t)
	require.NoError(t, app.Start(ctx))

	router := web.Router(t, app, nil)
	ts := httptest.NewServer(router)

		resp, err := client.Do(request)

	require.NoError(t, err)

	require.NoError(t, err)
