### Title
Pre-commit signing path never re-verifies the same-tenure `DuplicateBlockFound` invariant against the node, letting signers who missed a competing tenure-start proposal sign a conflicting block - (File: stacks-signer/src/v0/signer.rs)

### Summary
Exactly one invariant that guards against two accepted blocks in the same tenure — the `DuplicateBlockFound` check in `validate_tenure_change_payload` — is enforced only at proposal time and is never re-checked against the node before a signature is actually produced. Every other chainstate re-check (`check_block_against_signer_db_state`) is re-run at validate-ok and at the pre-commit-threshold crossing, but this specific check is not among them, and the "own-tenure conflict guard" that the code comments claim covers the gap only consults each signer's *local* record of conflicting signed blocks, not the node.

### Finding Description
`SortitionsView::check_proposal` (v1) dispatches tenure-change blocks to `validate_tenure_change_payload`, which rejects with `RejectReason::DuplicateBlockFound` when `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` already returns a block for that tenure: [1](#0-0) 

This check runs only inside `check_proposal`, i.e. only when a signer first receives a `BlockProposal` for a *new* block. It is never re-invoked afterward. The two places that re-validate a block before it is signed — `handle_block_validate_ok` and the pre-commit-threshold path in `handle_block_pre_commit` — both call `check_block_against_signer_db_state`, which for a tenure-change block only checks that it confirms the expected **parent** tenure (`check_tenure_change_confirms_parent`), never the block's **own** tenure: [2](#0-1) [3](#0-2) 

The project's own documentation confirms this gap is deliberate and states the backstop is the "own-tenure conflict guard" in `handle_block_pre_commit`: [4](#0-3) 

That backstop, however, is driven entirely by `self.signer_db.get_signed_conflicts(...)`, i.e. blocks *this signer itself* has locally recorded as conflicting/signed: [5](#0-4) 

If `conflicts` is empty (this signer never received, validated, or pre-committed the earlier competing tenure-start block), the code falls straight through to `!conflicts.is_empty()` being false and proceeds directly to `mark_locally_accepted` / sign, with no query at all to the node about whether the tenure already has an accepted first block: [6](#0-5) 

Because a single miner controls what it broadcasts to each signer, it can send tenure-start block B1 to a subset of signers and a different tenure-start block B2 (same tenure/consensus_hash, same parent, different content/hash) to a disjoint subset. Signers in the B1 group validate/pre-commit/sign B1 normally (`DuplicateBlockFound` is irrelevant to them since they never see B2). Signers in the B2 group never saw B1, so their own `check_proposal` call to `validate_tenure_change_payload` also finds no prior globally accepted block for the tenure (they don't know about B1 either) and passes. They then validate B2, pre-commit, and — since their local `get_signed_conflicts` has no record of B1 — cross the pre-commit threshold and sign B2 without ever consulting the node about the tenure's real state. This produces two disjoint groups of signers each backing a different, mutually exclusive tenure-start block for the same tenure, i.e. a broken "one accepted block per tenure" equality analogous to the missing pause-check in the `SwellLib.BOT`/`deleteActiveValidators` report: nearly every code path re-verifies this class of invariant except this one, which is silently assumed to be covered by a check that only fires when the signer has *already seen* the conflict locally.

### Impact Explanation
This is a Critical-class issue: it lets a subset of honest signers sign a non-canonical/conflicting block (a second, competing tenure-start block for the same tenure) purely because the sole invariant preventing it — `DuplicateBlockFound` — is proposal-time-only and its intended backstop at signing time is local-knowledge-only rather than node-verified. If the two disjoint signer groups each cross the signing weight threshold for their respective block, both B1 and B2 could accumulate valid signatures for the same tenure slot, directly breaking the aggregated-weight vs. verified-single-accepted-block invariant.

### Likelihood Explanation
Triggerable by a single miner (the one-slot miner controlling proposal broadcast/gossip) with no need for a signer majority or key compromise — only selective delivery of two distinct tenure-change proposals to disjoint signer subsets, which is within a miner's normal control over what it gossips and to whom.

### Recommendation
Re-run (or add an equivalent of) the own-tenure `DuplicateBlockFound`/`get_last_globally_accepted_block` check against the node at both `handle_block_validate_ok` and inside `handle_block_pre_commit` before signing, instead of relying solely on the signer's local `get_signed_conflicts` cache. At minimum, when `conflicts` is empty for a tenure-change block, query the node (e.g. via `get_tenure_tip`/equivalent) for whether the block's *own* tenure already has an accepted block before marking it locally accepted and signing.

### Proof of Concept
1. Miner wins a sortition and crafts two distinct tenure-change blocks, B1 and B2, both with the same `consensus_hash` (own tenure) and same `prev_tenure_consensus_hash` (parent tenure), but different transactions/hash.
2. Miner sends B1 only to signer subset A, and B2 only to signer subset B (feasible since block proposals are pushed by the miner, not globally broadcast atomically).
3. Subset A: each signer's `check_proposal` → `validate_tenure_change_payload` sees no prior globally accepted block in the tenure (they don't know of B2), passes; they validate, pre-commit, and (if weight sufficient among A) sign B1 via `handle_block_pre_commit` (stacks-signer/src/v0/signer.rs:1250-1479).
4. Subset B: symmetric — each signer's `check_proposal` passes for B2 for the same reason; `get_signed_conflicts(chain_length, B2_hash)` returns empty because B has no local record of B1; the conflict branches at lines 1403/1432/1458 are all skipped; B signs B2 via the same `handle_block_pre_commit` path.
5. Both B1 and B2 accumulate signer signatures for the same tenure slot, with neither group's signing path ever consulting the node to detect the other's competing, already-locally-accepted block.
