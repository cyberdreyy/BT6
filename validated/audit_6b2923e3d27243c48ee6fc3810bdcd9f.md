### Title
`TerminalConnect`'s `Close()` is a no-op, so `Session.Kill()` does not tear down the live Kubernetes exec proxy on job cancellation - ([File: executors/kubernetes/terminal.go])

### Summary
The Kubernetes executor's `terminalConn.Close()` in `executors/kubernetes/terminal.go` unconditionally returns `nil` and performs no teardown of the underlying exec stream, unlike the Docker executor's equivalent which cancels a context tied into the exec calls. Since `common.Build.waitForTerminal` reacts to job cancellation by calling `Session.Kill()`, which in turn only calls `terminalConn.Close()`, the Kubernetes proxy path keeps serving/routing bytes to the pod's `exec` websocket after the owning job has been canceled, until something unrelated (client disconnect, pod deletion by cleanup, or 1‑hour default `MaxSessionTime`) eventually ends it.

### Finding Description
`s.executor.TerminalConnect()` returns a `terminalConn{settings: settings}` value that carries only static `terminal.TerminalSettings` (URL, bearer token, CA cert) and has no context or cancel function at all: [1](#0-0) 

Its `Close()` method is a hard-coded no-op: [2](#0-1) 

Compare this to the Docker executor, which binds a cancelable context (`ctx, cancelFn := context.WithCancel(s.Context)`) into every exec/attach/wait call, and whose `Close()` actually calls `cancelFn()` to interrupt those in-flight operations: [3](#0-2) [4](#0-3) 

The job-cancellation path that is supposed to tear down an active terminal is `common.Build.waitForTerminal`, which on `ctx.Done()` (job canceled) calls `b.Session.Kill()`: [5](#0-4) 

`Session.Kill()` does nothing more than invoke `terminalConn.Close()` and clear the reference: [6](#0-5) 

Meanwhile, the actual byte-shuffling for the terminal happens in a separate goroutine handling the live HTTP/WebSocket request in `Session.execHandler`, which calls `terminalConn.Start(w, r, s.TimeoutCh, s.DisconnectCh)` and blocks inside `terminal.ProxyWebSocket(w, r, t.settings, wsProxy)`: [7](#0-6) [8](#0-7) 

That blocking call is only unblocked by `terminalsession.ProxyTerminal`'s internal watcher, which reacts solely to `timeoutCh` (a session timeout) or client disconnect — never to `Session.Kill()`/job cancellation: [9](#0-8) 

Because the Kubernetes `terminalConn.Close()` neither cancels a context nor signals `wsProxy.StopCh`, calling `Session.Kill()` from `waitForTerminal` has no effect on an already-running Kubernetes terminal proxy: the goroutine keeps forwarding stdin/stdout between the client and the pod's `pods/exec` SPDY/WebSocket stream against the Kubernetes API using the same `bearerToken`/URL captured at connect time, entirely independent of the job's cancellation state. The only things that actually stop it are: the remote client disconnecting, the (very long, `MaxSessionTime: 0` meaning unlimited per `getTerminalSettings`) session timing out, or the backing pod eventually being deleted as part of normal build cleanup (a separate, unsynchronized code path). This is exactly the "proxy state remains live after cancellation" scenario: [10](#0-9) 

The same `getTerminalSettings()` helper (and hence the same lack of cancellation binding) is reused by the service-proxy path in `proxyWSRequest`, which similarly has no tie to job/build cancellation and is only gated by `servicesRunning` (pod phase/container readiness), not by whether the owning job is still active: [11](#0-10) 

### Impact Explanation
An attacker who opened an interactive terminal or service-proxy WebSocket against their own live Kubernetes job, then has that job canceled (by themselves, a pipeline timeout, or another actor), retains a live channel that continues to execute commands in / route bytes to the build container after the job is supposed to be terminated. This matches the "session hijack or post-job disclosure" impact: the attacker can continue interacting with (or exfiltrating output from) a pod that GitLab believes is no longer associated with an active job, for as long as the pod happens to still exist (bounded only by eventual cleanup/pod deletion, not by the intended cancellation logic).

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: open an interactive terminal (or service proxy) session against a running job, then cancel the job while keeping the WebSocket open. `Session.Kill()` is reliably invoked on cancellation but is a functional no-op for the Kubernetes executor, so the race is deterministic, not merely theoretical — the proxy will keep running for as long as the pod is reachable, which is a window that always exists between job cancellation and pod teardown.

### Recommendation
Give the Kubernetes `terminalConn` the same cancellation wiring the Docker executor has: create a `context.Context`/`cancelFn` pair in `TerminalConnect`, thread that context into the `pods/exec` request (e.g., via `remotecommand`/`ProxyWebSocket` variant that accepts a context, or by wrapping the underlying transport/connection so it can be forcibly closed), and have `Close()` call `cancelFn()` (and/or push an error into `wsProxy.StopCh`) so that `Session.Kill()` actually terminates the in-flight proxy immediately instead of only clearing a reference. Apply the analogous fix to `proxyWSRequest`/`proxyHTTPRequest` in `executors/kubernetes/service_proxy.go` so the service-proxy path is also bound to the job's cancellation context.

### Proof of Concept
Go integration test outline (mirrors `executors/docker/terminal_test.go:TestTerminalConn_Start` but for the Kubernetes executor):
1. Stand up a fake Kubernetes API server (or use client-go fake/httptest) that upgrades the `pods/exec` websocket and simply echoes bytes indefinitely once connected.
2. Build a kubernetes `executor` pointed at that fake API, call `s.TerminalConnect()` to get `terminalConn`, and register it with a `session.Session` via `SetInteractiveTerminal`.
3. Dial the session's `/exec` WebSocket endpoint as the "attacker", and confirm bytes written are echoed back (proxy is live).
4. In a separate goroutine, simulate job cancellation by calling `session.Kill()` directly (as `waitForTerminal` does on `ctx.Done()`).
5. Assert that writes/reads on the attacker's WebSocket continue to succeed after `Kill()` returns — i.e., `session.Connected()` becomes `false` (since `terminalConn` reference is cleared) but the underlying proxy goroutine and the fake API connection remain active and continue echoing, proving the proxy was not actually terminated. Contrast with an equivalent Docker test where cancelling the context passed through `cancelFn` (`t.cancelFn()`) actually aborts the `ContainerExecAttach` stream.

func (s *Session) Kill() error {
	s.lock.Lock()
	defer s.lock.Unlock()

	if s.terminalConn == nil {
		return nil
	}

	err := s.terminalConn.Close()
	s.terminalConn = nil

	return err
}

func ProxyTerminal(timeoutCh, disconnectCh, proxyStopCh chan error, proxyFunc func()) {
	disconnected := make(chan bool, 1)
	// terminal exit handler
	go func() {
		// wait for either session timeout or disconnection from the client
		select {
		case err := <-timeoutCh:
			proxyStopCh <- err
		case <-disconnected:
			// forward the disconnection event if there is any waiting receiver
			nonBlockingSend(
				disconnectCh,
				errors.New("finished proxying (client disconnected?)"),
			)
		}
	}()

	proxyFunc()
	disconnected <- true
}

func proxyWSRequest(
	s *executor,
	w http.ResponseWriter,
	r *http.Request,
	requestedURI string,
	port proxy.Port,
	proxySettings *proxy.Settings,
	logger *logrus.Entry,
) {
	// In order to avoid calling this method, and use one of its own,
	// we should refactor the library "gitlab.com/gitlab-org/gitlab-terminal"
	// and make it more generic, not so terminal focused, with a broader
	// terminology. (https://gitlab.com/gitlab-org/gitlab-runner/issues/4059)
	settings, err := s.getTerminalSettings()
	if err != nil {
		logger.WithError(err).Errorf("service proxy: error getting WS settings")
		http.Error(w, http.StatusText(http.StatusServiceUnavailable), http.StatusServiceUnavailable)
		return
	}

	req, err := s.serviceEndpointRequest(r.Method, proxySettings.ServiceName, requestedURI, port)
	if err != nil {
		logger.WithError(err).Errorf("service proxy: error proxying WS request")
		http.Error(w, http.StatusText(http.StatusServiceUnavailable), http.StatusServiceUnavailable)
		return
	}

	u := req.URL()
	u.Scheme = proxy.WebsocketProtocolFor(u.Scheme)

	settings.Url = u.String()
	serviceProxy := terminal.NewWebSocketProxy(1)

	terminal.ProxyWebSocket(w, r, settings, serviceProxy)
}
