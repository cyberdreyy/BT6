### Title
Current-tenure miner can indefinitely re-arm its own inactivity timer with cheap conflicting proposals, wedging the tenure-extend fallback - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_latest_block_in_tenure` treats *any* block proposal for the current tenure that does not advance the chain (i.e. a proposal whose `chain_length` is no higher than what the signer already locally/pre-committed/globally accepted) as valid "miner activity" and calls `SignerDb::update_last_activity_time` to reset the tenure's inactivity clock — exactly analogous to the reported bug where any caller could reset a reward timestamp with a trivial (1‑wei) deposit. Here, the current sortition winner can reset its own liveness clock with a trivial, cheap, non-advancing/conflicting proposal instead of actually producing a signable block.

### Finding Description
`check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-478`) is the function that both `check_tenure_change_confirms_parent` and `confirms_latest_block_in_same_tenure` delegate to when a `BlockProposal` for the active tenure arrives. It is invoked on every incoming proposal via the v1/v2 `check_proposal` paths (`stacks-signer/src/chainstate/v1.rs`, `v2.rs`), i.e. on the ordinary miner→signer `handle_block_proposal` path (`stacks-signer/src/v0/signer.rs:1574`), no signer majority or special access required.

The relevant branch: [1](#0-0) 

If the proposed block's `chain_length` is not higher than an already known block for the tenure, the function does **not** just reject the proposal — it also calls `update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` as long as the existing block hasn't been globally accepted for longer than `reorg_attempts_activity_timeout`. The same pattern repeats for a merely `PreCommitted` (unsigned) block: [2](#0-1) 

`update_last_activity_time` unconditionally overwrites the tenure's activity timestamp with `INSERT OR REPLACE`: [3](#0-2) 

This timestamp is exactly what `SortitionState::is_timed_out` / `SortitionMinerStatus::is_timed_out` (`stacks-signer/src/chainstate/v1.rs`, invoked from `check_proposal` at `stacks-signer/src/chainstate/v1.rs:144-157`) measures against `block_proposal_timeout` to decide whether to mark the current miner `SortitionMinerStatus::InvalidatedBeforeFirstBlock`. Per the shipped config documentation, this invalidation is one of the two required gates before the signer set will accept a tenure-extend from the *previous* miner: [4](#0-3) 

So the equality/liveness guard being broken is: *"has the current miner been silent for `block_proposal_timeout`?"* The reported vulnerability let anyone reset "has the user been silent long enough to unlock rewards?" for 1 wei; here the current tenure's own miner can reset "has the miner been silent long enough to be invalidated?" by resending the same or a slightly worse proposal (same/lower `chain_length`, same tenure) — an operation that costs nothing more than crafting and broadcasting a `BlockProposal`, no valid transactions or real mining effort required, and is explicitly *not* re-validated as a duplicate the way a fresh, advancing proposal is (comment at line ~406-410 even acknowledges "this invalid block proposal" is deliberately counted as activity).

### Impact Explanation
As long as the current sortition winner (or anyone able to get a `BlockProposal` accepted into the miner's StackerDB slot for that tenure — a single, one-slot actor) keeps sending stale/conflicting/non-advancing proposals for its own tenure faster than `block_proposal_timeout`, `is_timed_out` never returns true, so the miner is never marked `InvalidatedBeforeFirstBlock`. Per the documented behavior, this is a hard prerequisite gate for the signer set to accept a tenure-extend from the *previous* miner. A stalled/unresponsive-but-still-message-sending miner can therefore indefinitely block both (a) its own invalidation and (b) the fallback tenure-extend path, wedging block production for the tenure — a liveness denial-of-service reachable by a single actor with minimal resources, matching the "signer wedged into never signing valid blocks" / liveness-wedge impact category.

### Likelihood Explanation
Likelihood is high for any actor who is or can impersonate traffic into the current miner's tenure slot: the check runs on every `BlockProposal` received for the active tenure (`handle_block_proposal` → `check_block_against_state` → `check_proposal` → `confirms_latest_block_in_same_tenure`/`check_tenure_change_confirms_parent` → `check_latest_block_in_tenure`), requires no signature threshold, no cooperation from other signers, and the "activity" proposal can be arbitrarily cheap (e.g., resubmitting the same or a lower-height block). This is a normal, always-reachable code path, not a rare edge condition.

### Recommendation
Do not treat a non-advancing/conflicting proposal as unconditional proof of liveness. At minimum:
- Rate-limit or dedupe activity-timer resets per tenure/proposal-hash so the same (or trivially modified) stale proposal cannot repeatedly re-arm the clock.
- Require the "activity" proposal to be distinct from previously-seen non-advancing proposals, or bound the number of times a non-advancing proposal can extend the timer within `block_proposal_timeout`.
- Consider decoupling the tenure-extend gate from a signal that a stalled miner fully controls, e.g. corroborating "activity" with the stacks-node's own view (`get_tenure_tip`) rather than solely on `update_last_activity_time`.

### Proof of Concept
1. Miner M wins the sortition for tenure T and gets its `BlockProposal` for height N pre-committed/locally-accepted by a signer S.
2. Signer S is now waiting `block_proposal_timeout` of silence from M before invalidating M (a gate for accepting a tenure-extend from the prior miner).
3. Instead of proposing height N+1, M (or anyone who can get a proposal accepted for tenure T) repeatedly resends a `BlockProposal` for tenure T with `chain_length <= N` (e.g., the exact same block, or a deliberately inferior sibling) at an interval shorter than `block_proposal_timeout`.
4. Each time, `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:395-417`) hits the `chain_length <= info.block.header.chain_length` branch and calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())`, resetting the clock consulted by `is_timed_out`.
5. `is_timed_out` never fires, M is never marked `SortitionMinerStatus::InvalidatedBeforeFirstBlock`, and the signer set never accepts a tenure-extend from the previous miner — the tenure is wedged as long as M keeps sending cheap stale proposals, with no real block production required.

Note: I was not able to fully trace, within available tool budget, the exact upstream authentication/slot-ownership check that gates whether an arbitrary network peer (vs. only the legitimate sortition winner's key) can get a `BlockProposal` accepted into the tenure's StackerDB slot; the analysis above assumes the reachable path is limited to the current tenure's one sortition-winning miner (a "one-slot miner," consistent with the scan's allowed threat model), which is sufficient to establish the liveness wedge even without any additional privilege escalation.

    /// Update the tenure (identified by consensus_hash) last activity timestamp
    pub fn update_last_activity_time(
        &mut self,
        tenure: &ConsensusHash,
        last_activity_time: u64,
    ) -> Result<(), DBError> {
        debug!("Updating last activity for tenure"; "consensus_hash" => %tenure, "last_activity_time" => last_activity_time);
        self.db.execute("INSERT OR REPLACE INTO tenure_activity (consensus_hash, last_activity_time) VALUES (?1, ?2)", params![tenure, u64_to_sql(last_activity_time)?])?;
        Ok(())
    }
