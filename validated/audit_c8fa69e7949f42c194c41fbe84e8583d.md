### Title
`Blockstore::do_get_complete_block_with_components` panics on rooted-slot blockhash lookup, crashing RPC block-serving requests - (File: ledger/src/blockstore.rs)

### Summary
`Blockstore::do_get_complete_block_with_components`, the function backing `get_rooted_block`/`get_complete_block` (used by `getBlock`-family RPC calls), computes the block's terminal blockhash by scanning the fetched slot components for the last transaction-entry hash and calls `.unwrap_or_else(|| panic!(...))` if none is found [1](#0-0) . Like the Reth.sol `withdraw` path that assumed the `RocketDepositPool` would always have "excess balance" and reverted the whole operation when that assumption failed, this code assumes a full, rooted slot will always contain at least one `EntryBatch` component with a non-empty entry list, and panics the entire validator process handling the request if that assumption is violated.

### Finding Description
The function first validates that `slot_meta` exists and `slot_meta.is_full()`, then loads `slot_components` via `get_slot_components_with_shred_info`, and separately guards against `slot_components.is_empty()` by returning `BlockstoreError::SlotUnavailable` [2](#0-1) . However, past this guard it does not verify that any of the returned components is actually an `EntryBatch` with at least one entry — it only checks that the outer `Vec<BlockComponent>` is non-empty. The blockhash extraction then does:

```rust
let blockhash = slot_components
    .iter()
    .rev()
    .find_map(|component| match component {
        BlockComponent::EntryBatch(entries) => entries.last().map(|entry| entry.hash),
        BlockComponent::BlockMarker(_) => None,
    })
    .unwrap_or_else(|| panic!("Rooted slot {slot:?} must have blockhash"));
``` [1](#0-0) 

If `slot_components` consists solely of `BlockComponent::BlockMarker` entries (non-empty, satisfying the earlier `is_empty()` check) or contains only `EntryBatch` variants with empty entry vectors, the `find_map` returns `None` and the process panics with `Rooted slot {slot} must have blockhash`, unwinding/aborting the thread handling the RPC request rather than returning a graceful `BlockstoreError`.

This mirrors the audited pattern in `Reth.sol::withdraw`: both assume an underlying resource (excess balance / non-empty entry batch) is always present without an explicit runtime check, and both fail hard (revert / panic) instead of degrading gracefully, when that latent assumption is violated by a state the code path did not anticipate.

### Impact Explanation
A panic here is reached from an unprivileged, remote-triggerable path: any RPC client calling `getBlock`/`getConfirmedBlock` for a slot whose on-disk components include only `BlockMarker`s (or empty `EntryBatch`es) causes the request-handling thread to panic. Depending on how the RPC handler thread pool is configured, this can crash the validator's JSON-RPC service, matching the "concrete validator-process crash ... from one request" acceptance criterion. This does not require a malicious client to control chain state beyond what conditions can lead to such a components layout being persisted, and does not require multiple clients or a high call rate — a single request may suffice.

### Likelihood Explanation
The likelihood depends on whether normal (or slightly abnormal but still-valid, non-consensus-breaking) blockstore states can produce a `slot_components` vector containing only `BlockMarker` components or `EntryBatch`es with empty entry lists for a slot that passes `slot_meta.is_full()` and is rooted. I could not fully trace `get_slot_components_with_shred_info` and the `entry::block_component` construction path within the tool budget available, so I cannot conclusively confirm whether such a layout is reachable in practice versus purely theoretical. This is a meaningful gap in the analysis: the exploitability hinges entirely on whether `BlockMarker`-only (or empty-EntryBatch) full/rooted slots can occur through normal shred insertion, replay, or a race with pruning/compaction — a condition I was unable to verify from the available context.

### Recommendation
Explicitly validate, before or in place of the `unwrap_or_else(panic!)`, that the located blockhash exists; if not, return `Err(BlockstoreError::SlotUnavailable)` (or a dedicated error variant) instead of panicking. Additionally, harden `slot_components.is_empty()` guard to also account for the case where all `EntryBatch` components are present but contain zero entries, so that no code path can reach the `find_map`/`unwrap_or_else` with a guaranteed-`None` result.

### Proof of Concept
Not verified end-to-end due to inability to confirm, within the available tool budget, a concrete state-construction sequence (via shred insertion/replay) that yields a full, rooted slot whose `slot_components` are exclusively `BlockComponent::BlockMarker` or contain only empty `EntryBatch` lists. The vulnerable code and its unconditional panic are confirmed by direct inspection [3](#0-2) , but a reproducible trigger sequence could not be established with confidence in this session; a Devin session with terminal/build access would be needed to construct and run such a test against `Blockstore::insert_shreds` to determine reachability definitively.
