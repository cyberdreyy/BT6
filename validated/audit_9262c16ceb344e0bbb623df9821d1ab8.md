### Title
Front-runnable, deterministic lockup address lets any unprivileged account deploy a victim's lockup with attacker-chosen schedule and whitelist - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` is a fully public, unauthenticated entrypoint that derives the new lockup's account id solely from `sha256(owner_account_id)`, and lets the caller freely choose `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`, with the only gate being `attached_deposit() >= MIN_ATTACHED_BALANCE`. Because the resulting account id depends only on the intended beneficiary's `owner_account_id`, not on the caller or a nonce, any unprivileged account can pre-create (front-run) the lockup for a known/anticipated grant recipient with attacker-chosen terms before the legitimate grantor's transaction lands.

### Finding Description
Binding claimed to hold: `lockup.schedule_fields (lockup_duration, release_duration, vesting_schedule, whitelist_account_id) == grantor_intended_fields`. The code never enforces this.

`create` at [1](#0-0)  only checks the attached deposit and then deterministically derives `lockup_account_id` from `owner_account_id` alone:

```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
```

There is no `assert_called_by_foundation`, no owner/allowlist check, no nonce, and no reservation mechanism — any caller supplies `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and optionally a custom `whitelist_account_id` (defaulting to the factory's configured whitelist otherwise), as seen in the full parameter list and `LockupArgs` construction at [2](#0-1) .

Exploit flow:
1. Attacker learns/guesses a future grant recipient's `owner_account_id` (publicly knowable, e.g., a known team member or investor).
2. Attacker calls `create` with that `owner_account_id`, attaching exactly `MIN_ATTACHED_BALANCE`, and sets `release_duration`/`lockup_duration` to whatever they want (e.g., near-zero release for fast unlock or absurdly long, at attacker's choice) and `whitelist_account_id` to a malicious whitelist contract they control (which will later "whitelist" an attacker-controlled fake staking pool).
3. Because the account id is deterministic from `owner_account_id` only, this call creates and deploys the lockup at the exact address the legitimate grantor would have used.
4. When the real grantor later calls `create` for the same `owner_account_id` with the correct terms and full deposit, `Promise::new(lockup_account_id).create_account()` fails (account already exists); `on_lockup_create` detects failure via `is_promise_success()` and simply refunds the grantor's deposit — the legitimate lockup is never deployed at that address [3](#0-2) .
5. The victim's canonical lockup address now permanently runs attacker-chosen `staking_pool_whitelist_account_id` and schedule fields. If the victim (owner) later uses `select_staking_pool` on this contract, it queries `ext_whitelist::is_whitelisted` against the attacker-controlled whitelist contract [4](#0-3) , so the attacker can get their own fake "staking pool" whitelisted and have the owner delegate/stake real NEAR into it, a contract the lockup protocol now treats as trusted.

None of the existing guards catch this: `assert_owner` only protects owner-only *methods on the lockup*, not the factory's `create`; there is no `assert_called_by_foundation` anywhere in `lockup-factory/src/lib.rs`; `is_promise_success()` only detects the failed second creation and refunds — it does not prevent or reverse the first, malicious creation.

### Impact Explanation
The attacker permanently squats the deterministic address intended for a specific grant recipient, installing attacker-chosen `release_duration`, `lockup_duration`, and — most critically — an attacker-controlled `whitelist_account_id`. This matches "an account whitelisted or a lockup deployed with parameters its rightful creator never chose," and can escalate to Critical if the owner subsequently stakes into an attacker-whitelisted malicious pool, routing real NEAR to a contract the attacker controls. The attack is repeatable across any number of known/anticipated `owner_account_id`s at a cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per target, and blocks the legitimate grantor from ever deploying the correct lockup at that address.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only a NEAR account, `MIN_ATTACHED_BALANCE` (3.5 NEAR), and knowledge of the target `owner_account_id` before the legitimate grantor submits their `create` transaction. This is entirely plausible in practice — grant recipients are often publicly known (team members, advisors, investors) well before the token unlock/lockup is actually created on-chain, giving the attacker a wide window to front-run. The `README.md` documents this permissionless creation as an intentional feature ("no need to have access to the foundation keys to create lockup"), but does not account for the deterministic-address front-running consequence.

### Recommendation
Bind the lockup deployment to an authorized creator, e.g., require `env::predecessor_account_id() == self.foundation_account_id` (or a signed/allowlisted grantor) before allowing `create` to proceed with a given `owner_account_id`/schedule, or incorporate a grantor-supplied secret/nonce into the derived account id so it cannot be guessed/front-run, and add an explicit check that the target lockup account does not already exist with different terms before allowing funding to proceed silently.

```
Test plan (near-sdk `testing_env!` unit test, mirroring existing test scaffolding in `lockup-factory/src/lib.rs` tests module):
1. Initialize `LockupFactory` with `whitelist_account_id()` and `foundation_account_id()`.
2. As `attacker_account`, call `contract.create(victim_owner_account_id, malicious_short_duration, None, None, Some(malicious_release_duration), Some(attacker_whitelist_account_id))` with `attached_deposit = MIN_ATTACHED_BALANCE`; assert the promise succeeds (`PromiseResult::Successful`) via `on_lockup_create`, establishing binding: `deployed_lockup.whitelist == attacker_whitelist_account_id` (not `foundation`/intended whitelist).
3. As `foundation_account`, call `contract.create(victim_owner_account_id, intended_duration, None, None, Some(intended_release_duration), None)` with the full intended deposit, simulating the same deterministic `lockup_account_id`; feed `PromiseResult::Failed` for `create_account` (account already exists) into `on_lockup_create`; assert it returns `false` and refunds the foundation's deposit.
4. Assert final state: the lockup account at `sha256(victim_owner_account_id)` address has `whitelist_account_id == attacker_whitelist_account_id` and `release_duration == malicious_release_duration`, proving `deployed_terms != grantor_intended_terms` — the binding is broken.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
