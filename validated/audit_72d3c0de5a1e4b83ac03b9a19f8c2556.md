## Finding: Stale confirmations from removed multisig keys let requests execute below the required threshold — (File: `multisig/src/lib.rs`)

### Summary
The bug-class described in the report (a cached invariant — `tokenSupply` — that is never updated when the underlying state changes via `burn`, letting `MigrationAgent` operate on stale data) has a direct analog in `multisig/src/lib.rs`: the set of `confirmations` recorded for a pending request is never purged when the confirming key is later removed from the multisig. This lets a request execute using confirmations from an account/key that is no longer a valid multisig member, effectively executing a request with fewer *live* confirmations than `num_confirmations` requires.

### Finding Description
`MultiSigContract::confirm` counts entries in a per-request `HashSet<PublicKey>` and executes the request once `confirmations.len() + 1 >= self.num_confirmations` [1](#0-0) . Membership itself is not tracked by the contract; it is implicit in which access keys exist on the account, and a key is removed via a `DeleteKey` multisig request:

```
MultiSigRequestAction::DeleteKey { public_key } => {
    ...
    let request_ids: Vec<u32> = self.requests.iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k).collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [2](#0-1) 

This cleanup only removes requests **created (signed)** by the deleted key. It does **not** scan `self.confirmations` for other, still-pending requests that this key previously **confirmed** (added itself into the `HashSet<PublicKey>` via `confirm`, at [3](#0-2) ). Once the on-chain access key is deleted, that stale public key remains inside any other request's confirmation set forever, and it is still counted toward `num_confirmations` in the `>=` comparison in `confirm`.

**Equality that should hold:** `confirmations.len()` for a pending request should equal the number of *currently live* multisig members/keys that approved it. Instead, after `DeleteKey`, `confirmations.len()` can include phantom, revoked members, so `live_confirmers < recorded_confirmations`.

### Impact Explanation
This is a Critical-severity issue per the rubric ("a multisig request executed below threshold"). Concretely, with `num_confirmations = 2` and members A, B, C:
1. A creates request R (e.g., `Transfer`), B confirms it → `confirmations = {B}` (1 of 2).
2. The group later revokes B's key via a separate `DeleteKey{B}` request (a normal, legitimate multisig admin action, e.g. because B's key was thought compromised) — approved and executed with A+C (or any threshold) confirming.
3. `DeleteKey` only purges requests *signed by* B; R (signed by A, confirmed by B) is untouched, and B's stale entry stays in `confirmations` for R.
4. C alone calls `confirm(R)`; `confirmations.len() (1) + 1 >= num_confirmations (2)` is true, so R executes with only a single currently-valid confirming key (C), even though B is no longer a member.

This allows funds transfer (`MultiSigRequestAction::Transfer`), contract redeployment (`DeployContract`), or key/permission changes to be pushed through with fewer live approvals than configured, i.e. NEAR moved or account control changed by fewer authorized parties than the threshold — matching the "multisig request executed below threshold" Critical impact.

### Likelihood Explanation
No attacker outside the multisig membership is needed; this occurs through ordinary multisig operations (revoking a key is an expected administrative action, especially in response to a suspected key compromise). No special privilege beyond being one member confirming a pre-existing pending request is required at the final step. The only precondition is that a request was confirmed by a key before that key was removed — plausible in any long-lived multisig with periodic key rotation or after a leaked/compromised key is revoked (the exact scenario multisig key rotation is meant to protect against).

### Recommendation
When executing `DeleteKey` (and similarly `DeleteMember` in `multisig2`), iterate over **all** pending requests' `confirmations` sets (not just those signed by the removed key) and remove the deleted public key/member from each. Alternatively, validate at `confirm`/execution time that every public key present in a request's `confirmations` set still corresponds to a currently valid access key/member before counting it toward the threshold.

### Proof of Concept
Using the existing test harness in `multisig/src/lib.rs`:
1. `MultiSigContract::new(2)` deployed with keys `A`, `B` already as function-call access keys on the account (simulated by switching `signer_account_pk` in tests, as done in `test_multi_3_of_n` [4](#0-3) ).
2. As `A`, call `add_request(Transfer{...})` → `request_id`.
3. As `B`, call `confirm(request_id)` → `confirmations = {B}`, request not yet executed (1 < 2).
4. As `A`, create and confirm a `DeleteKey{public_key: B}` request with the same threshold (2 confirmations from other members) so it executes, deleting B's access key on-chain — note the `request_ids` filter in the `DeleteKey` handler only removes requests where `r.signer_pk == B`, so the earlier `Transfer` request (signed by A) is untouched and still has `confirmations = {B}` [2](#0-1) .
5. As `C` (a different valid remaining member, or even A again if permitted), call `confirm(request_id)` on the original `Transfer` request. `confirmations.len() (1, from stale B) + 1 >= 2` is satisfied, and `execute_request` fires the `Transfer`, despite only one currently valid key (`C`) having actually approved it after `B` was revoked.

This demonstrates the request executing with effectively 1 live confirmation against a configured threshold of 2.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
