### Title
Post-default instant withdraw receipts are minted at par and drain the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` has an explicit post-default path that routes new requests into `postDefaultRequests` and pays them only from `defaultRecoveryReserve` via `_claimPostDefaultWithdrawRequest`. `requestInstantWithdraw` has no equivalent handling: after `defaultRecoveryFinalized` it still mints a full-value strategy-token receipt, increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`, and `claimInstantWithdrawRequest` pays any receipt not recorded in `defaultRecoveryEpoch` at par via `_transferFundedClaim`. Since the only underlying held by the strategy after finalization is the recovery reserve, a post-default instant request is paid at par out of funds earmarked for defaulted-epoch claimants.

### Finding Description
The bug class of CVE-2017-10989 is a code path that fails to recognize a malformed/undersized object and processes it with normal logic. The analog here is a receipt created in a state the accounting did not anticipate: `requestWithdraw` explicitly detects `defaultRecoveryFinalized` and isolates the request (`postDefaultRequests[_user] = _amount`, mint/burn only, no `pendingWithdraws` bump) at IdleCreditVault.sol:247-257, but `requestInstantWithdraw` (lines 356-375) performs the pre-default flow unconditionally:

- `_mint(_user, _amount)` receipt at full value
- `instantWithdrawsRequests[_user] += _amount`
- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` where `currentEpoch > defaultRecoveryEpoch`
- `pendingInstantWithdraws += _amount`

On claim, `claimInstantWithdrawRequest` (lines 380-393) only routes receipts recorded under `defaultRecoveryEpoch` through the haircut path (`_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`). A receipt created after finalization sits in a later epoch bucket, survives the defaulted-claim clearing, and the full `instantWithdrawsRequests[_user]` remainder is paid 1:1 by `_transferFundedClaim`, which transfers underlying held by the strategy — post-default that balance is exactly `defaultRecoveryReserve` plus prefunded instant funds that belong to haircut-bearing claimants.

### Impact Explanation
Direct theft of recovery funds: the attacker receives `_amount` at par while every defaulted-epoch receipt holder is only entitled to `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`. Each post-default instant claim reduces the strategy's underlying balance without reducing `defaultRecoveryReserve`/`defaultRecoveryPrice` accounting, so legitimate defaulted and post-default claimants are left undercollateralized — the last claimants' `_transferDefaultRecovery` calls revert or pay less than the finalized recovery ratio. Loss is bounded by the attacker's tranche position but is effectively total for late claimants up to the reserve size.

### Likelihood Explanation
Requires: a finalized default (`defaultRecoveryFinalized`, `defaultInstantWithdrawsFinalized` can be either value — the par path executes regardless), the deployment in instant-withdraw mode (`allowInstantWithdraw` / `unscaledApr` conditions on the CDO side), and an unprivileged tranche holder able to trigger `requestInstantWithdraw` through `IdleCDOEpochVariant.requestWithdraw` when `lastEpochApr > currentApr + instantWithdrawAprDelta`. Attacker needs only a tranche-token balance; no privileged role is involved. The main uncertainty is whether the CDO's instant-withdraw branch remains reachable while `defaulted()` is true — nothing in `IdleCreditVault` blocks it, and `requestWithdraw`'s dedicated post-default branch shows the developers expected post-finalization requests to occur.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: if `defaultRecoveryFinalized`, route the receipt to `postDefaultRequests[_user]` (or revert), skip `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` updates, and ensure `claimInstantWithdrawRequest` cannot pay receipts created after `defaultRecoveryEpoch` at par via `_transferFundedClaim`.

### Proof of Concept
```solidity
// Foundry fork PoC (post-default instant claim drains recovery reserve)
// 1. Epoch N running; borrower defaults; manager calls finalizeDefault via CDO.
//    finalizeDefaultRecovery(recovered, source) sets defaultRecoveryPrice < RECOVERY_FULL,
//    defaultRecoveryEpoch = N, defaultRecoveryFinalized = true.
// 2. Attacker (tranche holder) calls cdoEpoch.requestWithdraw(amount, AAtranche)
//    with lastEpochApr > unscaledApr + instantWithdrawAprDelta so the CDO calls
//    creditVault.requestInstantWithdraw(underlyings, attacker).
//    => receipt minted at par into instantWithdrawsRequestsByEpoch[attacker][N+1].
// 3. Attacker calls cdoEpoch.claimInstantWithdrawRequest().
//    _claimDefaultedInstantWithdrawRequest clears only epoch-N receipts (returns 0),
//    then _burn + _transferFundedClaim pays full amount from strategy underlying.
// 4. A defaulted-epoch claimant calls claimWithdrawRequest();
//    _transferDefaultRecovery underflows/reverts or pays less than
//    claimBasis * defaultRecoveryPrice / RECOVERY_FULL because the reserve was drained.
assertGt(attackerGain, 0);
assertLt(victimPayout, victimBasis * defaultRecoveryPrice / RECOVERY_FULL);
```

Note: I was unable to fully verify within IdleCDOEpochVariant whether the instant-withdraw branch of `requestWithdraw` remains reachable while `defaulted()` is set; if the CDO hard-blocks all withdrawals post-default the attack path is unreachable. The asymmetry between `requestWithdraw` (which does handle the post-default state) and `requestInstantWithdraw` (which does not) is confirmed in the code.
