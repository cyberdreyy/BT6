## Title
Multisig executes requests below the live-member threshold because removing a key/member does not purge that key's stale confirmations from other pending requests - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
`confirm()` authorizes execution once the *count* of entries in a request's `confirmations` set reaches `num_confirmations`, but the contract never revalidates that every entry in that set still belongs to a currently authorized signer/member. When a key or member is removed via `DeleteKey` / `DeleteMember`, only the *requests that signer created* are purged; confirmations that signer previously cast on *other* still-pending requests are left untouched. This is the same bug class as the reported HydraDx issue: a state-changing operation (`remove_token`, here "remove signer") fails to propagate its effect into a downstream accounting/authorization check (`on_liquidity_changed`, here the confirmation-count threshold), leaving that check to operate on stale data.

### Finding Description
The invariant the multisig is supposed to enforce is:

`count(confirmations(R) ∩ current_members) >= num_confirmations` before `R` executes.

Instead, the actual check in `confirm()` is:

`len(confirmations(R)) + 1 >= num_confirmations`

with no filtering against the live signer/member set: [1](#0-0) 

The same unchecked-count pattern exists in the account/member-based rewrite: [2](#0-1) 

`assert_valid_request()` (called at the top of `confirm()`) only checks that the request and its confirmation set exist — it does not verify the members recorded in that confirmation set are still valid: [3](#0-2) 

When a key is removed via the `DeleteKey` action, cleanup is scoped only to requests *signed by* (i.e., created by) that key — `r.signer_pk == pk` — and the key's own `num_requests_pk` counter. Confirmations that the deleted key placed on *other* requests are never scrubbed from `self.confirmations`: [4](#0-3) 

The account/member-based `multisig2` variant has the identical gap in `delete_member`, filtering only `r.member == member` (requests created by the removed member) before removing the member from `self.members`: [5](#0-4) 

Since `self.members` (multisig2) / the underlying access-key set (multisig) is the source of truth for "who is currently entitled to approve," and `confirm()` never re-checks entries in `confirmations` against that source of truth, a confirmation cast by a since-removed signer keeps counting toward the K-of-N threshold indefinitely.

### Impact Explanation
This breaks the core custody binding of a multisig: *"a request executed below threshold."* An NEAR `Transfer`, `AddKey`/`AddMember`, `DeployContract`, or `FunctionCall` action can be executed by `execute_request()` even though fewer than `num_confirmations` **currently valid** signers actually approved it — one of the counted confirmations belongs to a party that has already been removed from the trusted signer set. This is listed explicitly as a Critical-severity impact ("a multisig request executed below threshold"), since it lets value move (e.g. via `MultiSigRequestAction::Transfer`) or privileged mutations occur (`AddKey`/`AddMember`, `DeleteKey`/`DeleteMember`, `DeployContract`) without the intended quorum of live authorizers.

### Likelihood Explanation
Key/member rotation (removing a departed or compromised signer) is an ordinary, expected multisig operation, not an edge case. Any pending request that received a confirmation from a signer prior to that signer's removal is silently left with a "phantom" confirmation that still counts. No attacker privilege beyond being one of the N signers is required: a malicious signer can deliberately confirm a request, then have their own key rotated out through a normal, otherwise-legitimate `DeleteKey`/`DeleteMember` request (which they may even help confirm), and their earlier confirmation remains valid toward the threshold on the original request. Only one additional legitimate confirmation is then needed to execute the request with an effective quorum of `num_confirmations - 1` current signers.

### Recommendation
When executing `DeleteKey` (multisig) or `DeleteMember` (multisig2), iterate all pending requests and remove the deleted key/member from every request's `confirmations` set (not only requests it created), or alternatively re-validate, inside `confirm()`, that every public key/member present in `confirmations(request_id)` is still a current signer/member before comparing the count against `num_confirmations`.

### Proof of Concept
1. Multisig configured 2-of-3 with keys A, B, C (`num_confirmations = 2`).
2. B calls `add_request` to create request `R` (e.g. `Transfer` to an attacker-controlled account).
3. A calls `confirm(R)` → `confirmations(R) = {A}`, `len+1 = 2 >= 2`? No wait 1+1=2>=2 so it would execute immediately with 2. To defer execution, assume 3-of-4 (A,B,C,D), `num_confirmations=3`.
4. A calls `confirm(R)` → `confirmations(R) = {A}` (1 < 3, pending).
5. Separately, a *different* fully-confirmed request `DeleteKey{public_key: A}` executes, removing A from the multisig. Cleanup only scans `self.requests` for entries where `signer_pk == A`; `R` was created by B, so it is untouched, and `confirmations(R)` still contains A. See [4](#0-3) .
6. C calls `confirm(R)` → `confirmations(R) = {A, C}`, len 2 (2 < 3, pending).
7. D calls `confirm(R)` → `len+1 = 3 >= 3` → `execute_request(R)` fires the `Transfer`, even though only C and D are currently valid signers — one of the "three" approvals (A's) came from a revoked key, per the check in [1](#0-0) .

The request executes with only 2 live-signer approvals against a nominal 3-of-4 threshold, confirming the threshold-bypass.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
