## Analysis

Confirmed analog: the `VoteInstruction::UpdateCommissionBps` (SIMD-0291) path lets a vote account's authorized withdrawer instantly change the `BlockRevenue` commission with no timing restriction, unlike the legacy commission-update path.

### Title
Vote Account Withdrawer Can Instantly Change `BlockRevenue` Commission With No Epoch Delay, Enabling Front-Running of Delegator Rewards - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
For the legacy `UpdateCommission` instruction, an in-epoch timing rule (only allow increases in the first half of an epoch) exists specifically to blunt "commission rug pulls," and reward calculation additionally reads a one-epoch-delayed snapshot of `inflation_rewards_commission` via `delay_commission_updates`. [1](#0-0) [2](#0-1) 

However, `update_commission_bps` (used for both `CommissionKind::InflationRewards` and `CommissionKind::BlockRevenue` under SIMD-0291) explicitly removes any timing rule, as the code comment states: "No commission update rule, per SIMD-0249 and SIMD-0291." [3](#0-2)  The vote processor also mirrors this "disable the commission update rule" reasoning: "Disable the commission update rule after the 'delay commission update' feature is activated because it imposes a minimum delay of one full epoch before the new commission rate takes effect." [4](#0-3) 

### Finding Description
For `CommissionKind::InflationRewards`, the removal of the in-epoch timing rule is safe because reward *calculation* independently reads a delayed, cached commission value from a snapshot taken at least one epoch earlier (`snapshot_epoch_vote_accounts`), specifically to prevent "last minute commission rugs": [5](#0-4) [2](#0-1) 

For `CommissionKind::BlockRevenue`, no equivalent delayed-snapshot mechanism exists. The block-reward split is driven by `pending_delegator_rewards`, which is accumulated via `DepositDelegatorRewards`/priority-fee deposits and split among delegators proportionally in `calculate_block_reward`, using the *current, live* `block_revenue_commission_bps` value read from `distribution_epoch_vote_accounts` (not any prior-epoch snapshot): [6](#0-5) 

Because `update_commission_bps` allows the authorized withdrawer to change `block_revenue_commission_bps` at any point, with any signer-controlled slot timing, and the reward-calculation path for block revenue has no equivalent epoch-delayed snapshot protection that the inflation-rewards commission enjoys, a vote account admin can raise the block revenue commission to 100% (10000 bps) immediately before block-reward distribution is computed/paid out, then lower it back afterward — capturing delegator rewards that had already accrued in `pending_delegator_rewards` prior to the change.

### Impact Explanation
This allows a malicious/compromised vote account withdrawer to unilaterally and instantly redirect delegator block-revenue rewards to themselves without delegators having any opportunity to react (undelegate/move stake), directly mirroring the "front-run users changing fees" pattern in the referenced report, but manifesting as concrete unsigned/unexpected fund redirection of delegator rewards within the Solana rewards/stake-accounting subsystem.

### Likelihood Explanation
The `update_commission_bps` instruction is reachable by any transaction signed by the vote account's `authorized_withdrawer` — no special/operator privilege beyond that key is required, and the change takes effect immediately within the same slot. Exploitation requires only that the withdrawer send the instruction shortly before epoch-boundary reward calculation/distribution and optionally revert it afterward. This is gated behind the `commission_rate_in_basis_points`, `delay_commission_updates`, and `block_revenue_sharing` feature flags being active, so it is only reachable once these SIMD-0291/SIMD-0123/SIMD-0249 features are activated on the cluster.

### Recommendation
Apply the same epoch-delay protection used for `inflation_rewards_commission` to `block_revenue_commission_bps`: either (a) snapshot `block_revenue_commission_bps` at the start of the rewarded epoch (or a prior epoch) similar to `CachedVoteAccounts`/`snapshot_epoch_vote_accounts`, and use that value in `calculate_block_reward`/the block-revenue split rather than the live value in `distribution_epoch_vote_accounts`, or (b) reinstate an in-epoch timing restriction specifically for `BlockRevenue` commission increases analogous to the pre-SIMD-0249 rule for `UpdateCommission`.

### Proof of Concept
Conceptual sequence, based on code paths inspected (not executed):
1. Delegators stake to vote account `V` with `block_revenue_commission_bps = 0`; over time, priority fees accumulate into `V.pending_delegator_rewards` via `DepositDelegatorRewards`. [7](#0-6) 
2. Immediately before epoch boundary reward calculation, `V`'s authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }`, which succeeds instantly since "No commission update rule" applies. [3](#0-2) 
3. At the epoch boundary, `calculate_block_reward` reads the now-updated `block_revenue_commission_bps = 10000` from the live/current vote state (`distribution_epoch_vote_accounts`), so delegators' share of `pending_delegator_rewards` collapses to zero even though the fees were accrued while commission was 0%. [6](#0-5) 
4. The withdrawer can then reset commission back to 0% for the next epoch, repeating the extraction each epoch boundary.

Note: I was unable to fully trace the exact code point where `block_revenue_commission_bps` is applied via `commission_split`/`commission_split_preserve_lamports` to divide `pending_delegator_rewards` between validator and stakers (this logic likely lives in a part of `runtime/src/inflation_rewards/mod.rs` or `block_component_processor/vote_reward.rs` not fully retrieved by the index within the iteration budget). This should be verified in a full checkout before treating the PoC as conclusive — I recommend starting a Devin session with full repository access to confirm the exact split call site and validate the timing window precisely.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }
