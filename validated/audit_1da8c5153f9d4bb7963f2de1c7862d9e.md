## Analysis: Missing mint-owner validation in Agave's token account parsing (analog to the GMX `initialLongToken`/`initialShortToken` type-confusion bug)

The GMX bug's root cause is: the code validates one field (`market.longToken`) but performs accounting using a different, unvalidated field (`params.initialLongToken`) that an attacker fully controls. Agave has a structurally identical pattern in the RPC token-account-parsing path: the code that resolves a token account's "mint" reference to compute its decimals/UI amount never verifies that the referenced mint account is actually owned by a known SPL Token program, even though a sibling code path (`get_token_supply`) does perform that exact check.

### Title
Missing SPL-Token-program ownership check on the referenced mint account causes wrong token balances/decimals to be reported by unprivileged JSON-RPC calls - (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
`get_mint_owner_and_additional_data` (used by `getTokenAccountBalance`, `getTokenLargestAccounts`, and — via `parsed_token_accounts.rs` — by every `jsonParsed`-encoded account/program-accounts RPC call) fetches whatever account is referenced by a token account's `mint` field and blindly unpacks it as an SPL `Mint`, without checking that this "mint" account is actually owned by a known SPL Token program. This is inconsistent with `get_token_supply`, which performs `is_known_spl_token_id(mint_account.owner())` before trusting the account's contents.

### Finding Description [1](#0-0) 

`get_mint_owner_and_additional_data` special-cases the native mint, and otherwise fetches `mint_account` and directly calls `get_additional_mint_data`: [2](#0-1) 

`get_additional_mint_data` only attempts to `StateWithExtensions::<Mint>::unpack(data)` — it never checks `mint_account.owner()`. Contrast this with `get_token_supply`, which explicitly enforces the ownership invariant before trusting the data: [3](#0-2) 

and `getTokenAccountBalance`, which validates the *token account's* owner but then calls the unchecked helper for the mint: [4](#0-3) 

The mint pubkey embedded in a token account is only guaranteed to point at a real SPL-Token-owned mint at the moment the token account was initialized (enforced by the SPL Token program itself, which is out of the agave scan scope). SPL Token-2022 mints support a `MintCloseAuthority` extension, which lets the mint's authority close a zero-supply mint, returning the account to system-program ownership while the pubkey (if it is a plain keypair address, not a PDA) remains reusable by whoever controls that keypair. An attacker who controls the mint's keypair can then reuse that same pubkey to create a new account owned by an arbitrary (e.g., attacker-deployed) program and write 82 bytes of data that still parses as a valid `Mint` struct, but with an attacker-chosen `decimals` value completely disconnected from the original token's real decimals — while any pre-existing `TokenAccount`s that still reference this pubkey as their `mint` field are untouched and still hold their real `amount`.

Because `get_mint_owner_and_additional_data`/`get_additional_mint_data` never re-validate that the referenced "mint" is still owned by a known SPL Token program at query time, every RPC call listed above will compute the token account's UI amount using the forged decimals, producing an arbitrarily wrong (over- or under-stated by orders of magnitude) `uiAmount`/`uiAmountString` for a token account that otherwise looks completely legitimate.

### Impact Explanation
This causes wrong/misreported account data to be returned by unprivileged, single-shot JSON-RPC calls (`getTokenAccountBalance`, `getTokenLargestAccounts`, and any `jsonParsed`-encoded `getAccountInfo`/`getMultipleAccounts`/`getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` call touching such an account). Downstream consumers (wallets, explorers, exchanges) that rely on the RPC-reported `uiAmount` rather than the raw `amount`+known decimals can be misled into displaying/using drastically incorrect balances, which is the class of impact explicitly accepted by the validation criteria ("wrong ... account data returned" / "decoder ... misreporting").

### Likelihood Explanation
The precondition (attacker controls a Token-2022 mint with `MintCloseAuthority`, closes it after emptying supply, and reuses the freed keypair address to seed forged `Mint`-shaped data under an attacker-owned program) is fully achievable by an ordinary unprivileged user with normal transactions, and the misreporting itself is then triggered by a single, cheap, unprivileged RPC read. It does not require any validator/peer/operator role, and does not require crafted snapshots or multiple RPC nodes.

### Recommendation
Add the same ownership check used in `get_token_supply` to `get_mint_owner_and_additional_data`/`get_additional_mint_data`, i.e. verify `is_known_spl_token_id(mint_account.owner())` before unpacking the account as a `Mint`, and propagate an `Invalid param` error (or fall back to raw/binary encoding) if the check fails — mirroring the recommended GMX fix of validating the actually-used field rather than only an unrelated one.

### Proof of Concept
1. Create a Token-2022 mint `M` with the `MintCloseAuthority` extension and `decimals = 9`; create token account `A` with `mint = M` and mint 1_000_000_000 units into `A` (i.e., "1.0" token).
2. Burn all supply of `M` to zero, then call `CloseAccount` on the mint (via the close-authority) — `M`'s pubkey reverts to system-program ownership; the attacker retains `M`'s private key.
3. Deploy a trivial attacker-owned program and use it (or `CreateAccount` + a custom write instruction) to re-create the account at pubkey `M`, owned by the attacker's program, with 82 bytes of data that unpacks as a valid `Mint` (`is_initialized = true`, `decimals = 0`).
4. Call `getTokenAccountBalance(A)` (or `getAccountInfo(A, {"encoding":"jsonParsed"})`). The response reports `uiAmount`/`decimals` computed with the forged `decimals = 0` instead of the original `9`, showing `A`'s balance as `1000000000` instead of `1.0` — a thousand-million-fold misreport — despite `A` never having been touched. pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}

    pub fn get_token_account_balance(
        &self,
        pubkey: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let account = bank.get_account(pubkey).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;

        if !is_known_spl_token_id(account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token account".to_string(),
            ));
        }
        let token_account = StateWithExtensions::<TokenAccount>::unpack(account.data())
            .map_err(|_| Error::invalid_params("Invalid param: not a Token account".to_string()))?;
        let mint = &Pubkey::from_str(&token_account.base.mint.to_string())
            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }

    pub fn get_token_supply(
        &self,
        mint: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;
        if !is_known_spl_token_id(mint_account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token mint".to_string(),
            ));

            Error::invalid_params("Invalid param: mint could not be unpacked".to_string())

            .get_extension::<InterestBearingConfig>()
