### Title
External Initiator credentials bypass "EIs not allowed" integer-ID job run restriction via shared SessionUserKey - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`PipelineRunsController.Create` intends to allow only real dashboard/API users to trigger job runs by integer job ID, explicitly stating `// only users are allowed to run jobs using int IDs - EIs not allowed` and gating the `RunJobV2` call behind `_, isUser := auth.GetAuthenticatedUser(c)` [1](#0-0) .

However, `auth.GetAuthenticatedUser` does not actually distinguish a real authenticated user from an external initiator. It simply checks whether the `SessionUserKey` value has been set on the gin context and type-asserts it to `*clsessions.User` [2](#0-1) . The EI authentication path, `AuthenticateExternalInitiator`, itself constructs and stores a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` under that same `SessionUserKey` for every successfully authenticated external initiator: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [3](#0-2) .

As a result, `GetAuthenticatedUser(c)` returns `ok == true` for both real dashboard users and for external-initiator-authenticated requests, since both populate the identical context key with a `*clsessions.User` object. The `isUser` boolean in `Create` therefore cannot actually tell the two apart, defeating the intended EI restriction. An attacker holding only valid EI credentials (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`) can hit `POST /v2/jobs/:ID/runs` with an arbitrary *integer* job ID (bypassing the UUID/webhook removal check entirely, since that only fires when the parameter parses as a UUID) and successfully invoke `prc.App.RunJobV2(ctx, jobID, nil)` for any job in the system — not merely the specific webhook/bridge job the EI was provisioned for.

### Impact Explanation
This is an authorization/role-check bypass: a lower-privilege, narrowly-scoped credential (external initiator) is able to perform an action — triggering an arbitrary job run by numeric ID — that the code explicitly intends to restrict to authenticated dashboard/API users only. This can cause unauthorized job execution (e.g. re-triggering OCR/Keeper/Flux-monitor-adjacent pipeline jobs, or any job type reachable via `RunJobV2`), which is an "unauthorized job run" impact class, and could be leveraged to cause unwanted on-chain transmissions or resource exhaustion depending on job type.

### Likelihood Explanation
The only precondition is possession of valid external-initiator credentials, which is explicitly listed as an in-scope, low-privilege attacker profile. No additional bridge/job association check is performed on the numeric-ID path (that check would need to happen inside `RunJobV2`/job ORM, but the routing-level `isUser` gate is what's supposed to prevent EIs from reaching this code path at all). The bypass is deterministic and repeatable for any valid EI credential set against any job ID known to the attacker.

### Recommendation
Do not reuse the same context key/type for both real users and external initiators. Track EI-vs-user identity separately (e.g. keep `GetAuthenticatedExternalInitiator` as the source of truth for EI sessions and add an explicit `isExternalInitiator` check in `Create`, or introduce a distinct marker such as a `SessionAuthenticatedByEIKey`/wrapper type) so `isUser` genuinely reflects only session/token-authenticated dashboard/API users, and reject integer-ID job run requests when the request was authenticated via `AuthenticateExternalInitiator`.

### Proof of Concept
1. In a handler/integration test, create an app with `cltest.NewApplicationEVMDisabled`, insert a job of any type via `app.AddJobV2` and obtain its integer `jb.ID`.
2. Create an `ExternalInitiator` bridge credential via the ORM/factory helpers used elsewhere in `core/web` tests (e.g. `cltest.MustInsertExternalInitiator` or equivalent) unrelated to the job created above.
3. Build an HTTP client that sends `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers for that EI (not a user session/API token) and POST to `/v2/jobs/<jb.ID>/runs`.
4. Assert that the response is `200 OK` with a `pipelineRun` resource (current behavior), demonstrating `isUser` was `true` for the EI, contradicting the code's own comment/intent that "EIs [are] not allowed" — expected/fixed behavior should be `401`/`403`.

	obj, ok := c.Get(SessionUserKey)
