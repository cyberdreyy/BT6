### Title
`instantWithdrawClaimsByEpoch` is never decremented on a funded instant-withdraw claim, inflating the default claim basis and diluting/locking default-recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to `Bribe.totalVoting` being increased on `deposit` but never decreased on `withdraw` (so `earned` divides by an inflated denominator), `IdleCreditVault` increases the per-epoch aggregate `instantWithdrawClaimsByEpoch[epochNumber]` in `requestInstantWithdraw` but never decreases it in `claimInstantWithdrawRequest` — it only zeroes `instantWithdrawsRequests[_user]` (lines 380–393). The stale aggregate is later used as a denominator/basis in `defaultPendingClaimBasis` (lines 644–649) and as the "prefunded reserve" in `_defaultPrefundedInstantReserve` (lines 716–723) during `finalizeDefaultRecovery`, so a user who claims an instant withdrawal and later re-requests (or any second requester) in the same epoch permanently poisons the recovery accounting for that epoch.

### Finding Description
`requestInstantWithdraw` records both per-user per-epoch basis and the global per-epoch aggregate:

```
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```
`contracts/strategies/idle/IdleCreditVault.sol:371-374`

`collectInstantWithdrawFunds` correctly decrements `pendingInstantWithdraws` when the CDO funds the queue (line 401), and `claimInstantWithdrawRequest` pays the user and zeroes `instantWithdrawsRequests[_user]` — but it leaves both `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched.

Later, if a default is finalized while `pendingInstantWithdraws != 0` in that same epoch, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes already-claimed amounts. Worse, `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` and counts that difference as underlying already held by the strategy — but those underlyings were already paid out to the claimants, so the reserve is phantom. `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` with an inflated `totalBasis` and a nonexistent `prefundedReserve`, diluting every recovery claimant.

Attack sequence (unprivileged lender, epoch E running):
1. Attacker calls `requestInstantWithdraw(100)` → `instantWithdrawClaimsByEpoch[E] = 100`, `pendingInstantWithdraws = 100`.
2. Borrower/CDO funds it via `collectInstantWithdrawFunds(100)` → `pendingInstantWithdraws = 0`.
3. Attacker calls `claimInstantWithdrawRequest` → receives 100; per-epoch counters still show 100.
4. Attacker (or a victim) calls `requestInstantWithdraw(50)` → `pendingInstantWithdraws = 50`, `instantWithdrawClaimsByEpoch[E] = 150`.
5. Borrower defaults before funding the 50; `finalizeDefaultRecovery` runs: `defaultPendingClaimBasis` includes 150 instant basis instead of 50, and `_defaultPrefundedInstantReserve` counts 100 phantom prefunded underlyings.

### Impact Explanation
All pending receipt holders and active LPs in the defaulted epoch receive `recoveryPrice` computed against a basis inflated by every previously-claimed instant withdrawal of that epoch, while the "prefunded" portion of the reserve does not exist in the contract. Concretely, with real recovery of R and true basis B, claimants get `R/(B + inflation)` instead of `R/B`, and because `_defaultPrefundedInstantReserve` books phantom funds, `defaultRecoveryReserve` overstates actual holdings — the last claimants' `_transferDefaultRecovery` calls revert on insufficient balance, permanently freezing the remainder of recovery funds in the strategy. This matches the report's impact class: users receive less yield and unclaimed amounts are permanently stuck.

### Likelihood Explanation
Requires only unprivileged actions (instant withdraw request + claim + a second request in the same epoch) plus a borrower default and `finalizeDefaultRecovery` with an unfunded instant remainder — a normal, expected state (pending instant requests at default time are explicitly handled by `defaultInstantWithdrawsFinalized`). No guard prevents re-requesting after an instant claim, and no code path clears the per-epoch aggregates outside the default claim itself.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the claim's epoch (tracked via a per-user last-instant-request marker, mirroring `lastWithdrawRequest`), so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only count unclaimed instant receipts. Alternatively store the request epoch per user and clear the per-epoch entries on funded claims.

### Proof of Concept
Foundry fork test skeleton (extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantClaimInflatesDefaultBasis() public {
    // epoch running; alice is a KYC'd AA lender
    vm.prank(alice);
    cdo.requestInstantWithdraw(100e6); // -> requestInstantWithdraw on strategy

    // borrower/manager funds instant queue via getInstantWithdrawFunds + collectInstantWithdrawFunds
    _fundInstantWithdraws();

    vm.prank(alice);
    cdo.claimInstantWithdrawRequest(); // pays 100, leaves instantWithdrawClaimsByEpoch[E] = 100

    // second request in same epoch, left unfunded
    vm.prank(bob);
    cdo.requestInstantWithdraw(50e6);

    // borrower defaults; finalize
    _triggerDefaultAndFinalize();

    // basis counted: 150 instead of real 50; recovery price diluted,
    // defaultRecoveryReserve exceeds actual balance -> last claimant reverts
    assertGt(strategy.defaultRecoveryReserve(), usdc.balanceOf(address(strategy)));
}
```

Expected: recovery price lower than `recovered/50`, and the final recovery claim reverts on `safeTransfer` underflow/insufficient balance, permanently freezing residual funds — mirroring the `Bribe.earned` dilution where `totalVoting` was never decremented on withdraw.
