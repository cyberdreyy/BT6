This confirms the guard holds. `broadcast_signed_block` at `stacks-signer/src/v0/signer.rs:2540-2560` explicitly rebuilds `block.header.signer_signature` from `addrs_to_sigs` (the DB-recorded, per-signer-address-authenticated signatures) rather than trusting whatever bytes happen to sit in the `signer_signature` field of the stored `NakamotoBlock`. ## No vulnerability found for this question.

**Why the claimed equality break doesn't produce exploitable divergence:**

- `signer_signature_hash_inner` and `miner_signature_hash_inner` include every header field except `signer_signature` (and `miner_signature` only for the miner hash), by design — this exclusion is intentional so multiple signers can sign the same hash incrementally. [2](#0-1) 
- The *only* header/body field that can differ between two payloads sharing the same `signer_signature_hash` is `signer_signature` itself; every other field (`tx_merkle_root`, `pox_treatment`, `consensus_hash`, `parent_block_id`, etc.) is committed inside the hash, and `txs` is bound via `tx_merkle_root`, so an attacker cannot substitute different transactions without breaking a collision-resistant hash. [2](#0-1) 
- `handle_block_proposal` does overwrite the stored `BlockInfo.block` on a re-proposal with the same `signer_signature_hash` key [3](#0-2) , so in principle the `signer_signature` bytes inside the stored block object could change between validation-submission time and signing time.
- However, this does not matter for chain safety: `create_block_acceptance` only signs `block.header.signer_signature_hash()` [4](#0-3) , which is invariant to that field by construction — so the signature always authenticates the same header content the node validated.
- More importantly, the *final* block that gets pushed to the chain is not the stored/possibly-tampered `block.header.signer_signature` — `broadcast_signed_block` explicitly discards whatever is in that field and rebuilds it strictly from the DB-tracked, per-address-verified signatures (`addrs_to_sigs`) ordered by `self.signer_addresses` [1](#0-0) . Each signature in `addrs_to_sigs` was independently authenticated via `Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s` against the correct `block_hash` in `store_and_process_block_signature`/`handle_block_signature` [5](#0-4) .

So the attacker cannot make a signer's signature authenticate different consensus-relevant bytes than what the node validated (the hash is invariant to the only mutable field), and cannot make the assembled/pushed block carry a mismatched `signer_signature` array either, since that array is reconstructed from verified per-signer signatures rather than propagated from the proposal payload. No safety or liveness property from the listed impact categories is broken by this path.

    fn signer_signature_hash_inner(&self) -> Result<Sha512Trunc256Sum, CodecError> {
        let mut hasher = Sha512_256::new();

        write_next(fd, &self.miner_signature)?;
        write_next(fd, &self.pox_treatment)?;

            write_next(fd, &self.problematic_txs)?;
