### Title
Missing monotonicity/finality check in `LPSkipToBlock` allows repeated replay of already-processed logs - ([File: core/web/lp_skip_controller.go])

### Summary
`LPSkipController.LPSkipToBlock` accepts an arbitrary `blockNumber` and forwards it directly to `Application.LPSkipToBlock` with only a trivial `>= 2` sanity check, `family`, and `chain-id` presence checks. There is no comparison against the LogPoller's current/finalized block height, so any caller authorized to hit this endpoint can repeatedly rewind the LogPoller to an earlier (even already-finalized) block, causing it to re-emit and re-process previously delivered logs.

### Finding Description
The handler `func (c *LPSkipController) LPSkipToBlock(gctx *gin.Context)` in `core/web/lp_skip_controller.go` performs the following validations only: [1](#0-0) 

- `request.BlockNumber < 2` rejection
- `Family` must be non-empty and equal `relay.NetworkEVM`
- `ChainID` must be non-empty

None of these checks compare the requested `blockNumber` to the LogPoller's currently tracked/finalized block for that chain. The value is then passed straight through to `c.App.LPSkipToBlock(ctx, request.Family, request.ChainID, request.BlockNumber)` at line 54, which repositions the LogPoller's replay cursor. Because there is no monotonic/finality guard in this function, two sequential calls — first with a high block number, then with a lower one — will both succeed, and the LogPoller will restart backfilling from the lower block on its next tick, re-delivering logs that were already processed (and already used to trigger downstream jobs/automation).

Whether this is exploitable by an unprivileged attacker depends on the router-level authorization applied to the `/v2/lp_skip_to_block` route; the question's premise (a "run-role" user, one of the explicitly in-scope attacker classes per the audit rules) implies that role is sufficient to invoke this endpoint, and the handler code itself contains no additional authorization or state check beyond whatever role gate the router assigns.

### Impact Explanation
Repeated invocation lets an authorized-but-unprivileged ("run" role) caller force the LogPoller to redeliver historical on-chain events. Depending on downstream consumers (log-triggered upkeeps, OCR/Automation jobs, external initiators listening on log-triggered pipelines), this can cause duplicate/replayed execution of financial-triggering job runs — i.e., unauthorized/duplicate job execution and potential unintended fund movement or duplicate payouts, matching the "unauthorized job run / fund movement" bounty impact class.

### Likelihood Explanation
The precondition is simply having credentials/role sufficient to call `/v2/lp_skip_to_block` (a "run" role token per the question's scoping, which is explicitly treated as an unprivileged/restricted attacker in this audit). No race condition or timing dependency is required — the vulnerability is a straightforward missing bound check, and the action is repeatable an unlimited number of times since nothing tracks the last-set or last-finalized checkpoint.

### Recommendation
Add a monotonicity/finality guard in `LPSkipToBlock` (or in `chainlink.Application.LPSkipToBlock`) that rejects requests where `blockNumber` is lower than the LogPoller's current finalized/last-processed block for the given chain, unless an explicit, higher-privileged "force rewind" flag/role is used. Additionally, confirm/tighten the router-level role requirement for this endpoint to an admin-only role given its operational sensitivity.

### Proof of Concept
1. In `core/web/lp_skip_controller_test.go`, set up the controller with a mock `Application` where `LPSkipToBlock` always succeeds and records invocations.
2. Issue request 1: POST `/v2/lp_skip_to_block` with `{"blockNumber": 1000, "family": "evm", "chain-id": "1"}` using a run-role authenticated client — assert `200 OK`.
3. Issue request 2 immediately after: POST same endpoint with `{"blockNumber": 500, "family": "evm", "chain-id": "1"}` — assert it also returns `200 OK` (no rejection due to being lower than the prior/finalized block).
4. Assert the mock `Application.LPSkipToBlock` was called twice with decreasing block numbers, demonstrating the absence of any monotonicity/finality check that should have blocked the second, lower request.

func (c *LPSkipController) LPSkipToBlock(gctx *gin.Context) {
	var request LPSkipToBlockRequest
	if err := gctx.ShouldBindJSON(&request); err != nil {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, err)
		return
	}
	if request.BlockNumber < 2 {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.Errorf("block number must be >= 2: %v", request.BlockNumber))
		return
	}

	if request.Family == "" {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.New("chain family was not provided"))
		return
	}
	if request.Family != relay.NetworkEVM {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.Errorf("unsupported chain family %q, only %s is supported", request.Family, relay.NetworkEVM))
		return
	}

	if strings.TrimSpace(request.ChainID) == "" {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.New("chain-id was not provided"))
		return
	}
