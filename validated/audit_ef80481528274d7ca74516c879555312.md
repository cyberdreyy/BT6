### Title
Withdraw claims always pay `msg.sender` — a lender blocked by the underlying token (e.g., USDC/USDT blacklist) can never claim funds - (contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.claimWithdrawRequest()` and `claimInstantWithdrawRequest()` hard-code `msg.sender` as the payout recipient and expose no `_receiver` parameter. When the vault's `underlying` is a centrally-controlled stablecoin such as USDC or USDT, a lender whose address gets blacklisted after requesting a withdraw cannot redirect the payout to another address, so the claim transaction always reverts inside the token's `transfer` and the lender's funds are permanently frozen in the strategy.

### Finding Description
`IdleCDOEpochVariant.claimWithdrawRequest()` at contracts/IdleCDOEpochVariant.sol:967-971 forwards the caller identity to the strategy:

```solidity
function claimWithdrawRequest() external {
  IdleCreditVault(strategy).claimWithdrawRequest(msg.sender);
}
```

and `claimInstantWithdrawRequest()` at contracts/IdleCDOEpochVariant.sol:975-979 does the same for instant requests:

```solidity
function claimInstantWithdrawRequest() external {
  _checkNotAllowed(!allowInstantWithdraw);
  IdleCreditVault(strategy).claimInstantWithdrawRequest(msg.sender);
}
```

Inside `IdleCreditVault` (contracts/strategies/idle/IdleCreditVault.sol), both claim functions burn the stored strategy tokens / clear the request entry and `safeTransfer` the `underlying` directly to the passed user address — i.e., `msg.sender`. There is no overload or alternate path allowing the requester to specify a different recipient. The withdraw request itself (`requestWithdraw`, burning tranche tokens and recording `withdrawsRequests`/`instantWithdrawsRequests`) is keyed to the requester, so the payout can only ever go to that same address.

If the lender's address is blacklisted by the underlying token issuer (Circle's `isBlacklisted` for USDC, Tether's equivalent for USDT) between `requestWithdraw` and the claim — or was blacklisted before claiming — the `safeTransfer` in the claim path reverts permanently. The tranche tokens are already burned at request time, so the lender cannot revert to a redeem flow either; the accounting entry sits as a claimable liability that can never be paid to a reachable address.

### Impact Explanation
Permanent freezing of funds. Once a withdraw request is recorded, the only exit is a claim that sends `underlying` to `msg.sender`. A blacklisted requester loses the full requested amount: the tranche tokens were already burned during `requestWithdraw`/`_withdrawOps`, so the user holds neither tranche tokens nor underlying. Loss = 100% of the requested withdrawal amount (principal plus accrued interest).

### Likelihood Explanation
- USDC/USDT blacklisting is a real, recurring event (regulatory orders, sanctions, exploit tracing); the protocol explicitly supports such tokens as `underlying`.
- No privileged party needs to misbehave — the freeze is triggered solely by the token issuer's action plus the missing `_receiver` param.
- Mitigation available today: none within the contracts. `isWalletAllowed`/Keyring only gates deposits, not claims, so a blocked-but-KYC'd user is still stuck. A third party cannot claim on the user's behalf because the request is keyed to `msg.sender`. This is the same bug class as the Derby `withdrawAllowance` finding (where `withdraw` had `_receiver` but `withdrawAllowance` did not); here both claim entry points lack a recipient argument.

### Recommendation
Add a `_receiver` parameter to `claimWithdrawRequest` and `claimInstantWithdrawRequest` (or provide an overload `claimFor(address receiver)` callable only by the requester) and pass it through to `IdleCreditVault.claimWithdrawRequest(msg.sender, receiver)` / `claimInstantWithdrawRequest`, transferring `underlying` to `_receiver` instead of `msg.sender`. The request bookkeeping must remain keyed to the original requester; only the payout destination should be parameterized. Applying the same treatment to `IdleCDOEpochQueue.claimWithdrawRequest`/`claimDepositRequest` (contracts/IdleCDOEpochQueue.sol:393-411) would harden the queued path, though that contract is out of scope here.

### Proof of Concept
Foundry fork PoC sketch against a mainnet USDC-based `IdleCreditVault` epoch pool, using the existing harness in `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testPoc_claimWithdrawRequest_BlacklistedUser() external {
    address alice = vm.addr(0xA11CE);
    deal(defaultUnderlying, alice, 10000e6); // USDC underlying
    deal(defaultUnderlying, borrower, 200000e6);

    // 1. Alice deposits into AA tranche
    vm.startPrank(alice);
    IERC20Detailed(defaultUnderlying).approve(address(idleCDO), type(uint256).max);
    uint256 mintedAA = idleCDO.depositAA(10000e6);
    vm.stopPrank();

    // 2. Epoch starts, then stops with interest; Alice requests withdraw
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());
    vm.prank(alice);
    cdoEpoch.requestWithdraw(mintedAA, address(AAtranche)); // tranche tokens burned here

    // 3. USDC blacklists Alice before she claims (simulate issuer action)
    vm.prank(usdcBlacklister); // e.g. 0x5db0115f3B72d19cEa34dD697cf412Ff86dc7E1b on mainnet
    IFiatToken(defaultUnderlying).blacklist(alice);

    // 4. Alice's claim always reverts inside USDC.transfer -> permanent freeze
    vm.startPrank(alice);
    vm.expectRevert(); // "Blacklistable: account is blacklisted"
    cdoEpoch.claimWithdrawRequest();
    vm.stopPrank();

    // No alternate path: request entry still recorded, but underlying never transferable to alice.
    // Alice holds no tranche tokens (burned in step 2) and no underlying -> 100% loss.
}
```

Steps 1–2 mirror `testClaimWithdrawRequest`/`testClaimInstantWithdrawRequest` in `test/foundry/IdleCreditVault.t.sol` (e.g., lines 4741–4790, 5851–5910); the only new step is invoking the fiat-token blacklister between request and claim. The same script works for the instant path via `claimInstantWithdrawRequest`.

Note: within this sandbox I could not view the exact `safeTransfer` lines inside `IdleCreditVault.claimWithdrawRequest`/`claimInstantWithdrawRequest` (grep returned no line-level snippets for that file), but the delegation is explicit at `IdleCDOEpochVariant.sol:970` and `:978`, and the msg.sender-only payout pattern is consistent across the codebase (`IdleCDOEpochQueue.sol:409`, `IdleCDOTruefiVariant.sol:75`). If the underlying claim functions internally support an arbitrary beneficiary parameter already, the exposure would be limited to the missing pass-through on the variant — the PoC confirms which is the case.
