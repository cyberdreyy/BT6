### Title
Stale-slot fallback in `JsonRpcRequestProcessor::bank()` can silently return account/state data from the wrong (root) slot instead of the requested commitment slot - ([File: rpc/src/rpc.rs])

### Summary
The InsuranceFund report is a TOCTOU/"stale dependency" bug class: a value used to resolve a follow-up read (`vusd` address) is mutated out-of-band between the time a user's intent is set and the time it is executed, causing the wrong underlying resource to be used without any error. The closest unprivileged-user analog in agave is `JsonRpcRequestProcessor::bank()` in `rpc/src/rpc.rs`, which resolves a `commitment` into a `slot` under one lock (`block_commitment_cache`) and then independently looks up the `Bank` for that slot under a different lock (`bank_forks`). If `BankForks` prunes/replaces that slot between the two lock acquisitions (a normal background operation done by `set_root`/`prune_non_rooted`, not a privileged "user" action from the RPC caller's perspective), the lookup misses and the code **silently falls back to `root_bank()`** instead of returning an error, so the RPC response can describe a completely different slot/state than what was requested.

### Finding Description
`bank()` is used by nearly every read-only, unprivileged JSON-RPC handler (`getAccountInfo`, `getBalance`, `getSlot`, `getTokenAccountBalance`, `getTokenSupply`, etc., via `get_bank_with_config`): [1](#0-0) 

The function:
1. Reads `self.block_commitment_cache` to translate the requested `commitment` into a `slot` (line 365-369).
2. Separately acquires `self.bank_forks.read()` and calls `r_bank_forks.get(slot)` (line 381-382).
3. If that slot is no longer present in `BankForks` — which happens whenever `BankForks::set_root()` prunes non-rooted/older banks concurrently — the code does **not** propagate an error. It logs a `warn!` and returns `r_bank_forks.root_bank()` instead (lines 382-399): [2](#0-1) 

The comment in the code explicitly documents this as a known race and a known bug:
> "The slot may not be found as a result of a known bug in snapshot creation... Also, it may occur after an old bank has been purged from BankForks and a new BlockCommitmentCache has not yet arrived. To make this case impossible, BlockCommitmentCache should hold an Arc<Bank> everywhere it currently holds a slot."

There is a regression test elsewhere in the codebase that documents essentially the same class of race for account loads (`set_root(N+1)` racing the commitment cache update): [3](#0-2) 

That test guards against the accounts-index/ancestors variant of the race (via ancestor-based filtering in `do_load`), but it does not cover the `bank()`/`BankForks` slot-resolution path used by RPC, which still has the documented fallback-to-`root_bank()` behavior.

`BankForks::set_root()` (invoked from `commitment_service.rs`/replay) prunes older forks via `prune_non_rooted` under the `bank_forks` write lock, independent of and not synchronized with updates to `block_commitment_cache`: [4](#0-3) 

Because `block_commitment_cache` and `bank_forks` are two separate `RwLock`s updated by two separate subsystems, an RPC caller resolving `commitment` to `slot` can race with a concurrent `set_root`/prune that removes exactly that slot from `BankForks` before the second lookup runs, without the RPC layer ever raising a `SlotRemoved`/`MinContextSlotNotReached`-style error to the caller.

### Impact Explanation
This is a "wrong-slot/fork/account data returned" class bug (explicitly listed as an acceptable impact). An unprivileged RPC client requesting data at a specific `commitment`/slot can receive a response whose `context.slot`/account/balance data corresponds to an unrelated, much older `root_bank()` slot instead of the requested one — with no error surfaced. This can mislead any consumer relying on RPC response consistency (e.g., wallets, indexers, bridges/oracles reading balances) analogous to how Alice in the InsuranceFund PoC withdrew against the wrong underlying asset because a dependency reference changed mid-flight. Unlike the accounts-index case (which has ancestor-based protection), this specific `bank()` fallback path has no such guard and is explicitly called out in the source comment as unresolved.

### Likelihood Explanation
The race window exists during every `set_root`/pruning cycle, which occurs roughly once per rooted slot under normal validator operation, and any RPC read using `commitment` (i.e., not pinned to an already-held `Arc<Bank>`) is a candidate. No special access or malicious input is needed — a single, ordinary, unprivileged JSON-RPC call landing in this narrow window suffices. However, exploiting it deterministically (rather than merely observing it happen due to normal validator background pruning) would require inducing pruning timing precisely, so real-world likelihood is more "occurs incidentally under load/pruning pressure" than "on-demand exploitable," matching the report's original characterization of an edge-case race rather than a routinely triggerable bug.

### Recommendation
Make the slot-to-bank resolution atomic with respect to `BankForks` pruning: either (a) have `BlockCommitmentCache` store an `Arc<Bank>` directly for the commitment slot (as suggested in the existing code comment) instead of a bare `Slot`, or (b) hold the `bank_forks` read lock across both the slot computation and the `get(slot)` lookup, or (c) return a `MinContextSlotNotReached`/`SlotRemoved`-style RPC error instead of silently substituting `root_bank()` when the resolved slot is no longer present in `BankForks`.

### Proof of Concept
Not independently reproducible from the index alone (requires a running validator with concurrent `set_root` pruning and RPC traffic to hit the race window); the vulnerable code path and its self-documented race condition are shown above at `rpc/src/rpc.rs:349-399` and `runtime/src/bank_forks.rs:461-528`. Due to index size limits, a live reproduction would need to be validated in a full Devin session with the actual validator binary running concurrent replay/root-setting and RPC clients to confirm timing-dependent triggering.

    #[allow(deprecated)]
    fn bank(&self, commitment: Option<CommitmentConfig>) -> Arc<Bank> {
        debug!("RPC commitment_config: {commitment:?}");

        let commitment = commitment.unwrap_or_default();
        if commitment.is_confirmed() {
            let bank = self
                .optimistically_confirmed_bank
                .read()
                .unwrap()
                .bank
                .clone();
            debug!("RPC using optimistically confirmed slot: {:?}", bank.slot());
            return bank;
        }

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
