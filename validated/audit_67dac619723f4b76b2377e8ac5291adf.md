### Title
EI credential holders bypass the "EIs not allowed" integer-job-ID restriction in `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`PipelineRunsController.Create` gates the integer-job-ID run path with `_, isUser := auth.GetAuthenticatedUser(c)` and a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed" [1](#0-0) . However, `GetAuthenticatedUser` simply reads the `SessionUserKey` from the gin context [2](#0-1) , and `AuthenticateExternalInitiator` — the auth method used for external-initiator (EI) credentials — explicitly injects a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` into that same `SessionUserKey`: [3](#0-2) 

Because `Authenticate` runs multiple auth methods (session, token, EI) and whichever succeeds sets `SessionUserKey` [4](#0-3) , a request authenticated purely via EI `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (no session cookie, no user API token) ends up with `GetAuthenticatedUser(c)` returning `ok=true`, i.e., `isUser == true` in `PipelineRunsController.Create`. This defeats the intended restriction: the EI holder can then POST `/v2/jobs/<intID>/runs` and reach `prc.App.RunJobV2(ctx, jobID, nil)` exactly like a real dashboard/API user, contrary to the code's own comment and the reviewer's stated security invariant.

### Impact Explanation
An entity holding only EI credentials (a lower-trust, single-purpose credential intended only to trigger specific webhook job runs) can trigger arbitrary job runs by integer ID for **any** job on the node, not just the job(s) the EI credential was provisioned for. This is an authorization bypass allowing unauthorized job execution, matching the "unauthorized job run" bounty impact class. Depending on job type (e.g., jobs with side effects, on-chain transactions triggered from job pipelines), this could lead to unintended fund movement or unauthorized on-chain actions.

### Likelihood Explanation
Exploitation requires only a valid EI credential (access key + secret), which is a much lower-privilege credential than a user session/API token and is often distributed to external integrations. No admin/operator access needed. The request is trivially repeatable — it is a single HTTP POST with EI headers and an integer job ID that differs from the job(s) the EI is nominally scoped to. The vulnerability is deterministic (not a race or timing issue), so likelihood is high once an EI credential is obtained/leaked.

### Recommendation
Do not rely on `SessionUserKey`/`GetAuthenticatedUser` alone to distinguish real users from EI credentials, since `AuthenticateExternalInitiator` populates the same key. In `PipelineRunsController.Create`, explicitly check that the request was authenticated by session or API token (e.g., check absence of `auth.GetAuthenticatedExternalInitiator(c)`, or use a distinct context key/marker set only by `AuthenticateBySession`/`AuthenticateByToken`) before permitting the integer-ID run path. Alternatively, stop `AuthenticateExternalInitiator` from writing to `SessionUserKey` and instead have EI-specific routes/checks use only `SessionExternalInitiatorKey`.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a test router mounting `POST /v2/jobs/:ID/runs` behind `auth.Authenticate(store, auth.AuthenticateBySession, auth.AuthenticateByToken, auth.AuthenticateExternalInitiator)` wired to `PipelineRunsController.Create`, matching the real router wiring in `core/web/router.go`.
2. Create a job with a known integer ID via the ORM/fixtures, and a mocked `ExternalInitiator` record in the auth store.
3. Send `POST /v2/jobs/<intID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials, and **no** session cookie and **no** user API token headers.
4. Assert:
   - Current (vulnerable) behavior: response is `200`/pipeline-run resource JSON, and `App.RunJobV2` is invoked with the given `jobID` (verify via a mock/spy `RunJobV2`).
   - Expected (fixed) behavior: response is `422` with body `"bad job ID"`, and `RunJobV2` is never called, for EI-only authenticated requests.
5. Add a control test case authenticating via a real user session/API token confirming that the same int-ID path succeeds (`RunJobV2` called), to confirm the fix doesn't break legitimate user flows.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
