### Title
Dust-sized queued withdraw request permanently reverts `processWithdrawRequests`, freezing all queued withdrawals for the epoch - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external report describes an out-of-bounds read that hits an assert and causes a denial of service. The closest analog in idle-tranches is an attacker-controlled panic-style abort in the withdrawal-queue processing path: `IdleCDOEpochQueue.processWithdrawRequests` computes the epoch withdraw price as `_underlyingsRequested * ONE_TRANCHE / _pending` and reverts with `Is0()` when it rounds to zero. Any KYC-passing tranche holder can queue a dust-sized `requestWithdraw`, making the entire epoch's batch processing revert unconditionally and blocking every other user's pending withdrawal.

### Finding Description
In `contracts/IdleCDOEpochQueue.sol`, `requestWithdraw(uint256 amount)` accepts any `amount` of tranche tokens with no minimum and books it into `epochPendingWithdrawals[nextEpoch]` and `userWithdrawalsEpochs` [1](#0-0) . During the buffer period, the manager calls `processWithdrawRequests`, which forwards the aggregate `_pending` to `IdleCDOEpochVariant.requestWithdraw` and then derives the epoch price:

```solidity
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
``` [2](#0-1) 

The contract's own test `testProcessWithdrawRequestsWith0Price` confirms the revert path: a withdraw request of `100` wei of tranche tokens produces `_underlyingsRequested` that rounds to zero and makes `processWithdrawRequests` revert [3](#0-2) .

Because the revert rolls back the whole transaction, `epochWithdrawPrice[_epoch]` is never set and `pendingClaims` is never cleared. Every subsequent call reverts identically as long as the dust request remains in `epochPendingWithdrawals[_epoch]`. The attacker has no incentive to call `deleteWithdrawRequest`, and no other account (including owner/manager) can remove the attacker's entry — `deleteWithdrawRequest` only clears `userWithdrawalsEpochs[msg.sender]` [4](#0-3) . The attacker can repeat this every epoch at dust cost.

This mirrors the CVE bug class: an attacker-reachable edge input hits a hard abort (`Is0` revert, the Solidity analog of the packet-buffer assert), and the abort is on a shared batch path, so one malicious record DoSes all records in the same "packet" (epoch).

### Impact Explanation
All tranche tokens queued via `requestWithdraw` for the affected epoch are frozen inside the queue: `processWithdrawRequests` can never succeed while the dust entry exists, so no queued withdrawal in that epoch can be converted into a claim. Honest users can recover their tranche tokens by calling `deleteWithdrawRequest(_requestEpoch)` themselves, so the impact is a temporary (indefinite, attacker-renewable) freezing of queued withdrawal funds rather than permanent loss. Quantified: for the cost of ~100 wei of tranche tokens per epoch, the attacker blocks the entire `epochPendingWithdrawals[_epoch]` balance — potentially the full queued outflow of the pool — and can re-grief every subsequent epoch, effectively disabling the queued-withdrawal lane. Note the attacker must hold tranche tokens (i.e., be a KYC-passing lender or tranche-token holder), which is within the allowed unprivileged-attacker model.

### Likelihood Explanation
- Preconditions: the credit vault runs in a mode where `requestWithdraw` on the CDO can return a zero-rounded underlying amount for a dust request — true whenever `virtualPrice(tranche) * _pending < ONE_TRANCHE`, which holds for small `_pending` at any tranche price ≥ ~1e18 scaled values, and trivially during APR0 or low-price epochs. The existing test demonstrates it concretely.
- Cost: near zero (dust tranche amount); no privileged role needed.
- Detection/mitigation gap: there is no minimum-amount check in `requestWithdraw`, and the `Is0` guard — added to prevent a zero epoch price — converts rounding into a hard revert on a shared batch operation instead of isolating the offending request.

### Recommendation
Enforce a minimum `amount` in `IdleCDOEpochQueue.requestWithdraw` (e.g., an amount that guarantees `_pending * virtualPrice >= ONE_TRANCHE`), or handle the zero-price case gracefully: skip/zero out only the dust portion, or allow `processWithdrawRequests` to proceed with `isEpochWithdrawZero[_epoch] = true` semantics so users can clear their requests instead of reverting. Alternatively, let owner/manager delete any user's unprocessed withdraw request so a poisoned epoch can be unblocked.

### Proof of Concept
Reproducible Foundry fork PoC (mirrors `testProcessWithdrawRequestsWith0Price` plus a victim request):

```solidity
function testDustWithdrawBlocksEpochProcessing() external {
    _stopCurrentEpoch();                 // epoch #1 buffer

    // victim queues a real withdrawal
    address victim = makeAddr('victim');
    uint256 tranchesV = _depositWithUser(victim, 100e6);
    // attacker queues dust (must hold >=1 wei tranche)
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1e6);
    uint256 dust = 100; // wei of tranche

    vm.prank(manager);
    cdoEpoch.startEpoch();               // epoch running: requests allowed

    vm.prank(victim);
    queue.requestWithdraw(tranchesV);
    vm.prank(attacker);
    queue.requestWithdraw(dust);

    _stopCurrentEpoch();                 // buffer: requests processed
    // processing the whole epoch reverts because _epochPrice == 0
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    vm.prank(manager);
    queue.processWithdrawRequests();

    // repeat call still reverts; victim's tranches stay in the queue
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    vm.prank(manager);
    queue.processWithdrawRequests();
    assertGt(tranche.balanceOf(address(queue)), 0);
    // victim can only recover via deleteWithdrawRequest; attacker keeps dust to re-grief next epoch
}
```

Uncertainty note: whether `_underlyingsRequested` rounds to exactly 0 depends on `IdleCDOEpochVariant.requestWithdraw`'s pricing (`virtualPrice`), but the checked-in test already shows a 100-wei request triggering the `Is0` revert, so the path is confirmed reachable.

  function deleteWithdrawRequest(uint256 _requestEpoch) external {
    // if the epoch withdraw price is already set, withdrawal requests were already processed so
    // the withdraw request can't be deleted. Withdraw requests can be deleted even if the epoch is running
    _checkNotAllowed(epochWithdrawPrice[_requestEpoch] != 0 || isEpochWithdrawZero[_requestEpoch]);

    uint256 amount = userWithdrawalsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request for the epoch
    userWithdrawalsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending withdraw requests
    epochPendingWithdrawals[_requestEpoch] -= amount;
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, amount);
  }
```
