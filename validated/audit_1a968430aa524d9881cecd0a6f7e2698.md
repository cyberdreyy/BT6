### Title
`OverwriteKey` overwrites only the first duplicate-key entry while `Get`/`Value` return the last one, letting a trailing duplicate variable shadow the runner's authoritative overwrite - ([File: common/spec/variables.go])

### Summary
`Variables.OverwriteKey` (common/spec/variables.go:144-151) scans forward and mutates the *first* slice element whose `Key` matches, but every read path (`value()`, common/spec/variables.go:107-123) scans backward and returns the *last* matching element. Because the codebase itself documents that GitLab can hand the runner multiple `Variable` entries sharing the same `Key` with "the last one being the final overridden one" (see the `Dedup` doc comment, common/spec/variables.go:178-190), a duplicate-key situation is an expected, reachable state — and in that state `OverwriteKey`'s in-place edit of the first occurrence is invisible to every reader.

### Finding Description
- `value(key, pathnames)` explicitly implements "last-match-wins": `for i := len(b) - 1; i >= 0; i--`, returning as soon as it finds `b[i].Key == key` (common/spec/variables.go:114-121). `Get()` and `Value()` both delegate to this.
- `Set()` (common/spec/variables.go:74-94) and the `Dedup` comment (common/spec/variables.go:178-190) both encode the same assumption: when duplicate keys exist in a `Variables` slice, the *last* occurrence is authoritative, because GitLab's job payload can legitimately contain several entries for one key (e.g., different precedence tiers of CI/CD variables) with the final value appended last.
- `OverwriteKey` (common/spec/variables.go:144-151) does the opposite: `for i, v := range b { if v.Key == key { b[i] = variable; return } }` — it edits the *first* match it encounters and returns immediately, ignoring any later duplicate of the same key.
- Exploit flow: if the `Variables` slice already contains two entries with `Key == "X"` (index 0 = an earlier/lower-priority value, index 1 = a later/duplicate value that a job or pipeline-level variable definition placed after it), and the runner later calls `variables.OverwriteKey("X", authoritativeValue)` intending that authoritative value to take effect, the call silently rewrites index 0. Every subsequent `Get("X")`/`Value("X")` call still hits index 1 (the untouched duplicate) first during the backward scan and returns it instead of the runner's authoritative value.
- Existing protections don't help here: there is no guard in `OverwriteKey` that de-duplicates or that raises an error/asserts uniqueness before mutating; `Dedup()` exists but is not invoked as part of `OverwriteKey`, so nothing forces the invariant that at most one entry per key remains before/after the call.

### Impact Explanation
Any runner-internal call site that relies on `OverwriteKey` to make a value authoritative (e.g., forcing/overwriting a build-scoped variable) can be defeated whenever a duplicate-key entry with a higher slice index survives the call. Consumers of `Get()`/`Value()` (shell generation, variable expansion via `ExpandValue`, `StringList()` used to build the job's environment) would then observe the stale/duplicate value rather than the runner's intended overwrite — undermining whatever guarantee the overwrite was meant to enforce (e.g., masking, token scoping, or feature-controlled substitution), since the "old" value keeps propagating into the job environment/log output.

### Likelihood Explanation
The precondition — duplicate-key `Variable` entries — is not a contrived theoretical edge case; the runner's own `Dedup()` documentation states GitLab can produce exactly this situation as part of normal CI/CD variable precedence resolution. Whether this is *concretely* exploitable end-to-end depends on the specific call site in `common/build.go` that invokes `OverwriteKey` (only one call site was found), and I was unable to fully inspect that call site's surrounding context (which key/value it overwrites and whether a duplicate can realistically exist for that specific key at that point in the pipeline) within the available tool budget. The structural bug in `OverwriteKey` itself, however, is verifiable directly and reproducible with a self-contained unit test, independent of the specific caller.

### Recommendation
Make `OverwriteKey` consistent with the slice's documented "last occurrence wins" semantics: either (a) iterate backward and overwrite the last matching index (mirroring `value()`), or (b) remove all matching entries and append a single new one (mirroring `Set()`'s de-duplication behavior), so at most one entry for `key` remains after the call and it matches what `Get`/`Value` will return.

### Proof of Concept
```go
func TestOverwriteKey_DuplicateKeyShadowing(t *testing.T) {
    vars := Variables{
        {Key: "X", Value: "attacker-original"},
        {Key: "X", Value: "attacker-duplicate"}, // duplicate, higher index
    }

    vars.OverwriteKey("X", Variable{Key: "X", Value: "authoritative"})

    got := vars.Get("X")
    assert.Equal(t, "authoritative", got, "Get() should return the runner's authoritative overwrite, not the trailing duplicate")
}
```
Running this against the current implementation fails: `Get("X")` returns `"attacker-duplicate"` because `OverwriteKey` only rewrote index 0, while `value()`'s backward scan returns index 1 first.
