### Title
`UpdateTaskRunResult` allows overwriting an already-completed task's result within a still-suspended pipeline run via repeated PATCH to `/v2/resume/:runID` - ([File: core/services/pipeline/orm.go])

### Summary
`PipelineRunsController.Resume` forwards attacker-supplied `taskID`/`Result.Value` to `App.ResumeJobV2` → `runner.ResumeRun` → `orm.UpdateTaskRunResult`, whose SELECT only checks the parent run's aggregate state (`running`/`suspended`), not whether the individual `pipeline_task_runs` row is already finished. As long as the overall run has not fully completed (e.g. it is waiting on a second async task), a client can PATCH the same, already-resolved `taskID` a second time with a different `value`, silently overwriting the previously stored task output and re-triggering pipeline execution with the tampered value.

### Finding Description
`PipelineRunsController.Resume` (`core/web/pipeline_runs_controller.go:133-160`) parses `taskID` from the URL and a `Result` from the request body, then calls: [1](#0-0) 

This is wired unauthenticated at `unauthedv2.PATCH("/resume/:runID", prc.Resume)`: [2](#0-1) 

`ResumeJobV2` forwards directly to `pipelineRunner.ResumeRun`: [3](#0-2) 

`runner.ResumeRun` calls `orm.UpdateTaskRunResult` and, if `start` is true, re-runs the whole pipeline: [4](#0-3) 

The critical gap is in `orm.UpdateTaskRunResult`: the guarding SELECT filters only on `pipeline_runs.state in ('running','suspended')` — it does **not** filter on whether the specific `pipeline_task_runs.id = $1` row already has `finished_at` set (i.e., is itself already resolved). The subsequent `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1` unconditionally overwrites the row regardless of its prior finished state: [5](#0-4) 

Consequently, for a pipeline containing more than one async/suspending task, once task A has been resumed (finished) but the overall run remains `suspended` waiting on task B, an attacker who still knows task A's UUID can PATCH `/v2/resume/{taskA-uuid}` again with a new `value`. Because the run state is still `suspended`, the query matches, `finished_at`/`output` for task A are overwritten, `start` becomes `true` again, and `runner.Run` is re-invoked, re-executing the pipeline DAG (and any downstream task depending on task A's output, e.g. a `median`/`ETHTx` task) using the attacker's second value instead of the originally-resolved one.

Only once the run has fully transitioned to `completed`/`errored` does the guard `pipeline_runs.state in ('running','suspended')` prevent further resumption — at which point `UpdateTaskRunResult` returns `sql.ErrNoRows` and `ResumeJobV2` returns an error. So the isolation/state-binding invariant is enforced at the run level but not at the individual-task level.

### Impact Explanation
For multi-task async pipelines, this allows re-injection of a different `Result.Value` for a task that has already been individually resolved, causing the pipeline to recompute downstream logic (potentially feeding into an `ETHTx` task) with attacker-controlled, stale/duplicate task state. This matches the "unauthorized job run / state corruption of a financial pipeline task" impact class, since it can alter values feeding an on-chain transaction task before the run finalizes.

### Likelihood Explanation
The route `PATCH /v2/resume/:runID` is registered as **fully unauthenticated** (`unauthedv2` group, no session/API-key/role check), so exploitation requires no privilege at all beyond knowledge of a valid, still-in-flight taskID (a UUID) — a lower bar than the "run-role+ session" precondition stated in the question. The condition is real but scoped: it only applies while the parent run remains in `suspended`/`running` state (i.e., another async task is still pending), which limits the exploit window to multi-async-task pipelines with unfinished sibling tasks.

### Recommendation
In `orm.UpdateTaskRunResult`, add a check on the individual task row's own completion state (e.g., `AND pipeline_task_runs.finished_at IS NULL` in the guarding SELECT, or verify `finished_at`/`output`/`error` are NULL before applying the UPDATE) so that a task which has already been resolved cannot be resumed/overwritten a second time, regardless of the parent run's aggregate state.

### Proof of Concept
Go integration test plan (extending `core/services/pipeline/orm_test.go` patterns like `Test_PipelineORM_StoreRun_UpdateTaskRunResult`):
1. Build a pipeline spec with two async/suspending tasks (`ds1`, `ds2`) feeding a `median`/`ETHTx`-consuming node.
2. Run the pipeline via `runner.Run` so it suspends with both `ds1` and `ds2` pending.
3. Call `orm.UpdateTaskRunResult(ctx, ds1_id, Result{Value: "100"})` — assert `start == true`, run transitions to `running`, `ds1.FinishedAt` valid, `ds1.Output == "100"`.
4. Call `orm.UpdateTaskRunResult(ctx, ds1_id, Result{Value: "999"})` again (simulating a second PATCH to `/v2/resume/{ds1_id}`) before `ds2` is resumed.
5. Assert this **should fail** (current behavior: it succeeds) — expected: an error such as "task already finished" and `ds1.Output` unchanged at `"100"`.
6. At the HTTP layer, add a handler test in `pipeline_runs_controller_test.go`: PATCH `/v2/resume/{taskID}` twice with different `{"value": ...}` bodies for the same already-resolved task while the job run is still suspended on a second task; assert the second call returns a 4xx/409 rather than `200 OK`, and that `FindRun` shows the task's original output unchanged.

func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events

		// start the runner again

			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
			}
		}

		return loadAssociations(ctx, tx.ds, []*Run{&run})
	})

	return run, start, err
}
