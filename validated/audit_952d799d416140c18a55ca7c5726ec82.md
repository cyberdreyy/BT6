### Title
Mid-epoch depositor captures a full-epoch interest share via `requestWithdraw` - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`depositDuringEpoch` correctly prorates the interest a mid-epoch depositor is entitled to: shares are minted at a discount so the depositor only owns `amount + proratedInterest` at epoch end, and only the prorated `interest` is added to `expectedEpochInterest`. However, `requestWithdraw` is callable while the epoch is still running and computes withdrawal interest with `_calcInterestWithdrawRequest`, which pays the *full-epoch* tranche interest proportional to NAV (`_amount * totTrancheInterest / _trancheBal`) with no consideration for when the tranche tokens were acquired. A KYC'd attacker who deposits seconds before `epochEndDate` therefore upgrades a ~0-interest position into a receipt paying a full epoch of interest, diluting every honest holder who actually supplied capital for the whole epoch.

### Finding Description
1. Owner enables `isDepositDuringEpochDisabled = false` (a supported configuration; tests exercise it).
2. Epoch starts; honest lenders are in for the full `epochDuration`.
3. At `block.timestamp = epochEndDate - 1` (still `< epochEndDate`, so the guard at line 667 passes), the attacker calls `depositDuringEpoch(amount, AA)`:
   - `interest = _calcInterest(amount) * (1 + buffer) / (epochDuration + buffer)` ≈ only the buffer share.
   - Minted shares are priced so the attacker owns ~`amount + tinyInterest` at epoch end.
   - `expectedEpochInterest` increases by only that tiny prorated amount.
4. In the same or next block (still during the running epoch), the attacker calls `requestWithdraw(0, AA)`:
   - `_underlyings = _trancheToUnderlyings(shares)` ≈ `amount` (price hasn't moved).
   - `_calcInterestWithdrawRequest` returns `amount * totTrancheInterest / trancheNAV` — the full epoch's tranche interest per unit of NAV, identical to what a holder who lent for the entire epoch receives.
   - `pendingWithdrawFees` grows, but the upfront management/performance fee does not cancel the windfall for a reasonably-sized deposit.
   - `interestForOverUnderPerformance += diff` removes the *full-epoch* tvl-based interest from the next epoch's expected interest, although only the prorated amount was ever added — directly draining the interest budget of other holders.

The invariant "interest paid ∝ time capital was supplied" is broken: the receipt created by `requestWithdraw` encodes a full-epoch claim on capital supplied for seconds. At `stopEpoch`, the borrower repays only `expectedEpochInterest` (which counted the attacker's deposit for ~1 second + buffer), but the attacker's queued receipt is sized for the whole epoch, so the payout is funded by honest lenders' share — a direct transfer of yield.

### Impact Explanation
Direct theft/dilution of other tranche holders' epoch yield: the attacker's withdraw receipt over-claims interest that was never earned or funded for their deposit, and the `interestForOverUnderPerformance` bookkeeping subtracts a full-epoch interest amount that was never added, further reducing `expectedEpochInterest` for remaining holders in the next epoch. Loss magnitude ≈ (full-epoch interest on attack amount) − (fees + prorated interest credited), bounded only by the attacker's deposit size and the epoch APR.

### Likelihood Explanation
Requires `isDepositDuringEpochDisabled == false` (an intentionally supported mode), a KYC-passing wallet, and a transaction near `epochEndDate` — both `depositDuringEpoch` and `requestWithdraw` are permissionless for allowed wallets and callable in the same epoch phase. No privileged cooperation needed; sequencing is fully in the attacker's control around the honest manager's `stopEpoch` call.

### Recommendation
In `requestWithdraw`, weight `_calcInterestWithdrawRequest` by the time the caller's position was actually live (e.g., track a per-user deposit timestamp or derive eligible interest from `expectedEpochInterest` attributable to the position), or disallow `requestWithdraw` for positions acquired via `depositDuringEpoch` until the epoch in which they were minted has settled. Alternatively, record at deposit time the prorated interest entitlement and cap withdrawal interest at that amount.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (extends test/foundry/IdleCreditVault.t.sol patterns)
// 10% APR, 365d epoch, depositDuringEpoch enabled
idleCDO.depositAA(1000 * ONE_SCALE);              // honest lender, full epoch
vm.prank(owner); cdoEpoch.setIsAYSActive(false);
_startEpochAndCheckPrices(0);

vm.warp(cdoEpoch.epochEndDate() - 1);             // last second of epoch
vm.prank(owner); cdoEpoch.setIsDepositDuringEpochDisabled(false);

address attacker = makeAddr("attacker");
uint256 amt = 1000 * ONE_SCALE;
deal(defaultUnderlying, attacker, amt);

vm.startPrank(attacker);
IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), amt);
cdoEpoch.depositDuringEpoch(amt, address(AAtranche));
// attacker entitled to ~0 epoch interest (1s + buffer share only)
uint256 claimed = cdoEpoch.requestWithdraw(0, address(AAtranche));
vm.stopPrank();

// `claimed` ≈ amt + FULL epoch interest on amt (e.g. ~amt * 10% * AA share),
// not amt + prorated(1s) interest => honest AA lender is diluted by the same amount.
```

Note: I verified `depositDuringEpoch` proration (lines 691–724) and that `requestWithdraw` (lines 739–791) applies `_calcInterestWithdrawRequest`'s full-epoch interest (lines 856–878) with no deposit-time check. I could not fully trace `stopEpoch`/`claimWithdrawRequest` settlement within the available iterations, so the exact end-state (holder dilution vs. shortfall at claim) should be confirmed when writing the PoC; the over-crediting at request time is confirmed by the code above.
