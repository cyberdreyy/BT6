### Title
External vault liquidity dependence lets any Morpho borrower indefinitely block `stopEpoch`, freezing all pool funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The advisory's bug class is "the system trusts an unauthenticated external resource an attacker can control." The analog: `ProgrammableBorrower` parks all epoch funds in an external ERC4626 vault (e.g., a MetaMorpho vault), and `onStopEpoch` hard-reverts when `vault.withdraw` fails due to insufficient vault liquidity. Any unprivileged user of that ERC4626 vault — explicitly an allowed attacker class — can borrow out all underlying liquidity in the vault's Morpho markets, making `stopEpoch` permanently revert and freezing every LP's funds for as long as liquidity stays borrowed.

### Finding Description
In `onStopEpoch`, the programmable borrower must pull a `shortfall` from the configured external vault: [1](#0-0) 

The `try/catch` around `vault.withdraw` converts an otherwise-covered ERC4626 withdrawal failure into `revert StopEpochVaultLiquidityUnavailable()`. Because this executes inside `IdleCDOEpochVariant.stopEpoch` (owner/manager, honest), the entire epoch-stop transaction reverts. There is no fallback path: `startEpoch`, `stopEpoch`, and LP payouts are all blocked until the external vault's markets regain withdrawable liquidity.

MetaMorpho-style vaults only hold whatever underlying is currently unborrowed in their underlying Morpho markets. An unprivileged attacker (any EOA) can take a maximally-collateralized flash-assisted borrow that drains the idle liquidity of every market the vault allocates to, leaving `vault.maxWithdraw(programmableBorrower) < shortfall`. `withdraw` then reverts, `onStopEpoch` reverts, `stopEpoch` reverts. The attacker sustains the freeze by keeping the borrows open (cost = Morpho borrow APR on the drained amount, partially offset since the pool's own deposited liquidity is what earns it) or by repeatedly re-draining liquidity each time it frees up.

The existing guards do not stop this:

- `emergencyExitVault` calls `vault.redeem`, which hits the same liquidity check and reverts. [2](#0-1) 
- `onDefault`/`settleBorrowerInterest` are only reachable *after* `stopEpoch` succeeds, so the honest owner cannot even default the facility to unlock the emergency path while liquidity is drained.
- The `shortfall > _currentVaultAssets()` early-return only covers share *value*, not market *liquidity* — shares remain worth ≥ shortfall while withdraw reverts.

### Impact Explanation
Temporary freezing of 100% of funds routed through the programmable borrower (epoch principal parked in the vault plus all pending withdraw requests) for the duration of the liquidity drain — directly analogous to the advisory, where the attacker only needs control of an external resource the code depends on, not any privileged role. All tranche holders, pending withdraw receipt holders, and fee/management payouts are blocked; the epoch cannot close, no default can be declared, and no recovery path exists until the attacker releases liquidity.

### Likelihood Explanation
Requires only an ordinary Morpho borrower position against the same markets the configured vault allocates to — no role, no KYC, no governance action. The cost is the borrow interest on drained liquidity; against a vault where the pool is the dominant supplier, the attacker's borrow is substantially funded by the victim's own deposits. The attack is repeatable each epoch since `stopEpoch` must run for every epoch transition.

### Recommendation
Make the stop flow tolerate vault illiquidity: on `withdraw` failure, record the pending shortfall and let `stopEpoch` complete with what is on hand (withdrawing `vault.maxWithdraw`/`maxRedeem` instead of the full `shortfall`), then top up asynchronously via a permissionless `claimVaultShortfall`-style function when liquidity returns. Alternatively, fall through to the default/emergency path when the vault cannot pay, so honest owner/manager can still unwind the facility and LPs are not hostage to external market liquidity.

### Proof of Concept
Foundry fork test against mainnet MetaMorpho vault (mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup):

```solidity
function testStopEpochFrozenWhenVaultLiquidityDrained() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);   // funds parked in MetaMorpho vault

    // Unprivileged attacker drains Morpho market liquidity the vault allocates to.
    // (borrow max LTV against supplied collateral across each enabled market, or
    //  withdraw-while-others-borrow; net effect: vault.idleLiquidity < shortfall)
    _drainMorphoMarketLiquidity(vaultAddress);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Owner cannot escape: emergency redeem hits the same vault liquidity check,
    // and default handling is only reachable past a successful stopEpoch.
    vm.expectRevert();
    programmableBorrower.emergencyExitVault(0);

    // Funds stay frozen until attacker repays / liquidity returns.
}
```

  function emergencyExitVault(uint256 _shares) external nonReentrant returns (uint256 assets) {
    _checkOnlyOwnerOrManager();
    if (_shares == 0) {
      _shares = vault.balanceOf(address(this));
    }
    if (_shares == 0) revert InvalidAmount();
    assets = vault.redeem(_shares, address(this), address(this));
    if (epochAccountingActive) {
      epochWithdrawnFromVault += assets;
    }
