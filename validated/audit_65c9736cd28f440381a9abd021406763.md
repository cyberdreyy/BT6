### Title
`CostTracker::would_fit`'s `WouldExceedAccountDataBlockLimit` check can be bypassed via CPI-invoked `CreateAccount`/`Allocate`, letting real per-block account-data growth exceed `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` unmetered - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only scans the top-level compiled instruction list (`program_instructions_iter`) for System Program `CreateAccount`/`Allocate`/etc. and attributes zero cost to any allocation performed via `invoke`/`invoke_signed` inside a custom program. Because this same top-level-only computation is reused even for the *post-execution* cost reconciliation, the cost tracker's block-wide `allocated_accounts_data_size` counter never reflects real CPI-driven account growth, even though the actual growth is precisely tracked elsewhere in the runtime and enforced only at a per-transaction (not per-block) cap.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` (cost-model/src/cost_model.rs:265-301) iterates `instructions: impl Iterator<Item = (&Pubkey, SVMInstruction)>` and, for each instruction, checks `calculate_account_data_size_on_instruction` (cost-model/src/cost_model.rs:242-261), which only recognizes an allocation if `program_id == &system_program::id()` for that *top-level* instruction: [1](#0-0) 

If the attacker's top-level instruction targets their own deployed SBPF program (not the System Program directly), this function returns `SystemProgramAccountAllocation::None` for that instruction, contributing 0 to `tx_attempted_allocation_size`, regardless of what the program does internally via CPI.

Both the pre-execution estimate (`CostModel::calculate_cost`) and, critically, the *post-execution* reconciliation (`CostModel::calculate_cost_for_executed_transaction`) call `calculate_transaction_cost` with `transaction.program_instructions_iter()` — i.e., always the static top-level instruction list, never the actual executed CPI trace: [2](#0-1) [3](#0-2) 

This `allocated_accounts_data_size` value is what `check_block_cost_limits`/`get_transaction_costs` feed into `CostTracker::try_add` after execution completes: [4](#0-3) 

`CostTracker::would_fit` and `add_transaction_cost` use exactly this field to gate/accumulate the block-wide allocation budget: [5](#0-4) 

Meanwhile, the *actual* account-data growth caused by CPI (or top-level) resizes is tracked correctly and independently in `TransactionAccounts::update_accounts_resize_delta`/`can_data_be_resized`, which operates transaction-wide (not per top-level instruction) and is invoked from every account resize path including CPI: [6](#0-5) 

That real delta is captured as `AccountsDeltas::accounts_resize_delta` in the execution record: [7](#0-6) [8](#0-7) 

and is correctly rolled into the bank's on-chain `accounts_data_size_delta` accounting: [9](#0-8) 

However, this accurate, execution-derived `accounts_resize_delta` is **never fed back into the cost model's `allocated_accounts_data_size`** used by `CostTracker`. The only per-transaction enforcement of real growth is `can_data_be_resized`'s check against `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`, which caps a *single* transaction's real growth but has no bearing on the cost tracker's *block-wide* `allocated_data_size` limit (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA = 100_000_000`, cost-model/src/block_cost_limits.rs:37).

**Exploit flow**: Attacker deploys a program whose single top-level instruction (arbitrary opaque data, not itself calling System Program at the top level) performs `invoke`/`invoke_signed` to System Program's `CreateAccount`/`Allocate`, allocating close to the per-transaction cap (`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`, transaction-context/src/lib.rs). Because `program_id` for the top-level instruction is the attacker's program (not `system_program::id()`), `calculate_allocated_accounts_data_size` records 0 for this transaction. The attacker repeats this across multiple transactions within the same block; `CostTracker::would_fit`'s check against `self.limits.allocated_data_size` never increments meaningfully, so `WouldExceedAccountDataBlockLimit` is never triggered, even though the block's actual accounts-data growth (tracked correctly by the bank via `accounts_resize_delta`) can approach or exceed `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`.

### Impact Explanation
This is a compute/cost metering bypass: the block-level `allocated_data_size` budget (100MB per block) is a scheduling/replay safety limit intended to bound new account-data growth per block. Because the cost model only inspects top-level instructions, an attacker can drive substantially more real accounts-db growth into a single block than the cost tracker believes it has admitted, without any privileged access — only their own deployed program and funded keypair are required. This falls under "compute/cost metering bypass" and creates bank state size divergence pressure and leader/replay resource mismatch, matching the scoped impact described in the prompt.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: deploying an SBPF program that CPIs into `CreateAccount`/`Allocate` is a standard, unrestricted capability (no special permissions, no feature gate, no non-default config). The bypass requires no race condition or timing trick — it is deterministic and repeatable for every transaction whose top-level instruction is not itself a direct System Program call. The only constraint is the existing per-transaction cap (`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`), which does not prevent the block-level miscounting; it only bounds how much a single transaction can under-report, not whether it is under-reported at all.

### Recommendation
Reconcile the cost tracker's `allocated_accounts_data_size` using the actual post-execution `AccountsDeltas::accounts_resize_delta` (already computed correctly and available in `get_transaction_costs`/`check_block_cost_limits`) instead of recomputing it from `transaction.program_instructions_iter()` in `CostModel::calculate_cost_for_executed_transaction`. Concretely, pass the real per-transaction resize delta into `calculate_cost_for_executed_transaction` and use `max(0, accounts_resize_delta) - accounts_uninitialized_size` (or similar) as the `allocated_accounts_data_size` charged against the block limit after execution, rather than re-deriving it solely from the static top-level instruction scan.

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }

    // Returns the highest account cost for all write-lock accounts `TransactionCost` updated
    fn add_transaction_cost(&mut self, tx_cost: &TransactionCost<impl TransactionWithMeta>) -> u64 {
        self.allocated_accounts_data_size += tx_cost.allocated_accounts_data_size();
        self.transaction_count += 1;
        self.transaction_signature_count += tx_cost.num_transaction_signatures();
        self.secp256k1_instruction_signature_count +=
            tx_cost.num_secp256k1_instruction_signatures();
        self.ed25519_instruction_signature_count += tx_cost.num_ed25519_instruction_signatures();
        self.secp256r1_instruction_signature_count +=
            tx_cost.num_secp256r1_instruction_signatures();
        self.add_transaction_execution_cost(tx_cost, tx_cost.sum())
    }

    pub(crate) fn update_accounts_resize_delta(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        let accounts_resize_delta = self.resize_delta.get();
        self.resize_delta.set(
            accounts_resize_delta.saturating_add((new_len as i64).saturating_sub(old_len as i64)),
        );
        Ok(())
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
