### Title
Miner-side StackerDB listener double-counts a single signer's weight into both the accept and reject tallies for the same block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener::run` loop, which aggregates signer `BlockResponse` messages for the block-proposal coordinator, guards duplicate `Accepted` messages against `gathered_signatures` and duplicate `Rejected` messages against `responded_signers`, but never checks whether the *same* signer slot has already contributed weight to the *opposite* tally. A single signer (one StackerDB slot) can therefore have its weight counted in `total_weight_rejected` and, moments later, again in `total_weight_approved` for the same `signer_signature_hash`, breaking the invariant that a signer's weight should count toward at most one side of the 70%/30% threshold decision.

### Finding Description
In the `Accepted` branch, the only de-duplication check is against `gathered_signatures`: [1](#0-0) 
This means it never consults `responded_signers`, which is the set the `Rejected` branch uses to decide whether to add weight: [2](#0-1) 

Sequence:
1. A signer's slot sends a valid `Rejected` response for block B. `responded_signers.insert(slot_id)` returns `true` (first time) → `total_weight_rejected += weight`.
2. The same signer's slot later sends a valid `Accepted` response (a signature) for the same block B — e.g. after re-evaluating, or a byzantine/gossip-visible signer intentionally sending both. `gathered_signatures` does not yet contain `slot_id`, so the check `!block.gathered_signatures.contains_key(&slot_id)` passes → `total_weight_approved += weight` as well.
3. Both tallies now include this signer's weight simultaneously, even though only one message can reflect the signer's true, current opinion. This violates the equality the threshold logic depends on — that `total_weight_approved` and `total_weight_rejected` reflect disjoint, non-overlapping signer sets — and lets a single signer's weight satisfy both sides of the check in `wait_for_block_signatures`/coordinator logic that reads these fields: [3](#0-2) 

This is the exact bug class the reference NATS advisory illustrates: a value is bucketed into the wrong classification path (there, a password misclassified as a non-authenticating JWT; here, a signer's later message is folded into a second tally instead of superseding/being reconciled with the first), and that misclassification is externally observable through the aggregation path that other logic trusts. The project has already fixed the analogous defect on the *signer* side — the CHANGELOG explicitly documents this exact class as previously broken and fixed on the peer-tally path: [4](#0-3) 
That entry ("Do not count both a block acceptance and a block rejection for the same signer/block") describes remediation of the identical logic error, but the fix is not mirrored in the miner-side `stackerdb_listener.rs` aggregation loop, which independently re-implements the same accept/reject tally without the cross-set guard.

### Impact Explanation
This lets one signer's weight (reachable via a single compromised/misbehaving signer's StackerDB writes, i.e. "one slot plus gossip", no majority required) simultaneously inflate both `total_weight_approved` and `total_weight_rejected` for the same block as observed by the miner coordinator. Because the coordinator's rejection check is evaluated first in `wait_for_block_signatures`, a single flip-flopping signer can force a spuriously-early `SignersRejected` outcome, or — depending on timing relative to other signers' real weight — cause the approved/rejected thresholds to be satisfied using overlapping rather than disjoint weight, undermining the miner's ability to correctly determine that 70% *distinct* weight actually accepted (or that a genuine blocking-minority rejected) a block. This is a liveness/decision-integrity wedge on the node-side aggregation rather than a signature forgery, since each individual signer's actual signing decision (in `stacks-signer/src/v0/signer.rs` / `signerdb.rs`) is unaffected — the flaw is isolated to the miner's bookkeeping of who has said what.

### Likelihood Explanation
High reachability: any single registered signer (or an attacker who compromises/controls one signer's key or simply sends conflicting StackerDB chunks under gossip, since chunk authenticity is per-signer-signed but the coordinator does not require monotonic message ordering or exclusivity) can trigger this by publishing a `Rejected` chunk followed by an `Accepted` chunk (or vice versa, though the `Accepted`→`Rejected` order is guarded via `responded_signers`, the `Rejected`→`Accepted` order is not). No majority or additional signer keys are required.

### Recommendation
In the `Accepted` branch of `stackerdb_listener.rs`, check `responded_signers` in addition to `gathered_signatures` before adding to `total_weight_approved`, mirroring the same-address exclusivity fix already applied on the signer-side tally (`stacks-signer/CHANGELOG.md` 3.2.0.0.0.0 entry). Concretely, track a per-slot "last decision" (accept vs reject) and only allow the weight to move from one tally to the other (subtracting from the old tally, adding to the new) rather than allowing both to increase independently, so that at all times `total_weight_approved + total_weight_rejected` cannot exceed the sum of weights of signers who have actually responded.

### Proof of Concept
1. Start a node with the miner-side `StackerDBListener` running for a proposed block B (as in `wait_for_block_signatures`).
2. As signer slot `S` (weight `w`), publish a StackerDB chunk containing `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for B. Observe `block.total_weight_rejected` increases by `w` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-520`).
3. Immediately after, as the same slot `S`, publish a chunk containing `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same B with a validly recoverable signature. Because `gathered_signatures` does not yet contain slot `S`, `block.total_weight_approved` also increases by `w` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-465`).
4. Confirm via logs/instrumentation that `total_weight_approved + total_weight_rejected` now exceeds the weight of signers who have distinct, final positions on B — demonstrating the tallies are no longer mutually exclusive per signer.
