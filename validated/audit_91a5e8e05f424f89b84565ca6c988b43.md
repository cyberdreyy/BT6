### Title
BridgeTypesController.Show (and Index/Update/Destroy) leak the bridge's `OutgoingToken` to any authenticated caller, including view-role users - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Show` renders bridge details via `presenters.NewBridgeResource`, which unconditionally copies `OutgoingToken` from the stored `bridges.BridgeType` into the JSON response. Unlike `IncomingToken`, which is intentionally only set once (in-memory) during `Create` and never populated from the persisted model, `OutgoingToken` has no redaction and is returned on every `Show`/`Index`/`Update`/`Destroy` call.

### Finding Description
`BridgeTypesController.Show` looks up the bridge by name and returns `presenters.NewBridgeResource(bt)`: [1](#0-0) 

`NewBridgeResource` builds the JSON-serializable resource from the persisted `bridges.BridgeType`, explicitly copying `OutgoingToken` with no redaction, while `IncomingToken` (tagged `omitempty`) is left as its zero value because it is never set from the DB model — it is only manually assigned in `Create` from the freshly generated plaintext token: [2](#0-1) [3](#0-2) 

The struct tag `json:"outgoingToken"` (no `omitempty`, no masking) confirms `OutgoingToken` is always serialized: [4](#0-3) 

Thus the "redact after creation" design comment (`// The IncomingToken is only provided when creating a Bridge`) only applies to `IncomingToken`; `OutgoingToken` — the credential the node sends to the external adapter to authenticate itself/verify the callback — is exposed on every read of the bridge resource (`Show`, `Index`, `Update`, `Destroy`), to any role permitted to hit those routes.

### Impact Explanation
Any authenticated user who can reach `GET /v2/bridge_types/:BridgeName` (or the paginated `Index`) can read the `OutgoingToken` for any bridge configured on the node. This is a credential/secret disclosure: `OutgoingToken` is a bridge authentication secret, and its exposure to a lower-privileged (view/run-role) caller than the bridge's creator (edit/admin) violates secret confinement and could allow the caller to impersonate the node to the external adapter or otherwise abuse bridge-adapter trust.

### Likelihood Explanation
Precondition is simply a valid, low-privilege authenticated session (view or run role) able to call the bridge_types GET endpoints — no special exploitation is needed since this is the endpoint's normal documented behavior returning full JSON including `outgoingToken`. It is trivially and repeatably reproducible: create a bridge as admin, then GET it as a view-role session — the response body will contain `outgoingToken` populated with the real value every time.

### Recommendation
Redact `OutgoingToken` in `presenters.NewBridgeResource` for read paths (`Show`/`Index`) the same way `IncomingToken` is handled — omit it from the persisted-model resource entirely, or mask it, and only surface it (if ever needed) through a one-time, explicitly-scoped response tied to token creation/rotation, gated by an appropriate write-role check.

### Proof of Concept
Go unit test plan (extends `core/web/bridge_types_controller_test.go`):
1. Set up test application, create a bridge via `POST /v2/bridge_types` as an authenticated admin/edit session; capture the returned `incomingToken`.
2. Perform `GET /v2/bridge_types/<name>` using a view-role (or run-role) authenticated session.
3. Assert HTTP 200 and unmarshal JSON body into `presenters.BridgeResource`.
4. Assert `resp.IncomingToken == ""` (redaction holds for incoming token) but observe `resp.OutgoingToken != "" && resp.OutgoingToken == storedBridge.OutgoingToken` (leak confirmed) — the assertion `resp.OutgoingToken == ""` FAILS, proving the vulnerability.
5. Repeat against `GET /v2/bridge_types` (Index) and `PATCH`/`DELETE` responses to show the same leak across all read paths.
