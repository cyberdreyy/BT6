### Title
Unauthenticated `replace`/`clean` exports allow any account to overwrite migration state - (`state-manipulation/src/lib.rs`)

### Summary
The `replace` and `clean` functions exported by this contract write/remove arbitrary raw storage keys with no caller check at all. Since this contract is meant to be deployed temporarily on an account undergoing a migration, any unprivileged account can call `replace` after the operator deploys it and, by acting in the same or a later block, overwrite the operator's intended state with attacker-chosen bytes before the account is redeployed to the "real" contract code.

### Finding Description
The implicit binding this design relies on is: `caller_of(replace) == account_owner_performing_migration`, i.e. only the principal who deployed the state-manipulation helper (the account's full-access-key holder) can write into that account's storage while the helper is live. The actual code never checks this:

```rust
#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    ...
    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(&base64::decode(key).unwrap(), &base64::decode(value).unwrap());
    }
}

    ...

There is no `predecessor_account_id()` comparison against `current_account_id()`, no owner/key gate, and no `assert_self()`-style guard anywhere in the file. Any account, including a fully unprivileged attacker, can call `replace(entries)` or `clean(keys)` on the deployed account with the same rights as the operator.

Exploit flow: the operator deploys this helper WASM to an account that already holds another contract's state (e.g. a lockup or staking pool) in order to fix/migrate specific keys, then calls `replace` with the intended fixed bytes. Because the method is public and unauthenticated, an attacker observing the mempool/block can send their own `replace` call with different (malicious) key/value pairs targeting the same underlying storage keys (e.g. the borsh-serialized `STATE` key encoding `owner_account_id`, `staking_pool_id`, vesting/lockup parameters, etc.). Whichever call is applied last in the block determines the final on-chain state; since NEAR orders receipts and there is no versioning/nonce/ownership check, the attacker can simply race or immediately follow the operator's transaction to have their entries be the ones present when the account is subsequently redeployed to the production contract code. This directly breaks the "only one principal can drive migration" invariant and lets the attacker inject state (e.g. an owner_account_id equal to themselves, altered `vesting_information`, or altered stake/lockup amounts) that the redeployed contract will trust.

No existing guard in this file (`assert_owner`, `assert_self`, `is_promise_success`, etc.) is present to prevent this — the file simply has none of these checks.

### Impact Explanation
If the attacker's overwritten state is later relied upon by the account's production contract (lockup, staking pool, multisig, etc.), the attacker can end up as the recognized owner, unlock/withdraw funds early, or otherwise gain control of the account's held NEAR — matching the Critical impact category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" / "direct manipulation of contract state, enabling theft of the account's funds." This is repeatable on every migration that uses this helper contract and affects any account owner who deploys it, since the exposure window exists for as long as the helper contract remains deployed and reachable via RPC.

### Likelihood Explanation
The attacker needs no special privilege: they only need to know (a) which account is running this helper (visible from the deployed WASM/tx history) and (b) roughly which raw storage keys correspond to state fields worth corrupting (derivable from the target contract's Borsh/serialization layout, which is public source). The attack cost is a single low-gas function call transaction, and it can be attempted on every future use of this helper. Given the contract literally has zero access control, exploitation is trivial and highly likely if this helper is ever deployed against a live account without being immediately followed, in the *same* transaction (not merely the same block), by removal/redeployment.

### Recommendation
Add a `predecessor_account_id() == current_account_id()` check (i.e. require the caller to be the account itself, meaning only a signed transaction using that account's full-access key can invoke `replace`/`clean`), or better, ensure the deploy + `replace` + redeploy sequence is always executed as a single atomic batched transaction (multiple actions in one transaction) so no other transaction can be interleaved, and never leave this helper contract deployed and reachable across multiple blocks/transactions.

### Proof of Concept
```rust
// near-workspaces test, state-manipulation/src/lib.rs tests module
#[tokio::test]
async fn attacker_can_overwrite_operator_state() -> anyhow::Result<()> {
    let worker = workspaces::sandbox().await?;
    let wasm = fs::read("res/state_manipulation.wasm").await?;
    let contract = worker.dev_deploy(&wasm).await?; // operator deploys helper

    let attacker = worker.dev_create_account().await?; // unprivileged account

    let key = base64::encode(b"STATE");
    let operator_value = base64::encode(b"legit-owner-bytes");
    let attacker_value = base64::encode(b"attacker-owner-bytes");

    // Operator's migration write
    contract.call(&worker, "replace")
        .args_json(&serde_json::json!({ "entries": [[key.clone(), operator_value]] }))?
        .transact().await?;

    // Attacker calls replace on the SAME contract with no authorization at all
    attacker.call(&worker, contract.id(), "replace")
        .args_json(&serde_json::json!({ "entries": [[key.clone(), attacker_value.clone()]] }))?
        .transact().await?;

    let state_items = contract.view_state(&worker, None).await?;
    // Binding under test: final STATE bytes should equal operator_value if only the
    // operator can drive migration. It does not — attacker's value wins.
    assert_eq!(
        state_items.get(b"STATE".as_ref()).unwrap(),
        &base64::decode(attacker_value).unwrap()
    );
    Ok(())
}
```
This demonstrates that `replace` accepts writes from any predecessor, proving the "only one principal can drive migration" invariant does not hold. [1](#0-0)
