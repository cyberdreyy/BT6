## Analysis

I traced the "loss-of-reward-after-unauthorized-state-change" bug class into the Gloas builder-payment mechanism, which is the closest analog: a Gwei-denominated payment obligation (`BuilderPendingPayment`) that is supposed to be gated by a committee-weight quorum before it is converted into an actual withdrawal, but is instead settled unconditionally through a second, ungated code path.

### Title
Builder payments settle without PTC quorum check, letting one proposer pay a builder for an unattested payload - (File: `specs/gloas/beacon-chain.md`)

### Summary
`BuilderPendingPayment` entries are only supposed to convert into a real `BuilderPendingWithdrawal` (i.e. Gwei actually owed and eventually paid to the builder's `fee_recipient`) once enough attesting weight (`payment.weight >= get_builder_payment_quorum_threshold(state)`) confirms the payload was seen as available. This gate is implemented in `process_builder_pending_payments`, run once per epoch. However, `settle_builder_payment`, invoked from `apply_parent_execution_payload` on the very next block after a "full" parent, moves the same payment into `builder_pending_withdrawals` with **no weight check at all**, and does so before any attestation for that parent slot could possibly have updated `payment.weight` (since `process_parent_execution_payload` runs before `process_operations` in `process_block`). This lets a single participant — the very next block's proposer — decide unilaterally that the builder gets paid, bypassing the committee-based quorum entirely.

### Finding Description
`settle_builder_payment` unconditionally appends the withdrawal as long as the recorded amount is non-zero, ignoring `payment.weight`: [1](#0-0) 

Compare this to the epoch-boundary settlement path, which explicitly requires quorum weight before creating the withdrawal: [2](#0-1) 

`settle_builder_payment` is invoked from `apply_parent_execution_payload`, called by `process_parent_execution_payload` at the very next slot after the parent, purely based on whether the current proposer chose to build atop the parent as "full" (`bid.parent_block_hash == parent_bid.block_hash`): [3](#0-2) [4](#0-3) 

Critically, in `process_block`, `process_parent_execution_payload` runs **before** `process_operations` (which processes attestations that increment `payment.weight` via the PTC-vote-driven logic): [5](#0-4) 

The weight-increment logic itself only fires when an attestation votes on the parent slot with the payload-present bit set: [6](#0-5) 

Because `settle_builder_payment` for slot N's payment executes in block N+1 before that same block's `process_operations` step has any chance to raise `payment.weight` above zero, the block-processing path effectively always settles the payment with an unmet (typically zero) quorum weight. This is confirmed by the repo's own test, which sets `payment.weight == 0` and still observes a withdrawal created immediately upon `apply_parent_execution_payload`: [7](#0-6) 

Once `settle_builder_payment` clears the payment slot (`BuilderPendingPayment.empty()`), the later epoch-boundary quorum check in `process_builder_pending_payments` has nothing left to check — the weight-gated code path becomes dead for every full parent block, and the entire PTC-based availability quorum is bypassed by the unilateral decision of a single proposer (the very next slot's proposer, who alone determines whether the parent is treated as "full").

### Impact Explanation
This breaks the intended equality: *"a builder is only paid once the PTC/attesters reach quorum confirming the payload was available."* Instead, a single participant — the proposer of the very next slot — can single-handedly commit a Gwei payment to a builder regardless of whether the network's committee ever attested the payload as available. This matches the "High" impact category: a builder payment misdirected/escaped its intended committee-gated authorization, and a duty/outcome (payment settlement) is steerable by one participant without majority-weight backing.

### Likelihood Explanation
This triggers on every ordinary block where the immediately-following proposer builds atop the parent as "full" (the normal, expected case), not merely an edge case — it is a systemic ordering issue: `apply_parent_execution_payload` (and its call to `settle_builder_payment`) is placed before `process_operations` in `process_block`, so the ungated settlement path is the one used in virtually all block sequences, structurally starving the intended quorum-based path.

### Recommendation
Either: (1) move `process_operations`/attestation processing (or at least the weight-increment logic) before `apply_parent_execution_payload` within `process_block`, and have `settle_builder_payment` check `payment.weight >= get_builder_payment_quorum_threshold(state)` before pushing to `builder_pending_withdrawals`; or (2) remove the unconditional block-level settlement entirely and rely solely on the epoch-boundary `process_builder_pending_payments` quorum check, using the block-level call only to *evict* payments (as already done for `parent_bid.value > 0` in the "older than previous epoch" branch) rather than to unconditionally pay them.

### Proof of Concept
Using the existing spec test harness as a template: in `test_process_parent_execution_payload.py`, `_commit_parent_requests` sets `state.builder_pending_payments[payment_idx].weight = Gwei(0)` [8](#0-7) , and `test_process_parent_execution_payload__full_parent_settles_builder_payment` then processes exactly one child block and observes `builder_pending_withdrawals` gain an entry for the builder's payment despite weight remaining `0` throughout [7](#0-6) . This demonstrates that a builder is paid with zero PTC-attested weight, purely because the next proposer chose to treat the parent as full — no majority-weight attestation confirming payload availability is required.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

```markdown
def apply_parent_execution_payload(
    state: BeaconState,
    requests: ExecutionRequests,
) -> None:
    parent_bid = state.latest_execution_payload_bid
    parent_slot = state.latest_block_header.slot
    parent_epoch = compute_epoch_at_slot(parent_slot)

    assert len(requests.withdrawals) <= MAX_WITHDRAWAL_REQUESTS_PER_PAYLOAD
    assert len(requests.consolidations) <= MAX_CONSOLIDATION_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_deposits) <= MAX_BUILDER_DEPOSIT_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_exits) <= MAX_BUILDER_EXIT_REQUESTS_PER_PAYLOAD

    # Process execution requests from parent's payload. The execution
    # requests are processed at state.slot (child's slot), not the parent's slot.
    def for_ops(operations: Sequence[Any], fn: Callable[[BeaconState, Any], None]) -> None:
        for operation in operations:
            fn(state, operation)

    for_ops(requests.deposits, process_deposit_request)
    for_ops(requests.withdrawals, process_withdrawal_request)
    for_ops(requests.consolidations, process_consolidation_request)
    for_ops(requests.builder_deposits, process_builder_deposit_request)
    for_ops(requests.builder_exits, process_builder_exit_request)

    # Settle the builder payment
    if parent_epoch == get_current_epoch(state):
        payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_epoch == get_previous_epoch(state):
        payment_index = parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_bid.value > 0:
        # Parent is older than the previous epoch, its payment entry has been
        # evicted from builder_pending_payments. Append the withdrawal directly.
        state.builder_pending_withdrawals.append(
            BuilderPendingWithdrawal(
                fee_recipient=parent_bid.fee_recipient,
                amount=parent_bid.value,
                builder_index=parent_bid.builder_index,
            )
        )

    # Update parent payload availability and latest block hash
    state.execution_payload_availability[parent_slot % SLOTS_PER_HISTORICAL_ROOT] = Boolean(True)
    state.latest_block_hash = parent_bid.block_hash
```

def process_parent_execution_payload(state: BeaconState, block: BeaconBlock) -> None:
    bid = block.body.signed_execution_payload_bid.message
    parent_bid = state.latest_execution_payload_bid
    requests = block.body.parent_execution_requests

    if bid.parent_block_hash != parent_bid.block_hash:
        # Parent was EMPTY -- no execution requests expected
        assert requests == ExecutionRequests.empty()
        return

    # Parent was FULL -- verify the bid commitment and apply the payload
    assert hash_tree_root(requests) == parent_bid.execution_requests_root
    apply_parent_execution_payload(state, requests)

```python
@with_gloas_and_later
@spec_state_test
def test_process_parent_execution_payload__full_parent_settles_builder_payment(spec, state):
    """
    Test that when the parent block was full with a non-zero builder payment,
    the payment is settled into ``builder_pending_withdrawals`` and the pending
    payments slot is cleared.
    """
    builder_index = 0
    value = spec.Gwei(50_000_000)
    fee_recipient = spec.ExecutionAddress(b"\xab" * 20)

    # Set the fee recipient before committing the parent requests so the pending
    # payment uses the same address.
    state.latest_execution_payload_bid.fee_recipient = fee_recipient
    _commit_parent_requests(
        spec, state, spec.ExecutionRequests(), value=value, builder_index=builder_index
    )
    parent_bid = state.latest_execution_payload_bid.copy()
    payment_idx = spec.SLOTS_PER_EPOCH + parent_bid.slot % spec.SLOTS_PER_EPOCH

    block = build_empty_block_for_next_slot(spec, state)
    pre_pending_withdrawals_len = len(state.builder_pending_withdrawals)

    spec.process_slots(state, block.slot)
    yield from run_parent_execution_payload_processing(spec, state, block)

    # A new pending withdrawal was added for the builder payment
    assert len(state.builder_pending_withdrawals) == pre_pending_withdrawals_len + 1
    new_withdrawal = state.builder_pending_withdrawals[pre_pending_withdrawals_len]
    assert new_withdrawal.amount == value
    assert new_withdrawal.builder_index == builder_index
    assert new_withdrawal.fee_recipient == fee_recipient

    # The pending payment slot was cleared
    assert state.builder_pending_payments[payment_idx] == spec.BuilderPendingPayment()
```
