### Title
Token-balance metadata omits legitimate SPL token accounts referenced as an instruction's program-id, causing incorrect `preTokenBalances`/`postTokenBalances` in transaction status - (File: svm/src/transaction_balances.rs)

### Summary
`BalanceCollector::collect_balances` in [1](#0-0)  deliberately skips computing token-balance info for any account key that `transaction.is_invoked(index)` reports true for, even when that account is a fully valid, initialized SPL token account owned by a known token program. This is analogous to the Radiant `Compounder.claimCompound` bug: a loop over "reward"/"account" candidates special-cases one condition (RDNT / "invoked") and unconditionally skips it, silently dropping data that a consumer (the compounder / RPC client) expects to see, based on an assumption that the special-cased entry can never actually be relevant in practice.

### Finding Description
`collect_balances` builds both native lamport balances and token balances for every account key referenced by a transaction, for use in `TransactionStatusMeta.pre_token_balances` / `post_token_balances` returned by JSON-RPC methods such as `getTransaction`/`getConfirmedTransaction` and used for `preBalances`/`postBalances` fee/analytics.

The loop: [2](#0-1) 

only records `SvmTokenInfo` for a keyed account when:
```
has_token_program && !transaction.is_invoked(index) && !is_known_spl_token_id(key) && is_known_spl_token_id(account.owner())
```

`is_invoked(index)` returns `true` whenever the account key at that index is referenced as the `program_id` of *any* top-level instruction in the transaction message, regardless of whether that instruction actually succeeds — see the trait wiring in [3](#0-2) . A transaction author fully controls which account indices are marked as "invoked" simply by placing any pubkey as the `program_id_index` of an instruction in the message — there is no requirement that the account actually be executable, and this check happens purely at the message-compilation level.

Because the exclusion is keyed only on `is_invoked`, and not on whether the account is actually executable/a program, a user can construct a transaction that:
1. Includes a legitimate, owned SPL Token (or Token-2022) account among its account keys with a real balance.
2. References that same account's pubkey as the `program_id` of one of the transaction's instructions (this instruction will fail, e.g. with `IncorrectProgramId`/`UnsupportedProgramId`, since the account isn't executable).
3. Submits the transaction. The transaction still lands on-chain (as a failed transaction, fee still charged, `TransactionStatusMeta` still generated) because `collect_pre_balances`/`collect_post_balances` are invoked unconditionally as part of balance collection for the batch (both for successful and failed transactions), independent of whether `process_message` errors out.

For that transaction, the token account's balance is silently dropped from `pre_token_balances`/`post_token_balances` in the resulting `TransactionStatusMeta`, even though the account and its token balance are completely legitimate and its lamport balance is still correctly recorded in `pre_balances`/`post_balances`. This mirrors the RDNT case: a hard-coded exclusion condition ("if RDNT" / "if invoked") is applied to a general-purpose per-item loop and drops data, based on an implicit assumption ("invoked accounts are never real user-owned token accounts we care about") that a normal, permissionless user can trivially violate by constructing an appropriately-shaped transaction.

### Impact Explanation
This produces wrong/incomplete account data being returned via a JSON-RPC query (`getTransaction`, `getConfirmedTransaction`, `getBlock` with transaction details) for any transaction where an attacker/user references a real token account as an instruction program-id. Downstream consumers (indexers, wallets, exchanges auditing balance deltas) that rely on `pre_token_balances`/`post_token_balances` to reconcile token movements will see a token account silently omitted, even though its native lamport balance is reported. This is a "wrong account data returned" class of bug reachable from a single, permissionless, ordinary transaction — no validator/operator role required.

### Likelihood Explanation
Any user can trivially craft such a transaction (place any account key, including one they know holds an SPL token balance, as the `program_id_index` of one instruction). No special privileges, timing, or state are required; this is entirely under the control of the transaction author, with the deficiency only exposed for that same transaction's own metadata (the omitted account is one of the tx's own account_keys). Because this only affects a single transaction's own reported metadata, it is a low-severity but concretely reachable metadata-correctness bug.

### Recommendation
Do not rely on `is_invoked` alone to decide whether to compute token-balance metadata for an account key. Instead, gate the exclusion on whether the account is actually executable (or otherwise verify the account state actually unpacked from `generic_token::Account::unpack`/`Mint::unpack` before excluding it), so that legitimately-owned SPL token accounts are never dropped from `pre_token_balances`/`post_token_balances` purely because they were also referenced as a program id in the same message.

### Proof of Concept
1. Create an SPL Token (or Token-2022) account `T` owned by `owner`, with a non-zero balance, via a normal `InitializeAccount`+mint-to flow.
2. Construct a transaction with two instructions:
   - Instruction A: a normal instruction (e.g. a `System::Transfer`) so the transaction is otherwise well-formed.
   - Instruction B: an instruction whose `program_id` field is set to `T`'s pubkey (any account list/data, since it will fail during execution because `T` is not executable).
3. Submit the transaction; it will fail at instruction B (`IncorrectProgramId`) but the transaction still lands on-chain with `TransactionStatusMeta` populated (fee charged, `pre_balances`/`post_balances` include `T`'s lamports).
4. Query `getTransaction` for this signature and inspect `meta.preTokenBalances`/`meta.postTokenBalances`: `T`'s token balance entry will be missing, verifiable by tracing that `collect_balances` ( [4](#0-3) ) evaluates `transaction.is_invoked(index)` as `true` for `T`'s account index and skips calling `SvmTokenInfo::unpack_token_account` for it.

```rust
    fn collect_balances<CB: TransactionProcessingCallback>(
        &mut self,
        account_loader: &mut AccountLoader<CB>,
        transaction: &impl SVMTransaction,
    ) -> (TxNativeBalances, TxTokenBalances) {
        let mut native_balances = Vec::with_capacity(transaction.account_keys().len());
        let mut token_balances = vec![];

        let has_token_program = transaction.account_keys().iter().any(is_known_spl_token_id);

        for (index, key) in transaction.account_keys().iter().enumerate() {
            let Some(account) = account_loader.load_account(key) else {
                native_balances.push(0);
                continue;
            };

            native_balances.push(account.lamports());

            if has_token_program
                && !transaction.is_invoked(index)
                && !is_known_spl_token_id(key)
                && is_known_spl_token_id(account.owner())
                && let Some(token_info) =
                    SvmTokenInfo::unpack_token_account(account_loader, &account, index)
            {
                token_balances.push(token_info);
            }
        }

        (native_balances, token_balances)
    }
```
