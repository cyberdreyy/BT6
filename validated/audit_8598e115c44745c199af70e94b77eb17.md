### Title
Rate limiter and deleverage-equity accounting in `kamino_withdraw` use raw collateral-token amounts instead of the actual liquidity-token value, causing under/over-counted outflow tracking - ([File: programs/marginfi/src/instructions/kamino/withdraw.rs])

### Summary
`kamino_withdraw` feeds `rate_limit_amount` (a raw Kamino collateral-share amount, always denominated in Kamino's fixed collateral decimals) directly into `record_withdrawal_outflow` together with a price fetched for the bank's liquidity mint, without first converting collateral shares into liquidity-token-equivalent units. The real liquidity value of the withdrawal (`expected_liquidity_amount`, `received`) is only computed later via `collateral_to_liquidity`, after the rate-limit and deleverage-equity checks have already run.

### Finding Description
In `kamino_withdraw` [1](#0-0) , the withdrawal size is first determined in collateral-token units (`collateral_amount`/`share_amount`), and — for `withdraw_all` — `rate_limit_amount` is simply set to `collateral_amount`. This value, along with a price fetched via `fetch_asset_price_for_bank_low_bias` (a price for the bank's liquidity mint), is passed straight into `record_withdrawal_outflow` as both the "amount" arguments.

The actual liquidity-token amount that will be transferred to the user is only computed afterward, via `ctx.accounts.integration_acc_1.load()?.collateral_to_liquidity(collateral_amount)?` [2](#0-1) . `collateral_to_liquidity` applies the reserve's true collateral:liquidity exchange rate, which drifts away from 1:1 as interest accrues on the reserve [3](#0-2) . Kamino's `deposited_amount` field is explicitly documented as being in collateral token units, "Always 6 decimals," and distinct from the liquidity token, needing `collateral_to_liquidity` to convert back [4](#0-3) .

The same unconverted-amount pattern also affects the deleverage withdrawal-limit check: `withdrawn_equity` is computed via `calc_value(I80F48::from_num(collateral_amount), price, bank.get_balance_decimals(), None)`, directly treating the raw collateral amount as if it were already denominated in the bank's liquidity decimals [5](#0-4) . If the bank's liquidity-mint decimals differ from Kamino's fixed collateral decimals (6), or if the collateral:liquidity exchange rate has drifted from 1:1 due to accrued yield, both the rate limiter and the deleverage-equity cap will process an amount that is systematically smaller or larger than the true USD value actually leaving the vault.

Because `collateral_to_liquidity` and interest accrual normally make 1 collateral share redeemable for more liquidity than a naive 1:1 assumption (interest accrues to `available_amount`/`total_liq` while `mint_total_supply` collateral shares stay fixed until minted/burned), a withdrawal against a reserve with meaningfully appreciated collateral shares will register a smaller "amount" with the rate limiter/deleverage cap than the real liquidity value withdrawn.

### Impact Explanation
This breaks the PRICE_CONSERVATISM invariant that the permissionless rate limiter and deleverage-outflow cap must track true economic outflow, not raw share units. An attacker (or even an ordinary user) using `withdraw_all=true` against a reserve whose collateral shares have accrued value can extract more real USD-value liquidity per rate-limit window than the group's rate limiter is configured to permit, and can distort the deleverage withdrawal-limit accounting used during receivership/order-execution flows. This is a durable rate-limiter/deleverage-cap bypass with financial impact, not a pure liquidity or oracle-data issue.

### Likelihood Explanation
Preconditions are realistic and permissionless: `group.rate_limiter.is_enabled()` need only be true, and the attacker needs a Kamino collateral position that has accrued meaningful interest (any position held for some time in a reserve with active borrow demand). No privileged accounts, oracle manipulation, or admin action are required — the caller only needs to invoke the public `kamino_withdraw` instruction with `WITHDRAW_ALL_FLAG` repeatedly. The magnitude of the discrepancy scales with how far the reserve's exchange rate has drifted from 1:1 and with decimal differences between the collateral representation and the bank's liquidity mint decimals.

### Recommendation
Compute the real liquidity-token-equivalent amount via `collateral_to_liquidity` (or an equivalent Kamino exchange-rate conversion) before calling `record_withdrawal_outflow` and before computing `withdrawn_equity`, and use that liquidity-denominated value (matching the price's denomination and bank's liquidity decimals) for both the rate limiter and the deleverage withdrawal-limit check, rather than the raw collateral share amount.

### Proof of Concept
Rust integration/fuzz test plan:
1. Set up a Kamino reserve (`MinimalReserve`) with `available_amount`/`borrowed_amount_sf` inflated relative to `mint_total_supply`, so that `collateral_to_liquidity(1_000_000)` returns a liquidity amount noticeably larger than `1_000_000` (simulating accrued interest, exchange rate > 1).
2. Create a marginfi group with `rate_limiter` enabled with a known cap (e.g., max outflow value X per window).
3. Have a test user with a Kamino obligation deposit corresponding to a collateral amount C that, when converted via `collateral_to_liquidity`, yields real liquidity value V > X (i.e., V exceeds the rate limiter cap) while C * price (naively treated as liquidity decimals) stays under X.
4. Call `kamino_withdraw` with `flags = WITHDRAW_ALL_FLAG`.
5. Assert that the transaction succeeds (rate limiter does not block it) despite the real liquidity value transferred (`received` from `cpi_transfer_obligation_owner_to_destination`) exceeding the configured rate-limit cap X — demonstrating that `record_withdrawal_outflow` under-tracked true outflow.
6. Repeat withdrawals near the boundary across multiple calls to show cumulative real-value outflow durably exceeds the intended window cap.
