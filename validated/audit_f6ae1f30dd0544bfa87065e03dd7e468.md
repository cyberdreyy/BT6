### Title
APR0 withdrawal restriction bypassed by transferring tranche tokens to a fresh address - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In `IdleCreditVault`, depositors whose funds enter the pool under APR0 (no epoch interest) are tracked per address via the `apr0Users` accounting so that their later `requestWithdraw`/`claimWithdrawRequest` does not accrue normal epoch interest. The flag is bound to the depositing address, but AA/BB tranche tokens (`IdleCDOTranche`) are freely transferable ERC20s. The strategy deliberately locks receipt-token transfers (`_transfer` reverts unless `msg.sender == idleCDO`, lines 937-942) precisely because claims are address-bound — yet the same address-binding assumption is violated one level up: nothing prevents an APR0-flagged user from transferring their tranche tokens to a fresh address before requesting the withdrawal. The new address is not in `apr0Users`, so `_calcInterestWithdrawRequest` computes full epoch interest on principal that was deposited under a 0% APR. This mirrors the external report's pattern: a deposit-time reduction/mark applied only when the deposit lands on the flagged account is bypassed by routing the position through an unmarked account via `transfer`.

### Finding Description
- Attacker (KYC-passed, unprivileged) calls `depositAA`/`depositBB` on `IdleCDOEpochVariant` during a phase where their principal is recorded as APR0-flagged in `IdleCreditVault` (`apr0Users`).
- Attacker transfers the minted `AATranche`/`BBTranche` tokens to a second address they control. Tranche tokens are plain ERC20 (`IdleCDOTranche.sol`) with no `apr0Users` propagation hook.
- From the fresh address, the attacker calls `requestWithdraw` on `IdleCDOEpochVariant`. Since `apr0Users[freshAddress]` is unset, `_calcInterestWithdrawRequest` in `IdleCreditVault.sol` computes the withdrawal amount with the normal epoch APR instead of 0%.
- After `stopEpoch`, the attacker calls `claimWithdrawRequest`/`claimInstantWithdrawRequest` and redeems principal + full interest, although the position was funded under APR0 terms.
- The existing guard that locks strategy-receipt transfers (`_transfer` only callable by `idleCDO`, `IdleCreditVault.sol:939-941`) protects receipt claims but does not propagate the APR0 flag across tranche transfers, so it does not stop this path.

### Impact Explanation
Direct theft of yield: the attacker extracts epoch interest that the pool never priced for their deposit, diluting other tranche holders' `lastNAV` allocation. The stolen amount equals `principal * apr * epochDuration`, paid out of funds reserved for honest LPs' claims — an unfair mint/burn / solvency-dilution violation with quantified loss per epoch.

### Likelihood Explanation
Low-to-medium. Requires an APR0-class deposit to be possible for a KYC'd lender and a subsequent epoch withdrawal; the attacker needs two wallet addresses (both able to hold tranche tokens; KYC gating applies to deposit, not token receipt). It is a repeatable, gas-cheap sequence with no privileged cooperation.

### Recommendation
Bind the APR0 flag to the position rather than the depositing address: either record APR0 principal per-epoch against tranche-token balances that follow transfers (e.g., a `transferHook` in `IdleCDOTranche` notifying the vault, similar to the external fix of applying the reduction inside `_transfer`), or track APR0 exposure via a per-epoch receipt token instead of an address mapping. At minimum, propagate `apr0Users` state proportionally on tranche transfer, or prevent withdrawal requests for APR0 principal based on epoch-tagged balances rather than `msg.sender`.

// SPDX-License-Identifier: MIT
// Fork test against test/foundry/IdleCreditVault.t.sol setup
function testPoc_Apr0TransferBypass() external {
    uint256 amount = 100_000 * ONE_SCALE;
    address alice = makeAddr("alice");   // APR0 depositor
    address bob   = makeAddr("bob");     // fresh address, same attacker

    // Alice deposits under APR0 conditions -> apr0Users[alice] = true
    _depositWithUser(alice, amount, true);
    assertTrue(IdleCreditVault(address(strategy)).apr0Users(alice));

    // Epoch runs and ends with real APR paid by borrower
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Bypass: move tranche tokens to unflagged address
    uint256 shares = AAtranche.balanceOf(alice);
    vm.prank(alice);
    AAtranche.transfer(bob, shares);
    assertFalse(IdleCreditVault(address(strategy)).apr0Users(bob));

    // Bob requests withdraw -> interest computed with full APR, not 0%
    vm.prank(bob);
    uint256 claim = cdoEpoch.requestWithdraw(0, address(AAtranche));

    uint256 bobPre = underlying.balanceOf(bob);
    vm.prank(bob);
    cdoEpoch.claimWithdrawRequest();

    // Bob received interest on APR0 principal: claim > pure principal share
    uint256 honestPrincipalOnly = amount * AAtranche.totalSupply() / amount; // baseline
    assertGt(underlying.balanceOf(bob) - bobPre, amount, "APR0 bypass: interest paid to unflagged address");
}
