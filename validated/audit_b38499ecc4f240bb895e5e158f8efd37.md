### Title
Miner-side signer weight tally double-counts a signer that flips from Reject to Accept, letting stale rejection weight persist and corrupting both the acceptance and rejection thresholds - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` maintains a single `BlockStatus` per block hash with two independently-gated weight pools, `total_weight_approved` and `total_weight_rejected`, both fed by the same finite pool of signer weight (`self.total_weight`). The two pools are supposed to be mutually exclusive per signer (a signer's weight should count toward at most one side at a time), but the dedup guards protecting each pool are asymmetric, so a single signer that first rejects and later accepts the same block gets its weight credited to *both* pools, and the reject-side credit is never reclaimed.

### Finding Description
In `handle_new_messages` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`):
- The **Accept** branch gates weight addition on `block.gathered_signatures.contains_key(&slot_id)`, a set that is only ever touched by the Accept branch itself. [1](#0-0) 
- The **Reject** branch gates weight addition on `block.responded_signers.insert(slot_id)`, a set that is shared and also written by the Accept branch. [2](#0-1) 

Because `gathered_signatures` is never populated by the Reject branch, a signer that sends Reject first (crediting `total_weight_rejected` and inserting itself into `responded_signers`) and then later sends a genuinely valid Accept for the same block (e.g. after reconsidering, which the signer-side protocol explicitly allows — see `docs/signer-flows.md` section 5, "we do not change our votes on rejected blocks unless we receive a new block proposal…") will pass the Accept branch's `!gathered_signatures.contains_key(&slot_id)` check and get its weight added to `total_weight_approved` as well. The earlier `total_weight_rejected` credit is never removed — there is no code anywhere in this file or `signer_coordinator.rs` that decrements or clears a signer's contribution to either pool once written.

This breaks the intended equality that each signer's weight can occupy only one side of the tally at a time: the same registered signer's weight now simultaneously "counts" toward both the approve and reject running totals for the block.

### Impact Explanation
The node-side coordinator (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) reads these same two counters to decide the block's fate: [3](#0-2) 
It checks rejection weight first (`total_weight_rejected + weight_threshold > total_weight` → `SignersRejected`) and only afterward checks `total_weight_approved >= weight_threshold` → accept. Because a signer's stale rejection weight is never retracted after it flips to accepting, that phantom weight can combine with other genuinely-rejecting signers to cross the 30%-blocking-minority threshold and cause the miner to abandon/exclude a block that in fact has (or would have) a legitimate accepting supermajority — a liveness wedge triggered by a single signer's legitimate vote change, not requiring collusion or a majority of malicious signers. Symmetrically, the same signer's weight is double-booked in the approve tally, so `total_weight_approved` can reflect more cumulative weight than the number of currently-valid, live accepting signers actually represents, undermining the intended weight-vs-verified-signer equality that this pool of code exists to enforce.

### Likelihood Explanation
Reaching this requires only a single signer (not a majority) to emit a Reject followed later by an Accept for the same `signer_signature_hash` — a sequence explicitly contemplated by the signer's own reconsideration logic and easily produced by normal operation (a signer initially rejects due to a stale chain view, then a later message/validation makes it valid) or by simple message reordering/duplication over StackerDB gossip. No other signer's key, majority coordination, or special access is needed.

### Recommendation
Use a single authoritative per-slot vote state (e.g. an enum `Accepted(weight)` / `Rejected(weight)`) keyed by `slot_id` instead of two independently-gated sets/counters. When a new message from a slot arrives, look up any prior vote for that slot, and if it differs from the new vote, subtract the previous credit from its bucket before adding the new credit to the other bucket, so a signer's weight is always attributed to exactly one bucket at a time.

### Proof of Concept
1. Signer S (weight W) submits `BlockResponse::Rejected` for block B. `handle_new_messages` reject-branch: `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += W`.
2. S later re-validates (e.g., a new proposal / reconsideration path in `stacks-signer/src/v0/signer.rs`'s pre-commit/vote-change logic) and submits a genuinely valid `BlockResponse::Accepted` signature for the same B.
3. Accept-branch checks `!gathered_signatures.contains_key(&slot_id)` — true, since only the accept branch ever writes `gathered_signatures` — so `total_weight_approved += W` is also applied.
4. `total_weight_rejected` is never decremented; `BlockStatus` for B now reports both `total_weight_rejected` and `total_weight_approved` inflated by W from the same signer, corrupting the miner's threshold decisions in `signer_coordinator.rs`.
