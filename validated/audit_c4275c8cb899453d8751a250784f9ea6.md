## Analysis

This maps cleanly onto the report's bug class: a security check is implemented with a **narrower predicate than the one its own name/comment promises**, letting a case through that the design intends to block — exactly like `isBLSPublicKeyPartOfLSDNetwork` silently omitting the "is banned" half of `isBLSPublicKeyBanned`.

### The narrower check

In the v1 chainstate proposal validator, the "already have a block in this tenure" duplicate-block guard only looks at **globally accepted** blocks: [1](#0-0) 

```rust
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)
    ...
if let Some(last_in_current_tenure) = last_in_current_tenure {
    ...
    return Err(RejectReason::DuplicateBlockFound);
}
```

The v2 equivalent was hardened to also catch a block this signer only **locally** accepted (i.e., signed but not yet group-signed), using `get_last_signed_block` instead — and there's a regression test proving the v1-style bug was real and was fixed for v2: [2](#0-1) 

The project's own flow documentation states the asymmetry explicitly: [3](#0-2) 

> `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we have already accepted a block in the tenure a tenure-change block is starting. v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)... Because the duplicate check never runs again, a block that crosses the pre-commit threshold long after it was proposed relies on section 5's own-tenure conflict guard to cover the same ground.

So for a **v1-protocol signer**, a second tenure-start block for a tenure where this signer already signed (but the block never reached global acceptance) sails past `check_proposal` — it is neither "part of the accepted set" by the check's own logic, mirroring the LSD report's "not banned" gap.

### Why the backstop can fail

The only other place this could be caught is the pre-commit conflict guard in `handle_block_pre_commit`, but that guard is explicitly time-bounded (`freshness_cutoff`) and, once a same-tenure conflict goes stale, only vetoes if the **node's** canonical tenure tip has reached the conflicting height: [4](#0-3) 

A block that was only *locally* accepted (never handed to the node, since that requires the whole signer set) will not be visible to `get_tenure_tip`, so once its signature goes stale the guard stands aside and the signer proceeds to sign the second, competing tenure-start block.

### Title
Protocol-v1 signer duplicate-block check uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, letting a signer sign two conflicting tenure-start blocks for the same tenure — ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (v1 chainstate) is supposed to guarantee a signer never endorses more than one tenure-start block per tenure. It implements this via `get_last_globally_accepted_block`, which only matches blocks that reached the full 70% group threshold. A block this signer itself already signed but that stayed merely *locally accepted* (e.g., a competing miner proposal split the vote, or the rest of the network never reached threshold) is invisible to this check, so a second, different tenure-start block for the same tenure passes `check_proposal` cleanly.

### Finding Description
- At proposal time, `check_proposal` → `validate_tenure_change_payload` is the only place that guards against a duplicate tenure-start block in the same tenure (per `docs/signer-flows.md` lines 425-437, this is not re-run at validate-ok or at signing).
- v1's version of this guard queries `get_last_globally_accepted_block`, which strictly filters for `BlockState::GloballyAccepted` [5](#0-4) .
- A block the signer locally accepted (signed) but that never gathered group signatures remains in `BlockState::LocallyAccepted` and is therefore not returned by `get_last_globally_accepted_block`. The check consequently does not fire, and the miner's second tenure-start proposal for the same tenure is accepted at proposal time, submitted for validation, and pre-committed.
- The only remaining safety net is the pre-commit "own tenure" conflict check in `handle_block_pre_commit`, but that check only blocks while the conflicting signature is "fresh" or while the node's canonical tenure tip already reaches the conflicting height. A locally-accepted-only block is invisible to the node's tip, so once its freshness window (`tenure_last_block_proposal_timeout`) elapses, the guard permits signing the second block [4](#0-3) .
- v2's analogous check was hardened to use `get_last_signed_block` (locally OR globally accepted), and a regression test explicitly documents that the old (v1-style) behavior was a bug [2](#0-1) ; v1 was left unpatched.

### Impact Explanation
A single v1-protocol signer can end up signing two different tenure-start blocks for the same tenure/height, breaking the "one block per tenure-start slot" invariant this guard exists to enforce. This is a signer signing a conflicting block — a Critical-class outcome per the rules (a signer signing a conflicting block at the same height/tenure).

### Likelihood Explanation
Requires only: (1) a signer configured for protocol v1 (still selectable via the version-negotiation path noted in `docs/signer-flows.md`), (2) a miner proposing a first tenure-start block that a subset of signers locally accept but that fails to reach global threshold, and (3) the same miner (or gossip of an already-crafted proposal) re-proposing a different tenure-start block for the same tenure after the freshness timeout. No majority collusion, no other signer's key, and no node access beyond normal `/v3/block_proposal` flow is needed — matching the "one-slot miner plus gossip" threat model.

### Recommendation
Change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `get_last_signed_block` (or equivalent "locally or globally accepted") instead of `get_last_globally_accepted_block`, matching the v2 fix, so a signer's own locally-accepted tenure-start block also triggers `RejectReason::DuplicateBlockFound` for a competing proposal in the same tenure.

### Proof of Concept
1. Signer S runs with protocol v1 (`SortitionsView`).
2. Miner proposes tenure-start block A for tenure T; S validates it OK and locally accepts/signs A (`mark_locally_accepted`), but the group never reaches the 70% pre-commit/signature threshold (e.g., network split or slow signers) — A stays `BlockState::LocallyAccepted` forever, per `stacks-signer/src/signerdb.rs` state semantics.
3. After `tenure_last_block_proposal_timeout` elapses, the same miner proposes block B: a different tenure-start block for the same tenure T (same `consensus_hash`, contains a `TenureChange` with `cause=BlockFound`).
4. `check_proposal` → `validate_tenure_change_payload` calls `get_last_globally_accepted_block(T)`, which returns `None` (A was never globally accepted) — no `DuplicateBlockFound`, so B passes.
5. B is validated OK by the node, pre-committed, and reaches the pre-commit threshold. In `handle_block_pre_commit`, `get_signed_conflicts` finds A, but since A is stale (past freshness cutoff) and the node's `get_tenure_tip(T)` never reached A's height (A was never handed to the node), the own-tenure stale-conflict guard does not block signing.
6. S signs B via `mark_locally_accepted` / `handle_block_signature`, producing signer S's second signature over a conflicting block (B) in tenure T, alongside its earlier signature over A.
