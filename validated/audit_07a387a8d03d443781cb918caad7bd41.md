## Title
Stale confirmations from removed multisig members/keys are still counted toward the confirmation threshold, allowing requests to execute with fewer *live* approvals than `num_confirmations` requires - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
When a multisig member (or, in the legacy `multisig` contract, an access key) is removed via `DeleteMember`/`DeleteKey`, the contract only purges the confirmations and requests that the removed member *originated*. It never scans other pending requests to strip confirmations that the removed member had already *cast* on them. Because `confirm()` simply compares `confirmations.len()` against `self.num_confirmations` without checking that every entry still belongs to a current member, a stale confirmation from a departed member continues to count toward the threshold, letting a request execute with fewer genuinely live confirmations than the configured threshold.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` counts confirmations purely by set size: [1](#0-0) 

`delete_member()` only removes requests whose *originating* member equals the removed member; it does not touch the `confirmations` map for requests originated by *other* members that the removed member had confirmed: [2](#0-1) 

The same pattern exists in the older `multisig` contract's `DeleteKey` handler, which likewise only removes requests signed by the deleted key, leaving that key's confirmations on other members' requests intact: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`confirmations.len()` (recorded claims) == number of confirmations cast by **currently live** members/keys.

After a member/key is removed, this equality breaks: `confirmations.len()` still includes the removed member's stale entry, while the true count of live-member confirmations is one less.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." A pending request can reach `num_confirmations` and execute (e.g., transferring funds, adding a full-access key, deploying a contract) even though it only ever received `num_confirmations - 1` (or fewer) confirmations from members who are still part of the multisig at execution time. This undermines the fundamental k-of-n security guarantee of the multisig.

### Likelihood Explanation
This requires no attacker to be unprivileged in the sense of bypassing access control — it is a defect reachable through completely ordinary multisig operation: a request created and partially confirmed by one member, followed later by legitimate removal of one of the confirming members, followed by a remaining member reaching the nominal threshold. No malicious insider collusion beyond normal multisig usage patterns is required; it can happen purely as an artifact of routine member turnover (e.g., off-boarding an employee's key) combined with any request that member had confirmed before being removed.

### Recommendation
When executing `DeleteMember` (or `DeleteKey`), iterate over all entries in `self.confirmations` and remove the removed member's/key's entry from every confirmation set, not just from requests it originated. Alternatively, validate at `confirm()` time (and before executing a request) that every entry in the stored confirmation set still corresponds to a current member, discarding stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` to create Request `X` (e.g., `Transfer` to receiver `R`), then `A` calls `confirm(X)` → `confirmations[X] = {A}`.
3. `B` calls `confirm(X)` → `confirmations[X] = {A, B}` (2 of 3, request X pending).
4. Separately, members create and confirm Request `Y = DeleteMember{B}` with 3 live confirmations (e.g. `A, C, D`); it executes via `execute_request` → `delete_member` removes `B` from `members`, and only purges requests *originated* by `B` — Request `X` (originated by `A`) is untouched, so `confirmations[X]` still equals `{A, B}`.
5. `C` (a live member) calls `confirm(X)`: `confirmations[X].len() (2) + 1 = 3 >= num_confirmations (3)` → Request `X` executes.
6. Result: Request `X` executed with confirmations `{A, B, C}`, but `B` was no longer a member at execution time — only `A` and `C` are genuinely live confirmers, i.e., the request executed with 2 real confirmations against a nominal threshold of 3. [1](#0-0) [2](#0-1) [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
