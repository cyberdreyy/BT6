### Title
Missing zero-address check on `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permanently freezes migrated funds - (File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs)

### Summary
`TransferToNewAccount` and `TransferToNewAccountPda` let the current authority of a `MarginfiAccount` migrate all balances to a new account under a caller-supplied `new_authority` pubkey. The `new_authority` account is explicitly annotated `/// CHECK: WARN: New authority is completely unchecked` and no validation (not even a zero-address check) is performed before it is written into the new account and the old account is disabled/zeroed.

### Finding Description
In `transfer_to_new_account` (and the PDA variant `transfer_to_new_account_pda`), the handler:
1. Loads `old_account`, verifies flags/flashloan/receivership/order-execution state, and that it hasn't already migrated.
2. Initializes `new_account` by copying `old_account.lending_account` (all deposit/borrow balances) and setting `new_account.authority = ctx.accounts.new_authority.key()` via `initialize_migrated_account` [1](#0-0) .
3. Disables the old account and zeroes its `lending_account`, so the old account can never be used again [2](#0-1) .

The `new_authority` account struct field is defined as a fully unchecked account with an explicit warning comment, and neither the handler nor the account constraints reject `Pubkey::default()` (the zero address) [3](#0-2) . The same pattern exists in the PDA-account variant, where `new_authority` is likewise unchecked [4](#0-3) .

If a caller (this is the account's own current authority — an unprivileged, ordinary user action, not an admin operation) passes `new_authority = Pubkey::default()`, either by mistake or via a malicious front-end/relayer/third-party integration tricking the user into signing such a transaction, the new account's `authority` field is set to the zero pubkey. Since no private key corresponds to `Pubkey::default()`, `is_signer_authorized` checks elsewhere in the codebase (which compare `Signer<'info>.key()` against `account.authority`) can never succeed for that account again, and the old account is already permanently disabled and zeroed. All of the migrated deposit/borrow balances become durably unrecoverable by anyone.

The CLI helper `p0-cli/src/processor/account.rs::marginfi_account_transfer` does add a client-side guard (`if new_authority == Pubkey::default() { bail!(...) }`) [5](#0-4) , confirming the zero-address case is recognized as dangerous — but this check exists only in one off-chain CLI tool, not in the on-chain program, so any other client, integrator, or manually constructed transaction bypasses it entirely.

### Impact Explanation
This is a durable freeze of user funds with direct financial effect: successful exploitation (or even accidental misuse) permanently locks all of a `MarginfiAccount`'s deposited/borrowed balances with no recovery path, since the old account is disabled/zeroed and the new account's authority can never sign. There is no admin override instruction shown in these instructions to reset `authority` on an already-migrated account.

### Likelihood Explanation
The action is unprivileged and permissionless — it only requires the current account authority's signature, which is exactly the kind of caller-triggerable path in scope. The bug requires either user/integrator error or a maliciously crafted transaction (e.g., a compromised or malicious dApp front-end presenting a transfer transaction with a hidden/incorrect `new_authority`), which is a realistic vector since the account explicitly documents itself as "completely unchecked." The existence of a manual guard in the CLI tool shows the marginfi team is aware zero-address `new_authority` is a real risk, but that mitigation was not carried into the on-chain program.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that rejects `new_authority == Pubkey::default()`, mirroring the Lido `DepositSecurityModule` recommendation:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority // or a new dedicated error
);
```
This should be enforced before `initialize_migrated_account` mutates any state, so a bad `new_authority` aborts the whole transaction instead of silently bricking the account.

### Proof of Concept
1. User creates/owns a `MarginfiAccount` with deposits and/or borrows.
2. User (or a malicious front-end acting on the user's behalf) submits `transfer_to_new_account` (or `transfer_to_new_account_pda`) with `new_authority = Pubkey::default()` and a valid `new_marginfi_account`/PDA, valid `global_fee_wallet`, and valid `fee_payer`.
3. The instruction succeeds: `new_account.authority` is set to `11111111111111111111111111111111` (system program / zero pubkey), `old_account` is disabled and its `lending_account` zeroed [6](#0-5) .
4. No subsequent transaction can ever pass a `Signer` matching `Pubkey::default()`, so every downstream instruction requiring `is_signer_authorized`/`account_not_frozen_for_authority` against the new account's authority permanently fails — the account's balances are frozen forever with no admin recovery path shown in this instruction set.

    current_timestamp: u64,

    new_account.indexer_flags = old_account.indexer_flags;

}

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
