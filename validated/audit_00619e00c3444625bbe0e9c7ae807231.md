### Title
Missing borrower zero-address validation permanently locks deposited funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.initialize` accepts a zero-address borrower, while `deployCreditVault` only validates that the manager is nonzero. Once an epoch starts, `sendFundsToBorrower` transfers the vault surplus directly to `strategy.borrower()`, so a deployment initialized with `borrower == address(0)` permanently sends lender underlyings to the zero address. [1](#0-0) [2](#0-1) 

### Finding Description
`deployCreditVault` passes `strategyData.borrower` directly to `IdleCreditVault.initialize` and rejects only a zero manager. [3](#0-2)  `IdleCreditVault.initialize` stores `_borrower` without checking that it is nonzero. [1](#0-0)  This omission is inconsistent with `setBorrower`, which explicitly rejects `address(0)` and shows that a nonzero borrower is an intended protocol invariant. [4](#0-3) 

During `startEpoch`, the CDO computes pending instant withdrawals and transfers the remaining underlying balance to `sendFundsToBorrower`. [5](#0-4)  `sendFundsToBorrower` calls `_transferUnderlyings(_borrower(), _amount)`, and `_borrower()` returns the strategy’s unchecked `borrower` value. [6](#0-5) [7](#0-6) 

Standard ERC20 transfers to `address(0)` increase the zero-address balance rather than reverting or making the tokens recoverable. Any unprivileged deployer can therefore create a syntactically valid factory deployment with a real manager and underlying token but an unusable borrower.

### Impact Explanation
A lender deposits `N` underlyings and the honest configured manager later calls `startEpoch`. The CDO transfers the available underlying balance to `address(0)`, permanently removing those assets from circulation rather than placing them under borrower control. [2](#0-1) 

The next `stopEpoch` also cannot recover funds from the zero address, so the attempted borrower repayment fails and `_handleBorrowerDefault` marks the vault defaulted. [8](#0-7) [9](#0-8)  The quantified loss is the full amount sent to the zero address, including pooled lender principal available at epoch start.

### Likelihood Explanation
Exploitation requires one misconfigured public factory deployment and a subsequent routine epoch start by the configured owner or manager. The manager does not need to be malicious; the loss follows from normal protocol operation over a borrower value that the initialization path should have rejected. [10](#0-9) 

Likelihood is moderate to low because lenders and the configured manager would have to use the malformed vault, but the resulting loss is deterministic and equal to the amount transferred at epoch start.

### Recommendation
Reject `address(0)` for `strategyData.borrower` in `IdleCreditVaultFactory.deployCreditVault` and `deployRevolvingCreditVault`. Independently add `if (_borrower == address(0)) revert Is0();` or equivalent validation to `IdleCreditVault.initialize`, matching the existing `setBorrower` invariant. [4](#0-3)

  /// @notice Handle borrower default
  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.

    if (isProgrammableBorrower) {
      IProgrammableBorrower(_borrower()).onDefault();
    }

    // deposits should be already prevented
    if (!paused()) {
      _pause();
    }

    // stop the current epoch
    isEpochRunning = false;

    // prevent withdrawals requests
    allowAAWithdrawRequest = false;
    allowBBWithdrawRequest = false;

    emit BorrowerDefault(funds);
  }
