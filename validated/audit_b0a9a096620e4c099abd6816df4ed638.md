### Title
`check_parent_tenure_choice` grants an irrevocable reorg permit from a purely local, race-able view of "how many blocks the reorged tenure globally accepted" - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The Sherlock report's root cause is a check that reads a mutable aggregate ("current utilization") that a single actor can transiently manipulate within one atomic action, so a guard meant to cap risk is bypassed and the bypass's effect (draining liquidity) persists after the manipulation is undone. The signer analog is `SortitionData::check_parent_tenure_choice`, which permits one tenure to reorg another based on a **local, possibly-stale** count of "globally accepted" blocks in the tenure being reorged. Because this count is read from the local `SignerDb` rather than confirmed with the node/network truth, and because the resulting permit is **recorded once and never re-derived**, a miner can obtain (from any individual signer whose local view happens to lag) a permit that should never have been granted, and that signer will thereafter refuse to let its own signature block the replacement - permanently, since the permit is keyed only to the permitting sortition's canonicality, not to the truth of the block-count condition that justified it.

### Finding Description
`check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs`, lines 170-295) is invoked when a miner's tenure does not build off the prior sortition (i.e., it is proposing a reorg). For each tenure being reorged, it gates the reorg with:

```
let globally_accepted_blocks =
    signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
if globally_accepted_blocks > 1 {
    ...
    return Ok(false);
}
``` [1](#0-0) 

`get_globally_accepted_block_count_in_tenure` is a pure local-DB query - it counts rows in this signer's own `blocks` table marked `GloballyAccepted`, with no round-trip to the stacks-node or to the rest of the signer set to confirm the network's actual state: [2](#0-1) 

A block is only marked `GloballyAccepted` locally once *this* signer observes the node's `NewBlock` event (or advances the tenure tip check) confirming it - `mark_globally_accepted` is stamped asynchronously and can lag well behind the true global state, especially right after a fast succession of blocks in a tenure.

If the count check passes (because this signer's local view has not yet caught up to a second globally-accepted block in the reorged tenure), the function walks into the timing branch and, if the block was "poorly timed" relative to the sortition transition, it is added to `superseded_tenures`: [3](#0-2) 

Once every reorged tenure clears the (locally-evaluated) rules, the permit is committed permanently via `mark_tenure_superseded`/`record_superseded_tenure`: [4](#0-3) 

Crucially, per the design comment on `SignerDb::mark_tenure_superseded`, this decision is **recorded when granted and never re-derived**: "Recorded when the reorg is permitted rather than derived at signing time, because by the time a replacement reaches the pre-commit threshold the sortition view that sanctioned the reorg may be long gone." The only thing later re-checked is whether the *permitting* sortition is still canonical (`reorg_permit_stands`) - never whether the original "at most one globally accepted block" condition was actually true: [5](#0-4) 

And at the moment this permit is consulted (pre-commit threshold reached on the replacement), a standing permit **excludes the conflict outright** - this signer's own earlier signature over the reorged tenure's block no longer blocks anything: [6](#0-5) [7](#0-6) 

This is structurally identical to the Sherlock M-8 pattern: a guard that is supposed to cap a risky action ("do not reorg a tenure that already has ≥2 confirmed blocks") is evaluated against a value that a single actor (here, the miner racing its own reorg proposal against the propagation of the second tenure block's global-acceptance confirmation) can catch in a transient, unrepresentative state - and, unlike the loan-pool case where the check simply re-runs each time, here the wrong answer is **latched forever** as a per-tenure permit, and later removes this signer's veto power over an actually-canonical, multi-block tenure being reorged.

### Impact Explanation
If a single signer's local view lags such that it has recorded 0 or 1 globally-accepted blocks for a tenure that the network has actually already carried to 2+ globally-accepted blocks, `check_parent_tenure_choice` wrongly evaluates the reorg as permitted for that signer. The resulting `mark_tenure_superseded` record makes that signer treat any of its own prior signatures over that tenure's blocks as void conflicts from then on (`get_signed_conflicts`/`reorg_permit_stands`), so it will sign a replacement block belonging to a competing tenure at the same or lower height as a tenure the network has already canonized past height 1. This is exactly the class of outcome the rules classify as Critical: a signer signing a block that conflicts with (reorgs) a block that was already canonically accepted by the network, because the local "at-most-one-block" equality the permit is based on was evaluated on stale/incomplete local state and never re-verified. Because the permit is durable (only voided if the permitting sortition itself is orphaned), this is not a one-off timing blip but a persistent loss of that signer's conflict guard for the affected tenure.

### Likelihood Explanation
This requires no signer collusion and no majority - it is purely a race between (a) a signer's local processing of the second tenure block's global acceptance, and (b) a miner's/next-tenure's reorg proposal reaching that same signer, which is squarely in the "single miner (plus gossip)" trigger class the scope allows. Signers process events serially and asynchronously relay on `NewBlock` events from their own node instance; brief lag between block propagation and this bookkeeping is routine, not a contrived edge case, making the window realistic during normal high tempo tenure transitions (e.g., a tenure that mines two blocks in quick succession right before the next sortition).

### Recommendation
`check_parent_tenure_choice` should not treat the local `get_globally_accepted_block_count_in_tenure` result as authoritative. Before permitting a reorg, the signer should also query the stacks-node's canonical view of the reorged tenure's tip (the same `get_tenure_tip`/`get_tenure_forking_info` machinery already used elsewhere in this module) to confirm the local count is not stale, or should re-derive the "at most one globally accepted block" condition at signing time (consistent with how `conflict_still_blocks`/`reorg_permit_stands` re-derive every other liveness fact from the node instead of latching a one-time local snapshot). At minimum, `mark_tenure_superseded` records should be revoked if a later `NewBlock` event reveals the reorged tenure in fact had more than one globally-accepted block.

### Proof of Concept
1. Tenure A produces block A1, followed quickly by block A2, both eventually reaching global acceptance across the signer set.
2. Signer S has processed A1's `NewBlock` confirmation (marking A1 `GloballyAccepted` locally) but has not yet processed A2's `NewBlock` confirmation - so `get_globally_accepted_block_count_in_tenure(tenure_A)` on S's local DB returns 1, not the true 2.
3. Before S catches up, a miner proposes tenure B's first block, built on the sortition prior to A (i.e., attempting to reorg A). S's proposal-arrival evaluation calls `check_parent_tenure_choice`, sees `globally_accepted_blocks == 1` (not `> 1`), and - given the timing branch is satisfied for A1 - adds tenure A to `superseded_tenures`, then commits `mark_tenure_superseded(A, ..., permitting=B, ...)`.
4. From this point, per `get_signed_conflicts`/`reorg_permit_stands`, S treats its earlier signature over A1/A2 as excluded while B's sortition remains canonical, and will sign B's tenure-start block even though A already has two canonically-accepted blocks on the rest of the network - a signature over a block that conflicts with an already-canonical tenure, produced by S acting entirely on its own stale local bookkeeping.     /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
