### Title
Stale rejection weight is never retracted when a signer flips Reject→Accept, letting `total_weight_rejected` and `total_weight_approved` double-count the same signer's weight - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side `StackerDBListener` tallies per-block signer weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, guarded by two different membership checks (`gathered_signatures` vs `responded_signers`). Because `BlockInfo::check_state` explicitly permits a signer's local state machine to transition `LocallyRejected -> LocallyAccepted`, a signer can legitimately reject a block and later accept the same block. When that happens, the listener adds the signer's weight to `total_weight_approved` without ever removing it from `total_weight_rejected`, breaking the implicit invariant that a signer's weight should only be counted toward one side at a time — the exact "one balance updated on deposit/withdraw without reconciling the other side" bug class described in the report.

### Finding Description
`BlockStatus` tracks `total_weight_approved`, `total_weight_rejected`, and `responded_signers` per proposed block: [1](#0-0) 

In the `Accepted` branch, weight is only added the first time the slot id is *not yet* in `gathered_signatures`, and afterwards both `gathered_signatures` and `responded_signers` are updated: [2](#0-1) 

In the `Rejected` branch, weight is only added if `responded_signers.insert(slot_id)` returns `true` (i.e., this slot has never responded before, in *either* direction): [3](#0-2) 

The two guards are asymmetric:
- **Accept-then-Reject**: after Accept, `responded_signers` already contains the slot. A later Reject fails the `insert` check, so `total_weight_rejected` is correctly *not* incremented. Safe.
- **Reject-then-Accept**: after Reject, `responded_signers` contains the slot, but `gathered_signatures` does **not** (it is only populated in the Accept branch). A later Accept passes the `!gathered_signatures.contains_key(&slot_id)` check and adds the signer's weight to `total_weight_approved`, while the earlier addition to `total_weight_rejected` is **never reversed**. The signer's weight is now double-counted across both tallies.

This Reject→Accept sequence is not a hypothetical: it is explicitly permitted by the signer's own local state machine. `BlockInfo::check_state` allows any state to move to `LocallyAccepted`/`LocallyRejected` as long as the previous state wasn't already `GloballyAccepted`/`GloballyRejected`: [4](#0-3) 

and `mark_locally_accepted`/`mark_locally_rejected` are plain setters that invoke `move_to`: [5](#0-4) 

So a signer that first broadcasts `Rejected` (e.g. transient validation failure) and later re-evaluates and broadcasts `Accepted` for the same `signer_signature_hash` produces exactly this sequence at the coordinator.

### Impact Explanation
The coordinator uses `total_weight_rejected` to decide whether a blocking minority (>30%) has rejected the block, in which case it aborts the current attempt and can permanently/temporarily ban transactions: [6](#0-5) 

Because a stale rejection is never retracted once the same signer later accepts, `total_weight_rejected` can remain permanently inflated by weight that no longer represents the signer's current opinion. This can:
- cause the coordinator to spuriously conclude a blocking-minority rejection (`SignersRejected`) even though a real majority (by current votes) supports the block, stalling/wedging block production for that tenure attempt, and
- cause `failed_txids` weight tallies to reach the `blocking_minority` threshold using stale weight, permanently banning a transaction that the network no longer objects to.

This is a liveness wedge reachable by a single signer's legitimate vote-flip plus normal gossip delivery order, not requiring a majority of signers or key compromise, matching the in-scope "liveness wedge" impact class.

### Likelihood Explanation
Requires only one signer (out of the whole set) to send `Rejected` followed later by `Accepted` for the same block — a state transition explicitly allowed by the signer's own local state machine (`LocallyRejected -> LocallyAccepted`) and plausible under normal re-validation/timing behavior (e.g., a chainstate re-check that initially failed and later a re-evaluated/reproposed path succeeds) or simply reordered/delayed StackerDB message delivery. No majority collusion, no key compromise, and no protocol-version mismatch is required — a single honest signer flipping its vote once is sufficient to leave a stale entry in `total_weight_rejected` for the lifetime of that block's tracked status.

### Recommendation
Track approval/rejection membership with a single per-slot "last known vote" state instead of two independently-guarded weight accumulators, or recompute both weights from the *current* winning vote per slot on the fly whenever a new response for a previously-responded slot arrives (subtract stale weight before adding to the new bucket). Concretely: before adding to `total_weight_approved` in the `Accepted` branch, check whether the slot previously contributed to `total_weight_rejected` (e.g., track a `HashMap<slot_id, Vote>` and reconcile `total_weight_rejected` by subtracting the stale weight); apply the symmetric fix in the `Rejected` branch.

### Proof of Concept
1. Node proposes block `B` and starts `StackerDBListener` tracking `BlockStatus` for `B`'s `signer_signature_hash`.
2. Signer `S` (weight `w`) initially rejects `B` (e.g., due to a transient `check_block_against_signer_db_state` failure) and broadcasts `BlockResponse::Rejected`. The listener's `Rejected` branch: `responded_signers.insert(slot_S)` → `true` → `total_weight_rejected += w`.
3. `S`'s local re-check later succeeds (permitted transition `LocallyRejected -> LocallyAccepted` per `check_state`), and `S` broadcasts `BlockResponse::Accepted` for the same `B`.
4. The listener's `Accepted` branch checks `!gathered_signatures.contains_key(slot_S)` → `true` (never populated by the Reject path) → `total_weight_approved += w`, and inserts into `gathered_signatures`/`responded_signers` (already present, no-op).
5. Result: `total_weight_rejected` still includes `w` from step 2, and `total_weight_approved` now also includes `w` from step 4 — `S`'s weight is counted on both sides simultaneously, and `total_weight_rejected` is never decremented even though `S` no longer rejects `B`.
6. If enough signers repeat this pattern (each individually a minority), `total_weight_rejected` can cross `self.total_weight - self.weight_threshold` purely from stale votes, triggering `Err(NakamotoNodeError::SignersRejected { .. })` in `signer_coordinator.rs` and banning transactions/stalling the tenure attempt despite current signer sentiment favoring acceptance.

    pub fn mark_locally_accepted(&mut self, group_signed: bool) -> Result<(), String> {
        if group_signed {
            self.signed_group.get_or_insert(get_epoch_time_secs());
        } else {
            self.valid = Some(true);
            self.approved_time.get_or_insert(get_epoch_time_secs());
            self.signed_self.get_or_insert(get_epoch_time_secs());
        }
        self.move_to(BlockState::LocallyAccepted)
    }

    /// Mark this block's signed group time if not already set and attempt to mark it as globally accepted.
    pub fn mark_globally_accepted(&mut self) -> Result<(), String> {
        self.signed_group.get_or_insert(get_epoch_time_secs());
        self.move_to(BlockState::GloballyAccepted)
    }

    /// Mark this block as invalid and attempt to mark it as locally rejected
    pub fn mark_locally_rejected(&mut self) -> Result<(), String> {
        self.valid = Some(false);
        self.move_to(BlockState::LocallyRejected)
    }

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
