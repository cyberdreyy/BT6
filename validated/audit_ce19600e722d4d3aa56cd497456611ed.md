### Title
Front-runnable Vault request-digest allowlist authorization enables permanent DoS of legitimate CreateSecrets/UpdateSecrets/Delete/List requests - (File: core/capabilities/vault/allow_list_based_auth.go, core/capabilities/vault/authorizer.go, core/capabilities/vault/request_replay_guard.go)

### Summary
Chainlink's Vault gateway authorizes requests either via a signed JWT (bound to a specific signer) or, for legacy/no-`Auth` clients, via `AllowListBasedAuth.AuthorizeRequest` [1](#0-0) , which authorizes *any* HTTP caller who submits a JSON-RPC request whose content-hash (`req.Digest()`) matches a digest that was previously allowlisted on-chain — with no binding to the identity of the HTTP submitter. Immediately after authorization succeeds, `authorizer.AuthorizeRequest` consumes a single-use replay guard keyed only by that digest [2](#0-1) . Because the digest is a pure function of the request's `method`/`id`/`params` and is not bound to who submits it, any unprivileged actor who can reconstruct byte-identical request content for an already-allowlisted (public, on-chain) digest can submit it to the gateway before the legitimate workflow owner does, permanently consuming the replay-guard slot and causing the legitimate owner's subsequent, identical submission to be rejected with `ErrRequestAlreadySeen` ("request was already authorized previously") [3](#0-2) . This mirrors the reported `NFTFilter.verifyLoanValidity()` pattern: an unauthenticated function that validates externally-observable data and performs a one-time, stateful side effect (nonce/digest consumption), enabling front-running DoS against the legitimate caller.

### Finding Description
The Vault gateway-routed pipeline (`GatewayVaultRequestProcessor.ProcessRequest` → `authorizeAndStamp` → `Authorizer.AuthorizeRequest`) is reachable from an unauthenticated public HTTP entry point: `gateway.ProcessRequest` decodes and routes any raw JSON-RPC POST to the relevant handler with no caller identity check beyond the request content itself [4](#0-3) , and the vault handler forwards to `requestProcessor.ProcessRequest` for every non-`PublicKeyGet` method [5](#0-4) .

For requests without an `Auth` (JWT) field, authorization falls back to `allowListBasedAuth.AuthorizeRequest`, which:
1. Computes `req.Digest()` from the request's method/id/params.
2. Looks up whether that exact digest is present in the on-chain `WorkflowRegistry` allowlist (populated by a separate, public on-chain transaction, e.g. `AllowlistRequest`) [6](#0-5) .
3. Returns an `AuthResult` bound to the on-chain `Owner`, with **no verification that the HTTP caller is that owner or has any relationship to them** — anyone who submits matching bytes gets authorized as if they were the owner-submitted request.

The shared `authorizer.AuthorizeRequest` wrapper then immediately calls `replayGuard.CheckAndRecord(authResult.Digest(), ...)`, a process-wide, single-use map that marks the digest "seen" the very first time *any* caller's request is authorized [2](#0-1) , exactly as documented in `request_replay_guard.go`: "Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure that a given request digest is only accepted once." [7](#0-6) 

This is structurally identical to the reported bug class: `verifyLoanValidity()` validated externally-visible signed data and mutated a nonce as a side effect, with no check that the caller was the intended party — enabling a front-runner to consume the nonce before the legitimate borrower's transaction landed, causing the borrower's transaction to revert. Here, `AuthorizeRequest`/`CheckAndRecord` validates externally-derivable request content (whose validity was established by a public on-chain allowlist transaction) and mutates a "seen" set as a side effect, with no check that the HTTP submitter is the workflow owner — enabling an unprivileged actor who reconstructs the exact request bytes to consume the replay-guard slot before the legitimate owner's HTTP submission arrives.

The gateway test suite's own duplicate-request tests confirm the mechanism and its externally-visible error message, which any attacker (or the legitimate owner after being front-run) will observe: `"request was already authorized previously"` [8](#0-7) , and system tests explicitly document this replay-guard/DoS interaction as an accepted operational behavior under retries [9](#0-8) .

### Impact Explanation
If successfully front-run, the legitimate workflow owner's `SecretsCreate`/`SecretsUpdate`/`SecretsDelete`/`SecretsList` request is denied and cannot be resubmitted with the same content — the on-chain allowlisted digest is now considered "used," so the owner would need to submit a brand-new on-chain `AllowlistRequest` transaction (a new digest) and wait for propagation across the DON before retrying, per the workflow-registry-syncer polling delay noted in `allowListBasedAuthRetryInterval` [10](#0-9) . For time-sensitive secret rotations or emergency deletes this is a meaningful denial-of-service against the specific, targeted vault operation. It does not, by itself, allow secret exfiltration or fund movement, since `validateSecretOwnersMatchAuthorized` still checks that payload owner fields match the (attacker-supplied but on-chain-anchored) authorized owner [11](#0-10) .

### Likelihood Explanation
Exploitability depends heavily on the attacker's ability to reconstruct byte-identical JSON-RPC request content (method + id + params) that hashes to an already-allowlisted, publicly observable on-chain digest — the on-chain event exposes only the digest (a hash), not the preimage. For `MethodSecretsCreate`/`MethodSecretsUpdate`, the `params` contain TDH2-encrypted ciphertext that an outside attacker cannot feasibly reproduce, making pre-image reconstruction impractical. For `MethodSecretsList`/`MethodSecretsDelete`, however, params consist of plaintext, potentially predictable fields (owner address, namespace, key names, and a `request_id`), so likelihood there is higher if request IDs/keys follow guessable conventions, but remains speculative without further evidence that request IDs are ever predictable or otherwise learnable by an unprivileged party before submission. This is a genuine architectural weakness (missing binding between "who is authorized" and "who submitted the HTTP request," combined with an irrevocable single-use side effect), but I could not fully confirm a concrete unprivileged-attacker path to learn exact pre-image bytes ahead of time within the code available in this index — that gap should be validated further (e.g., checking whether client tooling makes request IDs deterministic/predictable, or whether any component logs/broadcasts the full un-submitted request before HTTP delivery).

### Recommendation
Bind the digest-allowlist authorization to a proof of caller identity (e.g., require a lightweight caller signature over the raw request, or require the HTTP submission to originate from a session/API-key tied to the same address that performed the on-chain `AllowlistRequest`) so that a third party who merely reconstructs matching request bytes cannot consume the allowlist entry on someone else's behalf. Alternatively/additionally, make replay-guard consumption idempotent per-authorized-owner rather than a single global "first submitter wins" digest, or require the *actual submission* itself to be signed (as is already done in the JWT path) rather than optionally falling back to an unauthenticated allowlist match.

### Proof of Concept
1. Workflow owner encodes a `ListSecretIdentifiersRequest` (or `DeleteSecretsRequest`) as a JSON-RPC request with a chosen `id`, computes `req.Digest()`, and submits an on-chain `WorkflowRegistry.AllowlistRequest(digest, expiry)` transaction (this transaction, and the digest, are publicly visible) [12](#0-11) .
2. An attacker who can reconstruct the exact same request bytes (owner address, namespace, id, key names) for that digest sends this raw JSON-RPC payload directly to the gateway's public HTTP endpoint before the legitimate owner does.
3. `allowListBasedAuth.AuthorizeRequest` finds the digest in the on-chain allowlist and returns success; `authorizer.AuthorizeRequest` calls `replayGuard.CheckAndRecord(digest, ...)`, marking it seen [2](#0-1) .
4. When the legitimate owner subsequently submits the identical request, `CheckAndRecord` returns `ErrRequestAlreadySeen`, and the gateway rejects it with `"request was already authorized previously"` [8](#0-7) , denying the owner's operation until a fresh on-chain allowlist entry is created and propagated.

// AuthorizeRequest authorizes a request using AllowListBasedAuth.
// It does NOT check if the request method is allowed.
func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}

// validateSecretOwnersMatchAuthorized checks that secret identifiers in the request payload
// match the authorized workflow owner. This is read-only validation; owner prefixing and
// param stamping happen later in GatewayVaultRequestProcessor.
func validateSecretOwnersMatchAuthorized(req jsonrpc.Request[json.RawMessage], workflowOwner string) error {
	switch req.Method {
	case vaulttypes.MethodPublicKeyGet:
		return nil
	case vaulttypes.MethodSecretsCreate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var createReq vaultcommon.CreateSecretsRequest
		if err := json.Unmarshal(*req.Params, &createReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(createReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsUpdate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var updateReq vaultcommon.UpdateSecretsRequest
		if err := json.Unmarshal(*req.Params, &updateReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(updateReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsDelete:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var deleteReq vaultcommon.DeleteSecretsRequest
		if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
			return err
		}
		return validateSecretIdentifierOwnerMismatch(deleteReq.Ids, workflowOwner)
	case vaulttypes.MethodSecretsList:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var listReq vaultcommon.ListSecretIdentifiersRequest
		if err := json.Unmarshal(*req.Params, &listReq); err != nil {
			return err
		}
		if vaultutils.NormalizeOwner(listReq.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("list secrets owner %q does not match authorized workflow owner %q", listReq.Owner, workflowOwner)
		}
		return nil
	default:
		return fmt.Errorf("owner validation not implemented for method %q", req.Method)
	}
}

var ErrRequestAlreadySeen = errors.New("request was already authorized previously")

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (g *gateway) ProcessRequest(ctx context.Context, rawRequest []byte, auth string) (rawResponse []byte, httpStatusCode int) {
	// decode
	jsonRequest, err := jsonrpc2.DecodeRequest[json.RawMessage](rawRequest, auth)
	if err != nil {
		return newError("", api.UserMessageParseError, err.Error())
	}
	msg, err := g.codec.DecodeJSONRequest(jsonRequest)
	if err != nil {
		return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
	}
	if len(jsonRequest.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return newError(jsonRequest.ID, api.UserMessageParseError, "request ID is too long: "+strconv.Itoa(len(jsonRequest.ID))+". max is 200 characters")
	}
	var isLegacyRequest = false
	var h handlers.Handler
	var handlerKey string
	if msg == nil || msg.Body.DonId == "" {
		serviceName := jsonRequest.ServiceName()
		if handler, ok := g.serviceToMultiHandler[serviceName]; ok {
			h = handler
			handlerKey = serviceName
		} else if donID, ok := g.serviceNameToDonID[serviceName]; ok {
			// Fallback to legacy service name -> DON ID mapping
			if handler, ok := g.handlers[donID]; ok {
				h = handler
				handlerKey = donID
			}
		}
		if h == nil {
			return newError(jsonRequest.ID, api.HandlerError, "Service name not found: "+serviceName)
		}
	} else {
		// Legacy request with DON ID - validate and fetch handler
		isLegacyRequest = true
		if err = msg.Validate(); err != nil {
			return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
		}
		handlerKey = msg.Body.DonId
		var ok bool
		h, ok = g.handlers[handlerKey]
		if !ok {
			return newError(jsonRequest.ID, api.UnsupportedDONIdError, "Unsupported DON ID: "+handlerKey)
		}
	}

	startTime := time.Now()
	var method string
	callback := handlerscommon.NewCallback()
	if isLegacyRequest {
		method = msg.Body.Method
		err = h.HandleLegacyUserMessage(ctx, msg, callback)
	} else {
		method = jsonRequest.Method
		err = h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)
	}
