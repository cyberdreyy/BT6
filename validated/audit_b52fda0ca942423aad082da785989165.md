### Title
Missing method allowlist check in `handler.HandleJSONRPCUserMessage` allows arbitrary attacker-chosen JSON-RPC method+payload to be relayed to every DON member node - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`handler.HandleJSONRPCUserMessage` in the confidential-relay gateway handler validates only `req.ID` (non-empty, ≤200 chars) and then unconditionally calls `h.newActiveRequest` and `h.fanOutToNodes`, without ever checking `req.Method` against the handler's declared method set (`MethodSecretsGet`, `MethodCapabilityExec`) returned by `h.Methods()`. Combined with a single-handler bypass in `multiHandler.getHandler`, any caller authorized to reach this handler's endpoint can submit an arbitrary `Method` string and arbitrary `Params` payload that gets forwarded verbatim to every node in `h.donConfig.Members` via `h.don.SendToNode`.

### Finding Description
The relevant code path is:

1. `gateway.ProcessRequest` (core/services/gateway/gateway.go:218-292) decodes the raw request and dispatches to a handler (`serviceToMultiHandler[serviceName]`) via `h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)`. There is no method allowlisting at this layer. [1](#0-0) 

2. If the configured service has only one handler type registered (a common single-handler-per-service setup, e.g. `confidentialrelay` alone), `multiHandler.getHandler` **bypasses the `methodToHandler` map lookup entirely** and returns the sole handler regardless of the requested method: [2](#0-1) 

3. The confidential-relay `handler.HandleJSONRPCUserMessage` then performs only ID-length validation and never checks `req.Method` against `h.Methods()` (`MethodSecretsGet`, `MethodCapabilityExec`), before creating an `activeRequest` and calling `h.fanOutToNodes`: [3](#0-2) 

4. `fanOutToNodes` sends the raw, attacker-controlled `ar.req` (method + `json.RawMessage` params, unbounded in size) to every node in `h.donConfig.Members` via `h.don.SendToNode`, with no method/schema validation applied anywhere in between: [4](#0-3) 

Because `Methods()` is only used to build the `multiHandler.methodToHandler` routing table (and is bypassed when only one handler type is configured) and is never consulted inside `HandleJSONRPCUserMessage` itself, an authorized-but-restricted caller of this gateway endpoint can submit `Method="arbitraryMethod"` with a large/malicious `Params` payload, and it will be relayed unmodified to all DON member nodes' websocket connections.

### Impact Explanation
This turns the gateway into an unauthenticated-at-the-application-layer relay for arbitrary JSON-RPC payloads directed at internal node infrastructure, violating the "requests bound to authorized job/method" invariant. Concretely: (a) it can be used to fan out oversized or malformed payloads to all DON nodes simultaneously (amplification / potential DoS vector against node-side JSON-RPC processing), and (b) it removes the intended authorization boundary that node operators rely on ("only `MethodSecretsGet`/`MethodCapabilityExec` requests reach us from the gateway"), which is a scoped authorization-bypass matching Chainlink's "unauthorized action" bounty class rather than node compromise directly (actual impact on nodes depends on node-side handling of unexpected methods, which is outside this function's scope).

### Likelihood Explanation
Requires only the credential/role needed to submit a JSON-RPC request to a gateway service backed by the confidential-relay handler (run-role gateway credential, per the precondition) — no admin/operator access needed. The exploit is a single crafted request; no timing or race conditions are needed, and it is fully repeatable. Likelihood is highest in configurations where a service has exactly one handler type (triggering the `getHandler` single-handler bypass in `core/services/gateway/multihandler.go:84-88`), but even in multi-handler configurations, once a request is routed to `confidentialrelay.handler` for one of its two legitimate methods, nothing stops a still-different unauthorized method value from being embedded — the routing check in `multiHandler.getHandler` only inspects `jsonRequest.Method`, so this specific "arbitrary Method reaching fan-out" issue is exploitable primarily through the single-handler-bypass path.

### Recommendation
In `confidentialrelay/handler.go`'s `HandleJSONRPCUserMessage`, explicitly validate `req.Method` against `h.Methods()` (i.e., `slices.Contains(h.Methods(), req.Method)`) and reject with an error before calling `newActiveRequest`/`fanOutToNodes`. Additionally, remove or gate the single-handler bypass in `multiHandler.getHandler` (core/services/gateway/multihandler.go:84-88) so that method validation against `methodToHandler` always occurs, even when only one handler type is registered.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. `setupHandler(t, N)` to build a handler with a mocked `don` (`don.On("SendToNode", ...)`).
2. Construct `req := jsonrpc.Request[json.RawMessage]{ID: "req-arbitrary", Method: "arbitraryMethod", Params: &largeMaliciousParams}`.
3. Call `h.HandleJSONRPCUserMessage(t.Context(), req, cb)`.
4. Assert the call returns an error (e.g., `require.ErrorContains(t, err, "unsupported method")`) and assert via `don.AssertNotCalled(t, "SendToNode", mock.Anything, mock.Anything, mock.Anything)` that no fan-out occurred.
5. Currently, this test would fail: `err` is `nil` and `SendToNode` is invoked once per DON member, confirming the vulnerability.

func (m *multiHandler) getHandler(method string) (handlers.Handler, error) {
	// If there's only one handler, return it directly.
	// This preserves backwards compatibility for cases where the method
	// isn't specified on responses (and for cases where only one handler is registered more generally).
	if len(m.typeToHandler) == 1 {
		for _, handler := range m.typeToHandler {
			return handler, nil
		}
	}

	handler, ok := m.methodToHandler[method]
	if !ok {
		return nil, errors.New("no handler found for method " + method)
	}

	return handler, nil
}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) fanOutToNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var (
		group      errgroup.Group
		nodeErrors atomic.Uint32
	)

	// Each send is bounded independently. A node whose websocket accepts no writes blocks
	// until its context is cancelled, and because the caller only reads the response callback
	// after this function returns, an unbounded send would hold the request open until the
	// client gives up, discarding a bundle that already reached quorum.
	sendCtx, cancel := context.WithTimeout(ctx, h.nodeSendTimeout)
	defer cancel()

	for _, node := range h.donConfig.Members {
		group.Go(func() error {
			err := h.don.SendToNode(sendCtx, node.Address, &ar.req)
			if err != nil {
				nodeErrors.Add(1)
				l.Errorw("error sending request to node", "node", node.Address, "error", err)
			}
			return nil
		})
	}
