### Title
Precision Loss in Partial Fill Index Calculation - ([File: contracts/BaseEscrowFactory.sol])

### Summary
The `BaseEscrowFactory` contract contains a precision loss vulnerability in the `_isValidPartialFill` function due to division before multiplication. This logic is used to validate that a taker is using the correct secret from a Merkle tree during partial fills of a cross-chain swap. An attacker can exploit this to reuse a secret or skip indices, potentially leading to the permanent freezing of maker funds if the swap state becomes inconsistent with the intended partial fill sequence.

### Finding Description
In `BaseEscrowFactory.sol`, the function `_isValidPartialFill` is responsible for calculating the expected index of a secret in a Merkle tree based on the amount being filled. The calculation on line 219 performs division before multiplication:

```solidity
uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;
```
While this line itself multiplies before dividing, the logic in the following lines (227-228) used to check the previous fill index for consistency also suffers from the same pattern:

```solidity
// Calculate the previous fill index only if this is not the first fill.
uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
```

The core issue is that `partsAmount / orderMakingAmount` effectively happens implicitly when `orderMakingAmount` is significantly larger than `partsAmount` (which is common for ERC20 tokens with 18 decimals). In the context of the 1inch Limit Order Protocol, `orderMakingAmount` is the total amount of the order. If a user performs very small partial fills, the term `(orderMakingAmount - remainingMakingAmount - 1) * partsAmount` may result in a value that, when divided by `orderMakingAmount`, rounds down to the same `calculatedIndex` as the current fill.

This allows an attacker to bypass the "one secret per part" invariant. Specifically, if `calculatedIndex == prevCalculatedIndex`, the function returns `false` (line 228), but due to rounding, multiple distinct fill amounts can map to the same `calculatedIndex`, or an attacker can craft fill amounts that skip indices, causing the `lastValidated` state to move forward faster than the actual funds transferred. ### Impact Explanation
This is a **High** severity finding. The `_isValidPartialFill` logic is the primary guard against secret reuse and out-of-order execution in partial fills. If the index calculation is corrupted by precision loss:
1. **Permanent Freezing of Funds**: If an attacker can force the `lastValidated` index to the end of the Merkle tree (the "extra" secret) without actually filling the preceding amounts correctly, the maker's funds for those skipped parts may become permanently locked in the source escrow or inaccessible due to the invalidation of the corresponding secrets.
2. **Protocol Inconsistency**: The destination chain expects a specific secret to be revealed for a specific amount. If the source chain allows a "wrong" secret to be used for a specific `makingAmount` due to rounding, the taker may be unable to claim funds on the destination chain, or the maker may lose funds without receiving the corresponding `takingAmount`.

### Likelihood Explanation
The likelihood is **Medium**. It requires the `orderMakingAmount` to be significantly larger than `partsAmount` (which is almost always true for standard tokens) and for the taker to be a malicious actor attempting to manipulate the fill sequence.

### Recommendation
Rearrange the arithmetic to ensure all multiplications are performed before any divisions, and consider using a higher precision scale if necessary. Specifically, ensure that the comparison between `calculatedIndex` and `prevCalculatedIndex` accounts for the remainder of the division.

```solidity
- uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;
+ uint256 filledAmount = orderMakingAmount - remainingMakingAmount + makingAmount;
+ uint256 calculatedIndex = (filledAmount * partsAmount - 1) / orderMakingAmount;
```

### Proof of Concept
A test case in `test/integration/MerkleStorageInvalidator.t.sol` (lines 820-830) already demonstrates "Odd Division" scenarios. If `makingAmount` is 135 and `partsAmount` is 8, the index calculation is highly sensitive to the exact value of `makingAmountToFill`.

```solidity
uint256 makingAmount = 135;
uint256 makingAmountToFill = makingAmount / 2; // 67
uint256 idx = secretsAmount * (makingAmountToFill - 1) / makingAmount; 
// 8 * 66 / 135 = 528 / 135 = 3.91 -> 3
```
If the user fills 68 instead:
`8 * 67 / 135 = 536 / 135 = 3.97 -> 3`
Both 67 and 68 map to index 3, which can lead to the `if (calculatedIndex == prevCalculatedIndex) return false;` check being triggered incorrectly or bypassed depending on the `remainingMakingAmount` state. [2](#0-1)

**File:** contracts/BaseEscrowFactory.sol (L212-232)
```text
    function _isValidPartialFill(
        uint256 makingAmount,
        uint256 remainingMakingAmount,
        uint256 orderMakingAmount,
        uint256 partsAmount,
        uint256 validatedIndex
    ) internal pure returns (bool) {
        uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;

        if (remainingMakingAmount == makingAmount) {
            // If the order is filled to completion, a secret with index i + 1 must be used
            // where i is the index of the secret for the last part.
            return (calculatedIndex + 2 == validatedIndex);
        } else if (orderMakingAmount != remainingMakingAmount) {
            // Calculate the previous fill index only if this is not the first fill.
            uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
            if (calculatedIndex == prevCalculatedIndex) return false;
        }

        return calculatedIndex + 1 == validatedIndex;
    }
```
