### Title
`IdleCreditVault` default-recovery basis ignores instant-withdraw receipts from epochs older than `defaultRecoveryEpoch`, so they escape the haircut and can still be claimed at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report's bug class is: a settlement function evaluates what a user is owed using only one balance bucket while ignoring a second legitimate bucket, producing an unfair outcome. In `IdleCreditVault`, `finalizeDefaultRecovery` computes the haircut basis via `defaultPendingClaimBasis()`, which only adds `instantWithdrawClaimsByEpoch[epochNumber]` (the default epoch's instant receipts). However, instant receipts are stored per-epoch (`instantWithdrawsRequestsByEpoch`) while the user-facing payout `claimInstantWithdrawRequest` pays the *aggregate* `instantWithdrawsRequests[_user]`. An instant receipt requested in an earlier epoch that remains unfunded across an epoch boundary is excluded from the haircut basis yet is still paid at par.

### Finding Description
`requestInstantWithdraw` records the receipt under the *current* `epochNumber` and increases the global `pendingInstantWithdraws` (lines 356-375). `pendingInstantWithdraws` only decreases when the CDO calls `collectInstantWithdrawFunds` (line 401), but the epoch number advances at `stopEpoch`/`deposit` regardless of whether all instant receipts were funded (line 610). A receipt recorded under epoch N can therefore survive into epoch N+1 unfunded.

At default finalization, `defaultPendingClaimBasis` (lines 644-649) computes:

```
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

Only the *current* epoch's instant claim basis joins the recovery basis. Similarly, `_defaultPrefundedInstantReserve` (lines 716-723) and `_claimDefaultedInstantWithdrawRequest` (lines 842-856) are keyed exclusively to `epochNumber`/`defaultRecoveryEpoch`. A stale receipt from epoch N is therefore:
- not haircut (excluded from `totalBasis`, so `defaultRecoveryPrice` is computed as if it did not exist), and
- still present in `instantWithdrawsRequests[_user]`.

When the user calls `claimInstantWithdrawRequest` (lines 380-393), `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (zero for this user), then the full aggregate `instantWithdrawsRequests[_user]` — including the unfunded epoch-N receipt — is burned and paid at par through `_transferFundedClaim`.

### Impact Explanation
A holder of an unfunded instant-withdraw receipt from a pre-default epoch receives 100% of face value while all default-epoch claimants and active LPs absorb the `defaultRecoveryPrice` haircut. The payout consumes strategy underlyings that were implicitly reserved for other purposes (the `_transferFundedClaim` guard only excludes `defaultRecoveryReserve`, so any non-reserve balance — residual borrower repayments, partially prefunded funds of other claimants, or recovery dust — is spendable). This dilutes every other claimant's realized recovery and can directly steal funds belonging to funded claimants whose backing sits in the contract but outside the accounted reserve. Analogous to the external report, the protocol assesses the user's position against only one accounting bucket and ignores the second, producing a loss borne by other users.

### Likelihood Explanation
Requires: (1) an instant-withdraw request that stays unfunded across an epoch transition — possible because `epochNumber` increments independently of `pendingInstantWithdraws` and no code clears or rolls `instantWithdrawsRequestsByEpoch` for old epochs; (2) a subsequent borrower default finalized via `finalizeDefaultRecovery`; (3) non-reserve underlying balance in the strategy at claim time. The attacker is an unprivileged tranche-token holder performing ordinary `requestInstantWithdraw` and `claimInstantWithdrawRequest` calls. Privileged roles only perform their honest epoch-stop/collect/default calls; no malicious privileged behavior is needed.

### Recommendation
Make the default-recovery accounting epoch-agnostic for instant receipts: in `defaultPendingClaimBasis`, include the *total* outstanding instant claim basis (e.g., iterate or track an aggregate `instantWithdrawClaimsTotal` alongside `instantWithdrawClaimsByEpoch`), and in `_claimDefaultedInstantWithdrawRequest` clear all of the user's unfunded instant receipt epochs — not only `defaultRecoveryEpoch` — applying `defaultRecoveryPrice` to each. Alternatively, prevent unfunded instant receipts from surviving an epoch boundary by forcing their funding or reverting `stopEpoch` while `pendingInstantWithdraws` attributable to prior epochs is non-zero.

### Proof of Concept
Foundry fork PoC (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testStaleInstantReceiptEscapesDefaultHaircut() external {
    // epoch N: user requests instant withdraw
    uint256 amount = 1000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);

    // request instant withdraw; queue is only partially funded by collectInstantWithdrawFunds
    cdoEpoch.requestInstantWithdraw(trancheBal / 2, address(AAtranche));
    // manager collects less than pendingInstantWithdraws -> pendingInstantWithdraws > 0
    // epochNumber advances to N+1 via stopEpoch/deposit while receipt stays under epoch N key

    _startEpochAndCheckPrices(1);
    // borrower defaults at stopEpoch -> _handleBorrowerDefault -> finalizeDefaultRecovery
    // defaultPendingClaimBasis() counts pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]
    // user's epoch-N instant receipt is NOT in basis -> defaultRecoveryPrice ignores it

    // claim: _claimDefaultedInstantWithdrawRequest clears only epoch N+1 (zero),
    // then amount = instantWithdrawsRequests[user] paid at par via _transferFundedClaim
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 received = underlying.balanceOf(address(this)) - balPre;

    // user got par value; assert recovery claimants' reserve was diluted
    assertEq(received, instantReceiptAmount);        // no haircut applied
    assertLt(defaultRecoveryReserveSpentOnOthers, expected); // others absorb the difference
}
```

Note: I could not fully trace the `IdleCDOEpochVariant` side that gates `claimInstantWithdrawRequest`/`collectInstantWithdrawFunds` timing within the available search budget; the core accounting asymmetry (per-epoch basis vs. aggregate payout in `claimInstantWithdrawRequest` and `defaultPendingClaimBasis`) is confirmed in `IdleCreditVault.sol`, but the exact sequence of honest manager calls needed to leave a cross-epoch unfunded instant receipt should be verified when writing the final PoC.
