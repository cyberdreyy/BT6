### Title
Reward-cycle isolation bypass in `check_submitted_block_proposal` lets a cross-reward-cycle proposal collision wedge a signer into never signing a valid block - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
Every reachable path in `Signer` that looks up a tracked block by `signer_signature_hash` filters the result through `block_lookup_by_reward_cycle`, which discards rows whose `reward_cycle` no longer matches `self.reward_cycle` — this filter exists specifically because the on-disk `signerdb` is shared by every `ConfiguredSigner` instance the node runs concurrently (one per active reward cycle), and the `blocks` table is keyed only by `signer_signature_hash`, not by `(reward_cycle, signer_signature_hash)`. `check_submitted_block_proposal`, the timeout handler for a proposal this signer itself submitted for node validation, is the one path that bypasses this filter and calls the raw, unfiltered `self.signer_db.block_lookup(...)` instead. This is structurally identical to the report's pattern: a safe, filtered reader (`CopyStats` / here `block_lookup_by_reward_cycle`) exists, but one adjacent, network-reachable reader (`Get`/`GetSortedList` / here raw `block_lookup`) skips the same gate.

### Finding Description
`block_lookup_by_reward_cycle` is the sanctioned accessor used by every other block-response handler (`handle_block_proposal`'s reevaluation path, `handle_block_validate_ok`, `handle_block_validate_reject`, `handle_block_pre_commit`, `handle_block_rejection`): [1](#0-0) 

Its own doc comment ("Helper for getting the block info from the db while accommodating for reward cycle") makes clear it exists precisely because the same `signer_signature_hash` primary key row in the shared `blocks` table can belong to a different reward cycle's `Signer` instance than the one currently querying it: [2](#0-1) 

`insert_block` is `INSERT OR REPLACE INTO blocks (... )` keyed by `signer_signature_hash` alone — there is no `(reward_cycle, signer_signature_hash)` composite key, so a row inserted by the reward-cycle-N `Signer` for a given block hash is silently clobbered if the reward-cycle-(N+1) `Signer` (running against the *same* db file) inserts a `BlockInfo` for a block with the identical hash.

The hash collision is trivially producible by a single miner (the "one-slot miner" actor): `signer_signature_hash` is derived only from `NakamotoBlockHeader` fields, not from the wrapping `BlockProposal.reward_cycle`/`burn_height` metadata. A miner can therefore broadcast the *same* block bytes twice — once tagged `reward_cycle = N`, once tagged `reward_cycle = N+1` — during the window where a node is running signer instances for both the outgoing and incoming reward cycles. Each `Signer` instance's `handle_block_proposal` only accepts the copy matching its own `self.reward_cycle`: [3](#0-2) 

...and stores a fresh `BlockInfo` (carrying its own `reward_cycle`) into the shared table: [4](#0-3) 

Now suppose Signer_N submits its copy for node validation and starts tracking `self.submitted_block_proposal`, while Signer_(N+1) later inserts its own row for the identical hash, overwriting the DB row's `reward_cycle` field to `N+1` before Signer_N's node answers. If Signer_N's validation response is slow and its timeout fires, `check_submitted_block_proposal` looks the block up with the **unfiltered** accessor: [5](#0-4) 

This returns the *foreign* row (now tagged `reward_cycle = N+1`, `state = Unprocessed`), which is not what Signer_N submitted. `check_submitted_block_proposal` then marks it `LocallyRejected` and writes it back: [6](#0-5) 

This corrupts Signer_(N+1)'s own, still-unvalidated tracked state for that hash. `BlockInfo::check_state` only allows `PreCommitted` to be reached from `Unprocessed`: [7](#0-6) 

so when Signer_(N+1)'s *own*, genuine node validation later returns OK and `handle_block_validate_ok` fetches the row through the safe, filtered accessor (which now legitimately matches `reward_cycle == N+1`, since the corrupting write preserved that tag), `mark_pre_committed()` fails because the state is already `LocallyRejected`, not `Unprocessed`: [8](#0-7) 

Because the resulting state is neither `GloballyAccepted`/`GloballyRejected` nor `LocallyAccepted`, the handler warns and returns without ever pre-committing, sending a pre-commit, or signing — Signer_(N+1) is now stuck for that block hash despite having validated it as genuinely valid.

### Impact Explanation
This is a liveness wedge on the signer's own equivocation/consensus bookkeeping: a single miner, using only gossip-reachable proposal messages with no majority of signers, another signer's key, or local access, can cause a target signer instance to durably mark a genuinely valid block as `LocallyRejected` before that instance's own validation completes, permanently blocking it from later signing that valid proposal (the `PreCommitted` transition is only reachable from `Unprocessed`). This matches the High-impact category: "a signer wedged into never signing valid blocks." At scale (repeated across the reward-cycle boundary window, or targeting several signers), this degrades the signer set's ability to reach the 70% pre-commit/signature threshold for legitimate blocks during the cycle transition, a liveness risk to tenure/block production during every reward-cycle boundary rather than a one-off edge case.

### Likelihood Explanation
The trigger requires only: (1) a miner able to send identical block bytes with two different `reward_cycle` tags via ordinary StackerDB proposal gossip, and (2) timing so that Signer_N's validation happens to be slower than `block_proposal_validation_timeout` while the reward-cycle-boundary overlap window is active (a normal, recurring operational window, not a rare corner case). No signer collusion, majority, or privileged access is needed — it is reachable purely through the standard block-proposal message path from a single miner.

### Recommendation
Make `check_submitted_block_proposal` use the same safe accessor as every other response handler:
```rust
let mut block_info = match self.block_lookup_by_reward_cycle(&proposal_signer_sighash) {
    Some(block_info) => { ... }
    None => { ... }
};
```
More robustly, close the underlying cause by making the `blocks` table (and every lookup/insert path) key on `(reward_cycle, signer_signature_hash)` instead of `signer_signature_hash` alone, so that concurrently-running reward-cycle `Signer` instances sharing one `signerdb` file can never overwrite each other's rows for a colliding hash, eliminating the need to remember to re-derive the filter at every call site.

### Proof of Concept
1. Node is near a reward-cycle boundary and runs two `Signer` instances against the same `signerdb` file: one for reward cycle `N` (still active) and one for reward cycle `N+1` (already registered).
2. A miner crafts one `NakamotoBlock` and broadcasts it twice over StackerDB as two separate `BlockProposal` messages with identical header/txs (same `signer_signature_hash`) but `reward_cycle = N` and `reward_cycle = N+1` respectively.
3. Signer_N's `handle_block_proposal` accepts its copy, inserts `BlockInfo{reward_cycle: N, state: Unprocessed}`, and submits it to the node for validation, arming `self.submitted_block_proposal`.
4. Shortly after, Signer_(N+1)'s `handle_block_proposal` accepts its copy and calls `insert_block`, which `INSERT OR REPLACE`s the same primary-key row, now tagged `reward_cycle: N+1, state: Unprocessed`.
5. Signer_N's node validation response is delayed past `block_proposal_validation_timeout`; `check_submitted_block_proposal` fires, calls the raw `signer_db.block_lookup(hash)`, fetches the `reward_cycle: N+1` row, marks it `LocallyRejected`, and writes it back — corrupting Signer_(N+1)'s tracked state before Signer_(N+1) ever validated it.
6. Signer_(N+1)'s own validation later returns OK; `handle_block_validate_ok` fetches the row via `block_lookup_by_reward_cycle` (matches, since `reward_cycle == N+1`), calls `mark_pre_committed()`, which fails because the state is `LocallyRejected` (only reachable to `PreCommitted` from `Unprocessed`), and the handler returns without pre-committing or signing — Signer_(N+1) never signs this valid block for its own reward cycle.

            return;

    /// Helper for getting the block info from the db while accommodating for reward cycle
    pub fn block_lookup_by_reward_cycle(
        &self,
        block_hash: &Sha512Trunc256Sum,
    ) -> Option<BlockInfo> {
        let block_info = self
            .signer_db
            .block_lookup(block_hash)
            .inspect_err(|e| {
                error!("{self}: Failed to lookup block hash {block_hash} in signer db: {e:?}");
            })
            .ok()
            .flatten()?;
        if block_info.reward_cycle == self.reward_cycle {
            Some(block_info)
        } else {
            None
        }
    }

    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {

            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
