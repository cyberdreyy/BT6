### Title
Run-role users can trigger unauthorized VRF fulfillment pipeline execution via `RunJobV2` on non-prod builds - ([File: core/services/chainlink/application.go])

### Summary
`ChainlinkApplication.RunJobV2` gates manual job execution only on `build.IsProd()`, and for VRF jobs it synthesizes a fake on-chain log (`testLog`) and feeds it into the job's real pipeline via `ExecuteAndInsertFinishedRun`. Any authenticated user holding only the run role (via GraphQL `runJob` mutation or `POST /v2/jobs/:ID/runs`) can invoke this against a VRF job ID and cause the VRF pipeline (which can include fulfillment transaction submission tasks) to execute end-to-end without any additional authorization check specific to VRF jobs.

### Finding Description
The GraphQL mutation `Resolver.RunJob` requires only `authenticateUserCanRun(ctx)` before calling `r.App.RunJobV2(ctx, jobID, nil)` [1](#0-0) , and the REST endpoint `PipelineRunsController.Create` only requires an authenticated user (`auth.GetAuthenticatedUser`), then likewise calls `prc.App.RunJobV2(ctx, jobID, nil)` [2](#0-1) . Neither path performs any job-type-specific authorization check (e.g., disallowing VRF/on-chain-triggering jobs for run-role users) — the only gate inside `RunJobV2` itself is `build.IsProd()` [3](#0-2) .

When the targeted job is of type `job.VRF`, `RunJobV2` builds a synthetic `types.Log` and derived `vars` map containing `jobSpec`/`jobRun` data (log block hash, tx hash, topics, data) and executes the job's real `PipelineSpec` through `app.pipelineRunner.ExecuteAndInsertFinishedRun(ctx, *jb.PipelineSpec, pipeline.NewVarsFrom(vars), saveTasks)` [4](#0-3) . This is the actual production VRF pipeline spec (parse request → compute proof → submit fulfillment transaction), not a mock/sandboxed pipeline — it is the same `PipelineSpec` used for real on-chain VRF requests. Although the attacker cannot control the specific field values in the synthetic log (seed, sender, fee, requestID are randomly generated), they can trigger full execution of the fulfillment pipeline for that job on demand.

The `build.IsProd()` check is the sole gate; the code comment states "Only used for local testing, not supported by the UI" but there is no server-side feature flag, config toggle, or dedicated admin-only role check enforcing this restriction. In many non-prod/staging/QA deployments (or intentionally, e.g. `IsProd()` returning false in any non-official-release build), this manual-run capability is reachable by any run-role user through the standard GraphQL/REST job-run APIs.

### Impact Explanation
A run-role user (a lower-privilege role than admin/edit) can force execution of a VRF job's real fulfillment pipeline, potentially causing the node to submit an on-chain VRF fulfillment transaction using node funds/keys, outside of any legitimate on-chain VRF request. This matches the "unauthorized job run / fund movement" impact class — an unprivileged/run-role actor triggering unintended on-chain transaction submission using the node's keys without normal admin confirmation.

### Likelihood Explanation
Preconditions: (1) the deployment is a non-prod build (`build.IsProd()` false — common in staging/test/self-hosted or any build not marked as an official production release), and (2) attacker holds a run-role user session/token or valid API credentials for the REST endpoint. Given these, exploitation only requires a single GraphQL `runJob` mutation call or `POST /v2/jobs/:ID/runs` request naming a known VRF job ID — no additional bypass is needed, since the endpoints already accept run-role/authenticated-user credentials by design and forward straight into `RunJobV2` with no VRF-specific gate.

### Recommendation
Restrict `RunJobV2` for job types capable of triggering on-chain transactions (VRF, DirectRequest with fulfillment, etc.) to a higher privilege role (e.g., admin) regardless of build type, or remove the VRF-specific synthetic-log path from the production binary entirely (e.g., build-tag it out of release builds instead of relying solely on a runtime `IsProd()` check). Additionally, add explicit server-side authorization in `Resolver.RunJob` and `PipelineRunsController.Create` to reject manual runs for VRF (and other transaction-emitting) job types unless the caller has admin privileges, and consider logging/blocking this capability outside of dedicated test environments.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a `ChainlinkApplication` test harness with `build.IsProd()` returning false (default test behavior).
2. Create a VRF job via `AddJobV2` with a real `VRFSpec` and `PipelineSpec` containing an ETH-transaction-submission task (mirroring production VRF pipeline).
3. Create a session/user with only the "run" role (not admin) and authenticate against the GraphQL endpoint or REST API.
4. Call GraphQL mutation `runJob(id: "<vrfJobID>")` (exercising `Resolver.RunJob` → `authenticateUserCanRun`) or `POST /v2/jobs/:ID/runs`.
5. Assert: (a) the call succeeds (HTTP 200 / no GraphQL error) despite the run-role-only credential, (b) `PipelineORM().FindRun` returns a completed run for the VRF pipeline, and (c) any transaction-submission task in the pipeline records a queued/submitted transaction in `TxmStorageService()`/`EvmTxStore`, confirming an unauthorized VRF fulfillment transaction was triggered by a run-role actor with no VRF-specific authorization check.
