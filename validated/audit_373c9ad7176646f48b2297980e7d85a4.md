### Title
`GET /v2/bridge_types/:BridgeName` leaks the bridge's `outgoingToken` to any authenticated caller regardless of role - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Show` (registered at `authv2.GET("/bridge_types/:BridgeName", bt.Show)` with no role wrapper) builds its response via `presenters.NewBridgeResource`, which unconditionally copies `OutgoingToken` from the stored `bridges.BridgeType` into the JSON-serialized `BridgeResource` field `OutgoingToken` (tagged `json:"outgoingToken"`, no `omitempty`/redaction). While `IncomingToken` is intentionally only set once at `Create` time and correctly omitted elsewhere, `OutgoingToken` is exposed on every `Show`/`Index`/`Update`/`Destroy` call to any authenticated user, including view-role users.

### Finding Description
- Route registration: `authv2.GET("/bridge_types/:BridgeName", bt.Show)` in `core/web/router.go` (around line 271) has no `auth.RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper, unlike `Create`/`Update`/`Destroy`, meaning any authenticated session/API token (including view-role) can call it.
- `BridgeTypesController.Show` (`core/web/bridge_types_controller.go`, lines 125-146) loads the bridge from `FindBridge` and returns `presenters.NewBridgeResource(bt)` directly with no additional filtering.
- `presenters.NewBridgeResource` (`core/web/presenters/bridges.go`, lines 30-42) sets `OutgoingToken: b.OutgoingToken` unconditionally, and the `BridgeResource.OutgoingToken` field (line 18) has JSON tag `json:"outgoingToken"` without `omitempty` — it is always serialized into the response.
- The comment on `IncomingToken` (line 16: "The IncomingToken is only provided when creating a Bridge") only documents the incoming-token redaction; `OutgoingToken` has no such protection anywhere in the codebase and is emitted for `Show`, `Index`, `Update`, and `Destroy` responses.
- A view-role authenticated user hitting `GET /v2/bridge_types/<name>` therefore receives the bridge's `outgoingToken` (the credential the node uses to authenticate outbound requests to the external adapter) in the JSON response body.

### Impact Explanation
This matches the Chainlink bounty "credential/secret disclosure" impact class: a low-privilege (view-role) authenticated caller can read the outgoing bridge token, which is a secret used by the node to authenticate to external adapters. An attacker holding a low-privilege node account/API token can enumerate bridge names (via `GET /v2/bridge_types`, also unrestricted) and then retrieve each bridge's outgoing token, potentially enabling impersonation of the node to the external adapter or reuse of the token elsewhere.

### Likelihood Explanation
High feasibility and full repeatability: the only precondition is possession of any valid authenticated session or API token (view or run role suffices, since `Show` has no role gate at all). No admin privileges, no misconfiguration, and no race conditions are required — this is deterministic on every call.

### Recommendation
Redact `OutgoingToken` from `BridgeResource` in `presenters.NewBridgeResource` (analogous to how `IncomingToken` is handled), only populating it in the `Create` response (or never returning it via API at all, since it's a secret the client already possesses from creation). Alternatively, add `omitempty` and stop setting it in `NewBridgeResource`, restoring it only through a dedicated one-time flow if needed. Additionally, consider adding an explicit role check (`auth.RequiresEditRole` or higher) on the `Show` route for defense in depth.

### Proof of Concept
Go test plan (extends `core/web/bridge_types_controller_test.go`):
1. Create an application (`cltest.NewApplication`) and an HTTP client authenticated with a view-role session/token (`app.NewHTTPClient(...)` with view role, similar to patterns used elsewhere in `core/web` tests that construct role-specific clients).
2. As an edit/admin-role client, `POST /v2/bridge_types` to create a bridge, capturing the bridge's `OutgoingToken` set server-side (e.g. via `bridges.NewBridgeType` output or by reading `app.BridgeORM().FindBridge`).
3. As the view-role client, `GET /v2/bridge_types/<name>`.
4. Parse the JSON:API response into `presenters.BridgeResource` and assert:
   - `resource.OutgoingToken` is non-empty and equals the bridge's actual outgoing token (demonstrating the leak), OR after the fix, assert `resource.OutgoingToken == ""`/field absent for all roles.
   - `resource.IncomingToken` remains empty (confirming that redaction, unlike `OutgoingToken`, is already correctly enforced).
