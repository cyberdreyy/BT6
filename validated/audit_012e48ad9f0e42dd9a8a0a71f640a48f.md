### Title
Loss-epoch withdrawal receipts escape the haircut when a newer request overwrites `lastWithdrawRequest`, and are paid at par through the funded-claim fallback path - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimWithdrawRequest` decides which recovery policy applies to a user's receipt by looking up a single epoch key — `lastWithdrawRequest[_user]` — in `lossRecoveryPriceByEpoch` and `defaultRecoveryEpoch`. Receipts are tracked per epoch in `withdrawsRequestsByEpoch`, but the loss-adjusted path only inspects the *latest* request epoch. When that lookup "misses" (no `lossRecoveryPriceByEpoch` entry for the newest epoch), an older receipt created in a loss epoch falls through to `_claimFundedWithdrawRequest`, which pays the whole `withdrawsRequests[_user]` aggregate at par. This is the credit-vault analog of the Traefik bug: a per-item policy lookup fails to resolve and the request is routed to the permissive default path.

### Finding Description
- `requestWithdraw` stores the request basis in `withdrawsRequestsByEpoch[_user][currentEpoch]` and sets `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) 
- On a loss stop (`stopEpochWithDuration(_lossAmount)`), the borrower only funds `pendingToFund = claimBasis * lossRecoveryPrice / RECOVERY_FULL`, and the haircut is enforced lazily at claim time via `lossRecoveryPriceByEpoch[lossEpoch]`.
- `claimWithdrawRequest` routes claims: `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and returns early if `lossRecoveryPriceByEpoch[lossEpoch] == 0` [2](#0-1) 
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the aggregate across *all* epochs — at par [3](#0-2) 
- `_clearWithdrawClaimForEpoch` only clears the entry for the epoch it is called with; entries for other epochs stay in `withdrawsRequests[_user]` [4](#0-3) 

Attack sequence (fixed-APR mode, epoch N running):
1. Attacker (any tranche holder) calls `requestWithdraw(X)` during epoch N.
2. Borrower repays only the loss-adjusted amount; manager calls `stopEpochWithDuration(apr, 0, duration, lossAmount)`, recording `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL`.
3. During the buffer of epoch N+1, the attacker calls `requestWithdraw(1 wei tranche)` — `lastWithdrawRequest[user]` becomes N+1.
4. Epoch N+1 ends normally; attacker calls `claimWithdrawRequest`. The loss lookup for epoch N+1 returns 0, so the epoch-N receipt is never haircutted; `_claimFundedWithdrawRequest` pays both receipts at par.

The claim gate `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest` passes because epoch N+1 has ended [5](#0-4) . No skim, default, or reserve guard intervenes: `_transferFundedClaim` only protects `defaultRecoveryReserve`, which is 0 here.

### Impact Explanation
The attacker recovers `X` at par while the vault only received `X * lossRecoveryPrice / RECOVERY_FULL` from the borrower for that receipt. The shortfall `(1 - lossRecoveryPrice) * X` is socialized onto remaining claimants/tranche holders — direct insolvency equal to the escaped haircut. The same shape applies to the default path: a receipt in `defaultRecoveryEpoch` whose `lastWithdrawRequest` was overwritten by a later (post-default) request skips `_claimDefaultedWithdrawRequest`'s `defaultRecoveryPrice` haircut and is paid at par, subject to the post-default request gating.

### Likelihood Explanation
Requires only an unprivileged tranche holder making two `requestWithdraw` calls bracketing a `stopEpochWithDuration` loss event. Loss stops are an honest manager action that occurs precisely when the haircut matters, and re-requesting before claiming is a documented, allowed flow. No privileged cooperation is needed.

### Recommendation
Do not key loss/default recovery on the single `lastWithdrawRequest` marker. In `claimWithdrawRequest`, iterate or track the set of request epochs per user (e.g., a per-user epoch list or a "earliest pending epoch" pointer) and clear each epoch through `_clearWithdrawClaimForEpoch` with its own `lossRecoveryPriceByEpoch`/`defaultRecoveryPrice`, so no receipt can fall through to the par-value `_claimFundedWithdrawRequest` path.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
