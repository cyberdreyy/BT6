Based on my analysis of the staking_contract.move module, I've identified a stronger local analog to the reported bug class. The report's root cause — an implicit invariant ("amounts only increase") baked into arithmetic that isn't actually guaranteed, causing a permanent abort — maps directly onto `update_distribution_pool` in Aptos's `staking_contract.move`.

### Title
Unchecked subtraction in `update_distribution_pool` assumes distribution-pool worth is monotonically increasing, causing permanent DoS of unlock/commission/distribute flows - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`update_distribution_pool` computes `unpaid_commission = (current_worth - previous_worth) * commission_percentage / 100` for every existing shareholder whenever the distribution pool's tracked `total_coins` changes [1](#0-0) . This subtraction implicitly assumes `current_worth >= previous_worth` for every shareholder, i.e., that the pool's `updated_total_coins` only ever increases between calls. This mirrors the reported pattern of an arithmetic operation whose safety silently depends on an unstated invariant that a *different, unrelated* code path can violate — in the Sherlock report it was `Dec*Dec` vs `Int*Dec` overflow behavior; here it is an unguarded subtraction that assumes monotonic growth.

### Finding Description
`update_distribution_pool` is invoked from two places: `add_distribution` (called on every `unlock_stake`/`request_commission`) and `distribute_internal` (called on every `distribute`) [2](#0-1) [3](#0-2) .

Crucially, `add_distribution` passes as `updated_total_coins` the **current `pending_inactive` amount read directly from the stake pool** via `stake::get_stake`, not a value that is guaranteed to only grow [4](#0-3) :
```
let (_, _, _, total_distribution_amount) = stake::get_stake(staking_contract.pool_address);
update_distribution_pool(distribution_pool, total_distribution_amount, operator, staking_contract.commission_percentage);
```
`pending_inactive` stake on the underlying `stake` module is automatically moved into `inactive` once the lockup period expires — this transition happens as part of normal, unprivileged epoch/lockup processing in `stake.move`, independent of whether `distribute()`/`distribute_internal` has been called to flush the `distribution_pool`. When that transition occurs, the stake pool's `pending_inactive` value (and therefore `total_distribution_amount`) can drop relative to the value previously recorded in `distribution_pool.total_coins`.

The next time `add_distribution` (or `distribute_internal`) is invoked with this now-smaller `updated_total_coins`, `update_distribution_pool` recomputes, for each existing shareholder, `current_worth` using the pool_u64 safe multiply-then-divide helper (`pool_u64::shares_to_amount_with_total_coins`, backed by `math64::mul_div`) [5](#0-4) , compares it against `previous_worth` (computed from the old, larger total), and then does raw unchecked subtraction:
```
let unpaid_commission = (current_worth - previous_worth) * commission_percentage / 100;
``` [6](#0-5) 

Since every shareholder's share of a proportionally smaller pool is smaller (`current_worth < previous_worth` for all of them when total coins decreases), this subtraction underflows and the transaction aborts.

### Impact Explanation
Once this state is reached, **every subsequent call** to `unlock_stake`, `request_commission`, `distribute`, `switch_operator`, or `switch_operator_with_same_commission` for that staker/operator pair will re-enter `update_distribution_pool` and abort in the same way, because these are the only code paths that can advance/flush the distribution pool. This permanently:
- Traps the staker's ability to unlock or withdraw further stake through `staking_contract`.
- Traps the operator's/beneficiary's ability to claim already-accrued commission.
- Blocks `distribute()`, meaning already-inactive funds sitting in the stake pool can never be paid out to shareholders.

This is a permanent, non-recoverable loss-of-claim-rights condition on stake, commission, and beneficiary payouts for the affected staking contract, matching the "Stake And Lockup Gate" criteria (permanent lock of claim rights; commission/share-accounting corruption trapping value).

### Likelihood Explanation
No attacker privilege is required. The trigger condition — `pending_inactive` shrinking because lockup expired and stake auto-transitioned to `inactive` between two ordinary staker/operator actions — occurs naturally whenever a staker delays calling `distribute()` across a lockup-cycle boundary while having previously accrued a distribution-pool entry (e.g., prior partial `unlock_stake` or `request_commission`). Any staker or operator on any `staking_contract` pool can end up in this state simply through normal usage patterns and timing, without any adversarial input.

### Recommendation
`update_distribution_pool` should not assume `updated_total_coins`, and hence per-shareholder worth, is monotonically increasing. It should:
- Detect when `updated_total_coins < distribution_pool.total_coins()` (or per-shareholder `current_worth < previous_worth`) and treat that as a decrease (e.g., loss/slashing/lockup-transition) rather than unconditionally computing a positive `unpaid_commission`.
- Use saturating/checked subtraction (e.g., clamp `unpaid_commission` to 0 when `current_worth <= previous_worth`) instead of raw `-`.
- More fundamentally, ensure the value passed into `update_distribution_pool` from `add_distribution` (`pending_inactive` snapshot) is reconciled against `distribute_internal`'s handling of the same pool so the two callers never race the pool through a state where its externally-observed size decreases without the pool being drained/reset first.

### Proof of Concept
Conceptual sequence, purely in terms of existing public entry functions (no special privileges needed):
1. Staker A creates a staking contract, operator gets some `pending_inactive` stake accrued (e.g., staker calls `unlock_stake` for a partial amount). This calls `add_distribution`, which calls `update_distribution_pool` with `updated_total_coins = pending_inactive_1` and buys shares in `distribution_pool` for the staker.
2. Before calling `distribute()`, the stake pool's lockup period elapses; on the next epoch boundary the underlying `stake` module (independent of `staking_contract`) transitions the `pending_inactive` stake into `inactive`. `stake::get_stake`'s 4th return value (`pending_inactive`) now reads a smaller number (or zero) than `pending_inactive_1`, while `distribution_pool.total_coins()` still holds the old, larger `pending_inactive_1` value because `distribute()` was never called to reset it.
3. Staker A (or operator) calls `request_commission` or `unlock_stake` again. This calls `add_distribution` → `update_distribution_pool(distribution_pool, pending_inactive_2, ...)` where `pending_inactive_2 < pending_inactive_1 == distribution_pool.total_coins()`.
4. Inside `update_distribution_pool`, for the existing shareholder, `current_worth` (computed against the smaller `pending_inactive_2`) is less than `previous_worth` (computed against the larger recorded total), so `current_worth - previous_worth` underflows and the transaction aborts [1](#0-0) .
5. From this point, every call into `unlock_stake`, `request_commission`, `distribute`, or `switch_operator*` for this staker/operator pair re-triggers the same abort, permanently freezing the staker's principal in `pending_inactive`/`inactive` state and the operator's unpaid commission.

    /// Return the number of coins `shares` are worth in `self` with a custom total coins number.
    /// `shares` needs to big enough to avoid rounding number.
    public fun shares_to_amount_with_total_coins(self: &Pool, shares: u64, total_coins: u64): u64 {
        // No shares or coins yet so shares are worthless.
        if (self.total_coins == 0 || self.total_shares == 0) {
            0
        } else {
            // Shares price = total_coins / total existing shares.
            // Shares worth = shares * shares price = shares * total_coins / total existing shares.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(shares, total_coins, self.total_shares)
        }
    }

    public fun multiply_then_divide(self: &Pool, x: u64, y: u64, z: u64): u64 {
        math64::mul_div(x, y, z)
    }
