### Title
Unbounded donation-inflated `totalInterestDueNow` mints unbacked strategy tokens and socializes the hole onto tranche LPs - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
The external bug is an authenticated endpoint writing attacker-controlled content into a trusted path that is later executed (arbitrary file → code execution). The analog is `ProgrammableBorrower`'s ERC4626 vault price: an unprivileged "user of the programmable borrower's ERC4626 vault" (explicitly an allowed attacker) writes arbitrary value into the vault's `convertToAssets` via a direct underlying donation. IdleCDO then treats that price as trusted epoch interest and, in minted-interest mode, mints unbacked strategy tokens against it, permanently inflating tranche prices beyond real backing.

### Finding Description
In programmable-borrower mode, `_stopEpoch` resolves interest by calling `IProgrammableBorrower.totalInterestDueNow()` instead of a capped override ( [1](#0-0) ). That value includes vault PnL computed as `convertToAssets(shares) + epochWithdrawnFromVault - (epochStartVaultAssets + epochDepositedToVault) + bufferedVaultDelta` ( [2](#0-1) ). Any ERC4626 vault depositor can raise `convertToAssets` arbitrarily by transferring underlying directly to the vault (donation / share-price inflation), and recover the donation afterward by redeeming their own vault shares.

When `isInterestMinted` is true and the pool is not closing, `_grossInterest` (which now contains the fake donation "yield") is passed to `_strategy.mintStrategyTokens(_grossInterest)`, minting strategy tokens with zero cash backing ( [3](#0-2) ). `_updateAccounting` then distributes this phantom yield into AA/BB tranche prices.

The only bound on resolved interest is the `maxApr` check at line 377-379, which requires `_interest > 1`. For programmable borrowers `_resolveStopEpochInterest` enforces `_interest <= 1` ( [4](#0-3) ), so the cap is unreachable and the vault-reported figure is trusted unbounded. `_skimDonatedAssets` (line 355) only skims donations sent to the CDO itself, not to the external vault.

### Impact Explanation
Broken invariant: fair mint/burn / solvency. For every `D` underlying donated to the vault during a running epoch, the pool mints `D` worth of unbacked strategy tokens and raises `pricePerShare` on both tranches. An attacker holding tranche tokens (any KYC-passing lender) then redeems at the inflated price, extracting up to `D` of other LPs' real backing. The attacker's donation is returned via vault redemption, so the net cost is ~gas. Last withdrawers are left with an insolvent pool short by `D`. Loss is quantified as the donation amount `D`, unbounded.

### Likelihood Explanation
Requires a deployment combining `isProgrammableBorrower` + `isInterestMinted` (the mode `settleBorrowerInterest`/`_mintInterest` is built for) and an ERC4626 vault that accepts donations that move `convertToAssets` (the standard ERC4626 weakness). Trigger is sequencing, not timing luck: deposit tranche tokens, donate to vault during the running epoch, wait for manager's `stopEpoch` (honest actor), redeem tranches at inflated price, redeem vault shares to recover the donation. No privileged cooperation needed.

### Recommendation
Bound the programmable-borrower interest path the same way the override path is: apply the `maxApr` cap check to the resolved interest whenever `_mintInterest` is true, not only when `_interest > 1`. Alternatively, have `ProgrammableBorrower` track vault yield via internal share-price snapshots resistant to in-band donations (e.g., compare against `convertToAssets` at epoch start with a floor, or use a TWAP-style checkpoint in `onStartEpoch`/`onStopEpoch`), so a transient donation cannot be booked as realized epoch interest.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: IdleCDOEpochVariant with isProgrammableBorrower = isInterestMinted = true,
// ProgrammableBorrower pointed at a real ERC4626 vault V (attacker holds shares of V).

// 1. Attacker (KYC'd lender) deposits into AA tranche before epoch start.
// 2. startEpoch() runs; ProgrammableBorrower deposits funds into V.
// 3. Attacker donates D underlying directly to vault V (inflates convertToAssets).
// 4. epochEndDate passes; manager calls stopEpoch(0, 0).
//    _resolveStopEpochInterest returns totalInterestDueNow() = realYield + D.
//    _checkNotAllowed(_interest > 1 && ...) is skipped since _interest == 0.
//    mintStrategyTokens(realYield + D) mints D unbacked tokens; tranche price inflates.
// 5. Attacker redeems tranche tokens at inflated price -> drains real backing.
// 6. Attacker redeems V shares -> recovers donation D.
// Assert: pool NAV - tranche claims == -D; attacker profit ≈ D; last LP withdraw reverts/underpays.
```

Caveat: I could not verify the exact deployment-time wiring (`_checkProgrammableBorrowerMode` requirements and which production pools enable `isInterestMinted`) within the iteration budget; if no minted-interest programmable pool exists, the same donation path in non-minted mode inflates `_expectedInterest` and the subsequent `transferFrom` pull, which fails-closed into `_handleBorrowerDefault` — a borrower-default DoS that the rules exclude. The finding stands specifically for the minted-interest configuration.
