### Title
Builder payment paid twice for the same bid (quorum path + late-confirmation fallback) - ([File: specs/gloas/beacon-chain.md])

### Summary
The Plaza bug (M-1) is a class of "state committed regardless of the preceding process's real success/failure" bug: `BondToken.increaseIndexedAssetPeriod` always records a coupon rate for the period that just ended, even when the corresponding auction failed and no funds actually arrived, letting bondETH holders claim coupons that were never funded. The Gloas (EIP-7732) builder-payment logic in `specs/gloas/beacon-chain.md` has the same shape: a builder's bid payment can be settled twice for the same slot — once through the PTC-attestation quorum path in `process_attestation`/`process_builder_pending_payments`, and again, independently, through the "late confirmation" fallback in `apply_parent_execution_payload` — because neither path checks whether the other has already paid.

### Finding Description
A non-zero bid creates a `BuilderPendingPayment` entry keyed by slot, holding both a `weight` and a `withdrawal` (amount/fee_recipient/builder_index): [1](#0-0) 

`process_attestation` increments `payment.weight` in place for attestations about the *same slot*, but never touches or clears `payment.withdrawal.amount`: [2](#0-1) 

Two independent mechanisms can turn that same `payment.withdrawal` into an actual `BuilderPendingWithdrawal`:

1. **Epoch-boundary quorum path** — `process_builder_pending_payments` pays out any entry whose accumulated `weight` reached quorum, then unconditionally evicts (clears) the slot regardless of outcome: [3](#0-2) 

2. **Direct confirmation path** — when a later block actually references the parent's payload as applied, `apply_parent_execution_payload` calls `settle_builder_payment`, which **unconditionally** re-adds the withdrawal if `payment.withdrawal.amount > 0`, with no check on `weight`/quorum and no check for whether the payment was already settled by path (1): [4](#0-3) [5](#0-4) 

Because `settle_builder_payment` reads `state.builder_pending_payments[payment_index]` and only clears that slot as a *side effect of being called*, while `process_attestation` writes `weight` into the very same slot without ever clearing `withdrawal.amount`, both mechanisms operate on the same underlying data independently of one another. The 2-epoch eviction/fallback logic in the spec text itself acknowledges that a stale bid's payment slot can already be evicted (paid-or-discarded) by the epoch-boundary process before a very-late confirming block shows up — the fallback branch was explicitly added to still pay the builder "regardless" in that case: [6](#0-5) 

This mirrors the Plaza root cause exactly: a value/commitment produced by a preceding process (attestation-quorum weight, i.e., the "auction") is pushed into a payment/settlement step (`settle_builder_payment`, the "coupon distribution") **unconditionally**, without checking whether that preceding process already resolved (paid or rejected) the same commitment.

Concretely, if:
- Block `S+1` includes enough PTC/attestation weight for slot `S`'s bid to reach quorum, and
- A further block within the same 2-epoch settlement window (or, per the explicit fallback, even after eviction) directly references `S`'s payload as its applied parent (satisfying `bid.parent_block_hash == parent_bid.block_hash`),

then `settle_builder_payment` for slot `S` will push a *second* `BuilderPendingWithdrawal` carrying the same `amount`, `builder_index`, and `fee_recipient` on top of the one already pushed by `process_builder_pending_payments`. `process_withdrawals` will then execute both entries and decrease `state.builders[index].balance` twice by `amount` (capped only by the builder's remaining balance) and mint two `Withdrawal`s to `fee_recipient` for a single accepted bid.

### Impact Explanation
This breaks the equality "a builder is paid exactly what it committed to pay for its one accepted bid" — a builder can be charged/paid out twice for one bid, i.e. a builder payment doubled and Gwei paid to the `fee_recipient` beyond what any single bid authorized. Per the report's own severity taxonomy this is explicitly called out as High: "a builder payment or withdrawal misdirected, doubled or escaped." It requires no malicious coalition — only ordinary network conditions (missed/late blocks) that are within the scope of honest, spec-following validators reconstructing the chain, since the spec text itself contemplates and handles the "confirmed 2+ epochs late" case via the `elif parent_bid.value > 0` fallback without cross-checking the quorum path.

### Likelihood Explanation
Reaching the exact double-payment requires a specific but not exotic ordering: quorum reached via attestations in the settling slot's own epoch window while the parent-confirmation of the same slot's payload is delayed into/through a different settlement branch (or is delayed past the 2-epoch window and then resurrected, as the spec's own test `test_builder_payment_after_missed_epochs` demonstrates is a supported code path). It does not require any single actor to misbehave; only imperfect but legitimate block-production timing/network conditions are needed to route the same `BuilderPendingPayment` slot through both settlement code paths.

### Recommendation
Make `settle_builder_payment`/the `apply_parent_execution_payload` fallback and `process_builder_pending_payments` mutually aware of each other's outcome for a given slot: e.g., have `settle_builder_payment` check `payment.weight` or an explicit "already settled" marker before pushing a withdrawal, and have `process_builder_pending_payments` leave a marker (rather than fully clearing amount to zero silently) so a later direct confirmation of the same slot cannot re-push a second `BuilderPendingWithdrawal` for a payment slot that was already resolved (paid or discarded) at the epoch boundary.

### Proof of Concept
Conceptual trace (cannot be executed here, but follows directly from the cited spec functions):
1. Builder `B` submits a non-zero bid for slot `S`; `process_execution_payload_bid` records `BuilderPendingPayment` at `SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH` with `withdrawal.amount = value`, `weight = 0`.
2. Block `S+1` includes attestations for slot `S` from committee members whose combined `effective_balance` exceeds `get_builder_payment_quorum_threshold`; `process_attestation` sets `payment.weight >= quorum` while leaving `payment.withdrawal.amount = value` unchanged.
3. Epoch boundary runs `process_builder_pending_payments`; since `weight >= quorum`, it appends a `BuilderPendingWithdrawal(amount=value, builder_index=B, ...)` to `state.builder_pending_withdrawals`, then evicts the slot.
4. A later block (built by a proposer who obtained slot `S`'s envelope out of band, exactly as in `test_builder_payment_after_missed_epochs`) sets `bid.parent_block_hash == S`'s `block_hash`; `process_parent_execution_payload` calls `apply_parent_execution_payload`, whose `elif parent_bid.value > 0` branch appends a second `BuilderPendingWithdrawal(amount=value, builder_index=B, ...)`.
5. `process_withdrawals` later executes both entries, decreasing `state.builders[B].balance` by `2*value` and minting two EL withdrawals of `value` to `fee_recipient`, for one bid that only committed `B` to pay `value` once.

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
