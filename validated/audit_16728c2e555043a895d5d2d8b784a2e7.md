### Title
`GuardedLaunchUpgradable` base contract has no storage gap, so any future state variable added to it will corrupt the storage layout of all upgradeable `IdleCDO` variants - ([File: contracts/GuardedLaunchUpgradable.sol](contracts/GuardedLaunchUpgradable.sol))

### Summary
`GuardedLaunchUpgradable` is the shared abstract base of `IdleCDO` and every upgradeable variant (`IdleCDOCreditVault`, `IdleCDOEpochVariant`, `IdleCDOEpochVariantPrefunded`, etc.). It declares two storage variables, `limit` (line 23) and `governanceRecoveryFund` (line 25), but reserves no `__gap`. While `IdleCDOStorage` correctly implements a `uint256[43] private __gap` (IdleCDOStorage.sol line 145), that gap sits at the *end* of the storage layout and cannot protect against a new variable inserted earlier in the linearized inheritance chain.

### Finding Description
The deployed proxies (see `.openzeppelin/` manifests) have a storage layout ordered as: `Initializable` → `ContextUpgradeable`/`OwnableUpgradeable`/`ReentrancyGuardUpgradeable` gaps → `GuardedLaunchUpgradable` (`limit`, `governanceRecoveryFund` at the next two slots) → `IdleCDOStorage` (`_lastCallerBlock`, `latestHarvestBlock`, `token`, `guardian`, `strategy`, `AATranche`, `BBTranche`, `priceAA`, `priceBB`, `unclaimedFees`, `feeReceiver`, `isProgrammableBorrower`, `managementFee`, `isBBDepositEnabled`, `__gap`, …).

If a future implementation adds a state variable to `GuardedLaunchUpgradable`, every `IdleCDOStorage` variable shifts down by one slot. `token` would alias `governanceRecoveryFund`, `strategy`/`strategyToken`/`AATranche`/`BBTranche` would alias neighboring values, `priceAA`/`priceBB`/`lastNAVAA`/`lastNAVBB`/`unclaimedFees`/`trancheAPRSplitRatio` would all be misread. Conversely, removing or reordering a variable in `GuardedLaunchUpgradable` causes overlap in the other direction. The `IdleCDOStorage.__gap` cannot compensate because it only reserves space *after* the last declared variable in that contract — the corruption happens before it.

This is the same bug class as the reported `CrossDomainEnabledUpgradeable` finding: a stateful base contract in an upgradeable inheritance hierarchy without reserved storage.

### Impact Explanation
An upgrade that adds even a single variable to `GuardedLaunchUpgradable` (e.g., a new TVL-limit parameter or a second recovery address) permanently corrupts every deployed credit vault / tranche CDO proxy: `token` and tranche addresses would read garbage, `deposit`/`withdraw`/`startEpoch`/`claimWithdrawRequest` would revert or operate on wrong addresses, and vault funds would be permanently frozen or stolen via corrupted `feeReceiver`/`strategy` pointers. Given the number of live proxies in `.openzeppelin/mainnet.json`, `arbitrum-one.json`, `optimism.json`, `base.json`, and `polygon-zk` manifests, this is a realistic upgrade path, not a hypothetical.

### Likelihood Explanation
Likelihood is moderate: it requires a future implementation upgrade that touches `GuardedLaunchUpgradable`'s storage — exactly the kind of change the base contract exists to receive (it is the contract that owns `limit` and the recovery fund, the most plausible fields to extend). The honest-owner assumption does not mitigate it, since the corruption is caused by compiler storage layout, not malicious intent. No existing guard (skim, flags, epoch gating, KYC, only-CDO) prevents it.

### Recommendation
Reserve a storage gap at the end of `GuardedLaunchUpgradable`:

```solidity
// contracts/GuardedLaunchUpgradable.sol
uint256[48] private __gap; // 50 - limit - governanceRecoveryFund
```

and validate with `openzeppelin-upgrades` storage layout checks (`validateUpgrade`/`upgrades.prepareUpgrade`) so any future layout change is caught at deploy time.

### Proof of Concept
A Foundry PoC deploys `IdleCDO` behind a `TransparentUpgradeableProxy`, records `token()`, `AATranche()`, `priceAA()`, then deploys `GuardedLaunchUpgradableV2` with an extra `uint256 public newVar` before the existing fields, upgrades via `ProxyAdmin`, and asserts `token()`/`priceAA()` now return shifted garbage values. The layout diff is already visible by comparing the `GuardedLaunchUpgradable` section (slots ~152–153) in `.openzeppelin/arbitrum-one.json` against `IdleCDOStorage`'s variables beginning immediately after.

Note on scope: this is a contract-upgrade-safety finding rather than a directly attacker-triggerable exploit — it requires an owner-driven upgrade to manifest, but the corruption itself is not owner-mitigable and results in permanent freezing/loss of vault funds, matching the Medium severity of the source report.
