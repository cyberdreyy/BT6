### Title
`internal_ping`'s monotonic balance assertion can be permanently broken by an unprivileged `withdraw`, freezing all pool funds - (File: `staking-pool/src/internal.rs`, `staking-pool/src/lib.rs`)

### Summary
`internal_ping` records `last_total_balance` from the account's current on-chain balance *before* `withdraw`'s outgoing transfer promise is dispatched, because `withdraw`/`withdraw_all` call `internal_ping()` first and `internal_withdraw` second. The transfer permanently removes funds from the account, so on the next epoch's `ping`, `env::account_locked_balance() + env::account_balance() - env::attached_deposit()` is smaller than the stale `last_total_balance`, and the hard `assert!` in `internal_ping` panics on every subsequent state-changing call, bricking the pool.

### Finding Description
The invariant claimed by the code is:
`last_total_balance == env::account_locked_balance() + env::account_balance() - env::attached_deposit()` at the start of every epoch (or the latter is larger, representing rewards).

`internal_ping` enforces this with a hard assert: [1](#0-0) 

Any state-changing entrypoint calls `internal_ping()` before performing its own effect. Crucially, in `withdraw` (and `withdraw_all`), the ping happens *before* the outgoing transfer is created: [2](#0-1) [3](#0-2) 

Sequence:
1. In epoch `E`, an unprivileged account with an available unstaked balance calls `withdraw(amount)`. `internal_ping()` runs first, computing `total_balance = B` from the pool's actual current balance (before the withdrawal leaves), and sets `self.last_total_balance = B`.
2. `internal_withdraw(amount)` then schedules `Promise::new(account_id).transfer(amount)`, which decrements the pool contract's real NEAR balance by `amount` at the point the outgoing receipt is created (confirmed by the README's own description of withdraw transfers moving balance, and by the fact that a *failed* withdraw transfer is explicitly re-credited as a reward in a later ping — meaning a *successful* one is never re-credited): [4](#0-3) 
3. `self.last_total_balance` is left at `B`, but the pool's real balance is now `B - amount`.
4. In epoch `E+1` (or any later epoch), *any* call — from any unprivileged account, including `ping()` itself — invokes `internal_ping()` again. It recomputes `total_balance` from the now-lower real balance. If validator/gas rewards accrued during the interim are smaller than `amount` (trivially true whenever the pool is not actively staking, i.e. `account_locked_balance() == 0`, or whenever the withdrawn amount is larger than one epoch's reward), `total_balance < last_total_balance` and the `assert!` panics, reverting the transaction and leaving `last_total_balance` unchanged (since it is only updated after the assert on the line following it): [5](#0-4) 

Because the assert never succeeds and `last_total_balance` is never lowered, every future call to `ping`, `deposit`, `deposit_and_stake`, `stake`, `stake_all`, `unstake`, `withdraw`, and `withdraw_all` calls `internal_ping()` first and will panic identically forever, unless cumulative rewards eventually exceed the gap `amount` — which never happens if the pool is not an active validator, or happens only after an indefinite time otherwise. No owner-only escape hatch bypasses `internal_ping`, so `assert_owner` provides no relief.

### Impact Explanation
Once triggered, no account can deposit, stake, unstake, withdraw, or even call plain `ping()` on the pool ever again (until/unless rewards outpace the gap, which the attacker can make impossible by targeting an idle or lightly staked pool). All NEAR already staked or held as unstaked-but-unwithdrawn balances in every delegator's account inside that pool becomes permanently inaccessible. This matches the Critical category: funds permanently frozen, with no owner or foundation privilege able to unwind it since the same guard blocks every entrypoint.

### Likelihood Explanation
The only precondition is holding an unstaked balance available for withdrawal in the pool (reachable by anyone who deposits, unstakes, waits the unbonding period, then withdraws) and choosing to withdraw an amount that exceeds the pool's reward accrual for the following epoch(s) — trivially satisfiable on a pool with zero or small locked stake, or simply by withdrawing a large amount. This requires no special privilege, no cooperation from the owner, and no more than normal transaction fees; it is fully repeatable across any staking pool instance deployed from this contract.

### Recommendation
Reorder `withdraw`/`withdraw_all` to perform `internal_withdraw` (or at least reserve/account for the outgoing amount) before computing/recording `last_total_balance` in `internal_ping`, or have `internal_withdraw` subtract the withdrawn amount from `last_total_balance` directly instead of relying on the next `ping` to observe the real account balance difference. More robustly, change the assertion so it derives the reward strictly from tracked balance deltas (deposits/withdrawals accounted internally) rather than from raw `env::account_balance()` snapshots that can be mutated by pending outgoing transfers between pings.

### Proof of Concept
```rust
// staking-pool/src/lib.rs test module (cargo test)
#[test]
fn test_ping_wedge_after_withdraw() {
    let mut emulator = Emulator::new(
        owner(),
        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".to_string(),
        zero_fee(),
    );
    let deposit_amount = ntoy(1_000);
    // bob deposits and immediately has unstaked balance available
    emulator.update_context(bob(), deposit_amount);
    emulator.contract.deposit();
    emulator.amount += deposit_amount;

    // withdraw in epoch E: internal_ping() runs first (captures last_total_balance = B),
    // then internal_withdraw sends `deposit_amount` out, real balance becomes B - deposit_amount
    emulator.update_context(bob(), 0);
    emulator.contract.withdraw(deposit_amount.into());
    emulator.amount -= deposit_amount; // mirror the real balance decrease from the transfer

    // advance one epoch with no compensating reward (locked_amount stays 0 / no growth)
    emulator.epoch_height += 1;

    // any call now panics: total_balance (B - deposit_amount) < last_total_balance (B)
    emulator.update_context(bob(), 0);
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        emulator.contract.ping();
    }));
    assert!(result.is_err(), "ping should have panicked due to the broken monotonic balance assertion");

    // demonstrate permanence: even later epochs with no new deposits keep failing
    emulator.epoch_height += 1;
    emulator.update_context(bob(), 0);
    let result2 = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        emulator.contract.withdraw(0u128.into());
    }));
    assert!(result2.is_err(), "contract remains permanently wedged");
}
```
This asserts the binding `total_balance >= last_total_balance` fails on both sides after a legitimate, unprivileged `withdraw`, and that the wedge persists across subsequent epochs with no recovery path — confirming permanent freezing of pool funds.
