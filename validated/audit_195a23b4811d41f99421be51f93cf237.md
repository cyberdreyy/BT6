### Title
Unbounded recursion in `TrieNode::decode` causes stack exhaustion on attacker-supplied trie preimages - (File: `crates/proof/mpt/src/node.rs`)

### Summary
`TrieNode::decode` recursively decodes nested `Extension` nodes with no depth limit, mirroring the CVE-2018-12641 bug class (unbounded recursive demangling causing stack exhaustion on attacker-controlled input). A malicious preimage supplied through the fault-proof program's `TrieProvider` (backed by an untrusted preimage oracle) can encode thousands of nested, directly-embedded `Extension` nodes inside a single RLP blob, driving unbounded native-stack recursion during trie-node decoding.

### Finding Description
`TrieNode::decode` inspects the RLP header and, for a 2-element list, calls `try_decode_leaf_or_extension_payload`, which for extension prefixes recurses back into `Self::decode(buf)` on the remaining bytes with no depth counter: [1](#0-0) 

The outer `Decodable` implementation dispatches into this same recursive path for every extension/branch encountered: [2](#0-1) 

Unlike Ethereum's blinding rule (nodes ≥32 bytes are referenced by hash and require a separate provider lookup), a sub-node shorter than 32 bytes is embedded directly and RLP-inline, so its decode continues within the *same* buffer and the *same* call stack — there is no intervening hash-lookup boundary to cap nesting depth. An attacker can therefore encode a single preimage blob containing thousands of nested `Extension { prefix: [], node: Extension { ... } }` wrappers (each costing only a few bytes of RLP overhead), producing deep, un-bounded native recursion in one `decode` call.

This decoder is reached by the fault-proof program whenever it resolves a trie node preimage supplied by a (potentially adversarial) preimage oracle/host during dispute-game execution, e.g.: [3](#0-2) 
and the L2 executor's in-memory trie DB: [4](#0-3) 

Notably, the codebase already guards an analogous CBOR parser against exactly this bug class with an explicit depth counter (`MAX_CBOR_NESTING_DEPTH`), showing the pattern is a recognized risk elsewhere but is missing here: [5](#0-4) 

No equivalent `MAX_TRIE_DEPTH`/recursion-depth check exists in `crates/proof/mpt/src/node.rs`.

### Impact Explanation
The MPT crate is the trie backend for `base-proof-executor`, used by the OP-stack-style fault-proof program to derive/verify L1 and L2 state during dispute-game execution. A dispute-game participant able to influence which preimages are served to the program (or a malicious/compromised host serving trie-node preimages for a state root the challenger controls) can construct a deeply-nested extension chain that overflows the fault-proof program's native call stack when `TrieNode::decode` is invoked. A crash mid-execution of the fault-proof program prevents it from computing a provable output root, i.e. a node halt / inability to produce a valid output for that dispute, directly undermining the correctness/liveness of the fault-proof system.

### Likelihood Explanation
Reaching this code path only requires providing an RLP-encoded preimage that `keccak256`-hashes to a hash the program is willing to fetch (e.g., account/storage trie nodes reachable during derivation or output-root computation) — no cryptographic break is needed, only crafting the RLP bytes of the preimage itself. Because extension nodes need only a handful of bytes per nesting level, a preimage well within normal size limits can nest deeply enough to exhaust a typical thread stack.

### Recommendation
Add an explicit recursion/nesting-depth counter to `TrieNode::decode` (and `try_decode_leaf_or_extension_payload`), bounding it to the maximum possible hexary-trie depth (64 nibbles) or a small constant, rejecting decode attempts that exceed it — mirroring the `MAX_CBOR_NESTING_DEPTH` pattern already used in `crates/proof/tee/registrar/src/cbor.rs`.

### Proof of Concept
Construct an RLP-encoded byte string of the form:
```
Extension(prefix=[], node=Extension(prefix=[], node=Extension(prefix=[], node=... Leaf(...))))
```
nested N times (each wrapper only a few bytes), such that the overall RLP length stays within the preimage-fetch limits used by the fault-proof program. Calling `TrieNode::decode(&mut bytes.as_slice())` (as done by `OracleL1ChainProvider::trie_node_by_hash` or the executor's `TrieProvider` implementations) will recurse N times without any bound, exhausting the stack for sufficiently large N and crashing the process.

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
        } else {
            match header.payload_length {
                0 => {
                    buf.advance(header.length());
                    Ok(Self::Empty)
                }
                32 => {
                    let commitment = B256::decode(buf)?;
                    Ok(Self::new_blinded(commitment))
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
        }
    }
