### Title
ProgrammableBorrower.onStopEpoch clears epoch accounting before IdleCDO's `transferFrom` resolves, permanently dropping buffered vault PnL and prepaid buffer interest from defaulted-epoch accounting - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The zcashd bug is a lifetime/order-of-destruction flaw: `txdata` is torn down before the check-queue workers that hold pointers into it are joined — state is released while in-flight consumers still depend on it. The closest structural analog is in the programmable-borrower stop flow: `ProgrammableBorrower.onStopEpoch` mutates and clears the epoch accounting state (`epochAccountingActive`, `epochPendingWithdraws`, `bufferedVaultDelta`, `bufferInterest`, `bufferStartVaultAssets`) *before* `IdleCDOEpochVariant._stopEpoch` performs the actual `transferFrom` pull (`getFundsFromBorrower`). If that pull fails and the CDO takes the catch path into `_handleBorrowerDefault`, the recovery hook `onDefault()` early-returns because `epochAccountingActive` was already set to `false`, so the cleared yield fields are never restored. The result is that realized but unclaimed yield (vault PnL accumulated in `bufferedVaultDelta`, borrower-prepaid `bufferInterest`) is permanently excluded from pool accounting and from the default-recovery basis.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch` the ordering is:

1. `IProgrammableBorrower(_borrower()).onStopEpoch(amount, isClosing)` is called (`contracts/IdleCDOEpochVariant.sol:398`).
2. Only *after* the hook returns `true` does the CDO do `try this.getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)` (`contracts/IdleCDOEpochVariant.sol:408`).
3. On failure, `_handleBorrowerDefault(...)` runs, which calls `IProgrammableBorrower(_borrower()).onDefault()` (`contracts/IdleCDOEpochVariant.sol:583`).

Inside `onStopEpoch` (`contracts/strategies/idle/ProgrammableBorrower.sol:231-268`), after withdrawing vault liquidity, the hook commits irreversible state changes at lines 259-265:

```solidity
bufferedVaultDelta = 0;
bufferInterest = 0;
bufferStartVaultAssets = _currentVaultAssets();
epochPendingWithdraws = 0;
epochAccountingActive = false;
```

If the subsequent `transferFrom` in `getFundsFromBorrower` fails (borrower contract has less on-hand underlying than `_amountRequired` even though the vault sleeve nominally covers the shortfall — e.g., ERC4626 withdraw returning fewer assets than `convertToAssets` implied under fee/share-conversion drift, or a token hook), control reaches `onDefault()` (`contracts/strategies/idle/ProgrammableBorrower.sol:289-301`), whose first statement is:

```solidity
if (!epochAccountingActive) return;
```

Since `onStopEpoch` already set `epochAccountingActive = false`, `onDefault` returns without doing anything — but there is nothing left to restore anyway: `bufferedVaultDelta` and `bufferInterest` are already zeroed. `_vaultNetInterest` (`lines 337-347`) returns `(0,0)` when `!epochAccountingActive`, so `totalInterestDueNow()` permanently drops the buffered vault PnL leg and `bufferInterest` is gone entirely. The corresponding assets still sit in the ProgrammableBorrower contract/vault shares, but they are no longer attributed to the pool: the defaulted-epoch recovery math and subsequent `finalizeDefaultRecovery`/`DefaultDistributor` flows operate on a basis that excludes this yield.

The invariant broken is "no accounting state may be finalized/zeroed before the transaction it describes is known to have settled" — the exact shape of the reference bug (resource released before the consumer that dereferences it has joined). There is no compensating write: `settleBorrowerInterest` is intentionally skipped on the default path (documented at `lines 270-274`), but that only covers `borrowerInterestAccrued`, which does survive — `bufferedVaultDelta`, `bufferInterest` and the `bufferStartVaultAssets` baseline do not.

### Impact Explanation
Loss = `bufferedVaultDelta` (positive vault PnL accrued during the buffer period) + `bufferInterest` (borrower interest already paid in cash during the buffer). These are real assets physically held by the ProgrammableBorrower, but after the ordering violation they are absent from both (a) active-epoch accounting and (b) the post-default recovery distribution, so tranche holders' recovery claims are understated by exactly that amount. The stranded assets remain locked in the borrower adapter with no code path re-attributing them to LPs (`setVault`/`emergencyExitVault` only move them to owner/manager control). This is a permanent loss of unclaimed yield / understated bad-debt recovery, quantified as `uint256(bufferedVaultDelta) + bufferInterest` at the moment of the failed stop.

### Likelihood Explanation
Requires the programmable-borrower mode plus a stop that clears `onStopEpoch` but fails `transferFrom`. The trigger is the honest owner/manager calling `stopEpoch`/`stopEpochWithDuration` once `block.timestamp >= epochEndDate` over a borrower adapter whose on-hand + withdrawable vault assets are nominally sufficient (`shortfall <= _currentVaultAssets()`) yet the actual cash pull short-falls — reachable whenever the ERC4626 vault's `withdraw` delivers less than the `convertToAssets` estimate used at `line 245`, or when prior borrower draws left on-hand below `_amountRequired`. Per the engagement rules this is borderline: the proximate trigger is an honest privileged call and the failure mode resembles a borrower-default scenario; the distinguishing factor is that the yield loss is caused by the state-clearing ordering defect, not by the default itself, and the default-handling code (`onDefault`) is rendered a no-op by it. I could not fully enumerate every `transferFrom` failure path within the iteration budget, so reachability without any borrower-side shortfall is uncertain; the defect itself (commit-then-pull with no compensation) is unambiguous in the code.

### Recommendation
Apply the "join workers before releasing state" fix shape — i.e., do not commit accounting teardown in `onStopEpoch` before the pull resolves:

- Split the hook into two phases: `onStopEpoch` performs only the vault `withdraw` and leaves `epochAccountingActive`, `bufferedVaultDelta`, `bufferInterest`, `epochPendingWithdraws` untouched; add a new `onStopEpochSettled()` called by IdleCDO inside the `try` block *after* `getFundsFromBorrower` and `collectWithdrawFunds` succeed (alongside the existing `settleBorrowerInterest` call), which performs the clearing at `lines 259-265`.
- With that change `onDefault()`'s `if (!epochAccountingActive) return;` guard becomes correct again: on the catch path accounting is still active and `onDefault` clears it in the default branch, preserving the recovery accounting path rather than silently no-oping.
- Alternatively (the "declare `txdata` before `control`" analog): have `onStopEpoch` snapshot the cleared values into transient variables and add an `onStopEpochRevert()` hook that `IdleCDOEpochVariant._handleBorrowerDefault` calls to restore them — more fragile, same trade-off as in the reference report.

### Proof of Concept
Foundry fork test outline (mainnet fork, real `IdleCDOEpochVariant` + `ProgrammableBorrower` wired with a real ERC4626 vault):

```solidity
function test_stopEpoch_clearsAccountingBeforePull() public {
    // Setup: programmable borrower with vault V, epoch running,
    // borrower drew principal during epoch, buffer interest prepaid (bufferInterest > 0)
    // and vault earned positive PnL during buffer (bufferedVaultDelta > 0).
    vm.prank(manager);
    // borrower repays enough that onStopEpoch's vault.withdraw succeeds
    // (shortfall <= vault.convertToAssets(shares)) but leaves ProgrammableBorrower
    // on-hand balance < _amountRequired at transferFrom time — e.g., vault withdraw
    // realizes fewer assets than convertToAssets estimate.
    cdo.stopEpoch(newApr, 0);   // or stopEpochWithDuration

    // transferFrom fails -> catch -> _handleBorrowerDefault -> onDefault() no-ops
    assertTrue(cdo.defaulted());
    assertFalse(pb.epochAccountingActive());
    assertEq(pb.bufferedVaultDelta(), 0);   // real gain dropped from accounting
    assertEq(pb.bufferInterest(), 0);       // prepaid yield dropped from accounting
    // totalInterestDueNow now excludes both legs; recovery basis understated by
    // (prevBufferedDelta + prevBufferInterest)
    assertLt(pb.totalInterestDueNow(), borrowerOwedPlusYield);
}
```

Expected result: `defaulted == true` with `bufferedVaultDelta`/`bufferInterest` zeroed before the pull was known to fail, while the corresponding assets remain stranded in the adapter — demonstrating state teardown preceding the operation that depends on it, with the compensating hook (`onDefault`) disabled by the very flag the teardown cleared.
