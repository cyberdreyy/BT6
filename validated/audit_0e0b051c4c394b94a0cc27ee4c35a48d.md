### Title
KYC/whitelist gating on `requestWithdraw` locks existing tranche holders out of exits after credentials are enabled or revoked - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.requestWithdraw` reverts unless `isWalletAllowed(msg.sender)` passes Keyring, while `claimWithdrawRequest`/`claimInstantWithdrawRequest` do not perform a wallet check. A user who deposited before `keyring`/`keyringPolicyId` was enabled, or whose credential later expires, cannot create a withdrawal request for tranche tokens they still hold, even though claiming already-processed requests remains open.

### Finding Description
The Kyber analog is “entry gated later also gates exit.” In `IdleCDOEpochVariant`, `_deposit` correctly checks `isWalletAllowed(msg.sender)`, but `requestWithdraw` applies the same check to exits:

```solidity
// contracts/IdleCDOEpochVariant.sol
function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
  _checkTranche(_tranche);
  _checkNotAllowed(
    (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
    !isWalletAllowed(msg.sender)
  );
  ...
}
```

`isWalletAllowed` returns true only when `keyring == address(0)` or `IKeyring(keyring).checkCredential(keyringPolicyId, _user)` passes. The queued path has the same issue: `IdleCDOEpochQueue.requestWithdraw` calls `_checkAllowed(msg.sender)`, which requires `cdoEpoch.isWalletAllowed(wallet)`. By contrast, `claimWithdrawRequest` and `claimInstantWithdrawRequest` forward to `IdleCreditVault` without any Keyring check, showing the codebase already treats claims as exit settlement rather than new exposure.

There is no ungated burn/redeem path in the epoch variant comparable to Kyber’s `burnRTokens`; the normal exit requires `requestWithdraw` during the buffer/allowed window and later `claimWithdrawRequest`.

### Impact Explanation
An existing AA/BB tranche holder who is not credentialed under a newly configured Keyring policy, or whose credential expires/is revoked while holding tranche tokens, cannot initiate withdrawal. Their funds remain locked through subsequent epochs until they pass KYC or the owner removes/changes the Keyring config. Because claims are ungated, any already-processed requests remain payable, but new redemption requests are impossible. This is temporary/permanent freezing of principal depending on whether the user can ever satisfy the policy; for a non-KYC-able holder it is effectively permanent.

### Likelihood Explanation
Requires a config or credential state change rather than attacker action: owner/manager enables `keyring` after users deposited, or Keyring credential status changes for an existing holder. These are honest privileged/external events within scope, and the user is then blocked solely by `requestWithdraw`’s wallet gate. The guard is intentional for deposits, but applying it to exit request creation creates the same oversight class as the external report.

### Recommendation
Do not gate exit request creation on current KYC status. Remove `!isWalletAllowed(msg.sender)` from `requestWithdraw`, and remove the wallet-allowed portion of `_checkAllowed` for `IdleCDOEpochQueue.requestWithdraw` while keeping `isEpochRunning` gating. If compliance requires restrictions, gate deposits only and allow all holders to request/claim withdrawals, or add a separate non-KYC redemption path that burns tranche tokens at current epoch pricing.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

import "forge-std/Test.sol";

contract KeyringGateWithdrawPoC is Test {
  // Existing test harness assumed: deploy IdleCDOEpochVariant + IdleCreditVault,
  // with keyring initially unset, then owner calls setKeyringParams.
  function test_existing_holder_cannot_request_withdraw_after_keyring_enabled() public {
    // 1) Alice deposits while keyring == address(0)
    uint256 minted = cdo.depositAA(1000e6); // example underlying decimals
    assertGt(minted, 0);

    // 2) Honest owner later enables Keyring policy that Alice does not satisfy
    vm.prank(owner);
    cdo.setKeyringParams(address(keyring), policyId); // keyring.checkCredential(alice) == false

    // 3) During buffer period, withdrawals are otherwise allowed
    assertTrue(cdo.allowAAWithdrawRequest());
    assertFalse(cdo.isWalletAllowed(alice));

    // 4) Alice cannot create a withdraw request despite holding tranche tokens
    vm.prank(alice);
    vm.expectRevert(NotAllowed.selector);
    cdo.requestWithdraw(minted, address(AAtranche));

    // 5) Claims are not gated, proving settlement does not require KYC
    // A previously processed request can still be claimed by a non-credentialed user.
    vm.prank(alice);
    cdo.claimWithdrawRequest(); // would succeed if alice had a matured request
  }
}
```
