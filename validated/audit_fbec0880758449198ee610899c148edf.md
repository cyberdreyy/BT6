### Title
Own-tenure conflict guard lets a signer sign two conflicting tenure-start blocks in the same tenure when the node has never confirmed the tenure's tip - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The elrond-go advisory concerns a "read-only" evaluation whose intended effect (no state mutation) is bypassed, letting a later action alter state as if the constraint never existed. The signer analog is the deliberate split between a **pre-commit** (explicitly documented as carrying "no signature... commits nothing") and a **signature** [1](#0-0) , combined with a duplicate-block guard that is checked only once, at proposal time, against *signed* blocks — never against pre-commits, and never re-checked later.

### Finding Description
`should_reevaluate_reject_reason`/`validate_tenure_change_payload`'s `DuplicateBlockFound` check runs only when a proposal first arrives, and only counts blocks that have actually been signed (`get_last_signed_block` in v2, `get_last_globally_accepted_block` in v1) [2](#0-1) . A block the signer has only pre-committed to (no signature) is explicitly excluded from this notion of "signed", as codified in the regression test: [3](#0-2) 

and confirmed by the dedicated test `check_tenure_change_accepts_when_only_pre_committed_block_exists`, whose comment states the proposal is accepted "because the signer never signed the pre-committed block" [4](#0-3) .

The only other place a same-tenure conflict is checked is the "own-tenure conflict guard" that runs immediately before the signer actually signs (`handle_block_pre_commit`), documented in the flow diagram: [5](#0-4) 

Critically, that guard's answer depends on `get_tenure_tip(own tenure)` — a query to the stacks-node for whether the tenure has been confirmed at or above this height. If the node has never confirmed *any* block in that tenure (which is exactly the situation for two competing tenure-start proposals still racing for signatures, before either has been accepted on-chain), the guard's own-tenure branch resolves to "never confirmed → SIGN", i.e. it does **not** block signing: [5](#0-4) 

Putting the two together: the proposal-time gate treats "pre-committed but unsigned" as equivalent to "not signed at all" (correctly, since no signature has left the signer), so a second tenure-start block for the same tenure is not rejected as `DuplicateBlockFound`. Both blocks can independently accumulate pre-commits and reach the 70% pre-commit threshold. When each one individually reaches `handle_block_pre_commit`'s signing decision, the *only* remaining safeguard for a same-tenure sibling is the own-tenure guard — and that guard explicitly allows signing when the node has never confirmed the tenure, which is guaranteed to be true for both siblings until one of them is actually pushed to the node. This lets a single signer emit valid signatures over two conflicting (non-canonical relative to each other) blocks in the same tenure, breaking the "one signature per height/tenure slot" equality that the pre-commit/signature split is designed to protect (`docs/signer-flows.md` describes the pre-commit gap as "where most of the subtlety lives") [6](#0-5) .

This is directly analogous to the elrond-go bug class: an operation explicitly designed to be non-committing/read-only (the pre-commit) is treated by a downstream gate as sufficient evidence of "no conflict", while the real commit-time gate (the own-tenure check) is itself gated on external, not-yet-established state (the node's tenure tip), producing a window where the intended invariant (no double-signing within a tenure) does not hold.

### Impact Explanation
This is a Critical-class analog: a single signer signing two conflicting blocks in the same tenure is exactly the "signer signing a conflicting block" case called out in scope. If enough signers hit this window for each of the two tenure-start proposals, both could independently gather 70% signature weight, producing two validly-signed, conflicting blocks for the same tenure/slot — a signing-equality break requiring only a one-slot miner (or anyone who can post two proposals to StackerDB) plus normal gossip timing, not a majority of signers.

### Likelihood Explanation
The `check_tenure_change_accepts_when_only_pre_committed_block_exists` test already demonstrates the "second tenure-start proposal accepted despite a pre-committed sibling" half of the chain unconditionally, with no majority or attacker-key requirement — a single miner simply proposes two competing tenure-start blocks close together, before either is confirmed by the node. The remaining half (own-tenure guard resolving to "never confirmed → SIGN") is the documented default behavior of that check when the node hasn't seen the tenure yet, which is the normal state during the pre-commit race. This makes the likelihood high in exactly the racing-proposal scenario the code comments describe as the reason the guard exists at all.

### Recommendation
Have the own-tenure conflict guard in `handle_block_pre_commit` also treat a locally *pre-committed* sibling in the same tenure as a live conflict (not just signed/accepted ones), or re-run the `DuplicateBlockFound`-style duplicate check against pre-commits (not only against signed blocks) at the pre-commit-threshold/signing step, so that "node never confirmed the tenure" cannot be read as "no conflict exists."

### Proof of Concept
1. Miner proposes tenure-start block A for tenure T. Signer validates and pre-commits to A (`mark_pre_committed`, no signature) — `stacks-signer/src/v0/signer.rs` handle_block_validate_ok path [7](#0-6) .
2. Before A reaches the 70% pre-commit threshold, the miner proposes a second tenure-start block B for the same tenure T (different parent/content). Because `DuplicateBlockFound` only checks signed blocks, and A is only pre-committed, B is accepted for validation and can also be pre-committed, exactly as in `check_tenure_change_accepts_when_only_pre_committed_block_exists` [8](#0-7) .
3. Suppose different subsets of signers' pre-commit messages arrive such that this signer sees A cross 70% pre-commit weight first: `handle_block_pre_commit` runs the own-tenure guard; since T has never been confirmed by the node (neither A nor B has been pushed yet), `get_tenure_tip(own tenure)` returns "never confirmed", so the guard permits signing → the signer signs A (`mark_locally_accepted`).
4. Later, B also crosses 70% pre-commit weight (from a different quorum of signers who preferred B). The same signer re-runs `handle_block_pre_commit` for B; the own-tenure guard again checks `get_tenure_tip`, which is still unconfirmed (A has not yet been pushed to/accepted by this node), so it again resolves to "never confirmed → SIGN" and the signer signs B as well.
5. The signer has now produced valid signatures over two conflicting blocks (A and B) in the same tenure — breaking the intended one-signature-per-tenure-slot guarantee.
