### Title
Signer vote-flip causes double-counted weight across `total_weight_approved` and `total_weight_rejected` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` accumulates per-block acceptance and rejection weight into two independent counters, `block.total_weight_approved` and `block.total_weight_rejected`, gated by two different, non-overlapping guards. A signer that legitimately (or maliciously, via gossip only) sends a `Rejected` response and later a `BlockResponse::Accepted` for the *same* `signer_signature_hash` gets its weight counted into **both** totals, because the guard used for the accept path (`gathered_signatures.contains_key`) is never cleared or checked against the reject path's guard (`responded_signers`), and vice versa. This is directly analogous to the `LiquidityReward` bug: two separate accounting entries (`totalRewardDebt` vs. contract balance) are supposed to move together but can be independently inflated, producing an overestimate of the aggregate value used to make a consensus decision.

### Finding Description
`total_weight_approved` is incremented in the `BlockResponse::Accepted` branch, gated solely on whether the slot already has a stored signature: [1](#0-0) 

`total_weight_rejected` is incremented in the `BlockResponse::Rejected` branch, gated on a *different* set, `responded_signers`: [2](#0-1) 

Both branches insert the slot id into the *same* `responded_signers` set (line 465 for accept, line 515 for reject), but only the reject branch actually uses that set's `insert(..)` return value as a gate for adding weight. The accept branch's gate is `gathered_signatures`, which only ever holds accepted signatures, never rejections.

Consequence: if a signer's slot first sends `Rejected` (weight added to `total_weight_rejected`, slot recorded in `responded_signers`), and later — after a valid state re-evaluation, which is an explicitly supported signer-side transition (`LocallyRejected -> LocallyAccepted`, documented in `docs/signer-flows.md` section 2) — sends `Accepted` for the same block hash, the accept branch's guard (`!gathered_signatures.contains_key(&slot_id)`) is still true, so `total_weight_approved` is incremented too. The signer's weight is now counted in *both* aggregate sums simultaneously, even though only one canonical vote (its most recent one) should be authoritative.

This breaks the intended equality that `total_weight_approved` and `total_weight_rejected` each represent the weight of the *currently outstanding, mutually exclusive* set of accepting/rejecting signers. The aggregated tallies used by the coordinator no longer equal the sum of currently valid distinct votes — exactly the "aggregated-weight vs verified-accepts" class of bug: the weight is verified (real signature, real signer) but the bookkeeping lets a single signer's weight persist in the stale bucket after it moves to the other bucket.

### Impact Explanation
The coordinator (`signer_coordinator.rs`) uses these two counters to decide whether to reject block construction and exclude transactions, or to accept and broadcast the block: [3](#0-2) 

Because a signer's weight can remain "stuck" in `total_weight_rejected` after that signer switches to accepting, the miner/coordinator can compute `total_weight_rejected.saturating_add(weight_threshold) > total_weight` as true using stale rejection weight that no longer reflects the signer's live vote. This can cause the node to wrongly conclude a blocking minority rejected the block (`NakamotoNodeError::SignersRejected`), causing it to permanently or temporarily exclude transactions and abandon a block that a sufficient number of signers actually approve — a liveness wedge on block production driven purely by ordinary vote-flip gossip from a single signer, requiring no majority collusion. Symmetrically, stale approve-then-reject sequences are correctly guarded (the shared `responded_signers` gate blocks re-adding rejection weight after an accept was recorded), so the asymmetry specifically enables the reject→accept direction to inflate `total_weight_approved`'s counterpart bucket (`total_weight_rejected`) beyond what current votes justify.

### Likelihood Explanation
This requires only a single signer (one StackerDB slot) sending two ordinary protocol messages in sequence for the same block hash — no majority or additional key material is needed, and vote re-evaluation (Reject→Accept) is an explicitly designed, expected code path in the signer state machine (`stacks-signer/src/v0/signer.rs`, `signerdb.rs` `BlockState` transitions). Any signer that legitimately changes its mind (e.g., a rejection reason becomes stale and it re-evaluates to accept) will trigger this double count on the node side, independent of intent.

### Recommendation
Track a single canonical "current vote" per slot id (e.g., replace the independent `gathered_signatures`/rejection weight bookkeeping with one map from `slot_id` to `Vote::Accepted(weight)`/`Vote::Rejected(weight)`), and when a new vote for a slot supersedes a prior one, subtract the prior vote's weight from its bucket before adding the new weight to the new bucket, so `total_weight_approved + total_weight_rejected` (restricted to responded signers) never double-counts a single signer's weight across both totals.

### Proof of Concept
1. Node running `StackerDBListener` with `weight_threshold` set to 70% of `total_weight`.
2. Signer S (weight w) proposes/validates block B, and, e.g., due to a stale-conflict reason, sends `BlockResponse::Rejected` for B's `signer_signature_hash`. `stackerdb_listener.rs` line 515-518: `total_weight_rejected += w`, slot recorded in `responded_signers`.
3. The reject reason later becomes stale (per the documented conflict-still-blocks re-evaluation logic in `stacks-signer/src/v0/signer.rs`), and S's signer sends `BlockResponse::Accepted` for the *same* `signer_signature_hash`.
4. `stackerdb_listener.rs` line 443 checks `!block.gathered_signatures.contains_key(&slot_id)` — true, since S's slot has never had an *accepted* signature stored — so `total_weight_approved += w` is executed (line 444-446).
5. Now `block.total_weight_rejected` still includes `w` from step 2, and `block.total_weight_approved` also includes `w` from step 4: S's weight is counted in both totals simultaneously.
6. Depending on other signers' votes, this can make `total_weight_rejected.saturating_add(weight_threshold) > total_weight` evaluate true (line 509-513 of `signer_coordinator.rs`) using stale weight that no longer reflects S's live vote, causing the coordinator to incorrectly return `NakamotoNodeError::SignersRejected` and exclude transactions/abandon the block even though S (and possibly enough others) currently approve.
