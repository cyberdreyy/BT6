### Title
Cross-user response misdelivery in web API trigger callback due to `savedCallbacks` keyed only by client-chosen `MessageId` (no sender binding) - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores the caller's callback in `h.savedCallbacks` keyed solely by `msg.Body.MessageId` [1](#0-0) , and `handleWebAPITriggerMessage` looks up and delivers a DON node's response using only that same `MessageId` [2](#0-1) . Because `MessageId` is a client-chosen field (set from the JSON-RPC request `ID` in `ValidatedMessageFromReq`, up to 128 bytes, uniqueness not enforced across senders) [3](#0-2) [4](#0-3) , two different authenticated-but-unrelated callers who happen to (or deliberately) submit the same `MessageId` will collide in the map, and whichever request wrote last "owns" the callback slot that the first node response fills.

### Finding Description
Every legacy web API trigger request goes through `HandleLegacyUserMessage`, which validates payload/timestamp/method, converts the message to a JSON-RPC request, and then unconditionally stores (overwriting any existing entry) the caller's `Callback` under the raw `msg.Body.MessageId` key:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [1](#0-0) 

There is no check for `ok` on the map write, and no incorporation of `msg.Body.Sender` into the key, unlike the parallel `RequestCache` component in the same package family, which explicitly composes the key from `(sender, id)` and rejects duplicate keys with `"request already exists"` [5](#0-4) . The capabilities handler does not reuse that safer primitive for the legacy trigger path.

When any DON node subsequently returns a `web_api_trigger` response, `handleWebAPITriggerMessage` looks the entry up purely by `MessageId`, deletes it, and delivers the response to whichever `Callback` is currently stored there:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [2](#0-1) 

`MessageId` is fully attacker-controlled: it is taken directly from the JSON-RPC request `ID` field supplied by the caller in `ValidatedMessageFromReq` [3](#0-2) , constrained only to be non-empty, ≤128 bytes, and not ending in a null byte [6](#0-5) . Signature validation binds the request to a `Sender` address (recovered from the ECDSA signature) but does **not** bind or scope `MessageId` uniqueness per sender at the `savedCallbacks` layer. Thus, if a second caller (different signer/sender, e.g. a different workflow owner or external-initiator key holder) submits a request that reuses (guesses, predicts, or races) the same `MessageId` as an in-flight legitimate request, the map entry is silently overwritten. When the DON node then responds to the original `MessageId`, the response is delivered to whichever caller's callback is currently registered under that key — potentially the second, unrelated caller — leaking the first caller's HTTP trigger response (including embedded webhook/HTTP response data) to the wrong party.

### Impact Explanation
This is a cross-user response confusion / information disclosure: an attacker with only the ability to submit their own signed legacy user messages (workflow owner or external-initiator credential, no node/operator access) can, by colliding `MessageId` values, receive the callback data intended for a different, legitimate caller's web API trigger request. This matches the bounty impact class of "unauthorized access to another user's job run result / response cross-delivery leaking one user's workflow result to another."

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or race a legitimate caller's `MessageId`. Since `MessageId` has no server-enforced entropy or uniqueness scoping and is entirely client-supplied, if any calling pattern uses predictable/sequential/reused IDs (e.g., a fixed correlation ID per workflow execution, or an attacker racing many guesses/known naming schemes within the ~120s callback TTL window `defaultCallbackMaxAgeSec`) [7](#0-6) , collision is feasible. The credential bar is low (any account able to send a signed `web_api_trigger` message to the gateway), and the race window is bounded by the callback TTL/prune interval, making repeated attempts practical.

### Recommendation
Scope `savedCallbacks` keys by `(sender, MessageId)` tuple, mirroring the `globalId{sender, id}` pattern already used in `core/services/gateway/handlers/common/requestcache.go`, and reject (rather than silently overwrite) a `NewRequest`/`HandleLegacyUserMessage` call whose composite key already exists in the map. Additionally, validate response messages against the recorded sender/receiver of the original request before delivering the callback.

### Proof of Concept
Go unit test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler `h` with a small `CallbackMaxAgeSec`.
2. Simulate caller A: call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` where `msgA.Body.MessageId = "collide-1"` and `msgA.Body.Sender = addrA` (signed by key A).
3. Before any node responds, simulate caller B: call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` where `msgB.Body.MessageId = "collide-1"` (same ID) but `msgB.Body.Sender = addrB` (signed by key B).
4. Assert (current buggy behavior): `h.savedCallbacks["collide-1"].Callback == callbackB` (A's callback silently evicted).
5. Simulate a DON node response for `MessageId = "collide-1"` via `h.handleWebAPITriggerMessage(ctx, nodeResponseMsg, nodeAddr)`.
6. Assert (current buggy behavior): `callbackB.SendResponse` is invoked with the response, even though the response was intended to satisfy A's original request — demonstrating cross-user delivery.
7. After the fix (composite `(sender, id)` key + duplicate rejection), assert: `HandleLegacyUserMessage` for caller B either succeeds under its own independent key, both callbacks are preserved independently, and the node's response for A's request (correctly correlated via A's sender) is delivered only to `callbackA`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
```
