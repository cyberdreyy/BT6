## Finding

### Title
Gateway responses are routed to pending requests using only the client-supplied `MessageId`, without verifying sender/gateway identity - (File: `core/capabilities/webapi/outgoing_connector_handler.go`)

### Summary
The StarkNet report describes a class of bug where a party consuming a signed/attributed message cannot verify who actually produced it, allowing impersonation. The analogous pattern in this codebase is `OutgoingConnectorHandler.HandleGatewayMessage`, which matches an inbound gateway message to a pending outgoing request solely by `body.MessageId`, without validating that the message actually originated from the gateway/node that the request was sent to, or that `body.Sender`/signature correspond to an authorized DON member for that message.

### Finding Description
`OutgoingConnectorHandler.handleSingleNodeRequest` selects a specific gateway (`selectedGateway`) and sends a signed request keyed by `messageID` [1](#0-0) . When a response arrives, `HandleGatewayMessage` looks up the response channel purely by `body.MessageId` via `c.responses.get(body.MessageId)` [2](#0-1) , and forwards whatever payload is attached to that channel without checking that `gatewayID` matches `selectedGateway`, or that `body.Sender` (or a signature) matches an authorized/expected node.

The message parsing itself, `ValidatedMessageFromReq`, performs only JSON-RPC structural checks and calls `msg.Validate()` — it does not verify any cryptographic signature or sender authorization [3](#0-2) . Rate limiting in `HandleGatewayMessage` is keyed on `body.Sender`, a self-reported field in the payload rather than a cryptographically verified identity [4](#0-3) .

By contrast, `dummyHandler.HandleNodeMessage` demonstrates the intended safeguard is possible: it explicitly compares the transport-layer node address to `msg.Body.Sender` and rejects mismatches [5](#0-4) . `OutgoingConnectorHandler.HandleGatewayMessage` has no equivalent check.

This mirrors the StarkNet root cause conceptually: the entity consuming the message (the requester/UI) has no assurance about who actually produced the content associated with an identifier (message ID / signing account), because the identity-binding check is missing or not enforced at the point of consumption.

### Impact Explanation
If a gateway or any handler on the gateway side (or a compromised/malicious response path) can supply a `MessageId` matching a pending outgoing request, it can inject an arbitrary `api.Message` into that request's response channel via `ch <- msg`, and this becomes the returned response to workflow/capability code such as `HandleSingleNodeRequest` callers (compute actions, HTTP fetch results, workflow-syncer artifacts) [6](#0-5) . Because no sender/gateway verification ties the response back to the gateway that was actually contacted, this is a cross-user/cross-node response confusion primitive that could let one gateway's traffic answer for a request routed to a different, selected gateway.

### Likelihood Explanation
Exploitability depends on factors not fully verifiable from static reading alone — specifically, whether the gateway transport layer (the websocket connector, `AddHandler`, and any per-connection message routing in `connector.go`) enforces that only the specific `gatewayID` that was awaited/selected can deliver a response for a given `MessageId`, and whether signatures are checked upstream of `HandleGatewayMessage`. I was not able to find code that performs this binding inside `HandleGatewayMessage` itself, and `ValidatedMessageFromReq` confirmed no signature check occurs during message parsing. However, I could not fully trace whether an outer layer (e.g., `gatewayConnector.AddHandler` dispatch, or DON membership validation at the websocket handshake level per `network/handshake.go`) restricts which gateways can invoke this handler for a given DON, which would reduce likelihood to "any authenticated DON member/gateway can spoof," rather than any arbitrary external actor.

### Recommendation
In `HandleGatewayMessage`, verify that the responding `gatewayID` matches the gateway selected for that `messageID` (tracked in `awaitContext`/`responses`), and verify `body.Sender` against an expected/allow-listed DON member or verify the message signature before dispatching to the response channel, mirroring the check already present in `dummyHandler.HandleNodeMessage`.

### Proof of Concept
Not independently reproducible from the indexed code alone — a full PoC would require access to the gateway connector's transport-level authentication code path to confirm whether an already-authenticated-but-wrong gateway/node can deliver a spoofed `body.Sender`/payload for a live `messageID` and have it accepted by `HandleGatewayMessage`. This requires running the full connector/gateway stack, which is outside what the indexed context could confirm; I recommend a Devin session with full repo/test access to construct and run this PoC against the `outgoing_connector_handler_test.go` test harness style used in `fetcher_test.go` [7](#0-6) .

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
