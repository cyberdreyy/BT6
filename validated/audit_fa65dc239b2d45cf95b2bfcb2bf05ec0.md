### Title
Cross-user response confusion via unkeyed `savedCallbacks` map in the WebAPI gateway handler's legacy trigger path - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's legacy WebAPI handler stores a pending user callback keyed only by the client-supplied `msg.Body.MessageId`, with no uniqueness check before insertion. An unprivileged client can pick an arbitrary `MessageId` value (bounded only by length checks in `Message.Validate`), so it is possible for two independent, unrelated requests in flight at the same time to collide on this key. This mirrors the LimboDAO bug class: a single shared piece of state that only one "item" (request) can occupy, where the design assumes no interference, but an unprivileged actor can violate that assumption and corrupt behavior for a legitimate third party.

### Finding Description
`HandleLegacyUserMessage` unconditionally overwrites the `savedCallbacks` map entry for the request's `MessageId` with no existence check: [1](#0-0) 

Compare this with the sibling handlers in the same gateway package (confidentialrelay and vault), which explicitly guard against this exact scenario by rejecting a new request when an active request with the same ID already exists: [2](#0-1) [3](#0-2) 

The legacy WebAPI capabilities handler has no equivalent check. When a node later responds, the handler looks up and deletes the callback purely by `MessageId` and delivers the response to whoever is currently registered under that key: [4](#0-3) 

`MessageId` comes directly from the untrusted JSON-RPC request `ID` field / `msg.Body.MessageId`, constrained only by a max-length and non-null-terminator check in `Message.Validate`: [5](#0-4) 

There is no requirement that IDs be unique across senders, and the gateway's top-level `ProcessRequest` performs no cross-sender uniqueness enforcement for legacy requests before dispatching to the handler: [6](#0-5) 

Exploit scenario:
1. Victim sends a legitimate WebAPI trigger request with `MessageId = "X"`. The handler saves victim's callback under `savedCallbacks["X"]` and fans the request out to DON nodes.
2. Before any node responds, an attacker (any unprivileged client that can reach the gateway's legacy endpoint) sends their own request also using `MessageId = "X"`. The handler overwrites `savedCallbacks["X"]` with the attacker's callback, discarding the reference to the victim's callback (the victim's HTTP request is now orphaned — it will hang until the caller's own timeout, since nothing will ever call its `SendResponse`).
3. When a DON node responds to the victim's original relayed request (which was sent to the DON using ID "X"), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback, deletes the entry, and delivers the victim's DON response to the attacker.

This is a genuine cross-user response confusion / request hijacking condition reachable by any unprivileged actor, directly matching the bug class the report describes (shared, single-slot state that assumes serialized, non-adversarial use, but that an unprivileged party can corrupt).

I could not fully confirm from the available index whether an upstream layer (e.g., the connector or DON-side dedup) enforces per-sender ID scoping for the *legacy* message path before it reaches this handler; the JSON-RPC (`HandleJSONRPCUserMessage`) path in this same file explicitly declines to support this legacy call (`return errors.New("capabilities handler does not support JSON-RPC user messages")`), confirming `HandleLegacyUserMessage` is the only path exercised for this handler and it lacks the ID-collision protection present in its sibling handlers.

### Impact Explanation
Successful exploitation lets an attacker receive another user's DON/workflow-trigger response payload (a cross-user response confusion / information-disclosure class issue), and simultaneously causes the victim's original request to hang until timeout (denial of service for that one request). Depending on what data flows through WebAPI trigger responses, this could leak workflow execution results intended for the victim. This does not, on its own, cause a global "stuck forever" state like the LimboDAO case (the map is bounded and pruned by `pruneCallbacks`/`CallbackMaxAgeSec`), so the blast radius is scoped to per-colliding-ID request confusion rather than gateway-wide lockup — this is the key difference from the High-severity LimboDAO original.

### Likelihood Explanation
Likelihood is dependent on the attacker guessing or choosing the same `MessageId` as a victim's in-flight request within the request's lifetime window (bounded by `CallbackMaxAgeSec`, default 120s, and DON round-trip time). If `MessageId` values are generated by callers with low entropy, are otherwise predictable, or are visible/leakable to an attacker (e.g., logs, shared front-end conventions, sequential counters), the collision is trivial to force by simply choosing the same value. If IDs are always high-entropy UUIDs chosen client-side with no leakage channel, practical exploitation requires either observing the victim's ID or brute-forcing within the window, which is harder but not impossible given the ID space is only bounded by an arbitrary max length rather than a cryptographic namespace per sender.

### Recommendation
Scope `savedCallbacks` (and any equivalent map in `dummyHandler`) by `(sender, MessageId)` rather than by `MessageId` alone — consistent with `common/requestcache.go`'s `globalId{sender, id}` pattern already used elsewhere in the gateway package. Alternatively, reject a new legacy request if an active entry for the same `MessageId` already exists, mirroring the `newActiveRequest` uniqueness checks in the confidentialrelay and vault handlers.

### Proof of Concept
1. Start a gateway configured with the legacy WebAPI capabilities handler (`core/services/gateway/handlers/capabilities/handler.go`).
2. Client A sends a valid signed legacy `web_api_trigger` message with `Body.MessageId = "collide-1"`, targeting a DON, and holds the HTTP connection open waiting for a response.
3. Before the DON responds, Client B (attacker, different signer/sender) sends a valid signed legacy `web_api_trigger` message also with `Body.MessageId = "collide-1"`.
4. `HandleLegacyUserMessage` overwrites `h.savedCallbacks["collide-1"]` with Client B's callback (see `core/services/gateway/handlers/capabilities/handler.go:411-414`).
5. When a DON node eventually sends back a response addressed to message ID `"collide-1"` (in response to Client A's forwarded request), `handleWebAPITriggerMessage` (`handler.go:148-162`) looks up and removes `savedCallbacks["collide-1"]`, and delivers the response to Client B instead of Client A.
6. Client A's original HTTP request never receives a response and eventually times out; Client B receives data intended for Client A.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
