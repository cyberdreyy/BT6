This confirms the vulnerability. `delete_member` at [1](#0-0)  only purges requests where the deleted member is the *creator* (`r.member == member`), but never scans the `confirmations` map to strip the deleted member's stale confirmation entries from *other* pending requests they had merely confirmed (not created). The `confirm` function at [2](#0-1)  then blindly trusts `confirmations.len()` against `num_confirmations` without re-validating that each recorded confirmer is still in `self.members`.

### Title
Multisig request can execute below the live-member threshold due to stale confirmations from removed members - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts the size of the `confirmations: LookupMap<RequestId, HashSet<String>>` set against `num_confirmations` to decide whether to execute a pending request [3](#0-2) . When a member is removed via `DeleteMember`, `delete_member` only deletes requests that member *originated* (`r.member == member`) and never removes that member's confirmation entries from other, still-pending requests [4](#0-3) . A confirmation cast by a member who is later removed therefore remains "counted" forever, even though that identity no longer belongs to `self.members`.

### Finding Description
The binding that should hold is: `confirmations counted for a request == confirmations from currently live members`. Instead, `confirmations.len()` can include entries from principals that have since been deleted from `self.members`, because:
- `add_request`/`confirm` add an entry keyed by `member.to_string()` to the `confirmations` HashSet [2](#0-1) .
- `delete_member` removes a member from `self.members` and revokes their access key, but the cleanup loop only targets requests where that member is the *original requester* (`r.member == member`), leaving confirmations they cast on requests created by someone else untouched [5](#0-4) .
- `confirm` never re-checks that entries already present in the `confirmations` set still correspond to current `self.members`; it only validates the new signer via `current_member()` and then simply compares `confirmations.len() as u32 + 1 >= self.num_confirmations` [6](#0-5) .

Consequently a "ghost" confirmation from a removed member persists and is used to satisfy the K-of-N threshold, exactly analogous to the reported Cosmos SDK issue where stale/unvalidated vote-extension data let a proposer misrepresent voting power that the state machine no longer actually backs.

### Impact Explanation
This crosses the threshold/authorization boundary the multisig is designed to enforce: a request (e.g., `Transfer`, `FunctionCall`, `AddKey`) can be executed with fewer than `num_confirmations` *currently valid* signers, because one of the counted confirmations belongs to an account/key that has been deleted from the multisig membership set. This matches the "Critical - a multisig request executed below threshold" impact category, since NEAR (or other resources controlled by the multisig) can move or be reconfigured based on an incorrect confirmation count.

### Likelihood Explanation
Any workflow where a multisig proactively rotates or removes a member (e.g., compromised key, employee offboarding, key rotation) while an unrelated request is still pending confirmation triggers this condition. No special privilege beyond being one of the remaining members is required to supply the final confirmation that completes the stale-inflated count; the flaw is purely in the contract's bookkeeping, not attacker sophistication.

### Recommendation
When deleting a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests created by that member) and remove the deleted member's identifier from every confirmation set. Alternatively, when counting confirmations in `confirm`, filter the stored set to only members still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `multisig2` with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account). `confirmations[R] = {}`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1 < 2, not yet executed).
4. Members later approve a separate self-request `DeleteMember { member: B }` (e.g., because `B`'s key was thought compromised), which executes `delete_member`. This removes `B` from `self.members` and revokes its access key, but since `B` did not create `R`, `R`'s confirmations set is left untouched: `confirmations[R]` still contains `B`.
5. `A` calls `confirm(R)` → `confirmations[R].len() + 1 = 2 >= num_confirmations (2)` → request `R` executes via `execute_request`, even though only `A` is currently a live, trusted member who approved it; `B`'s stale vote made up the rest of the threshold.
