### Title
Post-default instant withdraw requests are co-mingled into the finalized default epoch bucket, corrupting recovery accounting and freezing or stealing user funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` has no post-default handling: it records new instant withdraw receipts into `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `epochNumber` never advances after `finalizeDefaultRecovery`. Because `defaultRecoveryEpoch == epochNumber` stays fixed, every instant request created after finalization is later read back by `_claimDefaultedInstantWithdrawRequest` as if it were a defaulted-epoch claim, exactly the stale-reference/lifetime bug class of the CVE (state read after its logical lifetime ended).

### Finding Description
After `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`, the vault still accepts instant withdraw requests:

- `requestInstantWithdraw` (lines 356-375) burns CDO strategy tokens, mints a par receipt to the user, and adds `_amount` to `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`. There is no `defaultRecoveryFinalized` branch, unlike `requestWithdraw` which routes post-default users into the isolated `postDefaultRequests` path (lines 247-257).

On claim, `claimInstantWithdrawRequest` (lines 380-393) first calls `_claimDefaultedInstantWithdrawRequest`, which uses `defaultRecoveryEpoch` as the lookup key (lines 842-856). Post-default receipts share that key, so:

1. `claimBasis = instantWithdrawsRequestsByEpoch[user][defaultEpoch]` includes the post-default amount.
2. `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` underflows whenever the user's combined basis exceeds the pre-default epoch aggregate (it reverts in Solidity 0.8.10), permanently freezing that user's claim and blocking their exit.
3. Even when it doesn't underflow (other users' defaulted claims keep the bucket large), the post-default receipt is paid at `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` — an unearned haircut on a request created after the loss was already crystallized — while `pendingInstantWithdraws` is clamped to zero and `defaultRecoveryReserve` is debited via `_transferDefaultRecovery`, draining recovery funds meant for defaulted-epoch claimants and leaving later legitimate claimants with `defaultRecoveryReserve -= amount` underflow reverts.

Broken invariant: one receipt, one correctly-priced payout, and isolation of the fixed-size recovery reserve to genuinely defaulted claims.

### Impact Explanation
Any user (KYC-passing lender / tranche holder) who calls `requestWithdraw` in instant mode after default finalization either (a) permanently loses the ability to claim — arithmetic underflow freeze — or (b) receives a haircut they should not bear and simultaneously debits `defaultRecoveryReserve`, causing subsequent `_claimDefaultedInstantWithdrawRequest`/`_claimPostDefaultWithdrawRequest`/`_claimDefaultedWithdrawRequest` calls of other users to revert on `defaultRecoveryReserve -= _amount` underflow (line 915). Result: theft/permanent freezing of recovery-reserve payouts for all remaining defaulted-epoch claimants, quantified as up to the full `instantWithdrawsRequestsByEpoch` excess over `instantWithdrawClaimsByEpoch[defaultEpoch]` and the drained reserve.

### Likelihood Explanation
Requires only that the vault reaches `defaultRecoveryFinalized` (a borrower default — a normal protocol state, not attacker-controlled privilege) and that any user submits an instant withdraw afterward. Nothing gates `requestInstantWithdraw` post-default; no flag, no epoch bump, no revert. The attacker is an ordinary user and the trigger is a single public call sequence.

### Recommendation
In `requestInstantWithdraw`, when `defaultRecoveryFinalized` is true, either revert or route the request through the same post-default mechanism as `requestWithdraw` (par-priced `postDefaultRequests`-style bucket paid 1:1 from reserve). Additionally, key defaulted instant claims by the recorded request epoch rather than assuming `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` only contains pre-finalization amounts, e.g. snapshot per-epoch buckets at finalization or bump a monotonically increasing receipt-epoch counter inside `finalizeDefaultRecovery`.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  /// @notice claim the instant withdraw request
  /// @dev we transfer the underlying tokens
  /// @param _user address of the user
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
