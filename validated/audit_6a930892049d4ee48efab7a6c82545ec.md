### Title
External-initiator credentials satisfy the `isUser` check and can trigger `RunJobV2` for arbitrary int32 job IDs with no initiator-to-job binding enforced - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates numeric job-ID runs on `auth.GetAuthenticatedUser(c)` returning `true`, but `AuthenticateExternalInitiator` unconditionally sets the same `SessionUserKey` to a synthetic `&clsessions.User{Role: UserRoleRun}`, making any valid external-initiator (EI) credential indistinguishable from a real user for this check. Since no code path checks that the EI is actually associated with the target job ID, any holder of a valid EI AccessKey/Secret pair can invoke `RunJobV2` for any int32 job ID on the node.

### Finding Description
In `core/web/pipeline_runs_controller.go`: [1](#0-0) 

the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," but the actual gate is `_, isUser := auth.GetAuthenticatedUser(c)`, which merely checks whether *any* `*clsessions.User` object was stored under `SessionUserKey` in the gin context — it does not distinguish whether that object originated from a real session/token authentication or from EI authentication.

In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` performs this exact substitution: [2](#0-1) 

Because `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` is executed for every successfully authenticated EI request, `auth.GetAuthenticatedUser(c)` returns `(user, true)` exactly as it would for a genuine user session. The `ExternalInitiator` struct (`ei` from `store.FindExternalInitiator`) is stored separately under `SessionExternalInitiatorKey`, but `Create` never reads or checks that value against the requested job ID — there is no job-binding validation anywhere in `Create`.

The intended invariant — that an EI/gateway credential is scoped to a single job/bridge it was registered for — is not implemented at the HTTP-route level for this endpoint. As a result, if the `/v2/jobs/:ID/runs` POST route (or any route reachable with `AuthenticateExternalInitiator` in its authentication chain) is used with EI credentials, the credential holder can supply an arbitrary int32 job ID belonging to any job on the node — including jobs never configured to use that initiator — and `prc.App.RunJobV2(ctx, jobID, nil)` will be invoked and a `pipelineRun` resource returned on success.

### Impact Explanation
This breaks request/credential binding: an attacker who legitimately holds credentials for one external initiator (e.g., a low-trust bridge integration) can trigger pipeline runs for unrelated jobs on the node, potentially including flux monitor/keeper/OCR-adjacent jobs that perform on-chain writes or consume paid external adapter calls, resulting in unauthorized job execution, resource exhaustion (spamming runs), or unintended on-chain transactions depending on job task graphs. This matches the "unauthorized job run" / authorization-bypass impact class.

### Likelihood Explanation
The only precondition is possession of any valid `AccessKey`/`Secret` for any registered `ExternalInitiator` on the node — no special privilege, admin access, or targeting of the specific victim job's initiator is required. This is a low/no-privilege external initiator holder, matching the allowed attacker model. The exploit is a single authenticated HTTP POST and is fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, explicitly check whether the request was authenticated via `AuthenticateExternalInitiator` (e.g., via `auth.GetAuthenticatedExternalInitiator(c)`) and reject int32-ID runs for that case, rather than relying solely on `GetAuthenticatedUser`. If EI-triggered runs by job ID must be supported, validate that the resolved `ExternalInitiator` is bound to the target job (e.g., matching `job.ExternalJobID`/webhook spec configuration) before calling `RunJobV2`.

### Proof of Concept
1. Register two `ExternalInitiator`s, EI-1 and EI-2, and two jobs, Job-A (bound conceptually to EI-1's use case) and Job-B (unrelated, e.g., a cron/direct-request job never configured for EI-1).
2. Send `POST /v2/jobs/<Job-B-ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-1's credentials (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`).
3. Assert the middleware chain accepts the request (EI-1 authenticates successfully) and `auth.GetAuthenticatedUser(c)` returns `(&User{Role: UserRoleRun}, true)`.
4. Assert `PipelineRunsController.Create` proceeds into the `isUser` branch, calls `prc.App.RunJobV2(ctx, Job-B-ID, nil)`, and returns HTTP 200 with a `pipelineRun` resource — despite EI-1 having no configured relationship to Job-B.
5. Compare against expected behavior: the request should be rejected (403/401) since EI-1 is not bound to Job-B.
