### Title
Stale confirmations from removed multisig members can count toward the confirmation threshold, allowing a request to execute below the live-member quorum - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`delete_member()` / `DeleteKey` only purges requests and confirmations for requests **originated** by the removed member/key. Confirmations that removed member added to requests **originated by someone else** are never cleaned up. Since `confirm()` counts raw `confirmations.len()` against `num_confirmations` without re-validating that every counted confirmer is still a live member, a stale confirmation from a member who has since been removed can still push a request over the threshold, letting it execute with fewer live confirming members than the configured quorum.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides execution purely from the size of the stored `HashSet<String>` of confirmer identities: [1](#0-0) 

The only cleanup of stale confirmations happens in `delete_member()`, which filters requests by matching the *creator* field `r.member == member`, then removes those requests' confirmations. It never scans other requests' confirmation sets for entries belonging to the member being removed: [2](#0-1) 

The same pattern exists in the older `multisig/src/lib.rs`, where `DeleteKey` removes only requests whose `signer_pk` (originator) matches the deleted key: [3](#0-2) 

`assert_valid_request()` only checks that the *current caller* is a member; it performs no re-validation of the confirmations already recorded in the set: [4](#0-3) 

This breaks the intended equality: `confirmations counted == confirmations from currently-live members`. Instead the contract enforces `confirmations counted (including stale entries) >= num_confirmations`, which is weaker than the documented quorum guarantee.

### Impact Explanation
Concretely: with members `A, B, C` and `num_confirmations = 2`, `A` creates a request and `B` confirms it (1/2, not yet executable). The multisig later removes `B` via `DeleteMember` (a normal governance action, not requiring any special attacker privilege beyond being a former member). `B`'s stale confirmation on `A`'s request is never purged because `delete_member()` only clears requests *created* by `B`, not requests `B` merely confirmed. When `C` later confirms the same request, `confirmations.len() + 1 == 2 >= num_confirmations`, so the request executes using one confirmation from a member who is no longer part of the multisig. This is exactly the "multisig request executed below threshold" impact category: the effective live-member approval is only 1 (C), not the required 2, yet the contract moves funds/executes actions (`Transfer`, `AddKey`, `FunctionCall`, etc.) as if quorum were met.

### Likelihood Explanation
This does not require any privileged compromise or redeploy — it only requires normal multisig lifecycle activity (a member confirms a request, is later legitimately removed via `DeleteMember`/`DeleteKey`, and a remaining request they had confirmed but did not originate is later completed by others). Given that member turnover and pending long-lived requests (up to `active_requests_limit` outstanding at once, `REQUEST_COOLDOWN` of 15 minutes) are expected operational patterns, this is readily triggerable in normal usage without any social engineering or malicious validator involvement.

### Recommendation
When removing a member/key, iterate over **all** confirmation sets (not just requests the member originated) and strip that member's entry. Alternatively, validate at `confirm()`/execution time that every string in the confirmations set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C], 2)`.
2. `A` calls `add_request_and_confirm(transfer_request)` → 1 confirmation (A).
3. `B` calls `confirm(request_id)` → 2 confirmations recorded, but this itself already meets/exceeds threshold in a 2-of-3 setup with A+B — instead use a 3-of-4 or higher setup, or delay execution: with `num_confirmations = 3` and members `A,B,C,D`: `A` creates & confirms (1), `B` confirms (2) — not yet executable.
4. `A`, `B` (still member at this point), and `C` execute a separate `DeleteMember { member: B }` request to remove `B` (self-request via multisig). This calls `delete_member()`, which does not touch the pending transfer request's confirmations since `B` did not originate it.
5. `D` (or `C`) confirms the pending transfer request → `confirmations.len() + 1 == 3 >= num_confirmations`, and the transfer executes — using `B`'s stale confirmation even though `B` is no longer a member, i.e., the request executed with only 2 live-member confirmations (A, D) against a nominal 3-confirmation policy.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
