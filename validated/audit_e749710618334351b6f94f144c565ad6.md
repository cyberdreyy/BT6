### Title
Vault Gateway Handler skips allowlist/JWT authorization for `GetPublicKey` while every other vault method enforces it - ([File: core/capabilities/vault/gw_handler.go])

### Summary
The `GatewayHandler.HandleGatewayMessage` dispatch in the node-side Vault gateway handler routes `MethodSecretsCreate`, `MethodSecretsUpdate`, `MethodSecretsDelete`, and `MethodSecretsList` through `h.requestProcessor.ProcessRequest`, which performs allowlist/JWT authorization and request validation before any secret data is touched. `MethodPublicKeyGet` is dispatched directly to `h.handlePublicKeyGet` with no authorization or validation step at all, mirroring the ERC4626 bug class where a sibling accessor function (`maxDeposit`/`maxMint`) fails to enforce the same guard (`whenTokenNotPaused`) that its paired functions (`maxWithdraw`/`maxRedeem`) enforce.

### Finding Description
In `HandleGatewayMessage`, the method dispatch explicitly branches: [1](#0-0) 

For `MethodSecretsCreate`/`MethodSecretsUpdate`, `MethodSecretsDelete`/`MethodSecretsList`, the code calls `h.requestProcessor.ProcessRequest(ctx, req, ...)`, which runs the configured `Authorizer` (allowlist-based and/or JWT-based) via `NewGatewayVaultRequestProcessor`: [2](#0-1) 

But for `MethodPublicKeyGet`, the handler calls `h.handlePublicKeyGet(ctx, gatewayID, req)` directly — bypassing `requestProcessor.ProcessRequest` entirely: [3](#0-2) [4](#0-3) 

This is structurally identical to the reported bug class: a set of sibling operations on the same object (here, vault JSON-RPC methods; there, ERC-4626 accessor functions) is supposed to share a common guard (here, `Authorizer`/allowlist-JWT chain; there, `whenTokenNotPaused`), but one function in the group (`maxDeposit`/`maxMint` there, `handlePublicKeyGet` here) omits the check that its siblings (`maxWithdraw`/`maxRedeem` there, Create/Update/Delete/List here) enforce.

### Impact Explanation
Any client capable of reaching the gateway can invoke `MethodPublicKeyGet` without being allowlisted or presenting a valid JWT, since the authorization chain (`Authorizer.AuthorizeRequest`) is never invoked for this method. This is a concrete authentication-bypass for one class of vault requests, inconsistent with the authorization model applied uniformly to all other vault JSON-RPC methods. It also means requests to this method skip the request validator's size/shape checks that gate the other methods, which are also folded into `requestProcessor.ProcessRequest`.

The severity is tempered because the payload returned (`GetPublicKeyResponse`, an asymmetric TDH2 public key) is not itself a secret — it exists to let unauthorized clients encrypt secrets before submission — so no confidential material is disclosed by this specific bypass. Nonetheless, this represents a genuine inconsistency in the authorization/validation guarantee model across sibling handler methods, which mirrors the exact judged-Medium bug class in the source report (breaking of a uniform interface invariant, not necessarily direct fund/secret loss).

### Likelihood Explanation
High: no special conditions are required — any gateway-reachable caller sending a `vault_getPublicKey` (or equivalent `MethodPublicKeyGet`) JSON-RPC request reaches `handlePublicKeyGet` with zero authorization or request-size validation, unlike every other vault method.

### Recommendation
Route `MethodPublicKeyGet` through the same `requestProcessor.ProcessRequest` pipeline (or an explicitly documented, deliberately-unauthenticated but rate/size limited path) used by `MethodSecretsCreate`/`Update`/`Delete`/`List`, so that all vault JSON-RPC methods share a consistent, auditable authorization and validation guard — analogous to overriding `maxDeposit`/`maxMint` in `TokenggAVAX` to match `maxWithdraw`/`maxRedeem`'s pause check.

### Proof of Concept
1. Deploy/observe the Vault `GatewayHandler` wired via `NewGatewayHandler`, which builds `requestProcessor` from `NewGatewayVaultRequestProcessor(requestValidator, authorizer, true, lggr)` [5](#0-4) .
2. Send a JSON-RPC request to the gateway with `Method: vaulttypes.MethodPublicKeyGet` and no `Auth` field / not present in any allowlist.
3. Observe in `HandleGatewayMessage` that the `case vaulttypes.MethodPublicKeyGet` branch calls `h.handlePublicKeyGet` directly without any call to `authorizer.AuthorizeRequest` or `requestProcessor.ProcessRequest` [3](#0-2) , in contrast to the `MethodSecretsList`/`Delete` branch that requires `ProcessRequest` to succeed before proceeding [6](#0-5) .
4. The response is returned to the (unauthorized) caller with no error, confirming the authorization bypass for this method relative to its siblings.

func (h *GatewayHandler) handlePublicKeyGet(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.GetPublicKeyRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	resp, err := h.secretsService.GetPublicKey(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to get public key: %w", err))
	}

	b, err := json.Marshal(resp)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&b),
	}
}
