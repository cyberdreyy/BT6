### Title
Post-default instant-withdraw requests drain the default recovery reserve at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` in `IdleCreditVault` has no post-default handling analogous to the `postDefaultRequests` path in `requestWithdraw`. After `finalizeDefaultRecovery` crystallizes a fixed `defaultRecoveryReserve`, an attacker can open a new instant-withdraw receipt and claim it through `claimInstantWithdrawRequest`, which pays `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim` — i.e., out of strategy-held underlying that is the defaulted claimants' recovery reserve.

### Finding Description
The normal withdraw path was explicitly hardened for the post-default phase: `requestWithdraw` checks `defaultRecoveryFinalized`, blocks users with pending receipts, and routes new requests into `postDefaultRequests` so they are "backed by the reserve" only after the haircut was applied at request time [1](#0-0) . `requestInstantWithdraw` has no such branch — after finalization it still burns CDO strategy tokens, mints a 1:1 receipt to the user, increments `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch[currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]` and `pendingInstantWithdraws` [2](#0-1) .

On the claim side, `claimInstantWithdrawRequest` only diverts into `_claimDefaultedInstantWithdrawRequest` when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, and that helper clears just the receipt recorded at `defaultRecoveryEpoch` [3](#0-2) [4](#0-3) . Whatever remains in `instantWithdrawsRequests[_user]` is then burned and paid **at par** through `_transferFundedClaim`, which transfers underlying held by the strategy — the same balance that constitutes `defaultRecoveryReserve` after finalization [5](#0-4) [6](#0-5) .

Two broken sub-cases:

- **Same-epoch request** (`epochNumber == defaultRecoveryEpoch`, which holds while no new epoch ever starts after default): the new receipt is folded into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, so `_claimDefaultedInstantWithdrawRequest` pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of the reserve and decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` for basis that was never part of the finalized total — corrupting the finalized accounting (potential underflow revert, permanently freezing other claimants' recovery, or unwarranted payouts).
- **Different-epoch or `defaultInstantWithdrawsFinalized == false`**: the defaulted-claim path is skipped entirely and the fresh receipt is paid 1:1 from strategy underlying.

Either way, the fixed `reserveAmount` sized in `finalizeDefaultRecovery` for `totalBasis` of genuine defaulted claimants is spent on post-default requesters [7](#0-6) .

### Impact Explanation
The recovery reserve is sized exactly to `totalBasis` at finalization; every token paid to a post-default instant requester is a token a defaulted-epoch receipt holder or active LP can no longer claim. An attacker (any tranche-token holder able to route a request through the CDO, per the threat model) can request the maximum instant withdraw and immediately claim, draining up to the full `defaultRecoveryReserve`. Last-claiming defaulted users then face reverts/insolvency — direct theft of unclaimed recovery plus permanent freezing of remaining claims. A same-epoch request can also revert inside `_claimDefaultedInstantWithdrawRequest` via underflow on `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis`, DoS-ing the claim path.

### Likelihood Explanation
The trigger is two permissionless calls (`requestInstantWithdraw` then `claimInstantWithdrawRequest`) after `finalizeDefaultRecovery`. The vault itself performs no `defaulted`/`defaultRecoveryFinalized` gating on instant requests — the asymmetry with `requestWithdraw`'s explicit post-default branch indicates the hardened path was simply not mirrored. The residual uncertainty is whether `IdleCDOEpochVariant.requestInstantWithdraw` reverts while `defaulted()` (e.g., via an `allowInstantWithdraw`/epoch-running gate); if it does not — and the codebase deliberately keeps request/claim UX alive after default for normal withdrawals — the exploit is unconditional. Even when `pendingInstantWithdraws == 0` at finalization (fully prefunded instant queue), the par-payment fallback in `claimInstantWithdrawRequest` still pays from held underlying.

### Recommendation
Mirror the normal-request post-default logic in `requestInstantWithdraw`/`claimInstantWithdrawRequest`:
- Revert (or route to an explicit post-default bucket funded independently of `defaultRecoveryReserve`) when `defaultRecoveryFinalized` is true.
- Alternatively, have `_transferFundedClaim` exclude `defaultRecoveryReserve`, or decrement the reserve accounting before any post-finalization instant payout.
- Never let new receipts be written into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` after `defaultRecoveryEpoch` is set.

```solidity
// 1. Deposit AA/BB, startEpoch, let borrower default (stopEpoch with loss /
//    _handleBorrowerDefault) such that defaulted() == true.
// 2. finalizeDefault: borrower/manager supplies recoveredAmount > 0;
//    strategy.finalizeDefaultRecovery sets defaultRecoveryReserve = R,
//    defaultRecoveryPrice < RECOVERY_FULL, defaultRecoveryEpoch = epochNumber.

// 3. Attacker (fresh user holding tranche tokens):

// vault minted `req` receipt tokens; instantWithdrawsRequests[attacker] = req

cdoEpoch.claimInstantWithdrawRequest();
vm.stopPrank();

// 4. Assert theft:
uint256 reserveAfter = strategy.underlyingToken().balanceOf(address(strategy));
assertLt(reserveAfter, R);            // reserve drained
assertGt(underlying.balanceOf(attacker), 0); // attacker paid (at par or recovery price)

// 5. Legitimate defaulted claimant now reverts or is underpaid:
vm.prank(victim);
cdoEpoch.claimInstantWithdrawRequest(); // insolvent / underflow on reserve
```

Honest limitation: I could not confirm within the indexed code whether `IdleCDOEpochVariant.requestInstantWithdraw` blocks calls once `defaulted()` is true; if it does, this vector is unreachable and the missing vault-side guard is defense-in-depth rather than exploitable. The PoC should first check that gate; if the CDO permits the request (consistent with post-default `requestWithdraw` being intentionally supported), the reserve drain is reproducible as written.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
