### Title
User enumeration via distinguishable CreateSession error for non-existent vs. existing accounts - ([File: core/sessions/localauth/orm.go])

### Summary
`orm.CreateSession` returns the raw, unwrapped database error (e.g., a `sql: no rows in result set`-style error) when `FindUser` fails to locate the supplied email, but returns the fixed string `"Invalid password"` when the email exists but the password is wrong. Because these two error values are textually different and are forwarded verbatim to the HTTP response body by `SessionsController.Create`, an unauthenticated caller of `POST /sessions` can distinguish "no such user" from "wrong password" and enumerate valid admin emails.

### Finding Description
`CreateSession` first calls `o.FindUser(ctx, sr.Email)` and, on error, immediately returns that raw error untouched: `return "", err` at [2](#0-1) . For a non-existent email, this is whatever `sqlx`/`database/sql` returns for zero rows (e.g. `sql: no rows in result set`), not a generic message. Only after `FindUser` succeeds does the function reach the `constantTimeEmailCompare` check and the password check, returning the fixed string `"Invalid password"` on mismatch [3](#0-2) . Since `findUser`'s query already matches case-insensitively (`lower(email) = lower($1)`), the "Invalid email" branch is effectively dead code and never fires for a nonexistent account — that case is already caught earlier by the `FindUser` error return.

`SessionsController.Create` (the HTTP handler backing `POST /sessions`) forwards this error directly into the JSON API error body with `jsonAPIError(c, http.StatusUnauthorized, err)` [4](#0-3) , without normalizing to a generic message. Both cases produce HTTP 401, but the response body text differs: a DB "no rows" style error vs. the literal `"Invalid password"`. An attacker sending `POST /sessions` with a set of guessed emails and a fixed wrong password can observe this difference and confirm which emails correspond to real accounts, without any credentials.

Note: the earlier call in the handler to `GetUserWebAuthn(ctx, sr.Email)` (used to decide whether to enable WebAuthn) does not leak account existence, since a non-existent email simply yields an empty WebAuthn list with no error [5](#0-4) .

### Impact Explanation
This falls under Chainlink's "authentication weakness / information disclosure" bounty class as a low-severity information leak: user enumeration of node admin emails. It does not by itself allow authentication bypass or privilege escalation, but it materially aids targeted credential-stuffing or phishing attacks against confirmed valid oracle-node admin accounts, since the pool of accounts to attack can be narrowed from a large guess-list down to only confirmed emails.

### Likelihood Explanation
No preconditions or credentials are required — this is reachable by any unauthenticated caller of `POST /sessions`. It's fully repeatable and cheap: an attacker just submits differing emails with the same known-bad password and diffs the response body text (or content), which will differ deterministically between "email exists" and "email doesn't exist" cases.

### Recommendation
Normalize the error returned by `FindUser` failure in `CreateSession` to the same generic message/format used for the wrong-password path (e.g., always return a constant `"Invalid email or password"` string regardless of whether the email or password check failed), and ensure `SessionsController.Create` does not leak differing error text/format to the client for these two cases. Also verify constant response timing where feasible (already partially addressed by `constantTimeEmailCompare`, but that check is unreachable in the current code and should either be removed or made the sole gate for email validity).

### Proof of Concept
Go unit test plan for `core/sessions/localauth/orm_test.go`:
1. Seed one user with a known email/password hash in the test DB.
2. Call `orm.CreateSession` with an email that does not exist in the DB and a fixed bad password; capture the returned `error.Error()` string.
3. Call `orm.CreateSession` with the seeded user's real email and a wrong password; capture the returned `error.Error()` string.
4. Assert that both calls currently return different error strings (demonstrating the bug) — e.g., non-existent-email error does NOT equal `"Invalid password"`.
5. As the fix verification, after normalizing errors, assert both calls return the identical generic error string/type.

Additionally, a handler-level integration test against `SessionsController.Create` (`POST /sessions`) can assert that the JSON response bodies for "unknown email" and "wrong password" requests are byte-for-byte identical after the fix.

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```
