### Title
Unbounded growth of per-Pubkey `UsageQueueLoaderInner` map in the unified scheduler enables memory/gas-grief DoS via ordinary transactions - (File: unified-scheduler-pool/src/lib.rs)

### Summary
`UsageQueueLoaderInner` maintains a `DashMap<Pubkey, UsageQueue>` that grows by one entry every time an ordinary user transaction references a previously-unseen account key, and is only ever cleaned up on a best-effort, out-of-band basis. Because any signer can cheaply generate new pubkeys (system-program-created accounts, unfunded/never-touched addresses referenced as readonly, etc.) and include them in transactions, an attacker can force this map to grow without any bond, stake, or fee proportional to the long-term resource cost imposed on the validator, mirroring the `activeWorkerIds` unbounded-growth gas-griefing pattern in the external report.

### Finding Description
`UsageQueueLoaderInner::load` inserts a new `UsageQueue` for every unique `Pubkey` seen across scheduled tasks, with no cap enforced at insertion time: [1](#0-0) 

The struct's own documentation explicitly acknowledges the design flaw: *"Currently, the simplest implementation. This grows memory usage in unbounded way. Overgrown instance destruction is managed via `solScCleaner`."* [2](#0-1) 

A secondary `is_overgrown` check exists, but it only compares against `max_usage_queue_count` reactively and is invoked by the pool for scheduler retirement/eviction decisions — it does not prevent an ordinary transaction from inserting an entry, and cleanup relies on a background thread (`solScCleaner`) rather than any per-transaction cost or bound: [3](#0-2) 

Since every account key referenced by any submitted transaction (including readonly and never-before-used accounts, e.g., freshly generated pubkeys that are never funded) causes an entry to be created via `load()`, and Solana account keys are essentially free to generate (no bond, no rent charged merely for being *referenced* as a non-existent account in a transaction that fails cheaply), this is directly analogous to the `activeWorkerIds` array growth in the report: a cheap, unprivileged action by any user creates persistent state that all subsequent scheduling/processing must carry, without the state ever being purged synchronously with the action that created it.

### Impact Explanation
Growth of `usage_queues` increases scheduler memory usage and the cost of `UsageQueueLoaderInner::count()` (called by `is_overgrown`) that is polled by the pool logic, and, since `UsageQueue` entries participate in dependency/ordering tracking for transaction scheduling, an inflated map increases the fixed per-lookup overhead (`DashMap` entry/hashing costs) for every subsequent transaction that happens to reference *any* pubkey, including legitimate users' transactions scheduled after the attacker's. This matches the reported impact class of "high gas costs to users" / degraded throughput for a leader's unified scheduler, and in the extreme could contribute to scheduler retirement/thrash if `max_usage_queue_count` handling and the `solScCleaner` background thread cannot keep pace, but does not directly cause fund loss or consensus divergence.

### Likelihood Explanation
Likelihood is low-to-moderate: unlike the Solidity report where the attacker must lock a bond, here there is effectively **no cost gate at all** on referencing new/unique pubkeys in a transaction (a `TransactionError::AccountNotFound`/similar cheap failure still causes the account key to be loaded/looked up), so the barrier to grow this map is lower than in the original report, but the actual per-entry resource cost (a `DashMap` entry plus an `UsageQueue`) is small and the pool has an `is_overgrown`/cleaner mitigation, which likely bounds real-world impact to a performance degradation rather than an outright DoS.

### Recommendation
Enforce a hard cap on `usage_queues.len()` at insertion time in `UsageQueueLoaderInner::load` (reject/backpressure new tasks referencing accounts once `max_usage_queue_count` is reached) rather than only checking `is_overgrown` after the fact for scheduler retirement, and consider synchronous eviction of used-once/stale `UsageQueue` entries at end-of-session instead of relying solely on the asynchronous `solScCleaner` thread.

### Proof of Concept
Not independently verifiable from static code review alone — reproducing this would require running the unified scheduler under load with transactions that reference a large number of distinct, previously-unseen pubkeys (e.g., readonly references to never-funded accounts) and observing `UsageQueueLoaderInner::count()` growth and its effect on scheduling latency; I was unable to execute or trace this at runtime. /// The primary owner of all [`UsageQueue`]s used for particular [`PooledScheduler`].
///
/// Its `load` method provides `Pubkey`-based multi-thread-friendly `UsageQueue` lookup
/// with automatic population on initial entry misses, fulfilling the Pubkey-UsageQueue 1-to-1
/// mapping responsibility as documented by `UsageQueue`.
///
/// Currently, the simplest implementation. This grows memory usage in unbounded way. Overgrown
/// instance destruction is managed via `solScCleaner`. This struct is here to be put outside
/// `solana-unified-scheduler-logic` for the crate's original intent (separation of concerns from
/// the pure-logic-only crate). Some practical and mundane pruning will be implemented in this type.
#[derive(Debug)]
struct UsageQueueLoaderInner {
    capability: Capability,
    usage_queues: DashMap<Pubkey, UsageQueue>,
}

impl UsageQueueLoaderInner {
    fn new(capability: Capability) -> Self {
        Self {
            capability,
            usage_queues: DashMap::default(),
        }
    }

    fn load(&self, address: Pubkey) -> UsageQueue {
        self.usage_queues
            .entry(address)
            .or_insert_with(|| UsageQueue::new(&self.capability))
            .clone()
    }

    fn count(&self) -> usize {
        self.usage_queues.len()
    }
}

/// Thin wrapper to encapsulate ownership variation of UsageQueueLoaderInner across block
/// verification and production. This is needed to provide a uniform interface for the overgrown
/// check.
#[derive(Debug)]
enum UsageQueueLoader {
    // UsageQueueLoader is owned by this wrapper itself; used by block verification.
    OwnedBySelf {
        usage_queue_loader_inner: UsageQueueLoaderInner,
    },
}

impl UsageQueueLoader {
    fn usage_queue_loader(&self) -> &UsageQueueLoaderInner {
        match self {
            Self::OwnedBySelf {
                usage_queue_loader_inner,
            } => usage_queue_loader_inner,
        }
    }

    fn load(&self, pubkey: Pubkey) -> UsageQueue {
        self.usage_queue_loader().load(pubkey)
    }

    fn is_overgrown(&self, max_usage_queue_count: usize) -> bool {
        if self.usage_queue_loader().count() > max_usage_queue_count {
            return true;
        }

        match self {
            Self::OwnedBySelf {
                usage_queue_loader_inner: _,
            } => false,
        }
    }
}
