### Title
Unbounded blockSubscribe notification payload size scales with attacker-controlled slot log/transaction volume, with no per-notification size cap - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
A single `blockSubscribe` subscription causes `RpcSubscriptions::notify_watchers` to call `blockstore.get_complete_block` and `filter_block_result_txs` for every newly-notified slot, encoding the *entire* block (all transactions, and with `TransactionDetails::Full` all logs/return data) into one JSON-RPC notification string that is sent to that subscriber in a single WebSocket text frame. Neither `RpcNotifier::notify` nor `RecentItems::push` nor the pubsub WebSocket sender enforces a maximum size for a single notification; the only configured limit, `queue_capacity_bytes`, is a rolling eviction budget across the shared recent-items buffer, not a per-notification cap.

### Finding Description
When a slot is notified to `notify_watchers` (`rpc/src/rpc_subscriptions.rs:968-1052`), for each `SubscriptionParams::Block` subscription the code does: [1](#0-0) 

`blockstore.get_complete_block` builds a `VersionedConfirmedBlock` containing *every* transaction and its full metadata (including log messages / return data) for that slot, with no size limiting inside the blockstore read path: [2](#0-1) 

`filter_block_result_txs` then encodes the full (or account-filtered) transaction set with the client-chosen `transaction_details`/`encoding`, again with no size cap: [3](#0-2) 

The result is handed to `RpcNotifier::notify`, which serializes it into a thread-local buffer, wraps it as `Arc<String>`, sends it over an unbounded-size `broadcast::Sender`, and pushes it into `RecentItems`: [4](#0-3) 

`RecentItems::push` only tracks a rolling byte/item budget (`queue_capacity_bytes` / `queue_capacity_items`) and evicts *other* stored items to make room — it never rejects or truncates a single oversized item: [5](#0-4) 

Finally, in the WebSocket connection handler, the notification JSON string is sent as one text frame with no outbound size check — `set_max_message_size`/`set_max_frame_size` are configured only on the receiving side for *incoming* client requests, not for outgoing broadcast payloads: [6](#0-5) 

Because `rpc_pubsub_enable_block_subscription` gates only whether `blockSubscribe` is accepted, and there is no additional guard limiting the size of the block being notified, an attacker who is not a validator/leader can:
1. Have any client establish one `blockSubscribe` subscription (`BlockSubscriptionKind::All`, or `MentionsAccountOrProgram` targeting an account they control).
2. Submit ordinary transactions (via `sendTransaction`) that maximize per-transaction log output and/or return data and pack a target slot to its compute/transaction throughput limit.
3. When that slot is confirmed/finalized, the pubsub notifier thread will build one `RpcBlockUpdate` containing the entire block's transactions/logs and push it as a single JSON string, whose size scales linearly with the attacker's authored on-chain content in that slot — potentially tens of megabytes for one slot — all serialized and sent for a single passive subscription that made only one `blockSubscribe` call.

No existing guard (parameter limits, commitment checks, or `queue_capacity_bytes`) constrains the *size of an individual notification*; `queue_capacity_bytes` only bounds the aggregate buffer used for republishing to slow test-only consumers (`RecentItems`), and even that budget is enforced by evicting other entries, not by rejecting the oversized one.

### Impact Explanation
This is an unbounded-cost-per-single-low-rate-call issue: a single, once-per-slot passive notification (well within `CLUSTER_SLOT_TIME_TARGET / 2` cadence) forces the validator's RPC-pubsub notifier thread to allocate, serialize, and transmit a payload whose size is controlled by attacker-authored transaction/log volume rather than any fixed bound tied to the subscription itself. This matches the "unbounded cost for a single low-rate call" bounty category — CPU (JSON encoding of the whole block), memory (multi-MB `Arc<String>` allocations per notification, shared with all pubsub connections via `RecentItems`), and network bandwidth on the validator's pubsub thread scale with attacker-controlled inputs, with no explicit cap distinct from the coarse, evictive `queue_capacity_bytes`.

### Likelihood Explanation
Feasibility is high and preconditions are minimal:
- Operator must have started the validator with `--rpc-pubsub-enable-block-subscription` (explicitly stated as a precondition), which is a supported, documented feature flag, not a misconfiguration outside the threat model.
- The attacker needs only one WebSocket connection with a single `blockSubscribe` subscription, and normal `sendTransaction` calls to submit transactions maximizing logs — all well under any RPC rate limitations, since block notification cadence is naturally bound to slot production and only one subscription is required.
- No special privileges (leader/validator/staked-node control) are needed; filling a slot with self-authored transactions that emit maximal logs is an ordinary, unprivileged action.

### Recommendation
Add an explicit per-notification size cap to the `blockSubscribe` path (and ideally to `RpcNotifier::notify` generally) that is checked before constructing/sending the notification, e.g.:
- Enforce a hard maximum encoded-JSON size (configurable, independent from `queue_capacity_bytes`) in `filter_block_result_txs` or immediately after encoding in `notify_watchers`'s Block arm; if exceeded, send an `RpcBlockUpdateError` (e.g., a new "block too large" variant) instead of the full block, rather than silently sending an oversized payload.
- Alternatively/additionally, reject or truncate items in `RecentItems::push` that individually exceed `max_total_bytes`, and enforce an outbound message size limit in `handle_connection`'s `sender.send_text` path, mirroring the inbound `set_max_message_size`/`set_max_frame_size` limits.

    fn new(max_len: usize, max_total_bytes: usize) -> Self {
        Self {
            queue: VecDeque::new(),
            total_bytes: 0,
            max_len,
            max_total_bytes,
            last_metrics_submission: Instant::now(),
        }
    }

    fn push(&mut self, item: Arc<String>) {
        self.total_bytes = self
            .total_bytes
            .checked_add(item.len())
            .expect("total bytes overflow");
        self.queue.push_back(item);

        while self.total_bytes > self.max_total_bytes || self.queue.len() > self.max_len {
            let item = self.queue.pop_front().expect("can't be empty");
            self.total_bytes = self
                .total_bytes
                .checked_sub(item.len())
                .expect("total bytes underflow");
        }

        let now = Instant::now();
        let last_metrics_ago = now.duration_since(self.last_metrics_submission);
        if last_metrics_ago > RPC_NOTIFICATIONS_METRICS_SUBMISSION_INTERVAL_MS {

                "rpc_subscriptions_recent_items",
                ("num", self.queue.len(), i64),

        } else {
            trace!(
                "rpc_subscriptions_recent_items num={} total_bytes={}",

fn filter_block_result_txs(
    mut block: VersionedConfirmedBlock,
    last_modified_slot: Slot,
    params: &BlockSubscriptionParams,
) -> Result<Option<RpcBlockUpdate>, RpcBlockUpdateError> {
    block.transactions = match params.kind {
        BlockSubscriptionKind::All => block.transactions,
        BlockSubscriptionKind::MentionsAccountOrProgram(pk) => block
            .transactions
            .into_iter()
            .filter(|tx| tx.account_keys().iter().any(|key| key == &pk))
            .collect(),
    };

    if block.transactions.is_empty()
        && let BlockSubscriptionKind::MentionsAccountOrProgram(_) = params.kind
    {
        return Ok(None);
    }

    let block = ConfirmedBlock::from(block)
        .encode_with_options(
            params.encoding,
            BlockEncodingOptions {
                transaction_details: params.transaction_details,
                show_rewards: params.show_rewards,
                max_supported_transaction_version: params.max_supported_transaction_version,
            },
        )
        .map_err(|err| match err {
            EncodeError::UnsupportedTransactionVersion(version) => {
                RpcBlockUpdateError::UnsupportedTransactionVersion(version)
            }
        })?;
