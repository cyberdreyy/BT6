### Title
Unprivileged pipeline author can force an unprotected job's cache volume into the "protected" volume namespace via a crafted `cache: key` suffix - ([File: executors/docker/internal/volumes/manager.go])

### Summary
`manager.withProtected` (`executors/docker/internal/volumes/manager.go:294-299`) appends the `-protected` suffix to Docker volume/host-cache names purely based on `ManagerConfig.Protected`, which is computed in `executors/docker/volume.go:14-28` as `e.Build.IsProtected() || protectedKeyIdx >= 0` — i.e. true if the job's ref is protected **or** if the job's own `cache.key` string ends with `-protected`. Because the `cache.key` value is fully controlled by the pipeline author in `.gitlab-ci.yml`, an unprivileged contributor on an unprotected branch/MR can flip `Protected` to `true` for their own job simply by naming their cache key with a `-protected` suffix.

### Finding Description
The Docker volume/host cache name is `<UniqueName>-cache-<md5(destination)><protection-suffix>` (`createCacheVolume`, `manager.go:194-251`; `createHostBasedCacheVolume`, `manager.go:169-192`). `UniqueName` is `Build.ProjectRealUniqueName()` (`common/build.go:385-397`), which is derived only from the runner token, system ID, project ID, and concurrency ID — it does **not** depend on the branch/ref. Therefore all pipelines for the same project/concurrency slot compute the same base name, and the *only* thing separating "protected-ref cache" from "unprotected-ref cache" is the `-protected` suffix decided by `withProtected`.

That decision is made in `executors/docker/volume.go`:
```go
protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
    return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
})
...
Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
```
This checks the raw, attacker-supplied `cache.Key` from `.gitlab-ci.yml` directly, with no restriction on who may set it or what ref the job runs on. A job on a non-protected branch that declares `cache: {key: "anything-protected"}` will have `Protected=true`, causing `withProtected` to append `-protected` to its volume/host-dir name — the exact same name a legitimate protected-ref job with the same destination path would produce.

Notably, elsewhere in the codebase (fallback cache keys, in `functions/concrete/builder/builder.go:321-333` and `shells/abstract.go:319-329`) the runner explicitly **blocks** any `CACHE_FALLBACK_KEY`/fallback key ending in `-protected`, specifically to stop jobs from reading into the protected cache namespace. No equivalent restriction exists for the primary docker volume path in `manager.go`/`volume.go`, showing the protection is inconsistently enforced.

### Impact Explanation
By joining the same Docker volume (or host cache directory) that protected-ref pipelines use, an unprivileged pipeline author on an unprotected branch/MR can:
- Read cached content previously written by protected-ref pipelines (build outputs, dependency caches, potentially sensitive files unintentionally cached), and
- Write/poison that same cache volume, so that a subsequent protected-ref pipeline (which typically runs with protected CI/CD variables, deploy keys, or production credentials) mounts and consumes attacker-controlled cache content — a supply-chain-style path to code execution/secret exfiltration in a trusted pipeline context.

This directly defeats the isolation the `-protected` suffix mechanism (work item 494478) was designed to provide between protected and unprotected refs.

### Likelihood Explanation
Highly feasible and repeatable: any contributor who can edit `.gitlab-ci.yml` for a non-protected branch/MR (a very common, low-privilege capability) can add a `cache.key` value ending in `-protected` and rerun the pipeline as many times as desired to read/poison the shared volume/host directory.

### Recommendation
Do not let an unprotected job's own cache key promote it into the protected volume namespace. Only derive `Protected` from `Build.IsProtected()` (server-determined ref protection), or, if the opt-in-suffix feature must be kept, restrict it to the "downgrade" direction only (a protected-ref job explicitly opting out via `-non_protected`) and never allow an unprotected-ref job's cache key to opt into `-protected` naming — mirroring the block already applied to `CACHE_FALLBACK_KEY`/fallback keys in `builder.go` and `abstract.go`.

### Proof of Concept
Go test extending `Test_CacheVolumeProtected` (`executors/docker/docker_command_integration_test.go:3378`):
1. Run job A with `GitInfo.Protected = true`, `cache.key = "shared"`, same `ProjectID`/`ProjectRunnerID` as job B, and write a marker file into the cached path.
2. Run job B with `GitInfo.Protected = false`, `cache.key = "shared-protected"`, same `ProjectID`/`ProjectRunnerID`, same cache destination path.
3. Assert both jobs' cache volumes resolve to the identical Docker volume name (`vol.Name` ends in `-protected` for both, and both match `<UniqueName>-cache-<md5>-protected`), and that job B's container can read the marker file written by job A — proving cross-protection cache access from an unprotected job.
