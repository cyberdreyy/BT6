### Title
Unsanitized variable Key path traversal in `ShellWriter.TmpFile` allows out-of-tmp-dir `rm -f` in cleanup script - (File: shells/bash.go, shells/powershell.go)

### Summary
`BashWriter.TmpFile` and `PsWriter.TmpFile` build the temp-file path by naively joining `TemporaryPath` with the caller-supplied `name` (here, a CI/CD variable `Key`), then only make the result absolute — they never reject or strip `..` path segments. Any code path that calls `w.TmpFile(variable.Key)` for a `File: true` variable (e.g. `AbstractShell.writeCleanupScript` via `w.RmFile(w.TmpFile(variable.Key))`) will therefore emit a shell/PowerShell delete command whose target path can be walked outside the job's tmp/build directory.

### Finding Description
`BashWriter.TmpFile`: [1](#0-0) 
uses `path.Join(b.TemporaryPath, name)` then `cleanPath` → `Absolute`: [2](#0-1) 
`path.Join` internally calls `path.Clean`, which lexically resolves `..` segments. Because `TemporaryPath` (`build.TmpProjectDir()`) is itself an absolute path, `path.Join(TemporaryPath, "../../etc/passwd")` collapses to an absolute path that can climb out of the tmp directory (and potentially out of the whole build root, depending on how many `..` segments are supplied relative to `TemporaryPath`'s depth). `Absolute()` then just returns the string unchanged because it is already absolute — there is no containment check.

The same pattern exists in `PsWriter.TmpFile` / `cleanPath`: [3](#0-2) 

`RmFile` on both shells simply builds a delete command around whatever path string it is given: [4](#0-3) [5](#0-4) 

Reachability: any `File: true` job variable is written via `Variable()`, which itself calls `TmpFile(variable.Key)` to decide where to materialize the file content: [6](#0-5) [7](#0-6) 
This means the traversal-laden key is not just used for deletion — it is used to decide where the variable's *content* is initially written, which is a stronger primitive (arbitrary-path file **write**, not just delete) reachable through `AbstractShell.writeExports`/`writePrepareScript`, and the same tainted key later flows into cleanup logic that calls `RmFile(TmpFile(key))`. No sanitization, allow-list, or "must be under TemporaryPath" check is applied anywhere along this chain in `shells/bash.go`, `shells/powershell.go`, or `shells/abstract.go`.

Existing protections reviewed: `isTmpFile()` only tests `strings.HasPrefix(value, TemporaryPath)` to decide whether to re-clean an already-tmp value inside `Variable()`; it never validates that a *newly computed* `TmpFile()` result actually stayed inside `TemporaryPath`. There is no key-format validation (e.g. `[A-Za-z_][A-Za-z0-9_]*`) enforced in this Runner code path itself — any such validation, if present, exists only upstream (GitLab Rails variable form validation), which is out of scope per the rules ("attacker action/data accepted by Runner").

### Impact Explanation
A crafted `File: true` variable with a traversal Key causes Runner-generated shell scripts to reference (write to, and later `rm -f`/`Remove-Item`) a file path outside the job's designated tmp/build directory. This violates the invariant that "file operations must stay within intended build/cache/artifact roots." The concrete blast radius is bounded by the OS/container permissions of the job process (e.g., root inside a Docker/Kubernetes build container, or the runner service account for shell executors), but it breaks the confinement guarantee that the codebase clearly intends to enforce (paths are supposed to be pinned under `TemporaryPath`).

### Likelihood Explanation
Any pipeline author who can define pipeline/job variables with `File: true` (e.g., via `.gitlab-ci.yml` `variables:` with `type: file`/API-triggered pipeline variables) and control the variable `Key` string can attempt this. Feasibility depends entirely on whether upstream GitLab actually restricts variable Key characters before shipping the job payload to Runner; Runner itself performs no defense-in-depth check, so if any accepted input path allows non-alphanumeric/`/`/`..` characters in a Key, exploitation is straightforward and repeatable (deterministic path resolution).

### Recommendation
In `TmpFile` (both `BashWriter` and `PsWriter`), after joining/cleaning the path, verify the result is still contained within `TemporaryPath` (e.g., compare with `filepath.Rel` and reject if it starts with `..`, or use a canonicalization+prefix check) and fall back to a safe, sanitized filename (e.g., hash of the key) if the check fails. This should be enforced centrally in `TmpFile` so every caller (`Variable`, `writeCleanupScript`, `writePrepareScript`, etc.) is protected uniformly, rather than relying on validation happening upstream in GitLab Rails.

### Proof of Concept
Go unit test in `shells/bash_test.go` (and equivalent for `shells/powershell_test.go`):
```go
func TestTmpFile_PathTraversalIsContained(t *testing.T) {
    w := &BashWriter{TemporaryPath: "/builds/project/0/.tmp"}
    got := w.TmpFile("../../../../etc/passwd")
    assert.True(t, strings.HasPrefix(got, w.TemporaryPath),
        "TmpFile result %q escaped TemporaryPath %q", got, w.TemporaryPath)
}
```
Expected current behavior (bug confirmed): the assertion fails because `got` resolves to something like `/builds/etc/passwd` or higher, outside `/builds/project/0/.tmp`.

Integration-level PoC: define a job variable `{Key: "../../../../tmp/victim", Value: "x", File: true}`, run `AbstractShell.writeCleanupScript`/`writePrepareScript` generation, and assert the produced script's `rm -f`/`Remove-Item` (and `printf ... >`) target does not contain `../` and lies under the job's `TmpProjectDir()`.

func (p *PsWriter) cleanPath(name string) string {
	if p.resolvePaths {
		return name
	}

	return p.fromSlash(p.Absolute(name))
}
