Confirmed root cause: `get_builder_withdrawals` in `specs/gloas/beacon-chain.md` builds the committed `Withdrawal.amount` field directly from `withdrawal.amount` (the builder's *requested* pending-withdrawal amount), with no cap to the builder's actual balance at that point in the withdrawals list construction. The cap only happens later, separately, in `apply_withdrawals`.

### Title
Builder pending-withdrawal amount committed to the execution layer exceeds the amount actually deducted from builder balance, causing Gwei to be minted with no matching debit - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` commits the *full requested* `withdrawal.amount` from `state.builder_pending_withdrawals` into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` (the amount the execution layer is required to mint to `fee_recipient`). `apply_withdrawals`, however, deducts only `min(withdrawal.amount, builder_balance)` from the builder's CL-side balance. When a builder's balance is less than the sum of its pending withdrawal requests at the time they are swept into a block (e.g., due to prior withdrawals draining the balance, or multiple pending withdrawals against the same builder queued before this one), the EL mints the requested amount in full while the CL only debits what the builder actually had.

### Finding Description [1](#0-0) 
`get_builder_withdrawals` iterates `state.builder_pending_withdrawals` and appends a `Withdrawal(..., amount=withdrawal.amount)` using the raw, uncapped requested amount — it never reads `state.builders[builder_index].balance` to bound the amount.

Compare this to the sibling function `get_pending_partial_withdrawals` for validators (Electra), where the amount is explicitly computed as `balance - get_max_effective_balance(validator)` — i.e., bound by the actual current balance before being placed into the committed `Withdrawal`. No equivalent bound exists for builder pending withdrawals.

The deduction step, `apply_withdrawals`: [2](#0-1) 
```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
```
caps the actual balance debit at `min(withdrawal.amount, builder_balance)`, while `withdrawal.amount` itself — the value already committed to the execution payload and that the EL is required to honor per the withdrawals-processing spec note — remains the *uncapped* requested figure.

The invariant that should hold is: `Gwei minted to fee_recipient == Gwei debited from builder.balance`. This is exactly the equality class the report analog targets — a payment applied (minted on the EL) that exceeds what the block's own state transition commits/debits, i.e. Gwei created (from the perspective of total system supply, since EL mints against the payload's `Withdrawal.amount` while CL debit is capped below that).

This can be reached whenever `builder_pending_withdrawals` contains more than one entry whose requested amounts, summed, exceed the builder's balance — a state fully reachable via ordinary spec-following request processing (e.g., `BuilderPendingWithdrawal` requests can be queued repeatedly for the same builder before being swept, and nothing enforces that the sum of pending requests against a single builder is bounded by that builder's balance at request-time; only the *deduction* is capped, not the *request accumulation* or the *committed amount*).

### Impact Explanation
Per the Gloas spec's own note on `process_withdrawals` (specs/gloas/beacon-chain.md, lines ~1976-1990), the EL mints the full amount declared in each `Withdrawal` regardless of what happens on the CL side; any CL-side capping "creates a net supply inflation." The authors explicitly acknowledge this class of issue for the `decrease_balance` saturate-at-zero case for validator sweeps, but the same unmitigated pattern exists for builder pending withdrawals via `get_builder_withdrawals`, where the committed amount is never capped to available balance at commitment time (unlike the validator case, where `amount = balance - max_effective_balance` is bound to `balance` at commit time). This is a genuine "Gwei created" defect matching the External Report's bug class (payout amount not validated/capped against actual available funds before being irrevocably committed), landing at High/Critical severity per the rules (Gwei created that a non-owner receives, mismatch between committed payment and applied debit).

### Likelihood Explanation
Reachable purely through ordinary, spec-following state evolution: multiple `BuilderPendingWithdrawal` entries can accumulate for the same builder before a sweep occurs (the queue is a FIFO list bounded only by `BUILDER_PENDING_WITHDRAWALS_LIMIT`, not by builder balance), and builder balance can be reduced between the time requests are queued and when they are processed (e.g. an earlier request in the same batch already draining it, as literally demonstrated by the test `test_builder_withdrawal_insufficient_balance` [3](#0-2)  that explicitly exercises the mismatch, confirming the withdrawal `amount` field remains the requested 5 ETH while only 1 ETH is actually deducted). No malicious peer, coalition, or client bug is required — it's a property of the spec logic itself when multiple pending withdrawals reference an under-collateralized builder.

### Recommendation
Cap the `amount` field written into the `Withdrawal` object inside `get_builder_withdrawals` to the builder's currently available balance minus amounts already committed to prior withdrawals in the same batch (mirroring how `get_pending_partial_withdrawals`/`get_validators_sweep_withdrawals` bound their withdrawal amounts to `balance` before appending), so that the value minted by the execution layer never exceeds what `apply_withdrawals` actually debits from `state.builders[builder_index].balance`.

### Proof of Concept
Using the existing spec test as evidence of the exact mismatch: [4](#0-3) 
1. `state.builders[0].balance = 1 ETH`.
2. `state.builder_pending_withdrawals` has one entry for builder 0 requesting `5 ETH`.
3. `get_builder_withdrawals` places `Withdrawal(validator_index=<builder 0>, amount=5 ETH)` into `payload_expected_withdrawals` — this is what the execution layer is contractually required to mint to the builder's `fee_recipient`.
4. `apply_withdrawals` then only debits `min(5 ETH, 1 ETH) = 1 ETH` from `state.builders[0].balance`, per the test's own assertion `builder_balances={builder_index: 0}` with `withdrawal_amounts_builders={builder_index: withdrawal_amount}` (5 ETH).
5. Net effect: 5 ETH is minted on the EL to the fee_recipient, but only 1 ETH is debited from CL builder state — 4 ETH of Gwei is created with no corresponding CL-side source, breaking the create/destroy/pay-to-owner equality.

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
