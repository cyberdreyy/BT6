### Title
Parsed `TransferChecked`/`Transfer` SPL Token-2022 instructions omit transfer-fee deduction, causing misreported recipient amount - (File: transaction-status/src/parse_token.rs)

### Summary
Agave's transaction-status instruction decoder for the SPL Token program reports the raw instruction `amount`/`tokenAmount` for `Transfer` and `TransferChecked` instructions as if it were the amount the destination account will receive. For Token-2022 mints configured with the `TransferFeeConfig` extension, the on-chain program silently deducts a transfer fee from every transfer — including plain `Transfer`/`TransferChecked` calls, not only `TransferCheckedWithFee` — yet `parse_token.rs` never consults the mint's fee configuration when decoding these instruction variants, so the value surfaced to RPC/JSON-parsed consumers overstates what the recipient actually gets by exactly the withheld fee. This mirrors the Sherlock M-11 root cause: an amount is assumed to be fully deliverable without accounting for a transfer fee actually applied at the token-program level.

### Finding Description
`parse_token` in `transaction-status/src/parse_token.rs` decodes `TokenInstruction::Transfer`/`TokenInstruction::TransferChecked` purely from the instruction's own `amount`/`decimals` fields: [1](#0-0) [2](#0-1) 

Neither branch looks up the mint account or any `SplTokenAdditionalDataV2`/fee-extension data; it reports the value taken directly from `instruction.data`. By contrast, when the fee-aware instruction variant is used, the parser explicitly returns both `tokenAmount` and `feeAmount`: [3](#0-2) 

However, spl-token-2022's transfer-fee mechanism is applied by the program to **any** transfer against a fee-enabled mint (plain `Transfer`/`TransferChecked` included) — `TransferCheckedWithFee` only adds client-side fee-slippage verification, it isn't a prerequisite for the fee to apply. Consequently, a transaction that moves tokens with an ordinary `TransferChecked` instruction against a fee-bearing Token-2022 mint will actually credit the destination with `amount - fee`, while the decoded/parsed instruction JSON returned to RPC clients (`getTransaction`, `getConfirmedTransaction`, explorers, indexers, wallets) still shows the pre-fee `amount`/`tokenAmount` with no accompanying fee, so downstream consumers assume the recipient received the full stated amount.

Note that the ground-truth `pre_token_balances`/`post_token_balances` recorded separately by the SVM (`svm/src/transaction_balances.rs`, `runtime/src/transaction_balances.rs`) do correctly reflect the actual post-fee balance because they read live account state rather than instruction arguments: [4](#0-3) 

but the *parsed instruction* field is the piece exposed directly under `transaction.message.instructions[].parsed.info.tokenAmount`, and it is this specific field that misreports the delivered amount, exactly analogous to the vault's `claims[recipientId][token] += amount` bug where the claimable/assumed amount ignores an in-flight fee.

### Impact Explanation
Any unprivileged party can create a Token-2022 mint with a `TransferFeeConfig` extension and then send an ordinary `Transfer`/`TransferChecked` instruction. Any RPC consumer relying on `parsed` instruction data (rather than diffing pre/post token balances) to determine how much a recipient received will be misled by exactly the fee amount, for every such transaction. This is a decoder-level misreporting bug in agave's own transaction-status parsing code, not a validator crash, but it can systematically corrupt on-chain-activity reporting (indexers, wallets, exchanges reconciling deposits) built on the parsed-instruction API.

### Likelihood Explanation
High. Fee-bearing Token-2022 mints are officially supported functionality, require no special privilege to create, and a single ordinary transfer instruction against such a mint is sufficient to trigger the discrepancy — no multi-call sequencing, mocked components, or validator/operator role is needed.

### Recommendation
When decoding `TokenInstruction::Transfer`/`TransferChecked` (and any other non-`...WithFee` transfer variants) for a `spl_token_2022` program id, look up the source mint's `TransferFeeConfig` extension (as already done for `TransferCheckedWithFee`) and compute/report the effective fee and net-delivered amount alongside the raw instruction `amount`, or otherwise clearly document that `parsed.info.tokenAmount` reflects requested (not delivered) amount and direct API consumers to `pre/postTokenBalances` for actual settled amounts.

### Proof of Concept
1. Create a Token-2022 mint with the `TransferFeeConfig` extension enabled (e.g., 5% fee) via `spl_token_2022_interface`.
2. Fund a source token account and submit a plain `TransferChecked` instruction moving `amount = 1000` to a destination account.
3. The token program deducts the configured fee (e.g., 50) from the transferred amount before crediting the destination, so the destination's balance only increases by 950.
4. Query the transaction via `getTransaction` (or any consumer of `transaction-status`'s `parse_token`) and observe `parsed.info.tokenAmount.amount == "1000"` with no fee field, while `postTokenBalances`/`preTokenBalances` for the destination account show only a 950 increase — demonstrating the parsed-instruction data overstates the amount actually delivered to the recipient.

impl SvmTokenInfo {
    fn unpack_token_account<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        account: &AccountSharedData,
        index: usize,
    ) -> Option<Self> {
        let program_id = *account.owner();
        let generic_token::Account {
            mint,
            owner,
            amount,
        } = generic_token::Account::unpack(account.data(), &program_id)?;

        let mint_account = account_loader.load_account(&mint)?;
        if *mint_account.owner() != program_id {
            return None;
        }

        let generic_token::Mint { decimals, .. } =
            generic_token::Mint::unpack(mint_account.data(), &program_id)?;

        Some(Self {
            account_index: index.try_into().ok()?,
            mint,
            amount,
            owner,
            program_id,
            decimals,
        })
    }
