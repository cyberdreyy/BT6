## Analysis

`createDstEscrow` is a fully permissionless entrypoint — any address can call it with an arbitrary `IBaseEscrow.Immutables` struct (paying the safety deposit + amount) and no code validates the length or shape of `dstImmutables.parameters`: [1](#0-0) 

The clone's address and stored-immutables hash are derived from `immutables.hashMem()`, which just hashes whatever bytes were supplied as `parameters` — there is no minimum-length or structural check at creation time.

Both `withdraw` and `publicWithdraw` funnel into `_withdraw`, which unconditionally decodes fee fields from calldata via `ImmutablesLib`: [2](#0-1) 

`integratorFeeAmountCd` is evaluated **before** `protocolFeeAmountCd` and reverts with `IndexOutOfRange` whenever `parameters.length < 0x40` (64 bytes): [3](#0-2) 

A `parameters` blob of 63 bytes satisfies the `>= 0x20` check used by `protocolFeeAmountCd`, but fails the `>= 0x40` check used by `integratorFeeAmountCd`. Since `integratorFeeAmountCd` is called first inside `_withdraw`, **the revert is unconditional and independent of what the actual protocol-fee value would be** — the premise in the question that this depends on "the protocol fee alone being near the full amount" is not accurate; any `parameters` length in `[32, 63]` bytes triggers the same unconditional revert regardless of encoded fee values.

Because `onlyValidImmutables` requires the exact same immutables (including this malformed `parameters` blob) to be replayed to match the CREATE2-derived hash, there is no way to "fix" the parameters after deployment. Both `withdraw` (taker-only) and `publicWithdraw` (anyone holding the access token) share `_withdraw`, so **both paths revert identically** — confirming the question's core claim that even the public path is bricked. `cancel()`, however, does not decode `parameters` at all and remains callable by the taker once `DstCancellation` is reached, returning `immutables.amount` to the taker (the escrow's own creator/funder) rather than to the maker: [4](#0-3) 

Since `createDstEscrow` has no whitelist/access restriction, the "escrow creator" here does not need privileged-resolver status — any unprivileged account funding the destination escrow can set this malformed `parameters` field. This satisfies an in-scope attacker model (destination escrow creation via a live entrypoint, no owner/governance/whitelisted-resolver assumption).

### Title
Malformed `parameters` length bricks both private and public `EscrowDst` withdrawal - (`contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`createDstEscrow` accepts a `parameters` bytes blob of arbitrary length with no minimum-size validation. If deployed with a length in `[32, 63]` bytes, `ImmutablesLib.integratorFeeAmountCd` unconditionally reverts inside `EscrowDst._withdraw`, which is shared by both `withdraw` and `publicWithdraw`. The maker can never receive the destination payout through the intended withdrawal path even with a valid secret; the funds can only be reclaimed via `cancel()` after the `DstCancellation` timelock, and they go back to the escrow's creator, not the maker.

### Finding Description
`_withdraw` decodes `integratorFeeAmountCd()` before `protocolFeeAmountCd()`. `integratorFeeAmountCd` requires `parameters.length >= 0x40`. A `parameters` blob shorter than 64 bytes (but at least 32) causes this call to always revert with `IndexOutOfRange`, blocking `_withdraw` entirely regardless of the encoded values. Since `withdraw` and `publicWithdraw` are the only functions using `_withdraw`, both the private and public withdrawal windows become permanently unusable for this escrow instance.

### Impact Explanation
This breaks the invariant that a funded destination escrow with a known secret can always be settled during its public-withdrawal window. Funds remain stuck in the escrow through the entire withdrawal lifecycle and can only be released via `cancel()` after `DstCancellation`, and even then they return to the taker/creator rather than completing the swap to the maker. This is a temporary freezing of the swap settlement during the live lifecycle, matching the High-severity "temporary freezing of funds during the live swap lifecycle" bucket.

### Likelihood Explanation
`createDstEscrow` is a public, unrestricted entrypoint; deploying with a crafted 63-byte `parameters` field requires no privileged role, only paying the escrow's safety deposit/amount. The condition is trivially reproducible and does not depend on any race condition or external state.

### Recommendation
Validate `parameters.length` (e.g., require it to be exactly `0x80` bytes, or `0` for the `EscrowSrc` case) at `createDstEscrow` time before allowing the clone to be deployed/funded, or replace the independent length checks in `ImmutablesLib` with a single upfront validation of the full expected parameters length before any fee field is decoded in `_withdraw`.

### Proof of Concept
1. Call `createDstEscrow` with `dstImmutables.parameters` set to any 63-byte blob (e.g., `abi.encode(protocolFeeAmount, integratorFeeAmount)` truncated by one byte), funding the required native/ERC20 amounts.
2. Warp to `DstWithdrawal` and call `withdraw(secret, immutables)` as the taker — reverts with `ImmutablesLib.IndexOutOfRange` from `integratorFeeAmountCd`.
3. Warp to `DstPublicWithdrawal` and call `publicWithdraw(secret, immutables)` as any access-token holder — reverts identically.
4. Only `cancel()` after `DstCancellation` succeeds, returning the deposited amount to the taker instead of completing the maker's payout. [5](#0-4) [6](#0-5)

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
