### Title
Missing caller check in `setApr`/`setAprs`/`setAprsWithBuffer` lets any EOA pin the vault APR before the CDO is wired - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr` intentionally skips its `msg.sender != idleCDO && msg.sender != manager` authorization check whenever `idleCDO == address(0)`, on the assumption that this state "can happen only during the setup". The same window is inherited by `setAprs` and `setAprsWithBuffer`, which set `unscaledApr` with no check at all and then delegate to `setApr`. Because `setWhitelistedCDO` (the only function that arms the check) does not reset the APR, an unprivileged attacker can front-run the owner wiring transaction and permanently seed `lastApr`/`unscaledApr` — most damagingly `0` — so the first epoch runs with attacker-chosen interest terms. This is the direct on-chain analog of the Jenkins advisory: an administrative configuration path reachable with lower-than-required privilege because the permission check is conditional on unrelated state.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `setApr` (lines 225-235) only enforces the caller check inside `if (_cdo != address(0))`. When `idleCDO` is unset it falls through and writes `lastApr = _apr` for any caller, bounded only by `maxApr` (default `DEFAULT_MAX_APR = 20e18`, line 89).
- `setAprs` (lines 206-210) and `setAprsWithBuffer` (lines 217-220) write `unscaledApr` unconditionally and then call `setApr`, so both APR fields are attacker-controllable in the same window.
- `initialize` (lines 124-158) sets `lastApr`/`unscaledApr` but leaves `idleCDO` at zero; `setWhitelistedCDO` (lines 954-957) later sets `idleCDO` without touching the APR values.

After `idleCDO` is wired, `requestWithdraw` (lines 285-286) branches on `unscaledApr == 0` and diverts withdraw requests into the APR0 bucket (`apr0Users`, `apr0TotalPrincipal`), and `IdleCDOEpochVariant` computes `expectedEpochInterest` from the strategy APR each epoch. An attacker who sets `unscaledApr = 0` and `lastApr = 0` before wiring therefore causes the first epoch to accrue zero interest for all AA/BB depositors while additionally misrouting their withdraw requests into the APR0 settlement path (`prepareStopEpochWithApr0`, lines 490-541).

Existing guards do not stop this: `maxApr` only caps the upper bound, nothing enforces a lower bound or re-validates the APR at `setWhitelistedCDO` or `startEpoch` time, and there is no event or flag marking the APR as "owner-confirmed".

### Impact Explanation
An unprivileged EOA (no deposit, no KYC, no role) can fix the vault's scaled and unscaled APR to `0` before the CDO is attached. If an epoch then starts on those values, all lender yield for that epoch is zeroed: the honest borrower repays only principal, and `expectedEpochInterest`/`_calcInterest` produce nothing for AA and BB holders — a loss equal to `principal * intendedApr * epochDuration / YEAR` for every depositor (e.g. ~10% annualized APR on a 90-day epoch ≈ 2.5% of TVL in stolen yield, redirected to the borrower's benefit rather than the attacker, but borne entirely by LPs). Additionally, `unscaledApr == 0` forces every `requestWithdraw` into the APR0 accounting path, altering the settlement semantics of pending receipts for the whole epoch. The invariant broken is fair yield distribution caused by a missing access-control check on a privileged configuration write.

### Likelihood Explanation
The exploit requires calling the setter in the window between `initialize` and `setWhitelistedCDO`. If the factory wires both atomically the window is small, but (a) `setWhitelistedCDO` is a separate owner transaction in the standard deployment flow, making it front-runnable on any public mempool, and (b) any deployment or upgrade path that sets the implementation before wiring the CDO leaves the check disarmed. The attacker cost is a single call; there is no economic barrier. The residual mitigation is that the honest owner/manager can overwrite the APR via `setAprs` after wiring — but only if they notice before `startEpoch`, and nothing forces them to.

### Recommendation
Remove the conditional skip in `setApr`: always require `msg.sender == idleCDO || msg.sender == manager` (or `onlyOwner` while `idleCDO == 0`). Alternatively, have `setWhitelistedCDO` clear/re-require APR confirmation, or emit and validate APR at `startEpoch`. Apply the same check to the `unscaledApr` write in `setAprs`/`setAprsWithBuffer`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";

contract SetAprAccessTest is Test {
    IdleCreditVault strategy;
    address owner   = address(0x1);
    address manager = address(0x2);
    address borrower= address(0x3);
    address attacker= address(0xbabe);
    address cdo     = address(0x4);

    function setUp() public {
        strategy = new IdleCreditVault(); // behind proxy in practice; impl token == address(1) is fine for logic test
        // deploy a fresh proxy or a second instance whose initialize leaves idleCDO == 0
    }

    function testAnyoneCanSetAprBeforeCdoWired() public {
        // vm.etch / proxy deploy so initialize(...) runs with real underlying
        // attacker calls before owner wires the CDO:
        vm.prank(attacker);
        strategy.setAprs(0, 0);            // unscaledApr = 0, lastApr = 0
        assertEq(strategy.unscaledApr(), 0);
        assertEq(strategy.lastApr(), 0);

        // owner wires the CDO; APR stays at attacker value (not reset)
        vm.prank(owner);
        strategy.setWhitelistedCDO(cdo);
        assertEq(strategy.unscaledApr(), 0);
        assertEq(strategy.lastApr(), 0);

        // now direct calls are properly blocked
        vm.prank(attacker);
        vm.expectRevert(NotAllowed.selector);
        strategy.setApr(1e18);

        // consequence: with unscaledApr == 0, requestWithdraw(_amount, user, _principal)
        // from the CDO diverts to _requestWithdrawApr0 (line ~285) and
        // expectedEpochInterest for the epoch is 0 -> LPs earn nothing.
    }
}
```
On a fork: deploy `IdleCreditVault` behind the proxy used by `IdleCreditVaultFactory`, `initialize` with the real underlying, have `attacker` call `setAprs(0,0)`, then `setWhitelistedCDO(cdo)`, run a full `IdleCDOEpochVariant` epoch (deposits → `startEpoch` → warp → `stopEpoch`), and assert `expectedEpochInterest == 0` and AA/BB virtual prices unchanged despite a configured non-zero intended APR.

One caveat worth noting: if `IdleCreditVaultFactory` (or the deployment script) calls `initialize` and `setWhitelistedCDO` atomically in one transaction, the attack window collapses to mempool front-running of that specific transaction; the unconditional `unscaledApr` write and the absent lower-bound on APR remain defense-in-depth issues regardless.
