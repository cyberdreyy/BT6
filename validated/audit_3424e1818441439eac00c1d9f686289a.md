Confirmed: `delete_member` (multisig2) and the `DeleteKey` handler (multisig) only purge requests *created by* the removed member (`r.member == member` / `r.signer_pk == pk`). Neither implementation scans `confirmations` on *other* pending requests to strip entries belonging to the removed member. This is a genuine analog to the WiseLending bug class: a check performed against a value ("number of confirmations") that is not kept consistent with the live state it's supposed to represent ("number of current members"), letting a request execute below the real authorization threshold.

### Title
Stale confirmations from removed members let a multisig request execute below the live confirmation threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
`confirm()` authorizes and executes a `MultiSigRequest` once `confirmations.len() + 1 >= num_confirmations` [1](#0-0) . `delete_member` (and, in the legacy `multisig` contract, the `DeleteKey` action) removes a member/key and only cleans up requests that member *originated*, but never scans `confirmations` entries of other, still-pending requests to remove that member's stale confirmation [2](#0-1) . The identical pattern exists in the legacy contract's `DeleteKey` action [3](#0-2) . As a result, a confirmation cast by a member while they were still a member continues to count toward `num_confirmations` even after that member has been removed from the multisig, so a request can be executed with fewer *live, currently-authorized* confirmations than the threshold demands.

### Finding Description
The equality that should hold is: `confirmations counted at execution == confirmations from currently-live members`. Instead, `confirmations` is a set of raw public keys / member identifiers that is only pruned when (a) the specific request is executed/removed, or (b) the specific request was *created by* the removed member [4](#0-3) . There is no invariant enforcement that a member confirming, then later being deleted via a separate `DeleteMember`/`DeleteKey` request, has their confirmation retroactively invalidated on requests they merely confirmed (as opposed to created).

`confirm()` blindly trusts the stored confirmation set size against the current `num_confirmations`, without re-validating that each entry in the `HashSet` still corresponds to a member in `self.members` [5](#0-4) .

### Impact Explanation
This crosses the "confirmations counted versus live members" authorization boundary explicitly called out as in-scope. A transfer, `AddKey`, `DeployContract`, or any other privileged multisig action can execute having been approved by fewer *actually authorized* signers than `num_confirmations` requires — e.g., in a 3-of-4 multisig, if member D confirms a pending Transfer request, is subsequently removed via a `DeleteMember` request (which does not touch D's stale confirmation on the Transfer request), the Transfer request can still be pushed to execution once 2 more live members confirm, effectively executing with only 2 genuinely live confirmers' consent recorded plus 1 stale/void one — a multisig request executed below the intended threshold of live authorizers. Per the impact bar this is a Critical-class issue ("a multisig request executed below threshold").

### Likelihood Explanation
Requires no special privilege beyond being (at some point) a legitimate multisig member/key holder whose access is later revoked — a routine operational event (key rotation, offboarding). The attacker/malicious-insider path is: confirm a request while still a member, be removed afterward (by the remaining, unaware co-signers, who see no reason this taints existing confirmations), then rely on the leftover confirmation to help push the request over threshold later. No admin misbehavior beyond routine `DeleteMember`/`DeleteKey` execution is required, and no code path currently purges the stale confirmation, so this is deterministic once the ordering occurs — realistic operational likelihood is Medium-High.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over `confirmations` for *all* pending requests (not just ones the member created) and remove the deleted member's/key's entry; alternatively, validate on `confirm()`/`execute_request()` that every recorded confirmer in the set is still present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Multisig deployed with members `{A, B, C, D}`, `num_confirmations = 3`.
2. Member `A` creates request `R1` (e.g., `Transfer`) via `add_request`.
3. Member `D` calls `confirm(R1)` → confirmations = `{A? , D}` (depending on whether A auto-confirmed) — assume confirmations = `{A, D}` after A creates-and-confirms.
4. Separately, members `A, B, C` create and fully confirm a `DeleteMember { member: D }` request, which executes `delete_member`, removing D from `self.members` and revoking D's access key — but `R1`'s confirmation set `{A, D}` is untouched since `R1.member == A`, not `D` [4](#0-3) .
5. Member `B` (still live) calls `confirm(R1)`. `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `R1` executes [6](#0-5) .
6. `R1` (the Transfer) executes with only `A` and `B` being genuinely live, currently-authorized confirmers, plus a stale confirmation from removed member `D` — i.e., the request executed with 2 live confirmations against a nominal 3-of-4 threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
