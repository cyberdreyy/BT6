### Title
Stale confirmations from removed multisig keys are still counted toward execution threshold - (File: multisig/src/lib.rs)

### Summary
`confirm()` counts entries in the `confirmations` set for a request against `num_confirmations` without verifying that each confirming public key is still a live access key on the account. `DeleteKey`'s cleanup in `execute_request` only removes confirmations for requests *originated by* the deleted key (`r.signer_pk == pk`); it does not remove that key's confirmations recorded on requests originated by *other* signers. This lets a request execute having been "confirmed" by fewer currently-valid keys than `num_confirmations` requires.

### Finding Description
`add_request`/`confirm` build a per-request `HashSet<PublicKey>` of confirmations [3](#0-2)  and `confirm` simply checks `confirmations.len() as u32 + 1 >= self.num_confirmations` before executing [2](#0-1) . Nothing in `confirm` or `assert_valid_request` [4](#0-3)  re-validates that the public keys already recorded in `confirmations` are still active access keys on the account — validity of a signature is only enforced implicitly by NEAR at call time for the *current* caller, not retroactively for past confirmers.

When a `DeleteKey` action executes, it purges requests and confirmations only for requests where the removed key was the *original requester* (`r.signer_pk == pk`):
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter(|(_k, r)| r.signer_pk == pk)
    .map(|(k, _r)| k)
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [1](#0-0) 

It never scans `self.confirmations` for entries where the removed key appears merely as a *confirmer* of someone else's still-pending request. That request's confirmation set keeps the departed key's entry, and its vote continues to count toward `num_confirmations` for as long as the request stays open.

The invariant that should hold is: `confirmations counted == confirmations from currently live members`. After a `DeleteKey`, that equality breaks for any pending request the removed key had confirmed (but not created): the recorded count still includes a key that is no longer a member of the multisig.

### Impact Explanation
This lets a request be executed by validated real-time signatures from fewer live members than `num_confirmations` intends — a multisig request executed below the effective live-member threshold. Concretely: with `num_confirmations = 3` and members `[K1, K2, K3]`, K1 opens a transfer request and confirms it (1/3). K2 confirms (2/3, pending). Later the group legitimately rotates out K2 via a `DeleteKey{K2}` request (K2's own outstanding *requests* are purged, but K2's confirmation on K1's transfer request is untouched). The transfer request still shows 2 confirmations. Now only K3 (a genuinely current member) needs to confirm to push it to 3/3 and execute — even though only K1 and K3 are still valid members, i.e., the funds move with confirmations effectively from 2 live signers plus one stale/departed one, not 3 live signers.

### Likelihood Explanation
This requires normal, expected multisig operation (key rotation via `DeleteKey`) combined with a pending request that a departing key had confirmed but not created — a routine and even likely operational sequence for any long-lived multisig account, requiring no privileged bypass beyond what member key-holders already can do.

### Recommendation
On any `DeleteKey`/`DeleteMember` action, scan all pending `confirmations` sets (not just requests originated by the removed key) and strip the removed key/member from every confirmation set, or re-validate at `confirm`-time that every entry in `confirmations` still corresponds to a currently active key/member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with keys `K1, K2, K3` (3-of-3).
2. K1 calls `add_request_and_confirm` with a `Transfer` action to an attacker-controlled account → confirmations = `{K1}` (1/3).
3. K2 calls `confirm(request_id)` → confirmations = `{K1, K2}` (2/3), request stays pending (not yet executed).
4. The group later executes a separate multisig request with `DeleteKey{ public_key: K2 }` to rotate K2 out (legitimate operational action) — this only purges requests where `signer_pk == K2` (K2 authored none here), so the pending transfer's confirmations `{K1, K2}` are untouched.
5. K3 (the only other live key) calls `confirm(request_id)` → `confirmations.len() + 1 == 3 >= num_confirmations`, and the transfer executes — funds move having been "approved" by K1, K3, and a stale confirmation from removed K2, i.e., effectively 2 live members instead of the required 3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
