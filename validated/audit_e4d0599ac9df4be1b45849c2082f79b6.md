### Title
Unauthenticated `/sessions` POST relies solely on per-IP rate limiting with no per-account lockout, enabling distributed credential-stuffing brute force - ([File: core/web/router.go])

### Summary
`sessionRoutes` protects `POST /sessions` only with a generic IP-keyed rate limiter (`rl.UnauthenticatedPeriod()`/`rl.Unauthenticated()`), and `SessionsController.Create` performs no per-account (per-email) failure tracking or lockout. An attacker who can vary source IP (e.g., via botnet/proxy pool, not merely source ports since the limiter keys on IP not port) can brute-force a known user's password with effectively unlimited total attempts, since each new IP resets the counter.

### Finding Description
In `core/web/router.go`, `sessionRoutes` wraps `unauth.POST("/sessions", sc.Create)` with `rateLimiter(rl.UnauthenticatedPeriod(), rl.Unauthenticated())` [1](#0-0) . `rateLimiter` builds an in-memory `ulule/limiter` keyed by the standard gin/mgin extraction of the client's remote IP [2](#0-1) . `engine.RemoteIPHeaders = nil` at line 50 disables trusting `X-Forwarded-For`/`X-Real-IP`, so the key used is the actual TCP peer address as seen by the node (or by the reverse proxy positioned in front of it) [3](#0-2) .

`SessionsController.Create` calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and on failure simply returns `401` — there is no per-email/per-account failure counter, delay, or lockout logic in this handler [4](#0-3) . The only brute-force mitigation is the shared IP-keyed rate limit applied to the whole `/sessions` group.

Because the limiter is keyed by IP address (not account, and not port — an attacker rotating only source ports on the same IP would in fact still be blocked, contrary to the question's port-rotation framing, since the limiter's per-connection state is IP-based), the actual bypass vector is an attacker distributing requests across many source IP addresses (botnet, proxy rotation, cloud IP pools). Each new IP gets its own independent rate-limit bucket in the `memory.NewStore()`, so the total number of password guesses against a single target account is unbounded by IP count, even though any single IP is throttled "fairly" as described.

### Impact Explanation
This maps to CWE-307 (Improper Restriction of Excessive Authentication Attempts). A successful brute force yields full account takeover: a valid session cookie, and through it downstream access to API tokens, CSA/ETH keys, and job/bridge management endpoints gated only by session/role auth — i.e., credential compromise leading to session hijack and key/token disclosure, matching the described scoped impact.

### Likelihood Explanation
No credentials or privileged network position are required — only unauthenticated access to `/sessions` and the ability to source requests from multiple IP addresses, which is inexpensive for a motivated attacker (cloud instances, botnets, residential proxy services). The weak points (per-IP-only limiter, no per-account lockout, no CAPTCHA/backoff, no failed-attempt persistence) are fully visible in `sessionRoutes`/`rateLimiter`/`SessionsController.Create`, so the attack is straightforward to reproduce and repeat indefinitely against any target account as long as new source IPs are available.

### Recommendation
Add an account-scoped (e.g., keyed by the submitted email, independent of client IP) failed-login counter with escalating delay or temporary lockout in `SessionsController.Create`, persisted (e.g., in the ORM/DB or a shared store) rather than purely in-memory per-IP. Consider combining IP-based and account-based limiting, and emit audit log/alerting on repeated failures for a given account.

### Proof of Concept
Go handler-level integration test plan:
1. Build a test router via `web.NewRouter` (or `cltest` helper) with a real `SessionsController` and default `RateLimit` config.
2. Simulate N failed `POST /sessions` requests for the same email/wrong-password from IP `A` until the IP-based limiter returns `429`.
3. Repeat the same failed attempts from a different simulated source IP `B` (by adjusting the test's `httptest.Request.RemoteAddr`) and assert the requests are again accepted (not `429`) — proving there is no per-account lockout independent of IP.
4. Assert failure: expected secure behavior would be a `429`/lockout response tied to the account regardless of source IP after cumulative N failures; current code allows continuation, confirming the gap.

```go
func rateLimiter(period time.Duration, limit int64) gin.HandlerFunc {
	store := memory.NewStore()
	rate := limiter.Rate{
		Period: period,
		Limit:  limit,
	}
	return mgin.NewMiddleware(limiter.New(store, rate))
}
```

```go
func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
```

```go
func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

	if err := saveSessionID(session, sid); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.Join(errors.New("unable to save session id"), err))
		return
	}

	jsonAPIResponse(c, Session{Authenticated: true}, "session")
}
```
