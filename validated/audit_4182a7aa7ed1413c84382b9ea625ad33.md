### Title
Silent eviction of pending legacy callbacks in `pruneCallbacks` causes delayed victim response without explicit error, but no unbounded hang - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`pruneCallbacks` can evict a victim's `savedCallback` from `h.savedCallbacks` under load without calling `SendResponse`, meaning the victim never gets an explicit "your request was evicted" error. However, the victim's caller does not hang indefinitely because `Callback.Wait` is invoked with the request's own `context.Context` in `gateway.ProcessRequest`, which is bounded by the standard HTTP request lifecycle/timeout, not by anything internal to `pruneCallbacks`.

### Finding Description
`HandleLegacyUserMessage` stores the caller's `Callback` in `h.savedCallbacks` keyed by `msg.Body.MessageId` [3](#0-2) . The periodic `pruneCallbacks` goroutine deletes both expired and, if `len(savedCallbacks) > maxSize`, the oldest half of entries directly from the map without ever calling `SendResponse` on the evicted `Callback` [4](#0-3) . This means when the corresponding node response later arrives via `handleWebAPITriggerMessage`, the lookup `h.savedCallbacks[msg.Body.MessageId]` will miss (`found == false`), and the response is silently dropped with no error surfaced to the evicted caller [5](#0-4) .

However, the claim that the victim "hangs forever on `Callback.Wait`" is not supported by the code. `Callback.Wait` only blocks on `<-ctx.Done()` or `<-c.ch`, and the `ctx` passed to it originates from the incoming HTTP request in `gateway.ProcessRequest`, not from an internal unbounded context [2](#0-1) [6](#0-5) . As soon as the request's context is canceled or times out (standard HTTP server/client-side deadline), `ctx.Done()` fires and `Wait` returns `ctx.Err()`, which `ProcessRequest` converts into an `api.RequestTimeoutError` response to the caller. There is no goroutine leak tied to `pruneCallbacks` beyond the normal bound of the caller's HTTP request context lifetime.

### Impact Explanation
The real, confirmed impact is narrower than stated: an attacker flooding `MethodWebAPITrigger` legacy messages (subject to the separate lack-of-allowlist finding, not addressed here) can cause `pruneCallbacks` to evict a victim's in-flight callback before the corresponding DON node response arrives, so the victim receives no successful payload — instead, they get a generic timeout error once their own request context expires, rather than a legitimate application response. This is a availability/DoS-adjacent nuisance (delayed/garbled response delivery under load) but not an unbounded resource leak, and not a violation of "guaranteed bounded lifecycle" since the timeout still bounds it via the caller's HTTP context.

### Likelihood Explanation
Requires the ability to submit a very large volume (tens of thousands, per `defaultMaxSavedCallbacks = 20000`) of `MethodWebAPITrigger` messages cheaply to push `savedCallbacks` past `maxSize`, which is a separate rate-limiting/allowlist gap already flagged elsewhere in the codebase (`// TODO: apply allowlist and rate-limiting here` at handler.go:384) [7](#0-6) . Given that gap, causing eviction of a specific victim message is feasible but requires precise timing/volume relative to the 30-second prune interval and 20000-entry threshold.

### Recommendation
On eviction in `pruneCallbacks`, call the evicted `Callback.SendResponse` with a bounded error (e.g., `api.RequestTimeoutError` / `LimitExceededError`) instead of silently deleting the map entry, so the caller receives an explicit signal rather than relying on their own HTTP context timeout to eventually surface a generic error.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks` set to a small number (e.g., 4).
2. Call `HandleLegacyUserMessage` multiple times with distinct `MessageId`s and real `common.NewCallback()` instances, exceeding the max, to populate `savedCallbacks`.
3. Invoke `h.pruneCallbacks()` directly.
4. For an evicted (oldest) callback, assert it is no longer in `h.savedCallbacks`, and call `cb.Wait(ctx)` with a `context.WithTimeout` of a few milliseconds — assert it returns `ctx.Err()` (bounded timeout), not an indefinite block, confirming no goroutine leak but confirming the caller never receives an application-level error/success payload from `SendResponse`.
