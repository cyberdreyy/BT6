## Title
Replay guard permanently consumes a Vault request's single-use authorization before owner-match validation completes, causing legitimate resubmission to be denied - (File: `core/capabilities/vault/authorizer.go`)

### Summary
In `authorizer.AuthorizeRequest`, the request-digest replay guard is recorded as "seen" *before* the owner-binding check (`validateSecretOwnersMatchAuthorized`) is evaluated. If that later owner check fails, the function still returns an error, but the digest has already been permanently marked consumed in `RequestReplayGuard`. This mirrors the C4 finding: state that should only be consumed once *all* checks pass is instead consumed after only a subset of the checks, so a legitimate retry of the exact same (now-fixed) request is rejected as a replay even though it never actually succeeded.

### Finding Description
`AuthorizeRequest` calls the allowlist/JWT auth mechanism to get an `AuthResult`, then:
1. Records the digest into the shared `RequestReplayGuard` via `CheckAndRecord` [1](#0-0) 
2. Only afterwards validates that the payload's declared secret owner(s) match the authorized workflow owner via `validateSecretOwnersMatchAuthorized` [2](#0-1) 

`RequestReplayGuard.CheckAndRecord` unconditionally stores the digest with its expiry the first time it's seen and returns `ErrRequestAlreadySeen` on any subsequent call with the same digest, regardless of whether that first call ultimately succeeded: [3](#0-2) 

Since the JSON-RPC request digest is computed over the full request body (method/params/id) via `req.Digest()`, and the allowlist entry itself is tied to that exact digest [4](#0-3) , any single on-chain allowlisted digest is meant to be usable exactly once for the *correct* payload. But because the replay guard fires before the owner-match check, a request that hits the allowlisted digest yet fails the subsequent owner-mismatch validation (e.g., malformed/incorrect owner field, encoding bug, or a race where a different payload happens to reuse that exact allowlisted digest) permanently burns that allowlist entry. The legitimate workflow owner's real request — which would use the identical digest since the digest is fixed by the on-chain allowlisting — can never be authorized afterward; it will always be rejected with `ErrRequestAlreadySeen` until the allowlist entry's expiry passes.

This directly parallels the C4 report's root cause: `approvedHashes[...][_hash]` (a single-use approval) is deleted on the first `checkSignatureValidity` call before all validity checks for that call chain complete, permanently blocking the same hash from being approved again even though the overall operation never succeeded.

### Impact Explanation
An unprivileged/external client interacting with the Vault gateway can cause a legitimate, correctly-formed Vault request from a workflow owner to be permanently un-authorizable (until the on-chain allowlist entry naturally expires), because the replay-guard consumption happens ahead of, and independently of, the owner-ownership validation outcome. This is a denial-of-service against a specific workflow owner's allowlisted secrets operation (create/update/delete/list), reachable purely through the gateway-routed JSON-RPC entry points (`GatewayVaultRequestProcessor.authorizeAndStamp` → `Authorizer.AuthorizeRequest`) without any privileged access. [5](#0-4) 

### Likelihood Explanation
The digest is derived from request content that an external actor influences (`req.Digest()`), and the allowlist is populated by on-chain `AllowlistRequest` events tied to a specific digest with a delayed propagation window (the code even retries for up to ~30s to accommodate syncer lag) [6](#0-5) . Any window where the same digest is submitted with a payload that fails the owner check (e.g., a client bug, stale param, or a duplicate/incorrect submission racing the correct one) results in permanent denial of the legitimate request without requiring any privileged or malicious-node behavior — only a normal externally-facing gateway client request.

### Recommendation
Perform all validation (owner-match, and any other pre-conditions) before calling `replayGuard.CheckAndRecord`, so the digest is only marked "consumed" once the request is fully authorized. Reorder the checks in `authorizer.AuthorizeRequest`:
```go
if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
    return nil, ownerErr
}
if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
    return nil, err
}
```

### Proof of Concept
1. A workflow owner allowlists a request digest `D` on-chain for a `vault.secrets.create` request intended for owner `0xabc`.
2. Before the legitimate request reaches the gateway/node, any client submits a request that hashes to the same digest `D` but whose payload's secret owner field doesn't match the authorized workflow owner (or otherwise fails `validateSecretOwnersMatchAuthorized`), e.g., due to a client-side bug, prefix stripping edge case, or a duplicate submission with mutated capitalization normalized differently.
3. In `authorizer.AuthorizeRequest`: `replayGuard.CheckAndRecord(D, expiry)` succeeds and records `D` as seen [1](#0-0) ; then `validateSecretOwnersMatchAuthorized` fails and the function returns an error [2](#0-1) .
4. The legitimate workflow owner then submits the correct request (which necessarily produces the same digest `D` since the digest is tied to the exact allowlisted request). `CheckAndRecord` now returns `ErrRequestAlreadySeen` [7](#0-6) , permanently denying the legitimate, allowlisted operation until the on-chain entry expires.

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}
```
