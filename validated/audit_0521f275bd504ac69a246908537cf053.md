### Title
Unbounded `operator_fee_scalar` / `operator_fee_constant` from L1 `SystemConfig` updates can render the entire L2 unusable - ([File: crates/common/genesis/src/updates/operator_fee.rs])

### Summary
The reported bug class ("a fee-percentage-like value is not range-checked in its setter") has a direct analog in Base's derivation of the Isthmus/Jovian `operator_fee_scalar` and `operator_fee_constant` from L1 `SystemConfig` update logs. These values are decoded and applied with no bounds validation, and are later multiplied directly into every non-deposit transaction's mandatory upfront fee, with saturating (not error-returning) arithmetic all the way down to fee enforcement.

### Finding Description
`operator_fee_scalar` is a fixed-point, percentage-like value: `OPERATOR_FEE_SCALAR_DECIMAL = 1_000_000` represents 100%, exactly analogous to the reported `_feePercentage` (expected range 0–100). [1](#0-0) 

`OperatorFeeUpdate::try_from` decodes the raw `u32` scalar and `u64` constant straight from L1 log data with **no upper-bound check** (e.g., no enforcement that the scalar stay ≤ `OPERATOR_FEE_SCALAR_DECIMAL`, i.e. ≤100%): [2](#0-1) [3](#0-2) 

`SystemConfig::process_config_update_log` applies any decoded update unconditionally, with no domain validation of the resulting field: [4](#0-3) 

The unbounded scalar/constant then flow directly into the mandatory per-transaction fee formula, using only `saturating_mul`/`saturating_add` (never returning an error, never clamped to a sane percentage): [5](#0-4) 

This fee is charged upfront on every non-deposit transaction, both in the standard EVM path and the EIP-8130 payer path, and an underfunded sender is unconditionally rejected: [6](#0-5) [7](#0-6) 

Under Jovian, the multiplier is even more aggressive (`gas * scalar * 100` with no division by the decimal factor): [8](#0-7) 

### Impact Explanation
Because the scalar/constant are unregulated and are derived unconditionally from attacker-written L1 `SystemConfig` log data (in-scope per the "derivation of attacker-written L1 deposit and system-config data" category), a malicious or compromised value here forces `operator_fee_charge` to a value on the order of `U256`'s magnitude. Every legitimate transaction sender (txpool admission, block building, and execution) will then be treated as underfunded and rejected — no non-deposit transaction can be included on the L2 until a corrective `SystemConfig` update is derived. This is a full node/chain halt for L2 user transactions and an effective permanent freeze of user funds (nothing can be moved) until intervention, matching the "node halt" / "permanent freezing of funds" impact categories.

### Likelihood Explanation
Reaching this path requires only a `SystemConfig` `ConfigUpdate` log of kind `OperatorFee` with an out-of-range scalar/constant to be emitted on L1 and picked up by derivation — there is no additional protocol-level sanity check anywhere in the decode → apply → fee-calculation pipeline. The report explicitly calls out this exact bug class (unregulated percentage-like fee parameter), so the underlying weakness (missing range validation on a "fee percentage" field) is proven to be a real, previously-exploited issue in adjacent code; here it recurs in the OP-stack-derived fee scalar path.

### Recommendation
Add explicit bounds validation when decoding/applying `OperatorFeeUpdate` (and mirror it in `L1BlockInfoTx`/`L1FeeParams`): reject or clamp `operator_fee_scalar` to a sane range (e.g., ≤ `OPERATOR_FEE_SCALAR_DECIMAL`, i.e. ≤100%) and cap `operator_fee_constant` to a bounded absolute value, consistent with the upstream OP-stack spec's expectations for these fields. Additionally, consider making `operator_fee_charge_inner` return an error (or clamp) rather than silently saturating, so a corrupted/malicious value cannot silently price every transaction out of the chain.

### Proof of Concept
1. Emit (or simulate via `SystemConfigLog`) a `ConfigUpdate` log with `updateType = OperatorFee` and payload `scalar = 0xFFFFFFFF (u32::MAX)`, `constant = 0xFFFFFFFFFFFFFFFF (u64::MAX)` as accepted by `OperatorFeeUpdate::try_from` in [9](#0-8) .
2. `SystemConfig::update_with_receipts` applies it unconditionally (no bound check) via [10](#0-9) .
3. On the next L2 block, `L1BlockInfoTx::try_new` (Isthmus/Jovian branch) propagates these unbounded values into the L1 attributes deposit tx: [11](#0-10) .
4. `operator_fee_charge_inner` computes `gas.saturating_mul(scalar).saturating_mul(100)` (Jovian) or `/1_000_000` (Isthmus), producing a fee far beyond any account's balance: [12](#0-11) .
5. Every subsequent non-deposit transaction fails the upfront affordability check in both the standard handler and EIP-8130 path, halting all user activity on the L2 until the `SystemConfig` is corrected on L1.

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

impl TryFrom<&SystemConfigLog> for OperatorFeeUpdate {
    type Error = OperatorFeeUpdateError;

    fn try_from(log: &SystemConfigLog) -> Result<Self, Self::Error> {
        let LogData { data, .. } = &log.log.data;

        let validated = UpdateDataValidator::validate(data).map_err(|e| match e {
            ValidationError::InvalidDataLen(_expected, actual) => {
                OperatorFeeUpdateError::InvalidDataLen(actual)
            }
            ValidationError::PointerDecodingError => OperatorFeeUpdateError::PointerDecodingError,
            ValidationError::InvalidDataPointer(pointer) => {
                OperatorFeeUpdateError::InvalidDataPointer(pointer)
            }
            ValidationError::LengthDecodingError => OperatorFeeUpdateError::LengthDecodingError,
            ValidationError::InvalidDataLength(length) => {
                OperatorFeeUpdateError::InvalidDataLength(length)
            }
        })?;

        // The operator fee scalar and constant are
        // packed into a single u256 as follows:
        //
        // | Bytes    | Actual Size | Variable |
        // |----------|-------------|----------|
        // | 0 .. 24  | uint32      | scalar   |
        // | 24 .. 32 | uint64      | constant |
        // |----------|-------------|----------|

        let payload = validated.payload();
        let mut be_bytes = [0u8; 4];
        be_bytes[0..4].copy_from_slice(&payload[20..24]);
        let operator_fee_scalar = u32::from_be_bytes(be_bytes);

        let mut be_bytes = [0u8; 8];
        be_bytes[0..8].copy_from_slice(&payload[24..32]);
        let operator_fee_constant = u64::from_be_bytes(be_bytes);

        Ok(Self { operator_fee_scalar, operator_fee_constant })
    }

    /// Rejects the transaction when `caller` cannot cover the full upfront charge — the maximum
    /// gas cost, the transferred value, and the OP-stack L1 data and operator fees.
    ///
    /// The framework's `validate_sender` already rejects a caller that cannot cover the gas cost
    /// and value, but it is unaware of the L1 and operator fees charged here, and
    /// [`charge_upfront`] deducts with wrapping arithmetic. Without this guard an underfunded
    /// caller would silently wrap to a spurious balance instead of the transaction failing; this
    /// mirrors the revm reference, which rejects such a caller with `LackOfFundForMaxFee`.
    ///
    /// A no-op for deposits (funded on L1 and exempt) and when fee charging or balance checks are
    /// disabled (e.g. `eth_call` simulation), matching the conditions under which `validate_sender`
    /// and `charge_upfront` themselves enforce balances.
    fn ensure_can_pay_fees(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        l1_fee: U256,
        operator_fee: U256,
    ) -> HandlerResult<()> {
        let Some(tx) = envelope.as_standard() else {
            return Ok(());
        };
        if !host.feature(EvmFeatures::FEE_CHARGE) || !host.feature(EvmFeatures::BALANCE_CHECK) {
            return Ok(());
        }
        let required = U256::from(tx.gas_limit())
            .saturating_mul(U256::from(tx.max_fee_per_gas()))
            .saturating_add(tx.value())
            .saturating_add(l1_fee)
            .saturating_add(operator_fee);
        let balance =
            host.state_mut().account(&caller, false).map_err(HandlerError::Fatal)?.balance();
        if balance < required {
            return Err(HandlerError::InsufficientFunds);
        }
        Ok(())
    }
