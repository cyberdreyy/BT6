### Title
Stale per-epoch instant-withdraw ledger inflates default recovery basis and phantom reserve, overpaying early claimants and freezing the rest - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug is a stale-list/double-count: entries were not removed when a queue was disabled, so a later insertion matched an old entry. The analog lives in `IdleCreditVault`: `claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or the global `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` re-count already-claimed instant receipts for the current epoch, corrupting both sides of the recovery-price computation in `finalizeDefaultRecovery`.

### Finding Description
`requestInstantWithdraw` records the receipt in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366-374). A successful funded claim via `claimInstantWithdrawRequest` clears only the per-user aggregate (lines 387-392); the per-epoch entries are only cleared in the defaulted path `_claimDefaultedInstantWithdrawRequest` (lines 847-853), which never runs for an already-paid claim.

When default finalization happens with `pendingInstantWithdraws != 0` (partially funded instant queue, explicitly contemplated by the comments at lines 636-640):

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` (line 647), which still includes receipts that were already funded and claimed.
- `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (lines 719-721) and treats the whole excess as underlying already held by the strategy. The stale claimed portion is phantom: those tokens were already transferred out by `_transferFundedClaim`, yet the amount is added to `reserveAmount` in `finalizeDefaultRecovery` (line 686) without any matching transfer.

### Impact Explanation
`recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) is computed with a numerator and denominator both inflated by the stale amount `A`, pushing the price toward 1 (par) while the real balance is `reserveAmount - A`. Every defaulted-epoch claimant — normal `_claimDefaultedWithdrawRequest`, instant `_claimDefaultedInstantWithdrawRequest`, and post-default requests — is paid `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` via `_transferDefaultRecovery`. Early claimers therefore receive more than the true pro-rata share, the reserve is exhausted early, and all remaining claims revert on the underlying transfer: permanent freezing of unclaimed default-recovery funds and effective theft by the earliest claimers. Loss equals the stale amount `A` (up to the full prefunded instant volume of the epoch), redistributed from late claimants.

### Likelihood Explanation
Requires only ordinary unprivileged actions: a lender requests an instant withdraw during a running epoch, the CDO funds it (`collectInstantWithdrawFunds`), the user claims, then other users' instant requests remain partially unfunded and the borrower defaults before epoch end. No privileged misbehavior is needed; the instant-withdraw mode plus a mid-epoch default is a supported configuration. The attacker can split the "claim-early" and "claim-late" legs across two addresses to both inflate the price and be first in line for the overpriced payout, avoiding the self-underflow at line 848.

### Recommendation
In `claimInstantWithdrawRequest`, also clear the per-epoch entries, mirroring `_claimDefaultedInstantWithdrawRequest`:

```solidity
uint256 currentEpoch = epochNumber; // or track the request epoch
uint256 perEpoch = instantWithdrawsRequestsByEpoch[_user][currentEpoch];
instantWithdrawsRequestsByEpoch[_user][currentEpoch] = 0;
instantWithdrawClaimsByEpoch[currentEpoch] -= perEpoch;
```

This requires storing the request epoch per user (analogous to `apr0Users.principalEpoch`) since a user could hold receipts across epochs. Alternatively, decrement `instantWithdrawClaimsByEpoch[requestEpoch]` whenever a funded instant claim is paid.

### Proof of Concept
```solidity
// Foundry fork test sketch against IdleCreditVault / IdleCDOEpochVariant
// Mode: instant withdrawals enabled, running epoch, then borrower default.
function test_StaleInstantEpochLedgerInflatesRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);           // enter epoch 1 buffer

    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address attacker1 = makeAddr('attacker1');
    address attacker2 = makeAddr('attacker2');
    address honest    = makeAddr('honest');

    uint256 tA = _depositWithUser(attacker1, 50e6);   // instant leg (will claim)
    uint256 tB = _depositWithUser(attacker2, 50e6);   // stays pending (unfunded)
    uint256 tH = _depositWithUser(honest,    50e6);   // normal pending withdraw

    vm.prank(manager);
    cdoEpoch.startEpoch();
    skip(101);

    // epoch E = strategy.epochNumber(); all three request instant/normal withdraws
    _requestInstantWithUser(attacker1, tA);
    _requestInstantWithUser(attacker2, tB);
    // fund only attacker1's request via CDO liquidity, then claim
    // -> instantWithdrawsRequests[attacker1] = 0
    // -> instantWithdrawsRequestsByEpoch[attacker1][E] stays = amountA (STALE)
    // -> instantWithdrawClaimsByEpoch[E] still includes amountA
    cdoEpoch.claimInstantWithdrawRequest(); // as attacker1 via CDO

    // borrower defaults; finalizeDefaultRecovery called by CDO/owner
    _triggerBorrowerDefault();

    // pendingInstantWithdraws != 0 (attacker2 + honest unfunded)
    // defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[E]
    //   includes stale amountA -> inflated denominator
    // _defaultPrefundedInstantReserve() = instantClaims[E] - pendingInstant
    //   includes stale amountA -> phantom reserve, no backing tokens

    uint256 balBefore = underlying.balanceOf(address(strategy));
    vm.prank(manager); // or CDO finalize path
    cdoEpoch.finalizeDefault(/* recovery source funding */);

    uint256 price = strategy.defaultRecoveryPrice();
    // price is biased toward RECOVERY_FULL by stale amountA on both sides
    // attacker2 claims early at inflated price:
    vm.prank(attacker2);
    cdoEpoch.claimInstantWithdrawRequest(); // succeeds, overpaid

    // honest user's defaulted claim now reverts: reserve exhausted by phantom basis
    vm.prank(honest);
    vm.expectRevert(); // SafeERC20 transfer exceeds actual balance
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `strategy.instantWithdrawClaimsByEpoch(epoch)` remains non-zero after `attacker1`'s successful funded claim; `defaultRecoveryReserve` exceeds the strategy's actual underlying balance by exactly the stale amount; the last claimant's transfer reverts, permanently freezing their recovery.
