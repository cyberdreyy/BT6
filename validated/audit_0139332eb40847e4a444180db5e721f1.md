### Title
Builder withdrawal amount is not capped to available balance when constructing the committed `Withdrawal`, while the balance deduction is capped - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` builds the `Withdrawal` objects that are committed into `state.payload_expected_withdrawals` (and thus into the actual execution-layer payload paid to `fee_recipient`) using the *raw, uncapped* `BuilderPendingWithdrawal.amount`, whereas the corresponding balance deduction performed by `apply_withdrawals` explicitly caps the amount with `min(withdrawal.amount, builder_balance)`. This is the same bug pattern as the reported "LP token amount" issue: one code path records/commits a nominal requested amount, while the other path that actually mutates the backing balance uses a different (capped) amount, breaking the equality between what is paid out and what is actually debited.

### Finding Description
In `get_builder_withdrawals`, each entry from `state.builder_pending_withdrawals` is turned into a `Withdrawal` using the stored `amount` field verbatim: [1](#0-0) 

That `Withdrawal` list becomes `state.payload_expected_withdrawals`, which the execution layer is required to honor exactly (real ETH sent to `withdrawal.address`): [2](#0-1) 

However, when the *beacon-state* accounting for the same withdrawal is later applied, the deduction from the builder's tracked balance is explicitly capped so it can never go negative: [3](#0-2) 

The existence of `min(withdrawal.amount, builder_balance)` in `apply_withdrawals` proves the spec authors anticipated a state where `builder.balance < withdrawal.amount` at withdrawal-processing time. But `get_builder_withdrawals` — the function that decides what actually gets paid out on the execution layer — never performs the same capping. So the two paths can diverge: the payload commits to paying the *uncapped* `withdrawal.amount` to `fee_recipient`, while the consensus-side ledger only debits `min(withdrawal.amount, builder_balance)` from the builder. If `builder.balance` is smaller than the queued `amount` (e.g. because the builder's balance was already reduced by an earlier withdrawal/sweep/exit that emptied the balance while a second pending withdrawal for the same builder is still queued), the execution layer would pay out more Gwei than is backed by the builder's remaining balance — Gwei created and paid to a recipient beyond what the protocol's own ledger reflects.

### Impact Explanation
This falls under "Gwei created… or paid to a non-owner" / "a payload or payment applied that the block did not commit to as intended" — the withdrawal amount actually paid on the execution layer is not reconciled with the amount actually removed from the builder's balance, so the value paid out can exceed what the builder's state entitles them to. This is a Critical-class issue per the rubric if reachable, since it breaks the invariant that Gwei paid to any party must be backed by an equal decrease somewhere in state.

### Likelihood Explanation
Exploitability hinges on whether the protocol elsewhere guarantees `sum(pending withdrawal amounts for a builder) <= builder.balance` at all times before `get_builder_withdrawals` runs. There is evidence (e.g. `process_execution_payload_bid` balance-sufficiency checks referenced in `test_process_execution_payload_bid_sufficient_balance_with_pending_withdrawals`) that new bids are only accepted if `balance - bid - existing_pending_withdrawals >= MIN_ACTIVATION_BALANCE`, which is designed to preserve this invariant. Whether every single path that appends to `state.builder_pending_withdrawals` (payment settlement, builder-exit requests, older-than-previous-epoch direct append in `apply_parent_execution_payload`) is bound by that same check, and whether the invariant can be violated across epoch boundaries or via interleaving of multiple queued withdrawals for the same builder, could not be fully confirmed within the scope of this review. The presence of the defensive `min()` in `apply_withdrawals` strongly suggests the authors considered the shortfall case reachable, which is why the missing symmetric cap in `get_builder_withdrawals` is a real code-level defect rather than a purely theoretical one — but a complete proof of an end-to-end reachable path was not established in this pass.

### Recommendation
In `get_builder_withdrawals` (and analogously in `get_builders_sweep_withdrawals` if applicable), cap the committed `Withdrawal.amount` to `min(withdrawal.amount, state.builders[builder_index].balance)` at the time the `Withdrawal` object is constructed, so the amount actually paid to the execution layer is always identical to the amount deducted from the builder's balance in `apply_withdrawals`.

### Proof of Concept
Not fully constructible without confirming whether an interleaving of multiple `BuilderPendingWithdrawal` entries for the same builder can exceed `builder.balance` given the balance-sufficiency checks in `process_execution_payload_bid`. The core code-level mismatch (uncapped amount used to build the committed `Withdrawal` vs. capped amount used for the balance deduction) is demonstrated directly by the cited lines in `get_builder_withdrawals` and `apply_withdrawals`.
