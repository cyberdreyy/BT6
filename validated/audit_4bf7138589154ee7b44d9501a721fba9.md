### Title
`parse_signers` mislabels the true Burn/MintTo/CloseAccount/FreezeAccount authority as a multisig when a trailing padding account is added, misreporting the real signer - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_signers` decides whether an instruction used a single authority or a multisig authority purely by comparing `accounts.len()` to `last_nonsigner_index + 1`, with no verification that the account actually pointed to by the "extra" index is a real SPL-Token `Multisig` account or that trailing accounts were real cosigners. Any unprivileged transaction submitter can append one arbitrary extra account index to a `Burn`/`MintTo`/`CloseAccount`/`FreezeAccount`/etc. instruction (which the on-chain SPL-Token-2022 program silently ignores since it never validates account-count), causing `getTransaction`/`getBlock` with `jsonParsed` encoding to report the real, single, non-multisig authority under `multisigAuthority` and an unrelated non-signing account under `signers`.

### Finding Description
In `parse_signers`, the single-vs-multisig decision is made solely from the length of the instruction's account list relative to `last_nonsigner_index`: [1](#0-0) 

For `Burn` (and identically for `MintTo`, `CloseAccount`, `FreezeAccount`, `ThawAccount`, `Transfer`, `TransferChecked`, `BurnChecked`, etc.) the call site is: [2](#0-1) 

`check_num_token_accounts` only enforces a *minimum* account count and places no upper bound on how many accounts a client may attach to the instruction: [3](#0-2) 

The real spl-token-2022 on-chain program decides single-vs-multisig by attempting to deserialize the account *at* the authority position as a `Multisig` struct — it does not care how many trailing accounts were included in the instruction, and it simply ignores any extra unused account indices that a client passes beyond what it reads. This means a caller can build a completely valid, on-chain-successful `Burn` instruction with accounts `[account, mint, real_authority, padding_account]`, where `real_authority` is an ordinary keypair (not a `Multisig` account) and `padding_account` is any arbitrary pubkey that plays no signing role at all. The transaction executes successfully because the program never reads or checks the 4th account.

When this finalized transaction is later fetched with `getTransaction`(`encoding: "jsonParsed"`), `parse_token` → `parse_signers` sees `accounts.len() (4) > last_nonsigner_index + 1 (3)` and therefore takes the multisig branch: it labels `real_authority` as `"multisigAuthority"` and reports `[padding_account]` as `"signers"`, even though `real_authority` is the sole true signer and `padding_account` had no role in authorization whatsoever. The `"authority"`/`"owner"`/`"freezeAuthority"` field that downstream integrators typically key off of for "who authorized this action" is never emitted at all in this case.

Existing tests already implicitly demonstrate that arbitrarily-sized account lists are accepted without validation or panic (`check_no_panic` loops over 0..20 accounts for confidential-burn/permissioned-burn parsers), confirming the length-based heuristic has no safeguard against padding: [4](#0-3) 

### Impact Explanation
This is a decoder misreporting bug in `transaction-status`, reachable via a single `getTransaction`/`getBlock` `jsonParsed` RPC call on a transaction the attacker fully controls the construction of (and needs no elevated privilege to submit). Downstream integrators, exchanges, explorers, and compliance/monitoring tooling that consume the parsed JSON and treat `"authority"` vs `"multisigAuthority"`/`"signers"` as authoritative attribution of who burned/minted/froze/closed a token account will attribute the action to the wrong entity (the real signer is buried anonymously inside a `"signers"` array while an uninvolved account is elevated to the `"authority"`/`"multisigAuthority"` label, or vice versa in other constructions). This matches the "decoder ... misreporting" category explicitly called out as in-scope in the Validate section.

### Likelihood Explanation
Fully attacker-controlled and trivially repeatable: constructing an instruction with one extra trailing account index costs nothing, requires no special privileges, and the on-chain spl-token-2022 program does not reject or even notice the padding account since it never validates instruction account-count beyond what it reads. Any wallet, bot, or dApp building `Burn`/`MintTo`/`CloseAccount`/`FreezeAccount` instructions with an extra account (even accidentally, e.g., a client library adding a placeholder/compute-budget-unrelated account) will trigger this misreporting on every subsequent `getTransaction` parse.

### Recommendation
Do not infer single-vs-multisig purely from account-list length. Either:
- Only take the multisig branch when the account at `last_nonsigner_index` can actually be recognized/decoded as a `Multisig` account (requires account data, which `transaction-status` does not have access to during parsing — so at minimum this ambiguity should be documented), or
- Cap accepted extra accounts by instruction-specific maximums matching each `TokenInstruction` variant's documented multisig account layout, rejecting (or flagging as ambiguous) any additional accounts beyond a sane bound, or
- Emit both a best-effort `"authority"`-style field and treat any extra accounts as unverified/ambiguous rather than asserting them as multisig signers, to avoid mislabeling.

### Proof of Concept
```rust
// transaction-status/src/parse_token.rs (test module)
#[test]
fn test_burn_signers_boundary_misreport() {
    use {
        solana_message::{AccountKeys, compiled_instruction::CompiledInstruction},
        solana_pubkey::Pubkey,
        spl_token_2022_interface::instruction::TokenInstruction,
    };

    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let real_authority = Pubkey::new_unique(); // ordinary keypair, NOT a Multisig account on-chain
    let padding_account = Pubkey::new_unique(); // never signs, never read by the on-chain program

    let account_keys_vec = vec![account, mint, real_authority, padding_account];
    let account_keys = AccountKeys::new(&account_keys_vec, None);

    let data = TokenInstruction::Burn { amount: 42 }.pack();
    let compiled_instruction = CompiledInstruction {
        program_id_index: 4, // arbitrary index not used by parse_token boundary check
        accounts: vec![0, 1, 2, 3], // minimum(3) + 1 padding account
        data,
    };

    let parsed = parse_token(&compiled_instruction, &account_keys).unwrap();

    // Bug: the true sole authority is mislabeled as "multisigAuthority",
    // and the unrelated padding account is reported as a "signer",
    // even though on-chain, `real_authority` is the only actual signer
    // and `padding_account` plays no role at all.
    assert_eq!(
        parsed.info["multisigAuthority"],
        real_authority.to_string()
    );
    assert_eq!(
        parsed.info["signers"][0],
        padding_account.to_string()
    );
    // "authority" field, which downstream consumers expect for a
    // single-signer Burn, is absent:
    assert!(parsed.info.get("authority").is_none());
}
```
This test only exercises code already present in `transaction-status/src/parse_token.rs` (`parse_token`/`parse_signers`) and demonstrates the exact boundary condition (`accounts.len() == last_nonsigner_index + 2`) at which a genuinely single-signer instruction is mislabeled as multisig, with the real authority attributed incorrectly and an uninvolved pubkey reported as a "signer".

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
