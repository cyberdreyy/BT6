### Title
Blacklisted user cannot claim matured withdraw requests: receipt tokens are non-transferable and payouts are hardcoded to `msg.sender` - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` withdraw claims always send underlying tokens to the request owner (`_user`, i.e. `msg.sender` relayed through `IdleCDOEpochVariant.claimWithdrawRequest`), with no way to specify an alternative recipient. Unlike the Footium report, the situation is worse here: the strategy-token "receipt" that represents the claim is non-transferable (`_transfer` reverts for any caller other than the CDO), so a user blacklisted by the underlying token (e.g. USDC) cannot even move the receipt to a clean address. The matured withdrawal is permanently frozen.

### Finding Description
- `IdleCDOEpochVariant.claimWithdrawRequest()` forwards `msg.sender` as the only possible beneficiary: `IdleCreditVault(strategy).claimWithdrawRequest(msg.sender)` (contracts/IdleCDOEpochVariant.sol:967-971). Same for `claimInstantWithdrawRequest` (line 975-979).
- All payout paths inside `IdleCreditVault` (`_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `_claimLossAdjustedWithdrawRequest`, `_claimFundedWithdrawRequest`, `claimInstantWithdrawRequest`) ultimately call `_transferFundedClaim(_user, ...)` / `_transferDefaultRecovery(_user, ...)`, which do `underlyingToken.safeTransfer(_user, _amount)` (contracts/strategies/idle/IdleCreditVault.sol:897-917).
- The receipt tokens minted to the user in `requestWithdraw` (`_mint(_user, _amount)`, line 275) cannot be transferred: `_transfer` reverts unless `msg.sender == idleCDO`, and `setCanTransfer(true)` is permanently disabled (lines 939-951).

If a lender's address is blacklisted by a blacklistable underlying (vaults commonly use USDC), the `safeTransfer(_user, ...)` reverts, every claim reverts, and the receipt cannot be sold, transferred, or claimed to another address — the funded underlying sits in the vault forever. Burning/re-requesting is also blocked: `requestWithdraw` reverts if a loss-adjusted receipt is still open (lines 263-271), so the user cannot reroute.

### Impact Explanation
Permanent freezing of the user's full matured withdrawal principal + interest. The funds are solvent and funded in the vault, but the address-bound claim can never execute. Loss equals the entire receipt value.

### Likelihood Explanation
Requires the user to be blacklisted by the underlying token's issuer — a low-probability external event — hence Medium rather than High, consistent with the original Footium finding.

### Recommendation
Add a recipient parameter: `claimWithdrawRequest(address _to)` / `claimInstantWithdrawRequest(address _to)` on `IdleCDOEpochVariant`, pass it through to `IdleCreditVault.claimWithdrawRequest(_user, _to)`, keep accounting/burn keyed on `_user` but send underlying to `_to`. Only the receipt owner can trigger the claim, so this cannot be abused to steal claims.

### Proof of Concept
```solidity
// Fork test on an epoch vault with a blacklistable underlying (e.g. USDC).
// Mock pattern: a Blacklister token mock where setBlacklist(user) makes transfer(user, x) revert.

function testBlacklistedUserClaimFrozen() external {
    address user = makeAddr('user');
    // 1. user deposits, epoch runs and stops normally
    _depositWithUser(user, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // 2. user requests withdraw; receipt strategy tokens minted to user
    vm.prank(user);
    uint256 claimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(claimBasis, 0);

    // 3. next epoch funded at stopEpoch; receipt is now claimable
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // 4. underlying issuer blacklists user
    BlacklistableMock(defaultUnderlying).blacklist(user);

    // 5. claim reverts on safeTransfer(user, amount) — no recipient override exists
    vm.prank(user);
    vm.expectRevert(); // blacklist revert bubbles through NotAllowed path
    cdoEpoch.claimWithdrawRequest();

    // 6. user cannot escape by transferring the receipt — _transfer reverts
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    IERC20Detailed(address(strategy)).transfer(makeAddr('clean'), claimBasis);

    // 7. user cannot re-request either while the loss/adjusted receipt is open
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // funds remain in the vault indefinitely
    assertGe(underlying.balanceOf(address(strategy)), claimBasis);
}
```
