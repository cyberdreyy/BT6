### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing a request to execute below the effective live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only removes *requests originated by* the deleted member and clears that member's `num_requests_pk` entry, but it never scrubs the deleted member's public-key/account-id string from the `confirmations` set of *other* still-pending requests it had confirmed. `confirm()` simply counts `confirmations.len()` against `self.num_confirmations` without checking that each confirming identity is still a current member, so a stale confirmation from a removed member still counts toward reaching the threshold.

### Finding Description
`confirm()` performs no membership re-validation on already-recorded confirmations: [1](#0-0) 

`delete_member()` filters requests by `r.member == member` (the *creator* of the request) and removes those requests' confirmation sets entirely, but any confirmation the same member cast on a request created by someone else (via `confirm()` -> `confirmations.insert(member.to_string())`, line 311) is left untouched in the `confirmations: LookupMap<RequestId, HashSet<String>>` storage: [2](#0-1) 

The invariant this breaks is "confirmations counted == live members who actually approved," i.e. `confirmations.len()` at execution time should equal the number of *current* members who confirmed. Instead, after a member is removed, `confirmations.len()` for pending requests they had confirmed retains a "ghost" vote from a non-member, so the equality `confirmations_counted == live_confirming_members` no longer holds — the recorded count exceeds the true number of authorized approvers.

This mirrors the reported `QuestSystem` bug class: a check (`maxCompletions`/`num_confirmations`) is validated against state that is updated on one action (`completions[questId]`/`confirmations.insert`) but never invalidated when the precondition backing an earlier action changes (quest definition change / membership change), letting stale prior state count toward a later threshold.

### Impact Explanation
This directly falls into the Critical impact category: "a multisig request executed below threshold." If `num_confirmations = 3` and a member is confirmed on a pending request, then removed from the multisig (e.g., because their key was compromised or they left the organization), their stale confirmation persists. The transaction can then execute with only `num_confirmations - 1` *live* member approvals plus one ghost vote from a non-member — funds transfer, key additions/removals, or contract deployments can be authorized without the intended number of currently-trusted signers.

### Likelihood Explanation
Requires only ordinary multisig operations that are explicitly supported: (1) a member confirms a request created by another member, (2) that member is subsequently removed via a legitimate `DeleteMember` multisig action (which itself needs threshold approval, but is a normal governance action, not a privilege escalation by the attacker), (3) remaining members continue confirming the still-pending request unaware the count already includes a non-member's vote. No exploitation of cryptography or out-of-scope actors is needed beyond the multisig's own documented member-management flow, and the bug is deterministic given the code path shown.

### Recommendation
When removing a member in `delete_member`, iterate over **all** pending requests (not just ones the member created) and remove the member's entry from each request's `confirmations` set, decrementing any cached count accordingly. Alternatively, have `confirm()`/`execute_request` re-validate that every account/key in `confirmations` is still `self.members.contains(...)` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C, D], 3)`.
2. `B` calls `add_request(...)` creating request `R` (transfer to some receiver).
3. `A` calls `confirm(R)` → `confirmations[R] = {A}` (1/3).
4. Members execute a separate multisig flow (`AddRequest`/`confirm` x3) for `MultiSigRequestAction::DeleteMember { member: A }`, executed and `A` removed. Per `delete_member`, only requests where `r.member == A` (i.e., requests A created) are purged; `R` (created by `B`) is untouched, so `confirmations[R]` still contains `A`'s stale vote.
5. `C` calls `confirm(R)` → `confirmations[R] = {A, C}` (2/3).
6. `D` calls `confirm(R)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` fires.
7. Result: `R` executed with confirmations from only 2 live members (`C`, `D`) plus a removed non-member (`A`), i.e., below the intended live-member threshold of 3.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
