### Title
Unbounded per-request compression/allocation cost in `getMultipleAccounts` with Base64Zstd encoding over up to `MAX_MULTIPLE_ACCOUNTS` maximal-size accounts - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_multiple_accounts` enforces only a *count* limit (`MAX_MULTIPLE_ACCOUNTS`, default 100) on the number of pubkeys, but applies no aggregate byte-size cap on the accounts returned. A single request for up to 100 pubkeys, each pointing to an attacker-authored account near the maximum account size, with `encoding=base64+zstd`, causes the server to sequentially run `get_encoded_account` → `encode_account` → `encode_ui_account` for each account, zstd-compressing full account data for every one, resulting in outsized aggregate CPU/allocation cost for one RPC call.

### Finding Description
The RPC entrypoint `AccountsDataImpl::get_multiple_accounts` only validates `pubkey_strs.len() > max_multiple_accounts` (default `MAX_MULTIPLE_ACCOUNTS = 100`) before calling `meta.get_multiple_accounts(pubkeys, config)`. [1](#0-0) 

`JsonRpcRequestProcessor::get_multiple_accounts` then loops over every pubkey and, for each one, spawns a blocking task calling `get_encoded_account(&bank, &pubkey, encoding, data_slice, None)`, awaiting completion before starting the next: [2](#0-1) 

`get_encoded_account` → `encode_account` → `encode_ui_account` performs, for `UiAccountEncoding::Base64Zstd`, a full zstd compression pass over the account's data buffer with no size guard: [3](#0-2) 

There is no check anywhere in this path bounding the sum of `account.data().len()` across the batch, unlike the base58 path which has an explicit `MAX_BASE58_BYTES` (128 bytes) guard in `encode_account`: [4](#0-3) 

Since accounts are attacker-controlled state (the attacker only needs to have previously stored large accounts on-chain, which is within the allowed "writing on-chain data later returned through RPC" threat model), a single `getMultipleAccounts([pk_1..pk_100], {encoding: "base64+zstd"})` call forces the validator's RPC blocking-thread pool to sequentially compress up to 100 large accounts. The per-request cost scales linearly with `MAX_MULTIPLE_ACCOUNTS × max_account_data_size` with no explicit aggregate byte limit — only the fixed count limit exists.

Note: the loop is a `for` loop that `.await`s each `spawn_blocking` call immediately (not `join_all`), so execution is sequential rather than a concurrent thread-pool flood; this reduces (but does not eliminate) the peak-memory/parallelism amplification, since only one account is being encoded/compressed at a time. The primary residual issue is elevated single-request wall-clock/CPU cost with no documented or enforced aggregate byte bound, not concurrent thread-pool exhaustion.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" category: one client, one JSON-RPC request within rate limits, can force the validator's RPC service to perform up to 100 full-account zstd compressions (bounded by whatever the maximum on-chain account size actually is), a cost that is not bounded by any explicit aggregate limit — the only limit enforced is the account *count* (`MAX_MULTIPLE_ACCOUNTS`), not aggregate bytes/CPU-time. This ties up `rpc_blocking_threads` (default `max(num_cpus/4, 1)`), degrading RPC service responsiveness for other clients under repeated exploitation, though it is confined to the RPC service and does not affect consensus, ledger correctness, or the leader/replay path.

### Likelihood Explanation
Trivial precondition: the attacker only needs to be able to fund large accounts on-chain in advance (already permitted as "writing on-chain data later returned through those APIs") and then issue a single, standards-compliant `getMultipleAccounts` call within the rate constraint (one call per `CLUSTER_SLOT_TIME_TARGET / 2`). No special privileges, no protocol violation, no malformed input — `encoding=base64+zstd` and 100 pubkeys are both fully within the documented/allowed RPC parameter ranges. The attack is fully repeatable at the permitted call rate.

### Recommendation
Add an aggregate data-size budget check in `JsonRpcRequestProcessor::get_multiple_accounts` (and/or in `encode_account`/`encode_ui_account`) analogous to the existing `MAX_BASE58_BYTES` guard for base58, rejecting or truncating requests whose summed `account.data().len()` across all requested pubkeys exceeds a configurable byte limit, particularly when `Base64Zstd`/`JsonParsed` encodings are used. Alternatively, apply per-request CPU-time/byte-processing budgeting shared across the blocking thread pool for `getMultipleAccounts` and `getAccountInfo`.

### Proof of Concept
Integration test plan (extending the existing `test_rpc_get_multiple_accounts` harness in `rpc/src/rpc.rs`):
1. Using `RpcHandler::start()`, store `MAX_MULTIPLE_ACCOUNTS` (100) accounts via `bank.store_account`, each with data close to the maximum permitted account size.
2. Build a `getMultipleAccounts` request with all 100 pubkeys and `{"encoding": "base64+zstd"}`.
3. Wrap `rpc.handle_request_sync(request)` with `Instant::now()` timing and a peak-memory sampler (e.g., via `jemalloc_ctl` or `/proc/self/status` VmHWM on Linux).
4. Assert wall-clock time and peak memory stay under a documented per-request bound (e.g., proportional to a single account's cost × small constant), failing the assertion demonstrates the aggregate cost scales linearly with `MAX_MULTIPLE_ACCOUNTS × account_size` with no cap, i.e., is currently unbounded relative to any single-account baseline.

    pub async fn get_multiple_accounts(
        &self,
        pubkeys: Vec<Pubkey>,
        config: Option<RpcAccountInfoConfig>,
    ) -> Result<RpcResponse<Vec<Option<UiAccount>>>> {
        let RpcAccountInfoConfig {
            encoding,
            data_slice,
            commitment,
            min_context_slot,
        } = config.unwrap_or_default();
        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
