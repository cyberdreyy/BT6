### Title
Zip archive extraction lacks path-containment checks, enabling Zip Slip path traversal - (`helpers/archives/zip_extract.go`)

### Summary
`extractZipFileEntry`, `extractZipSymlinkEntry`, and `extractZipDirectoryEntry` in `helpers/archives/zip_extract.go` write to `file.Name` from the zip's `zip.File` header without ever validating that the resolved path stays under the intended extraction root. This is the same class of bug that `commands/helpers/archive/tarzstd/tarzstd_extractor.go` explicitly guards against with a `filepath.Abs` + `strings.HasPrefix` chroot check, but the equivalent guard is entirely absent from the zip path.

### Finding Description
`ExtractZipArchive` iterates `archive.File` and calls `extractZipFile(file)` for every entry [1](#0-0) . `extractZipFile` only creates parent directories via `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and then dispatches by file type [2](#0-1) . The regular-file path calls `os.OpenFile(file.Name, ...)` directly [3](#0-2) , and the symlink path calls `os.Symlink(string(data), file.Name)` with the link target read straight from the zip entry's own file content [4](#0-3) . `file.Name` is attacker-controlled zip metadata (`zip.File.Name`) and is used verbatim as an OS path — there is no `filepath.Clean`, no rejection of `..` segments, no rejection of absolute paths, and no comparison against a destination root.

This is in stark contrast to the sibling tar/zstd extractor, which computes `path = filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects it unless `strings.HasPrefix(path, e.dir+string(filepath.Separator))` [5](#0-4) . The zip code path has no analogous check anywhere in `zip_extract.go`; the only sanitization present is `errorIfGitDirectory`, which only warns about `.git` paths and does not stop extraction or perform path containment [6](#0-5) .

Compounding this, the `ziplegacy` extractor — which wraps `archives.ExtractZipArchive` and is invoked with a `dir` parameter from callers like `commands/helpers/artifacts_downloader.go` — never uses that `dir` field at all: `Extract` just calls `archives.ExtractZipArchive(zr)` with no `chdir` or path-join against `e.dir` [7](#0-6) . So the caller-supplied destination root is a no-op for this extractor; extraction paths are resolved solely against the process's current working directory, and a crafted `file.Name` such as `../../etc/passwd` or an absolute path `/etc/passwd` (or a symlink entry whose data points outside the tree, followed by a same-name file entry) is written wherever the OS permissions of the runner/helper process allow.

I was not able to fully confirm, within the remaining tool budget, whether `fastzip`'s extractor (a third zip implementation in `commands/helpers/archive/fastzip/zip_fastzip_extractor.go`) is the default used instead of `ziplegacy` in production build/artifact flows, or under what configuration `ziplegacy`/`helpers/archives.ExtractZipFile` is actually reached (e.g., legacy artifact download fallback, `cache_extractor.go`, or `docker.New`-driven copy-out of build artifacts referenced in the question). This should be verified before treating impact as certain in all code paths, but the core defect — missing path containment in `helpers/archives/zip_extract.go` — is real and demonstrable in isolation.

### Impact Explanation
If a job (or a downstream job consuming another job's artifact via `dependencies:`) can get such a zip processed by this code path, `extractZipFileEntry`/`extractZipSymlinkEntry` will write/overwrite files or create symlinks outside the intended build/artifact/cache root, up to the OS permissions of the process performing extraction (typically the job's own user/container, so scope is bounded by that user's filesystem access, but can still corrupt/overwrite files outside the designated build directory, e.g. other paths writable by that same user, shared caches, or via symlink+write two-step to escape further).

### Likelihood Explanation
Exploitability requires the attacker to control the entries of a zip file that reaches `ExtractZipArchive`/`ExtractZipFile` — feasible whenever a job can influence the raw bytes/entry names of the artifact/cache zip it or a dependent job downloads. Reachability is confirmed at the `helpers/archives/zip_extract.go` level via unit tests exercising `ExtractZipFile` directly [8](#0-7) ; the production call graph through `ArtifactsDownloaderCommand` → `archive.NewExtractor` → `ziplegacy.extractor.Extract` → `archives.ExtractZipArchive` is present in code [9](#0-8) [7](#0-6) , but I could not verify from the index whether `ziplegacy` (vs. `fastzip`, which may already sandbox paths) is the actually-selected implementation for zip artifacts/cache in the current default configuration, nor whether the docker `helpers/docker/options.go` copy-out path (referenced in the question) invokes this same code or a different tar-based path (Docker's own copy API typically uses tar, not zip, which would make the docker-specific framing in the question potentially inaccurate).

### Recommendation
Add the same containment check used in `tarzstd_extractor.go` to `helpers/archives/zip_extract.go`: resolve each entry against an explicit destination root with `filepath.Abs(filepath.Join(root, file.Name))`, reject the entry if the result does not have `root+separator` as a prefix, and apply the identical check to symlink targets (reject symlinks whose target, once resolved, escapes `root`). Also make `ziplegacy.extractor.Extract` actually honor `e.dir` (chdir into it or thread it through as the root for the new containment check) so the currently-unused `dir` parameter is enforced rather than silently ignored.

### Proof of Concept
```go
func TestExtractZipFile_PathTraversal(t *testing.T) {
    tmpDir := t.TempDir()
    outsideMarker := filepath.Join(filepath.Dir(tmpDir), "zipslip_poc.txt")
    defer os.Remove(outsideMarker)

    zipPath := filepath.Join(tmpDir, "evil.zip")
    f, _ := os.Create(zipPath)
    zw := zip.NewWriter(f)
    w, _ := zw.Create("../zipslip_poc.txt") // traversal entry
    w.Write([]byte("pwned"))
    zw.Close()
    f.Close()

    wd, _ := os.Getwd()
    os.Chdir(tmpDir)
    defer os.Chdir(wd)

    err := archives.ExtractZipFile(zipPath)
    require.NoError(t, err)

    // Assert file escaped tmpDir and landed outside intended extraction root
    _, statErr := os.Stat(outsideMarker)
    assert.NoError(t, statErr, "zip entry escaped destination root via ../ traversal")
}
```
Expected result on current code: the assertion passes (file is created outside `tmpDir`), demonstrating the bug. After adding a `tarzstd`-style containment check, `ExtractZipFile`/the containment-checked equivalent should return an error and `outsideMarker` should never be created.

```go
func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
```

```go
func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}
```
