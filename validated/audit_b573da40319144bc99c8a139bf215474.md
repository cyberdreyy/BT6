### Title
Unprivileged ERC4626 liquidity drain permanently reverts `stopEpoch` via `ProgrammableBorrower.onStopEpoch`, freezing all pool withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external bug is a blocking call in a single shared worker that stalls every other service. The analog in this codebase is `ProgrammableBorrower.onStopEpoch`, called inline by `IdleCDOEpochVariant._stopEpoch` at contracts/IdleCDOEpochVariant.sol:398. When the idle liquidity is parked in an external ERC4626 vault whose assets are covered by share value (`convertToAssets`) but not withdrawable (`withdraw` reverts), the hook reverts with `StopEpochVaultLiquidityUnavailable` and the entire `stopEpoch` transaction reverts. An unprivileged user of the borrower's ERC4626 vault (explicitly an allowed attacker role) can create exactly this state by draining the vault's liquid balance into lent-out markets, so `shortfall <= _currentVaultAssets()` while `vault.withdraw(shortfall)` keeps reverting. This blocks the epoch state machine for every depositor and withdrawer, not just the attacker.

### Finding Description
In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:231-268) the liquidity guard distinguishes two failure modes: [1](#0-0) 

- If `shortfall > _currentVaultAssets()` the hook returns `true`, letting `getFundsFromBorrower`'s `transferFrom` fail so IdleCDO enters the default path.
- If `shortfall <= _currentVaultAssets()` but `vault.withdraw(shortfall)` reverts, the hook reverts `StopEpochVaultLiquidityUnavailable`.

`_currentVaultAssets()` is share-value based (`convertToAssets`), not liquidity based (`maxWithdraw`/vault idle balance). For real ERC4626 vaults like Morpho/Gauntlet (used in the fork tests at test/foundry/ProgrammableBorrowerCreditVault.t.sol:344-399), share value reflects assets supplied to underlying lending markets, while `withdraw` reverts when the markets have no idle liquidity. An attacker who can interact with those markets (e.g., supply collateral and borrow, or withdraw all idle liquidity as a vault user) makes `withdraw` revert while `convertToAssets` still covers the shortfall. Every subsequent `manager.stopEpoch` call then reverts at the same point, before `_updateAccounting`, fee transfers, or `pendingWithdraws` settlement, and before any default can be recorded — `stopEpoch` never reaches `_handleBorrowerDefault` because the hook reverts instead of returning `false` (contracts/IdleCDOEpochVariant.sol:395-404).

The regression tests confirm the mechanics: `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` shows the revert keeps the epoch running with no default and no withdrawal funding [2](#0-1) , and `testProgrammableBorrowerStopEpochDoesNotTrustBrokenMaxWithdraw` shows share-value coverage is what the code trusts, not `maxWithdraw` [3](#0-2) .

### Impact Explanation
Temporary freezing of all user funds with quantifiable duration and cost. While `stopEpoch` reverts, `epochEndDate` keeps passing with `isEpochRunning == true`: pending withdraw receipts in `IdleCreditVault.pendingWithdraws` are never funded (`collectWithdrawFunds` is unreachable), `claimWithdrawRequest` reverts because `epochNumber <= lastWithdrawRequest[_user]` (contracts/strategies/idle/IdleCreditVault.sol:326), new epochs cannot start, and queued withdrawals in `IdleCDOEpochQueue.processWithdrawRequests` cannot be processed. The attacker controls duration: each time liquidity frees, they can re-drain it before the honest manager retries. Cost is the capital needed to absorb the vault's idle liquidity (borrowed capital on Morpho carries only interest cost). The whole pool TVL plus all pending receipts are frozen for the attack duration — this matches the "sleep the single main RPC worker" class: one shared chokepoint blocks every service.

### Likelihood Explanation
Requires (a) the pool runs in programmable-borrower mode and (b) on-hand cash at the borrower is below `_amountToPullFromBorrower + _pendingWithdraws`, i.e., funds are parked in the vault — the normal state, since `onStartEpoch` deposits all idle balance into the vault [4](#0-3) . The attacker only needs to make the underlying ERC4626 illiquid at epoch end; on Morpho-style vaults this is routine market behavior (full utilization) that can be induced or simply awaited and reinforced. No privileged role, no KYC, and no pool position is needed. Existing guards don't stop it: the `shortfall > _currentVaultAssets()` early-return only helps when share *value* is insufficient, not when liquidity is; `onDefault`'s comment acknowledges the view can be unavailable but only protects the default path, which is never reached. Likelihood is moderate — it needs programmable mode and a cooperative/attackable vault market — and impact per incident is bounded to a temporary freeze rather than permanent loss (eventually liquidity returns or the facility defaults), consistent with Medium.

### Recommendation
In `onStopEpoch`, fall back to the default path instead of reverting when the vault is economically covered but illiquid: catch the `vault.withdraw` failure and return `false` (or `true` and let `transferFrom` fail) so `_handleBorrowerDefault` engages rather than leaving `stopEpoch` permanently retry-blocked. Alternatively, check real withdrawability (`vault.maxWithdraw(address(this))`) against `shortfall` before attempting the withdrawal, treating `shortfall > maxWithdraw` as a borrower repayment failure that IdleCDO's default machinery already handles. Retaining a revert path is reasonable only for transient failures that cannot be adversarially sustained; liquidity drain is sustainable, so it must degrade to default accounting, not to an unbounded retry loop blocking the epoch.

### Proof of Concept
Foundry fork test (Morpho/Gauntlet mainnet fork, as in `ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testStopEpochDosViaVaultLiquidityDrain() external {
    _setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);
    IERC4626 vault = IERC4626(GAUNTLET_USDC_PRIME);
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);

    // a user queues a normal withdrawal so stopEpoch must pull cash
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0); // idle balance is deposited into the ERC4626 vault

    // ATTACKER: a user of the same ERC4626 vault drains its liquid balance
    // (e.g., withdraws all idle USDC, or borrows it in the underlying Morpho market),
    // leaving share value intact but liquidity at zero.
    deal(USDC, attacker, 0);
    uint256 idle = USDC.balanceOf(address(vault)); // or vault's market liquidity
    // attacker withdraws / borrows `idle` from the vault's underlying market
    // => vault.convertToAssets(shares) still covers shortfall, vault.withdraw reverts

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Every retry reverts while the market stays illiquid; epoch never ends:
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());           // no default recorded, no recovery path
    assertGt(strategy.pendingWithdraws(), 0);    // receipts never funded
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();             // epochNumber <= lastWithdrawRequest
}
```

On each later retry after liquidity frees, the attacker re-drains idle vault liquidity in the same or a preceding transaction, so `stopEpoch` never succeeds and no default/finalization path is reachable — all pool funds and pending receipts remain frozen for the attack duration.
