### Title
Dust deposit in prefunded queue bricks `stopEpochWithDuration` via `prefundedDepositsToProcess` revert - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The prefunded epoch variant settles queued deposits inside `stopEpochWithDuration` via `_afterStopEpochWithDuration`, which calls `IdleCDOEpochQueue.prefundedDepositsToProcess()`. That view reverts whenever `epochPendingDeposits[_epoch] != 0` for the epoch being settled. An unprivileged KYC-passing depositor can leave a 1-wei `requestDeposit` sitting unprefunded in `epochPendingDeposits`, causing every `stopEpochWithDuration` call to revert — the same "crafted input resets expected state so the legitimate call fails its check" pattern as CVE-2016-9042 (crafted NTP packet resets `torg`, legitimate replies fail TEST2 and are dropped).

### Finding Description
In `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration` (contracts/IdleCDOEpochVariantPrefunded.sol:72-89), the base stop flow calls `_epochQueue.prefundedDepositsToProcess()`. In `IdleCDOEpochQueue.prefundedDepositsToProcess` (contracts/IdleCDOEpochQueue.sol:277-282), the function reverts via `_checkNotAllowed(epochPendingDeposits[_epoch] != 0)` — the "expected state" check. Any unprefunded queue deposit for the epoch therefore makes the entire `stopEpochWithDuration` transaction revert.

`requestDeposit` (lines 103-127) only blocks new deposits once `epochPrefundedDeposits[nextEpoch] != 0` or once inside `prefundedDepositWindow`; before that cutoff any KYC'd wallet can add arbitrary (including 1-wei) deposits. `processDepositsToBorrower` (lines 149-179) prefunds all pending deposits atomically, but only the owner/manager can call it and only before the same cutoff (`block.timestamp + _prefundedWindow < epochEndDate`, line 164). There is no privileged path to remove a user's pending deposit: `deleteRequest` (lines 184-199) is only callable by the depositor while `epochPrice[_epoch] == 0` — and since `stopEpochWithDuration` reverts before `epochPrice` is set, the attacker can simply refuse to delete.

The asymmetry: deposit acceptance and prefunding share the same cutoff, so once the cutoff passes, a pending deposit can never be converted to prefunded, and `prefundedDepositsToProcess` will revert at every subsequent stop attempt.

### Impact Explanation
If `epochPendingDeposits` for the settlement epoch is non-zero when `stopEpochWithDuration` is invoked, the epoch can never be stopped: the revert propagates through `_afterStopEpochWithDuration`. The vault is permanently stuck in the running epoch — all deposited funds, borrower repayment, and every withdraw receipt are frozen. This is a permanent freezing of all pool funds triggered by a dust-sized attacker deposit, with no unprivileged recovery path (the attacker controls `deleteRequest`).

In the more likely operational path, the manager notices and calls `processDepositsToBorrower` before the cutoff to fold the dust into the prefund — that converts the attack into a forced temporary freeze plus an unsolicited 1-wei prefund to the borrower. The permanent outcome requires the pending deposit to survive past the prefund cutoff window.

### Likelihood Explanation
Low cost (1 wei + KYC), but the permanent-freeze path requires the deposit to remain unprefunded past `prefundedDepositWindow`. Attack surface is real whenever the manager processes deposits lazily, prefunds before the attacker's front-run deposit lands, or when `prefundedDepositWindow == 0` (no cutoff at all, so a deposit can be placed arbitrarily late in the epoch while `processDepositsToBorrower` is equally unconstrained — still manager-dependent to clear). The attacker can also grief repeatedly each epoch at negligible cost. Acknowledged uncertainty: whether the manager prefunding the dust fully neutralizes the attack depends on the operational window configuration; the revert-on-pending-deposit design is nonetheless fragile because a single orphaned deposit is a hard brick with no escape hatch.

### Recommendation
In `IdleCDOEpochQueue.prefundedDepositsToProcess` / `processPrefundedDeposits`, do not revert on orphan `epochPendingDeposits` — instead return them to depositors (transfer underlying back and zero `userDepositsEpochs`) or settle the epoch anyway, leaving pending deposits refundable via `deleteRequest`. Alternatively, enforce a mandatory invariant that prefunding is the only way deposits can reach the settle epoch (e.g., make `requestDeposit` require that a prefund has not yet occurred AND that one is scheduled, or allow the manager to refund pending deposits post-cutoff).
