### Title
Permissionless `new_authority`/`account_index` in `transfer_to_new_account_pda` allows front-running to deny (and poison) target account-migration PDAs - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account_pda` derives the destination PDA solely from `(group, new_authority, account_index, third_party_id)`, and `new_authority` is an entirely unchecked, non-signing account. Any caller who owns *any* `old_marginfi_account` can invoke this instruction with an arbitrary `new_authority` pubkey and `account_index`, claiming the PDA slot that a legitimate user's own migration/creation call would derive to. This is the same root-cause pattern as the `DeployChain` bug: a permissionless entrypoint derives a deterministic PDA from caller-supplied "salt" values that belong to someone else, letting an attacker pre-empt the legitimate initialization and cause it to revert (`already in use`) — with the added twist that the attacker also seeds the destination account with their own (attacker-chosen) `lending_account` state.

### Finding Description
`transfer_to_new_account_pda` and its `Accounts` struct compute the new account PDA as: [1](#0-0) 

Only `old_marginfi_account`/`authority` are validated (that the *caller* is authorized on the source account being migrated, via `is_signer_authorized`). `new_authority` has no signer requirement and no ownership check at all — the field is explicitly commented `"WARN: New authority is completely unchecked"`: [2](#0-1) 

Compare this to the sibling, safe entrypoint `marginfi_account_initialize_pda`, where the PDA seed’s `authority` **must** sign, so nobody but the real owner can ever occupy that address: [3](#0-2) 

Because `transfer_to_new_account_pda` does not require `new_authority` to sign, an attacker can:
1. Create/own a throwaway `old_marginfi_account` (any account they control, even with attacker-chosen `lending_account` state).
2. Call `transfer_to_new_account_pda` with `new_authority` = victim's pubkey and `account_index` = the specific index the victim is expected to use (commonly a low/default index such as `0`).
3. This `init`s the PDA at `[MARGINFI_ACCOUNT_SEED, group, victim_pubkey, account_index, third_party_id]` first, copying the attacker's own `lending_account`, flags, and `migrated_from` into the new account via `initialize_migrated_account`: [4](#0-3) 

Once this PDA exists, any subsequent, legitimate attempt by the victim to create their own account at that same address — either via `marginfi_account_initialize_pda` or via their own `transfer_to_new_account_pda` — reverts with an Anchor `init`/"already in use" error, permanently denying that specific `(group, authority, account_index, third_party_id)` slot to the victim (they must fall back to a different `account_index`). This mirrors the `DeployChain` bug exactly: a permissionless call using a caller/attacker-controlled salt to derive and seize a PDA that a legitimate party was going to use, causing their transaction to fail.

Beyond simple denial-of-service, the planted account is not inert: its `authority` field is set to the victim's pubkey, and it carries attacker-chosen `lending_account`/flags data (potentially with debt/liability positions), meaning the attacker can plant a state-polluted account "owned" by the victim's key without the victim's consent.

### Impact Explanation
- Denial of a specific account-migration/creation slot: a targeted `(group, new_authority, account_index)` combination can be permanently squatted by any unrelated attacker for the cost of one transaction and rent, blocking the intended owner from ever initializing that exact PDA.
- Unauthorized state injection: because `initialize_migrated_account` copies the attacker's own `lending_account`/flags into the account now attributed to the victim's authority, the attacker can implant arbitrary (attacker-controlled) balance/liability/flag state under a pubkey the victim did not consent to use, without the victim ever signing anything.
- This is a durable, unauthorized state change with a financial dimension (planted debt/asset state, blocked/impossible legitimate account creation at that index), matching the "durable freeze/inconsistency with financial effect" bar.

### Likelihood Explanation
Likelihood is high for anyone who can predict the target `new_authority` pubkey and the intended `account_index` (commonly `0`, or otherwise low, sequential/well-known values) ahead of the victim's transaction landing — e.g. by observing the mempool/pending transaction, or simply pre-emptively squatting default indices for known/high-value addresses. No signature or permission from `new_authority` is required, and the attacker only needs control of one throwaway old account, which is trivial and permissionless to create via `marginfi_account_initialize` or `marginfi_account_initialize_pda`.

### Recommendation
- Require `new_authority` to be a `Signer` in `TransferToNewAccountPda` (and `TransferToNewAccount`), consistent with `MarginfiAccountInitializePda`, so the PDA/account can only ever be created with the consent of the actual intended owner.
- If a non-signing "gift" flow is intentionally desired, gate it behind an explicit opt-in/allow-list mechanism (e.g., a pre-registered pending-transfer record keyed by `new_authority` that only the real owner of `new_authority` can create/accept), rather than allowing any caller to derive and claim the destination PDA unilaterally.

### Proof of Concept
1. Attacker creates a throwaway marginfi account `attacker_old_account` (e.g. via `marginfi_account_initialize`), optionally funding it with arbitrary borrow/deposit positions.
2. Attacker determines a victim's authority pubkey `V` and a plausible `account_index` (e.g. `0`) that `V` is expected to use for `marginfi_account_initialize_pda` or their own migration.
3. Attacker calls `transfer_to_new_account_pda(account_index=0, third_party_id=None)` with:
   - `old_marginfi_account = attacker_old_account`
   - `authority = attacker` (signs, authorized on their own account)
   - `new_authority = V` (unchecked, does not sign)
   - `new_marginfi_account` = PDA derived from `[MARGINFI_ACCOUNT_SEED, group, V, 0u16, 0u16]`
4. The instruction succeeds: a new account is `init`'d at that PDA with `authority = V` and `lending_account` copied from `attacker_old_account`.
5. Victim `V` later attempts `marginfi_account_initialize_pda(account_index=0, third_party_id=None)` (or their own `transfer_to_new_account_pda` targeting the same index) — this fails because the PDA account already exists, demonstrating the front-run denial; additionally `V`'s pubkey is now the recorded `authority` on an account state the attacker fully controlled at creation time.
