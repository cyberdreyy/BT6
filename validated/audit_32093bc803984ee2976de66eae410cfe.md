### Title
Non-constant-time token comparison in `Session.withAuthorization` - ([File: session/session.go])

### Summary
`withAuthorization` compares the session token with `s.Token != r.Header.Get("Authorization")`, which is Go's native string inequality and short-circuits on the first mismatching byte, making the comparison time-variable rather than constant-time. This is a real code defect, but exploiting it to fully recover a 256-bit (64 hex-char) token over a network within the lifetime of a single interactive-terminal session is not practically feasible given realistic network/OS jitter.

### Finding Description
`generateToken` produces the session token via `helpers.GenerateRandomUUID(32)`, which is `hex.EncodeToString` of 32 random bytes, i.e. a 64-character hex string with 256 bits of entropy [1](#0-0) [2](#0-1) . `withAuthorization` checks this token against the incoming `Authorization` header using `s.Token != r.Header.Get("Authorization")` [3](#0-2) . Go string comparison is implemented as a byte-by-byte compare that returns as soon as a mismatch is found (and also short-circuits trivially on length mismatch), so in principle the time taken to reject a guess is correlated with the number of correctly-guessed leading bytes. No `crypto/subtle.ConstantTimeCompare` or similar timing-safe primitive is used anywhere in the repo for this check.

However, for this to be exploitable as described, an attacker would need to:
1. Have network access to the session server endpoint for a specific job's session (which is normally only reachable through GitLab's authenticated session-server proxy, not directly exposed to arbitrary attackers).
2. Measure timing differences on the order of the cost of comparing a handful of extra bytes in a string against a target token — differences that are on the order of nanoseconds and get completely swamped by TLS/HTTP handling, goroutine scheduling, GC pauses, and network jitter, especially for a request that also has to pass through `websocket.IsWebSocketUpgrade` and other handler logic in `execHandler` before the comparison result could even be measured cleanly at the `/exec` endpoint [4](#0-3) .
3. Recover a full 256-bit token (64 independent hex-character positions, 16 possibilities each) via averaged timing statistics, which for network-based attacks against a single active session (which exists only for the duration of one job's terminal usage) is not practically achievable — this class of attack against short, network-observable secrets has historically required extremely low-noise LAN environments and thousands to millions of samples per byte position, far exceeding what a single job's session lifetime allows.

### Impact Explanation
If exploited, an attacker could authenticate to another job's `/session/{uuid}/exec` endpoint and drive `terminalConn.Start`, gaining an interactive shell inside another job's container — this would be a genuine cross-job isolation break matching the "Runner-enforced... auth state must not let one job impersonate another" invariant. But the finding is only theoretically possible; the token space (256 bits) and the ephemeral, single-use nature of each session token make the described exploit chain impractical to demonstrate as a concrete, reproducible attack against a live GitLab Runner session server under normal network conditions.

### Likelihood Explanation
Low. The comparison is indeed not constant-time, which is a legitimate defensive-coding deficiency, but real-world exploitability requires: (a) direct, low-latency network access to a specific victim session endpoint, (b) the session to remain open long enough to gather the huge number of timing samples needed to resolve 64 independent hex positions, and (c) timing precision fine enough to detect single-byte-compare differences through the noise of Go's HTTP stack, TLS, and OS scheduling. These preconditions are not satisfied in the normal GitLab Runner session-server deployment model, where sessions are proxied through the GitLab instance and are short-lived per job.

### Recommendation
Replace the string inequality check with a timing-safe comparison, e.g.:
```go
if len(s.Token) != len(r.Header.Get("Authorization")) ||
    subtle.ConstantTimeCompare([]byte(s.Token), []byte(r.Header.Get("Authorization"))) != 1 {
    ...
}
```
This is good defensive hardening regardless of practical exploitability.

### Proof of Concept
A Go benchmark/test can show the *theoretical* timing variance (not a full working remote exploit):
```go
func BenchmarkTokenCompare(b *testing.B) {
    token := strings.Repeat("a", 64)
    close_ := "b" + token[1:]  // differs at first byte
    far := "a" + strings.Repeat("b", 63) // differs at last byte
    b.Run("mismatch-first-byte", func(b *testing.B) {
        for i := 0; i < b.N; i++ {
            _ = token != close_
        }
    })
    b.Run("mismatch-last-byte", func(b *testing.B) {
        for i := 0; i < b.N; i++ {
            _ = token != far
        }
    })
}
```
Expected assertion: statistically measurable (nanosecond-scale) difference between the two benchmarks confirms non-constant-time behavior at the Go level, but this does not by itself demonstrate a feasible remote token-recovery exploit against the running session HTTP server — no PoC job or integration test can reliably reproduce full token recovery over a network within a single job's session lifetime given the noise/entropy tradeoffs described above.

```go
func (s *Session) withAuthorization(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		logger := s.log.WithField("uri", r.RequestURI)
		logger.Debug("Endpoint session request")

		if s.Token != r.Header.Get("Authorization") {
			logger.Error("Authorization header is not valid")
			http.Error(w, http.StatusText(http.StatusUnauthorized), http.StatusUnauthorized)
			return
		}

		next.ServeHTTP(w, r)
	})
}
```

```go
func GenerateRandomUUID(length int) (string, error) {
	data := make([]byte, length)
	_, err := rand.Read(data)
	if err != nil {
		return "", err
	}

	return hex.EncodeToString(data), nil
}
```
