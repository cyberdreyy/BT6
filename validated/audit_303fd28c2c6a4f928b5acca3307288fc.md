### Title
Removing an access key from the multisig does not purge that key's existing confirmations on other pending requests, allowing a request to execute below the current confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The `confirm` function counts a request as approved once `confirmations.len() + 1 >= self.num_confirmations`, without verifying that every entry in `confirmations` still corresponds to a currently valid signer/member. `DeleteKey` (in `multisig/src/lib.rs`) and `DeleteMember` (in `multisig2/src/lib.rs`) only purge requests *originated* by the removed key/member, but never scrub that key/member's confirmations from *other* pending requests they had previously confirmed. This leaves "ghost" confirmations behind that count toward the threshold even after the signer is no longer a member, effectively letting a request execute with fewer live approvals than `num_confirmations` requires.

### Finding Description
The invariant the multisig is supposed to guarantee is:
```
confirmations counted (live members only) >= num_confirmations
```
but the actual check in `confirm` is:
```
confirmations.len() + 1 >= num_confirmations
``` [1](#0-0) [2](#0-1) 

`confirmations` is a raw `HashSet` keyed by the confirming key/member identity, populated whenever `confirm` is called and never revisited when membership changes.

When a member/key is removed via `DeleteKey` (multisig) or `DeleteMember` (multisig2), the cleanup logic only removes **requests that the removed signer originated**, and the signer's own `num_requests_pk` counter — it does not touch the `confirmations` set on requests originated by *other* members that the removed signer had already confirmed: [3](#0-2) [4](#0-3) 

So a confirmation recorded by a key/member that is later removed remains in the `confirmations` set forever, and is still counted by the `>= self.num_confirmations` comparison in `confirm`.

### Impact Explanation
This breaks the custody/authorization binding "confirmations counted versus live members." Since the multisig contract holds funds and access keys and gates all transfers/`AddKey`/`DeployContract`/`FunctionCall` actions behind `num_confirmations` live approvals, a stale confirmation effectively reduces the real threshold by one signer for any request that was partially confirmed before a member/key was removed. This matches the Critical impact category "a multisig request executed below threshold," since after removal the request can be pushed through `execute_request` (which can transfer NEAR, add/delete keys, or deploy new contract code) with one fewer legitimate, currently authorized signature than the configured policy requires.

### Likelihood Explanation
This requires no bypass of any documented flow — key/member removal (`DeleteKey`/`DeleteMember`) is a normal governance action any legitimate multisig membership churn will use (e.g., rotating a compromised or departing signer). Any pending request that had already collected a confirmation from the departing signer is silently left with a phantom vote. A member (including a since-partially-malicious or compromised one) simply needs to confirm a request before being removed for the vulnerability to manifest; no additional privilege beyond being an ordinary current member is needed to plant the stale confirmation, and no special exploitation step is needed to trigger it afterward - subsequent legitimate confirmations by other members will unknowingly complete execution one signature early.

### Recommendation
When removing a key/member (`DeleteKey` in `multisig/src/lib.rs`, `DeleteMember` in `multisig2/src/lib.rs`), iterate over **all** pending requests' confirmation sets (not just requests originated by that signer) and remove the departing signer's identity from each. Alternatively, change `confirm` to re-validate, at confirmation-counting time, that every entry in `confirmations` still corresponds to a current member/key (e.g., by intersecting `confirmations` with the live `members`/access-key set before comparing against `num_confirmations`).

### Proof of Concept
1. Multisig deployed with `num_confirmations = 3` and keys `K1, K2, K3, K4`.
2. Attacker (holder of `K1`) creates a malicious `Transfer` request `R` via `add_request`.
3. `K2` confirms `R` (`confirmations(R) = {K2}`, still short of threshold: needs 2 more).
4. Through normal, unrelated multisig operations, the members later remove `K2` (e.g., key rotation) via a `DeleteKey` request that reaches quorum and executes — `execute_request`'s `DeleteKey` branch only deletes requests *authored* by `K2`; `R` was authored by `K1`, so `R` and its `confirmations = {K2}` survive untouched.
5. `K1` (attacker) now confirms `R` itself: `confirmations.len() + 1 = 1 + 1 = 2`, still `< 3`, so one more confirmation is needed — but the set already contains the stale `K2` entry, which is a member no longer authorized.
6. `K3` confirms: `confirmations.len() + 1 = 2 + 1 = 3 >= 3` → `execute_request` fires the `Transfer`, even though only `K1` and `K3` are currently valid signers approving — one fewer live confirmation than the policy `num_confirmations = 3` requires, because `K2`'s vote is a ghost from a removed key.     pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
