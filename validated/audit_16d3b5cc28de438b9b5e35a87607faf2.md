### Title
Vault DKG result export is edit-role gated (not admin) and emits no audit log, unlike all other key-export endpoints - ([File: core/web/vault_controller.go])

### Summary
`VaultController.ExportDKGResult` returns the raw hex-encoded DKG result package (vault key share material) to any caller with only the edit role, and unlike every other key-export controller in the router it never calls `app.GetAuditLogger().Audit(...)` on success. This creates both an authorization gap (edit-role instead of admin-role) and an accountability gap (no audit trail) for exfiltration of vault secret material.

### Finding Description
The route is registered as `authv2.POST("/vault/dkg_results/export", auth.RequiresEditRole(vault.ExportDKGResult))` [1](#0-0) , whereas every comparable key-export route (`ekc.Export`, `vrfkc.Export`, `ocrkc.Export`, `ocr2kc.Export`, `p2pkc.Export`, `csakc.Export`, and the generic per-chain-key `Export` loop) is wrapped with `auth.RequiresAdminRole` [2](#0-1) .

Inside `ExportDKGResult`, the handler reads the DKG result package from the vault ORM and returns it hex-encoded to the caller with no side-effecting audit call: [3](#0-2) 

By contrast, `ETHKeysController.Export` performs the export and then unconditionally records an audit event before returning the key material: [4](#0-3) 

The same `audit.KeyExported` pattern is present in the sibling admin-gated key controllers (OCR/OCR2/P2P/CSA/VRF), confirming a project-wide convention that key export = admin role + audit log, from which `VaultController.ExportDKGResult` deviates on both axes.

### Impact Explanation
An edit-role user (a role explicitly below admin, intended for job/bridge/external-initiator management, not secret management) can retrieve the DKG result package — which contains an encrypted share of vault key material tied to `masterPublicKey` — via a single authenticated POST, and this action leaves zero trace in the audit log. This matches Chainlink's bounty impact class of "key or secret disclosure" combined with an authorization-boundary violation (privilege escalation from edit to what should be admin-only secret access), compounded by the loss of forensic accountability that the audit logging subsystem exists specifically to provide.

### Likelihood Explanation
The only precondition is possession of a valid edit-role session or API token — no admin credentials, no host access, and no additional exploitation steps beyond calling `POST /v2/vault/dkg_results/export` with a known/guessable `instanceId`. This is fully attacker-controlled once edit-role credentials are obtained (e.g., via a compromised low-privilege operator account or an over-provisioned API token), and it is trivially repeatable since the endpoint performs a stateless read with no rate limiting beyond the generic authenticated rate limiter.

### Recommendation
1. Change the route registration to `auth.RequiresAdminRole(vault.ExportDKGResult)` (and consider the same tightening for `VerifyDKGResult` if it exposes similarly sensitive verification internals) to align with the rest of the key-export surface.
2. Add an `app.GetAuditLogger().Audit(audit.KeyExported, map[string]any{"type": "vault_dkg_result", "instanceId": req.InstanceID})` call (or a new dedicated `audit.VaultDKGResultExported` event type) immediately before/after the successful response in `ExportDKGResult`, mirroring `ETHKeysController.Export`.

### Proof of Concept
Go handler-level integration test plan (to be added alongside `core/web/vault_controller_test.go`):
1. Set up a test app with an audit logger test hook (as used in `core/logger/audit/audit_logger_test.go`) and seed a vault DKG result via `vault.NewVaultORM`.
2. **Role-boundary test**: Authenticate as an edit-role (non-admin) user/token, call `POST /v2/vault/dkg_results/export` with a valid `instanceId`. Assert the response is `200 OK` with the DKG package returned — demonstrating edit-role sufficiency where admin should be required (compare against `POST /v2/keys/eth/export/:address` with the same edit-role credentials, which should return `401/403`).
3. **Audit-log-absence test**: After the successful export in step 2, query the audit logger's recorded events and assert no `audit.KeyExported` (or any) entry was created for the vault export, then repeat the same flow against `ETHKeysController.Export` and assert an `audit.KeyExported` entry IS present — proving the discrepancy.
4. Expected result confirming the bug: test 2 succeeds with edit role (should fail with 403), and test 3 shows an audit-log entry only for the ETH key export, not for the vault export.

func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")

func (ekc *ETHKeysController) Export(c *gin.Context) {
	defer ekc.app.GetLogger().ErrorIfFn(c.Request.Body.Close, "Error closing Export request body")

	id := c.Param("address")
	newPassword := c.Query("newpassword")

	bytes, err := ekc.app.GetKeyStore().Eth().Export(c.Request.Context(), id, newPassword)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	ekc.app.GetAuditLogger().Audit(audit.KeyExported, map[string]any{
		"type": "ethereum",
		"id":   id,
	})

	c.Data(http.StatusOK, MediaType, bytes)
}
