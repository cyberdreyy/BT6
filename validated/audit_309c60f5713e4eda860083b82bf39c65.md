### Title
Partially funded (loss-adjusted) withdraw receipts can be re-requested to escape the haircut and claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` funds pending withdraw receipts only partially and records the haircut in `lossRecoveryPriceByEpoch[epochNumber]`. The loss-adjusted claim path (`_claimLossAdjustedWithdrawRequest`) locates the haircut via `lastWithdrawRequest[_user]`. A user can simply submit a new `requestWithdraw` in a later epoch, which overwrites `lastWithdrawRequest[_user]` without clearing the old haircutted receipt, then claim the old receipt at 100% through `_claimFundedWithdrawRequest`. This is the direct analog of "a partially filled order can still be cancelled": a request that was already (partially) filled at a loss price can be reset into a fresh full-price claim.

### Finding Description
- `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds to the aggregate `withdrawsRequests[_user]` (`IdleCreditVault.sol` L281-293).
- On a loss, `collectWithdrawFunds` receives `_amount < pendingBasis`, zeroes `pendingWithdraws`, and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` (`IdleCreditVault.sol` L411-421). The vault then only holds `p * basis` underlying for that epoch's receipts.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol` L789-800). If a user files a new request in epoch `E+1`, `lastWithdrawRequest` becomes `E+1`, `lossRecoveryPriceByEpoch[E+1] == 0`, the function returns 0 and the epoch-`E` portion of `withdrawsRequests[_user]` is never cleared (`_clearWithdrawClaimForEpoch` is only reachable through this path).
- Execution falls through to `_claimFundedWithdrawRequest` (`IdleCreditVault.sol` L319-350), which after one further epoch roll pays `withdrawsRequests[_user]` — including the epoch-`E` amount — at par from the vault's funded balance.
- None of the guards stop this: `_transferFundedClaim` only protects the default recovery reserve, `requestWithdraw` has no pending-receipt or haircut check, and the per-epoch ledger `withdrawsRequestsByEpoch` is only consulted inside the skipped loss path.

### Impact Explanation
The attacker recovers the full face value `W` of a receipt that was funded only at `p * W`. The vault received only `p * totalBasis` for that epoch, so the excess `(1 - p) * W` is paid out of underlyings reserved for the other loss-epoch claimants — direct theft plus insolvency/frozen claims for later claimants (their `_transferFundedClaim` reverts on insufficient balance). Loss: `(1 - p) * W`, bounded by the attacker's request size.

### Likelihood Explanation
Requires a `stopEpochWithDuration(_lossAmount > 0)` partial funding (honest manager/borrower sequence, a designed mode), an attacker with a pending receipt in that epoch, and one additional `requestWithdraw` plus one epoch roll before claiming. The attacker only needs a KYC-passing wallet and tranche tokens. No privileged misbehavior needed; the sequence is fully unprivileged once a loss epoch occurs.

### Recommendation
Make `requestWithdraw` refuse (or first settle) when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` or when any `withdrawsRequestsByEpoch` entry has an associated non-zero `lossRecoveryPriceByEpoch`, so a haircutted receipt must be claimed at its loss price before a new request can overwrite `lastWithdrawRequest`. Alternatively, iterate all epochs in `withdrawsRequestsByEpoch` during claim rather than keying the loss lookup to `lastWithdrawRequest`.

### Proof of Concept
```solidity
// Foundry fork test sketch (IdleCreditVault.t.sol style)
// Setup: deploy IdleCDOEpochVariant + IdleCreditVault, KYC userA (attacker) and userB.

// 1. Epoch N-1: userA and userB deposit into AA.
uint256 a = cdoEpoch.requestWithdraw(mintedA / 2, address(AAtranche)); // userA
// userB requests withdraw as well; both recorded under epochNumber E.

// 2. Epoch E runs; at stop the borrower repays only part of pendingWithdraws.
//    Manager calls stopEpochWithDuration(_lossAmount > 0) which internally calls
//    strategy.collectWithdrawFunds(funded < pendingBasis):
//      lossRecoveryPriceByEpoch[E] = funded * RECOVERY_FULL / pendingBasis  (< 1)

// 3. ATTACK: before claiming, userA submits a NEW requestWithdraw in epoch E+1.
vm.prank(userA);
cdoEpoch.requestWithdraw(1, address(AAtranche));   // overwrites lastWithdrawRequest[userA] = E+1

// 4. Roll one epoch (startEpoch/stopEpoch) so epochNumber > lastWithdrawRequest[userA].

// 5. userA claims: _claimLossAdjustedWithdrawRequest reads
//    lossRecoveryPriceByEpoch[E+1] == 0 -> skipped; _claimFundedWithdrawRequest pays
//    withdrawsRequests[userA] (old epoch-E amount + new) at PAR.
vm.prank(userA);
cdoEpoch.claimWithdrawRequest();
assertGt(underlying.balanceOf(userA) - balPre, expectedHaircutPayout); // got > p*W

// 6. userB claims via the loss-adjusted path but the vault is drained:
//    _transferFundedClaim transfers less than his p*basis or reverts -> frozen claim.
vm.expectRevert();
vm.prank(userB);
cdoEpoch.claimWithdrawRequest();
```

Key invariant broken: loss waterfall / one receipt one payout — a receipt funded at `lossRecoveryPrice` must never be redeemable at par.
