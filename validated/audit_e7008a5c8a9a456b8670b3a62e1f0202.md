### Title
Legacy gateway messages bypass DON sender/allowlist authorization before being forwarded to DON nodes - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest` selects the legacy handler purely by `msg.Body.DonId` and only calls `msg.Validate()`, which recovers the ECDSA signer into `msg.Body.Sender` but does not check whether that sender is authorized for the targeted DON. The request is then forwarded straight to `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`, which itself contains an explicit `// TODO: apply allowlist and rate-limiting here` and forwards the message to every DON member node with no sender allowlist check at all.

### Finding Description
In `core/services/gateway/gateway.go`, for legacy requests (`msg.Body.DonId != ""`): [1](#0-0) 
`msg.Validate()` only verifies signature format/length and recovers the signer address into `msg.Body.Sender` — it performs no authorization/allowlist check against the DON: [2](#0-1) 
`handlerKey` is set directly to `msg.Body.DonId`, and the handler is fetched from `g.handlers[handlerKey]` with no sender check — any structurally valid, signed message targeting an existing DON ID reaches the handler: [3](#0-2) 

The reached handler, `capabilities.handler.HandleLegacyUserMessage`, validates payload structure, timestamp freshness, and method name, but explicitly skips sender authorization (`TODO: apply allowlist and rate-limiting here`) before forwarding the raw request to every configured DON member node: [4](#0-3) 

This gap is acknowledged directly in the handler's own test suite: [5](#0-4) 

An attacker with an arbitrary, non-allowlisted ECDSA keypair can craft a `Message` with `DonId = "victim-don"`, sign it, and it will pass `Validate()` (since Validate only checks signature well-formedness, not sender identity), be routed by `handlerKey = msg.Body.DonId`, and be forwarded by the handler to all of that DON's nodes as an apparently legitimate, signed message from the recovered (but unauthorized) `msg.Body.Sender` address.

### Impact Explanation
This allows an unauthenticated/unprivileged attacker to inject arbitrary `web_api_trigger` requests targeting any configured DON, which are forwarded to all DON member nodes carrying an attacker-controlled sender address and payload. Depending on downstream node-side handling of `web_api_trigger` messages, this can result in unauthorized workflow/job triggering on a DON that the attacker is not a member of or authorized to call — matching the "unauthorized job run" bounty impact class. It also enables allowlist-bypass style abuse (spamming/DoS of DON nodes with attacker-crafted trigger payloads) since there is no gateway-side sender-based rate limiting or authorization gate before fan-out to nodes.

### Likelihood Explanation
The only precondition is knowledge of a valid, configured `DonId` (these are effectively public routing identifiers, often discoverable via config/gateway service catalogs) and any ECDSA keypair (freely generatable by the attacker). No credentials, node access, or prior allowlisting is required — `msg.Validate()` succeeds for any self-signed message with correct field lengths. The vulnerability is deterministically reproducible for every legacy request path that reaches `capabilities.handler.HandleLegacyUserMessage`.

### Recommendation
Enforce sender authorization before dispatching legacy messages to DON handlers: after `msg.Validate()` recovers `msg.Body.Sender`, check it against a DON/service-scoped allowlist in `gateway.ProcessRequest` (or immediately at the top of `handler.HandleLegacyUserMessage`) before forwarding to `don.SendToNode`. Remove/resolve the outstanding `TODO: apply allowlist and rate-limiting here` in `core/services/gateway/handlers/capabilities/handler.go` by wiring in the same allowlist/rate-limit mechanism already used elsewhere in the gateway (e.g., `ratelimit.RateLimiter` keyed by sender, plus an explicit allowlist config per DON).

### Proof of Concept
1. In `core/services/gateway/gateway_test.go`, reuse `newSignedLegacyRequest` (or `newGatewayWithMockHandler`) but sign with a freshly generated `crypto.GenerateKey()` private key that is not part of any DON's configured node/member allowlist.
2. Build a `Message` with `Body.DonId = "testDON"` (an existing/configured DON), `Body.Method = MethodWebAPITrigger`, and a valid `TriggerRequestPayload`.
3. Call `gw.ProcessRequest(ctx, rawRequest, "")`.
4. Assert that:
   - The mock/real handler's `HandleLegacyUserMessage` is invoked (proving routing succeeded based on `DonId` alone).
   - No error/rejection occurs due to sender not being in an allowlist (there is no such check to fail).
   - In `capabilities.handler.HandleLegacyUserMessage`, `don.SendToNode` is called for every DON member (verifiable via the mocked `DON` interface), confirming the unauthorized sender's payload was forwarded to all DON nodes.
5. Compare against expected behavior: request should be rejected with an authorization error if `msg.Body.Sender` is not in a per-DON allowlist prior to any forwarding.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
