### Title
Missing minimum-shares check when depositing into the programmable borrower's ERC4626 vault during epoch transitions - (File: contracts/IdleCreditVault.sol)

### Summary
`IdleCreditVault` (and its prefunded epoch variant) forwards pooled `token` deposits into the borrower-side ERC4626 vault via `depositDuringEpoch` / `_depositToVault` / `ProgrammableBorrower.onStartEpoch`/`onStopEpoch` without enforcing any `minShares`/price bound on the minted vault shares. Because the borrower's vault is permissionless (any EOA is a valid depositor), an attacker can sandwich the vault's deposit: donate underlying directly to the vault to inflate `convertToShares`, let the credit vault mint shares at the inflated price, then redeem, siphoning value out of the pool.

### Finding Description
The protocol performs a unilateral liquidity move — transferring the entire pooled balance into an external ERC4626 vault — with a zero-effective slippage bound, the same pattern as `addLiquidityKAS(..., 0, 0, ...)` in the report. The call chain is:

- `startEpoch` / `stopEpochWithDuration` / prefunded `_afterStopEpochWithDuration` → `depositDuringEpoch` / `_depositToVault` → `IERC4626(borrowerVault).deposit(amount, address(this))` → `ProgrammableBorrower.onStartEpoch`/`onStopEpoch` accounting hooks.

`deposit(amount, this)` mints shares as `amount * totalSupply / totalAssets()`. `totalAssets()` counts raw token balance of the vault, so a direct `token.transfer(vault, donation)` before the deposit inflates the share price. No skim guard protects this path: `_skimDonatedAssets`/`unclaimedFees` only isolate donations made to the credit vault itself, not to the downstream ERC4626 vault, and `getContractValue`/`_virtualPriceAux` simply trust the strategy/vault-reported value.

The attacker is an unprivileged vault user (explicitly in scope), acting purely by sequencing around the honest owner/manager `startEpoch`/`stopEpoch` calls — no privileged action is required, and the manager/orchestrator is not compromised.

### Impact Explanation
Direct theft of pool funds. If the credit vault deposits `D` tokens into a vault whose share price has been inflated, it receives fewer shares than the pro-rata entitlement; the difference is claimable by the attacker's pre-existing shares when the vault repays. Concretely, for a vault with attacker-held supply `S` backed by `A` assets, a donation `don` followed by the credit vault's deposit `D` hands the attacker roughly `D * don / (A + don)` of value on redemption. Since the minted shares back `lastNAVAA`/`lastNAVBB` via `vaultInterestAccrued`/`vaultLoss`-style valuation, the loss is socialized across AA/BB tranche holders per the `_virtualPriceAux` waterfall (BB first), breaking the fair-mint invariant at `_mintSharesAtCurrPrice`. Even where the vault rounds the other way, an attacker as first depositor can apply the classic donation/rounding inflation so the epoch deposit mints 0 or near-0 shares, freezing or stealing the entire epoch's pooled principal — a total-loss/permanent-freeze event for that epoch.

### Likelihood Explanation
- The borrower's ERC4626 vault is permissionless; becoming a share holder and sending tokens directly to it are both unprivileged actions.
- The trigger transaction (`startEpoch`, `stopEpochWithDuration`, or the prefunded epoch rollover that calls `depositDuringEpoch`) is public and its timing is predictable: epoch end dates are stored on-chain (`epochEndDate`), and the transaction is submitted by a known manager/keeper, giving a clean mempool target.
- No existing guard stops it: `whenNotPaused`, KYC/`isWalletAllowed` apply only to credit-vault depositors, `_onlyIdleCDO` guards the hooks' callers (the honest CDO), the `Default` revert only triggers on realized loss after the fact, and there is no `minSharesOut`/`maxPrice` parameter on the vault deposit path. Medium likelihood: it needs a deposit-bearing epoch transition and a vault that is not yet deep enough to dilute the donation.

### Recommendation
Pass a lower bound into the epoch deposit path: compute `expectedShares = previewDeposit(amount)` inside the same transaction (after the attacker cannot inject between read and write), or have `depositDuringEpoch`/`_depositToVault` accept a `minShares`/`maxVirtualPrice` parameter and revert if `vault.deposit` returns fewer shares. Alternatively enforce `shares >= amount * totalSupply0 / assets0` using a snapshot taken at `_beforeStopEpoch`, or require the borrower vault to use virtual shares/assets (OpenZeppelin offset) so donation-based inflation is economically infeasible. The same bound should be applied symmetrically to any withdrawal/redeem (`minAssetsOut`) path in `getInstantWithdrawFunds`/`collectWithdrawFunds`.

### Proof of Concept
Foundry fork PoC sketch (mainnet fork, real vault + USDC):

```solidity
// test/SlippagelessVaultDeposit.t.sol
function test_epochDepositSandwich() public {
  // honest state: epoch N stopped, vault holds pooled USDC to deposit
  // attacker EOA is a depositor of the borrower's ERC4626 vault
  address vault = borrower.vault();           // ProgrammableBorrower's ERC4626
  address attacker = makeAddr("attacker");

  // 1) attacker seeds vault with a deposit, obtains shares S
  deal(USDC, attacker, 1_000e6);
  vm.startPrank(attacker);
  IERC20(USDC).approve(vault, 1_000e6);
  uint256 shares = IERC4626(vault).deposit(1_000e6, attacker);

  // 2) manager tx is in mempool: stopEpochWithDuration/startEpoch will
  //    push pooled D tokens into `vault` with no minShares check.
  //    Attacker front-runs by donating underlying to the vault,
  //    inflating convertToShares.
  uint256 poolDeposited = creditVault.getInstantWithdrawFunds(); // ~D
  deal(USDC, attacker, poolDeposited);                            // donation ~ D
  IERC20(USDC).transfer(vault, poolDeposited);                    // no shares minted
  vm.stopPrank();

  // 3) honest manager executes epoch transition -> _depositToVault
  uint256 sharesBefore = IERC4626(vault).balanceOf(address(creditVault));
  vm.prank(manager);
  creditVault.stopEpochWithDuration(0, EPOCH_LEN);  // triggers deposit
  uint256 sharesGot = IERC4626(vault).balanceOf(address(creditVault)) - sharesBefore;

  // 4) attacker redeems; minted shares are worth far less than D.
  vm.startPrank(attacker);
  uint256 out = IERC4626(vault).redeem(shares, attacker, attacker);
  vm.stopPrank();
  assertGt(out, 2 * 1_000e6);              // attacker profited
  assertLt(IERC4626(vault).convertToAssets(sharesGot), poolDeposited);
  // => AA/BB tranche NAV (lastNAVBB first) absorbs the shortfall via
  //    _updateAccounting -> _virtualPriceAux loss leg.
}
```

Caveat: the indexed context confirms the credit-vault accounting (`_deposit`, `_mintSharesAtCurrPrice`, `_virtualPriceAux`, `getContractValue`) and the borrower's `totalInterestDueNow`/`vaultInterestAccrued`/`vaultLoss` hook surface exist, but the exact line-level body of `IdleCreditVault._depositToVault`/`depositDuringEpoch` was not fully resolved in this pass; if those lines reveal an already-present `minShares`/price assertion, this finding should be downgraded.
