### Title
Cross-workflow HTTP response cache poisoning via workflow-owner-scoped (not workflow-scoped) cache key - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's HTTP Action response cache is documented as being isolated "per workflow" but is actually keyed only by `method + URL + headers + body + workflowOwner`, deliberately excluding `WorkflowID`. Any workflow deployed by the same owner can therefore read (and, by controlling `CacheSettings.Store`, write) the cached response for a request that another one of that owner's workflows made to the same URL — an analog of the DSProxyCache issue where a shared, loosely-keyed cache entry can be silently substituted and later served to an unrelated/unsuspecting caller, corrupting its execution.

### Finding Description
`responseCache` is a shared map keyed by `gateway.OutboundHTTPRequest.Hash()`: [1](#0-0) [1](#0-0) 

Test cases confirm the key composition: identical `WorkflowOwner` produces identical hashes regardless of `WorkflowID`, while different `WorkflowOwner` values do change the hash: [2](#0-1) 

The README explicitly claims per-workflow isolation ("Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"), which contradicts the actual `Hash()` behavior: [3](#0-2) 

The cache is written to and read from on every inbound HTTP-action node message via `makeOutgoingRequest`, using attacker/workflow-controlled `req.CacheSettings.Store` and `req.CacheSettings.MaxAgeMs` fields that come straight from the (deserialized, node-forwarded) `OutboundHTTPRequest`: [4](#0-3) 

Because these `CacheSettings` values originate from the workflow's own action request (compiled/authored by the workflow owner) rather than from a value validated as identical/consistent per URL across the owner's whole DON, one workflow belonging to an owner can set `Store: true` for a URL+body+headers combination it controls to seed a cache entry, and cause a different workflow — belonging to the *same owner* but with unrelated business logic/trust boundaries — to transparently receive that cached (potentially attacker-crafted) response the next time it issues what it believes is an isolated fetch with `MaxAgeMs > 0` to the same URL/method/body/headers. This is analogous to the DSProxyCache bug: a cache entry addressed by a coarse, attacker-influenced key is silently reused by a different, unsuspecting consumer, without any check that the consumer intended to share that cache slot.

### Impact Explanation
This breaks the "Workflow Isolation" property the code itself documents and can lead to cross-workflow response confusion: a compromised or malicious workflow under one `WorkflowOwner` account can poison the HTTP action cache seen by that owner's other, legitimate workflows hitting the same external endpoint, causing them to execute against attacker-controlled/stale data. Depending on what the target workflow does with the HTTP response (e.g., feeding it into on-chain writes or further capability calls), this can corrupt downstream execution — the "corrupted execution" impact class described in the original report.

### Likelihood Explanation
Likelihood is moderate: the attacker must control a workflow under the same `WorkflowOwner` as the victim workflow (a plausible scenario for an owner running multiple workflows, or where owner-controlled automation/CI onboard several workflows), and must be able to predict/target the exact `method+URL+headers+body` combination used by another one of their own workflows. No cross-owner attack is possible because `WorkflowOwner` is included in the hash, which meaningfully limits blast radius but does not close the isolation gap the documentation promises.

### Recommendation
Include `WorkflowID` (or another workflow-unique identifier) in `OutboundHTTPRequest.Hash()`/cache key so cache entries cannot be shared across workflows, matching the documented isolation guarantee, or explicitly document that isolation is only owner-scoped and warn workflow authors of the shared-cache risk between their own workflows.

### Proof of Concept
1. Deploy two workflows, `W1` and `W2`, under the same `WorkflowOwner`.
2. `W1` issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {Store: true}}` and receives/caches an attacker-influenced 2xx/4xx response (e.g., by controlling the target endpoint or timing a race before the legitimate endpoint responds).
3. `W2`, unaware of `W1`, issues the same `Method`/`URL`/`Headers`/`Body` request with `CacheSettings.MaxAgeMs > 0`.
4. Per `responseCache.Fetch`, `req.Hash()` matches `W1`'s cached entry (since `WorkflowID` is excluded from the hash), so `W2` receives `W1`'s cached response instead of making its own independent HTTP call: [5](#0-4)

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
