`find_bank_vault_authority_pda` is a pure, deterministic PDA-derivation helper — it just calls `Pubkey::find_program_address(bank_authority_seed!(vault_type, bank_pk), &crate::ID)` with no branching, no optional-account handling, and no "permissive default" path to downgrade. [1](#0-0) 

Critically, the on-chain `JuplendWithdraw` accounts struct does not trust any client-supplied PDA computed by this helper — it independently re-derives and enforces the `liquidity_vault_authority` via Anchor's `seeds`/`bump` account constraint, binding it to the exact bank and to the bump value stored on that specific bank account (`bank.load()?.liquidity_vault_authority_bump`), which was fixed at bank-creation time. [2](#0-1) 

This means even if an attacker supplied a "favored" precomputed PDA as an account meta, Anchor would reject it unless it matches `[LIQUIDITY_VAULT_AUTHORITY_SEED, bank.key()]` with the bank's stored bump — there is no code path where this check is skipped or downgraded to a permissive default. The CPI signer seeds used in withdrawal/transfer (`bank_signer!(BankVaultType::Liquidity, self.bank.key(), authority_bump)`) are likewise derived from the same on-chain-validated bump, so no foreign-bank vault authority could ever be used to authorize a transfer. [3](#0-2) 

Additionally, the "amount domain" reconciliation the prompt asks about (internal share/asset amounts vs. external token amounts) is independently enforced with `require_eq!` checks comparing CPI-reported deltas (`received_underlying`, `burned_shares`) against internally computed expected values (`token_amount`, `shares_to_burn`), which would cause the instruction to fail rather than proceed permissively on any mismatch. [4](#0-3) 

No branch in `find_bank_vault_authority_pda`, its callers, or `juplend_withdraw` matches the described "helper returns permissive default" pattern, and no unprivileged-attacker-controlled input can bypass the seeds/bump constraint or the amount reconciliation checks.
