### Title
Instant-withdraw claims pay unfunded receipts, draining balance earmarked for funded normal withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` enforces a "must be funded first" invariant on the normal withdrawal path (`_claimFundedWithdrawRequest` reverts until `epochNumber > lastWithdrawRequest[_user]`, i.e. the request's epoch has been stopped and `collectWithdrawFunds` has pulled borrower money into the vault), but performs no equivalent check on the symmetric instant-withdraw path. `claimInstantWithdrawRequest` pays out the full `instantWithdrawsRequests[_user]` balance regardless of whether `collectInstantWithdrawFunds`/`getInstantWithdrawFunds` was ever called for that request, so an unprivileged instant withdrawer can consume underlying that belongs to other claimants.

### Finding Description
When a user requests an instant withdraw, `requestInstantWithdraw` burns the CDO's strategy tokens, mints a 1:1 receipt to the user, and increments `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). The actual cash only arrives later, when the manager calls `getInstantWithdrawFunds` on the CDO, which calls `collectInstantWithdrawFunds` — the only place `pendingInstantWithdraws` is decremented and tokens are pulled in via `safeTransferFrom(idleCDO, ...)` (IdleCreditVault.sol:398-403).

The claim side has no gate tying the payout to that funding step:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:380-393
function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    _burn(_user, amount);
    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);   // pays whatever balance the vault holds
}
```

Contrast with the normal path, which reverts with `NotAllowed` while `epochNumber <= lastWithdrawRequest[_user]` (line 326), i.e. until the epoch containing the request has been stopped and funded. There is no analogous "instant bucket funded" check — `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` are written (lines 371-372) but only consumed during default finalization, not on the happy-path claim.

The only protection is inside `_transferFundedClaim` (lines 897-907), which exclusively shields `defaultRecoveryReserve`. Before any default finalization `reserve == 0`, so the guard is a no-op and the function transfers `_amount` out of whatever underlying the vault happens to hold — which in practice is the balance pulled in by `collectWithdrawFunds` to pay *normal* withdraw claimants.

This is exactly the DYAD H-06 shape: the solvency/backing invariant ("a receipt may only be paid from funds collected for it") is enforced on one redemption surface and omitted on its sibling.

### Impact Explanation
An attacker holding an instant-withdraw receipt can claim their full `instantWithdrawsRequests[_user]` amount before their request is funded, spending underlying that `collectWithdrawFunds` pulled in to satisfy normal withdraw receipts. Those normal claimants' `claimWithdrawRequest` calls then revert on insufficient balance (or their receipts are silently short-paid), producing direct theft of up to the attacker's instant-request amount and freezing of the victims' funded claims. Quantified loss: `min(instantWithdrawsRequests[attacker], vaultBalance)`, bounded by the whole funded-but-unclaimed normal receipt pool.

### Likelihood Explanation
Requires a non-prefunded instant-withdraw configuration (`instantWithdrawDelay > 0` mode in `IdleCDOEpochVariant`) where a window exists between (a) `stopEpoch`/`collectWithdrawFunds` depositing funds for normal receipts and (b) the manager calling `getInstantWithdrawFunds`. The attacker is an ordinary tranche holder who requested an instant withdraw — fully unprivileged and allowed by the threat model. The attack only needs transaction ordering around honest manager/borrower calls, not malicious privileged behavior. Likelihood is moderate: it depends on the funding window coexisting with a funded normal-receipt balance, which occurs naturally at every epoch stop that has both pending normal and pending instant requests.

### Recommendation
Mirror the funding gate used by normal claims onto instant claims. Two options:

1. Track a funded-per-epoch marker: decrement `instantWithdrawsRequestsByEpoch[_user][epoch]`/`instantWithdrawClaimsByEpoch[epoch]` inside `collectInstantWithdrawFunds` (or record `fundedInstantByEpoch[epoch]`), and in `claimInstantWithdrawRequest` only pay amounts whose epoch bucket has been collected — reverting `NotAllowed` otherwise, exactly as `_claimFundedWithdrawRequest` does.
2. Alternatively, introduce an `instantReserve` counter incremented by `collectInstantWithdrawFunds` and decremented on claim, and have `_transferFundedClaim`-equivalent logic revert if `amount > instantReserve` for instant claims — so unfunded instant receipts can never touch general balance.

### Proof of Concept
Foundry fork PoC sketch (extends `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function test_UnfundedInstantClaimStealsFundedNormalReceipt() public {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 amount = 10_000 * ONE_SCALE;

    // victim deposits and requests a NORMAL withdraw in epoch 0
    _depositWithUser(victim, amount, true);
    vm.prank(victim);
    uint256 victimClaim = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // attacker deposits and requests an INSTANT withdraw (instant mode enabled)
    _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // routed as instant in instant mode
    uint256 instantAmt = vault.instantWithdrawsRequests(attacker);
    assertGt(instantAmt, 0);
    assertEq(vault.pendingInstantWithdraws(), instantAmt); // NOT yet funded

    // epoch stops; manager/borrower fund only the normal receipts
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    // NOTE: getInstantWithdrawFunds is intentionally NOT called yet

    // attacker claims instantly and receives underlying funded for victim's receipt
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - balPre, 0, "unfunded instant claim paid");

    // victim's funded claim now reverts / is short-paid
    vm.prank(victim);
    vm.expectRevert(); // insufficient vault balance / NotAllowed
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat: the PoC assumes `claimInstantWithdrawRequest` on the CDO side is not gated by a funding check that would compensate for the missing vault-level gate — the CDO-side claim wrapper was not fully inspected within available context, so if `IdleCDOEpochVariant.claimInstantWithdrawRequest` enforces prefunding before calling the vault, the finding reduces to a defense-in-depth gap rather than an exploitable bug.
