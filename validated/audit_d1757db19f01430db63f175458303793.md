### Title
Missing minimum floor on server-supplied `X-GitLab-Trace-Update-Interval` allows unbounded-frequency polling - ([File: network/trace.go])

### Summary
`clientJobTrace.setUpdateInterval` clamps the server-supplied update interval only against an upper bound (`common.MaxUpdateInterval`) and rejects only non-positive values, but enforces no minimum floor. A response header value such as `1` (parsed as `1 * time.Second`) is fully valid and gets applied directly to `watch()`'s polling cadence via `getUpdateInterval()`.

### Finding Description
`NewRemoteJobStateResponse` in `network/remote_job_state_response.go` parses the `X-GitLab-Trace-Update-Interval` header with `strconv.Atoi` and converts it straight to `time.Duration(updateInterval) * time.Second` with no bounds check: [1](#0-0) 

That value flows into `PatchTraceResult.NewUpdateInterval` / `UpdateJobResult.NewUpdateInterval` and is passed to `clientJobTrace.setUpdateInterval`: [2](#0-1) 

```go
func (c *clientJobTrace) setUpdateInterval(newUpdateInterval time.Duration) {
	if newUpdateInterval <= 0 {
		return
	}
	...
	c.updateInterval = min(newUpdateInterval, common.MaxUpdateInterval)
	...
}
``` [3](#0-2) 

The only guard is `newUpdateInterval <= 0` (rejects 0/negative) and a ceiling clamp `min(newUpdateInterval, common.MaxUpdateInterval)` (`MaxUpdateInterval = 15 * time.Minute`, defined in `common/consts.go`). There is no lower bound such as `max(newUpdateInterval, someMinimum)`. `watch()` then sleeps for exactly `c.getUpdateInterval()` between `incrementalUpdate()` calls: [4](#0-3) 

So a value like `1` second (or any small positive integer) passes the `<= 0` check, is not raised to any minimum, and becomes the new polling interval — each cycle performing an authenticated `PatchTrace`/`UpdateJob` call using `c.jobCredentials` (this job's token).

### Impact Explanation
Given the stated precondition (attacker can influence `updateIntervalHeader` on responses to their own job's calls), the runner will honor arbitrarily small positive intervals (e.g., 1 second) for that job's trace-update loop, since only a ceiling (15 min) and a `<=0` rejection exist — no floor. This causes `clientJobTrace.watch()` to poll the GitLab backend at that job's token far more frequently than the documented default (`DefaultUpdateInterval = 3s`) would suggest, amplifying authenticated request volume attributable to a single job/token. This is scoped strictly to that job's own trace-update channel (its own `jobCredentials`), not to escaping the job sandbox or accessing another project's workload.

### Likelihood Explanation
Reachability is direct and requires no additional privilege beyond what the precondition already grants (control of response headers on that job's own PatchTrace/UpdateJob calls). The code path (`NewRemoteJobStateResponse` → `PatchTraceResult.NewUpdateInterval`/`UpdateJobResult.NewUpdateInterval` → `setUpdateInterval` → `watch()`) is exercised on every trace patch/update cycle, so the effect is repeatable and deterministic for any value in `(0, MaxUpdateInterval]`.

### Recommendation
Add a minimum floor in `setUpdateInterval`, e.g.:
```go
const minUpdateInterval = 3 * time.Second // or another sane floor

func (c *clientJobTrace) setUpdateInterval(newUpdateInterval time.Duration) {
	if newUpdateInterval <= 0 {
		return
	}
	c.lock.Lock()
	defer c.lock.Unlock()
	c.updateInterval = min(max(newUpdateInterval, minUpdateInterval), common.MaxUpdateInterval)
	...
}
```
This clamps both ends before the value is used to schedule `watch()`'s next poll.

### Proof of Concept
Add a unit test in `network/trace_test.go`:
```go
func TestSetUpdateIntervalEnforcesMinimum(t *testing.T) {
	trace := &clientJobTrace{updateInterval: common.DefaultUpdateInterval}
	trace.setUpdateInterval(1 * time.Second) // attacker-influenced tiny interval
	assert.GreaterOrEqual(t, trace.getUpdateInterval(), someMinimumFloor,
		"update interval must not go below a safe minimum")
}
```
Currently this assertion fails because `c.updateInterval` becomes exactly `1 * time.Second`, demonstrating the missing floor. A fuzz test over `updateIntervalHeader` values (`"0"`, `"-5"`, `"1"`, `"2"`) against `NewRemoteJobStateResponse` followed by `setUpdateInterval` can further confirm only the `<=0` and `MaxUpdateInterval` bounds are enforced.

func (c *clientJobTrace) setUpdateInterval(newUpdateInterval time.Duration) {
	if newUpdateInterval <= 0 {
		return
	}

	c.lock.Lock()
	defer c.lock.Unlock()

	// Let's hope that this never happens, but if the server behaves bogus
	// do not have too long an interval.
	c.updateInterval = min(newUpdateInterval, common.MaxUpdateInterval)

	if c.config.IsFeatureFlagOn(featureflags.UseDynamicTraceForceSendInterval) {
		forceSend := c.updateInterval * common.TraceForceSendUpdateIntervalMultiplier
		c.forceSendInterval = min(max(forceSend, common.MinTraceForceSendInterval), common.MaxTraceForceSendInterval)
	}
}
```

func (c *clientJobTrace) watch() {
	for {
		select {
		case <-time.After(c.getUpdateInterval()):
			if !c.incrementalUpdate() {
				// job is no longer running, wait for finish
				<-c.finished
				return
			}

		case <-c.finished:
			return
		}
	}
}

func (c *clientJobTrace) getUpdateInterval() time.Duration {
	c.lock.RLock()
	defer c.lock.RUnlock()

	return c.updateInterval
}
