### Title
Unauthenticated LDAP Bind Bypass via Empty Password in Login Request - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` forwards the client-supplied `sr.Password` directly to `conn.Bind(searchBaseDN, sr.Password)` without rejecting an empty password. Per LDAP protocol semantics (RFC 4513 §5.1.2), a Bind request with a non-empty DN and a zero-length password is treated as an "Unauthenticated Bind," which many LDAP servers (including default OpenLDAP configurations) will report as successful without verifying the account's real credential. An attacker who only knows (or guesses/enumerates) a valid target user's email can authenticate as that user without knowing their password.

### Finding Description
The unauthenticated `POST /sessions` endpoint binds JSON into `sessions.SessionRequest{Email, Password}` [1](#0-0)  and calls `AuthenticationProvider().CreateSession(ctx, sr)` with no server-side validation that `Password` is non-empty [2](#0-1) . `SessionRequest.Password` has no minimum-length or non-empty constraint [3](#0-2) .

In `CreateSession`, the request password is forwarded verbatim to the LDAP bind call: [4](#0-3) 

If `sr.Password == ""`, the LDAP `Bind` call constitutes an RFC-4513-defined "Unauthenticated Bind." Servers implementing the standard (unless explicitly configured to reject unauthenticated binds) return a successful bind result regardless of whether the credential is correct, because no password comparison is actually performed for this bind type. Since `err` from `conn.Bind` is nil in that case, `returnErr` stays nil, and the code proceeds to call `l.FindUser(ctx, escapedEmail)` to fetch the role and then unconditionally issues a valid session: [5](#0-4) 

There is no check anywhere in `CreateSession`, `sessions_controller.go`, or `SessionRequest` that rejects an empty/zero-length password before it reaches `conn.Bind`. This is exactly the reachable path from an unauthenticated attacker's login POST body to the vulnerable bind call.

### Impact Explanation
If the upstream LDAP directory permits unauthenticated binds (a common default absent explicit `disallow bind_anon` / similar hardening), an unauthenticated attacker can authenticate as any known LDAP user — including Admin-group members — by submitting `{"email": "<victim>@company.com", "password": ""}`. This grants a valid Chainlink node session with the victim's role (potentially Admin), enabling full RBAC bypass: job creation/deletion, key/secret access, fund-moving bridge/job actions, and other node-compromising operations gated behind session auth. This matches the Chainlink bounty "Authentication Bypass" / "Critical node compromise" impact class.

### Likelihood Explanation
Preconditions: (1) LDAP auth is enabled on the node, and (2) the backing LDAP server allows unauthenticated binds for the target DN (this is an LDAP-server-side setting, not something the Chainlink code controls). Given precondition (2), exploitation requires zero attacker privilege — only knowledge of a valid target email, which may be guessable/enumerable via corporate email conventions or the `FindUser`/`ListUsers` behavior. No credentials, network position, or operator access needed. This is a well-documented class of LDAP integration flaw (CWE-521/CWE-287 adjacent, "LDAP unauthenticated bind"), and it is trivially repeatable with a single crafted `POST /sessions` request.

Note: exploitability depends on the upstream LDAP server's configuration for unauthenticated binds, which is outside this repo's control; this reduces certainty of impact in any specific deployment, but the code provides no defense-in-depth against this well-known standard LDAP behavior.

### Recommendation
In `ldapAuthenticator.CreateSession` (and `TestPassword`), explicitly reject empty/zero-length passwords before calling `conn.Bind`, e.g.:
```go
if sr.Password == "" {
    return "", errors.New("unable to log in with LDAP server. Check credentials")
}
```
Apply the same guard in `TestPassword`. Additionally, consider using `UnauthenticatedBind` detection isn't sufficient — always fail closed on empty password client-side, regardless of server configuration, since this cannot be reliably remediated purely through server config in a defense-in-depth design.

### Proof of Concept
Go handler-level integration test plan in `core/sessions/ldapauth/ldap_test.go`:
1. Mock `LDAPClient.CreateEphemeralConnection` to return a mock `LDAPConn`.
2. Mock `LDAPConn.Bind(dn, "")` to return `nil` (simulating a real LDAP server's success response to an RFC-4513 unauthenticated bind), matching the DN template built from a known test email.
3. Mock `Search` calls used by `FindUser` to return a valid entry mapping to `sessions.UserRoleAdmin`.
4. Call `ldapAuthProvider.CreateSession(ctx, sessions.SessionRequest{Email: "victim@example.com", Password: ""})`.
5. Assert: the call returns a non-empty session ID and `nil` error (currently succeeds), demonstrating the bypass. After the fix, assert it returns an error and empty session ID for empty password input, without ever invoking `conn.Bind`.
