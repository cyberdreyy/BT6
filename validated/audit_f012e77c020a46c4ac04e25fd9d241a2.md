### Title
Write-account-lock contention lets an attacker perpetually deny a targeted user's transaction from landing (ingest starvation via priority-fee front-running) - ([File: core/src/banking_stage/transaction_scheduler/greedy_scheduler.rs])

### Summary
Agave's banking-stage scheduler grants **exclusive, first-come write locks per account** and schedules buffered transactions strictly by priority (compute-unit price). An attacker who observes a victim's pending transaction (via TPU/QUIC ingest, gossip, or simple knowledge of a popular shared account) can repeatedly submit their own higher-priority transaction that write-locks the same account. This is the direct on-chain analog of the Tracer `Trader` griefing bug: whoever "matches"/locks the shared resource first wins, and the loser is denied service — with no protocol-level fairness or ordering guarantee protecting the original submitter.

### Finding Description
Account locking is strictly exclusive per write-key, with no fairness/order guarantee beyond fee-priority: [1](#0-0) 

The scheduler pops transactions from a priority queue and attempts to lock accounts; on write-lock conflict the transaction is pushed back to "unschedulable" and must be retried later, while a higher fee always wins the lock race: [2](#0-1) [3](#0-2) 

Failed-to-lock transactions in the consumer path surface as `TransactionError::AccountInUse` and are marked retryable, meaning they loop back into the buffer rather than being processed — an attacker only needs to keep re-winning the lock race each scheduling pass: [4](#0-3) 

Compounding this, the per-thread buffer (`TransactionStateContainer`) has fixed capacity and evicts the **lowest-priority** transaction whenever a new one arrives while full — so a flood of attacker transactions with higher compute-unit price can also outright drop the victim's transaction from the buffer entirely, not merely delay it: [5](#0-4) [6](#0-5) 

Together, these mechanisms mean: (1) the write-lock on a contested account always goes to whichever conflicting transaction the scheduler processes/wins first (priority-fee driven), (2) the loser is retried but can be perpetually re-beaten, and (3) if attacker traffic saturates the buffer, the victim's transaction can be evicted and dropped before it is ever attempted — a direct structural analog of the "frontrun-and-match-first" griefing described in the Tracer report, where the attacker denies the victim access to a shared, exclusively-lockable resource (there: an order; here: a writable account).

### Impact Explanation
Any user transaction that writes to a shared/contested account (a popular AMM pool, order-book state account, escrow, etc.) can be persistently denied inclusion by a well-resourced attacker who continuously wins the write-lock race with higher priority fees. This is an ingest-starvation / censorship-style denial of service against specific users or specific on-chain economic actions (e.g., preventing a liquidation, preventing a trade from landing), mirroring the original report's "deny users from trading" impact, at the cost to the attacker of paying transaction fees (and, if they must also mutate the account themselves to hold the lock, the cost of executing their own competing transaction) — the same economic trade-off called out in the original report.

### Likelihood Explanation
Medium. This requires the attacker to (a) identify the target account being written to by the victim (observable from public transactions, mempool-like TPU forwarding, or simply from prior knowledge of a program's shared state account) and (b) sustain a higher compute-unit price than the victim across repeated scheduling passes/slots. No privileged access or protocol bug is required — this is a consequence of Agave's inherent per-account exclusive-lock + priority-fee scheduling design, so it is reliably reproducible by any unprivileged user with sufficient fee budget.

### Recommendation
This is largely an accepted trade-off of Solana's parallel, per-account-lock execution model, similar to the report's own conclusion that the underlying pattern is "hard to circumvent in the current design." Possible mitigations to reduce the practical severity include: enforcing minimum fair-scheduling guarantees (e.g., bounding how many times a transaction can be starved before being force-scheduled ahead of new higher-fee competitors), avoiding outright silent drops from the bounded `TransactionStateContainer` for transactions that have already survived multiple scheduling passes, and encouraging/enabling application-level design patterns (e.g., using multiple parallel state accounts or a local fee market/session keys) so that critical single-writer accounts are not easily monopolized by a single attacker.

### Proof of Concept
1. Victim submits a transaction `Tx_V` that writes to shared account `A` (e.g., calling a DEX/order-book program) with a modest compute-unit price.
2. Attacker observes `Tx_V` (or simply predicts contention on `A`) and repeatedly submits transactions `Tx_A1, Tx_A2, ...` that also write-lock `A`, each with a compute-unit price higher than `Tx_V`'s current priority.
3. In `greedy_scheduler`'s per-pass scan, the attacker's higher-priority transaction is always popped and locked first (`try_schedule_transaction`); `Tx_V` fails `can_write_lock` in `AccountLocks` and is marked `TransactionError::AccountInUse` / retried.
4. If the attacker sustains enough throughput/priority, `Tx_V` can additionally be evicted from the bounded `TransactionStateContainer` priority queue (`push_ids_into_queue` drops the lowest-priority entry once at capacity), permanently discarding it before it is ever executed — reproducing the "denied from trading" outcome from the original report.

    /// Returns the `ThreadId` if the accounts are able to be locked
    /// for the given thread, otherwise `None` is returned.
    /// `allowed_threads` is a set of threads that the caller restricts locking to.
    /// If accounts are schedulable, then they are locked for the thread
    /// selected by the `thread_selector` function.
    /// `thread_selector` is only called if all accounts are schdulable, meaning
    /// that the `thread_set` passed to `thread_selector` is non-empty.
    pub fn try_lock_accounts<'a>(
        &mut self,
        write_account_locks: impl Iterator<Item = &'a Pubkey> + Clone,
        read_account_locks: impl Iterator<Item = &'a Pubkey> + Clone,
        allowed_threads: ThreadSet,
        thread_selector: impl FnOnce(ThreadSet) -> ThreadId,
    ) -> Result<ThreadId, TryLockError> {
        let schedulable_threads = self
            .accounts_schedulable_threads(write_account_locks.clone(), read_account_locks.clone())
            .ok_or(TryLockError::MultipleConflicts)?;
        let schedulable_threads = schedulable_threads & allowed_threads;
        if schedulable_threads.is_empty() {
            return Err(TryLockError::ThreadNotAllowed);
        }

        let thread_id = thread_selector(schedulable_threads);
        self.lock_accounts(write_account_locks, read_account_locks, thread_id);
        Ok(thread_id)
    }

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }
