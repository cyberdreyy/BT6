### Title
Post-default instant withdraw receipts are indexed to the frozen `defaultRecoveryEpoch`, letting attackers drain `defaultRecoveryReserve` at the recovery haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.epochNumber` only increments inside `deposit()` when `isEpochRunning()` is true (`contracts/strategies/idle/IdleCreditVault.sol:607-611`). After a borrower default the pool never starts a new epoch, so `epochNumber` stays pinned to the defaulted epoch forever — which is exactly the value stored in `defaultRecoveryEpoch` by `finalizeDefaultRecovery` (`:693`). `requestInstantWithdraw` has no `defaultRecoveryFinalized` branch (unlike `requestWithdraw`, which routes post-default requests into `postDefaultRequests`, `:247-257`), so a receipt created after default finalization is recorded under `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (`:371-372`). This is the analog of the SDL buffer over-read: an epoch-indexed lookup reads a bucket boundary that no longer matches the semantic lifetime of the data.

### Finding Description
In `claimInstantWithdrawRequest` (`:380-393`), when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, `_claimDefaultedInstantWithdrawRequest` (`:842-856`) reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and pays `claimBasis * defaultRecoveryPrice / 1e18` out of `defaultRecoveryReserve`. Because post-default `requestInstantWithdraw` calls write into that same epoch slot and also increment `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` (`:372`), a fresh post-default receipt is indistinguishable from a pre-default defaulted claim:

1. Borrower defaults; `finalizeDefaultRecovery` sets `defaultRecoveryPrice = R < 1e18`, `defaultRecoveryEpoch = E`, `defaultInstantWithdrawsFinalized = true`, and sizes `defaultRecoveryReserve` from `defaultPendingClaimBasis()` (`:644-649`).
2. Attacker (any tranche holder) calls `cdoEpoch.requestInstantWithdraw(amount)` → strategy `requestInstantWithdraw` burns CDO tokens, mints a receipt to the attacker, and writes `instantWithdrawsRequestsByEpoch[attacker][E] += amount` since `epochNumber` is still `E`.
3. Attacker calls `claimInstantWithdrawRequest`; `_claimDefaultedInstantWithdrawRequest` clears the attacker's fake "defaulted" basis and transfers `amount * R` from `defaultRecoveryReserve` — reserve that was earmarked 1:1 for pre-default claimants.
4. Net effect: the attacker deposited receipt basis worth `amount` of strategy tokens (burned from the CDO at the post-default, haircut price) and withdrew `amount * R` of reserve underlying immediately, extracting reserve that belongs to legitimate default claimants and leaving the reserve short for them (insolvency of the recovery reserve). `_claimDefaultedInstantWithdrawRequest` also decrements `pendingInstantWithdraws` (`:852`) and `instantWithdrawClaimsByEpoch[E]` (`:853`), corrupting the funded/unfunded split used by `_defaultPrefundedInstantReserve` accounting symmetry.

### Impact Explanation
Direct theft of `defaultRecoveryReserve`: each post-default instant receipt converts already-haircut strategy tokens into an immediate reserve payout, draining funds reserved for pre-default normal/instant claimants and post-default `postDefaultRequests` claimants (`_claimPostDefaultWithdrawRequest`, `:760-767`). Quantified loss: up to the full `defaultRecoveryReserve`, bounded by the attacker's tranche holdings; every unit withdrawn at `R` is a unit unavailable to legitimate claimants, causing a permanent shortfall (last claimants revert on insufficient balance in `_transferDefaultRecovery`).

### Likelihood Explanation
Requires only that (a) a default occurred and recovery finalized with `pendingInstantWithdraws != 0` (so `defaultInstantWithdrawsFinalized` is true), and (b) `requestInstantWithdraw` remains callable on the CDO after default — the strategy itself imposes no post-default or running-epoch gate on this path, and instant withdraw is a queueing operation that does not require epoch liquidity. The attacker needs only tranche tokens, obtainable as an ordinary KYC'd lender. I was unable to confirm within the iteration limit whether `IdleCDOEpochVariant.requestInstantWithdraw` blocks calls while `defaulted()` is true; if it does, the exploit is unreachable and this reduces to a latent accounting inconsistency.

### Recommendation
Mirror the `requestWithdraw` post-default branch in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert or route the receipt into a separate post-default bucket keyed by a monotonically increasing index rather than the frozen `epochNumber`. Alternatively, snapshot `defaultRecoveryEpoch` claims at finalization (e.g., record `instantWithdrawClaimsByEpoch[E]` into a fixed `defaultInstantBasis`) and have `_claimDefaultedInstantWithdrawRequest` bound claims to that snapshot, and refuse `epochNumber`-indexed writes once `defaultRecoveryFinalized`.
