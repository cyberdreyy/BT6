### Title
Zero `calculatedIndex` from rounding in `_isValidPartialFill` causes incorrect secret validation or denial of service - ([File: contracts/BaseEscrowFactory.sol])

### Summary
A vulnerability exists in the `BaseEscrowFactory._isValidPartialFill` function where the calculation of `calculatedIndex` can round to zero due to integer division when `makingAmount` is small relative to `orderMakingAmount`. This mirrors the root cause in the seed report where a division-based calculation rounds to zero, leading to incorrect state transitions or potential DoS. In this context, it allows an attacker to reuse the first secret of a Merkle tree for subsequent partial fills or causes a revert when `partsAmount` is small.

### Finding Description
The function `_isValidPartialFill` is used to validate which secret from a Merkle tree should be used for a partial fill in a cross-chain swap [1](#0-0) . The index calculation is:
```solidity
uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;
``` [2](#0-1) 

When `(orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount < orderMakingAmount`, the `calculatedIndex` rounds down to `0`. 

Consider a scenario where a maker creates an order for a large `orderMakingAmount` and a small `partsAmount` (e.g., 2). If a taker performs a very small partial fill such that the numerator is less than the denominator, `calculatedIndex` becomes 0.

The function then checks:
```solidity
return calculatedIndex + 1 == validatedIndex;
``` [3](#0-2) 

If `calculatedIndex` is 0, the function expects `validatedIndex` to be 1. The `validatedIndex` is derived from `takerData.idx + 1` in `MerkleStorageInvalidator.takerInteraction` [4](#0-3) . This means the taker must provide a secret with `takerData.idx = 0`.

If the taker performs multiple tiny fills, the `calculatedIndex` may remain 0 for several iterations. Since the `validatedIndex` is checked against the index of the secret just validated in `takerInteraction`, the protocol might allow the reuse of the same secret index (index 0) if the state transition logic in `_isValidPartialFill` does not strictly enforce progress when rounding occurs. 

Specifically, the check:
```solidity
uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
if (calculatedIndex == prevCalculatedIndex) return false;
``` [5](#0-4) 
is intended to prevent this, but if the `makingAmount` is small enough, both `calculatedIndex` and `prevCalculatedIndex` will be 0, leading to a revert (DoS).

### Impact Explanation
This vulnerability leads to a **Medium** impact:
1. **Permanent DoS for small partial fills**: If a taker attempts a partial fill that is too small relative to the total order size, the `calculatedIndex` and `prevCalculatedIndex` will both round to zero, causing the transaction to revert [6](#0-5) . An unprivileged actor can trigger this by filling a tiny portion of a large order, effectively "bricking" the ability to perform small fills for that order.
2. **Incorrect Accounting**: If the logic fails to prevent index reuse due to rounding edge cases, it could lead to the release of funds on the destination chain using a secret that was already revealed for a previous partial fill on the source chain.

### Likelihood Explanation
The likelihood is **Medium**. It requires a specific configuration of `orderMakingAmount` and `partsAmount`, and a taker (who could be the attacker) to provide a `makingAmount` that triggers the rounding. This is a common pattern in 1inch limit orders where partial fills are frequent.

### Recommendation
Implement a minimum fill amount check or use a higher precision for the index calculation to ensure that any non-zero `makingAmount` results in a detectable progression of the `calculatedIndex`. Alternatively, ensure that `calculatedIndex` is strictly greater than `prevCalculatedIndex` by adding a requirement that the fill must cover at least one "part" of the Merkle tree.

### Proof of Concept
1. Alice creates a cross-chain order for `1000e18` tokens with `partsAmount = 10`.
2. Bob (Taker) calls `fillOrder` with `makingAmount = 1e18`.
3. In `_postInteraction`, `orderMakingAmount = 1000e18`, `remainingMakingAmount = 1000e18`, `makingAmount = 1e18`.
4. `calculatedIndex = (1000e18 - 1000e18 + 1e18 - 1) * 10 / 1000e18` = `(1e18 - 1) * 10 / 1000e18` = `0`.
5. If this is the second fill and the first fill was also small, `prevCalculatedIndex` will also be `0`.
6. The condition `if (calculatedIndex == prevCalculatedIndex) return false;` [6](#0-5)  triggers, reverting the transaction.
