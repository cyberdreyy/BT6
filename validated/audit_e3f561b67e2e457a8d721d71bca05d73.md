### Title
Re-requesting a withdrawal after a loss-adjusted epoch orphans `lossRecoveryPriceByEpoch` and pays the haircut basis at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2019-6956 is a buffer over-read: the code reads past the boundary of the intended buffer. The analog in `IdleCreditVault` is an index over-read across the epoch-indexed receipt storage: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch` only at the single slot `lastWithdrawRequest[_user]`. When a user has a loss-haircut receipt in epoch N and then submits a new `requestWithdraw` in epoch N+1, `lastWithdrawRequest` is overwritten, so the loss price at epoch N is never read ("read past" the haircut slot). The stale basis remains inside the aggregate `withdrawsRequests[_user]` and is later paid out at par by `_claimFundedWithdrawRequest`, even though `collectWithdrawFunds` only pulled `basis * lossRecoveryPrice` of underlying for it.

### Finding Description
- `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`) handles underfunded stops: when the borrower funds less than `pendingWithdraws`, it stores the haircut ratio in `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`. Only `_amount < pendingBasis` of underlying is actually transferred into the strategy.
- `requestWithdraw` (`IdleCreditVault.sol:282`) sets `lastWithdrawRequest[_user] = currentEpoch`, a single slot that can only point at one epoch.
- `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`) computes `lossEpoch = lastWithdrawRequest[_user]` and reads only `lossRecoveryPriceByEpoch[lossEpoch]`. There is no iteration over older epochs.
- `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-350`) pays `withdrawsRequests[_user]` at par; that aggregate is only reduced when `_clearWithdrawClaimForEpoch` is invoked for the specific epoch (`IdleCreditVault.sol:815-819`).

Attack sequence (any KYC'd lender / tranche holder):
1. Epoch N running: attacker calls `IdleCDOEpochVariant.requestWithdraw` → receipt basis B recorded in `withdrawsRequestsByEpoch[attacker][N]` and `withdrawsRequests[attacker] += B`; `lastWithdrawRequest[attacker] = N`.
2. Honest manager calls `stopEpochWithDuration`/`stopEpoch` where the borrower underfunds: `collectWithdrawFunds` pulls only `B * p` (`p = lossRecoveryPriceByEpoch[N] < 1e18`) and zeroes `pendingWithdraws`. All pending receipts of epoch N are supposed to be haircut to `p`.
3. Epoch N+1: attacker calls `requestWithdraw` again (even for a dust amount) → `lastWithdrawRequest[attacker] = N+1`. The epoch-N haircut entry is now unreachable.
4. After epoch N+1 stops (epoch gate `epochNumber > lastWithdrawRequest` passes), attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] = 0` and returns 0 without clearing `withdrawsRequestsByEpoch[attacker][N]` or decrementing `withdrawsRequests`. `_claimFundedWithdrawRequest` then pays the full aggregate `withdrawsRequests[attacker]` — which still contains the epoch-N basis B — at par.

No existing guard stops this: `_skimDonatedAssets`, epoch gating, `_transferFundedClaim`'s reserve check (`IdleCreditVault.sol:897-907`) all pass because default recovery is not involved, and the strategy holds the extra underlying precisely because other funded receipts or deposits sit in the same balance.

### Impact Explanation
Direct theft / insolvency. The attacker is paid `B` instead of `B * p`, extracting `(1 - p) * B` underlying that was never funded. For a 50% stop-loss (`p = 0.5e18`) and B = 1,000,000 USDC, the attacker overclaims 500,000 USDC from the strategy's underlying balance, leaving other funded receipt holders or the recovery reserve short — a broken "one receipt one (haircut) payout" invariant. It can also permanently freeze later claimants if the strategy balance is drained below their funded amount.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/`stopEpoch` that underfunds `pendingWithdraws` (a partial loss event, an explicit code path with `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds`), plus an unprivileged re-request and one epoch of waiting. The attacker is a normal lender; no privileged cooperation is needed. Likelihood is moderate: it needs a loss epoch to occur, but once it does the exploit is deterministic and repeatable per receipt.

### Recommendation
Track a per-user queue/set of request epochs (or store the loss price inside the per-user receipt), and in `_claimLossAdjustedWithdrawRequest` iterate all epochs with non-zero `withdrawsRequestsByEpoch[_user][e]` that have a `lossRecoveryPriceByEpoch[e]`, or check both `lastWithdrawRequest` and every unsettled epoch. Alternatively, when `requestWithdraw` is called, eagerly settle any prior loss-adjusted epoch receipt before overwriting `lastWithdrawRequest`, so no haircut entry can be orphaned.

### Proof of Concept
Foundry fork PoC sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testLossAdjustedReceiptPaidAtParAfterReRequest() external {
    // setup: deposit as attacker into AA, start epoch 0
    uint256 amount = 1_000_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    _startEpochAndCheckPrices(0);

    // 1) attacker requests withdraw during epoch 0
    uint256 basis = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));

    _startEpochAndCheckPrices(1);

    // 2) borrower underfunds at stopEpoch -> lossRecoveryPriceByEpoch[1? request epoch] = p < 1e18
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 funded = pending / 2; // 50% loss on pending receipts
    deal(defaultUnderlying, borrower, funded);
    // manager calls stopEpochWithDuration/stopEpoch path that calls previewLossAdjustedWithdrawFunds
    // and collectWithdrawFunds(funded) -> lossRecoveryPriceByEpoch[epochNumber] = 0.5e18, pendingWithdraws = 0

    // 3) attacker re-requests a dust withdraw in the next epoch, overwriting lastWithdrawRequest
    uint256 dustBasis = cdoEpoch.requestWithdraw(1, address(AAtranche));
    _startEpochAndCheckPrices(2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // borrower fully funds this epoch
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + IdleCreditVault(address(strategy)).pendingWithdraws());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // 4) attacker claims: gets basis + dustBasis at par instead of basis*0.5 + dustBasis
    uint256 balBefore = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balBefore;
    // expected (correct): basis / 2 + dustBasis ; actual: basis + dustBasis
    assertGt(got, basis / 2 + dustBasis + 1);
}
```

The assertion `got > basis * p + dustBasis` demonstrates the haircutted epoch-N basis being paid at par — i.e., the strategy paid out underlying that was never collected, at the expense of other claimants.
