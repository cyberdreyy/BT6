### Title
Cross-user response hijack via unchecked overwrite in `HandleLegacyUserMessage`'s `savedCallbacks` map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores each user callback in `h.savedCallbacks` keyed only by `msg.Body.MessageId`, with no existence/conflict check before writing, unlike the analogous `(*httpTriggerHandler).setupCallback` in `v2/http_trigger_handler.go` which explicitly checks `if _, found := h.callbacks[requestID]; found` and returns `jsonrpc.ErrConflict`. Because `MessageId` is attacker-supplied and not required to be unique across senders, two different unauthenticated clients (or the same client twice) can submit messages with the same `MessageId`, causing the second write to silently clobber the first client's callback, so the DON's eventual trigger response is delivered to the second (attacker) caller instead of the original requester.

### Finding Description
`HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421) validates payload timestamp/method, builds the outbound request, then does: [1](#0-0) 
This is an unconditional map write — no lookup for an existing entry, no rejection, no error returned to the caller when a collision occurs. Compare with the v2 handler's `setupCallback`, which locks the same-purpose map and explicitly rejects a colliding `requestID`: [2](#0-1) 

The `MessageId` field is fully attacker-controlled. `api.Message.Validate()` only checks length bounds and null-byte suffixes on `MessageId` — it enforces no uniqueness, and the cryptographic signature only proves who signed the message, not that the ID is unique: [3](#0-2) 

When a node later responds via `MethodWebAPITrigger`, `handleWebAPITriggerMessage` looks up the callback strictly by `MessageId`, deletes it, and forwards the response to whichever callback is currently stored — with no verification that the responding request corresponds to the original submitter: [4](#0-3) 

Exploit flow: Attacker A submits a legitimate `HandleLegacyUserMessage` with `MessageId = "dup"` targeting some workflow; the handler stores A's callback and forwards A's request to all DON members. Before the DON responds, Attacker B (or the same attacker under a different signature) submits a second message with the identical `MessageId = "dup"`. The second call overwrites `h.savedCallbacks["dup"]` with B's callback and also fires its own request to the DON. When the DON responds to either request (the first node to answer for ID "dup" — potentially even answering A's original request), `handleWebAPITriggerMessage` delivers that response to whatever callback is currently stored, which is now B's. This hijacks A's response to B, and A's own callback is silently dropped with no error ever surfacing.

### Impact Explanation
This is a cross-user response confusion / hijack: an unprivileged, unauthenticated gateway client can intercept or corrupt another user's workflow-trigger response by racing a duplicate `MessageId`. Depending on payload content, this could leak data intended for another caller back to the attacker (information disclosure) or silently drop/corrupt a legitimate user's request (denial of service for that request), matching Chainlink's "cross-user response confusion" impact class explicitly called out in this audit's rules.

### Likelihood Explanation
Preconditions are minimal: any client capable of producing a validly-signed `api.Message` (the standard, unauthenticated gateway HTTP/WS client requirement for this handler) can trigger this — no special role, allowlist entry, or elevated credential is required beyond what's already needed to call `HandleLegacyUserMessage` at all. The attack requires no cryptographic forgery of another user's message; the attacker simply reuses/guesses/races a `MessageId` value with their own validly-signed message. This is trivially repeatable and requires only two quick successive calls with a chosen colliding ID, matching the described attacker sequence `msg1(id='dup') -> msg2(id='dup')`.

### Recommendation
Add the same conflict-check pattern used in `(*httpTriggerHandler).setupCallback`: under `h.mu`, check `if _, found := h.savedCallbacks[msg.Body.MessageId]; found` before inserting, and if found, return an error/`ErrConflict`-style response to the caller (e.g., via `callback.SendResponse` with a JSON-RPC conflict error) instead of silently overwriting. Optionally scope the callback key by `(Sender, MessageId)` rather than `MessageId` alone to prevent even same-ID collisions across different senders from being treated as related.

### Proof of Concept
Go table/unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a mock `handlers.DON` that no-ops `SendToNode`.
2. Build two distinct `handlers.Callback` mocks, `cb1` and `cb2`, each recording whether `SendResponse` was invoked and with what payload.
3. Build two valid `api.Message`s with identical `Body.MessageId = "dup"`, valid `Method = MethodWebAPITrigger`, valid `Timestamp`, but signed by two different private keys (simulating two different senders) or the same key called twice.
4. Call `h.HandleLegacyUserMessage(ctx, msg1, cb1)` then `h.HandleLegacyUserMessage(ctx, msg2, cb2)`.
5. Assert: both calls return `nil` error (no conflict is ever surfaced) and `h.savedCallbacks["dup"].Callback` now equals `cb2`, i.e., `cb1`'s entry has been silently overwritten/lost.
6. Contrast with a second test that exercises `(*httpTriggerHandler).setupCallback` in `v2/http_trigger_handler.go` with the same duplicated `requestID`, asserting the second call returns a non-nil error and `cb1`'s `SendResponse` is invoked with `jsonrpc.ErrConflict`, demonstrating the v2 path correctly rejects the collision while the legacy path in `handler.go` does not.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
