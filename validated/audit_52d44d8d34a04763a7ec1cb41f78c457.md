### Title
`TransferPolicy::destroy_and_withdraw` Orphans Rule-Config Dynamic Fields, Permanently Locking Storage Rebates - (File: `crates/sui-framework/packages/sui-framework/sources/kiosk/transfer_policy.move`)

---

### Summary

`sui::transfer_policy::destroy_and_withdraw` deletes the `TransferPolicy` object's UID without first removing the rule-configuration dynamic fields that were attached via `add_rule`. Every `Field<RuleKey<Rule>, Config>` child object becomes permanently orphaned: it exists in the object store but can never be accessed or deleted, and its storage rebate is locked forever.

---

### Finding Description

When a rule is added to a `TransferPolicy<T>`, `add_rule` stores the configuration as a dynamic field on the policy's UID:

```move
df::add(&mut policy.id, RuleKey<Rule> {}, cfg);
policy.rules.insert(type_name::with_defining_ids<Rule>())
``` [1](#0-0) 

The `rules` field is a `VecSet<TypeName>` that tracks which rules are active. The actual configuration data lives in separate on-chain `Field<RuleKey<Rule>, Config>` objects (child objects of the policy UID).

`destroy_and_withdraw` unpacks the policy by value and calls `id.delete()`:

```move
let TransferPolicyCap { id: cap_id, policy_id } = cap;
let TransferPolicy { id, rules: _, balance } = self;
id.delete();
cap_id.delete();
``` [2](#0-1) 

`rules: _` silently drops the `VecSet` (which has `drop`), but the `Field<RuleKey<Rule>, Config>` objects on-chain are **not** removed. `id.delete()` is called while those child objects still exist. From this point forward, no transaction can ever reference or delete them — their parent UID is gone.

The correct removal path exists in `remove_rule`:

```move
let _: Config = df::remove(&mut policy.id, RuleKey<Rule> {});
policy.rules.remove(&type_name::with_defining_ids<Rule>());
``` [3](#0-2) 

But `destroy_and_withdraw` never calls it, and there is no guard (like `assert!(self.rules.is_empty(), ...)`) preventing destruction when rules are present. Compare with `Kiosk::close_and_withdraw`, which correctly asserts `item_count == 0` before deletion. [4](#0-3) 

The framework's own documentation acknowledges the general hazard:

> "It is possible to delete an object that has dynamic fields still defined on it … deleting an object that has dynamic fields still defined on it renders them all inaccessible to future transactions." [5](#0-4) 

The framework's own skill guide classifies this pattern as **SM-C1 — Orphaned dynamic fields / leaked UID on destruction [Critical]**:

> "Exploit: child objects/funds become permanently inaccessible (no recovery) — asset loss or locked collateral." [6](#0-5) 

---

### Impact Explanation

Each orphaned `Field<RuleKey<Rule>, Config>` object permanently locks its storage rebate in SUI. The object exists in the global object store but has no reachable parent UID, so no transaction can ever call `df::remove` on it or `object::delete` its inner UID. The locked SUI is unrecoverable. This is a **permanent fund lock** matching the High/Medium impact gate.

---

### Likelihood Explanation

`TransferPolicy` objects are widely deployed in the Kiosk ecosystem. Any policy that has had at least one rule added (via `add_rule`) and is then destroyed via `destroy_and_withdraw` — without the owner first calling `remove_rule` for each rule — triggers the orphaning. The `TransferPolicyCap` holder is an ordinary user; no privileged access is required. The function is `public` and callable from any PTB.

---

### Recommendation

Add a guard in `destroy_and_withdraw` that aborts if any rules remain:

```move
assert!(self.rules.is_empty(), ERulesNotEmpty);
```

Or, since `Config: store + drop`, iterate over the known rule keys and remove each dynamic field before calling `id.delete()`. The cleanest approach mirrors `Kiosk::close_and_withdraw`'s `assert!(item_count == 0, ENotEmpty)` pattern — require the caller to remove all rules before destroying the policy.

---

### Proof of Concept

1. Publish a package with a `Rule` witness type and a `Config: store + drop` struct.
2. Call `transfer_policy::new<T>` to create a `TransferPolicy<T>` and its cap.
3. Call `add_rule<T, Rule, Config>` — this writes a `Field<RuleKey<Rule>, Config>` dynamic field onto the policy's UID.
4. Call `destroy_and_withdraw<T>(policy, cap, ctx)` — the policy is destroyed, `id.delete()` is called, but the `Field` child object is never removed.
5. Observe: the `Field` object still exists in the object store (visible via `sui_getObject`) but can never be accessed, mutated, or deleted. Its storage rebate is permanently locked. [7](#0-6)

public fun destroy_and_withdraw<T>(
    self: TransferPolicy<T>,
    cap: TransferPolicyCap<T>,
    ctx: &mut TxContext,
): Coin<SUI> {
    assert!(object::id(&self) == cap.policy_id, ENotOwner);

    let TransferPolicyCap { id: cap_id, policy_id } = cap;
    let TransferPolicy { id, rules: _, balance } = self;

    id.delete();
    cap_id.delete();
    event::emit(TransferPolicyDestroyed<T> { id: policy_id });
    balance.into_coin(ctx)
}

```text
## Deleting an object with dynamic fields

It is possible to delete an object that has (potentially non-`drop`) dynamic fields still defined on it. Because field values can be accessed only through the dynamic field's associated object and field name, deleting an object that has dynamic fields still defined on it renders them all inaccessible to future transactions. This is true regardless of whether the field's value has the `drop` ability. This might not be a concern when adding a small number of statically known additional fields to an object, but is particularly undesirable for onchain collection types that could be holding unboundedly many key-value pairs as dynamic fields.
