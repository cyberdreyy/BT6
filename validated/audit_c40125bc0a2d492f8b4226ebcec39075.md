### Title
`createPolicy` assigns IDs from a shared global counter with no atomicity guarantee between simulation and inclusion, letting callers bind funds/tokens to an unexpected policy ID - (File: crates/common/precompiles/src/policy/logic/v1.rs, crates/common/precompiles/src/policy/logic/v2.rs)

### Summary
The Policy Registry precompile's `createPolicy` derives the returned `policyId` from a single, chain-wide monotonic counter (`next_counter`) that every caller of the precompile shares. `create_policy_inner` reads the counter, computes `policy_id = make_id(policy_type, counter)`, and writes `counter + 1` back to storage with no check that the counter still equals the value the caller expected. This is the same bug class as the reported Canto `Tray.buy()` issue: a value the client precomputes off-chain (via `eth_call`/simulation) to know "what ID/tiles I will get" can silently change on-chain if another transaction that also creates a policy lands first, and the caller's transaction still succeeds — assigning them a *different* policy ID than the one they simulated and intended to reference.

### Finding Description
`create_policy_inner` in both the V1 and V2 policy-registry logic implementations: [1](#0-0) [2](#0-1) 

reads the shared `next_counter` via `ensure_initialized_and_get_counter`, computes the new `policy_id`, and increments the counter — all without pinning the operation to an expected counter/ID supplied by the caller. `ensure_initialized_and_get_counter` reads a single, address-scoped storage slot shared by every caller of the precompile: [3](#0-2) 

The precompile's own system-test helper explicitly documents the precondition under which this is safe — and, by implication, the condition under which it is not: [4](#0-3) 
"Simulates the call first (`eth_call`) to obtain the ID the registry will assign, then dispatches the real transaction. Because the system test stack is single-sender the counter cannot advance between the simulation and the actual transaction." In production, with multiple unprivileged senders able to call `createPolicy`/`createPolicyWithAccounts` concurrently, the counter *can* advance between a caller's simulation and the inclusion of their transaction — via ordinary mempool activity or a deliberate front-run of a higher-fee transaction that also calls the registry. The caller's transaction does not revert; it simply succeeds with a `policyId` that encodes a different counter value than what was simulated/expected.

This mirrors the Canto Tray root cause precisely: a deterministic, precomputable output derived from evolving global state, consumed by a state-changing call with no check that the precondition (expected counter/hash) still holds at execution time.

### Impact Explanation
`policyId` is not an inert accounting value — it is the handle used to bind access-control policies to B-20 tokens (transfer gating via allow/block lists) and to reference the policy for later admin/membership updates. If an application or off-chain integrator precomputes the ID it expects a `createPolicy` call to yield (e.g., to pre-configure a token's transfer policy reference, or to coordinate a multi-step deployment script that binds a specific policy ID to a specific token/role) and the ID actually assigned differs due to counter drift, the caller can:
- End up owning/administering a policy ID different from the one referenced elsewhere in their deployment flow, so a token's transfer policy binds to the wrong (potentially attacker-created or unintended) policy, silently misconfiguring access control (allowing unauthorized transfers or freezing legitimate ones).
- Waste the gas paid for `createPolicy` while ending up with a policy object that does not match their intended `PolicyCreated`/`PolicyAdminUpdated` id, with no on-chain signal (no revert) that anything went wrong.

This is a Medium-severity issue: it requires the caller to rely on precomputed/simulated IDs (a supported, encouraged pattern per the precompile's own test helper) rather than always consuming the return value atomically in the same transaction, but when that pattern is used it can lead to unauthorized policy binding or fund/token access-control misconfiguration.

### Likelihood Explanation
Reachable by any unprivileged transaction sender calling the Policy Registry precompile (`createPolicy` / `createPolicyWithAccounts`), which is a public, permissionless precompile entry point once the `PolicyRegistry` activation feature is enabled. The race only requires ordinary mempool concurrency (any other account calling `createPolicy`/`createPolicyWithAccounts` in between simulation and inclusion) — no special privileges, and it can also be triggered deliberately by an attacker who front-runs a target's `createPolicy` transaction with their own policy-creation call to shift the counter.

### Recommendation
Do not rely on race-free simulate-then-send patterns for policy IDs derived from shared global state. Add an optional `expectedCounter`/`expectedPolicyId` parameter to `createPolicy`/`createPolicyWithAccounts` (or equivalently expose and require checking the current counter atomically) so the call reverts if the shared counter has advanced past what the caller anticipated, analogous to the recommended `_lastHash` check in the Tray fix. Document clearly that the `policyId` return value must be treated as authoritative only when consumed within the same transaction, not precomputed via a prior `eth_call`.

### Proof of Concept
1. Caller A calls `eth_call` for `createPolicy(admin=A, type=ALLOWLIST)` against `PolicyRegistryStorage`, observing predicted `policyId = (ALLOWLIST << 56) | N` (current `next_counter = N`).
2. Before A's real transaction is included, another account B (either coincidentally or as a front-run) sends and gets included first with its own `createPolicy` (or `createPolicyWithAccounts`) call, incrementing the shared counter to `N+1` via: [5](#0-4) 
3. A's transaction is then included and succeeds, but returns/emits `policyId = (ALLOWLIST << 56) | (N+1)` instead of the value A simulated and relied on.
4. If A's deployment script or another contract had already been configured (e.g., in a prior or parallel transaction) to reference the predicted `N`-based ID for token-transfer policy binding, that binding now points at the wrong policy, silently breaking the intended access control — with no revert anywhere in the flow to signal the mismatch.

    pub(crate) fn ensure_initialized_and_get_counter<S: PolicyAccounting>(
        &self,
        storage: &mut S,
    ) -> Result<u64> {
        let counter = storage.read_next_counter()?;
        if counter >= Self::BUILTIN_POLICY_COUNT {
            return Ok(counter);
        }
        // Assert that the ID constants match the enum discriminants and counter slots,
        // catching any future drift from enum reordering or constant changes.
        debug_assert_eq!(
            Self::make_id(PolicyType::BLOCKLIST.as_discriminant(), 0),
            Self::ALWAYS_ALLOW_ID
        );
        debug_assert_eq!(
            Self::make_id(PolicyType::ALLOWLIST.as_discriminant(), 1),
            Self::ALWAYS_BLOCK_ID
        );
        storage.mark_initialized()?;
        let builtin = PackedPolicy::new(Address::ZERO).into_u256();
        storage.write_policy_word(Self::ALWAYS_ALLOW_ID, builtin)?;
        storage.write_policy_word(Self::ALWAYS_BLOCK_ID, builtin)?;
        storage.write_next_counter(Self::BUILTIN_POLICY_COUNT)?;
        Ok(Self::BUILTIN_POLICY_COUNT)
    }

/// Creates a policy and returns its assigned ID.
///
/// Simulates the call first (`eth_call`) to obtain the ID the registry will
/// assign, then dispatches the real transaction.  Because the system test stack is
/// single-sender the counter cannot advance between the simulation and the
/// actual transaction.
async fn create_policy(
    client: &B20PrecompileClient<'_>,
    admin: Address,
    policy_type: IPolicyRegistry::PolicyType,
    label: &'static str,
) -> Result<u64> {
    let call = IPolicyRegistry::createPolicyCall { admin, policyType: policy_type };
    let output = client.call(PolicyRegistryStorage::ADDRESS, call.clone()).await?;
    let policy_id = IPolicyRegistry::createPolicyCall::abi_decode_returns(output.as_ref())
        .wrap_err("Failed to decode createPolicy return")?;
    client.send_call(PolicyRegistryStorage::ADDRESS, call, label).await?;
    Ok(policy_id)
}
