## Title
Masked CI/CD variable substring can corrupt `urlsanitizer` key detection and expose adjacent secret query-string values - ([File: common/buildlogger/internal/urlsanitizer/urlsanitizer.go])

## Summary
In `Logger.wrap`, `masker` is the outermost filter and processes raw bytes before `urlsanitizer` ever sees them [1](#0-0) . If a job-defined masked CI/CD variable's literal value happens to be a substring of one of `urlsanitizer`'s sensitive key names (e.g. `ate_tok` inside `private_token`), `masker` splits and rewrites the byte stream mid-key, so `urlsanitizer.Write` reconstructs a corrupted key (`priv[MASKED]en`) that no longer matches `tokenParamKeys`, causing the adjoining secret value to be forwarded to the trace unmasked.

## Finding Description
`masker.masker.Write` streams data to the next writer in fragments: unmatched bytes before a phrase match are sent via `m.next.Write(p[last:n])`, then on a full phrase match it recursively calls `m.Write(mask)`, which hits the fast path `bytes.Equal(p, mask)` and forwards the literal `[MASKED]` bytes to `m.next.Write(mask)` as a separate call [2](#0-1) [3](#0-2) .

`urlsanitizer.URLSanitizer.Write` accumulates a candidate key name in `s.match`, a struct field that persists across separate `Write` calls, until it hits `=`, `?`, `&`, or its capacity, then looks it up (case-insensitively) in `tokenParamKeys` [4](#0-3) .

Given a masked phrase `"ate_tok"` (a substring of `private_token`) and input `?private_token=SECRETVALUE\n`:
1. `masker` calls `urlsanitizer.Write("?priv")` — `s.match` becomes `"?priv"`.
2. `masker` calls `urlsanitizer.Write("[MASKED]")` — none of `=?&` appear in `[MASKED]`, so all 8 bytes get appended to `s.match`, producing `"?priv[MASKED]"`, and the whole chunk is forwarded to the underlying writer unmodified (this write never triggers `tokenParamKeys` lookup).
3. `masker` calls `urlsanitizer.Write("en=SECRETVALUE\n")` — `s.match` becomes `"?priv[MASKED]en"` after consuming up to `=`; `strings.ToLower(string(key[1:]))` = `"priv[masked]en"`, which does **not** match `"private_token"` in `tokenParamKeys`. The key check fails, `s.masking` is never set to `true`, and `SECRETVALUE\n` is written straight through to the base trace unmasked.

The existing "invariant" that filters compose safely across the `wrap` chain is broken because `masker` operates on raw bytes without any awareness of `urlsanitizer`'s key vocabulary, and `urlsanitizer` has no fallback to detect that its key-matching buffer was interrupted by a literal `[MASKED]` marker.

## Impact Explanation
A real secret value appearing in a URL query string logged during a job (e.g. `private_token=<GitLab PAT>` printed by a script, curl command, or tool output) is not masked by `urlsanitizer` when a masked CI/CD variable value coincides with a substring of the corresponding `tokenParamKeys` key name. The secret value is exposed in the job trace/log, readable by anyone with access to view the job's log (which may be broader than access to the masked variable itself).

## Likelihood Explanation
Requires the pipeline to define a masked CI/CD variable (`opts.MaskPhrases`, user-controlled) whose value is exactly a substring of one of the small set of `tokenParamKeys` names (`private_token`, `authenticity_token`, `rss_token`, `x-amz-signature`, `x-amz-credential`, `x-amz-security-token`) [5](#0-4) , and that a real secret value gets printed as `?<key>=<secret>` in the same job log. This is a narrow but entirely attacker(pipeline-author)-controlled precondition — no admin privileges needed, only ability to define a masked variable and print a URL. Reachability is straightforward given `wrap`'s fixed ordering.

## Recommendation
Do not let `masker`'s literal `[MASKED]` insertions interfere with `urlsanitizer`'s key/value state tracking. Options: run `urlsanitizer` before `masker` in the chain (masking sensitive URL params first, so masked-phrase matching operates on the sanitized text), or make `urlsanitizer` resilient to embedded `[MASKED]` markers/interrupted key buffers (e.g., treat `[` as a match-breaking character, or have `masker` and `urlsanitizer` share a single combined pass rather than independent streamed filters).

## Proof of Concept
Go integration test using the real `Logger.wrap` chain (not `urlsanitizer` alone):
```go
func TestMaskerCorruptsURLSanitizerKey(t *testing.T) {
    buf := &fakeTrace{}
    l := buildlogger.New(buf, logrus.NewEntry(logrus.New()), buildlogger.Options{
        MaskPhrases: []string{"ate_tok"}, // substring of "private_token"
    })
    w := l.Stream(buildlogger.StreamWorkLevel, buildlogger.Stdout)
    _, err := w.Write([]byte("?private_token=SECRETVALUE\n"))
    require.NoError(t, err)
    require.NoError(t, w.Close())

    out := buf.String()
    assert.NotContains(t, out, "SECRETVALUE") // FAILS: SECRETVALUE leaks
}
```
Expected (current buggy) result: assertion fails because `SECRETVALUE` appears in `out`, confirming the secret value bypasses `urlsanitizer` masking due to the earlier `masker` stage corrupting the `private_token` key name.
