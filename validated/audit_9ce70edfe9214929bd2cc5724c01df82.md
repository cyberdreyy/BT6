### Title
run-single never assigns a unique `ProjectRunnerID`, causing workspace-path collisions across concurrently-running sibling `run-single` processes for the same project - ([File: commands/single.go])

### Summary
`RunSingleCommand.processBuild` builds every job via `common.NewBuild` but never registers it with `buildsHelper.addBuild`, which is the only code path that increments `Build.ProjectRunnerID` to avoid collisions. Because `ProjectRunnerID` is a zero-valued `int` field that is never set anywhere except in `addBuild`, every `run-single` process always computes `ProjectRunnerID == 0`, so `Build.ProjectUniqueDir`/`ProjectUniqueName`/`ProjectUniqueShortName` are identical across sibling `run-single` processes serving the same runner token/project.

### Finding Description
`RunSingleCommand.processBuild` calls `common.NewBuild(*jobData, &r.RunnerConfig, abortSignal, data, provider)` directly and runs the build with `newBuild.Run(ctx, config, trace)`, with no call to `buildsHelper.addBuild` anywhere in `commands/single.go`. [1](#0-0) [2](#0-1) 

By contrast, the multi-runner path (`multi.go`'s `processBuildOnRunner`) explicitly calls `mr.buildsHelper.addBuild(build)` right after `common.NewBuild`, which is the only place `RunnerID`/`ProjectRunnerID` collision avoidance runs. [3](#0-2) 

`addBuild` scans all currently tracked builds sharing the same runner token and project ID, and bumps `build.ProjectRunnerID` until it finds a free slot: [4](#0-3) 

`ProjectRunnerID` is a plain zero-initialized field on `Build` and is not set by `common.NewBuild` or by any other code path in the repository outside of `addBuild`. [5](#0-4) 

Since `run-single`'s `processBuild` never calls `addBuild`, `ProjectRunnerID` stays `0` for every build the process ever runs. This value feeds directly into the directory/name-uniqueness functions used to build the on-disk checkout/cache paths: [6](#0-5) [7](#0-6) 

Documentation confirms `ProjectRunnerID` (surfaced as `CI_CONCURRENT_PROJECT_ID`) is meant to be "the index of the runner from the list of all runners that run a build for the same project concurrently" and is the mechanism that keeps concurrent jobs for the same project from sharing a build directory when `builds_dir`/`cache_dir` is shared: [8](#0-7) 

If an operator scales out with multiple independent `run-single` processes (a standard horizontal-scaling pattern documented for `run-single` as a "supplementary command to run a single build") pointed at a shared `builds_dir`/`cache_dir` (e.g., a shared volume mount across containers/pods, or `--working-directory` pointing to shared storage), and two of those sibling processes concurrently pick up jobs from the same project, both builds compute the exact same `ProjectUniqueDir(true)`/`ProjectUniqueName()`/`ProjectUniqueShortName()`, because `ProjectRunnerID` is `0` in both. No other existing check (allowed-images checks, overwrite guards, path validation) mitigates this, because those checks operate within a single build's own path, not across builds' path collisions.

An unprivileged pipeline author does not need any special access to trigger the collision: simply running two pipelines on the same project concurrently (which is entirely normal usage, not an attack primitive by itself) is enough to land two jobs on two different `run-single` siblings sharing storage, given the admin's (legitimate, non-privileged) deployment choice to run multiple `run-single` instances against shared storage for scale-out. This is not the same as "shell executor trust on a shared host" or another documented insecure choice — it is a genuine gap where the intended anti-collision mechanism (`addBuild`) simply isn't wired into the `run-single` code path at all.

### Impact Explanation
Two concurrently-running jobs for the same project, executing in sibling `run-single` processes that share `builds_dir`/`cache_dir`, resolve to the identical checkout directory / cache path / project-unique network name (`GetNetworkName` also derives from `ProjectUniqueShortName`). This breaks job workspace isolation: one job's checkout, Git working tree, or cache extraction can be read, overwritten, or raced by the other concurrently-running job on the same project, leading to cross-job checkout/cache/artifact collision and potential data corruption or unintended leakage of files between two pipelines' jobs on the same host/storage.

### Likelihood Explanation
Preconditions: (1) admin runs more than one `run-single` process for the same runner token concurrently against the same shared `builds_dir`/`cache_dir` for horizontal scale-out — a legitimate, documented use of `run-single` distinct from the disallowed "insecure admin choices" (privileged containers, docker.sock, PID namespace sharing); (2) two jobs for the same project are dispatched concurrently to two different sibling processes. Neither precondition requires any privilege beyond running normal CI pipelines concurrently on the same project, which any pipeline author can trigger. The bug is fully deterministic once these preconditions hold, since `ProjectRunnerID` is always `0` in `run-single`.

### Recommendation
Give `run-single` its own collision-avoidance mechanism equivalent to `buildsHelper.addBuild`, either by:
- Wiring `RunSingleCommand` to a shared/global (possibly file-lock or shared-memory backed, since `run-single` instances may be separate OS processes) registry that increments `ProjectRunnerID` per runner token/project, or
- Deriving a stable, externally-unique `ProjectRunnerID` for each `run-single` process (e.g., from a required `--concurrent-id`/env var that the operator must set uniquely per sibling process when sharing storage), and documenting that requirement, or
- Documenting explicitly that multiple `run-single` processes must never share `builds_dir`/`cache_dir` unless each is given a distinct, unique build root (and enforcing/validating this at startup).

### Proof of Concept
Go unit test in `common/build_test.go` style, reproducing the user's proof idea:
```go
func TestRunSingle_ProjectUniqueDir_CollidesWithoutAddBuild(t *testing.T) {
    jobInfo := spec.JobInfo{ProjectID: 42}
    runnerCfg := &RunnerConfig{RunnerCredentials: RunnerCredentials{Token: "same-token"}}

    buildA := &Build{Runner: runnerCfg, Job: spec.Job{JobInfo: jobInfo}}
    buildB := &Build{Runner: runnerCfg, Job: spec.Job{JobInfo: jobInfo}}
    // Neither build is passed through buildsHelper.addBuild, mirroring
    // commands/single.go's processBuild, which never calls addBuild.

    assert.Equal(t, 0, buildA.ProjectRunnerID)
    assert.Equal(t, 0, buildB.ProjectRunnerID)
    assert.Equal(t, buildA.ProjectUniqueDir(true), buildB.ProjectUniqueDir(true))
    assert.Equal(t, buildA.ProjectUniqueName(), buildB.ProjectUniqueName())
    assert.Equal(t, buildA.ProjectUniqueShortName(), buildB.ProjectUniqueShortName()) // differs only by build ID, dir portion still collides
}
```
Expected result: all assertions pass, proving that two `Build`s constructed the way `RunSingleCommand.processBuild` constructs them (via `common.NewBuild`, never through `buildsHelper.addBuild`) compute identical shared-storage paths for the same project/token, confirming the collision.

```go
func (b *buildsHelper) addBuild(build *common.Build) {
	if build == nil {
		return
	}

	b.lock.Lock()
	defer b.lock.Unlock()

	runners := make(map[int]bool)
	projectRunners := make(map[int]bool)

	for _, otherBuild := range b.builds {
		if otherBuild.Runner.Token != build.Runner.Token {
			continue
		}
		runners[otherBuild.RunnerID] = true

		if otherBuild.JobInfo.ProjectID != build.JobInfo.ProjectID {
			continue
		}
		projectRunners[otherBuild.ProjectRunnerID] = true
	}

	for runners[build.RunnerID] {
		build.RunnerID++
	}

	for projectRunners[build.ProjectRunnerID] {
		build.ProjectRunnerID++
	}
```

```go
// ProjectUniqueName returns a unique name for a runner && project. It uses the runner's short description, thus uses a
// truncated token in it's human readable form.
func (b *Build) ProjectUniqueName() string {
	projectUniqueName := fmt.Sprintf(
		"runner-%s-project-%d-concurrent-%d",
		b.Runner.ShortDescription(),
		b.JobInfo.ProjectID,
		b.ProjectRunnerID,
	)

	return dns.MakeRFC1123Compatible(projectUniqueName)
}
```

```go
func (b *Build) ProjectUniqueDir(sharedDir bool) string {
	dir, err := b.ProjectSlug()
	if err != nil {
		dir = fmt.Sprintf("project-%d", b.JobInfo.ProjectID)
	}

	// for shared dirs path is constructed like this:
	// <some-path>/runner-short-id/concurrent-project-id/group-name/project-name/
	// ex.<some-path>/01234567/0/group/repo/
	if sharedDir {
		dir = path.Join(
			b.Runner.ShortDescription(),
			fmt.Sprintf("%d", b.ProjectRunnerID),
			dir,
		)
	}

	if b.GetGitStrategy() == GitEmpty {
		dir += "-empty"
	}

	return dir
}
```
