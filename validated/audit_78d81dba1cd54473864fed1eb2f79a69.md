### Title
A single dust APR=0 withdraw request permanently bricks `stopEpoch` once APR is raised, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog of CVE-2023-22007 (low-privileged action → complete denial of service). In `IdleCreditVault.prepareStopEpochWithApr0`, any non-zero `apr0TotalPrincipal` causes `stopEpoch` to revert unconditionally whenever `unscaledApr != 0`. An unprivileged KYC-passing lender can open a dust-sized withdraw request while the pool APR is 0, and if the (honest) manager later sets a non-zero APR for a subsequent epoch — a normal operational action — every `stopEpoch` call reverts, leaving the pool stuck in `isEpochRunning = true` with all lender funds frozen.

### Finding Description
`requestWithdraw` routes requests to `_requestWithdrawApr0` whenever `unscaledApr == 0`, incrementing the global `apr0TotalPrincipal` (lines 285-286, 567-577). At `stopEpoch`, `IdleCDOEpochVariant` calls `prepareStopEpochWithApr0`, which reverts if the APR0 bucket is open but the current APR is non-zero: [1](#0-0) 

`apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` itself (line 540), i.e. after the reverting check, or per-user via `_clearWithdrawClaimForEpoch` with `_isClearingApr0 = true`, which is only reachable through the post-default claim path (`_claimDefaultedWithdrawRequest`, lines 772-780, 822-831). There is no normal-operation path to drain or cancel the bucket. Consequently, once `unscaledApr != 0` while an APR0 receipt is open:

- `stopEpoch` / `stopEpochWithDuration` always revert → `isEpochRunning` stays `true`, `epochEndDate` passes, deposits stay paused, and no withdraw requests can be opened (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` remain false).
- The pool can only be unstuck by the manager setting APR back to 0 (`setAprs` also writes `unscaledApr`, lines 206-210) or by a borrower default followed by `finalizeDefaultRecovery` plus defaulted-epoch claims that decrement `apr0TotalPrincipal` to 0.

No existing guard prevents this: the attacker only needs tranche tokens (any KYC'd lender) and a 1-wei-scale `requestWithdraw` during an APR=0 epoch. The denial is triggered by honest manager behavior (changing APR), not by any privileged malicious action.

### Impact Explanation
All lender principal and accrued yield in the vault is frozen for the duration of the stuck epoch — potentially permanent if the manager does not realize that restoring `unscaledApr = 0` unbricks the pool, or if the intended new rate was economically required. Even when resolved, it constitutes temporary freezing of the entire TVL (and blocks all withdraw-request claims, which require `epochNumber > lastWithdrawRequest`). Cost to the attacker: one dust deposit + one dust withdraw request.

### Likelihood Explanation
Requires (a) an epoch run at `unscaledApr == 0` (a supported, tested mode — APR0 flows are exercised throughout `test/foundry/IdleCreditVault.t.sol`), (b) the attacker depositing and requesting a withdraw during the buffer, and (c) the manager later raising APR — a routine parameter change. All preconditions are unprivileged or honest-role actions, so likelihood is moderate.

### Recommendation
Handle a stale APR0 bucket gracefully instead of reverting: e.g. in `prepareStopEpochWithApr0`, when `unscaledApr != 0`, settle the open APR0 receipts at principal-only (record `apr0RateByEpoch[epochNumber] = 0` semantics, migrate `apr0TotalPrincipal` into `pendingWithdraws`/settled principal) rather than reverting, or block APR changes in `setAprs`/`setAprsWithBuffer` while `apr0TotalPrincipal != 0` so the incompatible state can never be entered.

### Proof of Concept
Foundry fork PoC (sketch, built on the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testApr0DustRequestBricksStopEpoch() external {
    // Pool running at APR = 0 (unscaledApr == 0)
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    // Attacker: KYC'd lender, dust deposit
    address attacker = makeAddr("attacker");
    deal(defaultUnderlying, attacker, 1e6);
    // ... whitelist attacker via Keyring mock, then:
    vm.prank(attacker);
    idleCDO.depositAA(1e6);

    // Honest flow: run epoch 0, stop it
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

    // Attacker opens a dust withdraw request while unscaledApr == 0
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // -> _requestWithdrawApr0, apr0TotalPrincipal = 1
    assertEq(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 1);

    // Honest manager sets a normal non-zero APR for the next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, _scaleAprWithBuffer(initialProvidedApr));

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());

    // DoS: stopEpoch reverts forever while apr0TotalPrincipal != 0 and unscaledApr != 0
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // Pool is stuck: isEpochRunning stays true, deposits paused, no new requests,
    // existing withdraw receipts can never mature -> all TVL frozen until
    // manager restores unscaledApr == 0 or a full default+finalize cycle clears the bucket.
}
```

Note: this analysis is based on the indexed code paths; the exact helper names in the test harness may differ slightly, but the revert at `IdleCreditVault.sol:506-508` and the absence of a non-default clearing path for `apr0TotalPrincipal` are confirmed by the source.
