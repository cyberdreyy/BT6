### Title
Multisig executes requests using confirmations from removed members - threshold bypass (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the multisig2 contract only purges pending *requests* created by the removed member, but never scans the `confirmations` map to strip that member's confirmation from requests *created by other members*. Because `confirm()` counts entries in the stored `HashSet<String>` without validating that each entry still corresponds to a current member, a request can be executed with fewer live-member confirmations than `num_confirmations` requires, as soon as one stale confirmation from a removed member is present.

### Finding Description
`confirm()` accepts a request once `confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) . The `confirmations` set stores each confirming member's serialized identity (`member.to_string()`), but nothing re-validates set membership against the live `members` collection at confirm-time or at removal-time.

`delete_member` is the only place that prunes stale request/confirmation state when a member leaves, and it only targets requests where that member was the *requester* (`r.member == member`), not requests the member merely *confirmed*: [2](#0-1) 

Because of this, if member `B` had previously confirmed a request `R` created by member `A`, and `B` is later removed via a `DeleteMember` action, `B`'s entry remains inside `confirmations[R]`. `assert_valid_request` and `confirm` never check that stored confirmers are still members - they only verify the *new* caller is a current member via `current_member()` [3](#0-2) [4](#0-3) . The old, now-invalid confirmation still counts toward the threshold comparison.

This breaks the intended equality: `confirmations.len()` (live, authorized approvals) should equal the number of distinct **current** members who approved, but instead it can include confirmations from accounts/keys no longer authorized.

### Impact Explanation
This is a Critical-severity issue per the custody-binding categories in scope: "a multisig request executed below threshold." An attacker scenario:
- Confirmations threshold `num_confirmations = 3`.
- Member `A` creates and self-confirms transfer request `R` (`add_request_and_confirm`) → `confirmations[R] = {A}`.
- Member `B` also confirms `R` → `confirmations[R] = {A, B}` (2 < 3, not yet executed).
- Through a separate legitimate multisig action, `B` is removed (`DeleteMember`). `delete_member` does not touch `confirmations[R]` because `R.member == A`, not `B`.
- Member `C` confirms `R`: `confirmations.len() == 2` (stale `A`,`B`) `+ 1 == 3 >= num_confirmations` → `execute_request` fires (e.g. `Transfer`) with only 2 genuine live-member approvals (`A`, `C`) instead of 3.

Funds move (or a privileged action such as `AddKey`/`DeployContract` executes) with fewer real approvals than the multisig was configured to require, directly undermining the K-of-N custody guarantee.

### Likelihood Explanation
Requires no special privilege beyond being an ordinary multisig member who confirmed a request before being removed - a routine event (key rotation, offboarding a member, compromised key removal). Any subsequent confirmations by remaining members on that pre-existing request silently benefit from the stale approval. No attacker action needs to race governance; the vulnerable state persists until someone happens to `delete_request` that specific request (subject to the `REQUEST_COOLDOWN`), which is not automatic and not obviously indicated to members.

### Recommendation
When removing a member (`delete_member`), iterate all pending `confirmations` entries and strip the removed member's identity from every set (not just requests they authored). Alternatively, validate every entry in a request's confirmation set against current `members` at `confirm()`-time (i.e., recompute effective confirmations as the intersection of stored confirmers and current members) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C, D], 3)`.
2. As `A`: `add_request_and_confirm(R)` → `confirmations[R] = {A}`.
3. As `B`: `confirm(R)` → `confirmations[R] = {A, B}` (2 < 3, no execution).
4. Via a separate already-approved multisig request, execute `DeleteMember { member: B }` → `delete_member` runs; since `R.member == A` (not `B`), the filter in `delete_member` (`multisig2/src/lib.rs:362-366`) does not touch `confirmations[R]`, which still equals `{A, B}` even though `B` is no longer in `members`.
5. As `C`: `confirm(R)` → `confirmations.len() == 2` (`{A, B}`) `+ 1 == 3 >= num_confirmations(3)` → `execute_request(R)` runs the transfer, even though only `A` and `C` are genuinely current, live approvers - one fewer than the configured threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
