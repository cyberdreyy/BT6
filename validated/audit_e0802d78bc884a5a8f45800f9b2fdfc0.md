### Title
Unchecked `account_keys[idx]` indexing in SPL-Token multisig instruction parsing can panic on `jsonParsed` RPC encoding - ([File: transaction-status/src/parse_token.rs])

### Summary
The reported ParaSpace bug is about a signed data structure (`Credit`) that lacks a binding to the context it is meant to be used in (marketplace identifier), letting an attacker's supplied index (`orderId`) be reinterpreted in an unintended context and cause harm. The closest reachable analog in agave, restricted to the allowed unprivileged surfaces (transaction-status parsing used by JSON-RPC `jsonParsed` encoding), is a decoder that trusts attacker-supplied index bytes taken from a transaction's compiled instruction account list and uses them to index directly into the resolved `account_keys` array without a bounds check, which can panic when the index/context assumptions the decoder makes do not hold.

### Finding Description
`parse_signers` in `transaction-status/src/parse_token.rs` builds the "owner"/"multisigOwner"/"signers" JSON fields for SPL-Token instructions by directly indexing `account_keys` with raw `u8` values taken from the instruction's `accounts` list: [1](#0-0) 

Specifically, `account_keys[*i as usize]` (line 948) and `account_keys[accounts[last_nonsigner_index] as usize]` (line 952/958) use direct slice indexing rather than a checked `.get()`. The only validation performed before this call is `check_num_token_accounts`, which delegates to `check_num_accounts`, and only verifies that the *length* of the `accounts` byte-list meets a minimum count for the instruction type — it does not validate that each individual index value is `< account_keys.len()`: [2](#0-1) 

This same unchecked-indexing pattern recurs throughout the `transaction-status` parsers (`parse_instruction.rs`'s `make_ui_partially_decoded_instruction`, `extract_memos.rs`, and multiple `parse_token`/`parse_stake`/`parse_system` helpers), all of which are invoked from JSON-RPC/pubsub code paths that request `encoding=jsonParsed` (`rpc/src/rpc.rs`, `rpc/src/rpc_subscriptions.rs`, `rpc/src/rpc_pubsub.rs`). [3](#0-2) 

Normally, a fully sanitized transaction guarantees that every compiled-instruction account index is `< total account count` (static + resolved address-lookup-table entries) at the time it is executed. The panic surface arises whenever the `account_keys` slice handed to these parsers at decode/encode time (post-execution, for RPC responses) does not match the full resolved key set the original instruction indices assumed — e.g., a mismatch between the length of `account_keys` passed into `parse_token`/`parse_signers` and the actual number of keys used to compile the instruction, since the decoder has no independent way to verify that assumption and blindly trusts the raw index bytes.

### Impact Explanation
If an index exceeds `account_keys.len()`, `account_keys[idx]` panics via a Rust slice out-of-bounds panic. Because this code executes inside the JSON-RPC/pubsub encoding path (`getTransaction`, `getBlock`, transaction/account pubsub notifications with `jsonParsed` encoding), a panic here would crash or abort the RPC-serving thread/task, degrading node service — this matches the accepted impact category "decoder panic and misreporting" from the validation criteria.

### Likelihood Explanation
The likelihood is uncertain and cannot be fully confirmed with the available index. In the common case, transaction sanitization enforces that all account indices referenced by an instruction are valid against the full resolved account-key set before the transaction is admitted to a block, which would make the `account_keys[idx]` accesses safe for indices originating from that same, correctly-resolved key list. The risk is that this repeated pattern of *unchecked* indexing (`[]` instead of `.get()`) across the transaction-status parsing crate provides no defense-in-depth for any code path where the `account_keys` slice supplied to the parser could be shorter than what an instruction's indices assume (e.g., legacy vs. resolved address-lookup-table key sets being mismatched, or partial/failed lookup-table resolution surfacing in a transaction's metadata). I was not able to definitively trace a concrete call path where such a mismatch is actually reachable from an unprivileged JSON-RPC request without further investigation of address-lookup-table failure handling in the encoding pipeline, so this should be treated as a plausible but unconfirmed decoder-robustness gap rather than a fully proven exploit.

### Recommendation
Replace all direct slice-indexing (`account_keys[idx]`) in `transaction-status`'s parsers (`parse_token.rs`, `parse_instruction.rs`, `extract_memos.rs`, `parse_stake.rs`, `parse_system.rs`, etc.) with checked accessors (`account_keys.get(idx)`) that return a `ParseInstructionError`/decode error instead of panicking when an index is out of range. This removes the reliance on external invariants (upstream sanitization) holding at decode time and makes the JSON-RPC encoding layer robust to any input mismatch, consistent with defense-in-depth for a public-facing, unprivileged-reachable subsystem.

### Proof of Concept
Not conclusively demonstrable from the indexed codebase alone. A concrete PoC would require constructing a transaction (or subscription-triggered decode) where the `account_keys` slice passed into `parse_token::parse_signers` (or another parser using unchecked indexing) is shorter than the maximum index value referenced by the instruction's compiled `accounts` byte list, then requesting `jsonParsed` encoding via `getTransaction`/`getBlock`/pubsub to trigger the out-of-bounds panic. Further investigation into address-lookup-table resolution and metadata handling on the RPC encoding path would be needed to confirm reachability from a single unprivileged request; this is called out above as unverified.

fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}

fn make_ui_partially_decoded_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiPartiallyDecodedInstruction {
    UiPartiallyDecodedInstruction {
        program_id: account_keys[instruction.program_id_index as usize].to_string(),
        accounts: instruction
            .accounts
            .iter()
            .map(|&i| account_keys[i as usize].to_string())
            .collect(),
        data: bs58::encode(instruction.data.clone()).into_string(),
        stack_height,
    }
}
