### Title
Instant-withdraw receipts become permanently unclaimable when `allowInstantWithdraw` is disabled after request - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
Analogous to the KPI-token bug where a user who registered redemption intent (burned tokens) could never redeem once a state flag flipped, in `IdleCDOEpochVariant` a user who calls `requestInstantWithdraw` burns their tranche tokens and receives a strategy-token receipt, but the only claim path is gated by the `allowInstantWithdraw` flag. If instant withdrawals are disabled after the request was made, `claimInstantWithdrawRequest()` reverts permanently even though the vault already holds the funded underlying for that receipt.

### Finding Description
The flow:

1. `requestInstantWithdraw` in `contracts/strategies/idle/IdleCreditVault.sol:356-375` burns the CDO's strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, and `pendingInstantWithdraws`. The funds are collected from the borrower/CDO at `startEpoch` via `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`), so the underlying is already sitting in the vault reserved for this receipt.
2. Claiming goes through `IdleCDOEpochVariant.claimInstantWithdrawRequest()` (`IdleCDOEpochVariant.sol:975-979`), which first executes `_checkNotAllowed(!allowInstantWithdraw)` before delegating to `IdleCreditVault.claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`).

The vault-level claim itself does not check the flag — the gate exists only in the CDO wrapper, applied to *claims* rather than only to *new requests*. `setInstantWithdrawParams` can toggle the disabled flag at any time (the test at `IdleCDOEpochQueue.t.sol:1170-1175` shows the honest manager disabling instant withdrawals mid-epoch while a pending request exists).

So the sequence is:

- Epoch running, `allowInstantWithdraw == true`. Attacker/holder calls `requestInstantWithdraw` — tokens burned, receipt minted, funds reserved.
- Manager legitimately calls `setInstantWithdrawParams(delay, minAprDiff, true)` (disable flag), e.g. because market APR conditions changed — a normal honest operation.
- `claimInstantWithdrawRequest()` now reverts with `NotAllowed()` at `IdleCDOEpochVariant.sol:977`. There is no alternative claim path: `claimWithdrawRequest()` only services `withdrawsRequests`/`apr0Users` balances (`IdleCreditVault.sol:301-350`), not `instantWithdrawsRequests`, and the queue path (`IdleCDOEpochQueue.claimWithdrawRequest`) only pays out epochs it processed itself.
- Result: the burned receipt can never be redeemed. If the flag is never re-enabled (or the pool is later closed/defaulted with instant receipts still pending and not serviced by `_claimDefaultedInstantWithdrawRequest` for pre-default funded receipts in some orderings), the freeze is permanent; otherwise it is a temporary freezing of user funds at the manager's discretion.

This mirrors the external bug exactly: the "is expired" check was applied at redemption time instead of only at registration time, so a user who already paid (burned tokens) loses the payout. Here the "instant withdraws allowed" check is applied at claim time instead of only at request time.

### Impact Explanation
Direct fund impact: the user's tranche tokens are already burned and the corresponding underlying is already held by `IdleCreditVault` (`pendingInstantWithdraws` was decremented when funds were collected). The user permanently loses the full requested amount while the tokens remain locked in the vault — no other accounting bucket ever releases them, since `instantWithdrawsRequests[_user]` is only cleared inside `claimInstantWithdrawRequest`, which is unreachable. This is a permanent freezing/theft-class loss of the full `instantWithdrawsRequests` balance per affected user, not a DoS without fund impact (the funds are already escrowed and unrecoverable).

### Likelihood Explanation
Likelihood is moderate: it requires no attacker action beyond making a normal instant-withdraw request. The trigger is a routine honest manager call (`setInstantWithdrawParams` with the disable flag), which is a supported operational control explicitly exercised in tests (`test/foundry/IdleCDOEpochQueue.t.sol:1170-1175` disables instant withdrawals while a normal withdraw request is pending). Any user with a pending instant receipt at that moment is frozen out. Uncertainty: if the manager later re-enables instant withdrawals the claim succeeds, so permanence depends on the flag staying off or the pool defaulting/closing first — I was unable to fully trace whether `_claimDefaultedInstantWithdrawRequest` covers every pre-default funded receipt ordering, so in some default paths the receipt may be partially recoverable.

### Recommendation
Apply the flag check only to *new* instant-withdraw requests, not to claims of already-issued receipts. Either remove `_checkNotAllowed(!allowInstantWithdraw)` from `IdleCDOEpochVariant.claimInstantWithdrawRequest()` (the request side already gates via the delay/APR conditions at request time), or add a separate sweep path that lets holders of `instantWithdrawsRequests` receipts claim their already-funded underlying regardless of the current flag — same fix pattern as the external report's removal of the expiry check in `redeemCollateral()`.

### Proof of Concept
Foundry fork PoC (sketch, using existing test harness conventions from `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantReceiptFrozenAfterDisable() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    // enable instant withdrawals
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    _startEpochAndCheckPrices(0);

    // user requests instant withdraw: tranche tokens burned, receipt minted
    uint256 req = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
    // funds for the receipt are funded at epoch processing
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // honest manager disables instant withdrawals
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, true);

    // burned receipt can never be claimed -> revert NotAllowed
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest();

    // underlying stays stuck in the vault; receipt accounting unchanged
    assertEq(IdleCreditVault(address(strategy)).instantWithdrawsRequests(address(this)), req);
}
```

Relevant code: `IdleCDOEpochVariant.sol:975-979` (flag-gated claim), `IdleCreditVault.sol:356-375` (burn + receipt), `IdleCreditVault.sol:380-393` (ungated vault claim proving the gate is redundant), `IdleCreditVault.sol:398-403` (funds already escrowed).
