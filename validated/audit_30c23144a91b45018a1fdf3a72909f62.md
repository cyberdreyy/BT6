## Finding

### Title
Zero-address protocol/integrator fee recipients in `createDstEscrow` cause fee funds to be permanently burned - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
`BaseEscrowFactory.createDstEscrow` accepts an arbitrary `IBaseEscrow.Immutables` struct from *any* unprivileged caller, including the `parameters` field that encodes `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient` and `integratorFeeRecipient`. Neither the factory nor `EscrowDst._withdraw` validates that the fee-recipient addresses are non-zero. When the encoded fee amount is non-zero but the corresponding recipient address is `address(0)`, the fee is silently sent to and burned at `address(0)`, exactly the bug class described in the referenced Foundation report ("value 0 correctly handled for royalties, but not for the zero address").

### Finding Description
`createDstEscrow` has no access-control modifier and performs no validation of the `dstImmutables.parameters` payload beyond the native-value/token-balance check: [1](#0-0) 

The `parameters` bytes (containing `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, `integratorFeeRecipient`) are entirely caller-supplied and are never cross-checked against the source-chain commitment emitted in `SrcEscrowCreated`/`DstImmutablesComplement`: [2](#0-1) 

At withdrawal time, `EscrowDst._withdraw` reads the fee amounts and recipients straight out of these caller-supplied `parameters` and transfers funds unconditionally once the amount is non-zero, without checking the recipient address: [3](#0-2) 

`_uniTransfer`/`_ethTransfer` in `BaseEscrow` perform no zero-address guard either — a `call{value: amount}("")` to `address(0)` (or an ERC20 `safeTransfer` to `address(0)`) succeeds and the value is burned: [4](#0-3) 

Because the fee amount is subtracted from the amount ultimately paid to the maker (`uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;`), the maker's received amount is unaffected by where the fee goes — only the intended fee recipient (protocol/integrator) loses the value. This is the same root cause as the reported bug: a "recipient == 0 but amount > 0" state is not filtered out before the transfer, resulting in burned value rather than skipped/redirected value.

### Impact Explanation
Any unprivileged caller of `createDstEscrow` can supply `protocolFeeRecipient = address(0)` and/or `integratorFeeRecipient = address(0)` while keeping the fee *amounts* non-zero and all maker-visible terms (maker, amount, token, hashlock, safety deposit, timelocks) consistent with what was committed on the source chain. Off-chain verifiers typically confirm the primary swap terms (amount/token/hashlock/maker) before releasing the secret, but are not guaranteed to re-validate the encoded fee-recipient bytes inside `parameters`. Once the maker's secret is revealed and `withdraw`/`publicWithdraw` is executed, the protocol/integrator fee portion is transferred to `address(0)` and permanently destroyed. This is a permanent, irrecoverable loss of protocol/integrator fee revenue — matching the bounty's Medium/High category of "theft or permanent loss of unclaimed fee-like value."

### Likelihood Explanation
`createDstEscrow` is a public, unauthenticated entry point reachable by any address in the normal swap lifecycle — no whitelisting or owner/governance privilege is required to call it. The only "cost" to the caller is depositing the same total token amount and safety deposit they would deposit for a legitimate swap, making this a low-cost griefing vector against protocol/integrator fee revenue that can be executed on every dst-escrow deployment.

### Recommendation
- Validate in `createDstEscrow` (or in `EscrowDst._withdraw`) that when `protocolFeeAmount > 0`, `protocolFeeRecipient != address(0)`, and likewise for the integrator fee; revert (e.g., a new `InvalidFeeRecipient` error) if this invariant is violated.
- Alternatively/complementarily, cross-check the fee-related fields of `dstImmutables.parameters` supplied to `createDstEscrow` against the fee data committed on the source chain (as emitted in `SrcEscrowCreated`) so a taker cannot unilaterally substitute different fee recipients.
- As a defense-in-depth measure matching the original recommendation, treat `address(0)` as "no recipient configured" and redirect the corresponding amount to the maker instead of burning it.

### Proof of Concept
1. Taker (any address, no whitelist required) prepares `dstImmutables` with `token = dai`, `amount = TAKING_AMOUNT`, correct `maker`/`hashlock`/`timelocks`, but sets `parameters = abi.encode(protocolFeeAmount, integratorFeeAmount, address(0), address(0))` where `protocolFeeAmount`/`integratorFeeAmount` are non-zero and match the amounts expected from the source-chain commitment.
2. Taker calls `escrowFactory.createDstEscrow{value: safetyDeposit}(dstImmutables, srcCancellationTimestamp)` — succeeds since there is no fee-recipient validation, e.g. mirroring the existing test flow at: [5](#0-4) 
3. Off-chain systems (or the maker) verify the swap's core terms and reveal the secret.
4. Anyone calls `dstClone.withdraw(secret, dstImmutables)`. Inside `_withdraw`, since `integratorFeeAmount > 0` and `protocolFeeAmount > 0`, `_uniTransfer(token, address(0), integratorFeeAmount)` and `_uniTransfer(token, address(0), protocolFeeAmount)` execute successfully, permanently burning both fee amounts, while the maker still receives `amount - integratorFeeAmount - protocolFeeAmount` as usual — confirming the fee value is lost with no on-chain revert or safeguard.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

        if (token == address(0)) {
            _ethTransfer(to, amount);

            IERC20(token).safeTransfer(to, amount);
        }
    }
