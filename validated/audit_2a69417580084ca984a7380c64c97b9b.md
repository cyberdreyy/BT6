I have confirmed the vulnerability with full context of `multisig2/src/lib.rs`. This matches the required binding break class ("confirmations counted versus live members") and produces a Critical impact ("a multisig request executed below threshold").

### Title
Stale confirmations from removed multisig members are counted toward the approval threshold, allowing execution below the required live-member quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` only purges requests *created* by the removed member; it never scrubs that member's *confirmations* recorded on requests created by other members. Because `confirm` counts entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set without checking that each entry still corresponds to a current member, a vote cast by an account/key that is later removed from the multisig continues to count toward `num_confirmations` forever, letting a request execute with fewer than `num_confirmations` *live* approvals.

### Finding Description
The equality that must hold is: `confirmations.len()` for a request should equal the number of **live** members who approved it. This binding is broken because membership and confirmation state are not kept consistent.

- `confirm` inserts the caller's identity string into the request's confirmation `HashSet<String>` and later just checks `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide whether to execute: [1](#0-0) 

- `delete_member` (invoked through `DeleteMember` requests) removes the member from `self.members` and deletes any *requests* they authored, but does not iterate other pending requests to strip their prior confirmations from `self.confirmations`: [2](#0-1) 

- `current_member()` (used to authorize `confirm`/`add_request`) is only checked against `self.members` for the *caller* of the current transaction — it is never re-validated against the members who already contributed earlier confirmations stored in the `HashSet<String>`: [3](#0-2) 

As a result, a confirmation recorded while an account/key was a member remains valid data in `confirmations` even after that account/key is deleted from `self.members`, silently diverging the recorded approval count from the actual number of current, authorized approvers.

### Impact Explanation
This is a Critical-impact issue per the rules: "a multisig request executed below threshold." Concretely:

1. Multisig is configured `K` of `N` (e.g. 3 of 4: Alice, Bob, Key1, Key2).
2. Malicious/compromised member `Key1` creates or confirms a sensitive pending request `R` (e.g. a `Transfer` or `FunctionCall`), contributing 1 confirmation, alongside 1 more from another member — total 2/3.
3. Members later detect `Key1` is compromised and confirm a `DeleteMember{member: Key1}` request to remove it. `delete_member` runs but only cleans up requests *authored* by `Key1`; request `R` (authored by someone else) still has `Key1`'s stale confirmation in its `HashSet`.
4. A third legitimate member confirms `R`. `confirmations.len() + 1 >= num_confirmations` evaluates true (2 stale/live + 1 new = 3), so `execute_request` fires the transfer/function call — even though only 2 *current* members ever approved it, one fewer than the configured threshold of 3.

This lets a request bypass the intended `K`-of-`N` approval policy using the vote of an account that is no longer trusted, i.e., moving funds or executing privileged actions (`AddKey`, `FunctionCall`, `Transfer`) with insufficient live authorization — a direct threshold-bypass matching the in-scope "multisig request executed below threshold" impact.

### Likelihood Explanation
The trigger requires no attacker privilege beyond being (or having been) a legitimate multisig member at some point — a realistic and expected lifecycle event (member rotation/key compromise response) rather than an edge case. Any organization using this multisig that rotates keys/members while requests are in flight is exposed; no owner misconfiguration or malicious redeploy is needed, only normal usage of `DeleteMember` while other requests remain pending.

### Recommendation
When executing `DeleteMember`, iterate all `self.requests` (not just those authored by the removed member) and remove the deleted member's entry from each associated `confirmations` `HashSet`, or alternatively re-validate at `confirm`/execution time that every entry in a request's confirmation set is still contained in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members: [Alice, Bob, Key1, Key2], num_confirmations: 3)`.
2. As Bob, `add_request` a `Transfer` request `R` to some `receiver_id` → `request_id = R`.
3. As Key1, call `confirm(R)` → `confirmations[R] = {Key1}` (1/3).
4. As Alice, `add_request_and_confirm` a `DeleteMember{member: Key1}` request, then have Bob and Key2 confirm it to reach 3/3 → `delete_member` executes: `Key1` removed from `self.members`; note it does **not** touch `confirmations[R]`, which still contains `Key1`.
5. As Bob, call `confirm(R)` → `confirmations[R].len() (1) + 1 = 2 >= 3`? Not yet in a 3-of-4 example — but with a 2-of-3 configuration (Alice, Bob, Key1 with `num_confirmations = 2`) removing Key1 down to {Alice, Bob} (still ≥ num_confirmations=2, so deletion succeeds), then Bob's single new confirmation on `R` combined with Key1's stale one (`1 + 1 = 2 >= 2`) triggers `execute_request`, transferring funds despite only Bob (1 live member) actually approving `R` after Key1's removal.     /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
