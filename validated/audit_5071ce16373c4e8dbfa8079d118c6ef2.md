### Title
Permanent `stopEpoch` DoS: an APR0 withdrawal request bricks all future epoch transitions once APR is raised - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0()` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged KYC-passing lender can call `requestWithdraw` while the vault's APR is 0, which increments `apr0TotalPrincipal` via `_requestWithdrawApr0`. `apr0TotalPrincipal` is only cleared at the end of the same function that reverts, so once the manager (honestly) sets a non-zero APR for a subsequent epoch, every `stopEpoch`/`stopEpochWithDuration` call reverts unconditionally — the epoch can never be stopped and all pooled funds are frozen. This mirrors the CVE-2022-21348 bug class: a hang/crash (complete availability loss) induced through a reachable code path.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

```solidity
// prepareStopEpochWithApr0 (~L490-541)
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();            // <-- reverts BEFORE the bucket is cleared
}
...
apr0TotalPrincipal = 0;           // only reached when unscaledApr == 0
```

`apr0TotalPrincipal` is only (a) incremented in `_requestWithdrawApr0` (called from `requestWithdraw` when `unscaledApr == 0`, L285-286, L567-577) and (b) reset to `0` at the end of `prepareStopEpochWithApr0` — which is unreachable once APR is non-zero. There is no other path that decrements it: `_settleApr0` (L545-565) only moves per-user `apr0Users[_user].principal`, and claiming via `_claimFundedWithdrawRequest` deletes `apr0Users[_user]` but never touches `apr0TotalPrincipal`.

Attack sequence (attacker = KYC-passing lender / tranche holder, epoch running with `unscaledApr == 0`):
1. Attacker deposits (e.g. `depositAA`) and calls `IdleCDOEpochVariant.requestWithdraw(amount, AATranche)` → `IdleCreditVault.requestWithdraw` routes to `_requestWithdrawApr0` because `unscaledApr == 0` and the pool is not closed → `apr0TotalPrincipal += amount` (> 0).
2. Epoch ends; manager calls `stopEpoch(0, ...)` (keeps APR 0) — succeeds, `apr0TotalPrincipal` resets. To make the bug deterministic the attacker instead keeps a request open: `_requestWithdrawApr0` supports multiple requests in the same epoch, and after `stopEpoch` resets the bucket the attacker simply requests again during the buffer while APR is still 0.
3. Manager now calls `stopEpoch(newApr > 0, ...)` or `setAprs` raises `unscaledApr` — a normal, honest configuration change.
4. From now on every `stopEpoch`/`stopEpochWithDuration` hits `apr0TotalPrincipal != 0 && unscaledApr != 0` → `revert NotAllowed()`. No existing guard stops this: `requestWithdraw` is permissionless for allowed wallets, `_skimDonatedAssets`/`_updateAccounting` don't help, and the `NotAllowed` revert is by design.

Broken invariant: liveness of the epoch state machine — `stopEpoch` must always be callable; here a user-controlled storage slot makes it permanently revert.

### Impact Explanation
All funds in the CDO are frozen: no `stopEpoch` → `epochNumber` never advances → `claimWithdrawRequest` reverts at the `epochNumber <= lastWithdrawRequest` check (IdleCreditVault L326-328) → deposits and withdrawal claims are bricked; NAV, instant withdrawals, and default handling all stall. The only recovery requires the manager to first set APR back to 0 and run one `stopEpoch` cycle to flush `apr0TotalPrincipal` — during which the attacker can re-request while APR is still 0 in the buffer to repeat the griefing. Loss magnitude: temporary-to-permanent freezing of 100% of vault TVL, at the cost of the attacker's own (re-lockable) request.

### Likelihood Explanation
Requires an APR0-mode vault (used e.g. by programmable/rate-zero deployments), an attacker that passes `isWalletAllowed` (KYC — an accepted unprivileged persona), and a subsequent honest APR increase by the manager. Attack cost is one deposit + one `requestWithdraw` tx; the attacker's funds are recoverable, so the griefing is cheap and repeatable.

### Recommendation
Don't revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Either:
- Settle the APR0 bucket at rate 0 and clear it (move `apr0TotalPrincipal = 0` before the APR check, and forgo the pro-rata interest allocation for that transitional epoch), or
- Decrement `apr0TotalPrincipal` in `_settleApr0`/claim paths so orphaned per-epoch buckets cannot outlive their request lifecycle.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `test/foundry/IdleCreditVault.t.sol::testApr0WithdrawGetsInterestAtStopEpoch`):

```solidity
// setup: standard epoch variant, manager sets APR 0 via setAprs(0,0)
vm.prank(manager);
IdleCreditVault(address(strategy)).setAprs(0, 0);

// attacker: allowed wallet deposits and requests withdraw while APR == 0
uint256 amt = 10_000 * ONE_SCALE;
uint256 minted = _depositWithUser(attacker, amt);
vm.prank(attacker);
cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));
assertGt(strategy.apr0TotalPrincipal(), 0);

// epoch rolls with APR still 0 (bucket cleared) — attacker re-requests in buffer
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());
vm.prank(attacker);
cdoEpoch.requestWithdraw(minted / 4, address(AAtranche));

// manager honestly raises APR for next epoch
_startEpochAndCheckPrices(1);              // calls setAprs internally w/ newApr > 0
vm.warp(cdoEpoch.epochEndDate() + 1);
// borrower funded with exact expected amounts
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);      // apr0TotalPrincipal != 0 && unscaledApr != 0
cdoEpoch.stopEpoch(newApr, 0);

// every subsequent attempt reverts: epoch stuck, claims frozen
vm.prank(attacker);
vm.expectRevert(NotAllowed.selector);      // epochNumber never advanced
cdoEpoch.claimWithdrawRequest();
```
