### Title
Unguarded `initializeConfig` Allows Any Caller to Inject a Malicious `IBridgeConfig` into `BridgeCommittee` — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` is an `external` function with no access control. Its only guard is `require(address(config) == address(0), ...)`, which is always satisfied on the first call. Any unprivileged caller can front-run the deployer's legitimate initialization transaction and permanently install a malicious `IBridgeConfig` contract. Because `config` is consumed by every downstream bridge operation — chain-ID validation, token-address resolution, chain-support checks — the attacker gains the ability to corrupt or permanently freeze the entire EVM bridge.

---

### Finding Description

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  L63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

The function is `external` with no `onlyOwner`, no `initializer`, and no committee-signature check. The sole guard — `address(config) == address(0)` — is always `true` on the first call, exactly mirroring the Note.sol pattern where `_setAccountantAddress` skipped its `msg.sender == admin` check whenever `accountant == address(0)`.

The deployment script calls `initializeConfig` in a **separate transaction** after the proxy is deployed:

```solidity
// bridge/evm/script/deploy_bridge.s.sol  L175-178
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));
BridgeCommittee committeeImplementation =
    BridgeCommittee(Upgrades.getImplementationAddress(bridgeCommittee));
committeeImplementation.initializeConfig(address(bridgeConfig));
```

This two-step deployment creates a front-runnable window. An attacker who observes the pending `initializeConfig` call in the mempool can submit the same call with a malicious `_config` address at a higher gas price, winning the race and permanently locking in the attacker-controlled config.

Once set, `config` cannot be changed through any non-upgrade path. The only recovery route is `upgradeWithSignatures`, but that modifier itself reads `committee.config().chainID()`:

```solidity
// bridge/evm/contracts/utils/MessageVerifier.sol  L46
require(message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID");
```

If the malicious config returns a wrong `chainID`, even the committee-signed upgrade path is broken, making the misconfiguration permanent.

---

### Impact Explanation

`config` is consumed in every critical bridge path:

| Call site | Effect of malicious config |
|---|---|
| `SuiBridge._transferTokensFromVault` (L250) | `tokenAddressOf` returns `address(0)` → all withdrawal claims revert → **permanent fund lock** for all users who bridged from Sui |
| `SuiBridge.onlySupportedChain` modifier (L285) | `isChainSupported` returns `true` for all chains → deposits accepted to unsupported chains → **permanent fund lock** for depositors |
| `MessageVerifier.verifyMessageAndSignatures` (L46) | `chainID()` returns wrong value → all governance/upgrade messages fail chain-ID check → **bridge governance frozen** |
| `SuiBridge.transferBridgedTokensWithSignatures` (L74,79) | Wrong `chainID` / wrong `tokenAddressOf` → token claims silently misdirected or permanently blocked |

The worst-case outcome is a permanently bricked bridge: all locked vault funds become unclaimable, and the committee cannot recover the contract because the upgrade path itself depends on the corrupted `config`.

This matches the HackenProof Critical impact class: **bridge governance or upgrade bypass that enables illegitimate mint or unlock**, and the High/Medium class: **permanent fund lock**.

---

### Likelihood Explanation

- The attack requires only a standard Ethereum transaction — no special role, no stake, no key material.
- The vulnerable window exists between proxy deployment and the `initializeConfig` call, which the deployment script performs as a separate on-chain transaction.
- Ethereum mempool front-running is a well-understood, routinely exploited technique.
- The attacker needs only to observe one pending transaction and submit the same call with higher gas.

---

### Recommendation

Add an `initializer` modifier (OpenZeppelin's `Initializable`) to `initializeConfig`, or fold the config assignment into the existing `initialize` function that already carries the `initializer` guard:

```solidity
// Option A: merge into the existing initializer
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // ← add this
) external initializer {
    // ... existing committee setup ...
    require(_config != address(0), "BridgeCommittee: Invalid config");
    config = IBridgeConfig(_config);
}

// Option B: guard the separate function
function initializeConfig(address _config) external initializer {
    require(_config != address(0), "BridgeCommittee: Invalid config");
    config = IBridgeConfig(_config);
}
```

Either option ensures the function can only be called once and only during the controlled initialization sequence, eliminating the front-running window.

---

### Proof of Concept

1. Deployer broadcasts `BridgeCommittee(proxy).initialize(members, stakes, minStake)` — succeeds, committee is set.
2. Deployer broadcasts `BridgeCommittee(proxy).initializeConfig(legitimateConfigAddr)` — sits in the mempool.
3. Attacker sees the pending transaction, deploys `MaliciousConfig` implementing `IBridgeConfig`:
   - `chainID()` → returns `255` (invalid)
   - `tokenAddressOf(any)` → returns `address(0)`
   - `isChainSupported(any)` → returns `true`
4. Attacker calls `BridgeCommittee(proxy).initializeConfig(address(maliciousConfig))` with higher gas — executes first.
5. Deployer's transaction reverts: `"BridgeCommittee: Config already initialized"`.
6. `SuiBridge.transferBridgedTokensWithSignatures` now calls `committee.config().tokenAddressOf(tokenID)` → `address(0)` → `require(tokenAddress != address(0))` reverts → all bridge withdrawals permanently blocked.
7. `upgradeWithSignatures` calls `committee.config().chainID()` → `255` → chain-ID check fails for all legitimate committee messages → upgrade path is also broken.
8. All funds locked in `BridgeVault` are permanently inaccessible.
