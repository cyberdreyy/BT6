### Title
Reject-then-Accept from a single signer double-counts weight in `total_weight_approved`/`total_weight_rejected`, breaking the aggregated-weight-vs-verified-accepts invariant - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`BlockStatus` in the miner-side StackerDB listener tracks aggregated signer weight for a proposed block via two independent counters, `total_weight_approved` and `total_weight_rejected`, plus a shared `responded_signers: HashSet<u32>`. The guard used to prevent double-counting is asymmetric between the two message-handling branches: the `Rejected` branch gates on `responded_signers.insert(slot_id)`, while the `Accepted` branch gates on `!gathered_signatures.contains_key(&slot_id)`. Because these are two different sets, a signer that first rejects a block and later signs (accepts) the same block hash has its weight added to `total_weight_rejected` and never removed, and then added again to `total_weight_approved` when the acceptance arrives.

### Finding Description
`BlockStatus` (used by `SignerCoordinator`/`StackerDBListener` to decide whether a proposed block has reached the 70% approval or blocking-minority-rejection threshold) is defined with: [1](#0-0) 

On receipt of a `BlockResponse::Rejected` message, the weight is added only the first time a given `slot_id` responds, gated by `responded_signers.insert(slot_id)`: [2](#0-1) 

On receipt of a `BlockResponse::Accepted` message for the *same* block hash, the weight is instead gated on a completely different collection, `gathered_signatures`: [3](#0-2) 

and `responded_signers.insert(slot_id)` is called unconditionally right after (line 465), with no check of the return value and no attempt to reconcile with a prior rejection: [4](#0-3) 

Sequence that triggers the bug for a single signer `S` with weight `w` on block `B`:
1. `S` sends `BlockResponse::Rejected` for `B`. `responded_signers.insert(slot_id_S)` returns `true` (first response) → `total_weight_rejected += w`.
2. `S` later sends `BlockResponse::Accepted` for the same `B` (this is a normal occurrence — a signer can revisit a proposal, e.g. after a stale rejection due to a chainstate-check race, and then sign per the flow documented in `docs/signer-flows.md` section 5/6, where `handle_block_pre_commit`/`handle_block_signature` re-evaluate consistency at signing time). In the `Accepted` branch, `gathered_signatures` does not yet contain `slot_id_S` (this is the *first* accept from `S`), so the `if` branch fires → `total_weight_approved += w`. `responded_signers.insert(slot_id_S)` is a no-op (already present) but its return value is ignored, so there is no code path that decrements `total_weight_rejected`.

Result: `total_weight_rejected` still includes `w` from step 1, and `total_weight_approved` now also includes `w` from step 2. The invariant that a signer's weight can only ever count toward one side of the ledger — i.e., `total_weight_approved + total_weight_rejected` should never exceed `self.total_weight` — is broken. This is the direct analog of the external report's `stakedButUnverifiedNativeETH`: a value is incremented on one action (stake / reject) and never decremented on the corresponding reversing action (unstake / later-accept), so the stale accounting persists and corrupts a downstream equality/threshold check.

### Impact Explanation
`get_block_status` in `signer_coordinator.rs` uses these two aggregated counters to decide the fate of a block proposal, checking the rejection condition *before* the acceptance condition: [5](#0-4) [6](#0-5) 

Because a signer's stale `total_weight_rejected` contribution is never cleared once that signer switches to accept, the miner can observe `total_weight_rejected` crossing the blocking-minority threshold purely due to ghost/stale rejection weight from signers who have since legitimately accepted the block — causing the miner to treat an actually-approved (≥70% weight) block as globally rejected (`NakamotoNodeError::SignersRejected`), discard/exclude transactions, and fail to advance the tenure. This is a liveness wedge on block production driven purely by the aggregated-weight bookkeeping being wrong relative to the verified/live per-signer votes — matching the in-scope class "aggregated-weight vs verified-accepts" equality break. It does not require a majority of signers to be malicious; a single signer switching its own response is sufficient to poison the shared aggregate counters that all decisions for that block hash rely on.

### Likelihood Explanation
This requires only one signer to emit two responses for the same block hash — first a `Rejected`, then later an `Accepted` — which is a realistic and even expected signer behavior path (the signer’s own local state machine re-validates chainstate consistency at multiple points — validate-response time and pre-commit/signing time — and can flip from a rejection decision to a signing decision for the same proposal per the documented flow in `docs/signer-flows.md`, e.g., stale conflicts becoming acceptable, sortition changes, or races settled in the signer's favor). No cryptographic forgery, no majority coordination, and no node-authentication bypass is needed — only the natural message flow already produced by the existing signer implementation.

### Recommendation
Track a single per-signer vote outcome (e.g., `HashMap<u32, BlockResponseKind>`) instead of two independently-gated counters plus a shared `responded_signers` set. When a new response for a `slot_id` arrives that differs from a previously recorded outcome for the same block hash, first subtract the signer's weight from whichever bucket it was previously counted in before adding it to the new bucket, so that `total_weight_approved + total_weight_rejected` can never exceed the sum of weights of signers who have actually responded, and a signer's weight is only ever counted once, in its most current, verified state.

### Proof of Concept
1. Set up a `BlockStatus` for block `B` with a reward set containing signer `S` (weight `w`) among others, `weight_threshold` = 70% of total.
2. Deliver `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` from `S` for `B`. Observe `block.total_weight_rejected == w`, `block.responded_signers == {slot_id_S}`.
3. Deliver `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` from the same `S` for the same `B`. Observe `block.total_weight_approved == w` while `block.total_weight_rejected` remains `w` (unchanged) — i.e. `total_weight_approved + total_weight_rejected == 2w`, exceeding `S`'s actual weight contribution and, at scale, capable of pushing `total_weight_rejected` over `total_weight - weight_threshold` in `get_block_status`'s decision logic even though the real, current vote tally would not warrant rejection.
