### Title
Claimed instant-withdraw receipts are never removed from epoch accounting, corrupting default recovery and stranding/diluting recovery funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug is a termination path that drops an in-flight descriptor instead of queuing it for cleanup (`terminate_all()` never moves the active `vdesc` to `desc_terminated`, so it is never freed). The direct analog lives in `IdleCreditVault`: when an instant-withdraw request is serviced, the aggregate counter is cleared but the per-epoch records (`instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`) are never "freed". A later default finalization then treats those already-paid receipts as still outstanding, inflating the claim basis, diluting `defaultRecoveryPrice`, and leaving part of the recovery reserve permanently stranded.

### Finding Description
`requestInstantWithdraw` records three pieces of state per request: the user aggregate `instantWithdrawsRequests[user]`, the per-epoch entry `instantWithdrawsRequestsByEpoch[user][epochNumber]`, and the epoch total `instantWithdrawClaimsByEpoch[epochNumber]`, plus the global `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375). [1](#0-0) 

The normal claim path `claimInstantWithdrawRequest` burns the receipt, zeroes `instantWithdrawsRequests[_user]`, and pays via `_transferFundedClaim`, but never deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]` (contracts/strategies/idle/IdleCreditVault.sol:380-393). [2](#0-1)  The funding path `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws`, not the per-epoch records (contracts/strategies/idle/IdleCreditVault.sol:398-403). [3](#0-2) 

These stale records matter because default accounting reads them:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` (line 644-649). [4](#0-3) 
- `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `totalBasis` includes that inflated instant basis (line 686-692). [5](#0-4) 
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant`, which also double-counts already-paid receipts as "prefunded reserve" (line 716-723). [6](#0-5) 
- `_claimDefaultedInstantWithdrawRequest` pays out directly from `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`, the mapping the normal claim path failed to clear — it is only saved from double-paying the same user by the `instantWithdrawsRequests[_user] -= claimBasis` underflow (line 844-852). [7](#0-6) 

### Impact Explanation
Consider an epoch in which users A and B each request 100k instant withdrawals. The CDO collects only part of the funds (`collectInstantWithdrawFunds(100k)`), A claims 100k in full while B's 100k remains pending (`pendingInstantWithdraws = 100k`). The borrower then defaults and `finalizeDefaultRecovery` runs in the same epoch. Because `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis` includes `instantWithdrawClaimsByEpoch[epoch] = 200k` — A's already-paid receipt is counted again. `recoveryPrice` is computed against a basis up to 2x the true outstanding claims, so every genuine claimant (B, normal pending withdrawers, and active tranche holders via `activeFinalNAV`) receives roughly half the recovery they are owed, while the surplus reserve is stranded in the strategy as recovery dust that `claimWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` can never attribute to a live receipt. This is a quantified, permanent freezing/misallocation of recovery funds — the same "terminated work item never released" class as the leaked `vdesc`.

### Likelihood Explanation
Triggering requires only ordinary unprivileged actions: an instant-withdraw request (a tranche holder calling `requestInstantWithdraw` on the CDO), a successful instant claim, a partial instant queue (`pendingInstantWithdraws != 0` at finalization, e.g. when `startEpoch` cash covered only part of the queue), and a borrower default finalized by the honest manager. Instant-withdraw mode is a supported vault configuration, and same-epoch claim-then-default sequences are realistic since defaults are declared on missed repayment. No privileged misbehavior, no external oracle manipulation, and no "rejected" surface (legacy tranches, epoch queue contract, wrappers) is required — the bug is entirely in `IdleCreditVault`'s own receipt bookkeeping.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records the same way the defaulted path does: compute the request epoch (it is `epochNumber` at request time — store or derive it, e.g. via a `lastInstantWithdrawRequest[user]` marker or by iterating the single open epoch entry) and set `instantWithdrawsRequestsByEpoch[user][epoch] = 0` and `instantWithdrawClaimsByEpoch[epoch] -= amount` before paying out. Alternatively, have `collectInstantWithdrawFunds`/`startEpoch` reconcile the epoch-level claim total so `instantWithdrawClaimsByEpoch` only ever reflects unclaimed receipts. This mirrors the upstream fix: every terminated in-flight item must be enqueued for cleanup rather than left as a stale accounting entry.

### Proof of Concept
Reproducible on a Foundry mainnet/local fork using the existing `IdleCreditVault`/`IdleCDOEpochVariant` harness (pattern follows `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Enable instant-withdraw mode; users A and B depositAA, epoch runs.
// 2. A and B call cdoEpoch.requestInstantWithdraw(100e6, AAtranche-equivalent).
//    strategy: instantWithdrawClaimsByEpoch[E] == 200e6, pendingInstantWithdraws == 200e6.
// 3. CDO collects only 100e6: collectInstantWithdrawFunds(100e6)
//    -> pendingInstantWithdraws == 100e6; instantWithdrawClaimsByEpoch[E] still 200e6.
// 4. A claims: cdoEpoch.claimInstantWithdrawRequest() for A -> A gets 100e6.
//    OBSERVE BUG: instantWithdrawsRequestsByEpoch[A][E] == 100e6 (not cleared),
//    instantWithdrawClaimsByEpoch[E] == 200e6 (not decremented).
// 5. Borrower fails to repay; manager calls the default path and
//    finalizeDefaultRecovery(recovered, source) in epoch E.
// 6. ASSERT: defaultPendingClaimBasis() == pendingWithdraws + 200e6
//    (double-counts A), so defaultRecoveryPrice is halved.
// 7. ASSERT: B's _claimDefaultedInstantWithdrawRequest pays ~half of entitled
//    recovery, and an equivalent amount of defaultRecoveryReserve can never be
//    claimed by any live receipt (stranded dust).
```

I was unable to read the lines immediately following `claimInstantWithdrawRequest` (the snippet cut at line 393), so if cleanup of the per-epoch mappings occurs below the visible range the finding would not hold; the visible code and the absence of any other writer to `instantWithdrawClaimsByEpoch` besides `requestInstantWithdraw` and `_claimDefaultedInstantWithdrawRequest` strongly indicate it is not cleared.

    _onlyIdleCDO();

      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
