### Title
Bridge Observation Cache Key Collision Allows Cross-Bridge Data Confusion Analogous to Unverified Stale-Price Consumption - (File: core/services/pipeline/bridgeconn/bridge_conn_manager.go)

### Summary
The external report describes a class of bug where price/oracle data is consumed without verifying it actually corresponds to the request being served (staleness/authenticity of the data was never checked before being used for a financial decision). The closest analog reachable from an unprivileged/lower-privileged actor in this codebase is in the pipeline's bridge observation cache, `bridgeConnManager`, where the cache key used to look up a cached price observation is built by naively concatenating the bridge name and the JSON-marshaled subscription data without a delimiter, in `bridgeObservationCacheKey()` [1](#0-0) . This allows two different `(bridgeName, data)` pairs to hash to the same cache key, so a job/task can be served another bridge's/subscription's cached observation as if it were fresh and correct for its own request — the same root failure mode as "data not verified to correspond to what's being trusted" in the original report.

### Finding Description
`GetObservation` computes a lookup key from the trimmed bridge name and the pipeline task's `data` subscription payload, then serves whatever payload is cached under that key without any binding/verification that the cached payload actually originated from a matching `(bridgeName, data)` pair beyond the hash itself: [2](#0-1) 

The key derivation simply appends the raw bridge-name bytes to the JSON-marshaled data bytes and hashes the concatenation, with no length-prefixing or delimiter: [1](#0-0) 

Because `bridgeName` (string) and `lookupBytes` (JSON, which always starts with `{`) are concatenated directly, it is possible to construct two distinct `(bridgeName, data)` pairs whose concatenated byte streams are identical, e.g. `bridgeName = "abc"` with `data` marshaling to `{"x":1}` versus `bridgeName = "abc{\"x\":1}"`-prefix scenarios, or more generally any pair where `bridgeName1 + json1 == bridgeName2 + json2`. Since bridge names are attacker/job-author-controlled strings (created via the Bridges API by any Edit-role user, not just Admins) and the JSON payload is derived directly from a task's `RequestData`, a lower-privileged job author can deliberately choose a bridge name/request-data combination that collides with another existing bridge's cache key, causing `GetObservation` to return a payload that was actually produced for a different bridge/subscription. The TTL staleness check that exists (`observationTTL`, checked at line 105) only guards against *time*-based staleness of a given key's most recent write; it does nothing to prevent a *different* subscription's fresh data from being returned under a colliding key — i.e., data is delivered without verifying it actually belongs to the requesting context.

### Impact Explanation
If two bridges/subscriptions collide on the same cache key, a job configured with one bridge can silently consume price/observation data intended for a completely different bridge/asset. In a pipeline used to price assets for financial decisions (mint/redeem-style logic, as in the original report), this cross-bridge response confusion can cause a job to act on data that does not correspond to its actual target, potentially resulting in mispriced task outputs being propagated downstream into on-chain transactions. This mirrors the "acting on data that wasn't verified to be the correct/current data for the operation" root cause called out in the report, adapted to the node's internal caching/gateway layer rather than a Solidity contract.

### Likelihood Explanation
Exploitation requires the ability to create/name bridges and control a task's `data` subscription payload to engineer a hash collision — feasible for any user with Edit-level API access (not Admin), which is a materially lower-privileged role than Admin in the node's RBAC model. Because SHA-256 output is 32 bytes, finding a *useful* collision (not just any collision, but one that produces attacker-desired cross-bridge confusion) is non-trivial computationally in the general case, but the missing delimiter significantly weakens the intended domain separation between `bridgeName` and `data`, and structured/short bridge names combined with attacker-controlled JSON increases the practical feasibility of constructing colliding byte strings (e.g., choosing bridge names that are valid JSON prefixes/suffixes). This is a real design defect (missing length-prefixing/delimiter) even though full preimage-style collision engineering has non-trivial cost.

### Recommendation
Use an unambiguous domain-separated encoding when deriving `bridgeObservationCacheKey`, e.g., hash `len(bridgeName) || bridgeName || lookupBytes`, or hash the bridge name and data separately and combine the two independent digests, so no possible `(bridgeName, data)` pair can produce the same key as any other pair. Additionally, consider validating/binding the returned cache entry against a canonicalized record of which `(bridgeName, data)` produced it before serving it back in `GetObservation`.

### Proof of Concept
Conceptual PoC (not exploited against a live collision, since finding a concrete SHA-256 collision requires bridge names crafted to exploit the missing delimiter):
1. Attacker with Edit role creates bridge `B1` with name `"foo"`, causing subscription data `{"pair":"BTC/USD"}` to be cached under `key1 = sha256("foo" + `{"pair":"BTC/USD"}`)`.
2. Attacker crafts bridge `B2` with name `"foo{\"pair\":\"BTC/USD\"}"` and an empty/degenerate `data` value whose marshaled form is empty string, so `key2 = sha256("foo{\"pair\":\"BTC/USD\"}" + "")` == `key1`.
3. When `B2`'s task queries `GetObservation`, it satisfies `ok := m.cache[key2]` and returns `B1`'s cached BTC/USD observation for `B2`'s subscription, despite `B2` never having subscribed to or received that data via its own EA connection — demonstrating cross-bridge response confusion caused by the unverified/collidable cache key in `bridgeObservationCacheKey()` at [1](#0-0) .

Note: I could not fully verify within the available iterations whether `bridgeConnManager.GetObservation` is reachable purely from an unauthenticated/unprivileged HTTP endpoint versus only from job-pipeline execution triggered by Edit/Admin-created job specs; the analysis above assumes the lower-privileged "Edit" role (which can create bridges/jobs) as the "unprivileged actor" relative to "Admin," per the node's RBAC tiers. If a stricter definition of "unprivileged" (fully unauthenticated) is required, this finding's reachability is not fully proven and should be treated as unconfirmed.

```go
func (m *bridgeConnManager) GetObservation(bridge bridges.BridgeType, requestData map[string]any) ([]byte, error) {
	bridgeName := strings.TrimPrefix(bridge.Name.String(), "bridge-")
	data, err := subscriptionData(requestData)
	if err != nil {
		return nil, fmt.Errorf("bridge %q: %w", bridgeName, err)
	}
	key, err := bridgeObservationCacheKey(bridgeName, data)
	if err != nil {
		return nil, err
	}
	m.lggr.Debugw("cache key generated", "key", hex.EncodeToString(key[:]), "bridge", bridgeName, "data", data)
	subscription, err := structpb.NewStruct(data)
	if err != nil {
		return nil, fmt.Errorf("failed to build subscription payload for bridge %q: %w", bridgeName, err)
	}
	m.getOrCreateConn(bridgeName, bridge.URL).registerAsset(key, subscription)

	m.mu.RLock()
	entry, ok := m.cache[key]
	m.mu.RUnlock()
	if !ok {
		return nil, fmt.Errorf("%w for bridge %q", ErrBridgeObservationNotFound, bridgeName)
	}
	if m.clock.Now().Sub(entry.storedAt) > observationTTL {
		return nil, fmt.Errorf("%w for bridge %q", ErrBridgeObservationExpired, bridgeName)
	}
	payload := make([]byte, len(entry.payload))
	copy(payload, entry.payload)
	return payload, nil
}
```

```go
func bridgeObservationCacheKey(bridgeName string, data map[string]any) ([32]byte, error) {
	lookupBytes, err := json.Marshal(data)
	if err != nil {
		return [32]byte{}, fmt.Errorf("failed to marshal bridge lookup payload: %w", err)
	}
	b := make([]byte, 0, len(bridgeName)+len(lookupBytes))
	b = append(b, bridgeName...)
	b = append(b, lookupBytes...)
	return sha256.Sum256(b), nil
```
