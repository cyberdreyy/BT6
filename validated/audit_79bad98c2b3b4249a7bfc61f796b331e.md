### Title
Loss-adjusted withdrawal haircut stored under a different epoch index than the one read at claim time — pending receipts can be claimed at par or become unclaimable - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` writes a haircut into `lossRecoveryPriceByEpoch[epochNumber]`, while `_claimLossAdjustedWithdrawRequest` reads the haircut from `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. The write index and the read index come from two different counters (`epochNumber` mutated by `deposit()` during `stopEpoch`, versus the epoch captured at request time), so the haircut is only applied if the two indices happen to coincide — the same class of bug as the LibRaw OOB read: a length/index used at read time is not the index the data was stored under.

### Finding Description
When `stopEpoch` cannot fully fund `pendingWithdraws`, the CDO calls `collectWithdrawFunds`, which records the recovery ratio:

`IdleCreditVault.sol` (lines 411–421):
```solidity
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
if (lossRecoveryPrice == 0) revert NotAllowed();
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

But the claim path resolves the haircut via the user's *request* epoch, not the stop epoch (lines 789–800):

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

`epochNumber` is incremented inside `deposit()` whenever it is called while the epoch is still marked running (lines 607–614). If `stopEpoch` performs the borrower-funding `deposit()` (which bumps `epochNumber`) before `collectWithdrawFunds`, the haircut is stored under `requestEpoch + 1` while every requester's `lastWithdrawRequest` equals `requestEpoch`. The read then hits the wrong slot — a zero — so `_claimLossAdjustedWithdrawRequest` returns 0 and `_claimFundedWithdrawRequest` pays the full par basis from an already-haircutted pool (`epochNumber > lastWithdrawRequest` passes the wait check). The same wrong-index read exists in `requestWithdraw` (lines 261–271), which would fail to detect the pending loss-adjusted receipt and allow new requests.

Conversely, if the keys do match for the intended epoch, any user whose `lastWithdrawRequest` points at a different epoch than the one receiving the haircut (e.g., multiple outstanding epochs aggregated in `pendingWithdraws`) is still paid at par, since the haircut is only looked up under a single index.

### Impact Explanation
Direct fund loss / broken loss-socialization invariant. A haircut applied to `pendingWithdraws` (say 50% recovery) is silently skipped: early claimers burn receipts and withdraw the full claim basis via `_transferFundedClaim`, draining the limited funded amount; later claimers get nothing because `pendingWithdraws` was zeroed but the funded reserve is exhausted. In the worst case this is insolvency for the last claimer equal to `claimBasis * (1 - lossRecoveryPrice)`, and can revert on insufficient strategy balance — permanent freezing of the remaining funded claims.

### Likelihood Explanation
Medium-to-high impact, likelihood gated on `stopEpoch` call ordering: the bug is exploitable by any unprivileged KYC'd tranche holder whenever `stopEpochWithDuration`/`stopEpoch` realizes a loss against non-zero `pendingWithdraws`. I could not fully confirm within this pass whether `IdleCDOEpochVariant.stopEpoch` calls `deposit()` (bumping `epochNumber`) before `collectWithdrawFunds`; the Foundry PoC below resolves that ordering empirically. The `requestWithdraw` guard that re-checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]` shares the same index assumption, so it does not mitigate a mismatch — it is either consistent with the claim path (both wrong) or inconsistent with the write path (both wrong).

### Recommendation
Key the haircut by the request epoch it applies to rather than the mutable `epochNumber` at collect time — e.g., store `lossRecoveryPriceByEpoch[pendingEpoch]` where `pendingEpoch` is captured before the stop-epoch `deposit()` bump, or store the haircut under a dedicated `lastLossEpoch` variable that claims read directly instead of deriving the index from `lastWithdrawRequest`. Alternatively, record the request epoch inside each receipt and iterate/lookup by explicit epoch parameter passed by the CDO.

### Proof of Concept
Foundry fork test (place in `test/foundry/`, reuse harness from `IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptReadAtWrongEpochIndex() external {
    // setup: deposit AA/BB, startEpoch, user requests withdraw -> lastWithdrawRequest = N
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 minted = idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);
    uint256 requested = cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));
    uint256 reqEpoch = strategy.lastWithdrawRequest(address(this));

    // stopEpoch with loss: borrower funds only half of pendingWithdraws
    uint256 pending = strategy.pendingWithdraws();
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(_lossAmount, _duration); // path that underfunds receipts

    // WRITE index check:
    uint256 storedAtStopEpoch  = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber());
    uint256 storedAtReqEpoch   = strategy.lossRecoveryPriceByEpoch(reqEpoch);
    emit log_named_uint("price@epochNumber", storedAtStopEpoch);
    emit log_named_uint("price@reqEpoch", storedAtReqEpoch);

    // If price@reqEpoch == 0 while price@epochNumber != 0, the claim pays par:
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;
    // Bug: paid == requested (par) instead of requested * lossRecoveryPrice / 1e18
    assertEq(paid, requested, "loss haircut bypassed via wrong-index read");
}
```

Run: `forge test --match-test testLossAdjustedReceiptReadAtWrongEpochIndex -vvv --fork-url $RPC`. The assertion documents both directions: a mismatch in the two `lossRecoveryPriceByEpoch` lookups proves the wrong-index write/read; the par payout proves the fund-loss impact.
