### Title
Donated strategy-token receipts to the IdleCDO inflate close-pool recall and default-recovery basis, forcing wrongful default / diluted claims - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCreditVault` mints unrestricted ERC20 "receipt" strategy tokens directly to users in `requestWithdraw` (`_mint(_user, _amount)`). Because `IdleCDOEpochVariant` and `IdleCreditVault.finalizeDefaultRecovery` measure pool value and recovery basis with the raw `balanceOf(idleCDO)` / `_contractTokenBalance(strategyToken)`, an unprivileged receipt holder can `transfer` their receipt tokens to the CDO. This (a) inflates the borrower recall amount in close-pool `stopEpoch(0, 1)`, forcing a wrongful borrower default that freezes the whole pool, and (b) inflates `totalBasis` in `finalizeDefaultRecovery`, permanently diluting `defaultRecoveryPrice` for every legitimate pending claimant and stranding reserve in the strategy.

### Finding Description
- `IdleCreditVault.requestWithdraw` mints the user's receipt as plain strategy tokens (`_mint(_user, _amount)`), which are freely transferable ERC20 — there is no `_transfer` hook or whitelist restricting them.
- In `IdleCDOEpochVariant._stopEpoch`, the close-pool branch (`_interest == 1`) computes the recall as `_totBorrowed += _contractTokenBalance(strategyToken)` and then demands `_amountToPullFromBorrower + _pendingWithdraws` from the borrower via `getFundsFromBorrower` inside a try/catch. Donated receipts sitting on the CDO inflate that demand by exactly the donated amount.
- If the honest borrower does not hold/approve the extra (inflated) amount, the pull reverts and `_handleBorrowerDefault` fires: `defaulted = true`, `paused`, withdraw requests disabled — i.e., a full-pool freeze triggered by an unprivileged transfer.
- Even without a forced default, after any real default `IdleCreditVault.finalizeDefaultRecovery` computes `activeBalance = balanceOf(idleCDO)` and `totalBasis = activeBasis + pendingBasis`; `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`. Donated receipts raise `totalBasis` with zero added reserve, so `defaultRecoveryPrice` drops below the fair ratio and all `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` / post-default tranche claims are underpaid, with the unallocated remainder stuck in `defaultRecoveryReserve`.
- `_skimDonatedAssets` only skims the underlying `token` balance of the CDO (`_transferUnderlyings(feeReceiver, _contractTokenBalance(token))`); it does not isolate donated `strategyToken` balances, so the guard does not stop this.

### Impact Explanation
Two quantified losses, both reachable in named phases:
- Temporary freezing of all user funds (buffer/stopped → defaulted): an attacker holding any pending receipt can force `stopEpoch(0,1)` into the `catch` branch during pool closure, flipping `defaulted`, pausing deposits and disabling `allowAAWithdrawRequest`/`allowBBWithdrawRequest` until governance runs `finalizeDefault`. This is the direct analog of the CVE's "hang/crash" availability impact, but with fund impact since every LP's liquidity is frozen behind an honest-borrower "default".
- Permanent theft/dilution of recovery (defaulted/finalized): donating `D` receipt tokens lowers `defaultRecoveryPrice` by a factor `totalBasis / (totalBasis + D)`; legitimate claimants lose that fraction of their recovery payout permanently, and the surplus reserve remains locked in the strategy.

### Likelihood Explanation
- Attacker cost is the face value of one withdraw receipt; receipts are obtained by any KYC-passed lender calling `requestWithdraw`, and once APR drops the instant path mints them too. No privileged action is required.
- The only mitigation is that the attacker destroys their own claim value, so this is griefing/dilution rather than profitable extraction by itself — though combined with a post-default claim (`postDefaultRequests`) on an inflated basis the accounting can also be skewed in the attacker's favor when `balanceOf(idleCDO)` is double-counted against `pendingBasis`.

### Recommendation
- Make receipt strategy tokens non-transferable (override `_transfer`/`_beforeTokenTransfer` in `IdleCreditVault` to only allow mint/burn and transfers initiated by `idleCDO`), or
- Track the CDO's entitled principal in internal accounting rather than raw `balanceOf`/`_contractTokenBalance(strategyToken)`, and add a `_skimDonatedStrategyTokens` step in `stopEpoch`, `startEpoch`, and `finalizeDefaultRecovery` that excludes unsolicited strategy-token balances from `_totBorrowed`/`activeBasis`.

### Proof of Concept
```solidity
// Foundry, fork context of test/foundry/IdleCreditVault.t.sol
// Setup: pool running, borrower honest, minted-APR or fixed-APR mode irrelevant.
uint256 amount = 10_000 * ONE_SCALE;
idleCDO.depositAA(amount);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

// Attacker (ordinary lender) requests a withdraw -> receives receipt strategy tokens
uint256 requested = cdoEpoch.requestWithdraw(ONE_TRANCHE, address(AAtranche));
uint256 receipts = IERC20Detailed(address(strategy)).balanceOf(address(this));
assertGt(receipts, 0);

// Attacker donates receipt tokens to the CDO
IERC20Detailed(address(strategy)).transfer(address(cdoEpoch), receipts);

// Next epoch runs; manager tries to close pool with stopEpoch(0, 1)
_startEpochAndCheckPrices(1);
vm.warp(cdoEpoch.epochEndDate() + 1);

// Borrower only owes principal + interest, not principal + interest + donated receipts.
// The inflated transferFrom reverts -> forced default.
vm.prank(manager);
cdoEpoch.stopEpoch(0, 1);
assertEq(cdoEpoch.defaulted(), true);   // wrongful default: pool frozen
assertTrue(cdoEpoch.paused());

// After a real default, donation also dilutes recovery:
// finalizeDefaultRecovery uses balanceOf(idleCDO) -> totalBasis grows, reserve fixed
// => defaultRecoveryPrice < fair ratio, every claimant underpaid.
```
