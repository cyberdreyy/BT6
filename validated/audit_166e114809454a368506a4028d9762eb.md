### Title
Cross-tenure sibling conflicts stop blocking a second signature once the fixed `tenure_last_block_proposal_timeout` (default 30s) elapses, even if the first block was never globally accepted — ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit`'s conflict guard is the only backstop against a signer placing signatures on two sibling blocks at the same Stacks height in different tenures. That guard is gated on a fixed local timestamp comparison (`last_endorsed > freshness_cutoff`, `freshness_cutoff = now - tenure_last_block_proposal_timeout`, default 30s). Once a conflicting signature ages past that fixed window, the code treats the conflict as fully resolved unless it happens to live in the *same* tenure as the new proposal — even though the underlying reason a stale, only-locally-accepted conflict is supposed to keep blocking (per the code's own doc comments) is precisely to prevent an equivocation. This is the same bug class as "a 1‑day stale-price window is too long to safely treat data as fresh": a fixed, short, local timer is used as a stand-in for "the conflict is resolved," when in fact resolution (global acceptance/propagation) can legitimately take longer than the window under normal network conditions.

### Finding Description
In `Signer::handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs`): [1](#0-0) 

```
let conflicts = ... self.signer_db.get_signed_conflicts(chain_length, &block_hash) ...
let freshness_cutoff = get_epoch_time_secs().saturating_sub(tenure_last_block_proposal_timeout.as_secs());
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(...)

    return;

```

`get_signed_conflicts` deliberately returns *every* signed block (ours or the observed group's) at or above the proposed height, in **any** tenure, because "two blocks at the same height are siblings no matter which tenure they belong to." [2](#0-1) 

But the freshness check that decides whether such a cross-tenure conflict still blocks is a pure wall-clock comparison against `tenure_last_block_proposal_timeout` (default **30 seconds**, per `sample/conf/signer/mainnet-signer-conf.toml`). [3](#0-2)  Once `last_endorsed <= freshness_cutoff`, the conflict is dropped from the "fresh" `find` entirely — `conflict_still_blocks` (the function that actually asks the node whether the older block could still land in the chain, including the explicit "sibling at this height still blocks" rule) is **never invoked** for it: [4](#0-3) 

The code then only re-checks conflicts whose `consensus_hash` equals the **new proposal's own tenure**: [5](#0-4) 

A stale conflict that lives in a **different (third) tenure** — e.g., an earlier sibling that was only `LocallyAccepted` and never reached the node — is matched by neither branch: it is too old to be caught by the "fresh" `find`, and its `consensus_hash` does not match the new block's tenure, so the own-tenure tip check never inspects it either. The code's own comment even claims this gap is "settled by the chainstate checks above" [6](#0-5) , but `check_block_against_signer_db_state` (the "chainstate checks above") is explicitly documented to look at only **one** tenure — the block's own, or its parent for a tenure-change block — and a signed sibling in a *third* tenure is invisible to it: [7](#0-6) 

The design intent, per `conflict_still_blocks`'s own doc comment, is that "a sibling at the same height keeps blocking (signing both would be the double-sign this guard is for)" specifically when the older block was never globally accepted, because the signer cannot distinguish "not yet propagated" from "dead." [8](#0-7)  That protection is exactly what the fixed 30‑second freshness cutoff discards for cross‑tenure conflicts once it elapses — regardless of whether the older block has actually been resolved (globally accepted or provably dead).

### Impact Explanation
This is a break of the "conflicting-signature" equality/guard: the signer can end up producing signatures over two different blocks (siblings) at the same Stacks height in two different tenures — an equivocation — solely because more than `tenure_last_block_proposal_timeout` (30s by default) elapsed between the two pre-commit thresholds being reached, which is a completely ordinary occurrence under normal network delay, StackerDB propagation lag, or a slow-to-converge node (the node not yet reflecting the first, locally-accepted-only block). This matches the Critical impact class: "a signer signing an invalid, non-canonical, or conflicting block." It requires no majority of signers and no key compromise — only ordinary timing between two legitimate tenures' proposals reaching the normal 70% pre-commit threshold on this one signer.

### Likelihood Explanation
The trigger conditions are all reachable through normal protocol operation by a single miner/tenure sequence plus gossip, without needing a majority of colluding signers:
1. Tenure 1's block B1 at height H reaches pre-commit threshold and is signed by this signer, but never reaches global acceptance on the node (e.g., it's still `LocallyAccepted` because the aggregate signature hasn't been submitted/observed by the node yet, or the miner failed to push it).
2. More than `tenure_last_block_proposal_timeout` (30s default) elapses — plausible under normal signer/node latency, especially with `stackerdb_timeout`/`block_proposal_validation_timeout_ms` defaults of 120s that already assume round trips can take minutes.
3. A new tenure 2 proposes a sibling block B2 at the same height H (e.g., a normal reorg/re-mine scenario after tenure 1 stalled), which the signer validates and pre-commits.
4. When B2 reaches pre-commit threshold, `get_signed_conflicts` finds B1's stale signature, `conflict_still_blocks` is never consulted for it, and the own-tenure check does not apply (different tenure) — so the signer signs B2 as well.

The severity is high, but likelihood is moderate: it depends on the first block staying `LocallyAccepted` (not yet globally accepted) for more than the freshness window while a legitimate sibling from another tenure independently reaches pre-commit — a timing window that is entirely plausible given how short the default `tenure_last_block_proposal_timeout` (30s) is relative to other signer timeouts (120s validation, 120s StackerDB), but not certain to occur on every fork/stall.

### Recommendation
For cross-tenure conflicts, do not let the fixed local freshness timer alone silence the guard when the underlying resolution state (`conflict_still_blocks`'s node-derived questions) has not actually been checked. At minimum:
- Always invoke `conflict_still_blocks` for conflicts in tenures other than the proposal's own tenure, regardless of `last_endorsed` freshness, since that function already correctly distinguishes "dead" (globally accepted then reorged, or burn-chain orphaned) from "possibly still live" (only locally accepted, same height).
- Reserve the pure freshness-timeout shortcut only for the own-tenure case, where a stale conflict is already re-verified against the node's canonical tenure tip.
- Consider making `tenure_last_block_proposal_timeout` bound to actual global-acceptance confirmation (or a substantially longer default) rather than a short, fixed wall-clock window, so that "stale" reliably implies "resolved" rather than merely "old."

### Proof of Concept

1. `stacks-signer/src/v0/tests.rs::stale_sibling_replaced_when_canonical_tip_below` already demonstrates that with `Duration::ZERO` freshness timeout, a signer signs a replacement block B once conflict A's signature is "stale," specifically for the **own-tenure** case where the node's tip is checked. 2. No analogous test exists (in the excerpts reviewed) covering a **stale, only-locally-accepted, cross-tenure** sibling — exactly the gap identified above, where `conflicts.iter().any(|conflict| conflict.consensus_hash == block_info.block.header.consensus_hash ...)` at [10](#0-9)  silently skips conflicts from a different tenure, letting the signer fall through to `mark_locally_accepted` and sign.
