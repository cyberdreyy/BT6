### Title
Stale per-epoch instant-withdraw receipt is never cleared on a funded claim, enabling a second payout from the default-recovery reserve after borrower default - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]`. If the borrower later defaults in that same epoch and default recovery is finalized, `_claimDefaultedInstantWithdrawRequest` resurrects the already-paid receipt (the "freed" object) and pays it again from the recovery reserve — a direct analog of CVE-2018-11358's use-after-free caused by skipped cleanup.

### Finding Description
In `claimInstantWithdrawRequest` (lines 380-392), the non-default claim path does:

```
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It does not touch `instantWithdrawsRequestsByEpoch[_user][epochNumber]` or `instantWithdrawClaimsByEpoch[epochNumber]`, which `requestInstantWithdraw` populated at lines 371-372.

Later, when the borrower defaults and `finalizeDefaultRecovery` sets `defaultRecoveryEpoch` to the epoch where the stale receipt still lives, `_claimDefaultedInstantWithdrawRequest` (lines 842-856) reads:

```
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
instantWithdrawsRequests[_user] -= claimBasis;
pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
_burn(_user, claimBasis);
_transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

Attack sequence (attacker is an ordinary KYC'd lender):

1. **Running epoch E:** attacker calls `requestInstantWithdraw` for X underlying → `instantWithdrawsRequestsByEpoch[attacker][E] = X`, aggregate = X, receipt tokens minted.
2. Epoch E ends normally; attacker calls `claimInstantWithdrawRequest` → paid X at par, aggregate zeroed, but `instantWithdrawsRequestsByEpoch[attacker][E]` stays X (skipped cleanup).
3. Borrower defaults in epoch E's accounting; `finalizeDefault`/`finalizeDefaultRecovery` records `defaultRecoveryEpoch = E` and seeds the recovery reserve.
4. Attacker calls `requestInstantWithdraw` again for any amount ≥ X (this function has no `defaultRecoveryFinalized` guard — unlike `requestWithdraw`, which explicitly reverts if prior receipts exist). New aggregate ≥ X, new receipt tokens minted.
5. `claimInstantWithdrawRequest` → `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` → `_claimDefaultedInstantWithdrawRequest` revives the stale basis X, burns X of the *new* receipt tokens, and pays `X * defaultRecoveryPrice` from the reserve. The normal path then pays the remaining new-request aggregate as well.

### Impact Explanation
The attacker receives a second payment for a receipt that was already fully funded and claimed — direct theft of `X * defaultRecoveryPrice` underlying from the default-recovery reserve, which is shared pro rata by all defaulted-epoch claimants. Every other lender's haircut is effectively deepened; with a large first receipt the attacker can drain reserve funds earmarked for honest claimants. Even without step 4, the subtraction `instantWithdrawsRequests[_user] -= claimBasis` underflows on a zeroed aggregate, permanently reverting the user's entire `claimInstantWithdrawRequest` and freezing any legitimately funded newer instant receipts.

### Likelihood Explanation
Requires only: an instant-withdraw request that is funded and claimed, a subsequent borrower default whose `defaultRecoveryEpoch` equals the epoch the stale receipt was recorded in, and one new instant request to satisfy the burn/aggregate bookkeeping. All steps use unprivileged user functions; the epoch alignment is natural whenever the default happens in the same epoch the original request was made (the common case, since instant receipts accumulate in the current epoch). No privileged misbehavior is needed.

### Recommendation
In `claimInstantWithdrawRequest` (and `collectInstantWithdrawFunds` funding path), clear `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and decrement `instantWithdrawClaimsByEpoch[requestEpoch]` — mirroring what `_clearWithdrawClaimForEpoch` does for normal withdrawals — so a funded receipt is fully destroyed rather than left for the default-recovery path to re-read. Alternatively, iterate and zero all per-epoch entries contributing to the claimed aggregate.

### Proof of Concept
```solidity
// Foundry fork PoC against contracts/strategies/idle/IdleCreditVault.sol
function testStaleInstantReceiptDoubleClaim() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);            // in epoch 1

    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address attacker = makeAddr('attacker');
    uint256 tranches = _depositWithUser(attacker, 100e6);
    vm.prank(attacker);
    AAtranche.approve(address(cdoEpoch), tranches);

    vm.prank(manager);
    cdoEpoch.startEpoch();                      // epoch 1 running
    skip(101);

    // 1) instant withdraw request X in epoch E = strategy.epochNumber()
    uint256 epochE = strategy.epochNumber();
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tranches / 2, address(AAtranche));
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epochE), tranches / 2);

    // borrower funds instant liquidity; attacker claims -> aggregate cleared, ByEpoch stale
    // (fund via manager/borrower as in testClaimInstantWithdrawRequest)
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker), balPre);
    assertEq(strategy.instantWithdrawsRequests(attacker), 0);
    // BUG: per-epoch receipt still alive
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epochE), tranches / 2);

    // 2) borrower defaults in epoch E; recovery finalized
    // ... _handleBorrowerDefault -> finalizeDefaultRecovery(defaultRecoveryEpoch == epochE)

    // 3) attacker opens a new instant request to satisfy burn/aggregate bookkeeping
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tranches / 2, address(AAtranche));

    // 4) stale receipt is resurrected and paid again from the recovery reserve
    uint256 reservePre = underlying.balanceOf(address(strategy));
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // paid X * defaultRecoveryPrice for the stale receipt + the new request
    assertGt(reservePre - underlying.balanceOf(address(strategy)), 0);
}
```
