### Title
Pending withdraw receipts ignore tranche seniority and socialize realized losses pro rata, breaking the BB-first loss waterfall - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`stopEpochWithDuration` realizes a loss by splitting it between (a) pending withdraw receipts and (b) active tranche positions. Because `pendingWithdraws` is a single aggregate bucket that does not record whether each receipt came from an AA or BB tranche, `previewLossAdjustedWithdrawFunds` assigns the pending bucket a strictly pro-rata share of the total loss (`_lossAmount * pendingBasis / totalBasis`). The active remainder is then applied BB-first via `_forceUpdateAccounting`. The result is that AA holders who happened to request a withdrawal in the loss epoch are haircut even when the BB tranche alone could have absorbed the entire loss, while BB holders who requested a withdrawal escape the junior-first waterfall with only a blended haircut. Losses are therefore distributed by request timing, not by tranche seniority.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the manager-supplied `_lossAmount` is routed through `IdleCreditVault.previewLossAdjustedWithdrawFunds`, which computes `pendingLoss = _lossAmount * pendingBasis / totalBasis` and reduces `pendingToFund` accordingly [1](#0-0) . The reduced amount is pulled from the borrower and `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis`, so every receipt of that epoch — AA or BB — claims at the same haircut [2](#0-1) . The code itself documents the limitation: "pending receipts share the pending portion of the loss pro rata because tranche identity is not stored" [3](#0-2) .

This contradicts the vault's own loss-ordering invariant. Active positions apply losses strictly BB-first: `_updateAccounting` only touches `lastNAVAA` after `_totalBBGain` exhausts `lastNAVBB` [4](#0-3) . But a pending receipt minted from an AA tranche is haircut by `pendingLoss` even when `activeLoss < lastNAVBB` (i.e., BB fully covers the active-side loss and active AA holders lose nothing). Conversely, a pending receipt minted from a BB tranche is haircut only by the blended `pendingLoss`, which can be far smaller than the junior share it would bear had it stayed active — letting fast BB holders partially dodge junior losses by requesting withdrawal in the epoch where the loss is realized, concentrating the loss onto remaining active BB holders.

Concretely: NAV AA=90, BB=10, `pendingWithdraws`=10 (all from AA requests), realized `_lossAmount`=5. `pendingLoss = 5*10/110 ≈ 0.45` haircut hits the AA pending receipts even though BB NAV (10) covers the full loss — active AA holders lose 0 while pending AA claimants lose ~4.5% of their receipt. If instead the pending receipts were BB requests, they would absorb only ~0.45 of a 5 loss while the remaining active BB absorbs ~4.55 — an improvement over the ~5 they would bear under the waterfall.

### Impact Explanation
Violates the loss-waterfall invariant: AA claimants suffer losses while junior capital is still intact, and junior claimants can reduce their loss share below the waterfall allocation by timing `requestWithdraw` before a stop that realizes a loss. The misallocation is proportional to `pendingBasis / totalBasis` and is bounded by the realized loss, but within a single epoch it can transfer value between same-seniority users purely based on request timing — the exact "losses are not distributed equally" class.

### Likelihood Explanation
The trigger is any `stopEpochWithDuration`/`_stopEpoch` call with `_lossAmount != 0` while `pendingWithdraws != 0`. This occurs whenever a borrower repays less than owed (credit impairment short of a full default) during an epoch where users requested withdrawals — a routine scenario for a credit vault. No privileged misbehavior is required: the manager passes the realized loss honestly, and the misallocation happens deterministically.

### Recommendation
Record tranche identity (or at least the AA/BB split) for pending receipts at request time — e.g., `pendingWithdrawsAA`/`pendingWithdrawsBB` per epoch — and apply `activeLoss` ordering to the pending bucket: haircut BB-denominated pending receipts first, and only haircut AA pending receipts for loss exceeding total BB basis (active `lastNAVBB` + pending BB). Alternatively, on loss epochs, settle pending receipts through the same post-loss tranche price used for active positions by re-minting them as tranche claims rather than fixed underlyings receipts.

```solidity
function testPendingAABearsLossWhileBBCovers() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address pendingAA = makeAddr('pendingAA');
    address activeAA  = makeAddr('activeAA');

    // AA=90k, BB=10k; pendingAA and activeAA each hold 10k AA
    _depositWithUser(pendingAA, amount, true);
    _depositWithUser(activeAA, amount, true);
    idleCDO.depositAA(70_000 * ONE_SCALE);
    idleCDO.depositBB(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);

    // pendingAA requests a normal withdraw during the running epoch
    vm.prank(pendingAA);
    uint256 receiptBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // borrower repays with a 5k shortfall -> manager realizes the loss honestly
    uint256 lossAmount = 5_000 * ONE_SCALE; // < lastNAVBB (10k)
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), lossAmount);

    // pendingAA is haircut pro rata even though BB fully covers the loss
    uint256 balPre = underlying.balanceOf(pendingAA);
    vm.prank(pendingAA);
    cdoEpoch.claimWithdrawRequest();
    uint256 payout = underlying.balanceOf(pendingAA) - balPre;
    assertLt(payout, receiptBasis);        // pending AA lost money
    assertGt(cdoEpoch.lastNAVBB(), 0);     // while BB NAV remains intact
    // activeAA suffers no loss at all
    assertApproxEqAbs(
        cdoEpoch.virtualPrice(address(AAtranche)),
        ONE_TRANCHE, // (scaled to price decimals)
        1e15
    );
}
```

The assertion `payout < receiptBasis` together with `lastNAVBB > 0` demonstrates that AA pending receipts absorbed a loss that, under the vault's own BB-first waterfall, should have been borne entirely by junior capital.

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }
