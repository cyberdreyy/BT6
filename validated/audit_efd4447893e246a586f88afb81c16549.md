### Title
Unverified `email` ID-token claim is trusted as durable account identity in OIDC session/token binding - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`handleTokenExchange` extracts the `email` claim from a verified-signature ID token but never checks the companion `email_verified` claim before using it as the permanent account identifier stored in `oidc_sessions.user_email` and, transitively, `oidc_user_api_tokens.user_email`. Any identity provider that returns an unverified/self-asserted `email` claim (self-service realms, generic OIDC bridges, federated IdPs that copy an untrusted attribute into `email`) lets a user who can authenticate at the IdP bind a Chainlink session or API token record to an arbitrary email string, including one matching a real operator's identity.

### Finding Description
In `handleTokenExchange` (`core/sessions/oidcauth/oidc.go:163-276`), after the ID token signature is verified with `oi.provider.Verifier(oi.oidcConfig).Verify(ctx, rawIDToken)` [1](#0-0)  the code reads the claim map and pulls `email` directly with no `email_verified` check: [2](#0-1) 

That raw email is then written as the durable identity for the new session: [3](#0-2) 

`AuthorizedUserWithSession` later resolves every subsequent authenticated request purely from this table row (`user_email`/`user_role`), with no cross-check against verified identity data: [4](#0-3) 

Because the RBAC role is derived independently from the configured group claim (`IDClaimsToUserRole`, `core/sessions/oidcauth/oidc.go:599-618`), the attacker cannot elevate their *role* above what their own IdP group membership legitimately grants — the signature-verified group claim gates privilege, not the email. However, the `Email` field returned by `AuthorizedUserWithSession`/`FindUser`/`GetAuthenticatedUser` is propagated as the user's identity throughout the rest of the app (audit logs, `UpdateRole`/`Delete` self-action guards in `core/web/user_controller.go:122-131,177-186`, `ClearNonCurrentSessions` in `core/sessions/oidcauth/oidc.go:441-449`, and `oidc_user_api_tokens` bound to `user.Email` in `SetAuthToken`, `core/sessions/oidcauth/oidc.go:510-548`). An attacker who controls an IdP account that can present an arbitrary/self-asserted `email` claim can therefore collide their session's recorded identity with a real operator's email, causing audit-log misattribution, self-action-guard bypass (e.g. an attacker session "claiming" to be the target admin's email defeats `strings.EqualFold(sessionUser.Email, request.Email)` checks), and — if that email also has a row in the local `users` table used for password-gated flows (`TestPassword`, `SetPassword`) — collision with that local admin's credential-store operations.

### Impact Explanation
This does not, by itself, grant admin *role* — role is bound to the verified group/claim membership, which the attacker does not otherwise possess. The concrete, unconditional impact is account/session identity collision and accountability/audit-log spoofing (a verified OIDC user can make their actions attributed to another operator's email). Escalation to credential/API-token tampering additionally requires the collided email to also be a local admin account and, for token-minting endpoints (`NewAPIToken`, `DeleteAPIToken`), still requires passing `TestPassword` against that local account's real password, which the attacker does not have. So the realistic impact is best classified as an authentication/identity-integrity weakness (medium-high, cross-user impersonation/audit spoofing) rather than the unconditional "unauthenticated admin takeover" framing in the question, because privilege ultimately still depends on the signature-verified group claim.

### Likelihood Explanation
Exploitation requires the attacker to be able to complete a real OIDC authorization-code flow against the node's configured IdP (i.e., have or create an account there) and for that IdP to emit an `email` claim that is attacker-controlled/unverified (no `email_verified: true` requirement) — this is IdP/deployment-dependent rather than something the Chainlink code alone determines, but the code provides no defense-in-depth check (`email_verified`) that would neutralize IdPs with this property. Given a suitable IdP, the collision itself is trivial and repeatable for every login.

### Recommendation
Before trusting the `email` claim as an identity binding key, require and verify `claims["email_verified"] == true` (reject the login otherwise), and prefer binding sessions/tokens to an immutable subject identifier (`sub` claim, scoped to `iss`) rather than the mutable/self-asserted `email` claim. If `email` must remain the primary key for display/audit purposes, store the verified `sub`+`iss` pair as the actual foreign key for `oidc_sessions`/`oidc_user_api_tokens` and use it (not `email`) in the self-action guard comparisons in `core/web/user_controller.go`.

### Proof of Concept
Go unit test plan for `core/sessions/oidcauth`:
1. Construct two fake ID tokens signed by a test OIDC provider (using `oidc.NewProvider`/test JWKS as in `helpers_test.go`): token A with `email: "victim-admin@example.com"`, `email_verified: false` (or field absent), and a valid `RunClaim` group; token B is the legitimate victim's real, verified login.
2. Call `handleTokenExchange` (via test HTTP harness) with token A and assert that: (a) currently, the request succeeds and inserts an `oidc_sessions` row with `user_email = "victim-admin@example.com"` (demonstrating the bug), and (b) after the fix, the handler returns an error/rejection because `email_verified` is not true.
3. Add a table-driven test on `ExtractIDClaimValues`/`handleTokenExchange` asserting that a missing or `false` `email_verified` claim is rejected, and that binding uses `sub`/`iss` instead of `email`.
4. Integration-level test: with the buggy code, log in as attacker (token A), then call `ClearNonCurrentSessions`/`UpdateRole` self-guard style code path with `sessionUser.Email` and show it collides with victim's real `oidc_sessions` rows keyed on the same email, confirming cross-account interference.
