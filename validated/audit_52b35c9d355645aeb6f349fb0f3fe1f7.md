I need to check the ordering of `epochNumber` increment vs `collectWithdrawFunds` in `stopEpoch`, plus how `requestWithdraw` maps `lastWithdrawRequest`.### Title
Funded instant-withdraw claims never decrement `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, inflating default-recovery basis with phantom reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class of the external report is a missing refcount decrement (`of_node_put` after `of_find_compatible_node`): a resource reference that is acquired but never released. The closest analog in `IdleCreditVault` is the funded instant-withdraw claim path: `claimInstantWithdrawRequest` releases the aggregate counter `instantWithdrawsRequests[_user]` but never clears the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements the epoch-level `instantWithdrawClaimsByEpoch[epoch]`. Those per-epoch counters are later consumed by `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` during `finalizeDefaultRecovery`, so already-paid claims are counted again — once as claim basis and once as "already-held" recovery reserve that no longer exists.

### Finding Description
`requestInstantWithdraw` records three counters (IdleCreditVault.sol:366-374): `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]`.

When funds are collected (`collectInstantWithdrawFunds`, line 398-403), only `pendingInstantWithdraws` is decremented — the per-epoch claim totals are intentionally kept so a later default can distinguish funded vs. unfunded instant receipts via `pendingInstantWithdraws != 0`.

However, `claimInstantWithdrawRequest` (lines 380-393) only does:
```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```
It never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` and never subtracts the paid amount from `instantWithdrawClaimsByEpoch[epoch]`. Compare with `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which does clear both — that path exists only when a default is already finalized.

If a user fully claims a funded instant withdrawal in epoch E, and the borrower later defaults while `epochNumber` is still E with `pendingInstantWithdraws != 0` (other users' instant receipts unfunded), `finalizeDefaultRecovery` computes:
- `defaultPendingClaimBasis()` (line 644-649): adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes the already-paid claim.
- `_defaultPrefundedInstantReserve()` (lines 716-723): returns `instantBasis - pendingInstant`, which includes the already-paid amount as "already-held underlying reserved" — but those tokens were already transferred to the user.

So `reserveAmount` is overstated by the phantom amount and `totalBasis` is overstated by the same amount. The vault physically holds `reserveAmount - phantom` tokens: the last claimants' `_transferDefaultRecovery` calls (lines 912-917) will revert on insufficient balance, and the overstated `defaultRecoveryReserve` can never be fully distributed, leaving recovery funds permanently stranded. Additionally, `instantWithdrawClaimsByEpoch[E]` retains a stale entry forever since `_claimDefaultedInstantWithdrawRequest` only subtracts each claiming user's own basis.

### Impact Explanation
Recovery claimants (unprivileged tranche holders and withdraw requesters) are underpaid or unable to claim: the contract's accounting asserts `reserveAmount` tokens are available for recovery distribution while up to the phantom amount was already paid out through the funded claim path. The shortfall equals the sum of instant receipts fully claimed before finalization in the defaulted epoch. Claims at the tail of the queue revert on token transfer, permanently freezing part of the recovery reserve (the strategy has no function to sweep `defaultRecoveryReserve`).

### Likelihood Explanation
Requires a specific but plausible sequence in one epoch: at least two instant-withdraw requests in epoch E; the CDO collects instant-withdraw funds covering only a subset (`collectInstantWithdrawFunds` with partial `_amount`, leaving `pendingInstantWithdraws != 0`); the funded user claims via `claimInstantWithdrawRequest` (payable since the vault holds the collected funds); then the borrower defaults and `finalizeDefaultRecovery` runs while `epochNumber == E`. The prefunded-instant flow is an explicitly supported mode (comments at lines 636-640 describe exactly this partially-funded scenario), so the accounting gap is reachable by ordinary user action sequencing around honest manager/borrower calls.

Caveat: I could not fully verify `IdleCDOEpochVariant`/`IdleCDOEpochVariantPrefunded` internals (e.g., whether any path clears `instantWithdrawClaimsByEpoch` during `startEpoch`/`stopEpoch`, or whether `claimInstantWithdrawRequest` remains callable while `pendingInstantWithdraws != 0` in all variant configurations). The finding holds if, as the strategy code indicates, no other function mutates the per-epoch instant-claim counters.

### Recommendation
In `claimInstantWithdrawRequest`, after computing `amount`, also clear the per-epoch entries for all epochs in which the user has funded instant receipts. Since only the latest request epoch is tracked implicitly, the minimal fix is to decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the relevant epoch(s) — e.g., track `lastInstantRequestEpoch[_user]` or loop over the same epoch marker used at request time, mirroring the cleanup already performed in `_claimDefaultedInstantWithdrawRequest`.
