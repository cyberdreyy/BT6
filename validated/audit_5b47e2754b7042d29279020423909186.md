### Title
`getAccountInfo` with `encoding=base64Zstd` compresses full account data with no explicit size cap, unlike the bs58 path - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account` in `account-decoder/src/lib.rs` enforces an explicit size guard (`MAX_BASE58_BYTES = 128`) before running `bs58::encode`, but the `UiAccountEncoding::Base64Zstd` (and plain `Base64`) branches feed the entire sliced account data directly into `zstd::stream::write::Encoder::write_all`/`BASE64_STANDARD.encode` with no analogous size cap. Because an attacker can grow an on-chain account up to `MAX_PERMITTED_DATA_LENGTH` and fill it with incompressible random bytes, a single `getAccountInfo` call can force the RPC thread to zstd-compress up to the maximum account size, with CPU/memory cost driven purely by attacker-controlled account size rather than an RPC-specific limit.

### Finding Description
In `account-decoder/src/lib.rs`, `encode_bs58` explicitly checks `slice.len() <= MAX_BASE58_BYTES` before encoding and returns an error string otherwise: [1](#0-0) 

The `Base64Zstd` branch of `encode_ui_account`, in contrast, unconditionally streams the full (unsliced, unless `data_slice_config` is supplied) account bytes into a zstd encoder: [2](#0-1) 

There is no equivalent to `MAX_BASE58_BYTES` gating the `Base64` or `Base64Zstd` branches, and `slice_data` simply returns the caller-requested slice (or the whole account) with no additional cap: [3](#0-2) 

An attacker can: (1) create/realloc an account and fill it with `MAX_PERMITTED_DATA_LENGTH` bytes of incompressible random data (a single, low-rate on-chain write, allowed per the threat model), then (2) issue a single `getAccountInfo` RPC request with `encoding: "base64Zstd"` and no `dataSlice`. The RPC handler in `rpc/src/rpc.rs` calls into `encode_ui_account`, which will run the zstd encoder over the entire account buffer for that one request. Because zstd compression cost (CPU time and internal buffer allocation) scales with input size and is worse for incompressible data (the compressor cannot shortcut it), a single request forces the validator's JSON-RPC handling thread to do CPU work proportional to the attacker-chosen account size, with no RPC-layer size/complexity limit distinct from the protocol-level account size cap.

### Impact Explanation
This falls into the "unbounded cost for a single low-rate call" category in scope: a single unprivileged client, at ≤1 call per `CLUSTER_SLOT_TIME_TARGET / 2`, can force a disproportionate amount of CPU (zstd compression) and memory (output buffer, intermediate zstd internal buffers, plus the base64-encoded string, which is asymptotically larger than the input) to be consumed servicing one `getAccountInfo` request. This matches the described "single low-rate call causes disproportionate CPU/memory use serving one client" impact scope. The `bs58` path shows the maintainers are aware such a guard is necessary (hence `MAX_BASE58_BYTES`), but the guard was not applied consistently to the `Base64`/`Base64Zstd` branches.

### Likelihood Explanation
Feasibility is high and fully attacker-controlled and repeatable: any account owned by a program the attacker controls (or any account the attacker can grow via CPI/realloc) can be sized up to `MAX_PERMITTED_DATA_LENGTH` and filled with random data using ordinary transactions, with no special privileges required. The RPC call itself is a single, ordinary `getAccountInfo` request with `encoding=base64Zstd`, requiring no elevated rate or multiple clients.

### Recommendation
Add an explicit size guard on the `Base64` and `Base64Zstd` encoding branches of `encode_ui_account`, analogous to `MAX_BASE58_BYTES` for `encode_bs58` — e.g., reject or truncate encoding requests (with an explicit "data too large" error, similar to the existing bs58 path) when the sliced data length exceeds a fixed, RPC-appropriate threshold, independent of `MAX_PERMITTED_DATA_LENGTH`. Alternatively, bound the zstd encoder's per-request memory/CPU budget (e.g., limit compression level/window size, or process in fixed-size chunks with an overall byte budget) so cost is capped by an RPC-side constant rather than the full account size.

```rust
#[test]
fn bench_encode_ui_account_base64_zstd_large_incompressible() {
    use std::time::Instant;

    // Baseline: small account
    let small_data = vec![7u8; 128];
    let small_account = AccountSharedData::from(Account {
        data: small_data,
        ..Account::default()
    });

    let start = Instant::now();
    let _ = encode_ui_account(
        &Pubkey::new_unique(),
        &small_account,
        UiAccountEncoding::Base64Zstd,
        None,
        None,
    );
    let small_elapsed = start.elapsed();

    // Attacker-authored: max-size, incompressible (random) data
    let max_data: Vec<u8> = (0..solana_sdk_ids::system_program::MAX_PERMITTED_DATA_LENGTH as usize)
        .map(|_| rand::random::<u8>())
        .collect();
    let large_account = AccountSharedData::from(Account {
        data: max_data,
        ..Account::default()
    });

    let start = Instant::now();
    let _ = encode_ui_account(
        &Pubkey::new_unique(),
        &large_account,
        UiAccountEncoding::Base64Zstd,
        None,
        None,
    );
    let large_elapsed = start.elapsed();

    // Expected (post-fix) assertion: cost should be bounded by an explicit
    // RPC-side cap, not scale ~linearly with attacker-chosen account size.
    // Pre-fix, this assertion fails because large_elapsed >> small_elapsed
    // and scales with MAX_PERMITTED_DATA_LENGTH.
    assert!(
        large_elapsed.as_millis() < small_elapsed.as_millis() * 10,
        "encode_ui_account cost scales with attacker-controlled account size: \
         small={:?}, large={:?}",
        small_elapsed,
        large_elapsed
    );
}
```
Expected result pre-fix: the assertion fails, demonstrating that `encode_ui_account`'s `Base64Zstd` cost scales with attacker-controlled account size up to `MAX_PERMITTED_DATA_LENGTH`, with no explicit RPC-side cap analogous to `MAX_BASE58_BYTES`.

```rust
fn slice_data(data: &[u8], data_slice_config: Option<UiDataSliceConfig>) -> &[u8] {
    if let Some(UiDataSliceConfig { offset, length }) = data_slice_config {
        if offset >= data.len() {
            &[]
        } else if length > data.len() - offset {
            &data[offset..]
        } else {
            &data[offset..offset + length]
        }
    } else {
        data
    }
}
```
