### Title
Deleting a multisig key does not purge that key's confirmations on other pending requests, allowing a request to execute below the intended live-signer threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The `DeleteKey` action (multisig) and `DeleteMember` action (multisig2) only clean up requests that the deleted key/member itself *created*, and remove that key's `num_requests_pk`/`num_requests_per_member` counter. They never scan the `confirmations` map to strip that key's confirmation from *other*, still-pending requests it had previously confirmed but not created. As a result, a stale confirmation from an already-removed key/member remains counted toward `num_confirmations`, letting a request execute with fewer live, currently-authorized signers than the configured threshold.

### Finding Description
Both multisig contracts model a K-of-N confirmation threshold. `confirm()` checks the confirmations set size for a request and executes once `confirmations.len() + 1 >= num_confirmations`: [1](#0-0) 

Deleting a key is implemented as one of the `MultiSigRequestAction`s executed inside `execute_request`: [2](#0-1) 

This cleanup only removes requests where `r.signer_pk == pk` (i.e., requests *added* by that key) — via `self.requests.iter().filter(|(_k, r)| r.signer_pk == pk)`. It does not iterate the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map to strip the deleted key from confirmation sets of requests *created by other signers* that this key had already confirmed.

The equivalent `multisig2` `delete_member` has the identical gap: [3](#0-2) 

Here `request_ids` is filtered by `r.member == member` (the request's original creator/signer), again leaving that member's entries inside `self.confirmations` for requests created by anyone else untouched.

Concretely:
1. Member A confirms request R (created by member B) via `confirm()`, which inserts A's key into `confirmations[R]` (multisig) or `confirmations[R]` (multisig2, keyed by `member.to_string()`) — see the `else` branch that does `confirmations.insert(...)`: [4](#0-3) 
2. R has not yet reached `num_confirmations`, so it stays pending.
3. The multisig legitimately removes member A (e.g., because A's key was compromised, A left the org, or the group is rotating signers) via a properly-confirmed `DeleteKey`/`DeleteMember` request.
4. R's confirmation set is left untouched because R was created by B, not A — R is not in the "requests created by A" filter.
5. Now only `num_confirmations - 1` *live* members need to confirm R for it to reach the threshold and execute (since A's stale confirmation is still counted), even though A is no longer an authorized signer.

This breaks the intended custody binding: `confirmations counted == confirmations from live/current members`. After removal, the equality becomes `confirmations counted > confirmations from live members`, letting `execute_request` (which can `Transfer`, `AddKey`/`AddMember`, `DeployContract`, arbitrary `FunctionCall`, etc.) run while the real live-signer threshold was never met.

### Impact Explanation
This falls under the "Critical" bucket explicitly called out: *"a multisig request executed below threshold"*. Once R executes with a stale confirmation counted, funds can be transferred (`Transfer`), new keys/members added (`AddKey`/`AddMember`), or arbitrary contract code deployed (`DeployContract`) — all custody- and authorization-critical actions of the multisig account — despite fewer than `num_confirmations` currently-authorized parties having actually approved it. This can lead to unauthorized movement of NEAR held by the multisig account.

### Likelihood Explanation
This does not require compromising a private key, social engineering, or foundation/owner-only privilege beyond the multisig's own normal, expected operation: rotating/removing a signer is a routine multisig administrative action. Any scenario where (a) a member confirms a request that isn't immediately executed, and (b) that member is later removed before the request is deleted/executed/expired, triggers the bug. Because requests have no expiration other than a manual `delete_request` (gated only by a 15-minute cooldown, not automatic), and member rotation is a normal lifecycle event, the window for this to occur is realistic, especially in any multisig that actively rotates signers.

### Recommendation
When executing `DeleteKey`/`DeleteMember`, iterate over `self.confirmations` for *all* pending requests (not just ones created by the removed key/member) and remove the deleted key/member's entry from each confirmation set, or alternatively re-validate at `confirm()`/execution time that every already-recorded confirmer is still a current, valid multisig member before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize a 3-of-4 multisig with members `{A, B, C, D}` (`num_confirmations = 3`).
2. `B` calls `add_request` to create transfer request `R` (receiver arbitrary, amount = pool balance).
3. `A` calls `confirm(R)` → `confirmations[R] = {A}` (1 of 3, not yet executed). [5](#0-4) 
4. The group legitimately executes a separate, properly-confirmed request to `DeleteKey { public_key: A }` (3-of-4 confirmed by, say, `B, C, D`). Execution removes only requests where `signer_pk == A`; `R` (signed by `B`) is untouched, and `confirmations[R]` still contains `A`. [2](#0-1) 
5. Now `C` calls `confirm(R)` → `confirmations[R].len() + 1 = 2 + 1 = 3 >= num_confirmations(3)` → `execute_request(R)` runs and transfers funds.
6. Result: `R` executed with confirmations from `{A (removed), B (creator, implicitly trusted as adder—not a confirmer), C}` — only 1–2 *live* confirming members (`C`, plus creator `B`) actually authorized it at execution time, not the required 3 live signers, because `A`'s stale confirmation was still counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
