## Finding: Workflow-trigger JWT verification ignores issuer/audience, allowing signature reuse across DON/gateway deployments

### Title
Missing issuer/audience (domain-separation) verification in `VerifyRequestJWT` allows Ethereum-signed trigger tokens to be replayed across different DON/gateway deployments - (File: `core/utils/jwt.go`)

### Summary
The Chainlink Gateway's HTTP workflow-trigger authentication uses `CreateRequestJWT`/`VerifyRequestJWT` (an Ethereum-signature-based JWT scheme) to authorize workflow owners' signing keys. `CreateRequestJWT` supports `Issuer`/`Audience` claims explicitly for this purpose, but `VerifyRequestJWT` never checks them during verification.

### Finding Description
`CreateRequestJWT` allows setting `Issuer` and `Audience` claims in the token [1](#0-0) , but `VerifyRequestJWT`, which performs the actual authentication of the signed token, only validates the signature, `jti` (replay cache), `exp`/`iat` bounds, and that the claimed `digest` matches `req.Digest()` — it never inspects `Issuer` or `Audience` at all [2](#0-1) .

This verification function is used directly by `WorkflowMetadataHandler.Authorize`, the gateway-side authorization gate for HTTP-triggered workflow executions [3](#0-2) . The only binding enforced is: (1) the recovered signer address is in the workflow's authorized-key set, and (2) the request digest (method + id + params, which includes the target workflow selector) matches the claim. Nothing in the digest, claims, or verification path binds the token to a specific gateway/DON instance, environment, or deployment (the analog of Hermez's missing "contract address"/"chainId" binding).

Because the same workflow definition (same `workflowOwner`/`workflowName`/`workflowTag`, hence potentially the same derived `workflowID`) can be re-registered or re-deployed to a different DON/gateway instance (e.g., staging vs. production, or after a DON migration/re-deployment), and because the signed payload's digest only covers the JSON-RPC request contents (not the serving DON/gateway identity), a JWT that a workflow owner signs once for a legitimate request/DON is structurally indistinguishable from — and therefore replayable on — any other Gateway/DON instance that recognizes the same workflowID and authorized signer, exactly mirroring the Hermez `_checkSig` weakness where a signature bound only to application data (not the deploying instance) could be replayed across forks/redeployments.

### Impact Explanation
An attacker who can induce a workflow owner to sign a request destined for one Gateway/DON deployment (e.g., a test/staging environment they control) can replay the exact same signed JWT + JSON-RPC request against any other deployment that shares the workflow's authorized-key configuration, triggering unauthorized workflow executions there. Since `HandleUserTriggerRequest` fans out execution across shard nodes upon successful `Authorize` [4](#0-3) , a replayed signature can cause unauthorized job/workflow runs — a concrete "unauthorized job run" impact.

### Likelihood Explanation
Exploitation requires only unprivileged client capability (submitting a JSON-RPC request with a previously-obtained valid, unexpired JWT to a different but reachable Gateway endpoint before the `jti`/replay cache and 5-minute expiry window elapse) [5](#0-4) ; the jti-replay cache is scoped per `WorkflowMetadataHandler` instance and does not span deployments, so it provides no protection here.

### Recommendation
Bind `VerifyRequestJWT` to check `Issuer`/`Audience` (or an equivalent DON/gateway identifier) against the expected value for the serving deployment, and/or include the gateway/DON identity in the signed digest, so tokens minted for one deployment are cryptographically rejected by any other.

### Proof of Concept
1. Workflow owner signs an `HTTPTriggerRequest` JWT via `CreateRequestJWT` for workflow `W` intended for Gateway instance `A` (e.g., staging).
2. Attacker captures the resulting JWT + request body (network observation, staging log, or by convincing the owner to test on a controlled instance).
3. Attacker submits the identical JWT and request body to Gateway instance `B` (e.g., production) that also has workflow `W` (or an identically-owned/named workflow) registered with the same authorized signer.
4. `WorkflowMetadataHandler.Authorize` on instance `B` independently recovers the same signer address, matches the same digest, and — since `Issuer`/`Audience` are never checked — accepts the token, triggering execution on `B` without the owner's intent for that deployment.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```

```go
func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}
```
