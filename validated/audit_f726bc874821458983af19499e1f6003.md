### Title
Global `requestCache` has no per-sender quota, allowing any signer to exhaust `maxCacheSize` and deny other users' requests - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces a single global `maxCacheSize` bound shared by all callers, keyed only by `(sender, messageId)` [1](#0-0) . Because there is no per-sender limit or reservation, any party able to submit distinct `sender`/`messageId` pairs that reach this cache can fill it with entries that only clear on `timeout`, causing `NewRequest` to return `"request cache is full"` for every other sender until those entries expire [2](#0-1) .

### Finding Description
`requestCache[T]` stores pending requests in a single map `cache map[globalId]*pendingRequest[T]` with a fixed `maxCacheSize` [3](#0-2) . `globalId` is `{sender, id}`, so distinct senders (or distinct `MessageId`s per sender) each get their own slot in the same shared map, and the size check `len(c.cache) >= int(c.maxCacheSize)` counts entries across all senders together [4](#0-3) [5](#0-4) . Entries are only removed via `deleteAndSendOnce`, triggered either by a matching `ProcessResponse` or by the `time.AfterFunc(c.timeout, ...)` timer firing after `c.timeout` [6](#0-5) [7](#0-6) . There is no logic in this file that reserves capacity per sender or rejects a flood of unique senders before it consumes the whole table.

### Impact Explanation
If an attacker can cause `NewRequest` to be invoked `maxCacheSize` times with distinct `sender`/`MessageId` combinations that never receive a matching node response, the cache fills and remains full for up to `timeout`, causing legitimate victims' calls to the same cache instance to fail with `"request cache is full"`. This is a denial-of-service / availability impact scoped to whatever handler shares this single `requestCache` instance, not a data leak, key disclosure, or authorization bypass.

### Likelihood Explanation
Whether this is practically reachable by an unprivileged attacker depends entirely on what gates precede the call to `NewRequest` for a given handler, and I could not fully confirm this for every caller within the scope of this investigation. Notably, of the concrete callers found, the vault gateway handler does **not** use this generic `requestCache`; it maintains its own `activeRequests` map guarded by `h.requestProcessor.ProcessRequest` (on-chain allowlist / JWT authorization) before any entry is created [8](#0-7) , which would prevent unauthenticated Sybil flooding for that handler. Other consumers of `common.RequestCache` (e.g. `core/services/gateway/handlers/capabilities/handler.go`) were located but their pre-`NewRequest` authentication/rate-limiting path was not verified in this session. Absent evidence of a per-sender rate limiter or authorization/allowlist step gating access to those call sites, the generic cache implementation itself provides no per-sender isolation and is the root cause if such a gate is missing or bypassable.

### Recommendation
Add per-sender quotas or reservations in `requestCache` (e.g., cap the number of concurrent pending entries per `sender`, independent of the global `maxCacheSize`), and/or require callers to authenticate/authorize the sender (allowlist, staking, or per-sender rate limiting) before invoking `NewRequest`, so a flood of distinct signer identities cannot consume the shared table.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/common/requestcache_test.go`:
1. Construct `cache := common.NewRequestCache[requestState](time.Hour, N)` with a small `N` (e.g., 3).
2. Loop `N` times, each iteration using a unique `sender` (e.g., `fmt.Sprintf("0xattacker%d", i)`) and a fixed or unique `MessageId`, calling `cache.NewRequest(lggr, req, callback, &requestState{})`; assert each call returns `nil`.
3. As the victim, call `cache.NewRequest(lggr, victimReq, victimCallback, &requestState{})` with a distinct `sender="0xvictim"`; assert the returned error is `"request cache is full"`.
4. This demonstrates that filling the shared cache with attacker-controlled distinct senders denies a legitimate victim's request at this layer, confirming no per-sender isolation exists in `requestCache.NewRequest`.

```go
func (c *requestCache[T]) deleteAndSendOnce(key globalId, callbackResponse handlers.UserCallbackPayload) error {
	c.mu.Lock()
	entry, deleted := c.cache[key]
	delete(c.cache, key)
	c.mu.Unlock()
	if deleted {
		entry.timeoutTimer.Stop()
		return entry.SendResponse(callbackResponse)
	}

	return nil
}
```
