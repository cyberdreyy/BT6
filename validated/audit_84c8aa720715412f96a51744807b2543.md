### Title
EI credentials bypass "no int-ID job runs for EIs" check and can trigger ANY job by ID - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` into the gin context under `SessionUserKey`, so `auth.GetAuthenticatedUser(c)` returns `ok=true` for EI-authenticated requests even though no real user exists. `PipelineRunsController.Create` uses exactly that boolean (`isUser`) to gate the "run job by integer ID" code path, so any valid EI credential can trigger `prc.App.RunJobV2` for any job ID, not just jobs bound to that initiator.

### Finding Description
The route is registered as: [1](#0-0) 

`auth.Authenticate` tries `AuthenticateExternalInitiator` first; on success it sets both `SessionExternalInitiatorKey` and a fake `SessionUserKey`: [2](#0-1) 

`auth.RequiresRunRole` only checks `user.Role != UserRoleView`, so the synthetic `UserRoleRun` user passes: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code explicitly intends "only users are allowed to run jobs using int IDs - EIs not allowed", and gates the RunJobV2 call on `isUser`: [4](#0-3) 

But `GetAuthenticatedUser` merely does a type assertion on whatever object is stored at `SessionUserKey` — it cannot distinguish a real session/token user from the synthetic EI user set by `AuthenticateExternalInitiator`: [5](#0-4) 

Because `AuthenticateExternalInitiator` sets `SessionUserKey`, `isUser` is `true` for EI-authenticated requests, defeating the intended restriction. The code then parses the `:ID` path param as an int32 job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` unconditionally — there is no check that the job ID belongs to, or is configured with, the external initiator that authenticated the request (webhook/external-initiator-bound job UUID matching was removed per the comment at lines 103-107, and no other binding check exists for the int-ID path).

### Impact Explanation
Any holder of a valid EI AccessKey/Secret pair (a low-privilege credential intended only to trigger its own bound webhook-style runs) can trigger a pipeline run on **any** job in the node by integer ID — including OCR, keeper/automation, or other job types never associated with that initiator. This is an authorization bypass allowing unauthorized triggering of arbitrary job pipelines (e.g., forcing an OCR job's observation/tasks to execute, consuming node resources, or performing tasks with side effects such as HTTP calls, bridge calls, or writes performed by pipeline tasks). This matches the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions: attacker needs one valid `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` pair for any external initiator registered on the node (a minimal, non-admin credential), plus knowledge/guess of a target job's integer ID. Both are attacker-obtainable in normal deployments (external initiators are often given to third-party integrations with lower trust), and job IDs are small sequential integers that are easy to enumerate. This is fully reproducible via a single HTTP POST and requires no timing tricks or race conditions.

### Recommendation
`GetAuthenticatedUser`/`PipelineRunsController.Create` must distinguish real users from the synthetic EI user. Options: (1) do not set `SessionUserKey` at all in `AuthenticateExternalInitiator`, and have `PipelineRunsController.Create` check `auth.GetAuthenticatedExternalInitiator(c)` explicitly to reject EI-driven requests on the int-ID path; or (2) tag the synthetic user with a distinguishing marker (e.g., a dedicated field or sentinel) and check for it in `Create` before allowing `RunJobV2`. Also, if EI-triggered runs by ID are ever desired, add an explicit binding check between the authenticated `ExternalInitiator` and the target job.

### Proof of Concept
Handler-integration test (Go, in `core/web/pipeline_runs_controller_test.go` style):
1. Start an app, create an OCR job Y via `app.AddJobV2` (unrelated to any external initiator).
2. Create an `ExternalInitiator` X via `bridges.NewExternalInitiator` + `app.BridgeORM().CreateExternalInitiator`.
3. Build an HTTP client that does NOT set session cookie/API token, only sets headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` for X.
4. POST `/v2/jobs/<Y.ID>/runs` with that client.
5. Assert current (buggy) behavior: `http.StatusOK` and a `pipelineRun` resource is returned (i.e., `prc.App.RunJobV2` was invoked) — proving the EI credential unlocked a job it has no relation to.
6. Expected/fixed behavior: response should be `http.StatusUnprocessableEntity` (or 401/403) with an error such as "bad job ID" / "EIs not allowed", and `RunJobV2` must not be called for EI-authenticated requests unless the job is explicitly bound to that initiator.

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
