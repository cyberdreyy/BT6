### Title
Symlink target (`Linkname`) is never validated against the extraction root - `os.Symlink(hdr.Linkname, path)` writes an unchecked link target - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
`extractor.Extract` validates that a tar entry's *destination path* (`hdr.Name`) stays within `e.dir` [1](#0-0) , but for symlink entries it never validates `hdr.Linkname` (the symlink's target) before calling `os.Symlink(hdr.Linkname, path)` in the deferred pass [2](#0-1) . This lets a crafted cache/artifact archive create a symlink whose *name* is safely inside `e.dir` but whose *target* points anywhere on the filesystem (e.g. `../../etc` or an absolute path).

### Finding Description
The only chroot check in `Extract` operates on the computed destination `path` (`filepath.Join(e.dir, hdr.Name)`), and only for the entry itself [1](#0-0) . Symlink entries are deferred and materialized after all regular files/dirs are written, and the deferred loop calls `os.Symlink(hdr.Linkname, path)` with `hdr.Linkname` used verbatim — there is no `strings.HasPrefix`, `filepath.Rel`, or any other check on `Linkname` anywhere in this file [3](#0-2) . The same gap exists in the ZIP extractor (`extractZipSymlinkEntry`), which reads the link target from the entry's content and calls `os.Symlink(string(data), file.Name)` without any chroot validation of the target [4](#0-3) .

However, the specific ordering scenario in the question — a regular file `a/evil` written before the symlink `a` is materialized, with the write "safely" landing inside `e.dir` — does not actually work as described. Because `a/evil` is processed in the main loop before the deferred pass, `os.MkdirAll(filepath.Dir(path))` creates a **real directory** `e.dir/a` on disk (the symlink for `a` has not been created yet, only recorded in `deferred`) [5](#0-4) . When the deferred loop later attempts `os.Symlink(hdr.Linkname, path)` for `a`, that path already exists as a non-empty real directory, so `os.Symlink` fails with `EEXIST` and `Extract` returns an error immediately [6](#0-5) . This aborts extraction rather than completing the described exploit chain — no cross-root write occurs via that ordering, only a failed extraction (denial of extraction, not path traversal).

The real, verifiable defect is narrower than described: an archive containing **only** a symlink entry (no colliding directory/file entries under the same name) will successfully create a symlink node whose path is inside `e.dir` but whose target (`Linkname`) is unchecked and can point outside `e.dir` (e.g., `/etc`, `../../..`). `updateFileMetadata` uses the `l*`-prefixed syscalls (`lchtimes`, `lchmod`, `lchown`) which operate on the link itself and do not dereference it [7](#0-6) , so `Extract` itself never follows the dangling/escaping symlink to write data outside `e.dir`. The escape only becomes exploitable if some **later, separate** operation writes through that symlink by relative path (e.g., a subsequent job step, or another cache/artifact restore that resolves paths under `e.dir/a`), which is outside the scope of this function and depends on downstream behavior not shown to write unprivileged data through un-dereferenced symlinks within the same trust domain as the archive's own author.

### Impact Explanation
Confirmed: `hdr.Linkname` is genuinely unchecked, which is a real gap relative to the invariant "symlink target ... must not allow later operations to escape e.dir." But the concrete, reachable impact described in the question (regular-file write "landing safely inside e.dir" combined with the symlink materialization to complete an escape within `Extract` itself) does not hold — that ordering causes `os.Symlink` to fail with `EEXIST` and aborts extraction before any escape completes. The residual risk (a dangling symlink left inside `e.dir` pointing outside it) requires a second, independent write operation from a *different* untrusted or higher-privileged actor writing through that symlink to have any cross-boundary impact; a user restoring their own cache/artifact and later writing through their own planted symlink does not cross a privilege or tenancy boundary (self-inflicted, not an escalation), and for containerized executors any such symlink resolves inside the container's own mount namespace, not on the host.

### Likelihood Explanation
Low as scoped. The exact call chain in the question (regular file write before symlink materialization producing a completed, unnoticed escape) is not reproducible — it errors out instead. Exploiting the residual unchecked-`Linkname` gap for genuine cross-tenant/cross-root impact would require an additional trust-boundary violation (e.g., shared/poisoned cache across projects, or a subsequent unprivileged write through the dangling symlink) that is not demonstrated to exist in this code path.

### Recommendation
Regardless of the specific chain being invalid, `hdr.Linkname` should still be validated/resolved against `e.dir` before calling `os.Symlink`, consistent with the existing check applied to `hdr.Name`, to remove the residual dangling-symlink primitive. The same fix should be applied to `extractZipSymlinkEntry` in `helpers/archives/zip_extract.go`.

### Proof of Concept
A Go test can confirm both halves:
1. Confirm the described "safe write + escaping symlink" ordering fails, not succeeds: build a tar+zstd archive with entries `a` (symlink -> `..`) then `a/evil` (regular file), extract via `extractor.Extract`, and assert it returns a non-nil error (`EEXIST` on `os.Symlink`) rather than completing successfully — disproving the exploit chain as stated.
2. Confirm the residual gap: build an archive containing only a symlink entry `link` -> `../../etc/passwd` (no colliding directory entries), call `Extract`, assert it returns `nil` error, then `os.Lstat`/`os.Readlink(filepath.Join(dir, "link"))` and assert the target is not rejected/rewritten — showing `Linkname` is accepted verbatim without chroot validation (a hardening gap, though not demonstrated to be directly exploitable for cross-root writes within this function alone).

```go
func (e *extractor) updateFileMetadata(path string, hdr *tar.Header) error {
	fi := hdr.FileInfo()

	if err := lchtimes(path, fi.Mode(), time.Now(), fi.ModTime()); err != nil {
		return err
	}

	if err := lchmod(path, fi.Mode()); err != nil {
		return err
	}

	_ = lchown(path, hdr.Uid, hdr.Gid)
	return nil
```

```go
func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
```
