### Title
Blacklisted maker permanently blocks `EscrowDst` withdrawal, letting the resolver seize both legs of the swap - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` pushes the destination token directly to `immutables.maker.get()` via `_uniTransfer`/`safeTransfer`, with no pull-based fallback. If the maker's address is blacklisted by the destination token (e.g. USDC), every call to `withdraw` and `publicWithdraw` reverts for the whole withdrawal window, and the only remaining exit is `cancel`, which returns the destination funds to the taker instead of the maker [1](#0-0) .

### Finding Description
`EscrowDst._withdraw` unconditionally transfers `amount` to `immutables.maker.get()`: [2](#0-1) 

Both entry points that reach `_withdraw` — the taker-only `withdraw` and the access-token-gated `publicWithdraw` — always route funds to the same hardcoded maker address, with no alternate recipient or pull-claim option [3](#0-2) . The underlying transfer helper `_uniTransfer` calls `IERC20.safeTransfer(to, amount)` for ERC20 tokens, which reverts if `to` is blacklisted by the token contract [4](#0-3) . Unlike `EscrowSrc`, which exposes `withdrawTo(secret, target, immutables)` allowing the taker to redirect ERC20 proceeds to an arbitrary `target` [5](#0-4) , `EscrowDst`/`IEscrowDst` has no equivalent redirect mechanism [6](#0-5) .

This is the same root cause as the referenced report: a push-based transfer to a potentially blacklisted, unprivileged, user-controlled address (`maker`) with no pull/claim fallback, causing every withdrawal attempt (private and public) to revert throughout the entire withdrawal window.

Once the withdrawal window elapses, the only remaining path is `cancel`, which sends the same destination `amount` to `immutables.taker.get()` (the resolver) rather than to the maker: [7](#0-6) 

Meanwhile, the resolver (taker) already possesses the secret needed to withdraw the maker's original assets from `EscrowSrc` on the source chain, since the maker must reveal the secret for the swap to proceed at all. Because `EscrowSrc.withdraw` only requires knowledge of the secret and `onlyCaller(taker)`, the resolver can withdraw the maker's source-chain funds using that same secret [8](#0-7) . Combined with the dst-side `cancel` returning the destination funds to the resolver, the resolver ends up recovering *both* legs of the swap while the maker — who did nothing malicious except being blacklisted by the destination token issuer — receives nothing.

### Impact Explanation
This results in the maker's escrowed source-chain assets being effectively transferred to the resolver with no compensating destination-chain delivery: the maker permanently loses the value they locked in `EscrowSrc`, and the resolver realizes an unearned gain from `EscrowDst.cancel` plus the source-chain withdrawal. This fits "temporary freezing of funds during the live swap lifecycle" (destination withdrawal window fully blocked) escalating into "theft or permanent loss" of the maker's swap proceeds, matching the High-impact bucket in the bounty scope. The attacker model here is not a privileged actor — any regular maker who happens to be blacklisted by a stablecoin issuer (a routine, externally-triggered condition, not an attack the maker controls) triggers this unprivileged failure mode, consistent with the required unprivileged-user model.

### Likelihood Explanation
Low likelihood, matching the original report's classification: it requires the destination token to be a blacklistable asset (e.g. USDC, USDT) and the maker's address to already be on that blacklist. This is a plausible but infrequent real-world condition, not something the maker can trigger at will, and the resolver cannot arbitrarily blacklist a maker (that's an issuer-only action), so it cannot be weaponized on demand — it is an edge case that surfaces naturally.

### Recommendation
Adopt a pull-over-push pattern for `EscrowDst` withdrawals: instead of unconditionally pushing `amount` to `immutables.maker.get()` in `_withdraw`, credit an internal claimable balance for the maker (or wrap the transfer in a try/catch that falls back to an escrowed/claimable balance) so a blacklisted recipient cannot block the state transition. Alternatively, add a `withdrawTo`-style function symmetric to `EscrowSrc`, allowing the maker (or a party acting on the maker's instructions, via signature) to redirect destination proceeds to an alternate, non-blacklisted address before the cancellation window opens.

### Proof of Concept
1. Maker signs an order; resolver fills it, deploying `EscrowSrc` (funded with maker's source tokens) and `EscrowDst` (funded with resolver's destination USDC).
2. Maker's address is (or becomes) blacklisted by the destination USDC contract.
3. Maker reveals the secret off-chain to the resolver so the resolver can proceed with withdrawal.
4. Resolver calls `EscrowSrc.withdraw(secret, immutables)` and receives the maker's source-chain tokens [8](#0-7) .
5. Resolver (or any access-token holder via `publicWithdraw`) attempts `EscrowDst.withdraw`/`publicWithdraw`; both revert inside `_withdraw`'s `safeTransfer` to the blacklisted maker [9](#0-8) .
6. After the `DstCancellation` timelock elapses, resolver calls `EscrowDst.cancel`, reclaiming the destination USDC for themselves [7](#0-6) .
7. Net result: resolver holds both the maker's source tokens and their own reclaimed destination tokens; the maker receives nothing.

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
