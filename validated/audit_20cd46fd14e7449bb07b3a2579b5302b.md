### Title
Signer vote-flip (Reject → Accept) double-counts weight in the node's `StackerDBListener`, corrupting the aggregated approve/reject tally and wedging block consensus - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` (used by the miner-side `SignerCoordinator`) tracks per-block consensus with a single `BlockStatus` struct holding `total_weight_approved`, `total_weight_rejected`, and a shared `responded_signers` set [1](#0-0) . The `Accepted` branch gates weight-addition on `gathered_signatures.contains_key(&slot_id)`, while the `Rejected` branch gates it on `responded_signers.insert(slot_id)` — two different membership checks against different collections for the same "have we already counted this signer" question. When a signer legitimately flips its vote from Rejected to Accepted for the same block (a state transition the signer explicitly supports: `LocallyRejected --> LocallyAccepted : re-evaluated`), the node adds that signer's weight to `total_weight_approved` without ever removing it from `total_weight_rejected`, because nothing in the codebase decrements `total_weight_rejected` when a later acceptance from the same signer arrives.

### Finding Description
In the `Accepted` handling code, weight is only added the first time a signature from a given slot is seen (`!block.gathered_signatures.contains_key(&slot_id)`), and the slot is then inserted into both `gathered_signatures` and the shared `responded_signers` set [2](#0-1) .

In the `Rejected` handling code, weight is added the first time `responded_signers.insert(slot_id)` returns true [3](#0-2) .

Consider the normal, non-Byzantine sequence:
1. Signer S rejects block B (e.g. a stale chainstate check fails); the coordinator records `total_weight_rejected += weight(S)` and `responded_signers.insert(S)`.
2. Per the documented signer state machine, block B can be re-evaluated and this same signer can subsequently transition `LocallyRejected -> LocallyAccepted` and broadcast an `Accepted` response for the same `signer_signature_hash` (this is an intended, non-adversarial path, not a majority/collusion requirement) — see `docs/signer-flows.md` state diagram, `LocallyRejected --> LocallyAccepted : re-evaluated` and the "should_reevaluate_reject_reason"/"should_reevaluate_block" logic that re-drives blocks through evaluation on re-proposal.
3. On the node side, this `Accepted` message is looked up by `gathered_signatures.contains_key(&slot_id)` — which is `false` (S never signed before) — so `total_weight_approved += weight(S)` is applied.
4. `total_weight_rejected` for S is never decremented; there is no code path anywhere in `stackerdb_listener.rs` that reduces `total_weight_rejected` or `total_weight_approved` once added.

The result: S's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously, for the same block. This breaks the accounting invariant that the sum of per-signer weights recorded across `total_weight_approved`/`total_weight_rejected` for one block should never exceed `self.total_weight` (the reward-set total). This is precisely analogous to the H-22 pattern: an action that logically "moves" a signer's weight from one bucket (reject) to another (accept) updates only the destination side, leaving the stale source-side accounting in place — an equality/consistency invariant (aggregated weight vs. actual distinct-signer votes) is silently violated.

### Impact Explanation
The corrupted `total_weight_rejected` value feeds directly into the liveness/consensus decision for block production:

```rust
if block.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    // Signal to anyone waiting on this block that we have enough rejections
    cvar.notify_all();
}
``` [4](#0-3) 

Because a single flipped vote inflates `total_weight_rejected` by weight that has, in reality, already moved to the approve side, the coordinator can be made to believe a blocking-minority rejection threshold has been reached (or reached earlier than it truly would be) even though the same signer's current, valid Accepted vote is also being counted toward the 70% approval threshold. This can cause the coordinator/miner to give up on a block that the actual current signer set would otherwise approve, forcing the miner to abandon and re-propose — a liveness wedge on block production reachable without needing a majority of signers or any key compromise: it only needs one signer whose vote legitimately changes from reject to accept for the same block hash, which is an explicitly supported state transition. This matches the "High" impact category: a wedge preventing valid block signing progress under normal single-signer behavior.

### Likelihood Explanation
This does not require a majority of signers, a compromised key, or any adversarial behavior — the signer's own state machine documents `LocallyRejected --> LocallyAccepted` as a normal re-evaluation outcome, and `should_reevaluate_block`/`should_reevaluate_reject_reason` on re-proposal explicitly drive re-evaluation of a previously-rejected block back through the pre-commit/acceptance path. Any timing where a signer initially rejects (e.g., transient node-tip lag, stale chainstate view) and then re-evaluates to accept on the same proposal will trigger this double counting. Likelihood is therefore moderate-to-high in real network conditions with re-proposals/timeouts.

### Recommendation
Use a single, unified per-signer decision map (e.g., `HashMap<u32, Vote>`) instead of independently gating `total_weight_approved` on `gathered_signatures` and `total_weight_rejected` on `responded_signers`. When a signer's vote changes from Rejected to Accepted (or vice versa) for the same block, first subtract the previously recorded weight from the old bucket before adding it to the new one, so the two counters remain mutually exclusive and their sum never exceeds `self.total_weight`.

### Proof of Concept
1. Node/coordinator tracks `BlockStatus` for proposed block B with `total_weight = W`, `weight_threshold = 0.7W`.
2. Signer S (weight w) sends `BlockResponse::Rejected` for B → `total_weight_rejected = w`, `responded_signers = {S}`.
3. S re-evaluates B (per the documented `LocallyRejected -> LocallyAccepted` transition) and sends `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. In the `Accepted` handler, `gathered_signatures.contains_key(&S)` is `false`, so `total_weight_approved = w` is added; `gathered_signatures`/`responded_signers` now also contain S.
5. `total_weight_rejected` remains `w` (never decremented).
6. Now `total_weight_approved + total_weight_rejected = 2w` can exceed what a single signer S should ever contribute, and if enough such flips accumulate, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can become true even though the *current* votes of all signers would actually reach the 70% approval threshold, causing the coordinator to prematurely treat the block as unreachable/rejected.
