### Title
Front-runnable, unauthenticated `init_global_fee_state` allows anyone to seize permanent control of the protocol's global fee admin - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
The `InitFeeState` instruction that creates the program-wide `FeeState` PDA is callable by any signer with no check that the caller is the intended deployer/authority. [1](#0-0)  The instruction accepts an arbitrary `admin_key` and `fee_wallet` argument and writes them directly into the `FeeState` account with no restriction on who the caller is, mirroring the reported `setIDOLContract()` pattern of an unauthenticated "set once" critical configuration function. [2](#0-1) 

### Finding Description
`InitFeeState` uses Anchor's `init` constraint on a PDA derived from the fixed, publicly known seed `FEE_STATE_SEED`, so it can only succeed once per program deployment: [3](#0-2)  But the accounts context only requires `payer: Signer<'info>` — any signer, not a designated deployer/upgrade authority — can be the caller. [4](#0-3)  The handler blindly assigns the supplied `admin_key` to `fee_state.global_fee_admin` and `fee_wallet` to `fee_state.global_fee_wallet`, exactly as `setIDOLContract()` did for `_IDOLContract` in the report (only guarded by "not-yet-set", with no authorization). [5](#0-4) 

Once set, this `global_fee_admin` becomes the sole authority who can subsequently modify the fee state via `edit_global_fee_state`, which is gated with `has_one = global_fee_admin`. [6](#0-5)  Because the PDA address is fully deterministic (derivable off-chain from the program ID and constant seed before the account is ever created), an attacker monitoring the mempool/program deployment can race the legitimate deployer's `init_global_fee_state` transaction and land their own first, permanently becoming `global_fee_admin` and redirecting `global_fee_wallet` to an address they control — with no on-chain recovery path since the account can never be re-initialized (`init` fails if it already exists).

### Impact Explanation
The `global_fee_admin`/`global_fee_wallet` set here is the protocol-wide fee sink referenced across banks, liquidation, order execution, and Drift/Kamino integrations (e.g., harvested Drift rewards and program fees are swept to this wallet). [7](#0-6)  An attacker who wins this race gains durable control to redirect all protocol-wide fees to themselves via `edit_global_fee_state`, and also controls `pause_delegate_admin` used in panic/pause logic. [8](#0-7)  This is a durable, unauthorized state takeover with direct financial impact (fee redirection) and no recovery mechanism (the `init` constraint prevents re-initialization).

### Likelihood Explanation
This is exploitable only during the narrow window between program deployment and the deployer's own `init_global_fee_state` call landing on-chain — it requires the attacker to detect the new deployment and front-run a single transaction with a known, deterministic PDA address, which is a realistic and previously-seen attack pattern on Solana ("deployment sniping"). Whether this is practically exploitable on the actual production deployment depends on operational details (e.g., whether deployment scripts bundle `init_global_fee_state` atomically with program upgrade in the same transaction, and whether the account already exists on the current mainnet deployment) which could not be fully confirmed from the indexed code alone — test/fixture code shows it invoked as a standalone instruction, sometimes bundled with `MarginfiGroupInitialize` in the same transaction, sometimes not. [9](#0-8) 

### Recommendation
Restrict `InitFeeState`/`init_global_fee_state` to a hardcoded, immutable authority (e.g., the program's upgrade authority or a constant deployer pubkey checked via `#[account(constraint = payer.key() == EXPECTED_DEPLOYER)]`), or require that this instruction be invoked atomically in the same transaction/CPI as program deployment so it cannot be front-run, consistent with the reported recommendation to restrict `setIDOLContract()`-style one-time setters to the deployer only.

### Proof of Concept
1. Attacker observes a new marginfi program deployment (or upgrade adding this instruction) on-chain.
2. Attacker derives the deterministic `FeeState` PDA using `FEE_STATE_SEED` and the program ID — no privileged information needed. [3](#0-2) 
3. Attacker submits `init_global_fee_state(admin=attacker, fee_wallet=attacker, ...)` before the legitimate deployer's transaction lands, using only their own signature. [10](#0-9) 
4. `FeeState.global_fee_admin` and `global_fee_wallet` are now permanently controlled by the attacker; legitimate deployer's later attempt to `init_global_fee_state` fails (`init` constraint — account already exists) and `edit_global_fee_state` is now gated behind the attacker's signature via `has_one = global_fee_admin`. [11](#0-10)
