### Title
Deleting a multisig member does not purge that member's confirmations on other pending requests, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in `multisig2/src/lib.rs` only removes requests that were *created* by the removed member; it never scrubs that member's entries out of the `confirmations` sets of requests created by other members. Since `confirm()` counts confirmations purely by set size against `num_confirmations`, a confirmation cast by a member who has since been deleted still counts toward reaching the threshold, letting a request execute with fewer than `num_confirmations` *currently authorized* signers.

### Finding Description
`confirm()` only checks whether the confirming caller is a current member (`current_member()` via `assert_valid_request`) at the moment it adds *its own* confirmation; it never re-validates the already-stored confirmations in the `HashSet<String>` before comparing `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

When a member is removed via the `DeleteMember` action, `delete_member` deletes only the requests whose *creator* (`r.member`) equals the removed member, and clears confirmations solely for those requests: [2](#0-1) 

It does not scan `self.confirmations` for entries keyed by the removed member's `to_string()` on requests created by *other* members. Any such stale confirmation remains in storage and is still counted the next time `confirm()` is called on that request.

Binding that should hold: `count(confirmations for request R) == count(confirmations from accounts that are still in self.members)`. After a `DeleteMember` action, this equality breaks for any request R that (a) was not created by the removed member and (b) was previously confirmed by the removed member — the stored count now exceeds the count of confirmations from currently authorized members.

### Impact Explanation
This falls under "a multisig request executed below threshold" (Critical, per the custody-binding categories for this scope): a transfer, `AddKey`, `DeployContract`, or `FunctionCall` request can be pushed to execution once the *stored* confirmation count reaches `num_confirmations`, even though one of the counted confirmers is no longer a member. Effectively the request executes with only `num_confirmations - 1` (or fewer, if multiple members were removed) live-member approvals, defeating the K-of-N security guarantee the contract exists to enforce (e.g., moving funds, adding a rogue full-access key, or deploying new contract code to the multisig account).

### Likelihood Explanation
No attacker privilege beyond being a former (now-removed) member is required, and no special preconditions beyond normal, expected contract usage are needed:
1. Member M (any legitimate member, e.g. one whose key is later rotated out) confirms a pending request R created by another member.
2. Before R accumulates the full threshold, the multisig (via a separate, legitimate `DeleteMember` request) removes M — a completely ordinary key-rotation/off-boarding action.
3. R still shows M's stale confirmation in `self.confirmations`, counting toward the threshold.
4. One more confirmation from a remaining live member on R reaches `num_confirmations` and triggers execution, even though only `num_confirmations - 1` *currently valid* members actually approved.

This requires no privileged/owner-only action beyond normal multisig operation (member removal is a designed feature), and is reachable purely through the documented request/confirm/delete-member flow.

### Recommendation
When executing `DeleteMember`, iterate over all outstanding requests' confirmation sets (not just requests created by the removed member) and remove any confirmation entry matching the removed member's identity. Alternatively, when tallying confirmations in `confirm()`, filter/re-validate the stored `HashSet<String>` against `self.members` before comparing against `num_confirmations`, so stale confirmations from removed members never count toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `B` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account) — `R.member == B`. [3](#0-2) 
3. `D` calls `confirm(R)` — `confirmations[R] = {D}` (1 confirmation, threshold not reached). [1](#0-0) 
4. Separately, members confirm and execute a `DeleteMember { member: D }` request (a normal governance action, e.g. because D's key is being rotated). `delete_member` only inspects requests where `r.member == D` (i.e., requests *created* by D) — since `R` was created by `B`, `R`'s confirmation set is untouched; `D`'s stale confirmation for `R` remains. [2](#0-1) 
5. Now only `A, B, C` are members (3 total), and `num_confirmations` is still 3. `C` calls `confirm(R)`. `confirmations[R].len()` is `1` (from stale D) `+ 1` (C) `= 2`, `2 + 1 >= 3` is true, so `execute_request` fires and `R` (the `Transfer`) executes — even though it was approved by only 2 live members (`B` implicitly as creator is not itself a confirmer, and `C`), one fewer than the configured 3-of-4/3-of-3 threshold. [4](#0-3)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
