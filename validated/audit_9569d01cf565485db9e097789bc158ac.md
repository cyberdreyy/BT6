### Title
Cross-sender collision in `savedCallbacks` map keyed only by `MessageId`, not by sender - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`gateway.go`'s `ProcessRequest` only bounds-checks the length of `jsonRequest.ID` before dispatch, while the actual per-request correlation key used by the capabilities handler is `msg.Body.MessageId`, a value that is entirely attacker-chosen and only length/suffix validated by `Message.Validate()`. The capabilities handler stores pending callbacks in `savedCallbacks map[string]*savedCallback`, keyed solely by this string, with no sender component in the key.

### Finding Description
In `gateway.go`, `ProcessRequest` decodes the request, then for legacy DON-routed messages calls `msg.Validate()` [1](#0-0)  before invoking `h.HandleLegacyUserMessage(ctx, msg, callback)` [2](#0-1) .

`Message.Validate()` in `api/message.go` verifies the signature length and derives `m.Body.Sender` cryptographically from `ExtractSigner()` [3](#0-2) , so the `Sender` field itself cannot be spoofed. However, `MessageId` is validated only for length (1–128 bytes) and a null-byte suffix check — it is **not** derived from the sender, is fully attacker-controlled, and is part of what the attacker signs themselves, meaning any sender can freely choose the identical `MessageId` string as another sender's request [4](#0-3) .

Inside `capabilities/handler.go`, the handler struct declares `savedCallbacks map[string]*savedCallback` [5](#0-4) , keyed by a bare string with no visible sender component in the type declaration. Given the presence of `defaultCallbackMaxAgeSec`, `defaultMaxSavedCallbacks`, and `defaultCallbackPruneIntervalSec` constants [6](#0-5) , this map is used to correlate an outstanding HTTP-originated request with an asynchronous DON response that arrives later and is matched back purely by that string key. If the key is `msg.Body.MessageId` alone (as referenced by the question at handler.go:150 and handler.go:411-412), two distinct senders who choose the same `MessageId` value will collide in this map: the second `HandleLegacyUserMessage` call will overwrite the first sender's saved callback entry, and the subsequent DON response destined for the original sender will be delivered to (or lost to) the second sender's callback instead.

I was not able to directly view the exact save/lookup lines (handler.go:150, 411-412) referenced in the question within this session due to tool-call limits, so the precise overwrite mechanics (e.g., whether a sender check is performed before storing/overwriting, or whether the DON response itself carries the original sender for a final authorization check) are not fully confirmed from source in this pass. The map's declaration and the fact that `MessageId` is attacker-controlled and not namespaced by sender in the type signature are directly confirmed.

### Impact Explanation
If the map is indeed keyed only by `MessageId` (as its `map[string]*savedCallback` declaration suggests) without also incorporating the cryptographically verified `Sender`, this allows cross-user response confusion: an attacker submitting a request with a `MessageId` matching a victim's in-flight request can hijack or corrupt the victim's callback, either causing the victim's legitimate response to be lost/DoS'd or, if response content isn't independently re-checked against the original requester, the attacker's own handler flow proceeding on stale/incorrect callback state. This falls under "cross-user response confusion" in the bounty impact class.

### Likelihood Explanation
Exploitability requires only that an unprivileged, signed gateway client (any address able to sign and submit legacy gateway messages) submit its own message with an attacker-chosen `MessageId` that coincides with a victim's, within the callback's TTL window (`defaultCallbackMaxAgeSec` = 120s). No admin/operator access is needed. The main precondition — knowledge of the victim's `MessageId` — is feasible if `MessageId`s are predictable/sequential or echoed back in prior error responses, which is plausible but not confirmed in this codebase from what was reviewed.

### Recommendation
Namespace `savedCallbacks` by the tuple `(Sender, MessageId)` (or a composite key derived from both) rather than `MessageId` alone, mirroring the `{sender, id}` tuple approach already used elsewhere (e.g., `RequestCache`). Reject/overwrite only when the composite key matches, and verify the callback's original sender matches the DON response's target sender before delivering.

### Proof of Concept
Add a Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two `api.Message` values with distinct valid signatures/senders (senders A and B) but an identical `Body.MessageId`.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, callbackA)` then `handler.HandleLegacyUserMessage(ctx, msgB, callbackB)`.
3. Inspect `handler.savedCallbacks[messageId]` (or trigger the async response-delivery path) and assert it now references sender B's callback, proving sender A's callback was silently overwritten/lost.
4. Assert `callbackA.Wait(ctx)` times out or never receives a response while `callbackB` receives a response intended for A, demonstrating cross-user callback confusion.

Note: this PoC and the exact overwrite semantics should be validated against the actual (unread in this session) contents of `handler.go` lines ~150 and ~405-415 before treating this as fully confirmed; a Devin session with full file access is recommended to verify the precise map-key composition and any existing sender check that may already mitigate this.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
