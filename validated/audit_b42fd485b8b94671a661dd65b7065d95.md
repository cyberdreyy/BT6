### Title
External initiator credential holder can trigger arbitrary integer-ID job runs by inheriting UserRoleRun identity - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates integer-ID job runs solely on `_, isUser := auth.GetAuthenticatedUser(c)` returning `true`, without distinguishing the authentication method that produced the session-user object. `AuthenticateExternalInitiator` in `core/web/auth/auth.go` deliberately stores a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` under the same `SessionUserKey` used by real session/token-authenticated users, so an EI credential holder satisfies `isUser==true` identically to a genuine run-role human user.

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) authenticates a request using only `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers against `bridges.ExternalInitiator` records, and then explicitly does:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [1](#0-0) 

This stores a fabricated `clsessions.User` under the exact same context key (`SessionUserKey`) used by `AuthenticateBySession` and `AuthenticateByToken` for real users. [2](#0-1) [3](#0-2) 

`GetAuthenticatedUser` simply reads that key and type-asserts to `*clsessions.User`, with no way to tell which `authMethod` populated it:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
}
``` [4](#0-3) 

`PipelineRunsController.Create` then uses this ambiguous signal to gate the int-ID run path, with a comment that directly contradicts the actual behavior:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
	...
	jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
	...
}
``` [5](#0-4) 

Because `isUser` is `true` for both a real run-role user and an EI-authenticated request, the "EIs not allowed" comment is not enforced by the code — the check cannot distinguish the two identities. The root cause is that `AuthenticateExternalInitiator` conflates the EI identity with the human-user identity by writing into the same `SessionUserKey`/`clsessions.User` representation instead of a distinct type or a marker that `Create` could check (e.g., by additionally checking `GetAuthenticatedExternalInitiator` and rejecting if present, which it does not).

### Impact Explanation
An external-initiator (EI) credential holder — a lower-privilege, narrowly-scoped credential intended only to notify job runs for the EI's own bridge/webhook jobs — can invoke `POST /v2/jobs/:ID/runs` with any integer job ID and trigger `prc.App.RunJobV2`, running arbitrary jobs on the node identical to a human run-role user. This matches the "unauthorized job run" impact class: an attacker with only EI credentials gains job-run capability beyond bridge/webhook use, potentially triggering jobs that move funds, submit transactions, or consume node resources, without ever holding a real user session or role.

### Likelihood Explanation
Preconditions are minimal: possession of a single valid EI access key/secret pair (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`), which is a lower-trust credential than a full user session/API token. No admin, DB, or operator access is required. The vulnerable code path (`Create`) is reachable directly via the documented `POST /v2/jobs/:ID/runs` route, and the check is a simple boolean with no distinguishing logic, making exploitation deterministic and repeatable for any int32 job ID on the node.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests where the external-initiator identity is set, e.g. check `if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI { reject }` before/alongside `isUser`, or have `AuthenticateExternalInitiator` set a distinct context key/type (not reusing `clsessions.User`/`SessionUserKey`) so `GetAuthenticatedUser` genuinely only returns human-authenticated users. Route registration should also be reviewed to ensure `/v2/jobs/:ID/runs` for int IDs is not wrapped with the `AuthenticateExternalInitiator` method at all if EI access to this endpoint is unintended.

### Proof of Concept
Go handler-level integration test plan (in `core/web/pipeline_runs_controller_test.go` style):
1. Set up an app with a job having a small int32 `jobSpec.ID` (a job type not requiring webhook UUID).
2. Create a valid `bridges.ExternalInitiator` record with known access key/secret via the test ORM.
3. Send `POST /v2/jobs/<intID>/runs` with headers `X-Chainlink-EA-AccessKey` and `X-Chainlink-EA-Secret` set to the EI's credentials, and no session cookie or `X-API-KEY`/`X-API-SECRET`.
4. Assert response status is `200 OK` (or whatever `RunJobV2` success returns) and a `pipelineRun` resource is returned, identical to what a run-role user session would receive for the same request — demonstrating that `isUser` was `true` purely from EI auth, and `RunJobV2` executed with the EI's implicit `UserRoleRun` identity.
5. Compare with a table test using a real run-role user session, asserting response shape parity, confirming cross-identity confusion at `auth.GetAuthenticatedUser(c)`.
