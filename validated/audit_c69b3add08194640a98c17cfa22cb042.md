### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations` threshold - ([File: multisig2/src/lib.rs])

### Summary
`DeleteMember` in `MultiSigContract::delete_member` only purges confirmations for requests that were *originated* by the removed member, but does not purge any confirmations the removed member had already cast on requests originated by *other* members. Those stale confirmations remain in the `confirmations` set and continue to count toward the `num_confirmations` threshold check in `confirm()`, allowing a request to execute with fewer live-member approvals than the configured threshold.

### Finding Description
`confirm()` counts confirmations from a `HashSet<String>` keyed by member string, comparing its length against `self.num_confirmations`: [1](#0-0) 

`delete_member()` is invoked only through `execute_request` for `MultiSigRequestAction::DeleteMember`, and it removes outstanding *requests* filtered by `r.member == member` (i.e., requests the removed member originated), decrementing `num_requests_pk` and removing the member's access key, but never scans `self.confirmations` to strip the removed member's entries from requests originated by someone else: [2](#0-1) 

Because `confirmations` is a `HashSet<String>` of member identity strings rather than a live reference validated against current membership at tally time, the binding "confirmations counted == confirmations from currently-live members" is broken: `confirmations.len()` can include entries from accounts/keys that are no longer members. `current_member()` is only used to identify the *caller* confirming, not to re-validate the historical set: [3](#0-2) 

### Impact Explanation
This lets a request execute (e.g. `Transfer`, `AddKey` with a full-access key, `AddMember`, `FunctionCall`) below the true current confirmation threshold, since a removed member's earlier vote still counts. This directly maps to the rules' explicit custody boundary: "confirmations counted versus live members." A multisig configured for k-of-n can be satisfied with fewer than k live signers, enabling a minority (or a single remaining signer colluding with the residual confirmation of an ex-member) to move funds or add a full-access key that bypasses the multisig entirely — a Critical impact ("a multisig request executed below threshold").

### Likelihood Explanation
Requires only ordinary contract usage: (1) a request is created and gets a confirmation from member B, (2) before the confirmations reach threshold, the members vote to remove B via `DeleteMember` (a normal governance action, not requiring any special privilege beyond normal multisig operation), (3) the remaining members confirm the same request. B's confirmation is still counted. This is a realistic operational sequence (e.g., revoking a compromised or departing key while a pending request exists) and requires no attacker-controlled deployment or foundation privilege — any set of members operating the multisig normally can trigger it, intentionally or not.

### Recommendation
When deleting a member, also iterate `self.confirmations` (or maintain an index from member → request_ids they confirmed) and remove the member's entry from every request's confirmation set, not just requests they originated. Alternatively, revalidate confirmations against current membership at tally time in `confirm()`/`execute_request`, filtering out confirmers who are no longer in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig with members `[A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request(Transfer{...})` → request_id 0 (member=A).
3. `B` calls `confirm(0)` → confirmations = `{A, B}`... wait, `confirm` requires exactly threshold check `len()+1 >= num_confirmations`; after A's implicit add via `add_request_and_confirm` or a second confirm, assume confirmations = `{B}` only (A didn't auto-confirm via `add_request`).
4. Before reaching threshold, members execute a `DeleteMember{member: B}` request (via normal 2-of-3 confirmation from A and C). `delete_member` removes B's access key/account and any requests B *originated*, but request 0 (originated by A) still has confirmations `{B}`.
5. `C` calls `confirm(0)`. `current_member()` returns C (still a live member), `confirmations.len() == 1` (contains stale `B`), so `1 + 1 >= 2` → threshold met and `execute_request` runs the `Transfer`, even though only `A` (originator, uncounted) and `C` are live confirmers — B, whose vote is counted, is no longer a member.

This demonstrates execution with only one *currently valid* confirming member's vote, contrary to the configured 2-of-N threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Returns current member: either predecessor as account or if it's the same as current account - signer.
    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()
                    .unwrap_or_else(|_| env::panic_str("Failed to deserialize public key")),
            }
        } else {
            MultisigMember::Account {
                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
