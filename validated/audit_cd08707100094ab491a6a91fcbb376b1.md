### Title
Post-default withdraw requests are paid at par from the default recovery reserve, draining the haircuted reserve owed to defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class is an extraction filter that applies an in-scope operation (claim/payout) to targets outside the funded boundary. The analog is in `IdleCreditVault`: after `finalizeDefaultRecovery`, the reserve `defaultRecoveryReserve` is sized as `recoveryPrice * totalBasis`, but `_claimPostDefaultWithdrawRequest` pays new post-default receipts 1:1 out of that same reserve. Each post-default claim consumes `1 / recoveryPrice` times its accounted share, so the reserve is exhausted early and defaulted-epoch claimants' `_transferDefaultRecovery` calls revert permanently.

### Finding Description
`finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` and sets `defaultRecoveryReserve = reserveAmount`, where `totalBasis` covers only the pre-default active basis and defaulted receipts. [1](#0-0) 

After finalization, `requestWithdraw` takes the post-default branch: it burns CDO strategy tokens, mints receipt tokens to the user, and records `postDefaultRequests[_user] = _amount` without adding any backing to the reserve. [2](#0-1) 

`claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest`, which burns the receipt and calls `_transferDefaultRecovery(_user, amount)` at the full `_amount` (par), decrementing `defaultRecoveryReserve` by the unhaircuted amount. [3](#0-2) [4](#0-3) 

The reserve was only funded with `recoveryPrice` per unit of defaulted basis. When `recoveryPrice < RECOVERY_FULL` (the normal partial-recovery default), paying post-default claims at par consumes the reserve faster than it was provisioned. Once `defaultRecoveryReserve` (or the underlying balance backing it) is depleted, remaining defaulted-epoch claims via `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` underflow on `defaultRecoveryReserve -= _amount` or fail the transfer, permanently freezing their recovery. [5](#0-4) [6](#0-5) 

The comment at line 253 claims post-default amounts are "already-haircut" because finalization lowered `virtualPrice`. That only makes the receipt economically fair relative to active LPs — it does not add underlying to the reserve, and the reserve is the sole source of the payout.

### Impact Explanation
Direct theft of unclaimed yield plus permanent freezing. In a hard default with `recoveryPrice = r < 1`, every post-default withdraw claim of `X` removes `X` from a reserve provisioned at `r` per unit of defaulted basis. Post-default withdrawers recover strictly more per unit of basis than defaulted-epoch claimants, and once cumulative post-default claims exceed `(reserveAmount - unclaimed defaulted payouts) / 1`, subsequent defaulted claims revert (underflow or failed `safeTransfer`), permanently freezing their recovery share. Loss is bounded by `reserveAmount * (1 - r) / r`-equivalents shifted to early post-default claimants.

### Likelihood Explanation
Requires a borrower default followed by `finalizeDefault` (privileged but honest flow — attacker only sequences around it). After finalization, any KYC-passed lender holding tranche tokens can trigger `requestWithdraw` post-default and claim at par before defaulted-epoch receipt holders claim. No special timing is needed beyond claiming before the reserve drains; the first movers are systematically advantaged, which is exactly the unfair-payment condition.

### Recommendation
Do not pay `postDefaultRequests` from `defaultRecoveryReserve`. Either (a) fund post-default payouts from a separately accounted bucket sourced from the burned CDO strategy-token backing (e.g., add `_amount` equivalent underlying at request time, or track `postDefaultReserve` incremented at request), or (b) apply `defaultRecoveryPrice` to post-default claims as well so every claim consumes reserve at the same per-basis rate. Alternatively, price post-default receipts through `defaultRecoveryPrice` at claim time inside `_claimPostDefaultWithdrawRequest` (`amount * defaultRecoveryPrice / RECOVERY_FULL`) so reserve consumption matches provisioning.

```solidity
function testPostDefaultClaimDrainsRecoveryReserve() external {
    // 1. Alice deposits AA, epoch starts, Alice requests withdraw (defaults-epoch receipt).
    // 2. Bob deposits AA and keeps tranche tokens (no request).
    // 3. Warp past epochEndDate; owner calls cdoEpoch.stopEpoch(0,0) -> defaulted.
    // 4. Manager calls cdoEpoch.finalizeDefault(recovered, manager) with recovered < basis
    //    => defaultRecoveryPrice = r < 1e18.
    // 5. Bob calls cdoEpoch.requestWithdraw(amount, AATranche) -> postDefaultRequests[bob] = amount.
    // 6. Bob calls claimWithdrawRequest() -> receives `amount` at par from defaultRecoveryReserve.
    // 7. Repeat with enough post-default requests until reserve < Alice's haircut claim.
    // 8. Alice calls claimWithdrawRequest() -> reverts (reserve underflow / failed transfer).
    // Assert: bobReceived == amount (par) while aliceClaim reverts, although
    // aliceBasis * r was provisioned for her.
}
```

Key assertion: `underlying.balanceOf(bob)` increases by the full requested amount while `strategy.defaultRecoveryReserve()` drops by that same unhaircuted amount, and Alice's `claimWithdrawRequest()` reverts despite holding a valid defaulted-epoch receipt in `withdrawsRequestsByEpoch[alice][defaultRecoveryEpoch]`.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }
