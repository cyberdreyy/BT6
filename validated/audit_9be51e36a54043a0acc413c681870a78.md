### Title
EI-authenticated pseudo-users bypass the "EIs not allowed" check in `PipelineRunsController.Create`, enabling arbitrary int32 job-run triggering - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` sets `SessionUserKey` to a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` (no Email/ID) whenever valid EI credentials are presented. `PipelineRunsController.Create` gates job-run triggering with `_, isUser := auth.GetAuthenticatedUser(c)`, which only checks presence of a `*User` in context, not whether the requester is a real user or an EI-derived pseudo-user, so the comment "only users are allowed to run jobs using int IDs - EIs not allowed" is not actually enforced.

### Finding Description
The `userOrEI` route group wraps `POST /v2/jobs/:ID/runs` with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` and `auth.RequiresRunRole`: [1](#0-0) 

`AuthenticateExternalInitiator` validates EI access-key/secret and, on success, stores both `SessionExternalInitiatorKey` and a fabricated `SessionUserKey` value with role `run`: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, which passes for this synthetic EI role-run user, so the request reaches `PipelineRunsController.Create`: [3](#0-2) 

Inside `Create`, the code calls `auth.GetAuthenticatedUser(c)`, which simply type-asserts whatever is stored under `SessionUserKey` — it does not distinguish a genuine session/token user from the EI-injected pseudo-user, and does not check `GetAuthenticatedExternalInitiator` to reject EI callers: [4](#0-3) [5](#0-4) 

As a result, `isUser` evaluates `true` for EI credential holders even though the comment states "EIs not allowed", and the handler proceeds to parse the attacker-supplied `:ID` path parameter as an arbitrary `int32` job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` with zero ownership/initiator-to-job binding check — any int32 job ID is accepted regardless of job type (OCR, VRF, direct-request, etc.) or which EI (if any) is associated with it.

However, `RunJobV2` itself contains a build-time gate: [6](#0-5) 
`if build.IsProd() { return 0, errors.New("manual job runs not supported on secure builds") }`. This check is unconditional of caller identity — it blocks all callers (legitimate users included) from triggering manual runs via this path on secure/production builds, not just EI-derived callers. I was unable to locate the `build` package definition/`IsProd()` implementation in the indexed context, so I cannot confirm exactly which build configurations satisfy `IsProd()` (e.g., official release binaries vs. dev builds), but its existence indicates this whole code path (for both real users and EI callers) is intentionally disabled in production-grade builds.

### Impact Explanation
On builds where `build.IsProd()` is false (non-secure/dev builds), an EI credential holder can trigger `RunJobV2` against any int32 job ID node-wide — including jobs unrelated to that EI, jobs of other tenants/job types (OCR, VRF, keeper/DR, etc.) — resulting in unauthorized job-run execution outside the EI's intended scope (webhook-triggered runs, which have since been removed as a job type per the UUID-rejection branch in `Create`). This matches an authorization-bypass / unauthorized-action class (cross-privilege job run triggering) but its real-world severity is capped because the same function unconditionally refuses to run on secure/production builds regardless of caller, which appears to be the primary control preventing this from affecting production nodes.

### Likelihood Explanation
Requires only valid EI credentials (access key + secret), no operator/admin access — matches the "unprivileged attacker: external-initiator credential holder" threat model. Exploitability is fully gated by whether the target node is a "secure"/production build; if `build.IsProd()` returns true (which appears to be the expectation for deployed production Chainlink nodes), the request always fails with "manual job runs not supported on secure builds" regardless of the `isUser`/EI confusion, neutralizing the bug in the primary deployment target. On non-production builds (e.g., local/dev/test toggles), the bypass is trivially and repeatably reproducible with any valid EI credential and any known int32 job ID.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated via `AuthenticateExternalInitiator` by checking `auth.GetAuthenticatedExternalInitiator(c)` and rejecting if present (or by checking a per-request flag distinguishing "real user" vs. "EI pseudo-user"), rather than relying solely on `GetAuthenticatedUser`, which cannot differentiate the two. This restores the documented invariant "only users are allowed to run jobs using int IDs - EIs not allowed" independent of the `build.IsProd()` gate in `RunJobV2`.

### Proof of Concept
Handler-level integration test plan (Go):
1. Start a `cltest.TestApplication` in a non-prod build configuration (as done in existing tests, e.g. `core/web/pipeline_runs_controller_test.go`).
2. Create an `ExternalInitiator` via `bridges.NewExternalInitiator` and persist via ORM (`app.BridgeORM().CreateExternalInitiator`), and separately create/insert a job (e.g., an OCR job as in `setupPipelineRunsControllerTests`) with ID `jobID`, unrelated to the EI.
3. Build an HTTP client that sets `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`) instead of session/API-token headers.
4. POST to `/v2/jobs/<jobID>/runs` with these EI headers only.
5. Assert the response is `200 OK` with a `pipelineRun` resource returned (i.e., `RunJobV2` was invoked and succeeded), demonstrating that `isUser` passed and `RunJobV2` executed for the arbitrary job despite no EI-to-job relationship — proving the "EIs not allowed" invariant is not enforced in code (mock `Application.RunJobV2` and assert it was called with `jobID` and the EI's synthetic context, per the existing mock helper `Application_RunJobV2_Call` in `core/internal/mocks/application.go`).

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
