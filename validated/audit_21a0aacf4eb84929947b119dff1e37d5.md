### Title
`mark_tenure_superseded` overwrite-by-primary-key discards an earlier valid reorg permit, wedging the signer against a canonical chain it already sanctioned - (File: stacks-signer/src/signerdb.rs)

### Summary
The `superseded_tenures` table keys a reorg permit by `consensus_hash` (of the *superseded* tenure) only, and `SignerDb::mark_tenure_superseded` writes with `INSERT OR REPLACE`. If two different later tenures each legitimately sanction a reorg of the same earlier tenure, the second permit silently overwrites the first, exactly like `PrePOMarketFactory`'s salt collision overwriting `_deployedMarkets[_salt]`. The permit lookup used by `get_signed_conflicts`/`Signer::reorg_permit_stands` then only ever sees the *latest* permitting sortition, even if that one is later orphaned by a burn fork while the *earlier* permit's sortition becomes canonical again.

### Finding Description
`CREATE_SUPERSEDED_TENURES_TABLE` defines `consensus_hash TEXT PRIMARY KEY` for the superseded tenure, and stores only the single latest permitting tenure (`superseded_by_consensus_hash`, `superseded_by_burn_block_hash`): [1](#0-0) 

`mark_tenure_superseded` performs an unconditional `INSERT OR REPLACE` keyed only on the superseded tenure's `consensus_hash`, and its own doc-comment concedes: "A re-permit by a different tenure replaces the record, so the latest permitting sortition is the one checked": [2](#0-1) 

The permit is only recorded once `check_parent_tenure_choice` has *fully* validated a reorg (every reorged tenure passed the rules), so any single call to `record_superseded_tenure` is legitimate at write time: [3](#0-2) 

`get_signed_conflicts` joins `blocks` against `superseded_tenures` on `consensus_hash` and surfaces only the single stored `superseded_by_*` pair for the caller (`Signer::reorg_permit_stands`) to check liveness of that one permitting sortition against the node: [4](#0-3) 

Reachable sequence with a single miner slot plus ordinary burnchain forking (no majority-signer collusion required):
1. Tenure `T1` mines a block; the signer signs it (`signed_self`/`signed_group` set).
2. Sortition `S_A` wins, builds off an ancestor before `T1` (reorging `T1`), passes `first_proposal_burn_block_timing` timing rules, and the signer records `superseded_tenures[T1] = S_A`. From now on, a signature over `T1`'s block is excluded from conflict checks as long as `S_A`'s sortition is canonical.
3. A Bitcoin fork orphans `S_A` (a normal, permissionless burnchain event, not requiring signer majority).
4. The same or a different single miner wins a new sortition `S_B` on the surviving branch, which — because `S_A` is now gone — again has to build off the ancestor before `T1`, again reorging `T1`, again legitimately passing the timing checks. The signer overwrites `superseded_tenures[T1] = S_B`, discarding the `S_A` record entirely.
5. The Bitcoin chain forks again, this time re-orphaning `S_B` and restoring `S_A`'s branch as canonical (chain-tip flips are ordinary Bitcoin behavior, no signer collusion needed).
6. The signer now evaluates whether `T1`'s old signed block still conflicts with a new proposal. It queries `superseded_tenures[T1]`, gets `S_B` (not `S_A`), and asks the node whether `S_B`'s sortition is canonical. It is not (step 5 orphaned it), so `reorg_permit_stands` returns false: the permit is treated as *not standing*, even though the original permit (`S_A`, now canonical again) unambiguously sanctioned exactly this replacement.
7. The stale, now-conflicting signature over `T1`'s block is resurrected as a live conflict against the currently-canonical chain built on `S_A`, even though the signer already sanctioned removing it.

### Impact Explanation
This breaks the intended equality "a sanctioned reorg's conflict-suppression holds for as long as *some* legitimately-permitting canonical sortition exists," because the single-row-per-key design can only remember the *most recent* permit, not the set of all permits ever legitimately granted. The consequence is a signer that refuses to sign new, valid, canonical blocks because it believes an already-sanctioned old signature still conflicts — a liveness wedge on the affected signer against a chain state it previously and correctly approved reorging. Per the stated impact classes, this maps to "a signer wedged into never signing valid blocks... or losing the equivocation guard" (the equivocation-avoidance bookkeeping itself becomes stale/wrong).

### Likelihood Explanation
The trigger only needs ordinary burnchain re-org activity (which requires no majority-signer collusion, no auth token, no other signer's key) plus two natural reorg-timing-eligible tenure transitions around the same superseded tenure — a scenario the codebase's own reorg-permit design anticipates handling (`first_proposal_burn_block_timing`, `MAX_FORK_DEPTH` pruning) but does not defend against for the *overwrite* case specifically. It requires a double burnchain flip-flop, which is not common but is fully within the permissionless, single-miner-triggerable threat model assumed by this scan.

### Recommendation
Do not use `consensus_hash` (of the superseded tenure) alone as the primary key for `superseded_tenures`. Instead, store permits keyed by `(consensus_hash, superseded_by_consensus_hash)` so multiple historical permits for the same superseded tenure are retained, and have `get_signed_conflicts`/`reorg_permit_stands` check *all* retained permits for that tenure, treating the conflict as suppressed if *any* recorded permitting sortition is currently canonical, rather than only the most-recently-written one.

### Proof of Concept
1. Sign block `B1` in tenure `T1` (sets `signed_self`).
2. Call `check_parent_tenure_choice` for sortition `S_A` that reorgs `T1` within the timing window → `mark_tenure_superseded(T1, h1, S_A, burn_hash_A)` is invoked, storing `superseded_tenures[T1] = S_A`.
3. Call `check_parent_tenure_choice` again for a different sortition `S_B` that also legitimately reorgs `T1` within the timing window → `mark_tenure_superseded(T1, h1, S_B, burn_hash_B)` runs `INSERT OR REPLACE`, overwriting the row so `superseded_tenures[T1] = S_B` only.
4. Simulate the node reporting `S_B`'s sortition as no longer canonical (orphaned) while `S_A`'s sortition is canonical again.
5. Call `get_signed_conflicts` for a height ≥ `B1`'s height; the joined row for `B1` returns `superseded_by_consensus_hash = S_B`, and `Signer::reorg_permit_stands` queries the node about `S_B`, finding it non-canonical, so the permit is reported as not standing — despite `S_A`'s permit (now discarded from the table) being valid and canonical, reproducing the loss of the original entry seen in the `PrePOMarketFactory` salt-collision report.

static CREATE_SUPERSEDED_TENURES_TABLE: &str = r#"
CREATE TABLE IF NOT EXISTS superseded_tenures (
    -- consensus hash of a tenure that a later tenure was permitted to reorg. Its sortition is
    -- still canonical -- unlike an orphaned tenure -- but the reorg rules
    -- (`first_proposal_burn_block_timing`) sanctioned replacing the blocks it built, so a
    -- signature we put over one of them must not stand in the way of that replacement.
    consensus_hash TEXT PRIMARY KEY,
    -- burn block height of the superseded tenure's sortition, used to age the record out
    burn_block_height INTEGER NOT NULL,
    -- consensus hash of the tenure that was permitted to do the reorg. The permit only means
    -- anything while this tenure's sortition is still canonical: if a burnchain fork orphans
    -- it, the reorg we sanctioned can no longer happen and the record stops excluding the
    -- superseded tenure's blocks from conflict checks.
    superseded_by_consensus_hash TEXT NOT NULL,
    -- burn block hash of the permitting tenure's sortition, used to ask the node whether that
    -- sortition is still canonical
    superseded_by_burn_block_hash TEXT NOT NULL,
    -- epoch seconds at which we permitted the reorg
    superseded_at INTEGER NOT NULL
) STRICT;"#;

    /// permitting tenure's sortition (`superseded_by_*`): the permit only holds while that
    /// sortition is canonical, which the caller derives from the node per evaluation (see
    /// `Signer::reorg_permit_stands`) -- like every other question about whether a conflict is

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,

            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash

                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";

            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];

    /// The permit is only honored while the permitting tenure's sortition is still canonical
    /// (checked against the node when the record is applied): if a burnchain fork orphans it,
    /// the reorg we sanctioned can no longer happen, so the record must not keep suppressing
    /// this tenure's conflicts. A re-permit by a different tenure replaces the record, so the
    /// latest permitting sortition is the one checked. Records age out via
    /// [`SignerDb::prune_superseded_tenures`].
    pub fn mark_tenure_superseded(
        &mut self,
        consensus_hash: &ConsensusHash,
        burn_block_height: u64,
        superseded_by_consensus_hash: &ConsensusHash,
        superseded_by_burn_block_hash: &BurnchainHeaderHash,
    ) -> Result<(), DBError> {
        self.db.execute(
            "INSERT OR REPLACE INTO superseded_tenures (consensus_hash, burn_block_height, superseded_by_consensus_hash, superseded_by_burn_block_hash, superseded_at) VALUES (?1, ?2, ?3, ?4, ?5)",
            params![
                consensus_hash,
                u64_to_sql(burn_block_height)?,
                superseded_by_consensus_hash,
                superseded_by_burn_block_hash,
                u64_to_sql(get_epoch_time_secs())?
            ],
        )?;
        Ok(())
    }
