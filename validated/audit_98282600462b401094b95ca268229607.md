### Title
Instant-withdraw claim never clears `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, so already-paid receipts are re-counted in `defaultPendingClaimBasis` and dilute `defaultRecoveryPrice` — ([contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The CVE bug class is "a clear-credentials operation that silently fails to clear, leaving stale state to be reused by later operations that should not see it." The analog lives in `claimInstantWithdrawRequest`: when a user claims their funded instant-withdraw receipt, the per-user aggregate `instantWithdrawsRequests[_user]` is zeroed, but the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and the epoch total `instantWithdrawClaimsByEpoch[epoch]` are never decremented. Later, if the borrower defaults in that same epoch while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis()` adds the stale `instantWithdrawClaimsByEpoch[epochNumber]` — including claims that were already paid out — into the recovery basis used by `finalizeDefaultRecovery` to compute `defaultRecoveryPrice`. The recovery pool is then spread across ghost claims, permanently underpaying the real remaining claimants and trapping the excess as reserve dust.

### Finding Description
The claim path only clears the per-user aggregate:

`contracts/strategies/idle/IdleCreditVault.sol` (lines ~380–393)
```solidity
function claimInstantWithdrawRequest(address _user) external {
  _onlyIdleCDO();
  if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);
  }
  uint256 amount = instantWithdrawsRequests[_user];
  _burn(_user, amount);
  instantWithdrawsRequests[_user] = 0;          // cleared
  _transferFundedClaim(_user, amount);
  // instantWithdrawsRequestsByEpoch[_user][epoch] — NOT cleared
  // instantWithdrawClaimsByEpoch[epoch]          — NOT decremented
}
```

Compare with `requestInstantWithdraw`, which populates all three structures (lines ~366–374):
```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

`collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` as cash arrives, but `instantWithdrawClaimsByEpoch` keeps the full *request* basis. The default-recovery path then consumes that stale total:

`defaultPendingClaimBasis` (lines ~644–649):
```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber]; // includes already-claimed receipts
}
```

`finalizeDefaultRecovery` (lines ~679–692) divides the actual reserve by this inflated `totalBasis`, so `recoveryPrice = reserveAmount * 1e18 / totalBasis` is too low. The claimed-out funds counted in the basis have no corresponding reserve backing, so each honest claimaint's `claimBasis * defaultRecoveryPrice` payout is haircut below the intended recovery ratio, and the surplus never becomes payable — it sits as unclaimable recovery dust in `defaultRecoveryReserve`.

### Impact Explanation
Direct theft of default-recovery proceeds and permanent freezing of part of the reserve. With `C` claimed instant receipts in the default epoch, outstanding instant basis `O`, and pending basis `P`, the recovery price is computed over `P + C + O` while the reserve only covers `P + O` (roughly). Every remaining claimant (instant, queued withdrawers, and active tranche holders via the active-side basis) loses a factor of `(P+O)/(P+C+O)` of their intended recovery; the `C`-proportional share is stranded in the contract forever since no live receipt can draw it. On a real pool a malicious or even honest early claimant triggers this by simply claiming before the default, so the loss is unconditional once partial instant funding + same-epoch default occurs.

### Likelihood Explanation
Requires the sequence: epoch running → instant requests → partial `collectInstantWithdrawFunds` (borrower funds only part of the instant queue, leaving `pendingInstantWithdraws != 0`) → at least one user claims → borrower defaults in the same epoch → manager finalizes recovery. Partial instant funding followed by default is exactly the stressed scenario the recovery machinery was built for, and the claiming user needs no malicious intent — an unprivileged KYC'd lender can also deliberately claim early to dilute others' recovery. All roles involved (borrower, manager, CDO) are honest; no privileged misbehavior is needed.

### Recommendation
Mirror the per-epoch clearing used for normal requests (`_clearWithdrawClaimForEpoch`). In `claimInstantWithdrawRequest` (and the funded branch of `_claimDefaultedInstantWithdrawRequest`), decrement `instantWithdrawClaimsByEpoch[requestEpoch]` by the claimed amount and delete `instantWithdrawsRequestsByEpoch[_user][requestEpoch]`. Because the current code does not store which epoch a funded claim belongs to when `instantWithdrawsRequests` aggregates multiple epochs, either track a `lastInstantWithdrawRequestEpoch` per user (as `lastWithdrawRequest` does for normal requests) or iterate/cap the decrement against the user's recorded per-epoch entries. Add a regression test: request two instant withdrawals, partially collect, claim one, then default and assert `defaultPendingClaimBasis` only counts the outstanding receipt.

### Proof of Concept
Foundry fork test (e.g. Polygon, existing `IdleCreditVault` + `IdleCDOEpochVariant` deployment):

```solidity
function test_InstantClaimInflatesDefaultBasis() public {
  // --- epoch N running ---
  vm.startPrank(manager); cdo.startEpoch(); vm.stopPrank();

  // Alice and Bob each request instant withdraw of 100e6 USDC
  requestInstantViaCdo(alice, 100e6);
  requestInstantViaCdo(bob,   100e6);
  assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), 200e6);

  // borrower funds only half the instant queue
  fundBorrower(100e6);
  vm.prank(address(cdo)); // via stop/queue machinery
  vault.collectInstantWithdrawFunds(100e6);
  assertEq(vault.pendingInstantWithdraws(), 100e6);

  // Alice claims her funded receipt — epoch accounting is NOT cleared
  claimInstantViaCdo(alice);
  assertEq(vault.instantWithdrawsRequests(alice), 0);
  assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), 200e6); // stale

  // borrower defaults in same epoch; recovery = 100e6 (Bob's prefunded share)
  triggerDefaultAndFinalize(0 /*external recovery*/);

  // totalBasis includes Alice's already-paid 100e6 ghost claim:
  // recoveryPrice = reserve(100e6 + active) / basis(active + pending + 200e6)
  // Bob's payout = 100e6 * recoveryPrice < intended share;
  // the Alice-sized slice of the reserve is stranded as dust.
}
```

Caveat: the request/claim calls must be routed through the IdleCDO (only-CDO guard), and the exact helper `_claimDefaultedInstantWithdrawRequest` body was not fully indexed in this session — if it happens to decrement `instantWithdrawClaimsByEpoch` on defaulted-epoch claims, the inflated-basis window still exists for the funded-branch claim shown above, which is the path exercised before finalization.
