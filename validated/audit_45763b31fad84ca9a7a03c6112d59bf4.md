### Title
`setApr`/`setAprs` in `IdleCreditVault` skip caller authorization entirely while `idleCDO == address(0)` - ([File: contracts/strategies/idle/IdleCreditVault.sol:225-235])

### Summary
The external finding shows an `onlyManager` modifier that silently no-ops when `manager == address(0)`, leaving guarded functions callable by anyone. The identical anti-pattern exists in `IdleCreditVault.setApr`: the caller check is executed only when `idleCDO != address(0)`. While `idleCDO` is unset, **any** EOA can set `lastApr` (and `unscaledApr` via `setAprs`/`setAprsWithBuffer`), i.e. the fixed APR the vault uses to accrue borrower interest and mint interest to tranche holders.

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
225:  function setApr(uint256 _apr) public {
226:    address _cdo = idleCDO;
227:
228:    // if cdo is not yet set we skip the check (this can happen only during the setup)
229:    if (_cdo != address(0)) {
230:      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
231:    }
232:    uint256 _maxApr = maxApr;
233:    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
234:    lastApr = _apr;
235:  }
```

`initialize` sets `borrower`, `manager`, `lastApr`, `unscaledApr`, `maxApr = DEFAULT_MAX_APR` but never `idleCDO` or `require(_manager != 0)`, exactly the uninitialized-role gap flagged in the external report (`initialize` lines 124-158, `setManager`/`setBorrower` lines 185-194 — only `setBorrower` rejects zero). If `idleCDO` is later set to a wrong (or attacker-controlled, in a proxy misdeployment) address it is never re-validated; there is no `setIdleCDO` zero-check in the snippet surface.

### Finding Description
- `setApr` gates `msg.sender` behind `idleCDO != address(0)` (line 229). Before `idleCDO` is assigned, the guard is skipped and `lastApr` is freely writable by any account.
- `setAprs` (lines 206-210) and `setAprsWithBuffer` (lines 217-220) write `unscaledApr` **before** delegating to `setApr`, so the same zero-guard bypass lets an attacker control both the unscaled and scaled APR atomically.
- Only the `maxApr` cap (`DEFAULT_MAX_APR = 20e18`, line 89) bounds the value; if `setMaxApr(0)` was ever called (line 198: "0 disables the cap"), the written APR is unbounded.
- Broken invariant: fair interest accrual / access control on a privileged setter. `lastApr` drives `_calcInterest`-style accrual consumed by `IdleCDOEpochVariant` (`_checkOnlyOwnerOrManager` reads `IdleCreditVault(strategy).manager()` at `IdleCDOEpochVariant.sol:93-95` and epoch accounting reads `lastApr`/`unscaledApr` when computing `expectedEpochInterest` and `stopEpoch` interest).

### Impact Explanation
An attacker who writes `lastApr`/`unscaledApr` during the unset-`idleCDO` window can:
- Set the APR to the cap (or unbounded if `maxApr == 0`), inflating the interest the epoch accounting expects the borrower to pay. With minted-interest accounting (`isInterestMinted`), this mints excess strategy-token yield to tranche holders against no real borrower repayment, causing AA/BB solvency shortfall at `stopEpoch`/`_handleBorrowerDefault` — direct insolvency, not just DoS.
- Set `unscaledApr = 0`, which flips `requestWithdraw` into the APR=0 accounting branch (line 285: `unscaledApr == 0`), changing how interest is settled for all subsequent withdraw requests and freezing user payouts behind `apr0Users` settlement invariants.

Loss is quantified by `(inflatedAPR - realAPR) * principal * elapsed / YEAR` worth of minted-but-unfunded yield, up to full NAV if `maxApr == 0`.

### Likelihood Explanation
The vulnerability is conditional on `idleCDO` being `address(0)`, which per the inline comment happens "only during the setup". In the normal factory flow `initialize` and CDO wiring are likely atomic, which constrains the window — same as the external finding, which depended on `manager` never being initialized. However: `initialize` does not enforce non-zero `_manager`/`_borrower` (only `setBorrower` does), `manager` stays a silent no-op principal (`msg.sender != manager` can never be true for `manager == 0` — actually the check still reverts for EOAs since `msg.sender != 0`, but a `manager == 0` vault permanently disables the manager role the code intends to gate on), and any deployment path that leaves `idleCDO` unset even briefly exposes `setApr`/`setAprs` to the public. Medium likelihood, high conditional impact.

### Recommendation
Mirror the external remediation:

```diff
  function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
-   if (_cdo != address(0)) {
-     if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
-   }
+   if (_cdo == address(0) || (msg.sender != _cdo && msg.sender != manager)) revert NotAllowed();
    ...
  }
```

and in `initialize` add `require(_manager != address(0) && _borrower != address(0))` plus a one-time `setIdleCDO` that reverts on `address(0)` and on second calls, so the setup window cannot leave `setApr` unguarded.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "contracts/strategies/idle/IdleCreditVault.sol";

contract IdleCreditVaultSetAprBypassTest is Test {
    IdleCreditVault vault;
    address attacker = makeAddr("attacker");
    address owner = makeAddr("owner");
    address manager = makeAddr("manager");
    address borrower = makeAddr("borrower");
    address underlying; // forked underlying token

    function setUp() public {
        // deploy implementation + proxy, then initialize WITHOUT setting idleCDO
        vault = IdleCreditVault(/* proxy */);
        vm.prank(owner);
        vault.initialize(underlying, owner, manager, borrower, "Borrower", 10e18);
        assertEq(vault.idleCDO(), address(0)); // not yet wired
    }

    function test_AnyoneSetsAprBeforeCdoWired() public {
        // attacker is neither CDO nor manager
        vm.prank(attacker);
        vault.setAprs(20e18, 20e18); // capped by DEFAULT_MAX_APR
        assertEq(vault.unscaledApr(), 20e18);
        assertEq(vault.lastApr(), 20e18);
    }

    function test_Apr0Flip() public {
        vm.prank(attacker);
        vault.setApr(0);
        assertEq(vault.lastApr(), 0);
        // subsequent requestWithdraw calls take the apr0Users branch (line 285)
    }
}
```
Run with a mainnet/optimism fork for `underlying`; after `idleCDO` is assigned the same calls revert with `NotAllowed`, confirming the guard only exists post-setup.

Caveat: exploitability depends on whether any production deployment path leaves `idleCDO` unset in a separate transaction from `initialize`; if `IdleCreditVaultFactory` always wires it atomically, this degrades to a defense-in-depth fix. I could not fully verify the factory wiring within the available iterations — that check would resolve whether the window is real on deployed instances.
