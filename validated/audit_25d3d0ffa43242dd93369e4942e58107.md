### Title
Stale confirmations from removed multisig keys let a request execute below the intended live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts entries in a request's `confirmations: HashSet<PublicKey>` against `num_confirmations` without verifying that every counted public key is still an active access key on the account. When a key is removed via a `DeleteKey` request, the contract only purges *requests whose `signer_pk` equals the removed key* and that key's `num_requests_pk` counter; it never scans other pending requests' `confirmations` sets to strip out that now-revoked key's stale confirmation. The stale confirmation continues to count toward the threshold, so a request can later be executed with fewer than `num_confirmations` distinct **currently live** members having approved it.

### Finding Description
The equality this contract must preserve is: *confirmations counted for a request == approvals from currently authorized (live) members*, and execution must only happen once that count reaches `num_confirmations` live approvals.

In `confirm`: [1](#0-0) 
the check is purely `confirmations.len() as u32 + 1 >= self.num_confirmations`, with no re-validation of the keys already present in `confirmations` against the account's current key set.

Key removal is handled inside `execute_request`'s `DeleteKey` branch: [2](#0-1) 
This only removes requests where `r.signer_pk == pk` (i.e., requests *created* by the removed key) and clears `num_requests_pk` for that key. It does **not** iterate over all other pending requests' `confirmations` maps to remove the deleted key's entry from any request it had merely *confirmed* (but not created).

Consequently: if key `A` confirms request `R` (created by a different key `B`), and afterward a separate multisig request removes key `A` from the account (a routine key-rotation/offboarding action), `R`'s `confirmations` set still contains `A`'s public key. A subsequent legitimate confirmer only needs to push `confirmations.len() + 1 >= num_confirmations`, and `A`'s stale, no-longer-valid confirmation is counted as if it were live. This lets `R` execute with fewer real, currently-authorized signers than `num_confirmations` requires.

### Impact Explanation
This breaks the core multisig custody guarantee: "a request executes only once `num_confirmations` *distinct, currently authorized* members have approved it." An attacker (or even an innocuous sequence of routine key-management actions) can cause a pending Transfer/AddKey/FunctionCall request to execute with an effective threshold lower than configured, moving NEAR or granting access with insufficient live authorization. This matches the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
No foundation, owner, or malicious node dependency is required — only an unprivileged sequence of otherwise-normal multisig operations: (1) a member confirms a pending request, (2) that member's key is later removed via a separate, legitimately-confirmed `DeleteKey` request (e.g., routine offboarding or key rotation), and (3) the original pending request is later confirmed and executed. Key removal is an expected/likely operational action in any long-lived multisig, making the stale-confirmation window realistic rather than purely theoretical.

### Recommendation
When executing a `DeleteKey` action, iterate all pending requests' `confirmations` sets (not just those with matching `signer_pk`) and remove the deleted public key from each. Alternatively, validate at `confirm`/execution time that every public key counted in `confirmations` is still a live access key of the current account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with keys `{A, B, C, D}` and `num_confirmations = 3`.
2. `B` calls `add_request_and_confirm(R)` → `confirmations[R] = {B}`.
3. `A` calls `confirm(R)` → `confirmations[R] = {B, A}` (2 < 3, not yet executed).
4. Members `B, C, D` create and confirm a separate request `R2` containing `DeleteKey{public_key: A}` (3 confirmations, executes). `execute_request` removes `A`'s access key and any requests where `signer_pk == A`, but `R`'s `confirmations` set (`{B, A}`) is untouched because `R.signer_pk == B`, not `A`.
5. `C` calls `confirm(R)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `R` executes, even though only `B` and `C` are actually live, authorized signers (2 live approvals instead of the required 3). [2](#0-1) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
