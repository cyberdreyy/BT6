### Title
Stale per-epoch instant-withdraw entries survive a funded claim and corrupt default recovery accounting — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The kernel bug is a use-after-free: `f2fs_evict_inode` frees an inode while its list node is still linked, so a later `list_del` in `f2fs_inode_synced` dereferences freed memory. The analog in `IdleCreditVault` is the same shape: `claimInstantWithdrawRequest` "frees" a user's instant-withdraw receipt (burns receipt tokens, zeroes `instantWithdrawsRequests[_user]`, pays out underlying) but never removes the per-epoch accounting nodes `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. Those stale entries are later dereferenced by default-recovery accounting as if the receipt were still live, inflating `defaultPendingClaimBasis` and fabricating "prefunded" reserve that has already been paid out.

### Finding Description
In `claimInstantWithdrawRequest` (lines 380-393) only the aggregate counter is cleared:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Neither `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` nor `instantWithdrawClaimsByEpoch[currentEpoch]` (both incremented in `requestInstantWithdraw`, lines 371-372) is decremented. Contrast with the default-claim path `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which correctly zeroes `instantWithdrawsRequestsByEpoch`, decrements the aggregate, decrements `pendingInstantWithdraws`, and decrements `instantWithdrawClaimsByEpoch`. The normal claim path is missing exactly those list-removal steps — the receipt is freed but stays linked.

The stale node is dereferenced in two places during `finalizeDefaultRecovery`:

1. `defaultPendingClaimBasis` (line 644-649): `basis += instantWithdrawClaimsByEpoch[epochNumber]` counts already-claimed receipts as defaulted claim basis.
2. `_defaultPrefundedInstantReserve` (lines 716-723): `prefundedReserve = instantBasis - pendingInstant` treats the stale, already-paid amount as underlying still held by the strategy, inflating `reserveAmount` (line 686) with phantom tokens.

Both errors push `recoveryPrice` toward 1: `(R + phantom)/(B + phantom) > R/B` whenever the true recovery is below par.

### Impact Explanation
Recovery price is set too high while the real underlying balance is unchanged. Early claimants — including the attacker, who can simultaneously hold a legitimate defaulted withdraw/instant receipt — are paid at the inflated ratio through `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` but cannot conjure tokens. The strategy's real balance is exhausted before all claims are serviced, so later claimants' `safeTransfer` reverts: permanent freezing of unclaimed yield for honest defaulted-epoch claimants, and direct theft of their recovery share by earlier claimants paid at the inflated price. Additionally, any user whose stale `instantWithdrawsRequestsByEpoch` entry exceeds their live aggregate hits an underflow at line 848 (`instantWithdrawsRequests[_user] -= claimBasis`), making `claimInstantWithdrawRequest` permanently revert for them.

Quantification: with claim basis `B`, real reserve `R` (`R < B`), and stale claimed amount `X`, the excess payout capacity created is `(B*X - R*X)/(B + X)` of underlying; for `B = 1M`, `R = 400k` (40% recovery), `X = 100k`, the price moves from 0.40 to ~0.4545, i.e., ~54.5k underlying overpaid to early claimants and stolen from later ones.

### Likelihood Explanation
Requires: (a) the vault operates instant withdrawals, (b) a user requests an instant withdraw in the epoch that later defaults and gets it funded/claimed before finalization, and (c) `pendingInstantWithdraws != 0` at finalization so `defaultInstantWithdrawsFinalized` is set and the current-epoch instant bucket enters the basis — i.e., the instant queue was only partially funded when the borrower defaulted, precisely the scenario this accounting exists for. The attacker needs no privileges: they request an instant withdraw as any KYC'd tranche holder via `IdleCDOEpochVariant.requestInstantWithdraw`, claim once funded (honest CDO/borrower sequencing), and optionally hold a second defaulted receipt to claim early. No guard stops it: `_ensureDefaultRecoveryInitialized` only checks aggregate `pendingInstantWithdraws`, and the `_transferFundedClaim` reserve guard does not exist yet at request/claim time.

### Recommendation
Mirror the normal-claim cleanup done for the default path. In `claimInstantWithdrawRequest`, also delete the per-epoch node:

```solidity
uint256 epoch = /* epoch the receipt was recorded in */;
instantWithdrawsRequestsByEpoch[_user][epoch] -= amount;
instantWithdrawClaimsByEpoch[epoch] -= amount;
```

Because a user's aggregate may span multiple epochs, either track the user's request epoch (e.g., reuse a `lastInstantWithdrawRequest` marker, analogous to `lastWithdrawRequest`) or iterate the known current epoch. Also consider decrementing `instantWithdrawClaimsByEpoch` inside `collectInstantWithdrawFunds`/claim consistently so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever see live, unfunded receipts.

### Proof of Concept
Foundry fork PoC (against `test/foundry/IdleCreditVault.t.sol` harness style):

```solidity
function testStaleInstantClaimInflatesDefaultRecovery() public {
    // attacker is a KYC'd AA holder
    uint256 X = 100_000 * ONE_SCALE;
    idleCDO.depositAA(X * 10); // fund pool

    // --- epoch N: attacker requests instant withdraw in the current epoch ---
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(X, address(AAtranche));

    // honest flow: CDO partially funds the instant queue; attacker's receipt is fully funded
    // (collectInstantWithdrawFunds pulls X into the strategy, pendingInstantWithdraws -= X
    //  while another user's request Y stays unfunded -> pendingInstantWithdraws = Y)
    fundInstantQueuePartially(X); // via borrower/manager honest calls

    // attacker claims normally: receipt "freed"
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(creditVault.instantWithdrawsRequests(attacker), 0);
    // BUG: stale node remains linked
    uint256 stale = creditVault.instantWithdrawsRequestsByEpoch(attacker, creditVault.epochNumber());
    assertEq(stale, X);
    assertEq(creditVault.instantWithdrawClaimsByEpoch(creditVault.epochNumber()), X + Y_);

    // --- borrower defaults in the same epochNumber, queue still partially unfunded ---
    makeBorrowerDefault(); // defaulted() == true, pendingInstantWithdraws == Y > 0

    uint256 realReserve = underlying.balanceOf(address(creditVault)) + externalRecovery;
    cdoEpoch.finalizeDefault(recovered, source); // -> strategy.finalizeDefaultRecovery

    // recovery price inflated toward 1 by phantom prefunded reserve + inflated basis
    uint256 price = creditVault.defaultRecoveryPrice();
    assertGt(price, realReserve * 1e18 / trueBasis);

    // attacker (or any first claimer) draws at inflated price; reserve drains early
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest(); // or claimInstantWithdrawRequest for defaulted receipt

    // last honest claimant's transfer reverts: permanent freeze of their recovery
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimInstantWithdrawRequest();
}
```
