### Title
Stale loss-adjusted withdraw receipt is paid at par after a later borrower default, draining other claimants' funded withdrawals - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimWithdrawRequest` handles a user who holds a loss-adjusted receipt from a `stopEpochWithDuration(_lossAmount)` epoch *and* a newer receipt from the epoch that later hard-defaults. The defaulted-epoch claim clears `lastWithdrawRequest`, so `_claimLossAdjustedWithdrawRequest` can no longer find the older loss epoch. The older receipt then falls through to `_claimFundedWithdrawRequest`, which pays it at 100% even though only `basis * lossRecoveryPrice` was ever collected by the strategy — overpaying the attacker at the expense of other funded claimants.

### Finding Description
When a borrower shortfall is processed via `stopEpochWithDuration`, `collectWithdrawFunds` collects only `_amount < pendingBasis`, stores `lossRecoveryPriceByEpoch[epoch]`, and zeroes `pendingWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:411-420). The underfunded remainder is a realized loss: affected receipts are meant to be paid only `claimBasis * lossRecoveryPrice / RECOVERY_FULL` inside `_claimLossAdjustedWithdrawRequest` (IdleCreditVault.sol:789-801).

That function locates the loss epoch via `lastWithdrawRequest[_user]` (IdleCreditVault.sol:790). If the same user later requests another withdrawal and that newer epoch ends in a borrower default, `finalizeDefault` sets `epochEndDate = 0` (contracts/IdleCDOEpochVariant.sol:222-223) and `claimWithdrawRequest` runs `_claimDefaultedWithdrawRequest` first, which calls `_clearWithdrawClaimForEpoch` and resets `lastWithdrawRequest[_user]` to 0 when it equals the default epoch (IdleCreditVault.sol:832-836). After that:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[0]`, gets 0, and returns 0 (IdleCreditVault.sol:790-792).
- `_claimFundedWithdrawRequest` sees `epochEndDate() == 0`, skips the epoch-wait revert (IdleCreditVault.sol:326-328), and pays the *remaining* `withdrawsRequests[_user]` — which still contains the full pre-haircut basis of the loss-adjusted epoch receipt — at par, burning the user's receipt tokens (IdleCreditVault.sol:338-349).

The reserve guard in `_transferFundedClaim` only protects `defaultRecoveryReserve` (IdleCreditVault.sol:899-905); it does not protect the pool of funded-withdrawal underlyings. The attacker receives `basis` instead of `basis * lossRecoveryPrice`, i.e. an overpayment of `basis * (1 - lossRecoveryPrice)`, paid out of underlyings collected for *other* users' funded receipts — a direct theft / insolvency of the funded-claim pool.

### Impact Explanation
Any unprivileged lender (KYC-passing tranche holder) can manufacture this state with ordinary `requestWithdraw` calls across two epochs — no privileged role required. The attacker extracts the un-funded loss portion that the waterfall explicitly assigned to receipts, stealing from other claimants whose funded withdrawals share the same strategy balance. Loss is quantifiable: `receiptBasis * (1 - lossRecoveryPrice)` per exploit, bounded by the strategy's funded-claim balance.

### Likelihood Explanation
Requires a sequence the protocol explicitly supports: a partial-loss epoch (`stopEpochWithDuration` with `_lossAmount` and underfunded `collectWithdrawFunds`), an unclaimed receipt kept open (the code comments acknowledge users may roll receipts forward), a second request, then a borrower default followed by `finalizeDefault`. All attacker steps are normal user calls; only the loss/default events come from the honest manager/borrower. Conditional on a default occurring while a user holds a stale loss-adjusted receipt, the overpayment is deterministic.

### Recommendation
In `_clearWithdrawClaimForEpoch`, when `lastWithdrawRequest[_user]` is cleared because it matched the claimed epoch, restore it to the user's next-oldest unclaimed receipt epoch (or track per-epoch receipts explicitly) so `_claimLossAdjustedWithdrawRequest` still resolves the pending loss epoch. Alternatively, in `requestWithdraw`, force settlement of any receipt whose epoch has a non-zero `lossRecoveryPriceByEpoch` before allowing a new request, mirroring the existing post-default open-receipt check.

### Proof of Concept
Foundry fork PoC (schematic, based on existing helpers in test/foundry/IdleCreditVault.t.sol):

```solidity
// 1. attacker deposits and requests withdraw in epoch N
_depositWithUser(attacker, amount, true);
vm.prank(attacker);
uint256 lossBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

// 2. epoch N stops with a partial loss: borrower returns only 50%
_startEpochAndCheckPrices(0);
// stopEpochWithDuration(0, interest, duration, _lossAmount) so that
// collectWithdrawFunds records lossRecoveryPriceByEpoch[N] = 0.5e18
// ... manager call per existing test helpers ...
// attacker does NOT claim; receipt stays open

// 3. buffer of epoch N+1: attacker deposits again and requests withdraw
_depositWithUser(attacker, amount, true);
vm.prank(attacker);
uint256 defaultBasis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // lastWithdrawRequest = N+1

// 4. epoch N+1 runs and borrower defaults at stopEpoch
_startEpochAndCheckPrices(1);
deal(defaultUnderlying, borrower, 0);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);          // _handleBorrowerDefault, defaulted = true
// owner finalizes with some recovery
cdoEpoch.finalizeDefault(recovered, manager); // epochEndDate = 0

// 5. attacker claims once
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();

// Expected by design: defaultBasis * defaultRecoveryPrice + lossBasis * 0.5e18/1e18
// Actual: defaultBasis * defaultRecoveryPrice + lossBasis (full par payout)
assertEq(underlying.balanceOf(attacker) - balPre,
         defaultBasis * recoveryPrice / 1e18 + lossBasis); // overpaid
```

The overpaid `lossBasis * (1 - 0.5)` is funded by underlyings collected for other users' funded receipts, whose subsequent `claimWithdrawRequest` will revert on `safeTransfer` for lack of balance — converting theft into freezing of the remainder.
