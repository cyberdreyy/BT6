## Analog Vulnerability Found

### Title
Stale confirmations from deleted members are still counted toward the confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
This is a direct structural analog of the GoatV1Pair "no check for `initialEth`" bug: in both cases a code path performs a numeric check against a value that is *supposed to reflect the current, live state* but actually reflects a value that can be manipulated/left stale, letting the check be trivially satisfied without the underlying invariant holding. In `GoatV1Pair.takeOverPool()`, `initialEth` had no bearing on the check meant to gate the takeover. In `multisig2/src/lib.rs`'s `confirm()`, the number of "confirmations" counted toward `num_confirmations` includes confirmations made by members who have since been removed from the multisig, because `delete_member()` never purges a removed member's confirmation entries from requests they did not themselves create.

### Finding Description
`MultiSigContract::confirm()` checks the live threshold using the size of the `confirmations` `HashSet<String>` stored per request: [1](#0-0) 

`confirmations` entries are keyed by `MultisigMember::to_string()` and are only removed for a given request when the request itself is executed, deleted, or when `delete_member` scans requests **created by** the removed member: [2](#0-1) 

Note that the `filter_map` in `delete_member` only matches `r.member == member`, i.e. the *creator* of the request, not members who separately called `confirm()` on that request. Consequently, if member `D` confirms a pending request `R` that was created by a different member `A`, and `D` is later removed from `members` via `DeleteMember`, `D`'s confirmation entry for `R` remains in `self.confirmations`. It is never invalidated. When the remaining live members subsequently confirm `R`, `D`'s stale confirmation still counts toward `num_confirmations`, exactly as if `D` were still a live signer.

This breaks the intended equality: `confirmations counted == confirmations by currently-live members`. Instead the code enforces `confirmations counted (including removed members) >= num_confirmations`, which is weaker.

### Impact Explanation
This allows a request to be executed with fewer *live* member confirmations than `num_confirmations` actually requires — i.e., a multisig request executed below threshold, which falls under the explicit Critical impact category. For example, with 4 members and `num_confirmations = 3`: member `D` confirms request `R` (created by `A`) and is then removed (e.g. as part of routine key rotation or because they left the organization/were compromised). Only 2 of the 3 remaining live members (`B`, `C`) need to confirm `R` afterward for it to execute, since `D`'s stale confirmation is still counted. This can be used to push through a `Transfer`, `DeployContract`, `AddKey`, or `FunctionCall` request with an effective threshold of `num_confirmations - 1` live signers, undermining the M-of-N security guarantee the contract is supposed to provide.

### Likelihood Explanation
No privileged role beyond ordinary multisig membership is required. Any member can confirm a pending request before being removed (a routine, expected lifecycle event for multisig membership, e.g. onboarding/offboarding of employees or key rotation), and the flaw is triggered by ordinary use of `add_request` + `confirm` + `DeleteMember` — no malicious deployer, malicious validator, or out-of-scope entity is needed.

### Recommendation
When a member is deleted, iterate over `self.confirmations` (not just `self.requests` filtered by creator) and remove the deleted member's identifier from every request's confirmation set, or alternatively re-validate at `confirm()` time that all counted confirmers are still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig with members `[A, B, C, D]`, `num_confirmations = 3` (see init at [3](#0-2) ).
2. `A` calls `add_request` to create request `R` (e.g. a `Transfer`).
3. `D` calls `confirm(R)` → `confirmations[R] = {D}` (size 1, below threshold, not yet executed).
4. Members `A`, `B`, `C` submit and confirm a `DeleteMember { member: D }` request (needs 3 confirmations, satisfied by the still-live `A, B, C`), which executes `delete_member` and removes `D` from `members`. Because `R` was created by `A` (not `D`), the `filter_map` in `delete_member` does not touch `confirmations[R]`, so `{D}` remains stored.
5. Now only `A, B, C` are live members, yet `num_confirmations` is still 3.
6. `B` calls `confirm(R)` → `confirmations[R] = {D, B}` (size 2, still below 3).
7. `C` calls `confirm(R)` → `confirmations[R].len() + 1 = 3 >= num_confirmations` → `R` executes using `D`'s stale confirmation, even though `D` is no longer a member and only 2 live members (`B`, `C`) actually approved it beyond the original creator `A`.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
