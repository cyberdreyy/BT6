This is the confirmed vulnerability location: `core/services/gateway/handlers/confidentialrelay/handler.go`, function `(*handler).HandleJSONRPCUserMessage`, handling `relaytypes.MethodSecretsGet`/`relaytypes.MethodCapabilityExec`.

### Title
Confidential relay gateway handler fans out `MethodSecretsGet`/`MethodCapabilityExec` requests to DON nodes with no authorization/allowlist/ownership check - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`(*handler).HandleJSONRPCUserMessage` in the confidential relay gateway handler only validates that `req.ID` is non-empty and ≤200 characters before creating an `activeRequest` and calling `h.fanOutToNodes`. Unlike the sibling `vault` handler, which calls `h.requestProcessor.ProcessRequest(...)` to authorize the request and derive `authorizedOwner` before dispatch, this handler performs no authorization, allowlist, or ownership/subscription check at all before forwarding the raw, attacker-supplied `Params` (which can contain an arbitrary `Owner`/subscription identifier) to every DON node.

### Finding Description
The reachable code path is: `HandleJSONRPCUserMessage(ctx, req, callback)` at [1](#0-0)  — it checks `req.ID` length/emptiness, calls `h.newActiveRequest(req, callback)`, and immediately calls `h.fanOutToNodes(ctx, l, ar)`, which sends `&ar.req` (the raw request, including `Params`) to every DON member via `h.don.SendToNode` at [2](#0-1) . There is no call to any authorizer, allowlist, or `AuthorizedOwner()`-style function anywhere in this file — grep for `MethodCapabilityExec|MethodSecretsGet` and for authorization primitives confirms the file only re-exports the method constants at [3](#0-2)  and never references `vaultcap.Authorizer`, `AllowListBasedAuth`, or any owner-authorization step.

This is in stark contrast to the vault handler (`core/services/gateway/handlers/vault/handler.go`), whose `HandleJSONRPCUserMessage` explicitly authorizes non-public-key methods via `h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)` and rejects unauthorized requests before dispatch: [4](#0-3) . The confidential relay handler has no equivalent step — an attacker's HTTP/gateway client can submit a validly-shaped JSON-RPC request for `MethodSecretsGet` or `MethodCapabilityExec` with an arbitrary `Owner`/subscription identifier in `Params`, and the handler will unconditionally forward it to all DON nodes for processing, relying entirely on the receiving nodes/enclave to reject it (a defense that is outside this file and not verifiable from this handler alone).

### Impact Explanation
If the downstream DON nodes/enclave do not independently re-validate ownership of the `Owner`/subscription identifier embedded in `Params` before acting on `MethodSecretsGet` (secret retrieval) or `MethodCapabilityExec` (capability execution), an unprivileged client could impersonate another user's identity in the request payload and trigger secret disclosure or unauthorized capability execution/fund-affecting actions under another user's subscription — this maps to Chainlink's "unauthorized action on another user's job/subscription/secret" and "secret disclosure" impact classes. The severity is scoped strictly to whatever enforcement the enclave/DON side does, but the gateway layer itself provides zero defense-in-depth, which is inconsistent with the pattern established by the vault handler for the same class of request.

### Likelihood Explanation
No credentials beyond generic gateway API access are required — no operator, admin, or node access needed, and no signature-forging is required since the handler does not even check for a signature/authorization struct on `req.Auth` (which the vault handler does, e.g., logging `req.Auth != ""` at [5](#0-4) ). The request only needs a validly-shaped `MethodSecretsGet`/`MethodCapabilityExec` JSON-RPC payload with a non-empty `ID` ≤200 chars — trivially reproducible and repeatable by any low-privilege attacker able to reach the gateway's HTTP endpoint.

### Recommendation
Add an authorization/ownership check in `(*handler).HandleJSONRPCUserMessage` before `fanOutToNodes` is called — analogous to the vault handler's `h.requestProcessor.ProcessRequest` call — that validates the requester is authorized for the `Owner`/subscription identifier embedded in `Params` for `MethodSecretsGet` and `MethodCapabilityExec`, rejecting the request with an appropriate error (e.g., `api.InvalidParamsError` or a new authorization error code) before any node fan-out occurs.

### Proof of Concept

1. Construct a `handler` with a mock `gwhandlers.DON` whose `SendToNode` is instrumented to record calls.

Assert: (a) no authorization/allowlist function is invoked anywhere in the call chain (there is none to mock/verify against — confirmed absent from the package by inspection/grep), and (b) `don.SendToNode` is called once per DON member with the unmodified `Owner` field, proving the request reached fan-out without any authorization gate.
5. Compare against `core/services/gateway/handlers/vault/handler_test.go`'s equivalent test, which does mock/assert `Authorizer`/`ProcessRequest` invocation before fan-out — the confidential relay handler has no such test or code path, confirming the gap.

```go
func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}
```

```go
func (h *handler) fanOutToNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var (
		group      errgroup.Group
		nodeErrors atomic.Uint32
	)

	// Each send is bounded independently. A node whose websocket accepts no writes blocks
	// until its context is cancelled, and because the caller only reads the response callback
	// after this function returns, an unbounded send would hold the request open until the
	// client gives up, discarding a bundle that already reached quorum.
	sendCtx, cancel := context.WithTimeout(ctx, h.nodeSendTimeout)
	defer cancel()

	for _, node := range h.donConfig.Members {
		group.Go(func() error {
			err := h.don.SendToNode(sendCtx, node.Address, &ar.req)
			if err != nil {
				nodeErrors.Add(1)
				l.Errorw("error sending request to node", "node", node.Address, "error", err)
			}
			return nil
		})
	}
```
