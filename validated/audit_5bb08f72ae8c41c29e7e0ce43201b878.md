### Title
Unguarded `initializeConfig` Allows Any Caller to Permanently Hijack Bridge Config — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

### Summary

`BridgeCommittee.initializeConfig` is an `external` function with no access-control modifier and no zero-address check on its `_config` argument. Any caller can invoke it before the deployer and permanently bind the committee to a malicious `IBridgeConfig` contract. Once set to a non-zero address the guard `require(address(config) == address(0), …)` permanently blocks the legitimate deployer from overwriting it. This is the direct Sui-bridge analog of the external report's root cause: an initialization path that sets a critical authority address without the same validation that later mutating paths enforce.

---

### Finding Description

`BridgeCommittee.initializeConfig` at line 63–66:

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

Two defects are present simultaneously:

**1. No access control.** The function carries no `onlyOwner`, no committee-signature gate, and no `msg.sender` check. Any externally-owned account or contract can call it at any time before the deployer does.

**2. No zero-address check on `_config`.** If `_config == address(0)` the assignment `config = IBridgeConfig(address(0))` leaves `config` at its default zero value, so the "already initialized" guard continues to pass on every subsequent call. This silently bypasses the one-time-set protection and allows the function to be called repeatedly with `address(0)` as a no-op, masking the window during which a real front-run can occur.

The deployment script calls `initializeConfig` in a separate transaction from the proxy deployment:

```solidity
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));
``` [2](#0-1) 

Between the proxy deployment transaction and this `initializeConfig` call, the `config` slot is `address(0)` and the guard passes for any caller.

The `config` object is consumed by every critical bridge path in `SuiBridge`:

```solidity
IBridgeConfig config = committee.config();
require(tokenTransferPayload.targetChain == config.chainID(), "SuiBridge: Invalid target chain");
uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
    IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(), ...
);
``` [3](#0-2) 

A malicious `IBridgeConfig` can return arbitrary values for `chainID()`, `tokenAddressOf()`, `isTokenSupported()`, and `isChainSupported()`, corrupting every downstream bridge decision.

---

### Impact Explanation

If an attacker front-runs `initializeConfig` with a malicious `IBridgeConfig` contract:

- The deployer's subsequent call reverts with "BridgeCommittee: Config already initialized" — the legitimate config can never be installed.
- All `SuiBridge` token-transfer operations read chain IDs and token addresses from the attacker-controlled config.
- A malicious config returning `false` for `isTokenSupported` on all tokens permanently blocks all withdrawals, locking every asset held in `BridgeVault`.
- A malicious config returning a different `tokenAddressOf` causes the vault to attempt transfers of the wrong ERC-20, producing harmful smart-contract behavior on every legitimate claim.

This satisfies the **High/Medium** impact gate: permanent fund lock and harmful smart-contract behavior reachable from public input (an ordinary EOA submitting a transaction).

---

### Likelihood Explanation

The deployment script (`deploy_bridge.s.sol`) issues the proxy deployment and the `initializeConfig` call as **separate transactions**. Any mempool observer can detect the proxy deployment and submit a front-running `initializeConfig(maliciousConfig)` transaction with a higher gas price. No special privilege is required — only the ability to submit an Ethereum transaction.

---

### Recommendation

**Short term:** Add a zero-address check and restrict the caller to the deployer or a trusted address:

```solidity
function initializeConfig(address _config) external onlyDeployer {
    require(_config != address(0), "BridgeCommittee: Zero config address");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

Alternatively, pass `_config` directly into `initialize` and set it atomically in the same initializer call, eliminating the two-step window entirely.

**Long term:** Audit all two-step initialization patterns across the bridge EVM contracts for similar front-running windows. Consider deploying and initializing all contracts atomically within a single deployment transaction or using a factory contract that performs all initialization steps atomically.

---

### Proof of Concept

1. Attacker deploys `MaliciousConfig` implementing `IBridgeConfig` — all methods return values that block legitimate transfers (e.g., `isTokenSupported` always returns `false`).
2. Attacker monitors the mempool for the `BridgeCommittee` proxy deployment transaction.
3. Attacker submits `BridgeCommittee(proxy).initializeConfig(address(maliciousConfig))` with higher gas, front-running the deployer's `initializeConfig` call.
4. Attacker's transaction is mined first; `config` is set to `maliciousConfig`.
5. Deployer's `initializeConfig(realConfig)` reverts: "BridgeCommittee: Config already initialized".
6. `SuiBridge` is now permanently bound to `maliciousConfig`; all calls to `transferBridgedTokensWithSignatures` revert because `isTokenSupported` returns `false`, locking all vault assets. [1](#0-0) [4](#0-3) [5](#0-4)
