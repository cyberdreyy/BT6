### Title
View-role API token holder can retrieve a bridge's plaintext OutgoingToken via GET /v2/bridge_types/:BridgeName - ([File: core/web/presenters/bridges.go])

### Summary
`presenters.NewBridgeResource` unconditionally copies `bridges.BridgeType.OutgoingToken` into the JSON-serialized `BridgeResource.OutgoingToken` field, and `BridgeTypesController.Show` uses this presenter without any redaction or role check on the field. Since `OutgoingToken` is stored in plaintext (unlike `IncomingTokenHash`, which is salted+hashed), any caller authorized to hit the Show/Index/Update/Destroy bridge endpoints receives the bridge's outgoing credential in the response body.

### Finding Description
`core/bridges/bridge_type.go` shows the asymmetry in how the two bridge secrets are persisted: `IncomingTokenHash` is a salted SHA-256 hash [1](#0-0) , while `OutgoingToken` is stored as plaintext directly on `BridgeType` [2](#0-1) .

`presenters.NewBridgeResource` builds the API response by copying `b.OutgoingToken` straight into the `OutgoingToken` JSON field with no `omitempty` and no role-based filtering, unlike `IncomingToken` which is commented as "only provided when creating a Bridge" and is deliberately left blank here: [3](#0-2) .

`BridgeTypesController.Show` calls `orm.FindBridge` and passes the full `bridges.BridgeType` (including `OutgoingToken`) directly into `presenters.NewBridgeResource`, then serializes it to the client with `jsonAPIResponse`: [4](#0-3) . The same unredacted presenter is also used by `Index`, `Update`, and `Destroy` [5](#0-4) [6](#0-5) [7](#0-6) .

I was unable to fully verify the exact role requirement wired to this route in `core/web/router.go` within this session (the file content for the bridge route registration lines was not retrieved before tool access ended), so I cannot confirm with certainty whether `Show` is gated to admin-only or accessible to view-role tokens in this codebase revision. This is a gap in verification, not a refutation of the core defect: regardless of the minimum required role, the presenter itself performs no additional secret redaction based on caller role — it exposes the plaintext `OutgoingToken` to any caller who can reach the endpoint at all, which is architecturally inconsistent with the deliberate `IncomingToken` redaction pattern in the same struct.

### Impact Explanation
Exposure of a bridge's plaintext `OutgoingToken` is a "Chainlink authenticates bridge/external-adapter callbacks" credential leak — this token is intended to let the node itself authenticate to the external adapter/bridge server when POSTing callback results, and disclosure could allow an attacker who can query the API to impersonate the node to the external adapter or replay/spoof bridge responses depending on how the external adapter validates the header. This matches the bounty impact class of credential/secret disclosure via a controller/presenter that fails to redact.

### Likelihood Explanation
Feasibility depends entirely on the minimum role/permissions actually enforced by `router.go` for `GET /v2/bridge_types/:BridgeName`, which I was not able to confirm in this session. If the route only requires "view" role or a low-privilege API token (which is the case for read-only GET endpoints on most resources in this codebase's admin panel), the exploit requires only a valid low-privilege session/token and knowledge of an existing bridge name — trivially repeatable. If the route in fact requires admin role, this finding is reduced to a defense-in-depth/least-privilege issue rather than a privilege-escalation vulnerability.

### Recommendation
Redact `OutgoingToken` from `presenters.NewBridgeResource` for read paths (`Show`, `Index`) the same way `IncomingToken` is handled — only populate it (if ever) at creation time, or better, treat it symmetrically to `IncomingToken` (never return it after creation; store a hash and use it purely server-side for outbound authentication headers). At minimum, add `omitempty` and strip the value unless the caller has an elevated/admin role explicitly checked in the controller.

### Proof of Concept
1. In `core/web/bridge_types_controller_test.go` (or a new test file), set up an httptest app with a client authenticated as a "view" role user, and one as "admin".
2. As admin, `POST /v2/bridge_types` to create a bridge; capture the returned `bridges.BridgeType.OutgoingToken` from the ORM/DB directly.
3. As the view-role client, `GET /v2/bridge_types/:BridgeName`.
4. Assert `resp.Data.Attributes.OutgoingToken` is non-empty and equals the stored `OutgoingToken`, demonstrating the plaintext secret is returned to the low-privilege caller — while confirming `IncomingToken` is empty in the same response for contrast.

Note: this PoC's privilege-escalation conclusion is contingent on confirming the actual role gate configured for this route in `core/web/router.go`, which should be checked before treating this as a confirmed cross-privilege violation versus an over-broad-disclosure defect present at any authorized role.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
