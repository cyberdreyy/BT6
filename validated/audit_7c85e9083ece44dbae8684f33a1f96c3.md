## Finding confirmed

Tracing `switch_operator` and `distribute_internal` shows this beneficiary-redirect bug is real.

### Title
Stale operator commission distribution bypasses `BeneficiaryForOperator` after `switch_operator`, paying pending commission to the old operator's raw address instead of its beneficiary - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` calls `request_commission_internal(old_operator, ...)` which calls `add_distribution(old_operator, staking_contract, old_operator, commission_amount)` to record the commission owed to `old_operator` in the contract's `distribution_pool` [1](#0-0) . After the switch, the `StakingContract` (including this `distribution_pool` entry keyed by `old_operator`) is moved into the store under the `new_operator` key [2](#0-1) .

When the pending commission later becomes withdrawable and `distribute_internal` is subsequently invoked for `(staker, new_operator)`, the beneficiary redirect check only fires when the pool's shareholder matches the *current* `operator` argument being passed in:
```
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
``` [3](#0-2) 

Since `operator` is now `new_operator` but the stale shareholder is `old_operator`, the condition is false, so the payout goes directly to the raw `old_operator` address rather than through `beneficiary_for_operator(old_operator)`.

### Finding Description
`BeneficiaryForOperator` state is global per operator address [4](#0-3)  and `set_beneficiary_for_operator` promises: "Any existing unpaid commission rewards will be paid to the new beneficiary" [5](#0-4) . However, this invariant depends on `distribute_internal` correctly comparing the distribution recipient with the operator whose beneficiary should apply.

`request_commission_internal` inside `switch_operator` unlocks the operator's final commission and books it via `add_distribution(operator=old_operator, ..., recipient=old_operator, ...)` [6](#0-5) . This share entry is not distributed immediately — it stays keyed under `old_operator` as a shareholder in `distribution_pool`, but the `StakingContract` struct is then re-keyed by `new_operator` in `store.staking_contracts` [7](#0-6) .

Once the unlocked stake is finally withdrawable and anyone (staker, new operator, or a third party calling the permissionless `distribute` entry function [8](#0-7) ) triggers `distribute_internal(staker, new_operator, staking_contract)`, the loop over `distribution_pool.shareholders()` will encounter `old_operator` as a recipient, but `recipient == operator` compares `old_operator == new_operator`, which is false. The funds are paid straight to the `old_operator` account address, not `beneficiary_for_operator(old_operator)`.

### Impact Explanation
This breaks the beneficiary-payout invariant: an operator who previously registered a beneficiary (e.g. for compliance, custody, or tax-separation reasons) loses their claim over commission that was already earned before being switched out, if the staker calls `switch_operator` before the pending inactive stake becomes withdrawable and someone triggers a later `distribute`. The commission is not permanently lost (it still lands in an address `old_operator` controls), but the beneficiary is wrongly excluded from a payout it was entitled to — a direct instance of "Operator commission, beneficiary payout ... corruption that credits the wrong account," which is explicitly in the Required Impacts list.

Note that the staker triggering `switch_operator` legitimately owns their own stake pool, but they have no authority over the `old_operator`'s beneficiary relationship; the affected party (the beneficiary) has no ability to prevent or foresee this misrouting once a switch happens between the time commission is booked and the time it's actually distributed.

### Likelihood Explanation
This requires: (1) an operator has set a beneficiary via `set_beneficiary_for_operator`, (2) the staker calls `switch_operator` (a normal, permitted staker action) while unpaid rewards exist so `request_commission_internal` books a new distribution to `old_operator`, and (3) a `distribute` call happens later (which is a common, permissionless, and expected operational action) after the lockup period ends. All of these are routine operations in the staking contract lifecycle, making the scenario plausible in production usage, not a contrived edge case.

### Recommendation
Fix the beneficiary check inside `distribute_internal` to be independent of the `operator` argument currently bound to the contract. Instead of `if (recipient == operator)`, either:
- Track, per distribution-pool entry, which address is an "operator-owned" share versus a "staker" share (e.g., tag entries at `add_distribution` time so they always redirect through `beneficiary_for_operator(recipient)` regardless of the current contract operator), or
- Before allowing `switch_operator` to proceed, force full `distribute` of any already-booked-but-not-yet-withdrawable commission belonging to `old_operator` so no stale distribution entries survive the operator key change, or
- Simply always call `beneficiary_for_operator(recipient)` when `recipient` differs from `staker` (i.e., treat any non-staker shareholder as an operator identity eligible for redirection), rather than comparing against the currently-passed `operator`.

### Proof of Concept
Extend `test_operator_can_set_beneficiary`: after the operator sets its beneficiary, have the staker call `switch_operator` to a `new_operator` (this internally books the old operator's final commission distribution under `old_operator`), advance the epoch/lockup so the unlocked commission becomes withdrawable, then call `staking_contract::distribute(staker, new_operator)`. Assert that the coins were deposited to `old_operator`'s raw address instead of the registered beneficiary — demonstrating the beneficiary never receives the commission that was pending at the time of the switch, contrary to the documented behavior of `set_beneficiary_for_operator`.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }
```
