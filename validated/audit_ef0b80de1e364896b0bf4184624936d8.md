### Title
Attacker-Controlled JSON-RPC Request ID Enables Cross-User Callback Hijack in Gateway Legacy WebAPI Handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's legacy web-API handler indexes in-flight user callbacks in a single global map keyed solely by the JSON-RPC request `id` supplied by the (unprivileged, internet-facing) HTTP caller, with no ownership/session binding and no duplicate-key check before insertion. An attacker who submits a request with the same `id` as another user's still-pending request overwrites that user's saved callback, so the eventual DON node response for that message ID is delivered to the attacker's callback instead of the legitimate caller's — a cross-user response confusion class matching the DHT-ID-collision hijack pattern in the reference report (ID-driven resolution that can be squatted/collided by an unprivileged party).

### Finding Description
Any external, unauthenticated-to-role HTTP client hitting the gateway supplies the JSON-RPC `id` field directly: [1](#0-0) . For legacy requests this `id`/`MessageId` is propagated verbatim into the `api.Message` used to key pending callbacks: [2](#0-1) .

In `HandleLegacyUserMessage`, the callback is stored in a shared map `h.savedCallbacks[msg.Body.MessageId]` with **no check for an existing entry** — a new request with a colliding ID simply overwrites the previous (still pending) callback: [3](#0-2) . The map and its guarding mutex are declared in the handler struct without any per-user/session partitioning: [4](#0-3) .

When a DON node later replies, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `msg.Body.MessageId` and delivers the response to whichever callback is currently registered under that ID: [5](#0-4) . There is no sender/requester binding check tying the returned response back to the original caller — the code comment even flags that authorization/allowlisting for this path is not yet implemented ("TODO: apply allowlist and rate-limiting here"): [6](#0-5) .

This mirrors the DHT bug class: resolution of a "content"/response is routed purely by an ID that an unprivileged actor can choose and race to collide with, hijacking delivery of information meant for someone else.

### Impact Explanation
An attacker can:
1. Observe or guess another in-flight user's request `id` (client-chosen strings are often predictable/sequential, or an attacker can simply flood with many candidate IDs since there's no per-caller namespace).
2. Send a second request using the same `id` before the first is resolved, silently displacing the original caller's saved callback.
3. Receive the DON's response intended for the victim's original trigger request — a cross-user response confusion / potential information disclosure of the victim's workflow trigger result, and/or the victim never gets their real response (denial of service against the legitimate caller).

Because `savedCallbacks` has no cap enforcement tied to origin and is globally shared per DON handler instance, this also enables a lightweight collision race against any concurrent caller. The severity is bounded to the legacy `web_api_trigger` gateway path.

### Likelihood Explanation
Likelihood is limited by the requirement to guess/collide with an in-flight `id` within its short pending window (bounded by node round-trip time, typically sub-second to a few seconds) and the fact that this is only the legacy (non-JSON-RPC v2) code path used for `web_api_trigger`; the newer `httpTriggerHandler` in v2 is not confirmed to have the same gap (not fully verified due to time constraints — see below). Still, no cryptographic or session binding of any kind exists over the map key, making the attack trivial to attempt at scale (e.g., brute-forcing common/short IDs or racing observed IDs from client-side telemetry/logs).

### Recommendation
- Reject (rather than silently overwrite) a `HandleLegacyUserMessage`/`HandleJSONRPCUserMessage` request whose `MessageId` already has a pending `savedCallback` entry, returning a conflict error to the caller (the JSON-RPC v2 error table in this codebase already reserves `-32001 Conflict (duplicate request)` for this purpose — reuse it here).
- Bind saved callbacks to an opaque, server-generated correlation ID (or at minimum a per-connection/session nonce) rather than solely the client-controlled JSON-RPC `id`, and validate the responding DON node's message against the original request's expected DON/member set before dispatching to the callback.
- Complete the outstanding "TODO: apply allowlist and rate-limiting" for the legacy trigger path.

### Proof of Concept
1. Client A sends `POST /` with legacy `web_api_trigger` payload, `id = "X"`, targeting DON `D` — creates `savedCallbacks["X"] = A's callback` and forwards to all DON `D` members.
2. Before `D` responds, Client B (attacker) sends the same request shape with `id = "X"` — `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with B's callback (no duplicate check per lines 411-414 of `handler.go`).
3. DON member responds with `MessageId = "X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's intended response to B.
4. Client A's HTTP request times out or never resolves; Client B receives content intended for A.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
