### Title
`approve()` in the B-20 asset/stablecoin precompiles skips `TransferSender`/`TransferReceiver` policy checks, allowing blocked owners/spenders to create allowances - (File: crates/common/precompiles/src/b20_asset/logic/v1.rs, crates/common/precompiles/src/b20_asset/logic/v2.rs, crates/common/precompiles/src/b20_stablecoin/logic/v1.rs, crates/common/precompiles/src/b20_stablecoin/logic/v2.rs)

### Summary
Base's B-20 precompile tokens (the `IB20` asset and stablecoin variants) implement a configurable policy-registry mechanism (`ALLOWLIST`/`BLOCKLIST`) that gates `transfer`/`transferFrom` via `TransferSender`/`TransferReceiver` policy checks. `approve()`, however, is not gated by any policy check, so an account that is blocked/not-allowlisted for transfers can still be approved as an owner or spender.

### Finding Description
`transfer` and `transfer_from` in every B-20 logic implementation enforce `B20Guards::ensure_policy_type`/`ensure_authorized_by_id` against `B20PolicyType::TransferSender` and `B20PolicyType::TransferReceiver` before moving balances, e.g. in `StablecoinV1::transfer_inner`: [1](#0-0) 
and analogously in the Asset/V2 variants via `transfer_inner`/`transfer_from`: [2](#0-1) 

However, `approve()` in `AssetV1` only validates that neither address is the zero address and directly writes the allowance — it never calls `B20Guards::ensure_policy_type`/`ensure_authorized_by_id` against `TransferSender`/`TransferReceiver` (or any blocklist check): [3](#0-2) 

The same pattern (zero-address checks only, no policy gating) repeats in `AssetV2`, `StablecoinV1`, and `StablecoinV2` approve implementations, confirmed by the golden tests that only assert `InvalidSpender`/`InvalidApprover` reverts for `approve`, with no policy-based revert case: [4](#0-3) [5](#0-4) 

Additionally, `permit()` (EIP-2612-style meta-approval) calls straight into `self.approve(...)` after signature/nonce validation, inheriting the same gap: [6](#0-5) 

This is the direct Base analog of the reported issue: just as `EURFToken.approve()` was not overridden to call `transferSanity()` (owner/spender blacklist check), Base's B-20 `approve`/`permit` paths are not wired to the same `TransferSender`/`TransferReceiver` policy guard that `transfer`/`transferFrom` enforce.

### Impact Explanation
A B-20 token admin can configure a `BLOCKLIST` (or restrictive `ALLOWLIST`) policy on `TransferSender`/`TransferReceiver` to sanction/blacklist an address and prevent it from moving funds — this is the documented compliance mechanism (`b20_blocklist_sender_policy_blocks_listed_accounts`, `b20_allowlist_receiver_policy_blocks_non_members`) built into these precompiles: [7](#0-6) 
Because `approve` bypasses this gate, a blocked/blacklisted account can still grant or receive an ERC-20 allowance via `approve`/`permit`, breaking the invariant that blocked accounts cannot participate in transfer-related state changes on the token. While the allowance itself does not move funds, it creates an unauthorized state (an active allowance held by or granted to a sanctioned party) that a compliance-sensitive stablecoin/asset issuer explicitly relies on the policy system to prevent, and it directly contradicts the enforcement applied everywhere else in the token (transfer, transferFrom, mint receiver).

### Likelihood Explanation
High reachability: any unprivileged externally-owned account can call `approve` (or use `permit`) on any deployed B-20 token directly through a signed transaction; no special privileges, precompile internals, or race conditions are required. The gap exists identically across `AssetV1`, `AssetV2`, `StablecoinV1`, and `StablecoinV2`, so it affects all current B-20 token deployments.

### Recommendation
Add the same policy enforcement used by `transfer`/`transfer_from` to `approve` (and thus `permit`, which delegates to `approve`): call `B20Guards::ensure_policy_type(token, B20PolicyType::TransferSender, caller)` and `B20Guards::ensure_policy_type(token, B20PolicyType::TransferReceiver, spender)` (or the id-based `ensure_authorized_by_id` variant using pre-fetched policy ids) before writing the allowance, mirroring the checks already present in `transfer_inner`.

### Proof of Concept
1. Token admin creates a `BLOCKLIST` policy and wires it to `TransferSender` via `updatePolicy`, then adds address `X` to the blocklist (as shown working for `transfer` in `b20_blocklist_sender_policy_blocks_listed_accounts`): [8](#0-7) 
2. Address `X` calls `approve(spender, amount)` on the token contract directly — the call reaches `AssetV1::approve`/`StablecoinV1::approve`, which only checks `caller != Address::ZERO` and `spender != Address::ZERO`: [9](#0-8) 
3. The approval succeeds and `Approval` is emitted, even though `X` is blocked from transferring under the exact same `TransferSender` policy scope — demonstrating the enforcement gap between `approve` and `transfer`/`transferFrom`.

    fn permit(
        &self,
        token: &mut B20StablecoinToken<S, A>,
        chain_id: u64,
        now: U256,
        args: PermitArgs,
    ) -> Result<()> {
        if now > args.deadline {
            return Err(BasePrecompileError::revert(IB20::ExpiredSignature {
                deadline: args.deadline,
            }));
        }
        let domain_sep = self.domain_separator(token, chain_id)?;
        let nonce = token.accounting().nonce(args.owner)?;
        let signing_hash = args.signing_hash(domain_sep, nonce);
        let recovered = args.recover_signer(signing_hash)?;
        PermitArgs::validate_recovered_address(recovered, args.owner)?;
        token.accounting_mut().increment_nonce(args.owner)?;
        self.approve(token, args.owner, args.spender, args.value)
    }

    fn approve(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        spender: Address,
        amount: U256,
    ) -> Result<()> {
        if caller == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidApprover { approver: caller }));
        }
        if spender == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSpender { spender }));
        }
        token.accounting_mut().set_allowance(caller, spender, amount)?;
        token
            .accounting_mut()
            .emit_event(IB20::Approval { owner: caller, spender, amount }.encode_log_data())
    }

fn golden_approve_sets_allowance_and_emits() {
    let mut s = fresh();
    let out = op(
        &mut s,
        ALICE,
        FakePolicyAccounting::new(),
        IB20::approveCall { spender: BOB, amount: u(50) }.abi_encode(),

    assert_eq!(out, ok_true());
    read(&mut s, |t| assert_eq!(t.allowance(ALICE, BOB).unwrap(), u(50)));

    assert_root("approve", s, ROOT_APPROVE);
}

#[tokio::test]
async fn b20_blocklist_sender_policy_blocks_listed_accounts() {
    let mut scenario = B20PolicyScenario::new().await;

    let seed_bob =
        scenario.token_tx(IB20::transferCall { to: BerylTestEnv::bob(), amount: SEED_AMOUNT });
    let block = scenario.build_block(vec![seed_bob]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "seeding bob must succeed");
    scenario.assert_balance(BerylTestEnv::alice(), BerylTestEnv::B20_INITIAL_SUPPLY - 100_000);
    scenario.assert_balance(BerylTestEnv::bob(), 100_000);

    let blocklist_id = BerylTestEnv::policy_id(IPolicyRegistry::PolicyType::BLOCKLIST, 2);
    let create_policy = scenario.policy_tx(IPolicyRegistry::createPolicyCall {
        admin: BerylTestEnv::alice(),
        policyType: IPolicyRegistry::PolicyType::BLOCKLIST,
    });
    let block = scenario.build_block(vec![create_policy]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "createPolicy(BLOCKLIST) must succeed");

    let wire = scenario.token_tx(IB20::updatePolicyCall {
        policyScope: B20PolicyType::TransferSender.id(),
        newPolicyId: blocklist_id,
    });
    let block = scenario.build_block(vec![wire]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "updatePolicy must succeed");
