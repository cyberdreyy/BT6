### Title
Glob pattern `../` in the doublestar-split pattern segment bypasses working-directory containment check - ([File: commands/helpers/file_archiver.go])

### Summary
`findRelativePathInProject` validates that only the *base* (non-meta) portion of a `--path`/`--exclude` pattern resolves inside `c.wd`, then reattaches the meta pattern portion (`patt`) via `filepath.Join` without re-validating the final result. Because `patt` (the part of the pattern returned by `doublestar.SplitPattern` after the first meta character) can itself contain `../` segments, the final joined path can lexically collapse past `c.wd` and produce a path (or glob) that resolves outside the project working directory when passed to `doublestar.FilepathGlob`.

### Finding Description
In `commands/helpers/file_archiver.go`:

```go
base, patt := slashPath, ""
if strings.ContainsAny(slashPath, "*?[{") {
    base, patt = doublestar.SplitPattern(slashPath)
}
abs, err := filepath.Abs(base)
...
rel, err := filepath.Rel(c.wd, abs)
...
if strings.HasPrefix(rel, ".."+string(filepath.Separator)) || rel == ".." {
    return "", fmt.Errorf("artifact path is not a subpath of project directory: %s", path)
}
rel = filepath.Join(rel, patt)   // <-- patt is never validated
rel = filepath.FromSlash(rel)
return rel, nil
``` [1](#0-0) 

`doublestar.SplitPattern` splits a glob string at the path separator immediately preceding the *first* unescaped meta character (`*?[{`); everything after that boundary — including any further `/` and `..` segments the attacker places following a wildcard component (e.g. `subdir/*/../../../secret`) — is returned as `patt` and is **not** checked against `c.wd` at all. Only `base` (the literal prefix before the first meta char) is resolved and range-checked at lines 208-216 [2](#0-1) . The subsequent `rel = filepath.Join(rel, patt)` at line 219 performs a purely lexical `Clean`: if `patt` contains more `..` components than the depth already consumed by `rel`/`base`, Go's `filepath.Clean` cannot cancel them against real path segments and instead prepends literal `..` to the result, ie the reattached path escapes above `c.wd`. This joined, un-revalidated `rel` is returned directly to `processPath`, which feeds it straight into `doublestar.FilepathGlob(rel, ...)` [3](#0-2) , executed relative to the process CWD (which is `c.wd`). The same unchecked `rel` value is also used for `--exclude` matching via `isExcluded`/`doublestar.Match` [4](#0-3) .

The existing test suite only covers the case where `..` appears in the *base* segment before any wildcard (`"../*.*"`, expected to error) [5](#0-4) ; it does not cover `..` occurring in the pattern segment *after* the first meta character, which is the exact bypass this question describes. No test in the file exercises a pattern like `subdir/*/../../secret` or `foo/**/../../*.txt`.

### Impact Explanation
If exploitable, a pipeline author supplying a crafted `artifacts:paths` or `artifacts:exclude` glob (e.g. `subdir/*/../../../*` where `subdir` is one level deep) could cause the Runner's artifact archiver to walk and archive files located outside the job's designated build/working directory, i.e. read files that should be outside the sandboxed project root — matching the scoped impact of "unauthorized file access outside job roots via glob pattern injection."

### Likelihood Explanation
Preconditions are low-privilege and fully attacker-controlled: any user who can edit `.gitlab-ci.yml` (or otherwise control the `artifacts:paths`/`artifacts:exclude` values passed to `gitlab-runner artifacts-uploader`/`cache-archiver`, which use `fileArchiver.Paths`) can supply the crafted glob string. The bug is deterministic and repeatable given a fixed directory depth relationship between the job's CWD and the attacker-chosen `subdir` prefix (the number of `../` needed must match/exceed the depth consumed by `base`), which an attacker can arrange by choosing an existing subdirectory of the desired depth.

### Recommendation
After computing the final `rel = filepath.Join(rel, patt)` in `findRelativePathInProject`, re-validate that the fully joined path does not escape `c.wd` (e.g., re-run the same `..`-prefix check against the joined `rel`, or resolve the literal/non-glob portion of `patt` up front and reject if it contains `..` at all — glob patterns should not need `..` components). Alternatively, canonicalize `patt` before joining and reject any pattern whose lexically-cleaned combination with `rel` produces a path with a leading `..` segment or that is not a lexical descendant of `c.wd`.

### Proof of Concept
Add a test to `commands/helpers/file_archiver_test.go` alongside `TestFileArchiver_pathIsInProject`:

```go
func TestFileArchiver_patternWithDotDotAfterWildcardEscapesProject(t *testing.T) {
    wd, err := os.Getwd()
    require.NoError(t, err)

    c := &fileArchiver{wd: wd}

    // "subdir" is a single path component; three ".." after the wildcard
    // should be enough to walk back past wd if the base-only check is bypassed.
    path := filepath.Join("subdir", "*", "..", "..", "..", "secret", "*.txt")

    rel, err := c.findRelativePathInProject(path)
    require.NoError(t, err) // currently succeeds - this is the bug

    // Assert the returned rel does NOT escape wd once fully resolved.
    abs := filepath.Join(wd, rel)
    absClean := filepath.Clean(abs)
    assert.True(t, strings.HasPrefix(absClean, wd+string(filepath.Separator)) || absClean == wd,
        "resolved glob root %q escapes project working directory %q", absClean, wd)
}
```
Expected (current, buggy) result: `findRelativePathInProject` returns no error and a `rel` value that, once joined with `wd`, resolves to a path outside `wd` (e.g. `../secret/*.txt`), and `doublestar.FilepathGlob` in `processPath` would then match files under `secret/` outside the project directory. After the fix, this should return an error identical to the existing `"artifact path is not a subpath of project directory"` case.

Note: I could not directly inspect the vendored `bmatcuk/doublestar` v4 `SplitPattern` source in this index to confirm its exact split-boundary algorithm; the analysis above is based on its documented behavior (split at the last separator before the first unescaped meta character) plus Go's documented `filepath.Clean`/`Join` semantics for relative paths. The structural bug — that `patt` is never re-validated against `c.wd` after being rejoined at line 219 — is directly confirmed in the code and is independent of the precise doublestar split semantics.

}
