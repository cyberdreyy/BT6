### Title
Anyone can poison `IdleCDOPoLidoVariant`'s NFT queue so withdrawers receive a near-worthless poLido NFT while the CDO accounts a full redemption - (`contracts/IdleCDOPoLidoVariant.sol`)

### Summary
`IdleCDOPoLidoVariant` accepts any ERC721 via `onERC721Received` and, on withdrawal, blindly transfers the *last* poLido NFT held by the CDO to the withdrawer (`tokenIds[tokenIds.length - 1]`). Because the poLido NFT contract is `stMatic.poLidoNFT()` — a real ERC721 that anyone can mint by calling `stMatic.requestWithdraw` — an unprivileged attacker can mint a dust-valued withdrawal NFT and `safeTransferFrom` it to the CDO. The next withdrawer burns tranche tokens and reduces `lastNAV` at the full tranche price but receives the attacker's dust NFT instead of the NFT minted for their redemption.

### Finding Description
In `_withdraw` (`contracts/IdleCDOPoLidoVariant.sol:64-78`), after `_liquidate` triggers `IdlePoLidoStrategy._redeem` → `stMatic.requestWithdraw`, the CDO enumerates all poLido NFTs it owns and hands the last one to `msg.sender`:

```solidity
uint256[] memory tokenIds = stMatic.poLidoNFT().getOwnedTokens(address(this));
require(tokenIds.length != 0, "no NFTs");
...
uint256 tokenId = tokenIds[tokenIds.length - 1];
stMatic.poLidoNFT().safeTransferFrom(address(this), msg.sender, tokenId);
```

There is no check that the transferred `tokenId` is the one minted for this redemption, nor that its claim value (`stMatic.getMaticFromTokenId`) covers `toRedeem`. Meanwhile `onERC721Received` (`:81-88`) returns the receiver selector unconditionally, so any poLido NFT `safeTransferFrom`-ed to the CDO is retained and appended to `getOwnedTokens`. The same trust assumption exists in `IdlePoLidoStrategy._redeem` (`contracts/strategies/lido/IdlePoLidoStrategy.sol:131-137`), which also assumes the last-owned token is "the one we just minted" and even prices the redemption off that token via `getMaticFromTokenId(tokenId)`.

This is the same bug class as the report: an ERC721 delivered to the protocol through a bare transfer/`safeMint` is treated as protocol-owned collateral/output without validating provenance — here the operator/origin and claim amount are never checked.

### Impact Explanation
Direct theft from withdrawers. Sequence (running epoch, normal mode):

1. Attacker calls `stMatic.requestWithdraw(1 wei, attacker)`, receiving a poLido NFT worth ~0 MATIC.
2. Attacker `poLidoNFT.safeTransferFrom(attacker, idleCDO, dustTokenId)`. `onERC721Received` accepts it; it becomes the last entry of `getOwnedTokens(cdo)`.
3. Victim calls `withdrawAA`/`withdrawBB`. The CDO burns their tranche tokens, subtracts `toRedeem` (full tranche-price value) from `lastNAVAA`/`lastNAVBB`, but `safeTransferFrom`s `dustTokenId` to the victim.
4. The victim's NFT claims ~0 MATIC; their loss ≈ `toRedeem`. The CDO keeps the legitimate NFT minted by `_liquidate`, which the attacker (or owner) can later cause to be delivered to a subsequent withdrawal — repeating the theft each epoch of withdrawals.

Broken invariant: one redemption = one payout of `toRedeem` underlyings. The solvency accounting (NAV decremented by full `toRedeem`) diverges from the delivered claim value.

### Likelihood Explanation
High for any active PoLido-variant CDO. The attack requires no privileges, no approval, and only the gas cost of `stMatic.requestWithdraw` with a dust amount plus one NFT transfer. It can be timed to front-run any withdrawal since the ordering only requires the dust NFT to be the CDO's last-held token when `_withdraw` executes. The only caveat is that `IdleCDOPoLidoVariant`/`IdlePoLidoStrategy` are PoLido-specific deployments; if considered legacy, severity applies only to remaining TVL.

### Recommendation
- Record the expected NFT in `IdlePoLidoStrategy._redeem`: compute `tokenIds.length` before `requestWithdraw` (or use the returned `tokenId` / `getOwnedTokens` diff) and transfer exactly the newly minted token, not `tokenIds[length - 1]`.
- In `IdleCDOPoLidoVariant._withdraw`, track and transfer only the tokenId returned by `_liquidate`/strategy redeem rather than the last-owned NFT.
- Optionally restrict `onERC721Received` to accept only `msg.sender == address(stMatic.poLidoNFT())` with `operator == address(strategy)`/`address(this)` flow, i.e. reject direct user transfers (`operator != address(0)` / unexpected sender), so donated NFTs can't poison the queue.

### Proof of Concept
Foundry fork (mainnet, `ETH_RPC_URL`), building on `test/foundry/IdlePoLidoStrategy.t.sol` setup:

```solidity
function testNftPoisoningStealsWithdrawal() public {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);           // victim liquidity
    _cdoHarvest(true);
    skip(7 days); vm.roll(block.number + 1);

    // --- attacker (unprivileged EOA) ---
    address attacker = address(0xA77AC);
    deal(address(MATIC), attacker, 1);   // dust
    vm.startPrank(attacker);
    MATIC.approve(address(stMatic), 1);
    uint256 shares = stMatic.submit(1, attacker);          // dust stMATIC
    stMatic.approve(address(stMatic), shares);
    stMatic.requestWithdraw(shares, attacker);             // dust poLido NFT
    IPoLidoNFT nft = stMatic.poLidoNFT();
    uint256 dustId = nft.getOwnedTokens(attacker)[0];
    nft.safeTransferFrom(attacker, address(idleCDO), dustId); // accepted by onERC721Received
    vm.stopPrank();
    assertLt(stMatic.getMaticFromTokenId(dustId), 1e18);   // ~dust value

    // --- victim withdraws ---
    uint256 cdoNftBefore = nft.balanceOf(address(idleCDO));
    idleCDO.withdrawAA(IERC20Detailed(address(AAtranche)).balanceOf(address(this)));

    // victim received the attacker's dust NFT, not the NFT minted for their redemption
    uint256[] memory victimIds = nft.getOwnedTokens(address(this));
    uint256 received = victimIds[victimIds.length - 1];
    assertEq(received, dustId, "victim got attacker's dust NFT");
    assertLt(stMatic.getMaticFromTokenId(received), 1e18, "claim << toRedeem");

    // CDO still holds the legitimate withdrawal NFT, accounting already reduced NAV
    assertGt(nft.balanceOf(address(idleCDO)), 0);
}
```

Expected: victim's tranche tokens are burned and `lastNAVAA` reduced by the full `toRedeem`, but the delivered NFT claims ~0 MATIC — loss ≈ `toRedeem`, repeatable per withdrawal.
