### Title
Interactive web terminal `exec` ignores configured `Docker.User`, allowing privilege escalation within the container - ([File: executors/docker/terminal.go])

### Summary
`terminalConn.Start` builds `client.ExecCreateOptions` with only `TTY`, `AttachStdin/Stdout/Stderr`, and `Cmd` set, never populating `User`. When a runner administrator restricts the build container's execution user via `Docker.User` in the runner config, that restriction is applied to the main build container creation but is not propagated to the exec session created for the interactive web terminal, so the terminal process runs as the image's default user (frequently `root`).

### Finding Description
`commandExecutor.TerminalConnect` (`executors/docker/terminal.go:49-88`) constructs a `terminalConn` that only carries `containerID`, `client`, and `shell` — it does not carry or reference `s.Config.Docker.User` or any per-build resolved user value. `terminalConn.Start` (`executors/docker/terminal.go:101-115`) then issues:

```go
execConfig := client.ExecCreateOptions{
    TTY:          true,
    AttachStdin:  true,
    AttachStderr: true,
    AttachStdout: true,
    Cmd:          t.shell,
}
exec, err := t.client.ContainerExecCreate(t.ctx, t.containerID, execConfig)
```

There is no `User` field set. By contrast, elsewhere in `executors/docker/docker.go` the configured `Docker.User` is referenced (3 matches found for `Docker.User`) when the build container itself is created via `ContainerCreate`, meaning the main job commands run as the intended restricted user, but any interactive terminal `exec` spawned into that same container via `Session.execHandler -> newTerminalConn -> commandExecutor.TerminalConnect -> terminalConn.Start` does not inherit that restriction. Docker's `ContainerExecCreate` API defaults `User` to the container's image-defined user (often `root`) when the field is empty, regardless of what user the container's main process was started with.

An unprivileged pipeline author who has permission to open a web terminal session on their job (a standard GitLab feature, not requiring runner admin access) can therefore get an interactive shell running with more privileges (e.g., root) inside the container than the runner operator intended when they configured `Docker.User` to sandbox/restrict job processes.

### Impact Explanation
The scoped impact is privilege escalation within the container sandbox: a build container that the runner operator intentionally restricted to a low-privileged user for defense-in-depth can be interactively accessed as root (or whatever the image's default user is) through the terminal feature, undermining the `Docker.User` invariant. This does not break out of the container itself, but it defeats an explicit runner-enforced identity restriction, giving the job author stronger effective permissions inside the sandbox than configured (e.g., root-owned files, ability to install packages, modify permissions, or access resources gated by container-internal user checks).

### Likelihood Explanation
Preconditions are simple and fully attacker-reachable without any admin cooperation: the runner config sets `Docker.User`, and any pipeline author with the ability to open a job's web terminal (`/session/.../exec`) can trigger this path deterministically. No race conditions or special image contents are needed — the bug reproduces on every terminal session against such a runner.

### Recommendation
Propagate the resolved container user to the terminal exec: pass the same effective user used for `ContainerCreate` (derived from `Docker.User` / job-level or image-level user resolution) into `client.ExecCreateOptions.User` in `terminalConn.Start`. This requires threading the configured/resolved user value through `commandExecutor.TerminalConnect` into `terminalConn`.

### Proof of Concept
Go unit test in `executors/docker/terminal_test.go`:
1. Configure a `commandExecutor` with `Config.Docker.User = "restricteduser"`.
2. Call `TerminalConnect()` to get a `terminalConn`.
3. Mock `docker.Client.ContainerExecCreate` to capture the passed `client.ExecCreateOptions`.
4. Call `Start(...)`.
5. Assert `capturedOptions.User == "restricteduser"`.

Expected current behavior: the assertion fails because `capturedOptions.User == ""`, confirming the exec inherits the image's default user instead of the runner-configured restricted user. [1](#0-0)

func (s *commandExecutor) TerminalConnect() (terminalsession.Conn, error) {
	// Waiting for the container to start,  is not ideal as it might be hiding a
	// real issue and the user is not aware of it. Ideally, the runner should
	// inform the user in an interactive way that the container has no started
	// yet and should wait/try again. This isn't an easy task to do since we
	// can't access the WebSocket here since that is the responsibility of
	// `gitlab-terminal` package. There are plans to improve this please take a
	// look at https://gitlab.com/gitlab-org/gitlab-ce/issues/50384#proposal and
	// https://gitlab.com/gitlab-org/gitlab-terminal/issues/4

	timeout := s.terminalWaitForContainerTimeout
	if timeout == 0 {
		timeout = waitForContainerTimeout
	}
	containerID, err := s.watchForRunningBuildContainer(time.Now().Add(timeout))
	if err != nil {
		return nil, err
	}

	interactiveTerminalInfo := *s.Shell()
	interactiveTerminalInfo.Type = common.InteractiveShell

	interactiveShell, err := common.GetShellConfiguration(interactiveTerminalInfo)

	if err != nil {
		return nil, err
	}

	ctx, cancelFn := context.WithCancel(s.Context)

	return terminalConn{
		logger:      &s.BuildLogger,
		ctx:         ctx,
		cancelFn:    cancelFn,
		executor:    s,
		client:      s.dockerConn,
		containerID: containerID,
		shell:       interactiveShell.DockerCommand,
	}, nil
}

type terminalConn struct {
	logger   *buildlogger.Logger
	ctx      context.Context
	cancelFn func()

	executor    *commandExecutor
	client      docker.Client
	containerID string
	shell       []string
}

func (t terminalConn) Start(w http.ResponseWriter, r *http.Request, timeoutCh, disconnectCh chan error) {
	execConfig := client.ExecCreateOptions{
		TTY:          true,
		AttachStdin:  true,
		AttachStderr: true,
		AttachStdout: true,
		Cmd:          t.shell,
	}

	exec, err := t.client.ContainerExecCreate(t.ctx, t.containerID, execConfig)
	if err != nil {
		t.logger.Errorln("Failed to create exec container for terminal:", err)
		http.Error(w, "failed to create exec for build container", http.StatusInternalServerError)
		return
	}
