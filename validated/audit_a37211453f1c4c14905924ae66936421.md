### Title
Reentrancy in `EscrowDst._withdraw`/`EscrowSrc.cancel` allows repeated draining of native-token escrow balance before state is finalized - (File: contracts/BaseEscrow.sol, contracts/EscrowDst.sol, contracts/EscrowSrc.sol)

### Summary
Neither `BaseEscrow` nor its derivatives `EscrowSrc`/`EscrowDst` use a `nonReentrant` guard. `withdraw`, `publicWithdraw`, and `cancel` all perform multiple external value/token transfers (`_uniTransfer`/`_ethTransfer`) via low-level `.call{value: ...}("")` *before* the function returns, and there is no persistent per-escrow "already paid" flag that is set before these external calls. This is the same root-cause pattern as the Eggs Finance report: state-changing external calls happen without effects being finalized first, and no reentrancy lock exists to stop repeat execution of the payout logic within one transaction. [1](#0-0) [2](#0-1) 

### Finding Description
`EscrowDst._withdraw` performs up to four sequential external transfers using the fixed `immutables.amount` from a single deployed clone: integrator fee, protocol fee, maker payout, and safety deposit to the caller. [2](#0-1) 

When the destination token is native (`immutables.token.get() == address(0)`), every one of these transfers uses `_ethTransfer`, which is a raw `.call{value: amount}("")` — capable of invoking arbitrary code in the recipient: [1](#0-0) 

The `integratorFeeRecipient` and `protocolFeeRecipient` addresses are embedded in `immutables.parameters` and originate from the order's `extraData`/extension, which is attacker-controllable data supplied at order-creation time (the maker/integrator picks their own fee recipient address): [3](#0-2) [4](#0-3) 

The reentry vector into the same escrow is `publicWithdraw`, gated only by holding a nonzero balance of the (permissionless) access token — not an owner/whitelist check: [5](#0-4) [6](#0-5) 

Because `onlyValidImmutables`/`onlyValidSecret` only re-check the (immutable, unrevoked) hash and the already-revealed secret, and because there is no storage flag recording "already withdrawn" that is set before the external calls, a reentrant call into `publicWithdraw` during the fee transfer will pass all guards again and execute `_withdraw` a second (or Nth) time against the same escrow, paying out the same fee/maker/safety-deposit amounts again out of the escrow's native balance — as long as that balance holds out. This mirrors the Eggs Finance bug exactly: checks pass repeatedly because the vulnerable function has no reentrancy lock and does not finalize state/balance accounting before making the external call.

### Impact Explanation
For a native-token destination escrow, the contract's balance equals `safetyDeposit + amount` (fee amounts are carved out of `amount`, paid in the same native asset). An attacker who controls the `integratorFeeRecipient` contract (trivial — it's their own order's fee-recipient field) and also holds a de-minimis amount of the freely-tradable access token can, during the public-withdrawal window, trigger repeated re-entrant executions of `_withdraw` from within the fee-recipient's `receive()` hook using a raw `.call` that swallows failures instead of propagating a revert. Each successful nested call permanently pays out fee/maker/safety-deposit amounts again; only the final, insufficient-balance attempt fails, and since that failure is not propagated, all prior nested payouts remain committed. This drains the escrow's remaining native balance to the attacker/fee-recipient beyond the single intended payout — a direct theft of funds at rest in a production escrow contract during the live swap lifecycle, matching the bounty's Critical/High "theft of user funds" and "theft of unclaimed fee-like value" criteria.

### Likelihood Explanation
The only preconditions are: (1) using a native destination/source token escrow, (2) the attacker being the party that defines their own `integratorFeeRecipient` (fully within an unprivileged maker/integrator's control when constructing the order extension), and (3) holding a nonzero balance of the access token, which by design is meant to be broadly, permissionlessly obtainable to allow "public" withdraw/cancel. No admin, resolver whitelist, or governance role is required — this fits squarely in the "unprivileged user only" attacker model specified in the task.

### Recommendation
Add a `nonReentrant` modifier (OpenZeppelin `ReentrancyGuard` or a lightweight custom lock) to `withdraw`, `publicWithdraw`, and `cancel`/`publicCancel` in both `EscrowSrc` and `EscrowDst`, and follow checks-effects-interactions: mark the escrow as settled (e.g., via a boolean storage flag or by ensuring balance checks are strictly `<=` remaining escrowed funds) before performing any of the `_uniTransfer`/`_ethTransfer` external calls, particularly before sending funds to caller-supplied recipients (`integratorFeeRecipient`, `protocolFeeRecipient`).

### Proof of Concept
Note: I was not able to execute this against the test suite in this session (no tool access to run Foundry), so this PoC is a description of the exploit path based on static analysis of the cited code, not a verified trace/log. A background agent with repo/test access should implement and run this to confirm before treating it as fully validated:

1. Attacker (as maker) creates a cross-chain order whose extension `extraData` sets `integratorFeeRecipient` to a malicious contract they control, with `dstToken == address(0)` (native destination token) and a nonzero `integratorFee`. [7](#0-6) 
2. Order fills normally; `createDstEscrow` deploys `EscrowDst` funded with native `safetyDeposit + amount`. [8](#0-7) 
3. Attacker acquires a nonzero balance of the access token (permissionless) and waits for the `DstPublicWithdrawal` timelock stage. [6](#0-5) 
4. Attacker (or anyone) calls `publicWithdraw(secret, immutables)`. Inside `_withdraw`, the first `_uniTransfer` sends the native integrator fee to the attacker's malicious contract. [9](#0-8) 
5. The malicious contract's `receive()` uses a raw `.call` (ignoring the boolean return) to call `publicWithdraw(secret, immutables)` again on the same escrow, passing `onlyAccessTokenHolder`, `onlyValidImmutables`, and `onlyValidSecret` checks again, and repeats the full fee/maker/safety-deposit payout.
6. This recursion continues, each successful frame permanently paying out the same amounts again, until a nested attempt fails from insufficient balance; because that failure is swallowed (raw `.call`, no propagated revert), the outer transaction still finalizes with the previously executed nested payouts intact — draining more native balance from the escrow than a single legitimate withdrawal should release.

        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
