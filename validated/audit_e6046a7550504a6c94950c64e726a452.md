### Title
`BlockRejection` signature does not cover `reason`, `reason_code`, or `response_data`, allowing content-mutation of a signer's rejection while the signature still verifies - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` computes the signed digest solely from `signer_signature_hash` (plus `chain_id` baked into the structured-data domain). All the other fields of the struct — `reason`, `reason_code`, `response_data` (which carries `reject_reason` and `failed_txid`), and `metadata` — are **not** included in the signed payload, yet `verify()`/`recover_public_key()` only re-derive the digest from `signer_signature_hash`/`chain_id` and therefore accept any combination of the unsigned fields as long as the covered fields and signature match. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the `gitverify` bug class: a signature is nominally checked and "passes," but it doesn't actually authenticate all of the content that consumers subsequently trust as if it were signer-attested. Here, `BlockRejection.hash()`:

```rust
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
```
only commits to `signer_signature_hash` and `chain_id`. `verify()` and `recover_public_key()` both call `hash()` and check the ECDSA signature only against that narrow digest: [3](#0-2) 

Downstream code, however, treats the *entire* `BlockRejection` (including `reason_code`, `response_data.reject_reason`, `response_data.failed_txid`) as if it were authenticated by that same verified signature:

- The node-side listener trusts `rejected_data.reason_code` and `rejected_data.response_data.failed_txid` to accumulate per-signer weight toward flagging a transaction as "problematic," gated only on `recover_public_key()` matching the expected signer's pubkey: [4](#0-3) [5](#0-4) 

- The signer-side `handle_block_rejection` similarly recovers the pubkey, authenticates the sender against the stacking set, and then feeds `rejection.response_data.reject_reason` into `store_and_process_block_rejection`, treating the reject reason as signer-attested input to the local state machine: [6](#0-5) 

Because none of `reason`, `reason_code`, or `response_data` are covered by the signature, any party that can place a modified `BlockRejection` on the wire with the *same* `signer_signature_hash`/`chain_id`/`signature` as a genuinely-signed one (e.g. a relayer/gossip participant re-serializing the StackerDB chunk, or a signer replaying a previously-observed valid `(hash, signature)` pair with different unsigned fields) produces a message that both `verify()` and `recover_public_key()` accept as validly signed by the original signer, even though the semantic content (which rejection reason, which failed txid, which reason code) was never actually attested to.

### Impact Explanation
This breaks the equality "signed content == validated content": consumers believe `reason_code`/`reject_reason`/`failed_txid` are attributable to a specific signer's cryptographic signature, but they are not covered by it. Concretely:
- A node could accumulate `problematic_weight`/`total_weight`/tallies for an arbitrary attacker-chosen `failed_txid` or `RejectCode` under a real signer's identity, since only `signer_signature_hash` is checked.
- A signer's local state machine (`store_and_process_block_rejection`) makes decisions keyed off `reject_reason`, which is attacker-malleable content riding on a signature that only proves the signer once rejected *some* block with that `signer_signature_hash` — not that they rejected it for the substituted reason.

This is a cross-context-valid-signature class issue: a signature produced for one semantic payload (hash+chain_id only) is being accepted as proof for a broader payload (reason/response_data) that it never covered, letting a non-key-holder mutate signer-attributed metadata while preserving valid-looking verification.

### Likelihood Explanation
Reachable by any StackerDB message relay/gossip participant without needing a majority of signers or any signer's private key — they only need to observe one genuine `(signer_signature_hash, chain_id, signature)` tuple from a target signer (trivial, since these are broadcast) and can then substitute `reason`, `reason_code`, and `response_data` freely. The remaining open question (not fully verifiable from the indexed context) is whether the outer StackerDB chunk-level signature (in `libstackerdb`) independently authenticates the exact serialized byte content of the whole chunk; if it does, an external relay cannot smuggle a mutated chunk onto a legitimate signer's slot, which would limit this to the signer's own client-side inconsistency rather than a true third-party forgery. This should be confirmed with a live investigation of `libstackerdb`'s chunk signing/verification path.

### Recommendation
Include `reason`, `reason_code`, and all of `response_data` (and ideally `metadata`) in the structured-data hash committed to by `BlockRejection::hash()`, so that `verify()`/`recover_public_key()` cryptographically bind the entire semantically-significant content of the rejection to the signer's signature, not just `signer_signature_hash`/`chain_id`.

### Proof of Concept
Conceptual (pending confirmation of outer chunk-signing scope):
1. Observe a legitimately signed `BlockRejection` from signer S for block B with `signer_signature_hash = H`, `chain_id = C`, and some `reason_code`/`response_data`.
2. Construct a new `BlockRejection` with the same `H`, `C`, and `signature`, but arbitrary `reason`, `reason_code` (e.g. `ValidationFailed(ProblematicTransaction)`), and `response_data.failed_txid` pointing at an unrelated transaction.
3. Call `BlockRejection::verify(&S_pubkey)` / `recover_public_key()` on the mutated struct — both succeed because `hash()` only depends on `H`/`C`, which are unchanged.
4. Feed the mutated message into `stackerdb_listener.rs`'s handling loop or `stacks-signer`'s `handle_block_rejection` — both accept it as S's authenticated statement despite the reason/txid being forged.

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
}

    /// Handle an observed rejection from another signer
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
            (&rejection.response_data.reject_reason).into(),
        );
    }
