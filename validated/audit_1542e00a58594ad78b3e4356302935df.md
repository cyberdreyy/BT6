### Title
`EscapeForPosix` fails to hex-escape control characters, allowing raw ANSI/terminal escape injection into trace section preview when `posix_escape=true` - ([File: functions/script_legacy/internal/escape.go])

### Summary
`EscapeForPosix` only escapes backtick, double-quote, backslash, dollar, and select punctuation, leaving all C0 control bytes (0x00-0x1F, 0x7F), including ESC (0x1B) and BEL (0x07), untouched, unlike `EscapeForAnsiC` which explicitly hex-escapes them. Since `TraceSectionWriter.escape` routes to `EscapeForPosix` when `posixMode` is true (driven by the `posix_escape` step input, which mirrors `FF_POSIXLY_CORRECT_ESCAPES`), any control bytes present in the user-supplied `command` string reach the generated `printf` command line unescaped and get emitted verbatim into the job trace.

### Finding Description
`TraceSectionWriter.writeSectionStart` builds the preview line by concatenating `ansiBoldGreen + commandPrefix + command + ansiResetTrace` and passing it to `w.escape(...)`, which dispatches to `EscapeForPosix` when `posixMode` is true. [1](#0-0) [2](#0-1) 

`EscapeForPosix` iterates the input and only special-cases backtick/quote/backslash/dollar (backslash-escaped) and a small punctuation set (double-quoted), leaving every other byte — including control characters — copied through untouched: [3](#0-2) 

This directly contrasts with `EscapeForAnsiC`'s documented invariant that control characters (0x00-0x1F, 0x7F) and non-ASCII bytes must be hex-escaped "to prevent terminal manipulation" and "prevent jobs from clearing the screen or rewriting logs using ANSI escape sequences": [4](#0-3) 

This asymmetry is also visible in the test suites: `TestEscapeForAnsiC_SecurityFeatures` explicitly asserts hex-escaping of ESC sequences (`\x1b[2J`, `\x1b[10;20H`, etc.), while `TestEscapeForPosix` has no equivalent control-character/security test at all. [5](#0-4) [6](#0-5) 

The attacker-controlled input is the `command` string passed into `TraceSectionWriter.WriteSection`, which originates from the `script` array input of the `script_legacy` builtin function — a pipeline-author-controlled list of shell command strings (`scriptInput.GetListValue().GetValues()`), gated to trace-section handling only for multi-line commands, with `posixMode` set from the `posix_escape` boolean input: [7](#0-6) [8](#0-7) 

If a job's multi-line script command contains raw control bytes (e.g., a script line copied from a file, generated dynamically, or containing literal ESC/BEL bytes), and `posix_escape=true`, those bytes pass through `escape()` → `EscapeForPosix` unescaped and are written directly into the `printf '%s\n' ... section_start:...` line that becomes the collapsible-section preview text in the job trace. Because the output is delivered via `printf '%s\n'`, the raw control bytes are emitted verbatim into the log stream that the GitLab web trace viewer renders, allowing an attacker to inject cursor movement, line-clear, or color-manipulation sequences (or literal BEL) into the trace to visually spoof or hide subsequent log output within the same job's own trace.

The existing protection (`EscapeForAnsiC`'s hex-escaping) is bypassed specifically because it is not used in the `posixMode=true` branch; there is no other control-character sanitization anywhere in this call path before the string reaches the generated shell script / trace stream.

### Impact Explanation
Scoped impact is trace log spoofing within the job's own output: a job author who enables `posix_escape=true` (or when the corresponding `FF_POSIXLY_CORRECT_ESCAPES` behavior is mirrored) can craft a multi-line command whose text contains raw terminal control bytes that survive escaping and are written into the `section_start` preview line, letting the malicious content manipulate how that job's own trace is rendered in the web UI (e.g., overwrite/hide portions of the displayed log). This does not cross job/project boundaries, does not leak secrets, and does not escape the executor sandbox — it only affects rendering of the job's own trace output.

### Likelihood Explanation
Preconditions: `posix_escape=true` and `trace_sections=true` (trace sections apply only to multi-line commands) must both be enabled, and the attacker must control a multi-line script string containing raw control bytes. This requires the pipeline author to embed literal non-printable bytes in their own script definition, which is unusual but technically reachable (e.g., via heredoc content, base64-decoded strings interpolated into the command array, or CI variables containing raw escape sequences). The escaping gap itself is deterministic and trivially reproducible via a fuzz/unit test.

### Recommendation
Add hex-escaping (or otherwise neutralize) control characters (0x00-0x1F, 0x7F) in `EscapeForPosix`, mirroring `EscapeForAnsiC`'s behavior, before the string is quoted, e.g. extend the `switch` in `EscapeForPosix` with a default case that hex-escapes `r < 0x20 || r == 0x7F` (using an ANSI-C `$'...'` sub-quote if strict POSIX `"..."` double-quoting cannot represent `\xHH` hex escapes, since POSIX double-quoted strings do not support `\xHH`).

// EscapeForAnsiC escapes a string for use in ANSI-C quoting ($'...').
// Control characters and non-ASCII bytes are hex-escaped to prevent terminal manipulation.
// This prevents jobs from clearing the screen or rewriting logs using ANSI escape sequences.
// Matches GitLab Runner's ShellEscape behavior.
func EscapeForAnsiC(s string) string {
	var buf strings.Builder

	for i := 0; i < len(s); i++ {
		c := s[i]
		switch c {
		case '\\':
			buf.WriteString("\\\\")
		case '\'':
			buf.WriteString("\\'")
		case '\n':
			buf.WriteString("\\n")
		case '\r':
			buf.WriteString("\\r")
		case '\t':
			buf.WriteString("\\t")
		case '\a':
			buf.WriteString("\\a")
		case '\b':
			buf.WriteString("\\b")
		case '\f':
			buf.WriteString("\\f")
		case '\v':
			buf.WriteString("\\v")
		default:
			// Hex-escape control characters (0x00-0x1F, 0x7F) and non-ASCII (>0x7F)
			// This prevents ANSI escape sequences (ESC = 0x1B) from manipulating terminal
			if c < 0x20 || c == 0x7F || c > 0x7F {
				fmt.Fprintf(&buf, "\\x%c%c", hextable[c>>4], hextable[c&0x0f])
			} else {
				buf.WriteByte(c)
			}
		}
	}

	return buf.String()
}

func EscapeForPosix(s string) string {
	if s == "" {
		return "''"
	}

	var buf strings.Builder
	needsQuoting := false

	for _, r := range s {
		switch r {
		case '`', '"', '\\', '$':
			buf.WriteRune('\\')
			buf.WriteRune(r)
			needsQuoting = true
		case ' ', '!', '#', '%', '&', '(', ')', '*', '<', '=', '>', '?', '[', '|':
			buf.WriteRune(r)
			needsQuoting = true
		default:
			buf.WriteRune(r)
		}
	}

	if needsQuoting {
		return `"` + buf.String() + `"`
	}

	return buf.String()
}

// NewCommandProcessor creates a new command processor with the given configuration.
func NewCommandProcessor(config ScriptGeneratorConfig) *CommandProcessor {
	return &CommandProcessor{
		formatter:      NewCommandFormatter(config.PosixEscape),
		sectionWriter:  NewTraceSectionWriter(config.CheckForErrors, config.PosixEscape),
		checkForErrors: config.CheckForErrors,
		traceSections:  config.TraceSections,
	}
}

// ProcessCommand writes a single command to the buffer.
// Handles empty commands, trace sections, and normal commands.
func (p *CommandProcessor) ProcessCommand(buf *strings.Builder, index int, command string) {
	command = strings.TrimSpace(command)

	if command == "" {
		buf.WriteString("echo\n")
		return
	}

	if p.shouldUseTraceSection(command) {
		p.sectionWriter.WriteSection(buf, index, command)
	} else {
		p.writeNormalCommand(buf, command)
	}
}

func (p *CommandProcessor) shouldUseTraceSection(command string) bool {
	return p.traceSections && isMultiline(command)
}
