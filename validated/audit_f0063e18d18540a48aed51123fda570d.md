### Title
Withdraw instruction parser mislabels a range-proof context-state account as `owner` when only the minimum number of accounts is supplied - (File: transaction-status/src/parse_token/extension/confidential_transfer.rs)

### Summary
`parse_confidential_transfer_instruction`'s `Withdraw` branch only enforces `check_num_token_accounts(account_indexes, 4)`, i.e. a 4-account minimum, but the full semantic account layout for a Withdraw with both proofs supplied as `ContextStateAccount`s requires 5 accounts (`account`, `mint`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`, `owner`). An attacker can craft a transaction with exactly 4 accounts and `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0`, causing the parser to silently drop the `rangeProofContextStateAccount` field and instead label that same account as `owner` in the `jsonParsed` output.

### Finding Description
In the `Withdraw` arm at `transaction-status/src/parse_token/extension/confidential_transfer.rs`: [1](#0-0) 

the code walks a mutable `offset` starting at `2`, conditionally inserting `instructionsSysvar`, then `equalityProofContextStateAccount`, then `rangeProofContextStateAccount`, each gated by `offset < account_indexes.len().saturating_sub(1)` (reserving the last index for the `owner`/signer via `parse_signers`).

With `account_indexes.len() == 4` (the exact minimum allowed by `check_num_token_accounts(account_indexes, 4)`) and both `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0` (both proofs supplied as context-state accounts, requiring 5 real accounts: `account, mint, equality_ctx, range_ctx, owner`):

- `has_sysvar` is `false` (skip sysvar block).
- Equality block: `offset(2) < len-1(3)` → true → inserts `equalityProofContextStateAccount = account_keys[account_indexes[2]]`, `offset` becomes `3`.
- Range block: `offset(3) < len-1(3)` → false → skipped. `rangeProofContextStateAccount` is silently omitted, even though `range_proof_instruction_offset == 0` indicates it should be present.
- `parse_signers(map, 3, ...)` then labels `account_keys[account_indexes[3]]` as `"owner"`.

No index panic occurs (index `3` is within the 4-element `account_indexes` slice), satisfying the "no out-of-bounds panic" invariant, but the semantic labeling is wrong: the account at index 3 — which, per the real SPL Token-2022 confidential-transfer program layout, is meant to be the `rangeProofContextStateAccount` (a ZK proof context account, never a signer) — is reported as `owner` (a withdraw-authority signer). `decode_instruction_data` only depends on `instruction_data` bytes, so an attacker fully controls both offset fields independent of the account list length, and `check_num_token_accounts` performs no cross-check between the offset semantics and the number of accounts supplied.

The transaction need not execute successfully (the real program would separately fail due to a missing 5th account or an authority mismatch); it only needs to land on-chain as a failed transaction, which is still retrievable and parsed via `getTransaction` with `jsonParsed` encoding.

### Impact Explanation
This is a decoder misreporting bug (explicitly an accepted category): a non-signer, non-authority proof-context account is mislabeled as the withdraw `owner`/authority field in RPC `jsonParsed` output. Wallets, explorers, or any tooling relying on the parsed `owner` field for confidential-transfer withdraws could misattribute authority/control over the withdraw to an account that has no such role, and simultaneously the legitimate `rangeProofContextStateAccount` field silently disappears from the parsed output. Impact is scoped to RPC-level misreporting of account identity/roles for this instruction type; it does not affect consensus or validator execution.

### Likelihood Explanation
Fully attacker-controlled and reproducible with a single crafted transaction: exactly 4 accounts in the Withdraw instruction, `equality_proof_instruction_offset = 0`, `range_proof_instruction_offset = 0`. Since execution success is not required, the attacker only needs the transaction accepted into a block (even as a failed transaction) and later queried via `getTransaction` with `jsonParsed`. No special privileges, validator control, or race conditions needed — deterministic and always reproducible.

### Recommendation
Make `check_num_token_accounts` for `Withdraw` (and the analogous `Transfer`/`TransferWithFee` branches) dependent on the actual number of context-state accounts implied by the offset fields, rather than a fixed minimum of 4. Specifically, compute the required account count as `2 (account, mint) + (has_sysvar as usize) + (eq_offset==0 as usize) + (range_offset==0 as usize) + 1 (owner)` and validate `account_indexes.len()` against that derived value before assigning field labels, returning `ParseInstructionError::InstructionNotParsable` if the account list is insufficient rather than silently omitting fields and mislabeling the last account as `owner`.

### Proof of Concept
```rust
#[test]
fn test_withdraw_underspecified_accounts_mislabels_range_ctx_as_owner() {
    use spl_token_2022_interface::extension::confidential_transfer::instruction::WithdrawInstructionData;

    let account = Pubkey::new_unique();      // index 0
    let mint = Pubkey::new_unique();         // index 1
    let range_ctx_actual = Pubkey::new_unique(); // index 3 - should be rangeProofContextStateAccount
    let equality_ctx = Pubkey::new_unique(); // index 2

    // Build raw instruction data for Withdraw with both offsets == 0
    // (equality_proof_instruction_offset = 0, range_proof_instruction_offset = 0)
    let withdraw_data = WithdrawInstructionData {
        amount: 42.into(),
        decimals: 9,
        new_decryptable_available_balance: Default::default(),
        equality_proof_instruction_offset: 0,
        range_proof_instruction_offset: 0,
    };
    let instruction_data = encode_withdraw_instruction_data(&withdraw_data); // ConfidentialTransferInstruction::Withdraw tag + data

    // Only 4 accounts supplied (below the true 5-account minimum needed for
    // both proofs as ContextStateAccounts): account, mint, equality_ctx, range_ctx_actual
    let account_indexes: Vec<u8> = vec![0, 1, 2, 3];
    let account_keys = AccountKeys::new(&[account, mint, equality_ctx, range_ctx_actual], None);

    let parsed = parse_confidential_transfer_instruction(
        &instruction_data,
        &account_indexes,
        &account_keys,
    )
    .expect("should parse without panic");

    // Bug: rangeProofContextStateAccount is missing
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());

    // Bug: the actual range-proof context account is mislabeled as "owner"
    assert_eq!(
        parsed.info["owner"],
        json!(range_ctx_actual.to_string()),
        "range proof context account incorrectly reported as owner/authority"
    );
}
```
Expected (buggy) result: no panic occurs, `rangeProofContextStateAccount` is absent from `parsed.info`, and `owner` equals `range_ctx_actual`, demonstrating the misreported account identity described above.
