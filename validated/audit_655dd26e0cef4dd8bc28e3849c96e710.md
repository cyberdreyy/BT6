### Title
Cross-job pipeline run disclosure via unvalidated `:ID`/`:runID` binding in `Show` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Show` looks up a pipeline run solely by `runID` and never verifies that the run's `PipelineSpec.JobID` matches the `:ID` path parameter of the request. Any authenticated user (even one with only view-role) who can guess or enumerate a numeric `runID` can retrieve full run data — including `PipelineSpec` and task outputs — for a job they did not specify and may have no legitimate scope to.

### Finding Description
The route is registered as `GET /v2/jobs/:ID/runs/:runID` (see `core/web/router.go`), implying the run is scoped under job `:ID`. However `Show` completely ignores `c.Param("ID")`: [1](#0-0) 

It parses only `runID`, loads the run via `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)`, and returns it — with no comparison of `pipelineRun.PipelineSpec.JobID` (or any job-derived field) against the job ID from the URL. Compare this with `Index`, which does resolve and use the `:ID` job scope when querying `PipelineRuns` (`core/web/pipeline_runs_controller.go` lines 42-53), showing the intended invariant that a run is meant to be scoped to its job — an invariant `Show` fails to enforce.

The returned `presenters.PipelineRunResource` includes the full `PipelineSpec` (dot-graph pipeline spec, task run inputs/outputs/errors): [2](#0-1) 

so an attacker supplying job A's ID in the path but job B's `runID` receives job B's complete pipeline spec and run outputs, bypassing the path-based scoping that a client (or automated tooling relying on the URL structure) would assume is enforced server-side.

### Impact Explanation
This is an authorization/IDOR-class issue (broken object-level access control): a caller can retrieve `PipelineRun`/`PipelineSpec` data for a job outside the one named in the URL. On a Chainlink node, `PipelineSpec` and task outputs can reveal bridge names, external adapter URLs/params, contract addresses, and computed observations for jobs the caller should not be able to associate with the given job ID — providing reconnaissance value for further attacks (e.g., targeting the disclosed job's bridges/EAs, or later triggering/replaying that job's run once its correct job ID is inferred from the disclosed spec). Impact is confined to information disclosure of pipeline run/spec data reachable to any authenticated view-role user; it does not itself grant execution or fund-movement, but it does violate the request-binding invariant and directly returns attacker-uncontrolled-for job's data to a caller who only proved access to a different job.

### Likelihood Explanation
Feasible and repeatable with only view-role/read credentials since `Show` is a simple `GET` behind standard node-API authentication (session or API token) without any run→job ownership check. `runID`s are sequential integers (`pipeline.Run.ID`), making enumeration straightforward once any run ID range is known (e.g., from a job the attacker legitimately owns, or from `Index` for a job it can see). No special role beyond whatever minimal role guards this route is needed.

### Recommendation
In `Show`, after loading `pipelineRun`, additionally resolve the job ID from `c.Param("ID")` and verify `pipelineRun.PipelineSpec.JobID` matches it (return 404 on mismatch), mirroring the scoping done in `Index`.

### Proof of Concept
Add a table-driven handler test in `core/web/pipeline_runs_controller_test.go`:
1. Create Job A and Job B, each with a pipeline spec, and trigger a run for each via `CreateJobRun`/`RunJobV2`, capturing `runA.ID` and `runB.ID`.
2. Issue `GET /v2/jobs/{JobA.ID}/runs/{runB.ID}` as an authenticated view-role client.
3. Assert current (vulnerable) behavior: HTTP 200 and response body's `pipelineSpec` / run data corresponds to Job B, not Job A — i.e., `pipelineRun.PipelineSpec.JobID != JobA.ID` yet the request succeeds.
4. After fix, assert the same request returns 404/`ErrNoAffectedRows`-equivalent instead of Job B's data.

```go
func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
```
