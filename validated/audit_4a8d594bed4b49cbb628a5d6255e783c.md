### Title
Stale confirmations from deleted multisig members remain counted, allowing request execution below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts entries in the per-request `confirmations: HashSet<String>` against `self.num_confirmations` without verifying that every confirming identity is still a current member. `delete_member` only removes requests *created* by the removed member; it does not remove that member's confirmations recorded on other, still-pending requests. An account/key can therefore confirm a pending request, later be removed as a member (e.g., because it was compromised, offboarded, or malicious), and its confirmation still counts toward reaching `num_confirmations`, letting the request execute (e.g., a `Transfer`) with fewer live, currently-authorized confirmations than the configured threshold requires.

### Finding Description
The custody/authorization binding this contract is supposed to maintain is: `confirmations counted == confirmations from currently live members`. The code breaks this equality:

- `add_request`/`add_request_and_confirm` records confirmations in `self.confirmations: LookupMap<RequestId, HashSet<String>>` (`multisig2/src/lib.rs:126-128`, `188-207`).
- `delete_member` (`multisig2/src/lib.rs:356-379`) removes only requests where `r.member == member` (i.e., requests *originated* by that member), and clears `num_requests_pk`. It never iterates `self.confirmations` to strip the deleted member's `to_string()` entry from confirmation sets belonging to requests originated by *other* members.
- `confirm` (`multisig2/src/lib.rs:294-315`) simply checks `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide whether to execute — it treats every string in the stored `HashSet` as a valid, still-authorized confirmation, with no re-validation against the current `self.members` set at confirm/execution time.

So a confirmation cast while an account was a member persists as valid "weight" even after that account is deleted from `members`, permanently diverging the recorded confirmation count from the live authorized signer set.

### Impact Explanation
This directly matches the "multisig request executed below threshold" critical-impact class: a `Transfer` (or `AddKey`, `FunctionCall`, `DeployContract`, etc.) request can be executed with strictly fewer live, currently-trusted confirmations than `num_confirmations` mandates, because one or more of the counted confirmations belongs to a member who has since been removed. This is a NEAR-custody analog of the reported honeypot bug class: the state the buyer/other members rely on ("this request has K valid confirmations") diverges from reality ("only K-1 confirmations are from members currently entitled to authorize it"), and funds can move (or keys can be changed) without genuine current authorization.

### Likelihood Explanation
No privileged access is required beyond being a legitimate member who confirms a request before being removed — a normal operational sequence (e.g. rotating out a departing member or revoking a compromised key) rather than any adversarial setup that violates the exclusion rules. Any multisig using `DeleteMember` while requests are pending is exposed, and this is a completely unprivileged-attacker-reachable path once you're briefly a member.

### Recommendation
When executing `DeleteMember`, iterate all pending requests' `confirmations` sets and strip the deleted member's `to_string()` entry (not only requests it originated), or re-validate at `confirm`/execution time that every string in `confirmations` corresponds to a member still present in `self.members` before comparing the count against `self.num_confirmations`.

### Proof of Concept
1. Deploy multisig with members `{A, B, C, D}`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` for `Transfer{amount}` to some receiver → request `R` has confirmations `{A}`.
3. `B` calls `confirm(R)` → confirmations `{A, B}` (2/3, not yet executed).
4. Separately, members reach 3/4 confirmations on a `DeleteMember{B}` request, and it executes: `delete_member` removes `B` from `self.members`, but `R`'s confirmation set is untouched (`{A, B}` remains, since `R.member == A`, not `B`).
5. `C` calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations(3)` → `execute_request` runs the `Transfer`, even though the live confirming members are only `A` and `C` — one fewer than the configured 3-of-N threshold. [1](#0-0) [2](#0-1)
