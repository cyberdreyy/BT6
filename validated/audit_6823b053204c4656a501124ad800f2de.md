## Title
Removing a multisig member does not purge their existing confirmations, allowing a request to execute below the live-member threshold - (`multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`confirm()` counts entries in the `confirmations` set for a request and executes it once the count reaches `num_confirmations` [1](#0-0) . However, when a member is removed via `DeleteMember`/`DeleteKey`, the contract only deletes *requests that member originated*, not confirmation entries that member left on other still-pending requests [2](#0-1) . A stale confirmation from a since-removed member therefore still counts toward the quorum, letting a request execute with fewer live, currently-authorized signers than `num_confirmations` requires — the exact same class of bug as TRST-H-2 (confirmations/signatures counted vs. currently valid signers), just manifested via member removal instead of hat-wearer status change.

### Finding Description
The intended invariant of the multisig is: a request executes only once **`num_confirmations` currently-live members** have confirmed it. The code instead checks `confirmations.len() + 1 >= self.num_confirmations` where `confirmations` is a `HashSet<String>` of member identifiers collected over time [3](#0-2) .

`delete_member()` is the only place that prunes stale state on removal, and it filters `self.requests` by `r.member == member` — i.e., it removes requests *authored by* the removed member — but never scans `self.confirmations` values (the sets of confirming members per request) to strip out the removed member's votes from requests authored by someone else [4](#0-3) . The equivalent v1 contract has the same gap: `DeleteKey` removes requests where `r.signer_pk == pk` but does not scrub that `pk` from `confirmations` on other requests [5](#0-4) .

The only safeguard on removal is `self.members.len() - 1 >= self.num_confirmations`, which guards against `num_confirmations` exceeding the *count* of members, but does nothing about *stale identities* still embedded in a pending request's confirmation set [6](#0-5) .

### Impact Explanation
This breaks the equality "confirmations counted == live members who confirmed." Concretely, with 4 members {A, B, C, D} and `num_confirmations = 3`:
1. A creates request R (`add_request`); B confirms it → `confirmations[R] = {B}`.
2. Separately, A, C, D reach 3-of-4 quorum on a `DeleteMember{B}` request, executing it. `delete_member` removes B from `members` (now {A, C, D}, still `num_confirmations = 3`), but R's confirmation set still contains B.
3. C confirms R: `len({B,C})=2`, `2+1=3 < 3`? No — `2+1 >= 3` is true, so R executes with confirmations `{B, C}` plus C's own confirm — i.e., R executes after only C (and B's now-invalid vote) instead of 3 live members (A, C, D) ever approving it.

R (which can be an arbitrary `Transfer`, `FunctionCall`, `AddKey`, etc.) executes having been approved by only 1–2 genuinely live members instead of the mandated `num_confirmations` live members — a multisig request executed below the effective live threshold, matching the Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
This requires no privileged action beyond normal multisig operation: any member can create/confirm a request, and member removal is a standard, expected multisig action (`DeleteMember`/`DeleteKey`). Any account or key removal event while other requests are pending with that member's confirmation attached triggers the flaw — a routine operational sequence (rotate out a compromised or departing signer while other transfers/requests are in flight), not a contrived edge case.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate all entries in `self.confirmations` (not just `self.requests` filtered by author) and remove the departing member's/key's confirmation from every pending request's confirmation set (deleting the request's confirmation record entirely, or requiring re-confirmation) so that stale, no-longer-valid signatures cannot count toward quorum.

### Proof of Concept
Given `multisig2::MultiSigContract::new(members: [A,B,C,D], num_confirmations: 3)`:
```
1. as A: add_request(R)                     // requests[R] created, confirmations[R] = {}
2. as B: confirm(R)                          // confirmations[R] = {B}
3. as A: add_request(D2 = DeleteMember{B})   // separate request
4. as A: confirm(D2)                         // confirmations[D2] = {A}
5. as C: confirm(D2)                         // confirmations[D2] = {A,C}
6. as D: confirm(D2)                         // 2+1>=3 -> executes delete_member(B)
                                              // members = {A,C,D}; num_confirmations still 3
                                              // confirmations[R] still = {B} (stale, not purged)
7. as C: confirm(R)                          // confirmations[R] = {B,C}; check len=1+1=2 < 3 -> stored
8. as D... (not needed) -- recompute: after step7 len=2, 2>=3 false so stored {B,C}
9. as C(again not allowed) -- use remaining live member: as D: confirm(R)
                                              // confirmations[R]={B,C}, len=2, 2+1=3>=3 -> executes R
```
R executes having received live confirmations only from C and D (2 of the 3 currently required, live) members — B's confirmation is stale/phantom since B is no longer a member — demonstrating execution below the effective live-member threshold. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
