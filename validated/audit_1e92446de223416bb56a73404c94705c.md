### Title
`SortitionsView::check_proposal` computes `last_sortition`'s own timeout but never gates the `ProposedBy::LastSortition` branch on it - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`check_proposal` independently evaluates whether `last_sortition` has timed out and updates `last_sortition.miner_status` accordingly, but the later `ProposedBy::LastSortition` match arm only checks `self.cur_sortition.miner_status`, never `last_sortition.miner_status`. A miner who won the historical "last sortition" slot can therefore get a proposal validated via the `LastSortition` fallback even though that same miner's own tenure has independently timed out under the identical rule.

### Finding Description
In `stacks-signer/src/chainstate/v1.rs`, `check_proposal` first evaluates `cur_sortition`'s timeout [1](#0-0) , then separately evaluates `last_sortition`'s own timeout and, if timed out, sets `last_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock` [2](#0-1) .

Later, when the proposal's `consensus_hash` matches `last_sortition`, the code resolves `ProposedBy::LastSortition` [3](#0-2) , and the gating check in the `match proposed_by` block only inspects `self.cur_sortition.miner_status`: [4](#0-3) 

`last_sortition.miner_status` — which was just set to `InvalidatedBeforeFirstBlock` if that miner's own tenure timed out — is never read again anywhere in the function (confirmed via search: it is only ever *written*, at the two lines noted above, and never consulted afterward). So the only condition to accept a `LastSortition`-attributed block is that `cur_sortition` has timed out; `last_sortition`'s own independently-computed timeout state is discarded.

Attack: an attacker who legitimately won the historical `last_sortition` miner slot (one unprivileged slot) crafts/replays a `BlockProposal` with `consensus_hash` equal to `last_sortition`'s consensus hash, signed with their own miner key (so the `miner_pkh` check at line 276 passes trivially — it's their own slot). They gossip this via the normal StackerDB/proposal path a signer already consumes. If they time the proposal to arrive after `cur_sortition` has crossed `block_proposal_timeout` (setting `cur_sortition.miner_status = InvalidatedBeforeFirstBlock`), the `ProposedBy::LastSortition` branch will authorize the proposal to proceed to further checks (tenure-change/parent validation) — regardless of whether `last_sortition` itself has *also* crossed the exact same `block_proposal_timeout` and was just marked `InvalidatedBeforeFirstBlock` a few lines earlier in the same call.

The existing test `check_block_proposal_timeout` [5](#0-4)  does not actually exercise this scenario: it only calls `signer_db.insert_burn_block` for the current sortition's consensus hash [6](#0-5) , so `last_sortition`'s own `is_timed_out` check at [7](#0-6)  short-circuits to `Ok(false)` (no recorded receive time for `last_sortition`'s consensus hash), meaning `last_sortition.miner_status` is never actually flipped to `InvalidatedBeforeFirstBlock` in that test. Consequently the test's final assertion that a `last_sortition_block` validates after the sleep does **not** prove the code correctly handles the case where `last_sortition` is *also* timed out — it only proves the fallback works when `last_sortition` is still healthy. No test in the suite drives `last_sortition` itself past `block_proposal_timeout` and then asserts rejection.

### Impact Explanation
This breaks the intended liveness/staleness invariant that a signer should not sign for a miner whose tenure the signer's own rules have deemed abandoned. If `last_sortition` is allowed through despite being independently timed out, a signer can approve/sign a block from a miner two sortitions stale — a miner the signer has already (by its own logic) invalidated. This is an inconsistent application of the exact same rule (`is_timed_out` with `block_proposal_timeout`) applied to `cur_sortition` versus `last_sortition`, and it lets a non-canonical/abandoned miner's block pass local sortition-view validation, contributing to a signer potentially signing for a stale/non-canonical tenure. This is repeatable by any attacker each time they hold a "last sortition" slot and a stale window opens.

### Likelihood Explanation
Preconditions: `cur_sortition` and `last_sortition` both near/past `block_proposal_timeout` (a legitimate liveness-degraded but plausible network condition — e.g., two consecutive slow/absent miners), and the attacker must have legitimately won the `last_sortition` miner slot (one BTC-won slot, no privileged role required). The attacker only needs to gossip a `BlockProposal` for that slot's consensus hash timed after `cur_sortition` times out — a single-slot, low-cost, and repeatable action requiring no other signer's key or the auth token. Whether this actually causes a *signed* block by the network is bounded by the fact that other checks (tenure-change/parent confirmation checks at lines 319–339) still run afterward and could independently reject a genuinely stale/malformed tenure structure; however, the specific staleness/timeout gate itself is bypassed, which is the flaw the question targets.

### Recommendation
In the `ProposedBy::LastSortition` match arm, additionally check `last_sortition.miner_status == SortitionMinerStatus::Valid` (i.e., reject if `last_sortition.miner_status != SortitionMinerStatus::Valid`), consistent with how `ProposedBy::CurrentSortition` requires `sortition.miner_status == SortitionMinerStatus::Valid`. This ensures a stale `last_sortition` miner cannot be authorized merely because `cur_sortition` also timed out.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/v1.rs` (extending `check_block_proposal_timeout`):
1. Call `setup_test_environment`, build `curr_sortition_block` and `last_sortition_block` as in the existing test.
2. Insert burn-block receive times for **both** `cur_sortition.data.consensus_hash` and `last_sortition.data.consensus_hash` via `signer_db.insert_burn_block`, so both sortitions have a real `is_timed_out` clock (unlike the current test which only registers `cur_sortition`).
3. Sleep past `config.block_proposal_timeout` for both.
4. Call `view.check_proposal(..., &curr_sortition_block, ...)` and assert `Err` (current miner timed out) — same as today.
5. Call `view.check_proposal(..., &last_sortition_block, ...)` and assert `Err(RejectReason::InvalidMiner)` (or a new dedicated reject reason), asserting that `view.last_sortition.as_ref().unwrap().miner_status == SortitionMinerStatus::InvalidatedBeforeFirstBlock` was consulted and caused rejection — this assertion currently fails (the proposal wrongly validates) under the unpatched code, and passes once the fix in `stacks-signer/src/chainstate/v1.rs` lines 301–316 checks `last_sortition.miner_status` as well.

#[test]
fn check_block_proposal_timeout() {
    let (stacks_client, mut signer_db, block_sk, mut view, mut curr_sortition_block) =
        setup_test_environment(function_name!());
    curr_sortition_block.header.consensus_hash = view.cur_sortition.data.consensus_hash.clone();
    curr_sortition_block.header.sign_miner(&block_sk).unwrap();

    let mut last_sortition_block = curr_sortition_block.clone();
    last_sortition_block.header.consensus_hash = view
        .last_sortition
        .as_ref()
        .unwrap()
        .data
        .consensus_hash
        .clone();
    last_sortition_block.header.sign_miner(&block_sk).unwrap();

    // Ensure we have a burn height to compare against
    let burn_hash = view.cur_sortition.data.burn_block_hash.clone();
    let consensus_hash = view.cur_sortition.data.consensus_hash.clone();
    let burn_height = 1;
    let received_time = SystemTime::now();
    signer_db
        .insert_burn_block(
            &burn_hash,
            &consensus_hash,
            burn_height,
            &received_time,
            &view.last_sortition.as_ref().unwrap().data.burn_block_hash,
        )
        .unwrap();

    view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &curr_sortition_block,
        false,
        ReplayTransactionSet::none(),
    )
    .expect("Proposal should validate");

    view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &last_sortition_block,
        false,
        ReplayTransactionSet::none(),
    )
    .expect_err("Proposal should not validate");

    // Sleep a bit to time out the block proposal
    std::thread::sleep(Duration::from_secs(5));
    view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &curr_sortition_block,
        false,
        ReplayTransactionSet::none(),
    )
    .expect_err("Proposal should not validate");

    view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &last_sortition_block,
        false,
        ReplayTransactionSet::none(),
    )
    .expect("Proposal should validate");
}
