### Title
Stale confirmations from deleted multisig keys are still counted toward the confirmation threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` decides whether a request has reached the required threshold by counting the size of the `HashSet<PublicKey>` stored in `self.confirmations` for that request, without verifying that every public key in that set still corresponds to a currently-authorized access key on the account. When the `DeleteKey` action removes a member's key, the contract only purges requests and confirmations *originated by* that key — it never scans other pending requests to strip that key's stale confirmation out of their confirmation sets. This breaks the binding "confirmations counted == confirmations from live members," letting a request execute with fewer live signers than `num_confirmations` requires.

### Finding Description
`confirm()` reads the confirmation set for a request and treats its cardinality as the count of currently-valid approvals: [1](#0-0) 

The threshold check is `confirmations.len() as u32 + 1 >= self.num_confirmations`, purely a set-size comparison; it never re-validates that each already-recorded public key in the set is still an active access key on the contract.

When a `DeleteKey` request executes, the removal logic only targets requests whose *creator* (`signer_pk`) is the deleted key: [2](#0-1) 

```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter(|(_k, r)| r.signer_pk == pk)
    .map(|(k, _r)| k)
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
self.num_requests_pk.remove(&pk);
promise.delete_key(pk)
```

This code only removes confirmation sets for requests **created** by the removed key. It does not iterate over `self.confirmations` to strip that key's public key out of the confirmation `HashSet`s belonging to other, still-pending requests that this key had previously confirmed. Consequently, a confirmation recorded by a key that has since been revoked (via `DeleteKey`) remains permanently counted in `confirmations.len()` for any request it confirmed prior to its removal.

The equality this breaks: `confirmations counted for request R == number of confirmations from access keys currently valid on the account`. After a `DeleteKey` execution, the left side can exceed the right side.

### Impact Explanation
This falls under the "Critical" impact category explicitly listed in scope: "a multisig request executed below threshold." Concretely:
- Members A, B, C exist with `num_confirmations = 3`.
- A pending request R1 (created by some key) is confirmed by A and B (2/3), leaving R1 one confirmation short.
- The members then execute a separate, legitimate `DeleteKey` request removing B's key (e.g. B is compromised, offboarded, or rotated).
- R1's confirmation set still contains B's now-revoked public key; `confirmations.len()` for R1 is still 2.
- A single additional confirmation from the sole remaining live key (C, or even a newly added key D) pushes `confirmations.len() + 1 >= 3`, executing R1 with only 2 currently-valid signers (C and D) even though B's stale approval is still being counted toward the total — effectively executing with fewer live-key approvals than `num_confirmations` mandates.
- The receiver-controlled `execute_request` can perform `Transfer`, `FunctionCall`, `AddKey`/`DeleteKey`, or `DeployContract` actions, so funds can move or account control can change under a weakened, stale-approval quorum.

### Likelihood Explanation
Likelihood is realistic in normal multisig operation, not a contrived edge case: key rotation/offboarding via `DeleteKey` is an expected, routine multisig action, and pending unconfirmed requests coexisting with a key-removal action is a common real-world sequence (e.g., revoking a departing member's key while other requests are mid-flight). No attacker privilege beyond being one of the legitimate signers is required, and no code path currently prevents or cleans up this state.

### Recommendation
When executing `MultiSigRequestAction::DeleteKey`, iterate over all entries in `self.confirmations` (not just requests created by the removed key) and remove the deleted public key from every confirmation `HashSet`. Alternatively, validate at `confirm()` time (or before computing the threshold) that every public key present in a request's confirmation set is still present among the account's current access keys, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
Conceptual sequence (unit-test style, mirroring existing multisig test patterns such as `test_multi_3_of_n` in [3](#0-2) ):
1. Initialize `MultiSigContract::new(3)` with three access keys A, B, C.
2. `add_request` a `Transfer` request R1 as key A; `confirm(R1)` with A (1 confirmation) and B (2 confirmations) — R1 not yet executed (2 < 3).
3. `add_request_and_confirm` a `DeleteKey{public_key: B}` request as key C; get it confirmed by A and C (assume threshold met for this single-action request) → executes, calling `promise.delete_key(B)`. Note R1 is not among the requests filtered/removed, since R1 was created by A, not B — so `self.confirmations` for R1 still contains B's key.
4. Confirm R1 with key C: `confirmations.len()` for R1 is still 2 (A, B), `+1 = 3 >= num_confirmations(3)` → R1 executes, transferring funds, even though only A and C are live keys (B was deleted) — i.e., only 2 live-key approvals authorized a 3-of-n action.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
