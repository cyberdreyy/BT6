I found a concrete analog: `signerdb.rs::add_block_rejection_signer_addr` / `get_block_rejection_signer_addrs` explicitly *removes* a signer's rejection once they sign (see the `reject_then_accept` test), so the signer-side (`stacks-signer/src/v0/signer.rs`) tally is correct and self-healing. However, the **node-side coordinator tally in `stackerdb_listener.rs` has no such correction** — it never removes a signer's weight from `total_weight_rejected` after that same signer later accepts, and the accept branch uses a different, independent guard (`gathered_signatures.contains_key`) than the reject branch (`responded_signers.insert`). This is the exact class of bug in the report: a running tally that fails to account for a value that should have been subtracted/reconciled when the underlying position changed (there, `totalRewardsEgress`; here, a superseded rejection weight).

### Title
Stale rejection weight is never reconciled against a later acceptance, allowing double-counted signer weight to falsely trigger `SignersRejected` on the coordinator - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block using two independent, uncoordinated guards. A signer who first sends `BlockResponse::Rejected` and later legitimately (or maliciously) sends `BlockResponse::Accepted` for the *same* block has their weight added to `total_weight_approved` without ever being subtracted from `total_weight_rejected`. The two counters are supposed to represent a partition of live signer opinion (each signer counted at most once, in the category matching their *current* vote), but the coordinator's bookkeeping permanently retains stale rejection weight.

### Finding Description
In `handle_block_response`-equivalent processing inside `StackerDBListener::run` (`stackerdb_listener.rs`):

- The **Accepted** branch guards weight addition with `if !block.gathered_signatures.contains_key(&slot_id)` [1](#0-0) .
- The **Rejected** branch guards weight addition with `if block.responded_signers.insert(slot_id)` [2](#0-1) .

These are two separate data structures (`gathered_signatures: BTreeMap<u32, MessageSignature>` vs `responded_signers: HashSet<u32>`) [3](#0-2) , and neither branch checks the other's structure or clears the opposite tally when a signer's vote flips. Concretely:

1. Slot `X` sends `Rejected` first → `responded_signers.insert(X)` succeeds → `total_weight_rejected += weight(X)`.
2. Slot `X` later sends `Accepted` for the *same* `block_sighash` → the accept-branch guard checks only `gathered_signatures.contains_key(X)`, which is still `false` (X never sent a signature before) → `total_weight_approved += weight(X)` is applied *again*, and `total_weight_rejected` is **never decremented**.

By contrast, the signer's own local bookkeeping in `signerdb.rs` explicitly clears a rejection when a later signature is recorded for the same address/block, as proven by the `reject_then_accept` unit test: after `add_block_signature` succeeds, `get_block_rejection_signer_addrs` returns empty for that block [4](#0-3) . The coordinator's `StackerDBListener` tally has no equivalent reconciliation step, so it diverges from the semantics the signer side itself enforces.

A signer legitimately transitions from `LocallyRejected` back to `LocallyAccepted` via `should_reevaluate_reject_reason` for several reject reasons (e.g. `ConnectivityIssues`, `NoSortitionView`, `NoSignerConsensus`, `ConsensusHashMismatch`) [5](#0-4) , and the `docs/signer-flows.md` state diagram documents `LocallyRejected --> LocallyAccepted : re-evaluated` as a normal path [6](#0-5) . This is not a hypothetical edge case — it is a supported, reachable transition triggered by a single signer's own messages over StackerDB (gossip), requiring no majority or other party's key.

### Impact Explanation
The coordinator uses these two counters to decide the fate of a block proposal in `signer_coordinator.rs`:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... SignersRejected ... }
else if block_status.total_weight_approved >= self.weight_threshold { ... accepted ... }
``` [7](#0-6) 

Because `total_weight_rejected` can never decrease once incremented, a signer's weight that legitimately superseded its own rejection with an acceptance still counts toward the rejection threshold forever for that block hash. If enough weight accumulates in `total_weight_rejected` from signers who have since actually accepted (flipped their vote), the coordinator can declare the block `SignersRejected` even though the *current* opinion of the signer set, reflected by `total_weight_approved`, would otherwise reach or exceed the acceptance threshold. This is a liveness wedge: a block that has effectively been accepted by the required weight of signers can be discarded by the miner/coordinator due to phantom, un-reconciled rejection weight, causing repeated re-proposals or a stalled tenure — a High-severity impact matching "a signer wedged into never signing valid blocks" analog at the coordinator layer, since valid, ultimately-approved proposals can be discarded.

### Likelihood Explanation
This requires only a single signer (or a small number of signers) sending two ordinary, protocol-legal messages — `BlockResponse::Rejected` followed later by `BlockResponse::Accepted` for the same `signer_signature_hash` — which is an explicitly supported re-evaluation path in the v0 signer state machine (`should_reevaluate_reject_reason`). No majority collusion, no other signer's key, and no StackerDB-sync exploitation is needed; it can arise from perfectly normal network conditions (e.g., a signer that rejected due to `ConnectivityIssues` or `NoSortitionView` and later validated and signed once conditions resolved), making it readily triggerable by gossip alone.

### Recommendation
Reconcile the two tallies at the coordinator: when an `Accepted` message is processed for a slot that is already present in `responded_signers` due to a prior rejection, subtract that signer's weight from `total_weight_rejected` (and vice versa, should the reverse ever be observed) before applying the new tally, so `total_weight_approved` and `total_weight_rejected` continue to reflect only each signer's current vote — mirroring the correction already implemented in `signerdb.rs`'s `add_block_signature`/`add_block_rejection_signer_addr` pairing.

### Proof of Concept
1. Miner proposes block `B`; coordinator opens `BlockStatus` with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer `S` (weight `w`) initially rejects `B` (e.g., transient `ConnectivityIssues`) → StackerDB carries `BlockResponse::Rejected` from `S` → coordinator: `responded_signers.insert(S)` succeeds, `total_weight_rejected += w`.
3. `S` re-evaluates per `should_reevaluate_reject_reason` and later signs and broadcasts `BlockResponse::Accepted` for the same `B`.
4. Coordinator's accept-branch guard (`gathered_signatures.contains_key(S)`) is `false` (first signature from `S`), so `total_weight_approved += w` is applied — `S`'s weight now counted in *both* totals; `total_weight_rejected` is untouched.
5. Repeat with additional signers who follow the same reject→accept path until `total_weight_rejected.saturating_add(weight_threshold) > total_weight` is satisfied purely from stale, superseded rejection weight, even though `total_weight_approved` from the same signers would independently satisfy the acceptance threshold — the coordinator returns `Err(SignersRejected{...})` for a block the signer set has actually approved.
