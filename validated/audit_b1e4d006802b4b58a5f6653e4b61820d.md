**Analysis:**

The premise misattributes code. The "no excess `pending_inactive` is inactivated" special-case logic referenced in the question lives in `withdraw_internal`, not `unlock_internal`: [1](#0-0) 

`unlock_internal` itself performs only a straightforward transfer of coins/shares from `active_shares` to the pool's current-OLC `pending_inactive_shares_pool`, with no special-case branching: [2](#0-1) 

Crucially, `pending_inactive_shares_pool` at a given observed lockup cycle (OLC) is a **single shared shares pool** across all co-delegators. When a second delegator calls `unlock` after the validator has left the set (as in the extended `test_inactivate_no_excess_stake` scenario), it simply buys proportional shares into that same shared pool via `buy_in_pending_inactive_shares`: [3](#0-2) 

The bulk inactivation event that eventually happens (either at `join_validator_set_internal`'s lockup settlement or during epoch processing) merges the entire `pending_inactive` coin balance into `inactive` on the stake pool at once, not selectively per delegator: [4](#0-3) 

Because the shares-pool math (`amount_to_shares`/`redeem_shares`) tracks each delegator's proportional ownership precisely, this bulk inactivation is distributed pro-rata across all shareholders in that OLC's pool — it does not "corrupt" or misattribute one delegator's balance to another. This is exactly the invariant validated by `test_inactivate_no_excess_stake`, which confirms `pending_inactive` is not inactivated prematurely while the validator is inactive but lockup unexpired, and that both the validator's and delegator's shares correctly reflect their proportional inactive amounts once the OLC eventually advances: [5](#0-4) 

The invariant "withdrawing pending_inactive stake does not inactivate additional stake" is specific to the excess-stake escape mechanism in `withdraw_internal` (reactivate-then-withdraw-then-restore pattern), which only executes on `withdraw`, not `unlock`. An unprivileged delegator calling `unlock` in this window does not trigger `withdraw_internal`'s excess-stake logic at all, so this invariant is not implicated by the described call sequence. The proof idea's premise — that a second delegator's `unlock` would be affected by "the first's OLC advance" via `unlock_internal`'s special case — does not correspond to any code path that exists; no such special case exists in `unlock_internal`, and the shared shares-pool accounting already correctly isolates each delegator's proportional balance under bulk inactivation.
