### Title
Loss-adjusted withdraw receipts escape their haircut because `lossRecoveryPriceByEpoch` is keyed to the post-stop epoch number - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records a stop-epoch loss under `lossRecoveryPriceByEpoch[epochNumber]`, but `deposit()` increments `epochNumber` during `stopEpoch` before `collectWithdrawFunds` runs. Withdraw receipts are stored under the request-time epoch `N`, while the haircut is stored under `N+1`. `_claimLossAdjustedWithdrawRequest` therefore never sees the price for epoch `N`, and loss-adjusted receipts are paid out at par through the funded path.

### Finding Description
The Discourse bug class — hidden per-version data leaking through an adjacent visible version — maps here to a per-epoch receipt haircut that is hidden from the claim path by an off-by-one epoch key:

- `requestWithdraw` tags receipts with `epochNumber` at request time: `withdrawsRequestsByEpoch[_user][currentEpoch]` and `lastWithdrawRequest[_user] = currentEpoch` (lines 260-293). [1](#0-0) 
- `deposit()` increments `epochNumber` while `isEpochRunning()` is still true, i.e. inside `stopEpoch`, before `collectWithdrawFunds` executes (lines 607-611). [2](#0-1) 
- `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber]`, which is now `N+1`, while every pending receipt funded by that stop was recorded under epoch `N` (lines 411-421). [3](#0-2) 
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0, returns 0, and the claim falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` at par (lines 789-801, 338-349). [4](#0-3) 
- The `requestWithdraw` guard at lines 263-271 also reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, so it never blocks re-requests — the haircut epoch is invisible everywhere it should apply. [5](#0-4) 

`previewLossAdjustedWithdrawFunds` already computed that only `pendingBasis - pendingLoss` should be collected, and `collectWithdrawFunds` transfers exactly that reduced amount while zeroing `pendingWithdraws`. The vault then owes full receipts but holds only the haircut-funded amount.

### Impact Explanation
Invariant broken: pending-receipt loss waterfall / one receipt one haircut-adjusted payout. The first claimant(s) drain the vault at par; once `balance < amount` the remaining legitimate claimants' `safeTransfer` reverts — permanent freezing of unclaimed funded withdrawals, or direct theft of funds belonging to other pending receipt holders and (via `_transferFundedClaim`'s reserve guard at lines 897-907) effective shortfall absorption by the recovery reserve's protection. Quantified loss equals `pendingLoss` = the difference between `pendingBasis` and the collected amount, socialized onto whoever claims last. The attacker only needs a `requestWithdraw` during a running epoch followed by an early `claimWithdrawRequest` after `stopEpochWithDuration` — an ordinary lender action.

### Likelihood Explanation
Requires a `stopEpochWithDuration(_lossAmount > 0)` with pending receipts — a borrower partial-repayment event, an honest manager path, not an attacker privilege. The bug is deterministic given the `deposit()` → `collectWithdrawFunds` ordering inside `stopEpoch`; no race or privileged misbehavior needed. The one uncertainty is the exact call ordering inside `IdleCDOEpochVariant.stopEpoch`: if `collectWithdrawFunds` were invoked before the `strategy.deposit` that bumps `epochNumber`, the keys would align and the issue would not manifest. The `deposit()` comment ("deposit done on stopEpoch (before setting the var to false)") confirms the increment happens mid-stop, and funding collection is necessarily a late step (it pulls underlyings the CDO just received), so misalignment is the expected outcome.

### Recommendation
Record the loss under the epoch the receipts were tagged with, not the bumped counter. Options:
- Pass the request epoch explicitly: have the CDO pass `epochNumber - 1` (or the pre-increment value) to `collectWithdrawFunds`, and store `lossRecoveryPriceByEpoch[_claimEpoch]`.
- Or capture `pendingEpoch` alongside `pendingWithdraws` in `requestWithdraw`/`collectWithdrawFunds` so the haircut key cannot drift from the receipt key.
- Also key `_claimLossAdjustedWithdrawRequest` on the epoch recorded in `withdrawsRequestsByEpoch` rather than only `lastWithdrawRequest`, as a defense-in-depth measure.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCreditVault` + `IdleCDOEpochVariant`):

```solidity
// Setup: vault with manager-set APR, KYC'd lender `alice`, borrower funded.
// Epoch N running.
uint256 epochN = vault.epochNumber();

// 1. Alice requests withdraw of 100e6 underlying (via CDO withdrawRequest).
cdo.requestWithdraw(100e6); // -> vault.requestWithdraw(100e6, alice, principal)
assertEq(vault.lastWithdrawRequest(alice), epochN);
assertEq(vault.withdrawsRequestsByEpoch(alice, epochN), 100e6);

// 2. Manager stops epoch with a loss: borrower repays less than owed,
//    so previewLossAdjustedWithdrawFunds says pendingToFund = 90e6.
//    Inside stopEpoch: strategy.deposit(...) bumps epochNumber to N+1,
//    then collectWithdrawFunds(90e6) stores
//    lossRecoveryPriceByEpoch[N+1] = 0.9e18  (NOT epoch N).
vm.prank(manager);
cdo.stopEpochWithDuration(lossAmount, duration);
assertEq(vault.epochNumber(), epochN + 1);
assertEq(vault.lossRecoveryPriceByEpoch(epochN), 0);        // hidden haircut
assertEq(vault.lossRecoveryPriceByEpoch(epochN + 1), 0.9e18);

// 3. Alice claims. _claimLossAdjustedWithdrawRequest reads
//    lossRecoveryPriceByEpoch[N] == 0 -> skipped;
//    _claimFundedWithdrawRequest pays withdrawsRequests[alice] = 100e6 AT PAR,
//    while the vault only received 90e6 for all pending receipts.
uint256 balBefore = underlying.balanceOf(alice);
cdo.claimWithdrawRequest(alice); // -> vault.claimWithdrawRequest
assertEq(underlying.balanceOf(alice) - balBefore, 100e6); // got 100e6, expected 90e6

// 4. A second lender bob with the remaining pending receipt now finds
//    balance < claim -> his claim reverts (frozen funds), or
//    absorbs alice's overpayment if other funded liquidity exists.
vm.expectRevert(); // SafeERC20 low-level / NotAllowed
cdo.claimWithdrawRequest(bob);
```

Expected result without the bug: `lossRecoveryPriceByEpoch[N] == 0.9e18`, alice receives `100e6 * 0.9e18 / 1e18 = 90e6`, and bob's claim succeeds at his haircutted share.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
