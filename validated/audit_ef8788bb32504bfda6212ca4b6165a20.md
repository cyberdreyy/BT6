### Title
Unbounded per-slot signature materialization in `find_address_signatures_for_slot` ignores outer `limit`, allowing RPC cost proportional to on-chain data size for `getSignaturesForAddress` - (File: ledger/src/blockstore.rs)

### Summary
`Blockstore::find_address_signatures_for_slot` iterates and collects **all** `AddressSignatures` column entries for a given `(pubkey, slot)` pair into an in-memory `Vec<(Slot, Signature, u32)>` before any truncation occurs. This full-slot materialization happens unconditionally on every call to `get_confirmed_signatures_for_address2` (and thus every `getSignaturesForAddress` RPC), regardless of the caller-supplied `limit`, including `limit = 1`.

### Finding Description
`find_address_signatures_for_slot` opens a forward iterator over the `address_signatures_cf` column family starting at `(pubkey, slot, 0, Signature::default())` and pushes every matching `(pubkey, slot)` entry into `signatures` until the slot or address changes: [1](#0-0) 

This function takes no `limit` parameter at all, so it cannot early-exit based on how many results the caller actually wants.

It is called unconditionally from `get_confirmed_signatures_for_address2` to fetch "signatures in `slot`" (the resolved starting slot, either `highest_slot` or the slot derived from the `before` signature), *before* the outer `limit`-bounded loop and *before* the final `.take(limit)` truncation: [2](#0-1) [3](#0-2) 

The RPC handler `JsonRpcRequestProcessor::get_signatures_for_address` passes the caller's `limit` straight through to `get_confirmed_signatures_for_address2` without any pre-check that would bound blockstore work independent of on-chain data size: [4](#0-3) 

The only limit enforcement is `verify_and_parse_signatures_for_address_params`, which bounds `limit` to `MAX_GET_CONFIRMED_SIGNATURES_FOR_ADDRESS2_LIMIT` (1000) but has no effect on the size of the single-slot pre-fetch: [5](#0-4) 

Root cause: the initial-slot fetch is implemented as "get everything for this slot, then filter/reverse," rather than being bounded by `limit`. An attacker who fills a slot with transactions that all reference their own address (writable or read-only key) causes every one of those transactions to be indexed under `(attacker_pubkey, slot, tx_index, signature)` in `AddressSignatures` via `write_transaction_status`/`add_transaction_status_to_batch`: [6](#0-5) 

A subsequent `getSignaturesForAddress(attacker_pubkey, limit=1)` call that resolves to that slot (e.g. as `highest_slot`, or via `before` pointing into that slot) forces `find_address_signatures_for_slot` to materialize one tuple per transaction in the slot referencing the address, even though only 1 result was requested.

### Impact Explanation
The cost of a single, legitimately-rate-limited `getSignaturesForAddress` call becomes proportional to the number of transactions the attacker packed into one slot referencing their own address, not to the requested `limit`. This is an "unbounded cost for a single low-rate call" pattern: the per-request work and allocation size are controlled by attacker-supplied on-chain data (transactions-per-slot for one address) rather than by the RPC's own `limit` parameter, violating the intended invariant that request cost should be bounded by explicit limits. The practical ceiling is the runtime's per-block transaction/cost limits, but that ceiling is far larger than what a `limit=1` caller should require, so this is a real (if bounded by block-level limits) amplification of memory allocation and CPU per RPC call.

### Likelihood Explanation
Fully attacker-controlled and reproducible with a single unprivileged client: fill one slot with the maximum number of transactions all referencing the attacker's own address (feasible since the attacker chooses the account keys of their own transactions), then issue one `getSignaturesForAddress` call at legal rate with `limit=1` targeting that slot. No special privileges, leader/validator control, or multiple clients are required — a single call demonstrates the disproportionate work, matching the exact behavior already exercised (with far fewer transactions) by `test_find_address_signatures_for_slot`: [7](#0-6) 

### Recommendation
Thread the caller's `limit` (and remaining budget) into `find_address_signatures_for_slot` so the forward iterator stops once `limit` matching entries have been collected for the initial slot, instead of always draining the full per-slot range. Alternatively, restructure `get_confirmed_signatures_for_address2` to use a single bounded iterator across the initial slot and subsequent slots rather than special-casing a full-slot pre-fetch.

### Proof of Concept
```rust
// ledger/src/blockstore/tests.rs
#[test]
fn test_find_address_signatures_for_slot_ignores_limit() {
    let ledger_path = get_tmp_ledger_path_auto_delete!();
    let blockstore = Blockstore::open(ledger_path.path()).unwrap();

    let attacker = solana_pubkey::new_rand();
    let slot = 1;
    const N: u32 = 50_000; // representative "max transactions in a slot" for the attacker's address

    for x in 0..N {
        let signature = Signature::from({
            let mut bytes = [0u8; 64];
            bytes[..4].copy_from_slice(&x.to_le_bytes());
            bytes
        });
        blockstore
            .write_transaction_status(
                slot,
                signature,
                vec![(&attacker, true)].into_iter(),
                TransactionStatusMeta::default(),
                x as usize,
            )
            .unwrap();
    }

    // find_address_signatures_for_slot has no `limit` parameter and must
    // materialize all N entries even though a downstream caller only wants 1.
    let signatures = blockstore
        .find_address_signatures_for_slot(attacker, slot)
        .unwrap();
    assert_eq!(signatures.len(), N as usize);

    // A limit=1 RPC-level call still pays the full N-sized allocation cost
    // internally, via get_confirmed_signatures_for_address2's initial-slot fetch,
    // before any truncation to `limit` occurs.
    let result = blockstore
        .get_confirmed_signatures_for_address2(attacker, slot, None, None, 1)
        .unwrap();
    assert_eq!(result.infos.len(), 1);
    // Expected fix: an internal counter/instrumentation showing the initial-slot
    // fetch allocated only up to `limit` entries, not N.
}
```
Expected current behavior: `find_address_signatures_for_slot` returns a `Vec` of length `N`, proving the allocation and iteration cost scales with attacker-controlled transactions-per-slot, independent of the outer `limit=1`.

    // Returns all signatures for an address in a particular slot, regardless of whether that slot
    // has been rooted. The transactions will be ordered by their occurrence in the block
    fn find_address_signatures_for_slot(
        &self,
        pubkey: Pubkey,
        slot: Slot,
    ) -> Result<Vec<(Slot, Signature, u32)>> {
        let (lock, lowest_available_slot) = self.ensure_lowest_cleanup_slot();
        let mut signatures: Vec<(Slot, Signature, u32)> = vec![];
        if slot < lowest_available_slot {
            return Ok(signatures);
        }
        let index_iterator = self.address_signatures_cf.iter(IteratorMode::From(
            (
                pubkey,
                slot.max(lowest_available_slot),
                0,
                Signature::default(),
            ),
            IteratorDirection::Forward,
        ))?;
        for ((address, transaction_slot, transaction_index, signature), _) in index_iterator {
            if transaction_slot > slot || address != pubkey {
                break;
            }
            signatures.push((transaction_slot, signature, transaction_index));
        }
        drop(lock);
        Ok(signatures)
    }
