Found it. This is a critical bug: `mark_pre_committed` calls `self.valid = Some(true)` and stamps `approved_time` **before** attempting the state transition via `move_to`. If `move_to` fails (returns `Err`), those side effects are **not rolled back** — exactly the "assume success on a call that can silently signal failure differently than expected" class of bug from the report (there, `token.transfer` reverts instead of returning `false`, so the caller's own bookkeeping/expectations diverge from actual on-chain effect; here, the mutation happens unconditionally while the guarded transition can fail, so the record's `valid`/`approved_time` fields diverge from its `state`).

### Title
Partial state mutation on failed `mark_pre_committed`/`mark_locally_rejected` transition corrupts `BlockInfo.valid` independent of `state` - (File: stacks-signer/src/signerdb.rs)

### Summary
`BlockInfo::mark_pre_committed` and `mark_locally_rejected` set `self.valid` (and, for pre-commit, `approved_time`) unconditionally, then call `self.move_to(state)`, which can fail and return `Err` while leaving `state` unchanged. Every caller in `stacks-signer/src/v0/signer.rs` (`handle_block_validate_ok`, `handle_block_pre_commit`) treats the `Err` case as recoverable/ignorable when `has_reached_consensus()` is true or `state == LocallyAccepted`, but never resets `valid`/`approved_time` on failure. [1](#0-0) 

### Finding Description
`mark_pre_committed` does:
```
self.valid = Some(true);
self.approved_time.get_or_insert(get_epoch_time_secs());
self.move_to(BlockState::PreCommitted)
```
`move_to` only succeeds from `Unprocessed` (`check_state`: `PreCommitted => matches!(prev_state, BlockState::Unprocessed)`). If the block is already `LocallyRejected` (i.e., previously invalidated by `check_block_against_signer_db_state`), `move_to` returns `Err`, but `self.valid` has already been flipped to `Some(true)`. The caller in `handle_block_validate_ok` swallows this error whenever `has_reached_consensus() || state == LocallyAccepted`: [2](#0-1) 
In that swallow path, the code proceeds to `insert_block` (persisting `valid = true` even though `state` is still `LocallyRejected`), then unconditionally calls `send_block_pre_commit` and `handle_block_pre_commit` for a block this signer had already rejected. `handle_block_pre_commit`'s own gate, `if !block_info.valid.unwrap_or(false) { return; }`, is defeated because `valid` was mutated to `true` regardless of the failed transition: [3](#0-2) 
This breaks the intended equality "signed vs validated": `valid` is supposed to encode "this signer determined the block is valid", but it can now be `true` on a record whose `state` still says `LocallyRejected`, and that stale/incorrect `valid=true` is exactly what downstream pre-commit/consensus tallying reads to decide willingness to sign.

### Impact Explanation
A signer can end up broadcasting a pre-commit (and potentially contributing signing weight toward a threshold) for a block it previously locally rejected, because the `valid` flag was corrupted to `true` by the side-effecting `mark_pre_committed` call whose guarded `move_to` failed. This is the class of "a rejection recounted as an accept" — the signer's own bookkeeping says rejected (`state == LocallyRejected`), but the flag consulted by pre-commit/threshold logic says validated. This directly matches the High/Critical impact criteria: a signer contributing toward a pre-commit/signature threshold for a block it had determined invalid.

### Likelihood Explanation
This requires no majority collusion — it is triggered purely by the ordinary flow of a single signer receiving a validate-OK response for a block that it (locally) had already marked `LocallyRejected` via `check_block_against_signer_db_state`, which can legitimately happen on races between validation responses, re-proposals, and chainstate re-checks that are explicitly documented as occurring "between validation and threshold." This is a plausible, one-slot-triggerable timing condition, not a theoretical corner case.

### Recommendation
Make `mark_pre_committed`, `mark_locally_accepted`, and `mark_locally_rejected` transactional with respect to `move_to`: only mutate `valid`/`approved_time`/`signed_self`/`signed_group` after confirming the state transition succeeds (or roll back the mutation on `Err`), e.g.:
```rust
pub fn mark_pre_committed(&mut self) -> Result<(), String> {
    self.move_to(BlockState::PreCommitted)?;
    self.valid = Some(true);
    self.approved_time.get_or_insert(get_epoch_time_secs());
    Ok(())
}
```
Apply the same pattern to the other `mark_*` methods so a failed state transition never leaves `valid`/timestamps in a state inconsistent with `state`.

### Proof of Concept
1. Signer receives a block proposal, validates it, and `check_block_against_signer_db_state` flags a conflict → `mark_locally_rejected()` succeeds (`state = LocallyRejected`, `valid = Some(false)`).
2. A late/duplicate `BlockValidationResponse::Ok` for the same `signer_signature_hash` arrives (plausible given documented races: "we may have signed a different block... the world must be re-checked"), and this time `check_block_against_signer_db_state` returns `None` (conflict resolved/stale).
3. `handle_block_validate_ok` calls `block_info.mark_pre_committed()`; internally `self.valid = Some(true)` runs, then `move_to(PreCommitted)` fails because `prev_state == LocallyRejected` (not `Unprocessed`), returning `Err`.
4. Because `!block_info.has_reached_consensus()` may be false (e.g. it has since reached `GloballyRejected` from peer rejections) or `state == LocallyAccepted` is checked incorrectly, the guard at [4](#0-3)  does not `return`, and code falls through to `insert_block` (persisting `valid = true` with `state = LocallyRejected`) and calls `send_block_pre_commit` / `handle_block_pre_commit`.
5. `handle_block_pre_commit`'s check `!block_info.valid.unwrap_or(false)` now passes (since `valid == Some(true)`), so the signer counts/broadcasts a pre-commit for a block it had substantively rejected, corrupting the accept/reject accounting. [5](#0-4)

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }

    /// Attempt to transition the block state
    pub fn move_to(&mut self, state: BlockState) -> Result<(), String> {
        if !self.check_state(state) {
            return Err(format!(
                "Invalid state transition from {} to {state}",
                self.state
            ));
        }
        self.state = state;
        Ok(())
    }
