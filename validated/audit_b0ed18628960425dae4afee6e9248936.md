Based on my investigation, I found a concrete counting-symmetry bug in the node-side signing coordinator that mirrors the `reversed_swap`/`match_orders` asymmetry pattern from the external report: two code paths that are supposed to maintain mutually-exclusive tallies (accepted-weight vs. rejected-weight) use different de-duplication keys, allowing the same signer's weight to be counted into *both* buckets for the same block.

### Title
Signer weight double-counted into both `total_weight_approved` and `total_weight_rejected` for the same block due to inconsistent de-duplication keys - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` maintains a per-block `BlockStatus` with two weight tallies, `total_weight_approved` and `total_weight_rejected`, that the miner's `SigningCoordinator` uses to decide whether a block is accepted, rejected, or still pending. The `Accepted` and `Rejected` message handlers use two *different* guards to decide whether a signer's weight has already been counted, so a signer that sends both an `Accepted` and a `Rejected` `BlockResponse` for the same `signer_signature_hash` has its weight added to both tallies.

### Finding Description [1](#0-0) 
counts a signer's weight into `total_weight_approved` only when `!block.gathered_signatures.contains_key(&slot_id)`, and then unconditionally inserts the slot into `block.responded_signers`. [2](#0-1) 
counts a signer's weight into `total_weight_rejected` only when `block.responded_signers.insert(slot_id)` succeeds (i.e., the slot was *not* already in `responded_signers`).

Because the accept path's gate (`gathered_signatures`) and the reject path's gate (`responded_signers`) are different sets, a signer can:
1. Send `Rejected` first → `total_weight_rejected` increases, `responded_signers` now contains the slot.
2. Later send `Accepted` for the *same* `signer_signature_hash` → since `gathered_signatures` does not yet contain the slot, `total_weight_approved` also increases by the same signer's weight, and `gathered_signatures`/`responded_signers` are updated.

The result is that the same signer's weight is now present in both `total_weight_approved` and `total_weight_rejected`, breaking the invariant that a signer contributes to exactly one side of the tally for a given block — the same "asymmetric bookkeeping between two code paths" defect class as the reported `reversed_swap` vs. `match_orders` bug (one path increments/returns a counter correctly, the other path uses an inconsistent gate).

### Impact Explanation
`SigningCoordinator::run` (the consumer of `BlockStatus`) uses these two independently-computed weights to decide the block's fate: [3](#0-2)  bails with `SignersRejected` once `total_weight_rejected + weight_threshold > total_weight`, or accepts once `total_weight_approved >= weight_threshold`. With the double-count, `total_weight_rejected` and `total_weight_approved` no longer sum to at most `total_weight`, so both thresholds can be satisfied with fewer *distinct* signers than the 70% weight the protocol intends, or a rejection threshold can be crossed prematurely because previously-accepted signers' weight is also folded into the rejection count (or vice versa). Since the actual signatures used to build the block still come from `gathered_signatures` (real recovered signatures), this does not directly let an invalid block get a forged/insufficient signature set — `NakamotoBlockHeader::verify_signer_signatures` [4](#0-3)  independently re-derives weight strictly from the signatures actually present in the header. The practical impact is therefore a liveness/decision-quality defect in the miner's coordinator loop (premature `SignersRejected`, or reaching the "accepted" branch from `block_status.gathered_signatures` before real threshold-worth of accept signatures exist in some interleavings), not a chain-consensus safety break, since the header-level check remains the final gate.

### Likelihood Explanation
Triggering this requires only a single signer sending both `Accepted` and `Rejected` `BlockResponse` messages for the same `signer_signature_hash` over StackerDB — something normally prevented by the signer's own local state machine (`signer.rs` comments state a signer should not change its vote for the same block without a new proposal), but nothing in the miner-side `StackerDBListener` enforces or re-validates that invariant on the receiving end. A buggy, out-of-date, or malicious single-slot signer, or a replay of stale StackerDB chunks, can produce this sequence without needing any majority.

### Recommendation
Use a single, shared per-signer "already counted" gate for both the accept and reject paths (e.g., always check/set `responded_signers` before adding weight to either tally, and only allow a slot to contribute to one of `total_weight_approved` or `total_weight_rejected`, matching the design intent already documented in `stacks-signer/src/v0/signer.rs` that a signer's vote is fixed per block unless a new proposal is created).

### Proof of Concept
1. Signer S (slot N, weight W) sends `BlockResponse::Rejected` for sighash H → `responded_signers` = {N}, `total_weight_rejected += W`.
2. Signer S then sends `BlockResponse::Accepted` for the same sighash H (e.g., due to a bug, a stale/duplicated relay, or a byzantine signer) → since `gathered_signatures` does not contain N, `total_weight_approved += W` as well.
3. Now `total_weight_approved + total_weight_rejected` includes W twice, even though only one signer (weight W) actually participated — violating the intended mutual exclusivity of the two tallies used by `SigningCoordinator::run` to reach an accept/reject decision.

    pub fn verify_signer_signatures(
        &self,
        reward_set: &RewardSet,
        epoch_id: StacksEpochId,
    ) -> Result<u32, ChainstateError> {
        let message = self.signer_signature_hash();
        let Some(signers) = reward_set.signers() else {
            return Err(ChainstateError::InvalidStacksBlock(
                "No signers in the reward set".to_string(),
            ));
        };

        // if this is a shadow block, then its signing weight is as if every signer signed it, even
        // though the signature vector is undefined.
        if self.is_shadow_block() {
            return Ok(self.get_shadow_signer_weight(reward_set)?);
        }

        let mut total_weight_signed: u32 = 0;
        // `last_index` is used to prevent out-of-order signatures
        let mut last_index = None;
        // Before Epoch 4.0, signature order check contained a bug, so gate the
        // strict ordering behavior on the epoch.
        let strict_order = epoch_id.enforces_strict_signature_order();

        let total_weight = reward_set
            .total_signing_weight()
            .map_err(|_| ChainstateError::NoRegisteredSigners(0))?;

        // HashMap of <PublicKey, (Signer, Index)>
        let mut signers_by_pk: HashMap<_, _> = signers
            .iter()
            .enumerate()
            .map(|(i, signer)| (&signer.signing_key, (signer, i)))
            .collect();

        for signature in self.signer_signature.iter() {
            let public_key = Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(
                message.bits(),
                signature,
            )
            .map_err(|_| {
                ChainstateError::InvalidStacksBlock(format!(
                    "Unable to recover public key from signature {}",
                    signature.to_hex()
                ))
            })?;

            let mut public_key_bytes = [0u8; 33];
            public_key_bytes.copy_from_slice(&public_key.to_bytes_compressed()[..]);

            let (signer, signer_index) = signers_by_pk.remove(&public_key_bytes).ok_or_else(|| {
                warn!(
                    "Found an invalid public key. Reward set has {} signers. Chain length {}. Signatures length {}",
                    signers.len(),
                    self.chain_length,
                    self.signer_signature.len(),
                );
                ChainstateError::InvalidStacksBlock(format!(
                    "Public key {} not found in the reward set",
                    public_key.to_hex()
                ))
            })?;

            // Enforce order of signatures
            if let Some(index) = last_index.as_ref() {
                if *index >= signer_index {
                    return Err(ChainstateError::InvalidStacksBlock(
                        "Signatures are out of order".to_string(),
                    ));
                }
                if strict_order {
                    last_index = Some(signer_index);
                }
            } else {
                last_index = Some(signer_index);
            }

            total_weight_signed = total_weight_signed
                .checked_add(signer.weight)
                .expect("FATAL: overflow while computing signer set threshold");
        }

        let threshold = Self::compute_voting_weight_threshold(total_weight)?;

        if total_weight_signed < threshold {
            return Err(ChainstateError::InvalidStacksBlock(format!(
                "Not enough signatures. Needed at least {} but got {} (out of {})",
                threshold, total_weight_signed, total_weight,
            )));
        }

        return Ok(total_weight_signed);
