### Title
Any workflow owner can exhaust the node-wide `Global` workflow-activation quota, blocking legitimate owners from activating workflows - (`core/services/workflows/syncerlimiter/limiter.go`, `core/services/workflows/v2/engine.go`)

### Summary
The CRE workflow engine enforces workflow-activation capacity with a two-tier resource pool: a `PerOwner` limit and a `Global` limit shared across all workflow owners on a node. Because workflow registration/activation is a low-cost, self-service action available to any workflow owner (not an admin/operator), an owner can register and activate enough workflows to consume the entire shared `Global` capacity, causing `ErrGlobalWorkflowCountLimitReached` for every other owner attempting to activate a workflow on that node — mirroring the reported pattern of a cheap, permissionless action exhausting a shared per-resource quota and denying service to legitimate users.

### Finding Description
`syncerlimiter.NewWorkflowLimits` builds a `MultiResourcePoolLimiter[int]{owner, global}` combining a per-owner resource pool and a single node-wide `Global` resource pool: [1](#0-0) 

Every workflow engine, when starting, calls `e.cfg.GlobalWorkflowLimit.Use(ctx, 1)` before proceeding with initialization; if this succeeds it decrements the shared `Global` pool, and only the `PerOwner` scope constrains how much of that shared pool any single owner may claim: [2](#0-1) 

Test coverage confirms the exact mechanics: once the `Global` counter is exhausted by any combination of owners, subsequent activation attempts from *other, unrelated* owners fail with `ErrGlobalWorkflowCountLimitReached`, even though those owners are individually within their own `PerOwner` allowance: [3](#0-2) [4](#0-3) 

Workflow registration/activation is triggered by on-chain `WorkflowRegistry` events processed by the syncer `eventHandler`, and any registered workflow owner (an unprivileged product user, not a node operator/admin) can register and activate new workflow specs at will: [5](#0-4) 

This is structurally identical to the reported bug class: a shared, rate/quota-limited resource (`MAX_LOAN_PER_BLOCK` in the report vs. `Global` workflow slots here) is consumed by a low-privilege actor at negligible cost (gas + a small buy-in fee vs. simply registering/activating workflows), denying legitimate concurrent users access to the same shared resource.

### Impact Explanation
An attacker who controls (or Sybils) enough workflow-owner addresses under their `PerOwner` allowance can activate workflows until the node-wide `Global` counter is saturated. Because the check order is `[owner, global]`, the attack is bounded only by however high `PerOwner` is configured (including any per-owner override) relative to `Global`, and by how many distinct owner addresses the attacker controls — there is no cost barrier analogous to gas/ether beyond normal workflow registration, which the report identifies as the core enabling condition. The result is denial of service: legitimate owners' workflow activations fail non-retryably with `ErrGlobalWorkflowCountLimitReached` (classified as `ActivationNonRetryable` in `activation_errors.go`), so they cannot get their workflow engines started on that node until capacity frees up.

### Likelihood Explanation
Likelihood depends on the operator-configured `Global` and `PerOwner` values (`syncerlimiter.Config`, `cresettings.Default.WorkflowLimit` / `cresettings.Default.PerOwner.WorkflowLimit`), which I could not fully resolve from the indexed code (the `cresettings` package defaults were not found in the searchable index). If `PerOwner` is set generously (or a single attacker uses multiple owner addresses), exhausting `Global` is straightforward and requires no privileged access — only the ability to register/activate workflows, which is a standard unprivileged product capability. If `PerOwner` is tightly bounded relative to `Global` and Sybil owner creation is otherwise restricted, the practical severity is reduced, but the underlying shared-resource design flaw remains.

### Recommendation
1. Reserve headroom in the `Global` pool per distinct owner (e.g., cap the fraction of `Global` any single owner-cycle can consume within a time window), rather than relying solely on a static `PerOwner` ceiling that can still allow multiple/Sybil owners to collectively exhaust `Global`.
2. Consider a per-owner or per-request cost/friction (analogous to the report's "launch fee" recommendation) for workflow activation to raise the cost of mass activation.
3. Emit alerts/metrics distinctly when `Global` is saturated by a small number of owners so operators can detect and mitigate abuse (partial support exists via `IncrementWorkflowLimitGlobalCounter`, but it does not currently track "who" is consuming disproportionate share).

### Proof of Concept
Based on `TestWorkflowLimits` in `limiter_test.go`:
1. Configure `Config{Global: 3, PerOwner: 1}`.
2. Owners `user1`, `user2`, `user3` each activate one workflow, consuming the entire `Global` pool (`3/3`), each within their own `PerOwner` limit of `1`.
3. A legitimate `user4` (never having used the system before, well within their own `PerOwner` allowance) attempts to activate a workflow and is rejected with `settings.ScopeGlobal` — i.e., a fresh, well-behaved owner is denied service purely because unrelated owners collectively exhausted the shared `Global` capacity: [6](#0-5) 

This confirms that any set of owners collectively consuming up to `Global` slots (at the low cost of simply registering/activating workflows) blocks all other owners' legitimate workflow activations node-wide, directly analogous to the reported `takeLoan`/`MAX_LOAN_PER_BLOCK` exhaustion attack.

func NewWorkflowLimits(lggr logger.Logger, cfg Config, lf limits.Factory) (limits.ResourceLimiter[int], error) {
	lggr = logger.Named(lggr, "WorkflowExecutionLimiter")
	cfg.PerOwnerOverrides = normalizeOverrides(cfg.PerOwnerOverrides)

	ownerLimit := cresettings.Default.PerOwner.WorkflowLimit // make a copy
	if cfg.PerOwner > 0 {
		ownerLimit.DefaultValue = int(cfg.PerOwner)
	}
	perOwner := make(map[string]string, len(cfg.PerOwnerOverrides))
	for k, v := range cfg.PerOwnerOverrides {
		perOwner[k] = strconv.Itoa(int(v))
	}
	lf.Settings = keyedOwnerSettings{getter: lf.Settings, key: ownerLimit.Key, vals: perOwner}
	owner, err := limits.MakeResourcePoolLimiter(lf, ownerLimit)
	if err != nil {
		return nil, fmt.Errorf("failed to create owner resource limiter: %w", err)
	}

	globalLimit := cresettings.Default.WorkflowLimit // make a copy
	if cfg.Global > 0 {
		globalLimit.DefaultValue = int(cfg.Global)
	}
	global, err := limits.MakeResourcePoolLimiter(lf, globalLimit)
	if err != nil {
		return nil, fmt.Errorf("failed to create global resource limiter: %w", err)
	}

	lggr.Debugw("workflow limits set", "perOwner", cfg.PerOwner, "global", cfg.Global, "overrides", cfg.PerOwnerOverrides)

	return limits.MultiResourcePoolLimiter[int]{owner, global}, nil
}

func (e *Engine) init(ctx context.Context) {
	// Tracer is no-op if DebugMode is false
	ctx, span := e.tracer.Start(ctx, "workflow_engine_init",
		trace.WithAttributes(
			attribute.String("version", "v2"),
			attribute.String("component", "workflow_engine"),
		))
	defer span.End()

	// apply global engine instance limits
	// TODO(CAPPL-794): consider moving this outside of the engine, into the Syncer
	err := e.cfg.GlobalWorkflowLimit.Use(ctx, 1)
	if err != nil {
		if errLimited, ok := errors.AsType[limits.ErrorResourceLimited[int]](err); ok {
			switch errLimited.Scope {
			case settings.ScopeOwner:
				e.logger().Infow("Per owner workflow count limit reached", "err", err)
				e.metrics.IncrementWorkflowLimitPerOwnerCounter(ctx)
				e.cfg.Hooks.OnInitialized(types.ErrPerOwnerWorkflowCountLimitReached)
			case settings.ScopeGlobal:
				e.logger().Infow("Global workflow count limit reached", "err", err)
				e.metrics.IncrementWorkflowLimitGlobalCounter(ctx)
				e.cfg.Hooks.OnInitialized(types.ErrGlobalWorkflowCountLimitReached)
			default:
				e.logger().Errorw("Workflow count limit reached for unexpected scope", "scope", errLimited.Scope, "err", err)
				e.cfg.Hooks.OnInitialized(err)
			}
		} else {
			e.cfg.Hooks.OnInitialized(err)
		}
		return
	}
	e.workflowLimitUsed.Store(true)
