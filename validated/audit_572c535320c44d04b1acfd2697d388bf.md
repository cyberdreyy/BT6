## Finding

An unprivileged caller **can** trigger `staking_contract::distribute` in a way that pays a stale operator's queued commission directly to that operator's own address instead of to the `beneficiary_for_operator` they configured, because `distribute_internal`'s beneficiary-redirect check compares the pool's shareholder address to the *current* `operator` argument rather than to the shareholder's own identity.

### Title
Stale commission distribution entries bypass `beneficiary_for_operator` after `switch_operator` — ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`switch_operator` removes a `StakingContract` from the map keyed by `old_operator` and reinserts it keyed by `new_operator`, but the internal `distribution_pool` (a `pool_u64::Pool`) is carried over unchanged, still containing a shareholder entry keyed to `old_operator`'s address for any commission that was requested-but-not-yet-inactive at switch time [1](#0-0) . Once the stake becomes fully inactive, any unprivileged caller can invoke the unauthenticated `distribute(staker, new_operator)` entry function [2](#0-1) . Inside `distribute_internal`, the beneficiary redirect only fires when `recipient == operator` [3](#0-2) , where `operator` is the parameter passed in (`new_operator`). Since the stale shareholder key is `old_operator`, this comparison fails, so the funds bypass `beneficiary_for_operator(old_operator)` and are paid straight to the raw `old_operator` address.

### Finding Description
1. Staker creates a staking contract with `old_operator`. `old_operator` accrues rewards and calls `request_commission` (or `switch_operator` internally does this), which calls `add_distribution(operator=old_operator, ..., recipient=old_operator, amount)` [4](#0-3) . This adds a shares entry to `distribution_pool` keyed by the address `old_operator`, and calls `stake::unlock_with_cap`, which only becomes fully inactive after the lockup period.
2. `old_operator` calls `set_beneficiary_for_operator` to redirect all future commission payouts to a beneficiary address.
3. Staker calls `switch_operator(staker, old_operator, new_operator, ...)`. This removes the `StakingContract` record from the `old_operator` key and reinserts it under `new_operator`, carrying the same `distribution_pool` (still containing the pending `old_operator`-keyed share) [5](#0-4) . After this point `assert_staking_contract_exists(staker, old_operator)` fails [6](#0-5) , so `distribute` can no longer be called with `(staker, old_operator)`.
4. Once the lockup expires and the unlocked amount becomes `inactive`, any unprivileged third party calls `distribute(staker, new_operator)` (the function has no signer check, and its doc explicitly states it "does not need to be restricted to just the staker or operator") [7](#0-6) .
5. `distribute_internal` iterates `distribution_pool.shareholders()`, encountering the stale entry keyed `old_operator`. The redirect check `if (recipient == operator)` uses `operator = new_operator`, so it evaluates false, and the payout is sent directly to the `old_operator` address, not to `beneficiary_for_operator(old_operator)` [8](#0-7) .

This breaks the intended invariant documented in the module ("operator's recorded commission is only ever paid to the current beneficiary_for_operator") for any commission requested prior to an operator switch that had not yet fully unlocked.

### Impact Explanation
The value itself is not diverted to an external attacker's wallet — it still lands on the legitimate historical operator's own address — but the beneficiary redirection mechanism, which operators rely on for custody/accounting/security separation (e.g., cold wallet beneficiary, compliance routing, or a compromised/rotated operator key), is silently bypassed. Any unprivileged account can trigger this misrouting simply by calling the public `distribute` entry function once funds become inactive, with no special privileges required. This is a real violation of the beneficiary invariant described in the module's own documentation, reachable purely from unprivileged transaction input.

### Likelihood Explanation
High reachability: `distribute` is a permissionless `public entry fun`, and `switch_operator` is a normal staker operation. Any staking contract that undergoes an operator switch while commission is still unlocking (a routine, non-adversarial scenario — the switch itself calls `request_commission_internal` right before flipping operators) will produce this stale distribution-pool entry. No attacker privilege beyond calling public functions is needed to trigger the mispayment.

### Recommendation
In `distribute_internal`, when redirecting commission to a beneficiary, compare `recipient` against `beneficiary_for_operator(recipient)`'s owning identity rather than against the passed-in `operator` parameter — i.e., track/record the operator identity per distribution-pool entry (not implicitly via the current `operator` argument), or redirect any recipient address that has ever been an operator of this staking contract (not just the currently active one) to its own `beneficiary_for_operator`. Alternatively, force a full `distribute_internal` flush for `old_operator` synchronously inside `switch_operator` after `request_commission_internal`, ensuring no stale shares tied to `old_operator` persist in the pool across an operator switch (this requires waiting for/forcing the unlock cycle, or explicitly tracking historical operator-to-beneficiary mappings for outstanding shares).

### Proof of Concept
```
1. staker creates staking_contract(staker, old_operator, commission=10%) with sufficient stake.
2. old_operator earns rewards; call request_commission(old_operator, staker, old_operator)
   -> adds distribution_pool entry keyed `old_operator` for the commission, calls stake::unlock_with_cap (pending_inactive).
3. old_operator calls set_beneficiary_for_operator(old_operator_signer, beneficiary_addr).
4. staker calls switch_operator(staker, old_operator, new_operator, new_commission).
   -> StakingContract (with distribution_pool still containing `old_operator` share) is moved to key `new_operator`.
5. Advance epochs until lockup expires (pending_inactive -> inactive).
6. Any unprivileged account calls distribute(staker_addr, new_operator).
   -> distribute_internal(operator = new_operator) iterates distribution_pool,
      finds shareholder `old_operator`, checks `recipient == operator` (old_operator == new_operator) -> false,
      pays commission directly to old_operator's address instead of `beneficiary_addr`.
7. Assert: recipient of the payout == old_operator (WRONG), instead of beneficiary_for_operator(old_operator) == beneficiary_addr (EXPECTED).
```

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }
