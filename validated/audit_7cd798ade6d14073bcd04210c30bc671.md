### Title
Stale per-epoch instant-withdraw basis is never cleared on a normal claim, enabling a double payout from the default recovery reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records a per-epoch receipt basis in `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (IdleCreditVault.sol:371-372), but the normal funded claim path `claimInstantWithdrawRequest` only zeroes the aggregate `instantWithdrawsRequests[user]` (line 391) and never clears the per-epoch entries. If the borrower defaults in the same epoch in which the user already claimed, `defaultRecoveryEpoch` equals that epoch, and `_claimDefaultedInstantWithdrawRequest` later pays the stale basis again out of `defaultRecoveryReserve` at `defaultRecoveryPrice`. This is the direct analog of CVE-2015-3280: a resource that should have been deleted in one state transition (funded claim) survives into a later state transition (default finalization) and is consumed twice.

### Finding Description
Relevant code:

- `requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 371-372).
- `claimInstantWithdrawRequest` burns the user receipts and sets `instantWithdrawsRequests[_user] = 0`, but does not touch `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch` (lines 387-392). The per-epoch entries are only cleared inside `_claimDefaultedInstantWithdrawRequest` (line 847).
- After `finalizeDefaultRecovery`, claims route through `_claimDefaultedInstantWithdrawRequest` (lines 382-386), which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve` (lines 844-855).

Attack sequence (all in epoch N, "running" phase, instant mode):

1. Attacker deposits, calls `requestInstantWithdraw(W)` via the CDO. Receipt strategy tokens are minted to the attacker; `instantWithdrawsRequestsByEpoch[attacker][N] = W`.
2. The CDO funds instant liquidity (`collectInstantWithdrawFunds`) and the attacker calls `claimInstantWithdrawRequest`. They are paid `W` underlying at par, receipts burned, `instantWithdrawsRequests[attacker] = 0` — but `instantWithdrawsRequestsByEpoch[attacker][N]` still equals `W`.
3. Borrower defaults during epoch N; `finalizeDefault` / `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = N` and `defaultInstantWithdrawsFinalized = true`.
4. Attacker opens a new instant request `W2 >= W` post-default (`requestInstantWithdraw` has no `defaultRecoveryFinalized` gate — it only runs `_ensureDefaultRecoveryInitialized`, which only reverts on legacy `pendingInstantWithdraws`), minting fresh receipts.
5. Attacker calls `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` finds the stale basis `W`, decrements `instantWithdrawsRequests` to `W2 - W`, burns `W` of the attacker's `W2` receipts, and transfers `W * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve` — funds reserved for claimants whose receipts were genuinely unfunded at default. The remaining `W2 - W` is then paid at par in the same call.

### Impact Explanation
Direct theft of the default recovery reserve: the attacker is paid twice for the same instant-withdraw basis — once at par before default, once at `defaultRecoveryPrice` from the isolated reserve after finalization. Because `_transferDefaultRecovery` decrements `defaultRecoveryReserve` (line 915), other defaulted-epoch claimants' recovery is correspondingly reduced or made unclaimable. Loss is bounded by the attacker's pre-default instant-withdraw size but scales linearly with it.

### Likelihood Explanation
Requires an instant-withdraw-enabled vault, the attacker to front-run or coincidentally hold a claimed instant request in the epoch where the borrower defaults, and post-default instant requests to remain reachable through the CDO. The accounting flaw itself is unconditional — the per-epoch entries are simply never cleared outside the default path — so any epoch ending in default re-exposes every already-claimed instant basis from that epoch. Uncertainty: I could not fully confirm the CDO-side path still forwards `requestInstantWithdraw` after `defaultRecoveryFinalized`; if it reverts, the residual impact is a permanent revert (DoS) on the attacker's subsequent claims rather than reserve theft.

### Recommendation
In `claimInstantWithdrawRequest`'s funded path (and `collectInstantWithdrawFunds` if intended), clear the per-epoch entries: delete `instantWithdrawsRequestsByEpoch[_user][lastRequestEpoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` when a claim is paid at par. Equivalently, record the request epoch alongside `instantWithdrawsRequests` so the funded path can zero the exact per-epoch basis that was consumed.

### Proof of Concept
Foundry fork PoC outline (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantWithdrawStaleEpochDoubleClaim() external {
    // epoch N running, instant mode enabled
    _depositWithUser(attacker, W);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(W, address(AAtranche));
    // CDO funds instant liquidity
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();          // paid W at par
    assertEq(vault.instantWithdrawsRequests(attacker), 0);
    assertEq(vault.instantWithdrawsRequestsByEpoch(attacker, N), W); // stale

    // borrower defaults mid-epoch N
    _defaultBorrower();
    cdoEpoch.finalizeDefaultRecovery();              // defaultRecoveryEpoch == N

    // attacker re-enters post-default
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(W2, address(AAtranche)); // W2 >= W

    uint256 reservePre = vault.defaultRecoveryReserve();
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // reserve paid out again for the already-claimed W
    assertEq(reservePre - vault.defaultRecoveryReserve(), W * vault.defaultRecoveryPrice() / 1e18);
}
```
