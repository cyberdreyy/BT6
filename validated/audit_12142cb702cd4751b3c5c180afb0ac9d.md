### Title
Gateway HTTP Action Response Cache Omits WorkflowID from Cache Key, Enabling Cross-Workflow Response Confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's outbound HTTP response cache is documented as being workflow-isolated ("Cache entries are scoped by workflow ID to prevent cross-workflow data leakage") [1](#0-0) , but the actual cache key — `req.Hash()` — is proven by the repo's own test suite to deliberately exclude `WorkflowID` while including only `WorkflowOwner`, method, URL, headers, and body [2](#0-1) . This is the same class of bug as the external report: a value that should scope/limit an economic or authorization outcome to a specific requester (fee rate vs. cache scope) is instead shared/mutable across unrelated parties, letting one workflow's cached HTTP action response leak into a different workflow's execution when both share the same owner address.

### Finding Description
The `responseCache` type stores HTTP action responses in a map keyed by a hash "of the request (method, URL, headers, body, workflowOwner)" [3](#0-2) . `Fetch` and `Set` both use `req.Hash()` as the sole cache key without ever incorporating `WorkflowID` [4](#0-3) [5](#0-4) .

The repo's own regression test explicitly asserts this behavior:
- `"having different workflowID results in same Hash"` — two requests with different `WorkflowID` values produce the *same* hash [6](#0-5) .
- `"having different workflowOwner results in different Hash"` — hash is only differentiated by `WorkflowOwner` [7](#0-6) .

This directly contradicts the documented invariant in the module's own README that cache entries are "scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) . The cache is invoked from `makeOutgoingRequest`, which is reachable for every outbound HTTP action request forwarded by any workflow node, keyed only on the parsed `OutboundHTTPRequest` fields [8](#0-7) .

Consequences of this scoping gap:
- Two distinct workflows registered under the same `WorkflowOwner` address (a routine, unprivileged scenario — one owner can register many workflows) that happen to issue an HTTP action with the same method/URL/headers/body will read and write the *same* cache entry, even though they are logically separate executions with separate `WorkflowID`s.
- A workflow whose `CacheSettings.Store` is `true` can populate an entry that a *different* workflow (same owner, different WorkflowID) later reads via `CacheSettings.MaxAgeMs`-gated `Fetch`, receiving output that was never fetched or authorized for its own execution context. This is a direct "cross-user response confusion" scenario in the gateway's caches, mirroring the report's core theme: a boundary value that should isolate one party's outcome from another's is not actually enforced.

### Impact Explanation
Impact is High relative to correctness/isolation guarantees of the workflow HTTP capability: a workflow can receive stale or foreign response data associated with a sibling workflow under the same owner, undermining the documented workflow-isolation guarantee and potentially causing incorrect on-chain/automation decisions to be made from a response that was never actually fetched for that workflow's own request context (data integrity/cross-user confusion), analogous to how the external report's victim (Alice) receives an outcome computed under different, unauthorized parameters than she agreed to.

### Likelihood Explanation
Likelihood is Medium: it requires two workflows sharing the same `WorkflowOwner` address (a normal condition, since owners commonly run multiple workflows) and issuing outbound HTTP actions with `Store: true`/`MaxAgeMs > 0` and identical method/URL/headers/body — a realistic and easily reproducible configuration rather than a contrived edge case, and it does not require any privileged/operator action, only ordinary unprivileged workflow authorship.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the cache key computed by `Hash()`/used by `responseCache`, so that `Fetch`/`Set` isolate entries per workflow as the README already claims, e.g. incorporate `req.WorkflowID` alongside method/URL/headers/body/owner in the hash input, and add a regression test asserting different `WorkflowID`s under the same owner produce different cache keys (inverting the current `"having different workflowID results in same Hash"` assertion).

### Proof of Concept
1. Workflow A and Workflow B are both registered under the same `WorkflowOwner` address but have distinct `WorkflowID`s.
2. Workflow A issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", WorkflowOwner: "0xOwner", WorkflowID: "wfA", CacheSettings: {Store: true}}`. The gateway calls `h.responseCache.Set(req, outboundResp)` after fetching, storing the response keyed by `req.Hash()` [9](#0-8) .
3. Workflow B later issues the identical `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", WorkflowOwner: "0xOwner", WorkflowID: "wfB", CacheSettings: {MaxAgeMs: 600000}}`. Because `Hash()` does not include `WorkflowID` (confirmed by `TestRequestHash`'s `"having different workflowID results in same Hash"` sub-test) [6](#0-5) , `Fetch` returns Workflow A's cached response to Workflow B without ever calling `fetchFn` [4](#0-3) , demonstrating cross-workflow response confusion despite the documented per-workflow isolation guarantee.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
