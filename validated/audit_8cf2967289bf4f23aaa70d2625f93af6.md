I need to check whether the CDO still allows instant withdraw requests after default finalization.### Title
Post-default instant withdraws land in the frozen default epoch and drain the isolated recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The use-after-free pattern (a stale object/epoch reused after its logical lifetime ended) maps onto `IdleCreditVault`'s instant-withdraw accounting. After `finalizeDefaultRecovery`, `epochNumber` is frozen forever at `defaultRecoveryEpoch`. `requestInstantWithdraw` has no `defaultRecoveryFinalized` branch (unlike `requestWithdraw`, which routes post-default requests into `postDefaultRequests`), so any post-default instant request is recorded into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — the exact slot that `claimInstantWithdrawRequest` treats as a defaulted-epoch receipt and pays out of `defaultRecoveryReserve` at `defaultRecoveryPrice`. Those requests were never part of the recovery `totalBasis`, so each one consumes reserve that belongs to genuine defaulted claimants. [1](#0-0) [2](#0-1) 

### Finding Description
- `requestInstantWithdraw` unconditionally writes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, and bumps `pendingInstantWithdraws`, with no check for `defaultRecoveryFinalized`. [1](#0-0) 
- `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`. No epoch can ever advance past this point (defaulted vaults do not `startEpoch` again), so `epochNumber == defaultRecoveryEpoch` permanently. [3](#0-2) 
- `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`, decrements `pendingInstantWithdraws`, burns the receipt, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve`. [4](#0-3) [5](#0-4) 
- A post-default instant request therefore lands in the same per-epoch slot that the recovery payout reads. It is paid out of the isolated reserve even though it was created *after* `totalBasis` was computed at finalization — the reserve accounting (`reserveAmount = recovered + prefunded + reserveDefaultRecovery` vs. `totalBasis`) never included it. [6](#0-5) 
- Additionally, a post-default instant request burns the CDO's strategy tokens at the already-haircut post-default price and then applies `defaultRecoveryPrice` *again*, so the payout is funded entirely by other claimants' reserve share.

### Impact Explanation
Every defaulted or unfunded-instant receipt is entitled to `claimBasis * defaultRecoveryPrice` out of a fixed `defaultRecoveryReserve`. An attacker who makes an instant-withdraw request after finalization and calls `claimInstantWithdrawRequest` pulls `amount * defaultRecoveryPrice` from that reserve without the amount ever being counted in `totalBasis`. Repeated or large requests deplete the reserve so that legitimate defaulted-epoch claimants (normal withdraw receipts and unfunded instant receipts) later revert on `defaultRecoveryReserve -= _amount` or receive less than their entitlement — direct theft / permanent freezing of unclaimed recovery funds, bounded by the reserve size and the attacker's post-default tranche balance.

### Likelihood Explanation
Reachability requires the CDO (`IdleCDOEpochVariant` / prefunded variant) to still route `requestInstantWithdraw` to the strategy after default; the strategy itself performs no gating and the only caller check is `_onlyIdleCDO`. Post-default instant liquidity is nominally "funded" because the reserve sits in the strategy, so an instant-withdraw path keyed on available strategy balance is plausibly still open. If the CDO blocks instant requests once `defaulted()` is true, the bug is unreachable; I could not fully verify the CDO-side gating in this pass, so likelihood is moderate — it hinges on that single upstream check that the strategy does not enforce itself.

### Recommendation
Mirror the `requestWithdraw` post-default branch in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert, or route the request to a reserve-backed, already-haircut bucket (like `postDefaultRequests`) rather than `instantWithdrawsRequestsByEpoch[epochNumber]`. Alternatively, key defaulted instant claims to a snapshot marker recorded at finalization (e.g. require `instantWithdrawsRequestsByEpoch` epoch `< defaultRecoveryEpoch`-adjacent request time, or record a per-user `requestTimestamp <= finalizedAt` flag) so post-default requests can never collide with the frozen default epoch.

### Proof of Concept
Foundry fork scenario (standard `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
// Setup: pool running, attacker + victim hold AA tranches.
// 1. Epoch runs, borrower defaults; manager calls handleBorrowerDefault.
// 2. Some instant-withdraw receipts remain unfunded => pendingInstantWithdraws > 0.
// 3. Finalize: cdo.finalizeDefaultRecovery(recovered, source)
//    - epochNumber frozen at defaultRecoveryEpoch = E
//    - defaultRecoveryReserve = R, defaultRecoveryPrice = p < 1e18
// 4. Attacker (still holding tranches) calls cdoEpoch.requestInstantWithdraw(x):
//    - strategy burns CDO tokens, mints x receipt tokens to attacker
//    - instantWithdrawsRequestsByEpoch[attacker][E] += x   // same slot E!
//    - instantWithdrawClaimsByEpoch[E] += x
//    - pendingInstantWithdraws += x
// 5. Attacker calls cdoEpoch.claimInstantWithdrawRequest():
//    - _claimDefaultedInstantWithdrawRequest pays x * p / 1e18
//      from defaultRecoveryReserve (R -= payout)
//    - x was never in totalBasis => reserve now undercollateralized
// 6. Victim's legitimate defaulted claim of basis B now needs B * p,
//    but reserve has been drained by x * p => victim claim reverts
//    (underflow) or is permanently short.

assertLt(strategy.defaultRecoveryReserve(), R - attackerPayout);
vm.expectRevert(); // underflow on defaultRecoveryReserve
cdoEpoch.claimInstantWithdrawRequest(); // victim's tx, via victim prank
```

The broken invariant is donation/reserve isolation: `defaultRecoveryReserve` is consumed by receipts that were never part of the finalized claim basis.

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
