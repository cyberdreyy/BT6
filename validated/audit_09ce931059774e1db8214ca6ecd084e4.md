Based on my investigation, I found a genuine, concrete analog: `GlobalStateView::check_proposal` (v2 chainstate) is missing the `check_parent_tenure_choice` reorg-legitimacy check that its `SortitionsView::check_proposal` (v1) counterpart enforces.

### Title
Global-state (v2) signers skip the reorg-legitimacy check on tenure-change blocks, allowing a miner to force a signature over an illegitimate tenure reorg - ([File: stacks-signer/src/chainstate/v2.rs])

### Summary
In v1, `SortitionsView::validate_tenure_change_payload` explicitly calls `SortitionData::check_parent_tenure_choice` and rejects the proposal with `RejectReason::ReorgNotAllowed` if the parent tenure choice is not legitimate (e.g., reorging a tenure that already produced multiple globally-accepted blocks, outside the `first_proposal_burn_block_timing` grace window). [1](#0-0) 

The v2 equivalent, `GlobalStateView::validate_tenure_change_payload`, does not perform this check at all — it only checks that `prev_tenure_consensus_hash` matches the tracked `parent_tenure_id`, that `check_tenure_change_confirms_parent` passes, and that there is no already-signed block in the current tenure. [2](#0-1) 

### Finding Description
`check_parent_tenure_choice` is the rule that decides whether a miner's chosen parent tenure represents a legitimate continuation vs. an illegitimate reorg of an already-productive tenure (more than one globally accepted block, or a block signed too long before the sortition transition). [3](#0-2) 
This is exactly the check that v1's `check_proposal` runs both for the tenure-neutral case (via the outer `check_proposal` guard on `cur_sortition`) and specifically inside `validate_tenure_change_payload` for a tenure-change block. [4](#0-3) [1](#0-0) 

`GlobalStateView::check_proposal`, used by signers on the v2/global-state protocol, derives its trust for the miner from the `MinerState::ActiveMiner` state instead of re-deriving `SortitionsView`-style validity per proposal. [5](#0-4) 
However, its `validate_tenure_change_payload` — the function that specifically decides whether a tenure-change block confirming a parent tenure is acceptable — never calls `check_parent_tenure_choice` before accepting. [6](#0-5) 
I searched for other call sites of `check_parent_tenure_choice`/`is_tenure_valid` and found matches in `stacks-signer/src/v0/signer_state.rs` and `stacks-signer/src/chainstate/tests/v2.rs`, which strongly suggests `is_tenure_valid` (which does wrap `check_parent_tenure_choice`) may be invoked as part of miner-state transition logic elsewhere in `signer_state.rs`, rather than at proposal-check time. I was not able to fully trace, within the remaining iteration budget, whether that earlier call happens on every relevant transition path (including tenure changes) or only on a subset (e.g., only for setting `ActiveMiner` from a *new* sortition, but not re-validated against an evolving DB state — such as tenures that gain a second globally-accepted block *after* the miner state was already marked active). This is the key uncertainty in this finding: if `is_tenure_valid` is called once when the miner becomes "active" and never re-checked when new `check_proposal` calls happen for later blocks in that same tenure, then a miner who wins a sortition on an initially-plausible parent, and only *afterwards* the disqualifying condition materializes (e.g., a second globally-accepted block on the tenure being reorged arrives, or the timing window expires), can still get tenure-change blocks signed without this specific rejection path ever firing on the v2 code path.

### Impact Explanation
If confirmed that no other call site re-validates `check_parent_tenure_choice` per tenure-change proposal on the v2/global-state path, this breaks the "approved-parent vs canonical" equality: a v2 signer could sign a tenure-change block reorging a tenure that the equivalent v1 logic would reject with `ReorgNotAllowed`, producing a non-canonical/illegitimate reorg signature. That maps to the Critical impact category (a signer signing an invalid/non-canonical block) requested by the rules, and requires only a single miner slot plus normal gossip of the proposal — no majority or other signer's key needed.

### Likelihood Explanation
Likelihood cannot be confirmed as "high confidence" from the code paths I was able to read in the time available. The gap is real (v1 has the check inline in `validate_tenure_change_payload`; v2 does not), but I could not fully verify within budget whether `stacks-signer/src/v0/signer_state.rs`'s handling of `MinerState` transitions calls `is_tenure_valid`/`check_parent_tenure_choice` on a schedule that fully substitutes for the missing per-proposal check in v2's `validate_tenure_change_payload`. This needs to be verified by reading `stacks-signer/src/v0/signer_state.rs` (the `is_tenure_valid`/`check_parent_tenure_choice` call sites) and `stacks-signer/src/chainstate/tests/v2.rs` in full, which I flagged but did not have remaining iterations to read.

### Recommendation
Read `stacks-signer/src/v0/signer_state.rs` around its `check_parent_tenure_choice`/`is_tenure_valid` call sites and `stacks-signer/src/chainstate/tests/v2.rs` to establish exactly when/how often the reorg-legitimacy check is (re-)applied for the v2/global-state code path. If it is only applied once at miner-activation time and not re-checked per tenure-change block proposal (matching v1's inline check inside `validate_tenure_change_payload`), add an equivalent `check_parent_tenure_choice` call inside `GlobalStateView::validate_tenure_change_payload`, returning `RejectReason::ReorgNotAllowed` on failure, mirroring `stacks-signer/src/chainstate/v1.rs:497-504`.

### Proof of Concept
Conceptual, pending confirmation of the call-site gap above:
1. A miner wins a sortition whose parent tenure choice is initially valid (or plausible at the time signer_state marks it `ActiveMiner`).
2. Before the signer's local DB view catches up, the reorged tenure gains a second globally-accepted block (or the `first_proposal_burn_block_timing` window elapses), a condition that `check_parent_tenure_choice` would use to return `Ok(false)`.
3. The miner proposes a tenure-change block for this consensus hash. `GlobalStateView::check_proposal` → `validate_tenure_change_payload` runs only `check_tenure_change_confirms_parent` and the duplicate-block check — never `check_parent_tenure_choice` — so the proposal is not rejected on this basis.
4. A v2/global-state signer proceeds to pre-commit/sign a tenure-change block that a v1 signer, given the same underlying chain state, would have rejected as `ReorgNotAllowed`. [6](#0-5) [7](#0-6)

    fn validate_tenure_change_payload(
        &self,
        proposed_by: &ProposedBy,
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            self.config.tenure_last_block_proposal_timeout,
            self.config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // now, we have to check if the parent tenure was a valid choice.
        let is_valid_parent_tenure = proposed_by.state().data.check_parent_tenure_choice(
            signer_db,
            client,
            &self.config.first_proposal_burn_block_timing,
        )?;
        if !is_valid_parent_tenure {
            return Err(RejectReason::ReorgNotAllowed);
        }
        let last_in_current_tenure = signer_db
            .get_last_globally_accepted_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }

    /// if the tenure change confirms the expected parent block (i.e.,
    /// the last globally accepted block in the parent tenure)
    fn validate_tenure_change_payload(
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        parent_tenure_id: &ConsensusHash,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        config: &ProposalEvalConfig,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the signer's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            config.tenure_last_block_proposal_timeout,
            config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }

        // reorging the tenure blocks. Only blocks we have signed (locally or globally accepted) count

            .get_last_signed_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {

                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())

    pub fn check_parent_tenure_choice(
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,
            "sortition_state.prior_sortition" => %self.prior_sortition,
            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

        let tenures_reorged =
            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
        if tenures_reorged.is_empty() {
            warn!("Miner is not building off of most recent tenure, but stacks node was unable to return information about the relevant sortitions. Marking miner invalid.");
            return Ok(false);
        }

        // this value *should* always be some, but try to do the best we can if it isn't
        let sortition_state_received_time =
            signer_db.get_burn_block_receive_time(&self.burn_block_hash)?;

        // Track which tenures are superseded by the reorg, then mark them in
        // the DB after the reorg is permitted.
        let mut superseded_tenures = Vec::new();
        for tenure in tenures_reorged.iter() {
            if tenure.consensus_hash == self.parent_tenure_id {
                // this was a built-upon tenure, no need to check this tenure as part of the reorg.
                continue;
