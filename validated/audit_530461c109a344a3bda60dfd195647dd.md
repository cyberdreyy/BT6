### Title
Missing local approval timestamp defaults to zero elapsed time in `check_parent_tenure_choice`, letting a signer permit a late/unsafe tenure reorg - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_parent_tenure_choice` protects the signer against dangerous reorgs of an already-established tenure by requiring the reorged tenure's first block to have been proposed within `first_proposal_burn_block_timing` of the next sortition. When the signer has no local `approved_time` for that block (i.e. it never locally accepted it), the code substitutes `0` for the elapsed time instead of treating the case conservatively, causing the reorg-safety check to always pass regardless of how much wall-clock time actually elapsed.

### Finding Description
`check_parent_tenure_choice` computes, for each tenure being reorged, how long elapsed between the tenure's first-block proposal and the next sortition (`proposal_to_sortition`), and permits the reorg only if that duration is under `first_proposal_burn_block_timing`: [1](#0-0) 

Specifically:
```rust
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else {
    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
    0
};
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    // permit reorg, mark tenure as superseded
    superseded_tenures.push(tenure);
    continue;
}
```
When `local_block_info.approved_time` is `None`, `proposal_to_sortition` is hard-coded to `0`, which is always `< first_proposal_burn_block_timing` (any positive configured timing). The comment rationalizes this as "we haven't seen the proposal yet, so treat it as late-arriving," but that inference is not sound: `approved_time` can be absent for reasons unrelated to how recently the block was proposed — e.g. the signer simply never received/processed the tenure's first-block proposal over StackerDB gossip (ordinary network delay, being offline momentarily, or the block only being pre-committed rather than locally accepted; per `docs/signer-flows.md` and `BlockInfo::check_state`, `approved_time` is stamped at pre-commit **or** local acceptance, first one wins — but a block that was never proposed to/received by this signer at all has neither).

The `first_proposal_burn_block_timing` protection exists precisely to stop a miner from reorging a tenure that has been running (and building blocks) for a long time — the config documentation states the intended equality explicitly: [2](#0-1) 

By substituting `0` whenever local knowledge is missing, the code inverts this intended equality for exactly the signers who lack that knowledge: instead of failing safe (denying the reorg, or at minimum not asserting it was "recent"), it fails permissive, unconditionally treating the tenure as freshly proposed and voting to permit its replacement — and additionally records it as `superseded` via `mark_tenure_superseded`, which then stops any conflict check on this signer's own later signatures over that reorged tenure's blocks.

### Impact Explanation
This breaks the "approved-parent vs canonical" safety equality that `check_parent_tenure_choice`/`first_proposal_burn_block_timing` is meant to enforce for each signer independently. A signer whose local `approved_time` is missing for the reorged tenure's block will sign off on (and treat as canonical) a tenure-change/block proposal that reorgs an already-established tenure — a case the protocol explicitly designed to reject — because it (wrongly) believes the elapsed time is zero. This is a "signer signing an invalid/non-canonical/conflicting block" per the Critical impact criteria: the signer ends up approving (and marking `superseded`) a reorg of a tenure it should have refused, based purely on a local information gap rather than the actual timing the check is supposed to measure. Because the substitution of `0` is deterministic and not attacker-controlled data, this is reachable by ordinary gossip timing variance across signers (no majority collusion required to trigger the flawed local decision — only to observe divergent behavior between the signer with full local history and the one missing it).

### Likelihood Explanation
Likelihood is high for the *triggering condition* (a signer lacking `approved_time` for a given tenure's first block is a routine occurrence — StackerDB propagation delay, a signer coming online mid-tenure, or a block that was only pre-committed and never locally accepted all produce `None` here), and the effect (always-permit) is deterministic and not probabilistic like the original Dopex timing window. It requires no privileged access, no majority of signers, and no other signer's key — only the ordinary condition that this signer's local DB lacks the approval record for the tenure being reorged, which a miner can also encourage by simply not ensuring its early proposal reaches every signer before the next sortition.

### Recommendation
Do not default missing `approved_time` to `0` (i.e., "arrived just now"). Absence of local approval data means the timing is *unknown*, not *recent*; the check should fail safe:
- Treat missing local knowledge as failing the "recent enough" test (i.e., default to a value that is *not* less than `first_proposal_burn_block_timing`, or explicitly return `false`/deny the reorg when local approval data cannot establish timing), OR
- Fall back to a node-verifiable timestamp (e.g., corroborate via the `stacks-node`'s tenure-forking info / burn-block timestamps) rather than purely local signer state, consistent with how other timing checks in this module (e.g. `is_timed_out`) use a persisted, node-independent reference.

### Proof of Concept
Conceptual trace through `check_parent_tenure_choice` ( [3](#0-2) ):
1. Tenure A produces its first block at time T0; it is proposed and gossiped over StackerDB, but signer S (for whatever reason — brief network partition, being slow to process the message queue, or the block only reaching pre-commit before a competing tenure change happens) never records `approved_time` for that block in its `SignerDb` (`local_block_info.approved_time == None`).
2. Substantially later, at time T1 (T1 - T0 ≫ `first_proposal_burn_block_timing`, e.g. hours), a new sortition occurs and a miner proposes a tenure-change block that reorgs tenure A instead of building on it.
3. `check_parent_tenure_choice` is invoked (from `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs:496-501` or the v2 equivalent) as part of validating this new proposal.
4. Because `local_block_info.approved_time` is `None` for tenure A's first block on signer S, `proposal_to_sortition` is set to `0` — even though the real elapsed time (T1 - T0) vastly exceeds the configured `first_proposal_burn_block_timing`.
5. `Duration::from_secs(0) < first_proposal_burn_block_timing` is true, so the reorg is (incorrectly) permitted: tenure A is pushed into `superseded_tenures` and marked superseded via `signer_db.mark_tenure_superseded`.
6. Signer S then proceeds to accept/sign the new tenure-change block that reorgs a long-established tenure — the exact scenario `first_proposal_burn_block_timing` was designed to prevent — while other signers that *did* record `approved_time` correctly reject it (per `check_parent_tenure_choice_reorg_timing_bad`/`_ok` tests in `stacks-signer/src/chainstate/tests/v2.rs:362-380`, which only exercise the `Some(approved_time)` branch and never test the `None` fallback's safety implications). # Reorg protection window. Measures the time between when the first block
```text
# of a tenure was signed and when the next burn block (sortition) arrived.
#
# If a new miner tries to reorg a tenure that already produced blocks:
#   - If (burn_block_received - first_block_signed) < this value:
#     Reorg is ALLOWED (the tenure was "poorly timed" and the incoming
#     miner did not have sufficient time to RBF an outdated commit)
#   - If (burn_block_received - first_block_signed) >= this value:
#     Reorg is DENIED (the tenure was established long enough for the
#     incoming miner to RBF any outdated commit)
#
# WARNING: Setting this too LOW allows dangerous reorgs of established
# tenures. Setting it too HIGH blocks legitimate miner handoffs when
# the previous tenure's first block arrived shortly before the sortition.
#
# Default: 60
# Units: seconds
# first_proposal_burn_block_timing_secs = 60
```
