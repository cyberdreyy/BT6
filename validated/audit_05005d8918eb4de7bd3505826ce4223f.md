### Title
Instant-withdraw receipts can be claimed against other users' funded claim reserve because `claimInstantWithdrawRequest` never verifies that the epoch's instant funds were actually collected - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to a sensitive cookie missing its `Secure` flag: an instant-withdraw receipt is minted with **no attribute recording that its backing funds were collected**. `claimInstantWithdrawRequest` burns the receipt and pays out of the vault's commingled underlying balance, so a receipt whose funding never arrived can be settled with underlying that was collected and earmarked for other claimants (funded normal withdraws or post-default recovery).

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens, mints an equal receipt to the user, and increases `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375).

Funding happens separately and asynchronously: the CDO calls `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying into the vault (contracts/strategies/idle/IdleCreditVault.sol:398-403).

The claim path is the problem:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:380-393
function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    _burn(_user, amount);
    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
}
```

There is no check that `pendingInstantWithdraws` for the user's epoch was actually funded — i.e., that `collectInstantWithdrawFunds` moved matching underlying into the vault. The only implicit guard is the vault's `underlyingToken` balance, which is a **shared pool** also holding:

- underlying pulled in by `collectWithdrawFunds` for matured normal withdraw requests (lines 411-430), claimable at any later time by other users via `claimWithdrawRequest`, and
- the post-default recovery reserve backing `postDefaultRequests` and `_transferDefaultRecovery` payouts (lines 247-257, 855).

The receipt therefore lacks the "secure" attribute that would bind it to its own funding event. A claimant can redeem an unfunded instant receipt and the transfer succeeds as long as *someone else's* funded underlying sits in the vault.

The analogous normal-withdraw flow does not have this gap: `claimWithdrawRequest` enforces an epoch-wait via `epochNumber <= lastWithdrawRequest[_user]` and default/loss-adjustment flags before paying (lines 301-328), and loss-adjusted receipts are explicitly marked through `lossRecoveryPriceByEpoch`/`isEpochWithdrawZero` before they can be settled (lines 421, 360-362). Instant receipts get no equivalent funding marker — the "attribute" is simply missing.

### Impact Explanation
Direct theft of earmarked funds. If the instant-epoch funding step is skipped or underfunds relative to `pendingInstantWithdraws` (e.g., an epoch starts with insufficient fresh liquidity to source all instant requests — `getInstantWithdrawFunds` is conditional on available deposits), the first instant claimant(s) are paid in full out of underlying collected for matured normal withdraw receipts or for the default-recovery reserve. Those other users' later `claimWithdrawRequest`/`_transferFundedClaim`/`_transferDefaultRecovery` calls then fail on insufficient balance — permanent loss for them, quantified as the amount of the unfunded instant claims paid out, bounded by `pendingInstantWithdraws`.

### Likelihood Explanation
Requires instant withdrawals enabled (`allowInstantWithdraw`) and an epoch where instant funding is not fully sourced before a claim is executed — reachable whenever the CDO's collected amount is less than `pendingInstantWithdraws`, since `claimInstantWithdrawRequest` has no per-epoch funding gate and claims are permissionless once `cdoEpoch.claimInstantWithdrawRequest()` is callable during a running epoch (contracts/IdleCDOEpochVariant.sol:975-979). The attacker only needs to be a KYC-passed lender holding tranche tokens, i.e., unprivileged. Note: the invariant break depends on the funding path permitting claims before full collection; if the CDO atomically collects all instant funds before any claim can execute, this degrades to a liveness issue — this dependency could not be fully confirmed from the CDO-side `getInstantWithdrawFunds` flow within this review.

### Recommendation
Bind each instant receipt to its funding event, mirroring how normal receipts are bound to `pendingWithdraws`/`lossRecoveryPriceByEpoch`:

- Track funded vs. unfunded instant requests (e.g., a `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds` and decremented per claim), and revert in `claimInstantWithdrawRequest` when the user's basis exceeds the funded remainder — or store a per-epoch `instantFundedByEpoch[epoch]` flag and gate claims on it.
- Alternatively, segregate the instant-claim reserve from the normal-claim/recovery reserve so an unfunded instant receipt cannot draw on earmarked underlying.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol` patterns):

```solidity
// 1. Users A (normal) and B (instant) deposit into AA tranches; epoch 0 runs and stops.
// 2. Epoch 1 (buffer): A calls cdoEpoch.requestWithdraw(...) -> normal receipt;
//    borrower funds pendingWithdraws via stopEpoch -> collectWithdrawFunds pulls
//    underlying into the vault (vault balance now holds A's earmarked claim).
// 3. Epoch 2 starts with instant withdraws enabled but the CDO sources only part
//    (or none) of pendingInstantWithdraws from new deposits:
//    - B calls cdoEpoch.requestWithdraw(0, BBtranche) -> instant receipt minted,
//      instantWithdrawsRequests[B] = X, pendingInstantWithdraws = X.
//    - getInstantWithdrawFunds collects < X (or 0); collectInstantWithdrawFunds
//      reduces pendingInstantWithdraws but no underlying arrives for the remainder.
// 4. B calls cdoEpoch.claimInstantWithdrawRequest() -> _transferFundedClaim(B, X)
//    succeeds because the vault still holds A's funded underlying.
assertEq(underlying.balanceOf(B) - balPreB, X);          // B paid in full
// 5. A calls cdoEpoch.claimWithdrawRequest() -> _transferFundedClaim(A, ...)
//    reverts / underpays: vault balance drained by B's unfunded claim.
```

The broken invariant is one-receipt-one-funded-payout: B's receipt was honored against funds accounted to A, because the instant receipt carries no flag recording whether its epoch's funding was collected.
