### Title
`claimInstantWithdrawRequest` pays instant receipts at par from a commingled pool, draining loss-adjusted reserves that fund normal withdraw receipts - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Rocq bug is a checker that validates only self-recursive calls and ignores cross-calls between bodies, so an argument that grows through a *different* body keeps a stale "structurally smaller" spec. The analog in `IdleCreditVault` is the same shape: every guard on the instant-withdraw path inspects only the instant bucket (`instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `pendingInstantWithdraws`) while the payout spends from a shared underlying balance that also backs funded normal and loss-adjusted receipts. No function on the instant path checks whether the instant queue was actually fully funded before paying a receipt in full.

### Finding Description
`requestInstantWithdraw` mints the user a strategy-token receipt and accrues `pendingInstantWithdraws`, but performs no loss/funding guard — unlike `requestWithdraw`, which reverts when a loss-adjusted receipt exists for `lastWithdrawRequest` (`IdleCreditVault.sol:356-375`, `IdleCreditVault.sol:261-271`). Funding arrives via `collectInstantWithdrawFunds(_amount)`, which only decrements `pendingInstantWithdraws` and pulls `_amount` into the strategy's `underlyingToken` balance (`IdleCreditVault.sol:398-403`). Normal funded receipts are pulled into the *same* balance by `collectWithdrawFunds`, which records a haircut via `lossRecoveryPriceByEpoch` when underfunded (`IdleCreditVault.sol:411-430`).

`claimInstantWithdrawRequest` then burns the aggregate `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` for the *full* par amount (`IdleCreditVault.sol:380-393`). There is no check that `pendingInstantWithdraws == 0`, no per-epoch funded-vs-unfunded split for instant receipts, and no haircut application — the recovery-haircut logic exists only on the normal/APR0 claim paths (`_claimLossAdjustedWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `IdleCreditVault.sol:789-801`, `772-784`) and on the post-default instant path (`_claimDefaultedInstantWithdrawRequest`, `IdleCreditVault.sol:842-856`). Like `find_uniform_parameters` inspecting only self-calls, the instant-claim path is "uniform" w.r.t. itself while the cross-call into the shared funded pool goes unchecked.

### Impact Explanation
Broken invariant: one receipt, one payout; isolation of funded reserves. Sequence:

1. Epoch N running, instant withdraws enabled. Attacker (any KYC'd tranche holder / EOA) calls `requestWithdraw` on the CDO during the instant window → `requestInstantWithdraw`, accruing `instantWithdrawsRequests[attacker] = X` and `pendingInstantWithdraws += X`.
2. Honest borrower returns only enough to partially cover the instant queue plus normal pending receipts (borrower is honest but liquidity-limited — a normal market condition, not attacker-controlled misbehavior). The CDO calls `collectInstantWithdrawFunds(partial < X)` and `collectWithdrawFunds`, leaving `pendingInstantWithdraws > 0` and the strategy holding instant funds commingled with the normal-receipt reserve.
3. The queue calls `cdo.claimInstantWithdrawRequest()` → `claimInstantWithdrawRequest` pays the attacker's *entire* `X` at par from the strategy balance, consuming underlying that was collected to back other users' (possibly haircut) normal receipts.
4. Those users' `claimWithdrawRequest` → `_claimFundedWithdrawRequest` → `_transferFundedClaim` later fails on insufficient balance or pays less: direct theft of funded claims and freezing of unclaimed withdraw receipts, quantified as `X - instantFunded` stolen from the reserve.

The CDO-side `claimInstantWithdrawRequest` gate (`allowInstantWithdraw`) and `_onlyIdleCDO` do not stop this — they check *who/when*, not *whether the instant bucket is solvent*.

### Likelihood Explanation
Medium. Requires an epoch with instant withdraws enabled where the returned liquidity covers instant requests only partially. `defaultInstantWithdrawsFinalized` shows the codebase already acknowledges this state can occur (it handles unfunded instant receipts only after default finalization); the same state pre-default has no guard. Uncertainty: I could not fully verify the ordering in `IdleCDOEpochVariant.stopEpoch`/`_beforeStopEpoch` between `collectInstantWithdrawFunds` and `collectWithdrawFunds` — if normal receipts are always funded *after* instant and the strategy balance at claim time contains only instant money, impact reduces to temporary freezing. A Foundry PoC should confirm the funding order and that the strategy's underlying balance is shared.

### Recommendation
Track funded vs unfunded instant basis (e.g., `instantFundedByEpoch` or paying `min(instantWithdrawsRequests[_user], fundedInstantShare)`), or revert `claimInstantWithdrawRequest` while `pendingInstantWithdraws != 0` so unfunded receipts route through the loss/default haircut paths like normal receipts. Alternatively segregate instant-funded underlying from the general funded-claim pool inside `_transferFundedClaim`.
