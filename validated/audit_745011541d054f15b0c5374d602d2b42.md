### Title
Permanent freeze of all epoch funds: a single APR0 withdraw request bricks `stopEpoch` forever once APR becomes non-zero - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0()` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`, but `apr0TotalPrincipal` is only ever reset to zero inside that same function — *after* the reverting check. An unprivileged KYC-passed lender can therefore open an APR0 withdraw request (1 wei of principal suffices) and, if the honest manager/borrower subsequently sets the vault APR to a non-zero value (a normal operation the APR0 flow exists to accommodate), every subsequent `stopEpoch` call reverts. The epoch state machine is permanently stuck: deposits, pending withdraws and receipt claims can never be funded or settled.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed to `_requestWithdrawApr0`, which does `apr0TotalPrincipal += _amount` [1](#0-0) [2](#0-1) .

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which contains:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
...
apr0TotalPrincipal = 0;
``` [3](#0-2) 

The revert at `unscaledApr != 0` executes *before* `apr0TotalPrincipal = 0`, so the bucket is never cleared. There is no other code path that decrements `apr0TotalPrincipal`: `_settleApr0` only moves the user's `principal` into `settledPrincipal` [4](#0-3) , and `_claimFundedWithdrawRequest` deletes `apr0Users[_user]` without touching the global bucket [5](#0-4) . The check is global, not per-user, so even after the attacker claims or abandons their receipt, `apr0TotalPrincipal` stays non-zero and `stopEpoch` reverts unconditionally and permanently.

Attack sequence:
1. Pool runs an epoch with `unscaledApr == 0` (APR0 mode).
2. Attacker (any KYC-allowed lender) deposits and calls `requestWithdraw` via the CDO, creating a minimal APR0 receipt → `apr0TotalPrincipal > 0`.
3. Honest borrower/manager later sets `unscaledApr` to a non-zero value before that epoch's `stopEpoch` — a legitimate operation (rate renegotiation is exactly what the APR0 mode is built around).
4. `stopEpoch` → `prepareStopEpochWithApr0` → `revert NotAllowed()`, now and forever. `epochEndDate` passes, the pool can never be stopped, closed, or defaulted.

### Impact Explanation
Permanent freezing of 100% of vault TVL and of all pending withdraw receipts. `stopEpoch` is the sole entry point that increments `epochNumber`, funds `pendingWithdraws` via `collectWithdrawFunds`, and triggers borrower repayment; with it permanently reverting, active LPs cannot redeem (tranche burns only settle through epoch-funded claims), pending withdrawers can never claim (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest` and funded underlyings) [6](#0-5) , and even the default/recovery path is unreachable because default is declared through the stop flow. Loss equals the entire contract value at freeze time — analogous to the MySQL CVE's "complete DOS", here with direct, total fund impact rather than mere availability loss.

### Likelihood Explanation
Low cost for the attacker: a dust-size APR0 withdraw request while `unscaledApr == 0`. The trigger condition is an honest privileged action (raising APR from 0), which is plausible in normal operations — APR0 pools exist precisely so the borrower can run zero-interest epochs, and rate changes are a routine manager/borrower call that the security model instructs us to sequence around. No attacker control over privileged roles, oracles, or timing beyond placing the request is required. One caveat I could not fully verify within the indexed code: the exact setter and guardrails on `unscaledApr` (e.g., whether the protocol intends APR to be fixed while APR0 receipts are outstanding, or whether `setApr` is blocked during pending APR0 principal). If a guard elsewhere already forbids changing `unscaledApr` while `apr0TotalPrincipal != 0`, this finding is invalid; nothing in `prepareStopEpochWithApr0`, `requestWithdraw`, `_settleApr0`, or the claim paths enforces it.

### Recommendation
Handle the APR-change case gracefully instead of reverting: e.g., settle the outstanding APR0 bucket at a zero rate (or at the last stored `apr0RateByEpoch`) and clear `apr0TotalPrincipal` before returning, so `stopEpoch` proceeds. Concretely, move `apr0TotalPrincipal = 0` ahead of the `unscaledApr != 0` branch and, when APR is non-zero, finalize each pending APR0 request's principal into its claimable bucket without interest rather than blocking the epoch transition. Alternatively, prevent `unscaledApr` from being set non-zero while `apr0TotalPrincipal != 0` at the setter level, so the invariant "APR0 principal implies APR 0" holds by construction.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness, APR0-configured vault):

```solidity
function testPocApr0StopEpochFreeze() external {
    // pool configured with unscaledApr == 0
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1e6);          // KYC-allowed lender, dust deposit

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // attacker opens an APR0 withdraw request -> apr0TotalPrincipal > 0
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // minimal receipt
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // honest manager/borrower later sets APR > 0 before stopEpoch
    vm.prank(manager); // or borrower, per vault config
    strategy.setApr(10e18); // unscaledApr != 0 now

    // warp past epochEndDate and try to stop: reverts
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // permanent: even after attacker claims/abandons, bucket never clears
    // apr0TotalPrincipal is only zeroed inside the reverting function
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);
}
```

Expected: both `stopEpoch` calls revert, `epochNumber` never advances, and no path exists to clear `apr0TotalPrincipal` while `unscaledApr != 0`, leaving all vault funds permanently frozen.

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
```

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
