### Title
Stale-message check in the Web API Gateway handler can underflow and accept expired/replayed messages - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`HandleLegacyUserMessage` validates message freshness using unsigned integer arithmetic on an attacker-supplied timestamp field. Because the comparison mixes `uint` casts of both the computed cutoff and the client-controlled `payload.Timestamp`, a negative or otherwise adversarial timestamp value can wrap around and make the staleness check evaluate as "not stale" even though the message should be rejected — the same root-cause class as the TWAP report (a freshness/elapsed-time gate whose comparison logic can be defeated so a value is treated as fresh/valid when it should not be).

### Finding Description
The check is: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // "stale message" rejection
}
```

`payload.Timestamp` originates from `webapicap.TriggerRequestPayload`, decoded from the untrusted JSON payload of an inbound `HandleLegacyUserMessage` call reachable from a JSON-RPC/HTTP user-facing gateway message (an unprivileged/internet-facing entry point per the gateway's message-envelope handling described in the module's README). [2](#0-1) 

`uint(payload.Timestamp)` casts a signed `int64` (attacker-controlled) to `uint`. If the client supplies a negative `Timestamp`, the cast wraps to a very large unsigned value (near `2^64`), which will always be greater than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`. This makes the "stale message" branch never trigger for such a payload, defeating the entire purpose of the freshness check — analogous to how the TWAP `update` function's inverted elapsed-time condition let a stale value pass validation indefinitely.

The signature validation for the enclosing `api.Message` (`msg.Sign` / `msg.Validate`) covers message-level fields but the freshness gate is a separate, additional business check performed only inside `HandleLegacyUserMessage` on the decoded payload's `Timestamp` field, which is part of the signed payload but whose *numeric range* is not otherwise bounded before this unsigned comparison.

### Impact Explanation
If this staleness check can be bypassed, previously valid but stale (or maliciously fabricated with adversarial timestamp values) trigger messages could be treated as fresh and forwarded to DON members via `don.SendToNode`, potentially enabling message replay or acceptance of otherwise-rejected requests into the workflow node fan-out path. This mirrors the "denial of service / stale acceptance" class from the analog report, though the concrete blast radius here is bounded to gateway-level message freshness gating rather than direct fund movement.

### Likelihood Explanation
Exploitability depends on whether the JSON decoder for `TriggerRequestPayload.Timestamp` accepts negative integers without rejecting them elsewhere, and whether `msg.Validate()`/signature checks bind the *value* of `Timestamp` to any other invariant (e.g., minimum bound). I was not able to fully confirm the exact Go type and JSON validation constraints of `TriggerRequestPayload.Timestamp` in the indexed code (the definition lives in `core/capabilities/webapi/webapicap/event_trigger_generated.go`, which I could not fully inspect due to index coverage limits). This introduces uncertainty about whether negative timestamps are actually reachable at this check.

### Recommendation
Avoid mixed signed/unsigned comparisons on attacker-controlled timestamp fields. Perform the staleness comparison entirely in signed 64-bit arithmetic (or explicitly reject non-positive/out-of-range timestamps before the check), e.g.:
```go
now := time.Now().Unix()
if payload.Timestamp <= 0 || now-int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp {
    // stale/invalid message
}
```

### Proof of Concept
Conceptual (not verified end-to-end due to inability to confirm the exact `Timestamp` field type/decoder constraints):
1. Craft a `web_api_trigger` message whose JSON payload sets `"timestamp": -1` (or another negative value).
2. Sign the message so it passes `msg.Validate()`.
3. Send it to the gateway's user-facing endpoint that routes into `HandleLegacyUserMessage`.
4. `uint(payload.Timestamp)` wraps to `~2^64-1`, making `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec > uint(payload.Timestamp)` false, so the "stale message" rejection branch is skipped and the message is forwarded to DON nodes.

Note: due to indexing limits I could not verify the exact type/JSON-unmarshal behavior of `webapicap.TriggerRequestPayload.Timestamp`; a Devin session with full repo access would be needed to confirm whether negative values are actually parseable and whether this path is truly exploitable end-to-end.

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if payload.Timestamp == 0 {
		h.lggr.Errorw(ErrDecodingPayload)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload,
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
		h.lggr.Errorw("stale message")
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.HandlerError),
				"stale message",
				nil,
			),
			ErrorCode: api.HandlerError,
		})
	}
