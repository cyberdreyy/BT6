### Title
Signer weight double-counted into both accepted and rejected tallies for the same block sighash - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` aggregates per-block signer weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, keyed by `signer_signature_hash`. The guard used to gate the *rejected* increment (`responded_signers`) and the guard used to gate the *approved* increment (`gathered_signatures`) are two different sets. A single signer can therefore have its weight counted into **both** buckets for the same block by simply sending a `Rejected` message followed by an `Accepted` message (or vice versa), which is exactly the "deposit-then-withdraw" pattern from the Lottery report: state that should be mutually exclusive/reset is instead accumulated without being cleared, corrupting the aggregate used to decide the protocol's outcome.

### Finding Description
In the `Accepted` arm of the message-processing loop, weight is added to `total_weight_approved` guarded only by `block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

In the `Rejected` arm, weight is added to `total_weight_rejected` guarded by a *different* set, `responded_signers`: [2](#0-1) 

Because the Accepted-arm guard (`gathered_signatures`) is never touched by the Rejected arm, and the Rejected-arm guard (`responded_signers`) is never checked by the Accepted arm before incrementing `total_weight_approved`, a signer that sends a `Rejected` message and later a valid `Accepted` message for the *same* `signer_signature_hash` has its weight added to `total_weight_rejected` once and to `total_weight_approved` once. The intended invariant — a signer's weight contributes to at most one of the two mutually exclusive outcome tallies for a given block — is broken: `total_weight_approved + total_weight_rejected` can now exceed the true aggregate weight of participating signers by up to that signer's weight.

This mirrors the Lottery bug's pattern precisely: a state transition (accept↔reject) that is supposed to supersede/replace prior accounting instead only *adds* to it, because the two code paths use non-overlapping dedupe keys. Notably, the project's own changelog documents that this exact defect class ("count both a block acceptance and a block rejection for the same signer/block") was previously identified and fixed — but that fix (in `stacks-signer/src/signerdb.rs::add_block_rejection_signer_addr`, which explicitly checks for an existing signature before accepting a rejection, and vice versa) was applied to the **signer-side** SQLite bookkeeping only: [3](#0-2) [4](#0-3) 

The parallel **node-side** aggregator in `stackerdb_listener.rs`, used by the miner's `SignCoordinator`/`signer_coordinator.rs` to decide whether to abort a proposal (`SignersRejected`) or accept gathered signatures, was not given the equivalent single-outcome guard.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that `signer_coordinator.rs::poll_wait_for_signatures` relies on to decide the fate of a block proposal: [5](#0-4) 

The rejection-threshold check runs before the approval-threshold check on every loop iteration, and returns `Err(NakamotoNodeError::SignersRejected{...})` immediately once `total_weight_rejected + weight_threshold > total_weight`. Because `total_weight_rejected` is a monotonically-increasing counter that is never decremented when a signer flips to `Accepted` (only `reset_rejections` on a full timeout clears it, not a per-signer flip), stale rejection weight from a signer who has since legitimately validated and signed the block remains part of the blocking tally. This can cause the coordinator to spuriously reject/abort a proposal that a full, correct quorum has in fact signed, or — in the reverse timing — let a signer's rejection weight be "reused" to help satisfy the approved-weight threshold's accounting integrity assumptions. Either way, the safety property that each signer's weight is attributable to exactly one outcome is violated, which is the double-counting/"rejection recounted toward acceptance" class explicitly called out as in-scope. This is a liveness/accounting wedge on the miner's block-production path (does not require a majority of signers — only the flipping signer plus normal gossip of both of their StackerDB messages).

### Likelihood Explanation
Low/Medium: this requires no majority and no key compromise — a single signer (or a signer whose messages are naturally delayed/reordered over StackerDB gossip) sending a legitimate `Rejected` then `Accepted` response for the same block sighash is sufficient to trigger the double count. This is a realistic occurrence any time a signer initially rejects (e.g., stale validation state) and then reconsiders and signs after further checks, a pattern the signer-side code explicitly supports and handles correctly, but the node-side listener does not.

### Recommendation
Use a single, shared per-slot "responded" bookkeeping structure (or check `responded_signers`/`gathered_signatures` together) in both the `Accepted` and `Rejected` arms of `stackerdb_listener.rs`, mirroring the fix already applied in `stacks-signer/src/signerdb.rs::add_block_rejection_signer_addr`: before adding weight to `total_weight_approved`, check that the slot has not already been counted as rejected (and vice versa), and when a signer's outcome changes, move the weight from one bucket to the other rather than accumulating it in both.

### Proof of Concept
1. A miner is running `SignCoordinator` and has an in-flight block proposal with `signer_signature_hash = H`.
2. Signer S (slot `i`, weight `w`) sends `BlockResponse::Rejected` for `H`. In `stackerdb_listener.rs`, `responded_signers.insert(i)` succeeds, so `total_weight_rejected += w`.
3. Signer S later sends `BlockResponse::Accepted` for the same `H` (e.g., after re-validating and deciding to sign). In the `Accepted` arm, the guard is `!block.gathered_signatures.contains_key(&i)` — true, since S never previously sent an `Accepted` message — so `total_weight_approved += w` as well.
4. Now `total_weight_approved` and `total_weight_rejected` both include `w`, even though S is a single signer who can only "count" once. `total_weight_approved + total_weight_rejected` exceeds the actual sum of distinct signer weights that responded.
5. `signer_coordinator.rs::poll_wait_for_signatures` evaluates `total_weight_rejected` against the blocking-minority threshold first; depending on timing, either a proposal that in fact reached full signature quorum is aborted due to stale rejection weight from S, or the reject tally is inflated using weight that has already flipped to acceptance — corrupting the coordinator's accept/reject decision for the tenure.
