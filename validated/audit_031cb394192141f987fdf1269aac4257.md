### Title
Zip Slip in `extractZipFile`/`extractZipFileEntry` allows path traversal outside the extraction root - (File: helpers/archives/zip_extract.go)

### Summary
`extractZipFile` and `extractZipFileEntry` use `file.Name` from an untrusted zip archive directly as a filesystem path for `os.MkdirAll(filepath.Dir(file.Name), ...)`, `os.OpenFile(file.Name, ...)`, `os.Mkdir`, and `os.Symlink`, with no validation that the resolved path stays within the intended extraction directory. This is invoked by `ExtractZipArchive`/`ExtractZipFile`, which in turn is called unconditionally by the legacy zip extractor (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) that is registered for the `Zip` format used by cache/artifact extraction.

### Finding Description
`ExtractZipArchive` (helpers/archives/zip_extract.go:85-110) iterates `archive.File` and calls `extractZipFile(file)` for each entry. `extractZipFile` (lines 61-83) does:
```go
err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
```
and dispatches to `extractZipFileEntry`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry`, all of which perform `os.OpenFile`, `os.Mkdir`, or `os.Symlink` directly on `file.Name` (lines 12-59). The only pre-check applied is `errorIfGitDirectory` (helpers/archives/path_check_helper.go), which only rejects paths whose first path segment is `.git`; it does not detect or block `..` traversal segments.

Crucially, `file.Name` is never joined against, or validated against, any "extraction root" directory - the function has no concept of a root at all. This is exploitable because `ziplegacy.extractor.Extract` (commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:26-33) receives a `dir` field (the intended extraction root, passed via `archive.NewExtractor(format, r, size, dir)`) but **never uses `e.dir`** - it opens the zip reader and calls `archives.ExtractZipArchive(zr)` directly, relying entirely on the process's current working directory. Compare this to the sibling `tarzstd` extractor (commands/helpers/archive/tarzstd/tarzstd_extractor.go:57-64), which explicitly computes `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects the entry if `!strings.HasPrefix(path, e.dir+string(filepath.Separator))`. That chroot-style check is completely absent from the zip legacy path.

An unprivileged pipeline author fully controls the contents of cache/artifact zips created by their own jobs (or zips fetched via `cache:`/`artifacts:` job configuration), including crafting `zip.File.Name` values such as `../../shared-vol/payload` or `../../etc/foo`. When such a zip is later extracted by the runner helper (cache restore, artifact download) using the legacy zip extractor, `extractZipFile`'s `MkdirAll(filepath.Dir(file.Name))` and `extractZipFileEntry`'s `OpenFile` will create directories and write files outside the intended build/cache root, relative to whatever the process's current working directory is at extraction time.

### Impact Explanation
A crafted cache/artifact zip can write files to arbitrary relative paths outside the job's designated workspace/cache root, breaking the "file operations must stay within intended build/cache/artifact roots" invariant. In shared-filesystem executor configurations (e.g., Kubernetes executor with a shared `emptyDir`/PVC volume mounted into both the build and service/helper containers), this lets a job plant files in paths that a service container or later step may read/execute, potentially escalating beyond the job's own container identity.

### Likelihood Explanation
Fully attacker-reachable with no special privileges: any pipeline author can create an artifact/cache archive with crafted entry names (standard `archive/zip` API allows arbitrary `File.Name` strings including `../` segments) and have the runner extract it via the normal `cache:`/`artifacts:` job mechanism, which routes through the `Zip` format extractor. The only gate (`errorIfGitDirectory`) does not stop this. This is a deterministic, repeatable "zip slip" pattern with a known, working defensive precedent already implemented for the `tarzstd` extractor in the same codebase.

### Recommendation
Add the same chroot-style validation used in `tarzstd_extractor.go` to the zip extraction path: thread the extraction root directory through `ExtractZipArchive`/`extractZipFile`, resolve each entry as `filepath.Join(root, file.Name)`, take `filepath.Abs`, and reject (or skip with a warning) any entry whose resolved path is not equal to or a descendant of `root`. Also fix `ziplegacy.extractor.Extract` to actually use `e.dir` (currently ignored entirely) rather than relying on process CWD.

### Proof of Concept
```go
func TestExtractZipArchive_PathTraversal(t *testing.T) {
    tmpDir := t.TempDir()
    root := filepath.Join(tmpDir, "extract-root")
    require.NoError(t, os.MkdirAll(root, 0o755))

    outside := filepath.Join(tmpDir, "outside.txt")

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    w, _ := zw.Create("../outside.txt")
    _, _ = w.Write([]byte("pwned"))
    require.NoError(t, zw.Close())

    // simulate extraction rooted at `root` (current CWD-relative behavior)
    wd, _ := os.Getwd()
    require.NoError(t, os.Chdir(root))
    defer os.Chdir(wd)

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)
    require.NoError(t, archives.ExtractZipArchive(zr))

    // Expected (after fix): file must NOT exist outside `root`
    _, err = os.Stat(outside)
    assert.True(t, os.IsNotExist(err), "zip slip: file written outside extraction root")
}
```
Expected assertion after a fix: the traversal entry is rejected/sanitized and no file is created at `outside.txt`; currently, without a root-boundary check, the file is written outside `root`, confirming the vulnerability.
