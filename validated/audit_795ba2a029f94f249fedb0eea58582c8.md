### Title
Missing `return` after failed OIDC callback checks allows session creation to proceed with unvalidated data - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `oidcAuthenticator.handleTokenExchange`, two error/validation checks fail to `return` after logging the failure, letting the OIDC login flow continue and ultimately create and issue an authenticated session cookie based on incomplete or unpersisted data. This mirrors the reported bug class ("check performed but return value/failure ignored, execution proceeds unsafely"), applied to the node's unprivileged, internet-facing OIDC login callback rather than an `ERC20.transferFrom` return value.

### Finding Description
`handleTokenExchange` is the HTTP handler invoked by an unauthenticated client completing the OIDC authorization-code exchange. Two checks in this function detect failure but do not halt execution:

1. Email extraction check without `return`: [1](#0-0) 
If `claims["email"]` is not a string, the code logs an error and writes a 500 response via `c.String`, but does not `return`. Execution continues with `email` set to its zero value (`""`).

2. Session-insert failure check without `return`: [2](#0-1) 
If the `INSERT INTO oidc_sessions` call fails, the code logs the error and writes a 500 response, but again does not `return`. Execution falls through to setting the session cookie.

In both cases, control flow proceeds to: [3](#0-2) 
where the code audits a login success, sets `ginSession` with `clSession.ID`, saves the session cookie, and finally responds `200 OK` with `Success: true` — overwriting/duplicating the earlier failure response body that Gin already started writing.

This is directly analogous to the reported bug class: a return/result is checked (`err != nil` / `ok`) but the failure path does not actually stop execution, so the code proceeds to perform a sensitive state-changing operation (granting a session) using data that was never validated or persisted successfully.

### Impact Explanation
- If the email claim is malformed/missing, a session is still established with an empty `user_email` recorded in `oidc_sessions`, corrupting audit trail integrity (`audit.AuthLoginSuccessNo2FA` is logged with an empty email) despite the identity of the user being indeterminate from that field.
- If the `INSERT INTO oidc_sessions` fails (e.g., transient DB error, unique constraint collision on `clSession.ID`), the handler still sets the session cookie and returns `Success: true` to the client, giving the client a false signal that a valid, persisted session exists. Because the row was never committed, any subsequent lookup by that session ID will fail, but the client is misled about the login outcome, and multiple HTTP writes to `c` (`c.String` followed later by `c.JSON`) is undefined/inconsistent behavior in Gin and can produce corrupted responses.
- Neither path grants a full authentication bypass on its own (the underlying `AuthorizedUserWithSession` session lookup still requires a matching session ID row), but both represent the exact "check-but-don't-enforce" defect class from the report, occurring in unauthenticated, internet-facing code that mutates authentication state (audit log, session table, session cookie).

### Likelihood Explanation
This code path executes on every OIDC callback completion, i.e., for any client (not necessarily privileged) that can complete/replay the OAuth2 code exchange redirect. The missing-`return` defects are unconditionally reachable whenever the ID token's claims are malformed or the DB insert transiently fails — no attacker sophistication is required beyond influencing/observing the OIDC provider response or timing a DB failure.

### Recommendation
Add `return` immediately after each failure branch in `handleTokenExchange`:
- After `c.String(http.StatusInternalServerError, "Failed to get email from claims")` at line 229.
- After `c.String(http.StatusInternalServerError, "Error creating session")` at line 259.

This ensures the session cookie is never set and no success response is sent unless the email was successfully extracted and the session row was successfully persisted.

### Proof of Concept
1. Trigger the OIDC callback (`/sessions/oidc/callback` or equivalent route wired to `handleTokenExchange`) with a manipulated/edge-case ID token response where the `email` claim is absent or non-string (e.g., a number or missing key), while `idClaims`/group claims are still valid enough to pass role mapping.
2. Observe that despite the 500 write at line 229, execution proceeds through role mapping, session creation, and `ginSession.Save()` at line 265–266, and the handler ultimately responds `200 {"success":true}`.
3. Inspect the `oidc_sessions` table row created for this session and note `user_email` is empty, and the `audit.AuthLoginSuccessNo2FA` audit entry records an empty email — confirming the failed check did not stop the authenticated session flow. [4](#0-3)
