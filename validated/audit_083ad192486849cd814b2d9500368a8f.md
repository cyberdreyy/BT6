## Analog Found: Unvalidated `signer_token_account` ownership in marginfi deposit/repay

### Title
Token approvals can be stolen via `LendingAccountDeposit`/`LendingAccountRepay` due to unchecked `signer_token_account` ownership - (File: `programs/marginfi/src/instructions/marginfi_account/deposit.rs`, `programs/marginfi/src/instructions/marginfi_account/repay.rs`)

### Summary
The DAOfi bug class is "no validation that the token source address actually belongs to the caller, so a delegate/approval on a victim's tokens can be redirected to benefit the attacker." The same pattern exists in marginfi's `LendingAccountDeposit` and `LendingAccountRepay` instructions: `signer_token_account` is accepted as an `UncheckedAccount` with no on-chain constraint tying its owner to the transaction's `authority`, and only the SPL Token program's transfer-authority check (owner **or delegate**) gates the CPI.

### Finding Description
In `LendingAccountDeposit`, the source account for the deposit transfer is declared as:
```rust
/// CHECK: Token mint/authority are checked at transfer
#[account(mut)]
pub signer_token_account: UncheckedAccount<'info>,
``` [1](#0-0) 

There is no `has_one`, `constraint`, or `owner ==` check anywhere in the account struct or in `lending_account_deposit()` that ties `signer_token_account`'s owner to `authority.key()`. The instruction simply transfers using `authority` (the tx signer) as the token-program transfer authority: [2](#0-1) 

The same pattern exists in `LendingAccountRepay`:
```rust
/// CHECK: Token mint/authority are checked at transfer
#[account(mut)]
pub signer_token_account: UncheckedAccount<'info>,
``` [3](#0-2) 

The SPL token program itself will happily authorize the transfer if `authority` is either the **owner** of `signer_token_account` *or* an approved **delegate** with sufficient `delegated_amount` — this is the SPL analog of ERC-20's `approve`/`transferFrom`. Because marginfi never checks that `signer_token_account.owner == authority.key()`, any account holding a delegate approval over someone else's token account (from a prior, unrelated `Approve` — e.g., approvals left over for a CEX, aggregator, market maker, or other dApp) can supply the victim's token account as `signer_token_account` while signing as `authority`. The deposit is credited entirely to the attacker's own `marginfi_account` (ownership of the destination marginfi account is enforced via `is_signer_authorized(&a, g.admin, authority.key(), ...)` against `authority`, not against the token account owner): [4](#0-3) 

This exactly mirrors the DAOfi bug's root cause: the router used `lp.sender` (attacker-controlled) instead of validating against `msg.sender`; here marginfi uses an unvalidated `signer_token_account` while only checking that `authority` (attacker-controlled) is *a* valid signer for the transfer — without requiring that `authority` be the actual owner of `signer_token_account`.

### Impact Explanation
An attacker who possesses (or acquires, e.g. through phishing a delegate-approval signature, or from a previously-approved but now-compromised/malicious integration) delegate rights on any victim SPL token account can:
1. Call `lending_account_deposit` (or `lending_account_repay`) with `signer_token_account = victim_account`, `authority = attacker`.
2. The tokens move from the victim's account into the bank's `liquidity_vault`, but the resulting deposit shares are recorded against the **attacker's** `marginfi_account`.
3. The attacker then calls `lending_account_withdraw` to redeem the stolen funds to any destination they choose.

This is a direct, unauthorized value-redirection / theft of approved funds, with full financial impact bounded by the victim's outstanding SPL delegate allowance.

### Likelihood Explanation
Exploitation requires the attacker to hold a delegate approval on the victim's token account. This is a real-world occurrence risk (users routinely leave lingering `Approve` allowances for aggregators, bots, or other protocols); if any such delegate address is malicious or compromised, this path is directly and permissionlessly exploitable without any other precondition (no special account state, no oracle manipulation, no privileged role needed) — this raises it above merely "theoretical."

### Recommendation
Add a constraint ensuring the `signer_token_account`'s owner matches `authority.key()` (analogous to the reported fix of using `msg.sender` rather than an arbitrary caller-supplied address), e.g.:
```rust
#[account(
    mut,
    constraint = signer_token_account.owner == authority.key() @ MarginfiError::InvalidTokenAccountOwner
)]
pub signer_token_account: InterfaceAccount<'info, TokenAccount>,
```
applied to both `LendingAccountDeposit` and `LendingAccountRepay` (and any other instruction accepting an unchecked `signer_token_account`/`funding_account` as a deposit/repay source).

### Proof of Concept
1. Victim Alice's token account `A` has an SPL Token `Approve` delegate set to attacker Bob's pubkey (e.g. from an old dApp interaction) for amount `N`.
2. Bob builds a transaction calling marginfi's `lending_account_deposit` with `authority = Bob` (signs), `marginfi_account = Bob's own account`, `signer_token_account = A`.
3. Marginfi's `deposit_spl_transfer` issues an SPL `transfer`/`transfer_checked` CPI with `authority = Bob`; SPL Token program authorizes it because Bob is `A`'s delegate with allowance ≥ deposit amount.
4. Deposit succeeds: funds leave Alice's account `A`, land in the bank's `liquidity_vault`, and `share_amount` shares are credited to Bob's `marginfi_account` (see `deposit.rs` lines 86-92 and the account-authorization constraint on `marginfi_account`).
5. Bob calls `lending_account_withdraw` to redeem the shares to any token account he controls, completing the theft of Alice's approved funds.
