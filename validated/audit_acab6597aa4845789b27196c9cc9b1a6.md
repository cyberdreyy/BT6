### Title
Mid-epoch APR change leaves `expectedEpochInterest` stale, letting a `depositDuringEpoch` caller over-mint tranche shares and steal epoch yield - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The external bug class is: a privileged call fixes an off/on-chain claim basis (merkle root / expected interest), while an intervening unprivileged deposit changes accrued interest, so the stored basis no longer matches reality and value is misallocated or locked. The idle-tranches analog lives in `depositDuringEpoch` (`contracts/IdleCDOEpochVariant.sol:656-733`). The minted amount uses `expectedEpochInterest` — a value computed once at epoch pricing — as the "existing holders' expected final NAV" denominator, while the new deposit's own `interest` is computed at the *current* scaled APR (`_calcInterest(_amount)`). `IdleCreditVault.setApr`/`setAprs` (`contracts/strategies/idle/IdleCreditVault.sol:206-235`) allows the manager to change `lastApr` mid-epoch without updating `expectedEpochInterest`. After an honest APR increase, `expectedFinal` in the mint formula is understated while the deposit interest is overstated, so the depositor mints strictly more shares than fair, diluting existing AA/BB holders' claim on epoch interest.

### Finding Description
`depositDuringEpoch` mints via:

```solidity
uint256 interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer);
uint256 expectedInt = expectedEpochInterest;          // fixed at epoch start APR
...
uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
...
expectedEpochInterest += interest;                     // accrues at NEW apr
```

- `trancheExpected` (existing holders' interest claim) is derived from stale `expectedEpochInterest`, priced at the epoch-start APR.
- `trancheInterest` (the new deposit's credit) is computed at `lastApr`, which the manager may have raised via `IdleCreditVault.setAprs`/`setApr` mid-epoch (manager is honest but the call is permissioned to them by design).
- `expectedEpochInterest += interest` then bakes the new-APR interest into the borrower's stopEpoch liability, so the protocol actually owes the inflated total at `stopEpoch` — the over-minted shares are fully backed and the loss is socialized across pre-existing holders.

Broken invariant: fair mint — shares minted should equal the pro-rata claim on final NAV. Guards do not stop it: `depositDuringEpoch` only requires `isDepositDuringEpochDisabled == false`, a running epoch before `epochEndDate`, non-empty tranche supply, KYC (`isWalletAllowed`), and no AYS/programmable mode — all satisfiable by an ordinary whitelisted lender.

### Impact Explanation
Direct theft of yield / dilution of honest tranche holders. The attacker captures the spread between the stale expected interest (denominator) and the new-APR interest (numerator credit). Magnitude scales with `(newApr - oldApr) × remaining time × deposit size`, bounded by `maxApr` (default cap exists in `IdleCreditVault.maxApr`). With a doubled APR and a deposit comparable to pool size, the attacker can capture a mid-single-digit percentage of the pool's epoch interest that belongs to existing holders.

### Likelihood Explanation
Requires (1) fixed-APR non-AYS non-programmable vault, (2) `isDepositDuringEpochDisabled` unset (owner enables it for legit mid-epoch deposits), (3) an honest manager APR adjustment mid-epoch via `setAprs`, and (4) a KYC'd attacker depositing after the change. All are normal operational sequences — no malicious privilege needed. Medium likelihood.

### Recommendation
Recompute `expectedEpochInterest` atomically whenever `lastApr` changes mid-epoch (e.g., have `setApr`/`setAprs` callback update the CDO's expected interest for the remaining period), or recompute the existing-holders' expected interest inside `depositDuringEpoch` from the current APR rather than the stored `expectedEpochInterest`. Alternatively, disable `depositDuringEpoch` after any mid-epoch APR change.

### Proof of Concept
```solidity
// Fork-based Foundry PoC (test/foundry/), modeled on testDepositDuringEpochNumericalAA
function testMidEpochAprChangeDilution() external {
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);
    vm.stopPrank();

    idleCDO.depositAA(1000 * ONE_SCALE);
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    _startEpochAndCheckPrices(0);            // expectedEpochInterest = 100e6 @10%

    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);

    // Honest manager raises APR mid-epoch; expectedEpochInterest stays at 100e6
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(20e18, 20e18);

    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    address attacker = makeAddr('attacker');
    deal(defaultUnderlying, attacker, 1000 * ONE_SCALE);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), 1000 * ONE_SCALE);
    uint256 minted = cdoEpoch.depositDuringEpoch(1000 * ONE_SCALE, address(AAtranche));
    vm.stopPrank();

    // Fair minted (if denominator used refreshed 150e6 expected interest):
    //   (1000 + 100) * 1000e18 / 1150 = 956.52e18
    // Actual minted uses stale 100e6 interest -> (1000+100)*1000e18/1100 = 1000e18
    assertGt(minted, 956521739130434782608);  // over-mint vs fair value

    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(20e18, 0);

    uint256 price = cdoEpoch.virtualPrice(address(AAtranche));
    // attacker value > principal + its true interest; old depositor < 1150 expected
    assertGt(minted * price / ONE_TRANCHE_TOKEN, 1100 * ONE_SCALE);
    assertLt(IERC20(address(AAtranche)).balanceOf(address(this)) * price / ONE_TRANCHE_TOKEN, 1150 * ONE_SCALE);
}
```
