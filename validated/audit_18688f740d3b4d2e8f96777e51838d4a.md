### Title
`SystemInstruction::InitializeNonceAccount` has no signer/access check on the nonce account, enabling frontrun-based hijacking of nonce authority - ([File: programs/system/src/system_processor.rs])

### Summary
The `InitializeNonceAccount` instruction sets the durable-nonce `authority` field on an uninitialized system-owned account without requiring any signature — not from the nonce account itself, nor from the authority being installed. Any unprivileged transaction sender can race a legitimate initialization and become the nonce authority for someone else's freshly-created (but not-yet-initialized) nonce account.

### Finding Description
The processor dispatch for `InitializeNonceAccount` only requires a single instruction account (the nonce account) and performs no signer verification before calling into `initialize_nonce_account`: [1](#0-0) 

`initialize_nonce_account` itself never checks `is_signer`/authority relationship — it merely checks that the target account state is `Uninitialized` and rent-exempt, then unconditionally writes the caller-supplied `nonce_authority` pubkey into the account state: [2](#0-1) 

This mirrors the reported `CollateralManager.setCollateralEscrowBeacon` bug class exactly: a one-time "initializer" function is guarded only by an idempotency check (`Uninitialized` state / `reinitializer(2)`), but has no restriction on *who* may call it. Whoever's transaction lands first on an eligible uninitialized account controls the resulting authority. Compare with the sibling `AuthorizeNonceAccount`/`WithdrawNonceAccount` paths, which do enforce `check_signer` against the recorded authority once the account is initialized: [3](#0-2) 
No equivalent check exists for the initial `Initialize` transition.

### Impact Explanation
If account creation (`CreateAccount`, funding the nonce account and setting its owner to the System Program) and nonce initialization (`InitializeNonceAccount`) are ever submitted as separate transactions — e.g., by a wallet, exchange, or dApp workflow that creates the account first and initializes it in a follow-up transaction — an attacker monitoring the mempool can submit their own `InitializeNonceAccount` naming themselves as `nonce_authority` and have it land first. Because the check is purely "is this account still `Uninitialized`", whoever wins the race becomes the durable-nonce authority. Once installed as authority, the attacker can:
- Fully drain the account via `WithdrawNonceAccount`, which permits withdrawing the entire balance (`lamports == from.get_lamports()`) with only the attacker's own signature as authority, bypassing the rent/min-balance floor that applies to partial withdrawals: [4](#0-3) 
- Or retain persistent control of the nonce (advance/re-authorize) to disrupt the legitimate owner's durable-transaction flows.

This is a concrete unsigned fund-movement/authority-hijack primitive reachable from a single unprivileged transaction.

### Likelihood Explanation
Likelihood depends on client behavior: if account creation and initialization are always atomically combined in one transaction (as is conventional practice via helper builders), this is not exploitable, since both instructions commit or fail together and an attacker cannot interleave a transaction between them. The vulnerability is only reachable when a caller (wallet, program, or CLI flow) submits `CreateAccount` and `InitializeNonceAccount` as two separate transactions, leaving a window where the account exists, is rent-exempt, and is `Uninitialized`. The instruction-level check itself provides no defense against this regardless of caller intent — the protection currently relies entirely on client-side transaction packaging convention rather than on-chain enforcement.

### Recommendation
Require that the account being initialized (or the `nonce_authority` account named in the instruction, similar to `bpf_loader_upgradeable`'s `SetAuthority` pattern) be a transaction signer in `initialize_nonce_account`/`SystemInstruction::InitializeNonceAccount`, so that only the party controlling the newly created account (or an authority that has consented by signing) can perform the one-time initialization. At minimum, document and enforce that `CreateAccount` + `InitializeNonceAccount` must be atomic within a single transaction, and consider adding a defensive signer check on the nonce account itself for the `Uninitialized -> Initialized` transition.

### Proof of Concept
1. Victim submits transaction A: `SystemInstruction::CreateAccount` creating account `N` (owned by System Program, sized for `nonce::state::Data`, rent-exempt), intending to send a follow-up `InitializeNonceAccount(victim_authority)` transaction B.
2. Attacker observes account `N`'s creation (or predicts its address, e.g. via `create_with_seed`) and, before transaction B lands, submits `SystemInstruction::InitializeNonceAccount(attacker_authority)` referencing `N` as the sole account — no signature from `N` or `attacker_authority` is required per `system_processor.rs`'s account-count check and `initialize_nonce_account`'s lack of `is_instruction_account_signer` checks.
3. Once this attacker transaction lands, `N`'s state becomes `Initialized` with `authority = attacker_authority`. Victim's transaction B now fails with `InstructionError::InvalidAccountData` (already initialized), and legitimate control is lost.
4. Attacker submits `WithdrawNonceAccount(full_balance)` signed only by `attacker_authority`, which is permitted for a full-balance withdrawal without any rent/min-balance requirement, draining `N`'s lamports to an attacker-controlled recipient account.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
