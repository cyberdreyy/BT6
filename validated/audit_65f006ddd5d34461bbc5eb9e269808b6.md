### Title
Missing validation that `num_confirmations` is nonzero allows a single-key holder to bypass the K-of-N multisig threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::new()` accepts `num_confirmations: u32` with no validation that it is greater than zero. `confirm()` then approves and executes a request once `confirmations.len() + 1 >= self.num_confirmations` [1](#0-0) . If `num_confirmations` is `0`, this comparison (`1 >= 0`) is trivially true on the very first confirmation, so any single key holder can execute arbitrary `Transfer`, `FunctionCall`, `AddKey`/`DeleteKey`, or `DeployContract` actions without ever reaching the intended K-of-N threshold.

### Finding Description
The initializer performs no bounds check on `num_confirmations`: [2](#0-1) 

The confirmation logic compares the number of confirmations collected against `self.num_confirmations` and executes the request as soon as the threshold is met: [3](#0-2) 

If `num_confirmations` is `0` (whether set at `new()` or later via the unvalidated `SetNumConfirmations { num_confirmations }` action [4](#0-3) ), the very first `confirm()` call — even from a single, low-privilege function-call access key added to the multisig — satisfies `1 >= 0` and immediately triggers `execute_request`, bypassing the "K of N" custody guarantee the contract is documented to provide ("Set K out of N multi sig scheme ... until the required number of confirmation achieved" per `multisig/README.md`).

This is structurally the same bug class as the `SpeedBumpPriceGate.addGate()` report: a numeric configuration parameter (`priceIncreaseDenominator` / `num_confirmations`) is accepted without a floor check, and a later arithmetic/comparison operation that depends on that parameter silently produces a broken invariant instead of the intended guarantee.

The sibling implementation `multisig2/src/lib.rs` mitigates part of this (`assert(members.len() >= num_confirmations as usize, ...)` in `new()` [5](#0-4) ) but that check is also satisfied trivially when `num_confirmations == 0`, so the same threshold-bypass exists there too.

### Impact Explanation
This breaks the binding "confirmations counted versus live members/threshold": the contract is supposed to require `K` independent confirmations before moving funds or changing keys, but with `num_confirmations = 0` a single access-key holder — who may have been granted only a limited `FunctionCallPermission` key, not full ownership — can execute `Transfer` actions and drain the account, or add a full-access key for persistence. This matches the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
Requires the multisig to actually be initialized (or reconfigured via `SetNumConfirmations`) with `num_confirmations = 0`, which is a configuration/input-validation gap rather than requiring any privileged bypass by the attacker — any holder of one of the multisig's access keys can then unilaterally execute any request. No redeploy or malicious validator is needed by the attacker; the attacker merely needs to be one of the (possibly limited-permission) key holders once such a misconfiguration exists.

### Recommendation
Add `assert!(num_confirmations > 0, "num_confirmations must be positive")` in `MultiSigContract::new()` and in the `SetNumConfirmations` handler in both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, in addition to the existing (or added) `members.len() >= num_confirmations` check.

### Proof of Concept
1. Deploy `multisig/src/lib.rs` and call `new(0)` (or later execute a confirmed `SetNumConfirmations { num_confirmations: 0 }` request).
2. Add at least one function-call access key (even one restricted via `FunctionCallPermission`) to the multisig account, as intended by the K-of-N design.
3. From that single key, call `add_request_and_confirm` with a `Transfer` action targeting an attacker-controlled account.
4. In `confirm()`, `confirmations.len() as u32 + 1 (=1) >= self.num_confirmations (=0)` evaluates true, so `execute_request` runs immediately with only one confirmation, transferring funds out of the multisig without reaching any real threshold. [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
