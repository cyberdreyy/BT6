### Title
Unauthenticated flooding of `savedCallbacks` causes premature eviction of other users' pending callbacks - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores every valid (signed, non-stale, correct-method) request into a single shared map `h.savedCallbacks` keyed only by `MessageId`, with no per-sender quota or allowlist check [1](#0-0) . `pruneCallbacks` enforces a global size cap by deleting the globally-oldest entries once the map exceeds `MaxSavedCallbacks`, without regard to which sender created them [2](#0-1) . An attacker who can produce validly-signed `web_api_trigger` messages (any holder of an ECDSA signing key, since `msg.Validate()`/`msg.Sign()` only checks message well-formedness and signature validity, not sender authorization) can flood the gateway with enough requests to push the map over `MaxSavedCallbacks`, causing legitimate, not-yet-expired callbacks from unrelated users to be evicted before their response arrives or before `CallbackMaxAgeSec` elapses.

### Finding Description
- Entry point: `gateway.ProcessRequest` decodes any JSON-RPC request with a `DonId`, validates the message signature/shape via `msg.Validate()`, and dispatches to `handler.HandleLegacyUserMessage` [3](#0-2) . This validation only confirms the message is well-formed and signed by *some* key; it performs no sender allowlist or per-sender rate limiting.
- Inside `HandleLegacyUserMessage`, after basic payload/timestamp/method checks, the handler unconditionally inserts the message into the shared map: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` [4](#0-3) . The code explicitly acknowledges the missing control: `// TODO: apply allowlist and rate-limiting here` [5](#0-4) .
- `pruneCallbacks` runs periodically (via `CallbackPruneIntervalSec`), first removing entries older than `CallbackMaxAgeSec`, then — if the map is still over `MaxSavedCallbacks` — sorts *all remaining entries* (from all senders) by `createdAt` and deletes the oldest half, entirely ignoring which caller owns them: `entries[:len(entries)-maxSize/2]` [2](#0-1) .
- Because eviction is keyed purely on age and total count with no per-sender fairness/quota, an attacker submitting a burst of requests exceeding `MaxSavedCallbacks` (default 20,000, configurable) can cause a victim's earlier, still-unexpired legitimate callback to be deleted from the map before the corresponding node response arrives. When the DON's response for the victim later arrives at `handleWebAPITriggerMessage`, the lookup `h.savedCallbacks[msg.Body.MessageId]` will miss (`found == false`), so the victim's callback is silently dropped — the callback goroutine will eventually time out with a gateway `RequestTimeoutError` rather than getting its real response.
- No auth/role check or upstream rate limiter's/allowlist mediates this: `nodeRateLimiter` in the handler is only used to throttle *node*-originated messages (`HandleNodeMessage`/outgoing), not for gating incoming user `HandleLegacyUserMessage` calls; there's no equivalent for the user-facing legacy path.

### Impact Explanation
This is a scoped denial-of-service / cross-user response-loss condition: an unprivileged sender can cause other unrelated legitimate callers' pending `web_api_trigger` requests to silently fail (timeout) instead of receiving their genuine response, by exhausting the shared `savedCallbacks` map. This matches a "Denial of Service / degraded availability affecting other users' requests" impact class — it does not disclose secrets or bypass authentication but does violate isolation between unrelated callers' pending requests, causing response loss for victims.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to produce a validly-signed JSON-RPC message with `MethodWebAPITrigger`, a fresh timestamp, and a valid `TriggerRequestPayload` — using any ECDSA key pair they control (no assigned role, no API token, no allowlist entry required per the code as-is, since the `// TODO: apply allowlist` gap has not been implemented). The attack is straightforward to script (send many uniquely-keyed valid messages in a burst) and repeatable at will, limited only by `MaxSavedCallbacks` (default 20,000) and the `CallbackPruneIntervalSec` cadence.

### Recommendation
- Implement the pending `// TODO: apply allowlist and rate-limiting here` check in `HandleLegacyUserMessage` before inserting into `savedCallbacks` — enforce a per-sender/per-key quota on outstanding entries and/or a global incoming-request rate limiter (reusing/extending `ratelimit.RateLimiter`, analogous to `nodeRateLimiter`).
- Change `pruneCallbacks` eviction policy to be fairness-aware (e.g., cap outstanding callbacks per sender, or reject new inserts once the global cap is reached rather than evicting others' unexpired entries).
- Consider tracking `savedCallback` entries keyed by `(sender, MessageId)` and rejecting/backpressuring new insertions from a sender that already holds many pending callbacks.

### Proof of Concept
Handler-level Go test plan (extends `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct `handler` via `setupHandler(t)` with a small `MaxSavedCallbacks` (e.g., 10) and `CallbackMaxAgeSec` large (e.g., 120s) for determinism.
2. Insert a "victim" callback first via `HandleLegacyUserMessage` with a unique `MessageId="victim-1"` signed by a victim key, and register a callback `cbVictim`.
3. Immediately after, loop an "attacker" (different signing key) sending `MaxSavedCallbacks` additional distinct `MessageId`s via `HandleLegacyUserMessage`, all well within `CallbackMaxAgeSec`.
4. Call `handler.pruneCallbacks()` directly (or wait for the internal ticker) and then assert, via `handler.mu.Lock(); _, found := handler.savedCallbacks["victim-1"]`, whether the victim's still-unexpired entry was evicted purely due to attacker flooding.
5. Expected (documenting the vulnerability): `found == false` even though `now - victim.createdAt < CallbackMaxAgeSec`, i.e., the victim's callback was evicted purely by volume from an unrelated, unprivileged sender — proving the lack of per-sender isolation/quota in `pruneCallbacks`.

	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)

		}
	}
