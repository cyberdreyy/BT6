### Title
Shared global rate-limit token bucket can be drained by a single unprivileged sender exceeding only their own per-sender quota, causing denial-of-service for all other senders - (File: core/services/workflows/ratelimiter/ratelimiter.go)

### Summary
The `RateLimiter.Allow` implementation used to gate workflow/trigger requests always consumes a token from the shared **global** bucket, even when the calling sender has already exceeded (and will be rejected by) its own **per-sender** bucket. This mirrors the Linea rate-limiter bug class: a single unprivileged, well-resourced caller can burn through the protocol-wide/shared limit while being individually throttled, denying the shared resource to every other legitimate sender.

### Finding Description
`RateLimiter.Allow` is documented as a wrapper that supports "both global and a per-sender rate limiting" [1](#0-0) . Its implementation unconditionally evaluates both limiters on every call and returns both results independently:

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	...
	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
``` [2](#0-1) 

Because `rl.global.Allow()` is invoked regardless of the outcome of `senderLimiter.Allow()`, a sender that has already exhausted its own per-sender allowance (so `senderAllow == false` and the request is rejected) still consumes one token from the shared global bucket on every retry. There is no short-circuit that skips the global check once the sender check fails. This is the same root cause pattern as the Linea `RateLimiter.sol` issue referenced in the external report: a protocol-wide/shared limit that any single caller can drain through repeated (even individually-rejected) attempts, at the expense of every other caller relying on the same shared resource.

This rate limiter class is used to gate node/gateway-facing request handling for workflow requests (analogous "global" vs "per-sender"/"per-workflow" limiter shapes also appear in the Gateway's HTTP Trigger/Action handlers, e.g. the `userRateLimiter` with `globalRPS`/`perSenderRPS` config used for inbound, JWT-authenticated HTTP Trigger requests from external, otherwise-unprivileged clients) [3](#0-2) , and per-node/global limiters in the Gateway `http_handler.go` for outbound requests [4](#0-3) .

### Impact Explanation
If a caller (sender/workflow ID) that has no special privilege beyond normal request access continuously issues requests past its own per-sender quota, each such call still debits the shared global token bucket. Once the global bucket is exhausted, `globalAllow` becomes `false` for every other sender, causing legitimate requests from unrelated, well-behaved senders to be rejected — a denial-of-service of the shared endpoint/trigger path, without the attacker needing to succeed at anything beyond making network calls.

### Likelihood Explanation
The bug requires no special access: a single unprivileged caller identified only by its own `sender` string can repeatedly call the rate-limited entry point. Because Go's `rate.Limiter.Allow()` is stateless and cheap to invoke, sustaining enough request volume to exhaust a modest global burst/RPS setting is straightforward for any client capable of making network requests.

### Recommendation
Skip the global-bucket consumption when the per-sender check already fails, i.e., only call `rl.global.Allow()` when `senderAllow` is `true` (short-circuit evaluation), or reserve/release tokens atomically so a per-sender-rejected request cannot debit the shared global bucket:
```go
senderAllow = senderLimiter.Allow()
if !senderAllow {
    return false, true // or appropriate default; do not touch global bucket
}
globalAllow = rl.global.Allow()
```
Additionally, consider tracking and alerting on senders that repeatedly hit their per-sender limit, since that is itself a signal of abuse attempting to exhaust the shared global bucket.

### Proof of Concept
1. Configure `RateLimiter` with `PerSenderRPS/PerSenderBurst` small (e.g. 1/1) and `GlobalRPS/GlobalBurst` larger (e.g. 50/50).
2. From a single `sender` identity, call `Allow(sender)` in a tight loop well beyond its per-sender burst.
3. Observe that `senderAllow` quickly becomes `false` (correctly throttling that sender) — but `globalAllow` also flips to `false` for other senders far faster than expected, because every one of the attacker's calls (including the rejected ones) still consumed a token from `rl.global`, as shown at [5](#0-4) .
4. A concurrently-running legitimate sender making requests within its own per-sender quota will now receive `globalAllow == false` and be denied service, despite never exceeding its own allotment.

func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
```
