### Title
EI role incorrectly recognized as "user", allowing external initiators to trigger arbitrary non-webhook jobs via integer job ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` intends to restrict integer-job-ID runs to authenticated users only (rejecting external initiators), but the check `_, isUser := auth.GetAuthenticatedUser(c)` only verifies presence of `auth.SessionUserKey` in the gin context, which `AuthenticateExternalInitiator` also sets (to `&clsessions.User{Role: clsessions.UserRoleRun}`). As a result, a caller authenticated only via EI credentials passes the `isUser` check and can trigger `prc.App.RunJobV2` for any job by numeric ID, not just webhook jobs.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in a group that accepts EI, token, or session authentication interchangeably: [1](#0-0) . `auth.AuthenticateExternalInitiator` authenticates purely via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers and then sets the same `SessionUserKey` used by real logged-in users, giving the EI a synthetic `User{Role: UserRoleRun}`: [2](#0-1) .

In `Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed", but the guard only checks whether `SessionUserKey` exists via `GetAuthenticatedUser`, which returns `true` for both real users and EI-derived synthetic users: [3](#0-2)  and [4](#0-3) . Because `AuthenticateExternalInitiator` deliberately populates `SessionUserKey`, `isUser` is `true` for an EI-only-authenticated request, defeating the intended EI/user distinction and allowing `RunJobV2` to be invoked with any integer job ID for any job type (OCR, direct-request, cron, flux monitor, etc.), not just the webhook jobs EIs are meant to trigger.

### Impact Explanation
An attacker holding only EI credentials (no operator/admin access) can trigger execution of arbitrary non-webhook jobs on the node by numeric job ID, bypassing the intended restriction that EIs may only start webhook-type job runs. This is an authorization bypass allowing unauthorized job execution, which can trigger unwanted on-chain transactions, resource consumption, or unintended pipeline side effects — matching Chainlink's "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs valid EI access-key/secret credentials (the lowest tier of node API credential, `RequiresRunRole` is satisfied by the synthetic EI user). No admin/session/API-token credentials are needed. The request is a simple, repeatable HTTP POST to `/v2/jobs/:ID/runs` with a numeric ID in the path — fully attacker-controlled and requires no race condition or timing.

### Recommendation
Distinguish EI-derived synthetic users from real authenticated users, e.g. by checking `auth.GetAuthenticatedExternalInitiator(c)` (returns ok only when `SessionExternalInitiatorKey` was set) in addition to/instead of `GetAuthenticatedUser`, and reject the integer-ID path when the request was authenticated as an EI. Alternatively, have `AuthenticateExternalInitiator` set a distinct context key instead of reusing `SessionUserKey`, and update all role-check helpers that rely on `SessionUserKey` accordingly.

### Proof of Concept
Go handler-integration test plan (extending `core/web/pipeline_runs_controller_test.go`):
1. Create an app, insert an External Initiator via `cltest.MustInsertExternalInitiator` (or equivalent helper), and create a non-webhook job (e.g., the OCR job from `setupPipelineRunsControllerTests`).
2. Build an HTTP client that sets only `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers (no session cookie, no `X-API-KEY`/`X-API-SECRET`).
3. POST to `/v2/jobs/<jb.ID>/runs` (integer ID) using that EI-only client.
4. Assert the response is `200 OK` with a valid pipeline run resource (i.e., `prc.App.RunJobV2` was invoked) — demonstrating that the "EIs not allowed" guard in `Create` does not actually block EI callers.
5. Contrast with expected behavior: assert should instead be `401`/`422` since EIs should not be able to run non-webhook jobs by integer ID. [3](#0-2) [2](#0-1) [1](#0-0)
