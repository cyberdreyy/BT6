### Title
Claimed instant-withdraw receipts are never released from per-epoch tracking, inflating default recovery basis and locking reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the restrack leak (a tracking entry not released when its object is deleted), `claimInstantWithdrawRequest` clears the per-user aggregate `instantWithdrawsRequests` but never clears `instantWithdrawsRequestsByEpoch[user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If default finalization happens while `pendingInstantWithdraws` is still non-zero for that same epoch, the already-paid claim basis is counted again in `defaultPendingClaimBasis`, permanently diluting `defaultRecoveryPrice` and stranding the phantom share of `defaultRecoveryReserve`.

### Finding Description
`requestInstantWithdraw` records three pieces of tracking state: `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][epoch]`, and `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . The normal claim path releases only the first of them [2](#0-1) . The per-epoch entries are only ever cleared inside the default-recovery claim path `_claimDefaultedInstantWithdrawRequest` [3](#0-2) , which is unreachable for a receipt that was already claimed normally.

This stale tracking is load-bearing for default accounting: `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve` uses the same aggregate to size prefunded reserve [4](#0-3) . Partial funding is an explicitly supported path — `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` by any `_amount` [5](#0-4)  and the code comments describe exactly the "cash covered only part of the instant queue" case [6](#0-5) . `_transferFundedClaim` only requires the contract to hold enough underlying outside the (still zero pre-finalization) reserve, so an instant claimant whose receipt fits in the collected amount can claim while `pendingInstantWithdraws` remains positive [7](#0-6) .

When `finalizeDefaultRecovery` later runs, `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` includes the ghost basis, so every legitimate defaulted receipt and active LP is haircut more than the true recovery warrants, and the reserve fraction attributed to the phantom basis can never be claimed — the claimant's receipt tokens were already burned, and a second claim through `_claimDefaultedInstantWithdrawRequest` reverts on the `instantWithdrawsRequests[_user] -= claimBasis` underflow / `_burn` [8](#0-7) .

### Impact Explanation
Permanently locked recovery funds and diluted payouts. For each unit `X` of instant receipt claimed before finalization while `pendingInstantWithdraws != 0`, `totalBasis` is inflated by `X`; `defaultRecoveryPrice` drops proportionally, and `defaultRecoveryReserve * X / totalBasis` of underlying is stranded in the strategy forever since no live receipt maps to it. Additionally, the double-tracked user's subsequent claim reverts (underflow on `instantWithdrawsRequests` and burn of already-burned receipts), freezing any other receipts they hold. This is a direct solvency/"one receipt one payout" invariant break caused by unreleased tracking state, matching the bug class exactly.

### Likelihood Explanation
Requires the conjunction of (a) an instant-withdraw claim paid while the epoch's instant queue is only partially funded (`pendingInstantWithdraws > 0` — a documented, supported state) and (b) borrower default finalization occurring in that same epoch. Both are within honest privileged sequencing (manager stopEpoch/default flows, honest borrower defaulting), and the attacker is merely an ordinary tranche-token holder/instant withdrawer. Medium likelihood; impact is bounded by the instant-queue size but is a real, permanent loss.

### Recommendation
In `claimInstantWithdrawRequest`, release the per-epoch tracking the same way the default path does: iterate or track the user's request epochs and set `instantWithdrawsRequestsByEpoch[user][epoch] = 0` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed basis before burning. Since `requestInstantWithdraw` always writes to the current `epochNumber`, a user only ever has one open epoch entry, so clearing `instantWithdrawsRequestsByEpoch[_user][<requestEpoch>]` and subtracting from `instantWithdrawClaimsByEpoch[<requestEpoch>]` is sufficient (a `lastInstantWithdrawRequest`-style epoch marker may be needed, or reuse the pattern from `_clearWithdrawClaimForEpoch`).

### Proof of Concept
```solidity
// Foundry fork PoC sketch, on the deployed IdleCreditVault + IdleCDOEpochVariant
// Setup: epoch N running, instant mode enabled, attacker holds tranche tokens.
uint256 e = vault.epochNumber();

// 1. Attacker requests instant withdraw of X
cdo.requestInstantWithdraw(X, tranche); // burns X, mints receipt,
// instantWithdrawsRequestsByEpoch[attacker][e] = X,
// instantWithdrawClaimsByEpoch[e] = X (plus others' claims)

// 2. Honest manager/borrower partially funds the instant queue:
//    CDO pulls amount >= X but < pendingInstantWithdraws via
//    getInstantWithdrawFunds -> vault.collectInstantWithdrawFunds(amount)
//    pendingInstantWithdraws remains > 0; strategy holds >= X underlying.

// 3. Attacker claims normally while queue is partially unfunded:
cdo.claimInstantWithdrawRequest(attacker, tranche);
// vault pays X, burns receipt, instantWithdrawsRequests[attacker] = 0
// BUG: instantWithdrawsRequestsByEpoch[attacker][e] still = X,
//      instantWithdrawClaimsByEpoch[e] unchanged.

// 4. Borrower defaults; manager runs _handleBorrowerDefault + finalizeDefaultRecovery:
//    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[e]
//    -> includes attacker's already-paid X.
//    recoveryPrice = reserve / (trueBasis + X)  -> underpays everyone.
//    Attacker's entry is unclaimable: _claimDefaultedInstantWithdrawRequest
//    reverts (instantWithdrawsRequests underflow / burn of burned receipts),
//    so reserve * X / totalBasis is stranded in the vault permanently.
assertGt(vault.instantWithdrawsRequestsByEpoch(attacker, e), 0);
assertGt(vault.instantWithdrawClaimsByEpoch(e), /* live basis */);
```

Note: the exploit depends on step 2 being reachable — the CDO must permit collecting/claiming a funded instant receipt while `pendingInstantWithdraws` is still positive. The strategy code explicitly supports partial collection, but I did not fully verify the CDO-side gating of `claimInstantWithdrawRequest` in `IdleCDOEpochVariant.sol`; if it enforces full queue funding before any claim, the stale-entry leak reduces to an accounting inconsistency without the fund-impact path described.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
