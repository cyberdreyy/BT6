### Title
Instant-withdraw receipts are keyed to the request epoch but cleared at the finalization epoch, letting unfunded instant claims be paid at par after default - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The LibRaw bug class (an index/length computed from attacker-controlled file data that lands outside the intended buffer, so valid-looking data is read past its bounds) maps directly onto `IdleCreditVault`'s per-epoch receipt ledgers. Instant-withdraw receipts are *written* under `instantWithdrawsRequestsByEpoch[user][epochNumber]` at request time (mid-epoch N), but default finalization computes the recovery basis and later *clears* claims using `epochNumber` at finalization time — after `stopEpoch`/`deposit()` has already incremented `epochNumber` to N+1. The receipts therefore sit "out of bounds" of the recovery accounting: they are never included in `defaultPendingClaimBasis()` and never cleared by `_claimDefaultedInstantWithdrawRequest`, so `claimInstantWithdrawRequest` falls through and pays them at par via `_transferFundedClaim`.

### Finding Description
- `requestInstantWithdraw` books receipts under the *current* `epochNumber`: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .
- `epochNumber` is incremented inside `deposit()` whenever it is called while the epoch is running — i.e., during the `stopEpoch` sequence that detects the default [2](#0-1) . So a request made in running epoch N is keyed under N, while `finalizeDefaultRecovery` snapshots `defaultRecoveryEpoch = epochNumber` = N+1 [3](#0-2) .
- `defaultPendingClaimBasis()` only adds `instantWithdrawClaimsByEpoch[epochNumber]` (the already-bumped N+1, which is 0), so those instant receipts are excluded from the recovery basis and from `defaultInstantWithdrawsFinalized`'s intended coverage [4](#0-3) .
- On claim, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — epoch N+1 — finds 0, and clears nothing [5](#0-4) . Execution then continues in `claimInstantWithdrawRequest`, which burns `instantWithdrawsRequests[_user]` and pays the full unhaircutted amount through `_transferFundedClaim` [6](#0-5) .
- `_transferFundedClaim`'s only solvency check is `balance - defaultRecoveryReserve >= _amount`, so the payout draws on underlyings held for other users' funded withdraw receipts — the recovery reserve itself stays nominally intact while the funded-claims pool is drained [7](#0-6) .

Broken invariant: loss socialization / "one receipt one payout". Receipts that escaped the recovery haircut are paid 1:1, so the aggregate claims exceed funded assets.

### Impact Explanation
An unprivileged lender (KYC-passing, instant withdrawals enabled) calls `requestWithdraw`→`requestInstantWithdraw` during a running epoch that subsequently ends in a borrower default finalized via `finalizeDefault`/`finalizeDefaultRecovery`. Their receipt is excluded from the haircut basis yet paid at par, directly stealing underlying reserved for other users' funded `withdrawsRequests`. Loss equals the attacker's instant-request amount (bounded by their tranche position), and later legitimate claimants face insolvency — direct theft plus permanent freezing of remaining funded claims, quantified as the full instant-request amount per attacking user.

### Likelihood Explanation
Requires: instant withdrawals enabled (`allowInstantWithdraw`), a running epoch that defaults at its `stopEpoch`, and the attacker holding tranche tokens to convert into an instant request before the stop. All attacker actions are unprivileged; the honest manager drives the stop and finalization. The trigger window is the running epoch, which is wide. Uncertainty: whether `epochNumber` is already bumped before instant receipts are booked in the same epoch in every variant (it is incremented in `deposit()` during the stop sequence, so requests booked *earlier in the same epoch* land on the pre-increment index), and whether the CDO gates `requestInstantWithdraw` once `defaulted` is set — the strategy itself does not check `defaulted`/`defaultRecoveryFinalized` in `requestInstantWithdraw` [8](#0-7) . The same epoch-key mismatch also means `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` decrements in `_claimDefaultedInstantWithdrawRequest` never match the epoch the basis was written under, compounding the accounting drift.

### Recommendation
Key instant-receipt recovery accounting to the epoch the receipt was written under, not the finalization epoch — e.g., snapshot `instantWithdrawClaimsByEpoch` for the *request* epoch at `stopEpoch`/`_handleBorrowerDefault` time before `epochNumber` increments, or track a `instantWithdrawEpoch` cursor analogous to `lastWithdrawRequest`. In `claimInstantWithdrawRequest`, iterate/clear all per-epoch instant receipt buckets (or store the request epoch alongside `instantWithdrawsRequests[_user]`) so no bucket falls outside the `defaultRecoveryEpoch` lookup. Add a Foundry regression test that requests an instant withdraw in epoch N, defaults at the N→N+1 stop, finalizes, and asserts the claim is haircutted.

### Proof of Concept
Foundry fork sketch (Pareto credit vault, instant withdrawals enabled):

```solidity
// 1. Epoch N running. Attacker (KYC'd) deposits, then:
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackerTrancheBal, address(AAtranche));
// => instantWithdrawsRequestsByEpoch[attacker][N] = amt; pendingInstantWithdraws = amt

// 2. Honest manager stops epoch; borrower repays nothing -> default path.
//    deposit()/stopEpoch bumps strategy.epochNumber() to N+1.
// 3. Manager/owner finalizeDefault + finalizeDefaultRecovery(recovered, source).
//    defaultRecoveryEpoch = N+1; defaultPendingClaimBasis() reads
//    instantWithdrawClaimsByEpoch[N+1] == 0 -> attacker receipt NOT in basis.

// 4. Attacker claims at par:
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// _claimDefaultedInstantWithdrawRequest reads epoch N+1 -> 0, skips;
// pays full `amt` via _transferFundedClaim from the funded-claims pool.
assertGt(underlying.balanceOf(attacker) - balPre, amt * defaultRecoveryPrice / 1e18,
         'receipt paid above recovery price');

// 5. A second user with a legitimate funded withdraw request now reverts
//    on _transferFundedClaim (balance - reserve < amount) or receives less:
vm.expectRevert(); // insolvency for the honest claimant
vm.prank(victim);
cdoEpoch.claimWithdrawRequest();
```

Caveat: I was unable to fully confirm within the iteration budget whether `IdleCDOEpochVariant.requestInstantWithdraw` reverts once `defaulted`/`epochEndDate == 0`, and the exact ordering of the `epochNumber` increment relative to when instant receipts are booked. The strategy-side code itself imposes no default check on `requestInstantWithdraw`, and the write-vs-clear epoch key asymmetry is present in the code regardless; the PoC should verify the epoch-index mismatch empirically.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
