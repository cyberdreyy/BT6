### Title
Permissionless growth of the on-chain Vault request allowlist causes unbounded, synchronous per-request linear scans on the Vault gateway hot path - ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
Every unprivileged Vault JSON-RPC request that authenticates via `req.Auth == ""` is authorized through `allowListBasedAuth.AuthorizeRequest`, which performs a full linear scan (`fetchAllowlistedItem`) over the *entire* in-memory `allowListedRequests` slice, retried up to 11 times (`allowListBasedAuthRetryCount = 10` retries plus initial attempt) with a 3s sleep between attempts. The in-memory slice is populated by `workflowRegistry.syncAllowlistedRequests`, which appends every still-unexpired entry read from the on-chain `WorkflowRegistry` contract's allowlist. Any address can permissionlessly call `AllowlistRequest`/`UserAllowlistRequest` on that contract with an attacker-chosen `expiryTimestamp` far in the future, at negligible cost (one L1/L2 tx per entry, no on-chain cap on total entries observed in this repo). This mirrors the reported bug class: an unbounded, permissionlessly-growable collection that is iterated over synchronously on a hot, unmetered execution path.

### Finding Description
1. `workflowRegistry.getAllowlistedRequests` paginates through the contract's full allowlist and `syncAllowlistedRequests` merges new entries into `w.allowListedRequests`, pruning only entries whose `ExpiryTimestamp` has passed: [1](#0-0) 

2. `GetAllowlistedRequests` copies the *entire* slice on every call, with no cap on returned size: [2](#0-1) 

3. `allowListBasedAuth.findAllowlistedItemWithRetry` calls `GetAllowlistedRequests` and then linearly scans it via `fetchAllowlistedItem`, for up to `retryCount+1` (11) attempts per single incoming request, each attempt doing a full `O(n)` scan plus a full slice copy: [3](#0-2) [4](#0-3) 

4. This authorization path is invoked synchronously on every incoming JSON-RPC secrets request the gateway receives from an unprivileged client (`create`, `update`, `delete`, `list`), before any further processing: [5](#0-4) [6](#0-5) 

5. Any account can permissionlessly add entries to the on-chain allowlist for a low, fixed gas cost, with an arbitrarily long expiry (repo test/tooling code confirms unrestricted-looking usage — no visible entry cap or scaling fee is enforced anywhere in this repo's syncer or auth code): [7](#0-6) [8](#0-7) 

There is no size cap, eviction policy, or gas/compute metering on `w.allowListedRequests` or on the number of scan attempts per request — this is the direct analog of the reported "linear iteration over an unboundedly, permissionlessly-growable collection in an unmetered hot path."

### Impact Explanation
As the allowlist grows (attacker can flood it with many long-expiry entries at low, predictable per-entry cost), every single incoming Vault request — from any client, not just the attacker — pays the cost of scanning the full, ever-growing list, multiplied by up to 11 retry attempts with 3-second sleeps between them if the request isn't immediately found. This degrades Vault gateway node latency/throughput node-wide, and because the scan is synchronous within `HandleJSONRPCUserMessage`, it can starve request-processing goroutines/resources on the gateway and Vault DON nodes, denying service to legitimate users. Unlike the reported cosmos chain-halt (which affects consensus-critical `BeginBlock`), this is a node/service-level DoS against the Vault gateway path rather than a chain halt, but the root cause pattern (permissionless unbounded growth + unmetered linear iteration on every hot-path operation) is identical.

### Likelihood Explanation
Likelihood is **Medium-High**: `AllowlistRequest` appears callable by any address that can pay gas, with no evidence in this repo of an on-chain cap on total entries or of a scaling fee tied to current allowlist size (unlike the cosmos fix's recommended `BaseGasFeeForNewPlan*len(existingNumPlans)` approach). The syncer keeps entries in memory until `ExpiryTimestamp` passes, so an attacker can set very long expirations to keep the list large indefinitely. Every Vault write/list request pays the resulting scan cost, so the degradation is felt continuously, not just once per block.

### Recommendation
- Replace the linear scan in `fetchAllowlistedItem` with a map/index keyed by digest, maintained by `workflowRegistry` (e.g., `map[[32]byte]WorkflowRegistryOwnerAllowlistedRequest`) so lookup is O(1) regardless of allowlist size.
- Enforce an on-chain and/or off-chain cap on the number of active (non-expired) allowlist entries per owner and/or globally, or a growing fee similar to the cosmos fix's scaling gas cost recommendation, to make flooding the allowlist economically infeasible.
- Consider bounding `allowListBasedAuthRetryCount`/`retryInterval` total wall-clock cost per request independent of allowlist size, and moving the retry/backoff off the synchronous request-handling path.

### Proof of Concept
Not independently reproducible from the indexed code alone (no visible on-chain contract source for `WorkflowRegistry.AllowlistRequest` in this repo, and gas-cost/cap enforcement, if any, may live in the Solidity contract, which is out of scope for this Go-repo index). Conceptually, based on code inspected:
1. Attacker repeatedly calls `AllowlistRequest`/`UserAllowlistRequest` with N distinct digests and expiry timestamps set far in the future (as exercised functionally in `system-tests/tests/smoke/cre/vault_don_test_helpers.go:1546-1563` and `deployment/cre/workflow_registry/v2/changeset/operations/contracts/user_workflow_registry_ops.go:360-387`, though those are legitimate-usage test helpers, not exploit code).
2. `workflowRegistry.syncAllowlistedRequests` (workflow_registry.go:764-804) ingests all N entries into `w.allowListedRequests` and keeps them until expiry.
3. Every subsequent Vault client request through `allowListBasedAuth.AuthorizeRequest` (allow_list_based_auth.go:34-111) must scan the full N-entry slice up to 11 times, increasing gateway/Vault-node request latency proportionally to N.

**Uncertain/unverified**: Whether the on-chain `WorkflowRegistry` Solidity contract enforces any per-owner or global cap on allowlist size, or charges a scaling fee for `AllowlistRequest` — the contract source is not present in this repo's index (only Go bindings/wrappers are visible), so this cannot be fully confirmed. If the contract does enforce such limits, the practical severity of this analog would be reduced; a Devin session with full repo/contract access would be needed to confirm.

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}
