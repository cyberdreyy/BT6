## Finding: Unsynchronized commission "cache" allows operator to redirect already-earned commission to a new beneficiary

### Title
Operator can redirect uncommitted commission rewards to a new beneficiary by calling `set_beneficiary_for_operator` before `synchronize_delegation_pool` - ([File: aptos-move/framework/aptos-framework/sources/delegation_pool.move])

### Summary
`delegation_pool::set_beneficiary_for_operator` (and the analogous `staking_contract::set_beneficiary_for_operator`) updates the operator's payout address without first forcing a synchronization of the pool's reward/commission "cache." Because commission accrued since the last sync is attributed entirely to *whoever is the beneficiary at the time the next sync runs* rather than to who was beneficiary while the rewards accrued, an operator can switch its beneficiary mid-cycle and capture commission rewards that economically belong to the old beneficiary.

### Finding Description
`synchronize_delegation_pool` computes commission owed to the operator based on the drift between the stake pool's actual `active`/`pending_inactive` balances and the delegation pool's internal shares-pool totals since the last synchronization: [1](#0-0) 

When this drift is realized, the entire uncommitted commission for that whole elapsed window is bought in as shares for `beneficiary_for_operator(stake::get_operator(pool_address))` — evaluated at the moment `synchronize_delegation_pool` executes, not at the moment the rewards were actually earned: [2](#0-1) 

`set_beneficiary_for_operator` changes the beneficiary immediately and does **not** call `synchronize_delegation_pool` first, even though its own doc comment states this precondition is required to protect the current beneficiary: [3](#0-2) 

Because synchronization is permissionless and can be triggered by any unrelated delegator action later (`add_stake`, `unlock`, `vote`, `reactivate_stake`, `withdraw`, etc. all call `synchronize_delegation_pool` first), whichever address is `beneficiary_for_operator(operator)` *at the time that later, arbitrary transaction happens to run* receives 100% of the commission accrued over the whole unsynced window, including the portion of time before the beneficiary switch. This is the exact "cache not synced before dependent operation" flaw from the external report: the code assumes callers will manually call the sync function before beneficiary changes, but nothing enforces it, and the "cache" (delta between real stake pool and internal shares pools) silently accumulates and is misattributed.

The same unenforced-sync pattern also exists in `staking_contract::set_beneficiary_for_operator`, whose comment likewise says "To ensures payment to the current beneficiary, one should first call `distribute`... " but the function does not call `distribute_internal`/`request_commission_internal` itself: [4](#0-3) 

### Impact Explanation
This breaks the commission/beneficiary accounting invariant: an operator, by unilaterally calling `set_beneficiary_for_operator` without a preceding sync, can cause commission rewards accrued while the *old* beneficiary held that role to be paid to the *new* beneficiary instead. This is a "beneficiary payout ... corruption that credits the wrong account," directly matching the required impact category. Since the operator fully controls when it swaps its own beneficiary, and delegation pool synchronization is triggered by ordinary unprivileged delegator/voter transactions, the old beneficiary (who may be a distinct commercial party contractually entitled to that commission) permanently loses the diverted rewards with no recourse — they are paid out as shares to the new beneficiary and become withdrawable by them.

### Likelihood Explanation
High likelihood: the vulnerable path requires only that the operator (who already legitimately controls `set_beneficiary_for_operator`) call it without first calling the permissionless `synchronize_delegation_pool`. No special timing race is needed beyond simply not calling sync — which is the default behavior since sync is not enforced by the entry function itself. Any operator wishing to shortchange its current beneficiary (e.g., before a payout dispute, or right before terminating a business relationship) can trivially do this.

### Recommendation
Make `synchronize_delegation_pool` (and `distribute_internal`/`request_commission_internal` in `staking_contract.move`) a mandatory precondition of `set_beneficiary_for_operator`, i.e. call it at the start of the function before reading/writing `BeneficiaryForOperator`, so all commission accrued up to that point is settled to the *current* beneficiary before the beneficiary address is changed — the same pattern already used in `set_operator`, `update_commission_percentage`, `vote`, `add_stake`, `unlock`, etc.

### Proof of Concept
1. Operator `O` has beneficiary `B_old` set via `set_beneficiary_for_operator`.
2. Time passes and validator rewards accrue; the delegation pool's internal shares totals (`active_shares`, `pending_inactive_shares_pool`) fall behind the real stake pool balances (nobody has called `synchronize_delegation_pool` in the interim) — this is the "unsynced cache."
3. `O` calls `set_beneficiary_for_operator(O, B_new)` — no sync occurs, so `BeneficiaryForOperator[O]` is switched immediately to `B_new` without settling the pending commission owed to `B_old`.
4. Any unprivileged delegator later calls e.g. `add_stake`/`unlock`/`vote` on the pool, which internally calls `synchronize_delegation_pool(pool_address)`.
5. `calculate_stake_pool_drift` computes the full commission for the entire unsynced window (including the period `B_old` was beneficiary) and `buy_in_active_shares`/`buy_in_pending_inactive_shares` credit it to `beneficiary_for_operator(O)`, which now resolves to `B_new`.
6. `B_new` can withdraw commission that accrued while `B_old` was the rightful beneficiary; `B_old` receives nothing for that period.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensure payment to the current beneficiary, one should first call `synchronize_delegation_pool`
    /// before switching the beneficiary. An operator can set one beneficiary for delegation pools, not a separate
    /// one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
