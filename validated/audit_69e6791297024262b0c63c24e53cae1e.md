### Title
Stale per-epoch withdraw receipts escape `stopEpoch` loss haircut and are paid at par - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug class is a cleanup routine that detaches a delayed mechanism (timer) while a still-queued worker re-arms it on freed state. The vault analog lives in the same shape: `collectWithdrawFunds` detaches the entire `pendingWithdraws` bucket and records a single `lossRecoveryPriceByEpoch[epochNumber]` haircut, but per-user per-epoch receipt entries (`withdrawsRequestsByEpoch`) that were queued in *earlier* epochs survive "detached" and are later re-armed by `_claimFundedWithdrawRequest`, which pays them at par. A lender who stacks withdraw requests across two or more epochs can therefore escape the pro-rata loss that was already applied to the aggregate, over-draw the funded reserve, and leave later claimants insolvent.

### Finding Description
`requestWithdraw` explicitly allows a user to open new withdraw requests without claiming previous ones (`NOTE: if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests`). Each request records `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and overwrites `lastWithdrawRequest[_user] = currentEpoch`, while the aggregate `pendingWithdraws` accumulates all epochs' receipts.

When a `stopEpoch` loss occurs, `collectWithdrawFunds` computes one recovery price over the *whole* pending basis and stores it under a single epoch key: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`, then zeroes `pendingWithdraws`. Crucially, all receipts in the bucket — including ones requested in epochs *before* `epochNumber` — were haircut in aggregate, but only the latest epoch's ledger entry is reachable afterwards.

On claim, `_claimLossAdjustedWithdrawRequest` resolves the loss epoch exclusively through `lastWithdrawRequest[_user]`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
...
(claimBasis, burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
```

`_clearWithdrawClaimForEpoch` clears only `withdrawsRequestsByEpoch[_user][lossEpoch]`, and `withdrawsRequests[_user] -= normalAmount` removes only that epoch's share. The user's older-epoch entries remain in `withdrawsRequests[_user]`. Control then falls into `_claimFundedWithdrawRequest`, where `lastWithdrawRequest` was reset to 0 and `epochNumber > 0` always holds after the epoch advanced, so the remaining stale receipts are paid out at full par via `_transferFundedClaim(_user, amount)` — even though the borrower only funded `lossRecoveryPrice` of them.

### Impact Explanation
Direct insolvency/theft with a quantified loss. Suppose a user has 100 underlying pending from epoch N and 100 from epoch N+1, and `collectWithdrawFunds` funds only 150 of the 200 `pendingWithdraws` (recovery price 0.75). The attacker claims 100 × 0.75 = 75 for the N+1 entry plus 100 × 1.0 = 100 at par for the stale epoch-N entry: 175 total against 150 funded. The strategy's underlying balance is overdrawn by the un-haircut portion of every older-epoch receipt; honest lenders' later `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient balance, permanently freezing the residual payouts of whoever claims last. This breaks the loss-waterfall invariant (pending receipts must share stop-epoch losses pro rata, per `previewLossAdjustedWithdrawFunds`).

### Likelihood Explanation
An attacker is only a KYC-passed lender requesting withdrawals — fully within the permitted threat model, no privileged role needed. Pre-conditions: a `stopEpochWithDuration`/under-funded `collectWithdrawFunds` loss must occur while the attacker holds receipts in more than one request epoch. The attacker cannot force the loss, but can cheaply pre-position by splitting a withdrawal into two requests across consecutive buffer/epoch boundaries in any fixed-APR or minted-interest pool, then wait for any realized loss event to extract the excess. The guard at lines 263–271 only blocks *new* requests once a loss is already recorded against `lastWithdrawRequest`; it does nothing for pre-stacked receipts because the loss epoch is applied to the aggregate, not per-epoch.

### Recommendation
Track the loss-adjusted basis per epoch rather than keying resolution solely on `lastWithdrawRequest`. Concretely: in `_claimLossAdjustedWithdrawRequest`, iterate or otherwise account for *all* epochs of `withdrawsRequestsByEpoch[_user]` whose receipts were inside the haircutted `pendingWithdraws` bucket when `collectWithdrawFunds` ran (e.g., record `lossRecoveryEndEpoch`/a per-epoch settled flag and apply `lossRecoveryPrice` to every request epoch ≤ the loss epoch), or snapshot a per-user `lossAdjustedClaimBasis` at funding time so older stale entries cannot fall through to the par-funded path.

### Proof of Concept
Foundry fork PoC sketch against `IdleCreditVault` / `IdleCDOEpochVariant`:

```solidity
// Setup: pool running, attacker (KYC'd lender) holds tranche tokens.
// Epoch N: attacker calls cdoEpoch.requestWithdraw(100e18, tranche)  -> receipt A
// Epoch N+1 (without claiming): requestWithdraw(100e18, tranche)     -> receipt B
//   lastWithdrawRequest[attacker] = N+1; pendingWithdraws = 200e18.
// stopEpoch end of N+1: borrower only repays enough that
//   cdoEpoch.stopEpoch(...) -> strategy.collectWithdrawFunds(150e18)
//   pendingWithdraws = 0; lossRecoveryPriceByEpoch[N+2-ish epoch] = 0.75e18.
// Attacker claims:
cdoEpoch.claimWithdrawRequest();
// _claimLossAdjustedWithdrawRequest pays 100e18 * 0.75 = 75e18 (epoch N+1 entry)
// _claimFundedWithdrawRequest then pays remaining withdrawsRequests = 100e18 AT PAR
// Total received = 175e18 from a 150e18 funded reserve.
// Subsequent honest claimer: _transferFundedClaim safeTransfer reverts (insufficient funds).
assertEq(received, 175e18);   // exceeds funded 150e18
```

Uncertainty note: index limits prevented confirming the exact `epochNumber` value used as the `lossRecoveryPriceByEpoch` key inside `stopEpoch`/`IdleCDOEpochVariant` (whether the loss is stored under the pre- or post-increment epoch); the PoC should assert which epoch key is written, but the stale-entry fall-through does not depend on it.
