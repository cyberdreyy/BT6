### Title
Global (non-owner-scoped) HTTP trigger `requestID` map lets any authorized workflow caller front-run and block another workflow's execution request - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The Gateway's HTTP trigger handler (`httpTriggerHandler.HandleUserTriggerRequest`) accepts a caller-supplied `id` for every `workflows.execute` request and uses that raw, unscoped `id` as the key into a single global in-memory map (`h.callbacks`). Any party that can submit a valid, authorized trigger request for **any** workflow can pick the same `id` string that a different workflow (or the same workflow, different caller) is about to use, and if that request wins the race the legitimate request will be rejected with a conflict error. This mirrors the reported `BatonLaunchpad.create` bug class: a deterministic/attacker-controllable "slot" (there: a `CREATE2` salt; here: a request ID key) that is not namespaced per caller, enabling front-running griefing.

### Finding Description
`HandleUserTriggerRequest` validates the request, authorizes it against the target workflow's key material, and then calls `setupCallback`, which stores the pending request keyed **solely by the client-chosen `requestID`**: [1](#0-0) 

`requestID` validation only rejects empty IDs or IDs containing `/`; there is no requirement that it be unique to the caller, workflow, or owner: [2](#0-1) 

Authorization (`authorizeRequest`) verifies that the caller holds valid signing/auth material for the **target workflow** referenced in the request body, but this check is independent of, and does not bind, the global `requestID` namespace to that workflow or owner: [3](#0-2) 

Because `h.callbacks` is a single package-level map (`map[string]savedCallback`) shared across all workflows and all callers, an authorized caller for *workflow A* can submit a request using the exact same `id` that a legitimate caller is about to use for *workflow B* (or a subsequent call to A). Whichever request reaches `setupCallback` first claims the slot; the second is rejected outright: [4](#0-3) 

The test suite explicitly documents this "in-flight" rejection behavior, confirming any second request with the same `id` is treated as a conflict regardless of which workflow it targets: [5](#0-4) 

This is structurally the same as the reported bug: a shared, attacker-influenceable "slot" identifier (salt / request ID) that is not namespaced to `msg.sender` (here: workflow owner) allows an unprivileged-but-authorized actor to pre-empt another party's operation and force it to fail.

### Impact Explanation
This is a temporary Denial of Service on workflow HTTP trigger executions: a legitimate caller's `workflows.execute` request is rejected with `jsonrpc.ErrConflict` ("requestID: %s has already been used") instead of being executed, even though the caller followed the API correctly. Since request execution (and any downstream fund movement / job run triggered by the workflow) never happens for the victim's request, this can delay or block time-sensitive workflow executions. Impact is Medium, consistent with the original report's rating, since it is a griefing/DoS rather than a fund-theft primitive.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to (a) hold valid authorization for at least one workflow on the gateway (any onboarded workflow owner qualifies — this is an unprivileged, non-operator actor from the gateway's perspective), and (b) guess or learn the victim's `requestID` before the victim's request is processed, then race it. If callers use predictable or low-entropy request IDs (e.g., sequential counters, timestamps) this is easy to execute; if callers use high-entropy UUIDs, the practical likelihood of a successful race is lower, similar to the original report's assessment that the attack is easy to execute but offers limited attacker incentive.

### Recommendation
Scope the `callbacks` map key by the authorized owner/workflow rather than by the raw client-supplied `requestID` alone, e.g. key on `workflowID + ":" + requestID` (or `authorizedOwner + separator + requestID`, as already done elsewhere in the codebase — see `vaulttypes.RequestIDSeparator` usage in `core/capabilities/vault/gateway_vault_request_processor.go`). This ensures a caller can only collide with, and only ever griefs, their own in-flight requests, not another workflow's/owner's requests.

### Proof of Concept
1. Attacker is an authorized caller for `workflowA` (owns valid signing key for it).
2. Attacker observes/predicts that `workflowB`'s caller is about to (or routinely does) submit a `workflows.execute` request with `id = "X"`.
3. Attacker submits a validly-authorized `workflows.execute` request for `workflowA` using `id = "X"` just before the victim's request for `workflowB` arrives.
4. `setupCallback` inserts the attacker's entry into `h.callbacks["X"]` first.
5. When the victim's `workflowB` request with `id = "X"` arrives, `setupCallback` finds `"X"` already present and returns `jsonrpc.ErrConflict`, per the existing test at `http_trigger_handler_test.go:317-355`, causing the legitimate execution to fail.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
