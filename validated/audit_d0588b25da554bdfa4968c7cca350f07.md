## Title
Stale confirmations from deleted multisig keys let a request execute below the configured confirmation threshold - (`multisig/src/lib.rs`)

### Summary
The multisig contract's `confirm` method counts confirmations recorded in a per-request `HashSet<PublicKey>` toward the `num_confirmations` threshold. When a key is removed via a `DeleteKey` action, the contract only purges requests and confirmations for which the deleted key was the *original submitter* (`signer_pk`); it never scans other pending requests to strip confirmations that the deleted key previously cast as a *confirmer*. A stale confirmation from a since-revoked key therefore continues to count, letting a request be executed with fewer live, currently-authorized confirmations than `num_confirmations` requires — the same root-cause pattern as the reported bug, where a stale/reused authorization token (the Algorand `flash_loan_end` index) is trusted without validating it still corresponds to a live, correctly-bound counterpart (the "member" set here, the "mutex reset" there).

### Finding Description
`MultiSigContract` stores confirmations keyed by request id, as a set of `PublicKey`: [1](#0-0) 

`confirm` adds the caller's signer key to that set and, once the set size plus the new confirmation reaches `num_confirmations`, removes the request and immediately executes it: [2](#0-1) 

Validation before counting a confirmation is performed by `assert_valid_request`, which only checks that the predecessor is the contract itself and that the request/confirmation entries exist — it never checks that every public key already present in the confirmation set is still a valid access key on the account: [3](#0-2) 

The only place stale confirmations are ever cleaned up is inside `execute_request`'s `DeleteKey` action handler, and it is scoped exclusively to requests *submitted by* the deleted key (`r.signer_pk == pk`), not to confirmations that the deleted key cast on requests submitted by someone else: [4](#0-3) 

Because of this, once a key confirms a pending request and is later removed from the account through a separate, legitimate `DeleteKey` request, its earlier confirmation on the still-pending request is never purged. The pending request's confirmation count therefore reflects one confirmation from a public key with no live authority on the account, and it takes one fewer *live* confirmation than `num_confirmations` was configured to require in order to trigger execution.

Binding broken: `confirmations counted == confirmations from currently authorized keys` should hold before any request executes; instead `confirmations counted ⊇ confirmations from (currently authorized ∪ previously-authorized-but-now-revoked)` keys, i.e., stale confirmations are counted as if they were live.

### Impact Explanation
This allows a multisig request (e.g., a `Transfer` of the account's NEAR balance, an `AddKey`/`DeleteKey`, or a `FunctionCall`) to execute with fewer genuinely live confirmations than the configured `num_confirmations` threshold. This directly matches the Critical impact category "a multisig request executed below threshold," since it lets a smaller set of currently-authorized keys move funds or otherwise control the account than the K-of-N policy is supposed to permit.

### Likelihood Explanation
The precondition is realistic and common in normal multisig operations: a member confirms one or more pending requests (e.g., legitimate proposals awaiting more confirmations) and is subsequently removed from the multisig (key rotation, offboarding, compromise response) via a `DeleteKey` request targeting a different, still-pending request's submitter. No special privilege beyond normal multisig membership is required, and the flaw is exercised purely through the documented `add_request`/`confirm`/`DeleteKey` workflow — no owner or foundation abuse is needed beyond normal key-management operations that any K-of-N multisig is expected to perform over its lifetime.

### Recommendation
When executing a `DeleteKey` action, iterate over all pending requests' confirmation sets (not just requests submitted by the deleted key) and remove the deleted public key from each. Alternatively, validate at `confirm`-time (and at execution threshold-check time) that every public key already recorded in a request's confirmation set is still present as a valid access key on the account, discarding stale entries before comparing the confirmation count against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 3` and members `A, B, C, D`.
2. `B` calls `add_request` to create request `R1` (e.g., `Transfer` of the full balance to an attacker-controlled account), then `B` calls `confirm(R1)` — `R1.confirmations = {B}` (1 of 3).
3. Separately, `C` and `D` create and confirm a `DeleteKey { public_key: B }` request (`R2`), reaching 2-of-3... assuming a 2 more confirmations needed, or adjust so `R2` reaches threshold and executes, removing `B`'s access key from the account. Per `execute_request`'s `DeleteKey` branch, only requests where `signer_pk == B` are purged; `R1` (submitted by `B` but already confirmed, still pending) is untouched because `R1` is still keyed by request id and its `signer_pk` field is `B` too — but even for requests submitted by other members that `B` merely confirmed, the confirmation is never purged. Use a variant where `B` only *confirms* (not submits) a request `R3` created by `A` to demonstrate the confirmer-only case: `R3.confirmations = {B}` persists after `B`'s key is deleted.
4. `A` and `C`, both still-live keys, confirm `R3`: `R3.confirmations = {B, A, C}` → size 3 meets `num_confirmations = 3`, and `execute_request(R3)` runs — even though `B` is no longer a valid access key on the account, so effectively only 2 live members (`A`, `C`) authorized the action against a nominal 3-of-N policy.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
