## Title
Post-switch operator commission bypasses `beneficiary_for_operator` redirection - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

## Summary
`distribute_internal` only redirects a payout to an operator's registered beneficiary when the payout's shareholder key equals the *current* `operator` parameter passed into the function. When a staker calls `switch_operator`, any commission that was already requested (and thus recorded as a pending distribution under the old operator's address) is never re-keyed to the new operator. When that pending distribution later becomes withdrawable and `distribute()` is called, the recipient check `if (recipient == operator)` fails for the old operator (since `operator` is now the new operator), so the funds are sent directly to the old operator's raw address instead of through `beneficiary_for_operator(old_operator)`.

## Finding Description
`switch_operator` forces a commission request for the outgoing operator before re-keying the `StakingContract` under the new operator address: [1](#0-0) 

`request_commission_internal` records this pending commission as a distribution-pool share keyed by the **old** operator address, and unlocks it from the stake pool (subject to the lockup period): [2](#0-1) 

The `StakingContract` (including its `distribution_pool`) is then moved to be keyed by `new_operator` in the `Store.staking_contracts` map, while `operator` field is also mutated in place: [3](#0-2) 

Later, once the lockup expires and `distribute()` (or any other path calling `distribute_internal`) is invoked, it is always called with the **current** operator (`new_operator`), not the historical one that actually earned the pending commission: [4](#0-3) 

Inside `distribute_internal`, the beneficiary redirection is keyed strictly off equality with the `operator` parameter: [5](#0-4) 

Since the pending distribution's shareholder key is `old_operator` and the `operator` parameter passed to `distribute_internal` is now `new_operator`, the equality check `recipient == operator` is false. The commission is paid directly to `old_operator`'s raw account address instead of being routed through `beneficiary_for_operator(old_operator)`, even though `BeneficiaryForOperator` is a persistent, operator-address-keyed resource (not tied to any specific staking contract) that is never cleared on `switch_operator`: [6](#0-5) [7](#0-6) 

## Impact Explanation
This breaks the operator-commission/beneficiary accounting invariant: commission earned by an operator should always be payable to whatever beneficiary that operator has designated, regardless of whether they are still the active operator on a given staking contract at the time the underlying stake unlocks. Because a staker-initiated `switch_operator` silently detaches already-earned (but still-locked) commission from the beneficiary redirection, an outgoing operator's designated beneficiary (which may be a cold wallet, multisig, or custody address set up specifically to protect commission payouts) never receives funds it is entitled to; the value is instead credited to a different account (the operator's raw address) than the one the operator configured to receive it. This matches the "credits the wrong account" class of impact for operator commission/beneficiary flows.

## Likelihood Explanation
The trigger requires only an ordinary `switch_operator` call by the staker (a normal, expected lifecycle action, not privileged escalation) followed by the routine lockup expiry and a `distribute()` call — both of which are permissionless/anyone-can-call. No attacker privilege beyond being staker of their own contract, or simply calling the open `distribute` entry function, is needed to trigger the misrouting once the preconditions (pending commission + operator switch) occur, which makes this reasonably likely to occur in normal validator/operator rotation scenarios.

## Recommendation
Snapshot the correct beneficiary (or the operator address the commission was earned under) at the time the distribution is recorded in `request_commission_internal`/`add_distribution`, rather than resolving `beneficiary_for_operator` using the staking contract's *current* operator field at distribution time. Alternatively, force a `distribute_internal` payout (flushing all pending shares to their then-current beneficiaries) before allowing `switch_operator` to re-key the contract, in addition to the existing `request_commission_internal` call, so no beneficiary-eligible distribution entries survive the operator-address rekeying.

## Proof of Concept
1. Staker creates a staking contract with `operator1`, contract accrues rewards.
2. `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary1)`.
3. Staker calls `request_commission` (or triggers it implicitly via `unlock_stake`) — this locks in `operator1`'s commission as a pending distribution keyed by `operator1`, unlocked from the stake pool (still within lockup, i.e., `pending_inactive`).
4. Before the lockup expires, staker calls `switch_operator(staker, operator1, operator2, new_commission)` — the `StakingContract` (with its `distribution_pool` still containing the `operator1`-keyed pending share) is now stored under `operator2`.
5. After lockup expiry, anyone calls `distribute(staker_address, operator2)`.
6. `distribute_internal` is invoked with `operator = operator2`; the `operator1`-keyed distribution's `recipient == operator` check fails, so funds go straight to `operator1`'s address instead of `beneficiary1`, confirmed via `assert_distribution`/balance checks (`beneficiary1` balance remains 0 while `operator1` balance increases by the bypassed commission amount).

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
