## Finding

The audited scenario is real and is a genuine vulnerability in `multisig/src/lib.rs`. The binding claimed to hold is:

**`confirmations.get(&request_id).len()` (at time of execution) == number of distinct *currently valid* multisig keys that approved `request_id`.**

This binding is broken because `DeleteKey` only cleans up requests *originated* by the removed key, not confirmations that key added to *other* pending requests.

### Trace

- `confirm()` at [1](#0-0)  triggers execution purely based on `confirmations.len() as u32 + 1 >= self.num_confirmations` — it never checks whether each stored `PublicKey` in the confirmations `HashSet` still exists as a live access key on the account.
- `DeleteKey` execution at [2](#0-1)  only purges requests where `r.signer_pk == pk` (i.e., requests *created* by the removed key). It does **not** scan `self.confirmations` for other pending requests where that key merely added a confirmation (via `confirm()`, not `add_request`) — those stale `PublicKey` entries are left intact in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map.
- There is no on-chain mechanism for the contract to query the account's currently valid access keys to re-validate stored confirmations — this limitation is even called out in the multisig README's "Gotchas" section (documented for the *under*-counting/lockout case, but the same lack of validation also enables *over*-counting via stale confirmations).

### Exploit flow

1. Member A creates request `R` (e.g., `Transfer`) requiring `num_confirmations = 3`.
2. Member B confirms `R` via `confirm()` → `confirmations(R) = {A, B}` (2 entries, below threshold, so `R` is *not yet executed*, per [3](#0-2) ).
3. Separately, a request to `DeleteKey { public_key: B }` is confirmed to threshold and executed, which calls `promise.delete_key(B)` and only removes requests where `signer_pk == B` — `R`'s confirmations set is untouched since B was not `R`'s creator.
4. Member C later calls `confirm(R)`. `confirmations(R).len() (2) + 1 = 3 >= num_confirmations (3)` → `R` executes, transferring funds, even though B is no longer a live member and only A and C are currently valid approvers.

This directly matches the impact category explicitly listed as Critical: "a multisig request executed below `num_confirmations` live members."

### Note on the "unprivileged attacker calling confirm() after removal" framing

The literal claim that a removed key can itself call `confirm(request_id)` after removal is false — once `promise.delete_key` executes on-chain, that key can no longer sign transactions against the account, so NEAR's runtime will reject any subsequent call signed with it (`assert_valid_request`'s `predecessor_account_id == current_account_id` check is also unreachable without a valid access key signature). The actual exploitable bug is not that the removed member calls `confirm()` again, but that their **stale, previously-recorded confirmation persists** in `self.confirmations` and is silently counted when a *different, still-valid* member's subsequent `confirm()` call crosses the threshold.

## Answer

### Title
Stale confirmations from removed keys count toward `num_confirmations` threshold, allowing execution below live-member threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig/src/lib.rs` decides execution solely from the size of the stored `confirmations` `HashSet`, without re-validating that each entry corresponds to a currently valid access key. `DeleteKey` execution only removes requests *created* by the deleted key, not confirmations that key added to other pending requests, so a removed member's earlier confirmation remains counted toward execution of any request it had previously approved but not created.

### Finding Description
The invariant `confirmations_count(request_id) == number of distinct live members who approved request_id` is broken. Root cause: `execute_request`'s `DeleteKey { public_key }` branch at [2](#0-1)  only filters `self.requests` by `r.signer_pk == pk` (the request's *creator*) and removes only those requests/confirmations; it never scans `self.confirmations` for entries where `pk` participated as a *confirmer* on other still-pending requests. Then `confirm()` at [1](#0-0)  triggers `execute_request` purely from `confirmations.len() as u32 + 1 >= self.num_confirmations`, with no check that the stored public keys are still valid access keys on the account (the contract has no way to query live access keys on-chain). Exploit flow: member B confirms request R (created by A) but R stays below threshold; a separate `DeleteKey{B}` request executes, removing B's key but leaving B's stale confirmation entry in `confirmations(R)`; a third live member C then confirms R, and B's stale entry is counted, causing R to execute with only 2 live approvers instead of the required 3.

### Impact Explanation
Funds held by the multisig (e.g., via a `Transfer` action bundled in the request) can leave the account with fewer live approvals than `num_confirmations` mandates, directly matching the Critical category "a multisig request executed below `num_confirmations` live members." This is a systemic flaw in the confirmation bookkeeping, not a one-off griefing case, and is repeatable for any pending multi-step request whenever a confirmer is later removed before the request finalizes.

### Likelihood Explanation
Requires `num_confirmations >= 3` (so a request can sit partially confirmed without auto-executing) and a member-removal (`DeleteKey`) request to be processed for a key that previously confirmed — but did not create — a still-pending request. No attacker-controlled deposit or special privilege is needed beyond ordinary multisig operation; this is a plausible operational sequence (e.g., revoking a compromised/departing signer's key while other requests are in flight) that any multisig operator could unintentionally trigger.

### Recommendation
When executing `DeleteKey`, also purge the removed public key from every entry in `self.confirmations` (not just requests it originated), or re-validate on `confirm()`/execution that all stored confirming keys still exist as valid keys before counting them toward `num_confirmations`.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
