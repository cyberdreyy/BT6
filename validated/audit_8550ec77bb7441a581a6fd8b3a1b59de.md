### Title
Post-default instant-withdraw requests are booked under the stale `defaultRecoveryEpoch` and immediately claimable against the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug resets stale MMIO pointers so nothing can write through a mapping that outlives its device. The analog here is a stale epoch pointer: after a borrower default, `epochNumber` is not bumped, yet `requestInstantWithdraw` keeps stamping new receipts under `epochNumber` — which is exactly `defaultRecoveryEpoch`. `claimInstantWithdrawRequest` then treats that fresh, post-default receipt as part of the defaulted-epoch claim set and pays it from the finalized recovery reserve while destructively mutating the epoch's aggregate accounting.

### Finding Description
- `requestInstantWithdraw` (`contracts/strategies/idle/IdleCreditVault.sol:356-375`) only calls `_ensureDefaultRecoveryInitialized()` and has no `defaultRecoveryFinalized` branch. It executes `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` and `instantWithdrawClaimsByEpoch[epochNumber] += _amount`. On default, `epochNumber` is never incremented (the prefunded-queue code explicitly relies on this: `_prefundedEpochToProcess` adds `+1` only "on borrower default", `contracts/IdleCDOEpochQueue.sol:288-291`), so `epochNumber == defaultRecoveryEpoch`.
- `claimInstantWithdrawRequest` (`:380-393`) first calls `_claimDefaultedInstantWithdrawRequest(_user)` when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`.
- `_claimDefaultedInstantWithdrawRequest` (`:842-856`) reads `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — which now includes the attacker's brand-new receipt — burns only `claimBasis` receipt tokens, pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` out of `_transferDefaultRecovery`, and does `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` and `pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis`.
- Contrast with the normal path: `requestWithdraw` (`:243-258`) explicitly detects `defaultRecoveryFinalized`, requires the user to have zero outstanding receipts, and routes the request into `postDefaultRequests` so it never pollutes the defaulted-epoch ledgers. The instant path lacks the equivalent isolation.

Consequences once a fresh receipt is mixed into `defaultRecoveryEpoch`:
1. The attacker immediately receives a recovery-priced payout on a post-default request that should either be rejected or routed to a post-default bucket funded by new borrower repayments — the recovery reserve was sized only for pre-default receipts.
2. `pendingInstantWithdraws` is force-zeroed if `claimBasis >= pending`, erasing other users' unfunded instant-withdraw basis.
3. `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` underflows once `claimBasis` exceeds what was actually recorded for that epoch at finalization, permanently reverting `claimInstantWithdrawRequest` for every honest defaulted-epoch claimant (freeze of unclaimed recovery).

### Impact Explanation
An unprivileged lender (KYC-passing user able to call `requestInstantWithdraw` via the CDO) can, after default finalization, either (a) steal recovery funds by getting an instant haircut payout that was never part of the finalized claim set, or (b) permanently brick `claimInstantWithdrawRequest` via the `instantWithdrawClaimsByEpoch[defaultEpoch]` underflow, freezing all other users' defaulted instant-withdraw recovery. Loss is bounded by `defaultRecoveryPrice`-priced payout on the attacker's request plus the full unclaimed instant recovery of honest users.

### Likelihood Explanation
Requires the pool to reach the finalized-default state and the CDO to still forward `requestInstantWithdraw`/`claimInstantWithdrawRequest` calls for users post-finalization — the strategy itself places no post-default guard on this path, and the parallel normal-withdraw path shows the authors intended post-default requests to exist (via `postDefaultRequests`). Any user can trigger it with a minimal instant request; no privileged action needed. One caveat I could not fully verify within scope: whether `IdleCDOEpochVariant`/`IdleCDOCreditVault` externally gates instant-withdraw requests once `defaulted()`/`defaultRecoveryFinalized` is set; if the CDO blocks them entirely, the vector collapses to the freeze scenario via reentrancy of accounting only.

### Recommendation
Mirror the `requestWithdraw` post-default logic in `requestInstantWithdraw`: after `defaultRecoveryFinalized`, either revert or record the request in a dedicated post-default instant bucket keyed by a fresh epoch id, never under `defaultRecoveryEpoch`. Additionally, make `_claimDefaultedInstantWithdrawRequest` subtract `min(claimBasis, instantWithdrawClaimsByEpoch[defaultEpoch])` or explicitly cap the claimable basis to what was snapshotted at finalization, so post-default writes cannot mutate the defaulted epoch's aggregate.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
// Assumes existing harness helpers from test/foundry/IdleCreditVault.t.sol:
// idleCDO, cdoEpoch, strategy (IdleCreditVault), AAtranche, underlying,
// _depositWithUser, _startEpochAndCheckPrices, _stopEpochAndCheckPrices,
// borrower default via stopEpoch(initialProvidedApr, 0) + finalizeDefault flow.

contract InstantWithdrawStaleEpochTest is Test {
    // See test/foundry/IdleCreditVault.t.sol for fixture contracts.

    function testPostDefaultInstantRequestPollutesDefaultEpoch() external {
        IdleCreditVault vault = IdleCreditVault(address(strategy));
        uint256 amount = 10_000 * 1e6;

        // Honest user and attacker deposit AA.
        address honest = makeAddr("honest");
        address attacker = makeAddr("attacker");
        _depositWithUser(honest, amount, true);
        _depositWithUser(attacker, amount, true);

        // Honest user requests an instant withdraw during the epoch.
        vm.prank(honest);
        cdoEpoch.requestInstantWithdraw(/* tranche amount */, address(AAtranche));

        // Epoch ends with borrower default; default recovery is finalized.
        _startEpochAndCheckPrices(0);
        _stopEpochAndCheckPrices(0, initialProvidedApr, 0);
        // finalizeDefault / finalizeDefaultRecovery via manager (honest actor)
        // => defaultRecoveryFinalized = true, defaultInstantWithdrawsFinalized = true,
        //    defaultRecoveryEpoch == vault.epochNumber() (epochNumber not bumped).

        uint256 defaultEpoch = vault.defaultRecoveryEpoch();
        assertEq(vault.epochNumber(), defaultEpoch, "epochNumber stale after default");

        // Attacker files a NEW instant withdraw after finalization.
        vm.prank(attacker);
        cdoEpoch.requestInstantWithdraw(/* tranche amount */, address(AAtranche));

        // The fresh receipt lands in the defaulted epoch's ledger.
        assertGt(
            vault.instantWithdrawsRequestsByEpoch(attacker, defaultEpoch),
            0,
            "post-default receipt recorded under stale defaultRecoveryEpoch"
        );

        // Attacker claims instantly against the recovery reserve.
        uint256 balPre = underlying.balanceOf(attacker);
        vm.prank(attacker);
        cdoEpoch.claimInstantWithdrawRequest();
        assertGt(underlying.balanceOf(attacker), balPre, "attacker paid from default reserve");

        // Honest user's defaulted-epoch claim now reverts (underflow on
        // instantWithdrawClaimsByEpoch[defaultEpoch]) or pays less than entitled.
        vm.prank(honest);
        vm.expectRevert(); // underflow / NotAllowed depending on ordering
        cdoEpoch.claimInstantWithdrawRequest();
    }
}
```

Note: the PoC assumes the CDO epoch variant still routes `requestInstantWithdraw`/`claimInstantWithdrawRequest` after default finalization; if a higher-level guard exists in `IdleCDOEpochVariant`, the impact reduces to the accounting corruption of `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` whenever the strategy function is invoked — that guard could not be confirmed within this analysis.
