Based on my investigation, I found a concrete analog on the coordinator side (`stackerdb_listener.rs`), where a single miner-controlled loop (with gossip from at least one signer that changes its mind) causes a signer's rejection to be recounted as an acceptance without the rejection being retracted, letting a minority weight count on both sides of the equality that gates block acceptance/rejection.

### Title
Signer weight double-counted on both `total_weight_approved` and `total_weight_rejected` when a signer flips its vote for the same block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` independently, gated by two separate maps (`gathered_signatures` and, implicitly, the rejection path), rather than by a single "how did signer X vote on this block" ledger. A signer that first rejects, then (after `should_reevaluate_reject_reason`/`should_reevaluate_block` allow reconsideration) later accepts the same block, has its weight added to `total_weight_rejected` once and to `total_weight_approved` once — its weight is now standing on both sides of the ≥weight_threshold / >30%-blocking-minority equalities simultaneously.

### Finding Description
`handle_signer_message`'s `BlockResponse::Accepted` branch only guards against re-adding weight for a signer that has already accepted the very same block: [1](#0-0) 
It never checks whether that signer previously registered a *rejection* for this same `block_sighash`. Conversely, the rejection branch adds weight keyed only by `responded_signers.insert(slot_id)`: [2](#0-1) 
and does not remove that entry's contribution to `total_weight_rejected` if the signer subsequently accepts. Both counters are accumulated independently in the same `BlockStatus`/`RwLock` object, and are read together by the coordinator loop: [3](#0-2) 
This is the node-side counterpart to the same class of bug the signer's own DB layer already defends against — the signer library explicitly enforces that a rejection is cleared when a signature is later recorded for the same signer/block, and vice versa (see the `reject_then_accept`/`accept_then_reject` tests and the CHANGELOG entry "Do not count both a block acceptance and a block rejection for the same signer/block"): [4](#0-3) [5](#0-4) 
That fix was applied to the signer's local ledger (`add_block_signature`/`add_block_rejection_signer_addr`), but the equivalent guard is missing on the node-side `StackerDBListener`, which is the component that actually decides whether the coordinator broadcasts the block (`Ok`) or fails it (`SignersRejected`). A signer legitimately flipping its verdict is a normal, single-slot-triggered path: the signer's own state machine explicitly allows re-evaluating a prior rejection for certain reject reasons (`should_reevaluate_reject_reason`, `should_reevaluate_block`) and re-broadcasting an acceptance for the same `signer_signature_hash`.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that the coordinator relies on: a single signer's weight can simultaneously satisfy part of the acceptance threshold (`total_weight_approved >= weight_threshold`) and part of the rejection-trip condition (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`). In the boundary case, this can let the coordinator declare the block accepted (or unnecessarily reject it) using inflated tallies that do not correspond to the true number of distinct signers currently in a given state, effectively double-counting one signer's weight toward two mutually exclusive outcomes. This is a state-machine-wedge/liveness and integrity concern in the block acceptance accounting, meeting the "aggregated-weight vs verified-accepts" equality-break class described in the rules.

### Likelihood Explanation
It requires only the miner-run coordinator loop plus a single signer (potentially the attacker's own signer, or gossip content it forwards) sending a reject-then-accept (or vice versa) sequence for the same `signer_signature_hash` — a sequence the honest signer logic itself supports via reconsideration of certain reject reasons. No majority or other signer's key is needed; the flip can be triggered by one signer's own legitimate re-evaluation flow, and the node-side listener simply never reconciles it.

### Recommendation
In `StackerDBListener`, maintain a single per-slot "current vote" record (accept/reject) per `block_sighash`, and when a slot's vote transitions from reject→accept or accept→reject, subtract the previously counted weight before adding to the new bucket — mirroring the guard already implemented in `stacks-signer/src/signerdb.rs`'s `add_block_signature`/`add_block_rejection_signer_addr` pair.

### Proof of Concept
1. Coordinator is waiting on block `B` with `weight_threshold` set such that one signer's weight is decisive.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected(B)`. `total_weight_rejected += w`, `responded_signers.insert(slot_S)`.
3. Due to a reconsideration path in the signer state machine (`should_reevaluate_reject_reason`/re-proposal), `S` later sends `BlockResponse::Accepted(B)` for the same `signer_signature_hash`.
4. In the accept handler, `block.gathered_signatures.contains_key(&slot_S)` is `false` (never inserted before), so `total_weight_approved += w` is applied unconditionally.
5. Now both `total_weight_approved` and `total_weight_rejected` include `w`, even though only one signer voted, and once for each verdict — inflating both tallies used by `signer_coordinator.rs`'s threshold checks.
