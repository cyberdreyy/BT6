## Finding [1](#0-0) 

### Title
`distribute()` griefing: a single non-cooperative recipient can permanently block payout of all other shareholders' unlocked stake and commission - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
The JPEG'd report shows a generic `withdraw()` step that is assumed to always succeed being blocked because one specific asset (JPEG) was blacklisted by the strategy, reverting the whole migration and freezing funds. The Aptos analog is `staking_contract::distribute_internal`, which iterates over every shareholder of a `distribution_pool` (the staker's unlocked stake and the operator's/beneficiary's unpaid commission) in a single atomic loop and calls `aptos_account::deposit_coins` for each of them unconditionally. [2](#0-1) 

`aptos_account::deposit_coins` is not guaranteed to succeed for every address: Aptos accounts can opt out of un-registered/arbitrary coin deposits via the `DirectTransferConfig` resource, and an unregistered CoinStore recipient with `allow_arbitrary_coin_transfers = false` will cause the deposit to abort. [3](#0-2) 

Because the shareholder loop shares one atomic Move transaction and redeems `pool_u64` shares before depositing, an abort on **any single shareholder's payout** (e.g., a former operator who was replaced via `switch_operator` and still owns unclaimed commission shares in the same `distribution_pool`) reverts the entire `distribute()` call - including the staker's own already-unlocked, otherwise-withdrawable stake.

### Finding Description
- `switch_operator` removes the old operator from `staking_contracts` but keeps their unpaid commission inside the same `distribution_pool` object that is re-keyed under the new operator, via `distribute_internal` + `request_commission_internal` being invoked first. [4](#0-3) 
- `unlock_stake` (staker-triggered) and `request_commission` (operator-triggered) both add shares to the same shared `distribution_pool`, so the staker's principal withdrawal and the operator's/beneficiary's commission live in one accounting object.
- `distribute()` -> `distribute_internal()` withdraws the total potentially-withdrawable stake once, then loops `while (distribution_pool.shareholders_count() > 0)`, redeeming shares and calling `aptos_account::deposit_coins(recipient, ...)` for each shareholder in turn, including operator/beneficiary and staker. [5](#0-4) 
- An unprivileged operator (current or a former operator still owed unpaid commission) can, entirely on their own account and without any special privilege, disable arbitrary coin transfers before ever registering a `CoinStore<AptosCoin>` (`aptos_account::DirectTransferConfig.allow_arbitrary_coin_transfers = false`). Any subsequent `deposit_coins` call targeting that unregistered address then aborts.
- Because the redeem-then-deposit loop is a single atomic function, the abort rolls back the whole `distribute()` transaction — not just the problematic recipient's share. The staker's already-unlocked stake, and any other shareholder's payout sharing that pool, become non-recoverable through `distribute()` as long as the hostile shareholder keeps the deposit-blocking configuration in place.

### Impact Explanation
This breaks the "stake and lockup" invariant that unlock/withdraw paths must not permanently strand value belonging to a different, uninvolved party. A staker who already unlocked and waited out the lockup period can be denied withdrawal of their own funds indefinitely because of a third party's (operator's/beneficiary's) account configuration — a griefing/DoS vector that traps stake, satisfying "permanent lock or non-recoverable loss of claim rights" and "commission ... payout ... corruption that ... traps value" from the required impact list. The same shared-pool/loop pattern is reused by `vesting.move`'s withdrawal path (`withdraw_stake` calls `staking_contract::distribute`), so vesting beneficiaries could be similarly affected if a shareholder disables direct transfers. [6](#0-5) 

### Likelihood Explanation
Setting `allow_arbitrary_coin_transfers = false` on one's own address before ever holding a `CoinStore<AptosCoin>` requires no special privilege — it is a standard account setting callable by any signer. A malicious or simply careless operator/former-operator (who is otherwise an untrusted, unprivileged counterparty from the staker's perspective) can trigger this at will, or it can happen unintentionally, making the likelihood non-negligible for any staking_contract pool that has had an operator switch or an unregistered beneficiary.

### Recommendation
Do not let a single recipient's payout failure abort payouts for other shareholders in the same `distribution_pool`. Options:
1. Wrap each `aptos_account::deposit_coins` call in the loop with a fallback (e.g., detect via `coin::is_account_registered` / `can_receive_direct_coin_transfers` up front and skip/queue that shareholder's payment instead of aborting the whole call), continuing to distribute to all other, cooperative recipients.
2. Alternatively, force-register the stake pool's known recipients (staker, operator, beneficiary) for `AptosCoin` at contract-creation/beneficiary-set time (mirroring the explicit `assert_account_is_registered_for_apt` guard already used in `vesting::set_beneficiary`) so that `deposit_coins` cannot hit the un-registered/opted-out abort path later. [7](#0-6) 

### Proof of Concept
1. Staker creates a staking contract with `operator_1`, stake earns rewards, `staker` calls `unlock_stake`, adding staker's shares to `distribution_pool`.
2. Staker calls `switch_operator(staker, operator_1, operator_2, ...)`, which calls `distribute_internal` + `request_commission_internal` for `operator_1`, leaving `operator_1`'s unpaid commission as shares in the same `distribution_pool` that is now indexed under `operator_2` (per test `test_staker_can_switch_operator`). [8](#0-7) 
3. Before the lockup ends, `operator_1` calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account (never having registered a `CoinStore<AptosCoin>`).
4. Once the lockup expires and someone calls `staking_contract::distribute(staker, operator_2)`, the loop in `distribute_internal` reaches `operator_1`'s redeemed shares and calls `aptos_account::deposit_coins(operator_1, ...)`, which aborts.
5. The entire `distribute()` transaction reverts, so the staker's own already-unlocked stake (also queued in the same pool) is not paid out, and stays permanently stuck until `operator_1` chooses to re-enable direct transfers — something the staker cannot control.

### Caveat
Due to index size limits I could not retrieve the full body of `aptos_account::deposit_coins` (only the `DirectTransferConfig` struct and the analogous `transfer` helper were available), so the exact abort condition/error code is inferred from the documented purpose of `DirectTransferConfig.allow_arbitrary_coin_transfers` rather than the literal function body. If a Devin session is needed to confirm the exact abort semantics of `deposit_coins`, it should read `aptos-move/framework/aptos-framework/sources/aptos_account.move` in full.
