## No vulnerability found for this question.

The premise of the question — that `check_latest_block_in_tenure` passes a sibling-fork proposal purely on `chain_length` without any actual parent/canonicity check — does not survive tracing the full validation path.

The node-side validation, which runs before any signer chainstate check even matters, enforces the real parent equality. `postblock_proposal.rs`'s `validate()` looks up `parent_stacks_header` by `self.block.header.parent_block_id` directly out of chainstate and rejects with `UnknownParent` if it's not found, then calls `Self::check_block_has_valid_parent(chainstate, sortdb, &self.block)` to verify "this block's parent is the highest such block we can build off of." [1](#0-0) 
This means a proposal `C` whose `parent_block_id` is not the actual tip `B` (the sibling-fork scenario) is rejected by the node's own chainstate rules — the check the question calls "out of scope" as "the flaw itself," but which is precisely the mechanism that makes the height-only comparison in the signer safe. The doc comment on `check_latest_block_in_tenure` explicitly states this reliance: "If we can't look up `tenure_id`, assume `block` is higher... we are relying on the `stacks-node` proposal endpoint to do the validation on the chainstate data that it has." [2](#0-1) 

Separately, on the signer side, `SortitionsView::check_proposal` and `check_block_against_signer_db_state` don't rely solely on `check_latest_block_in_tenure`'s height comparison either. For tenure-change blocks, `validate_tenure_change_payload` cross-checks `tenure_change.prev_tenure_consensus_hash` against the actual sortition-derived parent tenure id, rejecting with `InvalidParentBlock` on mismatch: [3](#0-2) 
And there is an existing integration test (`nakamoto_integrations.rs`) that constructs exactly the sibling scenario described — a block header with the same `chain_length` as a previously-signed tenure block but a different content, and confirms `check_proposal` errors with "A sibling of a previously approved block must be rejected": [4](#0-3) 

Additionally, `check_latest_block_in_tenure` itself doesn't stop at the height comparison against `get_tenure_last_block_info` — after that early-rejection branch, it also fetches the node's canonical `tenure_tip` via `client.get_tenure_tip(tenure_id)` and only returns `Ok(true)` if `tip.height() < block.header.chain_length`, tying the pass/fail back to the node's actual canonical chain state, not just the local signer DB's cached height. [5](#0-4) 

The chain_length check in `check_latest_block_in_tenure` is explicitly documented as a fast early-rejection heuristic (comment: "we are relying on the stacks-node proposal endpoint to do the validation on the chainstate data that it has"), not the sole safety guard. The actual parent/canonicity equality is enforced by the node's `check_block_has_valid_parent` and `UnknownParent` checks in `postblock_proposal.rs`, which run in the validate-ok path that gates pre-commit and signing (per `docs/signer-flows.md` section 4: `RECHECK` only happens after the node has already returned `Ok`). A sibling fork whose `parent_block_id` doesn't equal `B.block_id()` never reaches the signing stage because the node rejects it as `UnknownParent`/invalid-parent before `check_block_against_signer_db_state`'s height-only recheck is even reached with a validated block.
