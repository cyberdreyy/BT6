### Title
Post-default instant withdraw requests are recorded under `defaultRecoveryEpoch` and drained the recovery reserve at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestInstantWithdraw` keeps crediting `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` even after `defaultRecoveryFinalized` is set. Because `epochNumber` no longer advances once the vault is defaulted (no further `stopEpoch`/`deposit` bump), every post-default instant request lands in `defaultRecoveryEpoch`. `claimInstantWithdrawRequest` then treats that fresh, un-haircut receipt as a defaulted-epoch claim and pays `defaultRecoveryPrice` out of `defaultRecoveryReserve`, even though this basis was never included in `totalBasis` when `finalizeDefaultRecovery` set the recovery price.

### Finding Description
At finalization, `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` and stores `defaultRecoveryEpoch = epochNumber` [1](#0-0) . After default, `epochNumber` stays frozen at that value. `requestInstantWithdraw` has no `defaultRecoveryFinalized` branch (unlike `requestWithdraw`, which routes post-default flow through `postDefaultRequests`): it burns CDO strategy tokens 1:1 at par, mints a full receipt to the user, and indexes it at `currentEpoch = epochNumber` [2](#0-1) . In `claimInstantWithdrawRequest`, when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, `_claimDefaultedInstantWithdrawRequest` clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the exact slot the new request was written to — decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` (which the new request re-incremented), and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from the isolated `defaultRecoveryReserve` [3](#0-2) [4](#0-3) . This is the analog of the unchecked enum/index in `rec_type_check_enum`: the claim path performs no per-epoch-type validation distinguishing "receipt created before finalization" from "receipt created after finalization," so post-default basis is accepted into the default-epoch bucket.

### Impact Explanation
Each post-default instant request of size X consumes `X * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve`, a reserve whose size was fixed against the finalized `totalBasis` and never accounted for new claims. Attackers can repeat the request/claim cycle and extract recovery underlying in excess of their fair haircut share, directly stealing the reserve owed to legitimate defaulted-epoch claimants (theft of unclaimed recovery / insolvency of the reserve). If `defaultRecoveryPrice` is high (partial recovery), the drain approaches 1:1 of the request size.

### Likelihood Explanation
Requires a finalized borrower default with `defaultInstantWithdrawsFinalized == true` (i.e., `pendingInstantWithdraws != 0` at finalization — a common state when the instant queue was only partially funded at epoch start) and the CDO still exposing an instant-withdraw request path post-default to ordinary tranche holders / KYC'd lenders. The attacker needs only an unprivileged position able to call the CDO's instant-withdraw entry point; no privileged role is involved. One caveat: whether `IdleCDOEpochVariant` keeps the `requestInstantWithdraw` route open after `defaulted()` could not be fully verified in the CDO code; if the CDO blocks instant requests post-default, the vector is unreachable and this collapses to a defense-in-depth gap.

### Recommendation
In `requestInstantWithdraw`, revert (or route through a post-default path analogous to `postDefaultRequests`) when `defaultRecoveryFinalized` is true, and/or key instant receipts to a per-request epoch marker that cannot equal `defaultRecoveryEpoch` (e.g., record `epochNumber + 1` for post-default requests). Alternatively, have `claimInstantWithdrawRequest` skip the defaulted-epoch clearing for receipts whose request timestamp/nonce postdates `defaultRecoveryEpoch` finalization.

### Proof of Concept
Foundry fork test outline:

```solidity
// assume: epoch N defaulted, finalizeDefaultRecovery ran with
// defaultRecoveryReserve = R, defaultRecoveryPrice = p, defaultRecoveryEpoch = N
// and pendingInstantWithdraws != 0 at finalization (defaultInstantWithdrawsFinalized == true)

// attacker (tranche holder / KYC'd lender) calls CDO instant withdraw path:
cdo.requestInstantWithdraw(x, attacker);           // -> strategy.requestInstantWithdraw(x, attacker)
// strategy now holds: instantWithdrawsRequestsByEpoch[attacker][N] = x
//                     instantWithdrawClaimsByEpoch[N] += x
//                     attacker receipt balance += x (minted 1:1, no haircut)

// attacker claims via CDO:
cdo.claimInstantWithdrawRequest(attacker);
// -> _claimDefaultedInstantWithdrawRequest clears slot [attacker][N]
// -> _transferDefaultRecovery(attacker, x * p / 1e18)
// assert: attacker received underlying, defaultRecoveryReserve decreased,
//         and no corresponding basis existed in totalBasis at finalization.

// repeat until defaultRecoveryReserve is exhausted; legitimate
// defaulted-epoch claimants then revert on _transferDefaultRecovery
// (defaultRecoveryReserve underflow) or receive nothing.
```

The PoC should assert `attacker`'s net payout exceeds the fair `defaultRecoveryPrice` share implied by their pre-default exposure, demonstrating reserve theft on a mainnet fork of the deployed vault/CDO pair.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
