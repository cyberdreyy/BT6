### Title
Unbounded per-request scan of the global Vault allowlist causes DON-wide CPU/time amplification DOS - (File: core/capabilities/vault/allow_list_based_auth.go)

### Summary
`allowListBasedAuth.findAllowlistedItemWithRetry` performs an O(n) linear scan (plus O(n) string-formatting) over the entire, unbounded slice of currently active workflow-registry allowlist entries on every single incoming Vault gateway request that lacks a JWT (`req.Auth == ""`). This is analogous to the reported `projectCost()` pattern: a loop with no bound other than "however large the tracked list has grown," executed unconditionally on a request path reachable by unprivileged external callers.

### Finding Description
The Vault gateway authorizer routes any request without `req.Auth` set to the legacy allowlist path: [1](#0-0) 

That path calls `allowListBasedAuth.AuthorizeRequest`, which in turn calls `findAllowlistedItemWithRetry`: [2](#0-1) 

For every attempt (up to `retryCount+1` = 11 iterations, each separated by a 3-second sleep — a built-in 30+ second amplification window per request), the code:
1. Fetches the full, currently-active allowlist via `r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)` — a list that grows with total organic Vault usage across *all* workflow owners on the DON, not scoped to the caller.
2. Unconditionally builds a `[]string` of formatted debug strings with `fmt.Sprintf` for every entry in that list (line 82-86), even though this is only used for a `Debugw` log call — the formatting work is done eagerly regardless of the configured log level.
3. Calls `fetchAllowlistedItem`, which does a second full linear scan of the same list: [3](#0-2) 

There is no cap on the list size, no per-owner narrowing before iterating, and no early termination other than the digest happening to be found. If the digest is not found (e.g., an attacker submits a request with a garbage/never-allowlisted digest, or simply replays before it's allowlisted), the node repeats this full double-scan + string-building sequence 11 times, each request thus costing `O(11 * n)` work plus holding a goroutine and gateway-connector context open for the full retry window.

### Impact Explanation
This is reachable by any external, unprivileged client capable of sending a request to the Vault gateway with `req.Auth` empty (the legacy/non-JWT path), i.e., before any credential-based check narrows the caller. An attacker can send a stream of such requests with fabricated/garbage request digests. Each request triggers repeated full scans over the DON-wide allowlist (which is shared, unscoped, and grows with legitimate global Vault activity) and repeated allocation/formatting work, all while holding node/gateway resources (goroutines, CPU) for up to ~30+ seconds per request due to the built-in retry/sleep loop. As legitimate Vault usage across the DON increases the allowlist size, the marginal cost of each malicious/garbage authorization attempt increases proportionally, degrading Vault authorization throughput and CPU for all callers — a resource-exhaustion/DOS vector on the node's authorization path, directly analogous to the referenced `projectCost()` unbounded-loop finding (unbounded work driven by global list growth, invoked on every unprivileged request with no incremental/cached check).

### Likelihood Explanation
Likelihood is moderate-to-high in environments where the legacy (non-JWT) allowlist auth path remains enabled, since it requires no special privilege to reach — any caller of the Vault gateway endpoint can omit `req.Auth` and supply an arbitrary digest, immediately triggering the expensive scan/retry sequence. The severity scales with the size of the DON-wide allowlist, which is an operational value outside any single caller's control but that an attacker benefits from as it grows.

### Recommendation
- Avoid unconditional formatting of the full allowlist for debug logging; gate the `fmt.Sprintf` loop behind an explicit log-level check (e.g., `if lggr.Level() <= zap.DebugLevel`) so it isn't paid on every request regardless of verbosity.
- Replace the O(n) linear scan with an indexed lookup (e.g., a `map[[32]byte]*WorkflowRegistryOwnerAllowlistedRequest` maintained/refreshed by `workflowRegistrySyncer`) so digest lookups are O(1) instead of O(n).
- Bound or short-circuit the retry loop for requests that are clearly malformed/never-allowlisted (e.g., rate-limit or fail fast per-caller before entering the 11x/30s retry loop), rather than always running the full retry+scan cycle to exhaustion.
- Consider applying a per-caller/per-IP rate limit ahead of `AuthorizeRequest` for the non-JWT allowlist path specifically, since it is the more expensive of the two authorization mechanisms.

### Proof of Concept
Conceptually:
1. An external client sends a Vault gateway JSON-RPC request (e.g., `MethodSecretsCreate`) with `req.Auth == ""` and a `Params` payload whose digest does not correspond to any real allowlisted entry.
2. This routes through `authorizer.authorizeRequest` → `authorizeAllowListBasedAuth` → `allowListBasedAuth.AuthorizeRequest` → `findAllowlistedItemWithRetry`.
3. On each of up to 11 attempts, the node fetches and fully iterates the DON's entire active-allowlist slice twice (once to build debug strings, once via `fetchAllowlistedItem`), sleeping 3 seconds between attempts.
4. Repeating this request from a script (with a fresh nonce/digest each time to bypass any request-level replay guard, since the replay guard executes *after* authorization succeeds/fails) forces the node to redo this expensive work per request, scaling with the real-world size of the allowlist, for roughly 30+ seconds of held resources per malicious request.

Note: I was not able to fully trace `gateway_vault_request_processor.go` (the actual entry point wiring gateway HTTP/JSON-RPC requests into `AuthorizeRequest`) within the tool budget, so the exact upstream request-validation steps before this authorization call (if any additional filtering occurs) are not fully confirmed — a Devin session with full repo access should verify whether any pre-authorization filtering reduces this exposure before treating this as final.

```go
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
```

```go
func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}
```

```go
func (r *allowListBasedAuth) fetchAllowlistedItem(allowListedRequests []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, digest [32]byte) *workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	for _, item := range allowListedRequests {
		if item.RequestDigest == digest {
			return &item
		}
	}
	return nil
}
```
