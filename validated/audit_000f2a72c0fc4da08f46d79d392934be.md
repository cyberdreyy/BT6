### Title
Permissionless multi-transfer instructions (`lending_pool_collect_bank_fees`, `lending_pool_handle_bankruptcy`) can be permanently blocked by a Token-2022 transfer-hook on the bank mint - ([File: programs/marginfi/src/instructions/marginfi_group/collect_bank_fees.rs], [File: programs/marginfi/src/instructions/marginfi_group/handle_bankruptcy.rs])

### Summary
The C4 auction bug relies on a single instruction that sequentially moves funds to multiple parties, where one leg invokes an attacker-controlled callback (`safeTransferFrom` → `onERC721Received`) that can revert, blocking payouts to every other participant in the same transaction. The structural analog in marginfi is any permissionless instruction that performs several sequential SPL-transfer CPIs for the *same* Token-2022 mint within one call, where an active `TransferHook` extension invokes an external, non-marginfi-controlled program on every leg.

### Finding Description
`lending_pool_emissions_deposit` explicitly guards against this by rejecting mints with an active transfer hook via `utils::has_transfer_hook`: [1](#0-0) 
and `has_transfer_hook` is implemented in: [2](#0-1) 

However, this check is `grep`-confirmed to exist in only one place in `programs/marginfi/src/`, meaning it is **not** applied in `lending_pool_add_bank` (bank creation performs no extension allow-listing before setting `IS_T22`): [3](#0-2) 
nor in `lending_pool_collect_bank_fees`, which performs three sequential `bank.withdraw_spl_transfer` calls for the *same bank mint* to three different destination vaults (`fee_vault`, `insurance_vault`, `fee_ata`) inside one permissionless instruction: [4](#0-3) 
nor in `lending_pool_handle_bankruptcy`, where the insurance-fund coverage transfer moves funds from `insurance_vault` to `liquidity_vault` for the debt-bank's mint before `bank.socialize_loss` is applied: [5](#0-4) 

The test-utils fixtures confirm regular deposit/borrow/repay/liquidation flows are expected to *support* Token-2022 mints carrying an active `TransferHook` (extra account metas are attached for the hook CPI), indicating the hook is intentionally invoked, not rejected, outside the emissions-deposit path: [6](#0-5) [7](#0-6) 

Because the mint's transfer-hook *program* can be an arbitrary, externally-controlled program (its authority is set by the token/mint creator, not by marginfi), that external party can cause the hook to conditionally (or unconditionally) revert. Since `lending_pool_collect_bank_fees` and `lending_pool_handle_bankruptcy` bundle multiple CPI transfers of the same mint into a single atomic instruction, a reverting hook blocks **all** transfers in that instruction, not just the "winner's" leg — exactly the same failure mode as the C4 auction's `claimAuction`.

### Impact Explanation
- For `lending_pool_collect_bank_fees`: if the hook always reverts, insurance/group/program fees for that bank can never be swept out of the liquidity vault into the insurance/fee vaults. Since bankruptcy handling (`lending_pool_handle_bankruptcy`) explicitly recommends running fee collection first to fully capitalize the insurance fund (per `guides/RISK_AND_LIQUIDATORS/BANKRUPTCY.md` and `guides/ADMIN/COLLECTING_FEES.md`), a griefed fee-collection path degrades the insurance fund's capitalization for that bank.
- For `lending_pool_handle_bankruptcy`: if the debt bank's mint carries a reverting hook, the insurance-vault → liquidity-vault transfer that funds bad-debt coverage can never complete, meaning `handle_bankruptcy` can never succeed for that bank. Per the bankruptcy guide, if bankruptcy never runs, "remaining depositors can never withdraw the whole balance in the bank" — a durable, financially-significant freeze affecting every depositor of that bank, not just the bankrupt account.
- This is a genuine "durable freeze/inconsistency with financial effect," matching the impact bar in the auction analog, though the blast radius is scoped to a single bank/mint rather than protocol-wide.

### Likelihood Explanation
Likelihood is **low-to-uncertain** and could not be fully confirmed within the available tool budget:
- It requires a group admin to list a Token-2022 bank whose mint has (or can later be given) an active transfer hook pointed at a program not controlled by marginfi. `lending_pool_add_bank` is admin-gated, so admins choosing to list such a mint is a prerequisite; this pushes the scenario toward "trusted mint listing," reducing but not eliminating unprivileged exposure, since the *hook program's* behavior (and its authority to change it later) is controlled by the external mint issuer, not the marginfi admin.
- I could not verify within this session whether `BankConfigImpl::validate()` (in `programs/marginfi/src/state/bank_config.rs`) independently rejects mints with active transfer hooks at add-bank time — the tool budget was exhausted before reading that function's body. If it does perform such a check, this finding would be moot for bank-creation time, though a hook could still be *activated later* by the mint's hook authority after the bank is already live, which would not be caught by an add-time check.
- Given this residual uncertainty about `bank_config.rs::validate()`, I cannot assert with full confidence that this is currently unmitigated in production.

### Recommendation
- Apply the same `utils::has_transfer_hook` (and non-zero transfer-fee) rejection used in `lending_pool_emissions_deposit` uniformly at `lending_pool_add_bank` time, and/or defensively re-check for an active transfer hook immediately before executing `lending_pool_collect_bank_fees` / `lending_pool_handle_bankruptcy`, failing gracefully rather than allowing the whole instruction to be blocked by an external hook.
- Alternatively, restructure `lending_pool_collect_bank_fees` and `lending_pool_handle_bankruptcy` so that a failure in one transfer leg does not abort the others (e.g., process each vault transfer in its own instruction, or catch/absorb the CPI failure per component and continue), mirroring the recommended fix in the C4 report to decouple the state transition from the potentially-reverting external call.

### Proof of Concept
Concrete exploitation could not be fully constructed within the available time/tools, because it depends on the not-yet-verified behavior of `BankConfigImpl::validate()` in `programs/marginfi/src/state/bank_config.rs`. Conceptually:
1. Admin adds a Token-2022 bank via `lending_pool_add_bank` for a mint that has (or later gains) an active `TransferHook` extension pointing to a program the admin does not control.
2. That hook program is authored to revert whenever invoked with specific source/destination accounts (e.g., the `insurance_vault` or `fee_vault` PDAs), or unconditionally.
3. Any subsequent call to `lending_pool_collect_bank_fees` or `lending_pool_handle_bankruptcy` on that bank triggers `transfer_checked`/CPI through the Token-2022 program, which invokes the hook and reverts, aborting the whole instruction and permanently blocking fee sweep / bad-debt socialization for that bank. /// Returns `true` if the given mint has an active transfer hook program.
```rust
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
```
