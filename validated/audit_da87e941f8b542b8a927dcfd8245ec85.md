### Title
External-initiator credentials are treated as `isUser` and can trigger arbitrary jobs by integer ID via `POST /v2/jobs/:ID/runs`, bypassing the intended EI/job binding - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` injects a synthetic `clsessions.User{Role: UserRoleRun}` into the same `SessionUserKey` context slot used for real session/token users, so `PipelineRunsController.Create`'s `isUser` check (intended to gate "run by integer job ID" to real users only, explicitly excluding EIs) cannot distinguish an EI-authenticated request from a genuine user. As a result, a holder of any valid EI credential can call `POST /v2/jobs/:ID/runs` with an arbitrary integer job ID and successfully trigger `RunJobV2` for a job it has no configured relationship to.

### Finding Description
The `userOrEI` route group wraps `/v2/jobs/:ID/runs` with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` followed by `auth.RequiresRunRole(prc.Create)`: [1](#0-0) 

`RequiresRunRole` only checks `clsessions.User.Role`, with no notion of which job/EI the credential is scoped to: [2](#0-1) 

Crucially, `AuthenticateExternalInitiator` sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` in addition to `SessionExternalInitiatorKey`: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code explicitly documents the intended restriction — "only users are allowed to run jobs using int IDs - EIs not allowed" — and gates this on `auth.GetAuthenticatedUser(c)`: [4](#0-3) 

Because `GetAuthenticatedUser` simply reads whatever object is stored under `SessionUserKey`, and `AuthenticateExternalInitiator` populates that same key with a fake `User{Role: UserRoleRun}`, `isUser` evaluates to `true` for EI-authenticated requests exactly as it does for real session/token users. The code never calls `auth.GetAuthenticatedExternalInitiator(c)` to check whether the caller is actually an EI, nor does it verify any EI-to-job association before invoking `prc.App.RunJobV2(ctx, jobID, nil)`.

The UUID-based path (legacy webhook jobs, which is what the question's proof idea targets) is separately and correctly blocked because the webhook job type has been fully removed — any UUID-style `:ID` is rejected with `job.ErrJobTypeRemoved` before any EI/job binding logic is reached: [5](#0-4) 

This is confirmed by existing tests, which show that even the legacy webhook path can no longer create/run webhook jobs at all: [6](#0-5) [7](#0-6) 

So the exact scenario in the question (two webhook jobs each bound to a distinct EI, EI-A UUID-targeting EI-B's job) cannot occur — webhook job creation/execution by UUID is rejected outright, independent of EI identity. However, the underlying invariant violation the question is probing for ("request binding: an EI request must be attributable to exactly one authorized job") still exists via the integer-ID branch: an EI credential holder can supply any integer job ID (belonging to any job of any type/owner) and successfully trigger a run, because the code's own EI-exclusion check is defeated by the shared `SessionUserKey` mechanism.

### Impact Explanation
This maps to "unauthorized job run" / authorization bypass: an EI credential — intended only to be an outbound-triggering mechanism for webhook jobs it is configured against (a feature now removed) — is instead functionally equivalent to a full `run`-role user across the entire node's job set. An attacker holding any single EI's access key/secret can enumerate/guess integer job IDs and trigger pipeline runs for jobs they have no authorization over, potentially causing unwanted on-chain transactions, unwanted external HTTP calls in job pipelines, resource exhaustion, or interference with other jobs' state.

### Likelihood Explanation
Preconditions are minimal: possession of any valid EI access key/secret (obtainable by any actor previously granted EI credentials, e.g., a partner integration) and knowledge/guessing of a target job's integer ID (job IDs are small sequential integers and are exposed via `GET /jobs`, which is reachable by any authenticated EI or user with `GetAuthenticatedUser` set). No admin/operator access required. The request is a single unauthenticated-relative-to-target-job `POST /v2/jobs/:ID/runs` call with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers and an integer `:ID`, fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or properly scope) requests where the caller is an EI, rather than relying on the shared `isUser`/`SessionUserKey` check that `AuthenticateExternalInitiator` also populates. If EI-triggered runs by integer ID are meant to be supported at all, add and enforce an explicit EI-to-job binding lookup (verify the specific `ei.ID`/`ei.Name` is associated with the target job) before calling `RunJobV2`. Consider using a distinct context key or a dedicated boolean flag (e.g., `IsExternalInitiator`) instead of overloading `SessionUserKey` with a synthetic `User` object.

### Proof of Concept
Go handler-level integration test plan (in `core/web/pipeline_runs_controller_test.go`):
1. Start an app with two non-webhook jobs (e.g., two `cron` or `webhook`-replacement job types no longer applicable — use two generically created jobs, `jobA` (ID=1) and `jobB` (ID=2)) not associated with any EI at all.
2. Create an external initiator `EI-A` via `cltest.CreateExternalInitiatorViaWeb`.
3. Send `POST /v2/jobs/<jobB.ID>/runs` using `EI-A`'s access key/secret headers (`static.ExternalInitiatorAccessKeyHeader`, `static.ExternalInitiatorSecretHeader`) via `cltest.UnauthenticatedPost`.
4. Assert the response is `200 OK` with a created `pipelineRun` resource (demonstrating `isUser` was true and `RunJobV2` executed for a job unrelated to `EI-A`), and assert `pipeline_runs` count increased — exposing that no EI-to-job binding check exists.
5. Compare against expected behavior: the request should instead return `401 Unauthorized`/`403 Forbidden` since `EI-A` has no relationship to `jobB`.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
