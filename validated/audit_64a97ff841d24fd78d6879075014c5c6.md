### Title
Epoch index re-evaluated at collection time stores stop-epoch loss haircut under the wrong epoch, letting haircutted withdraw receipts claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to `match_char()` re-evaluating `*str++` (an index expression with a side effect advancing between evaluations), `IdleCreditVault.collectWithdrawFunds` re-reads the mutable `epochNumber` at funding time rather than using the epoch in which the pending receipts were recorded. `deposit()` increments `epochNumber` when called while `isEpochRunning()` is true, so during `stopEpoch`/`stopEpochWithDuration` the haircut is stored under `lossRecoveryPriceByEpoch[epochNumber + 1]` while every affected receipt's `lastWithdrawRequest` and `withdrawsRequestsByEpoch` entries were recorded under the pre-increment epoch. The loss-adjusted epoch is then unreachable: the guard in `requestWithdraw` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` and finds 0, and `_claimLossAdjustedWithdrawRequest` finds no haircut — receipts recorded under the loss epoch are treated as ordinary funded receipts and paid at par.

### Finding Description
At request time, `requestWithdraw` snapshots the epoch once: `uint256 currentEpoch = epochNumber; ... lastWithdrawRequest[_user] = currentEpoch; withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (IdleCreditVault.sol:260-293). The loss-adjustment bookkeeping, however, re-evaluates the index at collection time: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` inside `collectWithdrawFunds` (IdleCreditVault.sol:421). Between those two evaluations, `deposit()` executes `epochNumber += 1` whenever it is called while `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is still true (IdleCreditVault.sol:607-610) — exactly the stopEpoch window before `isEpochRunning` is cleared. Because the strategy token is 1:1 with underlying (`price()` returns `oneToken`, IdleCreditVault.sol:174), the haircut is real money: the strategy only receives `pendingToFund` computed by `previewLossAdjustedWithdrawFunds`, yet every receipt recorded under the loss epoch claims its full face value.

The mismatch also neuters the explicit protection added for this scenario: `requestWithdraw` only blocks a follow-up request when `lossRecoveryPriceByEpoch[lossEpoch] != 0` (IdleCreditVault.sol:263-271). With the haircut parked under epoch N+1 and `lastWithdrawRequest[user] == N`, the lookup returns 0, the guard passes, and a new request overwrites `lastWithdrawRequest`, permanently orphaning the stored recovery price.

### Impact Explanation
Broken invariant: one receipt, one correctly-haircut payout. When `stopEpochWithDuration` realizes a loss over pending receipts, the strategy collects only `pendingBasis - pendingLoss` underlying, but every loss-epoch receipt is claimable at face value via `claimWithdrawRequest → _claimFundedWithdrawRequest` (the funded path requires only `epochNumber > lastWithdrawRequest`, already true after the increment, IdleCreditVault.sol:326). `_transferFundedClaim` pays early claimers 100 cents on the dollar from a reserve that only holds the haircut amount; later claimers' transactions revert on insufficient balance. Direct theft by earlier-claiming receipt holders (any unprivileged tranche holder who called `requestWithdraw` before the lossy stop) and permanent freezing of the remainder — loss bounded by `pendingLoss = _lossAmount * pendingBasis / totalBasis`, i.e. up to the full unrealized haircut. Existing guards do not stop it: the `lossRecoveryPrice != 0` check is bypassed precisely because the price is written under the wrong key, and `collectWithdrawFunds`'s `revert NotAllowed()` paths only fire on uninitialized/legacy receipts.

### Likelihood Explanation
Triggering requires only the ordinary loss flow: pending withdraw requests exist (any KYC-passed lender can create them), and the honest manager calls `stopEpochWithDuration` with a non-zero `_lossAmount` where `previewLossAdjustedWithdrawFunds` returns `pendingToFund < pendingBasis`. No privileged attacker is needed — any requestWithdraw user becomes a beneficiary of the mispricing, and claiming earlier than other receipt holders is a pure gas/first-mover race. The defect is deterministic once `deposit()`'s epoch increment precedes `collectWithdrawFunds` in the stop sequence, which is the natural order (strategy must hold CDO-pushed repayment funds before receipts are collected). The one caveat I could not fully verify within available context is the exact internal call ordering inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`; if `collectWithdrawFunds` were invoked strictly before the running-epoch `deposit()` that bumps `epochNumber`, the key would match and the finding collapses — a Foundry run of the existing `testRequestWithdraw...`/loss-path tests asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` disambiguates this in one assertion.

### Recommendation
Snapshot the receipt epoch once — mirroring the kernel fix of hoisting `*str` out of the macro. Either (a) in `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch[epochNumber - 1]`... — no, more robustly: record the "open receipt epoch" at request time (already available as `withdrawsRequestsByEpoch` keys / a `lastPendingEpoch` storage var) and have `collectWithdrawFunds` key the haircut to that recorded epoch rather than re-reading live `epochNumber`; or (b) increment `epochNumber` in a dedicated function invoked at epoch end rather than piggybacking on `deposit()`'s running-epoch branch, so the counter cannot shift mid-stop between the receipt-recording evaluation and the haircut-recording evaluation. Also make `requestWithdraw`'s guard defensive: track a `userLossEpoch` pointer explicitly set when `collectWithdrawFunds` stores a nonzero price, instead of deriving it from `lastWithdrawRequest`.

### Proof of Concept
Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testLossHaircutKeyedToWrongEpoch() external {
    uint256 amount = 10_000 * ONE_SCALE;
    // 1. Two lenders deposit and request withdraw in buffer phase (epoch N)
    uint256 trancheA = idleCDO.depositAA(amount);   // user1
    uint256 trancheB = idleCDO.depositAA(amount);   // user2 (different addr)
    cdoEpoch.requestWithdraw(trancheA, address(AAtranche)); // user1
    vm.prank(user2);
    cdoEpoch.requestWithdraw(trancheB, address(AAtranche));

    uint256 reqEpochUser1 = IdleCreditVault(address(strategy)).lastWithdrawRequest(user1);

    // 2. Run epoch, then stopEpochWithDuration with a loss so
    //    collectWithdrawFunds takes the lossRecoveryPrice branch
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 loss = /* partial loss < activeBasis + pendingBasis */;
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, loss); // internally: deposit() bumps epochNumber, then collectWithdrawFunds

    // 3. BUG ASSERT: haircut stored under epoch N+1, not user's request epoch N
    assertEq(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(reqEpochUser1), 0);
    assertGt(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(reqEpochUser1 + 1), 0);

    // 4. user1 claims at PAR despite the haircut -> drains the reduced reserve
    uint256 balPre = underlying.balanceOf(user1);
    vm.prank(user1);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(user1) - balPre,
             requestedUser1 * recoveryPrice / 1e18); // paid more than haircut share

    // 5. user2's claim reverts on insufficient strategy balance -> frozen funds
    vm.prank(user2);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Expected result: `lossRecoveryPriceByEpoch[N]` is 0 for the epoch every receipt was booked under while `lossRecoveryPriceByEpoch[N+1]` holds the haircut — proving the index advanced between the recording evaluation and the storing evaluation, exactly the `*str++` double-evaluation pattern.
