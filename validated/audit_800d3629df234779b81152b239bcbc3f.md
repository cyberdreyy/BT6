### Title
Vault request replay protection relies solely on non-persistent, per-process memory, allowing a previously-authorized (but still unexpired) request to be re-executed after a node restart - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
The Chainlink Vault capability's `Authorizer` guards against replay of a signed/allowlisted request using an in-memory `RequestReplayGuard` keyed by request digest and expiry timestamp. This is directly analogous to the reported `emitLoan()` issue: a single request/authorization intended to be used once remains valid and reusable for its entire (client-controlled) expiration window, and the *only* mechanism preventing repeated execution is a volatile, per-process map rather than a durable, single-use nonce enforced by the source of truth (the on-chain allowlist or the JWT issuer).

### Finding Description
`RequestReplayGuard` at [1](#0-0)  stores seen request digests in an in-process `map[string]int64` protected by a mutex, with no persistence to disk or a shared store. It is constructed fresh, per `Authorizer` instance, in `NewAuthorizer`: [2](#0-1) 

and each Vault DON node builds its own `Authorizer` (and therefore its own `RequestReplayGuard`) inside `NewGatewayHandler`: [3](#0-2) 

The `authorizer.AuthorizeRequest` flow only rejects replay by checking `CheckAndRecord(digest, expiresAt)` *after* successfully validating either the allowlist-based authorization or the JWT-based authorization: [4](#0-3) 

Both authorization paths otherwise treat "expiration in the future" as sufficient proof of authorization — the allowlist test explicitly documents this design: "Same request is still authorized here; replay protection lives in the generic Authorizer" ( [5](#0-4) ), and `VerifyRequestJWT` only checks that the JWT hasn't expired and its digest matches the request, not that the `jti` has never been consumed before ( [6](#0-5) ).

Because the only "used-once" bookkeeping is the ephemeral `RequestReplayGuard` map, any event that clears process memory — a node restart, redeploy, or crash/recovery — silently and completely erases the replay history while the underlying authorization (on-chain allowlist entry or signed JWT) remains valid until its `ExpiryTimestamp`/`exp`. Once that occurs, the exact same previously-executed request (e.g., a `SecretsUpdate` or `SecretsDelete` call) can be resubmitted and will be authorized and executed again, exactly like the reported `emitLoan()` signature reuse, where the sole safeguard was an expiration window the caller controls, rather than a persisted nonce.

### Impact Explanation
An attacker (or a curious/careless holder of a previously legitimate, not-yet-expired signed request/JWT — e.g. logged in application logs, a support ticket, browser history, or client-side storage) can resubmit that exact request to the Gateway after any Vault node restart and have it processed again as a fully authorized vault operation (create, update, or delete of a user's secrets) — a privileged action being replayed without the user's renewed consent. This subverts the intended single-use semantics of the authorization and can cause unauthorized secret mutation/deletion.

### Likelihood Explanation
Exploitation requires: (1) possession of a previously valid, not-yet-expired signed request/JWT/allowlist entry, and (2) a Vault node restart (deploy, crash-recovery, autoscaling event, etc.) occurring before that expiry. Node restarts are a normal and frequent operational event in a production DON, and expiration windows are set by the client/issuer, not enforced to be short by the protocol, so this is realistically triggerable without any special privilege beyond having previously made one authorized request.

### Recommendation
Persist replay-protection state (digest + expiry) outside of process memory — e.g., in a durable store shared across the DON, or by requiring the on-chain allowlist to mark/remove a `RequestDigest` as consumed once used, and by tracking JWT `jti` consumption in durable storage. Alternatively, bind authorization strictly to a monotonically-increasing, server-issued nonce that is invalidated on first use at the source of truth, rather than relying on an in-memory cache that resets on restart.

### Proof of Concept
1. Client obtains a valid allowlisted request digest (or a signed JWT) with `ExpiryTimestamp`/`exp` set far in the future, and successfully calls `SecretsUpdate` (or `SecretsDelete`) — the request is authorized and executed by all live Vault nodes, and each node's `RequestReplayGuard.CheckAndRecord` records the digest.
2. A Vault gateway node restarts (deployment, crash-recovery, scaling) before the authorization expires — `NewGatewayHandler`/`NewAuthorizer` creates a brand-new, empty `RequestReplayGuard` ( [2](#0-1) ).
3. The identical previously-used request/JWT is resubmitted to the gateway; `AuthorizeRequest` re-validates it as authorized (allowlist entry / JWT digest & expiry still valid) and `CheckAndRecord` succeeds again because the guard has no memory of the prior use, so the operation (e.g., secret delete/update) executes a second time.

type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}
