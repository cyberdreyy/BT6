### Title
Fee-on-transfer underlying mints unbacked strategy tokens and clears withdraw basis at nominal value, breaking vault solvency — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` accounts for underlying token transfers at the nominal `_amount` everywhere it pulls tokens, never measuring `balanceAfter - balanceBefore`. If the pool currency (e.g. USDT, which has a dormant fee mechanism its issuer can activate) ever takes a transfer fee, strategy tokens and funded withdraw basis are recorded at face value while less underlying actually arrives. The shortfall is socialized onto the last claimants — a direct solvency break, not a donation/isolation issue.

### Finding Description
Three pull paths credit the full `_amount` regardless of what is actually received:

1. `deposit()` pulls `_amount` from the CDO and mints `_amount` strategy tokens 1:1 (`price()` is hardcoded to `oneToken`). With a fee on transfer, the vault receives `_amount - fee` but mints full claims. [1](#0-0) 
2. `collectWithdrawFunds()` decrements `pendingWithdraws` (or stores `lossRecoveryPrice` computed from nominal `_amount`) and then pulls `_amount` — so borrowers/fulfillers are charged basis for tokens that never fully arrived, and every claimant's recovery price is overstated. [2](#0-1) 
3. `collectInstantWithdrawFunds()` reduces `pendingInstantWithdraws` by `_amount` while receiving less. [3](#0-2) 

`_transferFundedClaim` then pays claims at par from the actual balance, so the deficit materializes as an underflow/revert for the last claimer, not for the shortfall creator. [4](#0-3) 

No guard compensates: there is no skim-of-donated-assets or balance delta check on these paths, and `_transferFundedClaim` only protects `defaultRecoveryReserve`, not nominal-vs-actual mismatches.

### Impact Explanation
Insolvency equal to cumulative drained fees. Every strategy token minted in `deposit` is redeemable 1:1 (request flows burn/mint at par), so fee shortfalls accumulate as unbacked liabilities. Withdraw claimants — both funded receipts and loss-adjusted receipts priced via `lossRecoveryPriceByEpoch` — are shorted by the aggregate fee leakage. Quantified loss: `sum(fee_i)` across all pulls; e.g. a 10% fee on a 1,000,000-underlying epoch leaves ~100,000 unpayable to final claimants.

### Likelihood Explanation
Requires the underlying to take a transfer fee after vault initialization. `underlyingToken` is fixed at `initialize`, and pool currencies like USDT carry an issuer-controllable fee switch, so the scenario is realistic rather than hypothetical — the same "cannot guarantee the token stays non-deflationary" reasoning as the source report. No attacker privilege within the protocol is needed; any lender depositing during the fee-enabled window triggers the accounting drift automatically.

### Recommendation
Measure actual received amounts on every pull and account for that:

```solidity
uint256 balBefore = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - balBefore;
_mint(msg.sender, received);
```

Apply the same pattern in `collectWithdrawFunds`/`collectInstantWithdrawFunds`, or explicitly revert in `initialize` for tokens known to support fees and document the invariant that the pool currency must be fee-free.

### Proof of Concept
Foundry fork sketch (mainnet fork with a mock or fee-enabled token standing in for the pool currency):

```solidity
// 1. Deploy IdleCreditVault initialized with FeeToken (10% transfer fee).
// 2. Lender deposits 1_000_000 via IdleCDO -> strategy.deposit(1_000_000)
//    vault receives 900_000 but mints 1_000_000 strategy tokens to the CDO.
// 3. Epoch runs, borrower repays funded withdraw basis nominally;
//    collectWithdrawFunds(500_000) clears 500_000 of pendingWithdraws
//    while only 450_000 arrives.
// 4. First claimant: claimWithdrawRequest pays at par -> drains balance.
// 5. Final claimant's _transferFundedClaim reverts on insufficient balance,
//    demonstrating ~100k+ unbacked claims == permanent loss/freezing.
assertLt(underlyingToken.balanceOf(address(vault)), vault.balanceOf(idleCDO));
```

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
