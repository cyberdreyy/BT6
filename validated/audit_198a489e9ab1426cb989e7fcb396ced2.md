### Title
Missing min-out protection on `requestWithdraw` lets a lender dilute the epoch interest locked into another user's withdraw receipt — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw(uint256 _amount, address _tranche)` fixes the user's withdraw receipt (`_underlyings = principal + interest - totalFees`) entirely at request time, with no `minUnderlyings`/`minReturn` parameter. The interest component is computed in `_calcInterestWithdrawRequest` as `_amount * totTrancheInterest / _trancheBal`, where `_trancheBal` is the tranche's `lastSavedNAV` and `totTrancheInterest` is proportional to *total* managed NAV. An unprivileged, KYC-passing lender can front-run a victim's `requestWithdraw` with a large same-tranche `depositAA`/`depositBB`, inflating `_trancheBal` faster than `totTrancheInterest` grows, thereby shrinking the interest baked into the victim's fixed receipt. The forgone yield is redistributed to remaining tranche holders (attacker included) via `expectedEpochInterest`/`interestForOverUnderPerformance`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
In `requestWithdraw`, `_underlyings` is locked at request time:

- `principal = _trancheToUnderlyings(_amount, _tranche)`
- `(interest, diff) = _calcInterestWithdrawRequest(principal, _tranche)`
- receipt = `principal + interest - _totalWithdrawFees(...)`, minted to the user as strategy tokens via `creditVault.requestWithdraw(_underlyings, msg.sender, principal)` and burned out of live NAV via `_withdrawOps`.

`_calcInterestWithdrawRequest` computes `totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer)` (linear in total NAV), takes the tranche share `totTrancheInterest = totInterest * ratio / FULL_ALLOC`, and pays per-unit `_interest = _amount * totTrancheInterest / _trancheBal` where `_trancheBal = lastNAVAA` (for AA). Per-unit AA interest is therefore proportional to `ratio * (NAV_AA + NAV_BB) / NAV_AA`, i.e. it decreases strictly as `NAV_AA` grows relative to `NAV_BB`.

`_deposit` (`IdleCDOCreditVault._deposit`) has no slippage/min-share guard either, but critically it *mutates the denominator*: `_mintShares` does `lastNAVAA += _underlyings` and `_updateSplitRatio` then adapts `trancheAPRSplitRatio` toward the new AA TVL ratio — both effects reduce the victim's pending per-unit interest. Because the receipt is fixed at request time and there is no `minAmountOut` argument on `requestWithdraw`, the victim cannot bound this dilution. No existing guard stops it: `_skimDonatedAssets` only removes raw token donations, `isWalletAllowed` admits any KYC'd lender, `_updateAccounting` doesn't revert (no loss occurs), and the deposit path is `whenNotPaused` and usable during the buffer. ### Impact Explanation
Theft of unclaimed yield. The victim's strategy-token receipt — the exact amount later paid out by `claimWithdrawRequest`/`claimInstantWithdrawRequest` via `IdleCreditVault` — is understated versus the interest they would have locked had the attacker not diluted `_trancheBal`. Magnitude: for an AA pool at 50% AA ratio pushed to 90% by the attacker's deposit, the per-unit AA interest factor `(1 + NAV_BB/NAV_AA)` drops from `2·k·ratio` to `~1.11·k·ratio`, i.e. up to ~45% of one epoch's interest on the victim's principal is stripped from the receipt. The displaced interest stays in `expectedEpochInterest` (adjusted only by `interestForOverUnderPerformance`, which tracks the no-split baseline, not the dilution) and is distributed across tranche holders at `stopEpoch`, so the attacker — now the dominant AA holder — recaptures most of it. The attacker's costs are the upfront management fee on their deposit and one epoch of capital lockup; the victim's loss is deterministic once the request lands.

### Likelihood Explanation
Requires: (a) an epoch in buffer/running phase with `epochDuration > 0`, (b) the attacker to be a KYC-passing lender (`isWalletAllowed`), (c) capital large relative to AA NAV to move the ratio meaningfully. No privileged action, oracle, or borrower misbehavior is needed. The profit ceiling is the victim's epoch interest minus fees, so this is lucrative mainly against large withdraw requests in low-fee configurations; it is a griefing/dilution primitive that exists purely because `requestWithdraw` lacks a user-specified minimum output — the same missing-safeguard class as the reference report.

### Recommendation
Add a `minUnderlyings` parameter to `requestWithdraw` (and a `minShares` parameter to `depositAA`/`depositBB`/`depositDuringEpoch`) and revert when the computed receipt/minted amount is below the caller's floor. Alternatively, snapshot and commit the per-unit interest rate at the epoch boundary so intra-buffer deposits cannot change the interest rate applied to pending requests.

function testWithdrawRequestInterestDilution() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // 50% AA / 50% BB pool, epoch 0 runs and stops (buffer phase)
    uint256 mintedAA = idleCDO.depositAA(amount);       // victim
    _depositWithUser(attacker, amount, false);          // some BB
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Baseline: victim requests withdraw with no dilution
    uint256 vanilla = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
    // revert state / snapshot and replay with attacker front-run:
    // attacker deposits 8x AA TVL right before victim's request
    vm.startPrank(attacker);
    idleCDO.depositAA(8 * amount);                      // NAV_AA inflated
    vm.stopPrank();
    uint256 diluted = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    // diluted < vanilla: the strategy-token receipt minted by
    // IdleCreditVault.requestWithdraw is smaller; victim has no way to bound it
    assertLt(diluted, vanilla);
}

    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);
  }

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
