### Title
Claimed instant-withdraw receipts stay in the default-epoch claim basis, inflating `defaultRecoveryPrice` and stranding recovery funds for later claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a user's funded instant-withdraw receipt but only clears the aggregate `instantWithdrawsRequests[_user]`. It never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in the *same* epoch, `finalizeDefaultRecovery` counts those already-paid receipts twice: once inside `defaultPendingClaimBasis()` (inflating the recovery basis) and once inside `_defaultPrefundedInstantReserve()` (treating paid-out funds as still-held reserve). The resulting `defaultRecoveryPrice` is computed on phantom funds, so early post-default claimants are overpaid and the recovery reserve runs dry before the last claimants are paid — their claims permanently revert. This is the idle-tranches analog of the Popsicle "one position, multiple payouts" reward-accounting flaw: a receipt that was already settled remains in the accounting for a subsequent distribution.

### Finding Description
Relevant code:

- `claimInstantWithdrawRequest` (lines 380–393) burns `instantWithdrawsRequests[_user]` and zeroes the aggregate, but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched.
- `defaultPendingClaimBasis()` (lines 644–649) adds the full `instantWithdrawClaimsByEpoch[epochNumber]` — including already-claimed receipts — to the recovery basis whenever `pendingInstantWithdraws != 0`.
- `_defaultPrefundedInstantReserve()` (lines 716–723) computes `instantBasis - pendingInstant` and treats the difference as underlying already held by the strategy, even though part of it was already transferred out to users who claimed.
- `finalizeDefaultRecovery` (lines 685–692) then sets `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` using both inflated terms.

Concretely, let a user request instant withdraw `X` in epoch E, the queue gets partially funded (`collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` but it stays non-zero), and the user claims `X` at par via `claimInstantWithdrawRequest`. Then in the same epoch E the borrower defaults and `finalizeDefaultRecovery` runs:

- `instantWithdrawClaimsByEpoch[E]` still includes `X` → `totalBasis` inflated by `X`.
- `_defaultPrefundedInstantReserve` counts `X` as if still held → `reserveAmount` inflated by `X`, but the real balance is short by `X` (it was paid out).

With `R < B` (partial recovery), `(R + X)/(B + X) > R/B`: every defaulted-epoch claimant receives a *higher* recovery price than the strategy can actually honor. Early claimants (normal pending withdrawers, APR0 requesters, or post-default requesters) are paid the inflated rate from real funds; once the balance is exhausted, `defaultRecoveryReserve` underflows or the `safeTransfer` reverts for all remaining claimants, permanently freezing their recovery share.

Secondary effect: the user who already claimed and then made a second same-epoch instant request can never claim again — `_claimDefaultedInstantWithdrawRequest` subtracts the stale `claimBasis` (including the already-claimed `X`) from `instantWithdrawsRequests[_user]` and burns `claimBasis` receipt tokens the user no longer holds, so the call always reverts. That part is self-inflicted, but the basis inflation harms unrelated claimants regardless.

The existing guards do not stop this: `_transferFundedClaim` only protects the reserve *after* it is recorded (lines 899–905); the corruption happens at finalization time inside `finalizeDefaultRecovery`/`defaultPendingClaimBasis`, before the guard applies.

### Impact Explanation
Any defaulted-epoch claimant who claims early extracts more underlying than their pro-rata share of genuinely recovered funds; the excess is directly stolen from later claimants, whose `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls permanently revert once the reserve is depleted. Loss magnitude scales with the amount of same-epoch instant withdrawals that were funded and claimed before default — up to the full recovery reserve for the tail claimants. Severity is high but capped by the pre-default instant-claim volume.

### Likelihood Explanation
Requires: instant withdrawals enabled, an instant request partially funded and claimed during epoch E, and a borrower default finalized while `epochNumber == E` and `pendingInstantWithdraws != 0`. Defaults are the designed-for edge case of this vault, and the default-epoch bookkeeping is exactly where `instantWithdrawClaimsByEpoch` is consumed — the window is the normal instant-withdraw lifecycle, not an exotic path. Any unprivileged lender with an ordinary `requestWithdraw` receipt in the default epoch is the beneficiary of the inflated price; no privileged cooperation is needed beyond the honest manager/guardian finalizing the default.

### Recommendation
In `claimInstantWithdrawRequest`, also decrement `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (or track per-epoch claimed amounts), so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only count receipts that are still outstanding. Alternatively, snapshot `instantWithdrawClaimsByEpoch` at funding time and subtract claims as they are paid. A symmetric fix is needed for the per-user entry to avoid the underflow described above.

```solidity
function testInstantClaimedReceiptInflatesDefaultRecovery() external {

    // userA: requestInstantWithdraw(X) -> receipt minted

    //    so pendingInstantWithdraws != 0 but X is fully claimable for userA
    // userA: claimInstantWithdrawRequest() -> receives X at par
    // assert: instantWithdrawsRequestsByEpoch[userA][epoch] == X   // BUG: not cleared
    // assert: instantWithdrawClaimsByEpoch[epoch]   == X           // BUG: not decremented
    // userB: requestWithdraw(Y) -> pendingWithdraws = Y
    // borrower defaults; finalizeDefaultRecovery(R, source) with R < totalBasis
    // recorded defaultRecoveryPrice uses (R + X) / (B + X) > R / B
    // userB (or an attacker with a small default-epoch receipt) calls
    // claimWithdrawRequest() first -> paid at inflated price
    // a second defaulted-epoch claimant calls claimWithdrawRequest()
    //    -> reverts on defaultRecoveryReserve underflow / failed transfer
    //    => recovery funds permanently frozen for the tail claimant
}
```

The assertion that `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` retain the claimed amount is directly readable in `claimInstantWithdrawRequest` (lines 387–392), and the double consumption of the same stale ledger is visible in `defaultPendingClaimBasis` (line 647) and `_defaultPrefundedInstantReserve` (lines 719–722).
