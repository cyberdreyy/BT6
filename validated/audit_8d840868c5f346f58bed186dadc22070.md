### Title
Instant-withdraw claim pays unfunded same-user receipts at par by merging all queued requests — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The external bug is a failure to re-check a queued record's type after an initial pass already produced work: a second same-typed record is silently merged into the first record's processing. The analog lives in `claimInstantWithdrawRequest` in `IdleCreditVault`. `requestInstantWithdraw` records each request both in the aggregate `instantWithdrawsRequests[_user]` and per-epoch in `instantWithdrawsRequestsByEpoch[_user][epoch]`, while `pendingInstantWithdraws` tracks only the still-unfunded remainder. When the claim path runs, it pays and burns the entire aggregate `instantWithdrawsRequests[_user]` in one shot — without checking whether every queued record in that aggregate is actually funded — the exact "process the first record, then merge the next same-type record" shape of the kernel bug [1](#0-0) .

### Finding Description
`requestInstantWithdraw` can be invoked multiple times for the same `_user` across (or within) epochs; there is no guard like the `NotAllowed` revert that `requestWithdraw` applies for unfinalized loss receipts [2](#0-1) . Each call mints a full strategy-token receipt to the user and increments both `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`. Only `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` as the CDO actually pulls underlying into the strategy [3](#0-2) .

`claimInstantWithdrawRequest` then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It never consults `pendingInstantWithdraws` or `instantWithdrawsRequestsByEpoch` to distinguish a funded "record" from an unfunded one. `_transferFundedClaim` only protects `defaultRecoveryReserve` — it does not reserve pending instant withdrawals [4](#0-3) . So an earlier funded receipt and a later unfunded receipt are merged and both paid at par, exactly like the TLS loop processing the first queued record of the same type as if it were DATA. The same over-merging risk exists on the defaulted path: `_claimDefaultedInstantWithdrawRequest` clears the default-epoch piece, but the remaining aggregate is then paid in full without a per-epoch funded check [5](#0-4) .

### Impact Explanation
An unprivileged KYC-passing lender can stack two instant withdraw receipts where only the first is funded. When the claim executes, the strategy transfers underlying for both receipts at par, spending either (a) underlying held for other users' pending instant withdrawals (`pendingInstantWithdraws` is left non-zero while its backing is drained — permanent freezing/theft for later claimants), or (b) strategy liquidity backing active LPs (direct insolvency). The overpaid amount equals the unfunded second receipt, quantified as the user's own request size, bounded only by what the CDO permits instant requests for.

### Likelihood Explanation
Requires a configuration where an instant request can be queued without its funds being collected before a claim is processed — i.e., `pendingInstantWithdraws > 0` while a claim is still allowed for the same user. The vault-side ledgers explicitly model partially funded instant queues (`_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` for the current epoch [6](#0-5) ), so the protocol itself anticipates epochs where instant claims are only partly funded. Whether `IdleCDOEpochVariant` gates `claimInstantWithdrawRequest` on full funding of the caller's specific receipts — rather than only on elapsed delay — is the decisive question; I could not fully verify the CDO-side gating within this review. If the CDO only enforces the delay/funding at the epoch level, the merge is exploitable; if it strictly requires zero pending instant withdrawals for the caller before claiming, the severity drops.

### Recommendation
In `claimInstantWithdrawRequest`, before paying the aggregate, re-check each queued "record's" funding state: pay at most `instantWithdrawsRequests[_user]` minus the user's still-unfunded portion (e.g., cap the payout at funded receipts recorded per epoch, or revert while `instantWithdrawsRequestsByEpoch[_user][epochNumber]` is non-zero and `pendingInstantWithdraws` is non-zero). Alternatively, clear per-epoch instant ledgers on `collectInstantWithdrawFunds` so the claim path can distinguish funded from unfunded receipts instead of merging them.

### Proof of Concept
Foundry fork sketch (cannot be finalized without confirming CDO-side claim gating):

```solidity
// Epoch N running, instant withdraws enabled with delay.
// 1. user requests instant withdraw A (epoch N)
cdoEpoch.requestInstantWithdraw?  // via CDO -> strategy.requestInstantWithdraw(A, user)
// 2. CDO collects funds only for A: strategy.collectInstantWithdrawFunds(A)
//    pendingInstantWithdraws == 0 now
// 3. user requests instant withdraw B before claims are processed
//    instantWithdrawsRequests[user] == A + B; pendingInstantWithdraws == B
// 4. after delay, CDO calls strategy.claimInstantWithdrawRequest(user)
//    -> _burn(user, A + B); _transferFundedClaim(user, A + B)
// Assert: user received A + B while only A was funded;
//         pendingInstantWithdraws == B with no backing -> next claimant reverts/insolvency.
```

Uncertain points I could not fully verify: the exact CDO-side conditions under which `claimInstantWithdrawRequest` is invoked relative to `collectInstantWithdrawFunds`, and whether `IdleCDOEpochVariant` prevents a second instant request while a claim is pending. If the CDO guarantees atomic fund-then-claim per epoch for all queued receipts, this analog does not hold.

```text
    _onlyIdleCDO();

    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
