### Title
Job variables named `CI_SERVER_TLS_CERT_FILE`/`CI_SERVER_TLS_KEY_FILE`/`CI_SERVER_TLS_CA_FILE` override runner-injected TLS client-cert paths in generated shell scripts - (File: `common/build.go`)

### Summary
`Build.GetAllVariables` concatenates runner-injected TLS variables (from `GetCITLSVariables`) before job-supplied variables (`getNonFeatureFlagJobVariables`), with no key-collision check or reservation list preventing a job variable from reusing an internal key name. Because `BashWriter.Variable`/`PsWriter.Variable` simply emit sequential `export`/`${env:...}` assignments for every variable in order, a job variable with `Key == tls.VariableKeyFile` (i.e. `CI_SERVER_TLS_KEY_FILE`) is exported after the runner's own TLS key export and therefore wins in the final shell environment.

### Finding Description
`Build.getBaseVariablesBeforeJob` appends Runner variables, `GetDefaultVariables()`, then `GetCITLSVariables()` [1](#0-0) . `GetCITLSVariables` emits `spec.Variable{Key: tls.VariableCertFile/tls.VariableKeyFile, ..., Internal: true, File: true}` when the runner has configured TLS auth material [2](#0-1) . `GetAllVariables` then appends `getNonFeatureFlagJobVariables()` — i.e., the raw job-supplied variables, filtered only to exclude feature-flag names, with no filter for reserved/internal key collisions — directly after the "before job" block [3](#0-2) .

The shell writers (`BashWriter.Variable`, and analogously `PsWriter.Variable`) do not consult an `Internal`/protected flag at all; they simply write an `export key=...` (or file-write + export) line for every variable in the slice, in the order supplied [4](#0-3) . There is no deduplication pass applied to the variable list before generating the script — `Variables.Dedup`/`Set`/`OverwriteKey` exist in `common/spec/variables.go` but are not invoked in `GetAllVariables` or in the shell-script-generation path [5](#0-4) . Since bash/PowerShell execute statements sequentially, a later `export CI_SERVER_TLS_KEY_FILE=<attacker path/content>` line silences the earlier runner-issued one for the remainder of the script (including any subsequent internal consumers such as `writeGitSSLConfig`, which reads `build.GetCITLSVariables()` directly rather than the exported environment, but the exported env var itself becomes attacker-controlled for anything else invoking `git`/curl/etc. relying on `$CI_SERVER_TLS_KEY_FILE`) [6](#0-5) .

No allow/deny list on job variable keys was found in `common/build.go`, `common/network.go`, or `common/spec/variables.go` that would prevent a job from defining a variable named `CI_SERVER_TLS_KEY_FILE`, `CI_SERVER_TLS_CERT_FILE`, or `CI_SERVER_TLS_CA_FILE`.

### Impact Explanation
An unprivileged pipeline author can cause the runner-issued TLS client key/cert (used for authenticating to the GitLab server, e.g. for git clone over mTLS) to be silently replaced in the job's shell environment by attacker-controlled content, because the file written to `$CI_SERVER_TLS_KEY_FILE` will contain the job-supplied value instead of the runner's actual private key material path. This is a variable-shadowing/precedence-violation bug: job input overrides a runner-enforced "Internal" variable, breaking the intended precedence in `GetAllVariables`'s own documented contract ("Base variables that come before job variables ... Job variables ... Base variables that come after job variables" — implying "before" should not be overridable by job input for internal variables, but nothing enforces that for exported-env-name collisions).

### Likelihood Explanation
Fully reachable with no special privileges beyond defining a CI/CD job variable with an arbitrary key — a capability every pipeline author has via `.gitlab-ci.yml` `variables:` or the CI/CD variable UI (if not marked "protected" at the project level, which is a project-config choice, not a Runner-side control). Triggered on every job whose runner has TLS client-auth configured (`tls-cert-file`/`tls-key-file` in `config.toml`), which is a fairly standard GitLab Runner TLS setup.

### Recommendation
In `Build.GetAllVariables` (or `getNonFeatureFlagJobVariables`), filter out job-supplied variables whose `Key` collides with any `Internal: true` variable key already present in `getBaseVariablesBeforeJob()`/`getBaseVariablesAfterJob()` (e.g., `tls.VariableCAFile`, `tls.VariableCertFile`, `tls.VariableKeyFile`, and other runner-reserved `CI_*` keys), or re-order/re-apply the before-job block after job variables for keys marked internal, or have the shell writers skip/reject job variables whose key matches a reserved-key set before calling `Variable()`.

### Proof of Concept
Go unit test in `common/build_test.go` or `shells/bash_test.go`:
1. Construct a `Build` with `TLSData.AuthCert`/`TLSData.AuthKey` set (simulating runner TLS config), and `Variables: spec.Variables{{Key: "CI_SERVER_TLS_KEY_FILE", Value: "attacker-key-content", File: true}}`.
2. Call `build.GetAllVariables()` and assert that two entries with `Key == "CI_SERVER_TLS_KEY_FILE"` exist, or (post-fix) assert only the runner one remains.
3. Feed the resulting `Variables` through `NewBashWriter` + `Variable()` for each, call `Finish()`, and grep the resulting script for `export CI_SERVER_TLS_KEY_FILE=`; assert (pre-fix) the **last** occurrence's file content matches `"attacker-key-content"` rather than `build.TLSData.AuthKey`, demonstrating the override.

func (b *Build) getNonFeatureFlagJobVariables() spec.Variables {
	featureFlagNames := make(map[string]bool)
	for _, ff := range featureflags.GetAll() {
		featureFlagNames[ff.Name] = true
	}

	filtered := make(spec.Variables, 0, len(b.Variables))
	for _, variable := range b.Variables {
		if !featureFlagNames[variable.Key] {
			filtered = append(filtered, variable)
		}
	}

	return filtered
}

// GetAllVariables() returns final variables with a consistent precedence order:
// 1. Resolved feature flags (TOML takes precedence over job variables)
// 2. Base variables that come before job variables
// 3. Job variables (excluding feature flags to prevent overriding resolved values)
// 4. Base variables that come after job variables
func (b *Build) GetAllVariables() spec.Variables {
	if b.allVariables != nil {
		return b.allVariables
	}

	// Phase 1: Ensure feature flags have been resolved.
	if b.buildSettings == nil {
		b.Settings()
	}

	variables := make(spec.Variables, 0)

	// Phase 2: Add resolved feature flags first (maintains original precedence order)
	variables = append(variables, b.getResolvedFeatureFlags()...)
	variables = append(variables, b.getBaseVariablesBeforeJob()...)
	variables = append(variables, b.getNonFeatureFlagJobVariables()...)
	variables = append(variables, b.getBaseVariablesAfterJob()...)

func (b *BashWriter) Variable(variable spec.Variable) {
	if variable.File {
		variableFile := b.TmpFile(variable.Key)
		b.Linef("mkdir -p %q", helpers.ToSlash(b.TemporaryPath))
		b.Linef("printf '%%s' %s > %q", b.escape(variable.Value), variableFile)
		b.Linef("export %s=%q", b.escape(variable.Key), variableFile)
	} else {
		if b.isTmpFile(variable.Value) {
			variable.Value = b.cleanPath(variable.Value)
		}
		b.Linef("export %s=%s", b.escape(variable.Key), b.escape(variable.Value))
	}
}

// Set sets newJobVars on the JobVariables, replacing all existing variables with the same key.
// If newJobVars holds variables with the same key, only the last one is set.
func (b *Variables) Set(newJobVars ...Variable) {
	if len(newJobVars) < 1 {
		return
	}

	newVarsByKey := make(map[string]Variable, len(newJobVars))

	for _, v := range newJobVars {
		// for multiple newJobVars with the same key, only keep the last one
		newVarsByKey[v.Key] = v
	}

	*b = slices.DeleteFunc(*b, func(v Variable) bool {
		_, exists := newVarsByKey[v.Key]
		return exists
	})

	for _, v := range newVarsByKey {
		*b = append(*b, v)
	}
}
