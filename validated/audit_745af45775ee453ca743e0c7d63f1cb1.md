### Title
Unauthenticated pipeline run resumption endpoint allows unprivileged actors to inject arbitrary task results and force job-run state transitions - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `PATCH /v2/resume/:runID` endpoint is registered without any authentication middleware and forwards attacker-controlled result data directly into the pipeline run/task-run state machine, mirroring the `restartDca`-class bug: a state-mutating operation that omits the ownership/ authorization checks its sibling authenticated operations (e.g. `/v2/jobs/:ID/runs`) enforce.

### Finding Description
`prc.Resume` is mounted on an explicitly unauthenticated router group: [1](#0-0) 

```
func v2Routes(app chainlink.Application, r *gin.RouterGroup) {
	unauthedv2 := r.Group("/v2")

	prc := PipelineRunsController{app}
	psec := PipelineJobSpecErrorsController{app}
	unauthedv2.PATCH("/resume/:runID", prc.Resume)
```

Compare this to the sibling run-creation endpoint, which requires authentication and the `run` role: [2](#0-1) 

The `Resume` handler parses the path parameter directly into a `taskID`, decodes an attacker-supplied JSON body into a `pipeline.Result`, and passes both straight into `ResumeJobV2` with no ownership check, no verification that the caller is entitled to resume that specific task, and no confirmation that the referenced task is actually in a state that legitimately expects external resumption: [3](#0-2) 

This flows to `ResumeRun`, which calls `UpdateTaskRunResult` (unauthenticated write path) and then restarts the pipeline if applicable: [4](#0-3) 

Like `restartDca`, which duplicates `createDca`'s state-mutation logic but omits the checks (`isGelatoWatching`, existing-DCA check, approvals, price-limit validation) that guard against overwrite/spoofing, this endpoint duplicates the job/run-mutation capability of the authenticated `/v2/jobs/:ID/runs` and `ResumeJobV2` paths but omits authentication and any task-ownership/task-state validation — relying solely on the secrecy of the `taskID` UUID as an implicit bearer credential. There is no code path visible (within what is indexed) that verifies the task is still `pending`/awaiting an async adapter callback before accepting and applying attacker-supplied `Result` data, meaning a caller who obtains or guesses a `taskID` (e.g. via logs, monitoring systems, or a leaked async-task URL) can inject arbitrary success/error values into someone else's job run and force early termination/continuation of that run — a "cross-user response confusion" / "unauthorized job run" outcome, the same class of impact flagged in the report (any user can disrupt another user's task lifecycle without owner consent).

### Impact Explanation
An unprivileged actor who obtains a valid `taskID` (async task UUID) can:
- Inject fabricated `value`/`error` results into another party's job run, corrupting downstream pipeline computations (e.g., price-feed jobs, VRF/keeper-adjacent bridge tasks) — analogous to Eve corrupting/derailing Alice's DCA task in the original report.
- Force premature completion or resumption of a run out-of-band, since the resume path has no visible check that the task is still expecting external input, again mirroring `restartDca`'s missing "already running/expected state" checks.

This is scoped as High/Medium severity because it requires knowledge of the `taskID`, but the endpoint is intentionally unauthenticated by design (this pattern is used for external HTTP adapter callbacks), so the real question is whether adequate compensating controls (task-state validation, single-use enforcement, rate limiting) exist beyond what is visible in the reviewed code.

### Likelihood Explanation
Moderate: `taskID` values are UUIDs, so blind guessing is infeasible, but they are exposed to any bridge/external adapter integrated with the node and could leak via logs, monitoring, or a compromised adapter — at which point exploitation requires only a single unauthenticated HTTP PATCH request, no further authorization checks.

### Recommendation
1. Verify (in code not fully retrievable via the index) whether `UpdateTaskRunResult` validates that the target task run is currently pending/awaiting async resumption before applying the result, and rejects resumption of already-finished or non-async tasks.
2. Consider adding task-scoped, single-use, time-bound tokens rather than relying on the raw task UUID as the sole credential.
3. Add audit-log alerting/rate limiting specific to this unauthenticated route given its sensitivity.
4. Document the intended trust model for this endpoint (bearer-token-like UUID) and add unit/integration tests asserting that resuming a non-pending or already-finished task is rejected.

### Proof of Concept
Conceptual (not verified against a live node due to index limitations):
```
PATCH /v2/resume/<leaked-or-known-task-uuid>
Content-Type: application/json

{"error": "forced failure"}
```
No `Authorization`/session cookie is required because the route is registered under `unauthedv2` — [5](#0-4) . If the referenced task is still pending, this call is accepted and modifies the state of a run the caller does not own, mirroring the unauthorized-state-transition issue in `restartDca`.

**Note:** I could not fully retrieve the complete implementation of `UpdateTaskRunResult` (core/services/pipeline/orm.go, beyond line 168) within the available tool budget, so I cannot confirm or rule out whether it performs task-state validation before applying attacker-supplied results. This should be verified directly in the repository (a Devin session with full file access could inspect `UpdateTaskRunResult` in `core/services/pipeline/orm.go` in its entirety) before treating this as a confirmed exploitable gap versus an accepted design trade-off.

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```

```go
func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
```
