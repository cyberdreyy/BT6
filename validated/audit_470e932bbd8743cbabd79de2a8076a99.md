### Title
Stale per-epoch instant-withdraw basis escapes the default haircut and drains the recovery reserve at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The util-linux bug is a stale cached pointer: a prober stores a raw pointer into a realloc'd array, so the pointer still "works" but no longer refers to the allocation it was captured from. The direct analog in `IdleCreditVault` is the instant-withdraw receipt accounting: claim amounts are cached globally per user (`instantWithdrawsRequests`), but the default-recovery claim basis is indexed only by the *current* epoch (`instantWithdrawClaimsByEpoch[epochNumber]`). When an instant receipt survives unfunded across an epoch boundary, the aggregate still pays it out, while the recovery basis computed at `finalizeDefaultRecovery` silently excludes it — the old receipt is a "stale pointer" into an epoch bucket that is no longer referenced.

### Finding Description
`requestInstantWithdraw` records receipts both globally and per epoch, and bumps the global `pendingInstantWithdraws` counter: [1](#0-0) 

`defaultPendingClaimBasis` adds instant claims to the default basis only for `instantWithdrawClaimsByEpoch[epochNumber]`, i.e. the *current* epoch at finalization: [2](#0-1) 

The symmetric problem exists in `_defaultPrefundedInstantReserve`: it compares the *global* `pendingInstantWithdraws` (which includes unfunded receipts from older epochs) against the *current-epoch* `instantWithdrawClaimsByEpoch`. If old unfunded receipts make `pendingInstant >= instantBasis`, `prefundedReserve` is computed as 0 even though the strategy may already hold underlying collected for the old receipts, and those old claims are never added to `basis`: [3](#0-2) 

After finalization, `claimInstantWithdrawRequest` clears only the `defaultRecoveryEpoch` slice at the haircut price, then pays the *remaining aggregate* `instantWithdrawsRequests[_user]` — which still contains the older-epoch receipts — at par via `_transferFundedClaim`, drawn from the same strategy underlying balance that backs `defaultRecoveryReserve`: [4](#0-3) [5](#0-4) 

So an old-epoch instant receipt is excluded from `totalBasis` (no haircut was provisioned for it) yet is paid 1:1, consuming reserve/funded underlying priced for other claimants at `defaultRecoveryPrice < 1e18`.

### Impact Explanation
Direct theft / reserve insolvency. The holder of a stale pre-default-epoch instant receipt claims `amount` at par, while `defaultRecoveryReserve` was sized as `recoveryPrice * (activeBasis + pendingBasis)` with that receipt excluded from `pendingBasis`. Every wei paid to the stale receipt is a wei removed from the pool backing other defaulted receipts and active tranche holders. With `defaultRecoveryPrice` at e.g. 50%, a stale receipt of size `X` extracts `X` instead of the `0.5X` it should have shared in, and the shortfall is borne pro-rata by all remaining claimants (or the last claimants' transfers revert — permanent freezing of unclaimed recovery).

### Likelihood Explanation
Requires an instant-withdraw-enabled vault where an instant receipt is requested, only partially funded via `collectInstantWithdrawFunds` (so `pendingInstantWithdraws > 0` persists across an epoch roll), and the borrower then defaults with `finalizeDefaultRecovery` called in a later epoch than the request. The attacker is an ordinary KYC'd lender/tranche holder; all privileged calls (startEpoch, stopEpoch, finalize) are performed honestly by manager/owner. Sequencing is realistic: instant requests are serviced FCFS from whatever the borrower returned, so a partially funded queue carrying into a defaulted epoch is a normal operating state, not an edge case.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, sum `instantWithdrawClaimsByEpoch` over all epochs with outstanding receipts (or maintain a global `instantClaimBasis` counter alongside the per-epoch map) so unfunded instant claims from *any* epoch enter the recovery basis. In `claimInstantWithdrawRequest`, route all pre-default instant receipts (not just `defaultRecoveryEpoch`) through `_claimDefaultedInstantWithdrawRequest` at `defaultRecoveryPrice`, leaving only post-default receipts on the par path.

### Proof of Concept
Foundry fork-style PoC (against `test/foundry/IdleCreditVault.t.sol` harness conventions; must be validated in a session):

```solidity
function testStaleEpochInstantReceiptDrainsRecovery() external {
    // instant-withdraw mode vault
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _depositWithUser(attacker, amount, true);

    // Epoch 0: attacker requests instant withdraw; borrower returns only part.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(amount / 2);   // instantWithdrawsRequestsByEpoch[attacker][0]
    _startEpochAndCheckPrices(0);
    // CDO collects only half of the instant basis -> pendingInstantWithdraws stays > 0
    deal(defaultUnderlying, borrower, partial);
    // ... borrower repays partial; collectInstantWithdrawFunds pulls < requested ...

    // Epoch 1 rolls; a second user files a normal/instant request in epoch 1.
    _startEpochAndCheckPrices(1);

    // Borrower defaults in epoch 1; owner/manager finalize honestly.
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    vm.prank(manager);
    cdoEpoch.finalizeDefault(); // -> strategy.finalizeDefaultRecovery(...)

    // BUG: basis included only instantWithdrawClaimsByEpoch[1].
    // Attacker's epoch-0 receipt was excluded from the haircut but is still
    // in instantWithdrawsRequests[attacker].

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // Attacker paid ~par on the epoch-0 receipt while honest claimants
    // only recover defaultRecoveryPrice on their basis.
    assertApproxEqAbs(paid, epoch0Receipt, 1e8);
    // Reserve is now under-backed: last claimant reverts or recovers less
    // than claimBasis * defaultRecoveryPrice / 1e18.
}
```

Caveat: I was unable to fully verify the internals of `_transferFundedClaim`/`_transferDefaultRecovery` (whether they share the same underlying balance source) and the exact conditions under which `requestInstantWithdraw`/`collectInstantWithdrawFunds` leave a persistent `pendingInstantWithdraws` across epoch rolls; the PoC should be executed against the full repo to confirm the reserve drain end-to-end.

    _onlyIdleCDO();

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
