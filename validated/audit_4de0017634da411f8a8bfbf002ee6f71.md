### Title
Stale/Double-Counted Signer Weight in `StackerDBListener` Rejection Tally Can Wedge Legitimate Block Broadcasting - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tallies signer weight into two independently-guarded counters, `total_weight_approved` and `total_weight_rejected`, one per `BlockResponse` kind. The guard that prevents double-counting a rejection (`responded_signers.insert(slot_id)`) is never cleared or reconciled when the *same* signer later sends an `Accepted` response for the same block. As a result, a signer that first rejects and later legitimately signs (a `LocallyRejected -> LocallyAccepted` re-evaluation the signer protocol explicitly allows) has its weight counted in **both** totals simultaneously, permanently inflating `total_weight_rejected` with weight that no longer represents a live rejection.

### Finding Description
`handle_stackerdb_chunk` processes `BlockResponse::Accepted` and `BlockResponse::Rejected` messages with two separate, uncoordinated guards:

Accepted branch — guarded only by `gathered_signatures`: [1](#0-0) 

Rejected branch — guarded only by `responded_signers`: [2](#0-1) 

Note that the Accepted branch also unconditionally inserts into `responded_signers` (line 465), but the Rejected branch never removes a slot from `responded_signers` nor decrements `total_weight_rejected` when that same slot subsequently shows up as an `Accepted` response. Concretely:

1. Signer S (slot `k`, weight `w`) sends `Rejected` for block `B`. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
2. S re-evaluates (a transition the signer state machine explicitly documents as valid: `LocallyRejected --> LocallyAccepted : re-evaluated`) and later sends `Accepted` for the same `B`.
3. The Accepted branch only checks `gathered_signatures`, which does not yet contain `k` → `total_weight_approved += w` as well.

The signer's weight `w` is now counted in *both* `total_weight_approved` and `total_weight_rejected`. `total_weight_rejected` is stale and never corrected, because nothing in this code path treats a later acceptance as retracting an earlier rejection tally.

This directly parallels the referenced report's root cause: two quantities (deposit fee, withdrawal fee; here approve-weight, reject-weight) are each bounded/guarded individually, but their combination is never checked against the true invariant (a signer's weight should count toward at most one live outcome, and `approved + rejected` should never both approach 100% off overlapping weight).

### Impact Explanation
The miner's `SigningCoordinator::wait_for_signer_signature`/`get_stackerdb_signer_signatures` loop consumes these exact counters to make an accept/reject decision: [3](#0-2) 

Because `total_weight_rejected` can retain stale weight from a signer who has since legitimately accepted, the `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` ("blocking minority reached") condition can fire, or persist as firing, even though real signer sentiment no longer supports rejection. This causes the miner to prematurely conclude `NakamotoNodeError::SignersRejected` for a block that in fact has (or would have) legitimate 70% approval — a liveness wedge on block production that stems purely from a miscounted/aggregated weight value diverging from the verified/live set of accepts, matching the allowed "aggregated weight vs verified accepts" equality-break class. It can also permanently or temporarily exclude transactions (`permanently_excluded_txids`/`temporarily_excluded_txids`) based on this inflated rejection tally.

### Likelihood Explanation
This requires no majority collusion, no key compromise, and no malicious signer: it is triggered by a single signer legitimately changing its mind on a block, a scenario the signer state machine explicitly supports (`docs/signer-flows.md` documents `LocallyRejected --> LocallyAccepted: re-evaluated` as a normal transition), combined with ordinary network/gossip delivery ordering (reject arriving before the later accept). Any signer whose validation initially fails transiently (e.g., timing/tip-related chainstate re-check) and later passes can produce this ordering.

### Recommendation
When an `Accepted` message is processed for a slot that is already present in `responded_signers` due to a prior `Rejected`, retract that signer's weight from `total_weight_rejected` (and from any per-txid `failed_txids` weight it contributed) before adding it to `total_weight_approved`, so a signer's weight is attributed to exactly one live outcome. Alternatively, key both counters off `gathered_signatures`/`rejected_signers`-style keyed maps rather than raw counters, and recompute totals as the sum over disjoint, mutually-exclusive per-signer state so `approved + rejected <= total_weight` is an enforced invariant.

### Proof of Concept
1. Set up a `StackerDBListener` tracking a block `B` with `weight_threshold` = 70% of `total_weight`.
2. Deliver a `BlockResponse::Rejected` from signer S (weight `w`) for `B` — `total_weight_rejected` becomes `w`.
3. Deliver a `BlockResponse::Accepted` from the same signer S for the same `B` (representing S's honest re-evaluation flip) — `total_weight_approved` becomes `w` as well, while `total_weight_rejected` remains `w` (never decremented).
4. Repeat/accumulate with other signers such that `total_weight_rejected.saturating_add(weight_threshold) > total_weight` becomes true purely because of `w`'s stale double count, even though the true, current sentiment (accounting for S's flip) would not cross the rejection threshold.
5. `wait_for_signer_signature` returns `Err(NakamotoNodeError::SignersRejected{...})`, aborting a block that legitimately could/would reach the acceptance threshold — demonstrating the miscounted-response wedge.
