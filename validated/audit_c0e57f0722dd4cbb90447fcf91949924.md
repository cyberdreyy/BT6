Stale confirmations from removed multisig members remain counted toward the approval threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges pending requests that were *originated* by the removed member; it never scans the `confirmations` map to strip confirmation entries that the removed member cast on *other* still-pending requests as a confirmer. `confirm()` then authorizes execution purely by comparing `confirmations.len() + 1 >= num_confirmations` [1](#0-0) , with no re-validation that every entry in the stored `HashSet<String>` still corresponds to a live member. This breaks the intended binding: `num_confirmations` from currently valid members == threshold required to execute a request.

### Finding Description
`MultiSigContract` stores confirmations per request as a `LookupMap<RequestId, HashSet<String>>` keyed by member identity strings [2](#0-1) . When a member confirms a request that they did not create, their identity string is inserted into that request's `HashSet` [3](#0-2) .

`delete_member` removes the departing member from `self.members`, revokes their access key/entry, and deletes only the requests where `r.member == member` (i.e., requests they personally originated) [4](#0-3) . It does not iterate `self.confirmations` to remove the departing member's string from confirmation sets of requests that other members originated but which this member had already confirmed. Consequently, any pending request that the soon-to-be-removed member confirmed (but did not create) retains that confirmation in the `HashSet` even after the member is deleted.

`confirm()` decides whether to execute a request solely by counting set length: `if confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) . It never re-checks that each string already present in the set still corresponds to `self.members.contains(...)`. So a stale confirmation from an account/key that is no longer a member is treated as equivalent to a live member's confirmation.

### Impact Explanation
This lets a multisig request execute (transfers, `AddKey`, `FunctionCall`, etc.) with fewer *currently authorized* confirmations than `num_confirmations` requires, because one or more of the counted confirmations came from a member who has since been removed. This is a "multisig request executed below threshold" outcome — an unauthorized action moves funds or changes contract keys/state without the number of live approvals the owners configured, which is explicitly a Critical-severity custody-binding violation per the threshold vs. confirming-members equality that the contract is supposed to enforce.

### Likelihood Explanation
No privileged access or off-chain compromise is needed: this occurs through entirely permitted multisig operations — a member confirms a pending request, is later removed via a normal `DeleteMember` action (itself approved through the multisig), and the stale confirmation persists. Any request left pending across a membership change is susceptible; the timing dependency (a request must be confirmed-but-unexecuted when the confirmer is removed) makes this moderately likely in active multisigs with member churn, and it requires no attacker-controlled deployment parameters or malicious validators.

### Recommendation
When executing `DeleteMember` (and the analogous `DeleteKey` action in `multisig/src/lib.rs`), scan `self.confirmations` for all requests and remove the departing member's identity string from every confirmation set, not just requests they originated. Alternatively, when evaluating the count in `confirm()`, filter the stored confirmation set against `self.members` (or an equivalent live-membership check) before comparing its length to `num_confirmations`, so that only confirmations from currently valid members are counted toward the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 3)`.
2. Member `E` (originator) is not needed; assume member `A` calls `add_request` to create request `R` with a `Transfer` action, `A` auto-confirms via `add_request_and_confirm` (1 confirmation).
3. Member `B` calls `confirm(R)` — 2 confirmations, request not yet executed (`2 < 3`).
4. Separately, a `DeleteMember { member: B }` request is created and confirmed by 3 other members, executing `delete_member` for `B`: `B` is removed from `self.members` and its access key revoked, but request `R` (originated by `A`, only confirmed by `B` as a non-originator) is untouched, per [5](#0-4)  which only deletes requests where `r.member == B`.
5. Member `C` calls `confirm(R)`: `confirmations.len()` is still `2` (A, B) plus the new one from `C` = `3 >= num_confirmations(3)` → the request executes [1](#0-0) , even though `B` is no longer a member and only `A` and `C` are currently live confirmers (2 live confirmations, below the configured threshold of 3).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {

        }
