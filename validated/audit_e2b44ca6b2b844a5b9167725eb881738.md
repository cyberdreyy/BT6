### Title
Multisig executes requests counting confirmations from removed members, allowing execution below the true live-member threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
`confirm` counts entries in the `confirmations: LookupMap<RequestId, HashSet<...>>` set for a request against `num_confirmations` without verifying that each entry belongs to a currently active member. `delete_member` (multisig2) and the `DeleteKey` action handler (multisig) only clean up requests *originated by* the removed member/key (`r.member == member` / `r.signer_pk == pk`); they never scan and purge that member's/key's confirmations recorded on *other* outstanding requests. As a result, a confirmation cast by a member before removal remains in the `confirmations` set of any request the member did not originate, and later still counts toward the threshold.

### Finding Description
In `multisig2/src/lib.rs`, `confirm` is: [1](#0-0) 
and `assert_valid_request` only checks that the *caller* is a current member, never that stored confirmations belong to current members: [2](#0-1) 

`delete_member` purges only requests where `r.member == member` (i.e. requests the removed member itself created), and removes their `num_requests_pk` entry, but does not touch `self.confirmations` for requests created by other members that the removed member had already confirmed: [3](#0-2) 

The same gap exists in the legacy `multisig/src/lib.rs`, where the `DeleteKey` action only removes requests signed (`added`) by that key, not confirmations left by that key on other requests: [4](#0-3) 

The invariant that should hold is: `confirmations.len()` counted toward `num_confirmations` should equal the number of *live* members who confirmed. Instead the code holds the weaker, broken invariant: `confirmations.len()` equals the number of confirmations ever cast, regardless of subsequent membership changes.

### Impact Explanation
This breaks the multisig's core authorization guarantee: a `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` request can execute with only `num_confirmations - 1` (or fewer) *live* member confirmations, because a stale confirmation from a member removed in the interim (e.g. because their key was compromised or they were considered untrustworthy — the very reason `DeleteMember`/`DeleteKey` exists) still counts. This is exactly the "multisig request executed below threshold" Critical impact category: NEAR can be moved, keys added, or contract code deployed by fewer genuinely-authorized parties than the configured `num_confirmations` intends.

### Likelihood Explanation
No special privilege is required beyond being (at some point) a legitimate multisig member — this is the normal, expected life-cycle of key/member rotation (removing a member/key because it's compromised or the person left). The only requirement is ordering: a confirmation on request A precedes removal of that confirming member via request B, and request A is later completed by other members. This is a realistic operational sequence, not a contrived edge case.

### Recommendation
When removing a member/key (`delete_member` in multisig2, `DeleteKey` handling in multisig), iterate over all entries in `self.confirmations` (not just requests originated by that member/key) and remove the departing member's/key's entry from every confirmation set. Alternatively, re-validate at `confirm`/execution time that every principal recorded in a request's confirmation set is still a current member, discarding stale entries (and recomputing whether the threshold is actually met) before scheduling execution.

### Proof of Concept
Using `multisig2` with 3 members `A, B, C` and `num_confirmations = 2`:
1. `B` calls `add_request` for `MultiSigRequestAction::Transfer { amount }` targeting some receiver → creates request `R1` (member = B, confirmations = {}).
2. `A` calls `confirm(R1)` → `confirmations(R1) = {A}` (1 < 2, not yet executed).
3. Separately, `C` creates request `R2 = DeleteMember { member: A }` (because `A`'s key is now considered compromised/untrusted) and it gets the required 2 confirmations from `B` and `C` → `delete_member` executes, removing `A` from `self.members`. Because `R1.member == B`, not `A`, `R1` and its confirmation set `{A}` are left untouched by `delete_member`.
4. `B` calls `confirm(R1)`. `assert_valid_request` passes because `B` is a live member. `confirmations(R1)` becomes `{A} ∪ {B}`, and the check `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `1 + 1 >= 2` → true, so `R1` executes and the `Transfer` is sent — even though `A` is no longer a member and only one currently-live member (`B`) actually approved it in real time.     /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);

        }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());

            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
