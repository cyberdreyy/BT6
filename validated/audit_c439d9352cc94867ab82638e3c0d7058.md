### Title
Loss-adjusted withdraw receipts escape the haircut because `lossRecoveryPriceByEpoch` is keyed on the post-increment `epochNumber` while requests/claims are keyed on `lastWithdrawRequest` — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The dangling-symlink bug class — "the guard resolves the nearest *existing* ancestor and treats a not-yet-materialized leaf as safe" — maps here to how loss haircuts are attached to withdraw receipts. `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` (the epoch at funding time), but `requestWithdraw`'s escape guard and `_claimLossAdjustedWithdrawRequest` look it up under `lastWithdrawRequest[_user]` (the epoch at request time). Because `deposit()` increments `epochNumber` during `stopEpoch` before the funded amount is collected, the haircut is stored under a *different* epoch key than the one every lookup uses, so the loss-adjusted receipt "dangles" and is claimed at par.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` records `lastWithdrawRequest[_user] = epochNumber` and `withdrawsRequestsByEpoch[_user][epochNumber] += _amount` at request time (lines 282, 293).
- The escape guard only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 261–271).
- `_claimLossAdjustedWithdrawRequest` likewise only reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and returns early when it is zero, falling through to `_claimFundedWithdrawRequest` which pays `withdrawsRequests[_user]` **at par** via `_transferFundedClaim` (lines 789–801, 338–349).
- `collectWithdrawFunds` stores the haircut as `lossRecoveryPriceByEpoch[epochNumber]` — using `epochNumber` at *collect* time (line 421).

`epochNumber` is incremented inside `deposit()` whenever the deposit happens while the epoch is still running — i.e., during the borrower-repayment deposit inside `stopEpoch` (lines 607–610: "deposit done on stopEpoch … epochNumber += 1"). Funding for pending receipts is sourced from the borrower/strategy during that same `stopEpoch` (`collectWithdrawFunds` is invoked by the CDO after repayment is collected), so `epochNumber` has already been bumped from `E` to `E+1` when `lossRecoveryPriceByEpoch[epochNumber]` is written. Result: the haircut lives at index `E+1`, while every guard and claim lookup reads index `E`.

Consequences:

1. A user who requested a withdraw in epoch `E` and whose receipt was loss-adjusted (borrower underfunded via `stopEpochWithDuration`/`stopEpoch` with `_lossAmount`, so `collectWithdrawFunds(_amount < pendingBasis)`) can call `claimWithdrawRequest` in epoch `E+1` (the gate `epochNumber <= lastWithdrawRequest[_user]` passes since `E+1 > E`). `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[E] == 0`, returns 0, and `_claimFundedWithdrawRequest` pays the full `withdrawsRequests[_user]` at par — even though the strategy only pulled `pendingBasis − loss` of underlying.
2. The same indexing gap neuters the `requestWithdraw` guard: `lossRecoveryPriceByEpoch[E] == 0`, so the `NotAllowed` revert at lines 263–271 never triggers, letting the user stack new requests while the stale per-epoch receipt (`withdrawsRequestsByEpoch[_user][E]`) is never cleared.

Broken invariant: one receipt, one haircut-adjusted payout / loss socialization. The unfunded difference `(1 − lossRecoveryPrice) × claimBasis` is paid out of underlying belonging to other claimants and the default-recovery reserve.

### Impact Explanation
Direct theft / insolvency. Each escaping receipt withdraws `claimBasis` instead of `claimBasis × lossRecoveryPrice`. The strategy's underlying balance only received the haircutted amount, so the extra `(1 − p) × claimBasis` comes from funds reserved for other funded receipts or, when `defaultRecoveryReserve != 0`, is only bounded by the balance-vs-reserve check in `_transferFundedClaim` (lines 899–905) — which protects the reserve but not other users' claims. Late claimants' receipts become unpayable (permanent freezing of unclaimed withdrawals), or the first claimer extracts more than funded at other users' expense.

### Likelihood Explanation
Requires a partial-loss `stopEpoch` (`collectWithdrawFunds` with `_amount < pendingBasis`) while pending receipts exist — the exact scenario `previewLossAdjustedWithdrawFunds` (lines 440–460) is built for. The attacker is an ordinary KYC-passed tranche holder who made a normal `requestWithdraw`; no privileged collusion needed beyond the honest manager/borrower flow of an underfunded epoch stop. **Caveat:** the finding hinges on `collectWithdrawFunds` being invoked by `IdleCDOEpochVariant.stopEpoch` *after* the `deposit()` call that bumps `epochNumber` (the code comment at lines 607–610 states the increment happens on the stopEpoch deposit, and receipt funding necessarily follows repayment collection, but I could not verify the exact call order inside `stopEpoch` within my iteration budget). If the CDO calls `collectWithdrawFunds` before the epoch-bumping deposit, the indices align and this specific escape closes — a PoC should confirm the ordering first. The structural issue (per-epoch haircut storage keyed on a mutable global counter vs. lookups keyed on a per-user stale pointer) is real regardless.

### Recommendation
Key `lossRecoveryPriceByEpoch` under the epoch the receipts were tagged with, not the post-stop counter: e.g., store `lossRecoveryPriceByEpoch[epochNumber − 1]` (or capture `epochNumber` before the stopEpoch deposit increments it), matching `lastWithdrawRequest`/`withdrawsRequestsByEpoch` semantics. Alternatively, have `requestWithdraw` tag receipts with `epochNumber + 1` (consistent with the queue's `epochPendingWithdrawals` convention in `IdleCDOEpochQueue.sol`, which attributes requests to the next epoch). Add a regression test: request in epoch `E`, `stopEpoch` with a partial loss, then claim in `E+1` and assert the payout equals `amount × lossRecoveryPrice / RECOVERY_FULL` and that a new `requestWithdraw` before claiming reverts.

### Proof of Concept
Foundry sketch (fork/test harness style of `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptClaimsAtPar() external {
    // user deposits and requests withdraw during running epoch E
    uint256 amountWei = 10_000 * ONE_SCALE;
    address user = makeAddr("user");
    uint256 tranches = _depositWithUser(user, amountWei, true);
    vm.prank(user);
    cdoEpoch.requestWithdraw(tranches, address(AAtranche)); // lastWithdrawRequest[user] = E

    _startEpochAndCheckPrices(0);

    // stopEpoch with a loss: borrower underfunds pendingWithdraws
    // -> deposit() bumps epochNumber to E+1, collectWithdrawFunds stores
    //    lossRecoveryPriceByEpoch[E+1] while receipt lives under E
    uint256 expectedInterest = cdoEpoch.expectedEpochInterest();
    deal(defaultUnderlying, borrower, expectedInterest); // interest only, no principal for pending
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, lossAmount); // partial loss path

    // claim: _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[E] == 0,
    // funded path pays withdrawsRequests[user] at par
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user) - balPre;

    uint256 haircut = tranches * strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()) / 1e18;
    assertGt(paid, haircut); // BUG: paid at par instead of haircutted
}
```

If the assert fails because the keys align (i.e., `collectWithdrawFunds` runs before the `epochNumber` increment), the ordering assumption is disproven and this specific analog does not hold.
