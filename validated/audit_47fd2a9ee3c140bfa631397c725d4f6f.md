### Title
Malicious approved depositor can permanently lock a receiver's vault units via repeated `deposit()`/`mint()` calls - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2._syncDeposit` unconditionally overwrites `userUnitsRefundableUntil[receiver]` every time a sync deposit is made for that receiver, and `deposit()`/`mint()` allow any address the receiver has approved via `setDepositReceiverApproval` to make deposits *for* that receiver. Because `MultiDepositorVault._update` and `ProvisionerV2.redeem/withdraw/requestRedeem` all gate on `areUserUnitsLocked(user)`, an approved depositor can keep resetting the receiver's lock indefinitely with trivial dust deposits, permanently blocking the receiver from transferring, redeeming, or withdrawing their own vault units. This mirrors the Golom `VoteEscrowCore` finding where a trusted third party (`voter`) could repeatedly call `voting()`/`attach()` to keep a token perpetually locked against the owner's will.

### Finding Description
`ProvisionerV2.deposit()`/`mint()` are `anyoneButVault` functions guarded only by `_requireValidReceiver`: [1](#0-0) 

which allows `msg.sender != receiver` as long as `depositReceiverApprovals[receiver][msg.sender]` is true — a flag the receiver sets themselves via `setDepositReceiverApproval`: [2](#0-1) 

Every successful sync deposit (from `deposit()` or `mint()`) routes through `_syncDeposit`, which unconditionally sets the *receiver's* lock timestamp to `block.timestamp + depositRefundTimeout`, regardless of who is calling: [3](#0-2) 

This lock is enforced in three separate exit paths, all keyed on the affected user's address, not the depositor's:
- `MultiDepositorVault._update` blocks any transfer where `from` is locked (this includes ordinary ERC20 `transfer`/`transferFrom` of vault units, since `provisioner.areUserUnitsLocked(from)` is checked for every non-mint/non-burn transfer): [4](#0-3) 
- `ProvisionerV2.redeem()` and `withdraw()` explicitly require `userUnitsRefundableUntil[msg.sender] < block.timestamp`: [5](#0-4) [6](#0-5) 
- `ProvisionerV2.requestRedeem()` calls `safeTransferFrom(msg.sender, address(this), unitsIn)` on the vault's unit token, which triggers the same `_update`/`areUserUnitsLocked` check with `from = msg.sender` (the victim): [7](#0-6) 

Because `areUserUnitsLocked` returns true as long as `userUnitsRefundableUntil[user] >= block.timestamp`, and this timestamp can be re-armed at will by any address the user once approved, an approved depositor can perpetually keep the receiver's units locked by re-depositing a tiny amount before each `depositRefundTimeout` window expires: [8](#0-7) 

All three of the receiver's exit routes (ERC20 transfer, sync redeem/withdraw, async requestRedeem) are blocked simultaneously — the receiver has no path to move their own units while the malicious depositor keeps refreshing the lock. This is the direct analog of the Golom `VoteEscrowCore` bug: a party the user trusted (there, a `voter`; here, an approved `depositor`) repeatedly invokes an ordinary, unprivileged function (`voting()`/`attach()` there; `deposit()`/`mint()` here) whose side effect is to reset a lock/attachment flag tied to the victim's own asset, with no cap on how many times or how long this can be repeated, and no way for the victim to unilaterally clear it once the approval was granted (the approval itself can be revoked by the victim, but the lock is already re-armed for the current window and the depositor can race any revocation attempt in the same block/period).

### Impact Explanation
The receiver's vault units (their share of the vault's underlying assets) become frozen: no transfer, no sync redeem/withdraw, and no async redeem request can succeed while the lock is kept active. This is a freezing-of-user-funds condition against `MultiDepositorVault`/`ProvisionerV2`, which are the core deployed/bounty-listed vault contracts. Depending on how aggressively the malicious depositor refreshes the lock relative to `depositRefundTimeout`, this can be sustained indefinitely at negligible cost (dust `tokensIn` deposits), constituting at minimum a repeated temporary freeze and, if sustained continuously, a de facto permanent freeze of the victim's funds.

### Likelihood Explanation
Requires one precondition entirely under the victim's control at setup time but exploitable later if trust is misplaced or the approved address is compromised: the victim must have called `setDepositReceiverApproval(attacker, true)` at some point (e.g., to allow a relayer, custodial helper, or third-party integrator to deposit on their behalf — a legitimate, expected use of the feature). Once approved, the attack itself requires no special privileges, no oracle manipulation, and minimal capital (the attacker only needs enough tokens to produce `unitsOut >= 1` each cycle, floor-rounded). This is fully within an ordinary user's transaction capability using only public, unprivileged entry points (`deposit`/`mint`), matching the "external circumstance + high impact" profile of the referenced Medium-severity Golom finding.

### Recommendation
Decouple the deposit-refund lock from arbitrary third-party deposits on behalf of a receiver:
- Only extend/set `userUnitsRefundableUntil[receiver]` for the amount being deposited in that specific call (e.g., track lock per-deposit-hash rather than a single overwritable per-user timestamp), so a new deposit cannot silently re-lock previously depositable/withdrawable units.
- Alternatively, disallow `deposit()`/`mint()` calls where `msg.sender != receiver` from extending an existing, still-active lock — i.e., only set `userUnitsRefundableUntil[receiver]` if `block.timestamp >= userUnitsRefundableUntil[receiver]` (not already locked), or scope the refund-lock check independently per depositor rather than solely per receiver.
- Ensure `redeem`/`withdraw`/`requestRedeem`/ERC20 transfer restrictions cannot be perpetually re-armed by a third party the user approved only for deposits, not for locking control.

### Proof of Concept
Local Foundry fork steps:
1. Deploy/fork the `MultiDepositorVault` + `ProvisionerV2` setup with sync deposits enabled for a test token, and a nonzero `depositRefundTimeout`.
2. As `victim`, call `setDepositReceiverApproval(attacker, true)`.
3. As `attacker`, call `deposit(token, dustTokensIn, 1, victim)` — assert `provisioner.areUserUnitsLocked(victim) == true` and `userUnitsRefundableUntil[victim] == block.timestamp + depositRefundTimeout`.
4. As `victim`, attempt `vaultUnits.transfer(someone, amount)` — assert it reverts with `Aera__UnitsLocked()`.
5. As `victim`, attempt `provisioner.redeem(token, unitsIn, minTokensOut, victim)` — assert it reverts with `Aera__UnitsLocked()`.
6. As `victim`, attempt `provisioner.requestRedeem(token, unitsIn, minTokensOut, tip, deadline, maxPriceAge, false, victim)` — assert it reverts (via the underlying `safeTransferFrom` triggering `MultiDepositorVault._update`'s lock check).
7. Warp time to just before `depositRefundTimeout` expires; as `attacker`, repeat step 3 with another dust deposit — assert the lock is renewed and steps 4-6 continue to revert indefinitely across multiple `depositRefundTimeout` windows.

    /// @notice Handles a synchronous deposit, records the deposit hash, and enters the vault
    /// @dev Reverts if the deposit hash already exists. Sets the refundable period for the user
    /// @param token The ERC20 token to deposit
    /// @param tokenAmount The amount of tokens to deposit
    /// @param unitAmount The amount of vault units to mint for the user
    /// @param receiver The address receiving the minted units
    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }
