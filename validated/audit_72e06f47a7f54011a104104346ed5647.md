### Title
Bridge cache fallback ignores requestData, allowing cross-request response confusion - ([File: core/bridges/cache.go], [File: core/services/pipeline/task.bridge.go])

### Summary
`Cache.GetCachedResponse`/`UpsertBridgeResponse` key solely on `(dotId, specId)` via `responseKey` and never incorporate the request payload, and `BridgeTask.resolveFailureOrCache` blindly serves whatever is cached for that key as the failed run's `Result.Value`. For any job spec whose bridge task can be invoked with different `requestData` across runs (e.g. Direct Request/`oracleRequest`-triggered jobs where any on-chain caller supplies request parameters merged into `requestData` via CBOR-parsed job-spec vars), one triggering party's successfully-cached response body can be replayed into a different triggering party's run when the live bridge call fails.

### Finding Description
`Cache.setValue`/`latestValue` and the persisted table are addressed by `responseKey(dotId, specId)` only [1](#0-0) , and both `GetCachedResponse` and `UpsertBridgeResponse` never take or check the request payload that produced the cached value [2](#0-1) . In `BridgeTask.Run`, on a successful live call the response is unconditionally upserted keyed by `(t.dotID, t.specID)` regardless of what `requestData` produced it [3](#0-2) . On failure, `resolveFailureOrCache` calls `t.orm.GetCachedResponse(ctx, t.dotID, t.specID, ttl)` and, if a value is present, substitutes it as the task output without any binding to the current run's `requestData` [4](#0-3) . This breaks the "response must correspond only to the request that produced it" invariant whenever the same `dotId`/`specId` is shared across runs carrying materially different `requestData`.

In this codebase specifically, the webhook job type (the mechanism by which an EI credential holder could merge an arbitrary HTTP body into `requestData` via `jobRun.requestBody`) has been removed: `PipelineRunsController.Create` rejects any UUID-style job ID with `job.ErrJobTypeRemoved` [5](#0-4) , and inserting/running a webhook spec via the DB directly is likewise rejected at the pipeline layer in integration tests [6](#0-5) . Similarly, the run-role trigger (`RunJobV2`, reachable from GraphQL `RunJob` and the REST `Create` endpoint for authenticated users) only forwards a `meta` map into `jobRun.meta`; it never accepts or forwards attacker-supplied `requestData` [7](#0-6) , and `RunJobV2` is additionally disabled in secure/production builds [8](#0-7) . Therefore the specific attacker path described in the question (EI webhook body or run-role trigger supplying arbitrary `requestData`) is **not reachable** in this codebase version — both entry points are blocked before ever reaching `BridgeTask.Run`.

The underlying code defect (cache keyed without request binding) remains real and would be exploitable for any job type that both (a) shares a single job spec/dotID across multiple untrusted triggering identities and (b) allows those identities to influence `requestData` per run (e.g. Direct Request "run log" jobs driven by on-chain `oracleRequest` calls with attacker-supplied CBOR parameters). However, no such currently-reachable, unprivileged, per-run-varying-`requestData` trigger for a *shared* job spec is confirmed in the parts of the codebase inspected, and confirming the Direct Request pipeline-vars wiring in this repo would require further investigation beyond the scope of what was traced.

### Impact Explanation
If a reachable multi-identity trigger with varying `requestData` existed for a shared job/dotID, this would allow cross-user response confusion — attacker-controlled data injected into another triggering identity's job run output, as described. Given the confirmed removal of the webhook path and the meta-only nature of the run-role trigger, the specific exploit chain in the question is not currently reachable by an unprivileged attacker in this codebase.

### Likelihood Explanation
Low/not demonstrated for this codebase version: both concrete entry points named in the question (EI webhook `requestData` merge, run-role trigger `requestData` injection) are blocked — webhook job type returns `ErrJobTypeRemoved`, and `RunJobV2` only forwards `meta`, not `requestData`, and is disabled in production builds.

### Recommendation
Independent of reachability today, harden the cache to bind responses to their originating request: include a hash of the normalized `requestData` (and/or bridge name) in `responseKey`/the cache row key, or store and compare a `requestData` fingerprint before serving a cached fallback in `resolveFailureOrCache`, so cache hits can only ever be served for requests with matching payloads.

### Proof of Concept
Not applicable — the required precondition (attacker-controlled `requestData` reaching a shared job's `BridgeTask.Run` across distinct triggering identities) could not be confirmed as reachable via any currently-enabled, unprivileged trigger path in this codebase (webhook removed; run-role trigger passes only `meta`).

func (c *Cache) GetCachedResponse(ctx context.Context, dotId string, specId int32, maxElapsed time.Duration) ([]byte, error) {
	// prefer to get latest value from cache
	cached, inCache := c.latestValue(dotId, specId)
	if inCache && cached.FinishedAt.After(time.Now().Add(-maxElapsed)) {
		return cached.Value, nil
	}

	response, finishedAt, err := c.GetCachedResponseWithFinished(ctx, dotId, specId, maxElapsed)
	if err != nil {
		return nil, err
	}

	c.setValue(dotId, specId, BridgeResponse{
		DotID:      dotId,
		SpecID:     specId,
		Value:      response,
		FinishedAt: finishedAt,
	})

	return response, nil
}

func (c *Cache) UpsertBridgeResponse(ctx context.Context, dotId string, specId int32, response []byte) error {
	upsertTime := time.Now()

	// catch the rare case of a save race
	cached, inCache := c.latestValue(dotId, specId)
	if inCache && cached.FinishedAt.After(upsertTime) {
		return nil
	}

	c.setValue(dotId, specId, BridgeResponse{
		DotID:      dotId,
		SpecID:     specId,
		Value:      response,
		FinishedAt: upsertTime,
	})

	return nil
}
