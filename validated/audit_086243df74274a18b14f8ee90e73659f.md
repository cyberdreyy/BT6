### Title
Cross-user response hijacking via MessageId collision in gateway web_api_trigger callback map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's legacy WebAPI trigger handler stores pending user callbacks in `h.savedCallbacks` keyed **only** by `msg.Body.MessageId`, with no binding to the request's authenticated sender/signer. An attacker holding an arbitrary ECDSA keypair can sign and submit a `web_api_trigger` message reusing the `MessageId` of another still-pending request, silently overwriting the victim's callback entry so that the eventual DON node response is delivered to the attacker instead of the victim.

### Finding Description
In `core/services/gateway/gateway.go`'s `ProcessRequest` (lines 250-269), a legacy request is validated with `msg.Validate()` — which internally calls `Message.ExtractSigner()` (`core/services/gateway/api/message.go:124-134`) to correctly recover `msg.Body.Sender` from the signature — and then dispatched to `h.HandleLegacyUserMessage(ctx, msg, callback)`.

In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` (lines 341-421) stores the callback like this: [1](#0-0) 

This assignment is unconditional — there is no existence check and no inclusion of `msg.Body.Sender` in the key, unlike `core/services/gateway/handlers/common/requestcache.go`, which correctly scopes pending requests by `globalId{sender, id}`: [2](#0-1) [3](#0-2) 

`ExtractSigner()` itself correctly derives a distinct signer address per keypair/message — it does not "collide" for different signers. The exploitable gap is downstream: because `savedCallbacks` is keyed solely by the attacker-controlled `MessageId` string (whose only validation is length/null-byte checks in `Message.Validate()`, `core/services/gateway/api/message.go:54-88`), any signer can supply a `MessageId` matching another sender's still-pending request. When the DON responds, `handleWebAPITriggerMessage` looks the callback up purely by `MessageId`: [4](#0-3) 

Since the map entry was overwritten by the attacker's later request, whichever DON response arrives with that `MessageId` — including one triggered by the victim's original message forwarded to the DON before the overwrite — is delivered to the attacker's callback (`savedCb.SendResponse`), not the victim's. The victim's original callback reference is lost, so their HTTP request silently times out (`gateway.go` `callback.Wait(ctx)` → `api.RequestTimeoutError`), while the attacker receives the response payload that resulted from the victim's trigger event.

### Impact Explanation
This breaks per-request isolation between unrelated senders on the gateway: an unauthenticated (self-generated-key) attacker can (a) cause denial of service on a targeted victim request (silent timeout) and (b) receive response data/results attributable to the victim's trigger event instead of the victim, i.e., cross-user response confusion / unauthorized data exposure. This matches the Chainlink bounty impact class of unauthorized access to another user's request/response data via request impersonation.

### Likelihood Explanation
Exploitability requires only: (1) any valid ECDSA keypair — no gateway credential beyond the ability to submit an HTTP request signed with a self-generated key; (2) knowledge or prediction of a still-pending victim `MessageId` within the callback lifetime window (`CallbackMaxAgeSec`, default 120s, `handler.go:43`). `MessageId` values are not required to be unpredictable, and in some code paths they are computed deterministically (e.g., `messageID(url, parts...)` via SHA-256 of known inputs seen in `core/services/workflows/syncer/v2/fetcher_test.go:647-656`), making collision feasible for known workflow/DON targets. The race is straightforward to reproduce repeatedly with a scripted client.

### Recommendation
Scope `savedCallbacks` by both sender and `MessageId` (e.g., a composite key struct like `requestcache.go`'s `globalId{sender, id}`), and reject/rate-limit incoming trigger requests that attempt to reuse a `MessageId` already active for a *different* sender instead of silently overwriting the map entry.

### Proof of Concept
Go test plan in `core/services/gateway/handlers/capabilities/handler_test.go` (or a new table test):
1. Construct handler with `NewHandler`, register a DON with a mock `handlers.DON`.
2. Sign message A with keypair K1, `MessageId = "shared-id"`, call `HandleLegacyUserMessage` with callback C1; assert `h.savedCallbacks["shared-id"].Callback == C1`.
3. Sign message B with a different keypair K2, same `MessageId = "shared-id"`, call `HandleLegacyUserMessage` with callback C2; assert `h.savedCallbacks["shared-id"].Callback == C2` (overwrite confirmed, C1 dropped).
4. Simulate a DON node response via `HandleNodeMessage`/`handleWebAPITriggerMessage` with `MessageId = "shared-id"` and payload representing data from A's trigger context.
5. Assert C2 (attacker's callback) receives the response meant for A, and C1 (victim's callback) never fires and eventually is only satisfied by the gateway-level request timeout — proving cross-request response misattribution.
