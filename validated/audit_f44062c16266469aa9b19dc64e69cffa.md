This is a critical finding: in `http_trigger_handler.go`, `setupCallback` deduplicates strictly on the raw, user-supplied `req.ID` — **not** on a workflow-scoped or owner-scoped key. Unlike the Vault handler (`core/capabilities/vault/gateway_vault_request_processor.go`, `authorizeAndStamp`, lines 222-254), which explicitly rewrites `req.ID` to `authorizedOwner + separator + originalRequestID` *before* the in-flight dedup check, the HTTP trigger handler never namespaces the ID by caller/workflow before checking `h.callbacks[requestID]`.

### Title
Cross-Tenant Denial of Service via Global, Unscoped `requestID` Collision in HTTP Trigger Gateway Handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The gateway's `httpTriggerHandler` deduplicates in-flight requests using a single global map keyed only by the client-supplied JSON-RPC `id` field, with no per-workflow or per-caller namespacing, allowing any unprivileged client to block another user's request that happens to use the same ID.

### Finding Description
`HandleUserTriggerRequest` validates the request, authorizes the caller, and then calls `setupCallback(ctx, req.ID, callback, ...)` where `req.ID` is the raw, attacker-controlled JSON-RPC ID from the client request: [1](#0-0) [2](#0-1) 

`setupCallback` checks a global map `h.callbacks` (declared as `map[string]savedCallback // requestID -> savedCallback`) keyed purely by this unscoped `requestID`, and rejects the request with a conflict error if any entry already exists for that ID — regardless of which workflow or caller registered it: [3](#0-2) [4](#0-3) 

`validateRequestID` only rejects empty IDs or IDs containing `/`; it performs no uniqueness enforcement or per-caller scoping: [5](#0-4) 

This is structurally identical to the reported `LoanManager.createUserLoan` bug: a caller-chosen identifier (`loanId` / `requestID`) is checked for prior existence in a *single shared namespace*, and if an attacker submits first with the same identifier, the legitimate request is permanently blocked with a conflict error (`UserLoanAlreadyCreated` / `jsonrpc.ErrConflict`) until the entry naturally expires. The Vault handler's equivalent pipeline explicitly demonstrates the fix is well understood elsewhere in the codebase: `GatewayVaultRequestProcessor.authorizeAndStamp` computes `prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` and rewrites `req.ID` to this owner-scoped value *before* any in-flight/dedup check occurs, ensuring one caller cannot collide with another's namespace: [6](#0-5) 

The HTTP trigger handler has no analogous scoping step — `req.ID` used as the dedup key is never combined with `workflowID` or the authorized caller identity before the collision check in `setupCallback`.

### Impact Explanation
Any unauthenticated or low-privilege client that can submit HTTP trigger requests to the gateway can pick an arbitrary `requestID` and race a legitimate caller's request. If the attacker's request with that same ID lands first (trivial without needing to observe mempool timing, since IDs may be predictable, sequential, or simply guessed/brute-forced given no entropy requirement is enforced), the victim's genuine request is rejected with `jsonrpc.ErrConflict` and never delivered to the DON, causing denial of workflow execution for that request. Because the map is entirely global (not scoped by `workflowID`), this affects requests across different workflows and different callers, and an attacker can repeat this cheaply for many IDs to broadly deny service to the trigger handler.

### Likelihood Explanation
Exploitation only requires the ability to submit unauthenticated/low-cost requests with a chosen `id` field to the HTTP trigger method — no special privileges, no on-chain cost, and no knowledge beyond guessing or observing a target's ID scheme. The in-flight window is bounded (`createdAt`/cleanup logic exists), but during that window the collision is fully effective, and the check happens as one of the very first steps in the pipeline (`validateRequestID` → ... → `setupCallback`), before any workflow-specific authorization would meaningfully limit the attack surface for this shared key.

### Recommendation
Scope the in-flight `h.callbacks` map key (and the corresponding `savedCallback` set operation in `setupCallback`) by `workflowID` (or another server-derived identity, e.g., authorized caller/workflow owner) in addition to the client-supplied `requestID`, mirroring the pattern already used in `GatewayVaultRequestProcessor.authorizeAndStamp`. Compose the key as e.g. `workflowID + separator + requestID` and perform this composition immediately after authorization/`resolveWorkflowID`, before the `setupCallback` conflict check, so identical IDs from different callers/workflows cannot collide.

### Proof of Concept
1. Two independent callers (attacker and victim) target different workflows (or the same) via the gateway's `workflows.execute` HTTP trigger method.
2. Attacker submits a JSON-RPC request with `id = "X"` slightly before the victim's legitimate request also using `id = "X"` (a caller-chosen value, e.g., because the victim's client uses a predictable/sequential ID scheme or the attacker simply floods many candidate IDs).
3. The attacker's request succeeds and inserts `h.callbacks["X"]` via `setupCallback`.
4. The victim's request with the same `id = "X"` reaches `setupCallback`, finds `h.callbacks["X"]` already present, and is rejected via `h.handleUserError(..., jsonrpc.ErrConflict, "requestID: X has already been used...")`, exactly mirroring the existing test `TestHttpTriggerHandler_HandleUserTriggerRequest/duplicate_request_ID` at [7](#0-6)  — except in the real attack the two calls originate from different, unrelated, unprivileged callers rather than the same authorized session.

	}
	return nil

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil
