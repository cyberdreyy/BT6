### Title
`delete_member` fails to purge stale confirmations on other pending requests, allowing execution below `num_confirmations` live members - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` (`multisig2/src/lib.rs:356-379`) only deletes requests *authored* by the removed member and clears `num_requests_pk`, but never scans `self.confirmations` values on other still-pending requests for entries matching the removed member's `to_string()`. `confirm` (`multisig2/src/lib.rs:294-315`) counts `confirmations.len()` with no re-validation against current `self.members`, so a stale confirmation from a removed member still counts toward `num_confirmations`, letting a request execute with fewer live confirmers than required.

### Finding Description
The binding that must hold is: for any executed request, the count of distinct members present in `self.members` at execution time who confirmed == `self.num_confirmations`. In practice, `confirm` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) , where `confirmations: UnorderedSet<String>` is never filtered against `self.members`.

Root cause: `delete_member` removes requests where `r.member == member` (i.e., requests *authored* by the removed member) and clears that member's `num_requests_pk` entry, but does nothing to `self.confirmations` entries on *other* requests where the removed member appears merely as a confirmer: [2](#0-1) 

Exploit flow:
1. Member A creates request R1 (`Transfer`) via `add_request`; member M calls `confirm(R1)`, adding `M.to_string()` to R1's confirmation set (1 stale confirmation).
2. Separately, request R2 (`DeleteMember{member: M}`) reaches `num_confirmations` and executes, calling `delete_member` which removes M from `self.members` and clears M's own authored requests/`num_requests_pk`, but R1's confirmation set still contains M's entry — untouched.
3. Live member B calls `confirm(R1)` → confirmations = {M(stale), B} = 2, still below 3.
4. Live member C calls `confirm(R1)` → `confirmations.len() as u32 + 1 = 3 >= num_confirmations(3)` → `remove_request` + `execute_request` fires, executing the `Transfer`.

At this point only B and C are live members who actually confirmed (2 live confirmations), while the check passed using M's stale entry as the third. No guard (`assert_valid_request`, `current_member`, or `confirm`'s own logic) re-validates that all entries in the `confirmations` set correspond to accounts/keys still present in `self.members`.

### Impact Explanation
A `Transfer` (or any other multisig action, e.g. `AddKey`, `FunctionCall`, `DeleteMember`) can be executed with fewer live-member confirmations than `num_confirmations` requires, directly moving NEAR out of the multisig account to an attacker-controlled or arbitrary `receiver_id` without the intended level of authorization. This is a threshold-bypass on the multisig itself — Critical severity, matching "a multisig request executed below `num_confirmations` live members." The bug is repeatable for every request that was pending and confirmed by a member before that member is removed via a separate concurrent `DeleteMember` request; it can be triggered on any multisig deployment of this contract version.

### Likelihood Explanation
Preconditions are realistic and not attacker-privileged: the scenario requires ordinary multisig operation (two independently pending requests, one of which happens to be `DeleteMember`) and a minority of conspiring live members (fewer than `num_confirmations`) to push R1 over threshold using the stale entry. No special deposit or unusual capability is needed beyond being members with valid confirm rights — this is an internal-consistency bug rather than requiring the "unprivileged attacker" access model per se, but it is fully reachable through normal contract methods (`add_request`, `confirm`) with no additional guard blocking it. It is deterministic and reproducible via unit test with `testing_env!`.

### Recommendation
In `delete_member`, iterate over all entries in `self.requests`/`self.confirmations` and remove the deleted member's `to_string()` entry from every request's confirmation set (not just requests they authored). Alternatively/additionally, in `confirm`, recompute the confirmation count by filtering `confirmations` against `self.members` membership before comparing to `num_confirmations`, so stale entries never count toward the threshold.

### Proof of Concept
```rust
// multisig2/src/lib.rs tests module
#[test]
fn test_stale_confirmation_after_delete_member_bypasses_threshold() {
    // Setup: 5 members A..E (as MultisigMember::Account), num_confirmations = 3
    let mut c = MultiSigContract::new(members_5(), 3);

    // R1: authored by A, Transfer action
    testing_env!(context_with_account(a(), amount));
    let r1 = c.add_request(transfer_request(bob(), amount));

    // M confirms R1 (1 stale confirmation)
    testing_env!(context_with_account(m(), amount));
    c.confirm(r1);
    assert_eq!(c.confirmations.get(&r1).unwrap().len(), 1);

    // R2: DeleteMember{M}, authored+confirmed by others to reach threshold=3, executes delete_member
    testing_env!(context_with_account(d(), amount));
    let r2 = c.add_request(delete_member_request(m()));
    testing_env!(context_with_account(e(), amount));
    c.confirm(r2);
    testing_env!(context_with_account(a(), amount)); // third confirmer, executes
    c.confirm(r2);

    // M removed from members, but R1's confirmations still contain M's entry
    assert!(!c.members.contains(&MultisigMember::Account { account_id: m() }));
    assert!(c.confirmations.get(&r1).unwrap().contains(&m().to_string()));

    // Live members B and C confirm R1
    testing_env!(context_with_account(b(), amount));
    c.confirm(r1); // confirmations = {M(stale), B} = 2, still < 3
    assert_eq!(c.confirmations.get(&r1).unwrap().len(), 2);

    testing_env!(context_with_account(c(), amount));
    c.confirm(r1); // len()+1 == 3 >= 3 -> executes with only 2 live confirmers

    // Binding check: request executed (removed) despite only 2 live confirmers, not 3
    assert!(c.requests.get(&r1).is_none()); // R1 executed/removed
    let live_confirmers = 2; // B, C
    assert_ne!(live_confirmers, c.num_confirmations); // 2 != 3, binding violated
}
```

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
