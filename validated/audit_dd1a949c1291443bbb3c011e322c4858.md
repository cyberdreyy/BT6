### Title
Shared `RequestCache` has no per-sender quota, allowing any single authorized/unauthenticated sender to exhaust `maxCacheSize` and deny other users' requests - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces only a single global `maxCacheSize` bound with no per-sender partitioning, so one sender submitting many distinct `sender/MessageId` pairs can fill the cache and cause `"request cache is full"` for every other sender sharing the same `requestCache` instance. This is reachable from the vault handler's `MethodPublicKeyGet` path (which explicitly skips authorization) before the public key is cached, and more broadly by any already-authorized/allowlisted low-privileged sender through the vault and confidentialrelay handlers' create/update/delete/list flows.

### Finding Description
`NewRequest` keys entries by `globalId{sender, id}` [1](#0-0) , checks for an existing duplicate key, and then checks `len(c.cache) >= int(c.maxCacheSize)` before inserting [2](#0-1) . There is no per-sender counter or quota anywhere in this file - the `maxCacheSize` check is purely global across all senders sharing the `requestCache[T]` instance.

In `core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage` explicitly bypasses authorization for `MethodPublicKeyGet` when the public key is not yet cached: *"Public key requests don't require authorization, ... Note we cache this value quite aggressively so don't need to worry about DoS"* [3](#0-2) . This path calls `h.newActiveRequest(req, callback)`, which internally calls into the shared `RequestCache`. For all other vault methods (`SecretsCreate/Update/Delete/List`), `h.requestProcessor.ProcessRequest` (allowlist/JWT authorization) is checked before `newActiveRequest`/`NewRequest` is reached [4](#0-3) , meaning an attacker must already be an authorized/allowlisted sender to reach the cache for those methods - but once authorized, that sender is not further quota-limited by `RequestCache` and can consume the entire shared `maxCacheSize` budget with distinct `MessageId`s.

### Impact Explanation
This matches a denial-of-availability / quota-bypass impact: a single sender (either fully unauthenticated via the `MethodPublicKeyGet` race window, or an authorized-but-low-privileged sender for the other vault/confidentialrelay methods) can starve the shared cache, causing legitimate independent senders' `NewRequest` calls to fail with `"request cache is full"`. This breaks the isolation/fair-resource-allocation expectation between independent tenants/workflows sharing one gateway handler instance, though it does not leak secrets or escalate privileges directly.

### Likelihood Explanation
For the fully unauthenticated public-key path, the exploit window is narrow: only requests that arrive before the master public key is first fetched and cached can bypass authorization; once cached, subsequent `MethodPublicKeyGet` calls are served synchronously from cache and never reach `NewRequest` [5](#0-4) , limiting sustained abuse via that specific route. For the broader vault/confidentialrelay secret methods, reaching `NewRequest` requires passing `ProcessRequest`'s allowlist/JWT authorization first, so a fully anonymous, unallowlisted attacker cannot reach those paths - only an already-authorized (but low-privileged/limited) sender can, and rate limiting (`NodeRateLimiter`/`PerSenderRPS`) exists at other layers but is not applied inside `requestcache.go` itself. No per-sender partitioning exists in `RequestCache` for any caller.

### Recommendation
Add a per-sender quota (e.g., a configurable max pending requests per `sender`) inside `requestCache.NewRequest`, tracked alongside the global `maxCacheSize`, so no single sender can consume the entire shared cache capacity. Alternatively, shard the cache or reject/evict oldest entries per sender when a per-sender limit is hit, independent of the global limit enforced today in `requestcache.go` lines 64-66 [6](#0-5) .

### Proof of Concept
Go unit test in `core/services/gateway/handlers/common/requestcache_test.go`:
1. Construct `NewRequestCache[T](timeout, maxCacheSize=N)`.
2. Loop `N` times, calling `NewRequest` with distinct `sender_i`/`id_i` pairs (simulating one or many senders) - assert each call returns `nil`.
3. Call `NewRequest` once more with a brand-new distinct `sender`/`id` (representing a different legitimate user) - assert it returns the error `"request cache is full"`.
4. This demonstrates no per-sender partitioning exists; combine with a second test asserting that filling the cache using only requests from a *single* sender produces the same denial for a different sender's subsequent call, confirming the shared-quota exhaustion.
