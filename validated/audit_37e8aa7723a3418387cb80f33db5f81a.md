### Title
Refund-on-failure in `on_staking_pool_create` double-pays the deposit when `new` fails after account creation/transfer already committed - (File: `staking-pool-factory/src/lib.rs`)

### Summary
`create_staking_pool` schedules a single batched receipt (`create_account` → `transfer` → `deploy_contract` → `function_call("new", …)`) followed by a callback `on_staking_pool_create` that unconditionally refunds `attached_deposit` to the caller whenever the batched receipt's outcome is not `Successful`. Because NEAR does not roll back actions that already executed within a receipt when a later action in the same receipt fails, a `new` failure after `transfer` has already moved the deposit onto the freshly created account results in the deposit being retained at the new account **and** refunded again from the factory's own balance, breaking the invariant `refund + balance_left_at_created_account == deposit`.

### Finding Description
Binding claimed and traced: for every `create_staking_pool` call, `refund_amount + near_left_at(staking_pool_account_id) == attached_deposit` must hold regardless of whether `new` succeeds.

Code path:
- `create_staking_pool` (`staking-pool-factory/src/lib.rs:136-195`) builds one promise chain: `create_account().transfer(deposit).deploy_contract(wasm).function_call(b"new", …, gas::STAKING_POOL_NEW)`, then `.then(on_staking_pool_create(...))`. [1](#0-0) 
- `on_staking_pool_create` checks `is_promise_success()`; on failure it removes the id from the set and unconditionally does `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` — a second, independent transfer sourced from the factory contract's own balance, not from the newly created account. [2](#0-1) 

Root cause: within a single NEAR receipt containing multiple actions, if a later action (`function_call("new", …)`) fails (e.g., the deployed init call runs out of the fixed `gas::STAKING_POOL_NEW` budget, or panics for any other reason after the WASM is deployed), the actions that already executed earlier in the same receipt — `create_account` and `transfer(deposit)` — are **not reverted**. `is_promise_success()` in the callback only reflects the final action's outcome (Failed), so the factory believes the whole operation failed and refunds the deposit a second time from its own balance. None of the existing guards (`assert_self`, `is_promise_success`, the uniqueness check on `staking_pool_account_ids`, `env::is_valid_account_id`, `RewardFeeFraction::assert_valid`) detect or prevent this, because they only validate arguments before the promise is scheduled — they cannot observe or compensate for partial execution of the already-scheduled batched receipt.

The "crafted name" framing in the question is not itself the mechanism; `staking_pool_id` only determines which fresh subaccount is targeted (must be dot-free and not already present in `staking_pool_account_ids`). The actual trigger is any input/condition that makes the trailing `function_call("new", …)` fail (e.g., gas exhaustion in the deployed `new` execution) after the preceding `create_account`/`transfer` actions in the same receipt have already committed.

### Impact Explanation
Each successful exploitation permanently drains `attached_deposit` (≥ `MIN_ATTACHED_BALANCE` = 30 NEAR) from the factory contract's own balance while the equivalent NEAR is left stranded on the freshly created (deployed but uninitialized) account, and the caller additionally receives a full refund. This is a real transfer of NEAR out of a contract account (`staking-pool-factory`) that the entitled party (the factory/its future callers) never authorized, matching the Critical category "NEAR moved out of a pool/factory by a party not entitled to it." It is repeatable per attempt (each attempt requires a fresh `staking_pool_id` and a fresh ≥30 NEAR deposit) and will continue until the factory's own balance is exhausted, after which the refund `Promise::new(...).transfer(...)` itself would fail (this failure occurs asynchronously and does not revert the earlier double payment already made).

### Likelihood Explanation
Preconditions: attacker needs only to call the public, unprivileged `create_staking_pool` with the minimum deposit, and needs a way to make the trailing `function_call("new", …)` action fail after `create_account`/`transfer` have already applied — most plausibly by causing the deployed `new` invocation to exceed the fixed `gas::STAKING_POOL_NEW` (`BASE * 2` = 50 Tgas) budget. I was not able to fully inspect `staking-pool/src/lib.rs::new` (its exact assertions/compute cost) in this pass because the file content could not be retrieved with the tools available; this is a gap that would need to be closed (e.g., via a `near-workspaces` sandbox test) to fully confirm whether this specific gas budget is realistically exceedable by attacker-supplied but otherwise-valid `owner_id`/`stake_public_key`/`reward_fee_fraction` values, or whether some other failure mode inside `new` is reachable post-validation.

### Recommendation
Do not refund from the factory's own balance based solely on `is_promise_success()` of a receipt that already performed `create_account`/`transfer`. Options: (1) split account creation/funding from initialization into separate, independently-recoverable steps so a failed `new` can be retried/recovered on the already-funded account instead of triggering a second payout; (2) have the callback verify the created account's actual balance before refunding, or transfer only the difference; (3) increase/parametrize `gas::STAKING_POOL_NEW` with a safety margin and add an explicit self-balance check in `on_staking_pool_create` (`env::account_balance()` before/after) asserting the refund does not exceed what the factory can safely disburse without double-counting funds already sent to the created account.

### Proof of Concept
Cannot be fully constructed with the tools available in this session (would require a `near-workspaces`/sandbox-level test to observe true multi-action receipt semantics, which the existing `near-sdk` unit tests in `staking-pool-factory/tests/spec.rs` and the inline `#[cfg(test)] mod tests` cannot reproduce, since they mock `PromiseResult` directly rather than executing the real batched receipt). A `cargo test` proof would need to:
1. Deploy `staking-pool-factory` and `staking-pool` in a `near-workspaces` sandbox.
2. Call `create_staking_pool` with a deposit and craft conditions (e.g., insufficient gas for `new`) so the final `function_call("new", …)` fails while `create_account`/`transfer`/`deploy_contract` succeed.
3. Assert `refund_received_by_caller + balance_of(staking_pool_account_id) > attached_deposit`, proving the invariant is broken.

Given I could not verify the exact mechanism to force `new` to fail post-transfer (missing visibility into `staking-pool/src/lib.rs::new`), this finding should be treated as **plausible but not fully confirmed** — flag for follow-up with full sandbox reproduction before final severity sign-off.
