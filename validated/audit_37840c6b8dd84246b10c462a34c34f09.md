## Analysis

The external Ajna report describes a class of bug where a value that should have expired / stopped being a "live claim" (`reserveAuction.unclaimed` after the auction window ends) is nonetheless still counted as binding when computing whether an action can proceed, wrongly denying access to funds that are, in reality, free. The generalizable custody binding is: **the set of approvals counted toward a threshold must equal the set of approvals that are still live/valid.**

I found a direct analog of this class in `multisig2/src/lib.rs`: confirmations from a member who has since been **removed** from the multisig are never purged from *other* members' pending requests, and `confirm()` never re-validates that stored confirmations still belong to current members. A removed member's stale confirmation therefore keeps counting toward `num_confirmations`, allowing a request to execute with fewer genuinely live/current members' consent than the configured threshold — breaking the binding `confirmations counted == live members approving`.

### Title
Stale confirmations from removed multisig members still count toward `num_confirmations`, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the multisig2 contract only purges confirmations/requests that the removed member *created* (`r.member == member`), but never scans the `confirmations` map for entries where the removed member merely *confirmed* someone else's still-pending request. `confirm()` then counts `confirmations.len() + 1 >= self.num_confirmations` without checking that every previously stored confirmer is still in `self.members`. This lets a request execute using a mix of live and already-removed members' confirmations, i.e., with fewer currently-trusted signers than `num_confirmations` requires.

### Finding Description
`delete_member` cleans up only requests originated by the removed member: [1](#0-0) 

```rust

    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
    ...
}
```

The filter `r.member == member` only matches requests whose *creator* is the member being removed. It never inspects the `confirmations` HashSet keyed by member string on requests *created by other members*. So if member `A` confirmed a request created by member `B`, and `A` is later removed, `A`'s confirmation entry remains inside that request's `confirmations` set.

`confirm()` then blindly trusts the stored size of that set: [2](#0-1) 

```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self.current_member()...;
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), ...);
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        ...
    }
}
```

`assert_valid_request`/`current_member` only validate that the *calling* account/key is currently a member; they never re-validate the *previously stored* confirmers against `self.members`. [3](#0-2) 

The custody binding this breaks: `count of confirmations == count of currently-trusted members having approved`. After removal of a member, that equality is violated — the removed member's earlier confirmation still contributes to the count.

### Impact Explanation
This falls under the explicit Critical impact bucket "a multisig request executed below threshold." Concretely: suppose `num_confirmations = 3` with members `{A,B,C,D}`. Member `B` creates a `Transfer` request `R` to a malicious receiver and confirms it (1 confirmation: `B`). Member `A` (compromised or colluding) confirms `R` (2 confirmations: `A,B`), then the organization detects `A` is compromised and removes `A` via a separate, properly-threshold-confirmed `DeleteMember` request. Because `R` was created by `B`, not `A`, `delete_member`'s filter does not touch `R`; `A`'s confirmation persists in `R`'s confirmation set. Any one more current member (e.g. `C`) confirming `R` now satisfies `confirmations.len() + 1 (=3) >= num_confirmations (3)` and the transfer executes — even though only two currently-live members (`B` and `C`) actually approved it at execution time, plus a stale approval from an already-removed member `A`. Funds move out of the multisig-controlled account under authorization that does not reflect the current, intended trust set.

### Likelihood Explanation
Reachable by any account holding multisig membership at some point (no foundation/owner privilege beyond being a normal member), using only the contract's public `add_request`/`confirm`/`DeleteMember` flow — no redeploy, no key compromise assumption beyond the routine scenario the multisig itself is designed to defend against (member key compromise/removal). The bug requires only that a removal happens *after* a confirmation but *before* the request reaches threshold, and that the removed member wasn't the *creator* of the still-pending request — a very plausible real-world event, and exactly the situation `DeleteMember` exists to remediate.

### Recommendation
When executing `DeleteMember`, iterate over **all** pending requests' confirmation sets (not just requests created by the removed member) and strip the removed member's confirmation entry from each; alternatively, at confirmation-count time in `confirm()`, filter `confirmations` to only those entries whose corresponding member is still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`. [4](#0-3) 
2. `B` calls `add_request_and_confirm` with `MultiSigRequestAction::Transfer{amount}` to a receiver `E`, creating request `R` with confirmations `{B}`. [5](#0-4) 
3. `A` calls `confirm(R)` → confirmations become `{A, B}` (still < 3, not executed). [2](#0-1) 
4. Remaining trusted members (`B, C, D`) submit and confirm a separate request that executes `DeleteMember{member: A}` — this removes `A` from `self.members` but does not touch `R`'s confirmation set because `R.member == B ≠ A`. [6](#0-5) 
5. `C` (a legitimate, still-current member) calls `confirm(R)`. `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `R` executes and transfers funds to `E`, despite only 2 currently-live members (`B`, `C`) having actually approved it at execution time — `A`'s stale, post-removal confirmation supplied the missing vote.
