### Title
Owner-privileged NEAR-moving functions (`transfer`, `add_full_access_key`) lack one-yoctoNEAR 2FA, enabling theft/takeover via a limited Function Call access key - (File: `lockup/src/owner.rs`)

### Summary
`lockup/src/owner.rs` implements owner-privileged methods that move real NEAR or grant full account control, gated only by `assert_owner()` (a predecessor-account-id check). Unlike `w-near/src/w_near.rs::near_withdraw`, which is `#[payable]` and calls `assert_one_yocto()` before moving NEAR out of the contract, none of the fund-moving owner methods in the lockup contract require an attached yoctoNEAR. This is the exact bug class from the external report: privileged, asset-moving functions callable by a Function Call access key (which cannot attach any deposit) instead of requiring proof that the caller holds a Full Access key.

### Finding Description
`assert_one_yocto()` is used exactly once in this codebase, in the wNEAR contract's `near_withdraw`: [1](#0-0) . The corresponding pattern — `#[payable]` + `assert_one_yocto()` — is the NEAR-recommended two-factor check ensuring the caller signed with a Full Access key rather than a Function Call key (which per protocol rules cannot attach a deposit).

In `lockup/src/owner.rs`, the owner-authorization check is only `assert_owner()`, i.e. `predecessor_account_id == owner_account_id`: [2](#0-1) . This check is satisfied by *any* key on the owner account — Full Access or Function Call — because NEAR authorizes calls by account id, not key type, for non-payment-gated methods.

Two methods in `owner.rs` are the highest-value targets, since their doc comments explicitly warn "Not intended to hand over the access to someone else except the owner", implying the authors assumed only a trusted signer would ever call them, yet no deposit/2FA is enforced:

- `transfer(amount, receiver_id)` — moves the account's liquid NEAR balance to an arbitrary `receiver_id` with no `#[payable]`/`assert_one_yocto()` guard: [3](#0-2) 
- `add_full_access_key(new_public_key)` — grants a brand-new Full Access key to the lockup account, again with no deposit guard: [4](#0-3) 

A repo-wide search confirms `assert_one_yocto` is never used in `lockup/src/**` (or `multisig`, `staking-pool`, etc.) [5](#0-4) .

### Impact Explanation
If the owner account ever has a Function Call access key outstanding for the lockup account (e.g., issued to a web integration/dApp that is scoped to call owner methods on the lockup contract for convenience/automation), that key is sufficient to:
- Drain the entire liquid owner's balance via `transfer` to an attacker-controlled account, breaking the binding between the NEAR actually held/entitled to the owner and the NEAR that leaves the contract — Critical: "NEAR ... moved by a party not entitled to it."
- Call `add_full_access_key` to install an attacker's own Full Access key, permanently taking over the lockup account and any remaining locked/vested funds once conditions are later met — Critical: "locked or unvested tokens released early" / unauthorized custody takeover.

Both are irreversible, direct loss of custody once a Function Call key with access to these methods is compromised or misused — the same class of impact described in the atBTC report (theft of assets protected only by predecessor-id checks, not by a proof of Full Access signing).

### Likelihood Explanation
Exploitation requires that a Function Call access key exists on the owner account with permission to call `transfer` / `add_full_access_key` on the lockup contract (or a wildcard method key). This is a realistic operational pattern for lockup owners who use web wallets/dApps to automate staking/owner operations, exactly the scenario the original NEAR one-yocto guidance and the atBTC report warn about. It does not require the foundation, a redeploy, or any privileged party beyond the (compromised or malicious) key holder — an unprivileged holder of a leaked/malicious Function Call key is sufficient, matching the report's attacker model.

### Recommendation
Add `#[payable]` and `assert_one_yocto()` to all owner methods in `lockup/src/owner.rs` that move value or change custody/authorization state, at minimum `transfer` and `add_full_access_key`:
```rust
#[payable]
pub fn transfer(&mut self, amount: WrappedBalance, receiver_id: AccountId) -> Promise {
    assert_one_yocto();
    self.assert_owner();
    ...
}
```
Apply the same pattern to any other state-mutating owner method intended to be restricted to a Full Access key holder, consistent with the mitigation already applied to `w-near::near_withdraw`.

### Proof of Concept
1. Owner account `owner.near` controls `lockup1.near` and, for operational convenience, adds a Function Call access key to `owner.near` scoped to `lockup1.near` with method names including `transfer` (or an unrestricted method list) and no deposit allowance — a plausible integration pattern for automated owner tooling.
2. That Function Call key is exfiltrated (e.g., via a compromised web integration) — no Full Access key or admin privilege is needed.
3. Attacker signs a transaction from `owner.near` calling `lockup1.transfer({amount: <liquid_balance>, receiver_id: "attacker.near"})` using only the Function Call key. `assert_owner()` at [2](#0-1)  passes because `predecessor_account_id == owner_account_id`; there is no `assert_one_yocto()` to reject the call for lacking a Full Access signature.
4. `Promise::new(receiver_id).transfer(amount.0)` executes at [6](#0-5) , sending the owner's liquid balance to `attacker.near`. Alternatively, the attacker calls `add_full_access_key` with the same key to install a full-access key of their choosing, taking permanent control of `lockup1.near`.

    ///
    /// Requires 50 TGas (2 * BASE_GAS)
    /// Not intended to hand over the access to someone else except the owner
    ///
    /// Transfers the given amount to the given receiver account ID.
    /// This requires transfers to be enabled within the voting contract.
    pub fn transfer(&mut self, amount: WrappedBalance, receiver_id: AccountId) -> Promise {
        self.assert_owner();
        assert!(amount.0 > 0, "Amount should be positive");
        assert!(
            env::is_valid_account_id(receiver_id.as_bytes()),
            "The receiver account ID is invalid"
        );
        self.assert_transfers_enabled();
        self.assert_no_staking_or_idle();
        self.assert_no_termination();
        assert!(
            self.get_liquid_owners_balance().0 >= amount.0,
            "The available liquid balance {} is smaller than the requested transfer amount {}",
            self.get_liquid_owners_balance().0,
            amount.0,
        );

        env::log(format!("Transferring {} to account @{}", amount.0, receiver_id).as_bytes());

        Promise::new(receiver_id).transfer(amount.0)
    }

    ///
    /// Adds full access key with the given public key to the account.
    /// The following requirements should be met:
    /// - The contract is fully vested;
    /// - Lockup duration has expired;
    /// - Transfers are enabled;
    /// - If there’s a termination made by foundation, it has to be finished.
    /// Full access key will allow owner to use this account as a regular account and remove

    pub fn add_full_access_key(&mut self, new_public_key: Base58PublicKey) -> Promise {

        self.assert_no_termination();
