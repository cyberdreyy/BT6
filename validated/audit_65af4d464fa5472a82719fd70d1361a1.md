## Finding: RPC `bank()` commitment resolution can silently return stale/wrong-slot bank data

The Olympus bug class here is: **a component reports a value based on cached/tracked accounting state that has drifted from the actual underlying resource**, and callers trust the cached value without verifying it against the real state, causing operations to act on data that doesn't correspond to reality. The most direct analog in `agave` is how the RPC layer resolves a `Bank` for a given commitment level.

### Root Cause

`JsonRpcRequestProcessor::bank()` looks up the slot corresponding to a commitment level from the `BlockCommitmentCache`, and then tries to fetch the corresponding `Bank` from `BankForks`. If that bank is no longer present (e.g., it was purged from `BankForks` as an old bank, while `BlockCommitmentCache` has not yet been updated to reflect this), the code does **not** return an error — it silently substitutes `root_bank()` instead: [1](#0-0) 

The comment in the code itself documents that this is a known accounting mismatch between the cache and the real state of `BankForks`:
- The `slot` value returned by `self.block_commitment_cache.read().unwrap().slot_with_commitment(...)` is trusted as "the bank for this commitment level exists."
- `r_bank_forks.get(slot)` can return `None` because `BankForks` has already dropped/pruned that bank.
- Instead of surfacing an error to the caller, the code falls back to `r_bank_forks.root_bank()` — a **different slot** than what was requested — and logs only a `warn!`.

This is functionally identical to the Olympus bug: `TRSRY.getReserveBalance()` reported a capacity number based on outstanding-debt accounting that no longer matched the actual token balance in the treasury, so downstream code (bond markets, swaps) acted on a wrong value and failed at the point of actual transfer. Here, the `BlockCommitmentCache` "believes" a bank at a given slot is the correct target for a commitment level, but the actual store (`BankForks`) no longer has it — and instead of failing loudly, the RPC layer substitutes a different (root) bank silently.

### Impact

Since nearly all RPC handlers call `self.bank(commitment)` (or the equivalent `get_bank_with_config`) to select which bank to serve data from, any unprivileged JSON-RPC caller requesting data at a specific commitment level (`processed`/`finalized`) could receive account/balance/state data from the wrong slot/fork without any indication of an error. This matches the accepted category "wrong-slot/fork/account data returned" — the RPC response context (`slot`) and the actual data returned would correspond to a different bank than the one the client asked for via commitment level, and the client has no way to detect this from the response other than comparing slot numbers with expectations.

### Likelihood

This requires the specific known race the comment describes: `BankForks` purges an old bank before `BlockCommitmentCache` has advanced. The comment references this as a pre-existing, acknowledged edge case (linked to `solana-labs/solana#11078`), similar to how the Olympus finding was "unlikely" but still a real logic gap that the team acknowledged and confirmed needed a mitigating check.

### Recommendation

Rather than falling back silently to `root_bank()`, `JsonRpcRequestProcessor::bank()` should return an explicit RPC error (e.g. a `RpcCustomError` indicating the requested commitment/slot's bank could not be resolved) so RPC clients cannot silently receive data for the wrong slot. This mirrors the Olympus recommendation to "determine capacity from actual tokens held" rather than trust a cached/derived value — here, the RPC layer should verify the actual bank exists in `BankForks` rather than trusting `BlockCommitmentCache`'s value and masking the mismatch with a fallback.

### Proof of Concept

Conceptually:
1. A commitment-level slot `S` is recorded by `BlockCommitmentCache` (e.g., as `highest_super_majority_root`).
2. `BankForks` prunes bank `S` before `BlockCommitmentCache` is updated to reflect a new root (per the comment, this "may occur after an old bank has been purged from BankForks and a new BlockCommitmentCache has not yet arrived").
3. A client calls any RPC method with `commitment: "finalized"` (e.g., `getAccountInfo`, `getBalance`).
4. `self.bank(commitment)` resolves `slot = S`, `r_bank_forks.get(S)` returns `None`, and the code returns `r_bank_forks.root_bank()` instead — a different slot than `S` — with only a `warn!` log, no error surfaced to the RPC client.
5. The client receives a successful response with `context.slot` corresponding to the root bank, not slot `S`, with no error signal that the intended commitment-level bank was unavailable. [2](#0-1)

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
