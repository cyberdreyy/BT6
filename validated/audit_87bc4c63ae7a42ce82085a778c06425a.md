**Analysis summary:**

The `SyscallGetClockSysvar` (and generic `SyscallGetSysvar`) reads `Clock` directly from the executing bank's `SysvarCache`, which is populated per-bank from that bank's own account state via `TransactionBatchProcessor::fill_missing_sysvar_cache_entries` [1](#0-0) . Whatever slot a program executes in, the `Clock` it reads reflects that specific bank/fork's own state — this is expected, correct behavior, not a bug, and is verified by tests like `test_sysvar_cache_initialization` showing each bank has its own distinct clock value tied to its own slot [2](#0-1) .

The critical safety property is in how RPC resolves "finalized" commitment. `JsonRpcRequestProcessor::bank()` maps `CommitmentLevel::Finalized` to `block_commitment_cache.slot_with_commitment(Finalized)`, which returns `highest_super_majority_root()` [3](#0-2) [4](#0-3) . This value is only ever advanced by `AggregateCommitmentService::update_commitment_cache`, which computes `highest_super_majority_root` from real aggregated vote/stake data and only increases monotonically once actual supermajority consensus roots a slot [5](#0-4) . `getAccountInfo` then fetches the account from `bank_forks.get(slot)` for that rooted slot only [6](#0-5) .

Since a bank/fork that is never rooted is pruned from `BankForks` (`prune_non_rooted`) and never contributes to `highest_super_majority_root`, any account data (including a program-written copy of `Clock`) that only exists on a discarded, unrooted fork can never be returned by a `finalized`-commitment `getAccountInfo`/`getTransaction` call — by construction, "finalized" state is always derived from a bank that consensus has actually rooted. The attacker's ability to write `Clock` into an owned account via the syscall does not bypass this; it merely produces account data consistent with whichever bank actually executed the instruction, and that data is only visible at `finalized` commitment if and only if that bank's slot became the real root.
