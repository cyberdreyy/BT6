### Title
Cross-user response confusion via colliding `MessageId` in `savedCallbacks` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores a caller's `handlers.Callback` in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no binding to the sender/signer. Any unauthenticated client can choose an arbitrary `MessageId` (bounded only by length/format checks), so a second signed request using the same `MessageId` as a pending request will overwrite the map entry, causing `handleWebAPITriggerMessage` to route the node's response to the wrong caller.

### Finding Description
`HandleLegacyUserMessage` validates the message (signature, staleness, method) and then does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [1](#0-0) 

`msg.Body.MessageId` originates entirely from the incoming request body and is only checked for length/format in `Message.Validate()` — there is no uniqueness or per-sender scoping requirement: [2](#0-1) 

The signature does bind `MessageId` to a given signer's key (`GetRawMessageBody` includes MessageId in the signed payload), so an attacker cannot forge a victim's exact signed message. But the attacker doesn't need to forge the victim's message — they only need to independently pick and sign their **own** message using the **same** `MessageId` string as a currently-outstanding victim request. Since `Message.Validate()` derives `Sender` from the signature but this `Sender` is never consulted when storing/looking up `savedCallbacks`, two different senders' callbacks collide on the same map key.

When the node responds, `handleWebAPITriggerMessage` looks up and deletes by `MessageId` only and forwards to whichever callback is currently registered:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [3](#0-2) 

Because `MessageId` is not required to be a per-sender-namespaced or high-entropy server-generated value, and the map has no `(sender, messageId)` composite key, a race between two identical-`MessageId` requests from different signers results in whichever entry is currently stored being returned to whichever HTTP connection is waiting — i.e., cross-user response confusion or clobbering of the victim's pending callback.

### Impact Explanation
If exploited, one user's HTTP connection can receive another user's `web_api_trigger` response payload, or a victim's callback can simply be dropped (attacker's later insert overwrites the map entry, and when the victim's node response arrives it is delivered to the attacker's callback instead, while the victim's request is effectively lost/never answered). This is a cross-user response confusion bug, matching the "unauthorized access to another user's request/response data" bounty class for gateway components. It does not directly cause fund loss, key disclosure, or privilege escalation, but it breaks isolation guarantees between distinct callers of the same gateway/DON.

### Likelihood Explanation
Exploitation requires only that the attacker can send a validly self-signed `web_api_trigger` message to the gateway (unauthenticated, low-privilege — this matches "unauthenticated HTTP client sending a validly-signed message with own key") and can guess or observe a victim's in-flight `MessageId` value. Whether `MessageId` values are predictable in practice (sequential, timestamp-based, or attacker-observable via logs/telemetry) depends on the client library that generates them, which is outside this handler's scope and was not fully verifiable in the indexed code (client-side ID generation was not located during this review). If clients use high-entropy random IDs (e.g., UUIDv4), practical collision/guessing is very unlikely; if any client uses low-entropy or predictable IDs, exploitation is straightforward and repeatable with no special access. The population/collision path itself (no sender check on the map key) is a real code defect independent of ID entropy.

### Recommendation
Key `savedCallbacks` by a composite of `(Sender, MessageId)` (or a random server-generated internal correlation ID unrelated to the client-supplied `MessageId`) instead of `MessageId` alone, and validate on lookup in `handleWebAPITriggerMessage` that the responding node's message `Sender`/`DonId` context corresponds to the originally stored request before invoking `SendResponse`.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two `api.Message`s with identical `Body.MessageId = "X"` but signed by two different ECDSA keys (`Sign(privKeyA)`, `Sign(privKeyB)`), both with `Method = MethodWebAPITrigger`.
2. Create two mock `handlers.Callback` instances, `cbA` and `cbB`, each expecting `SendResponse` to be called at most once.
3. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` then `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` (simulating the race — B arrives before the node responds to A).
4. Simulate the node's response for `MessageId="X"` via `handler.HandleNodeMessage` (or directly `handleWebAPITriggerMessage`) once.
5. Assert that `cbB.SendResponse` is invoked (since B's entry overwrote A's in the map) while `cbA.SendResponse` is never invoked — demonstrating that the victim (A) never gets a response and the attacker (B) receives a response tied to A's original `MessageId`, confirming cross-user confusion caused by the missing sender component in the `savedCallbacks` key.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	}
	return nil
