### Title
Empty-password LDAP bind is treated as authentication success in `CreateSession` - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` forwards the client-supplied email and password directly into `conn.Bind(searchBaseDN, sr.Password)` with no check that the password is non-empty. Per RFC 4513 §5.1.2, an LDAP simple bind with a valid DN and an empty password is defined as an "unauthenticated bind," which most directory servers accept (`err == nil`) without verifying any credential. Because the code interprets `err == nil` as "user and credentials are present in LDAP directory," an attacker who knows (or guesses) any valid user email can log in with an empty password and be granted that user's mapped role.

### Finding Description
The HTTP route `POST /sessions` is handled by `SessionsController.Create` in [1](#0-0) , which binds the JSON body directly into `clsessions.SessionRequest` (containing `Email` and `Password` as plain strings, no validation tags) and immediately calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`. There is no middleware or presenter check rejecting an empty or whitespace-only password before this call.

In the LDAP provider, `CreateSession` performs: [2](#0-1) 

The bind call `conn.Bind(searchBaseDN, sr.Password)` is a standard LDAPv3 simple bind. If `sr.Password` is empty, and the directory server has not explicitly disabled unauthenticated binds, the bind succeeds (`err == nil`) even though no password was actually verified — this is the documented "unauthenticated bind" behavior of LDAP simple binds, not a credential match. The code path then proceeds to call `FindUser`, which queries the directory for the group memberships of the supplied `escapedEmail` (attacker-controlled) and maps them to a role via `groupSearchResultsToUserRole` / `GroupSearchResultsToUserRole` ( [3](#0-2) ). If the email happens to belong to a user in the Admin/Edit/Run group, the attacker session is created with that role — all without ever supplying a correct password.

No code path in `NewLDAPAuthenticator`, `CreateSession`, or the sessions controller rejects empty/whitespace passwords before the directory is contacted, so the "invariant to test" (empty-password binds must be rejected before contacting the directory) is not enforced anywhere in this file or the calling controller.

### Impact Explanation
If the target LDAP/AD server allows unauthenticated binds for a valid DN with empty password (a common default in many LDAP implementations, e.g. OpenLDAP unless `disallow bind_anon` is set), an unauthenticated attacker who can reach the node API port and knows or guesses any valid corporate/user email can obtain a valid Chainlink node session with that user's role — including Admin, if the targeted email belongs to the Admin group. This matches "Critical - node takeover": an unauthenticated attacker gains admin control of the node, enabling key export and unauthorized transaction submission.

### Likelihood Explanation
Exploitability depends entirely on the upstream LDAP/AD server's configuration (whether it permits unauthenticated/anonymous simple binds for a given DN with empty password), which is outside this code's control but is the default behavior for many directory deployments per RFC 4513. Given that dependency, exploitation from the Chainlink node's perspective requires only: (1) the LDAP authentication provider is configured (`NewLDAPAuthenticator` is used), (2) the attacker knows a valid user email in the directory, and (3) submits an empty password to `POST /sessions`. No other credential, cookie, or role is required — a fully unauthenticated network client can attempt this repeatedly.

### Recommendation
In `ldapAuthenticator.CreateSession` (and `TestPassword`), reject any `sr.Password` that is empty or consists only of whitespace before calling `conn.Bind`, returning an authentication error immediately without contacting the LDAP server. Additionally, consider validating this at the `SessionRequest` binding layer in `core/web/sessions_controller.go` so all authentication providers benefit from the check.

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

func GroupSearchResultsToUserRole(ldapGroups []*ldap.Entry, adminCN string, editCN string, runCN string, readCN string) (sessions.UserRole, error) {
	// If defined Admin group name is present in groups search result, return UserRoleAdmin
	for _, group := range ldapGroups {
		if group.GetAttributeValue("cn") == adminCN {
			return sessions.UserRoleAdmin, nil
		}
	}
	// Check edit role
	for _, group := range ldapGroups {
		if group.GetAttributeValue("cn") == editCN {
			return sessions.UserRoleEdit, nil
		}
	}
	// Check run role
	for _, group := range ldapGroups {
		if group.GetAttributeValue("cn") == runCN {
			return sessions.UserRoleRun, nil
		}
	}
	// Check view role
	for _, group := range ldapGroups {
		if group.GetAttributeValue("cn") == readCN {
			return sessions.UserRoleView, nil
		}
	}
	// No role group found, error
	return sessions.UserRoleView, ErrUserNoLDAPGroups
}
