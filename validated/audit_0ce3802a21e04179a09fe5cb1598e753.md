### Title
JWT authorization for `WorkflowMetadataHandler.Authorize` is not cryptographically bound to the target `workflowID`, enabling cross-workflow request replay - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` verifies a JWT's signature and digest against the request contents via `utils.VerifyRequestJWT`, but the `workflowID` the request is being authorized against is never included in the signed claims or in the digest computation. Because the JWT replay cache is also keyed globally by `jti` (not scoped per-workflow), a token that a signer produced for one workflow can be legitimately verified and accepted against a different workflow, provided the same underlying request content is used and the signer's key happens to be authorized for both workflows.

### Finding Description
`Authorize` calls `utils.VerifyRequestJWT(token, *req)` which validates the ECDSA signature, expiry/issuedAt bounds, and that `claims.Digest` matches `req.Digest()` [1](#0-0) [2](#0-1) . Nowhere in `JWTClaims` (`Digest`, `jwt.RegisteredClaims`) is the target `workflowID` encoded [3](#0-2) , and `Authorize` receives `workflowID` as a separate, out-of-band parameter used only to look up `h.authorizedKeys[workflowID]` after JWT verification succeeds [4](#0-3) .

The only anti-replay mechanism is `h.jwtCache.isReplay(claims.ID)`, which tracks JTIs in a single global map with no workflow scoping [5](#0-4) [6](#0-5) . This prevents the exact same JTI from being consumed twice anywhere, but it does not prevent a single not-yet-consumed token from being submitted to a different workflow's `Authorize` call than the one it was originally intended for — the digest check only verifies the request body content matches, not the destination workflow.

Consequently, if the same signer key is present in `h.authorizedKeys` for two workflows (workflow A and workflow B) — which is architecturally possible since `authorizedKeys` is populated independently per workflow from node-reported metadata [7](#0-6)  — an attacker who intercepts a valid unexpired JWT/request pair intended for workflow A can submit it to workflow B's `Authorize` call first. Since verification only checks signature, expiry, digest match, and JTI-not-yet-used (globally), the request is accepted for workflow B, and the JTI is then marked as used, potentially also blocking or racing the legitimate request to workflow A.

### Impact Explanation
This allows cross-workflow request impersonation: a request cryptographically intended for one workflow can be diverted to and accepted by another workflow sharing an authorized signer, without any explicit binding check tying the JWT to its intended workflow target. This maps to Chainlink's "request impersonation / oracle identity confusion" bounty class, potentially causing unauthorized workflow triggers or races that consume replay-protection state meant for the legitimate destination.

### Likelihood Explanation
The attacker needs only to be able to observe (intercept) or otherwise obtain a valid signed JWT+request pair before it is consumed — no privileged or admin access is required, since gateway JWT-authorized requests are exactly the kind of externally-submitted data an unprivileged run-role or requesting user handles. The additional precondition (same signer authorized for two workflows) is plausible in deployments where a shared DON/operator key is registered as an authorized key across multiple workflows, which is a supported, non-misconfiguration scenario given `authorizedKeys` is maintained per-workflow independently.

### Recommendation
Bind the JWT cryptographically to the target `workflowID`: include `workflowID` (and ideally the JTI) in the `JWTClaims` payload that is covered by the digest/signature, or explicitly compare `claims.Subject`/a dedicated `WorkflowID` claim against the `workflowID` argument inside `Authorize` before accepting the token. Additionally, scope the JTI replay cache per-workflow (e.g. key by `workflowID + jti`) so consuming a token for one workflow cannot affect or be confused with another workflow's authorization state.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go`:
1. Set up a `WorkflowMetadataHandler` with `authorizedKeys["workflowA"]` and `authorizedKeys["workflowB"]` both containing the same signer's `gateway.AuthorizedKey`.
2. Generate one JSON-RPC request `req` and sign a JWT for it with `utils.CreateRequestJWT(req, ...)` using the shared signer's private key (simulating a token minted for workflow A).
3. Call `h.Authorize("workflowB", token, req)` and assert it currently succeeds (returns the key, no error) — demonstrating the token intended for workflow A is accepted for workflow B.
4. Assert the current implementation contains no check comparing `claims` to `"workflowA"` — confirming the missing binding.
5. After the fix, repeat the same test and assert `Authorize("workflowB", token, req)` returns an authorization error because the JWT was not scoped to `workflowB`.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
