### Title
Stale-epoch instant receipts are dropped from the default-recovery basis, inflating `defaultRecoveryPrice` and freezing late claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report is a null-pointer dereference in `H5C__flush_single_entry`: an entry index is dereferenced even though it does not correspond to a real entry, crashing the flush path. The strongest analog in this codebase is `IdleCreditVault.defaultPendingClaimBasis()`, which dereferences only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch's instant-claim ledger — while `pendingInstantWithdraws != 0` can represent unfunded instant receipts recorded under *earlier* epochs in `instantWithdrawClaimsByEpoch[oldEpoch]` and `instantWithdrawsRequestsByEpoch[user][oldEpoch]` (`contracts/strategies/idle/IdleCreditVault.sol:644-649`, `356-375`). Those stale-epoch receipts are a real liability but are dereferenced through the wrong epoch key — the exact "pointer to a non-existent entry" shape — so they silently vanish from the recovery basis.

### Finding Description
`requestInstantWithdraw` records receipt basis per epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount; instantWithdrawClaimsByEpoch[currentEpoch] += _amount; pendingInstantWithdraws += _amount` (`IdleCreditVault.sol:367-374`). `collectInstantWithdrawFunds` decrements only `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`); the per-epoch ledgers are cleared only per-user at claim time (`_claimDefaultedInstantWithdrawRequest`, `IdleCreditVault.sol:842-856`). So when `startEpoch` funds the instant queue only partially, an unfunded remainder can persist across epochs while its basis stays keyed to the *request* epoch — the code comments themselves acknowledge "pendingInstantWithdraws is the still-unfunded remainder" and that cash "covered only part of the instant queue" (`IdleCreditVault.sol:636-640`, `712-723`).

At `finalizeDefaultRecovery`, the pending basis is `basis = pendingWithdraws; if (pendingInstantWithdraws != 0) basis += instantWithdrawClaimsByEpoch[epochNumber]` (`IdleCreditVault.sol:644-649`). Only the current epoch's instant claims are included; an unfunded remainder keyed to an older epoch is excluded from `totalBasis`. Two consequences:

1. `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (`IdleCreditVault.sol:688`) is computed on an understated basis, so `defaultRecoveryPrice` is inflated. Early `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` callers are paid `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` (`IdleCreditVault.sol:782-783`, `912-916`). Because the reserve was sized for the smaller basis, it drains before all claims are serviced; `defaultRecoveryReserve -= _amount` then underflows and reverts, permanently freezing late claimants' recovery while early claimants were overpaid relative to the fair haircut.
2. The owner of the old-epoch unfunded instant receipt is also stranded: `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (`IdleCreditVault.sol:843-847`), so their remaining `instantWithdrawsRequests` fall through to `_transferFundedClaim`, whose reserve guard `balance - reserve < _amount` reverts (`IdleCreditVault.sol:897-906`). Their receipt is neither haircutted through recovery nor payable at par — a permanent freeze.

### Impact Explanation
Direct theft plus permanent freezing of claims. When a default is finalized while `pendingInstantWithdraws` contains a remainder keyed to a pre-default epoch, `defaultRecoveryPrice` is overstated by a factor of `totalBasis / (totalBasis - missingBasis)`. Early claimants withdraw more than their fair share of a fixed `defaultRecoveryReserve` (theft from other claimants, quantified by the inflation factor), and once `defaultRecoveryReserve` hits zero every subsequent defaulted/post-default claim reverts on the unchecked subtraction in `_transferDefaultRecovery` — a permanent freeze of unclaimed recovery funds. The old-epoch instant receipt holder's claim is likewise permanently unpayable. No privileged misbehavior is required; the trigger is a partially funded instant queue (a routine `startEpoch` liquidity shortfall) followed by an honest borrower default and `finalizeDefault`.

### Likelihood Explanation
Likelihood is moderate. The preconditions are (a) an epoch where `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` funds less than `pendingInstantWithdraws` (possible whenever CDO liquidity at `startEpoch` is tight, and explicitly contemplated by the prefunded-reserve logic), and (b) a subsequent default finalized via `finalizeDefaultRecovery` while that remainder is still pending. Both arise from ordinary borrower/keeper behavior; the attacker only needs to be an instant-withdraw requester or an early recovery claimant to benefit, and the loss falls on honest claimants who did nothing wrong. The bug is a bookkeeping gap rather than an edge-case revert, so it triggers deterministically once the state exists.

### Recommendation
In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, include all outstanding unfunded instant basis, not just `instantWithdrawClaimsByEpoch[epochNumber]` — e.g. track a global `totalInstantClaimBasis` decremented on each instant claim/clear, or treat `pendingInstantWithdraws`'s full unfunded remainder plus its prefunded complement as the instant basis. Correspondingly, `_claimDefaultedInstantWithdrawRequest` should clear a user's receipts across all epochs that contributed to the default basis (or clear `instantWithdrawsRequests[_user]` entirely at `defaultRecoveryPrice`), so old-epoch receipts are haircutted rather than falling through to the at-par funded path and reverting on the reserve guard.

### Proof of Concept
Fork test sketch (add to `test/foundry/IdleCreditVault.t.sol`, reusing `_useStandardEpochVariant`, `_depositWithUser`, `_stopCurrentEpochWithApr`, `_getInstantFunds` helpers and `stdstore` patterns already in the suite):

```solidity
function testDefaultSkipsStaleEpochInstantBasis() external {
  _useStandardEpochVariant();
  // epoch 0: deposits, run, stop with lower APR to arm instant withdrawals
  uint256 mintedAA = idleCDO.depositAA(10_000 * ONE_SCALE);
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

  // user1 requests instant withdraw in epoch 1
  vm.prank(user1);
  uint256 req1 = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

  // epoch 1 starts but CDO funds only HALF the instant queue:
  // warp past instantWithdrawDelay, fund partially via deal/approve to CDO then
  // call the internal collect path so pendingInstantWithdraws keeps a remainder
  vm.prank(manager); cdoEpoch.startEpoch();
  vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
  uint256 pendingInstant = strategy.pendingInstantWithdraws();
  _getInstantFundsPartial(pendingInstant / 2); // helper: collect only half

  // epoch 1 stops; remainder of instant receipts is still keyed to epoch 1
  _stopCurrentEpochWithApr(initialProvidedApr);
  vm.prank(manager); cdoEpoch.startEpoch(); // epoch 2 running

  // borrower defaults at end of epoch 2
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(cdoEpoch.owner()); cdoEpoch.stopEpoch(0, 0); // defaulted
  vm.startPrank(manager);
  underlying.approve(address(strategy), recovered);
  cdoEpoch.finalizeDefault(recovered, manager);
  vm.stopPrank();

  // BUG: defaultPendingClaimBasis only counted instantWithdrawClaimsByEpoch[epochNumber]
  // (epoch 2), so user1's epoch-1 unfunded instant basis inflated defaultRecoveryPrice.
  // Early defaulted-epoch claimants drain defaultRecoveryReserve; the last claimant reverts:
  vm.prank(userLast);
  vm.expectRevert(); // underflow in _transferDefaultRecovery / NotAllowed in _transferFundedClaim
  cdoEpoch.claimWithdrawRequest();

  // user1's stale-epoch instant receipt is also unpayable:
  vm.prank(user1);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.claimInstantWithdrawRequest();
}
```

Uncertainty note: I confirmed the per-epoch keying, the aggregate `pendingInstantWithdraws` remainder, the reserve guard, and the epoch-scoped clearing in `_claimDefaultedInstantWithdrawRequest` directly from the source. I did not fully trace `IdleCDOEpochVariant.getInstantWithdrawFunds`/`collectInstantWithdrawFunds` to confirm the exact call path that leaves a partial `pendingInstantWithdraws` remainder (the in-code comments at `IdleCreditVault.sol:636-640` and `712-723` indicate partial funding is an expected state); the PoC's `_getInstantFundsPartial` helper would need to be implemented against that real funding path rather than `stdstore` shortcuts to be fully faithful.
