### Title
Duplicate tenure-start check uses `get_last_globally_accepted_block` instead of locally-signed state, allowing a signer to sign two conflicting tenure-start blocks - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionsView::validate_tenure_change_payload` rejects a proposed tenure-change block as a duplicate only if `SignerDb::get_last_globally_accepted_block` returns a block for that tenure's `consensus_hash`, i.e. only if the group has already reached signing threshold on some block in that tenure. It never consults the signer's own locally-accepted (self-signed) state for that tenure. If this signer already called `mark_locally_accepted` on tenure-start block A but the tenure stalls before reaching global acceptance, a second, distinct tenure-start block B for the same tenure will pass this check and can be signed too.

### Finding Description
The relevant code:
```
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)
    .map_err(...)?;
if let Some(last_in_current_tenure) = last_in_current_tenure {
    ...
    return Err(RejectReason::DuplicateBlockFound);
}
Ok(())
``` [1](#0-0) 

This is the *only* duplicate-tenure-start guard inside `validate_tenure_change_payload`. It is keyed off global acceptance (i.e., threshold-signed), not off this signer's own locally-committed signature. By contrast, the same file's `SortitionState::is_timed_out` deliberately uses a stricter, self-referential check — `db.has_signed_block_in_tenure(sortition)` — precisely because "a pre-commit carries no signature" and "if it never reaches the pre-commit threshold the tenure can stall indefinitely," and the comment explicitly states the signer "must not help abandon" a tenure it has already signed into:
```
let has_block = db.has_signed_block_in_tenure(sortition)?;
if has_block {
    return Ok(false);
}
``` [2](#0-1) 

This shows the codebase already recognizes and models the distinction between "I signed this" and "the group globally accepted this," yet `validate_tenure_change_payload`'s duplicate-tenure check only uses the latter, weaker notion. An attacker who wins a single miner slot can: (1) propose tenure-start block A for consensus hash CH; the signer validates it, finds no conflict, and calls `mark_locally_accepted` (self-signs A) — but group threshold is never reached (e.g., other signers are slow/offline/disagree, a realistic "stalled first proposal" precondition, not attacker-controlled majority collusion); (2) propose a second, different tenure-start block B also claiming CH as its tenure (e.g., different transaction set/parent selection consistent with the same `prev_tenure_consensus_hash`). When this signer evaluates B via `check_proposal` → `validate_tenure_change_payload`, `get_last_globally_accepted_block(CH)` still returns `None` (since A never reached threshold), so the duplicate check is bypassed, and nothing else in this function or its call path (as read) re-checks this signer's own prior local signature for CH.

### Impact Explanation
If nothing downstream re-derives "did I already locally sign a tenure-start block for this exact tenure" (a genuine equivocation guard, as opposed to a global-acceptance check), then this signer would sign two distinct, conflicting blocks at the same tenure-start position (same `consensus_hash`/tenure, same block height in the chain), breaking UNIQUENESS. This is a Critical chain-safety violation category: a signer producing a conflicting signed block. A single such signer, if it holds meaningful weight, contributes towards two mutually exclusive block-commit chains reaching the shared signing threshold once combined with other signers' independent votes, undermining the fork-choice guarantee signers are supposed to enforce.

### Likelihood Explanation
Preconditions: (1) attacker needs only a single miner slot (their own BTC-won sortition) to author both competing tenure-start blocks/proposals, well within the stated unprivileged-attacker capability; (2) the first proposal must stall at less-than-threshold group acceptance — plausible under normal network conditions (slow signers, temporary partition, disagreement) and not attacker-controlled; (3) the victim signer must have already called `mark_locally_accepted` on the first block, which happens automatically in the normal signing flow whenever `check_proposal` passes. No majority-signer collusion, no compromised keys, no auth_token, and no local host access are required — only crafting and gossiping a second `BlockProposal` for the same tenure. This is repeatable per tenure that stalls before reaching signer threshold.

### Recommendation
Change the duplicate-tenure-start check in `validate_tenure_change_payload` to also (or instead) query the signer's own locally-signed/pre-committed state for the tenure — e.g., use a `has_signed_block_in_tenure`/"last locally-accepted block in tenure" lookup analogous to the one already used in `SortitionState::is_timed_out` — so that once this signer has self-signed any tenure-start block for a given `consensus_hash`, it refuses to sign a second, different tenure-start block for that same tenure regardless of whether global acceptance was ever reached.
