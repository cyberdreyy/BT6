### Title
GET /v2/external_initiators leaks ExternalInitiator.OutgoingToken on every Index call, retrievable indefinitely by any authenticated user regardless of role - ([File: core/web/external_initiators_controller.go], [File: core/web/presenters/external_initiators.go])

### Summary
The `ExternalInitiatorResource` presenter used by `ExternalInitiatorsController.Index` includes the plaintext `OutgoingToken` field, which is re-served on every `GET /v2/external_initiators` call, not just at creation time. Unlike `HashedSecret`/`OutgoingSecret`, this field is never redacted, and the route has no role restriction at all (unlike `Create`/`Destroy`), so any authenticated user of any role can retroactively harvest `OutgoingToken` for external initiators created by other users.

### Finding Description
`ExternalInitiator.OutgoingToken` is generated once at creation in `bridges.NewExternalInitiator` [1](#0-0) . The `Create` handler returns it via `presenters.ExternalInitiatorAuthentication`, which is the "creation-only" credential-bearing presenter [2](#0-1) .

However, `Index` uses a separate presenter, `presenters.ExternalInitiatorResource`, which also carries `OutgoingToken` as a plain, non-omitempty JSON field: [3](#0-2) 

`ExternalInitiatorsController.Index` builds this resource from the DB-persisted `ExternalInitiator` for every row and returns it in the paginated response, unconditionally including `OutgoingToken`: [4](#0-3) 

The existing integration test confirms this behavior end-to-end — it fetches `/v2/external_initiators`, deserializes into `[]presenters.ExternalInitiatorResource`, and explicitly asserts `externalInitiators[0].OutgoingToken` equals the originally generated `eiFoo.OutgoingToken`/`eiBar.OutgoingToken`, i.e., the outgoing token is available at any later point, not just at creation: [5](#0-4) 

Route registration shows `GET /v2/external_initiators` has **no role gate at all** (`paginatedRequest(eia.Index)`), unlike `POST`/`DELETE` on the same resource which require `auth.RequiresEditRole`: [6](#0-5) 

This means any authenticated principal — including a session/token holder with only View role — can call Index and retrieve `OutgoingToken` for every external initiator in the system, including ones they did not create. `HashedSecret` and `OutgoingSecret` are not present on `ExternalInitiatorResource`, so those two specific fields are not leaked by Index; only `OutgoingToken` is.

### Impact Explanation
`OutgoingToken` is one half of the outgoing credential pair (`OutgoingToken`/`OutgoingSecret`) that the node uses when calling out to the external initiator's webhook endpoint (analogous to the bridge `OutgoingToken` used for outbound bridge authentication, per `core/bridges/bridge_type.go`). Persistent, role-unrestricted disclosure of this token via Index allows a low-privileged (even View-role) account to harvest per-initiator credentials indefinitely, which can be used to impersonate the node in outbound requests to that initiator's endpoint or to correlate/replay flows tied to that credential. This is a credential-disclosure class finding, though the blast radius is narrower than claimed in the question since `OutgoingSecret` and `HashedSecret` are not part of `ExternalInitiatorResource` and thus are not exposed by Index/Show.

### Likelihood Explanation
Any authenticated user (session cookie or API token) can trivially call `GET /v2/external_initiators` — no elevated role, no ownership check, and no special preconditions beyond having valid, low-privilege node credentials. The behavior is deterministic and repeatable (confirmed by the existing test assertions), making exploitation trivial and requiring no timing or race conditions.

### Recommendation
Remove `OutgoingToken` from `presenters.ExternalInitiatorResource` (or make it `omitempty` and only populate it in a one-time creation-only presenter), so Index/Show responses redact outgoing credentials the same way `HashedSecret`/`OutgoingSecret` are already excluded. Additionally, consider gating `GET /v2/external_initiators` with an appropriate role (e.g., `auth.RequiresEditRole` or higher) consistent with the mutating endpoints on the same resource, since it currently has no role check at all.

### Proof of Concept
Extend `TestExternalInitiatorsController_Index` (or add a new test) in `core/web/external_initiators_controller_test.go`:
1. Create an external initiator via `POST /v2/external_initiators`, capture `OutgoingToken` from the `ExternalInitiatorAuthentication` response (already covered by `TestExternalInitiatorsController_Create_success`).
2. As a separate, lower-privileged (View-role) authenticated client, call `GET /v2/external_initiators`.
3. Assert the returned `presenters.ExternalInitiatorResource.OutgoingToken` equals the value captured at creation (this is already effectively demonstrated by the existing assertions at lines 109 and 126 of `external_initiators_controller_test.go`).
4. Add a new assertion that this succeeds even for a client authenticated with only View role (no `RequiresEditRole`/`RequiresAdminRole` gate on the route), proving cross-role/cross-user retroactive credential harvesting.

	hashedSecret, err := auth.HashedSecret(eia, salt)
	if err != nil {
		return nil, pkgerrors.Wrap(err, "error hashing secret for external initiator")

	return &ExternalInitiator{
		Name:           strings.ToLower(eir.Name),
		URL:            eir.URL,
		AccessKey:      eia.AccessKey,
		HashedSecret:   hashedSecret,
		Salt:           salt,
		OutgoingToken:  utils.NewSecret(utils.DefaultSecretSize),
		OutgoingSecret: utils.NewSecret(utils.DefaultSecretSize),
	}, nil

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

		AccessKey:     ei.AccessKey,
