### Title
BB tranche holder frontruns `stopEpochWithDuration` with `requestWithdraw` to convert BB-first loss exposure into a pro-rata pending receipt, pushing losses onto AA holders and other withdrawers - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
Analogous to a recipient frontrunning `allocate` to rewrite agreed terms, a KYC-passed BB holder can frontrun a manager's loss-applying `stopEpochWithDuration(0, _interest, _duration, _lossAmount)` call (or `stopEpoch` in the same window) by calling `requestWithdraw`. The request converts their BB tranche position into a pending withdraw receipt before `_stopEpoch` runs, so their principal is haircut pro-rata across all receipts instead of absorbing losses BB-first.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the pending-receipt loss is computed first and applied pro-rata across all pending receipts, while the remainder is applied BB-first to active tranches: [1](#0-0) 

`requestWithdraw` has no check that `block.timestamp < epochEndDate`; it only requires `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed(msg.sender)`, both still true in the window between `epochEndDate` and the manager's `stopEpoch`/`stopEpochWithDuration` transaction: [2](#0-1) 

`IdleCreditVault.requestWithdraw` burns the CDO's principal, mints an equal receipt to the user, and records it under the current epoch, whose haircut price is stored in `lossRecoveryPriceByEpoch` at stop: [3](#0-2) 

Attack sequence (running epoch, fixed-APR mode, mempool-visible lossy stop):

1. Epoch ends (`block.timestamp >= epochEndDate`) but `isEpochRunning` is still true and withdraw-request flags are enabled.
2. Manager submits `stopEpochWithDuration(0, interest, duration, _lossAmount)` applying a loss.
3. Attacker (KYC'd BB holder, e.g. dominant BB position) frontruns with `requestWithdraw(bbBalance, BBTranche)`.
4. `_stopEpoch` now counts the attacker's principal as a pending receipt: its loss share is `_lossAmount * attackerReceipt / totalReceipts` instead of the much larger BB-first share it would have borne as an active BB position.
5. The escaping share is pushed onto (a) the other pending receipts via `lossRecoveryPriceByEpoch` haircuts and (b) remaining active tranches, ultimately AA once residual BB is exhausted — inverting the waterfall ordering the receipts/AA priced in.

### Impact Explanation
Broken invariant: BB-first loss waterfall. Innocent pending withdrawers receive a larger haircut via `lossRecoveryPriceByEpoch` and AA holders absorb loss earlier than designed. Quantified: the attacker avoids `min(bbLossShareBBFirst, attackerBBNAV) - proRataReceiptShare`, which can be arbitrarily large when the attacker dominates the BB side and at least one other receipt exists to dilute the receipt bucket.

### Likelihood Explanation
Requires a loss event (`_lossAmount > 0` via `stopEpochWithDuration`, or a default path), a public-mempool environment (Ethereum mainnet deployments of these vaults qualify), an attacker with a KYC-passed wallet holding BB tranches, and at least one other pending receipt to dilute. All attacker actions use only public, permissionless-for-lender functions during a legitimate epoch phase; no privileged cooperation needed.

### Recommendation
Disable `requestWithdraw` once `block.timestamp >= epochEndDate` while `isEpochRunning` (the "closing" window), or include late-filed receipts in the BB-first waterfall rather than the pro-rata receipt bucket. Alternatively, snapshot pending receipts at `epochEndDate` and treat receipts created after it as active tranche positions for loss purposes.

### Proof of Concept
Foundry fork-style outline (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testFrontrunLossyStopEpoch() public {
    // setup: user1 deposits AA, victim requests withdraw in epoch N (pending receipt),
    // attacker deposits large BB position, epoch N running.

    uint256 bbBal = IERC20(BBTranche).balanceOf(attacker);

    // warp past epochEndDate; manager's stopEpochWithDuration(_lossAmount) is in mempool
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // frontrun: attacker converts BB exposure into a pending receipt
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(bbBal, address(BBTranche));

    // manager executes lossy stop
    _repayBorrower(interest + strategy.pendingWithdraws());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, interest, duration, lossAmount);

    // assert: victim receipt haircut grew (lossRecoveryPriceByEpoch lower),
    // attacker's claimable amount exceeds what an active-BB position would
    // have been worth under BB-first accounting, and AA price fell more
    // than in the non-frontrun baseline run.
}
```

A control run without the frontrun shows the attacker's BB NAV absorbing the loss first; with the frontrun, the victim receipt and AA price absorb it instead. Exact delta should be asserted numerically using `virtualPrice(BBTranche)`/`lossRecoveryPriceByEpoch` before and after.
