## #Vulnerability found for Q0595

### Title
Stale confirmations from removed members inflate `confirmations.len()`, letting a request execute below live `num_confirmations` - (File: `multisig2/src/lib.rs`)

### Summary
`confirm()` decides whether to execute a request by comparing `confirmations.len() as u32 + 1 >= self.num_confirmations`, where `confirmations` is a `HashSet<String>` of member identifiers accumulated over the lifetime of the request. `delete_member()` only purges confirmation sets for requests originally *created* by the removed member, not confirmations that member cast on *other* members' requests, so a stale confirmation from an account/key no longer in `self.members` continues to count toward the threshold.

### Finding Description
The invariant the code should maintain is: `confirmations.len() == |{ live members who confirmed request_id }|` at the moment of the threshold check in `MultiSigContract::confirm`, `multisig2/src/lib.rs:294-315`. That invariant is broken because membership changes (`DeleteMember`, executed via `delete_member`, `multisig2/src/lib.rs:356-379`) only scrub confirmation entries for requests whose `request_with_signer.member == member` (i.e., requests *authored* by the removed member): [1](#0-0) 

Any confirmation that the removed member previously cast on a *different* request (one authored by someone else) is left untouched in the `confirmations: LookupMap<RequestId, HashSet<String>>` map. `confirm()` still evaluates the raw stored count: [2](#0-1) 

`current_member()` only validates the caller against the live member set for the *current* call, not against the historical confirmations already stored: [3](#0-2) 

Exploit flow (num_confirmations = 3, members = {A, B, C, D}):
1. D calls `add_request` to create request `R` (e.g., a `Transfer`).
2. A calls `confirm(R)` → `confirmations = {A}`.
3. B calls `confirm(R)` → `confirmations = {A, B}`.
4. Members B, C, D create and confirm a separate `DeleteMember { member: A }` request (3 confirmations against a request authored by, say, C — not A), which succeeds and removes A from `self.members`. Because that removal request was not authored by A, `delete_member`'s request-cleanup loop does not touch `R`'s confirmation set; A's stale entry in `confirmations` for `R` survives.
5. Members are now {B, C, D}. C calls `confirm(R)`: `confirmations.len()` is still 2 (`{A, B}`), so `2 + 1 >= 3` is true, and `execute_request` fires the `Transfer` — even though only B and C are live members who ever confirmed `R` (2 live confirmations, one short of the required 3).

None of the existing guards catch this: `assert_valid_request` only checks that the *caller* is currently a member, not that previously stored confirmers still are; there is no re-validation of `confirmations` contents against `self.members` anywhere in `confirm` or `delete_member`.

### Impact Explanation
This lets a multisig request (including `Transfer`, `AddKey`, `AddMember`, `FunctionCall`, etc.) execute with fewer than `num_confirmations` currently-authorized signers, directly matching the Critical category "a multisig request executed below `num_confirmations` live members." Because `Transfer` and `AddKey`/`AddMember` actions can move NEAR out of the account or grant new access, the blast radius is the full balance and control of the multisig account. The bug is repeatable on every multisig instance deployed via the factory whenever membership changes occur while requests are outstanding.

### Likelihood Explanation
The precondition is realistic and not exotic: any multisig that rotates members (a normal, expected operation — e.g., replacing a compromised key or removing a departing member) while an unrelated request has partial confirmations will hit this. No attacker needs elevated privileges beyond being (at some point) a legitimate member of the multisig, and the final triggering confirm is a completely ordinary `confirm()` call by a still-valid member who does nothing "wrong" — the stale state is silently exploited by the existing code path. This makes it highly likely to occur in practice, whether accidentally or through deliberate timing by a member who wants to push through a request with fewer real confirmations.

### Recommendation
When executing `delete_member`, iterate all outstanding requests' confirmation sets (not just those authored by the removed member) and remove the removed member's entry from each. Alternatively/additionally, in `confirm()`, recompute the effective confirmation count by intersecting stored confirmation identifiers with the current `self.members` set before comparing against `self.num_confirmations`, rather than trusting `confirmations.len()` directly.

### Proof of Concept
`cargo test` plan (extends `multisig2/src/lib.rs` test module):
```rust
#[test]
fn test_stale_confirmation_bypasses_threshold() {
    // members(): [alice(Account), bob(Account), key_c(AccessKey), key_d(AccessKey)]
    // num_confirmations = 3
    let amount = 1_000;
    testing_env!(context_with_account(bob(), amount));
    let mut c = MultiSigContract::new(members(), 3);

    // D (key_d) creates request R: transfer to bob
    testing_env!(context_with_key(PublicKey::try_from(TEST_KEY.to_vec()).unwrap(), amount));
    let request_id = c.add_request(MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    });

    // A (alice) confirms R
    testing_env!(context_with_account(alice(), amount));
    c.confirm(request_id);

    // B (bob) confirms R -> confirmations = {alice, bob}, len == 2
    testing_env!(context_with_account(bob(), amount));
    c.confirm(request_id);
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 2);

    // Remove alice via a *different* request authored by key_d, confirmed by bob + key_c + key_d
    testing_env!(context_with_key(PublicKey::try_from(TEST_KEY.to_vec()).unwrap(), amount));
    let del_id = c.add_request(MultiSigRequest {
        receiver_id: alice(), // current_account_id in this test setup
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::Account { account_id: alice() },
        }],
    });
    c.confirm(del_id); // key_d confirms
    testing_env!(context_with_account(bob(), amount));
    c.confirm(del_id); // bob confirms
    testing_env!(context_with_key(PublicKey::from(
        "ed25519:Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()), amount));
    c.confirm(del_id); // key_c confirms -> executes DeleteMember, alice removed

    // R's confirmations still contain the stale "alice" entry
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 2);
    assert!(!c.members.contains(&MultisigMember::Account { account_id: alice() }));

    // Only bob and key_c are live confirmers of R (2 live), yet one more live confirm executes it
    testing_env!(context_with_key(PublicKey::from(
        "ed25519:Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()), amount));
    c.confirm(request_id); // len()==2, +1 >= 3 -> executes with only {bob, key_c} as live confirmers

    // R executed despite only 2 live-member confirmations, not 3
    assert_eq!(c.requests.len(), 0);
}
```
This test demonstrates `confirmations.len() as u32 + 1 >= self.num_confirmations` (`multisig2/src/lib.rs:304`) evaluating true while the set of *live-member* confirmers is `2 < num_confirmations (3)`, proving the invariant break and unauthorized execution.
