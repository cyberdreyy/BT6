### Title
Unbounded, unlimited-memory `getProgramAccounts` scan when secondary indexes are disabled — (File: `rpc/src/rpc.rs`, `accounts-db/src/accounts.rs`)

### Summary
Analogous to the RabbitHole `Quest.claim()` DOS, where an unbounded iteration over a user/griefer-controlled, ever-growing token set could exhaust gas, Agave's `getProgramAccounts` RPC path can be forced into an unbounded, memory-unbounded full scan by an attacker who inflates the number of accounts owned by a given program/address, with no byte-size cap enforced on that specific code path.

### Finding Description
`JsonRpcRequestProcessor::get_filtered_program_accounts` branches on whether the `ProgramId` secondary index is enabled: [1](#0-0) 

- If the `ProgramId` account index **is** enabled, it calls `get_filtered_indexed_accounts`, which explicitly passes `self.config.scan_results_limit_bytes` (`byte_limit_for_scans`) down into `Accounts::load_by_index_key_with_filter`, which enforces `accumulate_and_check_scan_result_size` and aborts the scan (`ScanError::Aborted`) once the accumulated result size crosses the configured byte limit: [2](#0-1) [3](#0-2) 

- If the `ProgramId` secondary index is **not** enabled — which is the common/default configuration, since account secondary indexes are opt-in — the code takes the "else" branch, explicitly commented `// this path does not need to provide a mb limit because we only want to support secondary indexes`, and calls `bank.get_filtered_program_accounts`, which flows into `Accounts::load_by_program_with_filter`: [4](#0-3) [5](#0-4) 

`load_by_program_with_filter` uses a plain `Vec` collector and `ScanConfig::default()` with **no `byte_limit_for_scan` parameter at all** — unlike its indexed sibling `load_by_index_key_with_filter`, it has no mechanism to abort or cap the accumulated result size. `scan_accounts` in `accounts_db.rs` will walk the entire live account set (cache + index) and push every account whose `owner() == program_id` and that passes the filter into the in-memory collector, with no cap on count or bytes: [6](#0-5) 

This mirrors the reported bug class exactly: a caller (or a griefer who creates a large number of low-value accounts owned by a target program/address to be scanned) can inflate the eventual "token/account list" the validator must materialize fully in memory in one synchronous call, with no configured ceiling on the non-indexed path.

### Impact Explanation
This is reachable purely through the public RPC surface (`getProgramAccounts` when program-id secondary indexing is off, which is the default), i.e. "RPC request handling," one of the permitted analog categories. An attacker who mass-creates many small accounts owned by a given `program_id` (or convinces/waits for legitimate protocol usage to accumulate many accounts, exactly as in the original report's "Bob sends Alice many tokens" griefing scenario) can force any RPC node servicing that query to allocate and hold a `Vec<(Pubkey, AccountSharedData)>` covering the entire matching set in memory, unbounded by `scan_results_limit_bytes` on this path. Depending on account count/size this can cause excessive memory pressure, long scan-holding of the accounts index/scan guard, and ultimately RPC node resource exhaustion/crash for that request path — a legitimate "RPC crash"/ingest-starvation class impact, distinct from and weaker than fund-loss/consensus-divergence classes, but consistent with the accepted impact categories (RPC crash).

### Likelihood Explanation
Medium. Exploitation requires only permissionless account creation under a chosen `program_id` (any user can create accounts owned by an arbitrary program by funding rent), then issuing (or having a third party issue) a `getProgramAccounts` call with `account_indexes` not covering `ProgramId` for that key — which is the out-of-the-box default unless the validator operator has explicitly configured `--account-index program-id`. The severity is bounded by validator-side timeouts/OOM behavior and by the fact many operators disable `full_rpc_api` or don't serve `getProgramAccounts` publicly, but for RPC nodes that do serve it (a common configuration for indexers/wallets), no size guard exists on this path today.

### Recommendation
Apply the same `byte_limit_for_scan`/`scan_results_limit_bytes` enforcement used in `load_by_index_key_with_filter` to the non-indexed path in `Accounts::load_by_program_with_filter` (and, by extension, `load_by_program`), i.e. thread `self.config.scan_results_limit_bytes` through `get_filtered_program_accounts`'s non-indexed branch in `rpc/src/rpc.rs` and call `accumulate_and_check_scan_result_size`/abort-on-exceeded inside the non-indexed scan callback in `accounts-db/src/accounts.rs`, so both indexed and non-indexed `getProgramAccounts` scans are subject to the same configured result-size ceiling.

### Proof of Concept
1. Run a validator/RPC node with default `account_indexes` (no `ProgramId` secondary index configured) and `getProgramAccounts` exposed.
2. As an attacker, submit many low-lamport system/program-owned accounts (e.g., repeatedly invoke a program that creates PDAs/accounts owned by `program_id X`) until the account count under `X` is very large.
3. Call `getProgramAccounts(X)` (or wait for a legitimate client/indexer to do so). Because the request takes the `else` branch in `get_filtered_program_accounts` (`rpc/src/rpc.rs:2283-2298`), it calls `bank.get_filtered_program_accounts` → `Accounts::load_by_program_with_filter`, which has no `byte_limit_for_scan`, unlike the indexed path — the RPC worker thread must materialize the entire result set in memory before returning, with no configured abort point, unlike the indexed-scan path that would have aborted per `scan_results_limit_bytes`.

    pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
        if sort_results {
            // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
            accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
        }
        Ok(accounts)
    }

    fn calc_scan_result_size(account: &AccountSharedData) -> usize {
        account.data().len()
            + std::mem::size_of::<AccountSharedData>()
            + std::mem::size_of::<Pubkey>()
    }

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    fn maybe_abort_scan(
        result: ScanResult<Vec<KeyedAccountSharedData>>,
        config: &ScanConfig,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        if config.is_aborted() {
            ScanResult::Err(ScanError::Aborted(
                "The accumulated scan results exceeded the limit".to_string(),
            ))
        } else {
            result
        }
    }
