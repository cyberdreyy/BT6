## Title
Unsigned `reason_code`/`response_data` fields in `BlockRejection` let a relayer rewrite a signer's rejection reason and `failed_txid` without invalidating the signature - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` computes the signature digest over only `signer_signature_hash` and `chain_id`. `reason`, `reason_code`, `metadata`, and `response_data` (which carries `reject_reason` and `failed_txid`) are excluded from what is signed, yet `verify`/`recover_public_key` treat a signature over that narrow digest as authenticating the whole struct. This is the same bug class as the Traefik `Connection`-header issue: content that downstream consumers rely on for a security-relevant decision is not covered by the integrity mechanism that is supposed to protect the message, so an on-path relayer can drop/rewrite it while the "trusted" signature still checks out. [1](#0-0) 

### Finding Description
`BlockRejection` is a struct that mixes a small signed core (`signer_signature_hash`, `chain_id`) with a much larger set of fields that are *not* part of the signature: `reason` (free text), `reason_code`, `metadata`, and `response_data` (`reject_reason`, `failed_txid`, tenure-extend timestamps). [2](#0-1) 

`sign()`/`hash()` only bind the signature to `signer_signature_hash` + `chain_id`: [3](#0-2) 

The node's `stackerdb_listener.rs` recovers the pubkey from this narrow signature and, once it matches the expected signer's key, treats every other field of the struct - including `reason_code` and `response_data.failed_txid` - as authentic and uses them to update consensus-relevant weight-accounting state (`total_weight_rejected`, per-`failed_txid` weight, `problematic_weight`): [4](#0-3) [5](#0-4) 

Because `reason_code`/`response_data` are outside the signed digest, any party that can place a chunk into that signer's StackerDB slot (or otherwise get a modified copy of the message accepted, e.g. through message-replay/relay paths that don't re-verify field-by-field) can substitute a different `reason_code`/`response_data.failed_txid`/`reject_reason` while keeping the original, still-valid `signature`. `BlockRejection::verify()`/`recover_public_key()` will report success because they only ever re-derive `hash()` from the two signed fields - they never notice the swapped `reason_code`/`response_data`.

This breaks the equality the node relies on: "the rejection code/txid attributed to signer S is what S actually decided" vs. "the rejection code/txid an attacker relayed under S's signature." Concretely, the `failed_txid` weight-accounting logic in the coordinator (used to decide whether a tx is "problematic" and should be dropped/blacklisted, section `StackerDBListener`) can be fed an attacker-chosen `failed_txid`/`ValidateRejectCode::ProblematicTransaction` under a legitimate signer's signature, mis-attributing blame for a rejection to a transaction the signer never actually flagged, and correspondingly miscounting per-txid rejection weight without needing a majority of signers or their keys — only control over one relayed message for one signer's already-signed rejection.

### Impact Explanation
This is a rejection-content forgery: the aggregate "which txid is problematic and by how much signer weight" bookkeeping (`stackerdb_listener.rs`'s `failed_txids` map) can be corrupted by rewriting the unsigned `response_data.failed_txid`/`reason_code` fields of one already-signed rejection message, causing a miscounted response that does not reflect the real BlockRejection semantics the signer intended. It maps to the "rejection recounted" class called out in scope: the node believes a specific `RejectCode`/`failed_txid` combination was produced by a specific signer's signature, when in fact only the narrow `(signer_signature_hash, chain_id)` tuple was actually authenticated.

### Likelihood Explanation
Requires only the ability to substitute the mutable, unsigned trailer of an already-signed `BlockRejection` (a single message from a single signer) while the signature remains attached — no majority of signers, no possession of any signer's private key, and no majority collusion is needed; this is well within the "one-slot miner plus gossip" threat model since the fields are simply not covered by the cryptographic check performed in `verify()`/`recover_public_key()`.

### Recommendation
Include `reason`, `reason_code`, `metadata`, and `response_data` (or a hash/commitment of them) in the `BlockRejection::hash()` digest that gets signed, so any tampering with those fields invalidates the signature. Apply the same audit to `BlockAccepted`/other `SignerMessage` variants to ensure no consensus- or accounting-relevant field is excluded from the signed payload.

### Proof of Concept
1. Signer S produces a genuine `BlockRejection` for block `H` with `response_data.reject_reason = RejectReason::SortitionViewMismatch`, `reason_code = RejectCode::SortitionViewMismatch`, `failed_txid = None`, signed via `BlockRejection::new`/`sign` (only over `H` + `chain_id`).
2. A relayer intercepts the serialized `SignerMessage::BlockResponse(BlockResponse::Rejected(..))` chunk before/while it is being read by node instances, and rewrites `reason_code` to `RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` and `response_data.failed_txid = Some(victim_txid)`, leaving `signer_signature_hash`, `chain_id`, and `signature` untouched.
3. Node's `stackerdb_listener.rs` calls `rejected_data.recover_public_key()` [6](#0-5)  — this succeeds and matches S's known pubkey because `hash()` never touched the tampered fields.
4. The listener then attributes `signer_entry.weight` to `victim_txid`'s `problematic_weight`/`total_weight` bucket [7](#0-6)  even though signer S never actually flagged `victim_txid` as problematic — the rejection's real content was silently substituted, analogous to stripping/replacing an "Important-Security-Header" that only the backend was supposed to trust.

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }
