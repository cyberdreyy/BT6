### Title
Unchecked deposit size overflows fixed-APR accounting and freezes withdrawals - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`_guarded()` only compares a deposit with the configured TVL limit and does not bound deposits against the arithmetic used by `_calcInterestWithApr()`. [1](#0-0) [2](#0-1) 

A sufficiently large unprivileged deposit can therefore be accepted and then make both `startEpoch()` and `requestWithdraw()` revert with an arithmetic overflow until the APR is reduced to zero. [3](#0-2) [4](#0-3) 

### Finding Description
Deposits pass only `_guarded(_amount)` before the strategy mints one strategy-token unit per underlying unit. [5](#0-4) [6](#0-5) 

The deposited principal later feeds `_calcInterestWithApr()`, which evaluates `_amount * (_apr / 100) * epochDuration` before dividing by `365 days * ONE_TRANCHE_TOKEN`. [2](#0-1) 

Because `startEpoch()` calculates interest on the entire contract value, an attacker can deposit `type(uint256).max / ((_apr / 100) * epochDuration) + 1` base units and make the honest manager's `startEpoch()` call revert. [7](#0-6) 

The same overflow also affects `requestWithdraw()`, because `_calcInterestWithdrawRequest()` first calculates total vault interest from `_managedContractValue()`. [8](#0-7) [9](#0-8) 

Unlike donated raw underlying, the attacker's deposit is accounted TVL and cannot be removed by `_skimDonatedAssets()`, because `_deposit()` transfers it into the strategy and mints backing strategy tokens. [10](#0-9) [6](#0-5) 

### Impact Explanation
The oversized deposit temporarily freezes the vault's epoch lifecycle and normal withdrawal-request path for all existing lenders. [11](#0-10) [12](#0-11) 

In the fork configuration, a victim deposit of `10,000 USDC` is blocked once the attacker deposits approximately `3.23e53` USDC base units, and the manager can restore accounting only by setting the APR to zero and forfeiting the epoch's fixed-rate yield. [13](#0-12) 

If the attacker keeps the oversized position in the vault, every later positive-APR epoch remains exposed to the same overflow, while the attacker can still exit through the zero-APR withdrawal flow. [14](#0-13) 

### Likelihood Explanation
The likelihood is low because the attacker must control an extremely large underlying balance and the configured `limit` must permit the deposit. [1](#0-0) 

However, `limit = 0` explicitly means unlimited, the factory accepts the configured limit without checking it against arithmetic safety, and a KYC-passing lender can execute the deposit without compromising owner, manager, guardian, borrower, or strategy privileges. [15](#0-14) [16](#0-15) 

### Recommendation
Enforce a dynamic maximum deposit based on the current scaled APR and epoch duration, for example by requiring `getContractValue() + _amount <= type(uint256).max / ((_apr / 100) * epochDuration)` before accepting funds. [17](#0-16) 

Alternatively, implement the interest calculation with a checked `mulDiv`-style operation and explicitly handle an out-of-range result as a rejected deposit configuration rather than allowing an accepted deposit to poison later epoch accounting. [2](#0-1) 

The same bound should be applied to `depositDuringEpoch()`, which independently calls `_calcInterest(_amount)` before minting discounted shares. [18](#0-17) 

### Proof of Concept

function testOversizedDepositOverflowsEpochAccounting() external {
    uint256 victimDeposit = 10_000 * ONE_SCALE;
    idleCDO.depositAA(victimDeposit);

    uint256 scaledApr = IdleCreditVault(address(strategy)).lastApr();
    uint256 coefficient = (scaledApr / 100) * cdoEpoch.epochDuration();
    uint256 oversizedDeposit = type(uint256).max / coefficient + 1;

    address attacker = makeAddr("oversized-depositor");
    deal(defaultUnderlying, attacker, oversizedDeposit);

    vm.startPrank(attacker);
    underlying.approve(address(cdoEpoch), oversizedDeposit);
    cdoEpoch.depositAA(oversizedDeposit);
    vm.stopPrank();

    vm.expectRevert(stdError.arithmeticError);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.expectRevert(stdError.arithmeticError);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    uint256 requested = cdoEpoch.requestWithdraw(
        victimDeposit,
        address(AAtranche)
    );
    assertEq(requested, victimDeposit);
}

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
