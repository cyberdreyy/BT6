### Title
Confirmations from a revoked/deleted key or member remain valid and are counted toward the multisig threshold, allowing a request to execute below the intended live-signer threshold - ([File: multisig/src/lib.rs], [File: multisig2/src/lib.rs])

### Summary
Both `multisig` and `multisig2` contracts implement a K-of-N confirmation scheme where `confirm()` counts entries in a per-request `confirmations` set and executes the request once the count reaches `num_confirmations` [1](#0-0) . When a key/member is removed via `DeleteKey`/`DeleteMember`, the contract only purges *requests created by* that key/member, but does not scan and strip that key/member's *confirmations left on other pending requests* they had merely confirmed [2](#0-1) [3](#0-2) . This breaks the equality "confirmations counted == confirmations from currently live members," letting a request execute (e.g., a `Transfer` draining the account) with fewer live, authorized signers than `num_confirmations` requires.

### Finding Description
`confirm()` in both contracts checks `confirmations.len() as u32 + 1 >= self.num_confirmations` and, once satisfied, executes the request via `execute_request` [4](#0-3) . The `confirmations` map is a separate data structure (`request_id -> HashSet<PublicKey>` in `multisig`, `request_id -> HashSet<String>` in `multisig2`) from `requests` (`request_id -> MultiSigRequestWithSigner`, which only records the *creator's* key/member) [5](#0-4) [6](#0-5) .

When a `DeleteKey` action executes in `multisig`, cleanup only removes requests whose `signer_pk == pk` (i.e., requests *created* by the deleted key), and clears their confirmation sets along with them: [2](#0-1) 
It never iterates over `self.confirmations` for *other* requests to remove the deleted key from confirmation sets it had merely joined (not created). The identical pattern exists in `multisig2`'s `delete_member`: [3](#0-2) 

As a result, if member/key `D` confirms request `X` (created by someone else), and afterward `D` is removed from the multisig via a separate `DeleteKey`/`DeleteMember` request, `X`'s confirmation set still contains `D`'s entry. A later `confirm(X)` call by a remaining live member counts `D`'s stale confirmation toward `num_confirmations`, allowing `X` to execute even though only `num_confirmations - 1` (or fewer) currently-live members actually authorized it. `execute_request` will then run arbitrary bundled actions, including `Transfer` of the full account balance [7](#0-6) .

### Impact Explanation
This directly matches the allowed impact bucket "a multisig request executed below threshold" (Critical). An attacker who is (or colludes with) a soon-to-be-removed key/member can pre-confirm a malicious `Transfer` request before their removal is finalized; the removal transaction's cleanup logic does not retroactively invalidate that confirmation. The malicious request can later be pushed to execution by collecting only `num_confirmations - 1` genuinely live confirmations, moving NEAR out of the multisig account without the number of live authorizers the contract's K-of-N invariant is supposed to guarantee.

### Likelihood Explanation
Requires: (1) a member/key that will later be removed to first confirm a pending malicious/benign-looking request, and (2) that request to survive until after the removal and then be pushed over the confirmation threshold by remaining signers (who may be unaware the count includes a stale/revoked confirmation, since `get_confirmations` reports raw stored keys, not filtered against current membership) [8](#0-7) [9](#0-8) . This is a purely mechanical state-inconsistency (no economic cost, no privileged actor needed beyond a legitimate member who is later removed), making it readily triggerable in normal multisig operational flows (e.g., key rotation for a compromised or departing signer) rather than a contrived edge case.

### Recommendation
When executing `DeleteKey`/`DeleteMember`, iterate over all pending `requests`/`confirmations` entries and remove the deleted key/member's entry from every confirmation set (not just requests it created), or alternatively re-validate at `confirm()` time that all recorded confirmations for a request still correspond to current members before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig initialized with `num_confirmations = 3` and members `A, B, C, D, E`.
2. Member `C` creates request `X` (a `Transfer` draining the account) via `add_request`.
3. Member `D` calls `confirm(X)` → `confirmations[X] = {D}`.
4. Separately, members confirm and execute a `DeleteKey`/`DeleteMember` request removing `D` (e.g., because `D`'s key was compromised). `execute_request`'s `DeleteKey`/`DeleteMember` branch only purges requests *created* by `D`; `X` (created by `C`) is untouched, so `confirmations[X]` still contains `D`.
5. Member `E` calls `confirm(X)` → `confirmations[X].len() + 1 = 2 (stale D + fresh E, plus E itself makes it {D, E} then +1 for the caller counted before insert) ` reaches `3 >= num_confirmations`, and `X` executes.
6. Only `C` (creator, uncounted in confirmations) and `E` are genuinely live confirmers besides the stale `D`; the transfer executes with effectively fewer than 3 live authorizing confirmations, violating the K-of-N guarantee and draining funds from the account not entitled to be moved by that authorization set.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
