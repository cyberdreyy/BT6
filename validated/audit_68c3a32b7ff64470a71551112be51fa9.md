### Title
A single queued dust deposit permanently reverts `stopEpochWithDuration`, freezing the prefunded epoch for all users - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
Analog to GHSA-8vwm-8vj8-rqjf (fscrypt): an unprivileged user creates a cheap artifact (a malicious metadata file there; a raw queued deposit here) that a shared privileged path fails to handle, denying service to everyone. In `IdleCDOEpochQueue`, any KYC-passing lender can leave a dust `requestDeposit` sitting in `epochPendingDeposits` for the epoch being settled. `prefundedDepositsToProcess` then hard-reverts inside `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration`, which reverts the whole `stopEpochWithDuration` transaction, so the epoch can never be stopped and no withdrawals can be processed.

### Finding Description
- During a running epoch, `requestDeposit` pulls underlying from any allowed wallet and increments `epochPendingDeposits[nextEpoch]` (`contracts/IdleCDOEpochQueue.sol:103-127`).
- `processDepositsToBorrower` (owner/manager) converts pending deposits into `epochPrefundedDeposits` and forwards them to the borrower, but only while `block.timestamp + prefundedDepositWindow < epochEndDate` (`contracts/IdleCDOEpochQueue.sol:149-180`). After that cutoff (and always after `epochEndDate`), prefunding is impossible, and `deleteRequest` can only be called by the depositor for their own funds (`contracts/IdleCDOEpochQueue.sol:184-199`).
- At epoch end, `stopEpochWithDuration` runs `_afterStopEpochWithDuration`, which calls `prefundedDepositsToProcess()`. That view reverts when `epochPendingDeposits[_epoch] != 0`, where `_epoch = epochNumber` after the stop-time increment — exactly the bucket that deposits queued during the just-finished epoch wrote to (`contracts/IdleCDOEpochQueue.sol:277-291`, `contracts/IdleCDOEpochVariantPrefunded.sol:72-89`).
- Because the revert propagates through `stopEpochWithDuration`, `isEpochRunning` stays true, `epochEndDate` remains set, and every subsequent stop attempt reverts identically. Withdrawal requests are gated on `allowAAWithdrawRequest`/`isEpochRunning`, so all LP funds and the borrower's repaid cash are frozen.

The code comments explicitly state the assumption ("Prefunded queues must not reach stopEpochWithDuration with raw underlyings still sitting in the queue"), but nothing enforces it: the guard punishes the pool for a state any single depositor can create.

### Impact Explanation
One dust deposit (e.g., 1 wei of underlying) placed near the end of the allowed window — after which neither new deposits nor prefunding are possible — bricks `stopEpochWithDuration` permanently from the on-chain perspective. The epoch cannot close, borrower repayments cannot be pulled, `collectWithdrawFunds` never runs, and all tranche holders' funds plus pending withdraw receipts are frozen. The only escape is out-of-band: owner/manager calls `setEpochQueue(0)` to disable the queue (then `stopEpoch` direct path works since `_beforeStopEpoch` early-returns), and each queued depositor must individually call `deleteRequest` to recover. Until that manual recovery, the entire pool TVL is frozen — a griefing attack with near-zero attacker cost against the full pool.

### Likelihood Explanation
The attack requires only a KYC-passing wallet and a dust deposit timed into the last allowed block of the deposit window (or, when `prefundedDepositWindow == 0`, any deposit at all, since `processDepositsToBorrower` reverts unconditionally in that configuration — `_checkNotAllowed(_prefundedWindow == 0 || ...)`). No cooperation from any privileged role is needed beyond the normal sequencing gap between the deposit and the manager's prefunding call. Any honest operational delay makes the freeze permanent.

### Recommendation
Do not couple epoch settlement to per-user queue state that users control. Options:
- In `prefundedDepositsToProcess`, return 0 / skip instead of reverting on leftover `epochPendingDeposits`, and refund raw pending deposits back to depositors (or leave them claimable via `deleteRequest`) rather than blocking the stop.
- Alternatively, add an owner/manager sweep that force-clears `epochPendingDeposits[_epoch]` and refunds users before stop, so privileged recovery does not require redeploying `epochQueue`.
- At minimum, revert `requestDeposit` once `prefundedDepositWindow` has begun in a way that also guarantees the manager can still prefund (e.g., align the deposit cutoff strictly earlier than the prefunding cutoff, or allow `processDepositsToBorrower` up to `epochEndDate`).

### Proof of Concept
Foundry fork sketch (setup follows `test/foundry/IdleCDOEpochVariantPrefunded.t.sol` helpers `_requestDepositWithUser`, `_stopCurrentEpochWithApr`):

```solidity
function testDustQueuedDepositBricksStopEpoch() external {
    // prefunded variant with queue configured and PREFUNDED_DEPOSIT_WINDOW set
    queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);

    // honest LPs deposit and epoch starts
    _requestDepositWithUser(makeAddr("lp"), 10_000e6);
    _enterPrefundedWindow(PREFUNDED_DEPOSIT_WINDOW);
    vm.prank(manager);
    queue.processDepositsToBorrower();
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // attacker (KYC'd) queues 1 wei just before the deposit cutoff
    address attacker = makeAddr("attacker");
    deal(address(underlying), attacker, 1);
    vm.warp(cdoEpoch.epochEndDate() - PREFUNDED_DEPOSIT_WINDOW - 1);
    vm.startPrank(attacker);
    underlying.approve(address(queue), 1);
    queue.requestDeposit(1);
    vm.stopPrank();

    // after the cutoff, prefunding is impossible even for the manager
    vm.warp(cdoEpoch.epochEndDate() - PREFUNDED_DEPOSIT_WINDOW + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    queue.processDepositsToBorrower();

    // borrower repays fully; stopEpochWithDuration still reverts on the dust deposit
    uint256 toRepay = cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws();
    deal(address(underlying), strategy.borrower(), toRepay);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), toRepay);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector)); // from prefundedDepositsToProcess
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), 0);

    assertTrue(cdoEpoch.isEpochRunning()); // epoch stuck: all funds frozen
}
```

Note: I could not fully verify whether `epochNumber` increments inside the base `_stopEpoch` before `_afterStopEpochWithDuration` runs (which determines whether the attacker must target `epochNumber` vs `epochNumber + 1`); the test's `claimEpoch`/request-epoch bookkeeping in `IdleCDOEpochVariantPrefunded.t.sol` suggests deposits queued during epoch N land in `epochNumber + 1`, matching `_prefundedEpochToProcess`'s post-stop value — a PoC executor should confirm this ordering when writing the fork test.
