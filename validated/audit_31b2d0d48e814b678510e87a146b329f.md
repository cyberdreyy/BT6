### Title
Missing permission gate lets any RPC caller force the consensus node to dial an attacker-specified peer address - (File: crates/consensus/rpc/src/p2p.rs)

### Summary
The Base consensus node's `opp2p_*` JSON-RPC namespace (`BaseP2PApiServer`), including `opp2p_connectPeer`, is merged into the RPC server unconditionally whenever a P2P network sender is available — with no analog to the `enable_admin` gate that protects the `admin_*` namespace. This lets any client able to reach the RPC endpoint direct the node to dial an arbitrary, attacker-supplied `Multiaddr`, mirroring the missing-permission-check bug class in GHSA-whcg-2364-672f (CVE-2019-10290), where an unprivileged form-validation caller could make Jenkins connect to an attacker-controlled server.

### Finding Description
In `RpcActor::start`, the P2P module is merged whenever `p2p_network` is `Some(..)`, with no permission or feature gate: [1](#0-0) 

By contrast, the `admin_*` namespace is explicitly gated behind `self.config.admin_enabled()`, showing the codebase's own convention that "dangerous" control-plane operations should be conditionally exposed: [2](#0-1) 

Within the always-on P2P namespace, `opp2p_connect_peer` accepts an arbitrary caller-supplied string, parses it into a `libp2p::Multiaddr`, and forwards it directly to the connection layer to dial: [3](#0-2) [4](#0-3) 

The underlying gossip driver dials the multiaddr with no allow-list/permission check of the caller or destination beyond ordinary IP/subnet block lists, which themselves require separate RPC calls to configure: [5](#0-4) 

The crate's own README documents this as a design assumption rather than an enforced control: the `opp2p_*` and opt-in `admin_*` methods "rely on private-network controls instead of application authentication," and access is meant to be restricted by network topology, not code: [6](#0-5) 

This is the same root-cause shape as the Jenkins advisory: a form-validation/administrative-style RPC endpoint that triggers an outbound network connection to a caller-controlled destination string, exposed without a code-level permission check — differing only in that Jenkins meant to check `Overall/Read` and forgot, whereas here the equivalent gate (`admin_enabled`) exists in the codebase but was never applied to the P2P dial-out method.

### Impact Explanation
Any client that can reach the consensus RPC port (which is explicitly the model attacked in the advisory: "anonymous RPC client") can force the node to initiate outbound TCP/QUIC connections to attacker-chosen IP:port pairs framed as libp2p multiaddrs. This enables:
- SSRF-style probing of internal infrastructure reachable from the node's network position.
- Forcing repeated connection attempts to arbitrary hosts, which can be used for resource exhaustion or to fingerprint/attack other internal services from the node's IP.
- Undermining the connection-gate's peer/IP/subnet allow-deny model, since dialing bypasses inbound `can_connect_inbound` checks in `ConnectionGate` and only outbound dial logic applies.

This falls under "unauthorized operation" — an unprivileged caller triggers privileged node behavior (initiating network connections) that the codebase itself treats as sensitive enough to warrant an explicit enable flag for the sibling `admin_*` namespace but omitted for `opp2p_*`.

### Likelihood Explanation
Likelihood depends entirely on network exposure of the consensus RPC endpoint. The README explicitly warns operators to keep this "internal," implying it is sometimes exposed by misconfiguration, and the RPC actor code applies no code-level restriction (no auth middleware, no admin-style flag) specific to `opp2p_connect_peer` beyond the generic HTTP-only/concurrency middleware in `launch_rpc_server`: [7](#0-6) 
Given operators must proactively firewall this port, and the codebase provides no in-process permission check comparable to `admin_enabled`, likelihood of exposure across misconfigured or intentionally-shared RPC deployments is non-trivial.

### Recommendation
- Gate the `opp2p_*` namespace (or at minimum the mutating methods: `opp2p_connect_peer`, `opp2p_disconnect_peer`, `opp2p_block_*`, `opp2p_unblock_*`, `opp2p_protect_peer`, `opp2p_unprotect_peer`) behind the same `admin_enabled`-style flag used for `AdminRpc`, rather than merging it unconditionally in `RpcActor::start`.
- Alternatively, validate destination addresses against an allow-list/deny-list (e.g., reject private/loopback/link-local ranges by default) before dialing in `connect_peer_with_backoff` / `P2pRpcRequest::ConnectPeer` handling.
- Add integration tests asserting that `opp2p_connectPeer` and other mutating P2P RPC methods are unavailable unless explicitly enabled, matching the existing test pattern for `admin_*` wire names.

### Proof of Concept
1. Run a Base consensus node with the RPC server bound to an address reachable by the attacker (e.g., default config without a firewall in front of the RPC port, or a misconfigured deployment that exposes it beyond "trusted operators" as the README assumes).
2. From an unauthenticated client, call:
```json
{"jsonrpc":"2.0","id":1,"method":"opp2p_connectPeer","params":["/ip4/<attacker-controlled-ip>/tcp/<port>/p2p/<attacker-peer-id>"]}
```
3. The node parses the multiaddr and forwards it via `P2pRpcRequest::ConnectPeer` to `GossipDriver::dial_multiaddr`, causing the node to dial the attacker-specified endpoint: [5](#0-4) 
4. Repeat with different destination addresses to probe internal network reachability or trigger repeated outbound connection attempts — no permission check or destination allow-list prevents this, unlike the `admin_*` namespace which requires `--rpc.enable-admin`.
