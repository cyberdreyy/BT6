### Title
Funded instant-withdraw receipts become unclaimable during every buffer period because `claimInstantWithdrawRequest` is gated only on `allowInstantWithdraw` - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.claimInstantWithdrawRequest` gates claims on the single boolean `allowInstantWithdraw` (`_checkNotAllowed(!allowInstantWithdraw)`). That flag is reset to `false` at the end of every normal `stopEpoch` (`allowInstantWithdraw = _isRequestingAllFunds`), even though instant-withdraw receipts that were already funded during the epoch remain fully backed by underlying tokens sitting in `IdleCreditVault`. Like the OpenQ `bountyIsClaimable` bug — where claimability was reported only for the `OPEN` state even though `TieredFixedBounty`/`TieredPercentageBounty` remain claimable in `CLOSED` — the CDO reports "not claimable" during the buffer state even though the user's receipt is already funded and the payout is a pure accounting transfer. Claimability is keyed to the wrong state variable instead of to whether the receipt is funded.

### Finding Description
- Instant withdraw receipts are created by `IdleCreditVault.requestInstantWithdraw`, which burns CDO strategy tokens and mints a per-user receipt in `instantWithdrawsRequests[_user]`. The corresponding liability is tracked globally in `pendingInstantWithdraws`.
- The receipts become *funded* when underlying cash is moved into the vault via `IdleCreditVault.collectInstantWithdrawFunds`, called either inside `startEpoch` (when contract underlyings cover `pendingInstant`) or by `getInstantWithdrawFunds` after `instantWithdrawDeadline`. Both paths set `allowInstantWithdraw = true` once funded.
- Once funded, `IdleCreditVault.claimInstantWithdrawRequest` does not depend on epoch accounting at all: it burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim`, paying from cash already isolated in the vault.
- However, in the success path of `_stopEpoch`, `allowInstantWithdraw` is unconditionally set to `_isRequestingAllFunds`, i.e. `false` for every ordinary epoch stop. From `stopEpoch` until the next `startEpoch` (the whole `bufferPeriod`, which can be arbitrarily long and is restartable each cycle), `claimInstantWithdrawRequest` reverts with `NotAllowed` for any user holding a funded-but-unclaimed receipt.
- The same pattern repeats every epoch cycle: the flag is only re-enabled inside `startEpoch` (or after `finalizeDefault`, which correctly sets `allowInstantWithdraw = true`), so funded receipts oscillate between claimable (epoch running) and frozen (buffer) even though their backing never leaves the vault.
- No other path can pay these receipts: `claimWithdrawRequest` → `_claimFundedWithdrawRequest` only settles `withdrawsRequests`/APR0/loss-adjusted buckets and never touches `instantWithdrawsRequests[_user]`.

### Impact Explanation
An unprivileged lender who requested an instant withdrawal and did not claim before the epoch ended has their already-funded payout temporarily frozen for the entire buffer period, repeatedly, every epoch, despite the funds being fully segregated in `IdleCreditVault`. This is a temporary freezing of user funds with no solvency justification — the payout is a ledger burn plus a transfer of reserved cash. It also creates a footgun for integrations and the `IdleCDOEpochQueue` (`processWithdrawalClaims` calls `cdoEpoch.claimInstantWithdrawRequest()` for instant epochs and can only run when the flag happens to be true).

### Likelihood Explanation
- Triggers under ordinary operation whenever instant withdrawals are enabled (`disableInstantWithdraw == false`, non-programmable borrower) and a user simply fails to claim during the running epoch window.
- The window exists by design every epoch: `stopEpoch` (non-closing) → buffer → `startEpoch`.
- No privileged misbehavior is required; owner/manager/`stopEpoch` are all honest actors in the sequence.

### Recommendation
Decouple claimability of funded instant receipts from the `allowInstantWithdraw` flag. Either:
- keep `allowInstantWithdraw = true` whenever the vault still holds funded instant receipts (e.g. only clear it in `stopEpoch` when there are no outstanding funded claims, or set it based on funded vs pending amounts), or
- let `IdleCreditVault.claimInstantWithdrawRequest` be callable regardless of the flag once `instantWithdrawsRequests[_user]` is backed (i.e. the receipt's `instantWithdrawsRequestsByEpoch` was funded), reserving `allowInstantWithdraw` solely for gating *new* instant requests rather than claims of funded ones.

### Proof of Concept
Foundry fork test against `IdleCDOEpochVariant` + `IdleCreditVault` (standard epoch variant, instant withdraws enabled):

```solidity
function testFundedInstantReceiptFrozenDuringBuffer() external {
    // 1. Deposit AA/BB, run epoch 0 normally, stopEpoch with LOWER apr so
    //    requests during the buffer route to the instant path.
    idleCDO.depositAA(10_000 * ONE_SCALE);
    idleCDO.depositBB(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // 2. During buffer: user requests withdraw -> instant receipt created
    //    (burns tranche tokens, mints instantWithdrawsRequests receipt).
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    // 3. startEpoch: contract underlyings cover pendingInstant, so
    //    collectInstantWithdrawFunds moves cash into IdleCreditVault and
    //    allowInstantWithdraw = true. Receipt is now FUNDED.
    _startEpochAndCheckPrices(1);
    assertEq(strategy.pendingInstantWithdraws(), 0);
    assertGt(strategy.instantWithdrawsRequests(user), 0);

    // 4. User does NOT claim during the running epoch.
    // 5. Manager stops the epoch normally (borrower repays fully, no default).
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // allowInstantWithdraw is reset to false even though the receipt's cash
    // is still segregated inside IdleCreditVault.
    assertFalse(cdoEpoch.allowInstantWithdraw());

    // 6. During the buffer the user cannot claim their FUNDED receipt.
    vm.expectRevert(NotAllowed.selector);
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest();

    // The receipt and its backing are untouched - funds are merely frozen.
    assertGt(strategy.instantWithdrawsRequests(user), 0);
}
```

The freeze persists for the entire `bufferPeriod` and recurs every epoch until the user manages to claim inside a running-epoch window (or until pool close/default finalization re-enables the flag).
