Based on the code I retrieved, the vulnerability claim is confirmed by direct comparison of the two implementations:

### Title
V1 signer's tenure-change duplicate-block guard uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, allowing signing of two competing tenure-start blocks - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` guards against double-signing tenure-start blocks by checking `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, whereas the v2 equivalent in `stacks-signer/src/chainstate/v2.rs` checks `signer_db.get_last_signed_block(...)`, which also captures locally-accepted (but not-yet-globally-accepted) blocks. Because global acceptance requires signer-group threshold, a signer running v1 rules can be asked to sign a second, competing tenure-start block for the same tenure while its own prior signature on the first block is still only locally accepted.

### Finding Description
In `stacks-signer/src/chainstate/v1.rs` (lines ~505-518), `validate_tenure_change_payload` computes:
```rust
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)...
```
and returns `RejectReason::DuplicateBlockFound` only if this lookup finds a block. [1](#0-0) 

The v2 code, by contrast, explicitly documents the intended semantics: "Only blocks we have signed (locally or globally accepted) count here" and uses `get_last_signed_block`: [2](#0-1) 

This means in v1, if this signer has already signed (locally accepted) a tenure-start block A for consensus_hash `CH`, but group threshold has not yet been reached (so the block is not "globally accepted" in this signer's DB), a second competing tenure-start block B for the same `CH` will pass the `validate_tenure_change_payload` check (`get_last_globally_accepted_block` returns `None`), and continue through `check_proposal`'s remaining checks (miner pubkey, parent tenure, bitvec, etc.), which do not themselves detect this competing-block condition. The signer can then be induced to sign B, producing two signatures from the same signer for two conflicting blocks in the same tenure.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property: a signer must sign at most one block per tenure position under contention. If this signer's second signature on block B is combined with signatures from other signers (who may have signed A instead, or who similarly get confused), it can contribute to two conflicting tenure-start blocks reaching thresholds, or at minimum this signer directly produces an equivocating signature — the exact "signer signing a conflicting block" Critical impact category described in the rules.

### Likelihood Explanation
The precondition is narrow but plausible: the signer must be running on v1 chainstate rules (an older signer version/protocol path, as v2 exists specifically to supersede it), and the local state must be `LocallyAccepted` (signed by this one signer) but not yet `GloballyAccepted` for a tenure-start block. An attacker who wins a miner slot can trivially craft two competing tenure-start `BlockProposal`s for the same `consensus_hash` and gossip both before global acceptance is recorded — this requires only the attacker's own miner slot and normal gossip, no privileged access, and is repeatable across tenures where the signer runs v1 code.

### Recommendation
Update `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (matching v2's logic), so that any block this signer has already signed — locally or globally accepted — blocks a competing tenure-start proposal for the same tenure via `RejectReason::DuplicateBlockFound`.

### Proof of Concept
Add a test to `stacks-signer/src/chainstate/tests/v1.rs` mirroring v2's `check_tenure_change_rejects_when_locally_accepted_block_exists`:
1. Construct a `SignerDb` and insert a tenure-start block A for consensus_hash `CH` with `BlockState::LocallyAccepted` (via the same helper used in v2 tests, e.g. `signer_db.insert_block` with local-accepted state, not globally accepted).
2. Build competing tenure-start block B for the same `CH` (different `signer_signature_hash`), and construct `SortitionsView`/`ProposedBy` as in existing v1 tests.
3. Call `validate_tenure_change_payload` (or `check_proposal`) with block B.
4. Assert that v1 returns `Ok(())` (bug reproduced — no `DuplicateBlockFound`), while asserting the same scenario against v2's `validate_tenure_change_payload` returns `Err(RejectReason::DuplicateBlockFound)`, demonstrating the version-specific gap.
5. Optionally extend the test to run both proposals through the v0 signer state machine (`stacks-signer/src/v0/signer.rs`) to confirm two local `BlockResponse::Accepted` signatures are produced for A and B under v1 rules. [3](#0-2) [4](#0-3)

    fn validate_tenure_change_payload(
        &self,
        proposed_by: &ProposedBy,
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            self.config.tenure_last_block_proposal_timeout,
            self.config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // now, we have to check if the parent tenure was a valid choice.
        let is_valid_parent_tenure = proposed_by.state().data.check_parent_tenure_choice(
            signer_db,
            client,
            &self.config.first_proposal_burn_block_timing,
        )?;
        if !is_valid_parent_tenure {
            return Err(RejectReason::ReorgNotAllowed);
        }
        let last_in_current_tenure = signer_db
            .get_last_globally_accepted_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
