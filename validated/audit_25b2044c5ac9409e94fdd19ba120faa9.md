### Title
Single Malformed Account in `getMultipleAccounts` Aborts the Entire Batch Response - (File: rpc/src/rpc.rs)

### Summary
`JsonRpcRequestProcessor::get_multiple_accounts` iterates over the caller-supplied pubkey list and calls `get_encoded_account` for each one, propagating any single encoding error with `?`, which discards the results already computed for every other (valid) account in the batch.

### Finding Description
`get_multiple_accounts` builds its response by looping over the requested pubkeys and pushing the result of `get_encoded_account` for each one: [1](#0-0) 

Each per-account result is unwrapped with `?` inside the loop before being pushed into the `accounts` vector. `get_encoded_account` ultimately calls `encode_account`, which returns an `Err` (`InvalidRequest`) whenever the requested encoding is `Binary`/`Base58` and the account data (after applying `data_slice`) exceeds `MAX_BASE58_BYTES`: [2](#0-1) 

Because the `?` operator returns immediately from the async function on the first error encountered, a single oversized/incompatible account anywhere in the requested pubkey list causes the whole `getMultipleAccounts` call to fail with an RPC error, even though the accounts before it in the list were already fetched and successfully encoded. This is structurally the same bug class as the reported `send`-in-a-loop issue: one "bad" element in a batch operation can block delivery of results for all the other, unrelated elements in the same request, at attacker discretion (since any account owner can grow account data, or a caller can simply add a known-large account's pubkey plus base58/binary encoding to the request to force this failure for other pubkeys of interest in the same call).

### Impact Explanation
This does not crash the validator process or corrupt consensus state, but it produces a functionally incorrect batch RPC response: a client's `getMultipleAccounts` request for N accounts returns a hard error instead of the requested account data for the N-1 valid entries whenever one entry in the batch is encoding-incompatible (e.g., large account data requested with base58 encoding). This can be exploited by a query author (or someone who knows a large account will be included in someone else's batched request pattern) to reliably deny useful data for otherwise-valid accounts bundled in the same call.

### Likelihood Explanation
Low-to-moderate. It requires the caller to explicitly request `Binary`/`Base58` encoding (not the default `Base64`) and include a pubkey whose account data (after any data-slice) exceeds `MAX_BASE58_BYTES`. This is easy to trigger deliberately by a client but is not attacker-controlled against arbitrary third-party requests, since request encoding/pubkey list is fully controlled by the caller of that specific `getMultipleAccounts` call.

### Recommendation
Instead of using `?` inside the per-pubkey loop in `get_multiple_accounts` (rpc/src/rpc.rs:579-590), catch per-account encoding errors and convert them into a `None`/error marker for that specific slot in the response vector (mirroring how `getMultipleAccounts` already returns `null` for missing accounts), so that a single problematic account cannot suppress valid data for the rest of the batch.

### Proof of Concept
1. Store an account whose data length exceeds `account-decoder`'s `MAX_BASE58_BYTES` limit.
2. Call `getMultipleAccounts` with a pubkey list containing that large account together with several normal, existing accounts, and `encoding: "base58"` (or default/binary encoding).
3. Observe that the RPC call returns an `InvalidRequest` error for the whole call instead of returning valid encoded data for the normal accounts alongside an error/marker only for the oversized one — confirmed by the code path in `get_multiple_accounts` (rpc/src/rpc.rs:579-590) and `encode_account`'s error branch (rpc/src/rpc.rs:2591-2596), and by the existing base58-size-limit test `test_encode_account_throws_when_data_too_large_to_base58_encode`.

    pub async fn get_multiple_accounts(
        &self,
        pubkeys: Vec<Pubkey>,
        config: Option<RpcAccountInfoConfig>,
    ) -> Result<RpcResponse<Vec<Option<UiAccount>>>> {
        let RpcAccountInfoConfig {
            encoding,
            data_slice,
            commitment,
            min_context_slot,
        } = config.unwrap_or_default();
        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
