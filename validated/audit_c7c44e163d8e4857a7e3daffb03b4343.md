### Title
Stale confirmations from removed multisig members are not purged from other pending requests, allowing execution below the true live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in `multisig2/src/lib.rs` only removes confirmations for requests that were *created* by the member being deleted; it does not scan or purge that member's confirmations from requests *created by other members*. Because `confirm` counts raw entries in the `confirmations` `HashSet<String>` without re-validating that each entry still corresponds to a current member, a confirmation cast by a member before removal continues to count toward `num_confirmations` after that member is deleted, letting the remaining live members execute the request with fewer than `num_confirmations` currently-valid confirmations.

### Finding Description
The contract's core security invariant is: `confirmations.len() >= num_confirmations` should imply that at least `num_confirmations` **current** members approved the request — i.e. `confirmations recorded == live members confirming`.

`confirm()` checks this invariant purely by set size: [1](#0-0) 

`delete_member()` is the only place that prunes confirmations, and it prunes strictly by request *ownership* (`r.member == member`), not by *participation* in confirmations of other requests: [2](#0-1) 

Sequence:
1. Member `Y` creates request `R` (e.g. a `Transfer`). `R`'s `confirmations` set is empty.
2. Member `X` (still a valid member at this time) calls `confirm(R)`. `X`'s identity string is inserted into `confirmations[R]`.
3. Separately, the members execute a `DeleteMember { member: X }` request. `delete_member` removes `X` from `self.members`, deletes `X`'s own outstanding requests, but does **not** touch `confirmations[R]` because `R` was created by `Y`, not `X`. `X`'s stale confirmation string stays inside `confirmations[R]`.
4. Remaining live members continue confirming `R`. `confirm()` only compares `confirmations.len() + 1 >= self.num_confirmations`; it never re-checks that every string in the set still maps to a current member. Once the count reaches `num_confirmations` — counting `X`'s stale, now-invalid confirmation — `execute_request(R)` fires.

The equality that should hold, `confirmations counted == live members confirming`, is broken: the contract executes with `num_confirmations - 1` (or fewer) *live* approvals plus 1 *stale* approval from a party that is no longer a member and by definition no longer entitled to approve anything on the account.

The same defect exists in the v1 contract (`multisig/src/lib.rs`), where `DeleteKey` prunes confirmations only for requests signed (`r.signer_pk == pk`) by the deleted key, not for confirmations that key contributed to other requests: [3](#0-2) [4](#0-3) 

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." The multisig's entire value proposition is that any state-changing action (`Transfer`, `AddKey`/`AddMember`, `DeployContract`, `FunctionCall`, etc.) requires `num_confirmations` currently-trusted signers. With this bug, an action can be executed with confirmations from a mix of live and *already-removed* members, meaning fewer than the configured threshold of currently-authorized parties actually approved it — e.g. NEAR can be transferred out of the account, or a new full-access key can be added, with an insufficient live quorum.

### Likelihood Explanation
Membership changes (`DeleteMember`/`DeleteKey`) are a normal, documented operation of this contract (e.g. offboarding an employee/co-signer or rotating a compromised key), and it is common for a request to be created and partially confirmed before a membership change completes. No malicious server, redeploy, or foundation privilege is needed — only ordinary sequencing of two legitimate multisig operations (a pending request partially confirmed, then a member removal, then further confirmations pushing the same stale-inclusive count over threshold). The bug is a pure ordering/state-management defect in `delete_member`/`DeleteKey`, reachable by the contract's normal member set.

### Recommendation
In `delete_member` (and `DeleteKey` in the v1 contract), iterate over **all** pending requests' `confirmations` sets (not just requests created by the removed member) and remove the departing member's identity string from every one of them, e.g.:
```rust
for (request_id, mut confirmations) in self.confirmations.iter() {
    if confirmations.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confirmations);
    }
}
```
Additionally, as defense in depth, `confirm()` should validate at execution time that every entry in `confirmations[request_id]` still corresponds to a member in `self.members`, and only count those, rather than trusting the raw set length.

### Proof of Concept
1. Initialize `MultiSigContract::new(members: [X, Y, Z, W], num_confirmations: 3)`.
2. As `Y`, call `add_request(Transfer{ amount, receiver_id: attacker_controlled_or_any })` → `request_id = R`.
3. As `X`, call `confirm(R)` → `confirmations[R] = {X}`.
4. Members `Y`, `Z`, `W` collectively confirm (3-of-4) a separate `DeleteMember{ member: X }` request → executes, removing `X` from `self.members`. Note `confirmations[R]` is untouched because `R.member == Y`, not `X`.
5. As `Y`, call `confirm(R)` → `confirmations[R] = {X, Y}` (len 2).
6. As `Z`, call `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations (3)` → `execute_request(R)` fires and the transfer executes, even though only `Y` and `Z` are currently valid members who approved it (2 live approvals, not the required 3), with `X`'s stale approval making up the difference.

This confirms the request executed below the true live-member threshold, breaking the `confirmations counted == live members` custody binding.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
