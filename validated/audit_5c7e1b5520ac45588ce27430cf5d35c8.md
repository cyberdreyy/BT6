### Title
Unbounded per-request cost in `get_vote_accounts` scaling with attacker-created on-chain vote accounts - ([File: rpc/src/rpc.rs])

### Summary
`get_vote_accounts` (`rpc/src/rpc.rs:1155-1247`) iterates the *entire* `bank.vote_accounts()` collection to build `RpcVoteAccountInfo` entries, with no cap, pagination, or minimum-stake filter applied to the "current" bucket. Because any account owned by the vote program that is cached in the bank's `VoteAccounts` structure is included (only the `delinquent` bucket optionally filters out zero-stake accounts, and only when `keep_unstaked_delinquents` is false), an attacker who creates many cheap, zero-stake vote accounts and periodically submits vote transactions to keep `last_vote` recent can force every such account into the "current" bucket returned by a single `getVoteAccounts` call.

### Finding Description
In `RpcVoteAccountInfo` construction (`rpc/src/rpc.rs:1178-1230`), the handler:
1. Fetches `bank.vote_accounts()` — `vote::vote_account::VoteAccounts`, a hashmap of every vote-program-owned account cached by the bank [1](#0-0) , which is populated/kept for *every* vote account created on-chain, independent of stake.
2. Maps over all entries with `.iter()`, and for each entry, builds an `RpcVoteAccountInfo`, including `epoch_credits_iter()` collection up to `MAX_RPC_VOTE_ACCOUNT_INFO_EPOCH_CREDITS_HISTORY` per account [2](#0-1) .
3. Partitions the resulting `Vec<RpcVoteAccountInfo>` into `current`/`delinquent` purely based on `last_vote` recency, with **no stake filter applied to the "current" bucket** [3](#0-2) .
4. Only the `delinquent` bucket is filtered by `activated_stake > 0` when `keep_unstaked_delinquents` is false [4](#0-3) ; the `current` bucket has no equivalent cap.

There is no server-side limit on the size of `vote_accounts`, no minimum-stake gate for inclusion into `current`, and no pagination of the returned `Vec<RpcVoteAccountInfo>`. The cost of one `getVoteAccounts` call (allocation, iteration, per-account epoch-credit collection, and response serialization) is therefore proportional to the total number of vote-program accounts on-chain that have voted recently — a count entirely controlled by an unprivileged attacker who only needs to fund vote-account creation (cheap, rent-exempt minimum, no stake required) and periodic vote transactions to keep `last_vote` fresh.

Note: unlike the `clone_and_filter_for_vat` path used for consensus/leader-schedule purposes, which explicitly filters by stake, BLS pubkey, and truncates to `max_vote_accounts` [5](#0-4) , the RPC `get_vote_accounts` handler has no analogous cap.

### Impact Explanation
A single, low-rate `getVoteAccounts` JSON-RPC call incurs CPU and memory cost proportional to the number of attacker-created vote accounts rather than any fixed, documented bound — this matches the "unbounded cost for a single low-rate call" impact category. Repeated calls (at or below `CLUSTER_SLOT_TIME_TARGET / 2`) against a validator with tens or hundreds of thousands of attacker-created "current" vote accounts can degrade RPC responsiveness and consume significant memory for the response `Vec`/JSON payload, without requiring any privileged access, multiple concurrent clients, or gossip/gossip-identity control.

### Likelihood Explanation
Feasible and repeatable with only unprivileged funds: vote-account creation only requires paying the rent-exempt minimum for a vote account (no delegated stake needed), and keeping `last_vote` recent only requires occasional vote transactions signed by the vote account's own authorized voter (self-funded, no validator/leader control needed). The attacker fully controls N (the number of such accounts) and can grow it over time; the RPC handler's cost scales with N on every subsequent `getVoteAccounts` call, satisfying the "cost of one request bounded by attacker-authored on-chain data, not by explicit limits" scenario.

### Recommendation
Apply a stake-based filter (and/or explicit cap with pagination) to the `current` bucket in `get_vote_accounts`, mirroring the existing stake filter already applied to `delinquent` accounts, so that zero-stake vote accounts cannot inflate the response size or handler cost. Alternatively, bound the total number of `RpcVoteAccountInfo` entries constructed per call (e.g., truncate/cap similar to `clone_and_filter_for_vat`'s `max_vote_accounts` truncation) and document the cap, or require pagination for `getVoteAccounts` when accounts count exceeds a threshold.

### Proof of Concept
Integration test plan (Rust, using the existing `RpcHandler` test harness in `rpc/src/rpc.rs` tests, e.g. `test_get_vote_accounts` at `rpc/src/rpc.rs:7760`):
1. Start `RpcHandler` and record baseline handler latency for `getVoteAccounts` with only the bootstrap vote account present.
2. Loop N times (e.g., N = 10_000): create a new zero-stake vote account (`VoteStateV4::new_with_defaults` + `rpc.store_vote_account`, as done for `alice_vote_keypair` in the existing test), and submit a `tower_sync` vote transaction for it each time the bank advances so `last_vote` stays within `delinquent_slot_distance` of `bank.slot()`.
3. Issue a single `{"jsonrpc":"2.0","id":1,"method":"getVoteAccounts"}` request via `io.handle_request_sync` and measure wall-clock time and result payload size (`vote_account_status.current.len()`).
4. Assert that `vote_account_status.current.len()` grows linearly with N with no server-imposed cap, and that handler latency/memory grows correspondingly — demonstrating the invariant "cost of one request bounded by explicit limits" is violated, since no cap error or truncation is ever produced by `get_vote_accounts`.

    // 1. Filter out any vote accounts without BLS pubkey
    // 2. Given minimum_vote_account_balance, filter out any vote account

    // 3. If we have more than max_vote_accounts vote accounts after above
    //    filtering, sort by stake and truncate
    // 4. If any vote account in the resulting list has the same stake as any
    //    truncated vote account, just remove this vote account as well (A and
    //    B have the same stake amount, it's unfair to keep A in and kick B out
    //    just because of Pubkey difference, because that can be grinded)
    // 5. If we end up with an empty list (can happen if everyone in the world
    //    has the same stake, happens in tests, doesn't happen in real world),
    //    log a warning
    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
        }

        let valid_len = entries_to_sort.len();
        if entries_to_sort.len() > max_vote_accounts {
            // Find the cutoff stake using partial sort (more efficient than full sort).
            let (_, cutoff_entry, _) =
                entries_to_sort.select_nth_unstable_by(max_vote_accounts, |a, b| b.2.cmp(&a.2));
            let floor_stake = cutoff_entry.2;

            // Per SIMD 357, we remove all vote accounts with stake smaller or equal to
            // the first truncated one.
            entries_to_sort.retain(|(_, _, stake)| *stake > floor_stake);
