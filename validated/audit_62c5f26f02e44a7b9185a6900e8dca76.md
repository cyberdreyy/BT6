### Title
ProgrammableBorrower `onStopEpoch` judges repayability by `convertToAssets` instead of vault liquidity — an unprivileged vault user can permanently wedge `stopEpoch` between the "covered" check and a reverting `vault.withdraw`, freezing all LP funds and blocking the default path - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The Dgraph bug lets an attacker smuggle an unauthorized operation through a field the server trusts, because the "sanitization" (`strings.Replace`) answers the wrong question about the input. The analog here: `onStopEpoch` answers the wrong question about repayability. It checks `shortfall > _currentVaultAssets()` — a **share valuation** (`convertToAssets`) — to decide whether to withdraw from the ERC4626 vault, but `vault.withdraw` only succeeds if the vault has **cash liquidity**. An attacker who is a user of that vault can keep the valuation high (donation to the vault) while keeping cash at zero (withdrawing all vault liquidity, or borrowing it out in a lending-backed vault). Every `stopEpoch` then reverts with `StopEpochVaultLiquidityUnavailable` forever, and the `_handleBorrowerDefault` escape hatch is never reachable, because the hook reverts instead of returning `false`.

### Finding Description
In `onStopEpoch`:

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;   // valuation check
  try vault.withdraw(shortfall, address(this), address(this)) { ... }
  catch { revert StopEpochVaultLiquidityUnavailable(); } // liquidity failure
}
``` [1](#0-0) 

`_currentVaultAssets()` is `vault.convertToAssets(shares)` — total-assets-based, insensitive to how much cash is actually withdrawable [2](#0-1) . In `IdleCDOEpochVariant._stopEpoch`, a `false` return triggers `_handleBorrowerDefault`, and a `true` return proceeds to `getFundsFromBorrower` whose failing `transferFrom` also lands in the default path via the try/catch on `this.getFundsFromBorrower` [3](#0-2) . But a **revert** from the hook bubbles up through the whole `stopEpoch` transaction — no default, no epoch close, deposits remain paused (`_pause()` at startEpoch), and withdrawal requests cannot be fulfilled. The comment even acknowledges retriability ("Hook reverts bubble so transient ERC4626 liquidity failures can be retried"), but nothing bounds the retry: if the illiquidity is attacker-maintained, the freeze is indefinite.

Attacker recipe (unprivileged vault user, allowed by the threat model):
1. Pool is running an epoch; ProgrammableBorrower holds nearly all assets as vault shares (`onStartEpoch` deposits all idle balance via `_depositToVault` [4](#0-3) ).
2. After `epochEndDate`, on every attempted `stopEpoch`, the attacker ensures vault cash < `shortfall` (redeem/withdraw vault liquidity themselves, or keep a lending vault's markets fully utilized) while keeping `convertToAssets(shares) >= shortfall` — trivially maintained by donating dust/underlying directly to the vault contract, which also **increases** `totalInterestDueNow()` and hence `_amountRequired` [5](#0-4) .
3. Each `stopEpoch` call: `shortfall <= _currentVaultAssets()` → `vault.withdraw` reverts on insufficient cash → `StopEpochVaultLiquidityUnavailable` → whole tx reverts.

Existing guards don't stop this: the default path requires `onStopEpoch` to *return* `false` or the subsequent `transferFrom` to fail — the revert prevents both. `emergencyExitVault` (owner/manager) can redeem shares, but `redeem` is equally liquidity-bound, and does not unblock `stopEpoch` accounting anyway. Note the asymmetry: if the attacker instead pushed `convertToAssets` *below* `shortfall`, the pool would cleanly default — the vulnerability is specifically the wedge where valuation says "covered" but liquidity says "revert".

### Impact Explanation
Permanent freezing of the entire pool's funds (all tranche principal plus accrued interest parked in the vault) for as long as the attacker maintains the wedge; the manager's only recovery is `rescueTokens`/manual unwind, i.e., emergency intervention outside the epoch state machine. Quantified: the full vault share position (`_currentVaultAssets()`), which is essentially the whole CDO NAV mid-epoch. No privileged role misbehaves — owner/manager honestly call `stopEpoch` and it always reverts.

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault shares liquidity with public users (e.g., a lending-protocol vault where cash can be borrowed out, or any shared vault). The attacker's cost is one vault withdrawal plus periodic donations to keep the valuation propped — cheap relative to freezing an entire credit facility, and it can be used as extortion/griefing leverage. Medium likelihood, high impact.

### Recommendation
Make the coverage check match the failure mode: test actual withdrawable liquidity (e.g., `vault.maxWithdraw(address(this))`) instead of `convertToAssets` when deciding whether to `return true` vs attempt the withdrawal; and/or catch liquidity failures by returning `false` (or a tri-state) so IdleCDO can route to `_handleBorrowerDefault` after a bounded number of retries, rather than letting a revert permanently block `stopEpoch`. Optionally track a `failedStopAttempts` counter that escalates to the default path.

### Proof of Concept
Foundry fork test sketch:

```solidity
// Setup: cdoEpoch with isProgrammableBorrower, vault = ERC4626 (e.g. Morpho vault).
idleCDO.depositAA(amount);            // KYC'd LP
cdoEpoch.startEpoch();                // PB deposits all idle cash into vault
vm.warp(cdoEpoch.epochEndDate() + 1);

// Attacker (unprivileged vault user):
// 1) drain vault cash: vault.withdraw(maxWithdraw(attackerShares)) or
//    borrow out all liquidity on the underlying market
// 2) donate dust to vault so convertToAssets(pbShares) >= shortfall:
underlying.transfer(address(vault), 1); // keeps valuation "covering" shortfall

// Honest manager tries to stop the epoch:
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// Repeated attempts always revert; defaulted == false, isEpochRunning == true,
// LPs cannot withdraw, and _handleBorrowerDefault is never reached.
```

The wedge is preserved because `shortfall <= _currentVaultAssets()` (line 245) while `vault.withdraw` reverts on cash insufficiency (line 246→252).
