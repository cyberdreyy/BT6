### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing a request to execute below the effective live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both multisig implementations execute a pending request as soon as its confirmation count reaches `num_confirmations`, but `confirmations` (a `HashSet` of confirmer identities) is never purged of entries belonging to a member who is later removed via `DeleteMember`/`DeleteKey`. Removal only cleans up requests *created by* the removed member, not confirmations that member cast on other requests. A confirmation cast while the member was still valid keeps counting toward the threshold forever, even after that member is stripped of authority.

### Finding Description
`confirm` counts confirmations for a request and executes it once the count reaches `num_confirmations`: [1](#0-0) 

`delete_member` (multisig2) only removes requests whose creator (`r.member`) is the member being removed, and clears `num_requests_pk` for that member — it never scans `confirmations` for other requests the member may have already confirmed: [2](#0-1) 

The same gap exists in the original `multisig` contract: `DeleteKey` removes requests signed (created) by the deleted key, but leaves that key's confirmations on requests created by other keys intact: [3](#0-2) 

Since `confirmations` is stored per-`request_id` as a bare set of confirmer strings/public keys with no live-membership re-check at execution time, a stale confirmation from a now-removed member is indistinguishable from a confirmation by a current member when the sum is compared against `num_confirmations`.

### Impact Explanation
This breaks the binding: "confirmations counted" == "confirmations from currently authorized (live) members". Concretely:

- Members `{A, B, C, D}`, `num_confirmations = 3`.
- `A` creates request `R1` (e.g. `Transfer` to some address).
- `B` calls `confirm(R1)` → `confirmations = {B}` (count 1, below threshold).
- Separately, the multisig legitimately removes `B` (key rotation, suspected compromise, resignation) via a `DeleteMember{B}` request confirmed by `A, C, D`. `delete_member` only purges requests created by `B`; `R1` (created by `A`) is untouched, so `R1`'s confirmation set still contains `B`.
- `C` confirms `R1` → count 2. `D` confirms `R1` → count 3 ≥ `num_confirmations` → `R1` executes.

At execution time only `C` and `D` are current members who confirmed — 2 live confirmations — yet the contract treats the threshold as satisfied because it also counts `B`'s stale, pre-removal confirmation. This is exactly "a multisig request executed below threshold," which moves funds/keys/contract-code out of the account with fewer than the intended number of live authorizers.

### Likelihood Explanation
No malicious insider or privileged actor is required to trigger this — it happens through entirely ordinary, expected multisig lifecycle operations: a member confirms a request, and later (for routine reasons like key rotation) that member is removed via the standard `DeleteMember`/`DeleteKey` flow before the original request finishes collecting confirmations. Any multisig that rotates members while requests are in flight is exposed; the `REQUEST_COOLDOWN`/`active_requests_limit` mechanisms do nothing to mitigate this since they govern request creation cadence, not confirmation validity.

### Recommendation
When removing a member/key (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` handling in `multisig/src/lib.rs`), iterate over all pending requests' `confirmations` sets (not just requests the member created) and remove that member's entry, or alternatively re-validate at `confirm`/execution time that every entry in the stored confirmation set still corresponds to a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]`, `num_confirmations = 3`.
2. As `A`: `add_request({receiver_id: multisig, actions:[Transfer{amount}]})` → `R1`.
3. As `B`: `confirm(R1)` → confirmations = `{B}`.
4. As a quorum of `{A, C, D}`: `add_request_and_confirm({receiver_id: multisig, actions:[DeleteMember{member:B}]})` executes and removes `B` from `members` (see `delete_member`, `multisig2/src/lib.rs:356-379` — no scan of `R1`'s confirmations).
5. As `C`: `confirm(R1)` → confirmations = `{B, C}` (count 2).
6. As `D`: `confirm(R1)` → confirmations = `{B, C, D}` (count 3 ≥ `num_confirmations`) → `execute_request` fires, transferring funds, even though only `C` and `D` are currently authorized members who confirmed. [4](#0-3) [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
