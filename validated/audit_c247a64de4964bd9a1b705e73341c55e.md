### Title
Stale confirmations from removed multisig members are not purged, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
The bug-class from the external report ("stale/expired state still counted toward a binding total") has a direct analog in the multisig contracts. When a member is removed via `DeleteMember`, the contract only purges requests that member *originated*, but not confirmations that member previously cast on requests originated by *other* members. Those stale confirmations remain in the `confirmations` set and are still counted by `confirm()` toward `num_confirmations`, letting a request execute even though fewer than `num_confirmations` currently-valid members actually approved it.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` removes a member and cleans up only the requests that member added: [1](#0-0) [2](#0-1) 

It filters `self.requests` for entries where `r.member == member` (the request's *originator*) and clears those. It never scans `self.confirmations` for entries where the removed member is a *confirmer* of someone else's still-pending request.

`confirm()` counts confirmations purely by set size, with no check that every entry in the set still corresponds to a live member: [3](#0-2) 

So the binding the contract is supposed to guarantee — `confirmations counted == confirmations by current live members` — can diverge: `confirmations counted > confirmations by current live members` after any member removal that leaves behind confirmations they placed on other people's pending requests.

The equivalent flaw exists in the older `multisig/src/lib.rs` (`DeleteKey` action), which only purges requests whose `signer_pk` (the request's *adder*) equals the deleted key, not confirmations that key placed on other requests: [4](#0-3) 

### Impact Explanation
This lets a `MultiSigRequestAction::Transfer` (or `AddKey`/`FunctionCall`/etc.) execute with fewer than `num_confirmations` *currently authorized* members, because a stale confirmation from a member removed *after* they confirmed but *before* the request finished collecting confirmations still counts toward the threshold. This is a multisig request executed below threshold — matching the report's "Critical" impact tier (authorization boundary crossed: fewer live signers than the configured K-of-N actually approved fund movement).

### Likelihood Explanation
This requires only ordinary, in-scope multisig operations: one member creates a transfer request, a second member confirms it (but the request doesn't yet reach threshold), and a subsequent `DeleteMember` request (itself properly authorized by K confirmations) removes that second member for unrelated reasons (key rotation, offboarding, compromise). No malicious deployer, foundation, or out-of-scope actor is needed — any legitimate member churn combined with a pending request creates the condition, and a remaining member can then complete confirmation counts using the phantom vote.

### Recommendation
When deleting a member, also scan `self.confirmations` for every pending request and remove the entry keyed by that member's identity (`member.to_string()`), not just requests they authored. Equivalently, `confirm()` could re-validate that every already-recorded confirmer is still `self.members.contains(...)` before counting it. Apply the same fix to `multisig/src/lib.rs`'s `DeleteKey` handling for confirmations placed by the deleted key on other requests.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. Member `D` calls `add_request` with a `Transfer` action → `request_id = R1`.
3. Member `A` calls `confirm(R1)` → `confirmations[R1] = {D, A}` (2 < 3, stays pending). See `confirm` logic: [5](#0-4) 
4. Members `B`, `C`, `D` create and confirm a separate request `DeleteMember { member: A }`; it executes via `delete_member`, which only clears requests *added by* `A` — `R1` (added by `D`) is untouched, so `confirmations[R1]` still contains `A`. See [6](#0-5) 
5. Member `B` calls `confirm(R1)` → `confirmations.len() (2: {D, A}) + 1 >= num_confirmations (3)` → request executes, per [7](#0-6) , even though only `D` and `B` are still valid members who actually approved; `A`'s stale confirmation was counted as the third vote despite `A` no longer being a member.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
