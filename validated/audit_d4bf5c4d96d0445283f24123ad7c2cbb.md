### Title
Malformed `TransactionDeposited` log from a single depositor halts derivation of the entire L1 epoch's deposits - ([File: crates/consensus/derive/src/attributes/stateful.rs])

### Summary
`derive_deposits` in `crates/consensus/derive/src/attributes/stateful.rs` iterates over every log in every receipt of an L1 origin block and calls `Deposits::decode` on each log matching the deposit-contract address and event topic [1](#0-0) . Any single decode failure aborts the whole function via `?`, and the caller wraps that as a `PipelineError::BadEncoding(e).crit()` — a `Critical` pipeline error [2](#0-1) .

### Finding Description
`Deposits::decode` performs strict structural validation of the `TransactionDeposited` event log (topic count, selector, address padding, ABI offset/length encoding, padding zero-bytes, version, and opaque-data length) and returns a `DepositDecodeError` for any deviation [3](#0-2) . In `derive_deposits`, the loop only filters logs by the deposit contract address and the log's first topic equal to `Deposits::EVENT_ABI_HASH`, but performs no additional validation before calling `decode` and immediately propagates any decode error out of the loop via `?`, discarding all other deposits collected in the same batch [4](#0-3) .

Because the "malformed system config update" path in the same function is treated leniently (errors are only logged and skipped, not propagated) [5](#0-4) , this shows the intended design pattern for handling malformed/attacker-influenced L1 event data is to skip bad entries — yet the deposit-decoding path does not follow this pattern and instead treats a single malformed deposit as fatal for the whole epoch.

`PipelineError::BadEncoding(...).crit()` becomes `PipelineErrorKind::Critical`, which per the pipeline's own documentation "halts the derivation process ... require[s] external intervention" and cannot be resolved by retry or reset [6](#0-5) .

### Impact Explanation
An unprivileged L1 depositor triggers a `TransactionDeposited` log by calling the L1 deposit contract. If any part of the log the depositor controls (e.g. `opaqueData` length/offset fields, or padding bytes) can be made to violate one of the many strict structural checks in `Deposits::decode` (offset ≠ 32, non-multiple-of-32 length with non-zero padding, overflowing length, unsupported version, etc.), the resulting `DepositDecodeError` propagates as a `Critical` pipeline error and halts derivation of that epoch — blocking processing of every other legitimate deposit and system-config update batched in the same L1 block/epoch, and stalling L2 block production/derivation until node operators intervene. This is a direct analog of the reported bug class: a single malicious/malformed input in an iteration over a set of otherwise-independent items blocks progress for the whole batch.

### Likelihood Explanation
Whether this is actually exploitable depends on whether the on-chain deposit contract that emits `TransactionDeposited` fully constrains all of the fields `Deposits::decode` checks (e.g., it may always emit ABI-conformant tightly-packed encoding that can never trigger `InvalidOpaqueDataOffset`, `UnalignedData`, `InvalidOpaqueDataPadding`, etc.). I could not locate the Solidity/L1 deposit-contract source in this index to confirm whether it always produces conformant logs or whether a caller can influence any byte that reaches an unchecked-encoding path. This is the main source of uncertainty in this finding — if the contract's ABI encoding of `opaqueData` is fully deterministic and cannot be influenced into a decode-breaking shape, the practical likelihood is low; if any user-supplied field feeds into the packed opaque data without contract-side sanitization, the likelihood is high since it requires only a single ordinary deposit transaction.

### Recommendation
Change `derive_deposits` to treat a `DepositDecodeError` the same way malformed system-config updates are treated: log and skip the offending log/deposit rather than propagating a fatal, epoch-halting `Critical` error, unless the specific failure mode is proven unreachable by the deposit contract's encoding guarantees. At minimum, downgrade decode failures that stem from attacker-influenced log data to a `Temporary`/skippable classification instead of `Critical`, and add contract-level and derivation-level tests asserting that no permissionless deposit input can produce a `Critical` pipeline halt.

### Proof of Concept
Not independently verified against the L1 deposit contract in this repo index (contract source not found/indexed). The Rust-side proof-of-concept is the existing unit test `test_derive_deposits_decoding_errors`, which shows that a single malformed deposit log (`UnexpectedTopicsLen`-style failure) causes `derive_deposits` to return `Err`, discarding all other valid deposits batched with it [7](#0-6) . Confirming full exploitability requires checking the on-chain `OptimismPortal`/deposit-contract Solidity source (not present in this index) to determine whether any caller-controlled field can produce an `opaqueData` encoding that fails one of `Deposits::decode`'s structural checks (offset, length, padding, or version) shown at [8](#0-7) .

        let topics = log.data.topics();
        if topics.len() != 4 {
            return Err(DepositDecodeError::UnexpectedTopicsLen(topics.len()));
        }
        if topics[0] != Self::EVENT_ABI_HASH {
            return Err(DepositDecodeError::InvalidSelector(Self::EVENT_ABI_HASH, topics[0]));
        }
        if log.data.data.len() < 64 {
            return Err(DepositDecodeError::IncompleteOpaqueData(log.data.data.len()));
        }
        if log.data.data.len() % 32 != 0 {
            return Err(DepositDecodeError::UnalignedData(log.data.data.len()));
        }

        // Validate the `from` address.
        let mut from_bytes = [0u8; 20];
        from_bytes.copy_from_slice(&topics[1].as_slice()[12..]);
        if topics[1].iter().take(12).any(|&b| b != 0) {
            return Err(DepositDecodeError::FromDecode(topics[1]));
        }

        // Validate the `to` address.
        let mut to_bytes = [0u8; 20];
        to_bytes.copy_from_slice(&topics[2].as_slice()[12..]);
        if topics[2].iter().take(12).any(|&b| b != 0) {
            return Err(DepositDecodeError::ToDecode(topics[2]));
        }

        let from = Address::from(from_bytes);
        let to = Address::from(to_bytes);
        let version = log.data.topics()[3];

        // ```solidity
        // abi.encode(abi.encodPacked(uint256 mint, uint256 value, uint64 gasLimit, uint8 isCreation, bytes data))
        // ```
        //
        // The opaqueData will be packed as shown below:
        //
        // ------------------------------------------------------------
        // | offset | 256 byte content                                |
        // ------------------------------------------------------------
        // | 0      | [0; 24] . {U64 big endian, hex encoded offset}  |
        // ------------------------------------------------------------
        // | 32     | [0; 24] . {U64 big endian, hex encoded length}  |
        // ------------------------------------------------------------

        let opaque_content_offset: U256 = U256::from_be_slice(&log.data.data[0..32]);
        if opaque_content_offset != U256::from(32) {
            return Err(DepositDecodeError::InvalidOpaqueDataOffset(Bytes::copy_from_slice(
                &log.data.data[0..32],
            )));
        }

        // The next 32 bytes indicate the length of the opaqueData content.
        let opaque_content_len: U256 = U256::from_be_slice(&log.data.data[32..64]);
        let opaque_content_len: u64 = opaque_content_len.try_into().map_err(|_| {
            DepositDecodeError::OpaqueContentOverflow(Bytes::copy_from_slice(
                &log.data.data[32..64],
            ))
        })?;

        let opaque_data_ceil_32: u64 =
            (opaque_content_len.saturating_add(31) / 32).saturating_mul(32);

        // Ensure that the remaining data is only zeros.
        // The padding ends at the next multiple of 32 after the opaque data.
        let Some(padding_end): Option<u64> = 64_u64.checked_add(opaque_data_ceil_32) else {
            return Err(DepositDecodeError::OpaqueDataPaddingOverflow);
        };

        // by the EVM.
        let Some(opaque_data) = &log.data.data.get(64..64 + opaque_content_len as usize) else {
            return Err(DepositDecodeError::InvalidOpaqueDataLength {
                expected: opaque_content_len as usize,
                actual: log.data.data.len().saturating_sub(64),
