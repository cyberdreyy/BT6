I found the analog: `staking_contract::distribute_internal` (and the `vesting::distribute` path that calls into it) uses `aptos_account::deposit_coins` to pay every shareholder in the shared `distribution_pool`, and this call — unlike `AddCollateral`'s bump mismatch — can be permanently blocked by a single unregistered/frozen recipient, locking every other staker's/beneficiary's already-unlocked funds in the same contract.

### Title
Unregistered or coin-frozen recipient in `distribute_internal` permanently blocks payout of all other stakers'/beneficiaries' unlocked funds - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute`/`distribute_internal` is a permissionless, shared-state operation (comparable to `AddCollateral`/`WithdrawCollateral` sharing one `authority_bump`) that iterates over *every* shareholder in a single `distribution_pool` and pays them out in one loop, aborting the whole transaction if any single recipient cannot receive coins.

### Finding Description
`distribute` is explicitly documented as callable by anyone ("Allow anyone to distribute already unlocked funds...does not need to be restricted to just the staker or operator") [1](#0-0) . It delegates to `distribute_internal`, which withdraws all inactive/pending_inactive stake into `coins`, then loops `while (distribution_pool.shareholders_count() > 0)` and calls `aptos_account::deposit_coins(recipient, ...)` for each shareholder still tracked in the pool, including the operator/beneficiary [2](#0-1) .

`aptos_account::deposit_coins` aborts if the recipient account is not registered for `AptosCoin` (or, in the general coin-store case, if the coin store is frozen). Because `distribution_pool` can contain many recipients accumulated from earlier operator switches (see `add_distribution` calls made from `switch_operator`/`request_commission_internal`, e.g. `staking_contract.move:781-805`), the set of addresses who must successfully receive a deposit is not controlled by the person invoking `distribute`. Any one of these addresses — an old operator, an old operator's beneficiary, or a delegator recorded via `add_distribution` — becoming un-registerable for `AptosCoin` (dropped `CoinStore`, or, in the coin-migration path, a frozen fungible-store) causes every subsequent call to `distribute` for that entire `staker`/`operator` pair to abort, since the loop must reach and pay that same recipient before it can finish paying anyone else. This mirrors the report's root cause: a value shared across multiple stake-owners (`distribution_pool`) can be poisoned by one bad/uncontrollable entry, permanently locking value that belongs to unrelated, well-behaved parties (the staker's own withdrawable dust, other pending distributees, and future distributions), because there is no way to skip or forcibly evict the blocking recipient from the loop.

The `vesting` module's `distribute`/`terminate_vesting_contract`/`admin_withdraw` flow depends on the same `staking_contract::distribute` under the hood [3](#0-2) , so a poisoned `distribution_pool` also blocks vesting-contract termination and admin withdrawal for the same underlying stake pool.

### Impact Explanation
If the loop cannot complete, `distribute` (and everything that calls it — `switch_operator`, `terminate_vesting_contract`, `admin_withdraw`) permanently reverts for that staker/operator pair. This traps already-unlocked/inactive stake (which has already left the validator's `stake` state and cannot re-enter it) belonging to the staker, other pending recipients, and the operator/beneficiary — a non-recoverable loss of withdrawal rights matching the "Stake And Lockup Gate" criterion for permanent lock/non-recoverable loss of claim rights.

### Likelihood Explanation
I could not fully verify, within the available tooling, whether an account's `CoinStore<AptosCoin>` can actually become de-registered/un-depositable *after* being added to `distribution_pool` in current mainnet conditions (e.g., via the coin-to-fungible-asset migration freezing a primary store, or an account being deleted/never having a CoinStore in older flows). This distinction is critical to the exploitability of the bug and requires deeper investigation of `aptos_account::deposit_coins` and the coin/fungible-asset migration code, which was not reachable in this pass.

### Recommendation
Do not require all shareholders to be paid atomically in one transaction. Instead, allow each shareholder to pull their own share independently (or catch/skip failures per-recipient and re-queue), so that one recipient's inability to accept a deposit cannot block payout to all others sharing the same `distribution_pool`.

### Proof of Concept
Conceptual, not verified end-to-end:
1. Operator A operates a staking contract with delegator distributions accumulated via `add_distribution` (e.g., through `switch_operator`).
2. One recorded recipient in `distribution_pool` (e.g., previous operator, or a delegator) becomes unable to accept an `AptosCoin` deposit (no `CoinStore`, e.g. via a scenario not fully confirmed in this pass).
3. Any account calls `distribute(staker, operator)`; `distribute_internal`'s loop reaches that recipient's entry in `distribution_pool.shareholders()` and `aptos_account::deposit_coins` aborts.
4. The abort reverts the whole distribution, and since the loop always starts by paying `shareholders()[0]` in an undefined/insertion order, the same poisoned recipient blocks the transaction on every future retry, permanently locking all other shareholders' already-unlocked stake in that `StakingContract`.

Given I was unable to conclusively confirm the precondition (an already-added distribution-pool recipient later becoming non-depositable) within this pass, this should be treated as a candidate requiring further confirmation rather than a fully proven vulnerability.
