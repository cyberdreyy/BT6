## Analysis

The report's bug class is: an unprivileged actor can register an address that is guaranteed to revert as a payout target, and because a shared distribution routine reverts entirely on any single failed transfer, it permanently blocks payouts owed to an uninvolved victim.

### Local Aptos analog: `staking_contract::set_beneficiary_for_operator` + `distribute_internal`

`distribute_internal` withdraws all inactive/pending_inactive stake from the pool and then pays out **every** recipient currently registered in the shared `distribution_pool` (which holds both the staker's unlocked-stake claims and the operator's commission claim) in a single loop, using `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has never registered a `CoinStore` for `AptosCoin` and has explicitly opted out of direct transfers via `set_allow_direct_coin_transfers(false)`: [2](#0-1) [3](#0-2) 

The operator (a non-owner, unprivileged role relative to the staker's principal) controls the recipient of their own commission via `set_beneficiary_for_operator`, and unlike the analogous `vesting::set_beneficiary`, this function does **not** verify the new beneficiary can actually receive APT: [4](#0-3) 

Compare this to `vesting::set_beneficiary`, where the same class of bug was already identified and explicitly guarded against with a comment referencing exactly this failure mode: [5](#0-4) 

Because Move aborts revert the entire transaction, once `distribute_internal`'s loop reaches the poisoned operator/beneficiary entry, the whole withdrawal — including the staker's own unlocked stake sitting in the same `distribution_pool` — reverts. `distribute()` is a public entry function callable by anyone, and `switch_operator` (the only other path off this operator) also calls `distribute_internal` before proceeding: [6](#0-5) 

So both the direct-distribution path and the switch-operator escape hatch are blocked simultaneously.

### Title
Operator can permanently block a staker's stake withdrawal by setting a beneficiary that rejects coin transfers - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`set_beneficiary_for_operator` lets an operator redirect their own commission payouts without verifying the new beneficiary can receive `AptosCoin`. Because `distribute_internal` pays every recipient (including the staker's unlocked-stake shares) in one atomic loop over the shared `distribution_pool`, a revert on the operator's poisoned beneficiary entry aborts the entire distribution, permanently trapping the staker's already-unlocked/inactive stake.

### Finding Description
`distribute_internal` iterates `distribution_pool.shareholders()` and calls `aptos_account::deposit_coins` per recipient in a single Move transaction; any abort rolls back the whole withdrawal [1](#0-0) . An operator can call `set_beneficiary_for_operator` to point their commission at an address that (a) has never registered an `AptosCoin` `CoinStore` and (b) has called `set_allow_direct_coin_transfers(false)`, guaranteeing `deposit_coins` aborts every time [2](#0-1) . Unlike `vesting::set_beneficiary`, which validates the target with `assert_account_is_registered_for_apt` specifically to prevent this class of DoS [7](#0-6) , `set_beneficiary_for_operator` performs no such check [8](#0-7) .

### Impact Explanation
The staker's inactive/pending_inactive stake becomes permanently unreachable: `distribute()` always reverts, and `switch_operator` — the only mechanism to change operators — itself invokes `distribute_internal` first and thus also always reverts [6](#0-5) . This is a non-recoverable loss of withdrawal rights for value the staker legitimately owns, triggered entirely by the operator's unprivileged action.

### Likelihood Explanation
Any operator with an active staking contract can trigger this at will and at negligible cost (one `set_allow_direct_coin_transfers(false)` call on a fresh/unregistered address plus one `set_beneficiary_for_operator` call), gated only by `features::operator_beneficiary_change_enabled()` being on.

### Recommendation
Add an `assert_account_is_registered_for_apt`-style check (or `can_receive_direct_coin_transfers` check) on `new_beneficiary` inside `set_beneficiary_for_operator`, mirroring the guard already present in `vesting::set_beneficiary`. Additionally, consider making `distribute_internal` resilient to a single failed payout (e.g., skip/queue a failing recipient rather than aborting the whole batch) so one bad recipient can never block unrelated stakers.

### Proof of Concept
1. Staker creates a staking contract with Operator O via `create_staking_contract`, and stake becomes inactive/unlockable over time (`unlock_stake`, populating `distribution_pool` with the staker's share).
2. O creates a fresh account `M`, calls `aptos_account::set_allow_direct_coin_transfers(M_signer, false)` and never registers `M` for `AptosCoin`.
3. O calls `staking_contract::set_beneficiary_for_operator(O, address_of(M))` — succeeds, no validation performed.
4. Anyone calls `staking_contract::distribute(staker, O)`: `distribute_internal` withdraws the pool's inactive coins, and when the loop reaches O's redirected beneficiary `M`, `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, reverting the transaction and leaving the staker's already-unlocked stake stuck.
5. Staker attempts `switch_operator` to escape — it also calls `distribute_internal` first and reverts identically, leaving the staker permanently unable to withdraw.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }

    #[view]
    /// Return true if `account` can receive direct transfers of coins that they have not explicitly registered to
    /// receive.
    ///
    /// By default, this returns true if an account has not explicitly set whether the can receive direct transfers.
    public fun can_receive_direct_coin_transfers(
        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
            || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
