### Title
Instant withdraw requests bypass the upfront management fee charged to normal withdrawal receipts, letting KYC'd lenders exit without paying for the time their receipt sits outside live NAV - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In `requestWithdraw`, normal withdrawal requests are haircut by `_totalWithdrawFees` (upfront management fee plus performance fee), but the instant-withdraw branch (`lastEpochApr > currentApr + instantWithdrawAprDelta`) creates an identically-queued receipt via `IdleCreditVault.requestInstantWithdraw` with zero fees charged. The receipt still occupies protocol funds from request time until the next `startEpoch` plus `instantWithdrawDelay`, yet pays nothing for that period — the same class of bug as the wasm `memory.grow` metering flaw: the cost parameter that actually drives resource consumption (time the receipt must be funded) is ignored, and a static "base" charge of zero is applied.

### Finding Description
`requestWithdraw` in `contracts/IdleCDOEpochVariant.sol` charges normal requesters `_totalWithdrawFees(principal, interest)` (lines 772-778), which includes `_calculateManagementFee(principal, _withdrawRequestManagementFeeDuration())` — a fee covering one full `epochDuration` plus remaining `bufferPeriod`, explicitly justified by the comment "receipts leave live NAV at request time but can be claimed only after the next epoch settles". When the instant path is taken (lines 761-770), the function calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` and `_withdrawOps` and returns without calling `_totalWithdrawFees` or incrementing `pendingWithdrawFees`. The receipt is then funded by `collectInstantWithdrawFunds` at the next `startEpoch` and remains claimable only after `instantWithdrawDelay` — i.e. the user's claim occupies funded capital for at least `bufferPeriod`-remaining + `instantWithdrawDelay` (configured ~3 days), but no management fee or performance fee accrues on it at any point. `IdleCreditVault.claimInstantWithdrawRequest` (lines 380-393) pays the full recorded amount 1:1 with no fee deduction either.

### Impact Explanation
Every lender that can route through the instant-withdraw path avoids the management fee that an equivalent normal withdrawal pays. The unpaid amount is `principal * managementFee * t / FULL_ALLOC / 365 days` for `t` ≈ remaining buffer + `instantWithdrawDelay` (~8 days with defaults), per requester, repeatable every epoch whenever APR drops by more than `instantWithdrawAprDelta`. This is a direct loss of protocol revenue (unclaimed yield owed to `feeReceiver`/`owner`) and breaks the fee-parity invariant between receipt types that both leave live NAV and both must be funded by the borrower/strategy. With a 1% management fee, a 1M USDC instant exit skips ~220 USDC of fees per epoch-cycle.

### Likelihood Explanation
Requires `allowInstantWithdraw`/`!disableInstantWithdraw`, `isWalletAllowed` (KYC'd lender — an allowed unprivileged actor), and an APR drop exceeding `instantWithdrawAprDelta` between epochs, which is a normal operational event (the entire instant-withdraw feature exists for this case). No privileged collusion needed; the attacker simply calls `requestWithdraw` during the window.

### Recommendation
Apply the same fee accounting to the instant path: compute `_totalWithdrawFees` (or at minimum `_calculateManagementFee` over the actual funded wait — remaining buffer + `instantWithdrawDelay`) and deduct it from `_underlyings` before calling `requestInstantWithdraw`, crediting `pendingWithdrawFees` so the fee is distributed at `stopEpoch`.

### Proof of Concept
```solidity
// Foundry fork test, based on test/foundry/IdleCreditVault.t.sol harness
function testInstantWithdrawSkipsManagementFee() external {
    uint256 amount = 1_000_000 * ONE_SCALE;
    uint256 mgmtFeeRate = 1_000; // 1%
    _setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, cdoEpoch.managementFee());
    _setManagementFee(mgmtFeeRate);

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Manager lowers APR by more than instantWithdrawAprDelta -> instant path
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialProvidedApr / 2, initialProvidedApr / 2);

    uint256 trancheAmt = IERC20(address(AAtranche)).balanceOf(address(this));
    uint256 principal = trancheAmt * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;

    uint256 requested = cdoEpoch.requestWithdraw(trancheAmt, address(AAtranche));

    // Instant path: full principal receipted, no fee booked
    assertEq(requested, principal, "instant request was not charged any fee");
    assertEq(cdoEpoch.pendingWithdrawFees(), 0, "no management/performance fee accrued");
    assertEq(
        IdleCreditVault(address(strategy)).instantWithdrawsRequests(address(this)),
        principal,
        "receipt owed 1:1 despite occupying funded capital for buffer+delay"
    );

    // A normal request on the same principal would have paid:
    // principal * mgmtFeeRate * (epochDuration + remainingBuffer) / FULL_ALLOC / 365 days
}
```

Note: it is possible the zero-fee instant path is a deliberate product decision (instant withdrawers forgo all epoch interest, which is a larger "cost" than the skipped fee). If intentional, this is a design asymmetry rather than a vulnerability; the code gives no comment indicating the fee waiver is intentional, so it is worth flagging for confirmation.
