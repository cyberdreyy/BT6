Based on the investigation, I found a genuine analog to the reported fee-calculation asymmetry: the codebase computes the *same* nominal "70% supermajority" threshold in two different, mutually-inconsistent ways (floor vs. ceiling), in two places that are supposed to represent one equality.

### Title
Inconsistent supermajority-threshold rounding between `GlobalStateEvaluator::reached_agreement` and `NakamotoBlockHeader::compute_voting_weight_threshold` breaks the signed-vs-required-threshold equality - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
`GlobalStateEvaluator::reached_agreement`/`reached_disagreement` (used by every signer to decide the agreed global state: active miner, burn view, tx replay set, and protocol version) computes the 70%/30% cutoffs with plain integer division (floor), while `NakamotoBlockHeader::compute_voting_weight_threshold` (the canonical threshold used for actual block-signature approval and pre-commit gating) computes the same nominal cutoff with an explicit ceiling. For any `total_weight` where `total_weight * 7` is not a multiple of 10, these two "70%" thresholds disagree by exactly one weight unit — the exact same class of bug as the report's `subBp`/`addBp` direction mismatch, where one formula is applied where the inverse/rounded formula was required.

### Finding Description
`reached_agreement` floors the threshold: [1](#0-0) 

`compute_voting_weight_threshold`, used for the actual on-chain block-approval threshold and for pre-commit/signature-threshold gating in the signer (`handle_block_pre_commit`, `store_and_process_block_signature`, `handle_block_rejection`), ceils it: [2](#0-1) 

Both are meant to express "70% of total signer weight," exactly as the report's `previewMint`/`previewDeposit` were both meant to express "the fee on this trade." When `total_weight * 7 % 10 != 0` (which is the common case, e.g. `total_weight = 11` → floor = 7, ceil = 8), `reached_agreement` will declare consensus reached with strictly less weight than `compute_voting_weight_threshold` requires elsewhere in the same signer process for the identical nominal supermajority. This is deterministic and requires no majority collusion or privileged access — it fires purely from the arithmetic on whatever `total_weight` the reward set happens to have, so it is triggered naturally whenever signers' burn views/miner views diverge (e.g., during a fork or timing skew that a single miner's tenure-change can induce), not by any specific attacker action beyond normal operation.

`determine_global_state` (which decides the agreed `current_miner`, `burn_block`, and `tx_replay_set`) and `determine_latest_supported_signer_protocol_version` both gate on `reached_agreement`: [3](#0-2) 

This global state is then used by `check_block_against_global_state` to accept/reject block proposals: [4](#0-3) 

So the "agreed" state driving block accept/reject decisions can lock in with one weight-unit less than the true supermajority the rest of the protocol enforces for signatures, while the block-signature/pre-commit path a few lines away in the very same binary enforces the stricter, rounded-up threshold.

### Impact Explanation
This is a threshold-computation inconsistency ("acting on a stale/threshold mismatch") between the internal global-state-agreement gate and the canonical signature-approval gate. In edge-case weight distributions it can let a genuinely sub-70% (by the codebase's own canonical rounding rule) set of signers fix the "agreed" current miner / burn view / tx replay set that subsequently governs whether valid blocks from the legitimate miner are accepted or rejected — a liveness/consistency risk on the boundary condition, not a full majority break.

### Likelihood Explanation
High for occurrence (any `total_weight` not evenly divisible in the `*7/10` computation triggers the discrepancy — most real reward-set weight totals), but the magnitude of the discrepancy is bounded to a single weight unit, so practical impact depends on how close honest signer distributions sit to the boundary.

### Recommendation
Use one canonical, shared threshold function for both `reached_agreement`/`reached_disagreement` and `compute_voting_weight_threshold` (i.e., have `libsigner`'s `GlobalStateEvaluator` call the same ceiling-based `NakamotoBlockHeader::compute_voting_weight_threshold` logic rather than re-implementing the 70%/30% math with different rounding), eliminating any possibility of the two notions of "supermajority" diverging.

### Proof of Concept
With `total_weight = 11` and `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7`:
- `reached_agreement`: `11 * 7 / 10 = 7` (floor) → 7 weight units is "sufficient" to fix global state.
- `compute_voting_weight_threshold(11)`: `(11*7)/10 + ceil = 7 + 1 = 8` → 8 weight units required for block signature/pre-commit approval.

A vote/update set with weight 7 out of 11 (63.6%) is accepted by `determine_global_state`/`reached_agreement` as final global consensus, even though it is below the 8/11 (72.7%) supermajority the same codebase requires to actually approve a block signature, exposing the exact equality gap.     /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
