### Title
Builder index reuse (`get_index_for_new_builder`) does not check for outstanding pending payments, allowing a new builder's balance to be misdirected to a stale payment recipient - (File: specs/gloas/beacon-chain.md)

### Summary
The reused-slot mechanism for builder registration checks only `builder.balance == 0` and `builder.withdrawable_epoch <= current_epoch` before letting a brand-new builder (new pubkey) take over an old builder's index. It never checks `get_pending_balance_to_withdraw_for_builder`, the exact helper that exists to detect outstanding `builder_pending_withdrawals` / `builder_pending_payments` entries referencing that index. This is the consensus-layer analogue of the reported trading bug: a slot (`openTrades[...][index]` there, `state.builders[builder_index]` here) is freed and reassigned to a new occupant while a stale queued instruction that still carries the old occupant's index is left unresolved, and later executes against the new occupant.

### Finding Description
`get_index_for_new_builder` decides whether an exited builder's registry slot can be handed to a new pubkey: [1](#0-0) 

The only guards are zero balance and an elapsed `withdrawable_epoch`. Compare this to `get_pending_balance_to_withdraw_for_builder`, which was specifically written to detect balances still owed to/queued for a `builder_index` via two separate queues, `builder_pending_withdrawals` and `builder_pending_payments`: [2](#0-1) 

Both queue entry types carry only a `builder_index` and a `fee_recipient`/`amount` — they do not carry the builder's pubkey, so once the index is repurposed there is no way for `get_builder_withdrawals`/`process_builder_pending_payments` to detect that the "builder" behind that index is no longer the one the payment was queued for.

Crucially, the spec authors themselves reused exactly this check (`get_pending_balance_to_withdraw_for_builder(...) != 0`) as a precondition to protect a builder from being disturbed while it has unresolved payment obligations, but only for voluntary exit initiation: [3](#0-2) 

That same check is conspicuously absent from `get_index_for_new_builder`/`process_builder_deposit_request`, which is the function that actually determines whether an index is safe to hand to a different pubkey: [4](#0-3) 

Withdrawals against a `builder_index` are applied using whatever `Builder` currently occupies that slot, not a builder identity captured at queue time — the amount withdrawn is `min(withdrawal.amount, builders[withdrawal.builder_index].balance)`, and the balance mutated is `state.builders[builder_index].balance` (see the input/output-space report and test fixtures for `get_builder_withdrawals`): [5](#0-4) 

This is functionally identical to the reported trading bug: the "order" (here, a `BuilderPendingWithdrawal`/`BuilderPendingPayment`) stores an index, not an identity, and is executed later against whatever occupies that index — without verifying the occupant is still the one the order was created for. The report's own explicit note even documents that index reuse is by design ("Builder indices are reusable... a newly registered builder's public key may have previously appeared in the builder set"), but the design omits the missing-obligation check that `get_pending_balance_to_withdraw_for_builder` was built to provide.

### Impact Explanation
If a builder's balance is driven to `0` (e.g. by the sweep withdrawal mechanism or a full exit withdrawal) while it still has an outstanding `builder_pending_withdrawals`/`builder_pending_payments` entry queued against its index (these queues are processed on their own independent schedules, decoupled from the balance-zeroing event), `get_index_for_new_builder` will incorrectly treat the slot as reusable. A completely unrelated new builder can then deposit and take over that index. When the stale queue entry is later drained by `get_builder_withdrawals` / `process_builder_pending_payments`, it debits the **new** builder's freshly deposited balance and pays it to the **old** builder's `fee_recipient` — Gwei is moved out of a builder's balance without that builder's authorization and paid to a party it never committed to. This matches the in-scope Critical/High class: "a payload or payment applied that the block did not commit to" / "a builder payment or withdrawal misdirected."

### Likelihood Explanation
Likelihood is Medium: it requires a specific, but not implausible, timing where (a) a builder's `balance` becomes exactly `0` (e.g., via the withdrawal sweep or a full withdrawal) and `withdrawable_epoch` has elapsed, while (b) a `builder_pending_withdrawals`/`builder_pending_payments` entry that predates the zeroing is still queued for that same `builder_index`, and (c) a new builder deposit request lands before that stale queue entry is drained. I was not able to fully retrieve `settle_builder_payment` and `process_builder_pending_payments` in this pass to pin down the exact block/epoch ordering that produces balance-zero-with-pending-obligation; this should be verified against those two functions to confirm the precise window, but the missing guard in `get_index_for_new_builder` itself is directly confirmed in the spec text above and is the root cause regardless of exact timing.

### Recommendation
`get_index_for_new_builder` (and the reuse branch inside `process_builder_deposit_request`) should additionally require `get_pending_balance_to_withdraw_for_builder(state, index) == 0` before treating a slot as reusable — mirroring the guard already used in `process_builder_exit_request`. This ensures no `builder_index` is handed to a new pubkey while any queued payment obligation still references it, closing the "stale order executed against replaced occupant" class of bug identified in the external report.

### Proof of Concept
1. Builder `B_old` occupies `builder_index = k`. A bid win/payment settlement enqueues a `BuilderPendingWithdrawal` (or `BuilderPendingPayment`) with `builder_index = k`, `fee_recipient = <old payee>`, `amount = A`, to be drained by `get_builder_withdrawals` on a later slot/epoch.
2. Before that entry is drained, `B_old`'s `balance` independently reaches `0` (e.g., via sweep withdrawal or a full exit withdrawal) and `withdrawable_epoch <= current_epoch`.
3. A new `BuilderDepositRequest` for a fresh pubkey `B_new` is processed. `get_index_for_new_builder` sees `builders[k].balance == 0` and `withdrawable_epoch` elapsed, and returns `k`; `add_builder_to_registry` overwrites slot `k` with `B_new`, funded with the new deposit amount. [6](#0-5) 
4. On a subsequent slot, `get_builder_withdrawals` drains the stale entry for `builder_index = k`, decreasing `state.builders[k].balance` (now `B_new`'s balance) by `min(A, balance)` and creating a `Withdrawal` to the old `fee_recipient` — moving `B_new`'s Gwei to a recipient `B_new` never authorized.

```python
def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
```

def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

###### New `process_builder_deposit_request`

*Note*: Builder indices are reusable. When a builder exits, its index may later
be reassigned to a different builder with a new public key. Any deposit sent to
an exited builder will be withdrawn to the builder’s execution address. Exited
builders cannot be reactivated, although a newly registered builder’s public key
may have previously appeared in the builder set. Implementations that rely on
caching should account for this behavior.

```python
def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
