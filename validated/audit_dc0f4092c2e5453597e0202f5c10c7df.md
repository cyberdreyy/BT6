### Title
Loss-adjusted withdraw receipts bypass the `stopEpochWithDuration` haircut because `lossRecoveryPriceByEpoch` is indexed by the post-increment epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` records each user's receipt under the *pre-stop* `epochNumber` (`lastWithdrawRequest[_user]` and `withdrawsRequestsByEpoch[_user][epochNumber]`), but `collectWithdrawFunds` stores the loss haircut under `lossRecoveryPriceByEpoch[epochNumber]` after `deposit()` has already incremented `epochNumber` during `stopEpoch`/`stopEpochWithDuration`. Claims therefore look up the haircut under the wrong (stale) epoch key, read 0, and fall through to `_claimFundedWithdrawRequest`, which pays the full unhaircutted basis.

### Finding Description
The storage layout uses epoch-indexed mappings as a variable-length claim log:

- `requestWithdraw` writes the receipt at the epoch observed at request time: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch`, where `currentEpoch = epochNumber` (contracts/strategies/idle/IdleCreditVault.sol:282-293).
- `deposit()` increments `epochNumber` when `isEpochRunning()` is true, i.e., inside `stopEpoch`/`stopEpochWithDuration` before epoch state is cleared (contracts/strategies/idle/IdleCreditVault.sol:607-610).
- `collectWithdrawFunds` runs during the same stop flow, after the increment, and writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` using the *new* epoch value (contracts/strategies/idle/IdleCreditVault.sol:411-421), while zeroing `pendingWithdraws`.
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the old epoch — finds 0, and returns 0 (contracts/strategies/idle/IdleCreditVault.sol:789-800). Control reaches `_claimFundedWithdrawRequest`, whose gate `epochNumber <= lastWithdrawRequest[_user]` now passes (N+1 > N), so it burns and pays the full `withdrawsRequests[_user]` at par via `_transferFundedClaim` (contracts/strategies/idle/IdleCreditVault.sol:319-349).

The same stale-index mismatch makes the `requestWithdraw` re-request guard (lines 261-271) read `lossRecoveryPriceByEpoch` under the old epoch, so it never detects the pending haircut either.

### Impact Explanation
When `stopEpochWithDuration(_lossAmount)` funds only `pendingBasis - loss` into the strategy, a withdrawer with a pending receipt claims the full principal+interest basis instead of `basis * lossRecoveryPrice / 1e18`. The shortfall is paid out of underlyings held for other purposes — funded instant-withdraw claims, the default recovery reserve guard notwithstanding (it only protects `defaultRecoveryReserve`), or other users' funded receipts. Direct theft of the loss amount per claimant and protocol insolvency for subsequent claimants. Broken invariant: loss waterfall / one receipt one payout.

### Likelihood Explanation
Any KYC-passing lender or tranche-token holder can open a withdraw request during a running epoch; the exploit requires only a subsequent `stopEpochWithDuration` with a realized loss, which is a normal honest-manager/borrower flow. No privileged action by the attacker is needed. The loss-adjusted claim path becomes unreachable for every affected epoch, so all pending receipt holders of that epoch are overpaid.

### Recommendation
Store the loss recovery price under the epoch that owns the receipts — i.e., `lossRecoveryPriceByEpoch[epochNumber - 1]` after the increment, or perform the `collectWithdrawFunds` haircut bookkeeping before `deposit()` bumps `epochNumber`. Alternatively, track the "pending receipts epoch" explicitly and have both the writer and the reader use that single key.

### Proof of Concept
Foundry fork PoC outline:

```solidity
// setup: IdleCDOEpochVariant + IdleCreditVault, lender KYC'd, epoch running (epochNumber = N)
function test_LossAdjustedReceiptPaidAtPar() public {
    // 1. Alice deposits and requests withdraw of A underlyings in epoch N.
    vm.prank(cdo); // via cdo.requestWithdraw path
    vault.requestWithdraw(A, alice, A); // lastWithdrawRequest[alice] = N, withdrawsRequestsByEpoch[alice][N] = A

    // 2. Borrower repays partially; manager calls stopEpochWithDuration(loss).
    //    deposit() -> epochNumber = N+1; collectWithdrawFunds(A - lossShare)
    //    stores lossRecoveryPriceByEpoch[N+1] = price < 1e18; pendingWithdraws = 0.
    stopEpochWithLoss(loss);

    // 3. Alice claims: lossRecoveryPriceByEpoch[N] == 0 -> loss-adjusted path skipped;
    //    epochNumber (N+1) > lastWithdrawRequest (N) -> funded path pays full A.
    uint256 balBefore = underlying.balanceOf(alice);
    vm.prank(cdo);
    vault.claimWithdrawRequest(alice);
    uint256 paid = underlying.balanceOf(alice) - balBefore;

    assertEq(paid, A);                       // full par payout
    assertLt(paid, A - expectedHaircut);     // should have been A * lossRecoveryPriceByEpoch[N+1] / 1e18
}
```

Note: this relies on `deposit()` being invoked by the CDO inside `stopEpoch`/`stopEpochWithDuration` *before* `collectWithdrawFunds` (consistent with the comment at line 608 that the deposit happens "on stopEpoch (before setting the var to false)"). If the concrete CDO ordering places `collectWithdrawFunds` before the increment, the epoch keys match and this specific finding does not hold; I could not fully verify the call ordering inside `IdleCDOEpochVariant.stopEpochWithDuration` within this session.
