### Title
Blocked epoch settlement via forced `StopEpochVaultLiquidityUnavailable` revert prevents default crystallization and permanently freezes pool funds - (contracts/strategies/idle/ProgrammableBorrower.sol:246-253)

### Summary
`ProgrammableBorrower.onStopEpoch` distinguishes two failure modes: if vault shares cannot economically cover the required shortfall it returns `true` so the later `transferFrom` fails and IdleCDO enters `_handleBorrowerDefault`; but if shares nominally cover the shortfall while `vault.withdraw` reverts, it reverts with `StopEpochVaultLiquidityUnavailable`. Because hook reverts bubble through `_stopEpoch`, the whole epoch settlement aborts **before** the default path is reached — no `defaulted` flag, no loss waterfall, no recovery accounting, epoch stays "running" forever. This is the exact analog of the Blueberry report: a blocked repayment path prevents the insolvency/loss-realization mechanism from executing.

### Finding Description
In `onStopEpoch`, when `_amountRequired > onHand` the contract computes `shortfall` and only checks `_currentVaultAssets()` (a `convertToAssets` valuation) before attempting `vault.withdraw` [1](#0-0) . A `convertToAssets`-solvent but withdrawal-failing vault (e.g., a Morpho-style vault whose underlying liquidity is fully lent out or whose markets carry bad debt — shares still price above zero, withdrawals revert or are unavailable) forces the `catch` → `revert StopEpochVaultLiquidityUnavailable()` path.

The revert propagates out of `IProgrammableBorrower(_borrower()).onStopEpoch(...)` inside `_stopEpoch` — the code comments explicitly state "Hook reverts bubble so transient ERC4626 liquidity failures can be retried" [2](#0-1) . Consequently `_handleBorrowerDefault` is never reached: `defaulted` stays `false`, `isEpochRunning` stays `true`, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` remain in their pre-stop state, and `expectedEpochInterest`/recovery basis are never checkpointed [3](#0-2) .

There is no privileged escape: `emergencyExitVault` also calls `vault.redeem` and reverts under the same illiquidity [4](#0-3) , and `_repay`/`borrow` similarly revert on `vault.withdraw` failure [5](#0-4) . `restoreOperations` cannot declare a default and is gated by `defaulted || priceAA == 0` checks only for reopening. The pool is therefore stuck mid-epoch with neither settlement nor default.

An unprivileged attacker — explicitly in scope as "a user of the programmable borrower's ERC4626 vault" — can keep the vault in this state by borrowing out the vault's underlying market liquidity (flash or sustained), timing it so `stopEpoch`/`stopEpochWithDuration` always reverts. Unlike the intended `shortfall > _currentVaultAssets()` branch that degrades into a real default, this branch produces no terminal state at all.

### Impact Explanation
Permanent or indefinite freezing of the entire tranche NAV: withdraw requests from the previous epoch can never be claimed (funds remain in the borrower's vault, `pendingWithdraws` never collected), no new epoch can start, deposits/redeems stay gated, and — critically — the loss cannot be socialized because the default machinery (`_handleBorrowerDefault`, `finalizeDefaultRecovery`, `DefaultDistributor`) is never entered. If the vault's illiquidity reflects real bad debt in its underlying markets, the pool accrues unpriced losses indefinitely: the very scenario in the external report (blocked repayment preventing bad-debt realization → insolvency) is reproduced, since even honest manager calls to `stopEpoch` cannot force the default path. Broken invariant: epoch state machine liveness / guaranteed loss waterfall.

### Likelihood Explanation
Requires a programmable-borrower deployment whose vault can be simultaneously share-solvent and withdrawal-failing — a normal state for lending-market ERC4626s with fully-utilized or distressed markets. The attacker only needs to interact with the public ERC4626 vault/its underlying markets (unprivileged), and the condition can persist as long as the liquidity remains drained or impaired. No malicious privileged role needed; owner/manager calls are honest and simply revert.

### Recommendation
Make `onStopEpoch` fail-soft: instead of reverting on `vault.withdraw` failure, return `false` (or leave the funds unpulled and let `transferFrom` fail) so `IdleCDOEpochVariant` deterministically enters `_handleBorrowerDefault`, which pauses deposits, stops the epoch, disables withdraw requests, and enables the recovery distribution path. Alternatively, add a permissioned "force default" path in `IdleCDOEpochVariant` that works while the borrower hook reverts (the already-foreseen retryable design implies settlement liveness depends entirely on third-party vault liquidity).

### Proof of Concept
Foundry fork test (sketch, based on `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup):

```solidity
function testStopEpochBlockedByIlliquidVaultNeverDefaults() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // Attacker: unprivileged user of the ERC4626 vault drains its withdrawable
    // liquidity (e.g., borrows all idle assets from the underlying Morpho markets),
    // so convertToAssets(shares) still covers the shortfall but withdraw() reverts.
    _drainMorphoVaultLiquidity(); // leaves shortfall <= _currentVaultAssets()

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Honest manager tries to settle — reverts, no default, no settlement.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Invariant broken: epoch stuck running, default never declared.
    assertEq(cdoEpoch.defaulted(), false);
    assertEq(cdoEpoch.isEpochRunning(), true);
    assertFalse(programmableBorrower.epochAccountingActive() == false); // still active
    // Every subsequent stopEpoch reverts identically while vault is illiquid:
    // funds locked, pending withdraws unclaimable, losses never socialized.
}
```

Key steps: deposit → startEpoch → attacker removes vault withdraw liquidity while keeping share price intact → `stopEpoch` reverts in `onStopEpoch` catch branch instead of entering `_handleBorrowerDefault` → repeat indefinitely; loss waterfall and recovery distribution unreachable.

  /// @notice Handle borrower default
  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.

    if (isProgrammableBorrower) {
      IProgrammableBorrower(_borrower()).onDefault();
    }

    // deposits should be already prevented
    if (!paused()) {
      _pause();
    }

    // stop the current epoch
    isEpochRunning = false;

    // prevent withdrawals requests
    allowAAWithdrawRequest = false;
    allowBBWithdrawRequest = false;

    emit BorrowerDefault(funds);
  }
