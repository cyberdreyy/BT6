### Title
Attacker-controlled ERC4626 vault state corrupts `totalInterestDueNow()` and can permanently block `stopEpoch` - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
CVE-2016-10712 is a trust-boundary bug: `stream_get_meta_data()` returns metadata (`uri`) that is fully attacker-controlled, so code that trusts the "trusted" return value operates on injected data. The analog in this codebase is `ProgrammableBorrower`, which is a trust proxy between `IdleCDOEpochVariant` and an external ERC4626 vault. `IdleCDOEpochVariant` prices the entire epoch from a single external read — `totalInterestDueNow()` — which is derived from `vault.convertToAssets(shares)` and `vault.balanceOf()`, values any user of that ERC4626 vault can move by depositing, donating, or draining vault liquidity. `onStopEpoch` then hard-reverts (`StopEpochVaultLiquidityUnavailable`) if `vault.withdraw()` fails, permanently freezing the epoch when an attacker keeps the external vault illiquid.

### Finding Description
The flow is:

- `stopEpoch` on `IdleCDOEpochVariant` reads `ProgrammableBorrower.totalInterestDueNow()` to compute the interest that must be returned/minted (`contracts/strategies/idle/ProgrammableBorrower.sol:330-334`).
- `totalInterestDueNow` is computed in `_vaultNetInterest()` as `bufferedVaultDelta + (_currentVaultAssets() + epochWithdrawnFromVault) - (epochStartVaultAssets + epochDepositedToVault)` (`ProgrammableBorrower.sol:337-347`), where `_currentVaultAssets()` is `vault.convertToAssets(vault.balanceOf(this))` (`ProgrammableBorrower.sol:546-549`) — a value fully determined by external vault share price and vault liquidity, both manipulable by any ERC4626 vault user (an unprivileged attacker class per the engagement rules).
- In `onStopEpoch`, when on-hand balance is short, the code calls `vault.withdraw(shortfall, ...)` inside a try and reverts `StopEpochVaultLiquidityUnavailable` on failure (`ProgrammableBorrower.sol:246-253`). The early-return `if (shortfall > _currentVaultAssets()) return true;` only protects against share-value insufficiency, not liquidity insufficiency: an attacker can keep the vault's share price high (so `_currentVaultAssets()` covers the shortfall) while leaving zero borrowable/redeemable liquidity, forcing the revert on every `stopEpoch` attempt.
- Every interest-bearing component read by the CDO (`vaultInterestAccrued`, `vaultLoss`, `borrowerInterestOwedNow`) flows through the same attacker-influenced vault accounting. In `isInterestMinted` mode, an inflated `convertToAssets` (e.g., vault share-price inflation via a donation made while the attacker holds the dominant share position, or via vaults whose accounting counts attacker-controlled side balances) inflates `totalInterestDueNow`, and the CDO mints unbacked strategy-token interest that is then distributed pro-rata to withdraw-claimants, diluting real backing.

Existing guards do not stop this: the skim (`_skimDonatedAssets`) only covers raw underlying on the CDO, not the external vault; `nonReentrant` doesn't help; owner/manager cannot call `stopEpoch` successfully while the vault is illiquid; `onDefault` exists but only after `stopEpoch` reaches its default path, which the revert prevents.

### Impact Explanation
Broken invariants: solvency and fair mint/burn (minted interest backed by phantom external-vault gains), and liveness of the epoch state machine (permanent freezing). Concretely: an attacker who is a large LP/user of the programmable borrower's ERC4626 vault drains or borrows the vault's liquidity immediately before `epochEndDate`. Each `stopEpoch` call reverts in `onStopEpoch`. All tranche-holder funds and pending withdraw receipts stay frozen in the facility for as long as the attacker withholds liquidity — with a lending-market-style vault this can be permanent (attacker borrows and never repays, a standard vault user action). Quantified loss: the entire pool NAV plus all pending withdraw requests. Alternatively, in minted-interest mode, inflated vault accounting causes interest to be minted against gains the pool never receives, producing insolvency realized by the last claimants.

### Likelihood Explanation
Requires the programmable-borrower mode (a supported deployment: `setIsProgrammableBorrower`, `isInterestMinted` forced true, instant withdrawals disabled) and an external ERC4626 vault in which any unprivileged user can influence `convertToAssets` or redeemable liquidity — true for lending-market vaults, and for any vault where donations move share price. The attack needs no privileged role in this codebase; the attacker is merely a user of the external vault, which the threat model explicitly allows.

### Recommendation
- Decouple pool-facing interest from a manipulable external price: snapshot an internally-tracked interest baseline at epoch start and bound `totalInterestDueNow` by realized deltas (actual assets pulled in/out), not `convertToAssets`.
- Make `onStopEpoch` non-reverting on external-vault withdrawal failure: return `false`/partial so `IdleCDOEpochVariant` can proceed to its default or retry path rather than bricking the epoch state machine on an external dependency.
- Account vault deposits/withdrawals by actual assets moved (use the `withdraw` return/`previewRedeem` bounds) instead of trusting `convertToAssets` deltas.

### Proof of Concept
```solidity
// test/foundry/ProgrammableBorrowerStopEpochFreeze.t.sol — conceptual Foundry PoC
// Setup: IdleCDOEpochVariant with isProgrammableBorrower = true, isInterestMinted = true,
// ProgrammableBorrower configured against an external ERC4626 vault (e.g. a lending market
// or a vault the attacker can drain).
function testAttackerVaultUserFreezesStopEpoch() external {
    // 1. LP deposits during buffer; manager starts epoch.
    idleCDO.depositAA(100_000e6);
    vm.prank(manager);
    cdoEpoch.startEpoch(); // onStartEpoch deposits idle funds into external vault

    // 2. Attacker (unprivileged user of the same ERC4626 vault) drains vault liquidity,
    //    e.g. borrows all available assets or redeems to leave < shortfall borrowable,
    //    while keeping the pool's convertToAssets valuation intact.
    address attacker = makeAddr("attacker");
    vm.prank(attacker);
    externalVault.borrowOrWithdrawAllLiquidity(); // vault-specific user action

    // 3. epochEndDate passes; manager tries to stop the epoch.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    // onStopEpoch: shortfall <= _currentVaultAssets() (price fine) but vault.withdraw reverts
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(apr, 1);

    // 4. Repeatable forever while attacker withholds liquidity: funds frozen.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(apr, 1);

    // Invariant broken: isEpochRunning stays true, epochEndDate stays set,
    // and no LP can request or claim a withdrawal of pool NAV.
}
```

Uncertainty note: I verified the revert path and the external-valuation dependency in `ProgrammableBorrower.sol`, but did not fully trace every caller of `stopEpoch`/`_beforeStopEpoch` in `IdleCDOEpochVariant` nor confirm whether a queued recovery path exists that bypasses `onStopEpoch`; if such a bypass exists it reduces Impact to temporary freezing plus the minted-interest dilution leg.
