### Title
Unauthenticated `InitializeNonceAccount` allows front-running nonce account setup to seize authority and steal funds - (File: programs/system/src/system_processor.rs, programs/system/src/system_instruction.rs)

### Summary
The System Program's `InitializeNonceAccount` handler transitions a durable-nonce account from `State::Uninitialized` to `State::Initialized`, setting the nonce authority. Unlike every other privileged System Program operation (`Allocate`, `Assign`, `CreateAccount`, `WithdrawNonceAccount`, `AuthorizeNonceAccount`, `AdvanceNonceAccount`), it performs **no signer check at all** on the account being initialized or on any owner/authority key — it only checks that the account is writable and system-owned/uninitialized.

### Finding Description
`initialize_nonce_account` in [1](#0-0)  only validates that the account `is_writable()`, is in `State::Uninitialized`, and has enough lamports for rent-exemption — it never checks that the account itself, or any particular authority, signed the transaction. Compare this to `allocate`/`assign` in the same program, which explicitly require `address.is_signer(signers)` [2](#0-1) [3](#0-2) , and to `advance_nonce_account`/`withdraw_nonce_account`, which require the stored `authority` to sign [4](#0-3) [5](#0-4) .

The processor entry point for `SystemInstruction::InitializeNonceAccount` requires only one account and passes the `authorized` pubkey straight from unauthenticated instruction data, with no signature requirement tied to the target account or any existing owner: [6](#0-5) .

This is directly analogous to the reported bug class ("initialization functions can be front-run with malicious values"): whenever account creation (`CreateAccount`/`Allocate`+`Assign`) and nonce initialization happen as two independent instructions/transactions instead of the atomic bundle produced by `create_nonce_account()` (used by `cli/src/nonce.rs` and `system_instruction::create_nonce_account`, see [7](#0-6) ), any third party can race to submit `InitializeNonceAccount` targeting the not-yet-initialized, already-funded account before the legitimate owner does, since the instruction requires no signature tying it to that account or its intended owner.

Because `set_state`/`can_data_be_changed()` only require the account be **owned by the System Program** and writable [8](#0-7) , this precondition is trivially satisfied by any freshly `CreateAccount`'d (system-owned, rent-funded, zeroed) account awaiting initialization — exactly the intermediate state that exists if creation and initialization are split across transactions.

### Impact Explanation
An attacker who observes (or predicts) a rent-exempt, system-owned, uninitialized nonce-account address (e.g., a two-step create-then-initialize flow, a program that pre-funds addresses before initializing them in a follow-up transaction, or simply a delayed initialize after creation) can submit their own `InitializeNonceAccount` instruction first, becoming the nonce `authority`. Once initialized with the attacker as authority, the attacker can call `WithdrawNonceAccount`, which only requires the stored `authority` to sign [9](#0-8) , and drain the account's lamports (which were already funded by the victim to be rent-exempt) — concrete unsigned fund theft. It also lets the attacker seize control of a durable-nonce mechanism used for offline/durable transaction signing, potentially disrupting or hijacking the victim's intended nonce-based transaction flow.

### Likelihood Explanation
Exploitability depends entirely on account-creation and initialization being split into separate transactions instead of using the atomic `create_nonce_account`/`create_nonce_account_with_seed` helper that bundles `CreateAccount` + `InitializeNonceAccount` in one message (as used throughout the CLI, e.g. [7](#0-6) ). When that atomic helper is used, front-running is not possible because both instructions execute together and the "to" account must co-sign `CreateAccount`. The risk materializes only for callers/integrations (custom programs, scripts, CPI flows) that separate the two steps into different transactions or perform `Allocate`/`Assign` and initialize independently — a pattern the interface does not prevent nor warn against.

### Recommendation
Add an explicit signer requirement to `initialize_nonce_account` — e.g., require the account itself (or a specified authority) to be a transaction signer, mirroring the `Allocate`/`Assign`/`CreateAccount` pattern — so that only the party who created/controls the account can perform the initialization, closing the front-running window regardless of whether creation and initialization are bundled atomically.

### Proof of Concept
1. Victim sends a transaction containing `SystemInstruction::CreateAccount` (or `Allocate`+`Assign`) targeting pubkey `N`, funding it to rent-exemption for `NonceState::size()`, owned by the System Program, intending to send a follow-up `InitializeNonceAccount(victim_authority)` transaction.
2. Attacker observes the confirmed (or pending) creation and, before the victim's second transaction lands, submits their own transaction with `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` referencing account `N` as the sole (non-signing) account. Per [6](#0-5)  and [1](#0-0) , this succeeds with no signature from `N` or from `attacker_pubkey`.
3. `N`'s state becomes `State::Initialized{ authority: attacker_pubkey, .. }`.
4. Victim's original `InitializeNonceAccount` now fails (`State::Initialized` guard rejects re-initialization).
5. Attacker calls `SystemInstruction::WithdrawNonceAccount` signing as `attacker_pubkey`, per [10](#0-9) , draining `N`'s lamports to an account they control.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
