## Finding

### Title
Signer Fails Open and Signs a Conflicting Block When the Same-Tenure Tip Check Errors - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`Signer::handle_block_pre_commit` guards against double-signing within the same tenure by asking the node whether the tenure's canonical tip already reaches the height of a competing, previously-signed block. When that RPC call to the stacks-node errors (timeout, connection reset, node restart), the code treats the failure as if verification had succeeded in the signer's favor and continues on to sign and broadcast acceptance of the new block — the exact bug class in CVE-2024-48460 (Tabby sending credentials despite failed host-key verification): a security-relevant action proceeds past a check whose verification could not be completed.

### Finding Description
In `handle_block_pre_commit`, after the general freshness/cross-tenure conflict guard passes, the signer runs a same-tenure-specific check meant to stop it from signing two conflicting blocks inside one tenure: [1](#0-0) 

If `stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash)` returns `Ok`, the tip height is compared against the proposed block's height and the signer refuses to sign when the tenure is already confirmed at/above that height. But on `Err(e)`, the code only logs `"Treating the tenure as unconfirmed"` and falls through — there is no `return`. Execution proceeds directly to marking the block locally accepted and producing a real signature: [2](#0-1) 

`create_block_acceptance` unconditionally signs the block header hash with the signer's private key: [3](#0-2) 

This branch is only reached once `conflicts` (from `get_signed_conflicts`) contains a block the signer already put a signature over in the *same tenure* at the same or higher height: [4](#0-3) 

The design intent, per the accompanying documentation, is explicit fail-open here: "for the own-tenure question below, an unreachable node is instead treated as unconfirmed and the signature goes out," in contrast to every other conflict question in the same function, which fails closed ("Whenever the node cannot be asked, the conflict keeps blocking..."). [5](#0-4) 

The equality this breaks: a signer's own signed-block set at a given (tenure, height) should never contain two conflicting blocks — the very invariant this guard exists to enforce. A transient RPC failure between the signer and its local stacks-node (something a miner or normal network conditions can induce/exploit by timing a re-proposal during an outage/restart) causes the guard to silently pass, and the signer produces and broadcasts a second, conflicting acceptance signature in the same tenure.

### Impact Explanation
This falls under the Critical impact bucket in scope: "a signer signing an invalid, non-canonical, or conflicting block." A conflicting signature within the same tenure — the narrowest and most dangerous form of equivocation — undermines the one-per-height guarantee the whole pre-commit/conflict machinery (sections 5 and 7 of `docs/signer-flows.md`) is built to prevent. Unlike the cross-tenure/other-tenure conflict paths, which are explicitly designed to fail closed specifically because "wrongly signing cannot be taken back," this one path fails open.

### Likelihood Explanation
No majority of signers, another signer's key, or StackerDB/auth-token access is required. The trigger is an ordinary operational condition: any transient failure of the signer→node RPC call (timeout, restart, brief network blip) occurring exactly when a same-tenure conflicting proposal crosses the pre-commit threshold. A miner can increase the likelihood by re-proposing a conflicting block (as the codebase's own re-proposal flow already exercises after signature timeouts) during a period when the signer's node is momentarily unavailable, and simply retrying is free since the miner is not resource-constrained here.

### Recommendation
Change the `Err(e)` arm at `stacks-signer/src/v0/signer.rs:1449-1456` to fail closed like every other conflict question in this function: refuse to sign (log and `return`) rather than falling through to `mark_locally_accepted`/`create_block_acceptance` when the tenure tip cannot be fetched. If an unconfirmed-node fallback is truly desired for liveness, it should be bounded by staleness of the conflicting signature (as the cross-tenure freshness cutoff already is), not by a single RPC failure.

### Proof of Concept
1. Signer S validates and signs block A (tenure T, height h), reaching the pre-commit threshold via `handle_block_pre_commit`, recording A in `get_signed_conflicts`.
2. Miner proposes conflicting block B, also in tenure T at height h (e.g., a re-proposed tenure-start block, as already exercised by `run_sibling_scenario`/`run_cross_tenure_scenario` in `stacks-signer/src/v0/tests.rs`), and gathers enough pre-commits for B.
3. `handle_block_pre_commit` for B enters the same-tenure conflict branch (line 1432) because A's `consensus_hash` matches B's tenure.
4. At the moment S's node briefly cannot answer `get_tenure_tip` (restart/timeout/network blip), the `Err(e)` arm at line 1449 is hit, logging "Treating the tenure as unconfirmed" and falling through.
5. S proceeds to `mark_locally_accepted`, `create_block_acceptance`, and broadcasts a valid signature over B — a second, conflicting signature in the same tenure at the same height as A, from the same signer. [6](#0-5)

Whenever the node cannot be asked, the conflict keeps blocking: that only delays
the replacement until the signature goes stale, whereas wrongly signing cannot be
taken back. The one recorded exception is a tenure whose reorg we sanctioned
under the reorg-timing rules (section 8): there the node still serves the
conflict as fully live — replacing it is only legitimate because we permitted it
— so no question asked of the node about the _conflict_ could clear it. Instead
the record carries the permitting tenure's sortition, and `reorg_permit_stands`
asks the node whether that sortition is still canonical: while it is, the
conflict is excluded outright; if a burnchain fork orphaned it, the reorg we
sanctioned can no longer happen and the conflict gets its voice back. A false
404 there needs no tip-height guard — it merely restores a conflict, which at
worst delays the replacement. For the own-tenure question below, an unreachable
node is instead treated as unconfirmed and the signature goes out.
