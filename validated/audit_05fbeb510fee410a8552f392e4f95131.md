### Title
Missing audit log entry on job run creation via PipelineRunsController.Create - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` triggers job pipeline runs via `prc.App.RunJobV2` but never calls `prc.App.GetAuditLogger().Audit`, unlike `PipelineRunsController.Resume` which explicitly logs `audit.UnauthedRunResumed` after a successful `ResumeJobV2` call. This creates a detective-control gap: successful job-run triggers leave no audit trail entry.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` (lines 89-128) parses the job ID, verifies the request comes from an authenticated user (`auth.GetAuthenticatedUser(c)`), and calls `prc.App.RunJobV2(ctx, jobID, nil)`. On success it responds with the pipeline run resource via `respondWithPipelineRun` [1](#0-0) . No call to `prc.App.GetAuditLogger().Audit(...)` exists anywhere in this function. By contrast, `Resume` (lines 133-159) calls `prc.App.ResumeJobV2` and then explicitly emits `prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})` before responding [2](#0-1) . This asymmetry means every successful job-run-trigger via `POST /v2/jobs/:ID/runs` (or the equivalent path mounted in `core/web/router.go`) is silently unaudited, while resumed runs are logged. If a low-privileged/low-role authenticated user is able to reach `Create` (e.g., due to any missing or misapplied role check on this route), there is no audit event to detect that abuse after the fact, unlike the resume path.

### Impact Explanation
This is a detective-control gap, not itself an authorization bypass: it does not directly grant unauthorized run-triggering, but it removes the audit trail needed to detect and investigate misuse of the run-trigger endpoint by a low-role user, if such misuse were otherwise possible. This maps to the "insufficient logging/monitoring hindering incident response" category rather than a direct fund-loss or credential-disclosure impact.

### Likelihood Explanation
Any authenticated user (regardless of role) who can successfully POST to the job runs endpoint will trigger this gap deterministically — it requires no special conditions beyond a successful `Create` call, and is fully repeatable, since the audit call is simply absent from the code path.

### Recommendation
Add an audit log call in `PipelineRunsController.Create` after a successful `RunJobV2`, analogous to `Resume`, e.g., `prc.App.GetAuditLogger().Audit(audit.RunTriggered, map[string]any{"jobID": jobID, "runID": jobRunID})`, so that all job-run-triggering actions are consistently logged for later review.

### Proof of Concept
Go handler-level test plan:
1. Set up a test `Application` mock with a fake `AuditLogger` that records all `Audit` calls (many existing tests in `core/web/pipeline_runs_controller_test.go` already use such a fixture).
2. Issue `POST /v2/jobs/:ID/runs` with a valid integer job ID for an authenticated user, mocking `RunJobV2` to succeed and `FindRun` to return a valid pipeline run.
3. Assert HTTP response is `200 OK`.
4. Assert on the fake audit logger that zero `Audit` calls were recorded for this request, in contrast to a parallel test calling `PATCH /v2/jobs/:ID/runs/:runID` (`Resume`) where the fake audit logger records exactly one `Audit` call with `audit.UnauthedRunResumed`.
5. This differential assertion (`0` audit events for `Create` vs. `1` for `Resume`) demonstrates the missing audit coverage described above.
