### Title
Zip-slip in `ExtractZipArchive`/`extractZipFile` allows archive entries to write outside the extraction root - ([File: helpers/archives/zip_extract.go])

### Summary
`extractZipFile`, `extractZipFileEntry`, `extractZipDirectoryEntry`, and `extractZipSymlinkEntry` in `helpers/archives/zip_extract.go` use `file.Name` from the zip archive verbatim, with no containment check against the extraction destination. The only path check performed (`errorIfGitDirectory`) only rejects `.git` entries, not `..` traversal, so a crafted zip entry name such as `../../Users/Public/run.ps1` (or an absolute/rooted path) is passed straight to `os.MkdirAll(filepath.Dir(file.Name), 0o777)`, `os.OpenFile`, `os.Mkdir`, or `os.Symlink`.

### Finding Description
`ExtractZipArchive` (`helpers/archives/zip_extract.go:85-110`) iterates `archive.File` and calls `extractZipFile(file)` for each entry. `extractZipFile` (`zip_extract.go:61-83`) does:
```go
err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
```
and then dispatches to `extractZipFileEntry`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry`, all of which use `file.Name` directly for `os.OpenFile`, `os.Mkdir`, `os.Symlink`, and `os.Remove`. None of these functions resolve `file.Name` relative to a destination directory nor verify the resolved path stays within any root - `filepath.Dir`/`filepath.Clean` do not strip `..` segments, they only normalize them, so `../../Users/Public/run.ps1` remains a valid traversal path.

The only guard present, `errorIfGitDirectory` (`helpers/archives/path_check_helper.go:21-31`), is scoped exclusively to blocking `.git` as the first path component - it does not detect or reject `..` segments, drive-letter/absolute paths, or any other traversal pattern. `newPathErrorTracker` (used via `tracker.actionable`) only suppresses repeated *error* log lines; it performs no path validation and does not fail extraction on out-of-root writes.

After both extraction passes, `lchmod(file.Name, file.Mode())` (`helpers/archives/os_windows.go:9-13` on Windows, `os_unix.go` on Unix) is called with the same unsanitized `file.Name`. If the earlier `os.OpenFile`/`os.Symlink` call succeeded in writing outside the intended root, `lchmod` operates on that same escaped path and succeeds silently (or fails only for unrelated reasons such as permissions), giving no signal that containment was violated.

Whether this manifests as an actual escape from the *intended* extraction root depends entirely on the working directory/consumers that call `ExtractZipFile`/`ExtractZipArchive` (e.g. cache/artifact extractors in `commands/helpers/archive/ziplegacy` and `commands/helpers/archive/fastzip`), which this file itself does not restrict. Since `zip_extract.go` performs no root-containment logic at all, any caller that does not pre-sanitize entry names before invoking this shared helper inherits the zip-slip weakness.

### Impact Explanation
If reachable via an unsanitized caller path (e.g. cache or artifact zip extraction driven by data downloaded for a job/pipeline), a pipeline author who controls the contents of a project artifact or cache archive could craft entries with `..`-traversal names to write or overwrite files outside the job's working directory on the runner host filesystem, including scripts later executed by the shell/PowerShell executor stage. This turns archive extraction into a primitive for writing attacker-chosen file contents to attacker-chosen paths reachable by traversal from the extraction root, which is a file-system integrity violation of the "file operations must stay within intended build/cache/artifact roots" invariant.

### Likelihood Explanation
The `helpers/archives/zip_extract.go` code path itself performs zero root-containment checks for zip entry names besides a narrow `.git` filter, making the underlying primitive unconditionally present, deterministic, and repeatable given any caller that does not pre-sanitize `file.Name`. Whether it is fully exploitable end-to-end depends on the concrete caller (cache/artifact extractors) also lacking sanitization, which could not be fully confirmed from the files in scope for this question (`os_windows.go`/`zip_extract.go`), so the completeness of exploitation (versus root cause) is partially uncertain without inspecting `commands/helpers/archive/ziplegacy` and `fastzip` extractor call sites.

### Recommendation
In `extractZipFile`/`extractZipFileEntry`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry`, resolve `file.Name` against the known destination root with `filepath.Join(root, file.Name)`, then verify via `filepath.Rel` (or an equivalent prefix check on the cleaned absolute path) that the result stays within `root` before performing `MkdirAll`, `OpenFile`, `Mkdir`, or `Symlink`; reject (return an error, not just log a warning) any entry whose resolved path escapes the root, and apply this check symmetrically in `ExtractZipArchive` before the `lchmod` pass as well.

### Proof of Concept
```go
func TestExtractZipArchive_ZipSlip(t *testing.T) {
    root := t.TempDir()
    require.NoError(t, os.Chdir(root))

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    w, err := zw.Create("../../Users/Public/run.ps1")
    require.NoError(t, err)
    _, err = w.Write([]byte("malicious"))
    require.NoError(t, err)
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    err = archives.ExtractZipArchive(zr)
    require.NoError(t, err) // currently returns nil even though file escaped root

    escaped := filepath.Join(filepath.Dir(filepath.Dir(root)), "Users/Public/run.ps1")
    _, statErr := os.Stat(escaped)
    require.NoError(t, statErr, "file should not have been created outside extraction root, but zip-slip succeeded")
}
```
Expected result on the current code: the assertion `require.NoError(t, statErr, ...)` passes, proving the file was written outside `root`, demonstrating the missing containment check; after a fix, `ExtractZipArchive` should return a non-nil error and no file should exist at `escaped`.
