### Title
Unfunded instant-withdraw receipts from earlier epochs evade the default haircut and drain the recovery reserve at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`InstantCreditVault` tracks instant-withdraw receipt basis per epoch (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`), but default accounting only ever looks up the entry for the *current* `epochNumber` — the on-chain analog of CVE-2018-20481's "unallocated entry" dereference: receipts allocated under older epoch keys are treated as absent. `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read `instantWithdrawClaimsByEpoch[epochNumber]`, and `_claimDefaultedInstantWithdrawRequest()` only haircuts `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`. Receipts created in an earlier epoch that were never funded are therefore (a) excluded from the recovery claim basis, and (b) paid 1:1 by `claimInstantWithdrawRequest()` after finalization, consuming reserve that belongs to haircut claimants.

### Finding Description
- `requestInstantWithdraw` records basis under `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, and adds to the global `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). There is no check that prior pending instant requests are funded.
- If `startEpoch` can only partially cover pending instant requests, the CDO sends what it has (`collectInstantWithdrawFunds`) and returns early with `allowInstantWithdraw = false` (IdleCDOEpochVariant.sol:279-290). The unfunded remainder stays in `pendingInstantWithdraws` but its *per-epoch key* stays on the epoch in which it was created, which never changes.
- Later epochs proceed normally; `stopEpoch`/`startEpoch` do not force-fund instant receipts, and a user can keep an unfunded receipt pending for many epochs while `epochNumber` increments (IdleCreditVault.sol:610).
- On default, `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — i.e., the current-epoch bucket — to the haircut basis (IdleCreditVault.sol:644-649), and `_defaultPrefundedInstantReserve()` likewise only counts current-epoch prefunding (IdleCreditVault.sol:716-723). The older-epoch unfunded basis is invisible to `finalizeDefaultRecovery`, so `defaultRecoveryReserve` and `defaultRecoveryPrice` are computed as if those receipts did not exist.
- After `finalizeDefault`, `claimInstantWithdrawRequest` clears only the `defaultRecoveryEpoch` slice at the recovery price (IdleCreditVault.sol:842-856); the residual `instantWithdrawsRequests[user]` — which includes the unfunded earlier-epoch receipt — is then burned and paid in full via `_transferFundedClaim` (IdleCreditVault.sol:387-392), drawing from the strategy's underlying balance, i.e., the same pool backing the recovery reserve.

### Impact Explanation
An unprivileged KYC-passed lender whose instant request stayed unfunded across an epoch boundary receives 100% instead of `defaultRecoveryPrice`, while the recovery basis used to size the reserve never included their claim. The overpayment comes directly out of `defaultRecoveryReserve` / strategy-held underlying, so subsequent claimants (defaulted-epoch withdrawers, post-default requests, other instant claimants) are underpaid or the reserve is exhausted before all claims settle — direct theft from other users proportional to the attacker's unfunded earlier-epoch receipt. This breaks the "one receipt, one haircut" invariant and reserve solvency.

### Likelihood Explanation
Requires: instant withdrawals enabled, an epoch where buffer deposits only partially cover instant requests (so `pendingInstantWithdraws` remains > 0 into later epochs), the manager not calling `getInstantWithdrawFunds`, and a subsequent borrower default — all reachable with honest privileged roles; only the attacker (the receipt holder) is unprivileged. The accounting gap is structural: no code path migrates `instantWithdrawClaimsByEpoch` entries to the current epoch.

### Recommendation
- Track pending instant receipts with an epoch range or fold `pendingInstantWithdraws` into `defaultPendingClaimBasis` directly (the unfunded remainder), rather than only the current-epoch keyed entry.
- In `_claimDefaultedInstantWithdrawRequest`, apply the recovery haircut to *all* instant receipts outstanding at finalization, not only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`; e.g., haircut the full `instantWithdrawsRequests[user]` then separately settle any genuinely pre-funded component.
- Alternatively, record each request's funded/unfunded split at request time so older unfunded receipts are enumerable at finalization.

### Proof of Concept
Foundry fork sketch (revert/assert outline):

```solidity
function testOldUnfundedInstantEvadesHaircut() external {
    // Epoch N buffer: user deposits, requests instant withdraw
    uint256 req = cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant request, epoch N
    // startEpoch N+1 with insufficient buffer deposits -> partially unfunded
    _startEpochAndCheckPrices(1);
    assertGt(strategy.pendingInstantWithdraws(), 0);
    assertFalse(cdoEpoch.allowInstantWithdraw());
    // manager never calls getInstantWithdrawFunds; epochs advance
    _stopEpochAndCheckPrices(1, apr, funds);
    _startEpochAndCheckPrices(2); // still unfunded, epochNumber now > requestEpoch
    // borrower defaults at stopEpoch of current epoch
    _stopEpochDefault(...);
    // finalize with recovery ratio R < 1
    cdoEpoch.finalizeDefault(recovered, manager);
    // attacker claims: defaulted-epoch slice haircut, old unfunded slice paid at par
    uint256 balPre = underlying.balanceOf(user);
    cdoEpoch.claimInstantWithdrawRequest();
    // user received req * 1.0 instead of req * R; reserve shortfall = req * (1 - R)
    assertGt(underlying.balanceOf(user) - balPre, req * R / 1e18);
    // a second claimant's defaulted withdrawal then underflows reserve / reverts
    vm.expectRevert(); // insolvency
    victimCdo.claimWithdrawRequest();
}
```
