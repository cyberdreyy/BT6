### Title
Fee-on-transfer underlying breaks credit-vault receipt accounting: nominal `transferFrom` amounts are recorded/collected instead of actually received amounts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The vault assumes `amount sent == amount received` on every underlying `safeTransferFrom`. `IdleCDO._deposit` itself is safe because it mints tranche shares on the measured balance delta (`_contractTokenBalance(_token) - _preBal`), but the downstream strategy/vault paths in `IdleCreditVault` (`deposit`, `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `finalizeDefaultRecovery`) account and mint against the nominal `_amount`. With a fee-on-transfer (FoT) underlying, every pull settles less than recorded, desynchronizing `pendingWithdraws` / strategy-token supply from real held balance. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Three concrete mismatches exist on the credit-vault surface:

1. `deposit(uint256 _amount)` mints `_amount` strategy tokens to the IdleCDO after `safeTransferFrom(idleCDO, this, _amount)` without measuring the received delta. With a FoT token the vault receives `_amount - fee` but the CDO is credited `_amount` at a hardcoded `price() == oneToken`, inflating `getContractValue()` (strategy tokens are priced 1:1) by the fee amount.

2. `collectWithdrawFunds(uint256 _amount)` clears `pendingWithdraws` by the nominal `_amount` — either fully (`pendingWithdraws = pendingBasis - _amount`) or via the loss-haircut path (`lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`) — then pulls `_amount` but receives less. Funded claims later pay the full computed amounts through `_transferFundedClaim` / `_claimLossAdjustedWithdrawRequest`, so the last claimant's transfer reverts on insufficient balance.

3. Same pattern in `collectInstantWithdrawFunds` (`pendingInstantWithdraws -= _amount` while less was received) and in `finalizeDefaultRecovery` (`defaultRecoveryReserve = _recoveredAmount + ...` while `safeTransferFrom(_recoverySource, this, _recoveredAmount)` delivers less), causing the recovery reserve to be over-recorded and `_transferDefaultRecovery` to underflow/revert for the final claimants.

Phase/mode: applies in running/buffer epochs during `stopEpoch` funding, instant-withdraw funding, and default finalization — any mode (fixed-APR, APR0, instant, prefunded) since all funnel through these pulls. The guards that exist (`_transferFundedClaim`'s reserve check, `lossRecoveryPrice == 0` check, `_onlyIdleCDO`) do not compare sent vs. received, so none of them stop the desync. This is the same bug class as the Teller report: collateral/funds are moved in two hops and the second hop assumes the nominal amount.

### Impact Explanation
Insolvency / permanent freezing of unclaimed claims. The recorded claim basis (`pendingWithdraws`, `instantWithdrawsRequests`, `defaultRecoveryReserve`, CDO strategy-token balance at `price()==1`) exceeds actually held underlying by the cumulative FoT fee. Each claim pays the full recorded amount until the balance is exhausted; the final claimant(s) cannot be paid — their `safeTransfer` reverts or `defaultRecoveryReserve -= _amount` underflows — permanently freezing the shortfall. Loss magnitude ≈ `feeBps * totalFundedAmount / 100%` per funding event; for a 1% FoT token and a 1M USDC-equivalent epoch funding, ~10k units of claims become unbacked.

### Likelihood Explanation
Requires the vault to be deployed with a FoT/rebasing-on-transfer token as `underlyingToken`. Deployed Pareto credit vaults use USDC-class stables, so realized likelihood on current instances is low; however `initialize` accepts any ERC20 (`token = _underlyingToken` with no compatibility check) and nothing prevents deploying such a vault, and the docs-level assumption "any ERC20" mirrors the Teller report's "fee-on-transfer supported" claim. Conditional Medium.

### Recommendation
Measure received amounts at every vault boundary:

- In `deposit`: `uint256 before = underlyingToken.balanceOf(address(this)); underlyingToken.safeTransferFrom(idleCDO, address(this), _amount); _mint(msg.sender, balanceOf - before);`
- In `collectWithdrawFunds` / `collectInstantWithdrawFunds`: compute `received = balanceAfter - balanceBefore` and decrement `pendingWithdraws` / compute `lossRecoveryPriceByEpoch` against `received`, not `_amount`.
- In `finalizeDefaultRecovery`: set the reserve using the received delta of the `_recoverySource` pull.
- Alternatively, explicitly revert in `initialize` for tokens whose `transferFrom` delivers less than requested (e.g., probe or document that only non-FoT stablecoins are supported).

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
