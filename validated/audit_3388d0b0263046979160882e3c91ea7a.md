### Title
Stale-permitted reorg check bypasses `ReorgNotAllowed` re-verification before signing - (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/chainstate/mod.rs`, `stacks-signer/src/chainstate/v1.rs`)

### Summary
`check_parent_tenure_choice` — the check that decides whether a miner's tenure-change block is allowed to reorg a previous tenure — is only invoked at proposal-arrival time (inside `SortitionsView::check_proposal` → `validate_tenure_change_payload`, v1 path). The shared re-verification routine that runs later, at validate-ok and again right before the pre-commit threshold triggers a signature — `check_block_against_signer_db_state` — never calls it again. Because the legality of a reorg depends on mutable, time-sensitive state (`get_globally_accepted_block_count_in_tenure`, `get_burn_block_receive_time`) that can change between proposal arrival and the moment the signature is actually placed, a permit granted on a stale snapshot is never re-checked, and the "permit stands" mechanism only re-validates that the *permitting sortition* is still canonical — not that the underlying reorg-legitimacy conditions still hold.

This check decides a reorg is legitimate if the reorged tenure produced at most one globally-accepted block and that block was proposed close enough to the burn-block transition. When it passes, the reorged tenure is marked superseded so the signer's own prior signature over it stops blocking the replacement: [3](#0-2) 

Crucially, once superseded, the only thing later re-checked is whether the *permitting sortition itself* remains canonical (`reorg_permit_stands`), not whether the original justification (block count / timing) is still accurate: [4](#0-3) 

The function that re-verifies chainstate immediately before a signature is committed — at validate-ok and again at the pre-commit-threshold signing step — is `check_block_against_signer_db_state`. It only re-runs `check_tenure_change_confirms_parent` (parent-height confirmation) and `check_latest_block_in_tenure`; it never calls `check_parent_tenure_choice` again: [5](#0-4) 

This gap is explicitly acknowledged in the project's own documentation as belonging to "the proposal path only," listing the `DuplicateBlockFound` check (which the doc says is covered by a backstop in the pre-commit conflict guard) alongside the v2 wrapper's extra checks — but no equivalent backstop is documented or implemented for v1's `ReorgNotAllowed`/`check_parent_tenure_choice` result once a permit has been recorded: [6](#0-5) 

### Impact Explanation
A miner can time a tenure-change proposal so that, at the moment of proposal arrival, `check_parent_tenure_choice` evaluates the reorged tenure using ephemeral values (`get_globally_accepted_block_count_in_tenure`, `get_burn_block_receive_time`) that momentarily satisfy the "poorly-timed"/"≤1 globally accepted block" leniency rule, granting a reorg permit and marking the older tenure superseded. Between that proposal arrival and the actual moment a signature is placed (which can be delayed through the node-validation round trip and the pre-commit threshold wait), the reorged tenure's true state can settle to something that the rule itself says must NOT be reorged (e.g., it now has 2 globally-accepted blocks). Because `check_block_against_signer_db_state` never re-invokes `check_parent_tenure_choice`, the signer proceeds to sign the tenure-change block anyway, placing a signature over what its own consensus-safety rule has since deemed an illegitimate reorg of an established tenure. This is a signer signing a non-canonical/invalid tenure-change block — a Critical-class safety break.

### Likelihood Explanation
This requires only a single miner (plus normal network propagation delay) to control proposal timing relative to the concurrent formation of global acceptance on the tenure being reorged — no majority of signers or additional keys are needed. The race window is realistic: block validation at the node is asynchronous (`spawn_validation_thread`) and the pre-commit round requires waiting for 70% weight, both of which introduce a real delay between the proposal-time snapshot and the signing-time decision.

### Recommendation
Re-run `check_parent_tenure_choice` (or otherwise re-validate its component conditions — reorged tenure's current globally-accepted block count and proposal timing) inside `check_block_against_signer_db_state`, so the reorg legality determination is confirmed immediately before both validate-ok pre-commit promotion and the final signature, not only at proposal arrival. Alternatively, make the "superseded" permit self-invalidating if the reorged tenure's globally-accepted block count increases after the permit was granted, mirroring how `reorg_permit_stands` already re-checks the permitting sortition's canonicity.

### Proof of Concept
1. Miner submits a tenure-change block `B` for tenure `T2` whose parent choice reorgs tenure `T1`.
2. At the exact moment the signer processes the proposal, `T1` has 0 or 1 globally-accepted blocks and its first block's `approved_time` is within `first_proposal_burn_block_timing` of the sortition transition timestamp → `check_parent_tenure_choice` returns `true`, and `T1` is recorded as superseded (`stacks-signer/src/chainstate/mod.rs:290-295`).
3. `B` is submitted to the node for validation (async, `spawn_validation_thread`).
4. While validation is in flight, `T1`'s pending block finishes reaching global acceptance from the rest of the signer set, so `get_globally_accepted_block_count_in_tenure(T1)` would now return `2` — a value that, per the rule, should refuse the reorg.
5. Validate-ok returns for `B`; `check_block_against_signer_db_state` runs but only checks `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure`, not `check_parent_tenure_choice` (`stacks-signer/src/v0/signer.rs:1803-1841`). `B` is pre-committed.
6. Pre-commit threshold is reached; `check_block_against_signer_db_state` runs again with the same gap; the signer signs `B`, having placed a signature over a tenure-change that reorgs an established two-block tenure — precisely the scenario `check_parent_tenure_choice`'s `globally_accepted_blocks > 1` guard exists to prevent.

```rust
    pub fn check_parent_tenure_choice(
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,
            "sortition_state.prior_sortition" => %self.prior_sortition,
            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

        let tenures_reorged =
            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
        if tenures_reorged.is_empty() {
            warn!("Miner is not building off of most recent tenure, but stacks node was unable to return information about the relevant sortitions. Marking miner invalid.");
            return Ok(false);
        }

        // this value *should* always be some, but try to do the best we can if it isn't
        let sortition_state_received_time =
            signer_db.get_burn_block_receive_time(&self.burn_block_hash)?;

        // Track which tenures are superseded by the reorg, then mark them in
        // the DB after the reorg is permitted.
        let mut superseded_tenures = Vec::new();
        for tenure in tenures_reorged.iter() {
            if tenure.consensus_hash == self.parent_tenure_id {
                // this was a built-upon tenure, no need to check this tenure as part of the reorg.
                continue;
            }

            // disallow reorg if more than one block has already been signed
            let globally_accepted_blocks =
                signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
            if globally_accepted_blocks > 1 {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already more than one globally accepted block.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => ?tenure.first_block_mined,
                    "globally_accepted_blocks" => globally_accepted_blocks,
                );
                return Ok(false);
            }
```

```markdown
One decision does have to be recorded, because it is ours rather than the
node's. When a miner builds off something other than the prior sortition,
`check_parent_tenure_choice` decides whether the reorg is allowed: it is, if
every tenure being reorged has at most one globally accepted block and produced
its first block too close to the next sortition to count
(`first_proposal_burn_block_timing`). Having sanctioned that replacement, the
signer records those tenures as **superseded** (`mark_tenure_superseded`), so its
own signature over what they built does not then block the replacement it just
permitted — the node cannot answer this one at signing time, since it still
serves the reorged tenure as fully live until the replacement lands. What _is_
still derived from the node is the permit's own validity: the record carries the
permitting tenure's sortition, and it only excludes conflicts while that
sortition remains canonical (section 5, `reorg_permit_stands`), so a burnchain
fork that orphans the permitting tenure automatically voids the permit. A record
more than `MAX_FORK_DEPTH` (100) burn blocks below the tip is dropped; a fork
that deep would cause far bigger problems than a stale conflict.
```

```rust
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,

                self.proposal_config.reorg_attempts_activity_timeout,
```
