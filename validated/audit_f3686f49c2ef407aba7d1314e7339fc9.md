## Title
Node-side signature aggregation retains a stale `Accepted` signature and drops a subsequent `Rejected` from the same signer — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

## Summary
`StackerDBListener`'s event handler tracks per-signer responses to a block proposal using two data structures: `gathered_signatures` (accept signatures, keyed by `slot_id`) and `responded_signers` (a `HashSet<slot_id>` meant to dedup any single signer's vote). The `Accepted` branch unconditionally inserts the signer's `slot_id` into `responded_signers` after recording weight, while the `Rejected` branch only counts a rejection if `responded_signers.insert(slot_id)` returns `true` (i.e., first response wins). Because both branches share the same `responded_signers` set but the `Accepted` branch's weight-gating check uses a *different* set (`gathered_signatures`), a single signer who sends `Accepted` first and later sends `Rejected` for the identical block has their rejection silently discarded: the `Rejected` branch's `insert` returns `false` (slot already present from the `Accepted` insert), so `total_weight_rejected` is never incremented, `responded_signers`/`gathered_signatures` are never cleared, and the stale signature stays in `gathered_signatures`.

## Finding Description
In `stackerdb_listener.rs`'s `BlockResponse::Accepted` arm [1](#0-0) , weight is only added the first time `slot_id` appears in `gathered_signatures`, but `responded_signers.insert(slot_id)` is called unconditionally on every accepted message, regardless of whether it was already present.

In the `BlockResponse::Rejected` arm [2](#0-1) , the entire weight-accounting/logging block is gated behind `if block.responded_signers.insert(slot_id)`. Since the `Accepted` handler already inserted that same `slot_id` into `responded_signers`, this `insert` call returns `false` for a signer who accepted earlier, and the rejection is dropped entirely — no weight change, no signature/slot removal, no state correction.

The consequence: `block.gathered_signatures` (used verbatim by `SignCoordinator::wait_for_signatures` to build the final quorum signature set, [3](#0-2) ) and `block.total_weight_approved` retain the now-withdrawn signer's stale acceptance. This breaks the equality that the aggregated "verified accepts" weight should equal the weight of signers who *currently* consider the block valid; instead it is the weight of signers who *ever* sent an accept, even after that signer flagged the same block as invalid/conflicting via a subsequent `Rejected` message.

This matches the "rejection recounted as an accept" class of bug described in the task rules: an explicit reconsideration/withdrawal by a signer is discarded by the aggregation logic on the node side, and the block can still cross the 70% signature threshold and be pushed with a stale accept signature that the signer itself has since disavowed.

Note: I was not able to fully confirm, within the available tool budget, a concrete in-repo trigger where the *signer's own* logic (`stacks-signer/src/v0/signer.rs`) re-emits a `Rejected` `BlockResponse` for the exact same `signer_signature_hash` after it has already broadcast `Accepted` for that hash. `BlockInfo::check_state` in `signerdb.rs` does permit a `LocallyAccepted -> LocallyRejected` transition [4](#0-3) , which suggests the local state machine is designed to allow this reconsideration in principle, but I did not trace every call path that could produce a second, distinct network message for the same hash. This should be verified with a live/instrumented signer before treating this as a fully proven end-to-end exploit.

## Impact Explanation
If exploitable, this is a **Critical** impact per the task's rubric ("a rejection recounted as an accept"): the block-producing coordinator (`signer_coordinator.rs`) could gather and push a block using a stale, withdrawn signature from a signer who has since determined the block is invalid or conflicting, potentially causing the node to accept/broadcast a block that should have been blocked. At minimum it is a safety-equality break between "weight actually still endorsing this block" and "weight counted by the coordinator."

## Likelihood Explanation
Reachable by a single signer's own two consecutive StackerDB messages (`Accepted` then `Rejected` for the same `signer_signature_hash`), requiring no majority, no other signer's key, and no auth token — satisfying the in-scope trigger constraints. The main open question is how easily/legitimately the signer software itself produces this second message for an identical hash versus only ever producing at most one verdict per hash (in which case the listener-side bug would be latent/unreachable via the reference signer implementation, though still reachable by any custom/misbehaving signer client sending two legitimate-looking, correctly-signed messages).

## Recommendation
Make `Accepted`/`Rejected` handling mutually consistent and revocable-or-final in a way that matches intended semantics:
- Either treat a signer's vote as final once first recorded (which requires the `Accepted` branch to also check `responded_signers` for prior state before accepting, and vice versa, so that a "flip" can't silently retain the old vote weight while dropping the new one), or
- Explicitly support vote revision: when a `Rejected` arrives for a slot already in `gathered_signatures`, remove the entry from `gathered_signatures`, subtract the weight from `total_weight_approved`, and then apply the rejection weight/logic — and symmetrically for `Accepted` arriving after a prior `Rejected`.
Add a test that sends `Accepted` then `Rejected` (and the reverse order) for the same `signer_signature_hash`/slot and asserts that `total_weight_approved`, `total_weight_rejected`, and `gathered_signatures` reflect only the signer's most recent vote.

## Proof of Concept
1. A signer (slot `S`, weight `W`) sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for block hash `H`. `stackerdb_listener.rs` adds `W` to `total_weight_approved`, inserts `S` into `gathered_signatures` and `responded_signers`.
2. The same signer subsequently sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for the same `H` (e.g., because it detects the block is now stale/conflicting/invalid per its own chainstate recheck).
3. In the `Rejected` arm, `block.responded_signers.insert(S)` returns `false` (already present), so the whole rejection-accounting block is skipped: `total_weight_rejected` is unchanged, and `gathered_signatures` still contains `S`'s stale accept signature.
4. If `total_weight_approved` (still including `S`'s stale weight) reaches `weight_threshold`, `SignCoordinator::wait_for_signatures` [3](#0-2)  returns `Ok` with `gathered_signatures.values()`, which still includes `S`'s withdrawn signature, and the block is pushed as fully signed.
