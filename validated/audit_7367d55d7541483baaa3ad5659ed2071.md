### Title
Stale rejection weight is never retracted when a signer flips to acceptance for the same block, causing the mining coordinator to miscount votes and falsely conclude `SignersRejected` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The bug reported in the analog (vault weight not decremented per-synth on withdrawal, so a shared counter becomes stale/wrong) maps to `StackerDBListener`'s in-memory tally of `BlockStatus.total_weight_approved` / `total_weight_rejected`. When a signer first rejects a block and later re-evaluates and accepts the very same block (a documented, legitimate transition in the v0 signer state machine), the coordinator adds the signer's weight to `total_weight_approved` but never subtracts it from `total_weight_rejected`. The signer's weight is thus counted in both buckets simultaneously, corrupting the tally used to decide whether the block is signed or globally rejected.

### Finding Description
`BlockStatus` tracks, per `signer_signature_hash`, a `responded_signers: HashSet<u32>` (any response), a `gathered_signatures: BTreeMap<u32, MessageSignature>` (accept responses only), `total_weight_approved`, and `total_weight_rejected`.

On `BlockResponse::Accepted`, the guard that prevents double-counting only checks whether the slot already appears in `gathered_signatures`: [1](#0-0) 

On `BlockResponse::Rejected`, the guard uses the shared `responded_signers` set: [2](#0-1) 

Because the two branches use different guards, a signer that rejects first (recorded only in `responded_signers`, not in `gathered_signatures`) and later accepts the same block passes the accept guard (`gathered_signatures` does not yet contain its slot), so its weight is added to `total_weight_approved` while the weight it already contributed to `total_weight_rejected` is never removed. `total_weight_approved + total_weight_rejected` can therefore exceed the sum of the real, current per-signer votes, with the excess coming from a single signer's stale, superseded rejection.

This is architecturally the same class of bug as the referenced report: a shared/aggregate accounting value ("vault weight" there, "vote weight totals" here) is updated additively on one state transition without being retracted on the corresponding reverse transition, so a party's true current contribution is misrepresented in the aggregate. Notably, the DB-backed signer-side logic in `stacks-signer/src/v0/signer.rs` and `signerdb.rs` gets this right — `add_block_signature` explicitly deletes any prior rejection row for that signer/block, and `add_block_rejection_signer_addr` refuses to overwrite an existing signature: [3](#0-2) [4](#0-3) 
but the node-side mining coordinator's separate, independent tally in `stackerdb_listener.rs` has no equivalent reconciliation.

A signer flipping from reject to accept on the identical block is not a theoretical/attacker-only scenario — it is a documented part of the normal v0 signer lifecycle (`LocallyRejected --> LocallyAccepted : re-evaluated`), e.g. when a signer initially refuses to sign because a rival conflicting block is still live, then later signs once that rival goes stale: [5](#0-4) [6](#0-5) 

### Impact Explanation
The miner's block-status loop uses these totals directly to decide the fate of a proposed block: [7](#0-6) 
Because a signer's stale rejection weight is never retracted, it can combine with genuinely rejecting signers' weight to cross the blocking-minority threshold (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`) even though the real, current set of rejecting signers does not actually reach 30%+ of weight. This causes the miner to spuriously treat a legitimately signable block as `SignersRejected`, discarding it and excluding/penalizing transactions unnecessarily, and forcing the miner to rebuild and re-propose — a liveness degradation of block production driven purely by an accounting defect, not by any real lack of signer support. It requires only a single signer (a one-slot participant) re-evaluating its own vote plus ordinary gossip of the two responses; no majority collusion or key compromise is needed.

### Likelihood Explanation
Re-evaluation from `LocallyRejected` to `LocallyAccepted` for the same block hash is an intended, everyday code path in the v0 signer (e.g. resolving a transient conflict/duplicate rejection once the conflicting sibling becomes stale), not an edge case requiring adversarial behavior. Any signer that legitimately changes its answer during the lifetime of a still-undecided block proposal triggers the miscount.

### Recommendation
Make the two branches in `stackerdb_listener.rs` share one source of truth for "this signer's current vote," and reconcile the totals on transition instead of only adding:
- Track the signer's last known verdict (accept/reject) per slot.
- On `Accepted`, if the slot was previously counted in `total_weight_rejected`, subtract that weight before adding it to `total_weight_approved` (and vice versa for `Rejected`), mirroring the retract-then-record behavior already implemented in `stacks-signer/src/signerdb.rs`'s `add_block_signature`/`add_block_rejection_signer_addr`.

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListenerComms::insert_block` creates a fresh `BlockStatus` with all zero totals.
2. Signer `C` (weight `w_C`) rejects `B` (e.g. because a rival block is still live) → `total_weight_rejected = w_C`, `responded_signers = {C}`.
3. The rival block later goes stale; `C` re-evaluates per the documented flow and now signs/accepts `B`, broadcasting `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. In the `Accepted` handler, `block.gathered_signatures.contains_key(&C)` is `false` (C never accepted before), so `total_weight_approved += w_C`. `total_weight_rejected` is left unchanged at `w_C`.
5. Signer `D` (weight `w_D`) genuinely rejects `B`, such that `w_D` alone is below the blocking minority but `w_C + w_D` is not: `total_weight_rejected = w_C + w_D`, satisfying `total_weight_rejected + weight_threshold > total_weight` in `get_block_status`.
6. The coordinator returns `NakamotoNodeError::SignersRejected`, discarding a block that the real, currently-outstanding rejection weight (`w_D` alone) would not have blocked, purely due to `C`'s stale, superseded rejection weight never being retracted.

    pub fn add_block_signature(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        signer_addr: &StacksAddress,
        signature: &MessageSignature,
    ) -> Result<bool, DBError> {
        // Remove any block rejection entry for this signer and block hash
        let del_qry = "DELETE FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2";
        let del_args = params![block_sighash, signer_addr.to_string()];
        self.db.execute(del_qry, del_args)?;

        // Insert the block signature
        let qry = "INSERT OR IGNORE INTO block_signatures (signer_signature_hash, signer_addr, signature) VALUES (?1, ?2, ?3);";
        let args = params![
            block_sighash,
            signer_addr.to_string(),
            serde_json::to_string(signature).map_err(DBError::SerializationError)?
        ];
        let rows_added = self.db.execute(qry, args)?;

        let is_new_signature = rows_added > 0;
        if is_new_signature {
            debug!("Added block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        } else {
            debug!("Duplicate block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        }
        Ok(is_new_signature)
    }
