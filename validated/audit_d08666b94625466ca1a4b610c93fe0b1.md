### Title
Self-activity dilution: a stalling miner can perpetually reset `last_activity_time` on its own tenure via repeated low/duplicate block proposals, wedging the `block_proposal_timeout` inactivity fallback - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` treats any incoming block proposal that fails to exceed the highest known chain length in a tenure as "activity" for that tenure and bumps `last_activity_time` in the signer DB, as long as the last known block for that tenure has not reached `signed_group` (global acceptance). This mirrors the `notifyRewardAmount(0)` pattern from the external report: a cheap, no-progress message (a non-advancing/duplicate block proposal) repeatedly resets a timer that gates a safety fallback (`SortitionState::is_timed_out` / `block_proposal_timeout`), letting a single miner drag out its own inactivity window indefinitely instead of the timer ever expiring.

### Finding Description
`check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-418`) is invoked to validate that a proposed block is higher than the highest known block in a reference tenure. When the proposal does *not* exceed the known tip: [1](#0-0) 

it calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` whenever `info.signed_group.is_none_or(...)` — i.e. whenever the last known block of the tenure has **not yet reached global acceptance** (`signed_group == None`), the "activity" bump has **no time bound at all** (the `reorg_attempts_activity_timeout` gate only applies once `signed_group` is `Some`).

This `last_activity_time` is precisely the value consumed by `SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs:55-94`): [2](#0-1) 

`is_timed_out` computes `elapsed = now - last_activity` and only marks the current sortition's miner `InvalidatedBeforeFirstBlock` (via `check_proposal`, `stacks-signer/src/chainstate/v1.rs:144-163`) once `elapsed > block_proposal_timeout`. `InvalidatedBeforeFirstBlock` is the gate that lets the *previous* miner take over via tenure-extend (per `docs/signing.md` and the miner/signer coordination config comments).

Because the bump keyed on `block.header.consensus_hash` (the tenure being proposed into, i.e. the current miner's own tenure) has no expiry while `signed_group` is `None`, a miner that is capable of submitting block proposals (a one-slot actor — it only needs its own mining key, no other signer's key or majority) can keep submitting a proposal with `chain_length <= info.block.header.chain_length` (e.g., re-proposing the same or an older block, or a competing sibling at the same/lower height) each time before `block_proposal_timeout` elapses. Each such proposal resets `last_activity_time` to "now," so `elapsed` never grows past `block_proposal_timeout`, and the `is_timed_out` check in `check_proposal` never fires — exactly analogous to `notifyRewardAmount(0)` continually pushing `periodFinish` forward and never letting the reward-drought condition mature.

### Impact Explanation
This breaks the liveness/safety equality the state machine relies on: "if the current miner stops producing a valid, tip-advancing block within `block_proposal_timeout`, mark it invalid so the network can fall back to the prior miner." A miner that never actually advances the chain but keeps emitting cheap, rejected/duplicate proposals can indefinitely suppress that fallback, wedging the signer set into perpetually waiting on a miner that will never produce a valid block — a High-severity liveness wedge per the task's rubric ("a signer wedged into never signing valid blocks ... or acting on a stale ... threshold"). No majority of signers or other signer's key is required; only the current tenure's miner needs to keep sending block proposals, which is well within a single actor's unilateral capability.

### Likelihood Explanation
The precondition (`info.signed_group == None`, i.e., the tenure's last known block has not been globally accepted) is not exotic — it occurs naturally any time the network hasn't yet reached the 70% signature threshold on the tenure's latest block (slow signers, temporary partition, or simply because the malicious miner is also holding back cooperation on that front). Sending repeated low/duplicate proposals is a trivial, cheap, and fully miner-controlled action requiring no cooperation from other parties, making this readily triggerable by a single misbehaving miner.

### Recommendation
Bound the "activity" credit here the same way it is bounded once `signed_group` is `Some`: cap the total time that a `None`-`signed_group` tenure can keep generating fresh activity bumps (e.g., anchor the freshness window to when the tenure/sortition was first observed, not to "now" on every duplicate proposal), so that repeated non-advancing proposals cannot indefinitely extend `last_activity_time` and mask genuine miner inactivity from the `block_proposal_timeout` check.

### Proof of Concept
1. Miner M wins a sortition and is the current tenure's miner in the signer's `SortitionsView`.
2. M proposes an initial block B0 that gets only locally accepted/pre-committed by signers but never crosses the global-acceptance (`signed_group`) threshold (e.g., because M partially withholds proposals to some signers, or the network is briefly split).
3. Before `block_proposal_timeout` elapses, M submits another proposal B1 whose `chain_length <= B0.chain_length` (a duplicate, stale, or sibling block).
4. `check_latest_block_in_tenure` sees `chain_length` not higher than the known tip, sees `info.signed_group.is_none()==true`, and unconditionally calls `update_last_activity_time(M's consensus_hash, now)` — regardless of how long ago the tenure started.
5. Repeat step 3 every `< block_proposal_timeout` interval, forever. `SortitionState::is_timed_out` (`elapsed = now - last_activity`) never exceeds `block_proposal_timeout`, so `check_proposal` never demotes M to `InvalidatedBeforeFirstBlock`.
6. Result: signers never fall back to the prior miner via tenure-extend, and M can stall block production indefinitely while incurring only the cost of submitting cheap, non-advancing block proposals — the direct analog of `notifyRewardAmount(0)` perpetually diluting/dragging out `periodFinish`.
