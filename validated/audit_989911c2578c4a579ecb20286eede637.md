## Finding

Based on my review of `stacks-signer/src/chainstate/v1.rs`, I found an analog to the Hats "linked tophat eligibility can never be revoked" bug: a designed-but-unenforced distinction between two invalidation states lets a currently-valid, already-signed tenure become permanently unsignable, wedging the signer.

### Title
Sticky mislabeling of `SortitionMinerStatus` locks out a legitimately-signed tenure - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionMinerStatus` deliberately distinguishes a miner invalidated *before* the signer placed any signature in its tenure (`InvalidatedBeforeFirstBlock`) from one invalidated *after* (`InvalidatedAfterFirstBlock`), because only the former is safe to treat as fully dead and fall back away from [1](#0-0) . In practice, `InvalidatedAfterFirstBlock` is never assigned anywhere in the codebase (confirmed by search); every invalidation path writes `InvalidatedBeforeFirstBlock`, regardless of whether a block was already signed in that tenure.

### Finding Description
In `check_proposal`, the timeout-based invalidation branch correctly guards against mislabeling an already-signed tenure, because `SortitionState::is_timed_out` explicitly returns `false` early when `db.has_signed_block_in_tenure(sortition)` is true [2](#0-1) .

However, the second invalidation branch — which re-evaluates whether the current sortition's parent-tenure choice is still valid against the canonical tip — carries no such guard: [3](#0-2) 

This branch runs on *every* `check_proposal` call whenever the canonical tip no longer matches the current sortition's consensus hash or its parent-tenure id, and unconditionally sets `self.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock`, even if the signer already signed one or more blocks in that tenure earlier (e.g., a first block was accepted while the tip still matched, then a later burn/tenure event changes what the signer's view of the canonical tip is).

Once `miner_status` is anything other than `Valid`, the `ProposedBy::CurrentSortition` branch permanently rejects *every subsequent proposal in that same tenure* as `InvalidMiner`: [4](#0-3) 

There is no code path that ever restores `miner_status` back to `Valid` for `cur_sortition` within the same `SortitionsView` (only `reset_view`/`fetch_view`, triggered by an unrelated consensus-hash mismatch, replaces the whole view) [5](#0-4) . The tenure the signer already legitimately signed into is thus permanently — for the lifetime of that cached `SortitionsView` — treated as if the miner had never produced a valid first block, exactly mirroring the Hats bug pattern: a state meant to be revocable/one-directional-only under specific conditions instead gets stuck in the wrong bucket forever because the finer-grained state (`InvalidatedAfterFirstBlock`) that should have been used is dead code.

Compounding this, the fallback branch for accepting blocks from the *prior* sortition's miner only checks for the coarse `InvalidatedBeforeFirstBlock` value: [6](#0-5) 

Since `InvalidatedAfterFirstBlock` is never produced, this check cannot distinguish "invalidated pre-signature" (safe to fall back) from "invalidated post-signature" (unsafe — the current tenure's block is already signed and any competing block from the prior miner at that height is a genuine conflict). This weakens the intended safety boundary: the code's own comment says the fallback "should only consider blocks from last sortition winner if the new sortition was invalidated before we signed their first block," but the implementation cannot actually verify that condition.

### Impact Explanation
This is a High-severity liveness issue matching the accepted impact class "a signer wedged into never signing valid blocks." A tenure that the signer already validated and signed into can become permanently rejected by that signer for the remainder of its `SortitionsView` lifetime, purely because of a transient canonical-tip view change (e.g., a competing burn-chain fork that is later resolved back in the original tenure's favor). Any subsequent, genuinely valid block proposal within that tenure is rejected as `InvalidMiner`, forcing the signer to fall through to `check_pending_block_validations`/timeout logic and potentially stall or diverge from other signers who did not observe the same transient tip.

Secondarily, because the mislabeling also feeds the `ProposedBy::LastSortition` fallback check, it weakens (though does not by itself defeat, since `get_signed_conflicts` provides a downstream backstop per `docs/signer-flows.md` section 5) the safety boundary meant to prevent accepting a competing block from the previous miner once the signer has already committed to the current tenure.

### Likelihood Explanation
Any single miner/sortition participant can trigger the underlying condition through ordinary (or lightly adversarial) burn-chain activity — no majority of signers, no other signer's key, and no privileged access is required: the signer's own `check_parent_tenure_choice` re-evaluation against a shifting canonical tip is enough. This is purely local signer-side logic reachable via normal gossip/block-proposal traffic, matching the "one-slot miner (plus gossip) can trigger" scope.

### Recommendation
Restore the intended semantics: before setting `SortitionMinerStatus::InvalidatedBeforeFirstBlock` in the parent-tenure-choice branch (`stacks-signer/src/chainstate/v1.rs:187-201`), check `signer_db.has_signed_block_in_tenure(&self.cur_sortition.data.consensus_hash)`; if true, set `SortitionMinerStatus::InvalidatedAfterFirstBlock` instead (mirroring the guard already present in `SortitionState::is_timed_out`). Then update the `ProposedBy::CurrentSortition` and `ProposedBy::LastSortition` match arms to treat `InvalidatedAfterFirstBlock` distinctly — e.g., still allow the current tenure's own subsequent blocks (since the signer already committed to it) while continuing to refuse fallback to the prior sortition's miner.

### Proof of Concept
1. Signer receives sortition S for tenure T, with tip currently matching T; `check_proposal` signs block A in T (`cur_sortition.miner_status == Valid`).
2. A subsequent burn event causes `signer_db.get_canonical_tip()` to return a tip whose consensus hash and parent-tenure id no longer match `self.cur_sortition.data` (e.g., a transient fork), per `stacks-signer/src/chainstate/v1.rs:164-179`.
3. `check_parent_tenure_choice` evaluates to invalid for this transient state, setting `cur_sortition.miner_status = InvalidatedBeforeFirstBlock` (`stacks-signer/src/chainstate/v1.rs:193-194`) — despite block A already being signed in T.
4. The fork resolves back in favor of T (canonical tip realigns), and the miner proposes block B, a legitimate continuation of T.
5. `check_proposal` reaches `ProposedBy::CurrentSortition` and rejects B with `RejectReason::InvalidMiner` (`stacks-signer/src/chainstate/v1.rs:289-299`), because `miner_status` is stuck at `InvalidatedBeforeFirstBlock` and nothing in the `SortitionsView` lifecycle resets it back to `Valid` for the same sortition.

    /// Fetch a new view of the recent sortitions
    pub fn fetch_view(
        config: ProposalEvalConfig,
        client: &StacksClient,
    ) -> Result<Self, ClientError> {
        let CurrentAndLastSortition {
            current_sortition,
            last_sortition,
        } = client.get_current_and_last_sortition()?;

        let cur_sortition = SortitionState::try_from(current_sortition)?;
        let last_sortition = last_sortition
            .map(SortitionState::try_from)
            .transpose()
            .ok()
            .flatten();

        Ok(Self {
            cur_sortition,
            last_sortition,
            config,
        })
    }

    /// Reset the view to the current sortition and last sortition
