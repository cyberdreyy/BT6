### Title
Duplicate tenure-change guard in v1 chainstate only checks globally-accepted blocks, missing locally-signed ones - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` guards against double-signing a second tenure-change block for the same tenure by calling `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`. This only detects blocks that have reached network-wide global acceptance, not blocks the signer itself has already locally accepted/signed, allowing the signer to sign two competing tenure-change blocks for the same tenure before global acceptance is reached.

### Finding Description
The intended equality is "at most one block signed per tenure at the tenure-change boundary." The v1 code at [1](#0-0)  queries `get_last_globally_accepted_block`, which per `signerdb.rs` only returns blocks in `BlockState::GloballyAccepted`. A block the signer has locally signed but that has not yet reached the network-wide global-acceptance threshold (state `Signed`/`LocallyAccepted`) is invisible to this check, so `last_in_current_tenure` is `None` and the duplicate check passes.

The equivalent v2 function was patched to close exactly this gap: [2](#0-1)  now uses `get_last_signed_block`, and the comment explicitly states "Only blocks we have signed (locally or globally accepted) count here." A regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs` was added specifically to demonstrate that using `get_last_globally_accepted_block` incorrectly allows a duplicate tenure change when a locally-accepted block exists. [3](#0-2) 

The v1 path was never updated with this fix, and it is still reachable: `check_proposal` in v1 calls `validate_tenure_change_payload` directly for any block containing a tenure-change payload [4](#0-3) . `SortitionState::new`/`SortitionStateVersion::from_protocol_version` in `stacks-signer/src/chainstate/mod.rs` selects the V1 path whenever the active protocol/signer-set version is below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` [5](#0-4) , so the vulnerable code remains live for any deployment running the v1 (pre-global-state) signer protocol.

Attacker flow: win a single miner slot, propose a tenure-change block A for tenure T; get it locally accepted/signed by the target signer (state `Signed`, not yet `GloballyAccepted`); before the network reaches the global-acceptance threshold, propose a second, different tenure-change block B for the same tenure T (same `tenure_consensus_hash`) to the same signer. The duplicate check in `validate_tenure_change_payload` misses A (since it's not globally accepted) and B is evaluated as if no block had been signed in T yet.

### Impact Explanation
This breaks the uniqueness/equivocation guard that is supposed to ensure each signer commits at most one signature per tenure at the tenure-change boundary. If the signer proceeds to sign B in addition to A, the signer has now signed two conflicting blocks for the same tenure — this is a chain-safety-adjacent equivocation from an individual signer's perspective, matching the "losing the equivocation guard" / liveness-wedge category in the affected v1 code path. It is repeatable each time a v1-protocol signer processes a tenure change during the pre-global-acceptance window.

### Likelihood Explanation
Requires only: (1) the target signer running the v1 chainstate protocol path (determined by `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`/signer-set configuration, not attacker-controlled), (2) winning one miner slot to produce competing tenure-change block proposals, and (3) racing the second proposal in before block A's signatures cross the global-acceptance weight threshold. No majority of signers, no compromised keys, and no local access are needed — only one miner slot plus StackerDB gossip of the second proposal, consistent with the allowed attacker model.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to call `signer_db.get_last_signed_block` instead of `get_last_globally_accepted_block`, mirroring the fix already applied in `v2.rs`, so any block the signer has locally or globally signed in the tenure is treated as a conflict for a competing tenure-change proposal.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/v1.rs` (mirroring the existing v2 regression test `check_tenure_change_rejects_when_locally_accepted_block_exists`):
1. Set up a v1 `SortitionsView`/`SortitionState::V1` test environment analogous to `setup_test_environment` used in v2 tests.
2. Insert a `BlockInfo` for tenure T, call `mark_locally_accepted`/mark as `Signed` (not globally accepted), and `signer_db.insert_block`.
3. Build a second, distinct tenure-change block proposal B for the same `consensus_hash`/tenure T (different transactions/parent block id from the first).
4. Call `sortitions_view.check_proposal(...)` (v1 path) with block B.
5. Assert the result is `Err(RejectReason::DuplicateBlockFound)` — with the current code, this assertion fails (result is `Ok(())`), proving the bug; after applying the recommended fix (switching to `get_last_signed_block`), the assertion passes.
