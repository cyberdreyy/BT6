### Title
Signer's equivocation guard (`get_signed_conflicts`) is fully reset on local-DB loss/restart, allowing a double-sign on a conflicting sibling block - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The Keycloak advisory describes a server restart resetting an internal timing mechanism, which lets a previously-revoked refresh token be replayed. The structural analog here is the signer's double-sign/equivocation guard: it depends entirely on the *local* SQLite `SignerDb` (`signed_self`/`signed_group`/`approved_time` rows queried via `get_signed_conflicts`), which is not restored by anything on signer restart other than the miner-viewpoint `StateMachineUpdate` messages replayed from StackerDB. If the local `signer_db` file is lost or replaced (crash-restart onto a fresh volume, disk failure, manual recovery), the pre-commit conflict check re-derives an *empty* conflict set, so the signer will accept and sign a proposal it already signed once, on a conflicting sibling block at the same height — the exact "revoked-thing gets replayed because the timing/tracking state was reset by restart" bug class.

### Finding Description
`Signer::new()` `stacks-signer/src/v0/signer.rs:210-325` is the only place that repopulates in-memory/db state on startup. It rehydrates `state_machine_updates` from the latest StackerDB chunks (lines 228-271) and opens a fresh/possibly-empty `SignerDb` at `signer_config.db_path` (line 219-220). Nothing in this path reconstructs prior block signatures, `signed_self`/`signed_group`/`approved_time` rows, or previously-observed rejections/pre-commits from StackerDB (`BlockResponse`/`BlockPreCommit` history) — only `StateMachineUpdate` is replayed.

The signer's sole defense against putting a second signature over a conflicting sibling block at (or above) the same height is the pre-commit-threshold check in `handle_block_pre_commit`: [1](#0-0) 
This calls `SignerDb::get_signed_conflicts(chain_length, &block_hash)`, which queries the local `blocks` table for any block previously marked `signed_self`/`signed_group` at or above that height: [2](#0-1) 

`has_signed_block_in_tenure` (used to keep a tenure from timing out) and the whole pin described in `docs/signer-flows.md` §8 are explicitly noted as being "recorded" only in the signer's own persisted state, with rejection/staleness rules layered on top: [3](#0-2) 

None of this is a per-block network fact; it is purely local bookkeeping that only survives as long as the SQLite file does. `Signer::new()` opens this DB unconditionally without any check that it actually contains prior history, and does not attempt to reconstruct it from any gossip channel: [4](#0-3) 

Compare this with the miner-viewpoint state, which the code explicitly engineers to survive DB loss by replaying `StateMachineUpdate` chunks from StackerDB on startup — precisely so a signer that lost its local DB "can immediately start participating in signing" (the documented rationale, and the covered scenario in `signer_loads_stackerdb_updates_on_startup`): [5](#0-4) 
That test only proves the miner-view/state-machine path is durable across DB loss; it never asserts anything about the *conflict/equivocation* guard, because there is no equivalent recovery path for signed-block history.

### Impact Explanation
Before the DB loss: signer S has signed block A at height H (row with `signed_self` present). A conflicting sibling block A' is proposed by a one-slot miner at the same height H (e.g., a re-org attempt, or the same miner re-proposing under a different tenure). `get_signed_conflicts(H, hash(A'))` returns A as a live, fresh conflict, and `conflict_still_blocks` keeps S from signing A' (per the documented guard in `docs/signer-flows.md` §5 and `handle_block_pre_commit`).

After a restart in which the local `signer_db` file was lost/reset (while the miner-view `StateMachineUpdate` state is faithfully restored from StackerDB, giving the operator/attacker no visible indication anything is wrong): `get_signed_conflicts` now returns an empty vec — S has no record it ever signed A. The miner (or gossip) simply re-sends/re-proposes A' (a block conflicting with the already-signed A, at the same height); S will pre-commit and sign it, producing a bearer-instrument signature over two conflicting blocks at the same height from the same signer. This directly breaks the "sign at most one block per height / no double-sign" equality the whole `conflict_still_blocks` design in this codebase exists to enforce, matching the report's Critical impact category ("a signer signing an invalid/non-canonical/conflicting block").

### Likelihood Explanation
This requires the operational precondition that a signer's local DB is lost/reset independent of the reward-cycle key material and registration (crash + fresh volume mount, disk failure + recovery, container restart without persistent storage, manual DB-file deletion for maintenance) — this is analogous to the Keycloak precondition of "server restart", which is also not attacker-controlled by itself. Given that precondition, the trigger is trivial and fully within a single miner's control plus normal StackerDB gossip: simply re-propose (or have gossip redeliver) the old conflicting sibling block; no majority collusion, no other signer's key, and no auth-token/local access is needed beyond the operator-side DB loss that already happened. The asymmetry that the codebase engineered a StackerDB-based recovery specifically for miner-view state, but not for signed-block/conflict history, indicates this gap was not deliberately mitigated.

### Recommendation
Persist (or reconstruct) the equivocation-relevant history — at minimum, the highest signed height per tenure/height and its signature — from a durable, gossip-recoverable source (e.g., replay recent `BlockResponse`/accepted-signature StackerDB chunks the same way `StateMachineUpdate` chunks are replayed in `Signer::new`), or refuse to sign any block until the signer has re-derived/confirmed via the node that it has not previously committed to a conflicting block at or above the proposed height (e.g., by cross-checking the node's own view of already-broadcast signed blocks in adjacent tenures before allowing `handle_block_pre_commit` to proceed on a freshly-initialized/empty `SignerDb`). At minimum, treat a `SignerDb` with no prior block history as untrusted for signing decisions until such reconciliation completes, rather than treating an empty conflict set as "no known conflicts."

### Proof of Concept
1. Signer S signs block A (height H, tenure T) — `signed_self` set, `add_block_signature`/`mark_locally_accepted` persisted in `signer_db`'s `blocks` table (`stacks-signer/src/signerdb.rs`).
2. Operator restarts S with the SQLite file for `signer_db` missing/reset (e.g., ephemeral storage, disk failure, or manual reset); `Signer::new()` opens a fresh DB and replays only `StateMachineUpdate` chunks from StackerDB (`stacks-signer/src/v0/signer.rs:219-271`).
3. A conflicting sibling block A' at height H (same tenure or a competing tenure) reaches pre-commit threshold and is handled by `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1383-1421`).
4. `self.signer_db.get_signed_conflicts(H, hash(A'))` returns `[]` because block A's row no longer exists in the fresh DB.
5. S signs A', producing two signatures from the same signer over conflicting blocks at height H — an equivocation that the `conflict_still_blocks`/freshness guard was specifically designed to prevent.
