### Title
Incorrect `max_timestamp` Tracking in `add_simple_oracle` Corrupts Time-Window Filter and Skews Median Price — (File: `crates/sui-oracle/move/oracle/sources/meta_oracle.move`)

---

### Summary

`add_simple_oracle` unconditionally **overwrites** `max_timestamp` with each oracle's timestamp instead of keeping the running maximum. When oracles are added in non-chronological order the staleness anchor `min_timestamp = max_timestamp - time_window_ms` is computed from the wrong baseline, allowing stale price data to pass the time-window filter and be folded into the median, or causing fresh data to be excluded. The result is a corrupted median price returned to every caller of `median`.

---

### Finding Description

`MetaOracle.max_timestamp` is initialized to `0` in `new` and is meant to represent the most-recent timestamp seen across all registered oracles, so that `combine` can derive a correct staleness floor. [1](#0-0) 

In `add_simple_oracle`, however, the assignment is a plain overwrite: [2](#0-1) 

Every call replaces the stored value unconditionally. After all oracles are added, `max_timestamp` holds the timestamp of whichever oracle was added **last** that had data — not the maximum across all oracles.

`combine` then derives the staleness floor from this wrong value: [3](#0-2) 

`min_timestamp = max_timestamp - time_window_ms` is anchored to the wrong point in time. Any oracle whose timestamp falls between the incorrect `min_timestamp` and the correct one (i.e., data that is genuinely stale relative to the most-recent oracle) passes the `> min_timestamp` guard and is included in the value set fed to `quick_sort` and then to the median index pick. [4](#0-3) 

The `SimpleOracle` timestamp is set by `clock::timestamp_ms(clock)` at submission time and is therefore fully controlled by the oracle provider's submission order, not by the consumer: [5](#0-4) 

---

### Impact Explanation

Any contract that calls `median` to obtain a trusted price (as shown in `trusted_fx` in the test module) receives a value computed over a data set that may include readings outside the intended freshness window. Depending on how stale the included data is and how many oracles are involved, the returned median can deviate arbitrarily from the true current price. DeFi contracts using this oracle for collateral valuation, liquidation thresholds, or exchange rates would act on a corrupted price, constituting **harmful smart-contract behavior** (High/Medium under the allowed impact gate).

---

### Likelihood Explanation

The bug fires in **normal, non-adversarial usage** whenever the last oracle added has an older timestamp than a previously added oracle. Oracle providers update their feeds independently and at different times; the consumer has no guarantee that the addition order matches chronological order. The reference usage pattern in `test_module.move` adds three oracles in a fixed positional order with no timestamp sorting: [6](#0-5) 

No test in the package exercises `add_simple_oracle` with out-of-order timestamps, so the bug is undetected by the existing test suite.

---

### Recommendation

Replace the unconditional assignment with a max-update:

```move
public fun add_simple_oracle<T: copy + drop + store>(
    meta_oracle: &mut MetaOracle<T>,
    oracle: &SimpleOracle
) {
    let oracle_data = oracle::simple_oracle::get_latest_data(oracle, meta_oracle.ticker);
    if (option::is_some(&oracle_data)) {
        let ts = data::timestamp(option::borrow(&oracle_data));
        if (ts > meta_oracle.max_timestamp) {
            meta_oracle.max_timestamp = ts;
        };
    };
    vector::push_back(&mut meta_oracle.oracle_data, oracle_data);
}
```

### Proof of Concept

Setup: three `SimpleOracle` objects with the following `clock::timestamp_ms` values at the time their data was last submitted:

| Oracle | Timestamp (ms) | Age relative to most-recent |
|--------|---------------|-----------------------------|
| A      | 1 000 000     | 0 s (most recent)           |
| B      | 999 000       | 1 s                         |
| C      | 900 000       | 100 s (stale)               |

`MetaOracle` configured with `time_window_ms = 60_000` (60 s).

**Step 1** — add oracles in order A → B → C (a natural positional order):

```
add_simple_oracle(meta, oracleA)  → max_timestamp = 1_000_000
add_simple_oracle(meta, oracleB)  → max_timestamp =   999_000  ← overwritten (wrong)
add_simple_oracle(meta, oracleC)  → max_timestamp =   900_000  ← overwritten again (wrong)
```

**Step 2** — `combine` computes:

```
min_timestamp = 900_000 − 60_000 = 840_000
```

**Step 3** — filter evaluation:

| Oracle | Timestamp | `> 840_000`? | Included? | Correct? |
|--------|-----------|-------------|-----------|----------|
| A      | 1 000 000 | yes         | yes       | yes      |
| B      |   999 000 | yes         | yes       | yes      |
| C      |   900 000 | yes         | **yes**   | **NO** — should be excluded (900 000 < 1 000 000 − 60 000 = 940 000) |

**Step 4** — `median` sorts `[priceA, priceB, priceC]` and returns index `3/2 = 1`. If `priceC` is an outlier (e.g., a price from 100 seconds ago during a volatile period), the returned median is corrupted.

**Correct behavior** (if `max_timestamp` were properly tracked as `1_000_000`):

```
min_timestamp = 1_000_000 − 60_000 = 940_000
Oracle C (900_000 < 940_000) → excluded
median computed over [priceA, priceB] only
```

    fun combine<T: copy + drop>(meta_oracle: MetaOracle<T>, ): (vector<T>, vector<address>) {
        let MetaOracle { mut oracle_data, threshold, time_window_ms, ticker: _, max_timestamp } = meta_oracle;
        let min_timestamp = max_timestamp - time_window_ms;
        let mut values = vector<T>[];
        let mut oracles = vector<address>[];
        while (vector::length(&oracle_data) > 0) {
            let oracle_data = vector::remove(&mut oracle_data, 0);
            if (option::is_some(&oracle_data)) {
                let oracle_data = option::destroy_some(oracle_data);
                if (data::timestamp(&oracle_data) > min_timestamp) {
                    vector::push_back(&mut values, *data::value(&oracle_data));
                    vector::push_back(&mut oracles, *data::oracle_address(&oracle_data));
                };
            };
        };
        assert!(vector::length(&values) >= threshold, EValidDataSizeLessThanThreshold);
        (values, oracles)
    }
