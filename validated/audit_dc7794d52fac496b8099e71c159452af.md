### Title
`verifyAllowedImages` in kubernetes executor applies internal-image bypass without regard to `isServiceContainer`, letting a service image equal to the runner's build image evade `AllowedServices` - (`executors/kubernetes/kubernetes.go`)

### Summary
`common.VerifyAllowedImage` (`common/allowed_images.go`) accepts a single `InternalImages` list that, if matched, unconditionally allows the image regardless of which `AllowedImages`/`AllowedServices` list was supplied for the check. The kubernetes executor's `verifyAllowedImages` builds this `InternalImages` list from `s.Config.Kubernetes.Image` (and the helper image) and reuses it for both build-container and service-container checks, so a job that sets a service's `image:` to the runner's configured build image can bypass an admin-configured `AllowedServices` allowlist.

### Finding Description
`common.VerifyAllowedImage` first checks `AllowedImages` glob patterns, then falls through to an exact-match check against `InternalImages`, returning `nil` (allowed) on match — independent of which option (`images` vs `services`) is being validated: [1](#0-0) 

The kubernetes executor's `verifyAllowedImages` selects `AllowedImages` vs `AllowedServices` based on `opts.isServiceContainer`, but the `InternalImages` list it passes (built from `s.Config.Kubernetes.Image` / helper image) is not similarly scoped to container role, so it is used identically for build and service checks. This means an attacker-controlled `services:` entry whose `image:` string exactly equals `s.Config.Kubernetes.Image` will match `InternalImages` and be allowed, even if that image is absent from `AllowedServices`.

The `AllowedImages`/`AllowedServices` string is not secret: it is the runner's statically configured default image, generally observable by any pipeline author on that runner (e.g., via the default image used when a job omits `image:`, or via published runner configuration). This makes the exact-match precondition realistically satisfiable by an unprivileged pipeline author.

### Impact Explanation
When an admin has intentionally restricted `AllowedServices` to a narrow allowlist, this bypass lets a job run the runner's build image as a *service* container instead — a different lifecycle/role (long-running sidecar with network reachability from the build container) than what the admin's `AllowedServices` allowlist was meant to permit. This violates the "Runner-enforced restrictions on images ... must hold against user-controlled input" invariant, though the impact is bounded by the fact that the same image is already trusted to run as the build container on this runner.

### Likelihood Explanation
Requires: (1) the runner admin configured a restrictive `AllowedServices` list (a non-default hardening step) while `Kubernetes.Image` is set to a value that is discoverable/predictable by pipeline authors on that runner, and (2) the attacker sets a `services:` entry's `image:` to that exact string. Both conditions are plausible on runners with such hardening, but exploitability is contingent on knowledge of the exact configured image string.

### Recommendation
Scope `InternalImages` matching to the correct container role in `verifyAllowedImages` — e.g., only allow the helper image to bypass checks for helper containers, and do not let `Kubernetes.Image` auto-bypass the `AllowedServices` check for service containers. Alternatively, pass distinct `InternalImages` lists depending on `opts.isServiceContainer`.

### Proof of Concept
Go unit test in `common/allowed_images_test.go` style, extended to kubernetes executor:
```go
func TestVerifyAllowedImages_ServiceBypassViaInternalImage(t *testing.T) {
    err := common.VerifyAllowedImage(common.VerifyAllowedImageOptions{
        Image:          "registry.example.com/build-image:latest", // == s.Config.Kubernetes.Image
        OptionName:     "services",
        AllowedImages:  []string{"registry.example.com/allowed-service:*"},
        InternalImages: []string{"registry.example.com/build-image:latest"},
    }, logger)
    // Expect: err == common.ErrDisallowedImage, because the image is not in AllowedServices
    // Actual (bug): err == nil, bypass via InternalImages match
    assert.ErrorIs(t, err, common.ErrDisallowedImage)
}
```
For a kubernetes-executor-level PoC, construct a `containerBuildOpts{image: s.Config.Kubernetes.Image, isServiceContainer: true}` and assert `s.verifyAllowedImages(opts)` returns `common.ErrDisallowedImage` when that image is absent from `s.Config.Kubernetes.AllowedServices`; currently it returns `nil`.

func VerifyAllowedImage(options VerifyAllowedImageOptions, logger buildlogger.Logger) error {
	for _, allowedImage := range options.AllowedImages {
		ok, _ := doublestar.Match(allowedImage, options.Image)
		if ok {
			return nil
		}
	}

	for _, internalImage := range options.InternalImages {
		if internalImage == options.Image {
			return nil
		}
	}
