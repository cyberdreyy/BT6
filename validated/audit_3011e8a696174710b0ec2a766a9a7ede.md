### Title
`claimInstantWithdrawRequest` pays receipts from the shared vault balance without verifying the instant bucket was funded, letting an instant claimant drain other users' already-funded normal withdraw reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external report is an off-by-one bounds bug: a parser consumes one more unit than the buffer actually holds. The credit-vault analog is a funding-boundary bug: `claimInstantWithdrawRequest` consumes underlying from the strategy's aggregate token balance without checking that the instant-withdraw bucket it draws from was actually funded by `collectInstantWithdrawFunds`. The vault keeps three logically separate pots in one ERC20 balance — funded normal withdraw claims (`collectWithdrawFunds`), funded instant claims (`collectInstantWithdrawFunds`), and the isolated `defaultRecoveryReserve` — but only the default reserve is segregated in `_transferFundedClaim`. An instant receipt therefore "reads past the end" of its own funded slice into underlying that belongs to pending normal claimants.

### Finding Description

- `requestInstantWithdraw` burns CDO strategy tokens and mints receipt tokens to the user, incrementing `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`).
- Funds for instant requests arrive later and separately via `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying from the CDO (`IdleCreditVault.sol:398-403`).
- `claimInstantWithdrawRequest` burns the user's receipt and calls `_transferFundedClaim(_user, amount)` with no check against `pendingInstantWithdraws` and no per-epoch or per-request funding flag (`IdleCreditVault.sol:380-393`).
- `_transferFundedClaim` only protects `defaultRecoveryReserve`; when it is zero, any underlying balance in the vault — including underlying transferred in by `collectWithdrawFunds` for normal withdraw receipts whose `pendingWithdraws` counter was already zeroed — is spendable by any claimant (`IdleCreditVault.sol:411-430`, `897-907`).
- Normal withdraw claimants have no alternative pot: once their funded slice is drained, `claimWithdrawRequest` → `_claimFundedWithdrawRequest` → `_transferFundedClaim` reverts on the failed `safeTransfer`, permanently freezing their already-funded payout.

Concrete sequence (fixed-APR mode, buffer phase):

1. Epoch N ends; `stopEpoch` calls `collectWithdrawFunds(pendingBasis)`, pulling underlying into the vault and setting `pendingWithdraws = 0`. User A's receipt of, e.g., 100k USDC is now fully funded and awaiting claim.
2. Attacker B (an ordinary KYC'd tranche holder) calls `requestWithdraw`/`requestInstantWithdraw` through the CDO during the buffer, registering an instant request of 100k and minting receipt tokens.
3. Before the manager calls `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` to fund B's request, B calls `claimWithdrawRequest`/`claimInstantWithdrawRequest` on the CDO. The strategy burns B's receipt and transfers the vault's 100k USDC — which is A's funded reserve — to B.
4. A's subsequent `claimWithdrawRequest` reverts inside `_transferFundedClaim` (insufficient balance, `defaultRecoveryReserve == 0`). A's claim is unrecoverable because `withdrawsRequests[A]` was only cleared on the reverting path — the funds are simply gone.

Even in the partial-funding case (`collectInstantWithdrawFunds` collects less than the aggregate), there is no per-user funded attribution: the first claimant drains a shared underfunded bucket, which is precisely the boundary violation.

### Impact Explanation

Direct theft plus permanent freezing of unclaimed yield/principal: B receives underlying earmarked for A's funded withdrawal, and A's claim reverts forever once the balance is drained (the receipt tokens were burned on B's side; A's `withdrawsRequests` still shows the claim but there is no underlying to pay it). Loss is bounded by the funded-but-unclaimed normal withdraw balance, which can be the entire epoch's withdrawal volume — quantified at up to 100% of pending funded claims outstanding at the time of the instant claim.

### Likelihood Explanation

The attack requires only that (a) at least one funded normal withdrawal is unclaimed while (b) the attacker holds enough tranche tokens to place an instant request and (c) the instant claim path is reachable before/without full instant funding. Withdrawal claimers routinely lag — claims are permissionless and can sit across epochs — so funded unclaimed balances are the norm, not the exception. Whether the CDO layer adds an independent gate (e.g., an instant-withdraw window opened only after `getInstantWithdrawFunds`) needs verification against `IdleCDOEpochVariant.claimInstantWithdrawRequest`/`getInstantWithdrawFunds`; if such a gate exists it narrows the window to "partially funded instant bucket," which still leaves the first-come-first-served drain of shared balance intact. The strategy-level missing funding check is unambiguous.

### Recommendation

Segregate the instant bucket the same way `defaultRecoveryReserve` is segregated: track `fundedInstantWithdraws` (incremented in `collectInstantWithdrawFunds`, decremented on each instant claim) and have `claimInstantWithdrawRequest` pay `min(request, fundedInstantWithdraws)` or revert when unfunded. Alternatively, reserve funded normal claims in a counter checked inside `_transferFundedClaim` (e.g., `fundedNormalClaims`), so instant claims can never spend them. PoC should assert that after `collectWithdrawFunds` funds a normal receipt, an instant claimant's `safeTransfer` cannot reduce vault balance below `fundedNormalClaims + defaultRecoveryReserve`.

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
// Fork/test harness: extend test/foundry/IdleCreditVault.t.sol setup
function testInstantClaimDrainsFundedNormalClaim() external {
    uint256 amount = 100_000 * ONE_SCALE;
    // A deposits and runs epoch 0 to completion
    _depositWithUser(userA, amount, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // A requests normal withdraw; next stopEpoch funds it via collectWithdrawFunds
    vm.prank(userA);
    uint256 aClaim = cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());
    // vault now holds aClaim underlying; pendingWithdraws == 0

    // Attacker B deposits, requests instant withdraw (receipt minted, unfunded)
    _depositWithUser(userB, aClaim, true);
    vm.prank(userB);
    cdoEpoch.requestInstantWithdraw(aClaim, address(AAtranche));

    // B claims BEFORE manager funds the instant bucket
    uint256 bPre = underlying.balanceOf(userB);
    vm.prank(userB);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(userB) - bPre, aClaim, 'B stole A funded claim');

    // A can never claim: funded reserve was drained
    vm.prank(userA);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat: I was unable to inspect `IdleCDOEpochVariant.claimInstantWithdrawRequest`/`getInstantWithdrawFunds` gating in the remaining iterations; if the CDO blocks instant claims until after funding, the exploitable surface reduces to the partial-funding first-come-first-served drain, which is still unfixed by the current accounting.
