### Title
Old-epoch unfunded instant-withdraw receipts are excluded from default recovery basis but still claimed at par — frozen claims or reserve dilution - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`finalizeDefaultRecovery` computes the pending claim basis with `defaultPendingClaimBasis()`, which adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch's instant receipts — to `pendingWithdraws`. The unfunded counter `pendingInstantWithdraws`, however, is a global aggregate that can include instant receipts requested in *earlier* epochs that were only partially funded by `collectInstantWithdrawFunds`. This is the analog of an out-of-bounds/over-read: recovery accounting reads only the head-of-buffer (current epoch) while the aggregate counter reads past it. Old-epoch instant claimants then fall through to `_transferFundedClaim`, which pays the aggregate `instantWithdrawsRequests[_user]` at par or reverts permanently.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393), once `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (lines 842-856). Whatever remains in the aggregate `instantWithdrawsRequests[_user]` — including receipts from epochs *before* the default epoch — is burned and paid 1:1 by `_transferFundedClaim` (lines 387-392, 897-907).

But at finalization, `defaultPendingClaimBasis` (lines 644-649) includes only the *current*-epoch instant basis:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

and `_defaultPrefundedInstantReserve` (lines 716-723) likewise only credits `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`. If `pendingInstantWithdraws > instantWithdrawClaimsByEpoch[epochNumber]` (carry-over unfunded receipts from an older epoch, or a mix), the prefunded reserve is set to `0` even though partially collected cash for old receipts may sit in the strategy, and the old-epoch basis is entirely absent from `totalBasis` — so `defaultRecoveryReserve` contains no backing for those claims.

Two outcomes depending on strategy balance at claim time:

1. **Permanent freeze (most likely):** the old-epoch claimant calls `claimInstantWithdrawRequest`; `_claimDefaultedInstantWithdrawRequest` returns 0; `_transferFundedClaim` sees `balance - defaultRecoveryReserve < amount` and reverts `NotAllowed()` (line 904). The user's receipt tokens can never be claimed or re-requested — `requestWithdraw`/instant claims remain bricked forever even though other claimants recovered at `defaultRecoveryPrice`.
2. **Over-par theft:** if the strategy happens to hold non-reserve underlying above the reserve (e.g., late-arriving borrower funds or a new prefund), the old-epoch claimant is paid at *par* — a better ratio than every other defaulted claimant — draining value that belongs to active LPs or other recovery claimants.

Reachability: `pendingInstantWithdraws` is decremented only by `collectInstantWithdrawFunds` (lines 398-403). A partial prefund at `startEpoch` (explicitly contemplated in the comment at lines 636-640: "that cash covered only part of the instant queue") leaves an unfunded remainder that persists across epochs and across the epoch boundary, since instant receipts are never force-settled at `stopEpoch`.

### Impact Explanation
Unprivileged users holding instant-withdraw receipts from an epoch earlier than the default epoch either (a) permanently lose the ability to claim their haircut share of `defaultRecoveryReserve` — direct freezing of user funds — or (b) claim at par and dilute/steal from the recovery reserve and other claimants. The invariant "one receipt, one haircut payout" and reserve isolation (`_transferFundedClaim` guard) are simultaneously violated by the epoch-scoped read in `defaultPendingClaimBasis`/`instantWithdrawsRequestsByEpoch[defaultEpoch]`.

### Likelihood Explanation
Requires: instant-withdraw mode enabled, a partially funded instant queue that carries `pendingInstantWithdraws` across at least one epoch boundary, then a borrower default finalized via `finalizeDefaultRecovery`. All steps use only unprivileged-user-initiated flows plus honest manager/owner calls (`startEpoch`, `stopEpoch`, `finalizeDefault`), which is within scope. No existing guard (`_ensureDefaultRecoveryInitialized`, `_transferFundedClaim` reserve check, per-epoch clearing) accounts for the stale-epoch portion of the aggregate counters.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, account for *all* unfunded instant receipts, not just `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., track a global unfunded instant basis or require old-epoch instant receipts to be claimed/settled before `startEpoch`. Symmetrically, `_claimDefaultedInstantWithdrawRequest` should apply `defaultRecoveryPrice` to the user's total unfunded instant basis (all epochs up to and including `defaultRecoveryEpoch`), or revert partial-queue prefunding so receipts can never span epochs unfunded.

### Proof of Concept
Foundry fork PoC (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testOldEpochInstantReceiptExcludedFromRecovery() external {
    // 1. enable instant withdraws; deposit; requestInstantWithdraw(1000)
    // 2. manager startEpoch with borrower cash covering only 600 ->
    //    collectInstantWithdrawFunds(600); pendingInstantWithdraws = 400 (unfunded, epoch N)
    // 3. run epoch N, stopEpoch; epochNumber becomes N+1
    // 4. epoch N+1 running; borrower defaults (onStopEpoch fails) -> _handleBorrowerDefault
    // 5. owner finalizeDefaultRecovery(recovered, source)
  assertEq(strategy.instantWithdrawClaimsByEpoch(N + 1), 0); // user receipt is in epoch N
  assertEq(strategy.pendingInstantWithdraws(), 400);         // but unfunded counter includes it
    //    -> basis excludes the 400; reserve covers only epoch-N+1 receipts
    // 6. user claims:
  vm.expectRevert(); // _transferFundedClaim: balance - reserve < 400
  cdoEpoch.claimInstantWithdrawRequest(); // permanently frozen
}
```

Key assertions: `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` is 0 for the victim while `pendingInstantWithdraws` includes their receipt; `_claimDefaultedInstantWithdrawRequest` returns 0; the par-claim path reverts against the reserve guard, leaving the receipt permanently unclaimable.
