### Title
Miner activity timestamp is refreshed by the miner's own invalid/duplicate/conflicting proposals, letting a single miner suppress the inactivity fallback indefinitely - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_latest_block_in_tenure` is meant to answer "does this proposal confirm the tip we already know about?" and, as a side effect, calls `signer_db.update_last_activity_time` whenever a proposal from the current tenure's miner is rejected for not advancing the chain (a reorg attempt against a signed tip, or a conflict with a fresh pre-commit). This is the direct structural analog of the reported `highWaterMark` bug: a checkpoint value that is supposed to gate an important protective decision (there: fee accrual; here: the miner-inactivity timeout that triggers fallback to the prior tenure) gets refreshed by routine, cheap, non-progressing activity from the very party the checkpoint is meant to police.

### Finding Description
`is_timed_out` (v1: `stacks-signer/src/chainstate/v1.rs:52-94`; v2 analog gated by `SortitionState::is_timed_out`) measures `block_proposal_timeout` against `last_activity_time` recorded in the signer DB via `update_last_activity_time`. [1](#0-0) 

That timestamp is refreshed inside `check_latest_block_in_tenure`, which runs on every incoming proposal from the tenure's miner at proposal time, at validate-ok, and at signing time (`confirms_latest_block_in_same_tenure`, `check_tenure_change_confirms_parent`, `check_block_against_signer_db_state`): [2](#0-1) 

The comments in the code explicitly acknowledge the tradeoff — "the miner may just be slow, so count this invalid block proposal towards valid miner activity" and "Counting it as miner activity, but not rejecting the proposal" — but this means a miner can keep resubmitting a proposal that never advances the tenure's chain length (a stale/duplicate/reorg-attempt block) purely to keep `last_activity_time` fresh, without ever producing a valid, higher block: [3](#0-2) [4](#0-3) 

`check_miner_inactivity` in the signer state machine relies entirely on this timestamp to decide whether to fall back to the prior tenure's miner: [5](#0-4) 

Because the checkpoint (`last_activity_time`) is reset by cheap, repeatable, non-progressing input from the same actor the timeout is supposed to detect misbehavior/stalling from, the "since-last-real-progress" invariant the timeout is designed to enforce is broken — exactly as the `highWaterMark` update on every deposit/withdraw/mint broke the "since-last-fee-accrual" invariant in the referenced report.

### Impact Explanation
If a tenure's miner is effectively unable or unwilling to produce a valid next block (e.g., it is stalled, censoring, or otherwise stuck) but can still emit proposals that fail `check_latest_block_in_tenure` (a stale re-proposal, a conflicting/duplicate block, or a reorg attempt against an already-signed tip), it can indefinitely refresh `last_activity_time` and thereby prevent `is_timed_out` from ever returning true. This blocks `check_miner_inactivity`'s fallback path to the prior tenure and can wedge the tenure's liveness — the chain cannot progress via a fallback miner even though the current miner is not actually producing accepted blocks. This matches the High-severity class: "a signer wedged into never signing valid blocks... or losing the equivocation guard" via a liveness wedge triggerable by a single participant (the current tenure's miner), without needing a majority of signers.

### Likelihood Explanation
The trigger requires only the current tenure's miner (a one-slot actor) to keep sending cheap, already-signed (miner-signature-valid, since these checks run after basic proposal parsing) but non-advancing block proposals — e.g., resubmitting the same stale block, or a lower/duplicate chain-length block — at an interval shorter than `block_proposal_timeout`. This is inexpensive (no need to win additional sortitions or craft complex payloads) and is explicitly anticipated as "activity" by the code comments, meaning the pattern is easy to reach and does not depend on race conditions or other signers' cooperation.

### Recommendation
Do not treat every rejected/non-advancing proposal from the tenure miner as evidence of "liveness" that resets the same timer used to detect a stalled miner. Distinguish between (a) proof that the miner is capable of producing a valid, height-advancing block (which should refresh the timer) and (b) an actor merely resending old or invalid payloads (which should not). Concretely, only refresh `last_activity_time` when the proposal reaches a further validation milestone (e.g., passes node-side block validation, or is provably a legitimate resubmission attempt within a bounded number of retries), rather than immediately at `check_latest_block_in_tenure` for any proposal that fails the confirms-latest-block check.

### Proof of Concept
1. A miner wins a tenure and produces one valid tenure-start block that signers sign (`get_last_signed_block`/`get_tenure_last_block_info` now returns this block).
2. The miner then stops producing new, height-advancing blocks (it is effectively stalled), but every `block_proposal_timeout - ε` seconds it resubmits a stale/duplicate proposal at the same or lower `chain_length` (or re-broadcasts the original signed block as a "new" proposal).
3. Each such proposal enters `check_latest_block_in_tenure`; since `chain_length <= info.block.header.chain_length` and the last signature is still "fresh" relative to `reorg_attempts_activity_timeout`, the function calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` (`stacks-signer/src/chainstate/mod.rs:403-417`) before returning `Ok(false)` (rejecting the proposal).
4. `SortitionState::is_timed_out` therefore never observes `elapsed > block_proposal_timeout` (`stacks-signer/src/chainstate/v1.rs:76-93`), so `check_miner_inactivity` never falls back to the prior tenure's miner (`stacks-signer/src/v0/signer_state.rs:304-354`).
5. The tenure is wedged: the current miner is not producing any new accepted blocks, yet the fallback mechanism designed to route around a stalled miner never triggers, because the "activity" checkpoint keeps getting reset by the same non-progressing input the timeout exists to catch.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)

    pub fn check_latest_block_in_tenure(
        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
