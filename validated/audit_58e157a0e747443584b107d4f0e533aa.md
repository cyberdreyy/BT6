## Analysis

The reported bug class is: **a value embedded in attacker-controlled data (a cross-reference to another program's account) is trusted and used to compute derived state (rewards/decimals), without verifying that the referenced account is actually owned by / belongs to the program that is supposed to have produced it.**

In agave, the RPC token-parsing path has the same shape of bug. `get_mint_owner_and_additional_data()` takes a `mint` pubkey — which is read straight out of attacker-controlled account data (`token_account.base.mint`, an untrusted `TokenAccount.mint` field) — and fetches whatever account currently lives at that address, then decodes its `Mint` layout (decimals, interest-bearing config, scaled-UI-amount config) with no check that this mint account is actually owned by the same SPL Token / Token-2022 program that owns the token account being displayed: [1](#0-0) 

Callers of this helper discard the returned "owner" and only keep the decimals/extension data: [2](#0-1) [3](#0-2) 

This is the exact analog of `CLGauge.deposit()` trusting an NFT's implied pool without checking `token0/token1/tickSpacing` against the real pool — here, the RPC decoder trusts a `mint` pubkey embedded in a token account without checking that the mint's owner program matches the token account's owner program. The fix pattern that Velodrome/Spearbit applied (cross-check the referenced entity's identifying fields against the caller) is precisely what agave's own SVM-side balance collector already does correctly, showing the check is known and expected but missing from the RPC decoder: [4](#0-3) 

Note the explicit `if *mint_account.owner() != program_id { return None; }` guard at line 188, absent from the RPC path.

### Root cause / Impact

Because `is_known_spl_token_id` is only checked against the *token account's* owner, not the *mint's* owner: [5](#0-4) 

...a user (or an attacker crafting an account that later appears in a victim's `getTokenAccountsByOwner`/`getProgramAccounts` jsonParsed results) can create a fake SPL-Token(-2022) account whose `mint` field points at an unrelated `Mint` account (belonging to a different token program, or a Token-2022 mint carrying `InterestBearingConfig`/`ScaledUiAmountConfig` extensions with an arbitrary multiplier/rate). `getTokenAccountBalance`, `getAccountInfo`(jsonParsed), `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, and `getProgramAccounts`(jsonParsed) will then compute and return a `uiAmount`/`decimals`/extension state derived from that unrelated mint, producing a wrong (attacker-influenced) reported balance for an RPC caller — this is a decoder misreporting bug reachable via a single unprivileged JSON-RPC call, matching the "decoder panic and misreporting" / "wrong ... account data returned" acceptance criteria.

### Title
RPC token-balance/jsonParsed decoders trust an untrusted `mint` reference without verifying it is owned by the same token program, causing misreported balances — (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
`get_mint_owner_and_additional_data()` fetches and decodes whatever account sits at the `mint` pubkey taken from an untrusted `TokenAccount`'s data, without checking that this mint account's owner matches the token account's owner program. RPC handlers (`getTokenAccountBalance`, jsonParsed `getAccountInfo`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate`/`getProgramAccounts`) use the resulting decimals/interest-bearing/scaled-UI config to compute the displayed `uiAmount`, so a crafted token account can force a bogus balance/decimals to be returned for a legitimate-looking, attacker-influenced account.

### Finding Description
`get_mint_owner_and_additional_data` (`rpc/src/parsed_token_accounts.rs:92-108`) is called with a `mint` pubkey originating from `token_account.base.mint` or `get_token_account_mint(account.data())` — both values are read directly out of account data controlled by whoever created that account, and are not validated against the calling account's owner program before use. The function loads "whatever account is at that address" and decodes it as a `Mint`, returning its decimals plus `InterestBearingConfig`/`ScaledUiAmountConfig` extension data. Every call site — `get_token_account_balance` (`rpc/src/rpc.rs:2013-2035`) and `get_parsed_token_account(s)` (`rpc/src/parsed_token_accounts.rs:23-50, 52-88`) — discards or never obtains the mint's actual owner, so there is no check that the referenced mint is actually managed by the same SPL Token / Token-2022 program instance as the token account being decoded. This is the same missing-relationship-verification pattern as the CLGauge report: a value that is supposed to identify "the pool/mint this position/account belongs to" is trusted without checking it against the account under inspection. Contrast with `SvmTokenInfo::unpack_token_account` (`svm/src/transaction_balances.rs:174-203`), which performs exactly this check (`if *mint_account.owner() != program_id { return None; }`) before trusting a mint's decimals for building transaction pre/post token balances.

### Impact Explanation
An unprivileged actor can create/store an account owned by `spl_token`/`spl_token_2022` whose data unpacks as a valid `TokenAccount` (satisfying `is_known_spl_token_id`), but whose embedded `mint` field points at an arbitrary existing `Mint` account — e.g., a Token-2022 mint with an attacker-influenced or unrelated `ScaledUiAmountConfig`/`InterestBearingConfig`, or a mint with different `decimals` than the token account's real program intends. Any caller inspecting that account via `getTokenAccountBalance`, `getAccountInfo` (jsonParsed), `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, or `getProgramAccounts` (jsonParsed) — a single unprivileged JSON-RPC call — receives a `uiAmount`/`decimals`/extension-state value derived from the wrong mint, i.e., wrong account data is returned from a query, without any consensus-state mutation being required to trigger it.

### Likelihood Explanation
Trivially reachable: creating a token account with an arbitrary `mint` field is a normal, permissionless operation (no special authority needed), and querying it back through the standard jsonParsed RPC endpoints is a single, unprivileged JSON-RPC call.

### Recommendation
In `get_mint_owner_and_additional_data`, verify that the fetched mint account's owner matches the token program owning the account being decoded (mirroring the check already present in `SvmTokenInfo::unpack_token_account`), and propagate/enforce that check at all call sites (`get_token_account_balance`, `get_parsed_token_account`, `get_parsed_token_accounts`) before using the mint's decimals/extension data to compute `uiAmount`.

### Proof of Concept
1. Create account `A`, owned by `spl_token_2022`, packed as a valid `TokenAccount` with `amount = X` and `mint = M`, where `M` is a real Token-2022 mint (owned by `spl_token_2022`) that has a `ScaledUiAmountConfig` extension with an extreme `new_multiplier`, or where `M` belongs to a mismatched decimals configuration.
2. Call `getTokenAccountBalance(A)` (or `getAccountInfo(A, {encoding:"jsonParsed"})`, or `getTokenAccountsByOwner`/`getProgramAccounts` if `A`'s `owner` field is set to a victim pubkey).
3. Observe that `get_mint_owner_and_additional_data(bank, M)` is invoked without checking `M`'s owner against `A`'s owner (`rpc/src/parsed_token_accounts.rs:92-108`, `rpc/src/rpc.rs:2028-2035`), so the returned `uiAmount`/decimals is computed from `M`'s configuration regardless of any relationship validity, differing from the value a correctly-cross-checked decoder (as in `svm/src/transaction_balances.rs:174-203`) would produce.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

impl SvmTokenInfo {
    fn unpack_token_account<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        account: &AccountSharedData,
        index: usize,
    ) -> Option<Self> {
        let program_id = *account.owner();
        let generic_token::Account {
            mint,
            owner,
            amount,
        } = generic_token::Account::unpack(account.data(), &program_id)?;

        let mint_account = account_loader.load_account(&mint)?;
        if *mint_account.owner() != program_id {
            return None;
        }

        let generic_token::Mint { decimals, .. } =
            generic_token::Mint::unpack(mint_account.data(), &program_id)?;

        Some(Self {
            account_index: index.try_into().ok()?,
            mint,
            amount,
            owner,
            program_id,
            decimals,
        })
    }
