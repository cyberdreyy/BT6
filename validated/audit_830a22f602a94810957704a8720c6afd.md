### Title
Loss-adjusted withdraw receipt escapes haircut when user makes a later withdraw request - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug (`ip_vs_nat_icmp` reading `ihl` twice — validating one value, then writing past a different, attacker-shifted offset) maps to `IdleCreditVault`'s claim path, which validates the *claim epoch* through one field (`lastWithdrawRequest[_user]`) but pays out and burns through a *different*, aggregated field (`withdrawsRequests[_user]`). When a lender holds a haircut receipt from a loss epoch and then submits a new withdraw request in a later epoch, the loss-epoch index is overwritten, the loss-adjusted claim branch silently no-ops, and the funded-claim branch pays the loss-epoch receipt at par — writing a payout beyond the "validated area" (the funded loss-adjusted amount).

### Finding Description
On a realized-loss stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]`, transfers only the haircutted amount from the CDO, and zeroes `pendingWithdraws` [1](#0-0) . The corresponding claim, `_claimLossAdjustedWithdrawRequest`, selects the epoch to haircut from `lastWithdrawRequest[_user]` — i.e. the *latest* request epoch, not the epoch that actually suffered the loss [2](#0-1) .

`claimWithdrawRequest` runs the loss-adjusted claim and then unconditionally falls through to `_claimFundedWithdrawRequest`, which pays the whole `withdrawsRequests[_user]` aggregate at par and burns the matching receipt tokens [3](#0-2) . `requestWithdraw` records a new `lastWithdrawRequest[_user] = currentEpoch` and adds to `withdrawsRequestsByEpoch` on every request without checking for a pending haircut receipt [4](#0-3) .

Attack sequence (attacker = ordinary KYC-passing lender):

1. During the buffer before stop of epoch N, attacker calls `requestWithdraw` → receipt recorded in `withdrawsRequestsByEpoch[attacker][N]`, `lastWithdrawRequest[attacker] = N`.
2. Epoch N stops with a loss: `stopEpochWithDuration(_lossAmount)` → `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` funds only `pendingBasis - pendingLoss` and sets `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`; `pendingWithdraws = 0`.
3. Instead of claiming, attacker calls `requestWithdraw` again in epoch N+1 → `lastWithdrawRequest[attacker] = N+1`, aggregate `withdrawsRequests[attacker]` now covers both epochs.
4. Epoch N+1 stops fully funded.
5. Attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest = N+1`; `lossRecoveryPriceByEpoch[N+1] == 0` → early return, epoch-N receipt never cleared.
   - `_claimFundedWithdrawRequest` passes the `epochNumber > lastWithdrawRequest` gate, `_settleApr0` no-ops, and `_transferFundedClaim` pays `withdrawsRequests[attacker]` — including the full epoch-N basis — at par.

The epoch-N receipt was funded only `p/RECOVERY_FULL` of its basis, but is paid 1:1. The excess comes directly out of the strategy's funded-claim reserve.

### Impact Explanation
Direct theft of the haircut amount: `claimBasis_N × (1 − lossRecoveryPriceByEpoch[N]/RECOVERY_FULL)` is paid from underlyings that belong to other funded receipt holders (and the instant-withdraw reserve via `_transferFundedClaim`). With a 50% loss price, an attacker who requested 1M USDC before the loss epoch steals 500k USDC, leaving the last claimers' receipts unbacked — solvency/“one receipt, one haircut-adjusted payout” is broken. Note `collectWithdrawFunds` transferred only the haircutted sum, so the overpayment is real missing liquidity, not accounting slack.

### Likelihood Explanation
Requires a loss stop (`stopEpochWithDuration` with `_lossAmount > 0` or partial funding), which is an honest-manager action within scope, and an attacker who simply sandwiches a second `requestWithdraw` around it — no privileged role, no reentrancy, no oracle. Any lender can do it; the first request can even be an unrelated earlier position. The only constraint is requesting again before claiming, which is economically natural for an attacker seeking to dodge a haircut.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate/derive the claim epoch from the user's per-epoch data rather than `lastWithdrawRequest[_user]` — e.g. track the earliest unclaimed request epoch, or loop `lossRecoveryPriceByEpoch` over all epochs in which the user holds receipts. Alternatively, block new `requestWithdraw`/`requestInstantWithdraw` while `lossRecoveryPriceByEpoch[lastWithdrawRequest[msg.sender]] != 0` is unclaimed, mirroring how defaulted-epoch receipts are cleared via `withdrawsRequestsByEpoch[user][defaultEpoch]` regardless of `lastWithdrawRequest`.

### Proof of Concept
Foundry fork PoC sketch (contracts: `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
// setup: attacker deposits into AA, epoch N started by manager, buffer reached
// 1. attacker requests withdraw of X underlyings (epoch N receipt)
vm.prank(attacker);
cdo.requestWithdraw(shares, AA);

// 2. manager stops epoch N with a loss: borrower funds only haircutted amount
vm.prank(manager);
cdo.stopEpochWithDuration(duration, lossAmount); // -> collectWithdrawFunds(funded < basis)
// assert strategy.lossRecoveryPriceByEpoch(N) > 0 && < RECOVERY_FULL

// 3. epoch N+1 starts; attacker requests again instead of claiming
vm.prank(attacker);
cdo.requestWithdraw(remainingShares, AA); // lastWithdrawRequest -> N+1

// 4. epoch N+1 stops fully funded; epochNumber > N+1
// 5. attacker claims: loss branch no-ops on N+1, funded branch pays aggregate at par
uint256 balBefore = token.balanceOf(attacker);
vm.prank(attacker);
cdo.claimWithdrawRequest();
uint256 paid = token.balanceOf(attacker) - balBefore;

// attacker received epoch-N basis at par instead of * lossRecoveryPrice
assertGt(paid, expectedFundedN1 + basisN * lossPrice / 1e18);
// invariant: sum of funded transfers < sum of par claims -> strategy reserve drained
```

Key assertion: `withdrawsRequestsByEpoch[attacker][N]` was never cleared (the early return at `lossRecoveryPriceByEpoch[N+1] == 0` skips `_clearWithdrawClaimForEpoch`), yet its basis was included in the `withdrawsRequests[attacker]` payout.

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
