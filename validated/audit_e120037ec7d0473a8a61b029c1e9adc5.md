### Title
Loss-adjusted withdrawal haircut only applies to the user's most recent request epoch; receipts from earlier epochs are paid at par, draining the underfunded claim reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` records a single pro-rata `lossRecoveryPriceByEpoch[epochNumber]` for the whole `pendingWithdraws` bucket when `stopEpochWithDuration` realizes a loss, but `_claimLossAdjustedWithdrawRequest` looks the haircut up only under `lastWithdrawRequest[_user]` — the user's most recent request epoch. Any older unfunded-but-aggregated receipt held by the same or other users skips the haircut entirely and is paid at par through `_claimFundedWithdrawRequest`, while the underlying reserve was only funded `pendingBasis * lossRecoveryPrice`. First claimants over-withdraw and later loss-epoch claimants' transfers revert, permanently freezing their funds.

### Finding Description
The external bug is an out-of-bound read caused by scanning attacker-influenced records without validating that the record being read is in-bounds for the check performed. The analog here is the claim path "scanning" a per-epoch haircut keyed by the wrong (out-of-scope) epoch index:

1. `requestWithdraw` adds every request into the global `pendingWithdraws` bucket and sets `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) . Multiple epochs of unclaimed receipts can coexist: the funded-claim path only requires `epochNumber > lastWithdrawRequest`, so a user can stack a new request without claiming an old funded one.
2. When a stop realizes a loss, `previewLossAdjustedWithdrawFunds` haircuts the *aggregate* `pendingBasis` pro rata [2](#0-1) , and `collectWithdrawFunds` stores the ratio under `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` [3](#0-2) . The loss is thus applied to receipts from *all* request epochs.
3. At claim time, `_claimLossAdjustedWithdrawRequest` only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [4](#0-3)  and `_clearWithdrawClaimForEpoch` clears only that one epoch's basis [5](#0-4) .
4. The remainder (`withdrawsRequests[_user]` minus the cleared epoch) then falls into `_claimFundedWithdrawRequest`, which pays it at par [6](#0-5)  — even though it was part of the basis that was haircut. Worse, a user whose *only* receipt is from an older epoch has `lossRecoveryPriceByEpoch[oldEpoch] == 0`, so the loss-adjusted path is skipped entirely and the full par claim is paid.

The guard in `requestWithdraw` only blocks re-requesting when the *previous* epoch already has a nonzero recovery price [7](#0-6) ; it does not prevent holding a pre-loss receipt in an earlier epoch when the loss occurs.

### Impact Explanation
Direct theft plus freezing of unclaimed withdrawals. The strategy receives only `pendingBasis * lossRecoveryPrice` in underlying, but claimants collectively are owed `oldEpochBasis` (par) + `lossEpochBasis * price`. The first claimant(s) extract more than their haircut share; once the reserve is drained, `safeTransfer` in `_transferFundedClaim`/`_claimLossAdjustedWithdrawRequest` reverts for everyone else, permanently freezing their claims (there is no alternative path — `claimWithdrawRequest` is the only way out). Loss = `(total pending basis − loss-epoch basis) * (1 − lossRecoveryPrice)`, scaled by how much of the aggregate basis sits in older epochs — fully attacker-controllable by splitting requests across epochs.

### Likelihood Explanation
Requires only unprivileged lender actions: a tranche-token holder calls `cdoEpoch.requestWithdraw` in epoch N, lets it be funded without claiming, then requests again in epoch M (or a second attacker simply holds an old receipt). The trigger is an honest `manager`/`owner` call to `stopEpochWithDuration` with `_lossAmount > 0` — a supported, non-default flow — which is precisely when the haircut must bind to all pending receipts. No privileged misbehavior, oracle manipulation, or timing luck is needed; the accounting error is deterministic.

### Recommendation
Attribute the loss haircut to *all* pending receipts, not just the stop epoch. Concretely: record the loss ratio per user (e.g., store a global "latest unfunded loss price" applied to every pending receipt at claim time, or keep a running `lossRecoveryPrice` that `requestWithdraw` snapshots for each outstanding receipt), and make `_clearWithdrawClaimForEpoch`/the funded path apply it to every outstanding epoch basis, not only `lastWithdrawRequest`. Alternatively, force claim/settlement of all outstanding receipts before allowing a request in a later epoch.

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
