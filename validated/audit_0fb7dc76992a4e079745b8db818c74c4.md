### Title
Unsafe `int64`→`uint` conversion of user-supplied `Timestamp` bypasses the gateway's stale-message check for `web_api_trigger` messages - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
In `handler.HandleLegacyUserMessage`, the freshness/anti-replay check for `web_api_trigger` messages compares `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec` against `uint(payload.Timestamp)`, where `payload.Timestamp` is a signed `int64` field fully controlled by the (unprivileged) message sender before signing. Converting an attacker-chosen negative or out-of-range `int64` to `uint` wraps around to a huge unsigned value, which always satisfies `now - maxAge <= hugeValue`, so the "stale message" rejection never triggers, defeating the freshness check entirely. This is the same unsafe-downcast/conversion bug class as the `issue()` C4 report, but manifests here as a security-check bypass rather than a value truncation.

### Finding Description
`HandleLegacyUserMessage` decodes `webapicap.TriggerRequestPayload`, whose `Timestamp` field is declared as `int64` (`core/capabilities/webapi/webapicap/event_trigger_generated.go:107`) and is populated directly from the caller's signed JSON payload — the caller chooses this value before signing the message, so it is fully attacker-controlled content, not a server-derived clock value.

The staleness check is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    ... // "stale message" rejection
}
``` [1](#0-0) 

`uint` on the platforms this code targets is 64-bit, matching `int64`'s bit width. Casting a negative `int64` (e.g. `-1`) to `uint` does not error or clamp — it reinterprets the two's-complement bit pattern, producing a value near `math.MaxUint64` (e.g. `18446744073709551615`). Since the left side of the comparison (`now - maxAge`) is a comparatively small number, the condition `leftSide > hugeValue` is always false, so the "stale message" branch is skipped regardless of how old (or fabricated) the timestamp actually is.

This is structurally identical to the reported bug class: an unchecked/unsafe numeric type conversion of a user-supplied parameter that is relied upon for a security-relevant invariant (there, `basketsNeeded`/`allVestAt` invariants; here, message freshness), and which can be driven into wraparound territory purely by the caller choosing a boundary value, with no other cost or privilege required.

Supporting context on why this check exists and is exploitable by an unprivileged caller: the message is validated only for a well-formed signature (`msg.Validate()`), not against any allowlist prior to this staleness check — the code even carries a `// TODO: apply allowlist and rate-limiting here` comment right after the staleness check, confirming that at the point this check executes, any party capable of producing a validly-formatted signed message (using their own key) can reach it. [2](#0-1) 

### Impact Explanation
The staleness check is the gateway's only defense against replay/backdated `web_api_trigger` messages before the request is routed to DON member nodes and used to start workflow executions (`triggerConnectorHandler.processTrigger`, which derives `TriggerEventID` from `body.Sender + payload.TriggerEventId` and emits/starts workflow execution). By setting `Timestamp` to a negative value, an attacker-controlled sender can submit an arbitrarily old or fabricated trigger message that will never be rejected as stale, weakening the freshness guarantee. Combined with a `TriggerEventId` collision, this could enable replays of previously valid trigger events indefinitely; standing alone, it allows the timestamp-freshness control to be trivially and permanently disabled by any caller. This does not directly move funds or leak secrets, so it should be scoped as a request-integrity/anti-replay control bypass rather than a critical break, consistent with the "Medium" resolution the analogous Solidity finding ultimately received.

### Likelihood Explanation
The check is on the unauthenticated/unprivileged ingestion path for legacy `web_api_trigger` gateway messages, reached before any allowlist enforcement (per the in-code TODO). Any actor able to construct and sign a `web_api_trigger` payload — which requires only an EC keypair, not membership in any authorized set at this stage — can set `Timestamp` to `-1` (or any negative value) with zero cost and 100% reliability, since Go performs no bounds checking on `int64`→`uint` conversion.

### Recommendation
Replace the unsafe `uint(payload.Timestamp)` conversion with an explicit, safe comparison that treats negative/implausible timestamps as invalid rather than silently wrapping:
```go
if payload.Timestamp < 0 {
    return staleOrInvalidTimestampError
}
now := time.Now().Unix() // int64
if now-int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp {
    return staleMessageError
}
```
More generally, audit other places in the gateway/handlers code that mix signed (`int64`) and unsigned (`uint`/`uint32`) representations of user-supplied values used in security-relevant comparisons, and adopt a single signed arithmetic convention (or a checked/saturating cast helper, as already exists in `system-tests/lib/conversions/ints.go`) for all such conversions.

### Proof of Concept
1. Craft a `webapicap.TriggerRequestPayload` JSON body with `"timestamp": -1` (or any negative `int64`), a valid `trigger_id`/`trigger_event_id`/`topics`/`params`.
2. Sign the enclosing `api.Message` with any ECDSA key (`msg.Sign(key)`), as done in the existing test helper `triggerRequest` in `core/services/gateway/handlers/capabilities/handler_test.go:193-234`, but pass `timestamp = "-1"`.
3. Submit via `handler.HandleLegacyUserMessage(ctx, msg, cb)`.
4. Observe that the staleness branch at `handler.go:372-383` is never entered (`uint(-1)` ≈ `1.8e19`, far larger than `uint(time.Now().Unix())-MaxAllowedMessageAgeSec`), so the message proceeds to be dispatched to DON nodes despite carrying an invalid/backdated timestamp — confirming the freshness check provides no protection against attacker-chosen negative timestamps.
