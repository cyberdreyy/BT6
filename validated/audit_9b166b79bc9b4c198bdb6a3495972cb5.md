### Title
`store_and_process_block_signature` tallies peer acceptances toward the 70% signature threshold without checking this signer's own local rejection state, letting a `LocallyRejected` block flip to `LocallyAccepted` and be broadcast - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_signature`/`store_and_process_block_signature` never inspect the local `BlockInfo.state` before adding a peer's acceptance signature to the tally, and the state machine's `check_state` transition table explicitly permits `LocallyRejected -> LocallyAccepted`. A signer that locally/globally-through-its-own-node rejected a block can therefore have that rejection silently overwritten and re-broadcast as an acceptance once other signers (who validated the block differently, e.g., due to a momentarily inconsistent `SortitionsView`) push enough weight in.

### Finding Description
The claimed equality is: "once THIS signer sets `block_info.state = LocallyRejected` (or `GloballyRejected`) for a `signer_signature_hash`, no subsequent peer `BlockResponse::Accepted` for that same hash should ever cause this signer to count toward the 70% acceptance threshold or mark the block `LocallyAccepted`."

Tracing the code shows this equality does **not** hold:

- `handle_block_response` (`stacks-signer/src/v0/signer.rs:1789-1796`) routes any `BlockResponse::Accepted` straight into `handle_block_signature`, with no state check on `block_response`.
- `handle_block_signature` (`stacks-signer/src/v0/signer.rs:2372-2440`) looks up the local `BlockInfo` via `block_lookup_by_reward_cycle` and, if found, unconditionally calls `store_and_process_block_signature` — again no read of `block_info.state`.
- `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2443-2538`) stores the signature, and if the sending peer has already pre-committed (`has_committed == true`), it **skips** the pre-commit re-validation path (`handle_block_pre_commit`, which does call `check_block_against_signer_db_state`) and proceeds directly to tally weight and, once ≥70%, calls `block_info.mark_locally_accepted(true)` and `broadcast_signed_block`. At no point does it check whether `block_info.state` is already `LocallyRejected`/`GloballyRejected`.
- The state machine itself permits this: `check_state` in `stacks-signer/src/signerdb.rs:314-329` allows the transition `LocallyRejected -> LocallyAccepted` unconditionally (it is only blocked when the prior state was `GloballyRejected` or `GloballyAccepted`).

Crucially, the block *is* present in local signerdb with state `LocallyRejected` in the exact scenario the question describes: when the block was submitted to the node for validation (stored via `insert_block` at proposal time, `stacks-signer/src/v0/signer.rs:1717-1719`) and the node's response was a rejection (`handle_block_validate_reject`, mirroring the reject-branch pattern shown in `handle_block_validate_ok` at `stacks-signer/src/v0/signer.rs:1946-1959`, which calls `mark_locally_rejected` then `insert_block`). Because the block is stored (not the `check_block_against_state`-only-rejection path where nothing is inserted), `block_lookup_by_reward_cycle` succeeds later when a peer's acceptance arrives, and the tally proceeds.

An attacker with a single miner slot can craft a `BlockProposal` designed to be evaluated differently by different signers' nodes at the boundary of a burn/sortition event (a known, documented race — see `docs/signer-flows.md:274-297` on mid-reorg inconsistency) so that this signer's node rejects it via `/v3/block_proposal` while enough honest peers' nodes accept it and broadcast `BlockResponse::Accepted`. No majority-signer collusion or key compromise is needed; the attacker only crafts the proposal and lets honest signers gossip their (legitimately divergent) responses.

### Impact Explanation
This breaks the fail-closed safety property of the signer state machine: a block this signer's own node determined to be invalid can still be counted, marked `LocallyAccepted`, and pushed to the node via `broadcast_signed_block` -> `handle_post_block`, contributing this signer's weight toward finalizing a block it never itself validated as acceptable. This matches the Critical category "a rejection recounted as acceptance," directly undermining chain safety guarantees the local rejection was meant to enforce.

### Likelihood Explanation
Preconditions: the block must reach a stored `BlockInfo` with `LocallyRejected` state on this signer (achievable any time the node validation call returns Reject, or `check_block_against_signer_db_state` rejects post-validation), and at least 70% weight of peers must independently send `Accepted` for the identical `signer_signature_hash`. This requires only naturally-occurring or attacker-engineered timing divergence in `SortitionsView`/node state across signers, not collusion or a privileged role — one crafted proposal plus normal gossip suffices, and it is repeatable for any proposal that straddles such a race window.

### Recommendation
In `store_and_process_block_signature` (and/or `handle_block_signature`), check `block_info.state` before tallying: if it is already `LocallyRejected` or `GloballyRejected`, either ignore the peer acceptance for tally purposes or force a re-run of `check_block_against_signer_db_state` before allowing any transition back toward acceptance, mirroring the re-validation already done in `handle_block_pre_commit`. Additionally, tighten `check_state` in `signerdb.rs` so `LocallyRejected -> LocallyAccepted` is disallowed (or gated behind an explicit re-validation) rather than permitted unconditionally.

fn local_rejection_should_not_be_overturned_by_peer_acceptance() {
    // 1. Propose block B, submit for validation, receive validate-reject,
    //    driving block_info.state -> LocallyRejected via handle_block_validate_reject.

    let info_before = node.signer.signer_db.block_lookup(&hash_b).unwrap().unwrap();
    assert_eq!(info_before.state, BlockState::LocallyRejected);

    // 2. Feed enough peer BlockResponse::Accepted messages (each already pre-committed)
    //    for hash_b to cross the 70% weight threshold.
    for peer in honest_peers_with_70pct_weight {
        node.signer.process_event(
            &node.client,
            &mut sortition,
            Some(&SignerEvent::SignerMessages(vec![block_accepted_message(peer, &hash_b)])),
            &result_tx,
            1,
        );
    }

    // 3. Assert the local rejection was overturned.
    let info_after = node.signer.signer_db.block_lookup(&hash_b).unwrap().unwrap();
    assert_ne!(info_after.state, BlockState::LocallyRejected); // FAILS the fail-closed guard
    assert_eq!(info_after.state, BlockState::LocallyAccepted); // block re-broadcast despite local rejection
}

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
