### Title
Direct underlying donation to `IdleCDOCreditVault` inflates tranche price and lets a first depositor steal subsequent deposits - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.getContractValue()` includes the raw underlying balance of the CDO contract (`_contractTokenBalance(token)`) in NAV. Although `_managedContractValue()` and the comments claim unsolicited transfers are skimmed, `_skimDonatedAssets()` is only invoked on the guardian/owner `updateAccounting()` and `finalizeDefault()` paths — never on the user-facing `_deposit` / withdrawal-request path. An attacker can therefore perform a classic first-depositor/donation attack: deposit a minimal amount, donate a large underlying amount directly to the CDO, let the next depositor's `_updateAccounting()` crystallize the donation as "yield" at an inflated `priceAA`, then exit via a withdraw request redeeming nearly the entire victim deposit.

### Finding Description
- `getContractValue()` returns `strategyToken balance + raw token balance - unclaimedFees` (`contracts/IdleCDOCreditVault.sol:125-128`). Deposits are forwarded to the strategy (`IIdleCDOStrategy(strategy).deposit(_amount)`, line 211) and become strategy tokens, but a direct `token.transfer(cdo, D)` sits in the raw token balance and is indistinguishable from NAV.
- `_deposit()` calls `_updateAccounting()` *before* minting (lines 200-208). The donation produces `totalGain = D`, split between AA/BB via `_virtualPriceAux`, which pushes `priceAA` up to roughly `(seed + D - fee) / supply` (lines 287-336).
- Shares are minted at the saved post-donation price: `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` (line 346). The victim's deposit therefore buys almost no tranche tokens, while the attacker's seed shares now represent nearly the whole NAV including the victim's funds.
- The attacker exits through the epoch withdrawal flow (`requestWithdraw` in `IdleCDOEpochVariant`), whose receipt is computed from the inflated `_tranchePrice`/`virtualPrice`, paying out far more than the seed deposit — effectively `D + victimDeposit - fees`.
- The `_skimDonatedAssets()` mitigation (`IdleCDOEpochVariant.sol:794`) sends raw underlying to `feeReceiver`, but it is only called inside the privileged `updateAccounting()` (line 159) and `finalizeDefault()` (line 197). It never runs during a user deposit, so it does not stop the attack unless a guardian happens to skim between the donation and the victim's deposit — a race the attacker controls by executing donation → victim-deposit trigger timing themselves, or simply donating immediately before a queued/observed pending deposit in the same buffer phase.

### Impact Explanation
Direct theft of user funds: in a buffer epoch, the victim loses essentially their entire deposit (minus the fee percentage taken into `unclaimedFees`), and the attacker recovers the donation plus the victim's principal. Loss scales with the victim's deposit size; no privileged role misbehaves and no oracle manipulation is required. Quantified: with seed `s`, donation `D`, victim deposit `V`, attacker share ≈ `V·s/(s+D)` of victim NAV — with `D >> V` the victim's loss approaches `V·(1 − fee)`.

### Likelihood Explanation
Low attacker cost beyond temporary donation capital (fully recovered). Requires the vault to be in a deposit-open phase (buffer epoch) and a deposit to land after the donation — realistically the attacker donates right before their own second deposit or before a known queued deposit; even without a specific victim, the price remains inflated until a guardian manually calls `updateAccounting`/`finalizeDefault`, so any depositor is harmed. No timing of honest privileged calls is needed for the attack itself.

### Recommendation
Skim raw underlying inside `_deposit` (and any withdrawal-request accounting path) before `_updateAccounting()`, e.g. call `_skimDonatedAssets()` or subtract the unswept `token` balance from `getContractValue()`/`nav`. Alternatively track an internal `expectedUnderlying` counter credited only on protocol-initiated transfers and exclude `balanceOf(token)` from NAV entirely. Additionally enforce a minimum initial deposit or mint a portion of first-deposit shares to a dead address to dampen share-inflation edge cases.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOCreditVault} from "../contracts/IdleCDOCreditVault.sol"; // epoch variant deployment
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

/// Buffer-phase donation attack on a live IdleCDO credit vault (fork test).
/// Assumes: vault initialized, epoch in buffer (deposits open), AA deposits enabled,
/// attacker holds `token` and passes wallet screening (KYC/Keyring whitelist or open pool).
contract DonationInflationTest is Test {
    IdleCDOCreditVault cdo;      // forked IdleCDOEpochVariant / IdleCDOCreditVault instance
    IERC20Detailed token;        // underlying

    address attacker = address(0xA);
    address victim   = address(0xB);

    uint256 SEED   = 1e6;          // minimal deposit (above any guarded minimum)
    uint256 DONATE = 1_000_000e6;  // large direct transfer
    uint256 VICTIM = 500_000e6;    // victim deposit

    function testDonationInflatesPriceAndDrainsVictim() public {
        // 1) Epoch in buffer: attacker seeds AA tranche
        token.approve(address(cdo), SEED);
        cdo.depositAA(SEED);                          // minted ~ SEED shares at price = 1

        // 2) Attacker donates underlying straight to the CDO (not via strategy)
        token.transfer(address(cdo), DONATE);         // raw token balance, counted by getContractValue()

        // 3) Victim deposits during the same buffer phase.
        //    _deposit() -> _updateAccounting() treats DONATE as gain -> priceAA explodes.
        vm.prank(victim);
        token.approve(address(cdo), VICTIM);
        vm.prank(victim);
        cdo.depositAA(VICTIM);                        // minted ~= VICTIM * 1e18 / inflatedPrice ~ 0

        uint256 attackerShares = IERC20Detailed(cdo.AATranche()).balanceOf(attacker);
        uint256 victimShares   = IERC20Detailed(cdo.AATranche()).balanceOf(victim);
        assertGt(attackerShares / (victimShares + 1), 1);  // attacker holds ~all supply

        // 4) Attacker requests withdrawal at the inflated price
        vm.prank(attacker);
        cdo.requestWithdraw(attackerShares, cdo.AATranche()); // epoch-variant request flow

        // ... epoch advances / receipt claim ...
        // Attacker payout ~= SEED + DONATE + VICTIM * (1 - fee) — victim principal stolen.
        assertGt(token.balanceOf(attacker), SEED + DONATE + VICTIM * 9 / 10);
        // Victim's claim is dust.
        assertLt(token.balanceOf(victim), VICTIM / 10);
    }
}
```

Key citations: NAV includes raw token balance at `IdleCDOCreditVault.sol:125-128`; accounting runs before minting and donation is crystallized as gain at `IdleCDOCreditVault.sol:200-208` and `:230-246`; shares mint at the inflated saved price at `IdleCDOCreditVault.sol:344-347`; the skim mitigation exists only on privileged paths (`IdleCDOEpochVariant.sol:157-161`, `:794-796`).

Caveat: exact payout mechanics depend on the epoch-variant withdraw-request receipt computation (`requestWithdraw`/`_calcInterestWithdrawRequest`), which I did not fully read; the receipt is NAV-derived, so the inflated claim stands, but a Foundry PoC should confirm the claim step end-to-end.
