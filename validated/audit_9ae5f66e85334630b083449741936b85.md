### Title
`WebAuthnController.BeginRegistration`/`FinishRegistration` allow persistent MFA credential enrollment without step-up re-authentication or role restriction - ([File: core/web/webauthn_controller.go])

### Summary
The `/v2/enroll_webauthn` routes are wrapped only with `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)` and no role wrapper (`RequiresEditRole`/`RequiresAdminRole`) and no password re-verification, unlike other sensitive self-account endpoints in the same controller family (`NewAPIToken`, `DeleteAPIToken`) that call `TestPassword` before acting. This lets any authenticated session — regardless of role (`view`) — enroll a brand-new, persistent WebAuthn credential for the current user.

### Finding Description
The route registration in `core/web/router.go` shows: [1](#0-0) 
`wa.BeginRegistration` and `wa.FinishRegistration` are mounted under `authv2` with no `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, unlike almost every other mutating endpoint in the same file (keys, jobs, bridges, external initiators, etc.), which are consistently gated with `auth.RequiresEditRole`/`auth.RequiresAdminRole`.

Inside `BeginRegistration`, the only check performed is that a valid authenticated user exists in context, then it immediately proceeds to generate WebAuthn registration challenge options: [2](#0-1) 

`FinishRegistration` similarly only checks `auth.GetAuthenticatedUser` and then persists the new credential via `sessions.AddCredentialToUser`: [3](#0-2) 

Contrast this with the established pattern for other security-sensitive, self-account-mutating actions in `core/web/user_controller.go`: `NewAPIToken` and `DeleteAPIToken` both require the caller to supply and successfully re-verify the account password via `TestPassword` before the action is committed: [4](#0-3) [5](#0-4) 

`UpdatePassword` similarly requires the old password to match: [6](#0-5) 

No equivalent step-up check (password re-entry) exists for WebAuthn credential enrollment, even though registering a hardware/software authenticator is at least as security-sensitive as rotating an API token — a successfully enrolled credential becomes a durable, attacker-controlled authentication factor tied to the victim account, independent of the short-lived session/token that was used to enroll it.

### Impact Explanation
An attacker who obtains a valid session cookie or API token for a victim account — regardless of whether that credential has `view` (read-only) role — can silently register their own WebAuthn authenticator against that account. This converts a transient/leaked credential into a durable authentication method, extending the attacker's access window beyond the lifetime or revocation of the original stolen session/token, and undermining any subsequent MFA-based protections the victim believes are in place. This maps to Chainlink's authentication/authorization-bypass bounty class (unauthorized persistent credential enrollment on another/hijacked account context).

### Likelihood Explanation
Preconditions are minimal: possession of any valid session cookie or API token for the target account (any role, including `view`), which the threat model treats as attacker-controlled (hijacked short-lived session token). No admin/edit role, no password, and no additional secret is required — the endpoint is reachable via a simple `GET /v2/enroll_webauthn` followed by `POST /v2/enroll_webauthn` with a valid WebAuthn assertion generated client-side. This is fully repeatable for any authenticated identity.

### Recommendation
Require re-authentication (current password confirmation, similar to `NewAPIToken`/`DeleteAPIToken`/`UpdatePassword`) before allowing `BeginRegistration`/`FinishRegistration` to add a new WebAuthn credential, and/or invalidate/limit this action to sessions established through primary password authentication (not solely API token) so that a leaked long-lived API token or hijacked session cannot be used to durably extend access via MFA credential enrollment.

### Proof of Concept
Add a handler-level integration test in `core/web/webauthn_controller_test.go` (or a new test file) that:
1. Creates a user session via `AuthenticateBySession` only (no password re-entry step) with a low-privilege role.
2. Calls `GET /v2/enroll_webauthn` and asserts it currently returns `200 OK` with registration options (demonstrating the gap) — the fix should require the request to fail with `401`/`403` unless a fresh password confirmation (e.g., an `oldPassword`/`password` field) is supplied, mirroring the assertions in `TestUserController_NewAPIToken` for `TestPassword` mismatch behavior found in `core/web/user_controller_test.go`.
3. Calls `POST /v2/enroll_webauthn` with a crafted WebAuthn attestation and asserts that, post-fix, the request is rejected without a valid re-authentication step, and that `sessions.AddCredentialToUser` is never invoked in that case.

func (w *WebAuthnController) BeginRegistration(c *gin.Context) {
	ctx := c.Request.Context()
	user, ok := auth.GetAuthenticatedUser(c)
	if !ok {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("failed to obtain current user from context"))
		return
	}

	orm := w.App.AuthenticationProvider()
	uwas, err := orm.GetUserWebAuthn(ctx, user.Email)
	if err != nil {
		w.App.GetLogger().Errorf("failed to obtain current user MFA tokens: error in GetUserWebAuthn: %+v", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	webAuthnConfig := w.App.GetWebAuthnConfiguration()

	options, err := w.inProgressRegistrationsStore.BeginWebAuthnRegistration(*user, uwas, webAuthnConfig)
	if err != nil {
		w.App.GetLogger().Errorf("error in BeginWebAuthnRegistration: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	optionsp := presenters.NewRegistrationSettings(*options)

	jsonAPIResponse(c, optionsp, "settings")
```

func (w *WebAuthnController) FinishRegistration(c *gin.Context) {
	ctx := c.Request.Context()
	user, ok := auth.GetAuthenticatedUser(c)
	if !ok {
		logger.Sugared(w.App.GetLogger()).AssumptionViolationf("failed to obtain current user from context")
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	orm := w.App.AuthenticationProvider()
	uwas, err := orm.GetUserWebAuthn(ctx, user.Email)
	if err != nil {
		w.App.GetLogger().Errorf("failed to obtain current user MFA tokens: error in GetUserWebAuthn: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	webAuthnConfig := w.App.GetWebAuthnConfiguration()

	credential, err := w.inProgressRegistrationsStore.FinishWebAuthnRegistration(*user, uwas, c.Request, webAuthnConfig)
	if err != nil {
		w.App.GetLogger().Errorf("error in FinishWebAuthnRegistration: %s", err)
		jsonAPIError(c, http.StatusBadRequest, errors.New("registration was unsuccessful"))
		return
	}

	if sessions.AddCredentialToUser(ctx, w.App.AuthenticationProvider(), user.Email, credential) != nil {
		w.App.GetLogger().Errorf("Could not save WebAuthn credential to DB for user: %s", user.Email)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// Forward registered credentials for audit logs
	credj, err := json.Marshal(credential)
	if err != nil {
		w.App.GetLogger().Errorf("error in Marshal credentials: %s", err)
		jsonAPIError(c, http.StatusBadRequest, errors.New("registration was unsuccessful"))
		return
	}
	w.App.GetAuditLogger().Audit(audit.Auth2FAEnrolled, map[string]any{"email": user.Email, "credential": string(credj)})

	c.String(http.StatusOK, "{}")
```
