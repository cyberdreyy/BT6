### Title
Instant-withdraw receipts can be claimed before their funds are collected, draining underlyings reserved for other users' funded withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns the user's receipt strategy tokens and pays out from the strategy's underlying balance without verifying that the corresponding instant-withdraw funds were ever collected via `collectInstantWithdrawFunds`. This is the analog of the CVE-2021-4067 use-after-free class: a payout is made against a "freed"/unbacked receipt, concretely consuming underlyings that the strategy is holding in trust for *other* users' already-funded (but not yet claimed) normal withdraw requests.

### Finding Description
In `requestInstantWithdraw`, the CDO's strategy tokens are burned and the user is minted receipt tokens; `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` are incremented, but no underlying is moved at request time [1](#0-0) . The actual funding only happens later when the CDO calls `collectInstantWithdrawFunds`, which pulls underlying from the CDO into the strategy and decrements `pendingInstantWithdraws` [2](#0-1) .

`claimInstantWithdrawRequest` contains no check that this collection occurred, no per-epoch funding marker, and no timing gate — it burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim` [3](#0-2) . On the CDO side the only gate is `allowInstantWithdraw` [4](#0-3) .

Meanwhile, the strategy's underlying balance legitimately holds funds that do not belong to instant claimants: `collectWithdrawFunds` transfers borrower-funded withdraw amounts into the strategy, where they sit until funded receipts are claimed via `_claimFundedWithdrawRequest` → `_transferFundedClaim` [5](#0-4) . `_transferFundedClaim` only ring-fences `defaultRecoveryReserve`; there is no equivalent reservation for already-funded normal claims [6](#0-5) .

So in the buffer period after `stopEpoch` (normal withdraws funded into the strategy, instant withdrawals enabled, epoch not yet started / instant funds not yet collected), an attacker who requested an instant withdraw during the running epoch can call `claimInstantWithdrawRequest` immediately and be paid out of other users' funded-claim liquidity. The request's own backing (`pendingInstantWithdraws`) is still outstanding — the claim is paid by a balance the protocol believes belongs to someone else.

### Impact Explanation
Direct theft / insolvency: the instant-withdraw requester receives underlying up to the full strategy balance earmarked for funded withdraw receipts. Legitimate claimants of those funded receipts then revert on `safeTransfer` in `_transferFundedClaim` when they try to claim — a permanent loss for them up to the funded-claim reserve, equal to the attacker's instant request amount (bounded by their deposited principal, i.e. an unprivileged lender-sized theft with no privileged participation).

### Likelihood Explanation
Requires: instant withdrawals enabled (`allowInstantWithdraw`), the attacker holding tranche tokens and requesting an instant withdraw during a running epoch, and a non-zero strategy underlying balance at claim time (true whenever funded normal withdraw claims are unclaimed, which is common since claims are permissionless and often delayed across epochs). No privileged role is the attacker; the sequence is entirely EOA-driven around honest manager/borrower calls.

Caveat: whether the CDO additionally gates `claimInstantWithdrawRequest` on the epoch having started (e.g. an instant-withdraw delay counted from `startEpoch`) could narrow the window; the strategy itself records no funding marker, so any claim path reachable before `collectInstantWithdrawFunds` is exploitable, and a delay measured from `startEpoch` does not protect the pre-`startEpoch` buffer window.

### Recommendation
Track funded-vs-unfunded instant claims: either (a) record, per epoch or globally, the amount of instant-withdraw underlying actually collected via `collectInstantWithdrawFunds` and cap `claimInstantWithdrawRequest` payouts at the collected amount, or (b) account for a reserved `fundedClaimsReserve` (sum of outstanding `withdrawsRequests`/APR0 settled amounts and collected instant funds) inside `_transferFundedClaim` so unbacked instant claims cannot spend other claimants' reserves. Alternatively, gate `claimInstantWithdrawRequest` to revert while `pendingInstantWithdraws` still covers the requester's receipt epoch.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Setup: deposit victimAA and attackerAA, enable instant withdraws.
uint256 victimTranche = _depositWithUser(victim, 100_000 * ONE_SCALE);
uint256 attackerTranche = _depositWithUser(attacker, 50_000 * ONE_SCALE);

// Epoch runs; victim requests a normal withdraw, attacker requests instant withdraw.
_startEpochAndCheckPrices(0);
vm.prank(victim);   cdoEpoch.requestWithdraw(victimTranche, address(AAtranche));
vm.prank(attacker); cdoEpoch.requestInstantWithdraw(attackerTranche); // via CDO wrapper

// Honest manager stops epoch; borrower repays -> normal funded claims land in the strategy.
_stopEpochAndCheckPrices(0, apr, expectedFunds); // collectWithdrawFunds() moves underlying in
assertGt(underlying.balanceOf(address(strategy)), 0);

// KEY: no startEpoch / collectInstantWithdrawFunds has occurred.
// Attacker claims the unfunded instant receipt and is paid from victim's funded reserve.
uint256 pre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
assertGt(underlying.balanceOf(attacker), pre);          // paid out of other users' reserve
assertGt(strategy.pendingInstantWithdraws(), 0);        // attacker's backing never collected

// Victim's funded claim now reverts / underpays -> direct theft of funded claims.
vm.prank(victim);
vm.expectRevert();
cdoEpoch.claimWithdrawRequest();
```

If a concrete run shows the CDO-layer `claimInstantWithdrawRequest` reverting before `startEpoch`, the finding reduces to "no valid analog" and the queue/claim ordering should be re-examined; on the code indexed here, no such gate exists in `IdleCreditVault.claimInstantWithdrawRequest`.

    _onlyIdleCDO();

    // burn strategy tokens from cdo

    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    instantWithdrawsRequests[_user] += _amount;

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
