### Title
Loss-adjusted withdraw receipts escape the haircut when the loss epoch is not `lastWithdrawRequest`, draining funded reserves at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external tar bug is a check-then-act mismatch across an indirection: `fs::metadata()` validates the object reached by following a symlink, while `chmod` then acts on the symlink itself, so the permission change lands on an unintended target. In `IdleCreditVault`, the same pattern exists with `lastWithdrawRequest[_user]` playing the role of the symlink: both the new-request guard and `_claimLossAdjustedWithdrawRequest` resolve exactly one epoch through that single pointer and check `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, while the funded-claim path then acts on the *aggregate* `withdrawsRequests[_user]`, which spans every request epoch. A user holding receipts in more than one epoch can therefore have a loss-haircut applied to one epoch's price map while the payout logic — following only the latest-epoch pointer — pays the whole balance at par.

### Finding Description
`requestWithdraw` stores each receipt per epoch (`withdrawsRequestsByEpoch[_user][currentEpoch]`) and also accumulates a global `withdrawsRequests[_user]`, and the code comments explicitly acknowledge that users may hold requests from multiple epochs unclaimed ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests"). [1](#0-0) [2](#0-1) 

When a claim runs, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which derives the loss epoch solely from `lastWithdrawRequest[_user]` and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch]` is unset. [3](#0-2)  Control then falls into `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` — the sum across *all* request epochs — at full par via `_transferFundedClaim`. [4](#0-3) 

The guard in `requestWithdraw` that is meant to keep this consistent has the identical single-pointer flaw: it only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, so it cannot see a loss price recorded under any other epoch in which the user holds receipts. [5](#0-4)  `_clearWithdrawClaimForEpoch` only strips the matched epoch's slice out of `withdrawsRequests[_user]`, so any epoch the pointer misses is never haircutted. [6](#0-5) 

Concretely: an attacker makes withdraw requests in two consecutive epochs without claiming. A `stopEpochWithDuration` loss is recorded under the earlier request epoch (or under a later epoch that is then superseded in `lastWithdrawRequest` by bookkeeping ordering). Because the claim path only dereferences `lastWithdrawRequest`, the epoch carrying the non-par `lossRecoveryPrice` is never matched, `_claimLossAdjustedWithdrawRequest` returns 0, and the entire multi-epoch balance is paid at 1:1 from funded underlying.

### Impact Explanation
The broken invariant is the loss waterfall: receipts recorded for a loss epoch are supposed to settle at `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, but are instead settled at par. The overpayment comes directly out of the strategy's funded underlying (`_transferFundedClaim`), which is the same pool backing other users' pending receipts — the attacker extracts more than their haircut-adjusted entitlement and leaves later claimants with an under-collateralized reserve (insolvency for the residual claimants). Loss magnitude equals `receipt * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`, i.e. the full haircut that should have been applied; with a deep loss adjustment this approaches the entire receipt value.

### Likelihood Explanation
The attacker needs only to be a KYC-passed tranche holder who places withdraw requests across two epochs before claiming — the code explicitly supports carrying multiple unclaimed epochs, and `requestWithdraw`'s guard cannot detect the mismatch because it dereferences the same single `lastWithdrawRequest` pointer. [7](#0-6)  Triggering requires a `stopEpochWithDuration` loss event keyed to a request epoch other than the attacker's last — an honest manager action during a partial borrower shortfall, i.e. exactly the stressed condition loss adjustment exists for. No privileged misbehavior is required; the attacker just sequences ordinary `requestWithdraw`/`claimWithdrawRequest` calls around the epoch boundary.

### Recommendation
Do not resolve a single epoch through `lastWithdrawRequest` when validating or settling claims. Either (a) iterate/maintain the set of request epochs per user and apply `lossRecoveryPriceByEpoch[e]` to each epoch's slice before summing the funded payout, or (b) revert/force settlement whenever any epoch with receipts in `withdrawsRequestsByEpoch[_user][*]` has a nonzero `lossRecoveryPriceByEpoch`, and block `requestWithdraw` while *any* held epoch — not only the last — carries an unclaimed loss-adjusted receipt. A cheaper invariant: compute the funded-claim amount as the sum over per-epoch entries after per-epoch haircut, rather than paying the raw `withdrawsRequests[_user]` aggregate.

```solidity
function testLossEpochEscapeViaLastWithdrawRequest() external {
    // 1. KYC'd attacker deposits AA, epoch 0 runs and stops normally.
    idleCDO.depositAA(10000 * ONE_SCALE);
    _transferBurnedTrancheTokens(attacker, true);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, expectedInterest);

    // 2. Attacker requests withdraw in epoch 1 (lastWithdrawRequest = 1).
    cdoEpoch.requestWithdraw(amount1, address(AAtranche));
    _startEpochAndCheckPrices(1);

    // 3. Epoch 1 ends with a partial loss: manager calls
    //    stopEpochWithDuration(_lossAmount > 0) so
    //    lossRecoveryPriceByEpoch[1] is set < RECOVERY_FULL.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(lossAmount, duration);

    // 4. Attacker requests again in epoch 2 while the epoch-1 receipt
    //    is unclaimed — guard only checks lossRecoveryPriceByEpoch[2-or-last],
    //    which is 0 at request time, so it passes.
    cdoEpoch.requestWithdraw(amount2, address(AAtranche));
    _startEpochAndCheckPrices(2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, interest2); // normal stop, epoch 2 funded at par

    // 5. Claim: _claimLossAdjustedWithdrawRequest dereferences
    //    lastWithdrawRequest (=2) -> lossRecoveryPriceByEpoch[2]==0 -> 0.
    //    _claimFundedWithdrawRequest pays withdrawsRequests[attacker]
    //    = amount1 + amount2 fully at par.
    uint256 balBefore = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balBefore;

    // 6. Assert the epoch-1 receipt escaped its haircut.
    assertGt(paid, amount2 + amount1 * lossRecoveryPriceByEpoch[1] / RECOVERY_FULL);
}
```

Caveat: I could not open the write site of `lossRecoveryPriceByEpoch` (indexed under `stopEpochWithDuration`/`prepareStopEpoch` accounting) within the available iterations, so the exact epoch key used when recording the loss price should be confirmed during PoC development — if the loss price is always keyed identically to `lastWithdrawRequest`, the request-side guard at lines 263–270 still fails to inspect *earlier* held epochs, which is the alternative ordering that leaves the same aggregate-payout gap exploitable.
