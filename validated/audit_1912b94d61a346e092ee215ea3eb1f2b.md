### Title
Unbounded per-slot growth of `SlotVoteTracker.voted` via cheap zero-stake vote-account creation - (File: core/src/cluster_info_vote_listener.rs)

### Summary
`SlotVoteTracker.voted` is a `HashMap<Pubkey, bool>` that records every distinct vote pubkey observed voting for a slot, with no cap on the number of distinct pubkeys per slot. An attacker who can cheaply create many vote accounts and submit rate-limited `TowerSync` vote transactions from each can grow this map (and the surrounding `VoteTracker::slot_vote_trackers`) proportionally to the number of vote accounts created, independent of stake.

### Finding Description
`VoteTracker::slot_vote_trackers` is a `RwLock<HashMap<Slot, Arc<RwLock<SlotVoteTracker>>>>` [1](#0-0) , and entries are lazily created via `get_or_insert_slot_tracker`, which simply does `entry(slot).or_default()` with no limit on the number of slots or the size of each tracker [2](#0-1) . Each `SlotVoteTracker` holds a `voted: HashMap<Pubkey, bool>` that records "pubkeys that have voted for this slot" and whether the vote was also seen on gossip [3](#0-2) . Unlike `optimistic_votes_tracker`, which is stake-weighted and additionally rate-limited per pubkey by `MAX_VOTE_HASHES_PER_PUBKEY_PER_SLOT` [4](#0-3) , the `voted` map has no such per-pubkey or aggregate cap — it is keyed purely by vote-account pubkey and grows one entry per distinct pubkey that votes for the slot, regardless of stake. The only bound present, `MAX_VOTE_SLOT_DISTANCE_FROM_ROOT = 50_000` [5](#0-4) , limits how far behind root a slot tracker is retained, not how many distinct pubkeys can populate `voted` within that 50,000-slot window.

Because vote-instruction execution success does not depend on the amount of stake behind the voting account, a freshly created, zero-stake vote account whose `TowerSync` transaction lands in a block will still be forwarded through the replay vote pipeline into `track_new_votes_and_notify_confirmations`/`filter_and_confirm_with_new_votes`, which insert the new pubkey into `w_slot_tracker.voted` for that slot. Repeating this with a new vote-account pubkey each time (subject only to the sendTransaction rate cap) causes `voted.len()` — and thus `SlotVoteTracker`/`VoteTracker` memory — to grow linearly with the number of distinct vote accounts the attacker funds, not with anything the node can bound via explicit request/subscription limits.

### Impact Explanation
This is unbounded heap growth on the validator process driven entirely by cheap, permissionless on-chain actions (vote-account creation) combined with a rate-capped `sendTransaction` stream, rather than any privileged access. It falls into the "cost of one subscription/request not bounded by explicit limits, but by on-chain data volume" category — degrading node memory/CPU over time without ever exceeding the stated RPC rate limit.

### Likelihood Explanation
Feasible and repeatable by any unprivileged party: creating a vote account only requires paying minimal rent/fees, and submitting one `TowerSync` transaction per vote account at ≤1 call per `CLUSTER_SLOT_TIME_TARGET/2` fully satisfies the attacker model. Because there is no existing check tying `voted` map insertion to stake or to a fixed cap on distinct pubkeys per slot, the growth is directly proportional to the number of vote accounts the attacker is willing to fund, which is cheap and scriptable.

### Recommendation
Bound `SlotVoteTracker.voted` (and/or the broader `slot_vote_trackers` map) by either: (a) filtering out zero/low-stake vote pubkeys before insertion, similar to the stake gating already used for `optimistic_votes_tracker`, or (b) imposing an explicit maximum number of tracked pubkeys per slot (with eviction/LRU) independent of on-chain vote-account count, so memory cost is capped by node-configured limits rather than attacker-controlled on-chain state.

### Proof of Concept
Integration test plan:
1. In a test harness around `VoteTracker`/`cluster_info_vote_listener`, create `N` (e.g., 10,000) distinct `Pubkey`s to simulate distinct freshly created vote accounts.
2. For each pubkey, construct a valid `ReplayVoteMessage`/`TowerSync` vote referencing the same target slot `S`, and feed them through the code path that ultimately calls into `VoteTracker::get_or_insert_slot_tracker(S)` and inserts into `voted`, throttled to simulate ≤1 per `CLUSTER_SLOT_TIME_TARGET/2` real-time (or bypass timing in test and assert only on data-structure growth).
3. After processing, assert `vote_tracker.get_slot_vote_tracker(S).unwrap().read().unwrap().voted.len() == N`, demonstrating unbounded, uncapped linear growth with attacker-controlled pubkey count.
4. Compare against an expected fixed upper bound (e.g., assert failure if `voted.len()` exceeds some configured cap) to show no such cap currently exists in `SlotVoteTracker`/`VoteTracker`.

impl VoteTracker {
    fn get_or_insert_slot_tracker(&self, slot: Slot) -> Arc<RwLock<SlotVoteTracker>> {
        if let Some(slot_vote_tracker) = self.slot_vote_trackers.read().unwrap().get(&slot) {
            return slot_vote_tracker.clone();
        }
        let mut slot_vote_trackers = self.slot_vote_trackers.write().unwrap();
        slot_vote_trackers.entry(slot).or_default().clone()
    }
