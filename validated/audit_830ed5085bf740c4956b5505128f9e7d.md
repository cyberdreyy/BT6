### Title
Signer-identity collision in `block_rejection_signer_addrs` corrupts rejection-weight tallying across unrelated blocks - ([File: stacks-signer/src/signerdb.rs])

### Summary
The `block_rejection_signer_addrs` table, which backs the 30%-weight "globally rejected" tally for block proposals, is keyed with `PRIMARY KEY (signer_addr)` instead of a composite key scoped to the block being rejected. Because a signer's address is stable across every block it ever evaluates (unlike a block signature, which is unique per proposal), this schema can hold at most one rejection row per signer for its *entire lifetime*, not one per (block, signer) pair.

### Finding Description
The table is declared as: [1](#0-0) 

Compare this to `block_signatures`, whose `PRIMARY KEY (signature)` is safe only because an ECDSA signature is intrinsically unique per (block, signer) pair — a signer's signature over block A can never collide with its signature over block B: [2](#0-1) 

`signer_addr`, however, is a fixed identity that recurs across every block a signer ever rejects. With `PRIMARY KEY (signer_addr)`, the row for a given signer address can only ever describe its most recent rejection. This is read by `store_and_process_block_rejection`, which uses `get_block_rejection_signer_addrs(block_hash)` to compute `total_reject_weight` against `NakamotoBlockHeader::compute_voting_weight_threshold` and decide whether to call `mark_globally_rejected`: [3](#0-2) [4](#0-3) 

Depending on the exact conflict-resolution clause used by `add_block_rejection_signer_addr` (which I was unable to retrieve before running out of tool budget — the effective SQL is either an `INSERT OR REPLACE` or an `INSERT OR IGNORE`/plain `INSERT` guarded by the PK), the practical effect is one of two safety-relevant failures:

- If the insert is `INSERT OR REPLACE` keyed on `signer_addr`: once signer S rejects block B (an entirely unrelated later proposal, e.g. in a different tenure), S's row silently changes to point at B, and `get_block_rejection_signer_addrs(A)` for the *earlier* block A no longer returns S. Block A's rejection tally can permanently lose weight it had already legitimately accumulated, so `total_reject_weight.saturating_add(min_weight) <= total_weight` may keep evaluating false forever, and A never reaches the `GloballyRejected` verdict even though enough signers rejected it. Since `check_block_against_state`/`handle_block_proposal` route re-evaluation partly on `has_reached_consensus()`, an old bad proposal that should have died can instead sit in limbo consuming signer bookkeeping and StackerDB slots.
- If the insert is `INSERT OR IGNORE`/plain insert guarded by a PK check: the *first* rejection a signer ever records for any block permanently occupies its row, and the signer's address can never be recorded as rejecting a different (later, legitimate) bad block again. This has a stronger effect: `total_reject_weight` computed by `compute_reject_code_signing_weight`/`get_block_rejection_signer_addrs` under-counts real rejections for every subsequent block, for every signer that has rejected at least one prior block. Because 30% rejection is the *only* path to `GloballyRejected`, invalid/conflicting proposals can be starved of a majority-reject verdict indefinitely as the fleet ages — a systemic liveness wedge on the reject side of the state machine.

This is the closest structural analog to CVE-2021-23449 in scope: vm2's flaw was that a single shared, insufficiently-namespaced key (the prototype) let one context's writes silently corrupt state that a different, supposedly-isolated context depended on for its security decision. Here, the shared, insufficiently-namespaced key is `signer_addr`, and the corrupted decision is the block-rejection weight tally that gates `mark_globally_rejected` — an equality (`aggregated rejection weight` vs `actual set of signers who rejected this specific block`) that the schema cannot preserve across more than one block per signer.

### Impact Explanation
Either variant breaks the "aggregated-weight vs verified-accepts/rejects" invariant the report's rules flag as in-scope-critical/high: the signer set's global-rejection bookkeeping for a given `signer_signature_hash` no longer reflects the true set of signers who rejected it, once any signer involved has rejected a second, unrelated block. This can wedge a bad/conflicting proposal out of ever reaching `GloballyRejected`, tying up signer resources on stale proposals and undermining the fast-rejection path the pre-commit/threshold design relies on (see `docs/signer-flows.md` sections 5–7 on how rejection weight is meant to make "70% is now impossible" terminate a proposal promptly).

### Likelihood Explanation
This requires no majority collusion and no crafted signature — it is triggered by completely ordinary operation: any single miner (malicious or merely producing two different rejected proposals, e.g. one bad tenure-start block followed later by another) causes multiple genuine, honestly-generated rejections from the same signer address across the block's lifetime, which is exactly the workload the reward-cycle/tenure-based flow guarantees will recur. No special privileges beyond normal miner/gossip behavior are needed.

### Recommendation
Change the schema's primary key to `PRIMARY KEY (signer_signature_hash, signer_addr)` (with a supporting index, as is already done for `block_signatures_on_signer_signature_hash` and `block_rejection_signer_addr_on_block_signature_hash`), and add/verify a migration that rebuilds the table with the composite key so existing installations are not left with the collapsed, address-only rows. Audit `add_block_rejection_signer_addr`'s exact SQL to confirm which failure mode (silent overwrite vs. silent no-op) is currently occurring, and add a regression test that has the same signer address reject two different `signer_signature_hash` values and asserts both rejections are independently retained by `get_block_rejection_signer_addrs`.

### Proof of Concept
1. Signer S evaluates block proposal A (any tenure) and it fails validation; `store_and_process_block_rejection` calls `add_block_rejection_signer_addr(A_hash, S, reason)`, inserting `(A_hash, S)` into `block_rejection_signer_addrs`.
2. Enough other signers also reject A such that S's weight is the missing piece needed to cross the 30% blocking-minority threshold, but A is still short of `GloballyRejected` pending confirmation of S's vote being retained.
3. Before that threshold check is retried, the same miner (or a different one) proposes an unrelated block B at a later height/tenure. S's local validation also rejects B, and `add_block_rejection_signer_addr(B_hash, S, reason)` is called.
4. Because the table's primary key is `signer_addr` alone, this second insert collides with (and, depending on the exact conflict clause, overwrites or is silently dropped against) S's row from step 1.
5. `get_block_rejection_signer_addrs(A_hash)` in a later call to `store_and_process_block_rejection` for A no longer returns S (or never returned it for B), so `total_reject_weight` for A never reflects S's actual rejection, and `mark_globally_rejected` for A can be permanently delayed or never triggered despite sufficient real rejecting weight having been observed by the fleet.

Note: I was unable to retrieve the body of `add_block_rejection_signer_addr` (its exact `INSERT` clause) before tool budget ran out, so I cannot state with certainty which of the two collision modes (overwrite vs. no-op) is implemented — this should be the first thing verified when triaging this finding, as it determines the exact steady-state failure mode. The schema-level defect (`PRIMARY KEY (signer_addr)` on a per-block rejection table) is confirmed directly from the source shown above.
