### Title
Stale `block_pre_commits` entries are never invalidated when a signer later rejects the same block - ([File: stacks-signer/src/signerdb.rs])

### Summary
The signer's `block_pre_commits` table records every signer address that has broadcast a pre-commit for a given block, and this table is the sole source used to compute the pre-commit weight tally that gates whether *this* signer produces a signature (`handle_block_pre_commit`). Unlike the accept/reject pair for final signatures — where `add_block_signature` explicitly deletes a stale `block_rejection_signer_addrs` row for the same signer/block, and `add_block_rejection_signer_addr` explicitly refuses to record a rejection once a signature exists — there is no equivalent cleanup between a signer's earlier pre-commit and a later rejection from that same signer for the same block. This is the same bug shape as the referenced report: one code path (`add_block_signature`) performs `delete`/reconciliation of a sibling table, while an analogous path (rejection processing) does not perform the matching cleanup for `block_pre_commits`.

### Finding Description
`add_block_signature` performs an explicit reconciliation step before inserting a signature: [1](#0-0) 

and `add_block_rejection_signer_addr` refuses to overwrite an existing signature with a rejection: [2](#0-1) 

These two functions form a consistent, symmetric pair guarding the *signature* vs *rejection* equality. However, the *pre-commit* vs *rejection* equality has no such guard. `handle_block_pre_commit` unconditionally records the pre-commit and then tallies the pre-commit weight purely from `block_pre_commits`, with no filtering against any later rejection recorded for the same signer/block: [3](#0-2) 

Meanwhile, when this same signer subsequently determines the block should be rejected (e.g. `handle_block_validate_reject` or the chainstate re-check failing in `handle_block_pre_commit`/`handle_block_validate_ok`), the rejection is recorded only in `block_rejection_signer_addrs`: [4](#0-3) [5](#0-4) 

Neither of those rejection-handling code paths deletes the earlier `block_pre_commits` row for that signer/block, and grepping `signerdb.rs` for the pre-commit table turns up no deletion statement analogous to the reconciliation done in `add_block_signature`. The result: a signer's earlier pre-commit for a block remains permanently counted by `get_block_pre_committers`/`compute_signature_signing_weight` in `handle_block_pre_commit`'s threshold tally even after that same signer has broadcast (and had recorded) a rejection of the very same block.

### Impact Explanation
Because `handle_block_pre_commit` is re-invoked on every re-proposal of a block (`should_reevaluate_block` explicitly re-runs the pre-commit path for blocks in the `PreCommitted` state, and pending/queued pre-commits are replayed via `process_pending_responses_for_block`), the stale pre-commit weight from a signer who has since rejected the block keeps contributing to the ≥70% pre-commit threshold on every subsequent evaluation: [6](#0-5) [7](#0-6) 

This breaks the "aggregated-weight vs verified-accepts" equality: the tally no longer reflects each signer's *current* stance. A one-slot miner that re-proposes a block after a signer's rejection (a normal, attacker-triggerable action already exercised in this codebase's re-proposal tests) can cause this signer to cross the pre-commit threshold using a phantom vote that the voting signer itself has retracted, pushing this signer toward signing a block it should instead be treating as rejected — a step toward a signer signing a conflicting/invalid block.

### Likelihood Explanation
The precondition — a miner or the network causing a re-proposal after at least one signer's pre-commit/rejection sequence for the same block — is squarely within reach of a single miner plus normal gossip, matching patterns already tested in this repo (`stale_proposal_of_accepted_block_resends_acceptance`, `reproposal_signs_replacement_after_conflict_times_out`). No majority collusion or key compromise is required; only the ordinary pre-commit → validation-recheck-fails → rejection → re-proposal sequence that the state machine already supports.

### Recommendation
When a rejection is recorded for a signer/block pair (`add_block_rejection_signer_addr`), also delete any existing `block_pre_commits` row for that same signer/block (mirroring what `add_block_signature` already does for `block_rejection_signer_addrs`), so that `get_block_pre_committers`/the pre-commit weight tally only reflects each signer's current, non-retracted vote.

### Proof of Concept
Not independently reproduced with a runnable test in this session (index/tool budget exhausted); the sequence to reproduce is:
1. Signer S receives and stores a pre-commit for block B (`add_block_pre_commit` via `handle_block_pre_commit`).
2. Before B reaches the 70% pre-commit threshold, S (or another observer relaying S's message) determines B should be rejected and records it via `add_block_rejection_signer_addr`/`store_and_process_block_rejection` — the earlier `block_pre_commits` row for S is left untouched.
3. The miner re-proposes B (or a late pre-commit for B from another signer arrives), re-triggering `handle_block_pre_commit`'s weight tally, which still counts S's stale pre-commit row via `get_block_pre_committers`, inflating the tally toward the 70% threshold using a vote S no longer holds.
