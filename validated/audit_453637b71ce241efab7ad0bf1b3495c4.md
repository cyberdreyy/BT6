Confirmed: `ProposerPreferences`/`proposer_preferences` never appears anywhere in `specs/gloas/beacon-chain.md` — the file containing the actual state-transition function `process_execution_payload_bid`. The proposer's fee-recipient preference is checked against the builder's bid only at the p2p gossip layer, and only as a soft `IGNORE` (not `REJECT`).

### Title
Builder Can Redirect Its Bid Payment to an Arbitrary Address Because `fee_recipient` Is Never Bound to the Proposer's Committed Preference On-Chain - (File: specs/gloas/beacon-chain.md)

### Summary
In Gloas (EIP-7732 proposer-builder separation), a builder's payment destination (`bid.fee_recipient`) is supposed to match the proposer's own preference, communicated off-chain via a signed `SignedProposerPreferences` message. This equality is checked *only* in gossip validation as a best-effort, bypassable `IGNORE` condition. The state-transition function that actually processes the bid and creates the on-chain payment record, `process_execution_payload_bid`, never checks `fee_recipient` against anything and blindly trusts the value chosen by the builder.

### Finding Description
`SignedExecutionPayloadBid.message` contains a builder-controlled `fee_recipient` field that determines where the builder's promised `bid.value` payment will ultimately be withdrawn to [1](#0-0) .

The honest-builder procedure states the intent that `bid.fee_recipient` must be derived from the proposer's own signed `SignedProposerPreferences` message [2](#0-1) , and the p2p gossip validator for the `execution_payload_bid` topic does compare `bid.fee_recipient` against `proposer_preferences.fee_recipient` — but this is only an `IGNORE`, not a `REJECT`: [3](#0-2) 

Crucially, this check exists **only** in the p2p gossip validation layer and is completely absent from the consensus state-transition function `process_execution_payload_bid`, which is the function that actually determines block validity and commits the payment: [4](#0-3)  This function never references `ProposerPreferences` at all — confirmed by the absence of any match for `ProposerPreferences`/`proposer_preferences` anywhere in `specs/gloas/beacon-chain.md`. The pending payment/withdrawal is recorded straight from the untrusted bid field: `fee_recipient=bid.fee_recipient` [5](#0-4) .

Additionally, block proposers are explicitly permitted to obtain bids through channels other than gossip, which entirely bypasses even the soft gossip-layer check: "The block proposer MAY obtain these signed messages by other off-protocol means" [6](#0-5) , and the only requirement stated for inclusion is that the bid "MUST satisfy the verification conditions found in `process_execution_payload_bid`" [7](#0-6)  — which, as shown, does not check `fee_recipient` at all.

This mirrors the reported bug class precisely: a value (`encryptedOutputs` in Hinkal / `fee_recipient` here) that is supposed to be bound to a specific party's authorized preference is only checked by an optional, off-chain, best-effort mechanism (a relayer/gossip validator), while the authoritative on-chain state-transition logic accepts it unconditionally from an untrusted party (the relayer/builder) — breaking the equality "payment recipient == the recipient the payee actually authorized."

### Impact Explanation
This breaks the "a builder payment or withdrawal misdirected" equality. If a builder submits a bid (via a non-gossip channel, or exploiting the fact the check is only `IGNORE` rather than `REJECT`, meaning an honest client already has the bid queued/accepted before the mismatch is even relevant) with a `fee_recipient` different from what the proposer actually wants, and the proposer includes it, `process_execution_payload_bid` will accept it and later `settle_builder_payment`/withdrawal machinery will pay the builder's chosen address rather than the proposer's intended address. This qualifies as High severity: "a builder payment or withdrawal misdirected."

### Likelihood Explanation
The likelihood depends on how proposer client implementations source bids. Since the spec text itself permits "off-protocol means" for obtaining bids (relayers/builder APIs, similar to the current MEV-Boost pattern), and the canonical validity function `process_execution_payload_bid` does not enforce the fee_recipient constraint, any implementation or relay that skips (or bugs out on) the gossip-layer soft check would let a payment be silently redirected, with no way for the consensus layer to catch it after the fact. This is a spec-level gap, not merely a client bug: the specified state-transition function itself omits the check, so even a "spec-compliant" node accepts such a block as valid.

### Recommendation
Add an explicit assertion in `process_execution_payload_bid` (or a related block-validity check) binding `bid.fee_recipient` to the proposer's most recently authorized `ProposerPreferences` for the corresponding slot/dependent-root — analogous to how `bid.parent_block_hash`, `bid.parent_block_root`, and `bid.prev_randao` are already checked against state in the same function [8](#0-7) . This would require storing (or committing to) the proposer's preference in `BeaconState` so it can be verified deterministically during state transition, rather than relying solely on a bypassable gossip-layer `IGNORE`.

### Proof of Concept
1. Proposer P broadcasts `SignedProposerPreferences{proposal_slot=S, fee_recipient=0xPPP...}`.
2. Builder B (malicious or buggy) crafts `bid.fee_recipient = 0xBBB...` (an address B controls) instead of `0xPPP...`, and delivers it to P off-gossip (e.g., through a private relay/builder API, or exploiting a non-strict `IGNORE` gossip filter).
3. P's validator client only checks that `process_execution_payload_bid` conditions are satisfied per `specs/gloas/validator.md` lines 204-211 — none of which touch `fee_recipient` — and includes `signed_execution_payload_bid` in its block.
4. `process_block` → `process_execution_payload_bid(state, block.body.signed_execution_payload_bid)` executes successfully: it never checks `bid.fee_recipient` against P's preferences [9](#0-8) , and records `BuilderPendingWithdrawal(fee_recipient=0xBBB..., amount=bid.value, builder_index=B)`.
5. When the payment settles (`settle_builder_payment`), the withdrawal is paid to `0xBBB...` instead of proposer P's intended `0xPPP...`, even though the block and all state transitions are fully spec-valid.

##### New `process_execution_payload_bid`

```python
def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
