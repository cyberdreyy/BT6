### Title
`requestWithdraw` underflows and reverts when upfront management fee exceeds principal + interest, blocking lender exits - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug is an arithmetic underflow thrown inside a routine (`Bucket.keyEquals()`) that callers assumed was safe, turning a value-comparison edge case into a hard revert. The closest analog in `idle-tranches--008` is the unchecked subtraction `principal + interest - totalFees` in `requestWithdraw`, which reverts whenever `_totalWithdrawFees` returns more than the user's principal plus projected interest, freezing that lender's tranche tokens in the vault.

### Finding Description
In `requestWithdraw` (contracts/IdleCDOEpochVariant.sol:772-776):

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
```

`_totalWithdrawFees` (contracts/IdleCDOEpochVariant.sol:900-906) returns `_mgmtFee` verbatim whenever `_mgmtFee >= _interest`. `_mgmtFee` is computed on the *principal* over `_withdrawRequestManagementFeeDuration()` (contracts/IdleCDOEpochVariant.sol:925-931), which equals `epochDuration` plus the remaining buffer (`bufferEnd - block.timestamp`) — it is unbounded by the principal itself.

So whenever `managementFee * principal * (epochDuration + remainingBuffer) / (365 days * FULL_ALLOC) > principal + interest`, i.e. whenever the effective fee duration exceeds roughly `365 days / managementFee%`, the subtraction underflows (Solidity 0.8 checked arithmetic) and the whole transaction reverts. This is exactly the Hedera pattern: a value that was implicitly assumed to be `<=` another operand is subtracted unchecked, producing a panic instead of a clamped result.

Conditions that trigger it:
- Small/dust withdrawal requests (`principal` tiny makes the condition easy to hit even at moderate fee/duration).
- Long `epochDuration` + `bufferPeriod` combined with a high `managementFee`. For example at `managementFee = FULL_ALLOC` (100%) any fee duration above ~1 year underflows for every request; at 50% it takes >~2 years. Whether the fee setter caps `managementFee` below 100% was not fully verified in this pass — if capped lower, the trigger window requires correspondingly longer epoch+buffer durations, which are honest-owner-set parameters and legitimately configurable.
- Any request made early in a long buffer, since `remainingBuffer` inflates the fee duration.

Note that the same unguarded pattern appears in the view `maxWithdrawable` (contracts/IdleCDOEpochVariant.sol:911-917), where `currentUnderlyings -= _calculateManagementFee(currentUnderlyings, block.timestamp - latestHarvestBlock)` underflows for small balances after a long harvest gap — a read-only manifestation of the same class.

### Impact Explanation
A KYC-passed lender holding tranche tokens calls `requestWithdraw` during buffer/running phase and the call reverts with an arithmetic panic. Tranche tokens are not burned (the revert precedes `_withdrawOps`), but the user cannot create a withdrawal receipt, and `claimWithdrawRequest` is unreachable without one. All lenders whose `principal + interest < upfrontMgmtFee` are frozen out of the exit path for as long as the condition holds — i.e., until the buffer elapses enough to shrink the fee duration, or until fee/duration parameters change. For dust balances the freeze is effectively permanent since fee accrual scales with time, not balance. The broken invariant is fair burn/exit: a user holding a positive, valued tranche position is denied the only withdrawal path, a temporary (and for dust, permanent) freezing of user funds.

### Likelihood Explanation
Medium-low. It requires an honest-but-permitted parameter combination (high `managementFee` and/or long `epochDuration`/`bufferPeriod`) or dust withdrawals. No attacker action is needed beyond being a lender; the trigger is purely the arithmetic edge. Guard review: `requestWithdraw` has no check that `totalFees <= principal + interest` (contrast with the explicit clamps in `stopEpoch` at lines 452-455 and 463, which shows the codebase clamps elsewhere but not here). `_checkNotAllowed`, `_skimDonatedAssets`, and `_updateAccounting` do not prevent it.

### Recommendation
Clamp the fee instead of subtracting unchecked:

```solidity
uint256 maxFees = principal + interest;
if (totalFees > maxFees) totalFees = maxFees;
_underlyings = principal + interest - totalFees;
```

and apply the same guard to `currentUnderlyings -= _calculateManagementFee(...)` in `maxWithdrawable` (return 0 on underflow). Alternatively cap `_totalWithdrawFees` at `principal + interest` inside the helper.
