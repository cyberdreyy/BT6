### Title
Cross-user response confusion via unauthenticated MessageId collision in gateway capabilities handler's `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each incoming user request's response callback keyed solely by `msg.Body.MessageId` [1](#0-0) , and `MessageId` is a client-chosen value with no binding to the sender's identity/signature. Because the map key omits `Sender`, an attacker who submits a second `web_api_trigger` request with the same `MessageId` as a victim's in-flight request overwrites the victim's stored callback, so whichever node response arrives first for that `MessageId` is delivered to whatever callback is currently stored — potentially the attacker's — causing cross-user response confusion.

### Finding Description
The gateway's HTTP user-facing endpoint decodes the JSON-RPC request and derives the legacy `Message`, setting `m.Body.MessageId = req.ID` directly from the caller-supplied JSON-RPC `id` field [2](#0-1) . `Message.Validate()` only checks length/format constraints on `MessageId` (non-empty, ≤128 bytes, no trailing null) and binds a cryptographic `Sender` field to the message via signature extraction, but it never ties `MessageId` uniqueness to `Sender` [3](#0-2) . `gateway.ProcessRequest` only enforces `len(jsonRequest.ID) <= 200` before dispatching to the handler [4](#0-3)  — any two unrelated, validly-signed (each with their own key) users can pick the same `MessageId`.

In `HandleLegacyUserMessage`, the handler locks the mutex and unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` with the new callback, with no check for an existing entry or its owner: [5](#0-4) 

When a DON node later responds with the trigger result, `handleWebAPITriggerMessage` looks the callback up strictly by `MessageId`, deletes it, and invokes `SendResponse` on whatever is found — again with no sender/requester correlation: [6](#0-5) 

Exploit flow:
1. Victim sends a `web_api_trigger` HTTP request with `MessageId = "X"`, signed with the victim's key. `savedCallbacks["X"]` is set to the victim's callback and the request is fanned out to all DON members [7](#0-6) .
2. Before any node responds, the attacker sends their own `web_api_trigger` request, also using `MessageId = "X"` (their own valid signature, arbitrary payload) — this passes all validation, since nothing ties `MessageId` to sender identity.
3. `savedCallbacks["X"]` is overwritten with the attacker's callback.
4. When a DON node's response for `MessageId = "X"` arrives (which could be the response to either the victim's or attacker's underlying node message, since nodes process both independently but tag replies with the same `MessageId` that was sent to them), `handleWebAPITriggerMessage` deletes and delivers the response to whoever is currently stored in the map — the attacker's callback. The victim never receives a response for their own request (denial), and/or the attacker can trigger response delivery to their own connection using a `MessageId` they know is in-flight for the victim.

This directly violates the intended per-request isolation property: an unprivileged party (any unauthenticated HTTP client capable of self-signing a `web_api_trigger` request) can interfere with another party's request/response transaction purely by choosing a colliding `MessageId`, requiring no secret knowledge beyond observing/guessing the victim's chosen `MessageId` (which may be predictable, e.g., sequential counters, timestamps, or observed via logs/side channels as the audit question notes).

### Impact Explanation
This is a cross-user response confusion / request-hijacking vulnerability. Depending on payload content, this could let an attacker: (a) suppress a victim's legitimate trigger response (denial of service against a specific request), and/or (b) receive a response that was not intended for them if the underlying node happens to process and respond using the shared `MessageId`. This matches Chainlink's "request impersonation / cross-user response confusion" bounty impact class rather than fund loss, since the `capabilities` gateway handler here brokers HTTP trigger/action calls (not direct signing or fund movement), but it is a genuine isolation break for the gateway's user-facing message routing.

### Likelihood Explanation
- No privileged credentials are required — any client capable of signing a `web_api_trigger` message with their own key (unauthenticated w.r.t. the node, since the DON's allowlist/authentication only requires a valid signature over the payload, not a "no-collision" policy on `MessageId`) can trigger this.
- The only precondition is knowing or guessing the victim's `MessageId` during the small window (seconds) that the request is in-flight; this is realistic if `MessageId`s are predictable (e.g., generated with a JSON-RPC client library that uses sequential IDs, timestamps, or is otherwise observable through client-side telemetry/logs), as hypothesized in the audit question.
- The race is fully reproducible in a unit test with two `HandleLegacyUserMessage` calls sharing a `MessageId`.

### Recommendation
Key `savedCallbacks` by a composite of `(Sender, MessageId)` (or a gateway-generated internal ID unrelated to the client-supplied `MessageId`) instead of `MessageId` alone. Before overwriting an entry in `HandleLegacyUserMessage`, check if an entry already exists for the derived key and reject/queue the new request instead of silently overwriting. Correspondingly, `handleWebAPITriggerMessage` should validate that the responding message's sender/DON context matches the original request's sender before dispatching `SendResponse`.

### Proof of Concept
Go unit test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two `*api.Message` objects, `victimMsg` and `attackerMsg`, both with `Body.MessageId = "X"`, `Body.Method = MethodWebAPITrigger`, but signed with two different private keys (so `ExtractSigner`/`Validate()` yields different `Sender`s).
2. Create two mock `handlers.Callback` instances, `victimCallback` and `attackerCallback` (e.g., via `handlerscommon.NewCallback()` or a mock implementing `SendResponse`).
3. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`, then before any node response, call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`.
4. Assert `handler.savedCallbacks["X"].Callback == attackerCallback` (overwritten), demonstrating the victim's callback is orphaned.
5. Simulate a DON node response for `MessageId = "X"` by calling `handler.handleWebAPITriggerMessage(ctx, respMsg, nodeAddr)` and assert that `attackerCallback.SendResponse` is invoked instead of `victimCallback.SendResponse`, and that `victimCallback` never receives any response (times out).
6. Expected assertion: the test should fail against the intended isolation invariant, confirming `savedCallbacks` must be keyed by `(Sender, MessageId)`, not `MessageId` alone.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
