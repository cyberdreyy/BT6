### Title
Stale `Accepted` signature survives an explicit later `Rejected` for the same slot, permanently inflating `total_weight_approved` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tracks per-block signer state in `BlockStatus` (`responded_signers`, `gathered_signatures`, `total_weight_approved`, `total_weight_rejected`). When a signer sends `BlockResponse::Accepted` and later sends `BlockResponse::Rejected` for the *same* `signer_signature_hash`, the rejection handler is silently skipped because `responded_signers` already contains that slot id, so the earlier acceptance's weight and signature are never removed or decremented.

### Finding Description
In the `Accepted` branch [1](#0-0) , when a new signature arrives from `slot_id`, if `gathered_signatures` doesn't already contain the key, `total_weight_approved` is incremented, and then unconditionally `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)` are called.

In the `Rejected` branch [2](#0-1) , the accounting update (`total_weight_rejected` increment, per-txid tracking, logging) is gated entirely behind `if block.responded_signers.insert(slot_id) { ... }`. `HashSet::insert` returns `false` when the value is already present. Since the earlier `Accepted` path already inserted `slot_id` into `responded_signers`, this condition evaluates to `false` for the later `Rejected` message from the same slot on the same block hash, so:
- `total_weight_rejected` is never incremented for this rejection.
- `gathered_signatures` still contains the stale signature for `slot_id`.
- `total_weight_approved` is never decremented.

There is no removal path anywhere in the file for `gathered_signatures` or downward adjustment of `total_weight_approved` — the only mutation paths are additive [1](#0-0) . `reset_rejections` only clears rejection-related state and explicitly re-adds approving signers to `responded_signers`, never touching `gathered_signatures`/`total_weight_approved` [3](#0-2) .

The claimed equality — "`total_weight_approved` for hash H equals the sum of weights of signers whose most recent response for H is Accepted" — is broken: once a signer's `Accepted` message for H is processed, any subsequent `Rejected` message for H from the same signer is dropped silently, and the stale accept weight and signature persist in `gathered_signatures`/`total_weight_approved` for the lifetime of that `BlockStatus` entry.

The miner's aggregation loop in `SignerCoordinator::get_block_status` reads `block_status.total_weight_approved` directly to decide when a block has "enough signatures," and returns `block_status.gathered_signatures.values().cloned().collect()` as the final aggregate signature set once the threshold is crossed [4](#0-3) , so the stale, retracted signature is candidate material for the final block certificate.

### Impact Explanation
This breaks the "rejection recounted as acceptance" safety property: a signer's explicit, later-arriving rejection of a block it previously accepted has no effect on the aggregate state — the stale acceptance is effectively treated as still valid forever. If enough other signers approve independently, this stale entry can help push `total_weight_approved` over `weight_threshold` for a block a signer no longer endorses, and the stale signature can end up embedded in the final aggregated signature set returned by `get_block_status`. This is a chain-safety concern in the class of "a rejection recounted as acceptance."

### Likelihood Explanation
The trigger only requires an honest signer to send an `Accepted` message and then a `Rejected` message for the same `signer_signature_hash` — e.g., after detecting an issue post-hoc. A single attacker-controlled miner slot can craft a `BlockProposal` sequence designed to induce such a flip in an honest signer (the mechanism is generic to any cause of the flip, not attacker-privileged). The bug is deterministic once the precondition (accept-then-reject on same hash/slot) occurs, and is repeatable for every block hash processed by the same `StackerDBListener` instance since `gathered_signatures`/`responded_signers` are never corrected downward.

### Recommendation
In the `Rejected` handler, decouple the "already responded" bookkeping from correctness: on receiving a `Rejected` message, if the slot id is present in `gathered_signatures`, remove it and subtract its weight from `total_weight_approved` (in addition to, or instead of, gating solely on `responded_signers`). Track responses per-slot with the actual last-seen response type (Accepted/Rejected) rather than a single presence-only `HashSet`, so `total_weight_approved` can always be recomputed to equal the sum of weights of signers whose most recent response is `Accepted`.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
