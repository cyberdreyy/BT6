### Title
Global `requestID` uniqueness check in `setupCallback` allows cross-workflow/cross-user DoS via requestID collision - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
`httpTriggerHandler.setupCallback` deduplicates in-flight requests using a single process-wide map `h.callbacks` keyed only by the raw, user-supplied JSON-RPC `req.ID`, with no namespacing by workflow, owner, or authorized key. Any caller authorized for any workflow can pre-empt another, completely unrelated workflow/owner's request by submitting a request using the same `req.ID`, causing the victim's legitimate request to be rejected with `jsonrpc.ErrConflict`.

### Finding Description
`HandleUserTriggerRequest` validates the request, resolves the target workflow, calls `authorizeRequest` (which validates the caller's signature/auth against the *target workflowID only*, via `h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)`), and then calls `setupCallback`: [1](#0-0) 

The `callbacks` map is declared globally on the handler (not per-workflow, per-owner, or per-key): [2](#0-1) 

Because the key inserted is simply `requestID` (the caller-supplied `req.ID` string), and `authorizeRequest` only checks that the caller is entitled to trigger *some* workflowID (not that the `req.ID` "belongs" to them), an attacker who is authorized to trigger workflow A can submit a request with `req.ID = X` and win the race in `setupCallback` against a victim who is authorized only for a completely unrelated workflow B and independently chose (or was assigned by their client library) the same `req.ID = X`. The victim's `setupCallback` call then hits the `found` branch and is rejected with `jsonrpc.ErrConflict`, even though the two requests target entirely different workflows/owners. `HandleJSONRPCUserMessage` in `http_handler.go` passes the raw `req.ID` straight through with no additional scoping: [3](#0-2) 

No existing check (auth, rate limit, or ID validation) namespaces the ID by owner/workflow — `validateRequestID` only rejects empty IDs or IDs containing `/`: [4](#0-3) 

### Impact Explanation
This is a denial-of-service/griefing vector: an attacker who holds valid credentials for any workflow on the gateway (their own workflow, which they can register) can deny service to any other, completely unrelated user/workflow simply by colliding on the JSON-RPC `req.ID`. This matches Chainlink's "denial of service impacting a subset of node/workflow functionality" impact class rather than a full compromise, but it is a genuine isolation failure: `req.ID` uniqueness should be scoped at minimum per authorized key/workflow, not globally across all tenants of the gateway.

### Likelihood Explanation
Exploitability requires the attacker to hold a valid authorized key for *any* workflow on the shared gateway instance (trivial if workflow registration is self-service) and to predict or race the victim's `req.ID`. If client SDKs generate IDs deterministically/sequentially (as hinted at in the question) or the attacker can observe/guess timing, this is straightforward to reproduce with a simple race; if IDs are cryptographically random UUIDs, practical exploitation is reduced to a narrow race-condition window rather than pure guessing. The underlying code defect (global unscoped map) is deterministic and always present regardless of ID predictability.

### Recommendation
Scope the `callbacks` map key by a tuple that includes tenant isolation, e.g. `(workflowOwner, workflowID, requestID)` or `(authorizedKey, requestID)`, rather than `requestID` alone, so that a collision only affects requests within the same workflow/owner rather than across users.

### Proof of Concept
Go test plan in `http_trigger_handler_test.go`:
1. Configure two distinct workflows/owners (`workflowA`/`ownerA`, `workflowB`/`ownerB`) registered in `workflowMetadataHandler`, each with its own valid authorized key.
2. Craft two `jsonrpc.Request[json.RawMessage]` with identical `ID = "shared-id"`, one addressed to `workflowA` signed by `ownerA`'s key, one addressed to `workflowB` signed by `ownerB`'s key.
3. Call `h.setupCallback` (or `HandleUserTriggerRequest`) for the first request — assert it succeeds (no error, `doneCh` returned).
4. Call the same for the second, unrelated request — assert it fails with `jsonrpc.ErrConflict` via the callback's `SendResponse`, even though the two callers/workflows are unrelated.
5. Assert this demonstrates cross-tenant blocking: an unrelated caller with a colliding ID can deny another caller's in-flight request purely due to the global `h.callbacks` map, and document that scoping the key by `(workflowID/owner, requestID)` fixes the isolation gap.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
