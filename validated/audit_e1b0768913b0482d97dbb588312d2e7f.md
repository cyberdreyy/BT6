### Title
Multisig `confirm()` counts stale confirmations from removed members, allowing requests to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
The analog to the ditto `shutdownMarket()` bug — a critical, irreversible action gated on a value that is not kept in sync with live state — exists in `multisig2/src/lib.rs`. The confirmation threshold check in `confirm()` compares the *cached* size of a request's `confirmations: HashSet<String>` against `num_confirmations`, but `delete_member()` never purges a removed member's entries from the `confirmations` map of other pending requests. A member who confirmed a request and is later removed from the multisig still counts toward that request's threshold, letting the request execute with fewer live, currently-authorized members than `num_confirmations` requires.

### Finding Description
`confirm()` reads the existing confirmation set for a request and executes it once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

`delete_member()` is the only place that mutates state when a member is removed. It deletes *requests originally submitted by* the removed member (`r.member == member`) and clears their `num_requests_pk` entry, but it never scans `self.confirmations` to strip that member's entry from confirmation sets belonging to requests submitted by *other* members: [2](#0-1) 

Because `assert_valid_request()` / `current_member()` only check that the *caller* confirming right now is a live member — they never re-validate the *previously stored* confirmations set — a confirmation recorded by a member who has since been deleted remains in the `HashSet<String>` and is still counted by the `len()` comparison in `confirm()`: [3](#0-2) 

The binding that should hold is:
`confirmations.len()` (recorded consent) == number of *currently live* members who actually confirmed.

This bug breaks that equality: a removed member's stale confirmation is still recorded, so `confirmations.len()` can overstate live consent by one (or more, if multiple confirmers are later removed).

### Impact Explanation
This matches the "multisig request executed below threshold" Critical impact category. A request (e.g., a `Transfer` moving all NEAR held by the multisig account) can be executed with fewer live/currently-authorized confirmations than `num_confirmations` mandates, because a ghost confirmation from a removed member is silently retained and counted. This directly undermines the K-of-N custody guarantee the contract is supposed to enforce — NEAR can move on the authority of fewer real, current signers than intended.

### Likelihood Explanation
This requires normal, permitted multisig operations only (no owner/root privilege, no redeploy): any member can `add_request`/`confirm`, and member removal via `DeleteMember` is a standard action available to reach threshold. The bug is triggered purely by the ordinary sequence of (1) a request receiving partial confirmations, and (2) a confirmer subsequently being removed from the multisig for any reason (key rotation, offboarding, compromise response) before the request reaches full confirmation. This is a plausible, even routine, sequence of events in real multisig lifecycles, since `delete_member` is a documented, expected operation.

### Recommendation
When removing a member in `delete_member()`, iterate all pending requests' `confirmations` sets (not just requests originally submitted by that member) and remove the departing member's entry from each. Alternatively, re-validate at `confirm()`-time (and before executing) that every entry in the stored confirmation set still corresponds to a current member of `self.members`, discarding/ignoring stale entries when computing the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `A` calls `add_request_and_confirm(R1)` where `R1` is `Transfer { amount, receiver_id: <A-controlled account> }`. Confirmations for `R1` = `{A}`.
3. `B` calls `confirm(R1)`. Confirmations for `R1` = `{A, B}` (2 < 3, pending).
4. A separate, legitimately-confirmed request `R2 = DeleteMember { member: B }` executes (e.g., because `B`'s key is being rotated/offboarded), calling `delete_member(promise, B)`. `delete_member` only removes requests where `r.member == B` (requests **submitted** by B); `R1` was submitted by `A`, so it is untouched, and `B`'s entry remains inside `confirmations[R1] = {A, B}` — see [4](#0-3) . Members are now `{A, C, D}` (3 members, at the `num_confirmations` floor, allowed by the assert at line 357-360).
5. `C` calls `confirm(R1)`. `confirmations.len()` (2, including stale `B`) `+ 1 = 3 >= num_confirmations (3)` → `R1` executes via `execute_request`, transferring funds — even though only `A` and `C` are live members who truly confirmed; `B`'s stale confirmation was counted toward the threshold instead of a genuine third live confirmer (`D`).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
