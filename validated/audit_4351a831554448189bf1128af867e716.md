### Title
Mid-epoch depositor claims full-epoch interest via `requestWithdraw`, draining yield owed to existing LPs - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` mints tranche shares at a discounted price that only credits the depositor for the *remaining* epoch time plus buffer, and adds only that prorated interest to `expectedEpochInterest`. However, when the same user calls `requestWithdraw` during the buffer period, `_calcInterestWithdrawRequest` pays them a pro-rata share of the **entire epoch's** tranche interest based on their principal, with no adjustment for when they entered. A KYC'd attacker can deposit at the very end of an epoch and immediately queue a withdrawal that includes interest for time they were never in the pool — withdrawing more than fair value at the expense of other tranche holders. This mirrors the Clipper bug class (single-sided entry/exit at inconsistent pricing extracting pool value).

### Finding Description
Two paths price the same position inconsistently:

1. `depositDuringEpoch` mints `minted = (_amount + trancheInterest) * supply / expectedFinal` where `trancheInterest` is prorated by `(remaining + buffer) / (epochDuration + buffer)` — i.e. the depositor is credited interest only for the time they remain [1](#0-0) .
2. It then adds only that prorated `interest` to `expectedEpochInterest`, so the borrower's obligation grows only by the prorated amount [2](#0-1) .
3. `requestWithdraw` (allowed during the buffer once `allowAAWithdrawRequest`/`allowBBWithdrawRequest` hold) computes `_interest = _amount * totTrancheInterest / _trancheBal`, where `totTrancheInterest` is the tranche share of the **whole-epoch** vault interest [3](#0-2) .
4. The receipt is fixed at `principal + interest - fees` and funded via `creditVault.requestWithdraw` / `pendingWithdraws` [4](#0-3) .

Since `totTrancheInterest` is computed over the full epoch on `_managedContractValue()` but `expectedEpochInterest` only accrued the prorated amount for the late deposit, the receipt pays full-duration interest the borrower never owed for that deposit. The shortfall is socialized: `expectedEpochInterest` is distributed across all tranche holders, so remaining LPs' end-of-epoch NAV is reduced by exactly the excess interest paid out.

Sequence (buffer phase, fixed-APR mode, AYS off, non-programmable):
1. Attacker (KYC-passing lender) waits until `block.timestamp` is just before `epochEndDate`.
2. Calls `depositDuringEpoch(amount, AATranche)` — minted shares reflect only `remaining + buffer` interest.
3. After `epochEndDate` passes (buffer), calls `requestWithdraw(0, AATranche)` — receipt locks `principal + fullEpochShareOfInterest - fees`.
4. Claims after `stopEpoch`; the excess interest equals `amount * totTrancheInterest / NAV` minus the small prorated credit, extracted from honest LPs.

Existing guards do not stop this: `depositDuringEpoch` is permissionless for allowed wallets during a running epoch, `requestWithdraw` does not check deposit time or reduce interest for mid-epoch entrants, and there is no per-holder entry timestamp. The analogous protection that exists for the inverse direction (`interestForOverUnderPerformance` adjusting `expectedEpochInterest` on withdraw) only corrects the split between tranches, not the time-weighted entry.

### Impact Explanation
Direct theft of yield from other tranche holders. Magnitude scales with `amount` and with how late the deposit is: depositing at `remaining → 0` yields nearly the full epoch's tranche interest on `amount` while contributing almost nothing to `expectedEpochInterest`. With large `amount` relative to tranche NAV the extraction is proportional: `stolen ≈ amount * totTrancheInterest / lastTrancheNAV`. This is a medium-severity unfair-mint/unfair-claim issue consistent with the Clipper bug class.

### Likelihood Explanation
Requires only a whitelisted (KYC'd) wallet, an epoch-mode vault with `isDepositDuringEpochDisabled == false`, `isAYSActive == false`, `isProgrammableBorrower == false`, and open withdraw-request flags. All preconditions are normal operating states, not edge configurations. Timing the deposit near `epochEndDate` is trivially achievable by monitoring the public `epochEndDate`.

### Recommendation
In `requestWithdraw`/`_calcInterestWithdrawRequest`, discount the withdrawal interest for positions entered via `depositDuringEpoch` — e.g. store per-user or per-tranche entry-time weighted principal, or return only `totTrancheInterest * (remaining + buffer) / (epochDuration + buffer)` for mid-epoch deposits. Alternatively, disallow `requestWithdraw` in the same epoch a `depositDuringEpoch` position was created, or make `depositDuringEpoch` add the *full* epoch interest to `expectedEpochInterest` so the borrower obligation matches what withdrawers can claim.

// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
// assumes test harness from test/foundry/IdleCreditVault.t.sol is available:
// idleCDO (IdleCDOEpochVariant), cdoEpoch, strategy IdleCreditVault, underlying, AAtranche,
// helpers: _toggleEpoch(bool), _startEpochAndCheckPrices, deal/approve utilities.

contract MidEpochDepositInterestTheft is Test {
    function testLateDepositorExtractsFullEpochInterest() external {
        uint256 amount = 100_000 * ONE_SCALE;
        address honest = makeAddr("honest");
        address attacker = makeAddr("attacker"); // KYC-passed wallet

        // honest LP deposits before epoch start
        _depositAs(honest, amount, address(AAtranche));
        _startEpochAndCheckPrices(0); // fixed apr epoch starts

        uint256 end = cdoEpoch.epochEndDate();
        uint256 duration = cdoEpoch.epochDuration();

        // attacker deposits 1 block before epoch end at discounted price
        vm.warp(end - 1);
        _depositAs(attacker, amount, address(AAtranche)); // depositDuringEpoch path
        uint256 attackerShares = AAtranche.balanceOf(attacker);

        // buffer period: attacker requests full withdrawal incl. whole-epoch interest
        vm.warp(end + 1);
        vm.prank(attacker);
        uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

        // attacker committed funds for ~0 time but is owed principal + ~full-epoch
        // pro-rata tranche interest on `amount`
        uint256 fairInterest = amount * cdoEpoch.getApr(address(AAtranche)) / 100
            * 1 /* ~1 day held */ / (365 days * ONE_TRANCHE_TOKEN);
        assertGt(receipt, amount + fairInterest + 1); // strictly more than fair share

        // after stopEpoch the receipt is funded; honest LP's NAV is shorted by the excess
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);
        vm.prank(attacker);
        cdoEpoch.claimWithdrawRequest();
        assertGt(underlying.balanceOf(attacker), amount + fairInterest);
    }
}
