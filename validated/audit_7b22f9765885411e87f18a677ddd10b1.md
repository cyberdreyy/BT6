### Title
Attacker-controlled `message_id` collisions in the WebAPI capabilities gateway handler allow response hijacking / DoS of another client's pending request - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The bug class in the external report is: an unprivileged actor can insert entries into a shared, unbounded-but-capped data structure keyed by a value the actor fully controls, and this collides with / evicts another user's legitimate entry, denying that user their expected outcome. The closest reachable analog in this Chainlink node repo is the Gateway's legacy WebAPI capabilities handler, where the `message_id` used as the map key for pending callbacks is chosen entirely by the calling (unprivileged) client and is not scoped per-sender.

### Finding Description
The Gateway's `ProcessRequest` routes legacy requests to `handler.HandleLegacyUserMessage`, using the client-supplied `msg.Body.MessageId` as the correlation key [1](#0-0) . `Message.Validate()` only checks length/format constraints on `MessageId` (non-empty, ≤128 bytes, no trailing null byte); it performs no uniqueness check and does not bind the ID to sender identity [2](#0-1) .

In `HandleLegacyUserMessage`, the handler unconditionally stores the caller's callback in a shared map keyed by this attacker-controlled `MessageId`: [3](#0-2) 

Any concurrent request from any other (unprivileged) client using the same `MessageId` silently overwrites the previous entry in `savedCallbacks`. When a DON node later responds with that `MessageId` via `handleWebAPITriggerMessage`, the response is delivered to whichever caller currently occupies that map slot: [4](#0-3) 

This is analogous to the reported bug class: an attacker forcing collisions/overwrites in a data structure another party depends on for a correct, timely response — resulting in either (a) the victim's original callback being silently dropped/overwritten so their request hangs until timeout, or (b) the attacker's callback intercepting the response payload intended to correlate with the original request context if further validation is absent.

The `savedCallbacks` map also has a soft cap (`MaxSavedCallbacks`, default 20000) enforced only periodically via `pruneCallbacks`, which evicts the oldest half of entries once the cap is exceeded [5](#0-4) . Since insertion is not per-sender rate-limited beyond the node-to-node `nodeRateLimiter` (which only applies to outgoing DON->client messages, not incoming user triggers), an attacker submitting many trigger requests can cause premature eviction of other clients' pending callbacks before their DON responses arrive, causing legitimate requests to silently fail/timeout.

### Impact Explanation
Impact is Medium: a malicious or careless client can (1) collide `message_id`s to redirect or drop another user's in-flight WebAPI trigger response, causing cross-user response confusion/timeout, or (2) flood the shared `savedCallbacks` map to force premature eviction of other users' pending entries, denying them their expected callback. No fund movement or secret disclosure is involved, but it does violate expected per-request isolation for the gateway's legacy WebAPI trigger flow.

### Likelihood Explanation
Likelihood is Low-Medium: it requires an attacker to guess/predict or race against another legitimate client's chosen `message_id` (or to flood many trigger requests to force eviction), which is plausible in workflow ecosystems where message IDs may be predictable (e.g., derived from workflow-specific counters) but not guaranteed. No authentication bypass is needed since the gateway's legacy message path only requires a valid signature over the message the attacker itself controls.

### Recommendation
- Scope `savedCallbacks` keys by `(sender, message_id)` rather than by `message_id` alone so that different senders cannot collide.
- Reject re-use of an in-flight `message_id` from a different sender (or any sender) with an explicit "duplicate message ID" error rather than silently overwriting.
- Apply the existing `nodeRateLimiter` concept, or an equivalent per-sender limiter, to incoming user trigger requests, not just outgoing DON responses.

### Proof of Concept
1. Client A submits a `web_api_trigger` legacy message with `message_id = "X"`, gets stored in `h.savedCallbacks["X"]` awaiting a DON response.
2. Before the DON responds, Client B (attacker) submits its own signed legacy message also with `message_id = "X"` (Validate() only checks format, not global uniqueness) [6](#0-5) .
3. `HandleLegacyUserMessage` overwrites `h.savedCallbacks["X"]` with Client B's callback [3](#0-2) .
4. When the DON node responds with `MessageId = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds Client B's callback, and delivers the response to Client B while Client A's original request silently receives nothing until it times out [4](#0-3) .

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

		// Send first response from a node back to the user, ignore any other ones.

	}
	return nil

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
