### Title
`MultisigFactory::create` has no callback to detect failed sub-account deployment, permanently stranding the attached deposit - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` builds a single batched `Promise` (`create_account` → `deploy_contract` → `transfer` → `function_call`) and returns it directly with no `.then()` callback. If the batched receipt fails (e.g., the target account name already exists, is invalid, or `new` panics due to bad `members`/`num_confirmations`), the attached deposit is never returned to the caller and is not moved to the (never-created) sub-account either — it is simply retained by the `multisig-factory` contract balance with no method exposed to recover or refund it.

### Finding Description
The broken binding: `attached_deposit (paid by predecessor)` should equal `deposit received by new multisig OR refunded to predecessor`. In `MultisigFactory::create`: [1](#0-0) 

the function is `#[payable]`, takes attacker-controlled `name`, `members`, and `num_confirmations`, and constructs one promise batch containing `create_account`, `deploy_contract`, `transfer(attached_deposit)`, and `function_call("new", ...)`. All four actions are part of the same outgoing receipt to `account_id`. If any action in that receipt fails — most simply, `create_account` fails because `account_id` already exists (an attacker or anyone can pre-create/squat `"{name}.{factory}"`), or the `new` call panics on malformed `members`/`num_confirmations` — the entire receipt fails atomically, so the `transfer` action never executes and the funds never land on the new account. Since `create` returns the promise directly with no `.then(ext_self::...)` callback, there's no code path in this contract that runs `is_promise_success()` and issues a rollback `Promise::new(predecessor_account_id).transfer(...)`.

Contrast with the two sibling factories, which implement exactly this pattern deliberately: `StakingPoolFactory::create_staking_pool` and `LockupFactory::create` both chain `.then(ext_self::on_..._create(...))`, and their callbacks (`on_staking_pool_create` / `on_lockup_create`) call `assert_self()` and `is_promise_success()`, refunding `predecessor_account_id` on failure: [2](#0-1) [3](#0-2) 

`multisig-factory/src/lib.rs` has no equivalent module, no `assert_self`/`is_promise_success` helpers, and no callback method at all — confirmed by inspecting the crate's `src/` directory, which contains only `lib.rs`. No existing guard (`assert_owner`, `assert_self`, `is_promise_success`, `assert_one_yocto`, etc.) exists in this contract to intercept the failure.

Any unprivileged caller triggers this merely by calling `create` with a `name` that maps to an account which already exists (trivially producible by anyone pre-registering that subaccount, or by natural collision/retry), or with `members`/`num_confirmations` that cause the multisig `new` constructor to panic. The deposit sent with that call is retained on the `multisig-factory` account with no owner, no withdraw method, and no way for the original payer to reclaim it.

### Impact Explanation
The caller's attached NEAR becomes stuck on the `multisig-factory` contract account after a failed deployment — funds leave the payer's control and are not credited to any intended destination (no new multisig, no refund). This matches the "accounting value diverges from reality, funds frozen and unrecoverable via any exposed method" pattern (the factory contract has no admin/withdraw entrypoint), i.e., a High-severity frozen-funds condition. It is repeatable by any caller, on any attempt where the underlying receipt fails, and does not require privileged access.

### Likelihood Explanation
Trivial to trigger: any unprivileged account can call `create` with a `name` corresponding to an already-existing account (including one they intentionally pre-created themselves via `Promise::new` or a prior `create` call using the same `name`), or supply `members`/`num_confirmations` that fail multisig `new`'s internal validation. No special balances, roles, or races are needed beyond a standard NEAR transaction with an attached deposit. It is fully repeatable across accounts and attempts.

### Recommendation
Add an `ext_self` callback analogous to `on_lockup_create`/`on_staking_pool_create`: split `create` into the account-creation promise followed by `.then(ext_self::on_multisig_create(account_id, attached_deposit.into(), predecessor_account_id, ...))`, and in that callback call `assert_self()`, check `is_promise_success()`, and on failure issue `Promise::new(predecessor_account_id).transfer(attached_deposit)`.

### Proof of Concept
Using `near-sdk-sim`/unit test with `testing_env_with_promise_results` analogous to `lockup-factory`'s `test_create_lockup_rollback`:
1. Call `MultisigFactory::create(name, members, num_confirmations)` with `attached_deposit = D` from `predecessor_account_id = P`.
2. Simulate the batched promise's receipt failing (`PromiseResult::Failed`), e.g., by pre-registering `"{name}.{factory}"` before calling `create`.
3. Assert (a) no callback method exists to invoke/verify refund logic (attempting to call any `on_*_create`-equivalent on `MultisigFactory` fails to compile/exist), and (b) after the failed receipt, `P`'s balance is `unchanged - gas costs` (not `+D`) while the factory contract's balance holds `D` indefinitely, with no method on `MultisigFactory` capable of returning it — demonstrating `attached_deposit_paid_by_P != refunded_to_P + deposited_in_new_multisig`.
