## Analog Vulnerability Analysis

The `FCFSMint()` bug is a class of "privileged operation exposed without the required allowlist/authorization check being enforced at that call site." Searching the chainlink codebase for the same bug class in unprivileged-actor-reachable paths (node API auth, external initiator handling, gateway message handling) surfaces a directly analogous, explicitly-acknowledged gap in the gateway's legacy Web API trigger handler.

### Title
Missing Allowlist/Rate-Limiting Check on `HandleLegacyUserMessage` Allows Unauthenticated Broadcast to All DON Nodes - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway's `capabilities` package legacy handler entry point, `HandleLegacyUserMessage`, performs payload parsing, timestamp/staleness checks, and method validation, but contains a literal `// TODO: apply allowlist and rate-limiting here` before it fans the request out to every node in the DON. Unlike the FCFSMint case, per-sender authorization does exist one layer downstream (in `triggerConnectorHandler.processTrigger`), but the gateway itself — the internet-facing entry point — accepts and forwards any signed request from any keypair to all DON members with no allowlist or rate-limit gate, exactly the missing check pattern described in the report.

### Finding Description
`gateway.ProcessRequest` [1](#0-0)  routes any legacy (DON-addressed) JSON-RPC request straight to the resolved handler's `HandleLegacyUserMessage` after only validating the message envelope structure/signature format via `msg.Validate()` — it does not check whether the caller/sender is on any allowlist for the target DON.

Inside `HandleLegacyUserMessage`, the code validates payload decodability, a non-zero timestamp, and staleness, then hits the acknowledged gap: [2](#0-1) 

Immediately after that TODO, the handler unconditionally fans the (still-unauthorized) request out to **every member of the DON**: [3](#0-2) 

Real per-workflow sender authorization only happens later, inside each node's capability trigger handler (`triggerConnectorHandler.processTrigger`), which checks `trigger.allowedSenders[sender.String()]` and a per-sender rate limiter: [4](#0-3) 

This means the gateway-level "allowlist and rate-limiting" that the code comment says should exist is simply absent — anyone able to reach the gateway's public HTTP endpoint can generate a validly-signed (but otherwise arbitrary/unregistered) message and force it to be broadcast to and processed by every node in the target DON, with no gateway-side gate analogous to the missing whitelist check in `FCFSMint()`.

### Impact Explanation
Because the allowlist/rate-limit check is missing precisely where the code says it should be, an unprivileged, unregistered actor can repeatedly submit `web_api_trigger` (and any other legacy method mapped in this handler's `Methods()`) requests that are unconditionally forwarded to all DON nodes. Each node must parse, validate, and evaluate the request against every registered trigger config before finally rejecting unauthorized senders. This bypasses any gateway-level quota/allowlist control and shifts unbounded load onto DON nodes, enabling resource-exhaustion/DoS against the whole DON from a single unprivileged caller — the same "acknowledged, missing check before the ability is exercised" pattern flagged in the `FCFSMint()` report, just manifesting as a quota/allowlist bypass on the gateway ingress path rather than direct fund/asset issuance.

### Likelihood Explanation
High: the gateway HTTP endpoint is explicitly internet-facing and designed to accept requests from external/unregistered senders (that's its purpose). No additional privilege, secret, or role is required — only the ability to produce any ECDSA-signed message, which any caller can do with a throwaway key. The gap is also self-documented in-code via the `// TODO`, confirming it was a known, unaddressed omission rather than a defense-in-depth layer intentionally deferred with equivalent protection elsewhere at the gateway tier.

### Recommendation
Add an allowlist/rate-limiting check inside `HandleLegacyUserMessage` (or in `gateway.ProcessRequest` before dispatch) that verifies the message sender is permitted to reach the target DON/method combination and enforces a global/per-sender rate limit, consistent with the per-workflow `allowedSenders`/`rateLimiter` checks already implemented in `triggerConnectorHandler.processTrigger`. This closes the gap between the gateway ingress and the node-side authorization so that unauthorized senders are rejected before consuming DON-wide fan-out resources.

### Proof of Concept
1. Generate an arbitrary ECDSA keypair (as done in `core/scripts/gateway/web_api_trigger/invoke_trigger.go`) that is not present in any workflow's `allowedSenders` list. [5](#0-4) 
2. Sign and submit a legacy `api.Message` with method `web_api_trigger` to the gateway's public endpoint targeting a known `don_id`.
3. Observe via `gateway.ProcessRequest` → `HandleLegacyUserMessage` that the message passes all present checks (decodable payload, non-zero/fresh timestamp, correct method) and is forwarded via `don.SendToNode` to **every** node in that DON, despite the sender never having been allowlisted — confirming the missing gateway-level allowlist/rate-limit gate called out by the `// TODO` comment.
