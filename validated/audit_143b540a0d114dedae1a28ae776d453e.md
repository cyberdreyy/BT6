### Title
Raw internal error details from FindUserByAPIToken leaked to unauthenticated callers via jsonAPIError - (File: core/web/auth/auth.go)

### Summary
In `AuthenticateByToken`, any error from `FindUserByAPIToken` other than `sql.ErrNoRows`/`ErrUserSessionExpired` is returned unmodified (line 98) and propagated up through the `Authenticate` middleware to `jsonAPIError`, which serializes `err.Error()` directly into the JSON response body sent to the caller.

### Finding Description
`AuthenticateByToken` (`core/web/auth/auth.go:78-112`) calls `authr.FindUserByAPIToken(ctx, token.AccessKey)`. On error, it special-cases `sql.ErrNoRows` and `clsessions.ErrUserSessionExpired` to return the generic `auth.ErrorAuthFailed`, but for any other error (e.g., a DB timeout, connection failure, or an internal wrapped error from the LDAP/OIDC/local auth providers) it returns the raw `err` as-is: [1](#0-0) 

This error bubbles up through `Authenticate` (`core/web/auth/auth.go:157-175`), which calls `jsonAPIError(c, http.StatusUnauthorized, err)`: [2](#0-1) 

`jsonAPIError` (`core/web/auth/helpers.go:15-23`) writes `err.Error()` directly into the JSON response body returned to the client: [3](#0-2) 

The attacker is an unauthenticated caller sending any request with `X-API-KEY`/`X-API-SECRET` headers set to arbitrary values; if the backing datastore/auth provider returns a non-`sql.ErrNoRows` error (e.g. transient DB error, LDAP/OIDC internal error), the raw error text is echoed straight back in the HTTP response.

### Impact Explanation
This is a genuine information-disclosure path (error-message leakage), but the severity is limited: the actual content depends entirely on what the underlying `Authenticator` implementation puts into its error (`core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go`, `core/sessions/oidcauth/oidc.go`), which was not exhaustively confirmed here to contain secrets like connection strings or credentials in normal operation — these are typically Go SQL driver errors (e.g., `dial tcp: connection refused`, timeout messages), not raw connection strings or query text. This is a lower-severity internal-error-message disclosure (information leak) rather than a direct secret/key disclosure, credential exposure, or privilege escalation. It does not by itself grant authentication bypass, role escalation, or access to another user's data.

### Likelihood Explanation
Trivial to trigger: any unauthenticated attacker can send a request with the API auth headers set; triggering the non-`ErrNoRows` branch requires an underlying datastore/provider error (e.g., transient DB outage, LDAP/OIDC backend failure), which is not attacker-controlled and is an operational/misconfiguration-dependent condition rather than something an attacker can reliably force on demand.

### Recommendation
In `AuthenticateByToken`, replace the raw error return with a generic error (e.g., wrap with a fixed message like "internal error" or return `auth.ErrorAuthFailed`), and log the original error server-side instead of returning it to the caller — mirroring the pattern already used for the `sql.ErrNoRows` branch.

### Proof of Concept
Go handler-level test: construct a mock `Authenticator` (using `core/sessions/mocks` or a custom stub) whose `FindUserByAPIToken` returns a wrapped error such as `errors.New("dial tcp 10.0.0.5:5432: i/o timeout")`. Invoke `Authenticate(mockAuthr, AuthenticateByToken)` as gin middleware with `X-API-KEY`/`X-API-SECRET` headers set. Assert the HTTP response status is 401 and that the JSON body's error message equals the injected string (demonstrating the leak), then assert that after the fix, the body contains only a generic message (e.g., `"Unauthorized"`) with no substring of the original internal error text.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
