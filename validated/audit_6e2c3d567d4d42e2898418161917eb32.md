### Title
Unfunded post-default instant-withdraw receipts are mixed into the shared `instantWithdrawsRequests` aggregate and paid at par, draining the default-recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Undertow bug class is "one shared buffer is reused to decode the state of many concurrent requests, so requests contaminate each other". The closest analog in `IdleCreditVault` is the single per-user aggregate `instantWithdrawsRequests[_user]` (line 59), which mixes instant-withdraw receipts created in different epochs and different solvency regimes. Unlike `requestWithdraw` (line 243), which explicitly reverts when `defaultRecoveryFinalized` is set and the user still has old receipts (lines 247-258), `requestInstantWithdraw` (lines 356-375) has no `defaultRecoveryFinalized` guard at all. A user can therefore create a brand-new, completely unfunded instant receipt after default finalization, and `claimInstantWithdrawRequest` (lines 380-393) pays the entire shared aggregate 1:1 via `_transferFundedClaim`, even though only the pre-default epoch portion was ever backed.

### Finding Description
`requestWithdraw` correctly separates receipt regimes:

- Post-default requests are forced into a clean state: the user must have zero `withdrawsRequests`, `instantWithdrawsRequests` and `postDefaultRequests` before opening one (lines 248-251), and the new basis is parked in `postDefaultRequests` so it is claimed from `defaultRecoveryReserve` via `_claimPostDefaultWithdrawRequest` (lines 760-767) rather than from the strategy balance.
- `requestInstantWithdraw` only calls `_onlyIdleCDO()` and `_ensureDefaultRecoveryInitialized()` (lines 357-358). It then burns CDO strategy tokens, mints receipt tokens to the user, and adds `_amount` to the shared `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `pendingInstantWithdraws` (lines 360-374) — with no check on `defaultRecoveryFinalized`.

`claimInstantWithdrawRequest` first clears only the *default-epoch* slice via `_claimDefaultedInstantWithdrawRequest` (lines 382-386, 842-856), which is haircut by `defaultRecoveryPrice`. It then reads the remaining shared aggregate `instantWithdrawsRequests[_user]` and pays it at par from the strategy's underlying balance (lines 387-392). Because the aggregate is a single shared slot, a receipt minted *after* default finalization — which was never funded by the borrower and never added to `defaultRecoveryReserve` — is indistinguishable from an already-funded pre-default receipt and is paid at par. The paid tokens come from the same strategy balance that backs `defaultRecoveryReserve`, so every instant receipt created post-default steals from the reserve owed to defaulted-epoch claimants (or reverts once the balance is drained, freezing legitimate claims). This is the exact "request A gets request B's decoded state" mix-up from the advisory, expressed as "receipt regime A gets receipt regime B's funding treatment".

### Impact Explanation
Direct theft of the default-recovery reserve. Any unprivileged tranche holder can call `IdleCDOEpochVariant.requestWithdraw` during an epoch where `lastEpochApr > unscaledApr + instantWithdrawAprDelta` (IdleCDOEpochVariant.sol lines 761-769), which calls `IdleCreditVault.requestInstantWithdraw` and mints them an instant receipt. After `finalizeDefaultRecovery`, they call `claimInstantWithdrawRequest` through the CDO and receive the full receipt amount 1:1 from the vault balance, while defaulted claimants are only entitled to `claimBasis * defaultRecoveryPrice / 1e18`. The attacker extracts reserve tokens that do not belong to them; late legitimate claimants of `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`/`_claimPostDefaultWithdrawRequest` can revert on insufficient balance — permanent loss of recovery funds.

### Likelihood Explanation
Requires a vault that has been through borrower default and recovery finalization (`defaultRecoveryFinalized == true`), and the CDO's instant-withdraw path to still be reachable post-default (APR-decrease trigger). The attacker needs only a tranche position and no privilege: `requestInstantWithdraw` is callable by the CDO on behalf of any user allowed to request withdraws. The asymmetric guard — `requestWithdraw` checks `defaultRecoveryFinalized` (line 247) while `requestInstantWithdraw` does not — indicates the post-default path was simply missed, matching the pre-existing per-epoch fix applied to normal withdrawals but not to the instant aggregate payout.

### Recommendation
Mirror the normal-withdraw post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is set, either revert unless the user has no outstanding receipts, or record the request in a `postDefaultRequests`-style bucket backed by the reserve. Additionally, in `claimInstantWithdrawRequest`, pay only receipts whose per-epoch basis was actually funded — iterate `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` rather than paying the shared `instantWithdrawsRequests[_user]` aggregate at par, and ensure `_transferFundedClaim` cannot spend `defaultRecoveryReserve`.
