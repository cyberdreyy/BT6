### Title
Pending withdrawal requests reduce `getContractValue()` before being funded, letting the CDO exceed the `limit` TVL cap and rehypothecate new deposits to cover old obligations - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw` burns the user's tranche tokens and removes the requested principal from live NAV via `_withdrawOps`, while the matching obligation is only tracked as `pendingWithdraws` inside `IdleCreditVault` and is not actually funded until the borrower repays at `stopEpoch`. Because `GuardedLaunchUpgradable._guarded` enforces the TVL `limit` against `getContractValue()` alone, a withdrawal request instantly opens new deposit headroom even though the withdrawn funds are still owed by the borrower. New buffer-period deposits accepted in that headroom are forwarded to the borrower at `startEpoch`, so the borrower can effectively use fresh depositor principal to satisfy prior redemption obligations — the same insolvency/rehypothecation bug class as the SymmIO `SolverVaults` report.

### Finding Description
- In `IdleCDOEpochVariant.requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791), the user's tranche tokens are burned through `_withdrawOps(_amount, principal, _tranche)` and `IdleCreditVault.requestWithdraw` only *records* the liability: it burns `_principal` strategy tokens from the CDO, mints a receipt to the user, and increments `pendingWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:243-295). No underlying is moved to cover the request at this point.
- `getContractValue()` no longer counts the burned principal, but the funds backing it remain at the borrower until `stopEpoch` sources `pendingWithdraws` via `collectWithdrawFunds` (contracts/strategies/idle/IdleCreditVault.sol:421-430).
- During the buffer period, `_deposit` → `super._deposit` → `_guarded(_amount)` checks `getContractValue() + _amount > limit` (contracts/GuardedLaunchUpgradable.sol:45-50). Since pending withdrawals already exited the measured NAV but not the vault's true exposure, the effective cap becomes `limit + pendingWithdraws`.
- Concretely: with `limit = L`, user A deposits `L`, requests a full withdrawal in the buffer period, and the NAV-based check now permits user B to deposit another `L`. At `startEpoch` (contracts/IdleCDOEpochVariant.sol:233-300) B's deposit is sent to the borrower via `sendInterestAndDeposits`/`sendFundsToBorrower`, while the borrower must also fund A's `pendingWithdraws` at `stopEpoch`. If the borrower is short, the loss is socialized across active LPs and pending receipts through `previewLossAdjustedWithdrawFunds`/`lossRecoveryPriceByEpoch` (contracts/strategies/idle/IdleCreditVault.sol:440-460), i.e., B's fresh principal partially absorbs A's redemption.
- No existing guard prevents this: `_skimDonatedAssets` only removes raw donations, the default/epoch gates (`paused`, `allowAAWithdrawRequest`) are open exactly during the buffer window where this is exploitable, and `_guarded` has no notion of `pendingWithdraws`.

### Impact Explanation
- The TVL `limit` — a credit-risk bound on borrower exposure — can be exceeded up to `limit + pendingWithdraws`, roughly doubling intended maximum exposure in the worst case.
- New depositors' principal is economically used to satisfy prior redemption obligations (unintentional rehypothecation). If the borrower subsequently defaults or realizes a loss, late depositors absorb haircuts via `lossRecoveryPriceByEpoch`/default recovery they never consented to, i.e., direct loss of user funds proportional to the excess deposits.
- The vault reports as within-limit even while carrying unfunded liabilities, masking insolvency during a bank-run scenario.

### Likelihood Explanation
- Requires only unprivileged actions: a KYC-passed lender calls `requestWithdraw` during the buffer period, then any allowed wallet deposits. All privileged calls (`startEpoch`, `stopEpoch`, queue processing) are honest and proceed normally.
- `limit` is a configured feature (`_setLimit`), and buffer-period deposits plus withdrawal requests are the intended UX, so the sequence occurs organically — the larger the redemption queue relative to NAV, the larger the unintended headroom.

### Recommendation
- Include outstanding withdrawal obligations in the deposit-limit check, e.g., `_guarded` should compare `getContractValue() + IdleCreditVault(strategy).pendingWithdraws() + _amount` (plus pending instant withdrawals) against `limit`, so unfunded receipts still count as committed TVL until they are actually paid out.
- Alternatively, keep `getContractValue()` unchanged but have `_deposit`/`depositDuringEpoch` add `pendingWithdraws` when checking the cap.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract PendingWithdrawTvlBreachTest is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault strategy;
    IERC20Detailed underlying;
    address AA;

    address alice = makeAddr("alice"); // KYC'd lender
    address bob   = makeAddr("bob");   // KYC'd lender
    uint256 LIMIT = 1_000e6;           // TVL cap in underlying

    function setUp() public {
        // deploy + initialize cdo/strategy with limit = LIMIT,
        // whitelist alice and bob, deal underlying (standard repo fixture)
    }

    function testPendingWithdrawsBypassTvlLimit() public {
        // buffer period: alice fills the vault up to the cap
        _deposit(alice, LIMIT, AA);
        assertEq(cdo.getContractValue(), LIMIT);

        // bob cannot deposit while NAV is at the cap
        vm.expectRevert(); // ContractLimitReached
        _deposit(bob, 1, AA);

        // alice requests a full withdrawal: tranches burned, NAV drops,
        // but the underlying is still owed (recorded only as pendingWithdraws)
        vm.prank(alice);
        cdo.requestWithdraw(0, AA);
        assertEq(strategy.pendingWithdraws(), LIMIT);
        assertEq(cdo.getContractValue(), 0);

        // BUG: bob can now deposit a full additional LIMIT even though the
        // vault still owes alice LIMIT -> effective exposure 2 * LIMIT
        _deposit(bob, LIMIT, AA); // should revert but does not

        // startEpoch sends bob's funds to the borrower; stopEpoch must also
        // source alice's pendingWithdraws. If the borrower underpays, the
        // loss is socialized and bob's fresh principal absorbs alice's claim.
    }

    function _deposit(address user, uint256 amount, address tranche) internal {
        vm.startPrank(user);
        underlying.approve(address(cdo), amount);
        cdo.depositAA(amount); // or depositBB depending on tranche
        vm.stopPrank();
    }
}
```

Note: full PoC wiring uses the repo's existing Foundry fixtures (deploy/initialize, Keyring whitelist for `alice`/`bob`, `limit` set via `_setLimit`). The key assertion — `strategy.pendingWithdraws() == LIMIT` while `cdo.getContractValue() == 0` yet `depositAA(LIMIT)` succeeds — follows directly from `_withdrawOps` burning NAV at request time while `IdleCreditVault.requestWithdraw` only increments `pendingWithdraws`, and `_guarded` reading `getContractValue()` alone.
