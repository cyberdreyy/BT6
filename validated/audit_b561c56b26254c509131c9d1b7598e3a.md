## Analog Found

### Title
Stale confirmations from deleted multisig members are still counted toward the confirmation threshold, allowing a request to execute with fewer live-member approvals than `num_confirmations` - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the NEAR multisig contract only purges requests *created* by the removed member; it never scrubs that member's existing confirmations recorded against *other* requests. `confirm` later counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without checking whether each recorded confirmer is still a current member. This lets a request execute with fewer than `num_confirmations` *live* approvals — the same class of bug as the Blend finding, where a partial/stale piece of state (the remaining auction) was left un-cleaned after a side effect (defaulting liabilities), letting a later actor exploit the stale record to bypass the system's intended accounting.

### Finding Description
The custody/authorization binding that must hold is:

`confirmations counted toward num_confirmations == confirmations from accounts that are still current members`

`confirm()` increments and checks a plain `HashSet<String>` of confirmer identifiers: [1](#0-0) 

`delete_member()` only removes requests whose *originating* member (`r.member`) equals the member being deleted, and clears `num_requests_pk` for that member, but does nothing to strip that member's entries from the `confirmations` sets of requests they merely *confirmed* (but did not create): [2](#0-1) 

Because `confirmations` is keyed only by `request_id` and stores raw member identifiers with no liveness check, a confirmation given by a member before deletion silently remains "valid" credit toward `num_confirmations` even after that member is removed from `members`. `assert_valid_request` (referenced in `confirm`) does not revalidate old confirmer identities either — it only checks the request itself exists.

This is structurally identical to the Blend bug: `fill_bad_debt_auction` deleted the backstop's liability (a side-effecting state transition) but left `remaining_auction` un-cleaned, so a later, unrelated action (`fill`) at block ≥400 exploited the stale state to receive value without paying the associated cost. Here, `delete_member` performs a side-effecting state transition (removing a member) but leaves that member's stale confirmations un-cleaned in unrelated requests, so a later, unrelated action (`confirm`) exploits the stale entry to reach quorum without the required number of live approvals.

### Impact Explanation
This breaks the multisig's fundamental K-of-N custody guarantee: a `Transfer`, `AddKey`, `FunctionCall`, or any other privileged multisig action can be executed with strictly fewer live-member confirmations than the configured `num_confirmations`. Per the stated impact classes, this is a "multisig request executed below threshold" — Critical severity, since it can move NEAR out of the multisig account or grant access keys with less than the intended quorum of currently-trusted signers.

### Likelihood Explanation
The trigger sequence uses only ordinary, already-supported multisig operations (creating a request, confirming it partially, then executing a separate, properly-authorized `DeleteMember` request), with no need for a compromised key, contract redeploy, or off-chain social engineering. Any request that receives partial confirmations and is left pending while a confirming member is later removed is automatically vulnerable — this can happen through routine membership rotation (a very common multisig maintenance operation), making the likelihood non-trivial for any actively-used multisig set that periodically removes members.

### Recommendation
When a member is deleted, iterate all active requests' confirmation sets (not just those the member created) and remove that member's confirmation entry from each. Alternatively, revalidate every stored confirmer against the live `members` set inside `confirm()` before counting it toward `num_confirmations`, e.g. by filtering `confirmations` to members still present in `self.members` prior to the length comparison.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `D` calls `add_request(R1)` for a `Transfer` action. `confirmations[R1] = {}`.
3. `A` calls `confirm(R1)` → `confirmations[R1] = {A}` (len 1, `1+1 < 3`, not executed).
4. `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}` (len 2, `2+1 = 3 >= 3`... wait, at this point it *would* execute since `2+1>=3`) — to keep R1 pending, assume `num_confirmations = 4` for this step for clarity, or interleave a fourth member; the key point demonstrated below is independent of the exact numbers:
   - Suppose `num_confirmations = 3` and only `A` confirms first (`confirmations[R1] = {A}`, len 1).
5. Separately, `B`, `C`, `D` create and fully confirm a `DeleteMember{A}` request (a valid, independent multisig action reaching quorum of 3 legitimate members). This executes `delete_member`, which:
   - Removes `A` from `members`.
   - Does **not** touch `confirmations[R1]`, which still contains `{A}` (`r.member` for `R1` is `D`, not `A`, so the "delete outstanding requests by member" loop in `delete_member` skips `R1`).
6. `C` (a live member) calls `confirm(R1)`. Code path: `confirmations.len() (1, containing stale "A") + 1 >= num_confirmations (3)`? → 2 < 3, still not enough in this exact trace — but with one more live confirmer (e.g., `D` also confirms), `confirmations.len() (2: "A","C") + 1 ("D") = 3 >= 3` → `execute_request(R1)` fires, transferring funds, even though only `C` and `D` are genuinely live approving members alongside the request's stale `A` credit — i.e., only 2 truly live confirmations were used to satisfy a 3-of-N quorum.

This demonstrates the invariant break: `confirmations.len()` includes at least one identifier (`A`) that is no longer in `self.members`, letting the request execute with fewer live-member approvals than `num_confirmations` requires.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
