### Title
JWT replay-protection TOCTOU allows a single valid JWT to authorize two concurrent requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `jwtCache.isReplay(claims.ID)` and later calls `jwtCache.recordUsage(claims.ID)` as two separate lock acquisitions rather than one atomic check-and-set operation. Two goroutines racing with the same JWT can both pass the `isReplay` check before either calls `recordUsage`, allowing the same JWT to authorize two concurrent requests.

### Finding Description
`Authorize` first verifies the JWT and extracts `claims.ID` (jti), then calls `h.jwtCache.isReplay(claims.ID)`, which takes `cache.mu.RLock()`, reads the map, and releases the lock immediately (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go` lines 399-405). Only after several more (lock-free) steps — the `authorizedKeys` map lookup and signer/key validation — does the handler call `h.jwtCache.recordUsage(claims.ID)`, which separately acquires `cache.mu.Lock()` and writes the jti into the map (lines 407-412, called at line 105).

Between the `isReplay` read and the `recordUsage` write there is no lock held across both operations, so the check-then-act sequence is not atomic. If the same JWT (same `claims.ID`) is submitted twice concurrently — e.g., by the same holder firing two nearly simultaneous HTTP Trigger requests, or a request being retried/duplicated in flight — both goroutines can execute `isReplay` before either executes `recordUsage`, observe `exists == false` for both, and both proceed to pass authorization and independently call `recordUsage`. The second write simply overwrites the timestamp in the map; the race is not detected or rejected.

This defeats the intended "each JWT used once" invariant enforced by this component, since it is the only replay-prevention mechanism at this layer — the rest of `Authorize` only validates JWT signature and the `authorizedKeys`/`workflowID` binding (lines 92-104), and does not otherwise reject a duplicated jti.

### Impact Explanation
This allows a legitimate JWT holder (or anyone who has captured/replays the same JWT within its validity window) to have a single authorized token accepted twice concurrently, resulting in duplicate execution of the associated workflow-trigger capability/action bound to that JWT. This corresponds to a quota/allowlist-bypass and request-binding-bypass class impact: the "one-time use" guarantee for JWT-authorized workflow triggers can be circumvented to consume/execute the victim's authorization twice instead of once.

### Likelihood Explanation
Exploitation requires only possession of one valid, unexpired JWT (which the "attacker" here is the legitimate holder replaying their own token, or the token was leaked) and the ability to send it twice within a race window (a matter of the concurrent request handling, not a network condition or privilege). No signature forgery or key compromise is needed. It is fully reproducible with a deterministic test that synchronizes two goroutines against a shared `jtiReplayCache`/`Authorize` call.

### Recommendation
Make the check-and-record operation atomic: use a single `cache.mu.Lock()` (not RLock+separate Lock) to check for existence and insert the jti in one critical section, e.g. combine `isReplay`+`recordUsage` into one `checkAndRecord(jti string) bool` method returning `false` if already present (rejecting replay) or inserting and returning `true` if new. Call this atomic method in `Authorize` in place of the separate `isReplay`/`recordUsage` calls, ideally performed before the (unrelated) authorized-key lookup so a duplicate jti is rejected earlier as well.

3. To reliably force the race window, insert a small synchronization point (e.g., in a test-only wrapper) between `isReplay` and `recordUsage`, or run with `-race` and a tight loop of many iterations relying on the natural scheduling gap.
4. Assert that only one of the two goroutines returns success (`err == nil`) and the other returns the "JWT token has already been used" error; observe that with the current implementation, both can return success, demonstrating the bug. After applying the atomic fix, assert exactly one success is possible under the same test.
