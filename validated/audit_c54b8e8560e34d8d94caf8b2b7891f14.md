### Title
Job cancellation over SSH executor does not terminate detached/background processes spawned by the job script - ([File: helpers/ssh/ssh_command.go])

### Summary
`ssh_command.Client.Run` cancels a job only by sending an `ssh.SIGKILL` channel request and closing the SSH session/channel, which is insufficient to terminate detached child processes (e.g. `nohup ... &`, `disown`, `setsid`) spawned by `cmd.Script` on the remote host. Because these processes intentionally detach from the controlling session/terminal and ignore `SIGHUP`, they are not part of the process group that receives the signal, and `session.Close()` merely tears down the SSH channel/pty without killing orphaned children.

### Finding Description
`ssh.executor.Run` (`executors/ssh/ssh.go:55-73`) invokes `s.sshCommand.Run(cmd.Context, ssh.Command{Command: s.BuildShell.CmdLine, Stdin: cmd.Script, ...})`. In `helpers/ssh/ssh_command.go:141-178`, the job script (`cmd.Script`, fully attacker-controlled CI job content) is delivered via `session.Stdin` and executed by the remote shell (`session.Start(cmd.Command)`), i.e. `bash --login` reading the script from stdin.

On `ctx.Done()` (job cancellation/timeout), the only termination mechanisms used are:
```go
case <-ctx.Done():
    _ = session.Signal(ssh.SIGKILL)
    _ = session.Close()
    return <-waitCh
```
`session.Signal` sends an `SSH_MSG_CHANNEL_REQUEST "signal"` to the remote process attached to that channel. Two independent, well-known limitations apply:
1. Many `sshd` implementations (notably OpenSSH, historically) silently ignore signal delivery requests entirely, so the top-level shell itself may not even receive `SIGKILL` this way.
2. Even where signal delivery to the top-level shell works, a job script that runs `nohup sleep 600 & disown` (or `setsid ... &`) forks a child that detaches from the session's controlling terminal/process group and explicitly ignores `SIGHUP`. Killing or closing the parent shell/channel does not propagate any signal to this detached descendant, because it is no longer a child of the process being signaled/waited on, and `session.Close()` only closes the SSH channel, not any process tree on the remote host.

There is no code anywhere in `helpers/ssh/ssh_command.go` that captures the remote shell's PID/PGID, wraps the script in a `setsid`/process-group kill, or issues a `pkill -P <pid>`-style cleanup on cancellation. So there is no mechanism that stops an attacker's detached background process. This directly breaks the stated invariant ("job cancellation must terminate all processes spawned by the job on the remote SSH host") for the SSH executor.

### Impact Explanation
An unprivileged pipeline author using the SSH executor can submit a job whose script backgrounds and detaches a long-running or resource-consuming process (e.g., `nohup sleep 86400 &`, a crypto-miner, a network listener, or a fork-bomb-lite loop) before the job's normal completion or before cancellation. When the job is cancelled/timed out (`ctx.Done()` → `session.Signal(SIGKILL)` + `session.Close()`), the Runner reports the job as terminated, but the orphaned process continues running on the shared SSH host. On a shared/multi-tenant SSH target this yields persistent resource exhaustion / job-independent process survival — exactly the scoped impact of "persistent multi-tenant disruption via orphaned processes surviving job cancellation."

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged user's control: they only need a project configured to use the SSH executor (a legitimate, documented Runner executor for shared hosts) and the ability to control `.gitlab-ci.yml` script content, which every pipeline author has. The technique (`nohup cmd &`, `setsid`, `disown`) is a standard, well-known shell idiom, requiring no special host privileges — this is highly repeatable and does not depend on any other misconfiguration.

### Recommendation
On the remote host, wrap the launched job command in its own session/process group (e.g., run `setsid` implicitly, or capture the shell's PID and, on cancellation, execute a follow-up remote command such as `pkill -KILL -P <pid>` or kill the whole process group via `kill -KILL -- -<pgid>`) so that all descendants — including backgrounded/detached ones — are terminated. Alternatively/additionally, track and terminate the process group explicitly by requesting the shell's PID at start and issuing a second SSH exec (`kill -- -$(ps -o pgid= <pid>)`) during cancellation, since a single `ssh.SIGKILL` channel signal to the primary session channel is not guaranteed to reach detached children.

### Proof of Concept
```go
// helpers/ssh/ssh_command_integration_test.go (new, build tag integration)
func TestRun_CancelledJobLeavesDetachedProcessRunning(t *testing.T) {
    s, err := ssh.NewStubServer("testuser", "testpass") // or real sshd container
    require.NoError(t, err)
    defer s.Stop()

    c := s.Client()
    require.NoError(t, c.Connect())
    defer c.Cleanup()

    ctx, cancel := context.WithCancel(context.Background())
    var stdout, stderr bytes.Buffer

    go func() {
        time.Sleep(1 * time.Second)
        cancel() // simulate job cancellation
    }()

    err = c.Run(ctx, ssh.Command{
        Command: "bash",
        // marker file lets us check survival after Run() returns
        Stdin:   "nohup sh -c 'sleep 600; touch /tmp/marker_finished' >/tmp/out 2>&1 < /dev/null & disown; sleep 5",
        Stdout:  &stdout,
        Stderr:  &stderr,
    })

    // Run should return (job cancelled)
    require.Error(t, err)

    // Give remote side time, then assert the detached process is STILL running
    time.Sleep(2 * time.Second)
    out, _ := exec.Command("ssh", "testuser@host", "pgrep -f 'sleep 600'").CombinedOutput()
    assert.NotEmpty(t, out, "expected detached 'sleep 600' process to still be running after cancellation, proving orphan survives job termination")
}
```
Expected assertion: `pgrep -f 'sleep 600'` (or checking that `/tmp/marker_finished` eventually appears despite the job having been reported cancelled) confirms the detached process outlives `session.Signal(SIGKILL)`/`session.Close()`, proving processes spawned by a cancelled job are not reliably terminated.
