## Finding: Gloas builder withdrawal amount can exceed the deducted builder balance, printing uncollateralized Gwei

### Title
Builder sweep/pending withdrawal amount sent to the execution layer is not capped to the builder's actual balance before ledger deduction — ([File: specs/gloas/beacon-chain.md])

### Summary
This is the same bug class as the fee-on-transfer report: an external, irrevocable value movement (`amount`) is computed from one source of truth, while the internal ledger deduction is computed from a different, possibly smaller, value — with no "measure before/after" reconciliation. In `specs/gloas/beacon-chain.md`, `get_builder_withdrawals` places the queued `BuilderPendingWithdrawal.amount` directly into the `Withdrawal` object that is committed to the execution payload (real ETH credited to `fee_recipient`), while `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from `state.builders[...].balance`. [1](#0-0) [2](#0-1) 

### Finding Description
`get_builder_withdrawals` (line 1802) iterates `state.builder_pending_withdrawals` and, for each entry, constructs a `Withdrawal` whose `amount` is taken verbatim from the queued `BuilderPendingWithdrawal.amount`:

```python
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal.amount,
    )
)
``` [3](#0-2) 

This `Withdrawal` list becomes `state.payload_expected_withdrawals`, which the execution payload must match exactly (`assert list(payload.withdrawals) == expected.withdrawals` in the phase0/capella pattern this spec follows). The EL then credits `fee_recipient` with the full `amount` — an unconditional, irrevocable Gwei payment.

`apply_withdrawals`, however, only reduces the internal builder balance by the *minimum* of that same amount and whatever the builder's current balance happens to be:

```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [2](#0-1) 

If `withdrawal.amount > builder_balance` at execution time, the EL still pays out the full `withdrawal.amount` to `fee_recipient`, but the beacon state only zeroes out the builder's (smaller) balance. The difference — `withdrawal.amount - builder_balance` — is Gwei paid to a non-owner that was never subtracted from any account: it breaks the total-supply/asset-conservation invariant the spec elsewhere explicitly protects (the withdrawal mechanism is precisely why the note at the top of this section stresses "withdrawal balance deductions are applied immediately... to not break the total supply invariant").

The test helper for this exact function acknowledges the capping behavior only on the *balance* side, without asserting the EL-side `amount` is likewise capped:
```python
expected_deduction = min(total_amount, pre_balance)
assert post_balance == pre_balance - expected_deduction, ...
``` [4](#0-3) 

This confirms the spec's own reference test suite treats "amount sent to EL != amount deducted from ledger" as expected/normal, rather than guarding against it — i.e. the mismatch is a structural gap, not a corner case caught by tests.

### Impact Explanation
This falls under "Gwei created, destroyed or paid to a non-owner" (Critical) per the rules: value paid out to `fee_recipient` on the execution layer that is not backed by a corresponding decrease anywhere in the consensus-layer ledger is Gwei created from nothing. Any spec-following node applying this transition would accept a block that mints ETH on the execution layer without conservation on the beacon chain, which is a safety-relevant invariant violation, not merely an accounting nit.

### Likelihood Explanation
The precondition — builder's `balance` falling below the amount already queued in `builder_pending_withdrawals` before settlement occurs — depends on the builder-payment/deposit/exit mechanics (`settle_builder_payment`, `process_builder_deposit_request`, `process_builder_exit_request`) that determine whether balance can be reduced (e.g., by another concurrent settlement, an exit, or a partial withdrawal) between the time a payment is queued and the time it's paid out. I was not able to fully trace `settle_builder_payment` and the builder deposit/exit request handlers within the available context to confirm whether they already enforce that queued withdrawal amounts can never exceed available balance at settlement time. If such an invariant is enforced elsewhere, the `min()` in `apply_withdrawals` would be dead code and this would not be exploitable; if not, this is directly reachable by any builder participating in payment flow. This gap in verification should be resolved before treating this as fully confirmed.

### Recommendation
- Cap the `Withdrawal.amount` placed into `payload_expected_withdrawals` in `get_builder_withdrawals` (and `get_builders_sweep_withdrawals`, which already correctly uses the live `builder.balance`) to `min(withdrawal.amount, state.builders[builder_index].balance)` at construction time, so the amount committed to the execution layer can never exceed what is actually deducted.
- Alternatively, enforce and clearly document an invariant (with an explicit assertion) at the point `BuilderPendingWithdrawal` entries are queued (in `settle_builder_payment`) guaranteeing `amount <= builder.balance` and that the balance cannot drop below the queued amount before settlement.

### Proof of Concept
1. A builder's payment is queued into `state.builder_pending_withdrawals` with `amount = X` via `settle_builder_payment`/`process_parent_execution_payload` (line 1764-1770 shows a direct append path when the payment entry is evicted from `builder_pending_payments`).
2. Before this entry is processed by `get_builder_withdrawals`, the builder's `state.builders[builder_index].balance` is reduced below `X` through any legitimate path that decreases builder balance (e.g., another settlement or exit against the same builder).
3. `get_expected_withdrawals` → `get_builder_withdrawals` emits `Withdrawal(amount=X, address=fee_recipient, ...)` unconditionally. [5](#0-4) 
4. The execution payload must include this withdrawal crediting `fee_recipient` with `X` Gwei.
5. `apply_withdrawals` runs `state.builders[builder_index].balance -= min(X, builder_balance)`, deducting only `builder_balance < X` from the ledger. [2](#0-1) 
6. Net effect: `X - builder_balance` Gwei has been credited on the execution layer with no corresponding decrease anywhere in the beacon state — Gwei created and paid to `fee_recipient`, breaking supply conservation, while every node that follows this exact spec text accepts the block as valid.
