### Title
Stale confirmations from removed multisig members are counted toward the confirmation threshold, allowing execution of a request below the live-member quorum - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm()` trusts the raw size of the stored `confirmations` set for a request as the number of *live* approvals needed to reach `num_confirmations`. When a member is removed via `DeleteMember`, `delete_member()` only purges requests that member *created* — it never scrubs that member's confirmation out of other members' pending requests. A confirmation recorded by an account that is later removed from the multisig therefore remains valid forever and can be combined with fewer live members' confirmations to reach quorum and execute an arbitrary request (e.g. a `Transfer`), bypassing the K-of-N guarantee the contract is supposed to enforce.

### Finding Description
`confirm()` increments/checks confirmations purely by count: [1](#0-0) 

`delete_member()` is only invoked to clean up requests whose *creator* (`r.member`) is the account being removed — it does not scan the `confirmations: LookupMap<RequestId, HashSet<String>>` map for other requests that the removed member had separately confirmed: [2](#0-1) 

Because `confirmations` for a request that was created by *someone else* is never touched when one of its confirmers is later deleted, that stale confirmation string stays in the `HashSet<String>` and continues to count toward `confirmations.len() as u32 + 1 >= self.num_confirmations` in `confirm()`.

The equality this breaks is: `confirmations actually counted == confirmations from members currently in self.members`. After a `DeleteMember` action succeeds, this invariant is violated for any request that the removed member confirmed but did not create.

The identical pattern exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` filters `self.requests` by `r.signer_pk == pk` (the creator key) but does not purge that key from `confirmations` sets of requests created by other keys: [3](#0-2) 

### Impact Explanation
This lets a coalition of *fewer* than `num_confirmations` currently-valid members execute any multisig action, including `Transfer` of the account's NEAR balance, `AddKey`/`AddMember` (privilege escalation), or `DeployContract` (code takeover). This is a direct "multisig request executed below threshold" case — Critical impact per the given rules, since it allows unauthorized asset movement or account takeover by less than the required quorum of active signers.

### Likelihood Explanation
Requires a normal, expected sequence of legitimate multisig operations with no attacker-controlled deployment or foundation privilege:
1. A member is removed at some point (a routine key-rotation/membership-change action, which multisig explicitly supports via `DeleteMember`/`DeleteKey`).
2. That member had previously confirmed (not created) some other pending request before being removed.
3. Any subsequent confirmations from remaining live members can then complete quorum together with the stale confirmation.

This does not require exploiting a redeploy, an off-chain party, or a victim key — only ordinary use of `AddMember`/`DeleteMember`/`confirm`, all reachable by the account's own defined members using documented methods. Likelihood is Medium: it needs a membership change to occur while a request confirmed by the outgoing member is still pending, which is a realistic operational scenario for any multisig managing membership over time.

### Recommendation
When executing `DeleteMember` (or `DeleteKey` in v1), iterate all requests' `confirmations` sets (not just those created by the removed member) and strip the removed member's confirmation from each, or re-validate `confirmations` against `self.members` at the moment of the quorum check in `confirm()` — i.e., only count entries in the confirmations set that are still `self.members.contains(&member)` before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig deployed with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `B` calls `add_request_and_confirm(Transfer{amount})` → request `R` created with `confirmations = {B}`.
3. `A` calls `confirm(R)` → `confirmations = {B, A}` (2 confirmations, below quorum of 3, so `R` stays pending).
4. Separately, members `B, C, D` reach quorum (3-of-4) on a `DeleteMember{member: A}` request and execute it. `delete_member()` only purges requests where `r.member == A` — since `R.member == B`, `R` and its `confirmations = {B, A}` are left untouched, even though `A` is no longer a member.
5. `C` calls `confirm(R)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` fires the `Transfer`, even though only `B` and `C` are actually still-live confirming members (2 of the 3 remaining members: B, C, D), not the required 3-of-4 original quorum.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
