### Title
Stale Confirmations From Removed Multisig Members Bypass The Live-Member Confirmation Threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` authorizes execution of a request purely by counting entries in a `HashSet<String>` of confirmations, without verifying that each confirming identity is still a current member of the multisig [1](#0-0) . `delete_member` (and the equivalent `DeleteKey` action in the older `multisig` contract) only purges confirmations tied to requests *originated by* the removed member; it never scrubs that member's confirmation entries from other, still-pending requests they had previously confirmed [2](#0-1) . This is directly analogous to the reported bug class: a recorded value (confirmation count) diverges from the real state it is supposed to represent (live, currently-authorized members), letting a threshold be satisfied using stale data.

### Finding Description
Confirmations are stored as `confirmations: LookupMap<RequestId, HashSet<String>>` [3](#0-2) . When a member confirms a request that doesn't yet reach `num_confirmations`, their identity string is simply inserted into that request's set [1](#0-0) .

`delete_member` removes a member and cleans up state, but the cleanup only targets requests where `r.member == member`, i.e. requests the removed member *authored*: [4](#0-3) 
It does not scan `self.confirmations` for entries where the removed member had merely *confirmed* someone else's still-open request. That stale confirmation string remains in the `HashSet<String>` for that request indefinitely.

Later, when remaining live members confirm that same request, `confirm()` computes `confirmations.len() as u32 + 1 >= self.num_confirmations` and executes once the threshold is met [5](#0-4) . Because the stale entry still counts toward `confirmations.len()`, the request can execute with fewer *live* members having actually confirmed than `num_confirmations` requires — breaking the equality `confirmations counted == live members who confirmed`.

The original `multisig/src/lib.rs` has the identical pattern: `DeleteKey` only clears confirmations for `requests` where `r.signer_pk == pk` (the deleted key's own requests), not confirmations that key cast on other pending requests [6](#0-5) , while `confirm()` counts `confirmations.len()` the same way [7](#0-6) .

### Impact Explanation
This crosses the threshold-authorization boundary called out in scope: "confirmations counted versus live members." A multisig request (e.g. `Transfer`, `AddKey`/`AddMember`, `FunctionCall` with attached deposit) can be executed with effectively fewer authorized live signers than `num_confirmations`, since one or more counted confirmations belong to accounts/keys that have since been removed from the multisig. This can result in NEAR being moved, or privileged actions (adding a new full-access key, changing `num_confirmations`) being taken, below the intended authorization threshold — a Critical-tier outcome ("a multisig request executed below threshold").

### Likelihood Explanation
The trigger sequence is fully reachable by legitimate multisig operations without any special privilege beyond being (at some point) a member: a member confirms a pending request that doesn't hit the threshold, that member is later removed via a separate, unrelated `DeleteMember`/`DeleteKey` request, and the original request remains open (it is common for large-`n`/small-`k` multisigs to have several outstanding requests awaiting quorum). No malicious redeploy or foundation action is required — this is a straightforward interaction of two documented flows (`confirm` and `delete_member`) that the contract itself supports.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all entries in `confirmations` (not just requests authored by that member) and remove the member's identity from every confirmation set. Alternatively, validate at `confirm()`/execution time that every entry in a request's confirmation set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g. `Transfer` of contract funds), and `B` calls `confirm(R)` — confirmations for `R` = `{A, B}` (2/3).
3. Via a separate, already-fully-confirmed request, `B` is removed as a member using `DeleteMember { member: B }`. `delete_member` only cleans up requests *authored* by `B`; `R` (authored by `A`) is untouched, so `B`'s stale confirmation remains in `confirmations[R]` [8](#0-7) .
4. `C` (a genuinely live member) calls `confirm(R)`. `confirmations.len()` is now 3 (`A`, `B`(stale), `C`), which is `>= num_confirmations`, so `execute_request` runs the `Transfer` [9](#0-8) .
5. The transfer executes with only 2 live members (`A`, `C`) ever having confirmed it as current members — one confirmation short of the actual 3-of-current-members threshold the contract is supposed to enforce.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
