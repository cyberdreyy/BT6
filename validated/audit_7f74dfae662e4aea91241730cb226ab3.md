### Title
Loss-adjusted withdraw receipts are paid at par when a newer request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a `stopEpochWithDuration` loss partially funds pending withdraw receipts, the haircut is recorded in `lossRecoveryPriceByEpoch[epochNumber]`. The loss-adjusted claim path only clears the receipt keyed by `lastWithdrawRequest[_user]`. If the same user makes a second `requestWithdraw` in a later epoch, `lastWithdrawRequest[_user]` is overwritten, so the haircutted epoch's `withdrawsRequestsByEpoch` entry is never cleared and is instead paid at full par through `_claimFundedWithdrawRequest`. The user extracts more underlying than was funded, leaving the strategy insolvent for other claimants.

### Finding Description
`requestWithdraw` records per-epoch receipt ownership and overwrites the user's last-request epoch marker (`contracts/strategies/idle/IdleCreditVault.sol:282` — `lastWithdrawRequest[_user] = currentEpoch`).

When the borrower under-funds pending receipts at epoch stop, `collectWithdrawFunds` stores the recovery price per epoch and zeroes `pendingWithdraws`: [1](#0-0) 

The claim path applies the haircut only for the epoch stored in `lastWithdrawRequest[_user]`: [2](#0-1) 

`_clearWithdrawClaimForEpoch` is the only place that removes a haircutted epoch's `withdrawsRequestsByEpoch` entry from the aggregate `withdrawsRequests[_user]` (lines 815-820). If the user opens a second withdraw request in a later epoch, `lastWithdrawRequest[_user]` points to the new epoch, `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` is 0, `_claimLossAdjustedWithdrawRequest` returns 0, and `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still contains the haircutted epoch's full amount — at par: [3](#0-2) 

The only gate is `epochNumber <= lastWithdrawRequest[_user]` (line 326), which merely forces the user to wait one more epoch; it does not check for uncleared loss-adjusted epochs. The strategy contract only received `pendingBasis * lossRecoveryPrice / RECOVERY_FULL` for the defaulted epoch, so the excess payout is drawn from funds backing other users' funded receipts (or causes a revert that permanently freezes the next claimants' receipts).

### Impact Explanation
Broken invariant: one receipt, haircut-adjusted payout. An unprivileged KYC-passing lender can claim `amount * (1 - lossRecoveryPrice/RECOVERY_FULL)` more than was funded. With e.g. a 100k request haircut at 50%, the attacker drains ~50k underlying belonging to other pending receipt holders; subsequent `claimWithdrawRequest` calls either revert (permanent freezing of unclaimed funded receipts) or are paid by consuming whatever remains, i.e. direct theft / insolvency quantified at the unpaid haircut portion.

### Likelihood Explanation
Requirements are all reachable by unprivileged actors around honest privileged calls: (1) an epoch ends via `stopEpochWithDuration` with `_lossAmount > 0` such that `collectWithdrawFunds` takes the under-funded branch (manager action, but a normal bad-debt event, not attacker-controlled); (2) the attacker has a pending receipt in that epoch and later submits another `requestWithdraw` (allowed whenever `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are set and the wallet passes Keyring); (3) after one more epoch elapses, `claimWithdrawRequest` pays the stale haircutted amount at par. No existing guard (`_onlyIdleCDO`, epoch gating, `defaultRecoveryFinalized` branch ordering) prevents it — `_claimDefaultedWithdrawRequest` only handles `defaultRecoveryEpoch`, not `lossRecoveryPriceByEpoch` entries.

### Recommendation
Iterate all epochs with non-zero `lossRecoveryPriceByEpoch` for which `withdrawsRequestsByEpoch[_user][e] != 0`, or track a per-user earliest unclaimed loss epoch, so `_claimLossAdjustedWithdrawRequest` clears every haircutted receipt at its recovery price rather than only the one matching `lastWithdrawRequest`. Alternatively, in `_claimFundedWithdrawRequest`, subtract any epoch whose `lossRecoveryPriceByEpoch` is non-zero from the par-paid aggregate before transferring.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
