### Title
`ProvisionerV2.redeem()` can be permanently DoS'd when the configured yield-source pull reverts, freezing user withdrawals - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.redeem()` (the ordinary-user synchronous withdrawal path) calls `_syncRedeem`, which in turn calls `_pullFundsIfNeeded` to top up the vault's idle balance by invoking `IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data)` against a configured external yield source. This call is **not** wrapped in try/catch and is expected to revert on failure ("reverts on failure" per the code comment), unlike the symmetric `_pushFundsIfConfigured` path which explicitly swallows failures. If the underlying yield-source integration reverts (e.g., due to a withdrawal timelock, insufficient liquidity, or a paused external protocol), every `redeem()` call for that token permanently reverts until the external condition clears, mirroring the Knox/Premia pattern where an embedded external-pool withdrawal call blocks the entire withdraw/fee-collection flow.

### Finding Description
The ordinary-user entrypoint `redeem()` at [1](#0-0)  calls `_syncRedeem`, which unconditionally calls `_pullFundsIfNeeded(token, tokensOut)` before exiting the vault: [2](#0-1) 

`_pullFundsIfNeeded` computes the shortfall between the vault's idle balance and the required `tokensOut`, then performs a hard (non-try/catch) call to `IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data)`, which the doc comment explicitly states "reverts on failure": [3](#0-2) 

This is asymmetric with the deposit-side `_pushFundsIfConfigured`, which deliberately swallows failures via a low-level `.call`: [4](#0-3) 

The `submit` call ultimately triggers an arbitrary encoded operation against an external yield-source protocol (set once via `setTokenDetails`/SSTORE2 pointer by an authorized role). If that external protocol imposes a withdrawal timelock, requires a cooldown, or simply lacks sufficient liquidity at call time — exactly the root cause described in the Knox/Premia report (`depositedAt + 1 days < block.timestamp` type locks, or insufficient pool liquidity) — the `submit` call reverts, and because there is no try/catch, the revert propagates all the way up through `_syncRedeem` to `redeem()`, reverting the entire user transaction.

Because `redeem()` is the primary synchronous withdrawal path for ordinary users (guarded only by `anyoneButVault`, `nonReentrant`, `solvingNotPaused`), any user attempting to redeem when the vault's idle balance for that token is insufficient is forced through this pull path. There is no fallback, no partial-fill logic, and no circuit breaker distinguishing "temporarily illiquid external source" from "broken configuration" — the transaction simply reverts, and it will keep reverting for all subsequent redeemers of that token until the external protocol's lock/liquidity condition resolves or the admin removes the `pullFundsSubmitDataPointer` configuration.

### Impact Explanation
While the external yield source is locked or illiquid, **every** `redeem()` call for the affected token that requires pulling funds (i.e., whenever idle vault balance < requested `tokensOut`) reverts, freezing user access to their underlying tokens through the synchronous redeem path. This is a temporary freeze of user funds tied to third-party integration behavior chosen and wired by the vault operator (via `setTokenDetails`), analogous to the original Knox finding where Premia's `withdraw()` timelock blocked `_collectPerformanceFee`/`_withdraw`. This matches a Medium-severity "temporary freeze of funds" classification under typical Immunefi bounty scales, since funds are not stolen but ordinary users cannot withdraw via this path until liquidity/timelock conditions clear (asynchronous `requestRedeem`/`solveRequestsVault`/`solveRequestsDirect` paths remain available as a workaround, which somewhat mitigates severity — see Likelihood).

### Likelihood Explanation
Requires: (1) the vault admin has configured a `pullFundsSubmitDataPointer` for the token (an intentional, expected configuration for yield-bearing tokens), and (2) the vault's idle balance is insufficient to cover a redeem, forcing the pull, and (3) the external yield-source withdrawal is currently locked/illiquid/reverting. Conditions (2) and (3) are common operational states for real yield integrations (e.g., lending markets with withdrawal queues, timelocked strategies, or temporarily drained liquidity pools) and are not attacker-controlled — they occur naturally whenever the vault has deployed capital and market conditions restrict withdrawal at that exact moment, exactly as in the original report's Premia liquidity lock. This is a realistic, non-adversarial precondition rather than a contrived edge case.

### Recommendation
Wrap the `_pullFundsIfNeeded` call to the external yield source in a try/catch (mirroring the `_pushFundsIfConfigured` failure-swallowing pattern), and if the pull fails, either (a) revert with a specific, catchable error that front-ends can surface distinctly, or (b) fall back to allowing partial/async redemption via the existing `requestRedeem`/solver path instead of hard-reverting the entire synchronous redeem. At minimum, document and rate-limit the amount of idle balance the vault should always retain (a "liquidity buffer") so synchronous redeems rarely need to touch the potentially-locked external position.

### Proof of Concept
1. Deploy `MultiDepositorVault` + `ProvisionerV2` + `PriceAndFeeCalculatorV2` per test harness; enable `syncRedeemEnabled` for a token via `setTokenDetails`, and set a `pullFundsSubmitDataPointer` (via SSTORE2) that encodes a `submit()` operation calling a mock external "yield source" contract's `withdraw()` function.
2. Deploy the mock yield source to revert on `withdraw()` when `block.timestamp < depositedAt + 1 days` (mirroring Premia's `liq lock 1d`), and deposit vault idle funds into it so the vault's own token balance is now insufficient to cover a typical redeem.
3. As an ordinary user, call `deposit()` to receive vault units, then immediately call `redeem(token, unitsIn, minTokensOut, receiver)` for an amount exceeding current idle balance.
4. Assert the transaction reverts with the mock's `"liq lock 1d"`-style error, propagated through `_pullFundsIfNeeded` → `_syncRedeem` → `redeem()`, confirming the ordinary user cannot withdraw despite holding valid, unlocked vault units (`userUnitsRefundableUntil[msg.sender] < block.timestamp` passes) and despite `solvingNotPaused` and cap checks all passing.
5. Repeat for multiple users/blocks within the lock window to show the freeze is persistent and affects all redeemers of that token, not just the caller.

    /// @notice Pull funds from yield source if vault idle balance is insufficient
    /// @param token The redeem token
    /// @param tokensOut The amount of tokens needed for the redeem
    function _pullFundsIfNeeded(IERC20 token, uint256 tokensOut) internal {
        // Interactions: check vault's idle balance of the redeem token
        uint256 idleBalance = token.balanceOf(MULTI_DEPOSITOR_VAULT);
        if (idleBalance >= tokensOut) return;

        // Requirements: pull-funds submit data must be configured
        address pointer = tokensDetails[token].pullFundsSubmitDataPointer;
        require(pointer != address(0), Aera__PullFundsSubmitDataNotSet());

        // Effects: compute shortfall and store in transient storage
        uint256 shortfall;
        unchecked {
            // Unchecked: idleBalance < tokensOut checked above
            shortfall = tokensOut - idleBalance;
        }
        _storeAmount(shortfall);

        // Interactions: read submit data from SSTORE2 and call vault.submit (reverts on failure)
        bytes memory data = SSTORE2.read(pointer);
        IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data);
    }

    /// @notice Push deposited funds to yield source if configured
    /// @param tokenDetails The token details storage reference
    /// @param tokensIn The amount of tokens deposited
    function _pushFundsIfConfigured(TokenDetailsV2 storage tokenDetails, uint256 tokensIn) internal {
        // Interactions: check if push-funds submit data is configured (packed in tokensDetails slot)
        address pointer = tokenDetails.pushFundsSubmitDataPointer;
        if (pointer == address(0)) return;

        // Effects: store amount in transient storage
        _storeAmount(tokensIn);

        // Interactions: read submit data from SSTORE2 and call vault.submit (swallow failures)
        bytes memory data = SSTORE2.read(pointer);
        // solhint-disable no-unchecked-calls
        // slither-disable-next-line unchecked-lowlevel
        MULTI_DEPOSITOR_VAULT.call(abi.encodeCall(IBaseVault.submit, (data)));
        // solhint-enable no-unchecked-calls
    }

    function _syncRedeem(
        IERC20 token,
        uint256 tokensOut,
        uint256 unitsIn,
        address receiver,
        uint256 epochRedeemNumeraire,
        uint256 priceTimestamp
    ) internal {
        // Effects: roll epoch if PFC timestamp changed
        uint256 epochRedeemedNumeraire = _rollEpochIfNeeded(priceTimestamp);

        // Interactions: compute epoch cap
        (uint256 epochCapNumeraire,) = _computeEpochCap();

        // Requirements + Effects: check epoch cap and track redemption
        _requireEpochCapNotExceeded(epochRedeemNumeraire, epochCapNumeraire, epochRedeemedNumeraire);

        // Interactions: pull funds from yield source if vault idle balance is insufficient
        _pullFundsIfNeeded(token, tokensOut);

        // Interactions: exit vault — burns units from caller, sends tokens to receiver
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).exit(msg.sender, token, tokensOut, unitsIn, receiver);

        // Log redeemed event
        emit Redeemed(msg.sender, receiver, token, unitsIn, tokensOut);
    }
