### Title
Missing `InvalidFeeAmounts` invariant check in `createDstEscrow` causes underflow-revert lock of destination withdrawals - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
This is the same root-cause class as the external report ("`getBidValue()` is not always used"): an invariant that is enforced when a value is computed in one code path (`_postInteraction`) is silently skipped in the structurally analogous path (`createDstEscrow`) that consumes the same field. `BaseEscrowFactory._postInteraction` explicitly checks `integratorFeeAmount + protocolFeeAmount >= takingAmount` before allowing the source escrow to be created, but `BaseEscrowFactory.createDstEscrow`, which deploys `EscrowDst` with an attacker-suppliable `dstImmutables.parameters` field carrying the same `protocolFeeAmount`/`integratorFeeAmount` values, performs no equivalent check. [1](#0-0) [2](#0-1) 

### Finding Description
`_postInteraction` computes `integratorFeeAmount`/`protocolFeeAmount` and rejects the src-escrow creation if their sum is `>= takingAmount`: [1](#0-0) 

However, `createDstEscrow` takes a fully caller-supplied `Immutables` struct, including its `parameters` bytes field, and deploys `EscrowDst` from it with no comparable check on the fee fields relative to `dstImmutables.amount`: [2](#0-1) 

`ImmutablesLib` exposes `protocolFeeAmountCd`/`integratorFeeAmountCd` purely as raw reads of `immutables.parameters` with no bound relative to `immutables.amount`: [3](#0-2) 

`EscrowDst._withdraw` then subtracts both fee amounts from `immutables.amount` without any prior validation that the subtraction is safe: [4](#0-3) 

Because `createDstEscrow` is a permissionless, `external payable` function callable by any taker/resolver with a fully attacker-chosen `Immutables.parameters` value, an unprivileged caller can deploy a destination escrow whose `parameters` encode `protocolFeeAmount + integratorFeeAmount > amount`. Since `EscrowDst.withdraw`/`publicWithdraw` require the caller to resupply the exact same `Immutables` that were used at deployment (validated only by `onlyValidImmutables`, which merely checks the CREATE2 address, not the fee arithmetic), the underflow will occur on *every* future withdraw attempt for that specific deployed clone, in Solidity 0.8's checked-arithmetic mode causing a revert.

### Impact Explanation
This matches the Medium-risk bounty category: "smart contract unable to operate because required token/native balances can be broken by an unprivileged actor." Once such a destination escrow is deployed with malformed fee parameters, `withdraw`/`publicWithdraw` can never succeed for it — the maker can never receive their destination tokens through the intended path, only a `cancel` after the cancellation timelock can return the taker's own deposited funds. This breaks the atomic-swap withdrawal invariant for that swap instance during its live lifecycle, matching the "temporary freezing of funds during the live swap lifecycle" impact bar as well, since the maker's expected settlement path is permanently unusable for that specific escrow instance even though the taker can eventually recover their own funds via cancellation.

### Likelihood Explanation
Likelihood is bounded by the off-chain verification step described in the protocol design (the maker's client is expected to check the deployed `EscrowDst`'s parameters before revealing the secret), so a diligent maker would refuse to reveal the secret to a misconfigured escrow. However, the contract itself provides no on-chain guard equivalent to the one used in `_postInteraction`, so the invariant relies entirely on off-chain honesty/verification rather than a symmetric on-chain check — exactly the inconsistency pattern flagged in the source report. Any resolver (an unprivileged, permissionless caller of `createDstEscrow`) can trigger this by construction; no privileged role is required.

### Recommendation
Add the same fee-sum validation used in `_postInteraction` to `createDstEscrow`, e.g.:
```solidity
uint256 integratorFeeAmount = immutables.integratorFeeAmount();
uint256 protocolFeeAmount = immutables.protocolFeeAmount();
if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
placed before `_deployEscrow` is called in `createDstEscrow`, mirroring `contracts/BaseEscrowFactory.sol#L92`.

### Proof of Concept
1. Taker calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.amount = 100`, and `dstImmutables.parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 60` (sum `120 > 100`), self-funding the required `msg.value`/ERC20 transfer per `contracts/BaseEscrowFactory.sol#L165-L182`.
2. `EscrowDst` clone is deployed successfully; no check rejects the malformed fee split.
3. After `DstWithdrawal` stage begins, taker (or anyone with the secret) calls `withdraw(secret, immutables)`.
4. Inside `_withdraw`, `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` (`contracts/EscrowDst.sol#L92`) underflows and reverts under Solidity 0.8 checked arithmetic — withdraw is permanently impossible for this specific escrow, leaving only `cancel` (returns funds to the taker, not the maker) as the only viable path once the cancellation timelock elapses.

        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
