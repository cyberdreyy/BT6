### Title
Instant-withdraw claims never decrement `instantWithdrawClaimsByEpoch`/`instantWithdrawsRequestsByEpoch`, inflating the default recovery basis and stranding recovered funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records a receipt both per-user (`instantWithdrawsRequestsByEpoch[user][epoch]`) and globally (`instantWithdrawClaimsByEpoch[epoch]`), but a normal pre-default `claimInstantWithdrawRequest` only clears `instantWithdrawsRequests[user]` — the per-epoch records are never decremented. When a later default is finalized, `defaultPendingClaimBasis` counts those already-paid receipts as outstanding defaulted-epoch claim basis, diluting `defaultRecoveryPrice` for every legitimate claimant and leaving the corresponding share of `defaultRecoveryReserve` stranded forever.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw` the strategy tracks claims in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

The funded-claim path `claimInstantWithdrawRequest` burns the user's receipt tokens and zeroes only the aggregate per-user counter:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) . Neither `instantWithdrawsRequestsByEpoch` nor `instantWithdrawClaimsByEpoch` is decremented — the only place that ever subtracts from them is `_claimDefaultedInstantWithdrawRequest`, which runs only after default finalization [3](#0-2) .

At default time, `defaultPendingClaimBasis` treats the *entire* `instantWithdrawClaimsByEpoch[epochNumber]` as outstanding claim basis whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `finalizeDefaultRecovery` divides the actual reserve by this inflated `totalBasis` to set `defaultRecoveryPrice` [5](#0-4) . `_defaultPrefundedInstantReserve` only corrects for the *funded-but-uncollected* remainder (`instantBasis - pendingInstant`) [6](#0-5) , not for claims that were funded *and already paid out*, whose underlying left the contract entirely.

The same class of stale-pointer/stale-index defect as CVE-2024-48957 (a cursor past its real data) applies here: the per-epoch accounting cursor never moves back when a claim is consumed, so finalization reads ghost basis.

### Impact Explanation
Any epoch that contains both (a) instant receipts that were funded and claimed, and (b) at least one still-pending instant receipt at default time, produces an inflated `totalBasis`. `defaultRecoveryPrice` is depressed proportionally, so every defaulted-epoch pending claimant, instant claimant, and active tranche holder recovers less than the true pro-rata share. The over-reserved portion of `defaultRecoveryReserve` has no claimant and remains locked in the strategy as unrecoverable dust (the reserve is only spendable via `_transferDefaultRecovery`, which is keyed to real claims) [7](#0-6) . Loss is quantified: `staleBasis / totalBasis` of all recovered funds are effectively burned; with a large claimed instant receipt the dilution is unbounded in relative terms.

### Likelihood Explanation
The trigger requires a non-defaulted epoch where instant withdrawals are partially processed: some requesters funded via `collectInstantWithdrawFunds` and claimed, while at least one request remains pending when the borrower defaults in the *same* epoch. Partial instant funding is an explicitly supported state (`pendingInstantWithdraws` vs. prefunded reserve logic exists precisely for it), so this is a reachable configuration whenever the CDO only partially covers the instant queue at `startEpoch`. No privileged misbehavior is needed; any tranche holder can create the stale basis simply by claiming a funded instant withdrawal.

### Recommendation
Mirror the normal-withdraw cleanup on the instant path: inside `claimInstantWithdrawRequest`, track each receipt's epoch (or decrement `instantWithdrawsRequestsByEpoch[_user][epochNumber]`/the user's request-epoch record and `instantWithdrawClaimsByEpoch`) so that paid claims are removed from the basis `defaultPendingClaimBasis` later reads. If per-user request epochs must be retained, store the request epoch alongside `instantWithdrawsRequests` and clear `instantWithdrawsRequestsByEpoch[_user][reqEpoch]` and `instantWithdrawClaimsByEpoch[reqEpoch]` on claim.

### Proof of Concept
```solidity
// Foundry fork PoC (sketch) — same epoch as default
// 1. userA and userB deposit AA; epoch starts (running phase).
// 2. userA.requestInstantWithdraw(xA); userB.requestInstantWithdraw(xB);
//    instantWithdrawClaimsByEpoch[N] = xA + xB
// 3. CDO partially funds: collectInstantWithdrawFunds(xA) -> pendingInstantWithdraws = xB
// 4. userA.claimInstantWithdrawRequest()  // paid xA in full
//    // instantWithdrawClaimsByEpoch[N] still = xA + xB  (BUG)
// 5. borrower fails to repay; manager calls stopEpoch -> defaulted()
// 6. finalizeDefaultRecovery(recovered, manager):
//    pendingBasis = pendingWithdraws + (xA + xB)   // xA is ghost basis
//    defaultRecoveryPrice = reserve / totalBasis   // diluted by xA
// 7. userB and active holders claim at the diluted price;
//    recovered * xA / totalBasis remains in defaultRecoveryReserve forever.
assertGt(creditVault.defaultRecoveryReserve(), dustBound); // stranded recovery
```

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
