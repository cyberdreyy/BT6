### Title
Unchecked subtraction of upfront withdrawal fees wraps to ~2^256, minting an unbounded strategy-token receipt that freezes or defaults the entire pool - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
`requestWithdraw` in `IdleCDOEpochVariant.sol` computes the withdraw receipt as `_underlyings = principal + interest - totalFees` (line 776) without validating that `totalFees <= principal + interest`. `totalFees` comes from `_totalWithdrawFees`, which returns the full upfront management fee charged over `epochDuration + remaining buffer` whenever that fee is `>= interest` (lines 900-906, 925-931). When the management fee exceeds `principal + interest`, the unchecked `uint256` subtraction wraps to a value near `2^256`. That wrapped value is passed to `IdleCreditVault.requestWithdraw`, which mints the user an equal amount of strategy tokens as a receipt and adds it to the global `pendingWithdraws` counter (`IdleCreditVault.sol:275-279`). This is a direct analog of CVE-2026-74444: an unvalidated subtraction that wraps, producing a bound/amount the downstream accounting treats as legitimate.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw` (lines 772-790):

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;   // unchecked: wraps if totalFees > principal + interest
pendingWithdrawFees += totalFees;
creditVault.requestWithdraw(_underlyings, msg.sender, principal);
```

`_totalWithdrawFees` (lines 900-906) returns `_mgmtFee` when `_mgmtFee >= _interest`, where `_mgmtFee = _calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration())` and the duration is `epochDuration + bufferEnd - block.timestamp` (lines 925-931). The upfront fee is proportional to principal times fee rate times a duration that can exceed one year (long `epochDuration` plus a full remaining buffer). There is no guard that `_mgmtFee <= principal + interest` — the exact "reject undersized headers up front" precondition the kernel patch adds. On underflow, `IdleCreditVault.requestWithdraw` (`IdleCreditVault.sol:243-294`) executes `_mint(_user, _amount)` with `_amount` ~2^256 and `pendingWithdraws += _amount`, so the receipt is real: one attacker transaction manufactures a strategy-token claim orders of magnitude larger than all TVL.

Existing guards do not stop it: `_skimDonatedAssets`, the `lossRecoveryPrice` revert-guard, `lastWithdrawRequest` bookkeeping, and epoch gating are all downstream and never bound `_amount` against the user's actual balance. `maxWithdrawable` (lines 911-918) contains the same unchecked pattern but is view-only.

### Impact Explanation
Two failure modes, both qualifying:

1. **Permanent freezing of all funds.** `pendingWithdraws` becomes ~2^256. At `stopEpoch`, the borrower can never fund it. `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` → 0, and `IdleCreditVault.sol:419` reverts on a zero price, so loss-adjusted funding is impossible. The pool can only resolve via default; after `finalizeDefault`, `defaultPendingClaimBasis()` is dominated by the wrapped amount so `defaultRecoveryPrice` rounds to ~0 for every receipt — every honest withdrawer and active LP's claims are effectively frozen/worthless. All pool funds are locked permanently.

2. **Theft via claim ordering.** Any claim that resolves before the catastrophic epoch settles (`_claimFundedWithdrawRequest`, `_transferFundedClaim`) transfers real underlying; the wrapped receipt also gives the attacker a strategy-token balance large enough to dominate any default recovery distribution, diluting all other claimants.

Quantified loss: entire pool NAV and all pending/unclaimed yield.

### Likelihood Explanation
Requires a configuration where the upfront management fee exceeds principal plus projected interest — i.e., management fee rate × (epochDuration + remaining buffer) / 365d > ~100%. This needs long epoch durations (or a long buffer relative to deposit size) combined with a high management fee, both set by the honest owner — plausible for credit pools with multi-year epochs, but not guaranteed by default parameters. The attacker is any KYC-passing lender (unprivileged per scope). I could not fully verify `_calculateManagementFee`'s exact formula or whether a fee cap exists elsewhere in `IdleCDOCreditVault.sol`/`IdleCreditVaultFactory.sol` that would bound it below principal — if management fee is hard-capped such that fee ≤ principal + interest is guaranteed, severity drops to the revert-only (DoS) case, which still permanently freezes the receipt path. The subtraction itself is confirmed unchecked and unguarded.

### Recommendation
Mirror the kernel fix: validate the subtrahend before subtracting. In `requestWithdraw`, cap or revert:

```solidity
uint256 totalFees = _totalWithdrawFees(principal, interest);
require(totalFees <= principal + interest, "fees exceed claim");
// or clamp: _underlyings = totalFees >= principal + interest ? 0 : principal + interest - totalFees;
```

Apply the same guard in `maxWithdrawable` (line 917) so the view cannot wrap either, and consider capping `managementFee × maxDuration` at configuration time in `setFeeParams`/`setManagementFee`.

### Proof of Concept
Foundry fork test sketch (pattern follows `test/foundry/IdleCreditVault.t.sol`, e.g., `testRequestWithdrawNormal`):

```solidity
function testRequestWithdrawFeeUnderflow() external {
    // honest config: long epochDuration and high managementFee so that
    // _calculateManagementFee(principal, epochDuration + buffer) > principal + interest
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    _setManagementFee(20_000); // 20%/yr; with epochDuration ~5+yr fee > principal
    // alternatively long bufferPeriod pushes _withdrawRequestManagementFeeDuration up

    uint256 amountWei = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);

    // buffer phase, epoch not running
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // BUG: subtraction wrapped; receipt is astronomically large
    assertGt(requested, amountWei * 1e18); // >> principal
    assertEq(
        IdleCreditVault(address(strategy)).pendingWithdraws(),
        requested,
        'wrapped pending basis'
    );

    // Any subsequent startEpoch/stopEpoch cycle cannot fund pendingWithdraws;
    // collectWithdrawFunds(_amount < pendingBasis) computes price 0 and reverts,
    // so honest users' claims are permanently frozen / forced to ~0 recovery.
}
```

The PoC asserts that `requestWithdraw` returns (and `IdleCreditVault` mints) a receipt vastly exceeding the deposited principal, demonstrating the wrapped bound propagates into `pendingWithdraws` and breaks the solvency invariant the entire epoch/claim machinery depends on.
