### Title
APR0 dust withdrawal receipt permanently bricks `stopEpoch` after any APR change, freezing all vault funds — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2023-27789 is a crash/DoS triggered by an edge-case input reaching `cidr2cidr` — a single cheap call that kills the process. The strongest credit-vault analog is a liveness crash in the epoch state machine: an unprivileged, KYC-passing lender can plant a dust-sized APR=0 withdrawal receipt (`apr0TotalPrincipal > 0`). Once the honest manager subsequently sets a non-zero APR — a routine operation — `prepareStopEpochWithApr0` unconditionally reverts with `NotAllowed`, so `stopEpoch` can never execute again. Every LP's funds are permanently frozen; the only exit is a borrower default.

### Finding Description
`requestWithdraw` routes requests made while `unscaledApr == 0` into a separate bucket: it calls `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` (contracts/strategies/idle/IdleCreditVault.sol:285-286, 567+). At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which reverts whenever the bucket is non-empty but the current APR is no longer zero:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```
(contracts/strategies/idle/IdleCreditVault.sol:499-508)

The bucket can only be closed by:
1. `prepareStopEpochWithApr0` itself (line 540, `apr0TotalPrincipal = 0`) — unreachable because it reverts first;
2. `_clearWithdrawClaimForEpoch` with `_isClearingApr0` — reachable only through default-epoch claim paths (line 827).

Critically, the normal claim path does **not** decrement `apr0TotalPrincipal`: `_claimFundedWithdrawRequest` executes `delete apr0Users[_user]` but never touches the global counter (lines 346-348). So even if the attacker later claims their receipt, the dust remains in `apr0TotalPrincipal` and `stopEpoch` stays bricked. `setAprs`/`setApr` (lines 206-235) perform no check against `apr0TotalPrincipal`, so the honest manager has no on-chain warning that raising APR will freeze the pool.

### Impact Explanation
Broken invariant: epoch state machine liveness — permanent freezing of all user funds. After `epochEndDate`, every `manager.stopEpoch(...)` / `stopEpochWithDuration(...)` call reverts inside `prepareStopEpochWithApr0`. Withdraw receipt claims are gated on `epochNumber > lastWithdrawRequest`, which only advances via `stopEpoch`/deposit bookkeeping, so pending claimants cannot exit either. The entire vault NAV plus pending receipts are locked until the owner pushes the facility through the borrower-default path (`_handleBorrowerDefault` → `finalizeDefault`/`finalizeDefaultRecovery`), which crystallizes a loss instead of returning funds at par — i.e., a forced default on a solvent borrower. Quantified: 100% of `getContractValue()` plus `pendingWithdraws` is frozen; recovery requires invoking the default machinery on an otherwise healthy epoch.

### Likelihood Explanation
Low cost, plausible trigger sequence:
1. Buffer phase (or any period) where `unscaledApr == 0` — a supported "APR0 mode" exercised extensively in tests.
2. Attacker (any KYC-passing lender) calls `depositAA`/`depositBB` for a dust amount, then `requestWithdraw(1 wei-tranche, tranche)`. This burns principal, mints a receipt, and sets `apr0TotalPrincipal += 1` — no privileged action needed.
3. The honest manager later calls `setAprs(nonzero, ...)` to price the next epoch — routine and unchecked against the bucket.
4. From that block on, `stopEpoch` reverts deterministically. No honest call sequence recovers liveness short of default.

The attacker never needs another transaction; the crash is latent and detonates on the next routine manager action — mirroring the CVE where a single crafted input crashes a long-lived process at a later endpoint call.

### Recommendation
- In `prepareStopEpochWithApr0`, don't revert on `unscaledApr != 0`. Treat a non-zero APR as "APR0 receipts accrue no further interest": settle the bucket at `apr0RateByEpoch[epochNumber] = 0` (or last rate) and zero `apr0TotalPrincipal`, since `_settleApr0` already handles `rate == 0` gracefully.
- Alternatively/also: decrement `apr0TotalPrincipal` in `_claimFundedWithdrawRequest`/`delete apr0Users[_user]` so that a claimed receipt cannot leave a permanent dust bucket.
- Add a guard or warning in `setAprs` surfacing `apr0TotalPrincipal != 0` when raising APR from 0, so the state transition is explicit rather than a latent brick.

### Proof of Concept
Foundry fork test against `IdleCreditVault` / `IdleCDOEpochVariant` (modeled on the existing `testApr0Withdraw*` harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testApr0DustReceiptBricksStopEpoch() external {
  // Setup: pool in APR0 mode
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(0, 0);

  // Honest LP deposits
  idleCDO.depositAA(10_000 * ONE_SCALE);
  _startEpochAndCheckPrices(0);

  // Attacker: KYC'd lender, dust deposit + dust withdraw request
  address attacker = makeAddr('attacker');
  _depositWithUser(attacker, 10 * ONE_SCALE, true);   // isWalletAllowed'd
  uint256 dust = IERC20(AAtranche).balanceOf(attacker) / 1e6; // negligible receipt
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(dust == 0 ? 1 : dust, address(AAtranche));
  assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

  // Honest manager raises APR for next epoch - no on-chain warning
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, initialProvidedApr);

  // Epoch ends; every stopEpoch call now reverts -> funds permanently frozen
  deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.stopEpoch(0, 0);

  // Even the attacker claiming (if reachable) does not clear apr0TotalPrincipal,
  // because _claimFundedWithdrawRequest only deletes apr0Users[user].
  // The only remaining exits are borrower default or keeping APR == 0 forever.
}
```

Note: I was unable to fully verify in this pass whether a mid-epoch `deposit` bumping `epochNumber` (IdleCreditVault.sol:607-610) lets the attacker's claim path clear state before the APR change; however, since `delete apr0Users[_user]` never decrements `apr0TotalPrincipal`, the permanent revert holds regardless of whether the attacker's individual receipt is claimed.
