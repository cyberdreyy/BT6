### Title
Stale instant-withdraw epoch receipt is never cleared on claim, inflating `defaultPendingClaimBasis` and diluting/draining the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The nbd UAF is a classic freed-object-with-stale-reference bug: `nbd_dev_remove()` frees the device but `disk->private_data` still points at it, so `nbd_open()` uses freed state. The vault analog lives in `IdleCreditVault.requestInstantWithdraw`/`claimInstantWithdrawRequest`: the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are written at request time but **never cleared when the request is claimed**. The aggregate `instantWithdrawsRequests[_user]` is zeroed (the object is "freed") while the per-epoch records (the stale pointer) keep referencing it. Later, `defaultPendingClaimBasis()` reads that stale epoch data to size the default recovery haircut, counting already-paid claims as outstanding basis.

### Finding Description
- `requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 371–372).
- `claimInstantWithdrawRequest` pays the user at par, zeroes `instantWithdrawsRequests[_user]`, but never touches either per-epoch mapping (lines 387–392).
- On default, `finalizeDefaultRecovery` calls `defaultPendingClaimBasis()`, which adds `instantWithdrawClaimsByEpoch[epochNumber]` to the basis whenever `pendingInstantWithdraws != 0` (lines 644–649). That per-epoch total still includes receipts the strategy already paid out at full value.
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) is therefore depressed by phantom basis, so every honest defaulted receipt and every active AA/BB holder is underpaid.
- `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844). For an already-claimed user this is stale non-zero data; the subsequent `instantWithdrawsRequests[_user] -= claimBasis` underflows (0 - x) and reverts, permanently DoS-ing that user's `claimInstantWithdrawRequest` path, including any older legitimately funded receipt (line 382–386 always runs it first once `defaultInstantWithdrawsFinalized`).
- Because real claimants are paid `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` against an inflated `totalBasis`, `defaultRecoveryReserve` converges with leftover dust that no live receipt can claim (`_transferDefaultRecovery` underflows for late claimants in edge orderings), permanently locking residual recovery funds in the strategy.

Scenario: epoch N running; users A and B each request 50k instant withdrawals. Borrower returns partial funds; `collectInstantWithdrawFunds` collects A's 50k, leaving `pendingInstantWithdraws = 50k`. A calls `claimInstantWithdrawRequest` through the CDO and is paid at par — but `instantWithdrawClaimsByEpoch[N]` still reads 100k. Borrower then defaults and `finalizeDefaultRecovery` runs while `epochNumber == N`: basis counts B's legitimate 50k **plus A's already-paid 50k**, cutting `defaultRecoveryPrice` by up to the ratio of stale-to-real instant basis. B, normal pending redeemers, and all active tranche holders each lose that dilution.

### Impact Explanation
Direct, quantified dilution of the isolated default recovery reserve: every basis point of stale instant-claim data reduces `defaultRecoveryPrice` for all honest claimants (defaulted receipts, post-loss withdraw receipts, and AA/BB active NAV via `activeFinalNAV`). The already-paid attacker receives funds that are simultaneously still counted as outstanding, i.e. the same underlying is effectively claimed twice in the accounting — once at par, once inside the recovery basis — stealing value from all other claimants. Additionally, the stale per-epoch entry makes `claimInstantWithdrawRequest` revert for the claimed user and can leave residual `defaultRecoveryReserve` permanently locked. Loss magnitude: up to the full amount of instant withdrawals claimed within the defaulted epoch, distributed as a haircut on all other claimants.

### Likelihood Explanation
Requirements are all unprivileged/honest-sequenced: an epoch in which (a) at least two instant-withdraw requests exist, (b) the borrower partially prefunds so `collectInstantWithdrawFunds` leaves `pendingInstantWithdraws > 0`, (c) one requester claims, and (d) the borrower defaults in the same epoch with `finalizeDefaultRecovery` called by the honest owner/manager. No privileged misbehavior is needed — partial prefunding and same-epoch default are normal protocol states. The stale-write is unconditional: nothing ever decrements `instantWithdrawClaimsByEpoch` or `instantWithdrawsRequestsByEpoch` outside `_claimDefaultedInstantWithdrawRequest`. Likelihood is moderate-to-high: any epoch mixing instant claims and a default triggers it.

### Recommendation
In `claimInstantWithdrawRequest` (and anywhere else an instant receipt is fully paid), clear the per-epoch records alongside the aggregate:

```solidity
// after computing `amount` and before `_transferFundedClaim`
uint256 curEpoch = epochNumber; // or track per-request epoch
instantWithdrawsRequestsByEpoch[_user][curEpoch] = 0;
instantWithdrawClaimsByEpoch[curEpoch] -= amount;
instantWithdrawsRequests[_user] = 0;
```

More robustly, store the request epoch per user (like `apr0Users.principalEpoch`) so the correct per-epoch bucket is cleared even if claims span epochs, and ensure `instantWithdrawClaimsByEpoch` only ever reflects unclaimed, outstanding basis so `defaultPendingClaimBasis()` cannot double-count paid receipts.

### Proof of Concept
Foundry fork sketch (in-repo harness, e.g. extending `test/foundry/IdleCDOEpochQueue` / credit-vault default tests):

```solidity
// epoch N running, APR normal mode
cdoEpoch.startEpoch(); // manager
// A and B hold AA tranches; request instant withdraw of 50k each
cdoEpoch.requestInstantWithdraw(50_000e6, A); // -> strategy.requestInstantWithdraw
cdoEpoch.requestInstantWithdraw(50_000e6, B);

// borrower repays only 50k to CDO; manager collects it for instant claims
underlying.approve(cdoEpoch, 50_000e6); // borrower repays
cdoEpoch.collectInstantWithdrawFunds(50_000e6); // pendingInstantWithdraws: 100k -> 50k

// A claims at par; strategy pays A 50k
cdoEpoch.claimInstantWithdrawRequest(A);
assertEq(instantWithdrawsRequests[A], 0);
// BUG: stale records remain
assertEq(strategy.instantWithdrawsRequestsByEpoch(A, N), 50_000e6);   // stale pointer
assertEq(strategy.instantWithdrawClaimsByEpoch(N), 100_000e6);        // should be 50k

// borrower defaults in same epoch N; owner finalizes recovery
cdoEpoch._handleBorrowerDefault(...);
strategy.finalizeDefaultRecovery(recovered, recoverySource);

// defaultRecoveryPrice computed with +50k phantom basis:
// recoveryPrice == reserve * FULL / (active + pendingWithdraws + 100k) instead of +50k
// -> B and all active holders underpaid; A's claimInstantWithdrawRequest now always reverts
vm.expectRevert(); // underflow in _claimDefaultedInstantWithdrawRequest
cdoEpoch.claimInstantWithdrawRequest(A);
```

Assert `defaultRecoveryPrice` is strictly lower than the correct value `reserve * RECOVERY_FULL / (totalBasis - 50_000e6)` and that residual `defaultRecoveryReserve` remains unclaimable after all legitimate claims — the recovery-reserve analog of a use-after-free: the epoch bookkeeping still points at a receipt whose funds were already disbursed.
