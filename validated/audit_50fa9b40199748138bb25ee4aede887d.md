### Title
JWT replay-protection check-then-act race allows single-use trigger JWT to authorize multiple workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The Illuminate `Redeemer` bug is a class of "check happens against one piece of state, but the state used to actually finalize the operation is separate/updated later, non-atomically" — allowing an unprivileged user to get the operation to succeed (burn tokens) without the guard being enforced correctly. The closest reachable analog from an unprivileged client in this repo is the `WorkflowMetadataHandler.Authorize` JWT single-use check in the CRE HTTP Trigger gateway handler, where the "already used" check (`isReplay`) and the "mark as used" write (`recordUsage`) are two separate, non-atomic operations guarded by different lock scopes.

### Finding Description
`Authorize` is the entry point used by the internet-facing HTTP Trigger handler to validate a caller-supplied JWT before dispatching a workflow-execution request to DON nodes: [1](#0-0) 

The single-use protection relies on `jwtReplayCache`, whose `isReplay` (read lock) and `recordUsage` (write lock) are independent critical sections: [2](#0-1) 

In `Authorize`, the sequence is: read `isReplay(claims.ID)` → (if false) validate signer against `authorizedKeys` → call `recordUsage(claims.ID)`. There is a window between the `isReplay` read and the `recordUsage` write during which the same `jti` is not yet marked as used. If two requests carrying an identical signed JWT (same `jti`, same digest) reach the gateway concurrently — which an unprivileged caller can trivially trigger by sending the same signed request twice at once — both goroutines can pass `isReplay` before either calls `recordUsage`, because the check and the write are not combined into one atomic "check-and-set" operation (unlike, e.g., `RequestReplayGuard.CheckAndRecord` used in the Vault capability, which does perform an atomic check-and-record under a single mutex: [3](#0-2) ).

This exactly mirrors the root cause pattern in the Illuminate report: the guard variable (`holdings[u][m]` / here, the replay cache) is read to authorize an action, but the state mutation that should prevent re-use is deferred to a separate step, so an actor can trigger the "protected" effect (dispatching an authenticated workflow trigger to the DON) more than once using material that was only supposed to be valid once.

### Impact Explanation
A successfully authorized `HTTPTriggerRequest` is fanned out to DON nodes to execute a workflow (`h.triggerHandler.HandleUserTriggerRequest` → `Authorize` → dispatch), per the request/response flow described in the handler's own documentation: [4](#0-3) . If the same signed, single-use JWT can authorize two concurrent trigger requests instead of one, this constitutes an authentication/replay-protection bypass: the workflow can be executed more times than the JWT issuer intended, using request-forgery-adjacent duplication of a credential that was meant to be single-use. Depending on what the triggered workflow does (e.g., initiating on-chain actions, spending metered credits, or other side effects), this can translate into duplicate/unauthorized job execution and downstream fund or resource movement, matching the "unauthorized job run" acceptance criterion.

### Likelihood Explanation
Exploitation requires only an unprivileged external caller capable of sending two copies of the same signed JWT request to the gateway at (approximately) the same time — no special network position, no operator/node privilege, no dependency-only conditions. The race window is small (time between two lock acquisitions in the same function) but is a genuine TOCTOU gap; whether it is practically reliable depends on gateway concurrency/dispatch architecture (multiple goroutines/handler instances processing inbound node/user messages), which is plausible given the handler's use of `sync.WaitGroup`/goroutines elsewhere (e.g., `h.wg.Go` in `http_handler.go`). I could not fully verify from the indexed code whether `HandleUserTriggerRequest` itself serializes calls to `Authorize` per JWT/jti before reaching this function (only per-`req.ID` in-flight dedup was confirmed in tests, which does not protect against the same JWT sent under two different request IDs); this residual uncertainty should be resolved by reading `http_trigger_handler.go` in full inside a Devin session, since some file contents were not available in the index.

### Recommendation
Make the JWT replay check atomic: combine `isReplay` + `recordUsage` into a single method executed under one lock (as `RequestReplayGuard.CheckAndRecord` already does for the Vault flow), so that "check" and "mark used" cannot be separated by a race window. Apply this fix in `workflow_metadata_handler.go`'s `jwtReplayCache`, mirroring the `core/capabilities/vault/request_replay_guard.go` pattern.

### Proof of Concept
Conceptual PoC (cannot execute against the index, but derivable from the cited code):
1. Sign a valid JWT for a workflow (as in `TestWorkflowMetadataHandler_Authorize`, `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go:1081-1101`).
2. Submit two `HTTPTriggerRequest`s carrying the identical JWT (same `jti`) with different top-level `req.ID` values, concurrently (e.g., two goroutines calling `handler.Authorize(workflowID, tokenString, req)` at nearly the same time).
3. Because `isReplay` (read) and `recordUsage` (write) are separate calls (`workflow_metadata_handler.go:87-105`), both goroutines can observe `isReplay == false` before either calls `recordUsage`, so both calls to `Authorize` succeed and both trigger requests get dispatched to the DON — i.e., the single-use JWT authorized two workflow executions instead of one.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
