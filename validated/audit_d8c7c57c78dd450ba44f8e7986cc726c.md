### Title
Double-counting of a single signer's weight across `total_weight_approved` and `total_weight_rejected` when a signer flips its vote for the same block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The `StackerDBListener` tallies signer `BlockResponse` votes per block in a `BlockStatus` struct, using `gathered_signatures` (keyed by `slot_id`) to dedupe Accept votes and `responded_signers` (keyed by `slot_id`) to dedupe Reject votes. Because these are two separate dedup keys rather than one unified "has this signer already voted" state, a signer that first rejects and later accepts the same block gets its weight added to `total_weight_rejected` once and then also added to `total_weight_approved`, producing an aggregate weight sum that exceeds the real number of distinct signer weights and no longer matches the verified per-signer votes.

### Finding Description
On receiving `BlockResponse::Rejected`, the listener dedupes purely on `responded_signers`: [1](#0-0) 

so the first Reject from `slot_id` inserts into `responded_signers` and adds the signer's weight into `total_weight_rejected`.

On receiving `BlockResponse::Accepted` for the *same block* from the *same* `slot_id`, the dedup check is against a different set, `gathered_signatures`, not `responded_signers`: [2](#0-1) 

Since `gathered_signatures` was never populated by the earlier Reject, `contains_key(&slot_id)` is `false`, so the signer's weight is added again — this time into `total_weight_approved` — while the earlier contribution to `total_weight_rejected` is never reversed or reconciled. `responded_signers.insert(slot_id)` is a no-op at this point (already present), but that only prevents a *second* rejection contribution, not the initial rejection's residue.

The reverse order (Accept then later Reject) is correctly protected: the Reject branch's `responded_signers.insert(slot_id)` returns `false` because `responded_signers` was already populated by the Accept branch, so no double count occurs in that direction. The vulnerability is thus one-directional: Reject → Accept for the same `signer_signature_hash`/`slot_id` pair produces a stale, unreclaimed rejection weight that survives alongside a legitimate acceptance weight for the same signer.

This breaks the "aggregated-weight vs verified-accepts" invariant the coordinator depends on: `total_weight_approved + total_weight_rejected` (restricted to truly distinct, currently-held signer positions) should never double-count a signer's weight, since `get_block_status` uses these sums directly to decide whether to abort a tenure as rejected or confirm it as approved: [3](#0-2) 

### Impact Explanation
A single lower-weight signer, without any other signer's cooperation and without needing a majority, can inject phantom weight into `total_weight_rejected` that outlives its own vote change. If enough of this stale rejected weight accumulates (combined with genuine rejections from any other signers, or simply by itself for weight close to the blocking-minority threshold), the miner's coordinator can trip the `SignersRejected` abort path even though the real, current state of signer opinion no longer supports rejection — the flipped signer has since produced a genuine Accept and its signature is present in `gathered_signatures`. This is a liveness wedge on the miner side: a legitimately-approvable block/tenure can be forced into rejection/retry due to accounting residue rather than actual signer consensus, matching the "signer wedged" class of impact even though it manifests through the coordinator's vote tally rather than the signer client's own state machine.

### Likelihood Explanation
Triggering this requires only a single signer (not a majority) to emit two distinct, individually-valid signed `BlockResponse` messages for the same `signer_signature_hash` — a Reject followed later by an Accept. This is plausible under normal operation (a signer re-evaluating a proposal after new information arrives, e.g. parent block confirmation) and trivially reproducible by a Byzantine or misbehaving signer sending exactly this sequence deliberately. No StackerDB write privileges beyond the signer's own slot, no auth_token, and no other signer's key are needed.

### Recommendation
Unify the dedup key for weight accounting: check/record a single "has this signer already contributed weight to this block's tally" state (e.g. always gate weight changes on `responded_signers` for both branches, or track a `HashMap<slot_id, Vote>` and adjust weights symmetrically) so that a vote change either (a) is rejected/ignored after the first vote, or (b) reconciles by removing the prior bucket's weight before adding to the new bucket. Ensure `total_weight_approved + total_weight_rejected` can never exceed the sum of weights of signers who have actually cast a still-current vote.

### Proof of Concept
1. Coordinator proposes block `B` with `signer_signature_hash = H`.
2. Signer at `slot_id = k` (weight `w`) sends `BlockResponse::Rejected` for `H`. `stackerdb_listener.rs` sets `responded_signers = {k}`, `total_weight_rejected += w`. [1](#0-0) 
3. The same signer later sends `BlockResponse::Accepted` for the same `H` (e.g., after reconsidering). Since `gathered_signatures` does not contain `k`, the code adds `w` again into `total_weight_approved`, without decrementing `total_weight_rejected`. [2](#0-1) 
4. `get_block_status` now observes `total_weight_rejected` inflated by `w` that no longer reflects the signer's current (accepted) position, potentially pushing `total_weight_rejected + weight_threshold > total_weight` and forcing a spurious `NakamotoNodeError::SignersRejected` abort. [4](#0-3)
