### Title
Lazy default-recovery initialization zeroes live `pendingWithdraws`/`apr0TotalPrincipal` in a closed vault, orphaning real withdraw debt - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the ZetaChain `InitGenesis` nonce-reset bug, `IdleCreditVault._ensureDefaultRecoveryInitialized()` re-initializes aggregate accounting state to zero based only on the CDO's `epochEndDate == 0` flag, without verifying that the reset counters (`pendingWithdraws`, `apr0TotalPrincipal`) actually correspond to stale/orphaned state rather than real, unfunded user obligations. Any unprivileged user can trigger this reset via `requestWithdraw`, after which `collectWithdrawFunds`/`previewLossAdjustedWithdrawFunds` treat the pending bucket as empty and the orphaned claims can never be correctly funded or loss-adjusted.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`, the lazy migration helper:

```solidity
function _ensureDefaultRecoveryInitialized() internal {
  if (defaultRecoveryInitialized) return;
  if (pendingInstantWithdraws != 0) revert NotAllowed();
  if (pendingWithdraws != 0) {
    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    if (cdo.epochEndDate() != 0 || cdo.defaulted()) revert NotAllowed();
    pendingWithdraws = 0;      // ❌ resets real counter to 0
    apr0TotalPrincipal = 0;    // ❌ resets real counter to 0
  }
  defaultRecoveryInitialized = true;
  canTransfer = false;
}
``` [1](#0-0) 

This is invoked on the unprivileged `requestWithdraw` path, so any user can trigger it. The only guard distinguishing "stale" counters from real debt is `epochEndDate == 0 && !defaulted`. The reset does not check whether the aggregate `pendingWithdraws` equals the sum of per-user `withdrawsRequests`/`withdrawsRequestsByEpoch` claims, nor whether `apr0TotalPrincipal` matches open `apr0Users[*].principal` entries. If a vault reaches the closed state (`epochEndDate == 0`, `defaulted == false`) while the aggregate still represents genuine, unfunded obligations — e.g., a legacy pre-upgrade aggregate that was never collected via `collectWithdrawFunds`, or per-epoch `withdrawsRequestsByEpoch`/`apr0Users` entries that survive — the reset causes aggregate and per-user accounting to diverge, exactly like `NonceHigh` diverging from the real chain nonce.

After divergence:

- `previewLossAdjustedWithdrawFunds` sees `pendingBasis == 0` and assigns 100% of any subsequent `_lossAmount` to active LPs (`activeLoss = _lossAmount`), letting pending receipts escape the loss waterfall entirely. [2](#0-1) 
- `collectWithdrawFunds` sees `pendingBasis == 0`, so no borrower funding is pulled for the orphaned receipts. [3](#0-2) 
- Yet `_clearWithdrawClaimForEpoch`/`_withdrawClaimAmountsForEpoch` still honor the surviving per-epoch `withdrawsRequestsByEpoch` and `apr0Users` entries, paying them through `_transferFundedClaim` from vault cash that was never collected for them. [4](#0-3) 
- `apr0TotalPrincipal = 0` also orphans `apr0Users[*].principal` records whose `principalEpoch` references the zeroed bucket, corrupting `_settleApr0` and default-claim basis computations. [5](#0-4) 

### Impact Explanation
Broken invariant: fair loss waterfall + one receipt one payout. Orphaned pending receipts are paid from vault cash without corresponding borrower funding, transferring value from active AA/BB LPs (or, after default, from the `defaultRecoveryReserve` guard being bypassed through the `balance - reserve < _amount` check only partially applying) to the receipt holders. Alternatively, where cash is insufficient, the receipts are permanently frozen with no recovery path — the counters cannot be restored, mirroring the ZetaChain finding's "no functionality to recover" conclusion. Loss = the full orphaned `pendingWithdraws`/`apr0TotalPrincipal` basis, bounded only by vault balance.

### Likelihood Explanation
Requires a vault that is closed (`epochEndDate == 0`, not defaulted) while carrying a nonzero legacy aggregate `pendingWithdraws` or `apr0TotalPrincipal` backed by real per-user claims, plus an uninitialized `defaultRecoveryInitialized` flag — the exact post-upgrade state the function was written for. The upgrade task scripts (`tasks/cdo-factory.js`, `tasks/tranches-utils.js`) only *log* "stale closed-vault pending counters will normalize lazily" rather than verifying the counters are actually unbacked, so the trigger condition is plausible in production migrations and the trigger itself is a permissionless `requestWithdraw`. This is the weakest part of the finding: it hinges on the counters being backed by real claims in a closed vault, which the code comments assume cannot happen but never enforce on-chain.

### Recommendation
Before zeroing, reconcile the aggregates against per-user state, or require an explicit privileged migration (e.g., an `owner`/`manager` call that explicitly attests the counters are unbacked) rather than lazy zeroing on a permissionless path. Alternatively, only normalize when `withdrawsRequests`/`instantWithdrawsRequests` aggregates and `apr0Users` coverage prove the counters are stale, and revert otherwise — the same "export real state instead of defaulting to 0" fix recommended for the ZetaChain genesis bug.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `testLazyInitializeClearsOnlyStaleClosedCounters` in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLazyInitOrphansRealPendingDebt() external {
  IdleCreditVault creditVault = IdleCreditVault(address(strategy));
  address victim = makeAddr('victim');
  _depositWithUser(victim, 10_000 * ONE_SCALE, true);

  // Closed vault, legacy state: real pending claim recorded per-epoch
  vm.prank(victim);
  uint256 claimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

  // Simulate post-upgrade legacy state: aggregate backed by the claim above
  stdstore.target(address(creditVault)).sig(creditVault.defaultRecoveryInitialized.selector).checked_write(false);
  stdstore.target(address(creditVault)).sig(creditVault.pendingWithdraws.selector).checked_write(claimBasis);

  // Closed vault: epochEndDate == 0, not defaulted -> guards pass
  assertEq(cdoEpoch.epochEndDate(), 0);
  assertFalse(cdoEpoch.defaulted());

  // Attacker (any user) triggers lazy init
  cdoEpoch.requestWithdraw(0, address(AAtranche));
  assertEq(creditVault.pendingWithdraws(), 0, 'real debt erased');
  assertTrue(creditVault.defaultRecoveryInitialized(), '');

  // Any stop-epoch loss is now fully socialized to active LPs
  (uint256 pendingToFund, uint256 activeLoss) =
    creditVault.previewLossAdjustedWithdrawFunds(1_000 * ONE_SCALE);
  assertEq(pendingToFund, 0, 'pending escaped loss funding');
  // victim still claims claimBasis via _transferFundedClaim from uncollected cash
}
```

Expected: `pendingWithdraws` is zeroed while `victim`'s per-epoch claim survives, so `collectWithdrawFunds` never pulls funding and the claim is paid from other users' cash (or frozen if cash is short).

Note: I was unable to fully verify reachability of "closed vault + real backed pending aggregate" within the exploration budget; the test suite deliberately engineers this state via `stdstore`, so mainnet reachability depends on actual upgrade sequences.

  function prepareStopEpochWithApr0(uint256 _interest) external returns (uint256 _expInterest, uint256 _adjPendingWithdrawFees) {
    _onlyIdleCDO();
    IIdleCDOEpochVariant _cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 _pendingFees = _cdo.pendingWithdrawFees();
    uint256 _tvl = _cdo.getContractValue();
    _expInterest = _interest > 1 ? _interest : _cdo.expectedEpochInterest();
    _adjPendingWithdrawFees = _pendingFees;
    // Principal currently waiting for withdraw that was requested while APR was 0,
    // net of the upfront management fee charged at request time.
    uint256 _principal = apr0TotalPrincipal;

    // Fast path: no APR0 accounting needed.
    if (_principal == 0) {
      return (_expInterest, _adjPendingWithdrawFees);
    }
    // APR0 principal is only valid while APR is 0 for that request lifecycle.
    if (unscaledApr != 0) {
      revert NotAllowed();
    }

    uint256 _apr0NetInterest;
    // APR0 allocation is computed only when stopEpoch receives a real override interest.
    // _expectedInterest == 1 is the "request all funds back" sentinel and is handled in IdleCDO.
    if (_expInterest > 1 && _expInterest > _pendingFees) {
      // Remove already booked withdraw fees from the interest base before splitting.
      uint256 _interestNetOfFees = _expInterest - _pendingFees;
      // Total principal used for the pro-rata split:
      // IdleCDO TVL (which excludes APR0 requested principal) + APR0 principal bucket.
      uint256 _totalPrincipalForSplit = _tvl + _principal;
      if (_totalPrincipalForSplit != 0) {
        // APR0 users get a pro-rata share of realized interest.
        uint256 _apr0InterestGross = _interestNetOfFees * _principal / _totalPrincipalForSplit;
        if (_apr0InterestGross != 0) {
          // Same fee model as normal withdraw interest.
          uint256 _apr0Fee = _apr0InterestGross * _cdo.fee() / FULL_ALLOC;
          _apr0NetInterest = _apr0InterestGross - _apr0Fee;
          _adjPendingWithdrawFees += _apr0Fee;
          _expInterest -= _apr0NetInterest;
        }
      }
    }

    // Finalize one-epoch APR0 interest for current epoch only.
    if (_apr0NetInterest != 0) {
      // Funds owed to withdraw requesters increase by APR0 net interest.
      pendingWithdraws += _apr0NetInterest;
      // Save per-epoch net rate; each APR0 request accrues exactly once on its request epoch.
      apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;
    }
    // Close current APR0 bucket so it cannot accrue again on later stopEpoch calls.
    apr0TotalPrincipal = 0;
  }

    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
