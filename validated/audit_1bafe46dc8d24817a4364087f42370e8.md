## Title
Permanent, un-skippable DoS of `staking_contract::distribute` freezes all stake/commission withdrawals for a pool if any distribution-pool shareholder cannot accept a direct coin deposit - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

## Summary
This is the Aptos-native analog of the "transfer to an address that reverts locks the whole withdrawal" bug class in the report: instead of a hardcoded zero address, the risky recipient here is any address that ends up as a shareholder of a `staking_contract`'s `distribution_pool` (the staker, the current operator/beneficiary, or a *former* operator left over from `switch_operator`). `distribute_internal` pays out every shareholder in a single atomic loop using `aptos_account::deposit_coins`, which can abort for a recipient that has opted out of unregistered coin deposits. Because the loop has no way to skip or route around a failing recipient, one bad recipient blocks payout to *everyone* sharing that distribution pool, and the failure recurs on every subsequent call since the malicious shareholder is never removed.

## Finding Description
`distribute_internal` withdraws all inactive/pending-inactive stake, credits shares in `staking_contract.distribution_pool`, and then iterates over **all** shareholders, forcibly paying each one out in the same transaction: [1](#0-0) 

Payment is performed with `aptos_account::deposit_coins`, which can abort (`EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`) if the recipient's `CoinStore` isn't already registered for `AptosCoin` and the recipient has disabled arbitrary direct coin transfers via `DirectTransferConfig`: [2](#0-1) 

The `distribution_pool` can contain shareholders other than the current staker/operator pair. In particular, `switch_operator`/`switch_operator_with_same_commission` leave the *former* operator as a pending shareholder owed unpaid commission (confirmed by `test_staker_can_switch_operator`, which checks `assert_distribution(..., operator_1_address, commission_for_operator_1)` after the switch): [3](#0-2) 

`distribute()` itself is explicitly permissionless — "Allow anyone to distribute already unlocked funds" — and there is no filtering, retry-skip, or fallback-address mechanism (unlike the reported fix of sending to `address(1)`): [4](#0-3) 

Because the `while` loop processes recipients sequentially via `distribution_pool.shareholders()[0]` and any abort rolls back the whole transaction (including the share-accounting updates performed earlier in the same call), a single unpayable shareholder makes `distribute()` abort deterministically on every future invocation for that `(staker, operator)` pool, since the offending shareholder's shares are never removed by a failed transaction.

## Impact Explanation
Any account that becomes a distribution-pool shareholder (a former operator via `switch_operator`, or the staker/current operator/beneficiary themselves) can unilaterally and irreversibly set itself to reject un-registered direct coin deposits (`aptos_account::set_allow_direct_coin_transfers(false)`) while remaining unregistered for `AptosCoin`. This permanently blocks `distribute()` for that pool, trapping:
- the staker's unlocked/withdrawn stake principal,
- the current operator's (or its beneficiary's) unlocked commission,
- and any other pending shareholders' unlocked funds,
all of which sit un-withdrawable inside the resource account forever — a permanent, non-recoverable loss of claim rights, matching the "Permanent lock ... in stake, delegation, commission, beneficiary ... flows" impact category.

## Likelihood Explanation
This requires no privileged role: a former operator (who by definition no longer controls anything about the current pool) simply needs to disable direct coin transfers on their own account before their pending commission is distributed — a normal, unprivileged, one-line self-call (`aptos_account::set_allow_direct_coin_transfers`). Because `switch_operator` naturally creates lingering shareholders with unpaid commission, this scenario is not a hypothetical corner case but a direct consequence of a documented, supported staking_contract feature.

## Recommendation
Modify `distribute_internal` so a single recipient's failed deposit cannot block payouts to other shareholders and cannot be replayed indefinitely:
- Wrap each `aptos_account::deposit_coins` call so failures are caught/isolated per-recipient (e.g., check `coin::is_account_registered` / `can_receive_direct_coin_transfers` before attempting deposit), and
- If a recipient cannot receive funds, route their share to an escrow/fallback mechanism (analogous to the reported fix's `address(1)`) instead of aborting the whole distribution, or persist state changes for already-processed recipients so failures don't roll back prior payouts.

## Proof of Concept
1. Staker creates a staking contract with `operator_1`, commission 10% (`create_staking_contract`).
2. `operator_1` accrues commission via rewards; staker calls `switch_operator(staker, operator_1, operator_2, ...)`, which leaves `operator_1` as an unpaid shareholder in `distribution_pool` (see `test_staker_can_switch_operator`, lines 1561-1590 above).
3. `operator_1`, now with no further relationship to the pool, calls `aptos_account::set_allow_direct_coin_transfers(&operator_1, false)` and never registers a `CoinStore<AptosCoin>`.
4. Any subsequent call to `distribute(staker, operator_2)` (or `unlock_stake`, `request_commission`, etc., all of which call `distribute_internal`) reaches `operator_1` in the shareholder loop, calls `aptos_account::deposit_coins(operator_1, ...)`, which asserts `can_receive_direct_coin_transfers(operator_1)` — false — and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The abort reverts the entire transaction, including `update_distribution_pool`'s share bookkeeping, so `operator_1` remains a shareholder forever; every future `distribute()` call for this `(staker, operator_2)` pool fails identically, permanently freezing the staker's and `operator_2`'s unlocked stake/commission.

Note: I was not able to independently execute this against a live Move test harness (no terminal access), so the exact abort code path (`can_receive_direct_coin_transfers` vs. registration-guid edge cases) is derived from static reading of `aptos_account.move` and `staking_contract.move`/its tests rather than a runtime trace — this should be confirmed with an actual Move unit test before treating it as fully proven.
