### Title
Coordinator double-counts a signer's weight in both `total_weight_approved` and `total_weight_rejected` when a signer changes its vote from reject to accept - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The block coordinator (`StackerDBListener`) tallies signer weight for a proposed block using two independent counters, `total_weight_approved` and `total_weight_rejected`, guarded by two different sets/maps. The guard that prevents an already-rejected signer's later acceptance from being "un-rejected" is missing: once a signer rejects, its weight is permanently folded into `total_weight_rejected` and is never removed even if that same signer subsequently sends a valid acceptance signature, which is then folded into `total_weight_approved` as well. This mirrors the GiantMevAndFeesPool analog's root cause — a tally/accumulator computed from state that was never reconciled against the signer's up-to-date (later) vote before being used in a threshold decision.

### Finding Description
`BlockStatus` tracks acceptance and rejection weight for a given block hash: [1](#0-0) 

On acceptance (`BlockResponse::Accepted`), weight is added to `total_weight_approved` only if the slot hasn't already signed (`gathered_signatures.contains_key`), and `responded_signers` is unconditionally updated: [2](#0-1) 

On rejection (`BlockResponse::Rejected`), weight is added to `total_weight_rejected` **only if** `responded_signers.insert(slot_id)` returns `true`, i.e., only the first time this slot is ever seen in `responded_signers`: [3](#0-2) 

Sequence that breaks the equality:
1. Signer S sends `Rejected` first. `responded_signers.insert(slot)` returns `true` → `total_weight_rejected += weight(S)`. `responded_signers` now contains `slot`.
2. Signer S later sends `Accepted` for the same block hash (e.g., after reconsidering, or a stale/duplicated message replayed by the network). `gathered_signatures.contains_key(&slot)` is `false` (S never signed before) → `total_weight_approved += weight(S)`. `responded_signers.insert(slot)` is a no-op (already present), so nothing is subtracted from `total_weight_rejected`.

Result: `weight(S)` is now counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously; `total_weight_approved + total_weight_rejected` can exceed `total_weight`. The check that decides "no threshold can be reached, wake up waiters" uses the stale, still-inflated `total_weight_rejected`: [4](#0-3) 

Note the asymmetry: the reverse ordering (accept first, then reject) *is* protected — the `responded_signers.insert` guard on the reject path prevents that flip from re-adding weight — but the reject-then-accept ordering has no analogous guard on the accept path (it only checks `gathered_signatures`, a different set, not `responded_signers`/rejection state).

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that the miner's block-broadcast decision depends on. A rejection weight that should have been superseded by that signer's later acceptance remains permanently counted, inflating `total_weight_rejected`. Combined with genuine rejections from other signers, this stale/duplicated weight can push `total_weight_rejected` past the point where the coordinator concludes the 70% acceptance threshold is now unreachable (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`), stalling or wrongly abandoning a block that a legitimate 70%-weighted set of signers actually still supports. This is a liveness wedge on the miner/coordinator side, triggerable by the message pattern of a single signer (reject then accept for the same block), not requiring a majority of signers or another signer's key.

### Likelihood Explanation
Likelihood is moderate: it requires only one signer's client to emit a rejection followed later by an acceptance for the same `signer_signature_hash` (e.g., re-evaluation after a delayed proposal re-check, retransmission/gossip replay of an earlier rejection after the signer's local state already flipped to accept, or a byzantine/faulty signer probing coordinator behavior). No majority coordination or private key compromise is needed — the flaw is purely in the coordinator's bookkeeping of a single sender's two different response types for the same block.

### Recommendation
Track a single "current vote" per slot (accept/reject) rather than two independently-latched sets, and when the vote for a slot changes, subtract the old contribution before adding the new one. Concretely, before adding to `total_weight_rejected`, check whether `slot_id` is already in `gathered_signatures` (i.e., already counted for acceptance) and skip/adjust; and before adding to `total_weight_approved`, check whether `slot_id` was previously counted in `total_weight_rejected` and subtract that weight first, mirroring `get_and_cache_total_weight`-style tallies used elsewhere for reward/vote weight to keep the invariant `sum(per-slot latest vote weight) == total_weight_approved + total_weight_rejected`.

### Proof of Concept
1. Coordinator receives `BlockResponse::Rejected` from signer slot `k` (weight `w`) for block `B`. `total_weight_rejected` becomes `w`; `responded_signers = {k}`.
2. Coordinator later receives `BlockResponse::Accepted` (a valid signature) from the same slot `k` for block `B` (e.g., the signer resent an updated response, or a delayed/duplicated network message arrives). Since `k` is not in `gathered_signatures`, the code executes: [2](#0-1) 
adding `w` to `total_weight_approved` as well, while `total_weight_rejected` still equals `w` from step 1 — `weight(k)` is now double counted across both tallies, and the rejection threshold check at line 567-574 uses the stale, still-inflated `total_weight_rejected`. [5](#0-4)
