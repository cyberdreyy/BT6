### Title
Missing `return` after failed OIDC email-claim assertion allows sessions to be created and persisted with a blank `user_email`, causing cross-user session collision - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `handleTokenExchange`, the boolean result of the `claims["email"].(string)` type assertion is checked but the failure branch does not `return`, so execution continues using the zero-value (`""`) email exactly like the `success` flag in `INFTOracle.get()` being ignored and stale/invalid data being used downstream.

### Finding Description
`handleTokenExchange` extracts the OIDC ID token's `email` claim via a type assertion and inspects the `ok` result:

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
``` [1](#0-0) 

Unlike every other failure branch in this function, this one is missing a `return` statement. Execution falls through and continues using `email == ""`. The role is still computed correctly from the ID token's group claims:

```go
role, err := oi.IDClaimsToUserRole(idClaims, oi.config.AdminClaim(), oi.config.EditClaim(), oi.config.RunClaim(), oi.config.ReadClaim())
``` [2](#0-1) 

and a new session row is persisted with the empty email and the (potentially privileged) role, then the session cookie is unconditionally set and saved:

```go
_, err = oi.ds.ExecContext(ctx,
    "INSERT INTO oidc_sessions (id, user_email, user_role, created_at) VALUES ($1, $2, $3, now())",
    clSession.ID, strings.ToLower(email), role)
...
ginSession.Set(webauth.SessionIDKey, clSession.ID)
err = ginSession.Save()
``` [3](#0-2) 

The resulting session is fully valid for subsequent authenticated requests because `AuthorizedUserWithSession` only checks the session ID and expiry, never that `user_email` is non-empty:

```go
foundUser = clsessions.User{
    Email: foundSession.UserEmail,
    Role:  foundSession.UserRole,
}
``` [4](#0-3) 

`ClearNonCurrentSessions`, which is used to invalidate other sessions belonging to the same user, matches purely by `user_email`:

```go
_, err := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE lower(user_email) = lower($1) AND id != $2", email, sessionID)
``` [5](#0-4) 

Because every session created via this bug shares the same blank `user_email`, any single user hitting this bug and later calling `ClearNonCurrentSessions` will delete every other user's session that also has a blank email — a cross-user session collision entirely due to the unchecked `ok` value.

### Impact Explanation
Any OIDC identity provider response whose ID token lacks a top-level `email` claim (a very plausible misconfiguration — the code requests the `email` scope but does not enforce that the claim is present) causes the login flow to still succeed and issue a valid, working session cookie tied to a DB row with an empty `user_email` but with the caller's real RBAC role (e.g. Admin/Edit/Run) attached. This breaks per-user attribution/audit trails and creates a shared "anonymous" session bucket where `ClearNonCurrentSessions` for one blank-email user silently invalidates unrelated blank-email users' sessions — a cross-user response/session confusion. It also silently double-writes the HTTP response (`c.String` then falling through to `c.JSON`), indicating the code path was clearly not intended to continue.

### Likelihood Explanation
Reachable directly by any client completing the normal, unprivileged `/oidc-exchange` OIDC login flow — no attacker privilege is required. The only precondition is that the configured OIDC provider's ID token omits or mistypes the `email` claim, which is a realistic provider/configuration scenario, especially since `ExtractIDClaimValues` is what's actually validated for the RBAC group claim, not `email`.

### Recommendation
Add a `return` statement in the `!ok` branch after writing the error response, mirroring every other guard clause in `handleTokenExchange`:

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```

### Proof of Concept
1. Configure the OIDC identity provider such that the ID token returned to `/oidc-exchange` does not contain an `email` claim (or contains a non-string value), while still including the configured RBAC group claim (e.g. matching `AdminClaim()`).
2. Complete the standard `/oidc-login` → `/oidc-exchange` flow as an unprivileged client.
3. Observe that despite the "Failed to get email from claims" error being written, the handler falls through, `IDClaimsToUserRole` succeeds, a row is inserted into `oidc_sessions` with `user_email = ''` and the mapped role, and the response ultimately also emits `{"success":true}` with a valid session cookie set via `ginSession.Save()`.
4. Use the returned session cookie against any authenticated endpoint — `AuthorizedUserWithSession` accepts it and returns a `User{Email: "", Role: <mapped role>}`.
5. Repeat with a second distinct client hitting the same bug; call the logout/`ClearNonCurrentSessions` path as the first user and observe the second user's session (also `user_email = ''`) gets deleted, demonstrating cross-user session interference.

func (oi *oidcAuthenticator) ClearNonCurrentSessions(ctx context.Context, sessionID string) error {
	var email string
	if err := oi.ds.GetContext(ctx, &email, "SELECT user_email FROM oidc_sessions WHERE id = $1", sessionID); err != nil {
		return err
	}
	_, err := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE lower(user_email) = lower($1) AND id != $2", email, sessionID)
	return err
}
