### Title
Loss-adjusted withdraw receipts bypass their haircut when a newer request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` determines which epoch's `lossRecoveryPriceByEpoch` applies by reading the single slot `lastWithdrawRequest[_user]`, which only stores the user's most recent request epoch. Because `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]` with `currentEpoch` on every new request [1](#0-0) , a user who holds a haircutted receipt from a loss epoch can simply submit a new withdraw request in the following epoch. The loss-epoch lookup then reads `lossRecoveryPriceByEpoch[newEpoch] == 0`, the loss-adjusted path returns 0, and the entire aggregate `withdrawsRequests[_user]` (including the haircutted epoch's basis) is paid at par through `_claimFundedWithdrawRequest`. This is the same bug class as the missing `master_edition` PDA check: the code never validates that the receipt being claimed actually belongs to the epoch used for pricing, so an unauthenticated/haircutted claim is redeemed as if it were fully valid.

### Finding Description
When a borrower partially funds pending withdrawals at `stopEpochWithDuration`, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] < RECOVERY_FULL` [2](#0-1) . At claim time, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which derives the loss epoch solely from `lastWithdrawRequest[_user]` [3](#0-2) . `requestWithdraw` always writes `lastWithdrawRequest[_user] = currentEpoch` and adds the amount to `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) . `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` (the aggregate across all epochs) at par once `epochNumber > lastWithdrawRequest[_user]` [4](#0-3) . There is no check that the cleared claim epoch matches the epoch that carries the loss price — `_clearWithdrawClaimForEpoch` clears per-epoch entries but is only invoked with `lossEpoch = lastWithdrawRequest[_user]`, so a receipt recorded under an older, haircutted epoch is never matched to its `lossRecoveryPriceByEpoch` entry [5](#0-4) .

### Impact Explanation
An attacker with a pending receipt in a loss epoch (e.g., claim basis 100, `lossRecoveryPrice = 50%`) requests a second withdrawal of a dust amount in the next epoch. After waiting one more epoch (satisfying `epochNumber > lastWithdrawRequest`), `claimWithdrawRequest` pays the full 100 + dust at par instead of 50 + dust. The strategy only received the funded 50 for that epoch, so the extra 50 is paid from underlying held for other users' funded claims, subsequent epoch deposits, or forces the transfer to revert — i.e., either direct theft/solvency loss for other claimants or permanent freezing of their legitimate claims. The "one receipt, one priced payout" invariant is broken.

### Likelihood Explanation
The attacker only needs to be a KYC-passing lender/tranche holder able to call `requestWithdraw` — an explicitly in-scope unprivileged actor. The trigger requires a `stopEpochWithDuration` with partial funding (`collectWithdrawFunds` with `_amount < pendingWithdraws`), which is a normal owner/borrower-driven flow, not attacker-controlled but a plausible epoch outcome. The attacker's own action (a second dust `requestWithdraw`) is fully permissionless and requires no privileged cooperation. The existing comments acknowledge only the extra wait for normal re-requests; the haircut-bypass is not acknowledged.

### Recommendation
Store per-epoch request metadata instead of relying on a single `lastWithdrawRequest` slot for loss attribution. Specifically: in `_claimLossAdjustedWithdrawRequest`, iterate or track the user's request epochs (e.g., derive the claim epoch from `withdrawsRequestsByEpoch` non-zero entries rather than `lastWithdrawRequest`), or record `lossEpoch` per request at `requestWithdraw` time so a receipt created in a loss epoch is permanently bound to `lossRecoveryPriceByEpoch[thatEpoch]`. Alternatively, revert in `requestWithdraw` when the user has an unclaimed loss-adjusted receipt, mirroring the existing "wait another epoch" semantics.

```solidity
// test/foundry/LossAdjustedClaimBypass.t.sol — fork test outline
// Setup: standard IdleCDOEpochVariant + IdleCreditVault, fixed-APR mode, defaultRecoveryInitialized.
function testLossHaircutBypassedBySecondRequest() external {
    // 1. User deposits AA, epoch 0 runs and stops normally.
    uint256 shares = _depositAA(user, 100e6);
    _startEpoch(); _stopEpoch();

    // 2. User requests withdraw of all shares in epoch 1 (lastWithdrawRequest[user] = 1).
    vm.prank(user);
    cdoEpoch.requestWithdraw(shares, address(AAtranche));

    // 3. Epoch 2 runs; borrower only returns part of pendingWithdraws at stopEpochWithDuration.
    _startEpoch();
    uint256 pending = strategy.pendingWithdraws();
    _stopEpochWithDurationLoss(pending / 2); // collectWithdrawFunds(pending/2) -> lossRecoveryPriceByEpoch[2] = 0.5e18
    //    (loss epoch recorded under epochNumber at funding time; user's receipt epoch = 2)

    // 4. In next buffer, user makes a dust second request -> lastWithdrawRequest[user] = 3.
    vm.prank(user);
    cdoEpoch.requestWithdraw(1, address(AAtranche));

    // 5. Run one more epoch so epochNumber > lastWithdrawRequest[user].
    _startEpoch(); _stopEpoch(); // epochNumber = 4 > 3

    // 6. Claim: lossRecoveryPriceByEpoch[3] == 0 -> loss path skipped;
    //    _claimFundedWithdrawRequest pays withdrawsRequests[user] (full 100e6 + dust) at par.
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    // Assert overpayment: received full basis instead of haircut basis.
    assertGt(underlying.balanceOf(user) - balPre, pending / 2);
    // Assert insolvency: strategy funded claims balance is now short for remaining claimants.
    assertLt(strategyUnderlyingBalance(), remainingFundedClaims());
}
```

Uncertain detail: the exact epoch index under which `lossRecoveryPriceByEpoch` is written vs. `lastWithdrawRequest` depends on whether `epochNumber` has already been bumped by `deposit()` inside `stopEpoch` [6](#0-5) ; the PoC indices may need adjustment, but the core flaw — loss epoch keyed by a mutable single-slot `lastWithdrawRequest` while payout uses the aggregate `withdrawsRequests` — holds regardless of the off-by-one.

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
```
