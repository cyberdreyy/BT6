### Title
Single malformed/oversized account in a `getMultipleAccounts` batch aborts encoding of all other accounts in the request - (File: rpc/src/rpc.rs)

### Summary
`JsonRpcRequestProcessor::get_multiple_accounts` iterates over the caller-supplied list of pubkeys and calls `get_encoded_account` for each one inside a `for` loop, propagating any per-account error with `?`. Because the loop uses `?` instead of collecting per-item results, a single pubkey whose account cannot be encoded under the requested config (e.g. binary/base58 encoding is limited to 128 bytes, or the account data violates some other encoding precondition) causes the whole multi-account RPC call to fail with an error, even though the other accounts in the batch are perfectly valid and unrelated to the failing one.

### Finding Description
`get_multiple_accounts` builds up a `Vec` of decoded/encoded accounts one at a time: [1](#0-0) 

Each iteration spawns a blocking task that calls `get_encoded_account(&bank, &pubkey, encoding, data_slice, None)`, and the `?` on `.await.expect("rpc: get_encoded_account panicked")?` immediately returns from the whole function the moment any single account in the batch produces an `Err(..)` (for example, `Error::invalid_params` raised when data length exceeds the binary-encoding limit, or other encoding-specific validation failures inside `get_encoded_account`/`encode_account`).

This is directly analogous to the reported Solidity bug class: a loop that touches multiple independent "reward"/data items but aborts the entire operation because one item in the middle of the loop reverts/errors, denying service for all the other (unrelated, valid) items in the same call. In the RPC case, the "poison" element is any account whose data cannot satisfy the chosen encoding's constraints (not necessarily malicious data — a legitimate account larger than the historical 128-byte binary/base58 limit is enough), and the "loop of transfers" is the loop of per-account encodes.

### Impact Explanation
When a client calls `getMultipleAccounts` with a mixed batch of pubkeys, one poisoned/oversized account (which the client may not control or even know about — the batch can include third-party accounts) causes the JSON-RPC method to return an error for the entire request instead of returning valid data for the other pubkeys, or excluding just the bad one. This is a functional/availability degradation of a widely used JSON-RPC endpoint: legitimate accounts in a batch become unreadable purely because they happen to be requested alongside one large/incompatibly-encoded account, and no partial results are returned. It does not corrupt bank state, is not a crash of the validator process, and does not perform unbounded work per call (the loop bound is the client-provided pubkey list length, itself limited elsewhere), so it falls short of a critical/high-severity validator vulnerability — this is a service-quality bug in RPC response construction rather than a process crash, deadlock, or consensus-state issue.

### Likelihood Explanation
Any unprivileged RPC caller can trigger this by including in a `getMultipleAccounts` request a pubkey whose account content is incompatible with the requested encoding (e.g. binary/base58 default encoding on data > 128 bytes) alongside pubkeys the caller actually cares about. This requires only a single JSON-RPC call and no special access, but the effect is confined to the RPC response of that call (an error instead of partial success) rather than validator-wide impact.

### Recommendation
In `get_multiple_accounts` (rpc/src/rpc.rs), do not let a per-pubkey encoding error abort the whole batch. Instead, catch the error for the offending pubkey and place `None` (or an explicit per-item error indicator, if the API supports one) into the corresponding slot of the response vector, matching the semantics already used for accounts that simply don't exist. This mirrors the recommended Solidity mitigation of not letting one failing item block processing of the rest of the batch.

### Proof of Concept
1. Create/find a legitimate account whose data length exceeds the binary/base58 encoding size cap enforced inside `get_encoded_account`/`encode_account`.
2. Call `getMultipleAccounts` with `[oversized_pubkey, valid_pubkey_1, valid_pubkey_2]` using the default (`Base64`/`Binary`) encoding.
3. Observe that the RPC call returns an error for the whole request (surfaced from the `?` in the loop at rpc/src/rpc.rs:580-590), even though `valid_pubkey_1` and `valid_pubkey_2` would have encoded successfully on their own — confirmed by re-issuing the call with just the two valid pubkeys, which succeeds.     pub async fn get_multiple_accounts(
        &self,
        pubkeys: Vec<Pubkey>,
        config: Option<RpcAccountInfoConfig>,
    ) -> Result<RpcResponse<Vec<Option<UiAccount>>>> {
        let RpcAccountInfoConfig {
            encoding,
            data_slice,
            commitment,
            min_context_slot,
        } = config.unwrap_or_default();
        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }
