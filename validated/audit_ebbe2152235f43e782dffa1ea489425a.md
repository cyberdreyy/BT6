### Title
Denial of Service: a single valid signer StackerDB message can kill the node's `StackerDBListener` coordinator thread - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The bug class in the referenced `@hapi/hapi` advisory is: a single malformed-but-otherwise-plausible input value that should be handled gracefully instead escalates to an unhandled control-flow exit (a thrown exception) that kills the whole request-processing loop. The same pattern exists in `StackerDBListener::run`, the node-side coordinator thread that collects signer `BlockResponse`/pre-commit/signature messages for Nakamoto block mining: a message whose `slot_id` is not present in the locally-cached `signer_entries` map causes the function to `return Err(...)` instead of skipping that one message, unwinding the entire listener loop.

### Finding Description
In `StackerDBListener::run`, every StackerDB chunk received is looked up by `slot_id` in `self.signer_entries`, a `HashMap<u32, NakamotoSignerEntry>` that was built once at `StackerDBListener::new` time by enumerating `reward_set.signers()`: [1](#0-0) 

Inside the per-message loop, every other malformed/unexpected condition (unknown block hash, bad signature, fault injection, etc.) is handled by `continue`-ing to the next message: [2](#0-1) 

But the very first lookup in the loop escalates instead of degrading gracefully: [3](#0-2) 

Because `run()` is the thread body run by the `SignerCoordinator`'s spawned `stackerdb_listener_*` thread, a `return Err(...)` from `run()` terminates that thread entirely — it is only ever logged, not restarted or recovered: [4](#0-3) 

The `signer_entries` map used for the `slot_id` lookup is populated purely from `reward_set.signers()` (the Rust-side `RewardSet` structure), while the actual slot-id-to-signer binding enforced by StackerDB writes is separately maintained on-chain in the `.signers` boot contract's `stackerdb-signer-slots-0`/`stackerdb-signer-slots-1` lists: [5](#0-4) 

These are two independently constructed orderings of "the same" reward-cycle signer set. Nothing in `handle_block_proposal`/`StackerDBListener::new`/`run` cross-checks that the node's Rust-side `signer_entries` enumeration matches the slot assignment actually recorded in `signers.clar` for every entry, nor is a size/slot_id-range check performed before the map lookup. Any StackerDB chunk whose `slot_id` doesn't happen to be a key in `self.signer_entries` — whether due to enumeration-order/timing skew between the two representations, a signer_set/reward-cycle transition boundary, or a slot number outside the currently cached set — is fatal to the whole coordinator thread rather than to the single message.

### Impact Explanation
This matches the High-severity category "a signer wedged into never signing valid blocks" from the analog side of the equation applied to the node's coordinating thread: once `StackerDBListener::run` returns `Err`, the mining coordinator stops collecting signer signatures for the remainder of that tenure/mining-thread lifetime (`signer_coordinator.rs:174-177` only logs the error; nothing restarts the listener or the thread). Since the block-signature/threshold accumulation (`self.blocks`, `weight_threshold`) lives inside this same struct and thread, all subsequent legitimate signer acceptances for that node are silently dropped — the node can never again reach the ≥70% weight threshold to consider a block signed, wedging block production/mining for that tenure. This requires no majority of signers and no compromise of any signer's key: it only requires one message whose `slot_id` fails the map lookup to reach the loop.

### Likelihood Explanation
The trigger condition (`self.signer_entries.get(&slot_id)` returning `None`) is reachable by any StackerDB write that the p2p/StackerDB layer already accepts as a valid signed chunk for the `.signers-X-Y` contract (chunk signature is separately verified by `chunk.recover_pk()` in `SignerEvent::try_from`, which only checks the *chunk*'s signature, not that the specific `slot_id` is the one this node's cached `signer_entries` expects it to be): [6](#0-5) 

Because the Rust-side `signer_entries` (from `reward_set.signers()`) and the on-chain `.signers` slot list are two independently maintained orderings of the reward set, any divergence between them (e.g., at a reward-cycle boundary, a tenure-extend across a boundary, or a race between reward-set computation and listener construction) turns an ordinary, honestly-signed signer message into the crash trigger — no attacker collusion or majority is required, only one message landing on an unmapped `slot_id`.

### Recommendation
Change the `None` branch at `stacks-node/src/nakamoto_node/stackerdb_listener.rs:373-377` (and the following `StacksPublicKey::from_slice` failure branch at lines 378-383) from `return Err(...)` to `warn!(...); continue;`, consistent with every other per-message anomaly handled later in the same loop. If a hard failure is genuinely desired for this condition, it should not propagate out of the shared coordinator's `run()` loop as a way that silently disables all future signature collection without any recovery/restart path.

### Proof of Concept
1. Set up a Nakamoto node with `SignerCoordinator`/`StackerDBListener` running for reward cycle `N`, with `signer_entries` built at `StackerDBListener::new` from `reward_set.signers()` (`stackerdb_listener.rs:227-239`).
2. Have a legitimately-registered signer for that same signer_set/contract emit a `SignerMessageV0::BlockResponse` (or `BlockPreCommit`) chunk under a `slot_id` that is present in the actual `.signers-X-Y` boot-contract slot list but is not a key in the node's locally cached `signer_entries` map (achievable at a reward-cycle/signer_set transition, or whenever the Rust-side enumeration order used to build `signer_entries` disagrees with the Clarity-side `stackerdb-signer-slots-*` order for even one entry).
3. `StackerDBListener::run` receives the event, passes the `signer_set` check (`stackerdb_listener.rs:356-361`), then hits `self.signer_entries.get(&slot_id)` → `None` at line 373, and executes `return Err(NakamotoNodeError::SignerSignatureError(...))`.
4. The spawned `stackerdb_listener_*` thread in `SignerCoordinator::new` (`signer_coordinator.rs:174-177`) logs the error and exits; no other code restarts it. All subsequent, otherwise-valid signer signatures/pre-commits for this node are never processed, and the node can never accumulate `weight_threshold` again for that mining coordinator instance.
