### Title
Global `requestCache` has no per-sender quota, allowing a single sender to exhaust `maxCacheSize` and deny service to all other DON clients - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces only a global cache-size cap (`len(c.cache) >= int(c.maxCacheSize)`) keyed by `globalId{sender, id}`, with no per-sender limit on how many distinct pending `MessageId`s a single sender may register. A single valid, unprivileged sender can flood the shared cache with `maxCacheSize` distinct `MessageId`s, causing `NewRequest` for every other sender on the same DON to fail with "request cache is full" until entries expire via `c.timeout`.

### Finding Description
`NewRequest` computes `key := globalId{request.Body.Sender, request.Body.MessageId}` and checks only the *total* map size against `maxCacheSize`, not any per-sender count: [1](#0-0) 
There is no bound on the number of distinct `MessageId`s a single `sender` may register, nor any per-sender token bucket inside this component. The only rate limiting present near the gateway-request path is `nodeRateLimiter` in `core/services/gateway/handlers/capabilities/handler.go`, which throttles messages *from DON nodes* (`nodeAddr`) responding to outbound HTTP actions, not end-user requests into the cache: [2](#0-1) 
Because each entry only expires after `c.timeout` (via `time.AfterFunc`), an attacker who continuously submits fresh, distinct `MessageId`s faster than the timeout period can keep the cache saturated indefinitely, blocking `NewRequest` for all other senders on that DON handler instance.

Note: in this snapshot of the repository, `requestCache`/`NewRequestCache` is not instantiated by any currently-wired handler (`capabilities`, `vault`, `confidentialrelay` handlers were inspected and do not reference `common.RequestCache`); usage is only exercised in `requestcache_test.go`. This means the exploit is demonstrable at the unit level exactly as described in the proof idea, but I could not confirm a live, currently-reachable HTTP/JSON-RPC route in this codebase snapshot that wires an unauthenticated/end-user message directly into this specific `requestCache` instance — this may be due to index truncation or the component being staged for use by a handler not fully indexed.

### Impact Explanation
If/when a handler uses this shared `requestCache` to queue user requests, a single sender with a valid signing identity can cause global denial of service for all other legitimate gateway clients of that DON by exhausting `maxCacheSize` slots with self-generated, distinct `MessageId`s — no authentication bypass or data leak occurs, but availability for all other users of the shared cache is denied. This corresponds to a DoS / availability impact class rather than fund loss or privilege escalation.

### Likelihood Explanation
Precondition is minimal: the attacker only needs one valid signing identity capable of sending gateway messages (the same precondition any legitimate user has) — no elevated role, no node/operator access. The attack is trivially repeatable (loop submitting `maxCacheSize` requests with fresh `MessageId`s below the timeout interval) and requires no race condition. The only mitigating factor found is that this component does not appear wired into an active handler in the current snapshot, which limits real-world exploitability until/unless it is used to gate a live endpoint.

### Recommendation
Add a per-sender quota (e.g., max pending entries per `sender`, or use a per-sender rate limiter such as the `ratelimit.RateLimiter` already used elsewhere in the gateway, e.g., `PerSenderRPS`/`PerSenderBurst` as seen in `capabilities/handler.go` and `capabilities/v2` configs) inside `requestCache.NewRequest`, rejecting/throttling a sender who already has too many outstanding entries before checking the global cap.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/common/requestcache_test.go`:
1. Construct `cache := NewRequestCache[testData](timeout, N)` with `maxCacheSize = N`.
2. In a loop, call `cache.NewRequest(lggr, msg, callback, &testData{})` `N` times using the same `sender` but `N` distinct `MessageId`s; assert each call returns `nil`.
3. Call `cache.NewRequest` once more with a *different* `sender` and a fresh `MessageId`; assert the returned error is `"request cache is full"`.
4. This demonstrates that one sender alone can starve the shared cache and block an innocent second sender's request, confirming the lack of per-sender quota enforcement in `requestCache.NewRequest`.
