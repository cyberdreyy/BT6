### No vulnerability found for this question.

The claimed ambiguity does not exist in the code. `Registers::get_len` returns `Some(actual_len)` for any set register (including zero-length ones) and `None` only when the register id was never written; `VMLogic::register_len` maps that to `Ok(actual_len)` or `Ok(u64::MAX)` respectively via `self.registers.get_len(register_id).unwrap_or(u64::MAX)` [1](#0-0) . Because `max_register_size` (and `registers_memory_limit`) are hard-capped configuration values far below `u64::MAX`, a legitimately-set register can never report a length equal to `u64::MAX`, so the sentinel value `u64::MAX` unambiguously means "unused register" and can never collide with a real zero-length (or any valid-length) register — this is enforced at write time in `write_register`, which validates size against `limit_config` before calling `registers.set` [2](#0-1) . This exact behavior is already covered by existing unit tests distinguishing a real (non-zero) register value from an unset one (`test_one_register`, `test_non_existent_register`, `test_register_is_not_used`) [3](#0-2) [4](#0-3) , and the documented spec confirms this is intended, non-ambiguous sentinel design [5](#0-4) .

Additionally, the referenced file/scope in the prompt (`core/primitives/src/action/mod.rs -> Contracts execution flows`) has no relation to `register_len`/`Registers::get_len`, which live in `near-vm-runner`'s VM logic layer, not in action/receipt validation code. Any contract that chooses to branch business logic (e.g., skip a deposit check) on `register_len == u64::MAX` without actually writing a zero-length value into that register first is a smart-contract-level logic bug in the attacker's own or a third-party DeFi contract, not a nearcore protocol vulnerability — it does not bypass any signature, nonce, access-key, gas-metering, or size-limit check enforced by the runtime, and there is no reachable path by which an unprivileged attacker can force the *protocol* to conflate "unused register" with "zero-length register content."
