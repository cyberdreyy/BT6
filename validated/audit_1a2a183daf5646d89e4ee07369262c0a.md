## Title
Missing check for the default/null `Pubkey` when setting a new program or buffer authority via `UpgradeableLoaderInstruction::SetAuthority` — ([File: programs/bpf_loader/src/lib.rs])

### Summary
The BPF Upgradeable Loader's `SetAuthority` instruction handler mirrors the reported Solidity pattern: a "checked" code path validates the new authority correctly, while an "unchecked" sibling path omits that validation and lets an authority be permanently set to an address that can never sign again — the SVM analog of Solidity's `address(0)`.

### Finding Description
In `process_instruction` for `UpgradeableLoaderInstruction::SetAuthority`, the new authority is read as an *optional, unsigned* account key: [1](#0-0) 

For both `Buffer` and `ProgramData` state, that raw `new_authority` key is written directly into on-chain state with no check that it is not `Pubkey::default()` (the all-zero pubkey, which is also `system_program::id()`): [2](#0-1) [3](#0-2) 

Crucially, unlike `SetAuthorityChecked` — which requires the new authority account to be a *signer* of the instruction, and thus implicitly rejects `Pubkey::default()` because nobody holds its private key — [4](#0-3) [5](#0-4) 

the unchecked `SetAuthority` path performs no such signer or zero-address check on the new authority key at all. This is exactly the pattern described in the report: `changeAdmin()` (the "checked" path) validates against the zero address, while another code path that reaches the same state mutation (the constructor / here, `SetAuthority`) does not.

Setting `upgrade_authority_address` (or `authority_address`) to `Some(Pubkey::default())` differs semantically from the legitimate "finalize" path (`new_authority = None`, which correctly marks the state `Immutable`). With the default pubkey set, `upgrade_authority_address.is_none()` is `false`, so the account is not reported/treated as `Immutable`, yet no future `SetAuthority`/`SetAuthorityChecked`/`Upgrade`/`Close` call can ever succeed again because the required signature for `Pubkey::default()` cannot exist. This silently and irrecoverably bricks the program's/buffer's authority in a way that is indistinguishable on-chain from a normal mutable account, unlike the intentional, clearly-flagged `Immutable` finalize path.

### Impact Explanation
Any current program-authority or buffer-authority holder (including a delegated/CPI-invoked authority in a multisig, DAO governance, or automated deployment pipeline) that issues `SetAuthority` with the new-authority account key equal to `Pubkey::default()` (or any other pubkey it does not control) permanently locks that program/buffer out of further authority rotation or upgrades — with no explicit error and no `Immutable` flag being set, unlike the intended finalize flow. This is a state-mutation bug that produces an unrecoverable, misrepresented on-chain state (silent bricking) reachable directly through a builtin-program instruction issued by an ordinary signed transaction or CPI.

### Likelihood Explanation
This requires the current legitimate authority to submit (directly or via CPI from a program it trusts) a `SetAuthority` instruction with a bad/zero new-authority account — mirroring the original report's own framing ("deployment system implementation error" or "malicious internal actor uses their privileges"). It is not exploitable by an arbitrary unprivileged third party against someone else's program, since the current authority's signature is always required. Likelihood is therefore Low, matching the "Low" difficulty rating assigned in the original external report for the analogous Solidity issue.

### Recommendation
In the `SetAuthority` handler (unchecked path), reject `new_authority == Some(Pubkey::default())` (and any other unsignable/default pubkey), or require verification that the new authority is capable of being used before committing the new state — consistent with the protection already implicitly present in `SetAuthorityChecked`. Alternatively, deprecate the unchecked `SetAuthority` variant in favor of always requiring `SetAuthorityChecked` semantics.

### Proof of Concept
1. Deploy an upgradeable program via the BPF Upgradeable Loader; note its `ProgramData` account has `upgrade_authority_address = Some(authority_pubkey)`.
2. As the current `authority_pubkey` signer, submit `UpgradeableLoaderInstruction::SetAuthority` with instruction accounts `[programdata, authority (signer), Pubkey::default()]` (account index 2 not required to sign, per [1](#0-0) ).
3. The instruction succeeds and sets `upgrade_authority_address = Some(Pubkey::default())` per [3](#0-2) .
4. Any subsequent `Upgrade`, `SetAuthority`, `SetAuthorityChecked`, or `Close` instruction now requires a signature from `Pubkey::default()`, which is unobtainable — the program is permanently frozen at its current version, while `upgrade_authority_address.is_none()` remains `false`, so tooling/RPC consumers do not report it as `Immutable`.
