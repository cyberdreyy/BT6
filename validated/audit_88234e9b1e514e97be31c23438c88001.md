### Title
Revoked LDAP privileges remain valid on cached sessions until the periodic sync ticker runs - ([File: core/sessions/ldapauth/ldap.go])

### Summary
Per-request session validation for LDAP-authenticated users is handled by `AuthorizedUserWithSession`, which only reads the locally cached `ldap_sessions` table and never re-queries the upstream LDAP server. Revocation (removal from an LDAP group, deactivation, etc.) is only applied to that cache by `LDAPServerStateSyncer.Work`, which runs on a timer (or once at startup) rather than per request, contrary to what the package's own doc comment implies.

### Finding Description
The question's framing names `FindUser` as the vulnerable path, but `FindUser(ctx, email)` [1](#0-0)  takes an email, not a session ID, and is only invoked during initial login (`CreateSession`, which does perform a live LDAP bind and a live `FindUser` group lookup) [2](#0-1) , or by admin-only user-management handlers that already require an authenticated admin session (`UserController.Delete`, `UpdatePassword`, `NewAPIToken`, `DeleteAPIToken`) [3](#0-2) . It is not part of the "reuse an existing session id after revocation" path.

The actual per-request revocation check for an existing session cookie is `AuthorizedUserWithSession`, which is wired into the gin auth middleware via `AuthenticateBySession` [4](#0-3) . That function only performs a local SQL lookup against `ldap_sessions` and does not contact the LDAP server at all: [5](#0-4) . The role/email returned is whatever was cached at login time or last sync, so a session created before a revocation event keeps its old (possibly admin) role for every subsequent request.

Cache invalidation is performed exclusively by `LDAPServerStateSyncer.Work`, invoked from `run()` on a `time.NewTicker(UpstreamSyncInterval)` loop, or once at `Start()` if the interval is zero [6](#0-5) . Nothing in the authenticated request path (`AuthenticateBySession`, `RequiresAdminRole`, etc.) triggers an on-demand resync. This contradicts the package doc comment's claim that "this sync happens for every auth endpoint hit, and via the defined sync interval" [7](#0-6)  — the code does not actually resync per request.

### Impact Explanation
An LDAP admin who is de-provisioned or downgraded (removed from the admin group, or marked inactive) but whose browser/API session was created earlier retains full admin-level access to every endpoint gated by `RequiresAdminRole`/`RequiresEditRole` [8](#0-7)  until the next `UpstreamSyncInterval` tick purges or downgrades the `ldap_sessions` row. Depending on operator configuration this window can be arbitrarily long (interval is operator-configured, defaulting to whatever `UpstreamSyncInterval` is set to). During that window the holder of the still-cached session can create API keys, manage jobs, and otherwise act with the stale privileged role — matching an admin/privilege-persistence impact class rather than a fresh unauthenticated compromise, since the attacker must already possess a previously-valid session/cookie obtained while still authorized.

### Likelihood Explanation
This requires the attacker to already hold (or have stolen) a valid `ldap_sessions` cookie/ID issued before their access was revoked — this is not exploitable by a fully unauthenticated client with no prior valid credential, which weakens applicability to the "unauthenticated HTTP client" framing in the question. It is fully reproducible: log in as an LDAP user, remove them from their LDAP group (or deactivate them) without waiting for `UpstreamSyncInterval`, and observe that the existing session continues to authorize privileged requests until the next sync.

### Recommendation
Perform (or rate-limited) revalidation of the cached role/session against the upstream LDAP directory synchronously within `AuthorizedUserWithSession` (or trigger an out-of-band `Work()` call keyed to session use) rather than relying solely on the ticker-driven background sync, so that revocation takes effect on the next request rather than the next sync tick. At minimum, shrink the default `UpstreamSyncInterval` and clearly document that access revocation is not immediate.

### Proof of Concept
1. Configure LDAP auth with `UpstreamSyncInterval` set to a long duration (e.g., 1h).
2. Log in as a user in the Admin LDAP group via `POST /sessions`, capturing the session cookie; confirm `ldap_sessions` row is created with role `admin`.
3. Remove the user from the Admin group upstream (or mark inactive), without waiting for the sync tick.
4. Immediately reuse the captured session cookie against an admin-only endpoint (e.g. `POST /v2/users`) and assert the request still succeeds with admin privileges — demonstrating revocation is not honored until `LDAPServerStateSyncer.Work` runs.
5. Manually invoke `Work(ctx)` (or advance past the sync interval) and repeat step 4, asserting the request is now rejected/downgraded, confirming the cache-only nature of `AuthorizedUserWithSession`.

func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

func (l *LDAPServerStateSyncer) Close() error {
	close(l.stopCh)
	<-l.done
	return nil
}

func (l *LDAPServerStateSyncer) run() {
	defer close(l.done)
	ctx, cancel := l.stopCh.NewCtx()
	defer cancel()
	ticker := time.NewTicker(l.config.UpstreamSyncInterval().Duration())
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			l.Work(ctx)
		}
	}
}
