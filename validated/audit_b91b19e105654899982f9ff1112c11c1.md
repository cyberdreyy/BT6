### Title
EI credentials bypass "EIs not allowed" restriction on int32 job runs via `isUser` check confusion - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`AuthenticateExternalInitiator` authenticates external initiators (EIs) and then sets the *same* context key used for real user sessions: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [1](#0-0) . `GetAuthenticatedUser` simply does `c.Get(SessionUserKey)` and a type assertion to `*clsessions.User`, with no way to tell whether the value was populated by `AuthenticateBySession`/`AuthenticateByToken` (a real user) or by `AuthenticateExternalInitiator` (an EI) [2](#0-1) . In `PipelineRunsController.Create`, the code relies on `_, isUser := auth.GetAuthenticatedUser(c)` to gate int32 job-ID runs, with the comment "only users are allowed to run jobs using int IDs - EIs not allowed" [3](#0-2) . Since `AuthenticateExternalInitiator` populates `SessionUserKey` with a valid `*clsessions.User{Role: UserRoleRun}`, `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests exactly as it would for a real run-role user, making `isUser` true and allowing the int32-ID code path to execute `prc.App.RunJobV2`.

### Impact Explanation
This is a broken access-control / authorization bypass matching Chainlink's "authorization bypass" / "unauthorized job run" bounty impact class: an external-initiator credential (a lower-trust, narrowly-scoped credential typically meant only to POST bridge webhook triggers) is functionally elevated to be indistinguishable from a run-role user for the purpose of triggering arbitrary jobs by numeric ID, contrary to the code's own documented intent that "EIs not allowed" for int IDs.

### Likelihood Explanation
Precondition is simply possession of a valid EI access key/secret (a credential explicitly designed to be handed to comparatively less-trusted external initiator integrations). No user session, no admin/API token, and no additional privilege is required. The bypass is deterministic and repeatable on every request — it does not depend on race conditions or timing.

### Recommendation
Distinguish EI-originated sessions from real-user sessions in `GetAuthenticatedUser`/context storage — e.g., store a separate marker (or reuse `SessionExternalInitiatorKey` presence) and have `PipelineRunsController.Create` check `auth.GetAuthenticatedExternalInitiator(c)` is absent (or explicitly check the presence of `SessionExternalInitiatorKey`) before permitting int32-ID job runs, rather than relying solely on `GetAuthenticatedUser`'s generic ok bool.

### Proof of Concept
1. Handler-level Go test: build a gin context/router with `auth.Authenticate(store, auth.AuthenticateExternalInitiator)` middleware wrapping `PipelineRunsController.Create`.
2. Seed a valid `bridges.ExternalInitiator` in the mock/store `Authenticator`, and send `POST /v2/jobs/<int32ID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` matching the EI record (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`).
3. Assert that `prc.App.RunJobV2` is invoked and a 200/201 pipeline run response is returned — demonstrating that despite only EI credentials being presented, the "EIs not allowed" restriction did not hold.
4. Add assertion on `auth.GetAuthenticatedUser(c)`'s `ok` return value during an EI-authenticated request to show it equals `true`, identical to a real user session, confirming the root cause.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {

	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
