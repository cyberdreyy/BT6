### Title
Unrestricted vote-commission update via `update_commission_bps` allows withdraw authority to front-run epoch reward redemption and change effective commission with no delay window - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The legacy `update_commission` path in the vote program enforces an epoch-boundary rule (`is_commission_update_allowed`) that only allows commission *increases* in the first half of an epoch, specifically to prevent an authority from front-running reward calculation/redemption to unexpectedly change the cut taken from stakers. The newer basis-points commission path, `update_commission_bps`, explicitly removes this protection ("No commission update rule, per SIMD-0249 and SIMD-0291") and lets the authorized withdrawer change `inflation_rewards_commission_bps` (or `block_revenue_commission_bps`) at any slot, any number of times, subject only to a signature check. [1](#0-0) 

### Finding Description
`update_commission` (legacy percentage commission) requires that any commission *increase* only happen in the first half of the epoch, and always allows decreases: [2](#0-1) 

By contrast, `update_commission_bps`, used for the new basis-points commission fields introduced under SIMD-0291/SIMD-0123 (`CommissionKind::InflationRewards` / `CommissionKind::BlockRevenue`), performs no epoch-timing check at all — the only requirement is a valid signature from the authorized withdrawer: [3](#0-2) 

This is directly analogous to the OpenQV1 report: an account authority is able to change the "payout" (commission) term governing value owed to a third party (delegators/stakers) at any point in time, including immediately before the value-transfer event executes.

The reward-redemption path (`redeem_delegation_rewards` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`) reads the *current* `inflation_rewards_commission_bps()` value directly when `commission_rate_in_basis_points` is enabled, unless the separate `delay_commission_updates` feature is also active, in which case it instead looks up a commission value snapshotted from an earlier epoch: [4](#0-3) 

So the only thing preventing commission-front-running for reward redemption is the separate `delay_commission_updates` feature flag being active. If `commission_rate_in_basis_points` (and/or `block_revenue_sharing`) is active while `delay_commission_updates` is not (e.g., during a feature-activation rollout window, or on any cluster/testnet configuration where these flags are enabled independently), the withdraw authority of a vote account can submit an `update_commission_bps` transaction to raise the commission arbitrarily (up to `u16::MAX` bps) at any slot within the epoch — including immediately before the epoch-boundary reward-distribution computation reads it — extracting more commission from delegators than they anticipated, then lower it back afterward. This mirrors exactly the `OpenQV1.setPayout` front-running pattern: a privileged party changes the payout term unrestricted and at will, harming the unprivileged counterparties (stakers) who cannot react before the value transfer (reward redemption) occurs.

### Impact Explanation
This can result in stake/reward accounting corruption: delegators receive materially less staking reward than expected because the vote account's commission is spiked by the withdraw authority right before rewards are computed for the epoch, and then reduced back to a normal level afterward, repeating each epoch. This falls under the explicitly allowed "stake and reward accounting" category. The severity is bounded by the fact that (a) it requires the `commission_rate_in_basis_points`/`block_revenue_sharing` features to be active without `delay_commission_updates`, and (b) it requires control of the vote account's withdraw authority — but that is analogous to the original report where the "attacker" is the privileged bounty-issuer harming unprivileged claimers, so a vote-account operator harming its unprivileged delegators is a comparable trust relationship.

### Likelihood Explanation
Likelihood depends entirely on cluster feature-activation state: this is only exploitable during a window where the bps-based commission accounting is live but the anti-front-running delay feature is not. Because `update_commission` (legacy) explicitly retains its epoch-half restriction while `update_commission_bps` was deliberately designed ("per SIMD-0249 and SIMD-0291") without one, this appears to be an intentional, spec-approved design tradeoff rather than an accidental omission, so its likelihood of being an actively exploitable, unintended bug is uncertain and depends on feature-set rollout ordering, which I was not able to fully verify (feature IDs / activation epochs in `feature-set/src/lib.rs` and the exact conditions under which `commission_rate_in_basis_points` can be active without `delay_commission_updates`).

### Recommendation
Ensure `delay_commission_updates` is always active for any cluster/epoch where `commission_rate_in_basis_points` or `block_revenue_sharing` is active (i.e., make the delay a hard dependency/gate rather than an independently toggleable feature), or add an analogous epoch-timing restriction directly to `update_commission_bps` mirroring `is_commission_update_allowed`, so that commission increases affecting reward redemption cannot be applied and reflected within the same epoch's distribution.

### Proof of Concept
1. On a cluster/epoch where `commission_rate_in_basis_points` (or `block_revenue_sharing`) is enabled but `delay_commission_updates` is not, a vote account's withdraw authority holds a stake-weighted vote account with delegated stake.
2. Near the end of an epoch (before reward-distribution computation for that epoch runs), the withdraw authority submits a `VoteInstruction::UpdateCommissionBps` transaction raising `inflation_rewards_commission_bps` to a high value — reachable via `update_commission_bps` in `programs/vote/src/vote_state/mod.rs` lines 828-859, which imposes no epoch-timing restriction, only a withdrawer signature check (line 847).
3. When `redeem_delegation_rewards` runs (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs` lines 703-724), because `delay_commission_updates` is false, it uses `vote_state.inflation_rewards_commission()` directly — the just-updated, inflated value — reducing stakers' payout for that epoch.
4. After distribution, the withdraw authority submits another `UpdateCommissionBps` transaction to lower commission back to normal, repeating the cycle each epoch.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
