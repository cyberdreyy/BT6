### Title
Instant-withdraw receipts pay out unfunded claims from other users' funded withdraw reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` pays the full `instantWithdrawsRequests[_user]` balance at par without checking that the request was actually funded (`pendingInstantWithdraws` was collected via `collectInstantWithdrawFunds`) and without any epoch-boundary wait, unlike `claimWithdrawRequest` which enforces `epochNumber > lastWithdrawRequest[_user]` and per-epoch funding accounting. Analogous to the CVE-2018-19763 over-read, the claim path "reads" the user's receipt balance beyond the bounds of what was actually funded, paying it out of underlying held by the strategy that belongs to other users' already-funded withdraw receipts.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw` (lines 356-375), the CDO burns strategy tokens, mints a 1:1 receipt to the user, and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`. Funding arrives separately: `collectInstantWithdrawFunds` (lines 398-403) pulls underlying from the CDO and decrements `pendingInstantWithdraws`.

`claimInstantWithdrawRequest` (lines 380-393) then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no check that `pendingInstantWithdraws` was funded for this receipt, and no epoch gating. The strategy contract holds underlying transferred by `collectWithdrawFunds` (line 428) that is reserved for honest users' funded `pendingWithdraws` receipts. A user with a fresh, completely unfunded instant receipt can claim immediately and draw from that commingled balance. `_transferFundedClaim` (line 897+) deliberately skips the `defaultRecoveryReserve`, but it does not distinguish instant-funded underlying from normal-withdraw-funded underlying.

### Impact Explanation
Direct theft with a quantified loss: an attacker deposits tranche tokens, requests an instant withdraw of amount X (this burns real tranche value X of principal), and immediately calls `claimInstantWithdrawRequest`. The strategy pays X underlying out of funds collected for other users' funded withdraw receipts. The attacker's own request remains tracked in `pendingInstantWithdraws` (still owed by the borrower/CDO), so they effectively get paid twice: once from the funded reserve pool, once still claimable against borrower funding. Honest withdrawers' claims later revert on insufficient strategy balance — permanent loss up to the strategy's funded-but-unclaimed underlying balance.

### Likelihood Explanation
Requires the instant-withdraw path to be live (not programmable borrower, `disableInstantWithdraw == false`) and the CDO-side APR-drop condition `lastEpochApr > unscaledApr + instantWithdrawAprDelta` to hold at request time — a normal, honest configuration state, not an attacker-controlled precondition. The strategy must hold funded underlying, which is the normal state between `collectWithdrawFunds`/`collectInstantWithdrawFunds` and user claims. The attacker's only cost is temporarily locking tranche principal, which is recovered in the claim.

I could not fully verify the CDO-side `claimInstantWithdrawRequest` wrapper (whether it adds gating before calling the strategy) within the available iterations; if `IdleCDOEpochVariant.claimInstantWithdrawRequest` enforces an epoch wait or funding check, the exploitability window narrows accordingly, though the strategy-level missing funded-check remains a broken "one receipt one funded payout" invariant.

### Recommendation
In `claimInstantWithdrawRequest`, only pay the portion of `instantWithdrawsRequests[_user]` that has actually been funded — e.g., track a funded instant balance (incremented in `collectInstantWithdrawFunds`, decremented on claim) or gate claims on `pendingInstantWithdraws == 0` for the user's request epoch, mirroring how `claimWithdrawRequest` ties payout to per-epoch funding via `epochNumber > lastWithdrawRequest` and `lossRecoveryPriceByEpoch`.

### Proof of Concept
```solidity
// Foundry fork PoC sketch against IdleCreditVault + IdleCDOEpochVariant
function testInstantWithdrawDrainsFundedReserves() external {
    // 1. Honest user deposits AA, requests normal withdraw in epoch N.
    uint256 dep = 100_000e6;
    uint256 minted = idleCDO.depositAA(dep);
    cdoEpoch.requestWithdraw(minted, address(AAtranche));

    // 2. Epoch runs; stopEpoch funds pendingWithdraws into the strategy.
    _startEpoch();
    _stopEpochFullyFunded(); // collectWithdrawFunds moves underlying to strategy
    uint256 strategyBal = underlying.balanceOf(address(strategy));
    assertGt(strategyBal, 0); // funded reserve for honest receipt

    // 3. Attacker deposits, APR drops (honest manager action), requests instant withdraw.
    uint256 atkDep = strategyBal; // sized to drain the funded reserve
    uint256 atkMinted = idleCDO.depositAA(atkDep);
    // manager lowers unscaledApr below lastEpochApr - instantWithdrawAprDelta
    cdoEpoch.requestWithdraw(atkMinted, address(AAtranche)); // routes to requestInstantWithdraw

    // 4. Attacker claims immediately, before any collectInstantWithdrawFunds.
    assertGt(strategy.pendingInstantWithdraws(), 0); // still unfunded
    uint256 pre = underlying.balanceOf(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - pre, 0); // paid from honest reserve

    // 5. Honest user's funded claim now reverts / underpays.
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```
