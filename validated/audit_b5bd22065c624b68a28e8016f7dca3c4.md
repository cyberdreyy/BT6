## Title
`staking_contract::set_beneficiary_for_operator` omits the `assert_account_is_registered_for_apt` guard that `vesting::set_beneficiary` uses, letting an operator permanently brick `distribute`/`unlock_stake`/`request_commission`/`switch_operator` for a staker - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
This is the Aptos-native analog of the Vader "single non-payable recipient blocks the whole payout" bug class. `staking_contract::distribute_internal` pays out every shareholder of a `distribution_pool` (staker + operator/beneficiary) in one atomic loop using `aptos_account::deposit_coins`. If any one recipient in that loop cannot accept the deposit, the entire transaction — including the staker's own withdrawal — aborts. The framework already recognizes and mitigates exactly this risk in `vesting.move::set_beneficiary`, which explicitly requires the new beneficiary to be `assert_account_is_registered_for_apt` before allowing the switch [1](#0-0) . `staking_contract::set_beneficiary_for_operator`, however, performs no such check and lets any operator, unprivileged over the staker's funds, freely set an unregistered/non-accepting beneficiary address [2](#0-1) .

### Finding Description
`distribute_internal` withdraws the pool's total inactive/pending_inactive stake in one shot, then loops over all shareholders of the internal `distribution_pool` and pays each one via `aptos_account::deposit_coins`; when the recipient is the operator it is redirected to `beneficiary_for_operator(operator)` [3](#0-2) .

`aptos_account::deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the target account is not registered for the coin type and has opted out of direct transfers via `set_allow_direct_coin_transfers(false)` [4](#0-3) . Because Move aborts revert the entire transaction, this single failing deposit reverts every other payout processed earlier in the same `while` loop, including the staker's own unlocked stake.

`set_beneficiary_for_operator` lets the operator (any account, not privileged over the staker) set `new_beneficiary` to any address at all — there is no `assert_account_is_registered_for_apt` or account-existence check as there is on the equivalent vesting-contract path [5](#0-4) . Compare this to `vesting::set_beneficiary`, whose comment states the exact rationale for the missing check: *"Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered."* [6](#0-5) 

`distribute_internal` is reached from every important staking_contract entry point that an ordinary staker relies on: `distribute` (callable by anyone) [7](#0-6) , `request_commission` [8](#0-7) , `update_commision`, and `switch_operator` [9](#0-8) . Once the beneficiary is unpayable, none of these functions can complete for that (staker, operator) pair, so the staker cannot withdraw commission-adjacent stake nor switch away from the malicious operator through the normal path (switch_operator itself calls `distribute_internal` before touching the operator).

### Impact Explanation
A malicious operator can call `set_beneficiary_for_operator` with an address that has been configured (by the attacker) to reject unregistered direct coin transfers, with zero cost and zero special privilege over the staker's stake pool. Every subsequent `distribute`, `request_commission`, and `switch_operator` call for that staking contract will permanently abort, trapping the staker's already-unlocked/inactive stake (and any operator commission) inside the stake pool indefinitely. This matches the required "permanent lock or non-recoverable loss of claim rights in stake ... commission, beneficiary flows" impact.

### Likelihood Explanation
Likelihood is high: the operator role is routinely a separate, less-trusted party from the staker in `staking_contract` (that is the entire point of the module), the beneficiary-setting call is a plain, unprivileged `entry` function gated only by `features::operator_beneficiary_change_enabled()`, and no code path re-validates or allows the staker/governance to reset an operator's beneficiary. The framework's own comment in `vesting.move` confirms the authors were aware this exact registration gap causes `distribute()` to fail and block all other recipients, but the equivalent guard was not applied to `staking_contract::set_beneficiary_for_operator`.

Note: I was not able to fully verify, within the available tooling, whether `coin::is_account_registered<AptosCoin>`/`coin::deposit` still enforces the "not registered + opted out" abort path after the AptosCoin migration to the fungible-asset framework, or whether AptosCoin transfers now bypass this check entirely via a fungible-asset fast path. This affects whether the abort condition in `aptos_account::deposit_coins` is currently reachable for AptosCoin specifically. This should be confirmed with a live Move test before treating this as conclusively exploitable.

### Recommendation
Add the same guard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator` — require `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` before accepting the change — and/or make `distribute_internal` resilient to a single failing recipient (e.g., skip/queue a failed payout rather than aborting the whole distribution loop), consistent with the two mitigation options given in the original Vader report.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `create_staking_contract`.
2. `operator` calls `set_beneficiary_for_operator(operator, evil_addr)` where `evil_addr` is an account that has called `aptos_account::set_allow_direct_coin_transfers(false)` and is not registered for `AptosCoin` [5](#0-4) .
3. Stake accrues rewards and becomes unlockable/inactive.
4. Any call to `distribute`, `request_commission`, or `switch_operator` triggers `distribute_internal`, which withdraws the pool's inactive stake and then tries `aptos_account::deposit_coins(evil_addr, commission_coins)` when redistributing the operator's commission share [10](#0-9)  — this aborts, reverting the entire transaction and leaving the staker's inactive stake permanently stuck in the pool.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
