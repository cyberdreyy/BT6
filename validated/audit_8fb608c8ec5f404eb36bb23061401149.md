### Title
EI credentials can trigger arbitrary integer job runs via PipelineRunsController.Create, bypassing the "EIs not allowed" restriction - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` decides whether to allow triggering a job run by integer ID solely by checking `auth.GetAuthenticatedUser(c)`, but `AuthenticateExternalInitiator` also populates `SessionUserKey` (with a synthetic `Run`-role user) whenever a request authenticates via valid External Initiator (EI) credentials. This makes `isUser` true for EI-authenticated requests too, directly contradicting the code comment "only users are allowed to run jobs using int IDs - EIs not allowed," and lets any EI credential holder run any job by numeric ID.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group with three chained auth methods: [1](#0-0) . `auth.Authenticate` tries each method in order and stops at the first success; `AuthenticateExternalInitiator` succeeds for any request bearing valid EI `AccessKey`/`Secret` headers, and it explicitly sets a synthetic `Run`-role user in addition to the EI record: [2](#0-1) .

`RequiresRunRole` wraps the handler and only checks that `user.Role != UserRoleView`, which passes for this synthetic `Run`-role user, so an EI credential holder reaches `Create` unimpeded: [3](#0-2) .

Inside `Create`, the code parses the path param; if it looks like a UUID it is rejected (webhook job type removed), otherwise it checks `isUser` via `GetAuthenticatedUser(c)` and, if true, parses it as an int32 job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly — with no check on `GetAuthenticatedExternalInitiator(c)` to exclude EI-originated requests: [4](#0-3) . `GetAuthenticatedUser` simply checks for presence of `SessionUserKey` in the gin context and type-asserts it to `*clsessions.User`: [5](#0-4) , which is exactly what `AuthenticateExternalInitiator` populates. The `ExternalInitiator` credential itself (`AccessKey`/`HashedSecret`) is not scoped to any specific job or job ID: [6](#0-5) , so once authenticated, this bug lets it run any integer job ID in the system, not just the webhook jobs it was designed for (webhook jobs used UUIDs, which have since been removed entirely per line 103-107 of the controller).

The intended design (per the comment) is clearly to require a real user (session/token) — not an EI-derived pseudo-user — for integer-ID job runs, but the implementation only checks "is `SessionUserKey` present," which both real users and EIs satisfy.

### Impact Explanation
An external-initiator credential holder — a lower-trust class of credential intended only to trigger webhook-type job runs — can trigger execution of arbitrary jobs (by integer ID) belonging to any job type in the node (e.g., OCR, Direct Request, Cron, Flux Monitor jobs), consuming node resources, potentially triggering unwanted on-chain transactions/fund movement if the job's pipeline includes ETH/other chain transactions, or causing unauthorized side effects. This matches the "unauthorized job run" bounty impact class and constitutes an authorization-bypass / privilege-escalation issue since EI credentials are a narrower-scope credential than full user sessions/tokens.

### Likelihood Explanation
The precondition is simply possession of a valid EI `AccessKey`/`Secret` pair, which is a credential explicitly designed to be handed to external, less-trusted systems (as opposed to admin/API-token/session credentials). No additional privilege, race condition, or complex chaining is required — a single POST request with the EI headers set and an integer job ID in the path is sufficient. This is a straightforward, easily repeatable exploit for any party holding EI credentials for the node.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated as external initiators before permitting integer-ID job runs, e.g., check `if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI { return 422/401 }` prior to (or in addition to) the `isUser` check, rather than relying on the ambiguous overloaded `SessionUserKey`. More robustly, `AuthenticateExternalInitiator` should not silently synthesize a `*clsessions.User` under the same context key used for real users; instead, downstream handlers needing user-vs-EI distinction should query `GetAuthenticatedExternalInitiator` first and treat its presence as authoritative, or a distinct context key/type should be used for EI pseudo-users so `GetAuthenticatedUser` cannot conflate the two.

### Proof of Concept
Handler-level Go integration test:
1. Set up a `PipelineRunsController` with a mocked `chainlink.Application` whose `RunJobV2` is asserted to be called/not called.
2. Create a valid `ExternalInitiator` in the test DB/mock `Authenticator`, with known `AccessKey`/`Secret`.
3. Build a gin test router mirroring `v2Routes`'s `userOrEI` group registration for `POST /v2/jobs/:ID/runs`.
4. Send `POST /v2/jobs/5/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) set to the EI's valid credentials, and no session cookie or `X-API-KEY`.
5. Assert:
   - Expected (per comment "EIs not allowed"): response is `401`/`422` and `RunJobV2` is never invoked.
   - Actual (bug): response is `200` and `App.RunJobV2(ctx, int32(5), nil)` is invoked, since `AuthenticateExternalInitiator` sets `SessionUserKey` and `isUser` becomes `true`.
6. Add a companion test with a real session/API-token user hitting the same endpoint to confirm normal (intended) behavior still works, isolating the EI-specific bypass.

```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
```

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
