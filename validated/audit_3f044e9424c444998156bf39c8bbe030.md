### Title
Griefing DoS via pre-funding a not-yet-created System Program account address before it is claimed - (File: `programs/system/src/system_processor.rs`)

### Summary
The bug class in the CID NFT report is: a caller performs a multi-step operation that (1) assumes a not-yet-existing resource identifier/address will belong to it and (2) acts on that assumption in the same transaction, allowing a third party to front-run step (1) so that the address/ID is claimed by someone else, causing the caller's transaction to permanently or repeatedly fail. Agave's System Program `CreateAccount`/`CreateAccountWithSeed` path has the same "assumed-free-address" pattern: any account address (including deterministic ones derived from a base pubkey via `Pubkey::create_with_seed`, and other program-derived/nonce/stake account addresses that flow through `create_account`) is only allowed to be created if it currently has zero lamports. Because plain SOL transfers to an address require no signature or cooperation from that address's owner, an attacker can pre-fund the exact address a victim is about to use for account creation, causing `SystemError::AccountAlreadyInUse` and blocking the victim's legitimate create transaction.

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` enforces the "must not already be in use" invariant purely by checking the target account's lamport balance: [1](#0-0) 

```
fn create_account(
    ...
) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(...);
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    ...
}
```

`CreateAccountWithSeed` computes the target address deterministically from a public `base` pubkey, a `seed` string, and an `owner` program id via `Pubkey::create_with_seed`: [2](#0-1) 

Because the base pubkey, seed, and owner are all public inputs known ahead of time (e.g. visible in the CLI wallet/nonce/stake flows that compute `nonce_account_address` or `stake_account_address` before sending the creating transaction, as in `cli/src/nonce.rs` and `cli/src/stake.rs`), an attacker who observes or predicts the intended `(base, seed, owner)` tuple can simply send 1 lamport via an ordinary `SystemInstruction::Transfer` to that address before the victim's `CreateAccountWithSeed` transaction lands. This requires no signature from the target address at all — only the attacker's own funds and a normal transfer instruction. The victim's subsequent `create_account`/`CreateAccountWithSeed` call then fails at the `to.get_lamports() > 0` check.

This mirrors the analog reported in the CID NFT `mint()` bug: the victim's transaction is built assuming exclusive ownership of a not-yet-materialized resource (there, a sequential NFT ID; here, a deterministic account address), and an unprivileged third party can claim that resource first via an ordinary, cheap operation, forcing the victim's transaction to revert.

Agave developers were aware of a related aspect of this problem: `create_account_allow_prefund` was added specifically to allow account creation to succeed even when lamports were pre-sent to the target address: [3](#0-2) 

However, this variant is opt-in per instruction and is not what most existing flows use. Standard `CreateAccountWithSeed` (used by CLI nonce-account-with-seed creation, stake-account-with-seed creation, and general "create derived account" flows) and plain `CreateAccount` (used for durable nonce accounts, stake accounts, vote accounts, and countless SPL/user-facing flows) still use the strict `lamports > 0` check and thus remain vulnerable to this griefing pattern.

### Impact Explanation
An attacker can, at negligible cost (rent-exempt-minimum-independent — even a single lamport suffices to trip the `> 0` check), deny a legitimate user the ability to create an account at a specific deterministic address (nonce-account-with-seed, stake-account-with-seed, or any program's derived System-Program-owned account). Because the poisoning lamports remain on the account indefinitely (the account is never actually initialized, so nobody but the eventual creator — if the creation ultimately fails — can reclaim it through the normal creation path), this is not merely a transient front-run/revert as in the CID NFT case, but can constitute a persistent denial-of-service against that specific address, forcing the victim to abandon the address/seed combination entirely. This is a state-mutation-based griefing vector reachable by any unprivileged user issuing ordinary transfer transactions against a publicly predictable address.

### Likelihood Explanation
Likelihood is high in any workflow where the target address is deterministically derivable from public data before the creating transaction is submitted — this is exactly the design of `CreateAccountWithSeed` (`base`, `seed`, `owner` are all chosen/known by the caller in advance and often visible in CLI invocations, RPC calls, or mempool/QUIC-ingested transactions before they land). No privileged access, leaked keys, or validator cooperation is required; a single ordinary `SystemInstruction::Transfer` from any funded keypair suffices.

### Recommendation
For flows that create accounts at addresses derived from public inputs (seed-derived, PDA-imitating, or otherwise predictable addresses), prefer the `CreateAccountAllowPrefund` semantics (or equivalent: check for `owner == system_program::id() && data.is_empty()` rather than `lamports == 0`) so that pre-funding an address with attacker lamports cannot block legitimate account initialization. Alternatively, callers that build multi-instruction transactions relying on a specific target address existing/not-existing should re-derive and re-validate assumptions atomically within the same instruction rather than relying on the address being untouched between transaction construction and execution.

### Proof of Concept
1. Victim (or victim's CLI, e.g. `solana create-nonce-account --nonce-account-seed`) computes `nonce_account_address = Pubkey::create_with_seed(&nonce_account_pubkey, &seed, &system_program::id())` and prepares a `CreateAccountWithSeed` transaction targeting that address (see `cli/src/nonce.rs` `process_create_nonce_account`, lines 452-467).
2. Attacker, observing the base pubkey/seed pattern (or brute-forcing likely seeds) before the victim's transaction lands, submits an ordinary `system_instruction::transfer` sending 1 lamport to `nonce_account_address`.
3. When the victim's `CreateAccountWithSeed` transaction executes, `create_account` in `system_processor.rs` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, failing the victim's transaction and leaving the intended nonce/stake account address permanently poisoned for standard (non-prefund) creation.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
