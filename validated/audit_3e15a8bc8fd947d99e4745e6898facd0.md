### Title
Signer weight double-counted in both `total_weight_approved` and `total_weight_rejected` when a signer flips from rejection to acceptance - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::poll` tallies signer votes for a proposed block into two independent counters, `total_weight_approved` and `total_weight_rejected`, using two different guard sets (`gathered_signatures` for acceptances, `responded_signers` for rejections). Because a legitimate rejection can be followed by a legitimate acceptance for the same block (the signer's local view changes, e.g. once a pending Bitcoin block finishes processing), the same signer's weight is added to *both* running totals, breaking the invariant that the sum of weights the coordinator has counted should never exceed the total signer-set weight for a single block decision.

### Finding Description
The Taiko report's root cause is that the protocol permanently records/burns the "history" of an earlier verdict (a bond slashing) and never reconciles it once a later, contradicting-but-ultimately-authoritative verdict arrives — so the final state of the world ends up double-charged/inconsistent with what actually happened.

The same class of bug exists in the miner-side vote tally in `stackerdb_listener.rs`. On `BlockResponse::Accepted`: [1](#0-0) 
the code only guards against double counting an acceptance against itself (`!block.gathered_signatures.contains_key(&slot_id)`); it never checks whether that same `slot_id` already contributed weight to `total_weight_rejected`.

On `BlockResponse::Rejected`: [2](#0-1) 
the code guards against double-counting a rejection via the shared `responded_signers` set, but this only prevents a second rejection (or an acceptance-then-rejection, since `responded_signers` is also touched on acceptance) — it does not prevent a *reject-then-accept* sequence, because the acceptance branch never consults `responded_signers` before adding to `total_weight_approved`.

The repo's own test suite documents that a signer legitimately re-evaluates and flips a prior rejection into a pre-commit/acceptance for the *same* block once the reason for rejecting disappears (e.g. a delayed Bitcoin block finishes processing): [3](#0-2) 
This is exactly the "reject → later accept for the same object" sequence the coordinator's tally does not reconcile — mirroring the Taiko bug where an earlier verdict's consequence (a slashed bond, here: counted rejection weight) is never rolled back once a later verdict for the same subject supersedes it.

The `BlockStatus.total_weight_rejected`/`total_weight_approved` feed directly into the coordinator's accept/reject/timeout decision: [4](#0-3) 
so a signer's weight can simultaneously count toward "70% approved" and toward "the 70% threshold is impossible" (rejection ≥ 30%). This is the "aggregated-weight vs verified-accepts" equality named in scope: the sum of weight_approved and weight_rejected the coordinator has tallied for one block can legitimately exceed the total signer set's weight, corrupting both thresholds.

### Impact Explanation
Because `total_weight_rejected` keeps counting a signer's stale rejection weight even after that same signer later signs (accepts) the block, the coordinator can incorrectly conclude `SignersRejected` (returning an error and abandoning the block) at `stacks-node/src/nakamoto_node/signer_coordinator.rs:509-540` even though the outstanding, non-stale opinion of every signer would in fact reach the 70% approval threshold. This wedges block production on a valid block: the miner discards a block that has (or would reach) legitimate majority support, and must re-propose from scratch. This is a liveness degradation analogous to the "Critical/High" categories in scope (acting on a stale/incorrect aggregated threshold), though it does not itself cause an invalid/non-canonical signature — it is a miner-side (coordinator) tally corruption rather than a per-signer safety violation, so it sits closer to the "liveness wedge" bucket than to a signature-safety break.

### Likelihood Explanation
This requires no majority collusion and no extra trust: a single normal signer flipping its own vote in the ordinary reject→reconsider→accept flow the codebase already implements and tests (`reprocess_block_proposals.rs`) is sufficient to trigger the double count. A miner (the one-slot actor in scope) merely needs to observe/gossip proposals in a way that naturally produces this reconsideration (e.g., proposing while a Bitcoin block is still processing on some signers, as the existing regression test already exercises), so the timing window is realistically triggerable without any attacker-controlled majority.

### Recommendation
Use a single per-slot "current opinion" record for tallying instead of two independently-guarded counters. When a `BlockResponse::Accepted` arrives for a `slot_id` that is present in `responded_signers` due to a prior rejection, subtract that signer's weight from `total_weight_rejected` before adding it to `total_weight_approved` (and symmetrically, though rejection-after-acceptance is already blocked by the shared `responded_signers` set, make that symmetry explicit). Concretely, track weight per slot in a `HashMap<u32, (bool /*accepted*/, u32 /*weight*/)>` and recompute `total_weight_approved`/`total_weight_rejected` as sums over that map rather than incrementally through two independent guards.

### Proof of Concept

Recommend a Devin session instrument `stackerdb_listener.rs`'s `BlockStatus` in a unit test: send a `Rejected` message for `slot_id=X` (asserting `total_weight_rejected` increases), then send an `Accepted` message for the same `slot_id=X` and same block hash (asserting `total_weight_approved` also increases while `total_weight_rejected` is not decremented), demonstrating `total_weight_approved + total_weight_rejected > total_weight`.
