### Title
Stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` entries after normal instant-withdraw claims inflate default recovery basis and permanently dilute/lock recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` on the normal (non-default) claim path, but never deletes the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that were written in `requestInstantWithdraw`. Like the Zebra `cancel_handles` leak — an entry is retained because the code path that retires it never touches the keyed record — already-paid instant receipts remain indistinguishable from pending ones. When the CDO later defaults with a non-zero `pendingInstantWithdraws` in the same epoch, `defaultPendingClaimBasis()` counts the stale entries in `totalBasis`, `finalizeDefaultRecovery` computes a lower `defaultRecoveryPrice`, and the stranded remainder of `defaultRecoveryReserve` can never be claimed.

### Finding Description
`requestInstantWithdraw` records three things: the aggregate `instantWithdrawsRequests[_user]`, the per-user-per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the per-epoch total `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

`claimInstantWithdrawRequest` only zeroes `instantWithdrawsRequests[_user]` and pays out. It does not touch either per-epoch mapping [2](#0-1) . The only code that clears those mappings is `_claimDefaultedInstantWithdrawRequest`, which runs solely after a finalized default [3](#0-2) .

`defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` — i.e., when any current-epoch instant request was only partially funded [4](#0-3) . `finalizeDefaultRecovery` then sets `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` includes that stale claim mass [5](#0-4) .

Consequences:
- **Dilution**: every legitimate defaulted claimant (instant, normal withdraw, and active tranche holders via `activeFinalNAV`) gets a recovery ratio depressed by ghost claims that were already paid at par.
- **Permanent lockup**: the fraction of `defaultRecoveryReserve` corresponding to ghost basis can never be paid out. A user whose receipt was already claimed cannot consume the ghost entry either: `_claimDefaultedInstantWithdrawRequest` does `instantWithdrawsRequests[_user] -= claimBasis` and `_burn(_user, claimBasis)`, both of which underflow/revert once the aggregate receipt and minted tokens were cleared by the earlier normal claim [3](#0-2) .
- **Accounting skew via `_defaultPrefundedInstantReserve`**: `prefundedReserve = instantBasis - pendingInstant` is also inflated by stale entries, which can inflate `reserveAmount` by counting strategy-held funds not actually earmarked for those claims [6](#0-5) .

No guard catches this: `_ensureDefaultRecoveryInitialized` does not inspect instant per-epoch mappings, and `_transferDefaultRecovery` only decrements the reserve without reconciling basis [7](#0-6) .

### Impact Explanation
Direct, quantifiable theft-by-dilution plus permanent freezing: in an epoch where some instant requests were funded+claimed and others remain unfunded, `recoveryPrice` is scaled down by `staleBasis / (realBasis + staleBasis)`. Legitimate claimants lose that fraction of their recovery forever; the corresponding `defaultRecoveryReserve` remainder becomes unclaimable dust locked in the strategy. The attacker vector is mild (any instant-withdraw requester can seed stale basis by claiming before a default), but the loss accrues to all recovery claimants and requires no privileged action.

### Likelihood Explanation
Requires a borrower default occurring in an epoch with a partially-funded instant-withdraw queue and at least one already-claimed instant request in the same epoch. Defaults are rare but are exactly the scenario the recovery machinery exists for, and the instant-withdraw feature makes partially-funded queues a normal operating state.

### Recommendation
In `claimInstantWithdrawRequest`, also clear the per-epoch records for the claiming user's current request epoch: decrement `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, and `pendingInstantWithdraws` for the funded portion (or track which epoch's entry is being claimed, e.g. via a `lastInstantWithdrawRequest` marker analogous to `lastWithdrawRequest`). Alternatively, reconcile `instantWithdrawClaimsByEpoch` inside `collectInstantWithdrawFunds`/`_defaultPrefundedInstantReserve` so the per-epoch total only ever reflects unclaimed receipts.

### Proof of Concept
Foundry fork PoC sketch (instant-mode CDO):

```solidity
// Setup: instant-withdraw enabled vault, epoch E running.
// 1. userA and userB both requestInstantWithdraw(X) in epoch E.
//    instantWithdrawClaimsByEpoch[E] = 2X, pendingInstantWithdraws = 2X.
// 2. CDO collects only X via collectInstantWithdrawFunds(X):
//    pendingInstantWithdraws = X (unfunded remainder).
// 3. userA calls claimWithdrawRequest/claimInstantWithdrawRequest via CDO:
//    instantWithdrawsRequests[userA] = 0, paid X.
//    BUG: instantWithdrawsRequestsByEpoch[userA][E] == X,
//         instantWithdrawClaimsByEpoch[E] still == 2X.
// 4. Borrower defaults; CDO calls finalizeDefaultRecovery(recovered, source).
//    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[E]
//                               = pendingWithdraws + 2X   // should be X
//    recoveryPrice = reserve * 1e18 / totalBasis  // depressed by X ghost basis
// 5. Assert: strategy.defaultRecoveryPrice() < expected par-adjusted price.
//    Assert: after all legitimate claims, defaultRecoveryReserve > 0 dust remains
//    that no claimant can ever withdraw (userA's stale entry reverts on claim).
```

Confirm the revert on the stale-entry path by calling `claimInstantWithdrawRequest` for `userA` post-finalization: `instantWithdrawsRequests[userA] -= claimBasis` underflows, so the ghost basis is permanently stranded.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
