### Title
Fail-closed guard bypassed: re-proposal of a `GloballyRejected` block with a stale, retriable local `reject_reason` discards the terminal rejection state and re-enters full evaluation - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_proposal` guards against re-processing a `GloballyAccepted` block (`should_reevaluate_block` → `block_info.globally_approved_and_responded()`), but has no symmetric guard for `GloballyRejected` blocks. If a tracked block's local `reject_reason` falls into the "retriable" category (`should_reevaluate_reject_reason`), a re-proposal of the identical block causes the signer to build a brand-new `BlockInfo` (`state = Unprocessed`) and re-run full validation from scratch, silently discarding the previously-recorded `GloballyRejected` verdict and overwriting it in `signerdb` — a state transition that `BlockInfo::check_state`/`move_to` is explicitly designed to forbid.

### Finding Description
The intended invariant (see `docs/signer-flows.md` §2 and `BlockInfo::check_state` in `stacks-signer/src/signerdb.rs:314-329`) is that `GloballyAccepted` and `GloballyRejected` are terminal and mutually unreachable:
```
BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
``` [1](#0-0) 

That guard, however, only protects transitions performed via `move_to` on an *existing* `BlockInfo`. In `handle_block_proposal`, when a proposal for an already-tracked block arrives, `should_reevaluate_block` decides whether to re-evaluate:

```
if block_info.globally_approved_and_responded() { ... return false; }
if !should_reevaluate_reject_reason(block_info) { ... return false-branches ... }
...
true   // fall through: re-evaluate
``` [2](#0-1) 

The only short-circuit for an already-decided block is `globally_approved_and_responded()`, which per its usage/log message ("received a block proposal for a globally accepted block to which we have already responded") only covers `GloballyAccepted`. There is no equivalent check for `GloballyRejected`. If the block's local `reject_reason` is one of the "retriable" categories (`UnknownParent`, `NotFoundError`, `NoSortitionView`, `ConnectivityIssues`, `TestingDirective`, `InvalidTenureExtend`, `ConsensusHashMismatch`, `NoSignerConsensus`, `NotRejected`, `Unknown`):

```
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            ...
             => true,
            ... => false,
        }
    } else { false }
}
``` [3](#0-2) 

`should_reevaluate_block` returns `true`, and back in `handle_block_proposal` the code builds a fresh `BlockInfo` from the re-proposal — bypassing `move_to`/`check_state` entirely:

```
// Creating a new proposal will overwrite any prior proposal info on the block if it exists, e.g. validity, signed_timestamps, etc.
let mut block_info = BlockInfo::from(block_proposal.clone());
``` [4](#0-3) 

`BlockInfo::from(BlockProposal)` always sets `state: BlockState::Unprocessed`, `valid: None`, `reject_reason: None`, discarding everything, including the terminal `GloballyRejected` fact: [5](#0-4) 

This new `block_info` is then run through the full evaluation path (`check_block_against_state` → node validation → `check_block_against_signer_db_state` → `mark_pre_committed` → pre-commit threshold → `mark_locally_accepted`), and is persisted with `insert_block`, which upserts on `signer_signature_hash`, overwriting the previously stored `GloballyRejected` row.

Critically, the "conflict" guard that would otherwise block re-signing a previously-decided block (`get_signed_conflicts`) is explicitly documented to be based only on blocks that were *signed* — rejection, even global rejection, "does not clear a conflict" but also never *creates* one, since a rejected block was never signed: [6](#0-5) 

So a block that was globally rejected without ever being signed by this signer has no conflict record and nothing stops the fresh evaluation from reaching a signature.

Attacker's exact path (attacker has one miner slot + at most one signer's weight, plus gossip access): the attacker mines a block `B` and gets its `signer_signature_hash` recorded by the victim signer with a retriable local reason (e.g. their own node lags and returns `ConnectivityIssues`/`NotFoundError` while validating), while a >30% weighted set of peers reject it (for any reason) — reaching `mark_globally_rejected()` on the victim's `BlockInfo` via `store_and_process_block_rejection`. The attacker then simply re-gossips the *identical* `BlockProposal` bytes (same `signer_signature_hash`) as `SignerMessageV0::BlockProposal` over StackerDB. The victim signer's `handle_block_proposal` reconstructs a fresh `Unprocessed` `BlockInfo`, discards the `GloballyRejected` fact, and re-validates from scratch.

### Impact Explanation
This breaks the fail-closed / one-way-latch safety property: `GloballyRejected` must be terminal, yet the signer can be driven back to `Unprocessed` and potentially all the way to `LocallyAccepted`/signature for the exact same block hash it had already tallied as globally rejected. If the underlying chain-state checks still pass (plausible precisely because the retriable reasons are transient conditions like a lagging node or missing burn view that can resolve on re-check), the victim signer can end up signing a block that the network had already fail-closed rejected, contributing its weight toward re-legitimizing a previously blocked block. This matches the Critical category: "a rejection recounted as acceptance." It is repeatable per re-proposal and requires no majority of signers or any privileged role — only crafting a BlockProposal with the same bytes and gossiping it.

### Likelihood Explanation
Preconditions: the victim signer's local `BlockInfo.reject_reason` for the target block must be one of the ten retriable reasons, and enough aggregate rejection weight (30%+) from any signers must have already been observed by the victim to trigger `mark_globally_rejected`. These are realistic operational conditions (validation timeouts, node connectivity lag, sortition/burn-view races) that a miner-controlled attacker can help engineer by timing their proposal (e.g., proposing before the burn view or a parent is available, per the existing `signer_reevaluates_proposal_with_missing_burn_view` test, which already demonstrates the "reprocess a previously-rejected-with-retriable-reason proposal" mechanic at the pre-global-rejection stage). The attack cost is one crafted/re-gossiped `BlockProposal` message; it is repeatable against any signer independently and needs no signer majority, node access, or the auth_token.

### Recommendation
Add a symmetric, sticky guard for `GloballyRejected` in `should_reevaluate_block` (or `handle_block_proposal`) analogous to `globally_approved_and_responded()`, so any block already in `BlockState::GloballyRejected` is never re-evaluated regardless of its retriable local `reject_reason`, and never reconstructed via `BlockInfo::from(block_proposal)`. When re-evaluation of a retriable reason is desired, mutate the existing tracked `BlockInfo` (preserving `state`) rather than constructing a fresh default `BlockInfo`, so `move_to`/`check_state` can enforce the terminal-state invariant uniformly.

#[test]
fn globally_rejected_block_is_not_reevaluated_on_reproposal() {
    let mut signer = /* construct test Signer */;
    let block_proposal = /* build a BlockProposal with a fixed signer_signature_hash */;
    let sighash = block_proposal.block.header.signer_signature_hash();

    // 1. Track the block with a retriable local reject_reason.
    let mut block_info = BlockInfo::from(block_proposal.clone());

    //    driving this signer's tracked BlockInfo to GloballyRejected.
    for addr in other_signer_addrs_crossing_threshold() {
        signer.store_and_process_block_rejection(
            &mut None, &mut block_info, &addr, RejectReasonPrefix::ConnectivityIssues,
        );
    }
    assert_eq!(block_info.state, BlockState::GloballyRejected);
    signer.signer_db.insert_block(&block_info).unwrap();

    // ASSERTION (equality before): the persisted state for this hash is GloballyRejected.
    let persisted = signer.signer_db.block_lookup(&sighash).unwrap().unwrap();
    assert_eq!(persisted.state, BlockState::GloballyRejected);

    // 3. Attacker re-gossips the IDENTICAL block proposal bytes.
    signer.handle_block_proposal(&stacks_client, &mut None, &block_proposal);

    // ASSERTION (equality after, should hold but currently FAILS):
    // A globally-rejected block must remain GloballyRejected and must not be
    // reset to Unprocessed / re-validated.
    let persisted_after = signer.signer_db.block_lookup(&sighash).unwrap().unwrap();
    assert_eq!(
        persisted_after.state, BlockState::GloballyRejected,
        "FAIL-CLOSED VIOLATION: previously globally-rejected block was reset to {:?}",
        persisted_after.state
    );
}

fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {

        match reject_reason {

            | RejectReason::NoSortitionView
