## Analog Found

### Title
Missing chainstate re-check before broadcasting a threshold-reached block signature - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The report's bug class is "a state-changing action is reachable through a path that omits a guard that parallel paths to the same action enforce" (`authRedeem` lacking the `unpaused(p)` modifier that `redeem` carries). The same shape exists in the v0 signer: the code path that promotes a block to `LocallyAccepted`/`signed_group` and pushes it to the node when *other signers'* acceptance signatures cross the 70% threshold omits the chainstate re-check that every other path leading to the same broadcast performs.

### Finding Description
Three places in `stacks-signer/src/v0/signer.rs` can move a block toward being signed/broadcast, and two of them explicitly re-run `check_block_against_signer_db_state` immediately beforehand to catch the case where "the chain and signer db state may have changed materially since this block passed the proposal-time checks":

- `handle_block_validate_ok` re-checks before `mark_pre_committed`: [1](#0-0) 
- `handle_block_pre_commit` re-checks before signing at the pre-commit threshold, explicitly noting the reason: "Re-run the chainstate checks before putting a signature over the block": [2](#0-1) 

However, `store_and_process_block_signature`, which is invoked from `handle_block_signature` whenever a peer's `BlockAccepted` message is processed, tallies signature weight and — once the 70% threshold is crossed — calls `mark_locally_accepted(true)` and `broadcast_signed_block` directly, with **no call to `check_block_against_signer_db_state`** or to the sibling-conflict guard (`get_signed_conflicts`/`reorg_permit_stands`) that `handle_block_pre_commit` runs at the equivalent point: [3](#0-2) [4](#0-3) 

The docs confirm this recheck's purpose is exactly to catch the case that arises here — a signer having since signed a conflicting sibling block at the same height: [5](#0-4) 

### Impact Explanation
If a signer has already locally signed block A (own tenure or a rival tenure) and, before it re-evaluates, receives enough gossiped `BlockAccepted` signatures from *other* signers for a conflicting sibling block B at the same height, `store_and_process_block_signature` will mark B `LocallyAccepted`/`signed_group` and call `broadcast_signed_block`, pushing B to its own node via `handle_post_block`, without ever re-verifying B against the conflict/canonical-tip state that `handle_block_pre_commit` and `handle_block_validate_ok` are careful to re-check. This breaks the "signed vs. validated" / "one-per-height" equality the rest of the state machine maintains everywhere else a block is about to be broadcast, and can cause this signer's own node to adopt a block it has independent, still-fresh evidence conflicts with a block it itself signed — the equivocation-guard equality collapses on this path specifically because the guard other paths enforce is missing here.

### Likelihood Explanation
Reachable purely via gossip: it triggers whenever the local signer, having already signed one sibling, receives enough already-existing `BlockAccepted` messages (already signed by other, legitimate signers) for the competing sibling to cross the weight threshold — no majority or malicious key control by the attacker is required at this specific code path; the miner/attacker only needs to produce two conflicting proposals at the same height and let normal signer traffic flow, which the codebase's own sibling-conflict tests (`signer_refuses_to_sign_second_sibling_tenure_start`, `stale_sibling_still_refused_when_canonical_tip_at_height`) show is an expected scenario the pre-commit path is hardened against: [6](#0-5) 

### Recommendation
Add a `check_block_against_signer_db_state` (and the same conflict-freshness handling used in `handle_block_pre_commit`) call in `store_and_process_block_signature` immediately before `mark_locally_accepted`/`broadcast_signed_block`, mirroring the guard already present in `handle_block_pre_commit` at [7](#0-6) , so that reaching the acceptance threshold via *peer* signatures cannot bypass the same re-verification that reaching it via a *local* pre-commit does.

### Proof of Concept
1. Miner proposes tenure-start block A at height H in tenure T1; signer S validates and signs A (`mark_locally_accepted`), per [8](#0-7) .
2. A reorg/second tenure T2 proposes a conflicting block B at the same height H. Other signers (not S) independently validate and sign B before S's own conflict-check would run, crossing 70% weight among themselves.
3. S receives these `BlockAccepted(B)` messages via StackerDB gossip; `handle_block_signature` → `store_and_process_block_signature` tallies weight, crosses `min_weight`, and — per [9](#0-8)  — calls `mark_locally_accepted(true)` and `broadcast_signed_block` for B with no call to `check_block_against_signer_db_state`, unlike the equivalent local-threshold path in `handle_block_pre_commit`.
4. S's own node receives and processes B via `handle_post_block`, even though S has independent, still-fresh knowledge (its own signature on A) that B is a conflicting sibling — knowledge that would have blocked the analogous local-signing path.

*(Note: because `store_and_process_block_signature` only aggregates signatures already produced by other signers rather than adding S's own new signature, this does not by itself constitute S signing an invalid block; the safety break is that S's re-verification/equivocation guard is skipped on this specific path when relaying/finalizing to its own node — I could not find, within the indexed portion of the codebase, any additional check elsewhere that closes this gap, but I was not able to fully trace `broadcast_signed_block`'s downstream interaction with `handle_post_block` before the iteration budget ran out.)*

    fn handle_block_signature(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        accepted: &BlockAccepted,
    ) {
        let BlockAccepted {
            signer_signature_hash: block_hash,
            signature,
            metadata,
            ..
        } = accepted;
        debug!(
            "{self}: Received a block-accept signature: ({block_hash}, {signature}, {})",
            metadata.server_version
        );

        // recover public key
        let Ok(public_key) = Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(
            block_hash.bits(),
            signature,
        ) else {
            debug!("{self}: Received unrecovarable signature. Will not store.";
                   "signature" => %signature,
                   "signer_signature_hash" => %block_hash);

            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block acceptance with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }
        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_signature_response(
                block_hash,
                &signer_address,
                signature,
            ) {
                warn!("{self}: Failed to add pending block signature response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block acceptance";
            "signer_pubkey" => public_key.to_hex(),
            "signer_address" => %signer_address,
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "signer_weight" => self.signer_weights.get(&signer_address).copied().unwrap_or(0),
            "tenure_extend_timestamp" => accepted.response_data.tenure_extend_timestamp,
            "tenure_extend_read_count_timestamp" => accepted.response_data.tenure_extend_read_count_timestamp
        );
        self.store_and_process_block_signature(
            stacks_client,
            sortition_state,
            &mut block_info,
            &signer_address,
            signature,
        );
    }

**File:** docs/signer-flows.md (L274-286)
```markdown
Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
```
