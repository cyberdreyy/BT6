## What I found

The LDAP advisory describes unbounded recursive-descent parsing depth causing stack exhaustion (CWE-674/770). The closest structural analog in `EzraCole/base--017` is the recursive Merkle Patricia Trie node decoder:

- `TrieNode::decode` in [1](#0-0)  recurses into itself with no depth counter: a `Branch` variant decodes via `Vec::<Self>::decode(buf)`, and an `Extension` payload recurses via `Self::decode(buf)` in `try_decode_leaf_or_extension_payload` [2](#0-1) . Neither path enforces a maximum nesting depth.
- This decoder is used throughout the fault-proof stack — e.g. `crates/proof/proof/src/l1/chain_provider.rs`, `crates/proof/proof/src/l2/chain_provider.rs`, `crates/proof/proof/src/eip2935.rs`, and `crates/proof/executor/src/test_utils.rs` — to decode trie-node preimages fetched from a `TrieProvider`/preimage oracle.
- By contrast, `crates/proof/tee/registrar/src/cbor.rs` (Nitro attestation CBOR parser) explicitly guards against exactly this bug class with `MAX_CBOR_NESTING_DEPTH` checked at every recursive call [3](#0-2) , showing the codebase is aware of this failure mode elsewhere but does not apply the same guard to `TrieNode::decode`.

## Why I can't confirm this rises to a reportable vulnerability

The critical difference from the LDAP case is that `TrieNode::decode` is only ever invoked on bytes whose `keccak256` hash matches a previously-committed blinded commitment (`TrieNode::Blinded { commitment }`, unblinded via `fetcher.trie_node_by_hash`). An attacker supplying a deeply-nested payload would need that payload to hash to the exact commitment referenced by a legitimate state/storage root — infeasible without a preimage/collision break. Deep nesting *within* a single un-blinded node is also self-limiting, since the "blind if ≥32 bytes encoded" rule caps how much nested structure can fit before a child must be blinded (i.e., turned into a new hash-gated lookup) — this bounds practical recursion depth well below what's needed for a real stack exhaustion in a single preimage.

I also looked at `crates/common/consensus/src/transaction/eip8130/account_changes.rs`, since `AccountChange::decode` recurses into `Vec::<InitialActor>::decode` and `Vec::<SignedChange>::decode` directly from raw, attacker-submitted EIP-8130 transaction bytes (no hash-commitment gate) [4](#0-3) . This would be the stronger analog (unbounded recursive parsing reachable from a single signed transaction via txpool admission) *if* `SignedChange` or `InitialActor` were themselves self-referential (containing nested `AccountChange`/`SignedChange` lists), which would let an attacker nest lists arbitrarily deep purely through RLP list-of-list encoding, independent of any hash gate. I was not able to retrieve and confirm the actual field definitions of `SignedChange`/`InitialActor`/`CreateEntry` before running out of investigation budget, so I cannot state whether this structure is actually self-referential or a flat, non-recursive type. Separately, `TxEip8130::decode_calls` does cap phases via `MAX_CALL_PHASES_PER_TX` [5](#0-4) , which suggests the authors are already bounding some list dimensions in this format, but that cap doesn't by itself prove `SignedChange`/`AccountChange` nesting is bounded.

## Conclusion

I don't have enough confirmed evidence to assert a concrete, exploitable stack-exhaustion vulnerability analogous to the LDAP advisory in this codebase. The `TrieNode::decode` recursion lacks an explicit depth guard but appears practically gated by cryptographic hash commitments and self-limiting node-size constraints. The EIP-8130 `AccountChange`/`SignedChange` decode path is a plausible unguarded-recursion candidate reachable directly from an attacker's transaction bytes, but I could not verify whether the relevant types are actually self-referential — this would need direct inspection of `crates/common/consensus/src/transaction/eip8130/account_changes.rs` (full struct/enum definitions for `SignedChange`, `InitialActor`, `CreateEntry`) to confirm or rule out unbounded nesting.
