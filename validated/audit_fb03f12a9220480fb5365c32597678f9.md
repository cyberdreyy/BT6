### Title
Unsanitized artifact `--name` enables directory traversal in `generateStatementToFile` metadata file path - ([File: commands/helpers/artifact_metadata.go])

### Summary
`ArtifactsUploaderCommand.artifactFilename` correctly sanitizes the job-supplied `--name` via `filepath.Base`, preventing traversal for the actual archive filename sent to the API. However, `Execute()` passes the raw, unsanitized `c.Name` (only `shell.Expand`-ed, never `filepath.Base`-ed) directly into `generateStatementToFile`, which joins it into a local filesystem path without any sanitization.

### Finding Description
In `commands/helpers/artifacts_uploader.go`, `normalizeArgs` only shell-expands `c.Name` [1](#0-0) , and `Execute` forwards this raw value directly as `artifactName` to `generateStatementToFile`, bypassing the `artifactFilename` sanitizer entirely: [2](#0-1) 

In `commands/helpers/artifact_metadata.go`, that unsanitized name is used directly in a `filepath.Join`: [3](#0-2) 

There is no `filepath.Base` call or any other check that the resulting path stays within `opts.artifactsWd`. `filepath.Join` calls `filepath.Clean`, which does resolve `..` segments lexically, so a name such as `../../../../tmp/evil` (or an absolute path via a name that, after `Sprintf`, still contains `/`) causes `file` to resolve outside the intended artifacts working directory. This is the same job-controlled `--name` value (originating from the `artifacts:name` field in `.gitlab-ci.yml`, which can reference CI/CD variables), so a pipeline author fully controls this string.

The `artifactFilename` function itself (used for the archive body name uploaded via HTTP) is correctly hardened by `filepath.Base` [4](#0-3)  — so the traversal does not occur there. The real gap is that the metadata-generation code path re-uses the raw name instead of the sanitized one.

### Impact Explanation
When `GenerateArtifactsMetadata` is enabled (SLSA provenance/attestation generation), the runner writes a JSON metadata file whose path is `filepath.Join(artifactsWd, fmt.Sprintf("%v-metadata.json", artifactName))`. With attacker-controlled `artifactName` containing `../` sequences, the write target can be moved outside the intended artifacts/build directory to any path writable by the job process (subject to OS file permissions), e.g. overwriting or creating files elsewhere in the job's filesystem view. This violates the invariant that "file operations must stay within intended build/cache/artifact roots." The content written is JSON provenance data (not fully attacker-controlled), so this is primarily an out-of-directory file write / potential overwrite rather than arbitrary content injection, but it still breaks the intended artifact namespace boundary.

### Likelihood Explanation
Precondition: the runner/project must have SLSA provenance / artifact metadata generation enabled (`GenerateArtifactsMetadata`), which is a runner/project-level feature flag, not strictly attacker-controlled — but once enabled, the exploit is trivial: any pipeline author can set `artifacts:name: "../../evil"` (optionally using CI variables) in `.gitlab-ci.yml`, requiring no special privileges beyond normal pipeline authoring. This is fully reproducible and deterministic.

### Recommendation
In `generateStatementToFile` (or before calling it in `Execute`), sanitize `opts.artifactName` the same way `artifactFilename` does — e.g., apply `filepath.Base` to `artifactName` before use, and additionally verify the resulting `file` path, after `filepath.Clean`, remains within `opts.artifactsWd` (e.g., via `filepath.Rel` check or comparing against a resolved absolute prefix) before calling `os.WriteFile`.

### Proof of Concept
```go
func TestGenerateStatementToFile_PathTraversal(t *testing.T) {
    g := &artifactStatementGenerator{
        StartedAtRFC3339: time.Now().Format(time.RFC3339),
        EndedAtRFC3339:   time.Now().Format(time.RFC3339),
    }
    tmpWd := t.TempDir()

    file, err := g.generateStatementToFile(generateStatementOptions{
        artifactName: "../../../../tmp/evil",
        files:        map[string]os.FileInfo{},
        artifactsWd:  tmpWd,
        jobID:        1,
    })
    require.NoError(t, err)

    // Assert the resulting file path escapes artifactsWd
    rel, err := filepath.Rel(tmpWd, file)
    require.NoError(t, err)
    assert.True(t, strings.HasPrefix(rel, ".."),
        "expected metadata file to escape artifacts working directory, got %s", file)
}
```
Expected result before fix: assertion passes, confirming the file is written outside `tmpWd`. After applying `filepath.Base`/containment check in `generateStatementToFile`, the file should always remain inside `artifactsWd`, and the assertion should fail (test should be updated to assert containment instead).

func (c *ArtifactsUploaderCommand) artifactFilename(name string, format spec.ArtifactFormat) string {
	name = filepath.Base(name)
	if name == "" || name == "." {
		name = DefaultUploadName
	}

	switch format {
	case spec.ArtifactFormatZip, spec.ArtifactFormatZipZstd:
		return name + ".zip"

	case spec.ArtifactFormatGzip:
		return name + ".gz"

	case spec.ArtifactFormatTarZstd:
		return name + ".tar.zst"
	}
	return name
}
