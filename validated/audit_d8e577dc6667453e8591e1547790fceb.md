### Title
Stale per-epoch instant-withdraw ledger is never cleared on claim, permanently freezing a user's post-default instant claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epochNumber]` [1](#0-0) . If the borrower later defaults in the same epoch, `_claimDefaultedInstantWithdrawRequest` reads that stale per-epoch basis, which is strictly greater than the live aggregate, and the subtraction `instantWithdrawsRequests[_user] -= claimBasis` underflows — permanently reverting every instant-withdraw claim for that user [2](#0-1) .

### Finding Description
- `requestInstantWithdraw` increments both `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` [3](#0-2) .
- On a normal (funded) claim, only the aggregate is zeroed; the per-epoch entry is left behind [1](#0-0) . The only place that clears the per-epoch entry is `_claimDefaultedInstantWithdrawRequest`, and only for `defaultRecoveryEpoch` [4](#0-3) .
- Attack/impact sequence (unprivileged lender, running epoch N):
  1. User requests instant withdraw of X; the strategy funds it, user calls `claimInstantWithdrawRequest` → paid, `instantWithdrawsRequests[user] = 0`, but `instantWithdrawsRequestsByEpoch[user][N] = X` remains.
  2. Still inside epoch N (before `stopEpoch`, i.e. `epochNumber` still N), the user requests a new instant withdraw of Y → `instantWithdrawsRequests[user] = Y`, per-epoch = X + Y.
  3. Borrower defaults and `finalizeDefaultRecovery` runs with `pendingInstantWithdraws != 0`, so `defaultInstantWithdrawsFinalized = true` and `defaultRecoveryEpoch = N` [5](#0-4) .
  4. `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = X + Y` and executes `instantWithdrawsRequests[user] -= X + Y` on a balance of Y → underflow revert. The user's legitimate Y is frozen forever; no alternative path clears the stale entry.
- This is the vault analog of the CVE bug class: epoch-scoped receipt data is not deleted when the receipt is settled ("files not deleted on close"), so a later finalization pass treats already-paid receipts as outstanding.

### Impact Explanation
Permanent freezing of the user's post-default instant-withdraw claim (Y underlyings, arbitrary size). The revert is deterministic and unconditional; the stale `claimBasis` always exceeds the live aggregate by exactly the previously claimed amount X. It also leaves `instantWithdrawClaimsByEpoch[N]` and `pendingInstantWithdraws` inflated for that user's share, though other users' claims are unaffected.

### Likelihood Explanation
Requires the user to claim an instant withdrawal and re-request within the same epoch (possible whenever the instant delay fits inside the epoch duration), followed by a borrower default finalized while `pendingInstantWithdraws != 0` in that epoch. Defaults are rare but this is exactly the scenario the recovery code was built for, and no privileged actor misbehavior is needed — only the honest default/finalize flow.

### Recommendation
In `claimInstantWithdrawRequest`, delete the per-epoch ledger entries when paying a funded claim (e.g. iterate/reset `instantWithdrawsRequestsByEpoch[_user][epochNumber]` for the current epoch, or track the funded portion), and symmetrically reduce `instantWithdrawClaimsByEpoch[epochNumber]` so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` do not count already-paid receipts [6](#0-5) .

### Proof of Concept
Foundry fork PoC (against the existing `IdleCreditVault.t.sol` harness):

```solidity
// epoch N running, instant delay elapsed, strategy funded
// user is a KYC'd AA holder
cdo.requestInstantWithdraw(X, address(aaTranche));      // via IdleCDOEpochVariant
strategy.collectInstantWithdrawFunds(X);                // CDO funds the request
cdo.claimInstantWithdrawRequest();                      // user paid X
assertEq(strategy.instantWithdrawsRequests(user), 0);
assertEq(strategy.instantWithdrawsRequestsByEpoch(user, N), X); // STALE

// same epoch N: user requests again
cdo.requestInstantWithdraw(Y, address(aaTranche));

// borrower defaults; manager finalizes recovery with pendingInstantWithdraws != 0
cdo._handleBorrowerDefault();                           // honest privileged flow
strategy.finalizeDefaultRecovery(recovered, source);    // defaultInstantWithdrawsFinalized = true

// user tries to claim their Y receipt -> permanent revert (underflow)
vm.expectRevert();
cdo.claimInstantWithdrawRequest();
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
