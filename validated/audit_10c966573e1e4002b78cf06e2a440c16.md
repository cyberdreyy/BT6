## Title
Stale rejection weight not cleared on vote-flip lets total_weight_rejected and total_weight_approved double-count the same signer, causing the coordinator to misfire `SignersRejected` on a legitimately-accepted block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener`'s tally of `total_weight_approved` and `total_weight_rejected` is supposed to be a mutually-exclusive accounting of signer weight per block (`aggregated-weight vs verified-accepts` equality). Because the two `BlockResponse` branches guard on two *different* fields (`gathered_signatures` vs `responded_signers`), a signer that first rejects and later accepts the same block (a supported, documented flow) gets its weight counted into *both* tallies simultaneously, breaking the invariant `total_weight_approved + total_weight_rejected <= total_weight` and causing the coordinator's reject-threshold check — which is evaluated before the accept-threshold check — to fire on stale rejection weight even though the block has genuinely reached the real signature threshold.

### Finding Description
In `stackerdb_listener.rs`, the `Rejected` branch increments `total_weight_rejected` guarded on inserting into `responded_signers`: [1](#0-0) 

The `Accepted` branch increments `total_weight_approved` guarded on a *different* field, `gathered_signatures`, and unconditionally also inserts into `responded_signers` afterward: [2](#0-1) 

Sequence for a single signer `X` and a single block hash `H`:
1. `X` sends `Rejected(H)`. `responded_signers.insert(slot_X)` returns `true` (first response) → `total_weight_rejected += weight_X`. `gathered_signatures` still does not contain `slot_X`.
2. The miner re-proposes the same block (or `X` re-evaluates and changes its mind about `H`) and `X` now sends `Accepted(H)`. The accept branch checks `!gathered_signatures.contains_key(slot_X)`, which is still true (rejection never touched `gathered_signatures`), so `total_weight_approved += weight_X` as well.

Now `weight_X` is counted in *both* `total_weight_rejected` and `total_weight_approved` for the same block `H`. The signer software explicitly supports and tests this reject→accept flip for the same block hash: [3](#0-2) 

### Impact Explanation
The coordinator's consensus loop checks the reject condition *before* the accept condition: [4](#0-3) 

With the double-count, `total_weight_rejected` can retain stale weight from a signer that has since switched to accepting, while `total_weight_approved` independently reaches the real 70% threshold from genuinely distinct accepting signers. Because `total_weight_rejected.saturating_add(weight_threshold) > total_weight` is evaluated first, the coordinator can declare the block `SignersRejected` (excluding transactions and forcing a re-mine) even though the block has, in reality, collected sufficient valid distinct-signer signatures to be accepted. This is a liveness wedge on the miner/coordinator's view of consensus caused by the tallies acting on a stale threshold value rather than the current, verified accept state — analogous to the fee-on-transfer report's core issue of an "expected vs. actual" amount mismatch propagating into downstream accounting (deal tokens minted from an un-adjusted amount).

### Likelihood Explanation
No majority collusion is required. A single miner (one slot) re-proposing a block after an initial rejection, combined with one signer's legitimate re-evaluation from reject to accept on the same `signer_signature_hash`, is enough to reproduce the double count — this is exactly the scenario the codebase's own `signer_can_accept_rejected_block` test exercises. The bug is triggered purely by normal, supported protocol behavior (StackerDB gossip of `BlockResponse` messages), with no cryptographic bypass needed.

### Recommendation
Guard both `total_weight_approved` and `total_weight_rejected` increments on the same authoritative per-signer response state (e.g., always check/update `responded_signers` first and record which side a signer's weight was applied to, subtracting/clearing the previous tally when a signer flips its vote for the same block hash), so a signer's weight is only ever counted toward one of `total_weight_approved` / `total_weight_rejected` at a time for a given block.

### Proof of Concept
1. Configure a miner with the coordinator/listener from `stackerdb_listener.rs` and at least 2 signers, weight thresholds such that one signer's weight is enough to flip the calculation (or use the existing `signer_can_accept_rejected_block` test harness in `stacks-node/src/tests/signer/v0/mod.rs`).
2. Have signer `X` send `BlockResponse::Rejected(H)` for a proposed block `H` — `total_weight_rejected` increases by `weight_X`.
3. Re-propose the same block `H` (miner resend, as the existing test does) and have `X` now send `BlockResponse::Accepted(H)` — `total_weight_approved` increases by `weight_X` as well, since `gathered_signatures` never recorded `X`.
4. Have the remaining signers accept normally so that `total_weight_approved` (from genuinely distinct signers) reaches `weight_threshold`.
5. Observe that `total_weight_rejected` (inflated by `X`'s stale rejection) can simultaneously satisfy `total_weight_rejected.saturating_add(weight_threshold) > total_weight` in `signer_coordinator.rs`, causing the coordinator to return `Err(SignersRejected{...})` on the check preceding the accept check, even though the block already has legitimate 70% support.
