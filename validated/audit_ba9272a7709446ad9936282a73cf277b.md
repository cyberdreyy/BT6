### Title
Unbounded per-line buffering in `entrypointLogForwarder.Write` bypasses the job trace `OutputLimit` and grows memory unboundedly - (File: `executors/kubernetes/container_entrypoint_forwarder.go`)

### Summary
`entrypointLogForwarder.Write` accumulates bytes into `lf.buffer` via `append(lf.buffer, rest...)` and only calls `lf.Sink.Write` once a `\n` is found [1](#0-0) . Since `lf.Sink` (the job trace, ultimately backed by `network.trace.go`/`helpers/trace/buffer.go`'s `limitWriter`) is only invoked per completed line, `OutputLimit` enforcement never triggers if a job never emits a line terminator, allowing `lf.buffer` to grow without bound while the process is running.

### Finding Description
`Write` splits `p` into lines and only forwards a line to `lf.Sink.Write` when a `\n` is encountered [1](#0-0) . Any trailing partial line (`rest`) is appended to `lf.buffer` unconditionally with no size cap: `lf.buffer = append(lf.buffer, rest...)` [2](#0-1) .

The actual output-size enforcement mechanism in GitLab Runner is the trace `limitWriter`, which truncates and errors once `written >= limit` [3](#0-2) , configured from `RunnerConfig.OutputLimit` (default 4MB, `common.DefaultTraceOutputLimit`) in `setupLogLimit` [4](#0-3) . That limiter operates on bytes that actually reach the Sink/trace writer. Because `entrypointLogForwarder.writeLine` only calls `lf.Sink.Write` per completed line [5](#0-4) , a job that emits an extremely long single line with no `\n` never reaches the Sink, so the `limitWriter`'s 4MB cap is never consulted for that data — it just keeps accumulating in `lf.buffer` in the runner process's memory.

This is reachable in the Kubernetes executor path where the entrypoint log stream (attached to a step/command container in the "step-runner"/init-container based execution) is piped through `entrypointLogForwarder.Write`, per usage in `executors/kubernetes/kubernetes.go`. An unprivileged pipeline author fully controls job script content and can trivially produce a command that writes megabytes/gigabytes of output with no newline (e.g. `python3 -c "import sys; sys.stdout.write('A'*10**9)"` with output redirected without newlines, or `head -c 1G /dev/urandom | tr -d '\n'`).

### Impact Explanation
Scoped impact: this can grow `lf.buffer` inside the `gitlab-runner` process (not the job's container) without any cap, unlike the trace path, which is capped at `OutputLimit` (default 4MB). Since the runner process can be handling multiple concurrent jobs (`concurrent` setting), one job flooding a single unterminated line can consume unbounded host memory in the runner process, potentially causing OOM and disrupting other concurrently running jobs on the same runner host — a persistent multi-tenant denial-of-service condition consistent with the scoped impact described.

### Likelihood Explanation
Preconditions: this requires the Kubernetes executor with entrypoint log forwarding in use (init container / step-runner log capture path) — feasibility depends on that configuration being active, which is a normal, non-privileged configuration choice, not an admin-only opt-in security control. The attacker only needs control over job script output content, which any pipeline author has. It's fully repeatable and requires no cluster or GitLab admin compromise — one job with a single shell command suffices.

### Recommendation
Enforce a maximum size on `lf.buffer` in `entrypointLogForwarder.Write` (e.g., cap accumulation and forward/flush or truncate once a configurable threshold is exceeded, mirroring the `limitWriter` behavior in `helpers/trace/buffer.go`), so that unterminated lines cannot bypass the trace `OutputLimit`. Alternatively, flush accumulated partial-line bytes to the Sink periodically or once they exceed a fixed cap (e.g., 64KB–1MB) even without a trailing newline, relying on the downstream `limitWriter` to apply the real enforcement.

### Proof of Concept
Go unit test in `executors/kubernetes/container_entrypoint_forwarder_test.go` style:
```go
func TestEntrypointLogForwarder_UnboundedBufferGrowth(t *testing.T) {
    sink := &fakeEntrypointForwarderSink{}
    lf := &entrypointLogForwarder{Sink: sink}

    chunk := bytes.Repeat([]byte("A"), 1<<20) // 1MB, no newline
    for i := 0; i < 500; i++ {                 // simulate 500MB of no-newline output
        n, err := lf.Write(chunk)
        require.NoError(t, err)
        require.Equal(t, len(chunk), n)
    }

    // Assert failure: buffer grows without bound and sink.Write was never called
    assert.Equal(t, 0, sink.writeCallCount, "sink should never receive data because no newline was seen")
    assert.Greater(t, len(lf.buffer), 500*1<<20-1, "lf.buffer grew unbounded, no cap enforced")
}
```
Expected result today: `sink.writeCallCount == 0` and `len(lf.buffer)` equals the full accumulated size (~500MB), demonstrating the buffer is unbounded and the trace `OutputLimit` (whose enforcement lives downstream in `limitWriter`) is never engaged. A fix should assert that `lf.buffer` never exceeds a fixed cap and/or that `sink.Write` is invoked once the cap is reached even without a newline.

func (lf *entrypointLogForwarder) Write(p []byte) (int, error) {
	alreadyWritten := 0

	for i, b := range p {
		if b != '\n' {
			continue
		}

		err := lf.writeLine(append(lf.buffer, p[alreadyWritten:i+1]...))
		lf.buffer = nil
		if err != nil {
			return 0, err
		}

		alreadyWritten = i + 1
	}

	if alreadyWritten < len(p) {
		rest := p[alreadyWritten:]
		lf.buffer = append(lf.buffer, rest...)
	}

	return len(p), nil
}

type limitWriter struct {
	w       io.Writer
	written int64
	limit   int64
}

func (w *limitWriter) Write(p []byte) (int, error) {
	capacity := w.limit - w.written

	if capacity <= 0 {
		return 0, errLogLimitExceeded
	}

	if int64(len(p)) >= capacity {
		p = truncateSafeUTF8(p, capacity)
		n, err := w.w.Write(p)
		if err == nil {
			err = errLogLimitExceeded
		}
		if n < 0 {
			n = 0
		}
		w.written += int64(n)
		w.writeLimitExceededMessage()

		return n, err
	}

	n, err := w.w.Write(p)
	if n < 0 {
		n = 0
	}
	w.written += int64(n)
	return n, err
}
