### Title
`GasLimitUpdate::apply` derives the L2 block gas limit from L1 `SystemConfig` data with no minimum/maximum sanity bound - ([File: crates/common/genesis/src/updates/gas_limit.rs])

### Summary
`GasLimitUpdate`, the type produced from L1 `SystemConfig` `ConfigUpdate(GasLimit)` logs during rollup derivation, applies the decoded `gas_limit` value directly to `SystemConfig.gas_limit` with no lower or upper bound check beyond a `u64::MAX` overflow guard. This value flows unmodified into the L2 block header `gas_limit` field used by both the sequencer/builder and the derivation/validation pipeline.

### Finding Description
`GasLimitUpdate::try_from` decodes the raw `uint256` gas-limit value from the log payload and only rejects values that don't fit in a `u64`: [1](#0-0) 

`GasLimitUpdate::apply` then writes this value straight into `SystemConfig.gas_limit` with no clamping to any protocol-defined minimum or maximum: [2](#0-1) 

This is unlike the sibling EIP-1559 parameter path, which explicitly guards against a zero denominator to avoid division-by-zero / degenerate base-fee computation: [3](#0-2) 

No equivalent guard exists for `gas_limit`. The derived `SystemConfig.gas_limit` is fed into block-building/attribute-generation logic and ultimately becomes the block header's `gas_limit` and the EVM `BlockEnv.gas_limit` (e.g. as seen in `crates/proof/executor/src/builder/env.rs` and `crates/proof/executor/src/builder/assemble.rs`). A unit test confirms that even `gas_limit = 0` is accepted as a valid/matching attribute value with no rejection: [4](#0-3) 

The gas limit is committed on L1 by the `SystemConfig` contract owner and consumed unconditionally by L2 derivation - directly analogous to the reported `maxLockDuration` issue, where a protocol-configurable value lacks the upper/lower bound required by protocol/business rules, and is applied without validation in downstream logic that other code paths (elasticity/denominator) explicitly do validate.

### Impact Explanation
If the `SystemConfig` gas limit is set to `0` or a degenerate small value, the derivation pipeline and block builder pick it up on the L1 origin block that carries the change (per `gas_limit_change_applies_on_adopting_origin_block`), causing the L2 chain to build blocks that cannot include the mandatory deposit transaction or any user transactions, potentially halting the chain or causing derivation to diverge/panic from an inconsistent block env. Conversely, an extremely large value has no upper cap, potentially enabling denial-of-service via oversized blocks/resource exhaustion for the execution/derivation and proof pipelines, since only a `u64::MAX` bound is enforced, not any protocol-sane maximum. This is a node-halt / chain-availability class of impact.

### Likelihood Explanation
The `gas_limit` update log is a value written to L1 through the `SystemConfig` contract, i.e. governed by the chain's system-config admin (owner/operator role), which mirrors the "compromised/careless admin sets unbounded value" scenario in the original report. This isn't reachable by an arbitrary unprivileged L1 transaction sender, but it is reachable through the sanctioned "derivation of attacker-written L1 ... system-config data" analog class, since the derivation and execution code paths apply this value with no bound validation, unlike the neighboring EIP-1559 parameter path which explicitly validates for zero denominators.

### Recommendation
Add explicit validation in `GasLimitUpdate::apply` (or its `TryFrom` construction) to reject or clamp gas-limit values outside a protocol-defined `[MIN_GAS_LIMIT, MAX_GAS_LIMIT]` range, mirroring the zero-denominator guard used for EIP-1559 parameters, so that a misconfigured or malicious `SystemConfig` gas-limit update cannot degrade block production or open a resource-exhaustion vector.

### Proof of Concept
Not independently executed in this analysis; recommend a Devin agent extend `actions/harness/tests/derivation/main.rs::gas_limit_change_applies_on_adopting_origin_block` to enqueue `h.l1.enqueue_gas_limit_update(l1_sys_cfg_addr, 0)` (or `u64::MAX`) and observe the resulting L2 block header/derivation behavior to confirm the absence of bound enforcement, matching the pattern already used by that test file. pub(crate) fn decode_holocene_eip_1559_params_block_header(
    header: &Header,
) -> ExecutorResult<BaseFeeParams> {
    let (elasticity, denominator) = HoloceneExtraData::decode(header.extra_data())?;

    // Check for potential division by zero.
    // In the block header, the denominator is always non-zero.
    // <https://github.com/ethereum-optimism/specs/blob/main/specs/protocol/holocene/exec-engine.md#eip-1559-parameters-in-block-header>
    if denominator == 0 {
        return Err(ExecutorError::InvalidExtraData(Eip1559ValidationError::ZeroDenominator));
    }

    Ok(BaseFeeParams {
        elasticity_multiplier: elasticity.into(),
        max_change_denominator: denominator.into(),
    })
}

/// A `GasLimit` system-config update takes effect on the first L2 block that
/// adopts the L1 origin carrying the change, not a block later.
///
/// With `block_time=2` and L1 `block_time=12`:
/// - L2 blocks 1-5 stay on genesis (epoch 0) and keep the genesis gas limit
/// - L2 block 6 adopts L1 block 1 and must already use the updated gas limit
#[tokio::test]
async fn gas_limit_change_applies_on_adopting_origin_block() {
    const NEW_GAS_LIMIT: u64 = 60_000_000;

    let l1_sys_cfg_addr = Address::repeat_byte(0xCC);
    let batcher_cfg = BatcherConfig::default();
    let rollup_cfg = TestRollupConfigBuilder::base_mainnet(&batcher_cfg)
        .with_l1_system_config_address(l1_sys_cfg_addr)
        .build();
    let genesis_gas_limit = rollup_cfg
        .genesis
        .system_config
        .expect("base mainnet config defines a system config")
        .gas_limit;
    assert_ne!(genesis_gas_limit, NEW_GAS_LIMIT, "test setup must change the gas limit");

    let mut h = ActionTestHarness::new(L1MinerConfig::default(), rollup_cfg);
    h.l1.enqueue_gas_limit_update(l1_sys_cfg_addr, NEW_GAS_LIMIT);
    h.l1.mine_block();

    let l1_chain = SharedL1Chain::from_blocks(h.l1.chain().to_vec());
    let mut sequencer = h.create_l2_sequencer(l1_chain);

    for _ in 1..=5u64 {
        let block = sequencer.build_next_block_with_single_transaction().await;
        assert_eq!(sequencer.head().l1_origin.number, 0, "L2 blocks 1-5 stay on genesis origin");
        assert_eq!(
            block.header.gas_limit, genesis_gas_limit,
            "epoch 0 blocks must keep the genesis gas limit"
        );
    }

    let adopting = sequencer.build_next_block_with_single_transaction().await;
    assert_eq!(sequencer.head().l1_origin.number, 1, "L2 block 6 should adopt L1 origin 1");
    assert_eq!(
        adopting.header.gas_limit, NEW_GAS_LIMIT,
        "the first L2 block that adopts the updated L1 origin must use the new gas limit immediately"
    );
}
