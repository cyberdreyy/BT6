### Title
Write-off requests have no expiry, allowing stale asks to be filled at outdated prices across epochs - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` lets a lender escrow tranche tokens and set a fixed `underlyings` ask, but the request carries no deadline or epoch binding and `fullfillWriteOffRequest` can be invoked at any future time by anyone. An open ask is therefore executable arbitrarily later — after tranche prices have moved, after the epoch in which it was created has ended, and even after loss events — at terms the lender priced under stale conditions. This is the same bug class as the referenced EIP-4337 finding: a signed/recorded intent that remains valid forever and is executed at a worse effective price than the maker intended.

### Finding Description
- `createWriteOffRequest` only requires `isEpochRunning()` at creation and stores `{tranches, underlyings}` in `userRequests` with no timestamp, deadline, or epoch tag (`IdleCreditVaultWriteOffEscrow.sol:86-102`).
- `fullfillWriteOffRequest` performs no freshness check at all: it does not verify the epoch is still running, does not check `block.timestamp` against any expiry, and pays out exactly the stale `currentRequest.underlyings` amount (`IdleCreditVaultWriteOffEscrow.sol:123-151`). It can be called in a later epoch, during a buffer period, or after the tranche's `virtualPrice` has materially changed.
- Tranche tokens are appreciating receipts: AA/BB tranche value accrues interest each epoch via `_updateAccounting`/interest minting in `IdleCDOEpochVariant`, and can also fall via `stopEpochWithDuration(_lossAmount)` or `_handleBorrowerDefault`. An ask fixed at creation-time fair value becomes mispriced the longer it sits.
- While the request is open, the lender's tranches are locked in the escrow and cannot be used for `requestWithdraw`/`claimWithdrawRequest` in `IdleCDOEpochVariant`/`IdleCreditVault`; the lender can only recover them via `deleteWriteOffRequest` — a race the fulfiller can win by filling in the same block the lender's price assumptions break.

Concrete stale-fill path (unprivileged fulfiller):
1. Epoch N starts. Lender escrows `T` tranches asking `U` underlyings, fair at epoch-N prices.
2. Epochs run; tranche price appreciates via accrued interest (or a scheduled loss event is announced). The ask `U` no longer reflects fair value.
3. Fulfiller calls `fullfillWriteOffRequest(lender, T, U)` in a later epoch/buffer, pays the stale `U`, receives `T` tranches now worth `U + delta`.
4. Fulfiller immediately exits via `requestWithdraw`/`claimWithdrawRequest` (or a subsequent epoch claim), capturing `delta`.

The mirror-image harm also exists: after a loss crystallizes, a fulfiller will never fill, so the lender's capital stays locked in escrow while the pool defaults/finalizes, and the lender must actively cancel — nothing bounds how long the stranded position persists.

### Impact Explanation
Direct loss of funds for the lender equal to `T * (price_now - price_at_request)` when tranches appreciate, executed by an unprivileged fulfiller at zero risk (fill only when profitable). Alternatively, indefinite freezing of the lender's escrowed tranches when the ask becomes unfillable after a loss/default, since requests have no automatic expiry. The loss is bounded by the escrowed position size but is fully deterministic for the attacker, who cherry-picks execution timing.

### Likelihood Explanation
Requests are intended to sit open waiting for a borrower/off-chain buyer, so long-lived asks are the normal case, not an edge case. Any epoch where interest accrues (every epoch) makes old asks stale; loss announcements create one-block races the fulfiller always wins. The only mitigation is the lender monitoring and calling `deleteWriteOffRequest`, which is economically irrational to rely on as the sole defense.

### Recommendation
Bind each write-off request to a validity window: store the creation epoch (`IdleCreditVault(strategy).epochNumber()`) and/or a deadline chosen by the lender, and revert in `fullfillWriteOffRequest` if the request is stale (e.g., `block.timestamp > deadline` or `epochNumber != requestEpoch` after the epoch ends). Auto-expire requests when the epoch in which they were created stops, since the "epoch running" precondition that made the ask meaningful no longer holds.

### Proof of Concept
Foundry fork PoC (against the credit-vault deployment used by `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleWriteOffFill() external {
    // setup: AA deposit, epoch 0 running (reuse _startEpochAndCheckPrices harness)
    uint256 amount = 100_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // lender escrows tranches, asks fair value at epoch-0 price
    address lender = makeAddr('lender');
    IdleCDOTranche(AAtranche).transfer(lender, mintedAA / 2);
    uint256 price0 = cdoEpoch.virtualPrice(AAtranche);
    uint256 ask = (mintedAA / 2) * price0 / ONE_TRANCHE;
    vm.startPrank(lender);
    IdleCDOTranche(AAtranche).approve(address(escrowAA), mintedAA / 2);
    escrowAA.createWriteOffRequest(mintedAA / 2, ask);
    vm.stopPrank();

    // time passes: stop epoch, accrue interest, run more epochs — request stays fillable
    _stopEpochAndCheckPrices(0, apr, expectedFunds);
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, apr, expectedFunds);

    uint256 price1 = cdoEpoch.virtualPrice(AAtranche);
    uint256 fairNow = (mintedAA / 2) * price1 / ONE_TRANCHE;
    assertGt(fairNow, ask); // stale ask is below fair value

    // fulfiller fills in a later buffer period — no epoch/expiry check stops it
    address fulfiller = makeAddr('fulfiller');
    deal(address(underlying), fulfiller, ask);
    vm.startPrank(fulfiller);
    underlying.approve(address(escrowAA), ask);
    escrowAA.fullfillWriteOffRequest(lender, mintedAA / 2, ask);
    vm.stopPrank();

    // fulfiller exits at current (higher) price; lender received stale `ask`
    assertApproxEqAbs(
        IdleCDOTranche(AAtranche).balanceOf(fulfiller) * price1 / ONE_TRANCHE,
        fairNow, 1);
    // lender loss == fairNow - ask
}
```

Caveat: the index did not expose every line of `IdleCDOEpochVariant.requestWithdraw`/`_calcInterestWithdrawRequest`, so the PoC reuses the established epoch harness (`_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `virtualPrice`) visible in `test/foundry/IdleCreditVault.t.sol` rather than re-deriving withdraw internals. The escrow-side behavior — no deadline, no epoch binding, permissionless fulfillment — is fully verified from `IdleCreditVaultWriteOffEscrow.sol`.
