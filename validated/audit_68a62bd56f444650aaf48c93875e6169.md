### Title
Signer weight double-counted across accept and reject tallies in miner's `StackerDBListener` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` aggregates `BlockResponse` messages from signers into two running weight totals — `total_weight_approved` and `total_weight_rejected` — that drive the local decision of whether to broadcast a block (threshold reached) or abandon it (rejection makes 70% impossible). The gating logic that prevents a signer's weight from being counted twice is inconsistent between the two code paths, so a single signer that sends a `Rejected` response followed later by an `Accepted` response for the *same* block has its weight counted into **both** totals, i.e. a rejection is effectively recounted as an accept in the coordinator's tally.

### Finding Description
In `handle_signer_messages` (the message loop in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`):

- On `BlockResponse::Accepted`, weight is added to `total_weight_approved` gated on `!block.gathered_signatures.contains_key(&slot_id)`, after which `gathered_signatures` and `responded_signers` are both unconditionally updated: [1](#0-0) 

- On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` gated on `block.responded_signers.insert(slot_id)` (i.e., only the *first* time this slot appears in `responded_signers`, coming from either code path): [2](#0-1) 

The two paths use *different* de-duplication keys:
- Accept path's gate is `gathered_signatures` (a map populated only by Accept messages).
- Reject path's gate is the shared `responded_signers` set (populated by both Accept and Reject).

If a signer's Reject message for a given block is processed first, `responded_signers.insert(slot_id)` succeeds and `total_weight_rejected` is incremented, and the slot is added to `responded_signers`. If that same signer later sends an Accept for the same block (e.g. through re-evaluation after a previously stale rejection, or via a duplicitous/byzantine signer deliberately sending both), the Accept path checks `gathered_signatures.contains_key(&slot_id)` — which is still empty for this slot because it was never touched by the Accept branch — so the check passes and `total_weight_approved` is incremented as well. The signer's weight is now counted in both `total_weight_rejected` and `total_weight_approved` simultaneously for the same block.

(The reverse order — Accept then Reject — is correctly protected, because the Reject path's gate, `responded_signers`, was already populated by the Accept path, so the second weight add is skipped. Only the Reject-then-Accept ordering is vulnerable.)

### Impact Explanation
`total_weight_approved` and `total_weight_rejected` are the values used to wake waiting threads via `cvar.notify_all()` for two mutually exclusive outcomes: "enough approvals to push the block" and "enough rejections to consider the block dead" (the second check is visible immediately below the reject-handling block: rejection weight plus threshold exceeding total weight triggers notification). Because a single signer's weight can be counted into both totals, the coordinator's local aggregate can simultaneously claim the block is both on track to reach 70% approval and already doomed by >30% rejection — an internally inconsistent, corrupted tally. This falls squarely into the "a rejection recounted as an accept" analog: a genuinely-issued rejection from a signer is later re-applied toward the acceptance total for the same block, inflating the approved weight beyond what distinct signer weight actually supports. This can cause the coordinator to believe the acceptance threshold has been met (and attempt to push a block) based on partly phantom weight, contributed by a single acting signer rather than requiring a majority.

Note: this is a local decision-making bug in the miner's `StackerDBListener`/coordinator aggregation logic, not in the on-chain `verify_signer_signatures` check performed by receiving nodes (`stackslib/src/chainstate/nakamoto/mod.rs`), which independently recomputes signer weight from the actual signature set. I was not able to fully trace, within the remaining budget, the exact downstream code that consumes `total_weight_approved` to decide when to assemble and broadcast the final block (only the `cvar.notify_all()` trigger was inspected), so I cannot confirm with certainty whether this inflated tally alone can cause the miner to broadcast a block whose actually-gathered signature weight (`gathered_signatures`) is below the true 70% threshold, or whether the broadcast path independently re-verifies weight from `gathered_signatures` before pushing. This limits the finding to a demonstrated tally-corruption bug with a plausible, but not fully confirmed, liveness/premature-broadcast consequence.

### Likelihood Explanation
Triggering the root cause requires only a single signer (potentially even without malicious intent, through the documented re-evaluation flow where a signer that previously rejected can later come to accept the same block once the reason for rejection is no longer applicable) to emit a Reject followed by an Accept for the same `signer_signature_hash`. No majority, no other signer's key, and no auth token is required — a lone signer (or a lone byzantine actor controlling one signer's key) can trigger this ordering deterministically by crafting/replaying its own two `BlockResponse` messages.

### Recommendation
Use a single, unified de-duplication mechanism for weight accounting across both Accept and Reject paths — e.g., gate weight increments in both branches on `responded_signers.insert(slot_id)` (or track, per slot id, the specific verdict already counted and only allow weight migration between totals if the previous verdict is explicitly retracted, rather than allowing both to be counted).

### Proof of Concept
1. A single signer with weight `W` sends a valid `BlockResponse::Rejected` for `signer_signature_hash = H`.
   - In `handle_signer_messages`, `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += W`.
2. The same signer later sends a valid `BlockResponse::Accepted` for the same `H` (e.g., a legitimate re-evaluation, or the signer simply re-broadcasting via StackerDB).
   - `gathered_signatures.contains_key(&slot_id)` is `false` (nothing in the accept path has touched this slot yet) → `total_weight_approved += W`.
3. Now both `total_weight_rejected` and `total_weight_approved` include `W` for the same signer on block `H`, even though only one verdict from this signer should count toward the coordinator's decision logic. [1](#0-0) [3](#0-2)
