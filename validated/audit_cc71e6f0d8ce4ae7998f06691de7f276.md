Confirmed: the vault gateway handler namespaces `activeRequests` keys with an owner-derived prefix (`authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID`) before ever inserting into the map [1](#0-0) , so two different callers cannot collide on the same map key. The confidential-relay handler has no equivalent namespacing step — `HandleJSONRPCUserMessage` inserts directly on the raw, caller-supplied `req.ID` [2](#0-1) , and `newActiveRequest` treats a repeated ID as fatal for the *newer* caller rather than the attacker [3](#0-2) .

### Title
Unprivileged clients can DoS other users' confidential-relay gateway requests via request-ID collision - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

### Summary
The APWine bug is a class of vulnerability where a shared, non-namespaced counter/keyspace that different unprivileged actors can write to is used to gate processing for all participants, letting one attacker's cheap contribution block a legitimate participant's outcome. The `ConfidentialRelay` gateway handler exhibits the same class: it keys in-flight requests by the caller-supplied JSON-RPC `req.ID` with no per-caller/session namespacing, unlike the sibling `vault` handler which explicitly prefixes the ID with the authorized owner before using it as a map key.

### Finding Description
`gateway.ProcessRequest` decodes an untrusted, internet-facing JSON-RPC request and dispatches it to the appropriate handler based on `DonId`/service name [4](#0-3) . For the `confidentialrelay` handler, `HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and under 200 characters, with no authentication or ownership check on the ID itself, before calling `newActiveRequest` [2](#0-1) .

`newActiveRequest` stores the request in a single handler-wide map keyed directly by the raw `req.ID`: [3](#0-2) 

If a request with that exact ID is already active, the call fails with `"request ID already exists: " + req.ID"` for whichever request is processed second — there is no distinction between "my own retried request" and "someone else's request with the same ID." This mirrors the APWine root cause precisely: a shared resource (the FYT balance / here, the `activeRequests[ID]` slot) that is consumed on a first-come basis by mutually distrusting parties, where the code assumes IDs are effectively private to a caller but never enforces that assumption.

By contrast, the `vault` gateway handler pipeline explicitly derives a collision-safe key by prefixing the authorized owner onto the request ID (`prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID`) before it is ever used to track in-flight state [5](#0-4) , and the handler's own test suite documents that a duplicate ID from the *same* owner is expected to hit the replay guard as an intentional safety mechanism [6](#0-5) . The confidential-relay handler has no such owner binding anywhere in its request path.

### Impact Explanation
Any unauthenticated caller reaching the gateway's confidential-relay endpoint can pick a request ID and, by racing or repeatedly resubmitting it, deny a legitimate caller who happens to use (or is predicted/observed to use) the same or a sequential/predictable ID. Because the map entry lives until `requestTimeout` (default 30s) expires or is answered [7](#0-6) , an attacker can keep re-submitting that ID indefinitely to keep the slot occupied, causing the victim's genuine request to be rejected outright (`HandleJSONRPCUserMessage` returns an error rather than being queued/serialized), i.e., a sustained per-request denial-of-service for cross-user confidential relay calls. This is a cross-user request-blocking/DoS analog of the "permanent freezing" bug class: a cheap, repeatable action by one unprivileged party degrades outcomes for another unrelated party sharing the same resource keyspace.

### Likelihood Explanation
Exploitability depends on how request IDs are generated by legitimate clients of this endpoint. If IDs are client-chosen or predictable (sequential counters, workflow-execution IDs, hashes of public inputs), collision is trivial and cheap to trigger repeatedly, similar to the wei-cost griefing in the original report. If IDs are always high-entropy random values chosen by a trusted intermediary before reaching this handler, exploitability is lower. This determination could not be fully verified: the actual ID-generation path used by production callers of this handler (versus other gateway handlers like `vault` that add explicit namespacing) was not found in the indexed portion of the codebase.

### Recommendation
Namespace `activeRequests` keys by an authenticated caller identity (e.g., prefix with an authorized owner/session identifier, similar to the vault handler's `authorizedOwner + RequestIDSeparator + originalRequestID` pattern) before inserting into `h.activeRequests`, so that request IDs are only unique within a caller's own scope and cannot be used to block another caller's request.

### Proof of Concept
1. Attacker sends a `confidentialrelay` JSON-RPC request to the gateway's public endpoint with `ID: "X"` and any valid `MethodCapabilityExec`/`MethodSecretsGet` params, causing `newActiveRequest` to insert `activeRequests["X"]`.
2. Before that entry is cleared (via response completion or the up-to-30s timeout), a legitimate user submits a genuine request that happens to also carry `ID: "X"`.
3. The victim's `newActiveRequest` call hits the existing-ID check and returns `"request ID already exists: X"` [8](#0-7) , so `HandleJSONRPCUserMessage` errors out and the gateway returns a `HandlerError` to the victim instead of processing their request [9](#0-8) .
4. The attacker repeats step 1 continuously (at negligible cost, no authentication required) to keep the slot occupied for ID `"X"` indefinitely, denying that specific request identifier to legitimate use.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {

		return errors.New("request ID cannot be empty")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
