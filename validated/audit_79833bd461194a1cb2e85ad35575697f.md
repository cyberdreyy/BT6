### Title
JWT replay-guard race condition allows multiple authorized executions from a single-use token - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The `jwtReplayCache` used to enforce "single-use" JWTs in `WorkflowMetadataHandler.Authorize` performs the replay check (`isReplay`) and the replay record (`recordUsage`) as two separate, non-atomic critical sections guarded by different lock acquisitions. This is the same bug class as the reported "multiple redemptions" issue: the resource (the JWT / authorization) is not marked as "consumed" atomically with the check that gates its use, so concurrent requests can both pass the check before either records usage.

### Finding Description
`Authorize` first calls `h.jwtCache.isReplay(claims.ID)` under an `RLock`, and only after passing several more checks (workflow lookup, signer authorization) does it call `h.jwtCache.recordUsage(claims.ID)` under a separate `Lock`, as shown at [2](#0-1) . Because these are two distinct, unsynchronized operations, an unprivileged client can send two (or more) HTTP trigger requests bearing the *same* signed JWT concurrently. Both goroutines can call `isReplay` before either calls `recordUsage`, so both pass the "not yet used" check and both proceed to be treated as authorized, single-use requests — defeating the single-use guarantee the cache is meant to provide.

This is directly analogous to the reported `redeemObligation` bug: the state that should mark the resource as "already consumed" is updated too late (or without atomicity), enabling multiple uses of what should be a one-time-use credential. Note this is distinct from the correctly-implemented `RequestReplayGuard` used by the Vault gateway path (`core/capabilities/vault/request_replay_guard.go`), which performs check-and-record atomically under a single mutex via `CheckAndRecord`, as demonstrated by `core/capabilities/vault/request_replay_guard_test.go:96-126` (`TestRequestReplayGuard_ConcurrentAccess`) proving exactly-once semantics under concurrency. The `jwtReplayCache` in `workflow_metadata_handler.go` has no equivalent atomic check-and-record primitive or concurrency test. [3](#0-2) 

### Impact Explanation
An attacker (an unprivileged HTTP trigger client of the Gateway) who obtains one valid signed JWT for a workflow request can, by racing two concurrent requests with distinct request IDs (or by exploiting timing on retries) but same JWT (`jti`), potentially get `Authorize` to succeed twice for a JWT intended for single use. Since `Authorize` gates whether a request is treated as coming from an authorized signer for a given workflow, a successful bypass results in duplicate/unauthorized workflow executions being dispatched to the DON under the same authorization credential — i.e., unauthorized job/workflow execution beyond what the signer intended, and potential resource-exhaustion / duplicate side effects for the target workflow.

### Likelihood Explanation
Exploitation requires precise timing to win the race window between the `isReplay` read and the `recordUsage` write (which is short, but plausible over a fast local network to the gateway, especially since the window includes an extra JSON/lookup pass). It also requires an already-valid signed JWT, so it does not bypass authentication itself — only the "single-use" guarantee. Likelihood is moderate: this is a genuine TOCTOU race in security-sensitive replay-prevention code reachable from unprivileged client requests, but it needs concurrent request timing to trigger reliably.

### Recommendation
Make check-and-record atomic, mirroring the `RequestReplayGuard.CheckAndRecord` pattern already used for Vault: combine the `isReplay` check and the `recordUsage` write into a single critical section under one `Lock()` (not `RLock`/`Lock` split), returning "already used" immediately if the `jti` is present, and only inserting it if absent — all while holding the same lock, before subsequent authorization checks are considered final.

### Proof of Concept
1. Obtain (or generate) one valid signed JWT for a workflow request (`token`, `jti`) satisfying `Authorize`'s signer/workflow checks.
2. Fire two concurrent `HandleUserTriggerRequest` calls (e.g. via two goroutines / two rapid HTTP calls to the gateway) using the same JWT but different `id` fields to avoid the unrelated `setupCallback` requestID dedup at [4](#0-3) .
3. Both calls reach `WorkflowMetadataHandler.Authorize` concurrently; both call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`.
4. Both requests are authorized and dispatched to the DON, demonstrating that the "already been used" single-use protection can be bypassed under concurrency, unlike the vault path's `RequestReplayGuard.CheckAndRecord`, which is proven single-success under identical concurrent load in `TestRequestReplayGuard_ConcurrentAccess`.

func (cache *jwtReplayCache) isReplay(jti string) bool {
