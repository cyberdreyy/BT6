### Title
External Initiator credentials assume full `UserRoleRun` and can trigger `POST /v2/jobs/:ID/runs` for arbitrary jobs, bypassing the "EIs not allowed" restriction - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` sets the session's `SessionUserKey` to a full `clsessions.User{Role: clsessions.UserRoleRun}` object identical to what real logged-in users get. `PipelineRunsController.Create` gates its integer-job-ID run path with `_, isUser := auth.GetAuthenticatedUser(c)`, intending (per its own comment "only users are allowed to run jobs using int IDs - EIs not allowed") to exclude external-initiator sessions — but `GetAuthenticatedUser` cannot distinguish an EI-derived pseudo-user from a real user, so `isUser` is `true` for EI credentials too, letting any authenticated EI (with zero bound jobs) call `RunJobV2` for any job ID on the node.

### Finding Description
The `userOrEI` route group in `core/web/router.go` mounts only two endpoints behind `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)`: `GET /v2/ping` and `POST /v2/jobs/:ID/runs` (wrapped by `auth.RequiresRunRole`) [1](#0-0) .

When a request authenticates via EI credentials, `AuthenticateExternalInitiator` sets both the EI session key and a synthetic user object with `UserRoleRun`: [2](#0-1) 

`auth.RequiresRunRole` only rejects `UserRoleView`, so this synthetic EI "user" passes: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code explicitly comments that EIs should not be allowed to trigger runs by integer job ID, but its check for "is this a user" is `auth.GetAuthenticatedUser(c)`, which returns `true` for the EI-derived pseudo-user set above — it does not call `auth.GetAuthenticatedExternalInitiator` to exclude EI sessions, nor does it check that the job ID is bound to the authenticating EI: [4](#0-3) 

As a result, an EI credential with zero bound jobs can call `POST /v2/jobs/<any-int-ID>/runs` and have `App.RunJobV2` execute that job's pipeline — a job it has no legitimate relationship to, violating the least-privilege invariant that EI credentials are scoped only to their bound job(s).

`/v2/ping` itself (`PingController.Show`) returns only a static `{"message":"pong"}` and exposes no privileged data or state [5](#0-4) , so it is not independently sensitive; the actionable escalation is entirely through the second `userOrEI` route.

**Mitigating factor:** `ChainlinkApplication.RunJobV2` is gated by a build-mode check that blocks the entire code path in production/secure builds: [6](#0-5) 
The `Application` interface itself documents `RunJobV2` as "Testing only" [7](#0-6) . In `build.IsProd()` builds (the production/secure release configuration), any call — from a legitimate user or an unrelated EI — returns `"manual job runs not supported on secure builds"` before any job lookup occurs, neutralizing the exploit in production deployments.

### Impact Explanation
In non-production/dev builds (`build.IsProd() == false`), an attacker holding valid but unrelated EI credentials (with no bound jobs) can trigger execution of any job on the node by integer ID via `POST /v2/jobs/:ID/runs`, matching the bounty impact class of "unauthorized job run" / authorization bypass across job ownership boundaries. In production/secure builds this specific action path is blocked by the `build.IsProd()` guard in `RunJobV2`, substantially limiting real-world impact to non-production deployments and test/dev nodes. The `/v2/ping` route itself carries no exploitable impact.

### Likelihood Explanation
Preconditions: attacker needs only a valid (even entirely unrelated) External Initiator access key/secret pair — the lowest-privilege credential type in the system — and the target node must be running in a non-`IsProd()` build. No admin/operator access is required. The request is a single unauthenticated-relative-to-target-job HTTP POST with EI headers; fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests where `auth.GetAuthenticatedExternalInitiator(c)` returns an EI (rather than relying on the ambiguous `GetAuthenticatedUser` check), so EI sessions can never reach the integer-job-ID run path. Additionally, consider giving EI-derived sessions a distinct role/type from `clsessions.User` so downstream handlers cannot conflate EI-run authorization with full user "run" role, and ensure ownership/binding checks (job ↔ EI) are enforced anywhere an EI is permitted to trigger a run.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/router_test.go` / `core/web/pipeline_runs_controller_test.go` patterns):
1. Build app with a non-prod build tag (or mock `build.IsProd()` to false), create Job A (any runnable job type) and a separate `ExternalInitiator` EI-X via `bridges.NewExternalInitiator` + `BridgeORM().CreateExternalInitiator`, without binding EI-X to Job A.
2. Send `POST /v2/jobs/<JobA.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-X's credentials.
3. Assert response is `200 OK` with a `pipelineRun` resource for Job A (demonstrating unauthorized run of an unrelated job), and assert `App.JobORM()`/`PipelineORM()` show a new run for Job A was inserted.
4. Send `GET /v2/ping` with the same EI-X headers and assert it also succeeds (expected/benign), confirming the `userOrEI` group's only two routes are `/ping` (benign) and `/jobs/:ID/runs` (vulnerable).
5. Repeat step 2 with `build.IsProd()` forced true and assert `500`/error response containing "manual job runs not supported on secure builds", confirming the production mitigation.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
