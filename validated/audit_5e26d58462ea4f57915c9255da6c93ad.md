### Title
Builder Withdrawal Commits Full Requested Amount to Execution Layer While Only Deducting Capped Balance on Consensus Layer — Gwei Created - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas fork, `get_builder_withdrawals` builds `Withdrawal` objects for builder payouts using the full, uncapped requested amount from `state.builder_pending_withdrawals`, while `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from the corresponding builder's CL-side balance. Since the resulting `Withdrawal` list becomes `state.payload_expected_withdrawals`, which "any execution payload that has the corresponding block as parent beacon block is required to honor... in the execution layer," the EL will credit the fee recipient the full requested amount even when the CL only removed a smaller (capped) amount from the builder's balance. This mints Gwei that was never backed by any validator/builder balance.

### Finding Description
`get_builder_withdrawals` constructs the `Withdrawal` with the raw, unclamped amount: [1](#0-0) 

`apply_withdrawals`, however, deducts only the capped amount from the builder's stored balance: [2](#0-1) 

These two functions must be kept in agreement to preserve the invariant that "Gwei paid out equals Gwei deducted." They are not: whenever `builder.balance < withdrawal.amount`, the `Withdrawal` object commits the EL to pay `withdrawal.amount` to `fee_recipient`, but the CL state only loses `builder.balance` (capped) Gwei. The spec's own documentation on `process_withdrawals` explicitly states that withdrawal deductions are "applied immediately via `apply_withdrawals`" and that the EL "is required to honor these withdrawals," meaning the EL will mint the committed `withdrawal.amount` regardless of what the CL actually removed: [3](#0-2) 

This is corroborated by the existing test suite, which explicitly documents and asserts this exact behavior as intended: [4](#0-3) 

In this test, a builder with only 1 ETH balance has a pending withdrawal request for 5 ETH. The output `Withdrawal.amount` remains 5 ETH (the requested amount), while `builders[0].balance` decreases only by 1 ETH (capped). The 4 ETH difference is never deducted from any account in the consensus state, yet it is committed for payout to `fee_recipient` on the execution layer, which the analogous documentation confirms is honored unconditionally by the EL. This breaks the fundamental equality that every Gwei paid out via a `Withdrawal` must correspond to a Gwei removed from consensus-layer state.

Entries in `builder_pending_withdrawals` (e.g. `amount=parent_bid.value` in `apply_parent_execution_payload`) are protocol-derived at settlement time from the committed bid value, but the builder's balance can independently be reduced between bid settlement and withdrawal-sweep processing (e.g., by other builder-initiated withdrawals or additional payment settlements queued for the same builder before this one is processed), producing exactly the insufficient-balance scenario the tests exercise. `fee_recipient` is attacker-controllable (it is the fee recipient specified in the block builder's own bid), so the excess minted Gwei is paid to an address of the builder's/attacker's choosing.

### Impact Explanation
This is a Critical-class issue under the "Gwei created" criterion: consensus-layer state and execution-layer state diverge on total supply, with real ETH minted at `fee_recipient` that was never backed by any balance decrease in the beacon state. This is not a loss confined to the attacker's own stake — it manufactures new, unbacked ETH payable to an address the block builder controls.

### Likelihood Explanation
The condition is deterministic and requires only that a builder's registered balance be lower than the sum of amounts in its outstanding `builder_pending_withdrawals`/settled payments at the time the withdrawal sweep runs — a state reachable by a builder that simply requests exits/withdrawals in excess of its remaining balance, or by balance depletion via concurrent withdrawal processing before the sweep executes. No coalition, external client bug, or malicious peer is required — a single builder can trigger this via ordinary protocol-defined message flow.

### Recommendation
`get_builder_withdrawals` should clamp the `Withdrawal.amount` to `min(withdrawal.amount, state.builders[builder_index].balance)` at the point the `Withdrawal` object is constructed (mirroring the cap already applied in `apply_withdrawals`), so the amount the EL is committed to pay always matches the amount actually deducted from CL state.

### Proof of Concept
1. Register a builder with balance = 1 ETH.
2. Queue a `BuilderPendingWithdrawal` for that builder with `amount = 5 ETH` (achievable once outstanding builder payment/withdrawal requests exceed remaining balance).
3. Call `get_expected_withdrawals`/`process_withdrawals`. `get_builder_withdrawals` emits `Withdrawal(amount=5 ETH, address=fee_recipient)`.
4. `apply_withdrawals` reduces `builders[0].balance` from 1 ETH to 0 (only 1 ETH actually deducted).
5. `state.payload_expected_withdrawals` — which the EL is required to honor — still lists a 5 ETH withdrawal to `fee_recipient`, so the EL credits 5 ETH while the CL only removed 1 ETH: 4 ETH created out of nothing. This exact scenario is reproduced by the existing spec test: [5](#0-4)

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
