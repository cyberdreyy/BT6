### Title
Raw DB error text disclosed to unauthenticated external-initiator requests via `errors.Wrap` + `jsonAPIError` - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` wraps any non-`sql.ErrNoRows` error from `FindExternalInitiator` with `errors.Wrap(err, "finding external initiator")` and returns it up through the `Authenticate` middleware, which passes it unmodified to `jsonAPIError`. Because `jsonAPIError` falls back to embedding `err.Error()` directly in the JSON response when the error isn't a `*models.JSONAPIErrors`, any underlying database driver error text (potentially including query fragments, constraint names, or connection details) is returned verbatim to an unauthenticated caller.

### Finding Description
An attacker sends a request to any external-initiator-authenticated route with the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (`static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`). `AuthenticateExternalInitiator` calls `store.FindExternalInitiator(ctx, eia)`. If that call returns any error other than `sql.ErrNoRows`, the code does `return errors.Wrap(err, "finding external initiator")`, preserving the original driver/SQL error message inside the wrapped error's `.Error()` string. `Authenticate` middleware treats any non-`auth.ErrorAuthFailed` error as terminal (`break`) and calls `jsonAPIError(c, http.StatusUnauthorized, err)`. In `jsonAPIError`, since the wrapped error is a `*errors.withMessage`/`*errors.fundamental` type from `github.com/pkg/errors`, not `*models.JSONAPIErrors`, the `errors.As` check fails, and the handler falls through to `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))`, embedding the full wrapped error string — including the raw underlying DB error — into the HTTP response body served to the requester.

### Impact Explanation
This is an information-disclosure issue: it can leak internal implementation details such as SQL driver error text (e.g., `pq: ...` messages, malformed query fragments, connection-pool errors) to an unauthenticated caller, which could aid further attacks (e.g., inferring schema or driver info) but does not directly grant authentication bypass, key/secret disclosure, privilege escalation, or fund movement. It maps at most to a low-severity "informational disclosure" class, well below authentication bypass or credential exposure impact tiers, since triggering a non-`ErrNoRows` DB error condition on this query is itself an unusual/degraded-service precondition (e.g., DB connectivity issue, statement timeout) rather than something reliably triggerable by a normal malformed-header request in a healthy running node.

### Likelihood Explanation
Exploitability requires the underlying database to actually return an error other than "no rows" for the `FindExternalInitiator` query (e.g., a transient connection failure, timeout, or an actual driver-level fault) — this is not reliably attacker-triggerable through a well-formed or malformed `AccessKey`/`Secret` header alone in a healthy node, since a mismatched/nonexistent access key normally results in `sql.ErrNoRows`, which is explicitly handled and converted to the generic `auth.ErrorAuthFailed`. Thus the leak path is real but conditional on an underlying DB fault, making it low likelihood under normal operating conditions and not something a remote unprivileged attacker can force on demand without an existing DB instability.

### Recommendation
Do not propagate raw wrapped DB errors to the HTTP layer. In `AuthenticateExternalInitiator`, log the wrapped error server-side (with full detail) and return a generic sentinel error (e.g., a new internal error or the same `auth.ErrorAuthFailed`/a distinct "internal error" constant) to the middleware, so `jsonAPIError` only ever serializes a fixed, non-sensitive message for non-`ErrNoRows` failures.

### Proof of Concept
1. In `core/web/auth/auth_test.go` (or new test file), implement a mock `Authenticator` whose `FindExternalInitiator` returns a wrapped generic driver error, e.g. `errors.New("pq: relation \"external_initiators\" constraint violation on secret_column")`.
2. Build a `gin.Context` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to arbitrary values, invoke `Authenticate(mockAuthr, AuthenticateExternalInitiator)`.
3. Assert HTTP status is 401 and inspect the response body JSON (`models.JSONAPIErrors`), asserting the error detail field equals the exact expected constant/generic message and does NOT contain substrings `"pq:"`, `"constraint"`, `"relation"`, or the literal injected DB error text.
4. Currently this test would fail (body contains the injected DB error string), confirming the leak; after applying the recommended fix (replacing the wrapped error with a generic sentinel before returning), the test should pass.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
