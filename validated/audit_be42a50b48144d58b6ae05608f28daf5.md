### Title
Global (non-namespaced) request-ID uniqueness check in the Vault/Confidential-Relay gateway handlers lets any authorized user block another user's in-flight request - (File: `core/services/gateway/handlers/vault/handler.go`)

### Summary
The reported Ion-Protocol bug class is: an unprivileged actor can permanently or repeatedly block a legitimate operation at trivial cost by front-running it with a minimal, self-serving transaction that occupies a shared resource (here, `repayBadDebt` accepting 1 wei to make `liquidate` revert). The analogous pattern in the Chainlink gateway handlers is a **globally shared, client-chosen `req.ID` namespace** used to track in-flight requests: any caller who can pass their own authorization can pick the same `req.ID` as another (unrelated) caller's pending request and cause that caller's legitimate request to be rejected, at essentially zero cost, repeatable indefinitely.

### Finding Description
In the Vault gateway handler, `HandleJSONRPCUserMessage` validates the caller's own authorization (`h.requestProcessor.ProcessRequest`) and then calls `h.newActiveRequest(req, callback)`: [1](#0-0) 

`newActiveRequest` stores the request keyed **only by `req.ID`**, in a single map shared across all users of the gateway: [2](#0-1) 

Crucially, authorization (`ProcessRequest`) verifies that the caller is entitled to act on their own owner/secrets, but it does not tie the `req.ID` key to the authorized owner. Any two distinct, individually-authorized callers can collide on the same `req.ID` string, since the map has no per-owner or per-sender namespace: [3](#0-2) 

The unit test confirms the exact behavior — a second, unrelated caller reusing the same `req.ID` as an in-flight request is rejected with "request was already authorized previously" / "request ID already exists," which is the mechanism an attacker can weaponize to deny a specific victim's request: [4](#0-3) 

The identical pattern (global `req.ID` uniqueness check, unscoped by sender) exists in the Confidential Relay gateway handler: [5](#0-4) 

Because request IDs are client-supplied strings (up to 200 characters, no format requirement beyond non-empty) and many SDKs/clients use simple/sequential/predictable IDs (e.g., `"1"`, `"req-dup"` as seen in the tests), an attacker only needs to guess or observe a victim's `req.ID` scheme and race a trivial self-authorized request with the same ID to occupy the slot before the legitimate request lands.

### Impact Explanation
An unprivileged (but self-authorized) client can perform a denial-of-service against another specific user's Vault or Confidential Relay request by squatting on that user's `req.ID` value. The victim's legitimate secrets operation (create/update/delete/list) or capability execution is rejected outright ("request ID already exists"/"in-flight request") until the colliding entry expires and is cleaned up, and the attack can be repeated indefinitely for negligible cost (a single small JSON-RPC request that only needs to pass the attacker's own authorization, not the victim's). This mirrors the reported bug class of blocking a legitimate, time-sensitive operation via a trivial competing action that only needs to occupy a shared identifier/slot.

### Likelihood Explanation
Likelihood is limited by the need to predict or observe the victim's `req.ID` in advance and to win a race to submit before the victim. This is plausible when clients use deterministic/sequential/short IDs (the codebase's own tests use IDs like `"1"`), or when an attacker can observe pending request IDs through other channels. The attack requires no privileged access — only the ability to submit a normally-authorized request for the attacker's own resources.

### Recommendation
Scope the `activeRequests` map key by both the authorized owner/sender identity and the client-supplied `req.ID` (e.g., `authorizedOwner + separator + req.ID`), rather than by the bare client-chosen `req.ID` alone, so that request-ID collisions can only occur within a single authorized identity's own request stream, not across unrelated users. Apply the same fix to the Confidential Relay handler's `activeRequests`/`req.ID` uniqueness check.

### Proof of Concept
1. Victim (owner A) submits a Vault request with `req.ID = "42"` for `MethodSecretsList` (or any supported method) — the gateway stores it in `activeRequests["42"]`.
2. Attacker (owner B, unrelated, but able to authorize their own request) submits any request they are authorized for (e.g., their own `MethodSecretsList`) using the same `req.ID = "42"` before A's request completes.
3. Whichever request loses the race receives the "request ID already exists"/"request was already authorized previously" error and is dropped — demonstrated directly by the existing test `TestVaultHandler_HandleJSONRPCUserMessage/"unhappy path - duplicate requestId"`, which shows the second call with the same `req.ID` failing regardless of the underlying owner: [6](#0-5) 
4. Attacker repeats step 2 with fresh IDs whenever their occupied slot expires, sustaining the denial-of-service against the victim's request pattern.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

	if !vaulttypes.IsGatewaySecretsMethod(req.Method) {
		return h.sendImmediateUserResponse(ctx, req, callback, api.UnsupportedMethodError, errors.New("this method is unsupported: "+req.Method))
	}

	_, cachedPublicKey := h.getCachedPublicKey()
	authorized, err := h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)
	if err != nil {
		if vaultcap.IsInvalidVaultParamsError(err) {
			return h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)
		}
		h.lggr.Errorw("request not authorized", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "error", err)
		return errors.New("request not authorized: " + err.Error())
	}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
