### Title
Missing connection cleanup and AbortHandshake call when MaxRequestBytesLimiter.Limit fails - ([File: core/services/gateway/network/wsserver.go])

### Summary
In `(s *webSocketServer) handleRequest`, when `s.config.MaxRequestBytesLimiter.Limit(r.Context())` returns an error after the WebSocket upgrade has already succeeded, the handler writes `http.StatusInternalServerError` and returns without closing `conn` or calling `s.acceptor.AbortHandshake(attemptId)`. This is inconsistent with every other error branch in the same function (upgrade failure, invalid handshake message, `FinalizeHandshake` failure), all of which call both `conn.Close()` and `s.acceptor.AbortHandshake(attemptId)`.

### Finding Description
The relevant code: [1](#0-0) 

Compare to the sibling error paths that do clean up properly: [2](#0-1) [3](#0-2) 

At the point of the `Limit()` call, `StartHandshake` has already been invoked and the WebSocket upgrade has already succeeded, meaning the acceptor holds pending state for `attemptId`, per the interface contract: [4](#0-3) 

Because `AbortHandshake` is not called on this specific error path, the acceptor's pending-attempt state for `attemptId` is not cleared, and the raw upgraded `net.Conn`/`*websocket.Conn` is never closed, leaking the socket. This is a genuine deviation from the function's own established error-handling pattern.

### Impact Explanation
Confirmed impact: an underlying TCP/WebSocket connection is leaked (never closed) and the acceptor's per-attempt state is not cleaned up, which is a resource leak / minor DoS vector (repeated triggering could exhaust file descriptors) and a violation of the intended isolation invariant for failed handshakes.

I could not confirm the more severe claim in the question — that this enables "a different connection to complete `FinalizeHandshake` for someone else's `attemptId`" — because `attemptId` is a server-side identifier that is never transmitted to the client (only the `challenge` is sent back in the response header), and I do not have visibility into the concrete `ConnectionAcceptor` implementation (its `connAttempts`-style store) to verify whether a stale, un-aborted `attemptId` could actually be reused/guessed by a second, unrelated connection to hijack the pending state. Without that implementation detail, the cross-user hijack scenario is unverified.

### Likelihood Explanation
Reaching this code path requires the attacker to cause `MaxRequestBytesLimiter.Limit(ctx)` to return an error after a successful WS upgrade, e.g., by exhausting a shared limiter resource. This is a purely internal/library-dependent error condition; exploitability as a resource-exhaustion trigger is plausible for an unauthenticated remote attacker able to open many WebSocket handshakes, but confirmation that it can be reliably forced is not established from the code reviewed alone.

### Recommendation
Add the same cleanup performed in the other error branches: on `Limit()` error, call `conn.Close()` and `s.acceptor.AbortHandshake(attemptId)` before returning, e.g.:
```go
maxRequestBytes, err := s.config.MaxRequestBytesLimiter.Limit(r.Context())
if err != nil {
    s.lggr.Errorw("failed to get request size limit", "err", err)
    conn.Close()
    s.acceptor.AbortHandshake(attemptId)
    w.WriteHeader(http.StatusInternalServerError)
    return
}
```
