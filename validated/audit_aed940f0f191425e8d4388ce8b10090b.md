### Title
Deleting a multisig key does not purge that key's confirmations from other pending requests, allowing a request to execute below the current threshold - (File: multisig/src/lib.rs)

### Summary
The `DeleteKey` action in `execute_request` removes only the *requests* that the deleted key itself created, but does not remove the *confirmations* that key previously cast on requests created by other keys. A stale confirmation from a revoked key therefore continues to count toward `num_confirmations`, letting a request execute with fewer currently-valid signers than the threshold requires.

### Finding Description
`MultiSigContract::confirm` authorizes execution once `confirmations.len() + 1 >= self.num_confirmations` [1](#0-0) . The set of confirming public keys is stored per request in `self.confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` [2](#0-1) , and the implicit invariant the contract relies on is: *every public key present in a request's confirmation set is a currently valid multisig key*.

When a `DeleteKey` action executes, the contract cleans up state for the deleted key, but only in one direction — it removes requests whose *creator* (`signer_pk`) matches the deleted key, and clears `num_requests_pk` for that key: [3](#0-2) 

It never scans `self.confirmations` to strip the deleted key from confirmation sets of requests *created by other keys*. So if key `K` confirmed request `R` (created by a different signer), and `K` is later removed via a `DeleteKey` request, `R`'s stored confirmation set still contains `K`'s public key. `K`'s "vote" keeps counting toward `num_confirmations` even though `K` is no longer an authorized key on the account.

This breaks the intended equality: `confirmations counted == confirmations from live members`. After the key deletion, the real number of *live* approvers backing `R` is one less than what `confirmations.len()` reports.

### Impact Explanation
This allows a multisig request to be executed with fewer live, currently-authorized signers than `num_confirmations` requires — i.e., "a multisig request executed below threshold," which is explicitly a Critical-severity outcome for this class of contract. Since `MultiSigRequestAction` includes `Transfer`, `AddKey`, `DeployContract`, and `FunctionCall`, this can be leveraged to move NEAR out of the account, add a new full-access key, or deploy/redeploy the contract using confirmation counts inflated by a since-revoked key.

### Likelihood Explanation
This requires no attacker privilege beyond the normal multisig workflow: a legitimate key confirms a pending request, that same key is later revoked (e.g., because it was compromised, rotated, or an employee left — the exact scenario `DeleteKey` exists to handle), and the stale confirmation silently remains valid. Any account using multiple pending requests with overlapping confirmers around the time of a key rotation naturally triggers this, so likelihood is not contingent on any social-engineering or privileged step — it's a straightforward consequence of the existing `DeleteKey` cleanup logic being incomplete.

### Recommendation
When executing `DeleteKey`, iterate `self.confirmations` and remove the deleted public key from every request's confirmation set (not just requests the key itself created), e.g.:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // remove confirmations by this key on every request
    let request_ids: Vec<u32> = self.confirmations.keys().collect();
    for request_id in request_ids {
        if let Some(mut confs) = self.confirmations.get(&request_id) {
            if confs.remove(&pk) {
                self.confirmations.insert(&request_id, &confs);
            }
        }
    }
    // existing logic that removes requests created by pk and num_requests_pk
    ...
}
```

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with keys `A, B, C, D` all having access.
2. Key `A` calls `add_request` to create transfer request `R` (not self-confirmed).
3. Key `B` calls `confirm(R)` → confirmations = `{B}` (1/3).
4. Key `C` calls `confirm(R)` → confirmations = `{B, C}` (2/3, not yet executed).
5. Separately, an already-approved `DeleteKey { public_key: C }` request executes (e.g., because `C` was compromised and the remaining signers rotate it out) via `execute_request` [3](#0-2) . This removes any request *created* by `C`, and clears `num_requests_pk[C]`, but leaves `confirmations[R] = {B, C}` untouched.
6. `C`'s access key no longer exists on-chain, yet it is still counted as an approver of `R`.
7. Key `D` calls `confirm(R)`. `confirmations.len() + 1 = 3 >= num_confirmations (3)` [4](#0-3) , so `R` executes and the transfer is sent — even though only `B` and `D` are actually live, valid signers (2 of 4 remaining keys), one short of the required 3-of-n threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
