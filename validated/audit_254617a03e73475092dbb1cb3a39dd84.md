### Title
Pre-commit conflict veto uses a pure wall-clock freshness window, letting delayed threshold-reaching cause a signer to sign a conflicting block at the same/higher height - (File: stacks-signer/src/v0/signer.rs)

### Summary
The pre-commit-to-signature path vetoes signing a block when a conflicting block at the same/higher height was recently signed, but "recently" is defined purely by wall-clock elapsed time (`get_epoch_time_secs()` vs `conflict.last_endorsed`) rather than by chain-state facts. If the elapsed time between endorsing the first conflicting block and reaching the pre-commit threshold for the second exceeds `tenure_last_block_proposal_timeout`, the veto silently lapses even though the first block is still canonical/live, mirroring the reported bug class where a purely time-based freshness window (rather than the actual state at re-open/resume) determines whether a stale check is enforced or bypassed.

### Finding Description
In the pre-commit handler, once the pre-commit weight threshold is reached, the signer queries for previously signed conflicting blocks at the same chain height via `self.signer_db.get_signed_conflicts(...)` and then decides whether to veto signing based on freshness: [1](#0-0) 

`freshness_cutoff` is derived solely from `get_epoch_time_secs()` minus the configured `tenure_last_block_proposal_timeout`. The veto for a fresh, still-live conflict is only applied if `conflict.last_endorsed > freshness_cutoff`. If that time window has elapsed - e.g., because of signer downtime, restart, StackerDB propagation delay, or simply a slow-to-form pre-commit quorum for the second, conflicting block - `conflict.last_endorsed` falls below `freshness_cutoff`, and the block is treated as "stale" regardless of whether it is still part of the canonical chain (`conflict_still_blocks` is never even evaluated in that branch, because the `&&` short-circuits on the failed freshness comparison).

The code then falls through to a second guard that only re-applies a veto if the conflict is in the *same tenure* as the newly-proposed block: [2](#0-1) 

A cross-tenure sibling conflict (two different tenures both producing a block at the same chain height, e.g. via a reorg attempt) is explicitly exempted from re-verification once time has passed the `tenure_last_block_proposal_timeout` window - the code comment even states "A stale conflict in another tenure in particular no longer speaks for us... settled by chainstate checks above," relying entirely on `check_block_against_signer_db_state` (already run earlier in the same function) to catch it: [3](#0-2) 

But `check_block_against_signer_db_state` only checks tenure-change-confirms-parent and latest-block-in-tenure invariants against the *node's* current view - it does not re-derive "was there a fresher-than-now conflicting signature we issued." If the node's local canonical view has already been advanced (e.g., because the conflicting tenure has been abandoned on-chain due to the same downtime/delay that caused the freshness window to lapse), this check will not flag anything, and the signer proceeds to co-sign a second, conflicting block at the same height purely because wall-clock time exceeded `tenure_last_block_proposal_timeout` - not because the network state actually resolved the conflict.

This is directly analogous to the reported bug class: a purely time-based freshness/staleness cutoff, decoupled from the actual state of the world at the moment the delayed action executes, flips the outcome of a safety check (veto vs. no veto) based on how long the delay was, rather than on what happened during the delay.

### Impact Explanation
If this window lapses and the chainstate-level checks do not independently catch the conflict (which the code's own comments acknowledge depend on the node's local view rather than a hard invariant), the signer can co-sign two blocks at the same/higher chain-length in different tenures. Multiplied across the signer set experiencing the same or correlated delay (e.g., a shared StackerDB/gossip slowdown), this can produce two independently-signed, conflicting blocks - breaking the one-block-per-height invariant the pre-commit conflict check exists to protect, which maps to a Critical-class outcome (a signer helping produce a conflicting/non-canonical signature).

### Likelihood Explanation
Likelihood is Low: `tenure_last_block_proposal_timeout` is a governance-configured constant (default single-digit tens of seconds per the CHANGELOG defaults), and triggering the scenario requires a delay of that magnitude between endorsing block A and reaching pre-commit threshold on a genuinely conflicting block B, plus the node's local chainstate checks failing to independently catch the same conflict. This requires unusual timing/latency conditions (analogous to the report's "sequencer down for over 1 hour") rather than routine operation, and does not require compromising a majority of signers or their keys - a delayed quorum formation for a legitimately competing proposal is sufficient.

### Recommendation
Do not gate the conflict veto purely on wall-clock elapsed time. Instead, always invoke `conflict_still_blocks` (and `reorg_permit_stands`) regardless of the `last_endorsed` age, and only skip the node round-trip as a fast-path optimization, never as a correctness gate. If a "stale" conflict is still reported by the node as blocking, the veto must still apply irrespective of how long ago it was endorsed, so that only genuine changes in canonical state - not merely elapsed wall-clock time - can lift the veto.

### Proof of Concept
1. Miner proposes tenure-change block `A` at chain height `N` in tenure `T1`; the signer set pre-commits and signs it, recording `last_endorsed = t0` for `A`.
2. Due to gossip/StackerDB propagation delay, signer restart, or general network latency, a competing/conflicting block `B` at height `N` in a different tenure `T2` (e.g., a subsequent sortition winner's tenure-change block) accumulates pre-commit weight slowly, crossing the pre-commit threshold only at `t0 + tenure_last_block_proposal_timeout + ε`.
3. In `handle_pre_commit` for `B`, `get_signed_conflicts` returns `A` as a conflict at the same height; `freshness_cutoff = now - tenure_last_block_proposal_timeout`, so `A.last_endorsed <= freshness_cutoff` and the first veto branch (lines 1403-1421) is skipped entirely, bypassing the `conflict_still_blocks` node check.
4. The second veto branch (lines 1432-1451) only fires for same-tenure conflicts, so a cross-tenure conflict like `A` vs `B` is not re-checked here.
5. If `check_block_against_signer_db_state` (run earlier for `B`) does not independently detect the conflict against the node's current view (e.g., because the node hasn't yet updated its own tip past `A`'s tenure), the signer proceeds to sign `B`, producing two independently signed, conflicting blocks at height `N`.
