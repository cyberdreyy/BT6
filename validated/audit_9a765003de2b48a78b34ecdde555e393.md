### Title
Permissionless, identity-only-derived lockup account address in `LockupFactory::create` lets anyone front-run and permanently claim an owner's vesting lockup with attacker-chosen (unvested) parameters - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` computes the lockup contract's NEAR account ID solely as `sha256(owner_account_id)[..20] || "." || current_account_id` [1](#0-0) , independent of `lockup_duration`, `vesting_schedule`, `release_duration`, or `whitelist_account_id`. The function is `#[payable]` with no caller restriction, so any unprivileged account can call it for any `owner_account_id` [4](#0-3) . Because NEAR sub-account creation is a one-time, irreversible action (`create_account()` fails if the account already exists), whoever calls `create()` first for a given owner permanently owns that address with the parameters they chose. A legitimate/foundation transaction later attempting to create the *real*, correctly-vested lockup for that same owner will simply fail and get its deposit refunded [3](#0-2) , but can never obtain the correct address for that owner again.

### Finding Description
The binding that should hold is: `lockup_account_id(owner) == account deployed with the vesting_schedule/lockup_duration the foundation/funder actually intended for owner`. Because the account address depends only on `owner_account_id` and nothing else, an attacker can:
1. Observe (off-chain or via a pending, not-yet-mined transaction) that the foundation/funder intends to create a lockup for `owner_account_id = victim`.
2. Call `create(owner_account_id: victim, lockup_duration: 0, vesting_schedule: None, release_duration: None, whitelist_account_id: <anything>)` themselves, attaching only `MIN_ATTACHED_BALANCE` (3.5 NEAR) [5](#0-4) .
3. This creates and deploys the lockup contract at the exact deterministic address `hash(victim).lockup-master` with no vesting schedule and zero lockup duration.
4. The foundation's subsequent legitimate `create()` call for `victim` with the real multi-year vesting schedule then fails at `create_account()` (the account already exists), and its deposit is simply refunded to the foundation [6](#0-5) .
5. The address is now permanently occupied by the attacker's version. If the foundation is unaware and transfers the granted NEAR to that (wrong-looking-correct) address, or if any downstream process assumes "the lockup account for `victim`" is the one at that deterministic address, tokens end up in a contract with no lock/vesting at all instead of the intended vesting schedule.

This is the direct analog of the referenced Nouns Builder issue: an identity/content-derived ID with no additional binding to the caller's authorization lets an unprivileged party occupy the slot first with different data, permanently preventing the legitimate party from establishing the correct custody terms at that identity-bound address.

### Impact Explanation
This breaks the custody binding "a lockup's releasable amount versus its schedule" and matches the Critical impact category "locked or unvested tokens released early" / "a wrongly ... parameterised deployment": tokens intended to be locked/vested for `owner_account_id` can end up governed by an attacker-chosen (fully unlocked, zero-duration) lockup contract instance instead of the intended vesting schedule, because the deterministic address is squatted before the real deployment happens.

### Likelihood Explanation
The `lockup_account_id` derivation is public and computable by anyone knowing `owner_account_id` (a value that is typically known or guessable ahead of an announced grant). `create` has no caller restriction and only requires attaching `MIN_ATTACHED_BALANCE`. Front-running a create-lockup transaction (which is typically sent well in advance, sometimes announced publicly per the `scripts/deploy_lockup.sh` workflow) is straightforward for any funded account.

### Recommendation
Bind additional commitment data (e.g., a hash of `lockup_duration`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`, or a `predecessor_account_id`/nonce) into the derived account name, or restrict `create()` to be callable only by the foundation account (or a signed authorization from the intended owner) so that an arbitrary third party cannot pre-claim a specific owner's deterministic lockup address with unauthorized parameters.

### Proof of Concept
1. Foundation intends to grant `victim.near` a 2-year-vesting lockup and prepares to call:
   `create({owner_account_id: "victim.near", lockup_duration: ..., vesting_schedule: {...}})`.
2. Attacker, seeing this intent (e.g., via a public announcement, or by monitoring the mempool for the foundation's transaction), first calls:
   `create({owner_account_id: "victim.near", lockup_duration: "0", vesting_schedule: null})` with `attached_deposit = MIN_ATTACHED_BALANCE`.
3. Attacker's call succeeds, deploying the lockup contract at `hash(victim.near)[..20].lockup-master` with no lock/vesting.
4. Foundation's subsequent call for the same `owner_account_id` fails during `create_account()` (account exists) and is refunded per `on_lockup_create` [3](#0-2) , and the foundation can never deploy the intended vesting lockup at that address for `victim.near` again.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
