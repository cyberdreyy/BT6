### Title
Operator-fee truncates to zero for small but valid scalar values due to premature division by a fixed decimal constant - (File: `crates/common/l1-fees/src/params.rs`)

### Summary
The Isthmus/pre-Jovian operator-fee formula divides `gas * operator_fee_scalar` by the fixed constant `OPERATOR_FEE_SCALAR_DECIMAL` (1,000,000) in a single integer division. For any transaction whose gas usage multiplied by the configured `operator_fee_scalar` is below 1,000,000, the entire operator fee silently rounds down to zero, mirroring the Panoptic finding where `s_ITMSpreadFee` collapsed to zero whenever `ITM_SPREAD_MULTIPLIER * _poolFee` fell below the fixed `DECIMALS` divisor.

### Finding Description
`L1FeeParams::operator_fee_charge_inner` computes the pre-Jovian operator fee as: [1](#0-0) 

```
gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
```

`OPERATOR_FEE_SCALAR_DECIMAL` is a hard-coded `1_000_000` (6-decimal fixed-point scale): [2](#0-1) 

`operator_fee_scalar` is a 32-bit value set by the chain operator via the `OperatorFee` `SystemConfig` update and propagated to every L2 block through the L1 attributes deposit: [3](#0-2) [4](#0-3) 

Because the scale factor is applied via a single truncating division after multiplying by `gas`, any combination where `gas * operator_fee_scalar < 1_000_000` yields an operator-fee component of exactly `0`, not a rounded-down-but-still-positive amount. For a minimum-gas transaction (e.g. `gas = 21,000`), any `operator_fee_scalar` value from `1` up to roughly `47` produces a zero proportional operator fee, even though the operator explicitly configured a non-zero scalar intending to collect a fee. This is structurally identical to the Panoptic bug: a legitimate, small, non-zero governance/config parameter is silently zeroed out by premature division against a fixed decimal constant, rather than being scaled correctly. This truncated value is used directly to route funds during transaction settlement: [5](#0-4) 

The same truncation-prone division is used consistently across the codebase's operator-fee accessors: [6](#0-5) 

### Impact Explanation
Every ordinary L2 transaction sent by any unprivileged sender flows through `operator_fee_charge`/`operator_fee_charge_inner` to compute the amount routed to `Predeploys::OPERATOR_FEE_VAULT`. If the chain operator configures a small (but intentionally non-zero) `operator_fee_scalar` — a value fully within the legitimate 32-bit range — normal, minimum-gas transactions pay **zero** operator fee instead of the intended proportional amount. This breaks the intended operator-fee mechanism (loss of protocol revenue / broken fee functionality), exactly the class of impact ("broken functionality", judged Medium) that the referenced Panoptic report was scored on. It does not, however, constitute theft of user funds, unbacked supply, a node halt, or an RPC outage — the transaction still executes correctly, just without the intended fee component being collected for low-gas transactions at low scalar settings.

### Likelihood Explanation
This triggers automatically and deterministically whenever the configured `operator_fee_scalar` and typical/minimum transaction gas usage multiply to less than `1,000,000` — no attacker action beyond sending a normal transaction is required. The likelihood is governed by the chain operator's choice of `operator_fee_scalar`; for very small scalars (which are valid, in-range configuration values), essentially all low-gas transactions on the network are affected.

### Recommendation
Avoid the single truncating division on the combined `gas * scalar` product for small values. Options include: performing the division with higher intermediate precision (e.g., accumulate fee in a higher-precision unit and only round at the very end of aggregation across a block, similar to how L1 data fees combine multiple terms before a single final division), or explicitly documenting/enforcing a minimum effective `operator_fee_scalar` such that `min_gas * operator_fee_scalar >= OPERATOR_FEE_SCALAR_DECIMAL`, or switching from per-transaction truncating division to a scheme that carries remainder credit forward (analogous to fixed-point accumulator patterns) so small legitimate scalars are not systematically nullified.

### Proof of Concept
1. Chain operator issues a `ConfigUpdate(OperatorFee)` log setting `operator_fee_scalar = 10` (a valid, non-zero `u32`), as encoded/applied here: [7](#0-6) 
2. This value is embedded into every subsequent L1 attributes deposit and read back as `operator_fee_scalar` for the block.
3. A user submits a plain transfer with `gas_used = 21,000` (a typical/minimum value). During settlement:
   - `gas.saturating_mul(operator_fee_scalar) = 21,000 * 10 = 210,000`
   - `210,000 / OPERATOR_FEE_SCALAR_DECIMAL (1,000,000) = 0` (integer division)
   - `operator_fee_charge_inner` returns `0`, as directly demonstrated by the existing unit test pattern where scalars/gas below the decimal threshold yield `U256::ZERO`: [8](#0-7) 
4. The transaction executes and settles normally, but zero funds are routed to `Predeploys::OPERATOR_FEE_VAULT`, even though the operator explicitly configured a non-zero fee scalar intending to collect a proportional fee on every transaction.

    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }
