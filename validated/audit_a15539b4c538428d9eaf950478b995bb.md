Confirmed: `delete_member` and `confirm` never reconcile the `confirmations` `HashSet<String>` against currently live members, so a member's stale confirmation persists after that member is removed from the multisig.

### Title
Multisig executes requests below the live-member threshold via stale confirmations from deleted members - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes execution purely by comparing `confirmations.len()` to `num_confirmations`, without verifying that every account/key recorded in `confirmations` is still a current member. `delete_member` only purges requests that the removed member *originated* (`r.member == member`), not confirmations the removed member cast on other members' still-pending requests. This is analogous to the MIMOProxy defect where a value that should reflect current, trustworthy state (the true function selector actually delivered) was instead computed from stale/uncontrolled data — here the "K" in "K-of-N" is computed from a set that can contain confirmations from members who are no longer part of "N".

### Finding Description
`confirm` reads the stored `HashSet<String>` for a request and checks the size against `num_confirmations`: [1](#0-0) 

`delete_member` removes a departing member and deletes only requests that member itself submitted; it does not scan other pending requests' confirmation sets to strip that member's prior votes: [2](#0-1) 

`assert_valid_request`, the only gate invoked before `confirm` proceeds, checks that the *caller* is a current member and that the request/confirmations entries exist — it never re-validates the *existing* entries inside the confirmations set against the current `members` set: [3](#0-2) 

The binding that should hold is:
```
live_confirmations(request) = |{ c in confirmations[request] : c ∈ current_members }|
execute(request) ⟺ live_confirmations(request) + 1 ≥ num_confirmations
```
Instead the code enforces:
```
execute(request) ⟺ |confirmations[request]| + 1 ≥ num_confirmations
```
which is not equal once any confirming member has since been deleted, because `|confirmations[request]|` can exceed `live_confirmations(request)`.

### Impact Explanation
This lets a request (including `Transfer`, `FunctionCall`, `AddKey`, `AddMember`, `DeployContract`) execute with fewer confirmations from currently-authorized members than `num_confirmations` requires, i.e. a multisig request executed below threshold — explicitly a Critical-impact category. Funds (`Transfer`) can move, or a new key/member can be added, with the effective live-signer approval below the configured K, undermining the entire "K out of N" custody guarantee of the contract.

### Likelihood Explanation
No special privilege beyond being one of several *current* members is required, and member turnover (any `DeleteMember` action, which is a normal, expected multisig operation) is the only precondition. Any pending request that already carries a confirmation from a member who is later removed becomes exploitable: the remaining members only need to supply `num_confirmations - 1` (or fewer, if multiple removed members had confirmed) genuinely live confirmations to push it through. This is easy to trigger in ordinary key-rotation workflows and requires no redeploy, no foundation action, and no compromise of any live member's key.

### Recommendation
When removing a member in `delete_member`, iterate all pending requests and strip the removed member's entry from each request's `confirmations` set (not only requests they originated), or alternatively, recompute `live_confirmations` at `confirm`-time by intersecting the stored confirmation identities with the current `members` set before comparing to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. Member `X` (any member) calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account).
3. Member `A` calls `confirm(R)` → `confirmations[R] = {A}` (size 1, below 3, so no execution yet).
4. Separately, members create and confirm a `DeleteMember { member: A }` request with the required 3 live confirmations (a routine key-rotation action); this succeeds because `delete_member`'s only check is `members.len() - 1 >= num_confirmations`, and it does not touch `confirmations[R]`. `A` is now removed from `members`, but `confirmations[R]` still equals `{A}`. [4](#0-3) 
5. Members `B` and `C` (only 2 *live* confirmers) call `confirm(R)`. After `B`: `confirmations[R] = {A,B}`, size 2 (< 3). After `C`: `confirmations[R] = {A,B,C}`, size 3, so `confirmations.len() + 1 >= num_confirmations` (3+... actually `len()==3`, and check is `len()+1>=3`, already true at len 2) — the request executes on `C`'s confirmation with only `B` and `C` as live approvers plus the stale `A`. [5](#0-4) 
6. Request `R` (e.g., the `Transfer`) executes with effectively 2 live confirmations instead of the required 3, i.e., below the configured threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
