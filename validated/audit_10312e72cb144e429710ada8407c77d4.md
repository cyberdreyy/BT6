### Title
Proposer-controlled attestation ordering can zero out builder-payment weight credit before quorum is reached - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_attestation` in Gloas only credits a validator's effective balance toward `BuilderPendingPayment.weight` if that validator had **zero** participation flags set before this specific attestation was processed (`had_no_participation`). The block proposer fully controls which attestations are included in a block and in what order they are applied within `process_operations`/`process_attestation`. By feeding a validator's participation flags with a throwaway/partial attestation first (in the same block, ordered earlier), the proposer can make `had_no_participation` false for that validator when their "real" high-quality, same-slot attestation is processed later, silently suppressing the weight credit that attestation should have contributed to the builder's pending payment. This mirrors the courier bug's root cause: a privileged credit/assignment is gated by "is this participant currently in the zero/uninitialized state," and a third party can pre-empt that zero state via ordering control to deny the legitimate credit.

This weight is later checked against a quorum threshold in epoch processing:
```

    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

``` [3](#0-2) 

If `payment.weight` never reaches quorum before the 2-epoch window closes, the payment entry is silently dropped/rotated out — no `BuilderPendingWithdrawal` is ever created, so the builder's committed bid amount (`bid.value`, already used to build the canonical, committed payload) is never paid out to `fee_recipient`. The block proposer, who assembles `block.body.attestations` and their order, decides which attestations get applied to a given validator first within `process_attestation`. Nothing in the spec prevents the proposer from:
1. Including a low-quality attestation from validator V for the target slot first (setting e.g. only `TIMELY_SOURCE_FLAG_INDEX`), which flips `epoch_participation[V]` away from `0b0000_0000`.
2. Then including V's real, timely, same-slot, head-matching attestation, which still sets new flags (`will_set_new_flag=True`) and would have earned weight credit — except `had_no_participation` is now `False`, so `payment.weight` is **not** incremented for V's effective balance.

This is structurally identical to the courier bug: the courier-designation write in `_mint` was gated on `balanceOf(beneficiary) == 0`, and an attacker could front-run to make that condition false before the legitimate call, thereby preventing the legitimate assignment (of courier / here, of payment weight) without the beneficiary's (validator's, in aggregate the builder's) consent.

### Impact Explanation
This lets a single proposer, unilaterally and within their own block, deny a builder the payment they are contractually owed for the payload they already delivered and that the chain already committed to (the bid was signed, verified, and the payload was used). This is a "builder payment... escaped" scenario under the specified impact categories: Gwei that should be paid out per the committed bid never gets paid, purely due to a spec-defined ordering artifact that one participant (the block proposer) fully controls — no majority stake, no coalition, no external/client bug required. It also degrades payload-timeliness incentive accounting more broadly, since the weight-based quorum mechanism is meant to reflect honest majority PTC/attester agreement on payload timeliness, but a proposer can locally deflate it for individual validators of their choosing.

### Likelihood Explanation
Likelihood is comparable to the original courier bug: it requires deliberate action by a single actor (the block proposer for the slot in question) with no cost to themselves, similar to the "griefing, no profit motive needed but attacker fully controls timing" pattern the judges accepted as Medium severity in the original report. Here the attacker doesn't even need to front-run someone else's transaction — they are the proposer constructing the block and can simply order/select attestations inside their own block, making this arguably *easier* to execute than the original bug (which needed a front-run of another party's deposit tx).

### Recommendation
The weight credit should not depend on the validator's participation state at the moment this specific attestation happens to be processed within the block. Instead, weight crediting should be based on whether the *particular flag relevant to payload timeliness* (e.g., the head/timeliness flag driven by this attestation) is being newly set, independent of unrelated flags set by other (possibly proposer-ordered) attestations for the same validator/epoch in the same block. Concretely, gate `had_no_participation`-style logic on a flag that is specific to the payload-timeliness signal being tracked (or track weight credit per relevant participation flag rather than "epoch_participation == 0"), so that proposer-controlled ordering of unrelated/partial attestations cannot suppress the weight contribution of an otherwise-valid, high-quality attestation.

### Proof of Concept
1. At slot `S`, validator `V` is part of the committee and is eligible to same-slot attest with full timely-head-matching data, contributing `effective_balance(V)` to `builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH].weight` (this is exactly what `test_builder_payment_weight_tracking` in the test suite exercises and asserts). [4](#0-3) 
2. The proposer of the block that includes `V`'s attestations for slot `S` first includes a distinct attestation object from `V` for the same slot/target that satisfies only `TIMELY_SOURCE_FLAG_INDEX` (e.g., correct source/target but wrong head root), which is processed by `process_attestation` and sets `epoch_participation[V] != 0b0000_0000`.
3. The proposer then includes `V`'s legitimate, fully timely, same-slot, head-matching attestation second in `block.body.attestations`.
4. When `process_attestation` runs on the second attestation, `will_set_new_flag` is `True` (it sets `TIMELY_TARGET`/`TIMELY_HEAD`), but `had_no_participation` is now `False` (set by step 2's attestation), so the `if` block at lines 2383–2389 is skipped and `payment.weight` is **not** incremented by `effective_balance(V)`.
5. Repeating this for enough of the committee lets the proposer keep `payment.weight` below `get_builder_payment_quorum_threshold(state)` even though a majority of validators actually delivered valid, timely, same-slot attestations for the builder's payload. After the 2-epoch window, `process_builder_pending_payments` silently evicts the entry (no `weight >= quorum` branch taken), and the builder's bid payment is never appended to `state.builder_pending_withdrawals` — the committed payment "escapes." [3](#0-2) 

Note: I was unable to fully trace, within available tool calls, the exact code for `get_builder_payment_quorum_threshold` and `can_builder_cover_bid`/where `builder.balance` is actually decremented (i.e., whether the reserved bid amount is released back to the builder or remains locked) — this affects whether the impact is "builder payment escapes/never settles" vs. also involving a stuck-fund state. This detail should be verified directly in `specs/gloas/beacon-chain.md` before finalizing severity.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def test_builder_payment_weight_tracking(spec, state):
    """
    Test that builder payment weights are tracked correctly for Gloas.
    """
    transition_to_slot_via_block(spec, state, 2)

    # Create attestation for slot 0
    attestation_slot = 0
    attestation = get_valid_attestation(spec, state, slot=attestation_slot, index=0)
    attestation.data.index = 0  # Same-slot (slot 0) must use index 0

    # Get only the first validator to attest
    committee = spec.get_beacon_committee(state, attestation_slot, 0)

    # Clear all bits except first validator
    for i in range(len(attestation.aggregation_bits)):
        attestation.aggregation_bits[i] = i == 0

    attesting_validator_index = committee[0]
    expected_weight_increase = state.validators[attesting_validator_index].effective_balance
    assert expected_weight_increase > 0

    sign_attestation(spec, state, attestation)

    # Manually set up a non-zero builder pending payment for slot 0
    payment_slot_index = spec.SLOTS_PER_EPOCH + attestation_slot % spec.SLOTS_PER_EPOCH
    test_payment_amount = spec.Gwei(1000000000)
    state.builder_pending_payments[payment_slot_index] = spec.BuilderPendingPayment(
        weight=spec.Gwei(0),
        withdrawal=spec.BuilderPendingWithdrawal(
            fee_recipient=spec.ExecutionAddress(),
            amount=test_payment_amount,
            builder_index=0,
        ),
    )

    # Store initial weight for slot 0
    initial_weight = state.builder_pending_payments[payment_slot_index].weight

    # Process attestation
    yield from run_attestation_processing(spec, state, attestation, valid=True)

    # Check that weight was updated (this verifies the Gloas-specific logic)
    final_weight = state.builder_pending_payments[payment_slot_index].weight

    # Calculate expected weight increase for same-slot attestations in Gloas
    # Weight should increase by the effective balance of the attesting validator
    expected_final_weight = initial_weight + expected_weight_increase
