### Title
Cross-user response hijack via `MessageId`-only keyed `savedCallbacks` map in web API trigger handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `handler.savedCallbacks` map used to correlate a DON's trigger response with the originating user request is keyed solely by `msg.Body.MessageId`, which is fully attacker-controlled and never bound to the requester's identity (`Sender`). Two different, unauthenticated users submitting `HandleLegacyUserMessage` requests to the same DON with the same `MessageId` will collide in the map, so whichever request's `savedCallback` is present when a DON node's response for that `MessageId` arrives receives the response — potentially delivering one user's trigger result/error data to a different, unrelated caller.

### Finding Description
`HandleLegacyUserMessage` stores the caller's callback under the raw, client-supplied `MessageId`: [1](#0-0) 

`MessageId` is attacker-controlled input coming straight from the JSON-RPC request `ID` (or legacy message body), and its only validation is length/format, not uniqueness or association with sender: [2](#0-1) 

When a DON node later responds (`HandleNodeMessage` → `handleWebAPITriggerMessage`), the response is matched purely by `MessageId`, deleted from the map, and delivered to whatever callback is currently stored there — with no check that the response corresponds to the same `Sender` who registered that callback: [3](#0-2) 

`savedCallback` itself carries no sender/requester binding to allow such a check: [4](#0-3) 

Exploit flow: attacker A observes or guesses victim B's in-flight `MessageId` "X" (e.g. short/sequential/predictable IDs) and submits their own `HandleLegacyUserMessage` request with the same `MessageId="X"` to the same DON while B's request is still pending. Because `h.savedCallbacks[msg.Body.MessageId] = ...` is an unconditional overwrite with no existence check, whichever request registers last "wins" the map slot. When the DON node responds with `MessageId="X"` (echoing back the ID from whichever original signed request the node processed), the gateway's `handleWebAPITriggerMessage` delivers that response to whoever currently holds the map slot — which may be the other party's callback. This breaks the intended per-request isolation invariant since the map is not scoped by `(Sender, MessageId)`.

### Impact Explanation
This is a cross-user response confusion / hijack: attacker-controlled requests can intercept another user's DON response payload (trigger submission status/error content) or cause a user's request to silently receive no response (timeout) because their callback was evicted by a colliding `MessageId` from another party. This matches Chainlink's "unauthorized action on another user's job/subscription/response" bounty impact class, since data intended for one caller of the gateway API is delivered to a different, unrelated caller.

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or race a victim's `MessageId`. The gateway itself imposes no format/uniqueness requirements beyond length (≤200 chars, no trailing NUL), so if any legitimate client uses short, sequential, timestamp-derived, or otherwise guessable message IDs, the collision window is real and requires no special privilege — only the ability to send signed gateway requests to the same DON (any client with valid connector credentials, which is the unprivileged attacker class in scope). No admin/operator access is required; only network access to the gateway's `ProcessRequest` endpoint and knowledge/guess of a colliding `MessageId` at the right time.

### Recommendation
Key `savedCallbacks` (and the analogous map in `core/services/gateway/handlers/handler.dummy.go`) by a composite of `(Sender, MessageId)` instead of `MessageId` alone, and validate in `handleWebAPITriggerMessage`/`HandleNodeMessage` that the node's response `Sender` context matches the sender recorded at registration time before delivering the callback. Alternatively, generate gateway-side unique correlation IDs internally rather than trusting client-supplied `MessageId` for map keys.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two signed `api.Message`s from different private keys (simulating attacker A and victim B), both using the same `MessageId = "X"` and `MethodWebAPITrigger`, targeted at the same DON.
2. Call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` (victim registers first), then `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` (attacker registers second, overwriting the map slot).
3. Simulate the DON node responding to B's original request by constructing a valid `jsonrpc.Response` with `ID="X"` (as would come from `hc.ValidatedResponseFromMessage(msgB)`), and call `handler.HandleNodeMessage(ctx, respForB, nodeAddr)`.
4. Assert that `cbA.Wait(ctx)` (attacker's callback) — not `cbB.Wait(ctx)` — receives B's response payload, demonstrating cross-user delivery; expect this assertion to fail against a correct implementation once keying is fixed to `(Sender, MessageId)`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
