### Title
Missing project/job-scoping in `EnvironmentKey` allows cross-project resume/takeover of suspended containers - ([File: common/environment_key.go], [File: executors/internal/autoscaler/executor.go], [File: executors/docker/docker.go])

### Summary
`EnvironmentKey.String()` encodes only `RunnerID`, `SystemID`, and executor-specific opaque fields (e.g. `build-container-id`, `helper-id`, `acquisition-key`); it carries no project ID, job ID, or token binding. Both `validateEnvKey` (autoscaler) and `resumeDependencies` (docker) validate only that the runner/system match and that the referenced containers/acquisitions exist — neither verifies that the key belongs to the project or job attempting to resume it.

### Finding Description
`Build.suspendEnvironment` builds the key purely from runner identity and executor state: [1](#0-0) 
`EnvironmentKey.String()` serializes only those three components: [2](#0-1) 

On the consuming side, `validateEnvKey` in the autoscaler executor checks only `RunnerID`/`SystemID` equality and that an `acquisition-key` field is present — no project or job identity check exists: [3](#0-2) 

Similarly, the docker executor's `resumeDependencies` (exercised by `TestResumeDependencies_buildContainerNotFound`/`TestResumeDependencies_helperNotFound`) resolves `build-container-id`/`helper-id` straight from the key's fields and only fails if the container is *not found* by the docker daemon — it never checks that the container belongs to the same project/job: [4](#0-3) 

So, given any two jobs that land on the same runner/system (a realistic scenario for shared runners, which are explicitly cross-project by design), a key minted for job A (project X) is syntactically and semantically indistinguishable — at the Runner level — from a key that "belongs" to job B (project Y). Nothing in `common/build.go`, `common/environment_key.go`, `executors/internal/autoscaler/executor.go`, or `executors/docker/docker.go` binds the key to project/job identity; the only isolation is whatever the GitLab Rails backend does when deciding to place a stored `environment_key` into a given job's `SuspendOptions` in the `POST .../jobs/request` response.

This means the Runner code itself provides **no defense-in-depth** for the stated invariant ("a job's execution state stays confined to its own project"). If `SuspendOptions.EnvironmentKey` in a job payload is ever populated with a key belonging to a different project's job — whether through a backend authorization bug, replay, or job retry/rerun logic that doesn't correctly scope keys by project — the runner will happily accept it, `Resume()` the taskscaler acquisition, and `resumeDependencies()` will reattach to another project's running/stopped build+helper+service containers.

### Impact Explanation
If the precondition (a job payload with a foreign-project `environment_key`) is met, the resuming job would attach to another project's suspended containers, gaining access to that project's build filesystem, environment variables, mounted secrets, and running processes. This is exactly the "cross-project resume/takeover" scoped impact described. The severity is entirely gated on whether the environment_key can actually cross project boundaries in the job payload sent by the GitLab backend — a boundary this repository does not control or verify.

### Likelihood Explanation
The Runner-side code path is trivially reachable and unconditionally missing the check — a unit test proves it (see PoC). However, `Job.SuspendOptions.EnvironmentKey` is not a value that a pipeline author can set via `.gitlab-ci.yml`, CI/CD variables, or any other Runner-facing job input; it is populated server-side by GitLab Rails in the job response, based on state the backend previously received via `trace.SetEnvironmentKey`. Therefore, actually forcing a foreign-project key into a job's `SuspendOptions` requires either a bug in the GitLab backend's per-project/job scoping of stored environment keys, or attacker control over the backend's job-dispatch response — both of which are backend trust-boundary issues outside `gitlab-runner`'s code, and are excluded by the audit rules ("Do not rely on ... GitLab-admin compromise, or external service compromise alone").

### Recommendation
Add defense-in-depth to the Runner itself so it does not rely solely on backend scoping:
- Embed the project ID (and ideally job ID) in `EnvironmentKey` (`common/environment_key.go`) alongside `RunnerID`/`SystemID`.
- Extend `validateEnvKey` (`executors/internal/autoscaler/executor.go`) and the docker `resumeDependencies` check (`executors/docker/docker.go`) to verify the embedded project/job ID matches the current job's `JobInfo.ProjectID`/job ID before resuming, rejecting mismatches with a clear error.

### Proof of Concept
```go
func TestEnvironmentKey_CrossProjectReplay_NotRejectedByRunnerAlone(t *testing.T) {
    // Job A (project 111) suspends and gets an EnvironmentKey.
    keyA := common.EnvironmentKey{
        RunnerID: 101,
        SystemID: "sys-1",
        Fields:   url.Values{"acquisition-key": []string{"acq-A"}},
    }.String()

    // Job B (project 222), same runner/system, replays job A's key.
    // validateEnvKey has no notion of "project" at all, so it must succeed.
    acqKey, _, err := validateEnvKey(keyA, 101, "sys-1")
    require.NoError(t, err)
    assert.Equal(t, "acq-A", acqKey)

    // Assertion: nothing in validateEnvKey's signature or logic takes
    // project/job identity into account -> cross-project key is accepted.
}
```
Expected assertion result: the test passes today, demonstrating `validateEnvKey` (and analogously `resumeDependencies` in `executors/docker/docker.go`) performs no project/job ownership check — confirming the Runner-side gap, while noting the actual cross-project delivery of such a key depends on GitLab backend behavior outside this repository's control.

```go
func validateEnvKey(envKey string, runnerID int64, systemID string) (string, url.Values, error) {
	key, err := common.ParseEnvironmentKey(envKey)
	if err != nil {
		return "", nil, err
	}

	if key.RunnerID != runnerID {
		return "", nil, errors.New("environment key was not issued by this runner")
	}
	if key.SystemID != systemID {
		return "", nil, errors.New("environment key was not issued by this machine")
	}

	data, executorFields, err := parseEnvKeyFields(key.Fields)
	if err != nil {
		return "", nil, fmt.Errorf("environment key fields: %w", err)
	}

	return data.acqKey, executorFields, nil
```
