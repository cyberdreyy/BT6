### Title
APR0 withdraw requests are validated only at `stopEpoch`, letting an unprivileged lender freeze the epoch and all pending withdrawals when APR is later raised - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.requestWithdraw` accepts and escrows a withdraw request while `unscaledApr == 0` without checking whether the APR can remain zero for the request's lifecycle. The invariant "APR0 principal is only valid while APR is 0" is only enforced later, inside `prepareStopEpochWithApr0`, which `revert NotAllowed()` if `unscaledApr != 0` while `apr0TotalPrincipal != 0`. Because `apr0TotalPrincipal` is attacker-controllable (any lender can add to it via a withdraw request), a queued request poisons the epoch-completion path: any honest attempt by the manager to run the pool at a non-zero APR makes `stopEpoch`/`stopEpochWithDuration` revert, freezing every pending withdraw receipt and the pool's funds.

### Finding Description
The external bug is a deferred-validation flaw: instructions are accepted into a queue without an ordering check, and the revert only surfaces at completion time, after funds are already locked. The same pattern exists in the APR0 withdraw flow.

1. During a running epoch with `unscaledApr == 0`, any whitelisted lender calls `IdleCDOEpochVariant.requestWithdraw`, which calls `IdleCreditVault.requestWithdraw`. The function burns the CDO's strategy tokens, mints a receipt to the user, increases `pendingWithdraws`, and routes the amount into `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` (`IdleCreditVault.sol` lines 285-286, 567-577). No check is made that the APR will still be zero when the epoch ends — and there is no way to check, since APR is set by the manager per epoch.

2. At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`. If `apr0TotalPrincipal != 0` and the manager has since set `unscaledApr != 0` (a perfectly legitimate action), the function reverts (`IdleCreditVault.sol` lines 502-508):

```solidity
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

Because this revert happens inside the epoch-completion transaction, the epoch cannot be stopped. There is no cancellation path for a normal withdraw request in `IdleCreditVault` (unlike the queue's `deleteWithdrawRequest`), so the attacker's receipt cannot be removed to unblock `stopEpoch`.

3. The freeze persists as long as any APR0 principal exists and APR is non-zero. An attacker can keep `apr0TotalPrincipal` non-zero indefinitely by submitting a small APR0 withdraw request each buffer period, so the manager is forced to either keep `unscaledApr == 0` forever (denying all LPs yield) or leave the pool frozen. Even a single occurrence freezes all `pendingWithdraws`, all funded-but-unclaimed receipts, and forces an emergency shutdown path to recover.

Broken invariant: a request accepted and paid for (strategy tokens burned, `pendingWithdraws` incremented) must be completable; here completion validity depends on a condition (APR staying 0) that is neither guaranteed nor checked at request time, and failure is deferred to the privileged completion step — exactly the "queued transfer stuck on the source chain" pattern, mapped to the `requestWithdraw` → `prepareStopEpochWithApr0`/`stopEpoch` pipeline.

Existing guards do not prevent it: the APR0 revert at line 507 *is* the deferred check firing too late; `_onlyIdleCDO` and KYC do not help since any legit lender is in scope as an unprivileged attacker.

### Impact Explanation
Temporary-to-persistent freezing of funds with quantifiable loss: all pending withdraw receipts (`pendingWithdraws`) plus the pool's active NAV cannot be processed while `stopEpoch` reverts, and the borrower cannot be re-priced to a positive APR. The attacker pays only the opportunity cost of a small withdraw request. If the manager wishes to run any positive-APR epoch, the freeze is effectively permanent until the attacker stops topping up APR0 principal or funds are rescued via emergency shutdown (which itself socializes the disruption to all LPs).

### Likelihood Explanation
Requires only that the pool run an epoch with `unscaledApr == 0` (a supported configuration — the APR0 machinery exists specifically for it) and that a lender submits a withdraw request, after which the manager attempts a positive-APR epoch. Each step is a normal, unprivileged or honest-privileged action; no collusion or exotic state is needed. Mainnet pools that toggle APR between 0 and positive values across epochs make this reachable in ordinary operation.

### Recommendation
Enforce the lifecycle invariant at request time or remove the revert from the completion path, e.g.:
- In `requestWithdraw`, when `unscaledApr == 0`, record the request epoch and in `prepareStopEpochWithApr0` settle APR0 principal at the stored request-epoch rate (or zero interest) instead of reverting on `unscaledApr != 0`.
- Alternatively, reject APR0 withdraw requests unless the manager commits to keeping APR at 0 for the next epoch (e.g., a locked-APR flag checked in `setApr`/`setAprsWithBuffer`), so the validity of the request is guaranteed when it is queued rather than verified at completion.
- A cancellation/escape path for APR0 receipts (burn receipt, restore `pendingWithdraws`/`apr0TotalPrincipal`) would also unblock `stopEpoch` without protocol changes to settlement math.

### Proof of Concept
Foundry fork PoC (scaffold mirrors `test/foundry/IdleCDOEpochQueue.t.sol` helpers `_depositWithUser`, `_stopCurrentEpochWithApr`, `manager`, `cdoEpoch`, `strategy`, `tranche`):

```solidity
function testApr0RequestBlocksPositiveAprStop() external {
    // Epoch N runs with unscaledApr == 0 (APR0 mode configured by manager).
    _stopCurrentEpochWithApr(0);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Attacker: any whitelisted lender deposits, then requests a withdraw.
    address attacker = makeAddr('attacker');
    uint256 tranches = _depositWithUser(attacker, 1e6);
    _requestWithdrawWithUser(attacker, tranches);

    // Receipt minted, CDO strategy tokens burned, pendingWithdraws and
    // apr0TotalPrincipal increased - the request was accepted and paid for.
    assertGt(strategy.pendingWithdraws(), 0);
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // Honest manager sets a positive APR for the next epoch lifecycle.
    vm.prank(manager);
    strategy.setAprsWithBuffer(10e18, cdoEpoch.epochDuration(), cdoEpoch.bufferDuration());

    // Epoch end: stopEpoch calls prepareStopEpochWithApr0 -> reverts NotAllowed.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // No user-facing cancel exists in IdleCreditVault for normal requests:
    // the attacker's receipt keeps apr0TotalPrincipal != 0, so every
    // positive-APR stopEpoch keeps reverting. Attacker re-requests each
    // buffer period to make the freeze persistent; all pendingWithdraws
    // and funded receipts stay frozen meanwhile.
}
```

Both follow directly from the code cited.
