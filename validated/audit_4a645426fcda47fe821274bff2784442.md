### Title
`Clock::is_mutable` does not detect `MutableReference(DatatypeInstantiation(Clock_idx, []))`, allowing a crafted module to publish with a `&mut Clock` entry parameter and corrupt the global Clock timestamp — (`crates/sui-types/src/clock.rs`)

### Summary
`Clock::is_mutable` only matches `SignatureToken::Datatype` when recursing into a `MutableReference`. A hand-crafted module that encodes the Clock type as `DatatypeInstantiation(Clock_idx, [])` (a zero-argument generic instantiation, which is structurally valid for a non-generic struct) bypasses this check entirely. The Sui entry-point verifier then accepts the parameter as a normal object reference and publishes the module. The published entry function can be called with Clock (0x6) as a mutable shared-object input, allowing arbitrary writes to `clock.timestamp_ms`.

### Finding Description
`Clock::is_mutable` in `crates/sui-types/src/clock.rs` (line 41–48) matches only `SignatureToken::Datatype(idx)` when checking the inner type of a `MutableReference`. The Move binary format also permits `SignatureToken::DatatypeInstantiation(idx, type_args)` to represent a struct type; for a struct with zero type parameters (like Clock), an empty `type_args` list is accepted by the bounds checker (`check_bounds.rs` line 731–746: `sh.type_parameters.len() != type_params.len()` → `0 != 0` → no error). The Sui entry-point verifier's `verify_param_type` calls `Clock::is_mutable` first; when it returns `false`, the code falls through to `is_object`, which explicitly handles `DatatypeInstantiation` and returns `true` for any type with the `key` ability. The net result is that `verify_param_type` returns `Ok(())` for `MutableReference(DatatypeInstantiation(Clock_idx, []))`, and the module is published.

### Impact Explanation
The global Clock object at address 0x6 is a singleton shared object whose `timestamp_ms` field is the authoritative time source for all Move contracts on Sui. An attacker who publishes and calls the crafted entry function can set `clock.timestamp_ms` to an arbitrary value. This corrupts the global time state, enabling bypass of any time-gated asset transfer, time-lock, or deadline check in any deployed contract that reads `sui::clock::timestamp_ms`. This is state corruption of a system-level shared object reachable from a public package-publish + transaction path.

### Likelihood Explanation
The exploit requires only two ordinary transactions: a `Publish` transaction (package publisher role) and a `MoveCall` transaction (ordinary SUI holder). No privileged access, validator cooperation, or leaked keys are needed. The crafted binary module can be constructed with the public `move-binary-format` crate. Likelihood is high given the low barrier.

### Recommendation
In `Clock::is_mutable`, add a match arm for `S::DatatypeInstantiation`:

```rust
pub fn is_mutable(view: &CompiledModule, s: &SignatureToken) -> bool {
    use SignatureToken as S;
    match s {
        S::MutableReference(inner) => Self::is_mutable(view, inner),
        S::Datatype(idx) => resolve_struct(view, *idx) == RESOLVED_SUI_CLOCK,
        S::DatatypeInstantiation(inst) => {
            let (idx, _) = &**inst;
            resolve_struct(view, *idx) == RESOLVED_SUI_CLOCK
        }
        _ => false,
    }
}
```

Apply the same fix to `is_mutable_random` if it has the same pattern.

### Proof of Concept
Construct a `CompiledModule` in a unit test with:
- A `DatatypeHandle` for `sui::clock::Clock` with zero type parameters
- A function signature whose parameter list is `[MutableReference(DatatypeInstantiation(clock_handle_idx, []))]`
- `is_entry = true`

Call `Clock::is_mutable(view, &MutableReference(DatatypeInstantiation(clock_handle_idx, vec![])))` and assert it returns `true` — it currently returns `false`, confirming the gap. Then run the full Sui verifier (`verify_module`) against the crafted module and observe it returns `Ok(())` instead of an error.
