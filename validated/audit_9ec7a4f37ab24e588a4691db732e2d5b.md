### Title
`FREEZE_SETTINGS` flag on a `Bank` can never be disabled once set, permanently locking out `admin`/`delegate_curve_admin` from adjusting risk parameters - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs](programs/marginfi/src/instructions/marginfi_group/configure_bank.rs))

### Summary
The reported bug class is a boolean toggle that can be set but never reverted because the code path used to update the flag becomes unreachable once the flag is `true`. marginfi-v2's `Bank.flags` bitmask has an analogous "frozen" flag, `FREEZE_SETTINGS`, whose only mutation path is short-circuited the moment it is enabled, leaving no on-chain instruction able to clear it again.

### Finding Description
`Bank.flags` bit 3 is `FREEZE_SETTINGS`, described as freezing "most bank configuration parameters" while leaving only `deposit_limit`/`borrow_limit` adjustable [1](#0-0) . The flag itself is toggled through `Bank::configure`, which reads `config.freeze_settings` and calls `update_flag(flag, FREEZE_SETTINGS)` — a correct, bidirectional bit set/clear routine [2](#0-1) [3](#0-2) .

However, `lending_pool_configure_bank` (the only instruction handler that calls `Bank::configure`) branches on the *current* value of `FREEZE_SETTINGS` before doing anything:

```rust
if bank.get_flag(FREEZE_SETTINGS) {
    bank.configure_unfrozen_fields_only(&bank_config)?;
    ...
} else {
    bank.configure(&bank_config)?;
    ...
}
``` [4](#0-3) 

Once `FREEZE_SETTINGS` is `true`, every subsequent call routes into `configure_unfrozen_fields_only`, which only ever touches `deposit_limit` and `borrow_limit` and never inspects `config.freeze_settings` at all:

```rust
fn configure_unfrozen_fields_only(&mut self, config: &BankConfigOpt) -> MarginfiResult {
    set_if_some!(self.config.deposit_limit, config.deposit_limit);
    set_if_some!(self.config.borrow_limit, config.borrow_limit);
    // weights didn't change so no validation is needed
    Ok(())
}
``` [5](#0-4) 

Because the `else` branch (the only branch that reaches `Bank::configure`, where the flag toggle logic lives) is permanently excluded once the flag is set, there is no reachable on-chain code path for `admin` to ever flip `FREEZE_SETTINGS` back to `false` through `lending_pool_configure_bank`. The other bank-config instructions (`lending_pool_configure_bank_oracle`, `lending_pool_set_fixed_oracle_price`, `lending_pool_configure_bank_interest_only`) all `panic!`/no-op when `FREEZE_SETTINGS` is set and never write to `flags` either [6](#0-5) [7](#0-6) . This matches the root cause pattern of the external report exactly: a state-mutation function whose guard/branch permanently precludes the state from being toggled back, rather than a require statement that only blocks the specific same-state transition.

Documentation and tests describe the flag as intentionally providing a "credible commitment" and explicitly state settings are frozen "so they cannot be changed again" [8](#0-7) [9](#0-8) , indicating the irreversibility is *by design* rather than an accidental bug — this weakens the case that it's a genuine vulnerability rather than an intended one-way commitment mechanism (analogous to a deliberate design decision, not a coding defect like the Solidity report).

### Impact Explanation
If `FREEZE_SETTINGS` is ever set on a bank (intentionally, or accidentally via a misconfigured `configure_bank` call bundling `freeze_settings: Some(true)` with other unwanted parameters), the group `admin` permanently loses the ability to adjust that bank's asset/liability weights, oracle configuration, interest rate curve, risk tier, or `total_asset_value_init_limit` for the lifetime of the bank. In a market-stress scenario (e.g. an oracle needs to be fixed/migrated, or weights need emergency tightening to prevent bad debt), the admin would have no on-chain remedy, which could result in unmitigated risk exposure or bad debt accumulation. However, since documentation strongly suggests this irreversibility is intentional (a "credible commitment"), the practical severity is closer to a "missing escape hatch" design limitation than a value-redirection or authorization-bypass exploit.

### Likelihood Explanation
Low-to-medium. `FREEZE_SETTINGS` can only be set by the group `admin` (a privileged role), so triggering the state requires privileged action, not an attacker. The concern here is a durable freeze/inconsistency with financial-risk implications, but it does not permit any authorization bypass or fund redirection — it only prevents future risk-parameter tuning by the entity that set the flag itself. Given the explicit design language ("credible commitment", "cannot be changed again"), it is plausible this is intended irreversible behavior rather than a bug the team would fix.

### Recommendation
If irreversibility is not intended, add an explicit unfreeze path: e.g., always route `config.freeze_settings` through `Bank::configure`'s flag-update logic even when the bank is currently frozen (independent of the "other fields frozen" branch), so `admin` can still clear `FREEZE_SETTINGS` while all other risk-affecting fields remain protected until unfrozen. If irreversibility is intended (matching the "credible commitment" design goal), this should be explicitly documented as a permanent, non-reversible flag (similar to `CLOSE_ENABLED_FLAG`, which is already documented as impossible to toggle after creation) so users and auditors don't mistake it for a bug.

### Proof of Concept
1. `admin` calls `lending_pool_configure_bank` with `BankConfigOpt { freeze_settings: Some(true), .. }` on an operational bank. `bank.get_flag(FREEZE_SETTINGS)` is `false` at this point, so the `else` branch runs `Bank::configure`, which sets the flag via `update_flag(true, FREEZE_SETTINGS)` [2](#0-1) .
2. `admin` later calls `lending_pool_configure_bank` again with `BankConfigOpt { freeze_settings: Some(false), .. }`, intending to unfreeze.
3. `configure_bank` sees `bank.get_flag(FREEZE_SETTINGS) == true`, so it calls `configure_unfrozen_fields_only` instead of `configure` [10](#0-9) .
4. `configure_unfrozen_fields_only` never reads `config.freeze_settings` and never calls `update_flag` [5](#0-4) ; the flag remains set. The test suite corroborates this behavior by asserting the flag is expected to persist (`assertBNEqual(bank.flags, FREEZE_SETTINGS + CLOSE_ENABLED_FLAG)`) after a freeze operation, with no test exercising a corresponding "unfreeze" call [9](#0-8) .
