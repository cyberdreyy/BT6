### Title
Legacy WebAPI trigger messages are forwarded to the entire DON with no gateway-side allowlist or rate-limit enforcement - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Shardus report describes a message handler (`broadcast_state_complete_data`) that accepts and acts on incoming data from an untrusted party without verifying it is legitimate before it is propagated and trusted by the rest of the network, enabling manipulation of state before consensus. The closest concrete, unprivileged-reachable analog in this repository is the gateway's `HandleLegacyUserMessage` handler, which explicitly forwards every externally-submitted HTTP trigger message to **all** members of a DON before any gateway-side authorization or throttling check is performed — a gap the code itself marks as an unimplemented `TODO`.

### Finding Description
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` is the entry point for external, unprivileged clients submitting Web API trigger requests to the gateway. After only parsing the payload and checking a `Timestamp`/staleness field, the code contains: [1](#0-0) 
followed immediately by unconditionally forwarding the (validated-signature-only) message to every DON member: [2](#0-1) 

The comment `// TODO: apply allowlist and rate-limiting here` confirms that the intended access-control/quota layer for this externally-reachable path has not been implemented at the gateway. `ValidatedRequestFromMessage` (used to build the outgoing request) performs no sender-authorization or quota check — it only checks that `MessageId` and `Method` are non-empty: [3](#0-2) 

Downstream, node-side enforcement of `allowedSenders`/`allowedTopics`/`rateLimiter` does exist in `processTrigger` [4](#0-3) , but that check happens independently on every node in the DON only *after* the unthrottled fan-out from the gateway. There is no gateway-level allowlist or per-sender/per-source rate limiting comparable to what exists for other paths in the same file (e.g. `nodeRateLimiter` used in `handleWebAPIOutgoingMessage`, `core/services/gateway/handlers/capabilities/handler.go:166`), and comparable to the allowlist infrastructure that exists elsewhere in the gateway (e.g. `core/capabilities/vault/allow_list_based_auth.go`).

### Impact Explanation
Because the gateway is the internet-facing ingress point and the allowlist/rate-limit step is explicitly unimplemented, any unauthenticated/unprivileged external caller can cause the gateway to broadcast an unbounded volume of trigger requests to every node in the DON. Each node still must independently parse, validate, and evaluate the request against its own registered-workflow allowlist, meaning workflow execution itself is not directly hijacked, but the missing quota/allowlist enforcement at the single choke point (the gateway) removes the intended defense-in-depth and allows resource exhaustion / request flooding of the entire DON membership from a single unprivileged HTTP client.

### Likelihood Explanation
High reachability: `HandleLegacyUserMessage` is invoked directly from externally facing gateway user-message handling for any client hitting the legacy Web API trigger path, requiring no privileges beyond producing a validly-signed `api.Message`. The gap is explicitly acknowledged in code via the `TODO` comment, indicating it is a known, not-yet-closed hole rather than a defense implemented elsewhere that merely isn't visible in this file.

### Recommendation
Implement the allowlist and rate-limiting check at the gateway, before `HandleLegacyUserMessage` forwards to `don.SendToNode` for all members, mirroring the pattern already used for `nodeRateLimiter` in `handleWebAPIOutgoingMessage` and the allowlist pattern in `core/capabilities/vault/allow_list_based_auth.go`. Reject/throttle requests from senders not present in a gateway-side allowlist and enforce a per-sender rate limit prior to fan-out to the DON.

### Proof of Concept
Not independently reproduced (no execution environment available); the finding is based on direct code inspection of the referenced `TODO` and the unconditional forwarding loop in `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:384-420`), which shows no allowlist/rate-limit call exists between message validation and fan-out to `don.SendToNode` for every DON member.

```go
// ValidatedRequestFromMessage converts a legacy Gateway Message to a JSON-RPC request
func ValidatedRequestFromMessage(msg *api.Message) (*jsonrpc.Request[json.RawMessage], error) {
	if msg == nil {
		return nil, errors.New("nil message")
	}
	if msg.Body.MessageId == "" {
		return nil, errors.New("message ID is empty")
	}
	if msg.Body.Method == "" {
		return nil, errors.New("method is empty")
	}
	params, err := json.Marshal(msg)
	if err != nil {
		return nil, fmt.Errorf("failed to marshal message: %w", err)
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageId,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	return req, nil
```

```go
		return fmt.Errorf("error wrapping payload %w", err)
	}
	topics := payload.Topics

	// empty topics is error for V1
	if len(topics) == 0 {
		return errors.New("empty Workflow Topics")
	}

	// workflows that have matched topics
	matchedWorkflows := 0
	// workflows that have matched topic and passed all checks
	fullyMatchedWorkflows := 0
	for _, trigger := range h.registeredWorkflows {
		for _, topic := range topics {
			if trigger.allowedTopics[topic] {
				matchedWorkflows++
				if !trigger.allowedSenders[sender.String()] {

					continue

					err = fmt.Errorf("request rate-limited for sender %s, messageID %s", sender.String(), body.MessageId)
```
