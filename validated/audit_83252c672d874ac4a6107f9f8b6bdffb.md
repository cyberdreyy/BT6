## Finding: Missing reinitialization guard allows anyone to re-run `new` on the lockup contract and seize custody of locked NEAR

### Title
Lockup contract's `new` initializer lacks a `state_exists` guard, allowing reinitialization and hijacking of locked funds - (File: `lockup/src/lib.rs`)

### Summary
This is a direct analog of the reported bug class ("initialize function ... can be invoked multiple times"). Every other contract in this repository explicitly protects its `#[init]` constructor with `assert!(!env::state_exists(), ...)`, but `lockup/src/lib.rs`'s `new` function omits this guard.

### Finding Description
Compare the `#[init]` functions across the repo. `staking-pool`, `staking-pool-factory`, `lockup-factory`, `multisig`, `voting`, and `whitelist` all guard against re-initialization: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The `lockup` contract's `new`, by contrast, has no such check anywhere in its body: [7](#0-6) 

Since the codebase's own convention (repeated in six other contracts) is that this guard must be added manually — implying the `near-sdk` version in use does not automatically prevent re-invocation of `#[init]` methods once state exists — its absence here means `new` on a live, funded lockup contract can be called again by anyone (function calls in NEAR have no implicit caller restriction unless the code checks `predecessor_account_id`, which `new` does not).

Re-invoking `new` lets a caller:
- Set `owner_account_id` to an attacker-controlled account (breaking the binding: "owner recorded" must equal "owner originally granted by the funder/foundation").
- Reset `lockup_information` with `lockup_duration = 0`, `lockup_timestamp = None`, `release_duration = None`, while `lockup_amount` is recomputed from the contract's current NEAR balance (`env::account_balance()`), i.e., all NEAR actually held becomes immediately "unlocked."
- Reset `vesting_information` to `VestingInformation::None`, erasing any foundation termination rights.

### Impact Explanation
This breaks the custody binding "a lockup's releasable amount versus its schedule" and enables "NEAR moved by a party not entitled to it" / "locked or unvested tokens released early" — both explicitly listed Critical impacts. After re-initialization, the attacker (now `owner_account_id`) can call the owner's transfer/withdraw methods to drain the entire NEAR balance held by the lockup contract, since the lockup and vesting schedules have been zeroed out.

### Likelihood Explanation
Any external account can attempt this by simply calling `new` with attacker-chosen arguments against a deployed, already-initialized lockup contract account — no privileged role, redeploy, or key compromise is required, unlike the original report's scenario which required a compromised implementation/ProxyAdmin. This makes the analog arguably easier to exploit than the original Solidity finding, since NEAR contracts have no proxy/implementation split — the deployed contract's public method table is directly callable.

### Recommendation
Add the same guard used elsewhere in the codebase to `lockup/src/lib.rs`'s `new`:
```rust
#[init]
pub fn new(...) -> Self {
    assert!(!env::state_exists(), "The contract is already initialized");
    ...
}
```

### Proof of Concept
1. Foundation/user funds and initializes `lockup1` via `new(...)` with real `owner_account_id`, vesting schedule, and NEAR balance.
2. Attacker calls:
```bash
near call lockup1 new '{
  "owner_account_id": "attacker.testnet",
  "lockup_duration": "0",
  "transfers_information": {"TransfersEnabled": {"transfers_timestamp": "0"}},
  "vesting_schedule": null,
  "staking_pool_whitelist_account_id": "staking-pool-whitelist",
  "foundation_account_id": null
}' --accountId attacker.testnet
```
Because `new` has no `state_exists` check, this succeeds, overwriting the struct: `owner_account_id = attacker.testnet`, `lockup_information.lockup_amount = env::account_balance()` (full current balance), no lockup/vesting restrictions.
3. Attacker calls the owner-only transfer method (defined in `lockup/src/owner.rs`) to withdraw all NEAR, since they are now the recognized owner and nothing restricts the amount. [7](#0-6)

        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,

        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),

        assert!(

            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information

            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),

            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),

            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
