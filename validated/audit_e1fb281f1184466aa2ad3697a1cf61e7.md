### Title
Withdraw confidential-transfer parser misattributes context-state account as `owner` when proof account count is insufficient - (File: transaction-status/src/parse_token/extension/confidential_transfer.rs)

### Summary
In the `ConfidentialTransferInstruction::Withdraw` arm of `parse_confidential_transfer_instruction`, the manual `offset` bookkeeping used to place `instructionsSysvar`, `equalityProofContextStateAccount`, and `rangeProofContextStateAccount` is gated by `offset < account_indexes.len().saturating_sub(1)`, which silently *skips* inserting a required context-state field when the supplied account list is one account short of what the (`equality_proof_instruction_offset == 0`, `range_proof_instruction_offset == 0`) combination actually requires. The subsequent unconditional call to `parse_signers(map, offset, ...)` then reads `account_keys[account_indexes[offset]]` and labels it `"owner"`, even though that slot is really the omitted range-proof context-state account. [1](#0-0) 

### Finding Description
`check_num_token_accounts(account_indexes, 4)` only enforces a floor of 4 accounts for `Withdraw`, but the real spl-token-2022 layout needs 5 accounts when both `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0` (account, mint, equality-proof-context, range-proof-context, owner). [2](#0-1) 

The parser increments `offset` starting at 2 and, for each of the sysvar/equality/range checks, only writes the field and advances `offset` if `offset < account_indexes.len().saturating_sub(1)`. This guard is meant to reserve the final slot for the owner/multisig signer(s), but it does so by *dropping* the range-proof field rather than failing, when `account_indexes.len() == 4`: [3](#0-2) 
- `has_sysvar` is `false` (both offsets are 0) → sysvar block skipped.
- Equality block: `offset(2) < len-1(3)` → true → writes `equalityProofContextStateAccount` from `account_indexes[2]`, `offset` becomes 3.
- Range block: `offset(3) < len-1(3)` → false → `rangeProofContextStateAccount` is never written, `offset` stays 3.
- `parse_signers(map, offset=3, ...)` then reads `account_keys[account_indexes[3]]` and inserts it into the JSON as `"owner"`.

But in an intended/real 5-account withdraw with both offsets == 0, index 3 in the account list is the range-proof context-state account, and index 4 is the real owner. By crafting a transaction where the Withdraw instruction supplies exactly 4 account indexes with both proof offsets set to 0, the attacker forces `parse_confidential_transfer_instruction` to emit the range-proof-context-state pubkey (or any arbitrary pubkey the attacker places at that slot) as `"owner"` in the parsed JSON, instead of correctly reporting a missing/mismatched account or the real authority. `parse_signers` performs no signer-flag or role validation — it blindly indexes based on the caller-supplied `offset`. This transaction does not need to execute successfully on-chain; `getTransaction(jsonParsed)` parses the instruction from the message regardless of execution outcome, so an attacker only needs to submit one transaction and issue one subsequent `getTransaction` call.

### Impact Explanation
This is a decoder misreporting bug scoped exactly to the case described: `getTransaction(jsonParsed)` returns an incorrect `"owner"` field (and omits `"rangeProofContextStateAccount"`) for an attacker-crafted confidential-transfer Withdraw instruction with an edge-case account count. This falls under "wrong … account data returned" / RPC decoder misreporting, matching the Agave bounty category for incorrect JSON-parsed transaction data. It does not crash the validator or affect consensus, but any off-chain consumer (explorer, wallet, indexer) relying on `getTransaction(jsonParsed)`'s `"owner"` field for this instruction type would attribute withdrawal authority to the wrong pubkey.

### Likelihood Explanation
Fully attacker-controlled and requires only a single, unprivileged, self-authored transaction: an attacker constructs a Withdraw instruction (`ConfidentialTransferInstruction::Withdraw`) with `equality_proof_instruction_offset = 0` and `range_proof_instruction_offset = 0` but supplies only 4 accounts instead of the 5 the real instruction encoding needs. The transaction can be submitted and does not need to succeed on-chain, and only one `getTransaction(jsonParsed)` call is needed to observe the misreported field. This is deterministic and 100% reproducible.

### Recommendation
Make `check_num_token_accounts` for `Withdraw` (and the analogous `Transfer`/`TransferWithFee` arms) compute the exact minimum required account count based on `has_sysvar`, `equality_proof_instruction_offset == 0`, and `range_proof_instruction_offset == 0`, rather than a fixed floor of 4. Alternatively, change the `offset < account_indexes.len().saturating_sub(1)` guards to hard errors (return `ParseInstructionError::InstructionNotParsable`) when an expected context-state slot cannot be filled, instead of silently skipping the field and letting `offset` drift into an account that belongs to a different logical field.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test module)
#[test]
fn test_withdraw_insufficient_accounts_misattributes_owner() {
    use solana_message::Message;

    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let equality_ctx = Pubkey::new_unique();
    let range_ctx_mislabeled_as_owner = Pubkey::new_unique(); // should be range ctx, gets called "owner"

    // Manually build raw instruction data for Withdraw with both offsets == 0,
    // but only supply 4 accounts (account, mint, equality_ctx, range_ctx) -- omitting
    // the real owner account that a correctly-formed 5-account instruction would include.
    let instruction_data = build_withdraw_instruction_data(/* eq_offset = 0, range_offset = 0, ... */);
    let account_indexes: &[u8] = &[0, 1, 2, 3]; // len == 4

    let account_keys = AccountKeys::new(
        &[account, mint, equality_ctx, range_ctx_mislabeled_as_owner],
        None,
    );

    let parsed = parse_confidential_transfer_instruction(
        &instruction_data,
        account_indexes,
        &account_keys,
    )
    .unwrap();

    // Bug: rangeProofContextStateAccount is silently dropped.
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());

    // Bug: the range-proof context account is misreported as "owner".
    assert_eq!(
        parsed.info["owner"],
        json!(range_ctx_mislabeled_as_owner.to_string())
    );
}
```
Expected (correct) behavior: parsing should either fail with `ParseInstructionError::InstructionNotParsable` (insufficient accounts for the proof-offset configuration) or correctly report `rangeProofContextStateAccount` and leave `owner` absent/unresolved — never label the range-proof context account as `owner`.
