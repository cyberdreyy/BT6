## Analysis: Precompile Signature Verification Cost Unbounded Relative to Compute Budget Metering

### Title
Precompile signature verification work is unmetered against compute-unit accounting, enabling per-transaction CPU amplification - (File: `precompiles/src/ed25519.rs`, `precompiles/src/secp256k1.rs`, `program-runtime/src/invoke_context.rs`)

### Summary
Agave's precompile programs (`ed25519`, `secp256k1`, `secp256r1`) loop over an attacker-controlled `num_signatures` byte and perform expensive cryptographic verification (`verify_strict`, ECDSA recovery) for each entry, but this work is executed via `InvokeContext::process_precompile` [1](#0-0)  completely outside the SBF compute-unit metering that governs ordinary program execution. Builtin/precompile instructions are only charged a fixed `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (3,000 CU) in the cost model regardless of actual work performed [2](#0-1) , and the fee/cost model charges only a flat per-signature cost (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) [3](#0-2)  derived purely from the `num_signatures` count byte, not from the size of the messages being hashed/verified.

### Finding Description
The `ed25519::verify` function loops `0..num_signatures` (up to 255, from a single `u8`), and for each iteration parses `signature`, `pubkey`, and a `message` slice whose length (`message_data_size`) is attacker-controlled up to `u16::MAX` (65,535 bytes), potentially referencing any instruction's data blob in the transaction, then performs a full `verify_strict` Ed25519 check on that message [4](#0-3) . The `secp256k1::verify` function follows the same pattern, performing a keccak hash over the referenced message and a full ECDSA public-key recovery for each of up to 255 entries [5](#0-4) .

Crucially, this loop executes with **no `compute_meter.consume_checked` calls at all** — contrast this with ordinary syscalls such as `SyscallHash`, which explicitly meter cost per byte/slice before performing work [6](#0-5) , and `SyscallBigModExp`, which charges the flat base cost "up front, before doing any translation or work that could fail without being paid for" [7](#0-6) . The precompile path bypasses this discipline entirely: `InvokeContext::process_message` special-cases `is_precompile(program_id)` and calls `process_precompile`, which never touches the compute meter [8](#0-7) [1](#0-0) .

The only throttle on this work is the flat, count-based cost-model accounting used for block-cost-limit and fee purposes [9](#0-8) , which is proportional to `num_signatures` alone (extracted from `instruction.data.first()`) [10](#0-9)  and does **not** account for the size of the messages each signature references. This is a class-level analog of the reported bug: a loop over an attacker-supplied array length with per-element expensive work and no metering/gas check tied to the actual cost of each element (message length), only to a count.

### Impact Explanation
A single submitted transaction with several ed25519/secp256k1 precompile instructions, each declaring the maximum `num_signatures` (255) with `message_data_size` fields pointing at large data blobs (up to the packet/instruction-data limits), forces the validator (both during leader block production and during replay by every downstream validator) to perform a disproportionate amount of real CPU-bound cryptographic work relative to the compute units/fees actually charged. Because this work is unmetered by the compute budget and its cost-model accounting is based only on signature *count* rather than *message size*, a transaction can be crafted whose fee/CU accounting looks cheap while its execution wall-time is expensive, degrading block-processing throughput for the leader and, since all validators must replay it identically, for the rest of the cluster. This is a resource-exhaustion / leader-cost-limit-bypass concern rather than a fund-movement bug.

### Likelihood Explanation
Reachable by any unprivileged transaction sender: the precompile programs are always enabled (`feature: None`) [11](#0-10) , require no special accounts or privileges, and the fields controlling loop count and message size are fully attacker-controlled instruction data. The bound is limited by per-transaction size limits (`PACKET_DATA_SIZE`/v1 message size) and `MAX_INSTRUCTION_TRACE_LENGTH` (64 instructions) [12](#0-11) , so the practical amplification factor is bounded, but I was not able to fully verify the exact numeric worst-case (e.g., the precise v1 `MAX_TRANSACTION_SIZE` constant) within the available tool budget — this would need to be confirmed with direct access to `solana_message::v1::MAX_TRANSACTION_SIZE` to compute the maximum achievable bytes-hashed-per-transaction.

### Recommendation
Meter precompile verification work against the compute budget proportionally to both `num_signatures` and the size of each referenced message (similar to how `SyscallHash` charges `hash_byte_cost` per byte), or otherwise incorporate message-size-based costing into the cost model's `SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST` and block-cost-limit calculations rather than a flat per-signature charge, so that the cost model and actual CPU work performed during `process_precompile` remain proportionate for the leader and cluster-wide replay.
