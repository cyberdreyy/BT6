### Title
Unprivileged lender can permanently pin `unscaledApr` at 0 and brick `stopEpoch` whenever APR is raised — open APR0 withdraw request makes `prepareStopEpochWithApr0` revert - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. Any KYC-passing lender can open an APR0 withdraw request (`requestWithdraw` while `unscaledApr == 0`), which sets `apr0User.principal` and increments `apr0TotalPrincipal` (lines 567–577). From then on, if the APR is ever raised above zero, every `stopEpoch` / `stopEpochWithDuration` call reverts, freezing the epoch state machine. The manager's only recovery is to set APR back to 0 — meaning a dust request grants an unprivileged user a veto over all APR increases for as long as they keep an open APR0 request, which they can renew each buffer window at negligible cost.

### Finding Description
The crafted input is `requestWithdraw(_amount, _user, _principal)` with a dust `_amount` during a zero-APR epoch — analogous to the crafted PDF crashing `FoFiType1C::convertToType1`, a small attacker-controlled value drives a shared code path into a hard revert.

- `requestWithdraw` routes to `_requestWithdrawApr0` when `unscaledApr == 0` and the pool isn't closed, setting `apr0Users[_user].principal` and `apr0TotalPrincipal` (IdleCreditVault.sol:285–286, 567–577).
- On `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`; the fast path at line 502 only short-circuits when `_principal == 0`. Otherwise line 506–508 enforces `if (unscaledApr != 0) revert NotAllowed()`.
- There is no settlement path before an APR change: `_settleApr0` only runs inside a user's `claimWithdrawRequest` and requires `principalEpoch < epochNumber`, i.e., it can never clear the bucket while the request epoch is still open (lines 545–565).
- `setAprs`/`setAprsWithBuffer` (lines 206–220) do not check `apr0TotalPrincipal`, so the manager can unknowingly enter a configuration where the next `stopEpoch` is guaranteed to revert.

Consequence: once APR is nonzero with an open APR0 request, `epochNumber` can never increment, `pendingWithdraws` are never funded, and `claimWithdrawRequest` reverts for every user via the `epochNumber <= lastWithdrawRequest[_user]` gate (line 326) — a queue-wide freeze until the manager restores APR to 0. The attacker can repeat the dust request every buffer period, indefinitely suppressing APR and epoch progression.

### Impact Explanation
Temporary freezing of all vault funds (claims and funded withdrawals blocked while `stopEpoch` reverts) plus forced zero yield: the protocol cannot raise `unscaledApr` above 0 while any open APR0 request exists. Quantified loss per blocked epoch: the full expected epoch interest on `getContractValue()` for all LPs, plus extended withdrawal delay for every pending and instant receipt. The attacker's cost is a dust deposit's management fee and capital lockup.

### Likelihood Explanation
Requires a zero-APR epoch (a supported mode — `testApr0WithdrawGetsInterestAtStopEpoch` exercises it) and a subsequent APR increase while the request is open. The revert is documented as intentional ("APR0 principal is only valid while APR is 0 for that request lifecycle"), so this is a designed guard rather than a rounding accident; the vulnerability is that an unprivileged user — not just sequencing around the manager — can arm the guard with a dust request, turning an admin sequencing check into a liveness veto. I was not able to fully trace `IdleCDOEpochVariant.stopEpoch`'s ordering to confirm whether `epochNumber` increments before or after the `prepareStopEpochWithApr0` call, which affects whether a failed stop leaves partial state; the freeze conclusion holds either way because the whole call reverts atomically.

### Recommendation
Prevent entering the bricking configuration rather than reverting inside `stopEpoch`:
- Revert in `setAprs`/`setAprsWithBuffer` when `apr0TotalPrincipal != 0` and the new `_unscaledApr != 0`, forcing APR changes to happen only in epochs with no open APR0 requests; or
- Provide a settlement path that rolls open APR0 principal into the settled bucket (with zero rate) when APR transitions to nonzero, so `stopEpoch` never depends on APR staying 0.

### Proof of Concept
Foundry fork PoC sketch (against a live credit vault deployment or `TestIdleCDOBase` harness):

```solidity
// 1. Pool is in buffer/running epoch with unscaledApr == 0.
vm.prank(manager);
strategy.setAprs(0, 0);

// 2. Attacker (KYC'd lender) deposits dust and requests withdraw.
uint256 dust = 1e6; // 1 USDC
vm.startPrank(attacker);
underlying.approve(address(idleCDO), dust);
idleCDO.depositAA(dust);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // routes to _requestWithdrawApr0
vm.stopPrank();
assertGt(strategy.apr0TotalPrincipal(), 0);

// 3. Manager raises APR for the next period (valid admin action).
vm.prank(manager);
strategy.setAprs(10e18, 10e18); // unscaledApr != 0 now

// 4. Epoch end reached; borrower repaid interest. stopEpoch always reverts.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(expectedInterest, 0);

// 5. All pending claimers are frozen: epochNumber never advances.
vm.expectRevert(NotAllowed.selector);
vm.prank(victim);
cdoEpoch.claimWithdrawRequest();

// 6. Attacker renews the veto each buffer period with another dust request.
```
