### Title
Dust APR0 withdraw request permanently bricks `stopEpoch` once APR is raised — epoch freeze / forced zero-yield griefing — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` routes a request into the `apr0Users`/`apr0TotalPrincipal` bucket whenever `unscaledApr == 0` at request time. `prepareStopEpochWithApr0` — called by the CDO inside every `stopEpoch` — reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged lender can deposit during a buffer phase while APR is 0, file a dust `requestWithdraw`, and if the manager subsequently raises the APR, every `stopEpoch` call reverts. Because the stuck `apr0TotalPrincipal` cannot be cleared by any unprivileged path, the epoch can never end while APR is nonzero — the pool is frozen, or the manager is forced to keep APR at 0, destroying all lender yield.

### Finding Description
The bug chain is entirely in `contracts/strategies/idle/IdleCreditVault.sol`:

1. `requestWithdraw` files the receipt into the APR0 bucket based on the APR **at request time**, not at settlement time:
   `if (unscaledApr == 0 && !isClosed) { _requestWithdrawApr0(_amount, _user); }` which does `_apr0User.principal += _amount; apr0TotalPrincipal += _amount;` (lines 285–286, 567–577).

2. `prepareStopEpochWithApr0` hard-reverts when the bucket is non-empty but APR has changed:
   ```solidity
   if (_principal == 0) { return (...); }
   if (unscaledApr != 0) { revert NotAllowed(); }
   ```
   (lines 502–508). This runs inside `IdleCDOEpochVariant.stopEpoch`, so the revert bubbles up and the epoch cannot close.

3. No escape hatch exists for the attacker-created bucket:
   - The user cannot self-clear it: `claimWithdrawRequest` → `_claimFundedWithdrawRequest` reverts while `epochNumber <= lastWithdrawRequest[_user]` (line 326), and `epochNumber` can only advance via the now-reverting `stopEpoch`. `_settleApr0` (lines 545–565) does not decrement `apr0TotalPrincipal` anyway.
   - `apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` (line 540, unreachable after the revert) or by `_clearWithdrawClaimForEpoch` with `_isClearingApr0`, which requires a default-finalized claim.

Result: a single dust request made while `unscaledApr == 0` turns any later APR increase into a permanent `stopEpoch` revert. The honest manager's only recovery is to set the APR back to 0 — forfeiting the epoch's interest for all LPs — and the attacker can repeat the dust request in every buffer phase, pinning the pool at APR 0 indefinitely.

### Impact Explanation
- **Temporary/permanent freezing**: while `unscaledApr != 0`, `stopEpoch` always reverts, so the epoch cannot close; borrower repayment, withdraw funding, and all claims are frozen. `epochEndDate` passes with no way to transition state.
- **Theft of yield**: to unfreeze, the manager must keep `unscaledApr == 0`, so every lender loses 100% of the epoch's interest for as long as the griefer repeats the attack (cost to attacker is only a dust deposit locked for one epoch, recoverable later via `claimWithdrawRequest` once settled).
- Broken invariant: one attacker receipt must not be able to veto the epoch state machine.

### Likelihood Explanation
Requires a pool epoch configured with `unscaledApr == 0` during a buffer period (a supported mode — `setAprs(0,0)` and the APR0 flow are explicitly tested). Any KYC'd lender can `requestWithdraw` dust. The trigger condition (manager later raising APR, or a scheduled APR change) is routine. The attacker only needs to front-run the APR change with a dust request each buffer phase, making the grief repeatable.

### Recommendation
Do not hard-revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Instead, treat stale APR0 principal as ordinary pending receipts: either (a) add `apr0TotalPrincipal` back into the normal `pendingWithdraws`/per-epoch receipt accounting and zero the APR0 bucket with no interest, or (b) settle it with zero interest (`apr0RateByEpoch[epochNumber] = 0`) so `stopEpoch` proceeds. Additionally, snapshot the APR decision at request time is fine, but the settlement path must be tolerant of APR changes. Allow a user/admin path to clear `apr0TotalPrincipal` proportional to settled/claimed principal so a stuck bucket can never deadlock `epochNumber` advancement.

### Proof of Concept
Foundry fork PoC sketch (against the harness style in `test/foundry/IdleCreditVault.t.sol`, e.g. `testApr0WithdrawGetsInterestAtStopEpoch`):

```solidity
function testApr0DustRequestBricksStopEpoch() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);   // APR = 0 epoch

    // Attacker: dust deposit + withdraw request while unscaledApr == 0
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1 * ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // Manager legitimately raises APR for next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(500, 0); // 5%

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest()
        + IdleCreditVault(address(strategy)).pendingWithdraws());

    // stopEpoch reverts forever while APR != 0 -> epoch frozen
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // Attacker cannot self-clear: claim reverts (epochNumber unchanged)
    vm.prank(attacker);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();

    // Only recovery: manager forced back to APR 0 -> all lenders get 0 interest
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
}
```

Key evidence in code: the APR0 routing at request time (`IdleCreditVault.sol:285`), the unconditional revert (`IdleCreditVault.sol:506-508`), the epoch-advance gate on claims (`IdleCreditVault.sol:326`), and the absence of any `apr0TotalPrincipal` decrement outside `prepareStopEpochWithApr0` (`IdleCreditVault.sol:540`) and default-claim clearing.
