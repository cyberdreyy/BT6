Confirmed: `createDstEscrow` in `contracts/BaseEscrowFactory.sol` accepts caller-supplied `dstImmutables` (including the `parameters` bytes that encode `protocolFeeAmount`/`integratorFeeAmount`) with **no validation** that `integratorFeeAmount + protocolFeeAmount < immutables.amount`, unlike the source path which explicitly checks `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();` in `_postInteraction`.

### Title
Underflow in `EscrowDst._withdraw` fee subtraction due to unvalidated fee immutables in `createDstEscrow` enables secret-theft / fund freezing - (File: contracts/EscrowDst.sol, contracts/BaseEscrowFactory.sol)

### Summary
`EscrowDst._withdraw` computes `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` without any bound check that the fees are less than `amount`. [1](#0-0) . Unlike the source-chain path, where `_postInteraction` explicitly guards `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();` [2](#0-1) , the destination path `createDstEscrow` accepts arbitrary caller-supplied `dstImmutables` (including the fee-encoding `parameters` field) with no equivalent check. [3](#0-2)  Fee values are read directly out of `immutables.parameters` via `integratorFeeAmountCd`/`protocolFeeAmountCd` in `ImmutablesLib.sol` with no cross-check against `immutables.amount`. [4](#0-3) 

### Finding Description
Any unprivileged caller (the taker/resolver depositing the destination side of the swap) can call `createDstEscrow` with a crafted `dstImmutables.parameters` where `integratorFeeAmount + protocolFeeAmount > immutables.amount`. Because `createDstEscrow` performs no sanity check on the fee values relative to `amount` (only checking `msg.value` for the native/safety-deposit amounts and the cancellation-timing constraint), the escrow deploys successfully and is fully funded. [3](#0-2) 

When the maker (or their relayer) later attempts to withdraw with the correct secret, `_withdraw` pays out the fee amounts first, then computes `immutables.amount - integratorFeeAmount - protocolFeeAmount`, which underflows and reverts unconditionally under Solidity 0.8 checked arithmetic. [1](#0-0)  This is identical in root cause to the reported `BurnContract.burn` issue: an unguarded subtraction between two independently-controlled values that can underflow.

Because Ethereum transaction calldata is public regardless of success/failure, the secret submitted in the reverting `withdraw`/`publicWithdraw` call is exposed on-chain the moment it is broadcast. The malicious taker (who set the corrupted fee parameters) can observe this leaked secret and immediately use it to withdraw from the **source** escrow (`EscrowSrc._withdrawTo`) to claim the maker's source-chain funds. [5](#0-4)  Once the destination cancellation timelock elapses, the same taker calls `cancel()` on the destination escrow to reclaim their own deposited destination tokens in full (cancel transfers `immutables.amount`, unaffected by the corrupted fee split). [6](#0-5)  The maker ends up with neither the destination funds (withdraw permanently reverts) nor recourse, while the taker recovers both sides of the swap.

### Impact Explanation
This is direct theft of the maker's user funds and permanent freezing of the destination escrow's payout path caused entirely by production contract logic (`createDstEscrow` and `EscrowDst._withdraw`), reachable by any unprivileged party performing destination escrow creation — a Smart Audit Pivot explicitly listed as in-scope. It matches the Critical bar (direct theft of user funds at rest, permanent freezing of funds) since the maker's destination claim is permanently and unconditionally blocked once such an escrow is created, and the taker can extract the leaked secret to steal the corresponding source-side funds.

### Likelihood Explanation
The attacker only needs to call the already-public `createDstEscrow` entry point with `parameters` bytes they fully control, requiring no privileged role, governance, or race condition beyond normal transaction ordering. The only precondition is that the maker (or an automated relayer acting for the maker) eventually attempts a withdrawal using the correct secret, which is the expected, guaranteed step in the atomic-swap happy path.

### Recommendation
In `createDstEscrow` (contracts/BaseEscrowFactory.sol), validate `integratorFeeAmount + protocolFeeAmount < dstImmutables.amount` (decoded via `ImmutablesLib`) before deploying the destination escrow, reverting with a dedicated error (mirroring the existing `InvalidFeeAmounts()` check used in `_postInteraction`) rather than allowing the invariant to be silently broken and discovered only as an underflow revert inside `_withdraw`.

### Proof of Concept
1. Malicious taker constructs `dstImmutables` for `createDstEscrow` with a valid `hashlock`/`amount`/`safetyDeposit`, but sets `parameters` such that `protocolFeeAmount + integratorFeeAmount > amount` (e.g., `protocolFeeAmount = amount`, `integratorFeeAmount = 1`).
2. Taker calls `createDstEscrow{value: safetyDeposit(+amount if native)}(dstImmutables, srcCancellationTimestamp)`; no check rejects the malformed fee parameters, so escrow deploys and is funded normally per `contracts/BaseEscrowFactory.sol:165-185`.
3. Maker/relayer, once finality passes, calls `withdraw(secret, immutables)`; `_withdraw` pays out the (bogus) fee legs then executes `immutables.amount - integratorFeeAmount - protocolFeeAmount`, which underflows and reverts (`contracts/EscrowDst.sol:84-93`) — but `secret` is now publicly visible in the failed transaction's calldata.
4. Taker extracts `secret` from the reverted transaction and calls `withdraw`/`withdrawTo` on the source escrow (`contracts/EscrowSrc.sol:111-119`) to claim the maker's source funds.
5. After `DstCancellation` timelock elapses, taker calls `cancel()` on the destination escrow (`contracts/EscrowDst.sol:64-73`) to reclaim the full `immutables.amount` they deposited, completing the theft — maker receives nothing on the destination side and lost their source funds.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function protocolFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x20) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(parameters.offset)
        }
    }

    /**
     * @notice Returns the integrator fee amount from the immutables (calldata version).
     * @param immutables The immutables to extract the fee from.
     * @return ret The integrator fee amount.
     */
    function integratorFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x40) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(add(parameters.offset, 0x20))
        }
    }
```
