### Title
Confirmations accepted without expiry allow a stale request to execute below the threshold that was active when it was confirmed - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
Like the external report's `encodeTransactionData()`, which has no deadline so a signed authorization stays valid indefinitely until executed, the NEAR multisig contracts' `add_request`/`confirm` flow stores confirmations with no expiry. `MultiSigRequestWithSigner` only carries `added_timestamp` for a 15-minute *deletion cooldown*, not an expiry that invalidates stale confirmations [1](#0-0) . Because `num_confirmations` is a single mutable field checked at confirm-time rather than snapshotted per request, a request can end up executing with fewer approvals than the threshold that was in force when the signers actually confirmed it.

### Finding Description
`confirm()` finalizes and executes a request purely by comparing the *current* `self.num_confirmations` against the confirmations already collected for that request: [2](#0-1) 

`SetNumConfirmations` is itself just another request type that mutates `self.num_confirmations` in place once it collects enough confirmations: [3](#0-2) 

Because requests never expire (no deadline field, only a `REQUEST_COOLDOWN` that blocks *early deletion*, not confirmation), an older pending request — e.g. a `Transfer` created and partially confirmed while `num_confirmations = 3` — can sit in `self.requests`/`self.confirmations` indefinitely. If a separate `SetNumConfirmations` request later lowers the threshold to `2`, the stale `Transfer` request, which already holds 2 confirmations gathered under the old 3-of-N policy, immediately satisfies `confirmations.len() as u32 + 1 >= self.num_confirmations` on the very next `confirm()` call from any remaining signer and executes — with fewer distinct approvals than the policy that was in effect when those signers agreed to approve it. The same structure exists in `multisig2/src/lib.rs`: `confirm()` [4](#0-3)  and `SetNumConfirmations` handling [5](#0-4)  both read the live `self.num_confirmations` rather than a value captured at request creation time.

This is the same root cause as the report: an approval (signed/confirmed data) that has no time-bound or context-bound validity remains combinable with future contract state, breaking the intended one-to-one binding between "threshold at confirmation time" and "threshold at execution time."

### Impact Explanation
This crosses the explicitly listed threshold boundary: **"a multisig request executed below threshold."** A `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, or `DeployContract` request approved by a minority of signers under the original higher threshold can be pushed through once the threshold is subsequently (and independently) lowered, without re-collecting confirmations from the full new quorum. This can move NEAR funds or grant access-key/membership control with fewer independent approvals than intended — a Critical-severity outcome per the custody-binding rules (funds moved, or a multisig request executed below threshold).

### Likelihood Explanation
Requires: (1) an outstanding, partially-confirmed request under the current threshold, and (2) a separate, independently confirmed `SetNumConfirmations` request lowering the threshold before the first is confirmed/deleted. Both are ordinary multisig operations reachable by existing signers using only the contract's public `add_request`/`confirm` methods — no owner/foundation privilege beyond being one of the existing multisig members is needed, and no redeploy or key compromise is required. Because there's no per-request expiry or snapshot of the threshold, this can occur unintentionally (e.g., legitimate governance to reduce signer count) or be engineered by a malicious/complicit subset of signers timing their confirmations around a threshold-change request.

### Recommendation
Snapshot `num_confirmations` on `MultiSigRequestWithSigner` at `add_request` time and compare confirmations against that stored value in `confirm()`, rather than against the live `self.num_confirmations`. Additionally, consider adding an explicit expiry (deadline) to requests so that stale, long-pending requests cannot be executed arbitrarily far in the future under a different threshold or membership set — mirroring the recommendation in the original report to add a deadline for validity of a transaction/authorization.

### Proof of Concept
1. Multisig deployed with `num_confirmations = 3`, members A, B, C, D.
2. A calls `add_request` for `Transfer{amount}` to some receiver → `request_id = 0`.
3. B calls `confirm(0)` → 1 confirmation stored (added by A via `add_request_and_confirm` would be 2; assume A also confirmed at creation via `add_request_and_confirm`, giving 2 confirmations total).
4. Separately, C and D (plus one more confirmer) approve a `SetNumConfirmations{num_confirmations: 2}` request, which executes and sets `self.num_confirmations = 2`.
5. Any single remaining signer (even one who already confirmed, or a fresh confirmation is not even required) calls `confirm(0)` again is unnecessary — the existing 2 confirmations already satisfy `confirmations.len() as u32 + 1 >= self.num_confirmations` (`2 + 1 >= 2`), so the *next* `confirm` call from any signer not yet in the set finalizes and executes the `Transfer` with only 2 approvals, even though it was created and originally approved under a 3-of-N policy.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
