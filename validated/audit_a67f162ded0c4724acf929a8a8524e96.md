### Title
External-Initiator credentials bypass job-ownership checks in `PipelineRunsController.Create`, allowing runs of arbitrary jobs - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Create` intends to allow only authenticated dashboard/API-token *users* to trigger a job run by integer job ID, explicitly commenting "EIs not allowed." However, the gate it uses, `auth.GetAuthenticatedUser`, only checks for the presence of a `*clsessions.User` object in the Gin context, and `auth.AuthenticateExternalInitiator` unconditionally injects such an object (`Role: UserRoleRun`) for every successfully authenticated External Initiator. This makes the `isUser` check pass for EI credentials as well, letting any valid EI access-key/secret pair trigger `RunJobV2` for any arbitrary job ID, with no verification that the job is a webhook job or is associated with that EI at all.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is mounted with `auth.Authenticate(..., auth.AuthenticateBySession, auth.AuthenticateByToken, auth.AuthenticateExternalInitiator)` and wrapped by `auth.RequiresRunRole`. `AuthenticateExternalInitiator` validates the EI's access-key/secret via `bridges.AuthenticateExternalInitiator` [1](#0-0)  and, regardless of which job/bridge that EI is tied to, always sets:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [2](#0-1) 

`RequiresRunRole` only rejects `UserRoleView`, so `UserRoleRun` (set for every EI) passes through [3](#0-2) .

Inside `Create`, the code does:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [4](#0-3) 

`GetAuthenticatedUser` merely checks whether `SessionUserKey` exists and type-asserts to `*clsessions.User`; it does not check `SessionExternalInitiatorKey` is absent, or that the job ID belongs to that EI's registered webhook/bridge:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
	user, ok := obj.(*clsessions.User)
	return user, ok
}
``` [5](#0-4) 

Because `AuthenticateExternalInitiator` always populates `SessionUserKey`, `isUser` is `true` for EI-authenticated requests too — contradicting the inline comment stating EIs are not allowed. The handler then parses the raw `:ID` path parameter as an `int32` job ID with no cross-check against the authenticated EI's own job/bridge association, and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly.

### Impact Explanation
Any holder of a valid External Initiator access-key/secret pair (a low-privilege, narrowly-scoped credential meant only to trigger its own registered webhook job) can trigger a pipeline run for **any** job ID in the node — including jobs owned/managed by other EIs or purely UI-managed jobs unrelated to that EI. This is unauthorized job execution/state mutation across tenants/credentials, matching the "unauthorized job run or fund movement" bounty impact class, since job runs can include tasks that move funds, write on-chain transactions, or leak task inputs/outputs via the pipeline run result.

### Likelihood Explanation
Preconditions: attacker needs only a legitimately-issued EI access-key/secret for any external initiator on the node (a credential many integrations hold, not admin/session credentials). The exploit path is fully deterministic and reproducible — no additional bugs or side channels are required. The vulnerability is triggerable in every EI's valid session, every time.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests where the identity was established solely via `AuthenticateExternalInitiator`, e.g., by checking `auth.GetAuthenticatedExternalInitiator(c)` returns `ok == false` before treating the caller as a "user" allowed to run arbitrary job IDs, or by introducing a distinct role/context key for EI-derived sessions instead of reusing `SessionUserKey`/`clsessions.User`. Additionally, if EIs are meant to trigger runs at all, bind the check to verify the target job ID/webhook is actually associated with the authenticated EI.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/pipeline_runs_controller_test.go`):
1. Create two jobs: Job-A a webhook job registered/associated with External Initiator "EI-A", and Job-B an unrelated job (e.g., created via UI/no EI, or associated with EI-B).
2. Register EI-A via the EI creation endpoint, capturing its `AccessKey`/`Secret`.
3. Issue `POST /v2/jobs/<Job-B ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-A's credentials.
4. Assert current (vulnerable) behavior: response is `200/201` and `prc.App.RunJobV2` is invoked with Job-B's ID (verifiable via a mock `chainlink.Application` asserting `RunJobV2` called with Job-B's ID), despite EI-A having no relationship to Job-B.
5. Expected secure behavior: response should be `401/403` because EI-A is not authorized to trigger runs on Job-B.

	ctx := c.Request.Context()

	}

		return err
	}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
