### Title
Any authenticated External Initiator can trigger arbitrary job runs node-wide due to unscoped role assignment - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Finding Description
`AuthenticateExternalInitiator` authenticates the EI's access key/secret against the DB record, then unconditionally injects a synthetic session user into the gin context: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [1](#0-0) . This object carries no reference to which `ExternalInitiator` record authenticated the request, and every EI — regardless of its intended integration — is mapped to the identical `UserRoleRun` role.

`PipelineRunsController.Create` gates execution on `_, isUser := auth.GetAuthenticatedUser(c)` with a comment claiming "only users are allowed to run jobs using int IDs - EIs not allowed" [2](#0-1) . However, `GetAuthenticatedUser` simply reads whatever object was stored under `SessionUserKey` [3](#0-2) , and since `AuthenticateExternalInitiator` stores a fake `*clsessions.User` there too, `isUser` evaluates to `true` for EI-authenticated requests exactly the same as for real users. The comment/intent that "EIs not allowed" is therefore not enforced by the code — any successfully authenticated EI reaches the `RunJobV2(ctx, jobID, nil)` branch and can trigger any job by supplying an arbitrary numeric job ID in the URL path (`POST /v2/jobs/:ID/runs`), since there is no per-EI job binding anywhere in the `ExternalInitiator` model [4](#0-3)  or in the auth/role check path.

### Impact Explanation
Because role assignment is identical for all EIs and carries no job-level scope, a credential pair issued for one narrow integration (e.g., "EI-1" meant to trigger only Job A) can be used to invoke `Create`/`RunJobV2` for any other job ID on the node ("Job B", "Job C", etc.), including jobs it was never intended to access. This matches Chainlink's "unauthorized job run" impact class — an attacker holding a legitimately-issued but narrowly-scoped EI credential can trigger arbitrary jobs node-wide, potentially causing unwanted on-chain transactions, resource exhaustion, or interference with unrelated integrations.

### Likelihood Explanation
The only precondition is possession of any valid EI access key/secret pair — no admin/operator access, no additional privilege. This is a realistic scenario since EI credentials are commonly distributed to third-party external services; a compromised or malicious holder of any single EI credential can immediately exploit this by sending `POST /v2/jobs/:anyJobID/runs` with a numeric job ID belonging to a different job. The attack is trivially repeatable and requires no timing or race conditions.

### Recommendation
Bind the synthetic run-role identity created in `AuthenticateExternalInitiator` to the specific `ExternalInitiator` record (e.g., store the EI's ID/name alongside the role, or a distinct context key indicating "this is EI X"), and have `PipelineRunsController.Create` (and `RunJobV2`) verify that the job being triggered is actually associated with/authorized for that specific EI, rather than treating `isUser==true` as sufficient authorization for any numeric job ID. Alternatively, remove the misleading assumption that EIs are excluded from the `isUser` branch and implement explicit per-EI job-to-EI mapping enforcement before invoking `RunJobV2`.

### Proof of Concept
1. Create two External Initiators, `EI-1` and `EI-2`, via the EI creation endpoint, and create two jobs, `JobA` (int ID `1`) and `JobB` (int ID `2`), with no formal binding between EIs and jobs (since none exists in the schema).
2. Authenticate as `EI-1` using its access key/secret headers (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` equivalent per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`).
3. Send `POST /v2/jobs/2/runs` (Job B, "intended" only for EI-2) using EI-1's credentials.
4. Assert: request succeeds with `201`/`200` and a valid `pipelineRun` resource is returned for Job B — confirming `isUser` was true for the EI session and `RunJobV2(ctx, 2, nil)` executed despite EI-1 having no relation to Job B.
5. Add a unit test on `auth.AuthenticateExternalInitiator` + `auth.GetAuthenticatedUser` confirming that the returned `*clsessions.User` object is indistinguishable (same `Role`, no identifying EI reference) regardless of which EI authenticated, demonstrating the root cause.
