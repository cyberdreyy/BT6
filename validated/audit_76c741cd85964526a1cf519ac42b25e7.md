### Title
Stale confirmations from removed multisig members are not purged, allowing a request to execute below the live confirmation threshold — (`multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes execution purely by counting the size of the `confirmations` set for a request against `num_confirmations`, without verifying that every entry in that set still belongs to a currently active member. `delete_member` (v2) / the `DeleteKey` action (v1) only purges confirmations tied to requests *created* by the removed member; it never scrubs that member's confirmation entries from *other members'* pending requests. A member removed after confirming a still-pending request leaves a "phantom" confirmation behind that continues to count toward the threshold.

### Finding Description
The invariant the multisig is supposed to guarantee is: **a request executes only once `num_confirmations` *live* members have approved it** — i.e. `count(confirmations ∩ current_members) >= num_confirmations`.

The actual check in `confirm` only enforces `confirmations.len() >= num_confirmations`, with no re-validation against `self.members`: [1](#0-0) 

`delete_member` removes a member from `self.members` and purges only the requests *that member itself created* (`r.member == member`), plus that member's own `num_requests_pk` counter. It does not iterate `self.confirmations` to strip the deleted member's string identity from confirmation sets on requests created by *other* members: [2](#0-1) 

The same gap exists in the original `multisig` contract's `DeleteKey` action, which likewise only clears confirmations for requests signed by the deleted key, not confirmations that key gave elsewhere: [3](#0-2) 

This is structurally the same class of bug as the reported `ArmadaGovernor::resolveRatification` issue: an identity is bound into state at action time (a confirmation, analogous to the veto `proposer` field) and a later mutation of a different, separately-mutable surface (member list, analogous to the `securityCouncil` slot) is not reconciled against it, so a stale/departed identity's influence silently persists and lets a threshold be satisfied that should not be.

### Impact Explanation
An attacker who controls, or a legitimate governance flow that produces, a member removal event can retroactively "launder" a departed member's confirmation into satisfying the threshold on an unrelated, still-pending request (e.g., a `Transfer`). Concretely, with members A, B, C, D and `num_confirmations = 3`:
1. A creates+confirms a `Transfer` request → confirmations = {A}.
2. B confirms → confirmations = {A, B} (2/3, pending).
3. A `DeleteMember { B }` request is separately confirmed by A, C, D and executes — B is removed from `self.members`, but the transfer request from step 1 was created by A, not B, so its confirmations set `{A, B}` is untouched.
4. C confirms the transfer request → `confirmations.len() == 3 >= num_confirmations`, and `execute_request` fires the `Transfer`.

The transfer executes with only 2 genuinely live confirmers (A, C) instead of the required 3 — a multisig request executed below its intended live-member threshold, directly moving NEAR out of the account under insufficient authorization. This matches the Critical impact bar: "a multisig request executed below threshold."

### Likelihood Explanation
This requires no privileged capability beyond being one of several existing multisig members (i.e., an insider/subset of legitimate signers), and no unusual timing beyond an ordinary member-rotation event overlapping a pending request — a routine operational sequence (rotate a key/account while another request is mid-flight) rather than a contrived edge case. Any multisig that rotates members (key rotation, offboarding) while unrelated requests are open is exposed.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate all pending requests' confirmation sets and remove the departing member's identity from each, or alternatively re-validate every confirmation in `confirm`/`execute_request` against current `self.members` membership before counting it toward `num_confirmations`. The latter (filter confirmations by live membership at count time) is more robust since it also self-heals confirmation sets not otherwise touched by removal.

### Proof of Concept
Extend `multisig2/src/lib.rs`'s test module with a scenario mirroring the steps above: create members `A,B,C,D` with `num_confirmations=3`; have `A` `add_request_and_confirm` a `Transfer`; have `B` `confirm` it (2/3 pending); have `A,C,D` confirm a separate `DeleteMember{B}` request to execute and remove `B`; then have `C` call `confirm` on the original transfer request and observe it executes (`self.requests.len() == 0` and the transfer promise fires) despite only `A` and `C` being live confirming members at execution time — i.e., `get_confirmations(request_id)` at time of execution contained `B`, who was no longer in `self.members`, and `delete_member`'s cleanup path (`multisig2/src/lib.rs:361-371`) never touched that entry.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
