### Title
Bridge outgoing token/URL secret disclosed to any authenticated user (including view-only) via unauthorized GET - (File: core/web/bridge_types_controller.go)

### Summary
`BridgeTypesController.Show` and `BridgeTypesController.Index` are registered without any `auth.RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper, unlike `Create`, `Update`, and `Destroy` which are gated with `auth.RequiresEditRole`. Both handlers return a `presenters.BridgeResource` that includes the `OutgoingToken` field unconditionally (not redacted), so any authenticated session — including a `UserRoleView` session — can retrieve the bridge's secret outgoing token and URL.

### Finding Description
The route table in `core/web/router.go` registers:
```go
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
authv2.GET("/bridge_types/:BridgeName", bt.Show)
authv2.PATCH("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Update))
authv2.DELETE("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Destroy))
``` [1](#0-0) 

`bt.Show`/`bt.Index` sit only behind `authv2`, which requires `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)` — i.e. any valid, authenticated user of any role, including `UserRoleView`. [2](#0-1) 

`Show` fetches the bridge and serializes it via `presenters.NewBridgeResource`:
```go
bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
...
jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
``` [3](#0-2) 

`presenters.BridgeResource` includes `OutgoingToken` with no `omitempty`/redaction and `NewBridgeResource` always populates it from the DB record:
```go
OutgoingToken          string       `json:"outgoingToken"`
...
OutgoingToken:          b.OutgoingToken,
``` [4](#0-3) 

There is no role check inside `Show` itself (`RequiresRunRole`/`RequiresEditRole` are only asserted by the router wrapper, and `auth.go` shows `RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` explicitly abort for `UserRoleView` or lower roles). [5](#0-4) 
Because `Show`/`Index` are not wrapped by any such function, a `UserRoleView` session passes straight through to the handler and gets the full `BridgeResource` including `OutgoingToken`.

The existing test `TestBridgeController_Show` confirms the field is returned in the response and only checks name/URL/confirmations, not that outgoingToken is present — but per `NewBridgeResource`, it is included in the JSON payload regardless of caller role. [6](#0-5) 

Root cause: an authorization-gate inconsistency between mutating bridge endpoints (edit-role gated) and read endpoints (`Show`/`Index`, only base-authenticated), combined with a presenter that does not redact the `OutgoingToken` secret for lower-privileged callers.

### Impact Explanation
`OutgoingToken` is the shared secret the node uses to authenticate itself to an external adapter/bridge when it forwards a request (Chainlink's "Secrets never leave the node" principle for bridge credentials). A minimally-privileged `UserRoleView` account (or an API token scoped only for viewing) can read this secret for every configured bridge via `GET /v2/bridge_types/:BridgeName` or `GET /v2/bridge_types`, and use it to impersonate the node when calling the external adapter directly, or to correlate/replay bridge traffic. This matches the "sensitive information disclosure / secret disclosure" bounty class, since a low-privilege authenticated principal obtains a credential intended to be restricted to edit/admin-level operators.

### Likelihood Explanation
- Requires only a valid, authenticated session or API token with the lowest role (`UserRoleView`) — no elevated privilege needed.
- Trivially repeatable: any bridge created on the node can be queried by name or listed via the paginated index.
- No additional conditions (feature flags, config) are needed; this is standard routing behavior in `v2Routes`.

### Recommendation
- Gate `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` with at least `auth.RequiresRunRole` (or `RequiresEditRole`, matching the write endpoints) in `core/web/router.go`.
- Alternatively/additionally, redact `OutgoingToken` in `presenters.NewBridgeResource` for `Index`/`Show` responses unless the caller has edit/admin role (mirror how `IncomingToken` is only ever set at creation time), so the secret is never serialized on read paths regardless of role-gating changes.

### Proof of Concept
Go handler-level integration test (extends `TestBridgeController_Show` in `core/web/bridge_types_controller_test.go`):
1. Start app, create a bridge via `app.BridgeORM().CreateBridgeType` with an `OutgoingToken` set.
2. Create an HTTP client authenticated as a `UserRoleView` user/session (use `cltest.NewApplication` helpers or `app.NewHTTPClient` with a view-role user, as done in other role-based tests e.g. `auth_test.go`).
3. `GET /v2/bridge_types/{bridgeName}` with the view-role session.
4. Assert response status is `200 OK` (not `401`/`403`) and `resp.data.attributes.outgoingToken` equals the created bridge's `OutgoingToken` (non-empty, unredacted) — demonstrating the secret is disclosed to a view-only role.
5. Repeat via `GET /v2/bridge_types` (Index) with the same view-role session and assert the outgoing token appears in the listed bridge's attributes.
6. Expected (secure) behavior: request should be `401/403 Forbidden` for view-role, or the JSON response's `outgoingToken` field should be omitted/redacted.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func TestBridgeController_Show(t *testing.T) {
	t.Parallel()

	app := cltest.NewApplication(t)
	require.NoError(t, app.Start(t.Context()))

	client := app.NewHTTPClient(nil)

	bt := &bridges.BridgeType{
		Name:          bridges.MustParseBridgeName(testutils.RandomizeName("showbridge")),
		URL:           cltest.WebURL(t, "https://testing.com/bridges"),
		Confirmations: 0,
	}
	ctx := t.Context()
	require.NoError(t, app.BridgeORM().CreateBridgeType(ctx, bt))

	resp, cleanup := client.Get("/v2/bridge_types/" + bt.Name.String())
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusOK, resp.StatusCode, "Response should be successful")

	var resource presenters.BridgeResource
	cltest.ParseJSONAPIResponse(t, resp, &resource)
	assert.Equal(t, bt.Name.String(), resource.Name, "should have the same name")
	assert.Equal(t, bt.URL.String(), resource.URL, "should have the same URL")
	assert.Equal(t, bt.Confirmations, resource.Confirmations, "should have the same Confirmations")

	resp, cleanup = client.Get("/v2/bridge_types/nosuchbridge")
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusNotFound, resp.StatusCode, "Response should be 404")
}
