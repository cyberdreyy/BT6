### Title
Global (non-per-sender) `maxCacheSize` enforcement in `requestCache.NewRequest` allows single sender to exhaust the shared request cache and deny service to other gateway clients - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces `maxCacheSize` as a single global counter (`len(c.cache) >= int(c.maxCacheSize)`) shared across all senders, even though cache entries are keyed by `globalId{sender, id}`. A single low-privilege sender submitting `maxCacheSize` distinct `MessageId`s in a burst can fill the entire cache and cause `NewRequest` to return `"request cache is full"` for every other sender until entries expire via timeout.

### Finding Description
In `core/services/gateway/handlers/common/requestcache.go`, `NewRequest` computes the cache key as `key := globalId{request.Body.Sender, request.Body.MessageId}` [1](#0-0)  demonstrating per-sender identity is tracked, but the size check that gates admission is purely global: `if len(c.cache) >= int(c.maxCacheSize) { return errors.New("request cache is full") }` [2](#0-1) . There is no accounting of how many entries belong to a given `sender`, so nothing stops one sender from occupying the entire quota. The existing test `TestRequestCache_MaxSize` confirms the semantics: after two `NewRequest` calls from the *same* sender fill a `maxCacheSize=2` cache, a third call fails with an error [3](#0-2) ; the same mechanism would reject a *different* sender's request once the cache is full, since the check makes no distinction based on `request.Body.Sender`.

Entries are only removed on timeout (`c.timeout`) or once `ProcessResponse` aggregates a final response and calls `deleteAndSendOnce` [4](#0-3) , so an attacker can keep the cache saturated for up to `timeout` per burst, repeating indefinitely.

This class alone (`requestcache.go`) does not include any per-sender admission control or rate limiting — that responsibility is expected to live in the calling handler. Some callers do apply per-sender/global rate limiters before requests reach `NewRequest` (e.g. `checkRateLimit`/`userRateLimiter` in `http_trigger_handler.go` and `incomingRateLimiter`/`AllowVerbose` in `outgoing_connector_handler.go`), but these are separate, handler-specific mitigations layered on top and not a property of `requestCache` itself, and it is not guaranteed every consumer of `NewRequestCache` applies an equivalent per-sender gate before calling `NewRequest`.

### Impact Explanation
Impact is a denial of shared resource within a single gateway handler instance: once one sender fills the shared cache up to `maxCacheSize`, every other sender's `NewRequest` calls fail with `"request cache is full"` until entries age out via `timeout` or complete via `ProcessResponse`. This matches a service-disruption / DoS impact class (temporary denial of service to legitimate users of a shared gateway resource), scoped to whichever handler instance uses this cache.

### Likelihood Explanation
Feasibility depends entirely on whether the specific caller of `NewRequestCache` applies its own effective per-sender rate limiting/quota ahead of `NewRequest`. Where such limiting exists (as seen in some handlers), practical exploitability is reduced; where it doesn't, any gateway-reachable client able to submit distinct signed `MessageId`s in a burst can trigger this with low privilege and full repeatability, since the flaw is structural in `requestCache` itself, not incidental.

### Recommendation
Track and enforce cache occupancy per-sender in addition to (or instead of) the global cap — e.g., maintain a `map[string]int` of per-sender counts alongside `cache`, and reject/backpressure a sender exceeding its own quota, independent of the global fill level. Alternatively/complementarily, ensure every consumer of `NewRequestCache` enforces a per-sender admission limit before calling `NewRequest`.

### Proof of Concept
1. In `requestcache_test.go`, create `cache := common.NewRequestCache[requestState](time.Hour, N)` with a small `N` (e.g. 5).
2. From `senderA`, call `cache.NewRequest` `N` times with distinct `MessageId`s, asserting `require.NoError` each time.
3. From `senderB`, call `cache.NewRequest` once with a fresh `MessageId`, and assert `require.Error(t, err)` with message `"request cache is full"`.
4. This demonstrates that `senderB`'s request is rejected purely because `senderA` filled the shared cache, proving lack of per-sender isolation.

```go
func (c *requestCache[T]) deleteAndSendOnce(key globalId, callbackResponse handlers.UserCallbackPayload) error {
	c.mu.Lock()
	entry, deleted := c.cache[key]
	delete(c.cache, key)
	c.mu.Unlock()
	if deleted {
		entry.timeoutTimer.Stop()
		return entry.SendResponse(callbackResponse)
	}

	return nil
```

```go
func TestRequestCache_MaxSize(t *testing.T) {
	t.Parallel()

	cache := common.NewRequestCache[requestState](time.Hour, 2)
	callback := common.NewCallback()
	lggr := logger.Test(t)
	initialState := &requestState{}

	req := &api.Message{Body: api.MessageBody{MessageId: "aa", Sender: "0x1234"}}
	require.NoError(t, cache.NewRequest(lggr, req, callback, initialState))

	req.Body.MessageId = "bb"
	require.NoError(t, cache.NewRequest(lggr, req, callback, initialState))

	req.Body.MessageId = "cc"
	require.Error(t, cache.NewRequest(lggr, req, callback, initialState))
}
```
