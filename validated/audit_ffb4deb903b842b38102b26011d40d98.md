### Title
Non-constant-time session token comparison in `Session.withAuthorization` enables timing side-channel attack - ([File: session/session.go])

### Summary
`Session.withAuthorization` in `session/session.go` compares the session token using the Go `!=` string operator instead of a constant-time comparison. Note: the function actually lives in `session/session.go` (not `session/proxy/proxy.go` as stated in the question), but it is the exact gate that protects both the `/proxy/` and `/exec` endpoints wired up in `setMux`. The comparison short-circuits on the first mismatching byte, which is a textbook timing side-channel (CWE-208), and no `crypto/subtle.ConstantTimeCompare` or `hmac.Equal` is used anywhere in this codebase.

### Finding Description
`withAuthorization` performs the check: [1](#0-0) 
`if s.Token != r.Header.Get("Authorization") { ... }`. Go's built-in string equality compares byte-by-byte and returns as soon as a mismatch is found, so the number of comparison operations (and thus, in principle, execution time) grows with the length of the correct prefix shared between the guessed token and `s.Token`.

This handler wraps both session endpoints: [2](#0-1) 
`s.mux.Handle(s.Endpoint+"/proxy/", s.withAuthorization(...))` and `s.mux.Handle(s.Endpoint+"/exec", s.withAuthorization(...))`, and these are reachable over the network via the TLS listener set up in `session/server.go`'s `NewServer`/`Start`, which forwards every request to `session.Handler().ServeHTTP(w, r)`: [3](#0-2) 

The session `Token` is a 32-character random UUID string generated by `generateToken`: [4](#0-3) 
A grep across the repository confirms there is no usage of `crypto/subtle.ConstantTimeCompare` or `hmac.Equal` anywhere — the token check is the only comparison and it is non-constant-time.

### Impact Explanation
If timing differences were measurable and statistically distinguishable across the network, an attacker who can send many `/proxy/` or `/exec` requests to a victim's session `Endpoint` could theoretically infer correct-prefix length information about `s.Token` and iteratively narrow down the 32-character token, eventually forging a valid `Authorization` header and hijacking that job's terminal/proxy session (full session/terminal hijack of another job, matching the scoped impact).

### Likelihood Explanation
Exploitability in practice is low-to-theoretical: Go's native `==`/`!=` string comparison on short (32-byte) strings executes in a handful of nanoseconds per byte, and this signal must survive real network jitter, TLS overhead, goroutine scheduling, and HTTP framing before it becomes distinguishable at internet scale. Extracting a usable signal typically requires an attacker with very high request volume, low and stable network jitter (e.g., co-located attacker), and many repeated samples per candidate prefix — conditions that are hard to guarantee against a general internet-reachable GitLab Runner session server, but not impossible for a well-resourced, patient attacker on a low-latency path to the runner. The underlying code pattern is nonetheless a genuine, currently-unmitigated weakness: there is no constant-time comparison anywhere in the code path, so the theoretical attack surface exists exactly as described.

### Recommendation
Replace the direct string comparison with a constant-time comparison, e.g.:
```go
import "crypto/subtle"
...
if subtle.ConstantTimeCompare([]byte(s.Token), []byte(r.Header.Get("Authorization"))) != 1 {
    ...
}
```
Since both operands are fixed-length UUID strings, `subtle.ConstantTimeCompare` (or hashing both sides with HMAC and comparing digests via `hmac.Equal`) removes the length/prefix-dependent timing signal.

### Proof of Concept
Go unit test plan (statistical timing-differential test) in `session/session_test.go`:
1. Create a `Session` with a fixed 32-byte `Token`.
2. Build two sets of candidate `Authorization` values: "near-miss" tokens sharing an increasing correct-prefix length (1, 8, 16, 24, 31 bytes) with `s.Token`, and a control set of same-length but fully-random tokens.
3. For each candidate, issue N (e.g., 10,000) repeated HTTP requests directly to `session.Handler()` via `httptest.NewRecorder()`/`httptest.NewServer`, recording per-request latency with `time.Now()` before/after `ServeHTTP`.
4. Assert (via linear regression or Mann-Whitney U test) whether mean/median latency is statistically correlated with prefix length in the current `!=`-based implementation, and assert that the same test shows no significant correlation after switching the comparison to `subtle.ConstantTimeCompare`.
5. Expected result under current code: some (possibly small) latency correlation with prefix length, absent after the fix — demonstrating the constant-time property is restored.

```go
func (s *Session) withAuthorization(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		logger := s.log.WithField("uri", r.RequestURI)
		logger.Debug("Endpoint session request")

		if s.Token != r.Header.Get("Authorization") {
			logger.Error("Authorization header is not valid")
			http.Error(w, http.StatusText(http.StatusUnauthorized), http.StatusUnauthorized)
			return
		}

		next.ServeHTTP(w, r)
	})
}
```
