### Title
`getAccountInfo`/`getMultipleAccounts` with `encoding=jsonParsed` silently ignores client-specified `dataSlice` for SPL-token-owned accounts, returning full unsliced binary on parse failure - ([File: rpc/src/rpc.rs])

### Summary
`get_encoded_account` in `rpc/src/rpc.rs` routes any account whose owner satisfies `is_known_spl_token_id` to `get_parsed_token_account` whenever `encoding == JsonParsed`, and never forwards the caller's `data_slice` to that function. When the account's additional mint data cannot be resolved (e.g., an orphaned/forged token account whose mint is missing or fails to unpack), `encode_ui_account`'s `JsonParsed` branch falls back to base64-encoding the account's data with `data_slice_config = None`, i.e. the full, unsliced account data, regardless of what `dataSlice` the client requested.

### Finding Description
`get_encoded_account` dispatches based on owner and encoding: [1](#0-0) 

Note `data_slice` is bound in the function signature but is only passed into `encode_account` on the non-token branch; the SPL-token branch calls `get_parsed_token_account(bank, pubkey, account, overwrite_accounts)`, which has no `data_slice` parameter at all: [2](#0-1) 

Inside, `additional_data` is derived from `get_token_account_mint`; if the mint can't be resolved (deleted, reassigned, or the "account" is just arbitrary attacker-owned data claiming to be a token program account), `additional_data` becomes `None`, and `encode_ui_account` is invoked with `data_slice_config` hard-coded to `None`: [3](#0-2) 

`encode_ui_account`'s `JsonParsed` arm then attempts `parse_account_data_v3`; when it fails (e.g., `parse_token_v3` returns `AccountNotParsable`/`AdditionalDataMissing`), it falls back to base64-encoding `slice_data(account.data(), data_slice_config)` — with `data_slice_config` being `None` in this call path — thus always encoding the **entire** account buffer: [4](#0-3) 

By contrast, the generic (non-token) path preserves and applies the client's `dataSlice` on the same JsonParsed-failure fallback, as confirmed by an existing unit test asserting the sliced result is returned when parsing fails: [5](#0-4) [6](#0-5) 

So the discrepancy is real and code-confirmed: for accounts owned by a known SPL Token/Token-2022 program id, `dataSlice` is unconditionally dropped before reaching `encode_ui_account`, both in the parse-success case (where jsonParsed output is a JSON object, for which slicing is documented as inapplicable) and, importantly, in the parse-failure fallback case, where the API is expected to still honor `dataSlice` on the emitted binary/base64 data (per the sibling non-token code path and its test) but does not.

An attacker can trivially force the failure branch: create/own an account whose `owner` is `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` (or Token-2022) with arbitrary data that either isn't a valid SPL account/mint layout, or is a valid layout whose `mint` field points at a since-deleted/reassigned/invalid mint account, causing `get_token_account_mint`/`get_additional_mint_data` resolution to fail. The `is_known_spl_token_id` check only inspects the account owner field, not the validity of the account's internal structure, so this precondition is met with a single `system_instruction::create_account`-style write followed by `getAccountInfo`/`getMultipleAccounts` with `encoding: 'jsonParsed'` and a small `dataSlice`.

### Impact Explanation
This is a "returned data ignores the caller's own explicit cost-bounding parameter" bug (`getAccountInfo`/`getMultipleAccounts` category), not raw unbounded resource exhaustion: the response size for a single account is still capped by the account's on-chain size (which the attacker must pay rent for) and, for `getMultipleAccounts`, by `MAX_MULTIPLE_ACCOUNTS` count. However, a client that explicitly used `dataSlice` to bound its own response-size budget (e.g., a light client fetching only a small header from what it expects to be a JSON-parsed token account) receives the full, unsliced binary blob instead — silently defeating its cost/size assumption in a single low-rate RPC call, which matches the "cost bounded by explicit limits" invariant violation called out in the question.

### Likelihood Explanation
Trivially reproducible by an unprivileged attacker: create one account owned by the SPL Token or Token-2022 program id whose data does not resolve to a valid, mint-linked token account (e.g., garbage data, or a valid `Account` layout pointing at a mint that doesn't exist/doesn't unpack). No special privileges, no consensus mutation, single RPC call — fully within the unprivileged, single-call threat model.

### Recommendation
Thread `data_slice: Option<UiDataSliceConfig>` through `get_parsed_token_account` (and `get_parsed_token_accounts`) in `rpc/src/parsed_token_accounts.rs`, and pass the caller's `data_slice` from `get_encoded_account` into it, so that the `JsonParsed`-failure fallback inside `encode_ui_account` slices the binary output identically to the non-token code path.

### Proof of Concept
Rust integration test in `rpc/src/rpc.rs` test module (pattern similar to `test_rpc_get_account_info`):
1. Store an `AccountSharedData` owned by `spl_token_interface::id()` (or Token-2022) whose data is a buffer that does not unpack as `Account`/`Mint`/`Multisig` (e.g., a few arbitrary non-zero bytes long enough to exceed a small slice length), so `parse_token_v3`/`get_token_account_mint` fails and additional-mint resolution fails.
2. Issue `getAccountInfo(pubkey, { encoding: "jsonParsed", dataSlice: { offset: 0, length: 2 } })` via `create_test_request`/`rpc.handle_request_sync`.
3. Assert (expected to fail on current code, demonstrating the bug): `result["value"]["data"]` equals `[BASE64_STANDARD.encode(&data[0..2]), "base64"]` — i.e., the sliced 2 bytes — but actual current behavior returns the full un-sliced `BASE64_STANDARD.encode(&data)`.
4. Repeat via `getMultipleAccounts` with several such orphaned token accounts and a small `dataSlice` to show the full-size fallback applies per-account, multiplying response bytes beyond what the client's `dataSlice` implies.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
