### Title
Staked-Collateral (SVSP) LST Price Is Directly Manipulable by Any Unprivileged User via Donation to the Validator Stake/On-Ramp Account - (File: `programs/marginfi/src/state/price.rs`)

### Summary
For `StakedWithPythPush` banks, marginfi derives the LST-to-SOL exchange rate (`price_multiplier`) from the *live lamport balance* of the validator's single-pool stake account and on-ramp account, divided by the LST mint supply. Because these are ordinary system accounts, **any unprivileged user can transfer SOL into them with a plain `SystemProgram.transfer`**, instantly and directly inflating the price used by marginfi to value staked collateral — the same "directly influences the price" root cause as the DODO `adjustPrice` report, except here there is no privileged role involved at all, making it strictly worse and squarely in scope.

This mirrors the reported bug class exactly: a value ("I" in DODO, `price_multiplier`/NAV here) that directly and immediately drives the trading/collateral price can be moved by an actor just before they interact with the pool (deposit/borrow), and reversed/exploited immediately after, because the price update and the value-affecting action can be placed in the same transaction (donate lamports → price rises atomically → borrow against inflated collateral in the same tx, since price is fetched live from the same `remaining_accounts` at instruction time, not only from a stale cache — see `load_oracle_context_with_max_age` dispatch at `programs/marginfi/src/state/price.rs:294-421`).

### Impact Explanation
An attacker who controls (or creates) a validator's single-pool stake account with a small LST supply can:
1. Deposit into that Staked-Collateral bank to hold a large share of the LST supply.
2. Transfer SOL directly into the pool's stake or on-ramp account in the same transaction (or immediately before) a borrow.
3. Because `price_multiplier = NAV / lst_supply`, and NAV rises by the donated amount while `lst_supply` is unchanged, the attacker's *already-held* LST collateral value inflates by (their_LST_share × donated_amount / lst_supply). For small/new pools this leverage effect is large — the existing test shows a 9 SOL donation into a 40-SOL-supply pool moving the multiplier from 1.025 → 1.25 (a ~22% jump) — see `tests/specs/staked/s02_addBank.spec.ts:970-995`.
4. This inflated valuation is used directly for health/borrow-power checks, letting the attacker borrow more of other bank assets than their real collateral justifies, and abandon the position (default/never repay), leaving bad debt for lenders of the borrowed asset.

This is a real value-redirection/misvaluation with financial effect on other depositors in the group. Per `SECURITY.md`, "oracle manipulation/flash-loan attacks" are explicitly **not** excluded from scope.

### Likelihood Explanation
Likelihood is Medium-to-High for pools with small LST supply/NAV (e.g., freshly created validator pools, or intentionally attacker-created pools where the attacker holds most of the supply), since the cost (SOL donated) can be much smaller than the extractable extra borrow value when the attacker dominates the pool's share. It requires no privileged role, no oracle compromise, and no race against an admin transaction — the attacker fully controls the timing by combining the donation and the borrow/health-check in the same or sequential transactions.

### Recommendation
- Do not derive collateral pricing solely from a spot lamport balance of an externally-writable account; require the NAV/exchange-rate update to be sourced from a validated, rate-limited, or TWAP'd on-chain source (e.g., the SVSP program's own canonical exchange-rate account) rather than a raw balance read that any transfer can move.
- If raw balance reads must be used, apply confidence/deviation bounds, minimum elapsed-time between price jumps ("ramping"), or cap the multiplier's per-update delta, similar to the report's own recommendation to slow-ramp adjustable price-relevant parameters rather than allow instantaneous jumps.
- Consider requiring the total-asset-value / deposit-limit checks to be computed using a NAV smoothed over multiple pulses rather than the single most-recent lamport snapshot, to blunt single-transaction donation attacks.

### Proof of Concept
Existing test suite already demonstrates the primitive end-to-end (unprivileged wallet inflating the cached multiplier via plain SOL transfers): [3](#0-2) [6](#0-5) 

A full weaponized PoC (not present in the repo, and not verifiable further given index limits) would combine, in one attacker-controlled sequence: (1) deposit into a Staked-Collateral bank on a low-supply validator pool, (2) `SystemProgram.transfer` SOL into that validator's stake/on-ramp account, (3) call `lending_pool_pulse_bank_price_cache` (or rely on the live-fetch path in `borrow`) to reflect the inflated price, (4) borrow against the now-inflated collateral value, (5) default. Because full transaction-level verification requires running the test harness, this should be validated with a live Devin session against the bankrun test environment to quantify exact extractable value versus donation cost for realistic pool sizes.

fn staked_pool_net_asset_value(
    pool_stake_info: &AccountInfo,
    pool_onramp_info: &AccountInfo,
    rent: &Rent,
) -> MarginfiResult<u64> {
    let pool_rent_exempt_reserve = rent.minimum_balance(pool_stake_info.data_len());
    let onramp_rent_exempt_reserve = rent.minimum_balance(pool_onramp_info.data_len());

    let main_stake_value = pool_stake_info
        .lamports()
        .saturating_sub(pool_rent_exempt_reserve);
    let onramp_value = pool_onramp_info
        .lamports()
        .saturating_sub(onramp_rent_exempt_reserve);

    Ok(main_stake_value.saturating_add(onramp_value))
}

/// (permissionless) Refresh the cached oracle price for a bank.
pub fn lending_pool_pulse_bank_price_cache<'info>(
    ctx: Context<'info, LendingPoolPulseBankPriceCache<'info>>,
) -> MarginfiResult {
    let clock = Clock::get()?;

    let mut bank = ctx.accounts.bank.load_mut()?;

    let price_for_cache = OraclePriceFeedAdapter::get_price_and_confidence_for_cache(
        &bank,
        ctx.remaining_accounts,
        &clock,
    )?;

    bank.update_cache_price(Some(price_for_cache))?;

    Ok(())
}
