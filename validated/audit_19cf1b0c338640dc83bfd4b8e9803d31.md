## Analysis

This confirms a permanent-lockout analog to the reported bug class: an "uninitialized" (never-set) admin identity that permanently disables a privileged-mutation guard.

### Title
Zero `initialAdmin` at B-20 token creation permanently locks role administration - (File: `crates/common/precompiles/src/b20_factory/logic/v1.rs`)

### Summary
`FactoryV1::init_asset_token` / `init_stablecoin` only grant `DefaultAdmin` if `common.initial_admin` is non-zero [1](#0-0) . If a token is deployed via `createB20` with `initialAdmin = address(0)`, no admin is ever registered and `role_member_count(DefaultAdmin)` stays `0`, confirmed by the factory's own test `test_create_asset_token_grants_default_admin_role` ("Zero initialAdmin grants no role") [2](#0-1) .

### Finding Description
Every non-privileged mutation of roles (`grant_role`, `revoke_role`, `set_role_admin`) is gated by `ensure_role_admin_mutations_available`, which reverts with `AccessControlUnauthorizedAccount` whenever `role_member_count(DefaultAdmin) == 0` [3](#0-2) . This same guard is duplicated identically across `b20_asset/logic/v1.rs`, `b20_asset/logic/v2.rs`, `b20_stablecoin/logic/v1.rs`, and `b20_stablecoin/logic/v2.rs` [4](#0-3) .

Because the guard is a strict `== U256::ZERO` check with no bootstrap-recovery path once the token is live (the only unchecked/no-auth path — `grant_role_unchecked` — is reachable solely from the factory's `init_*` functions during `createB20`, not afterward), a token created with `initialAdmin = address(0)` reaches this state on creation and never leaves it: `grant_role`, `revoke_role`, and `set_role_admin` all revert forever for every caller, mirroring the `InnerOwnedSet`/`only_outer` pattern where an unset actor makes an authorization gate permanently unsatisfiable.

### Impact Explanation
Any account operational role (`Mint`, `Burn`, `Metadata`, `Operator`, `Pause`, etc.) can never be granted or revoked once the token is deployed with a zero `initialAdmin`, because every non-privileged grant/revoke/set-role-admin call is preceded by `ensure_role_admin_mutations_available`, which is unsatisfiable with zero admins [5](#0-4) . This permanently freezes the token's privileged administration surface — no future mint/burn/pause/metadata role can be assigned through the normal permissioned path, effectively bricking governance of that B-20 token (though the existing supply/balances/transfers remain usable). This matches the "permanent freezing" impact class for the deployed token's administrative capability.

### Likelihood Explanation
This requires only a single, ordinary `createB20` transaction from any unprivileged deployer/token creator with `initialAdmin` set to `address(0)` in `IB20Factory::B20AssetCreateParams`/`B20StablecoinCreateParams` — no special privilege or race condition needed [6](#0-5) . It can happen accidentally (a caller passing a default/zero address) or be used to deliberately create a token whose roles can never be administered post-deployment (e.g., misleading users about future governance/control).

### Recommendation
- In `FactoryV1::init_stablecoin` / `init_asset_token`, reject `common.initial_admin.is_zero()` outright (revert `createB20`) instead of silently skipping the admin grant, since a zero admin makes `ensure_role_admin_mutations_available` permanently unsatisfiable.
- Alternatively, provide an explicit, privileged recovery path (e.g., only the factory or protocol governance) to re-bootstrap `DefaultAdmin` on a token with `role_member_count(DefaultAdmin) == 0`.
- Add a unit/integration test that creates a token with `initialAdmin = address(0)` and asserts that `grantRole`/`setRoleAdmin` reverts indefinitely, to make this state explicit in test coverage (the existing test only checks that no role is granted, not that the token becomes permanently unadministered).

### Proof of Concept
1. Call `IB20Factory::createB20Call` with `variant = ASSET` (or `STABLECOIN`) and `initialAdmin = address(0)`.
2. `init_asset_token` skips the `grant_role_unchecked` branch since `common.initial_admin.is_zero()` [7](#0-6) ; `role_member_count(DefaultAdmin)` remains `U256::ZERO`.
3. Any subsequent call to `grantRole`/`revokeRole`/`setRoleAdmin` on the deployed token by any account (including the deployer) invokes `ensure_role_admin_mutations_available`, which reverts with `AccessControlUnauthorizedAccount` because `role_member_count == 0` [8](#0-7) .
4. There is no code path (short of a chain-level intervention) to set `role_member_count(DefaultAdmin)` above zero once the token is live — administration of the token's roles is permanently frozen.

```rust
    /// Ensures role-admin mutations are still reachable.
    fn ensure_role_admin_mutations_available<S: AssetAccounting, A: PolicyAccounting>(
        &self,
        token: &B20AssetToken<S, A>,
        caller: Address,
    ) -> Result<()> {
        let admin_role = B20TokenRole::DefaultAdmin.id();
        if token.accounting().role_member_count(admin_role)? == U256::ZERO {
            return Err(BasePrecompileError::revert(IB20::AccessControlUnauthorizedAccount {
                account: caller,
                neededRole: admin_role,
            }));
        }
        Ok(())
    }
```

```rust
    fn grant_role(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        role: B256,
        account: Address,
        privileged: bool,
    ) -> Result<()> {
        if role == B20TokenRole::DefaultAdmin.id() || !privileged {
            self.ensure_role_admin_mutations_available(token, caller)?;
        }
        if !privileged {
            let admin = token.accounting().role_admin(role)?;
            B20Guards::ensure_role(token, caller, admin)?;
        }
        self.grant_role_unchecked(token, role, account, caller)
    }
```
