### Title
Unvalidated negative `offset`/`limit` in `Resolver.Chains` GraphQL query causes index-out-of-range panic - ([File: core/web/resolver/query.go])

### Summary
The `Chains` resolver only checks `offset >= count` but never guards against negative `offset` or `limit` values before using them directly as slice indices in `chains[offset:end]`. Since `Offset`/`Limit` are attacker-supplied `*int32` GraphQL arguments converted via `pageOffset`/`pageLimit` with a plain `int(*offset)` cast (no clamping to zero), a view-role user can submit a negative offset (e.g. `-1`) and trigger a Go runtime panic (`slice bounds out of range`).

### Finding Description
`Resolver.Chains` (`core/web/resolver/query.go:116-159`) is reachable by any authenticated session because it only calls `authenticateUser`, which merely checks for a valid session and explicitly treats "presence of user" as sufficient — i.e. the lowest `view` role is enough [1](#0-0) .

Inside the resolver, the raw `int32` GraphQL arguments are converted to `int` without any lower-bound validation: [2](#0-1) 

The only bound check performed is `offset >= count`, which does not catch negative values, and `limit` is only used if `limit > 0`, meaning a negative `limit` is silently ignored (falls back to `end = count`) rather than rejected: [3](#0-2) 

If a client sends `offset: -1` (any negative int32), the check `offset >= count` evaluates false (assuming at least one chain is configured), so execution proceeds to `chains[offset:end]` with a negative starting index, which is invalid in Go and panics with `runtime error: slice bounds out of range [-1:]`.

Reaching this line requires only a valid authenticated session with `view` role — the minimal privilege level — and one chain configured on the node (a very common deployment state), satisfying the "unprivileged attacker" criteria.

### Impact Explanation
This is a per-request denial-of-service condition: a low-privileged (`view`-role) user can crash the goroutine handling their own GraphQL request via a runtime panic instead of receiving a graceful GraphQL error. Whether this escalates to a full node crash depends on panic-recovery middleware in the GraphQL execution engine / HTTP layer (e.g. `graph-gophers/graphql-go`'s internal resolver panic recovery, or gin's `Recovery` middleware), which was not confirmed to be present or absent in this codebase during this review — this is the primary unresolved uncertainty. At minimum, this represents a availability bug in the pagination bounds logic; at worst (if no recovery middleware wraps this call path), it could crash the node process, which is a Denial-of-Service impact class.

### Likelihood Explanation
Highly likely and trivially repeatable: it requires nothing more than a valid `view`-role session (the lowest privilege tier explicitly supported by `authenticateUser`) and a single crafted GraphQL query with a negative `offset` value. No special timing, race conditions, or additional preconditions are needed beyond at least one chain/relayer being configured, which is the normal operating state of a Chainlink node.

### Recommendation
Clamp `offset` and `limit` to non-negative values in `pageOffset`/`pageLimit` (e.g. return 0 for any negative input, or explicitly reject negative values with a GraphQL error), and add an explicit `offset < 0` check in `Resolver.Chains` (and `Resolver.Bridges`, which has the identical pattern) before slicing, returning a descriptive error instead of allowing the raw slice expression to execute with unvalidated bounds.

### Proof of Concept
Go table test in `core/web/resolver/query_test.go` (or a new test file) that:
1. Sets up a `Resolver` with `App.GetRelayers()` returning at least one chain/relayer via mocks.
2. Constructs `args := struct{ Offset *int32; Limit *int32 }{Offset: ptr(int32(-1)), Limit: ptr(int32(math.MaxInt32))}`.
3. Calls `r.Chains(ctx, args)` inside a `defer func(){ recover() }()` wrapped subtest, asserting:
   - No panic occurs (test fails if `recover()` catches a non-nil panic).
   - The returned `error` is non-nil and describes an invalid/out-of-range offset.
4. Repeat with additional negative/overflow combinations (`Offset: -100`, `Limit: -1`, `Offset: math.MinInt32`) to confirm no panic path is reachable and proper `error` values are returned for all of them.
