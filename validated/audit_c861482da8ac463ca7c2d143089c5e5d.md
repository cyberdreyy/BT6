### Title
Removing a multisig member does not purge that member's outstanding confirmations, allowing a request to execute with fewer live-member approvals than `num_confirmations` - ([File: multisig2/src/lib.rs])

### Summary
`delete_member()` only removes *requests authored by* the removed member; it never scans the `confirmations` map to strip that member's approval from *other* still-pending requests they had already confirmed. Because `confirm()` later counts `confirmations.len()` without re-validating that every entry still belongs to a current member, a stale confirmation from a removed member can be the deciding vote that pushes a request over the `num_confirmations` threshold, even though only `num_confirmations - 1` *live* members actually approved it.

### Finding Description
`MultiSigContract::confirm` tallies approvals purely from the `HashSet<String>` stored in `self.confirmations`, comparing its length against `self.num_confirmations`: [1](#0-0) 

`delete_member` is the only place that mutates membership. It removes requests that the departing member *authored*, and removes their `num_requests_pk` entry and their access key/membership record, but it does **not** iterate `self.confirmations` to remove the departing member's votes from requests authored by *other* members: [2](#0-1) 

`current_member()` and `assert_valid_request()` only check that the *caller* of `confirm`/`add_request`/`delete_request` is presently a member; they never re-validate the historical entries already stored in a request's confirmation set: [3](#0-2) [4](#0-3) 

This is directly analogous to the referenced report: just as `mapMember_weight` kept stale weight from a withdrawn synth because withdrawal only decremented a single scalar without being indexed per-synth, `confirmations` keeps a stale vote from a removed member because member removal only cleans up requests indexed by *that member as author*, not the member's votes recorded against *other* requests. The invariant the contract is supposed to guarantee is:

```
count(confirmations[request_id]) == count(live members who confirmed request_id)
```

After a member is deleted while having an outstanding confirmation on some other pending request, this equality breaks: the left side stays inflated by 1 relative to the right side.

### Impact Explanation
This is a threshold/authorization bug: a request can be executed (funds transferred, keys added, contract code deployed, etc.) with strictly fewer *live* member approvals than `num_confirmations` requires, because a phantom vote from a since-removed member counts toward the quorum. This falls squarely into the Critical impact category "a multisig request executed below threshold." No malicious/rogue member action is required to trigger the *bug* itself — the divergence is created by ordinary, legitimate use of `DeleteMember` (e.g., rotating out a departing team member) combined with a request that member had confirmed before being removed; from that point on, the threshold guarantee that all subsequent operations rely on is silently weaker than configured.

### Likelihood Explanation
Any multisig that (a) has more than one pending request at a time and (b) ever removes a member (a normal governance/key-rotation operation supported by `DeleteMember`) is exposed if that member had already confirmed a still-open, unrelated request. Given `active_requests_limit` allows up to 12 concurrent pending requests per member and member turnover is an expected lifecycle event for these contracts, the precondition is realistic and requires no privileged/malicious intent — just an ordering of routine operations.

### Recommendation
When removing a member in `delete_member`, iterate `self.confirmations` (or maintain a reverse index of member → confirmed request ids) and strip the departing member's entry from every request's confirmation set, not just requests they authored. Alternatively, when tallying in `confirm`, filter `confirmations` down to entries still contained in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)`.
2. `A` calls `add_request` to create request `R1` (e.g., a `Transfer`).
3. `A` calls `confirm(R1)` → `confirmations[R1] = {A}` (len 1, below threshold 3). [5](#0-4) 
4. Separately, `B` and `C` create and confirm a `DeleteMember{member: A}` request (`R2`) against the multisig's own account, reaching threshold 3 and executing it. `delete_member` removes `A` from `self.members`, deletes any requests *authored* by `A`, but `R1`'s confirmation set still contains `A`. [6](#0-5) 
5. `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}` (len 2).
6. `C` calls `confirm(R1)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `R1` executes. [7](#0-6) 

Only `B` and `C` — two *live* members — actually approved `R1` after `A`'s removal, yet it executed as if 3 live approvals were obtained, because the phantom confirmation from removed member `A` was never purged.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
