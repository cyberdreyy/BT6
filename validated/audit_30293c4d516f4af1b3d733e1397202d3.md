### Title
Cross-initiator job triggering due to missing initiator-to-job binding check in `AuthenticateExternalInitiator` - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` only verifies that the supplied `AccessKey`/`Secret` correspond to *some* registered external initiator, then unconditionally grants a generic `run`-role session and stores the resolved `ExternalInitiator` in the gin context. Nothing in the authentication path, nor apparently downstream, cross-checks that the specific `ExternalInitiator` who authenticated is the one actually bound to the job whose `/runs` endpoint is being invoked.

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` (lines 119-151) builds an `auth.Token` from `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`, resolves it via `store.FindExternalInitiator`, validates the secret with `bridges.AuthenticateExternalInitiator(eia, ei)`, and on success does: [1](#0-0) 
It sets `SessionExternalInitiatorKey` to the resolved `ei` and grants `clsessions.User{Role: clsessions.UserRoleRun}` — a role that satisfies `RequiresRunRole` for *any* job-runs route, not just jobs owned by that initiator.

The context value is exposed via `GetAuthenticatedExternalInitiator`: [2](#0-1) 

Searching the codebase for consumers of `GetAuthenticatedExternalInitiator` found no call site outside `core/web/auth/auth.go` itself — i.e., the value the middleware stores (which external initiator authenticated) is never read back and compared against the target job's registered external initiator anywhere in the request-handling path (e.g., the pipeline/job runs controller). Since `RequiresRunRole` only checks `user.Role`, and the role is uniformly `UserRoleRun` for every successfully authenticated external initiator regardless of identity, any external initiator's valid credentials pass the same authorization gate for every job's run endpoint — the binding between a specific initiator and a specific job is never enforced at the authentication/authorization layer that was inspected.

### Impact Explanation
An attacker who legitimately controls (or has leaked) one external initiator's `AccessKey`/`Secret` can authenticate successfully and, because the role check is generic (`run`) rather than job-scoped, potentially invoke `/v2/jobs/{jobID}/runs` for jobs registered to a different external initiator, triggering unauthorized job runs. This matches "unauthorized job run" impact class.

### Likelihood Explanation
Only a single external initiator's valid `AccessKey`/`Secret` are required — a credential an attacker could obtain by compromising or being one of many legitimate external initiators integrated with the node. No admin/operator access is needed, and the request is a standard authenticated HTTP call, making this a fully unprivileged attacker path once EI1 credentials are held. Repeatability is high since it is a stateless header-based auth bypass, not a race condition.

### Recommendation
Enforce initiator-to-job binding at the authorization layer: when handling a webhook/run creation request authenticated via `AuthenticateExternalInitiator`, fetch the target job's registered `ExternalInitiator`(s) and compare their ID(s) to the one returned by `GetAuthenticatedExternalInitiator`; reject with 401/403 if they don't match. This check should occur in the runs-creation handler (or a dedicated middleware) before any run is created, rather than relying solely on the generic `run` role.

### Proof of Concept
1. Register two external initiators EI1 and EI2 (distinct AccessKey/Secret) via `core/web/external_initiators_controller.go`.
2. Create Job1 bound to EI1 and Job2 bound to EI2 (webhook jobs with distinct `ExternalInitiatorWebhookSpec`).
3. Using EI1's `ExternalInitiatorAccessKeyHeader`/`SecretHeader`, `POST /v2/jobs/{Job2.ID}/runs`.
4. Assert: request currently succeeds (200/201) and a run for Job2 is created — expected/fixed behavior: request should be rejected with 401/403 because EI1 is not the initiator bound to Job2.
5. Repeat in reverse (EI2 credentials against Job1) to confirm symmetry.

// GetAuthenticatedExternalInitiator extracts the external initiator from the
// context.
func GetAuthenticatedExternalInitiator(c *gin.Context) (*bridges.ExternalInitiator, bool) {
	obj, ok := c.Get(SessionExternalInitiatorKey)
	if !ok {
		return nil, false
	}

	return obj.(*bridges.ExternalInitiator), ok
}
