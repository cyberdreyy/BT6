### Title
Kubernetes executor's `buildContainer` mounts the shared `scripts` emptyDir into attacker-controlled service containers, letting them tamper with helper/bootstrap files the build phase later trusts - (File: executors/kubernetes/kubernetes.go)

### Summary
`buildContainer` (executors/kubernetes/kubernetes.go:1549-1609) builds the `api.Container` spec for both the build container and every user-declared service container using the same `s.getVolumeMounts()` call, which unconditionally attaches the `scripts` emptyDir volume whenever attach-mode or dumb-init is enabled. Because service images/commands are fully attacker-controlled (job author defines `services:`), this grants a malicious service container write access to the same volume that carries the executed stage scripts, the copied `dumb-init` binary, and (in Concrete/steps mode) the bootstrapped `gitlab-runner-helper` binary that the build container later executes as `steps serve`.

### Finding Description
- `buildContainer` calls `s.getVolumeMounts()` (kubernetes.go:1708-1722) to populate `VolumeMounts` for the container it is constructing, with no distinction between `isServiceContainer` and the build container itself. [1](#0-0) 
- `preparePodServices` invokes `buildContainer` with `isServiceContainer: true` for every user-defined service, so the resulting service containers get the exact same volume set, including `scripts`, as the build container. [2](#0-1) 
- The `scripts` emptyDir is the volume where: (a) stage scripts are written via `saveScriptOnEmptyDir` before `runInContainer` executes them, and (b) `buildPermissionsInitContainer` copies `dumb-init` into it for later execution by the build container. [3](#0-2) [4](#0-3) 
- In Concrete/steps mode, the equivalent `stepsServiceContainer` explicitly mounts `stepsVolumeMounts()`, which also contains the `scripts` volume - the same volume the init container uses to bootstrap the trusted `gitlab-runner-helper` binary that the build container later executes verbatim as `<path> steps serve`. [5](#0-4) [6](#0-5) [7](#0-6) 
- There is no content-integrity check (checksum, read-only mount, or per-container sub-path isolation) before the build/helper container consumes files from this shared directory. `verifyAllowedImages` only restricts which image names can run as a service; it does nothing to constrain what a running service container writes to a shared volume it is legitimately allowed to mount. [8](#0-7) 
- Because all containers in a pod start concurrently (Kubernetes does not serialize container startup ordering beyond init containers), an attacker-controlled service container can begin executing before the build/helper container reads and executes the script or helper binary, creating a race window to overwrite it with attacker content.

### Impact Explanation
A pipeline author who can define a `service:` (fully within normal job authoring privileges - arbitrary image, and per `spec.Image`, potentially an overridden entrypoint/command) can use that service container to overwrite files in the shared `scripts` emptyDir - stage scripts, the `dumb-init` binary, or (in Concrete mode) the `gitlab-runner-helper` binary - before the build or helper container executes them. Since the build/helper container blindly executes whatever is at `scriptPath()`/`stepsRunnerBinaryPath()` without re-verifying its origin, this is a build-phase hijack: attacker-controlled service content can execute with the trust/authority of the build or helper container, including intercepting the `steps serve`/`steps proxy` protocol used by the dialer for pod exec.

### Likelihood Explanation
This requires only standard job-author privileges (defining a `services:` entry) plus a timing race against the build/helper container's read of the shared volume, no cluster-admin or GitLab-admin compromise needed. The race window exists because the script-writing (`saveScriptOnEmptyDir`) and script-execution happen after pod creation via separate `exec` calls, while the service container is already running and mounted on the same volume from pod start. Reliability depends on winning this race, which is feasible to script/retry from the attacker's service entrypoint (e.g., loop-polling and overwriting the target path).

### Recommendation
Do not mount the `scripts` (and, in Concrete mode, the bootstrap) emptyDir into service containers at all - only the build/helper containers should mount it. If service containers require some form of shared workspace, use a separate volume scoped away from executable script/binary paths. Additionally, verify the integrity of the helper binary/script (e.g., checksum or making the volume read-only from the perspective of service containers via `subPath`/read-only mounts) before execution by the build container.

### Proof of Concept
Go integration test plan (extending `executors/kubernetes/kubernetes_integration_test.go` style tests):
1. Configure a job with a service definition whose image runs a loop that continuously overwrites the file at the known `scriptsDir()` path (or `stepsRunnerBinaryPath()` in Concrete mode) with attacker payload content.
2. Run the job via `build.Run(...)` and assert that:
   - The build/helper container's script output shows execution of the attacker payload instead of the intended CI script content, or
   - `stepsRunnerBinaryPath()`'s executed binary is not byte-identical to the one written by `init-steps-bootstrap`.
3. Assert failure of the invariant: "content executed by build/helper container == content written by trusted init/helper writer", proving the build phase trusts unverified, service-writable shared-volume content.

func (s *executor) verifyAllowedImages(opts containerBuildOpts) error {
	// check if the image/service is allowed
	internalImages := []string{
		s.ExpandValue(s.Config.Kubernetes.Image),
		s.ExpandValue(s.helperImageInfo.Name),
	}

	var (
		optionName    string
		allowedImages []string
	)
	if opts.isServiceContainer {
		optionName = "services"
		allowedImages = s.Config.Kubernetes.AllowedServices
	} else if opts.name == buildContainerName {
		optionName = "images"
		allowedImages = s.Config.Kubernetes.AllowedImages
	}

	verifyAllowedImageOptions := common.VerifyAllowedImageOptions{
		Image:          opts.image,
		OptionName:     optionName,
		AllowedImages:  allowedImages,
		InternalImages: internalImages,
	}

	return common.VerifyAllowedImage(verifyAllowedImageOptions, s.BuildLogger)
}

func (s *executor) preparePodServices() ([]api.Container, error) {
	podServices := make([]api.Container, len(s.options.Services))

	for i, name := range s.options.getSortedServiceNames() {
		service := s.options.Services[name]
		kubernetesOptions := service.ExecutorOptions.Kubernetes.Expand(s.Build.GetAllVariables())
		securityContext := s.getSecurityContextWithUIDGID(
			string(kubernetesOptions.User),
			name,
			s.Config.Kubernetes.ServiceContainerSecurityContext,
		)

		var err error
		podServices[i], err = s.buildContainer(containerBuildOpts{
			name:               name,
			image:              service.Name,
			imageDefinition:    *service,
			isServiceContainer: true,
			requests:           s.configurationOverwrites.getServiceResourceRequests(name),
			limits:             s.configurationOverwrites.getServiceResourceLimits(name),
			securityContext:    securityContext,
		})
		if err != nil {
			return nil, err
		}
	}

// stepsRunnerBinaryPath returns the absolute path inside the pod at which
// the bootstrapped helper binary lives. The path is shared by:

func (s *executor) stepsRunnerBinaryPath() string {
	return path.Join(s.scriptsDir(), helperBinaryName)
}
