### Title
Front-running deterministic account creation permanently blocks the intended account via the System Program's "already in use" lamport check - (File: programs/system/src/system_processor.rs)

### Summary
`system_processor::create_account` decides whether a target address is "already in use" purely by checking `to.get_lamports() > 0`, with no requirement that the account be owned by the intended program or contain the intended data. Any unprivileged user who can predict a to-be-created address (a `create_with_seed` derived address, an Address Lookup Table PDA, or any other deterministically derivable pubkey) can transfer a trivial amount of lamports to that address before the legitimate creator's transaction lands, permanently causing the legitimate `CreateAccount` instruction to fail with `SystemError::AccountAlreadyInUse`.

### Finding Description
The System Program's `create_account` helper only guards against reuse by checking the lamport balance of the destination account: [1](#0-0) 

```
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ...
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
```

This is the same class of "existence" check as the `Governor.proposalId` collision check in the referenced report — it is derived from a value (lamports/`proposal.voteStart`) that a third party can set before the intended owner's transaction executes, and once set, the intended party is permanently blocked from creating at that exact deterministic address.

The pattern is reachable from ordinary user transactions/CLI flows that create accounts at deterministically-derived addresses before the account exists, most concretely durable nonce accounts created via `create_with_seed`, where the destination address is computed purely from a public base pubkey and a public seed string: [2](#0-1) 

```
    let nonce_account_pubkey = config.signers[nonce_account].pubkey();
    let nonce_account_address = if let Some(ref seed) = seed {
        Pubkey::create_with_seed(&nonce_account_pubkey, seed, &system_program::id())?
    } else {
        nonce_account_pubkey
    };
```

Because `nonce_account_pubkey` and `seed` are both public (the base keypair's public key is known before the funding/creation transaction is broadcast, and the seed string is often predictable/observable in the mempool), an attacker can front-run the `CreateAccount`/`CreateAccountWithSeed` instruction by sending 1 lamport to `nonce_account_address` first. The subsequent legitimate creation transaction will then hit the `to.get_lamports() > 0` branch in `create_account` and fail with `AccountAlreadyInUse`, permanently blocking creation at that specific address — the account owner must choose a new base/seed pair to retry, exactly mirroring the "proposer must slightly change proposal data" mitigation gap described in the Nouns Builder report. The CLI even performs an explicit pre-flight existence check for this reason: [3](#0-2) 

The same deterministic-address creation pattern (public inputs → derived address → one-shot `CreateAccount`, permanently un-reusable once occupied/deactivated) also underlies Address Lookup Table creation, which is explicitly documented as unrecoverable once blocked: [4](#0-3) 

### Impact Explanation
This enables a griefing/denial-of-service primitive against any unprivileged user attempting to create an account at a deterministically-derivable address (durable nonce accounts, PDAs computed by client-side tooling, etc.). The victim's `CreateAccount` transaction fails, the intended address becomes permanently unusable for its intended purpose, and the victim must regenerate parameters (new base keypair/seed) and retry — consistent with the Medium severity assigned to the analogous Nouns Builder finding, since it is griefing rather than direct fund theft, but it is a real, repeatable state-mutation-based denial of a specific, otherwise-legitimate on-chain resource.

### Likelihood Explanation
The attack requires only: (1) visibility of the destination address before the legitimate creation transaction confirms (trivial for nonce accounts, since the base pubkey is known ahead of time and often reused/predictable, or observable via mempool/RPC simulate calls), and (2) the ability to send an ordinary `SystemInstruction::Transfer` of 1 lamport to that address, which any funded account can do. No special privilege, signature over the target account, or validator cooperation is required, making this readily executable by any network participant that can race a transaction landing before another.

### Recommendation
Do not rely solely on `lamports > 0` to determine "already in use" for account creation flows that matter for correctness/availability guarantees at the application layer; more importantly, client/CLI tooling and any core account-creation helpers that are exposed to griefing should treat a non-zero-lamport, wrong-owner account as a signal to fail fast and clearly, and downstream protocols that need collision-resistant identifiers (e.g., derived addresses used once) should incorporate values not predictable/interceptable by third parties (e.g., an unpredictable nonce/seed chosen and revealed atomically within the same transaction, or requiring the destination address's derivation to include a value under exclusive control of the creator that cannot be front-run).

### Proof of Concept
1. Victim intends to create a durable nonce account with base pubkey `B` and seed `"my-nonce"`, computing `addr = create_with_seed(B, "my-nonce", system_program::id())` client-side, then broadcasts a `CreateAccountWithSeed` transaction funding `addr`.
2. Attacker, observing `B` and the seed in advance (or by simulating the same derivation off a known/reused base key), sends a `SystemInstruction::Transfer` of 1 lamport to `addr` and gets it confirmed first.
3. When the victim's `CreateAccountWithSeed` transaction executes, `system_processor::create_account` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, permanently preventing nonce-account creation at `addr` with those parameters (matching the pre-flight check and error path in `cli/src/nonce.rs::process_create_nonce_account`).
4. The victim must choose a different base key or seed and retry, exactly analogous to a proposer needing to alter `_description` to bypass the Nouns Builder `PROPOSAL_EXISTS`/cancel front-run.
