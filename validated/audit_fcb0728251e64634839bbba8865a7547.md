### Title
`check_parent_tenure_choice` treats a missing `approved_time` as "arrived at time 0", fail-opening a reorg-timing check instead of failing closed - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg a prior tenure by comparing how long elapsed between the reorged tenure's first block being locally approved and the new sortition. When the local `BlockInfo.approved_time` for that block is missing, the code substitutes `0` and logs it as a "late-arriving proposal", which unconditionally satisfies the `< first_proposal_burn_block_timing` check and permits the reorg regardless of the block's actual on-chain timing.

### Finding Description
The relevant branch is: [1](#0-0) 

`proposal_to_sortition` is meant to measure the real gap between the reorged tenure's first-block approval and the new burn block, and a *small* gap is what the protocol treats as excusable ("late-arriving," so the next miner couldn't reasonably have known about it) - a genuinely small gap causes `superseded_tenures.push(tenure)` (reorg permitted); a large gap falls through to `return Ok(false)` (reorg refused). When `local_block_info.approved_time` is `None`, the code hard-codes `proposal_to_sortition = 0`, i.e., the *most* permissive possible value, guaranteeing the reorg-permitted branch is taken irrespective of when the block was actually produced/accepted.

This is inconsistent with the sibling guard a few lines above it: when `signer_db.get_first_approved_block_in_tenure` returns `None` entirely (no local knowledge of the tenure at all), the function fails closed and returns `Ok(false)`: [2](#0-1) 
But when the `BlockInfo` exists yet the single timestamp field `approved_time` is absent (e.g. because the local signer restarted and lost the pre-commit timestamp, or never locally-approved the block and only observed the aggregated group signature), the same "missing information" scenario fails *open* instead, defeating the guard's purpose (CANONICITY: the reorg-permitted flag should equal real on-chain timing evidence, not an artifact of local bookkeeping loss).

An attacker who wins a single sortition slot can propose a `BlockProposal`/tenure-change that reorgs a prior tenure whose first block was actually accepted well before the burn-block transition (i.e., a reorg that should be refused). Any signer in the network whose local `approved_time` for that block is unset — a state reachable through ordinary signer restarts or through the signer never itself locally-accepting that block (only witnessing the aggregated signature) — will compute `proposal_to_sortition = 0` and incorrectly treat the reorg as permitted, then sign subsequent blocks built on the illegitimate reorg.

### Impact Explanation
This breaks the timing-canonicity guard that is supposed to gate whether a signer will sign blocks continuing an out-of-band reorg of a prior tenure. A signer hitting this branch will sign a block building on a tenure choice that the protocol's own rule says should have been rejected — matching the Critical category "a signer signing an invalid, non-canonical, or conflicting block." The bug is deterministic and repeatable any time the precondition (`approved_time == None`) holds for the reorged tenure's first block on a given signer, which requires no special access — only a normal restart or a block that reached this signer via aggregated signature rather than direct local approval.

### Likelihood Explanation
The precondition is not rare: signer processes routinely restart (upgrades, crashes, maintenance) and lose in-memory/derived state; also `approved_time` may simply never have been stamped on this signer if it did not itself locally pre-commit that specific block. The attacker only needs to win one sortition slot and gossip a normal block/tenure proposal that reorgs a tenure whose first block was, in fact, accepted early (i.e., a reorg that should fail the timing check) — no signer key, no majority coordination, and no privileged access are required from the attacker's side. The condition is per-signer and independent across the signer set, so its exploitability against any *one* signer's vote is high, though causing a network-wide finalized reorg would still require this condition (or an equivalent failure) to coincide across enough signer weight, which the attacker cannot directly force.

### Recommendation
Do not substitute `0` for a missing `approved_time`. Fail closed in the same way as the fully-missing-`BlockInfo` case: if `approved_time` is unavailable, either (a) treat the tenure as not-provably-late and refuse the reorg (`return Ok(false)`), or (b) fall back to a different verifiably-timestamped signal already present on `BlockInfo` (e.g., `proposed_time`, or the same `signed_self`/`signed_group` timestamps that `get_tenure_last_block_info` uses per its own comment about `approved_time` being unreliable) rather than assuming the most exploit-favorable value.

### Proof of Concept
Rust test plan (in `stacks-signer/src/chainstate/tests/`, alongside existing `check_parent_tenure_choice` tests in `v2.rs`):
1. Construct a `SortitionData` whose `parent_tenure_id` differs from `prior_sortition` (forcing the reorg-check path) and a mocked `StacksClient`/`get_tenure_forking_info` returning one reorged tenure with `first_block_mined = Some(block_id)`.
2. Seed `signer_db` so `get_globally_accepted_block_count_in_tenure` returns `1` and `get_first_approved_block_in_tenure` returns a `BlockInfo` for that tenure with `approved_time = None` but a `proposed_time`/`signed_group` far in the past (simulating an early, well-timed block that should NOT qualify for reorg).
3. Seed `get_burn_block_receive_time` to return `Some(now)`.
4. Call `check_parent_tenure_choice(&mut signer_db, &client, &first_proposal_burn_block_timing)`.
5. Assert it returns `Ok(true)` (reorg permitted) — demonstrating the fail-open bug — then contrast with a second run where `approved_time` is set to a timestamp reflecting the true early-acceptance time, asserting `Ok(false)` is returned instead, proving the equality "reorg permitted == actual on-chain timing warrants it" is violated only in the missing-timestamp case.
