### Title
Vault-share donation inflates `totalInterestDueNow()` and bypasses the `maxApr` sanity cap in minted-interest programmable mode, letting a tranche-holder/vault-depositor attacker mint unbacked tranche value - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` measures epoch vault interest as the delta of `convertToAssets(shares)` against a stored baseline (`_vaultNetInterest`, lines 337-346). Because `convertToAssets` counts raw token donations to the external ERC4626 vault, an attacker who is both a vault shareholder and a tranche holder can donate underlying to the vault during a running epoch and have it priced as earned interest via `totalInterestDueNow()` (lines 330-334). In `IdleCDOEpochVariant.stopEpochWithDuration`, the only bound on inflated interest, the `_maxApr` check, is gated on `_mintInterest && _interest > 1` (line 377), but programmable mode is invoked with the sentinel `_interest = 0`, so the cap never runs — the same bug class as CVE-2021-43844, where the `file://` scheme slipped past a check that was assumed to cover all URLs: the guard validates one input channel while the dangerous value arrives through another.

### Finding Description
In `ProgrammableBorrower`, `vaultInterestAccrued`/`totalInterestDueNow` derive interest purely from the vault share-to-asset conversion (`_currentVaultAssets() + epochWithdrawnFromVault` vs `epochStartVaultAssets + epochDepositedToVault`, lines 339-341). There is no isolation between "interest" and raw ERC20 donations made directly to the vault contract: any tokens pushed to the vault raise `convertToAssets` and are counted as net interest.

In `IdleCDOEpochVariant.sol` lines 361-362, `stopEpochWithDuration` sources `_expectedInterest` from `prepareStopEpochWithApr0`, which reads `totalInterestDueNow()`. The sanity cap that would reject absurd interest, `_checkNotAllowed(_maxApr != 0 && _grossInterest > _calcInterestWithApr(getContractValue(), _maxApr) + _pendingWithdrawFees)`, only executes when `_mintInterest && _interest > 1` (line 377). In programmable mode the honest manager calls `stopEpoch(0, 0)` (see `test/foundry/ProgrammableBorrowerCreditVault.t.sol` lines 218-219), so `_interest == 0` and the check is skipped entirely, even though `_grossInterest` is attacker-influenced. Lines 428-430 then call `_strategy.mintStrategyTokens(_grossInterest)`, minting strategy-token value against interest that was never received as cash, and `_updateAccounting()` (line 436) distributes it into tranche prices.

Attack path (running epoch, `isInterestMinted = true`, `isProgrammableBorrower = true`):
1. Attacker (a KYC-passing lender) deposits a large AA position and is also a depositor in the programmable borrower's ERC4626 vault — an explicitly permitted attacker role ("a user of the programmable borrower's ERC4626 vault").
2. During the running epoch, attacker transfers `D` underlying directly to the vault contract (standard ERC4626 donation). Their own vault shares absorb `D` proportionally, so the donation is fully recoverable through their vault position.
3. `_vaultNetInterest` returns `interest += D`; `totalInterestDueNow` includes `D`.
4. Honest manager calls `stopEpoch(0, 0)`. The `_maxApr` cap is skipped (`_interest = 0`), and `_strategy.mintStrategyTokens(grossInterest + D)` mints unbacked value into tranche prices.
5. Attacker redeems tranche tokens at the inflated `virtualPrice`, withdrawing real underlying belonging to other lenders, then redeems their vault shares to recover `D`.

The skim guard (`_skimDonatedAssets`) does not help: the donation never touches the CDO contract, it lives inside the external vault and is legitimized as "interest" by `convertToAssets`. `defaulted`/`isEpochRunning` gating only restricts timing to the running phase, which is exactly when the attack operates.

### Impact Explanation
Direct theft of other lenders' principal. Each donated unit `D` produces `D` minted strategy tokens of unbacked tranche value, of which the attacker captures a fraction equal to their tranche share `f`. Because the attacker recovers `D` through their vault shares (net donation cost ≈ 0 when they dominate the vault's share supply), profit ≈ `f·D`, bounded only by the pool's withdrawable liquidity. With `f ≈ 1` (attacker is the dominant lender in a small pool), they can mint-price the entire vault balance, including other depositors' principal, and drain it via tranche redemption or queued withdraw claims paid from real underlying.

### Likelihood Explanation
Requirements are all attacker-permitted: holding tranche tokens (KYC lender), holding vault shares (the external ERC4626 is permissionless), and timing a transfer before the honest manager's `stopEpoch`. No privileged role misbehaves. The only mitigating factors are that the vault must tolerate raw-donation inflation (true of standard ERC4626 `convertToAssets` = `totalAssets/totalSupply` vaults such as MetaMorpho) and that the attacker needs enough vault share dominance to recapture the donation; both are cheap when the vault sleeve is small relative to the tranche position.

### Recommendation
- Apply the `_maxApr` sanity cap to the resolved `_grossInterest`/`expectedEpochInterest` regardless of the `_interest` sentinel, i.e., whenever `isInterestMinted` (and especially when `isProgrammableBorrower`), the computed gross interest must not exceed `_calcInterestWithApr(getContractValue(), maxApr)`; the current `_interest > 1` gate silently disables it in programmable mode.
- In `ProgrammableBorrower`, decouple interest accounting from raw `convertToAssets` deltas: track principal flows and treat unexplained asset jumps as non-interest (or bound vault yield to a plausible rate over `epochStartVaultAssets`), mirroring the upstream fix of explicitly rejecting the dangerous input class instead of relying on a check that assumed coverage.

### Proof of Concept
Reproducible Foundry fork PoC sketch (extend `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which already runs against a live MetaMorpho vault):

```solidity
// setup identical to testProgrammableBorrowerStopEpochAutoRealizesInterestWithRealVault
uint256 amount = 10_000 * oneScale;
vm.prank(owner);
cdoEpoch.setIsInterestMinted(true);
idleCDO.depositAA(amount);          // attacker is dominant AA lender
_startEpochAndCheckPrices(0);

// attacker is also a vault depositor so the donation is recoverable
uint256 attackerVaultDeposit = 1 * oneScale;
deal(USDC, attacker, attackerVaultDeposit + DONATION, true);
vm.startPrank(attacker);
underlying.approve(address(morphoVault), attackerVaultDeposit);
morphoVault.deposit(attackerVaultDeposit, attacker);

// donate D directly to the vault -> convertToAssets inflates -> counted as interest
uint256 DONATION = 2_000 * oneScale;
underlying.transfer(address(morphoVault), DONATION);
vm.stopPrank();

uint256 interestBefore = programmableBorrower.totalInterestDueNow();

vm.warp(cdoEpoch.epochEndDate() + 1);
uint256 inflated = programmableBorrower.totalInterestDueNow();
assertApproxEqAbs(inflated - interestBefore, DONATION, 10); // donation priced as interest

vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);           // _interest == 0 -> maxApr cap skipped

// tranche price now reflects DONATION minted as unbacked strategy tokens
uint256 shares = morphoVault.balanceOf(attacker);
vm.prank(attacker);
morphoVault.redeem(shares, attacker, attacker); // attacker recovers donation

// attacker then redeems AA tranche tokens at inflated virtualPrice,
// extracting other lenders' real underlying; profit ~= f * DONATION
```

Key mechanics: `totalInterestDueNow()` rises by the full donation (`ProgrammableBorrower.sol:330-346`), `stopEpoch` mints it without the `_maxApr` guard because `_interest == 0` (`IdleCDOEpochVariant.sol:374-380`, `428-430`), and the attacker recovers `D` through their own vault shares, making the unbacked tranche-price inflation nearly free.
