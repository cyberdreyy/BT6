### Title
Post-default instant withdraws bypass the claim-first guard and pay an unbacked receipt at par, conflating receipts from different epochs under one aggregate claim - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug is a missing reverse mapping: two accounts can point to the same `cidNFTID` because registration never clears the previous owner's pointer. The idle-tranches analog lives in `IdleCreditVault.requestInstantWithdraw` / `claimInstantWithdrawRequest`. Normal withdraw requests were hardened so a user cannot stack receipts across epochs (`requestWithdraw` reverts while an unclaimed loss-adjusted receipt exists, and its post-default branch reverts unless every receipt bucket is zero). `requestInstantWithdraw` has no equivalent guard: after `finalizeDefaultRecovery`, a lender can open a brand-new instant receipt, which is recorded under a *new* epoch in `instantWithdrawsRequestsByEpoch` while being folded into the single aggregate `instantWithdrawsRequests[_user]`. The claim path then pays the old defaulted receipt at `defaultRecoveryPrice` and the new, never-funded receipt at par via `_transferFundedClaim`.

### Finding Description
- `requestWithdraw` post-default enforces: `_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0` → revert, and deliberately mints the post-default receipt under a haircut-aware path (`contracts/strategies/idle/IdleCreditVault.sol` lines 247-258).
- `requestInstantWithdraw` (lines 356-375) performs none of these checks. Post-default it still: burns CDO tokens, mints receipt tokens to the user, increases `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws`.
- `claimInstantWithdrawRequest` (lines 380-392) first clears the defaulted-epoch basis through `_claimDefaultedInstantWithdrawRequest` (haircut paid from `defaultRecoveryReserve`), then takes `amount = instantWithdrawsRequests[_user]` — the residual is the new post-default receipt — burns it, and calls `_transferFundedClaim`, which pays full underlying as long as the transfer does not dip into `defaultRecoveryReserve` (lines 897-906).
- Like the AddressRegistry bug, the epoch-indexed record (`instantWithdrawsRequestsByEpoch`, keyed by "identity" = request epoch) and the aggregate pointer (`instantWithdrawsRequests`) diverge: the new receipt's epoch marker in `instantWithdrawClaimsByEpoch[epochNumber]` can never match `defaultRecoveryEpoch`, so `_claimDefaultedInstantWithdrawRequest` will never touch it, yet the aggregate payout treats both as the same funded claim.

### Impact Explanation
The post-default receipt is never funded: the borrower has defaulted, `collectInstantWithdrawFunds` is never called for it, and `pendingInstantWithdraws` accounting only matters for default finalization which already ran. `_transferFundedClaim` releases any non-reserve underlying sitting in the strategy — funded receipts belonging to other users, post-finalization borrower repayments sent via `sendInterestAndDeposits`, or recovery amounts above the computed basis (`finalizeDefaultRecovery` allows `recoveryPrice > 1`, leaving excess underlying unreserved). The attacker therefore receives underlying that belongs to other claimants at par while everyone else is haircutted at `defaultRecoveryPrice`. If the vault balance is entirely reserve, the same call reverts, permanently freezing the attacker's own residual receipt — still a broken "one receipt, one priced payout" invariant.

### Likelihood Explanation
Requires only a KYC-passed lender holding tranche tokens after a borrower default and `finalizeDefaultRecovery`. The post-default `requestWithdraw` branch explicitly preserves "request/claim UX after default", showing the CDO continues to route withdraw flows post-default; `requestInstantWithdraw` is gated only by `_onlyIdleCDO` in the strategy. The attacker needs no privileged action — one instant request plus one claim.

### Recommendation
Mirror the `requestWithdraw` post-default guard in `requestInstantWithdraw`: after `defaultRecoveryFinalized`, either revert on any instant request, or require the caller to have fully claimed `instantWithdrawsRequests[_user]`/`instantWithdrawsRequestsByEpoch` receipts first and account the new receipt separately so it can only be paid once funded via `collectInstantWithdrawFunds`. Concretely:

```solidity
if (defaultRecoveryFinalized) {
  if (instantWithdrawsRequests[_user] != 0) revert NotAllowed();
}
```

and skip `pendingInstantWithdraws`/claim-aggregation for post-default receipts, or track a dedicated post-default instant basis per epoch.

### Proof of Concept
Foundry fork scenario:

```solidity
// Epoch N running: user deposits via CDO, then:
cdo.requestInstantWithdraw(amount);          // -> strategy.requestInstantWithdraw
// borrower defaults; CDO calls finalizeDefaultRecovery(...)
// recoveryPrice = 50e16 (50%)

// Attacker (KYC'd lender with tranche tokens), post-default:
cdo.requestInstantWithdraw(x);               // allowed: no guard
// strategy state: instantWithdrawsRequests[att] = defaultedBasis + x
//                 instantWithdrawsRequestsByEpoch[att][defaultEpoch] = defaultedBasis
//                 instantWithdrawsRequestsByEpoch[att][newEpoch]     = x

cdo.claimInstantWithdraw();                  // -> claimInstantWithdrawRequest(att)
// _claimDefaultedInstantWithdrawRequest pays defaultedBasis * 50% from reserve
// then _transferFundedClaim pays x AT PAR from any non-reserve balance

// assert attacker received defaultedBasis/2 + x while peers only get 50%
```

Verified against `contracts/strategies/idle/IdleCreditVault.sol` lines 243-295, 356-392, 760-856, 897-917. Caveat: exact reachability depends on the CDO-side instant-withdraw entrypoint remaining callable while `defaulted()` is true; the strategy code itself imposes no such check, and the analogous normal-withdraw path is explicitly designed to operate post-default, so the PoC should confirm the CDO entrypoint on fork.
