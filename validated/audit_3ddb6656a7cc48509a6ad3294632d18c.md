### Title
Unbounded per-blockhash growth of `StatusCache` from durable-nonce transactions makes `get_status_any_blockhash` scan cost proportional to attacker-authored on-chain nonce diversity - ([File: runtime/src/status_cache.rs])

### Summary
`StatusCache::insert` creates a new top-level `self.cache` entry for every distinct transaction blockhash it sees, and durable-nonce blockhashes (unlike regular recent blockhashes) do not expire on a fixed ~150-slot schedule — they only leave the cache when `purge_roots` advances the rooted-slot cutoff past their last-observed slot, which happens across the full `max_root_entries` (`MAX_RECENT_BLOCKHASHES`) rolling window. An attacker who creates and advances many durable-nonce accounts can therefore inflate the number of distinct keys in `self.cache` roughly linearly with the number of unique nonce blockhashes they get included on-chain within that window. `get_status_any_blockhash` performs a linear scan over `self.cache.keys()` for a single lookup, so its per-call cost scales with this attacker-controlled cache size.

### Finding Description
`StatusCache::insert` (runtime/src/status_cache.rs:210-239) inserts a new `(Slot, usize, KeyMap<T>)` entry into `self.cache: KeyStatusMap<T>` keyed by `transaction_blockhash` whenever a never-before-seen blockhash is used: [1](#0-0) 

`add_to_slot_delta` similarly grows `self.slot_deltas` per slot/blockhash pair: [2](#0-1) 

The only reclamation mechanism is `purge_roots`, which removes `self.cache`/`self.slot_deltas` entries only once the rooted-slot cutoff (based on retaining the newest `max_root_entries`, i.e. `MAX_RECENT_BLOCKHASHES`, roots) passes the blockhash's last-observed slot: [3](#0-2) 

Regular recent blockhashes are naturally capped because the runtime only accepts transactions referencing one of a bounded set of ~recent blockhashes (rejected once too old), so `self.cache` size for "normal" blockhashes self-limits. Durable-nonce transactions break this assumption: a nonce account's stored blockhash only changes when the nonce is advanced, so an attacker can create arbitrarily many nonce accounts, each carrying its own unique blockhash value, and submit one transaction per nonce account. Each such transaction inserts a brand-new `self.cache` key that survives until it ages out of the entire `max_root_entries`-root retention window (not just until the containing slot is rooted). The code's own test comments acknowledge this durable-nonce non-expiry property explicitly: [4](#0-3) 

`get_status_any_blockhash` is a linear scan over every key currently in `self.cache`: [5](#0-4) 

This function is reachable from `Bank`'s signature-status lookups (used for RPC `getSignatureStatuses`/`getTransaction` code paths that need to find a signature without knowing its exact blockhash). Because its cost is `O(number of distinct blockhashes currently cached)`, and that count is inflatable by attacker-authored on-chain nonce diversity rather than by any RPC-side parameter, a single low-rate RPC call pays a cost proportional to attacker-controlled on-chain state rather than a fixed bound.

### Impact Explanation
This is an unbounded per-request CPU cost issue: the cost of a single `getSignatureStatuses`/`getTransaction` call is not bounded by an explicit limit but grows with the number of distinct nonce blockhashes an attacker has caused to be inserted into the validator's in-memory `StatusCache`. This matches the "RPC DoS from unbounded per-request cost tied to attacker-controlled on-chain data size" bounty category, since the attacker needs only normal transaction submission privileges (no leader/validator control) and a single subsequent RPC call to trigger the expensive scan.

### Likelihood Explanation
Feasibility requires the attacker to fund and advance many durable-nonce accounts (bounded only by the attacker's own transaction throughput and the standard per-block transaction/compute limits, not by any StatusCache-specific defense) over the multi-minute `max_root_entries` retention window, then issue one qualifying RPC call. This is achievable by a single unprivileged client at normal transaction rates and does not require staked/leader/gossip control, matching the allowed threat model in this audit's rules. The main uncertainty is the exact magnitude of achievable cache inflation in a live cluster (bounded by block-level compute/transaction-count limits over the retention window), which would need to be measured empirically.

### Recommendation
Bound the cost of `get_status_any_blockhash` and/or the size of `self.cache`/`self.slot_deltas` independent of the number of distinct blockhashes observed — e.g., cap the number of distinct blockhash entries tracked (evicting oldest/least-recently-used regardless of durable-nonce non-expiry), or require callers needing "any blockhash" lookups to supply bounded search hints, and add explicit metrics/limits so a single RPC request cannot incur unbounded scan cost regardless of on-chain nonce-account population.

### Proof of Concept
Rust unit/integration test plan (extending `runtime/src/status_cache.rs` test module):
```rust
#[test]
fn test_get_status_any_blockhash_scales_with_distinct_blockhashes() {
    let mut status_cache = BankStatusCache::default();
    let ancestors = Ancestors::from(vec![0]);
    const N: usize = 50_000; // attacker-controlled distinct nonce blockhashes
    for i in 0..N {
        let blockhash = Hash::new_unique(); // simulates distinct advanced nonce blockhash
        status_cache.insert(&blockhash, Signature::new_unique(), 0, ());
    }
    let missing_sig = Signature::new_unique();
    let start = std::time::Instant::now();
    let result = status_cache.get_status_any_blockhash(missing_sig, &ancestors);
    let elapsed = start.elapsed();
    assert!(result.is_none());
    // Assert elapsed time/scan count scales ~linearly with N, demonstrating
    // no fixed upper bound independent of attacker-inflated cache size.
    assert!(status_cache_cache_len(&status_cache) == N);
}
```
Expected result: the time to execute a single `get_status_any_blockhash` call grows proportionally with `N` (number of distinct attacker-inserted blockhashes), with no cap independent of `N`, confirming the per-request cost is bound by attacker-authored on-chain nonce diversity rather than a fixed limit.

    pub fn purge_roots(&mut self) {
        let max_root_entries = self.max_root_entries();
        if self.roots.len() > max_root_entries {
            let num_roots_to_purge = self.roots.len() - max_root_entries;
            let mut roots = self
                .roots
                .iter()
                .copied()
                .collect::<SmallVec<[Slot; 0x200]>>();
            let (_, cutoff, _) = roots.select_nth_unstable(num_roots_to_purge - 1);
            let cutoff = *cutoff;

            self.roots.retain(|root| *root > cutoff);
            self.cache.retain(|_, (fork, _, _)| *fork > cutoff);
            self.slot_deltas.retain(|slot, _| *slot > cutoff);
        }
    }
