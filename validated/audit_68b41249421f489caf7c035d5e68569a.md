### Title
Post-default instant withdraw requests widen claim scope from haircutted to par, draining prefunded claim funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` has an explicit `defaultRecoveryFinalized` branch that routes post-default requests into the `postDefaultRequests` ledger (already-haircut, reserve-paid). `requestInstantWithdraw` has no equivalent branch: after default finalization it still mints the caller a 1:1 underlying receipt and books it in `instantWithdrawsRequests`. When `defaultInstantWithdrawsFinalized` is false (no *unfunded* instant remainder at finalization), `claimInstantWithdrawRequest` skips the defaulted-claim path entirely and pays the full receipt via `_transferFundedClaim` — letting an attacker convert haircut-valued tranches into par-valued claims and spend underlyings that belong to already-funded instant claimants.

### Finding Description
Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` (lines 243–258) checks `defaultRecoveryFinalized` and creates a `postDefaultRequests` entry paid from `defaultRecoveryReserve` at the post-haircut price.
- `requestInstantWithdraw` (lines 356–375) performs no post-default classification: it burns the CDO's strategy tokens, `_mint`s `_amount` to `_user`, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws`.
- `claimInstantWithdrawRequest` (lines 380–393) only clears defaulted receipts when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. `defaultInstantWithdrawsFinalized` is set at finalization to `pendingInstantWithdraws != 0` (line 696).
- `_transferFundedClaim` (lines 897–907) pays at par from any balance above `defaultRecoveryReserve`; `_defaultPrefundedInstantReserve` (lines 716–723) returns 0 when `pendingInstantWithdraws == 0`, so *fully prefunded* current-epoch instant claims are excluded from the reserve and remain in the strategy's free balance.

Attack (epoch phase: defaulted → `finalizeDefaultRecovery` executed; attacker is any KYC'd tranche holder):

1. Epoch E has instant withdraw requests that were fully funded via `collectInstantWithdrawFunds`, so at `finalizeDefaultRecovery` `pendingInstantWithdraws == 0` → `defaultInstantWithdrawsFinalized = false`, and the prefunded instant balance sits outside `defaultRecoveryReserve`.
2. Attacker calls the CDO's instant-withdraw entry point, burning tranche tokens priced at the post-default haircut `virtualPrice` (≈ `defaultRecoveryPrice / RECOVERY_FULL` of par).
3. `requestInstantWithdraw` mints `_amount` strategy-token receipts 1:1 (receipts are underlying-denominated) and credits `instantWithdrawsRequests[attacker]`.
4. `claimInstantWithdrawRequest` skips `_claimDefaultedInstantWithdrawRequest` (flag false) and pays the full `_amount` via `_transferFundedClaim`, which only guards `balance - defaultRecoveryReserve >= _amount`. The prefunded instant balance satisfies this.
5. Attacker paid ~`recoveryPrice * amount` in tranche value and withdrew `amount` of underlyings earmarked for other users' funded instant claims.

The broken invariant is receipt classification: the set of "funded, par-paid" instant claims is fixed at finalization by `defaultInstantWithdrawsFinalized`, but an attacker-controlled post-finalization request is silently admitted into that scope — the direct analog of an attacker widening a strict/namespace scope to cluster-wide via untrusted input.

### Impact Explanation
Theft of other users' funded instant-withdraw balances. The attacker burns tranches worth `amount * defaultRecoveryPrice / RECOVERY_FULL` and receives `amount` underlying, a profit of `amount * (1 - recoveryPrice)`. Victims holding legitimately funded instant receipts (or other non-reserve balances) later revert on `NotAllowed` in `_transferFundedClaim` or receive nothing — permanent loss up to the full prefunded instant balance.

### Likelihood Explanation
Requires three preconditions: (a) a borrower default with `finalizeDefaultRecovery` executed, (b) `pendingInstantWithdraws == 0` at finalization while prefunded instant claim funds remain in the strategy (so `defaultInstantWithdrawsFinalized` is false and free balance exceeds the reserve), and (c) the CDO still forwards `requestInstantWithdraw` after default finalization. Precondition (c) could not be fully verified — if `IdleCDOEpochVariant` gates instant withdrawals on a running epoch or a `!defaulted` check, the strategy-side gap is unreachable; this should be confirmed, but the missing `defaultRecoveryFinalized` branch is an inconsistency regardless of the CDO guard (defense-in-depth on the privileged callee).

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert outright or route through a haircut-priced `postDefaultRequests`-style ledger paid via `_transferDefaultRecovery`, and require the user to settle any outstanding `instantWithdrawsRequests`/`instantWithdrawsRequestsByEpoch` entries first. Alternatively, make `claimInstantWithdrawRequest` always run `_claimDefaultedInstantWithdrawRequest` once `defaultRecoveryFinalized` (not only when `defaultInstantWithdrawsFinalized`), so post-finalization receipts recorded under `defaultRecoveryEpoch` are haircutted before the par path.
