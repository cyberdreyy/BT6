### Title
Mid-epoch withdraw requests grow `pendingWithdraws` but never update `ProgrammableBorrower.epochPendingWithdraws`, so borrower draws can consume liquidity already owed to receipts and force a spurious default at `stopEpoch` - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower` reserves liquidity for pending withdraw receipts only once, in `onStartEpoch`, via `epochPendingWithdraws` (`ProgrammableBorrower.sol:205`). `availableToBorrow` then treats `totalAssets - epochPendingWithdraws` as freely drawable (`ProgrammableBorrower.sol:350-355`). However, `IdleCreditVault.requestWithdraw` increments `pendingWithdraws` at any time during a running epoch (`IdleCreditVault.sol:279`), and nothing propagates that growth to the borrower reserve — `epochPendingWithdraws` is only ever written in `onStartEpoch`, `onStopEpoch`, and `onDefault`. This is the direct analog of CVE-2024-53220: a resource requirement that accrues *after* the accounting snapshot (dirty data / new withdraw receipts) is not accounted in the reservation function (`__get_secs_required` / `availableToBorrow`), so the subsequent allocation (`new_curseg` / borrower `borrow` + `getFundsFromBorrower` pull) runs out and the system panics (kernel BUG / `_handleBorrowerDefault`).

### Finding Description
Epoch phase: running epoch on a programmable-borrower credit vault.

1. Epoch starts. `onStartEpoch` snapshots `epochPendingWithdraws = pendingWithdraws` at that moment (say `P0`). `availableToBorrow = totalAssets - P0`.
2. The honest borrower (or authorized executor) draws up to `availableToBorrow`. This is a permitted sequence per the rules — the borrower is honest and merely uses the facility.
3. An attacker who is a KYC-passing lender calls `requestWithdraw` mid-epoch. `IdleCreditVault.requestWithdraw` burns the CDO's strategy tokens, mints receipts, and does `pendingWithdraws += _amount` with no guard requiring `isClosed` (only `epochEndDate() == 0` skips it, `IdleCreditVault.sol:277-280`).
4. `stopEpoch` re-reads the *current* `pendingWithdraws` via `_strategy.pendingWithdraws()` (`IdleCDOEpochVariant.sol:364`) and demands `_amountToPullFromBorrower + _pendingWithdraws` through `onStopEpoch` → `getFundsFromBorrower`. But the borrower was never told to re-reserve the new `pendingWithdraws`, so its remaining assets (`onHand + _currentVaultAssets`) can be less than the pull amount.
5. In `onStopEpoch`, `shortfall > _currentVaultAssets()` returns `true` (success), so `stopEpoch` proceeds to `getFundsFromBorrower`'s `transferFrom`, which fails on insufficient balance/allowance-covered liquidity, triggering `_handleBorrowerDefault` (`IdleCDOEpochVariant.sol:398-402`, `408`).

Broken invariant: solvency/fair loss waterfall. The pool is forced into `defaulted` state even though the borrower is economically solvent — the liquidity was double-committed: once to withdraw receipts (which `pendingWithdraws` tracks) and once to the borrower draw (which `epochPendingWithdraws` failed to exclude). Receipt holders and active LPs are then haircut through `defaultRecoveryPrice`/`lossRecoveryPriceByEpoch` instead of being paid at par from a still-good facility.

Existing guards do not stop this: `requestWithdraw` has no cap tied to borrower liquidity; `availableToBorrow` only subtracts the stale snapshot; `onStopEpoch` explicitly returns success when the vault can't cover, deferring to the default path.

### Impact Explanation
A spurious borrower default crystallizes losses for all tranche holders and pending receipt claimants. The crystallized haircut is approximately `attacker-requested _amount` (the unfunded delta between the stale reserve and the grown `pendingWithdraws`), minus any borrower recovery via `finalizeDefaultRecovery`. This is insolvency-by-accounting-error: obligations were committed twice because one side of the ledger (borrower reserve) was never updated when the other side (strategy `pendingWithdraws`) grew — the same "consumed free segments not accounted → run out at allocation" failure as the f2fs bug.

### Likelihood Explanation
Requires the programmable-borrower deployment mode, an epoch where the borrower draws near `availableToBorrow`, and a mid-epoch withdraw request. All three are ordinary operations: draws are the facility's purpose and `requestWithdraw` is permissionless for any KYC'd tranche holder. No privileged misbehavior is needed — the attacker is only a lender exercising withdrawals.

### Recommendation
Keep the borrower reserve in sync with the live liability. Either (a) have `IdleCreditVault.requestWithdraw` / the CDO notify the programmable borrower to increase `epochPendingWithdraws` by `_amount` (revert the request if the borrower cannot cover it, i.e. return ENOSPC early like the f2fs fix), or (b) make `availableToBorrow` read the live `IIdleCDOEpochVariant → strategy.pendingWithdraws()` instead of the stale `epochPendingWithdraws` snapshot, so subsequent draws can never consume receipt-committed liquidity.
