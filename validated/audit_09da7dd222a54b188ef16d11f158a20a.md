### Title
Stale confirmations from removed multisig members/keys still count toward the confirmation threshold - ([File: multisig2/src/lib.rs], also [File: multisig/src/lib.rs])

### Summary
When a multisig member (or access key in the v1 contract) is removed via `DeleteMember`/`DeleteKey`, the contract only purges confirmations for requests that member *originated*, not confirmations that member previously *cast* on requests originated by someone else. Those stale confirmation entries remain in the `confirmations` set and are still counted by `confirm()` when checking `confirmations.len() + 1 >= num_confirmations`, letting a request execute with fewer than `num_confirmations` currently-live members' approval.

### Finding Description
`confirm()` computes the threshold purely from the size of the stored `HashSet` for a request, without re-validating that every entry in that set still corresponds to a current member: [1](#0-0) 

`delete_member` only removes outstanding *requests originated by* the removed member, and clears `confirmations` only for those specific requests — it never scans other requests' confirmation sets for entries belonging to the removed member: [2](#0-1) 

The equivalent v1 contract has the identical gap in `DeleteKey` handling: [3](#0-2) 

So the binding that should hold — `count(confirmations for request) == count(confirmations from members who are still live members)` — is broken: a removed member's historical confirmation continues to be credited toward the threshold on any request they didn't originate themselves.

### Impact Explanation
This lets a request execute with fewer than `num_confirmations` currently-authorized approvals, i.e. "a multisig request executed below threshold" (Critical per the accepted impact categories), since the actions executable via a confirmed request include `Transfer` (move NEAR) and `AddKey`/`AddMember` (grant new access), as seen in `execute_request`: [4](#0-3) 

### Likelihood Explanation
No privileged/owner access is needed beyond being (or having been) a normal multisig member — the actor model for this contract. The scenario only requires: (1) a request pending with partial confirmations including one from a member who is later removed, and (2) enough remaining live members to reach `num_confirmations - 1` further confirmations. This is a realistic operational sequence (member rotation/removal is a documented supported action) rather than a contrived edge case.

### Recommendation
When removing a member/key, iterate all outstanding requests' confirmation sets (not just those the member originated) and strip that member's/key's entry, or alternatively re-validate at `confirm()` time that every entry in the stored confirmation set still belongs to a current member/key before counting it toward the threshold.

### Proof of Concept
Using `multisig2/src/lib.rs` semantics with members `[A, B, C, D, E]` and `num_confirmations = 3`:
1. `A.add_request(maliciousRequest)` → `request_id = 0`, `confirmations = {}`.
2. `B.confirm(0)` → `confirmations = {B}` (`1+1=2 < 3`).
3. `D.confirm(0)` → `confirmations = {B, D}` (`2+1=3 >= 3`? no — wait: `len()=1`, so `1+1=2 < 3`, stored).
4. Separately, members `A, C, E` confirm a `DeleteMember{D}` request, removing `D` from `members` and calling `delete_member` — this only clears confirmations for requests *originated by* `D`, so request `0`'s set `{B, D}` is untouched.
5. `C.confirm(0)` → `confirmations.len() = 2` (`{B, D}`) `+ 1 = 3 >= num_confirmations (3)` → `maliciousRequest` executes.
6. Result: `maliciousRequest` (e.g. `Transfer` of the account's NEAR, or `AddKey`) executes with approvals effectively only from live members `B` and `C`, one short of the intended 3-of-N threshold, because removed member `D`'s stale confirmation was still counted.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();

            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
