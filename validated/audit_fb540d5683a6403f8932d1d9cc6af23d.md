### Title
Unprivileged ERC4626 liquidity drain can indefinitely block programmable-borrower epoch settlement - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower.onStopEpoch` treats an economically covered but presently illiquid ERC4626 withdrawal as a retryable failure and reverts `StopEpochVaultLiquidityUnavailable`. [1](#0-0)  Because `IdleCDOEpochVariant._stopEpoch` intentionally lets hook reverts bubble, an external user who drains the vault’s available underlying liquidity can prevent the honest manager’s `stopEpoch` transaction from completing. [2](#0-1)  The failed stop leaves `isEpochRunning`, the pause, and withdrawal-request restrictions unchanged, so pending withdrawal recipients cannot be funded or claim through the ordinary epoch path. [3](#0-2) 

### Finding Description

The programmable-borrower integration distinguishes two ERC4626 withdrawal failures:

1. If the requested shortfall exceeds the borrower contract’s total vault position, `onStopEpoch` returns successfully and allows the subsequent CDO `transferFrom` to fail into the default path. [4](#0-3) 
2. If the vault shares are economically sufficient but `vault.withdraw` reverts, `onStopEpoch` reverts `StopEpochVaultLiquidityUnavailable` instead of returning false. [5](#0-4) 

The CDO only converts a boolean `false` return into borrower default handling; it does not catch the hook revert. [2](#0-1)  Consequently, the entire `stopEpoch` call reverts before `collectWithdrawFunds`, `_updateAccounting`, and `isEpochRunning = false` execute. [6](#0-5) 

An unprivileged user of the configured ERC4626 vault or its underlying money markets can create this state by exhausting instantly withdrawable liquidity before the manager calls `stopEpoch`. [7](#0-6)  Repeating or maintaining that liquidity drain causes each later settlement attempt to revert in the same way, while the pool remains paused by the still-running epoch. [8](#0-7) 

### Impact Explanation

All funded and pending withdrawal liquidity can be temporarily frozen for as long as the attacker keeps the ERC4626 vault unable to satisfy the requested withdrawal. [1](#0-0)  The frozen amount is `_amountToPullFromBorrower + pendingWithdraws`; in minted-interest mode this includes all pending withdrawal receipts, and in close-pool mode it also includes recalled principal. [9](#0-8) 

This does not directly steal assets because the borrower contract’s vault shares must economically cover the shortfall for this branch to be reached. [4](#0-3)  The broken invariant is timely epoch settlement and withdrawal funding: liquidity exists economically, but users cannot receive it because settlement remains stuck in the running-epoch state. [10](#0-9) 

### Likelihood Explanation

The attacker does not need a privileged pool role; they only need the ability to consume the configured vault’s available underlying liquidity, which is expressly part of the programmable-borrower ERC4626 integration surface. [11](#0-10)  The attacker can observe the public `epochEndDate`, wait until settlement becomes callable, and drain liquidity before the honest manager’s `stopEpoch` transaction. [12](#0-11) 

For a MetaMorpho-style vault, liquidity can be exhausted through the underlying lending markets rather than by compromising the vault itself. [13](#0-12)  Maintaining the freeze may require capital, collateral, or interest costs, but no owner, manager, borrower, queue, or Keyring privilege is required.

### Recommendation

Do not let the external vault withdrawal revert indefinitely prevent CDO epoch settlement. [5](#0-4)  Prefer one of the following:

- Have `onStopEpoch` return `false` when covered liquidity cannot be withdrawn, and let the CDO invoke the existing default path. [2](#0-1) 
- Add a bounded settlement flow that records the liquidity failure, stops interest accounting, and permits a privileged recovery or delayed default after a defined grace period.
- Split liquidity recall from epoch finalization so a temporary ERC4626 withdrawal failure does not keep the entire CDO in the running/paused state. [14](#0-13) 

If retryability is retained, the CDO should expose an explicit recovery path for prolonged covered-but-illiquid vault states rather than relying on an honest manager repeatedly calling a transaction that can revert. [15](#0-14)

        external
    {
        _setUpProgrammableBorrowerCreditVault(
            GAUNTLET_FORK_BLOCK,
            GAUNTLET_USDC_PRIME
        );

        uint256 depositAmount = 10_000 * oneScale;
        uint256 withdrawAmount = 5_000 * oneScale;

        vm.prank(owner);
        cdoEpoch.setIsInterestMinted(true);

        idleCDO.depositAA(depositAmount);

        uint256 requested = cdoEpoch.requestWithdraw(
            withdrawAmount,
            address(aaTranche)
        );
        assertEq(strategy.pendingWithdraws(), requested);

        _startEpochAndCheckPrices(0);

        // Unprivileged ERC4626/Morpho user: borrow enough underlying market
        // liquidity that the vault has covered shares but cannot satisfy an
        // immediate withdraw(shortfall).
        address liquidityAttacker = makeAddr("liquidityAttacker");
        _drainUnderlyingMorphoLiquidity(
            GAUNTLET_USDC_PRIME,
            liquidityAttacker
        );

        assertGt(
            morphoVault.convertToAssets(
                morphoVault.balanceOf(address(programmableBorrower))
            ),
            strategy.pendingWithdraws(),
            "borrower position must economically cover the withdrawal"
        );

        vm.warp(cdoEpoch.epochEndDate() + 1);

        // Honest manager attempts normal settlement.
        vm.prank(manager);
        vm.expectRevert(
            abi.encodeWithSelector(
                StopEpochVaultLiquidityUnavailable.selector
            )
        );
        cdoEpoch.stopEpoch(0, 0);

        // Settlement never reached the success path.
        assertTrue(cdoEpoch.isEpochRunning(), "epoch remains running");
        assertEq(
            strategy.pendingWithdraws(),
            requested,
            "withdrawal receipt was not funded"
        );

        // A second attempt while liquidity remains drained fails identically.
        vm.prank(manager);
        vm.expectRevert(
            abi.encodeWithSelector(
                StopEpochVaultLiquidityUnavailable.selector
            )
        );
        cdoEpoch.stopEpoch(0, 0);

  /// Withdraws enough liquidity from the vault so IdleCDO can pull funds.
  /// @param _amountRequired total amount IdleCDO will pull via transferFrom.
  /// @param _isRequestingAllFunds whether IdleCDO is closing the pool and recalling all funds.
  /// @return success false when the borrower ledger makes close-pool settlement a real default.
  function onStopEpoch(uint256 _amountRequired, bool _isRequestingAllFunds) external nonReentrant returns (bool success) {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // if we want to close the pool and the borrower still owes any amount, consider it a failure and let IdleCDO handle it as a default instead of a close. 
    if (_isRequestingAllFunds && (borrowerPrincipal != 0 || borrowerInterestDebt != 0 || borrowerInterestAccrued != 0)) {
      return false;
    }

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (_amountRequired > onHand) {
      uint256 shortfall = _amountRequired - onHand;
      // If the vault shares do not economically cover the shortfall, let IdleCDO's later
      // transferFrom fail and use the existing default path. Only an otherwise-covered ERC4626
      // withdrawal failure should make stopEpoch retryable.
      if (shortfall > _currentVaultAssets()) return true;
      try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        if (epochAccountingActive) {
          epochWithdrawnFromVault += shortfall;
        }
        emit WithdrawnFromVault(shortfall, shares, address(this));
      } catch {
        revert StopEpochVaultLiquidityUnavailable();
      }
