### Title
Under-constrained `MaxAllowedMessageAgeSec` gateway config causes unsigned-integer underflow that disables message freshness checks - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `web-api-capabilities` gateway handler validates the freshness of an unprivileged user's trigger request using an unsigned-integer subtraction between the current time and an operator-configured `MaxAllowedMessageAgeSec` value. Because `MaxAllowedMessageAgeSec` is an unbounded `uint` with no upper-bound validation relative to `time.Now().Unix()`, and the user-supplied `Timestamp` field is likewise unconstrained, the freshness check is easy to defeat or to break entirely, mirroring the "unbounded and under-constrained variables" bug class from the referenced report (interacting time-based parameters with no cross-field bounds checking, leading to broken ordering/validation logic).

### Finding Description
`HandlerConfig.MaxAllowedMessageAgeSec` is an unconstrained `uint` loaded directly from JSON handler config with no validation of its range: [1](#0-0) 

When an unprivileged client's request reaches `HandleLegacyUserMessage` (entry point for external, unauthenticated gateway users, reachable via `gateway.ProcessRequest`), the staleness check is performed with raw unsigned arithmetic: [2](#0-1) 

`payload.Timestamp` is an `int64` field fully controlled by the requester in the JSON body (`webapicap.TriggerRequestPayload`), and only a `== 0` check is performed on it — there is no upper bound, no future-timestamp check, and no check that it is not negative: [3](#0-2) 

The comparison `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` mixes two under-constrained values:
1. `h.config.MaxAllowedMessageAgeSec` (operator-set, no bound versus `time.Now().Unix()`): if set larger than the current unix time (a plausible misconfiguration, since it's a plain seconds integer with no documented max and no validation at `NewHandler` beyond `== 0` defaulting), `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec` underflows to a very large `uint`, making the stale-message check always true — i.e., a DoS where every valid, freshly-signed request from every legitimate workflow client is rejected as "stale" regardless of Timestamp.
2. `payload.Timestamp` (attacker/unprivileged-client controlled `int64`, cast to `uint`): the requester can send any negative or arbitrarily large value. This same code path is analogous to the referenced bug's under-constrained `daPriceCurveLength`/`daDropInterval` relationship — two independently unbounded values are combined without joint validation, producing wrap-around/underflow-driven logic failures instead of a deterministic accept/reject decision.

The `NewHandler` constructor only defaults `CallbackMaxAgeSec`, `MaxSavedCallbacks`, and `CallbackPruneIntervalSec` when zero, but performs no such defaulting or bounds check for `MaxAllowedMessageAgeSec`: [4](#0-3) 

### Impact Explanation
If `MaxAllowedMessageAgeSec` is misconfigured to exceed the current epoch-seconds value (operationally easy to do by mistake, e.g. entering a value in milliseconds instead of seconds, or an intentionally "generous" value), the unsigned subtraction underflows and the handler will reject every legitimate user trigger request as "stale," producing a full denial-of-service on the `web-api-capabilities` DON path for all unprivileged clients using that gateway/DON — without requiring any attacker action, purely from an under-constrained operator-facing knob interacting with unconstrained system time. Separately, because `payload.Timestamp` (attacker-controlled) is cast to `uint` with no upper/lower bound enforcement beyond `== 0`, a requester can supply out-of-range timestamps that interact unpredictably with the same unsigned arithmetic, which can be used to probe or bypass the freshness gate depending on `MaxAllowedMessageAgeSec` value at runtime.

### Likelihood Explanation
Likelihood is moderate: the DoS trigger requires an operator misconfiguration of `MaxAllowedMessageAgeSec` (unit confusion or "safety margin" values larger than reasonable), which is plausible given there is no schema-level bound and no runtime validation rejecting out-of-range values. Given the value is unbounded and the interacting `time.Now().Unix()` is always a large but finite quantity, any config value exceeding that instantaneous unix time (technically over one billion, but not an implausible integer to accidentally set given the field's declared unit is ambiguous at the type level) immediately and permanently breaks message processing for all callers of the affected handler until the config is fixed, with no defensive clamp anywhere in the code path.

### Recommendation
- Validate `MaxAllowedMessageAgeSec` at handler construction time, rejecting or clamping values that are implausibly large (e.g., greater than some sane maximum such as a day), and reject it outright if it is large enough to make the unsigned subtraction underflow.
- Perform the freshness comparison using signed arithmetic (`int64`) instead of casting to `uint`, e.g. `time.Now().Unix() - int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp`, so the check degrades safely to "always reject" or "always accept" in a well-defined manner rather than silently underflowing.
- Bound `payload.Timestamp` on both ends: reject negative timestamps and reject timestamps too far in the future (not just checking for staleness in the past), consistent with a proper replay/freshness window.

### Proof of Concept
1. Deploy a `web-api-capabilities` gateway handler with `HandlerConfig.MaxAllowedMessageAgeSec` set to a value greater than the current `time.Now().Unix()` (e.g., due to an operator mistakenly using a millisecond-scale figure, such as `2000000000000` truncated/misapplied, or any value exceeding the current epoch-seconds count).
2. Send any correctly-signed, current-timestamp `TriggerRequestPayload` through `HandleLegacyUserMessage` (as legitimate workflow clients do, per `core/services/gateway/handlers/capabilities/handler_test.go` `triggerRequest` helper).
3. `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec` underflows to a huge `uint`, making the condition `> uint(payload.Timestamp)` true for essentially any legitimate timestamp, so the handler responds with `"stale message"` and the request is dropped — reproducible for every subsequent request until the misconfigured value is corrected, per the check at [5](#0-4) .
