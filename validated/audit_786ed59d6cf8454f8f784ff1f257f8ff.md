### Title
Shared, non-tenant-scoped global/per-node rate limiters in `ConfidentialRelayHandler.HandleNodeMessage` allow a single Owner's traffic to silently drop other tenants' relay responses - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`NewHandler` in `core/services/gateway/handlers/confidentialrelay/handler.go` builds `globalNodeRateLimiter` and `perNodeRateLimiters` from `cresettings.Default.GatewayConfidentialRelayGlobalRate`/`GatewayConfidentialRelayPerNodeRate` with no per-Owner, per-Org, or per-workflow dimension — the limiters are shared by every request routed through a given DON. `HandleNodeMessage` checks both limiters before processing any incoming node response and, if either is exhausted, silently drops the response (`return nil`), so one tenant's high request volume can cause legitimate, unrelated in-flight requests from other tenants on the same DON to time out.

### Finding Description
`NewHandler` constructs the limiters once per DON handler instance: [1](#0-0) 

These limiters are consumed in `HandleNodeMessage`, which is invoked for every signed response a DON member sends back for any active `CapabilityExec`/`SecretsGet` relay request on that DON, regardless of which Owner/workflow initiated the original request: [2](#0-1) 

Because the requestID→activeRequest map (`h.activeRequests`) is keyed only by request ID with no tenant partitioning of the rate limiters themselves, a workflow/Owner that drives a large number of `CapabilityExec` requests through the same DON causes proportionally many node responses to flow through `HandleNodeMessage`, consuming both `perNodeRateLimiters[nodeAddr]` and, more importantly, the single shared `globalNodeRateLimiter` budget. Once exhausted, `h.globalNodeRateLimiter.Allow(ctx)` returns false for *every* subsequent node response on that DON — including responses belonging to a completely different Owner's already-`fanOutToNodes`-dispatched request — and the handler returns `nil` without recording the response (`ar.addResponseForNode` is never reached). The dropped node responses can push the affected request below relay quorum, eventually causing `removeExpiredRequests`/`forwardBundleOrTerminateIfReady` to time it out with `api.RequestTimeoutError`.

There is no code path that scopes `globalNodeRateLimiter` by `Owner`/`OrgID`/`workflowID` — that tenant metadata is only available in the *request* (`CapabilityRequestParams.Owner`, etc. per `core/capabilities/confidentialrelay/handler.go:handleCapabilityExecute`), not plumbed into this gateway-side limiter.

### Impact Explanation
This is an availability/denial-of-service issue: a single low-privileged workflow Owner with a normal (non-privileged) confidential workflow can cause other tenants' confidential relay requests on the same DON to be starved of node responses and eventually time out, without needing any elevated permission, malicious node, or protocol-layer compromise. It maps to a cross-tenant denial-of-response-delivery / availability-degradation class rather than data exposure or fund movement — legitimate requests fail with `api.RequestTimeoutError` due to another tenant's traffic.

### Likelihood Explanation
Feasibility depends on how aggressively a single tenant can pump `CapabilityExec` round-trips before being throttled elsewhere (e.g., `ExecutionHelper.CallCapability`'s per-capability-name call limiters in `core/services/workflows/v2/capability_executor.go`, workflow execution concurrency limits, `Restrictions.MaxTotalCalls`). Those upstream limits are per-capability-name and per-workflow-execution, not designed to bound the *DON-wide* shared relay rate limiter, so with enough concurrent workflow executions or capability calls, especially across `F+1`-plus member DONs where every request fans out to all members, the shared global bucket can be driven to exhaustion. The exact rate values (`cresettings.Default.GatewayConfidentialRelayGlobalRate/PerNodeRate`) were not found in the indexed codebase, so the concrete numeric threshold for reproducing exhaustion in production could not be confirmed here.

### Recommendation
Scope the rate limiting to the request's tenant identity (Owner/Org/workflow) in addition to (or instead of) the DON-global bucket, e.g., derive a per-Owner or per-active-request rate limiter/token bucket so that one tenant's traffic cannot consume the budget needed for another tenant's in-flight `activeRequest`. Alternatively, prioritize/reserve capacity per `activeRequest` (e.g., check quota keyed by `resp.ID`'s owning request) rather than a single global counter for the whole DON.

### Proof of Concept
Go table/handler test plan in `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. Build a `handler` via `NewHandler` with a DON of ≥4 members and an artificially tiny `GatewayConfidentialRelayGlobalRate` (inject via `limitsFactory`/`cresettings` override or a fake `limits.RateLimiter` that fails after N calls).
2. Submit "tenant A" traffic: call `HandleJSONRPCUserMessage` for several distinct request IDs (simulating many `CapabilityExec` calls from one Owner), then feed synthetic node responses through `HandleNodeMessage` for each, driving `globalNodeRateLimiter.Allow` to return false.
3. Submit "tenant B" traffic: call `HandleJSONRPCUserMessage` for a fresh, unrelated request ID, then deliver a valid signed node response via `HandleNodeMessage`.
4. Assert that tenant B's response is dropped (i.e., `ar.copiedResponses()` for tenant B's request does not include the delivered response, and/or the callback eventually receives `api.RequestTimeoutError` after `removeExpiredRequests` runs), even though tenant B's request and response were otherwise valid — proving the shared global limiter causes cross-tenant response loss.

```go
func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		l.Debug("global relay rate limit exceeded")
		return nil
	}
```
