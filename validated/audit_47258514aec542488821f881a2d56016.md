### Title
Zip-Slip Path Traversal / Symlink Escape in `ExtractZipArchive` Allows Writing Outside Job Working Directory - ([File: helpers/archives/zip_extract.go])

### Summary
`ExtractZipArchive` (used by the legacy zip extractor `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) uses `file.Name` from the ZIP directly in `os.MkdirAll`, `os.OpenFile`, and `os.Symlink` calls without any sanitization for `..` traversal, absolute paths, or symlink target escape. Since artifact contents are fully attacker-controlled (an attacker crafts their own job's artifacts, which a downstream job then downloads via `dependencies:`/`needs:`), a malicious archive can write files outside the intended extraction directory.

### Finding Description
`ArtifactsDownloaderCommand.Execute` downloads an artifacts archive and calls `archive.NewExtractor(format, f, size, wd)` then `extractor.Extract(ctx)` [1](#0-0) . For the zip format, this resolves to the legacy extractor whose `Extract` builds a `zip.Reader` and calls `archives.ExtractZipArchive(zr)` — notably **without ever using `e.dir`** to scope or chdir into the target directory [2](#0-1) .

Inside `ExtractZipArchive`, each `zip.File.Name` is used verbatim:
- `extractZipFile` calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` [3](#0-2) 
- `extractZipFileEntry` calls `os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, ...)` after `os.Remove(file.Name)` [4](#0-3) 
- `extractZipSymlinkEntry` calls `os.Symlink(string(data), file.Name)`, where `data` (the symlink target) is fully attacker-controlled ZIP entry content [5](#0-4) 

There is no call to `filepath.Clean`, no rejection of entries containing `..`, no rejection of absolute paths, and no check that the resolved path stays within a base directory. The only existing guard, `errorIfGitDirectory`, only warns about `.git` directory names and does not stop extraction or validate paths [6](#0-5) .

Because the extraction runs in the process's current working directory (which is the job's working directory when the helper binary is invoked) and there is no path containment check, a ZIP entry named e.g. `../../../etc/passwd` or an absolute path, or a symlink entry pointing to `/etc/cron.d/x` followed by a same-named file entry that writes through the symlink, will write outside the job's working directory (`wd`), including into a sibling job's checkout on a shared shell/host executor, or overwrite arbitrary files reachable by the runner process's file permissions.

### Impact Explanation
An unprivileged pipeline author who controls the content of an artifact (either directly in their own job, or that a downstream job downloads via `dependencies:`/`needs:`) can craft a ZIP that, when extracted by the downloading job's runner process, writes/overwrites files outside the intended `wd` (job working directory). On shared-host executors (shell) or misconfigured executors sharing a builds root, this can overwrite files belonging to other jobs/projects or the runner's own state files, going beyond the intended artifact-extraction sandbox.

### Likelihood Explanation
Feasible and repeatable: any user who can define a job that produces artifacts (`artifacts:paths`) fully controls the ZIP entry names and symlink target contents that GitLab Runner will later extract. No special privilege beyond normal pipeline authorship is needed; the vulnerable code path (`ArtifactsDownloaderCommand.Execute` → `ExtractZipArchive`) is always exercised whenever a job downloads zip-format artifacts (the default format), which is the common case.

### Recommendation
In `extractZipFile` (and `extractZipDirectoryEntry`/`extractZipFileEntry`/`extractZipSymlinkEntry`), resolve `file.Name` against the target extraction directory using `filepath.Join(dir, file.Name)`, then verify with `filepath.Clean`/`filepath.Rel` that the resulting path stays within `dir` before performing any `Mkdir`, `OpenFile`, or `Symlink`. Reject entries with absolute paths or resolved paths containing `..` above the root. Also validate/clamp symlink target contents (`extractZipSymlinkEntry`) so a symlink cannot point outside `dir`, and thread `e.dir` through `ExtractZipArchive` (currently unused) so extraction is anchored to the intended directory rather than relying implicitly on process cwd.

### Proof of Concept
Go unit test in `helpers/archives`:
```go
func TestExtractZipArchive_PathTraversal(t *testing.T) {
    dir := t.TempDir()
    require.NoError(t, os.Chdir(dir)) // simulate job wd as cwd

    buf := &bytes.Buffer{}
    zw := zip.NewWriter(buf)
    w, _ := zw.Create("../../evil.txt")
    _, _ = w.Write([]byte("pwned"))
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    err = ExtractZipArchive(zr)
    require.NoError(t, err)

    // Assert the file escaped the intended directory
    _, statErr := os.Stat(filepath.Join(filepath.Dir(filepath.Dir(dir)), "evil.txt"))
    assert.NoError(t, statErr, "expected zip-slip write outside extraction dir")
}
```
Expected: without a fix, `os.Stat` succeeds, proving the write escaped `dir`. A second test should craft a symlink entry (`os.ModeSymlink`) pointing outside `dir` followed by a regular file entry with the same name, and assert the final written file resolves outside `dir` via the symlink — this should fail (return error / refuse) once the fix (path containment check) is applied.

```go
func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
```
