## Title
Missing SPL-Token-program ownership check when resolving a token account's associated mint allows an attacker to spoof `decimals`/extension config and cause wrong balances to be returned by `jsonParsed`-encoded RPC endpoints - (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
This is the closest reachable analog to the Caviar `PrivatePool.flashLoan`/`execute` bug: in both cases a function accepts/derives an address (`token`/`nft` in Caviar, a "mint" pubkey in agave) and then blindly trusts whatever lives at that address without verifying it is actually the expected privileged contract/program. In Caviar, `flashLoan` let the caller choose an arbitrary `token` address instead of forcing use of the pool's real `nft`. In agave's RPC layer, `get_parsed_token_account`/`get_parsed_token_accounts` (used by `getAccountInfo`, `getMultipleAccounts`, `simulateTransaction`, `getTokenAccountsByOwner`, and `getTokenAccountsByDelegate` with `encoding: "jsonParsed"`) resolve the *mint* referenced inside a token account's data and unpack it as an SPL `Mint`, without verifying that this mint account is actually owned by a recognized SPL Token program.

### Finding Description
`get_parsed_token_account` in [1](#0-0)  takes the mint pubkey embedded in a token account's raw data via `get_token_account_mint`, loads whatever account currently exists at that address, and passes its raw `data()` straight into `get_additional_mint_data`, which just does `StateWithExtensions::<Mint>::unpack(data)` — it never checks `mint_account.owner()`.

Likewise, `get_parsed_token_accounts` (plural, used by `getTokenAccountsByOwner`/`getTokenAccountsByDelegate`) calls `get_mint_owner_and_additional_data` at [2](#0-1)  and `get_additional_mint_data` at [3](#0-2) , and it only uses the *decimals/extension data* returned — it never checks whether the returned `mint_owner` is a known SPL Token program id before trusting the decoded decimals.

This is inconsistent with sibling RPC methods that operate on the *same kind of data*: `get_token_account_balance` and `get_token_supply` explicitly call `is_known_spl_token_id(account.owner())` before unpacking a mint, rejecting non-token-program accounts — see [4](#0-3)  and [5](#0-4) . `get_token_largest_accounts` also performs this check after calling `get_mint_owner_and_additional_data`: [6](#0-5) . The `jsonParsed`-path functions in `parsed_token_accounts.rs` omit this check entirely.

Because `StateWithExtensions::<Mint>::unpack` only validates byte layout (and, for extensions, an account-type discriminator) and not ownership, any account — owned by any program, including one deployed and controlled entirely by an unprivileged user — that happens to contain 82 bytes shaped like a `Mint` (arbitrary `decimals`, `mint_authority`, `freeze_authority`, or forged Token-2022 extension bytes like `InterestBearingConfig`/`ScaledUiAmountConfig`) will be accepted as "the mint" for computing `ui_amount`/`ui_amount_string` for any real SPL token account that happens to reference that address as its `mint` field.

### Impact Explanation
This causes the RPC node to return wrong account/derived data (misreported `UiTokenAmount.decimals`, `uiAmount`, `uiAmountString`, and forged interest-bearing/scaled-UI-amount extension fields) for legitimate token accounts to any client of `getAccountInfo`, `getMultipleAccounts`, `simulateTransaction` (with `jsonParsed` account encoding), `getTokenAccountsByOwner`, and `getTokenAccountsByDelegate`. This falls squarely into the "decoder ... misreporting" and "wrong ... account data returned" impact categories in scope. It does not corrupt on-chain state or consensus, but it can mislead wallets/exchanges/bots that trust these RPC responses for UI display or automated decision-making about balances, potentially leading to real financial loss downstream (analogous in spirit, though not mechanism, to the original report's token-theft-via-blind-trust theme).

### Likelihood Explanation
Reaching this requires only a single unprivileged, unauthenticated JSON-RPC call plus the (cheap, permissionless) ability to place an account at an arbitrary address with attacker-chosen data — e.g., deploying a small BPF program that writes attacker-chosen bytes into an account it owns, then causing (or waiting for) a real SPL token account to reference that address as its `mint`. No validator, peer, or operator privilege is needed, and the query itself is a single, low-cost read, matching the "single low-rate call" criterion. Likelihood is moderate-to-high because it only needs standard, permissionless Solana operations (create account + assign to a user-owned program + write bytes), no cluster-wide state manipulation.

### Recommendation
Add an `is_known_spl_token_id(mint_account.owner())` check (mirroring `get_token_account_balance`/`get_token_supply`/`get_token_largest_accounts`) before treating any resolved "mint" account's data as trustworthy inside:
- `get_parsed_token_account` (`rpc/src/parsed_token_accounts.rs:23-50`)
- `get_mint_owner_and_additional_data` / its callers in `get_parsed_token_accounts` (`rpc/src/parsed_token_accounts.rs:52-108`)

If the check fails, fall back to non-`jsonParsed` (raw) encoding for that entry rather than trusting forged decimals/extension data, consistent with how invalid mints are already excluded elsewhere (see the existing test expectation that "accounts with invalid mints" are dropped from `jsonParsed` results, e.g. [7](#0-6) ).

### Proof of Concept
1. Deploy an unprivileged user-owned program (or use an existing on-chain account you control that is *not* owned by `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` or Token-2022) at address `M`.
2. Write 82+ bytes into the account at `M` shaped like a valid `spl_token_2022_interface::state::Mint` (e.g., `is_initialized = true`, `decimals = 255` or any attacker-chosen value, plus a forged `InterestBearingConfig`/`ScaledUiAmountConfig` extension if desired), while its `owner` remains the attacker's own program (not a real token program).
3. Create (or find) a genuine SPL token account `T` whose `mint` field is set to `M` (the token program itself will reject *transfers* referencing a mint it doesn't own, but nothing stops the RPC decode path from reading `T`'s raw `mint` field, which is just bytes at offset 0 of `T`'s data, unconditionally).
4. Call `getAccountInfo`/`getTokenAccountsByOwner` for `T` with `{"encoding": "jsonParsed"}`.
5. Observe that `parsed.info.tokenAmount.decimals`/`uiAmount`/extension fields reflect the attacker-forged data at `M`, since `get_additional_mint_data`/`get_mint_owner_and_additional_data` unpack `M`'s data without verifying `M.owner()` is a known SPL token program, unlike the equivalent checks in `get_token_supply`/`get_token_account_balance`.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
