### Title
Revoked lenders cannot create withdrawal requests for already-owned tranches - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw` re-checks the caller’s current Keyring credential before converting an existing tranche position into a withdrawal receipt. A lender who satisfied KYC at deposit time, but whose credential later expires or is revoked, is permanently unable to initiate redemption unless the credential is restored or the tranche tokens are transferred to another eligible wallet. Claims themselves are not credential-gated, indicating that existing withdrawal rights are intended to remain redeemable after creation. [1](#0-0) [2](#0-1) 

### Finding Description
Deposits correctly require the caller to be currently allowed through `isWalletAllowed`. [3](#0-2) 

However, `requestWithdraw` applies the same eligibility check to a wallet that already owns tranche tokens:

```solidity
// contracts/IdleCDOEpochVariant.sol
function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256) {
  _checkTranche(_tranche);
  _checkNotAllowed(
    (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
    !isWalletAllowed(msg.sender)
  );
``` [1](#0-0) 

The credential is evaluated dynamically through the configured Keyring contract, so an honest credential expiration or revocation changes the result after the position was created. [4](#0-3) 

Once the request reverts, the tranche tokens are not burned and no strategy-token withdrawal receipt is minted, leaving the lender without a claimable balance. [5](#0-4) 

The queued withdrawal path has the same structural issue: `IdleCDOEpochQueue.requestWithdraw` checks both the running epoch and `isWalletAllowed(msg.sender)` before accepting the lender’s tranche tokens, while later `claimWithdrawRequest` does not re-check eligibility. [6](#0-5) [7](#0-6) 

### Impact Explanation
A lender’s full tranche balance can be prevented from entering the redemption path after a credential revocation. If the revocation is irreversible and the lender cannot or is not permitted to transfer the position to an eligible address, the underlying principal and accrued yield remain frozen indefinitely. [1](#0-0) 

This breaks the fair mint/burn invariant: authorization to enter the pool is re-used as authorization to exit an already-established position. The issue is analogous to checking collateral eligibility again during redemption after that collateral was already accepted. [4](#0-3) 

### Likelihood Explanation
The trigger does not require malicious behavior. An honest Keyring administrator can revoke or fail to renew a lender’s credential for routine compliance, expiration, jurisdiction, or policy changes. Because the credential is queried at request time rather than using the fact that the tranche position was previously issued under an allowed deposit, ordinary administrative state changes can strand existing lenders. [4](#0-3) 

The vulnerable path is the ordinary redemption flow, so any lender whose credential state changes before submitting `requestWithdraw` is affected. [1](#0-0) 

### Recommendation
Do not re-check `isWalletAllowed(msg.sender)` when creating a withdrawal request for tranche tokens already held by the caller. Keep credential checks on deposits and other entry points, while allowing exits to burn existing tranche tokens and create the corresponding withdrawal receipt.

Apply the same change to `IdleCDOEpochQueue.requestWithdraw`: retain the epoch-state requirement needed by the queue, but do not require the withdrawing user’s credential to still be active when surrendering tranche tokens. [8](#0-7) 

If compliance requires restricting the payout destination, enforce that policy explicitly at claim/payout time rather than preventing the existing position from entering the withdrawal queue.

### Proof of Concept
The following test can be placed in the existing `test/foundry/IdleCreditVault.t.sol` fixture context, where `cdoEpoch`, `underlying`, `manager`, and `AAtranche` are already initialized.

```solidity
function testRevokedLenderCannotRequestWithdraw() external {
  address lender = makeAddr("lender");
  address keyring = makeAddr("keyring");
  uint256 policyId = 1;
  uint256 amount = 100e6;

  vm.prank(manager);
  cdoEpoch.setKeyringParams(keyring, policyId);

  bytes memory credentialCall = abi.encodeWithSelector(
    IKeyring.checkCredential.selector,
    policyId,
    lender
  );

  // Lender is eligible when entering the pool.
  vm.mockCall(keyring, credentialCall, abi.encode(true));
  deal(address(underlying), lender, amount);

  vm.startPrank(lender);
  underlying.approve(address(cdoEpoch), amount);
  uint256 trancheBalance = cdoEpoch.depositAA(amount);
  vm.stopPrank();

  // Honest Keyring state change after the tranche position was created.
  vm.mockCall(keyring, credentialCall, abi.encode(false));

  // The existing position cannot even enter the withdrawal-request flow.
  vm.expectRevert(NotAllowed.selector);
  vm.prank(lender);
  cdoEpoch.requestWithdraw(trancheBalance, AAtranche);

  assertEq(
    IERC20Detailed(AAtranche).balanceOf(lender),
    trancheBalance,
    "tranche principal remains locked"
  );
  assertEq(
    IdleCreditVault(address(strategy)).withdrawsRequests(lender),
    0,
    "no withdrawal receipt was created"
  );
}
```
