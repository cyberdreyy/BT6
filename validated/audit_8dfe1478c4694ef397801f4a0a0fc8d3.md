### Title
Stale instant-withdraw receipt accounting leaks into default recovery: double claim of `defaultRecoveryReserve` and diluted `defaultRecoveryPrice` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns the user's aggregate receipt balance but never clears the per-epoch receipt records `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (`IdleCreditVault.sol:380-393`). These stale entries are only decremented in the post-default path `_claimDefaultedInstantWithdrawRequest` (`:842-856`) and are also re-read by `defaultPendingClaimBasis` (`:644-649`). The result is a classic leak: claim accounting is allocated but never freed, so already-paid instant receipts are counted again when a default is finalized, diluting the recovery price and letting the same user recover twice on the same principal.

### Finding Description
1. During epoch `N` (buffer phase), lender Alice calls `IdleCDOEpochVariant.requestWithdraw`, which routes to `requestInstantWithdraw` (`:356-375`). She gets a receipt token and `instantWithdrawsRequestsByEpoch[Alice][N] += amt`, `instantWithdrawClaimsByEpoch[N] += amt`.
2. At `startEpoch`, the CDO funds instant receipts via `collectInstantWithdrawFunds`, which reduces `pendingInstantWithdraws` but not `instantWithdrawClaimsByEpoch` (`:398-403`).
3. Alice calls `claimInstantWithdrawRequest` and receives her underlying. `instantWithdrawsRequests[Alice]` is zeroed, but `instantWithdrawsRequestsByEpoch[Alice][N]` and `instantWithdrawClaimsByEpoch[N]` remain nonzero forever (`:387-392`).
4. A second instant requester (Bob) in the same epoch stays unfunded (`pendingInstantWithdraws > 0`), so `instantWithdrawClaimsByEpoch[N]` still includes Alice's already-paid amount plus Bob's.
5. The borrower then defaults mid-epoch. `finalizeDefault` → `finalizeDefaultRecovery` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (`:644-648`). The denominator is inflated by Alice's stale receipt, so `defaultRecoveryPrice` is set artificially low (`:688`); all honest claimants (tranche holders via `activeFinalNAV` at `:699-705` and pending redeemers at `:782`) receive less than they should.
6. Because `defaultInstantWithdrawsFinalized` is set true (`:696`), `claimInstantWithdrawRequest` now first calls `_claimDefaultedInstantWithdrawRequest`, which reads the stale `instantWithdrawsRequestsByEpoch[Alice][N]`. Alice only needs `instantWithdrawsRequests[Alice] >= claimBasis` to pass the `-=` at `:848`; she can top it up with any small post-finalization request path (e.g., a new `requestInstantWithdraw` for `claimBasis` minted via the CDO, since post-default gating checks only `instantWithdrawsRequests[user] != 0`, which is currently 0 — `:249`). She then burns the new receipt tokens and is paid `(claimBasis * defaultRecoveryPrice) / 1e18` a second time for principal already claimed, straight out of `defaultRecoveryReserve` (`:853-855`).

Broken invariant: one receipt, one payout — the same epoch-`N` instant principal is paid once as a funded claim and again as a defaulted claim, while also inflating the recovery denominator.

### Impact Explanation
Direct theft of the isolated recovery reserve: Alice extracts up to `staleAmount * defaultRecoveryPrice / 1e18` of underlying a second time. Even without the second claim, the inflated `totalBasis` permanently locks the excess portion of `defaultRecoveryReserve` (no function sweeps it; `transferToken` is owner-only and honest per the model), so recovered funds owed to honest defaulted-epoch claimants are underpaid and the remainder is permanently frozen. Loss scales linearly with the attacker's instant-withdraw amount, which is unbounded by anything except deposited TVL.

### Likelihood Explanation
Requires the confluence of (a) an instant withdraw that is funded and claimed, (b) at least one unfunded instant receipt in the same epoch so `defaultInstantWithdrawsFinalized` is set, and (c) a subsequent borrower default in that epoch. All are unprivileged-user-reachable transitions around honest manager/owner calls; no privileged misbehavior is needed. The stale-storage leak itself is unconditional — every successful `claimInstantWithdrawRequest` leaves the per-epoch record behind.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting when the receipt is paid:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
// add: clear stale per-epoch basis
uint256 ep = lastInstantRequestEpoch[user]; // or iterate: track request epoch like lastWithdrawRequest
instantWithdrawsRequestsByEpoch[_user][ep] = 0;
instantWithdrawClaimsByEpoch[ep] -= instantWithdrawsRequestsByEpoch value;
```

Equivalently, record the request epoch per user (mirroring `lastWithdrawRequest`) so funded claims decrement `instantWithdrawClaimsByEpoch` and zero `instantWithdrawsRequestsByEpoch`, preventing already-paid receipts from entering `defaultPendingClaimBasis` or `_claimDefaultedInstantWithdrawRequest`.

### Proof of Concept
Foundry fork-style PoC (sketch, against `IdleCreditVault` + `IdleCDOEpochVariant`):

```solidity
function test_InstantReceiptLeak_DoubleRecovery() public {
    // buffer phase of epoch N
    uint256 amt = 100e6;
    vm.prank(cdo); vault.requestInstantWithdraw(amt, alice);   // instantWithdrawsRequestsByEpoch[alice][N]=amt
    vm.prank(cdo); vault.requestInstantWithdraw(amt, bob);     // bob's stays unfunded
    // manager starts epoch; CDO funds only alice's receipt
    vm.prank(cdo); vault.collectInstantWithdrawFunds(amt);     // pendingInstantWithdraws: 2amt -> amt
    vm.prank(cdo); vault.claimInstantWithdrawRequest(alice);   // alice paid; per-epoch entries NOT cleared
    assertEq(vault.instantWithdrawsRequestsByEpoch(alice, vault.epochNumber()), amt); // stale

    // borrower defaults; owner finalizes recovery with partial recovery
    finalizeDefaultRecovery(recovered);                        // basis inflated by alice's stale amt
    // recoveryPrice is lower than honest value -> honest claimants diluted,
    // excess reserve permanently locked.

    // alice re-registers an instant receipt (post-default request path only
    // checks instantWithdrawsRequests[alice] != 0, which is 0)
    vm.prank(cdo); vault.requestInstantWithdraw(amt, alice);   // instantWithdrawsRequests[alice]=amt again
    uint256 balBefore = token.balanceOf(alice);
    vm.prank(cdo); vault.claimInstantWithdrawRequest(alice);   // pays stale epoch-N basis AGAIN at recovery price
    assertGt(token.balanceOf(alice) - balBefore, 0);           // stolen from defaultRecoveryReserve
}
```

Key assertions: `instantWithdrawsRequestsByEpoch[alice][N]` is nonzero after a successful funded claim; `defaultPendingClaimBasis()` includes it; `_claimDefaultedInstantWithdrawRequest` pays it a second time once `instantWithdrawsRequests[alice]` is non-zero again.     _ensureDefaultRecoveryInitialized();

```text
    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    if (defaultRecoveryFinalized || !cdo.defaulted()) revert NotAllowed();
    if (_recoveredAmount != 0 && _recoverySource == address(0)) revert NotAllowed();

    // Split gross backing by saved NAV and default interest by the configured APR split.
    // The CDO strategy-token balance is its gross active value before `unclaimedFees`.
    // Using it directly restores those waived unpaid fees to active recovery basis.
    uint256 activeBalance = balanceOf(idleCDO);
    uint256 activeInterest = _defaultActiveInterestBasis(cdo);
    uint256 activeBasis = activeBalance + activeInterest;
    defaultBBNav = _defaultBBBasis(cdo, activeBalance, activeInterest);
    // Pending receipts have already left active CDO NAV, so they are added as a separate basis.
    uint256 pendingBasis = defaultPendingClaimBasis();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (totalBasis == 0) revert NotAllowed();

    // Some recovery funds may already be in this strategy: partially prefunded instant requests
    // and borrower-send funds that failed at epoch start. Count both without pulling them again.
    uint256 prefundedReserve = _defaultPrefundedInstantReserve();
    uint256 reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve;
    // Recovery can be above par if the recovered funds exceed the computed basis.
    uint256 recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis;

    defaultRecoveryFinalized = true;
    defaultRecoveryReserve = reserveAmount;

    // _forceUpdateAccounting so tranche prices/virtualPrice expose the crystallized loss.
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
