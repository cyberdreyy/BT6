### Title
Post-default `requestInstantWithdraw` receipts are paid at par from the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a lifetime/reference bug: notifier callbacks were allowed to take a reference on a dying `fib_info`. The credit-vault analog is a stale-reference claim bug: `requestInstantWithdraw` has no `defaultRecoveryFinalized` handling, so a brand-new instant receipt can be opened *after* default finalization and then claimed through `_transferFundedClaim` at full par, spending underlying that is supposed to be exclusively backing `defaultRecoveryReserve` for defaulted-epoch claimants.

### Finding Description
In `IdleCreditVault`:

- `requestWithdraw` explicitly handles the finalized-default state: it forces the user to first clear all old receipts, then records the request in `postDefaultRequests` (paid from `defaultRecoveryReserve`, already haircut by the CDO-side price): [1](#0-0) 
- `requestInstantWithdraw` performs no such check. It mints a receipt, increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws` unconditionally: [2](#0-1) 
- On the claim side, the recovery path is only taken when `defaultInstantWithdrawsFinalized` is set, which is defined as `pendingInstantWithdraws != 0` at finalization time: [3](#0-2)  and [4](#0-3) 

So when the pool defaults with all instant claims already funded (`pendingInstantWithdraws == 0`, hence `defaultInstantWithdrawsFinalized == false`), an attacker can:

1. Call `requestInstantWithdraw` post-default. The CDO mints the receipt at the post-haircut `virtualPrice`, so `_amount` is already net of the default haircut.
2. Call `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` is skipped; the code reads `instantWithdrawsRequests[_user]` and pays `_amount` 1:1 via `_transferFundedClaim`: [5](#0-4) 

The strategy holds only one underlying balance; `defaultRecoveryReserve` is pure accounting over it. Paying the post-default instant receipt at par therefore consumes tokens reserved for defaulted-epoch claimants (normal pending receipts paid via `_claimDefaultedWithdrawRequest`/`_transferDefaultRecovery` and BB/AA recovery via `DefaultDistributor`). Additionally, `pendingInstantWithdraws += _amount` in step 1 corrupts the invariant used by `_claimDefaultedInstantWithdrawRequest` and any subsequent accounting that treats `pendingInstantWithdraws` as an unfunded remainder.

A second, symmetric case exists when `defaultInstantWithdrawsFinalized == true`: `epochNumber` is frozen at `defaultRecoveryEpoch` (it only increments inside `deposit` during `stopEpoch`: [6](#0-5) ), so a post-default instant request lands in `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and is paid `amount * defaultRecoveryPrice` — a double haircut on a receipt that was already priced net of the haircut — permanently locking the corresponding slice of the recovery reserve.

### Impact Explanation
Direct theft / insolvency: post-default instant receipts are paid 1:1 from the same underlying balance that backs `defaultRecoveryReserve`, so defaulted-epoch withdraw requesters and tranche holders claiming through `finalizeDefaultRecovery`/`DefaultDistributor` receive less than `claimBasis * defaultRecoveryPrice`, or the last claimers' transfers revert for lack of balance. Loss is bounded by the post-default instant receipt size the attacker can mint (their post-haircut tranche value), and every unit claimed overdraws the recovery reserve by the same amount.

### Likelihood Explanation
Requires the pool to be in `defaulted`/`finalized` phase with `pendingInstantWithdraws == 0` at finalization (the common case, since instant withdrawals are designed to be funded instantly) and the CDO to still route `requestInstantWithdraw`/`claimInstantWithdrawRequest` to the strategy after default — the strategy-level code contains no guard, so only upstream gating in `IdleCDOEpochVariant` (which I could not fully confirm within the available search budget) could prevent it. The same asymmetry (guarded `requestWithdraw` vs unguarded `requestInstantWithdraw`) is consistent with this being an oversight rather than an intentional design.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert, or route the receipt into `postDefaultRequests` (already haircut, paid via `_transferDefaultRecovery`) so it cannot be paid at par through `_transferFundedClaim` nor double-haircut via the `defaultRecoveryEpoch` bucket. Also consider reverting when `defaulted()` is true and the claim epoch equals `defaultRecoveryEpoch`.

### Proof of Concept
Foundry fork sketch (based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Setup: deposit AA for attacker + victim, run epoch 0, then default epoch 1
// with all instant claims funded (pendingInstantWithdraws == 0) so that
// defaultInstantWithdrawsFinalized == false after finalizeDefault.

_depositWithUser(attacker, amount, true);
_depositWithUser(victim, amount, true);
_startEpochAndCheckPrices(0);

// victim requests a normal withdraw so a defaulted-epoch claim basis exists
vm.prank(victim);
uint256 victimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

_startEpochAndCheckPrices(1);
uint256 activeBasis = cdoEpoch.getContractValue()
    + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees();
uint256 recovered = (activeBasis + victimBasis) * recoveryRatio / ONE_TRANCHE;
_stopEpochAndCheckPrices(1, initialProvidedApr, 0);
_checkDefault();

deal(defaultUnderlying, manager, recovered);
vm.startPrank(manager);
IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
// assert pendingInstantWithdraws == 0 => defaultInstantWithdrawsFinalized == false

// Attacker opens an instant receipt AFTER finalization; amount is already
// haircut because virtualPrice was lowered by finalizeDefault.
vm.startPrank(attacker);
uint256 receipt = cdoEpoch.requestInstantWithdraw(attackerTrancheBal, address(AAtranche));
uint256 reservePre = IdleCreditVault(address(strategy)).defaultRecoveryReserve();
uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
cdoEpoch.claimInstantWithdrawRequest();
vm.stopPrank();

// Bug: paid at par from the shared underlying balance => recovery reserve
// is silently drained; victim's haircuted claim can no longer be fully paid.
assertEq(IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre, receipt);
// assert victim's claim now reverts or pays less than basis * recoveryPrice
```

Caveat: whether `IdleCDOEpochVariant.requestInstantWithdraw` remains callable once `defaulted()` is true could not be fully verified in this pass; if it reverts upstream the strategy-level hole is unreachable and this finding should be downgraded.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
