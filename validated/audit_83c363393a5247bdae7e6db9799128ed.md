### Title
Multisig confirmation count is not revalidated against live membership, allowing a request to execute with a stale confirmation from a removed member - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` only validates that the *current* caller is a member before adding their confirmation, but it never re-validates the membership of confirmations that were already stored in the `confirmations` set for a pending request. If a member is removed (`DeleteMember`) after having confirmed a still-pending, different request, that removed member's stale confirmation is still counted toward `num_confirmations` when the request is later finalized, letting a request execute with fewer *currently live* confirmations than the configured threshold.

### Finding Description
`confirm` computes whether the threshold is met purely from the size of the stored `HashSet<String>` of confirmer identifiers, plus one for the new confirmer: [1](#0-0) 

It checks `assert_valid_request(request_id)` and that the *new* confirmer (`current_member()`) is not already in the set, but it does not iterate over the existing `confirmations` set to confirm that each previously-recorded confirmer is still a `MultisigMember` in `self.members`. Membership changes are made via `DeleteMember`, executed through the very same `confirm`/`execute_request` path: [2](#0-1) 

Because `confirmations` (a `LookupMap<RequestId, HashSet<String>>`) is keyed independently per request and is never scrubbed when `self.members` changes, a confirmation recorded by a member who is later removed remains in the set for any other request that was pending at the time.

The binding this breaks: the contract's intended custody invariant is `number of confirmations from currently-live members >= num_confirmations` before any request (e.g. `Transfer`) executes. What is actually enforced is `size of a historical confirmation set (which may include removed members) + 1 >= num_confirmations`. These two are not equal once membership changes between a confirmation being recorded and a request being finalized.

### Impact Explanation
This crosses the "confirmations counted versus live members" custody boundary explicitly called out as in-scope. A `Transfer`, `FunctionCall`, `AddKey`/`AddFullAccessKey`, or `DeployContract` request can be pushed through `execute_request` while the number of confirmations coming from accounts that are still members of the multisig is below the configured `num_confirmations`. This matches the "Critical" impact category: a multisig request executed below threshold, potentially moving NEAR (via `Transfer`) or granting full account control (via `AddKey`) with fewer live approvals than intended.

### Likelihood Explanation
This requires the natural, expected multisig workflow: multiple requests can be outstanding simultaneously (`active_requests_limit` explicitly allows up to `ACTIVE_REQUESTS_LIMIT = 12` concurrently pending requests per member), and membership changes (`DeleteMember`) are a normal governance action that can complete while other requests are still pending. No attacker needs privileged access beyond being one of the existing members (which is the threat model the multisig is designed to defend against — a subset of members colluding, or a member being removed for cause after already "spending" a confirmation). The bug is triggered purely by ordinary sequencing of legitimate calls, no exploit of an external contract or reentrancy needed.

### Recommendation
When finalizing a request in `confirm`, filter (or lazily prune) the stored confirmation set against `self.members` before comparing its size to `num_confirmations`, e.g.:
```rust
let live_confirmations = confirmations
    .iter()
    .filter(|m| self.members.contains(&MultisigMember::from_str(m)))
    .count();
if live_confirmations as u32 + 1 >= self.num_confirmations { ... }
```
Alternatively, whenever `DeleteMember` executes, iterate all pending `requests`/`confirmations` and remove the deleted member's confirmation entries so stale confirmations can never be counted.

### Proof of Concept
1. Multisig deployed with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request(R1)` where `R1 = Transfer{amount}` to an attacker-controlled/collaborating account. `confirmations[R1] = {}`.
3. `B` calls `confirm(R1)`. Since `confirmations.len() + 1 == 1 < 2`, `B` is inserted: `confirmations[R1] = {B}`. `R1` is not yet executed.
4. Separately, `C` calls `add_request(R2)` where `R2 = DeleteMember{B}`, then `A` and `C` both call `confirm(R2)`, reaching `num_confirmations = 2` and executing `DeleteMember{B}` (see `execute_request`, `MultiSigRequestAction::DeleteMember` branch, `multisig2/src/lib.rs:239-242`). `B` is now removed from `self.members`.
5. `A` calls `confirm(R1)`. `confirm` only checks that `A` (the new confirmer) is a current member — it does not re-check `B`. Since `confirmations[R1].len() + 1 == {B} + A == 2 >= num_confirmations`, `R1` (the `Transfer`) executes via `execute_request`, even though only one currently-live member (`A`) plus one stale, no-longer-a-member confirmation (`B`) approved it — a threshold bypass relative to the live member set.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
