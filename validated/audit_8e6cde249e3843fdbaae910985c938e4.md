## Title
Signer weight double-counted across both accept and reject tallies after a vote switch, causing the miner coordinator to spuriously treat an approved block as rejected - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tallies signer weight for block approval/rejection into two independent counters, `total_weight_approved` and `total_weight_rejected`, that `SignerCoordinator::get_block_status` compares against the approval threshold and the "blocking minority" respectively. The dedup guards used to prevent a signer's weight from being counted twice are asymmetric: an accept-then-reject sequence from the same signer is correctly suppressed, but a reject-then-accept sequence (a signer reconsidering, which is an explicitly supported protocol behavior) is not. The signer's weight ends up counted in *both* buckets simultaneously, and the stale rejection weight is never removed. This is the same class of defect as the reported "no cap on the sum of shares" bug: nothing enforces that each signer's weight is exclusive to a single bucket, so the sums no longer partition the total weight.

### Finding Description
When an `Accepted` message is processed, weight is only added to `total_weight_approved` if the slot is not already present in `gathered_signatures`: [1](#0-0) 

When a `Rejected` message is processed, weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` succeeds (i.e., this slot has not yet "responded" in any way): [2](#0-1) 

The `responded_signers` set is shared between the two code paths, but `gathered_signatures` is populated only by the Accept path. Consequently:
- Accept, then later Reject from the same signer: `responded_signers` already contains the slot from the Accept, so `insert()` returns `false` and the whole rejected-weight block is skipped — correctly de-duplicated.
- Reject, then later Accept from the same signer: `responded_signers` was populated by the Reject (adding weight to `total_weight_rejected`), but `gathered_signatures` is still empty for that slot, so the Accept path's guard (`!gathered_signatures.contains_key(&slot_id)`) is satisfied and the signer's weight is added *again*, this time to `total_weight_approved` — with no corresponding subtraction from `total_weight_rejected`.

The result: a single signer's weight can simultaneously count toward both `total_weight_approved` and `total_weight_rejected`, breaking the intended invariant that these two "shares" of the total signer weight are mutually exclusive and bounded by `total_weight`.

This matters because `SignerCoordinator::get_block_status` evaluates the reject condition *before* the accept condition: [3](#0-2) 

If stale rejection weight (from a signer who has since switched to accepting) combines with a genuinely rejecting minority to cross the `total_weight - weight_threshold` blocking-minority line, the miner will take the `SignersRejected` branch even though `total_weight_approved` has also legitimately reached `weight_threshold`.

### Impact Explanation
This is a liveness wedge on the miner/coordinator side of the equality "aggregated-weight vs verified-accepts": a block that has genuinely reached the 70% signer-approval threshold can be discarded by the miner as rejected due to a leftover, no-longer-valid rejection tally from a signer that reconsidered. The CHANGELOG documents that "reconsidering" a previously rejected proposal is expected signer behavior, so this is a realistic, protocol-sanctioned sequence rather than a contrived edge case: [4](#0-3) 

The consequence is wasted re-proposals, incorrect miner activity/rejection accounting, and potential mis-triggering of the txid exclusion logic that only fires on the rejection branch: [5](#0-4) 

### Likelihood Explanation
Triggering this requires only ordinary message timing from a single signer (reject then later accept the same proposal) combined with a small number of genuinely-rejecting signers whose combined weight, added to the stale rejection weight, crosses the blocking-minority threshold. No majority collusion, no key compromise, and no protocol violation by any signer is required — it can arise from normal reconsideration/gossip reordering in a live network.

### Recommendation
Track each signer's current stance in a single map (e.g., `HashMap<slot_id, Vote>`), and when a new stance is recorded, subtract the previous stance's weight from whichever bucket it was in before adding the new weight to the other bucket. Concretely:
- Before adding weight to `total_weight_approved` on Accept, check whether `slot_id` was previously counted as rejected (regardless of `responded_signers`/`gathered_signatures` particulars) and subtract that weight from `total_weight_rejected`.
- Symmetrically for Reject.
- Ensure `total_weight_approved + total_weight_rejected <= total_weight` is maintained as an invariant after every update, mirroring the "sum(shares) <= cap" checks recommended in the referenced report.

### Proof of Concept
With `total_weight = 100`, `weight_threshold = 70` (blocking minority = 30):
1. Signer A (weight 25) sends `Rejected` for block B → `total_weight_rejected = 25`.
2. Signer A reconsiders and sends `Accepted` for block B → guard passes (`gathered_signatures` has no entry for A's slot) → `total_weight_approved = 25`, while `total_weight_rejected` stays at 25 (never decremented).
3. 45 more weight worth of signers send `Accepted` → `total_weight_approved = 70` (accept threshold reached).
4. 10 more weight worth of signers genuinely reject → `total_weight_rejected = 35` → `35 + 70 > 100`, satisfying the reject-threshold branch in `get_block_status`.
5. Because the reject check (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`) is evaluated first, the miner returns `NakamotoNodeError::SignersRejected` even though `total_weight_approved (70) >= weight_threshold (70)` was also true — a block with legitimate 70%+ live approval is treated as rejected.
