### Title
Removing a multisig member does not purge their stale confirmations from other pending requests, allowing a request to execute below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only deletes *requests created by* the removed member; it never scrubs that member's confirmations from *other* members' pending requests. Since `confirm()` authorizes execution purely by counting `HashSet<String>` length against `num_confirmations`, a stale confirmation from an already-removed member is still counted as a valid vote, letting a request execute with fewer confirmations from currently-live members than the configured threshold requires.

### Finding Description
`confirm()` decides to execute a request solely based on set cardinality: [1](#0-0) 

`delete_member` removes the member from `self.members`, deletes the access key, and clears requests *the removed member itself created* — but it does not touch `self.confirmations` entries for requests created and/or confirmed by other members: [2](#0-1) 

`assert_valid_request` only checks that the *caller* confirming right now is a current member; it never re-validates that entries already stored in a request's `confirmations` set still belong to current members: [3](#0-2) 

Binding that should hold: `confirmations_counted(request) == confirmations_from_live_members(request)`. Because `delete_member` never re-derives or filters a surviving request's confirmation set, this equality is broken the moment a member who had confirmed some *other* pending request is removed: that stale confirmation continues to count toward `num_confirmations` in `confirm()`.

### Impact Explanation
This falls under the Critical bucket "a multisig request executed below threshold." A K-of-N multisig's core security guarantee is that K *currently authorized* signers must approve any action. With this defect, a request can execute with fewer than K live confirmations — one or more of the "votes" belongs to an account/key that has since been removed (e.g., because it was compromised or an employee departed). This can let a malicious or stale request (a `Transfer`, `AddKey`, `FunctionCall`, etc.) execute on the multisig account's funds/permissions without the intended live-quorum's consent.

### Likelihood Explanation
No special privilege is needed beyond being (or having been) one of the N members at some point. Any scenario where:
1. Member A confirms request X (created by another member, so `delete_member` won't clean it up),
2. Member A is later removed via `DeleteMember` (the `assert` on line 357-360 only checks that the remaining member count still meets `num_confirmations`, not confirmation validity),
3. Request X is still pending and later reaches `num_confirmations` count via `confirmations.len()+1 >= self.num_confirmations`, counting A's stale entry,

...results in execution with a live-member vote count one short of the intended threshold. This is entirely plausible in normal multisig operational flow (rotating out a compromised or departing signer while other requests are in flight), requiring no exotic conditions.

### Recommendation
When deleting a member, iterate over **all** pending requests (not just ones created by that member) and remove the departing member's entry from each request's `confirmations` set (re-checking afterward if any request now has 0 confirmations and can be dropped, and re-validating no longer-current confirmations don't count toward `num_confirmations` in `confirm()`). Alternatively, validate on every `confirm()` call that all entries in the stored `confirmations` set are still `self.members.contains(...)`, filtering out stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. B creates request X (e.g., `Transfer`) via `add_request`.
3. A calls `confirm(X)` — `confirmations = {A}` (1 < 2, not yet executed).
4. C and B jointly execute a separate request `DeleteMember { member: A }` — `delete_member` only clears requests *created by A*; request X (created by B) is untouched, so `confirmations` for X still contains `A`.
5. B calls `confirm(X)` — `confirmations.len() + 1 = 2 >= num_confirmations (2)` → request X executes, even though only B (a single live member) plus a stale, now-removed member A's confirmation authorized it — never truly 2 live-member confirmations. [4](#0-3) [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
