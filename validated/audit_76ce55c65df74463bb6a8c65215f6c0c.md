## Title
`update_next_withdrawal_validator_index` treats a `BUILDER_INDEX_FLAG`-tagged withdrawal index as a raw `ValidatorIndex` when `MAX_WITHDRAWALS_PER_PAYLOAD` is reached with builder withdrawals - ([File: specs/capella/beacon-chain.md])

### Summary
`Withdrawal.validator_index` is an overloaded field: for builder payouts it is `convert_builder_index_to_validator_index(builder_index)`, i.e. `builder_index | BUILDER_INDEX_FLAG` [1](#0-0) , and this is exactly the "same underlying bits interpreted under an unchecked type tag" pattern that produced the TensorFlow `CHECK`-failure (a value's true "type"/origin must be checked before it is consumed as a different one). The inherited (capella) sweep-index updater, `update_next_withdrawal_validator_index`, does not check `is_builder_index()` before treating the *last* withdrawal's `validator_index` as a plain sweep cursor when a full batch of `MAX_WITHDRAWALS_PER_PAYLOAD` withdrawals occurred:

```python
def update_next_withdrawal_validator_index(
    state: BeaconState, withdrawals: Sequence[Withdrawal]
) -> None:
    if len(withdrawals) == MAX_WITHDRAWALS_PER_PAYLOAD:
        next_validator_index = (withdrawals[-1].validator_index + 1) % len(state.validators)
        state.next_withdrawal_validator_index = next_validator_index
    else:
        ...
``` [2](#0-1) 

### Finding Description
The Gloas fork reuses the `Withdrawal` container for both validators and builders, distinguishing them only by an unchecked bit flag on `validator_index` [3](#0-2) . `apply_withdrawals` (the balance-mutation path) correctly checks `is_builder_index()` before deciding whether to touch `state.builders[...]` or `state.balances[...]` [4](#0-3) . However `update_next_withdrawal_validator_index`, which is *inherited unchanged* from capella and still called at the end of Gloas's `process_withdrawals` [5](#0-4) , performs `(withdrawals[-1].validator_index + 1) % len(state.validators)` on whatever the *last* entry in the combined withdrawals list happens to be — without checking whether that last entry is a builder-flagged index (`>= BUILDER_INDEX_FLAG = 2**40`).

If the full `MAX_WITHDRAWALS_PER_PAYLOAD` batch's last entry is a builder withdrawal (its ordering position is achievable because builder pending/sweep withdrawals are placed ahead of partial and validator-sweep withdrawals in `get_expected_withdrawals`) [6](#0-5) , then `withdrawals[-1].validator_index` is a huge integer (`builder_index | 2**40`), and `(that + 1) % len(state.validators)` produces an essentially attacker/builder-steerable, effectively pseudo-random `ValidatorIndex` in `[0, len(validators))` rather than the deterministically-intended "next index after the sweep position." This breaks the equality that `next_withdrawal_validator_index` must equal "the validator immediately following the last *validator* withdrawal actually swept" — a value that determines which validators are checked for withdrawal in every subsequent block's sweep.

The repository's own test suite documents that this exact class of bug was previously present and was fixed for one specific scenario (all `MAX_WITHDRAWALS_PER_PAYLOAD` slots filled by builder withdrawals, PR #4832/#4835) by reserving one slot for the validator sweep so a full builder batch alone can no longer trigger it [7](#0-6) . That mitigation (`get_builder_withdrawals`/`get_builders_sweep_withdrawals` each cap themselves at `MAX_WITHDRAWALS_PER_PAYLOAD - 1`, reserving 1 slot) prevents the *all-builder* full-batch case, but `update_next_withdrawal_validator_index` itself was never changed to filter on `is_builder_index()`. As long as it is possible to construct a state where a full `MAX_WITHDRAWALS_PER_PAYLOAD`-sized withdrawal list ends with a builder entry (e.g. builder pending withdrawals fill up to `MAX_WITHDRAWALS_PER_PAYLOAD - 1` slots and are immediately followed, in the same batch, by partial or builder-sweep withdrawal(s) that still leave the final slot occupied by a builder entry, since builder-sweep withdrawals are processed *after* partial withdrawals but *before* validator sweep and can legitimately occupy slot `MAX_WITHDRAWALS_PER_PAYLOAD - 1`), the sweep cursor divergence recurs.

### Impact Explanation
`next_withdrawal_validator_index` is consensus-critical state that every node must compute identically; it seeds `get_validators_sweep_withdrawals` in the next block. If the value can be perturbed by builder-controlled data (which builder indices/ordering populate `builder_pending_withdrawals`/`state.builders`, controllable by any active builder), a builder can steer which validators get swept for withdrawal in future blocks. This does not directly break consensus determinism (all honest nodes still compute the same formula), but it breaks the intended selection equality — "the next sweep starts right after the last validator actually processed" — turning a supposed round-robin fairness guarantee into a value influenced by an unrelated actor (a builder), i.e. a steerable duty/selection outcome as flagged as in-scope ("a duty selection one participant can steer").

### Likelihood Explanation
Requires reaching the corner case where a full `MAX_WITHDRAWALS_PER_PAYLOAD` withdrawal batch's *final* element is builder-flagged. The existing repository fix (reserving one slot for validator sweep in `get_builder_withdrawals`/`get_builders_sweep_withdrawals`) reduces likelihood substantially for the "pure builder pending overflow" scenario, but the underlying `update_next_withdrawal_validator_index` function was not modified to guard against a mixed batch (builder pending + partial + builder sweep) still ending on a builder entry in the last slot. I was not able to fully trace every combination of `get_pending_partial_withdrawals` count and `get_builders_sweep_withdrawals` count that could still place a builder-flagged entry in the very last of exactly `MAX_WITHDRAWALS_PER_PAYLOAD` slots — this needs execution-level verification (e.g. running the pyspec test harness) to confirm whether the "reserve one slot" invariant actually holds transitively across all four withdrawal-source functions combined, or only bounds each source individually. Given the uncertainty in fully proving the reachable state, I present this as a likely-but-unconfirmed corner case rather than a fully demonstrated exploit.

### Recommendation
Make `update_next_withdrawal_validator_index` filter to the last **validator** (non-builder-flagged) withdrawal before computing the modulo, or track/pass an explicit "last validator index processed" value from `get_expected_withdrawals` rather than deriving it from the tagged `Withdrawal.validator_index` field. This removes the implicit "same field means two different types" assumption instead of relying on downstream call sites to remember to gate on `is_builder_index()`.

### Proof of Concept
Not independently executed against the pyspec harness (no code-execution tool available in this session). Conceptually:
1. Populate `state.builder_pending_withdrawals` and/or age builders into `builder.withdrawable_epoch <= epoch` so that `get_builder_withdrawals` + `get_builders_sweep_withdrawals` contribute several entries.
2. Arrange `state.pending_partial_withdrawals` and validator balances so that the combined withdrawal list from `get_expected_withdrawals` reaches exactly `MAX_WITHDRAWALS_PER_PAYLOAD` entries with a builder-sourced entry (from `get_builders_sweep_withdrawals`, which runs after partial withdrawals) as the last element.
3. Run `process_withdrawals(state)` and observe `state.next_withdrawal_validator_index == (builder_flagged_index + 1) % len(state.validators)`, a value governed by the builder's index rather than any real validator's position, and compare against `spec.get_validators_sweep_withdrawals` run from the "intended" cursor to show the sets of validators swept next diverge from what an index scheme ignorant of `BUILDER_INDEX_FLAG` would intend.

This scenario requires running the actual spec test suite (`tests/core/pyspec/eth_consensus_specs/test/gloas/block_processing/test_process_withdrawals.py`) with a custom state to confirm reachability; I was unable to execute code in this session to validate it end-to-end.

#### New `update_next_withdrawal_validator_index`

```python
def update_next_withdrawal_validator_index(
    state: BeaconState, withdrawals: Sequence[Withdrawal]
) -> None:
    # Update the next validator index to start the next withdrawal sweep
    if len(withdrawals) == MAX_WITHDRAWALS_PER_PAYLOAD:
        # Next sweep starts after the latest withdrawal's validator index
        next_validator_index = (withdrawals[-1].validator_index + 1) % len(state.validators)
        state.next_withdrawal_validator_index = next_validator_index
    else:
        # Advance sweep by the max length of the sweep if there was not a full set of withdrawals
        next_index = state.next_withdrawal_validator_index + MAX_VALIDATORS_PER_WITHDRAWALS_SWEEP
        next_validator_index = next_index % len(state.validators)
        state.next_withdrawal_validator_index = next_validator_index
```
