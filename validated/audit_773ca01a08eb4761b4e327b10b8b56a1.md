### Title
Unvalidated instruction account indices used to directly index `AccountKeys` cause decoder panic - (File: transaction-status/src/lib.rs)

### Summary
The Timelock `cancel()` bug is a case of an unvalidated, attacker-controlled identifier being used directly to compute a memory/storage location without any bounds/derivation check, leading to out-of-range access. The closest reachable analog in this agave repo is in `transaction-status/src/lib.rs`, where `make_ui_partially_decoded_instruction()` and `parse_ui_instruction()` index directly into an `AccountKeys` collection using raw `u8` indices taken from a `CompiledInstruction` (`program_id_index`, `accounts[..]`) without any bounds check, unlike sibling parsers in the same crate.

### Finding Description
`make_ui_partially_decoded_instruction()` computes: [1](#0-0) 
and `parse_ui_instruction()` similarly does: [2](#0-1) 

Both directly index `account_keys[instruction.program_id_index as usize]` and `account_keys[i as usize]` for every `i` in `instruction.accounts`. `program_id_index` and each byte in `instruction.accounts` are raw `u8` values taken from the `CompiledInstruction` as encoded in the transaction message — they are not re-validated against the length of the (possibly loaded-address-augmented) `AccountKeys` at this decoding layer.

This is directly analogous to the Timelock bug: in Solidity, `cancel(bytes32 id)` treated `id` as trusted and used it to derive a storage slot without checking that it actually corresponded to a real operation, allowing manipulation of unrelated slots. Here, sibling instruction parsers in the very same crate (e.g., `parse_token.rs`, `parse_associated_token.rs`) explicitly guard against this exact scenario before indexing: [3](#0-2) [4](#0-3) 
with the comment "Runtime should prevent this from ever happening" — an explicit acknowledgment that this invariant is not otherwise guaranteed at this layer and must be defensively checked. `make_ui_partially_decoded_instruction`/`parse_ui_instruction` in `lib.rs` lack this same defensive check, which is the "fallback" path used whenever a program-specific parser (`parse()`) fails or doesn't recognize the instruction/program.

The account-index space these functions consume is `AccountKeys`, which is a combination of the transaction's static account keys plus any addresses resolved from address-lookup tables at replay time. When historical transaction status is decoded for RPC responses (`getTransaction`/`getConfirmedTransaction`/`getBlock`), the `loaded_addresses` used to reconstruct `AccountKeys` come from `TransactionStatusMeta` stored in the blockstore at execution time, not re-derived length checks at decode time in this fallback function.

### Impact Explanation
If `AccountKeys` length is ever shorter than the maximum account index referenced by an instruction (e.g., due to future protocol changes, malformed/corrupted stored `TransactionStatusMeta`, or use of this function on non-fully-sanitized data), `account_keys[i as usize]` panics with an out-of-bounds index, since `Index` on this slice-backed type does not return `Option`. A panic inside the JSON-RPC request-handling thread (`getTransaction`, `getBlock`, or pubsub log/transaction notifications that reach `EncodableWithMeta`) triggered by decoding a single stored or supplied transaction is a decoder panic reachable from a single unprivileged RPC call — matching the "decoder panic and misreporting" acceptance criterion.

### Likelihood Explanation
Likelihood is lower than the original Timelock bug because normal transaction sanitization (`solana_message`/`solana_sdk_transaction` sanitize checks, `MAX_ACCOUNTS_PER_INSTRUCTION`, etc.) is expected to guarantee `accounts[i] < account_keys.len()` for any transaction that made it into the ledger. This function's own sibling parsers in the same crate treat that guarantee as *not* fully trustworthy at the decode layer ("Runtime should prevent this from ever happening" — implying it is a defensive, not proven, invariant), which is why they add the explicit check that `make_ui_partially_decoded_instruction`/`parse_ui_instruction` omit. I was not able to fully trace, within the remaining tool budget, every call path and every source of `AccountKeys`/`loaded_addresses` construction that feeds into these two functions (e.g., whether any code path can produce a mismatched length before invoking them), so likelihood is assessed as low-to-moderate and unconfirmed pending deeper review of `TransactionStatusMeta`/`AccountKeys` construction across all RPC and geyser paths.

### Recommendation
Add the same defensive bounds check used elsewhere in the crate (as in `parse_token.rs`/`parse_associated_token.rs`) to `make_ui_partially_decoded_instruction()` and `parse_ui_instruction()` in `transaction-status/src/lib.rs`: verify `instruction.program_id_index` and every entry of `instruction.accounts` is `< account_keys.len()` before indexing, and return a graceful error/fallback encoding instead of panicking if not.

### Proof of Concept
Not independently confirmed with a runnable exploit in this session — the code path (`transaction-status/src/lib.rs:96-126`) is confirmed to lack the bounds check via static analysis and by direct comparison with sibling parsers in the same crate that do check. Constructing a concrete PoC would require confirming a code path that supplies `AccountKeys`/`CompiledInstruction` pairs where the invariant `max(accounts) < account_keys.len()` is violated at the point these functions are invoked (e.g., a corrupted/legacy stored `TransactionStatusMeta` with fewer `loaded_addresses` than the instruction's on-chain execution had), which was not fully verified within the available tool budget.

fn make_ui_partially_decoded_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiPartiallyDecodedInstruction {
    UiPartiallyDecodedInstruction {
        program_id: account_keys[instruction.program_id_index as usize].to_string(),
        accounts: instruction
            .accounts
            .iter()
            .map(|&i| account_keys[i as usize].to_string())
            .collect(),
        data: bs58::encode(instruction.data.clone()).into_string(),
        stack_height,
    }
}

pub fn parse_ui_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiInstruction {
    let program_id = &account_keys[instruction.program_id_index as usize];
    if let Ok(parsed_instruction) = parse(program_id, instruction, account_keys, stack_height) {
        UiInstruction::Parsed(UiParsedInstruction::Parsed(parsed_instruction))
    } else {
        UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(
            make_ui_partially_decoded_instruction(instruction, account_keys, stack_height),
        ))
    }
}
