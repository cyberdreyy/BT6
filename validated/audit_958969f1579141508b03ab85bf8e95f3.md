## Analog Found

### Title
No retry of a failed one-shot block push leaves a signer permanently committed to a block the node never receives, wedging it against future valid proposals - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The ETH report's root cause is a one-shot, no-retry push of state-changing effects that silently fails and permanently locks out remediation. The `stacks-signer` v0 protocol has a structurally identical pattern: once a block crosses the 70% signature threshold, the signer performs exactly one push attempt to its own node (`handle_post_block`), commits the block's state to `LocallyAccepted` in `signerdb` *before* that push is attempted, and never revisits the push if it fails. Because the signature is a "bearer instrument" that keeps registering as a conflict regardless of node acknowledgment, a single failed push permanently (until an unrelated staleness timer or a real burnchain reorg) wedges this signer against ever signing any other block at that height/tenure.

### Finding Description
`store_and_process_block_signature` marks the block `LocallyAccepted` and persists it to `signerdb` *before* attempting to deliver it to the node: [1](#0-0) 

The delivery itself, `broadcast_signed_block` → `handle_post_block`, is a single attempt. `StacksClient::post_block` does retry transient HTTP failures internally via exponential backoff, but once that backoff is exhausted (or the node returns a non-transient rejection, e.g. because `process_new_nakamoto_block_ext` on the node side rejects the block for a reason the signer's own validation never checked), the error path in `handle_post_block` does nothing but log a warning — no retry is scheduled, no different state is recorded: [2](#0-1) 

Crucially, there is no other code path that re-triggers this push for the same block. `store_and_process_block_signature` short-circuits on any future signature message for this block once `signed_group` is set: [3](#0-2) 

Meanwhile, this block is now permanently registered in `signerdb` as a signed conflict. Per the signer's own conflict-guard semantics, rejection (even global rejection) clears nothing, and only two conditions clear a conflict: the node confirming the tenure/burn block was orphaned, or the node's canonical chain confirming it reached (and thus superseded) the block: [4](#0-3) 

Since the push failed, the node never received the block, so `get_tenure_tip` will 404 and `node_reaches_conflict` is false — but because the conflict was never `globally_accepted` and its height is `<= proposed_height` for any sibling at the same height, `conflict_still_blocks` returns `true` and keeps blocking: [5](#0-4) 

This is the exact analog of the Aave bug: a single push of a state-changing effect (ETH transfer / block delivery) that, once attempted, is treated internally as "done" (signature recorded, block marked locally accepted) regardless of whether the external party (the redeemer contract / the stacks node) actually received it, with no fallback delivery mechanism.

### Impact Explanation
This falls under "High – a signer wedged into never signing valid blocks." A signer that hits this path becomes unable to endorse any sibling block at that same chain height for as long as the stale conflict record is retained (bounded by whatever freshness/staleness cutoff governs `conflict_still_blocks`'s callers), reducing the effective signing weight available to the network and potentially stalling tenure progress if enough signers experience the same transient node connectivity issue simultaneously (e.g., a shared node restart window, or a node upgrade that briefly rejects `postblock_v3` requests).

### Likelihood Explanation
This does not require a majority of signers or key compromise — any single signer whose RPC connection to its own node blips, times out, or whose node momentarily rejects the block (chain-tip race, node restarting) during the exact push window will fall into this state. It is a plausible operational condition rather than a contrived edge case, and unlike the ETH bug it does not even require malicious input — pure timing/networking suffices, similar in spirit to how the original report emphasized that ordinary EIP-1884-driven gas changes (not attacker action) could turn previously safe fallback functions into permanently unredeemable deposits.

### Recommendation
Do not treat `mark_locally_accepted` + `insert_block` as terminal. Either: (1) record push success/failure explicitly (e.g. a `pushed`/`push_failed` flag alongside `block_broadcasted`) and retry unpushed-but-locally-accepted blocks on a periodic housekeeping tick, mirroring the retry-until-success pattern already used for `StateMachineUpdate`/pre-commit gossip; or (2) fold `handle_post_block` failures back into a status that the conflict guard treats as "not yet delivered, safe to reconsider sooner" rather than requiring the full staleness timeout before this signer can consider a sibling block.

### Proof of Concept
1. Signer set gathers 70% signatures over block B at height H; this signer's `store_and_process_block_signature` calls `mark_locally_accepted(true)` and persists B to `signerdb` [1](#0-0) .
2. `broadcast_signed_block` → `handle_post_block` attempts `stacks_client.post_block(&block)`; the node is momentarily unreachable/restarting and all backoff retries are exhausted, or the node rejects the block for a reason the signer set didn't check. `handle_post_block`'s `Err` arm just logs a warning [6](#0-5) .
3. No further attempt to push B is ever made; B remains `LocallyAccepted`, never `GloballyAccepted`, and is a registered conflict via `get_signed_conflicts`.
4. Miner (same or new) proposes block B′ at height H (e.g., after a legitimate reorg-permit or retry). `conflict_still_blocks` is evaluated: `get_tenure_tip` 404s (node never got B) and `!globally_accepted && height <= proposed_height` holds, so the function returns `true` [5](#0-4) .
5. This signer refuses to sign B′ until the conflict is judged stale, even though B was never delivered to any node and can never become canonical — a self-inflicted liveness wedge caused solely by the earlier one-shot push failure.

    ///
    /// The guard exists to stop us endorsing two blocks that could both end up in the chain. It
    /// must not, however, outlive the block it protects: a Bitcoin reorg can kill a block we
    /// signed, and a dead signature must not stall the chain restarting beneath it.
    ///
    /// Two questions, each answerable by the node at any time:
    ///
    /// 1. Is the tenure's sortition still on the canonical burn chain? We saved the tenure's
    ///    burn block when it arrived, and `/v3/sortitions` resolves it against the node's
    ///    canonical fork. A 404 means a burnchain fork orphaned the tenure: everything it built
    ///    is void, so the conflict is dead no matter what state its block is in.
    ///
    /// 2. Does the node's canonical Stacks chain still reach the block?
    ///    * If it does, the block is real chain state, so it keeps blocking. (If the reorg-timing
    ///      rules sanctioned replacing it, the tenure is recorded as superseded and the conflict
    ///      never reaches this check at all.)
    ///    * If it does not, and the block was once globally accepted, the node had it and a
    ///      reorg moved past it. That is proof it is dead, so it stops blocking.
    ///    * If it does not, and the block was never globally accepted, the node may simply never
    ///      have been handed it, since that only happens once the whole signer set has signed. We
    ///      cannot tell "dead" from "not yet known", so a sibling at the same height keeps
    ///      blocking (signing both would be the double-sign this guard is for), while a block
    ///      above the proposal does not: it is no sibling, and abandoning an unconfirmed block to
    ///      restart beneath it is a reorg rather than an equivocation.
    ///
    /// If we have no saved burn block, or the node is unreachable, the conflict keeps blocking.
    /// That only delays the replacement until our signature goes stale, whereas wrongly signing

    /// Attempt to post a block to the stacks-node and handle the result
    pub fn handle_post_block(&mut self, stacks_client: &StacksClient, block: &NakamotoBlock) {
        #[cfg(any(test, feature = "testing"))]
        if self.test_skip_block_broadcast(block) {
            return;
        }
        let block_hash = block.header.signer_signature_hash();
        match stacks_client.post_block(block) {
            Ok(accepted) => {
                debug!("{self}: Block {block_hash} accepted by stacks node: {accepted}");
                if let Err(e) = self
                    .signer_db
                    .set_block_broadcasted(&block_hash, get_epoch_time_secs())
                {
                    warn!("{self}: Failed to set block broadcasted for {block_hash}: {e:?}");
                }
            }
            Err(e) => {
                warn!("{self}: Failed to broadcast block {block_hash} to the node: {e}")
            }
        }
    }
