### Title
Funded instant-withdraw claims never clear `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, inflating `defaultPendingClaimBasis` and booking phantom recovery reserve on a same-epoch default - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a flag/data desync: `io_futex_data` was assigned without setting `REQ_F_ASYNC_DATA`, and the error path freed the data without clearing the pointer, leaving a dangling marker. The idle-tranches analog is in `IdleCreditVault.claimInstantWithdrawRequest`: when an instant-withdraw receipt is claimed at par, only the aggregate `instantWithdrawsRequests[_user]` is cleared, while the per-epoch markers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are left stale. If the borrower later defaults in that same epoch while another instant receipt is still unfunded, `finalizeDefaultRecovery` reads the stale aggregate through `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, double-counting an already-paid claim and reserving underlying that no longer exists in the strategy.

### Finding Description
- `requestInstantWithdraw` records both the aggregate and per-epoch receipt data: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, `pendingInstantWithdraws` [1](#0-0) .
- When the receipt is funded, `claimInstantWithdrawRequest` burns the receipt tokens and zeroes only `instantWithdrawsRequests[_user]` [2](#0-1) . The per-epoch entries are never cleared on this success path — the "freed data, live pointer" pattern of the CVE.
- Those stale entries are only cleaned inside `_claimDefaultedInstantWithdrawRequest`, which is gated by `defaultInstantWithdrawsFinalized` [3](#0-2) .
- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` [4](#0-3)  — including the claimed, already-paid-out amount.
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and treats it as underlying held in the strategy [5](#0-4) . For a claimed receipt those tokens already left the contract, so this books phantom reserve.
- `finalizeDefaultRecovery` then uses both values: `totalBasis` is inflated (lowering `defaultRecoveryPrice` for all claimants) and `defaultRecoveryReserve` is set above the real balance [6](#0-5) .

### Impact Explanation
Two concrete harms in the defaulted phase:
1. **Diluted recovery price.** The stale claimed amount enlarges `pendingBasis`/`totalBasis`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is lower than it should be, reducing what every defaulted-epoch claimant and active LP recovers — a direct, quantified mispricing (loss ≈ `claimedInstant × (1 - truePrice/truePriceActual)` spread across claimants).
2. **Phantom reserve → permanent freezing.** `defaultRecoveryReserve` includes funds already paid out. Legitimate claimants calling `claimInstantWithdrawRequest`/`claimWithdrawRequest` drain the real balance until `_transferDefaultRecovery` underflows on `defaultRecoveryReserve -= _amount` [7](#0-6) , permanently reverting the tail claims.

Broken invariant: one receipt one payout — a claimed receipt still contributes claim basis and reserve.

### Likelihood Explanation
Requires a specific but unprivileged sequence: (a) attacker requests and successfully claims an instant withdrawal during a running epoch (the normal instant-liquidity path); (b) any other user leaves an instant request unfunded so `pendingInstantWithdraws > 0` at finalization (setting `defaultInstantWithdrawsFinalized = true`); (c) the borrower defaults and recovery is finalized in the same epoch. All actors are unprivileged; default is an honest borrower event, not the attacker. No existing guard prevents it — `_ensureDefaultRecoveryInitialized` only normalizes legacy counters and explicitly never clears instant state [8](#0-7) .

### Recommendation
Mirror the kernel fix — clear data and marker together:
- In `claimInstantWithdrawRequest`, also zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` for the receipt's epoch(s). Since the funded path doesn't track the epoch, either store the request epoch alongside the aggregate (analogous to `lastWithdrawRequest`) or iterate `instantWithdrawsRequestsByEpoch` when clearing.
- Alternatively, make `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` compute instant basis from still-live receipts only (e.g., `sum of instantWithdrawsRequests` or a dedicated unfunded counter) rather than the never-cleared `instantWithdrawClaimsByEpoch` aggregate.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCDOEpochVariant` + `IdleCreditVault` deployment):

```solidity
// test/foundry/InstantWithdrawStaleEpoch.t.sol
function testStaleInstantBasisOnDefault() external {
    // Setup: KYC'd users, deposits, epoch started (isEpochRunning).
    _stopCurrentEpochAndDeposit();
    vm.prank(manager); cdoEpoch.startEpoch();

    // 1) Attacker: instant withdraw request -> borrower funds it -> claim at par.
    uint256 inst = 50e6;
    _requestInstantWithdraw(attacker, inst);       // sets instantWithdrawsRequestsByEpoch[attacker][E]
    _fundInstantWithdraw(inst);                    // CDO calls collectInstantWithdrawFunds
    vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();
    // instantWithdrawsRequests[attacker] == 0 but per-epoch entries are stale
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epoch), inst); // stale marker

    // 2) Victim: instant withdraw request in same epoch, left unfunded.
    _requestInstantWithdraw(victim, 100e6);        // pendingInstantWithdraws > 0

    // 3) Honest borrower defaults; manager finalizes recovery same epoch.
    _borrowerDefaultAndFinalize(partialRecovery);

    // BUG: basis included attacker's already-paid 50e6;
    // reserveAmount counted it as prefunded -> phantom reserve.
    uint256 reserve = strategy.defaultRecoveryReserve();
    uint256 bal = underlying.balanceOf(address(strategy));
    assertGt(reserve, bal, "phantom reserve booked");

    // 4) Victim claims recovery; tail claimant's _transferDefaultRecovery underflows.
    vm.prank(victim); cdoEpoch.claimInstantWithdrawRequest(); // ok or short-paid
    vm.expectRevert(); // second claimant (or AA/BB redeem) reverts: reserve > balance
    vm.prank(otherClaimant); cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty note: I verified the stale-marker write/read paths in `IdleCreditVault.sol`, but could not fully trace whether `IdleCDOEpochVariant`'s instant-withdraw funding flow always routes through `collectInstantWithdrawFunds` before a same-epoch default can be finalized; the PoC assumes `_handleBorrowerDefault`/`finalizeDefaultRecovery` are callable while `pendingInstantWithdraws > 0`, which the code at lines 644–696 explicitly anticipates.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
