Single-step, irrecoverable `dao`/admin-role transfer in `ActivationRegistryStorage::set_admin` — ([File: crates/common/precompiles/src/activation/storage.rs])

### Summary
`ActivationRegistryStorage::set_admin` implements a single-transaction privileged-role transfer for the activation registry admin, matching the reported bug class (single-step `setDao`/`setOwner` without a claim/confirmation step). If the current admin submits an incorrect `new_admin` address, control over the activation registry is permanently and unrecoverably lost, unlike the codebase's own `PolicyRegistry`, which implements a proper two-step `stageUpdateAdmin`/`finalizeUpdateAdmin` pattern for the analogous role.

### Finding Description
`set_admin` writes `new_admin` directly into the `admin` storage slot in the same transaction, after only checking that the caller is the current admin and that `new_admin` is non-zero: [1](#0-0) 

There is no staged/pending-admin field and no separate "claim" transaction required from `new_admin` to confirm receipt of the role, unlike the `PolicyRegistry` admin-rotation mechanism in the same codebase, which uses `stage_update_admin` + `finalize_update_admin` (finalized only by the pending admin) precisely to avoid this class of bug: [2](#0-1) [3](#0-2) 

The activation admin gates `activate`/`deactivate` for core Base-native precompile features (`PolicyRegistry`, `B20Stablecoin`, `B20Asset`) via `require_admin_caller`: [4](#0-3) [5](#0-4) 

The only validation on `new_admin` is a zero-address check; there is no way to verify the address is one the sender actually controls (e.g., a typo'd EOA, a contract without the ability to call `set_admin` back, or a precompile/system address) before the role is transferred: [6](#0-5) 

### Impact Explanation
If the admin address is mis-set to an inaccessible or unintended address, no account can subsequently call `set_admin` to correct it (only the current — now wrong — admin is authorized), and there is no fallback recovery once state-backed admin storage is enabled and non-zero, since a non-zero stored admin always wins over the static fallback: [7](#0-6) 

This permanently freezes the ability to activate or deactivate the `B20Asset`, `B20Stablecoin`, and `PolicyRegistry` features going forward — a permanent loss of a privileged chain-governance capability, matching the "Medium" severity class of the original finding (permanent freezing of a critical operational control, not theft of funds directly, but loss of the ability to manage which precompiles are live on the chain).

### Likelihood Explanation
This requires only a single mistaken/malformed transaction from the legitimate current admin (fat-fingered address, copy-paste error, or wrong checksum) — no attacker action or malicious actor is needed, matching the exact "unlikely but devastating" scenario called out in the source report. The codebase's own test suite exercises `set_admin` only for the happy path and simple guard reverts (zero address, static call, unauthorized caller), with no protection against a valid-but-wrong non-zero address: [8](#0-7) 

### Recommendation
Adopt the two-step pattern already implemented elsewhere in this codebase for `PolicyRegistry` admin rotation (`stage_update_admin` / `finalize_update_admin`) for `ActivationRegistryStorage::set_admin`: stage the `new_admin` in a separate storage slot, and require a transaction from `new_admin` itself to finalize the rotation, only then updating the effective `admin` value.

### Proof of Concept
1. Chain is configured with `ActivationAdminConfig::state_backed(...)`, admin = `A`.
2. `A` calls `set_admin(B)` where `B` is a typo'd address / an address `A` does not control.
3. `set_admin` succeeds in one transaction, `admin` storage is now `B`: [9](#0-8) 
4. `A` can no longer call `activate`/`deactivate`/`set_admin` (`require_admin_caller` rejects it): [5](#0-4) 
5. Since `B` never controls a private key for that address, no one can ever call `set_admin` again — the activation registry's admin role is permanently bricked, freezing the ability to activate/deactivate `B20Asset`, `B20Stablecoin`, and `PolicyRegistry` features.

    pub fn set_admin(
        &mut self,
        new_admin: Address,
        admin_config: ActivationAdminConfig,
    ) -> Result<()> {
        if self.storage.is_static() {
            return Err(BasePrecompileError::revert(IActivationRegistry::StaticCallNotAllowed {}));
        }
        if !admin_config.state_enabled {
            return Err(BasePrecompileError::revert(
                IActivationRegistry::AdminStorageNotEnabled {},
            ));
        }
        if new_admin.is_zero() {
            return Err(BasePrecompileError::revert(IActivationRegistry::ZeroAdminAddress {}));
        }

        let caller = self.require_admin_caller(admin_config)?;

        self.__initialize()?;
        self.admin.write(new_admin)?;
        self.emit_event(IActivationRegistry::AdminChanged {
            previousAdmin: caller,
            newAdmin: new_admin,
            caller,
        })?;

        Ok(())
    }
