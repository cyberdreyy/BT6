### Title
External ERC4626 liquidity/valuation manipulation aborts `stopEpoch` and can force a spurious default — programmable borrower trust in an unauthenticated vault channel - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
Like CVE-2021-41034, where build-time binaries were pulled over an unauthenticated channel and could be substituted by a MITM, `ProgrammableBorrower.onStopEpoch` pulls both liquidity and the epoch's pricing valuation from an external ERC4626 vault that pool-unprivileged users can manipulate. Any user of that vault (an explicitly in-scope attacker) can (a) drain the vault's redeemable liquidity so `vault.withdraw` reverts and `stopEpoch` cannot complete, or (b) depress `convertToAssets` below the required shortfall so the hook returns `true`, the subsequent `transferFrom` fails, and `IdleCDOEpochVariant` records a borrower default with BB-first loss socialization even though the vault position is later recoverable.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` delegates the critical stop-epoch step to the programmable borrower hook (`contracts/IdleCDOEpochVariant.sol:395-404`):

```solidity
if (!IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)) {
  _handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws);
  return;
}
```

Inside `onStopEpoch` (`contracts/strategies/idle/ProgrammableBorrower.sol:239-253`) the hook decides coverage using the external vault's own `convertToAssets` (`_currentVaultAssets()`), then calls `vault.withdraw`:

```solidity
if (shortfall > _currentVaultAssets()) return true;
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
  ...
} catch {
  revert StopEpochVaultLiquidityUnavailable();
}
```

Two properties are fully controlled by an unprivileged user of the ERC4626 vault:

1. **Redeemable liquidity.** If the vault's underlying liquidity is exhausted (e.g., an attacker borrows all idle assets from the Morpho markets a MetaMorpho vault allocates to, or mass-redeems a redeemable vault), `vault.withdraw` reverts and `StopEpochVaultLiquidityUnavailable` bubbles up through `stopEpoch`, which then cannot complete. The epoch stays running, pending withdraw requests can never be claimed, and `startEpoch`/deposit flows remain blocked for as long as the attacker maintains the liquidity squeeze. The same condition also blocks the owner/manager escape hatch `emergencyExitVault`, since `vault.redeem` is equally liquidity-bound (`ProgrammableBorrower.sol:361-372`).

2. **Reported coverage.** When `convertToAssets` is depressed below the shortfall (e.g., during an attacker-induced vault loss event or on vaults whose `totalAssets` is balance/price manipulable), the hook takes the `return true` path at line 245 *without* pulling liquidity. `getFundsFromBorrower`'s `transferFrom` then fails and `_handleBorrowerDefault` executes — a hard default that triggers `onDefault()`, burns epoch accounting, and socializes the "missing" funds BB-first. The vault shares, however, still exist and can later be recovered via `emergencyExitVault`, meaning a recoverable position was prematurely booked as a realized loss to junior tranche holders.

### Impact Explanation
- **Temporary freezing of the entire pool TVL**: for the duration of a liquidity squeeze, `stopEpoch` always reverts, so no withdraw request can be paid out and no new epoch can start; all tranche holders' funds (full `getContractValue()`) are frozen while the attacker's cost is only the borrow interest / opportunity cost of the vault position.
- **Permanent mis-booked loss**: on the depressed-valuation path, a non-defaulting borrower is defaulted and the resulting `lossAmount` is imposed BB-first on junior tranche holders and pending receipts, while the recovered vault assets remain in `ProgrammableBorrower` — a direct, quantified loss equal to the depressed `shortfall`.

### Likelihood Explanation
The attacker needs no privilege: any EOA that can interact with the underlying ERC4626 vault (supply/borrow/redeem on Morpho markets backing MetaMorpho, or deposit/redeem on balance-based vaults) qualifies. Both manipulations are atomic-sandwichable around the manager's `stopEpoch` call, and the liquidity variant can be repeated indefinitely at bounded cost. The only mitigations — the `shortfall > _currentVaultAssets()` early-true and the revert-retry design — are themselves the mechanism, not guards against manipulation.

### Recommendation
- Do not treat an external vault's instantaneous `convertToAssets`/liquidity as the solvency oracle: on `vault.withdraw` failure, allow a graceful degrade path (e.g., partial pull + retained vault shares transferred or escrowed to the CDO/strategy) instead of revert-or-default.
- Only enter the default path after an explicit, owner/manager-confirmed realized-loss settlement (e.g., redeem shares for what they fetch and book the realized shortfall), rather than inferring insolvency from a single failing `withdraw`.
- Consider pulling vault *shares* to the strategy during `onStopEpoch` and redeeming them asynchronously, decoupling epoch settlement from the vault's instantaneous liquidity.

```solidity

//   attacker supplies large collateral to m, borrows ~all market liquidity.
// Morpho borrows only require collateral; attacker cost = borrow interest.

// Step 2 — manager attempts to stop the epoch.
vm.prank(manager);
vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);

// onStopEpoch: shortfall <= vault.convertToAssets(shares) (solvency intact),

assertTrue(cdoEpoch.isEpochRunning());
// pending withdraw requests remain unclaimable; TVL frozen for the duration.
```
