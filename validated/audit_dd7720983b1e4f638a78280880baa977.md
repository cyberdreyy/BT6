### Title
Stale confirmations from removed multisig members can be counted toward the confirmation threshold, allowing requests to execute below the required live-member quorum - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The multisig contracts' `delete_member`/`DeleteKey` logic only purges confirmations for requests that the removed member *originated*, but never scans and removes that member's confirmation entries from *other* outstanding requests they had confirmed as a participant. This breaks the binding `confirmations counted == confirmations from live members`, letting a request execute with fewer genuine confirmations than `num_confirmations` requires.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` compares `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide whether to execute a request [1](#0-0) . The `confirmations` set is a `HashSet<String>` of `member.to_string()` values, one entry per member who has confirmed a given `request_id`.

When a member is removed via `delete_member`, the code only removes requests that member had *created* (`r.member == member`), and deletes the confirmation sets for *those* requests [2](#0-1) . It does not iterate over all other active `requests` to strip that member's entry out of their `confirmations` sets. Consequently, if member `M` confirmed some other still-outstanding request `R` (created by a different member) and is later removed from `self.members`, `M`'s confirmation string remains in `confirmations[R]` forever, still counted by the `>=` comparison in `confirm()`.

The equivalent flaw exists in the older `multisig/src/lib.rs` contract: the `DeleteKey` action removes only requests where `r.signer_pk == pk` (the deleted key's own requests) and their confirmations, but does not clean the deleted key's confirmation entries from other pending requests' `confirmations` map [3](#0-2) .

This is structurally analogous to the "phantom levels" bug: a check (`isAdminOfHat`/here, `num_confirmations` threshold) trusts a path/entry (an admin hat / here, a confirmation) without verifying the entry still corresponds to a live, valid entity (a real minted hat / here, a current multisig member). The protocol's implicit invariant — every entry in `confirmations` corresponds to a currently active member — is not actually enforced once membership changes.

### Impact Explanation
This breaks the multisig's core custody/authorization binding: "confirmations counted vs live members." A request (e.g. a `Transfer` of NEAR, `AddKey`/`AddMember` granting new signers, or a `DeployContract` upgrade) can be executed with a confirmation count that includes a "ghost" confirmation from an account that is no longer a member. This can let the request execute with fewer than `num_confirmations` distinct *live* approvers, effectively lowering the K-of-N threshold, allowing moving funds or altering multisig configuration below the intended authorization threshold. This matches the Critical impact category: "a multisig request executed below threshold."

### Likelihood Explanation
The precondition — a member confirms a request, and is later removed from the multisig while that request is still outstanding (not yet reaching threshold and not yet deleted) — is a realistic operational sequence in multisig governance (member rotation, key revocation, offboarding), and requires no privileged bypass; it happens through the normal, documented `confirm`/`AddMember`/`DeleteMember` (or `AddKey`/`DeleteKey`) flow that any current majority of members can trigger. No malicious input or race condition beyond standard usage is required.

### Recommendation
In `delete_member` (`multisig2/src/lib.rs`) and the `DeleteKey` branch (`multisig/src/lib.rs`), iterate over all active `requests`/`confirmations` entries (not just ones the removed member created) and remove the removed member's/key's entry from every request's confirmation set, e.g.:
```rust
for (request_id, _) in self.requests.iter() {
    if let Some(mut confs) = self.confirmations.get(&request_id) {
        if confs.remove(&member.to_string()) {
            self.confirmations.insert(&request_id, &confs);
        }
    }
}
```
Alternatively, validate at `confirm()` time that every entry in `confirmations` still belongs to `self.members` before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` creates request `R` (e.g. `Transfer` of funds) via `add_request`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (len 1, below threshold).
4. Members execute an already-confirmed `DeleteMember { member: B }` request, removing `B` from `self.members`. Per `delete_member` [2](#0-1) , since `B` did not create `R`, `R`'s confirmations are untouched — `confirmations[R]` still equals `{B}`.
5. `C` (still a live member) calls `confirm(R)` → `confirmations.len() + 1 = 2`, still below 3, so it just inserts `C`: `confirmations[R] = {B, C}`.
6. `D` calls `confirm(R)` → `confirmations.len() + 1 = 3 >= num_confirmations(3)` → `execute_request(R)` fires, transferring funds/executing the action — even though only 2 currently-live members (`C`, `D`) actually approved it, with `B`'s stale confirmation making up the deficit.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }

        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);

            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
