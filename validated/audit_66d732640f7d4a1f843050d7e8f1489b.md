### Title
Unvalidated tranche address in epoch-variant withdrawal/write-off paths lets an attacker inject a fake tranche token and steal vault underlyings - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
CVE-2020-7609 is a code-injection bug: `node-rules.fromJSON()` evaluates user-supplied strings as executable rules with no sanitization. The credit-vault analog is attacker-supplied input that the contract interprets as a trusted system object without validating it against the set of legitimate values. In `IdleCDOEpochVariant`, withdrawal and write-off entry points take the tranche address as a user parameter (e.g., `requestWithdraw(amount, tranche)`, `writeOffDeposit(tranches, tranche)` — the latter's signature is exercised in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:230`). Downstream, `IdleCDOCreditVault._withdrawOps` uses the supplied `_tranche` directly: it calls `IdleCDOTranche(_tranche).burn(msg.sender, _amount)` and then selects which NAV bucket to decrement with a plain `_tranche == AATranche` equality test — any other address silently falls into the `else` branch that decrements `lastNAVBB` [1](#0-0) . If the epoch variant does not enforce `_tranche == AATranche || _tranche == BBTranche` before calling `_withdrawOps`, the parameter becomes injected "code": the attacker substitutes their own contract for the burn step while the vault mutates real accounting and pays out real underlyings.

### Finding Description
`_withdrawOps(uint256 _amount, uint256 _underlyings, address _tranche)` performs three things keyed off the caller-supplied address: (1) `IdleCDOTranche(_tranche).burn(msg.sender, _amount)`, (2) `lastNAVBB -= _underlyings` whenever `_tranche != AATranche`, (3) `_updateSplitRatio` [2](#0-1) . There is no membership check that `_tranche` is one of the two tranche tokens deployed in `initialize` (`AATranche`/`BBTranche` at `IdleCDOCreditVault.sol:65-66`) [3](#0-2) .

An attacker deploys `FakeTranche` implementing `burn(address,uint256)` as a no-op (and `totalSupply()`/`decimals()` as needed by `virtualPrice`/`_trancheSupply` paths). In a stopped epoch (or wherever `requestWithdraw`/`collectWithdrawFunds`/`writeOffDeposit` route into `_withdrawOps` or the equivalent NAV-decrement path), the attacker calls the withdrawal function passing `address(FakeTranche)`:

- `burn` succeeds trivially — no real tranche tokens are consumed, so "one receipt one payout" is broken.
- `_tranche != AATranche`, so `lastNAVBB -= _underlyings` executes, deflating `priceBB` and shifting the `trancheAPRSplitRatio` via `_updateSplitRatio` — real NAV is drained from honest BB holders' accounting.
- The attacker receives `_underlyings` of `token` (or, in the write-off path, releases funded claims) without surrendering any vault claim.

### Impact Explanation
Direct theft plus insolvency: each call pays out `_underlyings` while burning zero value, and simultaneously corrupts `lastNAVBB`/`priceBB`, so remaining BB holders absorb a phantom loss while the attacker exits with underlyings. Repeatable until the buffer/vault balance is drained — quantified loss equals the lesser of vault liquid balance and `lastNAVBB`, i.e., effectively all BB NAV plus whatever liquidity the payout path draws down.

### Likelihood Explanation
Requires only an EOA (no KYC, no privileged role) if the public entry point that forwards `_tranche` lacks a whitelist check. Caveat: I could not fully verify the parameter-validation logic inside `IdleCDOEpochVariant.requestWithdraw`/`writeOffDeposit` within the tool budget — the grep hit 104 matches and the exact guard lines were not read. If the epoch variant does check `tranche == AATranche || tranche == BBTranche` at the boundary, this finding does not hold and should be discarded. The PoC below asserts the exploit only where that check is absent.

### Recommendation
Validate the tranche parameter at every public entry point that forwards it into accounting: `if (_tranche != AATranche && _tranche != BBTranche) revert NotAllowed();` before any `burn`/NAV mutation. Additionally, inside `_withdrawOps` itself, replace the `if/else` on `== AATranche` with an explicit revert for unknown tranches so internal callers cannot silently mis-bucket NAV [4](#0-3) .

### Proof of Concept
Foundry fork PoC sketch (reproducible where the guard is absent):

```solidity
contract FakeTranche {
    function burn(address, uint256) external {} // no-op burn
    function totalSupply() external pure returns (uint256) { return 1; }
    function decimals() external pure returns (uint8) { return 18; }
}

function testFakeTrancheWithdrawalTheft() public {
    // epoch stopped; attacker holds no real tranche tokens
    FakeTranche fake = new FakeTranche();
    uint256 vaultBalPre = underlying.balanceOf(address(cdoEpoch));
    uint256 attackerPre   = underlying.balanceOf(attacker);

    vm.prank(attacker);
    // if this succeeds, the guard is missing and funds are paid against no burn
    cdoEpoch.requestWithdraw(1000e18, address(fake));
    cdoEpoch.claimWithdrawRequest(); // or equivalent payout path

    assertGt(underlying.balanceOf(attacker) - attackerPre, 0);
    assertLt(underlying.balanceOf(address(cdoEpoch)), vaultBalPre);
    assertLt(cdoEpoch.lastNAVBB(), navBBPre); // phantom loss socialized to BB
}
```
