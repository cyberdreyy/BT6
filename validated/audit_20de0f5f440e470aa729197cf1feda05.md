### Title
Unsanitized path traversal in Vault KV-v2 `engine.dataPath`/`metadataPath` allows job-controlled `VaultSecret.Path` to escape the configured mount prefix - (File: helpers/vault/secret_engines/kv_v2/engine.go)

### Summary
`engine.dataPath` and `engine.metadataPath` build the Vault API request path with `path.Join(e.path, "data", p)` / `path.Join(e.path, "metadata", p)`, where `p` is the job-controlled `VaultSecret.Path` field. Because `path.Join` internally calls `path.Clean` on the concatenated string, a sufficient number of `../` segments in `p` can walk back past the configured mount prefix `e.path` itself, producing a Vault request path outside the intended mount/subpath boundary.

### Finding Description
`VaultSecret.Path` is a plain `string` field in `common/spec/spec.go` (`VaultSecret` struct, line ~782) that is expanded with job variables in `VaultSecret.expandVariables` [1](#0-0) . Job variables (including CI/CD variables set by a pipeline author/trigger) are attacker-influenced input, so the final `Path` string reaching the resolver is effectively job-controlled.

The call chain is: `resolver.Resolve()` reads `secret.Vault` and calls `s.GetField(secret, secret)` [2](#0-1) , which eventually reaches `engine.Get(path)`: [3](#0-2) 

`engine.Get` passes the raw job-controlled `path` string straight into `e.dataPath`, which does no validation or normalization check before joining: [4](#0-3) 

The same pattern exists for `Delete`/`metadataPath`: [5](#0-4) 

`path.Join` treats its arguments as one combined string and calls `path.Clean`, which resolves `..` lexically against everything to its left, including the `e.path` mount component itself. For example, with `e.path = "secret"` and `p = "../../other-project/secret"`, `path.Join("secret", "data", "../../other-project/secret")` cleans to `"other-project/secret"` — the resulting Vault path no longer contains the configured mount prefix at all, and Runner performs a `client.Read` against a completely different top-level path than the administrator intended to scope the job to.

There is no check anywhere in `engine.Get`/`Put`/`Delete` (or upstream in the resolver/service layer, based on what is reachable in `helpers/vault/service`) that rejects `..` segments, absolute paths, or verifies the final joined path still has `e.path` as a prefix.

### Impact Explanation
If a Vault deployment scopes CI secrets by relying on the runner-configured mount path/prefix (`e.path`) as the sole isolation boundary — while granting the runner's authenticated Vault token/role broader read permissions across sibling paths (a common integration pattern, e.g. a shared JWT auth role with a policy on `secret/data/*` intended to be constrained per-project only by the mount path the job requests) — an unprivileged pipeline author can craft `Path` with `../` sequences to read secrets outside the intended KV subpath/mount, i.e., cross-project secret disclosure via path traversal. The actual reachability of another project's secret still ultimately depends on Vault-side ACL policy scope, but the Runner provides no defense-in-depth check to enforce the "job-controlled path must stay under the configured mount" invariant, which the audit question specifically calls out.

### Likelihood Explanation
This is straightforward to trigger: any pipeline author who can set the `secrets:vault:path:` value or influence a CI/CD variable used inside it can supply `../` traversal sequences (subject to whatever normal string content GitLab's `secrets:` schema permits in that field). No special executor, image, or admin privilege is required — it's a pure string-construction defect exercised on every `Get`/`Put`/`Delete` call. Exploitability for actual cross-project data exposure is gated by Vault-side policy configuration, which is outside Runner's control, but the Runner-level check is genuinely missing.

### Recommendation
In `engine.dataPath`/`engine.metadataPath` (and any other `SecretEngine` implementations using the same pattern), sanitize `p` before joining: reject or strip leading `/`, reject any resulting path containing `..` after `path.Clean`, and assert that the final joined path still has `e.path` as a strict prefix (e.g. `strings.HasPrefix(cleaned, e.path+"/")`) before issuing the Vault API call. Return an error instead of silently proceeding if the invariant is violated.

### Proof of Concept
```go
func TestEngine_Get_PathTraversalEscapesMount(t *testing.T) {
    client := new(vault.MockClient) // mocked vault.Client
    client.On("Read", mock.AnythingOfType("string")).
        Return(nil, nil).
        Run(func(args mock.Arguments) {
            requestedPath := args.String(0)
            assert.True(t, strings.HasPrefix(requestedPath, "secret/"),
                "requested Vault path %q escaped configured mount prefix", requestedPath)
        })

    e := NewEngine(client, "secret")
    _, _ = e.Get("../../other-project/secret")

    client.AssertExpectations(t)
}
```
Expected current (buggy) behavior: `client.Read` is invoked with `"other-project/secret"` (mount prefix `secret/` stripped entirely), failing the `HasPrefix` assertion — demonstrating the traversal escape. A fuzz test over `p` values containing `..`, URL-encoded `%2e%2e`, embedded NUL bytes, and absolute paths (`/foo`) should assert `strings.HasPrefix(result, e.path+"/")` holds for every generated input once a fix is applied.
