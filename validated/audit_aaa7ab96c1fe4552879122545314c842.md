### Title
Dust-deposit donation can permanently block an exited builder's reactivation via strict `balance == 0` check - (File: specs/gloas/beacon-chain.md, function `process_builder_deposit_request`)

### Summary
`process_builder_deposit_request` resets an exited builder's `withdrawable_epoch` back to `FAR_FUTURE_EPOCH + MIN_BUILDER_WITHDRAWABILITY_DELAY`-style reactivation only when the builder's on-chain balance is *exactly* zero at the moment the top-up is processed [1](#0-0) . Builder deposit requests (top-ups) are permissionless — anyone can submit a `BuilderDepositRequest` for any existing builder pubkey, and top-ups do not require a valid signature [2](#0-1) . This mirrors the reported "PT donation" bug class: a strict equality check on a balance that can be nudged by an unprivileged third party, causing a legitimate operation to permanently fail (DOS).

### Finding Description
When a builder deposit request targets an existing pubkey, the spec does:
```
if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
    epoch = get_current_epoch(state)
    builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY
builder.balance += request.amount
``` [3](#0-2) 

This reset only fires when `balance == 0` exactly. The intended flow (confirmed by tests) is: a builder exits, its full balance is swept to `0` via `get_builders_sweep_withdrawals` (`builder.withdrawable_epoch <= epoch and builder.balance > 0`) [4](#0-3) , and once truly at `0`, a subsequent top-up deposit both re-funds the builder and resets its `withdrawable_epoch` so `is_active_builder` can later become `True` again after finalization [5](#0-4) .

Because deposits are permissionless and unauthenticated for top-ups, any third party can send a dust deposit (e.g. `Gwei(1)`) to the exited builder's pubkey/withdrawal-credential pair the instant the sweep zeroes the balance but before the builder's real re-registration deposit lands. That dust deposit makes `builder.balance` non-zero again, so when the builder's genuine top-up deposit is processed, `balance == 0` is `False` and the `withdrawable_epoch` reset branch is skipped — the builder's balance increases but `withdrawable_epoch` stays stuck in the past. Since `is_active_builder` requires `withdrawable_epoch == FAR_FUTURE_EPOCH` [6](#0-5) , and there is no other code path that resets `withdrawable_epoch` back to `FAR_FUTURE_EPOCH` for an already-exited builder, the builder is permanently locked out of the active-builder set — a griefer with no stake at risk can indefinitely DOS a builder's re-registration for as little as 1 Gwei per attempt (they only need to win the race after each sweep). The test suite explicitly documents the intended pre/post behavior split between `balance == 0` (reset happens) and `balance > 0` (no reset) [7](#0-6) [8](#0-7) , confirming the equality is load-bearing and unprotected against dust griefing.

### Impact Explanation
This does not directly steal Gwei, but it permanently and unauthorizedly mutates a builder's ability to become active again without its authority — an unprivileged, stakeless third party can lock a builder's reactivation indefinitely by racing a 1-Gwei deposit against the builder's own re-registration deposit after every sweep. This falls under "a validator or builder ... re-credentialed [or reactivated] without its authority" / permanent denial of a legitimate state transition that the spec intends to allow, matching the High-severity category of unauthorized mutation of a builder without its authority.

### Likelihood Explanation
Likelihood depends on the attacker being able to observe the exact epoch/slot at which the sweep zeroes the target builder's balance and then front-run/interleave a 1-Gwei execution-layer deposit before the builder's own re-registration deposit is included and finalized. Builder deposit requests are processed via execution-layer requests included on-chain, so an attacker monitoring the mempool/EL state and continuously re-submitting cheap deposits after every sweep could reliably win this race, since the cost per attempt is minimal (1 Gwei, effectively unlosable since it goes to their own builder... wait, actually the dust deposit's Gwei stays with the *target* builder's balance, so the attacker's cost is the donated dust itself, which is lost to the target builder). This keeps the attacker's cost near-zero and repeatable every sweep cycle, making sustained griefing practically feasible for a determined actor.

### Recommendation
Do not gate the `withdrawable_epoch` reset on the exact value `balance == 0`. Instead, track whether the builder has been fully swept using an explicit sentinel/flag (e.g., a dedicated "swept" boolean, or comparing against the balance value captured at the time the exit was finalized) rather than relying on the mutable `balance` field which any unauthenticated depositor can perturb. Alternatively, require top-up deposits directed at an exited builder to also carry a valid deposit signature (removing the "unsigned top-up" permission for exited/inactive builders) so that only the legitimate execution-address owner can influence the reset condition.

### Proof of Concept
1. Builder `B` (index `i`) is active, then submits `process_builder_exit_request`; `withdrawable_epoch` is set to `current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY` [9](#0-8) .
2. Once `withdrawable_epoch <= epoch`, the withdrawal sweep pays out `B`'s full balance, setting `builder.balance == 0` [10](#0-9) .
3. Attacker `A` (no relation to `B`, no signature required) submits a `BuilderDepositRequest` for `B`'s pubkey with `amount = Gwei(1)` the moment the sweep completes. `process_builder_deposit_request` runs the `balance == 0` branch, resets `withdrawable_epoch`, and sets `balance = 1` — this itself is harmless if it lands first.
4. However, if instead `A`'s dust deposit lands *after* the sweep but *before* `B`'s intended real re-registration deposit, then when `B`'s deposit is processed, `builder.balance` is already `1` (non-zero) so the reset branch is skipped: `withdrawable_epoch` remains stuck at its old past value while `balance` grows by `B`'s deposit amount.
5. From then on `is_active_builder(state, i)` evaluates `builder.withdrawable_epoch == FAR_FUTURE_EPOCH` as `False` forever [6](#0-5) , and there is no other spec path to reset it — `B` can never bid or become active again through this builder index, despite having redeposited a full stake, unless `B`'s balance is swept back to exactly `0` again (which itself can be re-griefed by `A` repeating the attack after every future sweep).

def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:

    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
