Based on the investigation, I found a legitimate analog to the "validate once, act later without re-validating" bug class from the CVE, in the pre-commit → signature gate of the v0 signer.

### Title
Stale miner-validity/timeout state is not re-checked before a signer signs, allowing a signature over a block from a miner the signer's own sortition view has since invalidated - (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionsView::check_proposal` (v1) is the only place that evaluates whether the proposing miner is still `SortitionMinerStatus::Valid` — it lazily flips the status to `InvalidatedBeforeFirstBlock` on a timeout check performed inline, but that mutation only happens when `check_proposal` itself runs (i.e., on a fresh proposal evaluation). The gate that is re-run immediately before a signature leaves the signer, `check_block_against_signer_db_state`, never re-invokes this miner-validity/timeout logic — it only re-checks tenure confirmation (`check_latest_block_in_tenure` / `check_tenure_change_confirms_parent`).

### Finding Description
`check_proposal` performs the timeout-driven miner invalidation as a side effect of being called: [1](#0-0) 

This state mutation (`self.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock`) only fires while evaluating a proposal — there is no independent timer or background task that re-runs it.

The signer's own docs confirm that this check belongs to the proposal path only and is explicitly **not** re-run later: [2](#0-1) 

The two gates that *are* re-run before a signature is produced — at validate-ok (`handle_block_validate_ok`) and at the pre-commit threshold (`handle_block_pre_commit`) — both call `check_block_against_signer_db_state`, which only checks tenure confirmation, never miner status/timeout: [3](#0-2) 

And the pre-commit-threshold signing path re-runs exactly that same function right before marking the block locally accepted and broadcasting a signature: [4](#0-3) 

So the sequence is: a proposal from miner M passes `check_proposal` while M is still `Valid`; the block is pre-committed by peers over time; while pre-commits are accumulating toward the 70% weight threshold, `block_proposal_timeout` elapses for that tenure, meaning a *fresh* `check_proposal` call would now invalidate M (`InvalidatedBeforeFirstBlock`) — but because no new proposal triggers that re-evaluation, the signer's local `cur_sortition.miner_status` field is never actually flipped. When the pre-commit threshold is subsequently reached, only `check_block_against_signer_db_state` runs, which is blind to miner status/timeout, so the signer signs anyway.

### Impact Explanation
This breaks the "signed vs validated" equality the design intends to hold: the whole point of the two-round (pre-commit → signature) protocol described in `docs/signer-flows.md` is that "one last look" happens before the signature leaves the box, specifically to re-check that the world still supports signing. Here, one entire class of invalidation (timed-out/invalid miner) silently drops out of that last look, so a signer can end up putting a signature on a block proposed by a miner it would otherwise consider invalid at that moment. This matches the "signer signing a block that should have been rejected" impact tier.

### Likelihood Explanation
No majority or key compromise is required: a single miner (or simply the natural passage of `block_proposal_timeout` while pre-commit gossip continues to trickle in from honest peers) is sufficient to create the window between "would fail if re-evaluated" and "the only re-check performed doesn't look at that criterion." The precondition is just timing between the pre-commit round finishing and the timeout elapsing, which a miner or network conditions can influence.

### Recommendation
Have `check_block_against_signer_db_state` (or an equivalent check invoked from both `handle_block_validate_ok` and `handle_block_pre_commit`) also re-verify that the sortition/miner for the block's `consensus_hash` is still considered valid (i.e., re-run the timeout/`SortitionMinerStatus` check from `check_proposal`) rather than relying on that mutation happening only as a side effect of a fresh proposal evaluation.

### Proof of Concept
1. Miner M wins a sortition and proposes tenure-start block B; signers validate via `check_proposal`, find M `Valid`, and start pre-committing.
2. M goes idle (deliberately or due to network conditions) long enough that `block_proposal_timeout` elapses for this tenure, but no new proposal arrives to re-trigger `check_proposal`'s timeout check.
3. Pre-commits from the already-committed signers continue to propagate over StackerDB and cross the 70% weight threshold.
4. `handle_block_pre_commit` re-runs only `check_block_against_signer_db_state` (tenure confirmation only) — not `check_proposal` — so the signature is produced for B even though a fresh evaluation at this point would have marked M's sortition `InvalidatedBeforeFirstBlock` and rejected the block.

    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }
