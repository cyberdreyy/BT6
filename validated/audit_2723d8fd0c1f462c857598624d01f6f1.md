### Title
Reused Builder Index Lets a Pending Builder Payment Debit an Unrelated Successor Builder - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_index_for_new_builder` allows a fully exited, zero-balance builder's registry slot (`builder_index`) to be reassigned to a completely different builder (new pubkey) once `withdrawable_epoch <= current_epoch` and `balance == 0` [1](#0-0) . However, `BuilderPendingPayment`/`BuilderPendingWithdrawal` entries reference builders only by this same `builder_index`, not by pubkey [2](#0-1) . If a payment tied to the old occupant of that index is still in flight (queued in `builder_pending_payments`/`builder_pending_withdrawals`) when the slot is reused, the withdrawal will later be applied against the *new* builder occupying that index, deducting Gwei from a party that never incurred that obligation - the exact bug class described in the report (`updateOwner()` reassigning an owner-keyed slot without syncing/protecting stale pending amounts tied to the old owner).

### Finding Description
`process_builder_exit_request` only blocks exit while there is a pending payment *at the time of the exit request*: it checks `get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0` before calling `initiate_builder_exit` [3](#0-2) . This check is not re-validated at the moment the slot becomes reusable, nor at the moment a new builder deposit reuses the slot in `process_builder_deposit_request` [4](#0-3) .

Because bid settlement is asynchronous (a builder's payment for slot `N` is queued in `state.builder_pending_payments`/`builder_pending_withdrawals` and only converted to an actual balance decrease later, when `get_builder_withdrawals` runs during `process_withdrawals`) [5](#0-4) , there is a window between (a) a bid being accepted/settled for builder index `B` and (b) the corresponding `BuilderPendingWithdrawal(builder_index=B, ...)` actually being processed and debited from `state.builders[B].balance`.

During that window, if builder `B` fully exits and is swept to `balance == 0`, its slot satisfies `get_index_for_new_builder`'s reuse condition (`withdrawable_epoch <= current_epoch and balance == 0`) and can be handed to a brand-new, unrelated builder via `add_builder_to_registry`/`process_builder_deposit_request` [6](#0-5) . The stale `BuilderPendingWithdrawal(builder_index=B, ...)` is still queued referencing index `B` by index only. When it is eventually processed, `get_builder_withdrawals` withdraws `min(withdrawal.amount, builder.balance)` from `state.builders[B]`, which is now the *new* builder [7](#0-6) . The equality broken is "a validator/builder mutated without its authority" and "Gwei ... paid to a non-owner": the new builder's stake is silently reduced to pay off a debt it never incurred, and the withdrawal is sent to `withdrawal.fee_recipient`, an address the new builder never authorized to be paid from its balance.

This is precisely the report's bug class: an index-keyed mapping (`adapterOwners[adapter]` / here `builder_index -> Builder`) is reassigned to a new owner (`updateOwner()` / builder-slot reuse) while other index-keyed pending state (`refereeFeeAmounts` / `builder_pending_payments`/`builder_pending_withdrawals`) is not synced or invalidated, so the pending amount gets misapplied against the new owner instead of the rightful (old) party.

### Impact Explanation
This breaks a Critical/High-severity equality: Gwei is deducted from a builder's balance and paid to a `fee_recipient` the current owner of that index never authorized ("builder mutated without its authority" / "Gwei ... paid to a non-owner"). The magnitude equals the queued builder payment amount (bounded by bid value, potentially the builder's entire remaining balance if smaller). It also silently harms the *original* payee's expectation is preserved (the correct address still gets paid) but at the expense of an innocent third party's stake, which is itself an unauthorized balance mutation of a builder that did nothing wrong.

### Likelihood Explanation
Requires: (1) a builder's bid settles into `builder_pending_payments`/`builder_pending_withdrawals` referencing index `B`; (2) builder `B` exits and gets fully swept (`balance == 0`) before that specific withdrawal is processed out of the queue; (3) a new builder deposit request lands in the same or a later block, landing on the now-reusable index `B` via `get_index_for_new_builder` (which picks the first eligible index, so this is not hard to target); (4) the stale withdrawal is processed after the slot reuse. All of these are permissionless EL-triggered operations (builder deposit/exit requests) with no special privilege required, and the queue-processing ordering (`builder_pending_withdrawals` before validators/builders sweep, and index reuse happening independently in operation processing) makes the race plausible within ordinary epoch/slot timing, though it needs careful sequencing by an attacker or unlucky timing by honest actors. This lands as a real, exploitable protocol design gap in the current spec text, not merely a theoretical concern, since `get_pending_balance_to_withdraw_for_builder` is checked only at builder-exit time and never again at slot-reuse time.

### Recommendation
Prevent slot reuse while any pending payment/withdrawal still references that `builder_index`, mirroring the exit-time check: `get_index_for_new_builder` (or `add_builder_to_registry`) should additionally verify `get_pending_balance_to_withdraw_for_builder(state, index) == 0` before treating an exited, zero-balance slot as reusable. Alternatively, key `BuilderPendingPayment`/`BuilderPendingWithdrawal` by pubkey (or a monotonically-increasing builder generation/uid) instead of by the reusable `builder_index`, so a slot-reuse event cannot cause a stale withdrawal to be misapplied to an unrelated successor builder.

### Proof of Concept
1. Builder `B` at index `i` wins a bid; the payment is queued as `BuilderPendingPayment`/eventually `BuilderPendingWithdrawal(builder_index=i, fee_recipient=X, amount=A)`.
2. Before that withdrawal is drained via `get_builder_withdrawals`, builder `B` submits a `BuilderExitRequest` at a time when `get_pending_balance_to_withdraw_for_builder(state, i)` transiently reports `0` (e.g., the payment is still sitting in `builder_pending_payments` under quorum and hasn't yet become a `builder_pending_withdrawals` entry, so it isn't counted) - `initiate_builder_exit(state, i)` succeeds.
3. Builder `B` is swept to `balance == 0` in a subsequent `process_withdrawals`, satisfying `withdrawable_epoch <= current_epoch and balance == 0`.
4. A new, unrelated builder `C` submits a `BuilderDepositRequest`; `get_index_for_new_builder` returns index `i` and `C` is installed there with a nonzero balance via `add_builder_to_registry` [8](#0-7) .
5. The originally queued payment for `B` reaches `state.builder_pending_withdrawals` with `builder_index=i` and is processed by `get_builder_withdrawals`, decreasing `state.builders[i].balance` (now `C`'s balance) by `min(A, C.balance)` and paying `X` [9](#0-8) .
6. Result: builder `C` loses stake it never pledged for a payment it never made, sent to `fee_recipient` `X` which `C` never authorized.

(Note: the exact interleaving of step 2's timing relative to `get_pending_balance_to_withdraw_for_builder` accounting for both `builder_pending_payments` and `builder_pending_withdrawals` was not fully traced against every fork variant in this session; a background Devin session with full repo/test access should confirm whether `get_pending_balance_to_withdraw_for_builder` covers both queues at all times, which determines whether the exit-time guard alone already closes this gap or whether the slot-reuse check is genuinely missing as described.)

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

###### New `process_builder_deposit_request`

*Note*: Builder indices are reusable. When a builder exits, its index may later
be reassigned to a different builder with a new public key. Any deposit sent to
an exited builder will be withdrawn to the builder’s execution address. Exited
builders cannot be reactivated, although a newly registered builder’s public key
may have previously appeared in the builder set. Implementations that rely on
caching should account for this behavior.

```python
def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount

###### New `process_builder_exit_request`

```python
def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
