### Title
`delete_member` fails to purge stale confirmations from removed members, allowing requests to execute below the live-member confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
This is an analog of the reported bug class (a stale/incorrectly-tracked index or set letting privileged validation diverge from the live authoritative set). In `committee::execute_blocklist`, a stale `member_idx` let matching diverge from the actual current committee order. In `MultiSigContract`, a stale confirmation set lets the vote count diverge from the actual, current set of live members, breaking the binding "confirmations counted == confirmations from live members."

### Finding Description
`confirm` decides whether to execute a request purely by comparing the size of the `confirmations` `HashSet<String>` for that `request_id` against `self.num_confirmations`: [1](#0-0) 

`delete_member` is the only place that removes stale request/confirmation state for a departing member, but it only purges **requests originally added by** that member (`r.member == member`). It never scans other requests' `confirmations` sets to strip out that member's prior confirmation: [2](#0-1) 

So if member `C` confirms a pending request `R` (added by a different member `B`) and is later removed from `self.members` via `DeleteMember`, `R`'s confirmation set still contains `C`. `C`'s vote is not a "confirmation from a live member" anymore, but it is still counted toward `self.num_confirmations` the next time anyone confirms `R`, in `confirm`'s check `confirmations.len() as u32 + 1 >= self.num_confirmations`. This is the direct analog of the Move bug: an index/set that should be reset/purged when the authoritative membership changes is not, and the search/count then diverges from the true current committee.

### Impact Explanation
This lets a request execute with fewer *live* member confirmations than `num_confirmations` requires — i.e., a multisig request executed below threshold, which is explicitly listed as a Critical impact ("a multisig request executed below threshold"). Since `execute_request` can perform `Transfer`, `AddKey`/`AddMember` (granting full access keys), or `FunctionCall`, this can be used to move NEAR held by the multisig account or grant unauthorized access with insufficient live authorization.

### Likelihood Explanation
Requires: (1) a member who confirms a request and is later removed (a realistic operational event — member rotation, compromise response, or a malicious member removed after being caught proposing/confirming a bad request), and (2) that request remaining unconfirmed/pending in `self.requests` until after removal. `add_request`'s `active_requests_limit` (default 12) and lack of any expiry purge for confirmation membership means a stale, still-pending request can sit around across a `DeleteMember` execution. No privileged access beyond being a former (now-removed) member is required to have contributed the stale vote; any current member can complete confirmation to trigger execution while unaware the vote count includes a no-longer-authorized party.

### Recommendation
When executing `DeleteMember`, iterate all pending requests (not just those added by the removed member) and strip the removed member's entry from each request's `confirmations` set, re-checking whether remaining requests still satisfy live-member confirmation counts. Alternatively, validate at `confirm`-time that every entry in the stored `confirmations` set still corresponds to a current member of `self.members` before comparing against `self.num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)` (see `new` at [3](#0-2) ).
2. `B` calls `add_request` with a `Transfer` action to an attacker-controlled account, producing `request_id = R` [4](#0-3) .
3. `A` calls `confirm(R)` → `confirmations = {A}` (1/3, not executed).
4. `C` calls `confirm(R)` → `confirmations = {A, C}` (2/3, not executed) [1](#0-0) .
5. Separately, a `DeleteMember { member: C }` request is confirmed and executed (e.g. because `C` was compromised/misbehaving) via `delete_member`, which removes only requests **added by** `C`, leaving `R`'s confirmations `{A, C}` untouched [2](#0-1) . Live members are now `[A, B, D]`.
6. `D` calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations(3)` → `execute_request` runs the `Transfer`, even though only `A` and `D` are live members who actually authorized it (2 of 3 current members), with `C`'s stale, now-invalid vote making up the count.

    /// Add request for multisig.
    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
