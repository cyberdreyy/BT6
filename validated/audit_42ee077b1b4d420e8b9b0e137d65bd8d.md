### Title
`CommandArgExpand` uses `psDoubleQuote` without escaping `$`, allowing PowerShell subexpression injection via attacker-controlled arguments - (File: shells/powershell.go)

### Summary
`PsWriter.CommandArgExpand` builds command lines by wrapping the command and every argument in PowerShell double quotes via `psDoubleQuote`, which does not escape the `$` character. Because PowerShell expands `$(...)` subexpressions and `$variable` references inside double-quoted strings at parse time, any attacker-controlled argument text containing `$(...)` is executed as PowerShell code before the intended external command even runs.

### Finding Description
`CommandArgExpand` delegates to `buildCommand(psDoubleQuote, command, arguments...)`: [1](#0-0) [2](#0-1) 

`psDoubleQuote` escapes backticks, control characters, `#`, `'`, `"`, and smart quotes, but deliberately does **not** touch `$`: [3](#0-2) 

Compare this to `psQuoteVariable`, which is used elsewhere specifically because it *does* escape `$` (via `` `$ ``) to keep interpolated values literal: [4](#0-3) 

The existence of `psQuoteVariable` alongside `psDoubleQuote` shows the codebase is aware that `$` must be escaped when a value is meant to stay literal inside a double-quoted PowerShell string. `CommandArgExpand`, however, uses the non-`$`-escaping `psDoubleQuote` for every argument it emits (`Command` uses `psSingleQuote`, which is safe, but `CommandArgExpand` intentionally opts into `psDoubleQuote` so that PowerShell environment-variable references embedded in arguments get expanded).

In PowerShell, inside a double-quoted string, both `$variable` and `$(expression)` are evaluated by the parser before the string value is produced — this includes full command invocation via `$(some-command; malicious-command)`. Since `CommandArgExpand`'s arguments come from `psDoubleQuote(argument)` with no `$` escaping, any attacker-controlled argument value containing `$(...)` becomes executable PowerShell code embedded directly in the generated script, run in the runner's shell context (not the sandboxed job command being invoked) at the moment the surrounding `& "cmd" "arg1" "$(evil)"` line is executed.

Attacker-controlled inputs reach `CommandArgExpand` through git operations, custom step/script metadata, and similar runner-generated commands (e.g., ref names, paths, or other values interpolated as arguments in `abstract.go`, which calls `CommandArgExpand` in numerous places for git/helper invocations). If any of these values (refs, branch/tag names, file paths, or job-supplied strings) are attacker-influenced and passed as arguments to `CommandArgExpand`, an attacker who can control that string can smuggle `$( ... )` to achieve command execution in the runner-generated PowerShell script.

### Impact Explanation
This allows an attacker who controls one of these argument values (e.g., a git ref/branch name, a variable name/value, or other job-supplied string reaching `CommandArgExpand`) to inject arbitrary PowerShell code that executes in the runner's script context — the same execution context as the intended external command invocation, which typically runs with higher trust/capability than the job's isolated payload (e.g., helper/setup commands executed before user script isolation, or with access to credentials/temp paths not otherwise exposed to job scripts). This matches the "stronger-context command execution" impact.

### Likelihood Explanation
Exploitability depends on which call sites feed unsanitized, attacker-influenced strings into `CommandArgExpand` (as opposed to constant strings). Given `CommandArgExpand` is called throughout `abstract.go` for git and other command generation with values such as refs, URLs, and paths that can be influenced by pipeline authors (branch names, custom variables, etc.), the precondition (attacker controls a string that flows into one of these arguments) is plausible for an unprivileged pipeline author. The bug is a straightforward missing-escape issue in a shared escaping helper, making it broadly reachable wherever `CommandArgExpand` is used with non-constant arguments.

### Recommendation
Escape `$` (as `` `$ ``) in `psDoubleQuote`, or introduce a dedicated quoting function for `CommandArgExpand`/argument contexts that escapes `$` the same way `psQuoteVariable` does, while preserving whatever specific expansion behavior (if any) is intentionally required for `CommandArgExpand`. Audit all `CommandArgExpand` call sites in `shells/abstract.go` to confirm whether `$` expansion is actually required for any argument (as opposed to only for the command name), and if not, switch those call sites to a strictly literal quoting function.

### Proof of Concept
Go unit test in `shells/powershell_test.go` (or extending `shells/abstract_test.go`):
```go
func TestCommandArgExpand_DollarInjection(t *testing.T) {
    writer := &PsWriter{Shell: SNPwsh, EOL: "\n"}
    writer.CommandArgExpand("git", "checkout", `$(Write-Output PWNED > pwn.txt)`)
    script := writer.String()

    // Assert the malicious argument is NOT emitted as an escaped/literal string,
    // i.e., the `$(` sequence survives unescaped inside the double-quoted argument,
    // proving PowerShell will evaluate it as a subexpression rather than literal text.
    assert.Contains(t, script, `$(Write-Output PWNED > pwn.txt)`)
    assert.NotContains(t, script, "`$(") // if properly escaped, `$` would be backtick-escaped
}
```
Expected result with the current code: the test passes, confirming `$(...)` is emitted unescaped inside the double-quoted argument — proof that a PowerShell interpreter executing this generated script would run `Write-Output PWNED > pwn.txt` as code rather than treating it as literal argument text. After applying the fix (escaping `$`), the assertion `NotContains "` $("` should hold, showing the payload is neutralized.

func psDoubleQuote(text string) string {
	text = psReplaceSpecialChars(text)
	text = strings.ReplaceAll(text, "“", "`“")
	text = strings.ReplaceAll(text, "”", "`”")
	text = strings.ReplaceAll(text, "„", "`„")
	return doubleQuote(text)
}

func (p *PsWriter) buildCommand(quoter stringQuoter, command string, arguments ...string) string {
	list := []string{
		psDoubleQuote(command),
	}

	for _, argument := range arguments {
		list = append(list, quoter(argument))
	}

	return "& " + strings.Join(list, " ")
}
