### Title
Secrets resolution (Vault) ignores job cancellation context, leaking goroutine/HTTP connection on unresponsive attacker-controlled endpoint - ([File: common/secrets.go], [File: common/build.go], [File: helpers/secrets/resolvers/vault/resolver.go], [File: helpers/vault/client.go])

### Summary
`Build.attemptResolveSecrets` and the entire secret-resolution call chain (`executeResolveSecretsStage` → `resolver.Resolve` → vault `resolver.Resolve()` → `service.NewVault`/`GetField` → `vault.Client`) never receive or check a `context.Context`, so job cancellation (`trace.SetCancelFunc`/`AbortFunc`) has no effect on an in-flight secret resolution call. An unprivileged pipeline author who controls a CI variable interpolated into `VaultServer.URL` can point Vault resolution at a host that accepts a TCP connection but never responds, then cancel the job; the goroutine executing that job remains blocked on the HTTP read until the underlying client's own (Vault SDK-default or absent) timeout elapses, not until job cancellation.

### Finding Description
- `Build.resolveSecrets` expands `VaultServer.URL` from job variables via `b.Secrets.ExpandVariables(b.GetAllVariables())` before resolving [1](#0-0) , confirming the URL is attacker-influenceable through ordinary CI variables.
- `Build.attemptResolveSecrets` builds a `retry.New().WithMaxTries(attempts)` runner but never calls `.WithContext(ctx)`, so the retry's internal `ctx` defaults to `context.Background()` [2](#0-1) . In `helpers/retry/retry.go`, `retryRun` only checks `retry.ctx.Done()` between attempts/backoff waits, never during the blocking `fn()` call itself [3](#0-2) ; since `ctx` here is always `Background()`, this check is dead regardless.
- `executeResolveSecretsStage` calls `resolver.Resolve(b.Secrets)` synchronously with no context parameter at all [4](#0-3) .
- The vault-backed `SecretResolver.Resolve()` has signature `Resolve() (string, error)` — no context — and calls `service.NewVault(url, namespace, secret)` then `s.GetField(secret, secret)`, both blocking, non-cancelable calls [5](#0-4) .
- `helpers/vault/service` and `helpers/vault/client.go` construct an `api.Client` from `api.NewClient(&api.Config{Address: apiURL})` with no explicit HTTP timeout override, and perform `Authenticate`, `Read`/`Write` calls with no context threading anywhere in the interfaces (`Client.Read(path string) (Result, error)`, etc.) [6](#0-5) [7](#0-6) .
- Consequently, `trace.SetCancelFunc(cancel)`/`SetAbortFunc(cancel)` [8](#0-7)  cancels the job's outer context, but that cancellation is never observed by the secret-resolution code path — there is no `select { case <-ctx.Done(): }` anywhere between `Build.attemptResolveSecrets` and the raw HTTP call. The only thing that can unblock the goroutine is the transport's own timeout (Vault/OpenBao SDK default, or none if not configured) or eventual connection refusal/reset.
- Existing protections (masking, allowed-image checks, path validation) are irrelevant here; there is no mechanism that stops or bounds this because the missing piece is context propagation/cancellation, not an input validation gap.

### Impact Explanation
For the duration of the unbounded/long HTTP call, the goroutine running that job's `Build.Run` remains alive and blocked in `attemptResolveSecrets`, holding onto the job's execution slot and an open TCP connection, even though the job has already been canceled from the GitLab side. If the Runner's concurrency accounting treats "job canceled" as "slot freed" prematurely while the goroutine is still running (or if job cleanup/executor teardown is gated on this stage completing), a small number of pipeline authors can each launch and cancel similar jobs to accumulate blocked goroutines/connections, degrading throughput for other tenants sharing the same runner/executor pool until the underlying transport eventually times out.

### Likelihood Explanation
Fully attacker-reachable with standard, documented CI features: any pipeline author who can define a `secrets: vault:` block with a variable-sourced URL (a normal, supported configuration) and control `SECRETS_RETRIEVAL_ATTEMPTS` can trigger this. No special privileges are required beyond authoring a `.gitlab-ci.yml` and pointing the Vault URL at attacker-controlled infrastructure (a host/port that accepts but never answers). The bug is deterministic and repeatable — the missing context wiring is structural, not a race condition.

### Recommendation
Thread `context.Context` through the entire secret-resolution path: `Build.attemptResolveSecrets` should call `retry.New().WithContext(ctx)`, and `SecretsResolver.Resolve`, the vault `SecretResolver.Resolve()`, `service.Vault.GetField/Put/Delete`, and `vault.Client.Read/Write/Delete`/`Authenticate` should accept and honor a `context.Context`, using `http.NewRequestWithContext`-based calls under the hood (the Vault/OpenBao API client supports `WithContext`/`SetClientTimeout`). Additionally set an explicit bounded HTTP client timeout on `api.Config` when constructing the Vault client so no call can hang indefinitely even without an active context cancellation path.

### Proof of Concept
Go integration test outline:
1. Start a TCP listener that accepts connections but never writes a response (simulating an unresponsive attacker-controlled "Vault" endpoint).
2. Build a `Build` with `Secrets = spec.Secrets{"S": spec.Secret{Vault: &spec.VaultSecret{Server: spec.VaultServer{URL: listenerAddr}}}}` and `SECRETS_RETRIEVAL_ATTEMPTS=3`.
3. Run `b.Run(ctx, ...)` in a goroutine; record `runtime.NumGoroutine()` baseline before start.
4. After the resolve stage has started (e.g., synchronize via a channel signaled when the TCP listener accepts a connection), cancel `ctx` via the same mechanism `trace.SetCancelFunc` exposes.
5. Assert that `Build.Run` returns (job aborts) within a short bound (e.g., 2s) — this will fail today because the goroutine remains blocked on the read until the Vault client's default/absent timeout expires (potentially far longer, or never, if no timeout is configured).
6. Assert `runtime.NumGoroutine()` and open connection count return to baseline shortly after cancellation — this assertion fails, demonstrating the leak.

```go
func (b *Build) attemptResolveSecrets(trace JobTrace, attempts int) error {
	retryRunner := retry.New().WithMaxTries(attempts)

	if b.IsFeatureFlagOn(featureflags.UseExponentialBackoffStageRetry) {
		backoffConfig := b.getStageRetryBackoffConfig()
		retryRunner = retryRunner.
			WithBackoff(backoffConfig.Min, backoffConfig.Max).
			WithBuildLog(&b.logger)
	}

	return retry.NewNoValue(retryRunner, func() error {
		return b.executeResolveSecretsStage(trace)
	}).Run()
}
```

```go
func (b *Build) executeResolveSecretsStage(trace JobTrace) error {
	b.OnBuildStageStartFn.Call(BuildStageResolveSecrets)
	defer b.OnBuildStageEndFn.Call(BuildStageResolveSecrets)

	section := helpers.BuildSection{
		Name:        string(BuildStageResolveSecrets),
		SkipMetrics: !b.Job.Features.TraceSections,
		Run: func() error {
			logger := b.getNewLogger(trace, b.Log(), false)
			defer logger.Close()

			resolver, err := b.secretsResolver(&logger, GetSecretResolverRegistry(), b.IsFeatureFlagOn)
			if err != nil {
				return fmt.Errorf("creating secrets resolver: %w", err)
			}

			variables, err := resolver.Resolve(b.Secrets)
			if err != nil {
				return fmt.Errorf("resolving secrets: %w", err)
			}

			b.secretsVariables = variables
			b.RefreshAllVariables()

			return nil
		},
	}

	return section.Execute(&b.logger)
}
```

```go
func retryRun[T any](retry *Retry, fn RunValueFunc[T]) (T, error) {
	var err error
	var tries int
	var value T

	select {
	case <-retry.ctx.Done():
		return value, retry.ctx.Err()
	default:
	}

	for {
		tries++

		value, err = fn()
		if err == nil || !retry.check(tries, err) {
			break
		}

		backoffDuration := retry.backoff.Duration()

		select {
		case <-time.After(backoffDuration):
		case <-retry.ctx.Done():
			return value, retry.ctx.Err()
		}
	}

	return value, err
}
```

```go
func (v *resolver) Resolve() (string, error) {
	if !v.IsSupported() {
		return "", secrets.NewResolvingUnsupportedSecretError(resolverName)
	}

	secret := v.secret.Vault

	url := secret.Server.URL
	namespace := secret.Server.Namespace

	s, err := newVaultService(url, namespace, secret)
	if err != nil {
		return "", classifyError(err)
	}

	data, err := s.GetField(secret, secret)
	if err != nil {
		return "", classifyError(err)
	}

	if data == nil {
		return "", common.ErrSecretNotFound
	}

	return fmt.Sprintf("%v", data), nil
}
```
