### Title
Precision loss from premature division in migration-epoch stake reward calculation - (File: `runtime/src/inflation_rewards/mod.rs`)

### Summary
During the Tower→Alpenglow migration epoch, `calculate_stake_rewards()` computes a staker's tower-portion of inflation rewards using two sequential multiply-then-divide steps instead of combining all multiplications before dividing. This mirrors the reported FeeCollector bug class (division before multiplication), causing unnecessary rounding-down of stake rewards that are ultimately minted to stakers.

### Finding Description
In the `AlpenglowEpochType::MigrationEpoch` branch of `calculate_stake_rewards`, the tower-portion reward is computed as:

```rust
let total_slots = (num_tower_slots + num_ag_slots) as u128;
let tower_points = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points)
    .unwrap()
    .checked_mul(*num_tower_slots as u128)
    .unwrap()
    .checked_div(total_slots)
    .unwrap();
tower_points + ag_points
``` [1](#0-0) 

This is mathematically `((tower_points * rewards) / points) * num_tower_slots / total_slots`, which truncates twice (once dividing by `points`, once dividing by `total_slots`). The precision-preserving form would combine both multiplications before either division: `tower_points * rewards * num_tower_slots / (points * total_slots)`. Because integer division truncates the fractional remainder at each step, performing the division in two separate stages discards more of the true fractional value than a single combined division would, exactly the "weight" pattern flagged in the external report (`weight = a*BASIS/total`, then reapplied with another multiply/divide).

This computation feeds directly into `rewards` used to derive `staker_rewards`/`voter_rewards` via `commission_split`/`commission_split_preserve_lamports`, which are minted into stake and vote accounts during epoch reward distribution: [2](#0-1) 

### Impact Explanation
The migration epoch is a one-time, network-wide event that computes stake rewards for every delegated stake account active during the Tower→Alpenglow migration. The double-truncation causes stakers to receive systematically fewer lamports than the mathematically exact split would produce. While individual per-account losses are at most a few lamports (bounded by two roundings instead of one), this affects reward accounting correctness for the entire active stake set during migration, and the "lost" lamports are not tracked/re-distributed (unlike bugs that explicitly account for burned dust), so this results in real, avoidable stake reward underpayment cluster-wide during migration.

### Likelihood Explanation
This code path executes unconditionally for every stake delegation whose vote account transitions through the Tower→Alpenglow migration epoch — it requires no attacker action beyond normal, permissionless staking (delegating a stake account, which any user can do via a standard transaction). It is guaranteed to run once per migration for all active delegations, so likelihood of the precision loss occurring is effectively certain for any network performing the Alpenglow migration; only the magnitude per account is small.

### Recommendation
Reorder the arithmetic so both multiplications happen before either division, using u128 (or higher precision) to avoid overflow:

```rust
let numerator = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .and_then(|v| v.checked_mul(*num_tower_slots as u128))
    .expect("Rewards intermediate calculation should fit within u128");
let denominator = point_value.points
    .checked_mul(total_slots)
    .expect("denominator should fit within u128");
let tower_points = numerator.checked_div(denominator).unwrap();
```
This performs a single truncation instead of two, minimizing rounding loss consistent with how `commission_split`/`commission_split_preserve_lamports` already multiply-before-dividing elsewhere in the same file.

### Proof of Concept
Given `tower_points = T`, `point_value.rewards = R`, `point_value.points = P`, `num_tower_slots = N`, `total_slots = S`:

- Current (buggy) order: `floor(floor(T*R/P) * N / S)`
- Correct order: `floor(T*R*N / (P*S))`

Example: `T=7, R=1_000_000_000, P=3, N=1, S=3`
- Current: `floor(7_000_000_000/3) = 2_333_333_333`; `floor(2_333_333_333*1/3) = 777_777_777`
- Correct: `floor(7_000_000_000 / 9) = 777_777_778`

The current implementation underpays by 1 lamport in this example; the discrepancy grows with less favorable divisor alignments across the full range of `T, R, P, N, S` values seen during a real migration epoch across many stake accounts, each losing lamports that are never re-credited. [3](#0-2)
