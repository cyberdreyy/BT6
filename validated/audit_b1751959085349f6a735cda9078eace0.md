### Title
`claimInstantWithdrawRequest` never decrements per-epoch instant-receipt counters, corrupting default-recovery accounting — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Like CVE-2017-18221 (paired `mlock`/`munlock` operations corrupt the `NR_MLOCK` accounting counter), `IdleCreditVault` keeps three paired counters for instant withdraws — `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, and `instantWithdrawClaimsByEpoch` — but the successful funded-claim path only clears the first. The stale per-epoch basis is later consumed by `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest`, inflating the recovery denominator with phantom claims and permanently locking the corresponding slice of `defaultRecoveryReserve`.

### Finding Description
`requestInstantWithdraw` records `_amount` in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]`, plus `pendingInstantWithdraws` [1](#0-0) . `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` as the CDO fronts liquidity [2](#0-1) . The user-facing `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and pays out, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` [3](#0-2) .

Those per-epoch counters are live state at default finalization: `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery denominator whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` using the same inflated number [5](#0-4) . Post-finalization, `_claimDefaultedInstantWithdrawRequest` re-reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and executes `instantWithdrawsRequests[_user] -= claimBasis`, which underflows to a revert for any user whose receipts were already claimed [6](#0-5) .

### Impact Explanation
Sequence: during a buffer epoch, two users (KYC'd lenders holding strategy-token receipts — in-scope attackers) open instant withdrawals; the CDO prefunds and the first user claims successfully. `pendingInstantWithdraws` remains non-zero (the second request is unfunded) and `instantWithdrawClaimsByEpoch[epoch]` still contains both requests. The borrower then defaults in that same epoch and `finalizeDefaultRecovery` runs. The inflated `totalBasis` lowers `defaultRecoveryPrice` for every claimant — active AA/BB holders (whose NAV is re-denominated by the same `recoveryPrice` at [7](#0-6) ) and normal pending redeemers alike. The reserve share attributed to the phantom basis is permanently unclaimable: the only code path that would release it, `_claimDefaultedInstantWithdrawRequest`, reverts on the `instantWithdrawsRequests[_user] -= claimBasis` underflow because the real balance is zero. Net effect: every legitimate recovery claimant is diluted and a quantified slice (`phantomBasis / totalBasis`) of the recovery reserve is frozen forever — a direct fund-loss invariant break, not a mere DoS.

### Likelihood Explanation
Requires a borrower default in an epoch where instant withdrawals were partially prefunded and at least one was claimed — the exact partially-prefunded scenario the code explicitly handles (`_defaultPrefundedInstantReserve`, `defaultInstantWithdrawsFinalized`). No privileged misbehavior is needed; the attacker is an ordinary instant-withdraw requester whose normal claim leaves the stale basis. Recovery dilution is proportional to the claimed instant amount, so a large instant withdraw maximizes impact.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records alongside the aggregate: subtract `amount` (or the exact per-epoch entries) from `instantWithdrawClaimsByEpoch[requestEpoch]` and zero `instantWithdrawsRequestsByEpoch[_user][requestEpoch]`. Since a user's aggregate receipt can span epochs, either track a per-user FIFO of request epochs or disallow new instant requests while an unfinalized receipt exists, mirroring the `lastWithdrawRequest` guard used for normal withdraws [8](#0-7) .

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
