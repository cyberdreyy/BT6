## Title
Operator-triggered pending_inactive→inactive settlement in `join_validator_set_internal` desyncs `delegation_pool` accounting and can permanently strand delegator unlocked stake — (File: `aptos-move/framework/aptos-framework/sources/stake.move`)

## Summary
`stake::join_validator_set_internal` contains custom logic (not present in the pattern used elsewhere in the module for epoch-driven settlement) that, for an INACTIVE validator whose lockup has already expired, silently merges the entire `pending_inactive` coin balance into `inactive` at the moment the operator calls `join_validator_set`/`join_validator_set_internal` — completely outside of `delegation_pool`'s `synchronize_delegation_pool`/OLC (observed lockup cycle) bookkeeping path. [1](#0-0) 

## Finding Description
`delegation_pool.move`'s accounting model is built entirely around the invariant that `pending_inactive → inactive` transitions on the underlying `StakePool` are only ever observed and processed through `synchronize_delegation_pool` (via `calculate_stake_pool_drift`), which is required to run before *every* stake-management operation, and which is the sole mechanism responsible for detecting a "lockup cycle end" and advancing the `ObservedLockupCycle` (OLC) — isolating the old `pending_inactive` shares pool so delegators can withdraw from it: [2](#0-1) 

However, `join_validator_set_internal` in `stake.move` independently mutates the `StakePool`'s coin balances — merging `pending_inactive` into `inactive` — whenever an inactive validator (re)joins the validator set and its lockup has expired: [3](#0-2) 

This function is reachable by calling `stake::join_validator_set(operator, pool_address)`, which requires only that the caller be the current `operator_address` of the stake pool — it does **not** require the `OwnerCapability`, and it does **not** call into `delegation_pool::synchronize_delegation_pool` at all: [4](#0-3) 

For a `delegation_pool`-backed validator, the operator is a distinct, often externally-controlled account (set via `delegation_pool::set_operator`/`stake::set_operator`), separate from the resource-account signer that holds the `OwnerCapability`. The operator is therefore able to unilaterally trigger this pending_inactive-to-inactive settlement by leaving and rejoining the validator set (or simply calling `join_validator_set` again after having previously left while inactive with an expired lockup), without the delegation pool ever calling `synchronize_delegation_pool` to observe the transition.

Because the OLC-advance logic in `delegation_pool` only lives inside `calculate_stake_pool_drift`/`synchronize_delegation_pool` (triggered from delegator-facing entrypoints like `unlock`, `reactivate_stake`, `withdraw`, `set_operator`, etc.), a `pending_inactive → inactive` transition that happens via `join_validator_set_internal` is not reflected in `pool.observed_lockup_cycle`, `pool.total_coins_inactive`, or the per-OLC `inactive_shares` `pool_u64`. The stake pool's `inactive` balance is now higher than what `delegation_pool.total_coins_inactive` reflects, and the delegators' pending_inactive shares still point at a shares-pool for an OLC whose real backing coins have already left `pending_inactive` on the `StakePool`. When `synchronize_delegation_pool` is eventually invoked, `calculate_stake_pool_drift` computes rewards/commission by diffing current vs. last-known `active`/`pending_inactive` amounts read from `stake::get_stake`; an out-of-band drop in `pending_inactive` (to zero, from the merge) that was not driven by an actual OLC-ending epoch transition corrupts this drift computation, either mis-attributing the moved stake as slashing/loss (delegators lose accounted stake) or as leftover-inactive coins that never get properly captured into `total_coins_inactive` at the correct OLC boundary — leaving delegators unable to correctly withdraw their entitled inactive stake, since `withdraw_internal`'s excess-stake accounting also depends on `stake::get_stake`'s `pending_inactive` at the time.

## Impact Explanation
This corrupts accounting across `active`/`pending_active`/`pending_inactive`/`inactive` state for a `delegation_pool`, potentially stranding or misattributing delegator unlocked stake without delegator or admin consent — a direct violation of the "Accounting across active, pending_active, pending_inactive, inactive, rewards, and commission state must preserve value and withdrawal rights" pivot. The trigger requires only operator-role access (no owner privilege, no delegator privilege beyond the existing operator relationship), and operators are not trusted with delegator funds beyond commission — this lets an untrusted/malicious operator desynchronize the pool's internal ledger from the real `StakePool` balances, causing wrong-amount withdrawals or permanently-stuck delegator inactive stake. This is a High-severity accounting/lockup-invariant violation.

## Likelihood Explanation
Reaching this requires: (1) the validator becoming `INACTIVE` (e.g., voluntarily leaving the validator set, dropping below minimum stake, or being kicked for low performance) while it still has `pending_inactive` stake and an expired lockup, and (2) the operator calling `join_validator_set` again. Both conditions are plausible in normal delegation-pool operator lifecycle (leave/rejoin is a common maintenance operation) and require no elevated privilege beyond the operator role, which is not assumed to be trusted with delegator fund-safety invariants. I was not able to fully trace the exact numeric corruption through `calculate_stake_pool_drift`'s drift-detection arithmetic within the available exploration budget — this is the main verification gap.

## Recommendation
- Do not perform ad hoc `pending_inactive → inactive` coin merges inside `join_validator_set_internal`. Instead, route any such settlement through the same code path used by `update_stake_pool`/reconfiguration so all consumers (including `delegation_pool::calculate_stake_pool_drift`) observe the transition consistently.
- Alternatively, require `delegation_pool::synchronize_delegation_pool` (or an equivalent generic hook) to be invoked before/after this settlement whenever the stake pool is delegation-pool-owned, or expose an explicit event/callback so dependent modules can keep their OLC and `total_coins_inactive` bookkeeping in sync.
- Add invariant checks/tests ensuring that after any operator-triggered `join_validator_set` cycle, `delegation_pool`'s `total_coins_inactive` plus all `inactive_shares` pools accurately reconcile against `stake::get_stake`'s reported `inactive` balance.

## Proof of Concept
Conceptual reproduction (not executed, given tool constraints):
1. Operator runs a validator backed by a `delegation_pool`; delegator calls `unlock` moving stake to `pending_inactive`. [5](#0-4) 
2. Validator becomes `INACTIVE` (e.g., operator calls `stake::leave_validator_set`) while `pending_inactive > 0`.
3. Time passes until `stake_pool.locked_until_secs` has elapsed (lockup expired) but `synchronize_delegation_pool` is not called by any delegator action in the meantime.
4. Operator calls `stake::join_validator_set(operator, pool_address)` directly.
5. Inside `join_validator_set_internal`, since `locked_until_secs > 0` and `now >= locked_until_secs`, the entire `pending_inactive` balance is merged into `inactive` on the `StakePool`: [6](#0-5) 
6. `delegation_pool.total_coins_inactive`, `observed_lockup_cycle`, and the per-OLC `inactive_shares` pool are never updated by this call (no `synchronize_delegation_pool` invocation occurs in this path), producing a divergence between the delegation pool's internal ledger and the actual `StakePool` state that surfaces as incorrect rewards/commission or stuck withdrawals the next time synchronization runs.

I was unable to fully execute this scenario against Move test infrastructure to confirm the exact numeric outcome (stranded vs. mis-credited amount) within the available tool budget; a Devin session with test execution capability would be needed to build a concrete `#[test]` reproducing the exact corrupted balance.

```text
Accounting main invariants:
 - each stake-management operation (add/unlock/reactivate/withdraw) and operator change triggers
the synchronization process before executing its own function.
 - each OLC maps to one or more real lockups on the stake pool, but not the opposite. Actually, only a real
lockup with 'activity' (which inactivated some unlocking stake) triggers the creation of a new OLC.
 - unlocking and/or unlocked stake originating from different real lockups are never mixed together into
the same pool_u64. This invalidates the accounting of which rewards belong to whom.
 - no delegator can have unlocking and/or unlocked stake (pending withdrawals) in different OLCs. This ensures
delegators do not have to keep track of the OLCs when they unlocked. When creating a new pending withdrawal,
the existing one is executed (withdrawn) if is already inactive.
 - <code>add_stake</code> fees are always refunded, but only after the epoch when they have been charged ends.
 - withdrawing pending_inactive stake (when validator had gone inactive before its lockup expired)
does not inactivate any stake additional to the requested one to ensure OLC would not advance indefinitely.
 - the pending withdrawal exists at an OLC iff delegator owns some shares within the shares pool of that OLC.
```
