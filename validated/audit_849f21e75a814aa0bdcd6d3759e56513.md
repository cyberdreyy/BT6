### Title
Post-default instant withdraw requests are recorded and paid from the default-recovery/funded reserve without a post-default branch - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The curl CVE leaks credentials across a context switch (redirect to a different proxy scheme): state valid in one context is silently honored in another. The same defect exists in `IdleCreditVault.requestInstantWithdraw`. Unlike `requestWithdraw` — which has an explicit `defaultRecoveryFinalized` branch that burns the CDO's tokens, mints a haircut-priced receipt, and tracks it in `postDefaultRequests` without touching borrower-facing debt buckets — `requestInstantWithdraw` has no post-default handling at all, even though it calls `_ensureDefaultRecoveryInitialized()` (proving post-default entry was anticipated). A post-default instant request is minted 1:1, added to `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws`, none of which will ever be funded by a `stopEpoch`/`collectInstantWithdrawFunds` because the pool is defaulted. The receipt is then redeemed through the default-epoch instant claim path, paying `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of `defaultRecoveryReserve`, diluting the reserve that belongs to legitimate defaulted-epoch claimants.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` (lines 247–258) short-circuits when `defaultRecoveryFinalized` is true: it reverts if the user has any open receipt, mints a post-haircut receipt into `postDefaultRequests`, and deliberately does not increment `pendingWithdraws`.
- `requestInstantWithdraw` (lines 356–375) has no equivalent branch. Post-finalization it still executes `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount`, `instantWithdrawClaimsByEpoch[epochNumber] += _amount` and `pendingInstantWithdraws += _amount`.

Because `epochNumber` no longer advances after default, the new request lands in `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the same bucket as real defaulted receipts. When `claimInstantWithdrawRequest` runs (lines 380–393), `_claimDefaultedInstantWithdrawRequest` (lines 842–856) pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the recovery reserve for *any* balance recorded in that epoch bucket, including receipts created after finalization that were never part of the finalized claim basis.

Two broken invariants follow:

1. Recovery-reserve conservation: `finalizeDefault` sizes `defaultRecoveryReserve` for the claims that existed at finalization (`instantWithdrawClaimsByEpoch[defaultEpoch]` is decremented on each claim, but the reserve itself is finite). Every post-default instant request creates a brand-new claim against the same reserve at the recovery price while the requester only burned post-haircut-priced CDO strategy tokens — net extraction of reserve assets that legitimate pending claimants were promised.
2. `pendingInstantWithdraws` corruption: post-default requests inflate the "unfunded remainder" counter that `_claimDefaultedInstantWithdrawRequest` relies on (`pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis`), breaking the funded/unfunded split used for prefunded-reserve accounting.

The guards present do not stop this: `_onlyIdleCDO` is satisfied, `_ensureDefaultRecoveryInitialized` passes, there is no `_hasWithdrawRequest`-style revert, and nothing in the instant path checks `defaultRecoveryFinalized`.

### Impact Explanation
Any tranche-token holder (or apr0/receipt holder that can route through `IdleCDOEpochVariant.requestInstantWithdraw`) can, after default finalization, request an instant withdraw and immediately claim `amount * defaultRecoveryPrice / RECOVERY_FULL` underlying from `defaultRecoveryReserve`. The reserve is sized for pre-existing claims, so each such claim is a direct transfer of other users' recovery proceeds to the attacker. Loss is bounded by the reserve balance; repeatability is limited only by the attacker's tranche balance, and the post-haircut receipt purchase price means the payout exceeds the attacker's cost basis whenever `defaultRecoveryPrice` applied to an unhaircutted fresh receipt exceeds the post-default tranche value burned. The same sequence also permanently desynchronizes `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch`, freezing residual recovery accounting.

### Likelihood Explanation
Reachability requires that `IdleCDOEpochVariant` still routes `requestInstantWithdraw` to the strategy after default; the strategy itself explicitly anticipates post-default calls via `_ensureDefaultRecoveryInitialized()` and mirrors `requestWithdraw`, which is deliberately callable post-finalization (`postDefaultRequests` flow). Preconditions: the pool must reach `defaultRecoveryFinalized` with a non-empty `defaultRecoveryReserve` and `defaultInstantWithdrawsFinalized` set — a supported, tested state. If the CDO layer reverts instant requests while defaulted, the bug degrades to accounting corruption only when the reserve path is reached through the epoch bucket collision; residual uncertainty on CDO-side gating is noted since that file's guard logic was not fully traced.

### Recommendation
Add the same post-default short-circuit to `requestInstantWithdraw` that `requestWithdraw` has: when `defaultRecoveryFinalized` is true, either revert `NotAllowed` or route the amount through a `postDefaultRequests`-style bucket paid from the reserve without touching `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`, `instantWithdrawClaimsByEpoch`, or `pendingInstantWithdraws`. Alternatively, snapshot defaulted-epoch claims at finalization and require `epochNumber` to advance before new instant receipts can be recorded.

### Proof of Concept
Foundry fork test (place in `test/foundry/IdleCreditVault.t.sol` harness, reusing `_depositWithUser`, `_startEpochAndCheckPrices`, `_checkDefault`):

```solidity
function testPostDefaultInstantWithdrawDrainsRecoveryReserve() external {
    address victim  = makeAddr('victim');
    address attacker = makeAddr('attacker');
    uint256 amount = 10_000 * ONE_SCALE;

    // victim creates a pre-default instant withdraw request (funded-epoch receipt)
    _depositWithUser(victim, amount, true);
    _depositWithUser(attacker, amount, true);

    _startEpochAndCheckPrices(0);
    // epoch ends with borrower default
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // manager finalizes default with partial recovery
    uint256 recovered = cdoEpoch.getContractValue() * 7e17 / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();
    assertTrue(IdleCreditVault(address(strategy)).defaultRecoveryFinalized());

    uint256 reservePre = IdleCreditVault(address(strategy)).defaultRecoveryReserve();

    // attacker requests an INSTANT withdraw AFTER finalization
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(IERC20(AAtranche).balanceOf(attacker) / 2, address(AAtranche));

    // receipt lands in defaultRecoveryEpoch bucket and is paid from the reserve
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    uint256 paid = underlying.balanceOf(attacker) - balPre;
    assertGt(paid, 0, 'post-default instant receipt paid from recovery reserve');
    assertLt(
        IdleCreditVault(address(strategy)).defaultRecoveryReserve(),
        reservePre - paid + 1,
        'reserve was not sized for this claim'
    );
}
```

Expected: `requestInstantWithdraw` succeeds post-finalization (no guard), and `claimInstantWithdrawRequest` pays out underlying drawn from `defaultRecoveryReserve`, reducing funds available to legitimate defaulted-epoch claimants — the strategy-token "credential" minted in the post-default context is honored by the default-epoch claim path, mirroring the cross-proxy credential forward.
