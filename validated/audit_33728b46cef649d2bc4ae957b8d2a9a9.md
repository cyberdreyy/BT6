### Title
Unbounded CPU/memory cost decoding and JSON-serializing a maximal-size Address Lookup Table account via `getAccountInfo`/`getProgramAccounts` (`jsonParsed`) - ([File: account-decoder/src/parse_address_lookup_table.rs])

### Summary
`parse_address_lookup_table` and its `UiLookupTable::from` conversion iterate over every address in an ALT account and convert each 32-byte `Pubkey` into a base58 `String` with no size cap, unlike the binary/base58 encoding path which is explicitly bounded by `MAX_BASE58_BYTES`. Because `jsonParsed` encoding bypasses that size check entirely, an attacker who funds a maximal-size (~10 MiB) account owned by the Address Lookup Table program can force any single `getAccountInfo`/`getMultipleAccounts` (`encoding: jsonParsed`) call against that account to allocate and stringify roughly 327,680 pubkeys and produce an oversized JSON response.

### Finding Description
In `rpc/src/rpc.rs`, `encode_account` only enforces the `MAX_BASE58_BYTES` (128-byte) length check for `UiAccountEncoding::Binary` and `UiAccountEncoding::Base58`: [1](#0-0) 

For `UiAccountEncoding::JsonParsed`, `encode_ui_account` (in `account-decoder/src/lib.rs`) instead calls `parse_account_data_v3` directly with no size guard: [2](#0-1) 

When the account owner is the Address Lookup Table program, this reaches `parse_address_lookup_table`, which deserializes the full account and converts it via `UiLookupTable::from`, mapping every address entry to a `to_string()` (base58) call and collecting into a `Vec<String>`: [3](#0-2) 

An attacker only needs to create an ALT account and extend it (paying transaction fees over multiple `extend_lookup_table` calls, a normal unprivileged on-chain operation) up to the network's maximum account size (10 MiB, enforced elsewhere as `MAX_PERMITTED_DATA_LENGTH`), filled with valid pubkey entries. Any subsequent single `getAccountInfo(pubkey, {encoding: "jsonParsed"})` call — issued once by any client, satisfying the "one call per slot" constraint — forces the RPC node to: (1) deserialize ~327k pubkeys from the raw bytes, (2) base58-encode each one into an owned `String`, and (3) serde-serialize the resulting `UiLookupTable` (with `addresses: Vec<String>`) into the JSON-RPC response. None of the size guards that exist for the raw base58/binary encoding path (`MAX_BASE58_BYTES`) apply to this jsonParsed decode-and-stringify path, so the cost of a single request scales with attacker-controlled account size rather than any explicit bound.

### Impact Explanation
A single unprivileged, fee-paying account write (attacker funds and extends one ALT account to max size) turns every future `jsonParsed` `getAccountInfo`/`getMultipleAccounts` call against that account into a large, unbounded CPU/allocation/JSON-serialization spike on the RPC node, and produces an oversized response for every client that fetches it. This matches the "unbounded cost for a single low-rate call" RPC DoS bounty category since only one call per account fetch is required and no additional privilege, multiple clients, or unfiltered `getProgramAccounts` scan is needed.

### Likelihood Explanation
Fully feasible with only unprivileged funds and standard `extend_lookup_table` instructions (no special permissions, no leader/validator control, no config change). The exploit is deterministic and repeatable: once the account exists at max size, every jsonParsed fetch of it reproduces the cost.

### Recommendation
Apply an explicit bound on the number of addresses (or serialized data size) processed by `parse_address_lookup_table`/`UiLookupTable::from`, analogous to `MAX_BASE58_BYTES` for binary encoding — e.g., cap the number of addresses converted/returned, or fall back to raw/base64 encoding when the ALT account exceeds a safe size threshold, mirroring the existing fallback behavior in `encode_ui_account`'s `JsonParsed` branch on parse failure.

### Proof of Concept
Rust unit test in `account-decoder/src/parse_address_lookup_table.rs` (or a new bench):
```rust
#[test]
fn test_parse_address_lookup_table_max_size_unbounded_cost() {
    use std::time::Instant;
    // Build ~10 MiB of valid ALT data: header + ~327,608 pubkeys
    let num_addresses = (10 * 1024 * 1024 - LOOKUP_TABLE_META_SIZE) / std::mem::size_of::<Pubkey>();
    let mut addresses = Vec::with_capacity(num_addresses);
    addresses.resize_with(num_addresses, Pubkey::new_unique);
    let lookup_table = AddressLookupTable {
        meta: LookupTableMeta::default(),
        addresses: std::borrow::Cow::Owned(addresses),
    };
    let data = AddressLookupTable::serialize_for_tests(lookup_table).unwrap();

    let start = Instant::now();
    let result = parse_address_lookup_table(&data).unwrap();
    let elapsed = start.elapsed();

    if let LookupTableAccountType::LookupTable(ui) = result {
        assert_eq!(ui.addresses.len(), num_addresses);
        // Also measure serde_json::to_string cost/size
        let json = serde_json::to_string(&ui).unwrap();
        assert!(json.len() > 10_000_000); // oversized response
    }
    // Expected: no size cap triggers, elapsed time/memory scale with num_addresses,
    // demonstrating unbounded cost for a single decode/serialize call.
    println!("decode+convert took {:?}", elapsed);
}
```

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
