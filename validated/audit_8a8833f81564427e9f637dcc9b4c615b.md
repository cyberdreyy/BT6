### Title
Stale cached `global_fee_wallet` in `MarginfiGroup.fee_state_cache` allows account-transfer fees and closed-account rent to be redirected to a rotated-out fee wallet - (File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs, programs/marginfi/src/instructions/marginfi_account/admin_close.rs)

### Summary
Analogous to the PhiNFT1155 issue where each NFT contract permanently cached `protocolFeeDestination` at `initialize()` and never re-synced with `PhiFactory`, marginfi's `MarginfiGroup` caches the program's `global_fee_wallet` in `fee_state_cache.global_fee_wallet`. This cache is only refreshed by the permissionless `propagate_fee` instruction and is not automatically kept in sync with the canonical `FeeState` account. Several instructions validate against this stale group-level cache instead of the live `FeeState` account, so after the global fee admin rotates `global_fee_wallet` (e.g. because the old wallet was compromised), any group whose cache has not yet been refreshed will keep sending fees/lamports to the old wallet.

### Finding Description
`FeeState.global_fee_wallet` is the canonical, admin-controlled fee destination, updatable via `edit_fee_state`: [1](#0-0) 

Each `MarginfiGroup` stores a local `FeeStateCache` copy of this wallet: [2](#0-1) 

This cache is only updated by the explicit, permissionless `propagate_fee` instruction — it is not refreshed automatically whenever `FeeState` changes or whenever the group is touched: [3](#0-2) 

Some instructions correctly re-validate against the *live* `FeeState` account via `has_one = global_fee_wallet` (e.g. `end_liquidation`, `LendingPoolCollectBankFees`'s ATA check, `PlaceOrder`): [4](#0-3) 

However, `TransferToNewAccount`, `TransferToNewAccountPda`, and `AdminCloseAccount` instead validate the destination against the group's **stale cache**, `group.fee_state_cache.global_fee_wallet`, rather than the canonical `FeeState`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `global_fee_wallet` in these three account structs is an `UncheckedAccount` whose only validation is equality with the cached (possibly stale) value, any caller (these ixs are permissionless/user-driven, requiring no special signer over the fee-wallet account) can supply the *old* wallet address as long as the group's cache has not yet been refreshed via `propagate_fee`, and the transfer/close will succeed, sending funds to the old address.

This mirrors the PhiNFT1155 root cause precisely: a per-instance/per-group cached copy of a mutable, factory/global-admin-controlled destination address is never automatically re-fetched, so after rotation, some code paths keep paying the old, potentially compromised destination.

### Impact Explanation
If the global fee admin rotates `global_fee_wallet` (a realistic operational action, e.g. because the current wallet key is compromised or being retired), any `MarginfiGroup` that has not had `propagate_fee` re-run against it will continue to:
1. Send the `ACCOUNT_TRANSFER_FEE` SOL fee to the old wallet on every `transfer_to_new_account` / `transfer_to_new_account_pda` call.
2. Close eligible, empty/inactive `MarginfiAccount`s via `admin_close_account` with `close = global_fee_wallet`, sending the account's rent-exempt lamports to the old wallet — this is a permissionless instruction, so any caller (not just an admin) can trigger this fund flow to the stale/compromised address.

If the old wallet address is compromised or malicious, this results in continued value redirection to an address the protocol explicitly intended to stop using. It also means the protocol cannot atomically/instantly cut off a compromised fee wallet across all groups — the exposure window is bounded only by how promptly `propagate_fee` is called for every existing group (an unbounded, permissionless, but not automatically triggered, action). This is a genuine, concrete value-redirection bug with financial effect, matching the External Report's root cause and impact class.

### Likelihood Explanation
Low-to-moderate likelihood, consistent with the original finding being rated Medium: it requires the global fee admin to actually rotate `global_fee_wallet` (an infrequent, deliberate admin action), and for at least one group's cache to remain unpropagated at that time — which is the normal/default state immediately after any rotation, since propagation must be manually triggered per group. Given marginfi can have many groups, ensuring `propagate_fee` is called for every single one before an old wallet is fully deprecated is operationally easy to miss, especially under the urgency of an incident-driven rotation (the very scenario where this bug matters most).

### Recommendation
Do not rely on the group-cached `fee_state_cache.global_fee_wallet` for authorizing/validating fund transfers. Instead, validate `global_fee_wallet` directly against the live `FeeState` PDA (using `has_one = global_fee_wallet` on the `fee_state` account, as already correctly done in `EndLiquidation` and `LendingPoolCollectBankFees`) in `TransferToNewAccount`, `TransferToNewAccountPda`, and `AdminCloseAccount`. If the group cache must be retained for other (non-financial) purposes (e.g. interest-rate fee display), keep it, but never use it as the source of truth for where money is actually sent.

### Proof of Concept
1. Global fee admin calls `edit_global_fee_state` with `fee_wallet = NEW_WALLET` to rotate away from `OLD_WALLET` (e.g., because `OLD_WALLET` was compromised): [1](#0-0) 
2. `propagate_fee` has not yet been called for `GROUP_X`, so `GROUP_X.fee_state_cache.global_fee_wallet` still equals `OLD_WALLET`: [3](#0-2) 
3. Any user with an account in `GROUP_X` calls `transfer_to_new_account_pda`, passing `global_fee_wallet = OLD_WALLET`. The check `ctx.accounts.global_fee_wallet.key() == group.fee_state_cache.global_fee_wallet` passes (both are `OLD_WALLET`), and `ACCOUNT_TRANSFER_FEE` is transferred to `OLD_WALLET` instead of `NEW_WALLET`: [6](#0-5) 
4. Similarly, anyone can call the permissionless `admin_close_account` on an eligible empty/inactive account in `GROUP_X`, passing `global_fee_wallet = OLD_WALLET`; the `constraint` passes against the stale cache and the account's rent lamports are sent to `OLD_WALLET` via `close = global_fee_wallet`: [7](#0-6)

```rust
pub fn propagate_fee(ctx: Context<PropagateFee>) -> Result<()> {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let fee_state = ctx.accounts.fee_state.load()?;

    group.fee_state_cache.global_fee_wallet = fee_state.global_fee_wallet;
    group.fee_state_cache.program_fee_fixed = fee_state.program_fee_fixed;
    group.fee_state_cache.program_fee_rate = fee_state.program_fee_rate;

    let clock = Clock::get()?;
    group.fee_state_cache.last_update = clock.unix_timestamp;

    group
        .panic_state_cache
        .update_from_panic_state(&fee_state.panic_state, clock.unix_timestamp);
```
