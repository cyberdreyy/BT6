### Title
Unfunded instant-withdraw receipts can steal funded withdrawal claims held in the vault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The MariaDB UAF (`Item_args::walk_arg` using a stale argument after the underlying item was freed) maps to stale/freed accounting in the vault: `claimInstantWithdrawRequest` pays a receipt that was never funded, spending underlying that is accounted to *other* receipts. Instant withdraw receipts are minted and claimable immediately, but their backing is only delivered later via `collectInstantWithdrawFunds` during `startEpoch`. Because the claim path never verifies funding and `_transferFundedClaim` only protects `defaultRecoveryReserve`, an unfunded instant claim spends fungible vault balance that belongs to already-funded normal/APR0 withdraw receipts.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw` (lines 356-375), the CDO burns `_amount` strategy tokens, mints a 1:1 receipt to the user, increments `instantWithdrawsRequests[_user]`, and increments `pendingInstantWithdraws`. The actual underlying for these receipts arrives later: `collectInstantWithdrawFunds` (lines 398-403) is only called by the CDO during `startEpoch`, decrementing `pendingInstantWithdraws` and pulling tokens from the CDO.

`claimInstantWithdrawRequest` (lines 380-393) contains no funding check and no epoch gating:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` (lines 897-907) reverts only if spending would dip into `defaultRecoveryReserve`; all other vault balance — including underlying delivered by `collectWithdrawFunds` (lines 411-430) at `stopEpoch` to back `withdrawsRequests`/`apr0Users.settledPrincipal` claims — is spendable.

Attacker sequence (running → stopped phase, fixed-APR mode with `allowInstantWithdraw` enabled):
1. During a running epoch the borrower APR drops so `lastEpochApr > unscaledApr + instantWithdrawAprDelta`. Attacker (KYC'd tranche holder) calls `IdleCDOEpochVariant.requestWithdraw`, which routes to `requestInstantWithdraw`, minting an instant receipt. `pendingInstantWithdraws` increases; no funds move.
2. Epoch ends; `stopEpoch` calls `collectWithdrawFunds`, transferring underlying for honest users' funded normal receipts into the vault.
3. Attacker calls `claimInstantWithdrawRequest` before `startEpoch` funds the instant queue. `_transferFundedClaim` pays the attacker out of the honest users' funded receipts.
4. Honest users' `claimWithdrawRequest` now reverts on `safeTransfer` (insufficient balance) — their receipts are burned-claimable accounting with no backing until the next funding event, if ever.

The analog holds: the instant receipt "walks" vault balance that was freed from its own accounting (`pendingInstantWithdraws` still counts it as unfunded) but is claimed anyway — a stale-reference spend. No guard stops it: `pendingInstantWithdraws` is never consulted on the claim path, and `_transferFundedClaim`'s reserve guard only covers the post-default reserve.

### Impact Explanation
Direct theft of other users' funded-but-unclaimed withdrawal receipts, up to the attacker's instant receipt size, bounded only by `instantWithdrawsRequests[attacker]` vs. vault balance. Honest claimants suffer a temporary (or permanent, if the CDO never tops up) freeze of their already-realized claims. Loss ≈ attacker's instant receipt amount, capped by funded-but-unclaimed normal/APR0 receipts in the vault.

### Likelihood Explanation
Requires `allowInstantWithdraw` on (a supported mode per `_isInstantWithdrawEnabled`) and an APR decrease larger than `instantWithdrawAprDelta` — both attainable without any privileged misbehavior (borrower/APR changes are honest flows). The attacker needs only a KYC-passed tranche position. The window exists every epoch transition where instant receipts are outstanding while `stopEpoch` funds normal receipts, plus any time the vault idles with unclaimed funded claims.

### Recommendation
On `claimInstantWithdrawRequest`, verify the request was funded — e.g., require `instantWithdrawsRequests[_user] <= (instantWithdrawClaims funded)` by tracking funded instant claims separately, or revert while `pendingInstantWithdraws != 0` covers the user's receipt. Alternatively, escrow funded amounts per receipt epoch at `collectInstantWithdrawFunds` time and only permit claims against that escrow.

### Proof of Concept
Foundry fork sketch (against a fork block with an existing `IdleCreditVault` + `IdleCDOEpochVariant` deployment where `allowInstantWithdraw` is true):

```solidity
// 1. Honest user H deposits AA, requests withdraw (normal), epoch 0 runs.
// 2. Attacker A deposits AA; force APR drop via manager's honest setAprs on new epoch,
//    or wait for a real APR decrease so requestWithdraw routes to requestInstantWithdraw.
//    A's instant receipt is minted; pendingInstantWithdraws = A_amount; vault balance ~0.
// 3. Warp past epochEndDate; prank manager: cdoEpoch.stopEpoch(apr, 0).
//    collectWithdrawFunds pulls underlying for H's receipt into the vault.
// 4. Before startEpoch: prank A -> cdoEpoch.claimInstantWithdrawRequest()
//    assert underlying.balanceOf(A) increased by A_amount (paid from H's funded claim).
// 5. prank H -> cdoEpoch.claimWithdrawRequest() -> reverts (insufficient vault balance).
```

Uncertainty I could not fully verify in the available iterations: whether `IdleCDOEpochVariant` blocks `claimInstantWithdrawRequest` during the stopped/buffer phase via some path I didn't read (the function at IdleCDOEpochVariant.sol:975-979 only checks `allowInstantWithdraw`), and whether `startEpoch` always funds instant requests before any normal receipts are funded into the vault. If the CDO strictly orders funding such that instant claims can only execute when the vault balance equals exactly their funded amount, the exploit narrows to stealing residual unclaimed funded claims, which still breaks the funded-claim isolation invariant.
