### Title
Debug/pprof endpoints reachable by any authenticated role (including lowest "view" role) instead of admin-only - ([File: core/web/router.go])

### Finding Description
The pprof debug endpoints are registered via `metricRoutes(authv2)` inside `v2Routes` at [1](#0-0) , which places them under the `authv2` group. This group only requires `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` at [2](#0-1)  — i.e., any successfully authenticated session or API token, regardless of role.

Unlike every other sensitive route in the same file (e.g. `/v2/users`, `/v2/transfers`, `/v2/keys/*/export`) which are explicitly wrapped with `auth.RequiresAdminRole(...)` or `auth.RequiresEditRole(...)`, the `metricRoutes` handlers registered at [3](#0-2)  have **no role wrapper at all**:

```go
func metricRoutes(r *gin.RouterGroup) {
	pprofGroup := r.Group("/debug/pprof")
	pprofGroup.GET("/", ginHandlerFromHTTP(pprof.Index))
	pprofGroup.GET("/cmdline", ginHandlerFromHTTP(pprof.Cmdline))
	pprofGroup.GET("/profile", ginHandlerFromHTTP(pprof.Profile))
	...
	pprofGroup.GET("/goroutine", ginHandlerFromHTTP(pprof.Handler("goroutine").ServeHTTP))
	pprofGroup.GET("/heap", ginHandlerFromHTTP(pprof.Handler("heap").ServeHTTP))
	...
}
```

Since `RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` (which call `addForbiddenErrorHeaders` on failure, see [4](#0-3) ) are never invoked for these routes, a user holding only the lowest privilege (`UserRoleView`) — which the audit rules explicitly treat as an acceptable unprivileged attacker — can successfully call `GET /v2/debug/pprof/cmdline`, `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/trace`, `/v2/debug/pprof/profile`, etc. This exposes the node process command line (which can contain `-password` / secret CLI flags), full heap dumps (may contain private keys or session tokens resident in memory), and goroutine stack traces.

The route RBAC test suite (`routesRolesMap` in `core/web/auth/auth_test.go`) covers essentially every other admin/edit/run-restricted route but does not include any `/v2/debug/pprof/*` entries, so this gap is untested and unnoticed. [5](#0-4) 

The similar `/debug/vars` route (`debugRoutes`) at [6](#0-5)  also only requires `AuthenticateBySession` with no role check, exposing expvar metrics to any logged-in user.

Note: this is **not** reachable by a fully unauthenticated client — `auth.Authenticate` still enforces a valid session or API token. But it is reachable by any authenticated user of the lowest role (`view`), which the question's attacker-capability rules explicitly allow ("a view/run-role user").

### Impact Explanation
A low-privilege `view`-role user (or restricted API-token holder) can pull full heap/goroutine/cmdline profiles from a running node via `/v2/debug/pprof/*`. Depending on operational practices (e.g., secrets passed via CLI flags, key material resident in memory, session data in heap), this can leak sensitive node data to a user who was only meant to have read-only dashboard access — a privilege-escalation / information-disclosure issue matching "server credential/key theft" bounty class, though the actual presence of secrets in `cmdline`/heap depends on deployment.

### Likelihood Explanation
High feasibility and repeatability: any account with the `view` role (the lowest privilege tier, obtainable via normal onboarding or a leaked read-only API token) can immediately issue `GET /v2/debug/pprof/heap`, `/cmdline`, `/goroutine` etc. without any additional exploitation step, since there is no role check at all — just a valid session/token.

### Recommendation
Wrap all `metricRoutes` (and the `/debug/vars` route in `debugRoutes`) with `auth.RequiresAdminRole(...)` (or the highest configured role) so that pprof/debug/metrics endpoints are restricted to admin operators only, consistent with the rest of the sensitive routes in `core/web/router.go`. Add corresponding entries to the `routesRolesMap` RBAC test table in `core/web/auth/auth_test.go` to prevent regression.

### Proof of Concept
1. In `core/web/auth/auth_test.go`, add entries to `routesRolesMap` for `{"GET", "/v2/debug/pprof/heap", false, false, false}`, `{"GET", "/v2/debug/pprof/cmdline", false, false, false}`, `{"GET", "/v2/debug/pprof/goroutine", false, false, false}`, and `{"GET", "/v2/debug/vars", false, false, false}` (marking them admin-only, i.e. all `false`).
2. Run `TestRBAC_Routemap_ViewOnly` (and `TestRBAC_Routemap_Run`) — expected assertion per the test's `switch` logic (`!route.EditAllowed` → `assert.Equal(t, http.StatusForbidden, resp.StatusCode)`).
3. Currently this will FAIL because the handler returns `200 OK` (pprof data) instead of `403 Forbidden`, confirming the missing role check.
4. After applying the fix (wrapping with `auth.RequiresAdminRole`), rerun the test and confirm `403 Forbidden` with `forbidden-required-role: admin` header set via `addForbiddenErrorHeaders`.

```go
// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
```
