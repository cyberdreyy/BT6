### Title
Loss-adjusted withdraw receipt escapes its haircut and is paid at full basis when the user re-requests withdraw in a later epoch - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` tracks a loss-adjusted claim epoch only through `lastWithdrawRequest[_user]` (a single slot). If a stop epoch ends with a realized loss (`collectWithdrawFunds` collects less than `pendingWithdraws` and records `lossRecoveryPriceByEpoch[epochNumber]`), a user whose receipt was haircutted can simply make a new `requestWithdraw` in the following epoch. That overwrites `lastWithdrawRequest[_user]` with the new epoch, so `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[newEpoch] == 0` and returns early — while the stale per-epoch basis `withdrawsRequestsByEpoch[user][oldEpoch]` and the aggregate `withdrawsRequests[user]` still hold the full pre-haircut amount. The funded-claim path then pays the full basis at par, although the strategy only received the haircutted amount from the borrower.

This is the closest analog of the CVE's "wrong-type node treated as valid → invalid free" class: an already-impaired (haircutted) receipt is treated as a fully-funded one, paying out funds that were never collected — the double-spend equivalent of a double-free.

### Finding Description
Relevant code, `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` records the full basis and bumps `lastWithdrawRequest[_user] = currentEpoch` (lines ~281-294).
- `collectWithdrawFunds` (lines 411-430): on shortfall it sets `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` and zeroes `pendingWithdraws`, but **only `_amount` is transferred in**; per-user `withdrawsRequests`/`withdrawsRequestsByEpoch` are left at full basis.
- `claimWithdrawRequest` (lines 301-314) runs `_claimLossAdjustedWithdrawRequest` then `_claimFundedWithdrawRequest`.
- `_claimLossAdjustedWithdrawRequest` (lines 789-801) derives the claim epoch solely from `lastWithdrawRequest[_user]`; if `lossRecoveryPriceByEpoch[thatEpoch] == 0` it returns without clearing the old epoch's basis.
- `_claimFundedWithdrawRequest` (lines 319-350) then pays `withdrawsRequests[_user]` (which still includes the old epoch's full basis) via `_transferFundedClaim`, gated only by `epochNumber > lastWithdrawRequest[_user]`.

Attack sequence (unprivileged KYC'd lender/tranche holder):
1. Epoch N running; attacker calls `requestWithdraw` → `withdrawsRequests[A] = X`, `withdrawsRequestsByEpoch[A][N] = X`, `lastWithdrawRequest[A] = N`.
2. Manager calls `stopEpochWithDuration(_lossAmount)`; borrower funds `X * r` where `r = lossRecoveryPriceByEpoch[N] < 1e18`.
3. Attacker calls `requestWithdraw` again in epoch N+1 (any small amount `Y`) → `lastWithdrawRequest[A] = N+1`.
4. Epoch N+1 ends normally (fully funded). Now `epochNumber > lastWithdrawRequest[A]` wait-gate passes.
5. Attacker calls `claimWithdrawRequest`: loss path checks epoch N+1 (price 0, skips); funded path pays `X + Y + interest` at par and burns the receipt.

The strategy only ever received `X*r` for epoch N, so the excess `X*(1 - r)` is paid out of funds belonging to other funded claimants or the default recovery reserve.

### Impact Explanation
Direct theft / insolvency: for every unit of haircutted receipt, the attacker extracts `1 - lossRecoveryPrice` of uncollected underlying. With a 50% recovery price on a large receipt, the attacker drains half the receipt basis from other users' funded claims; subsequent legitimate claimants revert on insufficient balance (permanent freezing of their claims). Quantified loss = `claimBasis * (RECOVERY_FULL - lossRecoveryPriceByEpoch[lossEpoch]) / RECOVERY_FULL` per attacker, bounded by total haircutted basis in the loss epoch.

### Likelihood Explanation
Requires a `stopEpochWithDuration` loss event (manager/borrower are honest, but losses are a designed-for path) plus an attacker who simply re-requests a withdrawal before claiming — a normal, unprivileged action. No privileged misbehavior needed; the attacker can even use a tiny second request. The `defaultRecoveryInitialized` guard and the `lossRecoveryPrice == 0` revert do not stop it, because the bug is stale-epoch keying, not initialization.

### Recommendation
Track loss-adjusted claims per epoch rather than via the single `lastWithdrawRequest` slot. Either iterate/clear all epochs with `lossRecoveryPriceByEpoch[e] != 0` for which `withdrawsRequestsByEpoch[_user][e] != 0`, or decrement `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch` to the haircutted basis inside `collectWithdrawFunds` (pro-rata per user is not possible there, so per-epoch clearing on claim is the cleaner fix — e.g., store the user's loss-epoch list or use `withdrawsRequestsByEpoch` scanning keyed by recorded request epochs rather than `lastWithdrawRequest`). At minimum, `requestWithdraw` should first flush any pending loss-adjusted claim for the user before overwriting `lastWithdrawRequest`.
