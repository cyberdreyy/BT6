### Title
Front-runnable ERC4626 liquidity drain makes `stopEpoch` revert and temporarily freezes all lender funds — ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

The rclone bug is "a failed transport interaction returns an unusable result, and the caller crashes instead of degrading gracefully." The credit-vault analog is `ProgrammableBorrower.onStopEpoch`: when the configured shared ERC4626 vault cannot service a withdrawal mid-stop, the function reverts (`StopEpochVaultLiquidityUnavailable`) and that revert propagates through `IdleCDOEpochVariant.stopEpoch`, so the entire epoch stop — and with it every lender's `claimWithdrawRequest` / `claimInstantWithdrawRequest` path — is blocked. Any unprivileged user of the borrower vault can force this state on demand.

### Finding Description

In `onStopEpoch`, when IdleCDO requires more than the contract's on-hand balance, the strategy computes `shortfall = _amountRequired - onHand` and attempts `vault.withdraw(shortfall, ...)` inside a `try`/`catch` at lines 240–253:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:240-253
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
    uint256 shortfall = _amountRequired - onHand;
    if (shortfall > _currentVaultAssets()) return true;
    try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        ...
    } catch {
        revert StopEpochVaultLiquidityUnavailable();
    }
}
```

The guard `shortfall > _currentVaultAssets()` compares the shortfall against `convertToAssets(shares)` — a *valuational* check. It does not verify that the vault actually holds enough underlying liquidity to service the withdrawal. For shared ERC4626 vaults (the design explicitly supports an external vault sleeve), `convertToAssets` reflects total assets, while `vault.withdraw` reverts when the vault's liquid balance is below `shortfall`, when `maxWithdraw` is lower than the converted value, or when share-price inflation makes the required shares exceed the balance.

An attacker who is an ordinary depositor of that vault can front-run the manager's `stopEpoch` transaction, withdraw/redeem vault liquidity so `withdraw(shortfall)` reverts, and make every `stopEpoch` call revert until liquidity returns. During the freeze the epoch keeps running, the borrower keeps the drawn principal, and pending withdraw requests cannot be paid.

### Impact Explanation

Temporary freezing of all lender funds in the vault: for the duration of the liquidity drain, `stopEpoch` cannot complete, so `epochEndDate` passes, the pool cannot settle interest, `claimWithdrawRequest` and `claimInstantWithdrawRequest` remain blocked, and neither AA nor BB holders can exit. The borrower additionally continues to hold drawn principal (interest accrues at `borrowerApr`, but settlement is delayed), and the attacker can repeat the drain each time the vault regains liquidity, extending the freeze. The quantified loss is the unavailability of the full contract value (`getContractValue` of the CDO, i.e., all AA + BB NAV) for the freeze duration, plus any missed `instantWithdrawDeadline` window.

### Likelihood Explanation

- The attacker needs only to be a user of the programmable borrower's ERC4626 vault — an explicitly in-scope unprivileged role — no Idle roles required.
- Triggering condition is realistic: shared ERC4626 vaults routinely have `totalAssets` greater than instantly withdrawable liquidity, and `convertToAssets` coverage does not imply `withdraw` success.
- It requires sequencing around the honest manager's `stopEpoch` call (front-running or simply draining liquidity while an epoch is overdue), which is a standard MEV-style ordering assumption.
- Impact is temporary rather than permanent: funds recover once vault liquidity is restored, which caps this at medium severity, matching the "temporary freezing" acceptance criterion.

### Recommendation

- In `onStopEpoch`, check the vault's actual withdrawable amount (e.g., `vault.maxWithdraw(address(this))` or `vault.maxRedeem`) instead of only `convertToAssets` coverage before deciding between the withdraw path and the `return true` / default path, so a liquidity-reverting vault routes to the controlled settlement path instead of an unbounded revert.
- Alternatively, make the catch branch degrade gracefully: pull as much as `maxWithdraw` allows, mark the residual as borrower-side shortfall, and let the default/partial-settlement logic handle it rather than reverting the whole stop.
- As defense in depth, allow `stopEpoch` to be retryable with a reduced `_amountRequired` (on-hand + maxWithdrawable) so a temporarily illiquid vault cannot hold the epoch state machine hostage.

### Proof of Concept

```solidity
// test/foundry/ProgrammableBorrowerVaultDoS.t.sol
// Concept: shared ERC4626 vault whose liquidity can be drained by any depositor.

function testStopEpochRevertsWhenVaultLiquidityDrained() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    // attacker deposits into the same ERC4626 vault used by ProgrammableBorrower
    underlying.mint(attacker, amount);
    vm.startPrank(attacker);
    underlying.approve(address(externalVault), amount);
    externalVault.deposit(amount, attacker);

    _startEpochAndCheckPrices(0);

    // borrower draws principal so onHand < amountRequired at stop
    vm.prank(borrower);
    programmableBorrower.borrow(drawAmount);

    // attacker drains vault liquidity; convertToAssets still reports coverage
    vm.startPrank(attacker);
    externalVault.withdraw(externalVault.maxWithdraw(attacker), attacker, attacker);

    // manager's stopEpoch now reverts inside onStopEpoch's catch
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(apr, expectedFunds);

    // all lender claims remain frozen while vault liquidity is unavailable
    vm.expectRevert();
    vm.prank(lender);
    cdoEpoch.claimWithdrawRequest();
}
```

The PoC demonstrates: (1) `shortfall <= convertToAssets(shares)` so the early `return true` guard does not fire, (2) `vault.withdraw` reverts on insufficient vault liquidity, (3) `stopEpoch` reverts, leaving the epoch running and lender funds frozen for as long as the attacker keeps the vault drained.
