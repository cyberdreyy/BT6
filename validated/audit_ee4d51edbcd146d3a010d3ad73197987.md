### Title
Loss-adjusted withdraw haircut only applies to the latest request epoch; receipts from older epochs are paid at par and drain the funded claim reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores a haircut under `lossRecoveryPriceByEpoch[epochNumber]` for the *entire* `pendingWithdraws` aggregate, but `_claimLossAdjustedWithdrawRequest` only clears the per-epoch receipt stored at `lastWithdrawRequest[user]`. Receipts the same user recorded under an earlier epoch key remain in `withdrawsRequests[user]` and are paid at par by `_claimFundedWithdrawRequest`, breaking the loss-socialization invariant and over-paying the claimant out of funds reserved for other pending receipts.

### Finding Description
- On a partial stop-epoch funding, `collectWithdrawFunds` writes one global recovery price `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` where `pendingBasis = pendingWithdraws` covers *all* pending receipts regardless of the epoch they were requested in [1](#0-0) .
- Each `requestWithdraw` only records the user's receipt under the *current* `epochNumber` and overwrites `lastWithdrawRequest[user] = currentEpoch` [2](#0-1) .
- At claim time, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` and clears only `withdrawsRequestsByEpoch[user][that single epoch]` [3](#0-2) . `_clearWithdrawClaimForEpoch` then resets `lastWithdrawRequest[user] = 0` [4](#0-3) .
- The remainder of `withdrawsRequests[user]` — i.e., the older-epoch receipt that was *also* inside the haircutted `pendingBasis` — falls through to `_claimFundedWithdrawRequest`, which pays it at par from the vault balance [5](#0-4) .
- The guard in `requestWithdraw` only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`; at the time of the second request the older epoch has no loss price yet, so it does not block this sequence [6](#0-5) .

This is the on-chain analog of the out-of-bounds write in CVE-2021-30592: the haircut is "written" under a single epoch index while the loss actually applies to a multi-epoch aggregate, leaving sibling receipts outside the bounds of the write.

### Impact Explanation
Quantified overpayment: for receipts `W1` (epoch N) and `W2` (epoch N+1) and recovery price `p`, the vault collected `(W1 + W2) * p` but pays `W1 + W2 * p`. The excess `W1 * (1 - p)` is taken from underlyings that were funded to satisfy *other* users' pending receipts (or, after default finalization, would be protected by the `defaultRecoveryReserve` guard in `_transferFundedClaim` [7](#0-6) ). With a 50% haircut and equal `W1`, `W2`, the attacker extracts ~33% more than funded, causing insolvency for the last claimants — direct theft of funded withdraw receipts.

### Likelihood Explanation
Requires only unprivileged actions: deposit via the epoch CDO, call `requestWithdraw` in two consecutive buffer windows, decline to claim the first matured receipt (explicitly supported — comments note unclaimed requests wait), then `claimWithdrawRequest` once after the manager calls `stopEpochWithDuration(_lossAmount)` (an honest privileged call that realizes a partial loss). Any real borrower-loss event while a user holds receipts across two epochs triggers it; no race, no privileged collusion.

### Recommendation
- Track the haircut per user against the full pending basis: on claim, apply `lossRecoveryPriceByEpoch` to *all* of the user's receipts that were pending at the loss epoch (e.g., maintain a cumulative loss-price product per user, or iterate/store all epochs contributing to `withdrawsRequests`).
- Alternatively, in `requestWithdraw`, revert if `withdrawsRequests[user] != 0` whenever *any* loss price exists for epochs at or before the new request, and/or force-claim earlier receipts before allowing a new epoch-keyed request.
- Add a regression test: requests in epochs N and N+1, partial loss at stop of N+1, assert total payout equals `(W1 + W2) * p`.

function testCrossEpochLossEscape() public {
    // attacker deposits and requests withdraw W1 during buffer of epoch N
    _depositWithUser(attacker, W1, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // epochNumber = N

    // honest manager runs epoch N (full funding, no loss)
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch()); // epochNumber -> N+1

    // attacker does NOT claim W1; requests W2 during buffer of epoch N+1
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // lastWithdrawRequest = N+1
    // second victim/user also has pending receipt V in epoch N+1

    _startEpochAndCheckPrices(0);
    // honest manager stops epoch N+1 with a realized loss:
    // collectWithdrawFunds funds (W1+W2+V)*p and sets lossRecoveryPriceByEpoch[N+1] = p
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(_lossAmount, ...);

    // attacker claims: pays W2*p via _claimLossAdjustedWithdrawRequest,
    // then W1 at par via _claimFundedWithdrawRequest
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    // invariant broken: paid W1 + W2*p > (W1+W2)*p funded for attacker
    // victim's claim of V*p now reverts/underflows or drains unrelated balance
}

Caveat I could not fully verify within the iteration limit: the exact call ordering inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` (whether `epochNumber` increments before `collectWithdrawFunds` writes the price). The exploit relies only on `lossRecoveryPriceByEpoch[N+1]` applying to an aggregate that includes the epoch-N receipt `W1`, which the code's own comments confirm; if the increment ordering instead keyed the price to N, the same attack works symmetrically with the older receipt under `lastWithdrawRequest` coverage — the core defect (single-epoch keyed haircut vs multi-epoch aggregate `withdrawsRequests`) holds either way.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
