## Title
Multisig executes requests below the required confirmation threshold because stale confirmations from removed members are never purged — ([File: multisig2/src/lib.rs](multisig2/src/lib.rs))

### Summary
The `multisig2` contract counts a request as approved once `confirmations.len() + 1 >= num_confirmations` [1](#0-0) , but the confirmation set is keyed only by an opaque member-identifier string and is never reconciled against the *current* live `members` set when a member is removed. `delete_member()` only clears confirmations for requests that were *originally created* by the removed member (`r.member == member`); it does not scan or purge the deleted member's entries from the confirmation sets of *other, still-pending* requests [2](#0-1) . This breaks the intended equality `confirmations counted == live authorized members who confirmed`, allowing a request to execute with fewer live confirmers than `num_confirmations`.

### Finding Description
The contract stores per-request confirmations as `confirmations: LookupMap<RequestId, HashSet<String>>` [3](#0-2) . When a member confirms a request, their string identifier is added to this set via `confirm()` [4](#0-3) .

When a member is later removed through `DeleteMember`, `delete_member()` removes the member from `self.members`, deletes their access key, and cleans up requests/confirmations **only for requests they authored** (`r.member == member`) [5](#0-4) . It never iterates the `confirmations` map to strip the removed member's identifier from other pending requests' confirmation sets.

Consequently, any confirmation a member cast on a request *before* being removed remains permanently counted toward that request's threshold in `confirm()`'s check `confirmations.len() as u32 + 1 >= self.num_confirmations` [6](#0-5) . This is structurally the same class of bug as the referenced SEDA report: a stale/absent membership fact (there, a validator not yet recognized; here, a member already removed) is not reconciled against the live authorization set before a threshold decision is made, except here it manifests as under-counting the real threshold rather than over-counting, letting execution proceed with fewer authorized signers than configured.

### Impact Explanation
This directly matches the Critical impact class "a multisig request executed below threshold." A request (e.g., `Transfer`, `AddKey`, `FunctionCall`, or even another `DeleteMember`/`AddMember`) can be executed by promise with fewer currently-authorized confirmers than `num_confirmations` requires, because a stale confirmation from a now-removed member is still counted. This can lead to unauthorized transfers of NEAR held by the multisig account or unauthorized key/member changes, moving funds or control by a party (a minority of live members) not entitled to unilaterally do so under the configured K-of-N policy.

### Likelihood Explanation
This requires no privileged access beyond being one of the multisig's own members (an "unprivileged" party relative to the full K threshold) — it only requires: (1) a member confirms a pending request, (2) that member is subsequently removed via a normal `DeleteMember` request, and (3) fewer than `num_confirmations` remaining live members then confirm the still-pending request to push it over threshold using the stale count. Membership changes are an expected, ordinary multisig operation, so the precondition is easily reached in normal contract lifecycle without any external attacker action beyond being a temporary member.

### Recommendation
In `delete_member()`, iterate all entries in `self.confirmations` and remove the deleted member's identifier from every confirmation `HashSet`, not just the confirmation sets of requests the member authored. Alternatively, when checking the threshold in `confirm()`, filter `confirmations` to only those identifiers still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request` to create malicious request `R` (e.g., `Transfer` to an attacker-controlled account). `R`'s confirmations = `{}`.
3. `B` calls `confirm(R)` → confirmations for `R` = `{B}` (1 of 3, not yet executed) [4](#0-3) .
4. Separately, members legitimately approve and execute a `DeleteMember{B}` request (using 3 confirmations from `A, C, D`). `delete_member()` removes `B` from `self.members` but does not touch `R`'s confirmation set, which still contains `"B"` [5](#0-4) .
5. Now live members are `[A, C, D]`, threshold still 3. `A` calls `confirm(R)` (2 of 3), then `C` calls `confirm(R)` — count reaches `2 + 1 = 3 >= num_confirmations`, so `R` executes [7](#0-6) , even though only `A` and `C` (2 live members) actually approved it, one short of the configured 3-of-N threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
