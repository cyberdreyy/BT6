The reported bug's root cause is a boolean `hasRefunded[gameId][player]` flag scoped per user+game that is never reset when the user rejoins the same game, so a later legitimate refund path reverts and funds get stuck. In `ProvisionerV2.sol`, the analogous refund/cancel/solve tracking is done via `asyncRequestHashes` (async deposit/redeem requests) and `syncDepositHashes` (sync deposits), both keyed by a hash of the full request parameters (including token, amounts, deadline, receiver, etc.), not by a persistent per-user boolean flag [1](#0-0) . Every new deposit/redeem request (via `requestDeposit`/`requestRedeem`) or sync deposit (`_syncDeposit`) computes a fresh hash from its own parameters and sets it to `true`, then any refund/cancel/solve path (`refundRequest`, `cancelRequest`, `solveRequestsVault`, `solveRequestsDirect`, `refundDeposit`) unsets that specific hash to `false` after transferring funds [2](#0-1) [3](#0-2) . Because there is no persistent "already refunded" flag scoped by user (only per-request hashes that are freshly created and independently cleared each time), re-issuing a new deposit/redeem request after a previous one was refunded creates a brand-new hash rather than reusing/relying on a stale boolean, so the described "stuck flag blocks legitimate re-claim" pattern does not reproduce in this code path. I did not find a concrete function pair matching the required root cause (a non-reset per-user boolean guard combined with a leave/rejoin/cancel sequence) in the deposit/mint/request/solve/refund/redeem/withdraw surfaces of `ProvisionerV2` or `MultiDepositorVault`.
