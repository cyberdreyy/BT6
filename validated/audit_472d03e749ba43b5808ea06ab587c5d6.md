## Finding

### Title
DoS via unbounded blocking `eth_subscribe` sink writes (flashblocks/base-specific subscriptions) - ([File: crates/execution/flashblocks/src/rpc/pubsub.rs])

### Summary
The Apache report describes an HTTP/2 DoS where a peer that never grants stream-level flow-control credit (window size 0) causes the server to block a worker indefinitely trying to write, exhausting connection-handling resources. The analogous pattern exists in Base's `eth_subscribe` handling for flashblocks-specific subscription kinds: the server-side sink write to a WebSocket client has no timeout, so a client that simply stops reading (a zero read-window equivalent) causes the per-subscription task to block forever, holding resources indefinitely.

### Finding Description
`EthPubSub::subscribe` in `crates/execution/flashblocks/src/rpc/pubsub.rs` spawns a task per subscription (`NewFlashblocks`, `PendingLogs`, `NewFlashblockTransactions`) that runs `pipe_from_stream`: [1](#0-0) 

`pipe_from_stream` writes every new item to the `SubscriptionSink` with `sink.send(msg).await` and no timeout: [2](#0-1) 

Unlike the separate `websocket-proxy` component, which explicitly wraps its outbound WebSocket write in `tokio::time::timeout(self.send_timeout_ms, ws_sender.send(msg))` and disconnects slow clients on timeout: [3](#0-2) 

the `eth_subscribe` pubsub path for `NewFlashblocks`/`PendingLogs`/`NewFlashblockTransactions` has no equivalent guard. `jsonrpsee`'s `SubscriptionSink::send` backpressures on the underlying WebSocket connection; if a client opens `eth_subscribe(["newFlashblocks"])` (or the other Base-specific kinds) over WebSocket and then stops reading from the socket (analogous to holding an HTTP/2 flow-control window at 0), the write will block indefinitely. The identical pattern exists for the other custom subscription sinks that lack a send timeout, e.g. `WsRPC::send_state_update` and `DevEngineRpc::send_queue_length_update`: [4](#0-3) [5](#0-4) 

An anonymous RPC/WebSocket client can open many such subscriptions and simply never read, tying up a `tokio::spawn`ed task per subscription (and any state/broadcast receiver it holds open, e.g. a canonical-state broadcast subscriber) for as long as the TCP connection stays open. Because there is no per-message send timeout and no idle/backpressure enforcement configured at the `jsonrpsee` `ServerConfig` level for these RPC actors, the connection can be held open with growing resource usage (each blocked task, the underlying stream/broadcast subscription it holds, and the socket buffer) with no automatic reaping.

### Impact Explanation
This is a resource-exhaustion / worker-starvation DoS against the public `eth_*` WebSocket RPC surface, directly reachable by any anonymous RPC client (no signed transaction or privileged access required). A modest number of concurrent "slow" subscriptions can pin a corresponding number of tokio tasks and hold internal broadcast/stream subscriptions open indefinitely, degrading or halting the node's ability to serve legitimate `eth_subscribe`/RPC requests — matching the "RPC the node can no longer serve" acceptance criterion.

### Likelihood Explanation
High feasibility: the attack requires only opening a WebSocket connection, issuing `eth_subscribe` with one of the Base-specific kinds, and then not reading from the socket (or reading extremely slowly), which is trivial for any client and requires no special privileges, funds, or race conditions.

### Recommendation
Wrap the `sink.send(...)` calls in `pipe_from_stream` (and the analogous `send_state_update`/`send_queue_length_update` helpers) in a bounded `tokio::time::timeout`, disconnecting (returning/aborting) the subscription task when the timeout elapses — mirroring the pattern already used in `crates/infra/websocket-proxy/src/registry.rs`. Additionally, configure `jsonrpsee`'s `ServerConfig` (ping interval / max idle time) for the execution and consensus RPC actors so idle/unresponsive WebSocket connections are proactively closed.

### Proof of Concept
1. Connect to the node's WebSocket RPC endpoint.
2. Send `{"jsonrpc":"2.0","id":1,"method":"eth_subscribe","params":["newFlashblocks"]}` (or `pendingLogs` / `newFlashblockTransactions`).
3. After receiving the subscription ack, stop reading from the socket entirely (do not call `recv`/`next` on the client side) while keeping the TCP connection open.
4. Trigger new flashblocks/logs on the node (normal chain activity) — the corresponding `pipe_from_stream` task's `sink.send(...).await` blocks indefinitely waiting for the client to drain the socket.
5. Repeat with many concurrent connections/subscriptions to pin many tasks and open stream subscriptions indefinitely, without any server-side timeout ever firing.

async fn pipe_from_stream<T, St>(sink: SubscriptionSink, mut stream: St)
where
    St: Stream<Item = T> + Unpin,
    T: Serialize,
{
    loop {
        tokio::select! {
            // dropped by client
            _ = sink.closed() => return,

            maybe_item = stream.next() => {
                // stream ended
                let Some(item) = maybe_item else {
                    return;
                };

                let msg = match SubscriptionMessage::new(
                    sink.method_name(),
                    sink.subscription_id(),
                    &item
                ) {
                    Ok(msg) => msg,
                    Err(err) => {
                        error!(
                            target: "flashblocks_rpc::pubsub",
                            %err,
                            "Failed to serialize subscription message"
                        );
                        return;
                    }
                };

                // if it fails, client disconnected
                if sink.send(msg).await.is_err() {
                    return;
                }
            }
        }
    }
}
