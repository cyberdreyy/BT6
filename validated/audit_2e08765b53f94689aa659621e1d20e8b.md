### Title
Post-default withdraw requests inject unpriced claim basis into the defaulted-epoch recovery bucket - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` has a finalized-default fast path (`postDefaultRequests`), but between the borrower default and `finalizeDefaultRecovery` it falls through to the normal path and writes `withdrawsRequestsByEpoch[_user][epochNumber]`. Since `defaultRecoveryEpoch` is later set to the same `epochNumber`, these injected receipts are paid at `defaultRecoveryPrice` even though they were never part of the finalized claim basis and (in the closed-pool branch) never entered `pendingWithdraws`.

### Finding Description
In `requestWithdraw` the post-default branch is only taken when `defaultRecoveryFinalized` is true (line 247). During the window where the CDO is already `defaulted()` but recovery is not yet finalized, the function executes the normal path:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:259-294
bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0;
uint256 currentEpoch = epochNumber;
...
if (!isClosed) {
  pendingWithdraws += _amount;
}
lastWithdrawRequest[_user] = currentEpoch;
withdrawsRequests[_user] += _amount;
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

`finalizeDefaultRecovery` then crystallizes the accounting with `defaultRecoveryEpoch = epochNumber` (line 693) and `defaultPendingClaimBasis()` only counts `pendingWithdraws` plus current-epoch instant claims (lines 644-649). Two problems result:

1. When the defaulted pool reports `epochEndDate() == 0` (closed/defaulted bookkeeping), the new receipt is **not** added to `pendingWithdraws`, so it is excluded from `totalBasis` and from the reserve computation, yet it sits in `withdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`. `_claimDefaultedWithdrawRequest` (lines 772-784) clears that whole epoch bucket and pays `claimBasis * defaultRecoveryPrice` from `defaultRecoveryReserve`, letting the attacker withdraw reserve that was sized only for pre-default claimants — direct theft of other users' recovery.
2. Even when `epochEndDate() != 0`, the request is priced by the CDO at the pre-finalization `virtualPrice` (the loss is only pushed into tranche prices by `_forceUpdateAccounting` during `finalizeDefaultRecovery`), so the attacker converts soon-to-be-impaired tranche value into full-basis default claims, diluting `defaultRecoveryPrice` for honest claimants.

The bug class is an injection analog: attacker-controlled input is injected into a fixed-scope aggregate (the defaulted-epoch claim bucket) after that scope should have been frozen, exactly like injecting rows into a query whose result set was already bounded.

### Impact Explanation
Any EOA holding tranche tokens (KYC lender or secondary-market buyer) can, in the default-to-finalization window, call `requestWithdraw` through the CDO and mint a receipt that `_claimDefaultedWithdrawRequest` treats as defaulted-epoch basis. In the closed-bookkeeping case every unit injected pays out `defaultRecoveryPrice` from a reserve that never accounted for it, directly stealing recovered funds owed to honest pending redeemers and active LPs. The loss is quantifiable: `injectedAmount * defaultRecoveryPrice / 1e18`, capped only by the attacker's tranche balance, and can drain the reserve below what legitimate claimants are owed.

### Likelihood Explanation
The window is permissionless and requires no privileged cooperation: borrower default is a normal protocol event, and `finalizeDefaultRecovery` is an explicit later step that cannot be assumed atomic with the default itself. The only precondition is that the CDO still forwards `requestWithdraw` while `defaulted()` is true; nothing in `IdleCreditVault.requestWithdraw` reverts on `cdo.defaulted()` before finalization (only `defaultRecoveryFinalized` is checked at line 247, and the loss-epoch guard at lines 263-271 only applies when `lossRecoveryPriceByEpoch` is set, which is a different mechanism). Attacker cost is just tranche tokens purchased at the pre-finalization price.

Caveat: I could not fully verify the CDO-side gating — whether `IdleCDOEpochVariant.requestWithdraw`/`_handleBorrowerDefault` blocks new requests while `defaulted()` but pre-finalization — within available iterations. If the CDO hard-reverts requests during that window, the issue reduces to a design assumption rather than a live exploit.

### Recommendation
In `IdleCreditVault.requestWithdraw` (and `requestInstantWithdraw`), explicitly revert when `IIdleCDOEpochVariant(idleCDO).defaulted()` is true and `defaultRecoveryFinalized` is false, so no receipt can be recorded between the default event and recovery finalization. Alternatively, record such requests into a distinct post-default bucket rather than `withdrawsRequestsByEpoch[user][epochNumber]` so they can never be cleared as defaulted-epoch basis.

### Proof of Concept
Foundry fork scenario (standard `IdleCreditVault` + `IdleCDOEpochVariant` setup as in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Honest users deposit, epoch starts.
// 2. Borrower defaults: manager triggers the default path so cdoEpoch.defaulted() == true,
//    but finalizeDefaultRecovery has NOT been called yet.
// 3. Attacker (tranche holder) calls:
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche));
//    -> IdleCreditVault.requestWithdraw writes
//       withdrawsRequestsByEpoch[attacker][epochNumber] += amount
//       while pendingWithdraws is unchanged (epochEndDate == 0 branch).
// 4. Manager/keeper finalizes:
vm.prank(manager);
cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);
//    -> defaultRecoveryEpoch == epochNumber; reserve sized WITHOUT attacker's receipt.
// 5. Attacker claims:
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
//    -> _claimDefaultedWithdrawRequest clears withdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch]
//       and pays claimBasis * defaultRecoveryPrice from defaultRecoveryReserve.
assertEq(underlying.balanceOf(attacker) - pre, injected * strategy.defaultRecoveryPrice() / 1e18);
// Honest claimants' subsequent claims underflow or receive less than entitled:
// reserve was sized for basis without the injected amount.
```

If step 3 reverts at the CDO layer (unverified), the finding is not exploitable as stated and should be treated as a missing strategy-side guard.
