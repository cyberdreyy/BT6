### Title
Divergent tenure-change duplicate-block check between chainstate v1 and v2 allows split signer decisions for the same tenure-start proposal - (File: stacks-signer/src/chainstate/v1.rs, stacks-signer/src/chainstate/v2.rs)

### Summary
`validate_tenure_change_payload` in `chainstate/v1.rs` only rejects a competing tenure-start block if a **globally accepted** block already exists for the tenure, whereas the v2 implementation rejects it if **any signed block (locally or globally accepted)** exists for the tenure. For a block that a signer has locally-but-not-globally accepted, a v1 signer will pass the duplicate check while a v2 signer will hit `RejectReason::DuplicateBlockFound` for the identical `signer_signature_hash`.

### Finding Description
In `chainstate/v1.rs::validate_tenure_change_payload`, the duplicate-tenure-start guard queries `signerdb.get_last_globally_accepted_block(&block.header.consensus_hash)`: [1](#0-0) 

In `chainstate/v2.rs::validate_tenure_change_payload`, the equivalent guard instead queries `signerdb.get_last_signed_block(&block.header.consensus_hash)`, and the accompanying comment makes the semantic change explicit: "Only blocks we have signed (locally or globally accepted) count here": [2](#0-1) 

Given a `BlockInfo` that has been recorded via `signerdb.insert_block` with a *locally-accepted-only* state (not yet globally accepted) for a given tenure `consensus_hash`, and an attacker-crafted second `BlockProposal` carrying a `TenureChangePayload` for the same `consensus_hash`:
- On a v1 chainstate signer, `get_last_globally_accepted_block` returns `None` (since the recorded block is only locally accepted), so the duplicate check passes and the proposal continues to be evaluated by the rest of `check_proposal`.
- On a v2 chainstate signer, `get_last_signed_block` returns `Some(...)` for that same locally-accepted block, so the proposal is rejected with `RejectReason::DuplicateBlockFound` before any further checks.

For the identical `signer_signature_hash` and identical signerdb equivocation record, the accept/continue-processing vs. reject decision differs solely based on which chainstate module (`v1` vs `v2`) the signer runs, not on any property of the proposal itself.

### Impact Explanation
This breaks the uniqueness/equivocation-guard property that is supposed to hold uniformly across the signer set for a given tenure: two different signer cohorts (grouped by chainstate version) can reach different conclusions about whether a second tenure-start block is a duplicate for the same tenure. If v1-run signers do not stop at this specific check (and no other check in the shared pipeline independently blocks it), they can proceed to sign a competing tenure-start block for a tenure where they (or others) already locally accepted a different block, while v2-run signers refuse. This risks two distinct signed blocks being producible at the same (tenure, height) across the network — a chain-safety/uniqueness violation, consistent with a Critical severity category.

### Likelihood Explanation
The precondition is a signer population running mixed chainstate versions (v1 vs v2) — plausible during a rolling signer-software upgrade window across a reward cycle, since chainstate version selection is a property of each signer's own binary/configuration rather than a globally-enforced consensus parameter in this code path. It also requires a block to have reached local-but-not-global acceptance for a tenure, which is a normal occurrence during ordinary signing rounds under a `SignerDb`-recorded `BlockInfo`. The attacker only needs one miner slot to submit the crafted competing `TenureChangePayload` block proposal and gossip it — no majority signer control or auth token is required. This is repeatable each time the mixed-version condition holds and the guard condition is met.

### Recommendation
Unify the semantics of the tenure-start duplicate check across `v1.rs` and `v2.rs`. Since v2's approach is explicitly justified by the comment (a pre-committed-but-unsigned block should not block a competing tenure-start, but any signed block — local or global — must), the fix should update `v1.rs::validate_tenure_change_payload` to also call `signer_db.get_last_signed_block(...)` instead of `get_last_globally_accepted_block(...)`, so both chainstate implementations enforce identical decisions for identical signerdb state.

### Proof of Concept
Two Rust tests exercising `validate_tenure_change_payload` (or the enclosing `check_proposal`) with an identical `BlockInfo` fixture that is locally-accepted-only for a given tenure `consensus_hash`:

```rust
// stacks-signer/src/chainstate/tests/v1.rs
#[test]
fn v1_allows_second_tenure_start_over_locally_accepted_block() {
    // Insert a BlockInfo into signer_db via signerdb.insert_block with
    // local-acceptance state only (not globally accepted) for tenure `ch`.
    // Build a second NakamotoBlock with a TenureChangePayload referencing `ch`.
    let result = view.validate_tenure_change_payload(&proposed_by, &tenure_change, &block2, &mut signer_db, &client);
    assert!(result.is_ok()); // passes duplicate check on v1
}
```

```rust
// stacks-signer/src/chainstate/tests/v2.rs
#[test]
fn v2_rejects_second_tenure_start_over_locally_accepted_block() {
    // Identical BlockInfo fixture: locally-accepted-only block for tenure `ch`.
    let result = GlobalStateView::validate_tenure_change_payload(&tenure_change, &block2, &parent_tenure_id, &mut signer_db, &client, &config);
    assert_eq!(result, Err(RejectReason::DuplicateBlockFound)); // rejects on v2
}
```

Both tests use the same `signerdb.insert_block` fixture and the same `signer_signature_hash` for the competing block, demonstrating the divergent outcome asserted above.
