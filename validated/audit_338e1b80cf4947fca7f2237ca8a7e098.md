### Title
Epoch queue can be replaced after prefunding, redirecting minted AA shares and freezing queued deposits - ([File: contracts/IdleCDOEpochVariantPrefunded.sol])

### Summary
`setEpochQueue` allows the owner or manager to replace `epochQueue` even after the current queue has prefunded deposits to the borrower. When the epoch is stopped, `_afterStopEpochWithDuration` queries and mints the newly issued AA tranche shares to the replacement queue rather than the queue that owns the pending deposits. A malicious or incompatible replacement queue can therefore receive the shares while the original queue’s users cannot have their deposits processed.

### Finding Description
The contract documents the required invariant: the queue must not be changed after deposits have been prefunded and before `stopEpochWithDuration` settles the epoch. [1](#0-0) 

That invariant is not enforced. `setEpochQueue` only checks caller authorization and unconditionally overwrites `epochQueue`. [2](#0-1) 

After the epoch stops, `_afterStopEpochWithDuration` reads the currently configured queue, asks it for `prefundedDepositsToProcess`, mints AA shares to that address, mints matching strategy tokens, and calls `processPrefundedDeposits`. [3](#0-2) 

Consequently, if prefunded deposits already exist in queue Q1 and the stored address is replaced with Q2 before settlement:

- Q2 controls the accounting result returned by `prefundedDepositsToProcess`.
- `_mintSharesAtCurrPrice` sends the newly minted AA tranche tokens to Q2.
- Q1’s `processPrefundedDeposits` is never called.
- Q1’s deposit records remain pending even though their underlying was already sent to the borrower and included in the epoch settlement.

This is the direct credit-vault analogue of replacing an active auction contract after the auction has started: settlement state and pending-user accounting remain associated with the old contract, while the replacement contract controls the completion hook.

### Impact Explanation
All prefunded deposits for the epoch can be misallocated or permanently frozen.

If the replacement queue is attacker-controlled and reports the real pending prefunded amount, it receives the AA tranche shares minted for the original queue’s depositors. Those users lose the tranche position corresponding to their prefunded underlying.

If the replacement queue reports zero, is incompatible, or reverts, the original queue’s deposits are never processed. The users’ underlying may already have been prefunded to the borrower and accounted for in the epoch, while their queue deposits remain unclaimable. The affected amount is the full `epochPrefundedDeposits(nextEpoch)` balance pending in the original queue.

### Likelihood Explanation
The issue requires an authorized owner/manager call to `setEpochQueue` between prefunding and `stopEpochWithDuration`, but the function provides no protection against that ordering. The codebase explicitly identifies this ordering as unsafe, yet leaves it as an operational convention rather than an enforced invariant. [1](#0-0) 

An attacker does not need to make the privileged call. The attacker only needs to control or exploit the replacement queue selected by an operator transaction. Once replaced, the settlement path automatically sends the minted shares and processing callback to the replacement. [4](#0-3) 

### Recommendation
Track the queue responsible for the current prefunded deposits, or prevent replacement while settlement is pending.

At minimum:

```solidity
function setEpochQueue(address _epochQueue) external {
    _checkOnlyOwnerOrManager();

    if (epochQueue != address(0)) {
        _checkNotAllowed(
            IIdleCDOEpochQueuePrefunded(epochQueue)
                .prefundedDepositsToProcess() != 0
        );
    }

    epochQueue = _epochQueue;
}
```

A stronger design is to snapshot `epochQueue` when prefunding begins and use that snapshot in `_afterStopEpochWithDuration`. This prevents an administrative queue update from changing the contract that owns the pending deposit records.

Add a Foundry test beside `test/foundry/IdleCDOEpochVariantPrefunded.t.sol` using the existing fixture and helpers:

```solidity
contract ReplacementQueue is IIdleCDOEpochQueuePrefunded {
    IdleCDOEpochQueue public oldQueue;
    uint256 public processedAmount;

    constructor(IdleCDOEpochQueue _oldQueue) {
        oldQueue = _oldQueue;
    }

    function prefundedDepositsToProcess()
        external
        view
        returns (uint256)
    {
        return oldQueue.prefundedDepositsToProcess();
    }

    function epochPrefundedDeposits(uint256 epoch)
        external
        view
        returns (uint256)
    {
        return oldQueue.epochPrefundedDeposits(epoch);
    }

    function processPrefundedDeposits(uint256 amount) external {
        processedAmount = amount;
    }
}
```

Test sequence:

```solidity
function testPrefundedSharesCanBeRedirectedToReplacementQueue() external {
    uint256 amount = 1_000_000;
    address user = makeAddr("queued-user");

    // Existing fixture helper: user queues a deposit.
    _requestDepositWithUser(user, amount);

    uint256 requestEpoch = strategy.epochNumber() + 1;

    // Existing fixture helper: enter the period where queue deposits can be
    // prefunded to the borrower.
    _enterPrefundedWindow(PREFUNDED_DEPOSIT_WINDOW);

    // Prefund using the same public queue call used by the existing prefunded
    // fixture. At this point Q1 owns the pending deposit records.
    queue.prefundDeposits();

    assertEq(
        queue.epochPrefundedDeposits(requestEpoch),
        amount,
        "deposit was not prefunded"
    );

    // Replace the settlement queue before stopEpochWithDuration.
    ReplacementQueue replacement = new ReplacementQueue(queue);

    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(replacement));

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(
        0,
        0,
        cdoEpoch.epochDuration(),
        0
    );

    // Q2 received the shares minted for Q1's prefunded depositors.
    assertEq(
        replacement.processedAmount(),
        amount,
        "replacement queue did not receive minted shares"
    );

    // Q1 still believes its deposits are pending and never received its
    // settlement callback.
    assertEq(
        queue.epochPrice(requestEpoch),
        0,
        "original queue unexpectedly processed deposits"
    );
}
```

The exact prefunding helper name may differ in the local fixture, but the state transition is deterministic: prefund deposits into `queue`, overwrite `epochQueue`, call `stopEpochWithDuration`, and observe that `_afterStopEpochWithDuration` mints to and finalizes the replacement while the original queue remains unsettled.

  function _afterStopEpochWithDuration() internal override {
    address _queue = epochQueue;
    if (_queue == address(0)) return;

    IIdleCDOEpochQueuePrefunded _epochQueue = IIdleCDOEpochQueuePrefunded(_queue);
    uint256 _prefunded = _epochQueue.prefundedDepositsToProcess();
    if (_prefunded == 0) return;
    // A zero post-loss AA price cannot safely mint new shares into the same tranche token.
    _checkNotAllowed(priceAA == 0);

    // Prefunded deposits already reached the borrower, so they must join AA even if stop defaulted.
    // Mint tranche shares at the post-stop price and mirror the same amount in strategy tokens,
    // so the queue can later distribute shares to users at the epoch price.
    uint256 _prefundedMinted = _mintSharesAtCurrPrice(_prefunded, _queue, AATranche);
    IdleCreditVault(strategy).mintStrategyTokens(_prefunded);
    // Finalize the prefunded epoch in the queue by storing the epoch price and clearing state.
    _epochQueue.processPrefundedDeposits(_prefundedMinted);
