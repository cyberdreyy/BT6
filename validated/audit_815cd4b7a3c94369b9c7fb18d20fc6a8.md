## Title
Malicious operator/beneficiary can permanently freeze `staking_contract::distribute_internal`, trapping staker principal, rewards, and commission - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

## Summary
`distribute_internal` in `staking_contract.move` pays out every shareholder in `distribution_pool` (staker's dust, operator's commission, and any past-operator residuals) inside a single `while` loop that must run to completion before the function returns. [1](#0-0) 
Payment is done via `aptos_account::deposit_coins`, which can abort for a recipient that has (a) no registered `CoinStore`/primary store for the coin type and (b) has called `set_allow_direct_coin_transfers(false)` on their own account. [2](#0-1) 
Because Move transactions are atomic, one non-cooperative recipient inside this loop reverts the *entire* distribution, not just their own share — analogous to the reported `processWithdrawalQueue` bug where a single reverting receiver freezes the whole queue.

## Finding Description
`distribute_internal` is invoked by `distribute()`, `request_commission()`, and `switch_operator()`/`switch_operator_with_same_commission()` (the latter two force a distribution before changing operator). [3](#0-2) [4](#0-3) 

Inside the loop, `redeem_shares` mutates `distribution_pool` state and `aptos_account::deposit_coins` is called for the resolved recipient (the operator's shares are redirected to `beneficiary_for_operator`). [5](#0-4) 
`aptos_account::deposit_coins` only auto-registers a coin store if `can_receive_direct_coin_transfers(to)` is true; if the recipient has never registered for the coin and has explicitly set `allow_arbitrary_coin_transfers = false` via `set_allow_direct_coin_transfers`, the call aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. [6](#0-5) [7](#0-6) 

Since the operator (or a beneficiary set via `update_beneficiary_for_operator`) always holds an outstanding commission share entry in `distribution_pool` whenever commission has been requested/accrued, that address's cooperation is required for the loop to finish. An operator who deliberately disables direct-transfer acceptance for the coin used (and never registers a store for it) permanently blocks the `while` loop from completing — not just for their own commission entry but for every other shareholder queued in the same pool (staker dust, previous operators' residual distributions), because `redeem_shares`/`deposit_coins` for all entries happen inside one atomic transaction.

This mirrors the external report's root cause precisely: a single "reverting receiver" inside a payout loop that must fully succeed can DoS the whole payout mechanism. The comment at line 494-496 even acknowledges griefing risk from too many pending distributions but does not address a *permanently reverting* recipient. [8](#0-7) 

The vesting spec file explicitly flags this exact loop-abort blind spot as unverified/untested: [9](#0-8) 
`vesting::distribute` has the analogous unbounded `for_each_ref` payout loop over `grant_pool` shareholders, calling `aptos_account::deposit_coins` per shareholder, with the same atomicity property. [10](#0-9) 

## Impact Explanation
If the operator (or their designated beneficiary) refuses transfers, `distribute()`, `request_commission()`, and `switch_operator()` all revert permanently for that staking contract:
- The staker can never withdraw already-unlocked/inactive stake sitting in the stake pool via this contract (since `distribute_internal` is the only path that calls `stake::withdraw_with_cap` and pays out the staker's residual).
- The staker cannot even switch away from the malicious operator, because `switch_operator` also force-calls `distribute_internal` first.
- Commission owed to the operator itself also becomes permanently unclaimable, but crucially the staker's own principal/dust becomes non-recoverable through this contract as a side effect.

This is a permanent, non-recoverable loss of claim rights over stake balances (principal and rewards) for the staker, satisfying "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows."

## Likelihood Explanation
The precondition (an address that never registers a `CoinStore`/primary store and calls `set_allow_direct_coin_transfers(false)`) is trivially achievable by any unprivileged account controlling itself — no special role or governance access is required, only ordinary entry-function calls available to any signer. The only requirement to weaponize it against a third party is being selected as `operator`/`beneficiary` of someone else's `staking_contract`, which is a normal, expected role assignment in this module (stakers routinely delegate operation to third-party node operators they don't fully trust). I was not able to fully verify from the indexed code whether `coin::is_account_registered<AptosCoin>` treats accounts as pre-registered once migrated to the primary-fungible-store model (which could reduce/eliminate the "unregistered" precondition for `AptosCoin` specifically) — this needs to be checked directly in `coin.move`'s `is_account_registered`/`register` implementation, which was not fully retrievable through the index. The vulnerability is more clearly exploitable for non-APT `CoinType` staking contracts (if any are deployed) or for any operator address that has genuinely never interacted with AptosCoin before being assigned.

## Recommendation
- Make `distribute_internal`'s payout loop resilient to a single failing recipient: wrap each `deposit_coins` call so a failure is caught/skipped (e.g., re-buy the shares back for the recipient, or route failed payouts to an escrow the recipient can later claim) instead of letting one revert abort the whole distribution.
- Alternatively, decouple the staker's/other shareholders' payouts from the operator's/beneficiary's payout so a failure for one recipient does not block others, mirroring the withdrawal-queue remediation of introducing a "permissive" transfer mode that does not propagate reverts.
- Apply the same fix to `vesting::distribute`'s `for_each_ref` payout loop over `grant_pool` shareholders.

## Proof of Concept
1. Staker creates a `staking_contract` with `operator = O` via `create_staking_contract`. [11](#0-10) 
2. `O` (or an account `O` designates as beneficiary via `update_beneficiary_for_operator`) has never registered a `CoinStore`/primary store for the relevant coin, and calls `aptos_account::set_allow_direct_coin_transfers(O, false)`. [12](#0-11) 
3. Once commission accrues and becomes inactive/withdrawable, anyone calls `distribute(staker, O)` or `request_commission`; `distribute_internal` reaches `O`'s entry in `distribution_pool.shareholders()` and calls `aptos_account::deposit_coins(O, ...)`, which aborts because `O` is unregistered and has opted out of direct transfers. [5](#0-4) 
4. The whole transaction reverts every time it is retried, so neither the staker's dust nor commission can ever be distributed, and `switch_operator` (which also calls `distribute_internal`) is equally blocked. [3](#0-2)

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
