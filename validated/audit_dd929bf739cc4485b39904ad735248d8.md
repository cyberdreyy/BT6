### Title
Loss-adjusted epoch claims only clear the latest request epoch, letting earlier haircutted receipts pay out at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`pendingWithdraws` is an aggregate bucket that gets haircutted once via `lossRecoveryPriceByEpoch[epochNumber]` in `collectWithdrawFunds`, but `_claimLossAdjustedWithdrawRequest` only clears the per-epoch receipt recorded in `lastWithdrawRequest[_user]`. Any earlier-epoch receipt of the same user — which was part of the same haircutted `pendingBasis` — stays in `withdrawsRequests[_user]` and is then paid in full by `_claimFundedWithdrawRequest`, which is unlocked because `_clearWithdrawClaimForEpoch` resets `lastWithdrawRequest[_user]` to 0. The epoch-1 receipt is paid twice-valued: once implicitly inside the haircut basis, and again at par.

### Finding Description
The external bug is a refcount/`use`-counter accounting error: an aggregate counter gates teardown, but an object freed through one path keeps stale accounting alive. The analog lives in `IdleCreditVault`'s two-layer withdraw-receipt accounting:

- `requestWithdraw` stores the claim both in the aggregate `withdrawsRequests[_user]` and per epoch in `withdrawsRequestsByEpoch[_user][currentEpoch]`, and unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) .
- On a `stopEpochWithDuration` loss, `collectWithdrawFunds` computes one `lossRecoveryPrice` over the entire `pendingWithdraws` aggregate — i.e., every user's every pending epoch is haircutted together [2](#0-1) .
- At claim time, `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` first, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — only the user's *latest* request epoch [3](#0-2) .
- `_clearWithdrawClaimForEpoch` zeroes only `withdrawsRequestsByEpoch[_user][_claimEpoch]` for that one epoch and, crucially, resets `lastWithdrawRequest[_user] = 0`, disabling the `epochNumber <= lastWithdrawRequest[_user]` freshness gate [4](#0-3) .
- Control then falls into `_claimFundedWithdrawRequest`, which pays the remaining `withdrawsRequests[_user]` (the older epoch's receipt) at par via `_transferFundedClaim` [5](#0-4) .

The strategy only received `pendingToFund = pendingBasis - pendingLoss` from the borrower. Paying a haircutted receipt at par spends reserve that belongs to other claimants.

### Impact Explanation
An attacker who splits a withdrawal across two request epochs recovers `epoch1Amount * 1.0 + epoch2Amount * lossRecoveryPrice / RECOVERY_FULL` instead of `(epoch1Amount + epoch2Amount) * lossRecoveryPrice / RECOVERY_FULL`. The excess `epoch1Amount * (1 - lossRecoveryPrice/RECOVERY_FULL)` is directly stolen from the funded-claim reserve; subsequent honest claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls underflow on `_burn` or fail on insufficient underlying, permanently freezing the tail of the funded claims. With a 50% loss price, an attacker requesting equal amounts in two epochs extracts ~25% more than their fair share.

### Likelihood Explanation
Requires only a KYC-passed lender (explicitly in-scope) making two ordinary `requestWithdraw` calls in different epochs before a stop that realizes a loss via `stopEpochWithDuration`/`collectWithdrawFunds` — an honest-manager flow the protocol explicitly supports (`previewLossAdjustedWithdrawFunds`, `lossRecoveryPriceByEpoch`). No privileged misbehavior, no reentrancy, no timing race is needed; the missing invariant is purely accounting. Triggering depends on a borrower partial loss occurring while the attacker holds two pending epochs, which is plausible but not attacker-controlled, so likelihood is moderate.

### Recommendation
Track all epochs contributing to a user's pending basis, not just `lastWithdrawRequest`. Options:

- In `_claimLossAdjustedWithdrawRequest`, iterate/clear *all* of the user's `withdrawsRequestsByEpoch` entries that were pending at the loss epoch (e.g., store a per-user list of request epochs, or a `lossEpoch` range check), applying `lossRecoveryPrice` to the combined basis.
- Alternatively, record a per-user `lossAdjustedBasis` at the first loss-affected claim and only route the remainder to `_claimFundedWithdrawRequest` after subtracting it.
- Do not reset `lastWithdrawRequest[_user]` to 0 in `_clearWithdrawClaimForEpoch` while other per-epoch receipts remain; reset it to the next outstanding epoch instead.

    _startEpochAndCheckPrices(2);
    // stop with a realized loss: borrower funds only pendingToFund < pendingWithdraws
    uint256 pending = strategy.pendingWithdraws();           // covers BOTH requests
    uint256 funded = pending * 50e18 / 1e20;                 // 50% recovery price
    deal(underlying, borrower, totalDue);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
