### Title
APR0 withdraw requests permanently brick `stopEpoch` once APR is raised — temporary freeze of all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
An unprivileged KYC-passed lender who files a normal `requestWithdraw` while `unscaledApr == 0` creates an entry in `apr0TotalPrincipal`. If the (honest) manager later raises the APR before the epoch stops — a legitimate, ordinary configuration action — `prepareStopEpochWithApr0` unconditionally reverts with `NotAllowed`, so `stopEpoch` can never succeed while APR stays non-zero. All queued withdrawals (which require `epochNumber` to bump at `stopEpoch`) and all lender funds are frozen until APR is set back to 0.

### Finding Description
- `requestWithdraw` routes requests into the APR0 bucket when `unscaledApr == 0`, incrementing `apr0TotalPrincipal` via `_requestWithdrawApr0` (IdleCreditVault.sol:285-286).
- At epoch stop, the CDO calls `prepareStopEpochWithApr0`, which reverts `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` (IdleCreditVault.sol:502-508). The revert happens *before* `apr0TotalPrincipal` is cleared (line 540), so the bucket is never reset and the failure repeats on every `stopEpoch` call while APR is non-zero.
- There is no recovery path inside the function: no partial settlement, no forfeiture of the APR0 bucket, no per-request cleanup. The only escape is the manager lowering `unscaledApr` back to 0, which may be economically impossible if the borrower agreement was repriced.
- Because `epochNumber` only advances on a successful `stopEpoch`, the `epochNumber <= lastWithdrawRequest[_user]` gate in `_claimFundedWithdrawRequest` (IdleCreditVault.sol:326) blocks every pending claim, and no new epoch can start — the pool is wedged in "running" state past `epochEndDate`.

### Impact Explanation
Temporary freezing of all user funds (principal + yield) in the vault for at least one full epoch and until APR is restored to 0. If the APR change is contractual or the epoch duration is long, the freeze can approach permanent in practice. Quantified loss: the entire vault TVL plus `pendingWithdraws` is illiquid; pending withdraw receipts cannot be claimed at all.

### Likelihood Explanation
Requires only an unprivileged lender calling `requestWithdraw` during an APR-0 epoch (a free, griefing-cost-only action), sequenced around a legitimate manager APR update — exactly the kind of honest privileged call the threat model allows sequencing around. No malicious privileged role needed. The guard was added to protect APR0 interest accounting, but it converts a data-inconsistency into an availability failure rather than settling or expiring the bucket.

### Recommendation
Instead of reverting, handle the stale APR0 bucket inside `prepareStopEpochWithApr0`: e.g., settle APR0 principal at 0 interest (move `apr0TotalPrincipal` into per-user `settledPrincipal` at their `principalEpoch` rate, which is 0 if `apr0RateByEpoch` was never set) and clear `apr0TotalPrincipal`, so `stopEpoch` always proceeds. Alternatively, block APR increases in `setAprs` while `apr0TotalPrincipal != 0`, keeping the revert at configuration time where it is cheap to retry.

### Proof of Concept
```solidity
// Foundry, extending test/foundry/IdleCreditVault.t.sol setup
function testApr0RequestBricksStopEpochAfterAprRaise() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR = 0 epoch

    // attacker: KYC-passed lender deposits and requests withdraw while APR == 0
    uint256 mintedAA = idleCDO.depositAA(10_000 * ONE_SCALE);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    _forceLastEpochAprToZero();
    cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche)); // fills apr0TotalPrincipal

    _startEpochAndCheckPrices(1);

    // honest manager reprices APR upward mid-epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialApr, 0);

    // borrower funds repayment fully; epoch ends
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // stopEpoch reverts forever while APR != 0: apr0TotalPrincipal is never cleared
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    // repeated calls revert identically; claimWithdrawRequest stays gated by epochNumber
}
```

Note: I could not fully verify `setAprs` access control (manager vs. owner) and whether any deployment keeps APR immutable after the first epoch; if APR can never change once non-zero, the freeze becomes permanent rather than temporary, which only strengthens the finding. The core mechanism — the unrecoverable `NotAllowed` revert in `prepareStopEpochWithApr0` ordering — is directly confirmed at IdleCreditVault.sol:502-540.
