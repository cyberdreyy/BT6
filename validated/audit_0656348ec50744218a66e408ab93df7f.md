### Title
External Initiator credential can trigger job runs on arbitrary jobs by int ID because the spoofed run-role User bypasses the "EIs not allowed" check - (File: core/web/auth/auth.go, core/web/pipeline_runs_controller.go)

### Summary
`AuthenticateExternalInitiator` unconditionally injects a `*clsessions.User{Role: clsessions.UserRoleRun}` into the gin context under `SessionUserKey`, indistinguishable from a real logged-in user object. `PipelineRunsController.Create` relies on `auth.GetAuthenticatedUser(c)` returning `ok` to decide "only users (not EIs) may trigger runs via integer job IDs," but since the EI-authenticated request also satisfies that check, an EI credential can run any job by numeric ID, not just the job it was provisioned for.

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) authenticates the caller against `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, verifies against a specific `bridges.ExternalInitiator` record, and then does: [1](#0-0) 
This sets a synthetic `User` object with `UserRoleRun`, with no reference to which specific EI/job it belongs to, and stores it under the same `SessionUserKey` used for real authenticated dashboard/API-token users.

The only route wired with this middleware is: [2](#0-1) 
i.e. `POST /v2/jobs/:ID/runs`, guarded by `auth.RequiresRunRole`.

Inside `PipelineRunsController.Create`: [3](#0-2) 
The comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and the code attempts to enforce this via `_, isUser := auth.GetAuthenticatedUser(c)`. However, `GetAuthenticatedUser` simply type-asserts whatever object is stored under `SessionUserKey` — it cannot distinguish a real authenticated user from the synthetic run-role `User` object created by `AuthenticateExternalInitiator`. Because of this, `isUser` evaluates to `true` for an EI-authenticated request, and the intended restriction is bypassed: the EI can supply any int32 job ID and successfully call `prc.App.RunJobV2(ctx, jobID, nil)` for a job it has no relationship to, rather than being limited to (or rejected from) its own provisioned job.

Other `RequiresRunRole` endpoints (`/replay_from_block/:number`, `/find_lca`, `/lp_skip_to_block`, `/execute_capability`) are registered under the `authv2` group, whose middleware chain is `AuthenticateByToken`/`AuthenticateBySession` only — `AuthenticateExternalInitiator` is not part of that chain, so EI credentials cannot reach those endpoints. The reachable impact is confined to `/v2/jobs/:ID/runs`.

### Impact Explanation
An external initiator credential — intended to authorize triggering a single specific job — can instead trigger a pipeline run on any job in the node by supplying an arbitrary integer job ID, because the code's "EIs not allowed to use int IDs" guard is defeated by the shared `SessionUserKey`/`GetAuthenticatedUser` abstraction. This is an unauthorized-job-run / authorization-exactness violation: it lets a low-scope EI credential act outside its intended job scope (e.g. trigger jobs that move funds, write on-chain, or call external bridges tied to a different job), which matches the "unauthorized job run" bounty impact class. It does not, however, extend to unrelated `RequiresRunRole` endpoints like replay/LCA/capability execution, since those are gated by a different middleware chain that never accepts EI credentials.

### Likelihood Explanation
Precondition: attacker must hold a valid EI access key/secret for any external initiator registered on the node (a legitimately provisioned, low-scope credential). No other privilege is required. Exploitation is a single crafted `POST /v2/jobs/:ID/runs` request with the EI headers and an arbitrary target job's integer ID — fully repeatable and requires no timing/race conditions.

### Recommendation
Distinguish EI-derived pseudo-users from real authenticated users explicitly, e.g. by checking `auth.GetAuthenticatedExternalInitiator(c)` in `PipelineRunsController.Create` and rejecting/short-circuiting integer-ID job runs for EI-authenticated requests (restoring the documented "EIs not allowed" int-ID path), or by tagging the synthetic `User` with initiator identity and validating that the requested job ID is the one associated with that specific `ExternalInitiator` before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test:
1. Create two jobs, Job A (int ID `1`) and Job B (int ID `2`).
2. Register an `ExternalInitiator` with credentials tied only to Job A's webhook configuration.
3. Issue `POST /v2/jobs/2/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials (no session cookie, no API token).
4. Assert the middleware chain accepts the request (`auth.RequiresRunRole` passes because `Role == UserRoleRun`), `isUser` evaluates true in `PipelineRunsController.Create`, and `RunJobV2` is invoked for Job B — expected (buggy) result: HTTP 200 with a created pipeline run resource for Job B, despite the EI credential having no relationship to Job B.
5. Contrast with expected secure behavior: request should be rejected (403/422) since the EI is not authorized for Job B.
