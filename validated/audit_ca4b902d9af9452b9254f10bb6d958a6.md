### Title
ERC4626 liquidity starvation forces `stopEpoch` to permanently revert, freezing all lender funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` tries to recall idle liquidity from the configured ERC4626 vault during `stopEpoch`. When the vault's share position *nominally* covers the required shortfall (`convertToAssets` on shares) but the vault has no redeemable liquidity, `vault.withdraw` reverts and the hook reverts with `StopEpochVaultLiquidityUnavailable`. An unprivileged user of the vault's underlying market (an explicitly in-scope attacker class) can drain borrowable liquidity — an "ERC4626 liquidity move" — and keep `stopEpoch` reverting indefinitely, temporarily freezing the entire credit pool.

### Finding Description
In `ProgrammableBorrower.onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:239-253):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The guard `shortfall > _currentVaultAssets()` only bypasses the withdrawal when the vault position is *economically* insufficient. For liquidity-managing ERC4626 vaults (e.g., MetaMorpho-style vaults that lend assets into money markets), `convertToAssets` reflects total assets under management, not withdrawable liquidity. A vault user can borrow all available liquidity from the underlying market, leaving the share valuation intact but making every `withdraw` revert.

`IdleCDOEpochVariant._stopEpoch` propagates hook reverts rather than catching them (contracts/IdleCDOEpochVariant.sol:395-403), so `stopEpoch` — the only path that moves the pool out of a running epoch — reverts on every attempt. During a running epoch, deposits and withdrawals are disabled and pending withdraw requests can only be fulfilled at epoch stop, so all lender funds are frozen for as long as the attacker keeps the market drained.

### Impact Explanation
Temporary freezing of the full pool TVL (all lender principal plus epoch interest) for a duration fully controlled by the attacker. The attacker only pays the underlying market's borrow interest on the drained amount. No privileged role can bypass the freeze cheaply: `emergencyExitVault` calls the same `vault.redeem`/`withdraw` path that reverts, and `setVault` is blocked because `vault.balanceOf(address(this)) != 0`. Recovery requires either the attacker's loans being repaid/liquidated or owner intervention (e.g., `rescueTokens` on vault shares), neither of which is guaranteed within any bound. This is the direct analog of the Flowise bug class: externally influenced data (the vault's real liquidity) is injected into a trusted execution path whose only validation (`_currentVaultAssets()` coverage check) passes while the operation still fails, escaping the intended try/catch sandbox and aborting the epoch state machine.

### Likelihood Explanation
Requires no privileged role — any user who can borrow from the vault's underlying market. The window is deterministic: `stopEpoch` can only be called after `epochEndDate`, so the attacker knows exactly when to keep liquidity drained. Cost is bounded by market borrow rates on the vault's asset, and many such markets allow near-total utilization by a single borrower.

### Recommendation
Handle vault illiquidity as a graceful failure rather than a revert: check redeemable liquidity (e.g., `vault.maxWithdraw(address(this))` or `maxRedeem`) before attempting the withdrawal, and when coverage exists but liquidity doesn't, return a distinct failure value so `IdleCDOEpochVariant` can route to `_handleBorrowerDefault` or a partial-settlement path instead of reverting. Alternatively, cap the withdrawal to `maxWithdraw` and let the subsequent `transferFrom` shortfall drive the existing default flow.
