### Title
Multisig requests execute using confirmations from members already removed via `DeleteKey`/`DeleteMember`, allowing a request to pass below the effective live-member threshold - ([File: multisig/src/lib.rs] / [File: multisig2/src/lib.rs])

### Summary
`confirm()` in both `multisig/src/lib.rs` and `multisig2/src/lib.rs` counts confirmations purely from the `confirmations: HashSet` stored against a `request_id`. When a key/member is removed via a `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`) action, the code only purges *requests originated by* that key/member — it does not purge confirmations that the removed key/member had already cast on *other, still-pending* requests. This mirrors the reported bug class: a stateful flag (`safeBeetle` in the report; `confirmations` set here) is set once and later trusted for a decision (asset custody / request execution) without re-validating that the condition which justified trusting it (staking ownership / current membership) still holds at the time it is relied upon.

### Finding Description
In `multisig/src/lib.rs`, `confirm()` computes readiness purely from the stored set: [1](#0-0) 

`DeleteKey`'s cleanup logic in `execute_request` only removes requests whose `signer_pk` (the *creator*) equals the deleted key; it does not scan `confirmations` for occurrences of that key on other requests: [2](#0-1) 

The same pattern exists in `multisig2/src/lib.rs`: `delete_member()` only removes requests created *by* the removed member, not confirmations *cast by* that member on other pending requests, and `confirm()` again just checks `confirmations.len() as u32 + 1 >= self.num_confirmations`: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`confirmations counted toward threshold == confirmations from currently live members`

But the code allows:
`confirmations counted toward threshold ⊇ confirmations from live members ∪ confirmations from members removed after confirming`

Because a stale confirmation from a since-removed member is never invalidated, a pending request can reach `num_confirmations` using fewer *live* member confirmations than the configured threshold requires.

### Impact Explanation
This falls under the Critical impact category explicitly listed in scope: "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` action can be executed with fewer genuine, currently-authorized approvals than `num_confirmations` mandates, because leftover confirmations from removed keys/members still count. This breaks the fundamental K-of-N custody guarantee of the multisig, potentially allowing funds to be moved or contract state/keys to be changed without the intended quorum of current signers.

### Likelihood Explanation
Exploitation requires: (1) a pending request with fewer than `num_confirmations` confirmations, one of which belongs to a member/key that is later removed via a separate, properly-authorized `DeleteKey`/`DeleteMember` request; and (2) a sufficient number of remaining live confirmations from other members to push the stale total over the threshold. This is a realistic operational sequence in any long-lived multisig with membership churn (turnover of employees/validators/keys) combined with slow-to-confirm pending requests — not a contrived edge case, and requires no special privilege beyond being one of the (still legitimate) confirming members who ends up executing the request; no code redeploy or foundation intervention is needed.

### Recommendation
When removing a key (`DeleteKey`) or member (`DeleteMember`), scan all pending requests' `confirmations` sets (not just requests *created by* that key/member) and strip the removed identity from them, or alternatively re-validate at `confirm()`/execution time that every entry in the `confirmations` set still corresponds to a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 5 members `A, B, C, D, E` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R1` (e.g., `Transfer` of contract funds to an attacker-controlled account).
3. `B` calls `confirm(R1)` → `confirmations = {B}` (1 < 3, not yet executed).
4. `C` calls `confirm(R1)` → `confirmations = {B, C}` (2 < 3, not yet executed).
5. Separately, members `A, D, E` (3 live confirmations, meeting threshold) submit and confirm a `DeleteMember` request removing `B` and a second `DeleteMember` request removing `C`. `delete_member()` only removes requests *created by* `B`/`C`; `R1` (created by `A`) is untouched, and `B`'s/`C`'s stale entries remain in `R1`'s `confirmations` set.
6. Now live members are `A, D, E` (3 total), and `num_confirmations` is still `3` — theoretically requiring unanimous live-member agreement.
7. `D` (or `A`) calls `confirm(R1)`. The check `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `2 + 1 = 3 >= 3` and executes the `Transfer`, even though only `D`'s confirmation came from a currently valid member — `B` and `C`'s stale confirmations (from removed members) satisfied the rest of the threshold.
8. Result: funds are transferred out with only 1 out of 3 required *live* member approvals, violating the K-of-N custody guarantee.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
