# Vulnerability Analysis

The closest analog to CVE-2017-2924 (a length/bounds desync in `read_legacy_biff` causing memory corruption via a stale aggregate) exists in `IdleCDOEpochQueue.processWithdrawalClaims`: the queue's per-epoch `epochPendingClaims[_epoch]` accounting is silently rebased against the vault's *global, multi-epoch* `withdrawsRequests[queue]` aggregate. A bounds desync between per-epoch basis and aggregate basis lets one epoch's claims absorb funds belonging to a later epoch.

### Title
Stale-epoch receipt aggregation lets an earlier withdrawal epoch over-claim and drain later epochs' queued funds - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
`processWithdrawalClaims(_epoch)` measures the received payout via a balance delta over `_cdo.claimWithdrawRequest()`. In `IdleCreditVault._claimFundedWithdrawRequest`, the claim pays out the user's *entire* `withdrawsRequests[_user]` aggregate — which, for the queue contract, accumulates receipts from every processed epoch. If `processWithdrawalClaims` for epoch N runs after `processWithdrawRequests` for epoch N+1, the call returns both epochs' receipts, and `epochWithdrawPrice[N]` is rebased upward (`epochWithdrawPrice[N] * _received / _pending`), while epoch N+1 keeps its original price but its underlying has been drained. ### Finding Description
1. `requestWithdraw` in the vault adds `_amount` to both `withdrawsRequestsByEpoch[user][epoch]` and the aggregate `withdrawsRequests[user]` (`IdleCreditVault.sol:292-293`).
2. `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` in full and zeroes it, gated only by `epochNumber > lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326-349`). There is no per-epoch claim bound — the claim amount is whatever the aggregate holds at claim time.
3. The queue treats the balance delta as belonging solely to `_epoch` and rebases `epochWithdrawPrice[_epoch]` to `price * _received / epochPendingClaims[_epoch]` (`IdleCDOEpochQueue.sol:352-357`).
4. The 1-epoch-wait guard does not prevent the desync: `lastWithdrawRequest[queue]` is overwritten each time `processWithdrawRequests` runs (`IdleCreditVault.sol:282`), so once the vault's `epochNumber` advances past the later request epoch, a single claim sweeps all pending receipts.

Broken invariant: one epoch receipt, one epoch payout. Funds credited to epoch N+1's claimants are paid into epoch N's price, breaking `epochWithdrawPrice` integrity and solvency of queued claims.

### Impact Explanation
Direct theft / insolvency. Epoch-N withdrawers (any KYC-passing tranche holder) claim at an inflated `epochWithdrawPrice[N]` and receive underlying that belongs to epoch N+1 claimants. Epoch N+1 retains its nominal `epochWithdrawPrice[N+1]` and `epochPendingClaims`, but the queue's balance was drained — late claimants' `claimWithdrawRequest(N+1)` calls revert on `safeTransfer` (permanent freezing of unclaimed yield, up to the full epoch N+1 pending amount). Loss equals the mispriced excess: `received - pending`, i.e. an entire epoch's withdraw basis can be redirected.

### Likelihood Explanation
Requires only an honest sequencing quirk: manager calls `processWithdrawRequests` for epoch N+1 before calling `processWithdrawalClaims(N)` — plausible whenever instant-withdraw and normal epochs interleave (the contract explicitly supports mixed instant/normal epochs via `isEpochInstant`). The exploiter is an ordinary epoch-N withdrawer; no privileged collusion needed. The `_received != _pending` rebase path was designed for APR-0 rounding differences, so the over-receipt branch is exercised by design, not reverted.

### Recommendation
Bound the claim to the epoch's basis. Either (a) track and claim only `epochPendingClaims[_epoch]` by adding a per-epoch claim path in `IdleCreditVault` (e.g., `_clearWithdrawClaimForEpoch` semantics limited to `_claimEpoch`), or (b) enforce `processWithdrawalClaims(epoch)` for all outstanding epochs before `processWithdrawRequests` can run again (assert the queue holds no unclaimed funded receipts), or (c) revert/ignore `_received > _pending` and isolate the excess.

### Proof of Concept
Foundry fork sketch (extends `test/foundry/IdleCDOEpochQueue.t.sol` harness):

```solidity
// epoch N: user1 requests withdraw via queue
_requestWithdrawWithUser(user1, tranches1);
_stopCurrentEpoch();              // vault epochNumber = N
queue.processWithdrawRequests();  // withdrawsRequests[queue] = amtN, epochPendingClaims[N] set
// epoch N+1: user2 requests withdraw
cdoEpoch.startEpoch();
_requestWithdrawWithUser(user2, tranches2);
_stopCurrentEpoch();              // vault epochNumber = N+1
queue.processWithdrawRequests();  // withdrawsRequests[queue] = amtN + amtN+1
// delayed claim for epoch N sweeps BOTH epochs' receipts
queue.processWithdrawalClaims(N); // _received = amtN + amtN+1 > epochPendingClaims[N]
// epochWithdrawPrice[N] now inflated ~2x; user1 over-claims
queue.claimWithdrawRequest(N);    // receives share of amtN+1
// epoch N+1 users: claimWithdrawRequest(N+1) reverts — queue underfunded
vm.expectRevert();
queue.claimWithdrawRequest(N + 1);
```

Note: if `processWithdrawRequests`/`processWithdrawalClaims` ordering is enforced elsewhere such that a later epoch's requests can never be recorded while prior claims are pending, the desync is unreachable — verification requires running the sequence against the deployed variant, since the queue gates only on the `pendingClaims` flag, which is cleared by `processWithdrawalClaims` and does not distinguish epochs.
