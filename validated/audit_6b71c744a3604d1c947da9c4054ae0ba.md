### Title
CORS wildcard origin bypass due to missing dot-boundary check in `isAllowedOrigin` suffix match - ([File: core/services/gateway/network/httpserver.go])

### Summary
`isAllowedOrigin` implements wildcard origin matching (`*.remix.com`) using `strings.HasSuffix(originHost, allowedHost)` without enforcing a dot boundary before the suffix. This allows attacker-controlled origins such as `evilremix.com` to satisfy the suffix check against an allowed wildcard `*.remix.com`, causing the gateway to reflect the attacker's `Origin` header into `Access-Control-Allow-Origin`.

### Finding Description
In `httpServer.isAllowedOrigin` [1](#0-0) , after stripping the `*.` prefix from an allowed wildcard entry, the code checks `strings.HasSuffix(originHost, allowedHost)`. Because `HasSuffix` performs a raw string suffix comparison with no requirement that the character preceding the match be a `.` (domain label boundary), any origin host that merely ends with the allowed suffix passes — not just true subdomains. For example, with an allowed origin of `*.remix.com`, the allowed suffix becomes `remix.com`; the attacker origin `evilremix.com` (no dot before `remix.com`) also ends with `remix.com` and is incorrectly treated as a subdomain match.

This check is invoked directly from `handleRequest` [2](#0-1) , which reflects the raw `Origin` header verbatim into `Access-Control-Allow-Origin` whenever `isAllowedOrigin` returns true, with no further validation or normalization. There is no allowlist re-verification, no exact-match enforcement, and no other middleware guarding this path — CORS is the sole gate for cross-origin trust here.

An unauthenticated attacker fully controls the `Origin` header sent by their own malicious web page (browsers set `Origin` automatically to the page's own origin, but an attacker who registers a domain like `evilremix.com` controls that value entirely). No credentials or node access are required to trigger this; the bug is purely in server-side string matching logic reachable pre-authentication (before body reading, JWT extraction, or `ProcessRequest`).

### Impact Explanation
This is a cross-origin isolation bypass: a domain never intended to be trusted (e.g. `evilremix.com`, `notremix.com.attacker.io` is not caught, but `evilremix.com` for `*.remix.com` is) is granted the same CORS trust as legitimate subdomains of `remix.com`. Because `Access-Control-Allow-Headers: Content-Type` is also granted, browser-based cross-origin `fetch`/`XHR` calls from the attacker's page to the gateway can succeed and have their responses read by attacker JavaScript when a victim (who is authenticated to the gateway via a bearer token accessible to page JS, e.g. stored by a legitimate dApp/plugin in a way readable across same-eTLD+1-looking domains) is lured to visit the attacker's page. This corresponds to a cross-user response confusion / origin-isolation bypass class issue, though its severity is bounded by the fact that no `Access-Control-Allow-Credentials` header is set, so browser-managed credentials (cookies) are not exposed — the risk is limited to scenarios where the client attaches bearer tokens via JS rather than cookies, and to phishing-style domain-squatting scenarios (registering `evilremix.com`/`fakeremix.com` style domains to impersonate a trusted partner subdomain).

### Likelihood Explanation
Exploitability requires only: (1) the gateway operator has configured a wildcard `CORSAllowedOrigins` entry such as `*.remix.com`, and (2) the attacker registers/controls a domain ending in that suffix without a dot boundary (e.g. `evilremix.com`). Both are realistic — wildcard subdomain allowlisting is a common configuration pattern, and domain squatting near a trusted brand name is cheap and common. No authentication, special role, or node access is needed to trigger the request itself. The confirmed unit-testable bug (`strings.HasSuffix` without boundary check) is deterministic and 100% repeatable given the described configuration.

### Recommendation
Fix the wildcard match in `isAllowedOrigin` at core/services/gateway/network/httpserver.go:169-175 to require a `.` boundary immediately preceding the suffix, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedSuffix := allowedHost[1:] // keep leading dot: ".remix.com"
    if strings.HasSuffix(originHost, allowedSuffix) {
        return true
    }
}
```
This ensures `evilremix.com` (no dot before `remix.com`) is rejected while `sub.remix.com` (dot-delimited) is accepted.

### Proof of Concept
Add a table-driven Go unit test for `isAllowedOrigin` in `core/services/gateway/network/httpserver_test.go`:
```go
func TestIsAllowedOrigin_WildcardBoundary(t *testing.T) {
    s := &httpServer{
        config: &HTTPServerConfig{CORSAllowedOrigins: []string{"https://*.remix.com"}},
        lggr:   logger.Test(t),
    }
    assert.True(t, s.isAllowedOrigin("https://sub.remix.com"))   // legit subdomain
    assert.False(t, s.isAllowedOrigin("https://evilremix.com"))  // should be rejected, currently passes due to bug
    assert.False(t, s.isAllowedOrigin("https://notremix.com"))   // should be rejected
}
```
Before the fix, `isAllowedOrigin("https://evilremix.com")` returns `true`, demonstrating the boundary bug; after applying the recommended fix it returns `false`.
