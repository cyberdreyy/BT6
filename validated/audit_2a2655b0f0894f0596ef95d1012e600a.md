## Analog Identified [1](#0-0) [2](#0-1) 

### Title
Account authority can front-run an admin `MarginfiAccountSetFreeze` (or `SetAccountFreeze` for `transfer_to_new_account_pda`) with `transfer_to_new_account`/`transfer_to_new_account_pda` to evade freeze/seizure controls - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` are permissionless-to-the-account-authority instructions that migrate all balances from an existing `MarginfiAccount` to a brand-new account, disabling the old one. The only frozen-state check is a snapshot of the *current* on-chain flag at execution time, with no mechanism to prevent racing an admin's concurrent freeze transaction. This mirrors the `rotateNodeRunnerOfSmartWallet` frontrun class: a party subject to an admin's protective/punitive state change can observe the pending transaction and race it to escape the intended restriction before it lands.

### Finding Description
`SetAccountFreeze`/`marginfi_account_set_freeze` is the admin-only mechanism used "for compliance, investigations, or protecting accounts in unusual situations," and once frozen, "the account authority is blocked from all operations" and "only the group admin can operate on the account (e.g. to withdraw or rebalance)" [3](#0-2) .

However, `TransferToNewAccount`/`TransferToNewAccountPda` are called by the account `authority` (not the admin), and only check the frozen flag as it exists at the moment the transaction executes: [1](#0-0) 

The migration copies all balances into a brand-new account (keypair or PDA) under a completely unchecked `new_authority` (`/// CHECK: WARN: New authority is completely unchecked`) and disables the old account: [4](#0-3) [5](#0-4) 

Because Solana transaction ordering allows any signer to observe pending transactions and submit a competing one that lands first, an account authority who anticipates (or observes in the mempool) an admin's `marginfi_account_set_freeze(frozen: true)` transaction targeting their account can front-run it with `transfer_to_new_account`/`transfer_to_new_account_pda`. This is functionally identical to the report's PoC: the malicious/targeted actor rotates/migrates their position to a fresh, unrestricted account before the admin's remediation transaction executes. When the admin's freeze transaction subsequently lands, it succeeds against the old account, but that account is now `ACCOUNT_DISABLED` with a zeroed `lending_account` — freezing it has no practical effect, since the actor's positions have already moved to a new, unfrozen account they fully control.

### Impact Explanation
Freeze is the protocol's only tool for compliance/seizure/investigation actions against a specific account [6](#0-5) . An account holder under investigation (e.g., holding stolen/sanctioned funds) can defeat this control entirely by racing the freeze transaction with a migration, relocating all collateral/debt positions to a new account (potentially under a different authority they control) that is completely outside the admin's freeze target. This is an unauthorized bypass of an intended security/compliance control with direct financial consequence: funds the admin intended to lock down remain fully liquid and controllable by the original bad actor.

### Likelihood Explanation
The account authority is by definition capable of monitoring transactions targeting their own account (mempool/leader schedule visibility on Solana is common practice for sophisticated/malicious actors), and only needs to submit `transfer_to_new_account` with a higher priority fee or faster inclusion than the admin's freeze transaction. No special privileges are required beyond being the account's own authority — the same actor the freeze is meant to restrict.

### Recommendation
Add a check in `TransferToNewAccount`/`TransferToNewAccountPda` (and any similar migration path) that also validates against a "pending freeze" or, more directly, make freeze immediately and atomically effective by having the admin action set a flag checked synchronously, or alternatively require an admin-imposed cooldown/lock before any user-initiated migration is allowed once an account is flagged for review. At minimum, consider giving the admin the ability to pause the migration instruction pathway independently (e.g., a `MIGRATION_LOCKED` flag settable by the same admin authority that can freeze), so an admin intending to freeze a suspicious account can lock migrations first.

### Proof of Concept
1. Admin observes suspicious activity on `marginfi_account_A` (authority = attacker) and submits `marginfi_account_set_freeze(frozen: true)` targeting `marginfi_account_A`.
2. Attacker (as `authority` of `marginfi_account_A`) observes this transaction in-flight and submits `transfer_to_new_account` (or `transfer_to_new_account_pda`), naming a fresh `new_authority`/`new_marginfi_account`, with a higher priority fee to ensure it lands first.
3. Attacker's transaction executes: `finalize_migrated_old_account` sets `ACCOUNT_DISABLED` and zeroes `lending_account` on `marginfi_account_A`, while all balances now live on `new_marginfi_account` under `new_authority` — an account the admin never targeted for freeze.
4. Admin's `marginfi_account_set_freeze` transaction subsequently lands and sets `ACCOUNT_FROZEN` on `marginfi_account_A`, but this account is now empty and disabled — the freeze has no effect on the attacker's actual funds, which remain fully accessible via `new_marginfi_account`.

```rust
/// Admin-only instruction to toggle `ACCOUNT_FROZEN` on a marginfi account.
///
/// Behavior:
/// - When frozen, the account authority is blocked from major actions (borrow/deposit/withdraw/repay/transfer/etc.) with `AccountFrozen`.
/// - The group admin retains access to operate the account while frozen (for remediation/seizure).
/// - Setting `frozen = false` clears the flag and returns control to the authority under normal auth rules.
pub fn set_account_freeze(ctx: Context<SetAccountFreeze>, frozen: bool) -> MarginfiResult {
    let group = ctx.accounts.group.load()?;
    check_eq!(
        group.admin,
        ctx.accounts.admin.key(),
        MarginfiError::Unauthorized
    );
    let mut marginfi_account = ctx.accounts.marginfi_account.load_mut()?;
    if frozen {
        marginfi_account.set_flag(ACCOUNT_FROZEN, true);
    } else {
        marginfi_account.unset_flag(ACCOUNT_FROZEN, true);
    }
    marginfi_account.last_update = Clock::get()?.unix_timestamp as u64;
```

```markdown
## Special Account States

### Frozen Accounts

The group admin can freeze any individual user account. When frozen:
- The account's authority is blocked from all operations.
- Only the group admin can operate on the account (e.g. to withdraw or rebalance).
- The account remains frozen until explicitly unfrozen by the admin.

This is used for compliance, investigations, or protecting accounts in unusual situations.
```
