### Title
APR0 withdraw requests permanently wedge `stopEpoch` if the manager raises APR mid-epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The IronBank report describes a privileged parameter change (`setCreditLimit`) that silently reclassifies an existing account — turning a credit account into an ordinary one, which then becomes subject to repay/liquidation of debt it could never repay. The analog in idle-tranches is the APR=0 withdraw-request bucket in `IdleCreditVault`: a withdraw request's accounting class (APR0 vs. normal) is fixed at request time by the current `unscaledApr`, but `prepareStopEpochWithApr0` later *reverts* if `unscaledApr != 0` while a live APR0 principal bucket exists. An unprivileged KYC-passed lender can plant an APR0 receipt, and any subsequent honest APR increase by the manager (via `setApr`/`setAprsWithBuffer`, which are directly callable by `manager`) reclassifies the epoch such that `stopEpoch` can no longer execute — freezing all LP funds until the APR is reverted to 0.

### Finding Description
- `requestWithdraw` records a receipt into the APR0 bucket only when `unscaledApr == 0` at request time: `_requestWithdrawApr0` increments `apr0Users[_user].principal` and the global `apr0TotalPrincipal` (contracts/strategies/idle/IdleCreditVault.sol:285-295, 567-577).
- At epoch end, `IdleCDOEpochVariant._stopEpoch` calls `IdleCreditVault.prepareStopEpochWithApr0`, which contains:
  ```solidity
  if (unscaledApr != 0) {
    revert NotAllowed();
  }
  ```
  guarded only by the fast-path `if (_principal == 0) return` (IdleCreditVault.sol:502-508).
- `setApr`/`setAprsWithBuffer` are callable directly by `manager` (not only by the CDO inside `stopEpochWithDuration`): `if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed()` (IdleCreditVault.sol:225-235).
- So the lifecycle is: epoch runs at `unscaledApr == 0` → lender calls `IdleCDOEpochVariant.requestWithdraw` → `apr0TotalPrincipal > 0` → manager later raises `unscaledApr` mid-epoch (a routine, permitted rate update for the same epoch) → `stopEpoch`/`stopEpochWithDuration` now always revert in `prepareStopEpochWithApr0` → the epoch can never close while `apr0TotalPrincipal != 0` and `unscaledApr != 0` hold simultaneously. Note that `apr0TotalPrincipal` is only zeroed inside the reverting function itself (line 540), so the wedge persists.

This mirrors the external bug exactly: a legitimate state change (APR update / credit-limit reduction) applied after positions were opened reclassifies those positions and breaks the settlement path that assumed the old class.

### Impact Explanation
All LP principal and yield in the CDO are frozen: `stopEpoch` reverting means `epochNumber` never increments, `pendingWithdraws` are never funded by the borrower, no claims (`claimWithdrawRequest`, `claimInstantWithdrawRequest`) can proceed, and new epochs cannot start. Recovery requires the manager to notice and set `unscaledApr` back to 0 before stopping the epoch — i.e., it is a temporary freeze, but one the protocol cannot resolve without an emergency parameter rollback, and during which the attacker can re-arm the wedge cheaply each buffer period (deposit → request withdraw while APR is 0). There is no direct fund theft; impact is temporary freezing of the entire pool's TVL.

### Likelihood Explanation
- Attacker requirements are minimal: any KYC-passed wallet (`isWalletAllowed`) with a small AA deposit can create a nonzero `apr0TotalPrincipal` with a dust-size `requestWithdraw` during an APR0 epoch.
- The trigger is an honest, permitted manager action (`setApr`/`setAprsWithBuffer`) taken while the receipt is pending — the rules allow sequencing around honest privileged calls. The vulnerability is the contract's own reclassification logic, not manager malice.
- Caveat / uncertainty: if deployments only ever change APR through `stopEpochWithDuration` (which zeroes the bucket inside `_stopEpoch` before `_setScaledApr` sets the new rate at IdleCDOEpochVariant.sol:520-546), the wedge window may be rare; it materializes whenever a manager adjusts APR for a live epoch, which the code explicitly supports ("If manager manually set apr from here...", IdleCreditVault.sol:222-224).

### Recommendation
Do not couple pending APR0 settlement to the *current* `unscaledApr`. Options:
- In `prepareStopEpochWithApr0`, settle the APR0 bucket using the APR that was in effect when the requests were recorded (store the request-epoch APR alongside `apr0RateByEpoch`/`principalEpoch`), instead of reverting when `unscaledApr != 0`.
- Alternatively, snapshot `unscaledApr` into `apr0Users`/the bucket at request time and treat a mid-epoch APR change as closing the bucket pro-rata, so `stopEpoch` can always proceed.
- At minimum, prevent `setApr`/`setAprsWithBuffer` from moving `unscaledApr` off 0 while `apr0TotalPrincipal != 0` (the same guard the IronBank report recommended: disallow the state change while an incompatible position exists).

### Proof of Concept
```solidity
// Foundry fork-style PoC (scaffold against existing test harness in test/foundry/IdleCreditVault.t.sol)
function testApr0PendingRequestWedgesStopEpochAfterAprRaise() external {
    // Setup: APR0 epoch running, attacker is a KYC'd AA lender
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);          // unscaledApr = 0
    idleCDO.depositAA(10_000 * ONE_SCALE);                      // attacker deposit (whitelisted)
    _startEpochAndCheckPrices(0);

    // Attacker plants an APR0 withdraw receipt (dust is enough)
    uint256 trancheBal = IERC20(AAtranche).balanceOf(address(this));
    cdoEpoch.requestWithdraw(trancheBal / 1000, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // Honest manager raises APR mid-epoch — permitted by setApr/setAprsWithBuffer
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e18, 30 days);  // unscaledApr != 0

    // Epoch end: stopEpoch can never execute — prepareStopEpochWithApr0 reverts NotAllowed
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, type(uint256).max >> 2);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);
    // All pendingWithdraws unfunded; claimWithdrawRequest reverts (epochNumber unchanged);
    // pool frozen until manager reverts unscaledApr to 0.
}
```
