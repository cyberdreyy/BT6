### Title
Stale Confirmations From Deleted Multisig Members Allow Requests To Execute Below The Live-Member Threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
The multisig contracts (`multisig` and `multisig2`) let a request accumulate confirmations from members/keys, and execute the request once `confirmations.len() + 1 >= num_confirmations`. When a member/key is removed via `DeleteMember`/`DeleteKey`, the code only purges *requests originally created by* that member, but never scans other pending requests to strip a confirmation the removed member had already cast as a co-signer. A stale confirmation from a now-removed member therefore continues to count toward the threshold, letting a request execute with fewer live, authorized members than `num_confirmations` requires.

### Finding Description
`confirm()` counts entries in the per-request `confirmations` set against `self.num_confirmations` to decide whether to execute a request: [1](#0-0) 

Membership removal is handled by `delete_member` (multisig2) / the `DeleteKey` action (multisig1). Both only remove *requests whose creator (`member`/`signer_pk`) equals the removed member*, and clear `num_requests_pk` for that member — they never look at the `confirmations` sets of *other* pending requests that the removed member may have already confirmed: [2](#0-1) [3](#0-2) 

This breaks the intended equality `confirmations counted == confirmations by currently-live members`. A request `R` created by member `A` and already confirmed by member `B` keeps `B`'s confirmation entry in `self.confirmations[R]` even after `B` is removed from `self.members` via a legitimate `DeleteMember`/`DeleteKey` execution. `current_member()` and `assert_valid_request()` only gate *new* actions (`add_request`, `confirm`, `delete_request`) by membership — they never re-validate confirmations already stored on a pending request: [4](#0-3) [5](#0-4) 

As a result, a subsequent legitimate confirmation from a live member `C` can push `confirmations.len() + 1` to `num_confirmations`, causing `execute_request` to run the transaction, even though only `A` and `C` are still live/authorized members — `B`'s stale confirmation is being counted as if `B` still endorses the action.

### Impact Explanation
This directly matches the "Critical" impact class of a multisig request executed below the threshold of live/authorized signers. In a K-of-N multisig, the security guarantee is that any executed action was approved by K *currently trusted* parties. Here, an action can execute with a stale approval from a party the organization has deliberately removed (e.g., an employee who left, or a key believed compromised and revoked). Any request type is affected, including `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, and `DeleteMember` itself — so funds can move, or a malicious key/member added, using a confirmation that no longer reflects a valid authorizer.

### Likelihood Explanation
The precondition is realistic and not attacker-privileged beyond being (or having been) an ordinary multisig member: a member confirms a pending request, and is later removed (routine key rotation/offboarding, or removal after compromise) without anyone noticing/cleaning the still-pending request the removed member had partially confirmed. The remaining members, expecting the threshold to require live signers, complete confirmation unaware a stale, revoked confirmation is still counted. No special privilege or malicious deployment is required — only that a member happens to leave/be revoked while having outstanding partial confirmations, which is a normal and even encouraged multisig workflow (confirm-then-rotate-keys).

### Recommendation
When executing `DeleteMember`/`DeleteKey`, scan **all** pending requests' `confirmations` sets (not just requests the member created) and remove the deleted member's/key's entry from each, in addition to purging requests it created. Alternatively, revalidate at `confirm()`/`execute_request()` time that every entry in `confirmations` still corresponds to a current member of `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(Transfer{...})` → request `R` has 1 confirmation (`A`).
3. `B` calls `confirm(R)` → `R` now has 2 confirmations (`A`, `B`); threshold (3) not met, so `R` stays pending.
4. The organization legitimately executes `DeleteMember{member: B}` (requires 3 confirmations from `A, C, D`, all live) because `B`'s key/account is being revoked. This calls `delete_member`, which removes `B` from `self.members` and removes only requests *created by* `B` — `R` (created by `A`) is untouched, and `R`'s confirmations set still contains `B`.
5. `C` (a live member) calls `confirm(R)`. `confirmations.len() (2) + 1 >= num_confirmations (3)` is true, so `execute_request` fires the `Transfer` immediately.
6. Result: `R` executed with confirmations from `A`, `B` (removed), `C` — only 2 currently-live members actually authorized it, yet the K=3 threshold check passed, because the stale confirmation from removed member `B` was never purged. [6](#0-5) [7](#0-6)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
