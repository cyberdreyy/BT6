### Title
Blacklisted `feeReceiver`/`owner` on a blacklistable underlying bricks deposits, withdrawal requests and epoch transitions via unsolicited `_skimDonatedAssets` push-transfers - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOCreditVault` and `IdleCDOEpochVariant` push the pool's underlying token (which can be a blacklistable ERC20 such as USDC/USDT) to the privileged `feeReceiver` and `owner()` inside `_skimDonatedAssets()` and `_transferFeeUnderlyings()`. `_skimDonatedAssets()` is invoked at the top of nearly every state-changing user and epoch function — `_deposit`, `requestWithdraw`, `depositDuringEpoch`, `startEpoch`, `_stopEpoch`, `writeOffDeposit` and `finalizeDefault` — and forwards *any* raw underlying balance to `feeReceiver`. If `feeReceiver` (or `owner()`) is blacklisted on the underlying token contract, the transfer reverts and every one of those entry points reverts unconditionally. An unprivileged attacker can keep the raw balance permanently non-zero by dust-donating 1 wei of underlying to the CDO, so there is no way to route around the revert except an owner `feeReceiver` rotation.

### Finding Description
The underlying `token` of an `IdleCDOCreditVault`/`IdleCDOEpochVariant` deployment is set at initialize time and can be any ERC20, including USDC or USDT which implement an address blacklist that makes `transfer`/`transferFrom` to a blacklisted recipient revert.

`_skimDonatedAssets()` transfers the contract's *entire* raw underlying balance to `feeReceiver`:

```solidity
// contracts/IdleCDOEpochVariant.sol:794-796
function _skimDonatedAssets() internal {
  _transferUnderlyings(feeReceiver, _contractTokenBalance(token));
}
```

`_transferUnderlyings` uses `safeTransfer`, so a blacklist revert propagates ( [1](#0-0) ). The same problem exists for `_transferFeeUnderlyings`, which pushes to both `feeReceiver` and `owner()` inside `_stopEpoch` ( [2](#0-1) , called at `IdleCDOEpochVariant.sol:419` and `:456`).

`_skimDonatedAssets()` is called unconditionally in:
- `_deposit` (buffer deposits) — `IdleCDOEpochVariant.sol:647`
- `depositDuringEpoch` — `IdleCDOEpochVariant.sol:679`
- `requestWithdraw` — `IdleCDOEpochVariant.sol:747`
- `startEpoch` — `IdleCDOEpochVariant.sol:242`
- `_stopEpoch`/`stopEpochWithDuration` — `IdleCDOEpochVariant.sol:355`
- `writeOffDeposit` — `IdleCDOEpochVariant.sol:941`
- `finalizeDefault` — `IdleCDOEpochVariant.sol:197`
- `updateAccounting` (owner/guardian) — `IdleCDOEpochVariant.sol:159`

Because the skimmed amount is the whole raw balance, a blacklisted `feeReceiver` turns *every* such call into a revert whenever `_contractTokenBalance(token) > 0`. Any EOA can guarantee a non-zero balance at any time by transferring dust underlying directly to the CDO — the code explicitly treats this as an expected "donation" vector (`_skimDonatedAssets` exists precisely for unsolicited transfers).

Notably, `stopEpoch` reverts *after* `getFundsFromBorrower` has already pulled repayment into the contract only if the failure were inside the `try`; the `_skimDonatedAssets` call at line 355 happens *before* the `try`, so the epoch simply can never be stopped while the balance is non-zero and `feeReceiver` is blacklisted. `startEpoch` likewise cannot proceed, so the vault is fully frozen: no deposits, no withdrawal requests, no epoch start/stop, and even `finalizeDefault` (the recovery path after a default) reverts.

### Impact Explanation
All user funds in the vault are frozen for as long as `feeReceiver` remains blacklisted and the CDO holds any raw underlying — a condition an attacker can sustain with a single 1-wei direct transfer re-applied after every successful owner rotation attempt that leaves a residue, or simply sustained indefinitely. Withdrawal claims routed through the strategy (`claimWithdrawRequest` → `IdleCreditVault.claimWithdrawRequest(msg.sender)`) pay the caller directly and are unaffected, but *requests* cannot be created and epochs cannot start/stop, so pending receipts cannot be funded — this is a protocol-wide temporary freezing of funds and yield, matching the Medium severity of the source report (DoS via blacklisted-transfer recipient). Loss is bounded to opportunity cost/gas plus the freeze duration, since the honest owner can eventually rotate `feeReceiver`.

### Likelihood Explanation
Requires two conditions: (1) the vault's underlying is a blacklistable token — plausible, since credit vaults denominated in USDC/USDT are a primary use case for this codebase; (2) `feeReceiver` (or `owner()` for the `_transferFeeUnderlyings` split and minted-fee path) ends up on the token's blacklist — an external event outside the protocol's control, identical in nature to the source finding. Given both, the attacker cost is one dust transfer and the DoS is deterministic, with no guard in the code path (`safeTransfer` revert propagates; there is no pull-pattern or fallback).

### Recommendation
Do not push underlying to `feeReceiver`/`owner` inside user-critical paths. Options:
- Route skimmed donations to the `strategy` contract (an internal, non-blacklistable recipient) instead of `feeReceiver`, and let `feeReceiver` pull them via `claimFees`.
- Wrap the skim transfer so a failure does not revert the caller, e.g. make `skimDonatedAssets` an external self-call in a `try/catch` (as already done for `sendFundsToBorrower`/`getFundsFromBorrower`), crediting `unclaimedFees` on failure.
- Apply the same to `_transferFeeUnderlyings`: accrue to `unclaimedFees` if the push reverts rather than blocking `stopEpoch`.

### Proof of Concept
Foundry fork test (mainnet, USDC `0xA0b8...eB48`):

```solidity
// test/foundry/BlacklistFeeReceiverDoS.t.sol
function test_blacklistedFeeReceiver_dos() public {
    // IdleCDOEpochVariant 'cdo' deployed with token = USDC, feeReceiver set
    address USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;
    address blacklister = 0x...; // USDC master blacklister (owner of blacklist)
    address feeRecv = cdo.feeReceiver();

    // External condition: USDC blacklists feeReceiver
    vm.prank(blacklister);
    IBlacklistable(USDC).blacklist(feeRecv);

    // Attacker (any EOA) dust-donates 1 wei USDC to the CDO
    deal(USDC, attacker, 1);
    vm.prank(attacker);
    IERC20(USDC).transfer(address(cdo), 1);

    // Now every guarded entry point reverts:
    deal(USDC, lender, 1000e6);
    vm.startPrank(lender);
    IERC20(USDC).approve(address(cdo), 1000e6);
    vm.expectRevert(); // safeTransfer to blacklisted feeReceiver in _skimDonatedAssets
    cdo.depositAA(1000e6);
    vm.expectRevert();
    cdo.requestWithdraw(0, cdo.AATranche());
    vm.stopPrank();

    // Epoch cannot start or stop either
    vm.prank(manager);
    vm.expectRevert();
    cdo.startEpoch();

    vm.prank(manager);
    vm.expectRevert();
    cdo.stopEpoch(newApr, 0);
}
```

The same revert hits `depositDuringEpoch`, `writeOffDeposit`, `finalizeDefault`, and `updateAccounting`, confirming vault-wide temporary freezing while `feeReceiver` is blacklisted.
