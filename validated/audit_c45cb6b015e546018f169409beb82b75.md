### Title
Changing `bufferPeriod` via `setEpochParams` desynchronizes the scaled-APR denominator from `depositDuringEpoch` mint pricing, letting a mid-epoch depositor mint tranche tokens at a wrong price - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`setEpochParams` lets the owner/manager change `bufferPeriod` while the pool is in buffer phase, but the code comments explicitly warn that `bufferPeriod` must not change once set because interest math depends on it. The scaled APR (`scaledApr`/`unscaledApr` in `IdleCreditVault`) is fixed at the last `stopEpoch`/`_setScaledApr` call using the *old* `epochDuration + bufferPeriod`, while `depositDuringEpoch` re-derives the participation fraction using the *current* `epochDuration + buffer`. After a parameter change, these two denominators diverge and mid-epoch depositors are minted tranche tokens at a miscomputed discounted price, diluting or being diluted by existing holders — a direct analog of the Fairside "threshold changed but dependent per-user/derived state is stale" bug class.

### Finding Description
The scaled APR stored in `IdleCreditVault` is computed once per epoch boundary via `_setScaledApr(_getStrategyApr())`, baking `epochDuration + bufferPeriod` into the per-second rate used by `_calcInterest`. `setEpochParams` (IdleCDOEpochVariant.sol:117-125) only checks `defaulted || isEpochRunning || _epochDuration == 0 || epochDuration == 0` — it does not rescale the APR and carries an explicit dev comment that `bufferPeriod` should not be changed because "interest calculations will be wrong."

`depositDuringEpoch` (IdleCDOEpochVariant.sol:691-697) then computes:

```solidity
uint256 interest = _calcInterest(_amount) *
  (remaining + buffer) /
  (epochDuration + buffer);
```

`_calcInterest(_amount)` returns the full-period interest for the *old* scaled duration, but the normalization divides by the *new* `epochDuration + buffer`. If `bufferPeriod` was raised, the mid-epoch depositor is credited more participation time than the scaled APR assumed and is minted too many tranche tokens (principal + overestimated prorated interest at epoch end); if lowered, they are minted too few. The minted amount is then checked against `expectedFinal` derived from stale `expectedEpochInterest`, which itself was fixed in `startEpoch` under the old parameters.

### Impact Explanation
An unprivileged KYC-passed lender can call `depositDuringEpoch` (when `isDepositDuringEpochDisabled` is false, which is a supported live mode) in the window between a `bufferPeriod` update and the next epoch boundary, receiving tranche tokens priced against a stale scaled APR. At `stopEpoch`, those tokens redeem principal plus interest that was never earned by the borrower — diluting all other AA/BB holders' `virtualPrice`/`tranchePrice`, i.e. a direct transfer of value from existing LPs to the attacker, quantified by `amount * scaledApr * |newBuffer - oldBuffer| / YEAR`-order discrepancy. The reverse direction (attacker under-minted) harms the depositor, so the theft direction is freely chosen by waiting for a favorable parameter update, which honest management may do as routine tuning.

### Likelihood Explanation
Requires the pool to run with `isDepositDuringEpochDisabled == false` (supported non-default config; `depositDuringEpoch` and `writeOffDeposit` exist for it) and a one-time `setEpochParams` call that changes `bufferPeriod` — an action the honest owner/manager is permitted to take at any buffer phase since the guard does not prevent it. No privileged collusion is needed beyond the parameter update itself, mirroring the Fairside report where an honest governance parameter change is the trigger and unprivileged users exploit the stale derived state. No existing guard (`_skimDonatedAssets`, `_guarded`, `_trancheTotSupply == 0` check, KYC) validates consistency between the scaled APR duration and current `epochDuration + bufferPeriod`.

### Recommendation
Either forbid changing `bufferPeriod`/`epochDuration` while `scaledApr` is nonzero (recompute `_setScaledApr` atomically inside `setEpochParams`, factoring the ratio of old to new total duration), or snapshot the denominator used by `depositDuringEpoch` at `startEpoch` time so the participation fraction always uses the same `epochDuration + bufferPeriod` that the scaled APR was built from. The existing dev comment acknowledging the hazard should be enforced in code.

### Proof of Concept
Foundry fork sketch (credit vault already running, `isDepositDuringEpochDisabled == false`):

```solidity
// 1. Pool in buffer phase. scaledApr was set with (epochDuration + oldBuffer).
uint256 oldBuffer = cdoEpoch.bufferPeriod();

// 2. Honest manager raises bufferPeriod (permitted while !isEpochRunning).
vm.prank(manager);
cdoEpoch.setEpochParams(cdoEpoch.epochDuration(), oldBuffer * 4);

// 3. Manager starts epoch. scaledApr still assumes oldBuffer.
vm.prank(manager);
cdoEpoch.startEpoch();

// 4. Attacker (KYC'd lender) deposits mid-epoch.
//    interest numerator uses remaining + 4*oldBuffer participation time
//    while _calcInterest was scaled for epoch + oldBuffer -> excess mint.
uint256 shares = cdoEpoch.depositDuringEpoch(attackAmount, address(AAtranche));

// 5. Epoch ends, borrower repays exactly expectedEpochInterest.
//    Attacker's tranche tokens redeem more underlying than deposit + fair
//    share; assert tranchePrice * shares > attackAmount + fairInterest,
//    with the excess borne by pre-existing AA/BB holders (virtualPrice drop).
```

Uncertainty note: the exact `_calcInterest`/`_setScaledApr` internals in `IdleCreditVault.sol` were not fully read; the PoC assumes `_calcInterest` uses the stored scaled APR over `epochDuration + bufferPeriod` as documented in the `depositDuringEpoch` comments. If the scaled APR is instead re-derived per call, the mispricing collapses and the finding reduces to no vulnerability. A full PoC should verify `scaledApr` is computed once at epoch boundary before asserting the dilution.
