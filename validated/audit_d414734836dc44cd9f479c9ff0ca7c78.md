### Title
Miner's `StackerDBListener` can double-count a single signer's weight into both `total_weight_approved` and `total_weight_rejected` for the same block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The analog to the "put option gives both premium and strike" bug — a value that should be attributed to exactly one side of a ledger instead gets credited to both — exists in the miner-side StackerDB signature aggregator. `BlockStatus::gathered_signatures`/`total_weight_approved` and `BlockStatus::responded_signers`/`total_weight_rejected` are updated by two independent, non-overlapping dedup checks, so a single signer's `BlockResponse::Accepted` and `BlockResponse::Rejected` for the *same* block can both be tallied, letting one signer's weight count toward both the 70% approval threshold and the >30% blocking-minority rejection threshold simultaneously.

### Finding Description
In `stackerdb_listener.rs`, the `Accepted` branch guards against re-tallying only via `gathered_signatures`: [1](#0-0) 

while the `Rejected` branch guards against re-tallying via the *separate* `responded_signers` set: [2](#0-1) 

Neither branch checks the other's tracking structure. `BlockStatus` declares them as two independent fields: [3](#0-2) 

So a signer can:
1. Send `BlockResponse::Accepted` for a block with a valid signature → `total_weight_approved += weight`, `slot_id` added to `gathered_signatures`.
2. Later (or even in a different processed order) send `BlockResponse::Rejected` for the *same* `signer_signature_hash` → since `slot_id` was never inserted into `responded_signers` by the Accepted path, the check `block.responded_signers.insert(slot_id)` succeeds and `total_weight_rejected += weight` is also applied.

The same weight is now counted in both tallies for the same block, breaking the invariant that a signer's vote is mutually exclusive between accept/reject — the exact invariant the analogous signer-side code was hardened for, per the changelog note: [4](#0-3) 

That fix ("Do not count both a block acceptance and a block rejection for the same signer/block") was applied to `stacks-signer/src/v0/signer.rs`'s own tally logic (`store_and_process_block_signature` / `store_and_process_block_rejection`, both of which key off a single canonical DB record per signer per block), but the equivalent node-side aggregator in `stackerdb_listener.rs`, which the mining coordinator relies on to decide block fate, was never given the same single dedup guard.

### Impact Explanation
The miner's `SigningCoordinator::get_block_status` decides the block's fate purely from these two counters: [5](#0-4) 

Because rejection is checked before approval, a minority of signers (well under 30% weight, no majority required) can each send both an `Accepted` and a `Rejected` message for the same block. Their weight is credited once to `total_weight_approved` (helping the block look validly signed) and again to `total_weight_rejected` (helping to cross the blocking-minority threshold), inflating `total_weight_rejected` beyond what genuinely-rejecting weight supports. This lets that same signer set force the miner into the `SignersRejected` path (`bump_naka_rejected_blocks`, txid exclusion) even though the same weight is simultaneously present in the accepted set — i.e., an acceptance is recounted into the rejection tally, corrupting the aggregated-weight-vs-verified-accepts equality the coordinator depends on to finalize blocks. This can wedge/deny liveness for otherwise validly-forming blocks and cause spurious transaction exclusion, using only a small, sub-30%-weight set of signers (or even a single signer if their weight alone matters for edge thresholds), no majority or key compromise required.

### Likelihood Explanation
Any signer (one slot) can trivially construct and broadcast both a valid `BlockResponse::Accepted` and `BlockResponse::Rejected` message for the same proposed block over StackerDB — this requires only their own valid signing key, matching the "one-slot miner plus gossip" threat model. The two dedup sets (`gathered_signatures` vs `responded_signers`) are always independently reachable in the message-handling loop, so no race condition or timing precision is needed; a signer can send both responses back-to-back.

### Recommendation
Use a single per-block, per-slot "has responded" set (or check both `gathered_signatures` and `responded_signers` before crediting weight to either side, mirroring the fix already applied in `stacks-signer/src/v0/signer.rs`) so that a signer's weight is attributed to at most one of `total_weight_approved`/`total_weight_rejected` for a given `signer_signature_hash`, consistent across both the signer-side and node-side aggregation logic.

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListener` creates a fresh `BlockStatus` for `B`'s `signer_signature_hash`.
2. Malicious/buggy signer `S` (weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` with a valid signature over `B`. `stackerdb_listener.rs:443-465` adds `w` to `total_weight_approved`, records `slot_id` in `gathered_signatures`.
3. The same signer `S` then sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for the same `signer_signature_hash`. `stackerdb_listener.rs:515-518` finds `slot_id` absent from `responded_signers`, inserts it, and adds `w` again — this time to `total_weight_rejected`.
4. Repeating with enough colluding signers (or combined with genuine rejecters) pushes `total_weight_rejected + weight_threshold > total_weight` in `signer_coordinator.rs:509-513`, causing `get_block_status` to return `Err(NakamotoNodeError::SignersRejected{...})` even though the same weight is simultaneously counted as approved — despite the block having legitimately reachable/reached approval weight.
