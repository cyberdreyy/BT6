### Title
Stale rejection weight is never retracted when a signer flips to acceptance — aggregated `total_weight_rejected`/`total_weight_approved` can both count the same signer's weight - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side StackerDB listener tallies signer weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, per `BlockStatus`. Unlike the signer-side `SignerDb`, which explicitly enforces mutual exclusivity between a signature and a rejection for the same signer/block, the coordinator's aggregator has no such invariant: a signer's weight can be counted into `total_weight_rejected` and later also into `total_weight_approved` for the same block, with the stale rejection weight never retracted.

### Finding Description
`stacks-signer/src/signerdb.rs` enforces on the signer side that a signature and a rejection for the same block/signer are mutually exclusive: `add_block_rejection_signer_addr` refuses to record a rejection once a signature exists [1](#0-0) , and `add_block_signature` clears out any prior rejection record for that signer (verified by the `reject_then_accept` test) [2](#0-1) . The docs also confirm this reject→accept transition is a normal, expected part of the state machine: `LocallyRejected --> LocallyAccepted : re-evaluated` [3](#0-2) .

The miner-side coordinator (`StackerDBListener`), however, tracks the *aggregate* weight across all signers in a completely separate structure, `BlockStatus { total_weight_approved, total_weight_rejected, responded_signers, gathered_signatures, .. } ` [4](#0-3) , and this structure has no equivalent invariant:

- On `BlockResponse::Accepted`, weight is added to `total_weight_approved` only guarded by `gathered_signatures.contains_key(&slot_id)` — it never touches or checks `responded_signers` (the set used by the rejection path) [5](#0-4) .
- On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` guarded only by `responded_signers.insert(slot_id)` succeeding — it never checks `gathered_signatures` (the map populated by the acceptance path) [6](#0-5) .

Neither branch ever removes or decrements the *other* counter's weight for that signer. So if signer S first broadcasts a `Rejected` (its weight is added to `total_weight_rejected`, and its slot is added to `responded_signers`), and later re-evaluates and legitimately broadcasts `Accepted` for the same block (exactly the `LocallyRejected -> LocallyAccepted` transition the protocol allows), the listener adds S's weight to `total_weight_approved` as well — `total_weight_rejected` is never decremented. The equality "each signer's weight counts toward at most one of {approved, rejected}" is broken; `total_weight_approved + total_weight_rejected` can exceed `total_weight`.

`SignerCoordinator::wait_for_signer_weight_and_time` (or equivalent block-status consumer) uses these two counters directly to decide the outcome: it declares the block globally rejected once `total_weight_rejected.saturating_add(weight_threshold) > total_weight`, and declares it accepted once `total_weight_approved >= weight_threshold` [7](#0-6) . Because stale rejection weight from signers who have since flipped to acceptance is never purged, `total_weight_rejected` can cross the blocking-minority threshold purely from data that no longer reflects any signer's current position.

### Impact Explanation
This is a liveness wedge, matching the "High" impact category (a signer/coordinator wedged such that a valid block can never be pushed). If enough signers who first rejected a proposal (e.g., due to a transient validation state, tenure-timing edge case, or asynchronous validation window — all legitimate per the documented state machine) later re-evaluate and accept, the coordinator can still conclude `SignersRejected` from the un-retracted stale rejection weight even though a genuine 70% of *current* signer opinion supports the block. This:
- causes the miner to discard/replace a block that could have reached legitimate consensus, forcing wasted re-mining,
- can permanently or temporarily exclude transactions (`permanently_excluded_txids`/`temporarily_excluded_txids`) based on rejection data that is no longer representative of any signer's live vote,
- requires no majority collusion and no other signer's key — a single signer flipping its own vote (its own key, its own legitimate behavior) is sufficient to demonstrate the broken equality, and the practical liveness impact scales with how many signers do so during a validation/timing race.

### Likelihood Explanation
The reject→accept transition is a documented, normal part of the v0 signer protocol (`LocallyRejected --> LocallyAccepted : re-evaluated`), and multiple existing tests exercise scenarios where signers change their minds about a block (e.g. `signers_respond_to_unprocessed_globally_rejected_block_proposals`, `locally_rejected_blocks_overriden_by_global_acceptance`) [8](#0-7) . This is not a rare edge case; asynchronous validation timing windows and pre-commit re-evaluation are described throughout `docs/signer-flows.md` as expected occurrences. No majority or malicious coordination is needed — the coordinator's per-signer double-count is triggered purely by one honest signer's legitimate response sequence being observed over gossip/StackerDB.

### Recommendation
In `StackerDBListener`'s message handling for `BlockResponse`, track a single per-signer "current verdict" for each block (e.g. a `HashMap<u32, Verdict>` keyed by slot id) instead of two independently-additive weight counters gated by separate sets/maps. When a new response for a slot arrives that differs from its previously recorded verdict, retract the old verdict's weight contribution before applying the new one — mirroring the mutual-exclusivity enforcement already present in `SignerDb::add_block_signature`/`add_block_rejection_signer_addr`. Concretely:
- On `Accepted`, if the slot previously contributed to `total_weight_rejected` (i.e. is present in `responded_signers` without a corresponding signature), subtract that weight from `total_weight_rejected` before adding to `total_weight_approved`.
- On `Rejected`, if the slot previously contributed to `total_weight_approved` (i.e. is present in `gathered_signatures`), subtract that weight from `total_weight_approved` before adding to `total_weight_rejected`.

### Proof of Concept
1. Coordinator tracks a proposed block B with `total_weight = 100`, `weight_threshold = 70` (70%), so the blocking minority is `> 30`.
2. Signer S1 (weight 35) initially rejects B (e.g. transient tenure check failure): `handle` for `BlockResponse::Rejected` runs, `responded_signers.insert(slot_1)` succeeds, `total_weight_rejected = 35` [6](#0-5) .
3. Two more independent signers S2, S3 (weight 5 total) also reject for unrelated reasons; `total_weight_rejected = 40` (> blocking minority of 30), which on its own would already flip the block — but suppose instead only S1 initially rejects and no others do yet (`total_weight_rejected = 35`, not yet over the threshold).
4. Meanwhile S1 re-evaluates (the rejection reason becomes stale/re-evaluable per `should_reevaluate_reject_reason`) and legitimately signs and broadcasts `Accepted` for B. The listener's `Accepted` handler checks only `gathered_signatures.contains_key(&slot_1)` (false, first time), so it adds S1's weight again: `total_weight_approved = 35` [5](#0-4) . `total_weight_rejected` remains 35 — it is never decremented.
5. Now suppose 2 more genuinely-rejecting signers (weight 6, distinct from S1) reject afterward: `total_weight_rejected = 41 > 30` triggers `SignersRejected` in `signer_coordinator.rs` [9](#0-8) , even though S1's 35 weight is stale (S1 currently supports the block) and the *actual* live opposing weight is only 6 — well under the 30 blocking minority. The block is wrongly declared globally rejected and its transactions may be excluded, despite genuine signer support being sufficient to reach 70% approval.
