### Title
Stale rejection weight is never cleared when a signer flips its vote from Reject to Accept, corrupting the aggregated-weight vs. verified-accepts invariant — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` aggregates per-signer `BlockResponse` messages into a `BlockStatus` (`total_weight_approved`, `total_weight_rejected`, `responded_signers`, `gathered_signatures`). Deduplication for the two counters uses two *different* keys (`gathered_signatures` for accept, `responded_signers` for reject), so a signer that legitimately re-evaluates a block from `LocallyRejected` to `LocallyAccepted` (an explicitly supported transition in the signer state machine) gets its weight counted in **both** `total_weight_rejected` and `total_weight_approved` simultaneously, with the stale reject weight never removed.

### Finding Description
`BlockStatus` is defined at [1](#0-0) .

For `BlockResponse::Accepted`, the weight-add guard checks `gathered_signatures`: [2](#0-1) 

For `BlockResponse::Rejected`, the weight-add guard checks a *different* set, `responded_signers`: [3](#0-2) 

Because these are two independent membership tests over two independent collections, there is no code path that removes a signer's weight from `total_weight_rejected` when that same signer later sends an `Accepted` message for the same block. The `Accepted` handler only checks `gathered_signatures` (empty for that signer, since they had only rejected before), so it happily adds the signer's weight to `total_weight_approved` too — while the earlier `total_weight_rejected` contribution is left untouched.

This is exactly analogous to the OpenQ `DepositManagerV1.fundBountyToken` bug: two conceptually distinct buckets (whitelisted/non‑whitelisted tokens vs. approved/rejected signer weight) are supposed to be mutually exclusive members of a shared accounting scheme, but the code lets an actor's contribution land in both buckets because the "already counted" check is keyed differently per bucket. The result is that `total_weight_approved + total_weight_rejected` can exceed `total_weight`, breaking the aggregated-weight-vs-verified-accepts equality that `SignerCoordinator::get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) relies on to decide the miner's next action: [4](#0-3) 

Crucially, the flip from `LocallyRejected` to `LocallyAccepted` is not a byzantine action — it's a first-class, documented re-evaluation path in the signer state machine (`BlockInfo::check_state` explicitly allows `LocallyRejected -> LocallyAccepted`): [5](#0-4) 
and is described in the design docs as an ordinary event ("LocallyRejected --> LocallyAccepted : re-evaluated"). A single signer therefore only needs to legitimately change its mind once (e.g., a rejection reason it flagged, such as a stale sortition-view mismatch, resolves itself and the signer subsequently signs on re-proposal/re-evaluation) to trigger the double count — no majority, no malicious key, no auth bypass required.

### Impact Explanation
`total_weight_rejected` is used directly to decide whether the block should be treated as a definite failure:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... return Err(SignersRejected...) }
```
Because a signer's stale rejection weight from before it flipped to Accept is never subtracted, the coordinator can compute a rejection-blocking-minority using weight that, at the time of evaluation, no longer represents an actual rejection. This can cause the miner to prematurely abandon a block proposal (`SignersRejected`) even though the real, current signer opinions (after the flip) would clear the 70% approval threshold — a liveness wedge on block production driven purely by stale accounting, not by any real minority veto. Symmetrically, because the same weight is also present in `total_weight_approved`, the sum of the two counters can exceed `total_weight`, which is an internal invariant violation of the aggregated-weight bookkeeping the coordinator's threshold logic assumes holds (`total_weight_approved`/`total_weight_rejected` are supposed to be non-overlapping partitions of `total_weight`).

This does not directly cause an invalid/non-canonical block to be signed, because the authoritative signature check (`NakamotoBlockHeader::verify_signer_signatures`) recomputes weight from the actual signature set independently, deduplicating by recovered public key: [6](#0-5) 
so this is bounded to a liveness/availability issue in the miner's block-production loop rather than a consensus-safety break.

### Likelihood Explanation
Any signer that rejects a proposal for a reason that is later re-evaluated as no-longer-applicable (e.g., a transient `SortitionViewMismatch`/`ConnectivityIssues` at validate-ok time, later resolved once the node catches up, or a conflict going stale per `should_reevaluate_reject_reason`) will naturally traverse `LocallyRejected -> LocallyAccepted` and broadcast a fresh `Accepted` message for the same `signer_signature_hash`. This is routine operational behavior under normal chain conditions (slow nodes, minor forks, retried proposals), not an attack requiring privileged access, so the double-count condition is readily reachable in practice with ordinary single-signer timing, no majority collusion needed.

### Recommendation
Use a single, unified per-slot response record for the "already accounted" decision (e.g., track each slot's *current* vote kind and weight in one map), and when a signer's message updates their kind (Reject -> Accept, or vice versa), atomically move the weight between `total_weight_approved` and `total_weight_rejected` instead of unconditionally accumulating into a fresh bucket while leaving the old bucket's contribution in place. Concretely, replace the two independent dedup sets (`gathered_signatures` and `responded_signers`) with one canonical "last known vote per slot" structure, and subtract the previous vote's weight from its counter before adding to the new one.

### Proof of Concept
Sequence (no majority or extra privileges required — one signer, one flip):
1. Miner proposes block B (`signer_signature_hash = h`). Coordinator's `BlockStatus` starts with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight `w`) validates B, hits a transient chainstate mismatch, and broadcasts `BlockResponse::Rejected` for `h`. `StackerDBListener` executes the reject branch: `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected += w`. [3](#0-2) 
3. On a subsequent proposal-arrival/re-evaluation pass for the same `h` (per `should_reevaluate_reject_reason` / re-proposal), the transient condition has cleared, S re-validates, moves `LocallyRejected -> LocallyAccepted`, and broadcasts `BlockResponse::Accepted(h, sig)`.
4. `StackerDBListener` executes the accept branch: `gathered_signatures.contains_key(slot_S)` is `false` (S never accepted before) → `total_weight_approved += w`. [2](#0-1) 
5. Now `total_weight_rejected` still equals `w` (never decremented) and `total_weight_approved` also equals `w`: the same signer's weight is counted in both buckets, and `total_weight_approved + total_weight_rejected` can exceed `total_weight` once other signers respond, violating the intended non-overlapping partition and potentially tripping the `SignersRejected` blocking-minority check in `SignerCoordinator::get_block_status` even after S's vote is a current Accept.

Note: I was unable to execute this scenario in a live test harness (no filesystem/terminal access in this mode); the trace above is derived directly from the cited source and the documented signer state-machine transition, not from an executed reproduction. Running an integration test that forces a `LocallyRejected -> LocallyAccepted` re-evaluation on one signer while observing `BlockStatus` fields would be needed for empirical confirmation.
