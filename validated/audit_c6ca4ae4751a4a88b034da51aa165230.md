### Title
Write-off underlyings can be permanently lost when the lender address is a contract unable to handle ERC20 tokens - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`fullfillWriteOffRequest` deletes the lender's write-off request and pushes the underlying payment to `userRequests[_user]`'s owner address with `safeTransfer`. The protocol never verifies the lender can actually receive/use the underlying token. If the write-off request was created by a contract that cannot transfer ERC20 out (e.g., a smart wallet, a programmatic lender contract, or a contract registered through a wrapper), the fulfilled underlyings are locked in that address forever while the request is irrevocably cleared — same bug class as the Allo V2 finding where recipients could be contracts unable to handle pool tokens.

### Finding Description
In `IdleCreditVaultWriteOffEscrow`, a lender creates a write-off request via `createWriteOffRequest`, which escrows their tranche tokens keyed by `msg.sender` (`userRequests[msg.sender]`, line 95–100). Any fulfiller can then call `fullfillWriteOffRequest(_user, _tranches, _underlyings)`:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:134-151
pendingUnderlyings -= ...;
delete userRequests[_user];                       // request permanently cleared

underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
...
underlyingToken.safeTransfer(feeReceiver, _totFee);
underlyingToken.safeTransfer(_user, _underlyings - _totFee);   // pushed to lender address
IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```

The underlying payout is pushed to `_user` — the address that created the request — with no codesize check and no "can handle tokens" confirmation. If `_user` is a contract that cannot initiate ERC20 transfers (e.g., a lender that deposited via a contract vault, a DAO contract without a token-rescue/transfer function, or a contract with a `receive`-only design), the underlyings are delivered into an address that can never move them. Because `delete userRequests[_user]` executes in the same transaction, there is no path to reroute the payment: the tranche tokens are gone to the fulfiller, the request is gone, and the underlying is frozen in the incapable contract. The same pattern exists in `DefaultDistributor.claim(address _to)` and `claimWithdrawRequest`/`_transferFundedClaim`, which push underlyings to a `_user`/`_to` address without any contract-capability check — but the escrow is the strongest analog since the deletion makes the loss final.

### Impact Explanation
Permanent loss of user funds. The lender's escrowed tranche tokens are transferred to the fulfiller, while the full underlying payout (`_underlyings - fee`) becomes permanently inaccessible inside a contract that cannot spend it. The loss equals the entire fulfilled write-off amount. Unlike a failed `transfer` (which would revert), a successful `transfer` to an incapable contract does not revert, so the fulfiller's payment succeeds and the lender has no recourse.

### Likelihood Explanation
Low-to-medium. It requires the lender to be a contract that cannot handle the underlying — plausible for institutional/programmatic lenders (smart contract wallets, vault contracts, or wrappers) interacting with a credit vault where borrowers and lenders are sophisticated entities. No attacker action is needed; any fulfiller (permissionless) triggering the fulfillment finalizes the loss. The protocol itself is what pushes the funds, so once the request exists, the loss is guaranteed on the first fulfillment.

### Recommendation
- In `createWriteOffRequest`, reject contract lenders by checking `msg.sender.code.length == 0`, or store an explicit `payoutTo` address validated at request time.
- Alternatively, use a pull pattern: keep the underlyings in escrow and let the lender call `claim(to)` with a destination it controls, rather than pushing to `msg.sender`.
- Apply the same consideration to `DefaultDistributor.claim(_to)` (already caller-chosen, acceptable) and to `_transferFundedClaim`/`_transferDefaultRecovery` in `IdleCreditVault`, where the receipt owner is the pushed recipient.

### Proof of Concept
Foundry fork-style sketch (contracts-only):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

// A lender contract that can approve/call the escrow but has NO
// function to transfer ERC20 tokens out.
contract IncapableLender {
    function createRequest(address escrow, address tranche, uint256 tranches, uint256 underlyings) external {
        IERC20Detailed(tranche).approve(escrow, tranches);
        IdleCreditVaultWriteOffEscrow(escrow).createWriteOffRequest(tranches, underlyings);
    }
    // note: no token rescue / no arbitrary call function
}

contract WriteOffRecipientLossTest is Test {
    IdleCreditVaultWriteOffEscrow escrow; // deployed & initialized for a running epoch
    IERC20Detailed underlying;            // vault underlying (e.g. USDC fork)
    IERC20Detailed tranche;
    address fulfiller = address(0xF1);
    IncapableLender lender;

    function test_underlyingsLostToIncapableLender() public {
        lender = new IncapableLender();

        uint256 tranches = 100e18;
        uint256 underlyings = 90e6;
        deal(address(tranche), address(lender), tranches);
        deal(address(underlying), fulfiller, underlyings);

        // 1. Lender contract creates the write-off request (epoch running)
        lender.createRequest(address(escrow), address(tranche), tranches, underlyings);

        // 2. Any unprivileged fulfiller fulfills it
        vm.startPrank(fulfiller);
        underlying.approve(address(escrow), underlyings);
        escrow.fullfillWriteOffRequest(address(lender), tranches, underlyings);
        vm.stopPrank();

        // 3. Request is deleted; underlyings are stuck in the lender contract forever
        (uint256 t, uint256 u) = escrow.userRequests(address(lender));
        assertEq(t, 0);
        assertEq(u, 0);
        uint256 fee = underlyings * escrow.exitFee() / escrow.FULL_VALUE();
        assertEq(underlying.balanceOf(address(lender)), underlyings - fee); // frozen, no way out
        assertEq(tranche.balanceOf(fulfiller), tranches);                   // lender's tranches gone
    }
}
```

The lender contract cannot call `transfer` on the underlying, so `underlying.balanceOf(lender)` is permanently unrecoverable — the pool-equivalent tokens are lost forever, matching the reported bug class.
