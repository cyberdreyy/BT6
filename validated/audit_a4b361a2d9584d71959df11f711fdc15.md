### Title
Signer double-signs conflicting tenure-start blocks in the same tenure due to inconsistent "already signed" predicate between v1 and v2 `validate_tenure_change_payload` - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::check_proposal` (v1 chainstate) and `GlobalStateView::check_proposal` (v2 chainstate) both run a `validate_tenure_change_payload` step that is supposed to reject a second, competing tenure-start block once the signer has already put a signature behind one block in that tenure. The two implementations use different signerdb predicates for "already handled this tenure," and the v1 predicate is strictly weaker than the v2 one, allowing a signer running the v1 code path to sign two different, conflicting tenure-start blocks for the same tenure.

### Finding Description
The duplicate/"already signed a block in this tenure" guard exists in both chainstate versions with the same intent (as documented in `docs/signer-flows.md`):

> `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we have already accepted a block in the tenure a tenure-change block is starting. v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`).

Concretely:

- v2: [1](#0-0) 
  uses `signer_db.get_last_signed_block(&block.header.consensus_hash)` — this counts a block as soon as **this signer has locally accepted/signed it**, even before the group threshold is reached.

- v1: [2](#0-1) 
  uses `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — this only counts a block once **global (group) acceptance** has been recorded, i.e. after ~70% signer weight has signed.

Both branches, on finding a prior block, return `RejectReason::DuplicateBlockFound` to stop the signer from processing a second tenure-start proposal for the same tenure. But in the v1 path, if the signer has only *locally* signed tenure-start block A for tenure X (its own signature broadcast, `signed_self` set) and global consensus on A has not yet been reached, `get_last_globally_accepted_block` returns `None`. A miner (or a byzantine/rogue miner acting within a single slot, since tenure-start block content is entirely miner-controlled and re-mineable) can then propose a second, different tenure-start block B for the same tenure X (same `consensus_hash`, different transactions/parent selection within the block body). Because:

1. `check_tenure_change_confirms_parent` only validates the **parent tenure's** last block — both A and B share the same parent tenure claim, so this check passes for both.
2. The v1 duplicate check (`get_last_globally_accepted_block`) sees no globally accepted block yet for tenure X and does not fire `DuplicateBlockFound`.

the v1 signer will proceed to submit B for node validation and, if the node accepts it, sign it — producing a second signature over a **conflicting** tenure-start block for the same tenure that it already signed once. This breaks the "one signed block per tenure-start slot" invariant that the duplicate check exists to enforce, and is exactly the kind of "signer signing a conflicting block" safety break called out as in-scope Critical impact.

This is structurally the same bug class as the Mako advisory: two code paths meant to enforce the same invariant use inconsistent normalization/strength of check (Mako: single-slash-strip vs full-strip; here: locally-signed-inclusive vs globally-accepted-only), and the weaker path is reachable and bypasses the intended guard.

### Impact Explanation
A signer running the v1 protocol (pre global-state-machine activation, `!uses_global_state()`, see `check_block_against_state` dispatch at [3](#0-2) ) can be induced by a single miner to sign two different, mutually exclusive blocks that both start the same tenure. This is a direct equivocation by an honest-but-following-the-code signer: two valid signatures exist over conflicting chain histories for the same tenure slot, undermining the safety property that a signer's signature commits it to one branch per tenure. If enough v1 signers are tricked this way, both competing tenure-start blocks could independently accumulate signer weight, creating a genuine fork/equivocation at the block level — a Critical-class outcome per the scan's own severity mapping ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
Triggerable by a single miner slot with no cooperation from other signers or majority control: the miner simply needs to (a) get one tenure-start block signed/locally-accepted by a subset of v1 signers before it reaches global acceptance, then (b) propose a second, different tenure-start block for the same tenure before global acceptance is reached. This requires only normal proposal-timing control that miners already have (rebroadcast/re-mine within a tenure), and the mismatch is a straightforward reachable code path, not a theoretical one. Likelihood is somewhat bounded by the fact that this is v1-only (a legacy/pre-global-state-machine code path still shipped and dispatched to for any signer/tenure where consensus is on v1, see `determine_active_signer_protocol_version`), and by the timing window needed (before the first block's global acceptance).

### Recommendation
Make the v1 `validate_tenure_change_payload` duplicate check consistent with v2: use `get_last_signed_block` (which includes locally-signed and locally/globally-accepted state, per the doc's characterization) instead of `get_last_globally_accepted_block`, so that a signer's own local acceptance of a tenure-start block is sufficient to block that signer from later signing a conflicting tenure-start block for the same tenure. Alternatively, factor `validate_tenure_change_payload`'s duplicate-check predicate into a single shared helper in `chainstate/mod.rs` used by both v1 and v2, eliminating the possibility of the two versions drifting again.

### Proof of Concept
1. Miner produces tenure-start block A for tenure X and proposes it; a v1 signer runs `SortitionsView::check_proposal` → `validate_tenure_change_payload`, finds no prior block in tenure X, passes, submits to node, node validates OK, signer locally signs A (`signed_self` set, not yet globally accepted since <70% weight has signed).
2. Before A reaches global acceptance, miner produces a different tenure-start block B for the same tenure X (same `consensus_hash`, differing tx set/parent selection) and proposes it.
3. v1 signer runs `check_proposal` on B: `check_tenure_change_confirms_parent` passes (same parent tenure claim as A), then `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [4](#0-3)  which returns `None` because A is only locally signed, not globally accepted — so `DuplicateBlockFound` is never raised.
4. Signer submits B for node validation; if node validates it OK, the signer signs B too, now having signed two conflicting blocks (A and B) for the same tenure X. [5](#0-4)
