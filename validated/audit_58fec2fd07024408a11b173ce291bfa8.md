### Title
Instant-withdraw claims pay the full unfunded receipt basis from the strategy balance, so a partially funded epoch permanently blocks or drains later claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays a user the entire `instantWithdrawsRequests[_user]` basis (plus any older funded receipts) directly from the strategy's underlying balance, without checking how much of that basis was actually funded through `collectInstantWithdrawFunds`. `pendingInstantWithdraws` tracks only the *unfunded remainder*, so the strategy's balance can legitimately be smaller than the locked instant-claim basis. The first claimant to be processed withdraws more than their funded share — or reverts — leaving later claimants permanently frozen, mirroring the "locked funds do not account for claims/refunds" bug class.

### Finding Description
The instant-withdraw flow has two accounting buckets that are never reconciled on the claim path:

- `requestInstantWithdraw` mints a receipt and increases `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and the global `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`).
- `collectInstantWithdrawFunds(_amount)` only decrements `pendingInstantWithdraws` by the amount actually pulled from the CDO (`IdleCreditVault.sol:398-403`). Partial funding is explicitly supported — `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` rely on `pendingInstantWithdraws` being a non-zero remainder (`IdleCreditVault.sol:644-649`, `716-723`).
- `claimInstantWithdrawRequest` then burns and pays `instantWithdrawsRequests[_user]` in full via `_transferFundedClaim`, with no check that the claimed amount was ever collected (`IdleCreditVault.sol:380-393`).

`_transferFundedClaim` guards only `defaultRecoveryReserve`, not the unfunded instant basis or other users' funded normal-withdraw receipts sitting in the same balance (`IdleCreditVault.sol:897-907`). So whenever `collectInstantWithdrawFunds` delivers less than the aggregate instant basis — e.g., the CDO could only source part of the queue from `getInstantWithdrawFunds`, or a later epoch's normal receipts are also funded and waiting in the contract — the first claimant drains underlying earmarked for other receipts, and subsequent calls revert on `safeTransfer` (balance < amount), exactly the "balance < locked funds → blocked refunds" invariant from the reference report.

### Impact Explanation
Permanent freezing of unclaimed yield/principal: users whose instant receipts were only partially funded cannot claim (transfer reverts), and their basis remains locked until a borrower default finalizes recovery — which is precisely the state the audit issue describes (only the first claim works; afterwards claims are impossible). In the worst case an early claimant withdraws underlying that was funded for another user's *normal* withdraw request, since `_transferFundedClaim` draws from a single shared balance with no per-bucket reserve.

### Likelihood Explanation
Requires a partially funded instant-withdraw epoch (CDO collects less than `instantWithdrawClaimsByEpoch[epochNumber]`, leaving `pendingInstantWithdraws > 0`) and two or more claimants. This is a documented state of the system — the default-recovery code explicitly accounts for `pendingInstantWithdraws != 0` meaning current-epoch instant receipts "were not fully funded" (`IdleCreditVault.sol:694-696`) — so it is reachable without privileged misbehavior; an unprivileged user simply requests an instant withdraw in a low-liquidity epoch and claims first.

### Recommendation
Track funded-vs-claimable instant amounts per epoch (e.g., an `instantFundedPriceByEpoch` analogous to `lossRecoveryPriceByEpoch`), and have `claimInstantWithdrawRequest` pay `min(receiptBasis, fundedShare)` or revert early when `pendingInstantWithdraws` still covers part of the user's basis. Alternatively, reserve funded instant proceeds in a dedicated bucket so `_transferFundedClaim` cannot spend other receipts' backing.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` instant-withdraw tests):

```solidity
// users u1, u2 deposit via depositAA during buffer
// epoch running: u1.requestInstantWithdraw(a), u2.requestInstantWithdraw(b)
// manager stopEpoch; CDO collects only (a) from strategy into it
//   -> strategy.collectInstantWithdrawFunds(a); pendingInstantWithdraws == b
// CDO calls claimInstantWithdrawRequest(u1): strategy pays u1 `a` (ok)
// CDO calls claimInstantWithdrawRequest(u2):
//   instantWithdrawsRequests[u2] == b, strategy balance == 0
//   -> _burn(u2, b) succeeds, safeTransfer(u2, b) REVERTS
//   -> u2 receipt burned? No: whole tx reverts, so u2's claim is permanently
//      frozen until defaultRecoveryFinalized (which honest manager never triggers)
assertEq(strategy.instantWithdrawsRequests(u2), b); // locked forever
```
