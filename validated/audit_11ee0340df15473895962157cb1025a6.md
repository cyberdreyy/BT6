### Title
Frontrunnable `InitializeNonceAccount` allows unsigned nonce-authority takeover and fund theft - (File: `programs/system/src/system_instruction.rs`)

### Summary
The System program's `initialize_nonce_account` function sets the durable-nonce `authority` field to whatever pubkey is passed in the instruction data, without requiring any signature check on that authority, on the nonce account itself, or on the account that funded it. Any account that is System-owned, marked `Uninitialized`, writable, and rent-exempt can have its nonce authority set by *any* unprivileged transaction sender who is first to land an `InitializeNonceAccount` instruction against it.

### Finding Description
`initialize_nonce_account` only validates writability, `Uninitialized` state, and minimum rent-exempt balance before writing the caller-supplied `nonce_authority` into the account state — no `check_signer`/authority verification is performed anywhere in the function: [1](#0-0) 

This is in sharp contrast to the sibling functions in the same file, `withdraw_nonce_account` and `authorize_nonce_account`, both of which explicitly call a `check_signer` closure against the relevant authority/account key before mutating state: [2](#0-1) [3](#0-2) 

`system_processor.rs` dispatches `SystemInstruction::InitializeNonceAccount(authorized)` straight into `initialize_nonce_account` with only a check that the account and blockhash sysvar are present — no signer requirement is imposed at the processor level either: [4](#0-3) 

This mirrors the CNote `_setAccountantContract()` bug class exactly: the "post-creation initializer" that is supposed to run immediately after account creation lacks any access-control guard, so whoever's `InitializeNonceAccount` transaction lands first on a funded, uninitialized, System-owned account becomes its nonce authority — regardless of who created/funded that account.

### Impact Explanation
Once an attacker wins the race and becomes the `authority` of a victim's nonce account, they can immediately submit `WithdrawNonceAccount` for the full balance. In `withdraw_nonce_account`, a full-balance withdrawal from an `Initialized` account only requires `check_signer(&data.authority)` — which the attacker now satisfies because they set themselves as `authority` during the front-run: [5](#0-4) 

This produces concrete, unsigned fund movement: the attacker drains all lamports from the rent-exempt nonce account to an address of their choosing, without the legitimate creator/funder ever having signed away control.

### Likelihood Explanation
Standard tooling (e.g., the CLI's `process_create_nonce_account`, which uses `create_nonce_account`/`create_nonce_account_with_seed`) bundles `CreateAccount` and `InitializeNonceAccount` into the *same* atomic transaction/message, which closes this race in the common case: [6](#0-5) 

However, nothing in the System program enforces this atomicity. Any integrator, wallet, or custom program that allocates/funds a System-owned account in one transaction and defers `InitializeNonceAccount` to a later, separate transaction (e.g., due to multi-step UX flows, program-derived nonce accounts created via CPI, or batching) exposes a mempool-visible window in which any unprivileged sender can front-run the initialize call. Because the bug is in the builtin System program itself rather than application code, the likelihood of being reachable depends entirely on whether callers split account funding and nonce initialization across transactions — which the protocol permits and does not warn against.

### Recommendation
Require `initialize_nonce_account` to verify that the account itself (or the funding/creating signer) has signed the `InitializeNonceAccount` instruction before allowing the authority field to be set, closing the same-slot/same-tx assumption gap. At minimum, document/enforce that `InitializeNonceAccount` must occur in the same atomic transaction as the funding `CreateAccount`/`Allocate` instruction, and consider adding a runtime check that rejects `InitializeNonceAccount` if the account was not created in the same transaction.

### Proof of Concept
1. Victim submits `SystemInstruction::CreateAccount` funding a fresh keypair `N` with rent-exempt lamports, owned by the System program, intending to follow up with `InitializeNonceAccount(victim_authority)` in a later transaction.
2. Attacker observes `N`'s account state on-chain (uninitialized, System-owned, rent-exempt) and, before the victim's follow-up transaction lands, submits their own transaction containing `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` targeting `N`.
3. `initialize_nonce_account` accepts this because it only checks `is_writable`, `State::Uninitialized`, and minimum balance — no signature from `N`, the victim, or any authority is required: [7](#0-6) 
4. `N`'s nonce authority is now `attacker_pubkey`. The victim's original `InitializeNonceAccount` transaction subsequently fails with `InstructionError::InvalidAccountData` (already initialized), exactly matching the `initialize_inx_initialized_account_fail` test's error path: [8](#0-7) 
5. Attacker submits `SystemInstruction::WithdrawNonceAccount(full_balance)` signed only by `attacker_pubkey`, which passes `check_signer(&data.authority)` and drains all lamports from `N` to an attacker-controlled destination: [5](#0-4)

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
