### Title
Deterministic account (`0s...`) hijack via `CreateAccount`+`AddKey` bypassing the implicit-account creation gate - ([File: runtime/runtime/src/actions.rs])

### Summary
`check_account_existence`'s `Action::CreateAccount` branch only rejects account IDs for which `account_is_implicit` returns `true`, and `account_is_implicit` only recognizes `AccountType::NearImplicitAccount`/`AccountType::EthImplicitAccount`, never `AccountType::NearDeterministicAccount` [1](#0-0) . `action_create_account` itself performs no account-type check at all — it only validates `is_top_level()`/length/sub-account rules [2](#0-1) . As a result, an attacker can run a plain `CreateAccount`+`AddKey(FullAccess)` transaction against a `0s`+40-hex deterministic account ID (which is `is_top_level()==true` and length 42), install a full-access key, and thereby seize an account address that a depositor/dapp expects to be key-less and governed only by `DeterministicAccountStateInit`.

### Finding Description
`AccountType` has four variants: `NamedAccount`, `NearImplicitAccount`, `EthImplicitAccount`, `NearDeterministicAccount` — deterministic account IDs (`0s`+40 hex) are their own distinct type, not folded into the "implicit" family checked by `account_is_implicit` [3](#0-2) . In `apply_action`, before dispatching `Action::CreateAccount`, `check_account_existence` is called; for `Action::CreateAccount` it only blocks the action when `account_is_implicit(account_id, eth_implicit_accounts)` is true [4](#0-3) . Since `account_is_implicit` never returns true for `NearDeterministicAccount`, this gate is silently skipped for `0s...` IDs.

`action_create_account` then only enforces top-level-length/registrar and sub-account rules, with zero knowledge of `AccountType` [2](#0-1) . A `0s...` ID has no `.` so `is_top_level()==true`, and its fixed length (42) is compared against `min_allowed_top_level_account_length`; if the id length is `>=` that config value, no registrar predecessor is required, and the account is created bare with `actor_id` set to the account itself. A subsequent `AddKey(FullAccess)` action in the same receipt then passes `check_actor_permissions` (self-authorized) and installs an attacker-controlled full-access key.

This directly contradicts the documented protocol invariant: "Deterministic accounts cannot be created with a `CreateAccount` nor with a `Transfer` action. A special action, `DeterministicStateInitAction`, is required" [5](#0-4) . The `Action::DeterministicStateInit` branch of `check_account_existence` treats an existing account as a no-op continuation rather than re-validating/resetting keys [6](#0-5) , so a legitimate `DeterministicStateInitAction` arriving later does not remove the attacker's pre-installed full-access key.

Note: `AccountType::is_implicit()`'s exact source is defined in the external `near-account-id` crate and was not directly viewable in this index; this conclusion rests on the documented account-type taxonomy and the explicit wrapper comment noting `is_implicit` was extended only to cover ETH-implicit accounts, with no mention of deterministic accounts [3](#0-2) , together with the panic-safety comment in `action_implicit_account_creation_transfer` that explicitly assumes `account_is_implicit` returns false for non-implicit/deterministic-mismatched types [7](#0-6) .

### Impact Explanation
This is an authorization-escalation bug: an unprivileged attacker can plant a signing key over an account address that the protocol guarantees is key-less and exclusively contract-governed (NEP-616 deterministic accounts). Any dapp or depositor relying on that guarantee (e.g., sending funds or invoking a deterministic account expecting only its fixed `DeterministicAccountStateInit` code/state to have authority) can have those funds or that account's authority hijacked by the attacker's full-access key — a concrete authorization-escalation / fund-theft path matching "Unauthorized transaction" and "authorization escalation across accounts" bounty categories.

### Likelihood Explanation
Requires only an ordinary funded account submitting a standard `CreateAccount`+`AddKey` transaction to a known/precomputed `0s...` id (derivable off-chain via `derive_near_deterministic_account_id`), and requires that the target id's fixed length (42) is `>=` the network's `min_allowed_top_level_account_length` (removing the registrar requirement). No special privileges, races with block/chunk production, or social engineering needed — repeatable against any deterministic account id whose derivation a third party publishes before deploying/funding it.

### Recommendation
In `check_account_existence`'s `Action::CreateAccount` branch, reject the action whenever `account_id.get_account_type() != AccountType::NamedAccount` (i.e., cover `NearDeterministicAccount` in addition to implicit types), or equivalently extend `account_is_implicit` (or add a parallel check) so `NearDeterministicAccount` is also treated as non-`CreateAccount`-creatable, consistent with the documented invariant that only `DeterministicStateInitAction` may create such accounts.

### Proof of Concept
Unit test in `runtime/runtime/src/actions.rs` (or an integration test using `RuntimeGroup`/test-loop):
1. Build a `DeterministicAccountStateInit::V1` with an arbitrary global-contract identifier and empty data; call `derive_near_deterministic_account_id` to get the `0s...` id.
2. Construct a `SignedTransaction` with `[Action::CreateAccount, Action::AddKey(attacker_pubkey, FullAccess)]` targeting that id from an ordinary funded signer account.
3. Assert the resulting receipt executes `Action::CreateAccount` successfully (no `ActionErrorKind::OnlyImplicitAccountCreationAllowed`).
4. Assert `get_access_key(det_account_id, attacker_pubkey)` returns `Some(AccessKey::full_access())`.
5. Optionally follow with a legitimate `Action::DeterministicStateInit` transaction to the same id and confirm the attacker's key is still present afterward.

    if eth_implicit_accounts_enabled {
        account_id.get_account_type().is_implicit()
    } else {

pub(crate) fn action_create_account(
    fee_config: &RuntimeFeesConfig,
    account_creation_config: &AccountCreationConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    predecessor_id: &AccountId,
    result: &mut ActionResult,
) {
    if account_id.is_top_level() {
        if account_id.len() < account_creation_config.min_allowed_top_level_account_length as usize
            && predecessor_id != &account_creation_config.registrar_account_id
        {
            // A short top-level account ID can only be created registrar account.
            result.result = Err(ActionErrorKind::CreateAccountOnlyByRegistrar {
                account_id: account_id.clone(),
                registrar_account_id: account_creation_config.registrar_account_id.clone(),
                predecessor_id: predecessor_id.clone(),
            }
            .into());
            return;
        } else {
            // OK: Valid top-level Account ID
        }
    } else if !account_id.is_sub_account_of(predecessor_id) {
        // The sub-account can only be created by its root account. E.g. `alice.near` only by `near`
        result.result = Err(ActionErrorKind::CreateAccountNotAllowed {
            account_id: account_id.clone(),
            predecessor_id: predecessor_id.clone(),
        }
        .into());
        return;
    } else {
        // OK: Valid sub-account ID by proper predecessor.
    }

    *actor_id = account_id.clone();
    *account = Some(Account::new(
        Balance::ZERO,
        Balance::ZERO,
        AccountContract::None,
        fee_config.storage_usage_config.num_bytes_account,
    ));
}

pub(crate) fn check_account_existence(
    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            } else {
                if account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts) {
                    // If the account doesn't exist and it's implicit, then you
                    // should only be able to create it using single transfer action.
                    // Because you should not be able to add another access key to the account in
                    // the same transaction.
                    // Otherwise you can hijack an account without having the private key for the
                    // public key. We've decided to make it an invalid transaction to have any other
                    // actions on the implicit hex accounts.

                    // See https://github.com/nearprotocol/NEPs/pull/71
                    return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                        account_id: account_id.clone(),
                    }
                    .into());
                }
            }
        }
