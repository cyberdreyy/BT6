### Title
Unbounded disk consumption during tar+zstd extraction with no size quota and no effective mid-file cancellation - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`Extract()` copies each tar entry's decompressed content directly with `io.Copy(f, tr)` at line 93 with no cap on decompressed size, and the only cancellation check (`ctx.Err()` at line 70) runs once per tar header, before the copy begins — not during it. In the primary caller, `CacheExtractorCommand.Execute` (`commands/helpers/cache_extractor.go:660`), extraction is invoked with `context.Background()`, which never cancels, so the per-header check is a no-op in that path as well.

### Finding Description
The attacker (a normal job/pipeline author) fully controls the contents of a cache archive uploaded via `cache-archiver`/`cache-extractor` (or any similarly-invoked tar+zstd artifact). A crafted archive can contain a single tar header with a large `Size` field, backed by a zstd stream with a very high compression ratio (zstd supports extreme ratios, and `zstd.WithDecoderLowmem(true)` only limits decoder *memory* usage, not output size). When `Extract()` reaches this entry:
1. It passes the earlier checks (`irregularModes`, path traversal via `filepath.Abs`/`HasPrefix` at lines 58-64) — none of which bound size.
2. `ctx.Err()` is checked once at line 70, before `os.Create` and the copy loop.
3. `io.Copy(f, tr)` at line 93 then streams the entire decompressed entry to disk with no byte-count limit, no periodic re-check of `ctx.Err()`, and no interaction with cancellation until `io.Copy` itself returns (which only happens at EOF or on an underlying reader/writer error).

Because `commands/helpers/cache_extractor.go:660` calls `extractor.Extract(context.Background())`, there is no deadline or cancellation source at all reaching `Extract` in the cache-extraction path — the `--timeout` CLI flag only bounds the HTTP download phase (`CacheClient` timeout), not the extraction phase. So even the coarse "check between headers" mitigation the code appears to intend is not exercised in this call site.

None of the existing protections (`MaxUploadedArchiveSize` in `cache_archiver.go`, which only bounds *upload* size when pushing an archive to remote cache storage) constrain the *decompressed* size of an archive during extraction, and there is no artifact/cache extraction quota, disk-space check, or `io.CopyN`-style cap anywhere in `Extract()`.

### Impact Explanation
A malicious job can produce a small-on-disk (or normally-sized) tar+zstd cache archive that decompresses to an amount of data limited only by available disk space on the shared runner/cache host, consuming disk during a single `io.Copy` call that cannot be interrupted via context cancellation. On hosts where cache/build storage is shared across concurrently running jobs from other projects/pipelines (a common Runner deployment pattern for shell/docker executors sharing a cache volume), this can fill the shared disk and cause `ENOSPC` failures for unrelated jobs — a denial-of-service against other tenants' pipelines, consistent with the scoped invariant against persistent multi-tenant disruption.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: any pipeline author who can push a job cache (or an artifact processed by this same tar+zstd extractor) can shape the archive. No special runner configuration or privileged access is required beyond ordinary job execution. Constructing a high-ratio zstd bomb is straightforward and repeatable (standard "decompression bomb" technique), and the extraction code path is reached unconditionally for any tar+zstd formatted archive.

### Recommendation
- Enforce a maximum extraction size (aggregate and/or per-file) while copying, e.g. replace `io.Copy(f, tr)` with a bounded copy such as `io.CopyN(f, tr, maxAllowed+1)` and fail if the limit is exceeded, or wrap `tr` with a counting reader compared against the tar header's own `Size` and a global budget across the whole `Extract()` call.
- Re-check `ctx.Err()` periodically *during* large copies (e.g., chunk the copy loop, e.g. 32KB/1MB chunks, checking cancellation between chunks) rather than only once per header.
- Pass a real, bounded context (derived from `--timeout` or a dedicated extraction timeout) into `Extract()` from `CacheExtractorCommand.Execute` instead of `context.Background()`.
- Consider validating the tar header's declared `Size` against a sane maximum before starting the copy, and comparing actual bytes written against the declared size to detect zstd streams that produce far more output than the header claims.

### Proof of Concept
```go
package tarzstd

import (
	"archive/tar"
	"bytes"
	"context"
	"io"
	"os"
	"testing"
	"time"

	"github.com/klauspost/compress/zstd"
)

// buildZstdBomb creates a tar+zstd archive with one regular-file header
// claiming a huge Size, backed by highly compressible (zero-byte) content
// that zstd compresses to a tiny stream but decompresses to gigabytes.
func buildZstdBomb(t *testing.T, decompressedSize int64) []byte {
	var tarBuf bytes.Buffer
	tw := tar.NewWriter(&tarBuf)
	hdr := &tar.Header{
		Name: "bomb.bin",
		Mode: 0600,
		Size: decompressedSize,
	}
	if err := tw.WriteHeader(hdr); err != nil {
		t.Fatal(err)
	}
	zero := make([]byte, 1<<20) // 1MB of zeros, written repeatedly
	remaining := decompressedSize
	for remaining > 0 {
		n := int64(len(zero))
		if remaining < n {
			n = remaining
		}
		if _, err := tw.Write(zero[:n]); err != nil {
			t.Fatal(err)
		}
		remaining -= n
	}
	tw.Close()

	var zstdBuf bytes.Buffer
	zw, _ := zstd.NewWriter(&zstdBuf, zstd.WithEncoderLevel(zstd.SpeedBestCompression))
	zw.Write(tarBuf.Bytes())
	zw.Close()
	return zstdBuf.Bytes()
}

func TestExtract_ZstdBombIsBoundedOrCancellable(t *testing.T) {
	dir := t.TempDir()
	// Simulate a multi-GB decompressed bomb from a small compressed payload.
	data := buildZstdBomb(t, 5<<30) // 5 GiB claimed size
	r := bytes.NewReader(data)

	ex, err := NewExtractor(r, int64(len(data)), dir)
	if err != nil {
		t.Fatal(err)
	}

	ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer cancel()

	start := time.Now()
	err = ex.Extract(ctx)
	elapsed := time.Since(start)

	// Expect: Extract should abort promptly on ctx cancellation (well under
	// the time needed to write 5GiB), or the extractor should enforce a
	// size/quota limit and return an error before writing unbounded data.
	if err == nil {
		t.Fatalf("expected Extract to fail (ctx deadline or size-limit), got nil error, took %v", elapsed)
	}
	if elapsed > 2*time.Second {
		t.Fatalf("Extract() was not promptly cancellable during large file copy: took %v", elapsed)
	}

	// Confirm no unbounded file leaked onto disk.
	fi, statErr := os.Stat(dir + "/bomb.bin")
	if statErr == nil && fi.Size() > 100<<20 { // arbitrary sanity threshold: 100MB
		t.Fatalf("extractor wrote unbounded data to disk before enforcing any limit: %d bytes", fi.Size())
	}
}
```
