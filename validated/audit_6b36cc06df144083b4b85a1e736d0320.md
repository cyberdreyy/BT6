### Title
`LockupContract::new` is missing the `state_exists` initialization guard, allowing re-initialization of an existing lockup and theft of its locked/unvested balance - (File: `lockup/src/lib.rs`)

### Summary
Every other contract in this repository (`LockupFactory::new`, `MultiSigContract::new`, `StakingContract::new`, `StakingPoolFactory::new`, `WhitelistContract::new`, `VotingContract::new`) explicitly asserts `!env::state_exists()` at the start of its `#[init]` constructor to prevent re-initialization. `LockupContract::new` in `lockup/src/lib.rs` does not have this check, so any account can call `new` again on an already-deployed, already-funded lockup contract and overwrite its state, taking full ownership of the balance sitting in that account.

### Finding Description
The broken binding: `state_before_new_call == state_after_new_call` should imply `new` was never previously successful on this account (init-once invariant). In `lockup/src/lib.rs`, `LockupContract::new`: [1](#0-0) 

performs validation only on the supplied `owner_account_id`, `staking_pool_whitelist_account_id`, `transfer_poll_account_id`, and the vesting/foundation account combination — it never calls `assert!(!env::state_exists(), ...)`. Compare this with the sibling contracts in the same repository, which all guard their `#[init]` constructor with this exact check: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The near-sdk version used (`near-sdk = "3.1.0"`, per `lockup/Cargo.toml`) does not automatically block a second call to an `#[init]` method — that is precisely why every other contract in this repo has to add the explicit `assert!(!env::state_exists(), ...)` line manually. `LockupContract::new` is the one exception where this line was omitted.

Because `new` is a public, non-payable method with no `assert_self()` / owner check, any unprivileged account can send a `FunctionCall` transaction to an existing, already-funded lockup account calling `new` with attacker-chosen arguments. On re-entry, `env::account_balance()` (line `lockup_amount: env::account_balance()`) is re-read at call time and will reflect whatever NEAR currently sits in the lockup account (i.e., all the previously locked/unvested lockup tokens plus lockup rewards). The attacker sets:
- `owner_account_id` = attacker's own account,
- `transfers_information` = `TransfersEnabled` with an already-past `transfers_timestamp`,
- `vesting_schedule` = `None`, `foundation_account_id` = `None`, `release_duration` = `None`,

which produces a brand-new `LockupContract` state where the attacker is immediately the unrestricted owner of the entire account balance, bypassing whatever lockup/vesting schedule and `end_timestamp` previously restricted the funds. The scenario described in the question (calling `new` a second time after `end_timestamp`, when `get_unvested_amount` would return zero but release/lockup time still nominally remained) is simply one instance of this broader "no init-once guard" flaw — but the flaw is exploitable at any time, not only post-`end_timestamp`, since the attacker fully controls all constructor parameters including `transfers_information`, `lockup_timestamp`, and `release_duration` on the replay call.

No existing guard (`assert_self`, `assert_owner`, `assert_called_by_foundation`, `assert_one_yocto`, etc.) applies to `new`, since it is the initializer itself and none of those helper functions are invoked in it.

### Impact Explanation
This lets a non-owner take over full ownership of any deployed lockup contract account and its entire balance — locked, unvested, and liquid tokens are all released to a party (the attacker) never entitled to them. This is a Critical impact per the rubric: "locked or unvested tokens released early" / "an account ... deployed with parameters its rightful creator never chose," and effectively NEAR leaving legitimate control by an unauthorized re-initialization. It is repeatable against every lockup contract account deployed by the `lockup-factory` (or any lockup contract account in existence), giving a blast radius across the entire lockup contract fleet, not a single account.

### Likelihood Explanation
The attack requires no special privilege: the attacker only needs to know the account ID of any existing lockup contract (these are public/discoverable, e.g. `<name>.lockup.near`) and to send a single `FunctionCall` transaction to that account invoking `new` with self-chosen arguments — this costs only the standard NEAR gas fee. There is no confirmation, timelock, or owner check in the path. This is trivially and repeatably exploitable against every deployed lockup account, contingent only on `near-sdk 3.1.0`'s `#[init]` behavior indeed permitting a second call (strongly implied by the fact that every sibling contract manually re-implements the guard that `LockupContract::new` omits).

### Recommendation
Add `assert!(!env::state_exists(), "The contract is already initialized");` as the first statement of `LockupContract::new` in `lockup/src/lib.rs`, matching the pattern used consistently by `LockupFactory::new`, `MultiSigContract::new`, `StakingContract::new`, `StakingPoolFactory::new`, `WhitelistContract::new`, and `VotingContract::new`.

### Proof of Concept
```rust
// lockup/src/lib.rs tests module
#[test]
#[should_panic(expected = "already initialized")]
fn test_reinit_blocks_second_new_call() {
    let context = basic_context();
    testing_env!(context.clone());
    // First legitimate initialization funds/locks LOCKUP_NEAR tokens for account_owner().
    let _contract = new_contract(true, None, None, false);

    // Attacker (any account, no special key) sends a second `new` call to the
    // same already-initialized lockup account, choosing themselves as owner
    // and immediate unlock/no-vesting parameters.
    testing_env!(context.clone());
    let _attacker_contract = LockupContract::new(
        "attacker".to_string(),
        0.into(),                                   // lockup_duration = 0
        None,                                        // no future lockup_timestamp
        TransfersInformation::TransfersEnabled {
            transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS - 1).into(), // already in the past
        },
        None,                                         // no vesting schedule
        None,                                          // no release_duration
        "whitelist".to_string(),
        None,                                          // no foundation account
    );
    // BUG: without the missing `assert!(!env::state_exists(), ...)` guard,
    // this second call succeeds, overwriting owner_account_id to "attacker"
    // and re-reading env::account_balance() (still holding the original
    // LOCKUP_NEAR tokens) as the new unrestricted lockup_amount for "attacker".
    // Expected fix: this call should panic with "already initialized".
}
```
Running this test against the current code (without the fix) shows the second `new` call succeeds and produces a `LockupContract` state where `owner_account_id == "attacker"` and `get_owners_balance()` immediately reflects the full previously-locked balance, proving the funds are released to an unauthorized party. Adding the `assert!(!env::state_exists(), ...)` guard makes the second call panic as expected.

    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,

        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information

            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),

                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
