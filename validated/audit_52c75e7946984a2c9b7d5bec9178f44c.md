### Title
Local state machine dropped to `Uninitialized` on a replay-scope inference failure inside `bitcoin_block_arrival` - (File: stacks-signer/src/v0/signer_state.rs)

### Summary
`LocalStateMachine::bitcoin_block_arrival` takes `self` by `&mut`, immediately swaps it out to `Self::Uninitialized` (`std::mem::replace(self, Self::Uninitialized)` at line 575), and is only meant to restore a real state at the very end of the function once every fallible step (peer info fetch, replay-state inference, fork handling, sortition validity, miner-state construction) has succeeded. One of those fallible steps, `ReplayState::infer_state`, can return `None` (line 630-637), in which case the function returns `Err(SignerChainstateError::LocalStateMachineNotReady)` immediately — but `*self` is never reset back to `Pending`/`Initialized` before that return. The caller (`process_event` in `stacks-signer/src/v0/signer.rs`) only logs the error via `.unwrap_or_else(|e| error!(...))`; it does not attempt to preserve or recover state on this path, in contrast to the `node_behind_expected`/`node_on_equal_fork` branch a few lines above (line 615-628), which is careful to write `*self = Self::Pending { ... }` before returning its own `Err`.

### Finding Description
Every code path in `bitcoin_block_arrival` that can legitimately fail *before* line 630 (bad peer info, node-behind-expected) is followed by explicitly restoring `self` to a valid `Pending` or otherwise-recoverable variant before returning an `Err`. The `ReplayState::infer_state(...) == None` branch is the sole exception: it discards the mem::replace-extracted `prior_state_machine` entirely and returns without writing anything back into `*self`, so the enum is left as `LocalStateMachine::Uninitialized`.

Because `self.local_state_machine` is now `Uninitialized`, the signer effectively forgets:
- `current_miner` / `MinerState::ActiveMiner` (parent tenure, parent tenure last block, current miner pubkey hash),
- the `tx_replay_set` it was tracking.

Every function elsewhere in the signer that gates behavior on the state machine (`check_block_against_state`, `check_miner_inactivity`, `capitulate_viewpoint`, `handle_block_proposal`'s `check_proposal`, `try_into_update_message_with_version`, etc.) treats `Uninitialized` as "nothing to do" and short-circuits — this is visible directly in the codebase (e.g. `stacks-signer/src/tests/signer_state.rs:1136-1140` explicitly documents that "an uninitialized local state cannot be modified", and `LocalStateMachine::Uninitialized` branches throughout `signer_state.rs` return early without evaluating miner validity).

`ReplayState::infer_state` returning `None` happens specifically "due to scope being not set while in replay mode" — i.e. `tx_replay_set` is non-empty (the signer believes it is in a tx-replay window from a prior Bitcoin fork) but `tx_replay_scope` (an in-memory, non-persisted `Option` threaded through the runloop) is `None`. This combination is reachable purely from ordinary miner/gossip-driven activity: a Bitcoin fork sets `tx_replay_set` via `handle_possible_bitcoin_fork` on one burn-block pass, and if the process restarts, or the in-memory `tx_replay_scope` is otherwise not carried alongside a persisted `tx_replay_set` on the next `NewBurnBlock` event, the two go out of sync and the very next burn-block arrival hits this branch — no majority collusion or privileged access is required, only the normal chain-of-events a single miner triggers (mining a fork that forces the signer into replay mode).

### Impact Explanation
This is a liveness wedge: while `local_state_machine` is `Uninitialized`, the signer has no active-miner view, so `check_miner_inactivity`, `capitulate_viewpoint`, and block-proposal validation that depend on `current_miner`/`parent_tenure_last_block` cannot function correctly, and the signer cannot safely evaluate or sign new proposals until a subsequent `NewBurnBlock` event happens to re-initialize the state machine from scratch (via the `LocalStateMachine::Uninitialized => Self::place_holder(...)` branch on the next call). This matches the report's shape exactly: an edge-case codepath (an epoch-0-analogous "replay scope not set" condition) sends the state machine into a state that only self-heals once *another* triggering event (the next burn block) arrives — in the interim, the signer is effectively non-functional for signing decisions, which is a High-severity "wedged into never signing valid blocks" condition per the rules of this scan.

### Likelihood Explanation
Requires only: (1) a Bitcoin fork event that puts the signer into "replay mode" (setting `tx_replay_set`) via ordinary miner/fork activity, matching normal `handle_possible_bitcoin_fork` logic, and (2) the in-process, non-persisted `tx_replay_scope: ReplayScopeOpt` becoming desynchronized from the persisted `tx_replay_set` (e.g., across a signer restart, since `tx_replay_scope` is runloop/process-local state rather than being reconstructed from `tx_replay_set` at startup). No majority of signers, no other signer's key, and no privileged access are needed — this is triggerable by ordinary chain conditions plus a signer restart, which is a realistic operational occurrence.

### Recommendation
Before returning `Err(SignerChainstateError::LocalStateMachineNotReady)` in the `ReplayState::infer_state` failure branch, restore `*self` to a recoverable state (e.g., `Self::Initialized(prior_state_machine)` or a `Pending` update analogous to the `node_behind_expected` branch) instead of leaving it as `Self::Uninitialized`. Additionally, ensure `tx_replay_scope` is reconstructed/validated against the persisted `tx_replay_set` on signer startup so the two cannot desynchronize across a restart.

### Proof of Concept [1](#0-0) [2](#0-1) [3](#0-2) 

1. Signer observes a Bitcoin fork; `handle_possible_bitcoin_fork` sets `tx_replay_set` to a non-empty `ReplayTransactionSet` while `tx_replay_scope` is set in-process.
2. Signer process restarts (or the runloop's `tx_replay_scope` variable is otherwise reset) — `tx_replay_set` is persisted/reloaded via `SignerStateMachine`, but `tx_replay_scope` starts as `None` again since it is threaded through the runloop rather than reloaded from `tx_replay_set`.
3. Next `NewBurnBlock` event triggers `bitcoin_block_arrival`; at line 575, `self` becomes `Self::Uninitialized`; at line 630, `ReplayState::infer_state(&tx_replay_set, tx_replay_scope)` returns `None` because scope is unset while the (non-empty) replay set implies replay mode.
4. Function returns `Err(SignerChainstateError::LocalStateMachineNotReady)` at line 636 without restoring `*self`.
5. Caller (`stacks-signer/src/v0/signer.rs`, the `SignerEvent::NewBurnBlock` handler) only logs the error; `self.local_state_machine` remains `LocalStateMachine::Uninitialized` for the remainder of this and any intervening passes, until the next `NewBurnBlock` re-triggers full re-initialization via the `Uninitialized => Self::place_holder(...)` path.

I was not able to fully trace the exact runloop-restart code path that (re)constructs `tx_replay_scope` at startup within the indexed portion of the codebase, so I cannot conclusively confirm the precise restart mechanics that desynchronize it from `tx_replay_set`; this is noted as an area for the assigned engineer to verify directly against `stacks-signer/src/runloop.rs` and the signer's startup sequence.
