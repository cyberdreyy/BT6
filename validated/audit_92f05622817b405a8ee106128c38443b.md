### Title
View-role users can enumerate bridge names via unrestricted `GET /v2/jobs/:ID` and retrieve the bridge's `outgoingToken` via unrestricted `GET /v2/bridge_types/:BridgeName` - ([File: core/web/jobs_controller.go], [File: core/web/bridge_types_controller.go])

### Summary
`JobsController.Show` and `BridgeTypesController.Show` are both registered on `authv2` without any `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, unlike their sibling write endpoints. `NewBridgeResource` unconditionally populates the `OutgoingToken` field (no `omitempty`, no role check), so any authenticated session/token — including a view-role user — can chain job-show (to learn a bridge name referenced by a job's pipeline) with bridge-show (to pull that bridge's outgoing token).

### Finding Description
In `core/web/router.go`, the job and bridge "Show" routes are registered with no role gate: [1](#0-0)  and [2](#0-1) . Compare this to `bt.Create`, `bt.Update`, `bt.Destroy`, and `jc.Create/Update/Delete`, which are all wrapped in `auth.RequiresEditRole`. Only base session/token authentication (`auth.AuthenticateByToken`/`auth.AuthenticateBySession`) is required for the `Show` handlers, so a view-role user or restricted API token holder can call both.

`JobsController.Show` looks up the job by ID and returns it via `presenters.NewJobResource(jobSpec)` with no field-level redaction: [3](#0-2) . Job pipeline specs (DOT/TOML observation source) for bridge-based tasks reference the bridge name as a plain-text task parameter, which is part of the persisted job spec and therefore reachable by any caller of this endpoint that can view the job.

`BridgeTypesController.Show` takes the bridge name from the path, finds the bridge, and returns `presenters.NewBridgeResource(bt)` without any role check: [4](#0-3) . `NewBridgeResource` always sets `OutgoingToken` from the stored bridge type, with a JSON tag lacking `omitempty` (unlike `IncomingToken`, which is only ever populated on `Create`): [5](#0-4) . This means the outgoing token — a credential the node uses to authenticate outbound to the external adapter — is disclosed to any authenticated caller who knows (or can enumerate/guess/learn from a job) the bridge name, regardless of role.

### Impact Explanation
This matches the Chainlink bounty "secret/credential disclosure" impact class: a low-privilege (view-role) API token or session, which should only be able to read non-sensitive resource state, can retrieve a bridge's `outgoingToken`. That token can be used to impersonate the node to the external adapter/bridge endpoint, potentially manipulating bridge responses that feed into oracle jobs, or allowing the attacker to directly call the external adapter as the node.

### Likelihood Explanation
This is a low-effort, highly repeatable disclosure. It requires only a valid view-role session or API token — no privilege escalation or edit/admin role is needed. The two required requests (`GET /v2/jobs/:ID` then `GET /v2/bridge_types/:BridgeName`) are both reachable with baseline authentication, and the bridge name is either already known to a view-role operator (bridges are frequently named descriptively) or discoverable from a job's spec/pipeline. `GET /v2/bridge_types` (index, unwrapped) can also enumerate all bridge names directly without needing the job-chain at all, making exploitation trivial.

### Recommendation
- Wrap `authv2.GET("/bridge_types/:BridgeName", bt.Show)` and `authv2.GET("/bridge_types", ...)` with a role check appropriate for viewing secrets (e.g., `auth.RequiresEditRole` or `auth.RequiresAdminRole`), or strip `OutgoingToken`/`IncomingToken` from `BridgeResource` entirely for `Show`/`Index` and only ever return `IncomingToken` transiently on `Create`.
- Independently, add `omitempty`-style redaction so `OutgoingToken` is never serialized by default in `NewBridgeResource`, requiring an explicit opt-in only for the create response.
- Optionally, gate `JobsController.Show`/`Index` behind role checks consistent with the sensitivity of embedded pipeline data (bridge names, URLs), though the core fix is at the bridge secret boundary.

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, using existing test harness like `cltest.NewApplication` + `client.HTTPClientCloser` used throughout `core/web/*_test.go`):
1. Create a bridge type via admin/edit-role client: `POST /v2/bridge_types` with a name (e.g. `secretbridge`) and confirm the response contains `incomingToken`.
2. Create a job (e.g. an OCR/Cron job with a `type=bridge name="secretbridge"` pipeline task) via edit-role client.
3. Create a view-role user/API token (using `mocks.User{Role: user.ViewRole}` or equivalent auth test helper).
4. As the view-role client:
   - `GET /v2/jobs/:ID` and assert the response body's `observationSource`/pipeline field contains the string `secretbridge`.
   - `GET /v2/bridge_types/secretbridge` and assert the response JSON contains `outgoingToken` with a non-empty value equal to the bridge's stored `OutgoingToken`.
5. Assert failure of the invariant: expect the test to demonstrate that `outgoingToken` (and, in a stricter policy, the bridge name via jobs) is present in the view-role response, proving credential confinement is violated. A fixed implementation would return `403 Forbidden` on step 4's bridge fetch for view-role, or omit `outgoingToken` from the payload entirely.

```go
func (jc *JobsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	var err error
	jobSpec := job.Job{}
	if externalJobID, pErr := uuid.Parse(c.Param("ID")); pErr == nil {
		// Find a job by external job ID
		jobSpec, err = jc.App.JobORM().FindJobByExternalJobID(ctx, externalJobID)
	} else if pErr = jobSpec.SetID(c.Param("ID")); pErr == nil {
		// Find a job by job ID
		jobSpec, err = jc.App.JobORM().FindJob(ctx, jobSpec.ID)
	} else {
		jsonAPIError(c, http.StatusUnprocessableEntity, pErr)
		return
	}
	if err != nil {
		if errors.Is(errors.Cause(err), sql.ErrNoRows) {
			jsonAPIError(c, http.StatusNotFound, errors.New("job not found"))
		} else {
			jsonAPIError(c, http.StatusInternalServerError, err)
		}
		return
	}

	jsonAPIResponse(c, presenters.NewJobResource(jobSpec), "jobs")
}
```

```go
// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```

```go
// BridgeResource represents a Bridge JSONAPI resource.
type BridgeResource struct {
	JAID
	Name          string `json:"name"`
	URL           string `json:"url"`
	Confirmations uint32 `json:"confirmations"`
	// The IncomingToken is only provided when creating a Bridge
	IncomingToken          string       `json:"incomingToken,omitempty"`
	OutgoingToken          string       `json:"outgoingToken"`
	MinimumContractPayment *assets.Link `json:"minimumContractPayment"`
	UseConnectionManager   bool         `json:"useConnectionManager"`
	CreatedAt              time.Time    `json:"createdAt"`
}

// GetName implements the api2go EntityNamer interface
func (r BridgeResource) GetName() string {
	return "bridges"
}

// NewBridgeResource constructs a new BridgeResource
func NewBridgeResource(b bridges.BridgeType) *BridgeResource {

	}
```
