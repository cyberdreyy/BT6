### Title
Unprotected-ref job can flip `config.Protected` via crafted cache key and collide with a protected-ref's cache volume/hostPath name - (File: executors/docker/volume.go)

### Summary
`createVolumesManager` sets `config.Protected = e.Build.IsProtected() || protectedKeyIdx >= 0`, where `protectedKeyIdx` is derived purely from attacker-controlled `spec.Cache.Key` strings ending in `-protected`. Because the resulting Docker volume name / host cache path is `UniqueName` (project-scoped, not ref/protection-scoped) + hash(destination) + conditional `-protected` suffix, an unprivileged job on an unprotected branch can reproduce the exact volume name / host directory used by legitimately protected jobs of the same project, gaining read/write access to that protected cache.

### Finding Description
`protectedKeyIdx` is computed from `e.Build.Cache[i].Key` with no origin/trust check - the cache key is fully attacker-controlled CI config (`cache:key:` in `.gitlab-ci.yml`) and requires no elevated permission to set on a non-protected branch/MR. [1](#0-0) 

`config.Protected` feeds `manager.withProtected`, which appends `-protected` to the volume/host path name whenever `Protected` is true, with no distinction between "genuinely protected ref" and "attacker set a matching cache key": [2](#0-1) 

The volume name (`createCacheVolume`) and host-based cache path (`createHostBasedCacheVolume`) are both built from `m.config.UniqueName` (project-scoped, e.g. `ProjectRealUniqueName()`, not branch/ref-scoped) plus `hashPath(destination)` plus the conditional protected suffix: [3](#0-2) [4](#0-3) 

Since `UniqueName` and `hashPath(destination)` do not depend on ref protection, they are identical between a legitimate protected-ref build and an unprotected-ref build using the same project and the same cache `destination` path. The only variable differentiating the resulting name is `config.Protected`, which the attacker fully controls by naming a cache key with the `-protected` suffix. Docker's `VolumeCreate` API is idempotent for an existing name (it returns/attaches to the existing volume rather than failing), and for host-based cache the path is a plain filesystem join, so the attacker's container mounts the same underlying volume/directory a protected job would use for that path. There is no additional check (ownership, ACL, label validation preventing "Protected" mismatch with `e.Build.IsProtected()`) blocking this - `addCacheVolume`/`createCacheVolume` only labels the volume with the (attacker-influenced) `protected` boolean for informational purposes; it does not enforce any separate namespace for genuinely protected volumes versus keyed-in "protected" volumes beyond the naming suffix that the attacker can also produce.

### Impact Explanation
An unprivileged pipeline author on an unprotected branch/MR can read from and write to the cache volume/host directory that is normally reserved for protected-ref jobs of the same project (assuming the cache `destination` path matches, which is normal since cache paths are typically fixed in the shared `.gitlab-ci.yml`). This breaks the protected-ref cache isolation invariant introduced specifically to segregate protected and unprotected cache storage, allowing cross-protection-boundary cache read/write (e.g., poisoning a protected job's cache with attacker-controlled artifacts, or exfiltrating cache contents intended to be isolated to protected refs).

### Likelihood Explanation
Fully attacker-reachable: the attacker only needs commit access to a non-protected branch/MR (a common, low-privilege scenario) and control over `cache:key` in `.gitlab-ci.yml`, which is a completely ordinary CI configuration field. No special runner config or admin action is required. The collision is deterministic given matching `destination` (cache path), which is typically shared across jobs/branches in the same project's `.gitlab-ci.yml`.

### Recommendation
Do not let job-supplied cache key content influence `config.Protected`. Derive volume protection strictly from `e.Build.IsProtected()` (or another trusted CI/CD-provided signal such as protected-ref metadata from the GitLab backend), or if per-cache-key protection is desired, cryptographically bind the "protected" designation to a value that cannot be forged by pipeline config alone (e.g., separate volume namespace validated server-side, not just a name string suffix guessable/settable by the job author).

### Proof of Concept
```go
func TestCreateVolumesManager_UnprotectedRefWithProtectedCacheKeyCollidesWithProtectedVolumeName(t *testing.T) {
    destination := "/cache/path"

    // Legitimate protected-ref build, no special cache key.
    protectedBuild := &common.Build{
        JobResponse: common.JobResponse{
            Cache: common.Caches{{Key: "normal-key"}},
        },
    }
    protectedBuild.GitInfo.Ref = "main" // marks protected via IsProtected() == true in test double
    // config for protected build: Protected == true

    // Attacker build on unprotected branch, cache key crafted with -protected suffix.
    attackerBuild := &common.Build{
        JobResponse: common.JobResponse{
            Cache: common.Caches{{Key: "foo-protected"}},
        },
    }
    // attackerBuild.IsProtected() == false, but protectedKeyIdx >= 0 => config.Protected == true

    protectedVolumeName := computeCacheVolumeName(protectedBuild, destination) // Protected=true
    attackerVolumeName := computeCacheVolumeName(attackerBuild, destination)   // Protected=true via key trick

    // BUG: names collide, disproving isolation.
    assert.Equal(t, protectedVolumeName, attackerVolumeName,
        "unprotected job with '-protected' cache key produces same volume name as protected-ref job")
}
```
Expected result confirming the bug: `protectedVolumeName == attackerVolumeName` (both include the `-protected` suffix derived from `UniqueName` + `hashPath(destination)`), demonstrating the attacker's container binds to the same Docker volume / host cache directory used by protected-ref jobs.

func (m *manager) createHostBasedCacheVolume(destination string) error {
	destination, err := m.absolutePath(destination)
	if err != nil {
		return fmt.Errorf("defining absolute path: %w", err)
	}

	err = m.managedVolumes.Add(destination)
	if err != nil {
		return fmt.Errorf("updating managed volumes list: %w", err)
	}

	// The leaf directory dir has a name with a length of:
	//	- 42 chars when protected
	//	- 32 chars when not protected (the length of the md5sum only)
	dir := m.withProtected(hashPath(destination))
	hostPath := m.parser.Path().Join(m.config.CacheDir, m.config.UniqueName, dir)

	m.appendVolumeBind(&parser.Volume{
		Source:      hostPath,
		Destination: destination,
	})

	return nil
}

func (m *manager) createCacheVolume(
	ctx context.Context,
	destination string,
	reusable bool,
) (string, error) {
	destination, err := m.absolutePath(destination)
	if err != nil {
		return "", fmt.Errorf("defining absolute path: %w", err)
	}

	err = m.managedVolumes.Add(destination)
	if err != nil {
		return "", fmt.Errorf("updating managed volumes list: %w", err)
	}

	hashedDestination := hashPath(destination)
	name := m.config.TemporaryName
	if reusable {
		name = m.config.UniqueName
	}

	// volumeName might get quite long. Docker is however happy to create volumes with long names. There is the "myth"
	// that volume names are treated like DNS labels, and thus only allow a length of 63 chars, however that does not hold
	// true. In fact, we already create way longer names, and would catch those issues in various integration tests.
	volumeName := m.withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))

	vBody := client.VolumeCreateOptions{
		Name:       volumeName,
		Driver:     m.config.Driver,
		DriverOpts: m.config.DriverOpts,
		Labels: m.labeler.Labels(map[string]string{
			"destination": destination,
			"protected":   strconv.FormatBool(m.config.Protected),
			"reusable":    strconv.FormatBool(reusable),
			"type":        "cache",
		}),
	}

	v, err := m.client.VolumeCreate(ctx, vBody)
	if err != nil {
		return "", fmt.Errorf("creating docker volume: %w", err)
	}

	if m.permissionSetter != nil {
		err = m.permissionSetter.Set(ctx, v.Name, m.labeler.Labels(map[string]string{"type": "cache-init"}))
		if err != nil {
			return "", fmt.Errorf("set volume permissions: %w", err)
		}
	}

	m.appendVolumeBind(&parser.Volume{
		Source:      v.Name,
		Destination: destination,
	})
	m.logger.Debugln(fmt.Sprintf("Using volume %q as cache %q...", v.Name, destination))

	return volumeName, nil
}

// withProtected returns a string with a specific suffix when the config states, we are running against a protected
// ref, or when any of the cache keys includes the `-protected` suffix.

func (m *manager) withProtected(s string) string {
	if !m.config.Protected {
		return s
	}
	return s + protectedSuffix
}
