### Title
A single dust APR0 withdrawal request permanently DoSes `stopEpoch` once the APR is raised above zero - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` is invoked from `IdleCDOEpochVariant.stopEpoch` for every epoch close. When `apr0TotalPrincipal != 0` it hard-reverts `NotAllowed` if `unscaledApr != 0` [1](#0-0) . Any KYC'd lender can leave `apr0TotalPrincipal` non-zero forever with a dust `requestWithdraw` made while the pool is in APR0 mode, because the only code paths that decrement the global bucket are (a) the same `prepareStopEpochWithApr0` that reverts before reaching `apr0TotalPrincipal = 0` [2](#0-1) , and (b) `_clearWithdrawClaimForEpoch` during a default-finalized claim [3](#0-2) . Once the manager raises the APR for a later epoch — a routine, honest operation — every subsequent `stopEpoch` reverts and the pool can no longer close its epoch.

### Finding Description
1. Manager sets APRs to `(0, 0)` via `setAprs` (APR0 is a supported operating mode of the vault).
2. Attacker (KYC-passing lender) deposits a minimal amount and calls `cdoEpoch.requestWithdraw(1, AAtranche)` — or any dust amount. In `IdleCreditVault.requestWithdraw` the `unscaledApr == 0` branch routes into `_requestWithdrawApr0`, which does `apr0TotalPrincipal += _amount` and stores `apr0Users[user].principalEpoch = epochNumber` [4](#0-3) . `_settleApr0` cannot clear it because it early-returns while `reqEpoch >= epochNumber` [5](#0-4) .
3. The attacker abandons the position. Per-user `apr0Users[user].principal` cannot be touched by anyone else, and `_settleApr0` only zeroes the per-user entry — it never decrements the global `apr0TotalPrincipal` [6](#0-5) .
4. Manager later sets a positive APR (`setAprs(apr, 0)`) for a subsequent epoch — standard operation.
5. At `epochEndDate`, `manager.stopEpoch(...)` calls `IdleCreditVault.prepareStopEpochWithApr0`, which sees `_principal = apr0TotalPrincipal != 0`, skips the fast path, and hits `if (unscaledApr != 0) revert NotAllowed()` [7](#0-6) . The revert is unconditional: it fires before the interest split and before `apr0TotalPrincipal = 0`, so no amount of waiting or retrying helps.

Broken invariant: liveness of the epoch state machine. `stopEpoch` is the only way to realize interest, roll `epochNumber`, and mature pending withdraw receipts (`epochNumber <= lastWithdrawRequest` gating in `_claimFundedWithdrawRequest` [8](#0-7) ). With `stopEpoch` bricked, the pool is stuck in a running epoch: no lender can claim funded receipts, no borrower repayment can be booked, and interest accrual freezes. The only escapes are (a) the manager reverting the APR to 0 — forcing the pool to run at zero yield to regain liveness — or (b) an actual borrower default finalized via `finalizeDefault`, i.e. eating a real loss to unbrick claims. Neither is accessible to unprivileged users and both carry direct economic cost.

This maps the CVE's bug class (low-privileged input → repeatable crash/hang of the service) onto the vault's epoch finalization path: a cheap unprivileged state write (`apr0TotalPrincipal += dust`) makes the privileged-but-honest `stopEpoch` transaction permanently revert.

### Impact Explanation
Temporary freezing of all user funds plus a forced economic choice. While bricked: matured withdraw receipts cannot be claimed, borrowers cannot repay into `stopEpoch`, deposits may proceed but are locked, and AA/BB holders cannot exit at par. To restore liveness the operator must either run the pool at 0 APR (yield theft-equivalent for all LPs for at least one full `epochDuration`) or trigger and finalize a default (haircutting everyone by the recovery ratio). Quantified cost of the attack: one minimum-size deposit plus a dust `requestWithdraw` — the attacker loses only the dust principal; the pool loses at least one epoch of yield or suffers a forced default haircut on the full NAV.

### Likelihood Explanation
High when APR0 epochs are in use: the attack requires only that the manager has, at some point, configured `unscaledApr == 0` (a designed mode exercised by `testApr0WithdrawGetsInterestAtStopEpoch` [9](#0-8) ). The attacker needs only pass the same `isWalletAllowed`/Keyring KYC check as any lender, spend a dust amount, and wait for a routine APR raise. No privileged collusion, no oracle manipulation, no reentrancy required. Note: pools that never use APR=0 configuration are not exposed.

### Recommendation
Do not couple epoch liveness to residual APR0 state. Options:

- In `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, close the bucket (`apr0TotalPrincipal = 0`, store `apr0RateByEpoch[epochNumber] = 0`) instead of reverting — APR0 requesters simply forgo interest on an epoch that ran at positive APR, which matches their economic position anyway.
- Alternatively, make `requestWithdraw` settle/carry forward APR0 principal rather than re-bucketing it, so the aggregate is always drained by normal settlement.
- At minimum, add an owner/manager escape (e.g. `clearApr0Bucket()`) so a stale dust bucket cannot hold `stopEpoch` hostage.

### Proof of Concept
Foundry-style sketch on the existing `IdleCreditVault.t.sol` harness:

```solidity
function testApr0DustRequestBricksFutureStopEpoch() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    // 1. Pool legitimately operates at APR = 0
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // 2. Attacker: KYC'd lender, dust deposit + dust withdraw request
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 100, true);          // minimal allowed deposit
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // 1 wei of tranche tokens

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    assertGt(vault.apr0TotalPrincipal(), 0);         // global bucket poisoned

    // Attacker walks away; nothing clears apr0TotalPrincipal for them.

    // 3. Normal epochs run while APR is 0
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

    // 4. Manager raises APR for the next epoch — honest, routine operation
    vm.prank(manager);
    vault.setAprs(initialProvidedApr, 0);
    assertGt(vault.unscaledApr(), 0);

    // 5. Next stopEpoch reverts unconditionally
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, type(uint128).max); // borrower fully solvent
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // 6. Repeatable: it is not a transient failure
    vm.warp(block.timestamp + 30 days);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // 7. Consequence: all pending receipts stay frozen behind the epoch gate
    // (_claimFundedWithdrawRequest reverts while epochNumber <= lastWithdrawRequest)
}
```

Caveat: the exact call site inside `IdleCDOEpochVariant.stopEpoch` was located by name search (`prepareStopEpochWithApr0` appears in `contracts/IdleCDOEpochVariant.sol`) but its surrounding guard conditions were not fully re-verified in this session; the PoC above assumes it is invoked unconditionally on every `stopEpoch`, which the revert-visible guard structure and existing APR0 tests support.
