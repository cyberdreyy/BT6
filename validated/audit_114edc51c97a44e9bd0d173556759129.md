### Title
Claimed instant-withdraw receipts leave residual per-epoch claim basis that corrupts default recovery accounting — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[user]` but never deletes `instantWithdrawsRequestsByEpoch[user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. Like the Palmera `removeOrg` bug, deleted user state leaves residue that a later accounting round (`finalizeDefaultRecovery`) silently inherits, inflating both the default claim basis and the assumed prefunded reserve.

### Finding Description
In `requestInstantWithdraw` the strategy records three pieces of state per request (`IdleCreditVault.sol:356-375`):
- `instantWithdrawsRequests[user] += amount`
- `instantWithdrawsRequestsByEpoch[user][epochNumber] += amount`
- `instantWithdrawClaimsByEpoch[epochNumber] += amount`

When the user claims, `claimInstantWithdrawRequest` only resets the first of these (`IdleCreditVault.sol:387-392`):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;   // per-epoch entries left behind
_transferFundedClaim(_user, amount);
```

There is no `instantWithdrawsRequestsByEpoch[user][epoch] = 0` and no `instantWithdrawClaimsByEpoch[epoch] -= amount`. The only place those are ever decremented is `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:847-853`), which runs only after default finalization.

This residual basis is consumed by the default-recovery path:
- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the defaulted claim basis whenever `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-648`).
- `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` and treats it as underlying already held in the strategy (`IdleCreditVault.sol:716-723`).

So when a user has already been paid, their stale per-epoch entry is still counted (a) as outstanding claim basis and (b) as prefunded reserve that no longer exists in the contract (it was transferred out).

### Impact Explanation
If the borrower defaults in the same epoch in which an instant-withdraw receipt was funded and already claimed:

- `prefundedReserve` is overstated by the already-paid amount → `reserveAmount` and thus `recoveryPrice` in `finalizeDefaultRecovery` are computed against funds that are not actually held (`IdleCreditVault.sol:685-692`).
- `totalBasis` is simultaneously overstated by the phantom claim.
- The net effect is a mismatch between accounted reserve and real balance: either real claimants are diluted (recovery price lowered by dead claims, permanently stranding the excess reserve dust), or the accounted reserve exceeds the contract balance so the last claimants' `safeTransfer` in `_transferDefaultRecovery` reverts — permanent freezing of unclaimed recovery funds.

Broken invariant: one receipt one payout — a paid receipt is paid a second time *into the accounting*, and solvency of the recovery reserve is violated.

### Likelihood Explanation
Requires: (1) an instant-withdraw request in epoch N, (2) the CDO funding it via `collectInstantWithdrawFunds` while `pendingInstantWithdraws` remains non-zero (partial funding of the instant queue — explicitly contemplated by the code comments at `IdleCreditVault.sol:636-640` and `_defaultPrefundedInstantReserve`), (3) the user claiming, and (4) borrower default finalized while `epochNumber` is still N. This is a narrow but realistic sequence — partial instant-queue funding followed by default mid-epoch is exactly the scenario the prefunded-reserve logic was written for. No privileged misbehavior is needed; the fulfiller/funder is the honest CDO, and the attacker can simply be the lender who claims and lets the residue stand, or any subsequent claimant harmed by it. I note some uncertainty on the exact timing (whether `collectInstantWithdrawFunds` can occur mid-epoch in production configurations), which determines whether the stale epoch can coincide with `defaultRecoveryEpoch`; if instant claims are only funded at epoch boundaries, the impact is reduced and this may be unreachable.

### Recommendation
Mirror the fix used for normal withdraws (`_clearWithdrawClaimForEpoch`): in `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[user][lastRequestEpoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, i.e. fully delete all per-epoch state when a receipt is paid out — not just the aggregate slot. Add an invariant test asserting `instantWithdrawClaimsByEpoch[e] == sum of unclaimed instantWithdrawsRequestsByEpoch[*][e]`.

// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
// Fork test sketch (extend test/foundry/IdleCreditVault.t.sol setup)

function testStaleInstantClaimBasisInflatesDefaultRecovery() external {
    uint256 amount = 10000 * ONE_SCALE;

    // 1. LP deposits, epoch starts running
    idleCDO.depositAA(amount);
    _toggleEpoch(true, 0, 0);

    // 2. user requests instant withdraw in epoch N
    vm.prank(user1);
    cdoEpoch.requestInstantWithdraw(amount, address(AAtranche));
    uint256 epoch = creditVault.epochNumber();
    assertEq(creditVault.instantWithdrawClaimsByEpoch(epoch), amount);

    // 3. CDO partially funds instant queue; collectInstantWithdrawFunds
    //    reduces pendingInstantWithdraws but instantWithdrawClaimsByEpoch
    //    keeps the full amount.
    //    (simulate partial fund leaving pendingInstantWithdraws > 0)

    // 4. user claims -> aggregate cleared, per-epoch basis NOT cleared
    vm.prank(user1);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(creditVault.instantWithdrawsRequests(user1), 0);
    // RESIDUE: still non-zero after full payout
    assertEq(creditVault.instantWithdrawsRequestsByEpoch(user1, epoch), amount);
    assertEq(creditVault.instantWithdrawClaimsByEpoch(epoch), amount);

    // 5. borrower defaults in same epoch; finalizeDefaultRecovery reads
    //    defaultPendingClaimBasis() which still includes the paid receipt,
    //    and _defaultPrefundedInstantReserve() counts paid-out funds as held.
    //    -> recoveryPrice / reserveAmount computed on phantom basis,
    //    leaving reserve under-backed and later claims reverting or diluted.
}
