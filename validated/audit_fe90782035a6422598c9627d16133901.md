### Title
`BlockRejection` signature does not bind `reason_code`/`response_data`, allowing forged reject-reason attribution to another signer - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` only signs `signer_signature_hash` (plus `chain_id`); it does not cover `reason`, `reason_code`, or `response_data` (which carries `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, etc.). `BlockRejection::verify`/`recover_public_key` therefore validate a signature that is bound to far less content than the fields that drive consensus-relevant tallying in `store_and_process_block_rejection`. Any party that has observed one authentic rejection signature from a signer for a given block can re-package it with a different `reason_code`/`response_data` and have it accepted by peers as an authentic message from that signer.

### Finding Description
`BlockRejection::hash()` in [1](#0-0)  computes the signed digest solely from `self.signer_signature_hash` (via a structured-data domain tuple keyed only on chain_id) — `reason`, `reason_code`, and `response_data` are excluded from the hash. `sign()`, `verify()`, and `recover_public_key()` all operate on this same restricted hash [2](#0-1) .

On the signer side, `handle_block_rejection` trusts the identity recovered purely from this restricted signature to authenticate the *entire* message, including the untouched `response_data.reject_reason`: [3](#0-2) 
It recovers the public key with `rejection.recover_public_key()`, checks `is_valid_signer`, and then calls `store_and_process_block_rejection` passing `(&rejection.response_data.reject_reason).into()` — a field that was never covered by the signature that was just verified.

`store_and_process_block_rejection` uses that unauthenticated `reject_reason` to tally weight toward the `ReorgNotAllowed` bucket, which can flip the local sortition view to mark a miner invalid: [4](#0-3) 

Because `reason_code`/`response_data` are unauthenticated relative to the signature, anyone holding a single genuine `BlockRejection` byte blob from signer B for a specific `signer_signature_hash` (these are broadcast in the clear over StackerDB and readable by any observer, including the miner and other signers) can splice in a different `reason_code`/`response_data.reject_reason`/`failed_txid` while keeping B's original signature bytes untouched — the signature still recovers to B and still verifies, since none of the tampered fields participate in the hash. The node-side listener performs a similar decoupled check (`rejected_data.recover_public_key()` compared only to the StackerDB slot owner) [5](#0-4) , so the same gap is reachable from the node's tallying path (`total_weight_rejected`, `failed_txids` per-txid weight accounting) as well.

This breaks the equality "signed content == validated content": the cryptographic signature is supposed to bind a signer to the *specific rejection reason and response data* they intended, but it only binds them to the block hash. A forger (a single miner or a single colluding signer relaying gossip) can attribute an arbitrary `RejectReason` (e.g. `ReorgNotAllowed`) or arbitrary `failed_txid`/extend-timestamp data to another signer without that signer's consent.

### Impact Explanation
This falls under the "rejection recounted" / miscounted-response class the rules define as Critical, and at minimum meets the High bar ("a signer wedged... or acting on a stale/incorrect signer input"). Concretely:
- `store_and_process_block_rejection` uses the forged `reject_reason` (`ReorgNotAllowed`) weight to flip `sortition_state.cur_sortition.miner_status` to `InvalidatedBeforeFirstBlock`, wrongly invalidating a legitimate miner's tenure for other signers that process the forged message — a liveness/safety-relevant miscount driven by data the signature never covered.
- On the node side (`stackerdb_listener.rs`), forged `failed_txid`/`reason_code` values feed `failed_txids` weight accounting used to temporarily/permanently exclude transactions from block templates, again driven by data outside the signature's scope.
- The forged message is accepted because both the signer and node paths authenticate strictly against the narrow `signer_signature_hash`-only digest, never re-deriving identity from, or binding it to, the full message payload actually acted upon.

### Likelihood Explanation
Reaching this requires only observing one legitimately signed rejection from any signer for a block (trivially available: rejections are broadcast in the clear over StackerDB and mirrored via the event observer) and then re-wrapping the identical `signature`/`signer_signature_hash`/`chain_id` triple with attacker-chosen `reason`, `reason_code`, and `response_data`. This is achievable by a single miner or a single signer (well within "a one-slot miner plus gossip" scope) with no majority collusion, no access to the victim signer's private key, and no reliance on transport-layer StackerDB write authorization for the *victim's* slot — because the attacker only needs a channel that authenticates the attacker's own identity/slot to the receiver; the inner `BlockRejection.recover_public_key()` result (not the outer StackerDB chunk owner) is what `handle_block_rejection` actually trusts as "who rejected this."

### Recommendation
Extend the structured-data hash in `BlockRejection::hash()` to include `reason_code` and the full `response_data` (or a hash of them) alongside `signer_signature_hash` and `chain_id`, so that any tampering with the reject reason, failed txid, or extend timestamps invalidates the signature. Apply the same fix pattern to any other libsigner v0 message types whose optional/auxiliary fields are excluded from their signed digest.

### Proof of Concept
1. Signer B legitimately rejects block proposal `P` (hash `H`) with `RejectReason::ValidationFailed(BadTransaction)` and `failed_txid = None`; it broadcasts `BlockRejection { signer_signature_hash: H, reason_code: ValidationFailed(BadTransaction), response_data: { reject_reason: ValidationFailed(BadTransaction), failed_txid: None, ... }, signature: sig_B }` over its StackerDB slot, per `BlockRejection::from_validate_rejection` / `sign()` (`libsigner/src/v0/messages.rs:1767-1814`).
2. Attacker A (any other signer, or the miner relaying gossip) observes this broadcast (public StackerDB chunk / event observer feed).
3. A constructs a new `BlockRejection` value reusing the *exact same* `signer_signature_hash = H`, `chain_id`, and `signature = sig_B`, but sets `reason_code = RejectCode::ValidationFailed(ValidateRejectCode)` → e.g. flips `response_data.reject_reason` to `RejectReason::ReorgNotAllowed` (or changes `failed_txid` to target an arbitrary transaction).
4. A wraps this crafted `BlockRejection` in `SignerMessage::BlockResponse(BlockResponse::Rejected(..))` and writes it to A's own StackerDB slot, signed with A's own key (a normal write A is authorized to make).
5. Every other signer's `handle_block_response` → `handle_block_rejection` (`stacks-signer/src/v0/signer.rs:2208-2264`) calls `rejection.recover_public_key()`, which recomputes the hash from `H`/`chain_id` only, recovers B's pubkey (since `sig_B` still verifies against that restricted hash), passes `is_valid_signer(B)`, and stores the forged `reject_reason = ReorgNotAllowed` as if B itself reported it, feeding `store_and_process_block_rejection`'s `total_reorg_reject_weight` tally (`stacks-signer/src/v0/signer.rs:2340-2368`).
6. If enough forged/legitimate `ReorgNotAllowed` weight accumulates this way, `sortition_state.cur_sortition.miner_status` is incorrectly set to `InvalidatedBeforeFirstBlock`, even though B never actually voted `ReorgNotAllowed` — demonstrating the signature-scope gap concretely changes signer state based on unauthenticated fields.

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

    /// Handle an observed rejection from another signer
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
            (&rejection.response_data.reject_reason).into(),
        );
