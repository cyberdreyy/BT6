### Title
Double-refund / token inflation via `DeterministicStateInitAction` partial refund surviving receipt-level rollback - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
`action_deterministic_state_init` issues an immediate, action-level `Receipt::new_balance_refund` for the unused portion of `action.deposit` as soon as storage staking is satisfied, and this refund receipt is merged into the receipt's `new_receipts` list before any later action in the same receipt runs. If a subsequent action in the same batch subsequently fails (including the receipt-level post-loop `check_storage_stake` re-check against the *final* storage usage), the whole receipt's `state_update` is rolled back and the standard failure-path refund additionally re-refunds the *entire* `total_deposit` of the receipt — including the deposit already partially refunded by the successful `DeterministicStateInit` action — producing a duplicate refund and net token inflation.

### Finding Description
`action_deterministic_state_init` computes `deposit_refund` from `check_storage_stake(account, account.amount(), ...)` immediately after `deploy_deterministic_account` [1](#0-0) , and unconditionally pushes a `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)` into `result.new_receipts` [2](#0-1) .

In `apply_action_receipt`, each per-action `ActionResult` (including the one above) is merged into the receipt-level `result` via `result.merge(new_result)?` *before* checking whether that action (or the loop as a whole) failed [3](#0-2) . So a partial refund receipt queued by a successful `DeterministicStateInit` action is retained in `result.new_receipts` even if a *later* action in the same batch fails, or even if the final post-loop `check_storage_stake` re-check (run only when the whole loop succeeded, against the truly final `account.storage_usage()`) fails and calls `result.set_error(LackBalanceForState)` [4](#0-3) .

When `result.result` ends up `Err`, `state_update.rollback()` discards all trie-level state changes (account creation, contract deployment, balance updates) [5](#0-4)  — but `rollback()` only affects the `TrieUpdate`, not the in-memory `result.new_receipts` vector, which is untouched and later emitted as real outgoing receipts [6](#0-5) .

Separately, `refund_unspent_gas_and_deposits` computes, on failure, `deposit_refund = total_deposit` where `total_deposit` sums **every** action's deposit in the whole receipt, including the `DeterministicStateInitAction`'s full `action.deposit` [7](#0-6) . This full-deposit refund receipt is generated *in addition to* the already-queued partial refund from the successful `DeterministicStateInit` action, because that partial refund was never withdrawn when the receipt subsequently failed.

Net effect: for a deposit `X` attached to `DeterministicStateInitAction` where only `Y < X` was needed for storage staking, the attacker receives `(X − Y)` from the action-level refund plus `X` again from the failure-path total-deposit refund, i.e. `2X − Y` instead of the correct `X`. The extra `(X − Y)` is minted with no corresponding on-chain state change (everything was rolled back), constituting real token inflation payable to `receipt.balance_refund_receiver()`, which the attacker (predecessor) controls.

### Impact Explanation
This is a token-inflation / fund-creation bug: an attacker mints `(X − Y)` NEAR per exploited receipt (bounded only by how much deposit they attach beyond the storage-staking requirement and how many times they can repeat the batch), directly matching the "token inflation or loss" bounty category. It requires no privileged access — only crafting a normal multi-action receipt (e.g. via a transaction with multiple actions, or a `FunctionCall` promise batch) that includes a `DeterministicStateInitAction` followed by any action guaranteed to fail after storage usage increases (or simply any action guaranteed to fail, since a failing later action in the loop suffices even without needing to specifically fail the storage check).

### Likelihood Explanation
Fully reachable by an unprivileged account: submit a single receipt/transaction whose action list contains `DeterministicStateInitAction` (with `action.deposit` set comfortably above the storage-stake requirement) followed by any action that deterministically errors (e.g. a `FunctionCall` to a nonexistent method, or an action deliberately made to exceed storage/gas limits). No special permissions, validator access, or races are needed — the ordering and the merge-before-error-check behavior in `apply_action_receipt` is deterministic and repeatable every time.

### Recommendation
Do not allow a successful action's partial refund receipts to survive if the overall receipt later fails: either (a) have `apply_action_receipt` discard/roll back any `new_receipts` produced by actions preceding a failing action/step (mirroring the `state_update.rollback()` semantics), or (b) have `refund_unspent_gas_and_deposits`'s failure path subtract any deposit already refunded by earlier successful actions from `total_deposit` before generating the failure refund, so the total refunded on any failure path never exceeds the receipt's originally attached deposits.

### Proof of Concept
Runtime integration test (e.g. in `runtime/runtime/tests` or via `RuntimeTestFixture`):
1. Build an action receipt with actions `[DeterministicStateInitAction { state_init, deposit: X }, FailingAction]` where `X` exceeds the required storage-stake amount `Y` for `state_init`, and `FailingAction` is any action guaranteed to error against the receiver account (e.g. a `FunctionCall` to an undefined method, causing the per-action loop to break with `result.result = Err`).
2. Run `Runtime::apply_action_receipt` (or full `Runtime::apply`) on this receipt.
3. Assert: the deterministic account is *not* created in the resulting state (rollback occurred).
4. Assert: sum of all emitted `Receipt::new_balance_refund` amounts to `receipt.balance_refund_receiver()` equals `X` (correct behavior) — the bug is proven if the sum instead equals `2X − Y` (i.e., both the action-level partial refund `X - Y` and the failure-path full refund `X` are present in `outgoing_receipts`/`instant_receipts`).

            action.deposit

                let new_balance = safe_add_balance(account.amount(), missing_amount)?;
                account.set_amount(new_balance);
                action

                    account_id: account_id.clone(),
                    amount: missing_amount,
                }
                .into());
                return Ok(());
            }
        }
        Err(StorageStakingError::StorageError(err)) => {
            return Err(RuntimeError::StorageError(StorageError::StorageInconsistentState(err)));
