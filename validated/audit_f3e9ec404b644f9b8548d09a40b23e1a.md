### Title
Unauthenticated disclosure of internal health-check names and error details via GET /readyz?full=1 - ([File: core/web/health_controller.go])

### Summary
`healthRoutes` registers `GET /readyz` with no authentication middleware, unlike `/debug` and the pprof `metricRoutes`, which require `auth.Authenticate`. `HealthController.Readyz` returns, for any request with a `full` query parameter, a JSON list of `presenters.Check` entries containing each internal service's name and its raw `error.Error()` output, whereas `PublicReadyz` was purpose-built to strip that same data and is documented as doing so "to avoid leaking internal service state on publicly reachable endpoints."

### Finding Description
`NewRouter` mounts `/readyz`, `/public-readyz`, `/health`, `/health.txt` via `healthRoutes(app, api)` with only the global rate limiter and session middleware applied — no `auth.Authenticate*` wrapper: [1](#0-0) . Compare this to `/debug/vars`, which is wrapped in `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` [2](#0-1) , and to `metricRoutes` (pprof), which is only reachable via the authenticated `authv2` group [3](#0-2) .

`HealthController.Readyz` checks for the presence of any `full` query key (`c.GetQuery("full")`, value not inspected) and, if present, builds `presenters.Check` entries per failing/passing internal check, embedding `err.Error()` as `Output`, then serializes them as a JSON:API response: [4](#0-3) . This is functionally identical to what `Health`/`/health` already exposes unauthenticated, but the codebase's own comment on `PublicReadyz` states the intent is that a public-facing readiness probe must never emit per-check detail: [5](#0-4) .

The unit tests confirm the current (intended) behavior directly: `TestHealthController_Readyz` only asserts the status code on `/readyz` (no auth setup, no body assertion) [6](#0-5) , while `TestHealthController_PublicReadyz` explicitly asserts `/public-readyz?full=true` returns an empty body [7](#0-6) . There is no test asserting `/readyz?full=true` withholds detail — it doesn't.

### Impact Explanation
An unauthenticated network client (no token, no session, no admin role) can call `GET /readyz?full=1` and receive a list of internal service/component names (health-check identifiers such as chain clients, DB, subsystem names) plus the literal error strings returned by each failing `HealthReporter`, e.g. connectivity/config errors from `services.HealthReporter` implementations such as `StandardCapabilities.Ready()` [8](#0-7) . This is an information-disclosure issue (internal topology/component names and error text), matching a low/informational "internal service disclosure" bounty class — it is not by itself a credential leak, authentication bypass, or fund-movement primitive, but it does violate the documented security intent that only `PublicReadyz` is safe for exposure and `Readyz` (full detail) should not be reachable without authentication.

### Likelihood Explanation
Trivial and fully repeatable: no credentials, roles, or special network position are required beyond reaching the node's HTTP API port (the same reachability required for `/health`, which already exposes equivalent detail unauthenticated) [1](#0-0) . A single unauthenticated `GET` request triggers full disclosure whenever any registered health check is failing.

### Recommendation
Wrap `/readyz` (full-detail path) in the same authentication requirement used for `/debug`, or split it so that only `PublicReadyz`-style minimal status is served unauthenticated and the detailed `full=` output is moved behind `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` (or a separate authenticated route, e.g. `/readyz/full`). Note that `/health` and `/health.txt` have the identical exposure pattern and should be reviewed under the same fix if they are intended to be non-public.

### Proof of Concept
Handler-level integration test (extending `core/web/health_controller_test.go`):
1. Build `app := cltest.NewApplicationWithKey(t)` with a mocked `healthChecker` where `IsReady()` returns `(false, map[string]error{"chain.evm.1": errors.New("rpc dial failed: internal-db-host:5432")})`.
2. `client := app.NewHTTPClient(nil)` (no auth headers/session cookie set).
3. `resp, _ := client.Get("/readyz?full=true")` — assert `resp.StatusCode == http.StatusServiceUnavailable`.
4. Read body, unmarshal JSON:API `checks` array, assert it contains an entry with `Name == "chain.evm.1"` and `Output` containing `"internal-db-host:5432"`.
5. Repeat with `client.Get("/public-readyz?full=true")` on the same failing checker and assert the body is empty (already covered by `TestHealthController_PublicReadyz`), demonstrating the discrepancy between the two "public" readiness endpoints.

func (hc *HealthController) Readyz(c *gin.Context) {
	status := http.StatusOK

	checker := hc.App.GetHealthChecker()

	ready, errors := checker.IsReady()

	if !ready {
		status = http.StatusServiceUnavailable
	}

	c.Status(status)

	if _, ok := c.GetQuery("full"); !ok {
		return
	}

	checks := make([]presenters.Check, 0, len(errors))

	for name, err := range errors {
		status := HealthStatusPassing
		var output string

		if err != nil {
			status = HealthStatusFailing
			output = err.Error()
		}

		checks = append(checks, presenters.Check{
			JAID:   presenters.NewJAID(name),
			Name:   name,
			Status: status,
			Output: output,
		})
	}

	// return a json description of all the checks
	jsonAPIResponse(c, checks, "checks")
}

// Ready is a non-blocking check for the service's ready state.  Errors if not
// ready when called.
func (s *StandardCapabilities) Ready() error {
	if err := s.StateMachine.Ready(); err != nil {
		return err
	}
	select {
	case <-s.readyChan:
		// Startup goroutine has finished; surface its outcome (nil on success,
		// the WaitCtx/Initialise/Infos error otherwise).
		return s.getReadyErr()
	case <-s.stopChan:
		return ErrServiceStopped
	default:
		return ErrServiceNotReady
	}
}
