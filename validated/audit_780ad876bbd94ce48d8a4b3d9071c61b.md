### Title
ETH sent to `ConvexStrategyETH` is permanently locked — `receive()` accepts arbitrary ETH but no function can recover it — (File: contracts/strategies/convex/ConvexStrategyETH.sol)

### Summary
`ConvexStrategyETH` declares `receive() external payable {}` (needed to accept ETH unwrapped from WETH and returned by Curve's `remove_liquidity`), but it performs no validation on `msg.sender` and the strategy contains no ETH-sweep or native-balance rescue path. `_depositInCurve` forwards only the freshly unwrapped WETH balance (`{value: _balance}`), so any ETH pushed to the contract outside that flow sits in `address(this).balance` forever. The only recovery helper, `transferToken` in `ConvexBaseStrategy`, transfers ERC20 tokens and cannot move native ETH.

### Finding Description
In `contracts/strategies/convex/ConvexStrategyETH.sol`:

```solidity
function _depositInCurve(uint256 _minLpTokens) internal override {
    IWETH9 _weth = IWETH9(WETH);
    uint256 _balance = _weth.balanceOf(address(this));
    _weth.withdraw(_balance);
    uint256[2] memory _depositArray;
    _depositArray[depositPosition] = _balance;
    ICurveDeposit_2token(_curvePool(curveLpToken)).add_liquidity{value: _balance}(_depositArray, _minLpTokens);
}

receive() external payable {}
```

- `receive()` accepts ETH from **any** sender — there is no `require(msg.sender == WETH || msg.sender == curvePool)` guard as in `LidoCDOTrancheGateway.sol` (`require(msg.sender == wethToken, "only-weth")`).
- `add_liquidity` is called with `{value: _balance}` where `_balance` is only the WETH just unwrapped — the pre-existing/native ETH balance is never included or accounted for.
- `price()`/`getContractValue` accounting is based on Curve LP / Convex positions, so stray ETH is not credited to anyone and can never be redeemed.
- Unlike `LidoCDOTrancheGateway`, where `_mintStEth(address(this).balance)` incidentally recycles stray ETH into the next deposit, here nothing ever consumes `address(this).balance`.

### Impact Explanation
Any ETH that reaches the strategy — an accidental plain transfer by a depositor, ETH dust pushed by a reward/refund path, or ETH self-destructed into the contract — is permanently frozen. There is no owner, guardian, or CDO callable that returns it, mirroring the external report's "no way to withdraw ETH paid" bug class: value enters the contract balance but has no exit. Given an ETH-denominated tranche strategy, user-facing deposits routed through any helper that mis-forwards ETH (or plain user error) result in unrecoverable loss.

### Likelihood Explanation
Likelihood is moderate: the contract deliberately exposes an open `receive()` on a user-facing strategy, ETH pools are exactly the deployment context for this contract, and mistaken direct transfers to token/strategy contracts are a recurring real-world occurrence. The loss is bounded by whatever ETH is sent (unrecoverable, not a protocol insolvency), which keeps severity below High but the freezing is permanent and requires only an unprivileged transaction.

### Recommendation
Restrict the receive hook to the two legitimate senders and add an owner-only sweep for native balance:

```solidity
receive() external payable {
    require(
        msg.sender == WETH || msg.sender == _curvePool(curveLpToken),
        "only-weth-or-pool"
    );
}

function sweepETH(address _to) external onlyOwner nonReentrant {
    (bool ok, ) = _to.call{value: address(this).balance}("");
    require(ok, "sweep-failed");
}
```

Alternatively, fold `address(this).balance` into `_depositArray[depositPosition]` so stray ETH is absorbed into the next deposit rather than locked.

### Proof of Concept
Foundry fork test (mainnet fork, ETH-based Convex strategy deployed and initialized):

```solidity
function test_ETHStuckInConvexStrategyETH() public {
    // strategy: deployed ConvexStrategyETH (e.g. stETH/ETH pool)
    uint256 balBefore = address(strategy).balance;

    // unprivileged sender pushes ETH directly
    vm.deal(attacker, 1 ether);
    vm.prank(attacker);
    (bool ok, ) = address(strategy).call{value: 1 ether}("");
    assertTrue(ok); // receive() accepts from anyone

    assertEq(address(strategy).balance, balBefore + 1 ether);

    // deposit flow does not consume stray ETH: add_liquidity uses only WETH balance
    vm.prank(address(cdo));
    strategy.deposit(100e18); // normal WETH deposit path
    assertEq(address(strategy).balance, balBefore + 1 ether); // still stuck

    // no ETH recovery: transferToken only handles ERC20
    vm.expectRevert();
    vm.prank(owner);
    strategy.transferToken(address(0), 1 ether, owner); // ERC20 transfer on addr(0) fails

    // ETH remains permanently locked
    assertEq(address(strategy).balance, balBefore + 1 ether);
}
```

Note: I was unable to read the full `_redeem`/`transferToken` bodies in `ConvexBaseStrategy.sol` within the available iterations; the finding rests on `receive()` being unguarded and `add_liquidity` forwarding only `_balance` (the unwrapped WETH amount), both directly verified. If `transferToken` in `ConvexBaseStrategy` were implemented to special-case native ETH (unlike `IdleStrategy.sol:210`, which is ERC20-only via SafeERC20), the finding would be weakened — worth confirming in a full session.
