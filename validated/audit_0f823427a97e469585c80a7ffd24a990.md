### Title
Rejection weight double-counted across proposal retries via un-reset `failed_txids` map, enabling minority-weight signers to force permanent transaction exclusion - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListenerComms::reset_rejections` resets the vote-counting fields used for the 30%-rejection timeout retry (`responded_signers`, `total_weight_rejected`) but never clears `failed_txids`, the per-transaction weight accumulator that the signing coordinator uses to decide which transactions get permanently banned from future block proposals. On every retry of the *same* block proposal (same `signer_signature_hash`), the same minority of rejecting signers can re-add their weight to `failed_txids` without limit, eventually pushing a txid's recorded weight past the 30% "blocking minority" threshold even though no more than a minority of real signer weight ever rejected it.

### Finding Description
`BlockResponse::Rejected` handling only credits a signer's weight into `total_weight_rejected` and `failed_txids` when `block.responded_signers.insert(slot_id)` succeeds (i.e., the signer hasn't already been counted for this round): [1](#0-0) 

When the rejection-timeout path fires (a minority of signers reject, but not enough to hit the 30% blocking threshold, and the retry timer elapses), the coordinator calls `reset_rejections` to allow the *same* proposal to be re-evaluated: [2](#0-1) 

`reset_rejections` clears `responded_signers` and zeroes `total_weight_rejected`, explicitly to let rejecting signers "vote again" on the retried proposal, but it does not touch `failed_txids`: [3](#0-2) 

Because `responded_signers` was cleared, the same rejecting signer(s) resending their (unchanged) rejection for the retried block are treated as "new" votes and re-enter the crediting branch. `total_weight_rejected` is correctly bounded (it was reset to 0 and then rebuilt only from the current round's votes), but the nested `failed_txids` entry for the reported txid is *not* reset — it is simply added to again: [4](#0-3) 

Each retry round (driven purely by the miner's `block_rejection_timeout_steps` timer elapsing, not by any signer majority) lets the same minority weight accumulate again in `info.total_weight`/`info.problematic_weight`, so after enough retries a txid's recorded weight exceeds `blocking_minority` even though the real number of distinct signers (and their true weight) rejecting it never changed and never reached 30%.

When the block is eventually globally rejected (or on a later round where `total_weight_rejected` legitimately crosses 30% from fresh votes), the coordinator consults this inflated, un-reset map to decide exclusion: [5](#0-4) 

If `info.problematic_weight` (inflated by repeated counting) exceeds `blocking_minority`, the txid is inserted into `permanently_excluded_txids` and is banned from all future block proposals for that mining process — even though a genuine 30%+ weight of the signer set never agreed to ban it.

### Impact Explanation
This breaks the equality between "aggregated rejection weight recorded by the coordinator" and "verified, distinct weight of signers that actually rejected." A minority of signers (well under the blocking 30%) can, together with the miner's own retry cadence (a one-slot miner property — the miner controls how often it retries/times out and calls `reset_rejections`), inflate `failed_txids` weight past the 30% threshold purely through vote replay across rounds. This causes the coordinator to permanently exclude a transaction from block production based on a miscounted quorum, which is a liveness wedge: a transaction that a genuine supermajority would have accepted is permanently blacklisted by the mining process due to the counting bug, not due to real signer consensus.

### Likelihood Explanation
Reachable by a single miner (who legitimately controls the retry/timeout cadence via `block_rejection_timeout_steps`) plus ordinary gossip replay from an existing minority of rejecting signers resending their unchanged rejection on each retried proposal for the same block — no signer majority, no key compromise, and no auth token access is required. This is a normal operational scenario (a proposal that a minority object to, on a slow/contentious network with several retries), not a contrived edge case.

### Recommendation
Clear `failed_txids` (or otherwise cap/deduplicate weight contributions per signer address across rounds, independent of the ephemeral `responded_signers` set) inside `reset_rejections`, mirroring the explicit design already applied to `total_weight_rejected`. Alternatively, track per-signer contributions to `failed_txids` using signer address/slot as a key so a signer's weight is only counted once for a given txid regardless of how many rounds it has rejected across, until the underlying block proposal itself changes.

### Proof of Concept
1. Miner proposes block B (`signer_signature_hash = H`) that includes transaction T.
2. A minority (< 30% weight) of signers reject B, citing T as `ValidateRejectCode::ProblematicTransaction`. `failed_txids[T].total_weight` and `.problematic_weight` accumulate that minority's weight (e.g., 25%).
3. `total_weight_rejected` (25%) is below the blocking threshold, so the miner's rejection timer eventually elapses (`rejections_timer.elapsed() > rejections_timeout`), and the coordinator calls `stackerdb_comms.reset_rejections(H)`, clearing `responded_signers`/`total_weight_rejected` to 0 but leaving `failed_txids[T]` at 25%.
4. The miner resends the identical proposal for H. The same minority of signers, still holding the same rejection decision, re-broadcast their `Rejected` response for H/T.
5. Because `responded_signers` was cleared, `block.responded_signers.insert(slot_id)` again returns `true` for these signers, so their weight is added *again* to `failed_txids[T]` (now 50%), even though only 25% real distinct weight ever rejected T.
6. Repeat steps 3-5 (or accumulate one more genuine round) until `info.problematic_weight` for T exceeds `blocking_minority` (30%), causing `permanently_excluded_txids` to include T — banning a transaction that never had genuine 30%+ signer weight against it, purely due to the un-reset counter.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
