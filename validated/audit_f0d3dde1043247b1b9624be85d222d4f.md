Confirmed: no method anywhere in `lockup/src/owner.rs` or `lockup/src/foundation.rs` allows changing `staking_pool_whitelist_account_id` post-deployment — it's set once by whichever `create()` transaction wins the account-creation race in `lockup-factory/src/lib.rs`.### Title
`create()` in `lockup-factory/src/lib.rs` lets an unprivileged attacker win a deployment race and permanently bind an arbitrary `owner_account_id`'s lockup to an attacker-chosen `staking_pool_whitelist_account_id` - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the target lockup's account ID deterministically from `owner_account_id` alone via `sha256(owner_account_id)` and imposes no restriction on who may call it or what `whitelist_account_id` they pass. Because two `create()` calls for the same `owner_account_id` collide on the exact same NEAR account, whichever transaction's `create_account()` action is processed first wins, and its `staking_pool_whitelist_account_id` is permanently baked into the deployed `LockupContract` with no owner- or foundation-accessible setter to change it afterward.

### Finding Description
**Binding claimed:** `LockupArgs.staking_pool_whitelist_account_id` (as stored in the deployed lockup for `owner_account_id = victim`) `==` `official_whitelist_account_id` (the value the legitimate issuer intended to bind for `victim`).

**Code path:**
- `lockup_account_id = sha256(owner_account_id)[..20] + "." + factory_account`, computed purely from the caller-supplied `owner_account_id` [1](#0-0) .
- `staking_pool_whitelist_account_id` defaults to the factory's configured whitelist but is fully overridable by the caller-supplied `whitelist_account_id: Option<ValidAccountId>` with no membership check against any registry of "known-good" whitelists [2](#0-1) .
- `create()` has no `assert_eq!(predecessor_account_id, owner_account_id)` and no restriction tying the caller to the account being created for; anyone (attacker) can call `create(owner_account_id=victim, whitelist_account_id=Some(attacker_whitelist))` [3](#0-2) .
- The chosen `staking_pool_whitelist_account_id` is serialized into `LockupArgs` and passed to `new()` on the freshly created account via `Promise::new(lockup_account_id).create_account().deploy_contract(...).function_call(b"new", ...)` [4](#0-3) .
- `LockupContract.staking_pool_whitelist_account_id` is a plain field set once at `new()` [5](#0-4) , and is used unconditionally by `select_staking_pool` to check `is_whitelisted` against that fixed whitelist contract [6](#0-5) . There is no owner or foundation method in `lockup/src/owner.rs` or `lockup/src/foundation.rs` that can change `staking_pool_whitelist_account_id` after deployment.

**Exploit flow:** If a legitimate issuer and an attacker both submit `create(owner_account_id=victim, ...)` with different `whitelist_account_id` values, both promises target the identical `lockup_account_id`. NEAR's `create_account()` for an already-existing account fails, so only one of the two `function_call("new", ...)` sequences actually initializes state; the other's `on_lockup_create` callback observes `is_promise_success() == false` and refunds the attached deposit to its own predecessor [7](#0-6) . Whichever transaction is ordered first by the block producer becomes the permanent, unchangeable `staking_pool_whitelist_account_id` for `victim`'s lockup, regardless of who the "rightful" issuer was intended to be.

Existing guards (`assert_self()`, `is_promise_success()`, `MIN_ATTACHED_BALANCE` check) only handle promise-failure bookkeeping and deposit refunding; none of them validate that the caller is authorized to choose `owner_account_id` or `whitelist_account_id`, so they do not prevent the race.

### Impact Explanation
This matches the rules' explicitly listed Critical category: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." If the attacker wins, `victim`'s lockup is permanently bound to a whitelist contract the attacker controls. The attacker can subsequently list malicious "staking pool" contracts in that whitelist; if `victim` (the lockup owner) later calls `select_staking_pool` and `deposit_and_stake` against one of those, delegated NEAR can be routed to a pool that never returns it, since the whitelist's core security guarantee (only NEAR-Foundation-vetted pools can honor the "delegated funds cannot be lost" spec) is what protects lockup owners. It is also possible the attacker's whitelist rejects all legitimate pools, permanently blocking `victim` from ever staking through the standard whitelist (funds not frozen since transfer/withdraw still work, but staking access is corrupted for the life of the contract, since there is no setter). This is not one-shot: it can be attempted against any freshly-intended `owner_account_id` before the legitimate issuer's transaction lands.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to know (or predict) the `owner_account_id` for which a legitimate issuer is about to call `create()`, and to have `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus gas available - this is public information/observable via mempool or predictable naming conventions for large token grants. No special privileges, keys, or foundation access are required. The race is a matter of transaction submission timing/ordering, which any unprivileged network participant can attempt repeatedly and cheaply (each losing attempt only costs gas since the deposit is refunded on failure, and even the winning attempt's principal deposit simply funds `victim`'s lockup, not lost to the attacker). This is highly feasible against any account id known in advance to be a target for lockup issuance.

### Recommendation
Restrict `whitelist_account_id` in `create()` to only accept values from a foundation-maintained allow-list (e.g., require it equal to `self.whitelist_account_id` or be validated via a call to the whitelist contract's `is_factory_whitelisted`), or drop the caller-supplied override entirely and always use the factory's configured `whitelist_account_id`. Additionally, add a foundation-only method on the lockup contract to update `staking_pool_whitelist_account_id` post-deployment as a remediation path for accounts already created with a malicious whitelist.

### Proof of Concept

2. Deploy a second whitelist contract `attacker_whitelist` controlled by `attacker`.
3. In the same block, submit two `create` transactions concurrently:

   - tx_b: signer = attacker, owner_account_id = "victim", whitelist_account_id = Some(attacker_whitelist)
4. Await both; assert exactly one lockup account exists at sha256("victim")+"."+factory.
5. Query the deployed lockup's `staking_pool_whitelist_account_id` (add a temporary getter or inspect via `view_state`) and assert it equals whichever tx was processed first, NOT deterministically `official_whitelist`.

7. As secondary confirmation, call `select_staking_pool` on the resulting lockup as `victim` and show it consults `attacker_whitelist` (i.e., `ext_whitelist::is_whitelisted` targets `attacker_whitelist`), proving the mis-binding is live and exploitable.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
