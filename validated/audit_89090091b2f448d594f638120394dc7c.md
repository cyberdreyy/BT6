### Title
Loss-adjusted withdraw receipts read `lossRecoveryPriceByEpoch` under the request epoch, but `collectWithdrawFunds` writes it under the post-increment epoch — haircut silently bypassed, par claims drain the funded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The bundler bug is a "same name, wrong source" resolution flaw: an artifact is fetched from whichever source happens to answer first, not the intended one. The analog in `IdleCreditVault` is the epoch key used to store and later retrieve a stop-epoch loss haircut for withdraw receipts. `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]`, but every consumer — `_claimLossAdjustedWithdrawRequest` and the re-request guard in `requestWithdraw` — resolves the haircut via `lastWithdrawRequest[_user]`, which was snapshotted at request time, one epoch earlier. The receipt therefore resolves its haircut from a different epoch bucket than the one the loss was stored under, so the haircut is never applied.

### Finding Description
When a user calls `requestWithdraw`, the vault records `lastWithdrawRequest[_user] = epochNumber` (current epoch N) and `withdrawsRequestsByEpoch[_user][N]` at `IdleCreditVault.sol:282-293`. When the epoch ends, the CDO's `stopEpoch` flow calls `deposit()`, which executes `epochNumber += 1` because the epoch is still marked running (`IdleCreditVault.sol:607-610`). If the borrower short-funds the epoch, `collectWithdrawFunds` then stores the haircut under the already-incremented key: `lossRecoveryPriceByEpoch[epochNumber]` = epoch N+1 (`IdleCreditVault.sol:414-421`).

At claim time, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns 0 (`IdleCreditVault.sol:789-795`). Execution falls through to `_claimFundedWithdrawRequest`, whose only gate is `epochNumber > lastWithdrawRequest` — now N+1 > N, satisfied — so it pays the user the full un-haircut `withdrawsRequests[_user]` at par via `_transferFundedClaim` (`IdleCreditVault.sol:326-349`).

The re-request guard in `requestWithdraw` has the same off-by-one source: it looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0, so it never blocks a new request even though an uncleared loss-adjusted receipt exists under N+1 (`IdleCreditVault.sol:261-271`).

The same mismatch applies to defaulted receipts: `defaultRecoveryEpoch = epochNumber` is recorded after the bump, while `_claimDefaultedWithdrawRequest` clears the claim under `defaultRecoveryEpoch`, leaving `withdrawsRequestsByEpoch[_user][N]` residue that `_claimFundedWithdrawRequest` can later pay at par (`IdleCreditVault.sol:693, 772-784`).

### Impact Explanation
Only `pendingBasis - _amount` worth of underlyings was actually pulled into the strategy for the loss-adjusted epoch (`IdleCreditVault.sol:427-429`), yet every affected receipt pays out 100% of its claim basis. The first claimants on a loss epoch extract more than their pro-rata share of the funded amount; the deficit lands on later claimants, whose claims revert on insufficient balance — direct theft plus permanent freezing of other users' unclaimed withdrawals. Loss = `(claimBasis × (RECOVERY_FULL − lossRecoveryPrice) / RECOVERY_FULL)` per early claimant, up to the entire haircut amount of the epoch. The same mechanism lets a defaulted-epoch receipt be re-paid at par after finalization, double-spending the funded balance outside the isolated `defaultRecoveryReserve`.

### Likelihood Explanation
Triggering requires only a normal `requestWithdraw` during any epoch that later settles with `stopEpochWithDuration(_lossAmount > 0)` or a borrower default — no privileged action by the attacker is needed beyond holding tranches. Given any epoch where the borrower short-funds pending receipts (the exact scenario the loss-adjusted path was built for), every receipt holder on that epoch automatically escapes the haircut. Likelihood is bounded by how often short-funded stop epochs occur, but when they do the exploit is deterministic and requires no timing race.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the epoch the pending receipts belong to, not by the post-increment `epochNumber`. Concretely, in `collectWithdrawFunds` store under the request epoch (e.g., `epochNumber - 1` after the stop bump, or better, pass the settled epoch explicitly from the CDO), or conversely store `lastWithdrawRequest[_user]` as `epochNumber + 1` so both sides agree. Add an invariant test: request in epoch N → stop with partial loss → assert the claim equals `claimBasis × lossRecoveryPrice / RECOVERY_FULL` and that `pendingWithdraws`-funded underlyings exactly cover all claims.

### Proof of Concept
Reproducible Foundry fork PoC (sketch, `test/foundry/`):

```solidity
// Setup: deposit AA, startEpoch, then requestWithdraw in epoch N
idleCDO.depositAA(amount);
cdoEpoch.startEpoch();
uint256 receipt = cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
uint256 reqEpoch = strategy.epochNumber();          // N
assertEq(strategy.lastWithdrawRequest(user), reqEpoch);

// stopEpoch with a partial loss: deposit() bumps epochNumber to N+1
// then collectWithdrawFunds writes lossRecoveryPriceByEpoch[N+1]
deal(underlying, borrower, shortFundedAmount);
cdoEpoch.stopEpoch(lossAmount, expectedInterest);   // internally: deposit -> epochNumber N+1 -> collectWithdrawFunds(shortAmount)

assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);        // lookup key used by claim -> miss
assertGt(strategy.lossRecoveryPriceByEpoch(reqEpoch + 1), 0);    // stored under bumped epoch

// User claims at PAR instead of haircut
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(user) - balPre;
assertEq(paid, receipt);                                          // full claimBasis, haircut skipped
// Expected per spec: paid == receipt * lossRecoveryPriceByEpoch[N+1] / RECOVERY_FULL
```

Uncertainty note: the exploit assumes `deposit()` (which increments `epochNumber`) runs before `collectWithdrawFunds` inside the CDO `stopEpoch`/`stopEpochWithDuration` path — consistent with the comment at `IdleCreditVault.sol:607-610`; the exact call ordering lives in `IdleCDOEpochVariant.stopEpochWithDuration` and should be confirmed when writing the PoC. If the ordering is reversed, the storage key and lookup key still diverge for receipts requested during the buffer period, preserving the same mismatch class.
