### Title
Runner-configured `--user` privilege restriction is silently bypassed when `shell=pwsh`/`powershell` is selected - ([File: executors/shell/shell.go])

### Summary
`executor.Prepare` unconditionally propagates the runner-configured `options.User` into `s.Shell().User` regardless of which shell is configured, but only `BashShell.GetConfiguration` (`shells/bash.go:489-505`) actually consumes `info.User` to wrap the job script with `su`. When the shell executor is configured with `--user` to sandbox jobs as an unprivileged local account, but the shell is `pwsh`/`powershell`, the resulting `common.ShellConfiguration` produced for PowerShell has no equivalent privilege-drop wrapper, so the job process is launched directly under the runner service's own identity.

### Finding Description
`executor.Prepare` at `executors/shell/shell.go:32-34` does:
```go
if options.User != "" {
    s.Shell().User = options.User
}
```
This value flows through `AbstractExecutor.Prepare` into `common.ShellScriptInfo.User`, which is later passed to `shell.GetConfiguration(info)` to build the `common.ShellConfiguration` consumed by `executor.Run` (`executors/shell/shell.go:99`, `newCommander(s.BuildShell.Command, args, cmdOpts)`).

`BashShell.GetConfiguration` (`shells/bash.go:477-506`) is the only shell implementation confirmed to branch on `info.User`:
```go
if info.User == "" {
    return script, nil
}
script.Command = "su"
...
```
It rewrites `script.Command`/`script.Arguments` to `su ... -c <original command line>`, so the actual OS process the executor spawns is `su`, which drops privileges to the configured user.

No such branch was found consumed inside PowerShell's `GetConfiguration` (`shells/powershell.go`) function body for privilege dropping — the `Command`/`Arguments` built for `pwsh`/`powershell` are the interpreter invocation only, with no `runas`/impersonation wrapper equivalent to `su`. Since the choice of shell (`pwsh` vs `bash`) is a job-level/runner-config `.gitlab-ci.yml`/`config.toml` setting that a pipeline author can select whenever the runner is configured to allow multiple shells, an attacker who can pick `shell: pwsh` for their job on a runner sandboxed with `--user` gets a script executed directly as the runner process's OS identity rather than the restricted account.

### Impact Explanation
On a shell executor host configured with `--user <restricted-user>` specifically to sandbox job execution, a job that selects `shell: pwsh` (or `powershell`) runs as the runner service account instead of the intended restricted account — a privilege escalation relative to the administrator's configured security boundary, with no additional authentication or exploit needed beyond selecting the shell.

### Likelihood Explanation
Requires: (1) runner configured with `[[runners]] ... shell = ...` shell executor and `--user` set, and (2) the job or `.gitlab-ci.yml` able to select `pwsh`/`powershell` for that runner (either as the configured default shell for the runner, or if the runner allows shell override). This is fully attacker-controlled once those runner preconditions hold, and is deterministic/repeatable — every job using `pwsh` on that runner runs unrestricted.

### Recommendation
Implement equivalent user-restriction enforcement in `PowerShellShell.GetConfiguration` (e.g., via a `runas`/scheduled-task-based impersonation wrapper on Windows, or reject/fail `Prepare` when `options.User` is set but the selected shell doesn't support privilege dropping), and add a shared check in `executor.Prepare` that fails fast if `options.User != ""` and the resolved shell does not support user restriction, instead of silently ignoring it.

### Proof of Concept
Go unit test in `shells/powershell_test.go`:
```go
func TestPowerShellGetConfiguration_IgnoresUser(t *testing.T) {
    shell := &PowerShellShell{Shell: SNPwsh}
    info := common.ShellScriptInfo{User: "restricted-user", Type: common.LoginShell}
    cfg, err := shell.GetConfiguration(info)
    require.NoError(t, err)
    // Bug: expected wrapping with a privilege-drop mechanism, but none present
    assert.NotContains(t, strings.ToLower(cfg.Command), "runas")
    for _, a := range cfg.Arguments {
        assert.NotContains(t, strings.ToLower(a), "restricted-user")
    }
}
```
Complement with an integration test: configure a shell executor runner with `--user restricted-user`, run one job with `shell: bash` asserting `whoami` == `restricted-user`, and a second job with `shell: pwsh`/`powershell` asserting `whoami` != `restricted-user` (equals the runner service account), proving the bypass. func (b *BashShell) GetConfiguration(info common.ShellScriptInfo) (*common.ShellConfiguration, error) {
	script := &common.ShellConfiguration{
		Command: b.Shell,
		CmdLine: b.Shell,
	}

	if info.Type == common.LoginShell || info.Type == common.InteractiveShell {
		script.CmdLine += " -l"
		script.Arguments = []string{"-l"}
	}
	script.DockerCommand = []string{"sh", "-c", b.bashDetectScript(info.Type == common.LoginShell || info.Type == common.InteractiveShell)}

	if info.User == "" {
		return script, nil
	}

	script.Command = "su"
	if runtime.GOOS == OSLinux {
		script.Arguments = []string{"-s", "/bin/" + b.Shell, info.User, "-c", script.CmdLine}
	} else {
		script.Arguments = []string{info.User, "-c", script.CmdLine}
	}

	script.CmdLine = script.Command
	for _, arg := range script.Arguments {
		script.CmdLine += " " + helpers.ShellEscape(arg)
	}

	return script, nil
}
