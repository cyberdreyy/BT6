### Title
Settled APR0 withdraw receipts bypass the epoch-loss guard and escape `lossRecoveryPriceByEpoch` haircut — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`requestWithdraw` uses `lastWithdrawRequest[_user]` to pin a user's most recent request epoch so that a `lossRecoveryPriceByEpoch` haircut recorded by `collectWithdrawFunds`/`stopEpochWithDuration` cannot be orphaned. The guard at `IdleCreditVault.sol:263-271` only blocks a new request when the old epoch's basis still sits in `withdrawsRequestsByEpoch[user][lossEpoch]` or in the *open* `apr0Users[user].principal` slot. An APR0 (`unscaledApr == 0`) receipt is never written to `withdrawsRequestsByEpoch` (it is routed to `_requestWithdrawApr0` at line 285-286), and once `_settleApr0` runs, `principal` is zeroed into `settledPrincipal`/`settledInterest`. Neither settled bucket is checked by the guard, so the user can open a new request, overwrite `lastWithdrawRequest`, and later claim the settled APR0 amount at par through `_claimFundedWithdrawRequest` (lines 338-349) — permanently skipping the epoch-N haircut. This mirrors the CVE bug class: `RemoveChild` dangling/removal of a node no longer tracked, i.e., a claim erased from the bookkeeping structure while still payable.

### Finding Description
1. LP deposits in an APR0 (`unscaledApr == 0`) credit vault and calls `requestWithdraw` during the buffer phase of epoch N. The request is routed to `_requestWithdrawApr0`; `lastWithdrawRequest[user] = N`; nothing is written to `withdrawsRequestsByEpoch` (lines 282-294).
2. Epoch N stops with a realized loss. `collectWithdrawFunds`/`stopEpochWithDuration` records `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` and clears `pendingWithdraws` (lines 411-421), while `_settleApr0` moves the user's `principal` into `settledPrincipal`/`settledInterest` inside `apr0Users[user]`.
3. The attacker calls `requestWithdraw` again in epoch N+1. The guard evaluates `withdrawsRequestsByEpoch[user][N] == 0` and `apr0Users[user].principal == 0`, so it does not revert; `lastWithdrawRequest[user]` is overwritten to N+1 (line 282).
4. On the next `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[user] = N+1`, finds `lossRecoveryPriceByEpoch[N+1] == 0`, and returns 0 (lines 789-795). `_claimFundedWithdrawRequest` then pays `settledPrincipal + settledInterest` in full and deletes `apr0Users[user]` (lines 339-348).

The epoch-N haircut is never applied to the settled APR0 receipt — a direct loss-socialization escape. The same overwrite orphans any haircut for the *normal* receipt only when a `withdrawsRequestsByEpoch` entry exists, so APR0 mode is the unique gap: the guard tracks `principal`/`principalEpoch` but not `settledPrincipal`/`settledInterest`.

### Impact Explanation
The attacker receives 100% of a claim that should have been paid at `lossRecoveryPriceByEpoch[N]` (e.g., 70%). The difference is drawn from funded strategy underlyings via `_transferFundedClaim`, which only protects `defaultRecoveryReserve` — it does not know the claim should have been discounted. Other LPs and pending claimants absorb the overpayment, breaking the loss-waterfall invariant and reducing solvency by `(1 − lossRecoveryPrice) × settledApr0Amount` per exploiting user.

### Likelihood Explanation
Requires an APR0-mode credit vault (`unscaledApr == 0`), an attacker holding a matured/settled APR0 withdraw receipt across a loss epoch, and one extra `requestWithdraw`. No privileged collusion needed — the attacker is a plain KYC'd lender. Likelihood is gated by (a) APR0 vaults being deployed and (b) a `stopEpochWithDuration`/loss funding path coexisting with APR0 receipts, which the code explicitly supports (`apr0TotalPrincipal`, `apr0RateByEpoch`, `previewLossAdjustedWithdrawFunds`). Uncertainty: if in practice APR0 and loss-adjusted stop are never combined, impact is latent rather than live.

### Recommendation
In `requestWithdraw`, extend the `lossRecoveryPrice != 0` guard to also revert when the user holds any unsettled claim tied to `lossEpoch`, i.e., check `apr0Users[user].settledPrincipal != 0 || apr0Users[user].settledInterest != 0` (or track `settledPrincipalEpoch`) in addition to the open `principal` check. Alternatively, apply `lossRecoveryPriceByEpoch[lossEpoch]` to the settled APR0 buckets inside `_claimFundedWithdrawRequest`/`_settleApr0` before paying at par.

### Proof of Concept
Foundry fork PoC outline against `IdleCreditVault` + `IdleCDOEpochVariant` in APR0 mode:

```solidity
// 1. Configure vault with unscaledApr == 0 (APR0 mode), deposit via depositAA for attacker.
uint256 shares = cdoEpoch.depositAA(1000e6);           // attacker LP deposit
cdoEpoch.startEpoch();                                 // epoch N running (manager)
cdoEpoch.stopEpoch(apr, 0);                            // stop epoch N

// 2. Attacker requests withdraw in buffer of epoch N+1 -> routed to _requestWithdrawApr0,
//    lastWithdrawRequest[attacker] = N+1, nothing in withdrawsRequestsByEpoch.
cdoEpoch.requestWithdraw(shares, address(AAtranche));

// 3. Run epoch with loss so collectWithdrawFunds records
//    lossRecoveryPriceByEpoch[N+1] = e.g. 0.7e18 and _settleApr0 moves
//    apr0Users[attacker].principal -> settledPrincipal.
cdoEpoch.startEpoch();
cdoEpoch.stopEpochWithDuration(apr, lossAmount);       // loss haircut recorded

// 4. Guard passes because withdrawsRequestsByEpoch == 0 and principal == 0 after settle.
cdoEpoch.requestWithdraw(smallShares, address(AAtranche)); // lastWithdrawRequest overwritten

// 5. After next epoch, claim: loss-adjusted path finds price == 0, funded path
//    pays settledPrincipal + settledInterest at PAR (no 30% haircut).
cdoEpoch.startEpoch(); cdoEpoch.stopEpoch(apr, 0);
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
// assert paid == full settled amount instead of amount * lossRecoveryPrice / 1e18
```

Expected assertion: `underlying.balanceOf(attacker) - balPre` equals the un-haircut settled amount, while `lossRecoveryPriceByEpoch[lossEpoch] < RECOVERY_FULL` — demonstrating the skipped haircut.

Note: I was unable to read the bodies of `_settleApr0`/`_requestWithdrawApr0` in the available context, so the exact storage field names for the settled epoch pointer (e.g., whether a `settledPrincipalEpoch` exists) and whether settlement zeroes `principalEpoch` should be confirmed when implementing the PoC.
