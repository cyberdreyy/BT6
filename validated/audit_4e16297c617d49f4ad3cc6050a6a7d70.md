### Title
Epoch interest charged to the borrower is computed over fixed `epochDuration` instead of actual elapsed time, lowering payments when the epoch runs long - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The Teller bug class — capping/prorating a repayment amount with the wrong time base so late repayment is charged as a single scheduled installment — maps directly onto `IdleCDOEpochVariant._calcInterestWithApr`. The interest the borrower must pay for an epoch is computed as `_amount * (_apr / 100) * epochDuration / (365 days * ONE_TRANCHE_TOKEN)`, i.e. always exactly one `epochDuration`'s worth of interest, regardless of how much time actually elapsed between `startEpoch` and `stopEpoch`.

### Finding Description
- `_calcInterestWithApr` uses the constant `epochDuration` as the time factor, not the real elapsed time of the epoch. [1](#0-0) 
- `stopEpoch` only enforces `block.timestamp >= epochEndDate` (lower bound); there is no upper bound, and no recomputation of owed interest against `block.timestamp - epochStart`. The resolved interest is `expectedEpochInterest` (or an override), both derived from the fixed-duration formula. [2](#0-1) 
- This is the same shape as the reported EMI bug: there `min(cycleAmount * owedTime / cycleDuration, cycleAmount + interest)` clamped a multi-cycle repayment down to roughly one cycle. Here, `apr * epochDuration` permanently bakes in "one cycle" — if the epoch is stopped at `epochEndDate + T`, the borrower enjoyed the principal for `epochDuration + T` but pays interest only for `epochDuration`. The uncharged `T` of interest is a direct underpayment to tranche holders.
- The same pattern exists in `requestWithdraw`, where `_calcInterestWithdrawRequest` charges withdraw-request fees/interest on the fixed epoch schedule rather than the time the receipt actually waits.

### Impact Explanation
Tranche holders (AA/BB) permanently lose the interest corresponding to every extra period the epoch runs past `epochEndDate`. The yield that should accrue during the overrun is never collected from the borrower and never minted into `lastEpochInterest`, so `virtualPrice` is set too low at epoch end — theft of owed yield, quantified as `NAV * apr * (actualElapsed - epochDuration) / 365 days`. The loss scales linearly with how late `stopEpoch` is; a two-cycle overrun halves the effective APR paid by the borrower, exactly mirroring the report's `8.84 + 2` instead of `8.84 * 2` example.

### Likelihood Explanation
`stopEpoch` is called by the honest manager/owner and is realistically subject to operational delay — it is a manual keeper action gated on `block.timestamp >= epochEndDate` with no upper bound. Any delay directly under-charges the borrower without any privileged misbehavior. Unlike the Teller case, the loss does not require an attacker at all; it accrues from ordinary sequencing around the manager's call.

### Recommendation
Charge interest on actual elapsed epoch time: replace `epochDuration` with `min`-free `block.timestamp - epochStartTimestamp` (or `stopEpochTimestamp - startEpochTimestamp`) in `_calcInterestWithApr`/`_resolveStopEpochInterest`, so the borrower owes `apr * actualElapsed`, or enforce that `stopEpoch` cannot be called later than `epochEndDate` and treat overruns as explicit extension epochs that accrue additional interest.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup, non-programmable fixed-APR mode):

```solidity
// Deposit into AA tranche, start epoch, warp past epochEndDate + epochDuration
idleCDO.depositAA(amount);
idleCDO.startEpoch();
vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.epochDuration()); // epoch ran 2x its duration

uint256 interest = idleCDO.expectedEpochInterest(); // = NAV * apr * epochDuration / YEAR (fixed)
// interest only covers ONE epochDuration despite two durations of borrow time
vm.prank(manager);
idleCDO.stopEpoch(0, 0);
assertApproxEqAbs(idleCDO.lastEpochInterest(), interest, tolerance); // half of what is owed
// AA/BB virtualPrice reflects only one period of interest — the overrun yield is lost
```

Caveat: I could not fully verify in the remaining iterations whether `expectedEpochInterest` is additionally recomputed at `startEpoch` with a different time base, or whether overrun interest is compensated elsewhere (e.g. via strategy-side accrual during the buffer period in `IdleCreditVault`). If the fixed-`epochDuration` charge is an intentional design choice (fixed-term loan priced per scheduled epoch regardless of stop timing), this is a design trade-off rather than a bug; the finding stands if the intended semantics are "interest owed for time actually held", which the `epochEndDate`-gated, unbounded `stopEpoch` window contradicts.
