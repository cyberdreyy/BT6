### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing a request to execute below the intended live-member threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
This is the NEAR analog of the Basket reentrancy bug: authorization is validated once against state that can change mid-flight, and the rest of the logic keeps trusting the stale check. In `MultiSigContract::confirm`, the number of confirmations required to execute a request is compared only by *count* (`confirmations.len() as u32 + 1 >= self.num_confirmations`). Nothing re-validates that every public key/account already present in a request's `confirmations` set is still a live member of the multisig at the moment the threshold is reached and the request is executed.

### Finding Description
`execute_request`'s `DeleteMember`/`DeleteKey` handling only purges *requests whose creator* (`request_with_signer.member` / `signer_pk`) equals the removed member: [1](#0-0) 

It does **not** scan other, still-pending requests to strip confirmations that the removed member previously cast on those requests. The same pattern exists in the legacy contract's `DeleteKey` handler: [2](#0-1) 

`confirm` then trusts the raw size of `confirmations` (which may still contain a now-removed member's entry) to decide whether to execute: [3](#0-2) 

The binding that should hold is:
`num_confirmations` ≤ |{ c ∈ confirmations(request) : c ∈ current live members }|

What the code actually checks is:
`num_confirmations` ≤ |confirmations(request)|  (regardless of whether each entry is still a current member)

Because a member removed via `DeleteMember`/`DeleteKey` (its own separate, previously-confirmed request) keeps contributing its earlier confirmation to any *other* pending request it had confirmed before removal, `execute_request` can be triggered with fewer genuinely-live confirmations than `num_confirmations` mandates.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding for the multisig account, which typically custodies NEAR and access rights over the account (transfers, key/member management, contract deployment, arbitrary function calls). A request (e.g. `Transfer`, `AddKey`/`AddMember`, `DeployContract`, `FunctionCall`) can be pushed to execution while relying on a confirmation from a member who has since been revoked/removed — effectively executing at below the intended live-member threshold. This matches the Critical impact category "a multisig request executed below threshold," and in the case of a `Transfer` action, directly results in NEAR moved by a party (or with authorization) not actually entitled to it at execution time.

### Likelihood Explanation
This requires only ordinary, expected multisig activity — no compromise of the runtime, no reentrancy hack, and no privileged actor beyond the members the account already trusts: a member confirms a pending request, is later removed via a normal `DeleteMember`/`DeleteKey` request (e.g., offboarding, key rotation, suspected compromise), and the remaining members continue confirming the earlier request unaware that the stale confirmation is still silently counted. Any deployment that ever removes/rotates a member while requests are outstanding is exposed; this is a routine operational scenario, not a contrived edge case.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over **all** pending requests (not just those created by the removed member) and strip the removed member's/key's entry from each request's `confirmations` set. Alternatively, in `confirm`/`execute_request`, re-validate at execution time that every entry in `confirmations` is still contained in `self.members` (v2) / still corresponds to an active access key (v1), discarding stale entries and only counting confirmations from currently-live members before comparing to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member `B` calls `add_request` to create request `R` (e.g. `Transfer` to some attacker-controlled account).
3. Member `A` calls `confirm(R)` → `confirmations(R) = {A}` (count 1, below threshold 3).
4. Separately, members `B, C, D` create and confirm a `DeleteMember{member: A}` request, which executes: `delete_member` runs (see `multisig2/src/lib.rs:356-379`), removing `A` from `self.members` and deleting `A`'s access key — but it only purges requests where `r.member == A` (i.e., requests A *created*), not `R`, which A merely confirmed. `confirmations(R)` still equals `{A}`.
5. Member `C` calls `confirm(R)` → `confirmations(R) = {A, C}` (count 2).
6. Member `D` calls `confirm(R)` → count reaches `2 + 1 = 3 >= num_confirmations`, so `execute_request` runs and the `Transfer` executes — even though `A`'s confirmation is stale (A is no longer a member and could not sign a new transaction on this account), meaning the request executed with only 2 genuinely live confirmations against a 3-confirmation policy.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
