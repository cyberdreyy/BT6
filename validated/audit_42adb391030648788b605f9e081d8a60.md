### Title
Unbounded growth of `h.callbacks` map enables gateway memory-exhaustion DoS - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler` stores one `savedCallback` entry per in-flight `requestID` in `h.callbacks`, and only removes entries when a quorum response arrives (`HandleNodeTriggerResponse`) or when `reapExpiredCallbacks` runs and finds an entry older than `CleanUpPeriodMs`. There is no maximum-size cap on this map, unlike the analogous `pruneCallbacks`/`MaxSavedCallbacks` mechanism in `core/services/gateway/handlers/capabilities/handler.go`. An authorized workflow signer can keep the map growing by sending unique-`requestID` trigger requests toward a workflow whose shard members are slow/unreachable, since each accepted request lives for up to `CleanUpPeriodMs` before being reaped, and `userRateLimiter.AllowErr` only throttles the *rate* of accepted requests, not the count of concurrently pending callbacks.

### Finding Description
`HandleUserTriggerRequest` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:88-140`) validates the request, resolves the workflow, authorizes the signer via `authorizeRequest` (`:361-369`), then calls `checkRateLimit` (`:371-396`), which only enforces a token-bucket `Allow`/`AllowErr` call scoped to the workflow — it does not check or bound the number of currently pending entries in `h.callbacks`. [1](#0-0) 

After passing rate-limiting, `setupCallback` unconditionally inserts a new entry into `h.callbacks` keyed by the caller-supplied unique `requestID`, with no upper bound check on `len(h.callbacks)`: [2](#0-1) 

Cleanup of a saved callback occurs only in two places: (1) `HandleNodeTriggerResponse`, when a node quorum response is aggregated and sent back to the user, or (2) `reapExpiredCallbacks`, a periodic ticker that deletes any callback older than `CleanUpPeriodMs`: [3](#0-2) [4](#0-3) 

Notably, `sendToShard`'s final-timeout path (`ctx.Done()` after `MaxTriggerRequestDurationMs`) just returns an error up through `sendWithRetries`/`HandleUserTriggerRequest` — it never calls `cleanupCallback` or sends a user error response, so the entry remains in `h.callbacks` until `reapExpiredCallbacks` catches it at `CleanUpPeriodMs`, which can be configured longer than `MaxTriggerRequestDurationMs`. [5](#0-4) 

By contrast, the sibling gateway handler `capabilities/handler.go` bounds its equivalent callback map both by age (`CallbackMaxAgeSec`) and by absolute size (`MaxSavedCallbacks`), evicting the oldest entries when the cap is exceeded — this pattern is absent from `http_trigger_handler.go`. [6](#0-5) 

Because `checkRateLimit` governs request throughput (tokens/sec) and `reapExpiredCallbacks` governs the *retention window* (`CleanUpPeriodMs`), a sustained attacker at the workflow's allowed rate `R` accumulates a steady-state pending count of roughly `R × CleanUpPeriodMs`, entirely independent of any pending-callback cap (none exists). An attacker authorized on multiple workflows multiplies this linearly, since the rate limiter and pending set have no global cross-workflow cap either.

### Impact Explanation
This is a gateway memory-exhaustion / availability issue: sustained bursts of unique-`requestID` trigger requests toward slow/unreachable shard targets keep `savedCallback` entries (each holding response aggregators, callback channels, etc.) resident for up to `CleanUpPeriodMs`, and with no size cap on `h.callbacks`, memory usage scales with attacker-controlled request volume rather than any fixed bound — potentially exhausting gateway process memory and degrading service for all users of that gateway (DoS), matching a resource-exhaustion/availability-impact bounty class.

### Likelihood Explanation
Requires only that the attacker be an authorized signer for at least one workflow (or several, to multiply impact) — no admin/operator access needed, and the signature/JWT auth checks in `authorizeRequest` do not defend against this because the attack path is entirely downstream of successful authorization. Feasibility is high: an attacker just needs to submit unique-ID requests at (or near) the allowed per-workflow rate for a duration approaching `CleanUpPeriodMs`, targeting workflow shard members that are slow/non-responsive (or simply never reply, e.g. by using an owned workflow whose registered DON nodes are unreachable). Repeatable indefinitely as long as the attacker keeps generating unique `requestID`s.

### Recommendation
Add an explicit cap on concurrently pending callbacks, either per-workflow or globally (or both), independent of the token-bucket rate limiter — e.g., check `len(h.callbacks)` (and/or a per-workflow pending count) inside `setupCallback` under `callbacksMu`, and reject new requests with `jsonrpc.ErrLimitExceeded` once the cap is reached, mirroring the `MaxSavedCallbacks` eviction/cap pattern already used in `core/services/gateway/handlers/capabilities/handler.go`. Additionally, ensure `sendToShard`'s final-timeout error path proactively calls `cleanupCallback` and sends a user error response rather than relying solely on `reapExpiredCallbacks` at `CleanUpPeriodMs`.

### Proof of Concept
Go handler-level integration test plan (extending `http_trigger_handler_test.go`):
1. Configure `ServiceConfig{CleanUpPeriodMs: <large value>, MaxTriggerRequestDurationMs: <small value>}` and a `DON` mock whose `SendToNode` always blocks/errors (simulating unreachable shard members), as in `createTestTriggerHandlerWithConfig`.
2. Register one workflow and obtain a valid signed JWT for it via `createTestJWTToken`.
3. In a loop, submit `N` `HandleUserTriggerRequest` calls with distinct `req.ID` values, staying at or below the configured rate limiter's allowed rate (so `checkRateLimit` never rejects), for a duration approaching `CleanUpPeriodMs`.
4. After each batch, lock `handler.callbacksMu` and record `len(handler.callbacks)`.
5. Assert that `len(handler.callbacks)` grows roughly linearly with `N` and is **not** bounded by any cap independent of the rate limiter — i.e., add a `require.LessOrEqual(t, len(handler.callbacks), <expectedCap>)` assertion that currently fails, demonstrating the missing bound described in the recommendation.

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

	// Build one response aggregator per shard the workflow is assigned to.
	assigned := h.workflowMetadataHandler.WorkflowShards(workflowID)
	if len(assigned) == 0 {
		// this shouldn't happen because we checked it in authorizeRequest()
		h.handleUserError(ctx, requestID, jsonrpc.ErrInternal, fmt.Sprintf("Workflow %s is not assigned to any DONs", workflowID), callback)
		return nil, errors.New("workflow is not assigned to any shards")
	}

	aggregators := make(map[string]*aggregation.IdenticalNodeResponseAggregator, len(assigned))
	for _, shard := range assigned {
		// (N+F)//2 + 1 threshold where N = number of nodes, F = number of faulty nodes
		threshold := (len(shard.members)+shard.f)/2 + 1
		agg, err := aggregation.NewIdenticalNodeResponseAggregator(threshold)
		if err != nil {
			return nil, errors.New("failed to create response aggregator: " + err.Error())
		}
		aggregators[shard.donID] = agg
	}

	doneCh := make(chan struct{})
	h.callbacks[requestID] = savedCallback{
		Callback:            callback,
		requestStartTime:    requestStartTime,
		createdAt:           time.Now(),
		responseAggregators: aggregators,
		doneCh:              doneCh,
	}
	return doneCh, nil

	saved, exists := h.callbacks[requestID]
	if !exists {
		return
	}
	close(saved.doneCh)
	delete(h.callbacks, requestID)
}

// reapExpiredCallbacks removes callbacks that are older than the maximum age
func (h *httpTriggerHandler) reapExpiredCallbacks(ctx context.Context) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()
	now := time.Now()
	var expiredCount int
	for reqID, callback := range h.callbacks {
		if now.Sub(callback.createdAt) > time.Duration(h.config.CleanUpPeriodMs)*time.Millisecond {
			h.metrics.IncrementRequestErrors(ctx, jsonrpc.ErrInternal, h.lggr)
			h.cleanupCallback(reqID)
			expiredCount++
		}
	}
	if expiredCount > 0 {
		h.metrics.IncrementPendingRequestsCleanUpCount(ctx, int64(expiredCount), h.lggr)
		h.lggr.Infow("Removed expired callbacks", "count", expiredCount, "remaining", len(h.callbacks))
	}
	h.metrics.RecordPendingRequestsCount(ctx, int64(len(h.callbacks)), h.lggr)
}

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
