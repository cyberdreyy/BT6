### Title
Instance/VM-isolation image allow-list check validates unexpanded `options.Build.Image.Name`, while VM creation uses `ExpandValue`-resolved image — validated string and used string can differ - ([File: executors/instance/instance.go], [File: executors/internal/autoscaler/acquisition.go])

### Summary
In the instance executor's `Prepare`, `common.VerifyAllowedImage` is called against the raw, unexpanded `options.Build.Image.Name` when VM isolation is enabled. Later, in a separate code path (`acquisitionRef.createVMTunnel`), the actual image string used to create the nesting VM is `options.Build.GetAllVariables().ExpandValue(image)`, which can resolve to a different string than what was checked, breaking the invariant that the validated string must equal the string used to create the VM.

### Finding Description
`executor.Prepare` in [1](#0-0)  validates `options.Build.Image.Name` verbatim (no `ExpandValue` call) against `options.Config.Instance.AllowedImages` via `common.VerifyAllowedImage`.

The actual VM is not created here — `environment.Prepare` is called at [2](#0-1) , which for the autoscaler/nesting path eventually invokes `acquisitionRef.createVMTunnel`. There, the image is computed independently — again starting from `options.Build.Image.Name` — and then expanded: [3](#0-2) . This expanded value (`nc.Create(ctx, image, ...)`) is what actually determines the nesting VM's image, not the string that was checked by `VerifyAllowedImage`.

Because the CI/CD `image:` field supports `$VARIABLE` syntax and its value is only expanded at `createVMTunnel` time (a separate function, in a separate package, executed after `Prepare` returns from the allow-list check), the string fed into `VerifyAllowedImage` (raw, e.g. `"$MY_IMAGE"`) and the string used to actually create the VM (expanded, e.g. resolved to whatever `MY_IMAGE` currently holds) are not guaranteed to be identical. `VerifyAllowedImage` performs a `doublestar.Match` glob comparison against the literal, unexpanded text [4](#0-3) , so it is effectively validating a token/placeholder string rather than the real image that will run.

This is a genuine "check vs. use" (TOCTOU-style) mismatch: whenever the allow-list glob happens to match the raw/unexpanded literal (e.g., an admin uses a broad wildcard pattern, or a pattern intentionally written to permit variable-parameterized image references such as `"registry.example.com/*"` matching `"registry.example.com/$TAG"`), the subsequently expanded value can resolve to an entirely different, unvalidated image string, and no second validation is performed on the expanded value before `nc.Create` is invoked.

### Impact Explanation
If an `allowed_images` pattern is written in a way that matches the literal/unexpanded image reference (a realistic case for teams intentionally supporting variable-driven image names, e.g., a pattern like `"$CI_REGISTRY_IMAGE/*"` or a permissive wildcard), an attacker who controls the value of the referenced CI/CD variable (e.g., via pipeline variables, trigger API variable overrides, or parent/child pipeline variable propagation) can cause the nesting VM to boot an image whose expanded name was never actually checked against the allow list — bypassing the `AllowedImages` restriction and running an unauthorized VM image inside the isolated instance executor.

### Likelihood Explanation
Exploitability depends on the admin's `allowed_images` configuration containing a pattern that matches the raw/templated image string rather than only concrete image names — this is a plausible real-world configuration for runners that want to support variable-based image selection while still restricting the resolved registry/namespace. Where such a pattern exists, the bypass is fully triggerable by an unprivileged pipeline author simply by setting/overriding the referenced variable's value; no special access is required beyond normal job/variable control.

### Recommendation
Validate the same string that will actually be used to create the VM: call `options.Build.GetAllVariables().ExpandValue(...)` on the image name (mirroring the logic already used in `createVMTunnel`) before invoking `common.VerifyAllowedImage` in `executor.Prepare`, or move/duplicate the allow-list check into `createVMTunnel` immediately after computing the final `image` value at [5](#0-4) , so the check and the value passed to `nc.Create` are guaranteed identical.

### Proof of Concept
Go unit test outline for `executors/instance/instance_test.go`:
1. Configure `options.Config.Instance.AllowedImages = []string{"registry.example.com/*"}` and `options.Config.Autoscaler.VMIsolation.Enabled = true`.
2. Set `options.Build.Image.Name = "registry.example.com/$SUFFIX"` and `options.Build.Variables` containing `SUFFIX` with a value such that the expanded image (`options.Build.GetAllVariables().ExpandValue("registry.example.com/$SUFFIX")`) resolves to `"evil.example.com/malicious:latest"` (e.g., abusing that `doublestar.Match` treats `$SUFFIX` as an opaque wildcard match, or crafting the variable to demonstrate divergence).
3. Assert that `executor.Prepare` succeeds (allow-list check passes on the literal `"registry.example.com/$SUFFIX"`).
4. Separately call `ref.createVMTunnel` (or inspect the `image` value computed at acquisition.go line 208) and assert it differs from the string that was validated — proving the invariant "validated string == used string" is violated.
5. Expected fix assertion: after remediation, `Prepare` should fail with `common.ErrDisallowedImage` because the expanded image does not match `AllowedImages`.
