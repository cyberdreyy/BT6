Unvalidated `parameters` blob length in permissionless `createDstEscrow` allows self-inflicted decode revert that bricks both `withdraw` and `publicWithdraw` - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`createDstEscrow` is a permissionless entry point that accepts `dstImmutables` (including the raw `parameters` bytes blob) directly from the caller with no validation of its length or internal consistency. `EscrowDst._withdraw` (invoked by both the private `withdraw` and the public `publicWithdraw`) unconditionally decodes `integratorFeeAmountCd`/`protocolFeeAmountCd` and, whenever the decoded fee amount is non-zero, further decodes the corresponding recipient via `integratorFeeRecipientCd`/`protocolFeeRecipientCd`. Each of these `ImmutablesLib` getters independently bounds-checks only against its own offset, with no upfront validation that the full 128-byte (`0x80`) parameters layout is present.

### Finding Description
`createDstEscrow` [1](#0-0)  only validates `msg.value` against the deposit/amount and the cancellation-timing ordering; it never checks `dstImmutables.parameters.length` or verifies that the encoded fee amounts and recipients form a self-consistent, fully-populated 4-word layout.

`ImmutablesLib` exposes independent length checks per field: `protocolFeeAmountCd` requires `>= 0x20`, `integratorFeeAmountCd` requires `>= 0x40`, `protocolFeeRecipientCd` requires `>= 0x60`, and `integratorFeeRecipientCd` requires the full `>= 0x80` [2](#0-1) . With a 96-byte (`0x60`) `parameters` blob, the first three getters succeed, but `integratorFeeRecipientCd` reverts with `IndexOutOfRange`.

`EscrowDst._withdraw` calls `integratorFeeAmountCd()` and, when it is non-zero, unconditionally calls `integratorFeeRecipientCd()`: [3](#0-2) . Since both `withdraw` and `publicWithdraw` route to this same internal function [4](#0-3) , a `parameters` blob that encodes a non-zero integrator fee amount but omits the trailing recipient word makes withdrawal (private and public) revert unconditionally — even with a correct secret — because the decode failure happens before any transfer.

Because the escrow creator (an unprivileged "taker") fully controls `dstImmutables.parameters` at creation time, and `createDstEscrow` has no restriction on who may call it as long as the deposit is funded, a self-funding creator can deploy an escrow that is fully collateralized (passing any balance-only off-chain sanity checks) yet permanently bricked for withdrawal until the `DstCancellation` timelock elapses.

### Impact Explanation
This matches the High-severity "temporary freezing of funds during the live swap lifecycle" category: the maker's expected destination-chain payout cannot be withdrawn via either `withdraw` or `publicWithdraw`, even after presenting a valid secret, and settlement is delayed until the taker calls `cancel()` post-timelock — at which point the deposited tokens/native currency return to the taker, not the maker. The maker who already allowed their source-side funds to be claimed (secret revealed) receives nothing on the destination side for the duration of the freeze, and the swap never completes as intended.

### Likelihood Explanation
The precondition is fully within a single unprivileged actor's control: they choose `dstImmutables.parameters` at `createDstEscrow` call time and fund the escrow correctly, so all balance/amount checks pass. No governance, whitelisted-resolver, or oracle/relayer collusion is required — `createDstEscrow` performs no access control. The only mitigating factor is that a careful maker/relayer could inspect the raw `parameters` bytes off-chain before revealing the secret, but the on-chain contracts provide no such enforcement themselves.

### Recommendation
Validate `dstImmutables.parameters.length == 0x80` (or the exact expected fixed layout) inside `createDstEscrow` before deploying the clone and accepting funds, so malformed/truncated fee metadata cannot be encoded into a live escrow. Alternatively, have `ImmutablesLib`/`EscrowDst._withdraw` perform a single upfront length check for the full expected layout rather than deferring per-field bounds checks that can revert deep into the withdrawal flow.

### Proof of Concept
1. Attacker (as `taker`) calls `createDstEscrow` with `dstImmutables.parameters = abi.encode(uint256(1), uint256(1))` truncated/repacked to exactly 96 bytes such that the integrator-fee word (bytes `0x20:0x40`) is non-zero, while omitting the fourth (recipient) word. Fund with the correct `msg.value`/token amount so `InsufficientEscrowBalance` is not triggered [1](#0-0) .
2. Time-warp past `DstWithdrawal`; maker (or attacker itself) calls `withdraw(secret, immutables)` with the correct secret — reverts with `IndexOutOfRange` inside `integratorFeeRecipientCd()` [5](#0-4) , before any token transfer occurs.
3. Time-warp past `DstPublicWithdrawal`; any access-token holder calls `publicWithdraw(secret, immutables)` — reverts identically since it invokes the same `_withdraw` [6](#0-5) .
4. Only after `DstCancellation` timelock can the taker call `cancel()` to reclaim their own deposited funds and safety deposit; the maker never receives the destination-side payout.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
