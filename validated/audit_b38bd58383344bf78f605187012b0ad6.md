### Title
Unhealthy account owner can front-run pending liquidation by transferring the account, causing targeted liquidation to fail - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account` / `transfer_to_new_account_pda` let the `authority` of any `MarginfiAccount` move all balances into a brand-new account (with a freely chosen new authority/PDA seed) and disable the old account at any time, with no check on the account's health/liquidatability. Because both classic and receivership liquidation instructions target a specific, pre-known `marginfi_account`/`liquidatee_marginfi_account` pubkey, an under-collateralized owner who sees a pending liquidation transaction in the mempool can front-run it with a transfer, causing the liquidator's transaction (built against the old, now-empty/disabled account) to fail, exactly analogous to the UMA "position transfer to delay liquidation" bug class.

### Finding Description
`TransferToNewAccount`'s account constraints only check `account_not_frozen_for_authority` and `is_signer_authorized`, plus flags for flashloan/receivership/order-execution and prior migration — there is no health check and no delay/cooldown: [1](#0-0) 

The instruction body wipes the old account's `lending_account` (zeroed) and sets `ACCOUNT_DISABLED`, moving all balances to the newly created account under `new_authority`, which is completely unchecked: [2](#0-1) [3](#0-2) 

Both liquidation entry points reference a specific liquidatee account pubkey supplied ahead of time by the liquidator:
- Classic liquidation reads `liquidatee_marginfi_account` and computes health from its current on-chain state: [4](#0-3) [5](#0-4) 
- Receivership liquidation (`StartLiquidation`) requires the target account not be disabled/in receivership/etc., i.e. it fails outright once the account has been migrated away: [6](#0-5) 

Because a liquidator must first observe an unhealthy account, build a transaction naming that account's pubkey, and land it, the owner has a window (the time between observing the incoming liquidation and its confirmation, or simply proactively before every block) to submit `transfer_to_new_account`/`transfer_to_new_account_pda` targeting the same account. Once landed first, the old account's balances become zero and it is flagged `ACCOUNT_DISABLED`, so:
- The classic liquidation's health check on the (now empty) liquidatee account will show it healthy/zero-exposure, causing the liquidation instruction to fail its pre-liquidation health assertion, and
- The receivership `StartLiquidation` constraint explicitly rejects `ACCOUNT_DISABLED` accounts.

The docs even confirm any account authority can freely transfer at will, with no restriction on the destination or account state: [7](#0-6) 

This mirrors the UMA report's root cause: a permissionless, unrestricted "move my position/account" action that a liquidation target can always execute ahead of a specific, address-targeted liquidation transaction, defeating it.

### Impact Explanation
An under-collateralized sponsor-equivalent (marginfi account authority) can repeatedly dodge specific liquidation attempts by transferring to fresh accounts (self-controlled, since `new_authority` is unchecked) each time a liquidation transaction targets them. This can be used to buy time to top up collateral, or in the worst case to persist an under-collateralized position and continue to withdraw/borrow against it while liquidators must re-discover the new account pubkey each time, delaying bad-debt realization and potentially worsening protocol insolvency exposure — the same systemic risk called out in the original report (artificially low collateralization, extended exposure to price moves, delayed bankruptcy handling).

### Likelihood Explanation
The transfer only costs a flat SOL fee (`ACCOUNT_TRANSFER_FEE`) and requires only the account authority's signature — no privileged access is needed. On Solana, MEV/mempool visibility and the fact that liquidation bots must publicly submit transactions naming the victim account pubkey make this front-running practically reachable, though it requires the attacker to detect the incoming liquidation transaction before it lands (e.g., via RPC mempool/leader schedule observation or simply preemptively transferring whenever health drops), which is a realistic assumption for a sophisticated account owner motivated to avoid liquidation.

### Recommendation
Add a health/eligibility gate to `transfer_to_new_account`/`transfer_to_new_account_pda`, mirroring the UMA fix: either (a) disallow transfer when the account is currently liquidatable (fails `check_pre_liquidation_condition`-equivalent health check), or (b) impose a short timelock/delay on transfers of unhealthy accounts (similar to how withdrawal/deleverage rate limits are handled elsewhere in the codebase), so liquidators have a guaranteed window to execute against a known-bad account before it can be moved.

### Proof of Concept
1. Account `A` (authority `U`) borrows against collateral until it is undercollateralized/unhealthy.
2. A liquidator observes `A`'s poor health and submits `lending_account_liquidate` (or `start_liquidation`) naming `A` as `liquidatee_marginfi_account`/`marginfi_account`.
3. Before that transaction lands, `U` submits `transfer_to_new_account` (or `transfer_to_new_account_pda`) moving all of `A`'s balances to a new account `B` under `new_authority = U` (or any address `U` controls), setting `A.account_flags = ACCOUNT_DISABLED` and zeroing `A.lending_account`: [2](#0-1) 
4. The liquidator's pending transaction against `A` now fails: classic liquidation's health check sees no exposure on `A`, and receivership's `StartLiquidation` constraint rejects `ACCOUNT_DISABLED` accounts.
5. `U` repeats this process against `B`, `C`, ... each time a liquidation is imminent, indefinitely delaying enforcement while continuing to hold/borrow value at `B`'s new pubkey.

fn finalize_migrated_old_account(

    new_account_key: Pubkey,

pub struct TransferToNewAccount<'info> {
    #[account(
        constraint = (
            !group.load()?.is_protocol_paused()
        ) @ MarginfiError::ProtocolPaused
    )]
    pub group: AccountLoader<'info, MarginfiGroup>,

    #[account(
        mut,
        has_one = group @ MarginfiError::InvalidGroup,
        constraint = {
            let a = old_marginfi_account.load()?;
            account_not_frozen_for_authority(&a, authority.key())
        } @ MarginfiError::AccountFrozen,
        constraint = {
            let a = old_marginfi_account.load()?;
            let g = group.load()?;
            is_signer_authorized(&a, g.admin, authority.key(), false, false)
        } @ MarginfiError::Unauthorized
    )]
    pub old_marginfi_account: AccountLoader<'info, MarginfiAccount>,
