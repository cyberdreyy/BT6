### Title
Mid-epoch deposit mints discounted tranche shares but `requestWithdraw` pays a full epoch of interest, letting a depositor amplify a small late deposit into an unbudgeted full-epoch interest claim - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
This is the vault analog of the SoftEther amplification report: a small input (a deposit made near the end of an epoch) triggers a disproportionately large output (a withdraw receipt priced as principal plus a *full* epoch of interest). The mid-epoch deposit path in `IdleCDOEpochVariant` mints shares so that the depositor earns only the *prorated* interest for the remaining epoch time (`trancheInterest`, scaled by `remaining + buffer` over `epochDuration + buffer`), and it only adds that prorated amount to `expectedEpochInterest`. But `_calcInterestWithdrawRequest`, used by `requestWithdraw`, computes interest over the *entire* `epochDuration` with no dependence on when the user deposited. A KYC-passing lender can deposit right before `epochEndDate`, immediately call `requestWithdraw`, and carry a receipt worth principal + ~full-epoch interest into the next epoch, while only the prorated slice was ever budgeted from the borrower.

### Finding Description
Mid-epoch deposit mint path (`IdleCDOEpochVariant.sol:691-732`):

- `interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer)` — interest is prorated by the *remaining* epoch time.
- `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` — shares are minted at a discounted price so that `minted * priceEnd = amount + prorated interest`.
- `expectedEpochInterest += interest` — only the prorated amount is added to the borrower-funded interest budget.
- Underlyings are sent straight to the borrower via `_transferUnderlyings(_borrower(), _amount)` and `IdleCreditVault(strategy).mintStrategyTokens(_amount)`.

Withdraw request path (`IdleCDOEpochVariant.sol:739-790`, `856-878`):

- `_underlyings = _trancheToUnderlyings(_amount, _tranche)` converts the depositor's (discounted) tranche balance to underlyings at the current tranche price, which is approximately the deposited principal.
- `_calcInterestWithdrawRequest` computes `totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer)` and `_interest = _amount * totTrancheInterest / _trancheBal`. This is the interest for a **whole** `epochDuration` of participation. It is a per-unit-of-NAV rate applied uniformly, with no term that scales it by the time the requesting position actually existed.
- `creditVault.requestWithdraw(_underlyings, msg.sender, principal)` mints the user a strategy-token receipt for `principal + interest - totalFees` (`IdleCreditVault.sol:271-295`), and `pendingWithdraws += _amount` becomes a hard claim the next `stopEpoch` must fund via `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`).

The asymmetry: the minted share count encodes `amount + prorated interest` at end-of-epoch price, but the receipt encodes `amount + full-epoch interest`. For a deposit made `Δ` before `epochEndDate` in an epoch of length `T`, the attacker captures interest proportional to `T` while only `Δ`/`T` of it was ever credited to `expectedEpochInterest`. The amplification factor is roughly `T / Δ` — directly mirroring the reported >1x response amplification.

### Impact Explanation
The unbudgeted portion of the interest claim is funded in one of two ways, both harmful:

- If the borrower funds `pendingWithdraws` at `stopEpoch` (`collectWithdrawFunds`), the honest borrower pays out interest on capital it held for only a fraction of the epoch — a direct wealth transfer.
- If funding falls short, `collectWithdrawFunds` records a `lossRecoveryPriceByEpoch` haircut (`IdleCreditVault.sol:414-421`) socializing the shortfall across **all** pending receipts of that epoch, i.e. other honest withdrawers absorb the attacker's excess interest.

Quantified: with a 30-day epoch and 10% APR, depositing `X` one day before `epochEndDate` and requesting withdraw yields a receipt of `X + X*10%*30/365` while `expectedEpochInterest` was incremented by only `~X*10%*1/365`. Roughly `X*0.8%` of unbudgeted interest is created per deposit; repeating it across deposited capital extracts real yield not owed by the borrower, violating the "one receipt one payout / funded claims" invariant.

### Likelihood Explanation
Likelihood is moderate-to-high where mid-epoch deposits are enabled:

- Attacker needs only to pass `isWalletAllowed` (Keyring KYC) — explicitly an in-scope unprivileged role.
- `requestWithdraw` is permissionless aside from `allowAAWithdrawRequest`/`allowBBWithdrawRequest` flags and the KYC check.
- The interest computation uses fixed `epochDuration`/`lastNAV` values; nothing measures `block.timestamp` relative to the deposit, so the excess is deterministic, not timing-lucky.
- Guards do not stop it: `_skimDonatedAssets` only skims raw token donations, `_updateAccounting` does not alter the interest entitlement, and the `lastWithdrawRequest`/epoch gating in `_claimFundedWithdrawRequest` merely delays the claim by one epoch — which is by design.
- Limiting factors: deposits must occur while the epoch is running and the deposit path must be enabled for the deployment; upfront management/performance fees (`_totalWithdrawFees`) shave part of the excess; gains scale with APR and epoch length.

### Recommendation
Make the withdraw-request interest term consistent with the minted-share entitlement:

- Pro-rate `_calcInterestWithdrawRequest` (or the deposited principal's interest component) by actual participation time. Since per-share entitlement is fungible, the clean fix is to track per-user deposit epochs / weighted deposit timestamps for mid-epoch deposits, or record at request time the portion of the tranche balance minted via mid-epoch deposits and apply `interest * (remaining + buffer) / (epochDuration + buffer)` to that portion.
- Alternatively, when a mid-epoch depositor calls `requestWithdraw` in the same epoch as the deposit, cap the receipt's interest to the `trancheInterest` that was credited at deposit (the amount already embedded in their discounted share count), which requires storing that credited interest per user.
- Add a regression test: deposit mid-epoch, `requestWithdraw`, run `stopEpoch`/`startEpoch`, `claimWithdrawRequest`, and assert claimed interest ≤ prorated entitlement.

### Proof of Concept
Foundry fork-style PoC (extend `test/foundry/IdleCreditVault.t.sol` setup with a running epoch, borrower-funded interest, and a KYC'd attacker):

```solidity
function testPocMidEpochDepositInterestAmplification() external {
    // --- setup: epoch running, 30-day duration, apr set, borrower funded ---
    _startEpochAndCheckPrices(0); // epoch starts, expectedEpochInterest set

    uint256 apr = cdoEpoch.getAprAA();          // scaled apr
    uint256 deposit = 1_000_000 * ONE_SCALE;
    address attacker = vm.addr(0xA77A);
    _whitelist(attacker);
    deal(defaultUnderlying, attacker, deposit);
    deal(defaultUnderlying, borrower, 10_000_000 * ONE_SCALE); // borrower honest+funded

    // --- attacker deposits 1 day before epoch end ---
    vm.warp(cdoEpoch.epochEndDate() - 1 days);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(idleCDO), type(uint256).max);
    uint256 minted = idleCDO.depositAA(deposit);   // mid-epoch path: discounted mint

    // budgeted interest for this deposit (~1 day of apr)
    uint256 budgeted = cdoEpoch.expectedEpochInterest() - expectedIntBefore;

    // --- attacker immediately requests withdraw of full balance ---
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.stopPrank();

    uint256 receipt = IdleCreditVault(strategy)
        .withdrawsRequests(attacker);           // principal + FULL-epoch interest - fees
    uint256 fullEpochInterest = deposit * apr / FULL_ALLOC * 30 days / 365 days;

    // receipt interest is ~30x the budgeted (1 day) interest
    assertGt(receipt - deposit, budgeted * 10);

    // --- end epoch, borrower funds, next epoch, claim ---
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _stopCurrentEpoch();
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _stopCurrentEpoch();

    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 gained = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;

    // attacker realized ~full-epoch interest on a 1-day position;
    // excess was paid by borrower over-funding pendingWithdraws or
    // haircut to other receipts via lossRecoveryPriceByEpoch
    assertGt(gained - deposit, fullEpochInterest * 90 / 100);
}
```

Key assertion: the interest embedded in `withdrawsRequests[attacker]` exceeds the `expectedEpochInterest` delta recorded at deposit by a factor of ~`epochDuration / remainingTime`, demonstrating the input→output amplification.

*Uncertainty note:* I could not fully trace `_virtualPriceAux`/`virtualPrice` to confirm whether accrued expected interest is already reflected in the current tranche price used by `_trancheToUnderlyings`. If the live price already includes accrued expected interest, the receipt's "principal" component would also embed the prorated interest, making the excess slightly larger rather than smaller — the core mismatch (full-epoch interest vs. prorated entitlement) stands either way, but the exact amplification magnitude should be confirmed against the deployed variant's price path.
