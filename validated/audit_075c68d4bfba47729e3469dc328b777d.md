### Title
Dust-sized APR=0 withdraw request permanently reverts `stopEpoch` after a rate change, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` routes requests made while `unscaledApr == 0` into a per-user `apr0Users` bucket and a global `apr0TotalPrincipal` counter. At `stopEpoch`, `prepareStopEpochWithApr0` unconditionally reverts with `NotAllowed` if `apr0TotalPrincipal != 0` while `unscaledApr != 0`. An unprivileged lender can therefore hold a dust APR0 request open across the buffer, and any honest APR increase by the manager makes `stopEpoch` revert, leaving the epoch unable to close and all lender/borrower funds frozen until the manager restores `unscaledApr` to zero and lets the request settle.

### Finding Description
The slow-HTTP bug class — an attacker holding a scarce synchronization resource open with a dribbled-out request — maps onto the APR0 withdraw bucket, which acts as a lock on the epoch-close transition:

- `requestWithdraw` credits any request made while `unscaledApr == 0` into `_requestWithdrawApr0`, which sets `apr0Users[user].principal` and increments `apr0TotalPrincipal` (IdleCreditVault.sol:567-577). There is no minimum amount; a 1-wei-equivalent request suffices.
- `prepareStopEpochWithApr0` is called by `IdleCDOEpochVariant.stopEpoch` every epoch close and hard-reverts when the bucket is non-empty but the APR is no longer zero:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

- The attacker's bucket can only be cleared by `_settleApr0`/`_clearWithdrawClaimForEpoch`, which requires `epochNumber` to advance past the request epoch — but `epochNumber` only advances inside `stopEpoch`/`deposit`, which is exactly the call that reverts. There is no user-side cancel path in `IdleCreditVault` (queue `deleteWithdrawRequest` exists only on the periphery queue, not on direct CDO requests). Once `unscaledApr != 0` and `apr0TotalPrincipal != 0`, `stopEpoch` always reverts: a self-referential deadlock.
- Broken invariant: epoch state machine liveness. A single dust receipt vetoes the running → stopped transition for the entire pool, analogous to a slow client stalling a shared worker.

### Impact Explanation
All user funds are frozen: no `stopEpoch` means pending withdraw receipts never settle, new epochs cannot start, borrower repayment cannot be booked, and `startEpoch`/`stopEpochWithDuration`/close-pool flows that depend on epoch progression are blocked. Recovery requires the honest manager to restore `unscaledApr` to zero, wait for the request's epoch to settle, and only then raise APR — a manual intervention the attacker can repeatedly force by re-requesting dust each buffer period. This is temporary freezing of the full vault TVL (every lender's principal plus queued withdrawals), triggered at the cost of a dust deposit.

### Likelihood Explanation
Requirements: (1) a KYC'd lender deposits any amount and calls `requestWithdraw` while the vault runs at APR 0 — a normal supported mode (the test suite uses `unscaledApr == 0` vaults); (2) the honest manager subsequently calls `setAprs`/`setAprsWithBuffer` with a non-zero APR while the request is still unsettled — a routine, honest operational action (rate renegotiation between epochs). No malicious privileged role is needed; the attacker only supplies the dust request, and can re-arm the trap cheaply each epoch. The revert is deterministic once both conditions hold, so likelihood is moderate — it hinges on an APR change occurring while even one dust APR0 receipt is open, which the attacker can keep open indefinitely.

### Recommendation
Do not revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Instead, settle the open APR0 principal at the last valid `apr0RateByEpoch` (or at zero interest if no rate was recorded), clear `apr0TotalPrincipal`, and let `stopEpoch` proceed. Alternatively, treat an APR change as implicitly settling open APR0 requests pro-rata at the current epoch boundary, or block `requestWithdraw` into the APR0 bucket once the manager has scheduled a non-zero APR for the next epoch.

### Proof of Concept
Foundry fork PoC (against a Clearpool-style `IdleCreditVault` + `IdleCDOEpochVariant` deployment with `unscaledApr == 0`):

```solidity
function testApr0DustRequestFreezesStopEpoch() external {
    // --- setup: vault in APR0 mode, epoch N running ---
    vm.prank(manager);
    cdoEpoch.startEpoch(); // unscaledApr == 0 for this epoch

    // 1) Attacker (KYC'd lender) deposits dust and requests withdraw
    address attacker = makeAddr("attacker");
    deal(address(underlying), attacker, 1e6);
    _whitelist(attacker);
    vm.startPrank(attacker);
    underlying.approve(address(cdoEpoch), 1e6);
    cdoEpoch.depositAA(1e6); // or queued deposit processed into the epoch
    uint256 tranches = tranche.balanceOf(attacker);
    cdoEpoch.requestWithdraw(tranches, address(tranche)); // APR0 bucket: apr0TotalPrincipal > 0
    vm.stopPrank();
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // 2) Honest manager raises APR for the next epoch (routine repricing)
    vm.prank(manager);
    strategy.setAprsWithBuffer(10e18, epochDuration, bufferPeriod); // unscaledApr != 0

    // 3) Fast-forward to epoch end: stopEpoch always reverts -> funds frozen
    skip(epochDuration);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch();

    // Attacker cannot unstick it: claim requires epochNumber > requestEpoch,
    // but epochNumber only advances inside the reverting stopEpoch.
    vm.prank(attacker);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();

    // 4) Manager must restore APR=0 to let the dust request settle,
    //    losing at least one full epoch duration of liveness.
    vm.prank(manager);
    strategy.setAprs(0, 0);
    cdoEpoch.stopEpoch(); // now succeeds; attacker re-arms next epoch for 1 wei
}
```

Uncertainty note: the PoC assumes `stopEpoch` invokes `prepareStopEpochWithApr0` unconditionally on every epoch close (the call exists in `IdleCDOEpochVariant`); if it is gated behind a mode flag, the finding applies only to vaults where that path is active. The deadlock direction (revert inside stopEpoch, settlement requiring `epochNumber` bump inside stopEpoch) is confirmed directly from `IdleCreditVault.sol:490-541` and `326-330`.
