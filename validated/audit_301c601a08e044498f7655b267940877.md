### Title
DoS on receivership liquidation via `check_utilization_ratio()` in the `lending_account_withdraw` path used to seize collateral - (File: `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`, `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
Marginfi's classic liquidation (`lending_account_liquidate`) intentionally bypasses the utilization-ratio/liquidity check by using `withdraw_ignore_borrow_cap` (`BalanceDecreaseType::BypassBorrowLimit`), which skips `bank.check_utilization_ratio()`. [1](#0-0) [2](#0-1)  This is exactly the fix Sherlock's M-4 report recommended for Exactly's `Market.sol`. However, Marginfi's second liquidation mechanism - "receivership liquidation" (`start_liquidation`/`end_liquidation`) - lets the liquidator seize collateral by calling the **normal** `lending_account_withdraw` instruction against the liquidatee's account. [3](#0-2)  That instruction routes through `BankAccountWrapper::withdraw()`/`withdraw_all()`, both of which use `BalanceDecreaseType::WithdrawOnly` (not `BypassBorrowLimit`), so `bank.check_utilization_ratio()` is **not** bypassed. [4](#0-3) [5](#0-4) [6](#0-5) 

This reproduces the exact bug class from M-4: if a market/bank is highly utilized, seizing the liquidatee's collateral via the receivership-liquidation withdraw step can revert with an insufficient-liquidity/utilization-ratio error, causing the entire liquidation transaction (Start → Withdraw → Repay → End, which must be atomic per the documented rules) to fail.

### Finding Description
Receivership liquidation requires exactly one `Start`, some sequence of `Withdraw`/`Repay` calls, and one `End`, all in the same transaction, with the liquidator acting "as if they are the user." [7](#0-6)  The `Withdraw` step used to seize the liquidatee's collateral is literally the standard `lending_account_withdraw` instruction, gated on `ACCOUNT_IN_RECEIVERSHIP` only for skipping the *account health* check, not the bank-level liquidity check: [8](#0-7) 

Both withdrawal code paths inside that instruction unconditionally enforce liquidity availability at the bank level:
- Partial withdraw: `bank_account.withdraw(...)` → `decrease_balance_internal(..., WithdrawOnly)` → `bank.check_utilization_ratio()` is called because the operation type is not `BypassBorrowLimit`. [9](#0-8) 
- `withdraw_all`: `bank_account.withdraw_all(in_receivership)` also calls `bank.check_utilization_ratio()` unconditionally, regardless of the `in_receivership` flag (that flag only affects clearing a liquidation price-cache lock). [10](#0-9) 

By contrast, classic liquidation's `internalSeize`-equivalent explicitly documents that it "Ignores the utilization ratio check" via `withdraw_ignore_borrow_cap`, precisely to avoid this class of bug. [11](#0-10)  The receivership path has no equivalent bypass for the withdraw leg, so it reintroduces the root cause identified in Sherlock M-4: a liquidity/utilization check performed at seize-time that can be manipulated or naturally triggered to block liquidation.

### Impact Explanation
An attacker who controls (or colludes with) the unhealthy account can pre-emptively (or front-run, since Solana transactions are also subject to MEV/front-running) withdraw liquidity from the same bank using another account, driving the bank's utilization above the point where the seize-withdraw would succeed. Because the entire receivership-liquidation transaction is atomic (Start...Withdraw...Repay...End must be one tx, with no other liquidator recourse mid-tx), the `check_utilization_ratio()` revert inside the `Withdraw` instruction aborts the whole liquidation attempt. This:
- Blocks third-party liquidators from using the more capital-efficient receivership path against the affected position while the bank remains highly utilized.
- Can allow an unhealthy borrower to repeatedly avoid liquidation, accumulating further losses that are ultimately socialized as protocol bad debt if prices continue to move against them, mirroring the "risk-free trade until bankruptcy" scenario in the original Sherlock report.
- Undermines liquidations as a core safety mechanism for depositors during periods of high borrow demand, which is a normal (not edge-case) market condition for a healthy, actively-used lending market.

This does not affect classic liquidation (`lending_account_liquidate`), which already correctly bypasses the check, so overall protocol impact is scoped to the receivership-liquidation flow, but that flow is the one actively promoted as "use this instead" in the docs. [12](#0-11) 

### Likelihood Explanation
Likelihood is moderate-to-high: no special privileges are required, only ordinary deposit/withdraw actions on the same bank as the position being liquidated, matching the attack pattern accepted (albeit downgraded to Medium) in the referenced Sherlock judgment. High utilization is an expected, common state for actively used lending banks, and a borrower who wants to avoid a specific liquidation attempt on a receivership-liquidated position can simply ensure/keep the bank near its utilization ceiling before their position becomes unhealthy. I could not verify from the available code excerpts whether `bank.check_utilization_ratio()` has some soft/borrow-cap threshold that differs meaningfully from Exactly's `floatingBackupBorrowed + floatingDebt > newFloatingAssets` check (the exact numeric semantics of `check_utilization_ratio` in `bank.rs` were not retrieved in full), so likelihood/severity tuning would benefit from reviewing that function directly.

### Recommendation
Mirror the classic-liquidation approach for the receivership-liquidation withdraw leg: when `marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP)` is true in `lending_account_withdraw`, use a withdrawal primitive that bypasses `bank.check_utilization_ratio()` (analogous to `withdraw_ignore_borrow_cap`) rather than routing through `BankAccountWrapper::withdraw()`/`withdraw_all()`, which always enforce it. Concretely:
- In `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`, branch on `in_receivership` to call a liquidity-check-bypassing variant of `withdraw`/`withdraw_all` for the seize step, consistent with the comment "Only liquidation is allowed to bypass this check" already present in `decrease_balance_internal`. [2](#0-1) 
- Ensure any bad debt created by allowing the bank to go under-collateralized during a receivership seizure is handled via the existing bad-debt/bankruptcy socialization mechanism rather than being prevented by a hard revert at seize time, matching the resolution direction discussed in the referenced Sherlock issue.

### Proof of Concept
Conceptual PoC (based on documented receivership-liquidation flow and `withdraw`/`decrease_balance_internal` code paths; not executed against the live test suite):
1. Bank `B` reaches high utilization (e.g., via normal borrowing activity, or an attacker's own second account borrowing against separately-deposited collateral).
2. Account `U` becomes unhealthy while its sole/primary collateral is deposited in bank `B`.
3. A liquidator submits a receivership-liquidation transaction: `start_liquidation(U)` → `lending_account_withdraw(U, bank=B, amount=seize_amount)` (seizing `U`'s collateral) → `repay(...)` → `end_liquidation(U)`, per the documented rules that only `Withdraw`/`Repay` may appear between Start and End. [13](#0-12) 
4. Inside `lending_account_withdraw`, `bank_account.withdraw(seize_amount)` invokes `decrease_balance_internal(..., BalanceDecreaseType::WithdrawOnly)`, which calls `bank.check_utilization_ratio()` because the operation is not `BypassBorrowLimit`. [14](#0-13) 
5. If bank `B`'s liquidity is insufficient relative to the utilization/borrow-cap threshold enforced by `check_utilization_ratio()`, the withdraw instruction reverts, aborting the entire atomic liquidation transaction (Start/Withdraw/Repay/End), and `U` remains unliquidated despite being unhealthy.

I was not able to fully inspect the numeric body of `Bank::check_utilization_ratio()` in `programs/marginfi/src/state/bank.rs` within the indexed content (only imports/header were retrieved), so the exact threshold formula and whether any receivership-specific carve-out exists elsewhere in that function could not be fully confirmed from the index; a Devin session with full repo access would be needed to validate the precise revert condition and confirm no other guard neutralizes this path.

    /// Returns `(spl_withdraw_amount, asset_share_delta)`.

        let balance = &mut self.balance;
        let bank = &mut self.bank;

        let total_asset_shares: I80F48 = balance.asset_shares.into();

            MarginfiError::NoAssetFound
        );

            current_liability_amount.is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
            MarginfiError::NoAssetFound
        );

        bank.change_asset_shares(-total_asset_shares, false)?;
        bank.check_utilization_ratio()?;

In this approach, the liquidator takes control of an unhealthy account, enabling them to withdraw
and repay as if they are the user. At the end of liquidation we simply validate that they actually
improved account health.

Within the tx, the liquidator can withdraw, perform e.g. a jup swap, and repay the debt, keeping
whatever is leftover for themselves. This enables to the liquidator to operate without holding any
funds or creating a mrgn account at all.

We use transaction introspection to ensure that every liquidate_start has a corresponding
liquidate_end.

The process generally looks like this:

```
* ComputeBudgetProgram (optional)
* Liquidate Start Instruction
* Withdraw A
* Swap A to B via jup or similar
* Repay B
* Liquidate End Instruction
```

## Notable Rules:

- ComputeBudgetProgram ixes and Kamino refreshes are the only kind of instructions that can come
  before Start.

- There must be exactly one liquidate Start, and it must come first in the tx (other than Compute
  Budget)

- There must be exactly one liquidate End, and it must come last in the tx. No other instruction can
  come after End.

- The only other mrgn instructions that can be called are Withdraw and Repay.

- Account health must improve between Start and End. All health checks are ignored during withdraw
  and repay: only the final health matters. This means you can withdraw BEFORE repaying.
