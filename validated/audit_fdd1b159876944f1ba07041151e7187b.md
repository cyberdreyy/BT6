### Title
Unprivileged user can permanently lock own account funds by transferring authority to `Pubkey::default()` in `TransferToNewAccount`/`TransferToNewAccountPda` - (File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let an account's own `authority` (an unprivileged, non-admin signer) migrate all balances to a brand-new `MarginfiAccount` under an arbitrary `new_authority`, while permanently disabling the old account. The on-chain instruction places no constraint on `new_authority`, explicitly documenting it as unchecked. This mirrors the Nexus finding: an ordinary account-holder action (analogous to removing the last validator) can leave the account with no valid authorizer, permanently locking it out, matching the "no default validator initialized" root cause pattern.

### Finding Description
Both `TransferToNewAccount` and `TransferToNewAccountPda` accounts structs mark the `new_authority` field as completely unchecked: [1](#0-0) [2](#0-1) 

The handler `transfer_to_new_account` initializes the new account with `ctx.accounts.new_authority.key()` as its authority with no equality check against `Pubkey::default()`, then unconditionally disables the old account and zeroes its lending positions (moving all balances into the new account): [3](#0-2) [4](#0-3) 

Authorization for interacting with a `MarginfiAccount` is gated purely by matching the stored `authority` pubkey to the transaction signer (`is_signer_authorized`), with no special-case for `Pubkey::default()`: [5](#0-4) 

Since `Pubkey::default()` (all zeros) has no known private key, setting it as `new_authority` produces a new `MarginfiAccount` that can never be signed for by its "owner." All funds previously in the old account are now trapped in the new account, and the old account is irreversibly disabled (`ACCOUNT_DISABLED`, lending account zeroed), so there is no path back either.

Notably, this exact risk is documented and guarded against only in the off-chain `p0-cli` tooling, not on-chain: [6](#0-5) 

Any caller building a raw instruction directly against the program (bypassing `p0-cli`) is not protected by this check. Per the permissions guide, "New authority is completely unchecked" is explicitly called out as a known footgun in the account struct comments, confirming there is no on-chain validation.

There is no admin-side recovery mechanism for an account whose `authority` is set to the zero pubkey — freeze/unfreeze only helps when the group admin can still act on the account (which they can, since `admin` is allowed via `is_signer_authorized` fallback in some paths), but this is a Nexus-style scenario about the *user's own* action creating a durable, non-recoverable state.

### Impact Explanation
Impact is High: if `new_authority` is set to `Pubkey::default()` (accidentally, via a buggy or malicious front-end/integration, or a third-party wrapper building the raw instruction rather than the CLI), the resulting `MarginfiAccount` becomes permanently inaccessible — no signer can ever match `Pubkey::default()`. All positions (deposits and collateral) migrated into that account are frozen with no recovery path, since the old account is already disabled and its lending account is zeroed. This matches the Nexus report's "durable freeze with financial effect" bar.

### Likelihood Explanation
Likelihood is Low, mirroring the original Nexus finding's low-likelihood/high-impact classification: it requires either (a) a client/integration bug that fails to validate `new_authority` before submitting the transaction (as `p0-cli` does), or (b) a malicious frontend/dApp tricking a user into signing a transfer to a bad address. Because the on-chain instruction imposes no defense-in-depth check, the security guarantee currently rests entirely on client-side tooling correctness.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` rejecting `new_authority == Pubkey::default()` (and consider rejecting other unrecoverable/system-owned addresses), so the guarantee does not rely solely on `p0-cli`'s client-side `bail!` check.

### Proof of Concept
1. User creates a `MarginfiAccount` and deposits funds via the normal flow.
2. Instead of using `p0-cli`'s `marginfi_account_transfer` (which blocks the zero pubkey client-side), the user (or a malicious integration) directly constructs and signs a `TransferToNewAccount` instruction with `new_authority = Pubkey::default()`, per the account struct: [7](#0-6) 
3. The instruction succeeds: `initialize_migrated_account` sets the new account's `authority` field to `Pubkey::default()`, and `finalize_migrated_old_account` disables the old account and zeroes its lending positions.
4. No subsequent transaction can ever satisfy `is_signer_authorized` for the new account (no keypair corresponds to the zero pubkey), so all migrated funds are permanently locked, and the old account cannot be un-migrated (`migrated_to` is already set, guarded by `AccountAlreadyMigrated`).
