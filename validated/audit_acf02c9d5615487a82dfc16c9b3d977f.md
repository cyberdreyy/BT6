### Title
Race condition in `oidcAuthenticator.SetAuthToken` allows two simultaneously valid API tokens for the same user - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`SetAuthToken` wraps its DELETE+INSERT logic in `sqlutil.TransactDataSource`, but the closure body ignores the `tx` parameter and instead issues both queries directly against the outer `oi.ds` datasource. This means the "transaction" provides no atomicity/isolation, and concurrent `POST /v2/user/token` calls from the same authenticated user can interleave such that both requests' tokens end up persisted simultaneously.

### Finding Description
`SetAuthToken` is reached from `UserController.NewAPIToken` (`core/web/user_controller.go:244-286`), which requires only a valid session (`webauth.GetAuthenticatedUser`, any authenticated role) and a correct password re-check via `TestPassword`. Once authenticated, the handler calls `AuthenticationProvider().SetAuthToken(ctx, &user, newToken)`.

Inside `SetAuthToken` (`core/sessions/oidcauth/oidc.go:522-540`):
```go
err = sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
    if _, err = oi.ds.ExecContext(ctx, "DELETE FROM oidc_user_api_tokens WHERE user_email = $1", user.Email); err != nil {
        ...
    }
    _, err = oi.ds.ExecContext(ctx, "INSERT INTO oidc_user_api_tokens (...) VALUES (...)", ...)
    ...
})
```
Both the DELETE and INSERT use `oi.ds` — the outer, non-transactional datasource — instead of the `tx` parameter provided by `TransactDataSource`. As a result, the two statements are not grouped into a single atomic unit by this call; each executes and auto-commits independently (each is its own implicit single-statement transaction against `oi.ds`), and no locking/serialization is applied around the user's token row.

Because `oidc_user_api_tokens` is not shown to enforce a unique/primary key on `user_email` alone (schema at `core/store/migrate/migrations/0270_add_oidc_auth_tables.sql` was not confirmed to include such a constraint), two concurrent calls to `SetAuthToken` for the same user can interleave as: `DELETE(A)` → `DELETE(B, no-op)` → `INSERT(A)` → `INSERT(B)`, leaving two rows (both token A and token B) valid for the same account. This directly matches the "revoke-and-rotate" invariant break described in the question.

The password re-check performed by `NewAPIToken` (`TestPassword`) does not prevent this, since it only gates entry into `SetAuthToken` and does nothing to serialize concurrent calls; nor does anything else in the reachable path add row-level locking or `SELECT ... FOR UPDATE` semantics.

### Impact Explanation
An authenticated low-privilege user (or an attacker with valid credentials for any role, including `view`/`run`) can defeat the intended "regenerate token = invalidate previous token" guarantee by firing two concurrent `POST /v2/user/token` requests. This can leave two simultaneously valid `AccessKey`/secret pairs for the same account, undermining the revoke-and-rotate assumption depended on for credential rotation/incident response (e.g., after a suspected token leak, rotating the token would not reliably invalidate the old one). This maps to Chainlink's "authentication/session management flaw" impact class — stale credentials remaining valid post-rotation.

### Likelihood Explanation
No special privilege is needed beyond a valid session and knowledge of the account's own password (which the legitimate token owner has). The race window depends on database latency/goroutine scheduling but is realistically reproducible by firing two near-simultaneous requests from a script/goroutines, especially over a network with any round-trip latency between the DELETE and INSERT statements. It requires no OCR/DON/host access and is entirely reachable through the public HTTP API.

### Recommendation
Use the `tx` parameter (not `oi.ds`) inside the `TransactDataSource` closure for both the DELETE and INSERT statements so they execute as one atomic transaction. Additionally, add a unique constraint on `oidc_user_api_tokens.user_email` (if not already present) and/or use `SELECT ... FOR UPDATE` on the user's row (or an upsert with `ON CONFLICT (user_email) DO UPDATE`) to serialize concurrent token-regeneration requests for the same user and guarantee only one valid token can exist at a time.

### Proof of Concept
1. Go integration test in `core/sessions/oidcauth/oidc_test.go` (or a handler-level test hitting `POST /v2/user/token`):
   - Create a test user and enable `UserAPITokenEnabled()`.
   - Spawn two goroutines, each calling `oidcAuthenticator.SetAuthToken(ctx, user, auth.NewToken())` (or two concurrent HTTP `POST /v2/user/token` calls with the correct password) at the same time, synchronized via a `sync.WaitGroup`/barrier to maximize interleaving.
   - After both complete, query `SELECT count(*), array_agg(token_key) FROM oidc_user_api_tokens WHERE user_email = $1`.
   - Assert `count == 1`. If the race is present, `count == 2` and both `token_key` values authenticate successfully via `FindExternalInitiator`/token lookup path, proving two simultaneously valid credentials exist.
