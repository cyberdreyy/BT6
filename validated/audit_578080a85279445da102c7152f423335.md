## Title
Reentrant call in `_postInteraction` allows a malicious order maker to corrupt `lastValidated` before it is read, causing wrong hashlocks to be bound to `EscrowSrc` - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
`BaseEscrowFactory._postInteraction` performs an **external call to an attacker-supplied contract** (the optional "custom postInteraction" `tail` address embedded in the order extension) *before* it reads the shared `lastValidated` mapping that stores the Merkle-secret index/leaf validated for the current fill. This is the same root cause as the reported RPC bug: a single piece of shared mutable state (`lastValidated[key]` here, the broadcast channel there) is written by one logical request and consumed by another, and an interleaving write — in this case triggered deterministically via reentrancy rather than thread scheduling — corrupts the value before the original consumer reads it.

### Finding Description
For orders that allow multiple fills, `MerkleStorageInvalidator.takerInteraction` validates a Merkle proof and stores the result keyed only by `orderHash` + truncated root: [1](#0-0) 

This `lastValidated[key]` slot is shared across **every fill of the same multi-fill order**, since the key does not include the caller, the making amount, or a per-call nonce.

In `_postInteraction`, an external call to a maker-specified "custom postInteraction" contract is executed: [2](#0-1) 

only *after that* is `lastValidated[key]` read to determine the hashlock and validate the partial-fill index for the escrow currently being created: [3](#0-2) 

The `tail` address/data comes from the order's `extension`, which is signed and thus fully controlled by the order **maker** — an unprivileged user, not a privileged resolver. A malicious maker can:
1. Create a multi-fill order whose extension points the custom-postInteraction hook at their own contract.
2. Let (or coax) a resolver fill part of the order. `takerInteraction` validates and stores the correct `(index, leaf)` for that fill.
3. When `_postInteraction` runs for that fill, its own malicious hook is invoked *before* `lastValidated[key]` is read (line 95). From this callback, the attacker re-enters the Limit Order Protocol and fills a small dust portion of the **same order** with a proof for a different index that only the maker (who created the whole Merkle tree) can produce. This overwrites `lastValidated[key]` for the shared key.
4. Execution returns to the outer (honest resolver's) `_postInteraction`, which now reads the **corrupted** `validated.leaf`/`validated.index` and binds the wrong `hashlock` to the `EscrowSrc` clone being deployed for the resolver's real fill.

The resolver's destination-chain `EscrowDst` deposit (their real funds) is created using the hashlock they originally observed/expected, which no longer matches the corrupted `EscrowSrc` hashlock. Since only the maker (who authored every leaf in the tree) knows the secret behind the substituted hashlock, the resolver can never legitimately learn a secret that unlocks their own `EscrowDst` counterpart in the normal flow, leaving their funds unusable until the cancellation timelock expires.

### Impact Explanation
This breaks the core invariant that the hashlock bound to a source escrow corresponds to the Merkle index actually validated for that specific fill, and that this hashlock is agreed between the two chains for a given swap leg. The result is a resolver's destination-chain deposit becoming stuck (frozen) for the duration of the swap lifecycle because the secret revelation path is broken by maker-triggered reentrancy — a "temporary freezing of funds during the live swap lifecycle," matching the High-severity bucket in the bounty scope. It also demonstrates a business-logic failure (wrong secret index bound to an escrow) reachable purely by an unprivileged order maker without any resolver/owner/governance privilege.

### Likelihood Explanation
Likelihood is high for a determined malicious maker: they fully control the poisoned order's extension (the custom postInteraction target), fully control the Merkle tree/secrets for their own order, and can trigger the reentrant dust fill themselves in the same transaction as any honest resolver's fill of another part of the order. No special timing race is needed (unlike the original RPC bug) — the corruption is deterministic because it exploits a guaranteed external-call-before-critical-read ordering in `_postInteraction`.

### Recommendation
Read and consume `lastValidated[key]` (compute the hashlock and validate the partial-fill index) *before* invoking the optional external "custom postInteraction" call, or move the custom-postInteraction call to strictly after all escrow-critical state (hashlock, immutables, deployment) has been finalized. Alternatively, add reentrancy protection around `_postInteraction`/`takerInteraction`, and/or scope `lastValidated` to a single fill (e.g., clear/consume it immediately upon read, or include a per-call nonce) so that a nested fill cannot silently overwrite state that an outer, in-flight fill still needs to read.

### Proof of Concept
1. Malicious maker builds a multi-fill order with `N` secrets/Merkle tree (they know all secrets) and an extension whose `tail` (custom postInteraction address) points to their own `Attacker` contract.
2. Attacker pre-funds the CREATE2 addresses for both their own dust fill and lets an honest resolver's fill proceed for part of the order.
3. Resolver calls `fillOrderArgs` for their slice: `MerkleStorageInvalidator.takerInteraction` stores `lastValidated[key] = (idx_A+1, leaf_A)` for the resolver's intended index `idx_A`.
4. `_postInteraction` runs; at line 95 it calls into `Attacker.postInteraction`, which reenters `limitOrderProtocol.fillOrderArgs` to fill a tiny dust amount of the same order with a valid proof for a different index `idx_B` (known only to the maker). This causes `MerkleStorageInvalidator.takerInteraction` to overwrite `lastValidated[key] = (idx_B+1, leaf_B)`.
5. Control returns to the resolver's outer `_postInteraction`, which reads `lastValidated[key]` at line 118 and now binds `hashlock = leaf_B` to the resolver's `EscrowSrc`, not `leaf_A` as the resolver expects/has already funded on the destination chain via `EscrowDst`.
6. The resolver's `EscrowDst` (funded with real tokens) can never be unlocked with a secret matching `leaf_B` in the normal cooperative flow, freezing the resolver's funds until timelock-based cancellation. [4](#0-3) [5](#0-4)
