## Title
Multisig deployment can be frontrun, permanently trapping the depositor's NEAR - (File: `multisig-factory/src/lib.rs`)

## Summary
`MultisigFactory::create` in `multisig-factory/src/lib.rs` derives the new multisig sub-account name directly and deterministically from an attacker-observable, user-supplied `name` parameter, and schedules account creation, code deployment, fund transfer, and initialization as a single atomic promise chain — with **no success/failure callback**. Any unprivileged party can watch the mempool and front-run the `create` call using the same `name`, causing the honest caller's account-creation receipt to fail. Because there is no refund callback (unlike the sibling `lockup-factory` and `staking-pool-factory` contracts), the attached deposit is never returned to the depositor and becomes permanently stranded in the `multisig-factory` contract's own balance, which exposes no withdrawal mechanism.

## Finding Description
`create` computes the target account deterministically from caller-supplied input and schedules a single receipt performing `create_account → deploy_contract → transfer → function_call("new")`: [1](#0-0) 

Compare this to `lockup-factory` and `staking-pool-factory`, which both attach a `.then(ext_self::on_*_create(...))` callback that checks `is_promise_success()` and explicitly refunds `attached_deposit` back to `predecessor_account_id` if the sub-account creation failed: [2](#0-1) [3](#0-2) 

`multisig-factory/src/lib.rs` has no such callback and no other method besides `create` — there is no owner, no admin, no withdrawal function anywhere in the contract.

**Attack path:**
1. Victim submits `create({"name": "alice", "members": [...], "num_confirmations": ...})` with an attached deposit `D`, intending to fund and control `alice.multisig-factory`.
2. Attacker observes this transaction in the mempool and submits their own `create({"name": "alice", ...})` call first (with a trivial deposit, e.g. `num_confirmations: 1` and themselves as sole member), which succeeds and creates `alice.multisig-factory` under attacker control.
3. When the victim's transaction executes, `Promise::new("alice.multisig-factory").create_account()...` fails at the `create_account` action (account already exists). Per NEAR semantics, when one action in a receipt's action-chain fails, all subsequent actions in that *same* receipt (`deploy_contract`, `transfer`, `function_call`) are skipped and not applied.
4. The deposit `D` that the victim attached to the original `create()` call was already credited to the `multisig-factory` contract account when the outer receipt executed the `create` function. Since the follow-up `transfer` action never fires, `D` is never forwarded to the sub-account, and it simply remains part of the `multisig-factory` contract's own balance.
5. Because `multisig-factory` has no owner-controlled withdrawal, refund callback, or any other method, `D` is permanently unrecoverable.

The claim-vs-delivery equality that is broken: `attached_deposit (debited from victim) == NEAR delivered to victim-controlled multisig account`. After the front-run, the left side is `D > 0` and the right side is `0` — the funds are neither delivered to the intended account nor refunded.

## Impact Explanation
This is a Critical-severity outcome under the stated impact categories: "funds permanently frozen." The victim's attached NEAR deposit becomes unrecoverable with no mechanism in the contract to release it, and the account name the victim wanted is squatted by the attacker.

## Likelihood Explanation
Likelihood is high: any unprivileged network observer can watch the mempool for `create` calls to `multisig-factory` and front-run them cheaply, since `name` is fully attacker-controllable/predictable ahead of time and no minimum deposit, uniqueness reservation, or collision handling exists.

## Recommendation
Add a callback (mirroring `on_lockup_create`/`on_staking_pool_create`) that checks `is_promise_success()` after the sub-account creation attempt and refunds `env::attached_deposit()` to `env::predecessor_account_id()` on failure. Alternatively, avoid relying on caller-chosen, predictable account names (e.g., derive the sub-account name from a hash of `predecessor_account_id` plus a nonce, similar to `lockup-factory`'s use of `sha256(owner_account_id)`) to make front-running collisions non-exploitable.

## Proof of Concept
1. Victim sends `create({"name": "target", "members": [{"account_id": "victim"}], "num_confirmations": 1})` with deposit `D` attached, targeting `target.multisig-factory`.
2. Attacker, observing the pending transaction, sends `create({"name": "target", "members": [{"account_id": "attacker"}], "num_confirmations": 1})` with minimal deposit, and ensures it lands first.
3. Attacker's transaction succeeds, creating `target.multisig-factory` controlled solely by `attacker`.
4. Victim's transaction reaches the runtime; the receipt to `target.multisig-factory` fails at `create_account` (`ActionsValidationError: AccountAlreadyExists` in NEAR runtime), so `deploy_contract`, `transfer(D)`, and `function_call("new", ...)` never execute.
5. Query `multisig-factory`'s own account balance — it now includes the victim's `D`, which is unreachable since `multisig-factory/src/lib.rs` exposes only the `create` method: [4](#0-3) .

#[near_bindgen]
impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
