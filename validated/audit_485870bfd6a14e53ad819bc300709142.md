### Title
v1 `validate_tenure_change_payload` DuplicateBlockFound guard misses locally-accepted (unsigned-by-node) tenure-start blocks, letting a v1 signer double-sign competing tenure-start blocks - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`chainstate::v1::validate_tenure_change_payload`'s duplicate-block guard queries `SignerDb::get_last_globally_accepted_block`, which only matches blocks in `BlockState::GloballyAccepted`, while the v2 equivalent was fixed to query `SignerDb::get_last_signed_block` (covers `LocallyAccepted` + `GloballyAccepted`). A v1 signer that has already locally accepted (signed) a tenure-start block for tenure T, but whose block has not yet reached global acceptance, will not trip `RejectReason::DuplicateBlockFound` on a second, different tenure-start proposal for the same tenure T, so it can be induced to sign a conflicting tenure-start block.

### Finding Description
The invariant that should hold is: *a signer never signs two different tenure-start blocks for the same tenure*. This is enforced in `validate_tenure_change_payload` by looking up "have I already accepted a block in this tenure?" before allowing a second tenure-change block to pass chainstate checks.

- v1 implementation queries `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0) , which only returns rows with `state == GloballyAccepted` (a state reached only after the node itself has processed/confirmed the block, i.e., long after the signer's own signature is committed).
- v2 was explicitly patched to instead call `signer_db.get_last_signed_block(&block.header.consensus_hash)` [2](#0-1) , whose comment states the rationale: "Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us..." — i.e. the check must catch anything the signer already put a signature over, not just node-confirmed blocks.
- `get_last_signed_block` matches `LocallyAccepted` or `GloballyAccepted` [3](#0-2) , whereas `get_last_globally_accepted_block` (used only by v1) is strictly narrower.
- The v2 fix has an explicit regression test, `check_tenure_change_rejects_when_locally_accepted_block_exists`, which inserts a `LocallyAccepted` block and asserts `Err(RejectReason::DuplicateBlockFound)` is returned [4](#0-3) ; no analogous test exists in `stacks-signer/src/chainstate/tests/v1.rs`, confirming v1 never received the equivalent fix.
- The divergence is also explicitly documented as intentional-but-risky in the project's own flow documentation: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)" [5](#0-4) .

**Exploit flow (attacker = the single miner-slot winner):**
1. Attacker wins tenure T's sortition (their own BTC/miner slot — no signer privilege needed).
2. Attacker proposes tenure-start block B1 for tenure T. A v1-protocol signer locally accepts and signs B1 (`mark_locally_accepted`, `signed_self` set) — this happens naturally as soon as the signer's own signature threshold work completes, before the block reaches network-wide global acceptance.
3. Before B1 becomes `GloballyAccepted` (e.g., because gathering the remaining signer weight is slow, or the node hasn't yet processed it), attacker crafts and gossips a second, different tenure-start `BlockProposal` B2 for the same tenure T (same `consensus_hash`/`tenure_consensus_hash`, different transactions/parent selection).
4. B2 reaches the v1 signer via normal StackerDB/gossip proposal delivery and is passed into `validate_tenure_change_payload`.
5. `get_last_globally_accepted_block(&B2.consensus_hash)` returns `None` (B1 is only `LocallyAccepted`), so the `DuplicateBlockFound` branch is skipped and the check returns `Ok(())` [6](#0-5) .
6. B2 passes this stage of chainstate validation and — if the other independent checks (`check_tenure_change_confirms_parent`, `check_parent_tenure_choice`, node validate-endpoint round trip) also pass, which is plausible since B2 is a legitimately-constructed tenure-start block for the same tenure rather than a malformed one — the v1 signer proceeds to sign B2.
7. The signer has now placed its signature on two different tenure-start blocks (B1 and B2) for the same tenure T: an equivocation. Both signatures are public and can be aggregated by any observer toward the 70% threshold, so this is not merely a local inconsistency — it creates two competing, both-partially-signed candidate blocks for the same slot.

This bypasses only the tenure-change-specific duplicate check; it does not require compromising the node, a majority of signers, or any auth token — it is purely a timing race the miner controls by publishing a second proposal while the first is still in the `LocallyAccepted` window.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property for v1-protocol signers: the signer contributes valid signatures to two conflicting tenure-start blocks in the same tenure. If enough other v1 signers are raced the same way (each independently, with their own single proposal), the signature weight could split or be reassembled by an observer to finalize either of two forks — a chain-safety violation. This matches the "Critical" category: a signer signing a conflicting block (equivocation), scoped specifically to signers still running the v1 `SortitionStateVersion`, which is realistic during any mixed v1/v2 upgrade window. It is repeatable per-tenure as long as a v1 signer's most-recent local acceptance in that tenure hasn't yet reached `GloballyAccepted` state.

### Likelihood Explanation
Preconditions: the target signer must be running v1 (`SortitionStateVersion::V1`), must have locally-but-not-globally accepted a tenure-start block for tenure T, and the attacker must control the miner slot for tenure T (a routine, unprivileged capability by design — anyone can win a slot with sufficient BTC) and must be able to gossip a second `BlockProposal`/StackerDB message, which is the normal proposal-delivery channel available to any miner. No majority-signer collusion, no compromised keys, no auth_token, and no local host access are required. The exploit window (between local and global acceptance) is a normal, recurring part of block processing, not a rare edge case, making this readily repeatable across tenures during the v1/v2 mixed-version window.

### Recommendation
Change `chainstate::v1::validate_tenure_change_payload`'s duplicate-block check to call `SignerDb::get_last_signed_block` instead of `SignerDb::get_last_globally_accepted_block`, mirroring the fix already applied in `chainstate::v2::validate_tenure_change_payload` [2](#0-1) , so that `LocallyAccepted` blocks also block a competing tenure-start proposal in the same tenure.

### Proof of Concept
Add to `stacks-signer/src/chainstate/tests/v1.rs`, mirroring the existing v2 regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` [7](#0-6) :

1. Set up the v1 test environment (`setup_test_environment` equivalent for v1's `SortitionsView`).
2. Build `existing_block_info` with `consensus_hash = cur_sortition.data.consensus_hash`, call `existing_block_info.mark_locally_accepted(false)` (not globally accepted), and `signer_db.insert_block(&existing_block_info)`.
3. Construct a second tenure-start `BlockProposal`/`NakamotoBlock` for the same `consensus_hash`, with a `TenureChangePayload { cause: BlockFound, .. }` + coinbase tx, sign the miner header.
4. Call the v1 `sortitions_view.check_proposal(...)` (or directly `validate_tenure_change_payload`) with this second proposal.
5. Assert `matches!(result, Err(RejectReason::DuplicateBlockFound))`.

On the current v1 code, this assertion fails (`result.is_ok()` or a different rejection reason), demonstrating the divergence from v2's `check_tenure_change_rejects_when_locally_accepted_block_exists`, which asserts the same case correctly returns `Err(RejectReason::DuplicateBlockFound)`.

/// Test that a tenure change proposal is rejected when a locally-accepted
/// (but not globally-accepted) block already exists in the same tenure.
///
/// This is a regression test: previously, the check used
/// `get_last_globally_accepted_block`, which would miss blocks in
/// `LocallyAccepted` or `PreCommitted` state and incorrectly allow
/// a duplicate tenure change.
#[test]
fn check_tenure_change_rejects_when_locally_accepted_block_exists() {
    let MockServerClient {
        server,
        client: stacks_client,
        config: _,
    } = MockServerClient::new();
    let rand_int = server.local_addr().unwrap().port();

    let (_stacks_client, mut signer_db, block_sk, mut block, cur_sortition, _, sortitions_view) =
        setup_test_environment(&format!("{}_{rand_int}", function_name!()));

    // Set up the block in the current tenure
    block.header.consensus_hash = cur_sortition.data.consensus_hash.clone();
    let parent_block_header = make_parent_header_meta(&block_sk, &mut block);
    let response = crate::client::tests::build_get_tenure_tip_response(&parent_block_header);

    // Insert a locally-accepted block in the same tenure (same consensus_hash).
    // This simulates a miner's first tenure-start block that the signer has
    // locally accepted but that hasn't yet gathered enough signatures to be
    // globally accepted. In practice this block would contain a tenure-change
    // and coinbase tx, but we omit them here because `get_last_accepted_block`
    // only queries by consensus_hash and block state — the block's transactions
    // are irrelevant to the duplicate check.
    let existing_block_proposal = BlockProposal {
        block: NakamotoBlock::new(
            NakamotoBlockHeader {
                version: 1,
                chain_length: 10,
                burn_spent: 10,
                consensus_hash: cur_sortition.data.consensus_hash.clone(),
                parent_block_id: StacksBlockId([0; 32]),
                tx_merkle_root: Sha512Trunc256Sum([0; 32]),
                state_index_root: TrieHash([0; 32]),
                timestamp: 11,
                miner_signature: MessageSignature::empty(),
                signer_signature: vec![],
                pox_treatment: BitVec::ones(1).unwrap(),
                problematic_txs: vec![],
            },
            vec![],
        ),
        burn_height: 2,
        reward_cycle: 1,
        block_proposal_data: BlockProposalData::empty(),
    };
    let mut existing_block_info = BlockInfo::from(existing_block_proposal);
    existing_block_info.mark_locally_accepted(false).unwrap();
    signer_db.insert_block(&existing_block_info).unwrap();

    // Now build a *second* tenure-start block proposal for the same tenure.
    // This simulates the miner attempting to replace their first block (e.g.,
    // with different transactions). The tenure change tx must have
    // cause=BlockFound with a coinbase to be recognized as a tenure-start block.
    let tenure_change_payload = TenureChangePayload {
        tenure_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        prev_tenure_consensus_hash: cur_sortition.data.parent_tenure_id.clone(),
        burn_view_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        previous_tenure_end: block.header.parent_block_id.clone(),
        previous_tenure_blocks: 1,
        cause: TenureChangeCause::BlockFound,
        pubkey_hash: Hash160::from_node_public_key(&StacksPublicKey::from_private(&block_sk)),
    };
    let tenure_change_tx = make_tenure_change_tx(tenure_change_payload);
    let coinbase_tx = StacksTransaction::new(
        TransactionVersion::Testnet,
        TransactionAuth::Standard(TransactionSpendingCondition::new_initial_sighash()),
        TransactionPayload::Coinbase(CoinbasePayload([0; 32]), None, Some(VRFProof::empty())),
    );
    *block.executed_and_skipped_txs_mut() = vec![tenure_change_tx, coinbase_tx];
    block.header.sign_miner(&block_sk).unwrap();

    let exit_flag = Arc::new(AtomicBool::new(false));
    let moved_exit_flag = exit_flag.clone();

    let serve = std::thread::spawn(move || {
        crate::client::tests::write_response_nonblockinig(
            &server,
            response.as_bytes(),
            moved_exit_flag,
        );
    });

    let result = sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block);

    exit_flag.store(true, Ordering::SeqCst);
    serve.join().unwrap();

    // The proposal should be rejected because there's already a locally-accepted
    // block in this tenure. Before the fix, this would have incorrectly passed
    // because get_last_globally_accepted_block would not find the locally-accepted block.
    assert!(
        matches!(result, Err(RejectReason::DuplicateBlockFound)),
        "Expected DuplicateBlockFound rejection when a locally-accepted block exists in the tenure, got: {result:?}"
    );
}
