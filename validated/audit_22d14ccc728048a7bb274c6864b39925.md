### Title
Multi-epoch withdraw receipts escape `stopEpochWithDuration` haircut because the loss recovery price is keyed to a single epoch while `pendingWithdraws` is epoch-agnostic — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`collectWithdrawFunds` applies a pro-rata loss to the *entire* `pendingWithdraws` aggregate but stores the haircut under a single epoch key (`lossRecoveryPriceByEpoch[epochNumber]`). A user who stacked withdraw requests across two epochs only gets the latest epoch's receipt haircut (via `lastWithdrawRequest`); the older epoch's receipt is later paid at par through `_claimFundedWithdrawRequest` even though its share of the loss was already socialized into the haircut. This mirrors the bug class: one short/ambiguous key serves the wrong "artifact" — a full-price payout where a loss-adjusted one was funded.

### Finding Description
- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and adds `_amount` to a single global `pendingWithdraws` bucket. A user is explicitly allowed to request again in a later epoch without claiming ("he will have to wait for another epoch to claim both requests"). [1](#0-0) 
- On a lossy `stopEpochWithDuration`, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` over the whole aggregate (both epochs' receipts) and stores it under one key: `lossRecoveryPriceByEpoch[epochNumber]`. [2](#0-1) 
- `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and `_clearWithdrawClaimForEpoch` clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` — i.e., only the *latest* request epoch is haircutted. [3](#0-2) 
- The remaining older-epoch balance stays in `withdrawsRequests[_user]` (only `normalAmount` of the loss epoch is decremented) and is paid at par by `_claimFundedWithdrawRequest`, burning receipt tokens 1:1 and transferring the full `amount`. [4](#0-3) 
- The guard in `requestWithdraw` only blocks a new request when `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0`; it does not prevent stacking two requests across *normal* epochs before any loss occurs. [5](#0-4) 

### Impact Explanation
The strategy transferred in only `pendingBasis * lossRecoveryPrice` of underlying, but pays out `(latestEpochBasis * lossRecoveryPrice) + olderEpochBasis` in full. The older-epoch portion is overpaid by `olderBasis * (1 - lossRecoveryPrice)` — funds drawn from the strategy balance that backs active LPs' strategy tokens and the default recovery reserve, directly causing insolvency for later claimants (other pending receipt holders or LP redemptions revert on insufficient balance). Loss is bounded by the older-epoch receipt size times the haircut, e.g. a 50% loss epoch lets the attacker recover ~1.5× the funded amount.

### Likelihood Explanation
Requires only an unprivileged KYC-passing lender: request withdraw in epoch N, let the epoch roll, request again in epoch N+1, then a `stopEpochWithDuration(_lossAmount)` realized loss (an honest manager/borrower action, e.g. partial borrower repayment) triggers the mispricing. No privileged cooperation needed; the attacker merely sequences around normal epoch transitions.

### Recommendation
Apply the loss haircut per-epoch rather than relying on `lastWithdrawRequest`: iterate or track all epochs contributing to `pendingWithdraws` (e.g. store the loss price against every epoch with outstanding receipts, or mark a "loss pending" flag that forces *all* of a user's `withdrawsRequestsByEpoch` entries through `_claimLossAdjustedWithdrawRequest`). Alternatively, revert `requestWithdraw` while the user has any unclaimed receipt in a different epoch so `pendingWithdraws` can never mix epochs for one user.

### Proof of Concept
Foundry fork test sketch (fails on current code):

```solidity
// setup: standard epoch variant, lender A deposits, startEpoch
uint256 req1 = 100e6;
_requestWithdrawWithUser(attacker, req1);        // epoch N, lastWithdrawRequest = N
_stopCurrentEpochWithApr(10e18);                  // epoch N+1 starts
cdoEpoch.startEpoch();
uint256 req2 = 100e6;
_requestWithdrawWithUser(attacker, req2);        // epoch N+1, lastWithdrawRequest = N+1

// borrower repays only 50% of pendingWithdraws -> loss-adjusted funding
uint256 pending = strategy.pendingWithdraws();   // ~req1+req2
uint256 funded  = pending / 2;
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(lossAmount, ...); // collectWithdrawFunds(funded) stores price under one epoch key

// attacker claims: latest-epoch receipt at 50%, older receipt at 100%
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(attacker) - balPre;

// expected fair payout: pending * 0.5 ; actual payout > funded amount pulled in
assertGt(paid, funded); // overpaid: older-epoch basis escaped the haircut
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
