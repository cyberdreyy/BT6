### Title
Same-block deposit/withdraw lock (`_lastCallerBlock`) is keyed on `tx.origin` and is bypassed by transferring tranche tokens to a second account - (File: contracts/IdleCDO.sol)

### Summary
`IdleCDO` protects against same-block deposit→withdraw round trips (the anti-flashloan guard) by storing `keccak256(tx.origin, block.number)` in `_lastCallerBlock` on deposit and reverting in `_withdraw` via `_checkSameBlock()` when the hash matches. Because the lock is bound to the caller identity (`tx.origin`) rather than to the tranche tokens themselves, and `IdleCDOTranche` is a freely transferable ERC20 with no `_beforeTokenTransfer` hook, an attacker controlling two EOAs can deposit from A, transfer the minted tranche tokens to B, and withdraw from B in the same block — the identical bypass class as the reported `blockLock`/`transferFrom` issue. This enables same-block harvesting sandwiches: deposit just before a `harvest` call that raises tranche NAV/prices, then withdraw after it, extracting yield accrued by other depositors.

### Finding Description
`contracts/IdleCDO.sol:1016-1023`:

```solidity
function _updateCallerBlock() internal {
  _lastCallerBlock = keccak256(abi.encodePacked(tx.origin, block.number));
}

function _checkSameBlock() internal view {
  if (keccak256(abi.encodePacked(tx.origin, block.number)) == _lastCallerBlock) revert SameBlock();
}
```

`_deposit` calls `_updateCallerBlock()` (line 241) and `_withdraw` calls `_checkSameBlock()` (line 479); the same pattern is inherited/overridden in `IdleCDOEthenaVariant._withdraw`, `IdleCDOInstadappLiteVariant._withdraw`, `IdleCDOPoLidoVariant._withdraw`, and `IdleCDOTruefiVariant._withdraw`, and `contracts/IdleTokenFungible.sol` uses the identical `_checkMintRedeemSameTx`/`_minterBlock` scheme. `IdleCDOTranche` (`contracts/IdleCDOTranche.sol`) is a plain `ERC20` — transfers and `transferFrom` are unrestricted, and `burn` is callable only by the CDO on `msg.sender`'s balance.

Attack sequence (one block, two or three transactions):

1. `tx1` from EOA A: `depositAA(X)` (or BB) — sets `_lastCallerBlock = hash(A, block.number)`, mints tranche tokens to A.
2. `tx1`/`tx2`: A calls `tranche.transfer(B, minted)` (or approves B who calls `transferFrom`).
3. `tx3` from EOA B: `withdrawAA(amount)` — `_checkSameBlock` computes `hash(B, block.number) != _lastCallerBlock` and passes; B's tranche tokens are burned and underlying paid out.

The protection intent (no same-block mint+redeem) is defeated because the lock tracks *who* called, not *which tokens* were minted this block.

### Impact Explanation
The guard exists to prevent mint-and-redeem within one block so a user cannot capture a price change they did not wait for. With the bypass, an attacker sandwiches a `harvest` (or any same-block NAV-increasing event, e.g., a large strategy-token repayment or fee conversion that raises `_tranchePrice` via `_updateAccounting`/`getContractValue`): deposit before, withdraw after, at the post-harvest price. Profit equals the attacker's pro-rata share of the yield/loss repricing that other holders accrued over the preceding period — direct theft of unclaimed yield, quantified as roughly `minted * (pricePost - pricePre) / ONE_TRANCHE_TOKEN`. Capital requirement is flashloanable (single block), so the attacker can scale `X` to the pool's unlent/liquidity limits.

### Likelihood Explanation
Requires a same-block NAV repricing event the attacker can order around (e.g., a `harvest` tx in the public mempool, or a borrower/strategy repayment in the non-epoch variants). Harvest/keeper transactions are visible on public mempools and the sandwich needs only two attacker EOAs and a plain ERC20 transfer — no privileged action. Profit is bounded by the size of the repricing event, so it is a periodic rather than constant drain, but the invariant break (the guard provides zero protection) is unconditional.

### Recommendation
Bind the same-block lock to the minted position rather than the caller. Options:

- Record a per-token/per-tranche mint marker: store `keccak256(tranche, block.number)` or a per-holder mapping `lastMintBlock[holder]` updated in `_mintSharesAtCurrPrice`, and check it in `_withdraw` for `msg.sender` — but note this still fails when tokens are moved, so the robust fix is to record on the tranche token itself.
- Restrict tranche transfers in `IdleCDOTranche` for tokens minted in the current block (e.g., store `block.number` of last mint per account in the tranche token and revert `transfer`/`transferFrom`/`_withdraw` burns of freshly-minted balance), analogous to requiring `minter == address` cooldowns.
- Alternatively accept the residual risk and remove the illusory check (it is already ineffective in `IdleCDOEpochVariant`, where `_deposit` still calls `_updateCallerBlock` but `requestWithdraw` never calls `_checkSameBlock`), documenting that withdrawal delays must come from the epoch mechanism.

Do not key the fix on `msg.sender` alone — that reintroduces the same bypass. Do not lock the receiver of a transfer either (that would let a dust deposit/transfer DoS a victim's withdrawal — the exact DoS vector the BadgerDAO reviewer flagged).

### Proof of Concept
Fork test against a deployed `IdleCDO`-derived vault (e.g., an Ethena/Instadapp variant on mainnet) in Foundry:

```solidity
function testSameBlockLockBypass() public {
    address A = makeAddr("A");
    address B = makeAddr("B");
    deal(address(underlying), A, DEPOSIT);

    // tx1: A deposits (same block)
    vm.prank(A, A); // msg.sender == tx.origin == A
    cdo.depositAA(DEPOSIT);            // _updateCallerBlock(): _lastCallerBlock = hash(A, bn)

    uint256 minted = trancheAA.balanceOf(A);
    vm.prank(A);
    trancheAA.transfer(B, minted);     // plain ERC20 transfer, no hook

    // tx2: B withdraws in the same block — different tx.origin
    uint256 balBefore = underlying.balanceOf(B);
    vm.prank(B, B); // msg.sender == tx.origin == B
    cdo.withdrawAA(minted);            // _checkSameBlock(): hash(B, bn) != _lastCallerBlock -> passes

    assertGt(underlying.balanceOf(B), balBefore); // same-block mint+redeem succeeded
}
```

To show economic extraction, insert a `harvest` (or a strategy-token value-increasing call) between the deposit and the withdraw in the same block and assert `underlying.balanceOf(B) > DEPOSIT` net of fees, where the profit is drawn from `lastNAV` accrued by pre-existing holders. The PoC runs with `vm.roll`/`block.number` fixed; no privileged roles are involved. Note: `IdleCDOEpochVariant`/`IdleCreditVault` are not directly affected (withdrawals settle one epoch later and `_checkSameBlock` is never invoked there), so the finding applies to the non-epoch production variants sharing `IdleCDO._withdraw` or overriding it while keeping `_checkSameBlock`.
