### Title
Confirmations from a revoked multisig key remain counted toward the approval threshold, allowing request execution below the live-signer quorum - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` tallies approvals for a request purely from the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` set, without re-validating that every `PublicKey` in that set still corresponds to an active multisig key at execution time. When a key is revoked via the `DeleteKey` action, the contract only removes requests and confirmations for requests that the revoked key itself *created*, not confirmations the revoked key contributed to *other* requests. A stale confirmation from an already-deleted key therefore continues to count toward `num_confirmations`, letting a request execute with fewer genuinely live approvals than the configured threshold.

### Finding Description
`confirm()` requires `confirmations.len() as u32 + 1 >= self.num_confirmations` to execute a request [1](#0-0) . The set of prior confirmers is stored keyed only by `request_id`, independent of whether the confirming key is still a valid access key on the account.

The only cleanup of confirmation state happens inside the `DeleteKey` branch of `execute_request`: [2](#0-1) 
This code filters `self.requests` for entries where `r.signer_pk == pk` (i.e. requests *originally added by* the revoked key) and removes their confirmations. It never scans `self.confirmations` for entries where the revoked `pk` appears as a *confirmer* of a request added by someone else. Consequently, any confirmation previously recorded by that key on another still-open request survives the key's deletion untouched.

This breaks the intended binding: `confirmations recorded == confirmations from currently-authorized signers`. After a `DeleteKey` execution, that equality no longer holds for pre-existing requests — the left side (recorded count in the `HashSet`) can exceed the right side (keys that are still valid access keys on the account).

### Impact Explanation
This maps to the report's "confirmations counted versus live members" custody-binding class and is Critical per the review rubric ("a multisig request executed below threshold"). Concretely:
- Suppose `num_confirmations = 3` with keys `K1..K5`.
- `K1` (attacker or colluding/compromised signer) creates a malicious `Transfer` request `R`.
- `K2` (also colluding, or a key later found to be compromised) confirms `R`, bringing confirmations to 1 (not yet enough to execute).
- The remaining honest signers detect `K2` is compromised and revoke it via a separate, properly-confirmed `DeleteKey { public_key: K2 }` request.
- `K2`'s confirmation on `R` is **not** removed, because the `DeleteKey` cleanup only targets requests where `K2` was the *creator*, not requests `K2` merely confirmed.
- Now only 4 valid keys remain (`K1, K3, K4, K5`). If `K1` and one more honest key confirm `R`, the confirmation count reaches 3 (`K1`'s + `K2`'s stale one + one honest confirmer), and `R` executes — even though only 2 currently-valid keys ever actually approved it, below the intended 3-of-n threshold.
- Because `MultiSigRequestAction::Transfer` executes a `Promise::transfer`, this directly enables moving NEAR out of the account with fewer live approvals than policy requires, i.e., NEAR moved by parties not entitled (in aggregate) to authorize that move.

### Likelihood Explanation
This requires only the normal multisig operational flow — no owner or foundation privilege, no redeploy, no RPC interception. It is triggered whenever a key is revoked (a routine security response to a suspected compromised or departing signer) while that key has an outstanding confirmation on some other pending request. Any of the currently-authorized signers (including one who is later revoked) can trigger this by confirming a request and then being removed, which is a realistic and even expected operational sequence for key rotation/incident response.

### Recommendation
When executing `DeleteKey`, iterate over all entries in `self.confirmations` (not just requests created by the deleted key) and remove the deleted `public_key` from every confirmer set, decrementing/re-evaluating any requests whose confirmation count was inflated by that key. Alternatively, validate at `confirm()`/execution time that each `PublicKey` in the stored confirmation set is still a currently valid access key of the account (e.g., via `env::promise_batch_action_*` introspection or a maintained live-key registry) before counting it toward the threshold.

### Proof of Concept
Using the existing test harness structure in `multisig/src/lib.rs`:
1. `new(3)` with keys `K1, K2, K3, K4, K5` (5 keys added as full-access keys, `num_confirmations = 3`).
2. As `K1`: `add_request(Transfer { amount, receiver_id: attacker })` → `request_id = R`.
3. As `K2`: `confirm(R)` → confirmations for `R` = `{K1? no — only signer of confirm calls, so {K2}}` (1 confirmation, below threshold, request stays open).
4. As `K3, K4, K5` (3 honest keys): create and confirm a separate request `DeleteKey { public_key: K2 }` until it reaches 3 confirmations and executes — `K2` is removed from `num_requests_pk` and from any requests *K2 authored*, but `self.confirmations.get(&R)` still contains `K2`.
5. As `K1`: `confirm(R)` → confirmations for `R` becomes `{K2, K1}` = 2.
6. As `K3`: `confirm(R)` → confirmations count reaches 3 (`K2` stale + `K1` + `K3`) → `confirmations.len() as u32 + 1 >= 3` triggers execution, and the `Transfer` promise fires — despite only `K1` and `K3` being currently valid signers who actually approved, one short of the required 3 live approvals.

This demonstrates the request executes with only 2 genuinely live confirmations against a configured 3-of-n threshold, confirming the equality break identified above.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
