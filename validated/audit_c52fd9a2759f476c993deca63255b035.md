### Title
Reused `builder_index` lets a settled payment owed to an exited builder be paid out of the balance of a new, unrelated builder that later occupies the same slot - (File: `specs/gloas/beacon-chain.md`)

### Summary
`state.builder_pending_withdrawals` entries identify the payee only by `builder_index`, never by `pubkey`. `builder_index` slots are explicitly documented as reusable once a builder fully exits and sweeps to zero balance. If a pending withdrawal for builder A (queued via `process_execution_payload_bid` → `settle_builder_payment`) is still outstanding in `state.builder_pending_withdrawals` when slot `i` is freed and reassigned to a brand-new builder B, `get_builder_withdrawals`/`apply_withdrawals` will debit builder B's freshly-deposited balance to satisfy A's payment, sending B's Gwei to A's `fee_recipient`.

### Finding Description
This is the direct spec-level analog of the Caviar bug: in the Solidity report, the pool's *ownership token* (index) was resold while the previous owner retained stale authorization (`approve`), letting them later drain funds credited to the new owner. Here the equality broken is the same shape: **"the entity paying/being debited for withdrawal X must be the entity that actually incurred that obligation."**

Mechanics:
1. `is_active_builder` gates exit-eligibility, and `process_builder_exit_request` refuses to exit a builder while it has a nonzero `get_pending_balance_to_withdraw_for_builder` result. This suggests the spec *authors intended* pending withdrawals to block reuse. But `get_index_for_new_builder` reuse condition only checks `builder.balance == 0`, not "no outstanding `builder_pending_withdrawals` entries referencing this index."
2. `builder.balance` is decremented only inside `apply_withdrawals`, at the moment the withdrawal is actually swept from `state.builder_pending_withdrawals`/the FIFO queue processed by `get_builder_withdrawals`. Crucially, `settle_builder_payment` (called from `apply_parent_execution_payload`) appends the `BuilderPendingWithdrawal` object without touching `builder.balance` at all — the balance stays intact until the FIFO withdrawal queue actually reaches it.
3. Therefore there is a window where builder A has `balance == 0` (because its balance was never separately reserved for the pending withdrawal — the withdrawal amount is tracked purely in the `builder_pending_withdrawals` list) while still having an unpaid obligation recorded in that list at slot `i`.
4. If A's `withdrawable_epoch <= current_epoch` at this point (satisfied once A submits/settles a `BuilderExitRequest` and is swept, or simply because A's balance is 0 for any other reason), `get_index_for_new_builder` returns index `i` as free, and `add_builder_to_registry`/`process_builder_deposit_request` place new builder B's pubkey and deposit there via `set_or_append_list`.
5. B's `Builder` record now lives at index `i`, holding B's real deposited Gwei.
6. When `get_builder_withdrawals` eventually processes the still-queued `BuilderPendingWithdrawal(builder_index=i, fee_recipient=<A's address>, amount=X)`, `apply_withdrawals` does `state.builders[i].balance -= min(X, state.builders[i].balance)` — decrementing **B's** balance and creating a `Withdrawal` paid to **A's** `fee_recipient`.

### Impact Explanation
This is a Critical-class impact under the given rubric: Gwei is destroyed from builder B's account and paid to a non-owner (builder A's fee recipient) without B's authorization or any equivocation/misbehavior by B. It is a pure "stale obligation surviving identity reassignment" bug, structurally identical to the Caviar approval-farming exploit, except here it is baked into consensus-critical state transition logic (`get_builder_withdrawals`, `apply_withdrawals`, `get_index_for_new_builder`), not merely an application-level approval.

### Likelihood Explanation
Requires: (a) a builder with a pending, unsettled `builder_pending_withdrawals` entry, (b) that builder's balance separately reaching zero and `withdrawable_epoch` reaching the current epoch (e.g., via `process_builder_exit_request` + being swept by `get_builders_sweep_withdrawals`, or simply spending down/losing balance through other means while a payment is still enqueued), and (c) a new deposit landing in the freed slot before the old pending withdrawal is processed. Whether `get_pending_balance_to_withdraw_for_builder` (referenced in `process_builder_exit_request` and `process_builder_deposit_request`'s reuse gating, per the note about builder index reuse) is actually consulted by `get_index_for_new_builder` could not be fully confirmed from the excerpts retrieved — `get_index_for_new_builder`'s visible implementation only checks `withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0`, with no visible cross-check against `state.builder_pending_withdrawals`. This is the crux of the finding and needs to be verified against the full function bodies of `get_pending_balance_to_withdraw_for_builder` and `settle_builder_payment` (not fully retrieved) to be certain the balance-vs-pending-withdrawal invariant is not enforced elsewhere before slot reuse is permitted.

### Recommendation
Before allowing `get_index_for_new_builder` to return a slot, additionally verify that no entries in `state.builder_pending_withdrawals` (and `builder_pending_payments`) still reference that `builder_index`. Alternatively, resolve `BuilderPendingWithdrawal` payees by `pubkey` rather than positional `builder_index`, or reserve/ring-fence the pending amount from `builder.balance` at the moment the payment is queued (in `settle_builder_payment`) rather than at final sweep time, so a slot can only be freed once truly zero-obligation.

### Proof of Concept
Conceptual state-transition trace (spec-level, not full PoC code since I could not fully verify `settle_builder_payment`'s exact interaction with `builder.balance`):
1. Builder A (index 0) accepts a bid, payment is queued via `process_execution_payload_bid` → later `settle_builder_payment` appends `BuilderPendingWithdrawal(builder_index=0, fee_recipient=A_addr, amount=X)` to `state.builder_pending_withdrawals`.
2. Builder A's `balance` independently reaches 0 (e.g. exits and is fully swept by `get_builders_sweep_withdrawals`, or amount otherwise nets to zero) while the entry from step 1 is still queued (not yet reached by `get_builder_withdrawals`'s FIFO due to queue depth/limits).
3. `get_index_for_new_builder` sees index 0: `withdrawable_epoch <= current_epoch` and `balance == 0` → returns index 0 as reusable.
4. A `BuilderDepositRequest` for new builder B is processed; `add_builder_to_registry` places B (new pubkey, deposit amount Y) at index 0 via `set_or_append_list`, per `specs/gloas/beacon-chain.md:2222-2245`.
5. On a later slot, `get_builder_withdrawals` reaches the still-pending withdrawal entry `(builder_index=0, fee_recipient=A_addr, amount=X)`; `apply_withdrawals` executes `state.builders[0].balance -= min(X, state.builders[0].balance)`, decrementing B's `Y` balance and emitting a `Withdrawal` paying `X` to `A_addr`. def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:

    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
