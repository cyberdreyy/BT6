### Title
`parse_nonce` misreports oversized System-owned accounts as `Initialized` nonce accounts due to non-strict `bincode::deserialize` - ([File: account-decoder/src/parse_nonce.rs])

### Summary
`parse_nonce` calls `bincode::deserialize(data)` and only guards against the `State::Uninitialized` case, relying on the comment's assumption that "an account of the wrong length can never be initialized." `bincode::deserialize` does not require that the entire input buffer be consumed—it only reads as many bytes as needed for the target type and silently ignores any trailing bytes—so an account whose length is greater than the canonical nonce `State::size()` but whose leading bytes are a valid serialized `Versions::Current(State::Initialized(Data))` will still deserialize successfully.

### Finding Description
`parse_nonce` at [1](#0-0)  deserializes the raw account bytes into `Versions` and only rejects the `State::Uninitialized` variant; it performs no explicit check that `data.len()` equals the canonical nonce account size (`State::size()`), despite the adjacent comment claiming this can't happen ("An empty account of the wrong length can never be initialized as a nonce account..."). That invariant is only true because the *short*-buffer case fails via `UnexpectedEof` inside `bincode::deserialize`, as demonstrated by the existing unit test with a 4-byte buffer at [2](#0-1) . It is not true for the *long*-buffer case: `bincode::deserialize` reads a fixed-size, `Vec`/`String`-free structure (`Versions` -> `State::Initialized(Data)`, all fixed-width fields—`Pubkey`, `Hash`, `u64`) and stops once those fields are populated, without verifying that the remaining trailing bytes in the slice were consumed. An attacker who allocates a System-owned account via `CreateAccount`/`Allocate` with a length strictly greater than `State::size()`, and places a valid serialized `Initialized` nonce state as the byte prefix (with arbitrary trailing bytes), causes `parse_nonce` to return `Ok(UiNonceState::Initialized(...))` reporting attacker-chosen authority/blockhash/fee_calculator, even though this account can never actually function as a durable nonce account at the runtime level (nonce processing checks require the exact canonical size).

### Impact Explanation
This is an RPC data-integrity/misreporting bug: `getAccountInfo`/`getParsedAccountInfo` (jsonParsed encoding path calling into `parse_account_data` -> `parse_nonce`) can return fabricated "Initialized" nonce data (authority, blockhash, fee calculator) for an account that is not actually a functional nonce account. Clients relying on parsed RPC output (e.g., wallets checking nonce authority before signing a transaction with `nonce_advance`) could be misled into trusting attacker-controlled data as a legitimate durable-nonce account state, falling under the "wrong ... account data returned" / decoder-misreporting category in scope.

### Likelihood Explanation
Fully feasible with a single unprivileged client: create/allocate a System-owned account of chosen length (`CreateAccount`/`Allocate`), write arbitrary bytes via any means available to the account owner (e.g. via a follow-up transaction that writes data, or simply the initial `CreateAccount` with data), then issue one `getAccountInfo` RPC call with `encoding: jsonParsed`. No validator, leader, or gossip control is required—purely client-side account crafting plus a single read-only RPC call, well within the one-call rate limit.

### Recommendation
In `parse_nonce`, explicitly validate `data.len() == State::size()` (or the exact expected serialized length for `Versions::Current`) before or after deserialization, returning `ParseAccountError::from(InstructionError::InvalidAccountData)` for any mismatch, rather than relying on `bincode::deserialize`'s implicit short-buffer failure. Alternatively, use `bincode::deserialize` combined with an explicit check that all bytes were consumed (e.g., via `bincode::config` strict options or comparing `data.len()` against `bincode::serialized_size` of the decoded value).

### Proof of Concept
```rust
// account-decoder/src/parse_nonce.rs (added test)
use solana_nonce::state::{Data, State};
use solana_nonce::versions::Versions;

#[test]
fn test_parse_nonce_rejects_oversized_buffer() {
    let nonce_data = Versions::new(State::Initialized(Data::default()));
    let mut nonce_account_data = bincode::serialize(&nonce_data).unwrap();
    // Simulate an attacker-allocated account with extra trailing garbage bytes
    // (length != canonical nonce State::size()).
    nonce_account_data.extend_from_slice(&[0xAB; 16]);

    // Expected (per comment at lines 12-15): must be rejected as InvalidAccountData.
    // Actual (bug): bincode::deserialize ignores trailing bytes and this succeeds
    // with UiNonceState::Initialized(..), misreporting the account.
    assert!(
        parse_nonce(&nonce_account_data).is_err(),
        "parse_nonce incorrectly reported an oversized/garbage-suffixed account as Initialized"
    );
}
```
Run with `cargo test -p solana-account-decoder parse_nonce` to confirm the assertion fails against current code (i.e., `parse_nonce` returns `Ok(...)` instead of the expected `Err`), demonstrating the misreporting.

pub fn parse_nonce(data: &[u8]) -> Result<UiNonceState, ParseAccountError> {
    let nonce_versions: Versions = bincode::deserialize(data)
        .map_err(|_| ParseAccountError::from(InstructionError::InvalidAccountData))?;
    match nonce_versions.state() {
        // This prevents parsing an allocated System-owned account with empty data of any non-zero
        // length as `uninitialized` nonce. An empty account of the wrong length can never be
        // initialized as a nonce account, and an empty account of the correct length may not be an
        // uninitialized nonce account, since it can be assigned to another program.
        State::Uninitialized => Err(ParseAccountError::from(
            InstructionError::InvalidAccountData,
        )),
