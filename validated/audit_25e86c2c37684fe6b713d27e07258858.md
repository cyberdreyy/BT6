### Title
Instant-withdraw receipts requested before a `stopEpoch` are keyed to the wrong epoch at default finalization, permanently freezing their claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analog of the Vert.x static-handler cache poisoning: there, a crafted URI makes the cache store/lookup a resource under a non-canonical key so the legitimate file is denied (404). Here, instant-withdraw receipt claims are cached under the *request-time* `epochNumber` in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, but default finalization looks them up under the *current* `epochNumber` (`defaultRecoveryEpoch`). A stopEpoch bumps `epochNumber`, so any instant receipt left unfunded across an epoch boundary becomes unreachable by both claim paths — it is excluded from the recovery basis and blocked from the funded path by the reserve guard — permanently freezing the user's claim.

### Finding Description
`requestInstantWithdraw` records basis per request epoch (`instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`) and increases the global `pendingInstantWithdraws` [1](#0-0) . `epochNumber` is incremented in `deposit` whenever the CDO deposits while an epoch is running, i.e. at every `stopEpoch` [2](#0-1) . Nothing in `requestInstantWithdraw`, `stopEpoch`, or lazy init forces instant receipts to be funded before the epoch rolls over; `collectInstantWithdrawFunds` is optional and only reduces `pendingInstantWithdraws` [3](#0-2) .

On default, `finalizeDefaultRecovery` snapshots `defaultRecoveryEpoch = epochNumber` [4](#0-3) . `defaultPendingClaimBasis` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — so receipts recorded under an earlier epoch contribute zero to the recovery basis even though `pendingInstantWithdraws != 0` sets `defaultInstantWithdrawsFinalized = true` [5](#0-4) . `_defaultPrefundedInstantReserve` compares the current-epoch basis against the *global* `pendingInstantWithdraws`, so the stale receipts are never counted as prefunded either [6](#0-5) .

After finalization, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the wrong key — finds 0, and clears nothing [7](#0-6) . The stale amount remains in `instantWithdrawsRequests[_user]` and falls to `_transferFundedClaim`, which reverts because `balanceOf(this) - defaultRecoveryReserve < amount` (the receipt's backing was lent out and never added to the reserve) [8](#0-7) . The claim reverts `NotAllowed()` forever; there is no admin path to force-pay it without touching honest users' recovery reserve.

### Impact Explanation
Direct permanent freezing of user funds. A lender holding an unfunded instant-withdraw receipt loses 100% of the requested amount: the receipt tokens cannot be burned for recovery (wrong epoch key → zero claim basis) and cannot be paid at par (reserve guard). Additionally, because these receipts are missing from `totalBasis`, `recoveryPrice` is computed against a smaller denominator, slightly inflating payouts to other claimants — a secondary mispricing, though the primary loss is the frozen receipt.

### Likelihood Explanation
Requires only unprivileged actions in normal protocol flow: (1) any KYC'd tranche holder calls `requestInstantWithdraw` during epoch N while the strategy has no spare underlying (the common case — deposits are sent to the borrower); (2) an honest `stopEpoch` runs without the CDO calling `collectInstantWithdrawFunds`, bumping `epochNumber` to N+1; (3) the borrower defaults in a later epoch and the manager finalizes recovery. No malicious privileged role is needed; the bug triggers whenever an instant request survives an epoch boundary unfunded and a default is later finalized.

### Recommendation
Canonicalize the lookup key, mirroring the Vert.x fix (proper normalization before cache access). Either:
- Make `_claimDefaultedInstantWithdrawRequest` (and `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`) iterate or track all epochs with unfunded instant basis, not just `defaultRecoveryEpoch` — e.g. maintain a global `instantWithdrawClaimsTotal` that mirrors `pendingInstantWithdraws` semantics; or
- Roll each user's stale instant basis forward: in `requestInstantWithdraw` and at `stopEpoch`, migrate `instantWithdrawsRequestsByEpoch[_user][oldEpoch]` into the current epoch so the single-slot epoch key stays canonical, the same approach already used for `lastWithdrawRequest`/`lossRecoveryPriceByEpoch` in `requestWithdraw` [9](#0-8) .

### Proof of Concept
Foundry fork PoC outline (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantReceiptFrozenAcrossEpochBoundary() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    address victim = makeAddr('victim');

    // Epoch N running: victim deposits AA and requests an instant withdraw.
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    uint256 req = cdoEpoch.requestInstantWithdraw(0, address(AAtranche)); // victim's receipt

    // Epoch ends; CDO never calls collectInstantWithdrawFunds (no spare cash).
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0); // bumps vault.epochNumber() N -> N+1

    assertEq(vault.pendingInstantWithdraws(), req);
    assertEq(vault.instantWithdrawsRequestsByEpoch(victim, vault.epochNumber()), 0); // keyed under N

    // Borrower defaults in epoch N+1; manager finalizes recovery.
    _handleBorrowerDefault();            // honest manager/borrower flow
    vault.finalizeDefaultRecovery(0, address(0)); // via CDO

    // Victim's claim: defaulted path finds claimBasis == 0 (wrong epoch key);
    // funded path reverts on the reserve guard -> permanent freeze.
    vm.prank(victim);
    vm.expectRevert(IdleCreditVault.NotAllowed.selector);
    cdoEpoch.claimInstantWithdrawRequest();

    assertEq(vault.instantWithdrawsRequests(victim), req); // receipt never cleared
}
```

The test demonstrates the broken "one receipt, one payout" invariant: the receipt exists and is backed by borrower debt, yet neither the defaulted-epoch claim nor the funded claim can ever pay it.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
