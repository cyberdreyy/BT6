### Title
Loss-adjusted withdraw receipts claimable at par because `lossRecoveryPriceByEpoch` is keyed by the post-increment epoch while `lastWithdrawRequest` stores the request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` handles a borrower shortfall at `stopEpochWithDuration` by haircutting pending withdraw receipts: `collectWithdrawFunds` stores a funded recovery ratio in `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`. However, `epochNumber` is incremented inside `deposit()` when the CDO calls it during `stopEpoch` (isEpochRunning is still true), while `lastWithdrawRequest[_user]` was recorded at request time in the previous epoch. The user's receipt epoch and the haircut's storage key therefore disagree, so the haircut is never applied and the receipt is paid in full from funded reserves.

### Finding Description

- When a user calls `IdleCDOEpochVariant.requestWithdraw`, the strategy mints them a strategy-token receipt and records `lastWithdrawRequest[_user] = epochNumber` and `withdrawsRequestsByEpoch[_user][epochNumber] += _amount` [1](#0-0) .
- At `stopEpoch` the CDO pulls repayment via `strategy.deposit(...)`. Inside `deposit()`, because `isEpochRunning()` is still true, the strategy executes `epochNumber += 1` [2](#0-1) .
- On a shortfall, `collectWithdrawFunds(_amount < pendingBasis)` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis`, sets `pendingWithdraws = 0`, and stores it under the *already-incremented* `epochNumber` [3](#0-2) .
- The guard meant to force users to claim haircutted receipts checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the *pre-increment* epoch — so it reads `0` and lets the user open new requests freely [4](#0-3) .
- Worse, `_claimLossAdjustedWithdrawRequest` uses the same stale `lastWithdrawRequest` key, gets `lossRecoveryPrice == 0`, and returns 0. Execution then falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` at par via `_transferFundedClaim` [5](#0-4) [6](#0-5) .

The result: a receipt that should pay `claimBasis * lossRecoveryPrice / 1e18` pays `claimBasis` in full, while `pendingWithdraws` was already cleared — the excess comes out of the strategy's funded reserve destined for other claimants.

### Impact Explanation
Any KYC-passed lender with a pending withdraw request during an epoch that ends with `stopEpochWithDuration(_lossAmount > 0)` is overpaid by `claimBasis * (1 - lossRecoveryPrice)`. Since the haircutted reserve is sized for the haircut price, claimants who exit first drain underlying earmarked for later claimants, causing direct theft and insolvency for remaining receipt holders — a realized-loss socialization failure equivalent to the "corrupted allocator metadata" class of CVE-2024-5839.

### Likelihood Explanation
Requires only: (1) a lender request during buffer/running phase, and (2) the honest manager calling `stopEpochWithDuration` with a partial loss — a routine, expected operation. No privileged misbehavior needed. Attacker cost is one `requestWithdraw` plus one `claimWithdrawRequest`.

### Recommendation
Store the loss recovery price under the epoch in which the receipts were requested (e.g., persist `epochNumber` before the deposit-time increment, or key `lossRecoveryPriceByEpoch` by `epochNumber - 1`/the request epoch), and make `requestWithdraw`, `_claimLossAdjustedWithdrawRequest`, and `_clearWithdrawClaimForEpoch` resolve the haircut epoch consistently. Add a regression test asserting haircutted claims cannot be paid at par.

```solidity
// test/foundry/IdleCreditVault.t.sol — fork-style PoC sketch
function testLossAdjustedReceiptPaidAtPar() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // buffer phase: request withdraw -> lastWithdrawRequest[this] = epochNumber = N
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // manager starts epoch N+1, borrower repays partially -> stopEpochWithDuration(loss)
    _startEpochAndCheckPrices(0);
    uint256 loss = requested / 2; // 50% shortfall on pending receipts
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - loss);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss, initialProvidedApr); // deposit() bumps epochNumber to N+1; lossRecoveryPriceByEpoch[N+1] set

    // haircut lookup uses stale epoch N -> misses -> claim pays FULL amount
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // expected haircut payout was requested/2; user receives `requested` instead
    assertEq(paid, requested, "receipt paid at par despite recorded loss");
}
```
Note: this PoC assumes `collectWithdrawFunds` runs after the `deposit()`-time `epochNumber` increment inside `stopEpoch`/`stopEpochWithDuration`; if the CDO collects withdraw funds *before* the incrementing deposit, the epoch keys would agree and the bug does not manifest — I was unable to verify the exact ordering within `stopEpochWithDuration` before producing this answer, so that call order should be confirmed first when validating.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".

      // successful stop can fully fund the aggregate before lazy initialization occurs.
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```
