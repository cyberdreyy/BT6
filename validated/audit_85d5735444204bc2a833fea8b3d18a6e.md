### Title
Commitment-blind, fork-unaware TTL cache in `LargestAccountsCache` can serve accounts from a discarded fork to a `finalized`-commitment caller - ([File: rpc/src/rpc_cache.rs])

### Summary
`LargestAccountsCache::get_largest_accounts` and `set_largest_accounts` key cached entries solely by the `RpcLargestAccountsFilter` and validate freshness purely via a wall-clock TTL (`cached_time.elapsed() < Duration::from_secs(self.duration)`), with no reference to the bank's rooted status, slot commitment level, or fork identity. [1](#0-0)  Consequently, once a `(slot, accounts)` pair is cached from a bank on an as-yet-unrooted fork, any subsequent call for the same filter within the TTL window — including one explicitly requesting `commitment=finalized` — will receive that cached value with no check that the originating slot is still part of the rooted chain. [2](#0-1) 

### Finding Description
`LargestAccountsCacheValue` stores `accounts`, `slot`, and `cached_time`, and the cache map is keyed only by `Option<RpcLargestAccountsFilter>` (i.e., `Circulating`/non-circulating), not by commitment level or bank identity. [2](#0-1)  `get_largest_accounts` returns the cached `(slot, accounts)` tuple whenever `elapsed < duration`, regardless of what commitment the current request specifies. [3](#0-2)  There is no call back into `BankForks`/`bank_forks.root_bank()` or any rooted-status check to confirm the cached `slot` is still on the canonical/rooted chain before returning it.

Because the cache has a single entry per filter, a first request (default commitment, or any commitment that resolves to a bank on a fork that is later discarded) can populate the cache with data derived from an unrooted bank. If a second request for the same filter — even one specifying `commitment=finalized` — arrives before TTL expiry, the RPC layer's cache lookup path (`rpc.rs`'s largest-accounts handler, which consults `LargestAccountsCache` before falling back to computing from the commitment-selected bank) will short-circuit and return the stale, fork-A-derived `(slot, accounts)` pair without any re-validation against the currently rooted bank set.

This violates the invariant that finalized-labeled responses must be derived from rooted/finalized state: the cache mechanism itself provides no fork-awareness or invalidation hook triggered by root advancement or fork removal in `BankForks`.

### Impact Explanation
This is a correctness violation of RPC's commitment semantics: a client requesting `finalized` largest-accounts data can be served balances and a slot number that were computed from a bank belonging to a fork that was subsequently discarded and never rooted. This falls under wrong-slot/fork data returned to a legitimate, unprivileged single-caller request, matching the "consensus-state/data-correctness" bounty category for RPC responses that misrepresent finalized state.

### Likelihood Explanation
Requires only two ordinary JSON-RPC calls at legal request rates (`getLargestAccounts` with default/any commitment, then `getLargestAccounts` with `commitment=finalized`) straddling a natural fork-resolution event on the validator — no special privileges, multiple clients, or elevated call rate are needed. Fork switches occur regularly in normal cluster operation, so the timing window (within the cache TTL, which defaults to a value on the order of tens of seconds) is realistically reachable by an unprivileged client simply polling around a period of chain instability.

### Recommendation
Make the cache commitment- and root-aware: (1) include the commitment level (or bank's rooted/finalized status at cache-write time) in the cache key so entries computed under different commitments are never conflated; (2) before returning a cached entry, verify that `slot` is still present/rooted in `BankForks` (e.g., `bank_forks.read().unwrap().root() >= slot` and the bank at `slot` is still reachable via the rooted ancestor chain), invalidating and recomputing if not; (3) alternatively, drop cached entries proactively on root-advance notifications rather than relying solely on TTL expiry.

### Proof of Concept
Integration test sketch (to be added near `rpc_cache.rs`'s existing tests, exercised through the RPC handler layer that owns `LargestAccountsCache`):

```rust
#[test]
fn test_largest_accounts_cache_serves_stale_fork_data_as_finalized() {
    // 1. Build two competing forks A and B off a common parent, both containing
    //    distinct large-balance accounts, using BankForks test helpers.
    // 2. Call the RPC handler's getLargestAccounts with default commitment while
    //    the "best" bank is on fork A (unrooted), causing
    //    LargestAccountsCache::set_largest_accounts to store fork A's slot/accounts.
    let mut cache = LargestAccountsCache::new(30);
    let filter = None;
    cache.set_largest_accounts(&filter, fork_a_slot, &fork_a_accounts);

    // 3. Simulate consensus rolling back fork A and rooting fork B at slot fork_b_slot
    //    (drop fork A from BankForks, advance root to fork_b_slot).

    // 4. Call the RPC handler's getLargestAccounts with commitment = finalized
    //    within the TTL window; it consults the cache first.
    let (returned_slot, returned_accounts) = cache.get_largest_accounts(&filter).unwrap();

    // Expected (desired) behavior: returned_slot/accounts should reflect fork B
    // (rooted state), not fork A.
    assert_ne!(returned_slot, fork_a_slot, "cache returned discarded fork's slot");
    assert_eq!(returned_slot, fork_b_slot);
    assert_eq!(returned_accounts, fork_b_accounts);
}
```
This demonstrates that, as currently implemented, `LargestAccountsCache` has no mechanism to detect that `fork_a_slot` was discarded, so the assertions against fork B fail and the stale fork-A `(slot, accounts)` pair is returned to the `finalized`-commitment caller.

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }

    pub(crate) fn set_largest_accounts(
        &mut self,
        filter: &Option<RpcLargestAccountsFilter>,
        slot: u64,
        accounts: &[RpcAccountBalance],
    ) {
        self.cache.insert(
            filter.clone(),
            LargestAccountsCacheValue {
                accounts: accounts.to_owned(),
                slot,
                cached_time: SystemTime::now(),
            },
        );
    }
