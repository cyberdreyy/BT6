### Title
Truncated recovery price strands residual recovered funds in `IdleCreditVault` forever - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

After a borrower default, `finalizeDefaultRecovery` fixes a single aggregate multiplier (`defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`) and every receipt claim is then paid as `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`. Both divisions round down, and the payout path only ever dispenses the computed per-claim amount — never the contract's residual balance — so recovered underlying accumulates as permanently locked dust in the strategy, mirroring the Lido `NodeOperatorRegistry.distributeRewards()` remainder leak. The Lido fix (distribute the full balance / route residual to treasury) was never applied here: there is no sweep of the leftover recovery reserve and `_skimDonatedAssets` on the CDO only covers the CDO's own raw balance, not the strategy's reserve.

### Finding Description

In `finalizeDefaultRecovery` the recovery ratio is computed once with truncation: [1](#0-0) 

Every claim then truncates again:

- defaulted normal/APR0 receipts: `amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` (`_claimDefaultedWithdrawRequest`, lines 782-783)
- defaulted instant receipts: same formula (`_claimDefaultedInstantWithdrawRequest`, lines 854-855)
- loss-adjusted funded receipts: `amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL` where `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` was itself truncated in `collectWithdrawFunds` (lines 417-421, 799-800)

Each of these transfers out only the floored amount and decrements `defaultRecoveryReserve` (or leaves the surplus in the strategy balance for loss-adjusted claims) by exactly what was paid. Two compounding truncation layers exist:

1. `recoveryPrice` truncation: `reserveAmount * RECOVERY_FULL / totalBasis` loses up to 1 unit of `RECOVERY_FULL`-scaled price, i.e. up to ~`totalBasis / RECOVERY_FULL` underlying across all claimants.
2. Per-claim truncation: each of `n` claimants loses up to 1 wei, and the aggregate payout is strictly less than the funded `reserveAmount` whenever `recoveryPrice < RECOVERY_FULL` (any haircut).

Because the code distributes per-receipt computed amounts and not the whole reserve — exactly the pattern flagged in the Lido report — the residual has no claim path: all receipt mappings are zeroed on claim (`withdrawsRequestsByEpoch`, `instantWithdrawsRequestsByEpoch`, `apr0Users`), `postDefaultRequests` pay out their own recorded amount only, and after `defaultRecoveryFinalized` no function re-prices or sweeps the remainder. The comments at lines 655-657 acknowledge "recovery dust" for the sub-precision edge case but the general per-claim truncation residue is unhandled and unrecoverable to users.

### Impact Explanation

Permanent freezing of recovered borrower funds. The residual is bounded by roughly `n_claimants` wei plus the `recoveryPrice` truncation (`< totalBasis / RECOVERY_FULL` underlying) per defaulted/loss-adjusted epoch, and accumulates monotonically across epochs and — for `lossRecoveryPriceByEpoch` — across every stop-with-loss, since each epoch stores an independent truncated price and leftovers are never recycled into subsequent claims. With many small receipts (KYC'd lenders can each hold multiple receipts across epochs), the stranded amount can grow to a non-trivial absolute value of funds that economically belong to receipt holders. The honest owner/manager cannot fix it post-finalization because `defaultRecoveryFinalized` blocks re-pricing and no sweep exists for the strategy's recovery balance.

### Likelihood Explanation

Certain in outcome, small in magnitude per epoch — identical profile to the Lido issue (rated Medium: High impact capped by wei-scale leak, Low likelihood of materiality). Any default finalization or `stopEpochWithDuration` partial funding with a non-par recovery price guarantees residue; the only question is whether the accumulated dust is economically meaningful, which depends on receipt count and token decimals.

### Recommendation

Mirror the Lido remediation: distribute the entire balance rather than the freshly computed amount. Concretely, make the last claimant (or a designated sweep) receive `defaultRecoveryReserve` / the contract's remaining balance instead of `claimBasis * price / RECOVERY_FULL`, or track `distributedBasis` and periodically sweep `underlyingToken.balanceOf(address(this)) - sum(openClaimBases * price / RECOVERY_FULL)` to `feeReceiver`/treasury. Alternatively compute a per-unit payout once and add the rounding residue to the largest/first claim. The same applies to `lossRecoveryPriceByEpoch` claims in `collectWithdrawFunds`.

### Proof of Concept

A reproducible Foundry PoC (extending `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testDefaultRecoveryLeavesUnclaimableResidue() external {
  // 1. Two KYC'd lenders deposit, epoch starts, borrower defaults mid-epoch.
  //    (reuse existing default setup: depositAA/depositBB, startEpoch,
  //     then _handleBorrowerDefault via failed borrower repayment)
  // 2. Manager calls cdoEpoch.finalizeDefault(recovered, source) with
  //    recovered < totalBasis so defaultRecoveryPrice < RECOVERY_FULL
  //    and non-divisible, e.g. recovered = 333, basis = 1000.
  // 3. All users call cdoEpoch.claimWithdrawRequest() /
  //    claimInstantWithdrawRequest() until every receipt mapping is zero:
  //    - pendingWithdraws == 0
  //    - instantWithdrawsRequestsByEpoch[user][defaultEpoch] == 0 for all users
  // 4. assertGt(underlying.balanceOf(address(strategy)), 0)
  //    and assertGt(strategy.defaultRecoveryReserve(), 0):
  //    residual recovered funds remain locked with no claim or sweep path.
}
```

Steps: seed ≥2 withdraw receipts with `claimBasis` values not divisible by `RECOVERY_FULL`, force a default, call `finalizeDefaultRecovery` via `cdoEpoch.finalizeDefault` with a partial recovery so `reserveAmount * RECOVERY_FULL % totalBasis != 0`, exhaust all claims, then assert a nonzero strategy underlying balance and nonzero `defaultRecoveryReserve` that no external function can move. The same pattern applies to `collectWithdrawFunds` loss-adjusted epochs by asserting strategy balance exceeds the sum of payouts after all epoch receipts are claimed.
