### Title
Retained APR0 withdraw bucket bricks `stopEpoch` after APR is raised, freezing the epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the `sh` `_uid` incomplete privilege drop — where the process kept supplementary groups after dropping its UID — `IdleCreditVault` fails to fully "drop" the APR0 state when the vault leaves APR=0 mode. A lender who opened a withdraw request while `unscaledApr == 0` leaves residual privilege in `apr0TotalPrincipal`/`apr0Users`, and `prepareStopEpochWithApr0` reverts with `NotAllowed` whenever that bucket is non-zero while `unscaledApr != 0`. The stale bucket permanently reverts `stopEpoch`, freezing all pending withdrawals and epoch settlement until the APR is manually set back to 0 or the borrower defaults.

### Finding Description
When a user calls `requestWithdraw` while the vault is in APR=0 mode (`unscaledApr == 0` and pool not closed), the request is routed to `_requestWithdrawApr0`, which records `apr0Users[_user].principal` and increments the global `apr0TotalPrincipal` [1](#0-0) [2](#0-1) .

`apr0TotalPrincipal` is cleared in exactly two places: inside `prepareStopEpochWithApr0` at the end of a successful call, and inside `_clearWithdrawClaimForEpoch` during default finalization [3](#0-2) [4](#0-3) .

The problem is in `prepareStopEpochWithApr0` (called by the IdleCDO during `stopEpoch`): after the fast-path early return for `_principal == 0`, it reverts if `unscaledApr != 0` while `apr0TotalPrincipal` is still non-zero [5](#0-4) .

So the sequence is:

1. Vault runs an epoch with `unscaledApr == 0` (legitimate APR0 configuration).
2. Attacker (any KYC-passing lender) deposits a small amount and calls `requestWithdraw`, creating `apr0Users[attacker].principal` and `apr0TotalPrincipal > 0`.
3. Borrower/manager (honest) later raises the APR above 0 — e.g. renegotiating the pool rate between or during epochs.
4. Manager calls `stopEpoch` → `prepareStopEpochWithApr0` hits `if (unscaledApr != 0) revert NotAllowed()` → the whole `stopEpoch` reverts.
5. Every subsequent `stopEpoch` reverts identically. The stale APR0 bucket cannot be settled by the user (`_settleApr0` only runs inside `claimWithdrawRequest`, which itself requires `epochNumber > lastWithdrawRequest` — i.e. a completed `stopEpoch` that can never happen) [6](#0-5) [7](#0-6) .

The "incomplete drop" is the APR0 privilege: the bucket exists to grant APR0 requesters a pro-rata share of stopEpoch interest, but once the pool leaves APR0 mode that entitlement is neither stripped nor grandfathered — it instead becomes a permanent revert wedge inside the epoch state machine.

### Impact Explanation
While the revert persists, `stopEpoch` cannot complete: `epochNumber` never increments, pending withdraw requesters cannot claim (the `epochNumber <= lastWithdrawRequest[_user]` gate never opens), and borrower interest settlement is stalled. All lenders' funds are temporarily frozen for as long as `unscaledApr != 0` and `apr0TotalPrincipal != 0`. The freeze is recoverable only by an honest manager setting the APR back to 0 (forcing one more APR0-priced epoch) or by borrower default — both outside the frozen users' control. Loss is bounded by the time-value of the frozen TVL plus the forced APR0 epoch's interest mispricing.

### Likelihood Explanation
Requires two conditions: a vault legitimately configured with `unscaledApr == 0` at some point (the APR0 flow exists precisely for this), and a subsequent honest APR increase while an APR0 withdraw request is still open. The attacker contribution is a dust deposit + `requestWithdraw` during the APR0 window, which any whitelisted lender can do. There is no guard that strips `apr0Users`/`apr0TotalPrincipal` when `unscaledApr` changes, and the `revert NotAllowed` is a hard guard, not a recoverable branch.

### Recommendation
Drop the stale privilege instead of reverting: in `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, settle the open APR0 bucket at a defined rate (e.g. zero interest, since the APR0 entitlement ended when the APR changed) — move each user's `principal` into `settledPrincipal`, add it back to `pendingWithdraws` if it was excluded, and zero `apr0TotalPrincipal` rather than reverting. Alternatively, sweep `apr0TotalPrincipal`/`apr0Users` at the moment `unscaledApr` transitions away from 0 (the actual "privilege drop" point), so no stale bucket can survive into the next `stopEpoch`.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// contracts/IdleCreditVault.sol stale APR0 bucket -> stopEpoch DoS
function test_StaleApr0BucketBricksStopEpoch() public {
    // 1. Deploy vault + IdleCDOEpochVariant, borrower sets unscaledApr = 0 (APR0 mode)
    // 2. Whitelist attacker, attacker deposits 1 wei underlying, epoch starts
    // 3. attacker -> requestWithdraw(1, attacker, 1): goes through _requestWithdrawApr0
    //    assert apr0TotalPrincipal == 1
    // 4. Borrower/manager sets unscaledApr = e.g. 5% (honest rate change)
    // 5. manager.stopEpoch() -> IdleCDO calls prepareStopEpochWithApr0 ->
    //    _principal != 0 && unscaledApr != 0 -> revert NotAllowed()
    vm.expectRevert(NotAllowed.selector);
    cdo.stopEpoch();
    // 6. Repeat: always reverts; epochNumber never increments
    vm.expectRevert(NotAllowed.selector);
    cdo.stopEpoch();
    // 7. attacker's claimWithdrawRequest also reverts (epochNumber == lastWithdrawRequest)
    vm.expectRevert();
    cdo.claimWithdrawRequest(); // via IdleCDO for attacker
    // Vault is frozen until APR is set back to 0 -> temporary freezing of all lender funds
}
```

Note: the PoC requires a vault configured with the APR0 (`unscaledApr == 0`) path enabled; the freeze duration depends on when/if the manager lowers the APR back to 0 or the borrower defaults, and should be validated against the exact `stopEpoch` wiring in `IdleCDOEpochVariant` (specifically that `prepareStopEpochWithApr0` is invoked unconditionally on every `stopEpoch`).
