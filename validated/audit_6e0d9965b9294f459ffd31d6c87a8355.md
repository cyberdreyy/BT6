### Title
`DefaultDistributor` can be activated before funds are deposited, letting holders burn tranche tokens for a zero/diluted payout - ([File: contracts/DefaultDistributor.sol](https://github.com/ThankGod76/idle-tranches--024/blob/main/contracts/DefaultDistributor.sol))

### Summary
`DefaultDistributor.setIsActive(true)` enables `claim()` and snapshots the redemption `rate` from the distributor's **current** underlying balance. There is no check that the recovered funds were actually transferred first, even though the contract's own dev note states it "is expected to have *all* `token` transferred to this contract before the first claim". This is the same bug class as `setReadyForPayout()` not requiring `updateDistribution()` first: an irreversible state transition is enabled without verifying its prerequisite was fulfilled. Any tranche holder (unprivileged) who calls `claim()` in the gap between activation and funding has their tranche tokens pulled into the distributor and receives 0 underlying — a permanent, unrecoverable loss.

### Finding Description
`setIsActive` computes `rate = token.balanceOf(this) * ONE_TRANCHE / trancheToken.totalSupply()` at activation time and never recomputes it. [1](#0-0) 

`claim()` then unconditionally pulls the caller's entire tranche balance via `transferFrom` and pays `trancheBal * rate / ONE_TRANCHE`, with no `rate > 0` or minimum-payout guard. [2](#0-1) 

If activation happens before funding, `rate == 0` (or is diluted if only partial funds are present). Every claim in that window permanently forfeits the holder's redemption right — tranche tokens are burned into the distributor while nothing (or a pro-rata share of only the partial balance) is paid out. When the owner later sends the recovered funds, there is no mechanism to compensate the already-burned claimants; `transferToken` can sweep funds out, but the burned receipt is gone. The missing check is the analog of the recommended `isDistributionSet()` guard: `setIsActive` should require `token.balanceOf(this) > 0` (or accept the funded amount as a parameter) before enabling claims.

### Impact Explanation
A default-scenario tranche holder who claims after activation but before the recovery transfer loses their entire payout; their tranche tokens are confiscated into `DefaultDistributor` and cannot be un-burned. With partial funding, early claimants are paid from an understated `rate` denominator mismatch — actually rate is fixed so claimants get `trancheBal * rate` each, but `rate` was set on a smaller balance, so aggregate claims underflow and the last claimant's transfer reverts on insufficient balance: the pool is insolvent for late claimers. Loss is quantified as the claimant's full pro-rata share of recovered funds.

### Likelihood Explanation
The ordering mistake requires only that the owner/manager enable claims before the recovery funds land (a two-step process done across transactions/blocks). During that window any tranche holder — including a MEV bot watching the mempool or an impatient user — can claim. This is not a malicious-privileged scenario: it is sequencing around an honest privileged call, exactly the pattern of the source report.

### Recommendation
Gate activation on actual funding, mirroring the source recommendation:

```solidity
// contracts/DefaultDistributor.sol
function setIsActive(bool _active) external {
    require(owner() == msg.sender, '!AUTH');
    if (_active) {
        uint256 bal = IERC20(token).balanceOf(address(this));
        require(bal > 0, '!FUNDED');            // distribution must be set first
        rate = bal * ONE_TRANCHE / IERC20(trancheToken).totalSupply();
    }
    isActive = _active;
}
```

Additionally, `claim()` should `require(rate > 0)` as defense-in-depth so a zero-rate activation can never burn receipts for nothing.

### Proof of Concept
Foundry test (drop into `test/foundry/DefaultDistributor.t.sol` style harness):

```solidity
function testClaimBeforeFundingBurnsReceipt() external {
    // user holds `amt` tranche tokens; distributor NOT yet funded
    distributor = new DefaultDistributor(address(underlying), address(tranche), address(this));

    // owner activates claims before sending recovered funds (ordering gap)
    distributor.setIsActive(true);
    assertEq(distributor.rate(), 0);

    // unprivileged holder claims during the gap: receipt burned, payout = 0
    uint256 userTranche = tranche.balanceOf(user);
    vm.startPrank(user);
    tranche.approve(address(distributor), userTranche);
    distributor.claim(user);
    vm.stopPrank();

    assertEq(tranche.balanceOf(user), 0, 'tranche tokens confiscated');
    assertEq(underlying.balanceOf(user), 0, 'zero payout at rate 0');

    // owner now funds the distributor; victim cannot be made whole on-chain
    deal(address(underlying), address(distributor), claimable);
    // user's receipt is gone — permanent loss of their pro-rata recovery share
}
```

A variant with partial funding shows insolvency: `rate` is fixed on the partial balance, so the last claimant's `safeTransfer` reverts while early claimants were paid — the distributor cannot honor all receipts.
