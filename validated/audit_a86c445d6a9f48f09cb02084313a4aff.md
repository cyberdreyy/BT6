### Title
`taskTerminate` skips console/Ctrl-handler restoration when `AttachConsole` fails after `FreeConsole` succeeds - (File: `helpers/process/killer_windows.go`)

### Summary
In the legacy Windows termination path, `taskTerminate` calls `FreeConsole` and then `AttachConsole(pid)` sequentially, returning immediately on the first error. If `AttachConsole(pid)` fails (e.g. job process already exited or holds its own console), the function returns before ever reaching the "always attempt to restore" recovery block, leaving the runner permanently detached from a console and its Ctrl-C handler state altered.

### Finding Description
`taskTerminate` first runs, under `UseWindowsLegacyProcessStrategy`: [1](#0-0) 
Each of `freeConsole`, `attachConsole`, `setConsoleCtrlHandler` returns early via `if err := ...; err != nil { return err }`. Only after all three succeed does execution reach the comment "always attempt to restore console and Ctrl-C handler for runner process" and the `multierror`-based recovery block: [2](#0-1) 
So the recovery logic (re-`AttachConsole(math.MaxUint32)` and `SetConsoleCtrlHandler` restore) is only reached along the success path of the first three calls — it is never invoked if `attachConsole(pid)` (line 84) itself fails. Since `freeConsole` at line 81 already succeeded and detached the runner from its console before the failing `attachConsole` call, the runner is left with no console attached and no attempt made to reattach it.

The caller, `windowsKiller.Terminate`, only logs a warning and attempts a `ForceKill` — it does not attempt to restore console state itself: [3](#0-2) 

This legacy strategy is only active when `UseWindowsLegacyProcessStrategy` is enabled (a configurable option threaded through `CommandOptions`/`osCmd.Start`): [4](#0-3) 
A job process that exits or detaches its console before `Terminate()`/`taskTerminate` executes `AttachConsole(pid)` can trigger this early-return path with no attacker privilege beyond normal job control over its own process lifetime (the pid being targeted is the job's own process, not an arbitrary third party).

### Impact Explanation
The runner's own process becomes permanently detached from any console after this occurs, since `FreeConsole` already executed and the compensating `AttachConsole(math.MaxUint32)` restore is skipped. Because `taskTerminate` is invoked on every subsequent job termination under the legacy strategy and relies on `AttachConsole`/`GenerateConsoleCtrlEvent` against the *current* console state of the runner, corruphärung of that state by one job can cause termination signaling (`CTRL_C_EVENT`) for unrelated, later jobs run by the same runner process to misbehave — matching the scoped impact of persistent, cross-job disruption of graceful termination.

### Likelihood Explanation
This is fully reachable by an unprivileged pipeline author: any job configured to run with `UseWindowsLegacyProcessStrategy` (a `feature flag`/config option) that terminates or manipulates its console before the runner calls `Terminate()` will cause `AttachConsole(pid)` to fail (`ERROR_INVALID_PARAMETER`/target already exited), which is a very common, easily triggered condition (e.g., `alreadyStopped` scenario already exercised in `killer_integration_test.go` at lines 128-141). No special privileges are needed; a script that exits quickly or calls `FreeConsole`/`AllocConsole` on itself suffices.

### Recommendation
Restructure `taskTerminate` so that the recovery/restore steps (`GenerateConsoleCtrlEvent`, `FreeConsole`, `AttachConsole(math.MaxUint32)`, `SetConsoleCtrlHandler` restore) are executed unconditionally via `defer` (or a similarly guaranteed cleanup path) as soon as `FreeConsole` succeeds, rather than only being reached after the entire success path of `FreeConsole`→`AttachConsole`→`SetConsoleCtrlHandler`. Errors from the initial three calls should be aggregated into the same `multierror` result rather than short-circuiting with an early `return err` that bypasses restoration.

### Proof of Concept
Go integration test (Windows-only, extending `killer_integration_test.go`):
1. Start a test process with `UseWindowsLegacyProcessStrategy: true`.
2. Kill/exit the target process before calling `Terminate()` so that `AttachConsole(pid)` will fail (mirrors the existing `alreadyStopped` test case at lines 128-141 of `killer_integration_test.go`).
3. Call `k.Terminate()`.
4. Assert via `GetConsoleWindow()`/`AttachConsole(windows.ATTACH_PARENT_PROCESS)` (or a subsequent successful `GenerateConsoleCtrlEvent` on a second, unrelated live process) that the runner process still has a valid console attached and that `SetConsoleCtrlHandler` is restored to accept Ctrl-C — expected: currently fails (console remains detached), after fix: passes.

func (pk *windowsKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	if err := taskTerminate(pk.cmd.Process().Pid, pk.cmd.options.UseWindowsLegacyProcessStrategy); err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}
