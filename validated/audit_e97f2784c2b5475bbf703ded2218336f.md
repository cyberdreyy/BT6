### Title
Premature key-reset in `URLSanitizer.Write` lets a Write()-boundary split of the longest token key (`x-amz-security-token`) bypass masking - (File: `common/buildlogger/internal/urlsanitizer/urlsanitizer.go`)

### Summary
`URLSanitizer.Write` resets `s.match` whenever `len(s.match) == cap(s.match)` at the top of its scanning loop [1](#0-0) . Because `cap(s.match)` is sized to exactly `len(longest_key)+1` (the separator plus the longest key, `x-amz-security-token` = 21 chars, so cap = 22) [2](#0-1) , a *fully and correctly* accumulated longest key reaches `len(s.match) == cap(s.match)` exactly at the moment the key is complete but before the terminating `=` has been seen. If the `=` arrives in a subsequent `Write()` call (i.e., the job's output was split across two reads at that exact byte boundary), the very next loop iteration wipes the completed key before it can be looked up in `tokenParamKeys`, and the following `=<value>` is then treated as ordinary bytes and passed through the writer unmasked.

### Finding Description
`New()` sizes `s.match`'s capacity as `max(len(token) for token in tokenParamKeys) + 1` [2](#0-1) . The longest key, `x-amz-security-token`, is exactly `cap-1` characters, so `separator + key` exactly fills the buffer to `cap`.

The single-byte accumulation path (used when the current chunk contains no `=`, `?`, or `&` at all) appends bytes into `s.match` with no bound check [3](#0-2) . If the `Write()` call's buffer ends exactly when the 21st character of `x-amz-security-token` has been consumed (i.e., the outer `for n < len(p)` loop condition fails right after the append), the function returns with `s.match` holding the complete, valid key of length `cap` (22), still un-masked, correctly passed to output as plaintext key bytes.

On the next `Write()` call (carrying the rest of the parameter, starting with `=<secret>`), execution re-enters the loop and immediately performs the check at the top:
```go
if len(s.match) == cap(s.match) {
    s.match = s.match[:0]
}
``` [4](#0-3) 
Since `len(s.match) == cap(s.match) == 22` (the fully-matched, legitimate key), this branch fires and clears the match — even though the key is *not* garbage/overflow, it's a complete and valid `x-amz-security-token` waiting only for `=`. After the reset, `len(s.match)==0`, so the fast-path scan for the next `?`/`&` runs on the new chunk `=<secret>&...` [5](#0-4) . It skips over `=<secret>` (no `?`/`&` there) and treats it as ordinary text, so `s.masking` is never set, and this literal `=<secret>` segment is written verbatim to the trace at the final flush [6](#0-5) .

The existing bail-out check that guards the multi-byte append path (`off+len(s.match) > cap(s.match)`) uses `>` not `>=`, so it does not prevent this exact-boundary case; and critically, that check is irrelevant here because the failure occurs in the *next* `Write()` call, at the very top of the loop, before any of the offset-scanning logic runs at all.

`Write()` is fed job/service output byte-for-byte through the executor's stream/copy paths (e.g. shell executor's process stdout/stderr piped via `s.BuildLogger.Stream(...)` [7](#0-6) , and Docker service log streaming via `stdcopy.StdCopy` into the trace sink [8](#0-7) ). These copy paths do not guarantee line- or token-aligned buffering; an attacker fully controlling job output content and flush timing (e.g., via unbuffered `printf`/`write()` calls at controlled byte counts) can arrange for a chunk boundary to fall exactly after the 21-character `x-amz-security-token` key.

### Impact Explanation
If a job legitimately emits a URL containing `?x-amz-security-token=<AWS_STS_TOKEN>` (e.g. a presigned S3/artifact URL echoed by `curl -v`, `aws` CLI verbose output, or similar), and the attacker forces the write to split exactly after the key name, the STS security token value is written to the CI trace **unmasked** instead of being replaced with `[MASKED]`. This is the scoped impact described: leaking `x-amz-security-token` (or similarly the token value for `private_token`, if a chunk split coincidentally lands the buffered match exactly at `cap` — though `private_token` alone doesn't naturally reach the boundary since it is shorter than `cap`; the concrete, reliably reachable case is the longest key `x-amz-security-token`, which is exactly sized to hit the boundary).

### Likelihood Explanation
- Preconditions: the sensitive URL/token must appear in job-controlled output (fully realistic for jobs interacting with S3-compatible cache/artifact storage or printing verbose HTTP traces).
- The attacker needs the write to split at exactly the byte after the key ends and before `=`. This requires knowledge of/control over the executor's read/copy buffering (achievable by controlling total preceding output length and using unbuffered writes/flushes at specific counts), which is plausible but requires some trial-and-error/timing control, not guaranteed on every executor/transport.
- Reproducible deterministically at the `URLSanitizer.Write` unit level by directly issuing two `Write()` calls with the split at the exact boundary — this proves the bug mechanically, independent of how reliably an attacker can force that split in a live job.

### Recommendation
Do not reset `s.match` purely based on reaching `cap`. Only reset when the match has genuinely overflowed the maximum possible key length while still not having found `=`, i.e., check for overflow *after* appending (as already done at the bail-out check for the multi-byte path) rather than unconditionally at the top of every loop iteration regardless of whether a valid, complete key is sitting in the buffer awaiting `=`. Alternatively, increase `cap(s.match)` by the separator size explicitly and only trigger the reset when strictly greater than the maximum key length + 1, or track a distinct "have I already tried matching against `tokenParamKeys`" state that isn't destroyed by a chunk-boundary side effect at exactly the max key length.

### Proof of Concept
```go
func TestURLSanitizer_ChunkedLongestKeyBypassesMasking(t *testing.T) {
    var out bytes.Buffer
    s := urlsanitizer.New(internal.NewNopCloser(&out))

    // Split exactly after the 21-char key "x-amz-security-token"
    // ("?" + 21 chars == cap == 22 bytes) so the boundary falls
    // right before '='.
    part1 := []byte("?x-amz-security-token") // 22 bytes total incl. '?'
    part2 := []byte("=SUPER-SECRET-STS-TOKEN&next=1")

    _, err := s.Write(part1)
    require.NoError(t, err)
    _, err = s.Write(part2)
    require.NoError(t, err)
    require.NoError(t, s.Close())

    // Bug: token leaks in plaintext instead of being masked.
    assert.NotContains(t, out.String(), "[MASKED]")
    assert.Contains(t, out.String(), "SUPER-SECRET-STS-TOKEN")
}
```
Expected (buggy) result: the assertion `assert.Contains(t, out.String(), "SUPER-SECRET-STS-TOKEN")` passes, proving the secret is emitted verbatim; after the fix, the token should be replaced with `[MASKED]` regardless of the `Write()` call boundary.

func (e *executor) captureContainerLogs(ctx context.Context, cid, containerName string, sink io.WriteCloser) error {

		ShowStderr: true,
		ShowStdout: true,
		Timestamps: true,
		Follow:     true,
	})
	if err != nil {
		return fmt.Errorf("failed to open log stream for container %s: %w", containerName, err)
	}

	e.BuildLogger.Debugln("streaming logs for container " + containerName)
	go func() {
		defer source.Close()
		defer sink.Close()

		// Using stdcopy assumes service containers are run with TTY=false. If
		// containers are started with TTY=true, io.Copy should be used instead.

					"error streaming logs for container %s: %s",
					containerName,
					err.Error(),
				))
			}
		}
		e.BuildLogger.Debugln("stopped streaming logs for container " + containerName)
	}()
	return nil
