## Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing requests to execute below the intended live-member threshold - (File: `multisig2/src/lib.rs`, also applicable to `multisig/src/lib.rs`)

## Summary
`MultiSigContract::delete_member` (and the analogous `DeleteKey` action in the legacy `multisig` contract) only purges outstanding requests that were *originated* by the removed member. It does not scan the `confirmations` map to strip confirmations that the removed member had cast on requests originated by *other* members. Those stale confirmations remain in the `HashSet<String>` and continue to count toward `num_confirmations` in `confirm()`. This lets a request execute using a "confirmation" from an account/key that is no longer a multisig member at the time of execution, breaking the "confirmations counted == live members" invariant the multisig's security model relies on.

## Finding Description
Confirmations are stored per request in a `LookupMap<RequestId, HashSet<String>>` keyed by the confirming member's stringified identity: [1](#0-0) 

When a request accumulates `num_confirmations` entries it is executed, purely based on `confirmations.len()`: [2](#0-1) 

`delete_member` is responsible for cleaning multisig state when a member is removed, but it only removes requests where the removed member was the *originator* (`r.member == member`); it never touches the `confirmations` set of requests originated by *other* members that the removed member had already confirmed: [3](#0-2) 

`assert_valid_request` (called from `confirm`) only checks that the *caller* is currently a member; it never re-validates that the confirmations already stored for the request belong to accounts/keys that are still members: [4](#0-3) 

As a result, once a member's confirmation is recorded on a pending request they did not originate, that confirmation is permanent and is never invalidated even after the member is removed via `DeleteMember`. The identical pattern exists in the legacy single-tier `multisig` contract, where `DeleteKey` only purges requests signed by the deleted key: [5](#0-4) 

## Impact Explanation
The multisig's entire security guarantee is "K confirmations from K distinct *current* members are required to execute any request." This bug lets a request execute with fewer than K confirmations from members who are actually current/live at execution time — a removed member's (e.g., one whose key was compromised and revoked) stale confirmation still counts. This is a multisig request executed below the effective threshold of genuinely authorized signers, which is explicitly listed as a Critical-severity outcome (funds/actions authorized without genuine threshold approval).

## Likelihood Explanation
This requires no attacker-controlled deployment or foundation privilege beyond the multisig's normal legitimate operation: any member who confirms a pending request and is later removed (a routine key-rotation/compromise-response action) leaves a dangling confirmation. Any subsequent confirmations by the remaining live members can push the stale-inflated count over the threshold, executing the request (e.g. a `Transfer` action) with genuinely fewer live-member confirmations than `num_confirmations` requires. This is a realistic, low-effort scenario — it does not require a malicious validator, foundation action, or redeploy; it only requires the ordinary member-removal workflow the contract itself exposes.

## Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all outstanding requests' `confirmations` sets (not just the requests they originated) and remove the departing member's entry from each. Alternatively, validate at `confirm()`/execution time that every entry in the request's confirmation set still corresponds to a current member, discarding stale entries before comparing against `num_confirmations`.

## Proof of Concept
1. Deploy `multisig2` with members `A, B, C` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R)` for a `Transfer` action — confirmations(R) = `{A}`.
3. `C` calls `confirm(R)` — confirmations(R) = `{A, C}` (2/3, not yet executed).
4. The team detects `C`'s key is compromised and removes `C` via a properly-confirmed `DeleteMember { member: C }` request. `delete_member` only purges requests where `r.member == C` (i.e., requests C *originated*); `R` was originated by `A`, so it is untouched — confirmations(R) still contains stale entry `C`, even though `C` is no longer in `self.members`.
5. `B` (the only other genuinely live member besides `A`) calls `confirm(R)` — confirmations(R) = `{A, C, B}`, `len() == 3 >= num_confirmations(3)`, so `R` executes and the `Transfer` is sent — despite there being only 2 live members' worth of genuine authorization (`A`, `B`) at execution time, one short of the configured 3-of-3 threshold.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
