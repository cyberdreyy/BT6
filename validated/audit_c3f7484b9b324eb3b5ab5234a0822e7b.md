### Title
Local staleness clock instead of live node verification lets a signer sign a block that conflicts with a still-canonical signed sibling - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit` (and its equivalent re-check on `handle_block_validate_ok`) decides whether a fresh conflicting signature blocks a new signature using a local, timer-based "freshness" cutoff (`freshness_cutoff = now - tenure_last_block_proposal_timeout`) rather than always re-querying the node for ground truth. Once a previously-signed conflicting block's `last_endorsed` timestamp falls behind this local cutoff, it is treated as "stale" and is excluded from the conflict search entirely — for conflicts in a *different* tenure, the code goes straight to signing the new, conflicting block, without ever asking the node whether the older signed block's tenure/sortition is still canonical and could still land. This mirrors the reported oracle bug class: trusting a local, fixed-tolerance timeout as ground truth for "is this state still live?" instead of confirming against the authoritative source, with a consequence of an incorrect financial/consensus decision (here, an equivocating signature) rather than a simple loss of funds.

### Finding Description
`store_and_process_block_pre_commit`'s conflict-resolution logic in `stacks-signer/src/v0/signer.rs` works as follows [1](#0-0) :

1. It fetches all signed conflicts at or above the block's height, in *any* tenure, via `get_signed_conflicts`.
2. It computes `freshness_cutoff = get_epoch_time_secs() - tenure_last_block_proposal_timeout`.
3. It only treats a conflict as blocking if `conflict.last_endorsed > freshness_cutoff` **and** `reorg_permit_stands` is false **and** `conflict_still_blocks` (a node query) returns true.
4. If no conflict passes all three conditions — in particular, if every fresh-enough conflict has already been excluded because its `last_endorsed` predates the cutoff — the code falls through to a *second*, narrower check that only re-verifies the node's canonical tip when the conflict is in the **same tenure** as the new block [2](#0-1) . Conflicts in **other** tenures that are merely "stale" by the local clock are never re-verified against the node at all, and the signer proceeds straight to `mark_locally_accepted` / signs the new block [3](#0-2) .

`tenure_last_block_proposal_timeout` is a purely local, wall-clock-based tolerance (analogous to the oracle's heartbeat/deviation window): it does not track the real state of block propagation, sibling proposals in flight, or slow network delivery. The design's own documentation acknowledges this is a deliberate trust boundary — "a stale conflict in another tenure in particular no longer speaks for us" [4](#0-3)  — but that trust is placed in a fixed local timer rather than in the node's live chain state, exactly the failure mode the oracle report flags (trusting a stale/loosely-bounded local proxy for ground truth instead of the authoritative source).

Compare this to `get_tenure_last_block_info`, which uses the *same* timeout (`tenure_last_block_proposal_timeout`) to decide whether the tenure's last signed block still counts, and explicitly falls back to asking the node for the canonical tip once that local timer expires [5](#0-4) . The pre-commit conflict path at lines 1422-1457, however, only re-asks the node when the conflict shares the *same* consensus hash / tenure as the candidate block; a stale conflict belonging to a genuinely different, still-canonical tenure at the same or higher height is dropped from consideration with no node lookup whatsoever.

### Impact Explanation
If a signer's local clock crosses `tenure_last_block_proposal_timeout` for a conflicting signature it placed on a sibling block in another tenure — while that sibling's tenure sortition is, in fact, still canonical and the block could still be relayed/adopted by the node — the signer will place a fresh signature on a *second*, conflicting block at the same or higher height without any live verification. This is a direct instance of the Critical impact class defined by the rules: a signer producing a signature over a conflicting block relative to one it already signed. Because block signatures are the basis for chain finality, an equivocating signature from even a modest fraction of the signer set can contribute to a fork/conflicting-block scenario, undermining the one-signature-per-height guarantee the pre-commit conflict check exists to enforce.

### Likelihood Explanation
This requires no majority collusion, no other signer's key, and no StackerDB/transport tampering — it only requires ordinary timing conditions that are entirely plausible in production: a delayed/slow tenure-tip propagation, a signer that was briefly disconnected from its node, or a sibling-proposal race (of the kind already tested in `run_sibling_scenario` in `stacks-signer/src/v0/tests.rs`) that happens to straddle the `tenure_last_block_proposal_timeout` boundary. The codebase's own test suite already probes exactly this timing boundary (`tenure_last_block_proposal_timeout` interacting with sibling races) [6](#0-5) , showing the boundary is a recognized, reachable condition rather than a purely theoretical corner case. A single miner (one slot) plus normal network jitter/delay in propagating a competing tenure-start block is sufficient to trigger it; it is triggerable by ordinary tenure-boundary/miner-restart activity, not by malicious majority action.

### Recommendation
For conflicts that fall outside the local freshness window, do not simply drop them from consideration when they belong to a different tenure. Instead, always fall back to a node query (equivalent to `conflict_still_blocks`) before allowing the second, conflicting block to be signed — mirroring the pattern already used in `get_tenure_last_block_info`, where the local timeout is only used to *decide when to ask the node*, never as a substitute for asking it. In other words, treat `tenure_last_block_proposal_timeout` purely as a cache-invalidation hint rather than as authoritative evidence that a signed conflicting block can no longer become canonical.

### Proof of Concept
1. Signer S signs block A (tenure T1, height h) and records `last_endorsed = t0` for A via `add_block_signature`/pre-commit bookkeeping used by `get_signed_conflicts`.
2. Due to normal network delay, the node has not yet finalized T1/A, and T1's sortition remains canonical.
3. Time passes beyond `tenure_last_block_proposal_timeout` (a config value, e.g. tens of seconds) without S receiving confirmation that A is globally accepted or superseded.
4. Miner (or a re-proposal) submits block B in a different tenure T2, also at height h (or higher), reaching the pre-commit threshold.
5. `store_and_process_block_pre_commit` calls `get_signed_conflicts(h, hash_B)`, which returns A as a conflict, but `A.last_endorsed <= freshness_cutoff`, so the first `find` at lines 1403-1411 excludes it [7](#0-6) .
6. Because A's `consensus_hash` (T1) differs from B's `consensus_hash` (T2), the same-tenure re-check at lines 1432-1457 also does not apply to A.
7. No node query is ever made about T1's/A's continued canonicity; S proceeds to `mark_locally_accepted` and signs B [3](#0-2) .
8. If T1/A subsequently is (or becomes) processed by the node as canonical — which the "stale" local timer never verified — S has now placed valid signatures over two conflicting blocks at the same height, in different tenures, breaking the pre-commit conflict guard's core safety property.

    /// Get the last signed block from the given tenure if it has not timed out.
    /// Even globally accepted blocks are allowed to be timed out, as that
    /// triggers the signer to consult the Stacks node for the latest globally
    /// accepted block. This is needed to handle Bitcoin reorgs correctly.
    ///
    /// The timeout window is measured from the last time a signature actually covered the
    /// block: our own (`signed_self`) or the observed group/global acceptance
    /// (`signed_group`), whichever is later, matching how `get_signed_conflicts` measures
    /// endorsement freshness. `approved_time` is deliberately not used: it is stamped at
    /// pre-commit, which carries no signature, so it would close the window early. This also
    /// means a globally accepted block we never signed ourselves gets a full window from the
    /// time its acceptance was observed, rather than timing out instantly for lack of a
    /// timestamp.
    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
    }
