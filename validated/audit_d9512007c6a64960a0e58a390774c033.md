### Title
Defaulted instant-withdraw receipts keyed to a stale epoch escape the recovery haircut and are paid at par (or frozen) — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` records a user's receipt under the *current* `epochNumber` (`instantWithdrawsRequestsByEpoch[user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`), but `finalizeDefaultRecovery` and `_claimDefaultedInstantWithdrawRequest` look those mappings up under `defaultRecoveryEpoch = epochNumber` *at finalization time*. If the epoch counter advances between the instant request and default finalization — which the code itself allows, since `pendingInstantWithdraws` can remain non-zero after an epoch boundary ("startEpoch moved the CDO's available cash to the strategy but that cash covered only part of the instant queue") — the receipt is invisible to the recovery path and falls through to `claimInstantWithdrawRequest`, where it is burned and paid 1:1 via `_transferFundedClaim`. This is the same bug class as the Lighthouse CGC fix: a map keyed by an assumed "current" value is written/read without checking that the value still matches the state the writer expected.

### Finding Description
In `requestInstantWithdraw` (lines 356-375), the receipt is indexed by the epoch at request time. In `finalizeDefaultRecovery` (lines 661-710), `defaultRecoveryEpoch = epochNumber` and `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *finalization* epoch — only when `pendingInstantWithdraws != 0`. In `claimInstantWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` (lines 380-393, 842-856), the defaulted-epoch lookup `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` returns 0 for a receipt recorded under the prior epoch, so `claimBasis == 0` and execution continues to burn the full `instantWithdrawsRequests[user]` and pay it through `_transferFundedClaim` at par. `epochNumber` is bumped inside `deposit()` whenever `isEpochRunning()` (lines 607-611), i.e., during `stopEpoch` settlement, so any instant request made in epoch N is keyed under N while a default finalized in epoch N+1 searches key N+1. No guard compares the request epoch to the finalization epoch — the missing equivalent of the "expected cgc == current cgc" check.

Two broken outcomes follow: (a) if the strategy holds non-reserve underlying (partially prefunded instant cash, new buffer-period deposits, recovery dust), the stale-keyed receipt is paid 1:1 instead of `defaultRecoveryPrice`, stealing funds that belong to active LPs/recovery claimants; (b) if it does not, `_transferFundedClaim` reverts and the receipt is permanently unclaimable while `pendingInstantWithdraws` stays inflated forever, permanently freezing the user's claim and skewing `defaultPendingClaimBasis`.

### Impact Explanation
An unprivileged tranche holder who requested an instant withdrawal in epoch N can, after a default finalized in epoch N+1, claim the receipt at full face value while every other claimant takes the `defaultRecoveryPrice` haircut — direct theft/dilution of the non-reserve balance — or, where no such balance exists, suffer permanent freezing of the receipt. The solvency and "one receipt, one haircut" invariants are broken because the recovery basis silently omits the stale-keyed claim.

### Likelihood Explanation
Requires instant withdrawals to be enabled, an instant request that remains at least partially unfunded across an epoch boundary, and a borrower default in a later epoch. Partial funding is an explicitly supported state per the `_defaultPrefundedInstantReserve` comments (lines 636-640, 714-723), and borrower default is a designed-for flow. The attacker needs only to be a normal withdraw requester; sequencing depends on honest manager/borrower actions, so likelihood is conditional but not attacker-controlled.

### Recommendation
Key default-epoch instant claims by the *request* epoch, not the finalization epoch: e.g., track `instantWithdrawRequestEpoch[user]` (or iterate `instantWithdrawsRequestsByEpoch` over all epochs with unfunded `pendingInstantWithdraws`), include all unfunded instant claims in `defaultPendingClaimBasis`, and have `_claimDefaultedInstantWithdrawRequest` clear the receipt under its recorded epoch — mirroring the upstream fix of passing the expected epoch/state into the update rather than assuming it is unchanged.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVaultStaleInstantEpoch.t.sol
function test_staleEpochInstantReceiptEscapesHaircut() external {
    // epoch N running, instant withdraws enabled
    _depositWithUser(attacker, 100e6);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(amountAttacker, address(AAtranche));
    // strategy: instantWithdrawsRequestsByEpoch[attacker][N] = amount

    // stopEpoch N: borrower partially funds instant claims -> pendingInstantWithdraws > 0
    // epochNumber bumps to N+1 inside deposit() during stopEpoch
    _stopCurrentEpochPartialInstantFunding();

    // borrower defaults during epoch N+1; owner finalizes recovery
    _handleBorrowerDefaultAndFinalize(); // defaultRecoveryEpoch = N+1

    // attacker claim: lookup at epoch N+1 returns 0 -> falls through to
    // claimInstantWithdrawRequest, burns full receipt, _transferFundedClaim pays 1:1
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, amountAttacker); // par, not haircut
    // assertGt(paid, amountAttacker * defaultRecoveryPrice / RECOVERY_FULL);
}
```

Note: the exact ordering of `epochNumber` increment versus instant-claim funding inside `IdleCDOEpochVariant.stopEpoch`/`startEpoch` was not fully traced (the CDO-side code paths were not inspected in this pass); the PoC hinges on `pendingInstantWithdraws > 0` surviving an `epochNumber` bump, which the contract's own comments indicate is a supported state.
