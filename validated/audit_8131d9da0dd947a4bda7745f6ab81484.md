### Title
Inconsistent floor vs. ceiling rounding when deriving legacy `commission` percent from `commission_bps` causes misreported vote‑account data over unprivileged RPC/account-decoding paths - (File: `vote/src/vote_state_view/field_frames.rs`)

### Summary
Similar to the Sherlock M-1 report (division ordering causing avoidable precision loss/incorrect rounding), Agave has two different implementations that convert a vote account's `commission_bps` (basis points) into the legacy 0–100 `commission` percentage, and they round in opposite directions. One path floors, the other explicitly rounds up. Both values reach unprivileged JSON-RPC/account-decoding consumers, so the same underlying on-chain vote account can be reported with two different `commission` percentages depending on which code path served the request.

### Finding Description
`CommissionView::commission_percent()` — the zero-copy vote-account decoder used by `VoteStateView::commission()` — truncates (floors) when the account stores basis points: [1](#0-0) 

This `commission()` accessor is the general-purpose, RPC-reachable decoder for vote accounts. It is used, for example, in `get_vote_accounts` when the `commission_rate_in_basis_points` feature is *not* active, and to reconstruct basis points from the legacy percent (`vote_state.commission() as u16 * 100`) inside epoch-reward commission handling: [2](#0-1) [3](#0-2) 

By contrast, when the feature *is* active, `get_vote_accounts` derives the percent from bps using an explicit, intentionally different rounding rule — ceiling, not floor — with a comment showing this discrepancy was already recognized as an issue that needed a deliberate fix in this one call site: [4](#0-3) 

So the same `commission_bps` value (e.g. `250` bps = 2.5%) is reported as `2` via the floor-based `VoteStateView::commission()` path but as `3` via the ceiling-based inline conversion in `get_vote_accounts`. Both values are reachable by any unprivileged caller: `VoteStateView::commission()` backs generic vote-account decoding used by `account-decoder`'s jsonParsed vote encoding (`getAccountInfo`/`getProgramAccounts`) as well as `get_inflation_reward`'s legacy `commission` field, while the ceiling-based value is what `getVoteAccounts` itself returns for the same feature-active account.

### Impact Explanation
This falls under "wrong account data returned" for a single, unprivileged RPC/account-decode call: querying the same vote account's commission through different but equally public RPC surfaces (`getVoteAccounts` vs. `getAccountInfo`/`getProgramAccounts` jsonParsed vote decoding, or vs. `getInflationReward`'s `commission` field) yields inconsistent, silently-truncated percentages. This can mislead delegators/stakers comparing commission rates across endpoints, and downstream tooling that trusts the decoded `commission()` value (e.g. reward/commission accounting inside `redeem_delegation_rewards`) computes with a rounded-down commission that does not round-trip losslessly back to the authoritative `commission_bps`.

### Likelihood Explanation
Any validator that has activated `commission_rate_in_basis_points` (SIMD-0291) and sets a commission whose basis points are not an exact multiple of 100 (e.g. 2.5%, 12.34%) will trigger this discrepancy on every subsequent read via the two differing code paths. No special privileges, multiple round trips, or unusual conditions are required — a single `getAccountInfo`/`getProgramAccounts` call versus a single `getVoteAccounts` call is sufficient to observe conflicting values.

### Recommendation
Make `VoteStateView::commission()` / `CommissionView::commission_percent()` use the same `div_ceil(100)` (or otherwise identical, explicitly documented) rounding rule that `rpc/src/rpc.rs::get_vote_accounts` already uses, so that every consumer (account-decoder jsonParsed vote decoding, `get_inflation_reward`, epoch-reward commission handling, and `get_vote_accounts`) derives an identical, round-trip-consistent percent from `commission_bps`.

### Proof of Concept
1. Activate `commission_rate_in_basis_points` for a vote account and set `inflation_rewards_commission_bps = 250` (2.5%).
2. Call `getVoteAccounts` — per `rpc/src/rpc.rs` lines 1206-1209, `commission = 250.div_ceil(100) = 3`.
3. Call `getAccountInfo`/`getProgramAccounts` with `jsonParsed` encoding (or any other code path invoking `VoteStateView::commission()`, e.g. `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` line 716-718's fallback branch) — per `vote/src/vote_state_view/field_frames.rs` lines 320-330, `commission = 250 / 100 = 2`.
4. The two unprivileged, read-only RPC responses disagree (`3` vs `2`) for the identical on-chain state, demonstrating the misreporting.

```rust
impl CommissionView<'_> {
    pub(super) fn commission_percent(&self) -> u8 {
        if !self.frame.use_bps {
            self.buffer[0]
        } else {
            let data = unsafe { *(self.buffer.as_ptr() as *const [u8; 2]) };
            let bps = u16::from_le_bytes(data);
            let percent = (bps / 100).min(u8::MAX as u16);
            percent as u8
        }
    }
```
