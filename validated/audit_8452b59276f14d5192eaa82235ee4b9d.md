This confirms the design: the deterministic account ID is `keccak256`-derived from the **entire** `DeterministicAccountStateInit` (code + all data key/values), and this derivation is enforced at validation time. [1](#0-0) [2](#0-1) 

That means the scenario in the question is not exploitable as described:

1. **No address collision is possible.** The receiver account id (`0s...`) is validated to equal `derive_near_deterministic_account_id(&action.state_init)`; any change to `data` (e.g. injecting an attacker-chosen `owner` key) produces a completely different account id via keccak256 preimage resistance. So an attacker who sets a different `owner` value does not "hijack" any specific pre-existing or third-party-intended account — they simply create a brand-new, distinct account address that only they (and anyone else computing the same preimage) know about. [3](#0-2) 

2. **`set_deterministic_state_init_data_entry`/`append_deterministic_state_init` only mutate the outgoing receipt the caller itself is constructing**, before it is sent and validated; there's no shared/global state being altered on behalf of a third party. [4](#0-3) 

3. At apply time, `action_deterministic_state_init` / `deploy_deterministic_account` write the `code` (via `use_global_contract`, which just resolves the `GlobalContractIdentifier` to whatever contract is deployed there — a legitimate, existing global contract) and the literal `data` map into the new account's storage, with no re-entry into any "constructor" logic of the global contract. [5](#0-4) 
This is by design (documented in NEP-616 / `docs/DataStructures/Account.md`): the account is fully "content-addressed" — its identity *is* a commitment to its initial state, analogous to Ethereum's `CREATE2`. [6](#0-5) 

4. The `sharded-contract` test contract explicitly demonstrates the intended owner pattern: it constructs its own state-init with `OWNER_KEY -> caller`-chosen bytes and derives its own account id from that — i.e. whoever wants to become "owner" of a specific deterministic account must include that data in the very state-init whose hash becomes the account id; they cannot retroactively inject a different owner into someone else's already-derived account address. [7](#0-6) 

5. Repeated/idempotent init is also handled safely: once an account/contract exists (`account.contract().is_none()` is false), `deploy_deterministic_account` is skipped entirely and only the deposit is refunded — so a second `DeterministicStateInitAction` sent by an attacker against an *already-initialized* address cannot overwrite existing data. [8](#0-7) 

There's no reachable path where an attacker's `DeterministicStateInitAction` + `set_deterministic_state_init_data_entry` calls result in a *third party's intended* deterministic account (i.e., one whose address the third party has already derived and expects to control with their own `owner` data) ending up controlled by the attacker instead. The "resolution" of `GlobalContractIdentifier` only selects which global *contract code* to attach — it does not import or inherit any "authorized" storage state from that contract or from any other account; the receiver address itself is cryptographically bound to the exact data the attacker chose, so the attacker only ever controls the (new) address matching their own chosen data, never an address belonging to someone else's differently-parameterized state-init.

pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

fn deploy_deterministic_account(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    state_init: &DeterministicAccountStateInit,
    result: &mut ActionResult,
    storage_usage_config: &StorageUsageConfig,
) -> Result<(), RuntimeError> {
    // Step 1: set contract code (includes storage usage accounting)
    use_global_contract(state_update, account_id, account, state_init.code(), result)?;
    if result.result.is_err() {
        return Ok(());
    }

    // Step 2: insert provided key-value pairs
    let mut required_storage_usage = account.storage_usage();
    for (key, value) in state_init.data() {
        let trie_key = TrieKey::ContractData { account_id: account_id.clone(), key: key.to_vec() };

        let value_bytes = value.len() as u64;
        let key_bytes = key.len() as u64;
        let extra_per_record_bytes = storage_usage_config.num_extra_bytes_record;

        let new_bytes = value_bytes
            .checked_add(key_bytes)
            .and_then(|acc| acc.checked_add(extra_per_record_bytes))
            .ok_or(IntegerOverflowError {})?;
        state_update.set(trie_key, value.clone());
        required_storage_usage =
            required_storage_usage.checked_add(new_bytes).ok_or(IntegerOverflowError {})?;
    }
    account.set_storage_usage(required_storage_usage);

### Deterministic account ID

The account ID is derived from a `DeterministicAccountStateInit` instance.

To derive the deterministic account id, borsh-encode the `DeterministicAccountStateInit` enum instance into raw
bytes. Then use the following formula: `'0s' + keccak256(bytes)[12:32].hex()`.

### Deterministic account creation

Deterministic accounts cannot be created with a `CreateAccount` nor with a `Transfer` action.
A special action, `DeterministicStateInitAction`, is required.
This action validates that the account id matches its initial state.

As with all account types, you have to attach a large enough deposit to cover for the account storage. If the code and
initial state is small enough to fit below the zero-balance limit, no balance is required. The
`DeterministicStateInitAction` has a field to include a balance specifically to cover storage. Anything above the
required amount to cover storage requirements is refunded.

A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable,
however, until the `DeterministicStateInitAction` is also executed.

After successful initialization, the account will have all key-value pairs in `data: BTreeMap<Vec<u8>, Vec<u8>>` in its
contract storage. The contract code will be set to that of the global contract defined with
`code: GlobalContractIdentifier`.

unsafe fn sharded_contract_id() -> GlobalContractIdentifier {
    match current_contract_code(REG_A) {
        0 => panic("contract can't be None"),
        1 => panic("contract mustn't be Local"),
        2 => {
            let code_hash = register_to_memory(REG_A);
            GlobalContractIdentifier::CodeHash(
                CryptoHash::try_from_slice(&code_hash).unwrap_or_else(|e| panic(&e.to_string())),
            )
        }
        3 => {
            let account_id_bytes = register_to_memory(REG_A);
            let account_id_string = bytes_to_string(account_id_bytes);
            let account_id: AccountId = account_id_string
                .parse()
                .unwrap_or_else(|e: ParseAccountError| panic(&e.to_string()));
            GlobalContractIdentifier::AccountId(account_id)
        }
        _ => panic("unknown contract type"),
    }
}

unsafe fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> String {
    let data = borsh::to_vec(&state_init).expect("borsh must not fail");
    keccak256(data.len() as u64, data.as_ptr() as u64, REG_A);
    let hash = register_to_memory(REG_A);

    let hex_string: String = hash[12..32].iter().map(|b| format!("{:02x}", b)).collect();
    format!("0s{hex_string}")
}
