### Title
Symlink target (`hdr.Linkname`) is never validated against `e.dir`, allowing tar+zstd cache/artifact extraction to create symlinks pointing outside the extraction root - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
`extractor.Extract` validates that the tar entry's own path (`hdr.Name`) stays inside `e.dir` via a `strings.HasPrefix` check, but for symlink entries it never validates `hdr.Linkname` (the symlink target) before calling `os.Symlink(hdr.Linkname, path)`. An attacker-controlled `.tar.zst` cache/artifact can therefore create a symlink that is located inside `e.dir` but points to an arbitrary absolute path or a `../`-escaping relative path outside `e.dir`.

### Finding Description
In `Extract`, each entry's containment check only validates the destination path of the entry itself: [1](#0-0) 
For symlink entries, the header is deferred and later realized with the raw, unchecked `hdr.Linkname`: [2](#0-1) [3](#0-2) 
`hdr.Linkname` comes directly from the attacker-supplied tar stream and is passed unmodified to `os.Symlink`. The `HasPrefix` guard only constrains where the symlink *file itself* is written (`path`), not what it points to. This is reachable via `CacheExtractorCommand.Execute`, which opens the archive and calls `extractor.Extract(context.Background())` directly on job/cache-controlled input: [4](#0-3) 
A job can supply a cache archive containing a tar entry of type symlink with `Linkname` set to an absolute path (e.g. `/etc/something`) or a relative traversal (e.g. `../../outside`). The name-prefix check passes because it only inspects the symlink's own location, and the symlink is created pointing wherever the attacker wants.

Note the same missing-target-validation pattern exists in the legacy zip extractor's `extractZipSymlinkEntry`, which also calls `os.Symlink(string(data), file.Name)` without checking the target: [5](#0-4) . This confirms the gap is a real, unaddressed pattern rather than something already mitigated elsewhere in the codebase.

### Impact Explanation
A crafted cache/artifact tarball creates a dangling (or live) symlink inside the extraction root that resolves outside of it. Any subsequent write performed by the job or Runner-side tooling that writes "through" this symlink path (assuming it is confined to the cache/build root) will actually write to the symlink's target location outside `e.dir`, violating the "file operations must stay within intended build/cache/artifact roots" invariant. This is a classic tar symlink-extraction escape, scoped to creation of a symlink escaping the root that a later write can exploit — exactly the scoped impact in the question.

### Likelihood Explanation
Fully reachable by an unprivileged pipeline author: caches/artifacts are user-controlled content packaged and later restored via `cache-extractor`/`gitlab-runner cache-extractor`, which calls straight into `tarzstd.extractor.Extract` with no additional sanitization of `Linkname`. No special privileges are required beyond controlling job cache contents (e.g., via `cache:paths` combined with a custom-built cache archive, or a manipulated download in a MITM/self-hosted cache scenario is not even required — the job itself can populate its own cache before a later job/stage downloads and extracts it).

### Recommendation
Validate `hdr.Linkname` the same way `hdr.Name` is validated: resolve `filepath.Join(e.dir, hdr.Linkname)` (or, for absolute-looking `Linkname`, resolve relative to `filepath.Dir(path)`) via `filepath.Abs`, and reject the entry if the resolved target does not have `e.dir` as a prefix (or is not equal to it), mirroring the existing check at lines 62-64 before calling `os.Symlink`.

### Proof of Concept
Go unit test in the `tarzstd` package:
1. Build a `.tar.zst` stream containing a single entry: `Typeflag: tar.TypeSymlink`, `Name: "evil"`, `Linkname: "../../../../etc/passwd"` (or an OS absolute path).
2. Call `NewExtractor(reader, size, tmpDir)` then `Extract(ctx)`.
3. Assert `Extract` returns an error (expected fix behavior) OR, against current code, assert it succeeds and `os.Lstat(filepath.Join(tmpDir, "evil"))` shows a symlink whose target (`os.Readlink`) resolves outside `tmpDir` — proving the escape currently occurs unchecked.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
