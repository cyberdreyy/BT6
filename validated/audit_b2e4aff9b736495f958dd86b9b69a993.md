## Title
Signer treats unreachable-node failure as absence-of-conflict proof, allowing a chainstate confirmation check to fail-open - (`stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` is the shared chainstate check used at proposal time, at validate-ok time, and again at the pre-commit-threshold signing moment to decide whether a proposed/pre-committed block actually confirms the expected tip of a tenure. When the local signer has no cached signed/pre-committed block for that tenure, it falls back to asking the Stacks node for the tenure tip via `client.get_tenure_tip(tenure_id)`. If that RPC call fails for any reason (timeout, connectivity blip, node restart), the function does not reject or hold — it returns `Ok(true)`, i.e. it treats the *absence* of proof about the tenure's real tip as proof that the proposed block is higher than it. This is structurally the same bug class as the IBC "forged absence proof" pattern: an inability to prove non-existence/absence of a higher canonical block is silently converted into an affirmative "no conflict" result, rather than being rejected or held pending confirmation.

### Finding Description
`check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs` first checks the local `SignerDb` for a `last_signed_block`/`last_accepted_block` in the tenure via `get_tenure_last_block_info` and `get_last_accepted_block`. Only if none of the locally known state vetoes the proposal does it fall through to query the Stacks node: [1](#0-0) 

```rust
let tip = match client.get_tenure_tip(tenure_id) {
    Ok(tip) => tip.anchored_header,
    Err(e) => {
        warn!(
            "Failed to fetch the tenure tip for the parent tenure: {e:?}. Assuming proposal is higher than the parent tenure for now.";
            ...
        );
        return Ok(true);
    }
};
```

On any client error — not just a "not found," but any RPC failure, including transient timeouts — the function unconditionally returns `Ok(true)`: "the proposal confirms enough of the tenure." This same helper backs `confirms_latest_block_in_same_tenure` and `check_tenure_change_confirms_parent`, which in turn are invoked from `check_block_against_signer_db_state` at three points in the signer's lifecycle:
- proposal-time validation (`check_proposal`)
- post-validate-ok recheck (`handle_block_validate_response` → `handle_block_validate_ok`)
- at the pre-commit-threshold signing moment, immediately before the signer places a durable, network-broadcast signature (`handle_block_pre_commit`) [2](#0-1) 

Because the check is re-run right before signing specifically to catch state that changed "between validation and threshold," a transient node RPC failure occurring at exactly that recheck converts what should be a "hold/refuse for now" outcome into an affirmative pass, and the signer proceeds to sign.

### Impact Explanation
This breaks the "validated vs. verified-still-consistent" equality the recheck exists to guarantee. The whole design intent documented in `docs/signer-flows.md` (section 7) is that `check_latest_block_in_tenure` is the authoritative re-verification gate protecting a signature from being placed over a tenure-change/continuation block that does not actually confirm the real chain tip. Converting "I could not ask the node" into "the answer is yes" means a transient node outage (or an attacker-influenced timing window that makes a legitimate RPC call fail, e.g., load, restart, or network partition around the miner's proposal window) removes this gate entirely at the exact re-check point designed to catch it. This can let the signer place a signature on a block/tenure-change that does not correctly confirm the parent/own tenure's actual highest block — a non-canonical continuation getting a valid signer signature, which maps to this exercise's "Critical" bucket: a signer signing a non-canonical/invalid block.

However, this is mitigated by the fact that the actual node-side `postblock_proposal.rs::validate` independently re-derives and enforces `check_block_has_valid_parent`/`check_block_has_valid_tenure` against the node's own chainstate before any block is accepted into the chain — the comment at line 454 in `chainstate/mod.rs` explicitly acknowledges this ("we are relying on the stacks-node proposal endpoint to do the validation"). That backstop only fires at the initial validate step, though, not at the pre-commit-threshold recheck, where `check_block_against_signer_db_state` is the only chainstate check exercised again before signing — so the mitigating backstop does not cover this second call site.

### Likelihood Explanation
Any signer whose stacks-node RPC endpoint experiences a transient failure or timeout exactly during the pre-commit-threshold recheck window will silently fail open. This requires only a one-off connectivity hiccup at the right moment — no majority of signers, no key compromise, and no crafted message beyond a normally timed proposal/pre-commit sequence — making it plausible under ordinary operational conditions (node restarts, RPC congestion) rather than requiring an unusual attacker capability.

### Recommendation
Do not treat an `Err` from `client.get_tenure_tip` as an affirmative "proposal is higher" answer at the pre-commit-threshold recheck call site. Instead, distinguish "node unreachable" from "no such tenure/tip" and, at minimum, refuse to sign (treat as inconclusive/hold) when the check is being run as the pre-signature gate, reserving the "assume higher" fallback only for the pre-validation-submission call site where the node's own `postblock_proposal` validation is guaranteed to run afterward as a backstop.

### Proof of Concept
Not independently reproduced with a live cluster in this analysis; the finding is derived from static code inspection of `check_latest_block_in_tenure`'s error-handling branch and its call graph into the pre-commit signing path. A concrete PoC would require injecting an RPC failure from `StacksClient::get_tenure_tip` at the moment `handle_block_pre_commit` re-runs `check_block_against_signer_db_state` (e.g. via the `fault_injection` hooks already present in this codebase, such as those used in `postblock_proposal.rs`) to confirm the signer proceeds to sign despite the failed backstop query. This gap in direct empirical verification should be noted: I was not able to execute the signer's test suite in this session, so likelihood/impact are assessed from control-flow analysis alone.
