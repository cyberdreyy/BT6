### Title
JWT Replay-Protection Race Condition (TOCTOU) Allows Same JWT to Authorize Multiple Workflow Executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` checks whether a JWT's `jti` has already been used, and only *after* the full authorization chain succeeds does it record that `jti` as used. The check (`isReplay`) and the write (`recordUsage`) are two separate, independently-locked operations rather than one atomic check-and-set, creating a classic check-then-act race. This is the same bug *class* as the reported CVE-2017-6074 (an unsynchronized check/release of a supposedly single-use resource), adapted to Go/HTTP semantics: instead of memory being freed twice, a single-use JWT authorization token can be "used" twice.

### Finding Description
`Authorize` is invoked on every inbound HTTP trigger request (an unprivileged, internet-facing gateway path): [1](#0-0) 

The sequence is:
1. `h.jwtCache.isReplay(claims.ID)` takes an `RLock`, checks the map, and releases the lock.
2. Signer/authorized-key validation occurs.
3. `h.jwtCache.recordUsage(claims.ID)` takes a `Lock`, writes the map, and releases the lock. [2](#0-1) 

Because steps 1 and 3 are not performed under a single held lock (and are separated by the entire authorization body), two concurrent requests carrying the identical JWT (same `jti`, same signature) can both call `isReplay` and both observe "not yet used" before either calls `recordUsage`. Both then pass authorization and both proceed to trigger the workflow via `HandleUserTriggerRequest`, which forwards to the DON via `SendToNode`. The unit test at `http_trigger_handler_test.go:357-394` only demonstrates the *sequential* case (second request fails after the first completes) and does not cover concurrent/simultaneous submission, so the race is untested. [3](#0-2) 

### Impact Explanation
A single valid, signed JWT is meant to authorize exactly one workflow execution (enforced by the replay cache). Due to the TOCTOU window between `isReplay` and `recordUsage`, an unprivileged external client holding one valid signed JWT can fire two (or more) concurrent HTTP trigger requests and cause the workflow to be executed multiple times from a single authorization grant. This is an authentication/authorization-bypass-adjacent bug (bypassing the "used once" guarantee), which can result in unauthorized/duplicate job runs — directly impacting billing, side effects, or any downstream state change triggered by workflow execution.

### Likelihood Explanation
Exploitation requires only network-level concurrency (sending the same signed request twice at nearly the same time), which is trivial for any client that already possesses one valid JWT for a workflow — no additional privilege or secret is needed. The race window is bounded by the time to validate signer/authorized-keys (map lookups), so it is narrow but realistically exploitable by firing parallel requests.

### Recommendation
Make the check-and-record atomic: acquire a single lock covering both the existence check and the insertion (e.g., a `Lock()`/`defer Unlock()` around a combined "check-and-set" method that returns whether the `jti` was already present, similar to `sync.Map.LoadOrStore`), and reject the request if the `jti` was already present at the time of the atomic check, before proceeding with any downstream dispatch.

### Proof of Concept
1. Register a workflow and obtain one valid signed JWT (`jti = X`) as in `TestHttpTriggerHandler_HandleUserTriggerRequest` setup. [4](#0-3) 
2. Concurrently call `handler.HandleUserTriggerRequest` (or the underlying `Authorize`) from two goroutines with the identical JWT/request before either completes.
3. Both goroutines call `isReplay(X)` before either calls `recordUsage(X)`, so both pass and both proceed to `SendToNode`, resulting in two workflow executions from a single-use token, instead of the second failing with "token has already been used" as intended.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```
