### Title
B20 token creator can permanently disable all privileged token administration by setting `initialAdmin` to the zero address at creation - (File: `crates/common/precompiles/src/b20_factory/logic/v1.rs`)

### Summary
`createB20` lets the caller (an unprivileged B20 token creator, reachable via a plain user transaction to the `B20Factory` precompile) supply an `initialAdmin` address with no validation. If `initialAdmin` is the zero address, the factory silently skips granting `DefaultAdmin`, leaving the newly created token with zero `DefaultAdmin` role members forever, making every privileged/compliance function on that token (mint, burn, seize, pause, blocklist/policy updates, role management) permanently unreachable.

### Finding Description
`FactoryV1::create_b20` decodes creator-supplied `B20AssetCreateParams`/`B20StablecoinCreateParams`, including `initialAdmin: Address`, with no restriction other than a decimals/currency check. In `init_asset_token`/`init_stablecoin` the admin role is only granted `if !common.initial_admin.is_zero()`: [1](#0-0) [2](#0-1) 

There is no check preventing `initial_admin == Address::ZERO` from being accepted (unlike the `TokenAlreadyExists`/decimals/currency validations that do run). This is confirmed by the golden test which explicitly documents this as intended behavior: `initialAdmin = Address::ZERO` results in "grants no role": [3](#0-2) 

Once no account holds `DefaultAdmin`, every subsequent role mutation on that token is permanently blocked by `ensure_role_admin_mutations_available`, which reverts whenever `role_member_count(DefaultAdmin) == 0`, with no other code path capable of setting it (it can only be incremented via `grant_role`/`grant_role_unchecked`, both of which are gated behind an existing admin or the one-time factory bootstrap call): [4](#0-3) [5](#0-4) 

Because `grant_role`/`revoke_role`/`set_role_admin` for every role (`Mint`, `Burn`, `Seize`, `Pause`, `Metadata`, policy updates, etc.) all route through this same "admin mutations available" guard, or through `role_admin(role)` which itself defaults to `DefaultAdmin`, the token becomes an ungoverned, permanently-uncontrollable asset: no one can ever grant `Seize`, `Pause`, `BurnBlocked`, or update compliance policies (`updatePolicyCall` requires `DefaultAdmin`) on it.

This mirrors the Karak `NativeVault` bug class exactly: an unprivileged actor (there, the vault-creating operator; here, the B20 token creator) supplies an address parameter at creation time with no validation, and that unvalidated value silently and permanently disables a critical enforcement/compliance capability of the created asset (there, slashing; here, seize/pause/compliance-policy administration) for the entire lifetime of the contract, with no recovery path.

### Impact Explanation
Any address deployed via `createB20` with a zero (or otherwise deliberately abandoned/unreachable) `initialAdmin` becomes an asset that regulators/compliance operators can never seize, pause, or blocklist, and whose supply-cap/mint/burn roles can never be assigned. For a B-20 asset/stablecoin, this defeats the entire compliance and risk-control model built into the precompile (seize, pause, policy-gated transfers) — a core security guarantee of the protocol — with no way to recover once the token is created and initial admin omitted or set to zero/mistaken address. This is a permanent loss of the ability to enforce protocol-level compliance controls on a live, transferable asset, satisfying the "unauthorized operation / permanent freezing of the protocol's control mechanism" bar.

### Likelihood Explanation
`createB20` is a normal, permissionless entry point reachable by any user transaction (the "B20 token creator" role explicitly listed as an in-scope actor). Setting `initialAdmin` to `Address::ZERO` requires no special privilege and is demonstrated as an accepted, non-reverting path by the existing golden test suite itself, so it is trivially reproducible either by an attacker deliberately creating such a token, or accidentally by any integrator who forgets to pass a non-zero admin.

### Recommendation
Reject `createB20` calls where `initialAdmin == Address::ZERO` (or otherwise require and validate a non-zero admin for both `B20AssetCreateParams` and `B20StablecoinCreateParams`) in `TokenCreateParams::validate`/`check_version`, mirroring the existing `PolicyRegistry::createPolicy` guard that already rejects a zero admin (`zero_admin_create` test at `etc/systems/tests/policy_registry.rs`). Alternatively, allow zero-admin creation only if it is an explicit, clearly-labeled "immutable/no-admin" token variant, distinguished from the default variant so integrators cannot accidentally strand compliance controls.

### Proof of Concept
Using the existing golden test as a reproduction: [3](#0-2) 
1. Call `createB20` (ASSET variant) with `initialAdmin = Address::ZERO`.
2. `create_b20` succeeds and returns a token address; `has_role(DefaultAdmin, ZERO)` is `false` and no other account was granted the role.
3. Subsequently call `grantRole(Mint/Seize/Pause, anyAddress)` from any signer against this token — it reverts with `AccessControlUnauthorizedAccount { neededRole: DefaultAdmin }` as shown in `golden_grant_role_unprivileged_no_admin_reverts`: [5](#0-4) 
4. No address can ever obtain `DefaultAdmin` for this token afterward, so `seize`, `pause`, `updatePolicy`, and role-admin functions are permanently unreachable — the token is created "silently uncontrollable," analogous to Karak's silently unslashable `NativeVault`.

    /// Ensures role-admin mutations are still reachable.
    fn ensure_role_admin_mutations_available<S: AssetAccounting, A: PolicyAccounting>(
        &self,
        token: &B20AssetToken<S, A>,
        caller: Address,
    ) -> Result<()> {
        let admin_role = B20TokenRole::DefaultAdmin.id();
        if token.accounting().role_member_count(admin_role)? == U256::ZERO {
            return Err(BasePrecompileError::revert(IB20::AccessControlUnauthorizedAccount {
                account: caller,
                neededRole: admin_role,
            }));
        }
        Ok(())
    }
