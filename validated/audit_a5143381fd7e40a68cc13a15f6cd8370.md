## Finding

### Title
Stale confirmations from removed multisig members are counted toward the approval threshold, allowing requests to execute below the live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts every entry previously stored in a request's `confirmations` set toward `num_confirmations`, without verifying that each confirming member is still a current member of the multisig. `delete_member` only purges confirmations/requests that were *added* by the removed member, not confirmations that member previously cast on *other* still-open requests. This breaks the intended equality `confirmations counted == confirmations by live members`, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
`confirm()` reads the raw `HashSet<String>` of confirmations for a request and compares its size against `self.num_confirmations`: [1](#0-0) 

Nothing in this function checks whether the accounts/keys represented in `confirmations` are still present in `self.members`.

The only place stale confirmations are ever cleaned up is `delete_member`, and it only removes **requests whose original creator (`r.member`) equals the removed member**, deleting those requests (and their confirmation sets) wholesale: [2](#0-1) 

Crucially, this cleanup does not scan `self.confirmations` for entries where the removed member is one of the *confirmers* (but not the creator) of some other still-pending request. Those stale confirmation-strings remain in the request's `HashSet<String>` forever, and continue to count toward the `num_confirmations` threshold in `confirm()`.

`delete_member` does assert that `self.members.len() - 1 >= self.num_confirmations`, which only protects future/total-member accounting — it does nothing to invalidate confirmations already recorded by the removed member on requests created by other members.

Concrete break of the invariant "confirmations counted == live members who confirmed":
1. Multisig has members `A, B, C, D`, `num_confirmations = 3`.
2. `B` calls `add_request(X)` (e.g. a `Transfer`). `confirmations[X] = {}`.
3. `A` calls `confirm(X)`. `confirmations[X] = {A}` (count 1, below threshold, so it's just stored, not executed).
4. Members `B, C, D` (3 confirmations, satisfying threshold on a separate request) submit and confirm a `DeleteMember{A}` request. `A` is removed from `self.members`; `delete_member` scans and removes only requests where `r.member == A` (i.e. requests A itself created) — request `X`, created by `B`, is untouched, and its `confirmations[X] = {A}` set is left intact.
5. Now only `B, C, D` are live members. `B` calls `confirm(X)` → `confirmations[X] = {A, B}` (len 2, below 3, stored).
6. `C` calls `confirm(X)` → `confirmations.len() + 1 = 3 >= num_confirmations(3)` → `execute_request(X)` runs.

Request `X` executes with only 2 live-member approvals (`B`, `C`) plus one stale, no-longer-valid confirmation from the already-removed `A`, even though the contract is configured to require 3-of-current-members. This is a multisig request executed below the intended threshold, which is explicitly the type of solvency/authorization-boundary break in scope here (funds transferred, keys added, contracts deployed, etc., all go through `execute_request`).

The same structural gap exists in the sibling contract `multisig/src/lib.rs`'s `DeleteKey` action, which likewise only removes requests where `r.signer_pk == pk` and never scans other requests' `confirmations` sets for the removed key: [3](#0-2) 

### Impact Explanation
This crosses the authorization/threshold boundary explicitly called out as in-scope ("confirmations counted versus live members" and "a multisig request executed below threshold" is listed as a Critical impact). A member removed for being compromised, malicious, or simply offboarded can still have their historical confirmation "ride along" and be counted toward executing a `Transfer`, `AddKey`/`AddMember`, `DeployContract`, or arbitrary `FunctionCall` request that only a minority of the currently live members actually approved. Since `execute_request` can move NEAR (`Transfer`) or grant access (`AddKey`, `AddMember`), this is a direct path to unauthorized fund movement or privilege escalation below the configured quorum.

### Likelihood Explanation
No special privilege is required beyond being (at some point) a legitimate member who confirms an ordinary request that later remains pending while membership changes — a normal, expected sequence of multisig operations (open requests can remain pending indefinitely, and `delete_request` is even rate-limited by `REQUEST_COOLDOWN`, encouraging requests to sit open). Any of the remaining live members (potentially fewer than required threshold minus one) can then simply resume confirming the old request to push it over threshold. No signature forgery, race, or front-run timing is needed — it's a straightforward sequencing of standard `add_request`/`confirm`/`DeleteMember` calls.

### Recommendation
When a member is removed (`delete_member` in `multisig2`, `DeleteKey` in `multisig`), iterate over `confirmations` for *all* pending requests (not only those the removed member created) and strip the removed member's entry from each set. Alternatively, validate at `confirm()`-time / execution-time that every entry in a request's `confirmations` set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `B.add_request(X)` — a `Transfer` action to an attacker/target account.
3. `A.confirm(X)` — `confirmations[X] = {A}`.
4. `B/C/D` execute a `DeleteMember{A}` request (3 of 4 confirmations, valid quorum) — `A` removed from `members`; `confirmations[X]` untouched because `delete_member` only cleans requests created by `A`.
5. `B.confirm(X)` — `confirmations[X] = {A, B}`.
6. `C.confirm(X)` — count reaches 3, `execute_request(X)` fires, transferring funds, even though only `B` and `C` (2 of the 3 remaining live members) actually approved it as members at the time of execution.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
