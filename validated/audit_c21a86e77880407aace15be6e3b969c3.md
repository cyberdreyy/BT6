### Title
Silent loss of RPC pubsub notification registration on subscribe/unsubscribe race - (File: rpc/src/rpc_subscription_tracker.rs)

### Summary
The external report describes a bug class where an entity (a validator pending redelegation) is removed from tracking storage without properly recording that follow-up bookkeeping is still required, leaving the system in an inconsistent state that only surfaces later. The closest reachable analog in `agave` is in `SubscriptionControl::subscribe` in [1](#0-0) , which is invoked directly from unprivileged JSON-RPC pubsub subscribe calls such as `account_subscribe`/`accountSubscribe` handled in [2](#0-1) .

### Finding Description
`SubscriptionControl::subscribe` keys live subscriptions in a `DashMap<SubscriptionParams, WeakSubscriptionTokenRef>`. When a previous subscriber's `SubscriptionTokenInner` is in the process of being dropped (see `Drop` impl at [3](#0-2) ), the entry can still be `Occupied` with a now-dead `Weak` reference at the moment a new subscribe call for the same params acquires the DashMap entry lock. This "race window" is explicitly acknowledged in the code comment and exercised by the test `recreates_inner_when_weak_upgrade_fails` at [4](#0-3) .

In that branch, the code creates a brand-new `SubscriptionTokenInner`, reuses the stored `SubscriptionId`, and re-inserts the weak reference into the DashMap — but unlike the `Vacant` (fresh-subscribe) branch, it never sends a `NotificationEntry::Subscribed(...)` message on `self.0.sender`: [5](#0-4) 

Compare this to the `Vacant` branch which does send `NotificationEntry::Subscribed`: [6](#0-5) 

This `NotificationEntry::Subscribed` message is what registers the subscription with `SubscriptionsTracker` (the structure that actually drives notification delivery for accounts, logs, programs, signatures, slots, etc., per `SubscriptionsTracker::subscribe` at [7](#0-6) ). This is analogous to the reported bug: an entity (`SubscriptionTokenInner`) is "removed and re-created" in the front-line bookkeeping (the DashMap keyed by params) exactly like the validator being removed from the registry, but the corresponding pending registration action needed for correct downstream behavior is dropped/never scheduled — mirroring "the validator is removed from the storage, but there is not an adequate tracking of pending [operations] to be done later."

The practical effect: the client that hits this race receives a valid `SubscriptionId` back from the `accountSubscribe`/`programSubscribe`/etc. JSON-RPC call, appears successfully subscribed (it's present in `current_subscriptions` in [2](#0-1) ), but is never registered in `SubscriptionsTracker`, so it silently never receives any notifications for the lifetime of that subscription.

### Impact Explanation
This causes wrong/missing data to be delivered to an unprivileged JSON-RPC/pubsub client: the client is told (via successful subscription ID) that it is subscribed, but will never receive account/program/signature/slot notifications it is entitled to, with no error surfaced. This is a functional correctness defect in a client-facing, unprivileged code path (JSON-RPC pubsub subscriptions) reachable via `account_subscribe`, `program_subscribe`, `logs_subscribe`, `signature_subscribe`, etc.

### Likelihood Explanation
Triggering the race requires timing: a subscriber must drop a `SubscriptionTokenInner` (e.g., via an unsubscribe call or connection close) for a given `SubscriptionParams`, and a new subscribe for the identical params must land in the DashMap entry lock exactly while the drop is between checking `strong_count() == 0` and completing entry removal. This is inherently timing-dependent and not deterministically reproducible from a single isolated call; a single client could plausibly induce it by rapid subscribe → unsubscribe → resubscribe with identical parameters, but success is probabilistic rather than guaranteed. I was not able to fully trace, in the time available, the exact downstream consumer loop in `rpc/src/rpc_subscriptions.rs` that processes `NotificationEntry::Subscribed`/`Unsubscribed` messages to confirm there is no compensating recovery mechanism elsewhere — this should be verified with a full read of that file's `NotificationEntry` handling loop.

### Recommendation
In the `None` (stale-weak-upgrade) branch of `SubscriptionControl::subscribe`, send a `NotificationEntry::Subscribed(inner.params.clone(), id)` on `self.0.sender` just as the `Vacant` branch does, so that the recreated subscription is registered with `SubscriptionsTracker` and begins receiving notifications.

### Proof of Concept
Not independently reproduced in this session; the race is acknowledged and unit-tested for its bookkeeping/ID-reuse behavior (`recreates_inner_when_weak_upgrade_fails`), but that test only asserts `SubscriptionControl` counters, not that the recreated subscription is registered with `SubscriptionsTracker` and receives notifications — an end-to-end pubsub test exercising rapid subscribe/drop/resubscribe on the same params and asserting a subsequent notification is delivered would be needed to confirm exploitability.

    fn recreates_inner_when_weak_upgrade_fails() {
        // Exercise the race-window branch in `subscribe()` where a stale
        // `WeakSubscriptionTokenRef` is still in the DashMap because the
        // previous holder's `SubscriptionTokenInner::drop` is blocked on the
        // entry lock. A fresh subscribe must recreate the inner and reuse the
        // stored SubscriptionId rather than allocating a new one.
        let (sender, receiver) = bounded(1024);
        let (broadcast_sender, _broadcast_receiver) = broadcast::channel(42);
        let control = SubscriptionControl::new(2, sender, broadcast_sender);

        let stored_id = SubscriptionId::from(42);
        let dead_weak = {
            let arc = Arc::new(SubscriptionTokenInner {
                control: Arc::clone(&control.0),
                params: SubscriptionParams::Slot,
                id: stored_id,
            });
            let weak = Arc::downgrade(&arc);
            WeakSubscriptionTokenRef(weak, stored_id)
            // `arc` drops here; its Drop sees Vacant and logs a warning.
        };
        control
            .0
            .subscriptions
            .insert(SubscriptionParams::Slot, dead_weak);

        let token = control.subscribe(SubscriptionParams::Slot).unwrap();
        assert_eq!(token.id(), stored_id);
        assert_eq!(control.total(), 1);
        assert_eq!(control.subscriber_total(), 1);
        // Drain notifications emitted by the test (Drop-on-vacant warning is
        // log-only; the only entry should be the Subscribed from the recreate).
        while receiver.try_recv().is_ok() {}
        drop(token);
    }
