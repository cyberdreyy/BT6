### Title
Unprivileged lockup account squatting via unrestricted `owner_account_id`/`whitelist_account_id` in `LockupFactory::create` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the lockup contract's account id deterministically from `sha256(owner_account_id)[..20]` and lets the caller freely choose both `owner_account_id` and `staking_pool_whitelist_account_id`, with no check that the caller is the intended grantor or foundation. Any unprivileged account can pre-create the lockup for a victim's `owner_account_id` before the legitimate grantor does, permanently binding that victim's future lockup to an attacker-controlled whitelist.

### Finding Description
The claimed binding is: `LockupArgs.staking_pool_whitelist_account_id @ account(sha256(owner_account_id)[..20].<factory>) == the whitelist the real, intended grantor chose for owner_account_id`.

In `create`: [1](#0-0) 
the only guard is `attached_deposit() >= MIN_ATTACHED_BALANCE` (3.5 NEAR) — there is no check on `env::predecessor_account_id()`, no `assert_called_by_foundation`, and no requirement that the caller be `owner_account_id` or any privileged party. The account id is fully deterministic from `owner_account_id` alone: [2](#0-1) 
and `staking_pool_whitelist_account_id` is taken directly from the caller-supplied optional argument, defaulting only if omitted: [3](#0-2) 

Because the target account id only depends on `owner_account_id`, an attacker calling `create(owner_account_id="victim.near", ..., whitelist_account_id=Some("evil-whitelist.near"))` with the minimum deposit will have `Promise::new(lockup_account_id).create_account()...` succeed first (assuming the account doesn't already exist), deploying `CODE` with `LockupArgs.staking_pool_whitelist_account_id = "evil-whitelist.near"` under the attacker's chosen parameters at `hex::encode(sha256("victim.near")[..20]).<factory>`.

When the real grantor later calls `create` for `victim.near` with their intended (trusted) whitelist, `Promise::new(lockup_account_id).create_account()` fails at the protocol level because the NEAR account already exists. The callback `on_lockup_create` detects this via `is_promise_success()`: [4](#0-3) 
and simply refunds the legitimate grantor's deposit to `predecessor_account_id`, logging a failure — it does not revert or remove the attacker's already-deployed contract. The victim's lockup account permanently remains the attacker's contract instance, with the attacker's whitelist baked into its immutable `staking_pool_whitelist_account_id` state field.

No existing guard (`assert_self`, `is_promise_success`, `assert_owner`, etc.) prevents the initial unauthorized creation — those all operate after the fact on the callback, not on who is allowed to initiate `create` for a given `owner_account_id`.

### Impact Explanation
This directly matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." Once `victim.near`'s real grant/lockup is later provisioned (or if the victim/foundation is unaware and funds are moved into this squatted lockup account by other means), the account is permanently bound to the attacker's `staking_pool_whitelist_account_id`. Any staking action from that lockup (`select_staking_pool` / `deposit_and_stake`, per the standard lockup contract's whitelist-restricted staking flow) can only target pools approved via that attacker-controlled whitelist, letting the attacker later register/approve a draining or malicious pool. The blast radius is scoped to whichever `owner_account_id` the attacker chooses to front-run, and the attack is trivially repeatable across any number of victim account names for the cost of one minimum attached deposit each (refundable in most cases if unused, but the squatted contract itself persists).

### Likelihood Explanation
The attacker needs only: (1) knowledge/prediction of a victim account name that will eventually receive a lockup (grant recipients' NEAR account names are frequently public/predictable ahead of an on-chain grant), and (2) the `MIN_ATTACHED_BALANCE` (3.5 NEAR) to attach to the call. No special permissions, whitelisting, or privileged role is required — this is directly reachable by the generic unprivileged attacker profile defined in scope. The only limiting factor is winning the race against the real grantor's `create` call, which is a timing/observability problem, not an access-control one.

### Recommendation
Restrict `LockupFactory::create` so only the foundation/authorized caller (e.g. `assert_called_by_foundation` or a similarly enforced allow-list) can invoke it, or require `env::predecessor_account_id() == owner_account_id.as_ref()` so only the prospective owner (who holds no incentive to attack themselves) can trigger creation of their own lockup, closing the front-running window for third parties.

### Proof of Concept
```rust
#[test]
fn test_owner_account_squatting_locks_in_attacker_whitelist() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (unprivileged) front-runs create() for victim's owner_account_id,
    // picking their own whitelist.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35); // >= MIN_ATTACHED_BALANCE
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // stand-in for "victim.near"
        lockup_duration,
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // "evil-whitelist.near" equivalent
    );

    // Simulate the account_create promise succeeding for the attacker's call.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert!(contract.on_lockup_create(
        lockup_account(),
        ntoy(30).into(),
        String::from("attacker.near"),
    ));

    // Legitimate grantor now calls create() for the same owner_account_id.
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // Because create_account() on the already-existing derived account fails,
    // the legitimate call's callback observes failure, proving IDENTITY collision:
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    assert_eq!(res, false); // legitimate creation was rejected;
    // attacker's deployed contract with evil whitelist remains at lockup_account().
}
```
This demonstrates that `LockupArgs.staking_pool_whitelist_account_id @ lockup_account_id` equals the attacker's chosen value, not the value the legitimate grantor's `create` call attempted to set, breaking the claimed binding.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
