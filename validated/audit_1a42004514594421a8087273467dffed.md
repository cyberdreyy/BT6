### Title
Stale rejection weight is never retracted when a signer later accepts, letting a switched vote double-count toward both `total_weight_approved` and `total_weight_rejected` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
In the miner-side `StackerDBListener` message handler, an `Accepted` `BlockResponse` is only deduplicated against `block.gathered_signatures` (a map keyed by `slot_id` and populated *only* by the accept branch), while a `Rejected` response is deduplicated against the shared `block.responded_signers` set. Because the accept branch never checks `responded_signers` before adding weight, a signer who first rejects and later accepts the same block has their weight counted into `total_weight_rejected` *and* `total_weight_approved` simultaneously, with no code path ever subtracting the earlier rejection weight. This mirrors the Trader Joe `_cacheFees` bug class: a bookkeeping update is skipped/asymmetric across a state transition, letting a stale ledger entry (there: uncleared debt; here: uncleared rejection weight) coexist with the fresh, "correct" entry and corrupt an aggregate that downstream logic treats as ground truth.

### Finding Description
The relevant handler is in `handle_new_stackerdb_chunks`:

- `Rejected` path: gated by `if block.responded_signers.insert(slot_id) { ... total_weight_rejected += weight ... }` [2](#0-1) . Once a slot has responded (in either direction), this guard prevents a second reject-weight addition.
- `Accepted` path: gated only by `if !block.gathered_signatures.contains_key(&slot_id) { total_weight_approved += weight }`, then unconditionally `block.gathered_signatures.insert(slot_id, signature); block.responded_signers.insert(slot_id);` [3](#0-2) .

Because the accept branch's dedup key (`gathered_signatures`) is disjoint from what the reject branch already wrote into `responded_signers`, a signer that sends `Rejected` first (weight added to `total_weight_rejected`, and `responded_signers` marked) and later sends a validly-signed `Accepted` for the same `signer_signature_hash` will *also* have their weight added to `total_weight_approved`, since `gathered_signatures` was still empty for that slot. Nothing in this file, nor in the consumer `SignCoordinator::get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`), ever decrements `total_weight_rejected` when this happens [4](#0-3) . The `BlockStatus` struct that holds these two counters has no invariant enforcing that a slot's weight appears in exactly one of them [1](#0-0) .

This breaks the aggregated-weight vs. verified-responses equality that `SignCoordinator::get_block_status` relies on: it assumes `total_weight_rejected` reflects the weight of signers currently rejecting, and checks `total_weight_rejected + weight_threshold > total_weight` to decide the block is globally, irrecoverably rejected [5](#0-4) . With the stale double-count, `total_weight_rejected` can include weight from a signer who has since produced a valid signature accepting the block — inflating the rejection tally with weight that no longer represents a live rejection.

### Impact Explanation
A single signer (its own key, no majority, no other signer's key needed) whose weight is below the 30% blocking minority can flip Reject → Accept (e.g. an honest retry after a transient validation failure, or a deliberately timed flip by a Byzantine minority signer) and have that stale rejection weight permanently stuck in `total_weight_rejected`. Combined with genuine — but on their own insufficient — rejections from other signers, the miner's coordinator can cross the `> total_weight - weight_threshold` blocking-minority line and give up on a block via `NakamotoNodeError::SignersRejected` [6](#0-5) , even though the actual, current, distinct rejecting weight never reached the blocking minority and the block may simultaneously have crossed the 70% approval threshold with real signatures. This wedges block production for that proposal — a liveness failure that a minority signer (or an ordinary honest vote-flip under network jitter) can force without any majority collusion, matching the "liveness wedge" impact class.

### Likelihood Explanation
No special timing or majority collaboration is required: any signer that legitimately retries validation after an initial local rejection (a normal occurrence noted throughout the signer's own retry logic, e.g. `check_pending_block_validations`/re-proposal flows described in `docs/signer-flows.md`) can trigger the stale count purely as a side effect. A minority Byzantine signer can trigger it deliberately at will by rejecting first and accepting on cue.

### Recommendation
Track weight per-slot with a single canonical "current answer" (accept/reject) instead of two independently-latched booleans/maps. When an `Accepted` message supersedes a prior `Rejected` for the same `slot_id` (or vice versa), retract the old weight from the stale counter before adding it to the new one, e.g. maintain `HashMap<u32, Vote>` and recompute `total_weight_approved`/`total_weight_rejected` from that single source of truth rather than two independently-guarded running totals.

### Proof of Concept
1. Configure a reward set where signer S holds weight w such that `w < total_weight - weight_threshold` (below blocking minority) but other signers already reject with weight `r` where `r < total_weight - weight_threshold - w` (below blocking minority without S).
2. S sends a `Rejected` `BlockResponse` for hash H → `stackerdb_listener.rs` adds `w` to `total_weight_rejected`, marks `responded_signers.insert(S)`.
3. S then produces a valid signature and sends `Accepted` for the same H → the accept branch checks only `gathered_signatures`, which does not contain S, so it adds `w` again to `total_weight_approved`.
4. Now `total_weight_rejected == r + w`, which can be engineered to exceed `total_weight - weight_threshold`, while the *current* set of rejecting signers (excluding S, who switched) is only `r`, below the blocking minority.
5. `SignCoordinator::get_block_status` observes `total_weight_rejected + weight_threshold > total_weight` and returns `Err(SignersRejected)`, discarding a block that in reality never crossed the real blocking-minority rejection threshold and may have independently reached 70% approval.
